### Defects that block a high score

**1. Formal R1 + missing data is wrong as written (serious)**  
Pseudo-logic:
`R1_trigger  known(jur)  known(amount)  jurDE  amount100000`  
then `R1_ok  ¬R1_trigger  …`  
If jurisdiction is non-DE and amount is unknown, `R1_trigger` is false, so `R1_ok` becomes true. That silently treats missing amount as non-triggering, contrary to R6 and to the narrative/code (which correctly use a three-valued trigger). Bolting on a side predicate `R6_indeterminate` does not fix the broken biconditionals. For a formalization task this is a core flaw.

**2. R2 “relevant” review / freshness is under-specified in logic and code (serious)**  
Policy requires Enhanced_Review that is relevant to the HIGH/PEP state, and R1-style material change discipline is only half-applied.  
- Formal `R2_ok` only requires `Enhanced  Approve  Release` and amount-invalidation; it does **not** require Enhanced after the risk/PEP establishing change.  
- Code uses `enhanced_fresh` for R1 but **not** for R2 (`r2_ok = enhanced_usable and r2_order_ok`). A HIGH/PEP (or jurisdiction) change after Enhanced would still pass R2.  
No fixture exposes this, so the table stays lucky-correct; the rule encoding is still incorrect.

**3. R4 applied to R2 without defense**  
`InvalidForAmount` is folded into R2 in the pseudo-logic. R4 scopes invalidation to **amount-dependent** obligations; R2 is risk/PEP-driven. Over-binding without argument is a precision error (harmless on these rows only because the only post-review amount move is &lt;20%).

**4. Material-change definition is partly invented**  
Bundling every jurisdiction/risk/customer update plus only &gt;20% amount hikes as `M` is reasonable but not fully grounded in the rule text; R1’s “latest material data change” vs R4’s numeric test should be separated more carefully. Sub-20% updates are handled consistently with R4 in cases, which is good, but the formal layer blurs the sources.

**5. TX-302 label is slightly off-key**  
Fresh Enhanced_Review already satisfies R1 without EX-77. `JUSTIFIED_EXCEPTION` is not false, but `COMPLIANT` (with optional exemption) is the cleaner primary label; the write-up treats waiver as the headline path.

**6. Code requirement §8 only half-met**  
“Optionally” a DECLARE/trace-order check is absent; the control-flow insufficiency explanation lives in §6, not as a coarse executable screen beside the data checks. Minor versus (1)–(2), but incomplete relative to the spec checklist.
