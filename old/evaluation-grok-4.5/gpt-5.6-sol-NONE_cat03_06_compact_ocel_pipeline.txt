## Deductions (hypercritical)

### 1. Qualifier policy is internally inconsistent (0.5)
- e11 attaches Orders as `billed` (same token as V1).
- e12/e15 attach Orders *and* V1 as `invoice_context`, while M1/M2 get `payment_recorded`.
- Logistics uses `operational_context` / `package_content` / `delivery_content` for secondary links, but finance does not apply one clear primary-vs-context scheme.
- `item_added` on both Order and Item collapses distinct roles. Qualifiers remain “usable,” but not a clean vocabulary.

### 2. Stated O2O direction convention does not match all rows (0.4)
- Text: parent/context in `ocel:oid`, dependent/content in `ocel:oid_2`.
- Fits `Order contains Item`, `Package packs Item`, `Delivery carries Package`, `Invoice bills Order`.
- Fits poorly for `M1/M2  V1` under “parent/context  dependent.” Verb-subject framing would have been accurate; “parent/context” overclaims structural uniformity.

### 3. Narrative vs settlement labeling (0.4)
- Process text: “M1 and M2 are **partial** payments settling V1.”
- Model: M1 `partially_settles`, M2 `completes_settlement`.
- Requirements *allow* `completes_settlement`, so this is defensible, but the answer never reconciles the wording clash. Strict reading expects an explicit assumption.

### 4. Rich E2O policy underspecified as “source” vs “analytic” (0.3)
- §1 claims qualifiers prevent confusing propagation with source facts.
- In practice, Order links on Reserve/Pack/Dispatch/Confirm/Payment are analytic involvement, yet several use non-`operational_context` labels (`billed`, shared `invoice_context`).
- Provenance story is asserted more cleanly than it is encoded.

### 5. Data-model audit polish and precision (0.3)
- O2O pairs written `O100I1` without separators/arrows; weak against “compact tables” expectation.
- “Cardinality” column is just row counts (fine) but no note on many-to-many patterns (P1×items, V1×orders).
- Activitytype table is policy-true but flattens primary vs context participation.

### 6. Flattened DFG commentary is slightly mushy (0.3)
- Order edge list mixes universal edges with O100-only edges in one bullet stream; readable but easy to misread as one global DFG.
- Chronology of `Record Payment  Confirm Delivery` is correct, yet the “likely DFG edges” list underplays that this interleaving is a cross-lifecycle artifact of rich E2O, not an Order workflow law.
- Invoice: good warning on non-rework; still light on start/end and skeleton constraints.

### 7. OC discovery expectations hedge into vagueness (0.2)
- §5 correctly refuses a unique OC Petri net reading (good).
- OTG/ET–OT/interactions passages repeatedly defer to “depending on PM4Py version” without committing to the concrete co-occurrence patterns *this* relation set must induce (e.g., definite Order–Payment edge under their policy). Residual vagueness for a section that should predict *this* model.

### 8. Minor code/product nits (0.3)
- Extra `currency_unit="MU"` is harmless but unexplained.
- `assert set(objects) == set(relations[oid])` bakes “every object must appear in E2O” into validity; defensible under their rich policy, not a general OCEL integrity rule—should be framed as policy check.
- Commented viz names acknowledged; discovery APIs match the *prompt’s* spellings (no penalty), but there is no defensive `getattr`/try structure despite §1 version warnings—minor robustness gap for “executable-looking.”
- No assert that pack/dispatch E2O item sets match O2O `packs` content (easy semantic check omitted).

### 9. Not wrong, but overlong padding (0.0 structural; style only)
- §6 lists five alternatives; §7 fourteen failure modes; §8 fourteen checks. Quality is high; some items repeat. No hard penalty.
