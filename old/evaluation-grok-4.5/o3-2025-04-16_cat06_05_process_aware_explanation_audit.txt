## Section 1 — Leakage table

**Strengths**
- Correctly flags the hard leaks: `total_case_duration_hours`, `appeal_seen_anywhere`, `full_trace_variant_id`, `final_decision`, full-trace document totals, future sequence patterns involving Appeal / Settlement / full paths.
- Correctly notes `prior_claim_count_before_t0` SQL bug and `same_day_document_count_snapshot` intraday leak.
- Correctly treats `queue_length_at_t0` and `elapsed_since_registration_at_t0` as largely admissible.
- Same-timestamp `Claim Closed → Damage Assessment` impossibility + missing index is well handled.
- Distinguishes `Appeal → Settlement Decision` (future-only at t0) from the impossible closed-before-assessment pattern in spirit.

**Critical / high defects**
1. **`Documents Requested → Documents Received` marked “potentially valid / Low” is wrong for this prediction time.**  
   Normative process: after Coverage Check, evidence cycles are *future-possible*, not already in the prefix. At t0 the given prefixes are only `Claim Registered → Coverage Check Completed`. A global sequence explainer attributing impact to DOC→DOC at *this* t0 is using post-t0 (or non-prefix) structure unless each instance is proven ≤ t0. Calling it “no issue” / keep is a process-consistency error, not a minor caveat. Severity should be high for use in early explanations, with “keep only if timestamps ≤ t0” as remediation—not a clean pass.

2. **`Coverage Check Completed → Fraud Investigation Opened` as unconditionally “Valid / no action” is overstated.**  
   Fraud *may* open after a trigger and can run in parallel later; it is not guaranteed enabled immediately at first coverage completion for every case. As a *learned* pattern it can be predictive if the open event is ≤ t0; as a blanket “valid prefix signal” with no enablement check it overclaims. The task asked to distinguish enabled vs merely future-possible.

3. **`Damage Assessment Completed → Settlement Decision Recorded`:**  
   Saying damage assessment is “*always* after t0” is too strong. Fast-track damage assessment can follow coverage check; it is after t0 in the sense of not yet in the *minimal* prefix, but the pattern is future-relative to t0, not metaphysically impossible. Misstatement of process timing.

4. **`final_handler_team` severity High while duration/appeal/variant are Critical** is defensible, but the answer never states the 65% equality-to-t0 team fact as a *correlated mutable/lineage* issue (team-at-closure ≠ team-at-t0; warehouse lacks availability timestamp). Incomplete lineage story.

5. **Missing or thin coverage of required items**
   - Local-only / lineage notes: employee experience joined as-of extraction is mentioned in the prompt and never audited.
   - `num_document_requests_total` remediation (“requests before t0”) is right in principle but at true t0 that count is typically 0—should note null/zero informativeness at this cut, not imply it becomes a strong early warning after a trivial filter.
   - Severity column uses “–” instead of the required critical/high/medium/low scale for several rows (`initial_damage_complexity`, etc.), violating the specified table contract.
   - `appeal_seen_anywhere` remediation “appeal already filed by t0, which is impossible by definition” is slightly over-absolute (pathological data errors aside) but more importantly collapses “feature always 0 at t0 ⇒ zero information” with “remove”—fine, but then Case explanations should not treat appeal as a learned signal at all.

6. **`calendar_week` / `claimant_region`**  
   Reasonable medium severity, but “fairness & drift monitoring” for calendar_week mixes fairness with operational drift; calendar is primarily drift/policy/holiday proxy, not a classic protected-class fairness feature (region is). Blurry standards.

7. **Team causal slogans** (“Appeals cause breaches”, “final team determines delay”) are never systematically debunked in Section 1; only feature availability is. The task required distinguishing predictive vs causal presentation.
