### 3. Canonical signature is not a real equivalence key
The Python-like scheme is not reproducible in the sense required:

- It never builds a **rename-invariant** object role graph (no canonical coloring / typed isomorphism / sorted multiplicity vector by structural role).
- Multiplicities keyed by `(obj_type, event.activity)` lose packaging topology (one package of two items vs two packages of one; consolidated vs split delivery).
- `cross_order_sharing` keeps raw `obj_id` strings—unstable and not a clean EXT flag abstraction.
- Lifecycle extraction (`f"{obj_type}:{relation}"`) is underspecified relative to the given O2O notes (contains / packs / carries / bills / settles / replaces / `removed_before_dispatch` / partial settlement).
- Qualifiers are appended without normalizing endpoints, so the key is not clearly a function of the execution up to local renaming.
- Final `tuple(sorted(...))` over a heterogeneous dict does not reliably freeze nested `defaultdict`/`set` structure.

A “preferred” business-semantic key must distinguish at least: isolated baseline, split-pack consolidate-deliver, split-pack split-deliver + multi-payment, logistics EXT share, finance EXT share, replacement/removal qualifier, return-repack. This code does not clearly do that.
