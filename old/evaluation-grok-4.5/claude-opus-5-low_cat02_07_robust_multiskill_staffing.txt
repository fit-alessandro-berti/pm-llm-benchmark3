### Major defects (each costly)

**1. `mean_delay` is methodologically wrong for ME/ES under parallelism (silent)**  
Code accumulates `svc` as the **sum** of branch service draws, while `flow` follows the **parallel wall-clock path** (`max` of branches + coordination). Then `mean_delay = flow - svc`. For parallel multi-branch cases this subtracts roughly `min(d1,d2)` too much, so delay is biased down (can approach zero/negative contribution from the short branch). §4’s headline policy ranking on `mean_delay` / several “P_pool wins O1” claims inherit this bias. The error is not disclosed in the omission list.

**2. Simulated policies  described policies**  
Narrative P_pool/P_hybrid use least-slack / EFT re-dispatch, preemption rules, overflow T1–T4, and mode switches. The engine is **arrival-ordered greedy full-case booking** on a free-segment calendar: no event-driven queue, no least-slack competition at completions, **preemption not executed**, overflow/mode switch **not implemented**. §5’s primary recommendation *is* the mode-switching hybrid; §4’s table is mostly a different object (static reservation hybrid). Claiming U1/U2/U5 P1 patterns “as predicted by reserved capacity” overreaches what the code can show—especially with P1 n5–8/day and 6 seeds (SE on P1_SLA large; answer admits noise then still leans on signed gaps).

**3. Priority / P1 protection is only half-real in the engine**  
Because cases are scheduled in arrival order against a day-long calendar, earlier P2/P3 work can still lock future segments in ways a true priority shop-floor dispatcher would not. Reservation removes some eligibilities, but this is not equivalent to the stated slack/preemption design. Preemption and the 10% restart penalty—central in the scenario—are omitted while still discussed as if policy-differentiating.

**4. Offered-load model over-funges capacity**  
Block load/capacity ratios treat minutes as transferable across skills. The writeup later notes “no Mechanical after 18:00,” which is correct and important, but the audit table’s 1.09 and several bottleneck severities are softened by fungibility. Skill-period feasible capacity (Mechanical evening, Software morning under U3, Intake under outage) should have been the primary load objects.

**5. Objective–metric mismatch**  
O2 is defined with CVaR% and worst-scenario scoring; the comparison table uses `p90_flow`, noisy P1_SLA, and narrative resilience labels. O3’s fairness/robustness terms are only loosely tied to a scalar decision rule. Fine as rhetoric; weak as “objective formulations” that actually select the winner.
