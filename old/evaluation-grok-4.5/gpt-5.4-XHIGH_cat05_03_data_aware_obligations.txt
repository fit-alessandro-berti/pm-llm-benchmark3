## Grading rationale (strict)

The submission is strong: correct required structure, generally accurate event-time reasoning, and mostly right case outcomes. It is **not** near-flawless. Under a hypercritical bar, several real defects block a high-9/10.

### What is genuinely good
- **Case outcomes are largely correct** for TX-301–TX-311: material R4 invalidation (301, 309), R2 gaps (303, 307), sanctions re-screen (304), unknown amount (305), sub-20% increase (306), decrease non-invalidation (308), weak EX-88 (310), and `event_index` tie-break with release-time DE (311).

### Defects that lower the score

**1. Material formalization bug on R2 × R6 (serious)**  
Pseudo-logic and code both do:

- INDETERMINATE only if *both* `risk_level` and `customer_type` are unknown  
- else if HIGH/PEP  require controls  
- else  not triggered  

That is wrong. If `risk_level` is unknown and `customer_type` is known non-PEP, HIGH cannot be excluded under R6. Trigger status is **undecidable**, not “not triggered.” Correct 3-valued treatment: established / excluded / indeterminate. This is a direct logic error in the required formalization, even if no fixture hits it.

**2. Code does not implement the author’s own R1 material-change rule**  
Narrative/pseudo-logic treat jurisdiction and customer-type changes (plus >20% amount up) as R1-material, requiring `Enhanced_Review` after the latest such change. The evaluator only checks `r4_invalidates_enhanced` (amount >20%). `last_material_data_change` is computed then mostly unused for R1’s ordering obligation. That is an internal inconsistency between §2 and §5 and an incomplete operationalization of R1.

**3. R3 formalization is fragile**  
`ls  lu` is ill-defined when no prior `Sanctions_Screen` exists. The rule text is conditional on “after the latest Sanctions_Screen,” but the logic should state the empty-screen case explicitly. Minor, but sloppy for a “normalized” rule table.

**4. Coarse R1 satisfaction is under-specified in code**  
`REVIEW_PRESENT` if any pre-release ER survives R4 amount invalidation—no check that ER  all R1-material changes, no packet/content binding, no same-timestamp discipline beyond sort order. Acceptable as “coarse,” but weaker than the prose claims.

**5. Classification/evidence nits (smaller)**  
- TX-310 as `NONCOMPLIANT` is defensible (no ER; EX-88 not established under R5), and medium confidence helps; given contradictory evidence, a stricter reading could demand `INDETERMINATE` on the exemption limb while still failing R1—confidence/severity rubric is never defined.  
- `JUSTIFIED_EXCEPTION` is never used; fine, but TX-302’s dual path (ER **and** strong EX-77) could be sharper about primary vs backup basis.  
- `material_data_change` treats first non-null as a change (`NA != value`), adding noise to “latest material change.”  
- Optional PM4Py variant API/`format_dataframe` usage is version-sensitive; not shown run.

**6. Aggregation gap**  
Rules can yield mixed triggered/satisfied/indeterminate results; there is no explicit case-level composition policy (e.g., any NONCOMPLIANT wins; any undecidable trigger  INDETERMINATE unless overridden). Case table implies one, but §2 never states it.
