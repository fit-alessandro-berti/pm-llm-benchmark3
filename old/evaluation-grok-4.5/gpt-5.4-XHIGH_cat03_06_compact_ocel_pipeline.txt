### Deductions (hypercritical)

1. **Settlement semantics overstated (moderate)**  
   Narrative: “M1 and M2 are partial payments settling V1.”  
   Code marks `M2 -> V1` as `completes_settlement`. That is a defensible *choice*, but it is not given as fact. Treating M2 as completion invents allocation/finality the process text does not state. E2O then uses a third label (`settles_invoice`) for the same business link, so qualifier vocabulary is slightly inconsistent across E2O/O2O.

2. **E2O qualifier quality is uneven (moderate)**  
   Vocabulary is large but weakly principled: `order_subject` vs `container_order` vs `demand_order` vs `fulfilled_order` vs `dispatched_for_order` vs `confirmed_for_order`.  
   `fulfilled_order` on pack events overclaims lifecycle progress (pack  fulfill).  
   Confirm-delivery rows attach packages as `confirmed_package` even though the named act is delivery confirmation; justifiable under a rich policy, but not tightly motivated and easy to confuse with O2O `carries`.

3. **Validation looks stronger than it is (minor–moderate)**  
   Activity/timestamp consistency is checked only after `relations` was populated *from* `events` by merge, so that assert is largely circular.  
   Useful checks are missing: every event has 1 relation; every object appears in E2O or O2O as intended; qualifier set is closed/expected; no unexpected object types on an activity.  
   `str(events["ocel:timestamp"].dt.tz) == "UTC"` is brittle across pandas/tz implementations.

4. **Flattened-trace / DFG predictions slightly incomplete (minor)**  
   Order DFG discussion notes `Pack Package -> Pack Package` and `Dispatch Package -> Dispatch Package` for O100 but not the equally present `Add Item -> Add Item`.  
   Omitted-aspects text is good on payments and shared P1, but could be sharper that order flattening also drops payment objects entirely *by deliberate E2O policy*, not only “settlement sequence.”

5. **API/execution residual risk (minor)**  
   Constructor isolation is documented correctly, but several discovery helpers (`discover_etot`, `discover_otg`, `ocel_objects_interactions_summary`, `view_ocpn`) are taken exactly from the prompt with no defensive capability probes. That matches the task’s naming, yet a truly production-grade “executable-looking” script would isolate those the same way as `OCEL(...)`. Not a semantic error; still a robustness nit.

6. **Small clarity / audit nits (minor)**  
   Section 3 activity table is correct at type level but does not surface *which* orders/packages make e07/e09/e11/e13 consequential (that appears later, not in the audit table).  
   Section 5 OC-DFG/OTG prose is right about P1 and V1 but a bit loose on whether “invoice lifecycle” on orders includes payments (it does not, under their model).
