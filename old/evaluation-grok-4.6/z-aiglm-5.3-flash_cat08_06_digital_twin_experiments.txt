**6.5**

The design write-up is substantively strong: it hits all eight required sections, treats non-stationarity and cross-case dependence as first-class (NHPP, architect bursts, inspection batching, latent shared objections, shared calendars), refuses to inject empirical waiting as a delay, treats objections as unobserved, and does not claim optimality. That is well above a typical “independent M/M/1 per case” answer. Under a hypercritical reading, however, there are enough specification, statistical, and skeleton defects that it is not close to flawless.

**What holds up**
- Scope, entities, queues, calendars, and AND-join state for decision drafting are clear; resource pools match the brief (Monday clerk diversion, simple-only planners, fire Tue–Thu, env 60% duty, council-week legal shutdown).
- The planning-capacity arithmetic (~3.5 h × ~58 starts/day vs 8×8 h) is the right diagnostic: logged “service” is elapsed/multi-touch, not FTE consumption. Waiting is correctly reserved as a validation target.
- Objections are a mixture on notice duration minus a 14-day floor, not fake log events. D9 is correctly labeled as the least identifiable lever.
- Experiment matrix includes baseline, D1–D9, D10, extra combinations, and five stress cases, with CRN, Welch warm-up, paired CIs, bootstrap parameter uncertainty, tail-model caution, and Holm correction.
- PM4Py usage follows the stated conventions: pandas ingest (no `pm4py.read_csv`), `format_dataframe`, variants, DFG, performance DFG, `parse_process_tree` with an honest fallback, and a real split between log/model code and the DES.

**Defects that pull the score down**

1. **Skeleton is not coherent.** `end_activities` is assigned with `if False else dict(start_acts)`, so a required diagnostic is wrong on purpose. `waiting_days_est` uses the same dead `if False` pattern. `PermitDigitalTwin.run` calls undefined `SeedStreamHelper` while `SeedManager` sits unused. E10 in code is only D1+D2, not D1+D2+D3+D4. `TwinParameters` is `pass`. That fails the “coherent, modular” bar even for a skeleton.

2. **The one implemented arrival generator is broken.** Thinning mixes a float day-offset with `pd.Timestamp` (`t_now + t`, then `.month` / `.dayofweek`). Weekend intensity is `0.0`, but the excerpt itself has a Saturday portal submission (P002, 2026-01-03) and a Sunday completeness check (2026-01-04) — evidence the calendar leaks or weekends are real. `ResourceCalendar.is_open` never consults `WEEKLY` hours, so the advertised shift structure is unused.

3. **D5 is mis-specified.** “Parallelize legal pre-check” is implemented as legal start *after planning completion*. That only overlaps notice/inspection, not planning/fire/env.

4. **Identification vs validation circularity.** Service/wait split is to be chosen so utilization matches the log, and utilization is also a primary validation test. The 3-level split scenario only partly breaks that loop; it is not acknowledged as a weak identification design.

5. **Warm-up vs tails.** Complex p90 is 260 days; warm-up is 90 days. Backlog seeding and “extend if Welch still drifts” mitigate this, but a 90-day default is too short for the process they themselves describe.

6. **Numeric levers are often invented without flags.** Jun–Aug 1.2×, D1 clerk +15% / missing-doc ×0.45, rework service 0.7×, travel “30–50%” (reduction vs remaining is ambiguous), fairness 1.25× vs 1.15×. Some of this is inevitable; several items are not marked as assumptions.

The conceptual twin is usable as a design. The executable/PM scaffolding and a few intervention mappings are not tight enough for a high score under a strict rubric.
