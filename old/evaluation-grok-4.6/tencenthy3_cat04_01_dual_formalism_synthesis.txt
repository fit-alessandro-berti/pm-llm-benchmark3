# 1. Assumptions and Interpretation

1. **Low-risk / high-risk.** The data attribute is not modelled. Control flow is an exclusive choice after `Analyze Root Cause`: the low-risk branch is exactly `Supervisor Review`; the high-risk branch is the pair `Quality Review` and `Regulatory Review`, concurrent and unordered. Exactly one branch is taken. The two reviews never appear on a low-risk path, and `Supervisor Review` never appears on a high-risk path.

2. **Optional supplier consultation.** `Consult Supplier` is an exclusive choice against a silent skip (`tau`). It occurs at most once. The choice node is enabled only after `Analyze Root Cause`. If the visible branch is taken, that completion is a prerequisite of `Release Material`. If the silent branch is taken, release does not wait for a supplier event. Selection is treated as an unobserved case attribute.

3. **Passing inspection.** There is no pass/fail label. A trial cycle is `Execute Trial` then `Inspect Trial`. Failure-plus-rework is the loop redo `Adjust Parameters` followed by another cycle. Loop exit after `Inspect Trial` is the abstraction of a passing inspection. `Adjust Parameters` is therefore impossible after the last `Inspect Trial`.

4. **Duplicate visible labels.** Not used in either model. Every visible activity has a single labelled node. Silent nodes are unlabelled.

5. **Process-tree approximation policy.** An exact block-structured tree is impossible: after `Analyze Root Cause` the model must fork `Design Corrective Action`, the risk route, and optional supplier, join only `{Plan Verification, Design Corrective Action}` into the trial, keep the risk route concurrent with the trial, and join `{trial, risk route, supplier-if-selected}` at release. That DAG is not series-parallel. The tree is a **conservative under-approximation**: it adds waits that the narrative does not require, and it does not admit any completion order that the narrative forbids. Concretely, the risk route and supplier choice are delayed until both `Plan Verification` and `Design Corrective Action` have completed. Approval∥trial and supplier∥trial are kept.

6. **“May overlap”.** Interpreted as **absence of a precedence constraint**, i.e. interleaving concurrency (and, in a step semantics, possible simultaneity). It is not modelled as a fixed but arbitrary sequence. In the tree this is `PARALLEL`. In POWL it is the lack of an order edge.

7. **Recording semantics.** Each label is a single completion event. Start timestamps and data guards are out of scope.

8. **Loop and XOR over-approximation (both models).** Because pass/fail, risk, and supplier involvement are not labels, both models generate every combination of those choices. That is required by the brief; it is not extra process-tree loss.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
| --- | --- | --- | --- | --- |
| D1 | (process start) | `Register Deviation` | precedence | Every case starts here. |
| D2 | `Register Deviation` | `{Contain Material, Analyze Root Cause}` | fork / concurrency | The two streams are independent after registration and may overlap. |
| D3 | `Contain Material` | `Plan Verification` | precedence | Planning starts only after containment completes. |
| D4 | `Analyze Root Cause` | `Design Corrective Action` | precedence | Design starts only after root-cause analysis completes. |
| D5 | `Analyze Root Cause` | risk-route choice | precedence + XOR | Risk is selected after analysis: `Supervisor Review` XOR (`Quality Review` ∥ `Regulatory Review`). |
| D6 | `Quality Review` | `Regulatory Review` | concurrency | High-risk reviews have no mutual order. |
| D7 | `Analyze Root Cause` | supplier choice | precedence + optional XOR | `Consult Supplier` XOR `tau`; at most one visible supplier event; enabled only after analysis. |
| D8 | `{Plan Verification, Design Corrective Action}` | trial loop | synchronization (AND-join) | `Execute Trial` may start only when both work products exist. |
| D9 | trial loop | `Execute Trial` → `Inspect Trial` | sequence + LOOP | A cycle is execute then inspect; redo is `Adjust Parameters`; repeat until the silent exit (pass). |
| D10 | `Adjust Parameters` | next `Execute Trial` | precedence inside redo | Adjustment is only the bridge into a new cycle, never after the passing inspection. |
| D11 | risk route | trial loop | concurrency | Approvals need not finish before the trial and may overlap it. |
| D12 | supplier (if selected) | `{design, plan, approvals, trial}` | concurrency | Supplier work may overlap those activities. |
| D13 | `{passing Inspect Trial, completed risk route, supplier-if-selected}` | `Release Material` | synchronization (AND-join) | Release waits for all three obligations that apply to the case. |
| D14 | `Release Material` | `Archive Case` | precedence | Archival is strictly last. |
| D15 | `Archive Case` | (process end) | precedence | Every case ends here. |

# 3. PM4Py Process-Tree Model

Compact expression (PM4Py text: `->` sequence, `+` parallel, `X` exclusive choice, `*` loop with do/redo, `tau` silent):

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->('Analyze Root Cause', 'Design Corrective Action')
  ),
  +(
    *( ->('Execute Trial', 'Inspect Trial'), 'Adjust Parameters' ),
    X( 'Supervisor Review', +('Quality Review', 'Regulatory Review') ),
    X( 'Consult Supplier', tau )
  ),
  'Release Material',
  'Archive Case'
)
```

Mapping: the first `+` is the two initial streams; the second `+` is trial ∥ risk route ∥ supplier choice; `*` is “do execute–inspect, redo adjust”; each `X` is a data-free alternative.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    return ProcessTree(label=label)


def op(operator, children):
    node = ProcessTree(operator=operator)
    for child in children:
        child.parent = node
        node.children.append(child)
    return node


reg = leaf("Register Deviation")
contain = leaf("Contain Material")
analyze = leaf("Analyze Root Cause")
plan = leaf("Plan Verification")
design = leaf("Design Corrective Action")
supervisor = leaf("Supervisor Review")
quality = leaf("Quality Review")
regulatory = leaf("Regulatory Review")
supplier = leaf("Consult Supplier")
execute = leaf("Execute Trial")
inspect = leaf("Inspect Trial")
adjust = leaf("Adjust Parameters")
release = leaf("Release Material")
archive = leaf("Archive Case")
tau_supplier = ProcessTree(label=None)

contain_then_plan = op(Operator.SEQUENCE, [contain, plan])
analyze_then_design = op(Operator.SEQUENCE, [analyze, design])
initial_streams = op(Operator.PARALLEL, [contain_then_plan, analyze_then_design])

trial_cycle = op(Operator.SEQUENCE, [execute, inspect])
trial_loop = op(Operator.LOOP, [trial_cycle, adjust])

high_risk = op(Operator.PARALLEL, [quality, regulatory])
risk_route = op(Operator.XOR, [supervisor, high_risk])
supplier_choice = op(Operator.XOR, [supplier, tau_supplier])

concurrent_suffix = op(Operator.PARALLEL, [trial_loop, risk_route, supplier_choice])

tree = op(
    Operator.SEQUENCE,
    [reg, initial_streams, concurrent_suffix, release, archive],
)
```

The tree cannot start the risk route or supplier consultation as soon as root-cause analysis finishes. Both wait for the AND-join of `Plan Verification` and `Design Corrective Action`. They therefore cannot overlap planning or design, even though the narrative allows that. The tree also cannot let containment finish after approvals have already started. Those missing traces are excluded on purpose (under-approximation). The tree does represent exactly: start/end, containment before planning, analysis before design, XOR risk routes, concurrent high-risk reviews, optional single supplier, execute–inspect cycles with adjust only as redo, approval∥trial, supplier∥trial, and release after trial, chosen approvals, and supplier-if-selected.

# 4. PM4Py POWL Model

```text
nodes:
  RD, CM, AR, PV, DC,
  Risk = XOR(SR, PO{QR, RR}),
  Sup  = XOR(CS, tau),
  Trial = LOOP( PO{ET < IT}, AP ),
  RM, AC

edges:
  RD < CM, RD < AR
  CM < PV
  AR < DC, AR < Risk, AR < Sup
  PV < Trial, DC < Trial
  Trial < RM, Risk < RM, Sup < RM
  RM < AC
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

rd = Transition(label="Register Deviation")
cm = Transition(label="Contain Material")
ar = Transition(label="Analyze Root Cause")
pv = Transition(label="Plan Verification")
dc = Transition(label="Design Corrective Action")
sr = Transition(label="Supervisor Review")
qr = Transition(label="Quality Review")
rr = Transition(label="Regulatory Review")
cs = Transition(label="Consult Supplier")
et = Transition(label="Execute Trial")
it = Transition(label="Inspect Trial")
ap = Transition(label="Adjust Parameters")
rm = Transition(label="Release Material")
ac = Transition(label="Archive Case")
tau_supplier = SilentTransition()

high_risk = StrictPartialOrder(nodes=[qr, rr])

risk_route = OperatorPOWL(operator=Operator.XOR, children=[sr, high_risk])
supplier_choice = OperatorPOWL(operator=Operator.XOR, children=[cs, tau_supplier])

trial_body = StrictPartialOrder(nodes=[et, it])
trial_body.order.add_edge(et, it)
trial_loop = OperatorPOWL(operator=Operator.LOOP, children=[trial_body, ap])

powl = StrictPartialOrder(
    nodes=[rd, cm, ar, pv, dc, risk_route, supplier_choice, trial_loop, rm, ac]
)
powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, ar)
powl.order.add_edge(cm, pv)
powl.order.add_edge(ar, dc)
powl.order.add_edge(ar, risk_route)
powl.order.add_edge(ar, supplier_choice)
powl.order.add_edge(pv, trial_loop)
powl.order.add_edge(dc, trial_loop)
powl.order.add_edge(trial_loop, rm)
powl.order.add_edge(risk_route, rm)
powl.order.add_edge(supplier_choice, rm)
powl.order.add_edge(rm, ac)
```

Unconnected pairs stay concurrent because no required order exists between them: `Contain Material` and `Analyze Root Cause`; `Plan Verification` and `Design Corrective Action`; `Plan Verification` and the risk/supplier nodes; `Design Corrective Action` and the risk/supplier nodes; the trial loop and the risk route; the trial loop and supplier choice; the risk route and supplier choice; `Quality Review` and `Regulatory Review` inside `high_risk`. Adding any of those edges would invent a wait the narrative does not impose.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
| --- | --- | --- | --- | --- | --- |
| Two initial work streams | After RD, CM ∥ AR | `+(CM→PV, AR→DC)` | RD≺CM, RD≺AR, no CM–AR edge | Tree: exact on this pair. POWL: exact. | Containment and analysis can proceed without a false mutual wait. |
| Split dependencies into planning/design | PV only after CM; DC only after AR; PV incomparable with DC | Encoded by the two sequential arms | CM≺PV, AR≺DC, no PV–DC edge | Both exact | Planning is not blocked by analysis; design is not blocked by containment. |
| Risk route | After AR: SR XOR (QR ∥ RR) | XOR/AND subtree, but enabled only after PV∧DC | XOR node with AR≺Risk | Tree overconstrains enablement (extra wait for PV∧DC). POWL exact. | Tree reports late approval start as non-fitting even when legally early. |
| Overlap of approval and trial | Risk route ∥ trial; both precede RM | Second `+` keeps them concurrent | no Risk–Trial edge; both ≺ RM | Both exact on overlap; tree still starts approvals too late | Cycle-time models that use the tree understate achievable overlap. |
| Optional supplier consultation | After AR, at most once, ∥ design/plan/approvals/trial, ≺ RM if selected | XOR vs `tau` in the second `+` | XOR vs silent, AR≺Sup≺RM | Tree overconstrains start (cannot overlap PV/DC). Cardinality and release wait are exact in both. | A real log with CS during design will fail the tree and fit POWL. |
| Repeat-until trial | (ET IT)(AP ET IT)* ; no AP after last IT | LOOP(do=ET→IT, redo=AP) | same LOOP | Both exact for the label abstraction; both underconstrain the hidden pass/fail bit | Arbitrary numbers of rework cycles are generated; inspection quality is not checkable from labels. |
| Release synchronization | RM after passing IT, chosen approvals, and CS if selected | Sequence after the second `+` | Trial≺RM, Risk≺RM, Sup≺RM | Both exact for the obligations they place in that join | Premature release is excluded; tree additionally refuses some legal pre-release interleavings (T5). |
| Duplicate-label risk | Single occurrence of each activity name | No duplicates | No duplicates | Neither under- nor over-constrains via copies | Discovery/conformance will not split frequencies across cloned labels. Duplication was avoided because it would make two “same” steps look like distinct tasks. |

# 7. Preferred Representation and Validation Plan

**Canonical representation: the POWL model.** It states the non-series-parallel waits as edges and leaves everything else unordered. The tree can only match that graph by adding barriers or by cloning visible work. The conservative tree is useful as a sound, stricter skeleton (e.g. a safe scheduling envelope) but it is not faithful enough to be the system of record.

Validation plan:

1. **Accepting Petri-net conversion.** `net, im, fm = pm4py.convert_to_petri_net(powl)` and the same for `tree`. Treat a successful conversion as a well-formedness check, not as proof of fidelity to the narrative.

2. **Soundness.** `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on both converted nets. Require option to complete, proper completion, and no dead transitions among visible labels. Silent skip and loop-exit silents may be dead only if a construction error made a branch unreachable.

3. **Bounded / sampled playout.** `pm4py.play_out` on each net with a cap on visible length (e.g. at most two `Adjust Parameters` events). Inspect the sample for: RD first, AC last, no AP after the last IT, no ET before both PV and DC in the POWL net, and presence of both low-risk and high-risk variants.

4. **Positive and negative trace tests.** Build a small log with T1–T5 as expected positives for POWL, T1–T4 as expected positives for the tree, T5 as an expected tree negative, and T6–T8 as expected negatives for both. Decide membership with alignments or token replay against the converted nets. A mismatch is a model or conversion defect.

5. **Silent behaviour and duplicate labels.** Enumerate transitions after conversion. Assert that each of the fourteen business names appears on exactly one visible transition. Assert that the only unlabelled transitions are the supplier skip, XOR/loop routing, and any conversion bookkeeping. Replay T3 versus the same trace without CS and confirm the difference is exactly one skip alignment move, not a missing visible task.

6. **Limitations.** Soundness does not test the narrative. Playout will not enumerate the infinite loop language. Alignments can hide missing CS or missing reviews behind `tau`. Conversion can insert extra silents and change interleaving appearance. None of these checks recover the hidden risk/pass attributes. Version drift in `ProcessTree.children` / `OperatorPOWL` constructors is possible because this code was not executed in this session.

# 8. Final Self-Critique

1. **Semantic (process-tree barrier).** Delaying the risk route and supplier until after PV∧DC is a clean under-approximation, but it is a strong operational distortion: a supervisor who signs as soon as the root cause is known is conforming in the plant and non-conforming in the tree. T5 shows the gap; many similar traces exist.

2. **Semantic (free XOR / free loop).** Both models treat risk, supplier involvement, and inspection outcome as demonic choice. They therefore accept mixed policies in one language (a case that is “high risk” only after a trial has started, or that reworks without a real fail). That matches the activity-only brief and still leaves a gap against any data-aware SOP.

3. **Unevaluated constructors.** The Python is written to the stated PM4Py interfaces and sets `parent`/`children` explicitly, but it was not imported, converted, or replayed here. A version that builds `OperatorPOWL` with a different child-order convention for `LOOP`, or that rejects `label=None` versus `SilentTransition`, would require a local fix.
