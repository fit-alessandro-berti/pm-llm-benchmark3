## Material errors in the expected analysis

These are not taste differences. They contradict the same tables the answer just built.

**1. Order DFG contradicts the Order trace listed in the same section.**  
The O100 sequence is given as … `Issue` → `Payment M1` → `Confirm D1` → `Confirm D2` → `Payment M2` → `Close`. Immediately afterward the DFG is said to contain a `Record Payment` self-loop because M1 and M2 share an activity name. They are not adjacent. The real Order DFG edges around payments are `Record Payment → Confirm Delivery`, `Confirm Delivery → Confirm Delivery`, and `Confirm Delivery → Record Payment`. Invoice flattening is where the payment self-loop belongs; that part is stated correctly and then mis-copied onto Order.

**2. Flattened DFG nodes are treated as object instances.**  
`Pack P1` / `Pack P2` / `Dispatch P2` are not DFG activities. After `ocel_flattening`, both pack events are `Pack Package`. O100 therefore yields `Pack Package → Pack Package` and `Dispatch Package → Dispatch Package`, not a labeled P1/P2 fork. The “branches” language is the classic flattening mistake this task is designed to catch.

**3. False timeline.**  
“D1 confirmation preceded D2 dispatch by 20h” is wrong. `E10` Dispatch `P2` is 2026-04-06 10:15; `E13` Confirm `D1` is 13:00 the same day. Confirm D1 is *after* Dispatch D2. The claim also does not belong under Delivery flattening: `D1` and `D2` are separate cases, so that cross-delivery order cannot appear as a DFG edge there at all.

**4. Type-level views described as instance graphs.**  
`discover_otg` and `discover_etot` are type-level. The write-up talks about hub node `O100`, `Pack P1` columns, and M1/M2 pointing at `V1`. That is the object-interaction / event-instance story, which is already the job of section 5’s last bullet. As a result, OTG and ET–OT are not actually predicted.

Related slip: OC-DFG is said to show P2’s pack edge “carries only O100”. In this model `E8` also touches `P2` and `I2`. The real contrast with `P1` is *convergence cardinality* (two orders, two items), not a missing object type.

**5. Settlement qualifier is justified with a fact the process does not state.**  
The narrative calls *both* M1 and M2 partial payments against V1. The task permits `partially_settles` *or* `completes_settlement`; choosing the latter for M2 is allowed. Inferring “100+150 settles V1” is not. There is no invoice total.

## Secondary issues that still cost points

- **Qualifiers do not do what Section 1 claims.** PM4Py flattening and DFG discovery are qualifier-agnostic. Distinct labels such as `fulfills` vs `creates` will not stop propagated Order links from looking like source observations in the analyses the code actually runs. The only place the convention is visible is a manual table audit. The requirement was specifically about not confusing *analytical* propagation with source facts.
- **`fulfills` is reused for Dispatch and Confirm.** Harmless for DFG (activity names differ), but it erases the qualifier vocabulary’s claimed precision on the Order side.
- **Fragile flattening diagnostics.** `flat['case:concept:name']` / `flat.columns` assumes a DataFrame. Several PM4Py builds return an `EventLog`. The constructor import is isolated; these calls are not, despite the same version-skew risk.
- **O2O vs E2O neighborhood is blurred.** O100’s O2O neighbors are only `I1` and `I2` (plus being the *target* of `V1 bills`). Listing `P1,P2,D1,D2,M1,M2` as OTG degree via “E2O/O2O” mixes two graphs.
- **“via O2O” Item reachability is overstated** for Invoice/Payment/Delivery: those paths are multi-hop and are not encoded as O2O rows.
- Small nits: leftover spec text dumped under §2; `ocpn` stored but never printed; `about 14` / `about 10` when the counts are exact.
