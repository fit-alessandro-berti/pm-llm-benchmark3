That is a competent scaffold, not a correct model-plus-analysis.

## Critical semantic breaks

**1. The Order view does not match the E2O graph.**  
Payments are deliberately *not* linked to Orders (“avoid double-counting”). Flattening uses E2O, so `E012`/`E015` **cannot** appear in Order traces. Sections 4, 5, and 7 then repeatedly put both payments on `O100`/`O200`, invent DFG edges `Issue Invoice → Record Payment → Record Payment` for Order, and treat allocation ambiguity as a flattening artifact of *this* model. That is the central error: the analysis describes a different relation policy than the code.

**2. Timestamp order is ignored.**  
For the relations that *do* exist, `O100` is roughly:

`Create → Add → Add → Reserve → Pack → Pack → Dispatch → Dispatch → Issue Invoice → Confirm → Confirm → Close`

`Issue Invoice` is 11:00; `Confirm Delivery` is 13:00 and the next morning. The predicted Order DFG `Dispatch → Confirm → Issue Invoice` is false for this log. `O100` also has **two** packs, two dispatches, and two confirms; the “approximate trace” collapses that.

**3. “Source vs propagated” is applied to the wrong facts.**  
“Add Item I1 to O100” is a source-system fact about the **Order**. Marking `O100` as `references` / `propagated` collapses the very distinction the derivation column is supposed to protect. Meanwhile `Reserve Stock` uses qualifier `references` with derivation `source`, so `source` means two different things. That is not a coherent qualifier vocabulary.

**4. Own audit counts are wrong.**  
The constructed `relations` table has **43** rows, not 57. `o2o` has **12** rows, not 13. The closing “semantic coherence” table presents those wrong numbers as validated. A reviewer who trusts the audit is misled.

**5. OTG geometry is reversed.**  
O2O is `Package → Item`, `Delivery → Package`, `Invoice → Order`, `Payment → Invoice`. The claimed spine `Order → Item → Package → Delivery` is not that graph. The real type graph is closer to `Payment → Invoice → Order → Item ← Package ← Delivery`.

**6. Settlement is over-interpreted.**  
The process calls **both** `M1` and `M2` partial payments. Treating `M2` as `completes_settlement` and asserting `100+150=250` “suffices” invents an invoice total that is not in the narrative. The task allowed that qualifier pair; presenting it as observed fact is still a slip.

The pipeline *shape* matches the prompt (flatten + DFG + skeleton; OC-DFG, OTG, ET–OT, OC Petri net, interactions; commented viz). The implementations of those calls are guessed.
