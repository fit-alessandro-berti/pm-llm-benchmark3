**7.8**

The write-up is a strong control-objective review: it uses the required headings, does not treat activity counts or payment size as decisive, and consistently separates form from substance. The case map is mostly well judged (especially AP-202, AP-204, AP-205, AP-208). The code section, however, contains a material logic error, and a few classifications are internally inconsistent.

**What is done well**

- FEP-1 is decomposed into distinct threats (error, insider fraud, credential compromise, bank-change fraud, receipt/commercial validity, collusion, recoverability, emergency operability), with honest coverage gaps for AV-2 on receipt and for the whole package on collusion.
- The A–D sufficiency test includes the required dimensions (timing, independence, coverage, overrideability, recoverability, evidence quality, collusion resistance) and a serious argument that equal expected loss is not enough.
- Classifications are non-mechanical: same-user AP-203/AP-207 can still be `OBJECTIVE_MET`; distinct-user AP-204 is `OBJECTIVE_FAILED`; AP-208 is failed despite a legitimate outcome; AP-205 is correctly `LOSS_PREVENTED_BEFORE_COMPLETION`.
- Manager action after release but before settlement is treated as hybrid under economic-finality semantics, which matches MG-4/ED-1.
- Monitoring rules distinguish alerts from proof, including the dedicated-cell hypothesis for u12/u13.

**Material defects**

1. **PM4Py four-eyes polarity is wrong, and the code prefers the wrong set.** In current PM4Py, `filter_four_eyes_principle` keeps cases where the two activities are done by *different* resources (compliant traces). The answer asserts the opposite. The manual join is correct, but if the two disagree the script still sets `nominal_violations = pm4py_viol`. With PM4Py present, `same_user_fep1_violation` would invert: AP-204/AP-209 flagged as violations and AP-201/202/203/206/207/208 as conforming. That is a direct failure of the required evidence builder, not a cosmetic caveat.

2. **AP-206 is argued as formally indeterminate and then labeled `OBJECTIVE_PARTIALLY_MET`.** If token-before-prepare cannot be established, `INDETERMINATE` is the classification the write-up itself describes.

3. **Code evidence is thinner than the narrative it is supposed to support.** Pair counts come only from these nine cases (u12/u13 appears twice), so the 37-payment / shared-workstation facts that drive AP-204 and AP-209 never become flags. AP-202 has no settlement timestamp, so manager timing collapses to `POST_RELEASE_SETTLEMENT_UNKNOWN` even though ratification two days later is already known to be post-finality.

**Lesser issues**

- Vendor ages are invented (e.g., “new vendor” = 30 days). Harmless here, but they are presented as data.
- AP-201 is reasonably `OBJECTIVE_PARTIALLY_MET`, but the convenience bypass is under-weighted relative to ED-1’s rule that same-user release is a permission, not a habit.
- AP-207 as full `OBJECTIVE_MET` is defensible under the letter of condition 6, but post-release ratification is the weaker MG-4 mode; a `PARTIALLY_MET` option is not seriously weighed.

The control reasoning would sit near the top of the scale. The inverted four-eyes implementation and the AP-206 label/analysis split keep it well short of near-flawless.
