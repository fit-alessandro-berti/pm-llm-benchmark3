## Material defects

**1. Wrong reconstructed state for TX-311.**  
The findings table lists release state as `EUR 115,000; LOW; DE; RETAIL`. The log never updates `customer_type`. Create sets `CORPORATE`, and that value is still current at release. This is a direct failure of the thing Section 1 claims to do. It does not change R1/R2 on this file, but a compliance table that misstates a governed attribute is not a small editorial slip. Confidence “High” on that row is therefore unearned.

**2. Formalization is damaged and not internally consistent.**  
The pseudo-logic is missing its temporal operators (`e  f` instead of a defined precedence relation) and the three-valued predicate is introduced as `K()` over an empty condition. That is not usable first-order/temporal form.

Worse, `R1_satisfied` is Boolean:

`T1 = F ∨ ValidExemption ∨ ∃ fresh ER`

If `T1 = U` and an ER exists, the formula returns satisfied. TX-305 is then compliant by the formal rule and INDETERMINATE by R6 and by the case table. The code does the right thing (`UNKNOWN_TRIGGER` short-circuits), which means the “normalized” logic is not what was actually applied. `FreshR1Review` is also informal (“no unresolved post-e change makes freshness unknowable”) and is not a defined predicate.

**3. TX-310 is left softer than R5’s own test.**  
R1 is on, there is no Enhanced_Review, and EX-88 is the only cure. R5 requires that *the evidence support* timely Head_Compliance approval. The qualified certificate is created *after* release; the only earlier story is an oral claim by the requester. That is not “missing data.” It is affirmative technical evidence against a timely signed approval, plus a self-serving witness. INDETERMINATE is allowed by the “no canonical answer” note, but the write-up treats contradictory evidence as if it automatically yields an open verdict. A stricter application of R5 is: exemption not established ⇒ obligation unmet ⇒ NONCOMPLIANT, with residual residual doubt recorded in confidence, not in the classification. Section 4 almost says this, then does not carry it into the table.

**4. The code quietly bakes in the narrative judgment the prompt forbade as a lookup.**  
`evidence_assessment = STRONG_TIMELY | CONTRADICTORY_REVIEW` is not derived from timestamps, certificate time, or signer role. It is the author’s EX-77/EX-88 conclusion inserted as data. The rest of the exemption logic is then just a switch on that label. Coarse flags are still useful, but this is exactly the kind of hard-coded case wisdom the task asked to avoid.

**5. Code and prose disagree on “material.”**  
Prose limits R1 materiality to foreign/high-value relevance, threshold activation, and R4 increases. The implementation treats *any* post-ER jurisdiction change as stale, including a same-class non-DE → non-DE change. That is a different rule. It does not flip these 11 cases, but it is not a faithful encoding of Section 2.

**6. Smaller unclarities that should not be in a scored formalization.**  
- JUSTIFIED_EXCEPTION is defined, then unused, including on TX-302 where a valid R1 waiver actually exists. The taxonomy discussion is fine; the table still never exercises an allowed label that the exemption regime exists to support.  
- “Satisfied obligations” for TX-304 (“screen valid only at 08:10”) describes a lapsed control, not a satisfied one.  
- TX-305’s confidence cell (“High that evidence is insufficient”) is not a confidence score.  
- Review-coverage of amount is decisive for TX-305 and is never made an explicit predicate in the rule table.  
- The optional DECLARE demonstration is only a homemade `ER ≺ CA ≺ Release` existence check. Acceptable, but it does not show a real DECLARE constraint or a PM4Py conformance call.

## Bottom line

This is a strong examiner’s script with real event-time discipline and code that would actually help a reviewer. It is not a 9–10 artifact: it misstates TX-311’s customer type, publishes formal rules that do not match the classifications, hard-codes exemption verdicts, and leaves TX-310 one inference short of R5. Those are not polish issues. They are exactly the failure modes the exercise is testing.
