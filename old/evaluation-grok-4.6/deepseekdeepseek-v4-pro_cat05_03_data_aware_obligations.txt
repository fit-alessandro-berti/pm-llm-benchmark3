**Case reasoning (largest deduction).** Eight cases are essentially right (TX-301, 303, 304, 305, 307, 309, 310, 311). Three are not.

- **TX-306** should be **COMPLIANT**. R4 is the definition of a *material* amount change: only an increase **over 20%** invalidates a review for amount-dependent duties. The 220k→230k move is ~4.5%, and the log even labels it “increase below 20 percent.” Treating every amount edit as a “material data change” that restarts R1 makes R4 idle. This is a designed test; the primary classification is wrong.
- **TX-308** should be **COMPLIANT**. R4 states a decrease does not invalidate a review. 140k→100k still triggers R1, but the existing Enhanced_Review remains valid. Same conceptual error as TX-306.
- **TX-302** is **COMPLIANT via Enhanced_Review**, not a justified exception. Create at 180k GB CORPORATE, Enhanced_Review at 09:20, release at 09:40: R1’s review-after-last-material-change condition is already met. EX-77 is surplus. Calling the outcome JUSTIFIED_EXCEPTION and saying “R1 met via exemption” is a false causal story. The EX-77 vs EX-88 evidence contrast itself is good; the classification path is not.

Section 4 partly redeems this by stating the better readings for 306/308, but the official findings table is what an adjudicator would use, and it is wrong on the R4 triad (306/308/309).

**Section 4 gap.** TX-302, TX-305, and TX-310 are discussed. **TX-311 is not**, despite an explicit instruction to address it. The same-timestamp / `event_index` trap (review while US, release while DE) is exactly what that section was for.

**Code (heavy deduction).** The pipeline shape is right (StringIO → `pm4py.format_dataframe` → per-case order → release snapshot), but it does not do what section 5 required and would not compute the intended flags.

- Forward-fill is applied **before** “change” detection via `notna()`. After ffill, almost every later row looks like an update, so `latest_material_change_ts` collapses toward the release timestamp and `r1_review_ok` is systematically false. That is a fatal reconstruction bug.

A judge asked to score “usefulness of the PM4Py/pandas code” cannot treat this as a working checker.
