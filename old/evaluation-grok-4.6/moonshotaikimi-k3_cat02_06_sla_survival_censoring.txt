**6.6**

The write-up is a strong estimand-first analysis plan with the right process-mining instincts, but it is not close to flawless. Several headline numbers are wrong, and the document contradicts itself on the risk set that those numbers depend on.

**What is done well.** Time origin, horizon, and four estimands are defined before any estimator is chosen, and each is mapped to a real decision (compliance, late-stage work, WIP, partner/triage). Right censoring, competing events, and already-observed breaches are kept distinct; S03 / S09 / S06 / S08 are walked through under every estimand. Transfers get three encodings plus bounds, and 3/3 transferred cases being escalated is used correctly as evidence that T1 is informative. Immortal time and leakage are handled properly (`escalated` / `rework_count` / full prefixes / terminal last-activity are not treated as baseline). The method table is justified for *this* extract (n=32, 9 at risk at 72 h), not a generic catalog. Format is compliant: nine required headings, one Python block, PM4Py used only for control flow, no fabricated timestamps, open cases retained.

**Fatal consistency problem.** The text states that 9 cases remain under observation at 72 h (correct: S03, S09, S11, S13, S20, S25, S26, S28, S32). The pooled AJ/KM arithmetic then uses n=14 at 70 h and n=13 at 74 h. Those risk sets cannot coexist. The bug is failing to decrement n at several censoring times (starting with S31 at 23 h). Because of that, the pooled results that the rest of the memo treats as “hand-verified” are not the AJ/KM estimands the code actually implements.

Approximate *correct* pooled T2 figures (standard AJ, transfer competing):

| Quantity | Reported | Correct |
|---|---:|---:|
| E1 = 1 − F_R(72) | 71.5% | ~69.6% |
| E2 = F_R(∞) − F_R(72) | 13.9% | ~30.1% |
| E3 = S_any(72) | 42.9% | ~38.0% |
| Composition at 72 h (R / W / J / X / open) | 28.5 / 12.8 / 9.5 / 6.4 / 42.9 | ~30.4 / 14.0 / 10.1 / 7.5 / 38.0 |
| Naive resolution KM at 72 h | 30.0% | ~36.1% |

E2 is off by about 2×, mostly because late increments (especially S13 with a tiny risk set) were under-weighted. The claim that numbers were checked against the script is false: the script decrements n for every row in a time group and would print different values than §8’s “expected outputs.”

**What survives.** Cohort and priority strata happen to be right (A E1 73.3%, B 70.6%; P1/P2/P3 ≈ 75 / 64 / 80; AutoCheck-B 61.5% vs non-AC-B 100% on n=4). Resolved-only means/medians, 27 variants, 13/17 AutoCheck in B, and the 3/8 P1 transfer visibility gap are correct. RMST ≈ 50.4 h is accidentally right because early S(t), which dominates the integral, was computed before the risk-set error bites. Qualitative sensitivity conclusions (E1 relatively stable, E2/E3 move with transfer handling, “B improved the SLA” is not identified) still hold in direction, but the quantitative sensitivity table (E2 13.9→27.1, E3 34.8–47.8, “~19% of the tail later resolves”) does not.

**Smaller issues.** T1 increment list (0.03125×3 + 0.0325×4) does not match the 4+3 summary they sum to 0.291. T3 is not T1-plus-events-at-72: S21 and S08 must stay in the risk set until 72, which they only half-correct. S(t) is repeatedly written where S(t−) is meant. The Mermaid diagram is stuffed with `&nbsp;` to dodge a second fence; readable, but sloppy. Bootstrap intervals are wisely left unquoted.

**Bottom line.** As a design document this is well above average: estimands, competing risks, leakage, and operational use are at a high level. As a survival analysis of the supplied table it fails a basic check — the pooled risk sets are internally impossible, so the primary numerical claims and the “verified” code commentary cannot be trusted. That combination caps the score well below the near-flawless range.
