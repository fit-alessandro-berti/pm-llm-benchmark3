5.8

The answer is structurally complete and mostly on-task, but it is not close to a publishable digital-twin design. Under a strict reading of the brief, several required design constraints are only half-met, a few statistical claims are simply wrong, and the code misses an explicit deliverable.

**Scope is too thin for the interventions being compared.** The twin is described as a case-level DES with calendars and inspection bundles, which is the right class of model, but the state vector is incomplete for D2, D6, D7, and D9. There is no prior-violation flag, no aging/priority state, no appointment-slot inventory, no related-case or neighborhood graph, no no-show/readiness flag, and no first-class council-week or holiday calendar. `has_objections` is listed as if it were an observed case attribute. Decision-drafting’s AND-join (wait for every applicable review) is never made a state variable. Cross-case dependence is then explicitly narrowed to inspection batching plus resource contention, which drops neighborhood-objection contagion and same-architect in-process coupling. Arrival bursts are not the same thing as in-process dependence.

**Parameter estimation mixes good PM practice with a control-flow error.** Using the supplied median/p90 summaries because starts are missing is correct; treating DFG edge weights as XOR branching probabilities is not, because Planning / Fire / Environment are concurrent. That will mis-estimate optional reviews and the join before decision drafting. There is no quantile-matching procedure for the lognormal/gamma fits, no plan for the subsample that *does* have start times, and no estimator for travel, no-shows, or batch size. “Public-notice duration ⇒ objection frequency” is a proxy and should have been treated as only partially identified.

**Assumptions overreach.** “Start timestamps can be robustly ignored” collapses a known measurement problem. The 30-day objection rule is arbitrary. Calling removed emergencies “statistically negligible for capacity” is unevidenced. Rework is assumed to reuse first-pass service distributions. Calendars are assumed perfectly strict with no overtime. Those are all usable *as labeled assumptions*; they are presented with more confidence than the data support.

**The experiment matrix is a list, not a design.** D1–D10 and three stresses are present, which satisfies the heading, but effect sizes (−60% missing-doc loops, skip 30% of env reviews, 3-day batch wait, 40-day aging rule) are invented and written as if known. D2 drops the “no prior violations” clause. D5 drops Commercial. D8 is operationalized as skipping work, not triage. D9 “detects objections in Planning,” which is the wrong process phase unless the mechanism is a *risk* signal. Stress cases are not crossed with policies, so D10’s claimed synergy is not actually an experiment.

**Uncertainty treatment has two real errors.** Welch’s method and “steady-state queue stabilization” are the wrong frame for a strongly seasonal, non-stationary system; queues should oscillate. A 4-month warm-up is shorter than the 140–260 day complex tail, and right-censoring of unfinished cases at the horizon is ignored. “95% confidence intervals for medians and 90% credible intervals for p90” mixes frequentist and Bayesian language with no posterior. Input-parameter uncertainty is almost absent (one sensitivity on the objection threshold). CRN and 50 replications are fine.

**Validation and decision criteria are conventional but statistically naive.** KS tests on 31k cases will reject almost any residual difference; they should not be the acceptance rule or the fairness goal. D3/D5 travel is structurally longer, so “no significant geographic bias” is the wrong target. Utilization cannot be validated cleanly against HR estimates when start times are missing. SLA cutoffs (30 / 180 days) and the 85% utilization cap are invented. The section correctly avoids claiming optimality, which is one of the few constraint hits that is clean.

**The skeleton fails a written requirement.** It correctly avoids `pm4py.read_csv` and uses `format_dataframe` with the requested keys. `discover_dfg` / `discover_performance_dfg` / `get_variants` are plausible. PM4Py is separated from SimPy. But it never builds service/waiting columns or explains that this excerpt has only completion timestamps, so sojourn can be computed and the split cannot. It does not call `pm4py.parse_process_tree`; the limitation note is vague, and that API would likely parse most of the given string. The arrival generator is a stationary exponential, contradicting the non-stationarity requirement. Time units are incoherent (`avg_arrival_rate: 10` vs ~57 historical cases/day; `until=16000` as “22 months”). `FilterStore` resources are never populated, so the sketched case process would deadlock. Calendars, routing, batching, and the experiment matrix are comments, not placeholders with a usable interface.

The piece reads like a competent workshop write-up: right headings, some real DES and process-mining literacy, no optimality theater. It is not a nearly flawless design. The missed code deliverable, the DFG-as-XOR mistake, the steady-state treatment of seasonal demand, the retreat from cross-case dependence, and several invented “levels” keep it well below a high score.
