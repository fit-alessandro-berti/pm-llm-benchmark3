**7.4**

The final write-up is strong on the dimensions the task actually cares about: it reasons from control objectives, timing, coverage, independence, recoverability, and case risk, and it does not treat “a control occurred” as “the control was sufficient.” Headings match the spec, classifications are mostly well chosen, and AP-204 / AP-209 are not mechanically mapped from distinct users to `OBJECTIVE_MET`. That is the core of a good answer. It is not nearly flawless.

**What is right**

- FEP-1 is decomposed into concrete threat scenarios (error, bank redirection, duplicate, override abuse, emergency misuse, collusion, missing receipt, irreversibility), with honest coverage gaps for AV-2 (no receipt, no collusion) and RA-7 (detective; corrective only inside recall).
- Equivalence levels are defined on timing, independence, coverage, overrideability, recoverability, evidence quality, and collusion resistance. The rejection of “same expected loss” as the only standard is correctly tied to SoD, accountability, tail risk, and non-quantifiable fraud/regulatory harm.
- Case calls are largely defensible:
  - AP-203 / AP-207: ED-1 conditions actually hold → `OBJECTIVE_MET`.
  - AP-202 / AP-208: independence, AV, timing, and recoverability all fail → `OBJECTIVE_FAILED` (including AP-208 despite a legitimate outcome).
  - AP-204: form-satisfying four-eyes with fabricated receipt and impaired independence → `OBJECTIVE_FAILED`.
  - AP-205: blocked before completion → `LOSS_PREVENTED_BEFORE_COMPLETION`.
  - AP-201: convenience same-user with independent pre-settlement MG-4 and low exposure → `OBJECTIVE_PARTIALLY_MET`.
- Manager action after `Release_Payment` but before settlement is correctly treated as hybrid, not as full prevention.
- Monitoring recommendations distinguish alerts from proof and cover the requested signals.
- The pandas/PM4Py sketch is self-contained, reconstructs the CSV, separately flags AP-205, joins case facts, and labels output as evidence rather than a verdict. Dual event-vs-fact manager timing is a real strength given missing `Bank_Settlement` rows.

**Material problems**

1. **PM4Py four-eyes polarity is very likely wrong.** Public `pm4py.filter_four_eyes_principle` generally *keeps cases that satisfy* four-eyes (different resources), optionally via a `positive`/`keep` flag that the simplified API often does not expose. The script treats the returned case set as *violations*. On a standard build, `pm4py_nominal_four_eyes_violation` would mark AP-204/AP-209 and miss the same-user cases. Version caveats mention return *types*, not this polarity. The manual same-user column would contradict the PM4Py column; that is a landmine, not a documented inversion. For a required executable check, this is a serious defect.

2. **`INDETERMINATE` is never used**, despite the prompt planting two designed ambiguities: AP-206’s token “may be a logging delay or a failure of ED-1’s precondition,” and AP-209’s missing org-design documents for a dedicated u12/u13 cell. `OBJECTIVE_PARTIALLY_MET` is arguable in both, but refusing the provided indeterminate class while the facts explicitly withhold a fact is a judgment miss, not a style choice.

3. **Risk factors are smuggled in as controls.** AP-201 lists “low amount” under preventive controls. Amount is exposure, not a control. The same slippage appears when residual-risk language and control-package language are not kept cleanly apart.

4. **Hard-coded facts silently overclaim independence.** AP-208’s `manager_independent=False` is not in the case file (only m09 is identified as conflicted). AP-208’s emergency token is recorded as active *before Prepare* even though the log has no token event and the table only says “active.” Those booleans then feed `ed1_conditions_met`. The flag still fails on amount/AV/bank/timing, so the verdict does not change, but the evidence table is not faithful.

5. **“One business day” vs 24 hours is applied inconsistently.** AP-201’s next-morning audit (≈25h after release, ≈23h after the stated settlement) is coded `audit_within_1bd_fact=False`, while AP-207’s next-morning audit is `True`. ED-1’s clock is one business day; RA-7’s recall clock is ~24h from transfer. The narrative sometimes gets this right; the flags do not.

**Smaller nits**

- Rubber-stamp / review-depth is asserted more cleanly for AP-207 (“reviewed all supporting evidence”) than the log can show; AP-201’s m04 “reviewed” is taken from the fact table, which is fine, but the code cannot verify review quality.
- `format_dataframe` is called without an explicit `resource_key`; four-eyes then depends on `org:resource` surviving conversion unchanged. That belongs in the version caveat.
- Pair-count > 1 will not flag a single operator who repeats same-user payments; that is a monitoring hole relative to Section 6’s same-user-rate recommendation.
- The case table is too wide and packs two confidence levels into one cell (AP-204), which blurs the required schema.

The control reasoning would sit closer to 8.5 if Section 7 and the boolean evidence layer were accurate. Under a strict reading, the inverted four-eyes API use, the unused `INDETERMINATE` class, and several fact-coding shortcuts keep it well below “nearly flawless.”
