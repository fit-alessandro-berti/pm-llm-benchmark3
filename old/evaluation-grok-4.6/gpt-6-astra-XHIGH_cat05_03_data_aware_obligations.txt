## Defects that block a top score

**1. The code is not as executable or faithful as claimed.**  
It asserts “Execution produces …” without a runtime transcript. That claim is doing work it has not earned. Concrete risks:

- `v is True` / `v is False` in `tri_and`, `tri_or`, `obligation_status`, and `signature_verified is True` is unsafe after a pandas merge. Mixed `True`/`False`/`NaN` columns upcast to float or object; `1.0 is True` is false, so EX-77’s verified signature can silently become `None`. TX-302 still passes via ER, which is why the bug is easy to miss and still a bug.
- Sanctions additions are keyed from **pre-**`format_dataframe` `raw` timestamps, then compared to **post-**pm4py event timestamps. `format_dataframe` re-parses and often re-sorts; tz-aware vs tz-naive comparison raises. List updates should have been taken from the same frame the release loop uses.
- Packet linkage is ` "standard review packet" not in str(note).lower() `. That is a fixture hack, not evidence of review–approval binding, and it will mis-fire on `NaN` → `"nan"` or any other wording.
- Item 8 asked for a coarse DECLARE or trace-order check *in the code block*, with an explanation of why it is insufficient. The explanation exists; the demonstration does not. “Optionally” is a partial excuse, not a full one, because the required code list still named it.

**2. Materiality is extended beyond the text, then used as if it were the rule.**  
R4 defines a *material amount change* as a >20% increase. The write-up also treats every risk / jurisdiction / customer-type change as material for R1 freshness, while saying the policy does not define that. The extra rule does not flip any of these eleven labels, but it is still an unstated policy, and the code implements it (`material = event` on those columns). TX-306’s COMPLIANT / High confidence likewise depends on reading R1’s “material data change” as R4’s 20% test. That is the intended reading, but it is not the only one, and confidence should have been marked down for that dependence rather than stated as High.

**3. Exemption logic is slightly softer than R5.**  
R5 requires that “the evidence supports that approval existed at the relevant time.” For EX-88 the code never returns `False` for approval; failed digital proof becomes `None`, hence `REVIEW_REQUIRED`. That matches the narrative INDETERMINATE, and the problem allows non-canonical answers under contradiction. It is still a choice: a burden-of-proof reading (waiver not established ⇒ R1 fails ⇒ NONCOMPLIANT) is at least as faithful, and the coarse classifier will not emit `JUSTIFIED_EXCEPTION` on this log at all. The alternative is discussed in §4; it is not encoded as a first-class outcome.

**4. Small formal and table nits.**  
Expiry is assumed `[effective_from, expires_at)` with no warrant in R5. R3’s “no initial-screen obligation” is a reasonable parse of “after the latest Sanctions_Screen,” but it is an interpretation, and the code’s `screen is None → REVIEW_REQUIRED` path is not quite the same as the prose. Severity is an invented scale. `after(review, material)` uses the latest material event through *release*, which is correct for freshness, but creation is always stored as material, so “ER after create” is smuggled in as a universal extra constraint.

**5. Control-flow critique is repetitive rather than tighter.**  
Nine modes are listed; several overlap (stale review vs post-review updates; late recording vs post-hoc exemptions). The content is right. The claim of “at least six distinct” modes is met in substance, not in clean separation.
