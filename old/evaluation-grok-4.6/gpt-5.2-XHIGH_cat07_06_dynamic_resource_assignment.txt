## Algorithmic flaws (Section 2)

**SLA scoring is inverted for resource choice.** `sla_urgency_score` returns `-slack`, and slack shrinks when `est_service` grows. The candidate score then *rewards* the slower worker on the highest-weighted term (`w_sla=5`). Case ordering by urgency can be correct while resource ranking is backwards. Skill-match is supposed to counteract this, but it is weaker (`w_skill=3`) and will not reliably win on tight SLAs. This is not a notation nit; it is the wrong gradient.

**The overtime rule is written as a hard guardrail and then implemented only as a soft penalty.** `eligible()` never blocks `overtime_risk="high"` when the case is not urgent and a safer option exists. That is exactly constraint 4 / the prompt bullet “Do not overload high-overtime-risk resources unless justified.”

**`resilience_penalty` barely ranks people.** The bottleneck ratio is a property of the skill, not of the candidate, so it is a constant for all feasible `r`. Only `0.2 * assignments_in_batch(r)` differentiates. The prose claims bottleneck avoidance; the math does not do that job (it should penalize consuming scarce specialists when a competent option exists).

**Hours remaining are not a feasibility filter.** They appear in a fairness score, not as “can this person finish enough of this work today.” First-available, which the answer compares against, does use remaining hours. David at 3.0 hours, 14 open cases, is still eligible for new diagnosis.

**Continuity `eligible()` logic is ambiguous.** `if not supervision_possible(...): return True` is described as “forced handover” but only marks *this* `r` eligible. Security supervision checks that *some* supervisor has batch capacity `< 4` without reserving that slot, so two cases can claim the last supervisor.

**Quality batching is a stub.** The set `quality_batch` is built and then never used as a batch: C006 and C012 are both batch-eligible and are split across people.
