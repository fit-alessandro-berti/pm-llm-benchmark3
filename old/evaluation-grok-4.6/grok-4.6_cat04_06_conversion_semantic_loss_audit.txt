## Logical flaw that blocks a high score

The bounded explorer sets `truncated = True` whenever another `Correct Defect` would exceed `LOOP_BOUND`. On this model that extra redo is always enabled, so `exhaustive_under_bound` is **never** true if the loop is implemented correctly. The prose then says: if `truncated`, treat language equality as `not tested`. That decision procedure cannot validate the main language comparison on the actual source. Hitting the *slice boundary* is conflated with failing to finish the slice (`SEARCH_STATE_BOUND` / mid-search abort). For an unbounded loop those are different events. This is not a wording nit; it is a broken pass/fail rule.

Related: `seen` keys include the full trace, `silent_here` / `visible_here` are dead, and comments describe a “side map” / “local DFS” that the code does not implement. That is the same component, not a separate polish issue.

## Section 5 only half-satisfies the comparison requirement

The prompt asked to compare `net_from_powl` with every reverse net using soundness, footprints, reachability, bounded exploration, witnesses, and playout *where defensible*. The script calls `discover_footprints`, `convert_to_reachability_graph`, and `play_out`, then prints types or key names. It does not compare parallel/sequence relations to INV-02/INV-07, does not compare reachability graphs, and does not use playout traces as evidence. Witness replay plus set-difference of completed traces is real; the other listed tools are ceremonial.

`pm4py.execute_enabled_transition` is not in the stated interface. The `hasattr` guard and semantics fallback are better than a blind call, but `fire()` still has no exception handling. A signature mismatch crashes the audit instead of being recorded.

Section 5 is also not a complete program. It depends on `net_from_powl`, `roundtrip_nets`, `markings_ok`, and `diagnose_net` from Section 3. That is workable if concatenated, but it is not stated, and it is easy to mis-run.

## Table and audit unclarities

“Negative witness” is used inconsistently. INV-01/08/10/12 give forbidden traces. INV-02/05/07 give converter failure modes (“a conversion that admits only one order”). Those are useful rejection criteria, not witnesses. That blurs the exact distinction the header asks for.

Section 4 is a prediction template, not an audit of conversions. Almost every Petri→BPMN / round-trip cell is `expected preserved`, `ambiguous`, or `not tested`. Honest about not executing, but then the preservation table does not actually preserve-or-lose anything observed. Petri→Tree is filled with `conversion failed` on structural suspicion, while the text admits a tree object might appear and should then be scored `lost` / `approximated`. The table and the caveat disagree.

INV-03’s “at most one” is true of this POWL, but it is a consequence of the XOR sitting once in the partial order, not of XOR itself. Worth one clause; it is over-stated as if XOR implied uniqueness.
