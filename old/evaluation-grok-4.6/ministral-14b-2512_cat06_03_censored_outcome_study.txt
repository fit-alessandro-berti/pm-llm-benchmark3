**4.2**

The write-up has the right headline instinct — do not recode rejects/withdrawals/opens as non-default, and treat activation as a selection filter on the observed outcome — but it is not a statistically coherent study design. Under a strict reading of the rubric (honest estimand, as-of maturity, process-correct prefixes, non-leaky features, implementable PM4Py skeleton), it fails in several places that would produce a misleading early-warning system.

## What is actually sound

The primary *family* of target is the only one that is identified from these labels: 90-day default **conditional on activation**. Rejected, withdrawn, transferred, and still-open cases are not force-labeled 0. The cohort table at least enumerates all 48,000 applications. The leakage table correctly drops `final_limit`, `decision_reason`, `collection_status`, and post-prefix events. A random case split is rejected. Section 8 correctly refuses an unconditional or counterfactual default claim. Those are necessary, not sufficient.

## Section 1 — estimand and prediction time are wrong

Calling \(P(\text{default}_{90d}=1 \mid \text{activated}, \text{prefix})\) a **“causal risk”** is a basic identification error. That is an associational/selected-population predictive estimand. Nothing in the design identifies an effect of activation or of the prefix.

Prediction time is internally inconsistent and operationally late. “Last event before `Account Activated` (or a fixed prefix of 5)” is not “the first few events of every credit application.” By the last pre-activation event the accept/sign path is essentially known, so this is a post-decision account-risk model, not an application-stage early warning. The business question is thereby quietly replaced.

The multi-state alternative is mischaracterized. Predicting observed competing terminals (reject / withdraw / transfer / open / activate-and-default / activate-and-not) does **not** require counterfactual default risk. That is the reason to use it. Counterfactuals belong only to the “what if we had activated everyone” target. The survival alternative also misstates independent censoring as “censored cases comparable to observed defaults.”

The population cut “activated before 31 Dec 2025” cannot yield a matured 90-day label by 15 Feb 2026. Activation after mid-November 2025 is still inside the 90-day window; the feed then adds another 7–35 days. The design never writes the actual as-of inequality  
`activation_time + 90d + feed_delay ≤ extract_time`  
(or a conservative `activation_time ≤ extract_time − 125d`).

## Section 2 — flow table arithmetic is not a design

21,600+3,600+9,100+5,700+2,900+5,100 = 48,000, but the categories are conceptually sloppy.

- The 3,600 are “outcome or delayed feed not yet matured,” not uniformly delayed-feed right-censoring.
- Still-open cases are **not** censored observations of 90-day default. They were never activated; default under this policy is undefined, not missing.
- Transfers are dumped as one row. The 60% linkage / 40% lost follow-up / partner missing-feed mechanism is not turned into analysis strata.
- The text says censored activated cases are included; the “primary cohort” is only the 21,600 complete labels. That contradicts the Cox plan in §3. Complete-case restriction reintroduces the selection the rest of the memo warns about (partner feeds, late activations, delayed labels).

There is no case-level as-of object: start, first prediction time, activation, terminal type, censor time, `label_available_at`, maturity flag.

## Section 3 — missingness types are listed, then mishandled

Delayed labels are not right-censoring at day 90. If the 90-day window has elapsed and only the warehouse feed is late, the outcome exists and is unobserved until `label_available_at`. If the window has not elapsed, censor at **attained follow-up**, not at 90. Treating both as “censored at 90 days” biases the horizon.

`label_available_at` is used as a prefix-event filter. That is a leakage rule, not a delayed-label analysis. Delayed labels belong in **who is allowed into a backtest fold** (train only on labels that would have been known at the as-of date).

“Independent censoring is testable via Kaplan–Meier curves” is false. Independent/non-informative censoring is not identified from these data. KM does not test it.

IPW is given the wrong assumption (“unobserved defaults for non-activated cases are comparable to observed defaults”). The actual requirements are positivity and no unmeasured confounding of activation. Those are not established by “modeling the policy.”

A competing-risk model that treats reject/withdraw as competing with default on the same clock is process-incorrect unless a multi-state clock from application start is defined. Default is not at risk until activation.

Cox PH is announced as primary while §1 and the metrics in §7 are binary 90-day classification on complete cases. The paper never picks one likelihood.

## Section 4 — prefixes look into the activation decision

Prefixes are the last \(N\) events **before activation**. That conditions on a future absorbing state and is unusable for “every application.” Short cases are to be padded with NULL events (a bad encoding). Repeated document loops are **collapsed**, which destroys the rework count the feature section later wants. `Contract Signed` is treated as a post-activation event; in the given control flow it is **between** Accept and Activate. Activity-rename handling is a comment, not a rule (including duplicate events from 15 Oct 2025).

## Section 5–6 — features and leakage are only half-done

Several “prefix” features (`Credit Review → Accepted`, time to Accepted/Rejected) are only defined if the decision has already occurred. `documents_total` is called a static case attribute; it is a same-calendar-day snapshot and is not fixed by `timestamp ≤ prediction_time` — you need the **previous night’s** snapshot. Resource experience cannot be “repaired” from this extract; the file stores experience at extraction time, so the honest action is **drop** unless a historical HR table exists. `label_available_at` should not be a model feature. `default_90d` itself is never listed as a column that must be stripped from \(X\).

The DFG/variant examples run Alpha Miner and `get_variants` / `extract_temporal_features_dataframe` on the **full log**. That is completed-trace leakage, and Alpha Miner does not produce DFG features (`discover_dfg` would).

## Section 7 — the temporal split cannot be evaluated

Train through 30 Jun 2025 / val Jul–Sep / test Oct–Dec 2025 looks “temporal” and is still invalid:

- Almost no Oct–Dec 2025 start will have a matured 90-day post-activation label by 15 Feb 2026.
- Training only on the pre-1 Jul 2025 policy answers a retired policy; the deployment regime is never in train.
- “Monthly refit, score the next 30 days of activations” scores accounts whose 90-day label **cannot exist yet**.
- Brier/AUC and C-index are listed as if the target were both a binary complete-case problem and a survival problem.

A serious design would split on **case start**, require label maturity at a stated as-of date, hold out a post-policy slice only if labels can mature, and treat the October migration as a separate break (renames, duplicates), not just another date cut.

## Section 9 — the skeleton would not run as specified and implements the bugs above

Required `pm4py.format_dataframe(...)` is absent. `get_prefixes_from_log` is called with a fabricated `parameters`/`filter` lambda. `log_converter.apply` is not given the real argument names. Unused/wrong imports (`alpha_miner`, `xes_importer`, duplicated `dataframe_utils`).

`build_cohorts` treats “any event with `default_90d` missing” as evidence the **case** is unlabeled. The schema repeats the label only when known, so early events of labeled accounts are missing — the 21,600 and 3,600 will be hopelessly mixed, and “non-activated” will include censored activated cases.

`temporal_split` splits **event rows** on event timestamp, then prints them as “cases.” That is not a case-start split.

There is no case-level start/activation/terminal/censor/maturity table, no actual feature matrix, and no code that drops post-prefix columns. The “leakage audit” is a hardcoded dictionary, not a check. Survival is deferred to a nonexistent `pm4py.get_event_attributes`.

## Net

This is a fluent template around one correct prohibition (do not call rejects non-default) plus a leakage table. It then (i) misstates the estimand as causal, (ii) predicts at activation rather than from early prefixes of all applications, (iii) confuses undefined outcomes, delayed labels, and right-censoring, (iv) proposes a test set and a 30-day backtest in which labels cannot have matured, and (v) ships a PM4Py sketch that omits the one required API, invents another, and rebuilds the cohort with a label-missingness bug. That is well below a defensible study plan.
