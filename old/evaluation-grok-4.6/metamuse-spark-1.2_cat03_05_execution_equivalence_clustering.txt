## Fatal reproducibility failure

The preferred relation is defined as equality of
`(logistics_pattern, financial_pattern, item_lifecycle, collaboration)`,
and §2 is offered as the executable witness. The witness does not compute the table in §3.

`motif_abstract` sets `has_ext` globally, then:

- any execution with an external object and a single `Pack` is labelled `shared-package`;
- any execution with an external object and an `Issue Invoice` string in the E2O signature is labelled `shared-invoice`.

On that rule X5 (shared pack, **local** invoice) becomes `(shared-package, shared-invoice, …)` and X6 (local pack, **shared** invoice) becomes `(shared-package, shared-invoice, …)`. The two collaborative cases that the prose works hard to separate **collide**. The table instead assigns X5 `isolated-invoice` and X6 `single-package`. Those assignments match the English motif definitions and contradict the code.

That is not a style issue. The task asks for a signature that another analyst can rerun. Here the only operationalization of the preferred relation disagrees with every cluster that uses `EXT`.

Related defects in the same artifact:

- `remap` is computed and never applied. The advertised “canonical object ids” do not appear in the key.
- E2O/O2O signatures keep only `(type, ext, qual)` bags. That is **not** typed isomorphism: object identity across events is discarded. Two different incidence graphs with the same per-event type multiset hash together. The claim that the struct signature is “lossless except for identifier strings” is therefore false.
- `order_edges` is undefined. The `has_removed` E2O comprehension unpacks the wrong shape. `"Issue Invoice" in str(e2o_sigs)` is stringly-typed and would fire on any invoice-bearing execution once `has_ext` is true.

Prose motifs are usable; the reproducibility mechanism is not.
