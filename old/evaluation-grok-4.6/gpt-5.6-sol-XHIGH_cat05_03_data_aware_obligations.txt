## Defects that keep this well below a top score

**1. The normalized rule table is formally incomplete.**  
R1 is written as “jurisdiction  DE and amount  EUR 100,000.” R4 says “increase 20%.” R5 says “Effective-from `` obligation trigger.” The comparison symbols are simply gone. In a section whose job is formalization, that is not a cosmetic markdown issue. A reader cannot recover ≠, ≥, >, or ≤ from the table itself.

The pseudo-logic has the same hole: `q  r`, `q  a  r`, `u  s2  r`. The earlier definition of ≺ is useless if the axioms never use it.

**2. TX-302 is internally inconsistent.**  
The row says the Enhanced_Review independently satisfied R1, lists no deviations, and still classifies the case as `JUSTIFIED_EXCEPTION`. That label is for a waived, unmet obligation. If the required review occurred after the last material change and before release, the case is `COMPLIANT`. The exemption is a second sufficient path, not the reason the release is lawful. The footnote about taxonomy does not repair the contradiction in the findings table.

**3. Written R1/R4 and the code do not implement the same materiality test.**  
The formal `AmountInvalid` predicate is only `new > 1.20 * amount_at_review`. The pandas loop also marks a sub-20% move that merely crosses EUR 100,000 as `_material_known`, and then treats any later `_material_known` row as enough to set `r1_review_valid = False`. Crossing a threshold is trigger-relevant; it is not the invalidation rule in R4. No case in this log isolates the bug, but the checker is not a faithful encoding of the rules it claims to check.

The code is also broader in another way: any later jurisdiction / risk / customer-type change invalidates an R1 review. R1’s “latest material data change” can support that reading, but R4 only invalidates on amount. The write-up never states that the implementation chose the broader rule.

**4. Several formal predicates are names, not definitions.**  
`RelevantToCurrentRiskAndCustomer`, `ApprovalCoversEnhancedPacket`, and `ScreenUsedApplicableJurisdictionAndListVersion` are left as English. That is not first-order or Datalog-like formalization; it is a sketch.

**5. R3 is specified one way and coded another.**  
The formal rule triggers only if a prior `Sanctions_Screen` exists. The code, given a matching list update and no baseline screen, returns `REVIEW_REQUIRED_NO_BASELINE_SCREEN`. Those are different theories of the rule. There is no such case here, so it does not change a verdict, but it is still a specification error.

**6. R4 is treated as if it were an activatable obligation.**  
In TX-301 and TX-309, “Triggered rules” includes R4. R4 is an invalidation semantics for amount-dependent duties, not a release-time trigger like R1–R3. The table columns then stop making sense: there is no “satisfied obligation” for R4.

**7. TX-310 is allowed, but the R5 analysis is softer than the rule the answer itself wrote.**  
The answer’s own `ValidExemption` requires `EvidenceSupportsApprovalExistingBefore(x,r)`. The qualified certificate is created after release. The only pre-release story is oral approval asserted by the transaction requester. That is not evidence that “supports” timely approval; it is a conflicted assertion plus a backdated PDF. `INDETERMINATE` is permitted by the prompt, and `REVIEW_REQUIRED` in code is the right machine posture. The narrative still overweights the requester’s claim. A stricter application of the answer’s own R5 would be `NONCOMPLIANT` with residual evidential doubt, not a coin-flip.

**8. Minor semantic sloppiness.**  
- “The initial transaction state is the baseline that a later review must follow” is unclear and is not a policy rule.  
- Create_Transaction is marked material in code (`initial_baseline`). Harmless here, but it conflates “state origin” with “change that can stale a review.”  
- R2 in the table requires `Relevant risk/customer change < Enhanced_Review`. If HIGH/PEP is true from Create, that only works because Create was quietly treated as a change.  
- Confidence “High regarding indeterminacy” on TX-305 is rhetoric, not a calibrated score.

## Code, judged as a checker rather than as a write-up

The script does the required mechanical things: `StringIO`, timestamp parse, `event_index` preserved, `pm4py.format_dataframe`, per-case `ffill` and no `bfill`, release snapshot, last-control tracking, coarse R1–R4 flags, exemption join, unknown-value flags, and a clearly labeled control-flow toy check. It does **not** hard-code narrative verdicts, and EX-77 vs EX-88 is handled as evidence quality rather than as a case-id lookup.

That is useful. It is not a faithful executable formalization.

- Materiality in code ≠ materiality in Section 2.  
- R2’s “standard packet” test is a substring on `note`, which happens to catch TX-307 and would miss a note that does not contain the word “standard.”  
- There is no real DECLARE model; the optional item is two boolean columns. Acceptable, but then the surrounding claim about DECLARE is larger than the demonstration.  
- `format_dataframe` is called, then the pipeline immediately depends on custom columns surviving that call. That is the usual PM4Py behavior, but it is an unstated coupling.  
- Exemption evidence timestamps are still hand-authored facts. That is necessary. The later `ex_evidence_status` strings are what actually decide strong vs conflicted; the timestamp fields are mostly diagnostic.

The post-code remark that a global `Enhanced_Review ≺ Compliance_Approve ≺ Release_Funds` constraint both over-rejects and under-detects is correct and should have been the DECLARE demonstration, not a comment after a printout.
