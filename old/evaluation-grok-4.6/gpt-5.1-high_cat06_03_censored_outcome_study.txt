**6.0**

The write-up is conceptually above the usual failure modes: it does not code rejects/withdrawals/opens as non-default, it states an activation-conditional estimand, it keeps an as-of view, and it argues against a random split. Under a strict rubric that is the floor for a passing design, not evidence of a near-flawless one. Several errors would actually bias the study or leak the label.

**Target.** Conditioning on eventual activation is statistically honest and correctly distinguished from a counterfactual “activate everyone” quantity. It is still a poor match to the requested product—an early score on *every* application at first `Credit Review`—because activation is a *future* treatment. At scoring time the model estimates \(P(Y\mid X,\text{later activation})\) for cases whose activation status is unknown; that is selection, not a well-defined risk for the scored population. The multi-state alternative is described, then abandoned without a two-stage or mixture rule for deployment. The landmark (first `Credit Review` / +2 days) is also mixed with a 90-day clock that starts at a stochastic later time (`Account Activated`), so calendar time from prediction to outcome is undefined and heterogeneous; that is never treated as part of the estimand.

**Cohort.** 21,600 + 3,600 + 9,100 + 5,700 + 2,900 + 5,100 = 48,000, and competing outcomes are not relabelled as 0. The table then claims mutually exclusive rows and immediately adds “permanently missing partner feeds” as an overlapping, unknown subset of the 25,200 activated cases. Those feeds have no residual bucket in the snapshot: the omitted 26,400 are fully partitioned. Treating them as a free extra stratum is sloppy accounting and makes the sensitivity population unidentifiable. Transfers-with-new-IDs are allowed to enter the primary population via a 60% linkage table that is never operationalised, so double-counting vs loss-to-follow-up is unresolved. Terminal state via *last* `concept:name` is not a competing-risk classification once collections events exist; activation is patched with `activation_time`, reject/withdraw/transfer/open are not.

**Censoring.** The taxonomy is the right list, then it collapses. “Ordinary right censoring” is defined as both incomplete 90-day windows *and* delayed feeds, which Section 3 had just separated. Primary analysis is complete-case binary classification on the 21,600, i.e. drop all immature activations. For a fixed 90-day binary that is only valid if maturity is independent of \(Y\) given \(X\)—the assumption the partner-feed story itself undermines. Bounding missing partner outcomes as “all 0 / all 1” is not a serious sensitivity analysis for informative missingness; IPW/g-computation for activation is correctly labelled untestable, then offered as if it were a robustness check rather than a different, stronger estimand.

**Prefixes.** Landmark truncation and length-5 prefixes are specified together and then used differently. After cutting at first `Credit Review`, a k=5 prefix is either the whole truncated trace or an arbitrary cap; document-loop structure is thereby sometimes kept and sometimes chopped. Activity canonicalisation is asserted, not specified (no mapping, no rule for post-15 Oct 2025 duplicates that differ in name). Intra-day order at equal timestamps is ignored, so an Accept/Reject tied with `Credit Review` can enter the prefix.

**Features.** The inventory is reasonable (control-flow, rework, calendar, lagged historical rates). Historical rates and resource default rates are described as as-of, but there is no protocol that they are built only from labels mature *before* the focal prediction time (excluding contemporaneous cases is not enough). Variant IDs from `get_variants` / `discover_dfg` as features are proposed without a training-only vocabulary, so test-time new variants and in-sample leakage of rare paths are unaddressed. Policy/migration dummies based on start date cannot be identified when training is entirely pre-1 Jul 2025 (see validation). `insert_case_service_waiting_time` on a log with a single timestamp does not yield a meaningful service/wait split; inter-event times would.

**Leakage.** The table is the strongest section and still misses the most direct leak: `default_90d` is *repeated on events when known*. In a labeled extract that typically means the outcome is already sitting on Application Started / KYC / first Credit Review. It is not in the drop-list and not in `risky_columns`. `label_available_at` is barred as a feature but not stripped from the event table before aggregation. `documents_total` is “prefer lag, else drop”; the pipeline only drops. Resource experience is “repair if feasible” with no reconstruction rule. The automated check only inspects columns that were explicitly aggregated into `prefix_features`, so it cannot catch last/max aggregations of denormalised label fields or same-timestamp post-decision events.

**Validation.** This is the largest design failure. A 90-day-after-activation label plus 7–35 day feed means a case is evaluable only if `activation_time + 90 + delay ≤ 2026-02-15` (≈ activation by mid-October 2025 at the latest). Putting **test** on applications *started* 15 Oct–31 Dec 2025, then “restricting to matured labels,” yields a tiny, speed-selected slice (fast underwriting, fast activation, fast feed). Non-defaults cannot mature faster than the horizon; any earlier default recording would further distort class mix. Post-migration performance is therefore not identified, which was the point of that split. Train = all pre-policy starts plus a global maturity cutoff of 13 Oct 2025 that the code does not implement; the policy dummy is then constant in train. Rolling-origin with a 125-day lag is mentioned and not aligned with these cuts. Random-split criticism is correct and does not rescue the calendar design.

**Limitations.** This section is the most careful: conditional-on-policy association vs counterfactual default, informative missingness, and four deployment feedback loops. It still over-claims that the primary model is an “early warning for every application” after spending eight sections refusing that target.

**Skeleton.** It is in the requested range and hits several required calls, but it does not implement the study as written. `get_prefixes_from_log(..., max_prefix_length=...)` is likely the wrong signature (`length`), and `prefix_log_k` is never used; features are built from the untruncated landmark prefix. `extract_temporal_features_dataframe` is computed and discarded (and, depending on version, is not a per-case prefix feature table). Waiting time is read from a probably non-existent `case_service_waiting_time`. No train-as-of maturity cutoff, no linkage table, no activity map, no as-of historical rates, no strip of `default_90d` from `df_prefix`. Cohort flags from last activity plus `max` of `default_90d` are not an audit of the 48,000 flow. The survival/competing-risk “TODO” is a comment, which is acceptable only because the primary target was binary—after discarding the censoring problem.

**Net.** Honest target semantics and a real leakage vocabulary, undermined by an unevaluable temporal test, an unaccounted missing-feed population, label columns left on events, and a PM4Py pipeline that demonstrates APIs without wiring them to the design. That is a competent draft, not a study one could run.
