## Formalization quality is the largest gap

The rule table is usable. The pseudo-logic is not.

**R3 is formally wrong.**  
`∀ e_scr ≺ e_upd (act(e_scr) = Sanctions_Screen)` says every earlier event is a screen. On TX-304 that includes `Create_Transaction`, so the trigger as written does **not** fire on the only sanctions case. The obligation formula also leaves `e_upd` unbound. The table and the case row contradict the formulas.

**R1/R4 are smeared together.** `IsMaterialChange` treats every `Create_Transaction`, every jurisdiction change, HIGH reclass, and PEP change as material for R1. R4 is the only place the policy defines a material *amount* change. Risk/PEP changes belong to R2. That over-triggers “refresh Enhanced_Review” in the spec even when the case table does not apply it.

**R2 is incomplete.** It never encodes “relevant” Enhanced_Review, never excludes a Standard_Review packet, and never restates that Standard_Review ≠ Enhanced_Review except in prose. TX-307 is saved only because no Enhanced_Review exists at all.

**R6 is too coarse.** Missing amount or jurisdiction ⇒ R1 INDETERMINATE even when the trigger can already be excluded (e.g. `jurisdiction=DE`, or amount known and `< 100,000`). The policy is “cannot be established or excluded,” not “any hole yields unknown.”

**R1 state snapshot.** “Immediately prior to Release_Funds” would drop `exemption_id` carried *on* the release row (TX-302/TX-310). Evaluation must be at the release event, after applying that row’s own fields.

## Code: does the pipeline, then cheats

Required shape is mostly there: `StringIO`, timestamp parse, sort, `pm4py.format_dataframe`, per-case `ffill`, walk to `Release_Funds`, exemption join, diagnostic frame. Classification is computed, not a case→label dict, and the walk would likely label the 11 cases the same way as the table.

That does not make it faithful.

1. **R4 diagnostics are a case-id lookup** (`TX-301`/`TX-309`/`TX-308`/`TX-306`). The prompt forbids hard-coding the narrative result as a table; this is the same sin on the only rule they bothered to special-case. The loop already invalidates reviews; they then ignore that for `r4_flag`.
2. **`event_index` is used only to sort.** Obligation checks are timestamp `<` / `>=`. On TX-311, review and jurisdiction share `16:20:00Z`, so `t_enh_rev >= t_mat_change` is true even though index 4 is *after* the review. The prose lectures on a tie-break the code does not implement.
3. **R3 is hacked** (`or jur == 'XZ'`). Not a jurisdiction-matched list-delta check.
4. **Exemption `evidence_valid` is pre-judged in a Python dict**, i.e. the forensic conclusion is injected, not derived.
5. **Decision order hides dual satisfaction** (TX-302 becomes SATISFIED_BY_EXEMPTION without reporting that Enhanced_Review already passed).
6. The DECLARE tail is optional, but `pm4py.conformance_declare(...)` with that model shape is not shown to be a real, version-stable API. “Executable” is asserted, not evidenced. Unused `numpy` is noise.

So the code is a decent illustration and a weak checker.

## Section 6–7

The six failure modes are the right list (final-state leakage, post-hoc exemptions, post-review payload change, conditional activation, missing data, timestamp ties). Usefulness drops because of the TX-308 misread and because DECLARE vs data-aware obligations is explained in essay form more than in the script. Section 7 (immutable release payload, four clocks, policy hash, exemption fingerprint, mutation vectors, monotonic order) matches the asked control improvements.

## Net

This reads like a strong analyst note with a broken formal spec and a checker that re-encodes the author’s homework on R4/R3/evidence. Under a strict rubric—temporal semantics, formalization, case reasoning, code usefulness—that is clearly above a mediocre answer and clearly below “nearly flawless.” Minor slips were supposed to cost a lot; the R3 quantifier, the R4 lookup, the unused `event_index` in predicates, TX-308 in §6, and High-confidence TX-310 are not minor.
