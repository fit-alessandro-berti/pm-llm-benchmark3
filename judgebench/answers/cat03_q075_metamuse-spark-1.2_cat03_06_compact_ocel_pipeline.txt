## 1. Modeling assumptions

**Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. Capitalized singular nouns. `ocel:type` uses exactly this string; `ocel:oid` values are `O100`,`O200`,`I1`,`I2`,`I3`,`P1`,`P2`,`D1`,`D2`,`V1`,`M1`,`M2` (12 objects).

**Timezone:** All `ocel:timestamp` are timezone-aware `UTC` via `pd.Timestamp(..., tz='UTC')`. No timestamp ties, so total order is unambiguous.

**E2O qualifier vocabulary (verb-centric, consistent):**
* `creates` - Order creation
* `adds_item` - Item added to Order
* `reserves` - Stock reserved for Item (and operationally for its Order)
* `packs` - Package packing Item (and operationally Order)
* `dispatches` - Delivery dispatching Package
* `issues` - Invoice issued for Order
* `settles` - Payment settling Invoice
* `confirms` - Delivery confirmation
* `closes` - Order closure
Qualifiers describe *role of the object in the event*, not just type. Chosen to be human-readable and to allow filtering `relations[qualifier]`.

**O2O direction conventions (directed by business meaning, stored as qualifier):**
```
Order --contains--> Item
Package --packs--> Item
Delivery --carries--> Package
Invoice --bills--> Order
Payment --partially_settles--> Invoice  (M1)
Payment --completes_settlement--> Invoice (M2)
```
`o2o` is stored as `(ocel:oid = source, ocel:oid_2 = target, ocel:qualifier)` in this direction. PM4Py treats O2O as undirected for analysis, qualifier preserves semantics. No inverse rows are inserted.

**Richness of E2O for downstream events:**
We use a *deliberately rich but source-faithful* policy: shared operational events `e6 Reserve Stock` and `e7 Pack P1` relate **directly to both Items and both Orders** because the narrative says they are *jointly / operationally shared*. `e9/e10 Dispatch`, `e13/e14 Confirm` relate only to `Delivery`+`Package` (source-minimal) and `e11 Issue Invoice` relates to `Invoice`+`Orders`, `e12/e15 Record Payment` relate only to `Payment`+`Invoice`. 

*Trade-off:* Direct source-minimal relations (`Item` only for `e6/e7`, no `Order` link) avoid convergence inflation but make Order-flattened traces miss the shared work and understate synchronization. Full operational involvement (propagating every related Order/Item to every downstream logistics/finance event) makes Order flattening complete but creates massive convergence/divergence, duplicate events after flattening, and spurious DFG edges (e.g., `Confirm Delivery D1` appearing in both `O100` and `O200` traces even though D1 was never observed for O200 in the source system). Propagated analytical relations should not be confused with observation.

**Preventing confusion of source vs analytical propagation:**
E2O table contains *only observed* relations from the narrative. We never materialize O2O-transitive closure into E2O (e.g., we do not auto-add `O100` to `e13` via `O100-contains-I1-packs-P1-carries-D1`). If an analyst wants propagation they must compute it explicitly and tag it e.g. `derived_via_o2o` qualifier or separate DataFrame. This keeps `relations` auditable against the source system.

**Payment amount:** Kept as `events[amount]` attribute (`100` for M1, `150` for M2), not as object. Amount is event data, not an object identity.

**Version-dependent assumption:** `OCEL(events, objects, relations, o2o)` constructor location changed across PM4Py versions (`pm4py.objects.ocel.obj.OCEL` vs `pm4py.objects.ocel.object_ocel.OCEL`). The construction line is isolated in the code block. If `ImportError`, replace with:
```python
from pm4py.objects.ocel.importer import ... # or use pm4py.ocel.* helpers
# or ocel = pm4py.objects.ocel.obj.OCEL(...)
```
Data semantics (the four DataFrames) do not change.

**Most consequential event for convergence/divergence:** `e6 Reserve Stock` and `e7 Pack Package P1`. Each touches *two* Orders and *two* Items plus Package. After flattening on `Order`, the same event `e6`/`e7` is duplicated into both `O100` and `O200` traces (convergence  duplication). After flattening on `Item` or `Package`, `e7` also fans out. If we had instead chosen source-minimal (only `I1,I3` without Orders), Order flattening would incorrectly show no reservation/packing for Orders. `e11 Issue Invoice V1` is also convergence-critical (1 invoice  2 orders) and `e13/e14 Confirm Delivery` are divergence-critical if propagated to Orders.

## 4. Expected flattened behavior

**Order flattening (`pm4py.ocel_flattening(ocel, "Order")`):**
* Trace shape: 2 traces. `O100`: CreateAdd I1Add I2Reserve StockPack P1Pack P2Issue InvoiceClose . `O200`: CreateAdd I3Reserve StockPack P1Issue InvoiceClose . Approx 6-7 events per trace.
* Copied shared events: `e6 Reserve Stock`, `e7 Pack P1`, `e11 Issue Invoice` appear in *both* traces (identical eid duplicated). This is intentional convergence.
* Omitted: `Dispatch`/`Confirm` are omitted for Orders in this modeling (source-minimal downstream), so lifecycle after packing is invisible on Order view. Payments (`e12/e15`) also omitted (only linked to Invoice/Payment), so financial settlement disappears from Order traces.
* Likely DFG edges: `Create Order  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order`. With duplication, `Reserve Stock  Pack Package` will have frequency 2 (once per Order) though there was only one real reservation.
* Misleading interpretation: It looks like two independent reserve/pack operations, suggesting duplicate work; also `Pack P2` will appear only in O100 trace, masking that P1 combined items from both Orders.

**Package flattening (`Package`):**
* Trace shape: 2 traces. `P1`: Pack P1  Dispatch P1  Confirm D1 . `P2`: Pack P2  Dispatch P2  Confirm D2 . Very short.
* Copied: Nothing duplicated here because P1/P2 are distinct, but `e7`'s Item/Order links are dropped from Package view (only Package-relevant edges kept). If we had linked Dispatch to Order, Order noise would leak in.
* Omitted: Order creation, Item addition, Invoice/Payment, and the Order-sharing semantics.
* Likely DFG: `Pack Package  Dispatch Package  Confirm Delivery` linear per package.
* Misleading: Cannot see that P1 required two Orders; cross-order bundling is invisible unless correlation via Items is inspected.

**Delivery flattening (`Delivery`):**
* Trace shape: 2 traces. `D1`: Dispatch P1  Confirm D1 . `D2`: Dispatch P2  Confirm D2 . Even shorter (2 events each).
* Copied: None.
* Omitted: Everything before dispatch and financial layer. No visibility of packing sharing or invoicing.
* Likely DFG: `Dispatch Package  Confirm Delivery` single edge, frequency 2.
* Misleading: Suggests deliveries are independent; does not reveal that D1 delivery implicitly delivers items for two Orders.

**Invoice flattening (`Invoice`):**
* Trace shape: 1 trace for `V1`: Issue Invoice  Record Payment M1  Record Payment M2 . (3 events). If `Close Order` not linked to Invoice, it is omitted.
* Copied: No copy because single invoice, but `e11`'s duplication across Orders collapses to one event here.
* Omitted: Logistics (packing/dispatch/confirmation) entirely.
* Likely DFG: `Issue Invoice  Record Payment  Record Payment` linear; skeleton will show `Record Payment` can repeat (equivalence not strict precedence).
* Misleading: Appears as if invoice lifecycle is isolated from fulfillment; progress of Orders vs Payments not correlated.

**Why flattening on `Payment` would be particularly weak:**
Each Payment object (`M1`,`M2`) participates in exactly one event (`e12` for M1, `e15` for M2). Flattened Payment log therefore has 2 traces of length 1 each, no edges to discover. DFG is empty, skeleton is trivial. All context (which Invoice, which Orders, amounts, ordering between M1 and M2) is visible only via Invoice or via event attribute, not via Payment control-flow. Flattening on a degenerate object type destroys ordering information and yields no process model, demonstrating why object-centric rather than single-case flattening is needed for financial settlement.

## 5. Expected object-centric structures

**OC-DFG (`discover_ocdfg`):**
Shows typed edges. Expect `Create Order  Add Item` per `Order`, `Add Item  Reserve Stock` (Order and Item edges converging), `Reserve Stock  Pack Package` with both Order and Item colors indicating shared event `e7` processes `P1` plus `I1,I3` plus `O100,O200`. `Pack Package` bifurcates: `P1` edge to `Dispatch Package` (via D1) and `P2` edge separate. `Dispatch Package  Confirm Delivery` per `Delivery`/`Package`. Separate component `Issue Invoice  Record Payment` loops on `Invoice`. The OC-DFG correctly preserves that `P1` combines `I1` (O100) and `I3` (O200) while `P2` is exclusive to `O100`/`I2`. Divergence is visible as `Pack Package` having two output Package tokens.

**OTG (Object Type Graph):**
Nodes = types, edges = co-occurrence in an event or O2O. Expect strong clique `Order-Item-Package` via `e6/e7` and O2O `contains/packs`, `Package-Delivery` via `carries`, `Order-Invoice` via `bills`, `Invoice-Payment` via `settles`. Notably `Item` connects to `Order` and `Package` but not directly to `Delivery`/`Invoice`, revealing indirect delivery via Package. `Payment` only connects to `Invoice`, isolating financial layer.

**ET–OT (Event-Type – Object-Type) graph:**
Matrix of which activity touches which type. Expect `Reserve Stock` linked to `Order`+`Item` (not to Package/Delivery), `Pack Package` to `Order+Item+Package`, `Dispatch` to `Package+Delivery`, `Issue Invoice` to `Invoice+Order`, `Record Payment` to `Invoice+Payment` only, `Confirm Delivery` to `Delivery+Package` only. This makes the modeling choice transparent: logistics tail and payments are not artificially propagated to Orders.

**Object-centric Petri net (`discover_oc_petri_net`):**
Will discover a net with variable arcs for shared events. `Reserve Stock` transition will have variable arcs consuming/producing 2 `Order` and 2 `Item` tokens simultaneously, `Pack P1` similarly with 2 Orders + 2 Items + 1 Package. `Issue Invoice V1` transition will have 1 Invoice + 2 Order arcs. Places are typed. The net will allow replay where `P1` synchronizes `O100` and `O200`, and `V1` synchronizes payments `M1,M2`. No single total order is enforced; possibilities remain. Interpretation is *not* unique: different discovery parameters can merge/split transitions, and variable arcs may be under/over-generalized. Reviewer must not claim one canonical net.

**Object-interactions summary (`ocel_objects_interactions_summary`):**
Will report interactions per event: e.g., `e6` has 4 objects (2 Orders +2 Items), `e7` has 5, `e11` has 3. Aggregated, `Order`-`Item` interactions = 5+ (contains/packs), `Package`-`Item` =3, `Invoice`-`Order`=2, `Payment`-`Invoice`=2. Will highlight `P1` interacting with two Orders indirectly (via Items) and directly via E2O, `V1` interacting with both Orders and both Payments (`M1` partially, `M2` completing), and `O100` longer lifecycle than `O200` (extra `P2`).

## 6. Modeling alternatives

**A. Source-minimal relations (strict observation).**
*Policy:* Only link objects explicitly mentioned in the system record for that event. `e6` links only `I1,I3`; `e7` only `P1,I1,I3`; `e9/e10` only `Package+Delivery`; `e11` only `V1` (+ maybe Orders if invoice table says so but not propagated); payments only `Payment+Invoice`.
*Effect:* Flattened `Order` loses `Reserve Stock` and `Pack` entirely  Order DFG collapses to `Create  Add Item  Close`, missing operational sharing. OC-DFG shows no Order edges for reservation/packing, suggesting those activities are item-only, hiding cross-order bundling. Cleaner, no convergence duplication, but analytically incomplete for order-centric KPI (e.g., order lead time to dispatch).

**B. Full operational involvement (maximal propagation).**
*Policy:* Every event after order creation propagates to all Orders/Items that are transitively related via O2O at that time (e.g., `e9 Dispatch P1` also links `O100,O200,I1,I3`, `e13 Confirm D1` also links `O100,O200`, `e12 Payment M1` links `V1`+`O100`+`O200`).
*Effect:* Order flattening now shows `Dispatch` and `Confirm` and `Payment` in Order traces, enabling end-to-end Order lifecycle including delivery and payment. However causes massive relation inflation (e.g., `Confirm D1` duplicated into two Order traces despite only one delivery), divergence on Invoice/Payment, and spurious DFG edges (`Dispatch  Confirm` appears per Order though logically per Delivery). OC-DFG becomes dense with Order edges on every activity, obscuring which object type truly drives the activity.

**C. O2O-propagated analytical relations (separate derived layer).**
*Policy:* Keep E2O minimal as in (A) for source truth, but compute a derived relation table `relations_derived = propagate(events, o2o)` where qualifier prefixed `derived_via_*` (e.g., `derived_via_contains_packs`). Never mix into base `relations`; use only for specific analytical questions.
*Effect:* Business story unchanged. Discovery results can be compared: OC-DFG on base vs derived shows impact of propagation without polluting source model. Flattening can be done on base for fidelity or on derived for completeness, and the difference is auditable. Prevents treating propagation as observation and allows versioned qualifiers. More code, but cleanest for evaluation of semantic consistency.

All three preserve the same narrative (P1 combines two Orders, V1 bills both, M1+M2 settle V1) but change which object types appear to participate in which activities, thus changing convergence/divergence, duplicate counts, and discovered control-flow.

## 7. Failure modes

1. **Relation inflation:** Linking every downstream logistics/finance event to Orders/Items via transitive O2O adds 10+ spurious E2O rows (e.g., D1 confirm  O100,O200). Flattened Order log then duplicates Confirm events, inflating frequencies and creating false `Payment  Confirm` edges.

2. **Missing direct E2O links:** Omitting `O100`/`O200` from `e6 Reserve Stock` or `e7 Pack P1` makes Order flattening miss shared work, under-reports order waiting time, and makes P1 appear item-only. Convergence is lost.

3. **Treating O2O propagation as observation:** Materializing `O100--contains-->I1--packs-->P1--carries-->D1` as direct E2O `Confirm D1 – O100` and then interpreting it as “O100 was observed at delivery confirmation” conflates derived analytic linkage with source-system fact. Audit fails.

4. **Duplicate shared events after flattening:** `e6`/`e7`/`e11` appear once in reality but twice after Order flattening (one copy per Order). Naïve frequency-based DFG will count `Reserve Stock  Pack` as 2 though only 1 execution occurred; performance annotations double-count.

5. **Ambiguous payment allocation:** Modeling `M1`/`M2` as settling `Order` directly (instead of `Invoice`) loses that V1 bills both Orders jointly; it becomes unclear whether M1 settles O100 or O200. Invoice-centric settlement must be preserved via `Payment  Invoice` + `Invoice  Order` O2O, not `Payment  Order`.

6. **Overly short Payment traces:** Each Payment has single event, so Payment-flattened log has no transitions. Discovering DFG/skeleton on Payment yields empty models and misleading “no process” conclusion. Indicates wrong case notion.

7. **Constructor/API version mismatch:** `OCEL(events,objects,relations,o2o)` signature or `discover_ocdfg`/`ocel_flattening` naming changes across PM4Py 2.7–2.12. Hard-coding import without try/except causes `TypeError: unexpected keyword o2o` and the pipeline fails despite correct DataFrames. Isolating construction line and documenting fallback avoids semantic change.

8. **False total order for same-time events:** Even though this dataset has no timestamp ties, many pipelines sort by timestamp and then assume total order. If two events shared a timestamp (e.g., two Packs at 09:00), flattening order would be arbitrary but DFG would still infer `A  B`. Need to state that discovery assumes partial order; this example avoids ties intentionally to keep validation clean.

## 8. Final semantic checks

Reviewer can manually inspect tables without running code:

1. **Order split:** `objects` contains exactly `O100`,`O200` as `Order`; `o2o` shows `O100 contains I1,I2` and `O200 contains I3` – no Item belongs to both Orders.

2. **Cross-order package:** `o2o` `P1 packs I1` and `P1 packs I3` with `D1 carries P1`; together with `O100-contains-I1` and `O200-contains-I3` this proves `P1` bundles items from two different Orders. `P2 packs I2` is exclusive.

3. **Shared reservation:** `relations` for `e6 Reserve Stock` lists four rows: `I1,I3,O100,O200` with same timestamp `2026-04-06 08:30 UTC` – confirms joint reservation.

4. **Invoice bridges Orders:** `relations` for `e11 Issue Invoice` has `V1,O100,O200`; `o2o` has `V1 bills O100` and `V1 bills O200` – single invoice billing two Orders.

5. **Payments settle invoice not orders:** `relations` for `e12` and `e15` each contain `V1`+`M1`/`M2` only, with `amount 100` and `150` in `events`; `o2o` has `M1 partially_settles V1` and `M2 completes_settlement V1` – no direct `PaymentOrder` rows, correct partial settlement semantics.

6. **E2O consistency:** Every `relations` row repeats `ocel:activity` and `ocel:timestamp` exactly as in `events` for that `eid` (e.g., `e7` is always `Pack Package 2026-04-06 09:00 UTC`), no orphan `eid`/`oid`, no duplicate `eid+oid+qualifier`, and `Close Order` events `e16/e17` each relate to single distinct Order (`O200` then `O100`) with later timestamp for O100, matching narrative order of closure.
