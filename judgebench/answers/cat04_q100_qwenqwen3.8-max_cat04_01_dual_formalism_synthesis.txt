# 1. Assumptions and Interpretation

1. **Completion-time semantics.** The narrative says activities are recorded at completion time. Therefore, “X may start only after Y is complete” is modeled as a precedence constraint from the completion event of Y to the completion event of X.

2. **Low-risk/high-risk representation.** The risk route is represented as a control-flow exclusive choice after `Analyze Root Cause`:
   - low risk: `Supervisor Review`;
   - high risk: `Quality Review` and `Regulatory Review` in parallel, with no ordering between them.
   
   No explicit data attribute such as `risk = high` is modeled.

3. **Optional supplier consultation.** `Consult Supplier` is represented as an exclusive choice between `Consult Supplier` and a silent transition. This makes the activity optional and allows it at most once. The selection is assumed to be driven by external case data not represented in the control-flow model.

4. **Passing inspection abstraction.** The inspection result is not represented as a separate label. A trial cycle is `Execute Trial` followed by `Inspect Trial`. The loop redo branch `Adjust Parameters` represents a failed inspection followed by another trial cycle. Loop exit represents the passing inspection.

5. **Duplicate visible labels.** Duplicate visible labels are permitted in principle as an approximation technique, but they are **not used** in the final models below. Each visible activity label appears once in the process tree and once in the POWL model. This avoids label-duplication artifacts but requires the process tree to under-approximate some overlap behavior.

6. **Process-tree approximation policy.** The process tree uses a **conservative under-approximation** policy. It preserves all mandatory precedence constraints and release synchronization, but it forces the approval route and optional supplier consultation to complete before the trial loop starts. This excludes some intended overlapping behavior but does not admit unsafe release behavior.

7. **Interpretation of “may overlap.”** “May overlap” is interpreted as **absence of an order constraint** in the partial-order model. In a Petri-net or process-tree execution semantics this may correspond to true concurrency, but from a trace perspective it means all linearizations consistent with the partial order are allowed.

8. **Overlap with containment.** The only explicit precondition for `Consult Supplier` and the approval route is `Analyze Root Cause`. Since `Contain Material` and `Analyze Root Cause` may overlap, the models allow supplier consultation or approvals to overlap `Contain Material` if root-cause analysis finishes first. No additional `Contain Material -> Consult Supplier` dependency is added because it is not stated in the narrative.

9. **Loop semantics.** PM4Py’s `LOOP(body, redo)` is interpreted as executing the body at least once, then optionally executing the redo branch and repeating the body. Thus `LOOP(Execute Trial -> Inspect Trial, Adjust Parameters)` gives `Execute Trial, Inspect Trial, (Adjust Parameters, Execute Trial, Inspect Trial)*`.

# 3. PM4Py Process-Tree Model

Compact process-tree expression:

```text
sequence(
  Register Deviation,
  parallel(
    sequence(Contain Material, Plan Verification),
    sequence(
      Analyze Root Cause,
      parallel(
        Design Corrective Action,
        xor(
          Supervisor Review,
          parallel(Quality Review, Regulatory Review)
        ),
        xor(Consult Supplier, tau)
      )
    )
  ),
  loop(
    sequence(Execute Trial, Inspect Trial),
    Adjust Parameters
  ),
  Release Material,
  Archive Case
)
```

Here `tau` is a silent transition used to make `Consult Supplier` optional.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def make_leaf(label=None):
    """Create a process-tree leaf. label=None is treated as silent/tau."""
    return ProcessTree(label=label)


def make_node(operator, children):
    """
    Create a process-tree operator node and explicitly attach children.
    PM4Py requires both parent.children insertion and child.parent assignment.
    """
    n = ProcessTree(operator=operator, children=[])
    for child in children:
        n.children.append(child)
        child.parent = n
    return n


# Visible activity leaves
register = make_leaf("Register Deviation")
contain = make_leaf("Contain Material")
analyze = make_leaf("Analyze Root Cause")
plan = make_leaf("Plan Verification")
design = make_leaf("Design Corrective Action")
supervisor = make_leaf("Supervisor Review")
quality = make_leaf("Quality Review")
regulatory = make_leaf("Regulatory Review")
consult = make_leaf("Consult Supplier")
execute = make_leaf("Execute Trial")
inspect_trial = make_leaf("Inspect Trial")
adjust = make_leaf("Adjust Parameters")
release = make_leaf("Release Material")
archive = make_leaf("Archive Case")

# Silent leaf for optional supplier consultation
silent_supplier = make_leaf(None)

# High-risk route: Quality Review and Regulatory Review concurrent, either order
high_risk_route = make_node(Operator.PARALLEL, [quality, regulatory])

# Risk route: low-risk Supervisor Review XOR high-risk parallel reviews
approval_route = make_node(Operator.XOR, [supervisor, high_risk_route])

# Optional supplier consultation: Consult Supplier XOR silent
supplier_option = make_node(Operator.XOR, [consult, silent_supplier])

# After Analyze Root Cause: design, approval route, and optional supplier may proceed concurrently.
# This is the conservative under-approximation: they must complete before the trial loop.
post_analysis = make_node(
    Operator.PARALLEL,
    [design, approval_route, supplier_option]
)

analysis_branch = make_node(Operator.SEQUENCE, [analyze, post_analysis])
contain_branch = make_node(Operator.SEQUENCE, [contain, plan])

# Initial independent work streams: containment/planning and root-cause/design/approvals/supplier
initial_parallel = make_node(Operator.PARALLEL, [contain_branch, analysis_branch])

# Trial loop: Execute Trial -> Inspect Trial, repeat via Adjust Parameters
trial_body = make_node(Operator.SEQUENCE, [execute, inspect_trial])
trial_loop = make_node(Operator.LOOP, [trial_body, adjust])

# Full process tree
tree = make_node(
    Operator.SEQUENCE,
    [register, initial_parallel, trial_loop, release, archive]
)
```

The constructed tree is assigned to the variable `tree`. The helper `make_node` explicitly appends each child to `parent.children` and sets `child.parent`, satisfying PM4Py’s parent/child handling expectations.

The process tree cannot represent the intended behavior exactly because the intended pattern has mismatched synchronization: `Design Corrective Action` must join with `Plan Verification` to enable the trial, while the approval route and optional supplier consultation fork from `Analyze Root Cause` but synchronize later at `Release Material`, possibly after the trial has already started. A block-structured process tree cannot express this without either duplicating subtrees or forcing some obligations to complete earlier than required. The chosen tree therefore uses a conservative under-approximation. It exactly represents: start with `Register Deviation`; end with `Archive Case`; independent `Contain Material`/`Analyze Root Cause` streams; `Plan Verification` after containment; `Design Corrective Action` after root cause; low/high approval choice; high-risk review concurrency; optional supplier at most once; trial loop with no trailing `Adjust Parameters`; and release after trial. It approximates requirements 6, 7, and 9 by forcing the approval route and supplier consultation to finish before the trial loop starts. Thus it excludes legal overlaps of approvals or supplier consultation with trial work, but it does not permit release before those obligations are complete. It also abstracts data conditions: risk, supplier involvement, and inspection pass/fail are represented only through control-flow alternatives.

# 4. PM4Py POWL Model

Compact POWL description:

```text
Top-level nodes:
  R = Register Deviation
  C = Contain Material
  A = Analyze Root Cause
  P = Plan Verification
  D = Design Corrective Action
  ApprovalRoute = XOR(
      Supervisor Review,
      PO{Quality Review, Regulatory Review}   // no order between Q and G
  )
  SupplierOption = XOR(Consult Supplier, silent)
  TrialLoop = LOOP(PO{Execute Trial -> Inspect Trial}, Adjust Parameters)
  M = Release Material
  Z = Archive Case

Partial-order edges:
  R -> C
  R -> A
  C -> P
  A -> D
  A -> ApprovalRoute
  A -> SupplierOption
  P -> TrialLoop
  D -> TrialLoop
  TrialLoop -> M
  ApprovalRoute -> M
  SupplierOption -> M
  M -> Z

Intentionally absent edges:
  no C -> A or A -> C
  no P -> D or D -> P
  no ApprovalRoute -> TrialLoop or TrialLoop -> ApprovalRoute
  no SupplierOption -> TrialLoop or TrialLoop -> SupplierOption
  no Quality Review -> Regulatory Review or Regulatory Review -> Quality Review

# No order edge is added between them.
high_risk_route = StrictPartialOrder([quality, regulatory])

# Risk route: low-risk Supervisor Review XOR high-risk parallel reviews
approval_route = OperatorPOWL(Operator.XOR, [supervisor, high_risk_route])

# Optional supplier consultation: Consult Supplier XOR silent
supplier_option = OperatorPOWL(Operator.XOR, [consult, supplier_silent])

# Trial cycle: Execute Trial -> Inspect Trial

trial_cycle.order.add_edge(execute, inspect_trial)

# Trial loop: repeat trial cycle via Adjust Parameters until loop exit
trial_loop = OperatorPOWL(Operator.LOOP, [trial_cycle, adjust])

# Top-level POWL model
powl = StrictPartialOrder(
    [
        register,
        contain,
        analyze,
        plan,
        design,
        approval_route,
        supplier_option,
        trial_loop,
        release,
        archive,
    ]
)

# Initial split: Register enables Containment and Root Cause Analysis
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# Containment enables verification planning
powl.order.add_edge(contain, plan)

# Root-cause analysis enables design, approval route, and optional supplier
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, approval_route)
powl.order.add_edge(analyze, supplier_option)

# Trial loop requires both planning and design
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# Release synchronization: trial completion, selected approvals, and supplier if selected
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(approval_route, release)
powl.order.add_edge(supplier_option, release)

# Case end
powl.order.add_edge(release, archive)
```

The constructed POWL model is assigned to the variable `powl`.

The intentionally unconnected node pairs are deliberate concurrency permissions. `Contain Material` and `Analyze Root Cause` are unconnected because they may proceed independently after registration. `Plan Verification` and `Design Corrective Action` are unconnected because they depend on different predecessor activities and need not complete in a fixed order. `Design Corrective Action`, `ApprovalRoute`, and `SupplierOption` are all after `Analyze Root Cause` but are mutually unconnected because they may overlap. `ApprovalRoute` and `TrialLoop` are unconnected because approvals may overlap the trial cycle and need not finish before trial start. `SupplierOption` and `TrialLoop` are unconnected because supplier consultation may overlap trial work. `ApprovalRoute` and `SupplierOption` are unconnected because supplier consultation may overlap approvals. Inside the high-risk route, `Quality Review` and `Regulatory Review` are unconnected because they may occur concurrently and complete in either order. The only ordering constraints are those required by the narrative; all other pairs remain concurrent by design.

# 7. Preferred Representation and Validation Plan

The preferred canonical representation is the **POWL model**. The process tree is useful for compatibility with tools that require block-structured models, but it must under-approximate the intended behavior because the narrative contains mismatched synchronization: design and planning enable the trial, while approvals and optional supplier consultation synchronize later at release. The POWL model directly represents these cross-branch dependencies using partial-order edges, avoids duplicate visible labels, and preserves the intended overlap between approvals, supplier consultation, and trial work.

Validation plan:

1. **Convert models to accepting Petri nets where supported.**

   ```python
   import pm4py

   tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)

   # POWL-to-Petri-net conversion may depend on the PM4Py version.
   try:
       powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   except Exception as e:
       print("POWL conversion not supported or failed:", e)
       powl_net = powl_im = powl_fm = None
   ```

   The resulting Petri nets should be treated as accepting nets with explicit initial and final markings.

2. **Check soundness of converted nets.**

   ```python
   pm4py.check_soundness(tree_net, tree_im, tree_fm, print_diagnostics=True)

   if powl_net is not None:
       pm4py.check_soundness(powl_net, powl_im, powl_fm, print_diagnostics=True)
   ```

   Expected result: proper completion, no deadlocks, and no leftover tokens at final marking. Soundness is evidence of structural well-formedness, not proof of narrative fidelity.

3. **Bounded or sampled playout.**

   Use `pm4py.play_out` with a bounded event limit or sample limit. Because the trial loop is unbounded, the playout should be bounded, for example to at most three trial iterations or a maximum number of events per case.

   ```python
   # Illustrative; exact keyword arguments may vary by PM4Py version.
   tree_log = pm4py.play_out(tree, max_events=100)
   if powl_net is not None:
       powl_log = pm4py.play_out(powl, max_events=100)
   ```

   Inspect generated traces for expected patterns: initial registration, final archiving, at least one trial cycle, optional supplier presence/absence, and no trailing `Adjust Parameters`.

4. **Explicit positive and negative trace tests.**

   Use the eight witnesses from Section 5.

   Positive traces A1–A5 should be accepted by the intended semantics. In the process-tree net, A5 is expected to fail because it exposes the conservative under-approximation. In the POWL model, A5 should be accepted.

   Negative traces F1–F3 should be rejected by both models:
   - F1 violates the start rule.
   - F2 violates the cross-branch trial precondition.
   - F3 violates the repeat-until/no-trailing-adjustment rule.

   If PM4Py trace replay or fitness checking is available, replay each witness against the converted Petri nets. Otherwise, manually check token enabling for the earliest violating event.

5. **Silent-behavior and duplicate-label check.**

   Traverse both models and collect visible labels. Assert that each visible label appears once in the model. During playout, assert that no visible trace contains duplicate visible labels. Also assert that some traces contain `Consult Supplier` and some do not, demonstrating the silent optional branch. Silent transitions should not appear in visible traces.

   Additional loop check: in sampled playout, assert that every occurrence of `Adjust Parameters` is followed by another `Execute Trial` before `Release Material`.

6. **Limitations of the validation plan.**

   - Playout sampling is not exhaustive, especially with an unbounded trial loop.
   - Soundness checks structural net properties but does not prove that the model matches the business narrative.
   - The abstraction of risk, supplier involvement, and inspection results means that some business-invalid traces may be control-flow valid.
   - PM4Py’s POWL-to-Petri-net conversion may be version-dependent or may impose operational semantics that differ subtly from the intended partial-order interpretation.
   - The process-tree approximation intentionally excludes trace A5, so a failed replay of A5 on the tree is an expected approximation artifact, not a modeling bug.

# 8. Final Self-Critique

1. **Semantic weakness: data conditions are not represented.** The model treats risk level, supplier necessity, and inspection outcome as control-flow alternatives. Therefore, a trace that is control-flow valid may still be business-invalid if the underlying case data would have required a different route. Conformance checking against event logs without those data attributes cannot detect such mismatches.

2. **Semantic weakness: inspection pass/fail is inferred only from loop continuation.** The models assume that an `Inspect Trial` followed by `Adjust Parameters` represents a failed inspection, while loop exit represents a passing inspection. If an external quality system records a pass/fail attribute, the control-flow model alone cannot reconcile cases where the label sequence is ambiguous or inconsistent with that attribute.

3. **Representational/validation weakness: the process-tree approximation and bounded validation leave gaps.** The conservative process tree excludes legally allowed overlap, and the validation plan cannot exhaustively validate the unbounded trial loop. In addition, PM4Py’s handling of compound POWL operators, conversion to Petri nets, and interleaving semantics may vary by version, so successful construction or soundness checking should be treated as evidence to inspect rather than proof of full semantic fidelity.
