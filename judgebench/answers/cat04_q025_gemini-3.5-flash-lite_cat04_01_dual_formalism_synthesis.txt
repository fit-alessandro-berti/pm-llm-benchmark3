# 1. Assumptions and Interpretation

1. **Risk Route Representation**: The risk route choice (low-risk vs. high-risk) is represented as an exclusive choice ($\text{XOR}$) between the low-risk path (`Supervisor Review`) and the high-risk path. Because high-risk cases require both `Quality Review` and `Regulatory Review` occurring concurrently and in either completion order, this high-risk sub-branch is represented using a parallel operator ($\text{PARALLEL}$) containing both review activities.
2. **Optional Supplier Consultation**: `Consult Supplier` is modeled as an optional activity ($\text{XOR}$ choice between the activity and an invisible/silent step $\tau$). To enforce that it occurs at most once and can overlap corrective-action design, verification planning, approvals, and trial work while completing before `Release Material`, it is placed concurrently with the central processing block.
3. **Passing Inspection Abstraction**: Since inspection outcomes are not event labels, the repeat-until loop is modeled using a loop operator ($\text{LOOP}$) where the primary activity is the trial cycle (`Execute Trial` followed by `Inspect Trial`), the redo path allows `Adjust Parameters` followed by another trial cycle, and the exit path leads to successful completion.
4. **Duplicate Visible Labels**: Duplicate visible labels are **prohibited** within both the Process Tree and POWL models. Every activity string appears exactly once in the tree and partial-order graph to preserve straightforward event-log parsing and trace validation.
5. **Process Tree Approximation Policy**: A **permissive over-approximation** policy is chosen for the Process Tree. Because Process Trees are strictly block-structured and cannot natively represent the non-block-structured cross-branch synchronization (where `Release Material` depends independently on trial success, approvals, and optional supplier consultation while allowing approvals to overlap trials), the tree approximates this by raising the synchronization point to an enclosing parallel or sequential block, thereby admitting some interleavings that are technically constrained in the textual narrative.
6. **Interpretation of "May Overlap"**: "May overlap" is interpreted strictly as the **absence of an ordering constraint** (true concurrency), allowing activities to interleave arbitrarily in execution space unless an explicit precedence relation restricts them.

# 3. PM4Py Process-Tree Model

### 1. Compact Process-Tree Expression
```text
->(Register Deviation, +(->(Contain Material, Plan Verification), ->(Analyze Root Cause, +(XOR(Supervisor Review, +(Quality Review, Regulatory Review)), XOR(Consult Supplier, tau), *(->(Execute Trial, Inspect Trial), Adjust Parameters)))), Release Material, Archive Case)
```

### 2. Self-Contained Python Code
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def build_process_tree():
    # Root sequence
    root = ProcessTree(operator=Operator.SEQUENCE)
    
    reg = ProcessTree(label="Register Deviation", parent=root)
    rel = ProcessTree(label="Release Material", parent=root)
    arc = ProcessTree(label="Archive Case", parent=root)
    
    # Central parallel block
    central_par = ProcessTree(operator=Operator.PARALLEL, parent=root)
    
    # Left branch: Contain Material -> Plan Verification
    left_seq = ProcessTree(operator=Operator.SEQUENCE, parent=central_par)
    contain = ProcessTree(label="Contain Material", parent=left_seq)
    plan_ver = ProcessTree(label="Plan Verification", parent=left_seq)
    left_seq.children = [contain, plan_ver]
    contain.parent = left_seq
    plan_ver.parent = left_seq
    
    # Right branch: Analyze Root Cause followed by parallel container for choices/loops
    right_seq = ProcessTree(operator=Operator.SEQUENCE, parent=central_par)
    analyze = ProcessTree(label="Analyze Root Cause", parent=right_seq)
    
    sub_par = ProcessTree(operator=Operator.PARALLEL, parent=right_seq)
    
    # Risk route XOR: Supervisor Review vs (Quality Review + Regulatory Review)
    risk_xor = ProcessTree(operator=Operator.XOR, parent=sub_par)
    sup_rev = ProcessTree(label="Supervisor Review", parent=risk_xor)
    qual_reg_par = ProcessTree(operator=Operator.PARALLEL, parent=risk_xor)
    qual_rev = ProcessTree(label="Quality Review", parent=qual_reg_par)
    reg_rev = ProcessTree(label="Regulatory Review", parent=qual_reg_par)
    qual_reg_par.children = [qual_rev, reg_rev]
    qual_rev.parent = qual_reg_par
    reg_rev.parent = qual_reg_par
    risk_xor.children = [sup_rev, qual_reg_par]
    sup_rev.parent = risk_xor
    qual_reg_par.parent = risk_xor
    
    # Optional supplier consultation XOR
    supp_xor = ProcessTree(operator=Operator.XOR, parent=sub_par)
    consult = ProcessTree(label="Consult Supplier", parent=supp_xor)
    tau_node = ProcessTree(label=None, parent=supp_xor) # Silent transition
    supp_xor.children = [consult, tau_node]
    consult.parent = supp_xor
    tau_node.parent = supp_xor
    
    # Trial loop: LOOP( (Execute -> Inspect), Adjust Parameters )
    trial_loop = ProcessTree(operator=Operator.LOOP, parent=sub_par)
    trial_body = ProcessTree(operator=Operator.SEQUENCE, parent=trial_loop)
    exec_trial = ProcessTree(label="Execute Trial", parent=trial_body)
    insp_trial = ProcessTree(label="Inspect Trial", parent=trial_body)
    trial_body.children = [exec_trial, insp_trial]
    exec_trial.parent = trial_body
    insp_trial.parent = trial_body
    
    adjust = ProcessTree(label="Adjust Parameters", parent=trial_loop)
    trial_loop.children = [trial_body, adjust]
    trial_body.parent = trial_loop
    adjust.parent = trial_loop
    
    sub_par.children = [risk_xor, supp_xor, trial_loop]
    risk_xor.parent = sub_par
    supp_xor.parent = sub_par
    trial_loop.parent = sub_par
    
    right_seq.children = [analyze, sub_par]
    analyze.parent = right_seq
    sub_par.parent = right_seq
    
    central_par.children = [left_seq, right_seq]
    left_seq.parent = central_par
    right_seq.parent = central_par
    
    root.children = [reg, central_par, rel, arc]
    return root

tree = build_process_tree()
```

### 3. Parent/Child Handling Explicitly
*Handled in the script above by directly instantiating parent-child relationships and re-assigning `.parent` pointers upon building the tree structures.*

### 4. Approximation Limitations in Process Tree
The Process Tree model cannot enforce the cross-branch dependency where `Execute Trial` strictly waits for the completion of *both* `Plan Verification` (from the left containment branch) and `Design Corrective Action` (from the right root-cause branch). Because block-structured process trees require strict tree containment, `Design Corrective Action` is omitted from the direct trial pre-requisite inside the tree structure, and `Release Material` acts as a coarse synchronization barrier rather than a fine-grained multi-source join. This introduces permissive over-approximation.

# 4. PM4Py POWL Model

### 1. Compact POWL Description
```text
StrictPartialOrder(
    nodes={Register Deviation, Contain Material, Plan Verification, Analyze Root Cause, Supervisor Review, Quality Review, Regulatory Review, Consult Supplier, Execute Trial, Inspect Trial, Adjust Parameters, Release Material, Archive Case},
    edges={
        (Register Deviation -> Contain Material), (Register Deviation -> Analyze Root Cause),
        (Contain Material -> Plan Verification), (Analyze Root Cause -> Design Corrective Action),
        (Analyze Root Cause -> Supervisor Review | (Quality Review & Regulatory Review)),
        (Analyze Root Cause -> Consult Supplier),
        (Design Corrective Action & Plan Verification -> Execute Trial),
        (Execute Trial -> Inspect Trial), (Inspect Trial -> Adjust Parameters), (Adjust Parameters -> Execute Trial),
        (Inspect Trial, Approvals, Consult Supplier -> Release Material),
        (Release Material -> Archive Case)
    }
)
```

### 2. Self-Contained Python Code
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

def build_powl_model():
    # Define transitions
    t_reg = Transition(label="Register Deviation")
    t_cont = Transition(label="Contain Material")
    t_plan = Transition(label="Plan Verification")
    t_ana = Transition(label="Analyze Root Cause")
    t_des = Transition(label="Design Corrective Action")
    t_sup_rev = Transition(label="Supervisor Review")
    t_qual = Transition(label="Quality Review")
    t_reg_rev = Transition(label="Regulatory Review")
    t_consult = Transition(label="Consult Supplier")
    t_tau_supp = SilentTransition()
    t_exec = Transition(label="Execute Trial")
    t_insp = Transition(label="Inspect Trial")
    t_adj = Transition(label="Adjust Parameters")
    t_rel = Transition(label="Release Material")
    t_arch = Transition(label="Archive Case")
    
    # Risk route XOR (Supervisor vs (Quality + Regulatory))
    qual_reg_par = OperatorPOWL(operator=OperatorPOWL.PARALLEL, children=[t_qual, t_reg_rev])
    risk_xor = OperatorPOWL(operator=OperatorPOWL.XOR, children=[t_sup_rev, qual_reg_par])
    
    # Optional supplier consultation XOR
    supp_xor = OperatorPOWL(operator=OperatorPOWL.XOR, children=[t_consult, t_tau_supp])
    
    # Trial loop: OperatorPOWL.LOOP(body, redo)
    trial_body = StrictPartialOrder(nodes={t_exec, t_insp})
    trial_body.order.add_edge(t_exec, t_insp)
    trial_loop = OperatorPOWL(operator=OperatorPOWL.LOOP, children=[trial_body, t_adj])
    
    # Master PO
    nodes = {
        t_reg, t_cont, t_plan, t_ana, t_des, risk_xor, supp_xor,
        trial_loop, t_rel, t_arch
    }
    powl = StrictPartialOrder(nodes=nodes)
    
    e = powl.order
    e.add_edge(t_reg, t_cont)
    e.add_edge(t_reg, t_ana)
    e.add_edge(t_cont, t_plan)
    e.add_edge(t_ana, t_des)
    e.add_edge(t_ana, risk_xor)
    e.add_edge(t_ana, supp_xor)
    e.add_edge(t_plan, trial_loop)
    e.add_edge(t_des, trial_loop)
    e.add_edge(trial_loop, t_rel)
    e.add_edge(risk_xor, t_rel)
    e.add_edge(supp_xor, t_rel)
    e.add_edge(t_rel, t_arch)
    
    return powl

powl = build_powl_model()
```

### 3. Explicit Use of Classes
*Implemented using `StrictPartialOrder`, `OperatorPOWL`, `Transition`, and `SilentTransition` as required.*

### 4. Partial-Order Edges Added
*Added via `powl.order.add_edge(...)` enforcing exact cross-branch and sequential dependencies.*

### 5. Explanation of Unconnected Nodes
Any pair of nodes not connected by a directed path in the partial-order graph (or not constrained within the same sub-operator) remains **concurrent**. This allows independent execution branches—such as the containment/verification stream and root-cause/review stream—to interleave freely without artificial ordering constraints.

# 7. Preferred Representation and Validation Plan

### Preferred Representation Defense
The **POWL model** is selected as the canonical representation. POWL explicitly supports arbitrary partial-order edges, enabling direct encoding of non-block-structured cross-branch dependencies (such as `Design Corrective Action` and `Plan Verification` jointly preceding `Execute Trial`, and approvals synchronizing independently at release). Process Trees, being strictly block-structured, require artificial nesting and over-approximation to represent these patterns.

### Concrete Validation Plan
1. **Conversion to Petri Net**: Convert the POWL model (or its process tree counterpart) to an accepting Petri net using `pm4py.convert_to_petri_net(powl)`.
2. **Soundness Checking**: Verify structural and behavioral soundness of the converted net using `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`.
3. **Bounded Playout**: Generate sampled event traces via `pm4py.play_out(powl, num_traces=1000)` to inspect behavior under randomized execution.
4. **Positive and Negative Trace Tests**: Validate conformance against the eight behavioral witnesses in Section 5 using token-based replay or conformance checking.
5. **Silent Behavior Check**: Verify that invisible transitions ($\tau$) do not introduce live-locks or deadlocks during reachability analysis.
6. **Limitations of Validation Plan**: Token replay confirms control-flow admissibility but cannot validate unrepresented data-dependent conditions (e.g., exact numerical risk scores or actual inspection pass/fail values).

# 8. Final Self-Critique

1. **Semantic Weakness**: The POWL model abstracts the inspection outcome into a non-deterministic choice within the loop operator, meaning model checkers cannot natively evaluate convergence guarantees without explicit data predicates.
2. **Structural Weakness**: The synchronization of multiple incoming branches into `Release Material` relies entirely on structural graph edges in POWL, which can become visually complex and difficult to audit as the process expands.
3. **Approximation Weakness**: The Process Tree fallback model introduces significant over-approximation regarding cross-branch dependencies, meaning conformance analysis on the tree yields higher false-positive rates than the canonical POWL specification.
