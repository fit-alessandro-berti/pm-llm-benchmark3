# 1. Assumptions and notation

- A1. `Nominal` times are the rounded timestamps shown in the table. Because each endpoint was rounded to the nearest 5 minutes, any positive duration computed from two reported timestamps has an `actual` value in approximately `[nominal - 5 min, nominal + 5 min]`, truncated at 0 when needed.
- A2. For queue/WIP counting at a shared nominal timestamp, I use a post-event convention: completions free capacity first, then queue entries/arrivals occur, then eligible starts occur, and I report the state immediately after all events stamped at that nominal time. This avoids artificial spikes from simultaneous rounded events. Counts very near a tied timestamp can still move by about one case under a different tie-break because of rounding.
- A3. Observation window is `[2026-05-12 08:00, 2026-05-12 14:00)`. For endpoint reporting I also state the `14:00^-` state, meaning immediately before the censoring cutoff.
- A4. No hidden pre-08:00 work is assumed at S1 or S2, because no case is shown already in service or already queued at 08:00. If pre-window WIP existed but was omitted, early utilization would be understated.
- A5. S1 queue-entry time is `arrival_s1`. S2 queue-entry time is `s1_end`, because a case enters S2 as soon as S1 completes.
- A6. `MISSING` start means the activity definitely happened, resource and completion are known, but the start is unknown. I therefore bound the missing start by precedence, same-resource availability, nonnegative service, and the next known work on that resource.
- A7. I use three start-imputation scenarios for missing starts.
- A8. `Optimistic` means earliest feasible start: minimum queue wait, maximum service duration.
- A9. `Central` means pattern-based start: I choose starts that preserve the dominant observed service pattern when feasible. Here that gives P07 S1 start 09:30 and P15 S1 start 11:45 (both about 30 min S1 service), P05 S2 start 09:45 (about 30 min S2 service), and P11 S2 start 12:00 (about 25 min S2 service; shorter than usual but forced by C2 availability).
- A10. `Pessimistic` means latest feasible start: maximum queue wait, minimum service duration. This is a hard bound, not always a plausible physical realization, because it can imply nominal zero-minute service for some missing-start cases.
- A11. For `OPEN` activities I report elapsed service up to 14:00, not final service time. For cases still waiting, I report waiting lower bounds up to 14:00.
- A12. C2 availability is reduced by the stated outage from 10:55 through 11:10, so the S2 denominator for utilization is `360 + 345 = 705` resource-minutes rather than `720`.

Notation:

- `a_{c,1}` = S1 arrival of case `c`; `a_{c,2}` = S2 queue entry of case `c`.
- `b_{c,k}` = service start at station `k`.
- `e_{c,k}` = service end at station `k`; for open in-window elapsed quantities I substitute `T = 14:00`.
- `W^q_{c,k}` = queue waiting time.
- `W^s_{c,k}` = active service time.
- `W_{c,k}` = station sojourn time = waiting + service.
- `L_q(t)` = queue length, `B(t)` = in-service count, `L(t) = L_q(t) + B(t)` = total WIP.

# 2. Reconstruction method and formulas

- Case-level waiting at station `k` for a started case is `W^q_{c,k} = b_{c,k} - a_{c,k}`.
- Active service for a completed activity is `W^s_{c,k} = e_{c,k} - b_{c,k}`.
- Elapsed service for an open activity is `W^{s,elapsed}_{c,k} = T - b_{c,k}`.
- Station sojourn for a completed or open-started activity is `W_{c,k} = e_{c,k} - a_{c,k}` with `e_{c,k}=T` for elapsed open values.
- For a case still waiting at 14:00, only a lower bound is available: `W^q_{c,k} >= T - a_{c,k}` and `W_{c,k} >= T - a_{c,k}`.
- Completed-case total sojourn is `S_c = s2_end - arrival_s1`. For incomplete cases I report lower bounds `>= T - arrival_s1`.
- For any interval with both endpoints observed, rounding implies approximately `actual duration in [max(0, nominal - 5), nominal + 5]`. Missing-start ranges add a second layer of uncertainty beyond this basic rounding band.
- Station queue length under the post-event convention is `L_q(t) = count(c : a_{c,k} <= t < b_{c,k})`.
- In-service count is `B(t) = count(c : b_{c,k} <= t < e_{c,k})`.
- Total station WIP is `L(t) = count(c : a_{c,k} <= t < e_{c,k})`.
- Mean queue length or WIP over an interval `[u,v)` is the area under the piecewise-constant count process divided by `(v-u)`.
- Arrival rate over a subperiod is `lambda_in = arrivals / subperiod length`; departure or throughput rate is `lambda_out = completed services / subperiod length`.
- Resource utilization over the observation window is `busy time in window / available time in window`.

Lower, central, and upper estimates:

- Fully observed nonzero waits/services: nominal value with an implicit A1 band of about `+/- 5` minutes.
- Missing starts: optimistic, central, and pessimistic scenarios from A8-A10.
- Open cases: elapsed-service or waiting lower bounds only.
- Total WIP is more robust than queue/service split because missing starts change the split but not the fact that the case occupied the station between entry and completion/censoring.

Little's Law usage:

- I do not use the full 08:00-14:00 window because both stations are transient, S2 has an outage, and several cases are right-censored.
- I only use a short S1 queue interval with roughly stable backlog as a coarse check, and I treat any mismatch as expected boundary/transient error rather than a model failure.

# 5. Bottleneck and temporal interpretation

Evidence:

| nominal time | S1 queue | S1 total WIP | S2 queue | S2 total WIP | interpretation |
|---|---:|---:|---:|---:|---|
| 09:00 | about 3 | about 5 | about 1 | about 2 | S1 is already building backlog faster than S2. |
| 10:00 | about 6 | about 7 | about 2 | about 4 | Both stations have backlog, but S1 is still the larger visible queue. |
| 11:30 | about 7 | about 8 | about 3 | about 5 | S1 queue reaches its nominal peak. |
| 13:30 | about 1 | about 3 | about 4 | about 6 | Upstream largely drained; downstream backlog dominates. |
| 14:00^- | 1 | 2 | 4 | 6 | Most unfinished work is now in or ahead of S2. |

- Early window, S1 is the clearer bottleneck. External arrivals to S1 were `6.5/h` from 08:00-10:00 while S1 departures were only `3.0/h`, so S1 backlog had to grow sharply. That is exactly what the queue trajectory shows.
- Mid-window, S1 remains heavily loaded but stops worsening as quickly. From 10:00-11:10, S1 arrivals and departures are both `4.29/h`, so the large S1 queue mostly plateaus instead of exploding further.
- Late window, S2 becomes the active bottleneck. From 11:10-14:00, S1 arrivals fall to `1.41/h` while S1 departures stay near `3.18/h`, so S1 drains. Over the same interval S2 arrivals are `3.18/h` but S2 completions only `2.47/h`, so S2 accumulates more work.
- End-of-window evidence is strong: `14:00^-` leaves only `2` cases in S1 WIP but `6` in S2 WIP, of which `4` are still waiting. That pattern is not consistent with S1 being the sole bottleneck throughout.
- The service-time structure supports the same story. S1 services are usually `25-30` nominal minutes, whereas S2 services are usually `40-50`. With the same nominal two-resource staffing, S2 has lower effective capacity even before maintenance is considered.

Maintenance interval:

- C2 is unavailable from 10:55 through 11:10. The observed C2 schedule is consistent with that: P06 ends at 10:50 and P08 does not start until 11:15.
- During the outage slice 10:55-11:10, S2 receives `2` new arrivals but records only `1` completion, so the S2 queue must grow by at least one case in that slice.
- The outage is not the whole story. Even after 11:10, S2 continues receiving work faster than it finishes it, so the downstream backlog keeps growing. The outage is therefore an amplifier of an underlying capacity mismatch, not a complete explanation by itself.

Hypotheses consistent with the evidence:

- The process is not governed by one static bottleneck. It looks like an early upstream bottleneck at S1 caused by a burst of arrivals, followed by a downstream bottleneck at S2 caused by longer calibration times plus the C2 outage.
- P11's short feasible S2 service window and P05's relatively short feasible S2 service are more consistent with a mixture of real case heterogeneity, rounding compression, or slight logging imperfections than with a clean deterministic service regime.

Little's-Law check:

- A rough S1 queue check on 10:25-12:20 is defensible because the queue is large but roughly flat. Over that interval, mean S1 queue is about `5.87` cases, `7` starts occur in `115` minutes (`lambda ~= 3.65/h`), and the mean started-case S1 wait is about `85.7` minutes. Then `lambda * Wq ~= 5.22`, which is reasonably close to `5.87` given rounding, transients, and boundary effects.
- I would not trust the same check on the full window or on late S2, because those intervals are visibly nonstationary and strongly right-censored.

# 6. Missingness, censoring, and sensitivity analysis

| scenario | missing-start rule | main quantitative effect | conclusions that change | conclusions that do not change |
|---|---|---|---|---|
| Optimistic | Earliest feasible missing starts | S1 mean queue about `4.11`; S2 mean queue about `2.14`; S1 utilization about `84%`; S2 about `81%`. Queue waits are shortest and service times longest for missing-start cases. | Whole-window utilization ranking can look slightly more S1-heavy. | Early S1 buildup, late S2 backlog, S2 end-of-window dominance, and S2 peak queue near 5 all remain. |
| Central | Pattern-based missing starts | S1 mean queue about `4.14`; S2 mean queue about `2.14`; S1 utilization about `83%`; S2 about `81%`. | No major qualitative change. | Same bottleneck shift and same end-state interpretation. |
| Pessimistic | Latest feasible missing starts | S1 mean queue about `4.31`; S2 mean queue about `2.29`; S1 utilization about `74%`; S2 about `73%`. Queue waits are longest and some implied services become nominally zero. | Exact service-time averages for the missing-start cases become implausibly low, so this scenario is useful mainly as an upper bound on waiting. | S1 still peaks earlier, S2 still retains much more unfinished work by 14:00, and the overall story is still time-varying rather than single-bottleneck. |

Stable findings across scenarios:

- Missing starts materially affect the split between queue wait and active service for P05, P07, P11, and P15, but they do not change the total station occupancy interval for those cases.
- Therefore total WIP profiles are much more stable than queue/service decomposition. Mean WIP stays about `5.79` for S1 and `3.72` for S2 in all three scenarios, and the `14:00^-` states are unchanged.
- The downstream conclusion is robust: by the afternoon, S2 is the dominant unfinished-work location regardless of how the missing starts are placed.

Unstable or weakly identified findings:

- Whole-window average utilization ranking between S1 and S2 is not robust enough to support a single static bottleneck claim. The ranges overlap too much once missing starts and rounding are admitted.
- Exact average service time at S2 is sensitive to P05 and especially P11, because their feasible service windows are shorter than the modal `40-50` minute pattern.

Effect of right censoring:

- P15 and P17 understate final S2 service time because only elapsed service is known by 14:00.
- P21 understates final S1 service time for the same reason.
- P16, P18, P19, P20, and P22 understate final waiting and station sojourn because their next start is unobserved.
- These censored cases make late-window queue pressure look conservative, not exaggerated.

Effect of timestamp rounding:

- Individual fully observed waits/services can move by about `+/- 5` minutes.
- Queue and WIP counts near ties can move by about one case depending on actual intra-bucket ordering.
- Those perturbations are too small to overturn the larger temporal pattern: early S1 overload, later S2 overload.

# 7. Reproducible Python

The code below keeps `MISSING`, `OPEN`, and blank values distinct, builds a PM4Py-compatible interval-event DataFrame for usable observations, computes station-specific queue and WIP metrics with pandas under three scenarios, and uses PM4Py only on fully observed completed cases where its case-level semantics are defensible.

            "s2_end_eff": s2_end,
            "s2_resource": r.s2_resource,
            "state_at_14_00": r.state_at_14_00,
        })
    return pd.DataFrame(out)


def area_and_peak(intervals, window_start=OBS_START, window_end=OBS_END):
    events = []
    for start, end in intervals:
        if pd.isna(start) or pd.isna(end):
            continue
        s = max(start, window_start)
        e = min(end, window_end)
        if e <= s:
            continue
        events.append((s, 1))
        events.append((e, -1))
    # Post-event convention: departures before arrivals at identical rounded timestamps.
    events.sort(key=lambda x: (x[0], x[1]))
    cursor = window_start
    level = 0
    area = 0.0
    peak = 0
    for ts, delta in events:
        if ts > cursor:
            area += level * (ts - cursor).total_seconds() / 60.0
            cursor = ts
        level += delta
        peak = max(peak, level)
    if window_end > cursor:
        area += level * (window_end - cursor).total_seconds() / 60.0
    return area, peak


def station_metrics(station, scenario_name):
    scen_df = materialize_scenario(scenario_name)
    if station == "S1":
        queue_intervals = list(zip(scen_df["arrival_s1"], scen_df["s1_start_eff"].fillna(OBS_END)))
        service_df = scen_df[scen_df["s1_start_eff"].notna()].copy()
        service_intervals = list(zip(service_df["s1_start_eff"], service_df["s1_end_eff"]))
        wip_intervals = list(zip(scen_df["arrival_s1"], scen_df["s1_end_eff"].fillna(OBS_END)))
        started = service_df.copy()
        started["wait_min"] = (started["s1_start_eff"] - started["arrival_s1"]).dt.total_seconds() / 60.0
        started["service_in_window_min"] = (started["s1_end_eff"] - started["s1_start_eff"]).dt.total_seconds() / 60.0
        arrivals = len(scen_df)
        completions = int(df["s1_end_status"].isin(["OPEN", "BLANK"]).eq(False).sum())
        available_capacity = 2 * 360.0
    else:
        eligible = scen_df[scen_df["s2_entry_eff"].notna()].copy()
        queue_intervals = list(zip(eligible["s2_entry_eff"], eligible["s2_start_eff"].fillna(OBS_END)))
        service_df = eligible[eligible["s2_start_eff"].notna()].copy()
        service_intervals = list(zip(service_df["s2_start_eff"], service_df["s2_end_eff"]))
        wip_intervals = list(zip(eligible["s2_entry_eff"], eligible["s2_end_eff"].fillna(OBS_END)))
        started = service_df.copy()
        started["wait_min"] = (started["s2_start_eff"] - started["s2_entry_eff"]).dt.total_seconds() / 60.0
        started["service_in_window_min"] = (started["s2_end_eff"] - started["s2_start_eff"]).dt.total_seconds() / 60.0
        arrivals = len(eligible)
        completions = int(df["s2_end_status"].isin(["OPEN", "BLANK"]).eq(False).sum())
        available_capacity = 360.0 + 345.0  # C1 full window + C2 reduced by the outage

    q_area, q_peak = area_and_peak(queue_intervals)
    s_area, s_peak = area_and_peak(service_intervals)
    w_area, w_peak = area_and_peak(wip_intervals)

    return {
        "station": station,
        "scenario": scenario_name,
        "arrivals_to_station": arrivals,
        "completed_services_by_14": completions,
        "mean_wait_started_min": round(started["wait_min"].mean(), 2),
        "median_wait_started_min": round(started["wait_min"].median(), 2),
        "mean_service_in_window_min": round(started["service_in_window_min"].mean(), 2),
        "mean_queue_len": round(q_area / 360.0, 3),
        "peak_queue_len": int(q_peak),
        "mean_service_wip": round(s_area / 360.0, 3),
        "peak_in_service": int(s_peak),
        "mean_total_wip": round(w_area / 360.0, 3),
        "peak_total_wip": int(w_peak),
        "busy_minutes_in_window": round(s_area, 1),
        "utilization_of_available_capacity": round(s_area / available_capacity, 3),
    }


summary = pd.DataFrame(
    [station_metrics(station, scenario)
     for station in ["S1", "S2"]
     for scenario in ["optimistic", "central", "pessimistic"]]
)
print("\nSCENARIO_SUMMARY")
