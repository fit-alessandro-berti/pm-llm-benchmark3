## 1. Modeling assumptions

The object types are exactly Order, Item, Package, Delivery, Invoice, and Payment, with that capitalization. The object identifiers are globally unique across all types.

The E2O qualifier vocabulary is role-oriented:

- created: the event creates the object.
- item_added_to and added: the order-side and item-side roles of an Add Item event.
- operational_order: an order explicitly involved in a shared operational event.
- reserved: an item reserved by a stock-reservation event.
- packed and packed_into: the package-side and item-side roles of packing.
- dispatched and dispatch_delivery: the package-side and delivery-side roles of dispatch.
- issued and billed_order: the invoice-side and order-side roles of invoice issuance.
- recorded_payment and settlement_target: the payment-side and invoice-side roles of payment recording.
- confirmed: a confirmed delivery.
- closed: a closed order.

For O2O relations, ocel:oid is the source and ocel:oid_2 is the target. Thus, Order contains Item, Package packs Item, Delivery carries Package, Invoice bills Order, and Payment partially settles Invoice. The relation qualifiers are directed and use the verb associated with that direction.

The source E2O policy is deliberately conservative but not empty. It records all explicit event/object roles in the narrative. In particular, the shared Reserve Stock event directly touches O100, O200, I1, and I3, and the P1 packing event directly touches both Orders, P1, I1, and I3 because the narrative explicitly says that it relates to both Orders. The P2 packing event directly touches P2 and I2; the O100 connection is available through the O100–I2 O2O relation, but is not asserted as a source-system E2O fact. Dispatch events directly touch their Package and Delivery, confirmation touches Delivery, invoice issuance touches V1 and both Orders, and payments touch their Payment and V1. No payment amount is allocated directly to either Order because the narrative supplies no allocation.

Analytical propagation is kept separate from source facts. The relations table below contains only the chosen direct E2O rows. If a downstream analysis derives, for example, a D1-to-Order or Payment-to-Order connection through O2O closure, it should be placed in a separate derived table or marked with a provenance value such as derived_o2o_closure; it should not be silently appended to the source relation table.

The pipeline assumes the stated constructor signature, OCEL(events=events, objects=objects, relations=relations, o2o=o2o), and the named PM4Py discovery functions. In a PM4Py release with a different OCEL import or constructor signature, only the import/constructor adapter should change; the four DataFrames and their semantics should remain unchanged.

## 3. Data-model audit

The object inventory is:

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

The O2O vocabulary and observed cardinalities are:

| Qualifier | Direction | Rows | Cardinality in this dataset |
|---|---|---:|---|
| contains | Order → Item | 3 | one Order to many Items; O100 has 2 and O200 has 1 |
| packs | Package → Item | 3 | one Package to many Items; P1 has 2 and P2 has 1 |
| carries | Delivery → Package | 2 | one-to-one here |
| bills | Invoice → Order | 2 | V1 to many Orders |
| partially_settles | Payment → Invoice | 2 | many Payments to one Invoice |

The activity/object-type incidence is:

| Activity | Object types touched |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Order, Item |
| Pack Package | Order, Package, Item |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery |
| Close Order | Order |

The most consequential event is e007, Pack Package for P1: it is one event connected to O100, O200, I1, I3, and P1, so it makes the cross-order package convergence explicit. e006 similarly synchronizes the two Orders through joint stock reservation. e011 makes the shared invoice V1 a convergence point for O100 and O200, while e012 and e015 make M1 and M2 converge on V1. Conversely, e008 is intentionally only directly linked to P2 and I2; reaching O100 from it requires the O100–I2 O2O fact rather than a source E2O row.

## 4. Expected flattened behavior

For an Order flattening, O100 should be approximately:

Create Order → Add Item → Add Item → Reserve Stock → Pack Package → Issue Invoice → Close Order.

O200 should be approximately:

Create Order → Add Item → Reserve Stock → Pack Package → Issue Invoice → Close Order.

The shared events e006, e007, and e011 are copied into both Order cases. The O100 case has both Add Item events, whereas O200 has only the I3 Add Item event. The direct-source policy omits P2 packing from the O100 case because e008 has no direct O100 E2O row; it also omits dispatch, delivery confirmation, and both payments. Likely aggregate DFG edges include Create Order → Add Item, Add Item → Add Item, Add Item → Reserve Stock, Reserve Stock → Pack Package, Pack Package → Issue Invoice, and Issue Invoice → Close Order, with the two-item O100 trace supplying the repeated Add Item edge. A misleading interpretation is that each Order independently reserved and packed its own work and was invoiced independently. In reality, P1 and V1 are shared, and the flattened cases duplicate the same source events.

For a Package flattening, P1 is approximately:

Pack Package → Dispatch Package.

P2 has the same activity shape. P1's two item links and its cross-order meaning are not represented as a sequence, and the Package cases omit Order creation, item addition, stock reservation, delivery confirmation, invoice issuance, payments, and order closure. The likely DFG has Pack Package → Dispatch Package. This can misleadingly suggest two independent package workflows and conceal that P1 combines I1 from O100 with I3 from O200.

For a Delivery flattening, D1 is approximately:

Dispatch Package → Confirm Delivery.

D2 has the same shape. The delivery cases do not contain the package's Pack Package event because the packing event is directly linked to P1 or P2 rather than to D1 or D2. They also omit the carried package's items and Orders, as well as invoice and payment events. The likely DFG has Dispatch Package → Confirm Delivery. This can make delivery performance appear self-contained and makes the D1-to-P1-to-I1/I3-to-Orders lineage invisible in the flattened trace.

For an Invoice flattening, V1 is approximately:

Issue Invoice → Record Payment → Record Payment.

The two Record Payment events are e012 and e015, with event attributes 100 and 150 respectively. V1's case omits the two billed Orders, package and delivery lifecycles, and order closure. The likely DFG has Issue Invoice → Record Payment and Record Payment → Record Payment. It can misleadingly look like a generic invoice followed by two interchangeable payments; the object-centric model retains that the first payment is M1, the second is M2, and both target the same V1, but it still does not allocate either payment to O100 versus O200.

Flattening on Payment is particularly weak. M1 and M2 each have only one directly associated Record Payment event, so each Payment trace has length one and almost no control-flow information. The shared V1 relationship is a connection to a common object, not a useful lifecycle within either single-payment case. Payment flattening therefore hides the settlement sequence and cannot express the fact that the two payments jointly settle V1.

## 5. Expected object-centric structures

The OC-DFG should retain activity nodes together with object-aware connections rather than forcing every object type into a separate case. It should expose the shared Reserve Stock and Pack Package behavior, with e006 involving O100 and O200 and e007 connecting P1, I1, I3, O100, and O200. It should also retain the Issue Invoice event at the common V1 boundary and the two Record Payment events involving V1, M1, and M2. The close events remain distinct for O200 and O100. Exact edge weights and returned dictionary keys are PM4Py-version dependent, but the shared-object convergence is the important result.

The OTG should show the typed business structure: Orders connect to Items, Packages connect to Items, Deliveries connect to Packages, V1 connects to O100 and O200, and M1 and M2 connect to V1. Following the object graph through Items shows why P1 is special: P1 contains I1 and I3, and those Items belong to different Orders. Thus P1 is a cross-order bridge even though there is no direct Package-to-Order O2O row.

The ET–OT graph should summarize which event types touch which object types. Reserve Stock should have Order and Item incidences; Pack Package should have Package and Item incidences and also an Order incidence because e007 explicitly touches O100 and O200; Dispatch Package should have Package and Delivery incidences; Issue Invoice should have Invoice and Order incidences; and Record Payment should have Payment and Invoice incidences. It is an event-type/object-type view, so it may not preserve the fact that the P2 instance lacks a direct Order relation unless the returned structure retains instance-level detail.

The object-centric Petri net should represent several interacting typed lifecycles: Order creation, item addition, reservation, operational packing, invoicing, and closure; Package packing and dispatch; Delivery dispatch and confirmation; and Invoice payment. A shared transition or synchronized token pattern can be associated with the joint reservation of I1 and I3 and the P1 operation spanning O100 and O200. V1 provides a shared invoice-side point for both Orders, and M1 and M2 provide two payment-side interactions with that invoice. The discovered net is an algorithmic abstraction whose places, transition labels, and synchronization details depend on PM4Py discovery behavior; it does not have one uniquely determined business interpretation.

The object-interactions summary should identify strong interactions for Order–Item, Package–Item, Delivery–Package, Invoice–Order, and Payment–Invoice. It should also reveal event co-occurrence involving O100 and O200 at e006, e007, and e011; P1 with I1 and I3; V1 with O100 and O200 at issuance; and V1 with M1 and M2 at payment. Those interactions explain the cross-order convergence that the Order, Package, Delivery, and Invoice flattenings each partly hide.

## 6. Modeling alternatives

1. Source-minimal relations, used here. Record only explicit E2O roles and retain business lineage in O2O. This gives clean provenance and avoids asserting that a dispatch or payment was allocated to an Order when the source narrative did not say so. Flattened Order traces are shorter and omit some downstream events, but the object-centric structures make the paths available through O2O relationships.

2. Full operational involvement. Add direct context links to every operationally affected object. For example, e008 could also link to O100, e009 could link to O100, O200, I1, and I3 through P1, and e010 could link to O100 and I2. Delivery confirmations could carry the same order/item context. This makes Order flattenings more complete and increases direct DFG edges, but it inflates relation counts and may make every downstream event appear independently observed for every related Order and Item.

3. O2O-propagated analytical relations. Keep the source relations unchanged, compute an O2O closure, and create a separate analysis relation set. That set could propagate P1 to I1/I3 and then to O100/O200, D1 to P1 and its lineage, and M1/M2 through V1 to both Orders. This produces richer Order, Delivery, and Payment views and exposes end-to-end paths, but it changes the meaning of E2O rows from observed involvement to derived lineage. Provenance must be explicit, and derived rows should not be fed into source-fact discovery without qualification.

4. Explicit financial allocation. If the business supplies an allocation rule, add derived payment-to-Order context or allocation attributes, such as a per-Order allocated amount, while keeping the original 100 and 150 amounts on e012 and e015. This would make Order-level settlement analysis possible. Without such a rule, assigning M1 or M2 to O100 or O200 would invent a fact; the common V1 relationship is the defensible representation.

## 7. Failure modes

1. Relation inflation can result from linking every logistics event to every Order and Item reachable through O2O. It increases apparent activity frequency and can create spurious dependencies.

2. Missing direct E2O links can make an otherwise valid object appear to have an unnaturally short flattened trace. In this construction, omitting the P2-to-O100 direct link is intentional, but it must be documented.

3. Treating O2O propagation as observation confuses business lineage with what the source event actually recorded. A derived D1-to-O100 link should not be presented as a direct source relation.

4. Flattening shared events duplicates their case representation. e006, e007, and e011 appear in more than one Order case, so summing flattened event counts as if they were source-event counts is wrong.

5. Payment allocation is ambiguous. M1 and M2 both settle V1, but no amount is assigned to O100 or O200. A per-Order payment conclusion requires an additional allocation rule.

6. Payment traces are overly short. A Payment case contains only its single Record Payment event, so Payment flattening cannot discover a meaningful settlement lifecycle.

7. The OCEL constructor and PM4Py APIs are version-sensitive. Imports, constructor keyword names, flattening return types, visualization helpers, and OC Petri net return shapes may differ; silently changing the tables to fit an API would be a semantic error.

8. A naive implementation can impose a false total order on same-time events by sorting on an arbitrary identifier. This example has no timestamp ties, but a general pipeline should use a documented tie policy and should not infer causality from event IDs.

9. Naive timestamps can become timezone-naive or be localized inconsistently, causing incorrect ordering across events and invalid OCEL data.

10. Orphan event or object identifiers in relations, or activity/timestamp values copied by hand, break referential integrity and can cause PM4Py to drop or misinterpret rows.

11. Duplicate E2O or O2O rows can inflate interactions and discovery frequencies while looking like legitimate repeated business behavior.

12. Modeling the payment amount as an object would create spurious object identities and an incorrect process structure. The amount is an attribute of the Record Payment event.

13. Adding a direct O100 relation to e008 solely because O100 contains I2, without labeling it as derived or operational context, hides the difference between an observed relation and an inferred one.

14. Reading a discovered skeleton, DFG, or Petri net as a normative business specification overstates what the data supports, especially when shared events and sparse lifecycles are flattened or abstracted.
