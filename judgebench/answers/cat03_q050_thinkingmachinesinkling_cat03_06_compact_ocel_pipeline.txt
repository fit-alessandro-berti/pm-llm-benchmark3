## 1. Modeling assumptions

- **Object types (capitalized):** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.
- **E2O qualifier vocabulary:** `created_order`, `updated_order`, `added_item`, `reserved_item`, `shared_order`, `packed_package`, `included_item`, `source_order`, `dispatched_package`, `assigned_delivery`, `issued_invoice`, `billed_order`, `settled_invoice`, `recorded_payment`, `confirmed_delivery`, `closed_order`.
- **O2O direction conventions:** Source  Target (`ocel:oid`  `ocel:oid_2`) with the qualifier describing the semantic role. Example: `Order` `contains` `Item`.
- **Direct logistics/financial relations:** Logistics events relate directly to Orders only when operationally shared (`Reserve Stock`, `Pack Package` for P1). `Dispatch` and `Confirm` relate only to `Package`/`Delivery`. Financial events (`Issue Invoice`) relate directly to `Invoice` and `Order`. `Record Payment` relates only to `Invoice` and `Payment`—not to Orders—so that allocation ambiguity is not hidden in direct relations.
- **Preventing propagation confusion:** The `relations` table stores only source-system recorded pairs. Any OrderPayment link is left for analytical propagation (via `Invoice``Order` O2O) in discovery algorithms (`OTG`, `ET–OT`), not hard-coded as an E2O fact.
- **Version-dependent PM4Py assumption:** The pipeline uses `from pm4py.objects.ocel.obj import OCEL` and the constructor `OCEL(events=..., objects=..., relations=..., o2o=...)`. If the installed PM4Py version uses `pm4py.objects.ocel.importer.apply(...)` instead, isolate the constructor line and pass the same four DataFrames without altering semantics.

## 6. Modeling alternatives

1. **Source-minimal E2O:** Only record relations that the operational system explicitly wrote. Example: `Reserve Stock` relates only to `I1`/`I3` (not to `O100`/`O200`); `Pack Package` relates only to `P1`/`I1`/`I3` (not to orders). Discovery impact: `OTG` and `OC-DFG` still recover `Order` involvement via O2O (`contains`/`packs`), but direct interaction counts drop. The analyst must explicitly propagate via O2O to see convergence, which separates source facts from derived insights.

2. **Full operational involvement (relation inflation):** Every logistics event also gets direct E2O links to all upstream orders via O2O traversal at ingestion. Example: `Confirm Delivery` (`D1`) also links directly to `O100` and `O200` because `D1``P1`itemsorders. Discovery impact: The relations table doubles in size; `OC-DFG` becomes dense with redundant `Order``Delivery` edges; `interactions_summary` overstates direct event-object pairs; flattened logs become heavily duplicated.

3. **O2O-propagated analytical relations (derived layer):** Source `relations` remain minimal (alternative 1), but a derived `relations_derived` is computed before discovery by traversing O2O. Example: derive `M1``O100` and `M1``O200` via `M1``V1``bills`. Discovery impact: `OC-DFG` and interaction summaries become richer without polluting the source table. Analysts can compare `source` vs `derived` graphs to audit propagation assumptions—critical for avoiding the failure mode of treating derived links as observed facts.

## 7. Failure modes

1. **Relation inflation:** Adding propagated links directly into `relations` makes the table unnecessarily large and obscures which links are source-recorded.
2. **Missing direct E2O links:** If `e6` (Reserve Stock) omitted `O100`/`O200`, analysts might miss that the event is operationally shared across orders.
3. **Treating O2O propagation as observation:** Deriving `Payment``Order` links via `Invoice` and then reporting them as direct E2O facts misrepresents the data-generating process.
4. **Duplicate shared events after flattening:** `Reserve Stock` and `Pack Package` (P1) appear in both `O100` and `O200` traces, making frequency statistics misleading if summed naively.
5. **Ambiguous payment allocation:** If payments were linked directly to both orders, splitting `M1` (100) and `M2` (150) between `O100` and `O200` would require arbitrary allocation rules.
6. **Overly short Payment traces:** Flattening on `Payment` yields one-event traces (`Record Payment`), providing no causal or lifecycle context.
7. **Constructor/API version mismatch:** If `OCEL` is imported from a different module or requires `ocel_events`/`ocel_objects` parameter names, running `OCEL(events=...)` raises `TypeError`; isolating the constructor line allows quick adaptation without corrupting semantics.
8. **False total order for same-time events:** Although this dataset has no timestamp ties, if two events shared an identical timestamp, PM4Py flattening or skeleton algorithms might impose an arbitrary ordering, creating false `Directly Follows` edges (e.g., `Reserve Stock` before/after `Add Item`).
