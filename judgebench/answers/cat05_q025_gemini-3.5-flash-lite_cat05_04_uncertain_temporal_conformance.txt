## 1. Normalization Assumptions

### Interval Construction & Uncertainty Order
For every recorded timestamp $T_{\text{rec}}$ with resolution uncertainty interval $U_{\text{res}}$ and clock offset bound $U_{\text{clock}} = [a, b]$, the true time $T_{\text{true}}$ is bounded by:
$$T_{\text{true}} \in T_{\text{rec}} + U_{\text{res}} - U_{\text{clock}}$$
Where clock offset is defined as $\text{offset} = T_{\text{recorded}} - T_{\text{true}}$, meaning $T_{\text{true}} = T_{\text{rec}} - \text{offset}$. Thus, for an offset bound of $[a, b]$, the correction interval is $[-b, -a]$. 
**Order of operations:** Apply resolution uncertainty first to get the recorded event window, then apply the negative clock offset bounds.

### Display & Rounding Semantics
- **Exact to second (HUB):** $U_{\text{res}} = [0, 0]$ (displayed seconds).
- **Floor to minute (OPS-BER, VENDOR-NY, LEGACY-BER):** Displayed 10:14 means clock time in $[10:14:00, 10:14:59.999]$. Resolution uncertainty is $[0, 59.999]$ seconds.
- **Round to nearest 10 seconds (SENSOR):** Displayed time $\pm 5$ seconds. Resolution uncertainty is $[-5, +5]$ seconds. Completion event semantics mean the activity occurred at or before the timestamp, but our system bound applies to the recorded clock.
- **Round to nearest minute (MOBILE-LON):** Displayed time $\pm 30$ seconds.

### Time Zones & DST Folds
- **HUB, SENSOR:** UTC.
- **OPS-BER, LEGACY-BER:** Europe/Berlin (`UTC+1` Standard / `UTC+2` DST). CEST is `UTC+2`.
- **VENDOR-NY:** America/New_York (`UTC-5` Standard / `UTC-4` DST). EDT is `UTC-4`.
- **MOBILE-LON:** Europe/London (`UTC+0` Standard / `UTC+1` DST). BST is `UTC+1`.
- **LEGACY-BER DST Fold (2025-10-26):** Local times from 02:00 through 02:59 occur twice (once in CEST, once in CET). Per instructions, this creates two disjoint UTC intervals for every recorded timestamp in this range, which must be preserved unless ruled out by strict ingestion sequences.

### Mobile Entry Delay (T-406)
The user-entered timestamp from MOBILE-LON has an entry delay of up to 5 minutes ([0, 300 seconds] added to the recorded user time) *in addition* to the source clock bound (`[-300, +300]`). This entry delay shifts both the recorded time and our occurrence time estimate forward by up to 5 minutes, widening the overall uncertainty interval by adding $[0, 300\text{ s}]$ to the upper bound.

### Inferred Activities & Causal Constraints
- **T-404:** `Investigation_Start` is missing. Work record states investigation duration was $[18, 25]$ minutes ($[1080, 1500]$ seconds). We derive `Investigation_Start` by subtracting this duration range from `Investigation_Complete`.
- **T-405:** Ingestion sequence (`Alert_Received` $\to$ `Investigation_Start` $\to$ `Containment_Complete`) eliminates invalid DST-fold permutations where chronological order is inverted.
- **T-407:** `Alert_Received` is missing. Network delivery latency from `Alert_Sent` is $[0, 20]$ minutes ($[0, 1200]$ seconds). Causal assumption: receipt cannot be after investigation start.

def normalize_timestamp(row):
    ts = pd.to_datetime(row["time:timestamp"])
    system = row["org:resource"]
    if system == "HUB":
        return [(ts, ts)]
    elif system == "OPS-BER":
        return [(ts - pd.Timedelta(hours=2) - pd.Timedelta(seconds=90), 
                 ts - pd.Timedelta(hours=2) + pd.Timedelta(seconds=120) + pd.Timedelta(seconds=59))]
    elif system == "VENDOR-NY":
        return [(ts + pd.Timedelta(hours=4) - pd.Timedelta(seconds=180), 
                 ts + pd.Timedelta(hours=4) + pd.Timedelta(seconds=180) + pd.Timedelta(seconds=59))]
    elif system == "SENSOR":
        return [(ts - pd.Timedelta(seconds=5), ts + pd.Timedelta(seconds=5))]
    return [(ts, ts)]

df["feasible_intervals"] = df.apply(normalize_timestamp, axis=1)

# 3. Midpoint-only event log (Lossy Approximation)
midpoint_rows = []
for _, row in df.iterrows():

    # Use midpoint of first interval as lossy point estimate

    midpoint_rows.append({

## 6. Evidential Sufficiency

To resolve `INDETERMINATE` or `POSSIBLE_VIOLATION` findings into `CERTAIN` classifications, the following minimum evidence is required:
1. **Stronger Synchronization Evidence:** For OPS-BER (e.g., T-409) and VENDOR-NY, replacing daily or missing NTP bounds with sub-second continuous NTP synchronization logs to narrow offset bounds from minutes down to seconds.
2. **Missing Activity Evidence:** For T-404 (`Investigation_Start`), actual system audit logs of user login/action rather than retrospective work record ranges. For T-407, direct receipt acknowledgment telemetry to bound `Alert_Received` precisely.
3. **Duration Evidence:** For T-405, server-side packet capture logs to disambiguate the DST fold.
4. **Semantic Evidence:** Clear operational policy definitions specifying whether user-entry delay (MOBILE-LON) is classified as a recording artifact or an actual operational delay.

## 7. Governance Recommendation

To eliminate ambiguities in incident-response timing, implement the following controls:
- **UTC Storage:** Enforce strict UTC ISO-8601 storage across all microservices, databases, and logging pipelines.
- **Raw Timestamp Retention:** Store original recorded strings, time zones, and raw device payloads alongside normalized UTC timestamps.
- **Source Offset Telemetry:** Mandate continuous NTP synchronization with bounded drift logs ($\le \pm 100\text{ ms}$) embedded in heartbeat headers.
- **Resolution Metadata:** Standardize log metadata to explicitly declare rounding semantics (floor, ceil, round) and precision bounds.
- **Start/Complete Semantics:** Define whether timestamps mark initiation, ongoing processing, or completion (e.g., SENSOR completion events).
- **DST Fold Handling:** Require all systems operating in DST-observing zones to log epoch timestamps or explicit fold identifiers (`fold=0` or `fold=1`).
- **Causal Identifiers:** Implement distributed tracing IDs (`W3C Trace Context`) across `Alert_Sent`, `Alert_Received`, and lifecycle events.
- **Enforcement Policy:** Adopt an *interval overlap policy* for legal SLAs—if an interval partially overlaps an SLA violation threshold, trigger an automated audit rather than assuming a default pass or violation.
