# 1. Assumptions and Interpretation

1. **Risk route.** The low-risk/high-risk condition is not represented as data. I model it as an exclusive control-flow choice:

   * low risk: `Supervisor Review`;
   * high risk: both `Quality Review` and `Regulatory Review`, concurrent and unordered.

2. **Supplier consultation.** `Consult Supplier` is modeled as an optional branch `X(tau, Consult Supplier)`. This enforces “at most once” and makes the supplier obligation explicit when selected. The data condition deciding whether it is selected is outside the model.

3. **Passing inspection.** Because inspection outcome is not an activity label, I use loop position as the abstraction:

   * every `Inspect Trial` followed by `Adjust Parameters` is interpreted as a failed inspection;
   * the final `Inspect Trial` before `Release Material` is interpreted as the passing inspection;
   * `Adjust Parameters` cannot occur after the final passing inspection.

4. **Duplicate visible labels.** I do **not** duplicate visible activity labels in either model. A duplication-based process tree could approximate more interleavings, but duplicated labels would make alignments, frequency counts, and conformance diagnostics ambiguous.

5. **Process-tree approximation policy.** I use a **conservative phase-join approximation**. The process tree preserves the hard safety constraints: registration first, plan after containment, design after root-cause analysis, trial after plan and design, approval/supplier/trial completion before release, and archive after release. It deliberately excludes some valid intended behavior, especially approvals or supplier consultation that complete immediately after root-cause analysis but before the plan/design work-product phase has joined.

6. **Concurrency interpretation.** “May overlap” is interpreted as true concurrency at the model level. Since the log records completion events only, the observed traces are linear extensions of concurrent behavior.

7. **Release synchronization.** `Release Material` is treated as a join over three obligations: trial loop completed with a passing final inspection, selected approval route completed, and supplier branch completed if selected.

8. **POWL exactness goal.** The POWL model is the canonical semantic model here because its partial-order edges can directly express the non-block-structured cross-branch dependencies.

# 3. PM4Py Process-Tree Model

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->('Analyze Root Cause', 'Design Corrective Action')
  ),
  +(
    X(
      'Supervisor Review',
      +('Quality Review', 'Regulatory Review')
    ),
    X(tau, 'Consult Supplier'),
    *(
      ->('Execute Trial', 'Inspect Trial'),
      'Adjust Parameters'
    )
  ),
  'Release Material',
  'Archive Case'
)
```

This expression maps as follows: the first parallel block creates the containment/planning stream and the analysis/design stream; the second parallel block runs the selected approval route, optional supplier branch, and trial loop before the release join. In PM4Py process-tree notation, `->`, `X`, `+`, `*`, and `tau` represent sequence, exclusive choice, parallelism, binary loop, and silent behavior; manual construction also requires explicit parent assignment for children. ([GitHub][1])

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    """Visible activity leaf."""
    return ProcessTree(label=label)


def tau_leaf():
    """Silent activity leaf."""
    return ProcessTree()


def op(operator, *children):
    """Create an operator node and explicitly attach children."""
    parent = ProcessTree(operator=operator)
    for child in children:
        child.parent = parent
        parent.children.append(child)
    return parent


# Trial loop:
# body = Execute Trial -> Inspect Trial
# redo = Adjust Parameters
trial_once = op(
    Operator.SEQUENCE,
    leaf("Execute Trial"),
    leaf("Inspect Trial"),
)

trial_loop = op(
    Operator.LOOP,
    trial_once,
    leaf("Adjust Parameters"),
)

# Risk route:
# low risk = Supervisor Review
# high risk = Quality Review || Regulatory Review
high_risk_reviews = op(
    Operator.PARALLEL,
    leaf("Quality Review"),
    leaf("Regulatory Review"),
)

risk_route = op(
    Operator.XOR,
    leaf("Supervisor Review"),
    high_risk_reviews,
)

# Optional supplier consultation.
supplier_optional = op(
    Operator.XOR,
    tau_leaf(),
    leaf("Consult Supplier"),
)

# Conservative work-product phase:
# Containment enables planning; analysis enables corrective-action design.
work_products = op(
    Operator.PARALLEL,
    op(
        Operator.SEQUENCE,
        leaf("Contain Material"),
        leaf("Plan Verification"),
    ),
    op(
        Operator.SEQUENCE,
        leaf("Analyze Root Cause"),
        leaf("Design Corrective Action"),
    ),
)

# Late obligations are allowed to overlap with each other, but only after
# the first phase has completed.
late_obligations = op(
    Operator.PARALLEL,
    risk_route,
    supplier_optional,
    trial_loop,
)

tree = op(
    Operator.SEQUENCE,
    leaf("Register Deviation"),
    work_products,
    late_obligations,
    leaf("Release Material"),
    leaf("Archive Case"),
)
```

The process tree does **not** represent the narrative exactly. Its main loss is the phase boundary between `work_products` and `late_obligations`. In the intended process, `Supervisor Review`, `Quality Review`, `Regulatory Review`, and `Consult Supplier` may start after `Analyze Root Cause` even while `Contain Material`, `Plan Verification`, or `Design Corrective Action` are still in progress. The tree postpones those obligations until both `Plan Verification` and `Design Corrective Action` are complete. This is a deliberate conservative under-approximation: it excludes some valid overlap but avoids admitting releases before the mandatory obligations are complete. It also cannot represent data-driven risk and supplier conditions except as visible control-flow alternatives.

# 4. PM4Py POWL Model

```text
Root SPO nodes:
  R  = Register Deviation
  C  = Contain Material
  A  = Analyze Root Cause
  P  = Plan Verification
  D  = Design Corrective Action
  Risk = XOR(
           Supervisor Review,
           SPO{Quality Review || Regulatory Review}
         )
  Supplier = XOR(tau, Consult Supplier)
  Trial = LOOP(
            SPO{Execute Trial -> Inspect Trial},
            Adjust Parameters
          )
  Rel = Release Material
  Z = Archive Case

Root order:
  R -> C
  R -> A
  C -> P
  A -> D
  A -> Risk
  A -> Supplier
  P -> Trial
  D -> Trial
  Trial -> Rel
  Risk -> Rel
  Supplier -> Rel
  Rel -> Z
```

POWL is a better fit because a `StrictPartialOrder` directly expresses precedence among submodels, and intentionally unconnected nodes remain concurrent. `OperatorPOWL` provides the XOR and LOOP constructs used below. ([GitHub][1])

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


# Atomic visible transitions.
register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")

supervisor_review = Transition(label="Supervisor Review")
quality_review = Transition(label="Quality Review")
regulatory_review = Transition(label="Regulatory Review")

consult_supplier = Transition(label="Consult Supplier")
skip_supplier = SilentTransition()

execute_trial = Transition(label="Execute Trial")
inspect_trial = Transition(label="Inspect Trial")
adjust_parameters = Transition(label="Adjust Parameters")

release = Transition(label="Release Material")
archive = Transition(label="Archive Case")


# High-risk review submodel:
# Quality Review and Regulatory Review are intentionally unordered.
high_risk_reviews = StrictPartialOrder(
    nodes=[quality_review, regulatory_review]
)

# Risk-route choice:
# low risk = Supervisor Review
# high risk = Quality Review || Regulatory Review
risk_route = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor_review, high_risk_reviews],
)


# Optional supplier branch:
# either no visible supplier consultation, or one Consult Supplier.
supplier_optional = OperatorPOWL(
    operator=Operator.XOR,
    children=[skip_supplier, consult_supplier],
)


# One trial iteration: Execute Trial must precede Inspect Trial.
trial_once = StrictPartialOrder(
    nodes=[execute_trial, inspect_trial]
)
trial_once.order.add_edge(execute_trial, inspect_trial)

# Repeat-until abstraction:
# Execute->Inspect happens once; after a failed inspection, Adjust Parameters
# occurs and another Execute->Inspect iteration follows.
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_once, adjust_parameters],
)


# Root partial order.
powl = StrictPartialOrder(
    nodes=[
        register,
        contain,
        analyze,
        plan,
        design,
        risk_route,
        supplier_optional,
        trial_loop,
        release,
        archive,
    ]
)

# Start dependencies.
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# Split dependencies.
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, risk_route)
powl.order.add_edge(analyze, supplier_optional)

# Trial prerequisites.
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# Release synchronization.
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(risk_route, release)
powl.order.add_edge(supplier_optional, release)

# Final archival step.
powl.order.add_edge(release, archive)
```

The intentionally unconnected nodes remain concurrent for specific reasons. `Contain Material` and `Analyze Root Cause` are unconnected after registration because the narrative says they may proceed independently. `Plan Verification` and `Design Corrective Action` are not ordered relative to each other because they depend on different predecessors. The risk route is not ordered against `Design Corrective Action`, `Plan Verification`, the supplier branch, or the trial loop except through its own prerequisite `Analyze Root Cause` and the release join, because approvals may overlap those activities. The supplier branch is similarly unconnected from design, planning, approvals, and trial work after root-cause analysis, because supplier consultation may overlap them but must finish before release. Inside the high-risk branch, `Quality Review` and `Regulatory Review` are unconnected so either completion order is allowed.

# 7. Preferred Representation and Validation Plan

The canonical representation should be the **POWL model**. It preserves the non-block-structured dependencies without duplicating labels or imposing an artificial phase boundary. The process tree remains useful as a conservative executable approximation, especially when downstream tooling requires a process tree, but it should not be treated as the authoritative semantics.

Validation plan:

1. **Convert to accepting Petri nets where supported.** Convert both models with `pm4py.convert_to_petri_net(model)`. PM4Py exposes conversion and playout APIs for process models including process trees and POWL in current documentation, but conversion success should be treated as a technical check, not as proof of semantic fidelity. ([GitHub][1])

2. **Soundness checking.** For each converted net, run:

   ```python
   net, im, fm = pm4py.convert_to_petri_net(powl)
   pm4py.check_soundness(net, im, fm, print_diagnostics=True)
   ```

   Repeat for `tree`. Inspect dead transitions, improper completion, and livelocks, especially around the optional supplier branch and trial loop.

3. **Bounded or sampled playout.** Use bounded or sampled playout to generate traces from both models. Because loops can generate infinitely many traces, cap the number of trial iterations during analysis. Compare generated traces against expected patterns:

   * no release before trial completion;
   * no release before selected approval completion;
   * no supplier consultation after release;
   * no `Adjust Parameters` unless followed by another trial iteration before release.

4. **Explicit positive trace tests.** Replay or align the five allowed witnesses from Section 5. The POWL model should accept all five. The process tree should accept A1, A2, A3, and A5, but reject A4 for the documented approximation reason.

5. **Explicit negative trace tests.** Replay or align F1, F2, and F3. Both models should reject them. F1 specifically tests the cross-branch dependency from `Plan Verification` and `Design Corrective Action` into the trial loop.

6. **Silent-behavior check.** Test traces with and without `Consult Supplier`. Confirm that the silent supplier branch permits no visible consultation but still synchronizes before release internally. Also verify that a trace with two `Consult Supplier` events is rejected.

7. **Duplicate-label check.** Programmatically inspect visible labels in the constructed model objects and assert uniqueness. This guards against accidental duplicate transitions if the tree or POWL is later refactored.

8. **Limitations.** Validation cannot prove equivalence to the narrative because the narrative contains data conditions, start-time overlap, and inspection outcomes that are not visible as event labels. Sampled playout is incomplete for loops. Petri-net conversion may also introduce silent transitions whose behavior must be inspected rather than assumed harmless.

# 8. Final Self-Critique

1. The process tree is intentionally conservative and therefore rejects some valid intended traces, especially early supplier or approval completions after root-cause analysis but before planning/design completion.

2. The loop abstraction treats the final `Inspect Trial` as passing purely from its position in the trace. Without an inspection-result attribute, the model cannot distinguish a truly passing inspection from an unrecorded failed inspection.

3. The POWL model is semantically closer, but it still abstracts from start timestamps. It represents concurrency as lack of ordering among completion events, which is weaker than proving that activities actually overlapped in real time.
