Construct an OCEL 2.0-style in-memory dataset from the natural-language process below and write one coherent PM4Py analysis pipeline.

The task has several defensible modeling choices. There is no hidden exact DataFrame layout beyond the mandatory OCEL columns and the stated business facts. Your answer will be evaluated on semantic consistency, referential integrity, code quality, and the quality of the expected analysis—not on reproducing one secret implementation.

PROCESS DESCRIPTION

A retailer processes two Orders, O100 and O200.

Objects:
- Orders: O100, O200
- Items: I1, I2, I3
- Packages: P1, P2
- Deliveries: D1, D2
- Invoice: V1
- Payments: M1, M2

Business relationships:
- O100 contains I1 and I2.
- O200 contains I3.
- P1 contains I1 and I3, so P1 combines items from two Orders.
- P2 contains I2.
- D1 carries P1.
- D2 carries P2.
- V1 bills both O100 and O200.
- M1 and M2 are partial payments settling V1.

Events:
1. 2026-04-06 08:00 UTC — Create Order for O100.
2. 2026-04-06 08:05 UTC — Add Item I1 to O100.
3. 2026-04-06 08:06 UTC — Add Item I2 to O100.
4. 2026-04-06 08:10 UTC — Create Order for O200.
5. 2026-04-06 08:12 UTC — Add Item I3 to O200.
6. 2026-04-06 08:30 UTC — Reserve Stock jointly for I1 and I3. The event is operationally shared by O100 and O200.
7. 2026-04-06 09:00 UTC — Pack Package P1 with I1 and I3. The event relates to both Orders.
8. 2026-04-06 09:05 UTC — Pack Package P2 with I2.
9. 2026-04-06 10:00 UTC — Dispatch Package P1 in Delivery D1.
10. 2026-04-06 10:15 UTC — Dispatch Package P2 in Delivery D2.
11. 2026-04-06 11:00 UTC — Issue Invoice V1 for both Orders.
12. 2026-04-06 11:30 UTC — Record Payment M1 of 100 monetary units against V1.
13. 2026-04-06 13:00 UTC — Confirm Delivery D1.
14. 2026-04-07 09:00 UTC — Confirm Delivery D2.
15. 2026-04-07 10:00 UTC — Record Payment M2 of 150 monetary units against V1.
16. 2026-04-07 10:30 UTC — Close Order O200.
17. 2026-04-07 10:35 UTC — Close Order O100.

MODELING REQUIREMENTS

- Use pandas DataFrames named `events`, `objects`, `relations`, and `o2o`.
- `events` must contain at least `ocel:eid`, `ocel:activity`, and `ocel:timestamp`.
- `objects` must contain at least `ocel:oid` and `ocel:type`.
- `relations` must contain at least `ocel:eid`, `ocel:activity`, `ocel:timestamp`, `ocel:oid`, `ocel:type`, and `ocel:qualifier`.
- `o2o` must contain `ocel:oid`, `ocel:oid_2`, and `ocel:qualifier`.
- Use timezone-aware timestamps.
- Give every event a unique event identifier.
- Keep event attributes, such as payment amount, in `events`; do not model an amount as a separate object.
- Use meaningful E2O qualifiers. You may choose them, but they must be consistent.
- You must decide how richly to relate downstream events to Orders and Items. Explain the trade-off between direct source relations and analytically propagated relations.
- Assume that a constructor of the form
  `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`
  is available. If a PM4Py version differs, isolate this line and explain the adjustment rather than changing the data semantics.
