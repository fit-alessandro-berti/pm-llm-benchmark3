## 1. Normalization Assumptions

I treat every recorded timestamp as an **interval of possible clock-display values first**, then apply the source-clock offset bound.

- **Clock-offset direction**:  
  `clock_offset = recorded_clock - true_clock`.  
  If the offset bound is `[lo, hi]` and the recorded-clock interval is `[r_start, r_end]`, then the true-time interval is:

  \[
  [r\_start - hi,\; r\_end - lo]
  \]

- **Resolution / display uncertainty is applied before offset correction**:
  - **HUB**: exact displayed second, plus measurement uncertainty `±0.5s`. Recorded interval is `t ± 0.5s`; offset `[-1s, +1s]` gives true interval `t ± 1.5s`.
  - **OPS-BER / VENDOR-NY / LEGACY-BER floor-to-minute**: displayed `HH:MM` means recorded clock in `[HH:MM:00, HH:MM:59.999]`. I use `[HH:MM:00, HH:MM+1:00)` for arithmetic.
  - **SENSOR round-to-nearest-10-seconds**: displayed `08:51:10` means recorded clock in `[08:51:05, 08:51:15)`, then offset `[-5s, +5s]`.
  - **MOBILE-LON round-to-nearest-minute**: displayed `13:14` means recorded clock in `[13:13:30, 13:14:30)`, before considering user-entry delay.

- **Time-zone conversion**:
  - 2026-06-01: `Europe/Berlin` is CEST (`UTC+2`), `America/New_York` is EDT (`UTC-4`), `Europe/London` is BST (`UTC+1`).
  - All final intervals are expressed in UTC.

- **DST fold for LEGACY-BER on 2025-10-26**:
  - Local times `02:00` through `02:59` are ambiguous: first fold is CEST (`UTC+2`), second fold is CET (`UTC+1`).
  - I generate both fold alternatives, then apply the ingestion-order constraint `Alert_Received <= Investigation_Start <= Containment_Complete`.
  - Under that order constraint, only one fold combination survives for T-405: Alert in the first fold, Investigation_Start and Containment_Complete in the second fold.
  - If the ingestion-order constraint is not accepted, the individual event intervals remain disjoint fold unions; I preserve those in the notes.

- **T-404 inferred Investigation_Start**:
  - `Investigation_Start` is inferred from `Investigation_Complete - investigation_duration`.
  - The signed duration bound `[18, 25]` minutes is retained as an interval constraint; no midpoint substitution is used.

- **T-407 Alert_Received**:
  - `Alert_Sent` is not treated as definitionally identical to `Alert_Received`.
  - Primary conditional inference: `Alert_Received  Alert_Sent + [0, 20]` minutes, and for duration testing I consider only ordered pairs with receipt no later than `Investigation_Start`.
  - If that semantic/causal assumption is not accepted, T-407’s receipt-dependent tests should be treated as **INDETERMINATE**; I flag this explicitly.

- **Mobile user-entry delay for T-406**:
  - I assume the up-to-five-minute entry delay reflects uncertainty about the **occurrence time**, not merely the record-creation time.
  - Therefore, the occurrence-clock interval is shifted earlier by up to 300 seconds before clock-offset correction.
  - Alternative assumption: if the delay is purely administrative and the entered display time was observed at occurrence, the interval would be 5 minutes later at the lower bound. I note this sensitivity qualitatively; the primary interval is the more conservative occurrence-time interpretation.

- **Ordering / eventually-following semantics**:
  - For duration tests, I compute feasible durations from pairs where the later activity is not before the earlier activity.
  - If clock uncertainty permits reverse ordering, I do not claim a certain pass; the result is at least a possible violation or indeterminate depending on semantics.

- **Baseline temporal-profile zeta**:
  - The main findings table uses `zeta = 2` as the baseline statistical tolerance.
  - Sensitivity analysis evaluates `zeta = 1, 2, 3`.

- **SLA tolerance**:
  - Primary SLA classification uses the hard limits exactly.
  - Sensitivity analysis adds grace periods of 2 and 5 minutes.

        return None

    segs = seg_list(d)

    if all(s[1] <= limit for s in segs):

## 7. Governance Recommendation

I recommend interval-aware governance, not midpoint-based enforcement.

- **Store UTC and retain raw evidence**:
  - Store normalized UTC timestamps, but also retain raw local timestamps, display strings, time zone identifiers, and rounding semantics.
  - Retain measurement uncertainty and source-offset telemetry rather than only final timestamps.

- **Clock synchronization controls**:
  - Require continuous NTP or equivalent offset telemetry per source.
  - Preserve hour-level offset diagnostics; do not replace a missing hour with a generic engineering estimate without marking the evidence weak.
  - Define explicit maximum offset bounds by source and require periodic recalibration for OPS, sensor, mobile, vendor, and legacy systems.

- **Resolution metadata**:
  - Record whether each timestamp is exact to the second, floored to the minute, rounded to the nearest minute, or rounded to 10 seconds.
  - Forbid silent use of midpoints in enforcement; midpoints are only a secondary diagnostic approximation.

- **Start/complete and lifecycle semantics**:
  - Distinguish activity occurrence, recording, completion, receipt, and ingestion.
  - For sensors and work records, explicitly mark whether an event is a start, completion, sent message, received message, or log-ingestion event.
  - Require `Investigation_Start` to be logged directly instead of reconstructing it from completion minus a duration range where enforcement matters.

- **DST-fold handling**:
  - For zones with DST transitions, store either UTC or local time plus the DST fold indicator.
  - Treat unmarked ambiguous local times as unions, not exact points.
  - Preserve ingestion order separately from true occurrence order.

- **Causal identifiers and provenance**:
  - Link alerts, receipts, investigations, containment actions, and closure through stable causal identifiers.
  - Require receipt acknowledgments for external alerts before treating delivery latency as proof of receipt.
  - Record mobile entry mode: automatic versus user-entered, observed time versus entry time, and any manual delay.

- **Enforcement policy for uncertain intervals**:
  - Use certain violations for enforcement, sanctions, or formal noncompliance findings.
  - Use possible violations as triggers for targeted evidence collection, not as automatic penalties.
  - Use indeterminate results as data-quality findings requiring resubmission or stronger logging.
  - Define whether a grace tolerance is an adjudication policy or a change to the SLA; do not apply post hoc tolerances silently.

- **Temporal-profile governance**:
  - Keep the operational SLA separate from the statistical temporal profile. A case can violate expected duration behavior without violating a legal maximum, and vice versa.
  - Fix `zeta` by policy for monitoring alerts and separately document sensitivity to narrower or wider bands.
  - Do not claim that a midpoint-only process-mining diagnostic proves compliance when interval evidence remains ambiguous.
