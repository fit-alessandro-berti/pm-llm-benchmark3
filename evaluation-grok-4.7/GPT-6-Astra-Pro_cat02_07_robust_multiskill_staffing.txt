7.6

The capacity accounting is the strongest part of the answer and is largely right. Midpoint means (6.94, 26.30, 32.82, 38.50, 15.74), block loads, the 2,720.6 versus 2,490 regular and 2,670 overtime comparison, the 2,065–3,376 endpoint envelope, the U3 morning Ada/Farah coupling (about 107 versus 126 electrical base-minutes), and the U5 low-end load of about 2,613 against 2,190 are coherent and checkable. Multipliers are all at least 1, so the midpoint total is a real lower bound on resource-minutes. U2 renormalization is handled carefully, including the point that software load barely moves and that an absolute-volume reading is a different scenario. Assumptions are labeled, SLA time is arrival-to-validation, and the one-day cohort is not passed off as steady state.

The policy write-up and the recommendation are weaker than that arithmetic. Strict specialization assigns software only to Emil, so the morning has no software resource and ME/ES primary pools have an empty intersection. Parallel coordination is then charged even when the branches cannot overlap. That is a real coverage consequence of speed-only home queues, but it is also an unnecessarily weak specialist design: Chen’s morning software qualification is excluded by construction, so the horse-race overstates the cost of fixed queues. The hybrid ageing rule is oversold. A 120-minute credit against a 960-minute P2–P3 deadline gap almost never places a P3 ahead of a P2 who arrived the same day, so it does little to the starvation the text says it reduces. Reserve, overflow, and parallel-gain thresholds are stated precisely and then never varied. The lexicographic objective is not what the simulator computes: there is no CVaR and no squared utilization penalty, and the absolute U2 reading never enters the policy table. Worst-case P1 point estimates favor the hybrid (about 59% versus 52% and 44%), but the reported paired interval includes zero, while p95 delay favors pooling in five of six scenarios. Leading with the hybrid under that evidence is only weakly supported; the text’s own uncertainty section supports capacity first and pooling as the default routing rule.

Several implementation gaps sit between the prose and the code. Setup is reset to a full five minutes on resume, so a break during setup can repeat it. `idle_since` starts at 0 and is updated only on task completion, so Emil does not actually hold a reserve at 12:00. Preemption reorders a P1 already bound to that worker; it does not pull a P1 onto a busy faster resource, and the forecast ignores preemption. The outage path rewrites `queued_since` to minute 120, which drops outage wait out of the task-level queue metric. The published `main` prints seed means, SLA bootstraps, and delay percentiles; it does not compute the paired H−P interval given in the text. Artifact links do not match the relative paths the code writes. PM4Py use is conceptually strong—especially the warning that summed parallel service can make `@@waiting_time` negative, and that segment means are not task means—but those calls were not run, so the required demonstration is untested.

Section 9 is sound: instability under repeating demand, shadow dispatch, switchback rather than case-level randomization, and pre-registered P1 margins. The answer is well above a generic three-policy essay. It is not nearly flawless: the main numerical story is trustworthy, and the reported ranking is not.
