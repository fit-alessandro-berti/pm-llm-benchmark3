The case analysis is differentiated and mostly tracks control objective, timing, independence, and recoverability. It is not nearly flawless: one code path is unsafe, one timing conclusion is wrong, and the sufficiency test contradicts itself.

## Material defects

The PM4Py call does not do what the write-up claims. In current PM4Py, `filter_four_eyes_principle(...)` keeps cases that satisfy four-eyes unless `keep_violations=True`. The code treats the default result as the violation set, so completed same-user cases and the u12/u13 cases would be labeled in reverse. The version note discusses return type and column names, and it never mentions this polarity. That is the behavior that changes the evidence. The flags are also not a join: case facts are walked in a loop, and when the log has no settlement the code returns `"unknown"` and silently substitutes the narrative timing.

AP-201’s corrective-capacity claim is wrong on the facts given. Release is 08:06, settlement is 10:00, and audit is 09:00 the next day. That is about 25 hours after release and about 23 hours after settlement, so a rolling 24-hour recall clock measured from settlement is still open. The table states that audit was outside the recall window. “One business day” is also equated with 24 clock hours. Those are different tests, and the code hard-codes the same 24-hour proxy for ED-1.

The equivalence test is not stable. Section 2 counts review before irrevocable settlement as fully equivalent timing. Section 4 then says a post-release, pre-settlement manager action is not fully equivalent to a second releaser. Both statements are used to support the case grades. “Fully equivalent” also requires resistance to two-person collusion. Nominal FEP-1 fails under that same collusion, so the bar is stricter than the control being replaced and the category is poorly defined.

## Other inaccuracies

Section 5’s “control that breaks the causal chain” cell for AP-204 lists controls that did not break it: AV-2 cannot test the receipt, there is no manager, and audit finds the fabricated receipt only after loss. AP-202’s cell has the same drift.

AP-203 and AP-207 are graded `OBJECTIVE_MET` with high confidence and “none material” missing evidence. MG-4 still requires level L3 or above, and no level is in the record. AP-206’s manager approves at 13:04, before AV-2 at 13:05; that order is never examined. AP-206’s token time and AP-209’s missing payment-cell design are the planted ambiguities, and neither is classified `INDETERMINATE`. `OBJECTIVE_PARTIALLY_MET` is arguable, but it treats unresolved independence and an unresolved ED-1 precondition as partial success.

Section 1 mixes threat scenarios with control-failure modes. O2 credits AV-2 with preventing some collusive-beneficiary fraud, while the control definition says AV-2 does not detect collusion or show who controlled a compromised account. The RA-7 “collusion resistance” cell is filled with “Detective.” Residual risk and severity are never defined, yet the table uses Low, Moderate, Medium, High, and Critical. Several monitoring cutoffs, including 1%, 20 payments in 30 days, and 12 hours, are asserted without a baseline.

## What holds up

Same-user and distinct-user cases are not mapped mechanically: AP-203 and AP-207 can meet the objective under ED-1, AP-204 can fail despite two user IDs, and AP-205 is correctly `LOSS_PREVENTED_BEFORE_COMPLETION`. AP-202 and AP-208 are failed packages with the override, conflict, bank-change, outage, and recall facts in the right places. The post-release/pre-settlement manager action is explicitly hybrid, and expected loss is rejected as the only equivalence standard. Section 6 covers every requested monitoring signal and separates an alert from proof of misconduct.
