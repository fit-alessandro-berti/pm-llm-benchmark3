6.5

The case-level cleaning choices are mostly sound, but the decision tree is internally invalid and the ordering implementation contradicts both timestamps and the answer’s own admissible orders.

Section 2 handles the required pairs conservatively and correctly: merge only the reconciled scan (e03/e04) and the shared invoice (e11/e16); keep e05, e13, and e14; keep e06/e07 and e08/e09/e10 as distinct, with label refinement; treat e15 as an ERP summary. Counts of 15 events / 39 E2O relations, and 14 / 37 after an extra e06/e07 merge, follow from those choices. The `have_common_object` warning about e13/e14 is right, and the provenance schema and failure-mode list cover the required fields.

Section 1 does not. After “no reconciliation evidence,” the tree says “go to 6,” so summary events, harmonization collisions, and concurrent different-object events are never reached and fall into quarantine. That routing cannot produce the later decisions.

Section 3’s tie discussion is better than the code. The prose allows e13 and e14 in either order and treats within-source sequence as non-causal. The implementation then adds hard same-source `source_seq` edges, forcing e13 before e14, and runs one global topological sort with a source-system rank. That sort has no earlier-timestamp-before-later-timestamp edges, so Create Order can be placed after pick, pack, and release. Stable fallback is described as canonical eid but implemented as source rank. e08 before e09 is also stated as source semantics when it is only a logistics inference.

The PM4Py block calls `ocel_drop_duplicates` on the full raw log while calling that scope an exact-duplicate no-op, which is the failure mode the answer itself warns against. Refined labels stay in `refined_activity` and are not written to `ocel:activity`, so discovery still sees the collided labels. `DataFrame.at` on missing provenance columns will raise. The sensitivity claim that merging the picks creates an I1–I2 OTG link is wrong: e06 already relates I1 and I2. The aggressive retained count is only a 10–12 range, and OC-DFG “per clean order” is not what that metric is.
