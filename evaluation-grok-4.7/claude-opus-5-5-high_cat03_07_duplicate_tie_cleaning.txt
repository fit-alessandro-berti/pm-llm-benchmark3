7.8

The design is careful and mostly right: the decision tree separates the six cases, the dangerous merges are refused, and the main counts are internally consistent (conservative 15/39, evidence-based 13/35, activity-timestamp merge 10/28, relation-level drop 28 E2O). Provenance, the microseconds warning, and the point that `have_common_object=True` still merges e13 with e14 are all sound. It is not nearly flawless.

The load-bearing ordering claim is stronger than the facts. R3 treats Issue Invoice as the creation of V1 and therefore forces e16* before authorization. Nothing in the source facts says that. It is also the only rule that produces e16* → e12 → e13 → e14 → e15′. The canonical row is e16, whose `ingested_at` is 12:00:04, so the stated R5/R6 tie-break without R3 yields e12 → e13 → e14 → e16* → e15′. Calling Capture→Issue Invoice a “fake” loop treats an assumption as a finding. e11’s ingestion time (12:00:01) sits on the other side of the payments, so the direction is an artifact of which duplicate survives.

`materialize_order` sorts only on per-group `tie_rank`, which restarts at 0 for every timestamp, so row order is not chronological. `order_ts_bounded` has the right construction and is then ignored; `order_ts` follows `ocel_add_index_based_timedelta` on that scrambled frame. Small deltas probably save cross-group timestamp values, but the code breaks the invariant it states. `tie_decided_by` labels the last node of a tie as `constraint` after a tie-break has already removed the alternatives.

PM4Py behavior is slightly over-specified. Unique (activity, timestamp, object) rows are 28 regardless of order, but “12 events, dropping e04, e07, e09, e15, and e16, and stripping O1/P1 from e05” is keep-first under eid order, not a property of the function. On this log a union-find reading of `have_common_object=True` still yields the same 10 events; “10 to 12” is an unexplained range. Differing `payload_hash` values are excluded from conflict logging, and the authority maps name attributes that are not columns. The prose says every relabel is a provenance row; `refine_labels` only writes event columns. Q2 both “retains unchanged” and “quarantines” when identity evidence disagrees.

Event decisions for e03/e04, e03/e05, e08/e09, e13/e14, and the N:1 treatment of e15 are the right conservative calls, and the sensitivity patterns are largely real. Those merits do not cancel an ordering story and an implementation that disagree with the rules used to justify them.
