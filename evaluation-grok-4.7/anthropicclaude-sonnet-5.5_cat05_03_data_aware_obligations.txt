The case outcomes are largely right, and the temporal reconstruction is careful. The score is held down by formalization overreach, a few soft or inconsistent classifications, and code that does not fully implement the rules it states.

**Case reasoning.** TX-301, TX-303, TX-304, TX-306, TX-307, TX-308, TX-309, and TX-311 are correctly decided, including the inclusive EUR 100,000 line, the strict >20% test against the reviewed amount, DE un-triggering R1, and the TX-311 tie (ER sees US; release state is DE; the opposite order does not change the verdict). TX-302 as COMPLIANT is the better reading, because the 09:20 Enhanced_Review already meets R1 and EX-77 is only corroboration. TX-305 as INDETERMINATE is defensible. TX-310 as NONCOMPLIANT is a defended choice, but the evidence is contradictory rather than simply absent, so INDETERMINATE is at least as faithful to the “no canonical answer” instruction. Medium confidence does not remove that. Section 4 then undercuts TX-305 by leaning “probably compliant in form,” which is a second classification wearing a hedge.

**Formalization.** The rule table and the strict `≺` order are clear, and three-valued triggers are done correctly (DE is false even if amount is unknown; amount < 100,000 is false even if jurisdiction is unknown). Two rules are widened without textual support. R4 invalidates a review only for an amount increase of more than 20% and only for amount-dependent obligations. Folding risk→HIGH and customer→PEP into R1 freshness would condemn a still-valid amount review. Those facts belong to R2’s “relevant” Enhanced_Review, which the code partly separates (`ER_fresh_attr`) and then recombines (`MC_ER_seq` includes `attr_mat`). R3’s “no screen at all = violation” adds an initial-screening duty the rule does not state: the trigger is addition after the latest screen. `≼` is used for evidence and effective time but never defined, despite the promise to define every temporal relation. The R3 snapshot fixes “current jurisdiction” at release and does not say what happens if jurisdiction at the list update differs. TX-304’s “Satisfied obligations” cell lists the screen that R3 says is stale. R4 is named as triggered for TX-301 and omitted for TX-309. “+56%” is 56.25%.

**Code.** The implementation is the strongest part: forward-fill only on state-setting events, sanctions jurisdiction and settlement amount kept out of case state, `event_index` reimposed after `format_dataframe`, integer-safe `new * 5 > baseline * 6`, release state via shift, and settlement used only as a labeled sensitivity column. That matches the hard cases that are actually in the log. It still encodes the R1 overbreadth above. Exemption validity is not computed from evidence time; `STRONG` / `DISPUTED` are typed in by hand, so TX-310 becomes `REVIEW_REQUIRED` while the narrative says NONCOMPLIANT. That split is permitted, but it means the executable path does not reach the stated verdict. `format_dataframe` is called correctly and the DECLARE mismatch examples (TX-309, TX-304, TX-302/308/311) are the right ones.

**Sections 6 and 7.** The nine failure modes are distinct and tied to cases, and the logging recommendations cover payload, the four timestamps, rule version, scope, provenance, and ordering. Those sections do not compensate for the rule-boundary and classification issues above.
