The component formulas in §1 are the right skeleton (upstream, per-branch queue and service, `join_ready = max` of branch ends, sync slack, downstream gap, final service, flow time as `final_end − arrival`). Almost everything built on those formulas is unreliable, internally contradictory, or both.

**Double-counting is stated backwards.** Summing sync waits does not count `fork_release → join_ready` three times. Sync wait is only `join_ready − end_i`. The identity that triple-counts is `queue_i + service_i + sync_i = join_ready − fork_release` for every branch, so the sum over A, B, and C is three copies of the fork–join interval. §1 then asserts that fork–join elapsed “equals the sum of branch queue times, service times, and synchronization waits,” which is exactly that triple count, and it also folds downstream queueing into the fork–join interval after defining fork–join as ending at `join_ready`. The non-overlap equation and the sum-across-branches claim cannot both be true.

**The case table does not match the log.** A is the only branch that always starts at `fork_release` (queue 0, service 50). B queues are 5, 20, 20, 10, 25, 30, 30, 5, 25, 20, 10, 30 (mean about 19). C queues are material (notably 35, 25, 15, 10). The table sets every queue to 0. Final service is 20 on every case; the table reports 45–52. Recomputed flow times are 93, 115, 120, 115, 110, 120, 130, 110, 120, 115, 110, 125. The table’s 87/100/110/… series matches neither those spans nor its own components (F01’s 15+50+8+52 cannot be 87). Critical branch and `join_ready`: F04 is C at 09:52, F06 is B at 10:30, F07 is B at 10:55, F11 is A at 11:30. The table marks F04 and F11 as B and F06 as C, and often uses A’s end as the join. Frequency is A 2, B 8, C 2, with no ties. §3 says A 1, B 7, C 4, which also disagrees with the table (that table is closer to A 1, B 9, C 2).

**Worked cases override correct arithmetic with the wrong table.** F02’s A interval is 08:25–09:15 = 50, not 08:10–09:15, and 10:00−08:05 is 115, not 55 or 100; the write-up then borrows 12:00−09:50 from another case and blames the log. F04’s narrative actually gets C, 09:52, queue 35, downstream 18, and service 20, then replaces the flow time with the table’s 100. F07’s narrative gets join 10:55 and downstream 15, then keeps the table’s 10:30 and downstream 40. The same split happens for F11 (narrative A, table B). Hour subtraction is repeatedly short by 60 minutes.

**Aggregates and counterfactuals inherit those errors.** B’s mean service 37.5 matches the log (sum 450) but not the table (F01 is 40, so the printed column sums to 440). C’s mean is about 20.2, not 21.5 from an unexplained 258. Mean sync is not “negligible / 0 / variable”: roughly 11, 4.3, and 30 for A, B, and C. B is still the dominant critical branch, so the headline ranking is directionally defensible, but the margins that actually move `join_ready` (B often by 10–25 minutes; A and C only by 5–10) are never computed, and A vs C is a frequency tie the write-up does not report.

Cutting A service 20% can move the join only on F01 (by 5, until B at 08:55) and F11 (by 10). The §4 “2 minutes on F01 only” figure is unsupported, and F11 is omitted. Halving B queue is not a null intervention: mean B queue is about 19, and on several B-critical cases half of that is inside the lead over the runner-up. The code does not implement a 50% cut; it subtracts one minute and can start B before the fork. Adding capacity is modeled as “halve every downstream number,” using downstream values the log does not have (F07 is 15, not 40; F08 is 15, not 35).

**Downstream masking is visible in the resource column and is missed.** F1/F2 already exist. F05, F09, and F11 start exactly when the previous F1 case ends; F08 starts exactly when F06 ends. On those cases an earlier join only lengthens downstream wait until the join passes the resource-free time, so branch speed-up need not change flow time. Other cases still wait about 8–15 minutes after both the join and the resource are free, so that residual may be policy or setup rather than occupancy. §4 treats capacity benefit as applying to “B-critical” cases and treats branch speed-up as if `final_end` moves with the branch. Those are different constraints.

**§5 names two plausible levers (B elapsed time, final-station capacity) and then attaches the wrong mechanism.** It cites F07’s downstream 40→20 as the tail effect of faster B service, says B “starts at the fork,” and alternates between “a second station” and “F3” on a process that already has F1 and F2. Synchronization (the new critical branch after the lead is removed) and the split between B queue and B service are not designed or measured. The pilot (“5% for four weeks,” “simulate in PM4Py”) does not say which timestamp comparison would separate resource blocking from release lag.

**The Python block would not reproduce the prose and does not meet the PM4Py requirements.** Queue, service, join, downstream, and flow formulas in pandas are the right ones, and the second `critical_branch` rule is a deterministic A-then-B-then-C tie break. The first assignment is a broken line-continued expression that throws before any print. `fork_join_elapsed` sums all three branches. Counterfactuals 1 and 2 recompute joins but set flow time back to the original `final_end − arrival`, so printed savings are zero. Counterfactual 3 rebuilds flow from the triple-counted fork–join, so the “benefit” has the wrong magnitude and the wrong sign relative to a real capacity change. There is no `pm4py.format_dataframe`. The interval frame uses minute integers and `timestamp_start`/`timestamp_end`, not `start_timestamp` and `time:timestamp`. `convert_log_to_time_intervals` is called once with placeholder keywords and once on a list the comment admits is not a real conversion. No code comment states that directly-follows performance does not recover synchronization slack. Per-case savings are not printed.

§7 does list the right non-identifications (cause, branch capacity, preemption, policy versus queue). It does not tie them to the pattern actually in this log: constant 20-minute final service, chained F1/F2 occupancy, and a residual wait after the resource is free.
