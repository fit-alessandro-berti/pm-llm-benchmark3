6.5

The design correctly separates duplicate classes and, on the important pairs, chooses the defensible action: merge the reconciled I1 scan (e03/e04) and the shared invoice issuance (e11/e16), keep the distinct I2 pick (e05) and the distinct M2 capture (e14), refine the dispatch harmonization collision (e08/e09), and keep the ERP pack and balance summaries (e07, e15) in the minimum-change path. Counts of 17, 15, and 14 events, and 44, 39, and 37 event-to-object rows, follow from those choices. The warning that `have_common_object=True` still merges e13 and e14 because they share O1 and V1 is right. The nine required sections are present and the failure-mode list matches the real risks.

The ordering story contradicts itself. Section 3 gives the 10:00 total orders e03 < e04 < e05 < e06 < e07 and, after the verified merge, e03* < e05 < e06 < e07. The stable key is written as `(timestamp, stage_rank, source_priority, source_seq, source_event_key, eid)`, but `source_priority` is never defined, so that sequence is not derivable from the stated rules. The implementation sorts on the raw `source` string. Alphabetically SCANNER precedes WMS, which yields e04 < e05 < e03 before the merge and e05 < e03* after it. The scanner sequence that actually supports e04 before e05 (551 < 552) is then discarded: `merge_verified_pair` keeps the WMS `source_seq` of 100 and stores 551 only as a conflict.

Several constraints are firmer in the pipeline than in the evidence. Fact 5 establishes only e09 < e10. e08 < e09 is an inference, yet it is encoded as a hard stage rank and called a strong semantic order. Invoice-before-authorization is correctly labeled soft, because authorization can precede invoicing, and failure mode 10 warns against forcing it. `stage_rank` forces it anyway, and also forces M1’s authorization (e12) before M2’s capture (e14), which no stated rule requires. Section 3.3 prints one chain, e11* < e12 < e13 < e14 < e15, without marking which links are domain constraints, which are within-source sequence, and which are only tie-breaks.

The merge helper does not implement the stated policy. Section 2 specifies a namespaced union, both payload hashes, and source-specific authority (ERP versus billing on e11/e16). The code keeps the survivor’s value on every conflict, never creates `merged_from` or namespaced columns, and the audit record omits `source`, `source_event_key`, and per-attribute lineage. That is the attribute-loss failure the later section describes. `activity_refined` is also never copied into `activity`, so a PM4Py directly-follows graph on the conservative object still sees `Dispatch Package` and `Capture Payment`. The sensitivity claims that those edges become `Release from Warehouse → Carrier Acceptance` and `Pack Package → Pack Status Update (ERP)` therefore describe a dataset the code does not produce.

The pre-check groups by `(timestamp, activity, obj_sig)`. Identical signatures surface e03/e04 and e08/e09; different discriminating objects mean e03/e05 and e13/e14 produce no candidate row. The prose says the check covers `(timestamp, activity)` or `(timestamp, obj_sig)`. `ocel_drop_duplicates` is guarded by a strict fingerprint and then called with no keys, so the library’s own duplicate definition is what would run. On a typical activity–timestamp–relation reading, that definition also collapses e08 and e09. `ingested_rank` casts to int64 before `fillna`, so an unparseable ingestion time becomes the smallest integer rather than a last-resort key. The e14/e15 row is shifted: the decision cell contains `Medium (0.60)`, and “same as above” blurs that e15 is one invoice-level summary of both payment messages, not a second pairwise duplicate of e14.

Section 8 lists the right provenance fields, but reversibility is not closed. Retained attributes plus conflicts do not rebuild values that agreed, the code never writes `attribute_lineage`, and no pre-merge event-to-object snapshot or relation delta is actually stored. An analyst still needs the untouched raw object, which the copy discipline does preserve.

Conceptually this is a careful cleaning argument. As a deterministic, PM4Py-aware pipeline it does not carry out the order, the label refinement, or the attribute-authority rules it states.
