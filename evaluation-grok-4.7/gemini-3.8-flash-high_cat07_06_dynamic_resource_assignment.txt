5.5

The write-up is complete and readable, and several continuity calls are sound (C002, C007, C008, C011, C016). It still fails as an auditable policy because the queue result breaks its own hard rules, then certifies that result as compliant.

The decisive error is C015. R5_Eva’s Security score is 0. Constraint 6 allows Security Review only at skill 3, or at skill 1–2 under R7_Gita or R8_Hugo. Skill 0 is ineligible even with a supervisor. R10_Jonas is also Security 0. The note naming Eva/Jonas does not override that gate. The Stage 2 filter correctly drops skill 0, yet section 3 assigns Eva and states that Constraints 3 and 6 are satisfied. That is a false compliance claim on a regulated activity.

The training result is also wrong. Normal/low work is 9 cases, so the 20% floor is 2. The only assignment that matches a documented training priority and the skill rules is C009 (Amal, Diagnosis, skill 1). C015 is illegal. C010 gives Jonas Approval preparation, but his training priority is Security, not Approval. The claimed 3/9 (33%) is 1/9. Section 3’s “quota exceeded” check does not hold. The same matrix makes several stated priorities impossible under the gates (Eva/Jonas Security at 0; David/Hugo Approval at 0). The policy never says so.

The algorithm and the table diverge elsewhere. Stage 2 drops every high-overtime resource on non-urgent work, but C003 (normal, 18h, medium handover, complexity 0.66) is kept with R4_David. Constraint 5 does not force that: handover is medium, and R3_Celine is Diagnosis skill 3 with low overtime. Calling overtime protection “100%” is a relabeling of retention as “not new work,” not compliance. `compute_utility_score` is never defined, no scores are shown, and batching only sets a flag, so the table is not produced by the stated procedure.

The scoring spec is not executable. `CostBand(c)` is added as a number though it is categorical. Workload uses undefined `max_shift_hours` and `max_open_cases`. The diagram’s urgency index uses undefined `EstServiceTime`; the code uses a different formula. Weights `W_*` never appear in the point scheme. Overtime is both a hard skip and a −60 penalty. The “only if no safer alternative” exception is not implemented: every urgent case may still hit a high-overtime resource. Tie-breaks and `handle_assignment_exception` are stubs. “Greedy / Hungarian” names two different solvers; the code is greedy only.

Section 4 calls the policy “Optimal,” “Lowest,” and “Maximum Resilience,” which conflicts with the requested trade-off stance. Specialist-only is misstated: Approval skill 3 is only R6_Farid, not R2_Bruno (skill 2, tied with Eva). Baselines are not actually allocated, so throughput and SLA claims stay rhetorical. Resilience is oversold while R8_Hugo, a scarce Security specialist, also absorbs C014 rework.

The worker note overpromises. Normal/low skill 1 may be solo in the code, but workers are told they are “always” mentored and that 20% training is guaranteed. The audit set covers the requested indicators, yet indicator 8 requires supervision the policy does not, the >2 reassignment target ignores C007’s existing count of 3, and appeals are named but not measured.

The PM4Py sketch mentions the right families (handover, working-together, similarity, roles, batches, service/waiting, performance DFG, SNA save) but does not use `filter_event_attribute_values`, `filter_case_performance`, or `get_service_time`, despite importing an unused attribute filter. The overtime check treats `workload_snapshot` as the literal `'overtime_risk_high'`. The Security check matches two names and a reason string, not skill. `insert_case_service_waiting_time` is applied as if it returned a log with `case_waiting_time` / `case_service_time`. “Production-ready” is not earned.
