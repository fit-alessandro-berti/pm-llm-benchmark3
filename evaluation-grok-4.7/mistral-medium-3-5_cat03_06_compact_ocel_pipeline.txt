The pipeline skeleton, object inventory, O2O facts, and activity-to-type audit are largely in place, but the write-up contradicts its own relations, and several core process-mining claims are wrong.

The data construction covers all 17 events, all 12 objects, timezone-aware timestamps, payment amounts on events, and the required structural links (order–item, package–item, delivery–package, invoice–order, payment–invoice). Referential integrity of those tables is mostly sound, and Reserve Stock / Pack P1 are attached to both orders. Section 3’s tables match that code.

That model is not what the later sections analyze. Section 1 says logistics events relate to orders and items and that invoice and payment events relate to orders. In the relations table, Dispatch and Confirm touch only package/delivery or delivery, and Record Payment touches only the payment and V1. Section 1 also says only source observations are stored, while treating order links on payments as direct facts. Those are propagated through “V1 bills both orders,” which the same section says it will not do.

Section 4 then describes traces the relations cannot produce. Standard flattening keeps an event only when that object type appears in E2O. Order traces therefore contain Create, Add, Reserve, Pack, Issue, and Close. They do not contain Dispatch, Confirm, or either payment. O100 and O200 are also different: O100 has two Add Item events and both packs; O200 has one add and only the P1 pack. I2 never participates in Reserve Stock. The single blended order trace, including `Dispatch → Issue → Payment → Payment → Confirm`, matches neither object and is not even global time order (M1 is before Confirm D1; M2 is after Confirm D2). Package traces are Pack → Dispatch only. Confirm Delivery is not related to P1 or P2, so the predicted package edge Dispatch → Confirm is unsupported. Invoice flattening is the view that does put both payments on V1; the claim that this trace cannot show that both payments settle the same invoice reverses what that flattening shows. It also misses Record Payment → Record Payment.

Those false traces are repeated as reviewer checks and as a failure mode: check 9 and failure mode 5 say order flattening includes M1 and M2. On this code, that check fails. The consequential-event discussion calls Reserve Stock the enabler of “divergence” in packing. Event 6 is convergence. The stronger convergence is event 7 (and event 11 for the two orders). Divergence here is one object with repeated activities, such as O100’s two packs and V1’s two payments.

Section 5 mixes graph levels. An OC-DFG is per object type and would not contain the order path they list, nor make P1 a hub. An OTG relates types, so it cannot show that P1, unlike P2, bridges O100 and O200. ET–OT is about activity types: Pack Package touches three types (Order, Item, Package), not four, and event E7 is not a node. The object-centric Petri net is described as one determined token game in which Add Item consumes the order, Pack consumes the order, and a V1 place has arcs to the object identifiers O100, O200, M1, and M2. That consumes the order before Issue and Close, treats tokens as arc endpoints, and presents one interpretation as the expected net. The interaction summary undercounts P1 (D1 co-occurs at dispatch) and understates O100 (shared events also reach I3, O200, P1, P2, and V1).

The validation join is executable-looking and then fails on correct data. `events.amount` is null except on eids 12 and 15, the merge brings that column through, and `isna().sum().sum() == 0` fires on those nulls. Activity and object-type frequencies go through `ocel_get_activity_frequency` and `ocel_get_object_type_frequency`, which are not the required API and are not defended as version-specific. The import note points at `pm4py.objects.ocel.OCEL` rather than the usual `pm4py.objects.ocel.obj.OCEL`. Qualifiers are consistent verbs, but the same word is used for every participant, so order, item, and package roles are not distinguished. Both payments use `partially_settles`, which fits “partial payments” with no invoice total. Alternative 2’s pack relations are already the implemented model, and alternative 3 claims the same discovery results while also saying the extra links exist only at query time.
