**7.4**

The design is coherent and, on the main traps, right: it does not drop e05 or e14, does not treat equal activity and timestamp as identity, keeps e08/e09 and e06/e07 apart in the conservative path, preserves original timestamps, and correctly shows why `have_common_object=True` still merges e13 with e14. Event and E2O counts (17/44, 15/39, 14/37, 10/28) check out. It is not nearly flawless. Several required sections contradict each other or their own rules.

The decision tree does not generate the table. It is first-match, and Q3 fires on any difference in Item or Payment before the summary test. e06’s items are {I1, I2} and e07’s are empty; e13 has M1 and e15 has no Payment. The author’s own pre-check flags those sets as different, which routes both pairs to T5 (retain unchanged). Section 2 then labels them T3a and T3b. “Differ” is never defined as conflict versus subset, so the two required summary pairs have no unique terminal.

Ordering is internally inconsistent. Rule 2 makes same-source sequence semantic when a lifecycle object is shared. e04 and e05 share P1, with scanner sequence 551 then 552, so the merged I1 pick must stay before e05. The pipeline keeps the WMS row as canonical and never transfers that edge, then calls e05 → e03 → e06 → e07 admissible. That reverse order is not admissible under the stated rule. Ingestion only happens to put e03 first because the canonical row has `ingested_at` 10:00:01. `order_basis` is per event, so both picks are marked `constraint` because each precedes pack, even though their mutual order is fallback. That is the false precision the microseconds discussion warns against. Assumption edges are also forced: the reason field on `HARD_EDGES` is discarded, so “e08 before e09” is implemented as a fact. Rule 2’s type list excludes Invoice, so it would not produce e11 < e15; that edge exists only as a hardcoded exception.

One ordering claim is simply false. Unmerged ingestion order at 12:00 is e11, e12, e13, e14, e16, e15. e16 does not follow e11. In table order, timestamp order, and this fallback, Issue Invoice is not a directly-follows self-loop. Section 7’s “five spurious self-loops,” including Issue Invoice → Issue Invoice, treats same activity as adjacency. The other four loops are real; that one is not. “M1 is Authorize → Capture in every dataset except aggressive” overstates the aggressive case: M1 still has that edge; what changes is that the capture also carries M2.

The conservative attribute policy is not what the code does. Fact 6 and the e11/e16 row require a per-attribute authority split. `merge_verified_pairs` keeps the canonical value and logs the rest. Section 9 then lists an authority map as the safeguard against losing source-authoritative attributes. Billing fields never land on the canonical event. Compatibility is also narrower than the tree: only Item and Payment are checked, so a Package or Delivery clash would still merge.

Smaller gaps add up. Q1 treats `source_seq` as an identity alternative. The prose quarantines cyclic tie groups; the code raises. The audit dict does not carry the section 8 schema. The index-timedelta view never resynchronizes relation timestamps. e09 → e10 → e08 is listed as admissible once the release assumption is dropped, without keeping the weaker constraint that warehouse release still precedes handover.

The PM4Py sketch is otherwise careful: raw data are copied, exact-duplicate dropping is subset-scoped, verified merges are separate from `ocel_merge_duplicates`, and the synthetic clock is isolated. Those merits do not remove the contradictions in the decision tree, the lost scanner order, or the incorrect invoice self-loop.
