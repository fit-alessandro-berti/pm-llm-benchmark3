3.5

The write-up keeps the required outline and reaches the right coarse verdicts (P1/P3 differ; P2 can coincide after abstraction), but the operational semantics are wrong in the places that decide equivalence, so the traces, code, and metrics do not support those verdicts.

Loop semantics are mishandled despite the problem stating that the first loop child runs at least once. Model A’s body is `+(Analyze, Check)` then `X(Approve, tau)`, so every complete trace has at least one Check per Analyze iteration. The table’s “0 / unbounded” minimum is false, and it contradicts the later P2 claim: if A could omit Check and B could not, collapsing Check to a Boolean would separate the dashboard projections.

`+` inside A is ignored. “No concurrency inside A’s loop” and “A forbids Check before Analyze” are false; Analyze and Check are shuffled, and both must finish before Approve/tau and before Rework or loop exit. B has exactly one Check, concurrent with the whole loop, including after Approve and after the loop has otherwise finished. Approval placement is therefore not the same relative to Analyze.

The counterexample table fails the required two-and-two split:

- T1 (no Check) is in neither language.
- T2 is in B only (Check can trail the loop), not in A; membership is reversed.
- T3 is in both, because A’s parallel allows Check then Analyze, then hidden tau.
- T4 is the only correct witness (B not A): one Check cannot cover two A iterations.

No valid A-only trace is given. A minimal one is `Open, Analyze, Check, Approve, Rework, Analyze, Check, Close` (two Checks). Tau hides only the approval choice; it never deletes Check. That point is stated, but the listed traces do not use it correctly.

The Python does not implement A. The string `->(+'Analyze Revision','Check Revision',X(...))` is not `+(Analyze, Check)` sequenced before the XOR. Firing via `reachability_graph.execute(m, t)` is not the PM4Py semantics API (needs the net, and the usual argument order is transition, net, marking). Markings are put in a set with no hashable key. The search sketch does show the right bounds and does hide silent labels, but it is not a runnable exhaustive check.

Footprints are not identical. B has directly-follows pairs A lacks, notably Approve then Check. Equal footprints would be too weak anyway; a low EMD would also be too weak, but EMD 0 on a true trace metric would mean equal distributions. No footprint code is given, and the simplicity claim is an uncomputed number. Node counts are wrong: both trees have 12 nodes (6 visible leaves, 1 tau, 0 duplicate labels). Depth is about 5 for A and 6 for B, not 5 and 4. No counting procedure is shown.

The P2 tree is a reasonable reduction (8 nodes versus 12 and 12; Approve/tau removed; one Check beside `*(Analyze, Rework)`). It was not shown to be simpler by an explicit structural comparison. Preservation is not demonstrated: `(Open, Check, Analyze, Analyze, Close)` is listed as a regression trace that must be kept, yet this tree rejects it because Rework must sit between Analyzes. The two negative traces are valid. The closing warning treats non-equivalence beyond the bound as still open; one sound counterexample already refutes unbounded visible-trace equivalence, while P3 itself is exactly the bounded language, so an in-bound difference would prove P3 and not merely suggest it.
