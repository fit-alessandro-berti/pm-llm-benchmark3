6.5

The capacity arithmetic and the staffing diagnosis are largely sound. The comparison table and the required simulator are not. Those two pieces are what the decision is supposed to rest on, so they cap the grade.

**What holds up.** Mixture means (Intake 6.94, Mechanical 26.30, Electrical 32.82, Software 38.50, Validation 15.74), the 42-case mix, skill totals (about 2720.6 speed-1 minutes against 2490 paid minutes), the block presence map, and the exclusive speed-1 capacity table all check. U1’s 1.7 morning scaling, the proportional P1 shift, U2’s renormalized 12:00–16:00 shares, U3’s loss of Chen, and U4’s doubled diagnostic tails are applied correctly. The calendar reading is the right one: software is already tight on Emil at 16:00–18:00, mechanical eligibility is gone after 18:00, Farah leaves at 12:00, and Chen is the only speed-1 electrician from 08:00–10:00. O1 prices SLA shortfall and tail delay; O2 is a worst-scenario loss with a utilization spread. The prose policies name eligibility, reservation, preemption, parallelization, and overflow. The recommendation does not pick a winner from base-case mean delay, and it says routing cannot invent an evening mechanic. The PM4Py discussion correctly separates case-level waiting (sojourn minus interval time, including nights) from stage waits built off `queue_entry_ts`, and it treats overlapping ME/ES branches as joint work rather than a handover.

**Section 4 is not an estimate with a stated error model.** The method note calls the cells fluid-load judgment and, in the next sentence, calls the bands arrival/service Monte Carlo percentiles rather than model uncertainty. No run output is attached. The intervals are evenly rounded and keep the same policy order in every scenario. That overstates how precisely 0.92 is separated from 0.88, and from U5’s 0.76. The prompt allows qualitative ranges. It does not allow a stochastic percentile claim without a stochastic run.

**The program crashes before any policy metric exists.** `rng = random.Random(seed)` has no `poisson` method, and `generate_cases` calls `rng.poisson`. `capacity_report()` can print. The policy loop, the O1/O2 scores, the interval log, and the PM4Py calls do not execute. Numpy is imported and unused for sampling.

**The dispatcher that would run after that fix is a different policy from §3.** P-HY is specified as deadline order inside homes, Farah on Intake with cross-skill work only by trigger, P1 parallelization only if a second qualified resource is free or due within 10 minutes, and a P3 reservation on Emil/Deepa after 14:00 that also requires the partner to be idle or finishing within 10 minutes. The code scores P-HY with the pooling formula `Z`, puts Farah and Chen in the software home set, returns parallel for every P1 ME/ES, and drops the partner-idle test and the 85% utilization gate. P-SS prose parallelizes whenever both homes are idle and allows Deepa/Farah onto mechanical P1 only if both homes are busy; the code parallelizes only P1s and does not test home idleness. After 16:00 the evening rule says Deepa owns mechanical work. The code still treats Ada and Ben as the mechanical home, so a new P2/P3 mechanical case waits out the overflow timer while Deepa is the only person who can do it.

**Several mechanisms bias the metrics the code claims to report.**
- Preemption sets remaining work from multiplied resource time, and the next assignment multiplies by `m` again. The 10% restart is therefore applied to the wrong base.
- `busy_min` adds the full assignment at dispatch, then adds another slice if the job is preempted. Planned utilization is also multi-day busy time divided by one shift.
- Assumption A9 allows overtime to finish work already started. `advance_work` for non-P1 service is called with overtime disabled, so a job started at 15:50 stops at 16:00 and resumes the next morning.
- Service is logged from the first segment start to the last segment end, so breaks and overnight gaps sit inside the activity. `pm4py.get_service_time` would treat that idle time as service. Handover and setup are logged per segment; service is not.
- `handover_or_setup_burden` stays 0 unless `collect_log` is true, which is one seed of P-HY on the base day. The printed penalty column cannot support §4.
- The intake outage has no event at 10:00. If everyone is idle during 09:30–10:00, intake stays blocked until the next arrival. `t % 1440` also repeats that outage on later days; U5 is one outage.
- `idle_skill_ok` is true when one multi-skilled person can cover both branches. Both branches are then queued, `coord_pending` is set, and the 8 minutes are charged even if the branches never overlap. §1 says the 8 minutes apply only when the branches overlap, and that coordination is resource-free. The same section says parallel execution is more expensive in resource-minutes. Under a resource-free coordination rule, the two branches cost the same processing minutes either way; what changes is overlap, handover count, and contention.
- `Z = 1000·π + 2·slack + …` is not lexicographic. A priority gap of 2000 points is overtaken once slack differs by more than 1000 minutes. The code’s O1 also drops the prose term `0.01·E[(sojourn_P1−120)+]`.

**Smaller overstatements in the narrative.** The 231-minute gap is the expected load with tails included. Ordinary midpoints are about 2387 minutes, inside 2490 before multipliers and penalties. “Structurally over capacity” describes that mean, not a non-tail day. “Only fast morning electrician” is right for 08:00–10:00; Deepa is also at 1.00 from 10:00. Farah is qualified for all five activities. §5 says the hybrid plan stays within the 90% utilization cap; §4’s own base point estimate is 0.91 with a band to 0.97. The score uses the realized draw in `job.remaining`, while §6 says to score tabled mixture means. Service-time observability at dispatch is not listed as an assumption.

The hybrid-over-pooling-over-fixed-homes ranking, with an emergency mode and an explicit evening mechanical hole, is a coherent reading of the roster. It is not a result computed from the model in §8. Correct load definitions do not make the scenario table or the event-log analysis reproducible.
