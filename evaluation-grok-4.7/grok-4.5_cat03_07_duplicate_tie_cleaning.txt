6.8

The design is directionally strong: the decision tree separates the six duplicate types, the protected cases (e05, e14, e08 vs e09, e09 vs e10, abstraction-level e06/e07 and e15) are mostly handled correctly, ingestion time is not treated as business order, original timestamps are retained, and a total order is not claimed to be physical truth. The `have_common_object` trap on O1/V1 is explained correctly. Those merits do not offset the concrete defects below.

The conservative count of 15 (drop only e04 and e16) is arithmetically consistent, but it is not a minimum-change result. e11/e16 is rated only medium confidence on merge versus dual-retain, and the implementation’s `authority_attrs={}` does not apply the field-level authority map the table promises, so billing-authoritative attributes are not actually preserved. e03 before e05 is partly justified by “scanner/WMS `source_seq`,” which crosses source systems; `source_seq` is defined only within one source. After the merge, only the scanner order e04 (551) before e05 (552) is usable, and only as a transferred constraint.

Ordering overclaims uniqueness. e09→e10 is given. e08→e09 is not; equal timestamps plus different source meanings do not yield a unique semantic total. The rule text says invoice is “before/around” payment, then the partial order hard-wires e11*→e12, e11*→e13, and e11*→e14. That edge is an assumption, not a stated fact, and the admissible totals omit every interleaving in which authorization precedes the invoice.

Section 5 and the code disagree on the most sensitive event. Section 5 says e15 must not be folded into one of e13/e14 and should become invoice-level settlement attributes, with a retained count of 13–14. The evidence-based script merges e15 into e13 anyway. That attaches an invoice-level balance update to M1 only and leaves M2’s capture unrelated to the summary the prose itself calls ill-defined. The aggressive count “~10–12” is also loose: activity-plus-timestamp grouping, including under connected components with `have_common_object=True`, yields 10 events (e10 and e12 survive because their labels differ). A same-object-set predicate would yield 14, which is outside the stated band. e09/e10 are not fused by that library operation.

Sensitivity facts slip. After the conservative merges, Pick Item frequency is 2, not 1. Relation union does not make the I2 pick vanish; e05’s E2O rows move onto the surviving pick, so the damage is false convergence of I1 and I2, not a missing item event. The same union creates an OTG edge M1–M2 that no raw event supports. “OTG unchanged” is therefore wrong for the aggressive log. The table also says conservative durations come from original timestamps, while `ocel_add_index_based_timedelta` rewrites `ocel:timestamp`; default PM4Py performance then measures synthetic gaps. e10’s loss is discussed as if a standard duplicate merge could cause it; label inequality prevents that.

The Python block does not run. `verified_pair_merge` assigns `merge_provenance` through `.loc` on a column list that does not yet contain that column, which raises `KeyError`. Assigning `pd.Series(merged_attrs)` aligns on the row index, so a repaired column list can still write NaNs into the canonical event. `ocel_drop_duplicates` is called without a payload-hash restriction and its result is discarded. The aggressive sort is behind `if False`. `assign_deterministic_order` appends any eid missing from the hand list after the explicit prefix, which breaks timestamp order and does not implement the six-rule stack. Provenance JSON stores ids, sources, keys, and hashes, not full attribute images, discarded conflicts, or pre-merge relations, so the section 8 reconstruction procedure cannot be executed from what the code writes.

The audit schema and the failure-mode list are the most complete parts of the answer. They describe safeguards the pipeline does not enforce: no Payment-type equality check, no protected-eid assertion, and no check that the supplied total order respects e12→e13.
