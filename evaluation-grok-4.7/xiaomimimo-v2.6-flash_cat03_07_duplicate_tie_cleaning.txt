6.5

The design judgments are mostly right, but the ordering implementation, the e11/e16 code path, and several sensitivity numbers are wrong or internally inconsistent. That is too much error in the two criteria the task weights most heavily after the merge policy itself.

**What holds.** The decision tree separates exact duplicates, multi-system observations, summary/detail, harmonization collisions, true concurrency, and unresolved cases, and each terminal action is one of the allowed operations. The pair table covers every required pair. Keeping e05, e14, e06/e07, e08/e09, and e15, while merging only e03/e04 and e11/e16 in the conservative path, is the right conservatism. Headline sizes are right: 17/44 raw, 15/39 conservative, 14/37 evidence-based, 10/28 aggressive. The `have_common_object=True` explanation is correct: e13 and e14 share O1 and V1, so a non-empty intersection does not protect M1 vs M2. Within each tie group, the admissible orders match the stated facts (e06 before e07, e08 before e09 before e10, e12 before e13, e15 last, e13 vs e14 not causal). Provenance fields and the eight required failure modes are all specified. Microseconds-before-semantics is explained properly.

**Ordering code does not implement that policy.** `build_order_column` builds a graph only from `DOMAIN_RULES` and breaks ties by `source_seq`, source priority, ingestion, and eid. Timestamp is stored as `tie_group` and never used as a precedence constraint. On the conservative event set the initial ready set is e01, e02, e03, e05, e08, e11, sorted by `source_seq`, so e11 (seq 40) is emitted before e03 (100) and e08 (120). Invoice and payment events are interleaved ahead of picks and packing. `ocel_sort_by_additional_column` then `ocel_add_index_based_timedelta` would write that false order into timestamps — the failure the prose warns against. `source_seq` is also compared across sources, contradicting R3. `order_basis` is hardcoded to `"fallback"` for every event, so the claimed per-edge rule labels do not exist.

**e11/e16 is not actually merged under the stated policy.** Section 4 says transplant billing-authoritative attributes, record provenance, then drop. The code is `merge_verified_pair(...) if False else cons`, then `ocel_drop_duplicates` on the pair. The disabled call has an empty `attr_policy`. `apply_within` never writes `merged_source_eids`, `merge_rule`, or retained attributes. Dropping e16 therefore discards BILLING attributes and leaves no audit row, which violates the attribute policy in section 2 and safeguard 7 in section 9. The `assert dropped == ["e16"]` also depends on dataframe order, which the code does not fix.

**Scenarios are not independent.** The evidence-based log is built from `cons` after sort and `ocel_add_index_based_timedelta`. It inherits synthetic timestamps instead of branching from `ocel_raw`.

**Sensitivity analysis contradicts itself.** Order–Package support is given as 9/8/8/5, but P1 lifecycle length is 9/8/7/5. Every P1 event also has O1, so those rows must match; evidence-based is 7, not 8. Aggressive Order–Invoice is given as 4; after merging {e11,e16}, keeping e12, and merging {e13,e14,e15} it is 3. `Validate Order → Pick Item` is reported as 3→2→2→1. In a flattened directly-follows graph that edge occurs once whenever the picks are consecutive; 3/2/1 is the pick count, not the DFG frequency. That sits next to Pick→Pick, Pack→Pack, and Capture→Capture counts that are real directly-follows frequencies. Label refinement is also unresolved: if activity strings become `Pack Package (WMS detail)` and `Dispatch Package (warehouse release)`, the conservative self-loops counted in the table (4, including Pack and Dispatch) disappear and become cross-label edges. The text treats both readings as true.

**Smaller overclaims.** “Invoice V1 precedes every payment” and “warehouse release precedes carrier acceptance” are reasonable assumptions, not given facts (only e12 before e13, e09 before e10, and e15 after the payment messages are given). Both are encoded as hard domain/lifecycle edges with a single admissible 10:15 order.
