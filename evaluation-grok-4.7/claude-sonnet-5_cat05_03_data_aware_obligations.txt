The write-up reconstructs event-time state correctly for the determinate cases and is right on TX-301, TX-302, TX-303, TX-304, TX-306, TX-307, TX-308, TX-309, and TX-311. EX-77 versus EX-88, the standard-packet approval in TX-307, the exact €100,000 boundary in TX-308, the two >20% steps in TX-309, and the `event_index` order in TX-311 are handled carefully. The hard cases and the formal machinery are weaker than that narrative suggests.

TX-305 should not be closed as COMPLIANT. At release the amount is unknown, the review document contains no amount, and the next-day settlement figure is explicitly not an immutable release payload. R4 makes an increase from an unknown base unclassifiable, and R6 requires INDETERMINATE when the R1 trigger can neither be established nor excluded. The invariance claim (either the threshold is unmet, or the Enhanced_Review already satisfies it) fails in the high-amount branch: a review that never saw an amount does not establish a valid amount-dependent review, and materiality cannot be tested. Section 4 admits this and then still reports a binary verdict. TX-310’s NONCOMPLIANT label is a defensible burden-of-proof reading, but no case is classified INDETERMINATE in a log built around missing and contradictory evidence.

“Material data change” is not one predicate. Section 1 limits it to a >20% amount increase, the rule table adds jurisdiction, R1’s text is broader, and the code implements only a step-to-step amount test. R4 is cumulative against the amount at the review, not against the previous hop; two sub-20% hops that compound past 20% would be missed. Section 4 treats R2 as amount-dependent. R4 invalidates a review only for amount-dependent obligations; a ≥20% increase would break TX-306 through R1, not through R2.

The pseudo-logic does not define `MaterialChange`, takes `max` of a possibly empty set, leaves R1 with an unknown jurisdiction on no branch, and leaves R3 undefined when there is no earlier screen. R2 does not require the Enhanced_Review to post-date the risk or PEP change that makes it the relevant review. The R4 formula mixes a definition into a predicate.

The code matches the requested skeleton (inline CSV, `format_dataframe`, forward-fill, release snapshot, exemption join, no verdict lookup table) and would not leak TX-305’s settlement backward. It does not implement the rules it states. `NaN >= 100000` and `NaN == "HIGH"` are false, so the R6 branches inside `coarse_flag` are dead and an unknown trigger becomes `REVIEW_REQUIRED` rather than indeterminate. `scope_ok` is computed and never applied; customer type, `approved_by`, and waived-rule id are not checked. Review and change ordering stores timestamps only, so equal timestamps ignore `event_index`. `coarse_flag` returns on the first hit and can hide a second breach. The Petri-net discovery is not a conformance or DECLARE check against these obligations.

Temporal vocabulary and the clear-case table are strong. The score is held down by the TX-305 over-closure, the undefined materiality predicate, the R2/R4 mix-up, and checking code that misses unknowns, cumulative amount tests, exemption scope, and same-timestamp order.
