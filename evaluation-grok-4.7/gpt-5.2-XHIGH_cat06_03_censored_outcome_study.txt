7.4

The design correctly keeps `default_90d` defined only after activation, refuses to code rejects, withdrawals, and open cases as non-defaults, accounts for all 48,000 applications, and separates delayed feeds from competing terminals. The leakage table and the decision not to use a random split are sound. The remaining gaps are material.

The primary estimand \(\Pr(Y=1\mid X_{0:t_p},A=1)\) is coherent only if the scoring population is already activated. The chosen \(t_p\) is pre-decision, so \(A\) is still in the future, while Section 8 then authorizes limit-setting. That use applies a model fit on historically activated accounts to the approval frontier, which is the counterfactual the design says it will not claim. The joint \(\Pr(A=1,Y=1\mid X)\) is algebraically right and is not a default probability: a low value is often a low activation probability. Offering it for operational use without that warning blurs the estimand.

Censoring is named carefully, then handled with one IPCW model on \(p(\text{label observed}\mid t_a,\text{source},\text{channel},\text{region})\). Calendar immaturity is nearly deterministic, so recent activations produce extreme weights; eligible-but-missing feeds and not-yet-eligible windows need different treatments. IPCW also cannot represent partner accounts whose feeds never arrive, because there is no labeled mass to reweight. The MNAR bounds belong in the primary claim, not only as a side analysis. \(\Pr(A=1\mid X)\) is left unspecified for the 5,100 open cases; treating them as non-activation would bias that factor.

The cohort table collapses the 3,600 activated-but-unlabeled cases into one right-censoring / delay / missing-feed cell. Those mechanisms imply different estimators. Event time is also conflated with the 15 Feb 2026 extract: the stated event window ends 31 Dec 2025, but features, activation, and maturity all use the later extract date.

Validation prose is directionally right and then under-specified. There is no embargo of about 90+35 days, so training outcomes overlap the next fold. October–December 2025 is correctly reserved for drift in the text, while the code places every start after 30 Sep 2025 into `test` and never restricts metrics to `label_observed` and mature cases.

The skeleton follows the requested PM4Py path, drops the leaky columns, and truncates at the first stop event. It is not reliable as specified. `insert_case_service_waiting_time` is called with `case_id_key` and with the same column as start and end; `@@waiting_time` is then passed through `pd.to_timedelta`, which corrupts numeric seconds. `get_prefixes_from_log` at fixed length silently drops short traces, against the stated short-prefix rule. `terminal_state` uses a fixed priority rather than as-of time order. `grouper_freq` on the temporal extractor is an unsupported argument. Rework, queue, and label-maturity weights are described and not built.

Assumption labels are mostly honest. The design is usable only after the scoring time, the activation estimand, and the maturity filter are made the same object.
