4.5

The write-up keeps the right high-level refusal: rejected, withdrawn, transferred, and open cases are not coded as non-default, activation is treated as selection, the 48,000 rows are partitioned without an arithmetic gap, and validation is temporal rather than a random case split. Those choices do not make the design safe to follow. The estimand, the clock, the censoring rules, and the code disagree with each other, and several statistical claims are false.

The primary target is not operationally early warning. “Last event before Account Activated,” “last 5 events before activation,” and “first 5 events of traces that eventually contain activation” are three different prediction times. The first two are only known once activation has already happened, so they cannot be scores on the first events of every application. Conditioning the training sample on future activation also changes the prefix distribution relative to any deployment on still-open applications. That selection is never named. Calling \(P(\text{default}\mid\text{activated},\text{prefix})\) a “causal risk” is incorrect; it is a conditional predictive probability in the observed activation policy. The multi-state alternative is misspecified: default versus non-default is not a state of non-activated cases, transferred and still-open are omitted, and a descriptive competing-outcome model does not by itself require counterfactual default probabilities. The survival alternative’s limitation is also misstated. Non-informative censoring is not “censored cases are comparable to observed defaults.”

Cohort rules are not as-of rules. Extraction is 15 February 2026, the horizon is 90 days, and the feed lags by 7–35 days, so an activation on or after roughly mid-October 2025 is often immature. “Activated before 31 December 2025” does not encode that boundary, and excluding activations after 31 December 2025 is nearly vacuous because the event window already ends that day. The 3,600 immature or delayed activated accounts are included in the inclusion text, dropped from the primary cohort of 21,600, and then put back as Cox censoring in the next section. Still-open applications are labeled “no default observed.” Their default outcome is undefined until activation; they are censored for the process, not right-censored failure times. Permanent partner missingness is not separated from ordinary administrative immaturity. Transfer linkage and possible double-counting under a new identifier are absent from the cohort rules.

The missingness strategy conflates mechanisms that bias a default model in opposite directions. A binary label that has occurred but has not arrived is a missing outcome, not a censoring time. Censoring those 3,600 cases “at 90 days” is wrong in both directions: recent activations have been observed for far less than 90 days, and a delayed feed can hide a default that already occurred, which pulls survival estimates down. `label_available_at` is then described as a way to drop future prefix events, which it does not constrain, because it sits about 97–125 days after activation. Kaplan–Meier curves do not test independent censoring; that assumption is at most partially probeable. Policy stability is not an assumption to test: the threshold change on 1 July 2025 is given. Inverse-probability weighting is described with the wrong identifying assumption (“unobserved defaults are comparable”) and without a positivity warning for applicants who are almost never activated. The competing-risk sensitivity again treats undefined counterfactual default as if it were a subdistribution hazard.

Prefix handling would leak or destroy the process signal. Anchoring either a count or an elapsed window to activation uses the future. Padding short traces with null events invents activities; collapsing document loops before feature extraction erases the rework count later proposed as a feature; and the rename map is never actually applied. `pm4py.get_prefixes_from_log` returns the first \(k\) events, not the last \(k\) before activation, and it does not accept a `parameters` dict with a `filter` lambda. Traces are not cut at the prediction event, so Accepted, Contract Signed, and even activation can sit inside a short prefix. Same-day `documents_total` is classified as a static case attribute even though the audit later calls it a nightly snapshot.

The leakage table drops the worst fields, but the availability rules contradict the actions. `final_limit` and `decision_reason` are given a “timestamp at or before prefix end” rule and then dropped because they are supposedly never known then, which depends entirely on the unsettled prediction time. The same-day snapshot problem is not fixed by `<= prediction time`. `label_available_at` is marked Keep, with a use that would either do nothing or leak label existence. Feature examples fit an alpha miner, mislabel its Petri net as a DFG, and call `get_variants` a DFG feature, all on the untruncated log. Channel, region, migration date, and a hard feature timestamp cutoff are missing.

The split dates do not implement the stated stress test. Migration is 15 October 2025, while the test window starts 1 October, so it mixes pre- and post-migration. Training only on pre-policy starts estimates transport across a known break, not prospective performance under the new policy, and that distinction is not stated. The monthly backtest scores the next 30 days of activations on a 90-day endpoint with no 90-plus-delay embargo, which is impossible in real time and selects fast maturers if immature cases are simply dropped. The 20% censoring exclusion is arbitrary and itself biasing. AUC, Brier, and a concordance index are named without fixing the predicted quantity at day 90, without IPCW or another censoring-aware scoring rule, and without subgroup discrimination or calibration. The code then splits event rows by event time and calls those rows cases, so the temporal case-start split required for this study is not implemented.

Limitations correctly block unconditional default risk and a causal effect of loosening acceptance. They then claim the model can rank applications, which the conditional-on-activation estimand does not support. Of the three “deployment” effects, only intervening on activation changes the data-generating process. Policy drift and label lag are external. Missing are feature gaming, queue or staffing changes, and collection actions taken because of the score that alter subsequent default.

The skeleton does not implement the audit it describes. `pm4py.format_dataframe` is never called; columns are renamed away from the case/activity/timestamp fields the library expects. Case-level start, terminal activity, censor time, and label maturity as of a cutoff are not built. A case with `default_90d` filled on some rows and missing on others is eligible for both the labeled and censored sets, and “non-activated” is actually everyone except labeled activations, including censored activations. The leakage function ignores its arguments and returns a constant dictionary. Imports include an XES importer and an unused alpha miner; timestamp parsing covers only the event time. Survival analysis is deferred to lifelines or scikit-survival, which is appropriate, but that connection is outside the code and the suggested `get_event_attributes` step is not a survival design.

A usable version would need one prediction clock that does not look ahead, an estimand that matches that clock, censoring times equal to observed follow-up, a maturity embargo in every backtest, and a prefix table built only from events and attributes available at that clock. This draft names those problems and then specifies procedures that reintroduce them.
