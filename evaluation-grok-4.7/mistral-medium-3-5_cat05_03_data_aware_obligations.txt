4.7

The write-up is organized and gets several easy outcomes right, but it is not reliable as a temporal compliance analysis. One required classification is wrong, two other release states are mis-analyzed, the formalization is unsound, and the code both crashes and clears a sanctions miss.

## Case reasoning

TX-302 is the clearest error. At release the state is GB, EUR 180,000, MEDIUM, CORPORATE. R1 therefore applies, and Enhanced_Review at 09:20 sits after creation and before release, with no later material change. That satisfies R1 directly. EX-77 is also well evidenced, but it is surplus. The row says the review was satisfied and that there were no deviations, then labels the case JUSTIFIED_EXCEPTION. Those cannot be true together. The §4 counterfactual is the same mistake: an invalid exemption would still leave the case COMPLIANT.

TX-308 is wrong for a different reason. Release amount is EUR 100,000, and R1 is “at least EUR 100,000” with jurisdiction US. R1 triggers. The decrease from 140,000 does not invalidate the 14:20 Enhanced_Review, so the case is still COMPLIANT, but “Triggered rules: None / amount decreased; no triggers” is a false threshold reading. The label is right only by coincidence.

TX-306 is COMPLIANT, and the sub-20% increase (220,000 → 230,000, about 4.5%) correctly does not invalidate the review. R1 is still triggered (SG, 230,000) and satisfied. Listing only R2 understates the release state.

TX-301, TX-303, TX-304, TX-307, and TX-309 are substantively right: missing enhanced review after the 80,000 → 125,000 jump; HIGH risk with enhanced review but no Compliance_Approve; XZ listed after the only screen; PEP covered only by a standard packet; 118,000 → 145,000 (about 22.9%) invalidating the 15:25 review. TX-305 is correctly INDETERMINATE, and TX-310 is a defensible INDETERMINATE given contradictory exemption evidence. TX-311’s COMPLIANT label is right because release jurisdiction is DE.

The findings table still undermines those correct labels. Invalidated or pre-update events are listed as satisfied obligations (TX-304’s 08:10 screen, TX-309’s 15:25 review, TX-307’s standard packet). TX-303 calls HIGH risk “PEP-like.”

## Ambiguities

§4 names the required cases and then gets three of them wrong. TX-302 would not become NONCOMPLIANT if EX-77 failed. TX-305’s counterfactual says a known 150,000 release amount would be NONCOMPLIANT because there was no Enhanced_Review; there was one at 11:15, and the real residual issue is that the review document contains no amount and settlement is not a release payload. TX-311’s ordering does not decide the result: event 4 is still before release either way, so release jurisdiction is DE in both orders. The same-timestamp fact changes the state at review, not the R1 snapshot at release.

TX-310 is the only adequate alternative: a pre-release qualified signature would support JUSTIFIED_EXCEPTION; the 10:30 certificate and the requester-witness do not.

## Formalization

Section 1’s prose is mostly right: blanks are holds, lower `event_index` happens first, final case attributes are not retrojected, and a late record is evidence rather than an event-time update. It never cleanly separates event time, effective time, record time, and evidence time, and “material” is circular.

The pseudo-logic does not match that prose. R1’s `not enhanced_review(...)` is negation over any review, not over a review inside `(material change, release)`, so a stale review such as TX-309’s would fail to count as a violation; the time tests then use an unbound variable. R2 has the opposite polarity: the clause succeeds when the obligation is met, not when it is triggered. R3 repeats the bad negation and compares a time to a predicate. R5 never states that a displayed backdate is insufficient. R6 makes any missing attribute at any time indeterminate once a rule fires. R7 keeps the same-timestamp event with the smaller index, which is the earlier state, not the latest. The rule table is only a sketch: R4 is written as if a new review were always required before release, and R2 never says a standard-packet approval is not the relevant approval.

## Code

The pipeline has the right shape (inline CSV, `format_dataframe`, forward-fill, release snapshot, exemption dict, coarse flags, no classification lookup). It is not executable or faithful.

Exemption times are naive `datetime`s; `pd.to_datetime` on the `Z` timestamps is UTC-aware, so the comparison throws. R3’s flag is computed and then ignored: `classify` demands that no screen exist at all, so TX-304, which was screened only before XZ was listed, falls through to COMPLIANT. R1 satisfaction is “some Enhanced_Review exists,” not “one exists after the latest material change.” Compliance_Approve is not required to follow that review. `event_index` is never used. Material-change time is not tracked. `max(..., pd.NaT)` can discard a real review time because comparisons with `NaT` are false. The printed frame has neither unknown-value flags nor evidence timestamps. The optional control-flow check is absent; that part was optional, but the implemented flags still cannot stand in for the narrative.

## Sections 6 and 7

The six requested failure modes are present and illustrated. Final-state leakage is collapsed into the TX-309 post-review increase, and that increase is called 25% rather than about 23% from 118,000. Section 7 is the strongest part: immutable release payloads, effective versus record versus signature time, rule version, exemption scope, provenance, stable ordering, list versioning, and explicit unknowns are all concrete and relevant.
