6.2

The design correctly separates the six duplicate types and makes the right keep/merge calls on the required pairs: merge e03/e04 and e11/e16, keep e05, e14, e06/e07, e08/e09, e09/e10, and e13/e15, and do not treat shared O1/V1 as identity. The counts 17/44, 15/39, 14/37, and 10/28 match full-row equality, verified-pair union, one extra e06/e07 union, and activity-plus-timestamp clustering under a common-object rule. The warning about synthetic time, the optional invoice-before-payment edge, and the eight required failure modes are substantively right.

Those results do not survive the ordering or the implementation.

The partial-order policy merges lifecycle constraints into “domain constraints” and uses “source-specific semantics” for label repair rather than ordering. It states e08 before e09 as a domain fact; the known facts only place handover after carrier acceptance. e08 before e09 is an assumption, and the code hardcodes it. Within-source `source_seq` is then misapplied in the write-up. e11 (`ER`, seq 40) and e15 (`ER`, seq 41) are ordered by that rule, but the text calls e11-before-e15 a stable id fallback. e04 (`SCANNER`, seq 551) and e05 (`SCANNER`, seq 552) likewise give a within-source reason for the I1 scan before the I2 scan; the text calls e03-before-e05 arbitrary. The 12:00 sequence is written as one total order. With the stated constraints, M2 is incomparable with the M1 authorization/capture chain, so several interleavings remain admissible.

`assign_order_key` reverses that policy. `TopologicalSorter.add(node, *predecessors)` means `sorter.add("e12", "e13")` places e13 before e12. Every semantic edge is inverted, including the hard rule that authorization precedes M1 capture. Rank is unique, so the later `source_seq` and event-id keys never break ties. The index timedelta then stores that reversed total order.

Provenance is overclaimed. The schema has one `source`, one `source_event_key`, and one `source_seq` per canonical row. `verified_pair_merge` keeps the left row, ignores `rule` and `authority`, and drops the right event’s source, key, sequence, and ingestion time. e04’s `S-901` and e16’s `B-9` are not reconstructable. Unioned E2O links have no per-source ownership, so the raw relation table cannot be rebuilt. “Fully recoverable” is false. Label refinement also leaves no audit row, so the restored carrier-acceptance meaning exists only as a display string.

The PM4Py block will not execute the stated pipeline. A real OCEL uses `ocel:eid`, `ocel:activity`, `ocel:timestamp`, `ocel:oid`, and `ocel:type` via the OCEL column attributes. The normalized frame renames those away, so the library calls key-error or read the wrong fields. `ocel_drop_duplicates` has no `subset` argument; its actual key is activity, timestamp, and the same object set. On that key the conservative fallback is not a no-op: it can drop one of e08/e09, one of e03/e04, and one of e11/e16. `ocel_merge_duplicates` is demonstrated with `object_type` and `merge_only_same_activity`, not `have_common_object`. The prose discusses that flag, and the aggressive call does not pass it. The fallback still passes `object_type` outside the `try`, so that scenario raises. `timedelta=` on `ocel_add_index_based_timedelta` is not the usual signature; common implementations step by milliseconds and would create the duration distortion section 9 warns about.

Sensitivity names useful directly-follows changes, and the e06/e07 ET–OT point is valid: after that merge, every pack event carries items. Coverage then thins. OTG relations are absent. OC-DFG edge counts and lifecycle/performance are not compared across the four datasets. The raw I1 path “Pick → Pick → Pack” is not fixed by the raw timestamps, because e06 is in the same 10:00 tie. “Payment-flattened DFG no longer distinguishes M1 and M2” is too strong: after a union, M1 still has authorization and M2 does not, while the real damage is one capture related to both payments and the loss of e05 as a separate I2 pick.

Smaller defects match the same pattern. The harmonization terminal says “retain both unchanged” and also says to refine labels, which are different required decisions. The canonical-id column stores both e03 and e04. The decision tree is hardcoded pairs plus a coarse activity-timestamp pre-check, so the pre-check still lumps e03 with e05 and e13 with e14.
