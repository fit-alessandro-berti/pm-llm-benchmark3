3.8

The write-up follows the required section order and gets several release labels right (TX-301, TX-302, TX-304, TX-306, TX-309, TX-311, and a defensible INDETERMINATE on TX-310). Those labels are not reliable. Obligation identity, boundaries, and the formal rules frequently contradict the policy and the log, and the code does not implement the checks it claims to perform.

**Case reasoning.** TX-307 is wrong. At release the customer is PEP, the only review is a Standard_Review, and Compliance_Approve is explicitly of a standard packet. R2 still applies when jurisdiction is DE. The row omits PEP, treats “jurisdiction = DE” as an R1 trigger, and calls the case COMPLIANT on a “jurisdiction exemption” the policy does not contain. TX-303 is NONCOMPLIANT for the wrong reason: Enhanced_Review is present at 10:20, after the HIGH reclassification; the missing event is Compliance_Approve. TX-305 repeats that false “missing Enhanced_Review” claim; the review exists, and the open question is the unknown amount. TX-308 treats EUR 100,000 as below “at least EUR 100,000,” so it denies an R1 trigger that is present. COMPLIANT is only accidentally right, because the earlier Enhanced_Review survives a decrease under R4. TX-306 is COMPLIANT but incomplete: R1 also triggers, and a sub-20% increase is recorded as a deviation. TX-309 names R4 and not the R1 obligation that R4 invalidates. Across the table, failures are written into “Satisfied obligations.”

**Formalization.** Section 1 defines every attribute update as material. That contradicts R4 and the COMPLIANT results for TX-306 and TX-308. The R1 pseudo-logic is inverted: a review after the latest material change is COMPLIANT only if EX-77 also exists, and is otherwise NONCOMPLIANT. R3 refers to an unbound release event. R4 never defines the baseline amount, a decrease, or an unknown prior amount. R5–R7 have no pseudo-logic despite the requirement to formalize R1–R7. R2’s table points at an exemption register even though these exemptions waive R1 only. Comparison operators are missing in the rule text, so several rows are not actually formal.

**Alternatives.** TX-302 says effective time 09:00 is after the 09:20 review; it is before, and the review alone satisfies R1. TX-310 never states the rejection path: if EX-88 is not proved, the case is NONCOMPLIANT because only a Standard_Review occurred. The certificate-created-at-10:30 fact is stronger than “witness bias,” and the requester’s oral statement does not establish Head_Compliance approval. TX-311’s counterfactual is false: ignoring the change to DE would leave jurisdiction US, so R1 would trigger (and the Enhanced_Review would still meet it).

**Code.** `pm4py.format_dataframe` is never called. Forward-fill is applied to a filtered copy, grouped by `event_index` (one row per group), and not written back, so release rows keep blank attributes. `NaN >= 100000` is false, which silently treats a missing amount as not high-value and breaks R6. Same-timestamp `event_index` is unused. Only a flawed R1 flag is computed; R2–R4, per-event-type last timestamps, Sanctions_List_Update, an exemption-register join, evidence timestamps, and unknown-value flags are absent. Both EX-77 and EX-88 are hardcoded as sufficient. There is no DECLARE or trace-order check.

Sections 6 and 7 do list the six requested failure modes and the requested logging fields, but they stay generic. Final-state leakage is illustrated with a post-review amount change, which is a different failure.
