The case table is mostly right, but the formalization and checker are not reliable enough to carry the analysis.

TX-301, TX-303, TX-304, TX-306, TX-307, TX-308, TX-309, and TX-311 are classified correctly, and TX-305 and TX-310 are defensibly `INDETERMINATE`. TX-302 is not. Its Enhanced_Review at 09:20 already satisfies R1 before release, with no later material change, so the valid EX-77 signature is surplus. `JUSTIFIED_EXCEPTION` plus “waived” contradicts the same row’s “Enhanced Review” satisfaction. Section 4 then says a weak exemption would make TX-302 noncompliant, which is false while that review stands. The TX-305 counterfactual is also false: an Enhanced_Review does exist; retroactively using 150,000 would still not mean “no Enhanced Review,” and the review document having no amount would remain an R4/R6 problem.

R1’s pseudo-logic requires `last_review > last_change AND exemption_valid`. The rule is review-after-material-change unless a valid exemption applies. R4 never measures a >20% increase from the reviewed baseline and never encodes an increase from an unknown amount.

The code disagrees with the findings. Any `Update_Amount`, including TX-308’s decrease and TX-306’s sub-20% increase, is treated as invalidating. The missing-amount branch is unreachable because R1 is only entered when `amount >= 100000`, so TX-305 stays `COMPLIANT`. EX-77/EX-88 validity is hardcoded, so TX-310 becomes `NONCOMPLIANT` rather than `REVIEW_REQUIRED`. Standard_Review is not tracked, the diagnostics frame has no evidence timestamps or unknown-value flags, and `pm4py.format_dataframe`’s result is unused. There is no DECLARE or trace-order check.

Section 6 names the right six themes, but the “final-state leakage” example is really a stale review before an amount change. Section 1 and Section 7 are the cleanest parts: blanks, forward-fill, `event_index`, and the requested logging fields are handled substantively.
