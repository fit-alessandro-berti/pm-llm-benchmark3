The dependency design is largely right, but both required models mis-implement the loop, and the comparison table then calls that behavior exact. That is a core failure, not a notation nit.

The process-tree and POWL loops are both given three children: do-part, `Adjust Parameters`, and an explicit `tau` exit. In PM4Py, `Operator.LOOP` is binary: first child is the body, second is the redo, and the exit is implicit. `*(body, redo, tau)` is not a valid process tree, and `OperatorPOWL(Operator.LOOP, [do, redo, exit])` does not match the operator contract. Construction of `powl` is therefore not a valid model, and `tree` is ill-formed for conversion, playout, or soundness. Section 1’s claim that a passing inspection “triggers” that third child is also the wrong mechanism. The choice to exit or redo is a silent nondeterministic choice after the body; inspection does not cause it. Section 8 later admits this, so the document contradicts itself. The intended language `(Execute Trial, Inspect Trial)(Adjust Parameters, Execute Trial, Inspect Trial)*` is the right abstraction, but the code does not implement it, so the “Exact” repeat-until cells in §6 are not earned.

The partial-order skeleton itself is strong. Register precedes the two opening streams; containment gates only planning; root-cause analysis gates design, the approval XOR, and optional consultation; the trial waits for both work products; approvals and consultation join only at release; archive is last. The low/high-risk XOR, with quality and regulatory review unordered inside the high-risk branch, and consultation as XOR-with-skip, match the control-flow reading. The tree’s global barrier after `Contain Material || Analyze Root Cause` is a genuine conservative under-approximation, and trace 3 is a real witness of that loss.

§6 then undoes some of that honesty. It marks optional consultation, and the approval/trial overlap, as exact in the tree. They are not: consultation, approvals, and design also wait for containment, which §3 already states. The split-dependency row mentions only planning waiting for root-cause analysis and design waiting for containment, so the table under-reports the barrier. §4 explains concurrency with a few examples and never accounts for important unordered pairs such as containment with design, approvals, and consultation, or root-cause analysis with planning. The dependency row “Consult Supplier → None / Optionality” is not a real relation.

The eight witnesses are well chosen and, under the intended binary-loop semantics, the verdicts and earliest violations are right: low risk, high risk, consultation, a two-iteration redo, the tree’s extra barrier, a cross-branch start of planning before containment, a redo after release, and release before the approval route. Those verdicts do not hold of the code as written, because that code has no defined loop semantics.

The validation plan would not get that far. Converting either model fails on the loop arity before soundness, playout, or replay. It also never states the discriminating expectation that trace 3 fits the POWL net and fails the tree. The silent-behavior check is only a prose intention.
