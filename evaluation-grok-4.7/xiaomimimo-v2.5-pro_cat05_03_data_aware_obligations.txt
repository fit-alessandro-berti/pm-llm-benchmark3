**7.3**

The case conclusions are largely the right ones, and the temporal reading is coherent. The write-up is not nearly flawless: the published code results are not what that code computes, one required failure mode is misexplained, and the formalization does not actually cover R1–R7.

**Case conclusions.** Under a consistent reading of R4’s 20% rule as the amount-materiality test, the eleven classifications hold: TX-301, TX-303, TX-304, TX-307, TX-309, and TX-310 noncompliant; TX-302, TX-306, TX-308, and TX-311 compliant; TX-305 indeterminate. Release-time state is reconstructed forward, settlement on TX-305 is not copied back, EX-77 is not required once the enhanced review stands, EX-88 fails because the signing certificate is after release and the witness is the requester, and TX-311 correctly treats `event_index` so the jurisdiction is DE only after the review, which switches R1 off at release. The 22.9% figure on TX-309 and the sub-20% figure on TX-306 are right. Medium confidence on TX-306 is earned, because a stricter “any amount update is material” reading of R1 would flip it.

**Formalization.** The rule table has the required columns and the temporal directions are mostly explicit. R6 never appears in the pseudo-logic, despite the request for R1–R7. `R1_satisfied` and `R2_satisfied` are conjoined with the obligation, so “not satisfied” covers both “rule off” and “rule broken.” R1’s “after the latest material data change” is encoded as `≥` on `(timestamp, event_index)`, which is not strict after. The empty-change case is undefined in the logic and only handled in code.

**Code versus the printed diagnostics.** The script does the things asked: in-memory CSV, `event_index`, `pm4py.format_dataframe`, within-case forward fill, release snapshot, last review/screen/update, R1–R4 flags, exemption join, and a coarse trace-order check with a real explanation of why DECLARE-style order is not the policy. It does not look like a classification lookup. The “sample output” was not produced by that script. TX-301 has no enhanced review, so `mat_increase_after_enh` stays false and the percent stays 0; the table shows `True` and `56.2`. TX-305’s triggers are booleans in code (`False` when the amount is unknown), not `None`. That is a false execution claim. Evidence timestamps are stored and then omitted from the printed frame. `discover_dfg` is unguarded, so a pm4py failure kills the run after the real work.

**Section 6.** Post-hoc exemptions, post-review amount changes, conditional activation, missing data, and same-timestamp order are tied to the right cases. The “final-state leakage” row is a different fault: TX-303’s risk is already HIGH before release, so the final case state does not disagree with the release snapshot. The leakage the policy cares about is using an end-of-case value at an earlier event (TX-305’s settlement amount, or TX-311’s final DE at the review instant). The label is present; the explanation is not that failure mode. TX-308’s decrease-after-review tension, which is the same R1/R4 ambiguity as TX-306, is left out of the alternative-readings section.

Logging recommendations cover immutable release payloads, effective/record/signature time, rule version, structured exemption scope, change provenance, and stable ordering, with a clear reason for each.
