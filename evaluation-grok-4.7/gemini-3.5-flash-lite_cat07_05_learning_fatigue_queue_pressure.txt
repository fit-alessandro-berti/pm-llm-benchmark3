**6.5**

The required six-part structure is complete, the main constraints are respected, and the headline account is right: early slowness tracks a harder carryover mix, later speed-up tracks queue pressure, and raw late-shift error rates are not a basis for punishment. The write-up still misstates several data relationships and specifies analyses that do not identify the mechanisms it names.

The mechanism table is uneven. Learning, fatigue, circadian effects, case-mix, and batching are bounded in a usable way, including the point that batching is too local to explain the shift-wide curve. The queue-pressure row treats 16.8 minutes for high-WIP, high-complexity work as evidence against pressure. That cell is still a large speed-up from 22.4 minutes at low WIP, so it supports pressure while showing that complexity sets a floor. The automation row’s “against” cell restates the queue interaction that supports the mechanism. Fatigue is credited with the rise from 2.7% to 7.9% and rework from 5.0% to 13.7% without noting that those bins are also the high-queue bins. The night-staff citation pairs an 8.2% error rate that is conditional on high WIP with “despite lower volume.”

The integrated narrative overreaches the tables. Positions 1–5 average 18.8 minutes across all human resources, while seniors’ first 20 events average 15.9 minutes and juniors’ average 19.6. Senior handling of hard carryover does not account for the opening duration. The 10.9% error figure is the high-WIP, high-complexity cell; the 13.7% rework figure is the 76+ position bin, whose mean complexity is the lowest in the table, 0.43. Joining them as one collision result is incorrect. Truncated review, parallel processing, and general sequential batching are asserted as the cause of the drop to 10.8 minutes, while the log only supports short sequential Document Review batches for two juniors late in the Day shift. Section 2 treats the late error rise as established omissions and cognitive slips. Section 5 then says error flags are often created only when Quality Check runs, and Quality Check is batched in the last 45 minutes. That detection-timing explanation is absent from the mechanism table and the main narrative, so the same series is explained as both real slips and a measurement artifact.

The analysis plan names the right comparisons, then implements several of them incorrectly. The within-resource code never computes service time, never fits the promised fixed-effects model, and would difference activity mix inside a case if case effects were used without activity effects. Grouping on `resource_experience_months` does not recover Senior, Mid, Junior, and Night groups. `filter_event_attribute_values` on `range(0, 30)` does not build the stated WIP-by-complexity cross-tab, and the resulting object is named as if complexity were filtered. The complexity-adjustment block calls `filter_case_performance` on case duration of 300–7200 seconds, which does not hold complexity fixed. `discover_batches` is only printed as a count, so it does not test the Junior_H / Junior_I, Document Review, late-Day pattern. Shift overlap at 14:00–16:00 is a sound comparison, but it is left as a sentence, with no `filter_time_range` design. `get_rework_cases_per_activity` counts repeated activities, which is not the same measure as the 7-day `rework_flag`.

Intervention scoring is mostly operationally sound, especially the rejection of penalties and the warning that random assignment can send hard cases to juniors. Intervention 2 does not state the main downside: moving complex work out of the first hour can place it in the later high-WIP region, the cell already at 10.9% errors. Intervention 6 records delayed detection, but it still presents deferring Quality Check as a flow benefit and does not connect those deferred checks to the next shift’s hard opening backlog. “Hoarding” and “voluntarily or culturally absorb” add motives the log does not show. “Defays” is a straight error, and “ecological fallacy” is the wrong name for confounded worker-level rates.

The dashboard covers the requested families: service time, waiting, WIP, rework, errors, complexity mix, batching, and fairness with some handover content. `insert_case_service_waiting_time` is described as arrival-to-start delay; it sums within-case service and waiting. The complexity cutoff above 0.7 is undefined in the data, and queue-ownership change is only a handover delay inside the fairness indicator.
