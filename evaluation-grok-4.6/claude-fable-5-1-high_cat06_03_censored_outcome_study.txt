7.0

The design is conceptually strong: it refuses convenience non-defaults, conditions the primary estimand on activation, keeps an as-of cutoff, and accounts for all 48,000 cases. It is not nearly flawless. Several statistical and implementation defects are material.

**What holds up.** Section 1 correctly treats post-activation 90-day default as undefined for rejected, withdrawn, unlinked, and open cases, and writes a policy-conditional estimand \(P(T\le 90\mid X_k,A=1;\pi)\) rather than a fake universal default probability. Alternatives A and B answer different questions and are labelled as such. The cohort arithmetic is consistent with the snapshot (21,600 + 3,600 activated; 12.5% is a matured-activated rate only). Section 3 separates administrative censoring, delayed feeds, activation selection, transfer, and suspected permanent feed loss, and is honest about what is untestable (reject inference, MNAR feeds). The leakage table hits every required element with the right keep/repair/drop calls. Random splits are rejected for the right reasons (maturity truncation, July 2025 policy, October 2025 migration, target encoding).

**Target and estimand slips.** Scoring every open prefix as “risk if this application is activated under the current policy” slides from an associational, selected-population functional toward a counterfactual reading that Section 8 later disclaims. That is exactly \(P(T\le 90\mid x_k, do(A=1))\), which the answer itself says is not identified. The overlap diagnostic is the right mitigation and then never appears in the pipeline. The primary fit is a pooled hazard with a regime flag, despite the brief stating that the same prefix has a different selection probability and a different outcome map after 1 July 2025. A level shift does not identify that interaction; regime-specific models are demoted to sensitivity even though the policy break is known, not hypothesized. After activation, account closure / payoff is ignored, so non-default closed accounts would still accrue 90-day exposure.

**Cohort and missingness.** The 3,600 immature activated cases are never partitioned into ordinary censoring, delayed feed, and suspected permanent loss, so the cohort-flow table does not actually implement the taxonomy Section 3 relies on. Following ~60% of transfers into the outcome stage is inconsistent with the 48,000-application universe: partner reactivation may be a new identifier (double counting) or may lie outside this extract (labels that do not exist in the stated file). Unlinked transfer as informative loss-to-follow-up is described and then dropped from the code.

**Validation.** Using `ct_now` / `X_now` (as of 15 February 2026) for every test window means early folds are scored with fully matured labels that a real cutoff-c evaluation would not have; IPCW on “remaining” censoring does not reconstruct a prospective label calendar. The 2025-10-01 rolling fold and the “touched once” hold-out are the same start window. Test metrics therefore mix an easy early-fold regime with a structurally censored late fold and then invite a single narrative of “temporal robustness.”

**Section 9 is not a working survival pipeline.** This is the largest gap between the prose and the artifact.

- `np.fmin(days_default, fu)` is NaN whenever there is no Default Recorded event. Censored activated accounts—the cases the survival story exists to keep—get missing times instead of `fu`. The `(time, event)` hook is then unusable.
- Binary `y90` can fire from `default_90d` on the feed while `event` only fires on a Default Recorded timestamp. The prompt’s outcome is an external feed with 7–35 day lag, not a guaranteed near-real-time event. Feed-only defaults become `y90=1` and `event=0` (or NaN time). Interval-censoring / event-at-horizon when only the binary feed exists is not specified.
- `g["risk_score"].last()` is the last row, not the last non-null value the comment claims. Same-day `documents_total` is replaced by a “Documents Received” activity that is not in the process or the alias map, so the repaired feature is identically zero.
- `pm4py.get_prefixes_from_log(..., case_id_key=CASE)` is not the documented public signature; several PM4Py versions return an `EventLog`, after which the `groupby` logic is dead. `elapsed_prefixes` is defined and then omitted from `temporal_folds`, so the dual prefix design is unevaluated. Transfer linkage, IPCW, and the activation-propensity model are comments only.

**Smaller unclarities.** Applicant-level splitting is an untested assumption. `discover_dfg` is run on the full log, including post-outcome events, as a canonicalisation check that cannot validate prefixes. The alias map is presented as known migration truth. `label_status` “not activated” is recovered only via the crosstab, not as competing states in the case table used for modelling.

The piece would be in the high 8s if the estimand stayed strictly associational, the primary model respected the policy break, test labels were as-of a fold-specific maturity date, and the skeleton actually emitted a valid censored outcome table through real PM4Py APIs. As written, the methodology essay is substantially better than the pipeline that is supposed to instantiate it.
