## Decisive factual error: O2O cardinality

The O2O table in the code has **12** rows:

`contains` 3 + `packs` 3 + `carries` 2 + `bills` 2 + `partially_settles` 1 + `completes_settlement` 1 = **12**.

The answer states **11** in three places that matter:

- §1: “11 O2O facts, not 22”
- §3: qualifier table total **11** (the per-qualifier counts already sum to 12)
- §8 check 1: “`o2o` has exactly 11 rows”

That is not a rounding slip. It is an audit error repeated inside the reviewer’s checklist. Anyone following the stated semantic checks would reject a correct construction. On a task whose evaluation criteria include referential integrity and table-level audit, this is a serious self-inflicted defect.

## Policy vs. data mismatches

The stated E2O rule is: attach an object only if the narrative records operational involvement.

- **e7** (“relates to both Orders”) justifies `O100`/`O200` on Pack P1.
- **e8** is only “Pack Package P2 with I2.” Attaching `O100` as `affected_order` is an inference via Item→Order, i.e. the propagation the author claims not to put in `relations`. That single extra link is what creates O100’s `Pack Package → Pack Package` edge and the “packing occurs twice” warning. The analysis treats that edge as a fact of the log rather than a consequence of an undeclared exception.
- The process text calls **both** M1 and M2 “partial payments.” Mapping M2 to `completes_settlement` invents a fully-paid invoice of 250. The requirement *allows* that qualifier, but §8 presents it as a narrative fact. The assumption is never stated.
- `currency = "EUR"` is also invented; the text only says “monetary units.” Harmless in the DataFrame, sloppy relative to “source-faithful.”

These are small individually; together they mean the “moderate, source-faithful” slogan is not applied uniformly.

## Smaller inaccuracies and unclarities

- §8: “the **two** events on 2026-04-07” then lists **e14, e15, e16, e17**. Four events, not two.
- Qualifiers are called “exhaustive and **non-overlapping**,” but `affected_order` is reused across Add Item, Reserve Stock, Pack Package, and Issue Invoice. The real invariant is functional `(activity, type) → qualifier`, which the validator checks. The prose overclaims.
- §5 treats the OTG as an E2O co-occurrence graph (`order–package` via e7/e8; no `order–delivery`). `discover_otg` may instead be O2O-derived, in which case `order–package` is **absent** and `payment→invoice`, `invoice→order` dominate. The expected edge set is given without stating which definition is assumed.
- Alternative (a) says the OTG “loses the order–item edge on packing” — easy to misread as losing the order–item type edge entirely, which would still exist via Add Item.
- `iterrows` in the propagator is fine as a labeled analytical extra, but it is the weakest piece of otherwise clean pandas.

None of these break the business story. All of them are the kind of imprecision the rubric said to punish.
