**4.4**

The write-up has the right *headings* and avoids the worst failure mode (calling rejects/withdrawals non-default). Under a strict reading it is not a defensible study design. Several required artifacts are arithmetically wrong, the estimand is not aligned with the prediction time, the censoring strategy is statistically incorrect, and the PM4Py skeleton would mislabel outcomes and call APIs that do not work as written.

## Section 1 — Target (directionally acceptable, operationally incoherent)

The activation-conditional binary is a legitimate estimand: \(P(D_{90}=1 \mid \text{activated}, \mathcal{H}_{t^\*})\). The text never faces the operational fact that \(t^\*\) is the **first** Credit Review. At that time activation is still in the future. A model fit only on people who later activate cannot be scored on “every credit application” without a second model for selection, a two-stage likelihood, or an explicit “score only if you will activate” policy. That is the central design tension the prompt asked to confront. It is mentioned as a limitation later, not built into the target.

Worse, the horizon is 90 days **after activation**, not after \(t^\*\). Time from first review to activation is random and policy-dependent. Two applications with the same prefix can have different calendar gaps to the outcome window. That is not a standard 90-day early-warning target; it is a selected, time-shifted outcome. This is never treated as part of the estimand.

The competing-risks alternative is the better match to “every application,” then dismissed for the wrong reason. A multi-state model on {reject, withdraw, transfer, activate-and-survive, activate-and-default} does **not** require counterfactual default-if-accepted assumptions. Those assumptions appear only if you impute a default label for non-activated cases. That confusion recurs in Section 3.

No policy-specific counterfactual target is specified, despite the prompt listing it. Time-to-default with right censoring is not defined as a target here; it is smuggled in later and then misspecified.

## Section 2 — Cohort flow fails the only hard accounting test

The snapshot already partitions 48,000:

21,600 labeled + 9,100 rejected + 5,700 withdrawn + 2,900 transferred + 5,100 open + 3,600 immature activated = **48,000**.

The table invents a second 3,600 with “no Credit Review,” subtracts them to get 44,400, then lists **48,000** outcomes under that heading. The 3,600 immature activated cases are double-used. This is not a rounding issue; it is a fabricated exclusion that breaks the required cohort-flow table.

Other cohort problems:

- Exclusion of unlinked transfers and partner cases removes the hardest missingness mechanism instead of representing it.
- Inclusion “must eventually reach Account Activated” conditions on a post-prediction event. That is not an as-of rule.
- Maturity cut “Activated ≤ 15 Nov 2025” is wrong: 15 Feb 2026 − 90 days is **17 Nov 2025**. The +35-day feed cut “11 Oct” is also off (~13 Oct). Small, but this is the label-as-of rule.
- Still-open (never decided) and immature-activated (decided, outcome not mature) are conceptually distinguished in the table and then collapsed in the code (below).

Primary analysis “25,200 = 21,600 + 3,600” is only coherent for a survival analysis **from activation**, which is not the Section 1 target.

## Section 3 — Missing-data taxonomy is listed, then mishandled

The five-way split (ordinary censoring, delayed labels, activation selection, transfer, permanent feed loss) is the right list. The primary strategy is not.

“Treat immature activated cases as right-censored **at prediction time**” is a basic survival error. Those cases were observed through activation and part of the 90-day window. Censoring time is last follow-up / extract time measured **from activation** (or from \(t^\*\) if the clock starts there). Censoring at first Credit Review discards observed survival.

IPCW on the 21,600 mature actives can correct **label-maturity** censoring among actives. It does not correct **selection through activation**. The text treats them as the same “selection bias.”

“Censoring independence (log-rank test)” is false. Log-rank compares survival curves; it does not test independent censoring. Independent censoring is not identified from these data without extra assumptions. Delayed-label MAR is only weakly probeable; partner feed loss and unlinked transfers are essentially untestable. The testability paragraph is overconfident and technically wrong.

Multiple imputation of `default_90d` for immature **activated** cases can be a sensitivity analysis. Imputing default for rejects/withdrawals is a different, stronger, and unlabeled counterfactual. The sensitivity list does not keep that distinction sharp.

Partner-originated permanent missingness is named and then left out of the primary estimator. Transfer re-identification at 60% is not given a concrete rule (linked follow-up vs competing event vs inverse-probability of linkage).

## Section 4–5 — Process model is ignored

Process: Started → KYC → **Credit Review**, and only **then** document loops back to Credit Review.

If \(t^\*\) is the **first** Credit Review, the typical prefix is three events. Document-request counts, CR loops, rework, and most control-flow features are almost always zero. The feature list is written for a mid-case prediction point the target does not use.

The prefix section then adds first-3/5/7 events and 1/3/7-day prefixes from start, which **are not** the Section 1 prediction time. A 7-event prefix will often include post-first-CR events (more reviews, Accept, even Contract Signed). That silently moves \(t^\*\) and opens leakage. Short-case padding is irrelevant if first CR is required, and dangerous if it is not.

Activity renaming is handled by an invented map (`Old_KYC_Check`, `New_Credit_Review`) not in the schema. Collapsing names also erases the 15 Oct 2025 regime, which should be a cohort/calendar feature, not only a cleanup.

Historical “default rate for similar cases” and global DFG transition probabilities are proposed without an as-of constraint (only cases whose labels were mature **before** this case’s \(t^\*\)). That is target leakage dressed as a process feature.

Resource experience is listed despite being extract-time only. Queue length is correctly flagged as needing another table, then left unspecified.

## Section 6 — Leakage table is the strongest artifact, still sloppy

Required rows are present and `final_limit`, `decision_reason`, `collection_status`, future events are correctly dropped.

Faults:

- `default_90d` is marked **Keep**. It is the label, not a feature. In a leakage-audit table that is an ambiguous and risky instruction.
- Resource experience cannot be “repaired” from these data. Event-time tenure is not stored. Correct action is **drop** (or a clearly weaker proxy).
- `documents_total` “previous-day snapshot” is the right idea; no join key or snapshot table is defined.
- `source_system` “Keep / static” ignores partner-feed missingness and the migration. It may be a valid covariate; it is not harmless.
- `label_available_at` / `data_extract_time` are dropped as features (good) but never used as **as-of filters** in validation, which is their actual scientific role.
- No row for historical default rates, global DFG features, or `org:resource` assigned after \(t^\*\).

## Section 7 — Temporal split in name, contradictory in detail

A random split is correctly rejected. The proposed calendar cut (train 2024 / val H1 2025 / test H2 2025) is a start, not a backtest design.

Contradictions and gaps:

- Test is defined as 1 Jul–31 Dec 2025, then the text says the test set should contain **only** post-15 Oct cases. Both cannot be true.
- Validation is entirely pre-policy. Nothing is used to tune under the 1 Jul 2025 policy that the model will face.
- H2 2025 starts, especially after ~Oct, are heavily immature by 15 Feb 2026. Restricting test to mature actives conditions evaluation on fast activation and early H2 starts — a selected, easier slice. This is not discussed quantitatively.
- One fixed split is not “backtesting” across policy **and** migration **and** delayed labels. A rolling origin with an as-of label calendar is the minimum serious design.
- Train is later allowed to include censored cases; val/test keep only mature binaries. The estimand being evaluated is then not the estimand being fit.
- Metrics dump (AUC, PR, Brier, ECE, C-index) is generic. No IPCW/Brier-with-censoring protocol, no competing-risk scoring, no sample-size note (2,700 defaults over two years; the mature post-policy test set may be small and selected).

## Section 8 — Best section, still incomplete

Association vs selection vs counterfactual is stated clearly, and three+ deployment feedback loops are listed. That meets the prompt’s surface requirement.

It still understates the decision-use failure: a first-CR model trained on eventual actives **cannot** be the early-warning system the lender asked for without a selection model. “Use as relative scores only” does not fix applying those scores to rejects, withdrawals, and open cases that were never in the training measure.

## Section 9 — Skeleton looks like PM4Py, would not implement the design

Required shape is there: `read_csv`, timestamp parse, `format_dataframe`, temporal split by start, `get_prefixes_from_log`, a leakage check, cohort prints. Length is well above the 80–160 line cap, and quality is poor.

Concrete defects:

1. **`get_prefixes_from_log(..., max_events=7, activity_key=...)`** is not the PM4Py API. The public helper is `get_prefixes_from_log(log, length)`. Extra kwargs and the name `max_events` are invented.
2. Prefixes of length 7 are **not** prefixes to first Credit Review. A later timestamp filter is a patch, and if prefixing rewrites case IDs (common), the merge on `case:concept:name` breaks.
3. **`has_default` false ⇒ `non_default`** for every activated case. Immature and permanently missing labels are coded as 0. That is the exact dishonest labeling the prompt forbids, now in executable form.
4. Maturity uses `end_time + 90 + 35`, not activation time. A collections event months after activation makes an immature case look mature, and vice versa.
5. `still_open` is `end_time == CUTOFF_DATE` (exact equality) and can overwrite real terminal states.
6. **Train vs val/test populations differ**: train keeps all start-year cases; val/test keep only mature actives. The boolean filter on `val_cases.index` is also alignment-fragile.
7. `case_info.loc[x, "start_time"]` uses the case **name** as a DataFrame index. `case_info` was never `set_index`’d. This errors or mis-maps policy period.
8. **`get_variants_sorted` + `for case, variant in variants.items()`** misunderstands variants. PM4Py variants map *variant → traces*, not *case → variant*. The feature is wrong even if the function name exists in some version.
9. `discover_dfg` is computed on the whole prefix log and then ignored, except for a simple event count that did not need a DFG. No justification for the call.
10. `extract_temporal_features_dataframe` on prefixes that may still contain post-decision rows (if the prediction-time filter failed or was applied inconsistently) is not guarded.
11. Leakage “audit” only checks whether dropped columns are absent from a table that never selected them, and treats `risk_score.nunique() > 1` as evidence of post-prediction updates. Theatre, not an audit.
12. Unused `sklearn.model_selection.train_test_split` import undercuts the “temporal not random” claim. `pm4py.split_train_test` is not even mentioned as a baseline.
13. Survival/competing-risk hooks are a trailing comment, not a data contract (clock origin, censor indicator, competing-event code, as-of label date).
14. Transfer linkage, partner missing feeds, policy/migration regime flags as first-class cohort columns, and `label_available_at` as an as-of predicate are absent.

## What was actually required vs what was delivered

| Requirement | Verdict |
|---|---|
| Honest target; no convenient non-default labels | Prose yes; code no |
| All 48,000 accounted for | Fail |
| Ordinary censoring ≠ undefined-under-policy | Named, then conflated |
| Prediction time without lookahead | Stated, then mixed with 7-event prefixes |
| Process-aware features at \(t^\*\) | Mostly impossible at first CR |
| Leakage table on required fields | Mostly present, several bad actions |
| Temporal validation, not random | Intent yes; design contradictory |
| Working PM4Py-oriented skeleton | Structural outline only; wrong APIs and wrong labels |

A high score needed a consistent estimand, a cohort table that adds to 48,000, censoring times measured from the right origin, a prediction time that either includes document loops or admits the prefix is almost static attributes, and code that cannot recode missing `default_90d` as 0. This answer reads like a competent template and fails those bars.
