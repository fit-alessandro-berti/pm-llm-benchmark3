7.2

The design is substantively strong: it treats the twin as a non-stationary, resource-constrained, cross-case system; it keeps objections latent; it refuses to treat service/waiting as identified; it does not claim optimality; and the eight required sections plus the PM4Py/simulation split are all present. Under a hypercritical bar it is not nearly flawless. Several methodological and internal-consistency faults would change results or decision logic if taken literally.

**Serious design faults.** Snapshot initialization is preferred, but the log often has only completion times, so in-service versus queued state is not reconstructible. That contradiction is not resolved. KPI cases arriving through month 18 of a 24-month horizon cannot support Complex-variance p90 (~260 days): late arrivals are still open, and right-censoring then contaminates the tail metric that Section 7 treats as primary. Planning-review rework is in the problem statement and is omitted from case loop state (only completeness, inspection, legal, appeal). `Calendar.blocked_fraction` is defined for the 40% environmental reservation and never applied in `is_available`. Utilization in code is busy/horizon, not busy/rostered time, which conflicts with the 65–85% / 90% decision rule. Fire (2 FTE, Tue–Thu) and legal (council weeks off) may already violate the 90% hard cut in the baseline, which would eliminate every scenario. Fairness is both “≤ 1.3” and “not worse than baseline”; those are not the same if districts D3/D5 already exceed 1.3.

**PM4Py and code.** Loading via pandas + `format_dataframe`, avoiding `pm4py.read_csv`, documenting tree limits, and keeping waiting as a simulation output are correct. `discover_performance_dfg` does not return a dict of mean/median per edge; it returns one aggregation (default mean). Median requires a separate call with `aggregation_measure="median"`. Case-level filters should not be assumed to work via `filter_trace_attribute_values` when `case_type` sits on events. `to_dataframe` imports PM4Py inside the layer that was declared PM4Py-free. Log flags are `"yes"`/`"no"` while `Case.requires_fire` is `bool`; a string `"no"` is truthy, so routing can silently require every review. Cluster generation copies one attribute vector onto every case in a burst, overstating type/value/fire correlation. Scheduler capacity appears in the log and is absent from the resource model. Inspector “Monday office work” is invented and written as if it were given.

**Weaker experiment and validation choices.** Nested MC (50–100 outer × ≥20 inner × many scenarios, optionally up to 200 reps) has no compute budget, so the uncertainty procedure is not operational. KS/AD on ~31k cases will reject trivial differences; acceptance is then quietly moved to Wasserstein, which is unspecified. Validating simulated waits against log waits that were themselves inferred from completion-only data is partly circular. AND-concurrency in the tree is not checked against actual interval overlap in the log (P001 is sequential planning then fire). SLA cutoffs are invented and sit below several reported variant p90s, so baseline compliance may already miss the 90%/80% targets. E1’s 0.42 missing-doc rate is unexplained (overall vs Simple-only).

**What still holds.** Arrivals as a clustered NHPP, exogenous applicant/objection delays, calendars as first-class constraints, D10 sub-additivity, CRN streams, heavy-tail handling, out-of-sample plus natural-experiment validation, and an explicit non-optimality statement are all the right instincts. The skeleton is modular enough to be a real starting point, but it is not calibrated, not internally consistent on resources/time units/routing types, and not safe to use as a decision engine as written.
