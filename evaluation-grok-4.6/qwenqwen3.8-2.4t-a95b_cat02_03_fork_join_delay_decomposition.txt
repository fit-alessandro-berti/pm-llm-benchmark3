**8.4**

The final write-up is analytically strong: the fork-join math is internally consistent, the case table and the four worked examples check out, critical-branch counts are correct (A 2 / B 8 / C 2), and the answer does not confuse large mean service with path control. Double-counting is defined correctly (\(Q_{ci}+S_{ci}+W_{ci}=H_c\); \(\sum W\) is parallel slack, and F07’s \(77>75\) is a real illustration). Counterfactuals use max-join logic, report zeros when another branch remains critical, and treat CF1/CF2 savings as upper bounds if \(F\) does not pull forward.

It is not near-flawless under a strict reading.

**Unclarities / evidence gaps.** Section 4 asserts that some downstream wait is explained by the same-resource predecessor and some is not, but never shows the case-level split. That claim is therefore stronger than the presented evidence. The same section’s capacity remark (two \(F\) resources, constant 20-minute service) is left qualitative; arrival intensity versus service capacity is not computed. “Abort assumptions made explicit” is a leftover heading and reads as sloppy.

**CF3 is only loosely a capacity model.** “Eliminate \(D_c\)” (and a 50% cut) is a legitimate bound, and the text warns that policy holds may remain. It is still not a resource-constrained redesign: no recomputation of \(F\) starts from join-ready plus F1/F2 residual availability, so “adding capacity” and “deleting a delay column” stay conflated.

**Python is complete relative to the spec, not robust.** One block builds the table, decomposes, ties \(A\prec B\prec C\), runs the three CFs, builds an interval frame, and calls `format_dataframe` / `get_service_time`. A top-level `import pm4py` means none of the pandas tables print if PM4Py is missing; `get_service_time` is version-sensitive; numpy arrays stuffed into DataFrame columns are brittle; there is no printed check that \(T=U+H+D+V\).

**Smaller nits.** Sync waits are omitted from the main case table (allowed, but weaker for the double-counting claim). Utilization and “new bottleneck” talk in §5 is necessarily speculative given unobserved branch calendars; that uncertainty is labeled, but still thinner than the rest of the piece.

No material arithmetic error turned up in the final tables. The score is held down by the unshown resource-wait claim, the soft CF3 operationalization, the heading glitch, and the fragile PM4Py wrapper—not by the core delay decomposition.
