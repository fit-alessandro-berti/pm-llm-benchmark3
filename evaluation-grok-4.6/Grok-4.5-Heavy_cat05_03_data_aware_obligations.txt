## Formalization is internally inconsistent

The rule table, the pseudo-logic, and the code do not implement the same predicates.

- **R1 “material change” is overloaded.** §1 and `latest_material` treat HIGH/PEP/jurisdiction flips as material. R4 defines materiality as an amount increase >20% relative to the last review. Mixing activating changes into R1’s invalidation predicate is an interpretive expansion the log never tests, and the code does not implement it anyway.
- **`latest_material` is underspecified.** “`amount_at_last_review`” is not bound (review before the update? before release?). That is the whole of R4.
- **R2 table vs R2 logic.** The table requires Enhanced_Review after the activating change. The quantifiers only require `ER ≺ CA ≺ Release`. An Enhanced_Review performed while risk was still LOW would pass the formal check.
- **R2 missing-data rule is too coarse.** “Unknown risk or type that leaves HIGH/PEP possible → INDETERMINATE” fires even when risk is already known HIGH and type is unknown. The trigger is already decided.
- **R3 is written as a trigger and coded as a violation.** The formal rule also requires a *prior* screen (`∃ screen₀ ≺ lu`). A list update with no earlier screen would not fire. That matches a literal reading of “after the latest Sanctions_Screen,” but it is a hole and should have been named.

These are not cosmetic. The artifact’s job was to make the rules machine-checkable. It did not converge on one meaning.

## The code does not implement the rules it claims to check

The pandas/PM4Py skeleton meets the eight mechanical requirements (StringIO, `format_dataframe`, forward-fill, release snapshot, last-event trackers, coarse R1–R4 flags, exemption join, DECLARE caveat). Usefulness is undercut by logic bugs.

1. **R4 is wrong.** Materiality is `raw_amt / prev_known_amt > 1.20` against the *immediately previous* amount. `amt_at_last_review` is written and never read. Two sub-20% increases that compound to more than 20% since the last review would be missed. That is exactly the obligation R4 states.
2. **Same-timestamp order is abandoned in the checkers.** State is built in `(timestamp, event_index)` order, then `last_enh > last_material` compares timestamps only. Equal timestamps make `er_after_material` false even if the review is later by `event_index`. §1’s central claim is not implemented.
3. **R3 does not test that the list update added the *current* jurisdiction.** Any `Sanctions_List_Update` after the last screen is treated as an R3 hit.
4. **Exemption quality is baked in as STRONG/WEAK.** That is a narrative lookup sitting next to the instruction not to hard-code classifications. Leaving EX-77/EX-88 as evidence notes and forcing `REVIEW_REQUIRED` would have been cleaner; they already do that for every exemption reference, including TX-302, which their own analysis says is independently compliant.
5. **`pm4py.discover_declare` is unguarded.** If the API is absent, diagnostics already computed are lost.
6. **`unknown_amount` short-circuits to `REVIEW_REQUIRED` even when jurisdiction is DE** and R1 cannot fire.

None of these fire on *this* log, which is why the printed flags would likely match the table. That is luck, not a correct checker. A useful PM4Py artifact had to survive a slightly different amount path or a same-timestamp material update. This one would not.

## Residual case-analysis nits

No classification is outright wrong. A few confidence/status choices are sloppy.

- **TX-305 confidence “Medium” is confused.** The correct label is INDETERMINATE with *high* confidence. Medium mixes uncertainty about the facts with uncertainty about the meta-label.
- **TX-310 as a firm NONCOMPLIANT overstates a contradictory record.** Certificate-after-release plus a conflicted requester is enough to *reject the exemption*. The problem also says there is no canonical answer under contradictory evidence. Medium confidence plus an INDETERMINATE alternative almost saves this; the table still presents NONCOMPLIANT as the finding rather than a defended lean.
- **TX-302’s exemption path is called “redundant” and then the code still refuses to auto-clear it.** Harmless, but it shows the checker is not a formalization of §3.

## Net

The narrative compliance review is high quality: event-time state, R4/R5/R6, and the EX-77 vs EX-88 contrast are handled like an auditor who read the policy. The formal layer and the code were supposed to pin that reading down. They do not. Unused review-baseline amount, timestamp-only comparisons after a long lecture on `event_index`, and a three-way split on what “material” means are enough to keep this well below a top-band score.
