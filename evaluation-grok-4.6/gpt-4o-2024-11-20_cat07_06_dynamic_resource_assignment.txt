## Section 2 — the policy is not executable

An auditable policy needs a defined case order, eligibility predicate, scalar scores, combination rule, and exception path. This one has labels for those ideas and almost no mechanics.

- Cases are processed “for each case” with no stated order. Ranking by urgency is mentioned and then not used as the loop order, so the 4-assignment cap is path-dependent and unauditable.
- SLA formula multiplies by `case_priority`, which is a categorical string (`urgent` / `high` / `normal` / `low`). That expression is not defined. Priority is then counted a second time in the `1.0 / 0.75 / 0.5` term.
- Skill score uses `resource_skill - required_skill`, but `required_skill` in the log is a **skill name**, not a level. Even if a level were invented, `max(0, skill - required)` collapses trainee and competent into the same 0 whenever they are at or below the implicit bar.
- Continuity uses `handover_cost` as if it were numeric; the data are bands (`high` / `medium` / `low` / `none`).
- Training is folded into skill match instead of being its own scored term, despite the required outline.
- Resilience is a sentence, not a test (no specialist utilization cap, no team load check, no “second specialist reserved” rule).
- There is **no weighted objective**. Without weights, two reviewers cannot reconstruct why C003 moved and C016 did not.
- Tie-break text is broken: “lowest current open cases  highest skill level  highest training priority  lowest overtime risk.”
- Exception handling is “escalate,” with no trigger, no fallback pool, and no supervision protocol.

A policy that cannot be replayed from the log is not explainable in the sense the question asked.

## Section 7 — PM4Py sketch is wrong and incomplete

The question named specific functions. The sketch omits most of the ones that would actually inform the policy: `discover_organizational_roles`, `discover_activity_based_resource_similarity`, `discover_batches`, `insert_case_service_waiting_time`, `get_variants`.

What is written would not run as used:

- `filter_case_performance(..., performance_value=3, attribute="sla_deadline")` is not that API. It filters case **duration**, not an SLA attribute.
- `filter_event_attribute_values` is called without `level` / retain-vs-exclude semantics.
- `get_service_time` is invoked with no resource or aggregation logic.
- Nothing computes skill mismatch, owner change, overtime exposure, or policy deviation from `assignment_reason`.
- Nothing “learns” a policy; the comments only rediscover generic SNA and filter on a label that the policy itself would have to write.

So the implementation section does not show how event-log data would learn **or** audit the policy.
