## Material analytical errors

**1. T-409 profile A→I is silently treated as CERTAIN_PASS.**  
§3.2 says omitted pairs are CERTAIN_PASS at ζ=2. T-409 A→I is about [0, 17] min vs [4, 16] min. That is POSSIBLE_VIOLATION (too fast and too slow). This is a wrong label, not a formatting shortcut.

**2. T-409 S2 duration contradicts the stated precedence rule.**  
The write-up says it restricts to `Alert ≤ Start`. Under that constraint Start is about [15:59:58, 16:17:00] and I→C is about [18, 35] min, not [18, 43] min. The extra 8 minutes comes from allowing Start before Alert, which §1.2 claimed to forbid. S2 still CERTAIN_PASSes, so the classification luckily survives; the duration does not.

**3. ζ-sensitivity for A→C is wrong.**  
T-402 A→C is ≈62 min. At ζ=1 the band is [1980, 3420] s = [33, 57] min, so this is CERTAIN_VIOLATION, not a “border effect.” T-408 A→C is 65 min and is also a ζ=1 CERTAIN_VIOLATION. The text says only T-402 and T-403 show A→C ζ=1 effects and that most A→C pairs stay CERTAIN_PASS across ζ=1,2,3. That is false for T-408.

**4. T-409 is missing from the SLA tolerance matrix.**  
[0, 17] min vs 15 / 17 / 20 min is POSSIBLE → POSSIBLE → CERTAIN_PASS. The spec required discussing every case whose class changes.

**5. T-406 alternative semantics are not tested.**  
If the 5-minute mobile delay is late *recording* rather than uncertain *occurrence*, Start stays about [12:08:30, 12:19:30] UTC and S2 becomes ≈[32.5, 43.5] min — CERTAIN_PASS, not POSSIBLE_VIOLATION. The prompt flagged this as a substantive assumption. Stating one reading and never showing the other is incomplete.

**6. T-407 causal bound is over-committed and misdescribed.**  
“Intersected with the Investigation_Start interval” would yield ≈[14:16:58, 14:17:02], i.e. ~0 latency and S1 CERTAIN_PASS. The table instead uses [13:59:58, 14:17:02] and [0, 17.1] min. The prose and the numbers do not match. The prompt also says the receipt-before-start assumption is “plausible but not directly logged”; treating it as a hard cut without an INDETERMINATE / no-constraint branch overstates what the evidence supports.

**7. Approximate envelopes used as if they were the analysis.**  
HUB true time is ±1.5 s, reported as ±2 s, then durations are “≈[12.0, 16.5] min” etc. T-401 S1 min is 11 min 58 s, not 12.0. Harmless for some labels, not for a task that asked for interval reasoning and forbade collapsing uncertainty. T-408 I→C at ζ=2 actually straddles 3300 s by a few seconds ([3296, 3304] s); that POSSIBLE_VIOLATION is a boundary artifact and is never discussed in §6.

**8. ζ=3 is over-claimed.**  
T-406 A→I [3.5, 19.5] min vs ζ=3 [1, 19] min remains POSSIBLE_VIOLATION. T-407 A→I [0, 17.1] min still undershoots the lower bound. The text says ζ=3 makes most anomalies disappear except T-408.

## Section 5 code does not implement the paper

This is the largest single deduction. The executable block is required to reconstruct the events, normalize intervals, represent DST alternatives, derive classifications, build a labeled midpoint log, call PM4Py, and compare. Failures:

- T-404 inferred `Investigation_Start` is absent, so S1/S2 become INDETERMINATE in code.
- T-407 inferred `Alert_Received` is absent.
- MOBILE-LON +5 min entry delay is absent, so T-406 S2 in code is CERTAIN_PASS (~43.5 min max) while the narrative says POSSIBLE_VIOLATION.
- DST ingestion filtering is absent. Each T-405 event keeps both CEST and CET intervals; pairwise durations include ~0 and ~100 min I→C. Code S2 for T-405 is POSSIBLE_VIOLATION; the narrative says CERTAIN_PASS.
- Midpoint of min/max across both folds for T-405 is ~30 minutes off. That is not a small lossy approximation; it is a different event.
- Union intervals are collapsed to a single [global min, global max].
- `max(0, Δ)` turns order-impossible pairs into 0-length durations instead of dropping them.
- Sensitivity (SLA +0/2/5 min, ζ=1/2/3 interval classes) is not computed.
- The PM4Py “comparison” is a print statement plus `try/except`. No actual juxtaposition of midpoint diagnostics with interval labels.
- The midpoint log still contains `Investigation_Complete` and `Alert_Sent`, so profile pairs will not match the supplied activity names.

A reader who ran the code would not recover the §3 table. That violates item 5 of the required output.
