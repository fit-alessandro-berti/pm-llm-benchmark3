**3.0**

The write-up follows the required heading skeleton and sometimes states the right fork-join *idea* (join = latest branch end; do not treat longest mean service as influence). Almost everything built on that idea is then wrong, internally contradictory, or unimplemented. Under a strict reading this is a structurally complete but analytically unreliable answer.

## Fatal definition and accounting errors

The queue formula is reversed: `queue[c,i] = max(0, fork_release − start)` is the opposite of the stated rule that a branch may start *after* `fork_release` because of its own queue. The correct duration is `start[i] − fork_release`. The `max(0, ·)` form would zero every observed B/C wait. Section 2’s queue *values* are actually `start − fork` (correct), the worked lines write the inverted subtraction and then invent a positive result (`08:25 − 08:45 = 20`), and the Python uses the inverted formula. Three artifacts, three different meanings.

The double-counting paragraph is not a proof. `join_ready` is a timestamp, so “overstates elapsed time by `2·join_ready`” is not a duration identity. Summing the three sync waits equals `3·join_ready − (end_A+end_B+end_C)`, not `2·join_ready`. The no-double-count partition of case time is

`total = upstream + max_i(queue_i+service_i) + downstream + final`,

and `sum_i(queue_i+service_i+sync_i) = 3·fork_join`. That is the identity that should have been shown.

## Section 2 does not survive arithmetic

Required columns exist; several are not what they claim.

- `join_ready` is neither a clock time nor `max(end)−fork` (F01 should be 09:00 or 50 min, not 60; F04 should be 09:52 or 57 min, not 65; F11 should be 11:30 or 50 min, not 68). The column is an unexplained integer series.
- `downstream_queue` is right only for F01 (8). True values are 8, 15, 15, 18, 10, 15, 15, 15, 15, 20, 20, 10. The table’s 65–100 minute waits are inventions. The four worked cases compute the *correct* downstream (15, 18, 15, 20) and then the table contradicts those workings.
- `total_flow_time` is wrong for F05–F07 and F09–F12 (110, 120, 130, 120, 115, 110, 125 — not 130, 140, 150, 140, 155, 150, 165). Worked F07/F11 repeat the bad totals.
- **Critical branch is mislabeled whenever C is last.** F04: `max(09:45, 09:35, 09:52) = 09:52` is C, then the text says “critical = A”. F08: C ends 10:50 after A at 10:45, table still says A. That is not a rounding slip; it is failing to read the argmax the author just wrote.

True critical counts: A 2/12 (F01, F11), B 8/12, C 2/12 (F04, F08). Queue and service columns happen to be correct; that is not enough to salvage a decomposition table whose join, wait-after-join, flow time, and critical labels disagree with the data *and* with the worked section.

## Section 3: aggregates and influence are built on the bad labels

- B mean service is 37.5, not 36.3; C is 20.17, not 19.8; B mean queue is 19.17, not 19.6; C mean queue is 10.42, not 11.3.
- Mean sync wait is inverted in both number and meaning. Correct means: A 11.0, B 4.3, C **30.4**. Reporting C sync = 0.0 treats the earliest-finishing branch as if it never waits. By definition the *critical* branch has sync 0; C’s large sync is exactly the evidence that C does *not* set `join_ready`.
- “C never last” is false. Influence ranks that start from a 0% C frequency are not a near-tie issue; they omit a real critical branch.
- Required tail contribution to `join_ready` is absent. “Influence_score” 1/2/3 has no formula. Downstream masking of branch improvements — explicitly required — is not analyzed (F5/F8/F9/F11 waits are partly F1/F2 occupancy; F1/F02 already wait with a free server, so some “queue” is policy or unobserved work).

Qualitative line “do not equate longest A service with control” is the right slogan; B really is the modal last branch. Frequency for B is accidentally correct only because the two C cases were dumped onto A.

## Section 4: counterfactuals ignore slack, occupancy, and their own code

1. **A −20% service** is −10 min on A_end. It helps only if A is last (or last within 10 min). Real A-critical cases are F01 and F11, not {F01,F04,F08,F11}. F01 slack to B is 5 min, so the gain is 5, not 10. F04/F08 stay C-critical. Claimed 40 min total is wrong; secondary effects are not “none” (earlier join can only increase measured downstream wait if F start times stay put).
2. **B queue −50%** does not save `0.5 × mean(B_queue)` on every B-critical case. Slack binds on F05 (12.5 requested, 10 available) and F10 (10 requested, 5 available). A serious CF would recompute `join_ready` and then ask whether `final_start` can move. The text never does.
3. **Halve downstream to 47.5 min and save 47.5×12 = 570** is arithmetic on the fictitious table (true mean downstream ≈ 14.7 min). It also treats a capacity add as a uniform haircut with no contention model.

The Python CFs never rewrite the timestamps that define flow time (`A_end` unused in CF1; all three CFs keep original `final_end`). Printed savings are identically zero and cannot support Section 4. CF2 even *increases* `downstream_queue` when join moves in — that is the masking mechanism — and the prose never interprets it.

## Section 5: redesigns rest on false inventory and invented ops metrics

The process already has **two** final resources, F1 and F2, both busy in the log. “Add a second final-station resource” and “pilot F2 in standby” are category errors. Utilization “~90% → ~45%” is not computed (each resource does 120 min of 20-min jobs; busy-span utilization is ~66–67%, not 90%). Redesign 1 says B queues drop via pooling while “laboratory and stress-test resources remain unchanged; no new bottleneck,” which contradicts itself. Percentile and “~11% cycle-time” claims are not derived from the 12 sojourns. Neither recommendation is a measurement-first pilot of the actual binding constraint (B sojourn vs. residual F wait that is not occupancy).

## Section 6: the code cannot reproduce the paper

It builds the CSV and attempts the eight mandated steps, but:

- queue clip implements the reversed definition;
- `critical_branch()` would correctly return C on F04/F08, so a run would *not* match Section 2;
- CFs do not move `final_end` (or `A_end` in CF1), so they do not estimate flow-time savings, and per-case savings are not printed;
- `format_dataframe(..., timestamp_key='start_timestamp')` treats start as the event timestamp, which is the wrong column for interval service;
- comments gesture at why DFG ≠ sync wait, but the surrounding calculations never produce sync wait.

A “reproducible” block that cannot regenerate the reported table or the reported CF totals fails the section.

## Section 7

This is the only part near the quality bar: causality vs. contention, unknown branch capacity, unlogged preemption, and F wait as queue vs. release policy are all named, plus small-n tail instability. It does not offset the broken decomposition.

## Bottom line

Format compliance and a few correct building blocks (upstream, service, F01–F04/F08 totals, B as the usual last technical branch, limits of inference) keep this off the floor. Hypercritically, inverted queue algebra, a self-contradictory argmax on F04, erasure of C, fictitious join/downstream/flow columns, inverted sync means, non-operational counterfactuals, and a redesign that invents a missing F resource are not minor nits. They make the delay partition and the influence ranking unsafe to use.
