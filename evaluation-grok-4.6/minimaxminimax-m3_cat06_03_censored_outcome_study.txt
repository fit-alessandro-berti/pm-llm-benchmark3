**5.8**

The write-up has the right *shape*: it refuses to recode rejects/withdrawals/opens as non-default, keeps the full 48,000 in view, separates several missingness mechanisms, bans post-decision fields, and uses a temporal rather than random split. That is why this is not a low score. Under a strict reading it is still far from clean.

**Target and estimand are internally inconsistent.** The primary object is described as a 90-day post-activation CIF, then as “structurally zero” for non-activated cases, then as “undefined,” then as a policy-conditional score the model should still emit. Those are three different questions. A CIF with origin at application start is not the same object as a 90-day risk with origin at activation; competing risks that *prevent* activation are not the same as left-truncation *at* activation. The text uses all of these at once. Sensitivity 2 is also backwards: the 21,600 already *are* the activated mix, so “reweight them to the activation-mix distribution” does not correct selection.

**Censoring is treated too loosely.** Delayed ascertainment (horizon reached, feed late) is not ordinary right-censoring. Collapsing them, and never using `label_available_at` in the actual cohort logic, blurs a distinction the prompt asked to keep. MAR is not “partially testable” by comparing observed predictors of feed arrival; that checks imbalance, not MAR. Linked transfers that can re-enter under a new case id are noted and then not handled as a unit-of-analysis problem.

**Validation does not actually respect maturity or regime.** Train through 2025-01-31 uses labels that, in calendar time, are only known months later; that is never stated. Test A (starts Oct–Dec 2025, extract 15 Feb 2026) is full of activations whose 90-day window and 7–35 day feed cannot have matured. The only mature post-policy window (Jul–Sep 2025) is parked in an unused gap, so the current policy is never trained *or* cleanly tested. Calling Test A “in-regime” is misleading: train is pre-July policy.

**The skeleton would not implement the design.** Classifying outcome by *last* activity is process-wrong: after activation the log still has Contract Signed (before), Collections Contact, and Default Recorded, so most activated (and many defaulted) cases become `"open"`. `label_mature` ignores `label_available_at`. `default_90d` is never attached to the case table. `pm4py.format_dataframe` output is renamed off `case:concept:name`, then passed into PM4Py APIs that expect the standard columns. `get_prefixes_from_log` is invoked on a DataFrame, and the returned prefixes are discarded. Features are the *first event row*, not prefix aggregates. `extract_temporal_features_dataframe` is a *system-level* time-grouped extractor, not per-case timing features; merging it on `case_id` is an unjustified use of an API the prompt explicitly asked to use only when the interpretation holds. Same-day `documents_total` and as-of `risk_score` are audited and then not implemented.

**Smaller but real nits.** Prediction time is “first Credit Review,” “first exit,” or “last event ≤ extract date” depending on the paragraph; the last option lets long-open cases use years of post-decision history. Resource experience is “repaired” with a hire-date table that is not in the data. “This is the only defensible formulation” is overclaimed.

The leakage table, the 48,000 flow, the refusal to treat reject as non-default, and the deployment DGP caveats are the strongest parts. They are not enough to offset a confused estimand, an immature/out-of-regime test, and a pipeline that would mis-label the cohort and misuse the PM4Py calls it showcases.
