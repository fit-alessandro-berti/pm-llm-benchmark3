**6.9**

This is a strong, process-aware design that correctly refuses to treat omitted applications as non-defaults and that keeps an as-of discipline in prose. It is not nearly flawless. Several design claims contradict the skeleton, the primary temporal test for the migration regime is empty under the authors’ own maturity rule, and a few “leakage checks” do not actually check leakage.

## What is actually sound

The primary estimand is honest: \(P(D\le 90\mid X_{\text{prefix}}, A=1, \text{historical policy})\), not “default for every application.” Rejected, withdrawn, open, and transferred cases are competing or undefined outcomes, not zeros. Delayed feeds, activation selection, transfer, and permanently missing partner feeds are separated. The leakage table covers every required field and several extra ones (`data_extract_time`, linkage timing, full-case DFG). The code uses real PM4Py APIs, does not invent a survival function, and keeps DFG/variant discovery on train prefixes only.

Those are necessary strengths. They are not sufficient for a high score under a strict reading.

## Material design flaws

**1. The migration-era test cannot contain the primary target.**  
Extraction is 15 Feb 2026. Eligibility requires `activation + 125 days ≤ AS_OF`, so activation must occur by 13 Oct 2025. Cases that *start* on or after 15 Oct 2025 cannot activate before they start. Under the implemented rule, `test_migration_era` is empty for the binary mature-default outcome. The text softens this to “will not include many late-2025 activations.” That is false: it includes none. A serious backtest would split on activation or prefix time, shorten the feed-lag only in a named sensitivity, or treat post-migration vintages as process/shift monitors rather than a default-outcome test.

**2. Splitting on case start contaminates the pre-policy train set.**  
A case started in March 2025 can activate after 1 July 2025 and realize its 90-day outcome entirely under the new policy, yet it is labeled `train`. Outcome windows, not start dates, determine the regime of \(P(D\mid X, A=1)\). The design never closes this gap (buffer after last train start, split on activation time, or regime-at-activation as a covariate/stratum).

**3. Sequential as-of backtesting is specified and then not implemented.**  
Section 2 requires re-running inclusion at each historical cutoff so later labels cannot enter earlier training vintages. The skeleton builds one global `AS_OF`, one `eligible` table, then slices by start date. That is a retrospective dump with a time cut, not the backtest the validation section describes.

**4. Section 3 and the code disagree on ascertainment.**  
The text allows positives “once validly observed” while holding negatives to a 35-day grace period. That is label-dependent sampling and will inflate early-window default rates. The code is better: both classes need 125 days. The writeup therefore proposes a biased rule that the implementation quietly abandons. A methods document that contradicts its own pipeline is not a reliable study plan.

## Implementation and spec problems

**5. Written as-of rules are not coded.**  
Section 2 requires `event_time ≤ data_extract_time`. The code only requires `timestamp ≤ AS_OF` and `data_extract_time ≤ AS_OF` (and keeps rows with missing extract time). Same-batch future snapshots can still enter.

**6. Prefix-ID handling is a silent failure point.**  
`get_prefixes_from_log` is version-dependent: some builds rewrite case IDs or emit all prefixes up to \(k\). The comments admit this; the joins on `case:concept:name` do not preserve an original ID. `model_table` can become empty without failing an assertion.

**7. The “hard temporal assertion” is tautological.**  
`prefix_end` is the per-case max timestamp, so `TS ≤ prefix_end` cannot fail. It does not prove that prefixes exclude post-landmark warehouse columns or post-cutoff events.

**8. The skeleton overruns the required length.**  
The task asked for about 80–160 lines. The block is ~220–240 lines, yet still omits elapsed-time prefixes, partner-feed flags, and per-cutoff rebuilds that the prose treats as essential.

**9. Several coded features do not measure what they claim.**  
`was_duplicate` is computed, then those rows are dropped, so `duplicate_indicators` is identically zero. `groupby.apply(case_summary)` is a known pandas footgun (grouping column inclusion, stacked output). Activity mapping is an incomplete placeholder, which is acceptable only if the rest of the pipeline is tight; it is not.

## Smaller but real conceptual gaps

**10. Unit of analysis is blurred.**  
“Application / activated account after resolving linked identities” mixes a process instance with a person-level lineage. Partial (60%) linkage plus partner missingness makes merged units a selected, error-prone subset. The primary analysis should keep the application ID and treat linkage as a sensitivity, which the text half-says and the code does not do.

**11. Same-event leakage is ignored.**  
If `risk_score`, `decision_reason`, or `final_limit` are written on the Credit Review event that is also the landmark, “latest value at prefix time” still leaks the decision. The audit treats leakage as a column-timing problem only.

**12. Scoring every application with \(P(D\mid X, A=1)\) remains undertheorized.**  
Flagging “extrapolation” is not a decision rule. Without a pre-specified support region, a second-stage activation model, and a protocol for what the lender may display on likely rejects, the operational story still oversells the estimand the paper correctly refuses to identify.

**13. Delayed labels and ordinary censoring are distinguished in §3 and then collapsed** in the cohort table and `state()` (one `mature_by_time` bit). The source snapshot also lumps them; a design that claims to separate mechanisms should not immediately merge them in the only machine-checkable accounting.

## Bottom line

The answer would not commit the failure modes named in the rubric (train only on 21,600 uncritically, call rejects non-default, use collection fields, random-split across regimes). That puts it well above a failing design. Strictly graded, it still has a broken migration test, a train window that mixes policies, prose/code contradictions on maturity and as-of filters, a non-informative leakage assert, and a skeleton that misses the length band while remaining operationally fragile. Those are not polish nits; they are the difference between a careful memo and a study that could be executed without silently empty folds or shifting estimands.
