## Grading rationale

The submission is complete, well-structured, and strong on architecture, conflict analysis, resource/data checks, and deployment thinking. Under a hypercritical standard it still accumulates several material correctness failures that keep it well below the top band.

### What is strong
- **§1 R5/R6 handling** is one of the best parts: three resolutions, an explicit choice (C), and clear compliance risk. The 12h±2·6h = 24h link to R6 is insightful.
- **§2 mapping** covers R1–R12 with authoritative-layer discipline and honest limitations (especially R5/R11).
- **§3 design intent** is right: backbone in a ProcessTree; clarification, escalation/opinion, and post-activation change left out of the tree on purpose, with disclosure.
- **§6–§7** are solid: correct seconds conversion, zeta semantics, executable SoD / emergency / R11 checks, and explicit missing-attribute policy.
- **§9–§10** show real hybrid-modeling maturity (vacuity, support/confidence misuse, check order, surfacing policy-dependent findings).

### Material defects (score drivers)

1. **DECLARE `exactly_one` is wrong for mutually exclusive terminals**  
   Encoding `exactly_one` for *both* `Activate Vendor` and `Reject Vendor` (and for `Release First Payment`) fails every pure accept trace (no Reject), every pure reject trace (no Activate / no Release), and T8-style fragments. LS correctly uses `{0,1}`; DECLARE does not. This directly contradicts R10 and the verdict matrix (T1–T3 marked DECLARE `pass`).

2. **Model vs. verdict inconsistency on R5 approximation**  
   The model includes global `precedence(Obtain Legal Opinion, Activate Vendor)` and correctly calls it “too strong,” yet T1/T2/T4/T5 are scored DECLARE `pass`. Under that rule they must fail (Activate without prior Opinion). T6’s DECLARE cell is hand-waved as “pass under R6 / fail under R5” while the dict always contains the strict rule. The matrix is not a faithful evaluation of the published `declare_model`.

3. **ProcessTree code is structurally broken**  
   Leaf objects (`av`, `rfp`, `co`, …) are reused across XOR branches. Each node gets a single `.parent`, so the tree is not a valid ProcessTree. Separate leaves per occurrence are required. This is an implementation defect, not a nit.

4. **Procedural conformance story is incoherent**  
   Clarification, `Sanctions Escalation`, and `Obtain Legal Opinion` are deliberately outside the tree, but T2/T5/T6/T7 are marked procedural `pass`. Standard alignment would record log moves. §10 then says to use alignment to catch “activities outside the backbone,” which would fail those same traces. Projection-before-replay is never stated as a rule, so the procedural column is not well-founded.

5. **DECLARE container shape**  
   Task text asks for activity / tuple *keys* with `{support, confidence}` values (dict-of-dicts). The answer uses lists of `(constraint, params)` pairs. “Valid-looking” softens this, but it is still non-idiomatic relative to the stated PM4Py reminders.

6. **Temporal arithmetic slips**  
   T1 uses Release’s absolute hour (80) instead of 809 = 71h; T4 uses 70 instead of 709 = 61h. Outcomes stay `pass`, but the working is sloppy.

7. **Smaller modeling nits**  
   - `exactly_one` / R10 tension never cleaned up in §9.  
   - `activ_freq` caps for clarifications (`{0,1,2,3}`) are arbitrary.  
   - R2 “exactly one of the two approvals in an accepted case” is only partly on the backbone; DECLARE only has noncoexistence.  
   - Sharing one `Verify Bank Account` freq set `{1,2}` does not distinguish pre- vs post-activation instances (acknowledged, but still thin).

### Why not higher
Near-flawless work would need a DECLARE model that actually matches T1–T8, cardinality constraints that allow 0/1 terminals, a parent-safe ProcessTree, and one explicit rule for “project to backbone vs. full-trace alignment.” Those are not polish items; they break executability and internal coherence.
