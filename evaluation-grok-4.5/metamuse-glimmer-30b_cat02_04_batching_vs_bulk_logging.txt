### 3. PM4Py code is not faithful / not executable as specified

Hard requirements:

- call `pm4py.format_dataframe` and `pm4py.discover_batches`
- run batch discovery under ≥2 `merge_distance` and ≥2 `min_batch_size`
- compute independent pandas diagnostics (overlap rate, start/end equality groups, recording lag, granularity indicators, queue build-up)
- preserve clusters with missing/suspect lifecycle semantics
- print a compact cluster-level diagnostic table **and compare it with PM4Py’s detected batch categories**

Problems:

- `pm4py.discover_batches(..., merge_distance=md, min_batch_size=mbs)` is almost certainly the wrong API surface (PM4Py batch discovery typically uses a parameters dict / different entry point). The code would fail in a real environment.
- It never prints or compares PM4Py batch *categories* (simultaneous, start, end, sequential, etc.) against the cluster diagnoses—only `len(batches)`.
- “Timestamp granularity indicators” are reduced to reprinting the documented `precision` string, not measuring observed granularity (unique timestamp counts, residual structure inside bins, second-level stagger, etc.).
- No adjacency / chain-start diagnostics for G4/G8-style sequential work.
- No handling discussion for zero-duration events (G6) beyond leaving them in the frame.
- Resource is never passed into the formatted event log in a PM4Py-standard way (`org:resource`), so batch discovery by resource is dubious.
- No try/except, no version note, no fallback—yet the analysis pretends this is a working verification path.

That section was supposed to be a core quality differentiator (“combine PM4Py batch discovery with independent data-quality evidence”). It is mostly scaffolding.

### 4. Analytical overconfidence and mis-ranking

Evidence supports a *physical batch-capable cell with identical lifecycle stamps*, not proof of simultaneous physical execution. PLC identical start/complete can be scan-cycle or recipe-level logging. Ranking “genuine simultaneous batch” at 90 with “no data correction needed” overstates. Second place should more clearly include logging/scan-batch alternatives. “Service is batch level; optional split” is a correction need, not “No.”
