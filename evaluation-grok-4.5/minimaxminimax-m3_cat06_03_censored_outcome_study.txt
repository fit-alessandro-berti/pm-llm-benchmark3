**7.1**

## Grading rationale (strict)

The submission is a serious, process-aware design that correctly refuses the main failure modes (train-only on 21,600; rejectnon-default; random split; post-outcome fields). Sections 2, 3, 6, 7, and 8 are genuinely strong. It is not near-flawless: conceptual slips on the primary estimand, several material skeleton bugs, and a gap between the feature narrative and the code keep it well below the top band.

### What holds up
- **Selection honesty:** Activation is treated as a selective observation mechanism; rejects/withdrawals/transfers/open are competing or censoring states, not fake non-defaults (mostly).
- **Cohort accounting:** 18,900+2,700+3,600+9,100+5,700+2,900+5,100 = 48,000 with roles assigned.
- **Censoring taxonomy:** Ordinary right-censoring vs delayed feed vs activation selection vs transfer LTFU vs permanent missing feed is clearly separated; testable vs untestable assumptions are stated.
- **Leakage audit:** Required elements are covered with keep/repair/drop and as-of rules (`final_limit`, `decision_reason`, `collection_status`, future events, `documents_total`, `risk_score`, resource experience, label fields).
- **Validation:** Temporal blocked split, explicit post-policy gap, migration sanity, calibration/subgroup/PSI, and a clear attack on random case splits.
- **Limitations / deployment:** Association vs selection vs counterfactual is drawn; three feedback loops on the DGP are realistic.

### Deduction drivers (hypercritical)

**1. Target semantics contradiction (material)**  
Section 1 says for C/D/E/F the default probability is “structurally zero **(or undefined)**.” Zero and undefined are different claims. “Structurally zero” is uncomfortably close to the convenience error the brief forbids; “undefined under the observed policy” is the right stance. The primary estimand also oscillates between a post-activation CIF, a full-funnel multi-state process, and a policy-conditional hypothetical for non-activated cases without a single sharp identification statement (multi-state intensities vs left-truncation at activation vs two-stage P(activate)×P(default|activate)).

**2. Implementation skeleton is not faithful to §§4–5 (material)**  
- `default_90d` / `label_available_at` are never aggregated into the case table, so the skeleton cannot actually build event indicators or delayed-feed flags.  
- `pm4py.insert_case_service_waiting_time(tfeat)` is applied to an already-aggregated temporal feature table; that API expects an event-level log.  
- “Feature table” construction takes the **first event row** per case (`duplicated(keep="first")`) rather than prefix aggregates (loop counts, time-in-state, last pre-prefix `risk_score`, etc.)—far weaker than Section 5.  
- `outcome_state` logic is inconsistent: if `terminal_act == "Account Activated"`, `activation_time` should not be NaN; immature vs `activated_pending_feed` is not separable from the given snapshot fields as coded.  
- Cases missing `Credit Review` get NaT `pred_time` and are silently dropped by the timestamp filter, contrary to Section 4.  
These are not nitpicks; they break the “concrete enough to implement” bar.

**3. Cohort / maturity imprecision**  
The 3,600 bucket mixes “horizon not reached” and “feed delayed 7–35 days.” Section 2 keeps one row; the code invents a split without operational rules tied to `label_available_at` vs `activation_time + 90d`. Partner-originated permanent missingness is discussed in prose and under-specified in the pipeline (no `linkage` / partner flag path).

**4. Prediction-time definition is operationally fuzzy**  
“End of the first occurrence of Credit Review” / “first exit” can be a document-request exit, not a decision. That needs an explicit event rule (e.g., first CR followed by Accept/Reject/document request, with features frozen at that timestamp). Fixed-k vs elapsed-time is described, but the skeleton only half-implements one path.

**5. Secondary technical nits**  
- IPCW for unlinked transfers is named but not even stubbed (no weight columns, no truncation rule in code).  
- Some PM4Py call shapes look assumed (`extract_temporal_features_dataframe(..., include_case_id=True)`).  
- Leakage table in prose matches the required schema; the in-code audit collapses columns—minor.  
- Asserting `sum == 48000` couples the pipeline to the problem’s toy totals.

### Score band justification
Design quality alone would sit ~8.0–8.5 under normal grading. Under the requested strictness—estimand contradiction on non-activated outcomes, multi-state vs truncation underspecification, and a skeleton that would not correctly assemble labels, prefixes, or process features—the composite is **7.1**. Not a weak answer; not near-flawless.
