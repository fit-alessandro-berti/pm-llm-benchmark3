## Defects (why the score is held down)

### 1. Permissive model overshoots D5 and mislabels that overshoot (substantive)
D5 says SC may begin after **either** CC or ER (at least one), not after RO alone. The permissive POWL uses `RO  optSC`, which allows SC with **zero** checks complete. That is stricter than “broad domain rules” only if one ignores D5; calling it a “weaker D5 reading” is inaccurate. A domain-faithful permissive hypothesis would be an “after either” (OR-precedes) pattern, which is harder in pure StrictPartialOrder and was not attempted. They mark SC-first as “risky” and give it low confidence (~0.25), which mitigates but does not remove the conceptual error.  
**Impact**: Material on §5 boundary, §6 “why admitted,” §9/§10.

### 2. Validation suite labels are internally inconsistent (substantive)
SC-first is placed in the global `negative` list, yet the comment says permissive should accept it (`SC-first positive True`). “Negative” is therefore not a model-agnostic verdict nor cleanly model-specific. The suite still prints accept/reject, but it does not cleanly “check” a defined oracle. Minor API fragility (`play_out` args, metric names) is papered over with try/except — acceptable, but combined with the label muddle it weakens §8.

### 3. Conservative “unobserved = none” is true only inside a narrow bound (minor but overstated)

They mostly caveat this; residual overclaim is small.

### 4. Fitness “Perfect (1.0)” asserted for all three without qualification (minor)

Stating 1.0 as fact in the matrix before running code is slightly too brisk; “expected ~1.0 on alignments if encoding is faithful” would be tighter.

Several places lost operators (“DFG  concurrency”, “Language  seven”, arrows in prose). Readable from context, but sloppy relative to an otherwise formal answer.

### 6. No intermediate “SC after either check” hypothesis (minor–moderate)
