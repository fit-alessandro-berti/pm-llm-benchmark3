## Deductions (hypercritical)

### 1. Policy text vs code fidelity (material)
Hybrid policy is sold as **reserved P1 capacity** with primary pools and controlled overflow. The code implements **soft scoring** (P1 rank, lateness, slow-multiplier penalty, light fairness CV term) over the full qualified pool. There is no hard reservation state, no held idle slot, no explicit release rule matching Section 3/5 triggers. Monitoring asks for `reservation_state`, but the simulator never emits it. That is a direct claim–implementation gap on the recommended policy’s defining mechanism.

### 2. Section 4 metrics are not evidence-grade
The policy×scenario table is the evaluative core. Values are wide narrative bands (“500–720 min”, “80–95% P1_SLA”) labeled as estimates from “offered-load logic and the scaffold,” yet the write-up does **not** show the code’s printed comparison output or reconcile bands to seeds. Several cells look optimistic relative to the Section 2 overload story (multipliers, handovers, and chronic fragility vs high base P1_SLA for hybrid). Under strict rules—“use only supplied information,” “distinguish observations/estimates,” “exact numerical agreement less important than coherent calculations”—unanchored SLA bands presented in a results table are a serious audit weakness.

### 3. Capacity / delay internal tension under-discussed
Comparing **pre-multiplier** base minutes to active capacity correctly flags fragility, but actual resource minutes are base × multiplier (+ handover/setup treated as busy). Average multipliers on E/S/Validation paths are often >1, so true offered load is materially above 2721. Mean delays of many hours and same-day P2 SLA bands can still be reconciled via multi-day clearing, but the answer never closes this loop with a clear bound (e.g., residual backlog after 20:00, or fraction finishing next day). Overload is asserted; tail arithmetic is not tied tightly enough to the table.

### 4. Specialization design choices that overstate brittleness
Strict Software eligibility = **Emil only** (Chen/Farah excluded despite skill matrix) maximizes morning S/ES failure and flatters pooling/hybrid in U1/U3. That is a defensible extreme “fixed queues” reading, but it is not the only fair reading of “strict specialization,” and it is not stress-tested against a milder specialist pool. Similarly, strict Validation excludes Ada/Chen/Farah. Comparative advantage of hybrid is partly manufactured by an especially brittle baseline.

### 5. Python scaffold quality issues (not just “omitted mechanisms”)
- `random.Random` has no `.poisson`; fallback mixes RNGs and weakens seed reproducibility across blocks.
- Preemption is coarse: one interrupt attempt, weak “material P1 benefit” test relative to Section 3’s four gates; finish events for preempted jobs rely on stale-job guards (works, but fragile).
- Overtime is **always** folded into `shift_min` (+30), not activated under load—diverges from “limited OT” as a decision.
- Handover/team/setup are charged as **resource busy** time; prompt only guarantees elapsed delay—assumption should be labeled more sharply.
- Utilization denominator/`busy_active` accounting is approximate; fairness signal is weak relative to narrative.
- Large monolithic DES with many branches is not validated in-text; try/except around PM4Py is fine, but “reproducible” claims overreach without shown run artifacts.

These are not fatal for a “well-specified scaffold,” but the answer presents the table as if the scaffold underwrites it.

### 6. Smaller analytical nits
- U2 “Electrical 341  405” after double-then-renormalize is hand-wavy; renormalization does not yield a simple +64 on E minutes without showing post-renorm type shares.
- Objective B includes `skill_erosion_penalty` without operationalization anywhere in metrics or code.
- Parallel decision rules differ across Sections 3, 5, and code (`0.85 * target`, “10–15 minutes,” P2 `seq_cp > 75`) without reconciliation.
- Resilience column is qualitative with no explicit definition tied to Objective B regret.
- Arrival model: Poisson in code vs “deterministic expectations” for load—fine if labeled; multi-day spillover implications for SLA clocks could be clearer.

### 7. What is *not* wrong (credit retained)
No invented process facts outside the prompt; uncertainty scenarios are used; specialization vs pooling tension is central; Validation-as-downstream-bottleneck and handover burden are first-class; PM4Py usage matches the prompt’s required calls and the case-level labeling warning; pilot plan protects P1 and avoids unsafe big-bang rollout.
