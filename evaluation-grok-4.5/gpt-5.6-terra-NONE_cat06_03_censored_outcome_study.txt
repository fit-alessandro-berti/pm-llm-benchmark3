**8.4**

## Grading rationale (strict)

This is a strong, professionally structured design that hits the spirit of the task: activation selection is treated as central, rejected/withdrawn/open cases are not fake non-defaults, leakage is audited seriously, validation is temporal, and the PM4Py skeleton is concrete. Under hypercritical review it is **not** near-flawless.

### What is genuinely strong
- **Target honesty:** Primary estimand is explicitly conditional on activation and mature observation; alternatives (multi-state / counterfactual) are separated by question and assumptions.
- **Cohort accounting:** Full 48,000 reconciliation; rejected/withdrawn/transferred/open/not-mature are not collapsed into \(Y=0\).
- **Missingness taxonomy:** Ordinary censoring vs delayed labels vs activation selection vs transfer vs permanent MNAR-ish feed loss is clear; testable vs untestable is mostly right.
- **Leakage table:** Required fields are covered with sensible keep/repair/drop rules.
- **Deployment boundary:** Selection effects and feedback loops are stated at the right level of caution.
- **Code direction:** As-of cutoff, temporal split by start time, pre-decision filtering, forbidden-column assert, cohort status printing—aligned with the writeup.

### Deductions (material)

**1. Estimand / prediction-time mismatch (serious conceptual softness)**  
The writeup defines  
\(P(Y=1 \mid X_t, A=1, R=1)\)  
while \(A\) and \(R\) are **post-\(t\)**. Training on eventual activatees is defensible; calling the population “applications … that **would** eventually be activated” blurs a retrospective training filter with a prospective deployment quantity. At score time the model is either (a) only meaningful if restricted to cases that still look activation-bound under current policy, or (b) an extrapolation off the labeled support. Section 8 partially repairs this, but Section 1 should have stated the support restriction more sharply (train on \(A=1,R=1\); scoring non-activated cases is not the same estimand). This is the core statistical issue the prompt cares about.

**2. Temporal test design is partly unworkable as specified**  
With extract \(C=\) 2026-02-15 and maturity \(\approx\) activation \(+125\) days, a “migration test” of **starts from 2025-10-15 onward with mature 90-day labels** is nearly empty. Policy-shift starts in mid/late 2025 are also only partially mature. The text later admits deferral and mentions rolling as-of backtests, but the **primary split table still presents those folds as if they were first-class labeled tests**. A stricter design would make rolling as-of cutoffs with explicit label-maturity gates the main scheme, and treat late-2025 starts as process/selection evaluation only until feeds catch up.

**3. Prefix unit of analysis underspecified**  
Fixed \(k\in\{3,5,7\}\) plus time-based prefixes are proposed, but it is unclear whether evaluation is one prefix per case, a panel of prefixes, how repeated scoring is de-duplicated, and how metrics avoid pseudo-replication. Short-case handling correctly notes population change, then the code silently inner-joins to \(k=5\), changing the estimand again without a cohort-flow update.

**4. Implementation skeleton: good spine, several sharp edges**
- `discover_dfg` / `get_variants` run on the **full** formatted log (including post-decision/activation path structure) before any train-only restriction; comments say “recompute on train when used as features,” but the skeleton still invites leakage if copied carelessly.
- `pm4py.get_prefixes_from_log` is demonstrated then **abandoned** for a hand-rolled path—fine, but the hand-rolled path does not implement elapsed-time prefixes at all.
- `safe.get("risk_score")` is brittle if the column is absent; transfer linkage (60%) is discussed in prose and almost absent in code/cohort logic; `documents_total` and extraction-time resource experience are audited in the table but not operationalized.
- Code length/complexity overshoots a tight “skeleton” and still omits the harder repairs it promises.

**5. Smaller statistical nits**
- IPW is proposed without overlap/positivity checks, stabilization, or truncation—easy to create a false sense of repair for partner missingness that is plausibly MNAR.
- Horizon is defined cleanly post-activation, but the **operational** early-warning horizon (time-to-activation \(+90\)d, highly variable) is under-emphasized relative to a lender “early warning” brief.
- Momentary botched arithmetic aside (“48,300?”) is minor but sloppy in a section about reconciling 48,000.
- Primary strategy “complete case + transparent scope” is honest; wording that partner cases should be “retained only with an explicit strategy” sits slightly awkwardly next to complete-case dropping them from supervised training (diagnostics vs training cohort should be cleaner).

### What kept the score from falling further
It avoids the failure modes the prompt flags as weak: no naive “all omitted = non-default,” no training-on-21,600-with-no-caveats story, no random split as primary truth, no casual use of `final_limit` / `decision_reason` / `collection_status` as features, and no pretend survival API in PM4Py. Sensitivity analyses and limitations are above average.

### Score band justification
- **9.5–10:** would require crisp prospective-vs-retrospective activation language, a maturity-safe validation plan as the centerpiece, fully consistent cohort flows after prefix filters, and a tighter code path that implements the main repairs it claims.
- **~8.4:** excellent applied design with real statistical maturity, still carrying a few non-cosmetic conceptual and operational flaws under adversarial reading.

**Final grade: 8.4 / 10.0**
