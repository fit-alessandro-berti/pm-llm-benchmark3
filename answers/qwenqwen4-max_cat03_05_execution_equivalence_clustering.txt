def initial_colors(ex, keep_order=True, keep_ext=True, keep_qual=True):
    col = {}
    for i, e in enumerate(ex.events):
        col[('E', e.id)] = ('ACT', e.act, i if keep_order else None)
    for o in ex.objects:
        col[('O', o.id)] = ('TYPE', o.type, o.is_ext if keep_ext else False)
    return col

def refine(ex, col, keep_qual=True):
    while True:
        new = {}
        for n in col:
            nbrs = []
            for (m, role) in ex.incident(n):       # role = 'E2O' | 'O2O:qual' | 'ORDER'
                if role.startswith('O2O') and not keep_qual:
                    role = 'O2O'
                nbrs.append((role, col[m]))
            new[n] = (col[n], tuple(sorted(nbrs)))
        new = rerank(new)                          # dense integer ranks, deterministic
        if partition(new) == partition(col): return new
        col = new

## 1. Equivalence design space

All relations are defined on an *Order-centred execution* `X = (E, O, act, type, inc  E×O, R  O×O×Q, )`, where `inc` is E2O incidence, `R` are qualified O2O edges, and `` is the timestamp order. Objects whose creator is another Order are flagged `ext=True`.

**E1 — Activity-sequence equivalence.**
`1(X) = act(e1),…,act(en)` in timestamp order, repetitions kept; `X 1 Y  1(X)=1(Y)`.
*Preserved:* label identity, multiplicity, total order. *Discarded:* object types, identifiers, cardinalities, E2O/O2O, qualifiers, externality — i.e. everything object-centric.
*Reflexive/symmetric/transitive:* yes (kernel of a function).
*Concurrency:* equal-timestamp events form a block; a block is encoded as a **sorted multiset** of labels, so tie ordering never matters.

**E2 — Typed structural equivalence (identifier-renaming isomorphism).**
`X 2 Y` iff there exist bijections `f:E_XE_Y`, `g:O_XO_Y` with `type(g(o))=type(o)`, `act(f(e))=act(e)`, `(e,o)inc  (f(e),g(o))inc`, `(a,b,·)R  (g(a),g(b),·)R`, and `ee'  f(e)f(e')`. Base variant **ignores qualifiers and ext flags**; the qualified variant `E2q` preserves both.
*Preserved:* typed hypergraph shape, per-event object multiplicities, repeated activities, order. *Discarded:* identifier strings, and (base) qualification/externality.
*R/S/T:* yes — isomorphism is an equivalence relation.
*Concurrency:* variant `E2p` replaces `` by the causal poset induced by object lifecycles (Packits Dispatch, Dispatchits Return, Invoiceits Payments); `f` must be a poset isomorphism. Still R/S/T.

**E3 — Business-semantic equivalence (preferred).**
`X 3 Y  (X)=(Y)`, where `` returns the tuple
`(fulfilment_motif, shipped_coverage, boundary_shared, settlement_class, rework_flag)` computed from multiplicities, ext flags and O2O qualifiers (§2).
*Preserved:* fan-out topology class, whether ordered items were actually shipped, whether the order boundary leaks, single vs. installment settlement, presence of a reverse-logistics loop. *Discarded:* identifiers, exact interleaving of independent pack/ship chains, item ordering, **which** domain is shared and whether a shared payment is allocated (kept only as sub-tags).
*R/S/T:* yes (kernel of ).
*Concurrency:*  reads only causally implied order (e.g. rework before invoicing), so timestamp ties are irrelevant by construction.

**E4 — Terminal-outcome equivalence (auxiliary).**
Compare the final qualified state restricted to lead-order objects: `{item  shipped?}`, `{invoice  fully settled?}`, ignoring counts, paths and effort. Kernel of a state function  R/S/T; concurrency irrelevant. E4 is deliberately coarse and is used only to expose borderline disagreements.

## 2. Canonical signatures

Preferred relation = E3, computed on top of an exact canonical form of E2q. Two steps: (a) renaming-invariant canonical labelling by colour refinement + individualisation; (b) semantic projection.

```python
from itertools import permutations, product
from collections import defaultdict

def init_colors(ex, keep_order=True, keep_ext=True):
    c = {}
    for i, e in enumerate(ex.events):
        c[('E', e.id)] = ('A', e.act, i if keep_order else 0)
    for o in ex.objects:
        c[('O', o.id)] = ('T', o.type, o.ext if keep_ext else False)
    return c

def refine(ex, c, keep_qual=True):
    while True:
        nxt = {}
        for n in c:
            nb = []
            for m, role in ex.incident(n):        # 'E2O' | 'O2O:<qual>' | 'ORD'
                if role.startswith('O2O') and not keep_qual:
                    role = 'O2O'
                nb.append((role, c[m]))
            nxt[n] = (c[n], tuple(sorted(nb)))
        nxt = rerank(nxt)                          # dense ints, deterministic
        if same_partition(nxt, c):
            return nxt
        c = nxt

def canonical_signature(ex, keep_order=True, keep_ext=True, keep_qual=True):
    c = refine(ex, init_colors(ex, keep_order, keep_ext), keep_qual)
    ties = [objs for objs in group_by_color(c, node='O') ]   # symmetric objects only
    best = None
    for perm_choice in product(*[permutations(t) for t in ties]):   # <=20 nodes here
        name = {(t, ext, k): f"{t}#{k}" for ...}   # type+ext+rank, never raw ids
        sig  = serialize(ex, name, keep_order, keep_qual)
        best = sig if best is None else min(best, sig)
    return best

def serialize(ex, name, keep_order, keep_qual):
    evs = [(e.act, tuple(sorted((t, name[o]) for t, os in e.inc.items() for o in os)))
           for e in ex.events]
    if not keep_order:
        evs = canonical_linearization(evs, causal_poset(ex))  # ties sorted
    o2o = tuple(sorted((name[a], name[b], q if keep_qual else '*')
                       for a, b, q in ex.o2o))
    return (tuple(evs), o2o)

def semantic_projection(ex):
    packs = [e for e in ex.events if e.act == 'Pack Package']
    ships = [e for e in ex.events if e.act == 'Dispatch']
    rework = any(e.act in ('Return Item', 'Inspect Return') for e in ex.events)
    motif = ('REWORK' if rework else
             '1P1D' if len(packs) == 1 and len(ships) == 1 else
             'nP1D' if len(ships) == 1 else 'nPnD')
    dropped = {b for a, b, q in ex.o2o
               if q in ('removed_before_dispatch', 'replaced_by', 'replaces')}
    coverage = 'FULL' if not dropped else 'SUBST'
    shared   = any(o.ext for o in ex.objects)          # domain kept as sub-tag only
    pays     = [e for e in ex.events if e.act == 'Record Payment']
    settle   = 'SINGLE' if len(pays) <= 1 else 'INSTALLMENT'
    return (motif, coverage, shared, settle, rework)
```

Renaming invariance holds because names are built from *structural colours + position*, never from `I11`-style strings; the lexicographic minimum over tie permutations removes the residual arbitrariness of WL-indistinguishable objects (e.g. `I11/I12`).

## 4. Cluster interpretations

**S1 — Straight-through isolated order** (`1P1D;FULL;ISO;SINGLE`). Two items, one parcel, one shipment, one invoice, one payment. The textbook happy path; benchmark for cycle time and cost. Risk: it is the *attractor* cluster — every lossy repair pushes executions here. Flattening on Order, Package, Delivery or Invoice all reproduce it faithfully. Stable under any reasonable repair.

**S2 — Split packing, consolidated shipment** (`nP1D`). Warehouse-level fragmentation with a single logistics handover. Opportunity: packing parallelism without freight cost increase; risk: shipment blocked by the slowest package (a hidden synchronisation join). Flattening on **Package** duplicates the order, invoice and payment (revenue double count); flattening on Delivery erases the split. Stable unless package identifiers are merged during extraction.

**S3 — Fragmented fulfilment with installment settlement** (`nPnD;INSTALLMENT`). Two independent ship chains interleaved, then one invoice settled by two payments. Business meaning: partial availability plus staged cash collection; risks are DSO distortion, premature "completed" status after the first payment, and per-shipment cost attribution. Flattening on Package replicates the invoice and *both* payments; flattening on Order collapses two payment events into an ambiguous single "paid" state. Moderately stable: merging partial payments into one settlement record moves it to a split-ship/single-payment class.

**S4 — Boundary-leaking order** (`SHARED`). The Order is not a closed transaction: either logistics (X5) or finance (X6) is co-owned with another Order. Operational response is identical — route to an allocation/exception queue — which is why  merges them. Risks: double-counted freight or revenue, unallocatable cash, and KPIs that cannot be attributed to a single order. *Every* single-case flattening misrepresents this: it either drops EXT objects (inventing isolation) or copies the shared object into both orders (inventing volume). **Least stable cluster**: losing the EXT flag collapses it into S1. For compliance, use the refined split S4-log / S4-fin.

**S5 — Substituted / short-shipped order** (`SUBST`). Structurally almost baseline, semantically a different promise: one item never left the warehouse. Risk: invoicing for an unshipped item, silent customer-impact, SLA breach invisible in label statistics. Flattening on Order or Item shows "packed and dispatched" because the qualifier lives on the P71–I71 edge, not on an event. **Fragile**: it survives only through O2O qualifiers plus the extra DispatchItem incidence.

**S6 — Reverse-logistics rework loop** (`REWORK`). Return, inspection, repack, reship, invoice afterwards. Business meaning: recovery capability plus a billing decision deferred until the final state. Risks: duplicated freight/handling cost, invoice-timing disputes, returned item counted twice in throughput. Flattening on Delivery detaches the return from its originating shipment; flattening on Order makes it look like ordinary split shipping. **Most stable** cluster: `Return Item`/`Inspect Return` are hard activity evidence, independent of qualifiers.

## 5. Borderline cases

**X1 vs X2.** E1, E2, E3, E4 all merge. A definition that anchors canonical names to *identifier sort order* (`I21 < I22`) rather than to structure would split them — but that definition is not renaming-invariant and must be rejected. A defensible split exists only if item-add order is itself semantic (pick priority); nothing here supplies that, so merge.

**X1 vs X5.** E1 merges (identical label strings). E2 splits: Pack carries 3 items and 2 Orders. E3 splits on `boundary_shared`. E4 restricted to local objects merges. Disagreement is exactly "labels vs. typed cardinality"; the business question (can freight cost be attributed to O5 alone?) sides with splitting.

**X1 vs X6.** E1 merges; E2 splits because the Invoice node has two Order neighbours; E3 splits. Note the subtler pair **X5 vs X6**: E2 splits (different shared types), preferred E3 merges (same operational motif), compliance-refined E3 splits (freight allocation  revenue recognition). Both answers are defensible at their stated granularity.

**X1 vs X7.** E1 merges. E2 splits *only* because Dispatch has an extra Item incidence; a defensible "O2O-topology-only, qualifier-blind" structural definition merges them, since the packages/deliveries/invoices graph is identical. Qualifier-aware E3 splits on `SUBST`. This is the most dangerous merge in the set: a fully invoiced order that short-shipped.

**X3 vs X4.** E1, E2, E3 split. E4 merges: all items delivered, one invoice fully settled. A coarse "fragmented fulfilment" semantics also merges them. The split is justified by two distinct decision-relevant facts — number of freight handovers and installment cash collection — neither of which is visible in the terminal state.

**X4 vs X8.** E1/E2/E3 split (rework loop, extra activities). E4 merges: both end fully delivered and settled. An effort/cost semantics splits even more sharply than E3. Danger: if a taxonomy repair maps `Return Item`/`Inspect Return` away and payments become amounts, X4 and X8 become indistinguishable — a repair-induced false merge.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py key is built **per lead object**: the ordered activity labels of the events referencing that object, decorated per event with the related object types and their counts (a typed-cardinality abstraction). It therefore preserves E1 plus per-event multiplicity, but **not** O2O qualifiers, **not** externality, and **not** cross-order sharing beyond "there are 2 Orders here". Where an implementation retains related object identifiers in the key, every Order becomes its own cluster: identifiers are unique by construction, so exact keys degenerate to the identity partition and give zero generalisation.

Canonicalisation: re-derive each lead object's sub-execution, compute `canonical_signature` (§2), merge raw clusters whose canonical keys coincide, then apply `semantic_projection` for reporting. Exact equivalence is preferable when the partition must be *audit-safe* (X5/X6/X7 must never be absorbed into baseline) or when clusters feed a replay/conformance step; coarse business clustering is preferable for variant KPIs with adequate sample sizes. `max_objs` truncates how many related objects enter the key — with `max_objs=2`, X5's third (external) item can be cut, making X5 *look* like X1. Large connected components (a shared invoice touching hundreds of Orders) explode the per-object subgraph; bound hops, cap objects, and hash the remainder rather than silently truncating.

```python
import pm4py
from collections import defaultdict

LEAD = "Order"
raw = pm4py.cluster_equivalent_ocel(ocel, LEAD, max_objs=8)   # {key: [order_ids]}

def order_execution(ocel, oid, hops=2):
    rel = ocel.relations
    eids = set(rel.loc[rel["ocel:oid"] == oid, "ocel:eid"])
    objs, frontier = {oid}, {oid}
    for _ in range(hops):
        objs |= set(rel.loc[rel["ocel:eid"].isin(eids), "ocel:oid"])
        eids |= set(rel.loc[rel["ocel:oid"].isin(frontier), "ocel:eid"])
        frontier = objs - frontier
    return build_execution(ocel, eids, objs, lead=oid)   # marks non-lead-owned objs ext=True

structural, semantic = defaultdict(list), defaultdict(list)
for key, orders in raw.items():
    for oid in orders:
        ex  = order_execution(ocel, oid)
        sig = canonical_signature(ex, keep_order=True, keep_ext=True, keep_qual=True)
        structural[sig].append(oid)                      # audit-safe partition
        semantic[semantic_projection(ex)].append(oid)    # S1..S6 reporting view

for s, members in sorted(semantic.items(), key=lambda kv: -len(kv[1])):
    print(s, len(members), members[:5])
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** X7 loses `removed_before_dispatch`/replacement; if 's coverage term is qualifier-derived, X7  **S1** (a compliance-fatal merge). X4 keeps `INSTALLMENT` (payment count survives), X8 keeps `REWORK` (activity-derived), X5/X6 keep `SHARED` (flag-derived). Only S5 is qualifier-fragile.

**Collapse repeated same-label events.** Label sets become `{C,A,P,D,I,R}` for X1–X7 and `{…,Rt,In}` for X8: E1 collapses to 2 clusters. If 's motif uses counts, X3 and X4 lose split-fulfilment detection and fall into a baseline-like class; X4 also loses installments. **Payment multiplicity as an amount attribute.** X4 becomes `nPnD;FULL;ISO;SINGLE`: still separate from X3 by delivery count, but if consolidation is also abstracted, X3  X4. ## 8. Limitations and recommendation

- **Compliance monitoring:** `E2q` (typed structural with qualifiers *and* ext flags), i.e. the 7-cluster partition, refined further by shared-domain. Obligations attach to exact relations: revenue attribution (X6), short-ship disclosure (X7), cross-order cost sharing (X5). False merges are violations, not noise.
- **Operational segmentation:** preferred **E3** (6 clusters). Each cluster maps to one routing/handling policy; S4's merge is intentional because the operational response is the same queue.
- **Root-cause analysis:** E2q *plus* attributes and interleaving, drilled down from an E3 cluster. X4's interleaving and X8's loop position are causal evidence; abstracting them destroys the explanation.
- **Descriptive reporting:** E3 headline counts, optionally E4 for "outcome achieved" statistics, with an explicit caveat that E1-only reporting hides X5/X6/X7 inside the baseline.

No single notion dominates because the relations optimise different error costs. Compliance punishes false merges (a hidden short-ship); reporting punishes false splits (eight singleton "variants" with no statistical power); root-cause needs distinctions that segmentation deliberately discards; outcome views legitimately equate X4 and X8 while operations must not. The right deliverable is therefore a *lattice* of partitions — E4  E1  E3  E2q — with the perturbation set published, so that any consumer can see exactly which differences were ignored and which were preserved.
