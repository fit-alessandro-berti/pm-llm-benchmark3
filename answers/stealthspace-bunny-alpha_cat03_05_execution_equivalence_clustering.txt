## 1. Equivalence design space

Let a lead-centered execution contain one local `Order`, all its local objects, and every external object it references. An execution contains events, typed objects, E2O references, and optional qualified O2O relations. **Externality is lifecycle metadata, not a meaningful identifier string**: after ingesting `EXT-OA`, subsequent canonicalization preserves only its external flag and type, not the name `EXT-OA`.

### Activity-sequence equivalence — \(A\)

Represent an execution by its activity word:

\[
A(L)=(\operatorname{act}(e_1),\ldots,\operatorname{act}(e_n)).
\]

Two executions are equivalent when these words are identical.

- **Preserved:** activity labels, repetitions, and totalized execution order.
- **Discarded:** object references, object types, multiplicities, E2O/O2O structure, identifiers, and externality.
- **Properties:** reflexive, symmetric, and transitive because it is equality of words.
- **Concurrency:** use a reproducible serialization, such as timestamp followed by a technical event ID. This is a presentation convention, not evidence of causality. A preferable concurrent alternative is equivalence of event-label/role partial-order traces. “Sharing some linear extension” is not an equivalence on incompletely observed partial traces.

Thus \(A\) deliberately merges X1, X2, X3, X4, X5, X6, and X7: all have the word  
`Create, Add, Add, Pack, Dispatch, Issue, Payment`.

### Typed structural equivalence — \(T\)

Construct a graph whose nodes are events and objects. Events carry activity labels and their strict timestamp relation; objects carry types and local/external flags. Require a bijection preserving:

1. event labels and object types;
2. E2O incidence, including repeated participation of the same object;
3. the event partial order;
4. local/external status.

O2O relations and qualifiers are excluded. This is an order-agnostic typed-poset isomorphism, not merely equality of type counts.

- **Preserved:** object correlation across events, package–delivery incidence, the extra item reference at X7’s dispatch, and shared external references.
- **Discarded:** O2O direction/qualifiers, business meaning, and absolute timestamps and event IDs.
- **Properties:** identity, inverse, and composition of graph isomorphisms establish reflexivity, symmetry, and transitivity.
- **Concurrency:** equal timestamps produce incomparable events unless an explicit causal edge exists.

A stricter alternative, \(T_{\mathrm{total}}\), preserves the complete serialized event order. It still merges X1/X2 because the order of their otherwise independent item additions is irrelevant. It separates X3/X4 because their Pack/Dispatch sequences differ.

### Preferred business-semantic equivalence — \(S\)

Use equality of a normalized business signature. The preferred, deliberately coarse clustering recognizes **standard consolidated fulfillment**:

- one local order;
- no shared external object;
- all local items packed, and all packages carried by exactly one delivery;
- one invoice and successful settlement;
- no return, item substitution, or removal before dispatch;
- one or more packages is permitted.

Payment semantics are evidence-sensitive: one `Record Payment` is accepted as settlement; multiple payments qualify only when qualifiers establish partial and completed settlement. No amounts or missing refunds are inferred.

The signature also recognizes separate motifs for split fulfillment, logistics sharing, invoice sharing, substitution, and return/repacking.

- **Preserved:** local item/delivery/invoice/payment multiplicities, package–delivery coverage, external-object sites, relevant qualifiers, repeated settlement records, and lifecycle motifs.
- **Discarded:** local names, exact package count when all packages share one delivery, independent event order, and O2O qualifier multiplicity.
- **Properties:** equality of canonical signatures is reflexive, symmetric, and transitive.
- **Concurrency:** counts and motif presence do not require tie-breaking. For compliance, a stricter variant can additionally require packing-before-dispatch and return-before-replacement causal evidence; equal timestamps should remain unresolved rather than generate invented causality.

This definition intentionally groups X1 and X3: internal package partitioning is not the same business outcome as splitting deliveries.

## 2. Canonical signatures

The following Python-like signature is reproducible and identifier-invariant. `E` contains activity/timestamp/object-reference records; `O` maps IDs to type and an externally supplied lifecycle flag; `R` contains O2O triples.

Qualifier names are normalized to the supplied meanings, including `partial_settles`, `completes_settlement`, `removed_before_dispatch`, and `replaces`.

```python
from collections import Counter

def semantic_signature(E, O, R):
    # O[id] = {"type": ..., "external": ...}
    # R contains {"source": id, "target": id, "qualifier": ...}
    acts = Counter(e["activity"] for e in E)

    def refs(e, type_=None, local=True):
        return {
            oid for oid in e["objects"]
            if O[oid]["type"] == type_
            and (not local or not O[oid]["external"])
        }

    def local_count(type_):
        return sum(
            not x["external"] and x["type"] == type_
            for x in O.values()
        )

    items = {
        oid for e in E if e["activity"] == "Add Item"
        for oid in refs(e, "Item")
    }
    nI, nP = local_count("Item"), local_count("Package")
    nD, nV = local_count("Delivery"), local_count("Invoice")
    nPay = acts["Record Payment"]

    packed = set().union(*(
        refs(e, "Item") for e in E
        if e["activity"] == "Pack Package"
    )) if acts["Pack Package"] else set()

    dispatched = set().union(*(
        refs(e, "Package") for e in E
        if e["activity"] == "Dispatch"
    )) if acts["Dispatch"] else set()

    external_sites = sorted({
        (e["activity"], O[oid]["type"])
        for e in E for oid in e["objects"]
        if O[oid]["external"]
    })

    qualifiers = {r["qualifier"] for r in R if r["qualifier"]}
    item_replacement = any(
        q in qualifiers and
        O[r["source"]]["type"] == O[r["target"]]["type"] == "Item"
        for r in R for q in [r["qualifier"]]
    )
    item_substitution = (
        item_replacement or "removed_before_dispatch" in qualifiers
        or any(
            e["activity"] == "Dispatch" and refs(e, "Item")
            for e in E
        )
    )

    package_replacement = any(
        r["qualifier"] == "replaces"
        and O[r["source"]]["type"] == O[r["target"]]["type"] == "Package"
        for r in R
    )
    return_repack = (
        acts["Return Item"] > 0
        and acts["Inspect Return"] > 0
        and package_replacement
        and acts["Dispatch"] >= 2
    )

    logistics_share = any(
        e["activity"] in {"Pack Package", "Dispatch"}
        and any(
            oid in e["objects"] and O[oid]["external"]
            and O[oid]["type"] == "Order"
            for oid in e["objects"]
        )
        for e in E
    )
    finance_share = any(
        e["activity"] in {"Issue Invoice", "Record Payment"}
        and any(
            oid in e["objects"] and O[oid]["external"]
            and O[oid]["type"] == "Order"
            for oid in e["objects"]
        )
        for e in E
    )

    fully_settled = (
        nPay == 1
        or (
            nPay > 1
            and {"partial_settles", "completes_settlement"}
            <= qualifiers
        )
    )
    standard = (
        acts["Issue Invoice"] == 1 and nV == 1 and nPay > 0
        and fully_settled
        and nD == 1 and nP > 0
        and items and items <= packed
        and packed == dispatched
        and not external_sites
        and not item_substitution
        and not return_repack
    )

    # This intentionally does NOT include the raw package count.
    package_profile = (
        "all_packages_in_one_delivery"
        if nP > 0 and packed == dispatched and nD == 1
        else "other"
    )

    if return_repack:
        family = "S8"
    elif item_substitution:
        family = "S7"
    elif logistics_share:
        family = "S5"
    elif finance_share:
        family = "S6"
    elif standard:
        family = "S0"
    else:
        family = "S4"

    return (
        family,
        nI, nD, nV, nPay,
        package_profile,
        tuple(external_sites),
        tuple(sorted(qualifiers)),
        fully_settled,
        return_repack,
    )
```

Raw package counts can be retained as cluster metadata without making them equality criteria.

## 4. Cluster interpretations

The singleton clusters describe observed behavior, not statistically established populations.

| Preferred cluster | Business behavior, opportunity, and risk | Poor traditional flattening; repair stability |
|---|---|---|
| **S0 — {X1, X2, X3}** | Straightforward fulfillment with one delivery, one invoice, one payment, and no observed exception. Useful baseline for cycle-time or cost comparisons. Splitting X3 into packages creates additional handling opportunities. | An Order-only activity projection loses the distinction between one and two packed packages; a weak type histogram also resembles X4. Stable under renaming and independent event reordering. It moves if deliveries become split, externality is corrected, or substitution/return evidence appears. |
| **S4 — {X4}** | Two shipments and two payment records, with the second completing settlement. Useful for installment collection and split-delivery analysis. Risks include cash-allocation and delivery-to-invoice reconciliation. | An order-event word retains “two payments” but not their relation to the two deliveries. A terminal-event projection can misleadingly resemble one fulfilled order. Stable under renaming; not stable if split deliveries are semantically consolidated or settlement evidence is reclassified. |
| **S5 — {X5}** | A package mixes this order’s items with another order’s item and references both owning orders during dispatch. Opportunity: consolidated logistics. Risk: responsibility, inventory ownership, SLA, and damage attribution. | A projection rooted only at O5 hides the foreign owner and item. Stable while the external lifecycle flag and reference sites survive; correcting a false external flag can move it to S0. |
| **S6 — {X6}** | One invoice bills two orders, but there is no order-level payment allocation. Risks include duplicate revenue attribution and unclear cost allocation. | An Order-rooted trace can incorrectly attribute the whole shared invoice to O6. Stable under renaming; adding allocation improves interpretation but does not eliminate shared financial ownership. |
| **S7 — {X7}** | One item was substituted or removed after packing. Risks include obsolete inventory, unauthorized substitution, and discrepancies between the initial manifest and dispatched contents. | A bag of activity labels is identical to X1; a package-only projection hides the removed relation and replacement. Stable only while the dispatch item reference or explicit lifecycle evidence survives. |
| **S8 — {X8}** | Initial shipment, return of one item, inspection, and repacking into another package. This can explain extra handling, delayed revenue recognition, and net-versus-gross fulfillment differences. No refund or invoice adjustment is supplied. | Repeated Pack/Dispatch counts resemble X4, while a forward-only projection loses package lineage and the return. Stable under renaming and harmless event reordering; deleting or misclassifying the return/replacement evidence can move it. |

## 5. Borderline cases

- **X1 versus X2:** \(A\), \(T\), and \(S\) all merge them. Rename I11/I12 to I21/I22 and reverse the mapping. The identifier order in independent Add events carries no business meaning. A definition treating the within-event order of the two item IDs as significant would disagree, but that would encode serialization rather than behavior.

- **X1 versus X5:** \(A\) merges them. \(T\) and \(S\) separate them because X5 adds an external item, a second owning order, and multi-order logistics. A coarser “primary-order event footprint” definition would merge them, treating external participation as boundary metadata rather than part of fulfillment.

- **X1 versus X6:** \(A\) and a primary-Order lifecycle projection merge them; \(T\) and \(S\) separate them through multi-order invoice/payment references. The distinction is financial ownership, not package structure.

- **X1 versus X7:** \(A\) merges them, and \(T\) separates them through the extra item reference at Dispatch. \(S\) also preserves replacement/removal evidence. A substitution-tolerant definition asking only “was a package with the order’s items finally dispatched and paid?” would merge them, but would deliberately hide an important operational exception.

- **X3 versus X4:** \(T\) merges them under a partial-order, package–delivery interpretation; \(T_{\mathrm{total}}\) separates them. \(S\) separates them because X3 has one delivery/payment and X4 has two of each. A “completed order with all items fulfilled” definition could merge them by ignoring delivery granularity and installment structure.

- **X4 versus X8:** both have two local items, packages, and deliveries, so weak type histograms are dangerous. Typed and semantic relations separate them through payment cardinality and return/repack structure. A broad “order with an operational exception” cohort could merge them, but would not imply equivalent financial outcomes—X8 contains no supplied refund.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py function is an **exact clustering utility**, not a business-semantic equivalence standard. Pin the installed release when reproducibility matters. In the commonly used implementation, the key is built from **locally identified object-lifecycle footprints**: object types and activity occurrences with their associated/co-occurring object names. It therefore retains more than an activity word—object correlation, types, repetitions, and local names. It is not a timestamp-based business interpretation and does not independently interpret O2O qualifier values, revenue allocation, or lifecycle ownership. The prefix `EXT` has no intrinsic business meaning to that key.

Raw identifiers make exact clusters unnecessarily fine: O1 versus O2, I11 versus I22, and P11 versus P21 are renaming differences, not different executions. Conversely, removing all identifiers without canonicalizing object correlation can make clusters too coarse.

The recommended post-processing is hierarchical:

1. retain PM4Py’s exact cluster IDs;
2. decode each execution into E2O and qualified O2O records;
3. compute the preferred Order-centered signature;
4. aggregate by that signature while retaining the original exact-cluster ID.

A `max_objs` budget or similar size guard can exclude, bound, or truncate evidence for large connected executions, depending on release. Do not interpret under-keyed large traces as proven equivalent. Keeping them separately or using a bounded motif signature is safer.

```python
from collections import defaultdict
import pm4py

# Omit max_objs here so the default full-size key is used.
# With an installed release exposing it, an explicit suitable budget
# can be supplied, for example max_objs=10000.
exact_clusters = pm4py.cluster_equivalent_ocel(ocel)

semantic_groups = defaultdict(list)

for exact_id, cluster in enumerate(exact_clusters):
    # Some releases/packages may return a cluster or a list of traces.
    traces = [cluster] if hasattr(cluster, "events") else cluster

    for trace in traces:
        # Storage-specific adapter:
        # - identify the local lead Order;
        # - retain referenced external objects with explicit flags;
        # - decode E2O records;
        # - reconstruct normalized (source, target, qualifier) O2O rows.
        L = decode_order_execution(
            trace,
            lead_type="Order",
            external_objects="retain",
            o2o_qualifiers="retain",
        )

        signature = semantic_signature(**L)
        semantic_groups[signature].append({
            "exact_cluster": exact_id,
            "ocel": trace,
        })

# Each value preserves fine clusters inside a coarser business cohort.
```

Exact PM4Py clustering is preferable for reproducibility testing, auditing differences, and verifying an expected replay. Business clustering is preferable when local renaming, package partitioning, or installment mechanics should not prevent comparison.

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** the preferred assignments remain unchanged because X7 also has an item in its Dispatch event, and X8 still has Return, inspection, and package replacement evidence. A weaker rule that discards both qualifiers and this E2O anomaly would merge X1/X2 with X7. This is a concrete example of hidden replacement semantics.

- **Ignore external objects and their ownership links:** the semantic clusters become `{X1, X2, X3, X5, X6}` plus unchanged exception singletons. This falsely treats shared logistics and shared billing as isolated fulfillment. Typed clustering still separates them through external references and incidence.

- **Collapse repeated same-label events:** under literal removal of repetitions, activity-sequence equivalence merges X1, X2, X3, and X4 because all reduce to the same activity set. The preferred signature remains stable **if object inventories are retained**: X3 still has two packages, while X4 still has two deliveries and two payments. Collapsing duplicate event rows must not mean deleting their object lifecycles.

- **Treat Pack/Dispatch as partial rather than total order:** the preferred assignments do not change because it intentionally ignores independent event order. This would merge T3/T4 into a partial-order structural cluster, whereas \(T_{\mathrm{total}}\) separates them. A compliance profile should additionally retain observed per-package packing-before-dispatch dependencies.

- **Represent payment multiplicity as an amount attribute:** replacing two settlement events by their verified total can make X4 financially equivalent to a single-payment order. Its semantic cluster still remains S4 under the chosen rule because delivery cardinality is preserved. A coarser “completed commercial order” rule could then merge X1, X2, X3, and X4. No amount equality is justified here because amounts are absent.

## 8. Limitations and recommendation

- **Compliance monitoring:** use a strict annotated semantic signature: preserve exact counts, external scope, qualifiers, and observed causal dependencies. The preferred coarse \(S\) is insufficient because it intentionally ignores package count.
- **Operational segmentation:** use the preferred \(S\). It distinguishes ordinary consolidated fulfillment from substitution, returns, shared execution, and split fulfillment without treating renaming or packing granularity as major segments.
- **Root-cause analysis:** use \(T_{\mathrm{total}}\) plus qualifiers and operational attributes. Fine PM4Py clusters alone are not causal explanations, but the additional order information prevents conflating X1/X2 with X7.
- **Descriptive reporting:** use \(S\), supplemented by aggregate activity counts and durations. Activity words alone are compact but materially misleading for externality, replacement, and returns.

No single level is universally best. Compliance needs auditable distinctions, segmentation needs useful generalization, root-cause analysis needs preserved execution structure, and reporting needs interpretable summaries. The recommended business signature should therefore remain versioned, reproducible, and accompanied by its exact-cluster provenance.
