## 1. Temporal Data Semantics

- **Ordering:** Events are ordered per case by `(time:timestamp, event_index)`. If timestamps are equal, the lower `event_index` is earlier. This is decisive for TX-311, where `Enhanced_Review` index 3 precedes `Update_Jurisdiction` index 4.
- **Blank cells:** A blank attribute cell means **no update at that event**. It does not set the value to null and does not erase the prior value.
- **State reconstruction:** For amount, risk level, jurisdiction, and customer type, the current value at event `e` is the last nonblank value at or before `e` in event order. Initial state is unknown until the first nonblank value appears.
- **Release state:** Obligations are evaluated using the state at the `Release_Funds` event, not the final case state. Later values, such as TX-305’s settlement amount, are not copied backward.
- **Material data change:** A nonblank change to risk, jurisdiction, or customer type is material for the relevant rules. For amount, this policy treats a change as review-invalidating only when it is a **more than 20% increase after a review**; a decrease alone does not invalidate a review. A change from unknown amount is not safely classifiable.
- **Sanctions state:** A `Sanctions_List_Update` is tracked separately: it matters for R3 when the added jurisdiction is the current jurisdiction at release and occurs after the latest screen.
- **Time distinctions:**  
  - **Event time:** when the source event occurred, e.g., `Release_Funds`.  
  - **Effective time:** when an update or exemption actually applies, e.g., `effective_from`.  
  - **Record time:** when a database row was inserted, e.g., EX-77 inserted at 11:00.  
  - **Evidence time:** when reliable evidence shows approval occurred, e.g., EX-77 qualified signature at 09:05 or EX-88 certificate creation at 10:30.  
  A late record can be harmless if other evidence proves earlier approval. A backdated displayed field alone is not sufficient.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| R1 | `Release_Funds`; current jurisdiction is not DE and current amount  EUR 100,000 | `Enhanced_Review` before release and after latest material data change | `latest_material_change < Enhanced_Review < Release_Funds`; if no material change, `Enhanced_Review < Release_Funds` | State at release for amount and jurisdiction; review timing relative to changes | Matching valid exemption waiving R1 | Unknown amount or jurisdiction makes trigger indeterminate; do not default below threshold | Amount/jurisdiction update history, review timestamp, exemption approval evidence |
| R2 | `Release_Funds`; current risk HIGH or current customer_type PEP | `Enhanced_Review` and `Compliance_Approve` | `relevant_state_change < Enhanced_Review < Compliance_Approve < Release_Funds`; no standard-only packet cure | State at release for risk and customer type; relevant change history | None stated | Unknown risk/customer type is indeterminate unless other known value already triggers | Review records showing type and packet, approval timestamp, reclassification/PEP update history |
| R3 | `Release_Funds`; current jurisdiction was added to sanctions list after latest `Sanctions_Screen` and before release | New `Sanctions_Screen` after list update | `Sanctions_Screen_old < Sanctions_List_Update < Sanctions_Screen_new < Release_Funds` | State at release for jurisdiction; list update event and screen history | None stated | Unknown jurisdiction or unclear list scope is indeterminate | List update effective time, jurisdiction scope, screen timestamps/results |
| R4 | Any amount increase >20% after latest `Standard_Review` or `Enhanced_Review` | New valid review for amount-dependent obligations if the underlying obligation remains | `review < amount_increase < release` invalidates that review | Amount at review and amount at release | Decrease does not invalidate | Increase from unknown amount is indeterminate | Reliable pre-change and post-change amounts, review timestamp |
| R5 | Exemption invoked for an obligation | Exemption approval must support validity at obligation trigger | `approval_evidence_time  trigger`; `effective_from  trigger  expiry`; scope matches | State at trigger/release for jurisdiction, customer type, amount | Valid exemption waives only listed rules | Missing or contradictory approval evidence prevents using exemption | Approved_by, effective/expiry, scope, signature/evidence time, record time, outage/attestation proof |
| R6 | Any missing decisive attribute | None | N/A | Relevant event-time state | Other evidence may resolve | Indeterminate; no low-risk default | Source payloads, immutable release message, authoritative updates |
| R7 | Any event comparison | None | Events ordered by timestamp then `event_index`; updates effective at event time unless otherwise established | Event-time state, not final state | Explicit alternative effective time overrides | Same timestamp without tie-breaker is ambiguous | Stable source ordering, UTC timestamps, effective-time metadata |

**Pseudo-logic notation.** For a case `c`, let `e < f` mean event `e` is earlier than `f` by `(timestamp, event_index)`. Let `state_c(e)` be the state after applying all nonblank updates with update event ` e`. Let `rel` be the `Release_Funds` event. Let `last_A(< rel)` be the latest event of activity `A` before `rel`.

- **R1:**  
  `trigger_R1(c, rel)  state_c(rel).jurisdiction  DE  state_c(rel).amount  100000`.  
  If trigger is true, require either:  
  ` er < rel: activity(er)=Enhanced_Review  (last_material_change(<rel) is none  last_material_change(<rel) < er)`  
  or `valid_exemption(c, rel, R1)`.

- **R2:**  
  `trigger_R2(c, rel)  state_c(rel).risk=HIGH  state_c(rel).customer_type=PEP`.  
  Require:  
  ` er, ca: er < ca < rel  activity(er)=Enhanced_Review  activity(ca)=Compliance_Approve`.  
  The ER must follow the relevant HIGH/PEP state change. A `Standard_Review`, even with approval, is not an `Enhanced_Review`.

- **R3:**  
  Let `u < rel` be a `Sanctions_List_Update` adding `state_c(rel).jurisdiction`. If ` s < u: activity(s)=Sanctions_Screen`, require:  
  ` s' : u < s' < rel  activity(s')=Sanctions_Screen`.

- **R4:**  
  Let `r = latest Standard_Review or Enhanced_Review before rel`. If `state_c(r).amount` and `state_c(rel).amount` are known and  
  `state_c(rel).amount > 1.20 × state_c(r).amount`, then `r` is invalid for amount-dependent obligations. Unknown source or target amount yields `INDETERMINATE`.

- **R5:**  
  `valid_exemption(ex, rel, rule)  approved_by(ex)=Head_Compliance  approval_evidence_time(ex)  rel.time  effective_from(ex)  rel.time  expiry(ex)  scope_matches(ex, state_c(rel))  waives(ex, rule)  evidence_supports_earlier_approval(ex, rel.time)`.  
  Record time later than release is acceptable only when other evidence supports earlier approval.

- **R6:**  
  If a decisive trigger or exception cannot be established or excluded from event-time evidence, outcome is `INDETERMINATE`.

- **R7:**  
  `value_c(e, attr) = last nonblank value v(attr, u)` where `u  e`; ties resolved by `event_index`. No value is copied from events after `e`.

## 4. Ambiguities and Alternative Readings

- **TX-302:** The result depends on accepting EX-77’s evidence chain. The qualified digital signature at 09:05 and documented outage make the 11:00 database insert non-fatal. If the signature were invalid or the outage explanation rejected, the exemption would not be usable; however, because an ER also occurred before release with no later material change, the result would become `COMPLIANT`, not automatically `NONCOMPLIANT`.

- **TX-305:** If an immutable release payload proved amount  EUR 100,000, R1 would be triggered; because ER exists and no material post-review amount change is evidenced, the case would likely be `COMPLIANT`. If immutable release amount were < EUR 100,000, R1 would not trigger. If evidence showed a >20% amount increase after ER, it would be `NONCOMPLIANT`. The later settlement amount alone is insufficient.

- **TX-310:** If Head_Compliance attestation or a qualified signature timestamp before 10:00 corroborates EX-88, the case becomes `JUSTIFIED_EXCEPTION` because EX-88 waives R1. If the 10:30 certificate creation is treated as authoritative and the requester’s oral witness rejected, EX-88 is invalid, only a Standard Review exists, and the case becomes `NONCOMPLIANT`. The displayed 08:50 field alone does not resolve this.

- **TX-311:** If event_index were ignored, the same-timestamp jurisdiction update could be misordered relative to ER. Under the stated release-time rule and tie-breaker, current jurisdiction at release is DE, so R1 is not triggered. A different policy that attaches R1 whenever the case was foreign earlier in the case, or that requires a review after every later data change regardless of the release state, could change the result.

- **TX-306:** If every amount update were treated as material regardless of magnitude, the 220,000 to 230,000 update after ER/approval would require renewed review. Under R4, only >20% increases invalidate, so the case is compliant. A different rule version or threshold would change the result.

- **TX-308:** If a decrease after review were treated as a material data change requiring a new ER, TX-308 would be noncompliant. The stated R4 rule explicitly says a decrease does not by itself invalidate a review, so the result is compliant.

- **TX-309:** If the 15:28 update were merely a correction of an already-known amount rather than a material increase, the ER might remain valid. The log note says “increase over 20 percent since enhanced review,” so the >20% invalidation is well supported.

            ):
                latest_review = cand

        if latest_review is None:
            r4_invalidating = False
            r4_unknown = False
        elif pd.isna(amount) or pd.isna(latest_review["amount_state"]):
            r4_invalidating = None
            r4_unknown = True
        else:
            r4_invalidating = bool(amount > 1.20 * float(latest_review["amount_state"]))
            r4_unknown = False

        # R2 coarse flags.
        if risk == "HIGH" or cust == "PEP":
            r2_trigger = True
        elif unknown_risk or unknown_cust:
            r2_trigger = None
        else:
            r2_trigger = False

        r2_change_rows = prior[
            prior["material_change_kind"].fillna("").str.contains(
                "risk_change|customer_change", regex=True
            )
        ]
        latest_r2_change = last_row(r2_change_rows)

        r2_er_after_change = bool(
            latest_er is not None
            and (
                latest_r2_change is None
                or latest_er["_ord"] > latest_r2_change["_ord"]
            )
        )
        r2_ca_after_er = bool(
            latest_er is not None
            and latest_ca is not None
            and latest_er["_ord"] < latest_ca["_ord"] < rel_order
        )
        standard_packet_approval = bool(
            latest_ca is not None
            and "standard" in str(latest_ca["note"]).lower()
        )
        r2_ok = bool(
            r2_trigger is True
            and r2_er_after_change
            and r2_ca_after_er
            and not standard_packet_approval
        )

        # R3 coarse flags.
        r3_trigger = None if unknown_jur else False
        r3_violation = False
        r3_decisive_update = ""
        r3_missing_prior_screen = False

        if pd.notna(jur):
            matching_updates = prior[
                (prior[ACT] == "Sanctions_List_Update")
                & (prior["jurisdiction"] == jur)
                & (prior["note"].str.contains("add", case=False, na=False))
            ]
            r3_trigger = len(matching_updates) > 0

            for _, upd in matching_updates.iterrows():
                screens_before = prior[
                    (prior[ACT] == "Sanctions_Screen")
                    & (prior["_ord"].apply(lambda o: o < upd["_ord"]))
                ]
                screens_after = prior[
                    (prior[ACT] == "Sanctions_Screen")
                    & (prior["_ord"].apply(lambda o: upd["_ord"] < o < rel_order))
                ]
                if screens_after.empty:
                    r3_violation = True
                    r3_decisive_update = event_stamp(upd)
                    r3_missing_prior_screen = screens_before.empty
                    break

        # Exemption join and coarse evidence status.
        ex_id = "" if pd.isna(rel["exemption_id"]) else str(rel["exemption_id"]).strip()
        ex_cited = bool(ex_id)
        ex_present = ex_id in EX.index

        ex_scope_match = None
        ex_formal_ok = None
        ex_ev_status = "NONE"
        ex_waives_r1 = False
        ex_displayed = ex_effective = ex_expiry = ""
        ex_sig = ex_record = ex_witness = ""
        ex_evidence_note = ""

        if ex_present:
            x = EX.loc[ex_id]
            rel_time = rel[TIME]

            if unknown_amount or unknown_jur or unknown_cust:
                ex_scope_match = None
            else:
                ex_scope_match = bool(
                    (x["scope_jurisdiction"] == "ANY" or x["scope_jurisdiction"] == jur)
                    and (x["scope_customer"] == "ANY" or x["scope_customer"] == cust)
                    and pd.notna(x["max_amount"])
                    and amount <= x["max_amount"]
                )

            ex_formal_ok = bool(
                x["approved_by"] == "Head_Compliance"
                and pd.notna(x["displayed_approval"])
                and x["displayed_approval"] <= rel_time
                and pd.notna(x["effective_from"])
                and x["effective_from"] <= rel_time
                and pd.notna(x["expires_at"])
                and rel_time <= x["expires_at"]
            )

            sig_before_release = bool(
                pd.notna(x["qualified_signature_ts"])
                and x["qualified_signature_ts"] <= rel_time
            )
            ex_waives_r1 = "R1" in [p.strip() for p in str(x["waives"]).split("|")]

            if (
                x["evidence_class"] == "STRONG_TIMELY"
                and ex_formal_ok
                and sig_before_release
            ):
                ex_ev_status = "STRONG_TIMELY"
            else:
                ex_ev_status = "REVIEW_REQUIRED"

            ex_displayed = fmt_ts(x["displayed_approval"])
            ex_effective = fmt_ts(x["effective_from"])
            ex_expiry = fmt_ts(x["expires_at"])
            ex_sig = fmt_ts(x["qualified_signature_ts"])
            ex_record = fmt_ts(x["record_insert_ts"])
            ex_witness = fmt_ts(x["witness_ts"])
            ex_evidence_note = x["evidence_note"]

        # Coarse R1 outcome; never a final narrative classification.
        r1_clean_ok = bool(
            r1_er_before
            and r1_er_after_material
            and r4_invalidating is not True
        )
        r1_ex_ok = bool(
            ex_waives_r1
            and ex_scope_match is True
            and ex_formal_ok is True
            and ex_ev_status == "STRONG_TIMELY"
        )

        if r1_trigger is True:
            if r1_ex_ok:
                r1_outcome = "WAIVED_BY_EXEMPTION"
            elif r1_clean_ok:
                r1_outcome = "SATISFIED"
            else:
                r1_outcome = "DEVIATION"
        elif r1_trigger is None:
            r1_outcome = "UNKNOWN"
        else:
            r1_outcome = "NOT_TRIGGERED"

        needs_review = bool(
            unknown_amount
            or unknown_risk
            or unknown_jur
            or unknown_cust
            or unknown_amount_change
            or r1_trigger is None
            or r2_trigger is None
            or r3_trigger is None
            or r4_unknown
            or (ex_ev_status == "REVIEW_REQUIRED" and r1_trigger is True)
        )

        if needs_review:
            hint = "REVIEW_REQUIRED"
        elif r3_violation or (r2_trigger is True and not r2_ok) or r1_outcome == "DEVIATION":
            hint = "DEVIATION_CANDIDATE"
        elif ex_cited and ex_ev_status == "STRONG_TIMELY" and r1_trigger is True:
            hint = "EXCEPTION_CANDIDATE"
        else:
            hint = "NO_COARSE_DEVIATION"

        diagnostics.append({
            "case": case,
            "release_event": event_stamp(rel),
            "state_amount": amount,
            "state_risk": risk,
            "state_jurisdiction": jur,
            "state_customer_type": cust,
            "unknown_amount": bool(unknown_amount),
            "unknown_risk": bool(unknown_risk),
            "unknown_jurisdiction": bool(unknown_jur),
            "unknown_customer_type": bool(unknown_cust),
            "unknown_amount_change": unknown_amount_change,

            "R1_trigger": r1_trigger,
            "R1_er_before_release": r1_er_before,
            "R1_er_after_latest_material": r1_er_after_material,
            "R1_outcome": r1_outcome,

            "R2_trigger": r2_trigger,
            "R2_er_after_risk_customer_change": r2_er_after_change,
            "R2_approve_after_er": r2_ca_after_er,
            "R2_standard_packet_approval": standard_packet_approval,
            "R2_ok": r2_ok,

            "R3_trigger": r3_trigger,
            "R3_violation": r3_violation,
            "R3_missing_prior_screen": r3_missing_prior_screen,
            "R3_decisive_update": r3_decisive_update,
            "R3_new_screen_after_update": None if r3_trigger is None else (not r3_violation),

            "R4_invalidating_increase": r4_invalidating,
            "R4_unknown": r4_unknown,

            "exemption_id": ex_id,
            "ex_scope_match": ex_scope_match,
            "ex_formal_fields_ok": ex_formal_ok,
            "ex_waives_R1": ex_waives_r1,
            "ex_evidence_status": ex_ev_status,
            "ex_displayed_approval_ts": ex_displayed,
            "ex_effective_from_ts": ex_effective,
            "ex_expires_ts": ex_expiry,
            "ex_qualified_signature_ts": ex_sig,
            "ex_record_insert_ts": ex_record,
            "ex_witness_ts": ex_witness,
            "ex_evidence_note": ex_evidence_note,

            "latest_standard_review": event_stamp(latest_sr),
            "latest_enhanced_review": event_stamp(latest_er),
            "latest_compliance_approve": event_stamp(latest_ca),
            "latest_sanctions_screen": event_stamp(latest_screen),
            "latest_sanctions_list_update": event_stamp(latest_list_update),
            "latest_material_change": event_stamp(latest_material),
            "latest_material_kind": "" if latest_material is None else latest_material["material_change_kind"],
            "same_timestamp_material_after_er": same_ts_material_after_er,
            "coarse_hint": hint,
        })

        # Coarse control-flow-only check. This deliberately ignores data triggers and evidence.
        trace_order_checks.append({
            "case": case,
            "release_event": event_stamp(rel),
            "standard_before_release": latest_sr is not None,
            "enhanced_before_release": latest_er is not None,
            "compliance_after_enhanced": bool(
                latest_er is not None
                and latest_ca is not None
                and latest_ca["_ord"] > latest_er["_ord"]
            ),
            "screen_after_matching_sanctions_update": (
                "N/A" if not r3_trigger else bool(not r3_violation)
            ),
            "post_release_events": int((g["_ord"].apply(lambda o: o > rel_order)).sum()),
            "control_flow_only_warning": "Cannot express conditional data obligations or evidence validity.",
        })

diagnostics = pd.DataFrame(diagnostics)
trace_order_df = pd.DataFrame(trace_order_checks)

pd.set_option("display.max_columns", None)
show_cols = [
    "case", "state_amount", "state_risk", "state_jurisdiction", "state_customer_type",

The code emits `REVIEW_REQUIRED` where human evidential judgment is necessary, such as unknown release amount or contradictory exemption evidence. It does not encode the narrative classifications as a lookup table.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage:** Inspecting final attribute values would wrongly use TX-305’s settlement amount as the release amount. Event-time state must be reconstructed at release.
2. **Missing data is not low risk:** TX-305 has no release amount. Control-flow conformance sees ER and release and may declare success, but R1 cannot be evaluated safely.
3. **Conditional activation:** R1 depends on amount and jurisdiction, R2 on risk and PEP status, and R3 on sanctions-list state. A trace shape alone cannot know which rule was active.
4. **Material changes after review:** TX-301 and TX-309 have reviews followed by >20% amount increases. The presence of a review event is insufficient; its temporal validity relative to data changes matters.
5. **Decreases versus increases:** TX-308 has an amount decrease after ER. A naïve “any update after review invalidates” check would overflag it.
6. **Same-timestamp ordering:** TX-311 requires `event_index` to know that jurisdiction changed after ER. Timestamp-only models erase this consequence.
7. **Post-hoc exemptions and evidence time:** TX-302 and TX-310 both have late database records, but their evidential value differs. Control flow cannot distinguish a valid earlier signature from a backdated PDF.
8. **Review type and packet content:** TX-307 has a `Standard_Review` and a compliance approval, but R2 requires ER and approval after that ER. Event names alone do not encode packet adequacy unless logged precisely.
9. **Sanctions list dynamics:** TX-304’s initial screen was valid until XZ was added. A static “screen exists somewhere in trace” check misses the list-update timing.
10. **Approval ordering:** R2 requires `Enhanced_Review < Compliance_Approve < Release_Funds`; simple co-occurrence of these activities is insufficient.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload:** At `Release_Funds`, emit the exact amount, currency, risk level, jurisdiction, customer type, sanctions status, exemption ids, rule version, and review ids used for the decision.
- **Change provenance:** For every update event, log old value, new value, source system, reason, and whether the change is amount, risk, jurisdiction, customer type, or sanctions-list related.
- **Effective, event, and record times:** Separate `event_time`, `effective_from`, `effective_to`, `record_insert_time`, and `evidence_time` for all data changes and approvals.
- **Stable event ordering:** Require monotonically increasing source sequence numbers or event ids within each timestamp so same-time events are unambiguous.
- **Exemption structure:** Store exemption scope as fields: jurisdiction, customer type, minimum/maximum amount, waived rules, effective interval, approver, and policy version.
- **Approval evidence:** Require qualified signature timestamp, certificate id, hash, signer identity, and revocation status. If backfilling after outage, log the outage andController attestation separately.
- **Review packet identity:** `Enhanced_Review` and `Compliance_Approve` should include packet hash, reviewed amount, reviewed risk, reviewed jurisdiction, reviewed customer type, and review type.
- **Sanctions updates:** Log list version, added jurisdictions, effective time, source, and screen result linked to that list version.
- **Missing-data sentinels:** Use explicit status flags such as `AMOUNT_UNKNOWN_FEED_UNAVAILABLE` and `RELEASE_PAYLOAD_INCOMPLETE`; never infer release values from later settlement.
- **Rule versioning
