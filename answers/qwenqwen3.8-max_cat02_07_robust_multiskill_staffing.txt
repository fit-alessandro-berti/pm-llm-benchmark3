def get_scenario_meta(scenario):
    demand = []
    for row in DEMAND:
        b = row.copy()
        demand.append(b)
    absent=set(); tail_mult=1.0; outage=None
    if scenario in ('U1','U5'):
       for b in demand:
          if b['start'] < 240:
             b['arrivals'] *= 1.7
             new_p1 = min(100.0, b['P1_pct']+8.0)
             rem = 100.0-new_p1
             old = b['P2_pct']+b['P3_pct']
             if old > 0:
                scale = rem/old
                b['P2_pct'] *= scale
                b['P3_pct'] *= scale
             b['P1_pct'] = new_p1
    if scenario == 'U2':
       for b in demand:
          if 240 <= b['start'] < 480:
             counts = {}
             for typ in TYPE_TO_DIAG:
                counts[typ] = b['arrivals'] * b[f'{typ}_pct'] / 100.0
                if typ in ('E','ES'): counts[typ] *= 2.0
             total = sum(counts.values())

             for typ in TYPE_TO_DIAG: b[f'{typ}_pct'] = 100.0*counts[typ]/total
    if scenario in ('U3','U5'): absent.add('Chen')
    if scenario == 'U4': tail_mult=2.0
    if scenario == 'U5': outage=(90,120)

def generate_cases(scenario, seed):
    meta=get_scenario_meta(scenario)
    rng=np.random.default_rng(seed)
    cases=[]
    i=0
    for b in meta['demand']:
       n=int(rng.poisson(max(0.0,b['arrivals'])))
       if n==0: continue
       prio_p=np.array([b['P1_pct'],b['P2_pct'],b['P3_pct']], dtype=float)
       prio_p = prio_p / prio_p.sum()
       type_p=np.array([b[f'{t}_pct'] for t in TYPE_TO_DIAG], dtype=float)
       type_p = type_p / type_p.sum()
       for _ in range(n):
          arrival = float(b['start'] + rng.uniform(0, b['end']-b['start']))
          priority = str(rng.choice(['P1','P2','P3'], p=prio_p))
          typ = str(rng.choice(list(TYPE_TO_DIAG.keys()), p=type_p))
          target = {'P1':120,'P2':480,'P3':1440}[priority]
          diag = TYPE_TO_DIAG[typ]
          services={}

             services[act] = draw_service(act, rng, tm)
          cases.append({'case_id': f'{scenario}_s{seed}_{i}', 'arrival':arrival, 'priority':priority, 'type':typ, 'target':target, 'services':services, 'diag_skills':diag})
          i+=1
    return cases

# 1. Assumptions, objectives, and decision variables

## 1.1 Demand and service assumptions

I treat the supplied tables as the only empirical evidence. The main assumptions are labeled below.

**A1. Service-time distributions from ranges.**  
For each activity, the ordinary and complex-tail ranges are interpreted as uniform distributions. The mixture mean used for capacity approximations is:

\[
E[S] = (1-p) \cdot \frac{min_{ord}+max_{ord}}{2} + p \cdot \frac{min_{tail}+max_{tail}}{2}
\]

This gives the following base mixture means before resource multipliers:

| activity | mean base minutes |
|---|---:|
| Intake | 6.94 |
| Mechanical | 26.30 |
| Electrical | 32.82 |
| Software | 38.50 |
| Validation | 15.74 |

These means are used for hand calculations. The Python simulation samples from the uniform ranges and applies tail probabilities per activity.

**A2. Arrivals.**  
Expected arrivals are treated as Poisson means in the stochastic simulation, but as fixed expected counts in the capacity calculations. Arrivals within a two-hour block are assumed uniformly distributed.

**A3. Resource multipliers.**  
A multiplier \(m\) means the resource consumes \(m \times\) the drawn base service time. Multipliers are applied when an activity is assigned to a resource. Handover, setup, and restart penalties are modeled as additional time. Handover and setup are treated as resource-consumed time; parallel coordination is treated as case waiting time before Validation.

**A4. ME and ES parallelism.**  
For ME and ES cases, parallel execution reduces the case critical path from approximately the sum of branch times to approximately the maximum of branch times plus 8 minutes coordination, but it consumes two diagnostic resources simultaneously. Sequential execution avoids the 8-minute coordination delay and can be better when capacity is tight, but it lengthens the individual case path.

The parallel/sequential decision is therefore policy-controlled:

- Strict specialization: always sequential.
- Full pooling: parallel if the case is P1 or branch queues are short.
- Hybrid: parallel only when no P1 is waiting and branch queues are short.

**A5. Preemption.**  
P1 cases may preempt lower-priority diagnostic work. The restart penalty is 10% of the remaining active service time. A case can be preempted at most once. In the simulation, preemption is applied only to diagnostic activities, not Intake or Validation.

**A6. Overtime.**  
Each resource may work up to 30 minutes of overtime after shift end. In the simulation, overtime becomes available if work remains. In the base-case fairness rule, planned utilization above 90% of regular capacity is considered fragile.

**A7. U2 interpretation.**  
For U2, I assume E and ES expected counts double between 12:00 and 16:00 and then type proportions are renormalized. This increases total arrivals in those blocks. A less severe interpretation would keep total arrivals fixed and only shift the mix; I note this where relevant.

## 1.2 Objective formulations

At least two objective functions are relevant.

### Objective 1: SLA/tail-risk objective

This objective prioritizes P1 performance and tail delay:

\[
\min_{\pi} \sum_{c} w_{p(c)}
\left[
\alpha d_c
+ \beta \max(0, d_c - Q_{90})
+ M \cdot \mathbb{I}(d_c > T_{p(c)})
\right]
\]

where:

- \(\pi\) is the staffing/routing policy;
- \(d_c\) is elapsed delay for case \(c\);
- \(p(c)\) is priority;
- \(T_{P1}=120\), \(T_{P2}=480\), \(T_{P3}=1440\);
- \(Q_{90}\) is the 90th percentile delay;
- \(w_{P1} > w_{P2} > w_{P3}\);
- \(M\) is a large penalty for SLA violation.

This objective cares about mean delay but penalizes tail delay and SLA misses.

### Objective 2: Fairness/robustness objective

This objective penalizes poor worst-case behavior and unfair resource loading:

\[
\min_{\pi}
\left[
\max_{s \in \{Base,U1,...,U5\}} Regret_s(\pi)
+ \gamma \max(0, U_{max,s} - 0.90)
+ \delta (1 - Jain_s)
\right]
\]

where:

- \(Regret_s(\pi)\) can be defined against the best policy in scenario \(s\) using weighted delay or SLA miss rate;
- \(U_{max,s}\) is maximum resource utilization;
- \(Jain_s\) is Jain’s fairness index over resource utilizations;
- \(\gamma,\delta\) penalize overloading and unfairness.

This objective explicitly discourages a policy that wins the base case but collapses under shocks.

## 1.3 Decision variables

The main decision variables are:

1. Eligibility: which resources may take which queues.
2. Dispatch score: priority, SLA risk, handover/setup penalty, queue age.
3. Reservation: how much capacity is protected for P1/P2-at-risk cases.
4. Parallelization threshold: when ME/ES cases are split across two resources.
5. Preemption threshold: when P1 may interrupt lower-priority diagnostic work.
6. Overtime trigger: when overtime is authorized.
7. Overflow rule: when a case may leave a specialized queue and use a slower qualified resource.

# 3. Candidate policies

## 3.1 Policy 1: Strict specialization with fixed queues, `SPEC`

Operational rule:

- Each resource has a home diagnostic skill:
  - Ada: Mechanical
  - Ben: Mechanical
  - Chen: Electrical
  - Deepa: Electrical
  - Emil: Software
  - Farah: Mechanical
- Intake and Validation are pooled across qualified resources.
- Diagnostic work stays in fixed skill queues.
- A resource takes diagnostic work only from its home queue.
- Within each queue, P1 is dispatched before P2 before P3, then FIFO.
- ME and ES cases are processed sequentially.
  - ME: Mechanical then Electrical.
  - ES: Electrical then Software.
- Parallelization is not used.
- Preemption is allowed only within the same skill queue.
- Handover is minimized by keeping cases in specialized queues.
- Overflow is not allowed.

Strengths:

- Low setup and handover burden.
- Simple to audit.
- Protects skill identity.

Weaknesses:

- Poor resilience when one queue is overloaded.
- Chen absence is dangerous because software/electrical capacity cannot be flexibly reallocated.
- Late Mechanical demand has no natural mechanical capacity after Deepa’s shift.

## 3.2 Policy 2: Full pooling with transparent dispatch, `POOL`

Operational rule:

- Any qualified resource may take any task.
- Dispatch score:

\[
score = priority\_weight + 500 \cdot SLA\_risk - 0.5 \cdot (handover + cross-team + setup)
\]

where:

- priority weight: P1 = 1000, P2 = 100, P3 = 10;
- SLA risk increases as elapsed time approaches the SLA target;
- handover/setup penalties discourage unnecessary switches.

Parallelization:

- ME/ES cases are parallelized if the case is P1 or if the sum of the two branch queues is at most 3.
- Otherwise sequential.

Preemption:

- A waiting P1 diagnostic job may preempt a P2/P3 diagnostic job if no suitable idle resource is available.
- Preemption is limited to once per preempted case.
- Restart penalty is added explicitly.

Overtime:

- Used whenever P1/P2 work is waiting near shift end.

Strengths:

- Best average delay under many shocks.
- Good resilience because resources can move to bottleneck skills.
- Can balance load across shifts.

Weaknesses:

- Higher handover and setup burden.
- Can create excessive switching if dispatch score is not tuned.
- May feel less predictable to operators.

## 3.3 Policy 3: Hybrid P1 reservation with controlled overflow, `HYBRID`

Operational rule:

- All qualified resources are eligible, but dispatch is protected for P1 and P2-at-risk cases.
- P3 jobs are throttled if:
  - any P1/P2 job is waiting in the same skill queue; or
  - the resource’s regular utilization is already above 90%.
- Cross-skill overflow is allowed, but slower qualified resources are used only when queue age or SLA risk justifies it.
- Dispatch score is the same transparent form as `POOL`, but with P3 throttling.

Parallelization:

- ME/ES cases are parallelized only if:
  - no P1 diagnostic job is waiting;
  - combined branch queue length is at most 2.
- Otherwise sequential.

Preemption:

- P1 may preempt only when P1 SLA risk is high, e.g. risk > 0.7.
- Lowest-priority work is preempted first.
- At most one preemption per preempted case.

Overtime:

- Reserved primarily for P1/P2-at-risk cases.
- Fairness cap: avoid planning any resource above 90% regular utilization unless in shock mode.

Strengths:

- Strong P1 SLA protection.
- Better fairness than pure pooling.
- Retains pooling resilience.
- More interpretable than a black-box optimizer.

Weaknesses:

- P3 work can be deferred substantially.
- Requires thresholds and monitoring.
- Reservation can idle capacity if poorly tuned.

# 5. Robust recommendation

## 5.1 Primary recommendation

I recommend **`HYBRID`: P1-reserved pooling with controlled cross-skill overflow and threshold-based parallelization** as the primary policy.

It is robust under the chosen objective because:

1. It protects P1 SLA attainment better than full pooling in most shock scenarios.
2. It avoids the catastrophic queue isolation of strict specialization.
3. It keeps fairness better than pure pooling by throttling P3 when resources are overloaded.
4. It allows sequential ME/ES execution when capacity is tight, avoiding unnecessary coordination overhead.
5. It is operationally explainable: priority, SLA risk, handover/setup penalty, and reservation thresholds are visible.

## 5.2 Fallback crisis mode

A fallback mode is useful for U5-like conditions.

Trigger crisis mode if any of the following holds for more than 15 minutes:

- P1 queue length > 3.
- More than 25% of active P1 cases have SLA risk > 0.7.
- Intake queue length > 5 during a surge.
- A critical resource absence coincides with Electrical or Software queue length > 4.
- Maximum resource utilization > 110% of regular capacity.

Crisis mode rules:

- Suspend new P3 diagnostic starts except where needed to complete already-open cases.
- Dispatch all qualified resources by P1/P2 SLA risk only.
- Allow preemption of P3 by P1 with minimal threshold.
- Parallelize ME/ES only for P1 and only if two qualified resources are idle.
- Authorize overtime up to 30 minutes per resource.
- Prefer same-resource retention to reduce handover where possible.

Switch back to normal hybrid mode when:

- P1 queue length  1 for 30 minutes;
- P1 SLA risk  0.2 for 30 minutes;
- maximum regular utilization  90%.

## 5.3 When another policy may be preferable

- If the objective is purely minimum average delay and fairness is ignored, `POOL` may be preferable.
- If the organization is highly sensitive to handover errors, setup time, or skill dilution, `SPEC` may be preferable during low-load periods.
- If the system is consistently underloaded at night, a simpler specialized rule may be easier to operate.

# 6. Secondary effects and implementation risks

## 6.1 Gaming of estimates

If dispatch depends on predicted service times or SLA risk, operators or intake systems may learn to overstate priority or complexity. Mitigations:

- Use objective event-log feedback to recalibrate estimates.
- Audit repeated high-priority classifications that do not match actual service times.
- Keep priority rules transparent and medically/operationally defensible.

## 6.2 Starvation of P3 work

Hybrid reservation can defer P3 cases repeatedly. This is acceptable only if P3 SLA is monitored. Mitigations:

- Add an anti-starvation rule: if a P3 case waits longer than 50% of its SLA target, promote it to a protected queue.
- Reserve a small fraction of late-day capacity for P3 completion.
- Monitor P3 p95 delay separately.

## 6.3 Skill erosion

Excessive pooling may reduce deep specialization. If mechanical or electrical experts constantly do intake or validation, diagnostic quality may degrade. Mitigations:

- Track skill usage by resource.
- Set minimum diagnostic utilization bands for specialists.
- Use controlled overflow rather than unrestricted pooling.

## 6.4 Excessive preemption

Preemption can improve P1 response but imposes a 10% restart penalty and can create chaos. Mitigations:

- Limit preemption to one per case.
- Preempt only when P1 SLA risk is high.
- Avoid preempting jobs near completion, e.g. remaining time < 10 minutes.
- Monitor preemption count and post-preemption delay.

## 6.5 Coordination overhead

Parallel ME/ES cases add 8 minutes coordination and can create validation bursts. Mitigations:

- Parallelize only when branch queues are short.
- Stagger parallel starts if validation queue is rising.
- Prefer sequential execution during electrical/software bottlenecks.

## 6.6 New bottleneck at Validation

If pooling and parallelization accelerate diagnostics, Validation can become the new constraint. Mitigations:

- Monitor validation queue separately.
- Allow diagnostic resources with validation skill to help validation when diagnostic queues are short.
- Avoid releasing many parallel branches into validation simultaneously.

## 6.7 Fairness and shift effects

Farah works only 08:00-12:00 and has high multipliers for many diagnostic skills. Using her heavily may improve morning throughput but may be unfair or unsustainable. Emil starts at 12:00, so morning shocks cannot rely on him. Mitigations:

- Use Jain fairness index over regular capacity.
- Avoid systematic overloading of part-time resources.
- Consider shift overlap or flexible start times if morning surges persist.

## 6.8 Human interpretability

Operators need to understand why a case was assigned. The dispatch score should be logged and explainable:

- “Assigned to Deepa because P1 SLA risk = 0.82, handover penalty = 7, setup penalty = 0.”
- “P3 case deferred because two P2 cases are waiting and resource utilization is 93%.”

Black-box optimization should be avoided unless it can produce such explanations.

# 7. Monitoring and process-mining design

## 7.1 Event attributes

Each event should include at least:

- `case:concept:name`: case identifier.
- `concept:name`: activity, e.g. Intake, Mechanical, Electrical, Software, Validation, or explicit handover/setup/pause events.
- `start_timestamp`: activity start.
- `time:timestamp`: activity end.
- `org:resource`: resource identifier.
- `priority`: P1/P2/P3.
- `case_type`: M/E/S/ME/ES.
- `queue_entry_time`: when the job entered the queue.
- `assignment_decision`: dispatch score or rule name.
- `eligible_resource_set`: resources eligible under policy.
- `skill_used`: skill family used.
- `planned_service`: expected service time at assignment.
- `actual_service`: active service time.
- `pause_count`, `resume_count`: preemption or break pauses.
- `handover_delay`: handover minutes added.
- `setup_delay`: setup minutes added.
- `coordination_delay`: parallel coordination delay.
- `policy_version`: SPEC/POOL/HYBRID and version.
- `scenario_flag`: Base/U1/U2/U3/U4/U5 or live shock label.
- `sla_target`: 120/480/1440.
- `sla_remaining`: target minus elapsed time.
- `branch_mode`: parallel or sequential for ME/ES.

## 7.2 Deployment indicators

Monitor:

1. SLA attainment by priority and block.
2. Mean and p90/p95 end-to-end delay.
3. Queue length and waiting time by stage: Intake, Mechanical, Electrical, Software, Validation.
4. Resource utilization relative to regular capacity and overtime.
5. Fairness index across resources.
6. Handover count and handover minutes.
7. Setup count and setup minutes.
8. Preemption count and restart penalty minutes.
9. Parallelization rate and coordination delay.
10. Validation queue after parallel diagnostic completion.
11. P3 starvation indicator: P3 waiting time and P3 SLA risk.
12. Policy mode changes: normal, hybrid, crisis.

## 7.3 PM4Py analyses

Useful PM4Py analyses:

- **Case service/waiting time**: use `pm4py.insert_case_service_waiting_time` to understand case-level cycle time and waiting. These outputs are case-level, not stage-level, so stage metrics should be computed separately.
- **Activity service time**: use `pm4py.get_service_time` to detect service-time drift by activity. Compare against planned service and resource multipliers.
- **Handover network**: use `pm4py.discover_handover_of_work_network` to identify excessive resource switching and handover hotspots.
- **Directly-follows graph**: reveal drift from Intake  diagnostic  Validation, unexpected loops, or repeated preemption paths.
- **Performance spectrum**: identify waiting time accumulation by block and priority.
- **Bottleneck analysis**: compare queue entry and activity start times by skill.
- **Social network analysis**: detect over-reliance on specific cross-skilled resources.

# -----------------------------
# Simplifications made explicit
# -----------------------------
# 1. Service times are sampled once per case/activity. If a job is preempted and later
#    reassigned, the remaining resource minutes are not re-scaled by the new multiplier.
# 2. Handover and setup are resource-consumed delays. Parallel coordination is case waiting.

def to_ts(minutes):
    return BASE_TIME + pd.Timedelta(minutes=float(minutes))

def draw_service(activity, rng, tail_multiplier=1.0):
    spec = SERVICE[activity]
    p = spec["p"]
    if spec["diagnostic"]:
        p *= tail_multiplier
    p = min(1.0, p)
    if rng.random() < p:
        low, high = spec["tail"]
    else:
        low, high = spec["ord"]
    return float(rng.uniform(low, high))

def get_scenario_meta(scenario):
    demand = [row.copy() for row in DEMAND]
    absent = set()
    tail_multiplier = 1.0
    intake_outage = None

    if scenario in ("U1", "U5"):
        for b in demand:
            if b["start"] < 240:
                b["arrivals"] *= 1.7
                new_p1 = min(100.0, b["P1_pct"] + 8.0)
                rem = 100.0 - new_p1
                old = b["P2_pct"] + b["P3_pct"]
                if old > 0:
                    scale = rem / old
                    b["P2_pct"] *= scale
                    b["P3_pct"] *= scale
                b["P1_pct"] = new_p1

    if scenario == "U2":
        for b in demand:
            if 240 <= b["start"] < 480:
                counts = {}
                for typ in TYPE_TO_DIAG:
                    counts[typ] = b["arrivals"] * b[f"{typ}_pct"] / 100.0
                    if typ in ("E", "ES"):
                        counts[typ] *= 2.0
                total = sum(counts.values())
                b["arrivals"] = total
                for typ in TYPE_TO_DIAG:
                    b[f"{typ}_pct"] = 100.0 * counts[typ] / total

    if scenario in ("U3", "U5"):
        absent.add("Chen")

    if scenario == "U4":
        tail_multiplier = 2.0

    if scenario == "U5":
        intake_outage = (90, 120)  # 09:30-10:00

    return {
        "demand": demand,
        "absent": absent,
        "tail_multiplier": tail_multiplier,
        "intake_outage": intake_outage,
    }

def generate_cases(scenario, seed):
    meta = get_scenario_meta(scenario)
    rng = np.random.default_rng(seed)
    cases = []
    case_no = 0

    for b in meta["demand"]:
        n = int(rng.poisson(max(0.0, b["arrivals"])))
        if n == 0:
            continue

        prio_p = np.array([b["P1_pct"], b["P2_pct"], b["P3_pct"]], dtype=float)
        prio_p = prio_p / prio_p.sum()

        type_keys = list(TYPE_TO_DIAG.keys())
        type_p = np.array([b[f"{t}_pct"] for t in type_keys], dtype=float)
        type_p = type_p / type_p.sum()

        for _ in range(n):
            arrival = float(b["start"] + rng.uniform(0, b["end"] - b["start"]))
            priority = str(rng.choice(["P1", "P2", "P3"], p=prio_p))
            case_type = str(rng.choice(type_keys, p=type_p))
            target = SLA_TARGET[priority]
            diag_skills = TYPE_TO_DIAG[case_type]

            services = {}
            for act in ["Intake", "Validation"] + diag_skills:
                tm = meta["tail_multiplier"] if SERVICE[act]["diagnostic"] else 1.0
                services[act] = draw_service(act, rng, tm)

            cases.append({
                "case_id": f"{scenario}_s{seed}_{case_no}",
                "arrival": arrival,
                "priority": priority,
                "type": case_type,
                "target": target,
                "services": services,
                "diag_skills": diag_skills,
            })
            case_no += 1

    return cases

def simulate(policy_name, templates, scenario, seed):
    policy = POLICIES[policy_name]
    meta = get_scenario_meta(scenario)
    absent = meta["absent"]
    outage = meta["intake_outage"]

    # Resource state and availability
    resources = []
    for r in RESOURCES:
        if r["id"] in absent:
            avail = [False] * HORIZON
            regular_capacity = 0.0
        else:
            s, e = r["shift"]
            cur = s
            regular_intervals = []
            for bs, be in r["breaks"]:
                if bs > cur:
                    regular_intervals.append((cur, bs))
                cur = max(cur, be)
            if e > cur:
                regular_intervals.append((cur, e))

            regular_capacity = float(sum(max(0, ie - ib) for ib, ie in regular_intervals))

            # Overtime: up to 30 minutes after shift end.
            all_intervals = regular_intervals + [(e, min(HORIZON, e + 30))]
            avail = [False] * HORIZON
            for ib, ie in all_intervals:
                ib = int(max(0, ib))
                ie = int(min(HORIZON, ie))
                for tt in range(ib, ie):
                    avail[tt] = True

        resources.append({
            "id": r["id"],
            "skills": r["skills"],
            "avail": avail,
            "regular_capacity": regular_capacity,
            "current_job": None,
            "last_diag_skill": None,
            "last_case_id": None,
            "worked": 0.0,
        })

    # Case state
    cases = {}
    for tmpl in templates:
        cid = tmpl["case_id"]
        cases[cid] = {
            "id": cid,
            "arrival": tmpl["arrival"],
            "priority": tmpl["priority"],
            "type": tmpl["type"],
            "target": tmpl["target"],
            "services": tmpl["services"],
            "diag_skills": tmpl["diag_skills"],
            "last_resource": None,
            "last_skill": None,
            "preempted": False,
            "branches_open": 0,
            "pending_second": None,
            "coord_delay": 0.0,
            "completion": None,
        }

    job_counter = 0

    def make_job(case_id, skill, base_service, ready_time, priority, target):
        nonlocal job_counter
        job_counter += 1
        return {
            "job_id": job_counter,
            "case_id": case_id,
            "skill": skill,
            "base_service": float(base_service),
            "ready_time": float(ready_time),
            "priority": priority,
            "target": float(target),
            "started": False,
            "first_start": None,
            "remaining": None,
            "planned_service": None,
            "active_minutes": 0.0,
            "pause_count": 0,
            "cum_handover": 0.0,
            "cum_setup": 0.0,
            "preempted": False,
            "score": None,
            "eligible_str": "",
        }

    pending = []
    for tmpl in templates:
        pending.append(make_job(
            tmpl["case_id"],
            "Intake",
            tmpl["services"]["Intake"],
            tmpl["arrival"],
            tmpl["priority"],
            tmpl["target"],
        ))

    queues = {skill: [] for skill in SKILLS}
    events = []

    total_handover = 0.0
    total_setup = 0.0
    preemptions = 0

    def add_job(job):
        pending.append(job)

    def eligible_string(job):
        ids = []
        for r in resources:
            if job["skill"] not in r["skills"]:
                continue
            if (
                policy["eligibility"] == "specialized"
                and job["skill"] in DIAG_SKILLS
                and PRIMARY.get(r["id"]) != job["skill"]
            ):
                continue
            ids.append(r["id"])
        return "|".join(ids)

    def delay_components(res, job):
        c = cases[job["case_id"]]
        handover = 0.0
        cross_team = 0.0
        setup = 0.0

        if c["last_resource"] is not None and c["last_resource"] != res["id"]:
            handover = 7.0
            last_team = TEAM.get(c["last_skill"])
            new_team = TEAM.get(job["skill"])
            if last_team is not None and new_team is not None and last_team != new_team:
                cross_team = 5.0

        if (
            job["skill"] in DIAG_SKILLS
            and res["last_diag_skill"] is not None
            and res["last_diag_skill"] != job["skill"]
            and res["last_case_id"] != job["case_id"]
        ):
            setup = 5.0

        return handover, cross_team, setup

    def any_p1_waiting(t):
        for s in DIAG_SKILLS:
            for j in queues[s]:
                if j["priority"] == "P1" and j["ready_time"] <= t:
                    return True
        return False

    def decide_parallel(c, skills, t):
        if policy["parallel"] == "never":
            return False

        qsum = sum(len(queues[s]) for s in skills)

        if policy["parallel"] == "threshold":
            return c["priority"] == "P1" or qsum <= 3

        if policy["parallel"] == "reserved":
            return (not any_p1_waiting(t)) and qsum <= 2

        return False

    def create_diagnostic_jobs(c, t):
        skills = c["diag_skills"]
        if len(skills) == 1:
            add_job(make_job(c["id"], skills[0], c["services"][skills[0]], t, c["priority"], c["target"]))
            return

        if decide_parallel(c, skills, t):
            c["coord_delay"] = 8.0
            c["branches_open"] = 2
            c["pending_second"] = None
            for s in skills:
                add_job(make_job(c["id"], s, c["services"][s], t, c["priority"], c["target"]))
        else:
            c["coord_delay"] = 0.0
            c["branches_open"] = 1
            order = sorted(skills, key=lambda s: (len(queues[s]), c["services"][s]))
            c["pending_second"] = order[1]
            add_job(make_job(c["id"], order[0], c["services"][order[0]], t, c["priority"], c["target"]))

    def handle_diagnostic_completion(c, job, finish):
        c["branches_open"] -= 1

        if c["branches_open"] == 0 and c["pending_second"] is not None:
            s = c["pending_second"]
            c["pending_second"] = None
            c["branches_open"] = 1
            add_job(make_job(c["id"], s, c["services"][s], finish, c["priority"], c["target"]))
        elif c["branches_open"] == 0:
            ready = finish + c["coord_delay"]
            add_job(make_job(c["id"], "Validation", c["services"]["Validation"], ready, c["priority"], c["target"]))

    def start_job(res, job, t, score, handover, cross_team, setup):
        nonlocal total_handover, total_setup

        delay = handover + cross_team + setup
        job["cum_handover"] += handover + cross_team
        job["cum_setup"] += setup

        if not job["started"]:
            multiplier = res["skills"][job["skill"]]
            planned = job["base_service"] * multiplier
            job["planned_service"] = planned
            job["remaining"] = planned + delay
            job["started"] = True
            job["first_start"] = t
        else:
            job["remaining"] += delay

        job["score"] = score
        job["eligible_str"] = eligible_string(job)

        res["current_job"] = job
        if job["skill"] in DIAG_SKILLS:
            res["last_diag_skill"] = job["skill"]
            res["last_case_id"] = job["case_id"]

        total_handover += handover + cross_team
        total_setup += setup

    def maybe_preempt(t):
        nonlocal preemptions

        if policy["preemption"] == "none":
            return

        p1_jobs = []
        for s in DIAG_SKILLS:
            for j in queues[s]:
                if j["priority"] == "P1" and j["ready_time"] <= t:
                    p1_jobs.append(j)

        if not p1_jobs:
            return

        if policy["preemption"] == "risk":
            max_risk = 0.0
            for j in p1_jobs:
                c = cases[j["case_id"]]
                elapsed = t - c["arrival"]
                slack = j["target"] - elapsed
                risk = max(0.0, 1.0 - slack / j["target"]) if j["target"] > 0 else 1.0
                max_risk = max(max_risk, risk)
            if max_risk < 0.7:
                return

        p1_skills = {j["skill"] for j in p1_jobs}
        candidates = []

        for res in resources:
            j = res["current_job"]
            if j is None:
                continue
            if j["skill"] not in DIAG_SKILLS:
                continue
            if j["priority"] not in ("P2", "P3"):
                continue
            if cases[j["case_id"]]["preempted"]:
                continue
            if policy["preemption"] == "same" and j["skill"] not in p1_skills:
                continue
            candidates.append((res, j))

        if not candidates:
            return

        res, job = min(
            candidates,
            key=lambda x: (
                PRIO_RANK[x[1]["priority"]],
                -(x[1]["remaining"] if x[1]["remaining"] is not None else 0.0),
            ),
        )

        if job["remaining"] is None:
            return

        penalty = 0.1 * max(0.0, job["remaining"])
        job["remaining"] += penalty
        job["pause_count"] += 1
        cases[job["case_id"]]["preempted"] = True
        job["preempted"] = True

        queues[job["skill"]].append(job)
        res["current_job"] = None
        preemptions += 1

    def choose_and_start(res, t):
        if not res["avail"][t]:
            return

        best = None

        for skill in res["skills"]:
            if skill not in queues:
                continue

            if (
                policy["eligibility"] == "specialized"
                and skill in DIAG_SKILLS
                and PRIMARY.get(res["id"]) != skill
            ):
                continue

            for idx, job in enumerate(queues[skill]):
                if job["ready_time"] > t:
                    continue

                if skill == "Intake" and outage is not None and outage[0] <= t < outage[1]:
                    continue

                if policy["p3_throttle"] and job["priority"] == "P3":
                    higher_waiting = any(
                        q["priority"] in ("P1", "P2") and q["ready_time"] <= t
                        for q in queues[skill]
                    )
                    if higher_waiting:
                        continue
                    if res["regular_capacity"] > 0 and res["worked"] / res["regular_capacity"] > 0.90:
                        continue

                handover, cross_team, setup = delay_components(res, job)
                c = cases[job["case_id"]]
                elapsed = t - c["arrival"]
                slack = job["target"] - elapsed
                risk = max(0.0, 1.0 - slack / job["target"]) if job["target"] > 0 else 1.0

                score = PRIO_SCORE[job["priority"]] + 500.0 * risk - 0.5 * (handover + cross_team + setup)

                cand = {
                    "skill": skill,
                    "idx": idx,
                    "job": job,
                    "score": score,
                    "handover": handover,
                    "cross_team": cross_team,
                    "setup": setup,
                }

                if best is None or cand["score"] > best["score"]:
                    best = cand

        if best is not None:
            job = queues[best["skill"]].pop(best["idx"])
            start_job(res, job, t, best["score"], best["handover"], best["cross_team"], best["setup"])

    def complete_job(res, finish):
        job = res["current_job"]
        c = cases[job["case_id"]]

        events.append({
            "case:concept:name": job["case_id"],
            "concept:name": job["skill"],
            "start_timestamp": to_ts(job["first_start"] if job["first_start"] is not None else finish),
            "time:timestamp": to_ts(finish),
            "org:resource": res["id"],
            "priority": job["priority"],
            "case_type": c["type"],
            "skill_used": job["skill"],
            "queue_entry_time": to_ts(job["ready_time"]),
            "assignment_decision": job["score"],
            "eligible_resource_set": job["eligible_str"],
            "planned_service": job["planned_service"],
            "actual_elapsed": finish - (job["first_start"] if job["first_start"] is not None else finish),
            "active_service": job["active_minutes"],
            "pause_count": job["pause_count"],
            "handover_delay": job["cum_handover"],
            "setup_delay": job["cum_setup"],
            "policy_version": policy_name,
            "scenario_flag": scenario,
            "sla_target": job["target"],
        })

        c["last_resource"] = res["id"]
        c["last_skill"] = job["skill"]
        res["current_job"] = None
        res["last_case_id"] = job["case_id"]

        if job["skill"] == "Intake":
            create_diagnostic_jobs(c, finish)
        elif job["skill"] in DIAG_SKILLS:
            handle_diagnostic_completion(c, job, finish)
        elif job["skill"] == "Validation":
            c["completion"] = finish

    # Main minute-by-minute loop
    for t in range(HORIZON):
        new_pending = []
        for job in pending:
            if job["ready_time"] <= t:
                queues[job["skill"]].append(job)
            else:
                new_pending.append(job)
        pending = new_pending

        maybe_preempt(t)

        for res in resources:
            if res["current_job"] is None:
                choose_and_start(res, t)

        for res in resources:
            job = res["current_job"]
            if job is None:
                continue
            if not res["avail"][t]:
                continue
            if outage is not None and job["skill"] == "Intake" and outage[0] <= t < outage[1]:
                continue

            job["remaining"] -= 1.0
            job["active_minutes"] += 1.0
            res["worked"] += 1.0

            if job["remaining"] <= 0.0:
                complete_job(res, t + 1.0)

    # Metrics
    delays = []
    p1_flags = []
    p2_flags = []

    for c in cases.values():
        if c["completion"] is None:
            delay = float(HORIZON)
        else:
            delay = float(c["completion"] - c["arrival"])

        delays.append(delay)

        if c["priority"] == "P1":
            p1_flags.append(delay <= c["target"])
        elif c["priority"] == "P2":
            p2_flags.append(delay <= c["target"])

    mean_delay = float(np.mean(delays)) if delays else np.nan
    p95_delay = float(np.percentile(delays, 95)) if delays else np.nan
    p1_sla = 100.0 * float(np.mean(p1_flags)) if p1_flags else np.nan
    p2_sla = 100.0 * float(np.mean(p2_flags)) if p2_flags else np.nan

    utils = []
    for res in resources:
        if res["regular_capacity"] > 0:
            utils.append(res["worked"] / res["regular_capacity"])

    max_util_regular = 100.0 * max(utils) if utils else np.nan

    if utils:
        capped = [min(u, 1.25) for u in utils]
        s1 = sum(capped)
        s2 = sum(u * u for u in capped)
        fairness_jain = (s1 * s1) / (len(capped) * s2) if s2 > 0 else 1.0
    else:
        fairness_jain = np.nan

    metrics = {
        "mean_delay": mean_delay,
        "p95_delay": p95_delay,
        "P1_SLA": p1_sla,
        "P2_SLA": p2_sla,
        "max_util_regular": max_util_regular,
        "fairness_jain": fairness_jain,
        "handover_setup_min": total_handover + total_setup,
        "preemptions": preemptions,
        "n_cases": len(cases),
    }

    return metrics, events

# 9. Limits and validation plan

## 9.1 What cannot be concluded from the supplied data alone

The prompt provides expected arrivals, service ranges, skill multipliers, and rules, but it does not provide:

1. Actual arrival variance beyond expected block counts.
2. Correlation between case type, priority, and complexity.
3. Resource learning curves or fatigue effects.
4. Real handover failure rates or rework probabilities.
5. Whether overtime is actually available for all resources, especially Farah.
6. Whether P1 preemption is operationally allowed in all diagnostic states.
7. Whether parallel branches truly run independently or require shared physical resources.
8. Whether Validation capacity can be expanded dynamically.
9. Whether cases can safely carry over to the next day.
10. Human preferences, shift-swap rules, or fairness constraints beyond the 90% utilization guideline.

Therefore, the numerical delay estimates should be treated as scenario estimates, not guarantees.

## 9.2 Pilot design

A safe pilot should distinguish policies without endangering P1 cases.

### Phase 1: Shadow mode

Run all three policies in shadow mode for two weeks:

- Do not change actual dispatching.
- Log what each policy would have done.
- Compare predicted assignment, parallelization, and preemption decisions.
- Calibrate service-time distributions and handover/setup times using event data.

Success criterion: shadow recommendations are stable, explainable, and do not systematically overload one resource.

### Phase 2: Controlled hybrid pilot

Deploy `HYBRID` for a limited period, for example two weeks, with safeguards:

- P1 cases always have dispatch priority.
- Preemption requires supervisor-visible justification.
- P3 anti-starvation threshold is active.
- Overtime is capped and monitored.
- Crisis mode is available but manually triggered initially.

### Phase 3: A/B or switchback test

If operationally feasible, use a switchback design:

- Morning/afternoon blocks alternate between `POOL` and `HYBRID`.
- Keep `SPEC` only as a low-demand fallback.
- Protect P1 cases by requiring immediate fallback if P1 SLA risk exceeds threshold.

Primary evaluation metrics:

- P1 SLA attainment.
- P2 SLA attainment.
- p95 delay.
- resource utilization fairness.
- handover/setup minutes.
- preemption count.
- P3 starvation rate.

### Phase 4: Stress backtest

Backtest policies against historical high-load days or simulated U1/U3/U5 days. The policy should be accepted only if it maintains acceptable P1 performance under combined stress without causing unsafe P3 starvation or extreme resource unfairness.
