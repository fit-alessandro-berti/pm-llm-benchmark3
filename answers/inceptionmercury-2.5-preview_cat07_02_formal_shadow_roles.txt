# 2. Core versus peripheral activities

**Front Desk Generalists (R01, R02)**
*   **Core:** A1 (Register), A2 (Validate), A4 (Standard Response), A12 (Close). These constitute the majority of their activity counts (>70% total).
*   **Peripheral:** A3 (Diagnose), A5 (Configure). These occur only on medium complexity cases (e.g., Amira has 75 Diagnose events vs. Ben's 60).
*   **Authority:** They can close standard cases but escalate high-complexity items. Substitutions show they are stable resources, unlike temps.

**Temporary Front Desk (R11, R12)**
*   **Core:** A1, A2, A4, A12. High throughput matches permanent generalists.
*   **Peripheral:** A13 (Reopen). High reopen rate (17 cases) indicates incomplete validation notes, marking A2 as a risk point.
*   **Authority:** Limited to low complexity. Despite performing core activities, they lack the skill to handle validation notes effectively.

**Technical Specialists (R03, R04)**
*   **Core:** A3 (Diagnose), A5 (Configure), A10 (Implement). R03 and R04 perform most configuration and implementation work.
*   **Peripheral:** A6 (Security Review). R03 handles more (24 events) than R04 (6 events), indicating R03 is the senior technical specialist.
*   **Authority:** Both can implement solutions, but R03 handles more critical cases (median 0.71 vs 0.48).

**Oversight and Coordination (R08, R13)**
*   **Core:** R08 focuses on A9 (Approval). R13 focuses on cross-functional routing (sequence fragment 5).
*   **Peripheral:** A13 (Reopen), A6 (Security). R13 filters security referrals; R08 rechecks Mateo's approvals.
*   **Authority:** R08 has final sign-off authority. R13 lacks sign-off authority but coordinates complex paths.

# 3. Shadow and bridging roles

**R07_Giorgio as Commercial Shadow**
R07 acts as a commercial shadow. During R06’s absence, R07 handled 31 pricing exceptions. The similarity score (0.71) between R06 and R07 confirms significant overlap in commercial activities (A7, A8). However, R07 remains formally a Service Agent. This arrangement provides resilience against commercial specialist absence without formal role expansion.
*   **Benefit:** Business continuity during absenteeism.

**R13_Mateo as Cross-functional Escalation Broker**
R13 is a bridging role. The similarity with R08 is low (0.54), but Mateo handles 21 approvals when Hana is unavailable and coordinates sequences involving security and commercial specialists. R13 acts as a router, not a decision-maker for final approvals.
*   **Benefit:** Ensures cross-functional cases do not stall; filters critical risks from routine security checks.
*   **Risk:** Critical cases can still wait (>2 days) if filtering logic is flawed, as seen in weeks 7–8.

**R05_Erik as Rare but Critical Specialist**
R05 performs rare but critical interventions. A6 (Security Review) counts are low (96 total), but this resource handles 55 critical cases and the highest median complexity (0.86).
*   **Benefit:** Centralized control over high-risk activities.

**Automation Boundary Role (R14_Nora)**
R14 handles A1 and A2 for low-complexity cases (median 0.11). This role creates a high-volume boundary that filters simple traffic, reducing load on humans. It does not intervene in complex cases.

# 5. PM4Py role-discovery and similarity code

```python
import pandas as pd
import pm4py
from pm4py.objects.log.obj import EventLog, EventClass
from pm4py.algo.discovery.roles import discover_organizational_roles
from pm4py.algo.discovery.similarity import discover_activity_based_resource_similarity
from pm4py.algo.discovery.handover import discover_handover_of_work_network
from pm4py.algo.discovery.working_together import discover_working_together_network

# 1. Load and format dataframe
df = pd.read_csv('event_log.csv')
event_log = pm4py.format_dataframe(df, parameters={"case_id": "case:concept:name", "activity": "concept:name", "resource": "org:resource", "timestamp": "time:timestamp"})

# 2. Discover organizational roles (frequency-based)
roles = discover_organizational_roles(event_log, output_dict=True)

# 3. Discover activity-based resource similarity
similarity = discover_activity_based_resource_similarity(event_log, metric="cosine")

# 4. Compute handover and working-together networks
handover = discover_handover_of_work_network(event_log)
working_together = discover_working_together_network(event_log)

# 5. Join role discovery output with case complexity indicators
# Assuming 'df' contains case_complexity and temporary_substitution columns
role_stats = []
for res in df['org:resource'].unique():
    cases = df[df['org:resource'] == res]
    # Count high complexity cases
    high_complexity_cases = cases[cases['case_complexity'] > 0.7]
    # Count substitution episodes
    subst = cases['temporary_substitution'].sum()
    role_stats.append({
        'resource': res,
        'complexity_share': len(high_complexity_cases) / len(cases),
        'substitution_incidents': subst
    })

complexity_df = pd.DataFrame(role_stats)

# 6. Avoid over-interpreting activity-frequency clusters
# Filter resources with high similarity but low complexity/authority
# Example: Check R11/R12 against R01/R02
similar_pairs = [k for k, v in similarity.items() if v > 0.9]
# Cross-reference with complexity_df to ensure pairs aren't grouped by volume only
filtered_roles = {}
for role, resources in roles.items():
    if len(resources) > 1:
        # Check complexity variance
        complexity_values = [complexity_df[complexity_df['resource'] == r]['complexity_share'].values[0] for r in resources]
        if max(complexity_values) - min(complexity_values) > 0.3:
            # Flag as potentially misclustered if simple frequency used
            filtered_roles[role] = resources

print("Role Discovery Complete")
print(f"Potential Misclassification Groups: {filtered_roles}")
```
