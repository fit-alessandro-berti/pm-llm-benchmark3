# 1. Assumptions and Interpretation

1. **Risk choice.** The unmodeled case-data condition is represented by an XOR: either the low-risk route `Supervisor Review`, or the high-risk route containing both `Quality Review` and `Regulatory Review`. The high-risk reviews are concurrent.

2. **Supplier consultation.** The unmodeled supplier-involvement condition is represented by an XOR between silent skip and `Consult Supplier`. Consultation is therefore optional and selected at most once.

3. **Passing inspection.** Inspection outcome is not a visible label. A passing inspection is represented structurally by exiting the loop after `Inspect Trial`; a failing inspection is represented by taking the loop redo branch containing `Adjust Parameters` followed by another trial iteration.

4. **Duplicate visible labels.** Duplicate visible labels are permitted in the process-tree approximation where needed. The POWL model below avoids duplicate visible labels by using a loop submodel for the trial cycle.

5. **Process-tree approximation policy.** The process tree uses a **conservative under-approximation**: it preserves safe precedence constraints but unnecessarily serializes some activities that were intended to overlap, especially approvals relative to trial work. It does not deliberately admit releases before approvals or supplier consultation.

6. **Meaning of “may overlap.”** “May overlap” is interpreted as absence of a precedence relation, thus allowing true concurrency in the POWL model. In the process-tree approximation, some of those freedoms are intentionally lost.

7. **Completion-event interpretation.** Every visible activity denotes its completion event. Therefore, “may start after” is operationalized as precedence between completion events.

8. **Release synchronization.** `Release Material` is enabled only after a completed successful trial cycle, selected approvals, and selected supplier consultation. The process tree achieves this by sequencing those obligations before release; POWL expresses them as incoming partial-order edges.

9. **POWL partial-order semantics.** A `StrictPartialOrder` is interpreted as permitting all linearizations consistent with its edges. Nodes without an order edge between them may execute in either order and, semantically, may overlap.

# 3. PM4Py Process-Tree Model

The following compact expression documents the intended shape of the **approximate** process tree:

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->(
      'Analyze Root Cause',
      +(
        'Design Corrective Action',
        X(
          'Supervisor Review',
          +('Quality Review', 'Regulatory Review')
        ),
        X(tau, 'Consult Supplier')
      )
    )
  ),
  ->(
    *(
      ->('Execute Trial', 'Inspect Trial'),
      ->('Adjust Parameters', 'Execute Trial', 'Inspect Trial')
    ),
    'Release Material'
  ),
  'Archive Case'
)
```

The expression is explanatory only. The code below constructs an equivalent tree explicitly and assigns it to `tree`.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    return ProcessTree(label=label)


def tau():
    return ProcessTree(label=None)


def op(operator, *children):
    node = ProcessTree(operator=operator)
    for child in children:
        node.children.append(child)
        child.parent = node
    return node


# Visible activities
register = leaf("Register Deviation")
contain = leaf("Contain Material")
plan = leaf("Plan Verification")
analyze = leaf("Analyze Root Cause")
design = leaf("Design Corrective Action")

supervisor = leaf("Supervisor Review")
quality = leaf("Quality Review")
regulatory = leaf("Regulatory Review")
consult = leaf("Consult Supplier")

execute_first = leaf("Execute Trial")
inspect_first = leaf("Inspect Trial")

adjust = leaf("Adjust Parameters")
execute_redo = leaf("Execute Trial")
inspect_redo = leaf("Inspect Trial")

release = leaf("Release Material")
archive = leaf("Archive Case")

# Containment stream: containment before planning.
containment_stream = op(
    Operator.SEQUENCE,
    contain,
    plan
)

# Risk route: low-risk supervisor review OR high-risk concurrent reviews.
high_risk_route = op(
    Operator.PARALLEL,
    quality,
    regulatory
)
risk_route = op(
    Operator.XOR,
    supervisor,
    high_risk_route
)

# Optional supplier consultation: skip silently or consult once.
supplier_option = op(
    Operator.XOR,
    tau(),
    consult
)

# Analysis-dependent work.
# This preserves Analyze -> Design / approvals / supplier.
analysis_stream = op(
    Operator.SEQUENCE,
    analyze,
    op(
        Operator.PARALLEL,
        design,
        risk_route,
        supplier_option
    )
)

# Register enables containment and analysis streams concurrently.
preparation = op(
    Operator.PARALLEL,
    containment_stream,
    analysis_stream
)

# Loop encoding:
# do Execute+Inspect once; repeat Adjust + Execute + Inspect zero or more times.
# Exiting after an Inspect represents passing inspection.
trial_body = op(
    Operator.SEQUENCE,
    execute_first,
    inspect_first
)
trial_redo = op(
    Operator.SEQUENCE,
    adjust,
    execute_redo,
    inspect_redo
)
trial_loop = op(
    Operator.LOOP,
    trial_body,
    trial_redo
)

# Conservative approximation:
# all preparation obligations, including approvals and supplier if selected,
# complete before the trial loop starts.
tree = op(
    Operator.SEQUENCE,
    register,
    preparation,
    trial_loop,
    release,
    archive
)
```

The tree represents several requirements safely: registration first; containment before planning; analysis before design, approvals, and optional consultation; exclusive risk route choice; concurrent quality/regulatory review; optional single consultation; trial repetition with adjustment only on redo; and release before archive.

However, it does **not** represent the intended overlap exactly. The parallel `preparation` region must finish before the trial loop begins. Consequently, it forces selected approvals and supplier consultation to complete before `Execute Trial`, whereas the intended process permits approvals and supplier consultation to overlap trial work. It also forces `Plan Verification` and `Design Corrective Action` to be complete before the trial, which is correct, but cannot separately synchronize only those two prerequisites while leaving reviews and consultation independent until release. The tree is therefore a conservative under-approximation: it excludes valid cases where the trial starts before approvals or supplier consultation finish, but does not admit unsafe release behavior.

# 4. PM4Py POWL Model

Compact POWL description:

```text
StrictPartialOrder(
  nodes = {
    Register Deviation,
    Contain Material,
    Analyze Root Cause,
    Plan Verification,
    Design Corrective Action,
    XOR(
      Supervisor Review,
      PO(Quality Review || Regulatory Review)
    ),
    XOR(tau, Consult Supplier),
    LOOP(
      Execute Trial -> Inspect Trial,
      Adjust Parameters
    ),
    Release Material,
    Archive Case
  },

  edges = {
    Register Deviation -> Contain Material,
    Register Deviation -> Analyze Root Cause,
    Contain Material -> Plan Verification,
    Analyze Root Cause -> Design Corrective Action,
    Analyze Root Cause -> RiskRoute,
    Analyze Root Cause -> SupplierOption,
    Plan Verification -> TrialLoop,
    Design Corrective Action -> TrialLoop,
    TrialLoop -> Release Material,
    RiskRoute -> Release Material,
    SupplierOption -> Release Material,
    Release Material -> Archive Case
  }
)
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


# Individual visible activities
register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")

supervisor = Transition(label="Supervisor Review")
quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")

consult = Transition(label="Consult Supplier")

execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
adjust = Transition(label="Adjust Parameters")

release = Transition(label="Release Material")
archive = Transition(label="Archive Case")


# High-risk route: Quality and Regulatory Review have no edge between them.
high_risk_order = StrictPartialOrder([quality, regulatory])
high_risk_route = OperatorPOWL(
    Operator.PARALLEL,
    [high_risk_order]
)

# Low-risk OR high-risk route.
risk_route = OperatorPOWL(
    Operator.XOR,
    [supervisor, high_risk_route]
)

# Supplier is optional: silent skip OR one visible consultation.
supplier_option = OperatorPOWL(
    Operator.XOR,
    [SilentTransition(), consult]
)

# A successful iteration is Execute Trial followed by Inspect Trial.
trial_iteration = StrictPartialOrder([execute, inspect])
trial_iteration.order.add_edge(execute, inspect)

# POWL loop:
# body = one trial/inspection iteration;
# redo = Adjust Parameters, after which body is repeated.
# Exiting after the body represents a passing inspection.
trial_loop = OperatorPOWL(
    Operator.LOOP,
    [trial_iteration, adjust]
)

# Root partial order.
powl = StrictPartialOrder([
    register,
    contain,
    analyze,
    plan,
    design,
    risk_route,
    supplier_option,
    trial_loop,
    release,
    archive
])

# Required precedence and synchronization edges.
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

powl.order.add_edge(contain, plan)

powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, risk_route)
powl.order.add_edge(analyze, supplier_option)

powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

powl.order.add_edge(trial_loop, release)
powl.order.add_edge(risk_route, release)
powl.order.add_edge(supplier_option, release)

powl.order.add_edge(release, archive)
```

The intentionally unconnected node pairs remain concurrent because no business dependency was stated between them:

- `Contain Material` and `Analyze Root Cause` are both enabled after registration.
- `Plan Verification` and analysis-dependent work have no direct dependency after their respective prerequisites.
- `Design Corrective Action`, selected approvals, and selected supplier consultation are all analysis-dependent but otherwise unordered.
- The trial loop is constrained only by `Plan Verification` and `Design Corrective Action`; therefore selected approvals and supplier consultation may occur before, during, or after trial work, provided they finish before release.
- Within the high-risk submodel, `Quality Review` and `Regulatory Review` are intentionally unordered.
- `Consult Supplier` is unordered relative to planning, design, approvals, and trial activity after analysis.
- `Release Material` has edges from the trial loop, risk route, and supplier option, making it a synchronization point.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and analysis may proceed independently after registration. | Represents concurrency between containment stream and analysis stream. | Represents no edge between containment and analysis after registration. | Exact enough in both models. | Cases can progress containment and investigation independently. |
| Split dependencies into planning/design | Planning depends only on containment; design depends only on analysis. | Represents both dependencies. | Represents both dependencies directly with separate edges. | Essentially exact. | Avoids requiring analysis for planning or containment for design. |
| Risk route | XOR: supervisor, or concurrent quality and regulatory reviews. | Represents XOR and parallel high-risk reviews. | Represents XOR and partial-order high-risk reviews. | Essentially exact. | Preserves low/high-risk routing and high-risk dual approval. |
| Approval/trial overlap | Trial may begin once design and planning finish even if approvals remain open. | Not exact: approvals are forced to finish before trial. | Exact through absence of edges from risk route to trial loop, but edges from both to release. | Tree overconstrains. | Process tree can falsely report legitimate expedited cases as nonconforming. |
| Optional supplier consultation | Zero or one consultation after analysis; may overlap work; must finish before release if selected. | Optional once, but forced to finish before trial because it is inside preparation. | Optional once after analysis; may overlap trial and approvals; synchronized at release. | Tree overconstrains; POWL close to exact. | Tree removes legal supplier/trial overlap. |
| Repeat-until trial behavior | Execute then inspect; on failure adjust and repeat; exit only on pass. | Loop approximates this with a first iteration and zero-or-more redo sequences. | Loop body represents execution/inspection; redo represents adjustment before repetition. | Both abstract inspection outcome structurally; POWL interpretation depends on loop operator semantics. | Neither model records the actual pass/fail data value, but both distinguish exit from redo structurally. |
| Release synchronization | Passing inspection, selected approval route, and selected supplier consultation must all complete before release. | Safe, but stronger than necessary because everything is completed before trial. | Directly represented by incoming edges from trial loop, route, and supplier option. | Tree overconstrains timing; POWL is close to exact. | POWL supports legitimate concurrent work without allowing premature release. |
| Archive after release | Archive only after release. | Exact sequence. | Exact edge. | Exact. | Prevents closing a case before material release. |
| Duplicate-label risk | A visible activity should ideally correspond to one conceptual activity instance per iteration. | `Execute Trial` and `Inspect Trial` occur in both loop body and redo subtree, creating duplicate labels in the tree structure. | Uses one transition each within the loop submodel. | Tree has duplicate-label analytical ambiguity. | Label-based conformance or trace interpretation may not distinguish first versus repeated iterations. |

# 7. Preferred Representation and Validation Plan

The canonical representation should be the **POWL model**. Its strict partial order directly expresses the important non-block-structured dependencies:

- containment enables planning;
- analysis enables design, risk routing, and supplier selection;
- planning and design synchronize into the trial loop;
- approvals and supplier consultation remain independent from the trial loop;
- release synchronizes the independently progressing obligations.

The process tree remains useful as a conservative executable approximation, but it should not be treated as the authoritative behavioral specification because it serializes legal approval/supplier overlap with trial execution.

Validation plan:

1. **Convert both models where supported.**

   ```python
   import pm4py

   net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)
   net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)
   ```

2. **Check soundness of converted accepting Petri nets.**

   ```python
   pm4py.check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)
   pm4py.check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)
   ```

   Soundness should be interpreted as checking for structural problems such as deadlocks or inability to reach final marking, not as proof that the model matches the business narrative.

3. **Perform bounded or sampled playout.**

   ```python
   log_tree = pm4py.play_out(tree, variant=pm4py.algo.simulation.playout.process_tree.algorithm.Variants.BASIC_PLAYOUT)
   log_powl = pm4py.play_out(powl)
   ```

   Inspect sampled traces for:
   - low-risk and high-risk routes;
   - supplier selected and skipped;
   - one and multiple trial iterations;
   - release only after the required synchronization.

4. **Use explicit positive trace tests.** Test all five allowed witness traces. In particular, test A2 and A4 against the POWL model to confirm that approvals may finish after trial activity but before release.

5. **Use explicit negative trace tests.** Test all three forbidden witnesses and verify rejection or non-alignment:
   - trial before planning;
   - release before regulatory approval;
   - adjustment followed directly by release.

6. **Check silent behavior.** Specifically inspect traces generated through the supplier XOR skip branch. The silent skip must not create a visible event, and it must not accidentally permit more than one supplier consultation.

7. **Check duplicate-label behavior in the process tree.** Generate traces with two trial iterations and inspect the converted Petri net or event log to confirm that visible `Execute Trial` and `Inspect Trial` events appear in the intended repeated order. Because the tree has duplicate leaf labels, validate by occurrence position rather than label identity alone.

8. **Limitations.** Sampled playout cannot exhaustively demonstrate concurrency or all loop counts. Petri-net conversion and soundness checking validate the executable artifact, not the informal interpretation of POWL loop semantics. Ordinary traces also cannot show physical overlap; they show only completion-event order. Finally, the process tree’s conservative exclusion of valid overlap is intentional and should be evaluated as a policy choice rather than an implementation defect.

# 8. Final Self-Critique

1. The POWL loop uses a structural abstraction of inspection outcome. It represents “redo after failed inspection” versus “exit after passing inspection,” but it cannot record or validate actual pass/fail case data because those outcomes are not visible events.

2. The exact constructor conventions for `OperatorPOWL` can vary slightly across PM4Py versions. The code follows the stated API reminder, but deployment should be tested against the installed PM4Py release.

3. The process-tree model is deliberately conservative and therefore rejects legitimate traces in which approvals or supplier consultation overlap the trial cycle. It is executable, but it is not a faithful canonical representation of the intended operational flexibility.
