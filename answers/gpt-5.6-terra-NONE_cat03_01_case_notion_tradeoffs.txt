## 1. Analytical assumptions

**Case notion.** A case notion is an analytical projection that groups events around one object instance of a selected type. It is not assumed to be the “real” process instance. For example, an Order case groups direct E2O events of O1; a Package case groups direct E2O events of P3. These answer different questions.

**Convergence.** Convergence occurs when one event, object, or downstream lifecycle brings together multiple otherwise separate units. Examples include:

- P3 converging O2/I21 and O3/I31 at `e13`;
- P4 converging O3/I32 and O4/I41 at `e14`;
- D2 converging P2 and P3, hence O1, O2, and O3, at `e16`, `e24`;
- V2 converging O2 and O3 at `e19`, `e22`, `e25`.

**Divergence.** Divergence occurs when one business unit branches into multiple downstream objects or event streams. O1 diverges into P1 and P2 (`e11`, `e12`), then into D1 and D2 (`e15`, `e16`), with deliveries confirmed separately (`e23`, `e24`). O3 diverges across P3 and P4.

**Copied shared events.** I treat copied events as both:

1. **Evidence** of genuine interaction, because direct E2O relations explicitly say that, for example, `e16` concerns O1, O2, O3, P2, P3, and D2.
2. **Duplication in a flattened event log**, because the same real-world event is repeated in multiple cases. Thus occurrence counts and DFG edge counts are not counts of independent executions unless deduplicated or interpreted as object-incidence counts.

**Permitted transformations.** The baseline is always the supplied direct E2O relation set. I would permit a separate, explicitly labelled propagated-relation variant, but never silently substitute it for direct E2O. Examples:

- propagate package events from P3 to its packed items I21 and I31, or to O2 and O3 via item containment;
- propagate delivery D2’s events to P2/P3 and then to their items/orders;
- propagate V2 payment events to O2 and O3 through `bills`.

Such propagation can support “end-to-end responsibility” analysis, but it creates inferred relations and can amplify convergence even further. Direct and propagated results must therefore be compared rather than merged uncritically.

## 3. Concrete distortion analysis

1. **Order flattening — cross-order package P3 creates repeated fulfilment evidence.**  
   `e13` is directly related to O2 and O3 as well as I21, I31, and P3. In an Order flattening, both O2 and O3 contain `Pack Package`; similarly both contain `e16` and `e24`. The DFG edge `Pack Package  Dispatch` and then `Dispatch  Confirm Delivery` receives two order-case occurrences from one package P3 and one delivery D2. This is harmful if interpreted as two independent warehouse executions; informative if interpreted as the number of order incidences touched by a shared package.

2. **Order flattening — cross-order package P4 serializes O3’s two package branches.**  
   O3 is involved in P3 (`e13`, `e16`, `e24`) and P4 (`e14`, `e17`, `e27`). A single O3 trace orders them by timestamp and may display an apparent variant such as `Pack Package  Pack Package  Dispatch  Dispatch  ...`. That looks like rework or repeated packaging in a linear DFG, whereas it is split fulfilment across distinct items I31 and I32. Harmful for diagnosing loops; informative for detecting split-order fulfilment only if package identities remain available.

3. **Package flattening — P3 hides two order lifecycles behind one simple package trace.**  
   P3’s direct package trace is `e13 Pack Package  e16 Dispatch  e24 Confirm Delivery`. This appears clean and complete. Yet it is a cross-order package carrying I21/O2 and I31/O3. The apparent package variant is valid for warehousing, but harmful if interpreted as a single customer-order journey or used to attribute D2 delivery delay to only one order.

4. **Package flattening — P4 obscures asymmetric order completion.**  
   P4 has `e14  e17  e27`, involving O3 and O4. O3 also has prior P3/D2 activity; O4 does not. The package DFG hides that the same package is the final fulfilment branch for O3 but the sole branch for O4. Context-dependent: appropriate for package performance, insufficient for order-completeness decisions.

5. **Delivery flattening — consolidated D2 makes a three-order shipment look like one homogeneous case.**  
   D2 contains P2 and P3 and is directly associated in `e16`/`e24` with O1, O2, O3, I12, I21, I31. The delivery case has only `Dispatch  Confirm Delivery` with a three-hour interval. This is informative for D2 transport/confirmation SLA, but harmful if the interval is called “order delivery lead time” for O1, O2, or O3. O1’s other package was dispatched earlier in D1 at `e15` and confirmed at `e23`.

6. **Order flattening — D2 inflates the frequency of shared dispatch and confirmation.**  
   The single operational dispatch `e16` is copied into O1, O2, and O3 cases. Therefore, Order-level counts may report three `Dispatch` occurrences attributable to order traces although only one dispatch event took place. Likewise `e24` becomes three `Confirm Delivery` occurrences. Harmful for resource workload or event-volume claims; informative for “orders affected per dispatch.”

7. **Order flattening — consolidated invoice V2 manufactures two parallel billing paths.**  
   `e19 Issue Invoice`, `e22 Record Payment`, and `e25 Record Payment` are directly related to both O2 and O3 through V2. Order flattening yields each of O2 and O3 a billing/payment sequence. A DFG may therefore count two `Issue Invoice  Record Payment` transitions, while there was one invoice V2 and one first instalment M2. Harmful for invoice-volume and payment-event frequency analysis; informative for exposure of both orders to one receivable.

8. **Invoice flattening — partial payments can be mistaken for duplicate payment activity.**  
   V2’s trace is `e19 Issue Invoice  e22 Record Payment  e25 Record Payment`, where M2 is `partially_settles` and M3 `completes_settlement`. With only the activity label “Record Payment,” the DFG shows a self-loop or repeated activity. That can be wrongly labelled rework, duplicate posting, or delay. It is informative if payment object IDs and O2O qualifiers distinguish instalment versus completion.

9. **Payment flattening — near-singleton lifecycles are analytically degenerate.**  
   M1 appears only in `e21`, M2 only in `e22`, M3 only in `e25`, and M4 only in `e26`. Each Payment case is a one-event trace. A traditional DFG contains no meaningful control-flow edges, and any case duration is zero or undefined. This is harmful for end-to-end process discovery, but useful for payment-event audit counts, timing by event timestamp, and reconciliation against invoices.

10. **Item flattening — apparently complete fulfilment hides financial non-completion.**  
    I21’s direct sequence includes `e07 Add Item  e13 Pack Package  e16 Dispatch  e24 Confirm Delivery`. It ends at delivery confirmation, but the related invoice V2 is only fully settled after `e25` the next day. Thus an Item DFG may imply a completed lifecycle at `e24`, despite O2’s commercial settlement completing later. Harmful for order-to-cash compliance; appropriate for physical item fulfilment.

11. **Order flattening — temporal performance is biased by split delivery semantics.**  
    For O1, `e15` dispatches P1 and `e16` dispatches P2, while `e23` confirms D1 and `e24` confirms D2. A standard order trace forces a sequence of two dispatches followed by confirmations. Time from first dispatch to final confirmation is a valid “last-piece delivery” measure, but not a carrier transit-time measure; time from last dispatch to first confirmation is nonsensical as a single flow. Context-dependent, requiring explicit milestone definitions.

12. **Invoice flattening — invoice duration is not order duration under consolidation.**  
    V2 takes from `e19` at 12:05 to final settlement `e25` at 09:00 next day. This duration belongs to the shared invoice, not separately to O2 and O3. Attributing it independently to each order double-counts financial exposure and masks whether the customer or commercial arrangement was actually shared. Harmful for per-order payment-delay statistics unless allocation rules are supplied.

## 4. Traditional versus object-centric analysis portfolio

I would create several flattened logs, but label them as purpose-specific projections rather than a canonical event log.

| Flattened log | Questions it can answer relatively safely | Important limitation |
|---|---|---|
| Order | Customer-facing order milestones; frequency of split fulfilment; elapsed time from `Create Order` to `Close Order`; whether an order is touched by invoice/payment events. | Shared events such as `e16`, `e19`, and `e22` are duplicated across orders; it cannot distinguish independent work from shared work without event IDs and object interaction context. |
| Item | Item-level physical fulfilment: add-to-pack, pack-to-dispatch, dispatch-to-confirm; comparison of I11 versus I12, or I31 versus I32. | It excludes direct billing/payment/closure events, so it is not order-to-cash. |
| Package | Warehouse execution and package cycle time: P1–P4 pack-to-dispatch-to-confirm. | It has no direct creation, billing, payment, or order closure lifecycle. |
| Delivery | Carrier/delivery performance: dispatch-to-confirm times for D1–D3; detection of consolidated deliveries such as D2. | It begins at dispatch and ignores upstream preparation and downstream financial closure. |
| Invoice | Invoice issue-to-final-settlement analysis, especially V2’s staged payment. | It should retain M2/M3 identifiers or relation qualifiers; otherwise repeated `Record Payment` is ambiguous. |
| Payment | Audit/reconciliation counts by M1–M4 and relationships to invoices. | Not a viable traditional process log because traces are near-singletons. |

Questions requiring object-centric analysis include:

- **How often do orders share physical execution?** Use an object interaction summary and an OTG. P3 links O2/O3; P4 links O3/O4; D2 links O1/O2/O3.
- **Which activity transitions occur for which object types without forcing one case notion?** Use an OC-DFG, retaining object type and frequency definitions.
- **How do event-object participation patterns differ?** Use an ET–OT graph: `e16` and `e24` should visibly connect Order, Item, Package, and Delivery types; `e19`, `e22`, `e25` connect Order, Invoice, and Payment.
- **Are there structurally different executions rather than merely different flattened variants?** Use equivalent-execution clustering cautiously, especially for orders. O1 is split across two packages/deliveries, O2 is bundled with O3 in P3/V2, O3 spans P3/P4 and V2, and O4 shares P4 with O3 but has V3.
- **How does consolidation affect business objects?** Use O2O plus E2O interaction graphs rather than one DFG. The central question is not merely sequence but shared-object topology.

Contradictions should be reconciled by asking what each metric counts. If Order flattening reports three dispatch occurrences from `e16`, while the delivery view reports one, this is not necessarily an error: the former is three order incidences, the latter one delivery event. Report both with explicit denominators: unique event count, affected-order count, affected-package count, and affected-delivery count. Every surprising flattened edge should be traced back to the shared event IDs and their direct E2O relation sets.

## 5. Lead-object decision

**B. Use a primary lead object plus explicitly secondary lifecycles.**

### Decision criteria

1. Coverage of customer/business commitment from initiation to closure.
2. Ability to preserve meaningful timestamps and milestones.
3. Degree to which shared operational and financial work can be interpreted without pretending it is independent.
4. Availability of secondary objects for the major convergences: package/delivery and invoice/payment.
5. Fitness for the intended end-to-end question: order fulfilment, not only warehouse or finance.

### Primary lead object

Use **Order** as the primary lead object for customer-facing end-to-end analysis, with strong qualifications.

Orders are the only listed type directly present from creation (`e01–e04`) through item addition, packing/dispatch/delivery participation, invoice/payment participation, and closure (`e28–e31`). O1, for example, has a legible commitment lifecycle from `e01` to `e28`; O2 and O3 connect to the consolidated financial lifecycle V2; O4 connects to V3/M4.

### Explicitly secondary lifecycles

- **Package and Delivery** for physical execution and consolidation: P3/P4 reveal cross-order packing; D2 reveals three-order delivery consolidation.
- **Invoice and Payment** for financial execution: V2 and M2/M3 preserve partial versus completed settlement.
- **Item** for line-level fulfilment and split-order completeness.
- Payment should be audit-level rather than a standalone lifecycle lead.

### Strongest supporting evidence

Order is the only direct-E2O type spanning the major business lifecycle boundaries:

- starts with `Create Order` (`e01–e04`);
- ends with `Close Order` (`e28–e31`);
- participates in physical fulfilment (`e11–e17`, `e23–e24`, `e27`);
- participates in billing/payment (`e18–e22`, `e25–e26`).

No other type offers that breadth. Package and Delivery begin too late; Invoice begins at billing; Payment is nearly singleton; Item omits finance and close.

### Strongest counterargument

Order flattening strongly distorts execution because it turns shared objects into copied events and forces divergent package/delivery branches into one sequence. `e16` and `e24` are especially problematic: one D2 event is copied to O1/O2/O3. V2 similarly creates duplicated invoice/payment paths for O2/O3. Thus Order is not a reliable unit for event workload, warehouse control flow, or invoice counts.

### Residual risk

Even with secondary views, analysts may read an Order DFG as if it were a literal execution log. O3 is especially risky because it spans P3/P4, D2/D3, and shared V2. Its trace is long not because it necessarily followed one linear path, but because it participates in several overlapping object lifecycles.

### Conditions for changing the decision

I would move to **Position C, reject a single lead object**, if the primary business question shifted toward operational coordination across warehouse, transport, and finance rather than customer-order completion; if shared/consolidated fulfilment became the dominant norm; or if order closure events were absent or not meaningful. I would choose Package as the lead only for a warehouse-centric objective, Delivery for carrier SLA work, and Invoice for receivables analysis.

## 6. PM4Py analysis outline

```python
import pm4py
from collections import Counter

# The OCEL is assumed to already exist as variable: ocel
print(ocel)

# Basic inspection: exact APIs can vary slightly by PM4Py version / OCEL backend.
events_df = ocel.events
objects_df = ocel.objects
relations_df = ocel.relations

print("\nActivity frequencies:")
activity_frequencies = events_df["ocel:activity"].value_counts(dropna=False)
print(activity_frequencies)

print("\nObject-type frequencies:")
object_type_frequencies = objects_df["ocel:type"].value_counts(dropna=False)
print(object_type_frequencies)

selected_object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

# Traditional flattened projections: direct E2O-based unless the OCEL itself was
# explicitly transformed beforehand.
flattened_logs = {}
dfgs = {}
dfg_starts = {}
dfg_ends = {}
log_skeletons = {}

for object_type in selected_object_types:
    flat_log = pm4py.ocel_flattening(ocel, object_type)
    flattened_logs[object_type] = flat_log

    dfg, start_activities, end_activities = pm4py.discover_dfg(flat_log)
    dfgs[object_type] = dfg
    dfg_starts[object_type] = start_activities
    dfg_ends[object_type] = end_activities

    log_skeletons[object_type] = pm4py.discover_log_skeleton(flat_log)

print("\nFlattened-log DFGs and skeletons created for:")
print(list(flattened_logs.keys()))

# Object-centric discovery: retain multi-object participation rather than
# forcing events into a single object-type case notion.
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
interaction_summary = pm4py.ocel_objects_interactions_summary(ocel)

print("\nOC-DFG:")
print(ocdfg)

print("\nObject-type graph:")
print(otg)

print("\nEvent-type / object-type graph:")
print(etot)

print("\nObject interaction summary:")
print(interaction_summary)

# Lead-object decision B: Order is primary, but clustering is used only as a
# supplementary structural analysis. It does not make Order the uniquely true case.
order_equivalent_execution_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    leading_type="Order"
)

print("\nEquivalent OCEL execution clusters using Order as a qualified lead:")
print(order_equivalent_execution_clusters)

# Important methodological note:
# - Compare direct-E2O flattenings above with a separately constructed,
#   explicitly labelled propagated-relation OCEL if desired.
# - Do not interpret DFG frequencies from flattened logs as unique operational
#   event counts when shared events such as e16/e24/e19/e22/e25 are copied.
# - Keep event IDs and object IDs available for drill-down from every edge.
```

## 7. Sensitivity and validation plan

1. **Remove or down-weight copied shared events.**  
   For each flattened Order log, calculate both:
   - ordinary edge frequency, where `e16` contributes once in each of O1/O2/O3;
   - unique-event-weighted frequency, where each event has total weight 1 split across its related cases of the selected type.  
   For `e16`, each of the three Order cases would receive weight 1/3; for `e19`, O2 and O3 each receive 1/2. Compare whether dominant edges remain dominant after weighting.

2. **Direct E2O versus explicitly propagated E2O.**  
   Build a second OCEL representation in which package/delivery events may be propagated through declared O2O relationships, for example P3  I21/I31  O2/O3 and D2  P2/P3  relevant items/orders. Compare it with the direct view. If an edge appears only after propagation, report it as inferred responsibility/context, not observed event participation. In particular, test how invoice/payment visibility changes for item and package cases.

3. **Change the lead object.**  
   Repeat key statistics with Order, Package, Invoice, and Delivery leads. Compare:
   - start/end activities;
   - median and maximum durations;
   - dominant variants;
   - edge frequency rankings.  
   If Order reports many repeated pack/dispatch events while Package reports one clean sequence per P1–P4, interpret the difference as divergence/convergence structure rather than choosing whichever log looks simpler.

4. **Compare OC-DFG frequency semantics.**  
   For the OC-DFG, inspect frequencies based on:
   - unique events;
   - unique objects;
   - total object incidences.  
   `e16` should differ materially: one unique dispatch event, one delivery object D2, two packages P2/P3, three orders O1/O2/O3, and three involved items I12/I21/I31. The chosen metric must match the claim: operational workload, object exposure, or network connectivity.

5. **Partial-payment attribute/qualifier sensitivity.**  
   In Invoice analysis, split `Record Payment` into analytically distinct labels using the O2O qualifier or payment identity: “partial settlement” for M2 and “complete settlement” for M3. Compare this with the unmodified activity label. If the self-loop disappears under qualification, the original loop should not be called rework.

6. **Milestone-definition sensitivity for split orders.**  
   For O1 and O3, calculate several measures separately:
   - creation to first dispatch;
   - creation to last dispatch;
   - first dispatch to first delivery confirmation;
   - last dispatch to last confirmation;
   - invoice issue to final payment;
   - creation to close.  
   This prevents a single flattened trace duration from obscuring the fact that O1 and O3 have multiple package and delivery branches.

7. **Interaction-based validation.**  
   Validate all high-frequency flattened patterns against the interaction graph. Any claimed “common order variant” involving `Pack Package  Dispatch  Confirm Delivery` should be checked for whether it is driven by shared objects P3/P4 or D2 rather than independent repeated behaviour. Similarly, validate financial patterns against V2 and M2/M3.

8. **Manual event-level trace-back.**  
   For every surprising DFG edge or long waiting time, trace it to event IDs and direct E2O memberships. For example, verify that O2/O3 invoice-payment sequences refer to the same V2 events, and that the apparent three-order dispatch count arises from one `e16`. This is the final safeguard against treating flattening artifacts as process facts.
