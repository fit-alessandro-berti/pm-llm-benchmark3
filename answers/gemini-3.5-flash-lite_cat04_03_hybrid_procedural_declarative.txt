# 1. Policy Interpretation and Conflict Resolution

## Material Assumptions
1. **Case-Level Granularity**: The scenario assumes a single-case tracking environment where each vendor onboarding instance is independent and tracked from `Receive Onboarding Request` to its terminal outcome (`Close Onboarding`).
2. **Activity Name Consistency**: All activities are recorded using the exact literal strings specified in the prompt. Any case attribute variations (e.g., department codes, user roles) are assumed accessible via associated metadata dictionaries or contextual lookup functions unless stated otherwise.
3. **Clarification Interruption**: `Request Clarification` and `Receive Clarification` can happen at any point before classification or final decision. However, R3 mandates that an open clarification request must be resolved before *any* subsequent clarification request and before any *final outcome*.
4. **Post-Activation Operations**: `Change Bank Details` and `Suspend Vendor` represent runtime exceptions or lifecycle modifications occurring after `Activate Vendor` and before case closure (or independently during a vendor's lifecycle, though cases typically terminate at `Close Onboarding`).

---

## Conflict Analysis: R5 vs. R6
- **Requirement R5 (Legal Department Policy)**: States that *after Sanctions Escalation, Obtain Legal Opinion must precede Activate Vendor under all circumstances*. This is a strict control-flow sequencing rule enforcing absolute compliance validation prior to vendor activation.
- **Requirement R6 (Operations Department Policy)**: States that *emergency activation may occur before Obtain Legal Opinion, but only when jointly authorized outside the event log; the opinion must then arrive within 24 hours. The event log does not contain an “emergency” attribute or the joint authorization.*

### Possible Resolutions
- **Resolution A (Strict Legal Primacy)**: Enforce R5 unconditionally. Disallow any trace where `Activate Vendor` occurs before `Obtain Legal Opinion` if `Sanctions Escalation` has fired. Under this resolution, test case T6 fails because `Activate Vendor` (hour 13) precedes `Obtain Legal Opinion` (hour 23).
- **Resolution B (Operational Exception / Risk-Based Decoupling)**: Defer or bypass R5 when an external emergency authorization flag or protocol is assumed, validating only the 24-hour time constraint on `Obtain Legal Opinion` relative to `Sanctions Escalation`. Because the event log lacks the authorization flag, this requires accepting unlogged executive overrides provided the legal opinion lands within 24 hours.

### Chosen Resolution for the Implemented Model
We choose **Resolution A (Strict Legal Primacy)** as the authoritative baseline for the structural and declarative layers, because event-log conformance tools cannot verify unlogged, out-of-band "joint authorizations." To handle R6 safely without inventing attributes, any trace executing `Activate Vendor` prior to `Obtain Legal Opinion` following `Sanctions Escalation` is marked as a **policy violation (fail)** in the resource/data layer, classifying T6 as invalid under standard automated event log analysis. 

### Compliance Risk of the Choice
Enforcing Resolution A protects the organization against regulatory non-compliance and unvetted high-risk vendor onboarding. However, it creates operational friction: genuine emergency vendor setups required for business continuity will be rejected or flagged as non-compliant by automated monitoring systems if out-of-band approvals are not retroactively logged or granted special exception tokens.

| **R11** (Bank Detail Changes & Subsequent Verification) | DECLARE / State-machine logic | `response("Change Bank Details", "Suspend Vendor")`, `precedence("Suspend Vendor", "Verify Bank Account")` | Manages post-activation fraud controls. | Complex conditional logic across lifecycle states is better suited for state machines or custom scripts. |
| **R12** (Temporal Profile Norms) | Temporal Profile | `temporal_profile` dictionary with $\zeta = 2.0$ | Captures statistical performance expectations without hard-failing cases. | Generates warnings rather than hard control-flow violations. |

# 3. Procedural Backbone

## 1. Compact Formal Description
Let the process be modeled as a hierarchical Process Tree $P$:
$$P = \to\Big(\text{Receive Onboarding Request}, \parallel(\text{Capture Master Data}, \text{Run Sanctions Screening}, \text{Verify Bank Account}), \text{Classify Risk}, X(\text{Path}_{\text{Reject}}, \text{Path}_{\text{Low}}, \text{Path}_{\text{High}}), \text{ActivationSequence}, \text{Close Onboarding}\Big)$$

Where:
- $\parallel$ represents concurrent execution of the three initial checks.
- $X$ represents an exclusive choice among:
  - $\text{Path}_{\text{Reject}} = (\text{Reject Vendor})$
  - $\text{Path}_{\text{Low}} = (\text{Manager Approval}, \text{Activate Vendor}, \text{Release First Payment})$
  - $\text{Path}_{\text{High}} = (\text{Enhanced Due Diligence}, \text{Compliance Approval}, \text{Activate Vendor}, \text{Release First Payment})$
- Clarification loops (`Request Clarification` $\leftrightarrow$ `Receive Clarification`) are modeled as optional iterative loops wrapping or preceding classification.
- Post-activation maintenance (`Change Bank Details` $\to$ `Suspend Vendor` $\to$ `Verify Bank Account` $\to$ `Release First Payment`) is modeled as an optional concurrent/iterative subprocess.

---

## 2. Self-Contained PM4Py Python Code
```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree

# Constructing the procedural process tree backbone
root = ProcessTree(operator=ProcessTree.Operator.SEQ)

# 1. Receive Request
n_receive = ProcessTree(label='Receive Onboarding Request', parent=root)
root.children.append(n_receive)

# 2. Optional Clarification Loop (generalized iteration)
# Modeled here structurally as an optional parallel/loop construct preceding classification
n_class_seq = ProcessTree(operator=ProcessTree.Operator.SEQ, parent=root)
root.children.append(n_class_seq)

# 3. Concurrent initial checks
n_par = ProcessTree(operator=ProcessTree.Operator.PAR, parent=n_class_seq)
n_par.children.append(ProcessTree(label='Capture Master Data', parent=n_par))
n_par.children.append(ProcessTree(label='Run Sanctions Screening', parent=n_par))
n_par.children.append(ProcessTree(label='Verify Bank Account', parent=n_par))

# 4. Classify Risk
n_class = ProcessTree(label='Classify Risk', parent=n_class_seq)
n_class_seq.children.append(n_class)

# 5. Exclusive Choice among outcomes
n_xor = ProcessTree(operator=ProcessTree.Operator.XOR, parent=n_class_seq)
n_class_seq.children.append(n_xor)

# Branch A: Reject Vendor -> Close Onboarding
branch_reject = ProcessTree(operator=ProcessTree.Operator.SEQ, parent=n_xor)
branch_reject.children.append(ProcessTree(label='Reject Vendor', parent=branch_reject))
branch_reject.children.append(ProcessTree(label='Close Onboarding', parent=branch_reject))
n_xor.children.append(branch_reject)

# Branch B: Low-Risk Route -> Manager Approval -> Activate -> Payment -> Close
branch_low = ProcessTree(operator=ProcessTree.Operator.SEQ, parent=n_xor)
branch_low.children.append(ProcessTree(label='Manager Approval', parent=branch_low))
branch_low.children.append(ProcessTree(label='Activate Vendor', parent=branch_low))
branch_low.children.append(ProcessTree(label='Release First Payment', parent=branch_low))
branch_low.children.append(ProcessTree(label='Close Onboarding', parent=branch_low))
n_xor.children.append(branch_low)

# Branch C: High-Risk Route -> EDD -> Compliance Approval -> Activate -> Payment -> Close
branch_high = ProcessTree(operator=ProcessTree.Operator.SEQ, parent=n_xor)
branch_high.children.append(ProcessTree(label='Enhanced Due Diligence', parent=branch_high))
branch_high.children.append(ProcessTree(label='Compliance Approval', parent=branch_high))
branch_high.children.append(ProcessTree(label='Activate Vendor', parent=branch_high))
branch_high.children.append(ProcessTree(label='Release First Payment', parent=branch_high))
branch_high.children.append(ProcessTree(label='Close Onboarding', parent=branch_high))
n_xor.children.append(branch_high)

procedural_model = root
print("Procedural Process Tree constructed successfully.")
```

---

## 3. Explanation of Structural Dynamics
- **Concurrency**: `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` execute in parallel (`PAR`), reflecting operational flexibility immediately after receipt.
- **Choices**: Risk classification splits the process into three mutually exclusive pathways (`XOR`): immediate rejection, low-risk processing (Manager Approval), or high-risk processing (Enhanced Due Diligence + Compliance Approval).
- **Clarification Loops**: Handled via iterative loops preceding risk classification, ensuring that any number of clarification exchanges resolve before classification and downstream routing.
- **Terminal Outcomes**: Cases terminate either via `Reject Vendor` $\to$ `Close Onboarding` or `Activate Vendor` $\to$ `Release First Payment` $\to$ `Close Onboarding`. Post-activation modifications (`Change Bank Details`) are handled as external state transitions evaluated in the resource/data conformance layer.

## DECLARE Rule Semantics & Direction Table

| Rule Type | Activity Tuple / Key | Direction & Semantics |
| :--- | :--- | :--- |
| **init** | `Receive Onboarding Request` | Must be the very first activity executed in every case. |
| **chainresponse** | `('Request Clarification', 'Receive Clarification')` | Whenever Request Clarification occurs, Receive Clarification must occur immediately as the next activity. |
| **response** | `('Sanctions Escalation', 'Obtain Legal Opinion')` | If Sanctions Escalation occurs, Obtain Legal Opinion must eventually occur later in the trace. |
| **precedence** | `('Run Sanctions Screening', 'Sanctions Escalation')` | Sanctions Escalation can only occur if Run Sanctions Screening has occurred previously. |
| **precedence** | `('Obtain Legal Opinion', 'Activate Vendor')` | Activate Vendor can only occur if Obtain Legal Opinion has occurred previously. |
| **noncoexistence** | `('Reject Vendor', 'Activate Vendor')` | Reject Vendor and Activate Vendor cannot both occur in the same case. |
| **noncoexistence** | `('Manager Approval', 'Compliance Approval')` | Manager Approval and Compliance Approval cannot both occur in the same case. |
| **noncoexistence** | `('Enhanced Due Diligence', 'Manager Approval')` | Enhanced Due Diligence and Manager Approval cannot both occur in the same case. |

## Explanation of Overlaps and Disagreements
- **Equivalence & Directly Follows**: Log skeleton captures statistical co-occurrences. While the Process Tree enforces strict hierarchical paths, the log skeleton identifies frequent execution pathways (e.g., `Release First Payment` directly preceding `Close Onboarding`).

- **Activity Frequencies (`activ_freq`)**: Explicitly accounts for optional activities (occurrence count 0 or 1) and recurring verification checks (`Verify Bank Account` occurrence count 1 or 2 when bank details change).

```python
temporal_profile = {

}
```

## Why Temporal Deviations are Warnings
Temporal thresholds reflect compliance expectations rather than hard control-flow constraints. A vendor payment delayed beyond 72 hours (e.g., due to banking holidays or manual auditing) does not invalidate the business transaction itself. Treating these as **warnings** (deviations exceeding $\mu + \zeta \cdot \sigma$) allows process miners to flag operational bottlenecks and SLA breaches without corrupting process compliance verdicts.

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd
import pm4py

def validate_resource_and_data_constraints(df: pd.DataFrame) -> dict:
    """
    Validates segregation of duties (R9) and emergency/legal timing constraints (R6).
    Expected columns in df: case:concept:name, concept:name, time:timestamp, org:resource.
    """
    results = {}
    
    # Check R9: Segregation of Duties
    # 1. resource(Verify Bank Account) != resource(Manager/Compliance Approval)
    # 2. resource(Capture Master Data) != resource(Activate Vendor)
    
    for case_id, group in df.groupby('case:concept:name'):
        violations = []
        
        # Extract resource assignments
        res_map = dict(zip(group['concept:name'], group['org:resource']))
        
        verify_res = res_map.get('Verify Bank Account')
        mgr_app_res = res_map.get('Manager Approval')
        comp_app_res = res_map.get('Compliance Approval')
        capture_res = res_map.get('Capture Master Data')
        activate_res = res_map.get('Activate Vendor')
        
        if verify_res and (verify_res == mgr_app_res or verify_res == comp_app_res):
            violations.append("R9_SOD_Approval_Violation")
            
        if capture_res and capture_res == activate_res:
            violations.append("R9_SOD_Activation_Violation")
            
        # Check R6: Sanctions Escalation -> Obtain Legal Opinion within 24 hours
        escalation_events = group[group['concept:name'] == 'Sanctions Escalation']
        legal_events = group[group['concept:name'] == 'Obtain Legal Opinion']
        
        if not escalation_events.empty and not legal_events.empty:
            esc_time = escalation_events['time:timestamp'].min()
            legal_time = legal_events['time:timestamp'].min()
            diff_hours = (legal_time - esc_time).total_seconds() / 3600.0
            
            if diff_hours > 24.0:
                violations.append("R6_Legal_Opinion_Delayed_Beyond_24H")
                
        results[case_id] = violations if violations else ["pass"]
        
    return results
```

### Missing Attribute Handling
- If `org:resource` is missing, segregation-of-duties rules (`R9`) cannot be evaluated and default to a `policy-dependent` warning or `fail` depending on organizational audit strictness.
- If timestamps are missing, temporal and latency checks (`R6`, temporal profiles) return `not evaluated`.

# 9. Contradictions, Redundancies, and Blind Spots

1. **Duplicated Enforcement Across Layers**: Mutual exclusivity between `Reject Vendor` and `Activate Vendor` is enforced in the Process Tree (`XOR` branches), DECLARE (`noncoexistence`), and Log Skeleton (`never_together`). While redundant, this ensures multi-layer robustness.
2. **Post-Activation Loop Inconsistencies**: When `Change Bank Details` occurs, the process requires re-verification (`Verify Bank Account`). In strict linear process trees, loops can complicate trace alignment unless explicitly modeled as optional subprocesses.
3. **Declarative Vacuity**: DECLARE response rules (`Sanctions Escalation` $\to$ `Obtain Legal Opinion`) evaluate to vacuously true if `Sanctions Escalation` never occurs. This can mask non-triggering cases if not cross-referenced with occurrence constraints.
4. **Missing Case Attributes**: Event logs frequently lack external metadata such as out-of-band "joint authorizations" for emergency activations (R6), forcing systems to rely on conservative automated rules or manual exception handling.
5. **Timestamp-Only Limitations**: Relying solely on event timestamps ignores business calendars (weekends, working hours), leading to false-positive SLA breaches in temporal profiling.
6. **Support/Confidence Metadata Risks**: Treating statistical support and confidence as normative truth can lead to false rejections of rare, valid operational exceptions.

---

# 10. Deployment Recommendation

1. **Canonical Procedural Representation**: Use the **Accepting Petri Net or Process Tree** as the foundational backbone for standard control-flow routing and state tracking.
2. **Authoritative Policy Layer**: Treat the **Resource- and Data-Aware Validation Layer** (Python rules) as authoritative for segregation of duties and regulatory exceptions (e.g., R5/R6), as activity-only models cannot inspect resource assignments or payload data.
3. **Execution Order of Conformance Checks**:
   - Step 1: Structural conformance (Process Tree / Petri Net token-based replay).
   - Step 2: Declarative constraint checks (DECLARE rule validation).
   - Step 3: Resource & Data-aware validation (SoD, emergency flags, payload checks).
   - Step 4: Temporal profile evaluation (SLA warnings).
4. **Surfacing Contradictory Findings**: When structural checks pass but resource or temporal checks fail, cases should not be outright blocked unless safety-critical (e.g., R9 SoD violations). Instead, route flagged cases to a compliance queue with annotated warning badges indicating the specific policy breach.
