## 1. Equivalence design space

### 1. Activity-sequence equivalence

**Definition.** Two executions are activity-sequence equivalent when their ordered sequences of activity labels are identical after removing object identifiers and object references. Event multiplicity and order are retained.

For example, X1 and X2 both reduce to:

`Create Order, Add Item, Add Item, Pack Package, Dispatch, Issue Invoice, Record Payment`

**Preserved invariants**

- Activity labels.
- Number of events of each label.
- Total event order.
- Repetition of labels.

**Discarded information**

- Object types and E2O incidence.
- Number of objects per event.
- O2O topology.
- Local versus external objects.
- Qualified relations such as `partial_settles`, `removed_before_dispatch`, and `replaces`.
- Whether an event concerns one package or several.
- Item/package/delivery/payment multiplicity except indirectly through repeated activity labels.

**Algebraic properties.** Equality of normalized label sequences is reflexive, symmetric, and transitive.

**Concurrency / same timestamps.** A total-order variant should break ties deterministically, for example by event id. A more defensible concurrent variant compares layers of simultaneous events as multisets of labels rather than imposing an arbitrary order. In this answer, the displayed timestamp order is treated as the total order.

Activity-sequence clusters:

- `A1`: X1, X2, X5, X6, X7
- `A2`: X3
- `A3`: X4
- `A4`: X8

---

### 2. Typed structural equivalence under identifier renaming

**Definition.** Two executions are typed-structurally equivalent if there exists a bijection between their **local** objects, preserving object type, and an order-preserving bijection between events such that:

1. corresponding events have the same activity;
2. E2O incidence is preserved, including object types and repeated references;
3. O2O relations are preserved as typed edges;
4. object multiplicities and event participation patterns are preserved.

External objects are not freely renamed into local objects. They are represented as typed external boundary nodes, for example `Order[external]` or `Item[external]`. Their concrete external identifier is ignored, but their external status and type are retained.

A strict structural version treats all supplied O2O relation labels and qualifiers as graph labels. Thus an unqualified `packs` edge differs from a `packs` edge qualified with `removed_before_dispatch`.

**Preserved invariants**

- Activity order.
- Event-to-object incidence.
- Object types.
- Counts of items, packages, deliveries, invoices, payments, and external objects.
- Package-to-item and delivery-to-package topology.
- Whether financial or logistics objects are shared externally.
- O2O qualifiers.
- Repeated event occurrences.

**Discarded information**

- Local identifiers such as `O1`, `I11`, and `P11`.
- Incidental identifier order, such as X2 adding `I22` before `I21`.
- External identifier values themselves, while preserving externality and object type.

**Algebraic properties.** Typed graph isomorphism with labels is reflexive, symmetric, and transitive.

**Concurrency / same timestamps.** Events at equal timestamps should be represented as unordered nodes within a timestamp layer, or as a partial order. The isomorphism must preserve precedence constraints, not an arbitrary event-id ordering. The examples have an explicit order, so ordered-event isomorphism is sufficient.

Typed-structural clusters:

- `T1`: X1, X2
- `T2`: X3
- `T3`: X4
- `T4`: X5
- `T5`: X6
- `T6`: X7
- `T7`: X8

---

### 3. Preferred business-semantic equivalence

**Definition.** My preferred relation compares a canonicalized order-centered lifecycle signature. It preserves business-relevant multiplicities, boundary sharing, qualified O2O semantics, and lifecycle motifs, while ignoring local IDs and harmless ordering of exchangeable same-role events.

Two executions are semantically equivalent when they have the same values for:

1. **Order composition:** item count and item replacement/removal pattern.
2. **Fulfilment topology:** package count; package-to-item allocation; delivery count; delivery-to-package allocation.
3. **Cross-order coupling:** whether packages, deliveries, invoices, or payments involve external order/item objects.
4. **Financial topology:** invoice count, invoice-to-order sharing, payment count per invoice, and settlement qualifiers.
5. **Lifecycle motifs:** standard fulfilment, split fulfilment, consolidated shipment, multiple deliveries, partial payment, substitution/removal, return/repack/re-dispatch.
6. **Causal/temporal milestones:** creation before fulfilment; return after initial dispatch; repack before replacement dispatch. It does not distinguish harmless permutations of independent `Add Item` events.

This is deliberately coarser than complete typed isomorphism but finer than activity sequences.

**Preserved invariants**

- Business-relevant object multiplicities.
- Shared external-object involvement.
- Core allocation topology.
- Payment multiplicity and partial/completion status.
- Replacement, return, and repack motifs.
- Major lifecycle ordering constraints.

**Discarded information**

- Local identifiers.
- Which anonymous item happens to be called `I11` versus `I12`.
- Order among independently added items.
- Exact timestamps where they do not alter the lifecycle motif.
- Low-level topology distinctions not material to the selected business vocabulary.

**Algebraic properties.** If semantic equivalence is equality of a deterministic canonical signature, it is reflexive, symmetric, and transitive. This matters: “looks operationally similar” is not necessarily transitive, so informal similarity should not be called an equivalence relation unless converted into explicit signature classes.

**Concurrency / same timestamps.** Independent events at the same time are compared as a multiset or partial-order layer. If two events share a package, item, or delivery, their dependency edges remain meaningful. Thus concurrent independent `Add Item` events do not split a cluster.

Preferred semantic clusters:

- `S1 Standard isolated single-package fulfilment`: X1, X2
- `S2 Split packaging, consolidated delivery`: X3
- `S3 Split delivery with staged settlement`: X4
- `S4 Cross-order logistics coupling`: X5
- `S5 Cross-order financial coupling`: X6
- `S6 Substitution/removal before dispatch`: X7
- `S7 Return, repack, and re-dispatch`: X8

A fourth useful relation would be a **motif-level similarity** relation that groups X3 and X4 as “split fulfilment,” despite different delivery and payment structure. It is useful analytically but should be expressed as a hierarchical category rather than claimed as the same exact equivalence class.

## 2. Canonical signatures

The following Python-like outline creates an order-centered semantic signature. It assumes event ordering is available and O2O notes have been transformed into normalized relationship records.

```python
from collections import Counter, defaultdict

LOCAL = "local"
EXTERNAL = "external"

def object_scope(obj_id):
    return EXTERNAL if str(obj_id).startswith("EXT") else LOCAL

def canonical_semantic_signature(execution):
    """
    execution.events: ordered event objects:
      event.activity
      event.objects: dict {object_type: iterable of ids}
    execution.o2o: edges:
      edge.src, edge.dst, edge.relation, edge.qualifier
    """

    # Normalize objects to typed anonymous nodes.
    # Local ids are deliberately not preserved.
    objs_by_type_scope = defaultdict(set)
    for event in execution.events:
        for typ, ids in event.objects.items():
            for obj_id in ids:
                objs_by_type_scope[(typ, object_scope(obj_id))].add(obj_id)

    counts = {
        f"{typ}:{scope}": len(ids)
        for (typ, scope), ids in sorted(objs_by_type_scope.items())
    }

    # Event sequence retains repeated labels, but anonymous object IDs are removed.
    activities = tuple(event.activity for event in execution.events)

    # Extract typed, qualifier-aware O2O edge counts.
    o2o_counter = Counter()
    for edge in execution.o2o:
        key = (
            edge.relation,
            edge.qualifier or "",
            edge.src.type,
            object_scope(edge.src.id),
            edge.dst.type,
            object_scope(edge.dst.id),
        )
        o2o_counter[key] += 1

    # Business motifs, computed from E2O/O2O structure.
    package_count = counts.get("Package:local", 0)
    delivery_count = counts.get("Delivery:local", 0)
    invoice_count = counts.get("Invoice:local", 0)
    payment_count = counts.get("Payment:local", 0)

    has_external_logistics = any(
        scope == EXTERNAL and typ in {"Order", "Item", "Package", "Delivery"}
        for typ, scope in objs_by_type_scope
    )
    has_external_finance = any(
        scope == EXTERNAL and typ in {"Order", "Invoice", "Payment"}
        for typ, scope in objs_by_type_scope
    )

    qualifiers = Counter(
        edge.qualifier for edge in execution.o2o if edge.qualifier
    )

    motifs = {
        "split_packages": package_count > 1,
        "split_deliveries": delivery_count > 1,
        "partial_payment": qualifiers["partially_settles"] > 0,
        "completed_payment": qualifiers["completes_settlement"] > 0,
        "replacement_or_removal": (
            qualifiers["removed_before_dispatch"] > 0
            or qualifiers["replaces"] > 0
        ),
        "return_repack": (
            "Return Item" in activities
            and "Inspect Return" in activities
            and activities.count("Pack Package") >= 2
        ),
        "external_logistics": has_external_logistics,
        "external_finance": has_external_finance,
    }

    # Canonical, hashable representation.
    return (
        ("activity_multisequence", activities),
        ("typed_scope_counts", tuple(sorted(counts.items()))),
        ("o2o_edge_counts", tuple(sorted(o2o_counter.items()))),
        ("motifs", tuple(sorted(motifs.items()))),
        ("payment_count", payment_count),
        ("invoice_count", invoice_count),
    )
```

For the preferred semantic relation, one may omit distinctions judged operationally irrelevant from the signature, but each omission must be documented. For example, removing `activities` entirely makes the relation more robust to logging differences but risks conflating return/repack and ordinary split delivery.

## 4. Cluster interpretations

### S1 — Standard isolated single-package fulfilment

**Signature:** two items, one package, one delivery, isolated invoice, one payment, no exceptional qualifiers.

**Business behavior:** ordinary end-to-end order fulfilment.

**Risks/opportunities:** baseline for service-time benchmarking, straight-through-processing measurement, and conformance checking.

**Poorly represented by:** flattened order-event logs that lose package/item allocation; they may still look adequate here, but cannot distinguish this from X5, X6, or X7.

**Repair stability:** high. Renaming IDs, reordering independent adds, or repairing duplicate links should not change membership.

### S2 — Split packaging, consolidated delivery

**Signature:** multiple packages mapped to one delivery.

**Business behavior:** warehouse splitting occurs, but downstream transport is consolidated.

**Risks/opportunities:** package-handling complexity without multiple customer-facing shipments; potential consolidation optimization.

**Poorly represented by:** order-level flattening, which may show only one dispatch and hide the two-package workload.

**Repair stability:** high unless package-delivery links are incomplete or one package is incorrectly omitted.

### S3 — Split delivery with staged settlement

**Signature:** multiple packages and deliveries; one invoice; multiple payments with partial and completion qualifiers.

**Business behavior:** staged fulfilment and staged cash collection.

**Risks/opportunities:** delivery coordination, customer communication, credit risk, reconciliation complexity.

**Poorly represented by:** flattening on Order, because separate dispatches and payment statuses become merely repeated labels; flattening on Invoice hides fulfilment staging.

**Repair stability:** moderate. It depends on payment qualifiers being reliable. If payments are merely duplicate records, the class may collapse toward a split-delivery, single-settlement variant.

### S4 — Cross-order logistics coupling

**Signature:** local order participates in package/delivery logistics that also include external order/item objects; billing remains local.

**Business behavior:** mixed-order shipment, shared package, or joint logistics handling.

**Risks/opportunities:** allocation ambiguity, customs/labeling errors, cross-order contamination, but possible consolidation savings.

**Poorly represented by:** lead-order flattening, which makes X5 appear identical to X1.

**Repair stability:** moderate to high. It is stable if external references are authoritative; it disappears if external links are treated as accidental contamination.

### S5 — Cross-order financial coupling

**Signature:** logistics is isolated, but invoice and payment are shared across orders.

**Business behavior:** consolidated billing or combined settlement.

**Risks/opportunities:** revenue-allocation ambiguity, reconciliation burden, credit exposure shared across orders.

**Poorly represented by:** Order or Invoice flattening alone. The former hides shared billing; the latter may hide which fulfilment streams belong to each billed order.

**Repair stability:** moderate. A reliable allocation table could convert the shared financial process into separate order-level financial cases.

### S6 — Substitution/removal before dispatch

**Signature:** package initially relates to two items, one is qualified as removed before dispatch or replaced.

**Business behavior:** fulfilment substitution, stock correction, or late order amendment.

**Risks/opportunities:** inventory accuracy, customer dissatisfaction, wrong-item risk, and root-cause analysis of substitutions.

**Poorly represented by:** activity-only flattening, which makes X7 indistinguishable from X1.

**Repair stability:** low to moderate because it depends strongly on qualifier quality.

### S7 — Return, repack, and re-dispatch

**Signature:** dispatch, return, inspection, repack, second dispatch, with package replacement for one item.

**Business behavior:** reverse logistics followed by corrective fulfilment.

**Risks/opportunities:** avoidable return cost, quality issues, carrier handling, but also recovery effectiveness.

**Poorly represented by:** order flattening that treats repeated pack/dispatch as duplicated activity rather than a return loop.

**Repair stability:** high when return and inspection events are present; lower if the return is logged only as a replacement package.

## 5. Borderline cases

### X1 versus X2

Under activity-sequence equivalence, they are equal. Under typed structural equivalence, they are also equal because a type-preserving renaming maps `O1` to `O2`, items to items, and so on. A naive raw-ID exact comparison would incorrectly separate them. If exact event order is considered meaningful, the reversed anonymous item-add order still does not matter because the two `Add Item` events have identical structure after renaming.

### X1 versus X5

Activity-sequence equivalence groups them. A lead-order-only projection could also group them if it removes external references. Typed structural and preferred semantic equivalence separate them because X5 has an external order and item coupled to package and dispatch operations. The business distinction is mixed-order logistics rather than ordinary isolated fulfilment.

### X1 versus X6

Again, activity labels group them. A local-object multiplicity summary may also group them because both have one invoice and one payment. The preferred semantic relation separates them because the invoice and payment span multiple orders. One defensible coarser finance-insensitive definition could group them when only local fulfilment performance is of interest.

### X1 versus X7

Activity sequence and unqualified E2O incidence may group them. Qualifier-aware structural and semantic equivalence separate them: X7 has a replacement/removal lifecycle. A quality-insensitive throughput analysis might intentionally group them; substitution-rate monitoring must not.

### X3 versus X4

Both are “split fulfilment” under a high-level motif taxonomy. They differ under activity, structural, and preferred semantic equivalence: X3 has two packages in one delivery and one payment, whereas X4 has two deliveries and staged payment. A transportation-focused clustering could distinguish delivery multiplicity but ignore payment differences; a warehouse-only clustering could group them.

### X4 versus X8

Both involve multiple fulfilment legs and potentially repeated packing/dispatch. A coarse “multi-stage fulfilment” definition can group them. The preferred relation separates them because X8 contains an explicit return, inspection, replacement package, and re-dispatch; X4 is planned or staged split delivery rather than reverse logistics. Treating second dispatches without causal return information as equivalent would be risky.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` is useful for exact OCEL-style execution clustering, but its usefulness depends on what is included in the key representation. In general, an exact key based on event activity, object references, object types, event-object incidence, and related structure preserves more than a flat activity trace. If raw object IDs occur in the key, equivalent executions such as X1 and X2 can be separated solely because `O1 != O2`.

The remedy is to canonicalize each connected execution before exact comparison, or to post-process exact clusters using a local-ID-invariant signature. Externality must be retained explicitly rather than erased during renaming.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

# Exact PM4Py clustering. API details can vary by PM4Py version.
raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=LEAD_TYPE,
    max_objs=200
)

def semantic_key_from_cluster(cluster_ocel):
    # Convert cluster OCEL to order-centered executions, then apply the
    # canonical_semantic_signature described in Section 2.
    # Local object ids are anonymized; EXT-prefixed objects retain external flag.
    executions = extract_order_centered_executions(cluster_ocel, lead_type=LEAD_TYPE)
    return tuple(sorted(canonical_semantic_signature(x) for x in executions))

# Aggregate exact PM4Py clusters into coarser business-semantic groups.
semantic_clusters = defaultdict(list)
for exact_cluster_id, cluster_ocel in enumerate(raw_clusters):
    key = semantic_key_from_cluster(cluster_ocel)
    semantic_clusters[key].append(exact_cluster_id)

for key, exact_ids in semantic_clusters.items():
    print("semantic group:", key)
    print("contains exact PM4Py clusters:", exact_ids)
```

Exact equivalence is preferable for audit reproducibility, debugging transformations, regression testing, and detecting literal process-model variants. Coarser semantic clustering is preferable for operational segmentation, where identifier noise and harmless structural detail should not dominate.

`max_objs` matters because object-centric connected components can become large through shared invoices, packages, or deliveries. A large cross-order connected execution can exceed practical memory or runtime limits, or be truncated/filtered depending on the implementation. For Order-centered analysis, use a clearly documented extraction radius and boundary treatment: retain external objects as summarized boundary nodes rather than blindly expanding the full connected component.

## 7. Robustness analysis

1. **Ignore all O2O qualifiers.**  
   X7 may merge with X1/X2 if its only distinguishing information is `removed_before_dispatch`. X4 may lose its staged-settlement distinction if `partially_settles` and `completes_settlement` are discarded, though two payment events still distinguish it from X3. X8 remains distinct because return/repack events and repeated dispatches remain visible.

2. **Ignore external objects.**  
   X5 can merge with X1/X2 because its local sequence and local topology match the baseline. X6 can also merge with X1/X2 if invoice sharing is visible only through the external order reference. This is acceptable only for deliberately local, order-contained analyses.

3. **Collapse repeated same-label events.**  
   X4 becomes dangerously simplified: two dispatches become one conceptual dispatch and two payments become one conceptual payment, potentially making it resemble X1 or X3. X8 loses evidence of re-dispatch if repeated `Pack Package` and `Dispatch` are collapsed. Repeated events should normally be retained.

4. **Treat Pack and Dispatch order as partial rather than total.**  
   X1 and X2 remain together. X4’s staged structure remains because package-to-delivery allocation distinguishes the legs even if timestamps are partly concurrent. X8 remains distinct because return must causally follow initial dispatch and precede repack/re-dispatch. Only harmless reordering of independent operations should disappear.

5. **Treat payment multiplicity as an amount attribute rather than structure.**  
   If X4’s two payments are aggregated into one amount-valued settlement, X4 remains different from X3 due to two deliveries, but the financial motif becomes less distinctive. This may be appropriate for revenue reporting but not for collections-process analysis.

## 8. Limitations and recommendation

For **compliance monitoring**, use qualifier-aware typed structural equivalence or explicit conformance rules. Compliance often depends on whether a replacement, partial settlement, or shared invoice occurred, not merely on the visible activity sequence.

For **operational segmentation**, use the preferred business-semantic equivalence. It produces interpretable groups such as isolated fulfilment, split fulfilment, shared logistics, shared billing, and return/rework.

For **root-cause analysis**, retain the richest qualified structural representation, possibly augmented with attributes such as reason codes, quantities, shipment service level, and payment amounts. X7 and X8 especially require causal and qualifier detail.

For **descriptive reporting**, use a coarser motif taxonomy or activity-sequence grouping, but report counts of packages, deliveries, returns, and shared objects alongside it. Pure activity traces are easy to communicate but hide the object-centric causes of variation.

No single equivalence is best because the same difference can be noise for one question and decisive evidence for another. Local identifiers are normally noise; externality, allocation topology, and qualified relations are often not.
