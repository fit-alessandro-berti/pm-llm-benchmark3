# 1. Review Scope and Assumptions

This review distinguishes four primary use cases for the process model:

1. **Exploration/Discovery**: Understanding process variants, identifying bottlenecks, and generating hypotheses. Here, high fitness and simplicity are prioritized over precision, as false positives are less harmful than false negatives.

2. **Conformance Checking/Enforcement**: Detecting deviations from approved process paths. Requires high precision and clear semantics for mandatory activities. Fitness must be balanced with precision to avoid false compliance signals.

3. **Simulation/What-If Analysis**: Predicting process outcomes under different scenarios. Requires a model that generalizes to unseen but plausible variants while rejecting truly non-compliant behavior.

4. **Stakeholder Communication**: Serving as a reference for process owners, auditors, and IT. Must be interpretable, maintainable, and reflect policy nuances (e.g., correction handling).

The acceptable fitness/precision trade-off shifts with use case:
- Exploration tolerates lower precision (Model S's 0.584) if fitness is high.
- Enforcement demands high precision (Model C's 0.941) even at the cost of lower fitness.
- Simulation requires both generalization and precision.
- Communication prioritizes simplicity and clarity over metric perfection.

Key assumptions:
- The log is incomplete (missing Supplier Review events, no external/internal flag, no "affected check" attribute).
- Policy P1-P7 are correct but underspecified (e.g., "affected by correction" is ambiguous).
- The model must handle both internal and external orders, though the log does not distinguish them.
- Runtime and maintainability are secondary to correctness for enforcement, but critical for exploration.

# 3. Adversarial Review of Model S

**Strongest case for Model S**:
1. **Exploration-friendly**: High fitness and simplicity make it ideal for discovering process variants and bottlenecks. Its permissiveness ensures rare but valid paths (e.g., B5) are not falsely rejected.
2. **Robust to missing data**: Tolerates missing Supplier Review events (F4) and handles unseen combinations better than Model C (B5).
3. **Fast and maintainable**: Low runtime and no duplicate labels (F3) make it practical for IT and operations.
4. **Stakeholder-friendly**: High comprehension score (4.4) suggests it can serve as a communication tool.
5. **Generalizes well**: High holdout fitness and token-based generalization suggest it captures the process's "essence" without overfitting.

**Strongest case against Model S**:
1. **Policy violations**: Admits forbidden behavior (B3, B4, B8) and skips mandatory checks (F1). Its permissiveness is not just noise tolerance but semantic incorrectness.
   - **B3**: `Register Dossier  Manager Approval  Release Order` (skips mandatory checks).
   - **B4**: `Register Dossier  Expedite Review  Credit Check  Technical Review  Manager Approval  Release Order` (Expedite Review before mandatory checks).
   - **B8**: `Register Dossier  Credit Check  Technical Review  Credit Check  Manager Approval  Release Order` (repeated Credit Check without correction).
2. **Low precision**: 0.584 precision means it allows many non-compliant paths, making it unsuitable for enforcement (F7 is not a valid defense for compliance).
3. **Ambiguous semantics**: The `+` operator allows any order of checks, including none, violating P2 (mandatory checks). The `X` for approval does not enforce "exactly one" (P5) if silent transitions are involved.
4. **Correction handling**: Cannot distinguish between valid and suspicious rechecks (B6, B8). P6 requires repeating only affected checks, but Model S allows any recheck.
5. **Supplier Review**: Treats it as optional for all cases, violating P3 (required for external orders).

**Concrete undesirable behaviors admitted by Model S**:
1. `Register Dossier  Release Order` (skips all checks and approval).
2. `Register Dossier  Supplier Review  Release Order` (skips mandatory checks).
3. `Register Dossier  Expedite Review  Release Order` (skips mandatory checks).
4. `Register Dossier  Credit Check  Technical Review  Correct Dossier  Manager Approval  Release Order` (skips rechecks after correction).
5. `Register Dossier  Credit Check  Technical Review  Auto Approval  Manager Approval  Release Order` (dual approval, violating P5).

# 4. Adversarial Review of Model C

**Strongest case for Model C**:
1. **Audit-ready**: High precision (0.941) and explicit enumeration of frequent variants make it suitable for compliance (F8). It rejects forbidden behavior (B3, B4, B8).
2. **Policy adherence**: Explicitly models mandatory checks (P2), Supplier Review (P3), and approval (P5). Handles correction paths (though imperfectly).
3. **Negative behavior rejection**: Low holdout fitness may reflect correct rejection of unseen but non-compliant variants (e.g., B5 is plausible but not in training).
4. **Transparency**: Enumerated paths make it easier to audit which variants are allowed (though this is offset by duplicate labels).

**Strongest case against Model C**:
1. **Overfitting**: Low holdout fitness (0.744) and generalization (0.412) suggest it memorizes training variants rather than learning general rules. Rejects valid unseen combinations (F2, F4).
   - Example: B5 (`Supplier Review + Auto Approval + alternate check order`) is plausible but likely rejected.
2. **Maintainability**: 33 duplicate labels and enumerated branches make updates difficult (F2, F3). Adding a new variant requires modifying the model.
3. **Correction handling**: Only models a single correction path (repeating both checks), violating P6 (should repeat only affected checks). Cannot handle `Correct Dossier  Technical Review` alone (B6).
4. **Precision artifact**: High precision may reflect positive-log-only evaluation (F5). Without negative traces, precision is overstated.
5. **Runtime**: Slow alignment (0.440s) hinders exploration and real-time monitoring.
6. **Stakeholder comprehension**: Low score (1.9) makes it unusable for communication.

**Branch enumeration and unseen combinations**:
- Model C's paths are a subset of possible valid variants. It rejects:
  - Any path not in its enumerated list, even if valid (e.g., B5).
  - Paths with `Auto Approval` and `Supplier Review` (not in training).
  - Paths with `Expedite Review` after `Supplier Review` (only one order is allowed).
- This brittleness is a feature for enforcement but a bug for exploration.

**Duplicate labels**:
- Likely caused by silent transitions or repeated activities (e.g., `Credit Check` appears in multiple branches). Complicates impact analysis (F3) and ownership.

# 6. Likely Metric Pathologies

Ranked by decision impact:

1. **Positive-log-only precision (F5)**
   - *Impact*: High. Precision scores are inflated because they only compare against observed positive traces. Neither model was evaluated against negative behavior (e.g., B3, B4, B8).
   - *Evidence*: Model C's 0.941 precision is likely overstated. Model S's 0.584 may be artificially low if the log contains noise.
   - *Fix*: Curate a negative trace suite (e.g., B3, B4, B8) and recompute precision.

2. **Fitness rewarded by optionalizing mandatory behavior**
   - *Impact*: High. Model S achieves high fitness by making mandatory checks optional (e.g., B3 is accepted). This is a semantic flaw, not noise tolerance.
   - *Evidence*: Model S's near-perfect fitness (0.992) and low precision (0.584).
   - *Fix*: Use a metric that penalizes skipping mandatory activities (e.g., weighted fitness).

3. **Generalization rewarded by excessive permissiveness**
   - *Impact*: High. Model S's high generalization (0.907) may reflect its simplicity, not correctness. It generalizes by allowing forbidden paths.
   - *Evidence*: Model S accepts B3, B4, B8.
   - *Fix*: Use a generalization metric that accounts for policy violations (e.g., penalize forbidden paths).

4. **Holdout degradation due to unseen combinations (F4)**
   - *Impact*: Medium. Model C's low holdout fitness (0.744) may reflect correct rejection of non-compliant variants (e.g., B5) or overfitting to training variants.
   - *Evidence*: F4 notes holdout cases combine `Supplier Review + Auto Approval`, which may be valid but unseen.
   - *Fix*: Stratify holdout cases by attributes (e.g., external/internal) and policy-relevant combinations.

5. **Missing-event bias**
   - *Impact*: Medium. The log may omit `Supplier Review` events (F4), biasing both models. Model S treats it as optional; Model C may overfit to observed cases.
   - *Evidence*: P3 requires `Supplier Review` for external orders, but the log lacks the external/internal flag.
   - *Fix*: Impute missing events or use a model that can handle attribute uncertainty.

6. **Duplicate-label effects (F3)**
   - *Impact*: Medium. Model C's 33 duplicate labels complicate analysis but may not affect metrics directly. Could inflate precision if duplicates are treated as distinct.
   - *Evidence*: Undocumented definition of "duplicate label." Likely caused by silent transitions or repeated activities.
   - *Fix*: Document label semantics and recompute metrics with deduplication.

7. **Alignment-cost sensitivity**
   - *Impact*: Low. Alignment costs were not reported, so fitness/precision scores may not be comparable.
   - *Evidence*: Neither team supplied alignment-cost settings.
   - *Fix*: Standardize alignment costs and recompute metrics.

8. **Stakeholder-score methodology**
   - *Impact*: Low. The 1-5 comprehension score is informal and unvalidated. May reflect simplicity bias.
   - *Evidence*: Model S's simplicity (0.918) correlates with high comprehension (4.4).
   - *Fix*: Use a validated protocol (e.g., task-based comprehension tests).

9. **Runtime confounding by model size**
   - *Impact*: Low. Model C's slower runtime (0.440s) is likely due to its size, but this is less critical than correctness.
   - *Evidence*: Model S is simpler and faster.
   - *Fix*: Profile alignment to separate model size from implementation inefficiencies.

10. **Train/holdout leakage or split sensitivity**
    - *Impact*: Low. No evidence of leakage, but the 80/20 split may not preserve rare variants.
    - *Evidence*: No random seeds or preprocessing details.
    - *Fix*: Use stratified splits and publish seeds.

# 7. Third Alternative

**Design goals**:
1. **Safer than Model S**: Enforce mandatory checks (P2), Supplier Review (P3), and approval (P5) without over-permissiveness.
2. **More generalizable than Model C**: Handle unseen but valid combinations (e.g., B5) without enumerating all paths.
3. **Maintainable**: Avoid duplicate labels and branch enumeration.
4. **Policy-aware**: Distinguish valid from suspicious rechecks (P6, P7) and handle Expedite Review ordering (P4).
5. **Attribute-aware**: Account for missing external/internal flag and "affected check" attribute.

**Strategy**: A **block-structured procedural backbone** with **DECLARE constraints** for policy nuances. The backbone enforces the core process flow, while DECLARE handles:
- Mandatory checks (P2).
- Supplier Review for external orders (P3).
- Expedite Review ordering (P4).
- Approval exclusivity (P5).
- Correction/recheck logic (P6, P7).

**Limitations**:
- Cannot fully handle `external/internal` or `affected check` without log attributes.
- DECLARE constraints add complexity for stakeholders.

**Formal description**:
1. **Procedural backbone**:
   - `Register Dossier`  (mandatory checks in any order)  (optional Supplier Review)  (optional Expedite Review)  (exactly one approval)  `Release Order`.
   - Mandatory checks: `Credit Check` and `Technical Review` (P2).
   - Supplier Review: optional but required for external orders (P3). Since the log lacks the external flag, we model it as optional but add a DECLARE constraint to flag missing Supplier Review for external cases (if known).
   - Expedite Review: optional, must follow mandatory checks (P4).
   - Approval: exactly one of `Manager Approval` or `Auto Approval` (P5).
   - Correction: `Correct Dossier` can occur after mandatory checks, followed by rechecks of affected activities (P6). Since the log lacks "affected check," we model rechecks as optional but add a DECLARE constraint to flag suspicious rechecks (P7).

2. **DECLARE constraints**:
   - **Mandatory checks**: `Credit Check` and `Technical Review` must occur exactly once before approval.
   - **Supplier Review**: If the order is external (unknown), flag traces without `Supplier Review` for review.
   - **Expedite Review ordering**: `Expedite Review` must follow both mandatory checks.
   - **Approval exclusivity**: `Manager Approval` and `Auto Approval` are mutually exclusive.
   - **Correction/recheck**: After `Correct Dossier`, at least one mandatory check must repeat. Flag rechecks without `Correct Dossier` as suspicious (P7).

**PM4Py code**:

```python
from pm4py.objects.process_tree import util as pt_util
from pm4py.objects.process_tree import obj as pt
from pm4py.objects.declare import obj as declare
from pm4py.objects.petri_net import obj as petri

def create_model_third():
    # Procedural backbone: block-structured process tree
    register = pt.ProcessTree(label="Register Dossier")
    credit = pt.ProcessTree(label="Credit Check")
    tech = pt.ProcessTree(label="Technical Review")
    supplier = pt.ProcessTree(label="Supplier Review", optional=True)
    expedite = pt.ProcessTree(label="Expedite Review", optional=True)
    correct = pt.ProcessTree(label="Correct Dossier", optional=True)
    manager = pt.ProcessTree(label="Manager Approval")
    auto = pt.ProcessTree(label="Auto Approval")
    release = pt.ProcessTree(label="Release Order")

    # Mandatory checks in any order (P2)
    checks = pt.OperatorPOWL(pt_util.Operator.XOR_LOOP)
    checks.children.append(credit)
    checks.children.append(tech)

    # Optional Supplier Review (P3)
    supplier_seq = pt.OperatorPOWL(pt_util.Operator.SEQUENCE)
    supplier_seq.children.append(supplier)

    # Optional Expedite Review, must follow mandatory checks (P4)
    expedite_seq = pt.OperatorPOWL(pt_util.Operator.SEQUENCE)
    expedite_seq.children.append(expedite)

    # Optional Correction, followed by rechecks (P6)
    correct_seq = pt.OperatorPOWL(pt_util.Operator.SEQUENCE)
    correct_seq.children.append(correct)
    rechecks = pt.OperatorPOWL(pt_util.Operator.XOR_LOOP)
    rechecks.children.append(credit)
    rechecks.children.append(tech)
    correct_seq.children.append(rechecks)

    # Exactly one approval (P5)
    approval = pt.OperatorPOWL(pt_util.Operator.XOR)
    approval.children.append(manager)
    approval.children.append(auto)

    # Main sequence
    main_seq = pt.OperatorPOWL(pt_util.Operator.SEQUENCE)
    main_seq.children.append(register)
    main_seq.children.append(checks)
    main_seq.children.append(supplier_seq)
    main_seq.children.append(expedite_seq)
    main_seq.children.append(correct_seq)
    main_seq.children.append(approval)
    main_seq.children.append(release)

    # Convert to Petri net for DECLARE constraints
    net, im, fm = pm4py.convert_to_petri_net(main_seq)

    # DECLARE constraints
    declare_model = declare.DeclareModel()

    # Mandatory checks (P2)
    declare_model.add_constraint(
        declare.ActivityExistence("Credit Check", 1, 1),
        declare.ActivityExistence("Technical Review", 1, 1)
    )
    declare_model.add_constraint(
        declare.Precedence("Credit Check", "Manager Approval"),
        declare.Precedence("Technical Review", "Manager Approval"),
        declare.Precedence("Credit Check", "Auto Approval"),
        declare.Precedence("Technical Review", "Auto Approval")
    )

    # Supplier Review for external orders (P3)
    # Since external flag is missing, we flag traces without Supplier Review for review
    declare_model.add_constraint(
        declare.NotCoExistence("Supplier Review", "Release Order", flag_missing=True)
    )

    # Expedite Review ordering (P4)
    declare_model.add_constraint(
        declare.Precedence("Credit Check", "Expedite Review"),
        declare.Precedence("Technical Review", "Expedite Review")
    )

    # Approval exclusivity (P5)
    declare_model.add_constraint(
        declare.ExclusiveChoice("Manager Approval", "Auto Approval")
    )

    # Correction/recheck (P6, P7)
    declare_model.add_constraint(
        declare.AlternateResponse("Correct Dossier", "Credit Check"),
        declare.AlternateResponse("Correct Dossier", "Technical Review")
    )
    # Flag rechecks without correction as suspicious (P7)
    declare_model.add_constraint(
        declare.NotSuccession("Credit Check", "Credit Check", flag_suspicious=True),
        declare.NotSuccession("Technical Review", "Technical Review", flag_suspicious=True)
    )

    return main_seq, declare_model

model_third, declare_model = create_model_third()
```

**Semantics**:
1. **Mandatory checks**: Enforced by the procedural backbone and DECLARE constraints. Both `Credit Check` and `Technical Review` must occur exactly once before approval.
2. **Supplier Review**: Optional in the backbone but flagged if missing (for external orders).
3. **Expedite Review**: Optional but must follow mandatory checks (DECLARE constraint).
4. **Approval**: Exactly one of `Manager Approval` or `Auto Approval` (XOR in backbone, DECLARE constraint).
5. **Correction/recheck**:
   - `Correct Dossier` is optional.
   - After correction, at least one mandatory check must repeat (DECLARE `AlternateResponse`).
   - Repeated checks without correction are flagged as suspicious (DECLARE `NotSuccession`).

**Limitations**:
- Cannot distinguish external/internal orders, so `Supplier Review` is flagged rather than enforced.
- Cannot distinguish which check is affected by correction, so both are allowed to repeat.
- DECLARE constraints add complexity for stakeholders.

# 9. Validation Experiments

**Evaluation program**:

1. **Reproducible case splits**:
   - Use stratified 80/20 splits with fixed seeds (e.g., `random_state=42`).
   - Stratify by:
     - Presence of `Supplier Review` (proxy for external orders).
     - Presence of `Correct Dossier`.
     - Approval type (`Manager` vs `Auto`).
   - Publish preprocessing code (e.g., handling missing events, duplicates).

```python
from sklearn.model_selection import train_test_split

def stratified_split(log, test_size=0.2, random_state=42):
    # Extract case attributes for stratification
    cases = {}
    for trace in log:
        case_id = trace.attributes["concept:name"]
        has_supplier = any(e["concept:name"] == "Supplier Review" for e in trace)
        has_correct = any(e["concept:name"] == "Correct Dossier" for e in trace)
        has_auto = any(e["concept:name"] == "Auto Approval" for e in trace)
        cases[case_id] = (has_supplier, has_correct, has_auto)

    # Stratify by attributes
    case_ids = list(cases.keys())
    stratify = [f"{s}_{c}_{a}" for s, c, a in cases.values()]
    train_ids, test_ids = train_test_split(
        case_ids, test_size=test_size, stratify=stratify, random_state=random_state
    )

    # Split log
    train_log = [trace for trace in log if trace.attributes["concept:name"] in train_ids]
    test_log = [trace for trace in log if trace.attributes["concept:name"] in test_ids]
    return train_log, test_log
```

3. **Missing-event and duplicate-event perturbation tests**:
   - Remove `Supplier Review` events to test robustness to missing data.
   - Duplicate `Credit Check` events to test recheck handling.

```python
def perturb_log(log, remove_activity=None, duplicate_activity=None):
    perturbed = []
    for trace in log:
        new_trace = trace.copy()
        if remove_activity:
            new_trace = [e for e in new_trace if e["concept:name"] != remove_activity]
        if duplicate_activity:
            new_trace = []
            for e in trace:
                new_trace.append(e)
                if e["concept:name"] == duplicate_activity:
                    new_trace.append(e)  # duplicate
        perturbed.append(new_trace)
    return perturbed
```

```python
def alignment_cost_sensitivity(log, model, cost_range=(1, 5)):
    results = {}
    for cost in range(cost_range[0], cost_range[1] + 1):
        fitness = pm4py.fitness_alignments(log, model, parameters={
            pm4py.util.constants.PARAMETER_CONSTANT_ACTIVITY_KEY: "concept:name",
            pm4py.util.constants.PARAMETER_CONSTANT_RESOURCE_KEY: "org:resource",
            "pm4py:param:align_cost": cost
        })
        results[cost] = fitness
    return results
```

6. **Soundness and reachability checks**:
   - Verify the model is sound (no deadlocks, no livelocks) and can reach all activities.

```python
def check_soundness(model):
```

```python
        precision = pm4py.precision_alignments(log, net, im, fm)

    # Generalization

    simplicity = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")

    return {
        "fitness": fitness,
        "precision": precision,
        "generalization": generalization,
        "simplicity": simplicity
    }
```
