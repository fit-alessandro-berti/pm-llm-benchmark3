# 4. Network and conformance analyses

The supplied material contains summaries rather than event rows. The following is an **implementation skeleton and analysis design**, not newly computed findings.

## Establish the event and identity semantics

Preserve the raw export and construct a separately versioned reconstruction. In particular:

* Distinguish the **actual decision-maker**, clerical `entered_by`, `approved_by`, shared login, and bot identity. Do not resolve identities by blindly taking the first non-null field.
* Separate actual occurrence/signature time from posting, migration, and ingestion times. Normalize source time zones; do not impose the analyst’s local calendar.
* Use consistent lifecycle semantics. Resolve tied timestamps through genuine audit sequence numbers where available; otherwise retain ordering uncertainty.
* Obtain source event, PO, payment, maintenance-ticket, and override identifiers where possible. Mass maintenance replicated across cases must not become fictitious independent activity.

These additions address the specific attribution and linkage limitations in the supplied evidence. They are proposed enrichments, not existing columns in the export.  

## Four-eyes filtering and an all-occurrence cross-check

Use `keep_violations=True` to retain candidate violations. Also cross-check all occurrences explicitly: the inspected PM4Py pandas implementation reduces the second activity to its last row per case, which can miss an earlier same-resource approval followed by a different approver. Regression-test the installed version rather than relying on the function name alone. ([GitHub][1])

```python
import pandas as pd
import pm4py

C = "case:concept:name"
A = "concept:name"
T = "time:timestamp"
R = "org:resource"

CONTROL_PAIRS = {
    "po_separation": (
        "Create Purchase Order", "Approve Purchase Order"
    ),
    "bank_payment_separation": (
        "Change Vendor Bank Details", "Payment Approval"
    ),
}

# df is the event-level export, not the supplied summary tables.
# First validate labels, lifecycle semantics, source time zones, and ordering.
events = pm4py.format_dataframe(
    df.copy(), case_id=C, activity_key=A, timestamp_key=T
)

def four_eyes_screen(
    data: pd.DataFrame, resource_key: str = R
) -> dict:
    required = {C, A, T, resource_key}
    missing = required.difference(data.columns)
    if missing:
        raise ValueError(f"Missing columns: {sorted(missing)}")

    # Missing identities remain unresolved, not compliant.
    known = data.dropna(subset=[resource_key]).copy()
    results = {}

    for rule_name, (first, second) in CONTROL_PAIRS.items():
        left = known.loc[
            known[A].eq(first), [C, resource_key]
        ].drop_duplicates()
        right = known.loc[
            known[A].eq(second), [C, resource_key]
        ].drop_duplicates()

        pm4py_ids = set()
        if not left.empty and not right.empty:
            hits = pm4py.filter_four_eyes_principle(
                known, first, second,
                activity_key=A,
                timestamp_key=T,
                case_id_key=C,
                resource_key=resource_key,
                keep_violations=True,
            )
            pm4py_ids = set(hits[C])

        # Literal case-wide rule: any verified human appearing in both roles.
        overlap = left.merge(
            right, on=[C, resource_key], how="inner"
        )

        results[rule_name] = {
            "pm4py_case_ids": pm4py_ids,
            "all_occurrence_case_ids": set(overlap[C]),
            "overlap_evidence": overlap,
        }

    return results

raw_account_flags = four_eyes_screen(events)

# After independent identity reconstruction:
# Re-run on verified HUMAN events using resource_key="actor_id".
# Keep bot-origin and unresolved-identity cases separately classified.
```

An account-level overlap is only a screen. A verified-human overlap supports a control exception under the supplied case-wide rule. Missing activities or unresolved actors should not be reported as compliant simply because the filter returned no hit.

Report both the all-case share and a clearly defined **control-eligible denominator**, with missing-activity, bot-origin, and unresolved-identity populations disclosed separately. Do not use whole-quarter case percentages to compare control effectiveness across routes with different opportunities for violation.

## Networks, emergency comparison, and source-system isolation

Handover networks describe resource succession; working-together networks describe co-participation in cases. With `n=2`, the subcontracting analysis examines resource-return patterns of the form A→B→A. These are behavioral summaries, not evidence of communication, contractual subcontracting, or intent. Retain raw motif counts and unique-case counts alongside library network weights. ([Process Intelligence Solutions][2])

```python
def keep_cases(data: pd.DataFrame, case_ids) -> pd.DataFrame:
    return data.loc[data[C].isin(case_ids)].copy()

def network_bundle(data: pd.DataFrame, resource_key: str = R) -> dict:
    if data.empty:
        return {}
    args = dict(
        resource_key=resource_key,
        timestamp_key=T,
        case_id_key=C,
    )
    return {
        "handover": pm4py.discover_handover_of_work_network(
            data, beta=0, **args
        ),
        "working_together": pm4py.discover_working_together_network(
            data, **args
        ),
        "subcontracting_n2": pm4py.discover_subcontracting_network(
            data, n=2, **args
        ),
    }

# Precondition: emergency_flag is Boolean or missing, not a string.
g = events.groupby(C)["emergency_flag"]
consistent = g.nunique(dropna=False).eq(1)
status = g.first()

emergency_ids = status.index[
    consistent & status.eq(True).fillna(False)
]
non_emergency_ids = status.index[
    consistent & status.eq(False).fillna(False)
]

views = {
    "emergency": keep_cases(events, emergency_ids),
    "non_emergency": keep_cases(events, non_emergency_ids),
}
# Missing or inconsistent emergency flags remain outside this comparison.

sources = ["manual_upload", "legacy_erp", "quarter_close_upload"]
for source in sources:
    ids = events.loc[events["source_system"].eq(source), C].unique()
    views[source] = keep_cases(events, ids)

flagged_source_ids = events.loc[
    events["source_system"].isin(sources), C
].unique()
views["no_flagged_source"] = events.loc[
    ~events[C].isin(flagged_source_ids)
].copy()

networks = {
    name: network_bundle(view)
    for name, view in views.items()
}
```

Source views intentionally retain **whole cases** and may overlap. Deleting only manual-upload events from mixed-source cases could manufacture handovers, remove justifications, or conceal bank changes. Likewise, removing bots changes adjacency: label a human-only projection as such rather than treating it as the original handover network.

For substantive comparison, I would:

**Normalize by opportunity and routing.** Compare pair frequencies within eligible approval opportunities, not against all events or all employees. Condition comparisons on emergency status, purchase category, contract type, amount band, region, source system, and time period. Obtain team and on-call rosters where assignment constraints are not in the log.

**Use discriminating contrasts.** Compare V-77x work handled by other resources, Lena–Kim work outside V-77x, equivalent manual uploads by other teams, and comparable cases before and after the maintenance window. If these contrasts have little overlap, report that the effects of pair, vendor family, and source cannot be separated reliably.

**Test residual pair concentration cautiously.** A constrained permutation analysis could exchange approvers only among comparable, role-eligible approval opportunities while preserving workloads and availability. Excess pairing would indicate unexplained routing, not misconduct. Group uncertainty calculations by maintenance batch or vendor operation when many cases share one underlying event.

**Inspect loop content.** Reconstruct each A→B→A sequence with activities, document versions, changed fields, and elapsed times. An approval-comment correction is materially different from a beneficiary change after payment authorization.

## Timing checks

PM4Py’s path-performance filter can screen cases containing a directly-follows activity pair with an elapsed duration in a specified range. The thresholds below are **illustrative review thresholds**, not reconstructed definitions of the supplied “fast subgroups.” ([GitHub][1])

```python

    ("Create Purchase Order", "Approve Purchase Order"),

    max_performance=15 * 60,
    keep=True,

fast_bank_candidates = pm4py.filter_paths_performance(
    events,

```

For non-adjacent events, match the relevant PO revision, bank-change transaction, or payment explicitly; do not assume every event pair in a case represents the same decision.

A completion-to-completion interval is **not approval service time**: it can contain waiting and the second activity’s execution. Derive service or waiting features only where start/completion events can be reliably matched. Treat equal-minute timestamps and negative or implausible intervals as data-quality questions rather than instant proof of cursory review.

Recalculate timing distributions after reconstruction, retaining the raw result for reconciliation. Compare full distributions within comparable routes—not only selected fast medians against a global median.

## Retrospective justification: sequence, time, and independence

A hand-authored DECLARE response rule can screen whether an override is eventually followed by justification. It does not enforce a three-working-day calendar, human independence, or a documentary link to the particular override. ([Process Intelligence Solutions][3])

```python
retro_rule = {
    "response": {
        ("Emergency Override", "Retrospective Justification"): {}
    }
}

sequence_diagnostics = pm4py.conformance_declare(
    events,
    retro_rule,
    return_diagnostics_dataframe=True,
)
```

The complete check needs an explicit, occurrence-level extension:

```text
For each Emergency Override:
    identify its actual human authorizer and actual occurrence time
    calculate the deadline from the applicable regional working-day policy
    retrieve justifications explicitly covering this override

    if identity, chronology, linkage, or source completeness is unresolved:
        classify as "unverifiable"
        continue

    identify records that:
        follow the override in reliable event order
        are authored/approved by a different verified human
        substantively cover this override

    if a qualifying record exists by the deadline:
        classify the obligation as "satisfied"
    else if the extraction time has not passed the deadline:
        classify as "pending"
    else if a qualifying record exists only after the deadline:
        classify as "late"
    else:
        classify as "overdue—no qualifying independent justification"

    separately retain any same-human justification entries for review
```

The policy must determine holidays, day-end cutoffs, and treatment of repeated overrides; do not silently substitute 72 hours. A single document may cover multiple overrides only when its scope supports that linkage. A case-wide same-resource screen cannot establish which override a justification addresses.

A recently triggered obligation with time remaining is **pending**, not a confirmed violation. Cases without overrides should not inflate the compliance denominator through vacuous satisfaction. Include records beyond the quarter boundary where needed to observe matured obligations.

Discovered DECLARE or log-skeleton models can provide descriptive comparisons with an independently reviewed reference population. They should not replace the stated norm: a frequently omitted safeguard must not become “optional” merely because discovery learned the omission.

Review of the procurement-to-payment event-log summaries identified indicators requiring targeted validation, but did not establish fraud or collusion.
