# 3. Candidate policies

**P-A Strict specialization with fixed queues**
Eligibility: each resource limited to primary family: Ada/Ben/Farah  Mechanical, Ada/Chen/Deepa/Emil/Farah  Electrical, Chen/Emil/Farah  Software. Intake/Validation shared first-come first-served per resource.
Priority score = priority rank then FIFO.
Parallel ME/ES forced sequential on first qualified resource, no cross-skill overflow.
Handover minimised by sticky assignment per case.
Preemption disabled.

**P-B Full pooling with transparent dispatch**
Eligibility = all qualified resources.
Dispatch = earliest completion time = current time + queue + setup + handover + expected service, weighted by priority: score = ECT + penalty*priority. P1 penalty negative.
Parallel ME/ES chosen when sum of two ECTs < sequential ECT + 8 min coordination.
Preemption enabled for P1 after 30 min wait, max once, 10% restart penalty applied.
Overflow unrestricted.

**P-C Hybrid P1 reservation + controlled overflow**
Reserve 30% of each skill’s effective minutes for P1 in blocks 08-16. P1 jobs use reserved pool first, then overflow to general pool.
General pool dispatch = workload balancing with fairness penalty: choose resource with minimal (utilisation + 0.5*handover).
Cross-skill overflow allowed only if target resource idle >15 min and setup cost < expected wait saving.
Parallel ME/ES threshold: parallel if both branches can start within 15 min of each other and coordination cost < 20% of sequential makespan.
Preemption enabled for P1 into reserved pool only.

# 5. Robust recommendation

Primary: P-C Hybrid P1 reservation with controlled cross-skill overflow and threshold parallelisation.

Why: it keeps max utilisation 90% in base, protects P1 SLA under U1/U5, limits handover/setup vs full pooling, and retains fairness. Under U3 loss of Chen, controlled overflow from Emil and Farah to Software partially compensates, whereas strict specialization collapses.

Fallback mode: switch to P-B full pooling when P1 queue waiting exceeds 45 min for two consecutive blocks or when any skill utilisation >0.95 for >30 min. This trades fairness for tail reduction during shocks.

Switch thresholds:
* Activate pooling overflow if P1 SLA <85% over last 2h.
* Re-enable specialization if max utilisation <0.80 for 4h to reduce handover burden.
Strict specialization is preferable only if handover cost is shown to dominate delay in practice.

# 6. Secondary effects and implementation risks

* Gaming of estimates: priority inflation, under-reporting case complexity.
* Starvation of P3 under reservation and preemption; need max wait cap.
* Skill erosion if cross-skill overflow is permanent; monitor skill usage share.
* Excessive preemption raises restart penalty and p95.
* Coordination overhead 8 min for parallel ME/ES may be underestimated with resource contention.
* Validation bottleneck can migrate under U2/U3; monitor separately.
* Fairness vs responsiveness trade-off; operators need transparent score.

* get_service_time per activity/resource/skill to detect service-time drift and multiplier effects.

# 9. Limits and validation plan

Cannot conclude from expected arrivals and ranges alone:
* Actual service time distribution shape, correlation with priority, and learning effects.
* Real preemption frequency and restart penalty impact.
* Handover/setup times may be state dependent.
* Overtime acceptance and fatigue.

Pilot design:
* 4-week shadow run with policy version tag on 20% of cases, P1 protected.
* Backtest on historical log with replay using the dispatch scores.
* Primary KPIs: P1 SLA, p95 elapsed, max utilisation, handover minutes per case.
* Safety stop if P1 SLA drops >5pp vs baseline.

This scaffold provides auditable definitions and PM4Py-ready data for drift and bottleneck migration analysis.
