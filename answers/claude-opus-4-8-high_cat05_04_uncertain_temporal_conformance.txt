## 1. Normalization Assumptions

**Order of operations.** For every event I build the feasible *true-time* interval in three stages:

1. **Resolution/measurement uncertainty first** (as instructed). This widens the recorded value into a *recorded-clock* interval before any clock correction:
   - HUB "exact to displayed second, ±0.5 s": recorded-clock interval = [t − 0.5 s, t + 0.5 s].
   - Floor-to-minute (OPS-BER, VENDOR-NY, LEGACY-BER): displayed `mm` means clock time ∈ [mm:00.000, mm:59.999].
   - Round-to-nearest-10 s (SENSOR): displayed `t` means clock time ∈ [t − 5 s, t + 5 s].
   - Round-to-nearest-minute (MOBILE-LON): displayed `mm` means clock time ∈ [mm − 30 s, mm + 29.999 s].
2. **Time-zone conversion** of the recorded-clock interval to UTC using the offset in force on the date:
   - 2026-06-01: Europe/Berlin = CEST = UTC+2; Europe/London = BST = UTC+1; America/New_York = EDT = UTC−4.
   - 2025-10-26: fall-back day in the EU; Berlin is UTC+2 (CEST) before the fold and UTC+1 (CET) after. See DST handling below.
3. **Clock correction last.** Definition: `clock_offset = recorded_clock − true_clock`, offset ∈ [a, b] ⇒ `true = recorded − offset` ∈ [recorded − b, recorded − a]. I apply this to *both* endpoints of the UTC recorded interval, i.e. true ∈ [lower − b, upper − a].

**Clock-offset direction.** A positive offset means the clock runs fast, so true time is *earlier*; subtracting the offset interval widens both ends. I never treat the offset midpoint as the answer.

**Rounding as intervals, not points.** Floor/round semantics are kept as closed/half-open intervals; I do not collapse a floored minute to its midpoint. Midpoints are used only in §5 as an explicitly lossy secondary comparison.

**DST folds (T-405).** On 2025-10-26 a Berlin local time of 02:mm is ambiguous: it maps to UTC 00:mm (first pass, CEST/UTC+2) *or* UTC 01:mm (second pass, CET/UTC+1). Each ambiguous event is therefore a **union of two candidate intervals** (fold A and fold B). Ingestion ordering (Alert ≤ Investigation_Start ≤ Containment_Complete in true time) is used to eliminate fold combinations, but the surviving intervals remain intervals — they do not become exact.

**Inferred starts (T-404).** Investigation_Start is missing but a signed record bounds investigation duration to [18, 25] min. I infer Start = Complete − duration and carry *all* uncertainty: `Start ∈ [Complete_min − 25 min, Complete_max − 18 min]`.

**Causal constraints (T-407).** Alert_Received is missing; only Alert_Sent + delivery latency ∈ [0, 20] min is known, and Alert_Sent ≠ Alert_Received. Received ∈ [Sent, Sent + 20 min]. The plausible-but-unlogged rule "receipt ≤ investigation start" is applied as an *optional* upper clamp and I report results both with and without it.

**Mobile entry delay (T-406).** I treat the up-to-5-minute entry delay as **uncertainty about occurrence time, not merely about record time**: a user who enters a timestamp *late* records a value that is at or after the true occurrence, so the true event may be up to 5 min *earlier* than the clock-derived value. I therefore extend only the lower bound earlier by 300 s, on top of the source clock bound. (If instead one insists the delay shifts only the stored record and the displayed value equals occurrence, the extra 300 s vanishes; I flag this as the material assumption.)

**Weak offset (T-409).** For the flagged hour the NTP-derived [−90, +120] s bound is replaced by a weak engineering estimate [−12, +12] min. This is wide enough that the Alert→Investigation_Start ordering itself is no longer guaranteed, which drives an INDETERMINATE call.

**Profile bands.** Temporal-profile acceptance is `mean ± zeta·sd`. An interval wholly inside the band = CERTAIN_PASS; wholly outside (below or above) = CERTAIN_VIOLATION; partial overlap = POSSIBLE_VIOLATION. SLA rules S1–S3 are one-sided upper limits: interval wholly ≤ limit = pass, wholly > limit = certain violation, straddling = possible violation.

## 5. PM4Py Temporal-Conformance Code

```python
import pandas as pd
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo
import pm4py

UTC = timezone.utc

# ------------------------------------------------------------------
# 1. Interval normalization helpers
# ------------------------------------------------------------------
def utc_iso(y, mo, d, h, mi, s=0, us=0, tz="UTC"):
    """Return a tz-aware UTC datetime from a local wall time in tz."""
    naive = datetime(y, mo, d, h, mi, s, us)
    if tz == "UTC":
        return naive.replace(tzinfo=UTC)
    local = naive.replace(tzinfo=ZoneInfo(tz))
    return local.astimezone(UTC)

def interval(lo, hi):
    assert lo <= hi
    return (lo, hi)

def widen(iv, lo_sub, hi_add):
    """Widen an interval: subtract lo_sub seconds from lower, add hi_add to upper."""
    lo, hi = iv
    return (lo - timedelta(seconds=lo_sub), hi + timedelta(seconds=hi_add))

def clock_correct(iv, off_lo, off_hi):
    """true = recorded - offset, offset in [off_lo, off_hi] seconds."""
    lo, hi = iv
    return (lo - timedelta(seconds=off_hi), hi - timedelta(seconds=off_lo))

# Rounding/resolution windows -> recorded-clock interval (still in the source tz wall clock,
# but we build directly in UTC after conversion for HUB/SENSOR which are UTC).
def hub(dt):                      # exact +-0.5 s measurement, then clock [-1,+1]
    iv = (dt - timedelta(seconds=0.5), dt + timedelta(seconds=0.5))
    return clock_correct(iv, -1, 1)

def sensor(dt):                   # round-to-10s -> +-5, clock [-5,+5]
    iv = (dt - timedelta(seconds=5), dt + timedelta(seconds=5))
    return clock_correct(iv, -5, 5)

def floor_min_utc(dt_floor_utc, off_lo, off_hi):
    iv = (dt_floor_utc, dt_floor_utc + timedelta(seconds=59, milliseconds=999))
    return clock_correct(iv, off_lo, off_hi)

def round_min_utc(dt_utc, off_lo, off_hi):

# 3/4. Feasible duration intervals + interval classification
# ------------------------------------------------------------------
def dur_interval(a_ivs, b_ivs):
    """Feasible (b - a) seconds over unions: min(b)-max(a) .. max(b)-min(a) per pairing;
       returns the union hull here (single case rows have single intervals)."""
    outs = []
    for a in a_ivs:
        for b in b_ivs:
            lo = (b[0] - a[1]).total_seconds()
            hi = (b[1] - a[0]).total_seconds()
            outs.append((lo, hi))
    return outs

def classify_sla(dur_ivs, limit):
    los = [d[0] for d in dur_ivs]; his = [d[1] for d in dur_ivs]
    lo, hi = min(los), max(his)
    if hi <= limit: return "CERTAIN_PASS"
    if lo > limit:  return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

def classify_profile(dur_ivs, mean, sd, zeta):
    low, high = mean - zeta*sd, mean + zeta*sd
    lo = min(d[0] for d in dur_ivs); hi = max(d[1] for d in dur_ivs)
    if lo >= low and hi <= high: return "CERTAIN_PASS"
    if hi < low or lo > high:     return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"
```

## 6. Evidential Sufficiency

For each POSSIBLE_VIOLATION or INDETERMINATE result, the minimum additional evidence that would make it certain:

- **T-401 S1 / Alert→Inv (POSSIBLE).** *Stronger synchronization + resolution*: OPS-BER second-resolution timestamps (kill the 60 s floor) or a tighter NTP offset than [−90,+120] s would collapse the 718.5–991.5 s interval to one side of 900 s.
- **T-402 S2 / Inv→Cont (POSSIBLE).** *Resolution/sync*: sub-minute OPS-BER Investigation_Start; the S1 breach is already certain, so only S2 needs tightening.
- **T-403 S1 & profile (POSSIBLE).** *Synchronization (dominant)*: the [−180,+180] s vendor bound plus minute floor is the whole problem; an event-level time sync or acknowledgment from VENDOR-NY collapses it.
- **T-404 S1 & S2 (POSSIBLE).** *Missing-activity evidence*: capture the actual Investigation_Start, or tighten the signed duration record from [18,25] min to a narrower band; S2 flips to certain-pass once the true start is ≥10:09:59 with confidence.
- **T-405 S1 & profile (POSSIBLE).** *Semantic (DST) + resolution*: log the DST fold flag (offset-aware timestamps) and second-resolution values; ordering already fixed folds, but width remains.
- **T-406 S1 & S2 (POSSIBLE).** *Semantic + duration*: record whether the mobile value is occurrence-time or entry-time, and add a server-side receipt; resolving the entry-delay semantics and the ±300 s clock bound is decisive.
- **T-407 S1 & Alert→Inv/Alert→Cont (POSSIBLE / INDETERMINATE).** *Missing-activity + semantic*: a genuine Alert_Received receipt acknowledgment (not Alert_Sent) with its own timestamp, and confirmation of the "receipt ≤ investigation start" causal rule; without a receipt the ordering (hence S1) is INDETERMINATE.
- **T-409 S1 & Alert→Inv (INDETERMINATE).** *Synchronization (dominant)*: recover the missing NTP diagnostics for that hour. The [−12,+12] min estimate is so wide it permits Investigation_Start before Alert_Received; a real offset bound would restore both ordering and testability.

Categories at a glance: synchronization gaps drive T-401, T-403, T-405, T-409; missing-activity gaps drive T-404, T-407; duration evidence drives T-404, T-406; semantic (fold, occurrence-vs-entry, sent-vs-received, causal) evidence drives T-405, T-406, T-407.

## 7. Governance Recommendation

- **Store UTC, display local.** Persist every event in UTC with an explicit offset; never store bare local wall-clock. This alone removes the T-401/402/409 (Berlin), T-403 (NY), T-406 (London) conversion risk.
- **Retain raw timestamps + resolution metadata.** Keep the *as-recorded* value alongside the normalized UTC, plus a machine-readable resolution field (`exact_second±0.5s`, `floor_minute`, `round_10s`, `round_minute`). Interval reconstruction must not depend on tribal knowledge of a source's rounding.
- **Source offset telemetry.** Require per-event or per-hour clock-offset bounds (NTP diagnostics). T-409 shows what happens when they lapse: an otherwise-testable rule becomes INDETERMINATE. Alert loudly when offset telemetry is missing rather than silently falling back to a wide estimate.
- **Start/complete lifecycle semantics.** Log lifecycle transition types (`start`/`complete`) explicitly. SENSOR "completion events" and T-404's missing Investigation_Start both stem from ambiguous lifecycle. Never infer a start silently; when inferred, tag it and carry the duration interval.
- **DST fold identifiers.** On fall-back days, record the fold (first/second pass) or, better, the numeric UTC offset. T-405 was only resolvable because ingestion order happened to disambiguate; that is luck, not control.
- **Causal identifiers.** Emit correlation IDs linking Alert_Sent→Alert_Received (receipt acknowledgments) so T-407-style gaps are closed by data, not by a plausible-but-unlogged assumption. Distinguish "sent" from "received" as first-class, non-interchangeable activities.
- **Mobile/user-entry provenance.** Flag user-entered timestamps and capture server-receipt time; define policy on whether entry delay perturbs occurrence-time estimates or only record time (it materially moved T-406).
- **Enforcement policy on interval overlap.** Adopt a two-tier policy: **CERTAIN_VIOLATION** (interval wholly beyond the limit/band) triggers enforcement; **POSSIBLE_VIOLATION** triggers investigation/evidence escalation, not automatic penalty; **INDETERMINATE** blocks enforcement and opens a data-quality ticket. Concretely, only **T-408 (S2, S3)** and **T-402 (S1)** would be enforced today; everything else is escalation or remediation. Publish the tolerance and zeta used, and treat SLA (legal maximum) and temporal profile (statistical expectation) as independent regimes that are reported separately.
