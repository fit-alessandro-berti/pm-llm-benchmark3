## 1. Analytical assumptions

**Case notion.** I take a case notion to be the choice of an object type *T* together with the induced projection: trace(*o*) for *o*  *T* is the set of events *e* with (*e*,*o*)  E2O, ordered by (timestamp, eoid). Flattening therefore (i) selects events by **direct** E2O membership only, and (ii) **discards object identity** for every other type. Consequently, any fact encoded purely in object identity (that P3 spans O2 and O3, that V2 is one invoice for two orders) survives flattening only insofar as it forces an event to be copied. Flattening is a projection, not a reconstruction.

**Convergence.** I use two labelled senses. *(i) Event-level convergence*: one event relates to *k* objects of *T* and is copied *k* times — e16 and e24 have *k* = 3 for Order (O1, O2, O3) and *k* = 3 for Item (I12, I21, I31); e13, e14, e19, e22, e25, e27 have *k* = 2 for Order. Nine of 31 events (29%) are shared at Order level. *(ii) Object-level aggregation*: one object subsumes several objects of another type — V2 `bills` O2 and O3, P3 `packs` items of O2 and O3, P4 `packs` items of O3 and O4, D2 `carries` P2 and P3. Both senses inflate instance counts and smear jointly- produced behaviour across traces.

**Divergence.** Object-level: one object participating in many events and many activity types — O3 appears in 13 events covering all 8 activity types, O1 in 12 events / 8 types, with intra-trace parallel actions (e15|e16, e13|e14). The degenerate converse also exists: an object type whose instances touch only one activity — Payment (4 objects × 1 event each).

**Copied shared events: evidence *and* duplication.** Evidence, because the copy is the observable trace of a genuine coupling: O2 really was packed (e13), dispatched (e16), invoiced (e19) and settled (e22, e25) *together with* O3. Duplication, because instance counts stop counting physical occurrences: 3 Dispatch events yield 6 Order-level instances. I therefore always report two denominators (instances vs distinct eoids) and never read an instance frequency as an occurrence count.

**Permitted transformations.** (a) De-duplication by distinct (eoid, eoid) edge pairs; (b) an explicitly labelled O2O-propagated variant (BFS closure over `contains`, `packs`, `carries`, `bills`, `settles`), whose results are never merged with direct-E2O results; (c) qualifier-aware relabelling of *Record Payment* using the O2O qualifiers `partial_settles` (M2) and `completes_settlement` (M3) — this *requires* O2O and is thus a transformation; (d) edge weights 1/*k*. **Not permitted:** inventing events; back-propagating `Create Order`/`Close Order` to items, packages or payments; counting one copied event as two physical occurrences.

## 3. Concrete distortion analysis

**1. Cross-order package P3 — Order flattening (harmful).** e13 (*Pack Package*, 10:12) is copied into **both** O2 and O3. Instance edge `PackDispatch` = 6 (O1 ×2 via e11/e12, O2 via e13, O3 ×2 via e13/e14, O4 via e14) but only **4 distinct event pairs** exist — (e11,e15), (e12,e16), (e13,e16), (e14,e17). Costing packing effort "per order" charges one physical packing action to two orders; variant statistics then show 4/4 unique variants at *n*=4, overstating behavioural diversity.

**2. Cross-order package P4 — Item flattening (harmful).** I32 (O3) and I41 (O4) share e14, e17 and e27, so their traces are **identical**: `Add ItemPackDispatchConfirm Delivery`. Same for I21 and I31 (O2, O3 via e13, e16, e24). The item log therefore reports one homogeneous 6-member variant class, `PackDispatch` frequency 6 vs 4 physical pairs, and zero discriminative power. Item-level SLA differentiation is impossible; but the identity is *informative* evidence that P4 creates an unbreakable behavioural bond between O3 and O4.

**3. Cross-order packages — Package flattening (context-dependent).** P3's trace (e13, e16, e24) is activity-identical to P1's (e11, e15, e23). The consolidation is invisible because O2/O3 are dropped. Harmful for compliance questions ("is one order per package enforced?" — unanswerable), informative only as a baseline showing consolidation leaves no *activity* signature.

**4. Consolidated delivery D2 — Order flattening (harmful + informative).** e16 (11:05) and e24 (16:00) are copied to O1, O2, O3  Dispatch and Confirm Delivery each reach 6 instances vs 3 events (**2.0×**). The single physical edge e24e25 becomes edge `ConfirmRecord Payment` with frequency **2** (in O2 and O3) though it occurred **once**. Additionally the same 4h55m carrier delay is charged to three cases simultaneously, widening the order-level dispatchconfirm distribution (O1 sees 3h00m and 4h55m; O3 and O4 both see 22h45m for D3 — the same delay counted twice).

**5. Consolidated delivery D2 — Delivery flattening (context-dependent).** D2's trace is `DispatchConfirm Delivery`, indistinguishable from D1's, with no P or O labels. The analyst sees 4h55m vs D1's 3h00m and cannot know D2 carried three orders' goods, so "does consolidation cause delay?" is unanswerable — and any apparent ordering of shipments is really an ordering of *loads*. Zero duplication here reflects total loss of the consolidation fact.

**6. Naive KPIs ("avg payments per order = 1.5", "100 % of orders invoiced individually") are wrong; the correct denominators are per *invoice* (V2 = 2 instalments) and per *order-billing relation* (V2 covers 2 orders). **7. **8. Near-singleton lifecycle — Payment flattening (harmful, unredeemable).** 4 traces × 1 event  DFG with **0 edges**, log skeleton with no allowed transition, all conformance checks vacuously pass, all variants identical. Only defensible use: a timestamp census.

## 7. Sensitivity and validation plan

**S1 — Down-weight / de-duplicate copied shared events.** Recompute every Order-level edge twice: instance count vs distinct (eoid, eoid) pairs, and with weights 1/*k* where *k* = number of related orders (e16, e24  1/3; e13, e14, e19, e22, e25, e27  1/2). Expected deltas: `PackDispatch` 64, `IssuePayment` 43, `PaymentConfirm` 54, `ConfirmPayment` 2**1**. Decision rule: any conclusion that reverses under de-duplication is rejected. **Important negative result:** *deleting* the nine shared events instead of de-duplicating them would strip O2 of its only `Pack Package` event (e13 is shared) and manufacture a false `Add ItemDispatch` shortcut — so deletion is not an acceptable substitute for de-duplication.

**S2 — Direct E2O versus O2O-propagated relations.** Build a second OCEL in which each event's object set is closed over `contains/packs/carries/bills/settles`, then re-flatten all six types and diff `activity_coverage` and `copy_factor`. Expected: Payment coverage jumps 1/8  ~8/8 because M1's trace grows from {e21} to all 12 events reachable via V1O1 — i.e. the singleton problem is "solved" by fabrication, producing a log indistinguishable from O1's. Item coverage likewise rises while I11 and I12 become indistinguishable (both inherit all O1 events). **Rule:** propagated results are reported separately and may never be used to claim lifecycle completeness; if a KPI only exists under propagation, it is declared not identifiable from the snapshot.

**S3 — Change the lead object.** Re-run the full comparison and rank on (C1) activity coverage: Order 8/8, Item 4/8, Package 3/8, Delivery 2/8, Invoice 2/8, Payment 1/8; (C2) trace-length variance: {12,9,13,8} vs {4×6} vs {3×4} vs {2×3} vs {2,3,2} vs {1×4}; (C3) copy factor 1.35 / 1.50 / 1.20 / 1.00 / 1.00 / 1.00; (C4) which of the five business facts survive. Stress point: Position B must survive a *worst-case* lead swap — if switching to Invoice changes any of the five facts' verdict from "detectable" to "undetectable", the conclusion is recorded as lead-object-dependent rather than as a finding.

**S4 — Frequency denominators in the OC-DFG.** For each activity report three counts: physical events, distinct objects of each touched type, and instance copies. Expected: `Dispatch` = 3 events / 4 Orders / 4 Packages / 3 Deliveries / 6 Items; `Record Payment` = 4 events / 4 Orders / 3 Invoices / 4 Payments; `Pack Package` = 4 events / 4 Orders / 4 Packages / 6 Items. "How many dispatches occurred?" therefore has answers {3, 4, 6}. Every throughput or cost claim must state its denominator; disagreement between a flattened DFG and an OC-DFG node frequency is resolved by naming the denominator, not by preferring one view.

**S5 — Negative control on consolidation.** Remove (or split) the four consolidation events e13, e14, e19 and re-discover the Order DFG. If variant diversity collapses from 4/4 distinct variants toward a single canonical `CreateAddPackDispatchInvoicePayConfirmClose`, then the behavioural variety observed in the base log is *driven by consolidation* rather than by genuine order-level process variety — a finding that must be reported as such, and one that only the object-centric view (OTG/interactions) can explain.
