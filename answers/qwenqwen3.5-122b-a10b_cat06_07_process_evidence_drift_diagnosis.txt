## 2. Competing explanations and timeline

The deterioration is not a single event but a sequence of compounding failures. Treating January through October as homogeneous obscures the root causes.

*   **January – March (Stable Baseline):** Metrics indicate a healthy model. Breach rates (~0.18), AUROC (~0.81), and label maturity (100%) are consistent. No intervention required.
*   **April (Pipeline Incident):** The workflow migration broke the feature pipeline. The spike in mean predicted risk (0.28) without a corresponding rise in observed breach (0.19) indicates the model received corrupted inputs (wrong event prefixes, missing queue features). The collapse in AUROC (0.67) confirms the model could not distinguish classes due to bad data. This is an artifact, not a business reality change.
*   **May (Partial Recovery):** The mapping patch reduced Unknown activities, but derived features were not fully recomputed. Metrics improved (AUROC 0.78) but lagged baseline. Residual feature gaps may persist.
*   **June (Process Mix Shift):** A policy change increased V2 Remote usage to 52%. Since V2 has a historically lower breach rate (~0.10), the aggregate observed breach rate dropped to 0.15. The model’s mean risk (0.20) remained higher than observed, suggesting slight overestimation relative to the new mix, but discrimination (AUROC 0.79) held. This is a benign covariate/process mix shift, not model failure.
*   **July – August (Supplier-Driven Concept Drift):** Supplier delivery targets were missed starting July, severe in August. The `Order Part -> Part Received` edge time doubled (65h  130h). Crucially, the matured breach rate for V3 doubled (0.35  0.64). The model continued predicting ~0.19 risk, failing to capture the new reality that V3 cases were now far more likely to breach. This is genuine concept drift: the relationship between historical features and the outcome changed for the parts-dependent variant.
*   **September (Population & Process Overlap):** Partner Z onboarded, bringing rural cases and heavy V3 usage (42% total mix). Partner Z cases have higher inherent risk (observed 0.45) and lack key features (device age, travel distance) in the current model. Combined with ongoing supplier delays, the aggregate observed breach hit 0.31. However, label maturity began dropping (82%), meaning the true breach rate is likely higher than observed.
*   **October (Label Censoring Dominates):** An outcome API backlog caused label maturity to crash to 55% with a 52-day delay. The observed breach rate fell to 0.16, falsely signaling improvement. The model’s mean risk rose to 0.23, attempting to compensate for unseen risk. Using October data for evaluation would conclude the model improved, when in fact it is blind to a backlog of breaches.

## 5. Monitoring architecture

**Architecture Design:**
1.  **Data Quality Monitor:** Tracks `Unknown activity share`, `Missing queue feature %`, and `Duplicate event count`. Triggers alert if >5%.
2.  **Label Maturity Monitor:** Tracks `% Matured` and `Median Label Delay`. If maturity <80%, suppresses "Model Accuracy" alerts to prevent false positives.
3.  **Process Variant Monitor:** Tracks distribution of V1/V2/V3. Alerts if V3 exceeds 40% (threshold based on Sep drift).
4.  **Performance DFG Monitor:** Calculates median time on critical edges (`Order Part -> Part Received`). Alerts if >100h.
5.  **Prediction Monitor:** Tracks Mean Predicted Risk vs. Observed Breach Rate (lagged by maturity window).
6.  **Intervention Gate:** Retraining is only triggered if:
    *   Data Quality is Green AND
    *   Label Maturity is >90% AND
    *   Prediction Monitor shows significant drift (e.g., ECE > 0.10).

```python
import pandas as pd
import pm4py
from datetime import timedelta

def extract_monthly_process_evidence(csv_path, month_start, month_end):
    """
    Extracts auditable monthly summaries from field_service_events.csv.
    Handles label normalization, duplicates, and DFG discovery.
    """
    # 1. Read and Basic Filtering
    df = pd.read_csv(csv_path)
    df['timestamp'] = pd.to_datetime(df['timestamp'])
    
    # Filter for the target month range
    df_month = pm4py.filter_time_range(df, min_time=month_start, max_time=month_end)
    
    # 2. Normalize Renamed Diagnosis Labels
    # Map new 'Diagnostic Assessment Completed' back to standard 'Initial Diagnosis Completed'
    df_month.loc[df_month['activity'] == 'Diagnostic Assessment Completed', 'activity'] = 'Initial Diagnosis Completed'
    
    # 3. Duplicate Handling Strategy
    # Sort by timestamp and keep first occurrence per case/activity combo
    df_month = df_month.sort_values(by=['case_id', 'timestamp'])
    df_month = df_month.drop_duplicates(subset=['case_id', 'activity', 'timestamp'], keep='first')
    
    # 4. Format for PM4Py
    log = pm4py.format_dataframe(df_month, case_id='case_id', timestamp='timestamp', activity='activity')
    
    # 5. Discover DFG and Variants
    dfg = pm4py.discover_dfg(log)
    variants = pm4py.get_variants(log)
    
    # 6. Performance DFG (Time-based)
    perf_dfg = pm4py.discover_performance_dfg(log)
    
    # 7. Temporal Features Extraction
    # Returns dataframe with duration stats per case
    temp_features = pm4py.extract_temporal_features_dataframe(df_month)
    
    # 8. Construct Auditable Summary
    summary = {
        'month': f"{month_start.year}-{month_start.month:02d}",
        'total_cases': len(log),
        'unique_variants': len(variants),
        'dfg_edges_count': len(dfg),
        'median_case_duration_hours': temp_features['duration'].median() / 3600,
        'unknown_activity_share': (df_month['activity'] == 'UNKNOWN_ACTIVITY').mean(),
        'diagnosis_rename_fix_applied': True
    }
    
    return summary
```

## 6. Risks of acting on the wrong diagnosis

1.  **Retraining on Immature Labels (October Data):**
    *   *Failure Mode:* The model observes a low breach rate in October (0.16) due to censoring and learns to predict lower risks. When labels finally mature, the model will systematically underestimate risk.
    *   *Mitigation:* Implement a hard gate in the ML pipeline that blocks training data selection if `label_maturity < 90%`. Use vintage analysis to validate outcomes before inclusion.

2.  **Calibrating Around a Pipeline Bug (April Data):**
    *   *Failure Mode:* Treating April’s high predicted risk as real signal leads to adjusting thresholds to reduce false positives, degrading sensitivity for later periods.
    *   *Mitigation:* Maintain a "Golden Dataset" of clean pre-migration data (Jan-Mar). Any deviation in data quality metrics (Unknown activity, missing features) automatically flags the period for exclusion from calibration sets.

3.  **Ignoring Genuine Supplier-Driven Concept Drift (August):**
    *   *Failure Mode:* Attributing the V3 breach explosion solely to "bad luck" or population shift without updating the model logic. The model continues to recommend dispatching technicians for V3 cases without accounting for the high probability of parts delay.
    *   *Mitigation:* Create segment-specific performance monitors. If V3 AUROC/ECE diverges from V1/V2 by >0.15, trigger a specific investigation into parts supply chain features rather than global model updates.

4.  **Attributing Partner Z Population Shift to Unfair Model Behavior:**
    *   *Failure Mode:* Observing higher breach rates for Partner Z and assuming the model is biased against them, leading to unnecessary fairness constraints that degrade accuracy for all users.
    *   *Mitigation:* Conduct stratified fairness checks. Verify if the gap persists after controlling for `variant_type` and `location_rurality`. If the gap disappears when adding `travel_distance`, the issue is feature omission, not algorithmic bias.
