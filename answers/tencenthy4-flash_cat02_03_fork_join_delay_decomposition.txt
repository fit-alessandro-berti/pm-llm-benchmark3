# 1. Delay-decomposition definitions

I treat the stated fork-join rule as valid: after `fork_release`, all three branches are permitted to start, and `final_start` is allowed only after A, B, and C have all completed. Let \(c\) index cases and \(i \in \{A,B,C\}\) index branches. All durations below are in minutes.

Calculated definitions:

\[
U_c = \text{fork\_release}_c - \text{arrival}_c
\]

Upstream elapsed time is the time from process entry until the fork is released.

\[
Q_{i,c} = \text{branch\_start}_{i,c} - \text{fork\_release}_c
\]

Branch queue waiting is the delay from permission to begin until that branch actually starts.

\[
S_{i,c} = \text{branch\_end}_{i,c} - \text{branch\_start}_{i,c}
\]

Branch active service is the logged span from branch start to branch end, assuming no unlogged preemption.

\[
E_{i,c} = Q_{i,c} + S_{i,c}
= \text{branch\_end}_{i,c} - \text{fork\_release}_c
\]

Branch elapsed time from fork release to branch completion.

\[
J_c = \text{join\_ready}_c = \max_{i \in \{A,B,C\}} \text{branch\_end}_{i,c}
\]

Under the stated all-three rule, `join_ready` is the latest branch completion.

\[
L_c = J_c - \text{fork\_release}_c = \max_i E_{i,c}
\]

Elapsed fork-join stage time.

\[
W^{\text{sync}}_{i,c} = J_c - \text{branch\_end}_{i,c}
= L_c - E_{i,c}
\]

Branch-specific synchronization waiting after that branch completes. The last-completing branch has zero synchronization wait; if there is a tie, all tied branches have zero.

\[
D_c = \text{final\_start}_c - J_c
\]

Downstream queueing before final activity F, if the model assumptions hold.

\[
R_c = \text{final\_end}_c - \text{final\_start}_c
\]

Final service time.

\[
T_c = \text{final\_end}_c - \text{arrival}_c
\]

Total case flow time, with identity:

\[
T_c = U_c + L_c + D_c + R_c
\]

For each branch:

\[
L_c = Q_{i,c} + S_{i,c} + W^{\text{sync}}_{i,c}
\]

This is a per-branch identity, not an additive decomposition across branches. For three branches:

\[
\sum_i (Q_{i,c}+S_{i,c}+W^{\text{sync}}_{i,c}) = 3L_c
\]

because each branch path spans the same wall-clock interval from `fork_release` to `join_ready`. Also:

\[
\sum_i W^{\text{sync}}_{i,c} = 3L_c - \sum_i E_{i,c}
\]

So synchronization waits are overlapping gaps measured against the same common endpoint. Adding them as if they were disjoint elapsed-time slices double- or triple-counts calendar time. For example, in F01, B finishes five minutes before join_ready; that five-minute B synchronization gap overlaps the last five minutes of A's service. C's synchronization gap overlaps A/B activity as well. The elapsed fork-join stage must be counted once as \(L_c\), while branch synchronization waits are diagnostics of slack, not additive components of total flow time.
