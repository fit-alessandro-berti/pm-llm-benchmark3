

## 1. Conformance semantics

To interpret object-centric deviations accurately, we distinguish between several semantic categories based on the norm’s explicit declarations and structural assumptions.

- **Forbidden behavior:** Explicitly prohibited by normative relations marked forbidden (e.g., N3, T6, E10). Any observation matching these edges constitutes a direct violation regardless of context.
- **Missing mandatory behavior:** Occurs when a relation marked mandatory within its stated scope is absent from the observed data (e.g., N1, N4, E1-E8). This indicates a gap in the execution trace or a process failure.
- **Unexpected but unregulated behavior:** Relations present in the data but absent from the norm’s coverage (e.g., N6, T4, T5). These are permissible under open-world assumptions unless contradicted by a specific prohibition.
- **Typical-pattern absence:** Missing links in relations marked typical (e.g., N2, N5). Since exceptions are legitimate, absence does not imply noncompliance, only a deviation from the common path.
- **Likely data-quality error:** Observations that suggest technical faults, such as incorrect joins or labeling errors (e.g., Sensor Heartbeat–Invoice). These require investigation into data sources rather than process compliance.
- **Abstraction mismatch:** When the observed model relies on directly-follows traces but the business rule implies eventual satisfaction (e.g., Create Order to Validate Order with an intermediate unrecorded event).
- **Insufficient evidence:** Cases where observed counts are small or data attributes contradict structural relations, preventing definitive conclusions without further logs.

Open-world assumptions allow any relation not explicitly forbidden or mandatory to exist. Closed-world assumptions would treat unobserved relations as impossible. Here, the norm uses a hybrid approach: closed for forbidden and mandatory relations within scope; open for everything else. This prevents over-tagging unmodeled interactions as violations while preserving strictness for critical constraints.

## 3. Detailed reasoning by model family

### OC-DFG
The Object-Centric Directly Follows Graph captures flow sequences. It establishes ordering constraints like N1 (Create Order to Validate Order) and N3 (Cancel Order to Dispatch Package). However, it cannot establish eventual satisfaction; it only checks direct successors. Thus, a missing N1 link is suspicious but not conclusive if an intermediate event exists. Counts matter: N1 is 98% complete, whereas N3 is 0% complete (in the sense that forbidden edges appear). N2 (Validate Order -> Close Order) being typical allows 17% divergence. N4 (Pack to Dispatch) shows 99% adherence; the missing 1% may have valid business reasons.

### OTG
The Object Type Graph establishes structural links. It proves T1 (Order-Item) and T2 (Package-Delivery) exist as mandatory relations. It also detects forbidden T6 (Order-Payment cobirth). However, OTG cannot distinguish intent. An edge like (Order, object_interaction, Customer) is unregulated (T4) but appears in data; this is benign. The norm cannot confirm if T5 (RiskCase) is relevant; it merely permits it. Counts here reflect interaction volume but do not imply compliance without context (e.g., 200 Package-Delivery links imply compliance with T2 for all, assuming the scope covers external shipments).

### ET–OT
Event-Object Type relations verify event participation. E1 (Create Order -> Order) confirms all 100 events touch the correct object. E10 (Sensor Heartbeat -> Invoice) flags a forbidden connection. This model excels at detecting data anomalies because it checks if event types touch object types. It cannot validate temporal logic (e.g., did payment occur after invoice?). It treats "unapplied cash" ambiguously; if Record Payment touches Payment but not Invoice (E8), it could be a violation or a legitimate exception not labeled in logs.

### Abstraction and "Eventually"
The danger lies in treating "eventually expected" rules as "directly-follows." N1 says a created order should eventually enter validation, but we measure direct successors. If a manual review occurs between Create and Validate, OC-DFG will show a break. This is not noncompliance if the review is legitimate. However, for forbidden relations (N3), direct follows or eventual follows both matter equally; a package sent after cancellation is a violation regardless of intermediate steps.

## 6. Norm-completeness assessment

1. **Event labeling for unapplied cash (E8 gap):** The norm distinguishes Record Payment -> Invoice vs unapplied cash but does not mandate a specific event type for the latter.
   - *Risk:* Ambiguity causes false violations or missed fraud.
   - *Clarification:* Require `Record Payment` events to include an `unapplied_cash` attribute or distinct type.
   - *Status:* Mandatory (for correct classification).

2. **Reopening consequences (N6 gap):** Reopening is unspecified, but no rule prevents reopening then cancelling.
   - *Risk:* Infinite loops or financial inconsistencies.
   - *Clarification:* Prohibit cancellation after reopening, or allow but require reason codes.
   - *Status:* Forbidden (for cancellation after reopen).

3. **Delivery relation vs carrier attribute:** The norm mandates Delivery objects but the data sometimes uses attributes.
   - *Risk:* Structural nonconformance in reports despite operational success.
   - *Clarification:* Allow attribute-based delivery if no object exists, but label explicitly.
   - *Status:* Unspecified (as a workaround).

4. **Manual review scope (E9):** Reviews are specified but not governed by norms.
   - *Risk:* Reviews become a black box; no audit trail.
   - *Clarification:* Specify that all Reviews must link to a specific object.
   - *Status:* Mandatory.

5. **Sensor integration:** E10 forbids Sensor Heartbeat on Invoice but not on Package.
   - *Risk:* Sensor data may leak into finance via Package intermediates.
   - *Clarification:* Block all sensor links to financial objects (Invoice, Payment, Order).
   - *Status:* Forbidden.

6. **Thresholds for mandatory:** The norm lacks statistical tolerance.
   - *Risk:* Single errors trigger alarms unnecessarily.
   - *Clarification:* Define acceptable exception rates (e.g., 1% for N1).
   - *Status:* Mandatory (as a configuration parameter).

## 8. Uncertainty statement

The forbidden violations (Cancel  Dispatch, Sensor  Invoice, Order/Payment cobirth) are robust findings requiring immediate remediation. The missing mandatory relations (Create  Validate, Pack  Dispatch) depend on the norm’s abstraction level; they may be compliance gaps or merely missing logs for intermediate steps. The unapplied cash Payment relation depends entirely on whether the system distinguishes this state via attributes rather than object links. Graph summaries alone cannot decide the intent behind the Manual Compliance Review relations or the 2 Dispatch Packages missing Delivery objects. Without deeper log inspection, classification remains probabilistic.
