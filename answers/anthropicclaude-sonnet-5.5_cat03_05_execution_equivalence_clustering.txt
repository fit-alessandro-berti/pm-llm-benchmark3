## 1. Equivalence design space

All relations below are kernels of a canonicalization function, meaning x ~ y iff f(x) = f(y). Each is therefore reflexive, symmetric and transitive by construction. Threshold or distance-based "similar enough" clustering would not be transitive, so I avoid it.

**Conventions.** The lead object is the Order, and only events referencing it are kept. Timestamps define a weak order: events with equal timestamps form one block. Local identifiers carry no meaning. `EXT…` identifiers are a meaningful *externality flag* but their names are not.

**R1 – Activity-sequence equivalence (AS).**
- *Definition:* _AS(x) is the sequence of timestamp blocks, each block being the sorted multiset of activity labels of the lead's events. x ~ y iff _AS(x) = _AS(y).
- *Preserves:* labels, order, repetitions.
- *Discards:* all objects, E2O, O2O, externality.
- *Concurrency:* same-timestamp events form an unordered block.
- *Note:* this is a control-flow baseline, not an object-centric result.

**R2 – Typed structural equivalence (TS).**
- *Definition:* there is a bijection  between the objects of x and y that preserves object type, the externality flag, E2O incidence, event label and event block rank, and typed O2O edges. Qualifiers are ignored in the base version. The variant TS+q also preserves qualifiers.
- *Preserves:* type-level incidence shape, multiplicities, cardinalities, repeated events, external participants.
- *Discards:* identifier names, the order in which set members are listed, tie order inside a block, and (in base TS) qualifier semantics.
- *Properties:* reflexive (identity), symmetric (¹), transitive (composition).
- *Concurrency:*  must preserve the weak order only, so tie order is not distinguished.

**R3 – Business-semantic equivalence (SEM).**
- *Definition:* _SEM(x) = (L, B, D, R, P).
  - L  {iso, shared}: an external object occurs in a logistics event (Pack, Dispatch, Return, Inspect).
  - B  {iso, shared}: an external object occurs in a finance event (Invoice, Payment).
  - D  {1, n}: number of local Deliveries.
  - R  {none, subst, return}: `return` if a Return Item event exists. Otherwise `subst` if a Dispatch lists a strict subset of the items packed in its package, or if an O2O qualifier is `replaces` or `removed_before_dispatch`. Otherwise `none`.
  - P  {1, n}: more than one local Payment object per Invoice.
- *Preserves:* isolation, delivery fragmentation, rework and exception motifs, payment shape.
- *Discards:* package count (kept only as a descriptive sub-label), item identity, unrelated event order, qualifier detail such as partially versus completes settlement.
- *Concurrency:* flags are order-insensitive. Only the `return` motif relies on an event type, never on inferred tie order.

**R4 (optional) – Flattened lifecycle equivalence.** Two executions are equivalent iff, per object type, the multisets of local object lifecycles (ordered activity lists, externals removed) are equal. It discards cross-object synchronization and sharing, which makes it useful as a foil. It groups {X1, X2, X5, X6}.

## 2. Canonical signatures

My preferred relation is SEM, with TS as the auditable finer layer. TS uses a deterministic colour-refinement hash. Each object starts with the colour (type, ext flag, sorted incident (rank, activity) pairs) and is refined by its O2O neighbours. Hash collisions are theoretically possible, and the hash is not a complete invariant when objects are fully symmetric and ties are heavy. Use `networkx` isomorphism to confirm within a bucket if needed.

Execution format: `ex = {"events":[{"act","ts","objs":[oid,…]}], "otype":{oid:type}, "o2o":[(a,b,qual)], "ext":set(oids)}`. For the toy data, `ext = {o for o in otype if o.startswith("EXT")}`.

```python
import hashlib
from collections import defaultdict

LOGI = {"Pack Package","Dispatch","Return Item","Inspect Return"}
FIN  = {"Issue Invoice","Record Payment"}
H = lambda x: hashlib.sha1(repr(x).encode()).hexdigest()[:12]

def with_rank(events):
    r = {t:i for i,t in enumerate(sorted({e["ts"] for e in events}))}
    return [dict(e, rank=r[e["ts"]]) for e in events]

def structural_signature(ex, keep_ext=True, keep_qual=False, keep_o2o=True):
    ev, ot = with_rank(ex["events"]), ex["otype"]
    ext = ex["ext"]
    drop = set() if keep_ext else set(ext)
    inc = defaultdict(list)
    for e in ev:
        for o in e["objs"]:
            if o not in drop: inc[o].append((e["rank"], e["act"]))
    col = {o:(ot[o], (o in ext) if keep_ext else None, tuple(sorted(v))) for o,v in inc.items()}
    edges = [(a,b,q if keep_qual else "") for a,b,q in ex["o2o"]
             if a in col and b in col] if keep_o2o else []
    for _ in range(3):                                   # WL refinement
        col = {o:H((col[o],
                    sorted((q,"o",col[b]) for a,b,q in edges if a==o),
                    sorted((q,"i",col[a]) for a,b,q in edges if b==o))) for o in col}
    es = sorted((e["rank"], e["act"], tuple(sorted(col[o] for o in e["objs"] if o in col)))
                for e in ev)
    return H((es, sorted(col.values())))

def semantic_signature(ex, ignore_ext=False, use_qual=True):
    ev, ot, ext = with_rank(ex["events"]), ex["otype"], ex["ext"]
    def shared(acts):
        return (not ignore_ext) and any(o in ext for e in ev if e["act"] in acts for o in e["objs"])
    local = lambda t: {o for e in ev for o in e["objs"] if ot[o]==t and o not in ext}
    L = "shared" if shared(LOGI) else "iso"
    B = "shared" if shared(FIN)  else "iso"
    D = "1" if len(local("Delivery")) <= 1 else "n"
    pay = defaultdict(set)
    for e in ev:
        if e["act"]=="Record Payment":
            ps = {o for o in e["objs"] if ot[o]=="Payment" and o not in ext}
            for i in (o for o in e["objs"] if ot[o]=="Invoice"): pay[i] |= ps
    P = "n" if any(len(v)>1 for v in pay.values()) else "1"
    packed = defaultdict(set)
    for e in ev:
        if e["act"]=="Pack Package":
            its = {o for o in e["objs"] if ot[o]=="Item"}
            for p in (o for o in e["objs"] if ot[o]=="Package"): packed[p] |= its
    subst = False
    for e in ev:
        if e["act"]=="Dispatch":
            its = {o for o in e["objs"] if ot[o]=="Item" and o not in ext}
            for p in (o for o in e["objs"] if ot[o]=="Package"):
                subst |= bool(its) and its < packed[p]
    if use_qual:
        subst |= any(q in ("replaces","removed_before_dispatch") for _,_,q in ex["o2o"])
    ret = any(e["act"]=="Return Item" for e in ev)
    R = "return" if ret else "subst" if subst else "none"
    return (L,B,D,R,P)
```

- *Behavior:* I82 is shipped, returned from D81, inspected and repacked into P82, which D82 then delivers. The invoice is issued after the loop.
- *Risks and opportunities:* reverse-logistics cost and quality or damage signals. The invoice follows the rework, which may affect billing timing.
- *Poor flattening:* a flat Order trace shows a loop. Flattening on Item puts I82 in two Packages, which is hard to read.
- *Stability:* high, because the Return Item event is explicit. The O2O `replaces` edge between packages is optional evidence.

## 5. Borderline cases

**X1 vs X2.** AS, TS and SEM all group them. Only the listing order of the item identifiers in Add Item differs. A raw-identifier exact key (or lexical comparison of id lists) separates them, and a defensible identity-based definition would call this a difference. I treat it as noise because item identifiers are local and the labels are identical.

**X1 vs X5.** AS says equal, since the label sequence is the same. TS says different: X5 has an extra Order and an external Item, and Pack has three items. SEM says different: L = shared. Ignoring external objects makes them equal. The disagreement is whether an "execution" means the lead's local view or the closed system it depends on.

**X1 vs X6.** The structure is the same as in X5 but on the finance side, with EXT-OB in Invoice and Payment. AS says equal, TS and SEM say different (B = shared). Under "ignore externals" they merge. R4 also merges them, which shows how flattening hides sharing.

**X1 vs X7.** AS says equal. TS says different, because Dispatch has an Item in its E2O incidence and there is an item-to-item O2O edge, even with qualifiers ignored. SEM says different (R = subst). They merge only under a definition that ignores both O2O and Dispatch item incidence, i.e. a pure Order-flattened view. An analyst who reads the substitution as a master-data correction might defensibly merge them. A quality analyst would not.

**X3 vs X4.** Both have two items, and two packages. AS differs (Pack Pack Dispatch versus Pack Dispatch Pack Dispatch, plus a repeated Payment), as do TS and SEM (D = 1 versus n, P = 1 versus n). A "fragmented fulfilment" definition based on package count groups them. I separate them because consolidating to one delivery is the operational decision that drives shipping cost and customer experience. Under run-length collapse, X3 joins the baseline AS class while X4 does not.

**X4 vs X8.** Both have two Pack and two Dispatch events and one invoice. A fragmentation definition (packages and deliveries) groups them. AS, TS and SEM separate them. In X4 each item is shipped once in a planned split. In X8 I82 appears in two packages and two shipments after a return, so it is a reactive loop. If returns were logged in another system, only the E2O signal "item packed twice" would remain, which is still enough to separate them from X4.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**Information preserved.** To my understanding, PM4Py extracts each lead object's execution as a sub-OCEL and builds an exact key from it. The key covers the time-ordered events with activities, their E2O objects (with types and identifiers as stored), and the O2O relations. Check this on your installed version (`print(next(iter(clusters)))`). If the key includes timestamps or attribute values, exact clusters will be nearly singletons.

**Why raw identifiers make clusters too fine.** The raw ids `I11` and `I22`, and even the order in which ids are listed, enter the key, so X1 and X2 separate. Externality is also invisible to the key, because it is encoded in the id here and in the graph connectivity in real data.

**Post-processing.** Treat PM4Py clusters as a pre-grouping. Re-read each returned sub-OCEL, rename to canonical colours (section 2), flag externals, and aggregate by TS or SEM key.

**When exact equivalence is preferable.** It is better for compliance and audit replay, where identity-level facts such as which invoice covered which order matter. It is also better for deterministic regression tests of ETL or repair. A coarser business clustering is better for segmentation and reporting.

**Effect of `max_objs` and large executions.** Shared packages and invoices chain orders together, so one order's execution can expand to hundreds of objects. `max_objs` bounds this. Depending on the version, oversized executions may be truncated or excluded, so cluster membership then depends on the cap. Check whether oversize cases were dropped, count them, and do not read the clusters as complete. A better design is to cut the execution at other-lead objects and keep them as flagged stubs, exactly the `EXT` convention used here.

```python
import pm4py, pandas as pd
from collections import defaultdict

LEAD = "Order"
clusters = pm4py.cluster_equivalent_ocel(ocel, LEAD, max_objs=200)
# value: collection of sub-OCELs per exact key (verify for your version)

rel = ocel.relations
lead_by_eid = (rel[rel["ocel:type"] == LEAD].groupby("ocel:eid")["ocel:oid"].apply(set).to_dict())
orders_of = defaultdict(set)
for eid, oid in zip(rel["ocel:eid"], rel["ocel:oid"]):
    orders_of[oid] |= lead_by_eid.get(eid, set())

def to_ex(sub):
    r = sub.relations.sort_values("ocel:timestamp", kind="stable")
    otype = dict(zip(sub.objects["ocel:oid"], sub.objects["ocel:type"]))
    lead = r[r["ocel:type"] == LEAD]["ocel:oid"].value_counts().idxmax()  # most events
    ext = {o for o in otype if o != lead and (orders_of[o] - {lead})}
    events = [{"act": g["ocel:activity"].iloc[0], "ts": g["ocel:timestamp"].iloc[0],
               "objs": list(g["ocel:oid"])} for _, g in r.groupby("ocel:eid", sort=False)
              if lead in set(g["ocel:oid"])]
    o2o = []
    if len(sub.o2o):
        q = sub.o2o["ocel:qualifier"] if "ocel:qualifier" in sub.o2o else [""] * len(sub.o2o)
        o2o = list(zip(sub.o2o["ocel:oid"], sub.o2o["ocel:oid_2"], q))
    return {"events": events, "otype": otype, "o2o": o2o, "ext": ext, "lead": lead}

rows = []
for exact_key, subs in clusters.items():
    for sub in subs:
        ex = to_ex(sub)
        rows.append({"lead": ex["lead"],
                     "exact": hash(exact_key) % 10**8,
                     "struct": structural_signature(ex),                 # section 2
                     "sem": semantic_signature(ex)})                     # section 2
df = pd.DataFrame(rows)
print(df.groupby("sem").agg(n=("lead", "size"), exact_variants=("exact", "nunique"),
                            struct_variants=("struct", "nunique")))
```

## 7. Robustness analysis

| Perturbation | AS | TS | SEM |
|---|---|---|---|
| Ignore O2O qualifiers | unchanged | unchanged: base TS already ignores them and X7 keeps its unqualified edge | unchanged: X7 is caught by the Dispatch subset, X4 by payment count, X8 by Return Item. Only partial versus completes and replaces versus removed are lost |
| Ignore external objects | unchanged | {X1, X2, X5, X6} merge | S-B and S-C merge into S-A, giving {X1, X2, X3, X5, X6}. Coupling risk becomes invisible |
| Collapse repeated same-label events | Run-length collapse puts X3 with A1 (X4 still differs because the last two Payments collapse only). Global first-occurrence dedupe also puts X4 there, and X8 stays apart because of Return and Inspect | Changes the graph. X3's merged Pack event has two packages, so it still differs from X1 unless objects are also merged | unchanged if counts are taken from objects. If counts were taken from events, X4's P would become 1, but D = n keeps it apart |
| Pack and Dispatch as a partial order (order only via shared non-lead objects) | X4's two chains are concurrent, so "Pack Pack Dispatch Dispatch" would be equivalent to its actual order. X3 is a join, so it remains different. No current merge. X1 and X2's Add Items also become concurrent | same: orderings are now interleaving-invariant | unchanged |
| Payment multiplicity as an amount attribute | unchanged | X4 gets a single Payment object and stays apart through its delivery structure | P = 1 for X4, which stays alone through D = n. S-E reduces to planned split shipment |

Overall, SEM is robust to qualifiers, collapse and ordering choices. It is sensitive to externality handling, and X3's membership in S-A depends on the package-count choice. TS is sensitive to everything structural. AS is almost insensitive but too coarse.

## 8. Limitations and recommendation

- **Compliance monitoring:** TS with qualifiers and externality flags (TS+q), or exact PM4Py clusters. Compliance needs identity-level and O2O facts, such as which order was covered by which invoice, and a false merge is worse than a false split.
- **Operational segmentation:** SEM clusters S-A to S-F. They give a few actionable groups aligned to operational decisions: consolidation, billing, rework, shared logistics.
- **Root-cause analysis:** TS+q inside a SEM cluster, compared with the nearest baseline. For example, compare X7 to S-A to pinpoint the substituted item. The analysis needs fine structure but also a same-motif comparison group for contrast.
- **Descriptive reporting:** the four-family roll-up (Clean, Planned fragmentation, Coupled, Exception/rework), optionally annotated with AS variants. It keeps counts large enough to be stable and readable.

No single notion fits all four purposes. Finer relations give auditability but tiny clusters and unreadable output. Coarser ones give statistical power and communicability but can hide risk: S-B and S-C look identical to S-A under AS, and so do S-D and S-A. The right level depends on the cost of a false merge versus a false split. Every derived signature also depends on repair choices, so each published cluster should state its key, its externality policy, and its treatment of qualifiers.
