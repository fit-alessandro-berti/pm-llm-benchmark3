Here is the structured assessment:

---

## 1. Control-Objective Decomposition
FEP-1’s core objective is to prevent a single actor from both initiating and authorizing a payment, addressing these threat scenarios:

| **Objective/Threat**               | **Preventive Controls**       | **Detective Controls**       | **Corrective Controls**       | **Gaps**                          |
|-------------------------------------|--------------------------------|-------------------------------|--------------------------------|------------------------------------|
| **Unauthorized payment initiation** | AV-2 (block invalid requests)  | RA-7 (audit)                  | RA-7 (recall if within window)  | AV-2 cannot detect collusion or fake receipts |
| **Fraudulent authorization**        | MG-4 (independent manager)     | RA-7 (audit)                  | RA-7 (recall)                 | Manager may rubber-stamp or collude |
| **Duplicate/misrouted payments**    | AV-2 (duplicate check)         | RA-7 (audit)                  | RA-7 (recall)                 | AV-2 may miss manual duplicates   |
| **Bank-account compromise**        | AV-2 (bank ownership check)    | RA-7 (audit)                  | RA-7 (recall)                 | AV-2 relies on static data; no real-time fraud detection |
| **Emergency bypass abuse**          | ED-1 (strict conditions)       | RA-7 (audit)                  | RA-7 (recall)                 | ED-1 requires manual checks; audit may be delayed |
| **Collusion between preparer/releaser** | None (formal four-eyes)      | RA-7 (audit)                  | None                          | No preventive control; audit is reactive |

---

## 2. Equivalence and Sufficiency Test
A compensating package is **fully equivalent** if:
1. **Timing**: Preventive controls (AV-2, MG-4) occur **before irrevocable settlement** (not just before `Release_Payment`).
2. **Independence**: The second actor (manager/auditor) is **not in a conflict-of-interest relationship** with the preparer/releaser (e.g., no direct supervision or shared performance metrics).
3. **Coverage**: Controls address the **specific threat** (e.g., AV-2 blocks duplicates, MG-4 reviews bank changes).
4. **Overrideability**: Overrides (e.g., AV-2 warnings) require **documented justification** and are **audited retrospectively**.
5. **Recoverability**: Detective controls (RA-7) must operate **within the bank’s recall window** (24 hours).
6. **Evidence Quality**: Audit findings must include **supporting documentation** (e.g., receipts, bank statements) to prove compliance.
7. **Collusion Resistance**: No repeated pairing of the same users (e.g., u12/u13) without organizational justification.

**Partially equivalent** if:
- Controls are present but **timing is late** (e.g., manager approval after settlement).
- **Coverage is incomplete** (e.g., AV-2 passes but no manager review of commercial reasonableness).
- **Recoverability is uncertain** (e.g., audit after recall window).

**Ineffective** if:
- Controls are **absent or overridden without review** (e.g., AV-2 warning ignored).
- **Independence is violated** (e.g., supervisor approves subordinate’s payment).
- **No detective/corrective mechanism** exists (e.g., no audit for emergency payments).

**Why "same expected loss" is insufficient**:
- Controls may reduce loss but **not the likelihood** of fraud (e.g., collusion between u12/u13).
- **Reputational risk** (e.g., AP-202’s vendor link to an employee’s relative) is not quantified by loss.
- **Operational risk** (e.g., repeated shared workstations) may enable future fraud.

## 6. Evidence and Monitoring Recommendations

### **Key Evidence to Collect**
1. **Same-user rate**: Track % of payments where `Prepare_Payment` and `Release_Payment` are by the same user (threshold: <5% for non-emergency).
2. **Override rate**: % of AV-2 warnings overridden (threshold: <1% without manager review).
3. **Late manager approval**: % of `Manager_Ratify` events after `Bank_Settlement` (threshold: 0%).
4. **Audit-before-recall-window**: % of `Audit_Review` events within 24h of `Release_Payment` (threshold: 100% for emergency payments).
5. **Repeated resource pairs**: Flag cases where the same `(u12, u13)` pair appears >3 times in 30 days (threshold: 0 pairs without justification).
6. **Shared workstations**: Log workstation IDs for `Prepare_Payment`/`Release_Payment`; flag if same ID used by same pair >50% of the time.
7. **Bank-change proximity**: Flag payments where `Bank_Account_Change` occurred in the last 7 days (AV-2 should block these).
8. **Control outages**: Track `Validation_Service_Unavailable` events and manual fallback compliance (threshold: 0% manual bypasses without manager approval).

### **Monitoring Rules**
- **Alert**: Same user + amount > EUR 10k (not emergency)  **Manual review**.
- **Alert**: AV-2 override + manager not independent  **Block payment**.
- **Alert**: Repeated `(u12, u13)` pair  **Rotate releasers**.
- **Proof of Misconduct**: Audit finds fabricated receipt + same-user pair  **Investigate collusion**.
- **Proof of Misconduct**: Bank-change + override + funds unrecoverable  **Fraud risk**.
