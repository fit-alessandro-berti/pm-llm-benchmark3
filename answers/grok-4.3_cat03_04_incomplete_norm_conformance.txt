## 1. Conformance semantics
Forbidden behavior is any observation that matches a relation explicitly marked forbidden (N3, T6, E10) within the stated scope; these are closed-world. Missing mandatory behavior occurs when a relation or edge required by a mandatory norm (N1, N4, T1–T2, E1–E8) is absent for objects or events inside the declared scope; counts and scope qualifiers determine whether the gap is material. Unexpected but unregulated behavior covers any relation absent from the normative tables (Validate Order  Issue Invoice, Reopen Order  Close Order, Manual Compliance Review  Customer, Package object_codeath Delivery); these remain open-world and are not violations. Typical-pattern absence denotes shortfalls against typical norms (N2, N5, T3) where legitimate exceptions are acknowledged; such shortfalls are not automatically non-conforming. Likely data-quality error applies when an edge contradicts domain semantics and external indicators point to identifier reuse or join artifacts (Sensor Heartbeat–Invoice). Abstraction mismatch arises when a mandatory “eventually” rule (N1) is checked via a directly-follows summary that omits intermediate events. Insufficient evidence applies when observed counts lack frequency thresholds or when object lifecycles are incompletely typed.

Open-world assumptions treat every relation not listed as forbidden or mandatory-in-scope as permissible; closed-world applies only to the explicit forbidden relations and to mandatory columns inside their scopes. Consequently, absence from the normative tables never triggers a violation classification.

## 3. Detailed reasoning by model family
**OC-DFG**  
The OC-DFG family can establish presence or absence of directly-follows relations inside object lifecycles and can quantify how many objects traverse each arc. It cannot establish whether an absent arc violates an “eventually” rule when intermediate events exist, nor can it distinguish data-quality omissions from process deviations. Counts affect interpretation only when the normative scope supplies a denominator (e.g., “every newly created Order”); without tolerance bands, small gaps remain ambiguous. A relation can be conforming at the eventual level yet appear non-conforming under a directly-follows abstraction; the two Orders lacking Create Order  Validate Order illustrate this danger.

**OTG**  
The OTG family can confirm required object interactions for specific event types and can detect forbidden cobirth or codeath patterns. It cannot establish interaction semantics when an object participates in multiple events of the same type, nor can it evaluate typical relations that explicitly allow exceptions. High-weight edges (Order–Item 1450) confirm mandatory coverage; low-weight forbidden edges (Order cobirth Payment = 1) remain material regardless of weight. An edge absent from the normative OTG is unregulated unless it matches a forbidden tuple.

**ET–OT**  
The ET–OT family can verify that every instance of a listed event type is linked to the declared object types. It cannot evaluate unlisted event–object combinations or decide whether an unlabeled Record Payment event qualifies for the E8 exception. The single Sensor Heartbeat–Invoice link violates a closed-world forbidden rule; the three Manual Compliance Review–Customer links do not because the combination is unspecified.
