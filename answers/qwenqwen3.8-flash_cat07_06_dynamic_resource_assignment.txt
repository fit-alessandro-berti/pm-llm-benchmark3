# 1. Objectives and constraints

The policy is designed as a **multi-objective, explainable decision rule**, not as a single mathematical optimum. It should improve short-term service while protecting long-term capability, fairness, and resilience.

## Primary objectives

1. **SLA protection**
   - Minimize missed or threatened SLAs, especially for urgent and high-priority cases.
   - Reduce waiting time for cases with high handover cost or high complexity.

2. **Quality and rework control**
   - Avoid skill mismatch that historically increases rework and appeals.
   - Prefer competent or specialist resources for high-complexity, high-handover, or high-priority work.

3. **Continuity of ownership**
   - Preserve case ownership when handover cost is high and the current owner can perform safely, especially for high-complexity cases.
   - Avoid unnecessary reassignments, particularly where reassignment count is already elevated.

4. **Workload fairness and overtime control**
   - Prevent repeated assignment to already overloaded resources.
   - Protect resources with high overtime risk from non-urgent work.
   - Keep new assignments within a bounded batch limit.

5. **Skill development**
   - Provide documented training opportunities when SLA risk is acceptable.
   - Use supervised trainees, shadowing, and backup assignments to reduce single-specialist dependency.

6. **Resilience and bottleneck avoidance**
   - Avoid routing all specialist work to the same people, especially in Security Review and Final Approval.
   - Maintain backup capacity through supervised competent resources and cross-training.

## Hard constraints: safety, compliance, and feasibility

These constraints must not be violated except through an explicit, auditable exception.

1. **Skill eligibility**
   - Skill level `0` means not allowed for independent assignment.
   - A case cannot be assigned to a resource with skill `0` for the required activity.

2. **Security Review rule**
   - Security Review must be performed by skill level `3`.
   - Skill level `1` or `2` may perform Security Review only under explicit supervision by `R7_Gita` or `R8_Hugo`.

3. **Final Approval rule**
   - Final Approval must be performed by skill level `2` or `3`.
   - Skill level `1` may prepare but not finalize.
   - Skill level `0` cannot finalize.

4. **High-priority supervision rule**
   - No urgent or high-priority case may be assigned to a skill level below `2` unless supervised.

5. **Batch assignment cap**
   - No resource may receive more than `4` new assignments in the current decision batch, including supervised or shadowing roles if they materially consume capacity.

6. **High overtime-risk protection**
   - Resources with `overtime risk = high` should not receive additional non-urgent work unless:
     - the case is urgent, and
     - no safer alternative exists.

7. **Quality batching rule**
   - Quality Check may be batched only when:
     - priority is normal or low, and
     - SLA time remaining is greater than 24 hours.

8. **Continuity rule for high-complexity/high-handover cases**
   - For high-complexity cases with high handover cost, keep the current owner unless:
     - the current owner has skill `0` or `1`, and
     - no feasible supervision or co-work arrangement exists.

## Soft constraints: preference trade-offs

These are scored but may be overridden when justified.

1. **SLA urgency**
   - Urgent cases receive strong priority.
   - High-priority cases receive moderate priority.
   - Normal and low cases can be used for training or fairness if SLA risk is acceptable.

2. **Skill match**
   - Specialist skill `3` is preferred for complex or risky work.
   - Competent skill `2` is acceptable for routine work.
   - Trainee skill `1` is acceptable only when supervised and SLA risk is low.

3. **Continuity**
   - Current ownership is preferred when handover cost is high.
   - Reassignment count is treated as a warning signal: higher reassignment count increases the cost of another handover.

4. **Workload fairness**
   - Resources with low open cases and high remaining hours are preferred.
   - Resources with high open cases and low remaining hours are penalized.
   - Medium overtime risk is allowed with monitoring; high overtime risk is strongly penalized.

5. **Training and development**
   - Assignments matching documented training priorities receive a bonus.
   - Training is allowed mainly for normal/low-priority work or supervised high-priority work.
   - Shadowing or co-work may count as development if it does not create unsafe execution.

6. **Resilience**
   - If a specialist is overloaded or a bottleneck forms, the policy may use a supervised competent resource rather than forcing all work through the specialist.
   - The policy avoids making any one resource indispensable for Security or Approval unless no alternative exists.

# 2. Assignment policy

## Policy idea

The policy evaluates each case-resource pair using a transparent score. It first filters out unsafe or infeasible assignments, then ranks remaining candidates by a weighted combination of:

- SLA urgency,
- skill match,
- continuity and handover cost,
- workload fairness and overtime risk,
- training value,
- resilience and bottleneck avoidance.

The policy produces either:

- a single owner,
- a primary owner plus supervisor,
- a primary owner plus shadowing trainee,
- or an exception requiring human review.

## Eligibility filtering

For each case and candidate resource:

1. Reject if `required_skill` score is `0`.
2. For `Security Review`:
   - accept if skill is `3`;
   - accept if skill is `1` or `2` only with supervisor `R7_Gita` or `R8_Hugo`;
   - reject if skill is `0`, even with supervision.
3. For `Final Approval`:
   - accept if skill is `2` or `3`;
   - reject if skill is `1` for finalization;
   - reject if skill is `0`.
4. For urgent or high-priority cases:
   - accept if skill is `2` or `3`;
   - accept if skill is `1` only with supervision;
   - reject if skill is `0`.
5. Reject if resource already has `4` new assignments in this batch.
6. Reject if resource has insufficient remaining hours for the expected work, using a conservative capacity estimate.
7. Reject if resource has `overtime risk = high` unless:
   - the case is urgent, and
   - no lower-risk candidate with acceptable skill exists.
8. For Quality Check batching:
   - allow batching only for normal or low priority with SLA remaining greater than 24 hours.

## Scoring model

Each candidate receives a score from `0` to `100`.

```text
TotalScore =
    0.25 * SLAUrgencyScore
  + 0.20 * SkillMatchScore
  + 0.15 * ContinuityScore
  + 0.15 * WorkloadFairnessScore
  + 0.10 * TrainingScore
  + 0.10 * ResilienceScore
  + 0.05 * TeamOrContextScore
```

The weights are intentionally simple and explainable. They should be calibrated using historical logs.

## SLA urgency scoring

```text
SLAUrgencyScore =
    priority_weight * time_remaining_score

priority_weight:
    urgent = 1.0
    high   = 0.8
    normal = 0.5
    low    = 0.3

time_remaining_score:
    <= 4h  = 100
    <= 8h  = 80
    <= 18h = 55
    <= 36h = 35
    > 36h  = 15
```

If SLA remaining is very short and no specialist is available, the policy may create a supervised pair or escalate to a human.

## Skill-match scoring

```text
SkillMatchScore =
    skill_level / 3 * 100

Adjustments:
    +10 if skill = 3 and case_complexity > 0.6
    +5  if skill = 2 and case_complexity <= 0.5
    -20 if skill = 1 and case is high/urgent, unless supervision is strong
    -40 if skill = 1 and case_complexity > 0.7
```

For Security and Approval, the hard eligibility rules override this score.

## Continuity and handover-cost scoring

```text
ContinuityScore = 0

If candidate is current owner:
    +35
    +25 if handover_cost_band = high
    +15 if handover_cost_band = medium
    +5  if handover_cost_band = low

If candidate is not current owner:
    -20 if handover_cost_band = high
    -10 if handover_cost_band = medium
    -5  if handover_cost_band = low
    -15 * reassignment_count if reassignment_count > 0

If case_complexity > 0.7:
    increase owner bonus by +10
    increase non-owner penalty by +10
```

This encodes the historical evidence that high-complexity handovers add waiting time and that repeated reassignments correlate with rework and appeals.

## Workload and overtime fairness scoring

```text
WorkloadFairnessScore = 100

Penalties:
    -40 if overtime_risk = high
    -15 if overtime_risk = medium
    -0  if overtime_risk = low

    -25 if current_open_cases >= 10
    -15 if current_open_cases >= 8
    -10 if hours_remaining <= 3.5
    -20 if hours_remaining <= 2.5

    -30 if new_assignments_in_batch >= 4

Load ratio:
    load_pressure = current_open_cases / hours_remaining
    penalty += 10 * min(load_pressure, 2.0)
```

The goal is not to make everyone identical, but to avoid assigning urgent or high-risk work to resources already under pressure.

## Training and development scoring

```text
TrainingScore = 0

If resource.training_priority == case.required_skill:
    +30 if skill_level >= 1 and case.priority in {normal, low}
    +20 if skill_level >= 1 and case.priority is high/urgent and supervised
    +10 if resource participates only as shadow/observer

If case.notes mention training opportunity:
    +10

If assignment uses a trainee without supervision:
    TrainingScore = -100
```

The policy targets at least 20% of normal/low-priority assignments supporting documented training priorities, but only when SLA risk is acceptable.

## Resilience and bottleneck-avoidance scoring

```text
ResilienceScore = 50

Penalties:
    -25 if resource is the only available specialist for the required skill
    -20 if resource already has 2 or more assignments for the same bottleneck skill
    -15 if team concentration would leave no backup for Security or Approval

Bonuses:
    +10 if assignment uses a competent backup rather than the sole specialist
    +10 if assignment creates shadowing or co-work capacity
    +5  if assignment preserves specialist capacity for urgent work
```

This directly addresses the historical finding that specialist-only routing reduces immediate errors but creates queues in Security and Approval.

## Tie-breaking rules

If scores are close, break ties in this order:

1. Higher total score.
2. Lower number of new assignments in the current batch.
3. Lower `current_open_cases / hours_remaining` ratio.
4. Higher remaining hours.
5. Lower overtime risk.
6. Better continuity score.
7. Better training score, if normal/low priority.
8. Team alignment or local context.
9. Alphabetical resource name for deterministic auditing.
10. Human review if the difference is within a small threshold, e.g. 5 points.

## Exception handling

Exceptions are allowed but must be recorded with an `assignment_reason` and a monitoring flag.

1. **No eligible resource**
   - Allow a supervised trainee if SLA risk is acceptable.
   - Split the case into preparatory and expert-review parts if possible.
   - Escalate to a supervisor or team lead.
   - Delay only with an explicit SLA-risk note.

2. **Current owner has skill 0 or 1 on high-complexity/high-handover case**
   - If supervision is feasible, keep owner with supervisor.
   - If supervision is not feasible, reassign despite handover cost.

3. **High-priority case with only trainee available**
   - Assign trainee only with supervisor.
   - If no supervisor is available, escalate to specialist even if it creates a handover.

4. **High-overtime resource is the only specialist**
   - If case is urgent, allow assignment with overtime-risk flag.
   - If case is not urgent, use competent backup, supervised trainee, or delay.

5. **Quality batching**
   - Batch only when priority and SLA rules allow.
   - Record batch ID and expected batch completion time.

## Pseudocode

```python
def assign_batch(cases, resources, skill_matrix, policy_params):
    assignments = []

    # Process urgent/high first, then normal/low.
    cases = sort_cases_by_priority_and_sla(cases)

    for case in cases:
        candidates = []

        for r in resources:
            if r.new_assignments >= 4:
                continue

            if not has_capacity(r, case):
                continue

            skill = skill_matrix[r.name][case.required_skill]

            # Hard eligibility filters
            if skill == 0:
                continue

            if case.next_activity == "Security Review":
                if skill == 3:
                    supervisor = None
                elif skill in {1, 2}:
                    supervisor = choose_supervisor(r, allowed=["R7_Gita", "R8_Hugo"])
                    if supervisor is None:
                        continue
                else:
                    continue

            elif case.next_activity == "Final Approval":
                if skill < 2:
                    continue
                supervisor = None

            else:
                supervisor = None
                if case.priority in {"urgent", "high"} and skill < 2:
                    supervisor = choose_supervisor(r)
                    if supervisor is None:
                        continue

            # High overtime rule
            if r.overtime_risk == "high":
                if case.priority != "urgent" or not no_safe_alternative_exists(case, resources):
                    continue

            score = score_candidate(case, r, supervisor, skill)
            candidates.append((r, supervisor, score))

        if not candidates:
            assignment = create_exception(case, resources)
        else:
            best = max(candidates, key=lambda x: x[2])
            assignment = create_assignment(case, best[0], best[1], reason=explain(best))

        assignments.append(assignment)
        update_resource_load(best[0], best[1])

    return assignments
```

# 4. Comparison with baseline policies

The comparison below is directional. It does not claim that the proposed policy is universally optimal. The best policy depends on weights, case mix, and whether the organization values immediate throughput, error reduction, fairness, or capability building more strongly.

## Key trade-offs accepted by the proposed policy

1. **Not maximizing immediate throughput**

2. **Not eliminating handovers**

3. **Not using only specialists**

5. **Accepting supervision overhead**
   - Supervised pairs such as Celine/Hugo and Farid/Celine add coordination cost but reduce handover and skill risk.

# 5. Explanation to workers

The following explanation could be shown to workers and team leads.

## How assignments are made

We assign work using a simple set of visible rules. The goal is not to punish anyone or to treat you as a number. The goal is to keep customer promises, reduce unnecessary rework, protect people from overload, and help each other develop.

### 1. Safety and compliance come first

Some work has hard rules:

- Security Review must be done by a specialist, or by a competent person under explicit supervision by Gita or Hugo.
- Final Approval must be finalized by a competent or specialist approver.
- High-priority work should not go to a trainee unless someone can supervise.

If these rules are not met, the assignment is not allowed.

### 2. Urgent and high-priority cases get priority

Cases with short SLA time are looked at first. If a case is urgent, we prefer the resource who can complete it safely and quickly, even if that means a small handover or extra supervision.

### 3. We try to keep ownership when handover is costly

If a case is complex and changing owner is expensive, we prefer to keep the current owner, as long as the owner can do the work safely.

For example, C007 stays with Celine because it is high complexity, high handover cost, and Celine is already the rework specialist.

### 4. We protect people from overload and overtime

If someone has many open cases, little time left, or high overtime risk, we avoid giving them more non-urgent work.

For example, Bruno, David, and Iris have high overtime risk. We do not give them additional routine work unless there is no safer option.

### 5. We use training opportunities when the risk is acceptable

Training is not a favor. It is part of the service model. We look for cases where a trainee can learn safely.

For example:

- Amal and Farid have diagnosis training priorities, so normal-priority diagnosis cases can be used for supervised learning.
- Jonas has security training priority, but he is not yet allowed to perform Security Review independently. He can shadow Hugo on C015.

### 6. We avoid making one person a bottleneck

If the same specialist is always used for Security or Approval, queues grow and absences become risky. The policy tries to use competent backups and create learning opportunities.

### 7. Exceptions are allowed, but they are explained

If an assignment does not follow the normal pattern, there will be a reason, such as:

- urgent SLA risk,
- no safe alternative,
- supervision unavailable,
- quality batching,
- or a deliberate development opportunity.

You can ask for the reason, and the assignment can be reviewed or overridden by a human.

## Example explanations for this batch

- **C001 stays with Celine, supervised by Hugo**: changing owner would be expensive, but Hugo must supervise because Celine is not yet a security specialist.
- **C003 moves from David to Farid with Celine supervision**: David is at high overtime risk, and Farid has a diagnosis training opportunity. Celine supervises to reduce loop risk.
- **C006 and C012 go to Jonas as a batch**: both are normal/low quality checks with more than 24 hours remaining, and Jonas has capacity.
- **C015 stays with Hugo, with Jonas shadowing**: Hugo must perform the security review, but Jonas can observe because security training is a documented priority.
- **C010 moves from Bruno to Eva**: Bruno has high overtime risk, and Eva is a competent approver. This protects Bruno and spreads approval work.

# 6. Process-mining audit indicators

The deployed policy should be auditable using the event log. The following indicators can be calculated before and after policy deployment.

| Indicator | Definition | How to calculate from event log | Desired signal |
|---|---|---|---|
| **Handover frequency** | Rate of owner changes per case or per activity transition. | Use `pm4py.discover_handover_of_work_network`; count handover edges and normalize by total case transitions. | Downward trend, especially for high-complexity cases. |
| **Reassignment count** | Number of times a case changes owner. | Group by `case:concept:name`; count distinct changes in `current_owner` or `org:resource`. | Fewer cases with `reassignment_count > 2`; lower average reassignments. |
| **Skill mismatch** | Assignments where the resource lacks required skill or violates supervision rules. | Join events with skill matrix; flag `skill = 0`, high-priority `skill < 2` without supervisor, Security skill violations, Approval skill violations. | Near zero hard violations. Soft mismatches should decline. |
| **Workload distribution** | How evenly new assignments and open cases are distributed. | Count assignments per resource per batch; calculate max/min, Gini coefficient, or `open_cases / hours_remaining`. | No resource exceeds 4 new assignments; load ratios remain within calibrated bounds. |
| **Overtime risk exposure** | Share of work assigned to high-overtime-risk resources. | Count assignments to resources with `overtime_risk = high`; compare to total assignments. | Low share; exceptions only for urgent cases with no safer alternative. |
| **SLA misses** | Cases completed or advanced after `sla_deadline`. | Compare `time:timestamp` to `sla_deadline` at activity completion or assignment. | Downward trend, especially for urgent/high cases. |
| **Rework/appeal after assignment** | Cases that enter Rework or appeal after a given assignment. | Look for future activities named `Rework Correction`, appeal-related events, or reassignment after assignment. | Lower rate, especially after cases with high skill match or continuity. |
| **Training assignment share** | Share of normal/low assignments that support documented training priorities. | Filter assignments where `assignment_reason` includes training and `resource.training_priority == required_skill`; divide by normal/low assignments. | At least 20%, with no increase in SLA misses or rework. |
| **Specialist bottleneck indicators** | Queue length, waiting time, and service time in Security and Approval. | Use `pm4py.discover_performance_dfg`, `pm4py.get_service_time`, `pm4py.insert_case_service_waiting_time`, and activity filters. | No persistent queue growth for Security or Approval; no single resource dominates handover centrality. |
| **Deviations from assignment policy** | Assignments that do not match policy eligibility, scoring, or exception rules. | Compare actual assignment to policy recommendation; inspect `assignment_reason`; flag overrides, missing supervisors, or rule violations. | Deviations are rare, logged, and reviewed. |

## Useful thresholds to calibrate

These are starting points, not fixed truths.

1. **Hard skill violations**: target 0.
2. **High-priority unsupervised trainee assignments**: target 0.
3. **Assignments to high-overtime resources**: target below 5% of batch assignments, with all exceptions logged.
4. **Training assignment share for normal/low cases**: target at least 20%.
5. **Cases with more than 2 reassignments**: target downward trend.
6. **Security queue length**: monitor weekly; if it grows while specialist-only routing is used, increase backup routing or cross-training.
7. **Approval queue length**: monitor weekly; if Farid or Gita/Hugo dominate, redistribute competent work.
8. **SLA misses**: target downward trend, but evaluate together with rework and overtime exposure.
9. **Rework after assignment**: compare rework rate for supervised trainee assignments versus specialist-only assignments.
10. **Override rate**: if humans override the policy often, the weights or constraints may be misaligned.

## Indicators that may conflict

The audit should not optimize one indicator in isolation.

- Reducing handover frequency may increase overtime if current owners are overloaded.
- Increasing training share may increase short-term service time.
- Reducing specialist queues may increase skill mismatch if backups are not supervised.
- Reducing SLA misses may increase overtime if urgent cases are routed only to available specialists.

Therefore, the policy should be evaluated using a dashboard that shows these indicators together.

## 3. Candidate scoring function

```python
def score_candidate(case, resource_row, supervisor):
    required_skill = case["required_skill"]
    skill = get_skill(resource_row["resource"], required_skill)

    # SLA urgency
    priority_weight = {
        "urgent": 1.0,
        "high": 0.8,
        "normal": 0.5,
        "low": 0.3
    }[case["case_priority"]]

    remaining = case["sla_time_remaining_hours"]
    if remaining <= 4:
        time_score = 100
    elif remaining <= 8:
        time_score = 80
    elif remaining <= 18:
        time_score = 55
    elif remaining <= 36:
        time_score = 35
    else:
        time_score = 15

    sla_score = priority_weight * time_score

    # Skill match
    skill_score = skill / 3 * 100
    if skill == 3 and case["case_complexity"] > 0.6:
        skill_score += 10
    if skill == 1 and case["case_priority"] in {"urgent", "high"}:
        skill_score -= 20
    if skill == 1 and case["case_complexity"] > 0.7:
        skill_score -= 40

    # Continuity
    continuity_score = 0
    if case["current_owner"] == resource_row["resource"]:
        continuity_score += 35
        if case["handover_cost_band"] == "high":
            continuity_score += 25
        elif case["handover_cost_band"] == "medium":
            continuity_score += 15
        elif case["handover_cost_band"] == "low":
            continuity_score += 5
    else:
        if case["handover_cost_band"] == "high":
            continuity_score -= 20
        elif case["handover_cost_band"] == "medium":
            continuity_score -= 10
        elif case["handover_cost_band"] == "low":
            continuity_score -= 5

        if case["reassignment_count"] > 0:
            continuity_score -= 15 * case["reassignment_count"]

    if case["case_complexity"] > 0.7:
        if case["current_owner"] == resource_row["resource"]:
            continuity_score += 10
        else:
            continuity_score -= 10

    # Workload fairness
    workload_score = 100
    if resource_row["overtime_risk"] == "high":
        workload_score -= 40
    elif resource_row["overtime_risk"] == "medium":
        workload_score -= 15

    if resource_row["current_open_cases"] >= 10:
        workload_score -= 25
    elif resource_row["current_open_cases"] >= 8:
        workload_score -= 15

    if resource_row["hours_remaining_today"] <= 3.5:
        workload_score -= 10
    if resource_row["hours_remaining_today"] <= 2.5:
        workload_score -= 20

    load_pressure = resource_row["current_open_cases"] / max(resource_row["hours_remaining_today"], 0.5)
    workload_score -= 10 * min(load_pressure, 2.0)

    # Training
    training_score = 0
    if resource_row["training_priority"] == required_skill:
        if case["case_priority"] in {"normal", "low"}:
            training_score += 30
        elif supervisor is not None:
            training_score += 20

    # Resilience
    resilience_score = 50
    if required_skill in {"Security", "Approval"} and skill == 3:
        # Penalize overusing the same specialist if backup exists.
        specialist_load = count_specialist_load(resource_row["resource"], required_skill)
        if specialist_load >= 2:
            resilience_score -= 20

    total = (
        0.25 * sla_score +
        0.20 * skill_score +
        0.15 * continuity_score +
        0.15 * workload_score +
        0.10 * training_score +
        0.10 * resilience_score
    )

    return total
```

## 4. Batch assignment loop

```python
def assign_batch(cases, skill_matrix):
    assignments = []
    new_assignments = {r: 0 for r in skill_matrix["resource"]}

    cases = sorted(
        cases,
        key=lambda c: (
            {"urgent": 0, "high": 1, "normal": 2, "low": 3}[c["case_priority"]],
            c["sla_time_remaining_hours"]
        )
    )

    for case in cases:
        candidates = []

        for _, r in skill_matrix.iterrows():
            if new_assignments[r["resource"]] >= 4:
                continue

            ok, supervisor = eligible_for_case(case, r["resource"])
            if not ok:
                continue

            if r["overtime_risk"] == "high":
                safe_alternative_exists = has_safe_alternative(case, skill_matrix)
                if case["case_priority"] != "urgent" or safe_alternative_exists:
                    continue

            score = score_candidate(case, r, supervisor)
            candidates.append((r["resource"], supervisor, score))

        if not candidates:
            assignment = create_exception(case)
        else:
            best_resource, best_supervisor, best_score = max(candidates, key=lambda x: x[2])
            assignment = {
                "case": case["case"],
                "resource": best_resource,
                "supervisor": best_supervisor,
                "score": best_score,
                "assignment_reason": explain_assignment(case, best_resource, best_supervisor)
            }
            new_assignments[best_resource] += 1
            if best_supervisor:
                new_assignments[best_supervisor] += 1

        assignments.append(assignment)

    return assignments
```
