# 1. Evidence Ledger

Notation used throughout: `RO` = Register Order, `CC` = Credit Check, `ER` = Engineering Review, `SC` = Supplier Confirmation, `EX` = Expedite Review, `AC` = Approve Configuration, `RP` = Release Production, `AR` = Archive Case. Variants are labelled V1–V7 in the order given in the question (V1 = 12 cases, V2 = 7, V3 = 4, V4 = 3, V5 = 2, V6 = 1, V7 = 1). Counting facts used below: SC appears in 23/30 cases (V1, V2, V5, V6, V7) and is absent in 7/30 (V3, V4); EX appears in 2/30 (V6, V7); no activity repeats inside any observed trace.

**Why bidirectional DFG edges do not prove concurrency.** The DFG is an aggregation over cases: the pair `("Credit Check","Engineering Review"): 17` and `("Engineering Review","Credit Check"): 11` says only that *across the population* both completion orders occur. At least five mechanisms produce that same pattern:

1. **Genuine concurrency** (S2): the checks run in parallel and whichever finishes first is logged first.
2. **A mixture of strictly sequential subpopulations**: e.g. standard orders always run `CC → ER` and rush orders always run `ER → CC`, routed by an attribute that was not exported (exactly the situation S5 describes). Every individual case is sequential; only the aggregate looks symmetric. The correct model would then be an XOR of two sequences with a data guard, not an AND.
3. **Timestamp granularity and tie-breaking** (S7): equal completion timestamps are ordered by ingestion index, so a stable technical artifact can create a directed edge with no process meaning at all.
4. **Completion-only semantics** (D7): the completion order is compatible with sequential, overlapping, and fully parallel execution. Conversely, true parallelism in which one branch is systematically faster yields a *unidirectional* edge — so the absence of a reverse edge would not have disproved concurrency either. The relation is uninformative in both directions.
5. **Repetition or rework**: loops routinely create back-edges in a DFG. Here this explanation is excluded, because no activity occurs twice in any trace — which is itself worth noting: the bidirectionality is strictly *inter-case*, never *intra-case*.

Bidirectional directly-follows is therefore evidence of **order variability across cases**, which is necessary but not sufficient for concurrency. Distinguishing (1) from (2) requires lifecycle start/complete pairs, resource or queue data, or the routing attribute — none of which are available. This is exactly what D7 asserts, and it is the single largest source of model risk below.

# 2. Shared Assumptions

These assumptions hold for all three candidates. They are the fixed frame against which the candidates differ; if one of them is wrong, all three models are wrong in the same way.

- **A1 — Event semantics.** Every event is an *atomic completion* record (S7). Every model is a model of the language of recorded completion sequences, not of execution intervals. Consequently, a "concurrent" (unordered) construct in these models means only *order-indifferent in the log*; it makes no claim of temporal overlap, and a model with unordered CC and ER is observationally equivalent to a model in which they run sequentially in either order.
- **A2 — Timestamp ties.** Adjacency of two events may be an ingestion-index artifact (S7). No constraint in any candidate is justified by a single directed pair with count 1; single-count facts are used only when corroborated by a domain rule (this is why EX's position comes from D6/S6, not from V6/V7).
- **A3 — Alphabet closure and boundary.** The activity alphabet is exactly the eight given labels; no unobserved activity is admitted. `RO` occurs exactly once as the first event and `AR` exactly once as the last (D1); `AC` and `RP` occur exactly once, in that order, immediately before `AR` (D2, DFG-C).
- **A4 — No noise filtering.** All seven variants, including the two 1-count variants, are treated as real behavior, so every candidate must achieve fitness 1.0 on the 30 cases. The alternative — filtering V6/V7 as noise — is rejected because a compliance-relevant activity (EX) appears only there and D6/S6 independently confirm it exists. This decision means the models cannot use "it's noise" as a defence anywhere.
- **A5 — Missingness is modeled as optionality (disclosed abstraction).** In the balanced and permissive candidates, SC is represented as `X(SC, τ)`. This single construct conflates three distinct realities: (i) a genuine skip for stocked components (S4), (ii) an external component whose SC event was lost by the integration problem (S5), and (iii) an SC that was never performed although required (a real S3 violation). The models cannot separate them, because the external/stocked attribute was not exported. Consequences that must be stated to any user: an SC-less case will be reported as perfectly conforming even when it is a compliance violation, and no fitness/precision number computed with these models carries any information about SC compliance. The conservative candidate makes the same conflation in a different way: it simply lists SC-less variants as legal alternatives.
- **A6 — Quantified split between skip and loss.** Following the S5 arithmetic in §1, roughly 4–6 of the 7 SC-less cases are genuine skips and roughly 1–3 are lost events. Optionality is therefore taken to be a real feature of the process rather than a pure data artifact — but the estimate is an inference from one sentence, not a measurement.
- **A7 — No decision logic.** Because no case attribute is available, every choice construct is an unguarded XOR. None of the models is a decision model; none can predict whether SC will occur.
- **A8 — At most one EX.** D6 states this explicitly and no evidence contradicts it, so it is treated as a hard constraint in all three candidates, including the permissive one.
- **A9 — Soundness requirement.** Every candidate must convert to a sound accepting Petri net (workflow net, proper completion, no dead transitions), so that alignment-based conformance is well defined. All three do (§8).
- **A10 — Uniform evaluation protocol.** All comparisons use the same reconstructed 30-case log, alignment-based fitness and precision, token-replay generalization, and bounded playout. Differences between candidates therefore come from the models, not from the measurement setup.

# 3. Conservative Candidate

**Inductive bias.** The conservative candidate takes the position that with 30 cases, completion-only timestamps, and an explicitly unknown concurrency question (D7), the only defensible generalization is *none*: it admits exactly the seven observed variants and nothing else. Its bias is maximal precision and zero inductive commitment about the relation between CC, ER, SC, and EX — it neither asserts concurrency (contradicting S2's claim as fact) nor asserts a sequence (contradicting the log), it simply lists what happened. It does use the high-confidence rules D1, D2 and DFG-C to factor out the common prefix `RO` and the common suffix `AC, RP, AR`, which is a purely structural refactoring that does not change the language. This model is the right hypothesis if the process is in truth a small set of institutionalised recipes (as S1 hints) rather than a flexible partial order; it is the wrong hypothesis if the observed order variability is a sample from a much larger space of legal interleavings, which is what S2, D5 and D6 suggest.

**Compact formal expression.**

```
model_conservative =
  → ( RO,
      × ( → (CC, ER, SC),
          → (ER, CC, SC),
          → (CC, ER),
          → (ER, CC),
          → (CC, SC, ER),
          → (CC, ER, SC, EX),
          → (ER, CC, EX, SC) ),
      AC, RP, AR )
```

Language size: exactly 7 traces, in bijection with the observed variants.

**PM4Py code.**

```python
import pm4py

# Conservative candidate: an explicit XOR enumeration of the seven observed
# variant bodies, wrapped in the high-confidence prefix (D1) and tail (D2, DFG-C).
_BODIES = [
    "->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation' )",              # V1, 12x
    "->( 'Engineering Review', 'Credit Check', 'Supplier Confirmation' )",              # V2,  7x
    "->( 'Credit Check', 'Engineering Review' )",                                       # V3,  4x
    "->( 'Engineering Review', 'Credit Check' )",                                       # V4,  3x
    "->( 'Credit Check', 'Supplier Confirmation', 'Engineering Review' )",              # V5,  2x
    "->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review' )",   # V6, 1x
    "->( 'Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation' )",   # V7, 1x
]

_TREE_STR = (
    "->( 'Register Order', X( " + " , ".join(_BODIES) + " ), "
    "'Approve Configuration', 'Release Production', 'Archive Case' )"
)

model_conservative = pm4py.parse_process_tree(_TREE_STR)
print(model_conservative)
```

This is a `ProcessTree` (satisfying the requirement that at least one candidate be a process tree). Converted with `pm4py.convert_to_petri_net`, it yields a sound workflow net with 20 places, 25 transitions and 50 arcs.

**Duplicate labels and scalability.** The XOR enumeration necessarily duplicates labels: `Credit Check` and `Engineering Review` each appear 7 times as distinct leaves, `Supplier Confirmation` 5 times, `Expedite Review` 2 times — 21 leaves for a 4-activity body. Three consequences deserve to be spelled out. (i) *Analysis breakage*: the one-transition-per-activity assumption is gone, so anything keyed on activity name — transition-level performance, bottleneck analysis, decision mining, token-based diagnostics, model visualisation — must aggregate over duplicates, and diagnostics become hard to read. (ii) *Alignment ambiguity*: several optimal alignments may exist for a deviating trace, since the same label can be replayed in different branches; the optimal cost is still well defined, but the returned alignment (and hence the *explanation* given to a business user) is arbitrary among ties. (iii) *Scalability*: the model grows as Θ(Σ|variant|). Here that is 7 branches; a realistic order-handling log with 10³–10⁴ variants would produce tens of thousands of leaves, an alignment search space that grows with model size, precision that is 1.0 by construction and therefore uninformative, and a model no human can review. The conservative candidate is thus usable here only because this log is tiny, and it should be understood as a *reference baseline* rather than a deployable model. Note also that pm4py's `simplicity_petri_net` scores it *higher* than the balanced model (≈0.82 vs ≈0.79) because that metric averages arc degree and is insensitive to size and duplication — a concrete example of why the matrix in §7 stays qualitative.

**Behavior deliberately excluded.**

- Any interleaving of CC, ER, SC not literally observed — in particular `ER, SC, CC` (SC after ER only, the D5 "either check" reading) and `CC, SC, ER, EX`.
- EX in any case without SC, i.e. `CC, ER, EX` — even though D6 (EX optional, requires both checks) and S4 (stocked components skip SC) jointly make it plainly plausible.
- EX on the other side of SC in combination with orders not observed, e.g. `CC, ER, EX, SC` (observed only as `ER, CC, EX, SC`).
- Any repetition of SC (re-confirmation after a supplier change).
- Any behavior licensed by S2 or D5 in general form: the model contains no concurrency and no disjunctive enabling.
- All violations of D1–D4 and D6 (these are excluded by every candidate).

**Known underfitting risks.**

- **Brittleness to legal-but-unseen interleavings.** If CC and ER really are concurrent (S2), the model rejects roughly half of the legal orderings; the five traces listed in §6 for the balanced model would all be flagged as violations. With 30 cases, seeing only 7 of ≥12 plausible interleavings is exactly what sampling predicts, so false alarms are likely.
- **Frequency-driven omissions.** V6 and V7 have count 1; the *unobserved* EX combinations are missing for the same reason those two were nearly missing — small numbers, not prohibition.
- **Zero robustness to the known data-quality defect.** S5's missing SC events shift a case into a different variant shape. Sometimes that shape happens to be enumerated (dropping SC from V5 `CC,SC,ER` yields V3 `CC,ER`), but dropping SC from a hypothetical `ER,SC,CC` case yields `ER,CC`, and any *new* shape not in the list is rejected. Conformance results become a mixture of process deviation and integration failure.
- **Poor generalization scores and poor extrapolation.** Token-replay generalization is low (≈0.33 in the reference run of §8) because many duplicated transitions fire in only one or two cases; the model is fitted to the sample, and each newly observed variant requires a manual model edit.
- **False confidence.** Precision 1.0 looks like a perfect model to a stakeholder who does not know it was obtained by enumeration. It rewards memorisation, not understanding.

# 4. Balanced Candidate

**Inductive bias.** The balanced candidate encodes the weakest set of ordering constraints that (a) reproduces all 30 observed cases, (b) never contradicts a constraint that the log supports without a single counterexample, and (c) accepts medium-confidence domain rules (D4, D6, S6) where the log is too sparse to speak. Its bias is *evidence-proportional generalization*: constraints are dropped where the log shows variability and kept where the log is unanimous, and no hidden decision point is invented that the data cannot witness. Concretely, it treats the CC/ER order variability as order-indifference rather than as a hidden two-way routing decision — a choice made on parsimony and S2, and explicitly flagged as the model's main gamble (§10). It is expressed as a POWL strict partial order because that formalism can state "unordered but both before AC" without committing to a Petri-net-level interpretation of causality, and because the required constraint set (`CC → SC` but ER unordered with SC) is *not* expressible as a block-structured process tree over unique labels.

**How the four uncertain relations were decided.** A single explicit decision rule was applied, in priority order:

1. **A high-confidence rule binds unconditionally** (D1, D2, and D3's requirement that both checks precede AC). No log evidence can override it, and none does.
2. **A precedence with zero counterexamples across many opportunities becomes an edge.**
3. **A precedence with real counterexamples is dropped**, leaving the pair unordered — because A4 forbids explaining the counterexamples away as noise.
4. **A medium-confidence domain rule binds when the log offers no counterexample**, even if the supporting evidence is thin, because a normative source (D6/S6) outranks 1–2 observations.
5. **No XOR is introduced unless it is needed for fitness or corresponds to a nameable, in-principle-observable decision.** Optionality of SC and EX qualifies (S3/S4/D6 name the decision); a CC-vs-ER routing decision does not (no one named it, no attribute exists).

Applying this:

- **CC vs ER → unordered (rule 3).** Both orders are frequent (19 and 11 cases; 17 vs 11 in the DFG) and no activity repeats, so neither direction can be imposed. The alternative encoding, `X(→(CC,ER), →(ER,CC))`, has the *same* language but posits an unobservable decision and duplicates both labels; rule 5 rejects it. Per A1, "unordered" is a claim about log order only, not about temporal overlap — which is precisely how it stays compatible with D7.
- **CC vs SC → edge `CC → SC` (rule 2).** In all 23 cases containing SC, CC completes before SC — 23 opportunities, 0 counterexamples. This is the strongest non-trivial ordering fact in the log after the `AC → RP → AR` tail, so the constraint is retained.
- **ER vs SC → unordered (rule 3).** ER precedes SC in 21 of 23 SC cases, but V5 (2 cases) shows SC completing first. A strict `ER → SC` edge would misfit 2 cases (~9% of SC cases, ~7% of the log), violating A4. Dropping the edge also happens to be what D5 asks for. Note what this does *not* do: it does not assert that SC needs *only* CC. It asserts that the log cannot support an ER-before-SC constraint. The residual asymmetry — SC is allowed before ER but not before CC — is an artifact of which counterexample happened to be observed, and is the specific thing the permissive candidate relaxes.
- **EX vs CC and ER → edges `CC → EX`, `ER → EX` (rule 4).** Only 2 cases contain EX, far too few to infer anything, but D6 and S6 agree independently and both cases comply. Domain rule wins.
- **EX vs SC → unordered (rule 4 + rule 3).** S6 explicitly permits either side and the two observed cases show one instance of each (V6: SC then EX; V7: EX then SC). Sequencing them either way would misfit one case.
- **Optionality of SC and EX → `X(·, τ)` (rule 5, with A5's disclosure).** SC: 7/30 cases lack it; S3/S4 name the (unavailable) attribute that decides it. EX: D6 states optionality directly.
- **Not chosen: a disjunctive "after CC *or* ER" enabling of SC.** A strict partial order cannot express an OR-join. Encoding D5 faithfully requires an XOR over two partial orders, which is exactly what the permissive candidate does; the balanced model instead takes the strongest-supported conjunctive approximation (`CC → SC`), and treats the difference as a hypothesis to be tested (§9).

**Compact formal expression.**

```
model_balanced = PO( nodes = { RO, CC, ER, X(SC, τ), X(EX, τ), AC, RP, AR },
                     edges = { RO < CC,  RO < ER,
                               CC < X(SC,τ),
                               CC < X(EX,τ),  ER < X(EX,τ),
                               CC < AC,  ER < AC,  X(SC,τ) < AC,  X(EX,τ) < AC,
                               AC < RP,  RP < AR } )
```

Unordered pairs (the deliberate generalization): {CC, ER}, {ER, SC}, {SC, EX}. Language size: exactly **12** complete traces — 2 with neither SC nor EX, 3 with SC only, 2 with EX only, 5 with both — of which 7 are observed and 5 are not. This is verified by bounded exhaustive playout in §8.

**PM4Py code.**

```python
import pm4py
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

ro = Transition(label="Register Order")
cc = Transition(label="Credit Check")
er = Transition(label="Engineering Review")
ac = Transition(label="Approve Configuration")
rp = Transition(label="Release Production")
ar = Transition(label="Archive Case")

# Optionality of SC deliberately conflates "stocked component skip" (S4) with
# "SC event lost by the integration defect" (S5); see shared assumption A5.
sc_opt = OperatorPOWL(Operator.XOR, [Transition(label="Supplier Confirmation"),
                                     SilentTransition()])
ex_opt = OperatorPOWL(Operator.XOR, [Transition(label="Expedite Review"),
                                     SilentTransition()])

model_balanced = StrictPartialOrder([ro, cc, er, sc_opt, ex_opt, ac, rp, ar])
for _src, _tgt in [
    (ro, cc), (ro, er),          # D1: everything after Register Order
    (cc, sc_opt),                # 23/23 cases, zero counterexamples
    (cc, ex_opt), (er, ex_opt),  # D6 / S6: EX only after both principal checks
    (cc, ac), (er, ac),          # D3: both checks before approval
    (sc_opt, ac),                # D4: SC (when present) before approval
    (ex_opt, ac),                # D6 / S6: EX before approval
    (ac, rp), (rp, ar),          # D2 and the exception-free observed tail
]:
    model_balanced.order.add_edge(_src, _tgt)

# ER is intentionally left unordered w.r.t. SC (V5), and SC w.r.t. EX (V6 vs V7).
print(model_balanced)
```

This is the POWL candidate (satisfying the POWL requirement). It converts to a sound workflow net with 12 places, 11 transitions and 26 arcs — the smallest of the three.

**Behavior deliberately excluded.**

- SC before CC in any form (`RO, SC, …` or `RO, ER, SC, CC, …`), even though D5's literal wording would permit the latter.
- Any EX before both checks (`RO, CC, EX, ER, …`) or after AC.
- More than one SC or more than one EX per case; no rework or re-confirmation loops.
- SC after AC, RP before AC, anything after AR, any activity outside the eight labels, any case not starting with RO.
- Any second occurrence of CC or ER (no re-check after a failed credit check).

**Known underfitting/overfitting risks.**

- **Residual over-constraint (underfitting risk in the D5 direction):** the `CC → SC` edge is inferred from unanimity in 23 cases, but D5 says SC needs only *one* of the two checks. If procurement can start from an engineering release alone, the model wrongly rejects `ER, SC, CC` — an error that is invisible in this log by construction, since that shape has never been observed.
- **Over-generalization risk on concurrency (precision risk):** if the CC/ER variability is really a hidden two-policy mixture (S1 plus the missing attribute), then the model's unordered checks admit combinations that no real policy permits, and its precision advantage over an XOR-of-sequences model is illusory.
- **The optionality abstraction hides violations (A5):** an SC-less case fits perfectly, so genuine S3 violations and integration losses are both silently accepted. The model cannot be used to audit SC compliance.
- **EX constraints rest on 2 cases plus a medium-confidence rule:** if EX may in fact be issued after only the credit check (e.g. a commercial rush decision), the model is over-constrained; if EX may recur, it is over-constrained again.
- **Sparse support for the multi-optional combinations:** 5 of its 12 traces have never been seen. Their admission is an inference from compositionality (SC-optionality and EX-optionality being independent), not an observation.

# 5. Permissive Candidate

**Inductive bias.** The permissive candidate takes the weakest defensible reading of every medium- and low-confidence rule and treats the observed log as a small, biased sample of a larger legal language. Its bias is *rule-completeness over sample-fidelity*: any behavior that the stated domain rules do not forbid, and that a practitioner could describe without embarrassment, is admitted — including the disjunctive enabling of SC that D5 actually states, and supplier re-confirmation, which no rule prohibits. It deliberately stops short of a flower model: it is not "anything goes", but "everything the rules allow". It is the right hypothesis if the process is a flexible, expert-driven procedure whose recorded variants reflect what happened to be convenient in 30 cases; it is the wrong hypothesis if the organisation actually enforces a narrow set of recipes, in which case this model will happily accept genuine violations.

**Where the boundary lies.** *Reasonable generalization* (admitted): (i) SC enabled by **either** check, encoded as an XOR over two partial orders — the faithful reading of D5, which the balanced model could only approximate; (ii) SC **repeated** one or more times when it occurs, covering re-confirmation after a supplier or quantity change — no rule in D1–D6 or S1–S7 forbids it, and D4 only constrains its position; (iii) EX in **any** case that satisfies its preconditions, including cases with no SC (D6 + S4), and on **either** side of every SC occurrence (S6); (iv) all interleavings of the checks with SC and EX consistent with those constraints. *Still forbidden* (the hard boundary): any case not starting with `RO` or not ending with `AR` (D1); `RP` without a preceding `AC`, or `RP` before `AC` (D2); `AC` before both CC and ER (D3); any `SC` after `AC` (D4); `EX` before both checks, `EX` after `AC`, or a second `EX` (D6, S6, A8); `SC` as the very first activity of the body, i.e. before *both* checks (D5's floor — "after either check" still requires one); more than one occurrence of `RO`, `CC`, `ER`, `AC`, `RP`, `AR`; and any label outside the eight. Rejected as beyond the boundary: a flower/round-robin model over the eight activities, which would violate D1–D4 and is unusable for any compliance purpose.

**Compact formal expression.**

```
model_permissive = PO( { RO, BODY, AC, RP, AR },
                       { RO < BODY, BODY < AC, AC < RP, RP < AR } )

BODY = × ( B_noSC, B_afterCC, B_afterER )

B_noSC    = PO( { CC, ER, X(EX,τ) },              { CC < X(EX,τ), ER < X(EX,τ) } )
B_afterCC = PO( { CC, ER, *(SC,τ), X(EX,τ) },     { CC < *(SC,τ), CC < X(EX,τ), ER < X(EX,τ) } )
B_afterER = PO( { CC, ER, *(SC,τ), X(EX,τ) },     { ER < *(SC,τ), CC < X(EX,τ), ER < X(EX,τ) } )
```

`*(SC, τ)` is a loop yielding one or more SC occurrences; zero occurrences are covered by the `B_noSC` branch. The three branches are not disjoint (a trace with both checks before SC belongs to two of them), which is intentional: XOR over overlapping partial orders is the standard way to encode a disjunctive (OR) enabling condition in a formalism whose orders are conjunctive. The language is **infinite** because of the SC loop; restricted to at most one SC it contains exactly **14** complete traces (12 of them shared with the balanced model, plus `ER,SC,CC` and `ER,SC,CC,EX`), and under a trace-length bound of 8, 9, 10 events it contains 20, 40, 70 traces respectively (verified by bounded playout in §8).

**PM4Py code.**

```python
import pm4py
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


def _branch(sc_predecessor):
    """One body alternative. sc_predecessor in {None, 'CC', 'ER'}.

    None      -> no Supplier Confirmation at all (S4 stocked components, or the
                 S5 integration loss: the two are indistinguishable, see A5).
    'CC'/'ER' -> SC enabled by that single check, the literal reading of D5.
                 SC is looped (1..n) to admit supplier re-confirmation, which no
                 stated rule forbids.
    """
    cc = Transition(label="Credit Check")
    er = Transition(label="Engineering Review")
    ex_opt = OperatorPOWL(Operator.XOR, [Transition(label="Expedite Review"),
                                         SilentTransition()])
    nodes, edges = [cc, er, ex_opt], [(cc, ex_opt), (er, ex_opt)]  # D6 / S6
    if sc_predecessor is not None:
        sc_loop = OperatorPOWL(Operator.LOOP, [Transition(label="Supplier Confirmation"),
                                               SilentTransition()])
        nodes.append(sc_loop)
        edges.append((cc, sc_loop) if sc_predecessor == "CC" else (er, sc_loop))
    branch = StrictPartialOrder(nodes)
    for _src, _tgt in edges:
        branch.order.add_edge(_src, _tgt)
    return branch


body = OperatorPOWL(Operator.XOR, [_branch(None), _branch("CC"), _branch("ER")])

ro = Transition(label="Register Order")
ac = Transition(label="Approve Configuration")
rp = Transition(label="Release Production")
ar = Transition(label="Archive Case")

model_permissive = StrictPartialOrder([ro, body, ac, rp, ar])
for _src, _tgt in [(ro, body), (body, ac), (ac, rp), (rp, ar)]:  # D1, D3, D4, D2
    model_permissive.order.add_edge(_src, _tgt)

print(model_permissive)
```

The body block is sequenced before `AC` so that D3 (both checks before approval) and D4 (all SC occurrences before approval) hold in every branch without enumerating edges. Converted, it is a sound workflow net with 28 places, 29 transitions and 68 arcs.

**Behavior deliberately excluded.**

- `SC` before both checks (`RO, SC, CC, ER, …`): D5 grants "after either", never "before both".
- A second `EX` (A8, D6) and `EX` before both checks or after `AC` (D6, S6).
- `AC` before either check (D3), `RP` before `AC` or without it (D2), `SC` after `AC` (D4).
- Repetition of `CC`, `ER`, `RO`, `AC`, `RP`, `AR`: no rework loop on the checks or the approval, and no re-opening of an archived case.
- Any activity outside the eight labels, any case not starting with `RO` or not ending with `AR` (D1).

**Known overfitting/underfitting risks.**

- **Low precision by design.** With an infinite language it will accept deviations that a compliance reviewer should see. Precision on the observed log is the lowest of the three (≈0.82 in the reference run); on a larger log it will fall further.
- **The SC loop is the weakest link.** It is licensed only by the absence of a prohibition, not by any positive evidence. Duplicate consecutive SC events are also a classic *data-quality* signature (integration retries — plausible given S5), so the loop may be modeling a defect as if it were behavior.
- **The `B_afterER` branch is pure abduction.** No observed case has SC before CC. Admitting `ER, SC, CC` relies entirely on D5, which is explicitly low-to-medium confidence and whose only supporting case (V5) points the other way.
- **Overlapping XOR branches complicate diagnostics.** A conforming trace may belong to two branches, so alignment-based explanations ("the case took the after-CC path") are not unique, and the label duplication across branches raises the same aggregation problem discussed in §3, though at a much smaller scale.
- **Non-monotone generalization score.** Token-replay generalization is *lower* than the balanced model's (≈0.45 vs ≈0.75) because many of its transitions fire in very few cases; a permissive language does not automatically mean a good generalization metric, and this is a useful reminder not to read `generalization_tbr` as "ability to generalize".
- **Underfitting is still possible in one respect:** it forbids re-running a failed `CC` or a revised `ER`, which is common in real custom-production processes and is not forbidden by any stated rule; the log simply never shows it, and here the sample was trusted.

# 8. Validation Code

The script below is self-contained: it rebuilds all three candidates, the 30-case log, the conversions, soundness checks, metrics, bounded and sampled playout, and the manual positive/negative suite. It has been run against pm4py 2.7.23; the version-sensitive parts are noted in comments.

```python
"""Validation harness for the three candidate models (conservative / balanced / permissive).

Run: python validate_candidates.py
Requires pm4py (tested with 2.7.23). No external files are needed.
"""

import pm4py
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.algo.simulation.playout.petri_net import algorithm as pn_playout

RO, CC, ER = "Register Order", "Credit Check", "Engineering Review"
SC, EX = "Supplier Confirmation", "Expedite Review"
AC, RP, AR = "Approve Configuration", "Release Production", "Archive Case"

VARIANTS = [
    (12, [RO, CC, ER, SC, AC, RP, AR]),
    (7, [RO, ER, CC, SC, AC, RP, AR]),
    (4, [RO, CC, ER, AC, RP, AR]),
    (3, [RO, ER, CC, AC, RP, AR]),
    (2, [RO, CC, SC, ER, AC, RP, AR]),
    (1, [RO, CC, ER, SC, EX, AC, RP, AR]),
    (1, [RO, ER, CC, EX, SC, AC, RP, AR]),
]


# ---------------------------------------------------------------- 1. the log ---
def build_log():
    """30 cases, 205 events. One string per case, comma-separated activities."""
    strings = []
    for count, acts in VARIANTS:
        strings.extend([",".join(acts)] * count)
    assert len(strings) == 30
    return pm4py.parse_event_log_string(strings)


# ------------------------------------------------------------- 2. candidates ---
def build_conservative():
    bodies = [
        "->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation' )",
        "->( 'Engineering Review', 'Credit Check', 'Supplier Confirmation' )",
        "->( 'Credit Check', 'Engineering Review' )",
        "->( 'Engineering Review', 'Credit Check' )",
        "->( 'Credit Check', 'Supplier Confirmation', 'Engineering Review' )",
        "->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review' )",
        "->( 'Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation' )",
    ]
    return pm4py.parse_process_tree(
        "->( 'Register Order', X( " + " , ".join(bodies) + " ), "
        "'Approve Configuration', 'Release Production', 'Archive Case' )"
    )


def build_balanced():
    ro, cc, er = Transition(label=RO), Transition(label=CC), Transition(label=ER)
    ac, rp, ar = Transition(label=AC), Transition(label=RP), Transition(label=AR)
    sc_opt = OperatorPOWL(Operator.XOR, [Transition(label=SC), SilentTransition()])
    ex_opt = OperatorPOWL(Operator.XOR, [Transition(label=EX), SilentTransition()])
    po = StrictPartialOrder([ro, cc, er, sc_opt, ex_opt, ac, rp, ar])
    for s, t in [(ro, cc), (ro, er), (cc, sc_opt), (cc, ex_opt), (er, ex_opt),
                 (cc, ac), (er, ac), (sc_opt, ac), (ex_opt, ac), (ac, rp), (rp, ar)]:
        po.order.add_edge(s, t)
    return po


def _perm_branch(sc_pred):
    cc, er = Transition(label=CC), Transition(label=ER)
    ex_opt = OperatorPOWL(Operator.XOR, [Transition(label=EX), SilentTransition()])
    nodes, edges = [cc, er, ex_opt], [(cc, ex_opt), (er, ex_opt)]
    if sc_pred is not None:
        sc_loop = OperatorPOWL(Operator.LOOP, [Transition(label=SC), SilentTransition()])
        nodes.append(sc_loop)
        edges.append((cc, sc_loop) if sc_pred == "CC" else (er, sc_loop))
    po = StrictPartialOrder(nodes)
    for s, t in edges:
        po.order.add_edge(s, t)
    return po


def build_permissive():
    body = OperatorPOWL(Operator.XOR,
                        [_perm_branch(None), _perm_branch("CC"), _perm_branch("ER")])
    ro, ac = Transition(label=RO), Transition(label=AC)
    rp, ar = Transition(label=RP), Transition(label=AR)
    po = StrictPartialOrder([ro, body, ac, rp, ar])
    for s, t in [(ro, body), (body, ac), (ac, rp), (rp, ar)]:
        po.order.add_edge(s, t)
    return po


# --------------------------------------------------------------- 3. helpers ---
def variant_set(log):
    return {tuple(e["concept:name"] for e in trace) for trace in log}


def trace_fits(net, im, fm, activities):
    """Exact yes/no membership test for ONE trace, via optimal alignment."""
    one_case = pm4py.parse_event_log_string([",".join(activities)])
    diag = pm4py.conformance_diagnostics_alignments(one_case, net, im, fm)
    return abs(diag[0]["fitness"] - 1.0) < 1e-9


POSITIVE_SUITE = [  # (trace, models that must accept it)
    ([RO, CC, ER, SC, AC, RP, AR], {"conservative", "balanced", "permissive"}),   # V1
    ([RO, CC, SC, ER, AC, RP, AR], {"conservative", "balanced", "permissive"}),   # V5
    ([RO, ER, CC, EX, SC, AC, RP, AR], {"conservative", "balanced", "permissive"}),  # V7
    ([RO, CC, ER, EX, AC, RP, AR], {"balanced", "permissive"}),      # EX without SC (D6+S4)
    ([RO, ER, CC, SC, EX, AC, RP, AR], {"balanced", "permissive"}),  # mirror of V6
    ([RO, ER, SC, CC, AC, RP, AR], {"permissive"}),                  # D5 "either check"
    ([RO, CC, ER, SC, SC, AC, RP, AR], {"permissive"}),              # re-confirmation loop
]

NEGATIVE_SUITE = [  # must be rejected by ALL THREE candidates
    [RO, SC, CC, ER, AC, RP, AR],                    # SC before both checks (D5 floor)
    [RO, CC, EX, ER, AC, RP, AR],                    # EX before both checks (D6, S6)
    [RO, CC, ER, AC, EX, RP, AR],                    # EX after approval (D6, S6)
    [RO, CC, ER, RP, AC, AR],                        # RP before AC (D2)
    [RO, CC, ER, SC, EX, EX, AC, RP, AR],            # EX twice (D6, A8)
    [RO, CC, ER, SC, AC, RP],                        # no Archive Case (D1)
]


# ------------------------------------------------------------------ 4. main ---
def main():
    log = build_log()
    print("log:", len(variant_set(log)), "variants /", 30, "cases")

    candidates = {
        "conservative": build_conservative(),
        "balanced": build_balanced(),
        "permissive": build_permissive(),
    }

    nets = {}
    for name, model in candidates.items():
        # convert_to_petri_net dispatches on type: ProcessTree and POWL are both
        # supported in pm4py >= 2.7. Older builds need the POWL converter directly:
        #   from pm4py.objects.conversion.powl import converter; converter.apply(model)
        net, im, fm = pm4py.convert_to_petri_net(model)
        nets[name] = (net, im, fm)
        print(f"\n=== {name} ===")
        print(f"  net: {len(net.places)} places, {len(net.transitions)} transitions, "
              f"{len(net.arcs)} arcs")

        # ---- soundness. check_soundness is deprecated as of pm4py 2.3 but still
        # available; woflan is the underlying implementation.
        result = pm4py.check_soundness(net, im, fm, print_diagnostics=False)
        is_sound = result[0] if isinstance(result, tuple) else result
        print("  sound (WF-net, S-coverable, no dead tasks, live):", is_sound)

        # ---- metrics
        fit = pm4py.fitness_alignments(log, net, im, fm)
        prec = pm4py.precision_alignments(log, net, im, fm)
        gen = pm4py.generalization_tbr(log, net, im, fm)
        simp = pm4py.simplicity_petri_net(net, im, fm)
        print(f"  fitness={fit['log_fitness']:.3f} "
              f"(fitting traces {fit['percentage_of_fitting_traces']:.1f}%)  "
              f"precision={prec:.3f}  generalization_tbr={gen:.3f}  simplicity={simp:.3f}")

        # ---- bounded exhaustive playout + sampled playout
        for bound in (8, 9, 10):
            ext = pn_playout.apply(
                net, im, fm, variant=pn_playout.Variants.EXTENSIVE,
                parameters={pn_playout.Variants.EXTENSIVE.value.Parameters.MAX_TRACE_LENGTH: bound},
            )
            print(f"  exhaustive playout, trace length <= {bound}: "
                  f"{len(variant_set(ext))} distinct traces")
        sampled = pn_playout.apply(
            net, im, fm, variant=pn_playout.Variants.BASIC_PLAYOUT,
            parameters={
                pn_playout.Variants.BASIC_PLAYOUT.value.Parameters.NO_TRACES: 500,
                pn_playout.Variants.BASIC_PLAYOUT.value.Parameters.MAX_TRACE_LENGTH: 20,
            },
        )
        print(f"  random playout, 500 traces: {len(variant_set(sampled))} distinct traces")

        # ---- observed variants must all be reproducible
        missing = variant_set(log) - variant_set(
            pn_playout.apply(net, im, fm, variant=pn_playout.Variants.EXTENSIVE,
                             parameters={pn_playout.Variants.EXTENSIVE.value
                                         .Parameters.MAX_TRACE_LENGTH: 9}))
        print("  observed variants NOT reproduced by playout<=9:", len(missing))

        # ---- manual positive / negative suite
        failures = []
        for trace, accepting in POSITIVE_SUITE:
            expected = name in accepting
            if trace_fits(net, im, fm, trace) != expected:
                failures.append(("positive", trace, expected))
        for trace in NEGATIVE_SUITE:
            if trace_fits(net, im, fm, trace):
                failures.append(("negative", trace, False))
        print("  trace-suite failures:", failures if failures else "none")


if __name__ == "__main__":
    main()
```

**What this validation can and cannot establish.**

- *Soundness* is a decidable structural property and the check is conclusive: all three nets are workflow nets, S-coverable, free of dead tasks, with all tasks live.
- *Fitness, precision, generalization, simplicity* are computed against this 30-case log only. They are sample statistics, not model properties. Precision ≈1.0 for the conservative model reflects enumeration, and `simplicity_petri_net` is an arc-degree average that does not penalise duplicate labels or model size, so it ranks the conservative model above the balanced one. Do not read these numbers as a quality ordering.
- *Playout is not a language-inclusion proof.* Random playout samples the language; it can demonstrate that a trace **is** in the language but never that one is absent. Exhaustive playout is conclusive **only** relative to the stated length bound: for the conservative model (finite, max length 8) the bound-9 enumeration is a complete language description, and likewise for the balanced model (finite, exactly 12 traces). For the permissive model the language is **infinite** because of the SC loop, so no playout — bounded or sampled — can enumerate it; the counts 20 / 40 / 70 at bounds 8 / 9 / 10 are lower bounds on a growing family, and the growth pattern indicates unboundedness rather than proving it.
- *The membership test is exact where it matters.* Individual accept/reject verdicts in §6 come from optimal alignment on a one-trace log, not from playout, so each of those verdicts is conclusive for that trace. No claim is made about the infinitely many traces not tested.
- *No API here compares two infinite languages.* Asserting that the permissive language strictly contains the balanced one is a claim justified by construction (edge-by-edge relaxation of the same constraint set), not by any computation performed above.

# 9. Recommendation and Data-Collection Plan

**Recommend for immediate use: `model_balanced`.** It fits all 30 cases, is the simplest of the three structurally, every constraint maps to a named evidence ID, and it separates what the evidence fixes (`RO` first, `CC → SC`, both checks and any SC/EX before `AC`, the `AC → RP → AR` tail) from what the evidence leaves open (check order, ER-vs-SC order, SC-vs-EX order). It is tight enough to detect the violations that matter operationally (D1–D4, D6) without generating false alarms on interleavings that a 30-case sample simply failed to contain. Two conditions attach to this recommendation: SC-related conformance verdicts must be marked unreliable until the external/stocked attribute exists (A5), and the unordered CC/ER pair must be documented as "order not enforced by the model", not as "the checks run in parallel".

**Recommend for sensitivity analysis: `model_permissive`.** Running both models over the same incoming cases turns the disagreement set into a measurement instrument: any real case landing in `permissive \ balanced` (that is, SC before CC, or SC more than once) is direct evidence about D5 and about supplier re-confirmation, and each such case should be investigated individually rather than counted. Keep `model_conservative` as a third, non-deployed artifact: it is a useful variant catalogue and a precision reference point, and re-running it monthly shows how quickly genuinely new shapes appear — a fast-growing rejection rate is itself evidence that the balanced generalization is too narrow.

**Data to collect, in priority order.**

1. **Lifecycle timestamps (`start` and `complete`) for CC, ER, SC and EX.** This is the single highest-value change and the only one that can settle D7. With intervals: overlapping CC/ER intervals in a substantial fraction of cases confirm S2's concurrency; strictly disjoint intervals with a consistent direction *per case* points to a mixture of sequential policies (S1), which would demand an XOR-of-sequences model instead. Also record sub-second precision or an explicit sequence number so that S7's ingestion-index tie-breaking stops manufacturing directed edges.
2. **The external/stocked attribute (and, if available, a per-line component classification).** This converts the unguarded `X(SC, τ)` into a guarded decision and immediately separates the two readings of V3/V4. It is the only way to make the model usable for S3 compliance.
3. **An independent SC ground truth: the count and identifiers of supplier confirmations per case from the procurement/PO system.** Reconciling that count against the event log quantifies S5's loss rate exactly, splits the 7 SC-less cases into genuine skips versus lost events (the §1 arithmetic estimates 4–6 versus 1–3), and reveals whether SC ever legitimately occurs more than once — which decides whether the permissive loop is a real behavior or an integration retry artifact.
4. **The EX trigger and authorising role, plus the case's requested delivery date.** With 2 observations, everything about EX rests on D6/S6; a trigger attribute would let EX-optionality be modeled as a decision instead of a free choice, and would show whether EX truly requires both checks.
5. **Resource/queue attributes for CC and ER.** If the same resource performs both checks in a case, genuine concurrency is unlikely regardless of what S2 believes; distinct resources plus overlapping intervals is strong positive evidence.
6. **A rework indicator on CC and ER.** All three models forbid repeating a check; that is an assumption taken from a 30-case sample, not from any rule.

**Future traces that would be maximally informative.** Each of the following is a discriminating experiment: observing it would falsify at least one candidate, and its *absence* over a large sample is also informative.

| Observation | Distinguishes | Interpretation if it occurs |
| --- | --- | --- |
| `RO, ER, SC, CC, …` (SC after ER only) | Balanced (rejects) vs permissive (accepts) | D5 is literally true; drop the `CC → SC` edge from the balanced model. This is the highest-value single trace. |
| `RO, CC, ER, EX, AC, …` (EX, no SC) | Conservative (rejects) vs balanced/permissive | Confirms that SC-optionality and EX-optionality compose independently; retires the conservative model. |
| Two `SC` events in one case, corroborated by two PO confirmations in the source system | Balanced (rejects) vs permissive (accepts) | Re-confirmation is real behavior; the balanced model needs a loop. If not corroborated, it is an S5 artifact and the permissive loop should be dropped. |
| A case with `SC` and *no* preceding `CC` or `ER` | All three (all reject) | Would break D5's floor and force a rethink of the whole body block. |
| ≥30 further cases with lifecycle data showing CC/ER intervals overlapping | Concurrency (S2) vs hidden-attribute mixture (S1) | Vindicates the unordered checks; if intervals never overlap and the direction correlates with a case attribute, switch to an XOR of two guarded sequences. |
| A batch of SC-less cases whose newly exported attribute is uniformly "stocked" | True optionality vs missingness | Optionality is genuine and A5's conflation can be resolved into a guarded XOR. If any are "external", those are S3 violations that all current models silently accept. |
| Any case with a repeated `CC` or `ER` | All three (all reject) | All candidates need a rework construct; the current single-occurrence assumption (A3) is a sampling artifact. |

A useful stopping rule: after collecting lifecycle data and the stocked/external attribute for roughly 200–300 cases, re-run the same three-candidate comparison. If the balanced model's rejection rate on new cases stays low and the disagreement set with the permissive model stays empty, the balanced model can be promoted from "working hypothesis" to "reference model" — with SC compliance checked by data rules rather than by control flow.

# 10. Uncertainty Statement

Confidence levels below are subjective and calibrated on the evidence in §1: "high" means I would be surprised to be wrong (roughly 85–95%), "medium" roughly 60–80%, "low" roughly 40–60% (i.e. barely better than a coin flip).

| Decision | Confidence | Basis and what would change it |
| --- | --- | --- |
| `RO` first, `AR` last, `AC → RP → AR` tail, `AC` after both checks | Very high (≈95%+) | D1, D2, D3 plus 30/30 log support with zero counterexamples. Only a data-extraction error could overturn this. |
| SC, when present, precedes AC | High (≈90%) | D4 plus 23/23 cases. |
| SC is genuinely optional for some cases, not purely a data artifact | Medium-high (≈80%) | S4 states it; the S5 arithmetic (23 observed SC events at 90–95% completeness ⇒ ≈1–3 lost, ≈4–6 real skips) makes pure missingness arithmetically implausible at 7/30. Would be overturned if the true loss rate is far above the stated 5–10%. |
| CC and ER should be left **unordered** rather than sequenced | Medium (≈70%) | Both orders are frequent (19 vs 11) and S2 asserts parallelism; but this is order-indifference in the log, not proven concurrency (D7). This is the decision I would revisit first with lifecycle data. |
| The unordered encoding is preferable to an XOR of two sequences with equal language | Medium (≈65%) | Parsimony plus the absence of any nameable routing attribute. If a routing attribute exists and correlates with the order, the XOR encoding becomes strictly better because it supports decision mining. |
| `CC → SC` (SC never before the credit check) | Medium (≈65%) | 23/23 cases, which is strong; but it directly contradicts the spirit of D5, and the log may simply have never sampled the ER-only path. Deliberately relaxed in the permissive model precisely because of this tension. |
| No `ER → SC` edge (SC may precede ER) | Medium-high (≈80%) | V5 (2 cases) plus D5. Would collapse only if V5's ER timestamps turn out to be systematically delayed by the same integration defect that loses SC events (S5) — worth checking, since a single systematic timestamp bug could explain both. |
| EX requires both checks, is at most once, and precedes AC | Medium (≈75%) | D6 and S6 agree, and both observed cases comply — but there are only 2 cases, so this rests on normative sources rather than data. |
| EX and SC mutually unordered | Medium (≈70%) | S6 licenses it explicitly; V6 and V7 show one case on each side, which is the weakest possible empirical corroboration (n=1 per side). |
| SC repetition (the permissive loop) is real behavior | Low (≈40%) | Licensed only by the absence of a prohibition. Duplicate SC events are equally consistent with an integration retry (S5). This is the least defensible element of the permissive model and the first thing I would drop. |
| The `B_afterER` branch (SC after ER only) is legal | Low (≈50%) | D5 says so; the log says nothing (0/23 cases). A genuine coin flip, which is exactly why it lives only in the permissive candidate. |
| No rework on CC, ER, AC, RP (single occurrence of each) | Medium (≈70%) | 30/30 log support, but 30 cases is a small window for rework, which is common in custom production; no domain rule addresses it either way. |
| The balanced candidate is the right one to deploy | Medium-high (≈75%) | Conditional on the concurrency reading above. |

**Alternative interpretation that would materially change the recommendation.** Suppose the unexported attributes (S5) encode a product or channel type, and that within each type the process is strictly sequential — standard orders running `CC → ER` as the finance manager describes (S1), rush or engineering-driven orders running `ER → CC` — with SC required for the external type and skipped for the stocked type (S3/S4), and EX confined to rush cases. Every observed variant is reproduced by this mixture: the 19/11 split becomes the type mix, the bidirectional DFG edge becomes a pure aggregation artifact (mechanism 2 in §1), and V5's early SC becomes a rush-case pattern rather than evidence about enabling conditions. Under this reading the balanced model is not a well-calibrated generalization but an *over-generalization*: it admits interleavings that no policy permits, its unordered CC/ER pair misrepresents a governed decision as indifference, and its apparently modest precision loss is in fact a real loss of control. The correct model would then be an XOR over two (or three) guarded sequential branches — structurally close to the conservative candidate, but with data guards instead of variant enumeration — and the recommendation would flip to "deploy a segmented model, one branch per case type". The discriminating test is cheap and is item 1 of §9: export start timestamps and check whether CC and ER intervals overlap within cases, and whether the completion order correlates with any recoverable case attribute. Until that test is run, the balanced model should be labelled a working hypothesis rather than a discovered process.
