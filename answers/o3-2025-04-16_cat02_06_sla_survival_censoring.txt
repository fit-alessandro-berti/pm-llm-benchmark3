# 1. SLA estimands and time definitions
• Time origin: the timestamp of activity `Submit`.  
• Analysis horizon H: 72 h after `Submit` (regulatory SLA).  
• Clock: elapsed hours since `Submit`.

Events and states  
– `Resolve` (internal success)  
– `Reject`, `Withdraw` (internal terminal failures)  
– `Transfer` (handover to external organisation, internal observation stops)  
– `Open` (no terminal event before the extract’s cut-off)

Right censoring = the information loss produced by the cut-off while the case is still open.  
Competing events = termination modes that preclude ever observing internal resolution (Reject, Withdraw, Transfer when treated as a true hand-off).

We define two concrete estimands:

E1  Tail-breach survivor function S(72) = P(T > 72 h), where T is elapsed time to *any internal resolution*.  
• A success at 76 h (S03) counts as an observed breach (event at 76).  
• Open at 92 h (S09) is right-censored at 92 h, already known to have breached.  
• Withdraw at 27 h (S06) leaves the risk set at 27 as a competing event; the case neither breaches nor fulfils the SLA.  
• Transfer at 68 h (S08) is ambiguous; under the primary analysis it is **censored** at 68 h because internal resolution after hand-off is unobserved (see §2).

E2  Cumulative incidence of *late* resolution F(72) = P(T > 72 h, event = Resolve before right censoring).  
This splits the risk of tail breach into (i) never resolved, (ii) resolved late.  
• 76 h resolution contributes a late-resolution event.  
• 92 h open is still in the risk set; if it resolves after the cut-off it would enter this count, so it is right-censored.  
• Withdraw/Reject leave the risk set as competing events.  
• Transfer: same three options as in §2.

# 2. Event and censoring encoding
| observed_status | code for E1 (breach of 72 h) | code for E2 (late resolution) | right-censor? | sensitivity notes |
|-----------------|------------------------------|------------------------------|---------------|-------------------|
| resolved 72 h | event = 0, time=resolve_t | event = 0 | no | compliant success |
| resolved >72 h | event = 1, time=resolve_t | event = 1 | no | late success |
| withdrawn       | competing event = 2, time=withdraw_t | competing = 2 | no | never counts toward SLA |
| rejected        | competing event = 3 | competing = 3 | no | idem |
| transferred – Scenario A (PRIMARY) | right-censor at transfer_t | right-censor | yes | assumes external fate unknown |
| transferred – Scenario B | competing event = 4 “external” | competing = 4 | no | if hand-off closes obligation |
| transferred – Scenario C | event = 1 “automatic late breach” | event = 0 (never resolved) | no | pessimistic governance stance |
| open <72 h      | right-censor at cut-off     | right-censor | yes | still SLA compliant so far |
| open 72 h      | right-censor at cut-off, already known T>72 | right-censor | yes | partial information; treated like “breached but unresolved” |

# 3. Why naive completed-case analysis is biased
1. Survivor bias: analysing only resolved cases would exclude the very long open cases S09, S10, S11, S15, S24, S25, S26, S29, S31 – exactly the observations most at risk of breaching. The tail of the distribution is artificially shortened.
2. Informative censoring: Transfers (S08, S21, S32) are mostly P1 cases that were escalated. If we censor them non-informatively yet most would have taken longer than 72 h internally, breach risk is underestimated for high priority.
3. Competing risks: Withdrawn and rejected cases (e.g. S05, S12, S22, S30) exit early; completed-case analysis counts them as success-es because they did not breach, although they are *failures* from a product perspective.
4. Cohort imbalance: Cohort B adds `AutoCheck` and more escalations. Ignoring the staggered introduction and analysing only A or B could mistake policy change for time effect.
5. Left truncation of risk sets: open cases that are still <72 h (none in this extract) are in a different risk set than those already 72 h (S11, S26). Mixing them blurs the denominator for tail-breach probability.

# 4. Statistical analysis plan
Primary estimator  
• Aalen-Johansen cumulative-incidence curves for (i) resolution 72 h, (ii) late resolution >72 h, (iii) withdrawal/rejection, with `Transfer` censored (Scenario A).  
– Justification: competing events are present; AJ handles them without assuming proportional hazards.  
– Stratify by priority (P1 vs P2/3) and by cohort (A vs B) because policy and workload differ.

Secondary estimators  
a) Landmark Kaplan-Meier at 72 h conditional on “not yet terminal” to estimate probability of *ever* being resolved after a breach.  
b) Cause-specific Cox models with time-varying covariates (current stage, gap length) to study drivers of tail hazard.  
c) Restricted Mean Time Below SLA (RMTBS, integral of S(t) up to 72 h) for managerial KPI.

Not recommended as primary  
• Sub-distribution Fine-Gray: requires proportional sub-distribution hazard, doubtful with small N.  
• Unstratified KM: mis-classifies competing events.  
• Pure multi-state model with exact timestamps: ideal but impossible because we lack per-event times.

# 5. Process-aware features and stage hazards
Baseline covariates (fixed at Submit)  
• priority (P1-P3)  
• cohort (A/B) – proxy for policy exposure

Time-varying covariates (avoid leakage by updating only when they happen)  
• current stage = last activity in prefix (Submit, Screen, Review, Escalate, Rework, Transfer, Resolve …)  
• has_escalated flag, and time since first Escalate  
• review_count so far  
• inactivity gap = last_event_gap_h  
• AutoCheck already performed (yes/no) – changes the downstream path.

Potential leakage if used at baseline  
• “ever escalated”, “ever reworked”, variant id – because those facts happen after Submit.

Proposed state diagram (Mermaid)

```mermaid
stateDiagram-v2
    Submit --> Screen
    Screen --> AutoCheck
    Screen --> Review
    AutoCheck --> Review
    Review --> Escalate
    Escalate --> Review
    Review --> Rework
    Rework --> Review
    Review --> Resolve
    Escalate --> Resolve
    Screen --> Withdraw
    Review --> Withdraw
    Review --> Reject
    Escalate --> Transfer
    Submit --> Reject
```

Each arrow can carry a cause-specific hazard. Landmarking at each transition avoids immortal-time bias.

# 6. Sensitivity analysis
SA1  Transfer treatment  
– Scenario A (censor) vs B (competing) vs C (failure). Tail-breach risk for P1 may vary by ±10 pp; if Scenario C were true, escalation policy under-performs.

SA2  Withdrawal/Reject combined vs split. Combining them lowers the number of competing causes and can change Fine-Gray coefficients. Operational conclusion (share of internal failures) could widen or narrow.

SA3  Informative censoring by inactivity gap. Repeat primary analysis after inverse-probability censoring weights using a model of censoring ~ priority+gap. If the weighted late-resolution incidence rises, we conclude gaps are informative.

SA4  Cohort-policy effect. Run primary analysis inside A and B; then run a cause-specific Cox with cohort as covariate. If the hazard ratio for timely resolution shrinks toward 1 after adjustment for AutoCheck stage, then the policy effect operates through process change rather than direct acceleration.

Qualitative conclusions that could reverse:  
• “P1 always has lower breach probability” could flip if transferred cases are considered failures.  
• “Cohort B meets SLA faster” could disappear if AutoCheck merely deflects low-complexity work.

# 7. Operational interpretation
From the cumulative-incidence curves managers can:

Alerting  
– At 48 h compute individual conditional probability of breaching: P(T > 72 h | survival to 48 h, current stage). Flag cases above 0.3 for proactive escalation.

Workload steering  
– If RMTBS is below a target, redistribute reviewers.

Governance  
– Report monthly cause-specific incidences: on-time resolution, late resolution, withdrawal/reject, transfer.  
– Segment by priority and cohort for fairness: check that P3 cases in cohort B were not sacrificed to speed P1.

Calibration  
– Compare predicted vs actual breach counts each week; a Hosmer-Lemeshow-type time-bucket plot. Deviations signal drift.

# 2. encode two estimands and three transfer scenarios
def encode(row,transfer_scenario="A"):
    t=row.duration_or_age_h
    status=row.observed_status
    # E1: tail breach (1=breached,0=resolved<=72), competing=2/3, censor=NaN
    if status=="resolved":
        e1_event=1 if t>72 else 0
        e1_comp=None
    elif status in ("withdrawn","rejected"):
        e1_event=None
        e1_comp=status
    elif status=="transferred":
        if transfer_scenario=="A":
            e1_event=None  # censored
            e1_comp=None
        elif transfer_scenario=="B":
            e1_event=None
            e1_comp="transfer"
        elif transfer_scenario=="C":
            e1_event=1  # treat as breach
            e1_comp=None
    else:  # open
        e1_event=None
        e1_comp=None
    # censoring indicator
    censored = status in ("open",) or (status=="transferred" and transfer_scenario=="A")
    return pd.Series([t,e1_event,e1_comp,censored])

df[["time","e1_event","e1_comp","censored"]]=df.apply(encode,axis=1)

# 9. Limitations and additional data
1. No absolute timestamps  cannot estimate calendar-time congestion effects or weekend patterns.  
2. We observe only duration_or_age and last_event_gap; interior event times are missing, preventing proper multi-state hazard estimation.  
3. External outcomes after `Transfer` are unknown; risk of informative censoring remains.  
4. Cut-off date not supplied; cannot assess left-truncation or delayed entry.  
5. Workload variables (agent, queue size) absent; escalation effect confounded.  
6. Assignment mechanism to cohorts incomplete; need compliance flags.  
7. Small sample size; uncertainty is large, especially for stratified tail events.
