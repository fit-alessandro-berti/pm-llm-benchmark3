## 1. Target definition

**Primary target.** Predict `default_90d` among applications that are eventually activated under the historical lending policy.

- **Unit of analysis:** one credit-application journey. Reliably linked source/partner identifiers should be treated as one journey and assigned to the same validation split. Unlinked transfers remain separate, explicitly unresolved journeys.
- **Prediction time:** immediately after the third canonical business event, expected to be the first `Credit Review`, provided no Accept, Reject, Withdraw, Transfer, Contract Signed, or Account Activated event has occurred. This is a pre-decision landmark.
- **Features:** only information with an effective timestamp no later than the prediction timestamp.
- **Outcome:** \(Y=1\) if default occurs during \([0,90]\) days after `Account Activated`; \(Y=0\) only after the full 90-day horizon and reporting allowance have elapsed and a valid non-default label is received.
- **Population:** applications started in the study window that reach the landmark while still under review and subsequently activate under the observed policy.
- **Estimand:** for policy regime \(g\),
  \[
  r_g(x)=P(\text{default within 90 days of activation}\mid
  H(t_p)=x,\ A=1,\ G=g),
  \]
  where \(H(t_p)\) is the prefix available at prediction time and \(A=1\) denotes eventual activation. Feed availability is not part of the desired estimand; missing feeds are an observation problem.

This target is operationally defensible because default is well-defined only after credit exposure. It is nevertheless **selection-conditional**: activation occurs after prediction and depends on policy, applicant characteristics, and possibly unmeasured information. The resulting score may be shown on all applications, but its validated meaning applies only to applications resembling those activated under the relevant policy. It is not validated counterfactual default risk for rejected or withdrawn applicants.

**Alternative: all-application multi-state target.** Model transitions from review to rejection, withdrawal, transfer, continued-open status, or activation, followed after activation by default or 90-day non-default. At a fixed application-age horizon, output cumulative probabilities for mutually exclusive observed paths, such as:

- rejected before activation;
- withdrawn;
- transferred;
- still open;
- activated and defaulted within 90 days;
- activated and completed 90 days without default;
- activated but outcome still pending.

This answers “what path is likely under the current policy and process?” It does not reinterpret rejection as non-default. It can provide an output for every application, but the “activated and defaulted” probability combines disposition policy with credit risk.

A policy-specific target \(P(Y^{\text{activate}}=1\mid X)\) for every applicant would answer the lender’s informal question more directly, but it is counterfactual. Estimating it would require a well-defined activation intervention, consistency, conditional exchangeability, adequate overlap, and outcome ascertainment under activation. Those assumptions are not supplied by this export.

## 2. Cohort construction

Construct the cohort from the full event population, not from the 21,600-row labeled export.

**As-of and identity rules**

1. Include source applications whose `Application Started` timestamp is between 1 January 2024 and 31 December 2025.
2. Use only event versions and fields available by the applicable knowledge cutoff. For the current analysis, the cutoff is 15 February 2026, while process events end on 31 December 2025.
3. Canonicalize migration-related activity names using a version-controlled, process-owner-approved mapping. Preserve the original activity and source system for audit.
4. Resolve transfers with the linkage table where the relationship is reliable. Linked identifiers must not cross train/test splits. Because only about 60% are linked, report both source-application counts and linked-journey sensitivity results.
5. Classify cases from events available as of the cutoff. A missing terminal event means “still open,” not rejection or non-default.
6. For the primary model, require a valid pre-decision prediction landmark and activation after that landmark. Cases that do not reach the landmark, have ambiguous event ordering, or contain unresolved migration duplicates are reported as coverage failures rather than silently removed.
7. Never use future activation, terminal state, or label availability to construct prefix features. Activation is used only to define the primary outcome population.

**Cohort flow at the source-application level**

| Source-application state at snapshot | Count | Label/outcome status | Role in analysis |
|---|---:|---|---|
| Activated, mature non-default label | 18,900 | Observed `default_90d=0` | Primary binary outcome, subject to landmark eligibility |
| Activated, mature default label | 2,700 | Observed `default_90d=1` | Primary binary outcome, subject to landmark eligibility |
| Activated, outcome or delayed feed not mature | 3,600 | Mixture of ordinary right censoring and reporting delay; older cases may later reveal permanent feed loss | Retained as pending/censored, never coded 0 |
| Rejected | 9,100 | Default under activation is undefined | Competing disposition; evidence of activation selection |
| Withdrawn | 5,700 | Default under activation is undefined | Competing disposition |
| Transferred | 2,900 | Competing event and possible loss to another identifier/platform | Link where possible; otherwise informative missing follow-up |
| Still open | 5,100 | Administratively censored in the application process; not yet exposed | Retained in all-application process analysis; no binary default label |
| **Total** | **48,000** |  |  |

The 3,600 activated pending cases must be partitioned from timestamps:

- **ordinary right-censored:** activation occurred, but 90 days have not elapsed;
- **reporting-delay pending:** 90 days elapsed, but the case is still within the observed 7–35 day feed delay;
- **suspected permanently missing feed:** activation plus 90 plus 35 days elapsed without a label.

The aggregate snapshot does not provide the numerical split, so it should not be invented.

The primary model cohort is a later subflow of the 25,200 activated cases. It includes only cases with a valid pre-decision landmark and a mature, as-of label, while retaining mature-but-unlabeled cases for missing-feed modeling. Counts excluded for short prefixes, data defects, ambiguous duplicates, or activation before prediction must be published.

## 3. Censoring and missing-label strategy

These mechanisms should not be combined into a generic “missing outcome” category.

- **Ordinary right censoring:** an account has activated, but fewer than 90 outcome days are observable. This is genuine incomplete follow-up. It is not a non-default.
- **Delayed labels:** the 90-day horizon has ended, but the external feed has not yet arrived. This is an observation delay rather than additional event-free survival time.
- **Selection through activation:** rejection, withdrawal, transfer, and continued-open status determine whether the default outcome becomes defined and observed. This is post-prediction selection, not ordinary censoring.
- **Transfer:** in the all-application model it is a competing event. For a target following the customer across platforms, it also creates informative loss to follow-up because linkage is incomplete.
- **Permanent feed absence:** even after the maximum expected reporting delay, some activated accounts remain unlabeled. Partner origin makes this plausibly informative rather than missing completely at random.
- **Open applications:** these are administratively censored for application-state transitions, but they have not yet entered the post-activation default risk set.

**Primary analysis strategy**

1. Use a conservative binary maturity rule for negatives:
   \[
   \text{activation time}+90\text{ days}+35\text{ days}\leq
   \text{knowledge cutoff}.
   \]
   A positive can be known earlier if default has already occurred and the label was available, but confirmatory evaluation should use inception cohorts with comparable follow-up.
2. Train and evaluate the binary model among historically activated cases with as-of labels.
3. Among activated, reporting-complete cases, model the probability \(P(R=1\mid Z,A=1)\) that a label is observed. \(Z\) may include partner/source system, activation month, region, channel, and prefix attributes. These are nuisance-model variables; post-prediction determinants of feed routing must not enter the predictive score itself.
4. Use cross-fitted, stabilized inverse-probability-of-observation weights, with weight truncation and positivity diagnostics, to target all historically activated accounts rather than only accounts with functioning feeds.
5. Do **not** weight for activation in an attempt to infer default for all applications. That would change the estimand and require counterfactual assumptions.

**Sensitivity analyses**

- Fit a time-to-default model among activated accounts, using true default occurrence time where available and administrative censoring at 90 days. Use IPCW if censoring depends on observed history. `Default Recorded` time must not be substituted for occurrence time without quantifying reporting lag.
- Conduct pattern-mixture/tipping-point analyses for permanently missing feeds, separately for partner-originated and lender-originated accounts. Vary the missing cases’ default odds relative to observed cases and report bounds.
- For transfers, compare source-ID analysis, analysis using the 60% linked journeys, and bounds in which unlinked transfers have outcome rates ranging from those of linked transfers to materially higher rates.
- Compare pre-policy and post-policy models rather than relying only on a pooled model with a calendar indicator.

**Assumption status**

| Assumption or diagnostic | Status |
|---|---|
| Horizon and label-availability arithmetic | Directly testable |
| Observed feed-delay distribution and its association with source/channel | Testable among received feeds |
| Covariate overlap for the feed-observation model | Testable |
| Independent censoring after conditioning on recorded covariates | Partially testable; dependence on unmeasured risk is not |
| Missing-at-random permanent feeds conditional on \(Z\) | Fundamentally untestable from observed labels alone |
| Missing-at-random transfer linkage | Partially testable for observed covariates, not outcome dependence |
| Exchangeability of activated and rejected applicants for \(Y^{\text{activate}}\) | Fundamentally untestable here |
| Positivity of activation across applicant profiles and policies | Empirically diagnosable, but likely violated near policy thresholds |

## 4. Prefix extraction

**Fixed event-count prefixes**

The primary prefix uses the first \(K=3\) canonical business events and requires the third event to be the first `Credit Review`. The prefix timestamp is the timestamp of event \(K\). For dynamic experiments, fit separate models for \(K=1,3,5,\ldots\); do not combine predictions from different \(K\) values without encoding the landmark.

- Only events with timestamps no later than the \(K\)-th event enter the prefix.
- If several events share the boundary timestamp, use an ingestion sequence or immutable event ID. Without one, treat the timestamp batch atomically or flag the case for a tie-handling sensitivity analysis.
- Cases with fewer than \(K\) events are not padded with later events. Report fixed-prefix coverage and use a separately validated shorter-prefix or elapsed-time model.
- Cases already accepted, rejected, withdrawn, transferred, signed, or activated by the landmark are not actionable members of the pre-decision risk set.

**Elapsed-time prefixes**

A complementary design uses all events observed by a fixed elapsed time, such as 24 hours after `Application Started`.

- Applications with only the start event receive zero-count/default process features plus valid static attributes.
- Applications closed before 24 hours have already experienced a competing disposition; they should not be scored at 24 hours as though still under review.
- A truly universal score can be generated at application start, but it is a different, less informed landmark.

**Document loops and rework**

Repeated `Request Documents` and `Credit Review` events are retained because they reflect rework. Event-count prefixes may reach the same \(K\) at different elapsed times, while elapsed-time prefixes may contain very different numbers of events. Results should therefore be compared across event-count, elapsed-time, and stage-based landmarks.

**Migration handling**

Activity renaming is repaired with a dated, version-controlled map that only merges semantically equivalent activities. Exact duplicate rows can be removed. Near-duplicates after 15 October 2025 should be reconciled with a source event identifier; absent such an identifier, flag or quarantine ambiguous prefix cases and run a retain-versus-collapse sensitivity analysis. Legitimate same-time document rework must not be automatically deleted.

## 5. Process-aware features

**Static case attributes, frozen at application start**

- channel, region, requested amount;
- requested-amount bands and log amount;
- application start hour, weekday, month, and holiday indicator;
- policy regime at prediction time;
- source system and migration regime.

These fields are valid only if immutable or versioned. A value backfilled after decision must be reconstructed or dropped.

**Prefix-derived features**

- **Control flow:** activity sequence, last activity, counts by activity, number of distinct activities, direct-follow pairs, prefix variant, transition rarity, and whether the expected start–KYC–review path was followed.
- **Rework:** document-request count, Credit Review revisit count, self-loops, review-to-document-return cycles, repeated KYC, and number of risk-score updates.
- **Timing:** elapsed time since application start, inter-event mean/max/variance, time since last event, time to first review, and same-day versus overnight waiting.
- **Resource/queue:** current resource, number of distinct resources, handoffs, resource changes after document requests, and workload known at prediction time.
- **Risk score:** latest score whose effective timestamp is at or before prediction, initial score, change from initial score, and update count.
- **Calendar/process context:** pre/post 1 July policy indicator, pre/post migration indicator, week/month, source-system version, and recent application arrival volume.

There is only one timestamp per event and no lifecycle start/complete field. Consequently, PM4Py service and waiting-time functions should not be interpreted as true processing/service durations unless lifecycle semantics are added.

**Features requiring historical reference data**

- prefix-variant and DFG transition frequencies learned from earlier training prefixes;
- resource workload based on cases known open at the prediction time;
- resource experience reconstructed as the number or type of prior events handled before that timestamp;
- recent queue size and arrival rate;
- historical processing or default aggregates using only labels matured before the reference time.

All such features must be recomputed within each temporal training fold. Target encoding, resource performance, or variant outcome rates calculated from the entire export would leak future labels and regimes.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Set after the final decision and strongly encodes acceptance and treatment intensity | Only valid for a prediction explicitly made after limit assignment | **Drop** for the primary landmark | It is unavailable pre-decision and may mediate the effect of lending policy on default |
| `decision_reason` | Reveals Accept/Reject logic and is populated at or after decision | Must have an effective timestamp no later than a post-decision landmark | **Drop** | Unavailable at first Credit Review and directly encodes future disposition |
| `collection_status` | Post-activation field that may directly reveal delinquency/default | Never valid for pre-activation prediction | **Drop** | Direct target leakage |
| Future events, including `Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded` | Reveal selection, exposure, intervention, or outcome | Filter event rows to timestamp at or before prediction before aggregation | **Drop from prefix** | A full-trace process feature would otherwise leak the future |
| `documents_total` | Nightly snapshot may include later uploads from the same calendar day | Require event-time versioning and `effective_at <= prediction_time` | **Repair or drop** | Calendar-date filtering is insufficient; absent exact versioning, omit it |
| Updated `risk_score` | Latest exported value may have been updated after the prediction point or backfilled onto older rows | Use the last version with score-effective timestamp no later than prediction | **Keep if versioned; otherwise repair/drop** | A valid contemporaneous risk score is useful, but the final score is leaky |
| Resource experience at extraction | Uses work performed after the event and favors employees active later | Reconstruct from HR effective dates or prior events strictly before prediction | **Repair or drop** | Extraction-time tenure is future information |
| `label_available_at` | Encodes outcome workflow, calendar maturity, source system, and possibly outcome severity | Use only for as-of label construction and missingness weights | **Drop from predictors** | It is an observation-process variable, not a pre-decision applicant feature |
| `default_90d` | Direct target leakage when repeated on event rows | Access only after prefix features are finalized and only when available as of cutoff | **Target only** | Must never be present in event-level feature aggregation |
| `case:channel`, `case:region`, `case:requested_amount` | Case attributes may be overwritten after application | Use immutable application-start values or effective-dated versions | **Keep if frozen; repair otherwise** | Nominally static does not guarantee historically available |
| `source_system` | Can proxy migration, partner feed loss, and policy regime | Must be known at prediction time; evaluate temporal robustness | **Keep with monitoring** | Useful for shift and missingness, but may lead to brittle calibration |
| `data_extract_time` | Encodes the snapshot and label maturity rather than applicant risk | Use only to enforce the knowledge cutoff | **Drop from predictors** | Operational metadata, not a predictive feature |

## 7. Validation design

A random case split would mix policy regimes, allow migration variants into both development and test data, share linked transfer journeys across folds, and let recent process patterns inform older cases. It would also evaluate mostly on whichever accounts happened to have mature feeds, hiding temporal label selection.

**Current temporal design by application start**

- **Training:** 1 January–31 December 2024.
- **Pre-policy validation:** 1 January–30 June 2025.
- **Post-policy, pre-migration test:** 1 July–14 October 2025.
- **Post-migration shadow cohort:** 15 October–31 December 2025.

Within each block:

- assign the whole linked journey according to its earliest application start;
- derive policy regime at prediction time and report cases crossing a regime boundary separately;
- fit preprocessing, activity frequencies, DFG statistics, calibration, and feed-observation weights using earlier data only;
- suppress any label whose `label_available_at` is later than the simulated model-fit or evaluation cutoff;
- use block/bootstrap confidence intervals by start week, clustering linked journeys.

At the 15 February 2026 cutoff, conservative reporting completeness requires approximately activation by 13 October 2025. Thus no account activated on or after the 15 October migration can yet have a full 90-day horizon plus 35-day reporting allowance. The migration cohort can currently support schema, prefix-coverage, duplication, missingness, and drift tests—but not an honest confirmatory 90-day default evaluation. That evaluation should wait for a later extraction, approximately May 2026 for accounts activated through 31 December, plus confirmation that the outcome table covers the extended period.

Use rolling-origin backtests where possible: at each historical fit date, train only on labels available then and score the next start-time cohort. A current snapshot can reproduce historical label availability if `label_available_at` is reliable, but cannot reconstruct covariates that were overwritten rather than versioned.

**Metrics for the primary binary target**

- weighted Brier score and log loss;
- calibration intercept, slope, and reliability curves;
- weighted AUROC and precision–recall AUC;
- sensitivity, specificity, PPV, and capture rate at operational review capacities;
- expected calibration error with uncertainty intervals;
- label-observation rate, activation rate, and landmark coverage alongside predictive metrics.

Weights address censoring/feed observation only under stated assumptions; they do not turn the target into all-applicant counterfactual risk.

For the survival sensitivity analysis, report 90-day cumulative incidence calibration, IPCW time-dependent AUC, integrated Brier score through 90 days, and a censoring-adjusted concordance measure.

Report all metrics by channel, region, requested-amount band, policy regime, source system, partner origin, linked-transfer status, and prediction month. For each subgroup, also report activation and missing-feed rates because apparent predictive differences may be selection differences. Compare score distributions, prefix variants, activity frequencies, missingness, and calibration across the policy and migration boundaries.

## 8. Limitations and decision-use boundary

The study can estimate predictive associations between early prefixes and 90-day default **among accounts activated under the observed policy**, subject to censoring and feed assumptions. It can also estimate observed workflow/disposition probabilities for all applications.

It cannot claim that:

- a rejected, withdrawn, transferred, or open application would not default;
- the activated-account score is calibrated for rejected applicants;
- observed differences are causal effects of applicant attributes, resources, policy, or process paths;
- inverse-probability weighting for feed availability solves activation selection;
- performance before 1 July 2025 transfers unchanged to the new policy;
- current data validate post-migration 90-day outcomes.

Conditioning on activation can induce collider and policy-selection effects. The same prefix may receive a different score relationship after a threshold change because both who activates and what credit terms they receive have changed. A model for \(Y^{\text{activate}}\) for every applicant would need randomized exploration, a defensible quasi-experiment, or unusually strong exchangeability and positivity assumptions.

The default score should therefore be used as a risk-triage input for cases expected or planned to activate, accompanied by a separate disposition/activation model and explicit abstention for unsupported prefixes. It should not be used to call rejected cases “safe” or as sole evidence for automatic rejection.

Deployment can alter the data-generating process in several ways:

1. Using the score in acceptance decisions changes which applicants activate and therefore which labels are observed, creating selective-label feedback.
2. Changing limits, pricing, collateral, or terms in response to the score changes the post-activation default outcome itself.
3. Requesting documents or escalating manual review changes event sequences, queue times, withdrawal rates, and prefix features.
4. Earlier collections or support interventions can prevent defaults, making high predicted risk appear negatively associated with observed outcomes.
5. Routing cases to partners or specialists changes linkage and feed-missingness rates.
6. Staff may adapt logging or applicant-handling behavior once the score becomes operational.

These changes require ongoing shadow evaluation, randomized or policy-controlled monitoring where feasible, and periodic recalibration rather than assuming a stationary benchmark.

## 9. PM4Py-oriented Python implementation skeleton

```python
import warnings
import numpy as np
import pandas as pd
import pm4py

CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"
RESOURCE, LABEL_AT = "org:resource", "label_available_at"
STUDY_START = pd.Timestamp("2024-01-01", tz="UTC")
EVENT_END = pd.Timestamp("2025-12-31 23:59:59", tz="UTC")
CUTOFF = pd.Timestamp("2026-02-15 23:59:59", tz="UTC")
POLICY_DATE = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION_DATE = pd.Timestamp("2025-10-15", tz="UTC")
HORIZON, MAX_FEED_LAG, K = pd.Timedelta(days=90), pd.Timedelta(days=35), 3

date_cols = [TS, LABEL_AT, "data_extract_time"]
df = pd.read_csv("applications_events.csv", parse_dates=date_cols)
for col in date_cols:
    df[col] = pd.to_datetime(df[col], utc=True, errors="coerce")

# A historical cutoff is valid only if event fields are immutable/versioned.
df = df.loc[df[TS].notna() & df[TS].le(EVENT_END)].copy()
df = df.loc[df["data_extract_time"].isna()
            | df["data_extract_time"].le(CUTOFF)].copy()

# Populate from an approved migration dictionary; do not infer mappings from labels.
ACTIVITY_MAP = {}
df[ACT] = df[ACT].astype("string").str.strip().replace(ACTIVITY_MAP)

# Remove only exact duplicated rows. Near-duplicates are flagged, not blindly collapsed.
exact_dup = df.duplicated(keep="first")
df = df.loc[~exact_dup].copy()
dup_key = [CASE, ACT, TS, RESOURCE, "source_system"]
df["_possible_migration_duplicate"] = (
    df[TS].ge(MIGRATION_DATE)
    & df.duplicated(dup_key, keep=False)
)
df["_row_order"] = np.arange(len(df))
df = df.sort_values([CASE, TS, "_row_order"])

# Prefer the explicit Application Started event; fall back to first event for audit.
first_event = df.groupby(CASE)[TS].min()
app_start = (df.loc[df[ACT].eq("Application Started")]
               .groupby(CASE)[TS].min())
case_start = app_start.reindex(first_event.index).fillna(first_event)
study_ids = case_start[
    case_start.between(STUDY_START, EVENT_END, inclusive="both")
].index
df = df.loc[df[CASE].isin(study_ids)].copy()
case_start = case_start.loc[study_ids]

# Linkage resolution would occur here if a versioned transfer linkage table were supplied.
cases = pd.DataFrame({"case_start": case_start})
terminal_activities = {
    "activation_time": "Account Activated",
    "rejection_time": "Rejected",
    "withdrawal_time": "Withdrawn",
    "transfer_time": "Transferred",
}
for col, activity in terminal_activities.items():
    cases[col] = (df.loc[df[ACT].eq(activity)]
                    .groupby(CASE)[TS].min().reindex(cases.index))

terminal_cols = list(terminal_activities)
has_terminal = cases[terminal_cols].notna().any(axis=1)
first_terminal_col = cases.loc[has_terminal, terminal_cols].idxmin(axis=1)
state_names = {
    "activation_time": "activated", "rejection_time": "rejected",
    "withdrawal_time": "withdrawn", "transfer_time": "transferred",
}
cases["terminal_state"] = "still_open"
cases.loc[has_terminal, "terminal_state"] = first_terminal_col.map(state_names)
cases["terminal_time"] = cases[terminal_cols].min(axis=1)
cases["process_censor_time"] = cases["terminal_time"].fillna(EVENT_END)

# Convert labels robustly, but make them known only at label_available_at <= cutoff.
numeric_label = pd.to_numeric(df["default_90d"], errors="coerce")
text_label = (df["default_90d"].astype("string").str.lower()
              .map({"true": 1, "false": 0, "yes": 1, "no": 0}))
df["_label"] = numeric_label.where(numeric_label.isin([0, 1]), text_label)
known_rows = df.loc[
    df["_label"].notna() & df[LABEL_AT].notna() & df[LABEL_AT].le(CUTOFF)
]
label_info = known_rows.groupby(CASE).agg(
    default_90d=("_label", "max"),
    label_available_at=(LABEL_AT, "min"),
    label_values=("_label", "nunique"),
)
cases = cases.join(label_info)
cases["label_known_asof"] = cases["default_90d"].notna()
cases["label_inconsistent"] = cases["label_values"].fillna(0).gt(1)

activated = cases["activation_time"].notna()
cases["horizon_end"] = cases["activation_time"] + HORIZON
cases["reporting_deadline"] = cases["horizon_end"] + MAX_FEED_LAG
cases["reporting_complete"] = (
    activated & cases["reporting_deadline"].le(CUTOFF)
)
cases["right_censored_90d"] = (
    activated & cases["horizon_end"].gt(CUTOFF)
    & ~cases["default_90d"].eq(1)
)
cases["default_censor_time"] = cases["horizon_end"].where(
    cases["horizon_end"].le(CUTOFF), CUTOFF
)

cases["outcome_state"] = "not_activated/" + cases["terminal_state"]
cases.loc[cases["right_censored_90d"], "outcome_state"] = "right_censored"
delayed = (activated & ~cases["label_known_asof"]
           & cases["horizon_end"].le(CUTOFF)
           & cases["reporting_deadline"].gt(CUTOFF))
missing_feed = (activated & ~cases["label_known_asof"]
                & cases["reporting_complete"])
observed = (activated & cases["label_known_asof"]
            & (cases["horizon_end"].le(CUTOFF)
               | cases["default_90d"].eq(1)))
cases.loc[delayed, "outcome_state"] = "delayed_feed"
cases.loc[missing_feed, "outcome_state"] = "suspected_missing_feed"
cases.loc[observed, "outcome_state"] = "labeled"

expected = {
    "activated": 25200, "rejected": 9100, "withdrawn": 5700,
    "transferred": 2900, "still_open": 5100,
}
observed_flow = cases["terminal_state"].value_counts().to_dict()
print("Cases:", len(cases), "\nTerminal flow:", observed_flow)
print("Outcome states:\n", cases["outcome_state"].value_counts())
if len(cases) != 48000 or any(observed_flow.get(k, 0) != v
                              for k, v in expected.items()):
    warnings.warn("Observed flow differs from the supplied snapshot; audit mappings.")

# Remove targets and known post-decision fields before PM4Py sees feature events.
forbidden = {
    "final_limit", "decision_reason", "collection_status", "documents_total",
    "default_90d", "label_available_at", "data_extract_time",
}
safe_cols = [
    CASE, ACT, TS, RESOURCE, "case:channel", "case:region",
    "case:requested_amount", "risk_score", "source_system",
    "_possible_migration_duplicate",
]
safe = df[[c for c in safe_cols if c in df.columns]].copy()
safe["risk_score"] = pd.to_numeric(safe["risk_score"], errors="coerce")
formatted = pm4py.format_dataframe(
    safe, case_id=CASE, activity_key=ACT, timestamp_key=TS
)
event_log = pm4py.convert_to_event_log(formatted)

# Fixed-length prefixes. Short traces are retained for coverage reporting, not padded.
fixed_log = pm4py.get_prefixes_from_log(event_log, length=K)
prefix = pm4py.convert_to_dataframe(fixed_log).sort_values([CASE, TS])
prefix_sizes = prefix.groupby(CASE).size()
exact_k = prefix_sizes[prefix_sizes.eq(K)].index
prefix = prefix.loc[prefix[CASE].isin(exact_k)].copy()

last_event = prefix.groupby(CASE, as_index=False).tail(1).set_index(CASE)
has_decision = prefix[ACT].isin({
    "Accepted", "Rejected", "Withdrawn", "Transferred",
    "Contract Signed", "Account Activated",
}).groupby(prefix[CASE]).any()
ambiguous_dup = prefix.groupby(CASE)["_possible_migration_duplicate"].any()
eligible = last_event.index[
    last_event[ACT].eq("Credit Review")
    & ~has_decision.reindex(last_event.index, fill_value=False)
    & ~ambiguous_dup.reindex(last_event.index, fill_value=False)
]
prefix = prefix.loc[prefix[CASE].isin(eligible)].copy()

def first_nonnull(s):
    s = s.dropna()
    return s.iloc[0] if len(s) else np.nan

def last_nonnull(s):
    s = s.dropna()
    return s.iloc[-1] if len(s) else np.nan

def handoffs(s):
    s = s.dropna()
    return max(int((s.ne(s.shift())).sum()) - 1, 0)

g = prefix.groupby(CASE)
features = g.agg(
    prediction_time=(TS, "max"),
    prefix_start=(TS, "min"),
    n_events=(ACT, "size"),
    n_activities=(ACT, "nunique"),

    features["prediction_time"] - features["prefix_start"]

features["handoffs"] = g[RESOURCE].agg(handoffs)

features["credit_reviews"] = g[ACT].agg(

features["risk_score_latest"] = g["risk_score"].agg(last_nonnull)
for raw_col, out_col in [
    ("case:channel", "channel"), ("case:region", "region"),
    ("case:requested_amount", "requested_amount"),
    ("source_system", "source_system"),
]:
    features[out_col] = g[raw_col].agg(first_nonnull)

features = features.reset_index()
features["policy_post"] = features["prediction_time"].ge(POLICY_DATE)
features["migration_post"] = features["prediction_time"].ge(MIGRATION_DATE)

analysis["split"] = np.select(

        analysis["case_start"].lt(pd.Timestamp("2025-01-01", tz="UTC")),

        analysis["case_start"].lt(MIGRATION_DATE),
    ],
    ["train", "validation_pre_policy", "test_post_policy",],
    default="shadow_post_migration",
)
analysis["mature_binary"] = (
    analysis["reporting_complete"]
    & analysis["label_known_asof"]
    & ~analysis["label_inconsistent"]
)
model_ready = analysis.loc[
    analysis["terminal_state"].eq("activated")
    & analysis["activation_time"].gt(analysis["prediction_time"])
    & analysis["mature_binary"]
].copy()
print("Model-ready by split:\n", model_ready["split"].value_counts())

# Learn process reference structures from training prefixes only.

if len(train_prefix):
    train_fmt = pm4py.format_dataframe(
```
