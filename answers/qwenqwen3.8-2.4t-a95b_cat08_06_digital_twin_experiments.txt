## 1. Model scope and state variables

The digital twin should be a **stochastic, discrete-event, resource-constrained process simulation** of the municipal building-permit workflow. Its purpose is not only to reproduce historical cases, but to compare interventions under:

- non-stationary demand,
- resource calendars and skill restrictions,
- rework and appeals,
- applicant/third-party delays,
- cross-case dependencies,
- policy changes.

### Boundary

The simulated process starts at **Submit application** and ends at **Issue permit** or **Reject application**.

Included:

- municipal processing activities,
- queues and resource assignment,
- applicant document-response delays,
- public-notice duration and latent objection effects,
- inspection scheduling, travel, batching, and no-shows,
- rework loops,
- legal/calendar constraints,
- intervention-specific pre-submission or triage steps where relevant.

Excluded, unless modeled as an external delay or scenario factor:

- actual construction work,
- post-permit compliance enforcement,
- full political decision-making,
- detailed architectural design work,
- external court appeals beyond a modeled appeal/rework delay.

The twin should be refreshable from new event logs, but the simulation engine itself should remain separate from PM4Py log-mining code.

### Entities

| Entity | Purpose |
|---|---|
| Case | One building-permit application. |
| Document request | Missing-document loop between municipality and applicant. |
| Review task | Planning, fire-safety, environmental, legal, completeness work. |
| Inspection job | Scheduling, travel, site visit, possible rework. |
| Public-notice period | Fixed minimum duration plus possible objection extension. |
| Objection cluster | Latent object representing neighborhood objections affecting one or more related cases. |
| Architect cohort | Source of correlated submissions and possible bundled inspections. |
| Inspection bundle | Group of cases scheduled together by district/architect/inspector route. |
| Resource unit | Individual clerk, planner, fire reviewer, environmental reviewer, inspector, legal officer, or system capacity. |
| Calendar exception | Holidays, council meetings, part-time availability, non-permit duties, seasonal capacity changes. |

### Queues

The model should not use one generic queue. It should include separate queues or queue classes for:

- completeness check,
- missing-document response,
- planning review by case type/skill,
- fire-safety review,
- environmental review,
- inspection scheduling,
- inspection execution by district,
- decision drafting,
- legal check,
- urgent/aging priority queue,
- appeal/rework re-entry queue.

Queues should support:

- FIFO as default,
- priority for aging or urgent cases,
- skill-based routing,
- district-based routing for inspections,
- batching/bundling where allowed,
- calendar-aware waiting.

### Calendars

Calendars are first-class model objects.

Important calendar effects:

- clerks: Monday-Friday 08:00-16:00, one clerk dedicated to portal support on Mondays;
- planners: Monday-Friday 09:00-17:00, two planners restricted to Simple renovation;
- fire reviewers: Tuesday-Thursday only;
- environmental reviewers: Monday-Friday, but 40% reserved for non-permit duties;
- inspectors: field visits Tuesday-Friday, travel time district-dependent;
- legal officers: unavailable during council meeting weeks except urgent cases;
- public holidays affect municipal work but not necessarily applicant response;
- public-notice periods continue over weekends/holidays unless legally paused;
- temporary inspector capacity applies only in selected peak months.

### Cross-case dependencies

The simulation must not treat cases as fully independent. Dependencies to model:

1. **Architect submission bursts**  
   Large architects submit multiple related applications in the same week. This can be modeled using a batch-arrival or Hawkes-like process conditioned on architect identity.

2. **Inspection bundling**  
   Cases from the same architect and district, or cases in the same geographic area, may be grouped. Bundling reduces travel time per case but can increase waiting for the first case in the bundle.

3. **Neighborhood objections**  
   Objection events are not fully observed. The model should treat objections as latent events inferred from unusually long public-notice durations. Objections may affect multiple related cases in the same district or notice window.

4. **Shared specialized resources**  
   Fire reviewers, environmental reviewers, inspectors, and legal officers create coupling across cases through shared calendars and queues.

5. **Council calendar effects**  
   Legal check and some complex decisions are affected by council meeting weeks. This creates correlated delays across complex and commercial cases.

### 2.4 Service-time and waiting-time estimation

The log contains many completion timestamps but not reliable start timestamps. Therefore:

- completion-to-completion elapsed time is a **sojourn time**, not pure service time;
- service time and waiting time must be separated using assumptions, calendar-aware queueing logic, and empirical summaries.

For activities with observed start timestamps:

```text
service_time = completion_timestamp - start_timestamp
waiting_time = start_timestamp - previous_completion_timestamp
```

For activities without start timestamps:

1. Use the provided median and p90 service-time summaries as service-time priors.
2. Use resource calendars and queue lengths to infer waiting.
3. Fit service distributions separately from waiting distributions.
4. Do not assign all elapsed time to service.

Recommended distributions:

| Duration type | Candidate distributions |
|---|---|
| Short administrative service | lognormal, gamma, triangular |
| Review service | lognormal, gamma, hyperexponential |
| Applicant response | lognormal, Weibull, Pareto tail, mixture |
| Public notice | fixed minimum plus mixture extension |
| Inspection travel | district-conditioned empirical or gamma |
| Rework delay | empirical or lognormal |
| Queue waiting | simulated from resource contention rather than directly fitted where possible |

## 3. Assumptions

### Arrivals

1. Applications arrive exogenously to the municipal process, except where an intervention explicitly changes submission timing.
2. The arrival process is non-stationary and depends on month, weekday, and hour.
3. March-May and September-November have higher demand than January-February.
4. Mondays have elevated portal submissions, approximately 2.2 times Wednesday levels.
5. Large architects generate correlated batches of applications.
6. Intervention D7 can move a fraction of Monday submissions to appointment slots on other days, but may introduce applicant-side waiting before formal submission.
7. The pre-submission checker D1 may slightly delay formal submission because applicants prepare more documents before entering the official process.

### Service times

1. Municipal service times are stochastic and resource-dependent.
2. Service times are not directly observable for many activities because start timestamps are missing.
3. Completion-to-completion elapsed time is a sojourn time containing waiting, calendar delays, queueing, and service.
4. Service-time distributions are approximated from empirical summaries, expert input, and the subset of events with start timestamps.
5. Service times are assumed conditionally independent of queue waiting given case type, activity, resource pool, and intervention.
6. System tasks such as `Issue permit` have near-zero municipal service time but may still have small administrative delay.
7. Inspection service time includes on-site work; travel time is modeled separately.

### Routing

1. The observed flags `requires_fire`, `requires_environment`, and `requires_public_notice` are informative but incomplete.
2. Fire-safety review is required when `requires_fire=yes` and may also be required when building area exceeds an unobserved threshold.
3. Environmental review is required when `requires_environment=yes` and may also be required in environmentally sensitive districts.
4. Public notice is mandatory for Complex variance and some New residential cases.
5. Legal check is not required for all cases; its probability is estimated from variants and case type.
6. Decision drafting waits for all required reviews and inspection results.
7. Rare emergency paths removed from the log are outside the primary calibration scope unless explicitly added as a stress scenario.

### Resources/calendars

1. HR-reconstructed calendars are the best available representation of municipal capacity.
2. Clerks are available Monday-Friday, but one clerk is occupied by portal support on Mondays.
3. Two planners are restricted to Simple renovation cases.
4. Fire reviewers are available only Tuesday-Thursday.
5. Environmental reviewers have only about 60% effective permit capacity because of non-permit duties.
6. Inspectors perform field visits Tuesday-Friday and have district-dependent travel times.
7. Legal officers are largely unavailable during council meeting weeks except for urgent cases.
8. Public holidays reduce municipal capacity but do not necessarily stop applicant or third-party clocks.
9. Temporary inspector D4 adds one inspector only during selected peak months.

### Rework

1. Rework can occur after Planning review, Site inspection, Legal check, and applicant appeal.
2. Rework probabilities are estimated from repeated activities and variant groups.
3. Rework reasons are not reliably coded; therefore, rework cause is treated as latent.
4. Rework consumes municipal resources and can create additional applicant delays.
5. Interventions that reduce missing documents or improve triage may reduce some rework, but could also reveal new issues earlier.
6. Inspection rework is sensitive to inspector availability and applicant readiness.

### Applicant/third-party response

1. Applicant response to missing-document requests is external to municipal capacity.
2. Response times are heavy-tailed.
3. The municipality cannot force immediate applicant response, but reminders or pre-submission checking can change behavior.
4. Third-party consultant reports can delay environmental review.
5. Inspection no-shows are possible and depend on applicant readiness.
6. Objections are third-party actions and are not fully observed in the log.

### Cross-case dependencies

1. Same-architect submissions can be correlated in time and district.
2. Related cases can be bundled for inspection scheduling.
3. Bundling reduces travel time but can increase waiting for the first case in the bundle.
4. Neighborhood objections may affect multiple cases in the same district or related public-notice window.
5. Shared specialized resources create dependencies across otherwise unrelated cases.
6. Council calendar effects create correlated delays for legal and complex cases.

### Non-stationary demand

1. Demand varies seasonally and by weekday.
2. Peak demand can expose capacity constraints that are invisible in average-load analysis.
3. Interventions should be evaluated over a full seasonal cycle.
4. Demand uncertainty should be included in stress testing.
5. Appointment-slot interventions can change the shape of arrivals but not necessarily the total volume.

### Missing data

1. Start timestamps are missing for many human activities.
2. Objection events are missing; public-notice duration is only a proxy.
3. Rework reasons are unstructured and unreliable.
4. Some emergency decisions are removed from the log.
5. Resource calendars are reconstructed, not directly observed from the event log.
6. The flattened case log may underrepresent dependencies between related applications.
7. Missing data are handled through imputation, latent variables, sensitivity analysis, and explicit uncertainty ranges rather than treated as observed facts.

## 4. Experiment matrix

All interventions should be evaluated using common random numbers where possible, so that differences are attributable to policy changes rather than random demand variation. The matrix below includes baseline, individual interventions, combined policies, and stress scenarios.

| Experiment | Factors changed | Levels / parameterization | Expected trade-offs |
|---|---|---|---|
| E0 Baseline | Current process, current calendars, current routing | No intervention; seasonal demand as estimated; current resource levels | Establishes reference distribution of cycle time, SLA compliance, backlog, utilization, and fairness. |
| E1 D1 Pre-submission document checker | Missing-document probability, applicant preparation effort | Reduce missing-doc loop probability by 30%, 50%, or 70%; add applicant pre-submission time; possible small reduction in formal submission rate | Fewer completeness loops and lower clerk rework; higher applicant effort; possible shift of work outside municipal log; may reduce simple-case duration substantially. |
| E2 D2 Simple-renovation no-inspection rule | Inspection routing for low-risk Simple renovation | Skip `Site inspection` if `application_value < EUR 50,000` and no prior violations; optionally require document-based verification | Lower inspector load and shorter simple-case cycle time; risk of undetected non-compliance; needs risk score and audit mechanism. |
| E3 D3 District-batched inspection scheduling | Inspection queue discipline and travel time | Bundle cases by district/architect when 2+ cases are ready; reduce travel time by 10%-40%; increase waiting for first case in bundle | Better inspector productivity and lower travel; possible fairness concerns and increased waiting for early bundle members. |
| E4 D4 Temporary peak-month inspector | Inspection capacity | Add one inspector in March-May and September-November; full-time or 0.8 FTE variants | Reduces peak inspection queue and tail duration; cost increase; benefit depends on whether inspection is the active bottleneck. |
| E5 D5 Parallel legal pre-check | Legal routing for Commercial and Complex variance | Start legal pre-check before final decision drafting for selected case types; legal capacity unchanged or slightly increased | Shortens commercial/complex tail; increases legal WIP and possible rework if facts change; may worsen legal utilization if not triaged. |
| E6 D6 Reserved planner for aging cases | Priority rule for planning/decision drafting | Reserve one planner each day for cases above aging threshold, e.g. p75 or SLA risk | Improves tail and SLA compliance; may increase average duration for new cases; requires clear aging threshold. |
| E7 D7 Architect-facing appointment slots | Arrival shaping | Move 20%, 40%, or 60% of large-architect Monday submissions to Tue-Thu slots; add pre-submission waiting | Smooths clerk/planner queue spikes; may reduce Monday peak delays; could increase applicant waiting before formal submission. |
| E8 D8 Environmental-review triage | Environmental routing and service time | Classify low-risk environmental cases using district and project attributes; reduce service time or route to junior reviewer; high-risk unchanged | Faster environmental review for easy cases; risk of misclassification; requires data quality and audit. |
| E9 D9 Public-notice objection early-warning | Latent objection handling | Add early objection detection; reduce objection extension p90 by 20%-50%; add municipal/administrative effort | Shortens public-notice tail for contested cases; may increase staff workload; does not eliminate legal objection rights. |
| E10 D10 Combined D1+D2+D3+D4 | Multiple interventions | Pre-submission checker, low-risk no-inspection, district batching, temporary peak inspector | Synergistic reduction in simple/residential delays and inspection bottleneck; higher implementation complexity and cost; needs risk governance. |
| E11 Combined D1+D2+D7 | Demand smoothing plus document quality plus inspection exemption | D1 at 50% missing-doc reduction; D2 low-risk threshold; D7 at 40% Monday shift | Strong effect on simple and low-value cases; reduces clerk and inspector load; may increase applicant-facing process complexity. |
| E12 Combined D5+D6+D9 | Tail-reduction package for complex/commercial | Legal pre-check, aging planner reserve, objection early warning | Targets long-tail cases; may improve SLA compliance without increasing broad capacity; may stress specialized resources. |
| S1 Stress: demand surge | Non-stationary demand shock | Peak-month arrival rate ×1.3 or ×1.5; Monday burst intensity increased | Tests whether interventions remain effective under surge; likely exposes clerk, planner, and inspector bottlenecks. |
| S2 Stress: objection wave | Latent public-notice shock | Objection probability ×1.5; public-notice extension p90 increased to 90 days; related cases clustered | Tests D9 and complex-case resilience; expected tail degradation, especially Complex variance. |
| S3 Stress: resource shortage | Calendar/capacity shock | One inspector absent for 4 weeks; legal capacity reduced by council meeting extension; environmental non-permit duty rises to 60% | Tests robustness of D4, D5, D8; may reveal hidden dependencies on specialized resources. |
| S4 Stress: case-mix shift | Demand composition shock | Complex variance share rises from 10% to 15%; Simple renovation share falls | Tests whether efficiency interventions for simple cases hide deterioration in complex-case performance. |

For each experiment, the simulation should record outcomes by:

- case type,
- district,
- architect tier,
- month,
- weekday,
- intervention,
- replication,
- random seed.

## 5. Warm-up, replications, and uncertainty treatment

### Warm-up

Because demand is non-stationary, a traditional steady-state warm-up is not sufficient by itself. The model should use a **seasonal burn-in** approach.

Recommended approach:

1. Simulate at least 24 months.
2. Use the first 3 to 6 months as warm-up.
3. Initialize the system with either:
   - an empty pipeline, for clean comparative experiments; or
   - an empirical backlog sampled from the historical log, for operational realism.
4. Discard warm-up results unless the experiment explicitly studies backlog clearing.
5. Align seasonal effects across replications using common calendar structures.

If the municipality wants to compare interventions over an 18-month horizon, simulate 24 months and evaluate the final 18 months after warm-up.

### Run length

Minimum recommended run length:

```text
24 simulated months per replication
```

Rationale:

- covers two full seasonal cycles;
- includes peak and off-peak periods;
- allows rare tail events to appear;
- supports monthly and quarterly comparisons.

For high-stakes decisions:

```text
36 simulated months per replication
```

or multiple simulated years with different seasonal seeds.

### Replications

Use at least:

```text
30 replications for screening experiments
50-100 replications for final comparison
```

For heavy-tailed outcomes, use more replications if p95 or p99 estimates are unstable.

### Random seeds and common random numbers

Use a reproducible seed structure:

```text
seed = base_seed + replication_id
```

Use common random numbers across interventions for:

- arrivals,
- case attributes,
- applicant response propensities,
- latent objection events,
- resource calendar shocks,
- base service-time random draws where comparable.

This reduces variance when comparing policies.

### Confidence intervals

For each metric and experiment:

- compute mean or median across replications;
- compute 95% confidence intervals for means;
- compute bootstrap confidence intervals for quantiles;
- avoid relying only on averages because durations are heavy-tailed.

Recommended metrics:

```text
median cycle time
p75 cycle time
p90 cycle time
p95 cycle time
p99 cycle time
SLA compliance rate
backlog size
resource utilization
rework rate
fairness gap
```

### Heavy-tailed durations

Heavy tails arise from:

- applicant response,
- objections,
- complex variance cases,
- inspection rework,
- legal/calendar delays.

Treatment:

1. Fit mixture distributions or use empirical resampling.
2. Do not truncate tails unless explicitly justified.
3. Report quantiles, not only means.
4. Use quantile regression or quantile comparison for validation.
5. Test sensitivity of decisions to tail assumptions.

### Parameter uncertainty

Represent uncertain parameters as distributions, not fixed values.

Examples:

| Parameter | Uncertainty treatment |
|---|---|
| Missing-doc reduction from D1 | Use 30%, 50%, 70% scenarios |
| Objection probability | Beta distribution or bootstrap range |
| Public-notice extension | Mixture model with sensitivity bounds |
| Fire-review threshold | Latent probability conditioned on case attributes |
| Environmental sensitivity | District-level prior with wide credible interval |
| Inspector travel reduction from batching | Triangular or empirical range |
| Rework probability | Bootstrap from observed repeated activities |
| Calendar adherence | Scenario-based variation |

### Sensitivity analysis

Perform:

1. One-at-a-time sensitivity for major parameters.
2. Tornado analysis for median and p90 cycle time.
3. Scenario sensitivity for demand, objections, and resource absence.
4. Structural sensitivity:
   - with/without cross-case bundling,
   - with/without latent objection correlation,
   - with/without calendar interruptions.

The result should be a robustness assessment, not a claim of exact optimality.

## 6. Validation strategy

Validation should be iterative and multi-layered. The model should not be accepted merely because it reproduces average case duration.

### 6.1 Face validation

Present the model to process owners:

- permit clerks,
- planners,
- inspectors,
- legal officers,
- fire and environmental reviewers,
- portal administrators,
- policy analysts.

Check whether:

- control flow is plausible,
- queues correspond to known bottlenecks,
- calendar effects match operational experience,
- rework triggers are believable,
- intervention mechanisms are represented realistically.

Record structured feedback and update assumptions.

### 6.2 Event-log replay validation

Use observed historical arrivals and case attributes to drive the simulation.

Compare simulated and historical:

- activity sequences,
- variant frequencies,
- case durations,
- waiting times before key activities,
- rework frequencies,
- public-notice duration distribution,
- inspection scheduling delays,
- issue/reject rates.

PM4Py can support this by comparing:

- variants,
- directly-follows graphs,
- performance DFGs,
- conformance of simulated traces to the reference process tree.

### 6.3 Distributional validation

For each major activity and case type, compare simulated and empirical distributions.

Use:

- Q-Q plots,
- empirical CDF plots,
- Kolmogorov-Smirnov tests,
- Cramér-von Mises tests,
- quantile error metrics.

Important distributions:

- completeness check waiting,
- missing-document response time,
- planning review service/sojourn,
- fire-safety review delay,
- environmental review delay,
- public-notice duration,
- inspection scheduling waiting,
- site inspection duration including travel,
- legal check delay,
- total case duration.

Because objection events are missing, validate the **public-notice duration distribution**, not unobserved objection counts.

### 6.4 Resource-utilization validation

Compare simulated resource utilization with:

- HR calendar capacity,
- observed activity completion rates,
- known part-time restrictions,
- council meeting effects,
- Monday clerk portal support,
- fire reviewer Tuesday-Thursday constraint,
- environmental non-permit reservation,
- inspector travel and field availability.

Check for unrealistic outcomes:

- utilization above 100%,
- legal work during council weeks except urgent cases,
- fire review occurring on non-working days,
- inspectors completing field visits on Monday if prohibited,
- environmental reviewers exceeding effective permit capacity.

### 6.5 Bottleneck validation

The model should reproduce known bottleneck patterns:

- Monday completeness-check queue spikes,
- planning review queue dependence on district and case type,
- fire-safety queue due to Tuesday-Thursday capacity,
- environmental queue due to consultant reports and non-permit duties,
- inspection delay due to district travel and batching,
- legal delay due to council calendar,
- public-notice tail due to objections.

Validate using:

- queue length distributions,
- waiting time before activity,
- resource utilization,
- bottleneck ranking,
- case-stage aging.

### 6.6 Out-of-sample validation

Reserve part of the data for validation:

- hold out the last 3 months of the 18-month log; or
- hold out one district or one architect tier; or
- hold out one seasonal peak.

Calibrate on the remaining data and test whether the model predicts:

- median duration,
- p90 duration,
- SLA compliance,
- rework rate,
- backlog behavior.

### 6.7 Intervention sanity checks

Before trusting policy results, test simple sanity checks:

- adding capacity should reduce the relevant queue if that resource is binding;
- reducing missing documents should reduce completeness rework;
- skipping low-risk inspections should reduce inspector load;
- batching should reduce travel but may increase first-case waiting;
- legal pre-check should reduce complex tail only if legal capacity is sufficient;
- appointment slots should reduce Monday queue spikes.

If these checks fail, revisit model structure.

## 7. Decision criteria

Interventions should not be selected by a single metric. The decision framework should be multi-criteria and robustness-oriented.

### Primary decision metrics

| Metric | Definition | Why it matters |
|---|---|---|
| Median total cycle time | 50th percentile from submission to decision | Typical applicant experience |
| p90 total cycle time | 90th percentile | Tail performance |
| p95/p99 total cycle time | Extreme tail | Complex and contested cases |
| SLA compliance by case type | Share of cases finishing within target duration | Operational accountability |
| Backlog size | Open cases at month end | Capacity pressure |
| Resource utilization | Active permit work divided by available capacity | Efficiency and overload risk |
| Rework rate | Share of cases with one or more rework loops | Quality and waste |
| Missing-document loop rate | Share of cases requiring missing documents | Applicant readiness and portal quality |
| Inspection no-show/rework rate | Inspection failure indicator | Field-process quality |
| District fairness | Difference in p90 cycle time across districts | Equity |
| Architect-size fairness | Difference between large and small architects | Avoid preferential treatment |
| Applicant burden | Extra pre-submission or appointment waiting time | Political and service feasibility |
| Cost | Temporary staff, extra legal/planning capacity, tooling | Budget impact |
| Robustness | Stability of benefits under stress scenarios | Risk-aware decision-making |

### Suggested SLA targets

These should be calibrated with the municipality, but plausible starting targets are:

| Case type | Median target | p90 target |
|---|---:|---:|
| Simple renovation | 12 days | 25 days |
| New residential | 45 days | 95 days |
| Commercial | 60 days | 130 days |
| Complex variance | 120 days | 240 days |

These reflect the observed variant medians and p90s while allowing some improvement.

### Threshold logic

An intervention is attractive if, compared with baseline, it improves key outcomes without causing unacceptable side effects.

Example thresholds:

1. **Cycle-time improvement**
   - at least 10% reduction in median cycle time for target case type, or
   - at least 15% reduction in p90 cycle time for target case type.

2. **SLA compliance**
   - at least 5 percentage-point improvement in SLA compliance, or
   - no degradation in any case type while improving target case type.

3. **Utilization**
   - keep average utilization below 85% for constrained pools;
   - avoid sustained utilization above 90% unless explicitly approved;
   - temporary peak utilization above 90% acceptable only if short-lived.

4. **Fairness**
   - p90 cycle time gap across districts should not increase by more than 10%;
   - small architects should not experience materially worse outcomes than large architects;
   - bundling should not create systematic first-case penalties beyond an agreed threshold.

5. **Rework and quality**
   - rework rate should not increase by more than 5% relative;
   - inspection exemption D2 should include audit sampling and risk monitoring;
   - environmental triage D8 should include misclassification review.

6. **Applicant burden**
   - D1 and D7 should not shift excessive waiting to applicants before formal submission;
   - appointment delay should be transparent and bounded.

7. **Robustness**
   - intervention should retain positive net benefit under at least two stress scenarios;
   - if benefits disappear under mild demand surge, classify as fragile.

### Decision rule

Use a Pareto and scoring approach:

1. Remove interventions that violate hard constraints:
   - legal non-compliance,
   - unsafe risk exposure,
   - sustained resource overload,
   - unfair degradation to protected case classes.

2. Compare remaining interventions on:
   - tail improvement,
   - median improvement,
   - SLA compliance,
   - cost,
   - robustness,
   - fairness.

3. Prefer interventions that:
   - reduce bottlenecks,
   - improve tail performance,
   - maintain resource balance,
   - are robust under demand and objection shocks,
   - have manageable applicant burden.

The simulation should support decision-making, but it should not be used to claim exact optimality unless the model has been extensively calibrated, validated, and accepted by process owners.

def load_and_format_log() -> pd.DataFrame:
    """
    Load the illustrative CSV with pandas and format it according to
    PM4Py conventions.
    """
    df = pd.read_csv(
        io.StringIO(LOG_CSV),
        parse_dates=["time:timestamp"],
    )

    df = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )

    # Optional normalization of case attributes.
    bool_cols = [
        "requires_fire",
        "requires_environment",
        "requires_public_notice",
    ]
    for col in bool_cols:
        if col in df.columns:
            df[col] = df[col].map({"yes": True, "no": False})

    return df


def convert_to_event_log(df: pd.DataFrame):
    """
    Convert formatted dataframe to a PM4Py event log.
    """
    return pm4py.convert_to_event_log(df)


def safe_parse_process_tree(tree_string: str):
    """
    Attempt to parse the simplified process tree.

    If parsing fails, the fallback is to use a manually constructed
    simulation routing model. The simplified string may not capture all
    loop, parallel, and synchronization semantics required by the twin.
    """
    try:
        tree = pm4py.parse_process_tree(tree_string)
        return tree
    except Exception as exc:
        print("Process tree parsing failed or produced limited semantics.")
        print(f"Error: {exc}")
        print("Fallback: use extended simulation routing and state machine.")
        return None


# ---------------------------------------------------------------------
# 4. Time decomposition: waiting vs service
# ---------------------------------------------------------------------

def add_waiting_and_service_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Add elapsed-time columns.

    Important:
    - If only completion timestamps exist, elapsed_since_prev_days is a
      sojourn time, not pure waiting time.
    - If start_timestamp exists, service and waiting can be separated.
    """
    df = df.sort_values(
        by=["case:concept:name", "time:timestamp", "concept:name"]
    ).reset_index(drop=True)

    df["prev_completion"] = (
        df.groupby("case:concept:name")["time:timestamp"].shift(1)
    )

    df["elapsed_since_prev_days"] = (
        df["time:timestamp"] - df["prev_completion"]
    ).dt.total_seconds() / 86400.0

    if "start_timestamp" in df.columns:
        df["start_timestamp"] = pd.to_datetime(df["start_timestamp"])

        df["service_time_days"] = (
            df["time:timestamp"] - df["start_timestamp"]
        ).dt.total_seconds() / 86400.0

        df["waiting_before_activity_days"] = (
            df["start_timestamp"] - df["prev_completion"]
        ).dt.total_seconds() / 86400.0

    else:
        # No reliable start timestamps: do not claim this is pure waiting.
        df["service_time_days"] = np.nan
        df["waiting_before_activity_days"] = df["elapsed_since_prev_days"]
        df["time_decomposition_note"] = (
            "Completion-to-completion sojourn; service/waiting split requires "
            "assumptions or start timestamps."
        )

    return df

# 5. Basic PM4Py analytics
# ---------------------------------------------------------------------

def compute_pm4py_analytics(df: pd.DataFrame) -> Dict[str, Any]:
    """
    Compute variants, DFG, performance DFG, and arrival statistics.
    """
    log = convert_to_event_log(df)

    variants = pm4py.get_variants(log)
    dfg = pm4py.get_directly_follows_graph(log)

    try:
        performance_dfg = pm4py.get_performance_dfg(log)
    except Exception as exc:
        performance_dfg = None
        print(f"Performance DFG not available: {exc}")

    arrival_stats = compute_arrival_statistics(df)

    return {
        "variants": variants,
        "dfg": dfg,
        "performance_dfg": performance_dfg,
        "arrival_stats": arrival_stats,
    }


def compute_arrival_statistics(df: pd.DataFrame) -> Dict[str, Any]:
    """
    Compute simple arrival statistics from Submit application events.
    """
    submissions = df[df["concept:name"] == "Submit application"].copy()

    if submissions.empty:
        return {
            "mean_cases_per_day": np.nan,
            "median_cases_per_day": np.nan,
            "total_cases": 0,
        }

    submissions["date"] = submissions["time:timestamp"].dt.date
    daily_counts = submissions.groupby("date").size()

    submissions["weekday"] = submissions["time:timestamp"].dt.day_name()
    weekday_counts = submissions.groupby("weekday").size()

    return {
        "total_cases": int(submissions["case:concept:name"].nunique()),
        "mean_cases_per_day": float(daily_counts.mean()),
        "median_cases_per_day": float(daily_counts.median()),
        "mean_cases_per_weekday": weekday_counts.to_dict(),
    }

class ArrivalGenerator:
    """
    Non-stationary arrival generator.

    Full implementation should combine:
    - monthly seasonality,
    - weekday effects,
    - hour-of-day effects,
    - architect burst process,
    - appointment-slot shaping for D7.
    """

    def __init__(
        self,
        base_daily_rate: float,
        month_multipliers: Dict[int, float],
        weekday_multipliers: Dict[str, float],
        architect_burst_model: Optional[Any] = None,
    ):
        self.base_daily_rate = base_daily_rate
        self.month_multipliers = month_multipliers
        self.weekday_multipliers = weekday_multipliers
        self.architect_burst_model = architect_burst_model

    def expected_rate(self, ts: datetime) -> float:
        month_mult = self.month_multipliers.get(ts.month, 1.0)
        weekday_mult = self.weekday_multipliers.get(ts.strftime("%A"), 1.0)
        return self.base_daily_rate * month_mult * weekday_mult

    def sample_arrivals(
        self,
        start: datetime,
        horizon_days: int,
        rng: np.random.Generator,
        intervention: InterventionConfig,
    ) -> List[Dict[str, Any]]:
        """
        Placeholder arrival sampler.

        Full implementation should generate case attributes and arrival
        timestamps, including correlated architect batches.
        """
        arrivals = []
        for day in range(horizon_days):
            ts = start + timedelta(days=day)
            lam = self.expected_rate(ts)

            if intervention.architect_appointment_slots:
                # Placeholder: shift part of Monday demand to later weekdays.
                if ts.strftime("%A") == "Monday":
                    lam *= max(0.0, 1.0 - intervention.monday_shift_fraction)

            count = rng.poisson(lam)
            for i in range(count):
                arrivals.append(
                    {
                        "arrival_time": ts,
                        "case_type": "TO_BE_SAMPLED",
                        "district": "TO_BE_SAMPLED",
                        "architect_id": "TO_BE_SAMPLED",
                        "application_value": np.nan,
                    }
                )
        return arrivals


class RoutingPolicy:
    """
    Routing and branching policy.

    Full implementation should use fitted probabilities conditioned on
    case_type, district, architect tier, application_value, and intervention.
    """

    def __init__(self, intervention: InterventionConfig):
        self.intervention = intervention

    def requires_missing_documents(self, case: Case, rng: np.random.Generator) -> bool:
        base_prob = 0.30  # placeholder, estimate from log
        if self.intervention.pre_submission_checker:
            base_prob *= max(0.0, 1.0 - self.intervention.missing_doc_reduction)
        return rng.random() < base_prob

    def requires_site_inspection(self, case: Case) -> bool:
        if (
            self.intervention.simple_no_inspection_rule
            and case.case_type == "Simple renovation"
            and case.application_value < self.intervention.no_inspection_value_threshold
            and (not case.prior_violations or not self.intervention.require_no_prior_violations)
        ):
            return False
        return True

    def can_batch_inspection(self, case: Case) -> bool:
        return self.intervention.district_batched_inspection

    def requires_legal_precheck_parallel(self, case: Case) -> bool:
        return (
            self.intervention.legal_precheck_parallel
            and case.case_type in self.intervention.legal_precheck_case_types
        )


class InspectionBatcher:
    """
    Cross-case dependency handler for inspection bundling.

    Full implementation should maintain open inspection jobs by district,
    architect, and readiness time, then create bundles subject to max size,
    max waiting, and travel-time reduction.
    """

    def __init__(self, intervention: InterventionConfig):
        self.intervention = intervention
        self.open_jobs: List[Case] = []

    def add_job(self, case: Case) -> None:
        self.open_jobs.append(case)

    def form_bundles(self, current_time: datetime) -> List[List[Case]]:
        if not self.intervention.district_batched_inspection:
            bundles = [[case] for case in self.open_jobs]
            self.open_jobs = []
            return bundles

        # Placeholder: simple district grouping.
        by_district: Dict[str, List[Case]] = {}
        for case in self.open_jobs:
            by_district.setdefault(case.district, []).append(case)

        bundles: List[List[Case]] = []
        for district, cases in by_district.items():
            for i in range(0, len(cases), self.intervention.max_bundle_size):
                bundles.append(cases[i : i + self.intervention.max_bundle_size])

        self.open_jobs = []
        return bundles
