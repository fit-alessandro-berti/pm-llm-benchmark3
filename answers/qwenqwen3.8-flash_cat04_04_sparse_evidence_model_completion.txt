```
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition
from pm4py.objects.process_tree.obj import Operator

def make_balanced_powl():
    def T(label): return Transition(label=label)
    def seq(*children): return OperatorPOWL(Operator.SEQUENCE, list(children))
    def xor(*children): return OperatorPOWL(Operator.XOR, list(children))
    def pos(nodes, edges):
        p = StrictPartialOrder()
        p.nodes = set(nodes)
        for a,b in edges:
            p.order.add_edge(a,b)
        return p
    R = T("Register Order")
    A = T("Approve Configuration")
    RP = T("Release Production")
    AR = T("Archive Case")
    c1,e1 = T("Credit Check"), T("Engineering Review")
    ce_only = pos([c1,e1], [])
    c2,e2,s2 = T("Credit Check"), T("Engineering Review"), T("Supplier Confirmation")
    s_after_c = pos([c2,e2,s2], [(c2,s2)])
    c3,e3,x3 = T("Credit Check"), T("Engineering Review"), T("Expedite Review")
    x_only = pos([c3,e3,x3], [(c3,x3), (e3,x3)])
    c4,e4,s4,x4 = T("Credit Check"), T("Engineering Review"), T("Supplier Confirmation"), T("Expedite Review")
    s_c_x = pos([c4,e4,s4,x4], [(c4,s4), (c4,x4), (e4,x4)])
    block = xor(ce_only, s_after_c, x_only, s_c_x)
    return seq(R, block, A, RP, AR)
```

Why bidirectional DFG edges do not prove concurrency: the DFG edges `C -> E` and `E -> C` only show that `C` sometimes completes before `E` and sometimes `E` completes before `C`. This pattern can arise from two sequential processes with different durations, from two concurrent processes with different finish times, or from arbitrary ingestion ordering when timestamps tie. Without start timestamps, lifecycle transitions, resource calendars, or overlap indicators, the log cannot distinguish “C finished first” from “C started first” or “they overlapped.” Therefore, bidirectional edges support a disjunction of completion orders, not proof of concurrency.

# 2. Shared Assumptions

All three models share these assumptions:

- **Event-completion semantics.** Each trace is a sequence of completion events. The order in the log is not necessarily the order of activity starts. Same-timestamp ordering is ingestion-index-based and therefore weak evidence.
- **Activity alphabet.** The models use exactly the eight supplied activity labels. No additional lifecycle labels, such as `start` or `complete`, are available.
- **No loops.** Because no repeated activities appear in the observed variants and no rule permits rework, all candidates forbid repeated occurrences of the same activity within a trace.
- **Start and end.** `Register Order` is the first activity and `Archive Case` is the last activity in every admitted trace.
- **Approval chain.** `Approve Configuration -> Release Production -> Archive Case` is enforced in all models.
- **Missing Supplier Confirmation.** Absence of `Supplier Confirmation` is represented as a control-flow alternative: either a legitimate stocked-order skip or a missing event due to integration failure. The models cannot distinguish these two causes because the external/stocked attribute and event-completeness flags are absent.
- **Optionality representation.** Optional activities are represented either by XOR branches containing the activity or by branches omitting it. In POWL, this is done by alternative partial-order branches; in ProcessTree, by XOR branches.
- **Concurrency representation.** Where concurrency is plausible, it is represented as partial order/incomparability, not as proof from completion order. The resulting language is still a set of completion-order traces.
- **Expedite Review.** `Expedite Review` is optional, at most once, after both `Credit Check` and `Engineering Review`, and before `Approve Configuration`. Its order relative to `Supplier Confirmation` is left flexible because S6 and the two observed `X` variants support both orders.

# 3. Conservative Candidate

**Inductive-bias statement.** The conservative model assumes that the process language is exactly the set of observed completion variants, with no generalization beyond those variants. It treats every unobserved order as unsupported, even if it is consistent with medium-confidence domain rules. This is deliberately high-precision and low-recall: it avoids admitting speculative behavior, but it is brittle and likely underfits future legitimate cases. The model uses an XOR enumeration of observed prefixes followed by the common approval suffix. Duplicate activity labels appear across different XOR branches; this is acceptable for language representation but makes the model large, harder to maintain, and potentially confusing for metrics that rely on unique labels. Scalability is poor if the number of observed variants grows.

```text
P_obs = {
```

Then:

```text
L_conservative = { R p A RP AC | p in P_obs }
```

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model generalizes only where the evidence and domain rules jointly support it. It treats `Credit Check` and `Engineering Review` as partially ordered rather than strictly sequential because D7 and S2 make concurrency plausible, while the observed completion order shows both `C` before `E` and `E` before `C`. It does not claim true concurrency; it represents uncertainty as incomparability in a partial order. For `Supplier Confirmation`, it favors the observed pattern that `S` completes after `C` completes, because all observed `S` traces have `C` before `S`, and S1 supports `C` as a prerequisite. It does not require `E` before `S`, because V5 shows `S` before `E` completion. For `Expedite Review`, it enforces both checks before `X`, leaves `X` and `S` incomparable, and represents optionality through alternative branches. Missing `S` is modeled as a no-`S` branch, but this abstraction conflates stocked skips and integration missingness.

**How the model chooses between sequence, concurrency, and partial order.**

- **`Credit Check` vs `Engineering Review`:** Use partial order/incomparability, not strict sequence. S1 says `C` must finish before `E` starts, but the log only records completions and V2/V4/V7 show `E` completing before `C`. S2 says they may run in parallel. D7 says completion order cannot prove concurrency. Therefore, the balanced model allows either completion order without asserting actual concurrency.
- **`Supplier Confirmation`:** Use a partial-order edge `C -> S`, but no edge `E -> S`. This allows `C,E,S`, `E,C,S`, and `C,S,E`. It excludes `E,S,C` because no observed trace has `S` completing before `C`, and S1 makes `C` a plausible information source. This is more conservative than D5’s full “after either” reading.
- **`Expedite Review`:** Use edges `C -> X` and `E -> X`, but no edge between `X` and `S`. This satisfies D6/S6 and admits both observed `X` orders: `S` before `X` and `X` before `S`.
- **Optionality:** Use XOR branches for no-`S`/with-`S` and no-`X`/with-`X`. This represents optional behavior structurally, but it does not solve the missing-data problem.

**Compact formal expression.** Let `lin(P)` be the set of linearizations of a strict partial order `P`.

```text
B_bal = XOR(
  lin({C,E}, no edges),
  lin({C,E,S}, C -> S),
  lin({C,E,X}, C -> X, E -> X),
  lin({C,E,S,X}, C -> S, C -> X, E -> X)
)

L_balanced = { R b A RP AC | b is a linearization of some branch in B_bal }
```

**Self-contained PM4Py POWL code.**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
)
from pm4py.objects.process_tree.obj import Operator

def make_balanced_powl():
    def T(label):
        return Transition(label=label)

    def seq(*children):
        return OperatorPOWL(Operator.SEQUENCE, list(children))

    def xor(*children):
        return OperatorPOWL(Operator.XOR, list(children))

    def pos(nodes, edges):
        try:
            p = StrictPartialOrder(nodes=set(nodes))
        except Exception:
            p = StrictPartialOrder()
            p.nodes = set(nodes)
        for source, target in edges:
            p.order.add_edge(source, target)
        return p

    R = T("Register Order")
    A = T("Approve Configuration")
    RP = T("Release Production")
    AR = T("Archive Case")

    # Branch 1: both checks only; no Supplier Confirmation; no Expedite Review.
    c1, e1 = T("Credit Check"), T("Engineering Review")
    ce_only = pos([c1, e1], [])

    # Branch 2: Supplier Confirmation enabled by Credit Check.
    # Engineering Review is not required before Supplier Confirmation completion.
    c2, e2, s2 = T("Credit Check"), T("Engineering Review"), T("Supplier Confirmation")
    s_after_c = pos([c2, e2, s2], [(c2, s2)])

    # Branch 3: Expedite Review only; requires both checks.
    c3, e3, x3 = T("Credit Check"), T("Engineering Review"), T("Expedite Review")
    x_only = pos([c3, e3, x3], [(c3, x3), (e3, x3)])

    # Branch 4: Supplier Confirmation and Expedite Review both present.
    # S is enabled by C; X is enabled by both C and E; X and S are incomparable.
    c4, e4, s4, x4 = (
        T("Credit Check"),
        T("Engineering Review"),
        T("Supplier Confirmation"),
        T("Expedite Review"),
    )
    s_c_x = pos([c4, e4, s4, x4], [(c4, s4), (c4, x4), (e4, x4)])

    block = xor(ce_only, s_after_c, x_only, s_c_x)
    return seq(R, block, A, RP, AR)

model_balanced = make_balanced_powl()
```

**Behavior deliberately excluded.**

- `R,E,S,C,A,RP,AC`: `S` completes before `C`, which violates the balanced choice `C -> S`.
- `R,E,S,C,X,A,RP,AC`: same earliest violation, plus this is only admitted by the permissive symmetric `E -> S` hypothesis.
- `R,C,X,E,A,RP,AC`: `X` occurs before `E` completion, violating D6.
- `R,S,C,E,A,RP,AC`: `S` occurs before both checks, violating D5 and the balanced model.
- `R,C,E,A,S,RP,AC`: `S` occurs after `A`, violating D4.
- Any repeated activity, loop, missing start/end, or `RP` before `A`.

**Known underfitting risks.**

- It may exclude legitimate `E -> S` behavior if D5 is fully correct and Engineering can independently trigger supplier confirmation.
- It may underrepresent true concurrency because only completion-order linearizations are visible.
- It cannot distinguish stocked orders from missing `S` events.
- It cannot condition `S` on external/stocked attributes.
- It may be too restrictive if future data shows `S` enabled by `E` without `C`.

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model admits every completion-order linearization that is consistent with the broad domain rules D3, D4, D5, and D6, even if unobserved. It treats `Credit Check` and `Engineering Review` as unordered with respect to each other, treats `Supplier Confirmation` as optional and enabled by either check, treats `Expedite Review` as optional and enabled by both checks, and leaves `Supplier Confirmation` and `Expedite Review` incomparable. This maximizes recall and robustness to missing `S`, but it has the highest precision risk because it admits several plausible but unobserved orders. It is intended as an exploration or sensitivity model, not as a compliance baseline.

**Boundary between reasonable generalization and forbidden behavior.**

- **Admitted:** any completion order of `C`, `E`, optional `S`, optional `X` such that:
  - `C` and `E` are both before `A`;
  - if `S` is present, it is after `C` or after `E`;
  - if `S` is present, it is before `A`;
  - if `X` is present, it is after both `C` and `E`;
  - if `X` is present, it is before `A`;
  - `X` and `S` may appear in either order.
- **Forbidden:** `S` before both checks; `X` before either check; `A` before `C` or `E`; `S` after `A`; `X` after `A`; `RP` before `A`; missing `R` or `AC`; repeated activities; loops; additional activities.

**Compact formal expression.** Let `P_perm` be the set of sequences over optional `S` and `X` with mandatory `C` and `E` satisfying:

```text
C before A, E before A,
S optional, if present: (C before S or E before S) and S before A,
X optional, if present: C before X and E before X and X before A,
S and X may be in either order.
```

Then:

```text
L_permissive = { R p A RP AC | p in P_perm }
```

The 14 admitted prefixes are:

```text
C E
E C
C E S
E C S
C S E
E S C
C E X
E C X
C E X S
E C X S
C E S X
E C S X
C S E X
E S C X
```

**Behavior deliberately excluded.**

- `R,S,C,E,A,RP,AC`: `S` before both checks.
- `R,S,E,C,A,RP,AC`: `S` before both checks.
- `R,C,X,E,A,RP,AC`: `X` before `E`.
- `R,E,X,C,A,RP,AC`: `X` before `C`.
- `R,C,E,A,S,RP,AC`: `S` after approval.
- `R,C,E,S,A,RP,AC` with an extra `S`, `X`, loop, or missing `RP`/`AC`.

**Known underfitting risks.**

- It underfits conditional rules: it cannot represent that `S` is mandatory for external components and optional for stocked components because the attribute is missing.
- It underfits data-quality distinctions: missing `S` events are treated as legitimate skips.
- It may underfit a stricter start-time process if S1 is true and `C` must start before `E`; completion-order permissiveness does not capture that.
- It may admit behavior that compliance would reject if future evidence shows `S` cannot be enabled by `E` alone.

# 7. Comparative Model Matrix

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|
| Expected fitness on the 30 observed cases | Very high by construction; should fit all observed variants exactly. | Very high by construction; should fit all observed variants while generalizing modestly. | Very high by construction; includes all observed variants plus many plausible unobserved orders. |
| Expected precision risk | Low precision risk on observed sample, but high overfitting risk: it may reject legitimate future behavior. | Moderate precision risk: admits some unobserved but plausible behavior; still excludes symmetric `E -> S` cases. | High precision risk: admits many unobserved orders, including `E,S,C` and `E,S,C,X`. |
| Generalization potential | Low. | Medium-high. | High. |
| Structural simplicity | Moderate to complex: XOR enumeration of seven prefixes; duplicate labels across branches. | Moderate: four POWL branches with partial orders; easier to reason about precedence. | Complex: XOR enumeration of fourteen prefixes; duplicate labels across branches. |
| Explainability | High for auditors: “only observed variants are allowed.” | High: explicit partial-order constraints and optionality branches. | Medium: broad and plausible, but harder to defend as a compliance baseline. |
| Robustness to missing Supplier Confirmation events | Moderate: admits only observed no-`S` patterns; may falsely flag future missing-`S` variants. | High: no-`S` branches are built in, but missingness is conflated with stocked skip. | High: no-`S` branches are broad, but missingness is also conflated with legitimate skip. |
| Handling of unseen interleavings | None: only exact observed completion orders. | Some: allows `C/E` order uncertainty, `X/S` order uncertainty, and `S` before `E` completion. | Many: allows both `C -> S` and `E -> S` enablement and all compatible `X/S` orders. |
| Suitability for compliance versus exploration | Best for compliance-style lower-bound checks. | Best immediate operational model. | Best for sensitivity analysis and hypothesis exploration. |

```python
                "lifecycle:transition": "complete",

        log.append(trace)

def bounded_playout(name, model, net, im, fm, max_traces=25):
    """
    Sampled playout is not proof of language inclusion or exclusion.
    It is only a smoke test and a way to inspect representative traces.
    """
    generator = None

    try:
        generator = pm4py.play_out(model, max_traces=max_traces)
    except TypeError:
        try:
            generator = pm4py.play_out(net, im, fm, max_traces=max_traces)
        except TypeError:
            try:
                generator = pm4py.play_out(net, im, fm)
            except Exception as e:
                print(f"{name}: play_out failed: {e}")
                return []
    except Exception as e:
        print(f"{name}: play_out failed: {e}")
        return []

    traces = []
    try:
        for i, tr in enumerate(generator):
            if i >= max_traces:
                break
            traces.append(tr)
    except Exception as e:
        print(f"{name}: playout iteration failed: {e}")

    print(f"{name}: sampled playout returned {len(traces)} traces")
    return traces

def make_single_trace_log(trace):

def accepts_trace(net, im, fm, trace):
    """
    Best-effort acceptance check.

    Some PM4Py versions provide replay_trace; others do not. If replay is
    unavailable, alignment fitness is used as a proxy: a conforming trace
    should have fitness 1.0 for these acyclic models. This is not a formal
    language-membership proof.
    """
    try:
        result = pm4py.replay_trace(trace, net, im, fm)
        if isinstance(result, bool):
            return result
        if hasattr(result, "is_conforming"):
            return bool(result.is_conforming())
        if hasattr(result, "fitness"):
            return float(result.fitness) >= 0.999
    except Exception:
        pass

    try:
        fitness = first_float(pm4py.fitness_alignments(make_single_trace_log(trace), net, im, fm))
        return fitness >= 0.999
    except Exception as e:
        print(f"accepts_trace failed: {e}")
        return None

for name, (net, im, fm) in nets.items():
    pos_results = [accepts_trace(net, im, fm, trace) for trace in positive_traces]
    neg_results = [accepts_trace(net, im, fm, trace) for trace in negative_traces]

    print(f"{name}: positive trace acceptance = {pos_results}")
    print(f"{name}: negative trace acceptance = {neg_results}")
```

**Limitations of this validation.**

- If a model language is infinite, no finite sampled playout can prove language inclusion or exclusion.
- Alignment-based fitness is a proxy for trace acceptance; it may not be a formal membership test for all Petri-net languages.
- PM4Py API names and signatures can vary by version. The fallbacks improve portability but do not guarantee identical semantics across versions.
- Duplicate labels across ProcessTree XOR branches are expected here because different branches represent different occurrences of the same activity. This can make some metrics less interpretable, although the language itself remains well-defined.

# 9. Recommendation and Data-Collection Plan

**Recommendation for immediate use:** use `model_balanced`.

It is the best compromise among the three candidates:

- It fits all observed variants by construction.
- It encodes high-confidence rules D1, D2, D3, and D6.
- It avoids overclaiming concurrency from completion order.
- It allows `S` to occur before `E` completion, consistent with V5.
- It allows `X` before or after `S`, consistent with V6/V7 and S6.
- It represents optional `S` and optional `X` without pretending to know whether missing `S` is a stocked skip or data loss.

**Recommendation for sensitivity analysis:** use `model_permissive`.

The permissive model is useful as an upper-bound hypothesis. If future data contains traces admitted by `model_permissive` but rejected by `model_balanced`, especially traces like `R,E,S,C,A,RP,AC` or `R,E,S,C,X,A,RP,AC`, that would support the symmetric D5 interpretation that `Supplier Confirmation` can be enabled by `Engineering Review` alone. If such traces never appear, the balanced preference for `C -> S` becomes more credible.

`model_conservative` should be retained as a compliance lower bound, but it is not recommended as the primary model because it overfits the observed sample.

**Concrete data-collection plan.**

1. **Collect lifecycle timestamps.**
   - Record both start and completion timestamps for every activity.
   - Use a lifecycle attribute such as `lifecycle:transition` with values `start` and `complete`.
   - This is the single most important addition for distinguishing sequence, concurrency, and overlap.

2. **Collect order-attribute metadata.**
   - Export a binary or categorical attribute: `order:component_type` with values `external` and `stocked`.
   - Add `order:supplier_confirmation_required` as a derived or directly captured flag.
   - This allows testing S3 versus S4 instead of treating all no-`S` traces as ambiguous.

3. **Collect supplier integration quality flags.**
   - Add `supplier:event_missing_flag` or an integration error log.
   - Record whether a supplier confirmation was expected but not received.
   - This separates true process optionality from data loss.

4. **Collect resource and queue information.**
   - Record resources performing `Credit Check` and `Engineering Review`.
   - Record queue start times if available.
   - This helps determine whether checks are parallel, sequential, or merely finish in different orders.

5. **Collect expedite context.**
   - Add `expedite:reason`, `expedite:requested_by`, and `expedite:required_supplier_confirmation`.
   - This helps test whether `X` is associated with external components or supplier pressure.

**Future traces that would be maximally informative.**

- **To distinguish `C` before `E` versus concurrency:**
  - `R,C,E,A,RP,AC` with `C.start < E.start < C.complete < E.complete` would support overlap.
  - `R,E,C,A,RP,AC` with `C.start < E.start < E.complete < C.complete` would strongly contradict S1’s start-time claim.
  - If start timestamps consistently show `C.complete <= E.start`, S1 becomes credible and the balanced partial order should be replaced by a sequence model.

- **To test whether `S` can be enabled by `E` alone:**
  - `R,E,S,C,A,RP,AC` with `E.complete <= S.start` and `S.start < C.complete` would support D5’s full symmetric interpretation and favor `model_permissive`.
  - If such traces are absent over a large sample, the balanced `C -> S` preference is strengthened.

- **To test `X` prerequisites:**
  - `R,C,X,E,A,RP,AC` with `X.start < E.complete` would violate D6 and indicate either a process exception or a data-quality issue.
  - `R,E,C,X,S,A,RP,AC` and `R,C,E,S,X,A,RP,AC` with start timestamps would help confirm whether `X` truly waits for both checks or merely appears after them in completion order.

- **To separate stocked skips from missing `S`:**
  - `order:component_type = stocked` with no `S` event supports true optionality.
  - `order:component_type = external` with no `S` event and `supplier:event_missing_flag = true` supports integration missingness.
  - `order:component_type = external` with no `S` event and no missing flag would be a compliance exception.

# 10. Uncertainty Statement

Calibrated confidence assessments for major modeling decisions:

| Modeling decision | Confidence | Rationale |
|---|---:|---|
| `Register Order` is first and `Archive Case` is last | 95–99% | D1 and all observed variants. |
| `Approve Configuration -> Release Production -> Archive Case` | 95–99% | D2 and all observed variants. |
| Both `Credit Check` and `Engineering Review` complete before `Approve Configuration` | 85–95% | D3 and all observed variants; no counterexample. |
| If `Supplier Confirmation` is present, it completes before `Approve Configuration` | 80–90% | D4 and all observed `S` traces; low risk of hidden late `S`. |
| `Supplier Confirmation` is sometimes absent legitimately | 55–70% | S4 and no-`S` variants support it, but S5 says missing events are possible. |
| Absence of `Supplier Confirmation` can be fully explained by process optionality | 30–50% | Cannot distinguish stocked skips from missing events without the external/stocked attribute. |
| `Supplier Confirmation` is enabled by `Credit Check` completion | 60–75% | All observed `S` traces have `C` before `S`; S1 supports this. |
| `Supplier Confirmation` is enabled by `Engineering Review` alone | 35–55% | D5 says possible, but no observed trace has `S` before `C`. |
| `Credit Check` and `Engineering Review` are concurrent or overlapping | 40–60% | S2 supports it, but completion-order data cannot prove it. |
| `Credit Check` and `Engineering Review` are strictly sequential in actual execution | 25–45% | S1 supports a start-time sequence, but observed completion order contradicts a fixed completion sequence. |
| `Expedite Review` requires both `Credit Check` and `Engineering Review` | 70–85% | D6 and S6; only two observed `X` traces, but both are consistent. |
| `Expedite Review` may occur before or after `Supplier Confirmation` | 65–80% | S6 and V6/V7 show both orders, but counts are tiny. |
| The balanced model is the best immediate-use model | 60–70% | It fits the data and encodes plausible constraints, but it may be too restrictive on `E -> S`. |
| The conservative model is the best long-term process model | 10–25% | It is almost certainly overfit to the 30 traces. |
| The permissive model is the best compliance baseline | 10–25% | It is useful for exploration but too broad for compliance. |

**Plausible alternative interpretation that would materially change the recommendation.**

If future start-time data confirms S1—`Credit Check` must finish before `Engineering Review` starts—then the balanced and permissive models are too permissive in allowing `E` to complete before `C`. The recommended model would shift toward a sequence-based model with `C -> E`, possibly with `S` enabled after `C` and `X` after both. Conversely, if the external/stocked attribute shows that `Supplier Confirmation` is mandatory for all external orders and many no-`S` traces are actually missing events, then the no-`S` branches should not be treated as legitimate process behavior. In that case, the immediate-use model should be split into two models: a cleaned process model for complete traces and a data-quality model for missing supplier events, and the balanced model’s silent/no-`S` abstraction would become unsafe for compliance.
