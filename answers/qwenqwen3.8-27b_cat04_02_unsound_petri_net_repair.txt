# 1. Executive Verdict

The net is a workflow net: it has unique source and sink, and every node lies on some source-to-sink path. It should not be expected to be sound. The principal defect is that `t_join_waived` has only `p_waived` as input, so the waiver branch can reach `p_decision` without consuming the analysis branch. Consequently, `t_authorize` can fire before `t_analyze`, and after authorization a token remains in `p_analysis` or `p_analysis_done`. That token cannot be consumed on the waiver path because `t_join_normal` requires `p_review_done`, which is never produced when waiver is selected. Business consequence: cases can be authorized without mandatory analysis, and the net can reach a sink token without the exact final marking, potentially deadlocking with leftover tokens.

# 4. Minimal-Repair Alternatives

Edit-cost model:

- Added or removed arc: cost 1.
- Added or removed place: cost 2.
- Added or removed transition: cost 2.
- Label change: cost 0.
- Initial/final marking change: cost 3, not used below.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| R1: Add analysis input to waiver join | Add arc `p_analysis_done -> t_join_waived`. No removals. | 1 | Yes. Analysis remains mandatory. Review remains either standard or waiver. Authorization occurs only after analysis and the selected review outcome. | `t_join_waived` becomes a true AND join requiring both `p_waived` and `p_analysis_done`. `t_authorize` cannot fire before `t_analyze` on the waiver path. | `p_analysis_done` now feeds two alternative joins. This is safe under the current exclusive review split, but future changes allowing both review outcomes would need careful handling. |
| R2: Route waiver into the normal join | Remove arc `t_join_waived -> p_decision`; add arc `t_join_waived -> p_review_done`. | 2 | Yes. Analysis remains mandatory. Waiver is still recorded by `t_waive_review`. Authorization occurs after analysis and review outcome. | Waiver no longer has its own final join. `t_join_waived` becomes a one-input forwarder from `p_waived` to `p_review_done`, then `t_join_normal` synchronizes with `p_analysis_done`. Waiver traces include both `t_join_waived` and `t_join_normal`. | `t_join_waived` becomes a silent pass-through and may be misunderstood or removed. After `t_join_waived`, waiver and standard review are structurally indistinguishable in `p_review_done`. |
| R3: Policy change: remove mandatory analysis | Remove arcs `t_split -> p_analysis`, `p_analysis -> t_analyze`, `t_analyze -> p_analysis_done`, `p_analysis_done -> t_join_normal`; remove places `p_analysis`, `p_analysis_done`; remove transition `t_analyze`. | 10 | No. This changes the business policy: analysis is no longer mandatory for any case. | Cases can complete after standard review or waiver without analysis. `t_join_normal` becomes a single-input transition from `p_review_done`. | Violates the stated business rule if analysis is mandatory. Useful only if the business explicitly accepts global analysis optionality. |

Minimality justification:

- R1 is the cheapest policy-preserving repair under the stated cost model. A zero-edit net is unsound. A one-edit repair must either add or remove a single arc. Removing an arc cannot both preserve waiver completion and consume the analysis token: removing `t_join_waived -> p_decision` breaks waiver completion, and removing analysis arcs breaks mandatory analysis or leaves tokens. Adding an arc must make the waiver path wait for completed analysis or give `p_analysis_done` a consumer on the waiver path. The only place representing completed analysis is `p_analysis_done`, so adding `p_analysis_done -> t_join_waived` is the minimal enabling edit.
- R2 is minimal for the “single final join” family. A place cannot directly transfer a token to another place in an ordinary Petri net, so the existing transition `t_join_waived` must change its output. That requires removing one arc and adding one arc, cost 2.
- R3 is minimal for the global policy change of deleting the analysis branch, but it is not globally minimal because it changes the business policy.
- No tie occurs under the stated add/remove cost model. If an arc replacement were counted as one edit, R1 and R2 could tie at cost 1, but they remain behaviorally distinct: R1 preserves two alternative final joins, while R2 collapses the final decision into `t_join_normal`.

import pm4py
from pm4py.objects.petri_net.obj import Marking


def nonzero_marking(marking):
    return {
        getattr(p, "name", str(p)): int(v)
        for p, v in marking.items()
        if v > 0
    }


def copy_marking(marking):
    m = Marking()
    for p, v in marking.items():
        if v:
            m[p] = v
    return m


def enabled_names(net, marking):
    names = []
    for t in pm4py.get_enabled_transitions(net, marking):
        names.append(getattr(t, "name", str(t)))
    return sorted(names)


def fire_named_transition(net, marking, transition_name):
    enabled = enabled_names(net, marking)
    if transition_name not in enabled:
        raise ValueError(
            f"{transition_name} is not enabled in {nonzero_marking(marking)}"
        )

    t = None
    for tr in net.transitions:
        if getattr(tr, "name", None) == transition_name:
            t = tr
            break

    if t is None:
        raise ValueError(f"Transition {transition_name} not found in net")

    new_marking = copy_marking(marking)

    for arc in net.arcs:
        if arc.to == t:
            p = arc.fr
            if new_marking.get(p, 0) < 1:
                raise RuntimeError("Firing check failed: input token missing.")
            new_marking[p] = new_marking.get(p, 0) - 1

    for arc in net.arcs:
        if arc.fr == t:
            p = arc.to
            new_marking[p] = new_marking.get(p, 0) + 1

    for p in list(new_marking.keys()):
        if new_marking[p] <= 0:
            del new_marking[p]

    return new_marking


def run_sequence(net, initial_marking, sequence, label):
    m = copy_marking(initial_marking)
    print(f"--- {label} ---")
    print("initial:", nonzero_marking(m), "enabled:", enabled_names(net, m))

    for tname in sequence:
        m = fire_named_transition(net, m, tname)
        print(
            f"fired {tname}: "
            f"marking={nonzero_marking(m)} "
            f"enabled={enabled_names(net, m)}"
        )

    return m


for label, n, i, f in [

]:
    print(label, "check_is_workflow_net:", pm4py.check_is_workflow_net(n))

    print(label, "initial enabled transitions:", enabled_names(n, i))

    rg = pm4py.convert_to_reachability_graph(n, i, f)
    print(label, "reachability graph type:", type(rg).__name__)

# 7. Repair Trade-Offs and Residual Risks

- Waiver versus standard review distinguishability:
  - R1 keeps waiver and standard review structurally distinguishable: standard review goes through `p_review_done` and `t_join_normal`; waiver goes through `p_waived` and `t_join_waived`.
  - R2 preserves distinguishability only in the event log before convergence. After `t_join_waived`, the waiver token becomes indistinguishable from a standard-review token in `p_review_done`.
  - R3 removes analysis entirely, so the main remaining distinction is still standard review versus waiver, but the business rule about mandatory analysis is lost.

- Duplicate behavior and silent-transition confusion:
  - R1 does not introduce duplicate firing behavior because the review split gives only one token to `p_review`, so `t_standard_review` and `t_waive_review` are mutually exclusive.
  - R1 keeps `t_join_waived` silent, but it now has a clear synchronization role.
  - R2 makes `t_join_waived` a silent one-input forwarder. This can be mistaken for a join or removed during later refactoring, increasing maintenance risk.
  - R3 removes silent analysis-related structure but changes the intended process semantics.

- Soundness alone does not prove full business alignment:
  - Soundness proves option to complete, absence of deadlocks, and no remaining tokens under the chosen initial/final markings.
  - It does not, by itself, prove a business policy unless the policy is encoded in the net. For example, a net could be sound but still allow both standard review and waiver, or allow authorization without analysis if the model were changed incorrectly.
  - Therefore, regression traces are necessary in addition to soundness checks.

- Positive traces to regression-test:
  - Standard review, analysis first:
    ```text
    t_register; t_split; t_analyze; t_standard_review; t_join_normal; t_authorize
    ```
  - Standard review, review first:
    ```text
    t_register; t_split; t_standard_review; t_analyze; t_join_normal; t_authorize
    ```
  - Waiver, analysis first, for R1:
    ```text
    t_register; t_split; t_analyze; t_waive_review; t_join_waived; t_authorize
    ```
  - Waiver, waiver first, for R1:
    ```text
    t_register; t_split; t_waive_review; t_analyze; t_join_waived; t_authorize
    ```
  - For R2, the waiver happy path should include both joins:
    ```text
    t_register; t_split; t_waive_review; t_analyze; t_join_waived; t_join_normal; t_authorize
    ```

- Negative traces to regression-test:
  - Authorization before analysis:
    ```text
    t_register; t_split; t_waive_review; t_join_waived; t_authorize
    ```
    In R1, `t_join_waived` should be disabled before `t_analyze`.
  - Standard join without analysis:
    ```text
    t_register; t_split; t_standard_review; t_join_normal; t_authorize
    ```
    `t_join_normal` should be disabled before `t_analyze`.
  - Both review outcomes:
    ```text
    t_register; t_split; t_standard_review; t_waive_review
    ```
    The second review transition should be disabled because `p_review` has only one token.
  - Any trace reaching a marking with `sink: 1` plus `p_analysis: 1` or `p_analysis_done: 1` should be rejected.
  - Any trace where `t_analyze` occurs after `t_authorize` should be rejected for a properly completed case.

- Detecting accidental bypass of mandatory analysis:
  - Reachability check: search the reachability graph for any reachable marking containing both `sink` and either `p_analysis` or `p_analysis_done`.
  - Enabledness check: after `t_waive_review` but before `t_analyze`, verify that `t_join_waived` is not enabled in R1.
  - Log conformance check: for each case, require that `t_analyze` occurs before `t_authorize`, and that either `t_standard_review` or `t_waive_review` occurs before `t_authorize`.
  - Structural review: ensure no path from `source` to `sink` reaches `t_authorize` without passing through `t_analyze`.

# 8. Final Recommendation

Deploy Repair 1: add `p_analysis_done -> t_join_waived`. It is the cheapest policy-preserving fix, makes the waiver join a true AND join, and keeps mandatory analysis. Waiver and standard review remain structurally distinguishable, and no silent pass-through is introduced. The only minor risk is that `p_analysis_done` feeds two alternative joins, but the exclusive review split prevents both from being enabled at once.

Use Repair 2 as fallback if the process owner wants a single final synchronization point: remove `t_join_waived -> p_decision` and add `t_join_waived -> p_review_done`. This preserves correctness but makes waiver indistinguishable from standard review after the waiver transition and adds a silent forwarding transition. Do not use Repair 3 unless the business explicitly makes analysis optional. Before deployment, run the positive and negative regression traces in Section 7.
