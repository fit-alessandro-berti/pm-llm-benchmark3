# 1. Assumptions, objectives, and decision variables

### 1.1 Demand and Service Assumptions
- **Arrival Process**: Expected arrivals are treated as deterministic rates per 2-hour block for capacity planning, but variability is modeled via a Poisson process in the Python simulation (mean = expected_arrivals).
- **Service Times**: Ranges (e.g., 5-8 minutes) are treated as Uniform distributions $U(min, max)$. Complex-tail cases are modeled by increasing the upper bound of the distribution (e.g., 8-14 mins becomes $U(8, 14)$ for ordinary, or $U(10, 14)$ for complex-tail).
- **Case Distribution**: Percentages in the Demand table are applied to the expected_arrivals to derive case counts per block.
- **Skill Matching**: A resource is "qualified" for a task if their speed multiplier is not "-" (null).
- **Parallel Branches**: For ME/ES cases, branches are assumed parallel unless resource contention forces sequential execution. The 8-minute coordination delay is added at the start of Validation.
- **Preemption**: A case can be preempted once per diagnostic activity. The restart penalty (10% of remaining time) is added to the total service time.

### 1.2 Objectives
We define two competing objective functions to guide the policy selection:

1.  **SLA-Resilient Objective**: Minimize the probability of P1 breach ($P(\text{Time}_{P1} > 120m)$) while keeping P3 completion within 24h. This objective prioritizes tail risk reduction.
2.  **Fairness-Robustness Objective**: Minimize the maximum resource utilization variance across the shift, specifically ensuring no individual resource exceeds 90% utilization (defined as "unfair/fragile" in the prompt).

### 1.3 Decision Variables
- **Routing**: Map each case to a specific resource or queue.
- **Priority**: Determine preemption order (P1 > P2 > P3).
- **Parallelization**: Decide whether ME/ES branches run in parallel (adding 8m coordination) or sequentially (adding 0m coordination but potentially longer path).
- **Handover**: Minimize resource switches to avoid 7m handover delays.

# 3. Candidate policies

### 3.1 Policy A: Strict Specialization with Fixed Queues
- **Rule**: Cases are routed to queues based on the primary skill (M, E, S). ME/ES cases are split based on the first detected fault.
- **Dispatch**: First-Come-First-Served (FCFS) within the skill queue.
- **Overflow**: None. If a queue exceeds 5 cases, cases are dropped (or delayed indefinitely).
- **Pros**: Minimal handover (7m) between same-skill resources. Clear ownership.
- **Cons**: High risk of starvation in one queue (e.g., Software) while others are idle. Poor P1 response if P1 is in a "slow" queue.

### 3.2 Policy B: Full Pooling (SEPT)
- **Rule**: Any qualified resource takes any case.
- **Dispatch**: Shortest Expected Processing Time (SEPT). Calculate $E[\text{Service}]$ for the case type and assign to the resource with the lowest current load.
- **Parallelization**: Parallel ME/ES branches always used (8m coordination) unless resource is overloaded.
- **Pros**: Maximizes utilization and minimizes average delay.
- **Cons**: High handover/setup burden (7m handover + 5m family switch). P1 cases may be delayed by P3 work if resource selection is purely SEPT without priority weighting.

### 3.3 Policy C: Hybrid (P1 Priority + Controlled Overflow)
- **Rule**:
    - **P1 Cases**: Assigned to the fastest qualified resource available (Speed Multiplier > 1.0 preferred), regardless of queue.
    - **P2/P3 Cases**: Assigned by Specialization (Queue A, B, C).
    - **Overflow Trigger**: If a specialized queue exceeds a threshold (e.g., 2 cases waiting), P2/P3 cases from that queue are temporarily routed to the general pool (Policy B logic).
- **Preemption**: P1 can preempt P2/P3. Interrupted P2/P3 incur 10% restart penalty.
- **Parallelization**: ME/ES branches run sequentially if resource contention is high (to avoid coordination delay), otherwise parallel.
- **Pros**: Balances SLA adherence (P1) with efficiency (P2/P3).

# 5. Robust recommendation

**Primary Recommendation: Policy C (Hybrid)**

**Reasoning**:
1.  **SLA Robustness**: P1 cases are the highest risk (120m target). Policy C explicitly prioritizes them, ensuring they are not delayed by P3 work in a specialized queue (Policy A) or general pool starvation (Policy B).
2.  **Fairness**: By reserving specialized queues for P2/P3, we prevent "pooling" from causing utilization spikes on specific resources (e.g., Ada doing too many Intakes), keeping individual utilization <90%.
3.  **Resilience**: The overflow trigger allows the system to recover from shocks (U1, U3) by temporarily utilizing cross-skilled resources without permanently breaking specialization.

**Fallback Mode**:
- **Trigger**: If P1 SLA breach rate exceeds 5% for 2 consecutive hours.
- **Action**: Switch to Policy B (Full Pooling) for P2/P3 to maximize throughput, while keeping P1 priority strict.
- **Preferable Policy**: Policy A is only preferable if handover costs are proven to be >15 minutes (not supported by data).

**Trigger Thresholds**:
- **Overflow**: Queue length > 2 cases for 30 mins.
- **Mode Switch**: P1 SLA < 90% for 240 mins.

# 6. Secondary effects and implementation risks

- **Gaming of Estimates**: Operators might classify a "Simple Mechanical" case as "Complex" to avoid P1 preemption or to fit into a less busy queue. *Mitigation*: Audit classification accuracy.
- **Starvation of P3**: P1/P2 focus might delay P3 indefinitely. *Mitigation*: P3 cases must have a hard deadline (e.g., 24h) before re-prioritization.
- **Skill Erosion**: Cross-skilling (Policy C overflow) might reduce efficiency over time if resources are not trained. *Mitigation*: Training budget for cross-skills.
- **Excessive Preemption**: Frequent P1 preemption of P2/P3 adds restart penalties. *Mitigation*: Limit P1 preemption to only "Critical" sub-tasks.
- **Coordination Overhead**: Parallel ME/ES branches add 8m coordination. *Mitigation*: Use sequential execution for high-load periods to save coordination time.
- **Validation Bottleneck**: If Validation is the last step, it can become a bottleneck if all branches arrive simultaneously. *Mitigation*: Queue Validation separately from Diagnostic.
- **Human Interpretability**: Operators need clear rules. *Mitigation*: Policy C dispatch rules are explicit (P1 > P2 > P3).

            valid_time = get_service_time('Validation', is_complex)
            start_ts = end_ts
            end_ts = start_ts + timedelta(minutes=valid_time)
            
            log.append({
                'case:concept:name': f'Case-{case_id}',
                'activity': 'Validation',
                'start_timestamp': start_ts,
                'time:timestamp': end_ts,
                'org:resource': assigned_resource,
                'priority': priority,
                'case_type': case_type,
                'complex_tail': is_complex,
                'scenario': scenario
            })
            
            case_id += 1

    return pd.DataFrame(log)

# 9. Limits and validation plan

### 9.1 Limitations
- **Arrival Variability**: Expected arrivals are used as deterministic rates. Real arrivals are stochastic (Poisson). The code uses `np.random` for arrivals but the capacity analysis is static.
- **Service Time Correlation**: Service times for ME/ES cases are assumed independent. In reality, a complex case often implies long times for both branches.
- **Preemption Logic**: The code implements a simplified preemption (restart penalty) but does not simulate the actual interruption of work in a shared resource pool.
- **PM4Py Fit**: PM4Py is used for formatting and basic discovery, but complex simulation logic (queueing theory) is implemented manually in the Python script for flexibility.

### 9.2 Validation Plan
- **Pilot**: Run Policy C for 2 weeks on 10% of the workload (shadow mode). Compare actual P1 SLA against Policy A (current standard).
- **Backtest**: Use historical incident logs (if available) to run the Python simulation with `scenario='Base'` and compare mean delay against historical KPIs.
- **Safety Check**: Monitor resource utilization. If any resource exceeds 90% for >4 hours, trigger a fallback to Policy B (Pooling) for non-P1 cases.
- **Human Review**: Have senior engineers review the "Overflow Trigger" thresholds to ensure they align with operational reality.
