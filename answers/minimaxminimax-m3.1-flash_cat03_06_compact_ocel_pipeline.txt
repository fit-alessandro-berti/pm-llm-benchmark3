## 1. Modeling assumptions

- **Object types and capitalization:** the object types are `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Identifiers are globally unique across all types.
- **E2O qualifiers:** E2O qualifiers describe the role of an object in an event. The vocabulary is:
  - `created`, `contains`, `added_to`
  - `stock_reserved_for`, `stock_reserved`
  - `packed`, `packed_in`, `packed_for`
  - `dispatched`, `dispatched_in`, `dispatched_for`, `dispatched_item`
  - `issued`, `billed_by`
  - `recorded`, `payment_recorded_against`
  - `confirmed`, `delivery_confirmed_for`
  - `closed`
- **O2O vocabulary and direction:** the first O2O identifier is always the semantic source and the second is the target:
  - `contains`: `Order  Item`
  - `packs`: `Package  Item`
  - `carries`: `Delivery  Package`
  - `bills`: `Invoice  Order`
  - `partially_settles`: `Payment  Invoice`
  
  Both payments are modeled as partial settlements because the narrative does not state the invoice total or explicitly say that M2 completes settlement. M2 could instead use `completes_settlement` if an authoritative total of 250 were known.
- **Direct downstream involvement:** this construction uses a **curated operational-involvement** policy. Reserve Stock directly involves both affected orders and both items. Packing, dispatching, and delivery confirmation directly involve the affected orders and items, as well as the package and, where applicable, delivery. Packing does not directly involve a delivery because delivery assignment is first observed at dispatch.
- **Financial involvement:** Invoice issuance directly involves V1 and both billed orders. Payments directly involve the payment and invoice, but not individual orders or items, because no allocation of M1 or M2 to O100/O200 is stated. Invoice-to-order links exist in O2O, but payment amounts are not allocated through them.
- **Source facts versus propagation:** the final `relations` table contains no automatically generated O2O closure. It has a custom `link_origin` column with:
  - `stated`: directly asserted by the event wording;
  - `curated_operational`: a deliberate operational denormalization supported by the unambiguous package composition, such as linking Dispatch P1 to O100, O200, I1, and I3.
  
  This is richer than a strict source-minimal log, but it avoids representing an arbitrary object-closure as observed fact. Any future O2O propagation should be generated into a separate table or separate OCEL and labeled `o2o_propagated`.
- **Event attributes:** `payment_amount` is a nullable event attribute on the two `Record Payment` events. There are no amount, currency, or monetary-unit objects.
- **Version assumption:** the code assumes a PM4Py release exposing `pm4py.objects.ocel.ocel.OCEL` and the constructor call `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`. That constructor call is isolated. If an installation has a different signature, adapt only that line or preferably upgrade to a release supporting OCEL O2O; do not silently discard `o2o`.

# Recent PM4Py releases return a list of DataFrames from ocel_flattening.

def normalize_flattened_log(flat_log):
    """Expose the conventional PM4Py event-log columns without changing events."""
    out = flat_log.copy()

    if "concept:name" not in out.columns:
        activity_source = next(
            (column for column in ("ocel:activity", "activity") if column in out.columns),
            None,
        )
        if activity_source is None:
            raise ValueError("Cannot find an activity column in flattened log")
        out["concept:name"] = out[activity_source].astype(str)
    else:
        out["concept:name"] = out["concept:name"].astype(str)

    if "case:concept:name" not in out.columns:
        if "case:oid" in out.columns:
            out["case:concept:name"] = out["case:oid"].astype(str)
        elif "ocel:oid" in out.columns:
            out["case:concept:name"] = out["ocel:oid"].astype(str)
        else:
            out["case:concept:name"] = "flat_case"
    else:
        out["case:concept:name"] = out["case:concept:name"].astype(str)

    if "time:timestamp" not in out.columns:
        timestamp_source = next(
            (column for column in ("ocel:timestamp", "timestamp") if column in out.columns),
            None,
        )
        if timestamp_source is None:
            raise ValueError("Cannot find a timestamp column in flattened log")
        out["time:timestamp"] = out[timestamp_source]
    out["time:timestamp"] = pd.to_datetime(out["time:timestamp"], utc=True)

    # Stable sorting avoids inventing an order for equal timestamps.
    return out.sort_values("time:timestamp", kind="stable").reset_index(drop=True)

### Object inventory

### O2O qualifiers and observed cardinality

Cardinality below describes this dataset, not a schema-enforced database constraint.

| Qualifier | Direction | Pairs | Observed cardinality |
|---|---|---|---|
| `contains` | Order  Item | O100I1, O100I2, O200I3 | One-to-many from orders; every item has one owning order here |
| `packs` | Package  Item | P1I1, P1I3, P2I2 | One-to-many from packages; every item is in one package here |
| `carries` | Delivery  Package | D1P1, D2P2 | One-to-one in this dataset |

| `partially_settles` | Payment  Invoice | M1V1, M2V1 | Many-to-one from payments to invoice; each payment has one invoice |

The most consequential relation set is **E07, Pack P1**. E09 and E13 carry the shared P1 branch forward through dispatch and delivery confirmation, while E11 joins O100 and O200 through V1.

## 4. Expected flattened behavior

### Order flattening

- **O100 trace:** approximately `E01 Create  E02 Add  E03 Add  E06 Reserve  E07 Pack  E08 Pack  E09 Dispatch  E10 Dispatch  E11 Invoice  E13 Confirm  E14 Confirm  E17 Close`.
- **O200 trace:** approximately `E04 Create  E05 Add  E06 Reserve  E07 Pack  E09 Dispatch  E11 Invoice  E13 Confirm  E16 Close`.
- **Copied shared events:** E06, E07, E09, E11, and E13 appear once in each relevant order trace. They are not duplicated within a trace, but an aggregate Order DFG counts them in both cases.
- **Omitted lifecycle:** payment events E12 and E15 are absent because payments are deliberately not allocated to orders. Item-level and package-level distinctions are also lost once the activity labels are aggregated.
- **Likely DFG edges:** `Create Order  Add Item`, `Add Item  Reserve Stock`, `Reserve Stock  Pack Package`, `Pack Package  Dispatch Package`, `Dispatch Package  Issue Invoice`, `Issue Invoice  Confirm Delivery`, and `Confirm Delivery  Close Order`. O100's two consecutive additions may also produce an `Add Item  Add Item` self-loop, depending on DFG self-loop handling.
- **Misleading interpretation:** the common shape hides that O100 is involved in both P1/P2 and D1/D2, while O200 is involved only in P1/D1. Shared transitions can also be mistaken for independent order executions.

### Package flattening

- **P1 trace:** `E07 Pack  E09 Dispatch  E13 Confirm`.
- **P2 trace:** `E08 Pack  E10 Dispatch  E14 Confirm`.
- **Copied shared events:** no event is copied between P1 and P2. The shared order/item nature of E07 remains in the object-centric model, not in the package trace.
- **Omitted lifecycle:** order creation, item addition, stock reservation, invoice, payments, and order closure are absent.
- **Likely DFG edges:** `Pack Package  Dispatch Package  Confirm Delivery`.
- **Misleading interpretation:** the two package traces look independent even though P1 consolidates items from both O100 and O200.

### Delivery flattening

- **D1 trace:** `E09 Dispatch  E13 Confirm`.
- **D2 trace:** `E10 Dispatch  E14 Confirm`.
- **Copied shared events:** none across D1 and D2.
- **Omitted lifecycle:** packing is absent because packing events are not directly linked to deliveries. The `Delivery carries Package` O2O relation could analytically connect P1 to D1 and P2 to D2, but that would be propagation rather than a direct E2O observation.
- **Likely DFG edges:** `Dispatch Package  Confirm Delivery`.
- **Misleading interpretation:** the delivery trace looks like a complete two-step process and does not show the substantial upstream packing and order work.

### Invoice flattening

- **V1 trace:** `E11 Issue Invoice  E12 Record Payment  E15 Record Payment`.
- **Copied shared events:** none, because there is only one invoice.
- **Omitted lifecycle:** all order, item, package, delivery, and order-closure events are absent. V1's O2O links to O100 and O200 do not automatically add those events to the invoice trace.
- **Likely DFG edges:** `Issue Invoice  Record Payment`; the two consecutive payment events may produce a `Record Payment  Record Payment` self-loop or be collapsed as a repeated activity, depending on PM4Py's DFG implementation.
- **Misleading interpretation:** the trace proves that two payment records occurred against V1, but not that V1 was fully settled or how the 100 and 150 units were allocated between O100 and O200.

### Payment flattening

Flattening on Payment would yield one-event traces: M1 contains only E12, and M2 contains only E15. Each resulting DFG would have a single activity and no edges, and each log skeleton would be effectively degenerate. The flattening would also remove the invoice context that is available through `Payment partially_settles Invoice`. Payment flattening is therefore particularly weak: it preserves neither the payment sequence nor the object context needed to interpret settlement.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG should expose activity/object-type co-occurrence and, depending on PM4Py's graph semantics, behavior within that context. The most connected activities are Dispatch Package and Confirm Delivery, which touch four object types; Pack Package touches three; Reserve Stock, Add Item, Issue Invoice, and Record Payment connect behavior with object families.

P1 should manifest as a package-side hub because it is associated with I1, I3, O100, O200, and D1. V1 should manifest as a financial convergence point because it is associated with O100, O200, M1, and M2. Some OC-DFG implementations abstract to object types, in which case the identities P1 and V1 are intentionally replaced by `Package` and `Invoice`; their instance-level sharing must then be recovered from the OCEL, O2O, Petri net, or interaction summary.

A global timestamp-based view may also show apparently odd transitions such as an Add Item event followed by creation of O200. Such edges are scheduling observations, not proof of causal order.

### OTG

The object-type graph should expose the following semantic edges:

- Order `contains` Item
- Package `packs` Item
- Delivery `carries` Package
- Invoice `bills` Order
- Payment `partially_settles` Invoice

This connects the complete type schema into one graph. Item is a notable convergence type because it receives both ownership and packing relationships. At instance level, the O2O facts show that P1 reaches I1 and I3 and therefore connects both order branches, while V1 directly bills O100 and O200 and receives both M1 and M2. The OTG itself normally abstracts those instances to types, so P1, V1, M1, and M2 are represented through their types rather than retained as graph nodes.

### ET–OT graph

The ET–OT graph should correspond closely to the activity/object-type audit:

- Create Order and Close Order touch only Order.
- Add Item and Reserve Stock touch Order and Item.
- Pack Package touches Order, Item, and Package.
- Dispatch Package and Confirm Delivery touch Order, Item, Package, and Delivery.
- Issue Invoice touches Order and Invoice.
- Record Payment touches Payment and Invoice.

It therefore highlights Reserve Stock as the order/item bridge, Pack P1 as the package/order/item bridge, and Record Payment as the payment/invoice bridge. P1 and V1 instance identities are generally absent from this type-level graph.

### Object-centric Petri net

A defensible reading is that the net represents activity transitions connected to object resources or object-type places:

- P1 provides a synchronization path connecting the I1/O100 and I3/O200 branches from Pack P1 through Dispatch P1 and Confirm D1.
- I1 participates in both an ownership path from O100 and a packing path through P1.
- V1 connects the issuance event to two distinct payment transitions, M1 and M2. Thus M1 and M2 converge on the same invoice resource without implying that they belong to the same order.
- O100 and O200 have longer-lived resources spanning creation, reservation, packing, invoicing, and closure.

This is not a uniquely determined semantic interpretation. Exact places, colors, read/write arcs, initial markings, and whether places represent instances or types depend on PM4Py's discovery implementation and defaults. The graph should be read as one executable approximation of the observed object interactions, not as the only possible Petri-net semantics.

### Object-interactions summary

The summary should identify the strongest interaction clusters:

- **P1** interacts with I1, I3, O100, O200, and D1.
- **V1** interacts with O100, O200, M1, and M2.
- **O100** is the broadest hub, linking I1, I2, P1, P2, D1, D2, and V1.
- **O200** connects I3, P1, D1, and V1.
- **M1** and **M2** connect to V1 but not directly to O100 or O200.

Exact counts and formatting depend on the PM4Py version's summary definition, but the central hubs should remain visible.

## 6. Modeling alternatives

| Policy | E2O policy | Effect on discovery |
|---|---|---|
| **Source-minimal** | Link only objects explicitly named by each event. For example, E08 links P2 and I2 but not O100; E09 links P1 and D1 but not the affected orders/items; E13 links only D1. Keep the five O2O business relationships unchanged. | Order traces lose dispatch and confirmation details and contain fewer shared events. DFGs become sparse and understate cross-order synchronization. OTG and the explicit O2O graph remain stable because they are based on source business relationships. |
| **Full operational involvement — selected here** | Add affected orders and items to packing, dispatch, and confirmation events, while retaining explicit provenance. Keep payments linked only to their invoice. | Order traces become operationally complete but shared events are counted in multiple cases. The OC-DFG, ET–OT graph, Petri net, and interactions summary show stronger synchronization through P1 and V1. This is suitable for process analysis, provided `curated_operational` links are not presented as raw source fields. |
| **O2O-propagated analytical closure** | Start from source E2O and derive additional links by following O2O paths. For example, Delivery D1 can propagate through P1 to I1/I3 and then to O100/O200; M1 can propagate through V1 to both orders. Store these in a separate relation table with `link_origin=o2o_propagated` and preferably a separate OCEL. | Order and delivery traces become very dense, and DFG counts increase because one event may enter many cases. The Petri net becomes highly connected. Analytical coverage improves, but it is no longer possible to distinguish directly observed from inferred involvement without inspecting provenance. |

These alternatives change analytical visibility and event counts, but not the underlying business story: O100 owns I1/I2, O200 owns I3, P1 consolidates I1/I3, D1 carries P1, V1 bills both orders, and M1/M2 settle V1.

## 7. Failure modes

1. **Relation inflation:** broad links to V1, O100, or shared packages can multiply one event across many cases. Aggregate DFGs then overstate how often an activity occurred in the business process.
2. **Missing direct E2O links:** a strict source-minimal log can omit the order affected by a dispatch or confirmation. Flattening then produces artificially short or incomplete lifecycle traces.
3. **Treating O2O propagation as observation:** analytically deriving `Event  Order` from `Event  Package  Item  Order` makes an inferred link indistinguishable from a recorded relationship unless provenance is retained.
4. **Duplicate shared events after flattening:** E06, E07, E09, E11, and E13 legitimately occur in both order traces. They are not duplicate rows within one trace, but aggregation across traces double-counts their occurrence.
5. **Ambiguous payment allocation:** V1 bills both orders, but there is no line-level allocation of M1's 100 or M2's 150. Assigning either payment wholly or proportionally to both orders would fabricate business facts.
6. **Overly short Payment traces:** M1 and M2 each have only one directly linked event. Payment flattening loses both invoice context and the sequence of settlement.
7. **Constructor/API version mismatch:** older PM4Py versions may not accept `o2o` in the constructor or may not expose all requested OCEL discovery functions. Dropping O2O would change the model; the constructor line should instead be adapted or the package upgraded.
8. **False total order for same-time events:** all timestamps in this example are distinct, but in general a timestamp sort or event-ID tie-break would fabricate a sequence for simultaneous events. Even here, the global timestamp sequence is not a causal total order because E06 and E07 synchronize parallel order branches.
9. **Incorrect O2O direction:** reversing `Invoice bills Order` or `Payment partially_settles Invoice` without an explicit inverse convention can yield misleading ownership or settlement flows.
10. **Treating observed cardinality as a schema constraint:** V1 having two payments and two orders does not establish that every invoice must always have exactly two orders or payments.
11. **Qualifier drift:** using `contains`, `has_item`, and `contains_item` for the same semantic relation makes role analysis and graph annotations inconsistent.
12. **Modeling amounts as objects:** representing 100 or 150 as amount objects would incorrectly turn transaction attributes into independently identifiable business entities.
13. **Misreading a DFG as causal proof:** a globally interleaved DFG can show `Add Item  Create Order` or similar transitions that are scheduling artifacts rather than causal dependencies.
14. **Overinterpreting log skeletons:** two orders and one invoice provide very little repetition for robust conformance inference. The discovered skeletons are useful illustrations, not statistically strong process models.

## 8. Final semantic checks

A reviewer should be able to verify all of the following directly in the generated tables:

1. `events` has exactly 17 rows, unique IDs E01–E17, and every timestamp is timezone-aware.
2. `objects` has exactly 12 rows with the six expected types and globally unique IDs.
3. O100 contains I1 and I2, while O200 contains I3, through O2O rows with qualifier `contains`.
4. P1 packs I1 and I3, so the package explicitly combines items from both orders; P2 packs I2.
5. D1 carries P1 and D2 carries P2.
6. V1 bills both O100 and O200.
7. M1 and M2 each have a `partially_settles` O2O edge to V1, and their amounts 100 and 150 appear only as event attributes on E12 and E15.
8. E06 directly relates both O100 and O200 and both I1 and I3.
9. E07 directly relates P1 to I1, I3, O100, and O200, making it the principal convergence event.
10. Every E2O row has the same activity and timestamp as its event, and every referenced event and object exists.
11. There are no duplicate E2O or O2O rows and no orphan identifiers.
12. E16 closes O200 before E17 closes O100, with the stated timestamps.
