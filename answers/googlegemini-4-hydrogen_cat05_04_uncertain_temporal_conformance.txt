## 1. Normalization Assumptions

### 1.1 Interval Construction, Resolution, and Clock-Offset Direction
Let $R$ be the displayed timestamp in its source time zone.
1. **Timestamp-resolution uncertainty (applied first):** The source's local clock reading $C_{\text{local}}$ at the moment of recording lies in an interval $[C_{\text{local,min}}, C_{\text{local,max}}]$:
   - **HUB** (displayed second, $\pm 0.5\text{ s}$): $[R - 0.5\text{ s},\; R + 0.5\text{ s}]$.
   - **OPS-BER, VENDOR-NY, LEGACY-BER** (floor to minute): $[R,\; R + 59.999\text{ s}]$ (matching the stated $[10:14:00, 10:14:59.999]$ convention; treating the upper bound as open $+60\text{ s}$ changes boundary comparisons by $0.001\text{ s}$ and alters no classification).
   - **SENSOR** (round to nearest $10\text{ s}$): $[R - 5\text{ s},\; R + 5\text{ s}]$.
   - **MOBILE-LON** (round to nearest minute): $[R - 30\text{ s},\; R + 30\text{ s}]$.
2. **Time-zone & DST conversion:** Each local clock bound is mapped to UTC via IANA `Europe/Berlin`, `America/New_York`, `Europe/London`, or `UTC`. On `2026-06-01`, `Europe/Berlin` is CEST (`UTC+2`), `America/New_York` is EDT (`UTC-4`), and `Europe/London` is BST (`UTC+1`). On `2025-10-26`, `Europe/Berlin` falls back at `03:00 CEST -> 02:00 CET`, creating two UTC mappings for local `02:00`–`02:59`: `fold=0` (CEST, `UTC+2`) and `fold=1` (CET, `UTC+1`).
3. **Clock-offset correction:** Given $\text{clock\_offset} = \text{recorded\_clock} - \text{true\_clock} \in [a, b]$, true UTC time is $t = C_{\text{UTC}} - \text{offset}$. Therefore:
   $$t \in [C_{\text{UTC,min}} - b,\; C_{\text{UTC,max}} - a]$$
   Combined per-source margins around UTC-converted $R$ are:
   - **HUB**: $[-1.5\text{ s},\; +1.5\text{ s}]$
   - **OPS-BER** (with valid NTP): $[-120\text{ s},\; +149.999\text{ s}]$
   - **SENSOR**: $[-10\text{ s},\; +10\text{ s}]$
   - **VENDOR-NY**: $[-180\text{ s},\; +239.999\text{ s}]$
   - **LEGACY-BER** (per fold): $[-60\text{ s},\; +119.999\text{ s}]$
   - **MOBILE-LON** (clock + rounding only): $[-330\text{ s},\; +330\text{ s}]$
4. **Duration interval arithmetic:** For activity pair $(A, B)$ with independent true-time intervals $[t_{A,\min}, t_{A,\max}]$ and $[t_{B,\min}, t_{B,\max}]$, the feasible duration $d = t_B - t_A$ spans:
   $$[t_{B,\min} - t_{A,\max},\; t_{B,\max} - t_{A,\min}]$$
   (Without assuming identical clock offsets across events unless proven, offsets are varied independently within each source's bound.)

- **T-406 (Mobile user-entry delay):** Two interpretations exist for *"user may have entered the displayed time up to five minutes late"*:
  - **Primary assumption (occurrence-time shift):** The mobile app timestamps entry/submission rather than occurrence, so the investigation started up to $300\text{ s}$ *earlier* than the clock-corrected record time: $t_{\text{occ}} = t_{\text{rec}} - \delta,\; \delta \in [0, 300\text{ s}]$, widening the UTC interval from `[12:08:30Z, 12:19:30Z]` to `[12:03:30Z, 12:19:30Z]`.

- **T-407 (Missing `Alert_Received` & `Alert_Sent`):** `Alert_Sent` is not definitionally `Alert_Received`, no receipt acknowledgment exists, and the causal rule $t_{\text{Alert\_Received}} \le t_{\text{InvStart}}$ is unlogged. For **conditional sensitivity analysis**, we also evaluate the network-bounded inference $t_{\text{Alert\_Received}} = t_{\text{Alert\_Sent}} + [0, 1200\text{ s}]$ both with and without the causal clip $t_{\text{Alert\_Received}} \le t_{\text{InvStart}}$.
- **T-409 (Missing NTP diagnostics):** Because verified NTP telemetry is absent for that hour and only a *"weak engineering estimate"* of $[-12\text{ min}, +12\text{ min}]$ is available, rules depending on `OPS-BER` (`S1`, `S2`, `TP1`, `TP2`) are classified `INDETERMINATE` under strict audit standards, with conditional bounds under $[-720\text{ s}, +720\text{ s}]$ reported in sensitivity analysis. `TP3` (`Alert_Received -> Containment_Complete`) uses only `HUB` and remains `CERTAIN_PASS`.
- **Missing `Close_Incident` (T-402–T-407, T-409):** `Close_Incident` is absent with no basis for inference, so `S3` and `TP4` are not testable in those cases.
- **Baseline thresholds for Section 3:** Hard SLAs at $0\text{ min}$ tolerance (`S1 <= 900 s`, `S2 <= 2700 s`, `S3 <= 129600 s`); Temporal Profile at $\zeta = 2$ ($\mu \pm 2\sigma$). Section 4 tests tolerances $\{0, 2, 5\}\text{ min}$ and $\zeta \in \{1, 2, 3\}$.

def _parse_local(val: str) -> datetime:
    fmt = "%Y-%m-%d %H:%M:%S" if len(val) == 19 else "%Y-%m-%d %H:%M"
    return datetime.strptime(val, fmt)


def normalize_row_to_utc_intervals(row: pd.Series) -> List[Interval]:
    meta = SOURCE_META[row["system"]]
    zi = ZoneInfo(meta["tz"])
    naive = _parse_local(row["recorded_value"])

    # Detect whether local wall time maps to 1 or 2 UTC points (DST fold ambiguity)
    utc_candidates = sorted(
        {
            naive.replace(tzinfo=zi, fold=f).astimezone(timezone.utc)
            for f in (0, 1)
        }
    )

    res_mode = meta["res_mode"]
    if res_mode == "second_pm05":
        res_lo, res_hi = -0.5, 0.5
    elif res_mode == "floor_min":
        res_lo, res_hi = 0.0, 59.999
    elif res_mode == "round_10s":
        res_lo, res_hi = -5.0, 5.0
    elif res_mode == "round_min":
        res_lo, res_hi = -30.0, 30.0
    else:
        raise ValueError(f"Unknown res_mode: {res_mode}")

    off_a, off_b = meta["offset"]
    if row["note"] == "missing_ntp_weak_est":
        off_a, off_b = -720.0, 720.0

    # Apply resolution first, then subtract clock_offset in [a, b]
    delta_lo = timedelta(seconds=res_lo - off_b)
    delta_hi = timedelta(seconds=res_hi - off_a)

    # Apply primary user-entry delay shift [0, 300 s] earlier for MOBILE-LON
    if row["note"] == "entry_delay_0_300s":
        delta_lo -= timedelta(seconds=300.0)

    intervals: List[Interval] = []
    for base_utc in utc_candidates:
        t_min = pd.Timestamp(base_utc + delta_lo)
        t_max = pd.Timestamp(base_utc + delta_hi)
        intervals.append((t_min, t_max))
    return intervals

# 4. Feasible duration intervals and classifications

def duration_interval_union(ivs_a: List[Interval], ivs_b: List[Interval]) -> List[Tuple[float, float]]:
    spans: List[Tuple[float, float]] = []
    for a_lo, a_hi in ivs_a:
        for b_lo, b_hi in ivs_b:
            spans.append(((b_lo - a_hi).total_seconds(), (b_hi - a_lo).total_seconds()))
    return spans


def classify_band(spans: List[Tuple[float, float]], lo: float, hi: float) -> str:
    all_in = all(s_lo >= lo and s_hi <= hi for s_lo, s_hi in spans)
    if all_in:
        return "CERTAIN_PASS"
    all_out = all(s_hi < lo or s_lo > hi for s_lo, s_hi in spans)
    if all_out:
        return "CERTAIN_VIOLATION"
    return "POSSIBLE_VIOLATION"

### How Midpoint PM4Py Diagnostics Differ from Interval Conclusions
PM4Py's `conformance_temporal_profile` evaluates single point-to-point timestamps and therefore forces a binary pass/fail decision, hiding uncertainty:
- **False negatives on boundary straddles (`POSSIBLE_VIOLATION` masked as pass):** At $\zeta = 2$, `T-401 TP1` (midpoint $\approx 855\text{ s} \le 960\text{ s}$), `T-403 TP1` (midpoint $\approx 930\text{ s} \le 960\text{ s}$), `T-404 TP1` (midpoint $\approx 810\text{ s} \le 960\text{ s}$), `T-405 TP1` (midpoint $\approx 900\text{ s} \le 960\text{ s}$), and `T-406 TP1` (midpoint $\approx 690\text{ s} \le 960\text{ s}$) all pass in PM4Py despite feasible intervals exceeding $960\text{ s}$. Similarly, at $\zeta = 1$, `T-404 TP2` ($2490\text{ s} \le 2700\text{ s}$), `T-406 TP2` ($2430\text{ s} \le 2700\text{ s}$), and `T-403 TP3` ($3450\text{ s} > 3420\text{ s}$—here midpoint fails while lower feasible times pass) lose interval nuance.
- **False confidence on `INDETERMINATE` evidence:** In `T-407` and `T-409`, collapsing conditional/unverified evidence to a midpoint causes PM4Py to emit a clean pass at $\zeta = 2$, masking missing receipt acknowledgment (`T-407`) and missing NTP diagnostics (`T-409`).
- **T-408 `TP2` ($\zeta = 2$) & T-402 `TP1` ($\zeta = 2$):** Midpoints sit exactly on $3300\text{ s}$ and $1095\text{ s}$ respectively; PM4Py treats `T-408 TP2` as an exact pass ($3300 \le 3300$), missing the $3\text{ s}$ HUB uncertainty overflow, and treats `T-402 TP1` as a hard deviation, missing the $1.5\text{ s}$ feasible overlap inside $[240, 960]\text{ s}$.

## 6. Evidential Sufficiency

To resolve each `INDETERMINATE` or `POSSIBLE_VIOLATION` finding to `CERTAIN_PASS` or `CERTAIN_VIOLATION`, the minimum additional evidence falls into four distinct categories:

1. **Stronger synchronization evidence**
   - **T-409 (`S1`, `S2`, `TP1`, `TP2` — `INDETERMINATE`):** Verified NTP offset diagnostics for `OPS-BER` covering `2026-06-01 18:00–19:00 CEST` showing an offset tighter than $\pm 12\text{ min}$ (specifically, establishing `offset >= +180 s` or `<= -60 s` relative to the $15\text{ min}$ boundary resolves `S1`; any bounded NTP check within $\pm 12\text{ min}$ resolves `S2` to `CERTAIN_PASS`).
   - **T-401 (`S1`, `TP1`), T-402 (`S2`, `TP1`), T-403 (`S1`, `TP1`, `TP3`), T-405 (`S1`, `TP1`):** Event-time or sub-minute NTP offset telemetry (plus sub-minute timestamp resolution for `OPS-BER`, `VENDOR-NY`, and `LEGACY-BER`). For `T-401 S1`, narrowing `OPS-BER` offset + rounding uncertainty below $+1\text{ min}$ separates true durations above vs. below $15\text{ min}$. For `T-403`, tightening `VENDOR-NY` offset from $\pm 180\text{ s}$ to $< \pm 60\text{ s}$ resolves `S1`, `TP1`, and `TP3`.

2. **Missing activity evidence**

## 7. Governance Recommendation

1. **Canonical UTC Storage & Raw Provenance Retention:**
   - Store every event with a canonical UTC timestamp (`ISO-8601` with explicit `Z` suffix and at least millisecond precision) **alongside** the immutable raw local timestamp, IANA time-zone identifier (e.g., `Europe/Berlin`), and explicit **DST fold / UTC offset** (`+02:00` vs. `+01:00` or `fold=0/1`). Never store naive local timestamps.
2. **Source Synchronization & Resolution Metadata:**
   - Capture source-level NTP/PTP offset telemetry (`offset_estimate_s`, `offset_error_bound_s`, `sync_status`) per hour and attach a snapshot reference to ingested events. Flag missing telemetry (as in `T-409`) so downstream analytics automatically downgrade reliability rather than assuming zero error.
   - Record display/quantization semantics (`resolution_s`, `rounding_mode`: `floor`, `round`, `exact`) in a machine-readable source registry so interval engines construct exact bounds automatically.
3. **Lifecycle & Start/Complete Semantics:**
   - Standardize distinct activity taxonomy fields (`event_phase`: `sent`, `received`, `start`, `complete`, `recorded`) so `Alert_Sent` cannot silently substitute for `Alert_Received` (`T-407`) and mobile submission time is stored separately from user-asserted occurrence time (`T-406`).
   - Require explicit receipt acknowledgments for alert delivery and disallow silent backward inference unless linked to a signed work record with explicit min/max uncertainty bounds (`T-404`).
4. **Causal Identifiers & Sequence Integrity:**
   - Emit monotonic per-source sequence numbers and causal correlation IDs (`parent_event_id`, `trigger_event_id`) to validate ingestion order independently of wall-clock jumps or DST fallbacks (`T-405`).
5. **Interval-Aware Enforcement & Escalation Policy:**
   - **Hard legal/contractual enforcement (penalties, breach notices):** Require `CERTAIN_VIOLATION` (entire feasible duration interval violates the SLA). Do **not** enforce punitive action solely on interval overlap (`POSSIBLE_VIOLATION`) or weak/missing evidence (`INDETERMINATE`).
   - **Operational triage & audit escalation:** Treat `POSSIBLE_VIOLATION` and `INDETERMINATE` as **evidentiary-remediation triggers**—require root-cause clock/log verification (e.g., pulling NTP logs or receipt ACKs) within a fixed review window. Repeated `POSSIBLE_VIOLATION` or `INDETERMINATE` outcomes from a source (e.g., `VENDOR-NY`, `MOBILE-LON`, `OPS-BER`) should trigger a system-synchronization compliance breach even if individual incident SLAs cannot be proven violated.
