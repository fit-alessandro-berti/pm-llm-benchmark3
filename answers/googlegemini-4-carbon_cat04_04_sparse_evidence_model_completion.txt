### Why Bidirectional DFG Edges Do Not Prove Concurrency

The observed DFG contains three bidirectional pairs: `("Credit Check", "Engineering Review"): 17` vs. `("Engineering Review", "Credit Check"): 11`; `("Engineering Review", "Supplier Confirmation"): 13` vs. `("Supplier Confirmation", "Engineering Review"): 2`; and `("Supplier Confirmation", "Expedite Review"): 1` vs. `("Expedite Review", "Supplier Confirmation"): 1`. Treating $a \to b$ and $b \to a$ in a DFG as proof of concurrency ($a \parallel b$) is an inductive fallacy for four distinct reasons:

1. **Latent XOR of opposite sequences (Simpson's/routing aggregation)**: Two mutually exclusive case cohorts can each execute strictly sequentially in opposite orders—for example, new customers executing `CC -> ER` sequentially and repeat customers executing `ER -> CC` sequentially. Every individual case is strictly sequential with zero temporal overlap, yet pooling the cohorts produces strong bidirectional DFG edges.
2. **Completion-order inversion under staggered starts (D7)**: Even if `Credit Check` always *starts* before `Engineering Review`, variable processing times allow a fast `ER` to finish before a slow `CC` (`start(CC) < start(ER) < complete(ER) < complete(CC)`), producing `ER -> CC` in a completion-only log without independent parallel initiation.
3. **Coarse timestamps and tie-breaking artifacts (S7)**: When multiple department sign-offs are batch-committed at the same timestamp, ingestion-index ordering creates artificial sequential bigrams in either direction without reflecting execution order.
4. **Markovian context erasure (memoryless projection)**: A DFG discards prefix history. For example, `SC -> ER` (`n=2`) and `ER -> SC` (`n=13`) appear bidirectional, yet `SC` *never* precedes `ER` unless `CC` has already completed (`V5`). Naive DFG concurrency inference would falsely conclude `SC` and `ER` can execute in any order right after `Register Order`. Additionally, in general logs (outside this single-instance dataset), length-2 loops (`A -> B -> A`) also induce bidirectional DFG arcs without concurrency.

# 2. Shared Assumptions

All three candidate models share the following explicit foundational assumptions:

1. **Completion-event semantics (D7, S7)**: Every transition label represents the *logged completion* of the corresponding activity. Where `model_balanced` and `model_permissive` use partial orders or parallel operators (`+`), they assert *absence of a completion-order constraint* in the event log, **not** simultaneous resource execution or start-time independence.
2. **Single-instance, acyclic case scope**: Each of the eight activities occurs at most once per order (consistent with 30/30 observed traces and D6 for `Expedite Review`). Rework loops, re-checks, and repeated approvals are assumed out of scope for the current log population.
3. **Invariant framing stages (D1, D2, D3, D4)**: Every valid case starts with `Register Order`, completes both `Credit Check` and `Engineering Review` (and `Supplier Confirmation` whenever logged) prior to `Approve Configuration`, and finishes with the deterministic post-approval sequence `Approve Configuration -> Release Production -> Archive Case`.
4. **Conflation of true optionality and missing data for `Supplier Confirmation` (S3, S4, S5)**: Seven of 30 cases (23.3%: V3 and V4) contain no `Supplier Confirmation` event. With a reported 5–10% integration drop rate on `SC` (S5)—corresponding to roughly 1–3 lost `SC` events across ~25 external-component orders—both mechanisms are almost certainly active in the 30-case sample: ~4–6 cases reflect genuine stocked-component skips (S4) and ~1–3 cases reflect dropped integration messages (S5). Because the `external`/`stocked` attribute was not exported, all three models represent `SC` absence as a control-flow skip (`XOR` with silent `tau` or path enumeration). Consequently, conformance fitness cannot detect an external-component order whose `SC` event failed to log or failed to occur.
5. **Control-flow abstraction of unobserved data guards**: Both `Supplier Confirmation` (governed by component sourcing, S3–S4) and `Expedite Review` (governed by unlogged SLA/urgency escalation rules, D6/S6) are modeled via non-deterministic `XOR` choices rather than data-aware guards.

# 3. Conservative Candidate

### Inductive-Bias Statement
`model_conservative` adopts a strict empirical-sufficiency bias: it treats the 30-case log and high-confidence framing rules (D1, D2) as an exhaustive whitelist of verified completion sequences and refuses to extrapolate unseen interleavings from low-sample variants ($n=1, 2$) or contested stakeholder claims (S1 vs. S2, D5). By factoring only the invariant prefix (`Register Order`) and invariant suffix (`Approve Configuration -> Release Production -> Archive Case`) around an exclusive choice (`X`) over the seven observed pre-approval subtraces, the model guarantees maximal empirical precision and zero false-positive trace admissions, knowingly trading away generalization and structural parsimony to eliminate over-approximation risk.

### Compact Formal Expression
Using standard process-tree notation ($\to$ for sequence, $\times$ for exclusive choice):

$$M_{\text{cons}} = \to\!\Big(\text{RO},\; \times\!\big(\to(\text{CC}, \text{ER}, \text{SC}),\; \to(\text{ER}, \text{CC}, \text{SC}),\; \to(\text{CC}, \text{ER}),\; \to(\text{ER}, \text{CC}),\; \to(\text{CC}, \text{SC}, \text{ER}),\; \to(\text{CC}, \text{ER}, \text{SC}, \text{XR}),\; \to(\text{ER}, \text{CC}, \text{XR}, \text{SC})\big),\; \text{AC},\; \text{RP},\; \text{ArC}\Big)$$

Equivalently, $\mathcal{L}(M_{\text{cons}}) = \{\text{V1}, \text{V2}, \text{V3}, \text{V4}, \text{V5}, \text{V6}, \text{V7}\}$ with $|\mathcal{L}(M_{\text{cons}})| = 7$.

### Duplicate Labels and Scalability Note
Factoring the common prefix and suffix avoids duplicating `Register Order`, `Approve Configuration`, `Release Production`, and `Archive Case`, but enumerating the seven middle branches duplicates `Credit Check` (7 transitions), `Engineering Review` (7 transitions), `Supplier Confirmation` (5 transitions), and `Expedite Review` (2 transitions). In the induced Petri net, label duplication fragments activity-level transition statistics (requiring post-hoc aggregation by label to inspect bottlenecks), enlarges the alignment search space when replaying noisy traces, and obscures shared causal structure (e.g., that `CC` and `ER` always both occur). Worse, XOR enumeration scales combinatorially: for $k$ concurrent activities with $m$ optional tasks, the number of distinct linearizations grows as $\Theta((k+m)!)$, quickly rendering explicit path enumeration intractable as process breadth increases.

### Self-Contained PM4Py Code (`ProcessTree`)

```python
import pm4py

    "'Register Order', "
    "X( "
    "->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation' ), "
    "->( 'Engineering Review', 'Credit Check', 'Supplier Confirmation' ), "
    "->( 'Credit Check', 'Engineering Review' ), "
    "->( 'Engineering Review', 'Credit Check' ), "
    "->( 'Credit Check', 'Supplier Confirmation', 'Engineering Review' ), "
    "->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review' ), "
    "->( 'Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation' ) "
    "), "
    "'Approve Configuration', "
    "'Release Production', "
    "'Archive Case' "
    ")"
)
```

### Behavior Deliberately Excluded
- **All unobserved trace variants**, including any case with `Expedite Review` when `Supplier Confirmation` is skipped or unlogged (e.g., `RO, CC, ER, XR, AC, RP, ArC`).
- **Observed check orders paired with observed expedite orders in unseen combinations**, such as `RO, CC, ER, XR, SC, ...` or `RO, ER, CC, SC, XR, ...`.
- **Symmetric early supplier confirmation after engineering review** (`RO, ER, SC, CC, ...`).
- **Early expedite review** before both checks complete (`RO, CC, XR, ER, ...`) and **post-approval checks/confirmations**.

### Known Underfitting Risks
- **Severe small-sample censorship on `Expedite Review` ($n=2$)**: Only two expedited cases exist in the log (V6 and V7). Legitimate expedited cases for stocked components (`RO, CC, ER, XR, AC, ...`), dropped `SC` events on expedited cases (S5), or natural cross-combinations (`RO, CC, ER, XR, SC, ...` and `RO, ER, CC, SC, XR, ...`) will all be flagged as non-conformant.
- **Asymmetric censorship on interleaving (`V5`, $n=2$)**: `RO, CC, SC, ER, XR, ...` and `RO, ER, SC, CC, ...` are rejected purely because they did not appear in a 30-trace sample.

# 4. Balanced Candidate

### Inductive-Bias Statement
`model_balanced` seeks the highest-plausibility structural generalization by synthesizing empirical regularities across all 30 cases with medium-to-high-confidence domain and compliance constraints (D1–D4, D6, S2, S4, S6), while refusing to extrapolate low-confidence claims (D5's symmetric `ER`-only trigger for `SC`, which has 0/30 empirical support) or contradicted sequential claims (S1). It represents the process as a label-unique POWL `StrictPartialOrder` over mandatory activities and `XOR`-optional submodels, capturing fine-grained asymmetric dependencies without duplicating a single activity label.

### Decision Logic: Sequence vs. Concurrency vs. Partial Order
1. **`Credit Check` (`CC`) and `Engineering Review` (`ER`) — Unordered (concurrent completion)**: `CC` precedes `ER` in 19/30 cases (V1, V3, V5, V6) and `ER` precedes `CC` in 11/30 cases (V2, V4, V7). Per D7 and S2, we reject Finance's strict sequence claim (S1) as a descriptive rule and leave `CC` and `ER` mutually unordered between `Register Order` and downstream gates.
2. **`Expedite Review` (`XR`) — Gated by AND-join `{CC, ER} < XR < AC`, optional via `XOR(XR, tau)`**: D6 and S6 explicitly require *both* principal checks to finish before `Expedite Review` is permitted and require `XR` before `AC`. Both V6 (`CC, ER, SC, XR`) and V7 (`ER, CC, XR, SC`) satisfy `{CC, ER} < XR < AC`.
3. **`Supplier Confirmation` (`SC`) vs. `Expedite Review` (`XR`) — Mutually unordered**: V6 shows `SC < XR`, V7 shows `XR < SC`, and S6 confirms `XR` may occur before or after `SC`. Moreover, decoupling `XOR(SC, tau)` from `XOR(XR, tau)` naturally allows stocked orders (S4) or `SC`-dropped orders (S5) to undergo `Expedite Review`.
4. **`Supplier Confirmation` (`SC`) vs. `CC` and `ER` — Asymmetric partial-order edge `CC < SC` (no edge between `ER` and `SC`)**: In **23 out of 23 observed traces containing `SC`** (V1=12, V2=7, V5=2, V6=1, V7=1), `CC` completes before `SC`. By contrast, `ER` completes *after* `SC` in V5 (`RO, CC, SC, ER, ...`, $n=2$), refuting `ER < SC`. Meanwhile, `ER, SC, CC` and `SC, CC, ER` never appear (0/30). Enforcing `CC < sc_opt` while leaving `ER` unordered with `sc_opt` admits *exact* observed non-expedited `SC` variants (V1, V2, V5) while excluding unverified `ER, SC, CC` and `SC, ...` orderings.
5. **Why POWL (`StrictPartialOrder`) is structurally necessary**: The precedence relations among `{ER, CC, xr_opt, sc_opt}`—specifically $\text{ER} \prec \text{xr\_opt}$, $\text{CC} \prec \text{xr\_opt}$, and $\text{CC} \prec \text{sc\_opt}$, with no edge $\text{ER} \prec \text{sc\_opt}$—form an **induced N-poset (fence)**. By the classical characterization of series-parallel posets, an induced N-poset **cannot** be expressed as a single-label block-structured `ProcessTree` (`->`, `+`, `X`); POWL represents it directly without duplicate labels.

### Compact Formal Expression
Let $\text{sc\_opt} = \times(\text{SC}, \tau)$ and $\text{xr\_opt} = \times(\text{XR}, \tau)$. `model_balanced` is the strict partial order $(V, \prec^+)$ generated by the Hasse diagram:

$$V = \{\text{RO}, \text{CC}, \text{ER}, \text{sc\_opt}, \text{xr\_opt}, \text{AC}, \text{RP}, \text{ArC}\}$$
$$\prec_{\text{Hasse}} \;=\; \{(\text{RO}, \text{CC}),\; (\text{RO}, \text{ER}),\; (\text{CC}, \text{sc\_opt}),\; (\text{CC}, \text{xr\_opt}),\; (\text{ER}, \text{xr\_opt}),\; (\text{sc\_opt}, \text{AC}),\; (\text{xr\_opt}, \text{AC}),\; (\text{AC}, \text{RP}),\; (\text{RP}, \text{ArC})\}$$

Notice that $\text{CC} \prec \text{sc\_opt} \prec \text{AC}$ and $\text{ER} \prec \text{xr\_opt} \prec \text{AC}$ transitively enforce $\{\text{CC}, \text{ER}\} \prec \text{AC}$ even when $\text{sc\_opt}$ and/or $\text{xr\_opt}$ execute $\tau$. This yields $|\mathcal{L}(M_{\text{bal}})| = 12$ complete traces (the 7 observed + 5 unobserved).

### Self-Contained PM4Py Code (`POWL`)

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

ro = Transition(label="Register Order")
cc = Transition(label="Credit Check")
er = Transition(label="Engineering Review")
sc_opt = OperatorPOWL(
    Operator.XOR,
    [Transition(label="Supplier Confirmation"), SilentTransition()],
)
xr_opt = OperatorPOWL(
    Operator.XOR,
    [Transition(label="Expedite Review"), SilentTransition()],
)
ac = Transition(label="Approve Configuration")
rp = Transition(label="Release Production")
arc = Transition(label="Archive Case")

model_balanced = StrictPartialOrder(
    nodes=[ro, cc, er, sc_opt, xr_opt, ac, rp, arc]
)
model_balanced.order.add_edge(ro, cc)
model_balanced.order.add_edge(ro, er)
model_balanced.order.add_edge(cc, sc_opt)
model_balanced.order.add_edge(cc, xr_opt)
model_balanced.order.add_edge(er, xr_opt)
model_balanced.order.add_edge(sc_opt, ac)
model_balanced.order.add_edge(xr_opt, ac)
model_balanced.order.add_edge(ac, rp)
model_balanced.order.add_edge(rp, arc)
```

### Behavior Deliberately Excluded
- **`Supplier Confirmation` completing before `Credit Check`**, including both `RO, ER, SC, CC, ...` and `RO, SC, CC, ER, ...`.
- **`Expedite Review` completing before either `Credit Check` or `Engineering Review`** (e.g., `RO, CC, XR, ER, ...` or `RO, ER, XR, CC, ...`), preserving D6 and S6.
- **Any check, confirmation, or expedite activity after `Approve Configuration`**, preserving D2–D4 and D6.

### Known Underfitting Risks
- **Asymmetric rejection of D5 (`RO, ER, SC, CC, ...`)**: If D5 holds symmetrically—meaning `Engineering Review` alone can trigger `Supplier Confirmation` before `Credit Check` finishes—`model_balanced` will reject `RO, ER, SC, CC, AC, RP, ArC`. In a 30-case sample where only 8 `SC`-bearing traces had `ER` before `CC` (V2=7, V7=1), an occasional ~10–15% early-`SC` rate could easily yield 0 occurrences by chance.
- **Completion-timestamp inversion on concurrent `SC` (D7, S7)**: If procurement initiates `SC` from in-progress `CC` notes and `SC` finishes (or ties on batch timestamp) before `CC` is formally closed, `CC < SC` will reject the trace.

# 5. Permissive Candidate

### Inductive-Bias Statement
`model_permissive` prioritizes recall of plausible unseen execution orders consistent with broad domain invariants (D1–D6, S2, S4, S6) and completion-only logging uncertainty (D7, S7). Recognizing that D5 allows `Supplier Confirmation` to begin from partial information without waiting for both checks—and that completion timestamps can invert relative to start times—it relaxes the `CC < SC` constraint by placing optional `Supplier Confirmation` in parallel (`+`) with the check-and-expedite block `->( +(CC, ER), ?XR )` inside the pre-approval phase, yielding a clean, duplicate-free `ProcessTree`.

### Boundary Between Reasonable Generalization and Forbidden Behavior
- **Reasonable generalization (admitted)**: Any interleaving of optional `Supplier Confirmation` within the pre-approval window `[Register Order, Approve Configuration)` alongside `Credit Check`, `Engineering Review`, and post-check `Expedite Review`. This accommodates D5's symmetric `ER`-first trigger (`RO, ER, SC, CC, ...`), stocked-item expedites (`RO, CC, ER, XR, ...`), and completion-timestamp inversions where a fast supplier confirmation finishes after `Register Order` (or in-progress check communication) before `CC` and `ER` record completion timestamps (`RO, SC, CC, ER, ...`).
- **Hard red lines (strictly forbidden)**:
  1. **Framing and release gates (D1, D2)**: No activity may precede `Register Order`; `Approve Configuration -> Release Production -> Archive Case` is strictly sequential and terminal.
  2. **Pre-approval completeness (D3, D4, D6)**: Neither `CC`, `ER`, `SC`, nor `XR` may occur after `Approve Configuration`.
  3. **Compliance gate on `Expedite Review` (D6, S6)**: `Expedite Review` remains strictly gated behind the completion of *both* `Credit Check` and `Engineering Review` (`->( +(CC, ER), X(XR, tau) )`) and may execute at most once. Permitting `XR` before both checks complete would cross from reasonable generalization into explicit compliance violation.
  4. **Acyclicity**: Repeated executions of any activity remain forbidden.

### Compact Formal Expression
In process-tree notation ($\to$ sequence, $+$ parallel/AND, $\times$ XOR):

$$M_{\text{perm}} = \to\!\Big(\text{RO},\; +\!\big(\to\!(+(\text{CC}, \text{ER}),\; \times(\text{XR}, \tau)),\; \times(\text{SC}, \tau)\big),\; \text{AC},\; \text{RP},\; \text{ArC}\Big)$$

This model admits $|\mathcal{L}(M_{\text{perm}})| = 18$ complete traces, forming a strict inclusion hierarchy: $\mathcal{L}(M_{\text{cons}}) \subsetneq \mathcal{L}(M_{\text{bal}}) \subsetneq \mathcal{L}(M_{\text{perm}})$ ($7 \subsetneq 12 \subsetneq 18$).

### Self-Contained PM4Py Code (`ProcessTree`)

```python
import pm4py

model_permissive = pm4py.parse_process_tree(
    "->( "
    "'Register Order', "
    "+( "
    "->( +( 'Credit Check', 'Engineering Review' ), X( 'Expedite Review', tau ) ), "
    "X( 'Supplier Confirmation', tau ) "
    "), "
    "'Approve Configuration', "
    "'Release Production', "
    "'Archive Case' "
    ")"
)
```

### Behavior Deliberately Excluded
- **Premature `Expedite Review`** before both `Credit Check` and `Engineering Review` have completed (e.g., `RO, CC, XR, ER, ...` or `RO, XR, CC, ER, ...`), enforcing D6 and S6.
- **Unapproved production release or post-approval checks/confirmations** (e.g., `RO, CC, ER, AC, SC, RP, ArC` or `RO, CC, ER, RP, AC, ArC`), enforcing D2, D3, and D4.
- **Repeated activities / rework loops** (e.g., two `Credit Check` or two `Expedite Review` events).

### Known Underfitting Risks
- **Rework / re-confirmation cycles**: If an `Expedite Review` or failed `Engineering Review` occasionally forces a second `Supplier Confirmation` (e.g., switching to a faster supplier), acyclicity will reject the repeated `SC` event.
- **Conditional post-approval supplier confirmation**: D4 holds with medium confidence; if standard-configuration orders ever provisionally approve configuration (`AC`) while awaiting `SC` prior to `Release Production` (`RO, CC, ER, AC, SC, RP, ArC`), `model_permissive` will reject them. (Conversely, note its deliberate *overfitting/precision* tradeoff in the opposite direction: because ProcessTrees lack non-block 1-of-2 OR-joins without label duplication, `+` also admits `RO, SC, CC, ER, ...` where `SC` finishes before *both* checks.)

# 8. Validation Code

### Methodological Limitations on Playout and Infinite Languages
1. **Sampled playout does not prove language inclusion or exclusion**: `pm4py.play_out(net, im, fm)` draws a finite stochastic sample of traces. Failing to sample a trace does *not* prove the model excludes it, and observing a subset of traces in playout does *not* prove $\mathcal{L}(M_1) \subseteq \mathcal{L}(M_2)$.
2. **General Petri nets vs. finite acyclic nets**: For arbitrary Petri nets with loops, the trace language $\mathcal{L}(N, M_i, M_f)$ is infinite, exhaustive enumeration does not terminate, and general labeled Petri net language inclusion is undecidable. Below, we pair PM4Py's stochastic `play_out` with (a) exact **alignment-based membership testing** (`log_fitness == 1.0`, which handles silent `tau` transitions and duplicate labels in `model_conservative` exactly, unlike heuristic token-based replay) on a curated positive/negative trace suite, and (b) a **bounded BFS reachability explorer** with an explicit step/state bound (`max_depth=12`, `max_markings=5000`), noting that it covers the full language here *only* because all three candidates are loop-free and 1-safe.

def extract_log_fitness(fit_dict: dict) -> float:
    for key in ("log_fitness", "average_trace_fitness", "averageFitness"):
        if key in fit_dict:
            return float(fit_dict[key])
    raise KeyError(f"Unrecognized fitness keys: {list(fit_dict.keys())}")


def is_trace_accepted(trace_activities: list[str], net, im, fm) -> bool:
    single_log = pm4py.parse_event_log_string([",".join(trace_activities)])
    fit = pm4py.fitness_alignments(single_log, net, im, fm)
    return extract_log_fitness(fit) >= 1.0 - 1e-9


def bounded_language_playout(net, im, fm, max_vis_len: int = 12, max_states: int = 5000):
    """
    Bounded BFS over Petri net markings up to `max_vis_len` visible events
    and `max_states` visited `(marking, trace_prefix)` states.
    NOTE: Cannot exhaustively enumerate infinite languages on cyclic nets;
    returns `(accepted_traces_set, exhausted_cleanly_bool)`.
    """
    from pm4py.objects.petri_net.semantics import ClassicSemantics

    semantics = ClassicSemantics()
    queue = deque([(im, ())])
    visited = {(im, ())}
    accepted = set()
    truncated = False

    while queue:
        marking, vis_prefix = queue.popleft()
        if marking == fm:
            accepted.add(vis_prefix)
        if len(vis_prefix) >= max_vis_len:
            if semantics.enabled_transitions(net, marking):
                truncated = True
            continue
        for trans in semantics.enabled_transitions(net, marking):
            next_marking = semantics.weak_execute(trans, net, marking)
            next_prefix = (
                vis_prefix + (trans.label,)
                if trans.label is not None
                else vis_prefix
            )
            state = (next_marking, next_prefix)
            if state not in visited:
                if len(visited) >= max_states:
                    truncated = True
                    continue
                visited.add(state)
                queue.append(state)

    return accepted, (not truncated)
