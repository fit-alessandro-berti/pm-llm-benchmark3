# 1. Assumptions and Interpretation

1. **Low-risk/High-risk representation**: Modeled as an XOR choice immediately after "Analyze Root Cause". The decision point itself is abstracted; the model admits both branches but does not encode the data condition triggering each.

2. **Optional supplier consultation**: Represented using an XOR between "Consult Supplier" and a silent transition (). This allows the activity to occur at most once in the correct position but does not enforce the "at most once" constraint across multiple occurrences—this is a limitation of the visible label abstraction.

3. **Passing inspection abstraction**: Since event logs record activities at completion time without outcome labels, the loop structure "Execute Trial  Inspect Trial  [Adjust Parameters]  ..." is modeled as a LOOP operator where "Inspect Trial" is the exit condition. Failed inspections are represented by re-entering the loop body via "Adjust Parameters". The actual pass/fail data is external to the control-flow model.

4. **Duplicate visible labels**: Permitted where semantically necessary to preserve behavioral flexibility (e.g., "Execute Trial" and "Inspect Trial" appear multiple times in loop iterations). However, this creates ambiguity in trace analysis if not handled carefully.

5. **Approximation policy for process tree**: **Permissive over-approximation**. Where exact synchronization is impossible (e.g., Release Material requiring concurrent completion of three independent paths), the tree admits additional interleavings that do not violate explicit precedence constraints. This preserves flexibility while potentially admitting some unsafe traces.

6. **"May overlap" interpretation**: Interpreted as true concurrency (parallel execution permitted), not merely absence of order constraint. In the process tree, this is modeled using the PARALLEL operator; in POWL, using lack of ordering edges between nodes.

7. **Trial iteration limit**: The LOOP operator permits infinite iterations; real-world constraints on maximum retries are not encoded in the control-flow model.

8. **Release synchronization**: Process trees cannot natively express join-synchronization across parallel branches. This is approximated by sequencing Release after all branches complete in a linear fashion, which over-constrains valid interleavings.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator
import pm4py

def build_material_deviation_tree():
    """Constructs a permissive over-approximation of the material deviation process."""
    
    # Leaf nodes (visible activities)
    register = ProcessTree(label="Register Deviation", operator=None)
    contain = ProcessTree(label="Contain Material", operator=None)
    analyze = ProcessTree(label="Analyze Root Cause", operator=None)
    plan_verify = ProcessTree(label="Plan Verification", operator=None)
    design = ProcessTree(label="Design Corrective Action", operator=None)
    sup_review = ProcessTree(label="Supervisor Review", operator=None)
    qual_review = ProcessTree(label="Quality Review", operator=None)
    reg_review = ProcessTree(label="Regulatory Review", operator=None)
    consult = ProcessTree(label="Consult Supplier", operator=None)
    execute_trial = ProcessTree(label="Execute Trial", operator=None)
    inspect_trial = ProcessTree(label="Inspect Trial", operator=None)
    adjust = ProcessTree(label="Adjust Parameters", operator=None)
    release = ProcessTree(label="Release Material", operator=None)
    archive = ProcessTree(label="Archive Case", operator=None)
    tau = ProcessTree(label=None, operator=None)  # Silent transition
    
    # Build trial loop: Execute Trial  Inspect Trial  [Adjust  Execute Trial]*
    # Approximation: LOOP(Execute Trial, Inspect Trial, Adjust Parameters)
    # This admits multiple adjustments but doesn't enforce "adjust only on fail"
    trial_body = ProcessTree(operator=Operator.SEQUENCE, children=[execute_trial, inspect_trial])
    trial_loop = ProcessTree(operator=Operator.LOOP, children=[trial_body, adjust])
    
    # Build approval routes
    # Low-risk: Supervisor Review
    low_risk = ProcessTree(operator=Operator.SEQUENCE, children=[sup_review, tau])
    
    # High-risk: Quality Review || Regulatory Review (concurrent)
    high_risk = ProcessTree(operator=Operator.PARALLEL, children=[qual_review, reg_review])
    
    # Risk route choice (XOR after Analyze Root Cause)
    risk_route = ProcessTree(operator=Operator.XOR, children=[low_risk, high_risk])
    
    # Optional supplier consultation (XOR with silent)
    # Note: This allows zero or one occurrence; doesn't prevent multiple
    supplier_opt = ProcessTree(operator=Operator.XOR, children=[consult, tau])
    
    # Work streams from Register Deviation
    # Stream 1: Contain Material  Plan Verification
    stream1 = ProcessTree(operator=Operator.SEQUENCE, children=[contain, plan_verify])
    
    # Stream 2: Analyze Root Cause  [Risk Route]  [Supplier]  Design  Trial Loop
    # Note: This sequences things that should be parallel (approvals and trial)
    stream2_inner = ProcessTree(operator=Operator.SEQUENCE, children=[analyze, risk_route])
    stream2_supplier = ProcessTree(operator=Operator.SEQUENCE, children=[stream2_inner, supplier_opt])
    stream2_design = ProcessTree(operator=Operator.SEQUENCE, children=[stream2_supplier, design])
    stream2_full = ProcessTree(operator=Operator.SEQUENCE, children=[stream2_design, trial_loop])
    
    # Parallel initial streams (D1, D2)
    initial_streams = ProcessTree(operator=Operator.PARALLEL, children=[stream1, stream2_full])
    
    # Full process: Start  Initial Streams  Release  Archive
    # Note: This approximates synchronization at Release
    full_process = ProcessTree(operator=Operator.SEQUENCE, children=[register, initial_streams, release, archive])
    
    return full_process

tree = build_material_deviation_tree()
```

**Approximations and Limitations:**

1. **Release synchronization (D13, D14)**: The tree sequences `release` after `initial_streams`, forcing linear completion rather than true synchronization. Valid interleavings where approvals complete during trial are admitted, but the model also admits cases where release occurs before all prerequisites complete—a violation of intended semantics.

2. **Trial loop structure (D9-D11)**: The LOOP operator here places `adjust` as a post-loop action, which incorrectly suggests adjustment always occurs. A better model would nest adjust within the loop body with conditional branching, but process trees lack conditional loops.

3. **Approval-trial overlap (D7, D8 vs D13)**: The tree forces sequential completion of approvals before trial begins, contradicting requirement 7. This is a significant under-constraint.

4. **Supplier optionality (D6)**: The XOR with  allows zero or one occurrence but doesn't enforce "at most once" across the entire trace—multiple consultations could theoretically appear.

5. **Risk route timing (D5)**: The model forces risk route to complete before trial design, whereas approvals should overlap with trial work.

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

def build_material_deviation_powl():
    """Constructs a POWL model capturing partial-order dependencies."""
    
    # Create nodes
    nodes = {
        'Register': Transition('Register Deviation'),
        'Contain': Transition('Contain Material'),
        'Analyze': Transition('Analyze Root Cause'),
        'PlanVerify': Transition('Plan Verification'),
        'Design': Transition('Design Corrective Action'),
        'SupReview': Transition('Supervisor Review'),
        'QualReview': Transition('Quality Review'),
        'RegReview': Transition('Regulatory Review'),
        'Consult': Transition('Consult Supplier'),
        'ExecuteTrial': Transition('Execute Trial'),
        'InspectTrial': Transition('Inspect Trial'),
        'Adjust': Transition('Adjust Parameters'),
        'Release': Transition('Release Material'),
        'Archive': Transition('Archive Case'),
    }
    
    # Create strict partial order
    powl = StrictPartialOrder(nodes=list(nodes.values()))
    
    # Add essential dependencies
    # D1, D2: Register starts everything
    powl.order.add_edge(nodes['Register'], nodes['Contain'])
    powl.order.add_edge(nodes['Register'], nodes['Analyze'])
    
    # D3: Contain  PlanVerification
    powl.order.add_edge(nodes['Contain'], nodes['PlanVerify'])
    
    # D4: Analyze  Design
    powl.order.add_edge(nodes['Analyze'], nodes['Design'])
    
    # D5: Risk route (modeled as parallel options from Analyze)
    # Both low and high risk options available; actual choice determined externally
    powl.order.add_edge(nodes['Analyze'], nodes['SupReview'])
    powl.order.add_edge(nodes['Analyze'], nodes['QualReview'])
    powl.order.add_edge(nodes['Analyze'], nodes['RegReview'])
    
    # D6: Optional supplier (edge exists, but Consult node can be skipped in traces)
    powl.order.add_edge(nodes['Analyze'], nodes['Consult'])
    
    # D7, D8: Trial requires both Design and PlanVerification
    powl.order.add_edge(nodes['Design'], nodes['ExecuteTrial'])
    powl.order.add_edge(nodes['PlanVerify'], nodes['ExecuteTrial'])
    
    # D9: Trial  Inspection
    powl.order.add_edge(nodes['ExecuteTrial'], nodes['InspectTrial'])
    
    # D10, D11: Loop back on failure
    powl.order.add_edge(nodes['InspectTrial'], nodes['Adjust'])
    powl.order.add_edge(nodes['Adjust'], nodes['ExecuteTrial'])
    
    # D12, D13, D14: Release requires passing inspection + approvals + supplier (if selected)
    powl.order.add_edge(nodes['InspectTrial'], nodes['Release'])
    powl.order.add_edge(nodes['SupReview'], nodes['Release'])
    powl.order.add_edge(nodes['QualReview'], nodes['Release'])
    powl.order.add_edge(nodes['RegReview'], nodes['Release'])
    powl.order.add_edge(nodes['Consult'], nodes['Release'])
    
    # D15: Archive after Release
    powl.order.add_edge(nodes['Release'], nodes['Archive'])
    
    return powl

powl = build_material_deviation_powl()
```

**Concurrency Justification:**

1. **Contain Material and Analyze Root Cause**: No edge between them; allowed to overlap per requirement 2.

2. **Plan Verification and Design Corrective Action**: No direct edge; they depend on different predecessors and may proceed concurrently.

3. **Approvals and Trial Work**: No edges between {SupReview, QualReview, RegReview} and {ExecuteTrial, InspectTrial, Adjust}; approvals may overlap trial per requirement 7.

4. **Quality Review and Regulatory Review**: No edge between them; concurrent execution permitted per requirement 5.

5. **Consult Supplier and other activities**: Only constrained by Analyze  Consult and Consult  Release; overlaps with approvals and trial permitted.

# 7. Preferred Representation and Validation Plan

**Preferred Representation: POWL**

The POWL model is preferred because:
1. It directly expresses cross-branch dependencies without artificial sequencing
2. It admits true concurrency where intended (approvals overlapping trial)
3. It avoids the block-structure limitations of process trees
4. Partial-order semantics align better with the narrative's "may overlap" language

However, POWL lacks native support for:
- Mandatory XOR choices (risk route selection)
- Loop termination conditions (passing inspection)

These gaps require complementary data-aware extensions.

# 8. Final Self-Critique

1. **Risk Route Enforcement Gap**: Neither model truly enforces the XOR choice between low-risk and high-risk approval paths. The POWL includes edges for all review types, allowing traces that mix supervisor review with quality/regulatory reviews—a violation of requirement 5. This is a semantic weakness that requires data-aware extensions beyond pure control-flow modeling.

2. **Loop Termination Ambiguity**: The LOOP operator in the process tree and cyclic edges in POWL permit infinite trial iterations without encoding the "until passing inspection" condition. While the narrative acknowledges this is external to control flow, the models should ideally document this limitation more prominently. A silent transition marking "inspection passed" would improve fidelity.

3. **Supplier Consultation Multiplicity**: The XOR-with- approach in the process tree allows Consult Supplier to appear zero or one times, but doesn't prevent multiple occurrences in longer traces. Similarly, the POWL edge doesn't constrain frequency. This represents an under-constraint that could lead to unrealistic traces in conformance checking scenarios.
