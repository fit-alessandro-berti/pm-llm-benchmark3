```python
def load_nominal_model(log):
    """Parse the simplified tree; fall back to inductive discovery.

    Known limitations of the hand-written tree (documented, not hidden):
      1. The loop operator '*' in PM4Py is binary (do, redo[, skip]); a
         3-ary loop may fail to parse or parse differently than intended.
      2. Rework after Planning review / Legal check / appeal is NOT in the
         string; it must be added as loop constructs or guard-based rework
         in the simulation model.
      3. The tree cannot express attribute-based routing (requires_fire,
         district sensitivity, value thresholds) or batching; those live in
         the DES routing layer, not in the control-flow model.
    """
    try:
        tree = pm4py.parse_process_tree(NOMINAL_TREE_STRING)
        source = "parsed"
    except Exception:
        tree = pm4py.discover_process_tree_inductive(log, noise_threshold=0.2)
        source = "inductive_miner_fallback"
    net, im, fm = pm4py.convert_to_petri_net(tree)
    return tree, net, im, fm, source
```

Arrival process with NHPP thinning:

```python
MONTH_FACTOR = {1: 1.0, 2: 1.0, 3: 1.7, 4: 1.7, 5: 1.7, 6: 1.2, 7: 1.2, 8: 1.2, 9: 1.7, 10: 1.7, 11: 1.7, 12: 1.0}  # Jun–Aug interpolated (assumption)
WEEKDAY_FACTOR = {0: 2.2, 1: 1.4, 2: 1.0, 3: 1.3, 4: 1.2}  # Mon..Fri; Sat/Sun ~0 (portal 24/7 but checks start Monday) -- to calibrate

@dataclass
class NonStationaryArrivals:
    base_rate_per_workday: float
    monthly_factor: Dict[int, float] = field(default_factory=lambda: dict(MONTH_FACTOR))
    weekday_factor: Dict[int, float] = field(default_factory=lambda: dict(WEEKDAY_FACTOR))

    def intensity(self, t: pd.Timestamp) -> float:
        # calendar-day rate; weekend submissions captured via portal but processing starts next business day
        m = t.month; wd = t.dayofweek
        wd_f = self.weekday_factor.get(wd, 0.15)
        return self.base_rate_per_workday * self.monthly_factor.get(m, 1.0) * wd_f

    def next_arrival(self, rng, t_now) -> float:
        # Lewis–Shedler thinning with lambda_max = base*2.2*1.7 * safety
        lam_max = self.base_rate_per_workday * max(self.monthly_factor.values()) * max(self.weekday_factor.values()) * 1.2
        while True:
            t = t_now + pd.Timedelta(days=float(rng.exponential(1.0 / lam_max)))
            if rng.random() < self.intensity(t) / lam_max:
                return t
```

## 1. Model scope and state variables

### 1.1 Boundary and level of detail
- **In scope:** portal submission  terminal decision (Issue permit / Reject application), including rework loops after completeness check, planning review, inspection, legal check, and appeal (appeal modeled as delayed re-entry into Decision drafting / Legal check).
- **Out of scope:** payment/enforcement, physical construction; emergency decisions (removed from log — modeled only as a small synthetic stream in stress scenarios, never calibrated as if observed).
- **Abstraction level:** discrete-event simulation (DES) at activity × resource granularity. Service in minutes, third-party response and public notice in days. Inspections are modeled as *tours* (resource + travel + batch), not as atomic tasks. We deliberately do **not** simulate individual documents or applicant behavior in detail; applicant behavior enters as exogenous stochastic clocks.

### 1.2 Entities and attributes
| Entity | Key attributes |
|---|---|
| Permit case | case_type, district, architect_id, application_value, requires_fire/env/notice flags, stage, stage-entry time, accumulated wait/service, rework counters, age (for aging policies), bundle_id, related_group_id |
| Document request | request timestamp, applicant response clock (heavy-tailed, separate from municipal resources) |
| Objection (latent) | binary state per related-case group, extension draw for notice duration |
| Inspection bundle | district, member cases, tour date, travel time |
| Resource unit | class, skill restrictions (e.g., 2 planners = Simple renovation only), calendar, busy/idle state, accumulated busy time |

### 1.3 Resources, capacities, calendars
| Resource | Capacity | Calendar | Notes |
|---|---|---|---|
| Clerks | 5 FTE | Mon–Fri 08:00–16:00 | 1 clerk diverted to portal support Mondays |
| Planners | 8 FTE | Mon–Fri 09:00–17:00 | 2 handle only Simple renovation (skill-constrained queue) |
| Fire reviewers | 2 FTE | Tue–Thu only | Friday/Monday fire demand queues to Tuesday |
| Environmental | 3 FTE × 0.60 effective = 1.8 FTE | Mon–Fri | 40% reserved for non-permit duties |
| Inspectors | 4 FTE (+1 temporary in peak months under D4) | Field Tue–Fri | Travel matrix by district; D3/D5 longer |
| Legal | 2 FTE | Zero capacity in council-meeting weeks (urgent lane excepted) | Holiday + council calendar is exogenous input |
| System / portal | unlimited | 24/7 intake | |
| Applicant channel | n/a | Exogenous response clocks | Never counted as municipal service |

### 1.4 State variables
- **Global:** simulation clock; queue length per (activity, case_type, priority class); WIP by stage; per-resource busy-time accumulators and utilization; open document requests; current inspection tour plans per district/day; calendar state (holiday, council week, peak-month flag); random-number stream registry.
- **Per case:** current stage and stage-entry timestamp; set of pending AND-join inputs for Decision drafting (planning/fire/env/notice/inspection flags); rework counters per loop; elapsed age; eligibility flags for policies (e.g., D2 rule).
- **Cross-case registries:** related-case groups (architect_id × district × submission week), shared objection state, batching queues.

### 1.5 Queues and disciplines
One queue per activity, segmented by case type (skill constraints) and priority class. Default FIFO; policy levers replace discipline (D6 aging priority, legal "urgent" lane). Inspection scheduling is a **batching queue** with window *w* and max batch size *b*. Public notice and applicant response are timers, not queues.

### 1.6 Cross-case dependency mechanisms (must be in the state space, not replayed)
1. Shared resource contention (all human pools).
2. Architect bursts: correlated submissions from top-20 architects + correlated document quality (a shared "frailty" per architect).
3. Geographic inspection batching (reduces travel, adds wait for the first case in a bundle).
4. Neighborhood objections: one latent objection event can extend public notice for several related cases.
5. Calendar interruptions (holidays, council weeks) hitting Legal and Public notice.

## 2. Parameter-estimation plan

### 2.1 Arrivals
- Extract case-start timestamps (first event per case); fit a **non-homogeneous Poisson process** (t) =  · m(month) · w(weekday), with m estimated by a Poisson regression on month dummies (Jan–Feb = 1.0; Mar–May, Sep–Nov  1.7; Jun–Aug interpolated, flagged as an assumption) and w from weekday counts (Mon 2.2× Wed; Tue–Fri estimated, calibrated against queue spikes).
- **Burst component:** identify architect-day clusters (same architect_id, 5-day windows); fit a Poisson cluster process: rate of batch arrivals, batch-size distribution (top-20 architects  31% of volume), and within-batch spacing (lognormal hours). Correlate document quality within a batch (shared frailty).

### 2.2 Case attributes and routing
- Jointly sample case_type (45/28/17/10), district, and log(application_value) (lognormal per type, check correlation with `requires_fire`).
- Estimate branch probabilities with **Laplace-smoothed Beta posteriors** per case type: fire, environmental, public notice, legal check, missing-docs, decision outcome, each rework loop. Use logistic regressions for `requires_fire ~ type + value` and `requires_environment ~ type + district` to *partially* compensate for the unobserved area threshold and incomplete sensitivity data; treat coefficients as uncertain, not as ground truth.
- Use PM4Py variants (per case type, via `pm4py.get_variants_as_tuples` and attribute filtering) to enumerate reachable behavior; align variants against the process tree so the DES routing table covers observed paths plus expert-confirmed rare paths.

### 2.3 Service vs waiting split (critical limitation)
- Where lifecycle start+end timestamps exist, fit service distributions directly (lognormal/Weibull/gamma by AIC; mixture models for multi-modal activities).
- Where only completion timestamps exist, the observed gap = waiting + calendar idle + service. Split via two complementary methods, both reported with uncertainty: (a) flow-based bounds — consecutive completions by the same resource within one shift bound service from below; (b) **inverse calibration** — choose split parameters so simulated utilization/throughput matches observed completion counts. Carry a 3-level scenario on the split (wait-heavy/base/service-heavy) into the experiment matrix.
- **Reconciliation check (mandatory):** face-value arithmetic shows Planning review demand  3.5 h × ~58 starts/day  200 h/day vs. 64 FTE-h/day of planner capacity. This means the log's "service time" for Planning (and likely Environmental) mixes touch time with *elapsed waits for internal inputs/consultant reports*. Decompose into touches-per-case × touch time before treating it as capacity consumption; if unreconcilable, revise the capacity interpretation with the process owner. Similarly: Site inspection service includes travel (separate parameter), Public notice is a timer (service  0).

### 2.4 Waiting times
Empirical waiting quantiles (e.g., 6 d before Planning, 7 d before Legal) are used as **validation targets and queue-discipline diagnostics**, never as injected delays — otherwise queue formation under interventions would be meaningless.

### 2.5 Rework
Count repeated activity occurrences per case (PM4Py variants + direct pandas counting; optionally use alignment diagnostics to classify deviations). Estimate: loop probability, loop-count distribution (zero-truncated), and rework service time (typically ~0.7× first-pass; verify). Appeal = separate post-decision arrival stream into Decision drafting with its own delay distribution.

### 2.6 Calendars
Start from HR calendars as templates; validate against log (completions outside scheduled windows  overtime/absence flags). Environmental effective FTE = 3 × 0.6. Legal capacity zero in council weeks, with an urgent-lane probability. Fire Tue–Thu. Holidays list as exogenous input. Add stochastic short-term absence (~2%) as an uncertainty lever.

### 2.7 Applicant/third-party responses
Receive-missing-documents: requestreceive gap, calendar-corrected, heavy-tailed (lognormal body + Pareto tail above ~p85, or GPD peaks-over-threshold). No-show/reschedule rate for Site inspection from inspection-rework variants. **Objections are latent:** fit a 2-component mixture to (notice duration  14 d floor): no-objection vs objection (heavy tail, p90  60 d). Never treat the proxy as an observed event.

### 2.8 Dependencies
- Bundling propensity for same-architect/same-district cases within k days; travel-time saving as a function of batch size (capped).
- Related-case objection sharing (same district/week  correlated notice extension).

### 2.9 PM4Py responsibilities (and limits)
PM4Py is used for: log formatting (`pm4py.format_dataframe`), variant extraction, DFG and performance-DFG discovery, inductive tree discovery (`pm4py.discover_process_tree_inductive`, noise threshold  0.2) as a data-grounded cross-check of the hand-written tree, conversion to Petri net (`pm4py.convert_to_petri_net`), and conformance (`pm4py.conformance_diagnostics_alignments`, `pm4py.fitness_alignments`, `pm4py.precision_alignments`) for replay validation. **PM4Py is not used as the simulation engine** — it has no resource calendars, non-stationary arrivals, batching, or cross-case dependency semantics at the fidelity required here. The DES is a separate module; PM4Py also serves to *validate simulated logs* (run the same diagnostics on synthetic logs).

## 3. Assumptions

**Arrivals**
- NHPP with multiplicative month × weekday factors; Jun–Aug interpolated (1.2×, assumption); rates stable across the analysis horizon except policy/stress scenarios.
- Architect batches: batch size 2–6, within-batch spacing lognormal (hours–days); top-20 architects  31% share.

**Service times**
- Lognormal (or Weibull) per (activity, case_type); Site inspection = service + travel; Planning/Environmental decomposed into touch-time vs elapsed consultant wait; service independent of queue length given covariates.
- Completion-only activities: service/wait split uncertain  scenario parameter (limiting assumption, reported).

**Routing**
- Branching posteriors from variants; fire/env guards partially unobserved (area threshold, district sensitivity)  logistic proxies with wide priors; D2 eligibility ("no prior violations") needs an external data source — modeled as a probability if unavailable.

**Resources / calendars**
- HR calendars accurate to ±10% effective capacity; skills enforced (simple-only planners); system infinite capacity; absence stochastic; council/holiday calendar exogenous and known.

**Rework**
- Stage-specific Bernoulli re-entry with per-case-type probabilities; rework service  0.7× first pass; reasons not conditioned on unreliable free text except coarse validated keywords.

**Applicant / third-party response**
- Heavy-tailed response (median  5 d, long tail, capped at 180 d); inspection readiness drives inspection rework; objections latent, coupled within related-case groups.

**Cross-case dependencies**
- Bundling benefits accrue only when 2 cases co-qualify; first-in-bundle absorbs extra wait; objections shared in related groups; Monday burst interacts with the Monday-dedicated clerk.

**Non-stationary demand**
- Seasonal factors constant within horizon; growth scenarios applied multiplicatively; no endogenous feedback of backlog onto arrival rate (flagged).

**Missing data**
- Objection proxy only (notice duration); emergency cases absent  tail underestimated, synthetic 0.5% stream only in stress runs; rare-variant 7% lumped with its own duration distribution; calendars not event-derived; flattened log  weak identification of bundling parameters (wide priors + sensitivity analysis).

## 5. Warm-up, replications, and uncertainty treatment

- **Initialization:** seed the system with the observed in-flight backlog (snapshot of open cases by stage and age). This removes most of the warm-up transient; residual warm-up is verified with **Welch's method** (moving averages of WIP and median cycle time across 10 pilot replications); we discard the first 90 days minimum and extend if traces still drift.
- **Run length:** 48 months per replication, integer multiple of the annual seasonal cycle; statistics computed on months 4–48; per-year results reported separately to verify non-stationarity is reproduced.
- **Replications:** R = 100 per scenario-cell; adaptive increase until relative half-width 5% (median duration) and 10% (p90) per case type.
- **Seeds:** master seed 20260102; `numpy.random.SeedSequence` spawned into named streams (arrivals, routing, service, applicant, objection, travel, calendars) with identical layout across all scenarios  **common random numbers**; comparisons are paired on replication level (paired t on medians, Wilcoxon as robustness).
- **Uncertainty decomposition:** (i) aleatory = replication spread  percentile CIs; (ii) epistemic = nonparametric **bootstrap of the event log** (case-level resampling, B  100), re-estimating arrival/service/routing parameters and re-running a reduced replication set  combined credible intervals; report both layers.
- **Heavy tails:** candidate fits (lognormal, Weibull, gamma, GPD tail beyond p85) compared via AIC/Q–Q; applicant response and notice-with-objections explicitly heavy-tailed; p99 reported with caution (R=100 gives weak tail resolution — treat p99 as indicative only or increase R for finalists).
- **Sensitivity analysis:** one-way ±20–30% on: seasonal amplitude, objection probability and extension distribution, wait/service split for completion-only activities, D2 misclassification, no-show rate, bundling propensity; tornado chart; an intervention is called robust only if its sign of effect is stable across 80% of parameter draws.
- **Multiplicity:** Holm correction across the ~12 primary comparisons; rank policies by paired effect sizes, not point estimates.

---

## 6. Validation

1. **Face validation:** trace animations and sample simulated case traces reviewed with planners/inspectors; calendars, batching, and council-week behavior checked qualitatively.
2. **Replay/structural validation:** compare PM4Py variants and DFG of the *simulated* log vs the historical log; alignment-based fitness of simulated traces against the discovered model within 0.05 of the log's own fitness; variant-distribution distance (total variation  0.10).
3. **Distributional validation:** per case type — end-to-end duration median/p90 within CI of the 18-month empirical values (12/22/48/68/140 d medians; p90s as given); per-activity waiting quantiles vs empirical medians (calendar-adjusted); KS/Cramér–von Mises tests on simulated vs empirical duration distributions; weekly arrival counts vs fitted NHPP.
4. **Resource-utilization validation:** busy fractions per class vs log/HR-derived bounds (report intervals, not points, because start timestamps are missing): clerks 60–75% with Monday spike; inspectors 70–85% with Tue–Fri pattern; legal ~0 in council weeks; fire idle Fri/Mon. If simulated utilization is infeasible (>100%) or contradicts observed throughput, the service-time interpretation (touch vs elapsed) must be revised before any policy conclusion.
5. **Bottleneck validation:** simulated queue medians before Planning (~6 d), Legal (~7 d), Environmental (~8 d) within empirical CIs; March/May and September/November queue-spike magnitude reproduced; Monday completeness-check spike reproduced.
6. **Out-of-sample:** hold out the final 3 months (and one full peak season); fit on the remainder; predict arrivals, WIP, and cycle-time quantiles in the holdout. Additionally run a **trace-driven replay**: feed actual arrival times and attributes as exogenous inputs, compare resulting waiting times to observed (isolates model error from arrival error).
7. **Data-gap stress:** re-validate excluding all proxy-dependent metrics (objections) and confirm which decision rankings depend on the proxy (this mainly affects D9).

No policy conclusion is drawn from the twin until steps 1–6 pass their stated tolerances, and even then results are reported as *comparative estimates under model assumptions*, not optima.

## 7. Decision criteria

Primary metrics by case type (baseline E0 vs each intervention, paired CRN differences with 95% CIs):

| Criterion | Definition | Threshold / range |
|---|---|---|
| Median duration | per case type | 10% reduction for targeted types (5 d for Simple), CI excludes 0 |
| Tail duration | p90 per type | 10% reduction; p99 not worse than +10% |
| SLA compliance | statutory targets by type (placeholders, to be ratified: Simple 28 d 85%; New residential 70 d 80%; Commercial 98 d 80%; Complex 200 d 70%) | no type loses >2 pp vs baseline |
| Fairness | max district median gap 1.25× citywide; architect-size-class ratio 1.15; D3 batching must not penalize solo small applicants beyond batching window | hard guardrail |
| Utilization | core resources 65–85%; part-time pools (fire/legal) 90%; none sustained >92% | band, not point target |
| Rework | missing-doc loop rate, inspection rework, legal rework | D1: 40% relative drop in missing-doc loops; no other loop worsens >1 pp unless median gain 15% |
| Backlog | month-end WIP; share of cases older than 2× type median | WIP not >+10% vs baseline; aging share non-increasing |
| Robustness | effect across S1–S5 | net-positive in 3 of 4 stress scenarios; no scenario with >10% degradation on a guardrail metric |
| Implementability | FTE cost, transition effort, legal feasibility (qualitative score 1–5) | tie-breaker only |

Decision rule: adopt a policy (or portfolio) if it clears the primary-metric and tail thresholds **and** all fairness/utilization/backlog guardrails, is stable across 80% of sensitivity draws, and passes stress scenarios. Present a Pareto front (duration vs fairness vs cost); explicitly check D10 for interaction effects (e.g., D2 may make D4's extra inspector redundant; D1 reduces the clerk load that D7 targets). **The twin supports comparative ranking under stated assumptions; it does not certify an optimum.**

```python
# Part A3 — Service / waiting split from completion-only timestamps

# Caps from the empirical service-time summary (minutes). Used ONLY to split
# observed sojourns for exploratory analysis. These are NOT injected into the
# DES as waiting times; waiting in the DES must emerge from queues.
EMPIRICAL_SERVICE_CAPS_MIN: Dict[str, float] = {
    "Completeness check": 90, "Request missing documents": 25,
    "Planning review": 14 * 60, "Fire-safety review": 9 * 60,
    "Environmental review": 18 * 60, "Inspection scheduling": 60,
    "Site inspection": 3 * 60, "Decision drafting": 8 * 60,
    "Legal check": 16 * 60, "Issue permit": 20, "Reject application": 120,
}
# Activities whose logged "duration" is an external/waiting span, not work:
TIME_SPAN_ACTIVITIES = {"Receive missing documents", "Public-notice period"}


def add_sojourn_columns(log: pd.DataFrame) -> pd.DataFrame:
    """
    Compute sojourn-to-next-event and a *provisional* waiting/service split.

    LIMITATION (must be preserved downstream): with completion-only
    timestamps the split service = min(sojourn, cap) / waiting = remainder is
    an approximation that ignores calendar idle time and multi-touch work.
    Rows are flagged; distribution fitting uses only flagged-reliable rows
    or lifecycle-complete data.
    """
    df = log.sort_values(["case:concept:name", "time:timestamp"]).copy()
    grp = df.groupby("case:concept:name", sort=False)
    df["next_ts"] = grp["time:timestamp"].shift(-1)
    df["sojourn_days"] = (df["next_ts"] - df["time:timestamp"]).dt.total_seconds() / 86400.0

    cap_days = df["concept:name"].map(
        {k: v / 1440.0 for k, v in EMPIRICAL_SERVICE_CAPS_MIN.items()}
    )
    service = df["sojourn_days"].clip(upper=cap_days)
    service[df["concept:name"].isin(TIME_SPAN_ACTIVITIES)] = 0.0   # pure waiting span
    df["service_days_est"] = service
    df["waiting_days_est"] = df["sojourn_days"] - df["service_days_est"] if False else df["sojourn_days"] - service
    df["split_reliable"] = df["sojourn_days"].notna() & cap_days.notna()
    return df


def rework_summary(log: pd.DataFrame) -> pd.DataFrame:
    """Occurrences per (case, activity); occurrences > 1 indicate rework."""
    occ = (log.groupby(["case:concept:name", "case_type", "concept:name"])
              .size().reset_index(name="occurrences"))
    return occ[occ["occurrences"] > 1]


def routing_probabilities(log: pd.DataFrame) -> pd.DataFrame:
    """Laplace-smoothed presence probabilities per case type (branching X(tau,·))."""
    acts = ["Request missing documents", "Fire-safety review",
            "Environmental review", "Public-notice period", "Legal check",
            "Reject application"]
    presence = (log.assign(_p=1)
                   .pivot_table(index=["case:concept:name", "case_type"],
                                columns="concept:name", values="_p",
                                aggfunc="max", fill_value=0))
    presence = presence.reindex(columns=[a for a in acts if a in presence.columns],
                                fill_value=0)
    k = presence.groupby(level="case_type").sum()
    n = presence.groupby(level="case_type").count()
    return (k + 1) / (n + 2)          # Beta(1,1)-smoothed branch probabilities

# Part A4 — Nominal process model: parse the simplified tree, with fallback
# -----------------------------------------------------------------------------

NOMINAL_TREE_STRING = (
    "->( 'Submit application', "
    "*( ->( 'Completeness check', X( tau, ->( 'Request missing documents', "
    "'Receive missing documents' ) ) ), 'Completeness rework' ), "
    "+( 'Planning review', X( tau, 'Fire-safety review' ), "
    "X( tau, 'Environmental review' ) ), "
    "X( tau, 'Public-notice period' ), "
    "*( ->( 'Inspection scheduling', 'Site inspection' ), 'Inspection rework' ), "
    "'Decision drafting', X( tau, 'Legal check' ), "
    "X( 'Issue permit', 'Reject application' ) )"
)


def load_nominal_model(log: pd.DataFrame):
    """
    Try pm4py.parse_process_tree on the simplified string; fall back to
    inductive miner discovery on the real log.

    Known limitations of the simplified string (documented, not hidden):
      1. The loop operator '*' is binary (do, redo) in PM4Py trees; the
         3-argument loops in the string may fail to parse or parse with
         unintended semantics.
      2. Rework after Planning review, Legal check, and appeal is absent
         from the string and must be added as loops/guards.
      3. The tree cannot express attribute guards (requires_fire, value
         thresholds, district sensitivity), batching, or any cross-case
         behavior — routing lives in the DES, not in this model.
      4. Therefore the tree/Petri net is used for structure, replay
         validation, and conformance — never as the executable twin.
    """
    try:
        tree = pm4py.parse_process_tree(NOMINAL_TREE_STRING)
        source = "parsed_string"
    except Exception as exc:  # parse failure or version incompatibility
        print(f"[warn] parse_process_tree failed ({exc}); using inductive miner.")
        tree = pm4py.discover_process_tree_inductive(log, noise_threshold=0.2)
        source = "inductive_miner"
    net, im, fm = pm4py.convert_to_petri_net(tree)
    return tree, net, im, fm, source


def replay_conformance(log: pd.DataFrame, net, im, fm) -> dict:
    """Alignment-based conformance of the (historical or simulated) log."""
    fitness = pm4py.fitness_alignments(log, net, im, fm)
    precision = pm4py.precision_alignments(log, net, im, fm)
    return {"fitness": fitness, "precision": precision}

# Part B — Simulation engine (separate from PM4Py)
# PM4Py provides structure + validation; the DES owns state, calendars,

STREAM_NAMES = ("arrivals", "routing", "service", "applicant",
                "objection", "travel", "calendar")


@dataclass
class SeedManager:
    master_seed: int = 20260102

    def streams(self, rep: int) -> Dict[str, np.random.Generator]:
        ss = np.random.SeedSequence([self.master_seed, rep])
        children = ss.spawn(len(STREAM_NAMES))
        return {n: np.random.default_rng(c) for n, c in zip(STREAM_NAMES, children)}


# --- Arrivals: non-homogeneous Poisson process (thinning) + architect bursts

MONTH_FACTOR = {1: 1.0, 2: 1.0, 3: 1.7, 4: 1.7, 5: 1.7,
                6: 1.2, 7: 1.2, 8: 1.2,           # Jun–Aug interpolated (assumption)
                9: 1.7, 10: 1.7, 11: 1.7, 12: 1.0}
WEEKDAY_FACTOR = {0: 2.2, 1: 1.4, 2: 1.0, 3: 1.3, 4: 1.2}  # Mon..Fri; to calibrate


@dataclass
class ArrivalProcess:
    base_rate_per_day: float            # estimated from log (cases/working day)
    burst_model: Optional["ArchitectBurstModel"] = None

    def intensity(self, ts: pd.Timestamp) -> float:
        wd = WEEKDAY_FACTOR.get(ts_weekday := ts.dayofweek, 0.0)
        return self.base_rate_per_day * MONTH_FACTOR[ts.month] * wd

    def next_arrival(self, rng: np.random.Generator, t_now) -> float:
        """Lewis–Shedler thinning for the NHPP (returns absolute day offset)."""
        lam_max = (self.base_rate_per_day * max(MONTH_FACTOR.values())
                   * max(WEEKDAY_FACTOR.values()) * 1.2)
        t = 0.0
        while True:
            t += rng.exponential(1.0 / lam_max)
            day = t_now + t
            if rng.random() < self.intensity(day) / lam_max:
                return t


@dataclass
class ArchitectBurstModel:
    """Correlated batch submissions of the top-20 architects (~31% of volume);
    also carries the shared document-quality frailty used by RoutingModel."""
    top_share: float = 0.31
    batch_size_dist: Tuple = (1, 2, 3, 4)      # placeholder empirical pmf

    def draw_batch(self, rng) -> Tuple[str, int]:

class ResourceCalendar:
    """Weekly templates + exceptions. Council weeks and holidays are EXOGENOUS
    inputs (HR-derived), not inferred as exact event-log facts."""

    WEEKLY = {
        "clerk":     {d: [(8, 16)] for d in range(5)},
        "planner":   {d: [(9, 17)] for d in range(5)},
        "fire":      {1: [(9, 17)], 2: [(9, 17)], 3: [(9, 17)]},   # Tue–Thu
        "env":       {d: [(9, 17)] for d in range(5)},   # x0.6 effective duty
        "inspector": {1: [(9, 17)], 2: [(9, 17)], 3: [(9, 17)], 4: [(9, 17)]},
        "legal":     {d: [(9, 17)] for d in range(5)},
    }

    def __init__(self, holidays: set, council_weeks: set, peak_months: set):
        self.holidays, self.council_weeks, self.peak_months = (
            holidays, council_weeks, peak_months)

    def is_open(self, rclass: str, ts: pd.Timestamp) -> bool:
        if ts.date() in self.holidays:
            return False
        if rclass == "legal" and ts.isocalendar().week in self.council_weeks:
            return False
        return True

    def effective_fte(self, rclass: str, ts: pd.Timestamp) -> float:
        base = {"clerk": 5, "planner": 8, "fire": 2, "env": 3 * 0.6,
                "inspector": 4, "legal": 2}[rclass]
        if rclass == "inspector" and ts.month in self.peak_months:
            base += 1 * 0.8          # D4 temporary inspector (0.8 effective)
        return base
```

**Notes on the skeleton.** `pm4py.format_dataframe` is the only ingestion step (there is no `pm4py.read_csv`); the performance DFG is treated as a structure-level aggregate because its edge statistics conflate waiting and service. The simplified tree string is parsed opportunistically with `pm4py.parse_process_tree` but is not trusted: its 3-ary loops, missing appeal/legal rework, and inability to express attribute guards mean the DES implements the intended semantics explicitly, while PM4Py provides the replay-based validation layer. Arrivals are implemented (NHPP thinning) to show the intended non-stationary mechanism; routing, calendars/pools, batching, applicant behavior, and the experiment runner are structured placeholders with their estimation and policy hooks already defined.
