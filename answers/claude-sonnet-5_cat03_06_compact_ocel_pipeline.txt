## 1. Modeling assumptions

- **Object types (capitalized, singular)**: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. Capitalization is fixed and used consistently in `objects['ocel:type']` and `relations['ocel:type']`.
- **E2O qualifier vocabulary** (event  object role):
  `created_order`, `target_order`, `added_item`, `reserved_item`, `stock_reserved_for_order`, `packed_package`, `packed_item`, `order_fulfilled_by_package`, `dispatch_delivery`, `dispatched_package`, `issued_invoice`, `billed_order`, `recorded_payment`, `settles_invoice`, `confirmed_delivery`, `closed_order`.
  Each qualifier names the *role the object plays in that specific event*, not a generic "involves" link.
- **O2O direction convention**: the first object (`ocel:oid`) is the *container/actor*, the second (`ocel:oid_2`) is the *contained/target*: `OrderItem (contains)`, `PackageItem (packs)`, `DeliveryPackage (carries)`, `InvoiceOrder (bills)`, `PaymentInvoice (partially_settles / completes_settlement)`.
- **Direct vs. propagated relations**: Only events for which the narrative *explicitly* states a joint/cross-order fact (`Reserve Stock`, `Pack Package`, `Issue Invoice`) are given direct E2O links to `Order`. Downstream logistics events (`Dispatch Package`, `Confirm Delivery`) are linked only to `Package`/`Delivery`, and `Record Payment` is linked only to `Payment`/`Invoice`. Order- or Item-level effects of these later events must be *derived* through the O2O graph (`DeliveryPackageItemOrder`, `PaymentInvoiceOrder`), never asserted directly.
- **Preventing propagation-as-fact confusion**: `relations` contains *only* source-observed E2O facts; any Order/Item attribution of Dispatch/Confirm/Payment is computed at analysis time from `o2o`, kept in separate derived DataFrames, and never written back into `relations`. Comments in the code mark this boundary explicitly.
- **Version-dependent assumption**: `OCEL` is imported from `pm4py.objects.ocel.obj`; `pm4py.discover_otg` / `pm4py.discover_etot` are assumed available in the installed pm4py (2.7-class API). This import line and these two calls are isolated so they can be swapped without touching the data model.

# =========================================================================

flattened_logs = {}
dfgs = {}
skeletons = {}

for ot in target_types:
    flat = pm4py.ocel_flattening(ocel, ot)
    flattened_logs[ot] = flat
    dfg, start_acts, end_acts = pm4py.discover_dfg(flat)
    dfgs[ot] = {"dfg": dfg, "start_activities": start_acts, "end_activities": end_acts}
    skeletons[ot] = pm4py.discover_log_skeleton(flat)

# =========================================================================
# I. Object-centric structures
# =========================================================================
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)                      # VERSION-SENSITIVE call
etot = pm4py.discover_etot(ocel)                    # VERSION-SENSITIVE call
ocpn = pm4py.discover_oc_petri_net(ocel)
interactions_summary = pm4py.ocel_objects_interactions_summary(ocel)

print("\nOC-DFG discovered.")

print("Object-centric Petri net discovered.")
print("\nObject interactions summary:\n", interactions_summary)

# =========================================================================
# J. Optional visualizations (commented out; no display/file I/O by default)

# =========================================================================

## 3. Data-model audit

**Object types and objects**

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

**O2O qualifiers and cardinality**

| Qualifier | From  To | Count |
|---|---|---|
| contains | Order  Item | 3 |
| packs | Package  Item | 3 |
| carries | Delivery  Package | 2 |
| bills | Invoice  Order | 2 |
| partially_settles | Payment  Invoice | 1 |
| completes_settlement | Payment  Invoice | 1 |

**Activities and object types touched**

| Activity | Object types touched |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Item, Order |
| Pack Package | Package, Item, Order |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery |
| Close Order | Order |

**Most consequential event**: `e7` (`Pack Package`, P1) touches five objects across three types (`Package`, two `Item`s, two `Order`s). It is the single event that structurally encodes "P1 combines items from two Orders," and it is the primary source of **convergence** (one event shared by O100 and O200) as well as **divergence** (Order-flattened traces will show `Pack Package` twice for O100 but once for O200, at different implied "positions").

## 4. Expected flattened behavior

**Order** (`O100`, `O200`):
- Approximate trace shape: O100  `Create Order, Add Item, Add Item, Reserve Stock, Pack Package, Pack Package, Issue Invoice, Close Order` (8 events); O200  `Create Order, Add Item, Reserve Stock, Pack Package, Issue Invoice, Close Order` (6 events).
- Copied shared events: `e6` (Reserve Stock), `e7` (Pack Package), `e11` (Issue Invoice) appear identically in both traces (convergence duplication).
- Omitted lifecycle aspects: dispatch, delivery confirmation, and payment are invisible because no direct E2O link was modeled from those events to `Order`.
- Likely DFG edges: `Create OrderAdd Item`, `Add ItemAdd Item`/`Add ItemReserve Stock`, `Reserve StockPack Package`, `Pack PackagePack Package`/`Pack PackageIssue Invoice`, `Issue InvoiceClose Order`.
- Misleading interpretation: the flattened view suggests Orders "finish" right after invoicing, hiding that closure actually happens ~23 hours later, after full delivery and payment—an artifact of scope choice, not of the business process.

**Package** (`P1`, `P2`):
- Trace shape: `Pack Package, Dispatch Package` for both — very short, two-event traces.
- No shared/copied events across packages (each package has its own Pack/Dispatch event).
- Omitted: confirmation of delivery (linked to Delivery, not Package) and any order/item context.
- DFG edge: `Pack PackageDispatch Package` only.
- Misleading interpretation: the Package view looks like a trivial two-step process, hiding that P1 is operationally significant (multi-order package) while P2 is not — that fact only surfaces via O2O, not via the flattened Package log itself.

**Delivery** (`D1`, `D2`):
- Trace shape: `Dispatch Package, Confirm Delivery` — again two events each.
- DFG edge: `Dispatch PackageConfirm Delivery`.
- Misleading interpretation: identical shape for D1/D2 hides the ~23-hour delay difference (D1 confirmed same day, D2 confirmed next day) unless duration statistics are separately computed from timestamps.

**Invoice** (`V1`):
- Single trace (one Invoice object): `Issue Invoice, Record Payment, Record Payment`.
- DFG edges: `Issue InvoiceRecord Payment`, `Record PaymentRecord Payment`.
- Misleading interpretation: because both payments and the invoice belong to one object, the flattened log cannot distinguish that the invoice covers *two* orders — it looks like an ordinary single-order invoice-payment cycle.

**Why Payment flattening is weak**: each Payment object (`M1`, `M2`) participates in exactly one event (`Record Payment`). Flattening on `Payment` yields two single-activity traces with no internal transitions, so DFG discovery produces isolated nodes with no edges and log-skeleton discovery has nothing non-trivial to learn (all constraints degenerate to "exactly one occurrence"). The interesting behavior — that M1 and M2 jointly and partially settle V1, which in turn bills two orders — lives entirely in the O2O graph and in the *Invoice* flattening, not in the Payment object's own lifecycle.

## 5. Expected object-centric structures

- **OC-DFG**: per-object-type annotated edges (e.g., `Reserve StockPack Package` for both `Order` and `Item` types) with visibly higher object counts at the convergence points `Reserve Stock`, `Pack Package`, and `Issue Invoice`, because O100 and O200 both pass through the same underlying events (P1's dual-order nature surfaces as elevated Order-object counts on these edges relative to purely single-order edges like `Add Item`).
- **OTG (object graph)**: should render P1 as a bridge node connected simultaneously to I1, I3, and (transitively/directly, depending on construction) to O100 and O200; V1 as a hub connected to O100, O200, M1, and M2; M1 and M2 themselves are only reachable from each other *through* V1, never directly.
- **ET–OT graph**: a matrix showing, e.g., `Pack Package` with nonzero weight against `Package`, `Item`, and `Order` (weight 2 on `Order` due to P1's dual attribution), while `Record Payment` has nonzero weight only against `Payment` and `Invoice` — visually confirming the "no direct PaymentOrder" modeling choice.
- **Object-centric Petri net**: expected to show separate place-sets per object type synchronized at shared transitions; `Pack Package` should be a transition consuming/producing tokens in `Package`, `Item`, *and* `Order` places simultaneously for the P1 case, visibly requiring two Order-tokens (O100, O200) at once — a canonical convergence pattern. Multiple structurally valid nets can represent this synchronization (e.g., different independence/qualifier groupings), so no single discovered net should be treated as the unique ground truth.
- **Object-interactions summary**: should report high co-occurrence for (O100, O200) — shared across Reserve Stock, Pack Package, and Issue Invoice (3 shared events) — and for (I1, I3) — shared across Reserve Stock and Pack Package (2 events) — while (M1, M2) never co-occur in any event (0), demonstrating that their relatedness is purely O2O-mediated through V1.

## 6. Modeling alternatives

1. **Source-minimal relations**: Link each event only to the grammatically explicit object(s) in the sentence, dropping even the "relates to both Orders" annotations on `Reserve Stock`/`Pack Package`/`Issue Invoice` (i.e., treat those as Item/Package/Invoice-only events). *Effect*: Order-flattened traces shrink further (lose Reserve Stock, Pack Package, Issue Invoice entirely), OC-DFG shows almost no Order-level convergence, and the "P1 spans two Orders" fact becomes visible *only* via O2O traversal, never in event-level views — same business story, much less directly observable in per-type discovery.
2. **Full operational involvement**: Additionally attach `Order`/`Item` to `Dispatch Package`, `Confirm Delivery`, and `Record Payment` by transitively resolving the O2O chain at data-construction time. *Effect*: Order-flattened traces become full end-to-end lifecycles (through delivery and payment), OC-DFG gains many more edges and higher convergence counts, but the `relations` table stops being a faithful record of what the source systems actually logged — the same story now looks like a much more tightly integrated process than it operationally was.
3. **O2O-propagated analytical relations computed on demand**: Keep `relations` exactly as constructed here (source-minimal-plus-explicit-joint-facts) and derive extended object sets *only inside analysis code* (e.g., a helper that joins `relations` with `o2o` to attribute Payments to Orders for a revenue report), never persisting them back into `relations`. *Effect*: discovery on the canonical OCEL stays conservative and audit-friendly; richer views are reproducible and clearly labeled as derived, at the cost of needing bespoke derivation logic per question asked.

## 7. Failure modes

1. **Relation inflation**: attaching every transitively reachable object to every event (e.g., linking `Confirm Delivery` to Item, Order, and Invoice as well as Delivery) collapses discriminative power — nearly every event touches nearly every object, and OC-DFGs/interaction summaries become uniformly dense and uninformative.
2. **Missing direct E2O links**: forgetting to relate `e6`/`e7`/`e11` to *both* O100 and O200 (modeling them as single-order events) silently erases the documented joint/cross-order nature of stock reservation, packing, and invoicing.
3. **Treating O2O propagation as observation**: writing a derived fact such as "Record Payment  O100" directly into `relations` because Payment settles an Invoice that bills O100, when the source never recorded a Payment-to-Order link — this fabricates evidence and breaks the audit trail between "observed" and "inferred."
4. **Duplicate shared events after flattening**: naively counting activity frequencies on the Order-flattened log double-counts `e6`, `e7`, `e11` (once per Order trace), inflating apparent frequency of joint activities as if they happened twice.
5. **Ambiguous payment allocation**: M1 (100) and M2 (150) jointly settle V1, which bills O100 and O200 together; there is no source fact splitting the 250 total between the two orders, so any per-order revenue figure is an analytical assumption, not a modeled fact.
6. **Overly short Payment traces**: flattening on `Payment` yields degenerate single-event traces, and any DFG/skeleton mined from them may be misreported as "Payments have no discoverable behavior," rather than correctly interpreted as "Payment is the wrong granularity for lifecycle discovery here."
7. **Constructor/API version mismatch**: `OCEL` import path, required column names (e.g., `ocel:timestamp` vs. legacy `ocel:time:timestamp`), and availability of `pm4py.discover_otg`/`pm4py.discover_etot` vary across pm4py releases; blindly copying this code against an incompatible version will raise `ImportError`/`AttributeError` unrelated to the data model.
8. **False total order for same-time events**: although this dataset avoids timestamp ties by design, any log with two events sharing an identical timestamp risks having pandas/pm4py impose an arbitrary tie-break order (row order or lexicographic eid order), which can silently misrepresent causal precedence — code and downstream reasoning must not assume row order encodes causality when timestamps tie.
9. **Object-type capitalization drift**: inconsistent casing (`"order"` vs `"Order"`) introduced during manual data entry silently creates phantom extra object types, fragmenting `ocel_object_type_activities` and per-type flattening results.

## 8. Final semantic checks

1. `relations[relations["ocel:eid"] == "e7"]` lists exactly the five objects `{P1, I1, I3, O100, O200}` — confirming Pack Package's cross-order scope.
2. `o2o` shows `P1` with `packs` edges to both `I1` and `I3`, and `o2o`/`relations` together confirm `I1  O100` and `I3  O200` — jointly verifying "P1 combines items from two Orders."
3. `o2o[o2o["ocel:qualifier"] == "bills"]` contains exactly two rows, both with `ocel:oid == "V1"`, targeting `O100` and `O200` — no other invoice exists in `objects`.
4. `o2o[o2o["ocel:oid"].isin(["M1","M2"])]` targets only `V1`; no row anywhere links `M1` or `M2` directly to an `Order` — consistent with "partial payments settling V1," not orders.
5. For every row in `relations`, the joined `ocel:activity`/`ocel:timestamp` from `events` match exactly (validated programmatically; spot-checkable manually by filtering any `eid`).
6. `relations[relations["ocel:activity"] == "Close Order"]` touches only `Order`-typed objects (`O100`, `O200`) — never Item/Package/Delivery/Invoice/Payment.
7. Every `ocel:oid` appearing in `relations` or `o2o` also appears in `objects["ocel:oid"]` (no orphan references, spot-checkable via set difference).
8. `objects["ocel:type"].value_counts()` sums to 12 and matches the narrative counts (2 Orders, 3 Items, 2 Packages, 2 Deliveries, 1 Invoice, 2 Payments).
