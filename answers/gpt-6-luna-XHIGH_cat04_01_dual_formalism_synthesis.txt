# 1. Assumptions and Interpretation

1. Each visible event records an activity’s completion. A trace is therefore a linearization of the activities’ start/finish behavior; it does not record start times or durations.
2. The risk decision is represented by an exclusive choice after Analyze Root Cause: either Supervisor Review, or both Quality Review and Regulatory Review. The high-risk reviews have no order constraint between them.
3. Supplier selection is represented structurally as an exclusive choice between a silent branch and Consult Supplier. This enforces zero or one consultation in any one trace. The choice is not tied to case data, so the model cannot require consultation for a particular case.
4. Inspection outcome is not an event label. The loop abstracts a failed inspection as the decision to take the Adjust Parameters redo branch, and a passing inspection as the decision to exit after Inspect Trial. This captures the intended visible pattern, but cannot distinguish an actual pass from a failure in a trace.
5. No activity is duplicated in either model. The loop revisits the same Execute Trial and Inspect Trial activity nodes.
6. “May overlap” means true concurrency is permitted: absent a precedence edge, either activity may proceed while the other is unfinished. A recorded trace still orders their completion events.
7. The POWL model uses a strict partial order for the independent work and synchronization dependencies. The process tree uses a conservative under-approximation: it joins all pretrial work, including approvals and any selected supplier consultation, before allowing the trial cycle.
8. The models do not encode risk, supplier selection, or inspection outcomes as data attributes. Their control-flow alternatives describe which traces are admitted without binding a particular branch to a particular case.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D1 | Register Deviation | Contain Material and Analyze Root Cause | Precedence to both; concurrent branches | Both work streams follow registration and may progress independently. |
| D2 | Contain Material | Plan Verification | Precedence | Planning may start only after containment completes. |
| D3 | Analyze Root Cause | Design Corrective Action | Precedence | Design may start only after root-cause analysis completes. |
| D4 | Analyze Root Cause | Approval route choice | Precedence | The low/high risk route is selected after analysis. |
| D5 | Approval route choice | Supervisor Review OR (Quality Review AND Regulatory Review) | Exclusive choice; high-route concurrency | Low risk takes the supervisor branch. High risk takes both reviews, in either completion order. |
| D6 | Analyze Root Cause | Optional Consult Supplier | Precedence and optionality | Consultation, if selected, follows analysis and occurs at most once. |
| D7 | Design Corrective Action AND Plan Verification | Execute Trial | Synchronizing precedence | Both work products must be complete before the first trial. |
| D8 | Approval route and trial cycle | Each other | No precedence between them | Approvals may overlap trial work; both are independently required before release. |
| D9 | Trial iteration | Execute Trial → Inspect Trial | Sequence | Each iteration executes before its inspection. |
| D10 | Failed Inspect Trial | Adjust Parameters → next Execute Trial | Loop/redo | A failed inspection triggers adjustment and another complete trial cycle. |
| D11 | Passing Inspect Trial | Trial-cycle exit | Loop exit | A passing inspection ends the loop; adjustment cannot follow the final passing inspection. |
| D12 | Passing Inspect Trial, selected approval route, and selected supplier consultation | Release Material | Synchronizing precedence | Release waits for the successful trial and all obligations that apply to the case. |
| D13 | Release Material | Archive Case | Precedence | Archival follows release. |

# 3. PM4Py Process-Tree Model

Compact expression (SEQ is sequence, AND is parallel, XOR is exclusive choice, and LOOP has do, redo, and exit children):

~~~text
SEQ(
  Register Deviation,
  AND(
    SEQ(Contain Material, Plan Verification),
    SEQ(
      Analyze Root Cause,
      AND(
        Design Corrective Action,
        XOR(Supervisor Review, AND(Quality Review, Regulatory Review)),
        XOR(τ, Consult Supplier)
      )
    )
  ),
  LOOP(
    SEQ(Execute Trial, Inspect Trial),
    Adjust Parameters,
    τ
  ),
  Release Material,
  Archive Case
)
~~~

Self-contained construction:

~~~python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def activity(label):
    return ProcessTree(label=label)


def silent():
    return ProcessTree(label=None)


def operator(op, *children):
    parent = ProcessTree(operator=op)
    for child in children:
        parent.children.append(child)
        child.parent = parent
    return parent


containment_stream = operator(
    Operator.SEQUENCE,
    activity("Contain Material"),
    activity("Plan Verification"),
)

approval_choice = operator(
    Operator.XOR,
    activity("Supervisor Review"),
    operator(
        Operator.PARALLEL,
        activity("Quality Review"),
        activity("Regulatory Review"),
    ),
)

supplier_choice = operator(
    Operator.XOR,
    silent(),
    activity("Consult Supplier"),
)

root_cause_stream = operator(
    Operator.SEQUENCE,
    activity("Analyze Root Cause"),
    operator(
        Operator.PARALLEL,
        activity("Design Corrective Action"),
        approval_choice,
        supplier_choice,
    ),
)

trial_cycle = operator(
    Operator.SEQUENCE,
    activity("Execute Trial"),
    activity("Inspect Trial"),
)

trial_loop = operator(
    Operator.LOOP,
    trial_cycle,
    activity("Adjust Parameters"),
    silent(),
)

tree = operator(
    Operator.SEQUENCE,
    activity("Register Deviation"),
    operator(
        Operator.PARALLEL,
        containment_stream,
        root_cause_stream,
    ),
    trial_loop,
    activity("Release Material"),
    activity("Archive Case"),
)
~~~

The tree represents registration, the two independent initial streams, the planning/design prerequisites, the risk choice, optional consultation, and repeated trial cycles. Its approximation is the parallel join before the trial loop: it requires the selected approval route and selected supplier consultation to finish before any trial starts. The intended behavior permits both to overlap trial work, so the tree excludes those valid interleavings. This is a conservative under-approximation. The tree also cannot bind its approval or supplier choices to risk or case data, nor can it determine whether an inspection passed; those conditions are abstracted as branch choices.

# 4. PM4Py POWL Model

Compact description (PO means strict partial order; edges are precedence constraints; LOOP uses its first child as the do part and its second as the redo part):

~~~text
PO(
  nodes = {
    Register, Contain, Analyze, Plan, Design, ApprovalChoice,
    SupplierChoice, TrialLoop, Release, Archive
  };
  edges = {
    Register < Contain, Register < Analyze,
    Contain < Plan,
    Analyze < Design, Analyze < ApprovalChoice, Analyze < SupplierChoice,
    Plan < TrialLoop, Design < TrialLoop,
    TrialLoop < Release, ApprovalChoice < Release,
    SupplierChoice < Release, Release < Archive
  }
)

ApprovalChoice = XOR(
  Supervisor,
  PO(nodes={Quality, Regulatory}; edges={})
)
SupplierChoice = XOR(τ, ConsultSupplier)
TrialLoop = LOOP(
  PO(nodes={Execute, Inspect}; edges={Execute < Inspect}),
  Adjust
)
~~~

Self-contained construction:

~~~python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")

supervisor = Transition(label="Supervisor Review")
quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")
high_risk_reviews = StrictPartialOrder([quality, regulatory])
approval_choice = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor, high_risk_reviews],
)

consult = Transition(label="Consult Supplier")
supplier_choice = OperatorPOWL(
    operator=Operator.XOR,
    children=[SilentTransition(), consult],
)

execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
trial_iteration = StrictPartialOrder([execute, inspect])
trial_iteration.order.add_edge(execute, inspect)

adjust = Transition(label="Adjust Parameters")
# The do part is one execute-inspect iteration; adjustment is the redo part.
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_iteration, adjust],
)

release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

powl = StrictPartialOrder([
    register,
    contain,
    analyze,
    plan,
    design,
    approval_choice,
    supplier_choice,
    trial_loop,
    release,
    archive,
])

powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, approval_choice)
powl.order.add_edge(analyze, supplier_choice)
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(approval_choice, release)
powl.order.add_edge(supplier_choice, release)
powl.order.add_edge(release, archive)
~~~

Within the high-risk route, Quality Review and Regulatory Review have no edge, so either can complete first and they may overlap. At the root, Contain Material and Analyze Root Cause are unconstrained relative to each other after registration. Their downstream planning and analysis-derived work can also interleave subject to their respective incoming edges. Design, the approval choice, and supplier choice are mutually unconstrained after analysis. TrialLoop is constrained by Plan Verification and Design Corrective Action, but has no order constraint with the approval or supplier branches; all three branches meet at Release Material. Thus every intentionally unconnected pair may overlap, while every listed edge preserves the required precedence.

# 5. Behavioral Witnesses

Trace labels are visible activity completions. For the last two forbidden witnesses, the stated pass result and supplier selection are case facts omitted from the visible labels, as required by the activity-based abstraction. “Accept” and “Reject” refer to the model’s visible trace language.

| Trace ID | Visible trace | Intended verdict | Process-tree verdict | POWL verdict | Reason |
|---|---|---|---|---|---|
| A1 | Register Deviation, Contain Material, Analyze Root Cause, Plan Verification, Design Corrective Action, Supervisor Review, Execute Trial, Inspect Trial, Release Material, Archive Case | Allowed | Accept | Accept | Low-risk route; both prerequisites precede one successful trial, then release and archive. |
| A2 | Register Deviation, Analyze Root Cause, Contain Material, Design Corrective Action, Plan Verification, Quality Review, Regulatory Review, Execute Trial, Inspect Trial, Release Material, Archive Case | Allowed | Accept | Accept | High-risk route completes both reviews before the trial; Quality completes before Regulatory. |
| A3 | Register Deviation, Contain Material, Analyze Root Cause, Consult Supplier, Plan Verification, Design Corrective Action, Supervisor Review, Execute Trial, Inspect Trial, Release Material, Archive Case | Allowed | Accept | Accept | Supplier consultation is selected, follows analysis, and completes before release. |
| A4 | Register Deviation, Contain Material, Analyze Root Cause, Plan Verification, Design Corrective Action, Supervisor Review, Execute Trial, Inspect Trial, Adjust Parameters, Execute Trial, Inspect Trial, Release Material, Archive Case | Allowed | Accept | Accept | The first inspection is stipulated to fail and the second to pass; adjustment separates the two iterations. |
| A5 | Register Deviation, Contain Material, Analyze Root Cause, Plan Verification, Design Corrective Action, Execute Trial, Inspect Trial, Regulatory Review, Quality Review, Release Material, Archive Case | Allowed | Reject | Accept | High-risk approvals finish after the trial has started. POWL permits that overlap; the tree’s pretrial join forbids it. |
| F1 | Register Deviation, Analyze Root Cause, Plan Verification, Contain Material, Design Corrective Action, Supervisor Review, Execute Trial, Inspect Trial, Release Material, Archive Case | Forbidden | Reject | Reject | Earliest violation: Plan Verification completes before Contain Material, despite the required containment-before-planning dependency. |
| F2 | Register Deviation, Contain Material, Analyze Root Cause, Plan Verification, Design Corrective Action, Supervisor Review, Execute Trial, Inspect Trial, Adjust Parameters, Execute Trial, Inspect Trial, Release Material, Archive Case | Forbidden | Accept | Accept | The first Inspect Trial is stipulated to have passed. Adjust Parameters after that pass is forbidden, but neither model sees the hidden outcome and both interpret the event pattern as a failed iteration followed by a retry. |
| F3 | Register Deviation, Contain Material, Analyze Root Cause, Plan Verification, Design Corrective Action, Supervisor Review, Execute Trial, Inspect Trial, Release Material, Archive Case | Forbidden | Accept | Accept | Case data stipulates that supplier consultation was selected. The earliest violation is Release Material without completed Consult Supplier. The models cannot bind the silent supplier branch to that hidden selection. |

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and root-cause analysis follow registration and can overlap. | Parallel branches after registration. | Both follow Register; no edge orders them. | Neither over- nor under-constrained for these activities. | Both permit teams to begin independent work promptly. |
| Split dependencies into planning/design | Planning follows containment; design follows root-cause analysis. | Each is sequenced in its corresponding branch. | Explicit Contain→Plan and Analyze→Design edges. | Both represent the split prerequisites. | Work products cannot be planned or designed before their source work completes. |
| Risk route | Low risk requires Supervisor; high risk requires both Quality and Regulatory, in either order. | XOR between supervisor and a parallel pair. | XOR between supervisor and a partial order with both reviews and no edge. | Control-flow choice is represented; binding the choice to risk data is underconstrained in both. | Trace replay can check route shape, but case data is needed to check route correctness. |
| Approval/trial overlap | Trial waits for design and planning; approvals may continue during trial. | Approval branch must complete at the pretrial parallel join. | Approval branch and TrialLoop are independent until both precede Release. | Tree overconstrains; POWL represents the intended overlap. | Tree rejects efficient schedules with approvals finishing during trial. |
| Optional supplier consultation | Zero or one consultation, after analysis if chosen, complete before release; it may overlap trial. | XOR optional branch; joins before trial. | Silent-or-consult choice, constrained after analysis and before release. | Both cannot bind selection to case data; tree also overconstrains consultation relative to trial. | Tree may delay trial; both can miss a required consultation if the case’s selection is hidden. |
| Repeat-until behavior | Execute then inspect; failure leads to adjustment and a new cycle; pass exits; no adjustment after pass. | Do/redo/exit loop with adjustment between cycles. | Execute-before-inspect do-part with adjustment as redo. | Iteration shape is represented; outcome-conditioned exit is underconstrained in both. | A trace can look structurally valid while violating the real inspection result. |
| Release synchronization | Release waits for a passing inspection, selected route, and selected consultation. | All pretrial branches join before trials, then trial completes before release. | Explicit predecessor edges from trial, approvals, and supplier choice to release. | POWL models the synchronization directly. Both lack hidden outcome/selection conditions. | POWL allows concurrency while still enforcing a final join; external data checks remain necessary. |
| Duplicate-label risk | Activity labels identify event classes; repetitions arise from loop iterations. | One node per visible label; loop revisits trial nodes. | One transition per visible label; loop revisits its nodes. | No deliberate duplicate visible labels. Net conversion or later edits can still introduce multiple transitions with the same label. | Label-based replay may conflate distinct transition instances; inspect converted nets and preserve source-node mappings. |

# 7. Preferred Representation and Validation Plan

I would use POWL as the canonical representation. Its partial-order edges state the containment/planning, analysis/design, trial prerequisites, and release synchronization directly. It allows approvals and supplier consultation to overlap the trial while preserving the required join at release. The process tree remains a useful conservative fallback when a tree representation is required, with its lost schedules documented.

A concrete validation plan:

1. Convert each model to an accepting Petri net where the installed PM4Py version supports the conversion. Retain the initial and final markings returned by conversion.
2. Run soundness checking on each converted net with PM4Py’s check_soundness interface, and inspect diagnostics rather than treating successful conversion as evidence of semantic fidelity.
3. Generate bounded or sampled playouts, limiting the trial loop to a small number of retries and trace length. Confirm that generated traces begin with registration, end with archive, preserve required edges, and never place adjustment outside trial iterations.
4. Replay the five positive witnesses and three negative witnesses against both models or their nets. Include F1 as a dependency violation; document that F2 and F3 are expected to pass visible-label replay because their forbidden facts are hidden.
5. Inspect silent behavior and labels explicitly. Confirm that the supplier omission is the only intended silent supplier alternative, that loop exit does not skip an Execute/Inspect iteration, and that each source model has one visible node per activity label. After conversion, inspect any same-labeled net transitions and any additional silent transitions before relying on label-based replay.
6. Compare POWL and tree results on A5 to confirm the known approximation boundary: POWL accepts the approval/trial overlap, while the conservative tree rejects it.

These checks can find construction errors and expose some semantic mismatches, but bounded playout cannot prove all behaviors. Soundness establishes properties of the converted net, not fidelity to hidden case attributes or inspection outcomes. Trace replay over activity labels also cannot determine whether an inspection passed or whether the supplier branch was required for a particular case.

# 8. Final Self-Critique

1. The process-tree approximation delays trials until approvals and any selected supplier consultation complete, excluding intended schedules that could shorten case resolution.
2. The loop models failure and pass as control-flow choices rather than observed outcomes, so it admits adjustment after a real passing inspection and can exit after a real failure.
3. Both models admit or omit supplier consultation without knowing the case-data selection; their visible trace languages alone cannot validate that case-specific obligation.
