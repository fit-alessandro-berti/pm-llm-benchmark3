## 6. Candidate Site B intervention

**Eligibility rules:** Parallel execution allowed ONLY when `originals_required = false` (legally and operationally verified at Register via document-channel flag + case-type check). Initially also require `legal_review_required = false` and `complexity != high` to protect tail. Approx 20-25% pilot volume. All other cases follow statutory path.

**Statutory prerequisites that remain mandatory:** `Register -> Originals Receipt -> Document Check` when originals_required=true; `Register -> Identity Check`; `{Identity Check, Document Check} -> Assessment -> (Legal Review if required) -> Approve/Reject -> Notify`. `Request Supplement -> Document Check -> Assessment -> Legal Review` loop preserved.

**Concurrency allowed:** For eligible cases, after Register, create Identity Check (assigned to identity pool) and Document Check (assigned to document pool) concurrently. For ineligible, create Identity Check + `Awaiting Originals` placeholder; Document Check task is NOT created until Originals Receipt logged with proof (scan/tracking). Assessment task is created but remains `blocked: awaiting verification` until both prerequisites complete (POWL partial order enforces).

**Queue and WIP controls:** Per-role WIP caps: identity 6 per reviewer (copy A but per-role), document 5 per reviewer, assessment 4 per assessor, legal 4 per reviewer. Global CONWIP limit per stratum. Pull: Assessment signals capacity (kanban) to upstream; Document Check prioritizes cases where Identity Check already complete to maximize join. Daily huddles introduced as separate stratum-controlled treatment, not bundled.

**Resource responsibilities:** No cross-role execution; handoff via worklist, not task ownership transfer. Identity reviewers own Identity Check only; Document reviewers own Document Check and Supplement; Assessors own Assessment; Legal owns Legal Review. Float only for logging support.

**Legal-review and supplement loops:** Legal Review may issue Request Supplement only after reviewing both verifications; Supplement triggers Document Check rework in same document pool with priority flag; requires re-Assessment and re-Legal if originally legal. Bypass disabled.

**Logging requirements:** True start = first field edit/API call/work object open; true complete = submit. Prohibit back-entry >24h without supervisor flag. System flag `is_blocked_awaiting_originals` prevents Document start timestamp gaming. Overlap measured as `service_interval_overlap / min(service_lengths)`.

**POWL-style description:**

```
POWL model SiteB_Candidate:
  Leaves: Register, IdentityCheck, AwaitOriginals, OriginalsReceipt, DocumentCheck, Assessment, LegalReview, RequestSupplement, Approve, Reject, Notify
  Choice(caseType):
    Branch ELIGIBLE (digital, no originals, non-legal, low/med complexity):
      PO = PartialOrder(
        nodes = {Register, IdentityCheck, DocumentCheck, Assessment, Approve/Reject, Notify}
        order = {Register < IdentityCheck, Register < DocumentCheck, IdentityCheck < Assessment, DocumentCheck < Assessment, Assessment < {Approve,Reject} < Notify}
      )
    Branch INELIGIBLE_ORIGINALS:
      PO = PartialOrder(
        nodes = {Register, IdentityCheck, AwaitOriginals, OriginalsReceipt, DocumentCheck, Assessment, LegalReview?, Approve/Reject, Notify}
        order = {Register < IdentityCheck, Register < AwaitOriginals < OriginalsReceipt < DocumentCheck, IdentityCheck < Assessment, DocumentCheck < Assessment}
      )
      Loop after Assessment if LegalRequired:
        LoopDo: LegalReview -> Choice(RequestSupplement -> DocumentCheck -> Assessment -> LegalReview, Exit)
  Operationalization: Order edges enforce Assessment waits for both identity and document verification; DocumentCheck < Assessment; OriginalsReceipt < DocumentCheck in ineligible branch.
  Resource tags: IdentityCheck@identity_pool, DocumentCheck@document_pool, Assessment@assessor_pool, LegalReview@legal_pool
  WIP constraints external to POWL, enforced by worklist.
```

Partial-order relation set (must hold in all traces):
- `Register < Identity Check`
- `Register < Originals Receipt` (when required) `< Document Check`
- `Identity Check < Assessment`, `Document Check < Assessment`
- `Assessment < Legal Review` (when caseType=public/high-value)
- `Legal Review < Request Supplement < Document Check < Assessment` (loop)
- `Assessment|Legal Review < {Approve,Reject} < Notify`

How pilot separates mechanism failure from implementation failure (198 words):

The 2×2 (concurrent vs sequential × huddles) plus IT dual-worklist logging isolates mechanisms. Implementation failure is flagged when `assigned_parallel=1` but `true_overlap0`, DFG shows `Register->Document` creation without service start until Identity completes, or back-entry audit fails; then waiting_before_assessment does not move despite assignment. Bottleneck-shift failure is flagged when eligible subgroup waiting improves but ineligible stratum waiting, legal queue length, and p90 worsen, and global WIP rises, indicating true overlap occurred but capacity was non-transportable. Mechanism failure (theory invalid) is when even with verified true_overlap>50% and WIP caps respected, median waiting and cycle time for eligible show <1h gain and heterogeneity shows no effect even for low-complexity digital cases, implying workload independence does not translate to cycle reduction at B due to specialization handoff costs. ## 9. Recommendation

**Choice: `conditional go`**

What should be transferred is the validated queueing mechanism, not the literal Site A diagram. The shareable principle is that when Document Check is legally and materially workable at registration, delaying it behind Identity Check adds unnecessary synchronization waiting. This transfers only to the digital, originals-not-required, non-legal, low/medium complexity segment where both checks use independent data and the legacy system can be made to support true dual worklists with WIP caps. What should not be copied is the blanket “create both tasks simultaneously for every case.” At Site B 62% of cases legally require Originals Receipt before Document Check, the case-management lock prohibits true parallel service, specialized pools prevent pooling gains, and 40% require Legal Review with a documented 26% supplement loop that will amplify any premature document work into rework and legal congestion. Importing the full parallel launch would produce log-fiction overlap without service overlap and shift the bottleneck to 3 assessors and 2 legal reviewers, improving median slightly while worsening p90, as seen in the bottleneck-shift scenario.

The first subgroup to enter is the 20-25% digital no-originals cohort, randomized 1:1 to concurrent vs sequential within that stratum, with orthogonal randomization of huddles and frozen FTE/API. Expected benefits are modest: population median -1 to -2 hours, eligible subgroup -3 to -5 hours and waiting before Assessment -2 to -4 hours, with no material change in throughput until capacity is added. Risks are rework increase, duplicate customer requests, legal queue growth, and spurious logging compliance that masks failure.

Expand only if at 3-month interim the eligible subgroup shows 2.5 hour median reduction with true service overlap 50%, rework increase <1.5 percentage points, legal waiting flat, and ineligible stratum shows no spillover (+ p90 <3 hours). Modify to add assessment or legal capacity, or to exclude high-complexity cases, if median gains exist but tail worsens. Abandon blanket parallelization if IT-lock true overlap stays <20% or rework exceeds +3 points, and revert to sequential with only WIP controls and huddles retained as separately tested interventions.

## 10. Assumption register

1. `assumption` — Originals-required flag at Register correctly identifies statutory block — `why needed` — Eligibility gate determines feasibility of true_overlap — `how to test` — Audit 200 cases: flag vs legal text + incoming document type concordance — `consequence if false` — Illegal early Document Check, quality breach, forced rework, invalid pilot.

2. `assumption` — IT dual-worklist fix converts task creation into true service overlap despite specialization — `why needed` — Distinguishes implementation failure from mechanism failure — `how to test` — Measure true start timestamps, overlap ratio, and service time by role per arm — `consequence if false` — Spurious overlap inflates adherence, no waiting reduction, false negative on theory.

3. `assumption` — Assessment (3) and Legal (2) capacities non-binding for pilot volume — `why needed` — Prevents bottleneck-shift spillover confounding subgroup ATE — `how to test` — Track utilization, queue length, and ineligible stratum waiting before Assessment — `consequence if false` — Median improves but p90/rework worsen, population effect overestimated.

4. `assumption` — No unmeasured time-varying confound (demand, mix, API) differential across arms during pilot — `why needed` — Randomization validity and transport formula invariance — `how to test` — Phase-staggered rollout, compare eligible vs ineligible time trends, monitor arrival mix — `consequence if false` — Before/after bias repeats Site A error, confounded transport estimate.

5. `assumption` — Document Check duration independent of parallel launch (no quality degradation for eligible) — `why needed` — Ensures cycle gain not offset by loops — `how to test` — First-pass yield, supplement rate, service time per arm — `consequence if false` — Rework loop amplifies, neutralizing gains and increasing tail.

6. `assumption` — WIP caps enforceable without starvation of Assessment — `why needed` — Little's Law requires WIP control to prevent flow time inflation — `how to test` — Daily WIP per pool vs waiting time scatter, pull kanban compliance — `consequence if false` — Flooding, priority inversion, median flat and p90 degraded.

7. `assumption` — SUTVA within stratum except via measured capacity spillover (no hidden reviewer interference) — `why needed` — ITT estimates interpretable as direct effect — `how to test` — Intra-team correlation, reviewer-level random effects, cross-arm spillover test — `consequence if false` — Interference bias, underestimated variance, overconfident expansion.

8. `assumption` — Case mix and originals demand stable over 6mo (62% originals, 40% legal) — `why needed` — Eligible share calculation for population transport — `how to test` — Weekly eligible% control chart, legal-review% trend — `consequence if false` — Optimistic/digital-only scenarios no longer represent population, transport reweighting fails.
