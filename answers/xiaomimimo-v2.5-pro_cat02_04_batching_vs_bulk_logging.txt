# Overlap rate
def compute_overlap_rate(group):
    cases = group.sort_values('start_ts')
    n = len(cases)
    if n < 2:
        return 0.0
    overlaps = 0
    total = 0
    intervals = list(zip(cases['start_ts'], cases['complete_ts']))
    for i in range(len(intervals)):
        for j in range(i+1, len(intervals)):
            total += 1
            if intervals[i][0] < intervals[j][1] and intervals[j][0] < intervals[i][1]:
                overlaps += 1
    return overlaps / total if total > 0 else 0.0

# Start equality
def count_unique_starts(group):
    return group['start_ts'].nunique()

def count_unique_ends(group):
    return group['complete_ts'].nunique()

# Recording lag
def compute_recording_lag(group):
    lags = (group['recorded_at_ts'] - group['complete_ts']).dt.total_seconds()
    return lags.mean()

# Sequential adjacency
def check_sequential(group):
    sorted_g = group.sort_values('sequence_no')
    starts = sorted_g['start_ts'].values
    ends = sorted_g['complete_ts'].values
    adjacent = 0
    for i in range(len(ends) - 1):
        gap = (starts[i+1] - ends[i]) / np.timedelta64(1, 's')
        if abs(gap) <= 60:  # within 1 minute
            adjacent += 1
    return adjacent / max(len(ends) - 1, 1)

# Queue wait

    waits = (group['start_ts'] - group['queue_arrival_ts']).dt.total_seconds() / 60

def overlap_rate(grp):
    """Fraction of case-pairs whose [start, complete) intervals overlap."""
    intervals = list(zip(grp["start_ts"], grp["complete_ts"]))
    n = len(intervals)
    if n < 2:
        return np.nan
    overlaps = total = 0
    for i in range(n):
        for j in range(i + 1, n):
            total += 1
            if intervals[i][0] < intervals[j][1] and intervals[j][0] < intervals[i][1]:
                overlaps += 1
    return overlaps / total

def adjacency_rate(grp):
    """Fraction of consecutive-case pairs where start_{i+1} == end_i (±60 s)."""
    s = grp.sort_values("sequence_no")
    starts = s["start_ts"].values
    ends   = s["complete_ts"].values
    adj = 0
    for k in range(len(ends) - 1):
        gap_s = (starts[k + 1] - ends[k]) / np.timedelta64(1, "s")
        if abs(gap_s) <= 60:
            adj += 1
    return adj / max(len(ends) - 1, 1)

def classify_pattern(grp):
    """Pandas-based batch-type label."""
    n_s = grp["start_ts"].nunique()
    n_e = grp["complete_ts"].nunique()
    ov  = overlap_rate(grp)
    adj = adjacency_rate(grp)
    if n_s == 1 and n_e == 1:
        return "simultaneous"
    if n_s == 1 and n_e > 1:
        return "start_batch"
    if n_s > 1 and n_e == 1:
        return "end_batch"
    if adj >= 0.75:
        return "sequential"
    if ov is not None and ov > 0.5:
        return "concurrent_overlap"
    return "mixed"

# 5. Robustness and alternative explanations

## 5a. Resource IDs trusted vs. treated as shared accounts

| Scenario | Clusters affected | Interpretation change |
|---|---|---|
| **Trusted** — each resource ID = one physical worker or machine | G5 overlaps become **multitasking** by a single analyst. Service times are inflated because they include context-switching time. Utilization can exceed 100% in a naïve calculation. | The analyst "analyst_pool" is doing 4 things at once, which is either heroic multitasking or evidence of poor data quality |
| **Treated as shared** — resource IDs may mask multiple workers | G5 overlaps become **genuine parallel work** by 2–3 analysts. Each service time is individually correct. Utilization must be calculated per actual badge-holder, not per login. | The name "analyst_pool" and the documented sharing (up to 3 analysts) strongly support this interpretation. G1 (RBT-7), G4 (T-D scanner), and G8 (T-H scanner) are unlikely to be shared because the sources are dedicated devices. G6 (T-F) and G7 (T-G) are ambiguous — we cannot tell from the data alone whether these terminals are single-user. |

**Key conclusion:** G5 is the only cluster where the trust-vs-shared distinction substantially changes the analysis. For G1, G4, G8 the physical setup rules out sharing. For G6 and G7 the timestamps are so corrupted that the resource-identity question is secondary.

## 5b. Timestamps exact vs. interval-censored by stated precision

If timestamps are **exact** (to the stated precision):
- G1: starts are truly identical to the second  simultaneous processing is certain
- G4, G8: chaining is exact to the second  sequential processing is certain

If timestamps are **interval-censored** (± half the precision window):
- G2 (±30 s): starts could differ by up to 1 min in total; the "common start" might hide a small stagger — but the "begin group" button makes this academic
- G3 (±30 s): completions could differ by up to 1 min; the four items might not have finished at truly the same instant — but the documented folder-submission pattern makes this academic
- **G7 (±7.5 min)**: starts could range from 13:52:31 to 14:07:30; completions from 14:07:31 to 14:22:30. The overlap between M01's start window and M02's queue_arrival (14:01) is now explicable: M02's true start could have been 14:02 or later. **This is the cluster where the precision assumption most changes the interpretation** — under interval-censoring, we cannot determine the work pattern at all, and the 15-min service time is meaningless.
- G6 (±30 s): even with censoring, the 2+ hour spread in queue_arrivals and the identical timestamps point to bulk entry regardless of sub-minute imprecision

## 5c. Three cases where the same temporal pattern supports multiple explanations

**Case 1 — Identical start times (G1, G2, G6, G7):**
The pattern "all items start at the same timestamp" is consistent with:
1. *Genuine simultaneous batch* — a fixture or oven processes all items together (G1 is most consistent)
2. *UI-triggered common start* — a single button click logs the same start time for all (G2 is most consistent)
3. *Timestamp coarsening* — fine-grained differences are lost to rounding (G7 is most consistent)
4. *Bulk data entry* — all records created at once, start time is the entry time (G6 is most consistent)

PM4Py would label all four as "simultaneous batch." Only domain knowledge (source type, precision, contextual clues) distinguishes them.

**Case 2 — Identical end times (G1, G3, G6, G7):**
"All items complete at the same timestamp" is consistent with:
1. *Genuine simultaneous completion* — batch removed from fixture at once (G1)
2. *Bulk form submission* — folder submitted when last item is reviewed (G3)
3. *End-of-shift data entry* — everything logged at once (G6)
4. *Rounding artifact* — all snapped to same boundary (G7)

**Case 3 — Overlapping work intervals under one resource (G5):**
"Cases active at the same time under the same resource ID" is consistent with:
1. *Shared-account artifact* — multiple badge-holders logged in simultaneously (supported by "analyst_pool" name and documented 3-user sharing)
2. *Concurrent multitasking* — one person juggling multiple cases (less likely with 4 concurrent cases and 1-min precision overlaps of 10+ minutes)
3. *Timestamp coarsening* — if precision were very coarse, non-overlapping true intervals could appear to overlap (but 1-min precision is not coarse enough to explain 10-min overlaps)

# 6. Data-collection redesign

Prioritized recommendations, ordered by impact on analysis quality:

| Priority | Recommendation | Rationale | Clusters most affected |
|---|---|---|---|
| **1 (critical)** | **Record per-item start and complete timestamps independently from any bulk submission form.** The form should trigger individual lifecycle transitions, not a single timestamp for all items. | Eliminates the "inflated waiting / near-zero service" pathology entirely. Without this, G6-type data is unusable for any quantitative analysis. | G6, G3 |
| **2 (critical)** | **Require badge-level identity on every lifecycle event.** Disable shared accounts or overlay badge-scan events onto the activity log. | Disambiguates concurrent work from shared-logins. Enables accurate per-person utilization and service-time calculation. | G5 |
| **3 (high)** | **Preserve raw (unrounded) timestamps alongside any display rounding.** The legacy MES should store sub-second precision even if the UI shows 15-min intervals. | Without raw timestamps, G7 data is irrecoverable. The ±7.5 min uncertainty makes service-time analysis impossible. | G7 |
| **4 (high)** | **Synchronise clocks across all systems** (PLC, scanner, tablet, MES, safety system) to a common NTP source, and log the offset if synchronisation is imperfect. | The clock discrepancy in G8 makes it impossible to correlate the safety check with the queue gap. Even a 2-minute skew can distort waiting-time calculations. | G8 |
| **5 (medium)** | **Log batch / group / fixture identifiers** when items are processed together (G1), grouped in a UI action (G2), or submitted in a folder (G3). This enables PM4Py batch discovery to be validated against physical groupings. | Without batch IDs, we can only infer batching from timestamp patterns, which are ambiguous (see §5c). | G1, G2, G3 |
| **6 (medium)** | **Record pause / resume events** for any planned downtime (safety checks, breaks, changeovers). These should be lifecycle events on the workstation, not on individual cases. | G8's 30-min gap should be attributable to a specific downtime event, not inferred from a different system's clock. | G8 |
| **7 (medium)** | **Log workstation capacity** (e.g., fixture holds 4 items) as metadata on the resource or activity definition. | Validates the "genuine simultaneous batch" interpretation for G1 without relying on external context. | G1 |
| **8 (low)** | **Record the actual precision and rounding rule** of each source system as machine-readable metadata (not just documentation). | Current "precision" column is a human-readable label; an automated pipeline needs a numeric tolerance parameter for interval-censoring. | G7, all |
