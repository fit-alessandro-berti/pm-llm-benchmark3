## 1. Normalization Assumptions

To convert recorded timestamps into true event-time uncertainty intervals in UTC, we apply the following mathematical and domain semantics:

### 1. Source Clock Offset Direction & Formula
As defined by the true-time specification, the source clock offset is given by:
$$\text{clock\_offset} = t_{\text{recorded\_clock}} - t_{\text{true\_clock}} \implies t_{\text{true\_clock}} = t_{\text{recorded\_clock}} - \text{clock\_offset}$$
If a source system has a documented clock-offset bound $\text{clock\_offset} \in [\delta_{\text{min}}, \delta_{\text{max}}]$, the true clock time relative to recorded clock time lies in:
$$t_{\text{true\_clock}} \in [t_{\text{recorded\_clock}} - \delta_{\text{max}}, \; t_{\text{recorded\_clock}} - \delta_{\text{min}}]$$

### 2. Resolution & Rounding Bounds (Pre-Correction)
Timestamp resolution uncertainty is applied **before** applying clock offset corrections:
- **HUB (UTC):** Exact to displayed second; measurement uncertainty $\pm 0.5\,\text{s}$. Displayed $T$ expands to $[T - 0.5\,\text{s}, T + 0.5\,\text{s}]$. Clock offset is $[-1\,\text{s}, +1\,\text{s}]$. Total UTC true-time bound for displayed $T$:
  $$t_{\text{true}} \in [T - 0.5 - 1, \; T + 0.5 - (-1)] = [T - 1.5\,\text{s}, \; T + 1.5\,\text{s}]$$
- **OPS-BER (Europe/Berlin):** Displayed time is truncated (floored) to the minute. Displayed $HH:MM$ implies uncorrected clock time in $[HH:MM:00.000, HH:MM:59.999]$. Time zone is CEST (UTC+2) in June. Clock offset bound is $[-90\,\text{s}, +120\,\text{s}]$.
  $$t_{\text{true, UTC}} \in [\text{UTC}(HH:MM:00) - 120\,\text{s}, \; \text{UTC}(HH:MM:59.999) + 90\,\text{s}]$$
- **SENSOR (UTC):** Completion event. Rounded to the nearest 10 seconds. Displayed $T$ expands to $[T - 5\,\text{s}, T + 5\,\text{s}]$. Clock offset bound is $[-5\,\text{s}, +5\,\text{s}]$.
  $$t_{\text{true, UTC}} \in [T - 5 - 5, \; T + 5 - (-5)] = [T - 10\,\text{s}, \; T + 10\,\text{s}]$$
- **VENDOR-NY (America/New_York):** Floored to the minute. Time zone is EDT (UTC-4) in June. Clock offset bound is $[-180\,\text{s}, +180\,\text{s}]$.
  $$t_{\text{true, UTC}} \in [\text{UTC}(HH:MM:00) - 180\,\text{s}, \; \text{UTC}(HH:MM:59.999) + 180\,\text{s}]$$
- **LEGACY-BER (Europe/Berlin):** Floored to the minute. Offset bound $[-60\,\text{s}, +60\,\text{s}]$. DST fall-back ambiguity on 2025-10-26 (02:00–02:59 local time) means a local time can map to Fold 0 (CEST = UTC+2) or Fold 1 (CET = UTC+1).
- **MOBILE-LON (Europe/London):** BST (UTC+1) in June. Rounded to nearest minute ($[T - 30\,\text{s}, T + 30\,\text{s}]$). Offset bound $[-300\,\text{s}, +300\,\text{s}]$.

### 3. Case-Specific Inferences and Ingestion Constraints
- **Inferred Activity Start (T-404):** `Investigation_Start` is missing. A signed work record establishes an investigation duration of $[18, 25]$ minutes ($[1080, 1500]\,\text{s}$). We model $\text{Start} = \text{Investigation\_Complete} - \text{Duration}$. The resulting interval propagates both completion timestamp uncertainty and duration uncertainty without arbitrary midpoint collapse.
- **DST Ambiguity Causal Truncation (T-405):** Ingestion sequence requires $\text{Alert\_Received} < \text{Investigation\_Start} < \text{Containment\_Complete}$.
  - Alert (02:50 local): Fold 0 (CEST) maps to $\approx 00:50$ UTC; Fold 1 (CET) maps to $\approx 01:50$ UTC.
  - Inv Start (02:05 local): Fold 0 (CEST) maps to $\approx 00:05$ UTC; Fold 1 (CET) maps to $\approx 01:05$ UTC.
  - Containment (02:42 local): Fold 0 (CEST) maps to $\approx 00:42$ UTC; Fold 1 (CET) maps to $\approx 01:42$ UTC.
  
  If Alert is in Fold 1 ($\approx 01:50$ UTC), Inv Start in Fold 0 ($\approx 00:05$ UTC) or Fold 1 ($\approx 01:05$ UTC) would precede Alert, violating ingestion sequence. Thus, Alert **must** be Fold 0 (CEST, $\approx 00:50$ UTC), and Inv Start & Containment **must** be Fold 1 (CET, $\approx 01:05$ UTC & $\approx 01:42$ UTC). This eliminates impossible fold combinations while preserving interval uncertainty within the surviving fold combination.
- **Mobile Entry Delay Semantics (T-406):** User entry delay of up to $+5$ minutes ($[0, 300]\,\text{s}$) represents late user logging after actual event completion/occurrence. Therefore, true occurrence time occurred *earlier* than app entry time:
  $$t_{\text{occur}} \in [t_{\text{entry\_min}} - 300\,\text{s}, \; t_{\text{entry\_max}}]$$
  This entry delay shifts the lower bound of true occurrence time downward by 300 seconds.
- **Missing Alert Receipt & Causal Bounds (T-407):** `Alert_Received` is missing. Network latency from `Alert_Sent` is bounded to $[0, 20]$ minutes ($[0, 1200]\,\text{s}$). Thus, $\text{Alert\_Received} \in [\text{Alert\_Sent}_{\text{min}}, \text{Alert\_Sent}_{\text{max}} + 1200\,\text{s}]$. Causal constraint $\text{Alert\_Received} \le \text{Investigation\_Start}$ is evaluated both with and without enforcement.

## 7. Governance Recommendation

To eliminate temporal ambiguity, support legal auditability, and enable automated process mining across heterogeneous system architectures, the following temporal data governance controls should be implemented:

```
                  +-------------------------------------------------------+
                  |         Unified UTC Ingestion Standard               |
                  |  - Store all events in ISO 8601 UTC with microsecs    |
                  |  - Retain raw local string + offset in metadata       |
                  +-------------------------------------------------------+
                                              |
                                              v
                  +-------------------------------------------------------+
                  |       Synchronized Infrastructure Controls           |
                  |  - Mandatory PTP / NTP (IEEE 1588 / RFC 5905)         |
                  |  - Log drift metrics to continuous telemetry stream   |
                  +-------------------------------------------------------+
                                              |
                                              v
                  +-------------------------------------------------------+
                  |        Explicit Lifecycle & Causal Schema            |
                  |  - Separate Start and Complete event types            |
                  |  - Disallow client-side manual timestamp overrides    |
                  |  - Include trace context & parent message IDs         |
                  +-------------------------------------------------------+
                                              |
                                              v
                  +-------------------------------------------------------+
                  |       Dual-Policy SLA Enforcement Engine              |
                  |  - Conservative (Cert. Violations): Penalty / Audit   |
                  |  - Strict (Poss. Violations): Operational Escalation  |
                  +-------------------------------------------------------+
```

### Governance Control Specifications

1. **Storage & Representation Standards:**
   - **UTC Normalization:** All system event logs must be stored in UTC with microsecond precision (`YYYY-MM-DDTHH:MM:SS.ffffffZ`).
   - **Raw & Local Metadata Retention:** Local display time, local time zone string (e.g., `Europe/Berlin`), and active DST offset must be preserved in immutable metadata columns (`raw_timestamp`, `time_zone`, `dst_offset`).

2. **Synchronization & Telemetry Controls:**
   - Mandatory daily NTP/PTP synchronization across all internal nodes (`HUB`, `OPS-BER`, `SENSOR`).
   - System telemetry must capture continuous clock drift and offset estimates. If an NTP diagnostic log is missing, the system must tag event records as `uncalibrated_clock`.

3. **Lifecycle & Semantic Disambiguation:**
   - Eliminate implicit activity completion events. Require distinct `Activity_Start` and `Activity_Complete` events with explicit start/complete status tags.
   - For mobile/user-entered inputs (`MOBILE-LON`), record `event_occurrence_utc` and `server_ingestion_utc` separately. User-entered timestamps must never overwrite system-captured transaction times.

4. **Causal Lineage & Correlation:**
   - Assign unique correlation IDs (`trace_id`, `message_id`) across system boundaries (e.g., `VENDOR-NY` to `HUB`).
   - `Alert_Sent` events must generate a corresponding `Alert_Received` confirmation receipt via message queue acknowledgments (e.g., AMQP / Kafka headers).

5. **Enforcement & Compliance Policy:**
   - **Legal SLA Enforcement:** Enforce penalties or contractual violations *only* on **`CERTAIN_VIOLATION`** findings (where every point in the feasible interval violates the rule).
   - **Operational Escalation:** Trigger internal operational triage and investigation on **`POSSIBLE_VIOLATION`** findings to remediate synchronization or logging deficits before legal breaches occur.
