## 1. Model scope and state variables

### 1.1 Recommended architecture and boundary

Use a **discrete-event simulation (DES)** engine, such as SimPy, AnyLogic, or FlexSim, for execution and **PM4Py for process mining, conformance checking, and parameter preparation**. PM4Py should not be used as the simulation engine.

The operational boundary is:

- **Included:** portal submission, completeness assessment, applicant document response, municipal reviews, public notice, inspection scheduling and travel, site inspection, decision drafting, legal review, permit issuance or rejection, appeals, and associated rework.
- **Conditionally included for D1:** a pre-submission checker and applicant pre-submission effort. The observed log begins at submission, so D1 must add this stage rather than merely reducing an in-log loop.
- **Modelled as external events:** applicant responses, third-party consultant reports, objections, no-shows, and council decisions. These are not municipal service queues.
- **Excluded:** post-permit construction, inspections, and enforcement, except insofar as historical violation data are needed to evaluate D2.

The digital twin should support two modes:

1. **Historical/shadow mode:** initialize from a dated snapshot of arrivals, work in process, resource assignments, and calendar state.
2. **What-if mode:** run candidate policies against the same snapshot and a specified demand/resource scenario.

### 1.2 Level of detail

Use an **activity-and-resource level of detail**:

- Each workflow activity is a task with queue entry, work start, work end, duration, and rework metadata.
- Resources are role-based pools with individual calendars, skills, and availability.
- Time is continuous for service and waiting, with calendar resolution at the relevant day/hour.
- Cases are not simulated independently: they compete for pools, may share a district or architect cohort, and may be bundled for inspection.
- Public notice is a duration/deadline task rather than a human-resource task.

### 1.3 Entities and state variables

| Entity | Principal state variables |
|---|---|
| **Case** | case ID; submission time; case type; district; architect ID; application value; building area if later obtained; fire/environment/public-notice flags; current status; current activity; route; rework count; appeal count; legal/quality outcome; priority; age; inspection bundle ID; applicable SLA |
| **Case-task instance** | task type; attempt number; queue-entry time; work start/end; sampled service and waiting durations; assigned resource; required inputs; completion/failure status; rework reason |
| **Resource/agent** | role; skill; FTE; shift; leave; reserved capacity; current assignment; queue; busy time; effective utilization; travel state |
| **Resource pool** | role-specific queue; FIFO/priority discipline; batch policy; temporary staffing; environmental reserve; specialist restrictions |
| **Calendar** | workdays; shift hours; public holidays; council-meeting weeks; part-time schedules; district-specific interruptions; effective capacity by date |
| **Case cohort/group** | architect-week cohort; district-period cohort; geographic cluster; shared-objection shock; inspection bundle; dependency links |
| **Latent event** | objection occurrence and severity; applicant no-show; consultant delay; missing prior-violation information |
| **Policy configuration** | intervention switches; thresholds; staffing levels; routing changes; triage rules; priority rules; calendar overrides |
| **Scenario** | demand multiplier; seasonal/drift assumptions; objection rate; resource absence; applicant response; travel conditions; policy start date |
| **Outcome** | end-to-end duration; active work time; waiting time; SLA status; resource demand; rework; applicant effort; district/architect cohort results |

### 1.4 Resources, queues, and calendars

The baseline resource model should reflect:

- **Clerks:** 5 FTE, Monday–Friday 08:00–16:00. Model the Monday portal-support allocation as a capacity partition rather than simply adding capacity.
- **Planners:** 8 FTE, Monday–Friday 09:00–17:00; two planners are restricted to Simple renovation.
- **Fire reviewers:** 2 FTE equivalent, Tuesday–Thursday only. Calendar availability, not just daily capacity, must constrain fire review.
- **Environmental reviewers:** 3 FTE with 40% reserved for other duties, giving approximately 1.8 effective permit FTE. This can be represented as stochastic availability, reserved server capacity, or availability-adjusted service time.
- **Inspectors:** 4 FTE, Tuesday–Friday field availability, with district travel times and batching.
- **Legal officers:** 2 FTE, with no ordinary work during council-meeting weeks except explicitly modelled urgent work.
- **System tasks:** effectively unlimited capacity.
- **Scheduler:** the excerpt includes `scheduler_1`; scheduling should have its own capacity or be linked to inspection-day capacity.

Baseline queue discipline should normally be FIFO within a role pool, with these exceptions:

- D6 introduces an aging priority/reservation rule.
- D8 introduces environmental triage.
- D5 introduces legal pre-check tasks that can run concurrently with other reviews.
- D3 introduces bundle-closure waiting before inspection dispatch.

Tasks should generally be non-preemptive unless operational evidence supports preemption. Priority rules must include displacement or starvation monitoring.

### 1.5 Cross-case and workflow dependencies

The twin must contain at least four dependency mechanisms:

1. **Resource coupling:** unrelated cases compete for the same planner, reviewer, inspector, and legal capacity.
2. **Architect cohorts:** same-architect applications submitted in the same week form a correlated arrival cluster. They need not share a municipal resource, but their submission timing is not independent.
3. **Spatial and objection clusters:** cases in the same district or neighbourhood can experience correlated objections, public-notice extensions, and common inspection travel conditions.
4. **Bundle dependencies:** geographically related cases can share an inspection visit. A bundle waits for its closing condition, reducing travel but potentially delaying its first member.

Within a case, decision drafting is an **AND-join** over all applicable Planning, Fire, Environmental, Public-notice, and Inspection results. Optional reviews must not be treated as mandatory activities.

## 2. Parameter-estimation plan

### 2.1 Log preparation and PM4Py workflow

The full 18-month log, not the two-case excerpt, is required for calibration.

1. Load the event log with `pandas.read_csv`; PM4Py has no `pm4py.read_csv` function.
2. Normalize the PM4Py columns:
   - case ID: `case:concept:name`
   - activity: `concept:name`
   - timestamp: `time:timestamp`
   - optional start: `activity_start`
   - optional end: `activity_end`
3. Convert the DataFrame with `pm4py.format_dataframe`.
4. Write and reload an XES event log with `pm4py.write_eventlog` and `pm4py.read_eventlog` if an XES interchange artifact is required.
5. Use:
   - `pm4py.discover_log(log)` for a discovered process model;
   - `pm4py.discover_dfg(log)` for a directly-follows graph;
   - `pm4py.discover_performance_dfg(log)` for edge-lag diagnostics;
   - case-activity sequences to calculate empirical variants.
6. Compare discovered variants and paths with the supplied seven variant groups. Resolve discrepancies through trace inspection rather than forcing all cases into a variant.

The process tree should be used as a **documentary control-flow model**, not as the simulation model. It lacks resource assignment, calendars, probabilities, duration distributions, and explicit AND-join semantics.

### 2.2 Estimation plan by parameter family

| Parameter family | Estimation method | Important limitations and checks |
|---|---|---|
| **Arrival counts and seasonality** | Fit daily or hourly counts with a Poisson or negative-binomial marked point process. Model `(t) = 0 × seasonal(month) × day-of-week × calendar effects`. Normalize the seasonal weights so they reproduce the observed 18-month count unless a trend is estimated. | The reported 1.7 peak-to-trough ratio and 2.2 Monday-to-Wednesday ratio are starting constraints. Test for year-to-year drift and whether case mix changes with season. |
| **Time-of-day and day-of-week profile** | Estimate a within-day portal profile if timestamps support it; otherwise model daily totals. | Monday concentration may reflect submission timing rather than demand creation; distinguish both where possible. |
| **Architect arrivals** | Use a hierarchical marked process: architect-specific arrival intensity plus shared week-level burst factors. Compare observed same-architect/same-week co-submission rates with independence. | The flattened log may understate relatedness. The top-20 31% share is evidence of heterogeneity, not a complete set of architect weights. |
| **Case attributes** | Estimate case mix by month and architect cohort. Model application value on a log scale, conditional on case type. Infer fire/environment/public-notice flags from observed routing and covariates. | Building area, violation history, and environmental sensitivity must be added before D2 and D8 can be fully evaluated. Missing attributes are not “no”. |
| **Service times** | Where both start and end exist, fit empirical ECDFs or hierarchical lognormal/Weibull/gamma models with covariates for role, case type, district, and workload. Use survival models for right-censored activities. | Completion-only activities have weak service/wait identification. Do not infer service time from inter-event gaps. |
| **Waiting times** | For activities with start timestamps, calculate waiting from the causally preceding completion to work start. Calibrate queue rules against observed waiting and resource occupancy. | In parallel reviews, “previous event” is not necessarily the predecessor. Waiting is endogenous to service time and arrivals. |
| **Completeness and missing documents** | Estimate the probability of a missing-document loop and applicant response delay separately by case type and architect cohort. | `Receive missing documents` has essentially zero municipal service time; its five-day median is applicant/third-party delay. |
| **Review branching** | Estimate conditional probabilities with beta-binomial or hierarchical logistic models. Use known flags as observed covariates and treat uncertain area/sensitivity thresholds as latent or sensitivity parameters. | The supplied log lacks complete building attributes and district sensitivity. Do not infer deterministic thresholds from the excerpt alone. |
| **Public notice and objections** | Treat the 14-day minimum as a deterministic floor. Model observed duration as a mixture such as `14 days + I(objection) × extension`, where the objection indicator and extension severity are latent. Infer the mixture from duration frequencies plus external/domain information. | Objection events are not observed. A 60-day duration is a proxy for a possible objection episode, not an observed objection event. |
| **Rework** | Estimate transition-specific rework hazards after Planning, Inspection, and Legal, plus appeal/reopen transitions. Code unstructured reasons using a controlled taxonomy and multiple coders. | The absence of a dedicated “rework” activity means rework is often represented by repeated activities. Missing reasons and removed emergency cases create selection bias. |
| **Calendars and capacity** | Use HR calendars as prior information. Compare observed work starts against shifts, holidays, council weeks, and part-time schedules. Estimate effective utilization and specialist restrictions from the log. | HR calendars were reconstructed independently of the event log and may not match actual municipal behaviour. |
| **Case dependencies** | Construct architect-week, district-period, and geographic groups. Estimate joint submission/objection probabilities and shared variance components. | Related-case links are partly latent because the log was flattened by case. |
| **Inspection bundles** | Estimate bundle formation rules, bundle-size distribution, travel-time matrix, and bundle closure delay. | District alone is an imperfect geography; use centroids or travel data when available. |

### 2.3 Handling the missing service/wait split

This is the main identification problem.

- Activities with both timestamps provide observed service-time observations.
- Activities with only completion timestamps provide either an end-time observation or a censored service observation, depending on the selected model.
- Starting a service and finishing it immediately before the recorded completion is a valid duration, but the interval before work start remains unknown.
- Impute or infer start times using a joint service-and-queue model conditioned on resource, activity, case type, workload, and calendar.
- Treat the imputation model as uncertain: compare several service distributions and queue disciplines and propagate the resulting variation.
- Use the Performance DFG only to identify unusually long inter-activity lags. These lags are **not service times**.

### 2.4 Calibration objective

Calibrate against several targets jointly rather than minimizing one duration error:

- daily/weekly arrival totals and mix;
- empirical variant frequencies;
- median and p90 durations by variant;
- activity-level waiting distributions;
- resource utilization by role and period;
- queue lengths and age distributions;
- inspection travel and bundle behaviour;
- rework and appeal frequencies.

Use a hierarchical Bayesian model, particle/SMC calibration, or maximum-likelihood calibration with bootstrap replicates. Hold out the most recent period for validation rather than calibrating and reporting on the same observations.

## 3. Assumptions

These are explicit, testable assumptions, not claims that the supplied summary establishes the truth.

### Arrivals

- The non-homogeneous Poisson marked-process model is adequate at daily resolution, conditional on the chosen seasonal and day-of-week factors.
- The 1.7 seasonal ratio applies to March–May and September–November; other month ratios are estimated from the full log.
- Day-of-week effects are stable over the 18 months, unless out-of-sample testing rejects this assumption.
- Case mix is conditionally independent of arrival intensity unless the log shows otherwise.
- Architect bursts have a short memory—approximately within the same week—rather than lasting indefinitely.
- D7 redistributes arrivals across days or hours without reducing weekly demand. Demand displacement outside the municipal portal is not credited as a benefit.

### Service times

- Service duration is independent of queue wait once calendar, skill, case complexity, and workload are controlled for.
- The reported medians and p90s are useful calibration targets but do not identify the complete distribution.
- Heavy-tailed service distributions are retained; they are not winsorized to the p90.
- Public notice is a deadline-duration mechanism, not human service time.
- Environmental availability is represented by either an availability gate or equivalent service-time inflation calibrated to observed utilization.

### Routing

- Planning review is always required.
- Fire, environmental, and public-notice routing is driven by observed flags plus uncertain attributes; unknown thresholds are sensitivity parameters.
- Decision drafting waits for all applicable results.
- Legal check is not universally required; its probability is estimated by case type and observed sequence.
- D5 adds a legal pre-check before drafting while retaining a final legal check. Pre-check findings do not automatically imply approval.
- D2 exemption requires a positively observed clean violation history. A missing violation record is not treated as proof of no violations.

### Resources and calendars

- Municipal service is non-preemptive by default.
- Baseline queues are FIFO except where an intervention changes priority.
- The supplied HR calendars are correct in structure, although observed activity timestamps are used to test them.
- The Monday portal-support clerk is not freely available to all completeness work.
- Effective FTE, rather than nominal headcount, determines environmental capacity.
- Legal work during council weeks is possible only for explicitly sampled urgent cases.
- Inspection batching reduces travel but introduces bundle-closure delay.

### Rework

- Rework probability depends on case type and the preceding activity, not only on a global rate.
- Rework consumes capacity and can trigger renewed waiting.
- Applicant appeals are modelled separately from municipal rework.
- Repetition in the log is a reasonable but imperfect proxy for rework where dedicated rework events are absent.
- Rework reasons are treated as uncertain classifications rather than ground truth.

### Applicant and third-party response

- Applicant document response, consultant-report delay, and no-shows are independent of municipal service capacity except for the case’s own waiting state.
- Applicant response times are heavy-tailed and can exceed the p90 substantially.
- D1 reduces missing-document loops but adds applicant hours before the logged submission boundary.
- Applicant effort, repeat submissions, abandonment, and satisfaction must be measured in addition to municipal cycle time.

### Cross-case dependencies

- Same-architect, same-week submissions share a latent burst and may be bundled only when geographically feasible.
- Objections are clustered by neighbourhood or project, so they are correlated across related cases.
- Resource competition creates dependencies even between otherwise unrelated cases.
- The log’s flattening causes underestimation of these relationships; inferred coefficients are therefore conservative and stress-tested.

### Non-stationary demand

- Both demand and resource calendars are non-stationary over the calendar year.
- The model is reinitialized and re-estimated periodically as new data arrive.
- No long-run equilibrium is assumed for “normal” capacity; performance is evaluated over seasonal cycles and stressed periods.
- Candidate policies are tested under both the observed 1.7 peak factor and more severe peaks.

### Missing data

- Missing start timestamps are related at least partly to activity and resource, so complete-case deletion is inappropriate.
- Public-notice duration proxies an unobserved objection mechanism rather than directly revealing an objection.
- Emergency cases removed from the log represent a non-random selection and are included as a separate scenario rather than silently ignored.
- HR calendar reconstruction may misrepresent actual availability.
- Alternative imputations, dependency structures, and emergency rates are included in sensitivity analysis.

## 5. Warm-up, replications, and uncertainty treatment

### Warm-up and run length

Because the system has annual seasonality and long-tailed Complex variance cases:

- Run at least **365 days of warm-up** before collecting output, sufficient to traverse a complete seasonal cycle.
- Use a **730-day measurement period** as the default, covering two occurrences of each peak season.
- Extend to 1,095–1,460 days if aged backlogs do not drain or if the Complex variance tail remains sparse.
- Start the calendar at a consistent date and use the same start date across policies.
- Test two initial conditions:
  1. empty queues at the beginning of warm-up;
  2. warm-up initialized from the observed or synthetic backlog at the start of the measurement period.
- Do not impose a stationary initial distribution during warm-up. Inspect queue, age, and resource-utilization traces to determine whether the burn-in is adequate.
- Apply a stress shock only after warm-up, or ramp it according to a declared path, so that initial transients are not confused with shock effects.

### Replications and seeds

- Run 10 pilot replications per configuration to estimate Monte Carlo error.
- Use approximately **60 independent replications** for the main comparison, increasing to 100 if confidence intervals remain too wide.
- Derive seeds reproducibly with `numpy.random.SeedSequence`.
- For baseline-versus-policy comparisons, use the same seed and demand realization for both policies. This is common random numbers and substantially improves paired difference estimates.
- Keep scenario seeds and parameter draws distinct from policy implementation details.
- Record the complete seed, parameter-file hash, code version, and scenario for every result.

### Confidence and credible intervals

- Report 95% confidence intervals for means, medians, SLA proportions, and utilization, using replication-level estimates and bootstrap resampling where necessary.
- For p90/p95, use bootstrap quantiles or quantile regression; ordinary mean confidence intervals are insufficient.
- For policy differences, use paired bootstrap or simulation-based difference intervals.
- If a hierarchical Bayesian calibration is used, propagate its posterior into the DES and report posterior predictive intervals as well as seed-only intervals.
- Correct for multiple comparisons across ten interventions and several outcomes, for example with Holm correction or false-discovery-rate control.
- Require both statistical evidence and a practically meaningful effect before recommending a policy.

### Parameter and model-form uncertainty

Propagate uncertainty in:

- arrival rate, seasonal shape, and architect burst intensity;
- service-time parameters and their tail shape;
- applicant response and objection-mixture parameters;
- rework hazards;
- travel times;
- effective staffing and calendar availability;
- missing-start imputations;
- unknown routing thresholds;
- initial backlog.

Use a joint Bayesian posterior or block bootstrap so correlated parameters remain correlated. Also run an **ensemble of plausible model forms**, such as different queue disciplines, service distributions, and dependence structures. Seed variation alone understates uncertainty.

### Heavy-tailed durations

- Compare lognormal, Weibull, gamma, empirical-tail, and Pareto-tail mixtures for service and applicant response using likelihood and tail diagnostics.
- Preserve empirical upper-tail behaviour rather than using a normal distribution.
- For public notice, retain the deterministic minimum plus a mixture for objection-driven extension.
- Use the supplied p90 values as checks, not as truncation points.
- Apply caps only where an actual legal or operational rule exists. Otherwise, let long cases contribute to tail and backlog metrics.
- Treat rare emergency cases separately because they were removed from the observed log.

### Sensitivity analysis

Use Morris screening followed by Sobol or variance-based analysis over the most influential parameters. Also perform one-at-a-time structural sensitivity:

- competing service distributions;
- independent versus shared architect/objection shocks;
- different calendar interpretations;
- alternative missing-start imputations;
- different missing-threshold priors;
- no-batching versus alternative batching rules.

Report which policy rankings are stable and which conclusions depend on a particular assumption.

---

## 6. Validation strategy

Validation must be separated into model-form conformance, parameter validation, and predictive validation.

### 6.1 Face validation

Conduct workshops with clerks, planners, inspectors, legal officers, and applicant representatives. Confirm:

- activity definitions and rework conventions;
- when a case is considered submitted;
- whether the logged timestamp is start or completion;
- real specialist restrictions and reserve capacity;
- holiday and council-week effects;
- how objections, appeals, and no-shows occur;
- whether inspection bundles are chosen by the scheduler or automatically.

Use a clickable prototype and scenario narratives to detect impossible behaviour.

### 6.2 Event-log replay and conformance validation

Perform two different replay tests:

1. **Trace conformance:** compare each logged path with the process tree and discovered model. Repeated completeness checks, missing rework events, optional reviews, and appealed cases will generate deviations that must be explained.
2. **Resource-constrained historical replay:** feed the observed arrival times and case attributes into the simulation, allow routing and waiting to be generated by the model, and compare aggregate service time, waiting, queueing, and resource occupancy.

The second test is more informative than merely replaying known traces. A deterministic trace reproduction is not evidence that the twin predicts new cases.

### 6.3 Distributional validation

Compare simulated and observed distributions for:

- arrivals by day/week/month and day-of-week;
- case mix and variants;
- end-to-end duration by case type;
- activity service and waiting distributions where observable;
- missing-document response time;
- inspection travel and bundle size;
- rework and appeal rates.

Use quantile plots, median/p90 checks, and distributional tests such as KS or Anderson–Darling. Stratify by case type, district, architect cohort, and month. Do not use only an aggregate KS test that hides subgroup errors.

### 6.4 Resource-utilization validation

For each resource and calendar period, compare:

- busy time / available time;
- queue occupancy and queue age;
- idle capacity;
- effective capacity after reserve duties;
- work outside the reconstructed shift;
- legal work during council blackouts.

Discrepancies should be investigated as either calendar error, missing activity, or incorrect capacity assumptions—not automatically removed by recalibrating service times.

### 6.5 Bottleneck validation

Check whether the model reproduces the observed bottleneck hierarchy, for example:

- completeness queues after Monday peaks;
- environmental review;
- legal queues around council meetings;
- inspection scheduling and travel;
- Complex variance aged work.

A model that gives plausible aggregate durations but assigns the wrong bottleneck is not fit for intervention analysis.

### 6.6 Out-of-sample validation

- Hold out the most recent six months initially; expand to a rolling-origin design if sufficient history exists.
- Freeze parameters before testing.
- Compare forecasts of arrivals, duration quantiles, SLA rates, backlog, and utilization.
- Repeat after a calendar-year boundary to test seasonality.
- If validation fails, diagnose rather than add parameters until the fit appears good.

Validation supports credibility; it does not establish that one intervention is globally optimal.

---

## 7. Decision criteria

Provisional thresholds below should be replaced by statutory requirements, service-charter targets, and stakeholder-approved risk limits.

Illustrative SLA targets could be:

- Simple renovation: 15-day standard and 30-day extended target;
- New residential: 60/90 days;
- Commercial: 90/120 days;
- Complex variance: 180/240 days.

Pending cases at the measurement horizon should be reported separately and conservatively counted as SLA failures in a sensitivity calculation.

| Dimension | Metric | Provisional selection criterion or guardrail |
|---|---|---|
| **Median duration** | Submission-to-final-decision median by case type | At least 3 days or 10% improvement for the targeted group; no other group’s median worsens by more than 2 days |
| **Tail duration** | p90 and p95 end-to-end duration; aged-case duration | At least 5 days or 10% p90 improvement; no subgroup p90 worsens by more than 5 days |
| **SLA compliance** | Percentage within standard and extended SLA | At least +5 percentage points for the target group; no subgroup falls by more than 3 points |
| **Waiting versus work** | Queue wait, active service time, and wait share | Reductions should not merely convert waiting into unreported municipal work; inspect both components |
| **District fairness** | District-specific medians, p90s, SLA rates, and disparity ratios | No district p90 increase over 5 days or SLA decrease over 3 points; preferably reduce the largest existing disparity |
| **Architect fairness** | Results for high-volume versus small architects, including same-week cohorts | No systematic deterioration for small or low-volume architects; D7 must not penalize applicants unable to use appointment slots |
| **Resource utilization** | Busy time divided by effective available time by role | Sustainable target around 65–90%; avoid sustained utilization above 95%, and report reserve/non-permit capacity separately |
| **Backlog** | WIP, cases over age threshold, backlog-area trend, time to drain | No sustained increase in aged backlog; aged backlog should drain within two peak seasons |
| **Rework and missing documents** | Rework rate, loop count, missing-document rate, repeated-submission rate | No case-type rework increase above 1 percentage point without explanation; document D1’s reduction and applicant effort |
| **Applicant effort** | Hours, response rounds, abandonment, and satisfaction for D1/D7 | Total effort and abandonment must not be hidden outside the municipal metric; no unexplained increase in applicant burden |
| **Quality and safety** | Appeal, rejection, conflict, inspection-defect, and violation rates | No material deterioration. D2 requires external safety evidence and an explicit violation-data audit |
| **Throughput** | Completed decisions, permit issuance, and work-in-process | Policy should improve timeliness without reducing throughput or changing decisions merely by leaving cases unresolved |
| **Robustness** | Benefit and guardrail results across S1–S5 | Retain at least half the baseline benefit in at least three of four core stresses, with no catastrophic or safety-guardrail breach |
| **Cost-effectiveness** | Temporary FTE cost, administrative effort, applicant effort, and benefit per cost | Prefer Pareto-efficient policies; do not select an intervention that is statistically better but economically or operationally disproportionate |

### Selection procedure

1. Exclude policies that breach safety, quality, fairness, or workload guardrails.
2. Require a practically meaningful effect with a 95% interval excluding negligible harm.
3. Compare policies on the Pareto frontier of tails, SLA, applicant effort, cost, and robustness.
4. Test whether the combined package outperforms its components; do not assume synergy.
5. Document the chosen policy, thresholds, scenario set, uncertainty assumptions, and conditions under which the recommendation should be reconsidered.

---

def load_log_dataframe(csv_path: Optional[str] = None) -> pd.DataFrame:
    """
    PM4Py has no pm4py.read_csv. Use pandas, then format_dataframe.
    Optional columns activity_start/activity_end may be present in the full log.
    """
    if csv_path is None:
        df = build_excerpt_dataframe()
    else:
        df = pd.read_csv(csv_path)

    required = {CASE_ID, ACTIVITY, TIMESTAMP}
    missing = required.difference(df.columns)
    if missing:
        raise ValueError(f"Missing required columns: {sorted(missing)}")

    df[TIMESTAMP] = pd.to_datetime(df[TIMESTAMP], errors="coerce")
    for col in ("activity_start", "activity_end"):
        if col in df.columns:
            df[col] = pd.to_datetime(df[col], errors="coerce")

    return df.sort_values([CASE_ID, TIMESTAMP], kind="stable").reset_index(drop=True)


def format_pm4py_log(df: pd.DataFrame):
    """Convert a pandas DataFrame to a PM4Py EventLog."""
    kwargs = {
        "case_id": CASE_ID,
        "activity_key": ACTIVITY,
        "timestamp_key": TIMESTAMP,
    }

    start_end_present = {"activity_start", "activity_end"}.issubset(df.columns)
    if start_end_present and df[["activity_start", "activity_end"]].notna().all().all():
        kwargs["start_timestamp_key"] = "activity_start"
        kwargs["end_timestamp_key"] = "activity_end"

    return pm4py.format_dataframe(df, **kwargs)


def extract_case_variants(df: pd.DataFrame) -> Counter:
    """
    Simplified case-sequence variants. This deliberately preserves repeated
    Completeness check activities; a separate taxonomy may group variants
    by business meaning rather than exact sequence.
    """
    ordered = df.sort_values([CASE_ID, TIMESTAMP], kind="stable")
    sequences = ordered.groupby(CASE_ID, sort=False)[ACTIVITY].apply(list)
    return Counter(tuple(sequence) for sequence in sequences)


def completion_lag_dfg(df: pd.DataFrame) -> dict[tuple[str, str], dict[str, float]]:
    """
    Diagnostic fallback for completion-only logs.
    These are inter-completion lags, NOT service times.
    """
    edges: dict[tuple[str, str], list[float]] = {}
    for _, case in df.sort_values([CASE_ID, TIMESTAMP]).groupby(CASE_ID):
        activities = case[ACTIVITY].tolist()
        times = case[TIMESTAMP].tolist()
        for src, dst, t0, t1 in zip(
            activities[:-1], activities[1:], times[:-1], times[1:]
        ):
            hours = (t1 - t0).total_seconds() / 3600.0
            edges.setdefault((src, dst), []).append(hours)

    return {
        edge: {
            "n": len(values),
            "median_hours": float(np.median(values)),
            "p90_hours": float(np.quantile(values, 0.90)),
        }
        for edge, values in edges.items()
    }


def mine_with_pm4py(df: pd.DataFrame) -> dict[str, Any]:
    log = format_pm4py_log(df)

    variants = extract_case_variants(df)
    dfg = pm4py.discover_dfg(log)

    # PM4Py versions differ in whether discover_performance_dfg returns
    # (dfg, performance_dfg) or only performance_dfg.
    try:
        raw_performance = pm4py.discover_performance_dfg(log)
        if isinstance(raw_performance, tuple) and len(raw_performance) == 2:
            performance_dfg = raw_performance[1]
        else:
            performance_dfg = raw_performance
    except Exception:
        performance_dfg = completion_lag_dfg(df)

    try:
        process_model = pm4py.discover_log(log)
    except Exception:
        process_model = None

    # Optional interchange artifact:
    # pm4py.write_eventlog(log, "permit_log.xes")

    return {
        "eventlog": log,
        "variants": variants,
        "dfg": dfg,
        "performance_dfg": performance_dfg,
        "process_model": process_model,
        "completion_lag_diagnostic": completion_lag_dfg(df),
    }


def case_arrival_statistics(df: pd.DataFrame) -> dict[str, float]:
    first_activity = (
        df.groupby(CASE_ID)[TIMESTAMP].min().sort_values()
    )
    span_days = max(
        (first_activity.iloc[-1] - first_activity.iloc[0]).total_seconds() / 86400.0,
        1.0,
    )
    gaps = first_activity.diff().dt.total_seconds().dropna() / 86400.0

    return {
        "n_cases": float(len(first_activity)),
        "observation_span_days": float(span_days),
        "average_cases_per_day": float(len(first_activity) / span_days),
        "mean_interarrival_days": float(gaps.mean()) if len(gaps) else np.nan,
        "median_interarrival_days": float(gaps.median()) if len(gaps) else np.nan,
    }


def add_service_waiting_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Service and waiting are left unknown when only completion timestamps exist.
    When starts/ends exist, waiting is a sequential proxy; parallel activity
    attribution still requires process-aware logic.
    """
    out = df.sort_values([CASE_ID, TIMESTAMP], kind="stable").copy()
    out["inter_event_gap_days"] = (
        out.groupby(CASE_ID)[TIMESTAMP].diff().dt.total_seconds() / 86400.0
    )

    have_times = (
        {"activity_start", "activity_end"}.issubset(out.columns)
        and out[["activity_start", "activity_end"]].notna().all().all()
    )

    if have_times:
        out["service_hours"] = (
            out["activity_end"] - out["activity_start"]
        ).dt.total_seconds() / 3600.0

        previous_end = out.groupby(CASE_ID)["activity_end"].shift(1)
        out["waiting_proxy_hours"] = (
            out["activity_start"] - previous_end
        ).dt.total_seconds() / 3600.0
    else:
        out["service_hours"] = pd.NA
        out["waiting_proxy_hours"] = pd.NA

    return out

@dataclass
class WorkCalendar:
    workdays: frozenset[int]
    start_hour: int
    end_hour: int
    holidays: frozenset[date] = frozenset()
    blackout_dates: frozenset[date] = frozenset()

    def next_work_start(self, ts: datetime) -> datetime:
        """Find the next permitted work start; illustrative calendar logic."""
        candidate = ts
        for _ in range(370):
            is_workday = candidate.weekday() in self.workdays
            is_blocked = (
                candidate.date() in self.holidays
                or candidate.date() in self.blackout_dates
            )
            day_start = candidate.replace(
                hour=self.start_hour, minute=0, second=0, microsecond=0
            )
            day_end = candidate.replace(
                hour=self.end_hour, minute=0, second=0, microsecond=0
            )
            if is_workday and not is_blocked:
                if candidate < day_start:
                    return day_start
                if candidate < day_end:
                    return candidate
            candidate = (candidate + timedelta(days=1)).replace(
                hour=0, minute=0, second=0, microsecond=0
            )
        raise RuntimeError("No work start found within 370 days")


class ResourcePool:
    def __init__(self, env: simpy.Environment, spec: ResourceSpec):
        self.spec = spec
        # Integer server approximation. Fractional/effective availability can
        # also be implemented by stochastic availability or service inflation.
        self.server = simpy.Resource(env, capacity=max(1, int(round(spec.fte))))

    def effective_capacity(self, ts: datetime, scenario: StressScenario) -> float:
        capacity = self.spec.fte * self.spec.availability_fraction
        capacity *= (1.0 - scenario.reviewer_absence)

        if self.spec.name == "environment":
            capacity *= 1.0 - scenario.reviewer_absence

        if self.spec.name == "legal" and scenario.legal_blackout_weeks > 0:
            # The actual engine should use dated blackout intervals.
            capacity = 0.0

        return max(0.0, capacity)


class ArrivalGenerator:
    """
    Thinning-based non-homogeneous Poisson arrivals.
    Calendar parameters must come from calibration.
    """

    PEAK_MONTHS = {2, 3, 4, 8, 9, 10}  # zero-based months

    def __init__(
        self,
        base_rate_per_day: float,
        season_factors: dict[int, float],
        dow_factors: dict[int, float],
        scenario: StressScenario,
    ):
        self.base_rate_per_day = base_rate_per_day
        self.season_factors = season_factors
        self.dow_factors = dow_factors
        self.scenario = scenario
        self.max_intensity = (
            base_rate_per_day
            * max(season_factors.values())
            * max(dow_factors.values())
            * scenario.demand_multiplier
            * scenario.peak_demand_multiplier
        )

    def intensity(self, ts: datetime) -> float:
        seasonal = self.season_factors.get(ts.month, 1.0)
        dow = self.dow_factors.get(ts.weekday(), 1.0)

        if ts.weekday() == 0:
            dow *= self.scenario.monday_multiplier

        peak = (
            self.scenario.peak_demand_multiplier
            if ts.month - 1 in self.PEAK_MONTHS
            else 1.0
        )
        return (
            self.base_rate_per_day
            * self.scenario.demand_multiplier
            * seasonal
            * dow
            * peak
        )

    def sample_next(self, current: datetime, rng: np.random.Generator) -> datetime:
        proposal = current + timedelta(
            days=float(rng.exponential(1.0 / self.base_rate_per_day))
        )
        for _ in range(10000):
            acceptance = min(
                1.0, self.intensity(proposal) / self.max_intensity
            )
            if rng.random() <= acceptance:
                return proposal
            proposal += timedelta(
                days=float(rng.exponential(1.0 / self.max_intensity))
            )
        raise RuntimeError("Arrival thinning failed to converge")


class DependencyManager:
    """Architect cohorts, district shocks, and latent objection episodes."""

    def __init__(
        self,
        base_objection_probability: float,
        scenario: StressScenario,
        rng: np.random.Generator,
    ):
        self.base_objection_probability = base_objection_probability
        self.scenario = scenario
        self.rng = rng
        self.district_period_cache: dict[tuple[str, int, int], float] = {}

    @staticmethod
    def architect_week(case: CaseState) -> str:
        iso = case.submitted_at.isocalendar()
        return f"{case.architect_id}:{iso.year}:{iso.week}"

    def draw_latent_objection(self, case: CaseState) -> bool:
        # A shared district-period multiplier induces correlated objections.
        key = (case.district, case.submitted_at.year, case.submitted_at.month)
        if key not in self.district_period_cache:
            shock = float(self.rng.beta(4.0, 4.0))
            self.district_period_cache[key] = shock

        probability = (
            self.base_objection_probability
            * self.district_period_cache[key]
            * self.scenario.objection_probability_multiplier
        )
        probability = min(1.0, max(0.0, probability))
        return bool(self.rng.random() < probability)


def route_case(
    case: CaseState,
    policy: Policy,
    rng: np.random.Generator,
) -> dict[str, Any]:
    """
    Illustrative routing. The engine should represent review branches as
    concurrent tasks plus an AND-join, not merely a linear list.
    """
    activities = ["Submit application", "Completeness check"]

    missing_probability = case.p_missing_docs
    if policy.d1_pre_submission_checker:
        missing_probability *= policy.d1_missing_doc_multiplier

    missing_loop = bool(rng.random() < missing_probability)
    if missing_loop:
        activities += [
            "Request missing documents",
            "Receive missing documents",
            "Completeness check",
        ]

    activities.append("Planning review")
    if case.requires_fire:
        activities.append("Fire-safety review")
    if case.requires_environment:
        activities.append("Environmental review")
    if case.requires_public_notice:
        activities.append("Public-notice period")

    inspection_required = True
    if (
        policy.d2_skip_inspection_below_eur is not None
        and case.case_type == "Simple renovation"
        and case.application_value < policy.d2_skip_inspection_below_eur
        and case.no_violations is True
    ):
        inspection_required = False

    if inspection_required:
        activities += ["Inspection scheduling", "Site inspection"]

    legal_required = bool(rng.random() < case.p_legal)
    if (
        policy.d5_legal_precheck
        and legal_required
        and case.case_type in {"Commercial", "Complex variance"}
    ):
        activities.append("Legal pre-check")

    activities.append("Decision drafting")
    if legal_required:
        activities.append("Legal check")

    return {
        "activities": activities,
        "missing_loop": missing_loop,
        "inspection_required": inspection_required,
        "legal_required": legal_required,
    }

def make_seeds(n_replications: int, root_seed: int = 20260101) -> list[int]:
    root = np.random.SeedSequence(root_seed)
    return [
        int(child.generate_state(1)[0])
        for child in root.spawn(n_replications)
    ]


def run_replications(
    policy: Policy,
    scenario: StressScenario,
    n_replications: int,
    calibrated_parameters: dict[str, Any],
    root_seed: int = 20260101,
) -> list[dict[str, Any]]:
    # Reuse the same seeds for each policy to obtain paired comparisons.
    return [
        run_experiment(policy, scenario, seed, calibrated_parameters)
        for seed in make_seeds(n_replications, root_seed)
    ]


def summarize_case_table(case_table: pd.DataFrame) -> dict[str, float]:
    """
    Expected case_table columns:
    case_id, submitted_at, decided_at, case_type, district,
    architect_id, outcome, sla_days, rework_count, applicant_effort_hours.
    """
    completed = case_table.dropna(subset=["decided_at"]).copy()
    completed["cycle_days"] = (
        completed["decided_at"] - completed["submitted_at"]
    ).dt.total_seconds() / 86400.0

    result = {
        "n_completed": float(len(completed)),
        "median_cycle_days": float(completed["cycle_days"].median()),
        "p90_cycle_days": float(completed["cycle_days"].quantile(0.90)),
        "p95_cycle_days": float(completed["cycle_days"].quantile(0.95)),
    }

    if "sla_days" in completed.columns:
        result["sla_compliance"] = float(
            (completed["cycle_days"] <= completed["sla_days"]).mean()
        )

    if "rework_count" in completed.columns:
        result["cases_with_rework"] = float(
            (completed["rework_count"] > 0).mean()
        )

    if "applicant_effort_hours" in completed.columns:
        result["mean_applicant_effort_hours"] = float(
            completed["applicant_effort_hours"].mean()
        )

    return result
