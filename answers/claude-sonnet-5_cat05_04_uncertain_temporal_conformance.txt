# 1. Normalization Assumptions

**Order of operations.** For every timestamp: (1) apply the source's display/rounding semantics to get a *recorded-clock interval*; (2) convert time zone to UTC using the fixed offset stated for the date (CEST=UTC+2, EDT=UTC-4, BST=UTC+1, CET=UTC+1) — timezone conversion is a relabeling, not a source of uncertainty; (3) apply the clock-offset bound to convert recorded-clock interval to *true-time interval*.

**Offset algebra.** `clock_offset = recorded  true` with offset  [a,b]. For a recorded-clock interval [r_lo, r_hi], the true-time interval is **[r_lo  b, r_hi  a]** (subtracting the *bound*, not a midpoint). This is applied consistently to every system.

**Rounding semantics.**
- "Exact to displayed second ± measurement uncertainty"  symmetric ± window.
- "Floor to minute"  [hh:mm:00, hh:mm:59.999].
- "Round to nearest N seconds/minutes"  ± N/2 window around the displayed value.

**Midpoints.** Never used as the primary estimate; only introduced in Section 5 as an explicitly labeled lossy comparison.

**DST fold (T-405).** Both endpoints of the Oct-26 fold are carried as two candidate UTC intervals (CEST=+2, CET=+1) until a constraint eliminates one. The *ingestion-order fact* ("Investigation_Start after Alert_Received", "Containment_Complete after Investigation_Start") is treated as ground truth about true-time order (not merely ingestion artifact) and used to prune fold-combinations. Only one (fold1, fold2, fold2) combination for (Alert, Investigation_Start, Containment) survives all order constraints; the surviving values still carry their normal ±60 s offset uncertainty — the fold selection removes *ambiguity of epoch*, not *measurement uncertainty*.

**Mobile entry delay (T-406).** Treated as a **one-sided, occurrence-time** effect, not a record-time artifact: the user's button-press can lag true occurrence by up to 300 s, in addition to (not instead of) the ±300 s device-clock offset. This asymmetrically extends the true-time interval only toward *earlier* times: `true = recorded  offset  delay`, offset[300,300], delay[0,300]  true  [recorded_lo600, recorded_hi+300]. This is a substantive, stated assumption — an alternative reading (delay only affects when the record was *stored*, not the estimate of occurrence) would leave the interval at [recorded_lo300, recorded_hi+300]; we adopt the wider, occurrence-affecting reading because the prompt frames it as bearing on when the event happened.

**Missing Investigation_Start (T-404).** Inferred by subtracting a bounded duration [1080 s,1500 s] (18–25 min, signed record) from the Investigation_Complete true-time interval. Full interval width is preserved (no point estimate).

**Alert_Sent  Alert_Received (T-407).** Alert_Received is *not observed*. It is bounded as Alert_Sent_true + latency, latency[0,1200 s]. This yields a wide, weak proxy interval. A secondary, explicitly-labeled scenario applies the *unlogged* causal assumption "receipt  investigation start" to cap the upper bound at Investigation_Start_true's upper bound. Because this assumption is stated as "plausible but not logged," the **primary** analysis does not apply it (and is downgraded to INDETERMINATE where it produces physically-impossible negative-duration feasibility), and the causally-capped version is reported as a **sensitivity variant**, not the default finding.

**T-409 weak offset.** The stated [-12min,+12min] "weak engineering estimate" replaces OPS-BER's normal offset bound only for this instance. Because it is explicitly flagged as non-metrological (no NTP diagnostics), any conclusion drawn from it is downgraded in confidence regardless of the raw interval arithmetic.

**Duration-interval arithmetic.** For two independent true-time intervals X=[x_lo,x_hi] (earlier activity) and Y=[y_lo,y_hi] (later activity), feasible duration = [y_lox_hi, y_hix_lo]. Where a causal ordering constraint is asserted, it is used to prune, not silently narrow, the interval.
