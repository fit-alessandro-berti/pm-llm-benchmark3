## 1. Target definition

**Primary target: activation-conditional 90-day default.**

- **Population:** Applications that reach `Account Activated` (time A) and have a feed-confirmed 90-day outcome by the cutoff. This is the labeled cohort, and it is selected by activation.
- **Unit of analysis:** One application (case).
- **Prediction time t_p:** The timestamp of the K-th event (K = 3: Application Started, Identity/KYC, first Credit Review event). The prefix must be complete and must end strictly before the first decision or activation event (Accept, Reject, Withdraw, Transfer, Activate). If a case cannot satisfy this, it is not prediction-eligible.
- **Outcome:** Y = 1 if a default is recorded in (A, A + 90 days], and 0 if the 90-day window is complete and no default is recorded. The horizon is anchored at activation, not at t_p. The gap between t_p and A varies, so the model predicts risk over a variable lag. This is a known limitation, and a sensitivity analysis with a fixed calendar horizon from t_p is included.
- **Estimand:** P(Y = 1 | prefix at t_p, activated), the default risk among booked accounts given their pre-decision prefix.

**Why this is primary.** It is directly observed for every case in the target population. It needs no imputed outcomes and no assumption about what would have happened to rejected applicants. It answers the risk-monitoring question for accounts the lender books under the current policy. Its identification requires only that the labeled cohort's outcomes are correctly recorded and that the window is fully observed. It does not identify the risk of a random applicant. That transport requires the assumptions in Section 3.

**Credible alternatives:**

- **A. Competing-risk multi-state target for all applications.** States: activated, then default, rejected, withdrawn, transferred, or open at the cutoff. The estimand is the cumulative incidence of "default within 90 days of activation" among all applications, using a Aalen-Johansen-type estimator with competing terminal events. It answers "what fraction of applicants will become defaulted accounts under the observed policy?" It is identifiable only under the observed policy and independent censoring of open cases. It is the closest match to the business wording "for every application," but it measures a policy-mixed quantity. It is not a pure applicant-risk score.
- **B. Time-to-default after activation with right censoring.** The outcome is time from activation to default, with censoring at the earlier of the 90-day window end, feed end, or cutoff. This uses the 3,600 immature accounts with partial follow-up. It answers a hazard question and suits a survival or discrete-time hazard model. It requires non-informative censoring given the prefix.
- **C. Policy-specific counterfactual target.** Examples: P(default | prefix, would be activated under policy ) or P(default | prefix, rejected). The second is undefined because rejected applicants are never exposed to credit. The first requires exchangeability across the 1 July 2025 threshold change, positivity in both policy regimes, and that the default process is unchanged by the policy. These are strong assumptions. The threshold change provides natural variation, but it is not randomization.

Rejected, withdrawn, transferred, and open applications are never coded as non-default in any formulation.

## 2. Cohort construction

**Inclusion (primary analysis):**
1. Application Started between 1 Jan 2024 and 31 Dec 2025 (by start time, not extraction time).
2. Account Activated observed.
3. Labeled outcome: `default_90d` is non-missing and `label_available_at`  15 Feb 2026.
4. Prediction-eligible: at least K = 3 events, with the K-th event strictly before the first decision or activation event.

**Exclusions from primary analysis (retained elsewhere as noted):**
- Non-activated applications (rejected, withdrawn, transferred, open). Used in the competing-risk sensitivity.
- Activated accounts without matured labels. Used in the time-to-event sensitivity.
- Short cases with fewer than K events before decision. Used for activation-selection modeling.
- Exact duplicate events created by the migration. Removed before counting.

**As-of rules:**
- Features use only events with `time:timestamp`  t_p, and only the values that existed at that time (see Section 6).
- Labels enter training only if `activated + 90 days + 35 days`  the fold's evaluation cutoff. This is the maturity rule. Each training set is filtered this way, not only the validation set.
- `data_extract_time` is a global cutoff and is never a feature.

**Cohort-flow table (48,000 applications):**

| Category | N | Status | Treatment |
|---|---|---|---|
| Applications started | 48,000 | Total | Reconciliation anchor |
| Labeled export: non-default | 18,900 | Labeled, activated | Primary analysis (non-default) |
| Labeled export: default | 2,700 | Labeled, activated | Primary analysis (default) |
| Activated, immature (outcome or feed pending) | 3,600 | Right-censored (administrative) and not yet labeled | Excluded from primary binary model; used in time-to-event sensitivity |
| Activated, feed permanently missing | Unknown; must be counted | Selectively unobserved | Not default-coded; tipping-point sensitivity |
| Rejected | 9,100 | Competing terminal event; default undefined | Excluded from primary; used in competing-risk analysis |
| Withdrawn | 5,700 | Competing terminal event (applicant-driven) | Excluded from primary; sensitivity on non-ignorable withdrawal |
| Transferred | 2,900 | Missing follow-up; about 60% linked (about 1,740) | Linked: may recover follow-up. Unlinked (about 1,160): missing follow-up |
| Open at cutoff | 5,100 | Administrative censoring before decision | Excluded from training; scored later for drift only |

Check: 21,600 + 9,100 + 5,700 + 2,900 + 5,100 + 3,600 = 48,000.

**Two warnings:**
- The 21,600 labeled rows are an activation-selected subset. Their 12.5% default rate describes booked accounts, not applicants.
- Permanently missing feeds may be silently coded as `default_90d = 0` or omitted from the export. This must be verified before any analysis. The export's omission of them would shift the labeled cohort.

## 3. Censoring and missing-label strategy

**Mechanisms, distinguished:**
1. **Ordinary right censoring:** Activated accounts whose 90-day window has not closed by the cutoff. Their outcome is unknown, but they are not missing at random. Their observation time is known.
2. **Delayed labels:** Windows closed but the external feed arrives 7 to 35 days late. The label is missing for a reason that is independent of the outcome, provided the delay is not related to default. This is testable.
3. **Selection through activation:** Outcomes exist only for activated accounts. This is not censoring. Default is undefined for rejected applicants under the observed policy. The labeled cohort is a selected sample, and selection depends on the prefix and on the decision.
4. **Transfer as competing event or missing follow-up:** Transferred accounts can continue on another platform. If linked, follow-up may continue. If unlinked, follow-up is lost. Transfer is best treated as a competing event for the all-applicant target and as informative missingness otherwise.
5. **Permanently missing outcome feeds:** Partner-originated accounts are more likely to lack a feed. This is missing not at random unless the missingness depends only on observed variables.

**Primary analysis strategy:** Complete-case, activation-conditional, binary classification on the matured labeled cohort. Each included case has a complete 90-day window and an observed feed. Temporal validation (Section 7) handles calendar-driven selection. Immature cases are excluded, which is ignorable for this binary target only if their exclusion is unrelated to default given the prefix and calendar period. This is a partially testable assumption, and the temporal design mitigates it. The primary analysis targets the activation-conditional estimand, not the all-applicant estimand.

**Sensitivity analyses:**
- **S1: Time-to-event with censoring.** Discrete-time hazard or cause-specific Cox model using all activated accounts, censored at min(default, 90 days, feed end, cutoff). Adds the 3,600 immature accounts. Assumes independent censoring given the prefix.
- **S2: Inverse-probability weighting for activation.** Estimate P(activated | prefix, period) on all applications, then weight the labeled cohort to target the all-applicant risk. Requires positivity and no unmeasured confounding of activation and default.
- **S3: Manski-type bounds for unconditional all-applicant default.** Lower bound: treat every non-activated, non-matured application as non-default. Upper bound: treat them as default. Immature and open cases are shown as unknown. These bounds are wide, and that width is the honest answer.
- **S4: Transfer handling.** Compare (a) linked transfers with follow-up continued, (b) transfers censored, (c) transfers treated as default-unknown. Report the spread.
- **S5: Tipping-point analysis for permanently missing feeds.** Let the default odds among feed-missing accounts equal  times those among feed-observed accounts with the same prefix. Report how conclusions change over a plausible  range (for example, 0.5 to 3).

**Testability:**

| Assumption | Status | How |
|---|---|---|
| Label maturity is complete for matured windows | Testable | Count missing labels by activation week |
| Immature exclusion unrelated to prefix/default | Partially testable | Compare prefix distributions of matured vs immature accounts within the same calendar window |
| Activation depends only on observed prefix | Partially testable | Compare prefix distributions across status, within each regime |
| No unmeasured confounding of activation and default | Fundamentally untestable | Only sensitivity analysis (S2, S5) |
| Transfer censoring non-informative | Partially testable | Compare linked transfers' prefixes and outcomes with the rest |
| Feed missingness MAR given partner | Partially testable | Compare feed-missing rates across observed covariates |
| Feed missingness MNAR | Fundamentally untestable | Tipping point only (S5) |
| Policy-stable selection | Testable | Compare activation rates by prefix across regimes |

## 4. Prefix extraction

**Fixed-count prefixes (primary).** Use K = 3 events after deduplication and activity renaming. Count events in timestamp order per case. A case is prediction-eligible only if its third event exists and occurs strictly before the first decision or activation event. Sensitivities: K = 2 and K = 4.

**Elapsed-time prefixes (sensitivity).** Use all events with timestamp  start + 72 hours, capped at K events for comparability. Report results for 24 and 72 hours. Elapsed-time prefixes make early decisions and rework loops more visible but produce variable information horizons.

**Short cases.** Cases with fewer than K events before their first decision are excluded from the primary cohort and logged. Their existence is informative, so their rate is reported by regime.

**Document loops.** A loop (Credit Review  Documents Requested  Credit Review) adds events to the raw sequence. Two representations are used:
- Raw K events for timing and the prefix cutoff, so every case has the same information horizon.
- Collapsed stage sequence for control-flow features: repeated Credit Review events become a count rather than extra prefix length.

A loop can push the K-th event past the decision time. The guard in Section 4's code excludes such cases from the primary cohort, and the exclusion rate is reported.

**Activity renaming and duplicates.** The migration on 15 October 2025 renamed activities and created duplicates. Renaming uses an explicit map. Unmapped names are printed and must be resolved before analysis; they are not silently dropped. Exact duplicates on case, activity, timestamp, and resource are removed. Near-duplicates (same activity within one second) are collapsed. Duplicate rates are compared before and after migration. Directly-follows graph (DFG) differences across the migration are inspected for unexpected new arcs.

**pm4py.get_prefixes_from_log.** This is used as a cross-check on trace counts, not as the source of the design matrix. The manual K-prefix construction is the source, because it lets the as-of rules and the leakage whitelist be enforced explicitly. A count mismatch means PM4Py's prefix semantics differ in the installed version and must be investigated.

## 5. Process-aware features

Features are grouped by type. All must be computable at t_p.

**Static case attributes (available at start):**
- `channel`, `region`, `requested_amount` (as at start; check whether it is revised)
- `source_system`, used to derive a partner-origin flag, after checking that its encoding did not change at migration

**Prefix-derived features (from events  t_p):**
- *Control flow:* the K-event activity sequence, number of distinct stages reached, whether Credit Review occurred.
- *Timing:* `hours_start_to_tp`, inter-event gaps, time from start to first Credit Review.
- *Rework:* number of Documents Requested events, number of Credit Review returns within the prefix, time spent in the document loop.
- *Score:* the first non-null `risk_score` within the prefix. Later updates are excluded.

**Resource and queue features (require event-log history):**
- Resource ID at the first Credit Review event (hashed or grouped, not raw, due to sparsity).
- Queue length at the start of review: number of applications in Credit Review status at that timestamp, computed from the log as of that time.
- Resource workload over the preceding 7 days, as of the event time.
- Resource experience: number of prior completed reviews by that resource before the event time. This replaces the extraction-time experience field.

**Cohort and calendar features:**
- Start month or week, weekday, policy regime (before or after 1 July 2025), migration indicator (after 15 October 2025).
- Calendar-level features (for example, daily application volume) are computed from prior starts only.

**Historical reference features (require lagged reference data):**
- Historical default rate by channel or partner, computed only from labeled cohorts that matured before the prediction time, with a 125-day lag. Target encoding must be done inside each training fold.
- Partner feed-missing rate by period, computed as of the training cutoff.

**PM4Py helpers:**
- `pm4py.extract_temporal_features_dataframe` can generate calendar features from a timestamp column. Use it only on prefix-level or start-level timestamps, not on post-prefix events.
- `pm4py.insert_case_service_waiting_time` can compute waiting times between events. Its interpretation depends on the activity lifecycle; use it only on prefix events and verify the definition matches the queue concept.
- `pm4py.get_variants` can describe prefix or stage-sequence coverage by regime, which is useful for checking whether a policy change altered the observed control flow.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final credit decision, so it is a post-prefix consequence of the decision | Available only after the final decision, which is after t_p | Drop | Using it would encode the decision the model is supposed to inform. Could be used descriptively in a separate analysis of limit-default relationships |
| `decision_reason` | Written at or after Accept or Reject; reveals policy outcome and possibly manual review | Only after the decision event | Drop | Post-prefix. Could be used in a separate policy audit, not as a feature |
| `collection_status` | Updated after activation and may directly reveal default | Only after activation; can be after the outcome | Drop | Direct outcome leakage. Also not usable as an early-warning signal |
| Future events (any event with timestamp > t_p) | Prefix contains later Contract Signed, Activated, Collections, Default Recorded | Only events with timestamp  t_p | Drop | Enforced by the whitelist and by the `time:timestamp > t_p` audit |
| `documents_total` | Nightly snapshot includes documents uploaded later the same day | Count of upload events with timestamp  t_p | Repair | Recompute from event-level uploads; the snapshot cannot be time-stamped precisely |
| `risk_score` (updated) | Latest value may be set after review or after decision | Value of the first non-null score within the prefix, using its own timestamp | Repair | Keep the as-of value; drop later updates; log the number of updates inside the prefix |
| Resource experience | Stored at extraction time, so it counts reviews made after the event | Count of reviews completed by the resource before the event time | Repair | Recompute from the event log as of each event's timestamp |
| `label_available_at` | Reveals whether an outcome exists; availability is tied to the future | Used only for eligibility and censoring, applied at the fold's cutoff | Repair (use for eligibility only) | Using it as a feature encodes future data availability; using it as a filter is required for as-of correctness |
| `default_90d` | Outcome | Known only after the 90-day window and feed | Drop as feature; keep as label | Target only |
| `data_extract_time` | Global clock that changes between extracts | Not a feature | Drop as feature; use as global cutoff | Duration-to-extraction features leak future censoring |
| Transfer linkage table | Links to outcomes on other platforms, which may be observed after the prefix | Use only to recover follow-up for label construction | Drop as feature; repair for labels | Using linkage as a feature would leak future follow-up information |
| Activity names (pre- and post-migration) | Renaming changes the sequence vocabulary; a mismatch creates artificial regime differences | Mapped names with a documented table | Repair | Prevents spurious drift from renaming alone |
| Duplicate events | Duplicates inflate event counts and rework features | Unique by case, activity, timestamp, resource | Repair | Changes K-prefix composition and loop counts |
| `requested_amount` | May be revised later | Value as of the start event, or first observed value before t_p | Keep, with check | Revisions after t_p would be leakage |
| `channel`, `region` | Stable over time, but encoding may change | As at start | Keep | Standard static features |

## 7. Validation design

**Temporal, expanding-window backtesting by case start time.** Folds respect both calendar time and label maturity:

- **Fold 1:** Train on starts in 2024 whose activation + 125 days  30 June 2025. Validate on starts from January to June 2025. Both are pre-policy.
- **Fold 2:** Train on starts through June 2025 with the same maturity filter. Test on starts from 1 July 2025 to 14 October 2025. This tests the policy shift. Many late starts in this window will still be immature, so the test is only as large as the matured cases allow. Report the count.
- **Migration era (15 October 2025 onward):** Largely unlabeled at the cutoff. Use it only for covariate drift, score distribution, activation rate, and rework-rate monitoring. Do not report it as a performance benchmark until labels mature in a later extract.

**Why a random split is misleading here:**
- It mixes pre- and post-policy cases, so the test measures performance under a mixture of selection rules, not under the rule that will apply at deployment.
- It places the same resources and partners in both sets, which inflates performance through resource-specific patterns.
- It ignores label maturity: a random test set can contain cases whose labels were unavailable at training time.
- It can split duplicate or migrated events across sets.
- It hides distribution shift that is the main risk for deployment.

**Calibration.** Calibration is central because the score will be used as a risk estimate. Report:
- calibration-in-the-large (mean predicted vs observed default rate) by regime;
- calibration slope and intercept on the validation fold;
- decile-level reliability plots;
- recalibration (for example, logistic recalibration) fit on the most recent mature fold only, and tested forward.

**Subgroup performance.** Report by channel, region, partner origin, resource experience deciles, and regime. Use cluster bootstrap by resource or partner for confidence intervals, because cases share resources and partners.

**Metrics:**
- Discrimination: AUROC and AUPRC (base rate about 12.5% in the labeled cohort, so AUPRC should be read against that base rate).
- Calibration: Brier score, calibration slope and intercept, expected calibration error.
- Decision utility: net benefit at the thresholds the lender would use (decision curve analysis).
- For the time-to-event sensitivity (S1): time-dependent AUC and Brier score at 90 days with inverse-probability-of-censoring weights.

**Distribution shift monitoring.** Population stability index (PSI) for each feature. Score distribution by regime. Activation rate and prefix mix by regime, which shows the denominator changing. Rework-loop rate after migration, which signals process change. Alerts should trigger a review, not automatic retraining.

## 8. Limitations and decision-use boundary

**What the study can claim:**
- Among accounts activated under the observed policy, pre-decision prefixes predict 90-day default with measured discrimination and calibration, validated forward in time.
- Predictive association, under the stated temporal split, with calibration reported by regime.

**What the study cannot claim:**
- Causal effects of prefix features, resources, or queue length on default.
- The default risk of rejected, withdrawn, or transferred applicants. These are undefined under the observed policy.
- The all-applicant default rate without the assumptions in S2 and S3, which yield bounds, not a point estimate.
- Calibration after the migration or after the policy change without labels from those periods.
- Performance for partner accounts with missing feeds, because the missingness mechanism is untestable.

**Three levels of claim, kept separate:**
- **Predictive association:** the model's score correlates with observed default among booked accounts with similar prefixes.
- **Selection effect:** the labeled population differs from applicants because of activation, and the policy changed the selection rule.
- **Counterfactual default risk:** what default risk would be under a different policy or for a rejected applicant. This needs strong assumptions and is not estimated here.

**Ways deployment could change the data-generating process:**
1. **Score-driven decisions change the activation population.** If the score is used to reject applicants, the labeled cohort after deployment will be a different, more selected group. The model's calibration in that population is unknown. This is performative prediction.
2. **Score-driven routing changes process behavior.** If high-score applications are fast-tracked or sent to manual review, queue lengths, document loops, and resource assignments change. Features built on these patterns will drift.
3. **Feedback loops with collections.** If the lender changes collections for high-score accounts, default recording itself may change, altering the outcome definition.
4. **Partner routing.** If partners are steered toward or away from specialist platforms, the transfer rate and feed-missingness pattern will shift, affecting label availability.
5. **Resource allocation.** If experienced staff are assigned to high-score cases, resource experience becomes confounded with the score, and the model may learn an allocation artifact rather than a risk relationship.

## 9. PM4Py-oriented Python implementation skeleton

```python
import numpy as np
import pandas as pd
import pm4py

# ---- Assumptions (make them explicit; change only with a documented decision) ----
CUTOFF = pd.Timestamp("2026-02-15")           # data_extract_time: global as-of date
K = 3                                         # fixed prefix length in events
HORIZON = pd.Timedelta(days=90)               # default window after Account Activated
FEED_LAG = pd.Timedelta(days=35)              # max delay of external outcome feed
POLICY = pd.Timestamp("2025-07-01")           # credit-policy threshold change
MIGRATION = pd.Timestamp("2025-10-15")        # activity renaming / duplicate events
RENAME = {"KYC Check": "Identity/KYC Check"}  # illustrative; validate against migration log
A = dict(start="Application Started", review="Credit Review", docs="Documents Requested",
         accept="Application Accepted", activated="Account Activated",
         rejected="Application Rejected", withdrawn="Application Withdrawn",
         transferred="Application Transferred")
KNOWN = set(A.values()) | {"Identity/KYC Check", "Documents Uploaded"}

# ---- 1. Load, parse, standardise ----
raw = pd.read_csv("applications_events.csv")
raw["time:timestamp"] = pd.to_datetime(raw["time:timestamp"], errors="coerce")
raw["label_available_at"] = pd.to_datetime(raw["label_available_at"], errors="coerce")
raw["default_90d"] = pd.to_numeric(raw["default_90d"], errors="coerce")
df = pm4py.format_dataframe(raw, case_id="case:concept:name",
                            activity_key="concept:name", timestamp_key="time:timestamp")
df["concept:name"] = df["concept:name"].replace(RENAME)
print("unmapped activities:", sorted(set(df["concept:name"]) - KNOWN))  # must be empty
# Migration duplicates: identical case, activity, timestamp and resource -> keep one row
df = df.drop_duplicates(["case:concept:name", "concept:name", "time:timestamp", "org:resource"])

# ---- 2. Case-level status as of CUTOFF (for cohort and labels only, never features) ----
first = df.groupby(["case:concept:name", "concept:name"])["time:timestamp"].min().unstack()
keys = ["start", "accept", "activated", "rejected", "withdrawn", "transferred"]
case = first.reindex(columns=[A[k] for k in keys])
case.columns = keys
lab = df.groupby("case:concept:name").agg(default=("default_90d", "max"),
                                          label_at=("label_available_at", "max"))
case = case.join(lab)
has_act = case["activated"].notna()
labeled = has_act & case["default"].notna() & (case["label_at"] <= CUTOFF)
feed_missing = has_act & case["default"].isna() & (case["activated"] + HORIZON + FEED_LAG <= CUTOFF)
case["status"] = np.select(
    [labeled, feed_missing, has_act,
     case["rejected"].notna(), case["withdrawn"].notna(), case["transferred"].notna()],
    ["labeled", "activated_feed_missing", "activated_immature",
     "rejected", "withdrawn", "transferred"],
    default="open")
print(case["status"].value_counts())
assert len(case) == 48_000, "cohort does not reconcile to the 48,000 snapshot"

# ---- 3. Fixed-length prefixes as of the K-th event (labeled cohort in this skeleton) ----
ids = case.index[case["status"] == "labeled"]
ev = df[df["case:concept:name"].isin(ids)].copy()
ev["rank"] = ev.groupby("case:concept:name").cumcount() + 1
pre = ev[ev["rank"] <= K]                     # the ONLY events allowed to build features
# Cross-check of trace counts with PM4Py's prefix utility (not the feature source)
pref_log = pm4py.get_prefixes_from_log(pm4py.convert_to_event_log(ev), length=K)
print("pm4py prefix traces:", len(pref_log), "| manual cases with >=K events:",
      int((ev.groupby("case:concept:name").size() >= K).sum()))

g = pre.groupby("case:concept:name")
feat = pd.DataFrame({
    "n_events": g.size(),
    "t_p": g["time:timestamp"].max(),                  # as-of prediction time
    "channel": g["case:channel"].first(),
    "region": g["case:region"].first(),
    "amount": g["case:requested_amount"].first(),
    "source": g["source_system"].first(),
    "risk_at_tp": g["risk_score"].first(),            # first non-null score inside prefix only
    "n_doc_requests": pre[pre["concept:name"] == A["docs"]].groupby("case:concept:name").size(),
})
feat["n_doc_requests"] = feat["n_doc_requests"].fillna(0)
feat["hours_start_to_tp"] = (feat["t_p"] - case["start"].reindex(feat.index)).dt.total_seconds() / 3600

# As-of guard: prefix must end strictly before any decision or activation event
first_decision = case[["accept", "activated", "rejected", "withdrawn", "transferred"]].min(axis=1)
feat = feat.join(first_decision.rename("first_decision"))
feat = feat[(feat["n_events"] == K) & (feat["t_p"] < feat["first_decision"].fillna(CUTOFF))]
print("prefix-eligible labeled cases:", len(feat))

# ---- 4. Leakage audit: whitelist, post-prefix exclusion, forbidden-column check ----
FEATURES = ["n_events", "channel", "region", "amount", "source",
            "risk_at_tp", "n_doc_requests", "hours_start_to_tp"]
FORBIDDEN = {"final_limit", "decision_reason", "collection_status", "default_90d",
             "label_available_at", "documents_total", "data_extract_time"}
assert not (FORBIDDEN & set(FEATURES)), "forbidden column in design matrix"
post = ev.join(feat[["t_p"]], on="case:concept:name", how="inner")
print("post-prefix events excluded:", int((post["time:timestamp"] > post["t_p"]).sum()))

# ---- 5. Temporal split by case start (start is used to split, never as a feature) ----
# NOTE: for true backtesting, each training set must also satisfy
# activated + HORIZON + FEED_LAG <= fold cutoff. This skeleton shows the split geometry only.
data = feat.join(case[["start", "default"]], how="inner").dropna(subset=["default"])
train = data[data["start"] < "2025-01-01"]                                # 2024, pre-policy
valid = data[(data["start"] >= "2025-01-01") & (data["start"] < POLICY)]  # H1 2025, pre-policy
test = data[data["start"] >= POLICY]                                      # post-policy
for name, part in [("train", train), ("valid", valid), ("test", test)]:
    print(name, len(part), round(float(part["default"].mean()), 3))
print("labeled starts on/after migration:", int((data["start"] >= MIGRATION).sum()))

# ---- 6. Regime audit: control-flow drift across the migration (descriptive) ----
dfg_pre, _, _ = pm4py.discover_dfg(df[df["time:timestamp"] < MIGRATION])
dfg_post, _, _ = pm4py.discover_dfg(df[df["time:timestamp"] >= MIGRATION])
print("arcs seen only after migration:", sorted(set(dfg_post) - set(dfg_pre))[:10])

# TODO(survival): for the S1 time-to-default sensitivity, connect a discrete-time hazard
# or cause-specific Cox / Fine-Gray model here, with censor time =
# min(default, 90 days after activation, feed end, CUTOFF). No PM4Py survival API is used.
# TODO(IPW): for S2, fit P(activated | prefix, regime) on all applications and weight.
```
