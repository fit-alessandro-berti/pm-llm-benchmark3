## 1. Normalization Assumptions

I interpret each timestamp as an interval for the source clock, apply its stated display-resolution uncertainty, convert the local wall time to UTC, then subtract the source clock-offset interval. With offset = recorded clock − true clock, a recorded interval [rₗ,rᵤ] and offset [a,b] produce true-time interval [rₗ−b,rᵤ−a]. HUB’s displayed second has ±0.5 s measurement uncertainty before its offset bound, so its true-time interval is displayed time ±1.5 s. Endpoints below are shown to milliseconds; where rounding creates a half-open interval, I show the upper endpoint with “)” and use the closed millisecond approximation for duration calculations. Those endpoint conventions do not change any classification.

Floor-to-minute values cover the displayed minute through, but not including, the next minute. Nearest-minute values cover ±30 s; nearest-10-second values cover ±5 s. Berlin is UTC+2 (CEST) and London is UTC+1 (BST) for the June 2026 cases; New York is UTC−4 (EDT). For 2025-10-26 in Berlin I construct both UTC-offset folds, then retain only fold combinations consistent with the logged ingestion order. That leaves T-405 Alert_Received in the first fold and Investigation_Start and Containment_Complete in the second fold. The minute rounding and ±60 s clock bound still apply within those folds.

For T-404 I infer Investigation_Start by subtracting the signed record’s 18–25 minute elapsed duration from Investigation_Complete, retaining both timestamp and duration uncertainty. For T-407 I infer a possible Alert_Received interval from Alert_Sent plus [0,20] minutes of delivery latency, then condition it on receipt occurring no later than Investigation_Start. This causal constraint is plausible but not directly acknowledged; T-407’s S1 result is conditional on it. Without that assumption S1 is indeterminate because the received event/order is not established. In all eventually-following pairs I constrain feasible durations to be nonnegative.

For T-406 I treat the additional possible five-minute user-entry delay as late recording of the occurrence: after resolution and source-clock correction, I subtract an independent [0,300] s delay from the estimated occurrence time. If the delay only describes when the record was entered and does not estimate occurrence, the actual Investigation_Start cannot be bounded this way and related findings would be indeterminate. HUB bounds are propagated conservatively per event; I do not assume clock errors cancel between events.

For baseline classifications, SLA tolerance addition is zero and profile zeta is 1. An SLA accepts duration [0, maximum+tolerance]. A profile pair accepts its two-sided average ± zeta·standard-deviation band. I classify a duration interval as CERTAIN_PASS if wholly accepted, CERTAIN_VIOLATION if wholly outside, and POSSIBLE_VIOLATION if it has both accepted and violating feasible durations. Statistical-profile results are not legal SLA findings.

## 5. PM4Py Temporal-Conformance Code

The code builds its event evidence in memory and does not read files. It uses conservative interval arithmetic, Python’s zoneinfo for local-time conversion, and explicitly keeps the LEGACY-BER fold alternatives until ingestion ordering filters them. The midpoint log is a lossy approximation for diagnostics; PM4Py receives point timestamps and does not resolve timestamp uncertainty. The conformance result shape can vary by PM4Py version, so the code prints the returned object and only assumes that the call accepts the documented temporal-profile mapping and zeta argument. Install pandas and pm4py in the Python environment before running.

Interval = tuple[datetime, datetime]

def plus_seconds(t: datetime, seconds: float) -> datetime:

def normalize_one(recorded_text: str, system: str, fold: int = 0) -> Interval:
    zone_name, semantics, (offset_lo, offset_hi) = META[system]
    zone = ZoneInfo(zone_name)
    naive = datetime.fromisoformat(recorded_text)
    # Construct the source-clock interval before applying its clock correction.
    if semantics == "exact_second":
        wall_lo, wall_hi = naive - timedelta(seconds=0.5), naive + timedelta(seconds=0.5)
    elif semantics == "floor_minute":
        wall_lo, wall_hi = naive, naive + timedelta(minutes=1)
    elif semantics == "nearest_10":
        wall_lo, wall_hi = naive - timedelta(seconds=5), naive + timedelta(seconds=5)
    elif semantics == "nearest_minute":
        wall_lo, wall_hi = naive - timedelta(seconds=30), naive + timedelta(seconds=30)
    else:

    return (lo - timedelta(seconds=offset_hi),
            hi - timedelta(seconds=offset_lo))

    # For T-406, the entry may be up to five minutes later than occurrence.
    if row.case == "T-406" and row.activity == "Investigation_Start":
        candidates = [(lo - timedelta(seconds=300), hi) for lo, hi in candidates]
    return candidates

events: dict[tuple[str, str], list[Interval]] = {}
for row in raw.itertuples(index=False):

def ordered_fold_combinations(interval_lists: list[list[Interval]]) -> list[tuple[Interval, ...]]:
    good = []
    for combo in product(*interval_lists):
        # There must be a nonnegative possible duration at each ingestion step.
        if all(combo[i][0] <= combo[i + 1][1] for i in range(len(combo) - 1)):
            good.append(combo)
    return good

# Keep only LEGACY fold intervals which participate in an order-consistent triple.
legacy_keys = [
    ("T-405", "Alert_Received"),
    ("T-405", "Investigation_Start"),
    ("T-405", "Containment_Complete"),
]

    participating = {combo[idx] for combo in legacy_combos}
    events[key] = sorted(participating)

# T-404: infer start = completion − signed elapsed duration [18,25] minutes.
comp_lo, comp_hi = events[("T-404", "Investigation_Complete")][0]

events[("T-407", "Alert_Received")] = [
    (sent_lo, min(sent_hi + timedelta(minutes=20), start_hi))

def duration_intervals(case: str, first: str, second: str) -> list[tuple[float, float]]:
    left = events.get((case, first), [])
    right = events.get((case, second), [])
    out = []
    for a_lo, a_hi in left:
        for b_lo, b_hi in right:
            lo = (b_lo - a_hi).total_seconds()
            hi = (b_hi - a_lo).total_seconds()
            # These supplied profile pairs are eventually-following pairs.
            if hi >= 0:
                out.append((max(0.0, lo), hi))
    return out

def classify(durations, accept_lo: float, accept_hi: float) -> str:
    if not durations:
        return "INDETERMINATE"
    has_pass = any(hi >= accept_lo and lo <= accept_hi for lo, hi in durations)
    has_violation = any(lo < accept_lo or hi > accept_hi for lo, hi in durations)
    if has_pass and has_violation:
        return "POSSIBLE_VIOLATION"
    if has_violation:
        return "CERTAIN_VIOLATION"
    return "CERTAIN_PASS"

## 6. Evidential Sufficiency

A POSSIBLE_VIOLATION is not proof of breach. For any such result, enough new evidence must narrow the feasible duration wholly into the acceptance region or wholly outside it. At baseline, the cases requiring that resolution are:

- T-401 S1 and Alert→Investigation profile: obtain an event-level synchronized Investigation_Start (or a better OPS-BER clock trace) and retain the corresponding HUB alert measurement. That must resolve whether the duration is at most 900 s for S1 and at most 780 s for the zeta-1 profile.
- T-402 S1 and Investigation→Containment S2/profile: source-clock or lifecycle evidence must decide on which side of 900 s and 2700 s the respective true durations lie. For Alert→Investigation profile at zeta 2/3, tighten the same OPS-BER bound enough to settle the 960 s/1140 s edges.
- T-403 S1, Alert→Investigation profile, and Alert→Containment profile: the minimum useful evidence is a vendor event-level UTC synchronization/error bound narrow enough to settle the relevant 900 s, 780 s, and 3420 s boundaries. Better HUB data alone cannot remove the vendor uncertainty.
- T-404 S1, S2, and the two corresponding profile pairs: improve the signed duration bound and/or provide the actual start event with a synchronized timestamp. S2 needs evidence that places the duration wholly on one side of 2700 s; the current interval spans that boundary. This is missing-activity/duration evidence, not merely a time-zone issue.
- T-405 S1 and Alert→Investigation profile: the ingestion order already determines the surviving folds. A precise event timestamp or tighter legacy clock-offset evidence is needed to resolve the remaining minute/offset interval around 900 s and the 780 s profile edge. A DST fold field would independently make the audit trail reproducible.
- T-406 S1, S2, Alert→Investigation profile, and Investigation→Containment profile: first establish whether the five-minute delay estimates occurrence or only record-entry time. Then use a system-generated event timestamp or a signed entry/occurrence pair plus tighter mobile clock evidence. Without that semantic and event evidence, further arithmetic cannot decide the true durations.
- T-407 S1 and Alert→Investigation profile: a receipt acknowledgment or network delivery record tied to this alert is the minimum semantic/missing-event evidence. It must establish actual receipt and its order relative to investigation start. Under that receipt premise, tighter delivery-latency evidence can then decide the 900 s SLA and the profile band. Without it, classify the pair as INDETERMINATE.
- T-408 has no baseline POSSIBLE_VIOLATION. At zeta 2, Investigation→Containment becomes possible; a tighter pair of lifecycle timestamps would settle whether it is within 900–3300 s. Other profile/SLA findings remain certain at the tested thresholds.
- T-409 S1, Alert→Investigation profile, and Investigation→Containment profile: obtain NTP diagnostics or another trusted offset measurement for the OPS-BER host at the event hour. The current ±12 min engineering estimate overwhelms the profile and SLA boundaries.

These sufficiency statements apply to any POSSIBLE_VIOLATION introduced by the sensitivity table as well: compare the narrowed duration with that particular tolerance or zeta band edge. To make a POSSIBLE_VIOLATION certain as a violation, evidence must put every feasible duration outside the acceptance region; to make it a certain pass, evidence must put every feasible duration inside. Evidence that merely shrinks the interval while it still crosses an edge does not resolve it.

## 7. Governance Recommendation

Store event occurrence timestamps in UTC while retaining the original timestamp string, source time zone, offset or fold, clock-offset estimate and uncertainty, display resolution and rounding semantics, and ingestion time. Keep provenance that distinguishes source-generated times, user-entered times, inferred events, and downstream transformations.

Collect per-source clock telemetry with event-time-relevant bounds and preserve it alongside events. Record explicit lifecycle semantics for start, completion, sent, delivered, and acknowledged; do not equate Alert_Sent with Alert_Received. Use causal/correlation identifiers to tie alerts, delivery receipts, investigations, and containment actions together. For mobile entry, capture both occurrence time and entry time when possible, and label which one a timestamp represents. For ambiguous local times, require an explicit UTC offset or fold value.

For enforcement, retain interval-valued event times and compare the full feasible duration set to the SLA. Enforce automatically only when the feasible interval is a certain violation under the approved clock and event semantics. Treat interval overlap with the violation region as an investigation trigger, not a proven breach; escalate it for better evidence. Keep statistical temporal-profile conformance separate from legal SLA enforcement, and version the chosen zeta and tolerance policy with each report.
