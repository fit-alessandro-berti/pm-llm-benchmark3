# 1. Assumptions and Interpretation

1. **Low-risk/high-risk choice**: Represented as an exclusive choice (XOR) between `Supervisor Review` (low risk) and a parallel execution of `Quality Review` and `Regulatory Review` (high risk).
2. **Optional supplier consultation**: Represented as an exclusive choice (XOR) between the `Consult Supplier` activity and a silent transition (tau), allowing it to be skipped.
3. **Passing inspection abstraction**: Represented as the silent exit transition (tau) of a LOOP operator. The loop body executes the trial and inspection; upon failure, the redo block (`Adjust Parameters`) is executed before repeating the body. A passing inspection triggers the silent exit transition, terminating the loop.
4. **Duplicate visible labels**: Not permitted. Both models are constructed such that each visible activity appears exactly once, avoiding ambiguity in trace analysis and state-space explosion.
5. **Approximation policy for the process tree**: A conservative under-approximation is used. Because a process tree must be block-structured, we cannot express the cross-branch dependencies directly. We place `Contain Material` and `Analyze Root Cause` in a parallel block that must fully complete before the subsequent parallel block (containing planning, design, approvals, etc.) begins. This restricts intended concurrency (e.g., `Plan Verification` must wait for `Analyze Root Cause` to finish) but safely excludes any unsafe behavior (e.g., starting `Plan Verification` before `Contain Material` is complete).
6. **"May overlap" interpretation**: Interpreted as true concurrency (parallelism). In the models, this means the activities can be executed in any interleaved order or simultaneously, represented by parallel operators or unconnected nodes in a partial order.

# 3. PM4Py Process-Tree Model

```text
-> (
  'Register Deviation',
  + ( 'Contain Material', 'Analyze Root Cause' ),
  + (
    -> (
      + ( 'Plan Verification', 'Design Corrective Action' ),
      * (
        -> ( 'Execute Trial', 'Inspect Trial' ),
        'Adjust Parameters',
        tau
      )
    ),
    X ( 'Supervisor Review', + ( 'Quality Review', 'Regulatory Review' ) ),
    X ( 'Consult Supplier', tau )
  ),
  'Release Material',
  'Archive Case'
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# 1. Root sequence
tree = ProcessTree(operator=Operator.SEQUENCE)

t_RD = ProcessTree(label='Register Deviation')
t_RD.parent = tree
tree.children.append(t_RD)

# 2. First parallel block (Initial work streams)
n_parallel_1 = ProcessTree(operator=Operator.PARALLEL)
n_parallel_1.parent = tree
tree.children.append(n_parallel_1)

t_CM = ProcessTree(label='Contain Material')
t_CM.parent = n_parallel_1
n_parallel_1.children.append(t_CM)

t_ARC = ProcessTree(label='Analyze Root Cause')
t_ARC.parent = n_parallel_1
n_parallel_1.children.append(t_ARC)

# 3. Second parallel block (Planning, Design, Trial, Approvals, Supplier)
n_parallel_2 = ProcessTree(operator=Operator.PARALLEL)
n_parallel_2.parent = tree
tree.children.append(n_parallel_2)

# 3a. Sequence for Trial preparations and Trial cycle
n_seq_trial = ProcessTree(operator=Operator.SEQUENCE)
n_seq_trial.parent = n_parallel_2
n_parallel_2.children.append(n_seq_trial)

n_parallel_prep = ProcessTree(operator=Operator.PARALLEL)
n_parallel_prep.parent = n_seq_trial
n_seq_trial.children.append(n_parallel_prep)

t_PV = ProcessTree(label='Plan Verification')
t_PV.parent = n_parallel_prep
n_parallel_prep.children.append(t_PV)

t_DCA = ProcessTree(label='Design Corrective Action')
t_DCA.parent = n_parallel_prep
n_parallel_prep.children.append(t_DCA)

# Trial loop
n_loop = ProcessTree(operator=Operator.LOOP)
n_loop.parent = n_seq_trial
n_seq_trial.children.append(n_loop)

n_do = ProcessTree(operator=Operator.SEQUENCE)
n_do.parent = n_loop
n_loop.children.append(n_do)

t_ET = ProcessTree(label='Execute Trial')
t_ET.parent = n_do
n_do.children.append(t_ET)

t_IT = ProcessTree(label='Inspect Trial')
t_IT.parent = n_do
n_do.children.append(t_IT)

t_AP = ProcessTree(label='Adjust Parameters')
t_AP.parent = n_loop
n_loop.children.append(t_AP)

t_exit = ProcessTree(label=None) # tau
t_exit.parent = n_loop
n_loop.children.append(t_exit)

# 3b. Approvals XOR
n_app = ProcessTree(operator=Operator.XOR)
n_app.parent = n_parallel_2
n_parallel_2.children.append(n_app)

t_SR = ProcessTree(label='Supervisor Review')
t_SR.parent = n_app
n_app.children.append(t_SR)

n_app_high = ProcessTree(operator=Operator.PARALLEL)
n_app_high.parent = n_app
n_app.children.append(n_app_high)

t_QR = ProcessTree(label='Quality Review')
t_QR.parent = n_app_high
n_app_high.children.append(t_QR)

t_RR = ProcessTree(label='Regulatory Review')
t_RR.parent = n_app_high
n_app_high.children.append(t_RR)

# 3c. Optional Supplier Consultation XOR
n_cs = ProcessTree(operator=Operator.XOR)
n_cs.parent = n_parallel_2
n_parallel_2.children.append(n_cs)

t_CS = ProcessTree(label='Consult Supplier')
t_CS.parent = n_cs
n_cs.children.append(t_CS)

t_skip_CS = ProcessTree(label=None) # tau
t_skip_CS.parent = n_cs
n_cs.children.append(t_skip_CS)

# 4. Release and Archive
t_RM = ProcessTree(label='Release Material')
t_RM.parent = tree
tree.children.append(t_RM)

t_AC = ProcessTree(label='Archive Case')
t_AC.parent = tree
tree.children.append(t_AC)
```

The process tree cannot exactly represent the cross-branch dependencies where `Plan Verification` depends only on `Contain Material`, and `Design Corrective Action` (along with approvals and supplier consultation) depends only on `Analyze Root Cause`. Because the tree must be block-structured, we used a conservative under-approximation by placing `Contain Material` and `Analyze Root Cause` in a parallel block that must fully complete before the subsequent parallel block begins. This forces `Plan Verification` to wait for `Analyze Root Cause` to finish, and forces `Design Corrective Action`, approvals, and supplier consultation to wait for `Contain Material` to finish, which restricts the intended concurrency but safely prevents any activity from starting before its required predecessor.

# 4. PM4Py POWL Model

```text
StrictPartialOrder(
  nodes: {RD, CM, ARC, PV, DCA, APP, CS, TC, RM, AC},
  edges: {
    RD -> CM, RD -> ARC,
    CM -> PV,
    ARC -> DCA, ARC -> APP, ARC -> CS,
    PV -> TC, DCA -> TC,
    TC -> RM, APP -> RM, CS -> RM,
    RM -> AC
  }
)
where:
APP = OperatorPOWL(XOR, ['Supervisor Review', StrictPartialOrder(['Quality Review', 'Regulatory Review'])])
CS = OperatorPOWL(XOR, ['Consult Supplier', tau])
TC = OperatorPOWL(LOOP, [
       StrictPartialOrder(['Execute Trial', 'Inspect Trial'], edges={'Execute Trial' -> 'Inspect Trial'}),
       'Adjust Parameters',
       tau
     ])
```

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

t_RD = Transition(label='Register Deviation')
t_CM = Transition(label='Contain Material')
t_ARC = Transition(label='Analyze Root Cause')
t_PV = Transition(label='Plan Verification')
t_DCA = Transition(label='Design Corrective Action')

# Approvals
t_SR = Transition(label='Supervisor Review')
t_QR = Transition(label='Quality Review')
t_RR = Transition(label='Regulatory Review')
n_APP_high = StrictPartialOrder([t_QR, t_RR]) # No edges, so they are parallel
n_APP = OperatorPOWL(Operator.XOR, [t_SR, n_APP_high])

# Optional Supplier Consultation
t_CS = Transition(label='Consult Supplier')
t_skip_CS = SilentTransition()
n_CS = OperatorPOWL(Operator.XOR, [t_CS, t_skip_CS])

# Trial Cycle Loop
t_ET = Transition(label='Execute Trial')
t_IT = Transition(label='Inspect Trial')
n_TC_do = StrictPartialOrder([t_ET, t_IT])
n_TC_do.order.add_edge(t_ET, t_IT) # Sequence ET -> IT
t_AP = Transition(label='Adjust Parameters')
t_TC_exit = SilentTransition()
n_TC = OperatorPOWL(Operator.LOOP, [n_TC_do, t_AP, t_TC_exit])

t_RM = Transition(label='Release Material')
t_AC = Transition(label='Archive Case')

# Root POWL model
powl = StrictPartialOrder([t_RD, t_CM, t_ARC, t_PV, t_DCA, n_APP, n_CS, n_TC, t_RM, t_AC])

# Add partial-order dependencies
powl.order.add_edge(t_RD, t_CM)
powl.order.add_edge(t_RD, t_ARC)
powl.order.add_edge(t_CM, t_PV)
powl.order.add_edge(t_ARC, t_DCA)
powl.order.add_edge(t_ARC, n_APP)
powl.order.add_edge(t_ARC, n_CS)
powl.order.add_edge(t_PV, n_TC)
powl.order.add_edge(t_DCA, n_TC)
powl.order.add_edge(n_TC, t_RM)
powl.order.add_edge(n_APP, t_RM)
powl.order.add_edge(n_CS, t_RM)
powl.order.add_edge(t_RM, t_AC)
```

In the POWL model, nodes that do not have a directed path between them in the `StrictPartialOrder` are concurrent. For example, `Contain Material` is intentionally unconnected to `Analyze Root Cause`, allowing them to overlap as intended. Similarly, `Plan Verification` is unconnected to `Design Corrective Action`, `APP`, and `CS`, reflecting that planning can proceed independently of design, approvals, and supplier consultation. The `TC` (Trial Cycle) node is unconnected to `APP` and `CS`, which correctly captures the requirement that the trial may overlap with the approval route and supplier consultation. They only synchronize at the `Release Material` node.

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|

# 7. Preferred Representation and Validation Plan

**Preferred Representation:**
The POWL model is strongly preferred. It natively supports partial orders, allowing exact representation of cross-branch dependencies without duplicating labels or resorting to block-structured approximations. It captures the true concurrency of the process while maintaining a compact and readable structure.

**Validation Plan:**
1. **Conversion to Petri Net:** Convert the POWL model to an accepting Petri net using `pm4py.convert_to_petri_net(powl)`.
2. **Soundness Checking:** Verify structural correctness and absence of deadlocks/livelocks by running `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`.
3. **Bounded Playout:** Use `pm4py.play_out(net)` to generate traces and manually inspect them to ensure they match expected behavior. Since the model contains a loop, playout must be bounded to prevent infinite trace generation.
4. **Explicit Trace Tests:** Replay the 8 behavioral witnesses against the generated Petri net using token-based replay or alignment-based conformance checking. Ensure fitness is 1.0 for the 5 allowed traces and <1.0 for the 3 forbidden traces.
5. **Silent Behavior Check:** Specifically verify that the silent transitions (tau) used for the optional `Consult Supplier` and the loop exit do not introduce non-determinism that allows skipping mandatory activities (e.g., ensuring `Release Material` still waits for the XOR blocks to resolve).
6. **Limitations:** Playout cannot exhaustively test all interleavings or infinite loop unrollings. Soundness checking ensures structural correctness but not domain-specific semantic fidelity (e.g., it doesn't know *why* a loop exits, only that it can).

# 8. Final Self-Critique

1. **Semantic weakness:** The abstraction of a passing inspection as a silent loop exit (tau) loses the explicit data-driven outcome of the inspection. In reality, the inspection result (pass/fail) dictates the path, but the model allows non-deterministic choice, meaning the model could theoretically "choose" to exit the loop even if the real-world inspection failed, or loop again if it passed.
2. **Semantic weakness:** The POWL model enforces that `Adjust Parameters` happens strictly after `Inspect Trial` and before the next `Execute Trial`, but does not explicitly capture that `Adjust Parameters` is *only* for failures. A data-aware model would be needed to tie the loop condition to the inspection outcome.
3. **Methodological weakness:** The conservative under-approximation in the process tree significantly limits concurrency. A duplication-based approximation could have preserved the concurrency (e.g., duplicating `Analyze Root Cause` in different branches to allow independent progress), but was avoided to prevent trace ambiguity and state-space explosion.
