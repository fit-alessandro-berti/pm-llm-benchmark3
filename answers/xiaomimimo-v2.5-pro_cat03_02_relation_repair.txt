## 1. Consistency rules and evidence model

I classify every inference rule I will use, and I explain my evidence-combination strategy at the end.

### Hard invariants (violation  certain error)

| ID | Rule |
|---|---|
| H1 | An object referenced in an E2O relation must exist in the objects table. |
| H2 | An event referenced in an E2O relation must exist in the events table. |
| H3 | O2O qualifiers are directional; `DEL-X carries PK-7`  `PK-7 carries DEL-X`. |
| H4 | A `Record Payment` event must relate to exactly one Payment object (domain rule 7 — no event should carry two payments). |
| H5 | No object may be both source and target of the same O2O instance with the same qualifier. |

### Strong defaults (violation  high suspicion, but exceptions exist)

| ID | Rule |
|---|---|
| S1 | `Add Item` relates to one Order and one Item (domain rule 2). This fixes the E2O edges for ev03–ev05. |
| S2 | `Pack Item` relates to exactly one Item and one Package (domain rule 3). A missing package suggests a scanner outage, not a second item. |
| S3 | `Dispatch Package` relates to one Package and one Delivery (domain rule 4). A missing delivery on a dispatch event is suspicious. |
| S4 | `Issue Invoice` relates to one Invoice and one or more Orders (domain rule 6). Every order should eventually be invoiced. |
| S5 | `Record Payment` relates to one Payment and normally one Invoice (domain rule 7). Unapplied cash is possible but unusual for well-matched amounts. |
| S6 | Object lifecycles should be coherent: an object should not have a "later" activity event (e.g., Dispatch) without an "earlier" one (e.g., Pack). |
| S7 | Arithmetic matching (order values summing to invoice total, payment matching order) is strong evidence but never proof (domain rule 6). |

### Weak heuristics (supporting evidence, never decisive alone)

| ID | Rule |
|---|---|
| W1 | Matching identifier prefixes (e.g., scanner_ref `PK8-*`  `PK-8`) are informative but not decisive (domain rule 9). |
| W2 | Proximate timestamps (< 1 hour) between events and related objects increase plausibility. |
| W3 | Matching customer attributes across Order, Invoice, Payment increase plausibility. |
| W4 | Matching route attributes (NORTH) across Package, Delivery, and Dispatch events increase plausibility. |
| W5 | Matching amount attributes between Payment and Invoice or Order increase plausibility. |
| W6 | Object `order_hint` and `route_hint` attributes are soft pointers, not hard links. |

### Evidence against a repair

| ID | Rule |
|---|---|
| E1 | Two events referencing the same `external_ref` should relate to the same Delivery (or the reference is ambiguous). This argues against assigning ev10 to DEL-Y if N-420 already mapped to DEL-X in ev09. |
| E2 | `portal_customer=C17` on ev11 suggests a portal-mediated confirmation that may have lost carrier detail (domain rule 5), arguing against a direct Delivery E2O link. |
| E3 | Assigning both payments to the same Invoice when they have separate amount matches to separate orders conflates lifecycles and reduces analytical value. |
| E4 | A "Confirm Delivery" event with no clear delivery identifier should not be forced into a Delivery E2O relation when an Order-level relation is supported by the portal attribute. |
| E5 | Arithmetically tempting relations (e.g., PAY-2 = ORD-A = 130) may be coincidental when alternative interpretations (PAY-2  future ORD-B invoice) are also coherent. |

### Evidence combination strategy

I use a weighted, defeasible approach:

- **Amount matching** between Payment and Order is strong corroboration when combined with customer match (W3 + W5) but is weakened when an equally valid Invoice match exists (E5).
- **Temporal proximity** (W2) within the same day supports but does not prove a link. Same-timestamp events (ev09 and ev10 at 10:00) may be batch processed but refer to different objects.
- **Identifier prefixes** (W1) are useful for scanner references (`PK8-*`  `PK-8`) but ambiguous for carrier references (`N-42*`).
- **Lifecycle order** (S6) eliminates impossible repairs (e.g., Payment before Invoice) and makes others implausible (e.g., Dispatch before Pack).
- **Cardinality** (S1–S5) constrains the solution space. A `Record Payment` can have only one Payment; `Add Item` should have exactly one Item.
- **Existing O2O structure** provides a skeleton. Relations already stored in `ocel.relations` are treated as more reliable than inferred E2O relations, but I check for circular reasoning when an inferred E2O edge is "confirmed" only by a newly inferred O2O edge.
- **Arithmetic consistency** (S7) is treated as corroborative evidence of rank equivalent to customer + route + time matching, not as proof.

## 5. Lifecycle and cardinality audit

### Order

**ORD-A (Bundle A):** Create Order (ev01)  Add Item ×2 (ev03, ev04)  Pack Item ×2 (ev06, ev07)  Confirm Delivery (ev11)  Issue Invoice (ev12)  Record Payment (ev13). Lifecycle is complete and coherent. Every E2O relation is supported by at least two independent signals (activity semantics + attributes + lifecycle position).

**ORD-B (Bundle A):** Create Order (ev02)  Add Item (ev05)  Pack Item (ev08). **Lifecycle is incomplete.** No Confirm Delivery, no direct Issue Invoice E2O, no Record Payment. This incompleteness is honest: ev11 may or may not cover ORD-B, and the InvoiceORD-B link exists only via O2O, not E2O. An aggressive repair would add ev11ORD-B and ev14INV-44 + PAY-2 settles INV-44, completing the lifecycle, but at significant false-positive risk.

**Orphan check:** No orphan Order events. Both Create Order events (ev01, ev02) relate to their respective orders.

**Cardinality:** Each `Create Order` relates to exactly one Order (S1). Each `Add Item` relates to exactly one Order (S1). `Confirm Delivery` (ev11) relates to one Order — consistent with domain rule 5's "customer/order" case.

**Circular reasoning warning:** If I added ev11ORD-B *because* ORD-B has items that were dispatched, and then used ev11ORD-B as evidence that ORD-B was delivered, that would be circular. Bundle A avoids this.

### Item

**IT-A1:** Add Item (ev03)  Pack Item (ev06, PK-7). Complete. Independently supported by E2O (ev03IT-A1, ev06IT-A1) and O2O (ORD-A contains IT-A1, PK-7 packs IT-A1).

**IT-A2:** Add Item (ev04)  Pack Item (ev07, PK-8). Complete. Same dual support.

**IT-B1:** Add Item (ev05)  Pack Item (ev08, PK-8). Complete after R-01/R-08. E2O from ev05IT-B1 (observed) and ev08IT-B1 (observed). O2O from ORD-B contains IT-B1 (observed) and PK-8 packs IT-B1 (added).

**Cardinality:** Each item is added to exactly one order and packed into exactly one package. No one-to-many violations.

### Package

**PK-7:** Pack Item (ev06)  Dispatch Package (ev09)  Delivery (DEL-X via O2O). Complete lifecycle. E2O: ev06PK-7, ev09PK-7. O2O: DEL-X carries PK-7. Dual support.

**PK-8:** Pack Item (ev08, added)  **no Dispatch E2O.** Lifecycle is incomplete after ev10 is left unresolved. The O2O chain PK-8 packs IT-B1 (added) is supported, but the PK-8  Delivery chain is missing.

**Suspicious cardinality:** In the raw data, PK-8 appeared to pack only IT-A2 (via ev07). After repair (R-08), PK-8 packs both IT-A2 and IT-B1. This is a one-to-many O2O relation (PK-8  IT-A2, PK-8  IT-B1). Is this suspicious? In a fulfillment process, a package containing multiple items is normal, so this is **not** suspicious — it is expected when items from different orders are consolidated.

### Delivery

**DEL-X:** Dispatch (ev09)  optionally Confirm Delivery (ev11, if R-04 accepted). In Bundle A, ev11 is not linked to DEL-X, so DEL-X's lifecycle is just Dispatch. Minimal but valid.

**DEL-Y:** **Orphan.** No events link to DEL-Y in Bundle A. This is the most honest representation of the data: DEL-Y exists in the objects table but has no event evidence. It may be an unused placeholder, a future delivery, or a data artifact.

**Cardinality concern:** DEL-X carries PK-7 (one delivery, one package). If Bundle B were selected, DEL-Y would carry PK-8, maintaining one-to-one. If the ev10 ambiguity were resolved as "ev10 dispatches both PK-7 and PK-8 into DEL-X," that would create a one-to-many (DEL-X carries PK-7 and PK-8), which is valid for consolidated shipping but contradicts DEL-Y's existence.

### Invoice

**INV-44:** Issue Invoice (ev12)  Record Payment (ev13, PAY-1). After R-10, INV-44 bills both ORD-A and ORD-B (O2O). This is a one-to-many O2O relation (INV-44  ORD-A, INV-44  ORD-B). **Dual support check:** The InvoiceORD-A relation is supported by both E2O (ev12ORD-A observed) and O2O (INV-44 bills ORD-A implied by arithmetic + single invoice event). The InvoiceORD-B relation is supported **only** by O2O (arithmetic) — no E2O link from ev12 to ORD-B exists. This asymmetry is noted and is a source of uncertainty.

### Payment

**PAY-1:** Record Payment (ev13)  settles INV-44 (O2O). Complete. E2O: ev13PAY-1, ev13INV-44. O2O: PAY-1 settles INV-44. Dual support.

**PAY-2:** Record Payment (ev14). **Incomplete in Bundle A.** No settlement target. The amount (130) matches ORD-A's value, suggesting settlement of INV-44, but this is left provisional to avoid lifecycle conflation. The ev14INV-44 E2O link is added at lower confidence (0.55) as a weaker acknowledgment that Record Payment normally links to an Invoice.

**Circular reasoning warning for PAY-2:** If I say "PAY-2 settles INV-44 because the amount matches" and then say "INV-44 is fully paid because PAY-1 + PAY-2 = 230," the second statement uses the first as a premise. The arithmetic consistency check is not independent evidence — it is a consequence of the assumed settlement. Bundle A avoids this by not fully committing to the settlement.

## 8. Over-repair warnings

Here are at least five specific ways an aggressive repair could create false process behavior in this dataset:

**Warning 1: False delivery confirmation for DEL-Y.** If we add `ev11  DEL-Y` as an E2O relation, the OC-DFG gains a `Dispatch Package  Confirm Delivery` edge attributed to DEL-Y. Downstream, the Delivery flattening will show DEL-Y with a lifecycle (Dispatch  Confirm Delivery), when in fact DEL-Y has no observed event evidence whatsoever. Process analysts may conclude that two deliveries were confirmed, inflating the delivery confirmation frequency from 1 to 2 per delivery object. This could mislead SLA calculations and carrier performance dashboards.

**Warning 2: Conflated order lifecycles via shared invoice payment.** If we add `PAY-2 settles INV-44`, then flattening on Order shows both ORD-A and ORD-B receiving a `Record Payment` event (ev14). The Order-level process model will show a branching path after `Issue Invoice` where two payment events occur, which in reality correspond to two different orders' payments being processed against a single shared invoice. Activity frequency for `Record Payment` at the Order level jumps from 1 (only PAY-1 for ORD-A) to 2, and the DFG edge `Issue Invoice  Record Payment` appears twice, which may trigger false conformance violations if the reference model expects one payment per order.

**Warning 3: Phantom dispatch event for PK-8.** If we add `ev10  DEL-Y` as E2O, the `Dispatch Package` activity now shows 2 packages dispatched into 2 deliveries. But the external reference on ev10 is ambiguous (`N-421?`). If the `?` indicates a data-entry error and the true reference is `N-420` (same as ev09), then ev10 is a duplicate record or correction for the same dispatch. Adding DEL-Y creates a phantom delivery with a complete lifecycle that never actually occurred. The Package flattening will show PK-8 as dispatched, which may be correct — but the Delivery flattening will show a delivery (DEL-Y) that exists only because of the repair.

**Warning 4: False invoice completeness for ORD-B.** If we add `INV-44 bills ORD-B`, then the Invoice flattening shows INV-44 covering two orders. If a domain expert later issues a separate invoice for ORD-B (e.g., because the items were shipped separately and require individual invoicing for tax reasons), the OCEL will contain two invoices for the same order, creating a many-to-many that inflates the invoice count and distorts revenue attribution per order. The arithmetic evidence (230 = 130 + 100) is strong but defeasible; a discount or fee adjustment could make the arithmetic coincidence.

**Warning 5: Circular evidence amplification.** If we first add `ev08  PK-8` (E2O), then infer `PK-8 packs IT-B1` (O2O), then use the O2O edge to argue that PK-8's lifecycle is "complete" and therefore `ev10  DEL-Y` is justified (because PK-8 needs a dispatch), we have constructed a chain of reasoning where each step depends on the previous one. The final edge (ev10  DEL-Y) appears to be supported by "lifecycle coherence" but is actually resting entirely on the initial scanner-ref inference. If the initial inference is wrong (e.g., the scanner ref `PK8-2` is a typo for `PK7-2`), the entire chain collapses, and DEL-Y's phantom lifecycle disappears. Process mining algorithms that use lifecycle completeness as a quality metric would have been misled.

**Warning 6 (bonus): False `Confirm Delivery` coverage.** If we add `ev11  ORD-B` as E2O, the Order flattening for ORD-B gains a `Confirm Delivery` event. Combined with the `INV-44 bills ORD-B` O2O edge, ORD-B's lifecycle appears complete (Create  Add Item  Pack  Confirm Delivery  Issue Invoice  Record Payment). This looks clean in the process model, but it may mask the fact that ORD-B's delivery was never independently confirmed. The portal event (ev11) explicitly shows `portal_customer=C17` but not which order was confirmed. If C17 had a third order that was confirmed instead of ORD-B, the repair would create false delivery trace data.

**Warning 7 (bonus): Equivalent-execution clustering masking uncertainty.** In Bundle B, ORD-A and ORD-B have nearly identical lifecycles (differing only in the number of items and payments). A clustering algorithm that groups orders by lifecycle pattern will place them in the same cluster. But ORD-A's lifecycle is directly observed while ORD-B's is largely inferred. The cluster's statistical properties (mean cycle time, activity frequency) will mix observed and inferred data without any indication of which is which. Analysts using these clusters for process improvement may optimize for behavior that exists only in the repair, not in reality.
