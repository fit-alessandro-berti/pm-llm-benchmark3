3. **Refine harmonised labels where justified:**  
   - e08  “Dispatch Package (Release)”, e09  “Dispatch Package (Carrier Acceptance)”.

4. **Store original identifiers, labels, timestamps, and sources:**  
   - Add columns: `original_activity`, `original_timestamp`, `source_event_key` (array for merged events), `merged_from` (list of original eids).  
   - The `timestamp` column keeps the original UTC secondprecision; no microsecond injection.

5. **Introduce deterministic ordering without deleting legitimate concurrency:**  
   - Create a sort column `order_index` following the rules in §3.  
   - Events that are truly concurrent retain the same `order_index` rank; ties are broken by stable fallback but the original timestamp proves concurrency.

**Expected retained event count:**  
Original 17 events  minus 2 merges (e03/e04, e11/e16)  **15 events**.

## 5. Aggressive alternatives

### A. Evidencebased semantic merging
- **Additional merges:** Merge e06+e07 into a single “Pack Package” event, because the reconciliation report strongly suggests they refer to the same business transition (WMS packing triggers ERP status). Union objects: O1,I1,I2,P1. Merge attributes: keep WMS detail and ERP status.
- **Keep e08/e09 separate** (distinct steps), e13/e14 separate (distinct payments), e15 separate (summary).
- **Expected retained event count:** 15 (conservative)  minus 1 (merge e06/e07)  **14 events**.
- **Most likely semantic damage:** The loss of the explicit “summary” abstraction may hide the fact that the ERP update arrived later, which could affect latency analysis. It also removes the ability to trace the ERP status separately.

### B. Mechanically aggressive PM4Py merging
- Apply `pm4py.ocel_merge_duplicates` with default parameters (identical activity + timestamp, ignoring objects or using a relaxed objectmatch criterion).
- **Potential destructive merges:**  
  - e03, e04, e05 all “Pick Item” at 10:00:00  merged into one event, losing the distinction between picking I1 and I2.  
  - e08, e09 both “Dispatch Package” at 10:15:00  merged into one, conflating warehouse release and carrier acceptance.  
  - e13, e14 both “Capture Payment” at 12:00:00  merged, collapsing M1 and M2 into a single payment.  
  - e11, e16 merged (acceptable), but may also merge with e12? No, different activity.
- **Expected retained event count:** Could drop to **11–12 events** (depending on objectmatch rules).  
- **Severe semantic damage:**  
  - Distinct item picks disappear  Itemflattened DFG becomes meaningless.  
  - Two payment captures become one  financial audit trail broken.  
  - Two logistics steps become one  delivery performance metrics distorted.

**Why `have_common_object=True` is not sufficient to protect e13 and e14**  
e13 and e14 share objects O1 and V1 (the order and invoice), but they represent different Payment objects (M1 vs M2). A commonobject check would see O1 and V1 and incorrectly conclude they are duplicates, merging the captures and obliterating the partial payment distinction. The Payment object itself must be considered, not only the shared order/invoice.

## 6. PM4Pyoriented Python implementation

```python
import pm4py
import pandas as pd
from copy import deepcopy

# Assume ocel_raw is a PM4Py OCEL object with events DataFrame containing:
# ocel:eid, ocel:timestamp, ocel:activity, source, source_event_key, source_seq,
# ingested_at, payload_hash, and related_objects (list of object IDs)

def verify_and_merge_pairs(ocel, verified_pairs):
    """
    Custom merge for verified duplicate pairs.
    verified_pairs: list of tuples (eid_keep, eid_merge)
    Merges attributes and relations, preserving provenance.
    """
    events = ocel.events.copy()
    relations = ocel.relations.copy()
    # Prepare columns to store provenance
    if 'merged_from' not in events.columns:
        events['merged_from'] = None
    if 'original_activity' not in events.columns:
        events['original_activity'] = events['ocel:activity']
    if 'original_timestamp' not in events.columns:
        events['original_timestamp'] = events['ocel:timestamp']
    for keep, merge in verified_pairs:
        keep_mask = events['ocel:eid'] == keep
        merge_mask = events['ocel:eid'] == merge
        # Merge attributes: keep original, append merge's source_event_key
        keep_row = events[keep_mask].iloc[0]
        merge_row = events[merge_mask].iloc[0]
        # Combine source_event_key
        new_src_keys = [keep_row['source_event_key'], merge_row['source_event_key']]
        events.loc[keep_mask, 'source_event_key'] = str(new_src_keys)
        # Merge provenance record
        if keep_row['merged_from'] is None:
            events.loc[keep_mask, 'merged_from'] = [merge]
        else:
            events.loc[keep_mask, 'merged_from'] = keep_row['merged_from'] + [merge]
        # Update relations: add all object relations from merge row to keep eid
        merge_rels = relations[relations['ocel:eid'] == merge]
        for _, rel in merge_rels.iterrows():
            # Avoid duplicates
            if not ((relations['ocel:eid'] == keep) & (relations['ocel:oid'] == rel['ocel:oid'])).any():
                new_rel = rel.copy()
                new_rel['ocel:eid'] = keep
                relations = pd.concat([relations, pd.DataFrame([new_rel])], ignore_index=True)
        # Drop merge event and its relations
        events = events[~merge_mask]
        relations = relations[relations['ocel:eid'] != merge]
    # Rebuild OCEL
    ocel.events = events
    ocel.relations = relations
    return ocel

# Independent deep copies

print("Conservative candidate groups:", candidates_cons['ocel:eid'].unique())

# Verified pairs: e03/e04, e11/e16
verified_cons = [('e03', 'e04'), ('e11', 'e16')]
ocel_cons = verify_and_merge_pairs(ocel_cons, verified_cons)

# Refine labels (manual or rule-based)
refine_map = {

    'e07': 'Pack Package (Summary)',
    'e08': 'Dispatch Package (Release)',

}
for eid, new_act in refine_map.items():
    mask = ocel_cons.events['ocel:eid'] == eid
    ocel_cons.events.loc[mask, 'original_activity'] = ocel_cons.events.loc[mask, 'ocel:activity']
    ocel_cons.events.loc[mask, 'ocel:activity'] = new_act

# Deterministic ordering: create order_index based on §3 rules
# For brevity, we assign a manual order_index; in practice, implement a sorting function.
order_cons = pd.DataFrame({

    ocel_evid.events.loc[mask, 'original_activity'] = ocel_evid.events.loc[mask, 'ocel:activity']
    ocel_evid.events.loc[mask, 'ocel:activity'] = new_act
# (ordering omitted for brevity, similar to conservative)
```

## 8. Audit trail and reversibility

**Provenance schema** (stored alongside the cleaned OCEL, e.g., in a `provenance` table)

| Column | Description |
|--------|-------------|
| `canonical_event_id` | The surviving event ID after cleaning. |
| `source_event_ids` | List of original event IDs that were merged (empty if no merge). |
| `merge_rule` | Identifier of the rule applied (e.g., “same_physical_scan”, “same_invoice”, “abstraction_qualifier”). |
| `reviewer_or_rule_version` | Analyst name or rule version (e.g., “v1.0”, “manual_review”). |
| `original_activity` | Activity label before any refinement. |
| `refined_activity` | Activity label after pipeline (if changed). |
| `original_timestamp` | The exact UTC timestamp as ingested. |
| `adjusted_timestamp` | Always NULL – we never alter the timestamp. |
| `attributes_retained` | JSON object of attributes kept from each source (e.g., `{"ERP": {"invoice_total": 100}, "BILLING": {"tax_id": "..."}}`). |
| `discarded_conflicts` | Any attributes that were in conflict and dropped, with reason. |
| `confidence` | High / Medium / Low. |
| `reason` | Freetext justification. |

**Reconstructing the raw view:**
An analyst can join the canonical events with the provenance table on `canonical_event_id`, expand `source_event_ids`, and retrieve the original events from the raw ingestion log (or from a preserved `ocel_raw` copy). The `original_activity` and `original_timestamp` columns allow exact restoration of the precleaning state. Merged events can be exploded back into their constituent rows.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments**  
   *Failure:* Merging e13 (M1) and e14 (M2) because they share O1, V1, and activity.  
   *Safeguard:* Require Payment object in duplicate key; flag any merge where Payment objects differ.

2. **Converting abstractionlevel updates into false rework**  
   *Failure:* Keeping e06 and e07 with the same label “Pack Package” creates a selfloop, interpreted as rework.  
   *Safeguard:* Always refine labels when events are at different abstraction levels; use qualifiers.

3. **Ordering by ingestion time**  
   *Failure:* Using `ingested_at` as the primary business order would place e09 (carrier) before e08 (WMS) because ingestion times differ, violating the physical releasebeforeacceptance order.  
   *Safeguard:* Ingestion time is only a fallback after all semantic and domain constraints are exhausted.

4. **Treating shared objects as proof of duplication**  
   *Failure:* e08/e09 both have O1,P1,D1, so a naïve objectbased duplicate detector would merge them.  
   *Safeguard:* Include source system and original activity (before harmonisation) in the duplicate key; never merge across different source activities that were harmonised.

5. **Unioning incompatible E2O relations**  
   *Failure:* If e06 (with I1,I2) and e07 (only P1) are merged, their objects must be unioned; but if the merge is done carelessly, the relations may be lost or duplicated.  
   *Safeguard:* Use a merge function that deduplicates relations and validates referential integrity; verify that the union is semantically correct.

6. **Changing durations through synthetic microseconds**  
   *Failure:* Adding microseconds to the timestamp to break ties changes the actual duration between events, e.g., a 0second wait becomes a 1 ms delay, affecting performance calculations.  
   *Safeguard:* Never alter the original timestamp; use a separate sort column. If a timedelta is needed for a specific algorithm, it must be stored in a temporary column and never written back to the original timestamp.

7. **Losing sourceauthoritative attributes**  
   *Failure:* When merging e11 (ERP) and e16 (Billing), if only ERP attributes are kept, the billingspecific tax information is lost.  
   *Safeguard:* Merge attributes by keeping all nonconflicting fields; for conflicts, store both in a provenance record and let the analyst decide.

8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups**  
   *Failure:* Calling `pm4py.ocel_merge_duplicates` on the entire log without prior grouping or domain validation will blindly merge e03/e04/e05, e08/e09, e13/e14, etc.  
   *Safeguard:* Always prefilter candidate groups and apply merge rules only to verified pairs; use a custom merge wrapper that logs every decision.
