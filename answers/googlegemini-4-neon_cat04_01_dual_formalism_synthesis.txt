# 1. Assumptions and Interpretation

1. **Representation of the low-risk / high-risk choice:** Because risk level is an unmodeled case attribute, the choice after `Analyze Root Cause` is modeled as a nondeterministic exclusive choice (`XOR`) between two submodels: the low-risk branch (`Supervisor Review`) and the high-risk branch (a concurrent block containing `Quality Review` and `Regulatory Review` with no ordering constraint between them). A valid case executes either `Supervisor Review` alone, or both `Quality Review` and `Regulatory Review` in either completion order, never mixing the two routes.
2. **Representation of optional supplier consultation:** Because supplier involvement depends on unmodeled case data, `Consult Supplier` is represented as an exclusive choice (`XOR`) between `Consult Supplier` and a silent skip (`tau` / `SilentTransition`). Placing this choice in the model after `Analyze Root Cause` and before `Release Material` guarantees that `Consult Supplier` occurs at most once per case, never precedes `Analyze Root Cause`, and completes before `Release Material` whenever selected.
3. **Abstraction of passing vs. failing inspection:** Because inspection outcomes are not recorded as distinct event labels, the repeat-until semantics are captured using a structured `LOOP(do, redo)` construct with `do = SEQUENCE(Execute Trial, Inspect Trial)` and `redo = Adjust Parameters`. Taking the redo branch (`Adjust Parameters`) implicitly represents a failed inspection and forces a subsequent `Execute Trial`–`Inspect Trial` cycle; exiting the loop immediately after `Inspect Trial` implicitly represents a passing inspection. Thus, `Adjust Parameters` can occur only between two trial cycles and never after the final (passing) `Inspect Trial`.
4. **Duplicate visible labels:** Duplicate visible activity labels are **not permitted** in either model. Every one of the 14 visible activity labels appears exactly once. Keeping labels unique preserves unambiguous event-to-transition mapping for conformance checking, alignment diagnostics, and performance analysis, and avoids inflating model size with artificial duplicate copies (which still could not faithfully express an unbounded concurrent loop overlapping independent partial-order branches without severe structural distortion).
5. **Process-tree approximation policy:** A duplicate-free `ProcessTree` cannot represent the narrative's exact partial order because the intended dependencies form non-series-parallel (N-shaped) cross-branch synchronizations. We adopt a **conservative under-approximation** policy: the process tree never admits any unsafe or forbidden ordering (zero false positives / 100% precision with respect to intended behavior), at the cost of excluding a well-defined subset of intended concurrent interleavings. Specifically, we place a synchronization barrier after `PARALLEL(SEQUENCE(Contain Material, Plan Verification), SEQUENCE(Analyze Root Cause, Design Corrective Action))` and run `TrialLoop`, `RiskApproval`, and `OptSupplier` concurrently after that barrier. We prefer this barrier over the alternative conservative barrier (placing approvals and supplier consultation before the trial) because it preserves the explicitly required overlap between the trial cycle and the approval/supplier routes and avoids artificially delaying `Execute Trial`.
6. **Interpretation of "may overlap":** Structurally, our POWL model and its Petri-net translation model "may overlap" as **true concurrency** (independent concurrent enablement of transitions/submodels with no causal path between them). However, because activities are recorded only at completion time as atomic events without start timestamps, the observable trace semantics reduce concurrency to **interleaving semantics** (absence of an ordering constraint between completion events). In trace space, "may overlap" therefore manifests as arbitrary interleaving of completion events across concurrent branches.
7. **Execution multiplicity and case boundaries:** Every case begins with a single `Register Deviation` and ends with a single `Archive Case`. Except for the repeat-until trial activities (`Execute Trial`, `Inspect Trial`, `Adjust Parameters`), the optional `Consult Supplier`, and the unselected risk-approval branch, every activity executes exactly once per case.

```python
def make_operator(operator: Operator, children: list[ProcessTree]) -> ProcessTree:
    """Create a ProcessTree operator node with explicit parent/child wiring."""
    node = ProcessTree(operator=operator)
    for child in children:
        child.parent = node
        node.children.append(child)
    return node
```

## Representational Loss and Approximation Analysis

A duplicate-free process tree can only represent series-parallel (N-free) partial orders, whereas the intended dependencies contain two induced N-shaped subgraphs: `Plan Verification -> TrialLoop <- Analyze Root Cause -> RiskApproval` and `Plan Verification -> TrialLoop <- Analyze Root Cause -> OptSupplier` (as well as the analogous structures rooted at `Contain Material`). Because a `ProcessTree` must synchronize subtrees strictly at block boundaries, `tree` cannot let `RiskApproval` and `OptSupplier` start immediately after `Analyze Root Cause` while simultaneously letting `TrialLoop` wait for both `Plan Verification` and `Design Corrective Action` and still overlap `RiskApproval` and `OptSupplier`. Under our conservative under-approximation, `tree` enforces a synchronization barrier at the end of `preparation_phase`, which preserves all safety rules, initial concurrency (`Contain Material` || `Analyze Root Cause`), immediate trial start once `Plan Verification` and `Design Corrective Action` finish, and full overlap among trials, approvals, and supplier consultation. However, it cannot represent two intended flexibilities: (1) `RiskApproval` (`Supervisor Review`, `Quality Review`, `Regulatory Review`) is artificially blocked from starting until `Contain Material`, `Plan Verification`, and `Design Corrective Action` have all completed, preventing approvals from overlapping containment, verification planning, or corrective-action design; and (2) `Consult Supplier` is likewise artificially blocked until `Contain Material`, `Plan Verification`, and `Design Corrective Action` complete, violating the part of Requirement 6 that permits `Consult Supplier` to overlap corrective-action design and verification planning.

```text
      PO(nodes={'Execute Trial', 'Inspect Trial'}, order={'Execute Trial' --> 'Inspect Trial'}),
      'Adjust Parameters'
    ),
    rm  : 'Release Material',
    ac  : 'Archive Case'
  },
  order = {
    rd  --> cm,
    rd  --> arc,
```

```python
    OperatorPOWL,
    SilentTransition,
    StrictPartialOrder,
    Transition,
)
from pm4py.objects.process_tree.obj import Operator

# Visible transitions (each label appears exactly once)
rd = Transition(label="Register Deviation")
cm = Transition(label="Contain Material")
arc = Transition(label="Analyze Root Cause")

dca = Transition(label="Design Corrective Action")

ac = Transition(label="Archive Case")

# Silent transition for skipping optional supplier consultation

# Nested submodel 1: Risk-based approval route
# High-risk branch is a StrictPartialOrder with no edges (true concurrency)
high_risk_approval = StrictPartialOrder(nodes=[qr, rr])

trial_body = StrictPartialOrder(nodes=[et, it])
trial_body.order.add_edge(et, it)
trial_loop = OperatorPOWL(operator=Operator.LOOP, children=[trial_body, ap])

# Top-level strict partial order capturing all cross-branch dependencies directly
powl = StrictPartialOrder(
    nodes=[rd, cm, arc, pv, dca, risk_approval, opt_supplier, trial_loop, rm, ac]
)

# Direct partial-order dependencies (Hasse diagram of the intended order)
powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)
powl.order.add_edge(cm, pv)
powl.order.add_edge(arc, dca)
powl.order.add_edge(arc, risk_approval)
powl.order.add_edge(arc, opt_supplier)
powl.order.add_edge(pv, trial_loop)
powl.order.add_edge(dca, trial_loop)
powl.order.add_edge(trial_loop, rm)
powl.order.add_edge(risk_approval, rm)
powl.order.add_edge(opt_supplier, rm)
powl.order.add_edge(rm, ac)
```

## Justification for Intentionally Unconnected (Concurrent) Node Pairs

In `powl`, `rd` precedes all other nodes and `rm -> ac` follows all other nodes. Among the seven intermediate nodes (`cm`, `pv`, `arc`, `dca`, `risk_approval`, `opt_supplier`, `trial_loop`), 8 pairs are ordered directly or transitively, leaving 13 intentionally unconnected (incomparable) top-level pairs plus 1 nested pair:

- **`{cm, arc}`:** Requirement 2 explicitly allows `Contain Material` and `Analyze Root Cause` to proceed independently and overlap after `Register Deviation`.
- **`{cm, dca}`, `{cm, risk_approval}`, `{cm, opt_supplier}`:** `Design Corrective Action`, `RiskApproval`, and `OptSupplier` depend only on `Analyze Root Cause` (Reqs. 4–6), never on `Contain Material`.
- **`{pv, arc}`, `{pv, dca}`, `{pv, risk_approval}`, `{pv, opt_supplier}`:** `Plan Verification` depends only on `Contain Material` (Req. 3), not on root-cause analysis or its downstream obligations; Requirement 6 also explicitly permits `Consult Supplier` to overlap verification planning.
- **`{dca, risk_approval}`, `{dca, opt_supplier}`:** Both `RiskApproval` and `OptSupplier` branch independently from `Analyze Root Cause` alongside `Design Corrective Action`; Requirement 6 explicitly allows `Consult Supplier` to overlap corrective-action design, and approvals neither block nor wait on design.
- **`{risk_approval, opt_supplier}`:** Requirement 6 explicitly allows `Consult Supplier` to overlap approvals.
- **`{risk_approval, trial_loop}`:** Requirement 7 explicitly states that the selected approval route need not complete before the trial starts and may overlap the trial cycle.
- **`{opt_supplier, trial_loop}`:** Requirement 6 explicitly allows `Consult Supplier` to overlap trial work while still synchronizing before `Release Material`.
- **`{Quality Review, Regulatory Review}` (inside `high_risk_approval`):** Requirement 5 explicitly specifies that both high-risk reviews may occur concurrently and complete in either order.

# 7. Preferred Representation and Validation Plan

## Canonical Representation Choice

The **POWL model (`powl`)** is the preferred canonical representation. Unlike a duplicate-free `ProcessTree`, POWL natively combines partial-order concurrency (`StrictPartialOrder`) with structured choice and iteration (`OperatorPOWL` for `XOR` and `LOOP`). As demonstrated in Sections 4–6, `powl` expresses every control-flow dependency in the narrative—including both induced N-graphs (`Plan Verification -> TrialLoop <- Analyze Root Cause -> RiskApproval` and `Plan Verification -> TrialLoop <- Analyze Root Cause -> OptSupplier`)—**exactly**, with zero duplicate visible labels and zero artificial synchronization barriers. By contrast, `tree` is best retained only as a secondary conservative view for legacy process-mining tools that strictly require block-structured trees.

## Concrete Validation Plan

1. **Conversion to accepting Petri nets:** Convert both `powl` and `tree` using `net_p, im_p, fm_p = pm4py.convert_to_petri_net(powl)` and `net_t, im_t, fm_t = pm4py.convert_to_petri_net(tree)`. Inspect the resulting net topologies (initial marking `im`, final marking `fm`, place/transition counts) to confirm that conversion succeeds cleanly without dropping edges or merging unrelated places.
2. **Soundness verification:** Run `pm4py.check_soundness(net_p, im_p, fm_p, print_diagnostics=True)` and `pm4py.check_soundness(net_t, im_t, fm_t, print_diagnostics=True)`. Verify all three classical workflow-net soundness properties on both nets: option to complete from every reachable marking, proper completion (no residual tokens when `fm` is reached), and absence of dead transitions (every visible activity is reachable in at least one valid firing sequence).
3. **Bounded / sampled playout with behavioral assertions:** Generate bounded event logs from both models via `pm4py.play_out(net_p, im_p, fm_p, ...)` and `pm4py.play_out(net_t, im_t, fm_t, ...)` (setting explicit caps on trace count and maximum trace length to bound the `LOOP` operator). Run programmatic property assertions across all sampled traces to verify:
   - every trace starts with `Register Deviation` and ends with `Archive Case`;
   - all mandatory precedence constraints (`CM < PV`, `ARC < DCA`, `ARC < {SR, QR, RR, CS}`, `{PV, DCA} < first(ET)`, `last(IT) < RM`, `RM < AC`) hold in 100% of sampled traces;
   - `Consult Supplier` occurs 0 or 1 times, never > 1;
   - `SR` and `{QR, RR}` are strictly mutually exclusive, and whenever `QR` appears, `RR` also appears;
   - `ET` and `IT` alternate cleanly, `AP` appears only between an `IT` and a subsequent `ET`, and `AP` never follows the final `IT`;
   - differential coverage check: confirm that POWL playout produces valid traces where `CS`, `SR`, `QR`, or `RR` precede `PV` or `DCA` (matching T3/T4), whereas Process-Tree playout produces zero such traces.
4. **Explicit positive and negative trace tests (conformance alignments):** Encode witnesses T1–T8 as an event log and compute optimal alignments (e.g., `pm4py.conformance_diagnostics_alignments(log, net, im, fm)`) against both converted nets:
   - against `powl`: assert `fitness == 1.0` (zero log/model deviations) for T1–T5, and `fitness < 1.0` for T6–T8;
   - against `tree`: assert `fitness == 1.0` for T1, T2, T5, and `fitness < 1.0` for T3, T4 (explicitly confirming the conservative under-approximation) as well as T6–T8.
   - Add targeted edge-case negative traces beyond T6–T8 (e.g., `Consult Supplier` occurring twice; mixing `Supervisor Review` with `Quality Review`; `Consult Supplier` before `Analyze Root Cause`).
5. **Dedicated checks for silent transitions and duplicate labels:**
   - **Duplicate-label check:** Assert `labels = [t.label for t in net.transitions if t.label is not None]` has `len(labels) == len(set(labels)) == 14` and equals the exact expected label set for both models.
   - **Silent-behavior check:** Inspect all `t.label is None` transitions in `net_p` and `net_t` to verify that (a) no purely silent cycle (tau-livelock) exists in the reachability graph, and (b) aligning a trace without `Consult Supplier` (such as T1 or T4) consumes only silent skip moves (`(None, None)`) with zero visible model moves (`(None, 'Consult Supplier')`), confirming that `SilentTransition` cleanly models optionality without distorting fitness.
6. **Limitations of the validation plan:**
   - *Incomplete loop coverage:* Because `TrialLoop` generates an infinite regular language, bounded playout can only sample finite loop depths and cannot mathematically exhaust all interleavings of arbitrary-length trial sequences.
   - *Interleaving vs. true-concurrency observability:* Alignment and trace-based playout validate sequential interleaving languages rather than true-concurrency partial orders or wall-clock durational overlaps.
   - *Unmodeled data semantics:* Control-flow soundness and conformance cannot verify whether low-risk/high-risk routing matched actual defect severity, whether `Consult Supplier` was genuinely required, or whether the final `Inspect Trial` actually recorded a "pass" outcome in the quality-management system.
   - *Structural vs. semantic fidelity:* Passing `pm4py.check_soundness` proves only that the converted Petri net is behaviorally well-formed (sound), not that its edges faithfully capture the domain narrative—semantic fidelity still relies on human review of the dependency matrix and counterexample witnesses.

# 8. Final Self-Critique

1. **Unmodeled data guards allow semantically inconsistent cases (semantic weakness):** By encoding risk level, supplier necessity, and trial pass/fail decisions as nondeterministic control-flow choices (`XOR` and `LOOP`), both models accept traces that could violate underlying business data rules—for example, a genuinely high-risk deviation executing `Supervisor Review`, an arbitrary skip of `Consult Supplier` when a supplier-caused defect exists, or exiting the trial loop after an inspection that failed in the source system. Enforcing those rules would require extending the canonical POWL/Petri-net model into a Data Petri Net (DPN) with explicit guard expressions.
2. **Completion-time abstraction obscures true start-before-complete constraints (semantic weakness):** Because every activity is represented as a single atomic completion event, constraints phrased in the narrative as *"may start only after X is complete"* (e.g., `Plan Verification` starting only after `Contain Material` completes) are approximated as *"completes after X completes."* In an actual event log containing only completion timestamps, `Plan Verification` could improperly start *before* `Contain Material` finished yet still complete afterward, and both models would wrongly judge the trace conformant unless explicit `start` and `complete` lifecycle transitions are modeled.
3. **Unmodeled exception paths and unexecuted runtime verification (modeling and engineering weakness):** First, the models strictly follow the happy-path release narrative and omit realistic manufacturing exception outcomes (such as scrapping or rejecting non-conforming material instead of reaching `Release Material` after repeated failed trials). Second, while the Python code adheres directly to PM4Py's `ProcessTree` and `POWL` object interfaces, the snippets were derived deductively without live execution against a specific pinned PM4Py release; in practice, one should verify library-specific behaviors such as whether `StrictPartialOrder` conversion requires explicit transitive reduction/closure calls or specific alignment solver parameters in the target PM4Py version.
