6. **Normalization of Auto-Approval**

7. **M0’s Control-Flow Gaps**
   - **Concurrency**: M0 correctly models `Sanctions_Check` and `Quality_Review` as concurrent, but **real-world execution** may not always reflect this (e.g., SUP-708’s out-of-order checks).
   - **Rejection Path**: M0’s rejection path is **incomplete**—it does not account for **abbreviated pre-screen processes** (SUP-709).

**Conclusion**: M0 is **obsolete** (lacks auto-approval, loops), **incomplete** (missing resource rules, reactivation scope), and **incorrectly scoped** (rejected leads, notifications). Many deviations are **justified by overlays or data issues**, not process failures.

## 6. Revised Normative Architecture

### **Layered Architecture**
1. **Control-Flow Model (POWL)**
   - Standard path: `Register_Supplier`  (`Sanctions_Check`  `Quality_Review`)  `Manual_Procurement_Approval`  `Activate_Supplier`  `Notify_Requester`  `Close_Case`.
   - Auto-approval path (LOW-risk): `Register_Supplier`  `Sanctions_Check`  `Auto_Approve`  `Activate_Supplier`  (`Quality_Review` within 2 days)  `Notify_Requester`  `Close_Case`.
   - Emergency path: `Register_Supplier`  `Sanctions_Check`  `Provisional_Activate`  (`Quality_Review` + `Manual_Procurement_Approval` within 2 days)  `Notify_Requester`  `Close_Case`.
   - Rejection path: `Register_Supplier`  (`Sanctions_Check`  `Quality_Review`)  `Reject_Supplier`  `Notify_Requester`  `Close_Case`.
   - Loop: `Request_More_Info`  (return to `Sanctions_Check` or `Quality_Review`).
   - Reactivation: `Register_Supplier` (reactivation)  `Sanctions_Check`  (`Quality_Review` if expired)  `Manual_Procurement_Approval`  `Activate_Supplier`  `Notify_Requester`  `Close_Case`.

2. **Data-Aware Rules (DECLARE/Log-Skeleton Constraints)**
   - **Precedence**:
     - `Sanctions_Check` **before** `Activate_Supplier` (always).
     - `Quality_Review` **before** `Activate_Supplier` (except emergency path, where it must occur within 2 days).
   - **Exclusivity**:
     - `Manual_Procurement_Approval` **XOR** `Auto_Approve` **XOR** `Provisional_Activate`.
   - **Temporal**:
     - `Quality_Review` **within 2 business days** of `Provisional_Activate` or `Auto_Approve`.
     - `Manual_Procurement_Approval` **within 2 business days** of `Provisional_Activate`.

3. **Resource and Conflict-of-Interest Rules (Organizational Controls)**
   - **Separation of Duties**:
     - `Requester`  `Manual_Procurement_Approval` (enforced via role checks).
   - **Conflict of Interest**:
     - `Quality_Review` and `Manual_Procurement_Approval` cannot be performed by **related parties** (e.g., spouses, same reporting line) without disclosure.

4. **Policy-Overlay Governance**
   - **Pilots**: Temporary amendments (e.g., PD-3) must be:
     - **Time-bound**.
     - **Explicitly scoped** (e.g., LOW-risk DE suppliers).
     - **Approved by Compliance** (not just "monitored exceptions").
   - **Emergencies**: Directives (e.g., FD-7) must:
     - **Explicitly override** specific controls (e.g., `Quality_Review` timing).
     - **Include spend caps** and **retrospective approval requirements**.
     - **Auto-expire** unless extended in writing.

5. **Scope Rules**
   - **Rejected Leads**: Out of scope for M0; governed by **pre-screen process**.
   - **Reactivation**: Separate process with **explicit steps** (e.g., `Sanctions_Check` always, `Quality_Review` if certification expired).
   - **Withdrawals**: Cases withdrawn before `Sanctions_Check` are **out of scope**.

6. **Data Collection Proposal**
   - **Immutable Fields**:
     - `notification_id` (stable, linked to CRM).
     - `rule_version_id` (e.g., "CS-9-v2", "PD-3", "FD-7").
     - `eligibility_snapshot` (risk level, corporate group status at time of case).
     - `actor_aliases` (resolved to canonical IDs).
     - `delegation_evidence` (if approval was delegated).
   - **Timestamps**:
     - `effective_time` (when the activity occurred).
     - `record_time` (when logged, immutable).
   - **Audit Trail**:
     - All changes to mutable fields (e.g., CRM links) must be **versioned**.

## 7. PM4Py Model and Data Proposal

### **Revised POWL Model (Python Code)**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# Standard transitions
register = Transition(label="Register_Supplier")
sanctions = Transition(label="Sanctions_Check")
quality = Transition(label="Quality_Review")
manual_approval = Transition(label="Manual_Procurement_Approval")
activate = Transition(label="Activate_Supplier")
auto_approve = Transition(label="Auto_Approve")
provisional_activate = Transition(label="Provisional_Activate")
reject = Transition(label="Reject_Supplier")
notify = Transition(label="Notify_Requester")
close = Transition(label="Close_Case")
request_info = Transition(label="Request_More_Info")

# Concurrent checks (standard and auto-approval paths)
checks = StrictPartialOrder(nodes=[sanctions, quality])

# Standard approval branch
standard_approval = StrictPartialOrder(nodes=[manual_approval, activate])
standard_approval.order.add_edge(manual_approval, activate)

# Auto-approval branch (LOW-risk)
auto_branch = StrictPartialOrder(nodes=[auto_approve, activate, quality])
auto_branch.order.add_edge(auto_approve, activate)
auto_branch.order.add_edge(activate, quality)  # Quality_Review within 2 days

# Emergency branch
emergency_branch = StrictPartialOrder(nodes=[provisional_activate, quality, manual_approval])
emergency_branch.order.add_edge(provisional_activate, quality)
emergency_branch.order.add_edge(provisional_activate, manual_approval)

# Decision: XOR between standard, auto, emergency, or reject
decision = OperatorPOWL(
    operator=Operator.XOR,
    children=[
        standard_approval,
        auto_branch,
        emergency_branch,
        reject
    ]
)

# Request_More_Info loop (approximated as a silent transition back to checks)
silent_loop = SilentTransition(label="tau_loop")
loop = StrictPartialOrder(nodes=[request_info, silent_loop, sanctions, quality])
loop.order.add_edge(request_info, silent_loop)
loop.order.add_edge(silent_loop, sanctions)
loop.order.add_edge(silent_loop, quality)

# Full model
M1 = StrictPartialOrder(nodes=[register, loop, checks, decision, notify, close])
M1.order.add_edge(register, loop)
M1.order.add_edge(loop, checks)
M1.order.add_edge(checks, decision)
M1.order.add_edge(decision, notify)
M1.order.add_edge(notify, close)

# Note: POWL cannot enforce:
# - Time constraints (e.g., Quality_Review within 2 days)
# - Resource rules (e.g., separation of duties)
# - Spend caps (e.g., EUR 20,000 in emergency)
# These must be enforced via DECLARE constraints or organizational controls.
```

### **Limitations**
- **POWL cannot enforce**:
  - Time constraints (use DECLARE or pandas checks).
  - Resource rules (use organizational controls).
  - Spend caps (use data validation).
- **Loops**: Approximated with a silent transition, but **true loops** require a more expressive language (e.g., Petri nets with reset arcs).
- **Reactivation**: Modeled as a separate `Register_Supplier` (reactivation), but **scope must be clarified** in documentation.
