## 1. Analytical assumptions  
• Case notion= the set of events returned by `pm4py.ocel_flattening(ocel, object_type=…)`, i.e. every event that is directly related to the selected object instance, with the shared-event copy rule in force.  
• Convergence= a situation in which one flattened trace unintentionally combines the histories of several business entities (e.g., two orders) because they happen to share the chosen object (e.g., a package).  
• Divergence= a situation in which the lifecycle of a single business entity is split over several traces (e.g., one order that is packed in two packages).  
• Copied shared events are treated as (1) genuine evidence that something happened that is relevant to every referenced object, and simultaneously (2) a source of event-count duplication when statistics are computed per trace.  
• Permitted analytical transformations  
  – For sensitivity only we will create a “propagated” variant in which O2O links are recursively followed (Order  Item  Package  Delivery, etc.).  
  – No other structure is invented; all statements will distinguish clearly between the as-is E2O set and the propagated variant.

## 2. Object-type comparison matrix

|-------------|---------------------------|-------------------|--------------|------------------|-----------------|----------------------------|---------------------------------------|--------------------|
| Order | “How does a customer order evolve from creation to closure?” | All order-specific events (e01, … e31) and every shared event that names that order | Cross-order operational couplings (P3, P4; D2; V2) appear only as duplicated copies, not as explicit links | Low – each trace contains a single order | Medium – O1 spans two packages (P1/P2) and two deliveries (D1/D2), so time between ‘Pack’ events may look parallel not split | High: e13, e14, e16, e17, e19, e24 duplicate over 2–3 traces | Moderate: duplicated events shorten paths (“PackDispatch” seems more frequent) and parallelism hides consolidation delays | Good for customer-facing KPIs; poor for warehouse & finance |

## 3. Concrete distortion analysis  

1. Flattening: Package  
   Objects: P3 (packs I21, I31) in e13, e16, e24  
   Distortion: Convergence merges O2 and O3 into one trace. The DFG shows ‘Pack Package  Dispatch  Confirm Delivery’ once, hiding that items belonged to two separate orders. Frequency counts for ‘Dispatch’ are understated by 1 because one consolidated event is not copied across two package traces (only one trace exists).  
   Effect: Harmful when assessing order-level SLA; informative for load pooling.

2. Flattening: Package  
   Objects: P4 (O3 & O4) in e14, e17, e27  
   Distortion: Same as above but additionally creates the variant “Pack Package (for O3)  Close Order (O4)” never observed in reality. Harmful.

3. Flattening: Order  
   Objects: O2 and O3 share invoice V2 (e19), payments M2 (e22) and M3 (e25)  
   Events e19, e22, e25 are copied into both order traces.  
   DFG edge ‘Issue Invoice  Record Payment’ appears twice although only one invoice exists. Monetary amount statistics double-count. Frequency inflation—harmful.

4. Flattening: Order  
   Objects: O1 spans P1 & P2. Pack event e11 (P1) and e12 (P2) happen 10 min apart, but the Dispatch e15 and e16 are 5 min apart and belong to different deliveries. Flattened trace suggests two parallel “Pack  Dispatch” branches, exaggerating warehouse throughput. Divergence side-effect—context-dependent.

5. Flattening: Delivery  
   Object: D2 consolidates P2 (O1) and P3 (O2,O3). The trace contains events from three orders but no indication of separate invoice/payment status. Average delivery lead time appears longer because earlier creation times differ; harmful for transport KPI but may be acceptable for route-planning.

6. Flattening: Invoice  
   Object: V2 (O2 & O3) paid partially. The trace shows ‘Issue Invoice  Record Payment  Record Payment’ (e19  e22  e25). Variant mining will flag “multiple payments” as frequent (50 %), although only one of three invoices is split. Frequency inflation but informative about instalment practice—context-dependent.

7. Flattening: Payment  
   Object: M1 (e21) results in a singleton lifecycle of length 1. Any throughput or conformance metric becomes undefined (division by zero duration). Near-singleton lifecycle distortion—harmful.

8. Flattening: Item  
   Objects: I12 (O1) and I11 (O1) are shipped via different deliveries (D2 vs D1). In the item-level DFG the edge ‘Dispatch  Confirm Delivery’ appears once at 5 h (I12) and once at 3 h (I11). Order-level average becomes meaningless if one tries to aggregate item traces. Divergence—harmful.

## 4. Traditional versus object-centric analysis portfolio  

Recommended flattened logs  
• Order-based log: customer communication, overall SLA, backlog size.  
• Invoice-based log: finance ageing, payment compliance.  
• Delivery-based log: route optimisation.

Questions safe for flattened logs  
• “Time from Create Order (e01–e04) to Close Order (e28–e31)”  order log.  
• “Number of partial invoices”  invoice log.  
• “Trips per day”  delivery log.

Questions requiring OC techniques  
• “Which orders share packages?”  OTG & ET–OT.  
• “Impact of partial payments on delivery punctuality”  OC-DFG joining finance and logistics.  
• “Bottlenecks between packing and dispatch per physical package regardless of order”  OC-DFG or OTG centred on Package.  
• “Are cross-order consolidations (P3, P4) increasing lead time?”  Object interaction summary.

Reconciling contradictory findings  
1. Compute the metric on each relevant flattening.  
2. Re-express the metric on the OCEL using object-centric measures (events, unique objects, total objects).  
3. Highlight gaps; drill through the ET–OT graph to show which shared events cause the discrepancy.  
4. Decide whether duplication or genuine pooling explains the gap.

## 5. Lead-object decision  

Position B — Primary lead object ‘Order’ plus explicit secondary lifecycles  

Decision criteria  
• Stakeholder priority: customers and management think in orders.  
• Coverage of activities: Order appears in 25/31 events.  
• Acceptable distortion level: duplications are countable and can be corrected.  
• Cross-functional visibility: secondary Package, Delivery, Invoice perspectives are still required.

Supporting evidence  
• Every high-level milestone (‘Create’, ‘Pack’, ‘Dispatch’, ‘Issue Invoice’, ‘Record Payment’, ‘Close’) references the Order objects directly (events e01–e31).  
• Only 4 events (e11–e14) omit some orders when packages are split, a gap small enough to annotate.

Strongest counter-argument  
• Cross-order packages P3 & P4 and consolidated invoice V2 create duplication across order traces, inflating event counts by up to 50 % for those orders.

Residual risk  
• Analysts might ignore the duplication correction and double-count financial events.  
• SLA from creation to delivery will be slightly biased for O1, O2, O3 because of multi-delivery paths.

Change-of-decision conditions  
• If the warehouse starts mixing items from 5–10 orders per package routinely, convergence risk on packages and deliveries would grow and we would switch to position C (fully object-centric).

## 7. Sensitivity and validation plan  

1. Shared-event down-weighting  
   • Re-compute KPIs on an order-flattened log where each shared event contributes 1 / n to frequency (n = number of copied traces).  
   • Compare with unweighted results; flag >10 % deviations.

2. Propagation test  
   • Create `ocel_propagated` by recursively adding OrderItemPackageDelivery links.  
   • Re-discover OC-DFG and measure path frequency changes.  
   • Large increases indicate hidden couplings that order flattening misses.

3. Lead-object swap  
   • Redo DFG discovery on Package and Delivery flattenings.  
   • Evaluate whether any performance conclusion (e.g., average ‘PackDispatch’ time) changes sign (from improvement to deterioration).  
   • If yes, escalate for deeper OC inspection.

4. Metric basis sensitivity  
   • Compute throughput times (a) per event count, (b) per unique Order object, (c) per total Order objects (counting duplicates).  
   • Plot the three metrics. Divergence beyond ±5 % points indicates duplication bias.

These checks ensure that no single modelling choice dictates the business conclusion.
