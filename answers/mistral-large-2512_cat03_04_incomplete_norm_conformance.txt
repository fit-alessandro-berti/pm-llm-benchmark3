# Normative Interpretation of Object-Centric Deviations

## 1. Conformance semantics

**Distinction framework:**

1. **Forbidden behavior**: Explicitly disallowed by the norm (closed-world assumption). Any occurrence is a violation regardless of frequency.
2. **Missing mandatory behavior**: Required relations that are absent within their stated scope (closed-world for mandatory columns). Must consider scope applicability and abstraction limitations.
3. **Unexpected but unregulated behavior**: Relations not covered by the norm (open-world assumption). Only classified as suspicious if they contradict other normative statements or suggest data quality issues.
4. **Typical-pattern absence**: Common but non-mandatory relations that are missing. Only concerning if frequency suggests systematic deviation.
5. **Likely data-quality error**: Relations that violate logical consistency or system design principles, even if not explicitly forbidden.
6. **Abstraction mismatch**: Deviations that result from modeling choices (e.g., directly-follows vs. eventually-follows) rather than actual process issues.
7. **Insufficient evidence**: Cases where the norm's scope or the observation's context is too ambiguous to classify.

**Open-world vs. closed-world impact:**
- Closed-world applies only to:
  - Relations marked "forbidden" (any occurrence is a violation)
  - Mandatory relations within their stated scope (absence is a violation)
- All other relations are open-world: absence doesn't imply noncompliance, and presence doesn't imply compliance unless it contradicts a forbidden/mandatory rule.

## 3. Detailed reasoning by model family

### OC-DFG

**What it establishes:**
- Directly-follows relations between object lifecycle states
- Frequency counts for these relations
- Clear violations of forbidden patterns (N3)
- Potential gaps in mandatory patterns (N1, N4)

**What it cannot establish:**
- Eventually-follows relations (only directly-follows)
- Context of missing relations (whether they should apply)
- Whether missing relations are due to data quality or process variation
- The complete scope of "externally shipped packages" (N4)

**Counts and scopes:**
- N1: 98/100 is high but not 100%. The norm says "eventually" but we measure directly-follows. The 2 missing could be abstraction mismatch.
- N4: 198/200 suggests 1% missing, but scope is "externally shipped" - we don't know if the 2 missing were internal.
- N3: 2/100 is low frequency but critical severity because forbidden.

**Abstraction dangers:**
- Directly-follows is stricter than "eventually-follows". A missing directly-follows relation might still satisfy an eventually-follows requirement.
- The norm's "summary approximates this with directly-follows" (N1) acknowledges this limitation.

### OTG

**What it establishes:**
- Object-to-object relationships through specific interaction types
- Clear violations of forbidden object relationships (T6)
- Gaps in mandatory relationships (T1, T2)
- Unexpected but unregulated relationships (T4, T5)

**What it cannot establish:**
- Whether relationships are appropriate for the business context
- Whether missing relationships are due to data quality or process variation
- The semantic meaning of relationships (e.g., why Order-RiskCase exists)

**Counts and scopes:**
- T2: 200 expected, 198 observed - 1% missing. The 2 missing have carrier references, suggesting data quality rather than process issue.
- T6: 1 occurrence is critical because forbidden, regardless of frequency.
- T4/T5: High counts but unregulated - cannot classify as violations.

**Abstraction dangers:**
- Object interactions might be recorded at different granularities than expected.
- The norm doesn't specify whether relationships should be one-to-one or one-to-many.

### ET–OT

**What it establishes:**
- Which object types must be involved in each event type
- Clear violations of forbidden event-object combinations (E10)
- Gaps in mandatory event-object participation (E1-E8)

**What it cannot establish:**
- Whether missing object participation is due to data quality or process variation
- The semantic meaning of object participation (e.g., why Manual Compliance Review involves Customer)
- Whether unobserved object types should have been involved

**Counts and scopes:**
- E6: 200 expected, 198 observed - 1% missing. Similar to T2, likely data quality.
- E8: 93 payments, 92 invoices - 1 missing. The norm allows exceptions for unapplied cash, but this isn't labeled.
- E10: 1 occurrence is critical because forbidden.

**Abstraction dangers:**
- The norm specifies "every" event of certain types must involve certain objects, but real processes might have legitimate exceptions.
- Event-object relationships might be recorded at different levels of granularity.

```python
import pm4py
from typing import Dict, Tuple, List

# Load observed log
ocel = pm4py.read_ocel("observed_log.jsonocel")

# Discover observed models
observed_ocdfg = pm4py.discover_ocdfg(ocel)
observed_otg = pm4py.discover_otg(ocel)
observed_etot = pm4py.discover_et_ot_relations(ocel)

# Normative models (would be defined elsewhere)
norm_ocdfg = {
    "Order": {
        "Create Order": {"Validate Order": "mandatory"},
        "Cancel Order": {"Dispatch Package": "forbidden"},
        "Validate Order": {"Close Order": "typical"}
    },
    "Package": {
        "Pack Package": {"Dispatch Package": "mandatory"}
    },
    "Invoice": {
        "Issue Invoice": {"Record Payment": "typical"}
    }
    # ... other normative relations
}

norm_otg = [
    (("Order", "object_interaction", "Item"), "mandatory"),
    (("Package", "object_interaction", "Delivery"), "mandatory"),
    (("Invoice", "object_interaction", "Payment"), "typical"),
    (("Order", "object_cobirth", "Payment"), "forbidden")
    # ... other normative OTG relations
]

norm_etot = [
    (("Create Order", "Order"), "mandatory"),
    (("Add Item", "Order"), "mandatory"),
    (("Add Item", "Item"), "mandatory"),
    (("Dispatch Package", "Delivery"), "mandatory"),
    (("Sensor Heartbeat", "Invoice"), "forbidden")
    # ... other normative ET-OT relations
]

# Run conformance checking
ocdfg_diagnostics = pm4py.conformance_ocdfg(ocel, norm_ocdfg)
otg_diagnostics = pm4py.conformance_otg(ocel, norm_otg)
etot_diagnostics = pm4py.conformance_et_ot(ocel, norm_etot)

# Semantic classification layer
def classify_deviations(diagnostics: Dict, norm_model: Dict, model_type: str) -> List[Dict]:
    """
    Classify PM4Py diagnostics into semantic categories.
    Requires maintaining the normative status (mandatory/forbidden/typical/unspecified)
    outside the bare graph structures.
    """
    classified = []

    for deviation in diagnostics.get("deviations", []):
        # Extract norm reference
        norm_ref = None
        if model_type == "ocdfg":
            obj_type = deviation["object_type"]
            source = deviation["source"]
            target = deviation["target"]
            norm_ref = norm_model.get(obj_type, {}).get(source, {}).get(target)
        elif model_type == "otg":
            edge = (deviation["source_type"], deviation["relation"], deviation["target_type"])
            norm_ref = next((status for (e, status) in norm_otg if e == edge), None)
        elif model_type == "etot":
            edge = (deviation["event_type"], deviation["object_type"])
            norm_ref = next((status for (e, status) in norm_etot if e == edge), None)

        # Classify based on norm status and deviation type
        if norm_ref == "forbidden" and deviation["type"] == "present":
            classification = "forbidden_behavior"
            severity = "critical"
        elif norm_ref == "mandatory" and deviation["type"] == "missing":
            classification = "missing_mandatory"
            severity = "high"
        elif norm_ref == "typical" and deviation["type"] == "missing":
            classification = "typical_pattern_absence"
            severity = "low"
        elif norm_ref is None:
            classification = "unregulated_behavior"
            severity = "info"
        else:
            classification = "unclassified"
            severity = "medium"

        classified.append({
            **deviation,
            "norm_reference": norm_ref,
            "classification": classification,
            "severity": severity
        })

    return classified

# Classify all deviations
classified_ocdfg = classify_deviations(ocdfg_diagnostics, norm_ocdfg, "ocdfg")
classified_otg = classify_deviations(otg_diagnostics, norm_otg, "otg")
classified_etot = classify_deviations(etot_diagnostics, norm_etot, "etot")

# Combine and rank findings
all_findings = classified_ocdfg + classified_otg + classified_etot
ranked_findings = sorted(all_findings, key=lambda x: (
    0 if x["severity"] == "critical" else
    1 if x["severity"] == "high" else
    2 if x["severity"] == "medium" else
    3 if x["severity"] == "low" else 4,
    -x["count"] if "count" in x else 0
))

# Note: The normative status metadata must be maintained separately from the graph structures
# as shown in norm_ocdfg, norm_otg, and norm_etot above.
```

## 6. Norm-completeness assessment

**1. Scope of "externally shipped packages" (N4)**
- **Risk**: Cannot determine if missing Pack->Dispatch relations are violations or scope mismatches
- **Clarification**: Define criteria for "externally shipped" (e.g., carrier type, destination)
- **Status**: Mandatory (to apply the rule correctly)

**2. Eventually-follows vs. directly-follows (N1)**
- **Risk**: False positives for missing mandatory relations due to abstraction mismatch
- **Clarification**: Specify maximum allowed time between Create Order and Validate Order
- **Status**: Mandatory (to operationalize the rule)

**3. Unapplied cash labeling (E8)**
- **Risk**: Cannot distinguish legitimate unapplied cash from data quality issues
- **Clarification**: Require explicit event type for unapplied cash
- **Status**: Mandatory (to distinguish exceptions from violations)

**4. Manual Compliance Review scope (N6, T5)**
- **Risk**: Cannot assess whether interactions with RiskCase/Customer are appropriate
- **Clarification**: Define when Order-RiskCase interactions are expected/allowed
- **Status**: Typical (common but not required)

**5. Package-Delivery lifecycle completion (object_codeath)**
- **Risk**: Cannot determine if codeath edges indicate data quality issues
- **Clarification**: Specify whether codeath is allowed/expected for Package-Delivery
- **Status**: Explicitly unspecified (to acknowledge the gap)

**6. Minimum frequencies for typical patterns (N2, N5)**
- **Risk**: Cannot determine if low frequencies indicate process problems
- **Clarification**: Define statistical tolerance bands for typical patterns
- **Status**: Typical (to provide guidance without strict requirements)
