# 1. Assumptions and Interpretation

1. **Risk route.** The low/high risk choice is modeled as an observable-free XOR: low risk requires `Supervisor Review`; high risk requires `Quality Review` and `Regulatory Review` concurrently. Since risk data is not represented in event labels, the choice is nondeterministic control flow.
2. **Optional supplier consultation.** `Consult Supplier` is modeled as `XOR(silent skip, Consult Supplier)`. It is enabled only after `Analyze Root Cause` and must complete before `Release Material`. It occurs at most once because it is not inside a loop.
3. **Passing inspection abstraction.** Inspection pass/fail is not an event label. I model trial repetition as `LOOP(Execute Trial -> Inspect Trial, Adjust Parameters)`. The last `Inspect Trial` before exiting the loop is interpreted as the passing inspection; any `Adjust Parameters` is interpreted as following a failed inspection and must be followed by another `Execute Trial -> Inspect Trial` cycle. No explicit pass/fail event is added.
4. **Duplicate visible labels.** I do not permit duplicate visible-label nodes. Each activity label has one model node/transition. `Execute Trial` and `Inspect Trial` can occur multiple times only by executing the same loop node repeatedly.
5. **Process-tree approximation policy.** I use a **conservative under-approximation**. The process tree preserves all mandatory dependencies and release synchronization, but it forces an early join of `(Contain Material -> Plan Verification)` and `(Analyze Root Cause -> Design Corrective Action)` before risk review, supplier consultation, and trial begin. This excludes some valid interleavings but does not admit unsafe dependency reversals.
6. **“May overlap” interpretation.** “May overlap” is interpreted as true concurrency/interleaving. In POWL, absence of a partial-order edge means no enforced order. In the process tree, `PARALLEL` means interleaving, but because the tree is block-structured, some intended overlap is lost.
7. **Start and end.** Every trace starts with `Register Deviation` and ends with `Archive Case`.
8. **Data conditions.** Low/high risk, supplier selection, and inspection result are treated as control-flow alternatives/nondeterminism, not data-aware guards.

# 3. PM4Py Process-Tree Model

**Compact process-tree expression.**  
Here `->` is sequence, `+` is parallel, `X` is XOR, `*` is loop, and `tau` is silent.

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->('Analyze Root Cause', 'Design Corrective Action')
  ),
  +(
    *(
      ->('Execute Trial', 'Inspect Trial'),
      'Adjust Parameters'
    ),
    X(
      'Supervisor Review',
      +('Quality Review', 'Regulatory Review')
    ),
    X(
      tau,
      'Consult Supplier'
    )
  ),
  'Release Material',
  'Archive Case'
)
```

**Self-contained Python construction.**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def silent():
    return ProcessTree()

def op(operator, *children):
    node = ProcessTree(operator=operator)
    for child in children:
        child.parent = node
        node.children.append(child)
    return node

rd = leaf("Register Deviation")
cm = leaf("Contain Material")
arc = leaf("Analyze Root Cause")
pv = leaf("Plan Verification")
dca = leaf("Design Corrective Action")
sr = leaf("Supervisor Review")
qr = leaf("Quality Review")
rr = leaf("Regulatory Review")
cs = leaf("Consult Supplier")
et = leaf("Execute Trial")
it = leaf("Inspect Trial")
ap = leaf("Adjust Parameters")
rm = leaf("Release Material")
ac = leaf("Archive Case")

tau = silent()

risk_low = sr
risk_high = op(Operator.PARALLEL, qr, rr)
risk = op(Operator.XOR, risk_low, risk_high)

supplier_opt = op(Operator.XOR, tau, cs)

trial_body = op(Operator.SEQUENCE, et, it)
trial = op(Operator.LOOP, trial_body, ap)

left = op(Operator.SEQUENCE, cm, pv)
right = op(Operator.SEQUENCE, arc, dca)
init_join = op(Operator.PARALLEL, left, right)

post = op(Operator.PARALLEL, trial, risk, supplier_opt)

tree = op(Operator.SEQUENCE, rd, init_join, post, rm, ac)
```

**Exactness and approximation.**  
The tree cannot represent the intended non-block-structured partial order exactly. It preserves the mandatory precedences: `Register Deviation` first, `Contain Material -> Plan Verification`, `Analyze Root Cause -> Design Corrective Action`, risk XOR, high-risk concurrent reviews, optional supplier XOR, trial loop, and final `Release Material -> Archive Case`. However, it forces `Supervisor Review`, `Quality Review`, `Regulatory Review`, and `Consult Supplier` to start only after both `Plan Verification` and `Design Corrective Action` are complete, because they are placed in the second parallel block after the early join. The intended semantics only require approvals and supplier to start after `Analyze Root Cause`, and approvals may overlap `Design Corrective Action`, `Plan Verification`, and trial work. The tree therefore under-approximates allowed interleavings. It does not duplicate visible labels; the only repetition is through the trial loop.

# 4. PM4Py POWL Model

**Compact POWL description.**

```text
StrictPartialOrder(
  nodes:
    Register Deviation,
    Contain Material,
    Analyze Root Cause,
    Plan Verification,
    Design Corrective Action,
    RiskRoute = XOR(Supervisor Review,
                    StrictPartialOrder(Quality Review, Regulatory Review)),
    SupplierOpt = XOR(SilentTransition, Consult Supplier),
    TrialLoop = LOOP(StrictPartialOrder(Execute Trial -> Inspect Trial),
                     Adjust Parameters),
    Release Material,
    Archive Case

  edges:
    Register Deviation -> Contain Material
    Register Deviation -> Analyze Root Cause
    Contain Material -> Plan Verification
    Analyze Root Cause -> Design Corrective Action
    Analyze Root Cause -> RiskRoute
    Analyze Root Cause -> SupplierOpt
    Design Corrective Action -> TrialLoop
    Plan Verification -> TrialLoop
    TrialLoop -> Release Material
    RiskRoute -> Release Material
    SupplierOpt -> Release Material
    Release Material -> Archive Case
)
```

**Self-contained Python construction.**

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

rd = Transition("Register Deviation")
cm = Transition("Contain Material")
arc = Transition("Analyze Root Cause")
pv = Transition("Plan Verification")
dca = Transition("Design Corrective Action")
sr = Transition("Supervisor Review")
qr = Transition("Quality Review")
rr = Transition("Regulatory Review")
cs = Transition("Consult Supplier")
et = Transition("Execute Trial")
it = Transition("Inspect Trial")
ap = Transition("Adjust Parameters")
rm = Transition("Release Material")
ac = Transition("Archive Case")

# Risk route: low = Supervisor Review; high = Quality Review and Regulatory Review concurrent.
risk_low = sr
risk_high = StrictPartialOrder([qr, rr])  # no edge between qr and rr
risk = OperatorPOWL(Operator.XOR, [risk_low, risk_high])

# Optional supplier consultation.
supplier = OperatorPOWL(Operator.XOR, [SilentTransition(), cs])

# Trial loop: (Execute Trial -> Inspect Trial), then optionally Adjust Parameters and repeat.
cycle = StrictPartialOrder([et, it])
cycle.order.add_edge(et, it)
trial = OperatorPOWL(Operator.LOOP, [cycle, ap])

# Root partial order.
root = StrictPartialOrder([rd, cm, arc, pv, dca, risk, supplier, trial, rm, ac])

root.order.add_edge(rd, cm)
root.order.add_edge(rd, arc)
root.order.add_edge(cm, pv)
root.order.add_edge(arc, dca)
root.order.add_edge(arc, risk)
root.order.add_edge(arc, supplier)
root.order.add_edge(dca, trial)
root.order.add_edge(pv, trial)
root.order.add_edge(trial, rm)
root.order.add_edge(risk, rm)
root.order.add_edge(supplier, rm)
root.order.add_edge(rm, ac)

powl = root
```

**Concurrency explanation for unconnected nodes.**  
In the root `StrictPartialOrder`, missing edges mean no enforced order. `Contain Material` and `Analyze Root Cause` are both enabled after `Register Deviation` and have no edge between them, so they may overlap. `Plan Verification` and `Design Corrective Action` have no edge between them, so once their respective prerequisites are met they may overlap. `RiskRoute`, `SupplierOpt`, and `TrialLoop` have no edges among themselves, so approvals, supplier consultation, and trial work may overlap. Inside the high-risk branch, `Quality Review` and `Regulatory Review` have no edge and may occur concurrently or in either completion order. Inside `TrialLoop`, `Execute Trial` precedes `Inspect Trial` via `cycle.order.add_edge(et, it)`, but `Adjust Parameters` only returns to the next cycle. The optional supplier XOR has mutually exclusive children: skip versus `Consult Supplier`; those are intentionally not concurrent.

| Optional supplier consultation | Supplier may be skipped or selected once; if selected, after ARC and before release, overlapping other work. | XOR(silent, Consult Supplier) is correct, but it waits for early join. | XOR(silent, Consult Supplier); ARC -> SupplierOpt -> RM; no other edges. | Process tree under-approximates start; POWL exact. | Supplier can be involved concurrently when selected. |
| Repeat-until behavior | ET -> IT, failed IT triggers AP and next ET-IT; passing IT exits. | LOOP(ET->IT, AP) abstracts pass/fail. | LOOP(Execute Trial->Inspect Trial, Adjust Parameters) abstracts pass/fail. | No visible pass/fail label, so outcome is not directly auditable. | Repeated trials are modeled; hidden inspection result remains data-dependent. |
| Release synchronization | Release requires passing trial, selected approval route, and supplier if selected. | RM after post parallel of trial, risk, supplier. | Edges TrialLoop -> RM, RiskRoute -> RM, SupplierOpt -> RM. | Process tree synchronizes correctly but only after its early join; POWL exact. | Material cannot be released until all required obligations finish. |
| Duplicate-label risk | No duplicate activity nodes; only trial loop repeats ET/IT. | One node per activity; ET/IT repeat via loop. | One Transition per activity; ET/IT repeat via loop. | No duplicate visible-label nodes in either model. | Avoids conformance ambiguity from duplicated labels. |

# 7. Preferred Representation and Validation Plan

**Preferred canonical representation:** the POWL model. POWL expresses the intended cross-branch dependencies directly as partial-order edges: `ARC -> RiskRoute`, `ARC -> SupplierOpt`, `DCA/PV -> TrialLoop`, and `TrialLoop/RiskRoute/SupplierOpt -> Release Material`. The process tree is useful as an executable under-approximation, but it imposes an early join that is not in the intended semantics.

**Validation plan.**

1. **Conversion to accepting Petri nets where supported.** Convert the POWL model and the process tree using `pm4py.convert_to_petri_net(model)` where supported. If POWL conversion is not fully supported in the installed PM4Py version, convert the process tree and separately inspect POWL playout behavior.
2. **Soundness checking.** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on each converted Petri net. Inspect diagnostics for deadlocks, improper completion, and unreachable markings.
3. **Bounded or sampled playout.** Use `pm4py.play_out(powl, num_traces=1000)` and `pm4py.play_out(tree, num_traces=1000)` with a bounded number of traces. Check that every trace begins with `Register Deviation` and ends with `Archive Case`.
4. **Explicit positive and negative trace tests.** Encode the eight witness traces as event logs. Use token-based replay or alignment diagnostics to confirm A1–A5 are accepted by POWL and F1–F3 are rejected. For the process tree, confirm A1–A4 are accepted, A5 is rejected, and F1–F3 are rejected.
5. **Silent-behavior and duplicate-label check.** For `SupplierOpt`, inspect playout traces where `Consult Supplier` is absent versus present; ensure absence corresponds to the silent skip and does not create visible artifacts, and that `Consult Supplier` appears at most once. For the trial loop, check that every `Adjust Parameters` is followed by a new `Execute Trial` and `Inspect Trial`, and that no trace ends with `Adjust Parameters` immediately before `Release Material`. Count `Execute Trial` and `Inspect Trial` occurrences: they should match, and `Adjust Parameters` should occur exactly one fewer time than `Execute Trial` for multi-cycle traces. Verify no independent model node duplicates a visible label.
6. **Limitations.** Conversion may lose or approximate partial-order concurrency. Playout is bounded and cannot prove all behavior. The hidden data conditions—risk level, supplier involvement, inspection pass/fail—are not event labels, so conformance tests cannot distinguish real-world pass/fail or risk data from the control-flow abstraction. Soundness of a converted net does not prove fidelity to the original narrative.

# 8. Final Self-Critique

1. The process tree is a conservative under-approximation. It preserves safety but loses valid interleavings where risk review or supplier consultation starts before `Design Corrective Action`/`Plan Verification` complete. This is a semantic loss, not just a syntax choice.
2. The POWL loop abstracts inspection outcomes. It enforces that `Adjust Parameters` precedes another trial cycle, but it cannot verify from event labels that `Adjust Parameters` followed a failed inspection rather than a passing one; the passing/failing distinction remains an interpretive assumption.
3. Risk and supplier choices are free nondeterministic XORs. The model does not represent the case data that determines low/high risk or whether supplier consultation is selected, so analytics may overgenerate variants that would not occur under real data conditions.
