Compare methods:
- Kaplan-Meier: estimates survival, but treats competing events and transfers as censoring. Assumes independent censoring. Not ideal for competing risks or informative transfer. Can be used as secondary with sensitivity.
- Aalen-Johansen / CIF: estimates cumulative incidence of Resolve, Withdraw, Reject, Transfer (if treated as event) separately. Handles competing risks correctly. Primary for "probability of resolution by t" and "probability of breach" in competing risk sense.
- Cause-specific hazards: model instantaneous rate of each event type. Good for understanding drivers (e.g., does escalation increase resolve hazard or transfer hazard?). Secondary.

# 1. SLA estimands and time definitions

**Assumptions:** The time origin $t=0$ is the `Submit` event for every case. The SLA horizon is $\tau=72$ hours. All durations are observed elapsed hours from `Submit`; because exact event timestamps are not provided, any stage-level timing is approximate or sequence-based (see §8).

| Concept | Definition |
|---|---|
| **Time origin** | `Submit` |
| **Horizon / SLA** | $t = 72$ h |
| **Event of interest (success)** | `Resolve` |
| **Competing terminal internal events** | `Withdraw`, `Reject` |
| **External exit / observation stop** | `Transfer`; eventual resolution unknown |
| **Administrative right-censoring** | `open` at extract cutoff ($t = \text{duration\_or\_age\_h}$) |
| **Informative gap** | `last_event_gap_h > 0` suggests stalled processing |

**Estimands (at least three, with operational mappings):**

* **Estimand A — Overall non-resolution by 72 h (breach / workload risk).**  
  $\theta_{unres}(72) = \Pr(\text{case not observed as `Resolve`} \mid t \le 72)$.  
  This counts any case whose observed status at 72 h is not `Resolve`, including those already `Withdraw`/`Reject`/`Transfer` before 72 h and those still `open`. *Match:* Daily backlog and staffing alerts; “how many cases will miss SLA regardless of terminal outcome?”

* **Estimand B — Cumulative incidence of success within / after 72 h (CIF).**  
  $F_{res}(t) = \Pr(T \le t \land \text{event}=\text{Resolve})$, estimated via Aalen-Johansen to respect competing exits. The post-72 h tail is $F_{res}(t) - F_{res}(72)$. *Match:* Service-level reporting and “what fraction eventually resolves late?”

* **Estimand C — State occupancy / “no terminal internal disposition” at 72 h.**  
  $P(\text{state}=\text{Open} \cup \text{Transferred-at-72h} \mid T \ge 72)$. Because `Transfer` stops internal observation, it is ambiguous whether it counts as a terminal disposition; we therefore report both interpretations. *Match:* Queue forecasting and external-coordination workload.

* **Estimand D — Cause-specific hazard of resolution vs. exit.**  
  $\lambda_{res}(t) = \lim_{dt\to 0} \Pr(t \le T < t+dt, \text{Resolve} \mid T \ge t)/dt$. *Match:* Process diagnostics (e.g., does escalation raise $\lambda_{res}$ or $\lambda_{trans}$?).

**Concrete contributions:**

| Case | Status / time | Est A (not resolved by 72?) | Est B (CIF contribution) | Est C (open/unresolved at 72?) | Notes |
|---|---|---|---|---|---|
| **S03** (A, 76 h, resolved) | Resolved after horizon | **1** (not resolved at 72 h) | Adds to $F_{res}$ at 76 h | Not open at 72 h | Late success; breach |
| **S09** (A, 92 h, open) | Open, gap 31 h | **1** | Not yet in $F_{res}$ | **Yes** (open at 72 h) | Right-censored; already over SLA |
| **S06** (A, 27 h, withdrawn) | Competing exit early | **1** | Excluded from $F_{res}$; contributes to $F_{with}$ | No (terminal at 27 h) | Fast failure; removes from resolve risk set |
| **S08** (A, 68 h, transferred) | Transfer below 72 h | **1** (assuming unresolved) | Unknown; excluded from $F_{res}$ under competitive coding | Ambiguous (external exit) | Escalated (yes); informative |

> **Distinction:** “Not resolved by 72 h” (Est A) is a state at 72 h; “cumulative incidence after 72 h” (Est B) is a future projection requiring competing-risk handling; “open at 72 h” (Est C) is a subset of Est A that excludes already-closed failures.

# 2. Event and censoring encoding

| Observed status | Primary coding (Resolve-focused) | Competing-risk code | Censoring rule | Sensitivity alternatives |
|---|---|---|---|---|
| **resolved** | Event = `Resolve`; time = `duration_or_age_h`; event indicator = 1 | — | Not censored | Always an event; if $t>72$ contributes to late CIF |
| **open** | Event = none; time = `duration_or_age_h`; event indicator = 0 | — | **Administrative right-censoring** at cutoff | (a) If gap > 24 h treat as “stalled” / likely breach; (b) If cutoff is stale, impute failure; (c) If still active, remain censored |
| **withdrawn** | Event = `Withdraw`; time = duration; event = 0 for Resolve | Competing event (code 2) | **Not censored** — terminal observed | (i) Competing exit (correct); (ii) Censoring if only Resolve is of interest (biases $S(t)$ up); (iii) Failure if SLA applies to all cases |
| **rejected** | Event = `Reject`; time = duration; event = 0 | Competing (code 3) | Terminal observed | Same as withdrawn |
| **transferred** | Event = unknown / unobserved; time = duration; event = 0 | **Assumption T1 (Competing):** code 4; **Assumption T2 (Censored):** code 0; **Assumption T3 (Failure):** code 0 but counted as breach | (T1) Not censored; (T2) Right-censored at transfer; (T3) Failure / unresolved | See three scenarios below |

**Three explicit transfer-treatment assumptions:**

1. **T1 — Competing external exit (Aalen-Johansen / multi-state).** `Transfer` is an absorbing competing event at $t = 68, 26, 96$ h (S08, S21, S32). We estimate $F_{trans}(t)$ separately; these cases are removed from the Resolve risk set at transfer time.
2. **T2 — Informative right-censoring (Kaplan-Meier / Cox sensitivity).** `Transfer` is censored at $t$; we assume external resolution is independent of internal process, which is likely false because all three transfers (`S08`, `S21`, `S32`) are escalated (`escalated=yes`) and high-priority (P1).
3. **T3 — SLA failure / unresolved (worst-case / operational).** If external resolution is not guaranteed and the internal SLA is “resolve inside,” then transfer before 72 h is equivalent to breach. We code `event=0`, `status=failure`, and include in Est A numerator.

> **Critical distinction:** `Withdraw` and `Reject` are **not** ordinary non-informative censoring; they are terminal competing events that permanently prevent Resolve. Only `open` is administrative censoring, and only if the cutoff is neutral.

# 3. Why naive completed-case analysis is biased

A completed-case analysis that keeps only `resolved` cases (S01–S04, S07, S13, S16–S20, S27, S28; $n \approx 14$) and drops `open`, `withdrawn`, `rejected`, or `transferred` is biased in at least five ways, demonstrated with concrete IDs.

**1. Survivor / selection bias (ignores ongoing and failed cases).**
- Cases above 72 h that are **open** (S09 at 92 h, S26 at 104 h, S11 at 81 h, S25 at 79 h) are excluded, yet they are precisely the long-tail cases that define SLA risk. Removing S26 (B, P3, 104 h, gap 72 h) truncates the longest observed age.
- Completed-case mean time is $\approx 47$ h; including the five open cases above 72 h raises the average and changes the tail.

**2. Competing-risk distortion (fast failures disappear).**
- `S05` (P3, 9 h, rejected) and `S23` (P3, 11 h, rejected) are rapid failures. If excluded, the estimated “speed to resolution” is inflated because fast exits from the process are omitted.
- `S06` (27 h, withdrawn) and `S12` (15 h, withdrawn) and `S22` (44 h, withdrawn) and `S30` (70 h, withdrawn) represent cases that never reach Resolve; dropping them overestimates the probability of eventual success.

**3. Informative censoring by escalation / transfer.**
- Transfers (`S08`: P1, 68 h, escalated; `S21`: P1, 26 h, escalated; `S32`: P1, 96 h, escalated) are not random: all have `escalated=yes`. If treated as non-informative censoring, the analysis implicitly assumes transferred cases would have resolved like non-transferred cases, which is unsupported. Escalation is a process signal of difficulty.

**4. Cohort imbalance confounded by assignment mechanism.**
- Cohort A: `Screen` before `AutoCheck` in most paths (e.g., S01 `Submit>Screen>AutoCheck>Resolve`; S07 `Submit>Screen>Review>Rework>...`).
- Cohort B: `AutoCheck` often immediately after `Submit` (S16 `Submit>AutoCheck>Screen>Resolve`; S18 `Submit>AutoCheck>Escalate>Resolve`; S27 `Submit>AutoCheck>Screen>Review>Rework>Resolve`).
- Because assignment was not randomized and rollout compliance was incomplete, comparing only resolved cases across cohorts mixes process change (`AutoCheck` screening) with case-mix differences (B has more early `AutoCheck` paths and more P1 escalations). For example, S18 (B, P1, 12 h, escalated, resolved) is very fast; is that due to policy or due to case severity?

**5. Active open cases above vs. below 72 h have different meanings.**
- Below 72 h: S15 (35 h, gap 2 h, `AutoCheck>Review`) is actively progressing; S31 (23 h, gap 3 h, `AutoCheck>Screen`) is early-stage.
- Above 72 h: S09 (92 h, gap 31 h, `Review`); S26 (104 h, gap 72 h, `Review`). These are stalled. A naive completed-case analysis treats them as “not yet finished” and simply deletes them, when in fact they are likely breaches and should drive the tail-risk estimate.

> **Bottom line:** Any estimator that conditions on `observed_status == 'resolved'` conditions on the future and excludes the very cases (open long-gap, escalated-transferred, fast-rejected) that generate SLA risk.

# 4. Statistical analysis plan

| Method | What it estimates | Strengths for this data | Weaknesses / cautions | Recommended role |
|---|---|---|---|---|
| **Kaplan-Meier (KM)** | $S(t) = \Pr(T > t)$ for single event | Easy; handles right-censoring (open cases) if censoring is independent | Treats `Withdraw`/`Reject`/`Transfer` as censoring; assumes independent censoring (likely false for escalated transfers); overestimates resolution prob under competing exits | **Sensitivity / secondary only**; use under T2 (transfer=censored) with explicit caveat |
| **Aalen-Johansen (AJ)** | $F_k(t)$ for each cause $k$ (Resolve, Withdraw, Reject, Transfer) | Correctly partitions probability mass among competing exits; ideal for “probability of resolving by 72 h vs. withdrawing” | Requires larger $n$; with $n=32$ variance is high; still treats open cases as censored correctly | **Primary for SLA metrics** (Est B and A with competing-risk interpretation) |
| **Cause-specific hazards ($\lambda_k$)** | Instantaneous rate of each event | Shows whether escalation increases $\lambda_{res}$ or $\lambda_{trans}$; process-diagnostic | Not directly a probability; need integration for CIF | **Secondary / process-diagnostic** |
| **Subdistribution hazards (Fine-Gray)** | Effect of covariates on $F_k(t)$ directly | Useful if question is “does Cohort B reduce breach risk?” | Proportionality assumption on subdistribution is strong; interpretation is tricky with small $n$ | **Secondary for cohort/policy comparison** |
| **Restricted Mean (RMST)** | $\int_0^\tau S(t)\,dt$ or $\int_0^\tau F_{res}\,dt$ | Robust to censoring; no proportionality assumption; interpretable as “average hours saved/ lost to 72 h” | $\tau$ must be pre-specified; does not give tail beyond $\tau$ | **Secondary policy comparison** (e.g., Cohort A vs B up to 72 h) |
| **Landmarking** | Conditional survival from $t=\ell$ to $\tau$ among open cases | Dynamic: at 24 h or 48 h, forecast remaining 24–48 h to breach; uses `last_event_gap_h` naturally | Reduces sample at $\ell$; requires sufficient $n$ at landmark | **Operational alert model** (secondary) |
| **Multi-state model** | Transition intensities between stages (Submit  Screen  AutoCheck  Review  Escalate  Resolve/Transfer) | Directly uses prefixes; handles stage-dependent hazards; can define “time to Escalate” and “time from Escalate to Resolve” | More complex; needs time-stamped stage transitions (only sequence is observed here) | **Primary process-aware framework**; use for feature design and stage hazards (§5) |

**Recommendation for these 32 cases:**
- **Primary:** Aalen-Johansen / multi-state hybrid. Use multi-state logic to classify stage from prefix and compute transition patterns (e.g., `AutoCheck` first vs. second); then use AJ to estimate $F_{res}(72)$ and $F_{with}(72)$ separately by cohort/priority.
- **Secondary:** RMST to compare cohort B vs. A on mean time-to-resolution (or time-to-event) up to $\tau = 72$ or $120$ h, because assignment was non-random and RMST is less sensitive to tail assumptions.
- **Sensitivity:** KM under T2 (transfer=censored) and under T3 (transfer=breach) to bracket the range.

> The estimand determines the estimator: if the decision is “do we need more staff for cases that have not resolved by 72 h?”, use Est A / AJ / state occupancy; if the decision is “did the new screening policy speed up resolution?”, compare RMST or cause-specific $\lambda_{res}$ with cohort as covariate, but do not treat `escalated` as a baseline covariate.

- Unadjusted: Cohort B has faster resolved times (S16 16 h, S18 12 h, S19 58 h). But B also has more P1 escalations that resolve quickly (S18, S28 at 88 h) and more open overdue cases (S26 104 h).
- Adjusted / stratified by `priority`: P1 cases in B include S21 (transferred 26 h) and S32 (transferred 96 h); P1 in A include S04 (29 h resolved) and S08 (68 h transferred) and S11 (81 h open). The cohort effect is confounded by priority mix.

**Axis 4 — Informative censoring from long gaps.**

- Excluding open cases with `last_event_gap_h > 24` h removes S09 (31), S11 (55), S25 (48), S26 (72). This selectively drops stalled cases; if those are “true failures,” the remaining sample is optimistic.

> **Reversal risk:** If `Transfer` is actually a successful external resolution (not failure), then T3 makes Cohort B look worse; if it is failure, T2 makes B look better. The direction of comparison is **not stable** without external outcome data.

# 7. Operational interpretation

**From survival outputs to alerts (without causal claims):**

- **Dynamic 48-hour alert:** Use landmarking at $t=48$ h. Among open cases at 48 h (S09 at 92 h, S10 at 47 h, S15 at 35 h, etc.), those with `current_stage = Review` or `Escalate` and `last_event_gap_h > 10` h trigger coordination (e.g., S10 gap 19 h, S25 gap 48 h, S29 gap 6 h). Do **not** say “escalation causes delay”; say “cases that have escalated by 48 h have observed longer remaining times.”
- **72-hour breach flag:** Report Est A by cohort/priority. All open cases above 72 h (S09, S10? No S10 is 47; S11 81, S24 67, S25 79, S26 104, S29 51, S31 23) should be flagged. For cases already withdrawn/rejected (S05, S06, S14, etc.), flag as “non-resolved internal outcome,” not “breach due to delay.”
- **Workload action by stage:** Cases with `Rework` in prefix (S07, S13, S27) need quality review; cases with `AutoCheck` first (mostly B) need less manual triage; cases with `Review>Escalate>Transfer` (S08, S21, S32) need external liaison, not internal speed-up.

**Governance reporting:**
- Publish $F_{res}(72)$ and $F_{with}(72)$ separately by cohort, not a single “resolution rate.” If B’s $F_{res}(72)$ is higher, check whether it is due to faster `AutoCheck` screening or due to differential selection.
- Use **RMST to 72 h** for policy comparison: “Mean hours to resolution (or to exit) up to 72 h is X for A vs. Y for B.” This is a descriptive comparison, not a causal effect of the policy, because assignment was non-random.

**Calibration and fairness:**
- **Calibration:** Stratify predictions by `priority` (P1, P2, P3) and `cohort`. If predicted breach probability for P3 is 0.6 but observed is 0.4, recalibrate.
- **Fairness:** P1 cases have different paths (more escalations, more transfers: S04, S08, S11, S18, S21, S25, S32). Ensure risk scores do not penalize P1 merely because escalation is part of high-priority handling; instead, condition on stage (e.g., “P1 at Escalate stage” vs. “P1 at Resolve”).

> **No causal interpretation:** Do not state “Cohort B reduces breach risk by X%.” State: “Under observed assignment and conditional on priority, Cohort B shows a lower observed CIF of Resolve by 72 h (or higher, depending on transfer assumption), which may reflect policy, case mix, or incomplete rollout.”

# 9. Limitations and additional data

To strengthen inference beyond the current 32-case extract, the following are prioritized:

1. **Exact event timestamps for each activity** (`Submit`, `Screen`, `AutoCheck`, `Review`, `Escalate`, `Rework`, `Resolve`, etc.). Without them, stage hazards ($\lambda_{Screen \to Review}$) and time-varying covariates (`escalated(t)`) cannot be estimated precisely; only sequence order is known.

2. **External outcomes after `Transfer`** (`S08`, `S21`, `S32`). Currently `Transfer` is ambiguous (T1–T3). Knowing whether transferred cases resolved externally and when would resolve the sensitivity reversal risk.

3. **Cutoff / observation window dates** (when was the extract frozen?). `duration_or_age_h` is age at cutoff for open cases, but without calendar dates we cannot assess seasonality or whether long gaps (`S09` 31 h, `S26` 72 h) are due to inactivity or data latency.

4. **Time-varying workload / staffing levels** at `Screen`, `Review`, `Escalate`. Cohort B’s faster resolved cases (S16, S18) may reflect reduced workload rather than policy effect.

5. **Assignment mechanism and rollout compliance.** Cohort B began after an automated-screening and escalation-policy change, but assignment was not randomized and rollout was incomplete. We need documentation of which B cases actually received the new screening rule (e.g., did all B cases get `AutoCheck` first? S20 `Submit>Screen>Review` suggests incomplete compliance).

6. **Rework timing and reason codes.** `rework_count` is 0/1; knowing when `Rework` occurred relative to `Review` and whether it correlates with `Escalate` improves stage modeling.

7. **Case-level priority change history.** If `P1` is assigned after initial `Submit`, priority is partly endogenous.

> **Priority order for data collection:** (a) external transfer outcomes; (b) exact stage timestamps; (c) rollout compliance flags; (d) workload covariates. With these, the multi-state / Aalen-Johansen framework can move from descriptive to predictive.
