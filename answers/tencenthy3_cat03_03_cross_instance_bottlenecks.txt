- Expected benefit: eliminates up to 235 min (J1), 215 min (J2), 100 min (J4) of ready-to-start wait.
- Helped: J1, J2, J4, J5.
- Harmed: potentially energy efficiency and RACK-7 cleaning throughput.
- New cost/risk: more oven cycles, more frequent rack cleaning.
- Perverse metric: oven utilization or cost-per-batch may fall, tempting reversal to large batches.
- Evaluation: object-centric query measuring `Job ready`  `Batch start` delta before/after, by Batch and Job.

**I2 — Address tool contention**
- Target: FIX-A and CAL-3 serialization.
- Expected benefit: J4 saves ~115 min; J6 saves ~80 min.
- Helped: J4, J6, CNC-2, TEST-1.
- Harmed: capital budget; if second CAL-3 added, recalibration labor rises.
- New cost/risk: operators may hoard FIX-A to protect local cycle time.
- Perverse metric: tool utilization could drop and be misinterpreted as waste.
- Evaluation: object-centric Tool–Job–Machine start gaps and FIX-A release-before-use compliance.

**I3 — Shipment consolidation policy change**
- Target: S1-style consolidation hold.
- Expected benefit: J1 wait reduced from 355 min to a threshold such as 60 min.
- Helped: J1, possibly J4 if decoupled.
- Harmed: freight economics; shipment count increases.
- New cost/risk: higher transportation cost and carbon footprint.
- Perverse metric: minimizing consolidation wait could maximize shipments; evaluate with cost-per-unit-shipped, not wait alone.
- Evaluation: packed-to-dispatched delay per Shipment, with shipment count tracked as a spillover.

**I4 — Improve logging rather than operations**
- Target: data-integration artifacts.
- Expected benefit: exposes L7–J2/J5 coupling, tool waits, and override usage.
- Helped: all managers and continuous improvement.
- Harmed: integration effort; may surface noncompliant overrides.
- New cost/risk: if override incidents are punished, supervisors may hide them more.
- Perverse metric: “missing edges” could be gamed by fake linkages.
- Evaluation: completeness of Job–ComponentLot edges, presence of `Wait for Tool` events, and anomaly detection on overrides.

**I5 — Decouple component-lot releases**
- Target: L7 quarantine coupling.
- Expected benefit: J5 lot lock reduced from 210 min upper bound; S3 lateness reduced.
- Helped: J5, S3.
- Harmed: traceability overhead; smaller lots cost more to manage.
- New cost/risk: shortening quarantine may increase quality-escape risk.
- Perverse metric: quarantine time reduction could mask real quality problems.
- Evaluation: ComponentLot–Job wait time plus downstream defect rate, using object-centric lot-to-job relations.

## 7. PM4Py analysis outline

```python
import pm4py
import networkx as nx
import pandas as pd

# assume 'ocel' is a loaded OCEL object

# 1. Interaction summary: object-centric frequency metric A
interactions = pm4py.ocel_objects_interactions_summary(ocel)
print("Interactions summary shape:", interactions.shape)

# 2. Object graph and object-type graph

ocdfg = pm4py.discover_ocdfg(ocel)

# Metric A: interactions grouped by object-type pair
metric_a = (interactions
            .groupby(["obj_type_1","obj_type_2"])
            .size()
            .rename("interaction_count"))

# Metric B: OTG edge frequencies (object-type graph)
metric_b = otg.copy()  # expected to contain edge frequency columns
print("Metric A (interactions):\n", metric_a)
print("Metric B (OTG):\n", metric_b)

# 4. Flatten from two perspectives and discover performance DFGs
job_log = pm4py.ocel_flattening(ocel, obj_type="job")
batch_log = pm4py.ocel_flattening(ocel, obj_type="batch")

batch_dfg, batch_perf = pm4py.discover_performance_dfg(batch_log)

    ocel, obj_types=["job","batch","machine","tool","shipment"])
print("Feature matrix shape:", features.shape)

# 6. Object-centric waiting from event timestamps, NOT machine gaps
ev = ocel.events.copy()
rel = ocel.relations.copy()

# Example: J1 ready (Stage Component related to J1) vs B1 Batch Cure
j1_ready_ts = ev.loc[
    (ev["ocel:activity"] == "Stage Component") &
    (rel["ocel:oid"] == "J1"), "ocel:timestamp"].min()
b1_start_ts = ev.loc[
    ev["ocel:activity"] == "Batch Cure", "ocel:timestamp"].min()
if pd.notnull(j1_ready_ts) and pd.notnull(b1_start_ts):
    j1_wait_min = (b1_start_ts - j1_ready_ts).total_seconds() / 60.0
    print("Object-centric J1 sync wait (min):", j1_wait_min)

# Same pattern for J4/FIX-A using tool acquire-release events
fix_release_ts = ev.loc[
    (ev["ocel:activity"] == "Release") &
    (rel["ocel:oid"] == "FIX-A"), "ocel:timestamp"].max()
j4_start_ts = ev.loc[
    (ev["ocel:activity"] == "Machine Process") &
    (rel["ocel:oid"] == "J4"), "ocel:timestamp"].min()
if pd.notnull(fix_release_ts) and pd.notnull(j4_start_ts):
    j4_wait_min = (j4_start_ts - fix_release_ts).total_seconds() / 60.0
    print("Object-centric J4 FIX-A wait (min):", j4_wait_min)

# 7. Networkx conversion for path analysis
G = pm4py.convert_ocel_to_networkx(ocel, obj_graph)
print("Graph nodes:", G.number_of_nodes(), "edges:", G.number_of_edges())
```

The code compares interaction counts with OTG edge frequencies and computes waiting from object-related event timestamps, explicitly avoiding the inference of delays solely from machine-event gaps.

## 8. Falsification and additional data

**Observations that would weaken the top-ranked batch-synchronization explanation**
1. A recorded `Oven Qualification` event at 11:50 showing B1 start was driven by machine readiness, not J3’s 11:55 readiness.
2. Missing upstream events proving J1/J2 were not truly “ready” at 08:10/08:25 despite the table’s assumption.
3. Evidence that RACK-7 was unavailable until 12:05 for an unrelated prior batch, making batching not the binding constraint.
4. A pattern where batches are frequently split yet job cycle times do not improve.
5. Data showing J3’s 11:55 readiness was itself caused by an earlier tool or lot delay, implying batch sync is a symptom, not root cause.
6. Recurrent long waits in jobs that are never batched, indicating a different dominant mechanism.
7. If B1 started earlier for other lots, proving idle time was policy choice rather than synchronization.

**Additional fields or event types that would discriminate among hypotheses**
1. Explicit `Wait for Tool` / `Tool Available` events with timestamps.
2. `Job Ready` event separate from `Stage Component` to validate the 08:10/08:25 claims.
3. `Batch Window Close` timestamp to prove batch policy versus readiness.
4. `RACK-7 Cleaning Start/End` events linked to Batch and Machine.
5. `ComponentLot Released to Job` edge, not merely to Lot, fixing the L7–J2/J5 extraction gap.
6. `Shipment Hold` or `Consolidation Wait` event recording why J1 waited.
7. `Machine Setup Start/End` events to separate idle from blocked time.
8. Shift or operator ID to explain supervisor override and FIX-A scheduling.
9. Oven temperature/recipe events to test capacity versus synchronization.
10. Calibration reason code to distinguish mandatory CAL-3 recalibration from congestion.
