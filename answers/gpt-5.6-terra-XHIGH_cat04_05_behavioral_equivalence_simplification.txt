# 1. Equivalence Notions

Let the visible alphabet be:

\[
\Sigma = \{\text{Open Case},\text{Analyze Revision},\text{Check Revision},
\text{Approve Revision},\text{Rework Case},\text{Close Case}\}
\]

Let `tau` denote a silent transition. A complete execution is one that reaches the accepting final marking.

## Visible trace equivalence after hiding `tau`

For a model \(M\), let:

\[
L_v(M)=\{\pi_v(\sigma)\mid \sigma \text{ is a complete firing sequence of }M\}
\]

where \(\pi_v\) removes silent transitions.

Models are visible-trace equivalent iff:

\[
L_v(A)=L_v(B)
\]

This is a strict observation: visible labels, their order, and their multiplicity are retained.

At this level, repeated visible labels are distinguished by their **occurrence positions** in the trace, not by process-tree leaf identity. For example:

```text
<Check Revision, ..., Check Revision>
```

contains two distinct label occurrences, even though both may arise from repeated execution of the same loop-body leaf.

Under this notion, Models A and B are not equivalent.

## Bounded visible-language equivalence under P3

Define the P3-bounded language:

\[
L_{P3}(M)=\{w\in L_v(M)\mid |w|\leq 12 \land \#_{\text{Analyze Revision}}(w)\leq 3\}
\]

Models are P3-equivalent iff:

\[
L_{P3}(A)=L_{P3}(B)
\]

All visible labels remain observable under P3, including `Approve Revision`. Only `tau` is hidden.

This is a bounded testing relation. Equality of the two bounded sets would be evidence only; it would not prove equality of the unbounded languages.

## Business-relevant equivalence under P1

For P1, the relevant observation is not merely the global label set. It retains:

- `Open Case` and `Close Case`;
- revision boundaries induced by `Rework Case`;
- one `Analyze Revision` occurrence per revision attempt;
- the number and placement of `Check Revision` occurrences;
- optional `Approve Revision` occurrences and their placement;
- whether a check belongs to the same revision block as its analysis.

A revision block is the visible region between:

- `Open Case` or a prior `Rework Case`, and
- the next `Rework Case` or `Close Case`.

P1 treats `Analyze Revision` and `Check Revision` as interchangeable in order within the same completed revision block, because Model A explicitly makes them concurrent. It does **not** hide approvals, reworks, or checks.

A P1-compliant revision block must contain an analysis and its own check before the next `Rework Case` or `Close Case`. Thus, for \(n\) analysis attempts, P1 requires \(n\) corresponding checks.

P1-equivalence requires equality of the resulting revision-block behaviors, including approval placement. Model B fails because it can perform multiple analyses with only one check.

## Abstracted dashboard equivalence under P2

Define the dashboard abstraction \(\alpha_{P2}\) of a complete visible trace \(w\) as:

\[
\alpha_{P2}(w)=(
\text{first}(w),
\text{last}(w),
\#_{\text{Analyze Revision}}(w),
[\#_{\text{Check Revision}}(w)>0],
[\#_{\text{Rework Case}}(w)>0]
)
\]

where `[condition]` is a Boolean.

This abstraction:

- retains that `Open Case` is first;
- retains that `Close Case` is last;
- retains the number of analyses;
- collapses all checks to the Boolean fact that at least one check occurred;
- hides `Approve Revision`;
- hides `tau`;
- ignores exact interleaving between analysis and check;
- records only whether any rework occurred, not how many.

Under P2, duplicate checks are not distinguished by occurrence position or identity: they collapse to one Boolean fact.

For both models, for every \(n \geq 1\):

\[
\alpha_{P2} =
(\text{Open Case},\text{Close Case},n,\text{true},[n>1])
\]

Therefore, the models are equivalent only under this stated dashboard abstraction.

# 2. Structural Comparison

| Feature | Model A | Model B | Semantic consequence |
|---|---|---|---|
| Loop scope | The loop body contains both `Analyze Revision` and `Check Revision`. | The loop contains only `Analyze Revision` and optional approval. `Check Revision` is outside the loop. | A repeats a check for every revision attempt; B executes exactly one check for the entire case. |
| Minimum `Check Revision` occurrences | 1 | 1 | Both always produce at least one check. |
| Maximum `Check Revision` occurrences | Unbounded; one per loop iteration. | Exactly 1. | A can represent repeated compliance checks; B cannot. |
| Relation between analyses and checks | For \(n\) analysis attempts, A has exactly \(n\) checks. | For \(n\) analysis attempts, B has exactly one check. | A satisfies the P1 “one check per revision” rule; B can violate it when \(n>1\). |
| Possible placement of `Check Revision` | Inside every revision attempt. It may occur before or after that attempt’s analysis, but both must finish before approval, rework, or close. | May occur anywhere after `Open Case` and before `Close Case`, including before all analyses, between attempts, or after all analyses. | B can delay the only check until after one or more reworks. |
| Optional approval occurrences | For \(n\) attempts, 0 through \(n\) approvals. Each approval follows completion of both analysis and check for that attempt. | For \(n\) attempts, 0 through \(n\) approvals. Each approval follows its analysis, but the single check can occur before or after approvals. | B admits traces such as `Analyze, Approve, Check`; A does not. |
| Concurrency | `Analyze Revision` is concurrent with `Check Revision` within each loop iteration. | One `Check Revision` is concurrent with the entire revision loop. | A has repeated local synchronization; B has one global concurrent check. |
| Join before rework | The local parallel join completes before optional approval and before `Rework Case`. | There is no requirement that the check complete before a particular `Rework Case`. | A prevents rework before the current revision’s check; B does not. |
| Join before close | Each A loop iteration joins analysis and check before exiting that iteration. | The outer parallel join requires the one check and the entire loop to finish before close. | B guarantees only that one check occurs before close, not before each intervening rework. |
| Approval versus check ordering | If approval is visible, it follows both analysis and check. | Approval follows analysis; the check may be delayed until after approval. | This creates additional B-only traces even with one analysis attempt. |

# 3. Verdicts

| View | Verdict | Confidence | Decisive reason | Caveat |
|---|---|---:|---|---|
| P1 operational compliance | not equivalent | High | Model A has one check per revision attempt; Model B has one check for the entire case and can rework before the check. | If the business rule were weakened to “at least one case-level check before close,” the view would become closer to P2. |
| P2 executive dashboard | equivalent only under stated abstraction | High | Both produce one or more analyses, at least one check, `n-1` reworks for `n` analyses, and fixed open/close boundaries. P2 hides approvals and check multiplicity/interleaving. | This does not imply that the models are operationally interchangeable. |
| P3 bounded testing | not equivalent | High | There are complete traces within 12 visible events and with at most three analyses that occur in only one model. | A bounded match would not prove unbounded equivalence. Here, a bounded mismatch is conclusive for P3. |

The strict visible languages are also incomparable:

\[
L_v(A)\nsubseteq L_v(B)
\]

because A can emit two checks for two revisions, while B cannot.

\[
L_v(B)\nsubseteq L_v(A)
\]

because B can emit two analyses with only one check, while A cannot.

# 4. Counterexample Traces

All traces below are complete visible traces. Silent `tau` choices are omitted.

| Trace ID | Trace | Model A | Model B | First decisive semantic difference | Relevant view |
|---|---|---:|---:|---|---|
| A-1 | `<Open Case, Analyze Revision, Check Revision, Rework Case, Analyze Revision, Check Revision, Close Case>` |  |  | Two revision attempts produce two checks. B has only one `Check Revision` branch. | P1, P3 |
| A-2 | `<Open Case, Check Revision, Analyze Revision, Approve Revision, Rework Case, Check Revision, Analyze Revision, Approve Revision, Close Case>` |  |  | A repeats the check inside each revision attempt; B cannot emit the second check. | P1, P3 |
| B-1 | `<Open Case, Check Revision, Analyze Revision, Rework Case, Analyze Revision, Close Case>` |  |  | Two analysis attempts occur, but there is only one check. A requires a check in the second revision block. | P1, P3 |
| B-2 | `<Open Case, Analyze Revision, Approve Revision, Rework Case, Analyze Revision, Check Revision, Close Case>` |  |  | B can postpone the sole check until after the first rework. In A, the first revision must be checked before rework. | P1, P3 |
| B-3 | `<Open Case, Analyze Revision, Approve Revision, Check Revision, Close Case>` |  |  | In B, the outer concurrent check can occur after approval. In A, visible approval can occur only after both analysis and check complete. | P1, P3 |

The first four witnesses contain two analysis attempts.

Optional approval matters because the `X('Approve Revision', tau)` branch is not merely cosmetic:

- Selecting `tau` hides approval, but leaves the check-scope difference intact.
- Selecting `Approve Revision` exposes an additional ordering difference.
- In A, approval follows the local analysis/check synchronization.
- In B, approval follows analysis, while the global check may be delayed.

Thus, hiding `tau` does not make the models equivalent. It only removes silent branch choices from the observed trace.

Under P2, traces A-1 and B-1 both abstract to:

```text
(Open Case, Close Case, 2 analyses, check occurred=True, rework occurred=True)
```

This demonstrates why the P2 conclusion depends on the declared abstraction.

# 5. Bounded Comparison Code

The following program performs exhaustive bounded state-space exploration for the P3 bounds:

- at most 12 visible events;
- at most three `Analyze Revision` occurrences;
- silent transitions are traversed but not appended to traces;
- acceptance requires equality with the final marking;
- repeated states are pruned only when both the marking and the observed trace are the same.

It does not use `pm4py.play_out(...)`; random playout is not exhaustive and cannot establish bounded language equality.

```python
import pm4py
from collections import deque
from pm4py.objects.petri_net import semantics as petri_semantics


TREE_A = """
->(
  'Open Case',
  *(
    ->(
      +('Analyze Revision', 'Check Revision'),
      X('Approve Revision', tau)
    ),
    'Rework Case'
  ),
  'Close Case'
)
"""

TREE_B = """
->(
  'Open Case',
  +(
    'Check Revision',
    *(
      ->(
        'Analyze Revision',
        X('Approve Revision', tau)
      ),
      'Rework Case'
    )
  ),
  'Close Case'
)
"""

MAX_VISIBLE_EVENTS = 12
MAX_ANALYSES = 3


def is_silent(label):
    """
    PM4Py normally represents a tau transition with label None.
    The string check also makes the code robust to parsers that retain 'tau'.
    """
    return label is None or label == "tau"


def marking_key(marking, place_index):
    """
    Canonical, hashable representation of a marking.
    The place index is fixed per net, so this remains stable during exploration.
    """
    return tuple(
        sorted(
            (place_index[place], int(tokens))
            for place, tokens in marking.items()
            if tokens != 0
        )
    )


def bounded_visible_language(net, initial_marking, final_marking,
                             max_visible=12, max_analyses=3):
    """
    Exhaustively enumerate complete visible traces within the stated bounds.

    State key includes:
      - current marking;
      - visible trace prefix;
      - number of Analyze Revision events.

    Including the trace prefix is important. Pruning only by marking could
    incorrectly discard a different visible history that reaches the same
    marking. Repeating the same marking with the same visible prefix is safe
    to prune because Petri-net future behavior depends on the marking.
    """
    place_index = {place: i for i, place in enumerate(net.places)}

    queue = deque()
    queue.append((initial_marking, tuple(), 0))

    seen = {
        (marking_key(initial_marking, place_index), tuple(), 0)
    }

    accepted_traces = set()

    while queue:
        marking, trace, analyze_count = queue.popleft()

        # A complete trace must end exactly in the accepting final marking.
        if marking == final_marking:
            accepted_traces.add(trace)
            continue

        enabled = pm4py.get_enabled_transitions(net, marking)

        for transition in sorted(
            enabled,
            key=lambda t: (str(t.label), str(t.name))
        ):
            label = transition.label
            next_trace = trace
            next_analyze_count = analyze_count

            if not is_silent(label):
                if len(trace) >= max_visible:
                    continue

                if label == "Analyze Revision":
                    if analyze_count >= max_analyses:
                        continue
                    next_analyze_count += 1

                next_trace = trace + (label,)

            next_marking = petri_semantics.execute(
                transition, net, marking
            )

            state_key = (
                marking_key(next_marking, place_index),
                next_trace,
                next_analyze_count
            )

            if state_key not in seen:
                seen.add(state_key)
                queue.append(
                    (next_marking, next_trace, next_analyze_count)
                )

    return accepted_traces


def print_trace_set(title, traces):
    print(f"\n{title}: {len(traces)} trace(s)")
    for trace in sorted(traces):
        print("  <" + ", ".join(trace) + ">")


# 1. Parse process trees.
tree_a = pm4py.parse_process_tree(TREE_A)
tree_b = pm4py.parse_process_tree(TREE_B)

# 2. Convert to accepting Petri nets.
net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)

# 3. Check soundness.
print("Soundness Model A:")
print(pm4py.check_soundness(net_a, im_a, fm_a, print_diagnostics=True))

print("\nSoundness Model B:")
print(pm4py.check_soundness(net_b, im_b, fm_b, print_diagnostics=True))

# 4. Exhaustively derive P3-bounded visible languages.
language_a = bounded_visible_language(
    net_a, im_a, fm_a,
    max_visible=MAX_VISIBLE_EVENTS,
    max_analyses=MAX_ANALYSES
)

language_b = bounded_visible_language(
    net_b, im_b, fm_b,
    max_visible=MAX_VISIBLE_EVENTS,
    max_analyses=MAX_ANALYSES
)

# 5. Compare bounded trace sets.
only_a = language_a - language_b
only_b = language_b - language_a
common = language_a & language_b

print(f"\nP3 bounded language size A: {len(language_a)}")
print(f"P3 bounded language size B: {len(language_b)}")
print(f"Common bounded traces: {len(common)}")

print_trace_set("Traces only in Model A", only_a)
print_trace_set("Traces only in Model B", only_b)

if language_a == language_b:
    print("\nResult: equal under the P3 bound only.")
else:
    print("\nResult: not equivalent under P3 bounded visible-language comparison.")

# This is exhaustive for the specified bounds and these accepting nets.
# It is not random playout. In contrast, pm4py.play_out(...) would be
# sampling-based unless its exploration method and coverage guarantees
# were separately established.
```

For these structured process trees, the exploration terminates under the stated bound because loop repetition requires visible loop-body behavior. A general Petri net with an unbounded silent cycle would require additional care, such as a proven finite reachability graph or an explicit silent-step policy.

# 6. Stochastic and Footprint Comparison

## Footprints

`pm4py.discover_footprints(...)` can compare aggregate behavioral relations such as:

- directly-follows relations;
- sequence relations;
- possible parallelism;
- possible choice behavior.

For example, it may expose that Model A has local analysis/check concurrency, while Model B exposes a check concurrent with a larger loop scope.

```python
import pm4py

# Assumes tree_a and tree_b were created as in Section 5.
footprints_a = pm4py.discover_footprints(tree_a)
footprints_b = pm4py.discover_footprints(tree_b)

print("Model A footprints:")
print(footprints_a)

print("\nModel B footprints:")
print(footprints_b)
```

Equal footprints would not establish trace equivalence because footprints generally abstract away:

- exact repetition counts;
- loop scope;
- the fact that Model A emits one check per iteration;
- the fact that Model B emits one check per case;
- long-range ordering constraints;
- approval placement.

Therefore, equal footprints would be weak evidence of similarity, not a proof of equivalence.

## Stochastic languages

A process tree does not inherently specify probabilities for:

- XOR branch selection;
- loop continuation;
- interleaving choices in parallelism.

Therefore, no probabilistic conclusion should be drawn unless a probability model is declared.

One possible explicitly declared comparison policy is:

> Assign equal mass to every distinct P3-bounded visible trace discovered by exhaustive enumeration.

This is not an operational probability model. It is a deliberately uniform distribution over the finite bounded language.

```python
import pm4py
from pm4py.objects.log.obj import EventLog, Trace, Event


def uniform_log_from_trace_set(trace_set):
    """
    Creates an event log with one occurrence of each trace.
    Consequently, get_stochastic_language() returns a uniform empirical
    distribution over the supplied trace set.
    """
    log = EventLog()

    for trace_labels in sorted(trace_set):
        trace = Trace()
        for label in trace_labels:
            trace.append(Event({"concept:name": label}))
        log.append(trace)

    return log


# language_a and language_b are the P3-bounded trace sets from Section 5.
uniform_log_a = uniform_log_from_trace_set(language_a)
uniform_log_b = uniform_log_from_trace_set(language_b)

stochastic_language_a = pm4py.get_stochastic_language(uniform_log_a)
stochastic_language_b = pm4py.get_stochastic_language(uniform_log_b)

print("Uniform bounded stochastic language A:")
print(stochastic_language_a)

print("\nUniform bounded stochastic language B:")
print(stochastic_language_b)

emd = pm4py.compute_emd(
    stochastic_language_a,
    stochastic_language_b
)

print("\nEarth Mover's Distance over the declared bounded distributions:")
print(emd)
```

Alternatively, empirical event logs collected from real operations can be passed to `get_stochastic_language(...)`. In that case, the output represents observed relative frequencies, not all behavior allowed by the model.

## Earth Mover’s Distance

A low EMD can provide evidence that two declared probability distributions are behaviorally close under the selected distance metric. It does not establish trace equivalence because:

- rare but valid counterexample traces may have low probability;
- the distributions may be based on finite samples;
- the comparison may be bounded;
- different supports can still have low transport cost;
- EMD depends on the trace-distance metric and weighting policy.

Thus:

- equal footprints do not imply equal trace languages;
- low EMD does not imply equal trace languages;
- even EMD zero over a sampled or bounded distribution does not prove unbounded semantic equivalence.

# 7. Complexity Comparison

The following counts use these conventions:

- root depth is 0;
- node count includes operator nodes and leaf nodes;
- `tau` is a silent leaf;
- static duplicate-label count means duplicate labels among syntactic visible leaves, not repeated runtime executions caused by a loop.

| Metric | Model A | Model B | Comparison |
|---|---:|---:|---|
| Process-tree nodes | 12 | 12 | Equal static node count. |
| Operator nodes | 5 | 5 | Equal number of process-tree operators. |
| Maximum depth | 4 | 5 | B is structurally deeper because the loop is nested under the outer parallel operator. |
| Visible leaves | 6 | 6 | Equal visible activity vocabulary. |
| Silent leaves | 1 | 1 | Each has one `tau` branch for auto-approval. |
| Distinct visible labels | 6 | 6 | Equal. |
| Static duplicate-label types | 0 | 0 | Neither tree repeats a visible label as separate syntactic leaves. |
| Extra duplicate visible leaves | 0 | 0 | Runtime repetition is caused by the loop, not duplicated static leaves. |
| Dynamic check count | One per revision; unbounded | Exactly one | Major semantic difference not visible in static leaf counts. |

The exact process-tree counts follow directly from the tree syntax.

Model A operators are:

```text
->, *, ->, +, X
```

Model B operators are:

```text
->, +, *, ->, X
```

The following code calculates these counts and compares the converted Petri-net simplicity metric.

```python
import pm4py
from collections import Counter


def tree_statistics(node, depth=0):
    children = list(getattr(node, "children", []) or [])

    stats = {
        "nodes": 1,
        "operators": 0,
        "max_depth": depth,
        "visible_leaves": 0,
        "silent_leaves": 0,
        "visible_labels": Counter()
    }

    if not children:
        label = getattr(node, "label", None)

        if label is None or label == "tau":
            stats["silent_leaves"] = 1
        else:
            stats["visible_leaves"] = 1
            stats["visible_labels"][label] += 1

        return stats

    stats["operators"] = 1

    for child in children:
        child_stats = tree_statistics(child, depth + 1)

        stats["nodes"] += child_stats["nodes"]
        stats["operators"] += child_stats["operators"]
        stats["max_depth"] = max(
            stats["max_depth"],
            child_stats["max_depth"]
        )
        stats["visible_leaves"] += child_stats["visible_leaves"]
        stats["silent_leaves"] += child_stats["silent_leaves"]
        stats["visible_labels"].update(child_stats["visible_labels"])

    return stats


def summarize_tree(name, tree):
    stats = tree_statistics(tree)

    duplicate_label_types = sum(
        1 for count in stats["visible_labels"].values() if count > 1
    )
    extra_duplicate_leaves = sum(
        count - 1 for count in stats["visible_labels"].values() if count > 1
    )

    print(f"\n{name}")
    print("nodes:", stats["nodes"])
    print("operators:", stats["operators"])
    print("maximum depth:", stats["max_depth"])
    print("visible leaves:", stats["visible_leaves"])
    print("silent leaves:", stats["silent_leaves"])
    print("visible label counts:", dict(stats["visible_labels"]))
    print("duplicate-label types:", duplicate_label_types)
    print("extra duplicate leaves:", extra_duplicate_leaves)


# Assumes tree_a, tree_b, net_a, im_a, fm_a, net_b, im_b, fm_b exist.
summarize_tree("Model A tree statistics", tree_a)
summarize_tree("Model B tree statistics", tree_b)

print("\nConverted Petri-net sizes:")
print("A places:", len(net_a.places), "transitions:", len(net_a.transitions))
print("B places:", len(net_b.places), "transitions:", len(net_b.transitions))

print("\nPM4Py Petri-net simplicity:")
print("A:", pm4py.simplicity_petri_net(net_a, im_a, fm_a))
print("B:", pm4py.simplicity_petri_net(net_b, im_b, fm_b))
```

No exact `simplicity_petri_net(...)` value is stated here because it depends on the PM4Py conversion and metric implementation version. It should be computed from the generated nets rather than inferred from the tree syntax alone.

# 8. Simplified Model

The most appropriate target for simplification is P2, the executive dashboard view. P2 explicitly hides:

- approval occurrences;
- silent behavior;
- repeated check multiplicity;
- exact analysis/check interleavings.

A P1-preserving simplification would need to retain one check per revision and approval placement, which leaves little room to simplify Model A without weakening its operational behavior.

## Compact dashboard process tree

```text
->(
  'Open Case',
  *(
    'Analyze Revision',
    'Rework Case'
  ),
  'Check Revision',
  'Close Case'
)
```

This model means:

```text
Open Case,
Analyze Revision,
zero or more repetitions of (Rework Case, Analyze Revision),
Check Revision,
Close Case
```

For \(n \geq 1\), it produces:

- exactly \(n\) analyses;
- exactly \(n-1\) reworks;
- exactly one check;
- open first and close last.

It has the same P2 abstraction as both original models:

\[
(\text{Open Case},\text{Close Case},n,\text{true},[n>1])
\]

## PM4Py code

```python
import pm4py

SIMPLIFIED_TREE = """
->(
  'Open Case',
  *(
    'Analyze Revision',
    'Rework Case'
  ),
  'Check Revision',
  'Close Case'
)
"""

simplified_model = pm4py.parse_process_tree(SIMPLIFIED_TREE)

simplified_net, simplified_im, simplified_fm = (
    pm4py.convert_to_petri_net(simplified_model)
)

print(
    pm4py.check_soundness(
        simplified_net,
        simplified_im,
        simplified_fm,
        print_diagnostics=True
    )
)
```

## Structural comparison

| Model | Tree nodes | Operator nodes | Visible leaves | Silent leaves | Maximum depth |
|---|---:|---:|---:|---:|---:|
| Model A | 12 | 5 | 6 | 1 | 4 |
| Model B | 12 | 5 | 6 | 1 | 5 |
| Simplified P2 model | 7 | 2 | 5 | 0 | 2 |

The simplified model is structurally smaller than both originals:

- five fewer nodes;
- three fewer operators;
- no silent auto-approval branch;
- no parallel operator;
- no approval activity;
- no nested local/global check structure.

## Preservation table

| Property | Status | Reason |
|---|---|---|
| `Open Case` first | exact | The simplified model starts with `Open Case`. |
| `Close Case` last | exact | The simplified model ends with `Close Case`. |
| At least one analysis | exact | Binary-loop semantics execute the first child at least once. |
| Number of analyses | exact under P2 | The loop produces any positive number of analyses. |
| Whether rework occurred | exact under P2 | Rework occurs iff there is more than one analysis. |
| At least one check occurred | exact under P2 | The model contains one mandatory check. |
| Check count | abstracted/lost | The simplified model always has one check; Model A may have many. |
| Check placement | abstracted/lost | The simplified check occurs after the loop; P2 ignores interleaving. |
| Approval visibility and count | lost intentionally | P2 explicitly hides approvals. |
| P1 one-check-per-revision rule | lost | For multiple revisions, the simplified model has only one check. |
| Strict visible trace equivalence | lost | It removes approvals and changes check placement. |
| P3 bounded-language equivalence | lost | P3 retains all visible labels and ordering, so the model is not a P3 replacement. |

## Regression traces

The following are accepted complete visible traces of the simplified model.

| ID | Trace | Expected result |
|---|---|---|
| R-1 | `<Open Case, Analyze Revision, Check Revision, Close Case>` | Accept |
| R-2 | `<Open Case, Analyze Revision, Rework Case, Analyze Revision, Check Revision, Close Case>` | Accept |
| R-3 | `<Open Case, Analyze Revision, Rework Case, Analyze Revision, Rework Case, Analyze Revision, Check Revision, Close Case>` | Accept |

The following are negative traces for the simplified model.

| ID | Trace | Why rejected |
|---|---|---|
| N-1 | `<Open Case, Check Revision, Analyze Revision, Close Case>` | The simplified model fixes the check after the loop; it does not permit check-before-analysis. |
| N-2 | `<Open Case, Analyze Revision, Rework Case, Check Revision, Close Case>` | After rework, the binary loop must execute another analysis before it may exit. |

N-1 is intentionally rejected despite being possible in Model B, because P2 ignores the exact check/analysis ordering.

# 9. Final Recommendation

- **P1 operational compliance:** Use **Model A**. It enforces one check for every revision attempt before the next rework or close. Model B is unsuitable because it admits multiple revisions with only one case-level check.

- **P2 executive dashboard:** Either original model can be used only after applying the stated dashboard abstraction. The simplified P2 model is preferable as a dedicated dashboard-level model because it is substantially smaller and preserves exactly the dashboard facts: analysis count, whether rework occurred, and whether at least one check occurred.

- **P3 bounded testing:** Models A and B are not equivalent. They should be tested separately. The simplified P2 model must not replace either original model for P3 because it removes approvals and changes visible ordering and check multiplicity.

The simplified model should therefore replace neither original model as an operational source model. It is suitable only as a deliberately abstract dashboard representation.

Finally, bounded comparison has a strict limit: equality within the P3 bounds would not prove unbounded equivalence. In this case, however, the bounded counterexamples already prove P3 non-equivalence, and the loop-scope reasoning proves that the models also differ unboundedly.
