# 1. Assumptions and Interpretation

1. The low-risk/high-risk choice is represented as a non-deterministic XOR choice after `Analyze Root Cause`. The low-risk branch contains only `Supervisor Review`; the high-risk branch contains a concurrent `Quality Review` and `Regulatory Review`. No data condition is encoded because the model is control-flow only.
2. The optional supplier consultation is represented by an XOR with two branches: a silent skip branch and a `Consult Supplier` branch. The silent branch makes “not selected” visible as an invisible tau transition. The selected/data condition is not represented.
3. A passing inspection is abstracted by the loop structure itself: the loop body is `Execute Trial -> Inspect Trial`, and `Adjust Parameters` is the redo branch. A trace that exits the loop after `Inspect Trial` is understood as the passing iteration; a trace that performs `Adjust Parameters` and repeats is understood as a failed iteration. Because the actual inspection result is not an event label, the model cannot enforce pass/fail data, so the redo/exit choice is abstracted as nondeterminism.
4. Duplicate visible labels are not used in either model. All visible labels are unique in the process tree and in the POWL model, so duplicate-label ambiguity is avoided.
5. The process-tree approximation policy is a conservative under-approximation. It excludes some intended interleavings—especially the overlap of approvals/supplier consultation with the trial cycle—because that overlap is not block-structured. It does not intentionally admit traces that violate the stated precedence and synchronization rules.
6. “May overlap” is interpreted as true concurrency in the POWL model: two nodes with no partial-order path between them may be interleaved freely. In the process tree, overlap is captured only inside explicit `parallel` constructs; elsewhere the tree serializes work even when the narrative would allow concurrency.

# 3. PM4Py Process-Tree Model

## 3.1 Compact process-tree expression

```text
-> (
  'Register Deviation',
  + (
    -> ( 'Contain Material', 'Plan Verification' ),
    -> ( 'Analyze Root Cause', 'Design Corrective Action' )
  ),
  X (
    'Supervisor Review',
    + ( 'Quality Review', 'Regulatory Review' )
  ),
  X ( 'Consult Supplier', tau ),
  * (
    -> ( 'Execute Trial', 'Inspect Trial' ),
    'Adjust Parameters'
  ),
  'Release Material',
  'Archive Case'
)
```

## 3.2 Self-contained Python code

```python
import pm4py

process_tree_string = (
    "->('Register Deviation',"
    "+(->('Contain Material','Plan Verification'),"
    "->('Analyze Root Cause','Design Corrective Action')),"
    "X('Supervisor Review',+('Quality Review','Regulatory Review')),"
    "X('Consult Supplier',tau),"
    "*(->('Execute Trial','Inspect Trial'),'Adjust Parameters'),"
    "'Release Material','Archive Case')"
)

tree = pm4py.parse_process_tree(process_tree_string)
```

The parser builds all parent/child links internally, so no manual parent assignment is needed. The expression maps to the narrative as follows:

- The root sequence starts with `Register Deviation` and ends with `Release Material -> Archive Case`.
- The first `+` is the two independent streams after registration: `Contain Material -> Plan Verification` and `Analyze Root Cause -> Design Corrective Action`.
- The first `X` is the risk route: low risk is `Supervisor Review`; high risk is the parallel `+` of `Quality Review` and `Regulatory Review`.
- The second `X` is the optional supplier consultation: either `Consult Supplier` or silent `tau`.
- The `*` loop is the trial cycle: `Execute Trial -> Inspect Trial`, with `Adjust Parameters` as the redo branch.

## 3.3 Faithfulness limitations of the process tree

The process tree is an under-approximation. It cannot represent the non-block-structured overlap between the approval route, the supplier consultation, and the trial cycle. In the tree, `risk choice`, then `supplier choice`, then `trial loop` are serialized. Therefore:

- The selected approval route is forced to complete before `Execute Trial`, even though the narrative permits it to overlap the trial.
- Supplier consultation is forced to complete before the trial, even though it may overlap design, approvals, and trial work.
- The risk route is delayed until after `Plan Verification` and `Design Corrective Action` join, even though it should be selectable after `Analyze Root Cause`.
- The pass/fail condition is not visible, so the loop cannot condition `Adjust Parameters` on an actual failed inspection; it can only use the loop redo as an abstraction of failure.

# 4. PM4Py POWL Model

## 4.1 Compact POWL description

```text
Root = SPO(
  Register, Contain, Analyze, Plan, Design,
  RiskChoice, SupplierChoice, TrialLoop, Release, Archive
)

Edges:
  Register -> Contain
  Register -> Analyze
  Contain  -> Plan
  Analyze  -> Design
  Analyze  -> RiskChoice
  Analyze  -> SupplierChoice
  Plan     -> TrialLoop
  Design   -> TrialLoop
  TrialLoop -> Release
  RiskChoice -> Release
  SupplierChoice -> Release
  Release  -> Archive

RiskChoice = XOR(
  SupervisorReview,
  SPO(QualityReview, RegulatoryReview)   # no edge between the two reviews
)

SupplierChoice = XOR(tau, ConsultSupplier)

TrialLoop = LOOP(
  SPO(ExecuteTrial, InspectTrial),       # edge: ExecuteTrial -> InspectTrial
  AdjustParameters
)
```

## 4.2 Self-contained Python code

```python
import pm4py
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Visible transitions
register = Transition("Register Deviation")
contain = Transition("Contain Material")
analyze = Transition("Analyze Root Cause")
plan = Transition("Plan Verification")
design = Transition("Design Corrective Action")
supervisor = Transition("Supervisor Review")
quality = Transition("Quality Review")
regulatory = Transition("Regulatory Review")
consult = Transition("Consult Supplier")
execute = Transition("Execute Trial")
inspect = Transition("Inspect Trial")
adjust = Transition("Adjust Parameters")
release = Transition("Release Material")
archive = Transition("Archive Case")

# Low-risk branch: only Supervisor Review
low_branch = supervisor

# High-risk branch: Quality Review and Regulatory Review are concurrent
high_branch = StrictPartialOrder(nodes=[quality, regulatory])

risk_choice = OperatorPOWL(
    operator=Operator.XOR,
    children=[low_branch, high_branch]
)

# Optional supplier consultation
supplier_choice = OperatorPOWL(
    operator=Operator.XOR,
    children=[SilentTransition(), consult]
)

# Trial cycle: Execute Trial before Inspect Trial
cycle = StrictPartialOrder(nodes=[execute, inspect])
cycle.order.add_edge(execute, inspect)

trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[cycle, adjust]
)

# Root partial order
powl = StrictPartialOrder(nodes=[
    register, contain, analyze, plan, design,
    risk_choice, supplier_choice, trial_loop, release, archive
])

# Required precedence edges
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)

powl.order.add_edge(analyze, risk_choice)
powl.order.add_edge(analyze, supplier_choice)

powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

powl.order.add_edge(trial_loop, release)
powl.order.add_edge(risk_choice, release)
powl.order.add_edge(supplier_choice, release)

powl.order.add_edge(release, archive)
```

## 4.3 Why unconnected nodes may remain concurrent

In `StrictPartialOrder`, two nodes are concurrent exactly when there is no directed path between them. For example:

- `Plan Verification` and `Design Corrective Action` are not connected by an edge; they can happen while the two initial work streams are still interleaving.
- `RiskChoice` and `TrialLoop` are not connected; therefore approval work may overlap the trial cycle.
- `SupplierChoice` and `TrialLoop` are not connected; supplier consultation may overlap trial work as long as it completes before release.
- `Quality Review` and `Regulatory Review` are placed in the same high-risk branch with no edge between them, so they are concurrent and may finish in either order.
- `Plan` and `Design` are connected to `TrialLoop` only through incoming edges, so both must complete before the trial starts, but they do not need to be serialized with respect to each other.

# 7. Preferred Representation and Validation Plan

The preferred canonical representation is the **POWL model**, because it expresses the cross-branch dependencies directly as partial-order edges. In particular, `Plan Verification -> TrialLoop`, `Design Corrective Action -> TrialLoop`, and the separate `RiskChoice -> Release`, `SupplierChoice -> Release`, and `TrialLoop -> Release` joins are all explicit without duplicating activities. The process tree is useful as a conservative fallback for tools that require tree-structured models, but it overconstrains the intended concurrency.

Validation plan:

1. **Petri net conversion**: Convert the POWL model to a Petri net using `pm4py.convert_to_petri_net(powl)` where supported. If the installed PM4Py version does not support POWL conversion directly, use the process tree as an additional conversion source and compare the two nets.
2. **Soundness checking**: Apply `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` to the converted net. Check for dead transitions, missing final marking, and improper termination.
3. **Bounded or sampled playout**: Use `pm4py.play_out(powl, max_trace_length=...)` to sample many traces. For each sampled trace, assert:
   - it starts with `Register Deviation`;
   - it ends with `Archive Case`;
   - `Release Material` appears exactly once and immediately before `Archive Case`;
   - `Consult Supplier`, if present, appears at most once and before `Release Material`;
   - `Adjust Parameters` appears only between `Inspect Trial` and another `Execute Trial`.
4. **Positive and negative trace tests**: Replay traces A1–A5 as accepted witnesses and F1–F3 as rejected witnesses. Use token-based replay or alignment where available. A positive trace should have full fitness; a negative trace should be rejected by a fitness/alignment check.
5. **Silent/duplicate label check**: Inspect the converted net for silent transitions. There should be one silent skip in the optional supplier XOR. No visible label should appear on more than one transition, so duplicate-label ambiguity is avoided.
6. **Limitations of the validation plan**: The actual pass/fail condition of `Inspect Trial` is not encoded, so the validation cannot distinguish a failed inspection from a passed inspection at the event-label level. Also, if PM4Py’s POWL-to-Petri-net conversion has version-specific limitations, the validation may need to rely on the process tree for some checks.

# 8. Final Self-Critique

1. The process-tree model is an under-approximation and is not language-equivalent to the intended behavior. If it is accidentally used as the canonical model, it may under-report concurrency and overstate serialization between approvals, supplier consultation, and trial work.
2. Both models abstract the inspection result as loop nondeterminism. Consequently, the model can execute `Adjust Parameters` after an inspection that would be considered “passing” in the real data, and it can exit the loop after an inspection that would be considered “failed.” This is a semantic limitation inherent to omitting data conditions.
3. The POWL model uses a nested `OperatorPOWL` inside a `StrictPartialOrder`. Composite nodes in partial orders can be sensitive to tool-specific replay semantics, so the validation should include a direct Petri-net conversion check; otherwise, a valid-looking partial order could still be misinterpreted by a particular PM4Py version.
