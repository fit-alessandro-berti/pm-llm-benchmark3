## 1. Target definition

The primary target should be an all-application, process-aware competing-outcome target, not a binary default label assigned to every application. Let (i) denote an application episode and let (	au_i) be a prespecified landmark after the first few observed, pre-decision events. I would use the first three eligible events as the main landmark and retain a short-prefix variant for applications that reach a terminal route sooner. The prefix must end strictly before Accept, Reject, Withdraw, Transfer, Contract Signed, or Account Activated; a terminal event itself is a future outcome, not a feature.

For a fixed prediction horizon (H=180) days after (	au_i), define the state at that horizon, or the first absorbing transition before it, as one of:

- `rejected`, `withdrawn`, or `transferred`, according to the first such process transition;
- `activated_default90`, when activation occurs and a default occurs within 90 days after activation;
- `activated_survived90`, when activation occurs and the account reaches activation plus 90 days without a default, with the outcome feed mature;
- `no_qualifying_event_by_H`, only when follow-up is actually observed through (	au_i+H).

The last state is a process state at the horizon, not a claim that the application would not default. If follow-up ends before (H), the observation is right-censored instead. The primary estimand is the vector of state probabilities, equivalently the cumulative incidence of each cause by (H), conditional on the event-time prefix (X_i(	au_i)), under the lender's observed policy:

\[
  P\{Z_i(H)=z\mid X_i(\tau_i),\text{current policy}\}.
\]

The unit is one application episode. A transferred case is linked to a partner episode when the linkage table supports a defensible match; the original transfer remains the first process outcome. The default component uses the warehouse definition—default within 90 days after Account Activated—not default within 90 days of application start. The feed-arrival timestamp is an observation clock, not the default event time.

This formulation is operationally useful because it predicts what can happen to every application under the current process and exposes approval, withdrawal, and transfer as competing outcomes. It does not turn an unactivated case into an artificial non-default. It can be implemented with cause-specific hazards and cumulative-incidence estimates, with a separate transition from activation to default or survival at 90 days.

A credible alternative is the conditional activated-account target

\[
Y_i=1\{\text{default within 90 days of activation}\},\qquad A_i=1,
\]

using only eventually activated cases whose labels are mature. Its estimand is (P(Y_i=1mid X_i(	au_i),A_i=1)), not the default risk of a randomly selected applicant. It is appropriate for portfolio monitoring or for ranking accounts after the activation policy has selected them, but it is subject to selection and collider effects when used for all applicants. A policy-specific quantity such as (P(Y_i^{A=1}=1mid X_i)) for a rejected application is a counterfactual and requires substantially stronger assumptions; it should not be reported as observed default risk.

## 2. Cohort construction

I would define an application episode from the start event through the first lender terminal route, activation, or administrative end. The transfer linkage table may add a partner episode to the same analytical identity, but it must not silently manufacture a match. Exact duplicate event rows can be removed after an auditable deduplication step; ambiguous same-time events should be retained or treated as tied, with a sensitivity analysis.

For every prediction landmark, use only event rows with event timestamp at or before the landmark. For cohort assembly at the extraction cutoff, use events observed by 15 February 2026 and labels whose `label_available_at` is at or before that cutoff. A 90-day label is considered conservatively mature only after activation + 90 days + a 35-day maximum feed-delay buffer, unless the outcome feed has an explicitly documented earlier maturity guarantee. `data_extract_time` describes the snapshot and is not a prediction-time feature.

The supplied snapshot reconciles as follows. The transfer linkage split is approximate (60% of 2,900); the total transfer row is still exactly 2,900.

| Application disposition at the cutoff | Count | Primary treatment |
|---|---:|---|
| Activated, mature `default_90d=0` | 18,900 | Observed `activated_survived90` outcome |
| Activated, mature `default_90d=1` | 2,700 | Observed `activated_default90` outcome |
| Activated, outcome not mature or delayed/missing | 3,600 | Censored or selectively unobserved; never label as non-default |
| Rejected | 9,100 | Observed competing process outcome |
| Withdrawn | 5,700 | Observed competing process outcome |
| Transferred, linkage available (about 60%) | about 1,740 | Observed transfer cause; partner follow-up may be used only when linked and as-of valid |
| Transferred, linkage unavailable (about 40%) | about 1,160 | Observed transfer cause, but selectively unobserved partner follow-up |
| Still open | 5,100 | Ongoing/right-censored; not an outcome label |
| **Total** | **48,000** | |

Thus the 21,600-row labeled export is only the first two rows, and its 18,900 “non-defaults” are conditional survivors among activated accounts. The 3,600 activated-but-immature cases remain in the risk set for survival or competing-risk analysis when their follow-up is otherwise observable, but they cannot contribute a mature binary default endpoint. Rejected, withdrawn, and open cases are not assigned zero.

The inclusion rule is a valid application start in the 2024-01-01 through 2025-12-31 window, with a case identifier and a usable event timestamp. Exclude only records that fail those data-integrity requirements, and report their count separately. For a fixed three-event prefix analysis, cases that terminate before three pre-decision events are not silently removed from the overall cohort: they are included through the short-prefix protocol or analyzed separately as early-route cases. For a fully mature binary activated analysis, include only activated accounts with a mature, observed label and explicitly report the resulting selected cohort.

## 3. Censoring and missing-label strategy

These mechanisms need separate treatment.

- Ordinary right censoring occurs when an application has not reached a qualifying transition by the end of observed follow-up, or when a case is open at extraction. Censor at the last valid observation or administrative cutoff; do not call it non-default.
- Delayed labels occur when activation + 90 days has passed but the external feed has not arrived. Keep an outcome-maturity clock and an event clock. A label is usable for evaluation only if `label_available_at` is no later than the evaluation as-of date.
- Activation is a selection mechanism. Default is only observed after the institution's accept-and-activate path. Conditioning on (A=1) estimates a selected population and can induce bias because the decision depends on prefix variables and unobserved risk. It is not repaired by class weighting alone.
- Transfer is a competing process outcome for lender-originated activation/default. If the estimand instead concerns partner default, transfer is a loss-to-follow-up mechanism unless the new identifier is linked. The 60% linkage rate and its dependence on source, channel, date, or risk are evidence of informative observation, not ordinary independent censoring.
- A permanently missing partner outcome feed is neither zero nor a routine right-censored non-default. Its missingness mechanism may depend on partner, source system, or latent risk.

The primary analysis would fit cause-specific transition models from the prefix state and use an Aalen-Johansen-style cumulative-incidence calculation (or an equivalent competing-risk estimator) for the all-application state probabilities. For activated accounts, the 90-day transition is entered only when the label has matured. Cases with missing or delayed feeds are censored at the last defensible follow-up and receive inverse-probability-of-censoring weights estimated from information available at the prefix: source, partner, transfer linkage, channel, region, policy era, migration era, amount, risk score, process path, and observed follow-up. Standard errors should be clustered by application episode and uncertainty from the censoring model should be propagated.

As a sensitivity analysis, report all of the following separately: complete mature-label analysis; IPCW under missing-at-random conditional on observed prefix and source variables; and an MNAR tipping-point or bounds analysis that assigns the missing activated/partner outcomes default rates shifted by a prespecified delta relative to observed comparable accounts. Also repeat the analysis treating transfer as censoring rather than as a competing cause, and treating it as an absorbing competing cause. If conclusions change materially, the study should not present a single precise default estimate.

The existence of a transfer, the activation date, the feed-arrival date, and observed covariates are testable. Label maturity and missingness patterns are partially testable by source, time, and observed process history. Conditional independent censoring, the outcome of an unlinked partner account, and any default potential outcome for a rejected or withdrawn application are fundamentally untestable from this export. Those assumptions must be stated rather than hidden in a binary label.

## 4. Prefix extraction

All timestamps should be normalized to UTC and events sorted by case, timestamp, and a stable ingestion sequence. The migration activity dictionary must be versioned and applied before prefix construction. Exact duplicate rows can be removed; non-identical duplicate candidates created by the migration should be flagged and investigated, not blindly collapsed.

For an event-count landmark, use (K=3) as the preregistered “first few events” choice, with (K=5) as a sensitivity analysis. Take the first (K) information-bearing events strictly before a decision/activation event. Preserve repeated document-request and credit-review events: a loop is information about the process, not noise to be reduced to one activity. If a case reaches Reject, Withdraw, Transfer, or Accept before (K), construct a shorter prefix immediately before that terminal decision for the early-route analysis, and include its length as a feature. Do not use the terminal event itself. A fixed-(K) score should also be reported on the subset that actually reaches (K), so performance is not confused with short-case coverage.

For an elapsed-time landmark, use all events with timestamp no later than `application_start + 7 days`, again stopping at the first terminal/activation decision. If the case terminates before seven days, it leaves the active risk set at that event; post-terminal events are never backfilled into its seven-day prefix. Report both landmark types because event-count and elapsed-time prefixes answer different operational questions. Multiple dynamic landmarks per case require case-clustered uncertainty and a clear rule for whether decisions are made once or repeatedly.

A same-timestamp tie without an event sequence cannot be given a defensible causal order. Treat tied events as simultaneous, use a stable raw-row order only for an engineering convention, and exclude ambiguous ties in a sensitivity analysis. For `documents_total`, use document-upload events with their actual timestamps and a strict `< prediction_time` rule; do not use a nightly snapshot that can include later uploads from the same calendar day. Activity renaming must be based on a predeclared migration map, not on the future outcome.

## 5. Process-aware features

Static case attributes, copied from the first valid application event, include channel, region, requested amount, source system, and a coarse application-start calendar bucket. These are not outcome labels and should be frozen at their event-time values.

Prefix-derived features include:

- current activity and current process state; counts of each activity and transition; elapsed time since start; time since the preceding event; median and maximum inter-event gaps;
- counts of document requests, document receipts, and Credit Review visits; number of returns to Credit Review; repeated-activity and rework indicators; number of distinct activities and resources;
- resource currently handling the prefix, resource handoff count, and a queue/wait proxy based on observed inter-event times;
- the latest `risk_score` whose update timestamp is at or before the prefix, plus a missingness flag, never the value from the completed case;
- start month/week, day-of-week and hour where permitted, policy era (pre/post 1 July 2025), migration era (pre/post 15 October 2025), and interactions with channel, region, and source.

Historical-reference features can include resource workload in the preceding 30 days, empirical activity/transition rates estimated from training history only, and time-versioned employee experience as of the event. They require a point-in-time historical table or a point-in-time join. Extraction-time employee experience is not a valid substitute. DFGs and variants are useful for process diagnostics and drift monitoring; they should be learned on the training period and not treated as magically causal features.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final decision and therefore reveals the decision path | Usable only if a separate, timestamped limit genuinely existed before the landmark | Drop | The supplied field is post-decision |
| `decision_reason` | Written at or after Accept/Reject and directly reveals a competing outcome | Never use for a prefix before the decision | Drop | It is a label proxy and selection artifact |
| `collection_status` | Updated after activation and may directly encode default or collections activity | Use only in a separate post-activation monitoring model, never in the application-prefix model | Drop | It leaks the outcome and activation |
| Future events (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`) | Future process steps expose acceptance, exposure, collections, or default | Filter event timestamp/sequence to the strict prefix boundary; future events are labels or censoring evidence only | Drop from (X); retain for outcome construction | A target event cannot also be a predictor |
| `documents_total` nightly snapshot | Can include uploads later on the same calendar day than the nominal prediction time | Replace with timestamped uploads strictly before the landmark, or omit | Repair or drop | Calendar-day snapshots violate the as-of rule |
| Updated `risk_score` | A current case value may contain a later recalculation | Use the last value whose update event is at or before the prefix, with missingness flagged | Repair | Risk score is valid only as a point-in-time value |
| Resource experience | Stored at extraction time, so it includes experience accumulated after the prediction | Join a versioned employee-history table as of the event, or use only resource identity/counts | Repair or drop | Extraction-time attributes leak calendar time and future information |
| `default_90d` | Repeated on later events when known; the nonmissing value is the target | Never use as a feature; use only for a mature outcome as of the evaluation cutoff | Drop from (X) | It is direct target leakage |
| `label_available_at` | Encodes when a label arrived and can select older/easier cases | Use only to gate outcome availability in an as-of evaluation | Drop from (X) | Availability metadata is not applicant information |
| `data_extract_time` | A common snapshot timestamp can make recency and maturity look predictive | Use to define the analysis cutoff, not as a feature | Drop from (X) | It is administrative metadata |

## 7. Validation design

The primary split is by application start time, never by randomly distributing events or prefixes across folds. A concrete locked backtest is:

- training: starts from 1 January 2024 through 31 December 2024;
- validation/tuning: starts from 1 January 2025 through 30 June 2025;
- locked test: starts from 1 July 2025 through 31 December 2025.

The locked test therefore measures the post-policy population. It must be reported in two subperiods, 1 July–14 October and 15 October–31 December, to expose migration effects. A rolling-origin supplement can refit at each month or quarter and predict the next period. At every origin, features are frozen at their prefix timestamp, and a label is eligible only if it would have been available by that origin plus the prespecified evaluation lag. Recent test cases remain censored rather than being discarded as convenient negatives.

For the competing-outcome target, report time-dependent cumulative-incidence calibration at 30, 90, and 180 days, cause-specific Brier scores and integrated Brier scores with IPCW, calibration intercept/slope and reliability curves for each cause, and cause-specific time-dependent AUC or concordance. Because default is relatively uncommon, include AUPRC for `activated_default90`, but do not use it alone. For a conditional activated model, report the same survival-aware Brier/AUC measures on the mature activated risk set and clearly label the estimand. State-probability forecasts should be checked for coherence (nonnegative probabilities summing to at most one at each horizon).

Use bootstrap confidence intervals clustered by application and preferably repeat the test over several temporal origins. Report calibration and discrimination by policy era, migration era, channel, region, source system, amount band, partner/transfer-linkage status, and relevant resource strata, with uncertainty and minimum-cell rules. Compare prefix activity distributions, variant frequencies, event counts, risk-score distributions, acceptance/transfer rates, and missing-feed rates across periods using appropriate drift summaries such as PSI, standardized differences, or distributional tests.

A random case split can put near-duplicate migration events, the same policy regime, and cases with different label maturity into both train and test. It also permits later-period process patterns and outcome-availability patterns to influence training, and can make a model look calibrated on the historical selection mechanism while failing after the threshold change. Temporal validation preserves the deployment direction of time and makes maturity and drift visible.

## 8. Limitations and decision-use boundary

The study can estimate predictive association and, under stated censoring assumptions, the distribution of process outcomes under the observed lender policy. It can estimate default among mature activated accounts and the observed-policy probability that an application reaches an activated-default state. It cannot claim that a rejected application is a non-default, that the model has learned intrinsic borrower default risk independent of approval, or that a rejected applicant would default if activated. The latter is a counterfactual policy question requiring assumptions about unobserved outcomes and treatment effects.

Unlinked transfers and permanently missing partner feeds limit identification. The observed 90-day label may also be delayed, revised, or defined differently across source systems. Application episodes can be correlated after transfer linkage, and a data-quality correction can change apparent process timing. These limitations should be included in model cards and in any decision threshold review.

Deployment can change the data-generating process in several ways: (1) a new threshold or a model-driven approval rule changes who is activated and therefore who can generate default labels; (2) applicants and staff adapt their behavior, document timing, or channel choice in response to decisions; (3) staffing and queue changes alter waiting times, resource assignments, and the meaning of rework features; (4) a new migration or partner integration changes activity names, identifier linkage, and feed completeness; and (5) collections interventions can prevent or delay defaults, changing the outcome that the model was trained to predict. Monitoring must therefore include process, selection, label availability, calibration, and subgroup drift—not only aggregate AUC.

## 9. PM4Py-oriented Python implementation skeleton

```python
from pathlib import Path
import numpy as np
import pandas as pd
import pm4py

CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"
RESOURCE, CHANNEL, REGION = "org:resource", "case:channel", "case:region"
AMOUNT, RISK = "case:requested_amount", "risk_score"
DEFAULT, LABEL_AT = "default_90d", "label_available_at"
EXTRACT_AT = "data_extract_time"
CUTOFF = pd.Timestamp("2026-02-15", tz="UTC")
K, H_DAYS, FEED_LAG_DAYS = 3, 180, 35

# This map must come from the migration data dictionary, not from outcomes.
ACTIVITY_RENAME = {
    # "Identity_KYC_Check_v2": "Identity/KYC Check",
    # "Credit_Review_v2": "Credit Review",
}
DECISIONS = {"Accepted", "Rejected", "Withdrawn", "Transferred",
            "Contract Signed", "Account Activated"}
ROUTES = {"Rejected": "rejected", "Withdrawn": "withdrawn",
          "Transferred": "transferred"}

raw = pd.read_csv(
    Path("applications_events.csv"),
    parse_dates=[TS, LABEL_AT, EXTRACT_AT],
)
for col in [TS, LABEL_AT, EXTRACT_AT]:
    raw[col] = pd.to_datetime(raw[col], utc=True, errors="coerce")
raw = raw.dropna(subset=[CASE, ACT, TS]).copy()
raw[ACT] = raw[ACT].replace(ACTIVITY_RENAME)
raw = raw.drop_duplicates()  # exact duplicates only; retain an audit trail
raw = raw.sort_values([CASE, TS]).copy()
raw["event_seq"] = raw.groupby(CASE, sort=False).cumcount()
raw["duplicate_candidate"] = raw.duplicated(
    [CASE, ACT, TS, RESOURCE], keep=False
)
ev = raw.loc[raw[TS] <= CUTOFF].copy()  # point-in-time event view

# PM4Py diagnostics use only the as-of event log; these are not target features.
formatted = pm4py.format_dataframe(
    ev.copy(), case_id=CASE, activity_key=ACT, timestamp_key=TS
)
log = pm4py.convert_to_event_log(formatted)
dfg, starts, ends = pm4py.discover_dfg(
    log, activity_key=ACT, timestamp_key=TS
)
variants = pm4py.get_variants(log, activity_key=ACT)
prefix_log = pm4py.get_prefixes_from_log(
    log, length=K, case_id_key=CASE, activity_key=ACT, timestamp_key=TS
)
prefix_log_df = pm4py.convert_to_dataframe(prefix_log)  # audit only

ordered = ev.sort_values([CASE, TS, "event_seq"])
first = ordered.groupby(CASE, as_index=False).head(1)
case = first[[CASE, TS, CHANNEL, REGION, AMOUNT]].rename(columns={TS: "start_ts"})
case = case.set_index(CASE)
activation = ev.loc[ev[ACT].eq("Account Activated")].groupby(CASE)[TS].min()
route_rows = ev.assign(_state=ev[ACT].map(ROUTES)).dropna(subset=["_state"])
terminal = route_rows.sort_values([CASE, TS, "event_seq"]).groupby(CASE)["_state"].first()
known = ev.loc[ev[DEFAULT].notna()].sort_values([CASE, TS])
label = pd.to_numeric(known.groupby(CASE)[DEFAULT].last(), errors="coerce")
label_at = ev.groupby(CASE)[LABEL_AT].min()
case["activation_ts"] = activation.reindex(case.index)
case["process_terminal"] = terminal.reindex(case.index)
case[DEFAULT] = label.reindex(case.index)
case[LABEL_AT] = label_at.reindex(case.index)
due = case["activation_ts"].notna() & (
    case["activation_ts"] + pd.Timedelta(days=90 + FEED_LAG_DAYS) <= CUTOFF
)
mature = due & case[DEFAULT].notna() & case[LABEL_AT].notna() & (
    case[LABEL_AT] <= CUTOFF
)
case["state"] = "open"
case.loc[case["process_terminal"].notna(), "state"] = case["process_terminal"]
case.loc[case["activation_ts"].notna(), "state"] = "activated_unknown"
case.loc[mature & case[DEFAULT].eq(1), "state"] = "activated_default90"
case.loc[mature & case[DEFAULT].eq(0), "state"] = "activated_survived90"
case.loc[due & ~mature & case["activation_ts"].notna(), "state"] = "activated_feed_missing_or_delayed"
case = case.reset_index()
case["split"] = np.select(
    [case["start_ts"] < pd.Timestamp("2025-01-01", tz="UTC"),
     case["start_ts"] < pd.Timestamp("2025-07-01", tz="UTC")],
    ["train", "validation"], default="test"
)
print("case count:", case[CASE].nunique())
print(case["state"].value_counts(dropna=False).to_string())

# Reconstruct a fixed-K, strictly pre-decision feature table.
first_k = ordered.groupby(CASE, group_keys=False).head(K)
pmeta = first_k.groupby(CASE).agg(
    prefix_seq=("event_seq", "max"), prefix_ts=(TS, "max"), n_events=(ACT, "size")
).reset_index()
first_decision = first_k[first_k[ACT].isin(DECISIONS)].groupby(CASE)["event_seq"].min()
pmeta["first_decision_seq"] = pmeta[CASE].map(first_decision)
pmeta = pmeta[(pmeta["n_events"] == K) & (
    pmeta["first_decision_seq"].isna() |
    (pmeta["first_decision_seq"] > pmeta["prefix_seq"])
)]
prefix_rows = ordered.merge(pmeta[[CASE, "prefix_seq", "prefix_ts"]], on=CASE)
prefix_rows = prefix_rows[prefix_rows["event_seq"] <= prefix_rows["prefix_seq"]].copy()
prefix_rows["gap_h"] = prefix_rows.groupby(CASE)[TS].diff().dt.total_seconds() / 3600
start_map = case.set_index(CASE)["start_ts"]
prefix_rows["start_ts"] = prefix_rows[CASE].map(start_map)

pf = prefix_rows.groupby(CASE).agg(
    prefix_ts=(TS, "max"), prefix_event_count=(ACT, "size"),
    distinct_activities=(ACT, "nunique"), distinct_resources=(RESOURCE, "nunique"),
    mean_gap_h=("gap_h", "mean"), median_gap_h=("gap_h", "median"),
).set_index(CASE)
pf["elapsed_h"] = (pf["prefix_ts"] - pf.index.map(start_map)).dt.total_seconds() / 3600
activity_counts = pd.crosstab(prefix_rows[CASE], prefix_rows[ACT])
for name in ["Credit Review", "Documents Requested", "Documents Received"]:
    pf["n_" + name.replace(" ", "_").lower()] = (
        activity_counts[name].reindex(pf.index, fill_value=0)
        if name in activity_counts else 0
    )
pf["credit_review_rework"] = (pf["n_credit_review"] - 1).clip(lower=0)
current = prefix_rows.sort_values([CASE, TS, "event_seq"]).groupby(CASE).tail(1).set_index(CASE)
pf["current_activity"] = current[ACT]
pf["current_resource"] = current[RESOURCE]
risk_rows = prefix_rows.dropna(subset=[RISK]).sort_values([CASE, TS, "event_seq"])
pf["risk_score_asof"] = risk_rows.groupby(CASE)[RISK].last().reindex(pf.index)
pf["policy_era"] = np.where(pf["prefix_ts"] < pd.Timestamp("2025-07-01", tz="UTC"), "pre", "post")
pf["migration_era"] = np.where(pf["prefix_ts"] < pd.Timestamp("2025-10-15", tz="UTC"), "pre", "post")

# A historical workload proxy: only events before each prefix and in the prior 30 days.
hist = ordered.merge(pmeta[[CASE, "prefix_ts"]], on=CASE)
hist = hist[(hist[TS] < hist["prefix_ts"]) &
            (hist[TS] >= hist["prefix_ts"] - pd.Timedelta(days=30))]
pf["prior_30d_event_count"] = hist.groupby(CASE).size().reindex(pf.index, fill_value=0)
features = case.merge(pf.reset_index(), on=CASE, how="inner")
target_or_admin = {"state", DEFAULT, LABEL_AT, "activation_ts", "process_terminal", "split"}
X = features.drop(columns=target_or_admin, errors="ignore")
forbidden = {"final_limit", "decision_reason", "collection_status", DEFAULT, LABEL_AT, EXTRACT_AT}
assert forbidden.isdisjoint(X.columns), "leakage column entered feature table"

# Later connection point: fit cause-specific survival/competing-risk models on
# event times, maturity-aware censoring weights, and the case-level split above.
```
