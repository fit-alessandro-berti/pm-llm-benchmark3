- **Object Types:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. All capitalized to distinguish from activities and match OCEL type conventions.
- **E2O Qualifier Vocabulary:**
    - `created`: Event creates the object (e.g., Create Order).
    - `modified`: Event changes object state (e.g., Add Item, Close Order).
    - `contained_by`: Object is part of another (used inversely for clarity, e.g., Item contained_by Order). *Correction*: Standard is usually active voice on Event side. Let's use `acts_on` or specific verbs.
    - Revised Vocabulary: `created`, `added_to`, `reserved_for`, `packed_into`, `dispatched_via`, `issued_for`, `settled_by`, `confirmed_as`, `closed`.
    - Simplified for consistency in `relations`: `created`, `involved`, `billed`, `settled`, `packed`, `carried`, `confirmed`, `closed`.
- **O2O Direction Conventions:** Directed edges representing ownership or flow. `Source -> Target`. Example: `Order` `contains` `Item`; `Package` `packs` `Item`.
- **Logistics/Financial Relations:** Logistics events (Pack, Dispatch) relate directly to Packages/Deliveries. Financial events (Invoice, Payment) relate to Invoice/Payment. They do **not** directly relate to Orders in the `relations` table unless the event explicitly mentions the Order ID (e.g., "Issue Invoice V1 for O100"). Instead, connectivity is established via O2O links (Invoice `bills` Order). This prevents event-table bloat and preserves the separation of concerns.
- **Propagation vs. Observation:** Analytical propagation (via O2O) is distinguished from source-system facts (E2O relations). We do not duplicate E2O rows for inferred links. If an event acts on an Item, we record E2O(Item). If an Order contains that Item, O2O(Order, Item) allows the Order trace to inherit the event during flattening.
- **PM4Py Version:** Assumes `pm4py` >= 2.0 with explicit OCEL support (`pm4py.objects.ocel`). The constructor `OCEL(events, objects, relations, o2o)` is treated as a logical abstraction; in some versions, conversion via `pm4py.convert_to_ocel_log` is required.

**Consequential Event:** Event 6 (`Reserve Stock`) and Event 7 (`Pack Package`). These are the critical divergence/convergence points. E6 links I1 and I3 (different orders) operationally. E7 physically merges I1 and I3 into P1. Without these shared E2O relations, the system would treat O100 and O200 as completely independent silos until the Invoice event.

## 4. Expected flattened behavior

- **Order (O100/O200):**
    - *Trace Shape:* Create Order -> Add Items -> Reserve Stock -> Pack Package -> Dispatch -> Invoice -> Close Order.
    - *Copied Shared Events:* Events 6 (Reserve) and 7 (Pack P1) appear in both O100 and O200 traces due to O2O propagation (Order->Item->Package).
    - *Omitted Lifecycle:* Individual Item lifecycle is hidden; Package lifecycle is merged into Order view.
    - *Misleading Interpretation:* It may look like O100 and O200 were packed together simultaneously in the same physical space, obscuring the distinct P1/P2 packaging steps.
- **Package (P1/P2):**
    - *Trace Shape:* Pack Package -> Dispatch Package -> Confirm Delivery.
    - *Copied Shared Events:* None (Primary owner).
    - *Likely DFG Edges:* Pack -> Dispatch -> Confirm.
    - *Misleading Interpretation:* The financial aspect (Invoice) is absent unless O2O propagation is extended backward from Package to Invoice (which is not modeled here).
- **Delivery (D1/D2):**
    - *Trace Shape:* Assign Package -> Dispatch -> Confirm.
    - *Likely DFG Edges:* Similar to Package.
    - *Misleading Interpretation:* Cannot easily see which Orders were delivered without traversing O2O graph (Delivery->Package->Item->Order).
- **Invoice (V1):**
    - *Trace Shape:* Issue Invoice -> Record Payment (x2).
    - *Copied Shared Events:* None (Primary owner).
    - *Likely DFG Edges:* Issue -> Pay -> Pay.
    - *Misleading Interpretation:* The link to specific Orders is lost in the trace itself; the trace looks like a standalone financial transaction.

**Why Payment flattening is weak:**
Flattening on `Payment` yields extremely short traces (Record Payment -> End). It lacks the upstream context (Order creation, Delivery confirmation) necessary to analyze cash-to-cash cycles effectively. The Payment object is a leaf node in the value chain; its trace provides minimal sequential insight compared to Order or Delivery.

## 5. Expected object-centric structures

- **OC-DFG:** Will show parallel flows. One branch for Order Creation, branching into Item Addition. A merge point at `Reserve Stock` (connecting I1/I3). Another merge at `Pack Package` (P1 combining I1/I3). Distinct paths for P1 and P2 until `Issue Invoice` where they converge again.
- **OTG (Object Type Graph):** Will visualize `Order` connected to `Item`, `Item` to `Package`, `Package` to `Delivery`. `Invoice` connects to `Order` and `Payment`. It reveals the bipartite nature of Logistics (Order->Item->Pkg->Del) vs Finance (Order->Inv->Pay).
- **ET–OT (Event Type – Object Type):** Will highlight that `Pack Package` interacts with both `Package` and `Item`. `Issue Invoice` interacts with `Invoice` and `Order`.
- **Object-Centric Petri Net:** Likely a complex net with synchronized transitions. Transition "Pack" consumes I1 and I3 tokens and produces P1 token. Transition "Invoice" consumes O100 and O200 tokens. It demonstrates resource synchronization constraints (cannot invoice before orders are closed or goods dispatched, though our data doesn't enforce strict guards, the structure suggests it).
- **Object-Interactions Summary:** Will quantify that `P1` is the most interconnected object (links to I1, I3, D1, and via O2O to O100, O200). `V1` aggregates the financial burden of both orders.

## 6. Modeling alternatives

1.  **Source-Minimal Relations:**
    - *Policy:* Event relates ONLY to the primary object changed (e.g., `Pack Package` relates only to `Package`).
    - *Impact:* Flattening by `Order` would NOT see `Pack Package` events unless O2O propagation is aggressive. Reduces `relations` table size significantly but hides operational context in Order traces.
2.  **Full Operational Involvement:**
    - *Policy:* Every event relates to ALL objects affected, even indirectly (e.g., `Pack Package` relates to `Package`, `Item`, AND `Order`).
    - *Impact:* `relations` table explodes. Flattening becomes trivial (no need for O2O traversal). Discovery results become noisy because every event appears in every connected trace regardless of relevance.
3.  **O2O-Propagated Analytical Relations:**
    - *Policy:* Store only direct E2O relations. Use a post-processing step to create analytical logs where relations are computed on-the-fly during flattening.
    - *Impact:* Keeps storage efficient. Allows dynamic filtering (e.g., "Show me Order traces excluding Inventory events"). Requires robust query engines rather than static log flattening.

## 7. Failure modes

1.  **Relation Inflation:** Adding E2O links for every transitively related object (e.g., linking `Pack` to `Order` directly) makes the model rigid and hard to maintain if relationships change.
2.  **Missing Direct E2O Links:** If `Pack P1` is not linked to `I1` and `I3`, the system cannot track inventory consumption, breaking the link between Logistics and Finance.
3.  **Treating O2O Propagation as Observation:** Confusing derived links (O100 sees Pack P1 via Item) with observed links (Event happened on Order). This leads to false attribution of responsibility in compliance audits.
4.  **Duplicate Shared Events after Flattening:** If the flattening algorithm does not deduplicate events, `Reserve Stock` might appear twice in the consolidated Order trace, skewing duration metrics.
5.  **Ambiguous Payment Allocation:** With M1 and M2 settling V1, without specific allocation attributes (e.g., "covers O100"), it is unclear which order gets credit.
6.  **Overly Short Payment Traces:** As noted in Section 4, analyzing Payments in isolation yields little process insight.
7.  **Constructor/API Version Mismatch:** PM4Py evolves rapidly. Assuming a specific `OCEL` constructor signature may fail in production environments requiring `convert_to_ocel_log`.
8.  **False Total Order for Same-Time Events:** If multiple events occur at 08:00 UTC, flattening imposes an arbitrary order, potentially creating false causal dependencies in DFGs. (Not applicable here as timestamps are unique, but a risk in general).

## 8. Final semantic checks

1.  **Event 6 (Reserve Stock)** must link to **both** `I1` and `I3` in the `relations` table.
2.  **Event 7 (Pack P1)** must link to `P1`, `I1`, and `I3`.
3.  **Object `P1`** must have incoming O2O links from `I1` and `I3` (`packs` qualifier reversed or `packed_in`).
4.  **Invoice `V1`** must bill **both** `O100` and `O200` in `o2o`.
5.  **Payments `M1` and `M2`** must settle `V1`, but **not** directly link to Orders in `relations` (preserving separation).
6.  **Timestamps** must be strictly increasing for the main sequence (08:00 to 10:35 next day) with no ties, ensuring deterministic sorting.
7.  **Event IDs** must be unique across the `events` dataframe.
8.  **Activity Names** in `relations` must exactly match those in `events` for every `eid`.
