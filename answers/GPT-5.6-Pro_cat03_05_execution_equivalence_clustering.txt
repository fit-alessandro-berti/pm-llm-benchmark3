## 1. Equivalence design space

### Activity-sequence equivalence, (\equiv_A)

**Definition.** For execution (X), construct an activity signature
[
A(X)=\langle M_1,\ldots,M_k\rangle,
]
where each (M_i) is the multiset of activity labels in timestamp layer (i). Then (X\equiv_A Y) exactly when (A(X)=A(Y)). With no timestamp ties, this reduces to equality of the ordinary activity-label sequence. Repeated labels are preserved.

**Preserved:** activity labels, repetitions, and temporal order between timestamp layers.

**Discarded:** all object identifiers and types, E2O incidence, object multiplicities not visible as repeated events, O2O relations, qualifiers, externality, and attributes.

**Properties:** reflexive, symmetric, and transitive because it is equality of canonical sequences.

**Concurrency:** same-time events form an unordered multiset. Thus two executions are not separated merely because concurrent events were serialized differently.

### Typed structural equivalence, (\equiv_T)

Represent an execution as an ordered, typed graph containing:

* event nodes labeled by activity and timestamp layer;
* object nodes labeled by `(object type, external flag)`;
* E2O incidence edges;
* unqualified O2O adjacency;
* the strict order between event layers.

Then (X\equiv_T Y) when there is a bijection between their event nodes and a bijection between their object nodes that preserve node labels, E2O incidence, unqualified O2O endpoints, and event order. Local identifiers may be renamed arbitrarily within the same `(type, externality)` class.

**Preserved:** exact object and event multiplicities, repeated activities, identity continuity across events, typed interaction topology, external versus local status, and event order.

**Discarded:** literal local identifiers, absolute timestamps, durations, attributes, amounts, resources, and O2O qualifier names. The presence of an O2O edge is preserved, but not whether it means `packs`, `replaces`, or `removed_before_dispatch`.

**Properties:** reflexive by the identity mapping, symmetric by inverting an isomorphism, and transitive by composing isomorphisms.

**Concurrency:** events in the same timestamp layer may be permuted. Causal order can alternatively be derived from shared-object lifecycles rather than timestamp order alone.

### Preferred business-semantic equivalence, (\equiv_S)

I use the three-component signature

[
S(X)=(\text{scope},\text{lifecycle class},\text{execution shape}).
]

Its components are:

* **Scope:** `isolated` unless an `EXT` object participates in the execution; otherwise `cross-order`.
* **Lifecycle class:** `correction` if there is a return/inspection motif, a repack after return, or a qualifier such as `replaces` or `removed_before_dispatch`; otherwise `regular`.
* **Execution shape:** `fragmented` if there is more than one Package, Delivery, or Payment, or repeated Pack, Dispatch, or Payment activity; otherwise `atomic`.

Then (X\equiv_S Y) when these three categorical values are equal.

**Preserved:** the presence of cross-order coupling, lifecycle correction, and coarse one-to-many fragmentation.

**Discarded:** the exact multiplicity above one, the domain of sharing—logistics versus finance—the distinction between consolidated and split delivery, the phase of correction, and detailed event order.

**Properties:** reflexive, symmetric, and transitive because it is equality of a deterministic feature tuple.

**Concurrency:** the signature is mainly count- and motif-based, so arbitrary ordering of concurrent Pack or Dispatch events does not change the cluster.

### Detailed semantic-profile equivalence, (\equiv_D)

A useful refinement is equality of:

[
D(X)=(\text{sharing domain},P{\rightarrow}D\text{ topology},
\text{settlement mode},\text{correction kind/phase},
\text{qualified partial-order motif}).
]

This preserves, for example, logistics sharing versus invoice sharing, (2P{\rightarrow}1D) versus (2P{\rightarrow}2D), single versus partial payment, and pre-dispatch substitution versus post-dispatch return. It is also reflexive, symmetric, and transitive. It would separate all executions here except X1 and X2. It is preferable for compliance or diagnosis, but too sparse for many operational dashboards.

## 2. Canonical signatures

For these compact executions, exact identifier invariance can be obtained by trying every renaming within each `(object type, external flag)` class and choosing the lexicographically smallest serialization. This is factorial in the largest color class, but entirely practical here. Larger logs should use a graph-canonicalization package or a Weisfeiler–Lehman hash followed by exact isomorphism verification.

```python
from collections import Counter, defaultdict
from itertools import permutations, product

# Expected representation:
# ex.objects = {object_id: object_type}
# ex.events = [
#   {"activity": str, "layer": int,
#    "e2o": [(object_id, e2o_qualifier_or_None), ...]},
#   ...
# ]
# ex.o2o = [(source_id, qualifier_or_None, target_id), ...]

def is_external(oid):
    return str(oid).startswith("EXT")

def canonical_graph(ex):
    """Exact under renaming within (type, externality) classes."""
    classes = defaultdict(list)
    for oid, otype in ex.objects.items():
        classes[(otype, is_external(oid))].append(oid)

    alternatives = []
    for color in sorted(classes):
        otype, external = color
        old_ids = classes[color]
        canonical_ids = [
            (otype, "E" if external else "L", i + 1)
            for i in range(len(old_ids))
        ]
        alternatives.append([
            dict(zip(ordering, canonical_ids))
            for ordering in permutations(old_ids)
        ])

    best = None
    for selected_maps in product(*alternatives):
        rename = {}
        for mapping in selected_maps:
            rename.update(mapping)

        layers = defaultdict(list)
        for event in ex.events:
            incidence = tuple(sorted(
                (rename[oid], qualifier or "")
                for oid, qualifier in event["e2o"]
            ))
            layers[event["layer"]].append(
                (event["activity"], incidence)
            )

        event_part = tuple(
            (layer, tuple(sorted(layers[layer])))
            for layer in sorted(layers)
        )
        object_part = tuple(sorted(
            (rename[oid], otype, is_external(oid))
            for oid, otype in ex.objects.items()
        ))
        o2o_part = tuple(sorted(
            (rename[source], qualifier or "", rename[target])
            for source, qualifier, target in ex.o2o
        ))

        candidate = (event_part, object_part, o2o_part)
        if best is None or candidate < best:
            best = candidate

    return best

def preferred_signature(ex):
    graph_signature = canonical_graph(ex)
    object_counts = Counter(ex.objects.values())
    activity_counts = Counter(e["activity"] for e in ex.events)
    qualifiers = {q for _, q, _ in ex.o2o if q}

    cross_order = any(is_external(oid) for oid in ex.objects)
    correction = (
        bool({"replaces", "removed_before_dispatch"} & qualifiers)
        or activity_counts["Return Item"] > 0
        or activity_counts["Inspect Return"] > 0
    )
    fragmented = (
        object_counts["Package"] > 1
        or object_counts["Delivery"] > 1
        or object_counts["Payment"] > 1
        or activity_counts["Pack Package"] > 1
        or activity_counts["Dispatch"] > 1
        or activity_counts["Record Payment"] > 1
    )

    cluster_key = (
        "cross-order" if cross_order else "isolated",
        "correction" if correction else "regular",
        "fragmented" if fragmented else "atomic",
    )

    # Retained for drill-down, but not used to split preferred clusters.
    detail = {
        "object_counts": tuple(sorted(object_counts.items())),
        "activity_counts": tuple(sorted(activity_counts.items())),
        "qualifiers": tuple(sorted(qualifiers)),
        "canonical_graph": graph_signature,
    }
    return cluster_key, detail
```

## 4. Cluster interpretations

**S0 — isolated, regular, atomic.** The two items are fulfilled through one package and one delivery, followed by one invoice and one payment. It is a useful straight-through benchmark and a candidate for automation or service-time baselining. An Item flattening represents it poorly because the shared Pack and Dispatch can appear in multiple item cases, while order-level invoice and payment events may not fit naturally into either item trace. The assignment is highly stable under identifier changes and harmless reordering of identical Add Item events.

**S1 — isolated, regular, fragmented.** The Order is divided across multiple logistics or settlement objects. X3 consolidates two packages into one delivery; X4 uses two deliveries and two payments. The common business issue is fragmentation, with possible extra handling cost, synchronization delay, partial-customer experience, or reconciliation work. Consolidation and root-cause analysis of package splits are opportunities. An Order flattening shows repeated activities but not the package-to-delivery cardinality; a Delivery flattening loses the common Order context. The family assignment is moderately stable: collapsing X4’s two payments still leaves two packages and deliveries, while X3 would move only if one of its two packages were repaired away as erroneous.

**S2 — cross-order, regular, atomic.** The lead Order has a simple-looking local sequence, but its execution is coupled to another Order. X5 shares logistics capacity and physical contents; X6 shares an invoice and payment without an order-level allocation. Risks include delay propagation, ambiguous ownership, double counting, misallocated revenue or cost, and inability to settle or reverse one Order independently. Consolidation can also be beneficial when deliberate. Order flattening is particularly misleading because a shared event may be copied into both order traces, making one operation look like two independent operations. Stability is only moderate: deleting the external relations as extraction noise would move both executions toward S0.

**S3 — isolated, correction, atomic.** X7 performs a pre-dispatch substitution or removal without adding a visibly different activity. Risks include shipment-content mismatch, stale inventory reservations, and invoicing an item no longer dispatched. Detecting the correction before dispatch is an opportunity to prevent a return. An Order flattening is almost maximally poor: its activity sequence is indistinguishable from the baseline. The classification depends strongly on O2O qualifiers, although the extra Item relation at Dispatch provides supporting structural evidence. It therefore has low-to-moderate repair stability.

**S4 — isolated, correction, fragmented.** X8 has a completed first dispatch, return of I82, inspection, repacking, and a second dispatch. This is reverse logistics and rework rather than ordinary order splitting. Risks include customer delay, extra transport cost, quality failure, and inconsistent package or delivery status. The cluster is valuable for return-reason and first-time-right analysis. Order flattening reveals the loop but not reliably that the same item is moved from P81 to P82; Item flattening captures I82 better but loses the complete order-level financial context. The assignment is highly stable because explicit Return Item and Inspect Return events remain even if the `replaces` qualifier is missing.

## 5. Borderline cases

**X1 versus X2.** Record-level exact equality can separate them because the raw identifiers and item-reference order differ; that notion is useful for data lineage or duplicate detection, not behavioral clustering. Typed isomorphism and all business-semantic notions merge them because the first item in X1 can be mapped to the first-added item in X2. Under the prompt’s identifier semantics, merging is preferable.

**X1 versus X5.** Activity-sequence equivalence merges them. Typed structure and semantic scope separate them because X5’s Package and Delivery connect O5 to an external Order and external Item. A lead-Order projection that deliberately removes all external objects would defensibly merge them for local cycle-time reporting, while a coupling analysis must separate them.

**X1 versus X6.** Order-flattened activity behavior again merges them. Financial-scope equivalence separates X6 because the invoice and payment cannot be assigned solely to O6. An operational logistics segmentation might merge the pair because their package and delivery behavior is the same; compliance, accounting, and cash-allocation analyses should not.

**X1 versus X7.** Label-only equivalence merges them. Qualified structural or detailed semantic equivalence separates them because I72 replaces I71 and I71 is removed before dispatch. If O2O qualifiers are considered unreliable and the Dispatch–Item incidence is treated as redundant enrichment, merging is defensible but low-confidence.

**X3 versus X4.** Preferred semantic equivalence merges them as regular fragmented executions. Typed structure or detailed semantic profiles separate them: X3 is (2P{\rightarrow}1D) with one settlement, whereas X4 is (2P{\rightarrow}2D) with interleaved fulfillment and partial payment. The former clustering supports split-order workload analysis; the latter supports intervention design.

**X4 versus X8.** A logistics-multiplicity signature that ignores activity meaning and payment structure could merge them because both use two packages and two deliveries. Lifecycle-aware equivalence separates them: X4 is ordinary split fulfillment, while X8 contains return, inspection, and repack of the same item. Including payment multiplicity also separates them because X4 has two Payment objects and X8 one.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

In the current PM4Py release-branch implementation, `cluster_equivalent_ocel` first extracts one ancestors-and-descendants sub-OCEL per lead object, renames objects, and then computes a timestamp-free Variant-2 description. The key is a pair: an event tuple sequence and an object tuple sequence. Each event tuple contains the activity followed by its related object identifiers; each object tuple contains an object identifier and object type.

Variant 2 sorts events by timestamp, activity, and event identifier, and sorts related objects by object identifier before constructing the event tuples. With timestamps disabled, the key therefore preserves repeated events, deterministic total order, object inventory and types, and exact E2O identity incidence. It omits timestamps, event and object attributes, E2O qualifiers, O2O relations and qualifiers, and object changes. Consequently, two executions differing only in a `replaces` qualifier can be placed together unless another E2O or event difference exposes the correction.

The key schema contains identifiers, but current PM4Py normally replaces them with names based on object type, lifecycle start, lifecycle end, and lexical tie-breaking. Raw identifiers can nevertheless make clusters too fine in older implementations, when calling the descriptor directly, or when object types are excluded from renaming. Moreover, lexical tie-breaking is not a complete graph-isomorphism canonicalizer: symmetric objects with identical lifecycle bounds can still receive canonical positions influenced by their original identifiers.

A practical pipeline is therefore to retain PM4Py’s exact groups as diagnostic strata and aggregate their returned original sub-OCELs using an explicitly business-oriented key:

```python
import pm4py
from collections import Counter, defaultdict

exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type="Order",
    max_objs=10_000,
)

def coarse_type_incidence_key(pm4py_key):
    """Identifier-independent, but intentionally loses cross-event identity."""
    event_part, object_part = pm4py_key
    object_type = {oid: otype for oid, otype in object_part}

    result = []
    for event_tuple in event_part:
        activity = event_tuple[0]
        type_counts = Counter(object_type[oid] for oid in event_tuple[1:])
        result.append((activity, tuple(sorted(type_counts.items()))))
    return tuple(result)

def semantic_key(sub_ocel):
    oid_col = sub_ocel.object_id_column
    otype_col = sub_ocel.object_type_column
    activity_col = sub_ocel.event_activity

    ids = sub_ocel.objects[oid_col].astype(str).tolist()
    type_counts = Counter(sub_ocel.objects[otype_col].tolist())
    activity_counts = Counter(sub_ocel.events[activity_col].tolist())

    qualifiers = set()
    if sub_ocel.o2o is not None and "ocel:qualifier" in sub_ocel.o2o:
        qualifiers = set(
            sub_ocel.o2o["ocel:qualifier"].dropna().astype(str)
        )

    cross_order = any(oid.startswith("EXT") for oid in ids)
    correction = (
        bool({"replaces", "removed_before_dispatch"} & qualifiers)
        or activity_counts["Return Item"] > 0
        or activity_counts["Inspect Return"] > 0
    )
    fragmented = (
        type_counts["Package"] > 1
        or type_counts["Delivery"] > 1
        or type_counts["Payment"] > 1
        or activity_counts["Pack Package"] > 1
        or activity_counts["Dispatch"] > 1
        or activity_counts["Record Payment"] > 1
    )

    return (
        "cross-order" if cross_order else "isolated",
        "correction" if correction else "regular",
        "fragmented" if fragmented else "atomic",
    )

semantic_clusters = defaultdict(list)

for exact_key, sublogs in exact_clusters.items():
    type_only_key = coarse_type_incidence_key(exact_key)

    for sublog in sublogs:
        lead_order = sublog.parameters.get("@@central_object")
        semantic_clusters[semantic_key(sublog)].append({
            "lead_order": lead_order,
            "ocel": sublog,
            "pm4py_exact_key": exact_key,
            "type_incidence_key": type_only_key,
        })
```

Exact equivalence is preferable for regression testing, deduplication, reproducible pattern counts, and investigating one precise E2O topology. Coarser clustering is preferable when variants must map to common operational actions.

Operationally, `max_objs` stops processing after the first specified number of lead objects; it does not cap the number of objects contained in each extracted execution. Since extraction uses a transitive ancestors-and-descendants closure over the object-interaction graph, one highly connected Package, Invoice, or Delivery can produce very large, overlapping sub-OCELs. Such executions increase runtime and can make the concept of an Order-centered execution too broad.

## 7. Robustness analysis

**Ignoring all O2O qualifiers.** X7 loses its explicit correction semantics and would move from S3 to S0 under the preferred key. It may remain structurally distinct because Dispatch directly references I72 and because additional unqualified O2O adjacency remains. X8 stays in S4 because its Return Item, Inspect Return, repeated Pack, and repeated Dispatch events are explicit.

**Ignoring external objects.** X5 and X6 move from S2 to S0, assuming the external E2O and O2O relations are removed consistently. Their activity sequences already belong to A0. This perturbation demonstrates that externality is not decorative metadata: it determines whether the execution is isolated.

**Collapsing consecutive repeated same-label events.** The two Add Item events collapse everywhere. X3’s consecutive Pack events also collapse, making its activity signature equal to the collapsed baseline sequence, although its two Package objects still keep it in S1. X4’s consecutive payments collapse, but its separated Pack–Dispatch branches remain. Object-centric clustering is therefore more robust than activity-run clustering.

**Using a Pack/Dispatch partial order.** In X4, Pack P42 may be concurrent with Dispatch P41 because they concern different package-delivery branches. A partial-order equivalence would merge different serializations of those branches. It would not merge X4 with X3 under typed structure because X3 has a convergence of two packages into one Dispatch and one Delivery. Preferred clusters are unchanged.

**Representing payment multiplicity as an amount attribute.** Replacing X4’s two Payment objects/events with one payment carrying partial-settlement amounts changes A2 and T2. X4 nevertheless remains in S1 because its two packages and deliveries still make it fragmented. Financial root-cause analysis would lose the distinction unless settlement mode were retained as an attribute in the detailed profile.

## 8. Limitations and recommendation

The data contain no durations, amounts, resources, line positions, return reasons, or reliable concurrency information. Externality is encoded by an identifier convention, and the completeness of E2O and O2O relations cannot be tested from these eight executions. The thresholds behind `atomic` versus `fragmented` and the precedence given to correction motifs are analytical choices rather than discovered facts.

For **compliance monitoring**, use detailed semantic-profile equivalence (\equiv_D), preserving external sharing domains, qualified relations, settlement mode, and causal phase. X5, X6, X7, and X8 should not be hidden inside broad variants.

For **operational segmentation**, use the preferred (\equiv_S). Its five clusters are coarse enough to support common interventions while retaining the dominant distinction between straight-through, fragmented, coupled, and corrective work.

For **root-cause analysis**, start with typed structural equivalence (\equiv_T), then enrich clusters with timestamps, amounts, products, resources, and error reasons. This preserves the structural distinctions between X3 and X4 and between X5 and X6.

For **descriptive reporting**, activity-sequence equivalence (\equiv_A) is acceptable for compact volume summaries, but it should be cross-tabulated with semantic scope. Otherwise, X1, X5, X6, and X7 misleadingly appear to be the same behavior.

No single level is optimal: exact structure offers diagnostic precision but creates sparse clusters; activity abstraction gives stable counts but hides coupling; and semantic clustering is actionable only after analysts explicitly choose which distinctions matter.
