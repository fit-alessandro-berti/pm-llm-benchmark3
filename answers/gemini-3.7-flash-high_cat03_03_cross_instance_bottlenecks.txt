## 1. Interaction-graph description

The production process forms an object-centric interaction network coupling six jobs ($J_1 \dots J_6$) across equipment, tooling, thermal batch containers, quality lots, and shipments.

### 1.1 Node Types
- **Flow Objects**: `Job` ($J_1 \dots J_6$), `Batch` ($B_1, B_2$), `Shipment` ($S_1, S_2, S_3$).
- **Material Objects**: `Component` ($C_1 \dots C_6$), `ComponentLot` ($L_7, L_8$).
- **Resource Objects**: `Machine` (`CNC-2`, `OVEN-1`, `TEST-1`), `Tool` (`FIX-A`, `RACK-7`, `CAL-3`).

### 1.2 Edge Types and Qualifiers
- **Structural ($O2O_{struct}$)**: `requires` (`Job -> Component`, 1:1), `contains` (`ComponentLot -> Component`, 1:N), `batches` (`Batch -> Job`, 1:N), `consolidates` (`Shipment -> Job`, 1:N).
- **Dynamic Allocation ($E2O \to O2O_{dyn}$)**: `executes_on` (`Job/Batch -> Machine`), `utilizes_tool` (`Job/Batch -> Tool`), `governed_by` (`Job/Component -> ComponentLot`).

### 1.3 Higher-Order Motifs (>2 Object Types)
1. **Cross-Batch Tool Re-use (`Job – Batch – Tool – Machine – Job`)**: $B_1$ ($J_1, J_2, J_3$) locks `OVEN-1` and `RACK-7`. Batch $B_2$ ($J_4, J_5$) requires both. Although `OVEN-1` is idle at 12:55, $B_2$ cannot start until `RACK-7` cleaning completes at 14:35.
2. **Upstream Contention to Downstream Synchronization (`Job – Tool – Machine – Batch – Job – Shipment`)**: $J_3$ holds `FIX-A` at `CNC-2` until 11:40, starving $J_4$ (arrived 09:50). $J_3$ enters $B_1$ (cures 12:05), while $J_4$ finishes machining at 13:10 for $B_2$ (cures 14:50). $J_4$'s delayed pack (19:10) traps $J_1$ (packed 13:30) in $S_1$ until 19:25.
3. **Quality Pedigree Asymmetric Gating (`ComponentLot – Component – Job – Batch – Shipment`)**: $L_7$ contains $C_2$ ($J_2$) and $C_5$ ($J_5$). Quarantine on $L_7$ (10:20–13:50) affects both. $J_2$ enters $B_1$ at 12:05 via unrecorded override, while $J_5$ is held until 13:50 release, delaying $B_2$ (ready 14:40) and Shipment $S_3$ with $J_6$.

### 1.4 Direct vs. Inferred Edges
- **Direct**: Explicit event bindings (`Batch Cure` referencing $\{B_1, \text{OVEN-1}, \text{RACK-7}, J_1, J_2, J_3, C_1, C_2, C_3\}$; `S1 consolidates J1, J4`; `L7 contains C2, C5`).
- **Inferred**: Tool contention ($J_3 \xrightarrow{\text{contends}} J_4$ on `FIX-A`, deduced from $J_4$ arrival at 09:50, `CNC-2` idle gap 10:05–10:47, and $J_3$ release at 11:40); carrier hold ($B_1 \xrightarrow{\text{holds}} B_2$ on `RACK-7`).

## 2. Quantitative delay decomposition

Below are five explicit delay calculations across the multi-object network.

### 1. Batch $B_1$ Synchronization Waiting for $J_1$ and $J_2$
- **Timestamps**: $J_1$ ready 08:10; $J_2$ ready 08:25; $J_3$ ready 11:55; $B_1$ starts 12:05.
- **Decomposition**: $J_1$ total dwell = $12:05 - 08:10 = 235\text{ min}$ (3h 55m); $J_2$ total dwell = $12:05 - 08:25 = 220\text{ min}$ (3h 40m). Sync wait for lagging $J_3$: $J_1$ waited $11:55 - 08:10 = 225\text{ min}$; $J_2$ waited $11:55 - 08:25 = 210\text{ min}$. Total batch queue = $235 + 220 + 10 = 465\text{ job-min}$.
- **Counterfactual Assumption**: If smaller batches were viable on `OVEN-1` without thermal penalties, $J_1$ and $J_2$ could have completed curing before 10:00, saving up to 435 job-minutes.

### 2. Tool Contention Delay on `FIX-A` for $J_4$
- **Timestamps**: $J_4$ arrives at `CNC-2` at 09:50; `CNC-2` idle 10:05–10:47 (42 min) and 10:47–11:45 (58 min); $J_3$ holds `FIX-A` 09:00–11:40; $J_4$ starts 11:45.
- **Decomposition**: Total wait for $J_4 = 11:45 - 09:50 = 115\text{ min}$. Machine idle time during $J_4$'s wait = $42 + 58 = 100\text{ min}$. Overlap with $J_3$'s tool hold = $11:40 - 09:50 = 110\text{ min}$ (plus 5 min setup transition).
- **Counterfactual Assumption**: Assumes `CNC-2` was operator-ready at 10:05. Duplicate fixture `FIX-B` would let $J_4$ start at 10:05, eliminating 100 minutes of machine starvation.

### 3. Shipment Consolidation Holding Delay on $J_1$ in $S_1$
- **Timestamps**: $J_1$ packed 13:30; $J_4$ packed 19:10; $S_1$ dispatches 19:25.
- **Decomposition**: $J_1$ finished-goods dwell = $19:25 - 13:30 = 355\text{ min}$ (5h 55m). Delay strictly waiting for partner $J_4 = 19:10 - 13:30 = 340\text{ min}$ (5h 40m).
- **Counterfactual Assumption**: Assumes $J_1$ could ship independently upon packing at 13:45, accelerating delivery by 340 minutes.

### 4. Calibration Downtime Delay on `CAL-3` for $J_6$
- **Timestamps**: $J_5$ ready 16:00 (tests 16:10–16:35); $J_6$ ready 16:05; `CAL-3` recalibration 16:35–17:20; `TEST-1` idle 16:35–17:25; $J_6$ tests 17:25–17:50.
- **Decomposition**: Total test queue wait for $J_6 = 17:25 - 16:05 = 80\text{ min}$. Delay caused by `CAL-3` recalibration = $17:20 - 16:35 = 45\text{ min}$ (plus 5 min transition = 50 min).
- **Counterfactual Assumption**: Assumes `TEST-1` was operable. A spare calibrated tool `CAL-3B` at 16:35 would let $J_6$ test 16:35–17:00, advancing completion and $S_3$ dispatch by 50 minutes.

### 5. Dual-Constraint Delay on Batch $B_2$ ($J_4, J_5$)
- **Timestamps**: $L_7$ quarantined 10:20–13:50; $J_4$ ready for $B_2$ 13:10; `RACK-7` cleaning finishes 14:35; $J_5$ ready for $B_2$ 14:40; $B_2$ starts 14:50.
- **Decomposition**: $J_4$ pre-batch dwell = $14:50 - 13:10 = 100\text{ min}$. Blocked 13:10–14:35 (85 min) by `RACK-7` cleaning, and 14:35–14:40 (5 min) by $J_5$ arrival.
- **Counterfactual Assumption**: Without $L_7$ quarantine, $J_5$ arrives earlier, but $B_2$ still could not start before 14:35 due to `RACK-7`, showing `RACK-7` was the binding constraint for 85 min.

## 4. What flattening misses

Traditional 1D flattenings project multi-object processes onto a single case identifier, creating severe blind spots.

### 4.1 Viewpoint Breakdown
- **Job Viewpoint**:
  - *Visible*: Sequence (`Release -> Stage -> Machine -> Inspect -> Pack -> Dispatch`), rework loops (freq 2), total lead times.
  - *Hidden / Duplicated*: Hides batch synchronization barriers; hides tool starvation; duplicates shared events (`Batch Cure` cloned across $J_1, J_2, J_3$).
  - *Misleading Conclusion*: Job durations appear statistically normal (< 1.8 SD from mean), falsely suggesting stable operations.
- **Machine Viewpoint**:
  - *Visible*: Station cycles (`Setup -> Process -> Release`) and nominal utilization (`CNC-2`: 54%, `OVEN-1`: 44%, `TEST-1`: 58%).
  - *Hidden / Duplicated*: Hides waiting job queues; hides reasons for idle gaps; obscures batch size.
  - *Misleading Conclusion*: Low utilization (44%–58%) is interpreted as excess capacity, falsely implying no equipment bottlenecks exist.
- **Batch Viewpoint**:
  - *Visible*: Thermal cycle durations (`Load -> Cure -> Unload`) and chamber runtimes.
  - *Hidden / Duplicated*: Hides pre-batch arrival history (masks $J_1$ 235m wait vs $J_3$ 10m wait); obscures component pedigree.
  - *Misleading Conclusion*: Batch processing appears highly efficient, masking massive pre-process inventory holding costs.
- **Tool Viewpoint**:
  - *Visible*: Tool usage intervals, cleaning windows, and calibration durations.
  - *Hidden / Duplicated*: Hides commercial priority of blocked jobs; obscures revenue loss from tool downtime.
  - *Misleading Conclusion*: Tool maintenance (`CAL-3` 45-min recalibration) appears harmless in isolation, masking downstream test/shipping paralysis.
- **ComponentLot Viewpoint**:
  - *Visible*: Lot quarantine windows (10:20–13:50) and supplier traceability.
  - *Hidden / Duplicated*: Hides individual job execution paths; hides compliance violations ($J_2$'s supervisor override is unlinked).
  - *Misleading Conclusion*: Quality containment appears cleanly bounded (10:20–13:50), hiding that quarantined part $C_2$ was processed.
- **Shipment Viewpoint**:
  - *Visible*: Dock stages (`Create Shipment -> Load -> Dispatch`) and dock velocity (0.8h load + 0.3h dispatch = 1.1h median).
  - *Hidden / Duplicated*: Hides staging dwell of early-packed jobs ($J_1$ waiting 355m for $J_4$); hides upstream causes of late dispatch.
  - *Misleading Conclusion*: Logistics appears lean and rapid (1.1h turnaround), masking severe finished-goods holding delays.

### 4.2 Why Low Machine Utilization Coexists with Long Job Waiting
In multi-object manufacturing, an operation requires the **simultaneous co-presence** of multiple complementary resources:

$$\text{Operation Executable} \iff \text{Machine Free} \land \text{Tool Free} \land \text{Material Free} \land \text{Batch Cohort Present} \land \text{Quality Released}$$

If any auxiliary resource (`FIX-A`), carrier state (`RACK-7` cleaning), batch partner ($J_3$), or quality release ($L_7$) is missing, the primary machine is **starved** (idle) while available jobs are **blocked** (waiting). Auxiliary constraints decouple machine utilization from job dwell time.

## 5. Object-lifecycle evidence

### Narrative 1: Upstream Tool Contention Cascading to Shipment Consolidation Delay
*Spanning: `Job`, `Tool`, `Machine`, `Batch`, `Shipment`*
- **Temporal Precedence**: 09:00 $J_3$ acquires `FIX-A` at `CNC-2`; 09:50 $J_4$ arrives at `CNC-2`; 10:05–10:47 `CNC-2` sits idle (42 min); 11:40 $J_3$ releases `FIX-A` and reaches oven staging at 11:55; 11:45 $J_4$ starts machining on `CNC-2`; 12:05 $B_1$ cures on `OVEN-1`; 13:10 $J_4$ finishes machining and reaches oven staging for $B_2$; 13:30 $J_1$ is packed; 14:50 $B_2$ cures on `OVEN-1`; 19:10 $J_4$ is packed; 19:25 $S_1$ ($J_1, J_4$) dispatches.
- **Resource Feasibility**: `CNC-2` was available 10:05–10:47, but $J_4$ was blocked by `FIX-A`. `OVEN-1` was open 12:55–14:50, but $B_2$ was blocked by `RACK-7` cleaning (until 14:35) and $J_5$'s arrival (14:40).
- **Policy Constraints**: Single-fixture allocation rule for `FIX-A`; rigid full-order consolidation policy for $S_1$.
- **Causal Speculation**: Duplicating `FIX-A` would have allowed $J_4$ to machine at 10:05, advancing downstream testing and allowing $S_1$ to dispatch ~17:15, saving $J_1$ over 2 hours of staging dwell.

### Narrative 2: Quality Quarantine, Asymmetric Override, and Thermal Turnaround
*Spanning: `ComponentLot`, `Component`, `Job`, `Batch`, `Tool`, `Machine`, `Shipment`*
- **Temporal Precedence**: 08:25 $J_2$ ($C_2 \in L_7$) ready for $B_1$; 10:20 `Quarantine Lot` logged for $L_7$ ($C_2, C_5, J_2, J_5$); 12:05 $B_1$ cures on `OVEN-1` containing $J_2$ (via supervisor override); 12:55 $B_1$ unloads and `RACK-7` cleans until 14:35; 13:50 `Release Lot` logged for $L_7$; 14:40 $J_5$ ($C_5 \in L_7$) reaches oven staging; 14:50 $B_2$ cures on `OVEN-1`; 16:00 $J_5$ tests, packs, and joins $J_6$ in Shipment $S_3$.
- **Resource Feasibility**: `OVEN-1` was idle 12:55–14:50, but `RACK-7` was constrained until 14:35.
- **Policy Constraints**: SOP mandates holding quarantined parts; informal floor practice allowed an override for $J_2$, while $J_5$ was held until formal release at 13:50.
- **Causal Speculation**: If $J_2$ had not received an override, $B_1$ would have stalled until 13:50, colliding with $B_2$ on `OVEN-1`. If $J_5$ had also been overridden, $B_2$ would still have been blocked until 14:35 by `RACK-7` cleaning.

### Narrative 3: Calibration Recalibration Bottleneck and Final Inspection Gating
*Spanning: `Job`, `Tool`, `Machine`, `Shipment`*
- **Temporal Precedence**: 16:00 $J_5$ arrives at `TEST-1`; 16:05 $J_6$ arrives at `TEST-1`; 16:10–16:35 $J_5$ tests with `CAL-3`; 16:35–17:20 `CAL-3` undergoes 45-minute recalibration while `TEST-1` sits idle; 17:25–17:50 $J_6$ tests with `CAL-3`; 18:25 $J_6$ is packed; 19:00 Shipment $S_3$ ($J_5, J_6$) dispatches.
- **Resource Feasibility**: `TEST-1` was operable 16:35–17:25, but was non-functional without a certified calibration master.
- **Policy Constraints**: Mandatory recalibration rule after test cycles; $S_3$ policy requiring all jobs packed prior to dispatch.
- **Causal Speculation**: A pre-calibrated spare `CAL-3B` at 16:35 would have allowed $J_6$ to test immediately, advancing $S_3$ dispatch by 50 minutes.

## 6. Intervention portfolio and spillovers

### 1. Dynamic Batch Sizing & Time-Decoupled Curing (Reduces Synchronization)
- **Target Mechanism**: Batch synchronization barriers on `OVEN-1` ($B_1, B_2$).
- **Expected Benefit**: Saves up to 225 min of wait for $J_1$ and 85 min for $J_4$ by permitting 2-job batches or single-job expedited runs when wait exceeds 60 min.
- **Objects Helped**: $J_1, J_2, J_4$; increases `OVEN-1` schedule agility.
- **Objects Harmed**: Downstream inspection queues (earlier arrivals may create temporary queues).
- **New Cost or Risk**: Higher energy consumption per job due to partial chamber loads; potential thermal gradient variance.
- **Perverse Incentive Metric**: **"Chamber Fill %"** or **"kWh per Job"** — optimizing this forces operators to hold jobs for hours to maximize load density.
- **Evaluation Design**: Measure `Total WIP Dwell Time per Job` vs. `Batch Object Cardinality` extracted from OC-DFG.

### 2. Redundant Auxiliary Tooling & Rapid Turnaround (Addresses Tools)
- **Target Mechanism**: Tool contention on `FIX-A`, cleaning hold on `RACK-7`, calibration downtime on `CAL-3`.
- **Expected Benefit**: Eliminates 100 min starvation on `CNC-2` ($J_4$), enables immediate turnaround on `OVEN-1` ($B_2$), and recovers 50 min on `TEST-1` ($J_6$).
- **Objects Helped**: $J_4, J_6, B_2$; raises utilization of `CNC-2`, `OVEN-1`, `TEST-1`.
- **Objects Harmed**: Tool maintenance staff (higher cleaning/calibration workload).
- **New Cost or Risk**: Capital expense of duplicate `FIX-B`, spare `RACK-8`, and pre-calibrated `CAL-3B`.
- **Perverse Incentive Metric**: **"Tool Utilization Rate"** — incentivizes maintaining a minimal tooling pool, maximizing tool utilization while starving high-value machines.
- **Evaluation Design**: Compute `Machine Idle Time Overlapping Tool Hold by Other Jobs` across $O2O$ execution edges.

### 3. Milestone-Based Partial Shipment Release (Addresses Shipment Policy)
- **Target Mechanism**: Finished-goods holding delay induced by shipment consolidation ($S_1, S_2, S_3$).
- **Expected Benefit**: Saves 340 minutes of finished-goods staging dwell for $J_1$ by dispatching completed jobs via parcel carrier when partner jobs are delayed > 2 hours.
- **Objects Helped**: $J_1, J_2, J_5$; improves customer on-time delivery metrics.
- **Objects Harmed**: Freight logistics budget; customer receiving dock (split deliveries).
- **New Cost or Risk**: Higher aggregate freight costs (parcel/LTL premiums); invoice matching complexity.
- **Perverse Incentive Metric**: **"Freight Cost per Ton"** — minimizes shipping cost by holding packed jobs in warehouse staging, inflating lead times.
- **Evaluation Design**: Track `Finished Goods Staging Dwell` ($T_{\text{Dispatch}} - T_{\text{Pack}}$) partitioned by shipment size in OCEL.

### 4. OCEL 2.0 Ingestion & Tool Telemetry Pipeline (Improves Logging)
- **Target Mechanism**: Data-integration artifacts, unmodeled tool states, invisible queueing, and shadow overrides.
- **Expected Benefit**: Integrates MES, ERP, and QMS into an OCEL 2.0 schema, capturing explicit `ToolAcquired`, `ToolReleased`, `LotQuarantined`, and `OverrideApproved` events.
- **Objects Helped**: All jobs ($J_1 \dots J_6$), quality auditors, process analysts.
- **Objects Harmed**: Floor operators (additional scanning compliance).
- **New Cost or Risk**: Software licensing, RFID scanner infrastructure, database storage overhead.
- **Perverse Incentive Metric**: **"Scan Logging Velocity"** — leads to end-of-shift bulk scanning rather than real-time point-of-use logging.
- **Evaluation Design**: Measure `Unexplained Machine Idle Ratio` (percentage of machine idle intervals unlinked to any object constraint in OC-DFG).

### 5. Digital Pedigree Tracking & Electronic Override Governance (Quality Management)
- **Target Mechanism**: Asymmetric lot gating and undocumented shadow overrides ($L_7, L_8$).
- **Expected Benefit**: Rapid electronic dispositioning for quarantined lots within 15 minutes; prevents unauthorized processing of quarantined components ($J_2$).
- **Objects Helped**: $J_5$ (eliminates 3.5h hold); ensures compliance integrity.
- **Objects Harmed**: Floor supervisors (loss of informal, unmonitored override autonomy).
- **New Cost or Risk**: Temporary line stoppages if electronic sign-offs are delayed during off-shifts.
- **Perverse Incentive Metric**: **"Zero Override Exceptions"** — promotes extreme risk-aversion, halting production lines for minor paperwork discrepancies.
- **Evaluation Design**: Monitor graph distance and time delta between `Quarantine_Event` and downstream `Job_Processing_Event` across all linked jobs.

"""
Object-Centric Process Mining Analysis for Cross-Instance Bottlenecks
Assumes an initialized PM4Py OCEL 2.0 object named `ocel`.
"""

import pandas as pd
import numpy as np
import pm4py

# 1. Discover Object Types and Higher-Order Interaction Graph
obj_types = pm4py.ocel_get_object_types(ocel)
print(f"Discovered Object Types: {obj_types}")

o2o_interactions = pm4py.discover_objects_graph(ocel, graph_type="object_interaction")
interaction_summary = pm4py.ocel_objects_interactions_summary(ocel)
print("Interaction Summary:\n", interaction_summary.head(10))

otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
print("Event-to-Object Type Bindings:\n", etot)

# 2. Discover Multi-Dimensional OC-DFG
ocdfg = pm4py.discover_ocdfg(ocel)
pm4py.view_ocdfg(ocdfg)

# 3. Compare Object-Centric vs Flattened Frequency Metrics
# (A) Flatten log by Job and Machine
job_flat = pm4py.ocel_flattening(ocel, object_type="Job")
job_perf_dfg, j_start, j_end = pm4py.discover_performance_dfg(job_flat)

machine_flat = pm4py.ocel_flattening(ocel, object_type="Machine")
machine_perf_dfg, m_start, m_end = pm4py.discover_performance_dfg(machine_flat)

# Metric 1: Pure Event Frequency
event_freq = ocel.events['ocel:activity'].value_counts()
print("Metric 1 - Event Frequencies:\n", event_freq)

# Metric 2: Object-Participation Cardinality (Jobs per Event)
def get_object_cardinality(ocel_obj, activity_name, target_otype):
    rel_type = ocel_obj.relations[ocel_obj.relations['ocel:type'] == target_otype]
    merged = ocel_obj.events.merge(rel_type, on='ocel:eid')
    act_filtered = merged[merged['ocel:activity'] == activity_name]
    return act_filtered.groupby('ocel:eid')['ocel:oid'].nunique().describe()

print("\nMetric 2 - Job Cardinality for Batch Cure:\n", get_object_cardinality(ocel, "Batch Cure", "Job"))

# 4. Multi-Object Synchronization Delay Decomposition (No Machine-Gap Fallacy)
def compute_synchronization_dwell(ocel_obj):
    rel = ocel_obj.relations
    events = ocel_obj.events
    
    ready_ev = events[events['ocel:activity'].isin(['Stage Component', 'Ready for Batch'])].merge(
        rel[rel['ocel:type'] == 'Job'], on='ocel:eid'
    )[['ocel:oid', 'ocel:timestamp']].rename(columns={'ocel:timestamp': 'ready_time', 'ocel:oid': 'job_id'})
    
    cure_ev = events[events['ocel:activity'] == 'Batch Cure'].merge(
        rel[rel['ocel:type'] == 'Job'], on='ocel:eid'
    )[['ocel:oid', 'ocel:timestamp']].rename(columns={'ocel:timestamp': 'cure_time', 'ocel:oid': 'job_id'})
    
    sync_df = ready_ev.merge(cure_ev, on='job_id')
    sync_df['sync_dwell_min'] = (sync_df['cure_time'] - sync_df['ready_time']).dt.total_seconds() / 60.0
    return sync_df

print("\nComputed Job Synchronization Dwell:\n", compute_synchronization_dwell(ocel))
