## 1. Target definition

**Primary target: policy-conditional pathway risk from the lender’s observed application process.**

A single binary “default for every application” target is not observed: rejected, withdrawn, and many transferred applications were never exposed to the lender’s credit product. I would therefore use a finite-horizon multi-state target.

- **Unit of analysis:** an application-landmark pair. Every application receives a baseline score immediately after `Application Started`; updated scores may be produced after each of the first 1, 2, or 3 valid pre-decision events.
- **Prediction time:** landmark \(l\), immediately after the information in the prefix has become available to the lender.
- **Population:** applications still in the lender-controlled process and not already in an absorbing state at \(l\). The baseline population is all valid applications; later-prefix models are conditional on having reached that prefix without an earlier terminal event.
- **Process horizon:** 90 days after \(l\) to activate, reject, withdraw, transfer, or remain unresolved.
- **Credit-performance horizon:** for applications activated within those 90 days, observe default during the 90 days after `Account Activated`.
- **Primary outcome \(Y_l\):**

| Outcome state | Definition |
|---|---|
| `DEFAULT_90D` | Activated within 90 days after \(l\), then defaults within 90 days after activation |
| `ACTIVATED_NO_DEFAULT` | Activated within 90 days after \(l\), with an observed complete non-default 90-day post-activation window |
| `REJECTED` | Rejected before activation within 90 days after \(l\) |
| `WITHDRAWN` | Withdrawn before activation within 90 days after \(l\) |
| `TRANSFERRED` | Transferred before activation within 90 days after \(l\) |
| `PENDING_90D` | No activation, rejection, withdrawal, or transfer by day 90 |

The estimand is the vector of policy-conditional pathway probabilities:

\[
P(Y_l=j \mid H_l,\; \text{application active at } l,\; \pi_{\text{observed}})
\]

where \(H_l\) is the observed prefix and \(\pi_{\text{observed}}\) is the lender’s policy, operations, routing, and partner arrangement in force at the time.

The business-facing default quantity is the unconditional pathway probability:

\[
P(\texttt{DEFAULT\_90D}\mid H_l)
\]

not “default probability if every applicant were approved.” Rejected, withdrawn, transferred, and pending applications are not silently treated as non-default.

A credible alternative is the **conditional activated-account target**:

\[
P(D_{90}=1 \mid H_l,\; A_{90}=1)
\]

where \(A_{90}=1\) means that the application is eventually activated within the selected activation horizon under the observed policy. This answers: “Among applications that will be activated by this policy, which activated accounts will default?” It is useful for post-approval servicing or limit-setting, but it is selected by activation and should not be presented as a risk measure for every applicant.

Another alternative is a **time-to-default-after-activation** estimand among activated accounts, using survival methods with right censoring. That estimates default timing conditional on activation; it does not solve the unobserved counterfactual default risk of rejected applicants.

A counterfactual target such as “default risk if every application were activated” requires strong causal assumptions: consistency, positivity, no unmeasured confounding of activation and default, and valid follow-up for rejected or transferred cases. Those assumptions are not identified from this export alone.

## 2. Cohort construction

The source population is all 48,000 applications whose valid application start lies between 1 January 2024 and 31 December 2025.

### Inclusion rules

1. Retain applications with a valid `Application Started` event and a determinable case identifier.
2. Retain event records available as of the analysis cutoff, initially 15 February 2026.
3. Normalize known migration-era activity renames before prefixing, but retain a raw-activity audit field and migration indicator.
4. Remove only demonstrably duplicate events, for example exact duplicates on case, normalized activity, timestamp, source system, and resource. Do not collapse genuine repeated document requests or repeated credit-review loops.
5. Score at baseline for all valid starts. For later fixed-event-count models, include only cases that reached that prefix before a decision or other absorbing event.
6. Do not exclude applications merely because `risk_score`, requested amount, channel, or another valid pre-prefix covariate is missing; encode missingness.

### Exclusion and data-quality rules

- Exclude or separately quarantine cases with impossible timestamps, no valid start, or ambiguous event ordering at a score timestamp when no source event sequence or ingestion time exists.
- Do not merge transferred cases with partner cases in the primary cohort. The linkage table is incomplete and linkage is a sensitivity-analysis input, not a basis for silently relabeling transfers.
- Do not include cases whose label would only become known after the specified as-of cutoff in a complete-label classification analysis.
- For a conservative fully mature joint outcome cohort at cutoff \(C\), require:

\[
l + 90\text{ days (activation horizon)} + 90\text{ days (performance horizon)} + 35\text{ days (maximum feed lag)} \le C
\]

At 15 February 2026, this means landmarks must be approximately on or before 15 July 2025. Later landmarks remain useful for process-shift monitoring, but not for a fully mature primary default-outcome evaluation.

### Cohort flow at the current extract

| Current export disposition | Count | Status under the primary pathway target | Treatment |
|---|---:|---|---|
| Activated, observed default within 90 days | 2,700 | Candidate `DEFAULT_90D` label if activation is within the landmark’s 90-day activation horizon | Observed activated branch |
| Activated, observed non-default within 90 days | 18,900 | Candidate `ACTIVATED_NO_DEFAULT` label if complete follow-up is valid | Observed activated branch |
| Rejected | 9,100 | `REJECTED` competing pathway if rejection occurs within the process horizon | Not non-default |
| Withdrawn | 5,700 | `WITHDRAWN` competing pathway | Not non-default |
| Transferred | 2,900 | `TRANSFERRED` competing pathway in primary analysis | About 60% linkable for sensitivity analysis |
| Still open at extraction | 5,100 | `PENDING_90D` if observable through day 90; otherwise administratively censored | Never label as non-default |
| Activated but 90-day outcome/feed not mature | 3,600 | Delayed-label, right-censored, or permanently missing-outcome branch | Not non-default |
| **Total applications started** | **48,000** |  |  |

The supplied aggregate counts are case-level statuses at the current extract, not final landmark-specific labels. For example, an application may be in the 21,600 activated export but have activated more than 90 days after a particular early landmark; it would then be `PENDING_90D` at that landmark rather than a `DEFAULT_90D` pathway outcome.

## 3. Censoring and missing-label strategy

The study should explicitly distinguish five mechanisms.

1. **Ordinary administrative right censoring.**  
   A case may not be observed through the 90-day activation horizon, or an activated account may not yet have completed its 90-day post-activation performance window by the extract date. This is not a negative default label.

2. **Delayed labels.**  
   The outcome feed arrives 7–35 days after the nominal 90-day horizon. A nominally complete account is not necessarily label-complete at extraction. `label_available_at`, not merely activation date plus 90 days, should govern whether the label was observable at a historical as-of date.

3. **Selection through activation.**  
   Activation is not ordinary censoring in the primary target; it is a substantive process transition. It becomes selection when estimating a conditional target among activated accounts. The activated-only ML export estimates a selected population, not every application.

4. **Transfers.**  
   For the lender-platform primary target, transfer is a competing pathway because the lender stops controlling the case. If the intended target is applicant-level default across platforms, transfer becomes partly missing follow-up because only about 60% can be linked.

5. **Permanently missing outcome feeds.**  
   Partner-originated activated accounts have elevated probability of never receiving an outcome feed. Waiting longer does not necessarily solve this. Such cases should be represented as missing outcome ascertainment, not inferred non-defaults.

### Primary analysis strategy

Use a staged multi-state analysis with a conservative maturity cohort.

- First model the competing pathway probabilities through day 90: activation, rejection, withdrawal, transfer, or pending.
- Then, among activated cases, model default versus observed non-default over the 90 days after activation.
- Combine them to obtain:

\[
P(\texttt{DEFAULT\_90D}\mid H_l)
=
P(A_{90}=1\mid H_l)
\times
P(D_{90}=1\mid A_{90}=1,H_l)
\]

- Restrict the main complete-label analysis to landmarks with worst-case administrative maturity: 90 days for activation, 90 days for performance, and 35 days for label delay.
- Treat an activated account with no mature outcome feed as censored/missing in the default transition, not as `ACTIVATED_NO_DEFAULT`.
- Estimate an outcome-ascertainment model for the activated branch, using covariates available by activation such as source system, partner origin, channel, region, activation date, and pre-activation prefix features. Use inverse-probability-of-censoring weights or a weighted likelihood under a missing-at-random conditional-on-observed-history assumption.
- Report uncertainty using case-level and calendar-block bootstrap intervals, not only point estimates.

### Sensitivity analyses

1. **Missing outcome feed sensitivity.**  
   Compare:
   - complete observed outcomes;
   - inverse-probability weighted outcomes;
   - bounded analyses in which missing-feed accounts have default rates from 0% to 100%;
   - delta-adjusted analyses where missing-feed default odds are, for example, 0.5, 1, 2, and 3 times the observed-feed odds within source-system strata.

2. **Transfer handling sensitivity.**  
   Compare:
   - primary treatment: transfer as a competing lender-platform outcome;
   - linked-transfer continuation for the approximately 60% linked subgroup;
   - linkage-weighted analysis only if linkage plausibly depends on observed variables with sufficient overlap.

3. **Activation-horizon sensitivity.**  
   Repeat the pathway definition using 30-, 90-, and 180-day activation horizons. This shows whether conclusions depend on the arbitrary but operationally necessary finite process horizon.

4. **Censoring-model sensitivity.**  
   Compare weighted and unweighted estimates and inspect weight distributions, effective sample size, overlap, and source-system positivity.

### Assumption status

| Assumption or diagnostic | Status |
|---|---|
| Timestamp ordering, label-delay arithmetic, duplicate-event rate | Testable from data, subject to source-system correctness |
| Whether observed outcome-feed delay differs by channel, region, source system, partner origin, or prefix risk | Partially testable |
| Positivity for label-observation weights | Partially testable through overlap and extreme weights |
| Conditional independent censoring / missing at random after observed covariates | Fundamentally untestable |
| Linked transfers representing unlinked transfers | Fundamentally untestable without stronger linkage data |
| Rejected applicants’ default risk under activation | Fundamentally unidentifiable from these data without causal assumptions or experimental/quasi-experimental variation |

## 4. Prefix extraction

Prefixes must be created from an as-of view of the event stream.

For every score time \(l\), include only events that:

1. occurred at or before \(l\);
2. were available to the operational system at or before \(l\);
3. occur before any final decision, contract, activation, collections, or default event;
4. have a deterministic order within the case.

If `data_extract_time` is merely a file-level metadata field rather than an event-ingestion timestamp, it is insufficient for exact historical replay. A true production-grade study should request event availability or ingestion timestamps.

### Fixed event-count prefixes

Use separate landmark models for the first \(K\) valid pre-decision events, for example \(K=1,2,3\).

- The baseline score after `Application Started` is available for every valid application.
- The score after the third event is conditional on surviving and remaining in process long enough to reach the third event.
- Do not pad short traces with artificial events.
- Do not discard short terminal cases from the baseline cohort merely because they cannot reach a later prefix.
- Report results separately by prefix length; do not pool repeated prefixes as independent rows without clustered uncertainty handling.

### Elapsed-time prefixes

For elapsed-time landmarks such as 24 or 72 hours after start:

- Include only events observed and available by `start_time + elapsed_time`.
- Produce a score only if the application is still active and lender-controlled at that landmark.
- Cases rejected, withdrawn, transferred, or activated before that elapsed landmark do not receive that later update; they still belong in the baseline analysis.
- `documents_total` snapshots cannot be used unless they are reconstructed from document events with timestamps no later than the exact landmark.

### Rework loops, migration, and duplicate events

- Preserve repeated `Request Documents -> Credit Review` loops. Their count, timing, and recurrence are legitimate predictive process features.
- Normalize renamed activities introduced on 15 October 2025 using a version-controlled mapping reviewed by process owners.
- Keep a migration-period indicator and raw activity-name audit.
- Deduplicate only clearly duplicated records. Removing all same-day or same-activity events would incorrectly erase legitimate rework.
- If multiple events share a timestamp and the source does not provide a reliable sequence key, either score immediately before that timestamp or exclude the ambiguous landmark from model fitting and report its count. A stable CSV row order is not a valid causal event order.

## 5. Process-aware features

All features must be available at the landmark; the categories below should be retained separately in the feature specification.

### Static case attributes

Available only if recorded at or before the relevant prefix:

- `case:channel`
- `case:region`
- requested amount and missingness indicator
- application-start calendar date, weekday, month, holiday indicator
- policy regime indicator: pre/post 1 July 2025
- migration regime indicator: pre/post 15 October 2025
- source-system/origination-route indicator, if known at application start

### Prefix-derived features

Computed only from the prefix:

- event count, distinct activity count, current activity
- prefix variant or sequence encoding learned from training data only
- direct-following transition indicators, such as `KYC -> Credit Review`
- count of document requests, document uploads, and review re-entries
- count and duration of `Request Documents -> Credit Review` loops
- elapsed time since application start
- time since KYC completion, if completed
- inter-event gaps: mean, maximum, most recent, and business-hour-adjusted gaps
- waiting time before the first and subsequent credit-review events
- last valid pre-prefix `risk_score`, number of prior score updates, score change from first observed value, and missingness
- number of resources or queues encountered in the prefix
- whether the case was rerouted, reassigned, or returned for rework before the score time

### Features requiring historical reference data

These require strict temporal construction and should be fitted only on earlier training data.

- queue workload at the score time, computed from cases active as of that time rather than from future completions
- resource experience as of the event time, reconstructed from earlier events only
- historical median service or waiting times by channel, region, resource team, and activity, calculated from prior training cases
- deviation of the current prefix duration from historically expected duration
- frequency encoding of prefix variants or transitions based only on earlier training data
- resource-level outcome statistics only if lagged, maturity-filtered, temporally cross-fitted, and carefully governed; these are usually high-risk for leakage and fairness concerns

The study should avoid using final decision fields as process features. A final-limit field or decision rationale is not an early-warning signal if it is populated by the very decision that determines activation.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after final credit decision; often nearly determines exposure | Must be set and source-available before the landmark, which is not true for early prefixes | Drop for early-warning model | It is downstream of the credit decision |
| `decision_reason` | Direct decision leakage; may encode Reject/Accept outcome | Available only after or at decision | Drop | It reveals a competing target state |
| `collection_status` | Updated after activation and may directly reveal default | Never valid before pre-activation prediction time | Drop | Direct post-outcome leakage |
| Future events including `Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded` | Future-state and target leakage | Event timestamp and ingestion time must be no later than landmark | Drop from prefix; use only for endpoint construction | These events occur after the intended score time |
| `documents_total` nightly snapshot | May include documents added later the same day | Reconstruct from document events available no later than exact timestamp; otherwise do not use | Repair or drop | Calendar-day snapshots violate exact as-of semantics |
| Updated `risk_score` | Warehouse may expose a latest score rather than the score known at the prefix | Use last event-versioned score with event and availability time no later than landmark | Keep after repair | The score can be valid if versioned and time-aligned |
| Resource experience at extraction time | Uses future work history and may encode later staffing assignments | Reconstruct experience from events strictly before the event time; fit mappings on earlier training data | Repair | Extraction-time tenure leaks future information |
| `default_90d` | Target leakage if repeated onto early event rows | Never include as a feature | Drop from feature table | Endpoint only |
| `label_available_at` | Can leak label completion and operational delay; not a borrower feature | Use only to decide whether label was known at historical cutoff | Endpoint/censoring metadata only | Necessary for as-of label construction |
| `data_extract_time` | May be a post-hoc export timestamp rather than event availability | Use only if it truly denotes record availability | Audit metadata; otherwise do not model | Cannot substitute for ingestion time without validation |
| `case:channel`, `case:region`, requested amount | May be backfilled or revised after application start | Use only values recorded by the landmark; preferably immutable start-event version | Keep after provenance check | Legitimate early context if time-versioned |
| `source_system` | May proxy transfer route, feed completeness, or partner selection | Use only source known by landmark; monitor missing-label disparity | Keep with monitoring | Operationally relevant but may expose ascertainment bias |
| Activity name after migration | Same process step may have renamed labels; unseen variants may cause drift | Normalize using audited mapping; retain migration indicator | Repair | Needed for comparable prefixes across migration |

## 7. Validation design

A random case split is misleading because it mixes:

- pre- and post-policy-change applications;
- pre- and post-migration event vocabularies;
- different label-maturity regimes;
- related transferred or duplicate cases;
- the same resource teams and operational conditions across train and test;
- repeated prefixes from the same application.

### Temporal split and backtesting

Use a forward-chaining design based on **case start time**, with all preprocessing learned only from earlier periods.

At the 15 February 2026 cutoff, conservative full joint-label maturity requires landmarks around 15 July 2025 or earlier.

A realistic first evaluation plan is:

| Role | Case start period | Interpretation |
|---|---|---|
| Training | 1 Jan 2024 – 31 Dec 2024 | Historical pre-policy baseline |
| Validation | 1 Jan 2025 – 30 Apr 2025 | Hyperparameter selection, threshold selection, calibration |
| Pre-policy test | 1 May 2025 – 30 Jun 2025 | Unseen but broadly same-policy performance |
| Policy-transition stress set | 1 Jul 2025 – about 15 Jul 2025 | Limited mature post-policy evidence |
| Migration period | 15 Oct 2025 onward | Process-shift diagnostics only at current extract; no mature primary outcome claims |

There is not enough fully mature follow-up at the current extract to claim robust outcome performance after the 15 October 2025 migration. A post-migration outcome evaluation should wait for a later extract. For example, a landmark on 15 October 2025 needs roughly until 18 May 2026 under the conservative 90 + 90 + 35 day rule.

For each historical backtest date:

1. freeze events to those available at that date;
2. construct prefixes only from those events;
3. reveal labels only if `label_available_at` is no later than the backtest date;
4. fit preprocessing, encoders, imputation, calibration, and reference features using prior data only;
5. evaluate on the next calendar block.

If true event-ingestion timestamps are unavailable, exact historical feature replay cannot be guaranteed; this must be documented.

### Metrics

For the primary multi-state target:

- class-specific Brier scores and multiclass Brier score;
- weighted multinomial log loss where outcome-ascertainment weights are used;
- calibration-in-the-large, calibration slope, reliability curves, and expected calibration error for:
  - `DEFAULT_90D`,
  - activation,
  - transfer,
  - rejection/withdrawal;
- one-vs-rest AUROC and PR-AUC for `DEFAULT_90D`, reported as secondary discrimination measures;
- cause-specific cumulative-incidence calibration if fitting a time-to-event competing-risk model;
- time-dependent Brier score and integrated Brier score with IPCW for survival-style analyses;
- decision-curve or net-benefit analysis only after an intervention policy and cost structure are specified.

Report confidence intervals using clustered resampling by case and, where feasible, by time block.

### Policy, migration, and subgroup checks

Evaluate calibration and outcome ascertainment by:

- policy period: before and after 1 July 2025;
- migration period: before and after 15 October 2025;
- channel, region, requested amount band;
- source system and partner-originated status;
- linked versus unlinked transfers;
- prefix length or elapsed-time landmark;
- label-observed versus label-missing activated accounts.

Monitor distribution shift in:

- activity frequencies and normalized variants;
- document-loop counts;
- event timing and waiting times;
- risk-score missingness and distribution;
- activation, transfer, and label-availability rates;
- source-system composition;
- calibration drift, not only feature drift.

The post-policy and post-migration periods should not merely be added to a random holdout. They are transportability tests under changed decision thresholds, changed process instrumentation, and potentially changed selection into activation.

## 8. Limitations and decision-use boundary

This study can estimate predictive associations for the observed lender process:

- which early prefixes are associated with later activation, rejection, transfer, pending status, and observed default;
- the probability of a default pathway under the lender’s historical policy and data-capture system;
- uncertainty caused by delayed labels, transfer, and missing outcome feeds.

It cannot claim:

- that rejected applications are low default-risk borrowers;
- that `P(DEFAULT_90D | prefix)` is the default probability if every applicant were approved;
- that a high-risk score causes default;
- that policy changes or resource interventions would have the same effect as the observed historical associations;
- that unlinked transferred applicants have no default outcome elsewhere.

Activation is a selection mechanism. A model trained only on the 21,600 matured activated accounts answers a conditional activated-account question, even if it is numerically accurate within that selected export.

Deployment can change the data-generating process in several ways:

1. **Acceptance and limit feedback.**  
   If model scores affect accept/reject decisions, limits, pricing, or documentation demands, the future activated population and observed default rate will change.

2. **Operational intervention feedback.**  
   Routing high-risk applications to manual review, requesting more documents, or accelerating KYC changes the event sequence, waiting times, resource assignments, and potentially the borrower’s default outcome.

3. **Transfer and partner-routing feedback.**  
   Sending high-risk or hard-to-process cases to partners changes both exposure and missing-outcome rates, especially if partner feeds remain incomplete.

4. **Resource allocation feedback.**  
   Using scores to prioritize queues changes queue length, service time, rework, and resource experience, invalidating historical process-feature relationships.

5. **Policy and system changes.**  
   Threshold changes, activity renaming, new risk-score versions, and source-system migrations can alter both selection into activation and feature meaning.

The deployment boundary should therefore be early-warning and operational triage under monitored policy conditions, not unqualified automated credit denial or a causal estimate of borrower default risk under universal approval.

## 9. PM4Py-oriented Python implementation skeleton

```python
import numpy as np
import pandas as pd
import pm4py

# -------------------- Configuration --------------------
CASE = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"
CUTOFF = pd.Timestamp("2026-02-15", tz="UTC")
OBS_START = pd.Timestamp("2024-01-01", tz="UTC")
OBS_END = pd.Timestamp("2025-12-31 23:59:59", tz="UTC")

PREFIX_LEN = 3
ACTIVATION_HORIZON_DAYS = 90
DEFAULT_HORIZON_DAYS = 90
MAX_FEED_DELAY_DAYS = 35

# Validate these mappings with process owners; retain raw activity for audit.
ACTIVITY_MAP = {
    "KYC Check Completed": "Identity/KYC Check",
    "KYC verification": "Identity/KYC Check",
    "Credit Review v2": "Credit Review",
    "Documents Requested": "Request Documents",
}

BARRIER_ACTIVITIES = {
    "Accepted", "Rejected", "Withdrawn", "Transferred",
    "Contract Signed", "Account Activated",
    "Collections Contact", "Default Recorded",
}

STATIC = ["case:channel", "case:region", "case:requested_amount"]
FORBIDDEN_FEATURES = {
    "final_limit", "decision_reason", "collection_status",
    "default_90d", "label_available_at", "data_extract_time",
    "documents_total",
}

# -------------------- Read, normalize, and freeze as-of --------------------
date_cols = [TS, "label_available_at", "data_extract_time"]
raw = pd.read_csv("applications_events.csv", parse_dates=date_cols)

for col in date_cols:
    raw[col] = pd.to_datetime(raw[col], utc=True, errors="coerce")

raw[ACT] = raw[ACT].replace(ACTIVITY_MAP)
raw["default_90d"] = pd.to_numeric(raw["default_90d"], errors="coerce")
raw["risk_score"] = pd.to_numeric(raw["risk_score"], errors="coerce")

# PM4Py formatting is used for process discovery/prefix QA, not as a feature source.
formatted = pm4py.format_dataframe(
    raw.copy(), case_id=CASE, activity_key=ACT, timestamp_key=TS
)

# Assumption: data_extract_time is record availability. Replace with ingestion time
# if data_extract_time is only file-level metadata.
visible = formatted[TS].le(CUTOFF)
visible &= (
    formatted["data_extract_time"].isna()
    | formatted["data_extract_time"].le(CUTOFF)
)

dedupe_cols = [c for c in [CASE, ACT, TS, "org:resource", "source_system"]
               if c in formatted.columns]
events = (
    formatted.loc[visible]
    .drop_duplicates(dedupe_cols, keep="first")  # narrow duplicate removal only
    .sort_values([CASE, TS], kind="mergesort")
    .reset_index(drop=True)
)

# Restrict source population by application start observed in the stated window.
case_start_all = events.groupby(CASE)[TS].min()
eligible_cases = case_start_all[
    case_start_all.between(OBS_START, OBS_END, inclusive="both")
].index
events = events.loc[events[CASE].isin(eligible_cases)].copy()
events["event_order"] = events.groupby(CASE).cumcount()

# -------------------- Case-level endpoint and maturity information --------------------
def first_activity(activity):
    return events.loc[events[ACT].eq(activity)].groupby(CASE)[TS].min()

cases = pd.DataFrame(index=pd.Index(events[CASE].unique(), name=CASE))
cases["case_start"] = events.groupby(CASE)[TS].min()
cases["activation"] = first_activity("Account Activated")
cases["rejected"] = first_activity("Rejected")
cases["withdrawn"] = first_activity("Withdrawn")
cases["transferred"] = first_activity("Transferred")
cases["terminal"] = cases[["rejected", "withdrawn", "transferred"]].min(axis=1)
cases["censor_at"] = CUTOFF
cases["max_default_label_due"] = (
    cases["activation"]
    + pd.Timedelta(days=DEFAULT_HORIZON_DAYS + MAX_FEED_DELAY_DAYS)
)

# Labels are endpoint data only: never carried into the feature frame.
label_rows = events.loc[
    events["default_90d"].notna()
    & events["label_available_at"].notna()
    & events["label_available_at"].le(CUTOFF),
    [CASE, "default_90d", "label_available_at"]
].copy()

conflicts = label_rows.groupby(CASE)["default_90d"].nunique().gt(1).sum()
print(f"Conflicting observed default labels requiring audit: {conflicts}")

label_case = (
    label_rows.sort_values([CASE, "label_available_at"], kind="mergesort")
    .groupby(CASE)
    .tail(1)
    .set_index(CASE)
    .rename(columns={
        "default_90d": "observed_label",
        "label_available_at": "label_seen_at"
    })
)
cases = cases.join(label_case[["observed_label", "label_seen_at"]], how="left")

cases["raw_status"] = np.select(
    [
        cases["activation"].notna() & cases["observed_label"].notna(),
        cases["activation"].notna(),
        cases["rejected"].notna(),
        cases["withdrawn"].notna(),
        cases["transferred"].notna(),
    ],
    [
        "activated_label_observed",
        "activated_label_unavailable",
        "rejected",
        "withdrawn",
        "transferred",
    ],
    default="still_open_or_unobserved",
)
print("\nCase-level cohort counts:")
print(cases["raw_status"].value_counts(dropna=False))
print(f"Cases in stated observation window: {len(cases)}; expected source total: 48000")

# -------------------- Pre-decision traces and PM4Py prefix audit --------------------
barrier_order = (
    events.loc[events[ACT].isin(BARRIER_ACTIVITIES)]
    .groupby(CASE)["event_order"]
    .min()
    .rename("_barrier_order")
)
predecision = events.join(barrier_order, on=CASE)
predecision = predecision.loc[
    predecision["_barrier_order"].isna()
    | predecision["event_order"].lt(predecision["_barrier_order"])
].drop(columns="_barrier_order")

# PM4Py is given only process columns; labels and post-outcome fields are excluded.
if len(predecision):
    process_df = pm4py.format_dataframe(
        predecision[[CASE, ACT, TS]].copy(),
        case_id=CASE, activity_key=ACT, timestamp_key=TS
    )
    process_log = pm4py.convert_to_event_log(process_df)
    pm4py_prefix_log = pm4py.get_prefixes_from_log(
        process_log, length=PREFIX_LEN
    )  # process QA / visualization artifact only

prefix_sizes = predecision.groupby(CASE).size()
prefix_cases = prefix_sizes[prefix_sizes.ge(PREFIX_LEN)].index
fixed = (
    predecision.loc[predecision[CASE].isin(prefix_cases)]
    .groupby(CASE, group_keys=False)
    .head(PREFIX_LEN)
    .copy()
)

if len(fixed):

def classify_pathway(row):
    full_maturity = (
        row["landmark"]
        + pd.Timedelta(days=ACTIVATION_HORIZON_DAYS
                       + DEFAULT_HORIZON_DAYS
                       + MAX_FEED_DELAY_DAYS)
    )
    if full_maturity > CUTOFF:
        return "ADMIN_CENSORED"

    route_end = row["landmark"] + pd.Timedelta(days=ACTIVATION_HORIZON_DAYS)
    candidates = [
        (row["activation"], "ACTIVATED"),
        (row["rejected"], "REJECTED"),
        (row["withdrawn"], "WITHDRAWN"),
        (row["transferred"], "TRANSFERRED"),
    ]
    candidates = [(t, state) for t, state in candidates
                  if pd.notna(t) and row["landmark"] < t <= route_end]

    if not candidates:
        return "PENDING_90D"

    earliest = min(t for t, _ in candidates)
    if sum(t == earliest for t, _ in candidates) > 1:
        return "AMBIGUOUS_ROUTE_TIME"

    route = next(state for t, state in candidates if t == earliest)
    if route != "ACTIVATED":
        return route

    if pd.isna(row["observed_label"]):
        return "MISSING_OUTCOME_FEED"
    return "DEFAULT_90D" if int(row["observed_label"]) == 1 else "ACTIVATED_NO_DEFAULT"

target_frame["target"] = target_frame.apply(classify_pathway, axis=1)
```
