## 1. Conformance semantics

The norm is **closed-world only for two things**: explicitly forbidden edges and mandatory relations whose stated scope clearly applies. Everything else is open-world. This means:

- **Forbidden behavior**: an observed relation appears in N3, T6, or E10, and the relevant objects/events are in scope. The relation itself is enough to raise a violation, though data-quality explanations must still be checked.
- **Missing mandatory behavior**: a relation required by N1, N4, T1, T2, or E1–E8 is absent **and** the case has reached the point in its lifecycle where the relation should exist. Because several norms use “eventually” semantics, absence from a directly-follows graph is not by itself proof of noncompliance.
- **Unexpected but unregulated behavior**: a relation is not named in the norm, and the norm does not forbid it. Under open-world semantics, it is not automatically a violation.
- **Typical-pattern absence**: a relation has status “typical”. It is desirable and common, but legitimate exceptions are allowed. Low counts or missing edges are therefore not automatic violations, though they can signal drift.
- **Likely data-quality error**: an absurd or improbable relation exists in the log, often because of identifier reuse, ETL mistakes, or incomplete object linking. The raw fact may violate a norm, but the business interpretation should be tentative.
- **Abstraction mismatch**: the norm means “eventually” while the observed graph is a directly-follows approximation. An intervening event can make a mandatory relation disappear from the OC-DFG without violating the norm.
- **Insufficient evidence**: the summary does not contain enough information to decide whether the event-level lifecycle satisfies or violates the scope of a mandatory norm.

Because the norm is open-world with respect to unspecified edges, “not in the normative graph” is never a reason to call something noncompliant. Conversely, mandatory and forbidden edges require checking scope, timing, and event-level object relations, not just aggregate counts.

## 3. Detailed reasoning by model family

### OC-DFG

The OC-DFG shows, for each object instance, which event types directly follow other event types. It is useful for discovering dominant paths, but it is **not** a complete temporal reachability model.

What it can establish:
- That two event types were observed as direct successors for the same object.
- Aggregate confidence in a process path, e.g., 98 of 100 Create Order objects have Validate Order as the next event.

What it cannot establish:
- That an expected relation is absent forever.
- That an event occurring later after an intermediate event violates a mandatory “eventually” norm.
- That a forbidden relation is truly forbidden without checking actual event ordering, object identity, and event attributes.

The counts affect interpretation:
- 2 missing `Create Order -> Validate Order` edges are not necessarily 2 violations of N1, because N1 is explicitly eventual.
- 2 missing `Pack Package -> Dispatch Package` edges are not necessarily violations of N4 for the same reason.
- 2 observed `Cancel Order -> Dispatch Package` edges are serious because N3 is a direct prohibition.

The danger of interpreting an “eventually expected” rule as a directly-follows rule is that **any legitimate intermediate event** removes the edge from the OC-DFG. A manual compliance review, an item addition, or an inspection can all sit between creation and validation. If the conformance check is based only on the directly-follows graph, it will produce false positives. The same relation can be conforming at the eventual-lifecycle abstraction and suspicious at the directly-follows abstraction.

### OTG

The OTG summarizes co-occurrence of object types in events. It does not encode event types or temporal order.

What it can establish:
- That an object of type Order and an object of type Item occurred in at least one shared event.
- Aggregate presence of interactions such as Invoice–Payment.

What it cannot establish:
- Whether the interaction was caused by a `Create Order`, `Add Item`, `Dispatch Package`, or some unmodelled event type.
- Whether each mandatory event has the required object relations.
- Whether a missing relation is a real process violation or merely a missing object link.

For T1 and T2, the observed OTG weights look conforming:
- `(Order, object_interaction, Item)` = 1450
- `(Package, object_interaction, Delivery)` = 200

But the ET-OT information suggests the underlying event-level truth may differ: two Add Item events lack an Order, and two Dispatch Package events lack a Delivery. The OTG can still show the same aggregate because it counts all interactions, not only those from the relevant event type. This is the clearest example of **conforming at one abstraction and suspicious at another**. OTG-level conformance should never be used to close an ET-OT or event-level violation.

### ET–OT

ET-OT edges connect event types to object types and are the closest summary to the mandatory rules E1–E10.

What it can establish:
- Whether a `Create Order` event relates to an Order object.
- Whether `Record Payment` events relate to Payment and Invoice objects.
- Whether `Dispatch Package` events relate to Package and Delivery objects.

What it cannot establish:
- Whether a missing relation is a data-quality omission or a real process deviation.
- Whether a mandatory relation is missing because the norm’s scope does not apply.
- Whether an event with multiple objects has the correct number of object links.

The ET-OT counts reveal the most serious gaps:
- `Add Item -> Order` = 1448 while `Add Item -> Item` = 1450.
- `Dispatch Package -> Delivery` = 198 while `Dispatch Package -> Package` = 200.
- `Record Payment -> Payment` = 93 while `Record Payment -> Invoice` = 92.

These are aggregate differences, so they do not by themselves prove how many distinct events are affected. If every event has exactly one object of the relevant type, then the missing counts are exactly two, two, and one events. Event-level inspection is required.

The `Sensor Heartbeat -> Invoice` edge is forbidden by E10. The additional context strongly suggests this is a data-quality error caused by identifier reuse. Even so, the raw edge is a conformance exception and must be quarantined until repaired.

## 4. Mandatory, forbidden, typical, and unregulated behavior

### Mandatory behavior

These must hold when the stated scope applies:

- N1: All 100 newly created Orders should eventually be validated. The 2 missing direct edges are only violations if event-level reachability also shows no validation.
- N4: All 200 externally shipped Packages should eventually be packed before dispatch. The 2 missing direct edges are only violations if event-level reachability shows no pack before dispatch.
- E1: Every Create Order event relates to an Order. Observed 100/100.
- E2: Every Add Item event relates to an Order. Observed 1448/1450.
- E3: Every Add Item event relates to an Item. Observed 1450/1450.
- E4: Every Pack Package event relates to a Package. Observed 200/200.
- E5: Every Dispatch Package event relates to a Package. Observed 200/200.
- E6: Every Dispatch Package event relates to a Delivery. Observed 198/200.
- E7: Every Record Payment event relates to a Payment. Observed 93/93.
- E8: Every Record Payment event relates to an Invoice, unless explicitly typed as unapplied cash. Observed 92/93, and the single non-conforming event is not typed as unapplied cash.

T1 and T2 are mandatory in the sense that Add Item and Dispatch Package interactions must include the relevant object types, but the OTG summary alone is insufficient to confirm event-level compliance.

### Forbidden behavior

- N3: `Cancel Order -> Dispatch Package` observed 2 times.
- T6: `(Order, object_cobirth, Payment)` observed 1 time.
- E10: `Sensor Heartbeat -> Invoice` observed 1 time.

The E10 finding is likely a data-quality error, but if a real sensor event is ever linked to an Invoice, it is forbidden.

### Typical behavior

- N2: `Validate Order -> Close Order` is typical. Observed 83 Orders; the remaining validated orders may still be open.
- N5: `Issue Invoice -> Record Payment` is typical. Observed 92 of 110; 4 write-offs and 14 invoices without observed successors are acceptable or require further time-based analysis.
- T3: `(Invoice, object_interaction, Payment)` is typical. Unapplied cash is allowed, but the one untyped Record Payment event without an Invoice should be clarified.

### Unregulated behavior

These are not governed by this norm and are therefore not violations solely because they are unmodelled:

- `Create Order -> Manual Compliance Review` (3 Orders).
- `Validate Order -> Issue Invoice` (72 Orders).
- `Reopen Order -> Close Order` (1 Order).
- `Manual Compliance Review -> Customer` (3).
- `Manual Compliance Review -> RiskCase` (3).
- `(Order, object_interaction, Customer)` = 100.
- `(Order, object_interaction, RiskCase)` = 3.
- `(Package, object_codeath, Delivery)` = 7.

These become noncompliant only if another policy or norm governs them. This norm is silent.

## 6. Norm-completeness assessment

### Gap 1: Definition of “standard Order” in N1
- Risk: Orders that are not standard cannot be identified, so the two missing `Create Order -> Validate Order` edges may be outside scope or genuine violations.
- Clarification: Define standard order types, creation channels, and lifecycle entry events.
- Status: Mandatory.

### Gap 2: Directly-follows versus eventual semantics
- Risk: A directly-follows implementation will flag legitimate intermediate events as violations.
- Clarification: State explicitly that N1 and N4 mean “eventually before a defined endpoint” unless the relation is labelled as directly-follows.
- Status: Mandatory for the eventual relation; directly-follows is only a monitoring approximation.

### Gap 3: Scope of “Packages intended for external shipment” in N4
- Risk: Internal packages or non-shipment packages may be counted as violations.
- Clarification: Define the attribute or object type that marks a package as “intended for external shipment”.
- Status: Mandatory for external packages; explicitly unspecified for internal packages.

### Gap 4: N5 exceptions are not typed
- Risk: Write-offs, credit notes, and open credit terms cannot be distinguished from missing payments.
- Clarification: Require event types or attributes such as `write_off`, `credit_note`, or `open_credit`.
- Status: Typical.

### Gap 5: E8 unapplied-cash exception is not event-type encoded
- Risk: One valid unapplied cash payment may be reported as a violation because it is not typed.
- Clarification: Require an explicit event type or attribute for “unapplied cash”; otherwise the invoice relation is mandatory.
- Status: Typical as an exception under explicit typing; mandatory otherwise.

### Gap 6: OTG counts can mask ET-OT violations
- Risk: An aggregate OTG conformance result may hide missing object relations at the event level.
- Clarification: Mandatory object interactions should be checked at the event-object relation level, not only with OTG aggregates.
- Status: Mandatory.

### Gap 7: N6 Reopen Order is unspecified
- Risk: Reopening can extend an order lifecycle indefinitely, and no downstream expectation is defined.
- Clarification: Decide whether reopening resets validation or closure requirements; if allowed, define a typical path such as `Reopen -> Validate -> Close`.
- Status: Explicitly unspecified or typical, depending on business policy.

### Gap 8: No tolerance bands for typical relations
- Risk: It is impossible to know when a falling typical ratio becomes problematic.
- Clarification: Define monitoring thresholds or statistical bands for typical relations, without turning them into mandatory rules.
- Status: Typical.

## 7. Investigation and remediation plan

### Immediate containment
- For T6 (Order–Payment cobirth): quarantine the affected event and object identities. Determine whether this came from a system bug, API misuse, or deliberate bypass.
- For N3 (Cancel Order -> Dispatch Package): stop any further dispatch activity for the two affected orders. If the packages have already shipped, initiate recall/return and customer notification.
- For E10 (Sensor Heartbeat -> Invoice): suppress or quarantine the false edge so it is not reported as a financial-object sensor event.

### Data repair
- Fix the identifier-join logic that created the `Sensor Heartbeat -> Invoice` relation.
- Link the two missing Delivery objects for `Dispatch Package` using the carrier references in the event attributes.
- Identify the two Add Item events without an Order object and either add the correct order link or reclassify the events if they were not really Add Item events.
- Type the single Record Payment event without an Invoice as unapplied cash if finance confirms it is legitimate.

### Process investigation
- Trace the T6 event to its source system and determine why an Order and Payment were created in the same business event.
- Investigate the timing and approval chain around the two cancelled orders whose packages were dispatched.
- For N1 and N4, reconstruct full per-object event sequences. Only flag missing mandatory behavior if no eventual validation or no pack-before-dispatch exists.
- Review the four write-offs and fourteen invoices without successors to confirm they are documented legitimate exceptions.

### Norm revision
- Add explicit semantics for “eventually” versus “directly-follows”.
- Define scope qualifiers for “standard Order” and “externally shipped Package”.
- Add typed exceptions for unapplied cash, write-offs, credit notes, and open credit terms.
- Clarify whether Reopen Order should reset mandatory expectations.

### Monitoring
- Run event-level conformance checks for mandatory ET-OT and forbidden relations on every new event batch.
- Monitor typical relations with tolerance bands and aging thresholds.
- Alert specifically on forbidden edges: cancel-to-dispatch, order-payment cobirth, sensor-to-financial-object.
- Keep unregulated behaviors such as Manual Compliance Review, RiskCase relations, and codeath in a separate watch list, not in the violation report.

The two highest-severity findings are **T6** and **N3**. Both are forbidden and have direct business impact. The Sensor Heartbeat edge is also forbidden, but the available context strongly indicates a data-quality error, so the immediate priority is containment and repair rather than process redesign.

## 8. Uncertainty statement

Robust conclusions are that the forbidden T6 and N3 relations were observed in the supplied summary, the E10 sensor-to-invoice edge exists at the raw data level, and several mandatory ET-OT relations are incomplete at the aggregate level. It is also robust that unspecified relations such as `Reopen Order -> Close Order`, Manual Compliance Review, RiskCase interactions, and Package–Delivery codeath are not violations merely because they are unmodelled.

Conclusions that depend on the norm’s incompleteness include whether the two missing `Create Order -> Validate Order` edges and the two missing `Pack Package -> Dispatch Package` edges are actual violations. They may be valid under eventual semantics. Conclusions that depend on data-quality issues include the Sensor Heartbeat–Invoice link, the missing Delivery objects, the missing Order links in Add Item events, and the untyped unapplied cash event.

Graph summaries alone cannot decide whether a missing object relation is an ETL omission, an event-type misclassification, or a genuine process violation. They also cannot prove temporal ordering, eventual compliance, or scope qualification. Event-level inspection is required before any final legal or business determination is made.
