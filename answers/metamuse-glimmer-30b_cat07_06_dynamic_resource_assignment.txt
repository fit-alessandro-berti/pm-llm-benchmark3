# 1. Objectives and constraints

**Objectives**
* Minimize SLA risk for urgent/high priority cases
* Reduce rework and error risk via skill-match
* Preserve continuity of case ownership to avoid handover waiting
* Balance workload and protect resources with overtime risk = high
* Enable documented skill development without compromising SLA
* Maintain resilience against bottlenecks in Security and Approval

**Hard / safety compliance constraints**
* Security Review: skill 3, or skill 1-2 only under explicit supervision by R7_Gita or R8_Hugo
* Final Approval: skill 2-3 to finalize, skill 1 may prepare only
* High priority case: skill <2 only if supervised
* No resource >4 new assignments in the current decision batch
* Max 4 new assignments per resource

**Soft preference trade-offs**
* Prefer continuity when complexity high and handover_cost = high, unless current owner skill 0-1 and no supervision feasible
* Avoid new work on overtime risk = high unless SLA urgent and no safer alternative
* At least 20% of normal/low priority assignments support documented training priorities if SLA risk acceptable
* Quality Check batching allowed only for priority normal/low and SLA remaining >24h
* Specialist-only routing is avoided when it creates Security/Approval queues

# 2. Assignment policy

```
input: queue cases Q, resources R with skill matrix, workload, overtime risk, training priority
output: assignment mapping

for each case c in Q ordered by SLA urgency score descending:
  eligible = []
  for each r in R:
    if r.skill[required_skill] == 0: continue
    if required_skill == Security and r.skill <3 and not supervised_by_Gita_Hugo(r): continue
    if required_skill == Approval and r.skill <2: continue
    if priority in {high,urgent} and r.skill <2 and not supervised: continue
    if hours_remaining[r] < estimate(c): continue
    eligible.append(r)

  score(r,c) = w1*SLA_urgency(c) 
               + w2*skill_match(r,c) 
               + w3*continuity(r,c) 
               - w4*hand_over_penalty(c)
               - w5*workload_penalty(r)
               - w6*overtime_penalty(r)
               + w7*training_fit(r,c)
               + w8*resilience_bonus(r,c)

  skill_match = 1 if skill>=3, 0.7 if skill==2, 0.4 if skill==1 supervised, 0 else
  continuity = 1 if r == current_owner else 0
  handover_penalty = high/medium/low mapped from case
  workload_penalty = normalized open cases / hours remaining
  overtime_penalty = high=1, medium=0.5, low=0
  training_fit = 1 if c.priority in {normal,low} and r.training_priority == required_skill and SLA risk acceptable
  resilience_bonus = bonus for using non-bottleneck specialist

  pick r* = argmax score with tie break:
    1. lower reassignment_count increase
    2. lower current open cases
    3. overtime risk low -> medium -> high

  enforce constraints:
    if r* has >4 assignments in batch -> next best
    if priority high/urgent and skill <2 and not supervised -> discard
    if overtime risk high and SLA not urgent -> discard unless no alternative

  record assignment reason, trade-off, training flag, risk to monitor
```

# 4. Comparison with baseline policies

**Expected throughput**
* Proposed: Protects urgent SLA with specialist routing for Security/Approval, keeps routine work flowing. Slightly lower immediate throughput than first-available due to supervision overhead.
* First-available: Highest immediate starts, but more skill mismatches increase service time and rework, reducing effective throughput.
* Specialist-only: Maximizes first-pass quality but creates queues in Security and Approval, increasing waiting time and SLA misses for non-specialist work.

**SLA risk**
* Proposed: Urgent/high cases get skill >=2, continuity for high handover cost. Best SLA protection.
* First-available: SLA risk rises for high complexity Security/Approval cases assigned to weak skill.
* Specialist-only: SLA risk for urgent non-specialist tasks due to queue buildup.

**Error/rework risk**
* Proposed: Balanced. High handover cost cases kept with owner, reassignments avoided when >2 reassignments already present.
* First-available: Higher rework from skill mismatch and reassignments.
* Specialist-only: Lowest immediate errors but rework can increase from handover churn when specialists are overloaded.

**Fairness of workload**
* Proposed: Caps at 4 per batch, avoids new work on overtime high resources, redistributes from Iris/David/Bruno to Jonas/Celine.
* First-available: Unfair, concentrates on lowest open cases initially then overloads.
* Specialist-only: Unfair, overloads specialists R7,R8,R6.

**Skill development**
* Proposed: ~22% of normal/low assignments support training: C009 Diagnosis for Amal, C015 Security supervised for Eva. Meets 20% target.
* First-available: Incidental training, no control.
* Specialist-only: Minimal training, trainees starved.

**Continuity of case ownership**
* Proposed: Preserved for high complexity/high handover cost: C007, C016, C005, C002, C011, C008.
* First-available: Low continuity, frequent handovers.
* Specialist-only: Medium continuity, broken when specialist changes.

**Resilience to absence/bottlenecks**
* Proposed: Avoids over-reliance on single Security specialists via supervised training, spreads Approval load.
* First-available: Fragile to absence of low-load resources.
* Specialist-only: Fragile, single point of failure in Security/Approval.

# 5. Explanation to workers

Assignments are made to protect customers and your workload.

* Urgent and high priority cases go first to people with the right skill level and who already know the case, because handovers add waiting time.
* Security Review and Final Approval have compliance rules: only the right skill level can do the final step, and trainees can help only with supervision from Gita or Hugo.
* We keep high complexity cases with their current owner when a handover would cost a lot of time, unless the current owner cannot do it safely.
* We avoid giving new work to people already flagged with high overtime risk, unless a case is urgent and no safer option exists.
* Some normal and low priority cases are intentionally given to support your documented training priorities, e.g. Amal gets a Diagnosis case for development, Eva gets a supervised Security case for development. This is planned and the SLA allows it.
* Workload is balanced so no one gets more than four new assignments in a batch and batchable Quality Checks are grouped.

You will see the main reason, the trade-off we accepted, and the risk we will watch for each assignment. This is auditable and can be discussed in team huddles.

# 6. Process-mining audit indicators

* Handover frequency: `pm4py.discover_handover_of_work_network` per activity, handover count per case
* Reassignment count: case attribute reassignment_count trend over time
* Skill mismatch: join event log with resource skill matrix, compute skill level < required and priority high/urgent
* Workload distribution: current open cases per resource, assignments per batch, `pm4py.discover_working_together_network`
* Overtime risk exposure: assignments to resources with overtime risk=high per SLA class
* SLA misses: `pm4py.filter_case_performance` on sla_deadline vs completion, by assignment policy
* Rework/appeal after assignment: correlate rework rate with >2 reassignments, handover cost band, skill mismatch
* Training assignment share: % of normal/low priority cases assigned to resource where required_skill == training priority
* Specialist bottleneck indicators: waiting time before Security Review and Final Approval, `pm4py.get_service_time` and `pm4py.insert_case_service_waiting_time`
* Deviations from assignment policy: compare actual org:resource with policy recommendation per case, flag unsupervised skill <2 on high priority
