# 1. Delaydecomposition definitions  

For each case *c* (c = 1…12) and each branch *i*  {A,B,C} we define the following quantities using only the supplied timestamps.

| Symbol | Formula | Meaning |
|--------|---------|---------|
| `upstream_elapsed_c` | `fork_release_c – arrival_c` | Time from case entry to the moment all three branches are allowed to start. |
| `queue_{c,i}` | `start_{c,i} – fork_release_c`  (if `start_{c,i}  fork_release_c`, otherwise 0) | Time the branch waits in queue **after** the forkrelease before its first activity begins. |
| `service_{c,i}` | `end_{c,i} – start_{c,i}` | Actual processing time of the branch. |
| `join_ready_c` | `max( end_{c,A}, end_{c,B}, end_{c,C} )` | The latest branch completion; under the stated rule this is the time at which the forkjoin may proceed. |
| `sync_wait_{c,i}` | `max( 0 , join_ready_c – end_{c,i} )` | Time a branch spends waiting **after** its own completion until `join_ready_c`.  **Important:** summing `sync_wait_{c,i}` over *i* would doublecount the elapsed time, because only the critical branch has `sync_wait = 0` and the actual forkjoin span is `max_i( queue_{c,i} + service_{c,i} )`, not the sum of the individual waits. |
| `downstream_queue_c` | `final_start_c – join_ready_c` | Queue at the final station **after** the forkjoin but **before** the final activity starts. |
| `final_service_c` | `final_end_c – final_start_c` | Service time of the final decision activity (two resources F1/F2). |
| `total_flow_time_c` | `final_end_c – arrival_c` | Endtoend case duration from arrival to final release. |

The **forkjoin elapsed time** for case *c* is  

\[
\Delta^{\text{fj}}_c = \max_{i\in\{A,B,C\}}\bigl( queue_{c,i} + service_{c,i} \bigr)
\]

and the total flow time decomposes as  

\[
total\_flow\_time_c = upstream\_elapsed_c \;+\; \Delta^{\text{fj}}_c \;+\; downstream\_queue_c \;+\; final\_service_c .
\]

Summing `sync_wait_{c,i}` over the three branches would give  

\[
\sum_i sync\_wait_{c,i} = (join\_ready_c - end_{c,A}) + (join\_ready_c - end_{c,B}) + (join\_ready_c - end_{c,C}) 
= 3\,join\_ready_c - \sum_i end_{c,i},
\]

which is **not** the actual synchronization delay; it inflates the wait because the same `join_ready_c` is subtracted three times.

# 5. Recommended redesigns and risks  

| Redesign | Expected impact (throughput / flowtime tail) | Resource utilization | Possible new bottlenecks / synchronization effects | What to pilot / measure first |
|----------|-----------------------------------------------|----------------------|----------------------------------------------------|------------------------------|
| **1. Increase Bstation capacity (e.g., add a second machine or reduce setup time)** | • Reduces `B_queue`  average totalflowtime saving 4.5min per case (Counterfactual2). <br>• Tail of flowtime distribution shortens because the longestwaiting cases (F07, F12) are mitigated. | • Bresource utilisation drops from ~70% (observed max queue) toward a more balanced ~50% (depending on capacity added). | • If B’s queue disappears, the forkjoin max may shift to A or C, exposing their syncwait. <br>• Downstream queue may become relatively larger (observed in Counterfactual1 compensation). | • Instrument Bstation timestamps (start/end) to verify queue length distribution.<br>• Run a short pilot with an extra machine on a subset of cases; measure change in `join_ready` and total flow time. |
| **2. Reenginear the documentation branch C to parallelise or expedite (e.g., templatedriven review, dedicated admin resource)** | • Lowers `C_service` and `C_queue`; however, because C is critical only twice, overall average saving is modest (~1–2min). <br>• More importantly, reducing C’s earlyfinish syncwait (30min average) improves *resource idletime* but does **not** drastically cut total flow time unless C becomes the bottleneck. | • Cresource utilisation would increase (less waiting), but total admin capacity may need to grow to sustain the faster pace. | • Faster C could make C the new critical branch in some cases, shifting the bottleneck and potentially increasing `downstream_queue` if the final station is already busy. <br>• May uncover hidden dependencies (e.g., C must wait for A/B signoff). | • Test a “fasttrack” C path on a pilot group; track whether `critical_branch` frequency changes.<br>• Measure syncwait per case after the change to see if downstream queue expands. |

**Key insight:**  The most leverage lies in **branchB’s queue** (technical work).  Reducing B’s queue yields the biggest aggregate flowtime reduction and also mitigates the risk of downstream queue absorption.  Any redesign that only speeds A or C will have limited effect because the forkjoin maximum is already dominated by B’s queuedelay in the majority of cases.

# 7. Limits of inference  

1. **Causality:** The data are observational timestamps; we cannot infer *why* a branch queued longer (e.g., resource scarcity, workload spikes) without additional processmodel information.  
2. **Branch resource capacity:** The observed queue lengths reflect the *current* state but do not reveal the number of servers, processing rates, or setup times that generate those queues.  
3. **Work preemption / interleaving:** The log records start and endtimes only; we have no information about whether work was interrupted, reentered, or executed in parallel within a branch.  
4. **Finalstation waiting policy:** `downstream_queue` is calculated as `final_start – join_ready`.  It is ambiguous whether this truly represents a *queue* (waiting for an available resource) or a *release policy* (the final activity is deliberately delayed until a specific schedule or resourceallocation rule).  Without explicit resourceavailability logs, we cannot distinguish the two.  

These limitations mean that any redesign recommendation should be validated with finergrained operational data (e.g., resource utilisation logs, workitem traceability) before being implemented.
