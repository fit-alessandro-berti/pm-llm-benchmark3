# 1. Policy Interpretation and Conflict Resolution

- Each trace is one completed onboarding case. Events represent activity completions. The case opens with Receive Onboarding Request and ends with Close Onboarding. For R3, the decision boundary is Reject Vendor or Activate Vendor. Clarification can occur anywhere between receipt and that boundary, including during the checks or approval route. Each Receive Clarification closes one outstanding Request Clarification.
- The procedural model identifies the low- or high-risk route by the activities taken. The supplied events for Classify Risk lack a classification result. An independent result, when available, can be checked against the route taken.
- Each Sanctions Escalation requires a subsequent Obtain Legal Opinion in the same case. An opinion may cover multiple outstanding escalations when the log has no escalation or opinion identifiers. The activation gate considers escalations already recorded when activation occurs. A later escalation still triggers R4.
- The 24-hour exception window starts at Activate Vendor and includes the 24-hour endpoint. The opinion must be later in event order. A verified authorization must cover the activation and be effective at that time. The authoritative record must establish the required joint authorization.
- R9 compares the applicable approver with every Verify Bank Account resource, including post-activation reverification. It also compares the Capture Master Data resource with the activation resource. Resource values identify people consistently across activities.
- Under R11, a post-activation change makes earlier verification insufficient for any later payment. One subsequent suspension and one subsequent verification can each cover all changes outstanding at that point for the same vendor account. Suspension is due by case completion, and verification is due before the first subsequent payment, if any. The stated policy prescribes neither an order between suspension and verification nor a second activation.

R5 prohibits early activation in the same situation that R6 would allow it. Deploy one of the following policies as a decision rule.

| Resolution | Decision rule | Compliance risk |
|---|---|---|
| **Strict legal policy, implemented** | Block Activate Vendor while any earlier Sanctions Escalation lacks a subsequent Obtain Legal Opinion. Apply R4 on all routes. | A genuine and jointly authorized emergency would still be blocked. If Operations acts outside the gate, the early activation is a violation under this policy. |
| **Jointly authorized exception** | Keep the gate for ordinary activations. Allow an early activation only with verified external joint authorization. Require the opinion after activation and within 24 hours, and continue to apply R4. | The same sequence can reflect either an authorized or an unauthorized activation. Treating the event log as proof of authorization would allow unauthorized cases to pass. Missing evidence leaves retrospective conformance unresolved and is insufficient for prospective release. |

| R2 | Accepting Petri net | Each accepting path with Activate Vendor has exactly one approval, via Manager Approval or via Enhanced Due Diligence then Compliance Approval. # 3. Procedural Backbone

The symbol `‖` denotes parallel branches, `→` denotes sequence, and `⊕` denotes exclusive choice.

```text
Receive Onboarding Request
→ (Capture Master Data ‖ Run Sanctions Screening ‖ Verify Bank Account)
→ Classify Risk
→ (Reject Vendor
   ⊕ ((Manager Approval ⊕ (Enhanced Due Diligence → Compliance Approval))
      → Activate Vendor → Release First Payment))
→ Close Onboarding
```

The net adds a clarification token that permits zero or more paired cycles before the decision. It also adds optional events within the open case and a separate transition for post-activation verification.

```python
from pm4py.objects.petri_net.obj import Marking, PetriNet
from pm4py.objects.petri_net.utils.petri_utils import add_arc_from_to

net = PetriNet("Controlled Vendor Onboarding")
place_names = (
    "start", "open_case",
    "capture_pending", "screening_pending", "verification_pending",
    "capture_complete", "screening_complete", "verification_complete",
    "clarification_ready", "clarification_pending",
    "classified", "due_diligence_complete", "approved",
    "payment_pending", "paid", "post_activation", "close_ready", "end",
)
places = {name: PetriNet.Place(name) for name in place_names}
net.places.update(places.values())


def add_transition(name, label, inputs, outputs):
    transition = PetriNet.Transition(name, label)
    net.transitions.add(transition)
    for place in inputs:
        add_arc_from_to(places[place], transition, net)
    for place in outputs:
        add_arc_from_to(transition, places[place], net)


add_transition(
    "receive", "Receive Onboarding Request", ("start",),
    ("open_case", "capture_pending", "screening_pending",
     "verification_pending", "clarification_ready"),
)
add_transition(
    "capture", "Capture Master Data", ("capture_pending",), ("capture_complete",)
)
add_transition(
    "screen", "Run Sanctions Screening", ("screening_pending",), ("screening_complete",)
)
add_transition(
    "verify_initial", "Verify Bank Account",
    ("verification_pending",), ("verification_complete",),
)
add_transition(
    "classify", "Classify Risk",
    ("capture_complete", "screening_complete", "verification_complete"), ("classified",),
)
add_transition(
    "request_clarification", "Request Clarification",
    ("clarification_ready",), ("clarification_pending",),
)
add_transition(
    "receive_clarification", "Receive Clarification",
    ("clarification_pending",), ("clarification_ready",),
)
add_transition(
    "reject", "Reject Vendor", ("classified", "clarification_ready"), ("close_ready",)
)
add_transition("manager_approval", "Manager Approval", ("classified",), ("approved",))
add_transition(
    "due_diligence", "Enhanced Due Diligence",
    ("classified",), ("due_diligence_complete",),
)
add_transition(
    "compliance_approval", "Compliance Approval", ("due_diligence_complete",), ("approved",)
)
add_transition(
    "activate", "Activate Vendor",
    ("approved", "clarification_ready"), ("payment_pending", "post_activation"),
)
add_transition(
    "verify_again", "Verify Bank Account", ("post_activation",), ("post_activation",)
)
add_transition("pay", "Release First Payment", ("payment_pending",), ("paid",))
add_transition("merge_paid", None, ("paid", "post_activation"), ("close_ready",))

for name, label in (
    ("escalate", "Sanctions Escalation"),
    ("opinion", "Obtain Legal Opinion"),
    ("change_bank", "Change Bank Details"),
    ("suspend", "Suspend Vendor"),
):
    add_transition(name, label, ("open_case",), ("open_case",))

add_transition("close", "Close Onboarding", ("open_case", "close_ready"), ("end",))
initial_marking = Marking({places["start"]: 1})
final_marking = Marking({places["end"]: 1})
procedural_model = (net, initial_marking, final_marking)
```

- Receipt creates three independent check tokens. Their completion transitions can occur in any order. Classify Risk joins all three completions.
- Reject Vendor, Manager Approval and Enhanced Due Diligence compete for the classification token. On the high-risk branch, only Compliance Approval can produce the approval token. On either approval branch, Activate Vendor consumes that token and enables a single first payment. Both completed branches converge before Close Onboarding, which consumes the remaining open-case token.
- Requests and replies can interleave with the checks and approval steps. An unanswered request blocks Reject Vendor and Activate Vendor. Either decision removes the clarification token and ends the loop.
- The open-case self-loops accommodate escalation, opinion, change and suspension where they occur in the trace. Separate checks impose their conditional ordering. The post-activation token permits repeat Verify Bank Account events before or after first payment while the case remains open. The silent merge can fire immediately before closure, so a verification after payment remains replayable. Both verification transitions use the required visible label.

# 4. DECLARE Model

```python
declare_model = {
    "altresponse": {
        ("Request Clarification", "Receive Clarification"):
            {"support": 1.0, "confidence": 1.0},
    },
    "response": {
        ("Sanctions Escalation", "Obtain Legal Opinion"):
            {"support": 1.0, "confidence": 1.0},
    },
    "precedence": {
        ("Run Sanctions Screening", "Sanctions Escalation"):
            {"support": 1.0, "confidence": 1.0},
    },
    "noncoexistence": {
        ("Reject Vendor", "Activate Vendor"):
            {"support": 1.0, "confidence": 1.0},
        ("Enhanced Due Diligence", "Manager Approval"):
            {"support": 1.0, "confidence": 1.0},
        ("Compliance Approval", "Manager Approval"):
            {"support": 1.0, "confidence": 1.0},
    },
}
```

| Template | Source | Target | Direction and semantics |
|---|---|---|---|
| Alternate response | Request Clarification | Receive Clarification | Every request needs a later reply before the next request, or before trace end for the last request. Other activities may intervene. The net supplies the outcome boundary. |
| Response | Sanctions Escalation | Obtain Legal Opinion | Every escalation requires a later opinion. An opinion before the escalation does not discharge it. |
| Precedence | Run Sanctions Screening | Sanctions Escalation | Every escalation requires an earlier screening. The target triggers this backward-looking check. |
| Noncoexistence | Reject Vendor | Activate Vendor | The two activities cannot both occur, in either order. |
| Noncoexistence | Enhanced Due Diligence | Manager Approval | The two activities cannot both occur, in either order. |
| Noncoexistence | Compliance Approval | Manager Approval | The two activities cannot both occur, in either order. |

Response looks forward from its source. Precedence looks backward from its target. Alternate response bounds a response by the next source occurrence. Chain response would require the target to be the next event, which would prevent valid intervening work. Noncoexistence rules out both orderings. Nonsuccession would only forbid a source followed later by a target, so it would leave the reverse ordering possible.

# 5. Log-Skeleton Model

```python
log_skeleton = {
    "equivalence": set(),
    "always_before": {
        ("Activate Vendor", "Classify Risk"),
        ("Reject Vendor", "Classify Risk"),
        ("Release First Payment", "Activate Vendor"),
    },
    "always_after": {
        ("Activate Vendor", "Release First Payment"),
    },
    "never_together": {
        ("Reject Vendor", "Activate Vendor"),
        ("Enhanced Due Diligence", "Manager Approval"),
        ("Compliance Approval", "Manager Approval"),
    },
    "activ_freq": {
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1},
    },
    "directly_follows": set(),
}
```

In `always_before`, the first label is the activity being checked and the second label must occur earlier. Thus Classify Risk must precede an activation or rejection, and Activate Vendor must precede Release First Payment. In `always_after`, Release First Payment must occur after Activate Vendor in a completed case. These pairs echo the accepting paths. Their activities are single-occurrence on those paths. The three `never_together` pairs are symmetric and duplicate the DECLARE exclusions. The frequency sets implement R10 without requiring those activities on every route. There is no adjacency constraint because optional events can intervene even between Activate Vendor and Release First Payment. Equality of counts is unnecessary here, and would be unsuitable for relating a repeatable Verify Bank Account to a single Classify Risk.

For PM4Py versions that flag observed labels missing from `activ_freq`, give unrestricted labels a pass-through set of all their counts in the input log, including zero. The authored model still puts frequency bounds on only the three R10 labels. The adapter below takes a PM4Py `EventLog`.

```python
from collections import Counter

import pm4py


def check_log_skeleton(log):
    unrestricted = {}
    for trace in log:
        counts = Counter(event["concept:name"] for event in trace)
        for activity, count in counts.items():
            if activity not in log_skeleton["activ_freq"]:
                unrestricted.setdefault(activity, {0}).add(count)
    runtime_model = {
        **log_skeleton,
        "activ_freq": {**unrestricted, **log_skeleton["activ_freq"]},
    }
    return pm4py.conformance_log_skeleton(log, runtime_model)
```

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800, 86400),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200, 21600),
    ("Activate Vendor", "Release First Payment"): (259200, 129600),
}
zeta = 2.0
```

For each matched ordered pair, let `elapsed_seconds` be the difference between its recorded timestamps. Emit a warning if `abs(elapsed_seconds - mean_seconds) / standard_deviation_seconds > zeta`. In hours, the inclusive bands are 0–96 for clarification, 0–24 for escalation to opinion and 0–144 for activation to payment. The escalation profile measures from Sanctions Escalation. The R6 deadline measures from Activate Vendor.

For repeated activities, score the first valid Receive Clarification after each request and before the next request or decision, the first subsequent Obtain Legal Opinion for each escalation, and the subsequent Release First Payment for each activation on a valid path. If a trace has repeat activations or payments, its payment pairing is ambiguous and can be skipped with a diagnostic. A raw PM4Py temporal-profile run can compare multiple ordered occurrences across clarification cycles. Filter those comparisons by the matching policy before reporting normative warnings. If no matching pair with two usable timestamps exists, timing is `not evaluated` for that pair. Report missing required events through the appropriate control-flow or policy check. A completed pair outside its band yields a warning because R12 sets expectations about elapsed time.

# 7. Resource- and Data-Aware Checks

Group by case ID and use the trusted within-case order. `concept:name` supplies the label, `org:resource` the stable person identifier, and `time:timestamp` the event time for elapsed-time checks. Timestamp ties need a reliable sequence field if relative order is material. Do not use arbitrary sorting to resolve a material tie. Missing case ID, activity label or indispensable order makes the affected check `not evaluated`. Missing time alone still permits order checks if the event sequence is reliable.

**R9. Segregation of duties**

```text
compare_people(event1, event2):
    if either person identifier is missing or cannot be resolved:
        return not evaluated for this comparison
    if identifiers are equal:
        return fail for this comparison
    return pass

if the applicable approval can be identified:
    for every Verify Bank Account in the case, including reverification:
        compare_people(verification, applicable approval)

for every Capture Master Data and Activate Vendor pair in the case:
    compare_people(capture, activation)
```

Identify the applicable approval from the procedural route. On a malformed path with an activation and a single candidate approval, the comparison remains observable. If the approval cannot be identified unambiguously, mark the affected comparison `not evaluated`. A rejected-only path has no applicable approval or activation on a compliant trace. Missing required activity occurrences remain procedural findings. A known equality fails the check even when another comparison is unresolved.

**R5 and R6. Activation gate**

```text
pending_escalations = []
for each event in case order:
    if event is Sanctions Escalation:
        append event to pending_escalations
    if event is Obtain Legal Opinion:
        clear pending_escalations
    if event is Activate Vendor and pending_escalations is nonempty:
        if policy is strict:
            report fail at activation for the pending escalations
        else if policy is the jointly authorized exception:
            authorization = look up verified joint authorization for this case
                            and activation, covering the pending escalations
            opinion = first Obtain Legal Opinion after this activation
                      and before case closure
            if authorization is verified absent or invalid:
                report fail
            if opinion is absent in the completed trace:
                report fail
            if both timestamps are usable:
                elapsed = opinion timestamp - activation timestamp
                if elapsed is outside [0 seconds, 86400 seconds]:
                    report fail
            if no failure is known and authorization is unresolved:
                report policy-dependent
            if no failure is known and elapsed cannot be computed:
                report not evaluated for the deadline
            if authorization is valid and the elapsed time is within bounds:
                report pass for the exception
```

The exception lookup needs the case ID and an activation reference or an unambiguous equivalent, with evidence of coverage, effective time and joint authorization. An unavailable record or reference leaves authorization unresolved. A reliable determination that approval was absent or invalid fails the check. Missing activation or opinion timestamps leave the deadline unevaluated when both events exist. On an open case, an outstanding opinion remains pending until its deadline expires or the case closes. For prospective use, verify joint authorization before permitting activation and start the deadline monitor at activation. R4 continues to check opinions for every escalation under either policy.

**R11. Changed bank details**

```text
activated = false
awaiting_suspension = []
awaiting_verification = []
for each event in case order:
    if event is Activate Vendor:
        activated = true
    if event is Change Bank Details and activated:
        append event to both lists
    if event is Suspend Vendor:
        clear awaiting_suspension
    if event is Verify Bank Account:
        clear awaiting_verification
    if event is Release First Payment and awaiting_verification is nonempty:
        report fail at payment for the unverified changes
at case completion:
    report fail for every change still awaiting suspension
```

The lists contain only changes after activation. The check needs case ID, labels, order and reliable case completion for the suspension deadline. An open case can still incur a payment failure immediately. Missing completion evidence leaves the pending suspension obligation unresolved. If multiple accounts or separately tracked changes exist, use account or change IDs when matching verification and suspension. Missing identifiers then leave coverage `not evaluated`. The supplied cases support case-level matching.

If a trusted classification result is available, compare it with the observed low- or high-risk route on an accepted case. A mismatch fails that data check. With the supplied logs, the route is inferred from control flow and independent risk-result validation is `not evaluated`.

# 9. Contradictions, Redundancies, and Blind Spots

- The strict activation gate and the emergency permission cannot both govern the same early activation. Record the selected policy version and distinguish a failure under that version from an unresolved result under the alternative.
- The net, DECLARE and Log Skeleton can all report the same exclusivity violation. R10 also follows from the net. Retain the detailed findings, and show one case-level issue per underlying rule and offending event when the checks agree.
- A single-occurrence frequency or count equivalence for Verify Bank Account would conflict with valid post-activation reverification. A chain-response rule for clarification or an adjacency requirement from activation to payment would reject permitted interleavings. A blanket response from every Change Bank Details to Verify Bank Account would require verification even when the change is before activation or there is no subsequent payment.
- Response is vacuously true without its source, and precedence is vacuously true without its target. For example, a rejected case with no escalation can satisfy R4 and R7 without any legal opinion. Procedural paths establish required activity presence. Similarly, fulfilling a response eventually does not establish compliance with an intermediate activation gate.
- Without trusted risk results, actual route eligibility cannot be confirmed. Missing identity mappings prevent some R9 decisions. Missing authorization can leave an emergency claim unresolved. If several changes or escalations can have separate lifecycles, case-level matching needs additional correlation data to confirm coverage.
- Ordered timestamps can support duration checks given consistent clocks and completion semantics. Equal or coarse timestamps may conceal event order, and completion-only events cannot show that activities actually overlapped. Timing alone cannot establish identity, causal linkage, the start of unlogged work or authorization.
- DECLARE support and confidence values here are metadata for authored rules. Observed support and confidence depend on the population and treatment of vacuous cases. A frequently observed pattern can violate policy, and a rare rule can still be mandatory.

# 10. Deployment Recommendation

Use the accepting Petri net as the canonical representation of allowable onboarding paths. Maintain a versioned policy specification that assigns each requirement to its authoritative check in Section 2. Make the activation gate and the identity comparisons available to the operational system before it records the corresponding decision. The retrospective checks use the same definitions and preserve unknown evidence states.

1. Validate case boundaries, labels and ordering. Resolve identity and timestamp quality for the checks that need them.
2. Run exact procedural replay or alignments against the accepting net. Run DECLARE and Log Skeleton on the original trace even when the replay fails, preserving the original event positions and the evidence for each finding.
3. Evaluate the stateful, resource and external authorization checks on those same events. Continue independent checks on malformed cases where the corresponding evidence remains identifiable.
4. Score complete temporal pairs and report the elapsed time, expected band and matched events for each warning.
5. Report the earliest decisive violation, later findings, and any missing evidence that affects the verdict. Group duplicate findings by requirement and event. If layers disagree on a mandatory rule, show both results with their rule semantics and policy versions, use the designated authority for the verdict, and surface an implementation or configuration discrepancy for review. Under exception mode, keep an unverified early activation unresolved until its authorization evidence is adjudicated.
