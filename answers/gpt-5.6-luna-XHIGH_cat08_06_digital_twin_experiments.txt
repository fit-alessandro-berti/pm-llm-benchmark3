## 1. Model scope and state variables

The twin should represent the period from official portal submission through permit issuance or rejection. The pre-submission checker is an upstream extension of the boundary for D1, because it changes the probability that a submitted case is incomplete and changes applicant effort. Applicant behavior, objections, consultant reports, and prior violations remain external processes represented by calibrated stochastic inputs rather than being treated as municipal service.

The appropriate abstraction is a discrete-event, resource-constrained process model with case-level precedence and joins. It should be detailed enough to represent the stated activities, queues, calendars, rework, parallel reviews, public-notice minimum durations, and inspection batching. It need not model every keystroke, individual document field, or internal system transaction. System activities can be represented as zero- or near-zero-duration transitions with unlimited capacity, except where they impose a policy or calendar delay.

The main entities are:

- An application/case, with case type, district, architect, application value, building-area category, risk and sensitivity indicators, required reviews, public-notice requirement, prior-violation status, submission time, current state, applicable prerequisites, rework count, appeal status, and terminal outcome.
- An architect or submitting organization, with a time-varying submission intensity, propensity for related applications, response behavior, and possible appointment-slot assignment.
- A related-case or neighborhood group, linking applications that may share an architect and district, a development, or a neighborhood objection process.
- An inspection bundle, containing compatible cases grouped by district and geography. The bundle has a formation time, a maximum permitted waiting time, travel time, and a shared inspection route.
- Municipal resources: clerk pools, planners, fire reviewers, environmental reviewers, inspectors, schedulers, legal officers, and system capacity. Individual skills and calendars should be retained where they affect routing or capacity.

Important case state includes `current_activity`, `status`, `ready_time`, `last_completion_time`, activity completion flags, `pending_prerequisites`, `missing_document_loop_count`, `inspection_rework_count`, `appeal_count`, and timestamps for every modeled start and completion. It should also retain the reason for a rework transition when that reason is observed or imputed, and a censoring/observation flag.

The baseline precedence graph is the nominal process tree, augmented with explicit joins:

- Completeness check either proceeds or starts a request/receive loop.
- Planning, Fire, Environmental, and Public Notice are conditional. Reviews that apply can be concurrent, subject to their own resource pools.
- Decision drafting cannot start until all applicable review and inspection prerequisites have completed.
- Legal check and the issue/reject choice are conditional, and rework/appeal transitions return to the appropriate point rather than duplicating a case.

The twin must not model a case as independent after arrival. It should include (i) correlated architect-level arrival bursts, (ii) possible common neighborhood-objection state for related cases, (iii) inspection-bundle formation and shared travel capacity, and (iv) shared resource queues. A bundle may reduce travel and inspection service time, but a case can wait for the bundle or be split after a maximum wait. These dependencies should be visible in the state and event trace so that their effect can be measured.

Every municipal resource has a capacity, skill eligibility, working calendar, breaks/interruptions, and queue discipline. Calendars include weekdays, public holidays, part-time fire-reviewer days, reserved environmental capacity, field-visit days, and council-meeting exclusions for legal work. Calendar time, queue waiting, municipal service, applicant response, and third-party response must be separate clocks in the output.

## 2. Parameter-estimation plan

First standardize the event log without destroying the raw data. Parse timestamps as timezone-aware datetimes, sort by case and timestamp, preserve all case and event attributes, and record duplicate, out-of-order, and incomplete cases. Use PM4Py for event-log formatting, variants, DFGs, performance DFGs, and conformance diagnostics; use a separate estimation layer for covariate models and a separate discrete-event engine for simulation.

Arrivals should be estimated from `Submit application` events rather than from all case rows. Fit a non-homogeneous arrival model with at least month/season, day of week, hour, district, and case type effects. The 1.7 peak multiplier and 2.2 Monday multiplier are useful priors or shrinkage targets, not replacements for estimation. A practical baseline is a Poisson or negative-binomial rate model by hour/day with seasonal terms, augmented by architect-level random effects and a cluster/batch component for related submissions. Compare this with a self-exciting or Neyman-Scott cluster model if bursts are strong. Validate both the marginal rate and the distribution of counts per architect-week.

For service times, use explicit activity start and completion timestamps when available. Fit positive distributions by activity, case type, district, resource skill, and relevant flags; lognormal, gamma, Weibull, empirical bootstrap, and mixture models are reasonable candidates. Use robust tail diagnostics and information criteria or cross-validation, but prefer an empirical or mixture tail when p90 behavior is not captured by a single family. System events should be modeled separately. Do not infer human service time from the gap between two completion events.

For waiting times, calculate `activity_start - predecessor_completion` only for records with a reliable activity start. Decompose that time into calendar-closed time, queue time, and external waiting where the source permits it. If only completion timestamps are available, the observed gap is a total inter-event delay containing both queue and service; estimate the latent split using resource-calendar constraints, any available work-start or status data, and calibration to case durations. Carry lower/upper or alternative split scenarios into the simulation rather than presenting the split as observed fact.

Estimate routing probabilities conditionally, not only as global variant shares. Use case type, district, value, area/risk proxies, explicit `requires_fire`, `requires_environment`, and `requires_public_notice` fields. For incomplete thresholds and environmental sensitivity, fit a probabilistic classifier or hierarchical lookup using observed routes, retain predictive uncertainty, and generate a missing-feature scenario. D1, D2, D8, and D9 should replace or perturb these routing and information states only through explicit policy parameters.

Estimate rework from repeated activities and transitions after Planning, Inspection, Legal, and appeal-related events. Stratify by activity, case type, district, resource, and preceding conditions. Use structured event sequences first; use unstructured reason text only to create uncertain categories, with an `unknown` category and sensitivity to its allocation. Match both loop probability and loop delay. Rework is not simply a residual needed to force the mean duration to match.

Estimate resources from `org:resource`, activity eligibility, concurrent observed work where starts exist, and the HR-reconstructed calendars. The HR calendar is the primary capacity input because the event log cannot reliably recover all availability. Estimate resource heterogeneity only where there is enough data; otherwise use a pool distribution and test fast/slow-worker scenarios. Model public holidays, council weeks, reserved environmental time, and field travel explicitly as unavailable or reduced capacity.

Estimate applicant and third-party response distributions separately from municipal work. For missing documents, use request-to-receive intervals by case type, architect, document class if available, and season; heavy-tailed empirical or lognormal mixtures are more appropriate than a narrow normal distribution. Treat objections as latent: use public-notice duration, available objection indicators, and related-case timing to estimate a latent objection probability and an extension distribution. The log does not identify objection timing or causality, so calibrate multiple plausible latent models.

Estimate cross-case dependencies from architect-week counts, inter-arrival clustering, same-architect/same-district co-occurrence, related identifiers, and inspection dates. Fit a cluster arrival process and a bundle-formation rule, then calibrate the resulting bundle-size distribution, delay, and travel reduction. For neighborhood effects, estimate a shared latent group state whose probability depends on district, case type, and notice requirement; do not interpret an absent objection event as evidence of no objection.

The 18 months should be divided chronologically for calibration and evaluation. Use bootstrap or hierarchical resampling by architect and time block, rather than independently resampling rows, so that seasonality and clustering are preserved. Weight or model known missingness, compare cases with and without complete timestamps, and report parameter ranges for rare emergency cases and missing route attributes.

PM4Py handling should be explicit. `pm4py.format_dataframe` should establish the case, activity, and timestamp keys. Use `pm4py.get_variants` for sequence variants, `pm4py.discover_dfg` for control-flow frequency, and `pm4py.discover_performance_dfg` for performance edges. Use token replay or alignments where an appropriate Petri-net model has been constructed, but do not mistake conformance fitness for timestamp or resource validation. The simplified process-tree string is useful as a specification; parser support for every shorthand operator and whitespace form is version-dependent, so parsing must be checked and unsupported constructs converted to a programmatic process tree or explicit routing graph.

## 3. Assumptions

### Arrivals

- Official submissions follow a non-stationary rate varying by season, weekday, hour, district, and case type. Peak-season and Monday multipliers are calibrated, not hard-coded forever.
- Architect-level bursts are generated by a random-effect or cluster process. Conditional on modeled architect and group effects, remaining arrivals may be treated as approximately independent; this is a testable simplification.
- Future demand is exogenous to permit performance unless a scenario explicitly models feedback, such as appointment slots shifting rather than deleting submissions.

### Service times

- Human service times are positive and depend on activity and important case/resource covariates; calendar-closed time is not service.
- A service-time sample is not fabricated from completion gaps. Where starts are missing, the model uses a calibrated latent decomposition and reports its sensitivity.
- Parallel reviews can overlap in wall-clock time, while a case cannot enter the drafting join until all applicable reviews finish.

### Routing

- The nominal graph and stated rules define baseline routing. Missing thresholds and sensitivity attributes are represented by uncertain conditional probabilities.
- Simple low-value no-inspection eligibility includes the stated value condition and a reliable no-prior-violations condition; the rule does not silently apply to ineligible cases.
- D5 is a genuine pre-check with a defined point of execution and capacity, not free legal capacity. D8 and D9 can have false positives/negatives and those rates are scenario parameters.

### Resources and calendars

- The listed FTEs, skills, and HR calendars are the starting capacity model. A resource is unavailable outside its calendar, and a queue cannot consume capacity during closure.
- Activities are non-preemptive unless the municipality confirms otherwise. Queue priorities, aging rules, appointment slots, and urgent-case exceptions are explicit policy parameters.
- System tasks are effectively unlimited, but automated policy delays and public-notice minimum duration still consume time.

### Rework

- Rework is generated by calibrated conditional transition probabilities and delay distributions, including inspection rework and appeals.
- Uncoded reason text does not establish a causal reason. Unknown rework is retained or allocated across plausible reason categories in sensitivity runs.
- Interventions may change rework probabilities only where there is a stated mechanism, such as D1 reducing missing-document loops; all other changes are tested as uncertainty rather than assumed benefit.

### Applicant and third-party response

- Applicant response is an external, heavy-tailed delay and is not counted as clerk or planner service.
- Applicant behavior can vary by type, architect, season, and intervention. D1 may add pre-submission effort and D7 may shift submission timing, so those effects are modeled explicitly.
- Objections, consultant reports, and neighborhood effects are latent and are inferred from proxies or scenario ranges; missing objection records are not treated as observed zeroes.

### Cross-case dependencies

- Same-architect submissions can arrive in clusters and can share response behavior. Same-district/related cases can share inspection bundles and a latent objection environment.
- Bundling trades per-case travel and inspection effort against a first-case or bundle-formation wait. A maximum bundle wait prevents unbounded delay.
- If relations are absent from the log, the model uses observed architect/district correlations and a range of hidden-relatedness rates rather than claiming complete linkage.

### Non-stationary demand

- The seasonal pattern repeats approximately over the decision horizon, with an optional trend and stress multipliers for changed demand.
- Experiments use identical stochastic arrival streams across policies within each replication where possible, so differences are attributable to the intervention rather than a different random demand realization.

### Missing data

- Missing starts, objection events, rework reasons, emergency cases, and route attributes are informative or uncertain rather than automatically missing at random.
- The baseline is calibrated to observed completions and durations, but latent-state alternatives are retained. Results that change materially across those alternatives are reported as non-robust.
- Calendar data reconstructed from HR are treated as an input with measurement uncertainty, not as event-log observations.

## 4. Experiment matrix

The baseline and policy runs should use the same calibrated historical-like arrival and exogenous shock streams within a replication. The numerical levels below are design levels to be calibrated or replaced by municipal choices; they are not claims that the intervention will achieve them.

| Experiment | Factors and levels | Expected trade-offs |
|---|---|---|
| B0: calibrated baseline | Current routing; observed case mix; seasonal rate; current calendars and capacities; no new policy | Reference for duration, SLA, backlog, utilization, rework, and fairness. |
| D1: pre-submission document checker | Adoption 0%, 50%, 90%; missing-document loop probability reduced by a calibrated 20–60%; applicant pre-submit effort increased by 0.5–2 days or an empirically chosen amount | Less clerk rework and applicant-response tail, but added front-end effort, possible exclusion or extra burden, and checker false positives. |
| D2: low-risk no inspection | Eligible share based on value below EUR 50,000 and no prior violations; policy on/off; false-eligibility/error rate as a sensitivity factor | Faster and less inspector workload for Simple renovation; reduced inspection assurance and possible downstream risk or rework. |
| D3: district-batched inspection | Batch window 1, 3, or 5 working days; maximum bundle wait 2, 5, or 10 days; district route optimization on/off | Lower travel and possibly higher inspector throughput; longer wait for the first case and potential district unfairness. |
| D4: temporary peak inspector | 0 or 1 inspector FTE, active only in March–May and September–November; field calendar Tuesday–Friday; hiring cost and travel assumptions varied | Lower inspection queues and tail during peaks; cost, onboarding risk, and under-utilization outside peak months. |
| D5: parallel legal pre-check | Off/on for Commercial and Complex variance; pre-check capacity 0.25, 0.5, or 1.0 legal FTE; start after required early inputs | Earlier detection of legal conflicts and shorter late tail; legal capacity diversion, extra handoffs, and more early rework. |
| D6: aging-case planner reserve | Off/on; one planner reserved daily; aging threshold 20, 30, or 45 calendar days; reserve release rule varied | Protects old cases and fairness in the tail; reduces ordinary planner capacity and may increase new-case waiting. |
| D7: architect-facing appointment slots | Off/on; Monday submission cap or smoothing target 1.2, 1.5, or 1.7 times Wednesday rate; displaced demand shifted to later slots | Flattens clerk queue spikes and may improve predictability; applicant scheduling delay, access concerns, and possible demand displacement. |
| D8: environmental triage | Off/on; triage service capacity; 10–30% of cases routed to detailed review; false-negative and false-positive rates calibrated in sensitivity runs | Reduces environmental specialist queue for low-risk cases; safety/compliance risk and possible extra triage work. |
| D9: objection early warning | Off/on; detection rate 50%, 75%, or 90%; early outreach delay 1–5 days; objection extension distribution unchanged or reduced only with evidence | Makes long public-notice cases visible earlier and can reduce surprises; outreach work, privacy/access issues, and no guarantee that objections disappear. |
| D10: combined operational policy | D1 at selected adoption + D2 + D3 with selected batch window + D4 one peak inspector; compare additive and interaction effects | Potentially large peak improvement and inspector relief; policy interactions, implementation cost, risk of simultaneous optimistic assumptions. |
| C1: flow-and-aging package | D1 + D6 + D7, each at low/medium/high levels | Tests whether front-end smoothing and aging protection improve both typical and tail performance; may transfer delay to applicants or ordinary cases. |
| C2: review-risk package | D5 + D8 + D9, with conservative/central/aggressive detection and capacity levels | May reduce late legal/environmental/public-notice surprises; consumes scarce specialist capacity and can increase early work. |
| C3: full candidate portfolio | D1–D9, excluding D10 as a separate duplicate, with policy costs and risk penalties; compare a conservative and an aggressive configuration | Estimates interaction and Pareto frontier; greatest implementation complexity and parameter uncertainty. |
| S1: extreme demand peak | Peak arrival multiplier 2.0x and 2.5x relative to baseline; Monday multiplier 2.2x and 3.0x; same staffing | Tests queue stability and whether an intervention merely shifts the bottleneck. |
| S2: objection and external-delay shock | Objection prevalence 1.5x and 2.0x; public-notice extension p90 90 and 120 days; applicant response p90 1.5x | Tests robustness of D9 and whether municipal improvements are masked by external heavy tails. |
| S3: capacity/calendar shock | One inspector unavailable for 4 or 8 weeks; one legal officer unavailable during a council-heavy period; environmental reserved time 40% or 60% | Tests resilience, backlog growth, and recovery after a disruption. |
| S4: dependency burst | Top architect submission share 40% rather than 31%; related-case cluster size increased; inspection bundles forced or unavailable | Tests whether independent-case approximations would understate correlated queues and bundle delay. |

For every row, report the policy cost and implementation burden as factors where relevant. A factorial or fractional-factorial design can screen interactions, followed by a focused response-surface design around policies that are close to the decision frontier.

## 5. Warm-up, replications, and uncertainty treatment

Because demand is seasonal and cases can last 260 days or more, an empty-system warm-up shorter than a few weeks would be misleading. Use a pilot run and Welch plots of daily WIP, queue length, and utilization to identify stabilization, with a minimum warm-up of one full 365-day seasonal cycle for a recurring-demand comparison. A practical production run is 365 warm-up days, 365 measurement days, and at least a 260-day drain if terminal completion metrics are needed. If a policy changes the initial backlog, initialize every policy from the same sampled historical state or use a common steady-state initialization procedure.

Use at least 200 independent replications per experiment for screening and increase to 500 or more for heavy-tailed tail metrics or close policy comparisons. Assign deterministic, reproducible seeds by `(experiment, replication, random_stream)`, but use common random numbers for arrivals, applicant delays, objections, and baseline service draws across competing policies within a replication. Separate streams for each source prevent a policy-induced change in one stream from silently changing all other randomness.

Report paired 95% confidence intervals for intervention-minus-baseline differences. For each replication retain case-level observations, then use replicate means for means and a bootstrap across replications for medians, p90/p95, SLA proportions, fairness gaps, and CVaR. Daily or weekly time series should use batch means or block bootstrap to account for serial dependence. If Bayesian calibration is used, draw parameter sets from the posterior and report posterior predictive credible intervals in addition to process-variability intervals; otherwise use a bootstrap or asymptotic parameter distribution.

Separate two uncertainties:

- Process uncertainty: random arrivals, service, applicant response, objections, routing, resources, and rework conditional on fixed parameters.
- Parameter/model uncertainty: sampling uncertainty, missing-start decomposition, latent objections, incomplete thresholds, rare emergencies, and dependency structure.

Use an outer loop over plausible calibrated parameter sets and an inner loop of replications. Report the distribution of policy differences across both loops, not only a single fitted point estimate. Perform one-at-a-time and global sensitivity analysis on peak multipliers, response tails, objection prevalence, rework, bundle rules, calendars, and intervention adoption. Heavy-tailed durations should use empirical bootstrap plus a fitted tail such as a generalized Pareto above a validated threshold, or a mixture distribution with a high quantile cap only if operationally justified. Do not hide the tail by default Winsorization; report p95/p99 and conditional tail expectation, and check that a small number of extreme cases is not driving the conclusion.

Stop adding replications only when the predeclared precision target is met, for example a paired-mean half-width below 5% of the baseline mean, a median-difference half-width below 1–2 days where operationally meaningful, and an SLA-proportion half-width below 2 percentage points. If competing policies remain within the uncertainty interval, the result is “no demonstrated difference,” not an exact ranking.

## 6. Validation strategy

Face validation should involve clerks, planners, inspectors, legal staff, and process owners. Review the event calendar, precedence and join logic, routing predicates, queue priorities, rework paths, inspection bundling, and policy mechanisms with scenario walkthroughs. Ask SMEs to inspect simulated traces of ordinary, missing-document, complex-variance, objection, and peak-burst cases.

For event-log replay validation, replay or initialize the model with observed submission times and observed case attributes, then compare simulated activity sequences and terminal outcomes with the log. Use PM4Py token replay or alignments against a properly constructed baseline model to identify deviations, but retain deviations as evidence about routing uncertainty rather than deleting them to improve fitness. Compare the timing of known events and the number of cases still open at each observation date; completion-only data should be validated as total elapsed time, not falsely decomposed service time.

Distributional validation should compare, overall and by case type, district, season, and variant family:

- case completion time, median, p90, p95, and tail conditional mean;
- activity throughput, inter-event delays, and known service-time distributions;
- branch and variant shares, rework-loop counts, appeals, objections-as-proxy durations, and terminal outcomes;
- queue waiting versus external waiting where the log identifies the distinction.

Use empirical CDF/quantile plots and distributional distances such as Wasserstein or KS as diagnostics, with practical tolerances agreed in advance. A good aggregate mean is insufficient if the Complex variance tail or D3/D5 district effects are wrong.

Resource-utilization validation should compare busy fractions, daily/weekly workload, concurrent work where observable, calendar closures, queue lengths, and throughput for each pool. Confirm that the simulated resource capacity matches HR calendars and that utilization does not exceed capacity except for explicitly modeled overtime or urgent work.

Bottleneck validation should compare the ranking and timing of queues: the completeness Monday spike, planning waits, environmental specialist queue, inspection queue/travel, public-notice tail, and legal/council effects. Check Little’s Law approximately for stable periods and verify that adding capacity moves the bottleneck in a plausible way. A policy that improves one queue while producing an implausibly large downstream queue is not validated.

For out-of-sample validation, fit on an early chronological segment and test on later months, including at least one peak period if available. Use rolling-origin evaluation across seasons, hold out architect clusters where feasible, and separately test a high-burst period. Recalibrate neither routing nor service distributions on the holdout when scoring it. For latent objections and missing starts, validate predictions against any later data or manually reviewed sample; otherwise present only scenario robustness, not empirical validation.

## 7. Decision criteria

Define the municipality’s legal SLA vector by case type before running the final comparison. If no legal targets are supplied, use baseline-relative guardrails rather than inventing a legal standard. The following are reasonable screening thresholds to discuss and pre-register:

- Primary effectiveness: at least a 10% improvement in median total duration or p90 total duration, or at least a 5 percentage-point increase in SLA compliance, with a 95% interval that excludes a material deterioration. Report both total elapsed time and municipal-controlled time.
- Tail protection: p95 and p99 must not worsen by more than 5% overall; for Complex variance and appeal/rework cases, a small average gain is not acceptable if the tail worsens materially.
- SLA by case type: no case type may lose more than 2 percentage points of compliance relative to baseline unless the council explicitly accepts that trade-off. Report Simple, New residential, Commercial, and Complex variance separately, not only a portfolio average.
- Fairness: compare median, p90, SLA compliance, and backlog age by district and architect-volume band. A candidate should not increase the worst-to-best district median gap by more than 5 days or 10% (use the stricter bound), nor increase a district’s p90 by more than 10% without an approved reason. For architects, use volume bands and shrinkage or minimum sample sizes so that one small architect is not overinterpreted; appointment slots must be monitored for access bias.
- Capacity: target ordinary sustained utilization around 70–85% for pools with variable work. Sustained utilization above 90% for four or more weeks is a fragility flag, even if the mean duration improves. Report overtime, idle time, temporary-inspector cost, and specialist capacity diversion.
- Rework and quality: missing-document loops, inspection rework, legal rework, appeals, and rejects must be reported separately. Unless a policy intentionally changes a quality rule, no material rework rate should increase by more than 1–2 percentage points; D2 and D8 require explicit safety/compliance review of false negatives.
- Backlog stability: terminal throughput should keep pace with arrivals over the measurement horizon, the end-of-horizon open backlog should not grow across successive seasonal cycles, and the count and age of cases over a municipality-defined aging threshold should not worsen. A lower average duration achieved by leaving cases unfinished fails this criterion.
- Robustness: prefer a policy that passes all guardrails in at least 90% of parameter-draw scenarios and has a positive net benefit in at least 80% of replications/scenarios. A policy that wins only under one missing-data or objection assumption is not robust.

After guardrails, rank the non-dominated policies on duration, SLA, cost, fairness, quality, and resilience. Use a predeclared weighted utility only for a final trade-off, publish the weights and sensitivity to them, and include a “no material difference” category when confidence intervals overlap. The simulation supports a decision; it cannot establish exact optimality without validated causal effects and an implementation pilot.

        )
    except TypeError:
        performance_dfg = pm4py.discover_performance_dfg(df)

    # PM4Py's arrival-average helper is useful when available. The manual
    # calculation makes the unit and definition explicit and is also used as
    # a compatibility fallback.
    case_starts = (
        df.groupby(CASE, as_index=False)[TS]
        .min()
        .sort_values(TS)
    )
    interarrival_days = case_starts[TS].diff().dropna().dt.total_seconds() / 86400
    arrival_average_days = float(interarrival_days.mean()) if len(interarrival_days) else np.nan
    try:
        case_arrival_average = pm4py.get_case_arrival_average(
            df, case_id_key=CASE, timestamp_key=TS
        )
    except (AttributeError, TypeError):
        case_arrival_average = arrival_average_days

    return {
        "variants": variants,
        "dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
        "performance_dfg": performance_dfg,
        "case_arrival_average_pm4py": case_arrival_average,
        "case_arrival_average_days_explicit": arrival_average_days,
    }


diagnostics = pm4py_diagnostics(log_df)


def add_time_columns(df: pd.DataFrame) -> pd.DataFrame:
    """Add observable elapsed gaps and conditional service/wait columns."""
    out = df.sort_values([CASE, TS], kind="stable").copy()
    out["previous_completion"] = out.groupby(CASE)[TS].shift(1)
    out["elapsed_since_previous_completion_hours"] = (
        out[TS] - out["previous_completion"]
    ).dt.total_seconds() / 3600.0

    if START in out.columns:
        out[START] = pd.to_datetime(out[START], utc=True)
        out["service_time_hours"] = (
            out[TS] - out[START]
        ).dt.total_seconds() / 3600.0
        out["waiting_time_hours"] = (
            out[START] - out["previous_completion"]
        ).dt.total_seconds() / 3600.0
        out["time_split_observed"] = True
    else:
        # The excerpt has completion timestamps only. The gap is total elapsed
        # time, not waiting; leaving these columns NA prevents false precision.
        out["service_time_hours"] = np.nan
        out["waiting_time_hours"] = np.nan
        out["time_split_observed"] = False
    return out


timed_log_df = add_time_columns(log_df)

def parse_process_tree_checked(text: str) -> Optional[Any]:
    """Parse when supported; otherwise require an explicit routing graph."""
    parser = getattr(pm4py, "parse_process_tree", None)
    if parser is None:
        # Some PM4Py versions expose discovery/conformance APIs but not this
        # convenience parser. The simulation must then use a programmatic
        # ProcessTree or the Router below; silently treating text as a model
        # would be unsafe.
        return None
    try:
        return parser(text)
    except Exception as exc:
        # The notation is a readable specification, but parser grammars vary
        # by PM4Py version and may not accept this exact shorthand/whitespace.
        print(f"Process-tree parse requires explicit conversion: {exc}")
        return None
