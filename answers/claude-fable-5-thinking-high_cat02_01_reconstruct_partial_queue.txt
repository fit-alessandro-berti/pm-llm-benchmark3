# 1. Assumptions and notation

All clock times are on 2026-05-12; all durations are in minutes. Stations: S1 = Incoming Inspection (resources I1, I2), S2 = Calibration (resources C1, C2). Observation window: 08:00–14:00 (T = 360 min per resource; C2 has 345 min available because of the 10:55–11:10 outage).

- **A1 (event-order convention for ties).** When a rounded exit and a rounded entry share the same timestamp (e.g., P07 ends on C1 at 11:00 and P09 starts on C1 at 11:00), the exit is processed first. Intervals are half-open: a case occupies a queue during [entry, service_start) and a server during [service_start, service_end). This prevents phantom double-occupancy created purely by 5-minute rounding.
- **A2 (rounding treatment).** Reported times are used as point values for central estimates. Any single duration built from two rounded stamps carries roughly ±5 min uncertainty; I therefore avoid reporting station aggregates to better than ~5 min precision, and I do not treat 0–5 min discrepancies (back-to-back handovers, the I1/I2 5-min inter-job gaps) as real anomalies.
- **A3 (capacity).** I1, I2, C1, C2 are single-task servers; two jobs may not truly overlap on one resource. Same-minute handovers are allowed under A1. C2 is unavailable 10:55–11:10.
- **A4 (queue-entry definitions).** A case enters the S1 queue at `arrival_s1` and enters the S2 queue at `s1_end` (as stated in the scenario). No bypassing (given).
- **A5 (bounds for MISSING starts).** Each MISSING start is bounded below by max(queue entry, end of the same resource's latest earlier job, end of C2 maintenance where applicable) and above by the activity's own end (nonnegative service). This yields:
  - P05 S2 start ∈ [09:45, 10:15] (entry 09:25; C1 busy with P03 until 09:45);
  - P07 S1 start ∈ [09:25, 10:00] (arrival 08:45; I1 busy with P05 until 09:25 — an earlier start would double-book I1);
  - P11 S2 start ∈ [12:00, 12:25] (entry 11:05; maintenance until 11:10; C2 busy with P08 11:15–12:00);
  - P15 S1 start ∈ [11:40, 12:15] (arrival 10:10; I1 busy with P13 until 11:40; next I1 job P17 at 12:20 is not binding).
- **A6 (central imputation).** Central start = max(lower bound, end − median observed service at that station), i.e., a "typical-service" imputation capped by feasibility. Median observed service: S1 = 30, S2 = 40. This gives P05 → 09:45, P07 → 09:30, P11 → 12:00, P15 → 11:45. For P05 and P11 the feasibility cap binds, which is itself informative (see §6). This is also consistent with work conservation: whenever those servers freed up, a nonempty queue existed, so idling would be unexplained.
- **A7 (scenario endpoints).** "Early" scenario = lower bound of each MISSING start (maximum service, minimum wait, maximum utilization). "Late" scenario = end − 5 min (one rounding grid unit of service; minimum defensible service, maximum wait, minimum utilization). A literal zero-service start equal to the end time is kept only as a mathematical bound, not as a scenario.
- **A8 (censoring).** OPEN activities (P15-S2, P17-S2, P21-S1) contribute *elapsed* service up to 14:00 to busy time and WIP; their *final* service times are right-censored and never averaged together with completed services. Cases waiting at 14:00 (P16, P18, P19, P20 for S2; P22 for S1) contribute right-censored waits, reported as "≥ x", and they remain in queue/WIP integrations until 14:00. They are not discarded.
- **A9 (arrival semantics).** `arrival_s1` is an external arrival stamp from another system but rounded identically; I treat it as comparable to the operational stamps (its cross-system offset is an additional unquantified uncertainty noted in §6).
- **A10 (rate buckets).** Subperiod rates use half-open intervals [a, b) so no event is double-counted.

Notation: Wq(S) = queue waiting time at station S; Sv(S) = active service time; sojourn(S) = Wq + Sv; case total sojourn = `s2_end` − `arrival_s1`; WIP(S) = cases physically at station S (queue + in service); total WIP = cases arrived but not yet finished S2.

# 2. Reconstruction method and formulas

**Waiting, service, sojourn.**
- Wq(S1) = `s1_start` − `arrival_s1`; Sv(S1) = `s1_end` − `s1_start`; analogous for S2 with queue entry at `s1_end`.
- Case total sojourn = `s2_end` − `arrival_s1`. Note this is *exactly observed* for all 14 completed cases, including P05, P07, P11, because both endpoints are recorded; missingness only blurs the internal split between wait and service.
- For OPEN activities: elapsed service = 14:00 − start (a lower bound on final service). For blank next-station events: censored wait = 14:00 − queue entry (a lower bound on final wait).

**Lower/central/upper estimates.** For each MISSING start I carry the A5 interval through every formula: the early scenario minimizes waits and maximizes service/busy time; the late scenario does the reverse; the central scenario uses A6. Every aggregate below is reported either as a central value with a scenario range, or as a bound when censoring makes a point estimate indefensible.

**Queue length and WIP.** Piecewise-constant counting processes built from (entry, +1) and (exit, −1) events, with A1 tie-breaking (exits before entries). Time-average level = (∫ level dt)/360; peak = max level. Censored cases simply never emit their exit event inside the window.

**Throughput/rates.** Arrivals, S1 completions, and system departures (S2 completions) counted per half-open subperiod [08:00,10:00), [10:00,12:00), [12:00,14:00), divided by subperiod length.

**Busy time and utilization.** Busy(resource) = Σ (min(end, 14:00) − start) over its jobs, with MISSING starts spanning the scenario range and OPEN ends censored at 14:00. Utilization = busy / available, where available = 360 min except C2 = 345 min (A3). Because P21, P15-S2, P17-S2 are still running at 14:00, utilization is *not* inferred from completed cases alone.

**Little's Law.** Two forms:
1. *Identity (finite-window) form:* time-average queue length ≡ (total wait accrued inside the window, censored waits counted up to 14:00) / 360. This holds by construction and is used as an internal-consistency check between the wait table and the queue-length integration.
2. *Stationary form* L = λ·W, applied only on 09:30–11:30 for the S1 queue, the only stretch where the S1 queue level is roughly stable (fluctuating 4–6) rather than ramping; even there I treat it as approximate (see §5).

# 5. Bottleneck and temporal interpretation

**Evidence (directly computable from the log):**

1. **Demand exceeded S1 capacity all morning, most severely early.** Arrivals ran at 6.5/h in 08:00–10:00 and 4.0/h in 10:00–12:00, while S1 completed only 3.0–3.5/h throughout. S1 waits grew near-monotonically from 5 min (P01) to ~105 min (P20), the S1 queue peaked at 7 (~11:30), and S1 station WIP peaked at 8. S1 service itself is stable (20–35 min), so the growth is pure congestion, not service degradation.
2. **S1's effective capacity is ~3.4–3.7/h, below its nominal 4.2/h.** I2 shows a metronomic 5-min gap between consecutive jobs (P02→P04→…→P20, every handover exactly 5 min), and I1 shows the same pattern where observable. Whether this is changeover time or rounding artifact, the effective slot is ~35 min per job per server.
3. **S2's capacity is ~3.0/h (2 servers × ~40 min), below S1's output rate.** Consequently, once S1 began delivering at full rate (~10:00 onward), the S2 queue grew: completed S2 waits rose from 5–25 min (entries before 10:00) to 45–75 min (later entries), and at 14:00 four cases were queued for S2 with censored waits up to ≥85 min (P16) while both calibrators were busy. The S2 queue peaked at 5 (13:45–13:55) and was still 4 at the window end — growing, not draining.
4. **System departure rate converged to S2's capacity:** 1.5/h, then 2.5/h, then 3.0/h in the last two hours — exactly 2 servers/40 min. The last-period S1 completion rate (3.5/h) exceeded the departure rate (3.0/h), which is the direct flow-balance signature of S2 being the binding constraint at the end.
5. **The C2 outage (10:55–11:10) is small but visible.** C2 finished P06 at 10:50, sat idle/maintained through 11:10, and started P08 at 11:15: P08's 55-min S2 wait (versus 25 min for its neighbor P09) contains roughly 15–20 min directly attributable to the outage. P10's reroute to C1 at 11:45 (breaking the earlier I2→C2 pairing) is consistent with load rebalancing around the outage. Lost capacity ≈ 15 min ≈ 0.4 of a calibration — a real but second-order effect against a backlog measured in hours.

**Interpretation (labeled as such):** the morning is a *time-varying combination*, with a handoff. From 08:00 to roughly 12:00, S1 is the operative bottleneck: the arrival surge piles up in front of inspection, and early on S2 is actually starved (C1/C2 show idle gaps before ~09:45 and S2 waits are short). From roughly 12:00 to 14:00, arrivals nearly stop (only P22), S1 drains its queue from ~7 to 1, and the backlog migrates downstream: S2, with the lowest effective capacity in the chain (3.0/h vs S1's ~3.5/h), becomes the binding constraint and its queue is still growing at 14:00. Structurally — i.e., if arrivals persisted above 3/h — S2 is the long-run bottleneck; the morning's *experienced* pain was mostly S1's because the surge hit it first.

**Hypotheses (not directly verifiable from this log):** (i) the uniform 5-min inter-job gaps at S1 are changeovers rather than rounding, which would make S1's effective capacity genuinely ~3.4/h; (ii) P11's impossible-to-be-typical service time (≤25 min on C2 vs an observed C2 minimum of 40) reflects delayed logging of P08's completion or undocumented assistance rather than a genuinely fast calibration; (iii) P10's C1 assignment was a deliberate dispatcher reaction to the outage.

# 6. Missingness, censoring, and sensitivity analysis

**What is missing/censored and what each does:** two MISSING S1 starts (P07, P15) and two MISSING S2 starts (P05, P11) blur the wait/service split for those cases and put a 245–315 min range on I1's busy time; three OPEN activities (P21-S1, P15-S2, P17-S2) right-censor service times; five censored waits (P16, P18, P19, P20 at S2; P22 at S1) right-censor the upper tail of the waiting distribution — dropping them would understate late-morning congestion badly, since the largest S2 wait among *completed* cases (75) is smaller than the censored ≥85 of P16. Rounding adds ±5 min to every duration and manufactures ties (P07/P09 on C1 at 11:00), handled by A1. The C2 outage removes 15 min of capacity and demonstrably delayed P08.

**Three scenarios for the four MISSING starts (A5–A7):**

| quantity | early (starts at lower bound) | central (typical service, feasibility-capped) | late (end − 5 min) |
|---|---|---|---|
| P05 S2 (wait / service) | 20 / 30 | 20 / 30 | 45 / 5 |
| P07 S1 (wait / service) | 40 / 35 | 45 / 30 | 70 / 5 |
| P11 S2 (wait / service) | 55 / 25 | 55 / 25 | 75 / 5 |
| P15 S1 (wait / service) | 90 / 35 | 95 / 30 | 120 / 5 |
| I1 utilization | 88% | 85% | 71% |
| C1 utilization | 83% | 83% | 76% |
| C2 utilization (of 345 min) | 78% | 78% | 72% |
| S1 queue: time-avg / peak | 4.1 / 7 | 4.1 / 7 | 4.3 / 7 |
| S2 queue: time-avg / peak | 2.1 / 5 | 2.1 / 5 | 2.3 / 5 |

**Stable conclusions (survive all scenarios, and ±5 min rounding):** both stations are heavily loaded; S1 waits ramp 5 → ~105+ min; the S2 backlog builds through the morning and is unresolved at 14:00; peak queues (7 at S1, 5 at S2), peak total WIP (13), all throughput rates, I2's utilization (~81%, fully observed), the end-of-window state (8 cases in system), the bottleneck handoff story of §5, and every completed case's *total* sojourn. The queue/WIP profiles barely move (≤0.2 cases in time-average) because the four disputed starts shift only minutes of queue-vs-service classification.

**Unstable conclusions:** I1's utilization (71–88% — the widest gap, driven by P07 and P15 together contributing 0–70 min of unobserved busy time); C2's utilization (72–78%); the wait/service split for P05, P07, P11, P15 individually; and any claim about P11's true calibration duration. The "late" scenario is mechanically possible but operationally implausible: it requires three servers to have idled 25–50 min while queues of 4–7 cases waited, contradicting every fully observed handover in the log (which are all ≤ 10 min). I therefore weight the early/central scenarios, but no headline conclusion depends on that choice.

**Little's-Law checks (only where defensible):**
- *Identity form, full window (always valid):* accrued S1 queue-wait = 1490 min → time-average S1 queue = 1490/360 ≈ 4.14, matching the event-sweep integration exactly; S2: 770/360 ≈ 2.14, also matching. This validates internal consistency of the wait table and the queue profiles, including censored contributions.
- *Stationary form, S1 queue, 09:30–11:30 (the only quasi-stable stretch):* λ ≈ 4.0/h, mean Wq of that arrival cohort ≈ 94 min → L = λW ≈ 6.2 vs the observed time-average level of ≈ 5.5 in the same window. The ~13% gap is consistent with residual non-stationarity (waits were still lengthening) plus rounding; I report it as approximate agreement, not confirmation. I deliberately do *not* apply L = λW system-wide over 08:00–14:00: the system is a transient ramp (WIP 0 → 13 → 8), arrival and departure rates never equalize, and the naive calculation (e.g., λ_dep·W_dep ≈ 0.05/min × 137 min ≈ 7 vs actual mean WIP 9.5) mixes cohorts and would be misleading.

        df.loc[df[st + "_end_status"] == "OPEN", st + "_end_ts_c"] = W_END
    df["s1_wait"] = df["s1_start_ts_i"] - df["arrival_s1_ts"]
    df["s1_serv"] = df["s1_end_ts_c"] - df["s1_start_ts_i"]      # elapsed if OPEN
    df["s2_wait"] = df["s2_start_ts_i"] - df["s1_end_ts"]
    df["s2_serv"] = df["s2_end_ts_c"] - df["s2_start_ts_i"]      # elapsed if OPEN
    # right-censored waits: still waiting at 14:00
    df.loc[(df["s1_start_status"] == "BLANK") & df["arrival_s1_ts"].notna(),
           "s1_wait_cens"] = W_END - df["arrival_s1_ts"]
    df.loc[(df["s2_start_status"] == "BLANK") & df["s1_end_ts"].notna(),
           "s2_wait_cens"] = W_END - df["s1_end_ts"]
    return df

def mins(td):
    return td.dt.total_seconds() / 60 if hasattr(td, "dt") else td.total_seconds() / 60

# --- queue-length / WIP profiles with an explicit tie convention -------------
def profile(entries, exits, label):
    """Piecewise-constant count. Tie convention (A1): at identical rounded
    timestamps, exits are processed before entries, so a back-to-back handover
    at the same rounded minute does not create a phantom unit of queue/WIP.
    Censored cases never emit an exit event and stay counted until 14:00."""
    ev = [(t, +1) for t in entries.dropna()] + [(t, -1) for t in exits.dropna()]
    ev.sort(key=lambda x: (x[0], x[1]))  # -1 sorts before +1 at ties
    lvl, area, peak, prev = 0, 0.0, 0, W_START
    for t, d in ev:
        t = min(t, W_END)
        area += lvl * (t - prev).total_seconds() / 60
        prev = t
        lvl += d
        peak = max(peak, lvl)
    area += lvl * (W_END - prev).total_seconds() / 60
    return {"what": label, "time_avg": round(area / 360, 2), "peak": peak,
            "level_at_14": lvl}

def station_tables(df, scname):
    res = [
        profile(df["arrival_s1_ts"], df["s1_start_ts_i"], "S1 queue"),
        profile(df["s1_end_ts"],     df["s2_start_ts_i"], "S2 queue"),
        profile(df["arrival_s1_ts"], df["s1_end_ts"],     "S1 WIP"),
        profile(df["s1_end_ts"],     df["s2_end_ts"],     "S2 WIP"),
        profile(df["arrival_s1_ts"], df["s2_end_ts"],     "Total WIP"),
    ]
    out = pd.DataFrame(res)
    out.insert(0, "scenario", scname)
    return out

# --- resource busy time and utilization (open work counted up to 14:00) ------
def utilization(df, scname):
    rows = []
    for res, st in [("I1", "s1"), ("I2", "s1"), ("C1", "s2"), ("C2", "s2")]:
        sub = df[df[st + "_resource"] == res]
        busy = (sub[st + "_end_ts_c"].clip(upper=W_END) - sub[st + "_start_ts_i"]).dropna()
        busy_min = mins(busy).sum()
        avail = 360 - (15 if res == "C2" else 0)   # C2 maintenance 10:55-11:10
        rows.append({"scenario": scname, "resource": res, "busy_min": round(busy_min),
                     "avail_min": avail, "util_%": round(100 * busy_min / avail, 1)})
    return pd.DataFrame(rows)

all_prof, all_util, views = [], [], {}
for sc in ["early", "central", "late"]:
    v = build_view(sc)
    views[sc] = v
    all_prof.append(station_tables(v, sc))
    all_util.append(utilization(v, sc))

print("\n=== Queue / WIP profiles (time-avg and peak, in cases) ===")
print(pd.concat(all_prof, ignore_index=True).to_string(index=False))
print("\n=== Resource busy time / utilization by scenario ===")
print(pd.concat(all_util, ignore_index=True).to_string(index=False))

c = views["central"]
print("\n=== Central-scenario case table (minutes; NaN = censored / not applicable) ===")
print(pd.DataFrame({
    "case": c["case"],
    "S1_wait": mins(c["s1_wait"]).round(0),
    "S1_serv": mins(c["s1_serv"]).round(0),
    "S2_wait": mins(c["s2_wait"]).round(0),
    "S2_serv": mins(c["s2_serv"]).round(0),
    "S1_wait_cens>=": mins(c["s1_wait_cens"]).round(0),
    "S2_wait_cens>=": mins(c["s2_wait_cens"]).round(0),
    "state": c["state_at_14_00"],
}).to_string(index=False))

print("\n=== Station summaries, central scenario (minutes) ===")
for st in ["s1", "s2"]:
    done = c[c[st + "_end_status"] == "OBS"]
    w = mins(c[st + "_wait"].dropna())
    s = mins((done[st + "_end_ts"] - done[st + "_start_ts_i"]).dropna())
    print(f"{st.upper()}: completions={len(done)}, wait mean={w.mean():.0f} "
          f"(min {w.min():.0f}, max {w.max():.0f}); service mean={s.mean():.0f} "
          f"(min {s.min():.0f}, max {s.max():.0f})")

print("\n=== Rates per subperiod (cases/hour, half-open intervals) ===")
edges = [W_START, pd.Timestamp(D + "10:00"), pd.Timestamp(D + "12:00"), W_END]
for a, b in zip(edges[:-1], edges[1:]):
    h = (b - a).total_seconds() / 3600
    arr = ((raw["arrival_s1_ts"] >= a) & (raw["arrival_s1_ts"] < b)).sum()
    s1c = ((raw["s1_end_ts"] >= a) & (raw["s1_end_ts"] < b)).sum()
    s2c = ((raw["s2_end_ts"] >= a) & (raw["s2_end_ts"] < b)).sum()
    print(f"[{a.strftime('%H:%M')},{b.strftime('%H:%M')}): arrivals {arr/h:.1f}, "
          f"S1 completions {s1c/h:.1f}, system departures {s2c/h:.1f}")

print("\n=== Little's Law ===")
# (a) Identity form over the full window: time-avg queue == accrued wait / T.
for st in ["s1", "s2"]:
    wsum = mins(c[st + "_wait"].dropna()).sum() + mins(c[st + "_wait_cens"].dropna()).sum()
    print(f"{st.upper()} queue: accrued wait {wsum:.0f} min / 360 min -> "
          f"time-avg queue {wsum/360:.2f} (identity; matches the sweep above)")
# (b) Stationary-form spot check, S1 queue, 09:30-11:30 (only quasi-stable stretch).
a, b = pd.Timestamp(D + "09:30"), pd.Timestamp(D + "11:30")
coh = c[(c["arrival_s1_ts"] >= a) & (c["arrival_s1_ts"] < b)]
lam = len(coh) / 2.0
Wq = mins(coh["s1_wait"].dropna()).mean()
print(f"S1 queue 09:30-11:30: lambda={lam:.1f}/h, W={Wq:.0f} min, "
      f"lambda*W={lam*Wq/60:.1f} vs observed avg level ~5.5 "
      f"(gap = residual non-stationarity + rounding)")

# --- PM4Py part ---------------------------------------------------------------
# Interval-event dataframe restricted to USABLE observations: activity instances
# with an observed (not imputed, not censored) start AND end, so PM4Py never
# sees fabricated timestamps.
recs = []
for _, r in raw.iterrows():
    for st, act in [("s1", "Incoming Inspection"), ("s2", "Calibration")]:
        if r[st + "_start_status"] == "OBS" and r[st + "_end_status"] == "OBS":
            recs.append({"case:concept:name": r["case"], "concept:name": act,
                         "start_timestamp": r[st + "_start_ts"],
                         "time:timestamp": r[st + "_end_ts"],
                         "org:resource": r[st + "_resource"]})
ev = pd.DataFrame(recs)
ev = pm4py.format_dataframe(ev, case_id="case:concept:name",
                            activity_key="concept:name",
                            timestamp_key="time:timestamp")

# Case-level projection on which PM4Py's case metrics are semantically valid:
# COMPLETE cases whose two activities are both fully observed.
full_cases = raw.loc[raw["state_at_14_00"] == "COMPLETE", "case"]
proj = ev[ev["case:concept:name"].isin(full_cases)].copy()
proj = proj.groupby("case:concept:name").filter(lambda g: len(g) == 2)

proj = pm4py.insert_case_service_waiting_time(
    proj, timestamp_key="time:timestamp", start_timestamp_key="start_timestamp")
proj = pm4py.insert_case_arrival_finish_rate(
    proj, timestamp_key="time:timestamp", start_timestamp_key="start_timestamp")

# NOTE on semantics: the following outputs are CASE-LEVEL, not station-level.
# - @@waiting_time is only the within-case gap between S1 end and S2 start; it
#   EXCLUDES the pre-S1 wait, because the external arrival is not an activity.
# - @@sojourn_time runs from first activity START (not arrival) to last end.
# - @@arrival_rate / @@finish_rate are inter-case spacings of first-activity
#   starts / last-activity ends, not station queue-entry rates.
cl = (proj.sort_values("time:timestamp").groupby("case:concept:name")
          .last()[["@@service_time", "@@waiting_time", "@@sojourn_time",
                   "@@arrival_rate", "@@finish_rate"]] / 60)
print("\n=== PM4Py CASE-LEVEL metrics (minutes; fully observed COMPLETE cases only) ===")
print(cl.round(1).to_string())

# On pm4py.convert_log_to_time_intervals: we deliberately do NOT use it for the
# station-level queue/WIP reconstruction. It extracts case-level time intervals
# between activity pairs, so it cannot represent (i) the external arrival,
# which is not an activity, (ii) right-censored OPEN activities, (iii) cases
# still waiting at 14:00 that have no S2 events at all, or (iv) the imputation
# scenarios for MISSING starts. The direct pandas sweep in `profile` handles
# censoring and the tie convention explicitly, which is safer here.
