## 1. Target definition

**Primary target.** A multi-state, competing-outcome target for **all credit applications**, not only activated accounts. At a defined early prediction time \(t_p\), the event of interest is:

\[
E = \{\text{the original application is activated at } A > t_p,\ \text{and defaults within 90 days after activation}\}
\]

with a fixed operational horizon \(H\) days after \(t_p\). Primary \(H=365\) days; sensitivity \(H=180\) days. The estimand is the cumulative incidence of \(E\) by horizon \(H\), conditional on the observed prefix \(X_{t_p}\):

\[
F_E(H \mid X_{t_p}) = P(E \text{ by } t_p+H \mid X_{t_p})
\]

while treating Rejected, Withdrawn, Transferred, and Activated-no-default as competing outcomes, and Still-open/immature/missing-feed cases as censored or missing according to the analysis.

- **Prediction time \(t_p\):** earliest of: 7 calendar days after Application Started; just after the 4th event; or just before the first Accept/Reject/Withdraw/Transfer/Account Activated event. Only events strictly before \(t_p\) may be used as features.
- **Unit of analysis:** original credit application case.
- **Population:** all 48,000 applications started 2024-01-01 through 2025-12-31, subject to as-of feature and outcome availability.
- **Outcome semantics:** Rejected/Withdrawn/Transferred are **not** “non-default.” They are competing non-activation events. Still-open and immature cases are censored. Default is only defined after activation.

**Credible alternative.** A conditional target:

\[
P(\text{default within 90 days after activation} \mid \text{eventually activated}, X_{t_p})
\]

This answers “among accounts that reach activation, what is default risk?” It does **not** answer “what is the risk for every application?” unless combined with a separate activation/acceptance model. A policy-specific counterfactual target, e.g. “default if every application were accepted,” would answer a causal question but requires much stronger untestable assumptions.

## 2. Cohort construction

**Inclusion.** All applications started 2024-01-01 through 2025-12-31. One row per original case. Features use only events with timestamp \(< t_p\). Outcomes use events up to data extraction 2026-02-15.

**Exclusion.** Only malformed records with invalid/missing case IDs, timestamps, or unrecoverable activity-name corruption. Do not exclude Rejected, Withdrawn, Transferred, Still-open, immature, or missing-feed cases by convenience.

**As-of rules.**
- Prediction features: available only if timestamp \(< t_p\).
- Activation: first occurrence of Account Activated after \(t_p\).
- Default label: `default_90d` is valid only if activation occurred and `label_available_at <= 2026-02-15`.
- Still-open: right-censored at data extraction or at \(t_p+H\), whichever is earlier.
- Transferred: primary analysis treats transfer out of the original case as a competing event. Sensitivity merges linked transfers using the 60% linkage table.
- Partner-originated missing feed: flagged and handled as censored in primary, missing-not-at-random in sensitivity.

## 3. Censoring and missing-label strategy

**Distinctions.**
- **Ordinary right censoring:** Still-open cases, activated cases not yet reaching 90-day maturity, and cases whose \(t_p+H\) exceeds extraction.
- **Delayed labels:** Feed arrives 7–35 days after the 90-day horizon. Use `label_available_at`, not merely activation time plus 90 days.
- **Selection through activation:** Default is observed only for activated accounts. Rejected/Withdrawn/Transferred are competing non-activation outcomes, not non-defaults.
- **Transfer:** Primary treats transfer as a competing event for the original case. Sensitivity merges linked transfers; unlinked transfers remain missing follow-up.
- **Permanently missing outcome feeds:** Partner-originated activated accounts have elevated missingness. This is likely non-random.

**Primary strategy.** Fit a multi-state/competing-risk model from \(t_p\):
1. Cause-specific hazards for Rejected, Withdrawn, Transferred, and Activation.
2. Conditional default hazard after activation, with right censoring at extraction or horizon.
3. Combine into the cumulative incidence of “Activated then default within 90 days” by \(H\).

Use inverse probability of censoring weighting for ordinary censoring. Flag partner/source-system missingness.

**Sensitivity analyses.**
- Treat transfer as censoring instead of competing; merge linked transfers.
- Use worst-case bounds for permanently missing feeds: all missing are defaults vs all missing are non-defaults.
- Re-estimate with \(H=180\) vs \(H=365\).
- Estimate the conditional default-among-activated model separately and compare with the composite target.

**Assumptions.**
- Censoring independent of outcome given covariates: partially testable via censoring diagnostics.
- Missing feed is MAR given observed partner/source/channel/region: fundamentally untestable.
- Transfer linkage missingness is ignorable: partially testable using linkage table.
- Counterfactual “default if rejected were accepted”: fundamentally untestable without stronger assumptions.

## 4. Prefix extraction

Define \(t_p\) per case as above. Extract only events with `time:timestamp < t_p`.

- **Fixed event-count prefixes:** \(k=4\). Use `pm4py.get_prefixes_from_log` after filtering the formatted event log to pre-\(t_p\) events. If fewer than \(k\) events exist, use the available events and add `prefix_length` and `short_prefix` indicators.
- **Elapsed-time prefixes:** all events within 7 days of Application Started, but never at or after \(t_p\) or the first terminal decision.
- **Short cases:** no padding with future events. Add indicators for number of pre-\(t_p\) events.
- **Repeated document loops:** preserve sequence. Create counts such as Credit Review  Request Documents  Credit Review loops, number of document requests, and time since last Credit Review.
- **Activity renaming after 2025-10-15:** map old activity names to canonical names before prefix extraction.
- **Duplicate events after migration:** drop exact duplicates on case, activity, timestamp, and resource; keep first. Do not drop legitimate repeated activities.
- **Future leakage prevention:** after prefix extraction, only prefix-event columns and static case attributes available at \(t_p\) may enter the feature table.

## 5. Process-aware features

**Static case attributes.**
`case:channel`, `case:region`, `case:requested_amount`, `source_system`, application start month, policy regime before/after 2025-07-01, migration regime before/after 2025-10-15.

**Prefix-derived features.**
Control-flow sequence, first/last activity, variant ID, number of events, distinct activities, rework loops, document-request count, elapsed time since start, inter-event time summaries, time in Identity/KYC Check, time in Credit Review, latest `risk_score` update strictly before \(t_p\), and whether Credit Review has been reached.

**Resource/queue features.**
Resource IDs observed before \(t_p\), resource workload in a prior historical window, queue length at the time of each pre-\(t_p\) event, and time since prior case by the same resource. Resource experience must be reconstructed at event time or dropped; extraction-time experience is not valid.

**Cohort/calendar features.**
Policy period, migration period, day-of-week, month, holiday indicators, and channel/region macros only if available before \(t_p\).

**Historical reference features.**
Variant frequencies, activity frequencies, resource experience, and queue baselines computed only from training-period data. Never compute reference values using validation/test or future events.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Post-decision outcome of credit review | Only after final credit decision; not available at early \(t_p\) | Drop | Directly encodes the decision and likely correlates with default |
| `decision_reason` | Populated at/after Accept/Reject | Not available before decision; may reveal outcome | Drop | Leaks acceptance/rejection and downstream default risk |
| `collection_status` | Updated after activation; may directly reveal default | Only after activation and collection activity | Drop | Post-outcome leakage |
| Future events: Contract Signed, Account Activated, Collections Contact, Default Recorded | Occur after prediction point | Only events \(< t_p\) | Drop post-\(t_p\) events | Future process and outcome leakage |
| `documents_total` | Nightly snapshot can include same-day later uploads | Use previous-day snapshot or timestamped value \(< t_p\) | Repair or drop | Same-day future uploads can leak post-prediction documents |
| Updated `risk_score` | Multiple updates; later updates may reflect decision/default | Latest update strictly \(< t_p\) | Repair | Keep only as-of risk score |
| Resource experience | Stored at extraction time, not event time | Reconstruct from HR history if possible; else unavailable | Repair or drop | Extraction-time experience leaks future tenure |
| `label_available_at` | Label metadata | Never a feature | Drop from features | Only for maturity and censoring logic |
| `default_90d` | Target label | Never a feature | Drop from features | Direct target leakage |
| Account Activated | Future state for early prediction | Only as outcome/state | Drop from features | Leaks activation outcome |
| Contract Signed | Future event | Only events \(< t_p\) | Drop | Post-prediction leakage |
| `source_system` | May correlate with missing feed | Available at start | Keep with missingness audit | Useful for missingness and bias monitoring |

## 7. Validation design

Use **temporal validation**, not a random split. Random splits leak policy periods, migration effects, outcome maturity, and temporal autocorrelation.

**Primary temporal split.**
- Train: applications started 2024-01-01 to 2024-12-31.
- Validation: 2025-01-01 to 2025-06-30.
- Test: 2025-07-01 to 2025-12-31, with policy change on 2025-07-01 and migration on 2025-10-15.

**Backtesting.**
Rolling-origin quarterly evaluation: train on all matured data before an origin, predict the next quarter, advance the origin. At each origin, only use cases whose labels are mature as of that simulated extraction date.

**Policy change.** Include policy regime as a feature or fit separate pre/post-policy models. Evaluate calibration separately before and after 2025-07-01.

**System migration.** Normalize renamed activities, deduplicate events, and evaluate pre/post 2025-10-15. Monitor performance degradation after migration.

**Label maturity.** Never treat immature cases as non-default. At each origin, censor cases without mature labels and use time-aware evaluation.

**Calibration and subgroups.** Report calibration plots for cumulative incidence, Brier score, integrated Brier score, time-dependent AUC, and concordance. Evaluate by channel, region, source_system, partner vs direct, and policy period.

**Metrics for chosen target.**
For the competing-risk composite target: cause-specific time-dependent AUC, cumulative-incidence calibration, Brier score at \(H\), integrated Brier score. For conditional default: ROC-AUC, PR-AUC, calibration, and time-to-default concordance. For multi-state: multiclass log loss and confusion at \(H\), but always with censoring-aware metrics.

## 8. Limitations and decision-use boundary

This study can claim **predictive association** under the observed activation policy, observed maturity, and stated missingness assumptions. It can rank applications by estimated risk of activation followed by 90-day default.

It cannot claim:
- causal effect of rejecting or accepting an application;
- counterfactual default risk if non-activated cases had been activated;
- fairness or regulatory validity without separate audit;
- generalizability to new policy thresholds, new partner platforms, or changed collection practices.

Selection effects are central: activation is non-random, transfer follow-up is incomplete, and partner outcome feeds are selectively missing. These are not equivalent to ordinary missingness.

Deployment can change the data-generating process in at least three ways:
1. Early warnings change manual review, acceptance, or limit-setting, creating feedback loops.
2. Interventions after warning change default behavior, so the modeled outcome distribution shifts.
3. Applicant behavior changes because of communication, causing different withdrawal/rejection patterns.
4. Policy thresholds may change in response to model outputs.
5. Collection and `collection_status` definitions may change operationally.

Decision-use boundary: use for prioritization, monitoring, and capacity planning under the observed policy. Do not use for automated adverse action, fair-lending decisions, or causal policy evaluation without stronger design and governance.

# Assumptions: local CSV, PM4Py installed, timestamps UTC-ish, migration activity map supplied.
import pandas as pd
import numpy as np
import pm4py
from datetime import timedelta

CUTOFF = pd.Timestamp("2026-02-15", tz="UTC")
POLICY_CHANGE = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION = pd.Timestamp("2025-10-15", tz="UTC")
PREFIX_EVENTS = 4
PREFIX_DAYS = 7
HORIZON_DAYS = 365  # sensitivity: 180

raw = pd.read_csv("applications_events.csv")
for c in ["time:timestamp", "label_available_at", "data_extract_time"]:
    raw[c] = pd.to_datetime(raw[c], errors="coerce", utc=True)

# Basic hygiene and migration activity normalization.
raw = raw.sort_values(["case:concept:name", "time:timestamp", "concept:name"])
raw = raw.drop_duplicates(
    subset=["case:concept:name", "concept:name", "time:timestamp", "org:resource"],
    keep="first"
)
activity_map = {
    # "Old migration name": "Canonical name",
}
raw["concept:name"] = raw["concept:name"].replace(activity_map)

# PM4Py formatting.
df = pm4py.format_dataframe(
    raw,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

TERMINAL_DECISION = {"Accepted", "Rejected", "Withdrawn", "Transferred", "Account Activated"}
ACTIVATION = "Account Activated"
DEFAULT = "default_90d"

def summarise_case(g):
    g = g.sort_values("time:timestamp")
    start = g["time:timestamp"].min()
    decision_time = g.loc[g["concept:name"].isin(TERMINAL_DECISION), "time:timestamp"].min()
    kth_time = g["time:timestamp"].iloc[min(len(g) - 1, PREFIX_EVENTS - 1)] + timedelta(seconds=1)
    candidates = [start + timedelta(days=PREFIX_DAYS), kth_time]
    if pd.notna(decision_time):
        candidates.append(decision_time - timedelta(seconds=1))
    pred_time = min(candidates)

    act_time = g.loc[g["concept:name"].eq(ACTIVATION), "time:timestamp"].min()
    label_ready = g["label_available_at"].dropna().max() if g["label_available_at"].notna().any() else pd.NaT
    default_vals = g[DEFAULT].dropna()
    default_90d = default_vals.iloc[0] if len(default_vals) else np.nan

    terminal = set(g["concept:name"])
    rejected = "Rejected" in terminal
    withdrawn = "Withdrawn" in terminal
    transferred = "Transferred" in terminal
    activated = pd.notna(act_time)
    mature_default = activated and pd.notna(label_ready) and label_ready <= CUTOFF

    if activated and mature_default:
        state = "activated_default" if default_90d == 1 else "activated_no_default"
    elif rejected:
        state = "rejected"
    elif withdrawn:
        state = "withdrawn"
    elif transferred:
        state = "transferred"
    elif activated and not mature_default:
        state = "activated_immature_or_missing"
    else:
        state = "still_open_or_censored"

    return pd.Series({
        "case_start": start,
        "pred_time": pred_time,
        "activation_time": act_time,
        "label_ready": label_ready,
        "default_90d": default_90d,
        "mature_default": mature_default,
        "cohort_state": state,
        "policy_regime": "post_policy" if start >= POLICY_CHANGE else "pre_policy",
        "migration_regime": "post_migration" if start >= MIGRATION else "pre_migration",
    })

case_df = df.groupby("case:concept:name").apply(summarise_case).reset_index()

# Temporal split by case start. Random split would leak policy/migration/maturity.
train = case_df[case_df["case_start"] < pd.Timestamp("2025-01-01", tz="UTC")].copy()
val = case_df[(case_df["case_start"] >= pd.Timestamp("2025-01-01", tz="UTC")) &
              (case_df["case_start"] < POLICY_CHANGE)].copy()
test = case_df[case_df["case_start"] >= POLICY_CHANGE].copy()

# Build prefix events: only events strictly before each case pred_time.
pref = df.merge(case_df[["case:concept:name", "pred_time"]], on="case:concept:name", how="left")
pref = pref[pref["time:timestamp"] < pref["pred_time"]].copy()
pref = pm4py.format_dataframe(
    pref,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# Fixed-length prefixes. Short cases are retained through prefix_features below.
prefixes = pm4py.get_prefixes_from_log(pref, length=PREFIX_EVENTS)

def prefix_features(g):
    g = g.sort_values("time:timestamp")
    acts = g["concept:name"].tolist()
    return pd.Series({
        "n_events": len(g),
        "n_distinct_activities": g["concept:name"].nunique(),
        "first_activity": acts[0] if acts else None,
        "last_activity": acts[-1] if acts else None,
        "time_since_start_hours": (g["time:timestamp"].max() - g["time:timestamp"].min()).total_seconds()/3600 if len(g) else np.nan,
        "rework_credit_review": sum(1 for i in range(1, len(acts)) if acts[i] == "Credit Review" and acts[i-1] == "Request Documents"),
        "latest_risk_score": g["risk_score"].dropna().iloc[-1] if g["risk_score"].notna().any() else np.nan,
        "channel": g["case:channel"].iloc[0] if "case:channel" in g else None,
        "region": g["case:region"].iloc[0] if "case:region" in g else None,
        "requested_amount": g["case:requested_amount"].iloc[0] if "case:requested_amount" in g else np.nan,
        "source_system": g["source_system"].iloc[0] if "source_system" in g else None,
    })

features = pref.groupby("case:concept:name").apply(prefix_features).reset_index()
features = features.merge(
    case_df[["case:concept:name", "pred_time", "cohort_state", "case_start",
             "policy_regime", "migration_regime"]],
    on="case:concept:name", how="left"
)

# Process-structure audit from prefix log only.
variants = pm4py.get_variants(pref)
dfg, start_acts, end_acts = pm4py.discover_dfg(pref)

# Optional PM4Py temporal/waiting features if available in your version.
try:
    temp_feat = pm4py.extract_temporal_features_dataframe(pref)
    # temp_feat = pm4py.insert_case_service_waiting_time(pref)  # only on prefix log
except Exception as exc:

    print("Optional PM4Py temporal/waiting features unavailable:", exc)

# Leakage audit: forbidden columns must not be in feature table.
forbidden = {

      pd.Series({"train": len(train), "val": len(val), "test": len(test)}))
