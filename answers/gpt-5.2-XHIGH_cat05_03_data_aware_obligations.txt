## 1. Temporal Data Semantics

- **State reconstruction (no backward leakage)**: For each case, process events in chronological order and maintain a “latest known” state for `amount`, `risk_level`, `jurisdiction`, `customer_type`, and `exemption_id`. Blank cells mean **no update** at that event, so the prior value carries forward. Never copy the **final** case state backward in time.
- **Total event order**: Sort by `time:timestamp` (UTC) and break ties by `event_index` (source-system order). This creates a strict order \(e_a \prec e_b\) even when timestamps are equal. Consequence: within a shared timestamp, later `event_index` updates can change the state used at later events (and at release).
  - Example (given): **TX-311** has `Enhanced_Review` (event_index 3) and `Update_Jurisdiction` (event_index 4) at the same timestamp; therefore the jurisdiction becomes `DE` **after** the review in event order.
- **Event time vs. effective/record/evidence time**:
  - **Event time**: the log timestamp of each activity (e.g., `Release_Funds` at 09:40).
  - **Effective time** (default): when a data update governs obligations; unless explicitly stated otherwise, treat the update as effective at its event time.
  - **Record time**: when something is inserted/recorded (e.g., `Record_Exemption` can occur after release).
  - **Evidence time**: when an approval can be independently proven to have existed (e.g., qualified signature timestamp, certificate creation time, outage logs, reliable witness statements). Evidence time can support that an exemption approval existed earlier than record time.
  - **Validity interval**: `effective_from` ≤ trigger time < `expires` for exemptions.
- **Material changes and review validity**:
  - **Amount-dependent controls** (notably R1; and exemption scope checks) are sensitive to amount changes. Use R4’s semantics to decide whether an earlier review remains usable for amount-dependent obligations:
    - An **increase >20%** after the latest `Standard_Review` or `Enhanced_Review` invalidates that review for amount-dependent obligations.
    - A **decrease** does not by itself invalidate.
    - An increase from an **unknown** baseline is **not safely classifiable** (indeterminate).
  - Changes to **risk_level** or **customer_type** are material for R2; changes to **jurisdiction** are material for R1/R3/exemption scope.
- **Obligation evaluation point**: Evaluate each rule at `Release_Funds` using the **state as of that event** (post-updates up to that event in the total order). “After the latest material change” means the required review must occur **after** the last relevant change in that same event order.
- **Missing data**: Do not default unknowns to safe values. If a trigger cannot be established or excluded due to missing decisive data at the relevant time, classify the case outcome for that rule as **INDETERMINATE** unless other evidence resolves it.

### Concise pseudo-logic (R1–R7)

Let \(E_c\) be events of case \(c\). Define strict order:
\[
e_a \prec e_b \iff t(e_a) < t(e_b)\ \lor\ (t(e_a)=t(e_b)\ \land\ idx(e_a) < idx(e_b)).
\]
Let \(state(c,e).A\) be the last known value of attribute \(A\) over events \(\preceq e\) (blanks do not overwrite). “Current at event \(e\)” means \(state(c,e)\).

Define helper predicates/functions:
- \(release(e) \equiv act(e)=Release\_Funds\).
- \(enhanced(e) \equiv act(e)=Enhanced\_Review\); \(approve(e)\equiv act(e)=Compliance\_Approve\).
- \(screen(e)\equiv act(e)=Sanctions\_Screen\); \(listUpd(e)\equiv act(e)=Sanctions\_List\_Update\).
- \(known(x)\) is true if \(x\) is not missing.
- \(validEx(c,r)\) holds iff an exemption referenced at \(r\) is scope-valid and time-valid and supported by evidence that approval existed by \(t(r)\) (R5).
- \(Last(c,r,P)\) returns the latest event \(e\in E_c\) with \(e\prec r\) and predicate \(P(e)\) (undefined if none).

R7 (ordering): All temporal relations use \(\prec\) above (timestamp + `event_index`).

R6 (unknowns): If a rule’s trigger condition references any \(known(\cdot)\) value that is missing and no other evidence resolves it, outcome is **INDETERMINATE** (do not assume safe defaults).

R4 (amount-review invalidation): Let \(rev = Last(c,r, \lambda e.\ act(e)\in\{Standard\_Review,Enhanced\_Review\})\).
If \(known(amount(c,rev))\) and there exists \(k\) with \(rev\prec k \prec r\) and \(amount(c,k) > 1.2 \cdot amount(c,rev)\), then \(rev\) is invalid for amount-dependent obligations at \(r\).
If \(amount(c,rev)\) is unknown and a later amount becomes known, invalidation cannot be safely classified → INDETERMINATE for amount-dependent reliance on \(rev\).

R1: For each release event \(r\),
\[
Trigger\_R1(c,r) \equiv release(r)\land known(jur(c,r))\land known(amount(c,r))\land jur(c,r)\neq DE\land amount(c,r)\ge 100000.
\]
If \(Trigger\_R1(c,r)\) and \(\neg validEx(c,r)\), then require an \(er\) such that \(enhanced(er)\land er\prec r\land m\prec er\), where \(m\) is the latest “material change for R1” before \(r\) (at minimum: any jurisdiction change; and any amount increase that invalidates the last amount-dependent review under R4; conservative variants may also treat threshold-crossing as material).

R2: For each release event \(r\),
\[
Trigger\_R2(c,r)\equiv release(r)\land \big(risk(c,r)=HIGH\ \lor\ cust(c,r)=PEP\big)
\]
(unknown risk/customer → R6).
If \(Trigger\_R2(c,r)\), require an \(er\) and \(ap\) such that
\[
enhanced(er)\land approve(ap)\land m\prec er\prec ap\prec r,
\]
where \(m\) is the latest material change affecting R2 (risk/customer changes). Also require that the approval corresponds to the enhanced packet (given semantic fact).

R3: For each release event \(r\), let \(s=Last(c,r,screen)\). If there exists \(u\) with \(listUpd(u)\land s\prec u\prec r\) and \(addedJur(u)=jur(c,r)\), then require \(s2\) with \(screen(s2)\land u\prec s2\prec r\).

R5 (exemption validity): An exemption \(ex\) referenced at \(r\) is valid iff:
- approved_by = Head_Compliance;
- effective_from(ex) ≤ t(r) < expires(ex);
- scope matches: jurisdiction/customer_type/amount bounds at \(state(c,r)\);
- evidence supports that approval existed by \(t(r)\) (e.g., qualified signature time ≤ \(t(r)\); mere backdated display without corroboration is insufficient).

## 4. Ambiguities and Alternative Readings

- **TX-305 (INDETERMINATE)**:
  - **What would make it COMPLIANT**: an immutable release payload (or signed release message) proving amount at release and showing it was ≥100k (or <100k). If amount at release was indeed 150k and the `Enhanced_Review` is accepted as valid for that amount, R1 would be satisfied.
  - **What could make it NONCOMPLIANT**: evidence that the amount at release was ≥100k **and** that the enhanced review could not have considered the amount (e.g., a policy requiring the amount to be present in the review artifact), or that the actual released amount differed materially from settlement.
  - **Why settlement is insufficient alone**: the prompt states settlement is reliable **at settlement time** but release payload is not immutable; thus settlement amount is only weak evidence about the release-time amount.

- **TX-310 (INDETERMINATE)**:
  - **What would make it JUSTIFIED_EXCEPTION**: independent evidence that Head_Compliance approved EX-88 **before 10:00** (e.g., qualified signature timestamp ≤ 10:00, system audit log, email from Head_Compliance, voice recording, or a witness independent of the requester). Then R1 could be waived despite no enhanced review.
  - **What would make it clearly NONCOMPLIANT**: evidence that no approval existed before release (e.g., Head_Compliance calendar/audit shows approval granted only after 10:00; or an immutable workflow record shows approval time > release). The current certificate creation at 10:30 strongly undermines “document signed at 08:50,” but does not logically exclude an earlier oral approval—hence indeterminate rather than conclusively invalid.
  - **Interpretation sensitivity**: if the control standard requires **qualified** signing before relying on an exemption, EX-88 is invalid for the release and the case becomes NONCOMPLIANT.

- **TX-302 (explicit late-evidence handling)**:
  - **Why late `Record_Exemption` does not break validity here**: EX-77 has a qualified signature timestamp at 09:05, effective_from 09:00, and release at 09:40. The documented outage explains the 11:00 insertion, making it plausible record-time lag rather than post-hoc fabrication.
  - **If the signature evidence were absent**: relying solely on a backdated “displayed approval” would be weak under R5; validity could become INDETERMINATE. Note the case would still likely remain COMPLIANT because an `Enhanced_Review` occurred before release anyway.

- **TX-311 (same-timestamp ordering)**:
  - **If `event_index` were missing/unreliable**: the relative order of `Enhanced_Review` and jurisdiction change at 16:20 would be ambiguous, affecting whether the review was performed under US or DE jurisdiction and which state should govern at release. This could shift conclusions in more complex policies (e.g., if DE vs non-DE changed trigger conditions).
  - **If the jurisdiction change had an explicit earlier effective time** (not present): R7 would allow overriding the default “effective at event time,” changing the state at release and at review time.

- **Two additional interpretation-sensitive cases**:
  - **TX-306**: If “after the latest material data change” in R1 were interpreted as **after any amount change** (even <20%), then the 12:30 update would require a new enhanced review after 12:30, making the case NONCOMPLIANT. A harmonized reading is that R4 defines when amount changes are “material” for amount-dependent reliance (here <20% so review remains valid).
  - **TX-308**: If a strict process required re-review after any amount change, then the 14:25 decrease would require a new enhanced review after 14:25. R4 explicitly says decreases do not invalidate, supporting COMPLIANT under the stated policy.

            amt_at_review = amt
            invalidated = False
            indet_from_unknown = False
        else:
            if pd.notna(last_review_ts):
                if pd.isna(amt_at_review) and pd.notna(amt):
                    indet_from_unknown = True
                elif pd.notna(amt_at_review) and pd.notna(amt) and amt > 1.2 * amt_at_review:
                    invalidated = True
        out.append(
            {
                "last_review_ts": last_review_ts,
                "last_review_type": last_review_type,
                "amount_at_last_review": amt_at_review,
                "r4_invalidated": invalidated,
                "r4_indeterminate_from_unknown": indet_from_unknown,
            }
        )
    return pd.DataFrame(out, index=case_df.index)

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage**: If you use the final case attributes for all earlier events, you will mis-evaluate triggers (e.g., post-hoc jurisdiction or customer-type updates would be incorrectly assumed to have applied at earlier reviews).
2. **Conditional activation cannot be expressed**: R1 and R2 obligations activate only under data conditions at `Release_Funds` (amount/jurisdiction, risk/PEP). A control-flow model that “expects” `Enhanced_Review` in every trace will falsely flag compliant traces where the trigger never holds (e.g., TX-311 at release).
3. **Material changes after review**: R4 makes compliance depend on *how data changed after a review*. Control-flow alone can see that a review occurred, but not whether later amount changes invalidated it (TX-309).
4. **Post-hoc exemptions and evidence-time semantics**: Whether an exemption was valid at trigger time depends on evidence (signature/cert timestamps, outage logs), not just the presence of a `Record_Exemption` event. Control-flow sees the event order, but not evidential strength or the distinction between record time and approval time (TX-302 vs TX-310).
5. **Missing data produces indeterminacy**: Control-flow checkers often treat missing attributes as “not triggering” (implicitly safe). R6 requires treating missing decisive data as INDETERMINATE (TX-305).
6. **Same-timestamp ordering**: Many control-flow representations treat equal timestamps as concurrent or unordered. Here, `event_index` determines the governing state (TX-311), and that ordering can change whether a trigger holds or whether a review is “after” a change.
7. **External context changes (sanctions list)**: R3 depends on an external list update happening between screen and release. A pure trace of internal activities is insufficient unless the list update is modeled with its semantics and its linkage to the transaction’s jurisdiction (TX-304).
8. **Scope-checked exceptions**: Exemptions apply only to specific rules, jurisdictions, customer types, and amount ranges. Control-flow cannot validate scope without data-aware checks (R5).

## 7. Recommended Logging and Control Improvements

- **Immutable release payloads**: Log a signed/hashed `Release_Funds_Payload` containing amount, currency, jurisdiction, risk_level, customer_type, exemption references, and rule version evaluated at release.
- **Explicit timestamps for every notion of time**:
  - `event_time` (already present),
  - `effective_time` for attribute updates (when it should govern),
  - `record_time` (DB insert time),
  - `signature_time` / certificate metadata for approvals,
  - `evidence_source` and integrity hashes.
- **Rule and list versioning**: Include `policy_version` and `sanctions_list_version` identifiers at screening and at release, so R3 checks are deterministic.
- **Exemption scope as structured data**: Store `waives=[R1]`, jurisdiction scope, customer_type scope, amount bounds, effective_from/expires, and a cryptographic proof of approval by Head_Compliance.
- **Change provenance**: For each data update (`Update_Amount`, `Risk_Reclassify`, etc.), log `old_value`, `new_value`, source system, and reason code; this makes “material change” derivation auditable.
- **Stable event ordering**: Always log a monotonically increasing sequence number per case (stronger than `event_index`) and preserve it across system merges to avoid same-timestamp ambiguity.
- **Review artifacts linked to state**: Link each `Standard_Review`/`Enhanced_Review`/`Compliance_Approve` to the exact state snapshot (hash of payload) that was reviewed/approved, so it is clear whether later changes invalidate the reviewed facts.
- **Explicit “review invalidated” events** (optional): When R4-type thresholds are crossed, emit an automated `Review_Invalidated` event to force re-review before release.
