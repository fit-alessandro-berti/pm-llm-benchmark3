# 1. Policy Interpretation and Conflict Resolution

**Material Assumptions:**
- The event log contains only activity labels, timestamps, and resource identifiers. It lacks data attributes such as an "emergency" flag or "joint authorization" records.
- "Final outcome" in R3 refers to the terminal states of the onboarding decision: `Activate Vendor` or `Reject Vendor`.
- To evaluate traces against the strict procedural backbone, ad-hoc activities (e.g., `Request Clarification`, `Sanctions Escalation`, `Obtain Legal Opinion`) are assumed to be filtered out prior to replay.

**R5/R6 Conflict Resolution:**
The conflict lies between the Legal department's strict requirement (Opinion must precede Activation, R5) and the Operations department's exception (Emergency Activation can precede Opinion, R6).
- *Resolution 1 (Strict Compliance):* Enforce R5 strictly in the control-flow layer (e.g., via DECLARE `precedence`). Any emergency activation is flagged as a hard violation, requiring manual override outside the standard system.
- *Resolution 2 (Permissive Operations):* Relax the control-flow constraint to allow Activation before Opinion. Rely entirely on a post-hoc data-aware script to verify that the Opinion arrives within 24 hours.

**Chosen Resolution for Implemented Model:**
We choose **Resolution 1 (Strict Compliance)**. 
*Compliance Risk of Choice:* This creates false positives for legitimate emergency activations, potentially delaying critical operational needs. However, because the event log lacks the "emergency" attribute to distinguish valid emergencies from rogue activations, a strict control-flow block is the only way to guarantee no unapproved vendor is activated without an explicit, audited override.

# 2. Requirement-to-Formalism Mapping

| Requirement | Primary formalism | Exact encoding | Why this formalism | Redundancy or limitation |
|---|---|---|---|---|
| R1 (Reject/Activate mutually exclusive) | Log Skeleton | `never_together("Reject Vendor", "Activate Vendor")` | Naturally expresses mutual exclusion regardless of order. | Redundant with the XOR split in the Procedural model and DECLARE `noncoexistence`. |
| R2 (Manager/Compliance XOR) | Procedural | XOR split routing | Procedural models excel at enforcing strict, block-structured routing paths. | Redundant with Log Skeleton `never_together`. |
| R3 (Clarification cycles) | DECLARE | `altresponse("Request Clarification", "Receive Clarification")` | DECLARE handles non-block-structured loops and loose ordering elegantly. | Procedural models struggle with ad-hoc loops without becoming spaghetti-like. |
| R4 (Sanctions Esc -> Opinion) | DECLARE | `response("Sanctions Escalation", "Obtain Legal Opinion")` | Standard declarative rule for "if A happens, B must eventually follow". | Log Skeleton `always_after` is too strict if Opinion can happen without Escalation. |
| R5 (Opinion precedes Activation) | DECLARE | `precedence("Obtain Legal Opinion", "Activate Vendor")` | Directly maps to "B only if A has happened". | Conflicts with R6; enforces the Strict Compliance resolution. |
| R6 (Emergency Activation) | Resource/Data layer | Custom Python script checking timestamps | Requires time diff < 24h and external data (joint auth) not present in the log. | Cannot be expressed in activity-only formalisms. |
| R7 (Escalation after Screening) | DECLARE | `precedence("Run Sanctions Screening", "Sanctions Escalation")` | Enforces a prerequisite without forcing occurrence. | |
| R8 (EDD/Manager, Compliance/Manager no co-occur) | Log Skeleton | `never_together` for both pairs | Simple declarative mutual exclusion. | Redundant with procedural routing. |
| R9 (Four-eyes principle) | Resource/Data layer | `pm4py.filter_four_eyes_principle(...)` | Control-flow formalisms are resource-agnostic. | Requires `org:resource` attribute. |
| R10 (At most once: Activate, Reject, Release) | Log Skeleton | `activ_freq` set to `{0, 1}` for each | Directly restricts occurrence counts. | |
| R11 (Change Bank Details -> Suspend -> Verify -> Release) | DECLARE | `response("Change Bank Details", "Suspend Vendor")` | Loose temporal rules post-activation. | Procedural models struggle with post-completion ad-hoc changes. |
| R12 (Temporal expectations) | Temporal Profile | `pm4py.conformance_temporal_profile` | Built specifically for statistical time bounds. | Only flags statistical deviations, not absolute rules. |

# 3. Procedural Backbone

**1. Compact Formal Description:**
We use a block-structured Process Tree to represent the stable "happy path". 
`->( Receive, AND(Capture, Screen, Verify), Classify, XOR( ->(Reject, Close), ->(ManagerApp, Activate, Release, Close), ->(EDD, ComplianceApp, Activate, Release, Close) ) )`

**2. PM4Py Python Code:**
```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Leaves
receive = ProcessTree(operator=None, label="Receive Onboarding Request")
capture = ProcessTree(operator=None, label="Capture Master Data")
screen = ProcessTree(operator=None, label="Run Sanctions Screening")
verify = ProcessTree(operator=None, label="Verify Bank Account")
classify = ProcessTree(operator=None, label="Classify Risk")

reject = ProcessTree(operator=None, label="Reject Vendor")
close_rej = ProcessTree(operator=None, label="Close Onboarding")
seq_reject = ProcessTree(operator=Operator.SEQUENCE, children=[reject, close_rej])

mgr_app = ProcessTree(operator=None, label="Manager Approval")
act_low = ProcessTree(operator=None, label="Activate Vendor")
rel_low = ProcessTree(operator=None, label="Release First Payment")
close_low = ProcessTree(operator=None, label="Close Onboarding")
seq_low = ProcessTree(operator=Operator.SEQUENCE, children=[mgr_app, act_low, rel_low, close_low])

edd = ProcessTree(operator=None, label="Enhanced Due Diligence")
comp_app = ProcessTree(operator=None, label="Compliance Approval")
act_high = ProcessTree(operator=None, label="Activate Vendor")
rel_high = ProcessTree(operator=None, label="Release First Payment")
close_high = ProcessTree(operator=None, label="Close Onboarding")
seq_high = ProcessTree(operator=Operator.SEQUENCE, children=[edd, comp_app, act_high, rel_high, close_high])

xor_routing = ProcessTree(operator=Operator.XOR, children=[seq_reject, seq_low, seq_high])
and_checks = ProcessTree(operator=Operator.PARALLEL, children=[capture, screen, verify])

procedural_model = ProcessTree(operator=Operator.SEQUENCE, children=[
    receive, and_checks, classify, xor_routing
])
```

**3. Explanation of Concurrency, Choices, and Exclusions:**
- **Concurrency:** The `AND` operator allows Capture, Screen, and Verify to happen in any order.
- **Choices:** The `XOR` operator enforces exactly one terminal route (Reject, Low-Risk, or High-Risk).
- **Exclusions (Approximation Disclosed):** Clarification loops, Sanctions Escalation, Obtain Legal Opinion, and post-activation behaviors (Change Bank Details, Suspend Vendor) are deliberately excluded from this tree. Including them would break block-structuring and clutter the backbone with optional loops. We approximate the process by assuming these ad-hoc activities are filtered out before evaluating a trace against the procedural model, leaving their enforcement to DECLARE.

**Rule Semantics and Direction:**
| Template | Encoded Pair (Source, Target) | Direction & Semantics |
|---|---|---|
| `response` | (Sanctions Escalation, Obtain Legal Opinion) | If Escalation occurs, Opinion must eventually follow. |
| `response` | (Change Bank Details, Suspend Vendor) | If Bank Details change, Suspension must eventually follow. |
| `precedence` | (Obtain Legal Opinion, Activate Vendor) | Activation cannot occur unless Opinion has already occurred. |
| `precedence` | (Run Sanctions Screening, Sanctions Escalation) | Escalation cannot occur unless Screening has already occurred. |
| `precedence` | (Verify Bank Account, Release First Payment) | Release cannot occur unless Verify has already occurred. |
| `altresponse` | (Request Clarification, Receive Clarification) | After a Request, a Receive must occur before any subsequent Request (and before case end). |
| `noncoexistence`| Various pairs (e.g., Reject/Activate) | If one occurs, the other cannot occur in the same case (symmetric). |

# 5. Log-Skeleton Model

```python
log_skeleton = {
    "equivalence": set(),
    "always_before": {
        ("Receive Onboarding Request", "Activate Vendor"),
        ("Receive Onboarding Request", "Reject Vendor"),
        ("Activate Vendor", "Release First Payment")
    },
    "always_after": {
        ("Close Onboarding", "Receive Onboarding Request")
    },
    "never_together": {
        ("Reject Vendor", "Activate Vendor"),
        ("Manager Approval", "Compliance Approval"),
        ("Manager Approval", "Enhanced Due Diligence")
    },
    "activ_freq": {
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1}
    },
    "directly_follows": set()
}
```

**Overlap and Disagreement:**
- **Orientation:** We define `always_before(A, B)` to mean A always occurs before B, and `always_after(A, B)` to mean A always occurs after B.
- **Overlap:** `never_together` perfectly overlaps with DECLARE's `noncoexistence` and the Procedural model's XOR splits. `always_before("Activate Vendor", "Release First Payment")` overlaps with the Procedural sequence.
- **Disagreement:** The Log Skeleton is highly rigid. If we included `always_after("Obtain Legal Opinion", "Sanctions Escalation")`, it would disagree with DECLARE's `response` because `always_after` implies Opinion *always* happens, whereas `response` only requires it *if* Escalation happens. We omit it here to avoid disagreement.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800.0, 86400.0),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200.0, 21600.0),
    ("Activate Vendor", "Release First Payment"): (259200.0, 129600.0)
}
```
*Note: Times are in seconds. `zeta = 2.0` is used during conformance checking.*

**Why warnings rather than automatic control-flow violations?**
Temporal deviations (e.g., a vendor taking 5 days to clarify instead of 2) represent operational inefficiencies or soft policy breaches, not invalid business logic. Automatically rejecting cases for being slow would break the process and require manual restarts, which is counterproductive. They are best treated as warnings for compliance monitoring.

# 7. Resource- and Data-Aware Checks

**Segregation of Duties (Four-Eyes Principle):**
Activity-only models cannot express resource constraints. We use PM4Py's built-in filters.

**Emergency Policy Condition (R6):**
```python
# Required attributes: 'time:timestamp'
# If missing: Cannot evaluate time difference; flag for manual review.
def check_emergency_policy(case):
    events = case.events
    escalation_time = None
    activation_time = None
    opinion_time = None
    
    for event in events:
        if event["concept:name"] == "Sanctions Escalation":
            escalation_time = event["time:timestamp"]
        elif event["concept:name"] == "Activate Vendor":
            activation_time = event["time:timestamp"]
        elif event["concept:name"] == "Obtain Legal Opinion":
            opinion_time = event["time:timestamp"]
            
    if escalation_time and activation_time:
        if not opinion_time or opinion_time > activation_time:
            # Emergency activation occurred. Check if opinion arrived within 24h (86400s)
            if opinion_time and (opinion_time - activation_time).total_seconds() <= 86400:
                return "warning_emergency_audit_required"
            else:
                return "fail_missing_or_late_opinion"
    return "pass"
```

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement:** R1 and R8 are enforced redundantly across the Procedural model (XOR splits), DECLARE (`noncoexistence`), and Log Skeleton (`never_together`). While redundant, this provides defense-in-depth across different conformance algorithms.
- **Inconsistencies under loops:** R11 states that if `Change Bank Details` occurs post-activation, another `Verify Bank Account` must occur before a later `Release First Payment`. However, R10 strictly limits `Release First Payment` to at most once (`activ_freq = {0,1}`). If a payment was already released before the bank details changed, a second release to the new account would violate R10, creating an unresolvable contradiction in the rule set.
- **Vacuity in declarative rules:** A rule like `response("Sanctions Escalation", "Obtain Legal Opinion")` evaluates to true (vacuously) for any case where Escalation never happens. High support/confidence metadata for this rule does not mean the rule is actively triggered; it just means it is never violated.
- **Missing case attributes:** The inability to identify "emergency" cases or "joint authorizations" in the event log is a massive blind spot. Activity-only models are forced to either block legitimate emergencies (Strict Compliance) or allow unauthorized bypasses (Permissive).
- **Timestamp-only limitations:** Timestamps indicate when an activity was logged, not how long it actually took to perform. Temporal profiles measure waiting/idle time plus execution time, which can skew standard deviations.
- **Risk of metadata:** Treating `support` and `confidence` as normative truth is dangerous. A rule might have 1.0 confidence in a historical log simply by coincidence, not because it is a true business policy.

# 10. Deployment Recommendation

1. **Canonical Procedural Representation:** Use the Process Tree as the canonical representation for the stable, block-structured backbone. It provides the easiest visual model for stakeholders to understand the "happy path".
2. **Authoritative Policy Layer:** Use DECLARE as the authoritative layer for loose temporal constraints and ad-hoc loops, and the Resource/Data layer for Segregation of Duties.
3. **Execution Order:** 
   - First, project the trace onto backbone activities and run Procedural conformance (fastest, catches fundamental routing errors).
   - Second, run DECLARE and Log Skeleton on the full trace to catch policy and concurrency violations.
   - Third, run Resource/Data checks (SOD).
   - Finally, run the Temporal Profile to generate soft warnings.
4. **Surfacing Contradictions:** Provide a unified dashboard to end-users. Hard violations (Procedural, DECLARE, SOD) should block the case from progressing. Soft violations (Temporal deviations, or Emergency activations without explicit flags) should not block the case but must generate alerts routed to a compliance officer's queue for post-hoc review.
