> **Why bidirectional DFG  proof of concurrency:** A DFG counts *directly-follows* in completion order. Both AB and BA can be produced by (a) true concurrency with racing completions, (b) an XOR choice between two opposite sequences, (c) overlapping/long-running activities with different start times, (d) timestamp coarseness + ingestion ordering S7, or (e) distinct process variants with different business rules (e.g., SC interleaving). Without start timestamps, lifecycle, or resource data, the DFG is observationally equivalent under all these generators. Hence 17 vs 11 or 13 vs 2 indicates observed interleaving variability, not causal independence.

# 2. Shared Assumptions

1.  **Event-completion semantics:** Log events are activity completions. No start times are available (S7). Order in a trace is a total order imposed on completion times; concurrent or overlapping execution appears as interleaving. Therefore sequence in model means *required to complete before*, not necessarily *required to start after*. All models reason only about completion-order language.
2.  **Missing Supplier Confirmation:** Per S5, 5-10% of SC events may be absent due to integration loss. The dataset lacks the external/stocked attribute (S3/S4). Absence of SC in log (V3,V4, 23.3% of cases) is therefore *ambiguous*: it conflates legitimate skip (stocked) and unobserved mandatory SC (external + loss). We have no way to label ground truth. Modeling implication: **all candidates represent SC optionality as a control-flow XOR (SC vs silent skip)** and explicitly disclose this is an abstraction that over-approximates both mechanisms.
3.  **Absent external/stocked attribute:** Cannot condition SC requirement on case data. Data-conditioning alternative (`if external then SC`) is logically correct but not implementable without attribute; we therefore use pure control-flow alternatives and note scalability/expressiveness loss vs data-aware model.
4.  **Optionality representation:** Optional activities (SC, EX) are modeled as `XOR(activity, )` (silent transition). This admits exactly zero or one execution. For EX, we additionally enforce 1 via structure (no loop, not replicated in parallel branches). We do not use loops for optionality to avoid admitting 2 executions.
5.  **High-confidence invariants enforced in all models:** RO is start (D1), AR is end (D1), ACRPAR is strict sequence, with ACRP required (D2). CC and ER occur exactly once per case and precede AC (D3). No model admits traces violating these.
6.  **Closed-world for activity set:** No other activities are introduced. Duplicate labels are avoided in process trees by structure, not by replication, except where explicitly discussed for conservative enumeration.
7.  **Fitness/precision scope:** Metrics are computed on the 30-case log as given, without imputing missing SC events.

# 3. Conservative Candidate

**Inductive bias statement:** Prioritize *no hallucination* over generalization. The conservative model assumes every ordering choice and optionality combination must have been witnessed. It treats bidirectional DFG edges as evidence of XOR branching (distinct variants), not concurrency. It makes no claim about concurrency, partial order, or data-conditioned optionality; it deliberately overfits to the 7 observed variant strings plus high-confidence rules D1-D3. Its bias is low-variance, high-bias-against-novelty: prefer false negatives (reject unseen but plausible) to false positives.

**Formal expression:**
```
Conservative = ( RO , 
  X( (CC,ER,SC,AC,RP,AR),   // V1 12×
     (ER,CC,SC,AC,RP,AR),   // V2 7×
     (CC,ER,AC,RP,AR),      // V3 4×
     (ER,CC,AC,RP,AR),      // V4 3×
     (CC,SC,ER,AC,RP,AR),   // V5 2×
     (CC,ER,SC,EX,AC,RP,AR),// V6 1×
     (ER,CC,EX,SC,AC,RP,AR) // V7 1×
  )
)
```
This is exactly the language `L = {V1..V7}` prefixed by RO; `|L| = 7`. No concurrency operator (``) is used.

**PM4Py code:**

```python
   X( ->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Approve Configuration', 'Release Production', 'Archive Case' ),

      ->( 'Credit Check', 'Supplier Confirmation', 'Engineering Review', 'Approve Configuration', 'Release Production', 'Archive Case' ),
      ->( 'Credit Check', 'Engineering Review', 'Supplier Confirmation', 'Expedite Review', 'Approve Configuration', 'Release Production', 'Archive Case' ),
      ->( 'Engineering Review', 'Credit Check', 'Expedite Review', 'Supplier Confirmation', 'Approve Configuration', 'Release Production', 'Archive Case' )
   )

"""

model_conservative = pm4py.parse_process_tree(tree_str_conservative)

# Duplicate labels & scalability discussion:
# - Each XOR branch re-introduces CC, ER, etc. as separate leaf nodes with same label.
#   ProcessTree semantics allow this (distinct nodes, same label) but discovery/mining
#   algorithms often avoid duplicates for simplicity; here we intentionally use them.
# - Scalability: enumeration size = |observed variants|. For n activities with k optional
#   and interleavings, |L| grows combinatorially (e.g., 3! orderings × 2^2 optional = 24).
#   Unmaintainable beyond ~10 variants; motivates balanced/permissive generalization.
```

**Behavior deliberately excluded:**
- `RO, CC, ER, EX, AC, RP, AR` (EX without SC, after both checks - permitted by S6/D6 but never observed)
- `RO, CC, ER, SC, AC, RP, AR` with SC concurrent to ER (observed only as sequential interleaving, not overlapping)
- `RO, ER, CC, SC, EX, AC, RP, AR` (EX after SC - plausible swap of V7 but not observed)
- `RO, ER, ER...` or duplicate/repeated CC/ER/SC/EX
- Any SC after AC or before RO, any AC before CC/ER
- Any trace where SC precedes both CC and ER

**Known underfitting risks (overfitting to sample):**
- Fails to generalize to unseen interleavings that are causally identical to observed (e.g., EX skip vs include, SCEX swap)
- Fragile to missing data: a single missing SC imputation would be rejected even if S5 suggests it should be accepted
- Precision is perfect but generalization is minimal; future stocked/external mix will produce false non-conformance
- Cannot explain S2 parallelism claim; treats CCER variation as business-rule XOR rather than race condition

# 4. Balanced Candidate

**Inductive bias statement:** Encode the *most plausible* generalization under uncertainty: CC and ER are concurrent (S2 more plausible than S1 given bidirectional counts and D7), SC is optional and only needs one predecessor (D5), EX is optional, at-most-once, and depends on both CC+ER but is unordered with SC (S6). Bias is moderate: generalize to unobserved but logically permitted reorderings of the same dependencies, but do not yet admit fully unconstrained concurrency (e.g., SC before both CC and ER remains disallowed). Uses POWL partial orders to express concurrency natively and XOR for optionality.

**Formal expression:**
```
Let RO, CC, ER, SC, EX, AC, RP, AR be transitions.
opt(X) = X( X ,  )
SC_opt = opt(SC)
EX_opt = opt(EX)

Mid1 = PO( nodes={CC, ER, SC_opt, EX_opt},
           edges={ CCSC_opt, CCEX_opt, EREX_opt } )  // SC after CC, EX after both
Mid2 = PO( nodes={CC, ER, SC_opt, EX_opt},
           edges={ ERSC_opt, CCEX_opt, EREX_opt } )  // SC after ER

Mid  = X( Mid1 , Mid2 )  // SC must follow at least one of CC/ER (encodes D5)

Balanced = PO( nodes={RO, Mid, AC, RP, AR},
               edges={ ROMid, MidAC, ACRP, RPAR } )
```
Variant: `CC  ER` (no edge between them), `SC_opt  remaining check`, `EX_opt  SC_opt`.

**PM4Py code:**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

RO = Transition(label="Register Order")
AC = Transition(label="Approve Configuration")
RP = Transition(label="Release Production")
AR = Transition(label="Archive Case")

# Branch 1: SC after CC
CC1 = Transition(label="Credit Check")
ER1 = Transition(label="Engineering Review")
SC1 = Transition(label="Supplier Confirmation")
EX1 = Transition(label="Expedite Review")

skip_ex1 = SilentTransition()
opt_ex1 = OperatorPOWL(operator=Operator.XOR, children=[EX1, skip_ex1])
mid1 = StrictPartialOrder(nodes=[CC1, ER1, opt_sc1, opt_ex1])
mid1.order.add_edge(CC1, opt_sc1)   # SC requires at least CC in this branch
mid1.order.add_edge(CC1, opt_ex1)   # EX requires CC
mid1.order.add_edge(ER1, opt_ex1)   # EX requires ER

# Branch 2: SC after ER
CC2 = Transition(label="Credit Check")
ER2 = Transition(label="Engineering Review")
SC2 = Transition(label="Supplier Confirmation")
EX2 = Transition(label="Expedite Review")
skip_sc2 = SilentTransition()
opt_sc2 = OperatorPOWL(operator=Operator.XOR, children=[SC2, skip_sc2])
skip_ex2 = SilentTransition()
opt_ex2 = OperatorPOWL(operator=Operator.XOR, children=[EX2, skip_ex2])
mid2 = StrictPartialOrder(nodes=[CC2, ER2, opt_sc2, opt_ex2])
mid2.order.add_edge(ER2, opt_sc2)   # SC requires at least ER in this branch
mid2.order.add_edge(CC2, opt_ex2)
mid2.order.add_edge(ER2, opt_ex2)

mid = OperatorPOWL(operator=Operator.XOR, children=[mid1, mid2])

model_balanced = StrictPartialOrder(nodes=[RO, mid, AC, RP, AR])
model_balanced.order.add_edge(RO, mid)
model_balanced.order.add_edge(mid, AC)
model_balanced.order.add_edge(AC, RP)
model_balanced.order.add_edge(RP, AR)

# Decision rationale CC/ER/SC/EX:
# - CC vs ER: sequence vs concurrency vs partial order.
#   Frequency DFG both directions (17/11) + S2 parallel claim + S7 logging noise + D7 unknown
#    concurrency (no edge). Choosing sequence CCER would validate S1 but reject 14 traces (47%);
#   choosing XOR would duplicate language unnecessarily. Concurrency is most parsimonious.
# - SC placement: D5 low-medium confidence "after either CC or ER" + V5 (CCSCER) proves SC
#   need not wait for both. Two-branch XOR captures "at least one predecessor" which POWL cannot
#   express as single partial order (strict partial order cannot encode disjunctive dependency).
#   Alternative single PO with SCCCER would admit SC before both  weaker, we reject for balanced.
# - EX placement: D6/S6 medium confidence requires CC+ER before EX, before AC,  SC. Modeled as
#   CCEX, EREX, EXAC (via MidAC), no edge EXSC. Optionality via XOR+ ensures 0..1 occurrence.
```

**Behavior deliberately excluded:**
- Traces where SC precedes *both* CC and ER (`RO, SC, CC, ER, AC...`) - violates D5 interpretation adopted
- EX before CC or ER, EX after AC, EX duplicated
- CC or ER after AC, AC before RP, missing RO/AR
- Multiple SC or multiple EX

**Known underfitting risks:**
- Still rejects plausible permissive behavior where SC is truly independent (e.g., procurement can start immediately after RO) which some organizations allow
- Two-branch encoding doubles node count; duplicate labels across branches may confuse trace alignment diagnostics
- Assumes S5 missingness = optionality; if integration loss is systematic, model over-accepts skipped SC for external components
- Does not model resource-dependent queuing that could make CC/ER appear sequential despite logical concurrency

# 5. Permissive Candidate

**Inductive bias statement:** Admit any reasonable combination that respects only high and medium-high confidence rules (D1-D4, D3) and the minimal reading of D5/D6, ignoring the “at least one predecessor” nuance for maximal robustness. Bias is toward high recall, low precision: prefer to accept future unseen interleavings at cost of admitting behavior that domain experts might still consider undesirable but not forbidden. Useful for exploration, gap analysis, and stress-testing compliance.

**Formal expression:**
```
opt(X) = X(X, )
Permissive = PO( nodes={RO, CC, ER, opt(SC), opt(EX), AC, RP, AR},
                 edges={ ROCC, ROER, ROopt(SC),  // SC can start immediately after RO (most permissive D5)
                         CCopt(EX), ERopt(EX),   // EX after both checks only
                         CCAC, ERAC, opt(SC)AC, opt(EX)AC,
                         ACRP, RPAR })
Simplified: CCERSC (all three unordered after RO), EX after CC+ER but  SC, all before AC.
```
In implementation we omit ROSC edge if we want SC before both to be allowed; we keep only required edges to AC to maximize permissiveness.

**PM4Py code:**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

RO_p = Transition(label="Register Order")
CC_p = Transition(label="Credit Check")
ER_p = Transition(label="Engineering Review")
SC_p = Transition(label="Supplier Confirmation")
EX_p = Transition(label="Expedite Review")
AC_p = Transition(label="Approve Configuration")
RP_p = Transition(label="Release Production")
AR_p = Transition(label="Archive Case")

skip_sc_p = SilentTransition()
opt_sc_p = OperatorPOWL(operator=Operator.XOR, children=[SC_p, skip_sc_p])

skip_ex_p = SilentTransition()
opt_ex_p = OperatorPOWL(operator=Operator.XOR, children=[EX_p, skip_ex_p])

# Permissive: maximal concurrency - only edges are those forced by high-confidence rules
model_permissive = StrictPartialOrder(
    nodes=[RO_p, CC_p, ER_p, opt_sc_p, opt_ex_p, AC_p, RP_p, AR_p]
)
# High confidence anchors
model_permissive.order.add_edge(RO_p, CC_p)
model_permissive.order.add_edge(RO_p, ER_p)
model_permissive.order.add_edge(RO_p, opt_sc_p) # SC can start after RO (or omit this edge for even more permissive: no predecessor)
model_permissive.order.add_edge(RO_p, opt_ex_p) # EX still needs RO transitively via CC/ER
model_permissive.order.add_edge(CC_p, AC_p)
model_permissive.order.add_edge(ER_p, AC_p)
model_permissive.order.add_edge(opt_sc_p, AC_p)
# EX dependencies
model_permissive.order.add_edge(CC_p, opt_ex_p)
model_permissive.order.add_edge(ER_p, opt_ex_p)
model_permissive.order.add_edge(opt_ex_p, AC_p)
# Tail
model_permissive.order.add_edge(AC_p, RP_p)
model_permissive.order.add_edge(RP_p, AR_p)

# Note: by not adding CC->SC or ER->SC, we admit SC before both checks - a deliberate
# relaxation of D5 for exploration. If stricter permissive still desired, add RO->SC only
# and keep SCCCER, which is what we do here. Alternative fully unconstrained would have
# no edge RO->SC either, allowing SC at very start; we keep RO->SC to respect D1 start semantics.
```

**Behavior deliberately excluded (boundary “reasonable vs forbidden”):**
- *Reasonable and admitted:* any permutation of {CC,ER,SC} after RO (6 orders), EX in any position after CC+ER but before AC, including `RO, SC, CC, ER, AC...` or `RO, CC, ER, EX, SC, AC...` or `RO, CC, ER, SC, EX, AC...` etc.; SC optional, EX optional
- *Reasonable but still forbidden:* multiple occurrences of CC/ER/Mandatory repetition, skipping CC/ER, AC before RP, missing RO/AR, EX before CC/ER, EX after AC, SC after AC. These remain forbidden because they violate D1-D3/D6 high/med-high confidence.
- Boundary principle: **admit any control-flow interleaving that respects completion dependencies; forbid violation of mandatory completion-before constraints.** Data-conditioned mandatory SC (S3) is not enforced, so “unreasonable but admitted” includes stocked-component skip masquerading as missing external SC.

**Known underfitting (over-permissiveness) risks:**
- Admits SC before any check, which stakeholders might deem impossible (violates D5 stricter reading)
- Low precision: will not flag log integration loss (S5) as anomaly; compliance checking becomes vacuous for SC ordering
- May mask true process drift by accepting everything

```python
model_balanced.order.add_edge(AC, RP); model_balanced.order.add_edge(RP, AR)
```

# 9. Recommendation and Data-Collection Plan

**Immediate use: Balanced candidate**
- Reason: Achieves fitness 1.0 on observed, precision far better than permissive, tolerates S5 missingness without collapsing to “allow everything”, directly encodes D5 disjunctive dependency and S6 EX rule in an explainable POWL structure. Best bias-variance trade-off for operational monitoring, training, and conformance dashboards.
- Not recommended for strict compliance auditing where false positives must be zero  use conservative as reference shadow model.

**Sensitivity analysis: Pair Conservative (lower bound) + Permissive (upper bound)**
- Run both in parallel to bracket uncertainty: any trace rejected by permissive is definitely non-conformant (violates D1-D3 high confidence); any trace rejected by conservative but accepted by permissive is “novel but plausible” and should be flagged for human review. Drift detection: widening gap between conservative and permissive acceptance rates indicates process evolution or data-quality shift.

**Concrete data-collection plan to resolve ambiguities:**

1. **Attributes to collect (case-level):**
   - `external_component` boolean (to distinguish S3 mandatory vs S4 stocked skip; enables data-conditioned model `if external then SC`)
   - `stocked_flag`, `component_type`, `supplier_id`
2. **Attributes to collect (event-level):**
   - `lifecycle` with `start` and `complete` timestamps for CC, ER, SC, EX (currently only completion available  S7). Enables true concurrency detection via overlapping intervals.
   - `resource` (who performed CC/ER/SC) to detect resource contention vs parallelism
   - `sc_ integration_status` (success/missing) to label S5 missing events vs legitimate skip
   - `expedite_reason` and `expedite_approval_id` to validate D6 1
   - `supplier_confirmation_channel` to audit integration loss per 5-10% estimate
3. **Logging fixes:**
   - Emit SC event even when integration fails (with `is_missing=True` flag) instead of dropping
   - Preserve microsecond timestamps and original ingestion order index to de-bias S7
4. **Maximally informative future traces to collect (active sampling):**
   - **Test XOR vs concurrency for CC/ER:** Need `start` overlap. Any trace where `CC.start < ER.complete` and `ER.start < CC.complete` proves true concurrency/overlap, falsifying S1 sequence. Most informative: `RO, CC+ER overlapping, SC after both` with start timestamps.
   - **Test D5 disjunctive dependency:** `RO, SC, CC, ER, AC...` (SC before both) vs `RO, CC, SC, ER, AC` (SC between) vs `RO, ER, SC, CC, AC`. Observing SC-before-both would falsify balanced’s “after 1” and support permissive; absence across 100+ external cases would strengthen balanced/conservative.
   - **Test optionality vs missingness:** Collect 50 consecutive external-component cases per S3; if SC absence >10%, legitimate skip is rare  missingness hypothesis dominates. If stocked cases systematically lack SC  S4 validated and data-aware model becomes necessary.
   - **Test EX positioning and optionality:** Traces with EX without SC, EX before SC, EX after SC, all after CC+ER but before AC. Also trace with two EX attempts (should be blocked) to validate 1.
   - **Stress test concurrency:** Long-running CC overlapping ER and SC to see if SC can complete while ER still running  proves partial order not strict sequence.

**Decision rule:** After collecting ~100 new cases with start+complete timestamps and external/stocked attribute, re-run DFG on start vs complete orders separately. If CCER overlap in >30% of cases, lock in concurrency; if SC-before-both appears 0 times in external cohort, prune permissive edge; if SC missing rate drops to <2% after logging fix, replace XOR-silent SC with data-conditioned gateway.

**Plausible alternative interpretation that would materially change recommendation:**
> *The 23% SC-skipped traces are not legitimate stocked-component skips but 100% integration loss, and the true business rule is S3 “SC mandatory for every case”.* 
Under this interpretation, V3/V4 are *data-quality artifacts*, not true variants. The correct model would be **mandatory SC** (no XOR-silent skip) with a data-quality repair step. Then the conservative model would be *underfitting* the true mandatory-SC process, the balanced/permissive optional-SC models would be *over-permissive and dangerous* (they would certify non-compliant stocked-external cases as conformant), and recommendation would flip to: **use a mandatory-SC variant of the balanced model (`CCER  SC  (EX? )  AC`) for compliance, and treat SC absence as anomaly to be investigated, not accepted.** This alternative is currently unresolvable without the `external/stocked` attribute and `integration_status` flag proposed in Section 9.
