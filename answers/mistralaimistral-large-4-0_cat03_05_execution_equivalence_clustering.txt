## 1. Equivalence design space

### 1.1 Activity-sequence equivalence (ASE)

**Definition.**  
For an execution \(E\), let \(\text{acts}(E) = (a_1,\dots,a_n)\) be the sequence of activity labels in timestamp order. Two executions \(E,E'\) are ASE-equivalent iff

\[
\text{acts}(E) = \text{acts}(E').
\]

If events have identical timestamps, I break ties deterministically by sorting tied events by activity label and then by the multiset of object types involved. This makes the sequence total and reproducible.

**Invariants preserved.**  
Activity labels, their order, and repeated activity counts.

**Information discarded.**  
Object types, object identifiers, E2O incidence, O2O relations and qualifiers, external-object flags, multiplicities, timestamps, and execution boundaries.

**Properties.**  
Reflexive, symmetric, and transitive, because it is equality of sequences.

**Concurrency handling.**  
Same-time events are ordered by the deterministic tie-break above. Alternatively, one could use a partial order; the given executions are totally ordered, so the distinction does not affect the clusters below.

---

### 1.2 Typed structural equivalence under identifier renaming (TSE)

**Definition.**  
An execution is modeled as a typed event structure:

\[
(E, O, \lambda, \tau, \prec)
\]

where \(E\) is the set of events, \(O\) is the set of objects with types, \(\lambda\) assigns an activity label to each event, \(\tau\) assigns to each event the set of objects involved (E2O incidence), and \(\prec\) is the event order.

Two executions are TSE-equivalent iff there exists a bijection \(\phi\) on local object identifiers, preserving object types and external-object flags, such that:

1. \(\lambda(e) = \lambda(\phi(e))\) for every event \(e\);
2. \(\tau(\phi(e)) = \phi(\tau(e))\) for every event \(e\);
3. the event order is preserved: \(e \prec e' \iff \phi(e) \prec \phi(e')\).

O2O notes are ignored in this relation. External-object flags are preserved because they are a supplied semantic distinction.

**Invariants preserved.**  
Activity labels, event order, object types, E2O incidence, object multiplicities per event, and external-object flags.

**Information discarded.**  
Local object identifiers except for the external flag, O2O relations and qualifiers, timestamps, and the internal listing order of objects inside an event.

**Properties.**  
Reflexive, symmetric, and transitive, because it is isomorphism of typed event structures.

**Concurrency handling.**  
If same-time events exist, use partial-order isomorphism instead of total-order isomorphism. The given executions are totally ordered.

---

### 1.3 Business-semantic equivalence (BSE) — preferred relation

**Definition.**  
Two executions are BSE-equivalent iff their canonical signatures, defined in Section 2, are equal. The canonical signature includes:

- the lead object type, here `Order`;
- the event sequence with activity labels;
- for each event, the object types and canonical object identifiers involved, preserving multiplicities and external flags;
- the O2O graph with qualifiers;
- the lifecycle motif, i.e. the activity sequence.

**Invariants preserved.**  
Activity sequence, object types, E2O incidence, O2O topology and qualifiers, external-object flags, multiplicities, repeated activities, and lead object type.

**Information discarded.**  
Local object identifiers except for the external flag, timestamps, and the order of O2O notes.

**Properties.**  
Reflexive, symmetric, and transitive, because it is equality of canonical signatures.

**Concurrency handling.**  
Same deterministic tie-break as in ASE/TSE. If a partial order is preferred, the event list can be replaced by a canonical partial-order representation.

## 2. Canonical signatures

The following scheme is reproducible and invariant to local identifier renaming. Canonical identifiers are assigned by first occurrence in event order, separately per object type. External objects are canonicalized separately and keep an `EXT-` prefix.

```python
from collections import defaultdict

def canonical_signature(events, o2o_notes, lead_type="Order"):
    """
    events: list of (activity, {object_type: [object_id, ...]})
    o2o_notes: list of (subject_type, subject_id, object_type, object_id, qualifier)
    Returns a hashable canonical signature.
    """
    canon = {}
    counters = defaultdict(int)

    def cid(obj_type, obj_id):
        key = (obj_type, obj_id)
        if key not in canon:
            if obj_id.startswith("EXT"):
                counters[("EXT", obj_type)] += 1
                canon[key] = f"EXT-{obj_type}-{counters[('EXT', obj_type)]}"
            else:
                counters[obj_type] += 1
                canon[key] = f"{obj_type}-{counters[obj_type]}"
        return canon[key]

    event_sig = []
    for activity, obj_map in events:
        parts = []
        for obj_type in sorted(obj_map.keys()):
            ids = sorted(cid(obj_type, oid) for oid in obj_map[obj_type])
            parts.append((obj_type, tuple(ids)))
        event_sig.append((activity, tuple(parts)))

    o2o_sig = []
    for subj_type, subj_id, obj_type, obj_id, qualifier in o2o_notes:
        o2o_sig.append((
            subj_type, cid(subj_type, subj_id),
            obj_type, cid(obj_type, obj_id),
            qualifier or ""
        ))
    o2o_sig.sort()

    motif = tuple(activity for activity, _ in event_sig)

    return {
        "lead_type": lead_type,
        "events": tuple(event_sig),
        "o2o": tuple(o2o_sig),
        "motif": motif,
    }
```

This signature is invariant to local identifier renaming because canonical IDs depend only on first occurrence order and object type, not on the original local IDs. It preserves object types, multiplicities, external flags, event order, E2O incidence, O2O qualifiers, and repeated activities.

## 4. Cluster interpretations

### S1 — Clean single-package fulfillment (X1, X2)

**Signature.**  
`Order lead; 2 Items; 1 Package; 1 Delivery; 1 Invoice; 1 Payment; no external objects; no qualifiers; sequence Create  Add×2  Pack  Dispatch  Issue  Pay.`

**Business behavior.**  
Standard order-to-cash: two items are added, packed together, shipped in one delivery, invoiced once, and paid once.

**Risks/opportunities.**  
Low complexity; good candidate for straight-through processing and automation. Main risks are ordinary execution errors.

**Traditional flattening.**  
Flattening by `Order` represents this well. Flattening by `Item` or `Package` duplicates order-level events and loses the shared package/delivery.

**Stability.**  
Stable under ID renaming, Add Item order, and item listing order inside Pack.

---

### S2 — Split packages, consolidated delivery (X3)

**Signature.**  
`Order lead; 2 Items; 2 Packages; 1 Delivery; 1 Invoice; 1 Payment; no external objects; no qualifiers; sequence Create  Add×2  Pack×2  Dispatch(2 Pkg)  Issue  Pay.`

**Business behavior.**  
Items are packed separately but shipped together in one consolidated delivery; single invoice and payment.

**Risks/opportunities.**  
Risk of package-count mismatch and split-packing errors. Opportunity for logistics consolidation and lower shipping cost.

**Traditional flattening.**  
Flattening by `Order` hides the package split. Flattening by `Package` duplicates order/invoice/payment and may not show that both packages share one delivery.

**Stability.**  
Stable under renaming and package order. If package multiplicity is considered immaterial, it could merge with S1, but under multiplicity-preserving semantics it is separate.

---

### S3 — Split packages, split deliveries, partial payment (X4)

**Signature.**  
`Order lead; 2 Items; 2 Packages; 2 Deliveries; 1 Invoice; 2 Payments; no external objects; O2O: partial_settles/completes_settlement; sequence Create  Add×2  Pack  Dispatch  Pack  Dispatch  Issue  Pay×2.`

**Business behavior.**  
Items are shipped separately in two deliveries; invoice is issued once, but payment is made in two installments: partial settlement followed by completion.

**Risks/opportunities.**  
Risk of payment reconciliation, delivery fragmentation, and customer confusion. Opportunity for flexible delivery and payment terms.

**Traditional flattening.**  
Flattening by `Order` shows two deliveries/payments but hides package-delivery pairing. Flattening by `Payment` or `Delivery` fragments the order.

**Stability.**  
Stable. If payment amounts are treated as attributes, the two payments may collapse to one, but the delivery split remains.

---

### S4 — Cross-order logistics sharing (X5)

**Signature.**  
`Order lead O5 + EXT-Order; 2 local Items + EXT-Item; 1 Package; 1 Delivery; 1 Invoice; 1 Payment; O2O: Pkg packs local+EXT items, EXT-Order contains EXT-Item, Inv bills only O5.`

**Business behavior.**  
The lead order’s items are packed and shipped together with an external order’s item in a shared package/delivery. The invoice and payment cover only the lead order.

**Risks/opportunities.**  
Risk of logistics cost/revenue allocation, dependency on the external order, and liability for the external item. Opportunity for consolidated shipping and shared logistics.

**Traditional flattening.**  
Flattening by `Order O5` hides the external item. Flattening by `Package` or `Delivery` shows the shared package but may obscure which order is billed.

**Stability.**  
Stable if external flags are preserved. If external objects are ignored, it collapses to S1, losing the sharing semantics.

---

### S5 — Cross-order financial sharing (X6)

**Signature.**  
`Order lead O6 + EXT-Order in Issue/Pay; 2 Items; 1 Package; 1 Delivery; 1 Invoice; 1 Payment; O2O: Inv bills O6 and EXT-Order, Pay settles Inv without order-level allocation.`

**Business behavior.**  
Logistics are isolated for the lead order, but the invoice and payment are shared with an external order. There is no order-level allocation.

**Risks/opportunities.**  
Risk of revenue recognition, accounting allocation, and audit issues. Opportunity for consolidated billing.

**Traditional flattening.**  
Flattening by `Order O6` may show invoice/payment but not the external order. Flattening by `Invoice` shows the shared invoice but duplicates logistics.

**Stability.**  
Stable. If external objects are ignored, it collapses to S1.

---

### S6 — Item replacement/removal before dispatch (X7)

**Signature.**  
`Order lead; 2 Items; 1 Package; 1 Delivery; 1 Invoice; 1 Payment; Dispatch includes Item:I72; O2O: I72 replaces I71, P71 initially packs I71 and I72, qualifier removed_before_dispatch links P71 to I71.`

**Business behavior.**  
One item was substituted or removed before dispatch. The package initially contained both items, but the dispatch event and qualifiers indicate the replacement/removal.

**Risks/opportunities.**  
Risk of inventory/order accuracy, audit trail, and customer receiving a substitute. Opportunity for a controlled substitution process.

**Traditional flattening.**  
Flattening by `Order` sees the same activity sequence as S1. Flattening by `Item` may show I71 and I72 but not the removal qualifier.

**Stability.**  
Stable if O2O qualifiers and E2O incidence are preserved. If qualifiers are ignored, it becomes a structural outlier because Dispatch contains an extra Item.

---

### S7 — Return and repack (X8)

**Signature.**  
`Order lead; 2 Items; 2 Packages; 2 Deliveries; 1 Invoice; 1 Payment; extra Return Item and Inspect Return; O2O: P81 packs I81,I82; D81 carries P81; P82 repacks I82; D82 carries P82; P82 replaces P81 for I82.`

**Business behavior.**  
Initial shipment of two items; one item is returned, inspected, repacked, and shipped again. Invoice and payment occur once.

**Risks/opportunities.**  
Risk of returns processing, inventory inaccuracy, and customer dissatisfaction. Opportunity for reverse logistics and better returns handling.

**Traditional flattening.**  
Flattening by `Order` shows extra activities but may not show that the second package replaces the first for the returned item. Flattening by `Item` shows item lifecycle but duplicates order/invoice.

**Stability.**  
Stable. If returns are ignored, it may look like two deliveries, but not like S3 because of Return/Inspect and the repack qualifier.

## 5. Borderline cases

### X1 versus X2

- **ASE:** equivalent — same activity sequence.
- **TSE:** equivalent — renaming maps I11/I12 to I22/I21; the Pack item set matches.
- **BSE:** equivalent — same canonical signature.

**Disagreement.**  
If one treats the order of Add Item events as business-relevant, they differ. Under our definitions, local IDs and item addition order are not meaningful.

---

### X1 versus X5

- **ASE:** equivalent — same activity labels.
- **TSE:** not equivalent — extra `Order` and `Item` objects in Pack/Dispatch.
- **BSE:** not equivalent — external logistics sharing.

**Disagreement.**  
If external objects are ignored, or only lead-order local objects are considered, X5 collapses to X1. Activity-sequence equivalence also equates them. BSE preserves the distinction through external flags and multiplicities.

---

### X1 versus X6

- **ASE:** equivalent — same activity labels.
- **TSE:** not equivalent — extra `Order` in Issue Invoice and Record Payment.
- **BSE:** not equivalent — external financial sharing.

**Disagreement.**  
If only logistics is considered, or external objects are ignored, X6 collapses to X1. If financial sharing is out of scope for the lead order, they may be treated as equivalent.

---

### X1 versus X7

- **ASE:** equivalent — same activity labels.
- **TSE:** not equivalent — Dispatch includes `Item:I72`.
- **BSE:** not equivalent — O2O qualifier `removed_before_dispatch` and replacement relation.

**Disagreement.**  
If O2O qualifiers are ignored and the extra Item in Dispatch is treated as noise, X7 looks like X1. Activity-sequence equivalence equates them. BSE preserves the distinction through qualifiers and E2O incidence.

---

### X3 versus X4

- **ASE:** not equivalent — different activity sequences.
- **TSE:** not equivalent — different event order and multiplicities.
- **BSE:** not equivalent — X3 has one delivery and one payment; X4 has two deliveries and two payments with partial settlement.

**Disagreement.**  
If package/delivery/payment multiplicities are collapsed, or only the high-level “split packages” motif is considered, they could be grouped. If payment multiplicity is treated as an amount attribute, X4’s two payments become one, but the delivery split remains. Under BSE, they are separate.

---

### X4 versus X8

- **ASE:** not equivalent — X8 has Return Item, Inspect Return, and an extra Pack/Dispatch; X4 has two payments.
- **TSE:** not equivalent.
- **BSE:** not equivalent — X4 is split delivery with partial payment; X8 is return/repack with single payment.

**Disagreement.**  
If returns/repack are ignored or treated as another split delivery, X8 might be seen as two deliveries like X4. If payment multiplicity is collapsed and return activities are ignored, both have two packages/deliveries. But O2O qualifiers and lifecycle motifs distinguish them: X8 has `P82 replaces P81 for item I82`; X4 has `partial_settles`/`completes_settlement`.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### What the PM4Py key preserves

`pm4py.cluster_equivalent_ocel` typically clusters events by a typed key such as:

\[
(\text{activity}, \text{sorted object types involved})
\]

possibly truncated by `max_objs`. It preserves the activity label and the multiset of object types per event. It discards object identifiers, event order, O2O relations and qualifiers, and execution boundaries.

### Why raw object identifiers make exact clusters too fine

If the key includes raw object IDs, then `Pack Package` with `O1,I11,I12,P11` and `O2,I21,I22,P21` become different clusters, even though they are isomorphic under local ID renaming. Raw local IDs are not business-meaningful. Exact object-binding equivalence is useful only when object identity itself is globally meaningful, such as serial numbers or regulatory identifiers.

### Canonicalization and post-processing

Use `pm4py.cluster_equivalent_ocel` as a first-stage typed grouping. Then aggregate events by lead object `Order` and compute the canonical signature from Section 2. Orders with the same canonical signature are placed in the same business-semantic cluster. Optionally, coarsen further by lifecycle motif.

### When exact equivalence is preferable

Exact equivalence is preferable for:

- detecting duplicate events;
- auditing exact object bindings;
- cases where object IDs are globally meaningful;
- data-quality checks on event-object associations.

For business process analysis, exact equivalence is usually too fine.

### Effect of `max_objs` and large connected executions

If `max_objs` is too low, events with many objects are dropped or truncated. For example, X5’s Pack event involves five objects: `O5`, `EXT-OA`, `I51`, `I52`, `EXT-IA`, `P51` — actually six objects if counting `P51`. Setting `max_objs` too low would lose this structure. If `max_objs` is too high, large connected executions may produce many small clusters or a combinatorial explosion. The parameter should be set to cover the largest relevant event, or the clustering should be based on object types rather than raw object counts.

### Executable-looking Python outline

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

# Build object id -> type map
oid_to_type = dict(zip(ocel.objects["ocel:oid"], ocel.objects["ocel:type"]))

# First-stage typed clustering by PM4Py: activity + object types
typed_clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=6)

# Group events by lead Order
order_events = defaultdict(list)
for _, ev in ocel.events.iterrows():
    lead_ids = [oid for oid in ev["ocel:omap"] if oid_to_type.get(oid) == LEAD_TYPE]
    for oid in lead_ids:
        order_events[oid].append(ev)

def canonicalize_order(order_id, events):
    events = sorted(
        events,
        key=lambda ev: (
            ev["ocel:time"],
            ev["ocel:activity"],
            tuple(sorted(ev["ocel:omap"]))
        )
    )

    canon = {}
    counters = defaultdict(int)

    def cid(oid):
        t = oid_to_type[oid]
        if oid not in canon:
            prefix = "EXT-" if oid.startswith("EXT") else ""
            counters[t] += 1
            canon[oid] = f"{prefix}{t}-{counters[t]}"
        return canon[oid]

    event_sig = []
    for ev in events:
        parts = []
        for t in sorted({oid_to_type[oid] for oid in ev["ocel:omap"]}):
            ids = sorted(cid(oid) for oid in ev["ocel:omap"] if oid_to_type[oid] == t)
            parts.append((t, tuple(ids)))
        event_sig.append((ev["ocel:activity"], tuple(parts)))

    # Add O2O qualifiers if available
    o2o_sig = []
    if hasattr(ocel, "o2o"):
        for rel in ocel.o2o:
            if order_id in (rel["source"], rel["target"]):
                o2o_sig.append((
                    oid_to_type.get(rel["source"], "?"),
                    cid(rel["source"]),
                    oid_to_type.get(rel["target"], "?"),
                    cid(rel["target"]),
                    rel.get("qualifier", "")
                ))
    o2o_sig.sort()

    return (LEAD_TYPE, tuple(event_sig), tuple(o2o_sig))

# Cluster orders by canonical signature
sig_to_orders = defaultdict(list)
for order_id, evs in order_events.items():
    sig = canonicalize_order(order_id, evs)
    sig_to_orders[sig].append(order_id)

# Optional coarsening by lifecycle motif
def motif_of(sig):
    return tuple(activity for activity, _ in sig[1])

motif_to_orders = defaultdict(list)
for sig, orders in sig_to_orders.items():
    motif_to_orders[motif_of(sig)].extend(orders)
```

## 7. Robustness analysis

### 7.1 Ignore all O2O qualifiers

- **X7** loses `removed_before_dispatch` and `replaces`. It remains separate from X1 because Dispatch still contains an extra `Item`. However, its semantic interpretation weakens: it becomes a structural outlier rather than a clear replacement case.
- **X4** loses `partial_settles`/`completes_settlement` but remains separate because it still has two payments.
- **X8** loses `P82 replaces P81` but remains separate because of Return/Inspect and repack.
- Overall, S1–S7 assignments mostly remain unchanged, but the business meaning of X7 is reduced. If E2O incidence is also ignored, X7 could collapse to S1.

### 7.2 Ignore external objects

- **X5** loses `EXT-OA` and `EXT-IA` and collapses to S1.
- **X6** loses `EXT-OB` and collapses to S1.
- S4 and S5 disappear.

This is a major loss: cross-order logistics sharing and cross-order financial sharing become invisible.

### 7.3 Collapse repeated same-label events

If all repeated same-label events are merged into one event, merging their object sets:

- X1 and X2’s two Add Item events merge into one Add Item with two items.
- X3’s two Pack events merge into one Pack with two packages.
- X4’s two Dispatch and two Record Payment events merge.
- X8’s two Pack and two Dispatch events merge, hiding the repack.

This destroys multiplicity information. X3 may become closer to X1 if package multiplicity is also ignored, X4 loses partial-payment structure, and X8 loses its second dispatch. The preferred BSE does not collapse repeated events because multiplicities are business-relevant.

### 7.4 Treat Pack and Dispatch event order as a partial order

Under a partial order, X4’s interleaving `Pack  Dispatch  Pack  Dispatch` is no longer distinguished from X3’s `Pack  Pack  Dispatch` if delivery/payment multiplicities are also ignored. The real differences are one versus two deliveries and one versus two payments. X1, X2, X5, X6, X7, and X8 are largely unaffected except for per-package precedence constraints.

### 7.5 Treat payment multiplicity as an amount attribute

X4’s two Record Payment events become one payment with an amount or installment attribute. X4 remains separate from X3 because it still has two deliveries, and separate from X1 because it has two packages/deliveries. The partial-settlement semantics is lost, but the cluster may become a new “split delivery, single payment with amount” variant.

## 8. Limitations and recommendation

### Recommendations by purpose

- **Compliance monitoring:** Use **business-semantic equivalence**. Compliance requires preserving O2O qualifiers, external sharing, replacement/removal, and partial payment. Activity-sequence or typed structural equivalence would miss these distinctions.
- **Operational segmentation:** Use **business-semantic equivalence**. Clusters S1–S7 are operational personas: clean fulfillment, split/consolidated, split/partial, logistics sharing, financial sharing, substitution, and returns.
- **Root-cause analysis:** Use **typed structural equivalence**. Root-cause analysis often compares structurally similar executions to find deviations. Typed structural equivalence preserves event order and E2O incidence while ignoring local IDs and O2O qualifiers, which may be noise in that context.
- **Descriptive reporting:** Use **business-semantic equivalence** for cluster definitions, but report activity-sequence and object-type summaries inside each cluster. Do not use activity-sequence equivalence alone as an object-centric clustering, because it would group X1 with X5, X6, and X7 and hide object-centric differences.

### Why no single equivalence notion is best

Compliance monitoring needs strict qualifiers and external flags. Root-cause analysis benefits from structural isomorphism that ignores semantic qualifiers. Descriptive reporting needs business-meaningful groups. Activity-sequence equivalence is too coarse and loses object-centric information. Typed structural equivalence is useful but ignores O2O qualifiers. Business-semantic equivalence is the best default for business interpretation, but it may be too fine for root-cause analysis when qualifiers are irrelevant. The right equivalence level depends on the decision context.
