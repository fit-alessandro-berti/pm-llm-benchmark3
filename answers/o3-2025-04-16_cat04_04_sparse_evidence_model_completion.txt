# 2. Shared Assumptions

1. Events are **completion** timestamps; ordering within equal timestamps is arbitrary (S7).  
2. Missing Supplier Confirmation events are treated as “silent skips” caused by either stocked components (S4) or the 5–10 % integration loss (S5).  
3. Expedite Review, when present, occurs exactly once per case (D6). Absence is considered legitimate.  
4. Optionality is encoded with -silent branches inside XOR blocks (ProcessTree) or by simply omitting an activity in a POWL partial order.  
5. All models respect the hard precedences:  
   Register Order  …  Approve Configuration  Release Production  Archive Case (D1,D2).  
6. The external/stocked attribute is currently unavailable; therefore Supplier Confirmation optionality is kept unconditional.

# 3. Conservative Candidate

### Inductive-bias statement  
Prioritises replaying *only* the directly observed variant orders plus high-confidence domain rules. Any behaviour not yet seen or lacking strong evidence is blocked. Preference is given to the Finance manager’s stricter sequential view (S1).

### Formal expression (ProcessTree pseudo-syntax)

```
(
   Register Order,
   xor(
       (Credit Check, Engineering Review),   // 19 traces
       (Engineering Review, Credit Check)    // 11 traces
   ),
   xor( , Supplier Confirmation),            // optional, only after both checks
   xor(                                       
       ,                                     // no Expedite Review
       (                                   // Expedite after Supplier or directly before approval
           xor(, Supplier Confirmation),    // replay both observed placements
           Expedite Review
       )
   ),
   Approve Configuration,
   Release Production,
   Archive Case
)
```

### PM4Py code (self-contained)

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# helper
def seq(*children):
    node = ProcessTree(operator=Operator.SEQUENCE)
    node.children.extend(children)
    return node

def xor(*children):
    node = ProcessTree(operator=Operator.XOR)
    node.children.extend(children)
    return node

# leaf nodes
ro  = ProcessTree(label="Register Order")
cc  = ProcessTree(label="Credit Check")
er  = ProcessTree(label="Engineering Review")
sc  = ProcessTree(label="Supplier Confirmation")
ex  = ProcessTree(label="Expedite Review")
app = ProcessTree(label="Approve Configuration")
rel = ProcessTree(label="Release Production")
arc = ProcessTree(label="Archive Case")
tau = ProcessTree(operator=Operator.TAU)

# ordering of the two checks
alt_checks = xor(seq(cc, er), seq(er, cc))

# Supplier Confirmation optional
opt_sc = xor(tau, sc)

# Expedite Review optional with two observed placements
exp_after_sc   = seq(sc, ex)
exp_before_app = seq(ex)        # in combination with prior Supplier in main flow
opt_exp = xor(tau, xor(exp_after_sc, exp_before_app))

model_conservative = seq(ro, alt_checks, opt_sc, opt_exp, app, rel, arc)
```

### Deliberately excluded behaviour

• Concurrent execution of Credit Check and Engineering Review  
• Expedite Review before Supplier Confirmation (if Supplier present) unless in the two exact observed orders  
• Supplier Confirmation before completion of *both* checks  
• Multiple executions of Expedite Review  
• Any re-work loops

### Known underfitting risks

1. Rejects valid cases where Supplier Confirmation starts right after **only one** principal check (allowed by D5, S5).  
2. Excludes future—but compliant—orders of Expedite Review (e.g. after Supplier Confirmation skip).  
3. Blocks truly parallel execution of checks, possibly harming fitness if later logs include overlap.

# 4. Balanced Candidate

### Inductive-bias statement  
Seeks the simplest model that satisfies all medium-or-higher confidence rules while reconciling contradictory stakeholder statements (S1 vs. S2) by allowing concurrency but still supporting pure sequences. Strives for good fitness **and** precision.

### Formal expression (ProcessTree)

```
(
   Register Order,
   and( Credit Check, Engineering Review ),        // concurrent or any interleaving
   xor( , Supplier Confirmation ),                // optional, starts only after both checks
   xor( , xor( Expedite Review before SC,  
                Expedite Review after SC ) ),      // precedences from D6/S6
   Approve Configuration,
   Release Production,
   Archive Case
)
```

### Why these relations?  

• Credit Check & Engineering Review inside an AND block: every permutation admitted, satisfying both S1 and S2 and D3.  
• Supplier Confirmation inside optional XOR but *sequenced after the AND join* to respect D4 (must **finish** before Approve). Lack of start-to-start link keeps the model simple yet compliant.  
• Expedite Review optional XOR containing two SEQ children: (Expedite, ) and (, Expedite) to realise “before or after SC” while still under D6 constraint “after both checks”.  
• All silent moves () ensure  1 execution.

### PM4Py code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def seq(*c):
    n=ProcessTree(operator=Operator.SEQUENCE); n.children.extend(c); return n
def xor(*c):
    n=ProcessTree(operator=Operator.XOR); n.children.extend(c); return n
def pand(*c):  # parallel AND
    n=ProcessTree(operator=Operator.PARALLEL); n.children.extend(c); return n
tau = ProcessTree(operator=Operator.TAU)

ro,cc,er,sc,ex,app,rel,arc=[ProcessTree(label=l) for l in
 ("Register Order","Credit Check","Engineering Review",
  "Supplier Confirmation","Expedite Review",
  "Approve Configuration","Release Production","Archive Case")]

checks = pand(cc, er)
opt_sc = xor(tau, sc)
exp_before_sc = seq(ex, tau)          # Supplier skipped path
exp_after_sc  = seq(tau, ex)
opt_ex = xor(tau, exp_before_sc, exp_after_sc)

model_balanced = seq(ro, checks, opt_sc, opt_ex, app, rel, arc)
```

### Behaviour deliberately excluded

• Expedite Review starting before **both** checks complete  
• Supplier Confirmation overlapping with checks (start-before-finish)  
• Multiple Expedite Review occurrences  
• Missing Approve Configuration

### Underfitting risks

1. Still disallows the “Supplier Confirmation overlaps one unfinished check” scenario posited by D5.  
2. No path for Expedite Review when Supplier Confirmation is missing *and* taken “after SC” route (minor).  
3. Ignores possible rework.

# 5. Permissive Candidate

### Inductive-bias statement  
Admits every trace that respects *only* high- and medium-confidence precedence constraints while keeping the optionality rules. Implements the constraints as a strict partial order (POWL). Everything else may interleave arbitrarily  maximally tolerant yet still compliant.

### POWL construction

```python
from pm4py.objects.powl.obj import StrictPartialOrder, Transition, SilentTransition

po = StrictPartialOrder("Production-POWL")

# transitions
t = {n: Transition(n) for n in [
  "Register Order","Credit Check","Engineering Review",
  "Supplier Confirmation","Expedite Review",
  "Approve Configuration","Release Production","Archive Case"]}

for tr in t.values(): po.transitions.add(tr)

# mandatory order edges
po.order.add_edge(t["Register Order"], t["Credit Check"])
po.order.add_edge(t["Register Order"], t["Engineering Review"])
po.order.add_edge(t["Register Order"], t["Supplier Confirmation"]) # may start anytime after RO
po.order.add_edge(t["Credit Check"], t["Approve Configuration"])
po.order.add_edge(t["Engineering Review"], t["Approve Configuration"])
po.order.add_edge(t["Supplier Confirmation"], t["Approve Configuration"])
po.order.add_edge(t["Expedite Review"], t["Approve Configuration"])
po.order.add_edge(t["Credit Check"], t["Expedite Review"])
po.order.add_edge(t["Engineering Review"], t["Expedite Review"])

po.order.add_edge(t["Approve Configuration"], t["Release Production"])
po.order.add_edge(t["Release Production"], t["Archive Case"])

# optionality handled by omitting nodes in specific instances
model_permissive = po
```

### Boundary of permissiveness

Allowed:  
• Any interleaving of CC, ER, SC after RO, as long as their **completions** precede Expedite/Approve as required.  
• Expedite Review zero or one time, placed anywhere after both checks and before approval, regardless of Supplier Confirmation presence.  

Forbidden:  
• Multiple Expedite Review.  
• Approve Configuration without finishing both principal checks.  
• Violating hard precedences RO…ARC.

### Behaviour deliberately excluded

• Any second Expedite Review  
• Ending without Archive Case  
• Missing Release Production

### Under-/overfitting discussion

Underfitting minimal; precision risk high because most orderings admitted, including some never intended (e.g. SC  CC  ER). Overfitting unlikely.

```python
variants = [
 "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case"]*12 + \
[
 "Register Order, Engineering Review, Credit Check, Supplier Confirmation, Approve Configuration, Release Production, Archive Case"]*7 + \

[
 "Register Order, Engineering Review, Credit Check, Expedite Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case"]

log = pm4py.parse_event_log_string(variants)

def to_petri(tree_or_po):
    if hasattr(tree_or_po, 'operator') or tree_or_po.__class__.__name__=='ProcessTree':
        return pt_converter.apply(tree_or_po)
    else:
        return powl_converter.apply(tree_or_po)

nets = { name: to_petri(obj) for name,obj in
         [('cons',model_conservative),('bal',model_balanced),('perm',model_permissive)] }

# --- 3. soundness ---
for name,(net,im,fm) in nets.items():
    print(name, pm4py.check_soundness(net, im, fm, print_diagnostics=False)[0])

for name,(net,im,fm) in nets.items():
    print("\n",name.upper())
    print("fitness", pm4py.fitness_alignments(log, net, im, fm)['averageFitness'])
    print("precision", pm4py.precision_alignments(log, net, im, fm))
    print("generalization", pm4py.generalization_tbr(log, net, im, fm))
    print("simplicity", pm4py.simplicity_petri_net(net, im, fm))

# --- 5. bounded random playout ---
sampled = pm4py.play_out(model_balanced, no_traces=5, max_trace_length=12)

# --- 6. manual positive/negative suite ---
pos = pm4py.parse_event_log_string([
 "Register Order, Credit Check, Engineering Review, Expedite Review, Approve Configuration, Release Production, Archive Case"])

 "Register Order, Approve Configuration, Release Production, Archive Case"])
for name,(net,im,fm) in nets.items():
    print(name,"positive ok",
          pm4py.fitness_token_based_replay(pos, net, im, fm)['percFitTraces'])
    print(name,"negative ok",
          pm4py.fitness_token_based_replay(neg, net, im, fm)['percFitTraces'])
```

Limitations: alignment-based metrics approximate language inclusion; sampled playout is *not* exhaustive.

# 9. Recommendation and Data-Collection Plan

Recommendation:  
• **Deploy the balanced model** as current reference—it covers all explicit rules, admits parallel checks, handles missing Supplier Confirmation, and keeps precision acceptable.  
• **Keep the permissive model** for sensitivity analysis and anomaly detection; any case that fits permissive but not balanced signals either a process change or data quality issue.

Data to collect next quarter:

1. Start & complete timestamps for every activity (resolve concurrency / overlap, D7).  
2. Boolean attribute external/stocked on each component to confirm Supplier Confirmation optionality (S3–S5).  
3. Unique instance ID for Expedite Review to detect duplicates (D6).  
4. Flags for skipped Supplier Confirmation due to data integration fallback.  
5. KPI tags indicating whether an order was actually expedited.

Target observation: at least 200 new traces containing every possible combination of (external vs. stocked) × (expedite vs. normal). This factorial coverage will make it possible to test whether Supplier Confirmation can indeed overlap with an unfinished check and whether Expedite Review is allowed before Supplier Confirmation in the stocked path.

# 10. Uncertainty Statement

• Concurrency of Credit Check & Engineering Review: 60 % confidence in at-least-sometimes parallel (balanced & permissive accommodate), 40 % in strictly sequential (conservative).  
• Optionality of Supplier Confirmation: 50 % true optional, 50 % “missing event” artifact.  
• Placement flexibility of Expedite Review: 70 % confidence current precedence edges are correct; 30 % risk of tighter undisclosed rules.

Alternative interpretation that could flip the recommendation: If future data show that Supplier Confirmation **always** starts only after *either* check completes (true overlap), and Expedite Review actually requires Supplier Confirmation first, then a different partial-order model with more refined causal edges would be preferable.

We estimate 0.75 overall confidence that the balanced model will remain adequate after collecting the suggested additional attributes.
