## 2. Rule Interpretation

Let (N(e)) be the normalized human identity for event (e). It is a human only when the account/alias or reliable session evidence supports that conclusion. Let (t(e)), (c(e)), (a(e)), and (s(e)) be its event time, case, activity, and scope.

1. **RR1:** for every case (c), the normalized human performing `Draft_Change_Request` must not be the normalized human performing `Approve_Change`. If either side is an unresolved service account, the result is `UNKNOWN`, not a pass. Known aliases are compared as the same person. Thus `b.koch` and `u_bk` do not create four-eyes separation.

2. **RR2:** for every case, the normalized human performing `Implement_Change` must not be the normalized human performing `Verify_Implementation`. Again, an unresolved service account prevents a conclusive human-level pass. A PM4Py check that sees two different resource strings is only a technical-resource check when one string is a service account.

3. **RR3:** for a HIGH-risk approval, the approver must have an active QM standing role at (t(e)), or there must be a QM delegation (d) such that:

   `delegate(d) = N(e)`; `t(e)` is inside the inclusive effective interval; the delegation scope covers the case scope; the principal is absent or formally unavailable where the instrument requires it; the principal's authority is valid; and no prohibited subdelegation occurred.

   A signed delegation that was effective before the event can be evidence even if a migration record was entered later. A later database row alone cannot prove that a delegation existed earlier; it proves only that the row existed at its creation time unless its history, signature, and migration provenance establish the earlier state.

4. **RR4:** for an emergency HIGH-risk case, the emergency flag must be supported by a credible safety rationale. The approval enabling implementation must be by the IC or a valid IC delegate, and implementation must follow that approval. A QM or valid QM delegate must complete `Retrospective_QM_Review` within two business days. I count the first business day after the emergency implementation as day one, exclude Saturdays, Sundays, and site holidays, and use the site calendar supplied in the question. Thus an implementation on Tuesday 2026-08-11 is due by the end of Thursday 2026-08-13. The review must also have QM authority and applicable scope; being a QM delegate for production equipment does not authorize a cooling-system review.

5. **RR5:** a service account is never itself a human. A service session supports conformance only to the extent that logs reliably bind the session to an authorized human. Badge presence at a shared workstation is corroboration, not individual authentication. Identity aliases are normalized before RR1/RR2.

6. **RR6:** repeated pairs, reciprocal approvals, shared workstations, concentrated handovers, and unusual timing are risk indicators. They justify investigation and control testing, but they do not prove collusion. A conclusion of collusion requires corroborating evidence such as individual authentication, communications, work-product comparison, access records, or benefit.

An action by a principal while on leave is treated as an availability/identity conflict, not automatically as misconduct. If Asha really performed CHG-504, she remained the QM and could directly approve; the event also means she was not absent at that instant for purposes of a delegation condition. If the account was used by somebody else, the direct authority conclusion changes to an identity problem. A principal's account activity does not automatically invalidate every prior delegation, but it weakens any claim that the principal was absent at a delegate's event unless the periods are separately established.

UTC_MAX = pd.Timestamp.max.tz_localize("UTC")


def as_utc(value):
    if value is None or pd.isna(value):
        return UTC_MAX
    return pd.to_datetime(value, utc=True)


def make_intervals(frame, start_col="start", end_col="end"):
    frame = frame.copy()
    frame[start_col] = pd.to_datetime(frame[start_col], utc=True)
    frame[end_col] = frame[end_col].map(as_utc)
    frame["interval"] = pd.IntervalIndex.from_arrays(
        frame[start_col], frame[end_col], closed="both"
    )
    return frame

def active_role(human, role, when):
    r = roles[(roles["human"] == human) & (roles["role"] == role)]
    return bool(r["interval"].map(lambda iv: when in iv).any())


def principal_is_absent(human, when):
    r = absence[absence["human"] == human]

def scope_covers(d, case, event_scope):
    if d["scope"] != event_scope:
        return False
    # D-IC-03/D-IC-04 are limited to CI-44, which is not present in the CSV.
    if d["delegation_id"] in {"D-IC-03", "D-IC-04"}:
        return case_incident.get(case) == "CI-44"
    return True


def valid_delegations(delegate, delegated_role, when, event_scope, case):
    d = delegations[
        (delegations["delegate"] == delegate)
        & (delegations["delegated_role"] == delegated_role)
        & delegations["interval"].map(lambda iv: when in iv)
    ].copy()
    if d.empty:
        return d
    d["scope_ok"] = d.apply(lambda x: scope_covers(x, case, event_scope), axis=1)
    d["principal_absent_ok"] = d.apply(
        lambda x: (not x["requires_absence"])
        or principal_is_absent(x["principal"], when),
        axis=1,
    )
    d["principal_role_ok"] = d.apply(
        lambda x: active_role(x["principal"], x["delegated_role"], when), axis=1
    )
    d["subdelegation_ok"] = ~d["is_prohibited_subdelegation"]
    return d[
        d[["scope_ok", "principal_absent_ok", "principal_role_ok", "subdelegation_ok"]]
        .all(axis=1)
    ]

        return "LOW_RISK_NO_QM_TEST", True

    if not qm.empty:

    if bool(row["emergency"]):
        if active_role(human, "IC", when):

        if ic and safety is None:

    return "NO_VALID_HIGH_RISK_AUTHORITY", False

## 6. Control Improvements

- **Delegation creation and effective time:** create an immutable, signed delegation record before use, with UTC start and end timestamps, principal, delegate, role, risk class, asset/case scope, no-subdelegation status, and activation status. Preserve the original signed artifact and migration history; never use a later database insertion time as the effective time.
- **Principal availability:** connect delegation validation to an authoritative leave/on-call/availability service. Require an explicit availability assertion or controlled exception at the event time, and flag a principal's account activity during leave for review. Do not infer availability solely from a calendar weekend.
- **Alias management:** maintain one immutable human identity key with a versioned alias map. Put the canonical human identity—not the login spelling—into SoD checks, and retain the raw identifier for audit. Disable orphaned and ambiguous aliases.
- **Individual authentication:** prohibit shared interactive accounts for approval and verification. Bind every service session to an individual with step-up MFA, short-lived tokens, workstation lock, and a signed human acknowledgment. Badge presence alone should never be the sole attribution evidence.
- **Emergency review:** require an incident ID, safety rationale, emergency declaration, and explicit IC/QM role check before implementation. Enforce the no-subdelegation rule in workflow permissions. Create an on-call QM path so the retrospective reviewer has both authority and applicable scope, and generate a due-date alert based on the site business calendar.
- **Pair rotation and independence:** introduce rotation or an independent-review queue for concentrated Clara/Ben work, especially for HIGH-risk production changes. Monitor rejection/comment rates and require substantive review evidence, without treating concentration as proof of collusion.
- **Network monitoring:** use normalized-human handover and working-together networks, with separate service-account nodes and attribution confidence. Alert on concentration, reciprocal edges, same-cell pairings, and authority mismatches; route alerts to human investigation rather than automatically labeling collusion.
- **Evidential retention:** retain signed delegations, role snapshots, availability snapshots, workflow authorization decisions, MFA/FIDO events, endpoint/session logs, badge records, service-token issuance, incident links, safety rationale, and review timestamps under an immutable retention policy. Record provenance when records are migrated.
- **Workflow enforcement:** make the approval engine evaluate the event-time role/delegation interval and normalized identity before accepting an event. Block same-human draft/approval and implement/verification where identity is known, and hold unresolved service-account events for explicit attribution rather than silently passing them.

## 7. Executive Conclusion

The evidence supports several genuine authority or SoD failures: same-human draft/approval in CHG-502, CHG-508, and CHG-510; unauthorized HIGH-risk approval in CHG-507; failure of the D-QM-02 absence condition in CHG-509 on the supplied record; and an unauthorized/late retrospective QM review in CHG-505. CHG-501 is a well-supported valid QM substitution. CHG-505's initial Farid approval is conditionally valid only if the case is CI-44 and the safety rationale is credible.

The remaining apparent deviations are primarily evidence-quality problems: CHG-503 cannot prove who operated the service account, CHG-506 has a direct account-versus-sick-leave conflict, and CHG-504 has a leave-versus-direct-QM-action conflict. The Clara/Ben concentration and reciprocal behavior create meaningful organizational-pattern risk, but the supplied facts do not prove collusion. Overall, the population contains a material core of genuine control failures, a separate material identity/data-quality problem, and a high-risk concentration pattern that needs investigation rather than a misconduct finding.

The three highest-priority investigations are:

1. Reconstruct CHG-510 and CHG-505 from the controlled incident, delegation, workflow, and communication records, including the CI-44 link, safety rationale, prohibited subdelegation, and QM retrospective authority.
2. Resolve the authentication and attribution conflicts in CHG-503, CHG-504, and CHG-506 using MFA/FIDO, endpoint, badge, service-session, and leave-override evidence.
3. Review all 23 Clara/Ben HIGH-risk production cases for event-time delegation validity, substantive independent review, alias use, and pair concentration, while preserving the distinction between a suspicious pattern and proof of collusion.
