## 1. Equivalence design space

To cluster object-centric executions meaningfully, we define three equivalence relations ranging from syntactic to semantic. Each relation is an equivalence relation (reflexive, symmetric, transitive).

**1. Activity-Sequence Equivalence (ASE)**
*   **Definition:** Two executions are equivalent if their sequence of activity labels is identical. Object identifiers, types, and parameters are ignored.
*   **Invariants Preserved:** Control flow order, activity labels, event multiplicity.
*   **Information Discarded:** Object topology, object types, external dependencies, event parameters, qualifiers.
*   **Concurrency:** Treats events as a total order based on timestamp. Simultaneous events are ordered arbitrarily but must match exactly in the compared sequence.
*   **Use Case:** High-level process mining where object complexity is noise.

**2. Typed Structural Equivalence (TSE)**
*   **Definition:** Two executions are equivalent if there exists an isomorphism between their object-event graphs that preserves object types, event types, and relations, modulo local identifier renaming. External objects (`EXT`) are treated as distinct types or flagged.
*   **Invariants Preserved:** Object types, event parameters (which objects are involved), cardinality (e.g., 1 Invoice vs 2 Payments), graph topology.
*   **Information Discarded:** Specific identifier values (e.g., O1 vs O2), absolute timestamps.
*   **Concurrency:** Structural isomorphism respects the partial order induced by object lifecycles. If event order differs but causal dependencies remain identical, they may be considered equivalent depending on strictness. Here, we enforce strict event order for reproducibility.
*   **Use Case:** Technical validation, schema compliance, detecting structural deviations.

**3. Business-Semantic Equivalence (BSE)**
*   **Definition:** Two executions are equivalent if they represent the same business lifecycle motif, considering external dependencies, qualification flags (e.g., `removed_before_dispatch`), and lifecycle exceptions (e.g., Returns).
*   **Invariants Preserved:** Isolation status (internal vs. external), fulfillment integrity (standard vs. split vs. return), financial settlement logic.
*   **Information Discarded:** Minor structural variations that do not impact business outcome (e.g., split packages consolidated on one delivery vs. split deliveries might be grouped as "Split Logistics").
*   **Concurrency:** Focuses on causal milestones (e.g., "Payment Settled") rather than exact event interleaving.
*   **Use Case:** Operational segmentation, risk analysis, performance benchmarking.

## 2. Canonical signatures

We select **Business-Semantic Equivalence (BSE)** as the preferred relation for clustering, as it balances structural detail with business meaning. The canonical signature is a tuple constructed from normalized execution features.

```python
def generate_bse_signature(execution):
    """
    Generates a hashable signature for Business-Semantic Equivalence.
    execution: Dict containing events, objects, and o2o_notes.
    """
    # 1. Activity Sequence (Abstracted)
    # Map specific variations to standard labels if needed, else use raw labels
    activity_sequence = tuple(e['activity'] for e in execution['events'])
    
    # 2. External Dependency Flags
    # Check for EXT objects in specific phases
    has_ext_logistics = any('EXT' in str(e['objects']) for e in execution['events'] 
                            if e['activity'] in ['Pack Package', 'Dispatch'])
    has_ext_finance = any('EXT' in str(e['objects']) for e in execution['events'] 
                          if e['activity'] in ['Issue Invoice', 'Record Payment'])
    ext_flag = (has_ext_logistics, has_ext_finance)
    
    # 3. Lifecycle Motif
    # Detect returns, substitutions, or splits
    has_return = 'Return Item' in activity_sequence
    has_split_delivery = execution['o2o_notes'].get('split_delivery', False)
    has_substitution = execution['o2o_notes'].get('substitution', False)
    motif = (has_return, has_split_delivery, has_substitution)
    
    # 4. Payment Multiplicity
    payment_count = sum(1 for e in execution['events'] if e['activity'] == 'Record Payment')
    
    # Combine into signature
    # We abstract X3 and X4 into 'Split Logistics' despite payment diff for broader clustering
    if motif[1]: 
        motif_key = 'SPLIT_LOGISTICS'
    elif motif[0]:
        motif_key = 'RETURN_EXCEPTION'
    elif motif[2]:
        motif_key = 'SUBSTITUTION'
    elif ext_flag[0] or ext_flag[1]:
        motif_key = 'EXTERNAL_DEPENDENCY'
    else:
        motif_key = 'STANDARD_FULFILLMENT'
        
    return (motif_key, ext_flag, payment_count > 1)
```

This signature ignores local IDs, preserves external dependency types, and groups structural variations (like X3 vs X4) under common business motifs while retaining enough detail (payment count) to distinguish significant financial risks.

## 4. Cluster interpretations

**Cluster 1: Standard Fulfillment (X1, X2)**
*   **Signature:** Isolated order, single package/delivery/invoice/payment.
*   **Business Behavior:** The "Happy Path." An order is created, fulfilled, and settled without external interference or exceptions.
*   **Risks/Opportunities:** Low risk. Opportunities for automation are highest here.
*   **Flattening:** Traditional case tables represent this well.
*   **Stability:** Highly stable under data repair; identifier changes do not affect semantics.

**Cluster 2: Split Logistics (X3, X4)**
*   **Signature:** Multiple packages or deliveries, potentially multiple payments.
*   **Business Behavior:** Complex fulfillment due to item availability, size, or shipping constraints. X4 indicates cash-flow fragmentation (partial payment).
*   **Risks/Opportunities:** Higher logistics cost risk. X4 introduces reconciliation risk (matching multiple payments to one invoice).
*   **Flattening:** Poorly represented by flat tables; one order row cannot easily capture multiple delivery rows without duplication.
*   **Stability:** Stable, but sensitive to event granularity (e.g., if Dispatch is split).

**Cluster 3: External Dependency (X5, X6)**
*   **Signature:** Presence of `EXT` objects in Logistics (X5) or Finance (X6).
*   **Business Behavior:** Cross-order consolidation. X5 shares shipping (cost saving); X6 shares billing (contractual relationship).
*   **Risks/Opportunities:** Coupling risk. If EXT-Order fails, this order is impacted. Revenue recognition may be complex in X6.
*   **Flattening:** Very poor. Flat tables cannot represent the many-to-many relationship between Orders and Invoices/Packages easily.
*   **Stability:** Depends on accurate flagging of external objects.

**Cluster 4: Exception/Change (X7, X8)**
*   **Signature:** Substitution qualifiers (X7) or Return events (X8).
*   **Business Behavior:** Deviation from plan. X7 is a silent correction; X8 is a reverse logistics loop.
*   **Risks/Opportunities:** High customer satisfaction risk. X7 risks inventory discrepancy if not tracked. X8 increases handling costs.
*   **Flattening:** Poor. Loops and substitutions are often lost in case-level aggregation.
*   **Stability:** Unstable; depends heavily on data quality (qualifiers often missing).

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The `pm4py.cluster_equivalent_ocel` function clusters OCELs based on exact graph isomorphism of the object-event network.

*   **Preserved Information:** It preserves exact activity labels, object types, and the relations between them. It is sensitive to the exact structure of the OCEL.
*   **Identifier Issue:** Raw identifiers make clusters too fine (X1 != X2). `pm4py` handles this by abstracting IDs during isomorphism checks, but external objects (`EXT`) might be treated as unique types unless normalized.
*   **Canonicalization:** To align with BSE, post-processing is required. We must merge clusters that differ only in "acceptable" structural variations (e.g., merging X3 and X4).
*   **Exact vs. Coarse:** Exact equivalence is preferable for compliance (detecting unauthorized deviations). Coarse clustering is better for operational reporting (understanding general flow types).
*   **Scalability:** `max_objs` limits complexity. Large connected executions (like X5/X6 with external links) may exceed limits or be truncated, breaking equivalence checks.

```python
import pm4py

def cluster_executions_business_semantic(ocel_list):
    # 1. Exact Structural Clustering
    clusters_exact = pm4py.cluster_equivalent_ocel(ocel_list, activity_key='activity', 
                                                   object_type_key='object_type')
    
    # 2. Post-process for Business Semantics
    clusters_semantic = {}
    for cluster_id, ocel_indices in clusters_exact.items():
        # Extract signature from representative OCEL
        rep_ocel = ocel_list[ocel_indices[0]]
        sig = generate_bse_signature(rep_ocel)
        
        # Merge into semantic bucket
        if sig not in clusters_semantic:
            clusters_semantic[sig] = []
        clusters_semantic[sig].extend(ocel_indices)
        
    return clusters_semantic
```

## 7. Robustness analysis

We analyze how cluster assignments change under perturbations of the equivalence definition.

1.  **Ignore all O2O qualifiers:** X7 (Substitution) merges into **Standard Fulfillment**. The distinction between " replacing an item" and "adding an item" is lost. This increases false negatives in quality monitoring.
2.  **Ignore external objects:** X5 and X6 merge into **Standard Fulfillment**. The critical distinction of shared resources is lost. This hides supply chain and financial coupling risks.
3.  **Collapse repeated same-label events:** X4 (2 Payments) might merge with X1 if payment multiplicity is ignored. This hides partial payment scenarios, impacting cash-flow analysis.
4.  **Treat Pack/Dispatch as partial order:** If Pack and Dispatch are considered concurrent, X3 (Split Pack, Single Dispatch) might structurally resemble X1 depending on graph interpretation. However, BSE relies on the *result* (multiple packages), so the cluster assignment remains **Split Logistics**.
5.  **Payment as Attribute:** If payment count is an amount attribute rather than structure, X4 merges with X1 in TSE. BSE preserves the distinction via the `payment_count > 1` flag in the signature.

These perturbations show that BSE is more robust to structural noise (like event ordering) but sensitive to semantic flags (like EXT or Qualifiers).

## 8. Limitations and recommendation

No single equivalence notion serves all purposes.

*   **Compliance Monitoring:** Use **Typed Structural Equivalence (TSE)**. Strict adherence to process schema is required. Deviations like X7 (substitution) or X6 (shared invoice) must be flagged individually.
*   **Operational Segmentation:** Use **Business-Semantic Equivalence (BSE)**. Managers need to know "Split Logistics" volume vs. "Returns", not exact graph isomorphism. This enables resource planning.
*   **Root-Cause Analysis:** Use **TSE + Qualifiers**. To understand why X7 happened, the specific qualifier `removed_before_dispatch` is vital. BSE hides this detail.
*   **Descriptive Reporting:** Use **Activity-Sequence Equivalence (ASE)**. For high-level stakeholder updates, knowing "90% of orders follow the standard sequence" is sufficient without object complexity.

**Recommendation:** Adopt **Business-Semantic Equivalence (BSE)** as the default for object-centric process mining dashboards. It offers the best trade-off between the noise of exact structural matching and the oversimplification of activity sequences. It highlights meaningful variations (External Dependencies, Exceptions) that drive business value and risk, while remaining robust to irrelevant identifier changes. However, systems must allow drilling down into TSE for compliance audits where exact structure matters.
