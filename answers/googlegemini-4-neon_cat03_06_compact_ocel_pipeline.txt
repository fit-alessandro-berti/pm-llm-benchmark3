## 1. Modeling assumptions

- **Object types and capitalization**: Six PascalCase singular object types are used consistently across `objects` and `relations`: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Activity names use Title Case (`Create Order`, `Add Item`, `Reserve Stock`, `Pack Package`, `Dispatch Package`, `Issue Invoice`, `Record Payment`, `Confirm Delivery`, `Close Order`).
- **E2O qualifier vocabulary**: Qualifiers use lowercase `snake_case` in the form `<role>_<object_type>` to express the operational role each object plays in an event:
  - `Order`: `created_order`, `parent_order`, `associated_order`, `billed_order`, `closed_order`
  - `Item`: `added_item`, `reserved_item`, `packed_item`
  - `Package`: `packed_package`, `dispatched_package`
  - `Delivery`: `dispatched_delivery`, `confirmed_delivery`
  - `Invoice`: `issued_invoice`, `settled_invoice`
  - `Payment`: `recorded_payment`
- **O2O direction conventions**: Every `o2o` row is directed from the governing, containing, or acting object (`ocel:oid`) to the contained, carried, or acted-upon object (`ocel:oid_2`), so each triple reads naturally as `<ocel:oid> <ocel:qualifier> <ocel:oid_2>`:
  - `Order` `contains` `Item`
  - `Package` `packs` `Item`
  - `Delivery` `carries` `Package`
  - `Invoice` `bills` `Order`
  - `Payment` `partially_settles` `Invoice` (for `M1`, the first partial payment) and `Payment` `completes_settlement` `Invoice` (for `M2`, the final partial payment that settles `V1` before order closure).
- **Direct relations for logistics and financial events (trade-off)**: The baseline dataset follows a **direct operational involvement** policy:
  - Events explicitly involving Orders and Items in the operational narrative (`Add Item`, `Reserve Stock`, `Pack Package`, `Issue Invoice`) link directly to those Orders/Items. For activity-schema consistency, `Pack Package` for `P2` (`E08`) also links to `O100` (just as `Pack Package` for `P1` links to `O100` and `O200`).
  - Downstream carrier/logistics events (`Dispatch Package`, `Confirm Delivery`) link only to their native logistics objects (`Delivery` and `Package` for dispatch; `Delivery` for delivery confirmation), **not** directly to `Order` or `Item`.
  - Financial settlement events (`Record Payment`) link only to `Payment` and `Invoice`, **not** directly to `Order` or `Item`, because partial payments against a consolidated multi-order invoice (`V1`) have no unambiguous order-level allocation in the source narrative.
  - *Trade-off*: Direct source relations preserve system provenance, prevent double-counting of shared logistics/financial events across Orders, and keep the OTG structurally faithful to system boundaries; however, flattening on `Order` omits dispatch, delivery confirmation, and payment. Conversely, analytically propagating O2O links into E2O makes flattened `Order` views end-to-end complete at the cost of relation inflation and unverified attribution.
- **Preventing analytical propagation from being confused with source facts**: Structural links live exclusively in `o2o`, while `relations` stores only directly observed event-to-object facts. If an analyst later needs a propagated view (e.g., projecting `Confirm Delivery` onto `Order` via `Delivery -> Package -> Item <- Order`), it must be materialized as a **separate derived OCEL instance** whose propagated qualifiers are explicitly prefixed (e.g., `derived_o2o:delivered_order`) or accompanied by a provenance column (`relation_origin = "source"` vs. `"propagated_o2o"`). Source tables are never overwritten in place.
- **Version-dependent PM4Py assumptions**: The pipeline targets PM4Py 2.7+ with OCEL 2.0 support, where `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`, `pm4py.discover_otg`, and `pm4py.discover_etot` are available. The constructor call is isolated inside `build_ocel(...)` so that an older PM4Py build without the `o2o` constructor parameter can be adapted in one line (e.g., constructing `OCEL(events=events, objects=objects, relations=relations)` and attaching `ocel.o2o = o2o.copy()`) without altering any data semantics. Similarly, `pm4py.discover_otg` and `pm4py.discover_etot` are version-sensitive top-level wrappers introduced alongside OCEL 2.0 discovery utilities.

        # E12: Record Payment M1 (100 MU) against V1
        ("E12", "M1",   "recorded_payment"),
        ("E12", "V1",   "settled_invoice"),
        # E13: Confirm Delivery D1
        ("E13", "D1",   "confirmed_delivery"),
        # E14: Confirm Delivery D2
        ("E14", "D2",   "confirmed_delivery"),
        # E15: Record Payment M2 (150 MU) against V1
        ("E15", "M2",   "recorded_payment"),

def validate_ocel_tables(
    events: pd.DataFrame,
    objects: pd.DataFrame,
    relations: pd.DataFrame,
    o2o: pd.DataFrame,
) -> None:
    """Verify schema, uniqueness, referential integrity, and attribute consistency."""
    # Mandatory columns
    assert {"ocel:eid", "ocel:activity", "ocel:timestamp"}.issubset(events.columns)
    assert {"ocel:oid", "ocel:type"}.issubset(objects.columns)
    assert {
        "ocel:eid",
        "ocel:activity",
        "ocel:timestamp",
        "ocel:oid",
        "ocel:type",
        "ocel:qualifier",
    }.issubset(relations.columns)
    assert {"ocel:oid", "ocel:oid_2", "ocel:qualifier"}.issubset(o2o.columns)

    # Timezone-aware timestamps
    assert isinstance(events["ocel:timestamp"].dtype, pd.DatetimeTZDtype), (
        "events['ocel:timestamp'] must be timezone-aware."
    )
    assert isinstance(relations["ocel:timestamp"].dtype, pd.DatetimeTZDtype), (
        "relations['ocel:timestamp'] must be timezone-aware."
    )

    # Unique primary keys
    assert events["ocel:eid"].is_unique, "Duplicate event IDs found in events."
    assert objects["ocel:oid"].is_unique, "Duplicate object IDs found in objects."

    # Non-null qualifiers
    assert relations["ocel:qualifier"].notna().all(), "Null E2O qualifier detected."
    assert o2o["ocel:qualifier"].notna().all(), "Null O2O qualifier detected."

    # Referential integrity: no orphan event IDs or object IDs
    event_ids = set(events["ocel:eid"])
    object_ids = set(objects["ocel:oid"])

    orphan_rel_eids = set(relations["ocel:eid"]) - event_ids
    assert not orphan_rel_eids, f"Orphan event IDs in relations: {orphan_rel_eids}"

    orphan_rel_oids = set(relations["ocel:oid"]) - object_ids
    assert not orphan_rel_oids, f"Orphan object IDs in relations: {orphan_rel_oids}"

    orphan_o2o_src = set(o2o["ocel:oid"]) - object_ids
    orphan_o2o_dst = set(o2o["ocel:oid_2"]) - object_ids
    assert not orphan_o2o_src, f"Orphan source object IDs in o2o: {orphan_o2o_src}"
    assert not orphan_o2o_dst, f"Orphan target object IDs in o2o: {orphan_o2o_dst}"

    # Activity, timestamp, and object-type consistency between base tables and relations
    rel_evt = relations.merge(
        events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
        on="ocel:eid",
        suffixes=("_rel", "_evt"),
        how="left",
        validate="many_to_one",
    )
    assert (rel_evt["ocel:activity_rel"] == rel_evt["ocel:activity_evt"]).all(), (
        "Activity mismatch between events and relations."
    )
    assert (rel_evt["ocel:timestamp_rel"] == rel_evt["ocel:timestamp_evt"]).all(), (
        "Timestamp mismatch between events and relations."
    )

    rel_obj = relations.merge(
        objects[["ocel:oid", "ocel:type"]],
        on="ocel:oid",
        suffixes=("_rel", "_obj"),
        how="left",
        validate="many_to_one",
    )
    assert (rel_obj["ocel:type_rel"] == rel_obj["ocel:type_obj"]).all(), (
        "Object type mismatch between objects and relations."
    )

    # Absence of duplicate relation rows and O2O anomalies
    assert not relations.duplicated().any(), "Duplicate full rows in relations."
    assert not relations.duplicated(
        subset=["ocel:eid", "ocel:oid", "ocel:qualifier"]
    ).any(), "Duplicate (eid, oid, qualifier) entries in relations."
    assert not o2o.duplicated(
        subset=["ocel:oid", "ocel:oid_2", "ocel:qualifier"]
    ).any(), "Duplicate rows in o2o."
    assert (o2o["ocel:oid"] != o2o["ocel:oid_2"]).all(), "Self-loop detected in o2o."

    # Coverage: every declared event and object participates in at least one E2O row
    assert set(relations["ocel:eid"]) == event_ids, "Unlinked event(s) found."
    assert set(relations["ocel:oid"]) == object_ids, "Unlinked object(s) found."


def build_ocel(
    events: pd.DataFrame,
    objects: pd.DataFrame,

    """

### Most consequential events for convergence and divergence

- **Convergence hotspots (single event joining multiple objects of the same type)**:
  - **`E06` (`Reserve Stock`)**: Touches two Orders (`O100`, `O200`) and two Items (`I1`, `I3`). It is the earliest cross-order coupling point and duplicates once per Order (and once per Item) under flattening.
  - **`E07` (`Pack Package` for `P1`)**: Touches `P1`, `I1`, `I3`, `O100`, and `O200` (5 E2O rows—the highest fan-in event in the log). It physically merges items from two distinct Orders into a single parcel, driving convergence in both `Order` and `Item` flattenings.
  - **`E11` (`Issue Invoice` for `V1`)**: Touches `V1`, `O100`, and `O200`. It creates financial convergence across both Orders, duplicating the single invoicing event when flattened on `Order`.
- **Divergence hotspots (multiple events of the same activity attached to one object)**:
  - **`E02` & `E03` (`Add Item` for `O100`)**: Two item-addition events share `O100`, producing an `Add Item -> Add Item` self-loop in the flattened `Order` view even though each `Item` (`I1`, `I2`) is added once.
  - **`E07` & `E08` (`Pack Package` for `O100`)**: `O100` is split across `P1` and `P2`, creating a `Pack Package -> Pack Package` self-loop in the flattened `Order` view even though each `Package` is packed once.
  - **`E12` & `E15` (`Record Payment` for `V1`)**: Two distinct payments (`M1`, `M2`) settle `V1`, creating a `Record Payment -> Record Payment` self-loop in the flattened `Invoice` view even though each `Payment` is recorded once.

## 4. Expected flattened behavior

### Flattening on `Order` (`O100`, `O200`)
- **Approximate trace shape**: Two cases totaling 14 flattened event rows (from 11 distinct Order-touching events):
  - `O100` (len 8): `Create Order -> Add Item -> Add Item -> Reserve Stock -> Pack Package -> Pack Package -> Issue Invoice -> Close Order`
  - `O200` (len 6): `Create Order -> Add Item -> Reserve Stock -> Pack Package -> Issue Invoice -> Close Order`
- **Copied shared events**: `E06` (`Reserve Stock`), `E07` (`Pack Package` for `P1`), and `E11` (`Issue Invoice` for `V1`) are each duplicated across both `O100` and `O200`.
- **Omitted lifecycle aspects**: `Dispatch Package` (`E09`, `E10`), `Confirm Delivery` (`E13`, `E14`), and `Record Payment` (`E12`, `E15`) disappear completely (6 of 17 events dropped).
- **Likely DFG edges**: `Create Order -> Add Item (2)`, `Add Item -> Add Item (1)`, `Add Item -> Reserve Stock (2)`, `Reserve Stock -> Pack Package (2)`, `Pack Package -> Pack Package (1)`, `Pack Package -> Issue Invoice (2)`, `Issue Invoice -> Close Order (2)`.
- **Misleading interpretations**:
  - Event counts overstate operational workload (`Reserve Stock` appears to happen twice, `Pack Package` three times, and `Issue Invoice` twice).
  - The self-loop `Pack Package -> Pack Package` can look like rework/repacking rather than split fulfillment of `O100` into `P1` and `P2`.
  - The direct edge `Issue Invoice -> Close Order` makes it look as though Orders close without shipping, delivery confirmation, or payment, while hiding that the ~23.5-hour wait between `Issue Invoice` and `Close Order` is actually driven by `D2` delivery and `M2` settlement.

### Flattening on `Package` (`P1`, `P2`)
- **Approximate trace shape**: Two identical length-2 traces (`Pack Package -> Dispatch Package` for `P1` and `P2`).
- **Copied shared events**: None (`E07`/`E09` belong solely to `P1`; `E08`/`E10` belong solely to `P2`).
- **Omitted lifecycle aspects**: All order creation, item addition, stock reservation, delivery confirmation, invoicing, payment, and order closure events (13 of 17 events dropped).
- **Likely DFG edges**: `Pack Package -> Dispatch Package (2)`.
- **Misleading interpretations**: Suggests a trivial, homogeneous 2-step process. Completely hides that `P1` consolidates items from two Orders (`O100`, `O200`) while `P2` serves only `O100`, and hides that `P1`'s carrier leg (`D1`) was delivered 20 hours earlier than `P2`'s (`D2`).

### Flattening on `Delivery` (`D1`, `D2`)
- **Approximate trace shape**: Two identical length-2 traces (`Dispatch Package -> Confirm Delivery` for `D1` and `D2`).
- **Copied shared events**: None.
- **Omitted lifecycle aspects**: All pre-dispatch fulfillment (`Create Order`, `Add Item`, `Reserve Stock`, `Pack Package`) and all financial/closure stages (`Issue Invoice`, `Record Payment`, `Close Order`)—13 of 17 events dropped.
- **Likely DFG edges**: `Dispatch Package -> Confirm Delivery (2)`.
- **Misleading interpretations**: Structurally appears identical across `D1` and `D2` (masking the asymmetric business impact: `D1` delivers `O200`'s entire order plus half of `O100`, whereas `D2` delivers only `I2` for `O100`). Although throughput time differs sharply (3 hours for `D1` vs. 22h 45m for `D2`), a `Delivery`-only view cannot show how `D2`'s delay relates to payment `M2` or order closure.

### Flattening on `Invoice` (`V1`)
- **Approximate trace shape**: One single trace of length 3: `Issue Invoice -> Record Payment -> Record Payment`.
- **Copied shared events**: None (only one invoice exists).
- **Omitted lifecycle aspects**: All order, item, packing, dispatch, delivery confirmation, and order closure events (14 of 17 events dropped).
- **Likely DFG edges**: `Issue Invoice -> Record Payment (1)`, `Record Payment -> Record Payment (1)`.
- **Misleading interpretations**: A single-case log (`N = 1`) cannot distinguish normal behavior from exceptions. The `Record Payment` self-loop obscures that `M1` (100 MU) and `M2` (150 MU) are two distinct payment objects rather than repeated updates to one payment, and hides that `V1` bills two Orders (`O100`, `O200`) whose deliveries (`D1`, `D2`) interleave between `M1` and `M2`.

### Why flattening on `Payment` (`M1`, `M2`) is particularly weak
Flattening on `Payment` produces two length-1 traces (`M1: [Record Payment]`, `M2: [Record Payment]`), dropping 15 of 17 events. Because every trace has length 1, the discovered DFG has **zero edges**, the log skeleton collapses to trivial single-activity frequency constraints, and there is no trace-level evidence that `M1` and `M2` both settle the same invoice `V1` in sequence (`M1` partially, `M2` completing settlement).

## 5. Expected object-centric structures

- **OC-DFG (`discover_ocdfg`)**: Overlays six typed directly-follows layers onto the 9 shared activity nodes without duplicating events:
  - The `Order` layer traces `Create Order -> Add Item (loop on O100) -> Reserve Stock -> Pack Package (loop on O100) -> Issue Invoice -> Close Order`.
  - The `Item` layer reveals a crucial fulfillment distinction invisible in the `Order` DFG: `I1` and `I3` follow `Add Item -> Reserve Stock -> Pack Package`, whereas `I2` jumps directly `Add Item -> Pack Package` (no stock reservation logged for `I2`).
  - The `Package` layer links `Pack Package -> Dispatch Package` (for `P1` and `P2`), handing off to the `Delivery` layer (`Dispatch Package -> Confirm Delivery` for `D1` and `D2`).
  - The `Invoice` layer branches from `Issue Invoice` (for `V1`) to `Record Payment` with a self-loop (`M1` followed by `M2`), while the `Payment` layer marks `Record Payment` solely as a start/end activity for `M1` and `M2`.
  - Crucially, event-count annotations keep `Reserve Stock`, `Pack Package` (`P1`), and `Issue Invoice` (`V1`) at **1 event each**, while object-count annotations show **2 `Order` objects** (`O100`, `O200`) passing through them.

- **OTG (`discover_otg`)**: Captures which object types co-occur in events, revealing three architectural zones bridged by handoff types:
  - A tightly coupled fulfillment triangle `Order`–`Item`–`Package` (driven by `Add Item`, `Reserve Stock`, and especially `Pack Package` where `P1` binds `O100`, `O200`, `I1`, and `I3`).
  - A logistics tail `Package`–`Delivery` (linked via `Dispatch Package`).
  - A financial branch `Order`–`Invoice` (via `Issue Invoice` for `V1` billing `O100` and `O200`) extending to `Invoice`–`Payment` (via `Record Payment` for `M1` and `M2` against `V1`).
  - Notably, there is no direct OTG edge between `Order` and `Delivery` or between `Order` and `Payment`, directly reflecting the source-faithful E2O boundary.

- **ET–OT graph (`discover_etot`)**: Produces the bipartite incidence structure between the 9 activities and 6 object types:
  - Separates single-type boundary activities (`Create Order`–`Order`, `Confirm Delivery`–`Delivery`, `Close Order`–`Order`) from multi-type synchronization activities (`Add Item`, `Reserve Stock`, `Pack Package`, `Dispatch Package`, `Issue Invoice`, `Record Payment`).
  - Exposes cardinality variance: `Pack Package` involves 1 `Package` (`P1` or `P2`) but 1–2 `Item`s and 1–2 `Order`s (2 for `P1` across `O100`/`O200`; 1 for `P2` on `O100`); `Issue Invoice` links 1 `Invoice` (`V1`) to 2 `Order`s (`O100`, `O200`); `Record Payment` links 1 `Payment` (`M1` or `M2`) to 1 `Invoice` (`V1`).

- **Object-centric Petri net (`discover_oc_petri_net`)**: Synthesizes per-object-type Petri nets (each discovered from its flattened projection) merged on shared activity transitions, with variable arcs indicating multi-token consumption/production (notably for `Order` and `Item` tokens at `Reserve Stock` and `Pack Package` due to `P1`, and for `Order` tokens at `Issue Invoice` due to `V1`):
  - It visualizes synchronization points cleanly: `Pack Package` synchronizes `Order`, `Item`, and `Package`; `Dispatch Package` synchronizes `Package` and `Delivery`; `Issue Invoice` synchronizes `Order` and `Invoice`; `Record Payment` synchronizes `Invoice` and `Payment` (`M1`, `M2` on `V1`).
  - **Non-uniqueness of interpretation**: An automatically discovered OC-Petri net does **not** have one uniquely determined behavioral interpretation. Because PM4Py discovers each object-type net independently via flattening and glues them on shared transitions, the combined net can permit behaviors not intended by the business rules (for instance, firing `Close Order` for `O100` or `O200` before `Confirm Delivery` or before `M2` settles `V1`, because `Order` tokens do not pass through `Confirm Delivery` or `Record Payment`; or firing arbitrary numbers of `Add Item`, `Pack Package`, or `Record Payment` loops). It also does not enforce instance-level `o2o` identity binding (e.g., ensuring `P1` specifically carries `I1` from `O100` and `I3` from `O200`). Therefore, it should be read as a structural approximation rather than a complete executable specification.

- **Object-interactions summary (`ocel_objects_interactions_summary`)**: Reports instance-level co-occurrence across events (E2O-derived interactions, distinct from static `o2o`):
  - Shows direct event-level interaction between `O100` and `O200` (co-occurring in `E06`, `E07`, and `E11`), highlighting their operational and financial entanglement.
  - Shows `P1` directly interacting with `O100`, `O200`, `I1`, `I3` (at `E07`) and `D1` (at `E09`), contrasting with `P2` which interacts only with `O100`, `I2` (at `E08`) and `D2` (at `E10`).
  - Shows `V1` directly interacting with `O100`, `O200` (at `E11`) and separately with `M1` (at `E12`) and `M2` (at `E15`).
  - Confirms that `M1` and `M2` never directly co-occur in the same event (they connect only transitively through `V1`), and that `O100`/`O200` do not directly co-occur with `D1`, `D2`, `M1`, or `M2`—providing a concrete contrast against the transitive paths stored in `o2o`.

## 6. Modeling alternatives

1. **Source-minimal E2O policy (strict primary-object logging)**
   - *Definition*: Link each event only to the immediate primary objects manipulated by its executing microservice—e.g., `Reserve Stock` (`E06`) links only to `Item` (`I1`, `I3`), and `Pack Package` (`E07`, `E08`) links only to `Package` and `Item` (omitting `Order` from both activities), relying on `o2o` (`Order contains Item`) to associate fulfillment with Orders.
   - *Impact on discovery*: Flattened `Order` traces shrink to `Create Order -> Add Item -> Issue Invoice -> Close Order`, removing `Reserve Stock` and `Pack Package` convergence and eliminating the `Pack Package` self-loop on `O100`. In the OTG, the direct `Order`–`Package` edge vanishes (leaving `Item` as the sole bridge between `Order` and `Package`), and in the OC-Petri net `Order` tokens no longer synchronize at `Reserve Stock` or `Pack Package`. The underlying business story is unchanged, but operational cross-order contention at stock reservation and packing becomes invisible without an O2O join.

2. **Direct operational involvement (chosen baseline policy)**
   - *Definition*: Record all objects directly referenced by the operational event (`Order` + `Item` at `Reserve Stock`; `Order` + `Item` + `Package` at `Pack Package`; `Delivery` + `Package` at `Dispatch Package`; `Invoice` + `Order` at `Issue Invoice`; `Payment` + `Invoice` at `Record Payment`), without propagating downstream logistics or payment events onto Orders or Items.
   - *Impact on discovery*: Captures the explicitly stated cross-order sharing at `Reserve Stock`, `Pack Package` (`P1`), and `Issue Invoice` (`V1`), keeps the OTG cleanly segmented into fulfillment, logistics, and finance, and avoids inventing payment-to-order allocations. The trade-off is that `Order` flattening omits shipping, delivery confirmation, and payment, and `Package` flattening ends at `Dispatch Package`.

3. **Logistics-extended Package continuity (targeted local enrichment)**
   - *Definition*: Keep the baseline policy for Orders and Payments, but additionally relate `Confirm Delivery` (`E13`, `E14`) to the delivered `Package` (`P1`, `P2`)—reflecting carrier proof-of-delivery scans at parcel level.
   - *Impact on discovery*: Flattened `Package` traces expand from length 2 to length 3 (`Pack Package -> Dispatch Package -> Confirm Delivery`), making delivery throughput times visible at the `Package` level without polluting `Order` traces with duplicated logistics events or fabricating payment allocations. The ET–OT graph gains a `Confirm Delivery`–`Package` edge, and `Confirm Delivery` becomes a synchronization transition between `Delivery` and `Package` in the OC-Petri net.

4. **O2O-propagated analytical policy (transitive Order-centric enrichment)**
   - *Definition*: Materialize transitive `o2o` paths into a derived `relations` table so that `Dispatch Package` and `Confirm Delivery` also link to `Item` and `Order` (via `Delivery -> Package -> Item <- Order`), and `Record Payment` (`M1`, `M2`) also links to `O100` and `O200` (via `Payment -> Invoice -> Order`).
   - *Impact on discovery*: Flattened `Order` traces become end-to-end complete (`Create Order -> ... -> Dispatch Package -> Confirm Delivery -> Record Payment -> Close Order`), and the OC-Petri net enforces that `Order` tokens pass through delivery and payment prior to `Close Order`. However, `O100` and `O200` now both receive copies of `E09` (`Dispatch Package` `D1`), `E13` (`Confirm Delivery` `D1`), `E12` (`M1`), and `E15` (`M2`), causing severe event duplication, double-counting of payments (each order appears linked to 250 MU, totaling 500 MU across the flattened log), and a near-clique OTG that obscures true system boundaries.

## 7. Failure modes

1. **Relation inflation**: Over-eagerly linking every tangentially connected object to every event (e.g., attaching all Orders, Items, Packages, and Invoices to `Confirm Delivery` and `Record Payment`) explodes the size of `relations`, turns the OTG into an uninformative dense clique, adds spurious variable arcs to the OC-Petri net, and slows discovery algorithms. *Mitigation*: Restrict base `relations` to directly observed operational links and keep structural joins in `o2o`.
2. **Missing direct E2O links**: Under-linking events—such as omitting `Order` from `Issue Invoice` (`E11`) or omitting `Package` from `Dispatch Package` (`E09`, `E10`)—disconnects the OTG into isolated components and blinds object-centric discovery to genuine synchronization points and cross-order bottlenecks. *Mitigation*: Enforce activity-level E2O schema templates and verify OTG connectivity during model auditing.
3. **Treating O2O propagation as observation**: Merging inferred `o2o` paths directly into `relations` without provenance tags causes analysts and KPI queries to treat derived links as ground-truth source events—leading to double-counted revenue, fabricated timestamps of involvement, and non-auditable logs. *Mitigation*: Store propagated datasets separately with explicit `derived_o2o:` qualifier prefixes.
4. **Duplicate shared events after flattening**: Flattening on `Order` duplicates shared events `E06` (`Reserve Stock`), `E07` (`Pack Package` for `P1`), and `E11` (`Issue Invoice` for `V1`) across both `O100` and `O200`. Naive frequency counts, cost sums, or throughput-bottleneck statistics computed on the flattened DataFrame will overestimate workload by counting one physical event multiple times. *Mitigation*: Compute event-volume and cost KPIs directly on `ocel.events` (deduplicated by `ocel:eid`), never on flattened logs.
5. **Ambiguous payment allocation**: Linking `M1` (100 MU) and `M2` (150 MU) directly to `O100` and `O200` without an explicit allocation rule creates false accounting semantics: neither the narrative nor the invoice specifies whether `M1` settled `O100`, `O200`, or a pro-rata split. Reporting order-level DSO or paid status from speculated links will mislead finance stakeholders. *Mitigation*: Keep `Record Payment` linked to `(Payment, Invoice)` and introduce allocation objects/attributes only when backed by an explicit remittance rule.
6. **Overly short Payment traces**: Flattening on `Payment` yields only length-1 traces (`M1`, `M2`), producing empty DFGs and degenerate log skeletons. Automated pipelines that flatten every object type blindly may crash on empty edge sets or falsely conclude that payment processing has no control-flow structure. *Mitigation*: Inspect trace-length distributions before flattening and analyze payments jointly with `Invoice` in OC-DFG / OC-PN views.
7. **Constructor and API version mismatch**: PM4Py 2.x versions differ in whether `OCEL(...)` accepts `o2o` in `__init__` and whether top-level helpers like `pm4py.discover_otg` and `pm4py.discover_etot` are exposed or live in internal submodules. Unisolated calls fail with `TypeError` or `AttributeError` across environments. *Mitigation*: Isolate constructor/discovery adapters in thin wrapper functions and pin or assert the expected `pm4py.__version__`.
8. **False total order for same-time events**: Although this dataset has strictly distinct minute-level timestamps, real enterprise extracts frequently contain timestamp ties (e.g., batch jobs, same-second commits, or date-only fields). Sorting by `ocel:timestamp` then falls back to arbitrary row or `ocel:eid` order, fabricating deterministic directly-follows edges and spurious `always_before` / `always_after` log-skeleton rules. *Mitigation*: Check for timestamp collisions per object before discovery, preserve partial-order semantics where available, and avoid interpreting tie-broken edges as causal precedence.
