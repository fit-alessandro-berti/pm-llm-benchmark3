## 1. Conformance semantics

To interpret deviations against an incomplete norm, we must distinguish between logical violations and modeling gaps. The following semantics apply:

*   **Forbidden behavior:** An observed relation explicitly marked `forbidden` in the norm. This is a closed-world constraint; presence implies noncompliance.
*   **Missing mandatory behavior:** A relation marked `mandatory` within its scope that is absent in the observation. However, absence may stem from abstraction mismatches (e.g., intervening unmodeled events) rather than process failure.
*   **Unexpected but unregulated behavior:** Relations observed but marked `unspecified` in the norm. Under open-world assumptions, these are permissible unless they conflict with other constraints.
*   **Typical-pattern absence:** A relation marked `typical` that is less frequent than expected. This indicates deviation from the happy path but allows for legitimate exceptions (e.g., write-offs).
*   **Likely data-quality error:** Observations that contradict physical or system logic (e.g., sensor data linked to financial objects) where the norm marks the relation as `forbidden` due to architectural rules.
*   **Abstraction mismatch:** Discrepancies arising because the norm specifies a direct relation (e.g., `A -> B`) while the process allows intermediate steps (`A -> C -> B`), causing the direct edge to appear missing in a directly-follows summary.
*   **Insufficient evidence:** Cases where counts are too low or context too ambiguous to determine compliance without further trace-level inspection.

**Open-world vs. Closed-world:** The norm is closed-world only for `forbidden` relations and `mandatory` columns within stated scopes. Any relation not explicitly forbidden is permissible (open-world), even if `unspecified`. Therefore, observing an `unspecified` relation (e.g., `Order -> RiskCase`) is not a violation, whereas observing a `forbidden` relation (e.g., `Cancel -> Dispatch`) is a critical violation regardless of frequency.

## 3. Detailed reasoning by model family

### OC-DFG
The Object-Centric Directly-Follows Graph (OC-DFG) captures temporal precedence between activities on specific objects. Its primary limitation in this context is the **directly-follows abstraction**. Norm N1 (`Create Order -> Validate Order`) is mandatory, yet 2 of 100 orders lack this direct edge. The additional context suggests an unrecorded review event may exist between creation and validation. If the norm intends "eventually follows," this is compliant; if it strictly requires direct succession, it is a violation. Interpreting this as a violation without trace-level inspection risks false positives due to abstraction mismatch. Conversely, N3 (`Cancel Order -> Dispatch Package`) is forbidden. The observation of 2 instances is a hard violation regardless of intervening events, as the causal dependency implies shipping after cancellation.

### OTG
The Object Touching Graph (OTG) records structural relationships between object types. Norm T6 (`Order object_cobirth Payment`) is forbidden. The single observed instance suggests a systemic integrity issue where an order and payment are instantiated in the same transaction, violating segregation of duties or system design. This is a closed-world violation. However, the observation of `object_codeath` (co-death) between Package and Delivery is unspecified. Since the norm is open-world for unspecified relations, this is not a violation but indicates a synchronization point in the lifecycle that could be formalized. The count mismatch in `Add Item` (1450 Items vs 1448 Orders) suggests data quality issues in the interaction logging rather than process noncompliance.

### ET–OT
The Event-Type to Object-Type (ET-OT) mapping validates that events affect the expected objects. E10 (`Sensor Heartbeat -> Invoice`) is forbidden. The context confirms this is likely a data-quality error caused by a join on a reused numeric identifier. This highlights the danger of treating model output as ground truth; the conformance tool flags a violation, but human context reclassifies it as an ETL error. E8 mandates `Record Payment -> Invoice` except for unapplied cash. One payment lacks an invoice link. Since the event is not typed as unapplied cash, this is technically a deviation, but finance staff confirm the behavior is legitimate. This indicates a gap in data labeling (missing attribute) rather than process noncompliance.

**Abstraction Danger:** A critical risk is interpreting an "eventually expected" business rule (e.g., "Orders must be validated") as a directly-follows rule. If the norm implies eventually but the conformance check expects directly, valid processes with intermediate steps (like `Create -> Review -> Validate`) will be flagged as non-compliant. The 2 missing N1 relations exemplify this; they may be compliant under an eventual semantics but non-compliant under direct semantics.
