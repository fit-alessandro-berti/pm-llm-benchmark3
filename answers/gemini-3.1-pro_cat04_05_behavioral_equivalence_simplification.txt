# 1. Equivalence Notions

- **Visible trace equivalence after hiding `tau`**: Two models are equivalent if their sets of complete traces (from initial to final marking) are identical after removing all silent (`tau`) transitions. Duplicate visible labels are distinguished only by their label string and occurrence position in the trace sequence, not by transition identity.
- **Bounded visible-language equivalence under P3**: Two models are equivalent if their sets of complete visible traces are identical when the state space is restricted to traces containing at most 12 visible events and at most 3 occurrences of 'Analyze Revision'.
- **Business-relevant equivalence under P1**: Two models are equivalent if they enforce the same operational compliance rules: every 'Analyze Revision' must be paired with exactly one 'Check Revision' within the same iteration (before 'Rework Case' or 'Close Case'), 'Rework Case' strictly separates analysis attempts, and 'Approve Revision' is optional per iteration.
- **Abstracted dashboard equivalence under P2**: Two models are equivalent if they produce the same set of abstracted traces. An abstracted trace is a projection that records: 'Open Case' as first, 'Close Case' as last, the exact count of 'Analyze Revision' occurrences, a Boolean flag for whether 'Rework Case' occurred, and a Boolean flag for whether 'Check Revision' occurred. Silent events and 'Approve Revision' are hidden, and exact interleaving is ignored.

# 2. Structural Comparison

| Feature | Model A | Model B | Semantic consequence |
|---------|---------|---------|----------------------|
| Loop scope | Contains Analyze, Check, and Approve | Contains Analyze and Approve | In A, Check is repeated with every loop iteration. In B, Check is outside the loop and executes exactly once. |
| Minimum and maximum Check Revision occurrences | Min: 1, Max: unbounded (1 per iteration) | Min: 1, Max: 1 | A scales Check occurrences with the number of reworks. B strictly limits Check to a single occurrence. |
| Possible placement of Check Revision | Concurrent with Analyze within each iteration | Concurrent with the entire revision loop | In A, Check must complete before Rework or Close. In B, Check can execute at any point between Open and Close. |
| Optional approval occurrences | Inside the loop, after Analyze/Check | Inside the loop, after Analyze | In both models, Approve is optional per iteration. In A it follows the Analyze/Check parallel block; in B it follows Analyze. |
| Concurrency | Analyze and Check are concurrent per iteration | Check is concurrent with the entire loop | B allows Check to interleave with Rework or multiple Analyze events, whereas A synchronizes them per iteration. |
| Join before Close Case | Loop must terminate | Parallel block (Loop and Check) must terminate | Both models ensure all spawned concurrent branches and loops complete before the case is closed. |

**Explanation of optional Approve Revision and hidden `tau`:**
The optional 'Approve Revision' (modeled as an XOR with a hidden `tau` transition) doubles the number of possible traces per loop iteration, as each iteration can either emit the approval label or skip it silently. Because `tau` is hidden, skipping approval simply omits the label from the visible trace without breaking the sequence. This does not change the fundamental non-equivalence regarding 'Check Revision' counts, but it significantly increases the state space for bounded exploration and the number of visible traces.

# 5. Bounded Comparison Code

```python
import pm4py
from pm4py.objects.petri_net.semantics import get_enabled_transitions, execute

def get_bounded_visible_traces(net, im, fm, max_visible=12, max_analyze=3):
    """
    Performs an exhaustive breadth-first exploration of the state space up to the specified bounds.
    This is an exhaustive bounded exploration, not a random or heuristic playout.
    """
    # Queue stores tuples of (marking, visible_trace, analyze_count)
    queue = [(im, (), 0)]
    visited = set()
    completed_traces = set()
    
    while queue:
        marking, trace, analyze_count = queue.pop(0)
        
        # State representation for visited check
        state = (marking, trace)
        if state in visited:
            continue
        visited.add(state)
        
        if marking == fm:
            completed_traces.add(trace)
            continue
            
        enabled_transitions = get_enabled_transitions(net, marking)
        for t in enabled_transitions:
            next_marking = execute(t, net, marking)
            
            if t.label is None or t.label == 'tau':
                # Silent transitions do not increase visible length or analyze count
                queue.append((next_marking, trace, analyze_count))
            else:
                next_trace = trace + (t.label,)
                next_analyze = analyze_count + (1 if t.label == 'Analyze Revision' else 0)
                
                # Apply P3 bounds
                if len(next_trace) <= max_visible and next_analyze <= max_analyze:
                    queue.append((next_marking, next_trace, next_analyze))
                    
    return completed_traces

def compare_models():
    tree_a_str = "->('Open Case', *(->(+('Analyze Revision', 'Check Revision'), X('Approve Revision', tau)), 'Rework Case'), 'Close Case')"
    tree_b_str = "->('Open Case', +('Check Revision', *(->('Analyze Revision', X('Approve Revision', tau)), 'Rework Case')), 'Close Case')"
    
    # 1. Parse process trees
    tree_a = pm4py.parse_process_tree(tree_a_str)
    tree_b = pm4py.parse_process_tree(tree_b_str)
    
    # 2. Convert to accepting Petri nets
    net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
    net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)
    
    # 3. Check soundness
    print("Checking soundness...")
    pm4py.check_soundness(net_a, im_a, fm_a, print_diagnostics=True)
    pm4py.check_soundness(net_b, im_b, fm_b, print_diagnostics=True)
    
    # 4 & 5. Derive and compare visible trace sets under P3 bound
    print("Performing exhaustive bounded exploration...")
    traces_a = get_bounded_visible_traces(net_a, im_a, fm_a)
    traces_b = get_bounded_visible_traces(net_b, im_b, fm_b)
    
    unique_to_a = traces_a - traces_b
    unique_to_b = traces_b - traces_a
    
    # 6. Print traces unique to each model
    print(f"Traces unique to Model A (sample): {list(unique_to_a)[:3]}")
    print(f"Traces unique to Model B (sample): {list(unique_to_b)[:3]}")
    
    # 7. Distinction is stated in the docstring and implementation (BFS vs random playout)

if __name__ == '__main__':
    compare_models()
```

# 6. Stochastic and Footprint Comparison

- **`pm4py.discover_footprints(...)`**: Footprints extract binary relations (directly-follows, eventually-follows, parallel, etc.) between visible activities. Since Model A and B have different concurrency structures, their footprints will differ. For instance, in Model B, 'Check Revision' can be followed by 'Rework Case', while in Model A it cannot. However, equal footprints would still not establish trace equivalence because footprints only capture local binary relations and ignore loop bounds, exact occurrence counts, and long-range dependencies.
- **`pm4py.get_stochastic_language(...)`**: This computes or samples the probability distribution of traces. If we assign execution probabilities to the XOR choices and loop exits, we can generate a stochastic language. This adds evidence by showing which traces are most frequent, highlighting practical differences in expected behavior.
- **`pm4py.compute_emd(...)`**: The Earth Mover's Distance quantifies the difference between two stochastic languages. A high EMD would provide quantitative evidence of behavioral divergence. However, a low EMD would not establish trace equivalence because EMD can be small if differing traces have very low probability, and it is often an approximation when based on sampling.

# 7. Complexity Comparison

**Model A**:
- **Process-tree node count**: 12 nodes (1 root `->`, 1 `*`, 1 `->`, 1 `+`, 1 `X`, 6 visible leaves, 1 silent leaf).
- **Depth**: 5 (root -> loop -> sequence -> parallel/XOR -> leaves).
- **Number of visible and silent leaves**: 6 visible leaves, 1 silent leaf (`tau`).
- **Duplicate-label count**: 0 (each label appears exactly once).

**Model B**:
- **Process-tree node count**: 12 nodes (1 root `->`, 1 `+`, 1 `*`, 1 `->`, 1 `X`, 6 visible leaves, 1 silent leaf).
- **Depth**: 6 (root -> parallel -> loop -> sequence -> XOR -> leaves).
- **Number of visible and silent leaves**: 6 visible leaves, 1 silent leaf (`tau`).
- **Duplicate-label count**: 0.

**Converted-Petri-net simplicity**:
```python
simplicity_a = pm4py.simplicity_petri_net(net_a, im_a, fm_a)
simplicity_b = pm4py.simplicity_petri_net(net_b, im_b, fm_b)
```
Model A requires silent transitions to manage the parallel block inside the loop, while Model B requires silent transitions to manage the parallel block outside the loop. Their Petri net simplicity scores will be similar, but Model B's depth is slightly higher due to nesting the loop inside the parallel block.

# 8. Simplified Model

**Target Semantics**: P1 (Operational compliance view).
We can simplify Model A by replacing the parallel execution of 'Analyze Revision' and 'Check Revision' with a strict sequence. This removes the `+` operator, reducing the node count to 11 and eliminating the silent transitions required for parallel splits/joins in the Petri net, while fully preserving the P1 compliance rules.

1. **Compact process-tree expression**:
`->('Open Case', *(->('Analyze Revision', 'Check Revision', X('Approve Revision', tau)), 'Rework Case'), 'Close Case')`

2. **Self-contained PM4Py code**:
```python
import pm4py
simplified_model_str = "->('Open Case', *(->('Analyze Revision', 'Check Revision', X('Approve Revision', tau)), 'Rework Case'), 'Close Case')"
simplified_model = pm4py.parse_process_tree(simplified_model_str)
```

3. **Preservation table**:
| Property | Status | Explanation |
|----------|--------|-------------|
| 1:1 Check per Analyze | Exact | The sequence guarantees exactly one Check per Analyze. |
| Check before Rework/Close | Exact | Check is strictly ordered before the loop exits or reworks. |
| Optional Approve | Exact | XOR with `tau` is preserved. |
| Concurrency of Analyze/Check | Weakened | Concurrency is replaced by a strict sequence, which satisfies P1 but restricts interleaving. |

4. **Traces**:
- **Regression traces** (accepted by Simplified Model and Model A):
  1. Open Case, Analyze Revision, Check Revision, Close Case
  2. Open Case, Analyze Revision, Check Revision, Approve Revision, Close Case
  3. Open Case, Analyze Revision, Check Revision, Rework Case, Analyze Revision, Check Revision, Close Case
- **Negative traces** (rejected by Simplified Model, violating P1):
  1. Open Case, Analyze Revision, Close Case (Missing Check Revision)
  2. Open Case, Analyze Revision, Check Revision, Rework Case, Analyze Revision, Close Case (Missing second Check Revision)

# 9. Final Recommendation

- **For P1 (Operational view)**: Model A is suitable because it correctly enforces the 1:1 relationship between Analyze and Check per revision cycle. Model B fails this completely.
- **For P2 (Dashboard view)**: Model B is suitable because it guarantees at least one Check occurs concurrently with the process, abstracting away the exact count and interleaving, which perfectly matches the dashboard's Boolean requirement. Model A is also equivalent under P2 abstraction, but Model B structurally represents the "once per case" nature of the dashboard view better.
- **Replacement**: The simplified model should replace Model A for P1. It enforces all operational compliance rules while reducing structural complexity by eliminating unnecessary concurrency between Analyze and Check.
- **Warning**: Bounded comparison only explores behavior up to a fixed depth (e.g., 12 events). While it provides strong evidence for non-equivalence by finding counterexamples, it cannot mathematically prove unbounded equivalence because subtle behavioral differences might only manifest in longer traces (e.g., after many reworks).
