Event-time compliance checking for transaction-review rules R1-R4 over a changing-state event log.

Key ideas
---------
* Blank attribute cells mean "no update at this event": state is reconstructed by
  per-case forward-fill (last observation carried forward) in (timestamp, event_index) order.
  Nothing is copied backward; post-release events (e.g. Settlement_Confirmed, Record_Exemption)
  never change release-time state, though they can be *evidence* about earlier facts.
* Every obligation is evaluated with the state as known at the Release_Funds event.
* Exemptions are evaluated with R5 evidence logic: a displayed backdated field alone is not
  proof; trusted signature evidence that predates the trigger is.
* Cases the data cannot decide (e.g. TX-305) are labelled REVIEW_REQUIRED, not silently passed.
* A coarse trace-order (DECLARE-style) check is compared against the data-aware result to show
  why control-flow conformance alone cannot represent conditional, data-dependent obligations.

```python
def evaluate_exemption(ex_id, trig_ts, jur, cust, amt):
    """R5: a late DB record may evidence an earlier approval, but a displayed
    backdated field alone is not conclusive. Trusted evidence (qualified
    signature, valid hash) must predate the obligation trigger."""
    if not ex_id:
        return None, []
    row = EXEMPTIONS.loc[EXEMPTIONS["exemption_id"] == ex_id]
    if row.empty:
        return False, ["exemption unknown to register"]
    row = row.iloc[0]
    reasons, ok = [], True
    if row["approved_by"] != "Head_Compliance":
        ok = False; reasons.append("approver is not Head_Compliance")
    if row["effective_from"] > trig_ts:
        ok = False; reasons.append("effective_from after trigger")
    if trig_ts >= row["expires"]:
        ok = False; reasons.append("expired at trigger")
    if pd.notna(jur) and jur != row["scope_jurisdiction"]:
        ok = False; reasons.append(f"jurisdiction scope mismatch ({jur})")
    if pd.notna(cust) and cust != row["scope_customer"]:
        ok = False; reasons.append("customer-type scope mismatch")
    if pd.notna(amt) and amt > row["scope_max_amount"]:
        ok = False; reasons.append("amount above exemption scope")
    if pd.isna(row["trusted_evidence_ts"]) or (not row["trusted_evidence_hash_valid"]) \
            or row["trusted_evidence_ts"] > trig_ts:
        ok = False
        reasons.append("no trusted pre-trigger approval evidence "
                       "(displayed backdating alone is insufficient)")
    if row["witness_independent"] is False:
        reasons.append("witness not independent; given no weight")
    return ok, reasons
```

## 1. Temporal Data Semantics

**Ordering key.** Every event is positioned by the lexicographic pair `(time:timestamp, event_index)`. For events sharing a timestamp, `event_index` is the tie-breaker: an event with a smaller index is strictly *before* one with a larger index. This makes ordering total and state reconstruction deterministic.

**Blank cells.** A blank attribute cell means "no update at this event," never "set to null." State is rebuilt per case by forward-fill (last observation carried forward) over the non-blank cells in `(timestamp, event_index)` order. The state *at* an event includes that event's own writes; an event sees all writes of strictly earlier events plus its own. A write at `(t, k)` is **invisible** to events at `(t, k)` for `k < k` and visible to `(t, k)` for `k > k`. Consequence for TX-311: the `Update_Jurisdiction  DE` write at `(16:20, #4)` is *not* seen by the `Enhanced_Review` at `(16:20, #3)`; the review was performed on the US/€115,000 state, and the release at 16:30 sees DE.

**Missing  blank.** If an attribute has never been written in a case up to an event (e.g., TX-305's amount), the value at that event is UNKNOWN (), not zero, not low-risk, not the final value. Per R6, UNKNOWN never defaults to a low-risk value.

**Material changes.** R4 defines amount materiality: an increase of more than 20% over the last *known* amount invalidates the latest Standard/Enhanced review for amount-dependent obligations. A decrease never invalidates. An increase from an unknown prior amount is unclassifiable. For non-amount dimensions, any post-creation write to jurisdiction (R1-relevant) or risk/customer type (R2-relevant) is treated as material for that rule's trigger. The effective time of a change defaults to the change event's timestamp; no evidence in this log establishes a different effective time.

**Final attributes are never copied backward.** Every obligation is evaluated with the state known at its trigger event (here, `Release_Funds`). Post-release events (`Settlement_Confirmed` on 04-07, `Record_Exemption` at 11:00) cannot change release-time state; they can only be *evidence* about earlier facts, weighted by reliability.

**Four distinct clocks.**
- *Event time*: the timestamp on the log row (when the activity happened).
- *Effective time*: when a value begins to govern state. Default = event time of the write. Exemptions assert an effective time (`effective_from`), which is a claim requiring corroboration.
- *Record time*: when a record entered the system (e.g., `Record_Exemption` at 11:00 after an outage). Late record time does not defeat an obligation-relevant fact if the evidence chain explains it (EX-77); it is not itself proof either.
- *Evidence time*: when a piece of evidence was created (qualified signature 09:05 for EX-77; signing-certificate creation 10:30 for EX-88). Evidence time, not displayed time, decides whether an approval existed at the relevant moment. A displayed backdated field is an assertion, not evidence; an interested witness's assertion is weak evidence.

## 4. Ambiguities and Alternative Readings

**TX-305 (the INDETERMINATE case).** What would resolve it: (i) an immutable release payload — if the amount were < €100,000, the case is COMPLIANT (no R1 trigger; MEDIUM/CORPORATE means no R2; no sanctions events); if  €100,000, the question becomes whether ER 11:15 discharges R1 — a formalist reading says yes (a review exists, no material change after it), a substantive reading says a review that could not see the amount cannot discharge an amount-threshold obligation, and the later-known €150,000 is an "increase from an unknown amount" that R4 declares unclassifiable. (ii) A feed-outage ticket stating what ops knew between 11:00–11:30. (iii) The review document containing the amount. Interpretive fork: whether the settlement amount may be projected backward — I hold it cannot (no immutable payload; "may equal release amount" is not evidence of release-time state), but a supervisor applying a balance-of-probabilities standard could treat €150k as establishing the trigger, after which the formalist/substantive fork above decides the outcome.
