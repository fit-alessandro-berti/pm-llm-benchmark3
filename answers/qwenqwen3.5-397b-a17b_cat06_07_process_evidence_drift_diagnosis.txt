## 2. Competing explanations and timeline

**January – March (Baseline Stability):**
The system operates within expected parameters. Breach rates hover around 18-19%, AUROC is stable (~0.81), and data quality metrics (unknown activity, missing features) are negligible. This period establishes the ground truth for "normal" operations and model performance.

**April (Pipeline Incident):**
The sharp deterioration in April (AUROC 0.67, Unknown Activity 17%) is **not** process drift. It is a data-pipeline failure caused by the workflow migration renaming `Initial Diagnosis Completed`. The model received malformed inputs (UNKNOWN_ACTIVITY) and missing queue features, causing risk scores to spike artificially (0.28) without a corresponding rise in observed breaches (0.19). Treating this as concept drift would be a critical error; the process did not change, the visibility did.

**May (Residual Pipeline Noise):**
While the mapping patch deployed on 6 May reduced unknown activity to 2%, derived features (cached "number of events") were not fully backfilled. ECE remains elevated (0.050 vs 0.025 baseline). This is a continuation of the April incident, not a new process change.

**June (Policy-Driven Covariate Drift):**
The remote-routing policy increased V2 usage from 35% to 52%. This is **covariate drift** (change in input mix). However, because V2 has a low breach rate (0.09) and the model predicts it well, overall breach rates dropped (0.15) and AUROC remained stable (0.79). This is a "good" drift that requires monitoring but not necessarily model retraining, provided calibration is adjusted for the new mix.

**July – August (Supplier-Driven Concept Drift):**
The parts supplier failure introduced **concept drift**. The process variant V3 remained, but the semantic meaning of the `Order Part -> Part Received` edge changed (median time 42h  130h). The model, trained on historical 30-40h lead times, failed to predict breaches for V3 cases (Breach rate 0.35  0.64). This is a genuine performance degradation requiring feature updates (lead-time indicators) and retraining.

**September (Population Shift + Concept Drift):**
Partner Z onboarding introduced a **population shift** (24% of cases, rural, older devices) overlapping with the ongoing supplier concept drift. Partner Z cases have higher breach rates (0.45) and utilize V3 more heavily. The deterioration here is compound: the model lacks features to explain Partner Z risk (population), and V3 performance is still degraded (concept).

**October (Label Censoring):**
October metrics are **confounded by label delay**. With only 55% label maturity and a backlog in the outcome API, the observed breach rate (0.16) is artificially low compared to the predicted risk (0.23). Calculating AUROC on this cohort is invalid. This period must be excluded from performance evaluation until labels mature.

## 5. Monitoring architecture

**Architecture Overview:**
The monitoring system is layered to prevent false positives from triggering unnecessary retraining.
1.  **Data Quality Layer:** Checks schema, nulls, and unknown activities. *Dependency:* Blocks downstream metrics if quality < 95%.
2.  **Label Maturity Layer:** Tracks cohort completeness over time. *Dependency:* Suppresses Performance/Drift alerts if maturity < 80% for the evaluation window.
3.  **Process Evidence Layer:** Monitors DFG edge durations and variant mixes. *Dependency:* Triggers "Process Drift" alerts independent of model performance.
4.  **Predictive Performance Layer:** AUROC, Brier, ECE. *Dependency:* Only activates if Data Quality and Label Maturity checks pass.
5.  **Intervention Monitor:** Tracks deployment status and manual overrides.

**Alert Dependencies:**
*   `IF` Data Quality (Unknown Activity) > 5% `THEN` Trigger "Pipeline Alert" `AND` Suppress "Model Drift Alert".
*   `IF` Label Maturity < 80% `THEN` Suppress "Performance Degradation Alert".
*   `IF` Process DFG Edge Time > 2 `THEN` Trigger "Concept Drift Warning" (even if Model AUROC is stable).

**Process-Evidence Extraction Code:**

```python
import pandas as pd
import pm4py

def extract_monthly_evidence(file_path, month_start, month_end):
    # 1. Read and Format
    df = pd.read_csv(file_path, parse_dates=['time:timestamp'])
    # Ensure standard PM4Py column names
    df = df.rename(columns={'case_id': 'case:concept:name', 'activity': 'concept:name'})
    
    # 2. Normalize Renamed Diagnosis Activity (Pipeline Fix)
    # Maps 'Diagnostic Assessment Completed' back to baseline schema
    df['concept:name'] = df['concept:name'].replace(
        {'Diagnostic Assessment Completed': 'Initial Diagnosis Completed'}
    )
    
    # 3. Duplicate Handling Strategy
    # Keep the first occurrence of an activity per case within a 1-minute window
    df = df.sort_values(['case:concept:name', 'time:timestamp'])
    df['prev_time'] = df.groupby('case:concept:name')['time:timestamp'].shift(1)
    df['prev_activity'] = df.groupby('case:concept:name')['concept:name'].shift(1)
    time_diff = df['time:timestamp'] - df['prev_time']
    # Remove exact duplicates or near-duplicates same activity
    mask = ~((df['concept:name'] == df['prev_activity']) & (time_diff.dt.total_seconds() < 60))
    df = df[mask].drop(columns=['prev_time', 'prev_activity'])

    # 4. Filter Time Range (Event-Calendar vs Case-Start Cohorts)
    # Event-Calendar: All events occurring in the month
    df_events = pm4py.filter_time_range(df, start_time=month_start, end_time=month_end, mode='events')
    
    # Case-Start Cohort: Cases that started in the month (for outcome maturity tracking)
    # Identify start events first
    starts = df[df['concept:name'] == 'Case Created']
    case_starts = starts[starts['time:timestamp'].between(month_start, month_end)]['case:concept:name'].unique()
    df_cases = df[df['case:concept:name'].isin(case_starts)]

    # 5. Extract Process Evidence
    # Discover DFG for the month
    dfg = pm4py.discover_dfg(df_events)
    
    # Discover Performance DFG (median times on edges)
    perf_dfg = pm4py.discover_performance_dfg(df_events, measure='median')
    
    # Get Variant Distribution
    variants = pm4py.get_variants(df_cases)
    total_cases = len(df_cases['case:concept:name'].unique())
    variant_dist = {k: len(v)/total_cases for k, v in variants.items()}
    
    # 6. Extract Temporal Features (for pipeline audit)
    # Example: Time from Diagnosis to Dispatch
    temporal_features = pm4py.extract_temporal_features_dataframe(
        df_cases, 
        activity_start='Initial Diagnosis Completed', 
        activity_end='Dispatch Technician'
    )
    
    # 7. Return Auditable Summary
    return {
        'period': f"{month_start} to {month_end}",
        'case_count': total_cases,
        'variant_distribution': variant_dist,
        'critical_edge_median_hours': perf_dfg[('Order Part', 'Part Received')]['median'] / 3600 if ('Order Part', 'Part Received') in perf_dfg.index else None,
        'avg_diagnosis_to_dispatch_hours': temporal_features['duration'].mean() / 3600 if not temporal_features.empty else None,
        'dfg_edge_count': len(dfg)
    }
```

## 6. Risks of acting on the wrong diagnosis

1.  **Retraining on Immature Labels (October Risk):**
    *   *Failure:* Retraining the model using October data where 45% of breach labels are missing. The model will learn that recent cases are "non-breaches," biasing it towards under-prediction.
    *   *Mitigation:* Enforce a minimum label maturity threshold (e.g., 90%) for any data included in the training set. Use survival analysis for censored data if recent training is urgent.

2.  **Calibrating Around a Pipeline Bug (April Risk):**
    *   *Failure:* Applying Platt scaling to correct the April risk spike (0.28) without fixing the underlying `UNKNOWN_ACTIVITY` feature issue. The model remains blind to the diagnosis event, merely masking the symptom.
    *   *Mitigation:* Data quality gates must pass before calibration is allowed. If "Unknown Activity" > 5%, trigger a pipeline incident ticket, not a model tuning task.

3.  **Ignoring Genuine Supplier-Driven Concept Drift (August Risk):**
    *   *Failure:* Attributing the August breach spike solely to random noise or label delay, failing to update the model with supplier lead-time features. The model continues to underestimate V3 risk.
    *   *Mitigation:* Monitor process performance DFGs independently of model metrics. If `Order Part -> Part Received` time exceeds control limits, force a feature review regardless of AUROC.

4.  **Attributing Partner Z Shift to Unfair Model Behavior (September Risk):**
    *   *Failure:* Assuming the higher breach rate for Partner Z is model bias rather than a population shift (rural/device age) and removing valid predictive signals to "equalize" outcomes.
    *   *Mitigation:* Perform stratified calibration checks. If the model is well-calibrated within the Partner Z segment (predicted risk matches observed breach), the disparity is due to input risk factors, not model bias. Add missing context features rather than suppressing existing ones.
