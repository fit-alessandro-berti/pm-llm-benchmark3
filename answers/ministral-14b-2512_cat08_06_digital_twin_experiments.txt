# Simulation-Based Digital Twin for Building-Permit Process

## 1. Model Scope and State Variables

### **Digital Twin Boundary**
- **Scope**: End-to-end building-permit process from application submission to permit issuance/rejection.
- **Exclusions**: Post-permit construction oversight, external regulatory bodies (beyond municipal control), and applicant financial transactions.
- **Time Horizon**: 18-month simulation window (matching event-log period) with rolling validation against real-time data feeds.

### **Entities and State Variables**
| **Entity**               | **State Variables**                                                                 |
|--------------------------|------------------------------------------------------------------------------------|
| **Case**                 | `case_id`, `case_type`, `status`, `current_activity`, `next_activity`, `rework_count`, `objection_flag`, `architect_id`, `district`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, `related_cases` (list of linked case IDs), `submission_time`, `completion_time`, `decision` (permit/reject) |

| **District**             | `district_id`, `inspection_travel_time`, `environmental_sensitivity`, `public_notice_objection_rate` |
| **Calendar**             | `holidays`, `council_meeting_weeks`, `resource_specific_availability` (e.g., fire reviewers Tue-Thu) |

## 2. Parameter-Estimation Plan

### **Arrival Process**
- **Non-stationary Demand**:
  - Use **PM4Py’s `discover_arrival_distribution`** to fit a seasonal Poisson process with:
    - Monthly seasonality (1.7x rate in Mar-May/Sep-Nov).
    - Weekly seasonality (Mon submissions 2.2x Wed).
    - Architect bursts: Model top 20 architects as **Markov-modulated Poisson** (bursty arrivals).

    ```
- **Case Mix**: Directly use event-log summary (45% Simple, 28% New residential, etc.).

### **Service Times**
- **Human Activities**:
  - Fit **log-normal or Weibull distributions** to empirical medians/p90s (e.g., Planning review: median 3.5h, p90 14h).
  - Use **PM4Py’s `discover_performance_schema`** to extract service-time distributions per activity/resource.
  - **Missing start timestamps**: Assume service time = (completion - start) if start exists; otherwise, use **empirical waiting-time distributions** to infer service time.
- **System Activities** (e.g., Issue permit): Exponential with mean = empirical median.
- **Applicant/Third-Party Responses**:
  - `Receive missing documents`: Heavy-tailed (Weibull with shape < 1) with median 5d.
  - `Public-notice objections`: Latent variable; model as a Bernoulli trial with `p = 0.15` for Complex variance cases.

### **Waiting Times**
- **Queueing Delays**:
  - Use **PM4Py’s `discover_waiting_times`** to fit distributions per activity.
  - For activities with missing start times, assume waiting time = (start of next activity - completion of current activity).
- **Resource Calendars**:
  - Encode as **PM4Py-compatible calendars** (e.g., `pm4py.objects.log.util.xml_parser.apply` for XES logs).
  - Example: Fire reviewers only available Tue-Thu:

        "Mon": [], "Fri": [], "Sat": [], "Sun": []
    }
    ```

### **Routing Probabilities**
- **Branching Rules**:
  - Use **PM4Py’s `discover_process_tree`** to extract empirical probabilities (e.g., 26% of cases take the "Simple clean path").
  - Override with domain rules (e.g., `requires_fire=yes`  Fire-safety review).
- **Rework**:
  - Model as **Markov chains** with transition probabilities from the log (e.g., 9% of cases have inspection rework).
  - Rework triggers: Random (empirical) or based on latent variables (e.g., `objection_flag`).

### **Dependencies**
- **Related Cases**:
  - Cluster cases by `(architect_id, district)`; model inspection batching as a **priority queue** where cases in the same batch reduce travel time but increase waiting for the first case.
- **Objections**:
  - Proxy with `public_notice_duration`: If `duration > 30d`, assume `objection_flag=True` with probability `p = 0.7`.

## 3. Assumptions

### **Arrivals**
- **Non-stationary**: Seasonal Poisson with weekly/monthly patterns; top 20 architects modeled as bursty arrivals.
- **Missing Data**: Unobserved cases are assumed to follow the same distribution as observed cases (no selection bias).
- **Policy Impact**: Interventions like D7 (appointment slots) will reduce Monday bursts but may shift demand to other days.

### **Service Times**
- **Human Activities**: Log-normal distributions fit to medians/p90s; missing start times inferred from waiting times.
- **System Activities**: Exponential with mean = empirical median.
- **Applicant Responses**: Heavy-tailed (Weibull) for `Receive missing documents`; objections modeled as latent.

### **Routing**
- **Branching**: Empirical probabilities from PM4Py, overridden by domain rules (e.g., `requires_fire`).
- **Rework**: Markovian with empirical transition rates; rework triggers are stochastic or latent (e.g., objections).
- **Dependencies**: Related cases batched by `(architect_id, district)`; inspection travel time depends on district.

### **Resources/Calendars**
- **FTEs**: Fixed as per event-log summary; temporary resources (e.g., D4) added as interventions.
- **Calendars**: Strict adherence to HR data (e.g., fire reviewers Tue-Thu only).
- **Queue Priorities**: Aging cases get priority in D6; objections extend `public_notice`.

### **Rework**
- **Triggers**: Empirical (9% inspection rework) or latent (objections  rework).
- **Delays**: Rework adds 20-50% to median duration (from variant analysis).

### **Applicant/Third-Party Response**
- **Missing Docs**: Applicant-driven; modeled as heavy-tailed with median 5d.
- **Objections**: Latent variable; proxy with `public_notice_duration > 30d`.

### **Cross-Case Dependencies**
- **Architect Bursts**: Top 20 architects submit 31% of cases; modeled as correlated arrivals.
- **District Batching**: Inspections in D3/D5 have +20% travel time; batching reduces per-case travel but increases queueing.
- **Policy Dependencies**: D2 (no-inspection rule) applies only to `Simple renovation` with `application_value < 50k`.

### **Non-Stationary Demand**
- **Seasonality**: 1.7x rate in peak months; 2.2x Monday submissions.
- **Resource Calendars**: Holidays and council meetings reduce capacity (e.g., Legal check).

### **Missing Data**
- **Start Timestamps**: Service time inferred from waiting times; uncertainty quantified via sensitivity analysis.
- **Objection Events**: Modeled as latent; `public_notice_duration` used as proxy.
- **Rework Reasons**: Ignored; rework modeled as empirical probabilities.

## 5. Warm-up, Replications, and Uncertainty Treatment

### **Warm-up**
- **Approach**: Discard the first 3 months of simulation to eliminate initialization bias (queues fill to steady state).
- **Validation**: Check that key metrics (e.g., queue lengths, resource utilization) stabilize after warm-up.

### **Run Length**
- **Total Simulation**: 18 months (matching event-log period).
- **Replications**: 30 independent runs per experiment (sufficient for 95% CI with CV < 10%).
- **Random Seeds**: Fixed seeds for reproducibility; sensitivity to seeds tested via **Kruskal-Wallis test**.

### **Uncertainty Treatment**
- **Heavy-Tailed Durations**:
  - Use **Weibull distributions** for applicant responses and `public_notice` with shape < 1.
  - Validate via **quantile-quantile plots** against empirical data.
- **Parameter Uncertainty**:
  - **Bootstrapping**: Resample arrival/service-time distributions 100x to estimate CIs.
  - **Sensitivity Analysis**: Vary key parameters (e.g., objection rate ±20%) and measure impact on metrics.
- **Confidence Intervals**:
  - Report **95% CIs** for median durations, SLA compliance, and resource utilization.
  - Use **credible intervals** for Bayesian calibration (if priors are defined).

### **Handling Missing Data**
- **Start Timestamps**: Assume service time = (completion - start) if start exists; otherwise, use **empirical waiting-time distributions** to infer service time.
- **Objection Events**: Model as latent; proxy with `public_notice_duration > 30d` and `case_type = Complex variance`.

## 6. Validation Strategy

### **Face Validation**
- **Domain Expert Review**: Present process model and key metrics to municipal staff for plausibility checks.
- **Key Checks**:
  - Does the process tree match the nominal process?
  - Are resource calendars realistic (e.g., fire reviewers Tue-Thu only)?

### **Event-Log Replay Validation**
- **PM4Py Replay**: Simulate the event log and compare:
  - **Fitness**: % of log traces that can be replayed.
  - **Precision/Generalization**: Avoid overfitting to rare variants.
- **Metrics**:
  - Mean absolute error (MAE) in case durations.
  - Alignment score between simulated and real traces.

### **Distributional Validation**
- **Kolmogorov-Smirnov Test**: Compare empirical and simulated distributions for:
  - Case durations by variant.
  - Waiting times per activity.
  - Resource utilization.
- **Heavy-Tailed Validation**: Ensure simulated `public_notice` durations match empirical p90/p99.

### **Resource-Utilization Validation**
- **Queue Lengths**: Compare simulated vs. empirical queue lengths for each activity.
- **Utilization**: Ensure planners/inspectors are ~80% utilized (empirical target).

### **Bottleneck Validation**
- **Identify Bottlenecks**: Compare simulated bottlenecks (e.g., Planning review queue) with empirical data.
- **Intervention Impact**: Validate that D6 (aging-case priority) reduces backlog in the simulated bottleneck.

### **Out-of-Sample Validation**
- **Holdout Period**: Reserve the last 6 months of the event log for validation.
- **Metrics**:
  - Predictive accuracy of case durations.
  - Robustness to non-stationary demand (e.g., peak months).

### **Primary Metrics**

| **Fairness Across Districts**   | No district should have >1.5x median duration of others.                           | High       |
| **Fairness Across Architects**  | Top 20 architects should not have >1.2x median duration of others.                 | Medium     |
| **Backlog**                     | Reduce aging cases (>30d) by 30%.                                                  | High       |
| **Applicant Effort**            | Minimize additional burden (e.g., pre-submission checks in D1).                      | Medium     |

### **Secondary Metrics**
- **Queue Lengths**: Max queue length per activity (target < 50 cases).
- **Objection Handling**: Reduce `public_notice` duration for objection-prone cases.
- **Policy Robustness**: Interventions should perform well under stress scenarios (e.g., D10 under Stress 1).

### **Decision Rules**
1. **Pareto Frontier**: Plot interventions by (median duration reduction, rework rate) and select non-dominated solutions.
2. **Cost-Benefit**: Estimate implementation cost (e.g., D4 requires hiring a temporary inspector) vs. benefit.
3. **Robustness**: Prioritize interventions that perform well across stress scenarios.
4. **Fairness**: Reject interventions that worsen equity (e.g., D2 may disadvantage high-value Simple renovation cases).

    for exp_name, exp_results in results.items():
        df = pd.DataFrame(exp_results)
        # Median case duration
        case_durations = df.groupby("case_id")["end_time"].max() - df.groupby("case_id")["start_time"].min()
        metrics[f"{exp_name}_median_duration"] = case_durations.median()
        # p90 duration
        metrics[f"{exp_name}_p90_duration"] = case_durations.quantile(0.9)
        # Rework rate
        rework_cases = df[df["activity"].str.contains("rework")]
        metrics[f"{exp_name}_rework_rate"] = len(rework_cases) / len(df["case_id"].unique())
        # Resource utilization
        resource_utilization = df.groupby("resource")["end_time"].count() / (df["end_time"].max() / 3600 / 8)  # 8h workday
        metrics[f"{exp_name}_avg_utilization"] = resource_utilization.mean()
    return metrics
