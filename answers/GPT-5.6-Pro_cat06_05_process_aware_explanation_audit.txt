## 2. Process-model consistency checks

### Prediction-cut and label contract

Each model row should be anchored to the **first** `Coverage Check Completed` event using a stable event identifier. The cut should be represented as something like:

```text
(case_id, t0_event_id, t0_event_time, t0_sequence_index, scoring_time)
```

The prefix includes events that reliably precede the coverage event and the coverage event itself. It must not automatically include every event with `timestamp <= t0_event_time`, because an event ordered after coverage may share the same timestamp.

The target definition also needs a formal contract:

* Does the 10-day clock begin at `Claim Registered`?
* Does settlement mean the first decision, the final decision after an appeal, or closure?
* Are the ten days calendar days or business days?
* Does a withdrawal count as timely settlement, a competing outcome, or exclusion?
* When are labels mature enough to be used for training?

Without this contract, even a temporally valid slack feature can be interpreted incorrectly.

### Point-in-time availability and complete-trace tests

Maintain a feature manifest containing the source objects, aggregation window, valid time, system-availability time, mutability, refresh schedule, computation version, and source event identifiers. A feature is admissible only when both conditions hold:

```text
feature_valid_at <= t0
feature_known_at <= scoring_time
```

This dual-time rule prevents both event-time leakage and retrospective warehouse leakage.

The strongest automated test is **suffix invariance**:

1. Keep a case prefix through `t0` fixed.
2. Delete, replace, or permute every post-`t0` event.
3. Recompute the feature vector, score, and explanation.
4. Require them to remain identical.

`total_case_duration_hours`, `appeal_seen_anywhere`, total requests, final team, full-trace variant, final decision, and complete-trace sequence indicators will fail this test.

Static query checks should additionally flag:

* unbounded aggregations over a claim;
* joins to closure or final-outcome tables;
* “latest/current” values without an as-of predicate;
* joins using extraction date rather than `t0`;
* nearest-snapshot joins that can select a future snapshot;
* same-day aggregates without event-time filtering.

### Activity-order and prefix-state validation

A normative Petri net, BPMN model, process tree, or equivalent transition system can be used for prefix replay. After replaying:

```text
Claim Registered -> Coverage Check Completed
```

the validator should distinguish the following states:

| Activity or relation                           | Status immediately after coverage                                           |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| `Claim Registered`, `Coverage Check Completed` | Observed in the prefix                                                      |
| `Damage Assessment Completed`                  | Possible next branch for fast-track claims, but not yet observed            |
| `Documents Requested`                          | Possible next branch for evidence-dependent claims, but not yet observed    |
| `Documents Received`                           | Future-reachable only after a request; not currently enabled                |
| `Documents Validated`                          | Future-reachable only after receipt; not currently enabled                  |
| `Fraud Investigation Opened`                   | Conditionally future-possible after a trigger and may later run in parallel |
| First `Settlement Decision Recorded`           | Future-reachable only after required assessment work                        |
| `Appeal`                                       | Not enabled until a Partial or Deny decision                                |
| Second `Settlement Decision Recorded`          | Future-reachable only through a legitimate appeal path                      |
| `Claim Closed`                                 | Future-reachable after final decision or withdrawal; not enabled at `t0`    |
| `Claim Closed -> Damage Assessment Completed`  | Normatively infeasible as an ordered relation                               |

An explanation may say that an activity is a **possible future path** only when clearly presented as a model forecast or scenario. It must not present a future-reachable activity as something already observed.

Useful conformance mechanisms have different roles:

* **Prefix replay** determines the current process marking and which activities are currently enabled.
* **Alignments** find minimum-cost deviations between a full trace and the normative model. They can detect reversed order or missing prerequisites, but results depend on model completeness and alignment costs.
* **Footprint checks** provide a fast screen for ordering, parallelism, and exclusiveness. They lose context around loops and repeated labels and therefore cannot validate appeal semantics by themselves.
* **Declarative constraints** are well suited for rules such as “Appeal requires a previous Partial or Deny” and “Documents Received requires a previous Documents Requested.”
* **DFGs** describe observed direct succession. They do not establish normative permission, causality, or temporal availability. A frequent edge can be a logging convention, concurrency interleaving, or repeated data error.

In particular, a frequent `Claim Closed -> Damage Assessment Completed` DFG edge would not override the normative process.

### Same-timestamp ambiguity

Sequence construction should use a reliable sequence index only after checking that it is present, unique within a case where required, and generated according to the true business order. Ingestion order is not an acceptable substitute unless its semantics have been verified.

When timestamps tie and sequence information is missing:

1. Represent the events as a partial order or unordered equivalence class.
2. Do not emit a direct-succession feature between the tied events.
3. Evaluate feasible linearizations against the normative model.
4. Classify the case as **ambiguous** if at least one feasible normative ordering exists.
5. Classify it as a conformance violation only if no ordering can satisfy the process constraints.

For Case Z, the source does not support the assertion that closure preceded damage assessment. A plausible normative order within the tied timestamp could instead put assessment and decision before closure.

### Repeated settlement decisions

The coarse label may legitimately appear twice. Validation must use the decision-outcome attribute and surrounding context, not merely count duplicate activity labels.

A valid reconsideration fragment is:

```text
Settlement Decision Recorded [Partial or Deny]
-> Appeal
-> Settlement Decision Recorded [new decision]
```

The following should be flagged:

* Appeal after Approve or Withdrawn;
* a second decision without an intervening appeal, unless another documented reconsideration mechanism exists;
* Appeal before any decision;
* closure followed by a new assessment or decision without a documented reopening mechanism.

Thus, `Appeal -> Settlement Decision Recorded` is a valid later-process pattern. Its defect in the current explanation is **temporal leakage**, not process impossibility.

### Explanation-level conformance checks

Every local attribution should carry provenance to the exact source value or prefix events supporting it. The explanation validator should reject:

* an activity feature not present in the prefix;
* a resource or team field whose historical version is unavailable;
* a future-reachable event described in the past tense;
* a counterfactual path that is unreachable from the current process marking;
* a direct-succession relation manufactured from unresolved timestamp ties;
* a causal verb such as “caused” or “determines” when the evidence is only model attribution.

## 3. Alternative feature interpretations

Four different standards should be kept separate:

**Predictive validity** requires point-in-time availability, leakage-free construction, out-of-time performance, and acceptable calibration. A correlated feature can satisfy this standard.

**Causal interpretation** requires a defined intervention and an identification strategy addressing confounding and selection. SHAP-like importance alone does not satisfy it.

**Operational actionability** requires a modifiable, timely lever whose expected benefit exceeds its cost and spillovers. A valid predictor need not be actionable.

**Fairness acceptability** concerns subgroup errors, calibration, intervention allocation, disparate impact, legitimate business use, and proxy behavior. Predictive usefulness does not by itself establish acceptable use, but proxy status also does not automatically require deletion.

The direct suffix features—completed duration, realized appeal, final decision, total future requests, complete variant, complete-case role/team, and future sequence patterns—are rejected as current `t0` inputs before the following classification.

| Class                                          | Signals in admissible or repairable form                                                                                                                                                                                        | What may be claimed                                                                                                                                                                                                        | What may not be claimed                                                                                                                                                                                                        |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Defensible predictive signal**               | Frozen `initial_damage_complexity`; a genuinely event-time `initial_reserve`; potentially an as-of risk score after auditing its upstream lineage                                                                               | The value was available at `t0`, has a reproducible association with breach, and improves out-of-time prediction or calibration.                                                                                           | That the feature causes delay, that changing its recorded value changes the outcome, or that it identifies claimant fault.                                                                                                     |
| **Process-state or congestion signal**         | Backward-as-of `queue_length_at_t0`; `elapsed_since_registration_at_t0`; `team_at_t0`; `last_prefix_role`; document count genuinely available by `t0`; prefix waiting-time and state features                                   | The claim had a particular amount of consumed time or entered a particular operational state, and the model associates that state with risk. These can support prioritization hypotheses.                                  | That congestion caused the individual outcome, that moving the claim automatically prevents breach, or that an intervention has positive net effect without studying displaced work and capacity spillovers.                   |
| **Proxy requiring fairness/robustness review** | `claimant_region`; verified registration-time `claimant_channel`; repaired prior-claim count; potentially composite risk scores                                                                                                 | The feature is available and conditionally predictive under the evaluated population. It may be retained for carefully governed prediction, service support, or inequity monitoring if subgroup performance is acceptable. | That region or channel is itself the causal “delay driver,” that the claimant is responsible, or that the association will remain stable after network or policy changes. It should not automatically drive adverse treatment. |
| **Drift/calendar proxy**                       | `calendar_week`; explicit holiday indicator; policy-regime identifier; seasonal workload measures                                                                                                                               | The training period showed a temporal-regime association, and the feature may improve forecasts while that regime persists.                                                                                                | That week number causes breach or that a week-52 effect will recur unchanged. Calendar proxies should not conceal policy or capacity drift.                                                                                    |
| **Unusable until lineage is repaired**         | Current `risk_score_current`; current final-team field; undocumented `initial_reserve`; nightly same-day document snapshot; defective prior-claim SQL; extraction-date employee experience; any forward-selected queue snapshot | No substantive local explanation should be made from the current values. After historical reconstruction, the repaired feature may be reassigned to one of the other classes.                                              | That the present value existed at `t0`, that its contribution is trustworthy, or that the current probability remains valid after merely removing it from the displayed explanation.                                           |

A future event may also be modeled as an **outcome to predict** rather than an observed feature. For example, a prefix-only, cross-fitted estimate of future appeal propensity could be admissible, but the explanation must say “estimated appeal propensity,” not “an appeal occurred.”

## 5. Recommendations for explanation validation

1. **Immediately quarantine the current model for live decision support.** Mark its probabilities and explanations as retrospectively contaminated. Suppressing the leaked attributions in the user interface is insufficient because the model parameters, interactions, baseline, and calibration were learned with those features.

2. **Implement a bitemporal, point-in-time feature store.** Every feature value should carry:

   * entity and feature identifiers;
   * value;
   * `valid_from` and `valid_to`;
   * `known_at` or ingestion timestamp;
   * source event or snapshot identifiers;
   * transformation and schema version;
   * prediction cut and training-extraction version.

   Mutable team, role, reserve, risk-score, and employee attributes should use event sourcing or slowly changing dimensions. Snapshot joins must be backward-only.

3. **Reconstruct all historical training rows at the exact prefix cut.** For each claim, identify the first coverage-completion event and compute features only from information available through that event. Specifically:

   * remove total duration, realized appeal, final decision, complete variant, total requests, and complete-case resource fields;
   * count prior claims with `claim_created_at < t0`, excluding the current claim;
   * count documents using upload and availability timestamps no later than `t0`;
   * recover team, role, reserve, risk score, and employee experience as of `t0`;
   * use an event index rather than timestamp alone for equal-time events.

   Add suffix-invariance tests to the training-data build: changing the post-`t0` suffix must never change an input row.

4. **Put process-conformance tests into data and model CI.** Version the normative model and enforce:

   * coverage before evidence or assessment work;
   * request before receipt and receipt before validation;
   * assessment before the first decision;
   * Partial or Deny before Appeal;
   * Appeal between the first and second decision;
   * final decision or withdrawal before closure;
   * no ordered edge inferred from unresolved timestamp ties.

   Use DFGs for drift discovery, not as normative truth. Review alignment deviations before labeling them violations because the simplified model may omit legitimate exceptions.

5. **Retrain and recalibrate after feature removal.** Use forward-chaining or blocked temporal splits that separate the policy-change and holiday periods. Report discrimination and decision quality together with:

   * Brier score and log loss;
   * calibration intercept and slope;
   * reliability plots;
   * precision, recall, and workload at the operational threshold;
   * decision-curve or expected-cost analysis;
   * performance by process variant and calendar regime.

   Select new thresholds only after estimating intervention capacity and the costs imposed on non-intervened claims.

6. **Validate explanations independently of predictive performance.** Require every attribution to link to its feature timestamp and source evidence. Check that:

   * local contributions reconcile with the displayed score;
   * no hidden “other features” aggregate conceals material drivers;
   * suffix perturbations leave explanations unchanged;
   * contribution signs and top-feature ranks are stable across reasonable explainer backgrounds, resampling, and model seeds;
   * process-constrained counterfactuals remain reachable from the current marking;
   * explanation language distinguishes “associated with” from “caused by” and “candidate action” from “proven intervention.”

7. **Run structured proxy and fairness analysis rather than deleting proxies mechanically.** For region, channel, repaired prior history, and composite risk scores, examine:

   * subgroup and intersectional calibration;
   * false-positive and false-negative rates at the action threshold;
   * intervention-allocation rates and resulting service levels;
   * stability across time, channels, and network-capacity regimes;
   * incremental predictive value after adding direct operational variables;
   * whether the feature is used to improve support or to impose an adverse outcome.

   Where region primarily represents repair-network scarcity, the more actionable response may be capacity or routing support rather than removing the feature or penalizing the claimant.

8. **Test actionability separately from attribution.** Queue length is a plausible operational signal, but before recommending queue relief or priority escalation, estimate whether the intervention changes settlement time and whether it displaces work onto other claims. Controlled rollout, stepped-wedge designs, or credible quasi-experimental analyses can distinguish useful interventions from merely predictive congestion markers.

9. **Monitor schema, feature, process, and explanation drift continuously.** Track missing or duplicated activity labels, missing sequence indices, equal-timestamp rates, snapshot lag, late-arriving documents, feature-version availability, process-alignment costs, variant frequencies, calendar-policy interactions, model calibration, subgroup errors, and explanation-rank stability. A schema or policy change should automatically trigger historical-lineage tests and, where necessary, model recalibration or retraining.
