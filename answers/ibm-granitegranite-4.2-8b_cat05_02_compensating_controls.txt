## 2. Equivalence and Sufficiency Test
A compensatingcontrol package is evaluated against the following **six criteria** (each must be satisfied to claim *full equivalence*; missing one or more criteria reduces equivalence). The test is applied **per case** and per objective (fraud, error, collusion, override abuse, emergency timing).

| Criterion | Fullequivalence (all ) | Partialequivalence (3 , 1 ) | Merely mitigating (22 ) | Ineffective (1 ) |
|------------|--------------------------|-----------------------------------|---------------------------|----------------------|
| **Timing** – preventive checks (AV2) run **before** the releaser action; manager review (MG4) occurs **no later than** release or **before** irrevocable settlement; audit (RA7) starts **within 1business day** of release (or before settlement if recall possible). |  AV2 before Prepare/Release;  MG4 before Release (or before settlement);  RA7 1day. |  at least two of the three timing points correct; one delayed (e.g., manager review after release but before settlement still acceptable for fraud detection but not for recall). | Only one timing point correct (e.g., AV2 early, manager after settlement, audit late). | No timing support for prevention or recall (e.g., AV2 missing, manager after settlement, audit >1day). |
| **Independence** – the manager who ratifies/approves is not the preparer or releaser and has no unresolved conflict of interest; shared service accounts are not counted as independent actors. |  Independent manager + no conflict;  different human resources for Prepare & Release when not using ED1. |  Independent manager but same user performed both Prepare & Release (acceptable only under ED1 with all preconditions met); or conflict unresolved (e.g., supervisor relationship not resolved). | Manager is the same as preparer/releaser or has an unresolved conflict. | Manager is same as releaser or conflict present and not resolved. |
| **Coverage** – the set of checks (AV2) plus manager review addresses the relevant threat (duplicate invoice, bankaccount ownership, operatorlimit, basic PO match, receipt verification). Gaps such as commercial reasonableness or collusion detection are acknowledged as not covered. |  All relevant checks present and manager review includes invoice, bank details, receipt; no reliance on “rubberstamp”. |  Most checks present; one minor gap (e.g., receipt verification missing before release) but manager still reviews substantive docs. | Only preventive checks present, no manager review before release; reliance on postrelease audit only. | No preventive checks or manager review; only audit after release. |
| **Overrideability** – if AV2 emits a warning, an override must be recorded, limited to the same operator, and must require independent manager approval **before** settlement when an override is used. |  Override recorded; independent manager approves before settlement; no override without manager signoff. |  Override recorded but manager approval occurs after release (still before settlement) – acceptable for lowrisk overrides when amount < threshold and emergency not invoked. | Override used without manager approval or manager approval after settlement. | Override used freely without any manager check. |
| **Recoverability** – recall/recovery possible within 24h of bank settlement for payments released under normal flow; for emergency releases, recall window still 24h if audit completes within 1day. |  RA7 audit scheduled 1day; settlement timing permits recall (i.e., audit before or within 24h of settlement). |  Audit scheduled 1day but may finish after settlement in some cases (e.g., AP208); still some recoverability if bank allows recall. | Audit scheduled >1day or after settlement; recall uncertain (high unrecoverable exposure). | No audit scheduled or audit after settlement; no recall path. |
| **Evidence quality** – evidence of independent review (manager notes, receipt verification) is documented contemporaneously; “clean AV2 pass” is not taken as proof of receipt receipt or commercial reasonableness. |  Manager records review of invoice, bank details, receipt; audit report includes findings; timestamps align with process steps. |  Manager reviews but documentation incomplete (e.g., only signature on form); still sufficient for lowrisk cases. | Manager only signs a form without reviewing content; audit report missing details. | No evidence of independent review; reliance on later audit only. |

**Interpretation**

* **Fully equivalent** – all six criteria satisfied for the relevant objective(s). The compensating package meets the nominal foureyes objective without exception.
* **Partially equivalent** – 3 criteria satisfied, 12 criteria weak (e.g., manager review after release but before settlement for fraud detection, or audit slightly delayed). The package reduces risk but leaves a residual gap (usually detectonly or recoveronly).
* **Merely mitigating** – only 2 criteria satisfied (e.g., AV2 preventive + independent manager after settlement). Provides some protection but does not reliably prevent or recall erroneous/fraudulent releases.
* **Ineffective** – 1 criterion satisfied (e.g., manager same as releaser, no audit within window). Does not adequately address the control objective; risk remains high.

> **Why “same expected loss” is not the only standard** – loss size alone ignores timing of detection/recall, independence of the second actor, and the ability to recover funds within the 24hour bankrecall window. A lowamount payment that slips through with no recall path poses a higher residual risk than a highamount payment that is blocked by AV2 before release. The test therefore evaluates *preventdetectcorrect* dynamics rather than a single monetary threshold.

| **Manager ratify after Bank_Settlement (e.g., AP208, AP209)** | Detective only (cannot prevent settlement) | Detective – may detect defects after settlement; corrective capacity limited because recall unlikely after settlement. | Timing after settlement removes corrective efficacy; still provides detection value but not prevention or recall. |

> **Key semantic note:** “Manager action before Release_Payment” is **preventive** (it can stop the release if the manager finds an issue). “Manager action after Release_Payment but before Bank_Settlement” is **hybrid**: it cannot prevent the release that already occurred, but it can prevent irrevocable settlement and may enable recall if the audit completes within the 24hour window. “Manager action after Bank_Settlement” is purely **detective**; it cannot correct the payment because recall is uncertain.

## 6. Evidence and Monitoring Recommendations
1. **Sameuser rate** – monitor the proportion of completed payments where the same human resource performs both Prepare_Payment and Release_Payment (excluding cases that use ED1 with all preconditions met). Alert if >10% of nonemergency payments exhibit sameuser handling (simple convenience pattern may be acceptable for lowrisk officesupply payments only when no override was used).  
2. **Override rate** – track overrides of AV2 warnings. For each override, require (a) an independent manager signoff **before** Release_Payment and (b) a short justification logged by the operator. Alert if >2% of AV2 warnings are overridden without independent manager approval before settlement.  
3. **Late manager approval** – define “late” as manager ratify / approve occurring after Release_Payment and after the 4hour postrelease window (or after Bank_Settlement). Flag cases where late approval occurs; require remedial review before any future release in that case’s workflow.  
4. **Auditbeforerecallwindow** – ensure Audit_Review occurs within 1business day of Release_Payment and ideally before Bank_Settlement when possible. If Bank_Settlement occurs within 24h of Release_Payment, audit must be scheduled to finish within the recall window. Alert when Audit_Review timestamp exceeds Release_Payment + 1day or exceeds Settlement – 24h.  
5. **Repeated resource pairs** – build a lightweight pairfrequency log (PrepareResource + ReleaseResource) for each payment. Detect pairs that appear together in >5 payments within a 30day rolling window. Flag for manual review (check for workload clustering, shared workstation use, or potential collusion). No automatic enforcement; only investigative alert.  
6. **Shared workstations / IP proximity** – if operational policy allows, log the workstation ID or IP at Prepare and Release events. Flag when the same workstation is used for both steps in >3 consecutive payments by the same pair; trigger a brief policy reminder or supervisor check.  
7. **Bankchange proximity** – for every Release_Payment, automatically query the last bankaccount change timestamp for the vendor’s account. If a change occurred within the prior 7days and AV2 did not block/warn (i.e., no warning issued), raise an alert. Ensure that a clean AV2 pass does not imply “no bankchange risk”.  
8. **ED1 token timing verification** – at the start of Prepare_Payment, query the emergencytoken status; log “token active before Prepare?” (true/false). If false, do not allow singleoperator release even if other ED1 conditions appear met. Store this flag in the case facts for audit.  
9. **Evidence quality checklist** – require the manager who ratifies/approves to complete a short checklist (invoice reviewed, receipt verified, bankaccount ownership confirmed) and attach a screenshot or reference ID. Store checklist timestamp alongside Release_Payment. Periodically sample 10% of manager approvals to verify checklist completion.  
10. **Monitoring dashboard fields** (example): Sameuser % , Override% , Latemanager% , Auditwithinwindow% , Pairrepeat% , Bankchangenear% , ED1tokencorrect% . Set thresholds (e.g., >5% for any “alert” metric) and route to linemanager for investigation within 2 business days.

> **Alert vs. proof** – An alert signals a deviation or elevated risk; it does **not** constitute proof of misconduct. Investigations should gather additional context (workstation logs, manager email chain, vendor relationship records) before assigning blame or taking disciplinary action.

**Explanation of the code (kept brief as required):**

1. The CSV string is loaded into a pandas DataFrame via `io.StringIO`.
2. Timestamps are parsed to UTC `datetime64[ns, UTC]`.
3. `pm4py.format_dataframe` converts the DataFrame into a caselog format suitable for pm4py analysis.
4. `pm4py.filter_four_eyes_principle(log_cases, "Prepare_Payment", "Release_Payment")` returns the case IDs where the same human resource performed both steps (the nominal violation set).  
   *Note: The exact function name and signature may vary between pm4py releases; the snippet assumes the helper exists in recent versions. If unavailable, a manual percase check of the first `Prepare_Payment` and first `Release_Payment` resources suffices.*
5. Attempted but blocked releases (e.g., `AP205`) are identified by looking for an `Attempt_Release` event together with a preceding `Automated_Validate_Block`.
6. A tiny `facts` DataFrame mirrors the casefacts table (amount, emergency token, bankchange flag, managerbeforerelease, auditwithin1day, pairrepeat). In a production script these fields would be populated from policy data or audit logs.
7. Simple boolean flags are computed per case:
   * `emergency_eligible` – token active and manager approval before release (ED1 precondition roughly satisfied).  
   * `av_coverage` – presence of any AVrelated event (pass/block/warning).  
   * `late_manager` – manager action occurs after `Release_Payment`.  
   * `audit_late` – `Audit_Review` occurs more than one calendar day after `Release_Payment`.  
   These flags are **evidence cues** for the LLM judge; they do not replace judgment about sufficiency, independence, or residual risk.
8. The script prints the flags; the output is intended only as “evidence for judgment”, not as the final compliance verdict.

The code is selfcontained, uses only standard libraries (`pandas`, `io`, `pm4py`) and does not read external files or call external services. It illustrates how to reconstruct the log, detect nominal foureyes violations, flag attempted blocks, and compute the preliminary evidence indicators requested.
