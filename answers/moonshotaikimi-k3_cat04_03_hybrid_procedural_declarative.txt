# 1. Policy Interpretation and Conflict Resolution

**Material assumptions**

- A1. One case = one vendor onboarding. Labels are used exactly as given. Timestamps are hours since case start; the resource attribute is `org:resource`; case ID is `case:concept:name`.
- A2. `Classify Risk` occurs exactly once per case and requires all three checks (per the stated backbone).
- A3. "Final outcome" in R3 is operationalized as `Reject Vendor` or `Activate Vendor` (the decision events; `Release First Payment`/`Close Onboarding` are consequences).
- A4. `Sanctions Escalation` and `Obtain Legal Opinion` each occur at most once per case (assumption, not stated).
- A5. Accepted cases always reach `Release First Payment` and then `Close Onboarding` (backbone step 5 read as an obligation, not an option).
- A6. `Change Bank Details`/`Suspend Vendor` occur only after activation; at most one bank-change episode per case is assumed for frequency constraints.
- A7. `Verify Bank Account` may occur **twice** (initial verification + R11 re-verification); all other mandatory-once activities occur exactly once.
- A8. `support = 1.0` / `confidence = 1.0` in the hand-authored DECLARE model are **normative assertions** ("must hold for every case"), not statistics discovered from history.
- A9. Temporal-profile bounds are two-sided: a pair is flagged when |t  mean| > ·,  = 2.0.
- A10. The R6 joint authorization is **not observable** in the event log (stated in the scenario) and is treated as an evidentiary gap, not as an implicit pass.

**The R5/R6 conflict.** R5 (Legal) says: after escalation, the opinion must precede activation *under all circumstances*. R6 (Operations) permits activation *before* the opinion under out-of-log joint authorization, with a 24h deadline. These are incompatible policies over the same event pattern (`Sanctions Escalation`  `Activate Vendor`  `Obtain Legal Opinion`). They must not be silently AND-ed (that would ban all emergencies) or OR-ed (that would make R5 unenforceable). Candidate resolutions:

- **Resolution A — Legal precedence (strict).** R5 is enforced as a hard rule; any activation before the opinion after an escalation fails. R6 is rejected as unverifiable. *Risk:* false positives on genuine emergencies, business blockage, incentive to hide emergency practice off-log.
- **Resolution B — Conditional exception with compensating controls (CHOSEN).** The pattern is *not* an automatic violation; it is routed to a quarantine/exception queue as `policy-dependent`, the verifiable part of R6 (opinion within 24h of activation) is enforced as a hard check, and the unverifiable part (joint authorization) must be supplied as out-of-band evidence before audit closure.
- **Resolution C — Dual-variant conformance.** Maintain a "standard" model variant (R5) and an "emergency" model variant (R6); a trace conforming *only* to the emergency variant is automatically escalated for manual review.

**Chosen resolution: B.** *Compliance risk:* the decisive control (joint authorization) lives outside the log, so conformance can never be fully established from the event data; if the evidence-collection workflow is weak, "policy-dependent" degenerates into a rubber stamp and unauthorized emergency activations pass. Mitigations: quarantine queue with no automatic closure, hard 24h timestamp check (fully verifiable — T6 satisfies it at 10h), periodic re-audit of all emergency activations, and a data-quality action to add a `joint_authorization_ref` case attribute to the logging system so R6 becomes log-verifiable in the future.

```python
RFP = "Release First Payment";       CO  = "Close Onboarding"

def node(op, *children):
    t = ProcessTree(operator=op)
    t.children = []
    for c in children:
        c.parent = t
        t.children.append(c)
    return t

def act(label):            return ProcessTree(label=label)   # visible activity
def tau():                 return ProcessTree()              # silent step
def opt(sub):              return node(Operator.XOR, tau(), sub)
def opinion_slot():        return opt(act(OLO))              # optional Obtain Legal Opinion

def bank_change_slot(reverify_mandatory):
    tail = act(VBA) if reverify_mandatory else opt(act(VBA))
    return opt(node(Operator.SEQUENCE, act(CBD), act(SV), tail))

def accepted_tail():
    return node(Operator.SEQUENCE,
                act(AV),
                opinion_slot(),           # R6 emergency slot: opinion MAY follow activation
                bank_change_slot(True),   # pre-payment bank change -> mandatory re-verification
                act(RFP),
                bank_change_slot(False),  # post-payment bank change
                act(CO))

# zero or more strictly matched clarification cycles: XOR(tau, LOOP(do=RQ.RC, redo=tau))
clarification_loop = opt(node(Operator.LOOP,
                              node(Operator.SEQUENCE, act(RQ), act(RC)),
                              tau()))

# optional sanctions escalation (+ optional early opinion), available before any outcome
escalation_block = opt(node(Operator.SEQUENCE, act(SE), opinion_slot()))

reject_branch = node(Operator.SEQUENCE, act(RV), act(CO))
low_branch    = node(Operator.SEQUENCE, act(MA), accepted_tail())
high_branch   = node(Operator.SEQUENCE, act(EDD), opinion_slot(), act(CA), accepted_tail())

procedural_model = node(Operator.SEQUENCE,
    act(ROR),                                               # 1. start
    node(Operator.PARALLEL, act(CMD), act(RSS), act(VBA)),  # 2. three concurrent checks
    clarification_loop,                                     # 3. R3 matched cycles
    act(CR),                                                # 4. join / classification
    escalation_block,                                       #    optional SE (+OLO)
    node(Operator.XOR, reject_branch, low_branch, high_branch))

# Optional: pm4py.convert_to_petri_net(procedural_model) yields an accepting Petri net
# (initial marking = source place, final marking = sink place) for alignments.
```

## 3.3 Design explanation

- **Concurrency.** The three checks are a `PARALLEL` (AND) block: all 6 interleavings are admitted, and `Classify Risk` is the join (needs all three).
- **Choices.** One top-level XOR over the three outcome branches. Putting `Close Onboarding` inside each branch (rather than a shared tail after a second XOR) avoids a **cross-branch correlation defect**: a shared tail (`XOR(RV, MA, …)` then `XOR(, AV·…·RFP)` then `CO`) would illegally admit `RV … AV … CO`.
- **Clarification loop.** `XOR(, LOOP(SEQ(RQ, RC), ))` yields zero or more strictly matched request/response cycles. **Disclosed approximation:** a process tree is block-structured, so the loop is *positioned* between the checks and classification — it cannot interleave with the concurrent checks or occur after classification. R3 in full generality ("any time before the final outcome") is enforced position-free by DECLARE `altresponse`/`altprecedence` and the §7 backstop. All eight test cases place clarifications inside the modeled region.
- **Terminal outcomes.** Reject branch: `RV  CO`. Accepted branches: approval  `AV  RFP  CO`. Exactly-once behavior is structural (no loops over these activities) and redundantly enforced by `activ_freq`.
- **R5/R6 neutrality (deliberate).** The tree admits the opinion *before* approval (T7), *after activation* in the emergency slot (T6), or not at all when no escalation occurred (T1). The tree therefore does **not** encode R5 — that conflict is delegated to the policy layer (§7), because no block structure can express "OLO before AV *iff* SE occurred earlier" while also permitting the R6 exception.
- **Post-activation behavior.** Included: emergency opinion slot; one optional bank-change episode before payment (re-verification mandatory, R11) and one after payment. **Deliberately excluded:** multiple bank-change episodes, clarifications after classification, re-classification loops, and opinion after `Release First Payment`. Traces needing those fail the procedural layer by design and are handled declaratively/externally where justified.

**Rule semantics and direction** (keys are `(source, target)`):

| Rule | Direction | Meaning | Req. | Vacuity note |
|---|---|---|---|---|
| `init(ROR)` | unary | First event of every case is ROR | step 1 | Non-vacuous (always active) |
| `exactly_one(ROR / CR / CO)` | unary | Exactly one occurrence | A2 | Non-vacuous |
| `altresponse(RQ  RC)` | sourcetarget, forward | If RQ occurs, RC must eventually follow, **with no second RQ in between** | R3 | Vacuous in cases without RQ (T1, T3, T4, T6–T8) |
| `altprecedence(RQ  RC)` | targetsource, backward | Every RC is preceded by an RQ, **with no other RC in between** (no unsolicited or doubled answers) | R3 | Vacuous without RC |
| `precedence(RSS  SE)` | backward | SE is allowed only if RSS happened before | R7 | Vacuous without SE (T1–T5, T8) |
| `response(SE  OLO)` | forward | Every escalation is eventually followed by an opinion (any distance) | R4 | Vacuous without SE |
| `response(MA  AV)`, `response(CA  AV)` | forward | Approval must be followed by activation | step 5 | Vacuous on the other route / rejected cases |
| `succession(AV  RFP)` | both | Every AV is eventually followed by RFP **and** every RFP is preceded by AV | step 5 | — |
| `response(RV  CO)`, `response(RFP  CO)` | forward | Every terminal state closes | step 5 | — |
| `response(CBD  SV)` | forward | Bank change is eventually followed by suspension | R11 | Vacuous in all eight tests (no CBD) |
| `noncoexistence(RV, AV)` | symmetric | Never both in one case, in **either** order | R1 | — |
| `noncoexistence(EDD, MA)`, `noncoexistence(CA, MA)` | symmetric | Route exclusivity | R8 | — |

**Template distinctions that matter here.**

- *Response vs precedence:* `response(A,B)` constrains what must happen **after** A; `precedence(A,B)` constrains what must have happened **before** B. R4 is forward-looking (response); R7 is backward-looking (precedence). `succession(AV,RFP)` asserts both directions.
- *Alternate vs chain:* `altresponse(RQ,RC)` allows arbitrary events (waiting, other work) between request and answer, but forbids a second request before the answer. `chainresponse` would demand RC be the *immediately next* event — too brittle as a norm (it would fail any case where, e.g., a screening completes while awaiting clarification), so chain templates are deliberately unused. This also tells us T5's violation is *not* about adjacency but about a **missing** answer.
- *Noncoexistence vs nonsuccession:* R1 forbids the pair in **both** orders. `nonsuccession(Reject Vendor, Activate Vendor)` would only forbid AV-after-RV and would **miss T8** (which is RV-after-AV); two `nonsuccession` rules would be needed to approximate one `noncoexistence`. Noncoexistence is the correct template.
- *R5 deliberately absent:* there is no binary template for "OLO between SE and AV" — see §2, row R5. Encoding `precedence(OLO, AV)` would wrongly fail T1/T2; encoding `nonsuccession(SE, AV)` would wrongly fail T7.

# 5. Log-Skeleton Model

**Stated checking semantics (PM4Py subset-inclusion):** a trace conforms iff *every relation the trace exhibits* is contained in the model. Hence `equivalence`, `always_before`, `always_after`, `directly_follows` act as **whitelists** (omission = forbidden), while `never_together` and `activ_freq` are **blacklists**. `always_before(A,B)` means: whenever both occur, A occurs before B; `always_after(A,B)` is its dual (`always_after = {(b,a) | (a,b)  always_before}`).

```python
ROR="Receive Onboarding Request"; CMD="Capture Master Data"; RSS="Run Sanctions Screening"
VBA="Verify Bank Account"; CR="Classify Risk"; RQ="Request Clarification"; RC="Receive Clarification"
SE="Sanctions Escalation"; OLO="Obtain Legal Opinion"; EDD="Enhanced Due Diligence"
MA="Manager Approval"; CA="Compliance Approval"; RV="Reject Vendor"; AV="Activate Vendor"
CBD="Change Bank Details"; SV="Suspend Vendor"; RFP="Release First Payment"; CO="Close Onboarding"
ACT = [ROR,CMD,RSS,VBA,CR,RQ,RC,SE,OLO,EDD,MA,CA,RV,AV,CBD,SV,RFP,CO]

always_before = set()
def ab(a,b): always_before.add((a,b))

for x in ACT:                                   # ROR is first, before everything
    if x != ROR: ab(ROR, x)
CHECKS = [CMD, RSS, VBA]
AFTER_CHECKS = [RQ,RC,CR,SE,OLO,EDD,MA,CA,RV,AV,CBD,SV,RFP,CO]
for c1 in CHECKS:
    for c2 in CHECKS:                           # checks mutually concurrent: both orders allowed
        if c1 != c2: ab(c1, c2)
    for x in AFTER_CHECKS: ab(c1, x)            # checks precede all downstream behavior
ab(RQ,RC); ab(RC,RQ)                            # multiple cycles: both orders across iterations
for x in [CR,SE,OLO,EDD,MA,CA,RV,AV,CBD,SV,RFP,CO]:
    ab(RQ,x); ab(RC,x)                          # clarification region precedes classification+
for x in [SE,OLO,EDD,MA,CA,RV,AV,CBD,SV,RFP,CO]:
    ab(CR,x)                                    # classification before all outcomes
for x in [OLO,EDD,MA,CA,RV,AV,CBD,SV,RFP,CO]:
    ab(SE,x)                                    # R7: escalation after screening/CR, before outcomes
for x in [EDD,MA,CA,AV]:                        # R5/R6 CONFLICT: opinion ordering deliberately neutral
    ab(OLO,x); ab(x,OLO)
ab(OLO,RV); ab(OLO,RFP); ab(OLO,CO); ab(OLO,CBD); ab(OLO,SV)
for a in [MA,CA]:
    for x in [AV,RFP,CO,CBD,SV]: ab(a,x)        # approval before activation chain
for x in [CA,AV,RFP,CO,CBD,SV]: ab(EDD,x)       # EDD before CA / activation chain
for x in [RFP,CO,CBD,SV]: ab(AV,x)              # activation before payment/close/post-activation
ab(RV,CO)
ab(CBD,SV); ab(CBD,RFP); ab(RFP,CBD); ab(CBD,CO)   # bank-change episode may precede OR follow payment
ab(SV,RFP);  ab(RFP,SV);  ab(SV,CO);  ab(RFP,CO)

always_after = {(b,a) for (a,b) in always_before}   # exact dual

NEVER_EQUAL = {frozenset([RV,AV]), frozenset([RV,RFP])}   # exactly one of each pair occurs per case
equivalence = {(a,b) for a in ACT for b in ACT if a != b and frozenset([a,b]) not in NEVER_EQUAL}

log_skeleton = {
    "equivalence": equivalence,
    "always_before": always_before,
    "always_after": always_after,
    "never_together": {
        (RV,AV),(AV,RV),            # R1
        (EDD,MA),(MA,EDD),          # R8
        (CA,MA),(MA,CA),            # R8 / R2
        (RV,MA),(MA,RV),(RV,CA),(CA,RV),(RV,EDD),(EDD,RV),   # structural: reject-branch exclusivity
        (RV,RFP),(RFP,RV),(RV,CBD),(CBD,RV),(RV,SV),(SV,RV), # structural: nothing post-activation after rejection
    },
    "activ_freq": {
        ROR:{1}, CMD:{1}, RSS:{1}, CR:{1}, CO:{1},
        VBA:{1,2},                  # R11 re-verification
        SE:{0,1}, OLO:{0,1}, EDD:{0,1}, MA:{0,1}, CA:{0,1},
        RV:{0,1}, AV:{0,1}, RFP:{0,1},   # R10
        CBD:{0,1}, SV:{0,1},             # assumption A6
        # RQ/RC intentionally omitted: unbounded matched loop; any cap would be arbitrary
    },
    "directly_follows": {
        (ROR,CMD),(ROR,RSS),(ROR,VBA),
        (CMD,RSS),(RSS,CMD),(CMD,VBA),(VBA,CMD),(RSS,VBA),(VBA,RSS),   # concurrent checks
        (CMD,CR),(RSS,CR),(VBA,CR),          # checks -> classification (no open clarification)
        (CMD,RQ),(RSS,RQ),(VBA,RQ),          # checks -> first clarification request
        (RQ,RC),(RC,RQ),(RC,CR),             # matched cycles; NOTE: (RQ,CR) and (RQ,RQ) absent (R3)
        (CR,RV),(CR,MA),(CR,EDD),(CR,SE),
        (SE,EDD),(SE,MA),(SE,RV),(SE,OLO),
        (OLO,EDD),(OLO,MA),(OLO,RV),
        (EDD,OLO),(EDD,CA),(OLO,CA),
        (MA,AV),(CA,AV),
        (AV,OLO),(AV,CBD),(AV,RFP),          # emergency opinion slot (R6) / bank change / payment
        (OLO,CBD),(OLO,RFP),
        (CBD,SV),(SV,VBA),                   # NOTE: (SV,CBD) absent (R11 ordering)
        (VBA,RFP),(SV,CO),(VBA,CO),
        (RFP,CBD),(RFP,CO),(RV,CO),
    },
}
# usage: pm4py.conformance_log_skeleton(log, log_skeleton)
```

**Orientation of key pairs and layer interplay.**

- `(RSS, SE)` whitelisted in `always_before`, reverse omitted  escalation-before-screening is a skeleton violation (agrees with DECLARE `precedence`, R7).
- `(OLO, AV)` **and** `(AV, OLO)` are both whitelisted: the skeleton is **deliberately neutral** on the R5/R6 conflict (unlike the tree's slots, which also admit both). The conflict is adjudicated only in §7.
- `(CBD, SV)` present, `(SV, CBD)` absent  suspension must follow the change, never precede it.
- `directly_follows` omits `(RQ, CR)` and `(RQ, RQ)`: an *unanswered* request adjacent to classification (T5) or a re-request before an answer is caught here — a **stricter** check than `always_before`, which does allow `(RQ, CR)` at a distance (ordering legal, adjacency not).
- `equivalence` deliberately excludes `(RV, AV)` and `(RV, RFP)`: exactly one of each pair occurs in every compliant case, so their counts are *never equal*; T8 (RV=1, AV=1) exhibits the equality pair and is flagged. All other pairs (including counterintuitive 0=0 pairs among absent activities) must be whitelisted, because under subset-inclusion checking any equal-count pair a compliant trace shows must be in the model — a verbosity caveat discussed in §9.
- `activ_freq` overlaps the tree on at-most-once behavior and is the *only* layer catching a second `Obtain Legal Opinion` (the tree has three OLO slots).
- Disagreement by design: the tree is stricter on *placement* (loop region, slots); the skeleton is stricter on *adjacency and counts*; DECLARE is stricter on *conditional ordering*. A trace must satisfy all three to be fully conformant.

Effective flag windows (|t  mean|  ·): RQRC  [0h, 96h]; SEOLO  [0h, 24h]; AVRFP  [0h, 144h].

**Why warnings, not violations.** R12 is stated by Compliance as "normative enough to flag but not automatically reject": these are *statistical* expectations over a population, not per-case obligations. Individual deviation has legitimate causes (vendor responsiveness, legal workload, payment runs), the means/standard deviations are themselves estimated from historical logs and drift, and the ±2 band nominally tolerates ~5% of cases. Blocking control flow on them would manufacture false rejections and contradict the stated policy. They therefore feed monitoring dashboards, auditor sampling, and periodic recalibration — never the hard-verdict path. Note the separate, *hard* 24h deadline in R6 is deliberately **not** part of this profile; it is an absolute bound enforced in §7. Also note: pairs whose target never occurs (T5's unanswered request) are invisible to the temporal checker — that violation belongs to DECLARE, not to the profile.

# 7. Resource- and Data-Aware Checks

Activity-only models cannot see resources, occurrence counts relative to other events, or out-of-log authorization. These checks run on an event dataframe. **Required attributes:** `case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`; for R6 additionally a case attribute `joint_authorization_ref` (absent per scenario). **Missing-attribute policy:** missing `org:resource` on a checked activity  verdict `not evaluated`, data-quality incident raised, and the case is routed **fail-closed** to manual review (SoD cannot be proven); missing timestamp  temporal/R6 checks `not evaluated`; missing `joint_authorization_ref`  `policy-dependent` (never silently pass).

```python
import pandas as pd
CASE, ACT, TIME, RES = "case:concept:name", "concept:name", "time:timestamp", "org:resource"

def _first(g):                       # first occurrence of each activity in the case
    return g.sort_values(TIME).drop_duplicates(ACT).set_index(ACT)

def check_segregation_of_duties(df):
    """R9: resource(VBA) != resource(applicable approval); resource(CMD) != resource(AV)."""
    out = []
    for case, g in df.groupby(CASE):
        fo = _first(g); res = fo[RES]
        approval = next((a for a in ("Manager Approval", "Compliance Approval") if a in res.index), None)
        pairs = ([("Verify Bank Account", approval)] if approval else []) + \
                ([("Capture Master Data", "Activate Vendor")] if "Activate Vendor" in res.index else [])
        for a, b in pairs:
            ra, rb = res.get(a), res.get(b)
            if pd.isna(ra) or pd.isna(rb):
                out.append((case, "R9", "not evaluated",
                            f"missing org:resource on '{a}' or '{b}' -> fail-closed: manual review"))
            elif ra == rb:
                out.append((case, "R9", "fail", f"SoD breach: '{a}' and '{b}' both performed by {ra}"))
    return out
# Convenience (fixed pairs only): pm4py.filter_four_eyes_principle(log, "Verify Bank Account",
#   "Manager Approval") — verify the `positive` parameter semantics in your PM4Py version;
#   the custom check above is authoritative because the approval activity is case-dependent.

def check_escalation_policy(g, resolution="B", deadline=pd.Timedelta(hours=24)):
    """R4/R5/R6 for one case. resolution='A' (legal strict) or 'B' (emergency exception)."""
    fo = _first(g); t = fo[TIME]
    if "Sanctions Escalation" not in t.index:
        return ("R4-R6", "pass", "no escalation (vacuous)")
    if "Obtain Legal Opinion" not in t.index:
        return ("R4", "fail", "escalation without any legal opinion")
    olo = t["Obtain Legal Opinion"]; av = t.get("Activate Vendor")
    if pd.isna(av) or olo <= av:
        return ("R5", "pass", "opinion precedes activation (or no activation)")
    if resolution == "A":
        return ("R5", "fail", "activation before legal opinion after escalation")
    if olo - av > deadline:                                  # verifiable part of R6 (hard)
        return ("R6", "fail", "opinion arrived >24h after emergency activation")
    if g.attrs.get("joint_authorization_ref") is None:       # unverifiable part of R6
        return ("R6", "policy-dependent",
                "emergency authorization not in log; quarantine case, require out-of-band evidence")
    return ("R6", "pass", "emergency authorization evidenced externally")

def check_bank_change(g):
    """R11: post-activation Change Bank Details => eventual Suspend Vendor; and any
    Release First Payment after the change requires a NEW Verify Bank Account in between."""
    evs = list(g.sort_values(TIME)[[ACT, TIME]].itertuples(index=False, name=None))
    out = []
    av = next((t for a, t in evs if a == "Activate Vendor"), None)
    for i, (a, t) in enumerate(evs):
        if a == "Change Bank Details" and av is not None and t > av:
            later = evs[i + 1:]
            if not any(x == "Suspend Vendor" for x, _ in later):
                out.append(("R11", "fail", "bank change not eventually followed by suspension"))
            for j, (x, tx) in enumerate(later):
                if x == "Release First Payment":
                    if not any(y == "Verify Bank Account" for y, _ in later[:j]):
                        out.append(("R11", "fail", "payment after bank change without fresh verification"))
                    break      # RFP occurs at most once (R10)
    return out

def check_approval_cardinality(g):
    """R2 backstop: accepted => exactly one of {MA, CA}; rejected => neither; R1 backstop."""
    acts = set(g[ACT]); av, rv = "Activate Vendor" in acts, "Reject Vendor" in acts
    n = int("Manager Approval" in acts) + int("Compliance Approval" in acts)
    if av and rv:  return ("R1", "fail", "both terminal outcomes present")
    if av and n != 1: return ("R2", "fail", f"accepted case with {n} approvals")
    if rv and n != 0: return ("R2", "fail", "rejected case with approvals")
    return ("R2", "pass", "approval cardinality consistent")

def check_clarification_before_outcome(g):
    """R3 backstop: every request has an answer before the first final outcome (RV/AV)."""
    evs = list(g.sort_values(TIME)[[ACT, TIME]].itertuples(index=False, name=None))
    for i, (a, t) in enumerate(evs):
        if a == "Request Clarification":
            rc = next((tx for x, tx in evs[i+1:] if x == "Receive Clarification"), None)
            outcome = next((x for x, _ in evs[i+1:] if x in ("Reject Vendor", "Activate Vendor")), None)
            if rc is None or (outcome is not None and
                              all(tx2 >= rc for x2, tx2 in evs[i+1:] if x2 == outcome)):
                return ("R3", "fail", "request unanswered before final outcome")
    return ("R3", "pass", "all requests answered before outcome")
```

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement.** R1 is enforced three times (XOR branch, `noncoexistence`, `never_together` + equivalence exclusion); R8 twice; R10 twice; R7 twice. This is deliberate defense-in-depth for safety-critical exclusions, but it creates *maintenance drift risk*: if a policy changes (e.g., rejection after activation becomes legal), three artifacts must change in lockstep, and divergent layers produce confusing per-layer verdicts. §10 defines layer precedence for surfacing.
- **Loops vs. constraints.** The clarification loop interacts badly with relation whitelists: with repeated activities, `always_before` must contain *both* `(RQ,RC)` and `(RC,RQ)`, so the skeleton cannot by itself express alternation — that needs `altresponse` (DECLARE) and the block-structured loop (tree). Conversely, the tree's fixed loop position is stricter than R3's wording; the DECLARE layer compensates.
- **Post-activation changes.** R11's "another `Verify Bank Account`" means a *second occurrence* — inexpressible in standard DECLARE and approximated by `activ_freq {1,2}` plus the external check. Tension with R10: since `Release First Payment` occurs at most once, "any later RFP" is only non-vacuous when the bank change happens *before* payment; the pre-payment slot therefore makes re-verification mandatory while the post-payment slot does not.
- **Vacuity.** In T1/T3/T4/T8, `altresponse`, `precedence(RSS,SE)`, `response(SE,OLO)`, `response(CBD,SV)` are all *vacuously* satisfied (no activations). A vacuous pass is not evidence of compliant behavior; reports must show activation/vacuity counts per rule, otherwise dashboards overstate assurance.
- **Missing case attributes.** The decisive R6 attribute (joint authorization) is absent by construction; the risk *class* (low/high) is not logged either, so R2's "accepted case" is proxied by `Activate Vendor` presence and the route is inferred from activities rather than from the classification's actual output — a genuinely wrong `Classify Risk` decision is invisible to every layer.
- **Timestamp-only limitations.** Elapsed-time pairing uses first matching occurrences; wall-clock hours ignore business calendars, time zones, and case suspension time; lower-tail behavior (T7's 2h payment, z1.94) passes =2 despite being operationally suspicious — consider one-sided limits or additional control rules. The temporal checker also silently skips pairs whose target never occurs (T5).
- **Support/confidence as normative truth.** Here both are hand-set to 1.0 as normative claims. If the model were instead *discovered*, high support/confidence would merely describe historical behavior — frequent past emergencies would "launder" R6 violations into apparently legitimate rules. Descriptive statistics must never be read as policy.
- **Irreducible conflict.** R5 vs R6 cannot be merged at the activity level; any single-layer model that admits T6 either violates R5 silently (if it just permits the order) or violates R6 (if it forbids it). Only an explicit `policy-dependent` verdict with external evidence handling is honest.

# 10. Deployment Recommendation

- **Canonical procedural representation:** the §3 process tree — block-structured, sound by construction, directly convertible to an accepting Petri net (`pm4py.convert_to_petri_net`) for alignments and to POWL if partial-order reasoning over SE/OLO is later preferred. It encodes only *uncontested* structure; the R5/R6 conflict is intentionally left as admitted-but-policed behavior.
- **Authoritative policy layer:** the §7 resource/data-aware validators are authoritative for R2 (backstop), R5, R6, R9, R11; the DECLARE model is authoritative for position-free ordering norms (R3, R4, R7); the skeleton is authoritative for occurrence counts (R10, R11 frequency part). The temporal profile is advisory only.
- **Check order:** (1) schema/data-quality gate (required attributes present); (2) log skeleton (cheap counts, co-occurrence, adjacency); (3) procedural alignment (structural fit); (4) DECLARE ordering; (5) resource/data-aware checks incl. the R5/R6 adjudication; (6) temporal profile (non-blocking warnings last). Rationale: cheap hard checks first, expensive alignments after gross deviations are removed, soft temporal signals never block.
- **Surfacing contradictions:** never collapse layers into one silent AND. Emit a per-case verdict matrix (as in §8); label every finding with its rule ID and the *policy resolution in force* (a config flag records whether Resolution A or B was applied); route `policy-dependent` cases (T6-type) to a quarantine queue that cannot auto-close until the out-of-band authorization evidence is attached; show temporal warnings on a separate advisory channel. Any change to R5/R6 policy must be versioned so historical verdicts remain explainable.
