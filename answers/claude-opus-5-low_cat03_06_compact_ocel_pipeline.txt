## 1. Modeling assumptions

**Object types and capitalization.**
Object *types* are lowercase singular nouns: `order`, `item`, `package`, `delivery`, `invoice`, `payment`.
Object *identifiers* keep the narrative's uppercase form: `O100`, `O200`, `I1`, `I2`, `I3`, `P1`, `P2`, `D1`, `D2`, `V1`, `M1`, `M2`.
Activities are human-readable Title Case strings (`Create Order`, `Add Item`, `Reserve Stock`, `Pack Package`, `Dispatch Package`, `Issue Invoice`, `Record Payment`, `Confirm Delivery`, `Close Order`). Event identifiers are `e1 … e17` in narrative order.

**E2O qualifier vocabulary (role of the object *in* the event).**

| qualifier | object type | used by |
|---|---|---|
| `created_order` | order | Create Order |
| `closed_order` | order | Close Order |
| `affected_order` | order | Add Item, Reserve Stock, Pack Package, Issue Invoice |
| `added_item` | item | Add Item |
| `reserved_item` | item | Reserve Stock |
| `packed_item` | item | Pack Package |
| `packed_package` | package | Pack Package |
| `dispatched_package` | package | Dispatch Package |
| `dispatched_delivery` | delivery | Dispatch Package |
| `confirmed_delivery` | delivery | Confirm Delivery |
| `issued_invoice` | invoice | Issue Invoice |
| `settled_invoice` | invoice | Record Payment |
| `recorded_payment` | payment | Record Payment |

The vocabulary is exhaustive and non-overlapping: one activity/type pair always uses exactly one qualifier, so `groupby(['ocel:activity','ocel:type','ocel:qualifier'])` is a functional mapping and qualifier-based filtering is unambiguous.

**O2O direction conventions.** Every O2O row is stored **once**, from the *containing / issuing / active* object to the *contained / billed / passive* object, and the qualifier names the relation as read left-to-right:

- `order --contains--> item` (O100→I1, O100→I2, O200→I3)
- `package --packs--> item` (P1→I1, P1→I3, P2→I2)
- `delivery --carries--> package` (D1→P1, D2→P2)
- `invoice --bills--> order` (V1→O100, V1→O200)
- `payment --partially_settles--> invoice` (M1→V1), `payment --completes_settlement--> invoice` (M2→V1)

No inverse rows are materialised. Consumers that need the reverse direction must swap the columns explicitly; this keeps cardinality counts honest (11 O2O facts, not 22).

**Do logistics and financial events relate directly to Orders and Items?** Partly, and only where the narrative states operational involvement:

- `Reserve Stock` and `Pack Package` relate to Orders **directly**, because the text says explicitly that these events are shared by / relate to both Orders. They also relate to the Items they act on.
- `Dispatch Package` and `Confirm Delivery` relate **only** to the package and/or delivery. The narrative never says the order participates in dispatch; the link Order→Item→Package→Delivery is structural, not observational.
- `Issue Invoice` relates to `V1` **and** to both Orders (the narrative says "for both Orders").
- `Record Payment` relates to the payment and the invoice only. Payments settle an *invoice*, not an order; any order-level payment attribution is an inference.

This is a **moderate, source-faithful** policy: an E2O row exists only if the source system would plausibly have recorded that object on that event record.

**Preventing confusion between propagation and source facts.** Analytical enrichment is never written back into `relations`. The pipeline computes propagated links (e.g. "which order was dispatched") in a *separate* DataFrame `relations_propagated` carrying an extra boolean column `derived=True` and a `derivation_path` string, and this frame is **not** passed to the `OCEL` constructor. `relations` therefore stays a pure record of observation. Any analysis that uses the propagated frame must say so in its caption.

**Version-dependent PM4Py assumption.** Only one line depends on the API: `ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)`. In PM4Py builds where `OCEL.__init__` does not expose the `o2o` keyword, construct `OCEL(events=events, objects=objects, relations=relations)` and then assign `ocel.o2o = o2o` afterwards; in older builds the O2O table may be unsupported entirely, in which case it is kept as a side table and used for manual propagation. The *data semantics never change* — only the assignment mechanism. All later calls (`pm4py.ocel_flattening`, `discover_ocdfg`, `discover_otg`, `discover_etot`, `discover_oc_petri_net`, `ocel_objects_interactions_summary`) are assumed present in a recent PM4Py 2.x.

## 2. Complete Python pipeline

```python
"""
Compact OCEL 2.0-style dataset built in memory from a natural-language
retail process (2 orders, 3 items, 2 packages, 2 deliveries, 1 invoice,
2 partial payments), plus a full PM4Py object-centric analysis pipeline.

No external files, no network access.
"""

import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

TZ = "UTC"


def ts(s: str) -> pd.Timestamp:
    """Timezone-aware timestamp helper (all narrative times are UTC)."""
    return pd.Timestamp(s, tz=TZ)


# ---------------------------------------------------------------------------
# B/C. EVENTS  (17 events, unique ids, event attributes stay here)
# ---------------------------------------------------------------------------
EVENT_ROWS = [
    # eid, activity,           timestamp,               amount, currency
    ("e1",  "Create Order",    "2026-04-06 08:00:00", None,  None),
    ("e2",  "Add Item",        "2026-04-06 08:05:00", None,  None),
    ("e3",  "Add Item",        "2026-04-06 08:06:00", None,  None),
    ("e4",  "Create Order",    "2026-04-06 08:10:00", None,  None),
    ("e5",  "Add Item",        "2026-04-06 08:12:00", None,  None),
    ("e6",  "Reserve Stock",   "2026-04-06 08:30:00", None,  None),
    ("e7",  "Pack Package",    "2026-04-06 09:00:00", None,  None),
    ("e8",  "Pack Package",    "2026-04-06 09:05:00", None,  None),
    ("e9",  "Dispatch Package", "2026-04-06 10:00:00", None, None),
    ("e10", "Dispatch Package", "2026-04-06 10:15:00", None, None),
    ("e11", "Issue Invoice",   "2026-04-06 11:00:00", None,  None),
    ("e12", "Record Payment",  "2026-04-06 11:30:00", 100.0, "EUR"),
    ("e13", "Confirm Delivery", "2026-04-06 13:00:00", None, None),
    ("e14", "Confirm Delivery", "2026-04-07 09:00:00", None, None),
    ("e15", "Record Payment",  "2026-04-07 10:00:00", 150.0, "EUR"),
    ("e16", "Close Order",     "2026-04-07 10:30:00", None,  None),
    ("e17", "Close Order",     "2026-04-07 10:35:00", None,  None),
]

events = pd.DataFrame(
    [(e, a, ts(t), amt, cur) for (e, a, t, amt, cur) in EVENT_ROWS],
    columns=["ocel:eid", "ocel:activity", "ocel:timestamp",
             "amount", "currency"],
).sort_values("ocel:timestamp").reset_index(drop=True)


# ---------------------------------------------------------------------------
# B/C. OBJECTS
# ---------------------------------------------------------------------------
OBJECT_ROWS = [
    ("O100", "order"), ("O200", "order"),
    ("I1", "item"), ("I2", "item"), ("I3", "item"),
    ("P1", "package"), ("P2", "package"),
    ("D1", "delivery"), ("D2", "delivery"),
    ("V1", "invoice"),
    ("M1", "payment"), ("M2", "payment"),
]

objects = pd.DataFrame(OBJECT_ROWS, columns=["ocel:oid", "ocel:type"])

OBJ_TYPE = dict(OBJECT_ROWS)  # oid -> type, single source of truth


# ---------------------------------------------------------------------------
# D. EVENT-TO-OBJECT RELATIONS
# Source-faithful policy: an object appears on an event only if the narrative
# states operational involvement.  Activity and timestamp are copied from the
# events table (never re-typed by hand).
# ---------------------------------------------------------------------------
E2O_SPEC = {
    "e1":  [("O100", "created_order")],
    "e2":  [("O100", "affected_order"), ("I1", "added_item")],
    "e3":  [("O100", "affected_order"), ("I2", "added_item")],
    "e4":  [("O200", "created_order")],
    "e5":  [("O200", "affected_order"), ("I3", "added_item")],
    # jointly shared across both orders -> the convergence point of the log
    "e6":  [("O100", "affected_order"), ("O200", "affected_order"),
            ("I1", "reserved_item"), ("I3", "reserved_item")],
    "e7":  [("P1", "packed_package"),
            ("I1", "packed_item"), ("I3", "packed_item"),
            ("O100", "affected_order"), ("O200", "affected_order")],
    "e8":  [("P2", "packed_package"),
            ("I2", "packed_item"),
            ("O100", "affected_order")],
    # logistics: package + delivery only; order linkage stays structural (O2O)
    "e9":  [("P1", "dispatched_package"), ("D1", "dispatched_delivery")],
    "e10": [("P2", "dispatched_package"), ("D2", "dispatched_delivery")],
    "e11": [("V1", "issued_invoice"),
            ("O100", "affected_order"), ("O200", "affected_order")],
    # financial: payment + invoice only; order attribution is an inference
    "e12": [("M1", "recorded_payment"), ("V1", "settled_invoice")],
    "e13": [("D1", "confirmed_delivery")],
    "e14": [("D2", "confirmed_delivery")],
    "e15": [("M2", "recorded_payment"), ("V1", "settled_invoice")],
    "e16": [("O200", "closed_order")],
    "e17": [("O100", "closed_order")],
}

_ev_index = events.set_index("ocel:eid")[["ocel:activity", "ocel:timestamp"]]

relations = pd.DataFrame(
    [
        {
            "ocel:eid": eid,
            "ocel:activity": _ev_index.at[eid, "ocel:activity"],
            "ocel:timestamp": _ev_index.at[eid, "ocel:timestamp"],
            "ocel:oid": oid,
            "ocel:type": OBJ_TYPE[oid],
            "ocel:qualifier": qual,
        }
        for eid, pairs in E2O_SPEC.items()
        for (oid, qual) in pairs
    ]
).sort_values(["ocel:timestamp", "ocel:eid", "ocel:oid"]).reset_index(drop=True)


# ---------------------------------------------------------------------------
# E. OBJECT-TO-OBJECT RELATIONS (stored once, container -> contained)
# ---------------------------------------------------------------------------
O2O_ROWS = [
    ("O100", "I1", "contains"),
    ("O100", "I2", "contains"),
    ("O200", "I3", "contains"),
    ("P1", "I1", "packs"),
    ("P1", "I3", "packs"),
    ("P2", "I2", "packs"),
    ("D1", "P1", "carries"),
    ("D2", "P2", "carries"),
    ("V1", "O100", "bills"),
    ("V1", "O200", "bills"),
    ("M1", "V1", "partially_settles"),
    ("M2", "V1", "completes_settlement"),
]

o2o = pd.DataFrame(O2O_ROWS,
                   columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"])


# ---------------------------------------------------------------------------
# ANALYTICAL PROPAGATION -- kept strictly OUT of `relations`.
# These rows are *derived*, flagged, and never handed to the OCEL constructor.
# ---------------------------------------------------------------------------
def propagate_orders_via_o2o(relations_df: pd.DataFrame,
                             o2o_df: pd.DataFrame) -> pd.DataFrame:
    """Derive event->order links for logistics/financial events.

    package -> item -> order   and   payment -> invoice -> order.
    The result is an ANALYTICAL artifact (derived=True), not observation.
    """
    pkg_item = o2o_df[o2o_df["ocel:qualifier"] == "packs"]
    ord_item = o2o_df[o2o_df["ocel:qualifier"] == "contains"]
    del_pkg = o2o_df[o2o_df["ocel:qualifier"] == "carries"]
    inv_ord = o2o_df[o2o_df["ocel:qualifier"] == "bills"]
    pay_inv = o2o_df[o2o_df["ocel:qualifier"].isin(
        ["partially_settles", "completes_settlement"])]

    item_to_order = dict(zip(ord_item["ocel:oid_2"], ord_item["ocel:oid"]))
    pkg_to_orders = (pkg_item.assign(
        order=pkg_item["ocel:oid_2"].map(item_to_order))
        .groupby("ocel:oid")["order"].apply(lambda s: sorted(set(s))).to_dict())
    del_to_orders = {d: pkg_to_orders.get(p, [])
                     for d, p in zip(del_pkg["ocel:oid"], del_pkg["ocel:oid_2"])}
    inv_to_orders = (inv_ord.groupby("ocel:oid")["ocel:oid_2"]
                     .apply(lambda s: sorted(set(s))).to_dict())
    pay_to_orders = {m: inv_to_orders.get(v, [])
                     for m, v in zip(pay_inv["ocel:oid"], pay_inv["ocel:oid_2"])}

    lookup = {"package": pkg_to_orders, "delivery": del_to_orders,
              "invoice": inv_to_orders, "payment": pay_to_orders}
    path = {"package": "package->item->order",
            "delivery": "delivery->package->item->order",
            "invoice": "invoice->order",
            "payment": "payment->invoice->order"}

    observed = set(zip(relations_df["ocel:eid"], relations_df["ocel:oid"]))
    out = []
    for _, row in relations_df.iterrows():
        table = lookup.get(row["ocel:type"])
        if table is None:
            continue
        for order_id in table.get(row["ocel:oid"], []):
            if (row["ocel:eid"], order_id) in observed:
                continue
            out.append({
                "ocel:eid": row["ocel:eid"],
                "ocel:activity": row["ocel:activity"],
                "ocel:timestamp": row["ocel:timestamp"],
                "ocel:oid": order_id,
                "ocel:type": "order",
                "ocel:qualifier": "derived_order",
                "derived": True,
                "derivation_path": path[row["ocel:type"]],
            })
    return pd.DataFrame(out).drop_duplicates(
        subset=["ocel:eid", "ocel:oid"]).reset_index(drop=True)


relations_propagated = propagate_orders_via_o2o(relations, o2o)


# ---------------------------------------------------------------------------
# F. VALIDATION
# ---------------------------------------------------------------------------
def validate(events, objects, relations, o2o) -> None:
    assert events["ocel:eid"].is_unique, "duplicate event ids"
    assert objects["ocel:oid"].is_unique, "duplicate object ids"

    eids, oids = set(events["ocel:eid"]), set(objects["ocel:oid"])

    orphan_e = set(relations["ocel:eid"]) - eids
    assert not orphan_e, f"orphan event ids in relations: {sorted(orphan_e)}"

    orphan_o = set(relations["ocel:oid"]) - oids
    assert not orphan_o, f"orphan object ids in relations: {sorted(orphan_o)}"

    orphan_o2o = (set(o2o["ocel:oid"]) | set(o2o["ocel:oid_2"])) - oids
    assert not orphan_o2o, f"orphan object ids in o2o: {sorted(orphan_o2o)}"

    assert (o2o["ocel:oid"] != o2o["ocel:oid_2"]).all(), "self-loop in o2o"

    # every event participates in at least one relation; every object too
    assert eids == set(relations["ocel:eid"]), "event without any E2O relation"
    assert oids == set(relations["ocel:oid"]), "object without any E2O relation"

    # activity / timestamp consistency between events and relations
    merged = relations.merge(events[["ocel:eid", "ocel:activity",
                                     "ocel:timestamp"]],
                             on="ocel:eid", suffixes=("", "_ev"))
    assert (merged["ocel:activity"] == merged["ocel:activity_ev"]).all(), \
        "activity mismatch between events and relations"
    assert (merged["ocel:timestamp"] == merged["ocel:timestamp_ev"]).all(), \
        "timestamp mismatch between events and relations"

    # object type consistency
    tmap = dict(zip(objects["ocel:oid"], objects["ocel:type"]))
    assert (relations["ocel:oid"].map(tmap) == relations["ocel:type"]).all(), \
        "type mismatch between objects and relations"

    # no duplicate relation rows / no duplicate o2o rows
    assert not relations.duplicated(
        subset=["ocel:eid", "ocel:oid", "ocel:qualifier"]).any(), \
        "duplicate E2O rows"
    assert not relations.duplicated(subset=["ocel:eid", "ocel:oid"]).any(), \
        "same object attached twice to one event with different qualifiers"
    assert not o2o.duplicated(
        subset=["ocel:oid", "ocel:oid_2", "ocel:qualifier"]).any(), \
        "duplicate O2O rows"

    # timezone awareness
    assert events["ocel:timestamp"].dt.tz is not None, "naive timestamps"
    assert relations["ocel:timestamp"].dt.tz is not None, "naive timestamps"

    # one qualifier per (activity, type) -- vocabulary consistency
    vocab = relations.groupby(["ocel:activity", "ocel:type"])[
        "ocel:qualifier"].nunique()
    assert (vocab == 1).all(), "inconsistent qualifier vocabulary"

    # derived rows must never leak into the source relations table
    assert "derived" not in relations.columns, "derived flag leaked into E2O"

    print("validation: OK -- "
          f"{len(events)} events, {len(objects)} objects, "
          f"{len(relations)} E2O rows, {len(o2o)} O2O rows, "
          f"{len(relations_propagated)} derived (excluded) rows")


validate(events, objects, relations, o2o)


# ---------------------------------------------------------------------------
# G. OCEL CONSTRUCTION AND BASIC STATISTICS
# ---------------------------------------------------------------------------
# VERSION-SENSITIVE LINE -- isolated on purpose.
# If this PM4Py build's OCEL.__init__ has no `o2o` keyword, replace with:
#     ocel = OCEL(events=events, objects=objects, relations=relations)
#     ocel.o2o = o2o
# The data semantics are identical either way.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)

print("\n--- activity frequencies ---")
print(events["ocel:activity"].value_counts())

print("\n--- object-type frequencies (objects) ---")
print(objects["ocel:type"].value_counts())

print("\n--- object-type frequencies (E2O rows) ---")
print(relations["ocel:type"].value_counts())

print("\n--- pm4py.ocel_get_object_types ---")
print(pm4py.ocel_get_object_types(ocel))

print("\n--- pm4py.ocel_object_type_activities ---")
for otype, acts in pm4py.ocel_object_type_activities(ocel).items():
    print(f"{otype:9s} -> {sorted(acts)}")


# ---------------------------------------------------------------------------
# H. FLATTENED VIEWS PER OBJECT TYPE
# ---------------------------------------------------------------------------
FLATTEN_TYPES = ["order", "package", "delivery", "invoice"]

flat_logs, dfgs, skeletons = {}, {}, {}

for otype in FLATTEN_TYPES:
    flat = pm4py.ocel_flattening(ocel, otype)
    flat_logs[otype] = flat
    dfgs[otype] = pm4py.discover_dfg(flat)          # (dfg, start, end)
    skeletons[otype] = pm4py.discover_log_skeleton(
        flat, noise_threshold=0.0)

    dfg, start, end = dfgs[otype]
    print(f"\n=== flattened on '{otype}' "
          f"({flat['case:concept:name'].nunique()} cases, "
          f"{len(flat)} events) ===")
    print("  start:", dict(start), " end:", dict(end))
    for (a, b), c in sorted(dfg.items(), key=lambda kv: -kv[1]):
        print(f"  {a} -> {b} : {c}")


# ---------------------------------------------------------------------------
# I. OBJECT-CENTRIC STRUCTURES
# ---------------------------------------------------------------------------
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocpn = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

print("\n--- OTG (object-type graph) ---")
print(otg)

print("\n--- ET-OT graph (event type / object type) ---")
print(etot)

print("\n--- object-interactions summary (head) ---")
print(interactions.head(20))

print("\n--- OC Petri net: object types with a subnet ---")
print(sorted(ocpn.get("petri_nets", {}).keys())
      if isinstance(ocpn, dict) else type(ocpn))


# ---------------------------------------------------------------------------
# J. OPTIONAL VISUALIZATION (commented: needs Graphviz / a display)
# ---------------------------------------------------------------------------
# pm4py.view_ocdfg(ocdfg, annotation="frequency", format="png")
# pm4py.view_ocpn(ocpn, format="png")
# pm4py.save_vis_ocdfg(ocdfg, "ocdfg.png")     # relative path only
# pm4py.save_vis_ocpn(ocpn, "ocpn.png")


# ---------------------------------------------------------------------------
# Illustrative use of the DERIVED table -- clearly labelled as analytical
# ---------------------------------------------------------------------------
print("\n--- ANALYTICAL (derived, not source) event->order propagation ---")
if len(relations_propagated):
    print(relations_propagated[["ocel:eid", "ocel:activity", "ocel:oid",
                                "derivation_path"]].to_string(index=False))
```

## 3. Data-model audit

**Objects per type**

| type | objects | count |
|---|---|---|
| order | O100, O200 | 2 |
| item | I1, I2, I3 | 3 |
| package | P1, P2 | 2 |
| delivery | D1, D2 | 2 |
| invoice | V1 | 1 |
| payment | M1, M2 | 2 |

**O2O qualifiers and cardinality**

| qualifier | direction | rows | pattern |
|---|---|---|---|
| `contains` | order → item | 3 | 1:N (O100→2, O200→1) |
| `packs` | package → item | 3 | 1:N, and **cross-order** for P1 |
| `carries` | delivery → package | 2 | 1:1 |
| `bills` | invoice → order | 2 | 1:N (one invoice, two orders) |
| `partially_settles` | payment → invoice | 1 | M1→V1 |
| `completes_settlement` | payment → invoice | 1 | M2→V1 |
| **total** | | **11** | |

**Activity → object types touched** (E2O rows in parentheses)

| activity | # events | object types | E2O rows |
|---|---|---|---|
| Create Order | 2 | order | 2 |
| Add Item | 3 | order, item | 6 |
| Reserve Stock | 1 | order, item | 4 |
| Pack Package | 2 | order, item, package | 8 (e7: 5, e8: 3) |
| Dispatch Package | 2 | package, delivery | 4 |
| Issue Invoice | 1 | order, invoice | 3 |
| Record Payment | 2 | payment, invoice | 4 |
| Confirm Delivery | 2 | delivery | 2 |
| Close Order | 2 | order | 2 |
| **total** | **17** | | **35** |

**Consequential events.**
- **e6 (Reserve Stock)** and **e7 (Pack Package, P1)** are the convergence hotspots: each is attached to both orders and to items from both orders. Flattening on `order` duplicates each of them into two cases; flattening on `item` duplicates them across I1 and I3. Any frequency statistic computed on a flattened order log will therefore double-count them.
- **e11 (Issue Invoice)** is a second convergence point (one event, two orders); it is also the only place where the invoice enters the order lifecycle.
- **e12 / e15 (Record Payment)** are divergence-relevant: two independent payments hang off a single invoice, so the invoice case contains a repeated activity whose repetitions belong to *different* payment objects.
- **e8 (Pack Package P2)** is the deliberate asymmetry: a single-order pack event that makes P1 vs P2 structurally different, which is exactly what the OC-DFG should expose.

## 4. Expected flattened behavior

### Flatten on `order` — 2 cases

- **Trace shape.** O100: `Create Order → Add Item → Add Item → Reserve Stock → Pack Package → Pack Package → Issue Invoice → Close Order` (8 events). O200: `Create Order → Add Item → Reserve Stock → Pack Package → Issue Invoice → Close Order` (6 events).
- **Copied shared events.** e6, e7 and e11 appear in both cases — three events, six rows. 14 flattened rows from 17 source events, of which only 11 distinct events are covered.
- **Omitted lifecycle.** `Dispatch Package` and `Confirm Delivery` are **absent** from every order case, because we did not create direct E2O links for logistics events. Payments are also absent (they attach to the invoice). An order case therefore looks like it never ships and never gets paid.
- **Likely DFG edges.** `Create Order→Add Item`, `Add Item→Add Item` (O100 only), `Add Item→Reserve Stock`, `Reserve Stock→Pack Package`, `Pack Package→Pack Package` (O100 only), `Pack Package→Issue Invoice`, `Issue Invoice→Close Order`. Start = `Create Order` ×2, end = `Close Order` ×2.
- **Misleading interpretations.** (a) "Reserve Stock happens once per order" — it happens once in total. (b) "Packing occurs twice for O100" — e7 and e8 are different packages, not a repeat. (c) "Invoicing follows packing per order" — one invoice covers both. (d) Order cycle time (08:00→10:35 for O100) silently excludes the delivery it never saw.

### Flatten on `package` — 2 cases

- **Trace shape.** P1: `Pack Package → Dispatch Package` (e7, e9). P2: `Pack Package → Dispatch Package` (e8, e10). Two identical two-step traces.
- **Copied shared events.** None; each package touches disjoint events.
- **Omitted lifecycle.** `Confirm Delivery` is missing (it attaches to the delivery, not the package), as is everything upstream (order creation, item addition, stock reservation) and everything financial. The fact that P1 mixes items from two orders is completely invisible.
- **Likely DFG edges.** A single edge `Pack Package → Dispatch Package` with frequency 2; start `Pack Package` ×2, end `Dispatch Package` ×2.
- **Misleading interpretations.** The view suggests a trivial, perfectly uniform two-step process and a ~1h packaging lead time, hiding that P1 is the cross-order convergence object and the reason O100 and O200 are coupled.

### Flatten on `delivery` — 2 cases

- **Trace shape.** D1: `Dispatch Package → Confirm Delivery` (e9 10:00, e13 13:00 — 3 h). D2: `Dispatch Package → Confirm Delivery` (e10 10:15, e14 next day 09:00 — ~22.75 h).
- **Copied shared events.** None.
- **Omitted lifecycle.** Packing, ordering, invoicing, payment. The delivery view cannot say *what* was delivered or *for whom*.
- **Likely DFG edges.** `Dispatch Package → Confirm Delivery` ×2 only.
- **Misleading interpretations.** The mean transit time (~13 h) averages two very different situations from n=2; and because deliveries are disconnected from orders, one might wrongly conclude the delivery process is independent of order fulfilment.

### Flatten on `invoice` — 1 case

- **Trace shape.** V1: `Issue Invoice → Record Payment → Record Payment` (e11, e12, e15).
- **Copied shared events.** None *within* the flattening, but e11 is shared with both order cases — the same event is counted in three flattened logs.
- **Omitted lifecycle.** No order, packing, or delivery context; and the two `Record Payment` occurrences lose their distinguishing object (M1 vs M2). The amounts (100 + 150) survive only if the event attributes are carried into the flattened log.
- **Likely DFG edges.** `Issue Invoice → Record Payment` ×1 and `Record Payment → Record Payment` ×1.
- **Misleading interpretations.** The `Record Payment → Record Payment` self-loop reads as a rework/retry loop, when it is actually two distinct partial payments. A single-case log also invites over-generalisation: any "model" discovered here describes one invoice.

### Why flattening on `payment` is particularly weak

Each payment object touches exactly one event: M1 → e12, M2 → e15. The flattened log is two single-event cases, each with the trace `⟨Record Payment⟩`. There are **no directly-follows edges at all**, the DFG is empty apart from start/end counts, the log skeleton degenerates (every constraint is vacuously satisfied), and no ordering, duration, or conformance information can be extracted. Everything interesting about a payment here — that it settles V1, that V1 bills two orders, that M1 is partial and M2 completes — lives in O2O and in event attributes, not in the payment's own control flow. Payment is a legitimate *object type* but a useless *case notion* in this dataset.

## 5. Expected object-centric structures

**OC-DFG.** One directly-follows graph per object type, drawn over a shared activity set. Expect:
- an *order* strand `Create Order → Add Item → Reserve Stock → Pack Package → Issue Invoice → Close Order`, with `Add Item→Add Item` and `Pack Package→Pack Package` self-edges contributed by **O100** only, and a shorter path from **O200**;
- a *package* strand `Pack Package → Dispatch Package` and a *delivery* strand `Dispatch Package → Confirm Delivery`, which together stitch the logistics chain that no single flattening shows;
- an *invoice* strand `Issue Invoice → Record Payment → Record Payment` and a *payment* strand with no edges at all (only start/end markers on `Record Payment` for **M1** and **M2**).
Crucially, `Pack Package` carries order-, item- **and** package-typed arcs, so **P1**'s event (e7) is where the order strands of **O100** and **O200** visibly merge — the arc multiplicities on that node are the signature of convergence, and the OC-DFG shows it without duplicating the event.

**OTG (object-type graph).** Expect edges reflecting co-occurrence/relatedness among types: order–item, order–package, item–package (all via e7/e8), package–delivery (e9/e10), order–invoice (e11), invoice–payment (e12/e15). Order–delivery and order–payment edges should be **absent** under our source-faithful E2O policy — a direct, readable consequence of the modelling decision, and the clearest signal that logistics/financial linkage to orders is structural rather than observed.

**ET–OT graph.** A bipartite activity × object-type map, essentially the audit table of §3: `Reserve Stock` touches {order, item}; `Pack Package` touches {order, item, package}; `Dispatch Package` touches {package, delivery}; `Issue Invoice` touches {order, invoice}; `Record Payment` touches {payment, invoice}; `Confirm Delivery` touches {delivery}; `Create Order`/`Close Order` touch {order}. Expect the *cardinalities* to be informative: `Pack Package` has up to two orders and two items per event (**e7**), whereas most activities have exactly one object per type — the 1-vs-2 asymmetry is the convergence fingerprint of **P1**.

**Object-centric Petri net.** Expect a per-type subnet (order, item, package, delivery, invoice, payment) sharing transitions for activities that touch several types, with variable/double arcs where an activity consumes several objects of one type at once (`Pack Package` on **O100** and **O200**; `Reserve Stock` on I1 and I3). This model is **not uniquely determined**: with 17 events and 12 objects the discovery is severely under-constrained, the choice of underlying per-type discovery algorithm and its filtering thresholds changes the resulting subnets, and the placement of variable arcs is a modelling convention rather than a fact. Several structurally different nets fit this log equally well; the net should be read as one plausible summary, not as *the* process.

**Object-interactions summary.** Expect one row per co-occurring object pair, at minimum: (O100, I1), (O100, I2), (O200, I3) from `Add Item`; (I1, I3), (O100, I3), (O200, I1) and **(O100, O200)** from `Reserve Stock` and `Pack Package`; (P1, I1), (P1, I3), (P1, O100), (P1, O200) from e7; (P2, I2), (P2, O100) from e8; (P1, D1), (P2, D2) from dispatch; (V1, O100), (V1, O200) from e11; (V1, M1), (V1, M2) from the payments. The **(O100, O200)** pair is the headline: two orders that share no order-level identifier nevertheless interact three times (e6, e7, e11), and **P1** and **V1** are the objects that create that coupling. Note that **M1** and **M2** never co-occur with each other (different events) and never co-occur with any order — again a direct consequence of the E2O policy.

## 6. Modeling alternatives

**(a) Source-minimal E2O.** Attach to each event only the object(s) the activity names: `Reserve Stock` → items only; `Pack Package` → package + items; `Issue Invoice` → invoice only; `Close Order` → order. *Effect:* the order flattening collapses to `Create Order → Add Item(+) → Close Order`; the OTG loses the order–item edge on packing and the order–invoice edge; the OC-DFG order strand becomes short and clean and the item strand carries the fulfilment logic. Convergence largely disappears from the order view and reappears in the item view. Business story unchanged — the invoice still bills both orders, it is just recorded only in O2O.

**(b) Full operational involvement.** Attach every structurally implicated object to every event: dispatch and delivery confirmation also carry the items and orders; payments also carry both orders. *Effect:* the order flattening becomes rich — `… → Dispatch Package → Dispatch Package → Confirm Delivery → Confirm Delivery → Record Payment → Record Payment → Close Order` for O100 — and order cycle time finally spans the real end-to-end process. Cost: relation count roughly doubles, every logistics event is duplicated across order cases, frequency and performance statistics on the order view systematically over-count, and the log no longer distinguishes "the source system recorded the order on this dispatch" from "we inferred it".

**(c) O2O-propagated analytical relations.** Keep `relations` source-faithful (our choice) and generate the extra links on demand, flagged `derived=True`, as `relations_propagated` does. *Effect:* you can produce view (b) for a specific question — e.g. order-level lead time including delivery — while any default discovery run stays honest. Discovery results become a *function of an explicitly chosen propagation policy* rather than a property of the log; the same underlying business story supports both a narrow and a wide order view, and the difference is auditable.

**(d) Additional variant — qualifier-typed richness.** Attach the wide set of objects but distinguish them by qualifier (`primary` vs `context`), then filter by qualifier at analysis time. *Effect:* a single log serves both readings; the risk is that tools ignoring qualifiers will silently behave like (b).

## 7. Failure modes

1. **Relation inflation.** Attaching every reachable object to every event (policy b applied blindly) multiplies E2O rows, makes almost every event shared, and turns flattened frequency counts and OC-DFG arc weights into artefacts of the modelling policy rather than measurements. Mitigation: a stated, documented attachment rule plus the row-count audit in §3.
2. **Missing direct E2O links.** Our own policy's cost: no order ever "sees" a dispatch or a payment, so order-level SLA, on-time-delivery and days-to-cash cannot be computed from `relations` alone. A reader who does not check the ET–OT graph may conclude such events do not exist for orders. Mitigation: state the omission and expose `relations_propagated`.
3. **Treating O2O propagation as observation.** Writing derived rows back into `relations` destroys the distinction between recorded and inferred, and the derivation quietly becomes unfalsifiable. Mitigation: separate frame, `derived` flag, `derivation_path`, and an assertion that no `derived` column exists in `relations`.
4. **Duplicate shared events after flattening.** e6, e7 and e11 each become two rows in the order-flattened log. Summing durations, counting activity occurrences, or computing "work performed" over that log double-counts them. Mitigation: always count distinct `ocel:eid`, never flattened rows.
5. **Ambiguous payment allocation.** M1 (100) and M2 (150) settle V1, which bills both orders. Splitting 250 across O100 and O200 requires a rule (line-item value, pro-rata, FIFO) that the narrative does not supply. Any per-order revenue figure is therefore an assumption, not a fact. Mitigation: keep amounts as invoice-level event attributes and refuse to allocate silently.
6. **Overly short Payment traces.** Payment-flattened cases have one event each, yielding an empty DFG and a vacuous log skeleton. Reporting "the payment process has no deviations" from that is meaningless. Mitigation: treat payment as an object type only, and analyse payment behaviour through the invoice view.
7. **Constructor / API version mismatch.** `OCEL(..., o2o=...)`, `discover_otg`, `discover_etot` and `ocel_objects_interactions_summary` are not present or not identically signatured in all PM4Py versions; return shapes (dict vs tuple vs DataFrame) also vary. Mitigation: the constructor is isolated on one commented line with an explicit fallback, and downstream code should not assume a return shape without checking.
8. **False total order for same-time events.** All 17 timestamps here are distinct, so no ties occur — but the pipeline sorts by timestamp and any future addition with an identical timestamp would receive an arbitrary, implementation-dependent order that discovery would report as a real directly-follows edge. Mitigation: keep a stable secondary sort key (`ocel:eid`) and never interpret sub-resolution orderings as causal.
9. **Convergence-blind performance metrics.** Because e7 belongs to two orders, "packing time per order" computed on the flattened log counts the same 9:00 packing operation twice and understates true throughput.
10. **Qualifier drift.** If the same activity/type pair ever gets two qualifiers, qualifier-based filters silently drop rows. The `(activity, type) → 1 qualifier` assertion in `validate` catches this.
11. **Orphan and type-mismatch defects.** A relation row pointing at an unlisted object, or listing the wrong `ocel:type` for a known object, corrupts every type-partitioned view; both are asserted against.
12. **Over-reading the object-centric Petri net.** With 17 events, discovery is under-constrained and the net is one of many fitting models; presenting it as *the* discovered process is a substantive error.

## 8. Final semantic checks

A reviewer can verify these by eye in the generated tables:

1. **Counts.** `events` has exactly 17 rows with 17 distinct `ocel:eid`; `objects` has exactly 12 rows with 12 distinct `ocel:oid` split 2/3/2/2/1/2 across order/item/package/delivery/invoice/payment; `o2o` has exactly 11 rows; `relations` has exactly 35 rows.
2. **The joint reservation.** Event `e6` (`Reserve Stock`, 08:30) has exactly four relation rows — `O100`, `O200`, `I1`, `I3` — and no rows for `I2`, `P1` or `P2`. It is a single event, not two.
3. **The cross-order package.** `o2o` shows `P1 --packs--> I1` and `P1 --packs--> I3`, while `contains` maps `I1` to `O100` and `I3` to `O200`. Following those two hops must land on two *different* orders; that is the sole structural reason O100 and O200 are coupled through logistics.
4. **Invoice and payments.** `V1 --bills--> O100` and `V1 --bills--> O200` (two rows), and exactly two payment rows into `V1` with distinct qualifiers `partially_settles` (M1) and `completes_settlement` (M2). `events` carries `amount` 100.0 on `e12` and 150.0 on `e15`, and **no** object of type "amount" exists in `objects`.
5. **Timestamp and activity fidelity.** For every row of `relations`, joining on `ocel:eid` against `events` reproduces the same `ocel:activity` and the same tz-aware `ocel:timestamp`; e.g. all five rows of `e7` read `Pack Package` / `2026-04-06 09:00:00+00:00`. All timestamps are UTC-aware, and the two events on 2026-04-07 (e14 09:00, e15 10:00, e16 10:30, e17 10:35) are strictly ordered after all 2026-04-06 events.
6. **Deliberate absences.** No relation row links an `order` to `Dispatch Package`, `Confirm Delivery` or `Record Payment`, and no row links a `payment` to anything but `e12`/`e15`. These absences are the E2O policy, and any order-level shipping or payment link found in an analysis must come from the separately-flagged `relations_propagated`.
7. **Closure and coverage.** Every event id appears in `relations` at least once and every object id appears in `relations` at least once — no dangling events, no objects that exist only in O2O. `O200` closes (`e16`, 10:30) strictly before `O100` (`e17`, 10:35), matching the narrative's inverted closing order.
8. **Qualifier discipline.** Grouping `relations` by (`ocel:activity`, `ocel:type`) yields exactly one qualifier per group, and every qualifier used appears in the §1 vocabulary table — nothing more, nothing less.
