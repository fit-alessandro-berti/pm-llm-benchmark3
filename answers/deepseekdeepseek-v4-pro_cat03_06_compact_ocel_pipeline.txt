  - `Invoice`  `Order` : `bills`
  - `Payment`  `Invoice` : `partially_settles`

- **Logistics and financial events vs. Orders/Items**:  
  Dispatch and confirm-delivery events relate **only** to Package and/or Delivery objects. Payment events relate **only** to Payment and Invoice. This avoids overpropagation while still allowing miners to derive indirect involvement through O2O traversal.  
  **Tradeoff**: Adding direct Order/Item links to logistics events would make every downstream event “aware” of the originating order, enabling simpler flattened views but blurring the distinction between observed facts and inferred context.

- **Preventing propagation confusion**:  
  The `relations` table contains **exclusively** sourcesystem observations (what the process execution directly recorded). Objecttoobject (O2O) links store structural facts separately. Any analytical propagation (e.g., “D1 therefore relates to O100”) is performed by discovery algorithms later; it is never written back into `relations`. This keeps the audit trail clean.

- **PM4Py version assumption**:  
  The constructor `OCEL(events=…, objects=…, relations=…, o2o=…)` is expected to accept DataFrames with the `ocel:`prefixed columns specified in OCEL 2.0.  
  *If a different PM4Py version requires plain `event_id`, `event_activity`, … instead of `ocel:eid`, … the column names can be renamed just before the constructor call without altering semantics.* This adjustment is noted in the code.

## 4. Expected flattened behavior

### Order flattening
- **Trace shape**: Two traces (one per Order).  
  O100: `Create Order  Add Item (I1)  Add Item (I2)  Reserve Stock  Pack Package (P1)  Pack Package (P2)  Issue Invoice  Close Order`.  
  O200: `Create Order  Add Item (I3)  Reserve Stock  Pack Package (P1)  Issue Invoice  Close Order`.  
- **Copied shared events**: `Reserve Stock` appears in both traces; `Pack Package (P1)` also appears in both.  
- **Omitted lifecycle**: Dispatch, delivery confirmations, and payments are dropped.  
- **Likely DFG edges**:  
  O100: `Create Order  Add Item`, `Add Item  Reserve Stock`, `Reserve Stock  Pack Package`, …, `Issue Invoice  Close Order`.  
  O200: similar but after `Add Item` it goes directly to `Reserve Stock` (since only one item).  
- **Misleading interpretations**: Flattening suggests each order had its *own* reserve and pack steps, hiding the true shared nature. The fact that P1 carried items from both orders is invisible.

### Package flattening
- **Trace shape**: Two traces (one per Package).  
  P1: `Pack Package  Dispatch Package`.  
  P2: `Pack Package  Dispatch Package`.  
- **Copied shared events**: None, because `Pack Package` for P1 is already assigned to P1.  
- **Omitted lifecycle**: Orders, invoices, payments, delivery confirmations.  
- **DFG**: Simple linear sequences `Pack -> Dispatch` with a possible selfloop if many packages.  
- **Misleading**: The DFG captures only the logistics of the package, missing that P1 dispatches items from two different orders.

### Delivery flattening
- **Trace shape**: Two traces.  
  D1: `Dispatch Package (P1)  Confirm Delivery`.  
  D2: `Dispatch Package (P2)  Confirm Delivery`.  
- **Copied shared events**: `Dispatch Package` is mapped to the delivery; no duplication.  
- **Omissions**: Packing, invoicing, payments.  
- **DFG**: `Dispatch Package  Confirm Delivery`.  
- **Misleading**: Gives the illusion of a purely sequential delivery lifecycle; it does not show that D1 carries a package that mixes items from two orders.

### Invoice flattening
- **Trace shape**: One trace (Invoice V1):  
  `Issue Invoice  Record Payment (M1)  Record Payment (M2)`.  
- **Copied events**: `Issue Invoice` is the only event with Invoice involvement; payments are reused.  
- **Omissions**: All order and delivery work.  
- **DFG**: `Issue Invoice  Record Payment`, `Record Payment  Record Payment` (two successive payments).  
- **Misleading**: Suggests an incomplete picture where invoice closure is missing; the total amount settled is visible only as two separate payment amounts, not as an aggregated settlement.

### Why flattening on Payment would be particularly weak
- **Payment traces**: M1: `Record Payment` alone; M2: `Record Payment` alone. Each trace contains exactly one event.  
- There is no lifecycle beyond the payment record, no final settlement marker.  
- DFGs would be empty or trivial.  
- The connection between multiple payments and the invoice (V1) would be lost; a tracebased miner cannot detect that two oneevent traces should be correlated.

## 5. Expected object-centric structures

- **OCDFG**: Will show an activitygraph annotated with object types.  
  - `Create Order` (Order)  `Add Item` (Order, Item)  …  
  - The shared `Reserve Stock` will be a node labelled with both Order and Item.  
  - Crucially, `Pack Package` will appear as a node that involves Orders **O100 and O200**, Items **I1, I3**, and Package **P1**. This reveals the crossorder convergence that flattening hides.  
  - Financial activities (`Issue Invoice`, `Record Payment`) will form a separate cluster anchored on Invoice V1 and Payment M1/M2.

- **OTG (ObjectType Graph)**: Shows relationships among object types.  
  - Edges represent object interactions (e.g., Order–Item from `Add Item`, Package–Item from `Pack Package`, Delivery–Package from `Dispatch Package`, Invoice–Payment from `Record Payment`).  
  - Will highlight that Order, Item, Package, Delivery form a logistics supply chain, while Invoice and Payment form a financial subgraph that connects to Order through `Issue Invoice`.

- **ET–OT (EventType to ObjectType)**: Maps each activity to the set of object types it touches.  
  - `Reserve Stock` touches Order and Item, confirming it is a shared event.  
  - `Dispatch Package` touches only Package and Delivery, reinforcing that downstream logistics are decoupled from Orders.

- **Objectcentric Petri net**:  
  - In contrast to a traditional Petri net, places are typed by object.  
  - The net will contain a **convergence structure** where the tokens for O100 and O200 meet at a transition representing `Reserve Stock` or `Pack Package P1`.  
  - The net will faithfully represent that `P1` requires the presence of both `I1` (from O100) and `I3` (from O200).  
  - Payment records M1 and M2 will be separate transitions that both consume from a place for `V1` (Invoice), reflecting partial settlement.

- **Objectinteractions summary**: A table showing, for each pair of objects, the events in which they cooccur.  
  - P1 cooccurs with I1, I3, O100, O200.  
  - V1 cooccurs with O100, O200.  
  - M1 cooccurs only with V1; M2 cooccurs only with V1.  
  - This table will clearly show that the invoice V1 is the only object linking the two payments.

## 6. Modeling alternatives

1. **Sourceminimal relations**  
   - Every event is linked **only** to the objects it directly manipulates (e.g., `Dispatch Package` relates only to P1 and D1, no Orders).  
   - **Effect**: All indirect involvement must be derived through O2O traversal; the OCDFG will lack direct Order links, making flattened views very sparse. The Petri net still captures convergence if the miner uses O2O, but simpler analyses like DFG on Order flattening might lose the `Pack Package` step altogether (because P1 belongs to a Package, not an Order). This is the cleanest separation but may be too austere for some analytical questions.

2. **Full operational involvement**  
   - Every event that involves an object through any reachable O2O path is explicitly connected. For instance, `Dispatch Package P1` would also directly link to O100 and O200, and even to I1 and I3.  
   - **Effect**: Flattening on Order would show `Dispatch Package` as an event, making the trace richer but blurring the distinction between direct observation and inference. Discovery algorithms would see a denser, more heavily connected graph, possibly obscuring the true sharedevent pattern.

3. **O2Opropagated analytical relations** (stored in relations as extra rows)  
   - After building the sourceminimal set, we would algorithmically add E2O rows for every object reachable from the original objects via one or more O2O hops, labeling them with a distinct qualifier (e.g., `derived`).  
   - **Effect**: All downstream miners, both objectcentric and flattening, would see the propagated links as if they were original. This simplifies analysis but breaks auditability; a reviewer cannot tell which relations were observed and which were inferred. Discovery results would be highly inflated, showing many “fake” interactions.

All three alternatives preserve the same business story; they only differ in how much of the objectcentric structure is made explicit in the `relations` table.

---

## 7. Failure modes

1. **Relation inflation** – Adding propagated relations (e.g., linking D1 directly to O100) causes discovery algorithms to treat inference as observation, leading to an overly connected OTG and a bloated OCDFG where every logistics event appears related to every upstream order.

2. **Missing direct E2O links** – If `Reserve Stock` is linked only to Items but not to Orders, the crucial convergence point between O100 and O200 disappears from the Order view, and flattening would show two independent traces with no shared step.

3. **Treating O2O propagation as observation** – If a user runs a custom propagation script and stores the result in `relations` without documenting the qualifier, later analyses cannot distinguish source facts. The OTG would contain edges that are really structural (e.g., `Order  Package`) instead of eventdriven.

4. **Duplicate shared events after flattening** – Flattening on Order produces two copies of `Reserve Stock` and `Pack Package (P1)`. A naive tracevariant analysis will report two variants, obscuring the fact that the orders actually shared those events. Performance metrics based on variants may misjudge process uniformity.

5. **Ambiguous payment allocation** – Since no direct O2O links exist from Payment to Order, flattening on Order drops payments entirely. A financial analyst might mistakenly conclude that payments are missing from the process, rather than understanding that they were recorded against a shared invoice.

6. **Overly short Payment traces** – Flattening on Payment yields two traces of length one. Traditional process miners (e.g., inductive miner) cannot construct a meaningful model for such logs, and conformance checking is impossible.

7. **Constructor/API version mismatch** – Some PM4Py versions expect column names without the `ocel:` prefix (e.g., `event_id`, `event_activity`). Using the prefixed names will cause the OCEL constructor to fail silently or misinterpret columns. The pipeline must rename accordingly; if the adjustment is not made, the whole analysis crashes.

8. **False total order from timestamps** – Although this dataset has unique, increasing timestamps, many real logs have ties. Analysts might assume that the OCDFG or Petri net ordering respects the recorded order exactly. In reality, sametime events are concurrent, and miners should treat them as such. A failure to recognise this yields a sequential model that overconstrains the behaviour.

## 8. Final semantic checks
