## 6. Candidate Site B intervention

**Modified intervention: lawful segmented concurrency with blocked-state control.**

Eligibility rules:

1. **Class D — digital/no-originals cases:** no statutory originals requirement and documents available at registration. These cases may receive full Identity Check and Document Check concurrency.
2. **Class O — originals-required cases:** Originals Receipt and Identity Check may begin concurrently after Register. Document Check may be created in a blocked state but must not be worked until Originals Receipt is complete.
3. **Class L — legal-review cases:** public-sector or high-value cases follow the same verification rules as Class D or O, but Legal Review remains mandatory after Assessment before final decision.
4. Initial pilot should restrict Class D to low/medium complexity and non-legal or low-legal-pressure volume. Class O should enter second, using Identity/Originals overlap only. Legal-heavy cases should enter after downstream capacity is demonstrated.

Concurrent task rules:

- Register always precedes all other tasks.
- For Class D: create Identity Check and Document Check simultaneously.
- For Class O: create Identity Check and Originals Receipt simultaneously; create Document Check as blocked.
- Assessment cannot start until both Identity Check and Document Check are complete.
- Legal Review cannot be skipped where legally required.
- Request Supplement creates a new Document Check recheck and, if needed, a new Assessment task. Identity Check is not automatically repeated unless identity evidence is also deficient or expired.

Statutory prerequisites preserved:

- Original documents must be received before Document Check for originals-required cases.
- Legal Review remains mandatory for public-sector/high-value cases.
- Final Approve/Reject occurs only after all required reviews and rechecks are complete.
- No automatic decisioning based solely on elapsed time.

Queue and WIP controls:

- Pool-level CONWIP limits: initial maximum active tasks equal to approximately two to three open tasks per productive reviewer, adjusted after two weeks of queue data.
  - Identity: 4 reviewers, max 8–12 active tasks.
  - Document: 7 reviewers, max 14–21 active tasks.
  - Assessment: 3 assessors, max 6–9 active tasks.
  - Legal: 2 reviewers, max 4–6 active tasks.
- FIFO within priority class, except statutory deadlines and supplement rework.
- Daily huddle reviews blocked originals, Assessment queue, Legal queue, and supplement aging.
- Treatment cases are capped as a share of daily volume to avoid resource interference.

Resource responsibilities:

- Identity reviewers perform Identity Check only.
- Document reviewers perform Document Check and supplement rechecks.
- Assessors perform Assessment and reassessment after supplements.
- Legal reviewers perform Legal Review and issue Request Supplement with structured reason codes.
- Operations owner monitors WIP, queue age, and exception reports.

Legal-review and supplement loops:

- Legal Review outcome must be coded as Approve, Reject, or Request Supplement.
- Request Supplement must specify missing items and responsible document channel.
- Supplement rework receives priority over new Document Check work where SLA risk exists.
- If a case receives two supplements, it is escalated for root-cause review.
- Legal and Assessment repeat tasks are logged as distinct iterations, not overwrites.

Logging requirements:

- Event-time timestamps for Created, Claimed, Started, Blocked, Unblocked, Completed, and Returned.
- Separate fields for system event time and user entry time.
- Reason code whenever Document Check is blocked or unblocked.
- Legal outcome, supplement reason, and iteration number.
- Case ID, task ID, pool, reviewer ID, and eligibility class.

## 8. PM4Py model-construction code

```python
import pm4py

# ----------------------------------------------------------------------
# 1. Site A before and after process trees
# ----------------------------------------------------------------------

site_a_before = pm4py.parse_process_tree(
    "-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', "
    "X ( 'Approve', 'Reject' ), 'Notify' )"
)

site_a_after = pm4py.parse_process_tree(
    "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', "
    "X ( 'Approve', 'Reject' ), 'Notify' )"
)

net_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(site_a_before)
net_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(site_a_after)

# ----------------------------------------------------------------------
# 2. Site B candidate using POWL / strict partial order
#
# Important modeling note:
# A strict partial order can encode mandatory precedence and concurrency,
# but it does not naturally encode XOR choice, data-dependent eligibility,
# resource locks, or unbounded loops. The legal supplement loop below is
# therefore unrolled once as a conservative structural approximation.
# ----------------------------------------------------------------------

try:
    from pm4py.objects.powl.obj import StrictPartialOrder, Activity
except ImportError:
    # Some PM4Py versions expose Activity in a neighboring object module.
    from pm4py.objects.powl.obj import StrictPartialOrder
    from pm4py.objects.process_tree.obj import Activity


def make_activity(name):
    """Create an Activity node tolerating minor PM4Py API differences."""
    try:
        return Activity(name=name)
    except TypeError:
        return Activity(name)


def build_strict_partial_order(activities, edges, initial="Register", final="Notify"):
    """
    Build a strict partial order from activities and mandatory precedence edges.
    Concurrency is represented by absence of a precedence constraint.
    """
    spo = StrictPartialOrder()
    nodes = {}

    for act_name in activities:
        node = make_activity(act_name)
        nodes[act_name] = node
        spo.add_node(node)

    for source, target in edges:
        spo.add_edge(nodes[source], nodes[target])

    # Some PM4Py POWL implementations expose explicit initial/final setters.
    for setter in ("set_initial", "set_initial_activity", "set_source"):
```

## 9. Recommendation

Recommendation: **conditional go**.

Site B should not copy Site A’s universal “create Identity Check and Document Check immediately after Register” rule. It should transfer the underlying mechanism: safely overlap independent verification work, reduce waiting before Assessment, and use queue huddles/WIP controls. The universal rule is unsafe because Document Check is legally impossible before originals receipt for 62% of cases, and Site B’s separate roles, single-owner case lock, and legal-review burden can turn front-end speed into downstream congestion.

The first pilot should admit only digital, no-originals, non-public/high-value or low-legal-risk claims. In that stratum, Identity Check and Document Check can truly run in parallel. The second eligible group should be originals-required cases, but only with Identity Check and Originals Receipt concurrent and Document Check blocked until originals arrive. Legal-review cases should enter only after assessment/legal capacity is shown to absorb earlier completions.

Expected benefits are modest, not Site A’s nine-hour confounded reduction: perhaps 2–4 hours overall median improvement if the digital stratum responds like Site A, with larger gains in the treated digital subgroup. The principal risks are tail worsening, false overlap from back-entered timestamps, assessment/legal bottlenecks, and quality degradation through rework or appeals.

Expand only if the pilot shows true overlap rises substantially, waiting before Assessment falls, median improves without p90 worsening more than a small threshold, and rework/appeals remain stable. Modify if assessment or legal queues grow: add capacity, tighten WIP, or stagger eligibility. Abandon if true overlap cannot be implemented because of case locks, statutory misclassification occurs, p90 deteriorates materially, or quality metrics worsen.

## 10. Assumption register

1. **Identity and Document Check are operationally independent for eligible digital cases — needed because parallelization only saves time when neither task blocks the other — test by sampling task dependencies and reviewer interviews — if false, parallel work increases rework and interruptions.**

2. **Digital/no-originals cases truly have documents available at Register — needed to define the full-parallel eligible stratum — test document-channel fields and event-log timestamps — if false, the “digital” stratum is contaminated and gains are overstated.**

3. **Originals-required cases can lawfully run Identity Check while Originals Receipt is pending — needed to create the only safe overlap for 62% of volume — test statutory rules and legal review guidance — if false, even Identity/Originals overlap must be restricted.**

4. **Site B can record concurrent tasks with event-time lifecycle data — needed to distinguish true overlap from back-entered overlap — test IT sandbox and audit sample — if false, measured success may be an artifact.**

5. **Assessment and Legal capacity can absorb faster front-end completion — needed to prevent bottleneck shift — test pool utilization and queue age during pilot — if false, median may improve while p90 worsens.**

6. **WIP limits and huddles can be implemented with high fidelity — needed because Site A’s effect is confounded with queue management — test huddle attendance, exception logs, and WIP compliance — if false, the pilot confounds parallelization with management changes.**

7. **Rework and appeal rates will remain stable under parallelization — needed to avoid trading speed for quality — test rework, supplement, and appeal metrics by arm — if false, the intervention should be modified or stopped.**

8. **Site A’s observed nine-hour reduction is not a clean causal estimate — needed to avoid overextrapolation — test by decomposing Site A waiting, service time, mix, staffing, and API effects — if false and the effect was larger/causal, Site B may still benefit, but pilot evidence remains necessary.**
