# Industrial Payment Process Conformance Review

## 1. Control-Objective Decomposition

FEP-1's core objective is to prevent one person from both initiating and authorizing an erroneous or fraudulent transfer. This decomposes into five threat scenarios:

### Threat 1: Unilateral Initiation of Unauthorized Payment
**Scenario:** One operator prepares a payment to an unauthorized, collusive, or fraudulent vendor without oversight.  
- **FEP-1 (Four-Eyes):** Prevents only if the second human independently validates vendor and amount.  
- **AV-2:** Can detect duplicate invoices, sanctions-list hits, new bank accounts. Cannot detect whether the vendor itself is unauthorized or whether goods/services were actually needed.  
- **MG-4:** Preventive if performed before settlement and includes independent review of invoice, PO, and receipt. Detective if performed after release but before settlement (can stop if manager rejects). Fails if rubber-stamped or if manager lacks independence.  
- **RA-7:** Detective only; corrective only if funds can be recalled (within ~24 hours).  
- **ED-1:** Permits single-operator relief under strict conditions; does not eliminate the objective—it relocates verification responsibility to pre-payment emergency authorization and post-payment audit.

### Threat 2: Unilateral Modification of Vendor Bank Account
**Scenario:** One operator changes an established vendor's bank account to a fraudster's account and releases the payment.  
- **FEP-1:** Prevents only if the second human verifies the bank account.  
- **AV-2:** Explicitly checks bank-account changes within seven days and can block or warn. Weak against collusion (both operator and fraudster have incentive to override).  
- **MG-4:** Preventive if manager reviews bank-account details before release and notices the change. Requires manager to be alert to the vendor's normal account.  
- **RA-7:** Detective after settlement; recovery window is ~24 hours.  
- **ED-1:** Condition 4 requires no bank-account change in the previous seven days; this is preventive through design constraint, not through independent judgment.

### Threat 3: Collusive Fraud Between Preparer and Releaser
**Scenario:** Two individuals who appear distinct in the log coordinate to approve a fraudulent payment. This includes shared workstations, shared credentials, or implicit understanding.  
- **FEP-1:** Nominally satisfied by distinct IDs, but control objective is compromised.  
- **AV-2:** Cannot detect collusion; a pass may lull independent review into false confidence.  
- **MG-4:** Can detect collusion only if the manager independently validates the underlying business case (goods, receipt, commercial reasonableness). A manager who merely checks that both operators are listed may miss collusion.  
- **RA-7:** Detective if audit compares the preparer's, releaser's, and manager's notes to identify inconsistencies.  
- **ED-1:** Does not address collusion; the single-operator exception is incompatible with collusion because only one person acts.

### Threat 4: Unilateral Override or Circumvention of Automated Controls
**Scenario:** One operator prepares a payment, AV-2 emits a warning, and the same operator overrides without independent judgment.  
- **FEP-1:** Violated directly.  
- **AV-2:** The warning is issued; the override is a failure of governance, not of AV-2 itself.  
- **MG-4:** Preventive if the manager who approves the override is independent and reviews the reason for the warning. Detective if approval occurs after release. Fails if manager is the operator's supervisor or peer with unresolved conflict.  
- **RA-7:** Detective.  
- **ED-1:** Does not address override governance.

### Threat 5: Undetected Control Failure or Absence
**Scenario:** AV-2 is unavailable, or a required step is skipped, and no compensating control operates in time.  
- **FEP-1:** Nominally may be satisfied (distinct users), but if both prepare and release without any validation, control objective is at risk.  
- **AV-2:** Absent or failed.  
- **MG-4:** Preventive if performed before settlement and covers the missing validation. Detective if performed after settlement.  
- **RA-7:** Detective only; corrective capacity depends on settlement timing and recall window.  
- **ED-1:** Permits single-operator payment under strict conditions, including that AV-2 was fully operational and passed. ED-1 is inapplicable if AV-2 is unavailable.

## 2. Equivalence and Sufficiency Test

### Structured Test for Compensating-Control Adequacy

A compensating package is **fully equivalent** to the four-eyes principle if it reliably prevents the control objective from being violated. A package is **partially equivalent** if it reduces the frequency or magnitude of violations below acceptable risk. A package is **merely mitigating** if it reduces exposure post-facto but does not prevent the violation. A package is **ineffective** if it does not address the primary threat.

**Key Dimensions:**

1. **Timing and Irrevocability**
   - Manager approval *before* AV-2 validation: weak, because the manager has not reviewed the automated check results.
   - Manager approval *before* Release_Payment: preventive; the manager can stop release.
   - Manager approval *before* Bank_Settlement: still preventive for release-stage defects; detective for defects that AV-2 should have caught but the operator missed.
   - Manager approval *after* Bank_Settlement: purely detective; corrective capacity is limited to legal recovery (uncertain).

2. **Independence and Conflict of Interest**
   - Manager must not be in a relationship that creates an unresolved conflict (e.g., direct-report relationship, shared budget responsibility, repeated two-person cells).
   - Shared workstations or credentials between preparer and releaser compromise independence even if IDs are distinct.
   - Repeated pairing (>3 payments in 30 days) suggests potential implicit collusion or organizational design that weakens separation of duties.

3. **Coverage and Overrideability**
   - AV-2 must operate without override, or an independent human must approve each override.
   - A warning that the operator (the same person who is already releasing) can dismiss unilaterally does not satisfy the four-eyes objective.
   - A full pass is strong evidence only for the checks covered (duplicate, sanctions, bank ownership, amount limit, PO basic match). It does not cover vendor necessity or goods receipt.

4. **Recoverability and Settlement Timing**
   - If Bank_Settlement occurs before an independent manager review, recovery depends on exceptional legal mechanisms (slow, uncertain).
   - A recall window of ~24 hours is available for detected errors if audit is completed before settlement.
   - Audit after 24 hours is detective but not corrective for recovery.

5. **Evidence Quality and Collusion Resistance**
   - A manager's "ratification" that cites no review details (no signature on invoice, no notation of bank-account verification) is weak evidence of independent judgment.
   - AV-2 passing against a compromised account is not evidence that the account belongs to the vendor; it is only evidence that the account was not flagged in the database.
   - Retrospective audit is strongest when it compares the preparer's, releaser's, and manager's independent documentation and identifies discrepancies (e.g., preparer says "emergency," manager says "routine").

6. **ED-1 Conditionality**
   - ED-1 is a permission with conditions, not a waiver of the control objective.
   - All seven conditions must be satisfied for a single-operator payment to be justified. Missing even one condition means the payment is nonconforming, even if other controls compensate partially.
   - The emergency token must be active *before* Prepare_Payment; a token created after Prepare_Payment fails condition 1.

### Why "Same Expected Loss" Is Not the Only Standard

Control conformance is not purely a loss-minimization problem. Governance, transparency, and deterrence are also objectives:

- **Governance:** If a control is regularly bypassed or overridden without documented justification, the organization loses the ability to manage by exception. All cases begin to look like special cases.
- **Transparency:** If a manager's approval is a rubber stamp, then a later auditor cannot distinguish between a carefully reviewed case and a negligent case. The audit's corrective and deterrent value declines.
- **Deterrence:** If a fraudster knows that a warning can be dismissed by the same operator, the fraudster has less fear of detection. Even if the expected loss (frequency × magnitude) is the same, the fraud risk increases.

Therefore, a package that achieves the same expected loss but through weaker independence, late approval, or rubber-stamped review is **tolerable but inferior** to a package with genuine preventive control. A case should be classified based on how reliably the control objective is met, not solely on outcome probability.

## 4. Preventive–Detective–Corrective Comparison

| Control | Timing of Execution | Primary Function | Preventive? | Detective? | Corrective? | Semantic Clarification |
|---|---|---|---|---|---|---|
| **FEP-1 (Four-Eyes)** | At prepare and release | Enforce distinct humans | Yes (if enforced with true independence) | Moderate (independent second human may catch errors, but not guaranteed) | No (process control; does not recover funds or undo actions) | Prevention requires that the second human actually exercises independent judgment. Detective value depends on the second human's attention to detail and independence from the first. |
| **AV-2 (Automated Validation)** | Before release (at 08:03, 09:04, etc.) | Block or warn based on rules (duplicate, sanctions, bank change, amount, PO match) | Yes (if no override or if override is independently approved) | Yes (warning is issued; operator can choose to override) | No (does not recover funds; blocking a release before settlement prevents loss, but this is prevention, not correction) | Prevention requires that blocks are enforced without unilateral override. Warnings alone are weak because the operator who initiated the payment can dismiss them. Correction would require rollback of a settled transfer, which is not AV-2's role. |
| **MG-4 (Independent Manager Approval)** | *Timing varies: before release (preventive), between release and settlement (detective/corrective hybrid), or after settlement (detective only)* | Review invoice, bank details, and receipt; approve or reject | **Yes** (if before release and manager is truly independent) | **Yes** (if between release and settlement; manager can request recall) | **Partial** (if before settlement; manager can request recall within ~24 hours) | A manager approval *before* Release_Payment is **preventive**: the manager can stop the release if a defect is detected. An approval *between* Release_Payment and Bank_Settlement is a **detective/corrective hybrid**: the release has occurred (detective timing) but settlement has not, so the manager can still request a recall (corrective). An approval *after* Bank_Settlement is **purely detective**: the transfer is irrevocable for internal control purposes. The manager's independence is critical: a direct-report manager or a manager with conflict of interest provides weak preventive value because the manager may be biased or coerced. Rubber-stamped approval (no documented evidence review) is weak in all timings. |
| **RA-7 (Retrospective Audit)** | After release, typically 1–8 days later | Detect errors, fraud, or control violations; request recovery (if possible) | No | **Yes** (full detective) | **Partial** (if within ~24 hours of settlement and recovery is possible; full corrective only if funds can be recalled or legal action succeeds) | Audit is detective by definition: it occurs after the fact. Corrective capacity depends on timing relative to bank settlement. Within 24 hours, recall is usually possible (partial corrective). After 24 hours, recovery is uncertain (weak corrective). RA-7 is strongest when conducted 100% for high-risk cases (emergency single-operator, override, no AV-2) and when it includes comparison of independent evidence from preparer, releaser, and manager (to detect collusion). |
| **ED-1 (Emergency Single-Operator Permission)** | Precondition check at prepare; post-facto validation | Permit single-operator payment if all seven conditions hold | **Yes** (prevention via conditions: token precondition, amount cap, vendor tenure, no bank change, AV-2 pass, manager approval before settlement, audit within 24 hours) | Moderate (audit is detective) | Partial (audit within 24 hours allows for recall; same-day audit is strongest) | ED-1 is not a waiver; it is a conditional permission. Prevention is achieved through *design constraints* (token, amount cap, vendor tenure, bank-change check) and through *compensating controls* (mandatory manager approval before settlement and mandatory audit within 24 hours). If any condition fails, ED-1 is inapplicable, and the case is nonconforming. |

### Semantics of "Before Settlement vs. After Settlement" for Manager Approval

- **Before Release (e.g., AP-203 at 10:04, AP-206 at 13:04, AP-207 at 14:40 pre-settlement):** Manager review occurs *before* the Release_Payment step. This is **fully preventive**. If the manager detects a defect, the manager can decline to approve, and the release does not occur. The manager's approval *authorizes* the release.

- **Between Release and Settlement (e.g., AP-201 at 08:30, Bank_Settlement at ~10:00; AP-203 at 10:04, Settlement at 12:00; AP-207 at 14:40, Settlement at 16:00):** Manager review occurs *after* the Release_Payment step but *before* the Bank_Settlement step. This is a **detective/corrective hybrid**. The release has already been sent to the bank, but the bank has not yet settled the transfer (typically 2–4 hours later in same-day processing). If the manager detects a defect, the manager can request a recall from the bank, which is usually possible within 24 hours but not guaranteed. This timing is strong corrective.

- **After Settlement (e.g., AP-202 at 11:00 on 2026-05-06, with settlement at 09:06 on 2026-05-04):** Manager review occurs *after* the Bank_Settlement step. This is **purely detective**. The transfer is irrevocable for internal control purposes. If the manager detects a defect, the only recourse is legal recovery, which is slow and uncertain. This timing provides no corrective capacity for internal controls.

The key insight: **Timing relative to Bank_Settlement, not Release_Payment, determines corrective capacity.** A manager approval *after* Release_Payment but *before* Settlement is more valuable than a manager approval *after* Settlement.

## 5. Counterfactual and Residual-Risk Analysis

### AP-202: Unilateral Override of Bank-Change Warning, Post-Settlement Approval

**Plausible Loss Mechanism:**  
u23 (or u23 colluding with m09) prepared a payment to a new vendor with a bank account changed 2 hours earlier. AV-2 warned of both the bank change and the operator limit (EUR 480,000). u23 overrode the warning unilaterally at 09:05. No independent manager reviewed the override decision at that moment. The payment was released at 09:06 and settled approximately 2.5 hours later. m09 ratified the payment post-settlement, 40+ hours later. The payment went to an account linked to an employee's relative.

**Which Control Breaks the Causal Chain?**  
None did. The chain was:
1. New vendor, bank change 2 hours prior (high-risk indicators).
2. AV-2 issued a warning.
3. u23 overrode without independent review (control failure: no pre-override approval).
4. Payment was released and settled before m09's approval (control failure: manager was post-settlement).
5. Audit was 8 days later, after recall window (control failure: audit timing).

**What Remains Exposed:**  
- The override governance process is absent. There is no documented requirement for a manager to approve an override *before* the operator dismisses a warning.
- The manager m09 has an unresolved conflict of interest (direct-report relationship with u23). Even if m09 had reviewed pre-release, the conflict would weaken the approval.
- Whether u23 and m09 shared the override credential is unresolved. If they did, the four-eyes principle is doubly violated.

**What Would Likely Change Under a Truly Independent Second Releaser?**  
If a second human (not m09, not with a conflict of interest) were required to review and approve the override before it was executed, the second human would likely have noticed:
- The new vendor (high-risk).
- The recent bank-account change (high-risk).
- The EUR 480,000 amount exceeding typical limits.

The second releaser would either have rejected the override or escalated to a higher authority. The probability of fraud proceeding would be substantially lower. However, collusion between the preparer and a colluding second releaser is still possible; audit and manager governance would then be critical.

**Residual Risk Characterization:**  
- **Baseline risk (no controls):** Fraud probability ~40%, loss EUR 480,000 (given the high-risk indicators and eventual realization). Expected loss ~EUR 192,000.
- **Current state (controls as implemented):** Fraud occurred; loss was EUR 480,000. Post-facto detection was delayed; recovery was unsuccessful.
- **With preventive override approval:** Fraud probability would drop to ~5–15% (some chance of collusion between preparer and the second releaser, or between both and a corrupted manager). Expected loss ~EUR 24,000–EUR 72,000.
- **Remaining exposure:** Manager governance and post-settlement audit are weak deterrents once a deposit is made. The 24-hour recall window is the only lever; after that, recovery is legal and uncertain.

### AP-204: Fabricated Service Receipt, Shared Workstation

**Plausible Loss Mechanism:**  
u12 prepared a EUR 220,000 consulting payment. u13 released it. Both work at the same workstation and have approved 37 payments together in 30 days. AV-2 passed (no automated check covers service receipt validity). No manager approved. The audit, conducted 8 days later, discovered a fabricated receipt.

**Which Control Breaks the Causal Chain?**  
None did:
1. u12 and u13 are distinct in the log, but they share a workstation and work together daily (weakens independence).
2. AV-2 cannot detect a fabricated receipt (coverage gap).
3. No manager approved to review the receipt independently (governance gap).
4. Audit was too late for recall (timing gap).

**What Remains Exposed:**  
- Collusion (implicit or explicit) between u12 and u13 is plausible but unproven. The shared workstation and high frequency of pairing suggest either organizational design or implicit understanding.
- The absence of a manager approval for EUR 220,000 is a material governance failure. Without manager review, no one independently validated that the consulting service actually occurred.
- AV-2 does not check receipt validity or commercial reasonableness; this is a coverage gap that compensation (manager review or audit) would address if they occurred in time.

**What Would Likely Change Under a Truly Independent Second Releaser?**  
If a second human at a different workstation were required to release the payment (after u12 prepared it), that second human would receive the payment request separately and independently review the supporting receipt. If the receipt is fabricated, the second human:
- May notice inconsistencies (signature mismatch, date errors, vendor contact mismatch).
- May question u12 or the vendor directly.
- May escalate if unable to verify.

The second releaser would not be under pressure from u12 (they are not work partners); this reduces collusion probability. However, the second releaser still needs to actually *review* the receipt (not just check boxes); this is an attention/incentive issue, not a control issue.

Additionally, if a manager were required to approve for amounts > EUR 100,000, the manager would review the receipt and query the vendor independently, further hardening the control.

**Residual Risk Characterization:**  
- **Baseline risk (no compensating controls):** Fraud probability ~25% (consulting payments are high-risk; shared workstation + no manager = weak governance). Expected loss ~EUR 55,000.
- **Current state (four-eyes form + AV-2 only):** Fraud occurred. u12 and u13's collusion was not detected preventively. Audit detected it 8 days later, but recall was impossible.
- **With independent second releaser + manager approval:** Fraud probability would drop to ~5% (harder to collude with a truly independent second releaser, and manager review of receipt would likely catch fabrication). Expected loss ~EUR 11,000.
- **Remaining exposure:** Manager approval after release (detective timing) would still allow recall if the manager reviewed the receipt carefully before settlement. Audit would confirm or detect residual fraud. The u12/u13 pairing across multiple cases (AP-209) suggests a systemic governance issue that a single-case control cannot address.

### AP-206: Late Emergency Token, Outage Claim Unverified

**Plausible Loss Mechanism:**  
u52 prepared a payment for a EUR 95,000 production-outage repair at 13:00. An emergency token was created at 13:02, *after* the Prepare_Payment step. ED-1 condition 1 (token active before Prepare_Payment) appears to fail. This may be a logging delay, or it may indicate that u52 prepared the payment before the emergency was formally authorized. The outage was documented as occurring at 12:40, which is before the prepare time, so the timeline is plausible but unconfirmed. AV-2 passed. m11 approved at 13:04 (before 13:08 release and before 15:00 settlement). RA-7 audit occurred next morning.

**Which Control Breaks the Causal Chain?**  
The causal chain is not one of fraud, but of governance:
1. u52 initiated a payment at 13:00, claiming emergency.
2. Emergency token was issued at 13:02 (after, not before).
3. AV-2 passed (no evidence of fraud in the checks covered).
4. m11 approved pre-release (presumably after seeing the token or the emergency claim).
5. Payment settled at 15:00; next-day audit confirmed no defect.

If the question is whether the payment was legitimate, the compensating controls (MG-4 and RA-7) likely provided sufficient coverage:
- m11's pre-release approval, with a review of the outage claim and supporting evidence, is preventive for detection of a false claim.
- Next-day audit would confirm whether the vendor's invoice matched the repair claim.

If the question is whether ED-1 was properly invoked, the token-timing failure is a governance gap: the token should be issued *before* the payment is prepared, to ensure that the authorization precedes the action.

**What Remains Exposed:**  
- The token-timing failure is unresolved. If the token was created after u52 began preparing the payment, then the precondition for ED-1 was not satisfied, and the case is nonconforming by design (not just by outcome).
- Whether m11 verified the outage claim or merely accepted u52's assertion is not documented. If m11 did not independently verify the claim (e.g., by contacting operations or reviewing a log), then m11's approval is weak evidence of independent judgment.

**What Would Likely Change Under a Truly Independent Second Releaser?**  
If a second human (not u52, independent of u52) were required to release the payment, that second human would:
- Review the emergency claim and supporting evidence (outage log, vendor contact, repair scope).
- Verify that the payment amount is reasonable for the repair.
- Check that the vendor is authorized for this type of work.

The second releaser would be a check on whether u52's "emergency" claim is valid. If the claim is fabricated (e.g., u52 is colluding with a vendor to claim a fake outage), the second releaser might detect inconsistencies. However, if the outage is real (as in this case), the second releaser adds minimal value beyond confirming that u52 is honest—which is a deterrent, not a detection mechanism.

**Residual Risk Characterization:**  
- **Baseline risk (no ED-1 or compensating controls):** If a payment can be prepared and released by a single person for any reason, fraud probability ~15%. Expected loss ~EUR 14,250.
- **Current state (ED-1 with token-timing ambiguity + MG-4 pre-release + RA-7 next-day):** Fraud was not detected; however, the payment was later confirmed legitimate. If m11's review was genuine, the risk was reduced. If m11 rubber-stamped, the risk was not reduced by governance, only by the low probability that a EUR 95,000 outage claim is false given the supporting documentation.
- **With token-timing confirmed and second releaser:** Fraud probability would drop to ~5%. Expected loss ~EUR 4,750.
- **Remaining exposure:** The governance gap (token timing) suggests that emergency authorizations may not be issued before payment preparations in all cases. This is a process integrity issue that monitoring of token-creation timestamps would address.

### AP-208: AV-2 Unavailable, Post-Settlement Manager Approval, EUR 900,000

**Plausible Loss Mechanism:**  
u72 prepared a EUR 900,000 payment for a vendor with 8 months tenure (borderline on ED-1's 180-day rule) and a bank-account change 3 days prior. AV-2 was unavailable at 15:01, before the release at 15:04. No manual validation checklist was signed (or recorded). u72 released unilaterally. The payment settled at 16:00. m21 ratified the payment the *next day* (>24 hours post-settlement). Audit was 4 days later. The payment was later confirmed as legitimate, but the controls were insufficient to support that conclusion at the time of release.

**Which Control Breaks the Causal Chain?**  
None did. The causal chain is:
1. High-risk indicators (EUR 900,000, vendor tenure borderline, recent bank change).
2. AV-2 unavailable (preventive control absent).
3. No documented manual validation (compensating preventive control absent).
4. u72 released unilaterally without independent pre-release approval (process control failed).
5. Settlement occurred without any independent pre-settlement review.
6. m21's post-settlement ratification provides no corrective capacity (too late for recall).
7. Audit 4 days later is purely detective, and recall is impossible.

**What Remains Exposed:**  
- The AV-2 outage was not escalated or monitored. No rule requires a manager to approve high-risk payments (>EUR 100,000, recent bank change, vendor tenure borderline) if AV-2 is unavailable.
- The vendor tenure condition for ED-1 is borderline: 8 months is approximately 240 days, which is *technically* above 180, but it is not a strong margin. This should have triggered heightened scrutiny.
- No manual validation checklist was recorded. This is a critical gap: if AV-2 fails, the organization should have a fallback procedure (manual review, documented and signed). The absence of a checklist suggests that no fallback was invoked.

**What Would Likely Change Under a Truly Independent Second Releaser?**  
If a second human (not u72) were required to release, that second human would:
- Be informed that AV-2 is unavailable.
- Either postpone the payment until AV-2 is restored, or conduct a manual validation.
- If conducting manual validation, check the vendor's bank account against a pre-existing master file.
- Notice the recent bank-account change and query the vendor directly.
- Flag the case for manager approval due to the unavailable preventive control.

A truly independent second releaser, aware that AV-2 is absent, would likely request manager escalation or a documented manual validation. This would have introduced a review step that could have caught the control failure, even if the underlying payment is legitimate.

**Residual Risk Characterization:**  
- **Baseline risk (no controls, EUR 900,000, recent bank change, borderline vendor tenure):** Fraud probability ~35%. Expected loss ~EUR 315,000.
- **Current state (AV-2 unavailable, no manual validation, post-settlement approval, late audit):** Fraud was not detected; payment confirmed legitimate post-facto. If the payment is legitimate, controls did not prevent a loss (because there was no loss), but they failed to *prove* legitimacy at the time of execution. This is a control-failure outcome that happens to have no loss due to good luck.
- **With AV-2 restored, manual validation, and manager pre-release approval:** Fraud probability would drop to ~5%. Expected loss ~EUR 45,000.
- **Remaining exposure:** The AV-2 outage exposes the organization to all vendor-bank-account fraud risks for the duration of the outage. For a EUR 900,000 payment, this is a material gap. Monitoring and alerting for AV-2 availability, along with escalation procedures for unavailability, are critical.

## 6. Evidence and Monitoring Recommendations

### Core Monitoring Rules

1. **Same-User Four-Eyes Violation Rate**
   - **Alert Threshold:** Any case where Prepare_Payment and Release_Payment have the same org:resource *and* no documented compensating control (manager pre-release approval or active ED-1 conditions) is flagged as a governance alert.
   - **Evidence to Collect:** For each flagged case, collect:
     - ED-1 token-activation timestamp and token-issuer identity.
     - Manager approval timestamp and manager identity (compare to preparer/releaser to check independence).
     - Bank_Settlement timestamp (to determine if manager approval was pre-settlement or post-settlement).
     - Audit completion timestamp (to determine if within 24 hours of settlement and if any defect was found).
   - **Distinction:** An alert does *not* prove misconduct. It flags cases that require manual review to confirm compensating controls or to re-evaluate risk. A case like AP-203 is an alert (same-user), but it meets the control objective (ED-1 conditions + manager pre-release + audit within recall window).

2. **Override Rate and Timing**
   - **Alert Threshold:** Any case where AV-2 issues a warning or block, and the preparer or releaser overrides without a documented independent manager approval *before* the override is executed, is flagged.
   - **Evidence to Collect:** For each override case:
     - AV-2 warning or block reason (bank change, amount, sanctions, duplicate, etc.).
     - Identity of the human who approved the override (should be a manager, not the preparer/releaser).
     - Timestamp of override-approval relative to release: should be *before* Release_Payment (preventive) or at least before Bank_Settlement (detective).
     - Manager identity and conflict-of-interest check (is the manager independent of the preparer/releaser?).
   - **AP-202 Example:** u23 overrode without manager approval before override. This is a red flag. A documented manager pre-override approval (from m09 or an independent manager) would have mitigated, but it did not occur.

3. **Late Emergency-Token Issuance**
   - **Alert Threshold:** ED-1 condition 1 requires the emergency token to be active *before* Prepare_Payment. Any case where the token-creation timestamp is *after* the Prepare_Payment timestamp is flagged as a potential precondition failure.
   - **Evidence to Collect:** For each case claiming ED-1 exemption:
     - Token-creation timestamp (from the emergency-authorization system, not inferred from logs).
     - Prepare_Payment timestamp.
     - Clock-synchronization status between the two systems.
     - Emergency-incident report (outage log, incident ticket, etc.) timestamp.
   - **AP-206 Example:** Token created at 13:02, Prepare at 13:00. Appears to fail condition 1. Evidence required: was there a clock skew, or was the token genuinely created after the payment was prepared (indicating a failure to pre-authorize)?

4. **Manager Approval Timing and Independence**
   - **Alert Threshold:** Cases where Manager_Ratify or Manager_Approve occurs *after* Bank_Settlement are flagged as detective (not preventive).
   - **Evidence to Collect:** For each manager-approval case:
     - Relationship between manager and preparer/releaser (direct report? peer in the same cost center? vendor oversight responsibility?).
     - Whether the manager's approval is documented with specific evidence reviewed (invoice number, PO, receipt note, bank-account verification, etc.) or is a generic "OK."
     - Manager's escalation record (has the manager ever rejected a payment in the past 12 months? if not, there is a pattern of rubber-stamping).
     - Manager's background (is the manager qualified to assess the type of payment—e.g., a manager reviewing a complex consulting invoice should have purchasing or accounting expertise).
   - **AP-202 Example:** m09 is u23's direct supervisor (conflict of interest). m09's approval is post-settlement (detective, not preventive). Whether m09 and u23 shared an override credential is unresolved (amplifies conflict).

5. **Audit Timing and Defect Detection**
   - **Alert Threshold:** Cases where Audit_Review occurs *after* the ~24-hour bank-settlement recall window are flagged as purely detective (no corrective capacity). Especially flagged if the audit detects a defect (fraud, fabrication, duplicate).
   - **Evidence to Collect:** For each audit case:
     - Audit-review timestamp relative to Bank_Settlement (< 24 hours, 24–48 hours, > 48 hours).
     - Whether the audit was performed on 100% of cases or a sample (100% is required for high-risk, emergency, override, or same-user cases).
     - Audit findings (no defect, warning, error, fraud indicator).
     - Audit evidence reviewed (were invoice, PO, receipt, and bank-account details compared, or was the audit limited to log review?).
     - Recovery action (if defect detected, was recall requested? if recovery was not possible, why not?).
   - **AP-204 Example:** Audit on day 8, 8 days after release and 8 days after settlement (outside recall window). Fabricated receipt detected, but recovery was impossible. Audit-timing rule is broken: for high-risk cases (high-value consulting, no manager approval, u12/u13 pairing), audit should be same-day or next-day.

6. **Bank-Account Change Proximity**
   - **Alert Threshold:** Any payment to a vendor whose bank account was changed in the previous 7 days is flagged as high-risk. If the payment amount is > EUR 100,000 *or* the vendor tenure is < 2 years *or* the preparer/releaser are the same, escalate to a manager *before* release (if possible).
   - **Evidence to Collect:** For each payment:
     - Vendor master-file bank-account record (current account, previous account, change timestamp).
     - Whether the vendor *itself* reported the change (e.g., letter on company letterhead, form signed by vendor's authorized signatory) or the change was initiated by the payment operator (red flag).
     - Manual verification of bank ownership (e.g., calling the vendor's known number and confirming the new account, or reviewing a bank statement showing the account in the vendor's name).
   - **AP-202 Example:** Bank change 2 hours prior. AV-2 warned. But no manager pre-release review of the change (the override was unilateral). This is a critical failure.

7. **Repeated Resource Pairs (Potential Collusion or Undocumented Cell Structure)**
   - **Alert Threshold:** Any pair of humans (e.g., u12 and u13) who appear together in Prepare_Payment + Release_Payment (or other paired steps) more than 3 times in a 30-day window, or who share the same workstation, are flagged for collusion assessment.
   - **Evidence to Collect:** For each flagged pair:
     - All payments processed by the pair in the past 90 days (frequency, amounts, vendor types, defects).
     - Workstation logs (login/logout times, shared credentials).
     - Organizational design documents (is the pair a documented two-person payment cell? if so, the organization should formally recognize this and strengthen compensating controls, such as manager approval for all payments by the cell, or audit by a third party).
     - Audit findings for cases by the pair (are defects detected at a higher rate than for other pairs, or lower?).
     - Email or chat evidence of communication between the pair (are they discussing payment decisions, or are they working independently?).
   - **AP-204 & AP-209 Example:** u12 and u13 approved 37 payments in 30 days (AP-204 analysis) and now 39 payments (AP-209 re-count). This is ~1.3 payments per day for the pair. If the organization has 10 payment processors, the expected rate is 1/10 × total payments per day. If the pair is above that rate, it suggests either preferential assignment to them (organizational design) or collusion. Workstation logs are critical: do they log in from the same location? if so, do they physically share a desk (high collusion risk)?

8. **AV-2 Unavailability and Manual Validation Fallback**
   - **Alert Threshold:** Any case where Automated_Validate_Service_Unavailable, Validation_Service_Unavailable, or a similar system event is recorded, and no subsequent manual-validation checklist is recorded or signed, is flagged as a control failure.
   - **Evidence to Collect:** For each unavailability case:
     - AV-2 system logs (outage duration, root cause, notification to payment team).
     - Manual-validation checklist (signed by the preparer or releaser, listing checks performed: duplicate, sanctions, bank ownership, PO match, vendor history, etc.).
     - Manager escalation or approval (was a manager notified of the AV-2 outage? did the manager approve release with manual validation?).
     - Payment amount and risk profile (AV-2 unavailability for EUR 900,000, recent bank change is unacceptable without manager pre-release approval and documented manual validation).
   - **AP-208 Example:** AV-2 unavailable, no manual checklist recorded. For a EUR 900,000 payment with a recent bank change, this is a critical control failure. The rule should require: if AV-2 is unavailable for > 5 minutes *and* payment amount > EUR 100,000 *or* bank change in prior 7 days, then release requires manager pre-approval and a signed manual-validation checklist.

9. **ED-1 Condition-Satisfaction Assessment**
   - **Alert Threshold:** Any case claiming ED-1 exemption must satisfy *all seven* conditions. If *any* condition is not documented or is borderline, the case is flagged for re-assessment.
   - **Evidence to Collect:** For each ED-1 case:
     - Emergency-token record: issuance timestamp, issuer identity, incident description, incident timestamp, token activation timestamp.
     - Amount check: is the payment  EUR 100,000?
     - Vendor tenure: number of days since first payment to this vendor (must be  180 days).
     - Bank-account-change check: has the vendor's bank account changed in the prior 7 days? (must be "no" or date must be > 7 days ago).
     - AV-2 result: did AV-2 pass without override, or was there a warning/block that was overridden? (condition 5 requires full operational and pass without override).
     - Manager pre-release approval: did a manager of L3 or above, independent of the preparer/releaser, approve *before* Release_Payment?
     - Audit within 24 hours: was an audit completed within 24 hours of the release?
   - **AP-206 Example:** Token timestamp vs. Prepare_Payment timestamp is ambiguous (condition 1 may fail). Vendor tenure is 3 years (condition 3 satisfied). Amount is EUR 95,000 (condition 2 satisfied). No bank change (condition 4 satisfied). AV-2 passed (condition 5 satisfied). m11 approved pre-release (condition 6 satisfied). Audit next morning (condition 7 satisfied or borderline). Overall: six of seven conditions are clearly satisfied; one is ambiguous (token timing). This is a borderline ED-1 case that should be re-assessed with root-cause analysis of the token-timing ambiguity.

10. **Audit-Before-Recall-Window Frequency**
    - **Alert Threshold:** For each quarter, calculate the % of same-user or override or post-settlement-approval payments that received audit *within* 24 hours of release (and thus within recall window). Target: 100% of high-risk cases. If the % is < 90%, escalate.
    - **Evidence to Collect:** For each quarter:
        - Count of high-risk payments (same-user OR override OR post-settlement-approval OR AV-2-unavailable).
        - Count of high-risk payments with audit completed within 24 hours.
        - Root causes for cases where audit did not complete in time (audit team capacity, case complexity, etc.).
    - **Corrective Action:** Increase audit team capacity or prioritize high-risk cases to achieve 100% within-window audit.

### Evidence-to-Judgment Mapping

An **alert** (e.g., "same-user four-eyes violation" or "bank-account change 2 hours prior") is *not* proof of misconduct. Each alert triggers a manual review of evidence:

| Alert | What It Indicates | Evidence That Confirms Compensating Control | Evidence That Indicates Control Failure |
|---|---|---|---|
| Same-user payment | Process control nominally violated | ED-1 conditions 1–7 all satisfied; manager pre-release approval documented; audit within 24 hours confirms no defect | ED-1 precondition fails (e.g., token after prepare); manager approval is post-settlement or rubber-stamped; audit is late or detects defect |
| AV-2 override | Automated control bypassed | Manager pre-override approval documented; manager is independent; override reason is justified (e.g., system error); post-override audit confirms decision | Override is unilateral (no manager approval before override); override reason is not documented; manager has conflict of interest |
| Bank-account change < 7 days | High-risk fraud indicator | Vendor-initiated change documented (letter on vendor letterhead); manual verification of bank ownership (phone call, statement); manager pre-release approval | Change is operator-initiated (no vendor evidence); no manual verification; release is unilateral or post-settlement approval |
| Repeated resource pair | Potential collusion | Organizational design document confirming two-person cell; manager oversight of the cell; no defect rate elevation for the pair; audit confirms both work at separate workstations or at different times | No organizational design document; defect rate for the pair is higher than baseline; workstation logs show both present at the same time; email evidence of coordination on specific payments |
| AV-2 unavailable | Compensating control absent | Manual-validation checklist completed and signed; manager pre-release approval; audit confirms manual checks were correct | No manual-validation checklist; release is unilateral; no manager escalation |
| Late manager approval (post-settlement) | Corrective capacity lost | Audit conducted within 24 hours; audit detected no defect; vendor confirms payment correctness | Audit conducted after 24 hours or not conducted; audit detected fraud or error; vendor disputes the payment |

### PM4Py Limitations and Disclaimers

- **`pm4py.filter_four_eyes_principle()` Behavior:** This function (if it exists in the version used) is assumed to filter cases where the same resource appears in both a specified source activity and a specified sink activity. However, the exact behavior varies across PM4Py versions. The code reconstructs this logic manually to ensure compatibility.
- **Resource Independence:** PM4Py cannot determine whether two resources who are distinct in the log are truly independent (e.g., shared workstation, shared credentials, direct-report relationship). This requires external evidence (organizational design documents, access-control logs, audit notes).
- **Semantic Interpretation:** PM4Py treats `Manager_Approve`, `Manager_Ratify`, and similar activities as events. The code does not infer the quality or independence of the approval from the log alone; this requires documentation review.
- **Timestamp Precision:** The code assumes timestamps are accurate and synchronized across systems. Clock skew or logging delays (as suspected in AP-206) require investigation from system logs, not from the event log alone.

## Summary

This review applies a structured framework to evaluate payment-process conformance beyond simple four-eyes compliance:

1. **Control-Objective Decomposition** identifies five threat scenarios and maps each to preventive, detective, and corrective mechanisms.
2. **Equivalence and Sufficiency Testing** defines when compensating controls are adequate, accounting for timing, independence, coverage, overrideability, recoverability, and collusion resistance.
3. **Case-Level Findings** classify each case by control-objective achievement (not by nominal compliance), with evidence for each classification.
4. **Preventive–Detective–Corrective Comparison** clarifies semantic distinctions and timing implications.
5. **Counterfactual Analysis** shows which control fails in each case and what would change with a truly independent second releaser.
6. **Monitoring Recommendations** provide actionable rules to detect governance gaps and red flags, with evidence-to-judgment mappings.
7. **Code** enables preliminary evidence-flag generation, emphasizing that flags require context, documentation, independence checks, and outcome verification before judgment.

The core finding: **Nominal four-eyes compliance and control-objective achievement are related but distinct.** A case with distinct users may fail the objective (AP-204: collusion via shared workstation), while a case with the same user may meet the objective (AP-203: ED-1 with full conditions and pre-release manager approval). Governance is strengthened by monitoring for evidence of independence, pre-release manager review, timely audit, and compensating controls—not by counting user IDs.
