## 1. Duplicate-handling decision tree

Decision-making for handling event relationships:

### 1. Exact Technical Duplicates  
**Criteria:**  
- Exact match of all attributes: `timestamp`, `activity`, `source`, `source_event_key`, `payload_hash`, and `related_objects`.

**Action:**  
- Drop duplicate events except one.
  
---

### 2. Same Physical Event Observed by Multiple Systems  
**Criteria:**  
- Shared or reconciled domain knowledge confirms they denote the **same underlying action**, but system-specific attributes (e.g., WMS vs. SCANNER enrichments) differ.
- Example: e03 and e04 (same item picked, WMS added location).

**Action:**  
- Merge: Include all unique attributes and relations while marking the event as combined in provenance metadata.

---

### 3. Summary vs. Detailed Event  
**Criteria:**  
- Events represent different abstraction layers (e.g., e06 from WMS vs. e07 from ERP: the former is a specific WMS operation, the latter a derived status update).
- Organizational semantics suggest the summary is secondary.

**Action:**  
- Retain both with refined labels: E.g., append "Summary" for ERPs when traceability matters. Ensure provenance records this distinction.

---

### 4. Harmonization Collision Between Distinct Source Activities  
**Criteria:**  
- Events have the same label due to harmonization (e.g., "Dispatch Package") but semantics and source-system intent differ.  
- Example: e08 (release from WMS) vs. e09 (carrier acceptance).

**Action:**  
- Retain both with original timestamp. Refine activity labels for clarity (e.g., differentiate `Dispatch Package` as `Warehouse Release` and `Carrier Acceptance`).

---

### 5. Concurrent Same-Label Events Involving Different Objects  
**Criteria:**  
- Same `activity` and `timestamp`, but distinguishable by `related_objects`.
- Example: e03 (Pick I1) vs. e05 (Pick I2).

**Action:**  
- Retain both unchanged, as these represent separate events.

---

### 6. Unresolved Candidates  
**Criteria:**  
- Ambiguity remains (e.g., insufficient information to confirm semantic meaning or relevance of differences).

**Action:**  
- Quarantine for manual review, preserving all attributes and provenance.

## 3. Timestamp-tie ordering rules

### Ordering Policy

**Rules (in priority):**  
1. **Domain constraints (semantic):**
   - Lifecycle dependencies: e12 precedes e13 for M1.
   - Sequential events: e09 precedes e10.
2. **Within-source sequence (deterministic):**
   - Use `source_seq` where available.
3. **Shared-object lifecycle (semantic):**
   - Events interacting with the same object resolved based on probable causality (e.g., e08  e09).
4. **Source-specific semantics (semantic):**
   - Prioritize authoritative sources (e.g., e03 over e04).
5. **Ingestion time (deterministic fallback):**
   - Earliest `ingested_at` suggests timeliness.
6. **Stable fallback ordering (deterministic):**
   - Sort by `eid` where ties remain.

**Caution:** Artificial microseconds distort actual event intervals.

## 4. Conservative cleaning pipeline

### Steps:
1. Detect exact duplicates and drop.
2. Resolve known same-physical events (e.g., e03/e04).
3. Retain distinct business layers with refined labels (e.g., e06/e07).  
4. Quarantine unresolved ambiguities for review.
5. Enforce deterministic total ordering.

### Expected:
- Event count: 15–17 (quarantining uncertainties like e06/e07). Minimal attribute loss.  

---

## 5. Aggressive alternatives

### **1. Evidence-based merge**  
- Merge all semantically same events.  
- Event count: ~12–14. Semantic risk: Overgeneralization (e.g., e05 dropped).  

### **2. Library-driven merge**  
- Apply `pm4py.ocel_merge_duplicates`.  
- Retained count: ~10–12. Semantic risk: Mismerged distinct payments, lifecycle distortions.

## 6. PM4Py-oriented Python implementation

```python
from copy import deepcopy
import pm4py

# Deep copy scenarios
ocel_raw_c = deepcopy(ocel_raw)  # Conservative
ocel_raw_s = deepcopy(ocel_raw)  # Evidence-based semantic merge

# Pre-check for duplicates
duplicates = pm4py.ocel_get_potential_duplicates(ocel_raw)

# Conservative deduplication
pm4py.ocel_drop_duplicates(ocel_raw_c, mode="conservative")

# Aggressive deduplication
warnings.warn("Aggressive merging may cause semantic damage")
pm4py.ocel_merge_duplicates(ocel_raw_s, mode="aggressive")

# Deterministic ordering adjustment
pm4py.ocel_sort_by_additional_column(ocel_raw_c, "source_seq")

# Optional synthetic adjustment after domain rules
pm4py.ocel_add_index_based_timedelta(ocel_raw_c)

assert pm4py.ocel_check_referential_integrity(ocel_raw_c)
```

## 9. Failure Modes and Safeguards  

1. **Collapsing distinct payments (e13/e14):** Maintain Payment separation.  
2. **Mistaking Abstraction Events:** Use labels to preserve layers.  
3. **Ordering by ingestion:** Stick to domain constraints.  
4. **Harmonized label misuse:** Clarify via source semantics.  
5. **Unioning incompatible relations:** Disassociate cross-layer objects.  
6. **Synthesized microseconds:** Clarify fallback order risks.  
7. **Losing source fidelity:** Embed audit trail.  
8. **Workshop missteps:** Pre-review effect-specific groups.
