Definitions:
Let c be case; i  {A,B,C}. Times in minutes.

Upstream:
U_c = fork_release_c - arrival_c.

For branch i:
Q_{c,i} = start_{c,i} - fork_release_c. (branch-specific queue waiting)
S_{c,i} = end_{c,i} - start_{c,i}. (active service)
W^{sync}_{c,i} = join_ready_c - end_{c,i}. (sync waiting after completion; 0 if branch completes last)
join_ready_c = max(end_{c,A}, end_{c,B}, end_{c,C})
critical_branch_c = argmax_i end_{c,i} (with deterministic tie rule, e.g., all tied branches listed).
Fork-join stage elapsed:
FJ_c = join_ready_c - fork_release_c.
For every branch, FJ_c = Q_{c,i} + S_{c,i} + W^{sync}_{c,i}.
This identity holds per branch because start_i + S_i = end_i and end_i + sync_i = join_ready, so Q_i + S_i + sync_i = (start_i - fork_release)+(end_i - start_i)+(join_ready - end_i) = join_ready - fork_release.
Why summing all branch synchronization waits double counts: Branches run in parallel; the elapsed FJ_c is a single interval. If we sum FJ_c over branches we get 3*FJ_c, so sum of Q_i+S_i+W_i across i equals 3*FJ_c, not FJ_c. Alternatively, only one branch can be the latest at a time; sync waits for other branches overlap the critical branch's remaining service, so adding them to a case-level total double-counts time already represented by critical branch. Need be explicit.

Downstream queue:
D_c = final_start_c - join_ready_c (assuming final starts after join_ready; if negative would be data violation).
Final service:
S^F_c = final_end_c - final_start_c.
Total flow time:
T_c = final_end_c - arrival_c.
Additive decomposition:
T_c = U_c + FJ_c + D_c + S^F_c.
This is case-level additive. Branch-level components are not summed across branches; use critical branch's components or max logic. We can also express critical path:
T_c = U_c + Q_{c,crit} + S_{c,crit} + D_c + S^F_c, since W_sync for critical = 0.

# 1. Delay-decomposition definitions

Let \(c\) index cases and \(i \in \{A,B,C\}\) index branches. All times are minutes, with the same date 2026-05-19.

Define:

\[
\text{upstream\_elapsed}_c = fork\_release_c - arrival_c
\]

For each branch \(i\):

\[
Q_{c,i} = start_{c,i} - fork\_release_c
\]

\[
S_{c,i} = end_{c,i} - start_{c,i}
\]

\[
join\_ready_c = \max(end_{c,A}, end_{c,B}, end_{c,C})
\]

\[
W^{sync}_{c,i} = join\_ready_c - end_{c,i}
\]

where \(W^{sync}_{c,i}=0\) for the critical/last-completing branch. Then:

\[
\text{fork\_join\_stage}_c = join\_ready_c - fork\_release_c
\]

For every branch:

\[
Q_{c,i} + S_{c,i} + W^{sync}_{c,i}
= (start_i - fork\_release)
+ (end_i - start_i)
+ (join\_ready - end_i)
= join\_ready - fork\_release
\]

So each branch produces the same fork-join stage elapsed time.

Downstream queueing and final service are:

\[
\text{downstream\_queue}_c = final\_start_c - join\_ready_c
\]

\[
\text{final\_service}_c = final\_end_c - final\_start_c
\]

Total case flow time:

\[
\text{total\_flow\_time}_c = final\_end_c - arrival_c
\]

The additive case-level decomposition is:

\[
\text{total\_flow\_time}_c
=
\text{upstream\_elapsed}_c
+
\text{fork\_join\_stage}_c
+
\text{downstream\_queue}_c
+
\text{final\_service}_c
\]

**Why summing all branch synchronization waits double counts elapsed time**

Because branches run in parallel, the fork-join stage is a single interval. If we sum across branches:

\[
\sum_i (Q_{c,i} + S_{c,i} + W^{sync}_{c,i})
=
3 \times \text{fork\_join\_stage}_c
\]

The actual elapsed time is only one fork-join stage. The synchronization waits of early-finishing branches overlap the remaining service time of the critical branch. They are slack, not additional case-level elapsed time.

# 4. Counterfactual redesign analysis

Assumption for branch counterfactuals: I report direct savings as reductions in `join_ready`. Flow-time savings equal these reductions only if final can start earlier. If `final_start` remains fixed because of downstream congestion, then branch-only improvements do not reduce total flow time; they only increase downstream queue.

| case | CF1: A service 20% join_ready saving | CF2: B queue 50% join_ready saving | CF3: downstream queue 50% flow-time saving |
|---|---:|---:|---:|
| F01 | 5.0 | 0.0 | 4.0 |
| F02 | 0.0 | 10.0 | 7.5 |
| F03 | 0.0 | 10.0 | 7.5 |
| F04 | 0.0 | 0.0 | 9.0 |
| F05 | 0.0 | 10.0 | 5.0 |
| F06 | 0.0 | 15.0 | 7.5 |
| F07 | 0.0 | 15.0 | 7.5 |
| F08 | 0.0 | 0.0 | 7.5 |
| F09 | 0.0 | 12.5 | 7.5 |
| F10 | 0.0 | 5.0 | 10.0 |
| F11 | 10.0 | 0.0 | 10.0 |
| F12 | 0.0 | 15.0 | 5.0 |
| **Total** | **15.0** | **92.5** | **88.0** |

**Counterfactual 1: reduce A service time by 20%**

- A service changes from 50 to 40 min.
- A is critical only in F01 and F11.
- In F01, join_ready falls from 09:00 to 08:55, saving 5 min, not 10, because B becomes critical.
- In F11, join_ready falls from 11:30 to 11:20, saving 10 min, because B is tied at 11:20.
- All other cases have zero direct join_ready benefit because A was not critical.
- If final-start times are fixed, the flow-time saving is zero; the saved A time becomes extra downstream queue.
- Secondary effects: freeing lab capacity may reduce future A queue, but A currently has zero queue. Likely low system-level benefit unless final congestion is also reduced.

**Counterfactual 2: reduce B queue delay by 50%**

- B queue is halved, service unchanged.
- Direct join_ready savings total 92.5 min across 12 cases.
- Zero-benefit cases: F01, F04, F08, F11, where A or C remains critical.
- Partial-benefit cases:
  - F05: B queue falls 12.5 min, but A becomes critical, so join_ready saving is only 10 min.
  - F10: B queue falls 10 min, but A becomes critical, so join_ready saving is only 5 min.
  - F02: B queue falls 10 min, join_ready saving is 10 min with A tied.
- Full-benefit cases where B remains critical: F03, F06, F07, F09, F12, saving 10–15 min each.
- This counterfactual has the largest branch-side direct impact, but if final-start times are fixed, total flow-time savings are again zero because downstream queue grows.
- Secondary effects: B queue reduction may require extra B capacity or better scheduling. It would shift criticality toward A in several cases and could expose C variability later.

**Counterfactual 3: add final-station capacity or reduce downstream queueing**

Current downstream queue total is 176 min, mean 14.7 min.

If downstream queue is halved:
- Every case benefits because every case has positive downstream queue.
- Total flow-time saving = 88 min, mean 7.3 min per case.
- Largest per-case savings: F10 and F11 would each save 10 min.
- If downstream queue were eliminated, total flow-time saving would be 176 min, mean 14.7 min.

This counterfactual directly reduces total flow time, not just join_ready. It also makes branch improvements more visible. However, final resource utilization is only moderate over the observed horizon—about 120 min of service per resource over a 212-minute span, or roughly 57% per resource—so waiting appears to be partly due to arrival bunching or scheduling policy, not simply a capacity shortage.

Secondary effects: reducing downstream queue may shift the bottleneck upstream to the branches, especially B and A. It may also increase pressure on branch resources if final starts are pulled earlier.

# 5. Recommended redesigns and risks

## Recommendation 1: Reduce B queue delay, but only together with final-station decongestion

B is the most influential branch: it is critical in 8/12 cases, and a 50% reduction in B queue delay could reduce join_ready by about 92.5 min across the dataset.

- **Throughput:** Potential case-level acceleration, especially in later cases where B is on the critical path.
- **Flow-time tail:** Helps several tail cases such as F12, F09, and F07.
- **Resource utilization:** If achieved by adding B capacity, B utilization may fall; if achieved by better scheduling, utilization may improve.
- **Possible new bottlenecks:** A becomes critical more often, especially in F05 and F10. C could also become critical if its occasional queue/service spikes are not controlled.
- **Synchronization effects:** Early finishers, especially C, will have even larger synchronization slack. That is acceptable, but it means the benefit is capped by the next critical branch.
- **Pilot/measure first:** Measure why B queues occur. Test scheduling, prioritizing, or adding one B resource. Track critical-branch frequency, B queue, A queue, C queue, and downstream queue.

## Recommendation 2: Reduce downstream final-station queueing

The final station currently adds 8–20 min of downstream queue to every case. Halving this queue would save 88 total flow-time minutes, and every case would benefit.

- **Throughput:** Direct flow-time reduction; may increase throughput if final capacity is the limiting resource.
- **Flow-time tail:** Reduces downstream waiting across all cases, including tail cases.
- **Resource utilization:** Final resources are not highly utilized on average, so adding a full third resource may be overkill. A flexible resource or better scheduling may be better.
- **Possible new bottlenecks:** If final capacity increases, branch-side work becomes the next bottleneck, likely B and A.
- **Synchronization effects:** Less downstream queue means branch synchronization slack becomes more visible; branch improvements will translate more directly into flow-time savings.
- **Pilot/measure first:** Test a temporary third final resource or staggered release of cases to final. Measure downstream queue, final-start delay, final utilization, and total flow time before and after.

# 7. Limits of inference

- **Causality is not identified.** Timestamps show when activities started and ended, but not why delays occurred. A branch start delay could be queueing, resource unavailability, batching, or a release policy.
- **Branch resource capacity is unobserved.** There are no resource columns for A, B, or C. The “queue” measures `branch_start - fork_release`, but this is only an inferred waiting time.
- **Work preemption is unobservable.** Complete-event data give only `start` and `end`. Service time may contain interruptions, multitasking, or rework.
- **Synchronization waiting is inferred from the max branch end.** If there are unobserved constraints or rework after branch completion, `join_ready` may not equal true downstream readiness.
- **Final-station waiting may not be a pure queue.** `final_start - join_ready` could be caused by release policy, batching, resource contention, or other unobserved downstream requirements.
- **Single-day, 12-case sample.** There is no evidence about daily demand variation, staff shifts, or process stability.
- **Counterfactual estimates assume ceteris paribus behavior.** Reducing one delay may shift the bottleneck, change resource behavior, or alter arrival patterns in ways not captured by these timestamps.
