## 2. Process-model consistency checks

A robust predictive process monitoring system must enforce strict separation between past observations, enabled transitions, and future execution paths. The following validation suite details the mathematical checks, formalisms, and limitations required to guarantee process and temporal consistency.

### 2.1 Formal Framework and Prefix Semantics
Let a complete case trace be defined as a sequence of timestamped events $\sigma = \langle (e_1, \tau_1), (e_2, \tau_2), \dots, (e_n, \tau_n) \rangle$, where each event has an activity label $act(e_i)$, a timestamp $\tau_i \in \mathbb{R}$, and a transactional sequence index $idx(e_i) \in \mathbb{N}$.
For an SLA prediction epoch set at $t_0 = \tau(\text{Coverage Check Completed})$, the admissible prefix trace is strictly:
$$\sigma_{\le t_0} = \langle (e_i, \tau_i, idx(e_i)) \in \sigma \mid \tau_i \le t_0 \rangle$$
Any feature extraction function $f$ or sequence explainer $g$ evaluated at $t_0$ must satisfy the **Prefix Invariance Property**:
$$f(\sigma) \equiv f(\sigma_{\le t_0}) \quad \forall \sigma \in \mathcal{L}$$
If $f(\sigma) \neq f(\sigma_{\le t_0})$, the feature depends on the downstream execution future and must be rejected as temporal leakage.

### 2.2 Concrete Validation Suite

#### Check 1: Prefix-Time Availability and As-Of Joins
- **Mechanism**: Inspect every event and dimensional attribute bound to the prediction instance. Verify that the event timestamp $\tau(e) \le t_0$ and the database record assertion timestamp $t_{assert} \le t_0$.
- **Implementation**: Enforce point-in-time SQL join semantics:
  `ON dim.entity_id = event.entity_id AND dim.valid_from <= t0 AND (dim.valid_to > t0 OR dim.valid_to IS NULL)`.
  Any join referencing `extraction_date`, `CURRENT_TIMESTAMP`, or lacking temporal constraints fails this check (e.g., catching `prior_claim_count_before_t0` and `employee_experience`).

#### Check 2: Same-Timestamp Ambiguity and Monotonic Sequence Ordering
- **Mechanism**: When $\tau(e_i) = \tau(e_j)$ for $i \neq j$, timestamps alone cannot establish causality or ordering.
- **Root Cause in Case Z**: `Claim Closed` and `Damage Assessment Completed` possessed identical timestamps. Missing the database ingestion sequence index ($idx$) caused the pipeline to arbitrarily interleave them, generating the impossible pattern `Claim Closed -> Damage Assessment Completed`.
- **Validation Rule**: Ingestion pipelines must capture an atomic, monotonically increasing transaction log identifier (e.g., database Write-Ahead Log sequence number or auto-incrementing event ID). If identical timestamps occur without sequence indices, the pipeline must apply a topological sort constrained by the normative process model; if a cycle or illegal transition is implied, the trace must be quarantined for pipeline remediation.

#### Check 3: Activity State Classification at $t_0$ (Enabled vs. Future-Possible vs. Impossible)
Using a formal state-space representation (Petri net reachability marking $M(t_0)$ or Declare state), every activity $a \in \mathcal{A}$ is partitioned at $t_0$ into three distinct sets:
1. **Enabled at $t_0$ ($A_{enabled}$)**: Activities whose pre-conditions are fully satisfied by the prefix $\sigma_{\le t_0}$ and can execute immediately. At $t_0$ (immediately after `Coverage Check Completed`), $A_{enabled} = \{\text{Damage Assessment Completed}, \text{Documents Requested}, \text{Fraud Investigation Opened}\}$.
2. **Future-Possible at $t_0$ ($A_{future}$)**: Activities reachable in the process graph from $M(t_0)$ only after one or more intermediate transitions occur. Here, $A_{future} = \{\text{Documents Received}, \text{Documents Validated}, \text{Settlement Decision Recorded}, \text{Appeal}, \text{Claim Closed}\}$.
3. **Process-Impossible ($A_{impossible}$)**: Activities that cannot legally fire from $M(t_0)$ under normative business rules (e.g., `Claim Closed` firing before `Damage Assessment Completed` or `Settlement Decision Recorded`; `Appeal` firing before `Settlement Decision Recorded`).

**Explainer Constraint**: Sequence explainers operating at $t_0$ must strictly constrain their candidate pattern space to transitions within $\sigma_{\le t_0}$ (i.e., `Claim Registered -> Coverage Check Completed`). Explaining current case risk by asserting observed contributions from $A_{future}$ transitions (e.g., `Appeal -> Settlement Decision Recorded`) or $A_{impossible}$ transitions is a critical methodological failure.

#### Check 4: Semantic Legitimacy of Process Loops (Repeated Settlement Decisions)
- **Normative Rule**: Step 6 records `Settlement Decision Recorded` ($\in \{\text{Approve}, \text{Partial}, \text{Deny}, \text{Withdrawn}\}$). Step 7 allows `Appeal` *only* after `Partial` or `Deny`. A successful appeal transitions to reconsideration, legally producing a second `Settlement Decision Recorded`.
- **Formal Evaluation & Limitations of Process Mining Formalisms**:
  - **Directly-Follows Graphs (DFG)**: *Inadequate*. A DFG evaluates only adjacent transitions ($e_i \to e_{i+1}$) with 1st-order Markov memory. A DFG cycle `Settlement Decision -> Appeal -> Settlement Decision` cannot verify whether the first decision was `Partial`/`Deny` versus `Approve`, nor can it enforce that at most two decisions may occur. A DFG cannot distinguish valid reconsideration from corrupt duplicate ingestion.
  - **Transition Footprints**: *Inadequate*. Footprints capture static pairwise relationships ($\to, \leftarrow, ||, \#$) across entire traces; loops create causal conflicts in the matrix and flatten iteration context.
  - **Declarative Conformance (Declare / LTLf)**: *Optimal*. Formally evaluates temporal logic constraints across the trace history:
    - $\text{Precedence}(\text{Settlement Decision Recorded}[\text{Partial} \lor \text{Deny}], \text{Appeal})$
    - $\text{Response}(\text{Appeal}, \text{Settlement Decision Recorded})$
    - $\text{Absence3}(\text{Settlement Decision Recorded})$ (at most two decisions allowed).
  - **Prefix Alignments**: *Optimal for Prefix Verification*. Prefix alignments compute the minimum-cost edit distance between the observed prefix $\sigma_{\le t_0}$ and the nearest valid prefix of the normative model. At $t_0$, any model move trying to synchronize an `Appeal` or downstream `Settlement Decision` incurs an infinite cost, automatically pruning it.

**Distinction**: While `Appeal -> Settlement Decision Recorded` is a semantically legitimate normative loop in the completed process, it is strictly forbidden in an explanation at $t_0$ because neither the first decision, nor the appeal, nor the second decision has occurred yet.

## 3. Alternative feature interpretations

To prevent both naive leakage acceptance and overzealous feature deletion, features surviving audit or capable of lineage remediation must be categorized according to four rigorous standards:
- **Predictive Validity**: Stable statistical association $P(Y \mid X, t_0)$ holding out-of-sample and out-of-time.
- **Causal Interpretation**: Invariance under intervention $P(Y \mid do(X))$, requiring structural causal identification, absence of confounding, and correct temporal precedence.
- **Operational Actionability**: Controllable organizational levers (e.g., queue re-allocation, staffing) versus immutable case constraints.
- **Fairness & Governance Review**: Evaluating proxy discrimination, disparate impact, and historical bias.

### 3.2 Detailed Class Analysis

#### 1. Defensible Predictive Signals
- **Features**: `initial_damage_complexity`, `initial_reserve`.
- **What may be claimed**: High initial loss complexity and large reserve allocations (€25,000) are valid statistical predictors of longer processing duration. They reflect structural governance requirements (mandatory multi-tier approvals, senior adjuster reviews, and rigorous evidence standards).
- **What may NOT be claimed**: They must not be given causal or actionable narratives. An adjuster cannot "accelerate a claim by lowering the reserve" (which would violate solvency standards and commit fraud). They are unalterable baseline risk attributes.

#### 2. Process-State or Congestion Signals
- **Features**: `queue_length_at_t0`, `elapsed_since_registration_at_t0`.
- **What may be claimed**: These represent true operational state variables. By Little's Law ($L = \lambda W$), a queue length of 18 at $t_0$ introduces physical waiting time before an available resource picks up the claim. Similarly, `elapsed_since_registration_at_t0 = 1.2 h` measures consumed SLA budget, directly defining the remaining runway.
- **What may NOT be claimed**: Congestion must not be interpreted as handler incompetence or case defect. It is a system-level property. Explanations must clearly state that queue delay is an environmental operational factor.

#### 3. Proxies Requiring Fairness and Robustness Review
- **Features**: `claimant_region`, `claimant_channel`.
- **What may be claimed**: Region R4 and Broker channel correlate with settlement delays due to external infrastructure: authorized repair garage density in rural regions and multi-hop communication latency when transmitting documents through independent brokers.
- **What may NOT be claimed**: The team's assertion that "Region is a delay driver" is an unsupported causal claim. Attributing delay to claimant geography or broker choice risks unlawful proxy discrimination (redlining) and disparate impact across socioeconomic or linguistic groups. These features must undergo equalized odds and demographic parity audits before deployment and cannot be used to justify adverse settlement actions.

#### 4. Drift / Calendar Proxies
- **Features**: `calendar_week`.
- **What may be claimed**: Captures external macro-operational conditions known at $t_0$, specifically end-of-year backlog (Week 52) and statutory holiday staffing reductions.
- **What may NOT be claimed**: It must not be presented as a causal characteristic of the claim ("filing in Week 52 makes a case inherently slower"). It is a brittle proxy subject to concept and data drift; changes in annual operating policy or shift schedules invalidate historical learned weights.

#### 5. Unusable Until Lineage is Repaired
- **Features**: `prior_claim_count_before_t0` (SQL lookahead), `same_day_document_count_snapshot` (nightly batch lookahead), `final_handler_team` (closure overwrite), `risk_score_current` (mutable unversioned overwrite), `last_resource_role` (full-trace summary), `employee_experience` (extraction date join).
- **What may be claimed**: Currently **nothing**. Any observed predictive power in these features is contaminated by lookahead leakage, target correlation, and survivor bias.
- **What may NOT be claimed**: No operational, predictive, or causal inferences may be communicated to end-users or handlers until data pipelines implement strict point-in-time logging.

## 5. Recommendations for explanation validation

To transform this system into a trustworthy, compliant predictive process monitoring platform, the organization should execute the following prioritized eight-pillar roadmap:

```
+----------------------------------------------------------------------------------------------------+
|                         EXPLANATION VALIDATION & GOVERNANCE ROADMAP                                |
+----------------------------------------------------------------------------------------------------+
| Pillar 1: Feature Store & Point-in-Time Correctness  ==> Bi-temporal tables, strict As-Of joins     |
| Pillar 2: Prefix-Only Recomputation Pipeline         ==> Ingestion cutoffs, prefix-invariance tests |
| Pillar 3: Process Conformance & Rule Engines        ==> Declare / LTLf checks, monotonic ordering   |
| Pillar 4: Model Re-Estimation & Post-Hoc Calibration ==> Platt scaling, Brier score, ECE metrics   |
| Pillar 5: Explanation Stability & Robustness         ==> Perturbation testing, local fidelity checks|
| Pillar 6: Fairness Auditing & Proxy Deconstruction   ==> Disparate impact, equalized odds audits    |
| Pillar 7: Causal Boundary & Decision Governance      ==> UI counterfactuals, anti-actionable guard  |
| Pillar 8: Continuous Drift & Integrity Monitoring    ==> PSI, KS-tests, timestamp collision alerts  |
+----------------------------------------------------------------------------------------------------+
```

### Pillar 1: Feature Store Design and Bi-Temporal Point-in-Time Correctness
- **Immutable Event Sourcing**: Migrate all feature engineering to an enterprise feature store (e.g., Feast, Hopsworks) supporting bi-temporal modeling:
  - **Event Timestamp ($\tau_{event}$)**: When the business action occurred in the real world.
  - **Assertion / Ingestion Timestamp ($\tau_{assert}$)**: When the record was written into the database.
- **Enforce "As-Of" Joins**: All feature retrieval must use strict point-in-time joins where $\tau_{event} \le t_0$ and $\tau_{assert} \le t_0$. Eliminate all references to batch extraction dates or `CURRENT_TIMESTAMP`.
- **Eradicate Batch Snapshots**: Replace nightly scheduled batch tables (such as `same_day_document_count_snapshot` refreshed at 23:00) with event-driven state materializers that compute windowed counts strictly bounded by $t_0$.

### Pillar 2: Prefix-Only Pipeline Recomputation
- **Automated Prefix Invariance Tests**: Implement unit and integration tests in CI/CD that assert:
  $$|f(\sigma_{\le t_0}) - f(\sigma_{complete})| \equiv 0$$
  Any feature whose value changes when evaluated on the full trace versus the prefix slice must be automatically blocked from production deployment.
- **Quarantine and Re-extract Corrupted Historical Features**:
  - Re-extract `prior_claim_count_before_t0` by strictly enforcing `prior.claim_created_at < target.t0`.
  - Re-engineer `final_handler_team` to `assigned_handler_team_at_t0` by joining historical allocation logs.
  - Snapshot `risk_score` into an append-only change log to provide verifiable `risk_score_at_t0`.

### Pillar 3: Process Conformance and Topological Integrity
- **Mandatory Sequence Indexing**: Require all source transactional systems to emit a monotonic transaction log index ($idx$) to definitively break ties between events sharing identical microsecond timestamps.
- **Declarative Conformance Engine**: Embed an LTLf/Declare rule engine into the data validation pipeline. The engine must validate that every ingested trace prefix satisfies core structural rules:
  - Skips or inversions (such as `Claim Closed` before `Damage Assessment Completed`) must be flagged as pipeline ingestion errors and diverted to an exception queue before reaching ML inference.
  - Validate that loop patterns (such as repeated `Settlement Decision Recorded` events) strictly satisfy the intervening `Appeal` constraint following a `Partial` or `Deny` outcome.
