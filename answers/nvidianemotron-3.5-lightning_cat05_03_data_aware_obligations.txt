## 1. Temporal Data Semantics  

**State reconstruction** – For each case the event log is processed in chronological order (UTC timestamp first, then `event_index` as tiebreaker).  A running “lastknown” value is kept for every attribute (`amount`, `risk_level`, `jurisdiction`, `customer_type`).  Blank cells in the CSV mean “no update at this event”; the previous value is retained – the value is **not** set to `null` or a default lowrisk placeholder (R6).  

**Effective time vs. record time vs. evidence time** –  
*Event time* = the timestamp attached to the event in the log.  
*Effective time* = the moment an attribute becomes valid for obligations; for attribute updates it is the event’s timestamp unless explicit evidence says otherwise.  
*Record time* = when the value is persisted in the database (e.g., exemption insertion).  
*Evidence time* = when approval/signature occurred (e.g., Head_Compliance approval, digital signature).  The policy explicitly states that a displayed backdated field alone is not conclusive (R5).  

**Material data change** – Any change to `amount`, `risk_level`, `jurisdiction`, or `customer_type` is considered material.  For R4 only *increases* >20% after a review invalidate that review; *decreases* do not invalidate (R4).  

**Equaltimestamp ordering** – When two events share a timestamp, the `event_index` determines order: lower index fires first.  The consequence (which value is “latest”) must be stated (R7).  

**Final case attributes** – The final row of a case is **not** copied backward in time.  Each event’s state reflects only the events that precede it.

### Concise Formal PseudoLogic (R1–R7)

Below is a Datalogstyle skeleton; temporal relations are explicitly directed (`<` = “before”, `>` = “after”).  Tiebreaking uses `event_index`: `e1  e2` iff `e1.timestamp < e2.timestamp` **or** (`e1.timestamp = e2.timestamp` **and** `e1.event_index < e2.event_index`).

```prolog
%--- helpers -------------------------------------------------
max_release(C) = R  where R.concept = "Release_Funds" &
                     ¬(  R' . R'.concept = "Release_Funds" & R'  R ).

latest_material_change(C, T) = MC  where MC.concept  {Update_Amount,Update_Risk,Update_Jurisdiction,Update_Customer_Type} &
                                      MC  T    ¬(  MC' . MC'  T  MC'  MC ).

enhanced_review_before(C, T) = ER  where ER.concept = "Enhanced_Review" & ER  T.

%--- R1 -------------------------------------------------------
:- case C,
   R = max_release(C),
   Jur_at_R = forward_fill(C,R).amount,
   Jur_jur  = forward_fill(C,R).jurisdiction,
   (Jur_jur  "DE"  Jur_at_R  100000)
    (  ER . enhanced_review_before(C,R)  ER  latest_material_change(C,R) )
       (  EX . exemption_valid(C,EX) ).

%--- R2 -------------------------------------------------------
:- case C,
   R = max_release(C),
   risk_at_R   = forward_fill(C,R).risk_level,
   cust_at_R   = forward_fill(C,R).customer_type,
   (risk_at_R = "HIGH"  cust_at_R = "PEP")
    (  ER . enhanced_review_before(C,R) )
       (  CA . compliance_approve_before(C,R) )
       CA  ER   % Compliance after Enhanced_Review
       CA  R.

%--- R3 -------------------------------------------------------
:- case C,
   R = max_release(C),
   Jur_at_R = forward_fill(C,R).jurisdiction,
   SLU = latest_sanctions_list_update(C,R),   % exists if X added after screen
   ( SLU  SLU  R )
    (  SS . sanctions_screen_after(C,SS,R) )   % SS after SLU & before R

%--- R4 -------------------------------------------------------
:- case C,
   R = max_release(C),
   ER = latest_review_before(C,R) where Review  {Standard_Review,Enhanced_Review},
   Inc = latest_amount_increase_after(C,ER,R),   % increase >20% after ER
   ( Inc )
    invalidated(ER).

%--- R5 -------------------------------------------------------
exemption_valid(C,EX) :-
   approved_by_head(EX) ,
   effective_from(EX)  obligation_trigger(C) ,
   scope_matches(EX, C) ,
   not expired(EX) ,
   evidence_supports(EX, C).

%--- R6 -------------------------------------------------------
unknown_value(C, Attr) :-
    e  events(C) . e.Attr = blank .
 classify(C, INDETERMINATE)   % unless other evidence resolves.

%--- R7 -------------------------------------------------------
% tiebreaker already captured in  definition.
```

*Key directions*:  
- `ER  R`  Enhanced_Review **before** Release_Funds.  
- `ER  MC`  Enhanced_Review **after** latest material change.  
- `CA  ER`  Compliance_Approve **after** Enhanced_Review.  
- `SLU  SS`  Sanctions_List_Update **before** new Screen.

## 6. Why ControlFlowOnly Conformance Is Insufficient  

1. **Finalstate leakage** – Using the final case attributes (e.g., amount after all updates) and projecting them backward makes rules that depend on the state *at* Release_Funds appear satisfied when they were actually violated earlier.  

2. **Posthoc exemptions** – Exemptions recorded after the release (as in TX302, TX310) may be backdated in the UI; controlflow conformance that simply sees an “Exemption” activity after release would wrongly deem the case compliant.  

3. **Material changes after review** – Rules R1 and R4 hinge on whether an amount or risk change occurred *after* the last review.  A controlflow diagram has no intrinsic notion of “amount increase” vs. “decrease”; it would either ignore the change or treat all changes alike, leading to incorrect invalidation decisions.  

4. **Conditional activation** – R1R5 are activated only when certain attribute combinations hold (jurisdiction DE, amount100k, risk=HIGH, customer_type=PEP, exemption validity).  A pure Petrinet/DECLARE model that records only activity timestamps cannot express these datacentric conditions without adding separate datastate nodes, which defeats the purpose of flowonly conformance.  

5. **Missing data** – Blank attribute cells (R6) are treated as “no update”, not as a default lowrisk value.  A conformance checker that silently defaults to a low risk would produce falsenegative compliance judgments, as illustrated by TX305.  

6. **Sametimestamp ordering** – When two events share a timestamp, the `event_index` decides which value is latest (R7).  Controlflow models normally merge events with identical timestamps, losing the indexbased ordering and consequently misassigning which review or change governed the later obligation.  

*Additional failure modes (beyond the six required) include:*  
- **Immutable release payloads** not being captured, so the exact amount/jurisdiction at release is ambiguous.  
- **Versioned rule sets** where the same activity may be governed by different rule versions across cases, which a static flow model cannot distinguish.

## 7. Recommended Logging and Control Improvements  

| Recommendation | Why it Helps |
|----------------|--------------|
| **Immutable release payloads** – Store a snapshot of `amount`, `risk_level`, `jurisdiction`, `customer_type`, and exemption status at the moment of `Release_Funds`. | Prevents finalstate leakage; provides an unambiguous “state at release” for rule evaluation. |
| **Effective / record / signature timestamps** for every attribute change and exemption approval. | Distinguishes event time from effective time; enables precise “after/before” temporal checks (R1R5). |
| **Rule version field** on each case or perrule flag. | Allows retrospective auditing if rule interpretations change; avoids ambiguity when similar cases are evaluated under different rule sets. |
| **Exemption scope attributes** (jurisdiction, customertype, amount range) stored explicitly, not only in a freetext note. | Makes R5 validity checks deterministic; eliminates reliance on displayed backdates. |
| **Change provenance** – Record who triggered an update (resource, system) and why (note field). | Facilitates evidence evaluation (e.g., “customer increased order”) and supports R6 missingdata rulings. |
| **Stable global event ordering** – Always include a globally unique, monotonically increasing `event_index` (or a composite key `timestamp + sequence`) and never reuse indices across cases. | Guarantees deterministic tiebreaking for equaltimestamp events (R7) and avoids ambiguous “sametimestamp” outcomes. |
| **Materialchange flags** – Add a boolean `is_material_change` on update events, distinguishing increases from decreases where policy matters (R4). | Gives rule engines a clear signal whether a change is “material” for the purpose of review invalidation. |
| **Explicit unknownvalue flags** – When an attribute is blank at an event, store a flag `amount_unknown = true` rather than leaving the cell empty. | Enables R6 INDETERMINATE classification without having to infer defaults. |
| **Traceordered audit log** – Keep the original CSVstyle log plus an indexed, versioncontrolled copy; allow reprocessing with different rule sets without reparsing the source system. | Supports reproducibility and future ruleset experiments. |

Implementing these improvements will make future compliance assessments fully determinate, reduce the need for adhoc LLM judgment, and provide a solid audit trail for regulators and internal reviewers.
