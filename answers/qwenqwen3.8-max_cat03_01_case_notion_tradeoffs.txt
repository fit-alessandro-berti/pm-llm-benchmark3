## 1. Analytical assumptions

I treat a **case notion** as an analytical projection: when flattening on object type `X`, each object of type `X` becomes a case, and an event is copied into that case if the event is directly related to that object in the supplied E2O table. I do **not** treat any projection as recovering the “true” case notion; each projection answers a different business question.

I interpret **convergence** as the degree to which cases of the selected object type collapse into similar activity sequences or DFG paths. Convergence can be genuine, but it can also be artificial when the selected object participates in only a few event types or when shared events hide important differences.

I interpret **divergence** as the degree to which cases produce many variants, branches, loops, or interleavings. Divergence can be informative, as with split fulfilment, or misleading, when copied shared events create apparent repeated work.

I treat **copied shared events** as both evidence and duplication:

- **Evidence**: the copied event shows that the selected object participated in a shared activity. For example, `e16` is legitimate evidence that `O1`, `O2`, and `O3` were all affected by dispatch of `D2`.
- **Duplication**: if frequencies, throughput, costs, or activity repetitions are counted naively, the same underlying event may appear as multiple independent occurrences. For example, `e16` copied into three order cases should not be interpreted as three separate dispatch activities.

Baseline analysis uses only the supplied direct E2O relations. I would permit the following analytical transformations only as explicit sensitivity checks, not as the default:

- Propagating relations through the O2O graph, for example from `Order contains Item`, `Package packs Item`, `Delivery carries Package`, or `Invoice bills Order`.
- Enriching the activity name using O2O qualifiers, for example distinguishing `Record Payment (partial)` for `M2 partially_settles V2` from `Record Payment (completion)` for `M3 completes_settlement V2`.
- Down-weighting copied shared events by the number of selected objects related to the event.
- Preserving original event identifiers so that copied events can be de-duplicated analytically.

## 3. Concrete distortion analysis

1. **Cross-order package duplication in Order flattening**  
   Affected flattening: **Order**. Event `e13` is directly related to `O2`, `O3`, `I21`, `I31`, and `P3`. When flattening on Order, `e13` is copied into both `O2` and `O3`. The DFG edge `Pack Package -> Dispatch` can therefore appear twice for the same physical packing event, especially through `e13 -> e16`. This inflates packing frequency and can make shared packing look like independent order-specific work. The effect is **harmful for capacity and frequency analysis**, but **informative** if the question is which orders were exposed to shared packing.

2. **Cross-order package duplication in Item flattening**  
   Affected flattening: **Item**. Events `e14`, `e17`, and `e27` relate to both `I32` and `I41`, as well as `P4` and `D3`. Flattening on Item copies the same pack, dispatch, and confirmation events into both item cases. The item DFG may suggest two independent item flows, even though the physical handling occurred once in package `P4`. This is **harmful if used to count handling workload**, but **context-dependent** for item-level lead-time analysis because each item genuinely experienced the same physical milestones.

3. **Cross-order packages hidden as ordinary packages**  
   Affected flattening: **Package**. `P3` has trace `e13 -> e16 -> e24`, and `P4` has trace `e14 -> e17 -> e27`. In a package-centric log, these look like ordinary package lifecycles. The fact that `P3` consolidates items from `O2/O3` and `P4` consolidates items from `O3/O4` is not visible unless O2O relations are examined. This is **harmful for order-impact analysis**, because a delayed package may affect multiple orders, but **informative for logistics**, where the package is the relevant handling unit.

4. **Consolidated delivery duplication in Order flattening**  
   Affected flattening: **Order**. `D2` is dispatched in `e16` and confirmed in `e24`, and both events relate to `O1`, `O2`, and `O3`. In an order log, `e16` and `e24` are copied into three cases. The DFG edge `Dispatch -> Confirm Delivery` may be counted three times for the same delivery. Performance between `e16` and `e24` may also appear as three independent order-level durations. This is **harmful for unique delivery workload**, but **informative** for understanding how many orders were affected by the long `D2` transport duration.

5. **Delivery flattening truncates consolidated delivery `D2`**  
   Affected flattening: **Delivery**. `D2` appears only as `e16 -> e24`. The flattened delivery case hides that `D2` carries `P2` and `P3`, and that those packages relate to `O1`, `O2`, and `O3`. The lifecycle is artificially short and the DFG becomes trivial: `Dispatch -> Confirm Delivery`. This is **harmful if the delivery log is used for end-to-end fulfilment**, but **informative for transport duration**, where `e16` to `e24` is exactly the relevant interval.

6. **Consolidated invoice duplication in Order flattening**  
   Affected flattening: **Order**. Invoice `V2` is issued in `e19` and paid in `e22` and `e25`. These events relate to both `O2` and `O3`. When flattening on Order, both orders appear to have the same invoice and two payment events. Without payment amounts or settlement qualifiers, each order may look fully settled twice, or may appear to require two payments independently. This is **harmful for financial reconciliation**, but **informative** if the goal is to know which orders are linked to a consolidated invoice.

7. **Partial payments appear as repeated activity in Invoice flattening**  
   Affected flattening: **Invoice**. The `V2` case is `e19 Issue Invoice -> e22 Record Payment -> e25 Record Payment`. Because both payment events have the same activity label, a DFG or log skeleton may infer rework, repetition, or duplicate payment. The interval `e22 -> e25` may be interpreted as a delay or exception, although the O2O qualifiers show that `M2 partially_settles V2` and `M3 completes_settlement V2`. This is **harmful without qualifier enrichment**, but **informative** for analysing instalment settlement cycles.

8. **Near-singleton lifecycle in Payment flattening**  
   Affected flattening: **Payment**. Each payment object participates in exactly one event: `M1` in `e21`, `M2` in `e22`, `M3` in `e25`, and `M4` in `e26`. The resulting cases have length one. DFG discovery yields no meaningful edges, and lifecycle analysis is impossible. The partial/full relationship between `M2/M3` and `V2` is hidden unless O2O relations are used. This is **harmful for control-flow discovery**, but the flattening can still be useful for payment counts or timestamp audits.

9. **Close-before-confirm anomaly in Order flattening**  
   Affected flattening: **Order**. `e24` confirms `D2` at `2026-02-04 16:00`, but `O1`, `O2`, and `O3` close earlier: `e28` at `11:00`, `e29` at `11:05`, and `e30` at `11:05`. Therefore order traces can contain both `Confirm Delivery -> Close Order` edges, such as `e23 -> e28` for `O1`, and `Close Order -> Confirm Delivery` edges, such as `e28 -> e24`, `e29 -> e24`, and `e30 -> e24`. The DFG may show an apparent loop or process violation. This is **harmful if it reflects data-quality error**, but **informative if the business intentionally closes orders after payment and before final delivery confirmation**.

## 4. Traditional versus object-centric analysis portfolio

I would still create several flattened logs, but each should be labelled as a projection with known limitations.

**Flattened logs to create:**

- **Order log**: create as the primary accountability log. It is the only flattening that touches every event. It can safely answer questions such as: which orders reached closure; what order-level variants exist; which orders were exposed to shared packages, deliveries, or invoices; and what the elapsed time is from `Create Order` to `Close Order`, provided the close-before-confirm anomaly is explicitly checked.
- **Invoice log**: create for financial settlement analysis. It can safely answer: how many payments follow each invoice; how long settlement takes for `V1`, `V2`, and `V3`; and whether `V2` has multiple payment events. It should not be used to assess physical fulfilment.
- **Package log**: create for logistics analysis. It can safely answer: pack-to-dispatch and dispatch-to-confirm durations for `P1`–`P4`; and which packages share delivery events, if O2O relations are retained.
- **Delivery log**: create only for transport performance. It can safely answer: dispatch-to-confirm duration for `D1`, `D2`, and `D3`. It cannot answer end-to-end order fulfilment questions.
- **Item log**: create optionally for item-level physical lead time. It can answer: how long items take from `Add Item` to `Confirm Delivery`. It should not be used for financial or order-completeness analysis.
- **Payment log**: create only for counting payment objects and timestamps. It is not useful for DFG discovery because `M1`–`M4` are singleton cases.

**Questions requiring object-centric analysis:**

- Which unique orders, packages, and deliveries are affected by delayed `D2`? This requires an **OC-DFG** or object interaction summary, because flattened order logs duplicate `e16/e24`, while flattened delivery logs hide the related orders.
- How many unique events occur in shared logistics nodes such as `P3`, `P4`, `D2`, and `V2`? This requires unique-event counting in an object-centric representation.
- How do object types interact structurally? This requires an **OTG** to show relations such as `Order contains Item`, `Package packs Item`, `Delivery carries Package`, `Invoice bills Order`, and `Payment settles Invoice`.
- Which events connect which object types? This requires an **ET–OT graph** or equivalent event-to-object-type summary.
- Which executions are equivalent after normalising for shared events? This may require **equivalent-execution clustering**, especially if comparing order-centric variants while accounting for shared logistics and finance objects.

**Reconciling contradictory findings:**

If the order DFG shows repeated `Dispatch -> Confirm Delivery` edges but the OC-DFG shows only one underlying `e16 -> e24` event, report both: the order view measures case exposure, while the OC-DFG measures unique event frequency. If the invoice log suggests payment before delivery, check the direct E2O and O2O graph: `e22/e25` relate to `V2`, while `e24` relates to `D2`; partial payment before final delivery may be legitimate. Contradictions should be resolved by returning to the E2O/O2O graph and by stating which metric is being used: case copies, unique events, or object involvements.

## 5. Lead-object decision

**Position chosen: B. Use a primary lead object plus explicitly secondary lifecycles.**

I would use **Order** as the primary lead object, but only with explicit secondary lifecycles for **Package**, **Delivery**, **Invoice**, and **Payment**. Item can be included as an optional physical fulfilment secondary lifecycle.

**Decision criteria:**

1. **Business accountability**: the process is called order fulfilment, and orders are the objects for which closure is explicitly recorded.
2. **Lifecycle completeness**: orders have both creation events `e01`–`e04` and closure events `e28`–`e31`.
3. **Event coverage**: every event in the snapshot relates to at least one order, so order flattening loses no event.
4. **Distortion severity**: shared events create duplication, but the distortion can be managed with event identifiers and object-centric views.
5. **Need for secondary views**: consolidation in `P3/P4`, `D2`, `V2`, and `M2/M3` cannot be represented safely by orders alone.

**Strongest supporting evidence:**  
The strongest argument for Order as primary is that only the order projection connects the whole snapshot. `O1` includes creation, item addition, split packing, dispatch, invoice, payment, delivery confirmation, and closure. `O3` shows the most complex multi-package path through `e13`, `e14`, `e16`, `e17`, `e24`, and `e27`. Because every event has at least one order, the order log preserves the broadest end-to-end scope.

**Strongest counterargument:**  
The strongest counterargument is that order cases are not independent. `P3`, `P4`, `D2`, and `V2` are shared across orders. In particular, `e19`, `e22`, and `e25` are copied into both `O2` and `O3`, making it look as if each order independently receives two payments against `V2`. Without amounts or settlement qualifiers, the order view can materially misrepresent financial settlement.

**Residual risk:**  
Even with secondary lifecycles, the order view may inflate shared logistics and finance frequencies. It may also hide the fact that financial closure and physical closure are not aligned, as shown by `e28`–`e30` occurring before `e24`.

**Conditions under which I would change the decision:**  
I would abandon Order as primary if the analytical goal became logistics capacity, in which case Package or Delivery should lead; financial compliance, in which case Invoice or Payment should lead; or if the organisation required strict one-case-one-event independence. If shared events cannot be de-duplicated or if payment amounts cannot be allocated across `O2/O3`, I would move to a primarily object-centric analysis and reject a dominant lead object.

## 7. Sensitivity and validation plan

1. **Remove or down-weight copied shared events**  
   For each flattened log, keep the original event identifier and compute both copied-event frequency and unique-event frequency. For example, in the Order log, `e16` and `e24` are copied into `O1`, `O2`, and `O3`. A down-weighted version would assign weight `1/3` to each order copy. In the Package log, `e16` and `e24` would be weighted `1/2` across `P2` and `P3`. If DFG hotspots disappear after de-duplication, the original hotspot was caused by copying rather than by additional work.

2. **Compare direct E2O relations with a propagated-relation variant**  
   The baseline uses only direct E2O relations. A sensitivity variant should propagate relations through O2O links such as `contains`, `packs`, `carries`, `bills`, and `settles`. For example, payment events `e21`, `e22`, `e25`, and `e26` could be propagated from invoices to orders and, further, to items/packages if transitive closure is applied. This will lengthen item/package lifecycles and increase duplication. Comparing the two variants shows whether conclusions depend on direct event ownership or on inferred object involvement.

3. **Change the lead object**  
   Rerun the analysis with Order, Invoice, Package, and Delivery as lead objects. The Order lead should show the broadest lifecycle but high duplication. The Invoice lead should highlight `V2` settlement and partial payments but hide delivery. The Delivery lead should show short `Dispatch -> Confirm Delivery` traces and the long duration of `D2`. The Package lead should expose `P3/P4` logistics but hide order impact. If a conclusion changes when the lead object changes, it should be reported as projection-dependent.

4. **Compare frequency metrics based on events, unique objects, and total object involvements**  
   Use at least three metrics: copied event frequency, unique event frequency, and object-involvement frequency. For example, `e16` has three order copies, one unique event, three related orders, two related packages, and one related delivery. In the OC-DFG, these metrics can diverge sharply. If an activity is hot only under copied-event frequency, it is a shared-event duplication effect. If it is hot under unique-event frequency, it is a true event bottleneck. If it is hot under object-involvement frequency, it indicates broad object impact.
