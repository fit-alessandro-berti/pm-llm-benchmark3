```python
def evaluate_model_for_enforcement(net, im, fm, train_log, test_log, neg_log):
    """
    Decision rule: reject model for enforcement if ANY of:
    1. Negative trace fitness > threshold (e.g., 0.8) — model admits too many forbidden traces
    2. Holdout fitness < threshold (e.g., 0.7) — model doesn't generalize
    3. Training-holdout fitness gap > threshold (e.g., 0.2) — overfitting
    4. Soundness check fails — model has structural defects
    5. Stakeholder accuracy < threshold (e.g., 70%) — stakeholders can't predict model behavior
    """
    results = {}
    
    # 1. Negative trace fitness (should be LOW)
    neg_fitness = pm4py.fitness_alignments(neg_log, net, im, fm)
    results['neg_fitness'] = neg_fitness
    if neg_fitness.get('average fitness', 1.0) > 0.8:
        results['reject'] = True
        results['reason'] = 'Model admits forbidden behavior (neg_fitness > 0.8)'
        return results
    
    # 2. Holdout fitness
    test_fitness = pm4py.fitness_alignments(test_log, net, im, fm)
    results['test_fitness'] = test_fitness
    if test_fitness.get('average fitness', 0.0) < 0.7:
        results['reject'] = True
        results['reason'] = 'Model does not generalize (test_fitness < 0.7)'
        return results
    
    # 3. Train-holdout gap
    train_fitness = pm4py.fitness_alignments(train_log, net, im, fm)
    gap = abs(train_fitness.get('average fitness', 0) - test_fitness.get('average fitness', 0))
    results['fitness_gap'] = gap
    if gap > 0.2:
        results['reject'] = True
        results['reason'] = f'Model overfits (fitness gap {gap:.3f} > 0.2)'
        return results
    
    # 4. Soundness
    sound = pm4py.check_soundness(net, im, fm, print_diagnostics=False)
    results['sound'] = sound
    if not sound:
        results['reject'] = True
        results['reason'] = 'Model is not sound'
        return results
    
    results['reject'] = False
    return results
```

| Use case | Priority | Rationale |

# 4. Adversarial Review of Model C

## Strongest case *for* Model C

1. **High precision (0.941)** — the model constrains behavior tightly to observed variants, which is desirable for enforcement where conservatism is valued (F8: unseen behavior should be treated as noncompliant until approved).
2. **Rejects clearly forbidden traces** — B3, B4, and B8 are all rejected because no branch omits the checks, puts ER before them, or repeats a check without correction.
3. **Audit-friendly branch enumeration** — each branch is a concrete, reviewable scenario. An auditor can point to "branch 3" and say "this is the external, non-expedited, manager-approved path."
4. **Training fitness (0.973)** — covers most observed behavior with high fidelity.
5. **Exactly-one approval is structurally guaranteed** — every branch has exactly one of Manager/Auto, satisfying P5 unambiguously.

## Strongest case *against* Model C

The model is an **enumeration of memorized training variants**, not a structural description of the process. Its eight branches cover exactly the combinations seen in training and nothing else. This causes:

### Branch enumeration
Eight branches, each a fixed-length sequence. The combinatorial space of valid combinations (check order × SR present × ER present × correction × approval type) is at least 2 × 2 × 2 × 2 × 2 = 32 (more with correction variants). Model C covers 8 of 32. Each new valid combination requires manually adding a branch, re-running all metrics, and re-approving. This is O(n) per variant with n growing unboundedly.

### Duplicate labels (33)
With eight branches all containing "Credit Check" and "Technical Review," the same activity label appears on multiple transitions across branches. Effects:
- **Alignment ambiguity:** when aligning a trace with CC, which of the several CC-labeled transitions should it match? Different matches can produce different alignment costs, distorting both fitness and precision.
- **Precision distortion:** duplicate transitions can inflate precision by giving the model more ways to "narrowly" match positive traces.
- **Impact analysis (F3):** changing the semantics of "Credit Check" requires finding and auditing every instance across all branches.

### Unseen combinations
F4 identifies holdout cases combining Supplier Review, Auto Approval, and alternate check order in ways absent from training. Model C has no branch for:
- `TR, CC, Auto` (probe B2 — *valid*)
- `TR, CC, SR, ER, Auto` (probe B5 — *plausible valid*)
- `CC, TR, SR, Auto` (F4's issue)

F2 (Operations) correctly notes that Model C "rejects legitimate new combinations of already known behavior." Rejecting valid traces is a governance failure on par with accepting forbidden ones.

### Correction handling
Only one correction pattern exists (branch 7): `Correct, CC, TR` — both checks re-run. P6 explicitly allows re-running only the affected check (F6). Model C cannot represent:
- Correction with only CC re-running
- Correction with only TR re-running
- Correction combined with Supplier Review or Auto Approval
- Multiple corrections

### Holdout degradation (0.973  0.744)
A 0.23 drop is severe. It indicates that the model has memorized specific training sequences rather than learning transferable structure. The token-based generalization (0.412) confirms this: the model produces very few valid traces not already seen.

### Maintainability
Simplicity of 0.281 and stakeholder comprehension of 1.9 mean no one can realistically understand or update the model. F3 (IT architecture) flags branch enumeration as making "impact analysis and ownership difficult."

### High precision as memorization artifact
F5 states precision was computed only against observed positive traces with no negative suite. A model that reproduces training variants *exactly* will score high precision on training data *by construction*—it memorized the answer key. Whether Model C also rejects forbidden behavior is untested. The high precision number is therefore **unverified for its intended purpose** (enforcement).

# 6. Likely Metric Pathologies

## Ranked by likely decision impact

### 1. Fitness rewarded by optionalizing mandatory behavior *(highest impact)*
Model S wraps Credit Check and Technical Review in `X(activity, tau)`, making them optional. This directly inflates fitness: the model "fits" a trace like `Register, Manager, Release` by producing tau where CC and TR should be. A model that makes mandatory behavior optional will always show high fitness on logs with incomplete data. **Impact:** A governance board might see 0.992 training fitness and conclude Model S "works," when in fact it works by discarding the very constraints that matter for compliance.

### 2. Positive-log-only precision *(highest impact)*
F5 explicitly states that no curated negative suite was used. Precision computed only against positive traces answers: "How tightly does the model constrain behavior *similar to what was observed*?" It does not answer: "Does the model reject *forbidden* behavior?" A model that memorizes all training variants will have high positive-trace precision by construction (Model C: 0.941), yet may still admit forbidden traces in ways the metric cannot detect. **Impact:** Model C's primary advantage—high precision—is unverified for its intended enforcement use.

### 3. Train/holdout leakage or split sensitivity *(high impact)*
No random seed, preprocessing code, or held-out cases were published. Model C's holdout fitness drop (0.973  0.744) is dramatic, but without the seed we cannot confirm it isn't an artifact of an unlucky split (e.g., holdout containing a rare variant not in training). Conversely, Model S's high holdout score (0.981) could be inflated if preprocessing (e.g., activity filtering, case merging) leaked information from the holdout set. **Impact:** Both the "Model C overfits" and "Model S generalizes" claims are provisional until the split is reproduced.

### 4. Missing-event bias *(moderate-high impact)*
F4 notes that some Supplier Review events may be missing from the log. This means:
- Models trained on this log under-learn Supplier Review patterns (frequency, ordering).
- Metrics involving SR (fitness on SR-containing traces, precision of SR placement) are unreliable.
- The external/internal attribute is missing entirely, so no model can learn the gating rule for P3 from data.
**Impact:** Any conclusion about Supplier Review behavior—including which model handles it better—is based on incomplete evidence.

### 5. Generalization rewarded by excessive permissiveness *(moderate impact)*
Token-based generalization (TBR) rewards models that produce many valid unseen traces. Model S's TBR of 0.907 is consistent with its broad permissiveness: a model that accepts nearly any combination of activities will generate many "valid" unseen traces. But TBR does not distinguish between *useful* generalization (handling novel-but-valid combinations) and *harmful* over-generalization (admitting forbidden behavior). **Impact:** TBR should never be used in isolation; it must be read alongside precision and negative-trace fitness.

### 6. Duplicated-label effects *(moderate impact)*
Model C reports 33 duplicate labels with an undocumented definition. If duplicates mean the same activity label appears on multiple transitions (across branches), they cause:
- Alignment ambiguity: which transition should a trace event match?
- Precision distortion: more transitions = more narrow alignments = potentially inflated precision.
- Impact analysis difficulty (F3).
**Impact:** If duplicates inflate Model C's reported precision, the model's strongest metric is unreliable.

### 7. Silent-transition effects *(moderate impact)*
Model S uses four `tau` alternatives (one per optional activity). Silent transitions create invisible paths through the model, increasing the number of possible alignments for a given visible trace. This:
- Lowers precision (more silent paths = more ways to "match" the same trace).
- Can inflate fitness (model "fits" by producing tau instead of visible activities).
- Obscures what the model actually does—stakeholders see a diagram with four activities, but the model's behavior space includes many more traces.
**Impact:** Model S's low precision (0.584) is partly a structural consequence of its tau-heavy design, not necessarily a discovery error.

### 8. Alignment-cost sensitivity *(moderate impact)*
All alignment metrics depend on the cost assigned to insert, delete, and move operations. No cost settings were published. Different cost configurations can change model rankings: for example, if move costs are high, Model S's parallel structure (which forces many moves for ordered traces) would be penalized more, while Model C's fixed sequences would fare better. **Impact:** Without documented costs, the reported numbers are not independently reproducible.

### 9. Stakeholder-score methodology *(moderate impact)*
The "informal 1–5 score" has no documented protocol: no named respondents, no question wording, no scale anchors, no inter-rater reliability. The score of 4.4 vs. 1.9 is directionally meaningful (Model C is harder to understand) but should not be treated as quantitative evidence. **Impact:** Stakeholder comprehension matters for governance, but the current number cannot support a deployment decision.

### 10. Runtime confounding by model size *(lowest impact)*
Model C's 0.440 s vs. Model S's 0.018 s is primarily explained by model size (8 branches, ~60 transitions vs. ~10 transitions). This is a computational property, not a quality metric. It becomes relevant only if alignment runs in a real-time pipeline. **Impact:** Low. Do not weight runtime heavily in a model-selection decision unless latency requirements are specified.

# 7. Third Alternative

## Strategy

**POWL procedural backbone + post-hoc policy checks.** The POWL model encodes the *structural* control-flow constraints (ordering, mandatory/optional, XOR choices). Data-dependent behaviors that cannot be expressed in the control-flow model (correction re-check specifics, attribute-gated Supplier Review) are enforced by explicit, separately testable policy checks. This hybrid is chosen because:

- POWL's strict partial order naturally expresses "unordered but constrained" relationships (e.g., CC and TR are both mandatory but unordered) without enumerating branches.
- XOR nodes cleanly express optional and choice behavior.
- Post-hoc checks make *visible* what the control-flow model does not enforce—no silent gaps.
- The missing attributes (external/internal, affected-check) are honestly documented as limitations rather than papered over by making everything optional.

## 1. Compact formal description

```
model_third = StrictPartialOrder(
  N = { Register, CreditCheck, TechnicalReview, OptCorrect, OptSupplier, OptExpedite, Approval, Release }
  
  Mandatory:  Register, CreditCheck, TechnicalReview, Release
  Optional:   OptCorrect  = XOR(CorrectRecheck, )
              OptSupplier = XOR(SupplierReview, )
              OptExpedite = XOR(ExpediteReview, )
  Recheck:    Recheck     = XOR(CreditCheck', TechnicalReview', (CreditCheck'  TechnicalReview'))
  Approval:   Approval    = XOR(ManagerApproval, AutoApproval)
  
  Order:
    Register  {CreditCheck, TechnicalReview, OptCorrect, OptSupplier, OptExpedite, Approval, Release}
    CreditCheck  {OptCorrect, OptSupplier, OptExpedite, Approval}
    TechnicalReview  {OptCorrect, OptSupplier, OptExpedite, Approval}
    OptCorrect  Approval
    OptSupplier  Approval
    OptExpedite  Approval
    Approval  Release
    
  No order between: CreditCheck  TechnicalReview (P2: either order)
  No order between: OptCorrect  OptSupplier  OptExpedite (unordered optional block)
  
  External policy checks (post-hoc, not in control flow):
    [E1] Recheck after correction
    [E2] No unjustified recheck (P7)
    [E3] Supplier Review attribute gating (P3, when attribute available)
```

## 2. Self-contained PM4Py code

```python
import pm4py
from pm4py.objects.powl.obj import (
    Transition, SilentTransition, OperatorPOWL, StrictPartialOrder, Operator
)

#  Atomic transitions 
t_register = Transition(label='Register Dossier')
t_credit   = Transition(label='Credit Check')
t_tech     = Transition(label='Technical Review')
t_supplier = Transition(label='Supplier Review')
t_expedite = Transition(label='Expedite Review')
t_correct  = Transition(label='Correct Dossier')
t_manager  = Transition(label='Manager Approval')
t_auto     = Transition(label='Auto Approval')
t_release  = Transition(label='Release Order')
tau        = SilentTransition()

#  Optional Supplier Review (P3: gated by missing attribute) 
opt_supplier = OperatorPOWL(operator=Operator.XOR, children=[t_supplier, tau])

#  Optional Expedite Review (P4) 
opt_expedite = OperatorPOWL(operator=Operator.XOR, children=[t_expedite, tau])

#  Recheck choice after correction (P6; affected-check attr missing) 
r_cc_1  = Transition(label='Credit Check')
r_tr_1  = Transition(label='Technical Review')
r_cc_2  = Transition(label='Credit Check')
r_tr_2  = Transition(label='Technical Review')

recheck_choice = OperatorPOWL(operator=Operator.XOR, children=[
    r_cc_1,                                                  # only Credit Check
    r_tr_1,                                                  # only Technical Review
    StrictPartialOrder(nodes=[r_cc_2, r_tr_2])               # both (unordered)
])

#  Correction block: Correct  Recheck 
corr_block = StrictPartialOrder(nodes=[t_correct, recheck_choice])
corr_block.order.add_edge(t_correct, recheck_choice)

#  Optional correction (single occurrence; see Limitation 3) 
opt_correct = OperatorPOWL(operator=Operator.XOR, children=[corr_block, tau])

#  Exactly one approval (P5) 
approval = OperatorPOWL(operator=Operator.XOR, children=[t_manager, t_auto])

#  Main partial order 
model_third = StrictPartialOrder(nodes=[
    t_register,
    t_credit,          # mandatory  (P2)
    t_tech,            # mandatory  (P2)
    opt_correct,       # optional correction + embedded recheck (P6)
    opt_supplier,      # optional   (P3)
    opt_expedite,      # optional   (P4)
    approval,          # exactly one (P5)
    t_release          # mandatory, last (P1)
])

# P1 — Register first
model_third.order.add_edge(t_register, t_credit)
model_third.order.add_edge(t_register, t_tech)
model_third.order.add_edge(t_register, opt_correct)
model_third.order.add_edge(t_register, opt_supplier)
```

## 3. Declarative dictionaries / external policy checks

```python
def check_recheck_after_correction(activities):
    """E1 — P6: If Correct Dossier appears, 1 of CC/TR must follow before approval."""
    if 'Correct Dossier' not in activities:
        return True
    ci = activities.index('Correct Dossier')
    approval_labels = {'Manager Approval', 'Auto Approval'}
    for i in range(ci + 1, len(activities)):
        if activities[i] in approval_labels:
            between = activities[ci + 1:i]
            return ('Credit Check' in between or 'Technical Review' in between)
    return False   # no approval after correction


def check_no_unjustified_recheck(activities):
    """E2 — P7: Repeated CC/TR without a preceding Correct Dossier is suspicious."""
    for act in ('Credit Check', 'Technical Review'):
        indices = [i for i, a in enumerate(activities) if a == act]
        for idx in indices[1:]:
            if not any(activities[j] == 'Correct Dossier' for j in range(idx)):
                return False
    return True


def check_supplier_review_gated(activities, case_attrs):
    """E3 — P3: SR only for external orders (requires attribute)."""
    if 'Supplier Review' not in activities:
        return True
    ext_int = case_attrs.get('external_internal')
    if ext_int is None:
        return None   # indeterminate — attribute missing
    return ext_int == 'external'


# Declarative constraint dictionary (for DECLARE-based tooling)
declare_constraints = [
    {'type': 'response',  'source': 'Correct Dossier',
     'target': ['Credit Check', 'Technical Review'],
     'semantics': 'at_least_one',   # at least one recheck target after source
     'check': check_recheck_after_correction},
    {'type': 'not_cooccur_without',
     'source': ['Credit Check', 'Technical Review'],
     'requires': 'Correct Dossier',
     'semantics': 'repetition_requires_correction',
     'check': check_no_unjustified_recheck},
    {'type': 'conditional_absence',
     'source': 'Supplier Review',
     'condition': 'external_internal == "external"',
     'check': check_supplier_review_gated},
]
```

## 4. Explicit semantics

| Requirement | How `model_third` handles it |
|---|---|
| **Mandatory checks (P2)** | `t_credit` and `t_tech` are direct nodes in the strict partial order (not wrapped in XOR). They *must* execute. No edge between them allows either order. |
| **Optional Supplier Review (P3)** | `opt_supplier = XOR(t_supplier, tau)`. Present XOR absent. Attribute gating is enforced by external check **E3**, not the control-flow model (attribute missing from log). |
| **Expedite Review ordering (P4)** | `opt_expedite = XOR(t_expedite, tau)`. Edges `t_credit  opt_expedite` and `t_tech  opt_expedite` enforce ER after *both* checks. Edge `opt_expedite  approval` enforces ER before approval. No edge between `opt_expedite` and `opt_supplier` allows ER before or after SR. |
| **Exactly-one approval (P5)** | `approval = XOR(t_manager, t_auto)`. Exactly one of the two labels is produced. |
| **Correction / recheck (P6)** | `opt_correct = XOR(corr_block, tau)` where `corr_block = Correct  Recheck`. The recheck is `XOR(CC, TR, CC  TR)` — at least one check re-runs, possibly both. This handles "only affected checks repeat" by allowing the auditor to verify which check was affected (external check **E1** confirms 1 recheck occurred). |
| **Repeated check without correction (P7)** | Not enforceable in the control-flow model alone (repeated CC/TR is structurally impossible without correction in the POWL, since each mandatory node appears once). External check **E2** provides a belt-and-suspenders validation. |

## 5. Limitations caused by missing attributes

| Limitation | Cause | Impact | Mitigation |
|---|---|---|---|
| **Supplier Review not attribute-gated** | External/internal attribute missing from discovery log (P3). | Model allows SR on any case (present or absent). Cannot enforce "SR only for external." | External check **E3** returns `True`/`False`/`None` when attribute is available; `None` triggers a manual review flag. When attribute is added to log, refine with attribute-conditioned model family or data-aware DECLARE constraint. |
| **Recheck specificity unknown** | Affected-check attribute missing (P6). | Recheck allows any of {CC, TR, both}. Cannot verify that the *correct* check re-ran — only that *at least one* did. | External check **E1** confirms 1 recheck. When attribute becomes available, constrain `recheck_choice` to the specific affected check. |
| **Single correction occurrence** | POWL loop semantics do not cleanly model "correction re-runs a subset of checks, then flow continues." | Traces with 2+ corrections have alignment cost > 0 (second Correct is unmatched). | External check **E1** validates recheck after *each* correction. Future extension: wrap `opt_correct` in a POWL `LOOP` node (accepting that both checks re-run conservatively) or build a small family of models parameterized by correction count. |
| **SR ordering relative to checks** | P3 does not explicitly require SR after checks; model places SR after checks based on observed data and business logic. | If policy later allows SR before checks, model needs edge removal. | Document the assumption; revisit if policy clarifies. |

**Explicit non-solution:** These limitations are **not** addressed by making activities optional or by removing ordering constraints. The model retains hard structural constraints for mandatory behavior; gaps are documented and handled by external checks with explicit `None` (indeterminate) states when attributes are missing.
