## 1. Consistency rules and evidence model

### Hard invariants
These are strict, non-negotiable rules that must hold for any valid repair.

- **Hard invariant 1:** Every `Create Order` event must be linked to exactly one Order object.
- **Hard invariant 2:** Every `Add Item` event must be linked to exactly one Order and one Item object.
- **Hard invariant 3:** Every `Pack Item` event must be linked to exactly one Item and one Package object.

### Strong defaults
These default assumptions guide the selection of plausible repairs.

- **Strong default 1:** Timestamp proximity and identifier similarity (e.g., C17 across multiple events) strongly suggest the same logical entity.
- **Strong default 2:** Cardinality consistency (e.g., an Order with multiple Items) should be respected unless an explicit "weak heuristic" suggests otherwise.
- **Strong default 3:** Payment events must relate to an Invoice for the same Order/customer, unless there is an unexplained cash payment.

### Weak heuristics
These are soft cues that can guide but do not dictate the repair.

- **Weak heuristic 1:** O2O relations are directional and should align with the natural flow of goods (e.g., `Pack Item` should imply `Dispatch Package`).
- **Weak heuristic 2:** Consistent use of prefix "N-" for carrier references in `Dispatch Package` and `Confirm Delivery` suggests a single carrier for these two events.
- **Weak heuristic 3:** Invoice amounts (e.g., 230) should match the declared value of the Order they reference unless there is a known fee/discount mechanism.

### Evidence against a repair
Evidence that disqualifies a repair includes:

- **Evidence against 1:** A payment event referencing an Invoice that does not share the same Order or customer.
- **Evidence against 2:** An `Pack Item` event without a corresponding `Dispatch Package` event.
- **Evidence against 3:** Invoice total does not equal the sum of declared values of its related Orders.

These rules are applied consistently across both the conservative repair (Bundle A) and the alternative repairs (Bundles B and C).

## 5. Lifecycle and cardinality audit

### Object type: Order
- **Repair status:** All Orders (ORD-A, ORD-B) are now linked to at least one Item and one Invoice.
- **Lifecycle:** Orders have a clear start (Create Order) and end (Invoice) lifecycle. There is no end event for ORD-B in the repaired log, but this is acceptable as the repair does not claim to cover every possible state transition.
- **Cardinality:** Each Order has exactly one Invoice, respecting the strong default that invoices are tied to orders.
- **Orphan objects/events:** None identified. All Items and Payments are linked to Orders and Invoices.

### Object type: Item
- **Repair status:** Items IT-A1, IT-A2, and IT-B1 are now linked to Orders and have a packing event.
- **Lifecycle:** Items have a clear lifecycle from creation (Add Item) to packaging (Pack Item) and potentially dispatch (Delivery).
- **Cardinality:** Each Item appears exactly once, respecting the strong default that an item is added to a single order.
- **Orphan objects/events:** None identified.

### Object type: Package

- **Lifecycle:** Packages have a clear lifecycle from creation (Pack Item) to dispatch (Dispatch Package) and delivery (Delivery).

- **Orphan objects/events:** None identified.

### Object type: Delivery

- **Lifecycle:** Deliveries have a clear lifecycle from dispatch (Dispatch Package) to confirmation (Confirm Delivery).

### Object type: Payment

- **Lifecycle:** Payments have a clear lifecycle from recording (Record Payment) to settlement (Confirm Delivery).

### Circular reasoning audit
- **Circular reasoning check:** The repair does not rely on previously assumed E2O edges to validate O2O edges. Each relation is justified independently by evidence from both E2O and O2O relations.
- **Independent confirmation:** Both E2O and O2O evidence support the final structure, ensuring that no single source of evidence is used to confirm another.
