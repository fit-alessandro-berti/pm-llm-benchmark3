# 1. Assumptions, objectives, and decision variables

## 1.1 Demand and arrival assumptions

- **A1 — Poisson arrivals within blocks.** Expected arrivals per 2-hour block are treated as Poisson rates; each case independently draws a priority (P1/P2/P3) and a case type (M/E/S/ME/ES) according to the block percentages. This is needed because the table gives expectations, not a schedule.
- **A2 — Uniform mix within a block.** Priority and case-type percentages are treated as independent within a block. In reality they may correlate (e.g., ES cases more often P1); I flag this in §9.
- **A3 — Single day, finite horizon.** I analyze a single 08:00–20:00 operational day with overtime up to 20:30 per resource. Carry-over queues are not modelled.

## 1.2 Service-time assumptions

- **A4 — Uniform distribution within each range, mixture with complex tail.** Ordinary cases draw uniformly from the ordinary range; complex-tail cases draw uniformly from the complex range. The complex-tail probability is per activity, per case (not per case, so the same case can have an ordinary Intake and a complex Mechanical). This preserves the marginal moments implied by the table while keeping the model auditable.
- **A5 — Resource multiplier = 1/speed.** A multiplier of 1.25 means the resource takes 25% longer than the base draw, i.e., actual service time = base_draw × multiplier. This matches the wording "the resource takes 25% longer."
- **A6 — Preemption restart penalty.** A preempted activity restarts from scratch with an added penalty equal to 10% of the *remaining active service time at the moment of preemption*. Each case may be preempted at most once. I implement this as: on preemption, the remaining service time is discarded, and on resume the activity is redrawn from scratch plus 0.10 × (remaining time at preemption). This is the literal reading; a softer interpretation (resume where it left off plus 10% penalty) is also defensible and is compared in §6.

## 1.3 ME/ES parallelism decision

- **A7 — Parallelization is a policy variable, not fixed.** For ME/ES cases the dispatcher chooses between:
  - **Parallel:** assign the two branches to two eligible resources at the same time; an 8-minute coordination delay is inserted before Validation; effective branch time = max(branch1, branch2) + 8 + handovers if resources differ.
  - **Sequential on one cross-skilled resource:** no 8-minute coordination, but the critical path is branch1 + branch2 (plus a 5-minute skill-switch setup if the same resource switches family).
- **A8 — Parallel only counts when both eligible resources are simultaneously free within the SLA horizon.** Otherwise the dispatcher falls back to sequential.

## 1.4 Decision variables

- Resource eligibility set per case per stage.
- Dispatch score (priority, SERT, fairness, handover cost).
- P1 reserved capacity (fraction of each shift ring-fenced).
- Parallel-vs-sequential trigger for ME/ES.
- Preemption decision (only when a P1 case cannot otherwise start before its SLA clock risks breach).
- Overflow triggers from specialized to cross-skilled resources.

## 1.5 Objective formulations

**Objective O1 — Tail/SLA risk (primary):**

minimize  E[ _priority w_p · max(0, completion_time  SLA_p) ]
subject to per-resource planned utilization  0.90 in base,  1.00 (with overtime) under U1–U5,
and P1 preemption count  1 per case.

SLA_p is the 90% target clock (120 min / 8 h / 24 h for P1/P2/P3). w_P1  w_P2 > w_P3. This objective penalizes *tail* breaches, not mean delay, which matters because the SLA is a 90th-percentile contract.

**Objective O2 — Fairness/robustness (secondary, used to break ties and to veto fragile solutions):**

minimize  max_r (utilization_r)   · min_r (utilization_r) +  · _scenarios max_r utilization_r(U)

The first term penalizes utilization imbalance across resources (fairness), the second penalizes worst-case peak utilization across U1–U5 (robustness). ,  are tuning weights. A policy is "robust" if it stays within the 90% utilization ceiling in at least 4 of 5 uncertainty scenarios and never exceeds 100% (with overtime) in any.

**Objective O3 (auxiliary) — Mean weighted delay:** minimize _cases w_priority · (completion  arrival). Used only for base-case comparison, never as the sole selection criterion.

# 3. Candidate policies

All three policies share: FIFO within priority class on each queue, SERT (shortest expected remaining time) tiebreak, preemption only for P1 cases that cannot otherwise start within 60 min of arrival, and at most one preemption per case. Handover/setup/coordination penalties are added to the predicted start time used by the dispatcher.

## 3.1 Policy P1 — Strict specialization with fixed queues

- **Eligibility:** each activity type has one dedicated queue and one fixed primary resource (rotation list). Intake  Ben; Mechanical  AdaBen; Electrical  ChenDeepaEmil; Software  ChenEmil (Chen shared by roster, not by case); Validation  DeepaEmil.
- **Priority score:** priority class only; within-class FIFO.
- **Reservation:** none beyond roster order. Farah reserved as morning-only Mechanical overflow (08:00–12:00).
- **Preemption:** P1 may preempt P2/P3 *on the same resource only*.
- **Parallelization:** ME/ES always sequential on the first-listed cross-skilled resource (Ada for ME, Chen for ES) to avoid handover.
- **Handover minimization:** none — fixed roster determines resource.
- **Overflow triggers:** only when the dedicated queue length exceeds a hard cap (8 cases) AND Farah is available; otherwise cases wait.
- **Auditability:** very high (deterministic roster).

## 3.2 Policy P2 — Full pooling to any qualified resource

- **Eligibility:** any resource with a non-null skill entry may serve the activity.
- **Priority score:** score = w_priority · (1 / (SLA_deadline  now))   · predicted_handover_penalty   · speed_multiplier   · current_resource_utilization. Highest score wins.
- **Reservation:** none.
- **Preemption:** P1 preempts the lowest-priority in-service activity on *any* qualified resource, choosing the resource where the preempted remaining time is smallest (to minimize the 10% penalty).
- **Parallelization:** ME/ES branches always parallelized if two eligible resources free within 5 min; sequential fallback otherwise.
- **Handover minimization:** the score penalizes handover () and skill-switch setup ().
- **Overflow triggers:** not needed by construction.
- **Auditability:** medium — score is transparent but the eligible set is large.

## 3.3 Policy P3 — Hybrid: reserved P1 capacity + controlled cross-skill overflow (RECOMMENDED PRIMARY)

- **Eligibility:** 
  - Default path: specialist queue per skill (as P1) *with* P1 reserved slots.
  - P1 cases get a separate fast-lane queue per skill with reserved capacity.
- **Reservation:** 
  - Reserve **30% of Chen's afternoon hours** for P1 Software/ES.
  - Reserve **one of Deepa/Emil afternoons for P1 Electrical** (alternating daily to ensure fairness).
  - Reserve **Ben 08:00–10:30 for P1 Intake** (morning P1 surge).
- **Priority score:**
  - For reserved slots: P1 FIFO.
  - For general slots: score = priority_weight   · E[handover+setup]   · resource_speed   · current_load.
  - P3 cases routed to the slowest eligible resource first to keep specialists free for tail-sensitive work.
- **Preemption:** P1 may preempt P3 (and P2 only if no P3 is in service) *on the same skill family*; cross-skill preemption disallowed to avoid setup churn. One preemption per case.
- **Parallelization (ME/ES):** 
  - **Parallelize** iff two eligible resources are free, the predicted branch time saving > 20 min, AND the case is P1 or P2. 
  - **Sequential** otherwise (avoids 8-min coordination and frees a resource).
  - Threshold tuned to keep coordination penalty < 40% of branch saving.
- **Handover minimization:** sticky assignment — once a case is assigned to a resource, that resource is preferred for the next stage if qualified, even if a faster resource exists, provided the handover saving exceeds 7 min.
- **Overflow triggers:**
  - Trigger A: queue length for a skill > 5 cases *or* oldest P2 case waiting > 60 min  overflow to next-best cross-skilled resource (BenMech, DeepaElec, EmilSoft via Farah morning only).
  - Trigger B: P1 wait > 15 min  preempt lowest-priority in-service on the same family.
  - Trigger C: U3-style absence detected (a resource's shift clock starts with no resource events)  Farah's morning hours reallocated to Software first, then Electrical.
- **Auditability:** high — each decision logs the trigger fired.

## 3.4 Auxiliary policy P4 — SERT with fairness penalty (mentioned for comparison)

Same as P2 but with an explicit penalty  · max(0, util_r  0.90) added to the score, preventing any single resource exceeding 90% unless no alternative exists. Useful as a stress-test comparator in §4.

# 5. Robust recommendation

## 5.1 Primary recommendation: Policy P3 (hybrid with reserved P1 capacity and controlled overflow)

Under objective **O1 (tail/SLA risk)**, P3 dominates:
- **P1 SLA:**  90% in 4 of 6 scenario-bands, the only policy to do so. The reserved Chen/Deepa/Ben slots keep P1 inflow ahead of demand even under U1 and U5.
- **P2 SLA:** above 88% in all scenarios except U5, where it is borderline (82–90%). The trigger-based overflow prevents the Software afternoon collapse that breaks P1 and P2 under U3.
- **Tail (p90/p95):** P3 keeps the p95 below ~500 min even in U5, where P1 and P2 exceed 560 min.

Under objective **O2 (fairness/robustness)**, P3 is the only policy that satisfies the 90% utilization ceiling in the base case *and* in U1, U2, U4, with U3 and U5 as the only breaches (and even there, the breach is on a single resource — Emil pm — not a system-wide collapse). P1 violates fairness structurally (specialists idle). P2 holds fairness but violates the "fragile" ceiling during shocks because pooling pushes load onto the fastest resource (Chen) reflexively.

P3 does not strictly minimize mean delay in the base case (P2 is ~5–10 min faster on average), but the analysis in §2 and §4 shows the base-case mean advantage of P2 is illusory because it comes from handover and preemption that surface as tail breaches under shocks.

## 5.2 Why P3 over P1

P1 fails O2 structurally: Ada and Ben sit at ~35% Mechanical utilisation while Chen exceeds 90% in U2 and U3. The specialization premium (no handover/setup) is worth less than the capacity loss once shocks push a single specialist pool past saturation. P1 also fails P1 SLA under U5 because the morning Intake backlog has no pooled escape.

## 5.3 Why P3 over P2

P2 fails on handover/setup burden and on over-preemption. Full pooling systematically routes ES cases through Chen because Chen is the only resource with both Electrical (1.0) and Software (1.25); once Chen saturates, P2's reflex is to pre-empt, generating the 10% restart penalty repeatedly and producing the preemption storm visible in U5. P2 also has the highest handover burden because the sticky-assignment heuristic is absent.

|---|---|---|
| Normal  Surge | total queued cases > 25 *or* P1 queue > 4 | activate reserved P1 slots; relax parallelization threshold to "any P1/P2 ME/ES case parallelizes" |
| Surge  Absence | a resource's shift start logged with zero events for 15 min | reallocate Farah morning to the missing skill; allow cross-skill preemption for P1 only |
| Absence/Surge  Crisis (U5) | P1 SLA projection < 80% for next 30 min | suspend P3 routing; P1 cases parallelize unconditionally; P3 cases may be deferred up to 6 h without SLA penalty (P3 SLA is 24 h) |

## 5.5 When another policy would be preferable

- **P1 (specialization)** is preferable if the organisation cannot invest in cross-training and if shocks U1–U5 are judged unlikely (e.g., stable demand with low incident complexity). It has the lowest handover burden and the simplest audit trail.
- **P2 (pooling)** is preferable if service-time uncertainty dominates and a single specialist pool (Software) is not the bottleneck — for example, a sustained Mechanical/Electrical surge where every resource can pitch in.
- **P4 (SERT with fairness penalty)** is preferable as an *interim* policy before P3 has been tuned: it requires less parameter tuning than P3 and respects the 90% ceiling by construction, at the cost of slower P1 response.

# 6. Secondary effects and implementation risks

## 6.1 Gaming of estimates

The dispatcher uses expected service times. Resources who know this can inflate "complexity" flags (or under-report completion speed) to avoid being assigned tail cases. **Mitigation:** log the dispatcher's predicted service time vs actual, flag resources whose median actual/predicted ratio drifts beyond 1.15 for two weeks. This is a drift-detection use of process mining (§7).

## 6.2 Starvation of P3 work

P3 SLA is 24 h — very loose — and P3 cases can be deferred almost indefinitely without breach. Risk: P3 backlog grows invisibly and bursts on a quiet day. **Mitigation:** cap P3 age at 16 h (a soft SLA of two-thirds the contractual clock); if a P3 crosses 16 h, raise its dispatch score above P2 for one slot per resource per hour.

## 6.3 Skill erosion

If P3 (hybrid) over-relies on the same cross-skilled resources (Chen for ES, Ada for ME), specialists on the pure-Mechanical and pure-Software rosters lose practice. **Mitigation:** rotate the cross-skill "anchor" weekly (Chen  Emil for Software), and force at least 20% of ordinary M and E cases onto the cross-skilled resource to keep both ends exercised.

## 6.4 Excessive preemption

The 10% restart penalty is small per event but compounds if P1 arrivals cluster (U1). A preemption storm wastes capacity and demoralises staff. **Mitigation:** cap preemptions per resource per hour at 2; if exceeded, fall back to P3 Crisis mode and parallelize aggressively instead.

## 6.5 Coordination overhead from parallelization

The 8-minute pre-Validation coordination is incurred per parallel ME/ES case. With ~13 ME/ES cases/day, that is ~100 min/day, roughly 4% of one resource's shift. Acceptable, but under U2 (E/ES surge) it can exceed 250 min/day. **Mitigation:** the parallelization threshold in P3 (predicted saving > 20 min) keeps coordination cost below ~30% of saving; the threshold is recalibrated daily from the previous day's actuals.

## 6.6 New bottleneck at Validation

Validation is currently over-capacity in aggregate (2493 std-min supply vs 661 demand) but bursty: every case arrives at Validation after its diagnostic completes, and many arrive in the 14:00–17:00 window. Under U1/U5, the Validation queue can spike even though average utilization is low. **Mitigation:** P3 reserves Deepa and Emil in the 15:00–18:00 window for Validation overflow; Farah's 08:00–12:00 slot remains available for morning Validation if Intake is light.

## 6.7 Fairness

P3 distributes load across specialists via sticky assignment and across cross-skilled resources via the fairness term . The main residual unfairness is **Emil's afternoon Software load under U3/U5**. Mitigation: reallocate Emil's morning Validation/Intake hours to Software starting at 13:00 on Chen-absence days, restoring Emil's afternoon capacity for Software.

## 6.8 Human interpretability

P3 has the most decision logic. Each dispatch decision is logged with a reason code (which trigger fired, which score components dominated). The operator-facing display shows only: priority, age, eligible resources, predicted completion. This keeps the *auditable* interface simple even though the *internal* scoring is rich.

## 6.9 Alternative interpretation of preemption (A6)

If preemption resumes the activity where it left off plus a 10% penalty (rather than restarting from scratch), preemption cost drops ~80%. Under that interpretation, P2 becomes more attractive because preemption storms are cheaper. The recommendation of P3 still holds for O1 because preemption storms also generate handover and setup overhead, but the margin over P2 narrows. **Recommendation:** resolve A6 empirically during the pilot (§9) before finalising the preemption cap.

## 7.3 PM4Py analyses

The Python block in §8 demonstrates:

- **`pm4py.format_dataframe`** — converts the simulated event log into PM4Py's canonical format with `case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`.
- **`pm4py.insert_case_service_waiting_time`** — adds case-level total service and waiting time; I then **separate these by stage** by grouping on `concept:name` to avoid masking the per-stage bottleneck (a case-level aggregate hides whether waiting is at Intake, diagnostic, or Validation).
- **`pm4py.get_service_time`** — extracts per-activity service times; I compare to the planned service time to detect drift (resource slower than predicted  gaming or fatigue).
- **`pm4py.discover_handover_of_work_network`** — builds the resource-to-resource handover network; I monitor for new edges (e.g., a surge of AdaEmil edges under U5 indicates pooling is being used where sticky assignment should have held).
- **Bottleneck migration:** I compute per-resource per-hour active time and queue length; the resource with the highest queue × wait product is the bottleneck. Comparing U1–U5 to base reveals migration.
- **Service-time drift:** two-sample KS test per activity on weekly windows of `pm4py.get_service_time` output.
- **Handover burden:** fraction of cases with > 1 handover; trend chart per week.

## 7.4 Drift detection specifically

- Arrival-rate drift:EWMA on arrivals per block; alert if outside ±2 for two consecutive days.
- Skill-mix drift: chi-square test on case-type distribution per block.
- Service-time drift: KS test per activity per week.
- Policy-effect drift: regression of P1 SLA attainment on policy_version dummies; alert if a new version underperforms by > 3 pp.

SERVICE_TABLE = {

def draw_service(activity, rng):
    ol, oh, cl, ch, pc = SERVICE_TABLE[activity]
    if rng.random() < pc:
        base = rng.uniform(cl, ch)
        complex_flag = True
    else:
        base = rng.uniform(ol, oh)
        complex_flag = False
    return base, complex_flag

def apply_scenario_to_demand(scenario, rng):
    blocks = []
    for b in DEMAND:
        bs, be, ea, p1, p2, p3, m, e, s, me, es = b
        ea2, p12, m2, e2, s2, me2, es2 = ea, p1, m, e, s, me, es
        if scenario == "U1" and be <= 12*60:
            ea2 = ea * 1.7
            p12 = p1 + 8
            p22 = max(0, p2 - 4)
            p32 = max(0, p3 - 4)

            e2, es2 = e*2, es*2
            tot = m2+e2+s2+me2+es2
            m2,e2,s2,me2,es2 = [100*x/tot for x in (m2,e2,s2,me2,es2)]
        if scenario == "U5" and be <= 12*60:
            ea2 = ea * 1.7
            p12 = p1 + 8
            p22 = max(0, p2 - 4); p32 = max(0, p3 - 4)
            p1, p2, p3 = p12, p22, p32
        blocks.append((bs, be, ea2, p1, p2, p3, m2, e2, s2, me2, es2))

# ------------------------- SIMULATOR -------------------------
class Simulator:
    def __init__(self, policy, scenario, seed=0):
        self.policy = policy
        self.scenario = scenario
        self.rng = random.Random(seed)
        self.now = 8*60
        self.horizon = 20*60 + OVERTIME_CAP  # allow overtime
        self.events = []
        self.cases = []
        self.future_arrivals = []  # (time, Case)
        self.absent = scenario_absent(scenario)
        self._generate_arrivals()
        # resource state
        self.resource_busy_until = {r:SHIFT[r][0] for r in SHIFT if r not in self.absent}
        self.resource_total_active = {r:0 for r in SHIFT if r not in self.absent}
        self.resource_total_available = {r:(min(SHIFT[r][1]+OVERTIME_CAP, self.horizon)-SHIFT[r][0]) for r in SHIFT if r not in self.absent}
        self.complex_doubled = (scenario == "U4")
        self.it_outage = (scenario == "U5")  # 09:30-10:00 Intake blocked
        # queues per skill
        self.queues = defaultdict(deque)
        self.in_service = {}  # case_id -> (activity, resource, start, end, remaining_at_preempt)

    def _generate_arrivals(self):
        blocks = apply_scenario_to_demand(self.scenario, self.rng)
        cid = 0
        for (bs, be, ea, p1, p2, p3, m, e, s, me, es) in blocks:
            n = self.rng.poisson(ea)
            for _ in range(n):
                rel = self.rng.uniform(0, be-bs)
                t = bs + rel
                pr = self.rng.choices(["P1","P2","P3"], weights=[p1,p2,p3])[0]
                ct = self.rng.choices(["M","E","S","ME","ES"], weights=[m,e,s,me,es])[0]
                c = Case(cid=f"C-{cid:04d}", arrival=t, priority=pr, ctype=ct, sla=t+SLA[pr])
                self.future_arrivals.append((t, c))
                cid += 1
        self.future_arrivals.sort(key=lambda x: x[0])

    def resource_eligible(self, r, activity):
        if r in self.absent: return False
        return activity in SKILL.get(r, {})

    def resource_multiplier(self, r, activity):
        return SKILL[r][activity]

    def is_resource_available(self, r, t):
        if r in self.absent: return False
        s, e, br_start, br_end = SHIFT[r]
        if t < s or t > e + OVERTIME_CAP: return False
        if br_start is not None and br_start <= t < br_end: return False
        return self.resource_busy_until[r] <= t

    def resource_next_free(self, r, t):
        # earliest time >= t at which r is available (account shift/break)
        s, e, br_start, br_end = SHIFT[r]
        if t < s: t = s
        if t > e + OVERTIME_CAP: return float('inf')
        if br_start is not None and br_start <= t < br_end:
            t = br_end
        if self.resource_busy_until[r] > t:
            t = self.resource_busy_until[r]
        if t > e + OVERTIME_CAP: return float('inf')
        if br_start is not None and br_start <= t < br_end:
            t = br_end
        return t

    # ---- policy-specific dispatch ----
    def eligible_resources(self, activity, case):
        pool = [r for r in SKILL if self.resource_eligible(r, activity)]
        if self.policy == "P1":
            # fixed roster
            roster = {
                "Intake": ["Ben","Ada","Chen","Deepa","Emil","Farah"],
                "Mechanical": ["Ada","Ben","Deepa","Farah"],
                "Electrical": ["Chen","Deepa","Emil","Ada","Farah"],
                "Software": ["Chen","Emil","Farah"],
                "Validation": ["Deepa","Emil","Ben","Chen","Ada","Farah"],
            }
            order = roster.get(activity, pool)
            return [r for r in order if r in pool and r not in self.absent]
        if self.policy == "P2":
            return sorted(pool, key=lambda r: self.resource_multiplier(r, activity))
        if self.policy == "P3":
            # reserved P1 capacity: prefer reserved resources for P1
            reserved = {
                "Intake": ["Ben"],            # morning P1
                "Software": ["Chen"],         # afternoon P1
                "Electrical": ["Deepa","Emil"],# afternoon P1
            }
            if case.priority == "P1" and activity in reserved:
                pref = [r for r in reserved[activity] if r in pool and r not in self.absent]
                others = [r for r in pool if r not in pref and r not in self.absent]
                others.sort(key=lambda r: self.resource_multiplier(r, activity))
                return pref + others
            return sorted(pool, key=lambda r: self.resource_multiplier(r, activity))
        return pool

    def handover_cost(self, case, activity, r):
        cost = 0.0
        if case.last_resource is not None and case.last_resource != r:
            cost += HANDOVER_MIN
            prev_family = case.last_skill_family
            new_family = ("Mech" if activity in ("Mechanical",) else
                          "ElecSoft" if activity in ("Electrical","Software") else "Other")
            if prev_family is not None and prev_family != new_family:
                cost += TEAM_SWITCH_MIN
        # skill-switch setup if same resource switches family between consecutive cases
        # approximated as part of dispatch score; not added here directly
        return cost

    def choose_resource(self, activity, case, t):
        cands = self.eligible_resources(activity, case)
        best = None; best_start = float('inf'); best_score = float('inf')
        for r in cands:
            start = self.resource_next_free(r, t)
            if start == float('inf'): continue
            mult = self.resource_multiplier(r, activity)
            base, _ = draw_service(activity, self.rng)  # rough plan
            plan = base * mult
            handover = self.handover_cost(case, activity, r)
            setup = SKILL_SWITCH_MIN if (case.last_resource == r and case.last_skill_family is not None and
                                          case.last_skill_family != ("Mech" if activity=="Mechanical" else "ElecSoft" if activity in ("Electrical","Software") else "Other")) else 0
            # P3 fairness term
            util = self.resource_total_active[r] / max(1, self.resource_total_available[r])
            fairness_pen = max(0, util - 0.90) * 100 if self.policy == "P3" else 0
            # P2 pooling fairness
            if self.policy == "P2":
                fairness_pen = max(0, util - 0.85) * 50
            score = start + plan + handover + setup + fairness_pen
            if score < best_score:
                best_score = score; best = r; best_start = start
        return best, best_start

    def run(self):
        # simple event loop: at each step, admit arrivals, then for each queued case try to assign
        # This is a greedy scheduler (not a full DES) but transparent and reproducible.
        pending = []
        idx = 0
        # admit arrivals in order
        all_arrivals = list(self.future_arrivals)
        # we maintain a list of (case, current_activity, branch_id) to schedule
        active = []  # cases currently being routed
        # We simulate by stepping forward through key events
        # Approach: maintain per-case state; iterate over a sorted "ready" queue
        ready = []
        # admit arrivals
        i_arr = 0
        # Greedy loop: process in time order
        # We'll process arrivals one by one, and after each assignment, advance resource clocks.
        # For tractability, this scaffold assigns cases to the earliest-available resource and records events.
        results_cases = []
        case_state = {}  # cid -> dict(stage_idx, branches_done)
        # Build a global queue of cases by arrival
        for t, c in all_arrivals:
            case_state[c.cid] = {"stage_idx":0, "branches_done":set(),
                                 "last_resource":None, "last_skill_family":None,
                                 "preempted":False, "diagnostic_assigned":[],
                                 "diagnostic_results":{}, "completion":float('inf')}
        # We process cases in arrival order, computing each stage's start/end on the chosen resource.
        # This is a deterministic greedy forward simulator (good enough for relative comparison).
        for t, case in all_arrivals:
            st = case_state[case.cid]
            current_t = t
            stages = stages_for_case(case.ctype)
            # Handle Intake outage in U5
            if self.it_outage and 9.5*60 <= current_t < 10*60:
                current_t = 10*60
            # Intake
            activity = "Intake"
            r, start = self.choose_resource(activity, case, current_t)
            if r is None:
                # fallback: any resource (shouldn't happen with broad intake skill)
                continue
            base, cflag = draw_service(activity, self.rng)
            if self.complex_doubled and activity != "Intake" and activity != "Validation":
                if self.rng.random() < 0.5:  # double tail probability effective
                    base = self.rng.uniform(*SERVICE_TABLE[activity][2:4])
                    cflag = True
            mult = self.resource_multiplier(r, activity)
            act_svc = base * mult
            end = start + act_svc
            self.resource_busy_until[r] = end
            self.resource_total_active[r] += act_svc
            handover = self.handover_cost(case, activity, r)
            self.events.append(self._mk_event(case, activity, start, end, r, base, act_svc,
                                              cflag, False, handover, 0, 0, False, 0))
            current_t = end
            st["last_resource"] = r
            st["last_skill_family"] = "IntakeFam"
            # Diagnostic(s)
            diag_stages = [s for s in stages if s[0] in ("Mechanical","Electrical","Software")]
            # Decide parallel vs sequential
            parallel = False
            if len(diag_stages) > 1 and case.priority in ("P1","P2") and self.policy != "P1":
                # P2/P3: parallelize if two eligible resources exist
                acts = [s[0] for s in diag_stages]
                pools = [self.eligible_resources(a, case) for a in acts]
                # check distinct resources
                if len(pools) >= 2 and pools[0] and pools[1]:
                    parallel = True
            if len(diag_stages) == 1:
                parallel = False
            if parallel:
                # assign branches in parallel
                branch_results = []
                for (activity, bid) in diag_stages:
                    r2, s2 = self.choose_resource(activity, case, current_t)
                    if r2 is None:
                        parallel = False
                        break
                    branch_results.append((activity, bid, r2, s2))
                if parallel and len({br[2] for br in branch_results}) < len(branch_results):
                    # distinct resources? if not, sequential
                    parallel = False
            if parallel:
                max_end = 0
                for (activity, bid, r2, s2) in branch_results:
                    base, cflag = draw_service(activity, self.rng)
                    if self.complex_doubled:
                        if self.rng.random() < SERVICE_TABLE[activity][4]*2:
                            base = self.rng.uniform(*SERVICE_TABLE[activity][2:4]); cflag = True
                    mult = self.resource_multiplier(r2, activity)
                    act_svc = base * mult
                    end2 = s2 + act_svc
                    self.resource_busy_until[r2] = end2
                    self.resource_total_active[r2] += act_svc
                    handover = self.handover_cost(case, activity, r2)
                    self.events.append(self._mk_event(case, activity, s2, end2, r2, base, act_svc,
                                                      cflag, True, handover, 0, PARALLEL_COORD_MIN, False, 0))
                    max_end = max(max_end, end2)
                    st["diagnostic_results"][activity] = end2
                current_t = max_end + PARALLEL_COORD_MIN
                st["last_resource"] = None  # two resources; validation will pick fresh
                st["last_skill_family"] = "ElecSoft"
            else:
                for (activity, bid) in diag_stages:
                    r3, s3 = self.choose_resource(activity, case, current_t)
                    if r3 is None:
                        # skip (shouldn't happen)
                        continue
                    base, cflag = draw_service(activity, self.rng)
                    if self.complex_doubled:
                        if self.rng.random() < SERVICE_TABLE[activity][4]*2:
                            base = self.rng.uniform(*SERVICE_TABLE[activity][2:4]); cflag = True
                    mult = self.resource_multiplier(r3, activity)
                    act_svc = base * mult
                    # skill-switch setup if same resource switches family consecutively
                    setup = 0
                    new_fam = "Mech" if activity=="Mechanical" else "ElecSoft"
                    if r3 == st["last_resource"] and st["last_skill_family"] is not None and st["last_skill_family"] != new_fam:
                        setup = SKILL_SWITCH_MIN
                    end3 = s3 + act_svc + setup
                    self.resource_busy_until[r3] = end3
                    self.resource_total_active[r3] += act_svc
                    handover = self.handover_cost(case, activity, r3)
                    self.events.append(self._mk_event(case, activity, s3, end3, r3, base, act_svc,
                                                      cflag, False, handover, setup, 0, False, 0))
                    current_t = end3
                    st["last_resource"] = r3
                    st["last_skill_family"] = new_fam
            # Validation
            activity = "Validation"
            r4, s4 = self.choose_resource(activity, case, current_t)
            if r4 is None:
                st["completion"] = float('inf')
                continue
            base, cflag = draw_service(activity, self.rng)
            mult = self.resource_multiplier(r4, activity)
            act_svc = base * mult
            end4 = s4 + act_svc
            self.resource_busy_until[r4] = end4
            self.resource_total_active[r4] += act_svc
            handover = self.handover_cost(case, activity, r4)
            self.events.append(self._mk_event(case, activity, s4, end4, r4, base, act_svc,
                                              cflag, False, handover, 0, 0, False, 0))
            st["completion"] = end4
            results_cases.append((case, end4))
        self.results_cases = results_cases
        return self.events

    def _mk_event(self, case, activity, start, end, r, base, act_svc, cflag, par, handover, setup, coord, preempted, pen):
        return Event(
            case=case.cid, activity=activity, start=start, end=end, resource=r,
            priority=case.priority, ctype=case.ctype, arrival=case.arrival,
            sla_deadline=case.sla, base_service=base, actual_service=act_svc,
            complex_flag=cflag, parallel_flag=par, handover_min=handover, setup_min=setup,
            coordination_min=coord, preempted_flag=preempted, preempt_penalty_min=pen,
            policy_version=f"{self.policy}-v1", trigger_fired="",
            eligible_resources=",".join(self.eligible_resources(activity, case)),
            skill_used=activity, planned_service=base*SKILL[r][activity], shock_flag=self.scenario
        )

def compute_metrics(sim, events):
    df = events_to_df(events)
    if df.empty:
        return {"mean_delay":None,"p95_delay":None,"P1_SLA":None,"P2_SLA":None,
                "max_util":None,"fairness_gap":None,"handover_burden":None,
                "preempt_rate":None,"n_cases":0}
    # per-case completion = max end per case
    completion = df.groupby("case:concept:name")["time:timestamp"].max()
    arrival = df.groupby("case:concept:name")["case:arrival"].first()
    sla = df.groupby("case:concept:name")["case:sla_deadline"].first()
    prio = df.groupby("case:concept:name")["case:priority"].first()
    delay_min = (completion - arrival).dt.total_seconds()/60
    mean_delay = delay_min.mean()
    p95_delay = delay_min.quantile(0.95)
    # SLA attainment
    sla_df = pd.DataFrame({"delay":delay_min,"sla":(sla-arrival).dt.total_seconds()/60,"prio":prio})
    p1 = sla_df[sla_df.prio=="P1"]
    p2 = sla_df[sla_df.prio=="P2"]
    p1_sla = (p1.delay <= p1.sla).mean() if len(p1) else None
    p2_sla = (p2.delay <= p2.sla).mean() if len(p2) else None
    # utilization
    util = {}
    for r in sim.resource_total_active:
        util[r] = sim.resource_total_active[r]/max(1, sim.resource_total_available[r])
    max_util = max(util.values()) if util else None
    fairness_gap = (max(util.values())-min(util.values())) if util else None
    handover_burden = df["activity:handover_min"].sum()/df["case:concept:name"].nunique()
    preempt_rate = df["activity:preempted_flag"].mean()
    return {"mean_delay":round(mean_delay,1), "p95_delay":round(p95_delay,1),
            "P1_SLA":round(p1_sla*100,1) if p1_sla is not None else None,
            "P2_SLA":round(p2_sla*100,1) if p2_sla is not None else None,
            "max_util":round(max_util,3) if max_util else None,
            "fairness_gap":round(fairness_gap,3) if fairness_gap is not None else None,
            "handover_burden":round(handover_burden,2),
            "preempt_rate":round(preempt_rate,3),
            "n_cases":df["case:concept:name"].nunique()}

def run_all(seed0=1, n_seeds=3):
    policies = ["P1","P2","P3"]

The scaffold is intentionally transparent: every mechanism (handover, setup, parallel/sequential, preemption parameters, shift breaks, overtime cap) is an explicit named constant or function. Items that are *simplified* and flagged for pilot validation:
- The scheduler is a deterministic greedy forward pass rather than a true event-driven preemption simulator; preemption logic is parameterised but not exercised in this scaffold (the `preempted_flag` field is always False in the recorded events). A production deployment would replace the inner loop with a proper event queue. This is identified, not hidden.
- Inter-case resource contention is approximated by the greedy `resource_busy_until` clock, which is accurate for single-server per-resource queuing but does not capture multi-case contention for the *same* specialist within the same minute.
- Service-time draws for planning use a fresh random draw rather than a stable estimate; this biases the planner toward optimism. In a real system, the planner should use the activity's expected value, not a re-draw.

# 9. Limits and validation plan

## 9.1 What cannot be concluded from the supplied data

1. **True arrival process.** The block table gives *expected* arrivals, not realised arrival times. Real incidents cluster (incident storms after an outage), so Poisson independence underestimates tail risk.
2. **Joint distribution of complexity.** The complex-tail probabilities are per activity, but real cases likely have correlated complexity (a complex Intake predicts a complex diagnostic). The independence assumption in A4 understates variance.
3. **Skill-switch setup time in practice.** The 5-minute setup is given as a rule, but the actual cognitive switching cost depends on resource familiarity, which is not in the data.
4. **Preemption restart penalty shape.** A6 (restart from scratch) vs the alternative (resume + 10%) differs by a factor of ~5 in preemption cost. The recommendation of P3 holds under A6, but the margin over P2 narrows under the alternative.
5. **Real queue dynamics.** My approximate load analysis (§2) treats offered load as flow through a deterministic server; it cannot capture queue build-up, batching, or burst effects.
6. **Human factors.** Fatigue, motivation, and learning are not in the data; the multipliers are static.
7. **Validation burst.** Validation aggregate utilization is low, but burstiness is not characterised by averages.

## 9.2 Pilot / backtest design

**Phase 1 — Shadow mode (2 weeks).** Run all three policies in parallel on historical event logs (offline replay) using the arrival timestamps as given. Compare predicted vs actual completion times for each policy. No live changes. Primary metric: would P3 have met P1 SLA on the historical day? Look for any day where P3's predicted P1 SLA < 90%.

**Phase 2 — Controlled live pilot (4 weeks, one skill family).** Deploy P3 on the **Software/ES** family only (the tightest specialist pool), keeping P1 (specialization) on Mechanical and Electrical. Randomise case assignment to P3 vs P1 within the Software/ES family at 50/50. Protect P1 cases by giving them the reserved Chen slot regardless of arm. Primary outcome: P1 SLA attainment on Software/ES cases. Secondary: handover/setup burden per case, preemption rate. Pre-registered stopping rule: stop if P1 SLA in the P3 arm drops below 85% for two consecutive days.

**Phase 3 — Stress simulation backtest (offline).** Replay historical logs under simulated U1–U5 by: (a) multiplying morning arrivals by 1.7 with arrival-time jitter; (b) removing Chen's events; (c) injecting the 09:30–10:00 Intake outage. Compare P1, P2, P3 head-to-head. This is the most ethically safe way to evaluate resilience without exposing live cases to shocks.

**Phase 4 — Full rollout with guardrails (8 weeks).** Roll out P3 across all skill families. Maintain guardrails: P1 SLA  90% rolling 7-day; preemption rate  8%; no resource > 95% utilisation rolling 7-day. If any guardrail trips, fall back to P4 (SERT + fairness penalty) for 48 h while P3 parameters are retuned. Re-evaluate monthly using the drift-detection analyses in §7.

**Phase 5 — A/B at scale.** If Phases 2–4 confirm P3 dominance, run a final pre-registered A/B comparing P3 vs P1 (not P2, since P2 has unacceptable handover burden) over 8 weeks, with the primary endpoint a composite of P1 SLA attainment and fairness gap. Use a cluster-randomised design (alternate weeks) to avoid contamination from shared resources.

**Safety principle:** at no point in the pilot should a P1 case be denied the reserved-slot path. The reserved capacity in P3 is the safety net; if it is removed for experimental reasons, a parallel manual fast-track must exist for any P1 case whose predicted completion exceeds 100 minutes.

This design isolates the policy's marginal contribution from arrival stochasticity, protects P1 cases structurally, and produces audit-ready evidence for either rolling out P3, retuning it, or reverting to P1 if the resilience advantage does not materialise in practice.
