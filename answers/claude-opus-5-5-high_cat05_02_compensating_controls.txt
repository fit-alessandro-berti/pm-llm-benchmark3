## 1. Control-Objective Decomposition

FEP-1 is a surrogate rule. What it actually protects is this: before money becomes irrecoverable, an independent and accountable human who did not initiate the payment has made a contemporaneous judgment about it. Its value can be broken down into the threat scenarios below. Legend: **P** = can prevent (breaks the chain before irrevocable settlement), **D** = can detect, **C** = can correct (stop, recall, recover), **×** = does not address. Conditions in brackets state when the capability actually holds.

| # | Objective / threat scenario | AV-2 automated validation | MG-4 independent manager | RA-7 audit & recall | ED-1 emergency permission |
|---|---|---|---|---|---|
| O1 | **Payee integrity**: bank-account substitution, account takeover, business-email compromise, redirected payment | **P** [bank-ownership check, 7-day bank-change check; only if not overridden] | **P** [only if pre-settlement and the manager actually checks bank details; weak if rubber-stamped] | **D**; **C** only within ~24 h recall and before settlement is final for practical purposes | **P by scope restriction** (condition 4 excludes recent bank changes; condition 5 requires a clean AV-2) |
| O2 | **Payment accuracy**: duplicate invoice, wrong amount, PO mismatch, operator-limit breach | **P** strong (duplicate, limit, basic PO match) | **P/D** moderate | **D**, **C** within recall | Relies on AV-2 (condition 5) and amount cap (condition 2) |
| O3 | **Substantive legitimacy**: goods/services not received, fictitious services, fabricated supporting documents | **×** (explicitly not covered) | **P** [the *only* pre-release control that can address it, if receipt/service evidence is reviewed and independently corroborated] | **D** (e.g., AP-204), **C** only if timely | Vendor-age condition 3 lowers fictitious-vendor risk only; otherwise relies on MG-4 |
| O4 | **Commercial reasonableness / conflict of interest**: inflated price, related-party vendor, unnecessary spend | **×** (basic PO match is not reasonableness) | **P** partial [judgment-based; fails if manager is conflicted] | **D** (vendor-relationship analytics) | **×** beyond amount cap |
| O5 | **Independence against collusion**: two insiders, or insider + approver, acting together | **×** (cannot detect collusion) | **P** only if independent of *both* actors; adds a third party | **D** via pattern analysis (pairs, relationships); deterrent | **×**; ED-1 reduces to one operator + one manager, so collusion needs just one additional person |
| O6 | **Identity assurance / non-repudiation**: shared service accounts, borrowed credentials, shared workstations; "two IDs ≠ two humans" | **×** (trusts the authenticated identity) | **×** if its own credential can be used by others (AP-202) | **D** via session, device, and IP forensics | **×** |
| O7 | **Control-bypass integrity**: overrides, outages, emergency pretext, retroactive justification | Itself the target; **D** by emitting warnings; hard blocks **P** | **P** as override authority — but only if the override is performed by the manager personally | **D** 100% for emergency cases | **P** in design: token-before-prepare (condition 1) and no-override (condition 5) are anti-pretext conditions |
| O8 | **Legal / sanctions compliance** | **P** (sanctions list) | **P/D** partial | **D**; recall may not cure a sanctions breach (the violation occurs at transfer) | Relies on AV-2 |
| O9 | **Loss containment / recoverability** | n/a | Timing-dependent | **C** only while the defect can still be stopped or recalled | Condition 7 (one business day) aims at, but does not guarantee, the 24 h recall window |
| O10 | **Deterrence and accountability** | Weak | Moderate (named approver) | Strong if 100% and timely (certainty of detection) | Weakens it (single-operator norm) unless exceptions are rare and audited |

Key observations:
- The one thing FEP-1 uniquely gives is **contemporaneous independent judgment at the release point, on every payment**. Among the compensating controls, only a timely, independent, evidence-based MG-4 reproduces it. AV-2 reproduces a *subset of checks*, not *judgment*. RA-7 is detective and becomes corrective only while the recall window is open.
- No compensating control covers O3 (receipt/legitimacy) except a substantive MG-4 review, and none raises collusion resistance (O5) above FEP-1. FEP-1 itself fails against collusion or identity collapse (O5, O6), which is why a distinct-user case can still fail its objective.
- ED-1 is not a control. It is a **risk envelope**: it limits single-operator use to cases where the residual threats (O1 via bank-change and vendor-age limits, and exposure via the amount cap) are small, and it requires the other three controls to do the work. It does not make the four-eyes objective disappear.

## 2. Equivalence and Sufficiency Test

### Step 0 — Case risk profile (proportionality)
First decide which threats from Section 1 are *active* for the case, and how much exposure there is:
- exposure: amount, and whether money is recoverable after settlement;
- payee risk: vendor age, bank-change proximity, sanctions;
- substance risk: whether the payment depends on receipt of services (consulting and repairs are receipt-dependent; office supplies with a PO/GR match less so);
- actor risk: relationships, pair history, shared devices, prior anomalies;
- context: is the emergency genuine and documented?

The required strength of the compensating package scales with this profile. A small invoice to a six-year vendor needs less than EUR 900k to an eight-month vendor whose bank details changed three days earlier.

### Step 1 — Grade each control against each active threat on seven dimensions
Grades: Strong / Adequate / Weak / Absent.

| Dimension | Strong | Adequate | Weak | Absent |
|---|---|---|---|---|
| **Timing** (relative to the point of irrevocability, not the Release event) | Before Release_Payment | After release but before settlement, *with a proven hold/cancel capability* and slack | After settlement, within the 24 h recall window | After the recall window |
| **Independence** | Distinct human, own credential, separate device, no reporting line or conflict, L3+ for MG-4 | Distinct human, minor unverified attribute (e.g., level not evidenced) | Distinct ID but a shared workstation/credential, or a concentrated pair | Same person, conflicted supervisor, or borrowed credential |
| **Coverage** | Tests every active threat (for MG-4: invoice, bank details, receipt) | Tests most active threats | Tests only generic checks (e.g., AV-2 pass on a receipt-dependent payment) | Control absent or out of service |
| **Overrideability** | Hard block, or override only by an independent authorized manager personally | Override by an independent manager, justification logged | Override possible by a conflicted party | Overridden by the preparer or under a misused credential |
| **Recoverability** | Defect can be stopped before settlement | Recall is still available | Legal recovery only | None |
| **Evidence quality** | System-logged, check-level, reviewer evidence retained, reliable timestamps | Logged but review depth undocumented | Assertions only, unsigned checklists | No evidence |
| **Collusion resistance** | ≥ 2 independent humans plus pattern monitoring | 2 independent humans | 2 IDs whose independence is doubtful | 1 human |

### Step 2 — Knock-out rules
Each rule caps the package grade, however many other controls were present:
1. An approver who is not independent (conflict, reporting line, borrowed credential) cannot count as the second pair of eyes, so the package is at most *merely mitigating*.
2. A control that takes effect only after irrevocable settlement cannot count as prevention. At most it is mitigating (detective, possibly corrective through recall).
3. A check that was overridden by the preparer, or under someone else's credential, counts as **Absent** for the threats it covers.
4. A control outage with no signed, independent manual substitute is **Absent**.
5. A missing emergency precondition (e.g., token after Prepare_Payment) is a *permission* failure. It lowers the grade by one level unless reliable evidence shows it was a logging artefact.

### Step 3 — Aggregate to an equivalence level
- **Fully equivalent**: every active high-impact threat is covered by at least one control that is Strong on timing, independence, and coverage, with Adequate or better evidence, no overrides, and collusion resistance at least equal to FEP-1. → normally `OBJECTIVE_MET`.
- **Partially equivalent**: all active threats are covered before irrevocability, no knock-out applies, but one or more dimensions are only Adequate (hybrid timing, undocumented review depth, a precondition sequencing gap). → `OBJECTIVE_MET` if the weak dimension is irrelevant to this case's active threats, otherwise `OBJECTIVE_PARTIALLY_MET`.
- **Merely mitigating**: some active threat is covered only after irrevocability, or independence is weakened. Expected impact falls, but prevention is not reproduced. → `OBJECTIVE_PARTIALLY_MET` only if exposure is low and bounded, otherwise `OBJECTIVE_FAILED`.
- **Ineffective**: a knock-out neutralizes the decisive controls. → `OBJECTIVE_FAILED`.
- **Undecidable**: a decisive dimension (usually independence or coverage) cannot be graded from the evidence. → `INDETERMINATE`.
- **No completed payment**, because a preventive control stopped it. → `LOSS_PREVENTED_BEFORE_COMPLETION`. The attempt itself is still assessed as a conduct signal.

The same test applies to distinct-user cases. There, the nominal second releaser is simply one more "control" and is graded on independence, coverage, and evidence like any other.

### Why "same expected loss" is not the only standard
An expected-loss standard asks whether E[loss | compensating package] ≤ E[loss | FEP-1]. That is useful, but not sufficient:
1. **Tail risk and severity asymmetry.** Two packages with equal expected loss can have very different tails. One catastrophic, unrecoverable transfer (AP-202) can outweigh many small errors, and risk appetite is usually set on the tail, not the mean.
2. **Adversarial adaptation.** Fraud is not a stationary random process. Fraudsters seek the weakest path, so a path with low historical loss (such as emergency single-operator) attracts abuse once it is known to be weaker. Expected-loss estimates from past data understate that risk.
3. **Estimation uncertainty.** Fraud base rates are small, and many frauds are undetected, so expected-loss estimates are fragile. An assurance standard ("demonstrably independent review before irrevocability") is more robust than a point estimate.
4. **Deontic and regulatory obligations.** Segregation of duties, sanctions screening, and ICS/SOX-type attestations are obligations of form *and* substance. An auditor needs evidence that a control operated, not a statistical argument that loss was probably equal.
5. **Deterrence and accountability.** A two-person rule deters single-actor fraud and produces clear attribution. Retrospective audit deters less, because detection comes after the fact and recovery is uncertain.
6. **Recoverability is not neutral.** A loss detected and recalled still causes investigation cost, supplier and bank friction, and reputational and legal exposure (for sanctions, the breach occurs at transfer).
7. **Normalization of deviance.** Tolerating convenience-driven exceptions (AP-201) erodes the norm even when each instance is cheap.

The test therefore combines a risk criterion (residual exposure within appetite), an assurance criterion (evidence that the objective was achieved at the right time and by an independent party), and a legitimacy criterion (the exception path was used for its intended purpose).

### Semantics chosen for a manager action after Release_Payment but before settlement
I classify it as **hybrid: conditionally preventive**, and I classify controls by their position relative to the **point of irrevocability (bank settlement)**, not relative to the Release_Payment event. Reasons:
- **The loss event is settlement, not release.** A review that can still stop money from leaving breaks the causal chain, so functionally it is preventive with respect to loss.
- **But its preventive status is conditional.** It counts as preventive only if (a) a hold or cancel function exists between release and settlement, (b) the reviewer has authority and knows the cut-off, (c) the review finishes with enough slack before cut-off (AP-201: ~90 min; AP-207: 80 min), and (d) release has not already sent an irrevocable instruction to the bank. If any of these is unproven, the review is **detective** for sufficiency purposes. Hence AP-207 is MET only with medium-high rather than high confidence.
- **It is weaker than pre-release approval even when it works.** There is a race with settlement cut-offs. There is automation and commitment bias: a "Manager_Ratify" of a payment already released invites confirmation rather than scrutiny. And the preparer-releaser has already shown the institution that a single person can authorize.
- **After settlement it is detective only.** At best it triggers a recall inside the 24 h window. AP-208's ratification came exactly 24 h after settlement and ~25 h after release, so it did not even serve that purpose.

On reconciling "bank can usually recall within 24 h" with "settlement is normally irrevocable for internal-control purposes": I treat settlement as the **boundary of prevention** and the recall window as an **uncertain corrective channel**. It adds some value to detection, but it can never make a post-settlement control "equivalent" to prevention.

## 5. Counterfactual and Residual-Risk Analysis

Likelihood language is qualitative (remote / low / moderate / high / very high). No precise probabilities are claimed.

**AP-202 (critical, realized loss)**
- *Loss mechanism:* related-party payee fraud. The bank account (linked to an employee's relative) was attached to a new vendor two hours before payment, then released by the preparer, who overrode AV-2 with a supervisor's credential.
- *What should have broken the chain:* the AV-2 warning. It detected exactly the right risks (bank change, operator limit), but the override made it ineffective. MG-4 was conflicted and two days late; RA-7 was eight days late.
- *What remains exposed:* credential-sharing practice between m09 and u23 (whether m09 consented is unresolved); a bank-change process that allowed a same-day change for a new vendor; a supervisor-ratification path that is not independent; possibly other payments to the same account or vendor.
- *Under a truly independent second releaser:* the releaser would have seen an active warning they could not override themselves, and an override would have needed a genuine L3 manager. Interruption is **high to very high** likely, unless the fraud extended to the releaser. The core failure is identity and override integrity, not the number of steps.

**AP-204 (distinct users, objective failed)**
- *Loss mechanism:* payment for fabricated consulting services on a forged receipt, through collusion between u12 and u13, deception of both, or perfunctory release on a shared workstation.
- *What broke the chain:* nothing did before settlement. AV-2 cannot test receipts, and there was no MG-4. RA-7 detected the forgery on day 4, after the recall window.
- *What remains exposed:* the EUR 220k (recovery through legal channels only, uncertain); every other payment by the pair (37 in 30 days); receipt-dependent payments generally.
- *Under a truly independent second releaser (outside the pair, separate device):* the collusion path would be broken (**high** reduction if collusion was the mechanism). A skilled external forgery might still pass a releaser who does not corroborate receipts, so improvement is only **moderate** if deception was the mechanism. The decisive fix is independent receipt corroboration (goods-receipt/requester confirmation, three-way match) for high-value service payments, not just a different second person.

**AP-208 (no loss, control failed)**
- *Loss mechanism that was avoided only by luck:* bank-detail fraud. A young vendor with details changed three days earlier is the classic business-email-compromise pattern, and EUR 900k was released during an AV-2 outage.
- *What broke the chain:* nothing did. The payment was legitimate. Manager ratification came after settlement; the audit after four days.
- *What remains exposed:* any payment released during AV-2 outages; emergency tokens not bound to an amount cap in the system; bank-change verification.
- *Under a truly independent second releaser:* the releaser would likely have demanded bank-ownership verification (e.g., a call-back to a known contact) or deferred the payment. Interruption of a fraudulent variant is **moderate to high** likely, though a releaser alone cannot fully replace AV-2's ownership check. The right counterfactual is "outage means hold, or dual control plus a signed call-back", not merely a second click.

**AP-201 (tolerable deviation)**
- *Loss mechanism:* a clerical error or a small fraudulent invoice by a single operator.
- *What breaks the chain:* the AV-2 pass (duplicates, bank, PO) and m04's independent review before settlement, conditional on hold capability.
- *What remains exposed:* receipt verification (low value); norm erosion if u17 routinely self-releases; the audit started ~25 h after release, so recall was no longer a reliable backstop.
- *Under a truly independent second releaser:* marginal risk change (**low** exposure either way). The real gain is legitimacy and deterrence, not expected loss.

**AP-206 (token-precondition gap)**
- *Loss mechanism:* abuse of the emergency path by retroactive tokening, or a payment error under time pressure.
- *What breaks the chain:* m11's pre-release approval and the AV-2 pass. Together they cover payee integrity and accuracy.
- *What remains exposed:* whether m11 reviewed receipt evidence (depth not documented, and m11 approved before the AV-2 result); a risk of structuring near the EUR 100k limit (95k); integrity of the token process.
- *Under a truly independent second releaser:* **low** additional reduction; the package is already close to equivalent. The more valuable change is to make token-before-prepare a system-enforced precondition.

**AP-207 (plausible ED-1 use)**
- *Loss mechanism:* an error or fraud by a single operator under safety-repair urgency.
- *What breaks the chain:* m15's full-evidence review before settlement (hybrid) plus the clean AV-2.
- *What remains exposed:* the race between review and settlement cut-off if the hold capability is not guaranteed.
- *Under a truly independent second releaser:* **low** additional reduction. The main difference is timing: prevention would be certain rather than conditional.

**AP-209 (indeterminate)**
- *Loss mechanism if the pair is not independent:* the same as AP-204, with the audit possibly not testing receipt authenticity.
- *What breaks the chain:* the AV-2 pass for payee and duplicate risks, and a timely audit while recall was still open.
- *What remains exposed:* receipt legitimacy and independence of the two actors.
- *Under a truly independent second releaser:* a **moderate** reduction of collusion exposure. It would also resolve the indeterminacy, because independence would be evidenced rather than assumed.

**AP-203 and AP-205 (brief)**
- AP-203: an independent releaser would add little; a pre-release independent review of substantive evidence is at least as strong as a typical releaser click.
- AP-205: AV-2 already broke the chain, so an independent releaser adds nothing to loss. It would, however, have removed the opportunity for the same-user release attempt, which is the residual system-design gap.

| ED-1 envelope breaches | Token-backed payments ≥ EUR 100k, vendor < 180 days, bank change ≤ 7 days, AV-2 not clean | Any occurrence (AP-208) | Hard system block; immediate escalation |
| Near-threshold amounts | Token-backed payments in the band just below EUR 100k; same vendor split within a short window | Clustering in the 90–100k band | Structuring review |
| Override rate and integrity | Overrides per manager and per user; override actor vs credential owner vs session device/IP; override in the same session as prepare/release | Override where the session user ≠ credential owner (AP-202); override by the preparer's session | Suspend credential; forensic review |
| Late manager approval | Manager action relative to release and settlement (minutes of slack); share of "Ratify" vs "Approve" | Approval after settlement (AP-208); after the recall window (AP-202); slack < 30 min | Treat as missing control; escalate |
| Manager independence | HR graph: reporting line, performance-rating authority, family and personal relations, delegation chains; manager level ≥ L3 | Approver rates the preparer (m09/u23); level not evidenced | Reassign approval; exclude conflicted approvers in the system |
| Audit before recall window | Audit start time − release time; audit completed before 24 h and before settlement where possible | Emergency or same-user audits > 24 h (AP-201 borderline, AP-202, AP-208) | Auto-schedule audits in the recall window; alert on backlog |
| Repeated resource pairs | Pair concentration: share of each user's releases handled with one counterpart; count of joint payments | e.g., > 60% of releases with one partner, or > 20 joint payments/30 days, outside a documented cell | Rotate reviewers; targeted substantive audit of the pair |
| Shared workstations | Prepare and release events from the same device, IP, or overlapping sessions | Any prepare/release pair from one workstation (u12/u13) | Treat as potential identity collapse; require step-up authentication |
| Bank-change proximity | Hours between a bank-detail change and payment; who made the change; call-back verification record | Change ≤ 7 days, especially ≤ 24 h (AP-202: 2 h) | Hold payment until independent call-back |
| Control outages | AV-2 unavailability windows; payments released during outages; manual checklist signed by an independent person | Any release during an outage without a signed independent checklist (AP-208) | Default to hold; dual control plus call-back |
| Post-block attempts | Release attempts after AV-2 block; same-user release attempts without a token | Any occurrence (AP-205) | System hard-stop; conduct review |
| Receipt corroboration | For service or consulting payments: goods-receipt or requester confirmation independent of the preparer | High-value service payment without independent confirmation (AP-204, AP-209) | Mandatory MG-4 plus requester confirmation |

### Evidence collection
- Log **Bank_Settlement** consistently. It is missing for AP-201 to AP-205, which makes timing analysis depend on narrative facts.
- Log token request, creation, and approval, with the incident reference.
- Log AV-2 results at check level, not just pass or fail.
- Log override events with the credential ID, session user, device, and IP.
- Record MG-4 review content: documents opened, checklist fields, bank-detail verification method, the manager's level.
- Record audit scope and outcome, including whether receipts were independently confirmed.
- Keep payment-record hashes or immutability between approval and release, so the approved content is the released content.
- Obtain organizational-design documents for any standing two-person payment cell.

### Alert versus proof of misconduct
All the indicators above are **alerts**: they raise the priority of a case for review. None of them is a finding of misconduct.
- Repeated pairing can mean a legitimate dedicated cell. A shared workstation can come from hot-desking. A late token can be a logging delay. Credential use can mean theft rather than sharing.
- Proof requires corroborated attribution: strong authentication evidence linking the human to the action, knowledge or intent, and a beneficial link or concealment. It also requires due process for the people involved, e.g., interviews and the chance to explain.
- Concretely: AP-202 is a proven **control failure** with a realized loss, but whether m09 shared the credential remains **unresolved** and must be investigated under both hypotheses. For u12/u13, AP-204 proves a fabricated receipt passed their release but does not by itself prove collusion. AP-209 must not be classified as fraud because it resembles AP-204.
- Control conclusions (was the objective achieved?) and conduct conclusions (did someone act wrongfully?) should be recorded separately.

### PM4Py behavior I cannot guarantee across versions
- **Return orientation of `filter_four_eyes_principle`.** It is documented as filtering *out* violating cases, i.e., returning compliant ones. The underlying LTL checker has a `positive` parameter, and some versions or wrappers may expose options to keep violations. The code therefore infers the orientation by comparing the result with an independent pandas check and falls back to pandas if neither orientation matches.
- **Cases lacking one of the two activities.** In the default mode these are returned as "non-violating" (e.g., AP-205, which has no Release_Payment). That is why the code intersects the result with the set of *completed* payments and handles blocked attempts separately.
- **What the check compares.** PM4Py compares resource strings for equality and nothing else. It cannot see that `SYSTEM` is a shared account (handled separately above), that an override used someone else's credential (AP-202), or that two IDs shared a workstation (u12/u13). It also does not check event order or timing.
- **Keyword parameters.** `activity_key`, `case_id_key`, and `resource_key` exist only in newer versions, so the code passes them only when the signature accepts them.
- **`format_dataframe`.** It may add helper columns (e.g., `@@index`, `@@case_index`), re-sort the frame, cast the case ID to string, and handle timezones differently between versions (some keep tz-aware UTC, some convert). The code re-asserts tz-aware UTC afterwards. Newer releases may deprecate this function in favor of passing keys directly.
- **Business-day computation.** pandas `BDay` ignores public holidays, so a holiday calendar would change the RA-7 timeliness flags.
