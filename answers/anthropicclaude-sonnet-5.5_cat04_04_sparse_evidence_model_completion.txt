**Why CCER and ERCC in the DFG do not prove concurrency.**

1. Every trace contains each activity at most once. The 17 CCER and 11 ERCC occurrences therefore come from *disjoint* traces. A DFG is first-order and cannot show that the same case could have gone either way.
2. At least four generative stories produce exactly this DFG:
   - (a) true or overlapping concurrency;
   - (b) an XOR over two sequential orders, selected by an unobserved case attribute (customer tier, order value, and so on);
   - (c) one fixed order, with the other direction produced by tie-break and ingestion artifacts (S7);
   - (d) a mixture of populations, some following S1 and some following S2.
3. For exactly these two activities, `+(CC,ER)` and `×((CC,ER), (ER,CC))` accept the same language. The observations cannot discriminate between them. Differences appear only with third-party activities (SC, EX) or with lifecycle data.
4. Concurrency is therefore adopted as the *most compact generalization*, never as a finding. The only observable that could support it is overlapping start/complete intervals.

# 2. Shared Assumptions

1. **Event-completion semantics.** Each log event is the *completion* of an activity. Every model transition represents a completion event. An edge AB means "A's completion precedes B's completion". Parallelism means "completion order is unconstrained". It includes real parallelism, overlap, and sequential execution in either order. It does **not** assert simultaneous execution (D7, S7).
2. **Hard constraints in all three models.**
   - D1: RO first, ARC last.
   - D2: APPRELARC.
   - D3: CC and ER both mandatory and both before APP. This is 30/30 in the data, and S5 concerns only SC.
   - D4: SC, if present, before APP.
3. **No rework.** Each activity appears at most once per case. No loops are observed, and D6 forbids repeated EX. Multi-component orders might in reality need several SC events. This is unobserved and not modeled (see §9).
4. **Missing SC events and the absent external/stocked attribute.**
   - Without the attribute, the control flow cannot condition on "external".
   - SC is therefore represented marginally as `×(SC, )` in the balanced and permissive models.
   - **Disclosed abstraction:** the  branch conflates three things: (i) stocked components (true skip), (ii) SC events lost to the integration problem, (iii) any other legitimate skip. We do not separate them in control flow. A labeled silent branch (_stocked vs _missing) would give the same language. It is useless until data can label the two.
   - The conservative model has no generalized SC handling. It memorizes the observed SC-present and SC-absent variants. Its robustness to missing SC events is correspondingly poor.
   - Missing events are assumed to be *dropped*, not delayed or reordered.
5. **Optionality representation.** `×(X, )` for SC and EX only. CC and ER are never optional. The data (30/30) and D3 support this, and S5 does not claim they go missing.
6. **Noise.** All 30 cases are treated as noise-free. The two singleton variants (V-F, V-G) are retained because D6/S6 independently support them, not because of frequency. Ordering artifacts from S7 ties are acknowledged but unquantifiable.
7. **Scope.** Control-flow only. No time, resource, or data perspective. Duplicate labels appear in tree models only where a block-structured model needs them. No model is post-processed.
8. **Design invariant.** L(conservative)  L(balanced)  L(permissive). The three are nested hypotheses of increasing generality, not cosmetic variants. All three are finite-language (acyclic), so the languages can be enumerated exhaustively in §8.

# 3. Conservative Candidate

**Inductive-bias statement.** This model is pure memorization. The language equals the set of 7 observed variants, and nothing else is admitted. The bias is "what we have not seen is forbidden", which minimizes false admits. It is justified when the model is used as an audit baseline or whitelist, or when any unseen variant should trigger manual review. It strongly risks overfitting: it treats observed completion order as causal law, contradicts S2/D5's spirit, and has no defense against S5 missing events. A Good–Turing estimate (2 singleton variants of 30) puts the probability that the next case is an unseen variant at roughly 7% (rough range 3–15%). Every such case would be flagged as non-conformant.

**Formal expression** ( sequence, × exclusive choice):

```
( RO,
   ×( (CC,ER,SC), (ER,CC,SC), (CC,ER), (ER,CC),
      (CC,SC,ER), (CC,ER,SC,EX), (ER,CC,EX,SC) ),
   APP, REL, ARC )
```

**Duplicate labels and scalability.** The tree has 25 visible leaves for 8 distinct labels (CC appears 7 times, ER 7, SC 5, EX 2, and so on).
- Duplicate labels make the model hard to read as a causal story.
- They dilute transition-frequency-based generalization metrics, since many transitions fire only 1–3 times.
- They do not hurt soundness or alignments.
- Size grows linearly in the number of variants. It grows factorially in the number of order-free activities: k free activities need up to k! branches, and optional subsets multiply that further.
- The enumeration cannot express "SC missing" as a mechanism.

**PM4Py code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO, CC, ER, SC, EX = ("Register Order", "Credit Check", "Engineering Review",
                      "Supplier Confirmation", "Expedite Review")
APP, REL, ARC = "Approve Configuration", "Release Production", "Archive Case"

def _attach(parent, children):
    for c in children:
        c.parent = parent
        parent.children.append(c)
    return parent

def act(label): return ProcessTree(label=label)
def seq(*cs):   return _attach(ProcessTree(operator=Operator.SEQUENCE), cs)
def xor(*cs):   return _attach(ProcessTree(operator=Operator.XOR), cs)

observed_cores = [
    [CC, ER, SC], [ER, CC, SC], [CC, ER], [ER, CC],
    [CC, SC, ER], [CC, ER, SC, EX], [ER, CC, EX, SC],
]
model_conservative = seq(
    act(RO),
    xor(*[seq(*[act(a) for a in core]) for core in observed_cores]),
    act(APP), act(REL), act(ARC),
)
print(model_conservative)
```

**Behavior deliberately excluded**
- Any completion order or activity combination not in the 7 variants, including: EX without SC; SC after EX in CC-first cases; EX after SC in ER-first cases; ER SC CC; SC before CC.
- All violations of D1–D4 and D6.
- Repeats, missing CC or ER, and REL before APP.

**Known underfitting risks**
- It rejects plausible unseen variants. About 5 of the 12 core traces of the balanced model are unobserved, and the model flags them all.
- It has no representation of SC missingness (S5). For example, V-G with its SC event dropped becomes RO ER CC EX APP REL ARC, which is rejected.
- Its verdict on whether CC and ER are "concurrent" is undefined. It stores two orderings as two unrelated branches.
- It is fragile to any new lawful interleaving. Its fitness on a hold-out sample would drop by about the unseen-variant probability, which is not negligible for compliance use.

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model generalizes only where the evidence or domain rules give a reason. The rest stays forbidden. CC and ER are order-free (both orders observed at 19:11, with S2 supporting). SC is optional (7/30 absences exceed the 1–3 cases S5 can explain) and is ordered after CC, because SC followed CC in 23/23 cases, including all 8 ER-first cases with SC. This CCSC edge is a deliberate, evidence-derived bias that partly contradicts the literal reading of D5. SC stays order-free relative to ER (V-E). EX is optional, needs both checks (D6/S6), and is order-free relative to SC (V-F vs V-G). The result is a partial order with an N-shaped core (SC > CC < EX > ER) that block-structured process trees cannot express without duplicating labels. The bias is "generalize only along dimensions with both evidence and domain plausibility". It risks overfitting on the CCSC edge (only 8 exposures), and underfitting on any SC or EX behavior that never appeared.

**Formal expression**

```
PO( nodes = {RO, CC, ER, SC?, EX?, APP, REL, ARC},  SC? = ×(SC,),  EX? = ×(EX,)
    R = { RO<CC, RO<ER, CC<SC?, CC<EX?, ER<EX?, SC?<APP, EX?<APP, APP<REL, REL<ARC } )
```

CC<APP and ER<APP are implied transitively through SC? and EX?. A skipped optional node still transmits the order.

**How sequence, concurrency, and partial order are decided**

1. **Sequence (hard edge A<B)** if all of the following hold:
   - (a) B never completes before A in the log;
   - (b) a domain rule or plausible mechanism supports the dependency;
   - (c) there was real opportunity to see a violation.
   - Applied to: APP<REL and REL<ARC (D1/D2). CC<EX and ER<EX (D6/S6, 2/2). SC?<APP and EX?<APP (D4/D6). **CC<SC** (0/23 violations and 0/8 in the informative subset, plus the plausible mechanism that supplier confirmation needs credit-related information). This is the most contestable edge, at about 55% confidence (§10).
2. **Concurrency (no edge)** if both orders are observed (at least 2 cases each), no domain rule orders the pair, and nothing contradicts it.
   - CCER: 19 vs 11 cases, S2. S1 is rejected as a universal rule.
   - SCER: SC before ER in 2/23 cases, consistent with D5.
   - SCEX: 1 vs 1 case, S6.
   - This is a language-level statement ("either order allowed") and not a claim of physical parallelism (D7).
3. **Partial order (POWL)** is used when the combined relations are not series-parallel. Here CC<SC, CC<EX, ER<EX with SCER and SCEX is an N shape. A process tree must either drop a constraint or duplicate labels, so POWL is chosen.
4. **XOR over orders** is *not* used. It would only be justified if an attribute or lifecycle data showed the order is case-type-determined. Until then it is language-equivalent for the pair and less compact.

**PM4Py code**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def opt(label):
    return OperatorPOWL(operator=Operator.XOR,
                        children=[Transition(label), SilentTransition()])

ro  = Transition("Register Order")
cc  = Transition("Credit Check")
er  = Transition("Engineering Review")
sc  = opt("Supplier Confirmation")      # optional: stocked OR missing (conflated)
ex  = opt("Expedite Review")            # optional, at most once
app = Transition("Approve Configuration")
rel = Transition("Release Production")
arc = Transition("Archive Case")

model_balanced = StrictPartialOrder(nodes=[ro, cc, er, sc, ex, app, rel, arc])
for a, b in [(ro, cc), (ro, er),
             (cc, sc),                   # evidence-derived soft dependency (CC before SC)
             (cc, ex), (er, ex),         # D6/S6: EX after both checks
             (sc, app), (ex, app),       # D4/D6; CC<APP, ER<APP are transitive
             (app, rel), (rel, arc)]:
    model_balanced.order.add_edge(a, b)
print(model_balanced)
```

**Behavior deliberately excluded**
- SC completing before CC (ER SC CC, SC CC ER, and so on). Reason: the CCSC bias.
- EX before CC or ER completes, EX after APP, and EX twice (D6, S6).
- SC after APP (D4) and SC twice.
- Missing CC or ER (D3). REL before APP (D2). Wrong start or end (D1).
- CC-before-ER *enforced* (S1). Both orders are admitted.

**Known underfitting risks**
- If D5 is literally true, ER SC CC and ER SC CC EX are lawful but rejected here.
- EX without SC is admitted although no observed EX case lacks SC (risk in the other direction, see §6).
- The model has no multi-SC (multi-component) behavior, no rework, and no attribute-based guards.
- The CCSC edge could be an ingestion-order artifact (S7).
- Concurrency of CC and ER may mask a real case-type-based XOR. The language is the same, but the explanation and the conformance diagnostics differ.

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model admits any completion order that does not contradict a hard domain rule. It takes D5 in its widest reading. SC may *begin* after partial information from either check, so with completion-only timestamps (S7) it may *complete* before both checks. Hence SC floats freely. It is optional (S3/S4/S5) and only bounded above by APP (D4). EX must follow both checks (D6/S6), is unordered with SC, and is optional. The resulting language is a single block-structured parallel composition: the largest order-free generalization that still respects D1–D4 and D6. The bias is "unless a rule forbids it, allow it". It is an exploration or sensitivity hypothesis with a clear risk of underfitting (accepting behavior the true process never performs).

**Formal expression**

```
( RO,  ( ( (CC,ER), ×(EX,) ),  ×(SC,) ),  APP, REL, ARC )
```

**Boundary between "reasonable generalization" and "forbidden"**

| Admitted (reasonable) | Forbidden (remains hard) |
|---|---|
| Any completion order of CC, ER (S2) | Anything before RO or after ARC (D1) |
| SC or EX skipped (S3/S4/S5; D6 optionality) | REL without a preceding APP, APP after REL (D2) |
| SC anywhere before APP, including before both checks, justified by D5 (begin vs complete) and D7 | SC after APP (D4); SC repeated |
| EX before or after SC (S6) | EX before CC or ER completes; EX after APP; EX repeated (D6) |
| EX without SC (D6 does not make EX depend on SC) | Missing CC or ER (D3) |
| | Any activity outside the 8 labels, or any loop or rework (no evidence) |

The line is drawn where a high or medium-confidence domain rule (D1–D4, D6) is violated, or where there is *zero* supporting evidence and *no* rule (repeats, unknown activities). Everything that is merely unobserved but rule-compatible is admitted.

**PM4Py code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO, CC, ER, SC, EX = ("Register Order", "Credit Check", "Engineering Review",
                      "Supplier Confirmation", "Expedite Review")
APP, REL, ARC = "Approve Configuration", "Release Production", "Archive Case"

def _attach(parent, children):
    for c in children:
        c.parent = parent
        parent.children.append(c)
    return parent

def act(label): return ProcessTree(label=label)
def tau():      return ProcessTree()
def seq(*cs):   return _attach(ProcessTree(operator=Operator.SEQUENCE), cs)
def xor(*cs):   return _attach(ProcessTree(operator=Operator.XOR), cs)
def par(*cs):   return _attach(ProcessTree(operator=Operator.PARALLEL), cs)
def opt(label): return xor(act(label), tau())

model_permissive = seq(
    act(RO),
    par(
        seq(par(act(CC), act(ER)), opt(EX)),   # EX strictly after both checks
        opt(SC),                               # SC free before APP (D4 only)
    ),
    act(APP), act(REL), act(ARC),
)
print(model_permissive)
```

**Behavior deliberately excluded**
- Everything in the "Forbidden" column: D1, D2, D4, D3, D6 violations, repeats, and foreign labels.
- APP before SC or EX completes, since the parallel block must finish before APP.

**Known underfitting risks**
- It admits SC before both checks (SC CC ER). The data show 0/23 such cases, so it may be wrong.
- It cannot express a dependency if SC truly needs CC or credit results. Precision may be low.
- EX without SC, or ER SC CC EX, may never happen.
- Because it is nearly indifferent to order, conformance checking against it will miss ordering anomalies that matter for compliance.
- It still has no multi-SC or loop behavior, and no attribute conditioning.

| Conservative | RO CC ER SC APP ARC | Event 6 (ARC without REL): D2/D1. |
| Balanced | RO ER SC CC APP REL ARC | Event 3 (SC before CC completes): CC<SC, an evidence-derived soft edge and not a domain rule. |
| Balanced | RO CC EX ER APP REL ARC | Event 3 (EX before ER): ER<EX (D6/S6). |
| Balanced | RO CC ER SC APP EX REL ARC | Event 6 (EX after APP): EX<APP (D6/S6). |
| Permissive | RO CC EX ER SC APP REL ARC | Event 3 (EX before ER): D6/S6. |
| Permissive | RO CC ER APP SC REL ARC | Event 5 (SC after APP): D4. |
| Permissive | RO ER CC EX EX APP REL ARC | Event 5 (second EX): D6 (at most once). |
| Permissive | RO CC APP REL ARC | Event 3 (APP with ER not done): D3. |

# 8. Validation Code

I have not executed this script in the present environment. The API shapes follow the reminders. Minor version differences may need adjustment (for example, the return type of `check_soundness`, or the `play_out` arguments). POWL-to-Petri-net conversion requires a recent PM4Py (2.7.x with POWL support).

```python
import itertools, random
from collections import Counter

import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.petri_net.semantics import ClassicSemantics

# ------------------------------------------------------------------ labels
RO, CC, ER, SC, EX = ("Register Order", "Credit Check", "Engineering Review",
                      "Supplier Confirmation", "Expedite Review")
APP, REL, ARC = "Approve Configuration", "Release Production", "Archive Case"
ABBR = dict(RO=RO, CC=CC, ER=ER, SC=SC, EX=EX, APP=APP, REL=REL, ARC=ARC)
def T(s): return tuple(ABBR[x] for x in s.split())

# ------------------------------------------------------------------ 1. log
VARIANTS = [
    (12, "RO CC ER SC APP REL ARC"),
    (7,  "RO ER CC SC APP REL ARC"),
    (4,  "RO CC ER APP REL ARC"),
    (3,  "RO ER CC APP REL ARC"),
    (2,  "RO CC SC ER APP REL ARC"),
    (1,  "RO CC ER SC EX APP REL ARC"),
    (1,  "RO ER CC EX SC APP REL ARC"),
]
trace_strings = []
for n, s in VARIANTS:
    trace_strings += [",".join(T(s))] * n            # no spaces around commas
assert len(trace_strings) == 30
log = pm4py.parse_event_log_string(trace_strings)
OBSERVED = {T(s) for _, s in VARIANTS}

EXPECTED_DFG = {
    (RO, CC): 19, (RO, ER): 11, (CC, ER): 17, (ER, CC): 11, (CC, SC): 9,
    (ER, SC): 13, (SC, ER): 2, (ER, APP): 6, (CC, APP): 3, (SC, APP): 20,
    (SC, EX): 1, (CC, EX): 1, (EX, SC): 1, (EX, APP): 1, (APP, REL): 30, (REL, ARC): 30,
}
dfg, sa, ea = pm4py.discover_dfg(log)
print("DFG matches the given DFG:", dict(dfg) == EXPECTED_DFG)

# ------------------------------------------------------------------ models
def _attach(parent, children):
    for c in children:
        c.parent = parent
        parent.children.append(c)
    return parent
def act(l): return ProcessTree(label=l)
def tau():  return ProcessTree()
def seq(*c): return _attach(ProcessTree(operator=Operator.SEQUENCE), c)
def xor(*c): return _attach(ProcessTree(operator=Operator.XOR), c)
def par(*c): return _attach(ProcessTree(operator=Operator.PARALLEL), c)
def opt_pt(l): return xor(act(l), tau())

def build_conservative():
    cores = [[CC, ER, SC], [ER, CC, SC], [CC, ER], [ER, CC],
             [CC, SC, ER], [CC, ER, SC, EX], [ER, CC, EX, SC]]
    return seq(act(RO), xor(*[seq(*[act(a) for a in c]) for c in cores]),
               act(APP), act(REL), act(ARC))

def build_balanced():
    def opt(l): return OperatorPOWL(operator=Operator.XOR,
                                    children=[Transition(l), SilentTransition()])
    ro, cc, er = Transition(RO), Transition(CC), Transition(ER)
    sc, ex = opt(SC), opt(EX)
    app, rel, arc = Transition(APP), Transition(REL), Transition(ARC)
    po = StrictPartialOrder(nodes=[ro, cc, er, sc, ex, app, rel, arc])
    for a, b in [(ro, cc), (ro, er), (cc, sc), (cc, ex), (er, ex),
                 (sc, app), (ex, app), (app, rel), (rel, arc)]:
        po.order.add_edge(a, b)
    return po

def build_permissive():
    return seq(act(RO),
               par(seq(par(act(CC), act(ER)), opt_pt(EX)), opt_pt(SC)),
               act(APP), act(REL), act(ARC))

models = {"conservative": build_conservative(),
          "balanced": build_balanced(),
          "permissive": build_permissive()}

# ------------------------------------------------------------------ 2. Petri nets
nets = {k: pm4py.convert_to_petri_net(m) for k, m in models.items()}

# ------------------------------------------------------------------ helpers
def safe(fn, *a, **k):
    try:
        return fn(*a, **k)
    except Exception as e:
        return f"n/a ({type(e).__name__}: {e})"

def mkey(m): return frozenset((id(p), c) for p, c in m.items() if c > 0)

def enumerate_language(net, im, fm, max_len=10):
    """Exhaustive DFS over (marking, visible prefix). Exact for acyclic nets IF not truncated."""
    sem, target = ClassicSemantics(), mkey(fm)
    lang, truncated, seen, stack = set(), False, set(), [(im, ())]
    while stack:
        m, tr = stack.pop()
        k = (mkey(m), tr)
        if k in seen:
            continue
        seen.add(k)
        if mkey(m) == target:
            lang.add(tr)
        for t in sem.enabled_transitions(net, m):
            ntr = tr + ((t.label,) if t.label is not None else ())
            if len(ntr) > max_len:
                truncated = True
                continue
            stack.append((sem.execute(t, net, m), ntr))
    return lang, truncated

def random_playout(net, im, fm, n=500, seed=7, max_steps=60):
    """Sampled playout. Shows what is reachable, NOT a proof of language inclusion."""
    rnd, sem, out = random.Random(seed), ClassicSemantics(), Counter()
    for _ in range(n):
        m, tr = im, []
        for _ in range(max_steps):
            en = sorted(sem.enabled_transitions(net, m), key=lambda t: t.name)
            if not en:
                break
            t = rnd.choice(en)
            m = sem.execute(t, net, m)
            if t.label is not None:
                tr.append(t.label)
        if mkey(m) == mkey(fm):
            out[tuple(tr)] += 1
    return out

# ------------------------------------------------------------------ 3-4. soundness + metrics
for name, (net, im, fm) in nets.items():
    res = safe(pm4py.check_soundness, net, im, fm, print_diagnostics=False)
    sound = res[0] if isinstance(res, tuple) else res
    print(f"\n=== {name} === transitions={len(net.transitions)} places={len(net.places)} sound={sound}")
    print(" fitness (alignments):   ", safe(pm4py.fitness_alignments, log, net, im, fm))
    print(" precision (alignments): ", safe(pm4py.precision_alignments, log, net, im, fm))
    print(" generalization (TBR):   ", safe(pm4py.generalization_tbr, log, net, im, fm))
    print(" simplicity (arc degree):", safe(pm4py.simplicity_petri_net, net, im, fm))

# ------------------------------------------------------------------ 5. exhaustive + sampled playout
langs = {}
for name, (net, im, fm) in nets.items():
    lang, trunc = enumerate_language(net, im, fm)
    langs[name] = lang
    print(f"\n{name}: |L|={len(lang)}, observed covered={len(OBSERVED & lang)}/{len(OBSERVED)}, "
          f"unobserved admitted={len(lang - OBSERVED)}, truncated={trunc}")
    sample = random_playout(net, im, fm)
    print("  sampled variants:", len(sample), "| all inside exhaustive language:", set(sample) <= lang)
    print("  (sampling is a sanity check only; it proves nothing about language inclusion)")
    print("  pm4py.play_out attempt:",
          type(safe(pm4py.play_out, net, im, fm, parameters={"num_traces": 50})).__name__)

# Oracle: languages must equal the rule-defined sets (brute force over permutations).
def universe():
    for with_sc in (0, 1):
        for with_ex in (0, 1):
            core = [CC, ER] + ([SC] if with_sc else []) + ([EX] if with_ex else [])
            for p in itertools.permutations(core):
                yield (RO,) + p + (APP, REL, ARC)
def spec_permissive(t):
    return EX not in t or (t.index(EX) > t.index(CC) and t.index(EX) > t.index(ER))
def spec_balanced(t):
    return spec_permissive(t) and (SC not in t or t.index(SC) > t.index(CC))

SPEC = {"conservative": set(OBSERVED),
        "permissive": {t for t in universe() if spec_permissive(t)},
        "balanced": {t for t in universe() if spec_balanced(t)}}
for k in models:
    print(f"language of {k} equals rule-defined set:", langs[k] == SPEC[k])
print("nesting conservative < balanced < permissive:",
      langs["conservative"] < langs["balanced"] < langs["permissive"])
# Exact language-coverage ratio (uniform over traces; NOT a standard precision metric):
for k in models:
    print(f"  {k}: |observed  L| / |L| = {len(OBSERVED & langs[k])}/{len(langs[k])}")

# ------------------------------------------------------------------ 6. manual suite
# (trace, accepted by conservative, balanced, permissive)
SUITE = [
    ("obs V-A",               "RO CC ER SC APP REL ARC",        (1, 1, 1)),
    ("obs V-E",               "RO CC SC ER APP REL ARC",        (1, 1, 1)),
    ("obs V-G",               "RO ER CC EX SC APP REL ARC",     (1, 1, 1)),
    ("EX without SC",         "RO CC ER EX APP REL ARC",        (0, 1, 1)),
    ("V-E + EX",              "RO CC SC ER EX APP REL ARC",     (0, 1, 1)),
    ("SC between ER and CC",  "RO ER SC CC APP REL ARC",        (0, 0, 1)),
    ("SC first",              "RO SC CC ER APP REL ARC",        (0, 0, 1)),
    ("ER SC CC EX",           "RO ER SC CC EX APP REL ARC",     (0, 0, 1)),
    ("REL before APP",        "RO CC ER SC REL APP ARC",        (0, 0, 0)),
    ("ER missing",            "RO CC SC APP REL ARC",           (0, 0, 0)),
    ("CC missing",            "RO ER SC APP REL ARC",           (0, 0, 0)),
    ("SC after APP",          "RO CC ER APP SC REL ARC",        (0, 0, 0)),
    ("EX before ER",          "RO CC EX ER APP REL ARC",        (0, 0, 0)),
    ("EX twice",              "RO CC ER EX EX APP REL ARC",     (0, 0, 0)),
    ("SC twice",              "RO CC ER SC SC APP REL ARC",     (0, 0, 0)),
    ("wrong start",           "CC RO ER SC APP REL ARC",        (0, 0, 0)),
    ("no archive",            "RO CC ER SC APP REL",            (0, 0, 0)),
    ("EX after APP",          "RO CC ER SC APP EX REL ARC",     (0, 0, 0)),
]
for label, s, exp in SUITE:
    got = tuple(int(T(s) in langs[k]) for k in ("conservative", "balanced", "permissive"))
    print(f"{'PASS' if got == exp else 'FAIL'}  {label:24s} expected={exp} got={got}")
```

**Limitations.**
- The exhaustive enumerator is exact here only because all three nets are acyclic and `truncated` stays `False`. For models with loops, enumeration would be bounded, not exhaustive.
- Sampled playout shows reachability only. It cannot prove language inclusion or exclusion.
- Alignment-based precision and TBR generalization are log-based approximations. They do not compare full (possibly infinite) languages.
- The language-coverage ratio is an ad hoc, uniform-over-traces measure and not a standard metric.

# 9. Recommendation and Data-Collection Plan

**Immediate use: Balanced.** It has full fitness, rule-consistent generalization, a single explainable constraint set, robust handling of missing SC, and a small, auditable deviation set. Deviations from it are interpretable (for example, SC completing before CC).

**Sensitivity analysis: Permissive.** Run conformance against both. Cases accepted by permissive but rejected by balanced (ER SC CC, SC-first) are exactly the cases that test the CCSC bias and D5. The conservative model should be kept only as a regression baseline and whitelist of known-good variants. It is not recommended for operational monitoring, because it would flag roughly 7% (rough range 3–15%) of legitimate future cases.

**Data-collection plan**

1. **Attributes.**
   - Component type per component (external vs stocked), plus the number of components per order.
   - Customer tier, order value, and priority flag.
   - Expedite reason.
   - Source-system event IDs and PO line references.
2. **Lifecycle timestamps.** Start and complete events for CC, ER, SC, and EX, with source-system time separate from ingestion time, plus a flag for tie-broken ordering (S7). This is the only way to separate sequence from concurrency from overlap.
3. **Reconcile SC against ERP purchase-order lines.** External components with no SC event are missing data. Stocked components with an SC event contradict S4. This yields a direct estimate of the real missing rate versus the claimed 5–10%, and separates "missing" from "optional".

| Hypothesis | Observation that supports it | Observation that refutes it |
|---|---|---|
| CC and ER truly concurrent | ER starts before CC completes (overlapping intervals), with ER completing first. | ER always starts after CC completes (S1), with ER-first appearances due only to ties. |
| XOR of sequential orders (case-type-dependent) | Order perfectly predicted by an attribute, with no overlap. | Order is independent of attributes, and intervals overlap. |
| CCSC dependency (balanced) | No SC completes before CC across a larger sample, especially in external, ER-first cases. To bound the violation rate below 20% (95% confidence) need about 14 informative cases, below 10% about 29. | Even one SC completing before CC with a lifecycle start after ER's completion supports D5 and the permissive model. |
| SC optional vs mandatory-but-missing | External components with no SC after reconciliation are missing. Stocked with no SC confirm S4. | All SC-absent cases prove to be external with integration gaps (then SC is mandatory and optionality was an artifact). |
| EX semantics | EX before both checks complete or twice refutes D6. EX without SC supports independence. | Every EX case contains SC (suggesting dependency). |
| Multi-component SC | More than one SC in a case, or SC with component identifiers. | Always at most one SC per case. |

Most informative future traces:
- ER-first external-component cases with lifecycle data, to test CCSC and concurrency together.
- Expedite cases (stratify by priority flag, since EX currently appears in only 2/30 cases).
- Cases with SC-absent events but external components.
- Multi-component orders.

# 10. Uncertainty Statement

The probabilities are subjective and rough. They are calibrated against the evidence (30 cases, 7 variants, two singletons).

| Decision | Confidence | Basis |
|---|---|---|
| D1/D2 hard constraints (start, end, APPREL) | ~97% | 30/30, high-confidence domain rules. |
| CC and ER are mandatory, and both before APP | ~90% | 30/30. D3. |
| CC and ER completion order is *not* universally fixed (S1 rejected as a universal rule) | ~90% | 11/30 contradict it. About 10% residual for tie-break or ingestion artifacts (S7). |
| Mechanism of the CC/ER order is "concurrent" rather than a case-type XOR or mixture | ~50–55% | The language is identical for the pair. The mechanism is unidentifiable from completion order (D7). |
| SC has legitimate skips beyond missing events | ~85% | 7 absences versus 1–3 explained by S5. The residual reflects possible non-random (clustered) missingness. |
| SC is ordered after CC (balanced edge) | ~55% | 0/8 informative cases (95% upper bound on violation  31%), with D5 pulling the other way. |
| SC can complete before ER | ~75% | 2 cases (V-E), plus D5. |
| SC can complete before *both* checks (permissive) | ~20–25% | 0/23 observed. Possible only if SC starts on partial information. |
| EX is optional, at most once, after both checks | ~75% | Two cases and two rules (possibly not independent). |
| EX is order-free relative to SC | ~80% | 1 vs 1 plus S6. |
| EX can occur without SC | ~60% | No observed instance. The rule does not forbid it. |
| Balanced language equals the true language | ~25–35% | The space of alternatives is large and some constraints rest on small counts. |
| True language  permissive | ~70–75% | Depends on D1–D4 and D6 holding. |
| True language  balanced | ~45–50% | Mostly through the CCSC edge and the unseen EX/SC combinations. |
| Next case is in the conservative language | ~93% (rough 85–97%) | Good–Turing: 2 singleton variants of 30. |

**Plausible alternative interpretations that would materially change the recommendation**

1. **S1 is correct for the process and ER-first cases are ingestion artifacts.** If lifecycle data show CC always completes before ER starts, and S7 ties explain the 11 ER-first cases, then the balanced model's CCER is wrong and should be replaced by CCER (sequence). The conservative-like family becomes much more accurate, and concurrency-based generalization would create systematically false admits.
2. **SC is actually mandatory for external components and the 7 SC-absent cases are clustered integration failures.** If a time-clustered outage accounts for the absences, SC should be mandatory (not `×(SC,)`). Both the balanced and permissive models would then admit too much, and robustness to missingness should be handled by a separate data-repair step instead of in control flow.
3. **Case-type-dependent routing.** If CCER vs ERCC is determined by an attribute (for example customer tier), an XOR with guards would replace concurrency. The language would be unchanged, but conformance diagnostics and any predictive or simulation use would change.
4. **SC is triggered by partial information from either check (literal D5).** If lifecycle data show SC completing before CC, the permissive model (or the D5-strict variant admitting ER SC CC) becomes the recommended default and the balanced CCSC edge is dropped.
