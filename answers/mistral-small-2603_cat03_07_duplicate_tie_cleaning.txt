# OCEL Cleaning and Ordering Pipeline

## 1. Duplicate-handling decision tree

```mermaid
graph TD
    A[Start] --> B{Exact technical duplicate?}
    B -->|Yes| C[Drop all but one with full provenance]
    B -->|No| D{Same physical event observed by multiple systems?}
    D -->|Yes| E[Merge attributes and relations, retain both with refined labels]
    D -->|No| F{Summary event derived from detailed event?}
    F -->|Yes| G[Retain both with refined labels/qualifiers]
    F -->|No| H{Harmonization collision between semantically distinct activities?}
    H -->|Yes| I[Retain both unchanged]
    H -->|No| J{Concurrent same-label events with different objects?}
    J -->|Yes| K[Retain both unchanged]
    J -->|No| L{Unresolved candidate?}
    L -->|Yes| M[Quarantine for review]
```

**Terminal decisions:**
- **Exact technical duplicate**: Drop all but one with full provenance
- **Same physical event observed by multiple systems**: Merge attributes and relations, retain both with refined labels
- **Summary event derived from detailed event**: Retain both with refined labels/qualifiers
- **Harmonization collision**: Retain both unchanged
- **Concurrent same-label events with different objects**: Retain both unchanged
- **Unresolved candidate**: Quarantine for review

## 3. Timestamp-tie ordering rules

**Deterministic partial-order-to-total-order policy:**

1. **Domain constraints** (semantic):
   - Payment lifecycle: authorize  capture (for same payment)
   - Logistics lifecycle: release  accept  handover

2. **Within-source sequence** (semantic):
   - Use `source_seq` when available for same source system
   - Preserve source-specific ordering semantics

3. **Lifecycle constraints on shared objects** (semantic):
   - Events sharing objects must respect business lifecycle
   - Example: For payment M1, e12 must precede e13

4. **Source-specific semantics** (semantic):
   - ERP summary events typically follow detailed events
   - WMS events typically precede carrier events

5. **Ingestion time** (deterministic fallback):
   - Only used when no semantic ordering is available
   - `ingested_at` as last resort tiebreaker

6. **Stable fallback order** (deterministic):
   - Alphabetical by source system when all else fails
   - Preserves determinism without implying business meaning

**Why microseconds are dangerous:**
Adding microseconds before deciding semantic order can encode false causality by implying a precision that doesn't exist in the source systems. The timestamps represent business events, not clock ticks, so artificial sub-second precision can create spurious ordering that misrepresents the actual business process.

## 4. Conservative cleaning pipeline

**Minimum-change scenario:**

1. **Duplicate removal:**
   - Only remove exact technical duplicates (same payload_hash and timestamp)
   - For e03/e04: merge attributes but retain both with qualifiers
   - For e11/e16: merge attributes but retain both with system qualifiers

2. **Abstraction-level preservation:**
   - Retain both detailed and summary events (e06/e07, e13/e15, e14/e15)
   - Add qualifiers to activities to distinguish levels

3. **Provenance preservation:**
   - Store original identifiers, labels, timestamps, and sources
   - Maintain full source_event_key and source_seq information

4. **Ordering approach:**
   - Use semantic ordering rules first
   - Fall back to within-source sequence
   - Use ingestion time only as last resort

**Expected retained event count:** 17 events (all original events preserved with refinements)

**Implementation steps:**
1. Identify and merge exact duplicates (none in this dataset)
2. Add qualifiers to events with known relationships (e03, e04, e06, e07, e09, e10, e11, e16)
3. Apply semantic ordering rules
4. Preserve all E2O relations

## 5. Aggressive alternatives

**Scenario 1: Evidence-based semantic merging**

1. **Duplicate handling:**
   - Merge e03/e04 into single event with combined attributes
   - Merge e11/e16 into single invoice event
   - Keep e05 and e14 as distinct

2. **Summary events:**
   - Merge e06/e07 into single "Pack Package" event with combined attributes
   - Merge e13/e15 and e14/e15 into single payment lifecycle events

3. **Ordering:**
   - Apply same semantic ordering rules

**Expected retained event count:** 12 events

**Most likely semantic damage:**
- Loss of system-specific attributes in merged events
- Potential loss of detail in abstraction-level events
- Possible false simplification of the process flow

**Why `have_common_object=True` is insufficient:**
For e13 and e14, they share O1 and V1 but represent different Payment objects (M1 vs M2). Common objects alone don't indicate duplication - the distinct payment identifiers and amounts indicate separate business events that must be preserved.

**Scenario 2: Mechanically aggressive PM4Py merging**

1. **Duplicate handling:**
   - Use `pm4py.ocel_merge_duplicates` with activity and timestamp as keys
   - Merge all events with same activity and timestamp
   - Drop all qualifiers and system-specific attributes

2. **Ordering:**
   - Use `pm4py.ocel_sort_by_additional_column` with `ingested_at` as primary key

**Expected retained event count:** 8 events

**Most likely semantic damage:**
- Complete loss of system provenance
- Collapsing distinct business events
- False simplification of the process flow
- Potential creation of false rework loops

## 6. PM4Py-oriented Python implementation

```python
import pm4py
from copy import deepcopy
from typing import Dict, List, Tuple

def clean_conservative(ocel_raw: pm4py.objects.ocel.OCEL) -> pm4py.objects.ocel.OCEL:
    """Conservative cleaning pipeline with minimal changes"""
    ocel = deepcopy(ocel_raw)

    # Pre-check for candidate duplicate groups
    candidate_groups = _identify_candidate_duplicates(ocel)

    # Handle e03/e04 (same physical scan)
    if ('e03', 'e04') in candidate_groups:
        ocel = _merge_verified_pair(ocel, 'e03', 'e04', 'same_physical_scan',
                                   activity_qualifier='WMS-enriched')

    # Handle e11/e16 (same invoice)
    if ('e11', 'e16') in candidate_groups:
        ocel = _merge_verified_pair(ocel, 'e11', 'e16', 'same_invoice',
                                   activity_qualifier='system-qualified')

    # Add qualifiers to events with known relationships
    ocel = _add_qualifiers(ocel)

    # Sort using semantic ordering rules
    ocel = _semantic_sort(ocel)

    # Validate referential integrity
    _validate_integrity(ocel)

    return ocel

def clean_aggressive(ocel_raw: pm4py.objects.ocel.OCEL) -> pm4py.objects.ocel.OCEL:
    """Aggressive merging using PM4Py functions"""
    ocel = deepcopy(ocel_raw)

    # WARNING: This will merge events with same activity and timestamp
    # without considering semantic relationships
    ocel = pm4py.ocel_merge_duplicates(ocel, activity_key='activity',
                                      timestamp_key='timestamp')

    # Sort by ingestion time as fallback
    ocel = pm4py.ocel_sort_by_additional_column(ocel, 'ingested_at')

    # Validate referential integrity
    _validate_integrity(ocel)

    return ocel

def _identify_candidate_duplicates(ocel: pm4py.objects.ocel.OCEL) -> set:
    """Identify groups of events that might be duplicates"""
    groups = set()

    # Group by activity and timestamp
    by_activity_time = {}
    for event in ocel.events.to_dict('records'):
        key = (event['activity'], event['timestamp'])
        if key not in by_activity_time:
            by_activity_time[key] = []
        by_activity_time[key].append(event['eid'])

    # Identify candidate groups (more than one event with same activity/time)
    for events in by_activity_time.values():
        if len(events) > 1:
            groups.update(frozenset(pair) for pair in
                         [(events[i], events[j]) for i in range(len(events))
                          for j in range(i+1, len(events))])

    return groups

def _merge_verified_pair(ocel: pm4py.objects.ocel.OCEL, eid1: str, eid2: str,
                        merge_type: str, activity_qualifier: str = None) -> pm4py.objects.ocel.OCEL:
    """Merge two verified duplicate events with provenance preservation"""
    events = ocel.events
    relations = ocel.relations

    # Get the events
    event1 = events[events['eid'] == eid1].iloc[0]
    event2 = events[events['eid'] == eid2].iloc[0]

    # Create merged event
    merged = {
        'eid': f"{eid1}_merged_{eid2}",
        'timestamp': event1['timestamp'],  # Keep original timestamp
        'activity': f"{event1['activity']} ({activity_qualifier})" if activity_qualifier else event1['activity'],
        'source': f"{event1['source']}/{event2['source']}",
        'source_event_key': f"{event1['source_event_key']},{event2['source_event_key']}",
        'source_seq': min(event1['source_seq'], event2['source_seq']),
        'ingested_at': max(event1['ingested_at'], event2['ingested_at']),
        'payload_hash': f"{event1['payload_hash']}+{event2['payload_hash']}",
        'original_activity': f"{event1['activity']},{event2['activity']}",
        'original_timestamp': event1['timestamp'],  # Preserve original
        'original_source': f"{event1['source']},{event2['source']}",
        'merge_type': merge_type,
        'merge_confidence': 'high'
    }

    # Merge attributes - keep all non-conflicting attributes
    for col in events.columns:
        if col not in ['eid', 'timestamp', 'activity', 'source', 'source_event_key',
                      'source_seq', 'ingested_at', 'payload_hash', 'related objects']:
            if event1[col] == event2[col]:
                merged[col] = event1[col]
            else:
                merged[f"{col}_1"] = event1[col]
                merged[f"{col}_2"] = event2[col]

    # Merge relations - union of both
    merged_relations = []
    for rel in relations.to_dict('records'):
        if rel['source'] in [eid1, eid2]:
            rel['source'] = merged['eid']
            merged_relations.append(rel)

    # Create new OCEL
    new_events = pd.concat([
        events[events['eid'] != eid1],
        events[events['eid'] != eid2],
        pd.DataFrame([merged])
    ], ignore_index=True)

    new_relations = pd.DataFrame(merged_relations)

    # Update OCEL
    new_ocel = pm4py.objects.ocel.OCEL()
    new_ocel.events = new_events
    new_ocel.relations = new_relations
    new_ocel.objects = ocel.objects
    new_ocel.parameters = ocel.parameters

    return new_ocel

def _add_qualifiers(ocel: pm4py.objects.ocel.OCEL) -> pm4py.objects.ocel.OCEL:
    """Add qualifiers to events with known relationships"""
    events = ocel.events.copy()

    # Add qualifiers based on known relationships
    for i, row in events.iterrows():
        if row['eid'] == 'e04':
            events.at[i, 'activity'] = "Pick Item (scanner)"
        elif row['eid'] == 'e06':
            events.at[i, 'activity'] = "Pack Package (detailed)"
        elif row['eid'] == 'e07':
            events.at[i, 'activity'] = "Pack Package (summary)"
        elif row['eid'] == 'e09':
            events.at[i, 'activity'] = "Dispatch Package (carrier acceptance)"
        elif row['eid'] == 'e10':
            events.at[i, 'activity'] = "Handover to Carrier"
        elif row['eid'] == 'e16':
            events.at[i, 'activity'] = "Issue Invoice (billing system)"

    new_ocel = deepcopy(ocel)
    new_ocel.events = events
    return new_ocel

def _semantic_sort(ocel: pm4py.objects.ocel.OCEL) -> pm4py.objects.ocel.OCEL:
    """Sort events using semantic ordering rules"""
    events = ocel.events.copy()

    # Define semantic ordering rules
    def get_sort_key(row):
        timestamp = row['timestamp']

        # Payment lifecycle ordering
        if row['activity'].startswith('Authorize Payment'):
            return (timestamp, 1)
        if row['activity'].startswith('Capture Payment'):
            return (timestamp, 2)

        # Logistics lifecycle ordering
        if row['activity'] == 'Dispatch Package (release)':
            return (timestamp, 3)
        if row['activity'] == 'Dispatch Package (carrier acceptance)':
            return (timestamp, 4)
        if row['activity'] == 'Handover to Carrier':
            return (timestamp, 5)

        # Default ordering
        return (timestamp, 6)

    # Apply sorting
    events['sort_key'] = events.apply(get_sort_key, axis=1)
    events = events.sort_values('sort_key').drop(columns=['sort_key'])

    new_ocel = deepcopy(ocel)
    new_ocel.events = events
    return new_ocel

def _validate_integrity(ocel: pm4py.objects.ocel.OCEL):
    """Validate referential integrity after changes"""
    # Check all event relations point to valid events
    valid_eids = set(ocel.events['eid'])
    invalid_relations = ocel.relations[~ocel.relations['source'].isin(valid_eids)]
    if not invalid_relations.empty:
        raise ValueError(f"Invalid relations found: {len(invalid_relations)}")

    # Check all relations point to valid objects
    valid_oids = set(ocel.objects['oid'])
    invalid_relations = ocel.relations[~ocel.relations['target'].isin(valid_oids)]
    if not invalid_relations.empty:
        raise ValueError(f"Relations with invalid objects found: {len(invalid_relations)}")
```

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments:**
   - *Failure*: Merging e13/e14 into single event
   - *Safeguard*: Explicit check for distinct payment identifiers (M1 vs M2)
   - *Detection*: Payment-flattened DFG shows fewer edges than expected

2. **Converting abstraction-level updates into false rework:**
   - *Failure*: Treating e06 (detailed) and e07 (summary) as same event
   - *Safeguard*: Qualify events with "detailed"/"summary" labels
   - *Detection*: Order-flattened DFG shows false loops

3. **Ordering by ingestion time:**
   - *Failure*: Using `ingested_at` as primary sort key
   - *Safeguard*: Semantic ordering rules first, ingestion time only as fallback
   - *Detection*: Events out of business-logical order

4. **Treating shared objects as proof of duplication:**
   - *Failure*: Merging e13/e14 because they share O1 and V1
   - *Safeguard*: Check for distinct payment objects (M1 vs M2)
   - *Detection*: Payment-flattened DFG shows incorrect aggregation

5. **Unioning incompatible E2O relations:**
   - *Failure*: Combining relations from different abstraction levels
   - *Safeguard*: Preserve original relations and add qualified relations
   - *Detection*: OC-DFG shows edges that don't make business sense

6. **Changing durations through synthetic microseconds:**
   - *Failure*: Adding microseconds to create artificial ordering
   - *Safeguard*: Never modify original timestamps
   - *Detection*: Duration calculations show impossible values

7. **Losing source-authoritative attributes:**
   - *Failure*: Discarding attributes during aggressive merging
   - *Safeguard*: Preserve all non-conflicting attributes in merge
   - *Detection*: Attribute completeness metrics drop

8. **Applying duplicate functions without inspecting candidate groups:**
   - *Failure*: Using `pm4py.ocel_drop_duplicates` blindly
   - *Safeguard*: Pre-check to identify candidate duplicate groups
   - *Detection*: Unexpected event count reduction or semantic loss
