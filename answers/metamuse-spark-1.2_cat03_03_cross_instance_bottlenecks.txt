## 1. Interaction-graph description

Typed interaction graph $G = (V,E)$ where nodes are objects and edges are O2O relations or event-mediated co-occurrences. Extraction is at object instance level, not flattened.

**Node types and instances:**

* **Job:** J1, J2, J3, J4, J5, J6 - primary case objects
* **Component:** C1..C6 - each `requires` one Job; physical materialization
* **ComponentLot:** L7 {C2,C5}, L8 {C1,C3} - inventory / quality domain object
* **Batch:** B1 {J1,J2,J3}, B2 {J4,J5} - synchronization barrier on OVEN-1
* **Machine:** CNC-2, OVEN-1, TEST-1 - capacity resources
* **Tool:** FIX-A, RACK-7, CAL-3 - auxiliary resources with independent lifecycle
* **Shipment:** S1 {J1,J4}, S2 {J2,J3}, S3 {J5,J6} - outgoing consolidation barrier

**Edge types / qualifiers:**

Observed O2O (from table, direct from system):

```
requires:      J1->C1, J2->C2, J3->C3, J4->C4, J5->C5, J6->C6
contains:      L7->C2, L7->C5, L8->C1, L8->C3
batches:       B1->J1, B1->J2, B1->J3, B2->J4, B2->J5
consolidates:  S1->J1, S1->J4, S2->J2, S2->J3, S3->J5, S3->J6
```

Inferred / event-derived edges (not in O2O table but recorded via shared events):

```
uses:      J3 -FIX-A (acquire 09:00 release 11:40), J4 -FIX-A (process 11:45)
uses:      B1 -OVEN-1, B1 -RACK-7, B2 -OVEN-1, B2 -RACK-7, J1/J2/J3 -OVEN-1 via Batch Cure 12:05
uses:      J5/J6 -TEST-1, J5/J6 -CAL-3 via Final Test
quarantined: L7 -C2 -J2, L7 -C5 -J5 via Quarantine Lot 10:20 / Release Lot 13:50
```

**Direct vs. inferred:**

*Direct observation:* O2O relations listed above; Batch Cure event co-relating {B1, OVEN-1, RACK-7, J1,J2,J3, C1-3} at 12:05; FIX-A acquire/release timestamps; Quarantine/Release Lot events relating to L7; packing timestamps.

*Inferred:* `J4 waiting for FIX-A` - no `Wait for Tool` activity; inferred from J4 ready at CNC-2 at 09:50 + CNC-2 idle 10:05-10:47 + FIX-A held until 11:40 + J4 start 11:45. `J1/J2 waiting for B1` - inferred if readiness timestamps trustworthy. `J5 held by L7` - inferred from policy linkage L7->C5->J5 vs J2 override, but relation to Job is inconsistently logged.

**Higher-order motifs (>2 object types):**

**Motif A - Batch-Tool-Machine triangular blocking:** `RACK-7 -- B1/B2 -- OVEN-1`. Both B1 and B2 require *both* OVEN-1 *and* RACK-7. OVEN-1 idle 12:55-14:50 would suggest capacity free, but B2 cannot start at 13:10 when J4 ready because RACK-7 in cleaning/quarantine until 14:35. This is a 3-way AND-dependency invisible to Job-Machine or Batch-Machine edges alone.

**Motif B - Lot fan-out coupling across independent batches/shipments:** `L7 -- C2/C5 -- J2/J5 -- B1/B2 -- S2/S3`. Single lot L7 couples two jobs that are in different batches (B1 vs B2) and different shipments (S2 vs S3). Quarantine 10:20-13:50 creates cross-instance dependency between otherwise independent process instances. L8 {C1,C3} suggests J1 and J3 *could* have been similarly coupled but no quarantine observed.

**Motif C - Tool-mediated sequencing without machine contention:** `FIX-A -- J3/J4 -- CNC-2`. J3 holds FIX-A 09:00-11:40 while at unknown location; J4 occupies CNC-2 logical queue 09:50 onward. CNC-2 idle 42min proves machine not bottleneck, but FIX-A holds the line. Edge Job-Job via Tool, with Machine as witness. Job-flattened DFG shows only `Stage->Machine Process` 1.1h median, hides pre-queue.

**Motif D - Calibration serialization star:** `CAL-3 -- TEST-1 -- J5/J6`. TEST-1 can test any job, but every `Final Test` also requires CAL-3 (Tool). CAL-3 recalibration 16:35-17:20 after J5 blocks J6 despite J6 ready 16:05 and TEST-1 nominally idle. Binary tool dictates sequentialization, not machine capacity.

Compact edge-list representation:


## 2. Quantitative delay decomposition

All durations are *associative*, not causal proof. Each calculation states a counterfactual and its assumptions.

**Calc 1a: B1 synchronization waiting for J1**
Observation: J1 ready 08:10, B1 Batch Cure 12:05. Attributable waiting = 3h55m.
Counterfactual: *If* J1 could cure individually, or B1 dispatched on first-ready + minimal setup (e.g., at 08:25 when J2 ready + 15min load), J1 would have started ~08:40. Under that counterfactual, avoidable synchronization wait  3h25m after subtracting nominal load. 
Assumptions: readiness timestamps reflect true material readiness (trusted), no policy requiring 3-job full rack, OVEN-1 and RACK-7 available independently. If readiness is administrative rather than physical, wait overestimated. Evidence that J2's Lot quarantine was overridden suggests readiness may be policy-flexible, weakening trust in readiness.

**Calc 1b: B1 synchronization waiting for J2**
Observation: J2 ready 08:25 to 12:05 = 3h40m.
Counterfactual: Same individual-cure counterfactual as J1. If B1 allowed to depart with 2 jobs at 08:25, J2 wait  0m for J3 (J3 ready 11:55). The 3h30m until J3 arrival is pure synchronization tail. 
Conjecture distinction: We observe J3 is the *last-arriving* trigger (10min wait for J3). We infer J1/J2 waited *for* J3, but temporal succession does not prove J3 arrival *caused* dispatch; batch could have been held for OVEN-1 schedule or RACK-7 availability. However, 12:05 start only 10m after J3 ready makes J3 as pacing object highly plausible. Alternative: shift start to 14:50 level of B2 suggests batch window policy, not pure arrival.

**Calc 2: FIX-A contention delay plausibly associated with J4**
Observation: J4 reaches CNC-2 09:50. FIX-A held by J3 until 11:40. CNC-2 idle 10:05-10:47 (42m). J4 Machine Process starts 11:45.
Plausibly associated waiting = 11:45 - 09:50 = 1h55m total pre-process. Of that, 42m of proven machine idle rules out machine capacity as necessary cause.
Counterfactual: *If* FIX-A had duplicate instance or J3 released earlier, J4 could have started during CNC-2 idle window, e.g., 10:05-10:47. Under that, avoidable delay 42m proven idle + additional 58m (10:47-11:45) plausibly also FIX-A-related = up to 1h55m, but only 42m is evidence against machine capacity; remainder could also be CNC-2 setup or undetected operator absence.
Assumptions: FIX-A is exclusive and required for J4's operation (supported by shared event qualifier), no other prerequisite missing. System has no `Wait for Tool` activity so gap is hidden. Correlation does not prove FIX-A *caused* full delay; we treat as resource feasibility: FIX-A unavailability makes start infeasible, but feasibility  causality.

**Calc 3: Shipment consolidation delay imposed on J1 by S1**
Observation: J1 packed 13:30, J4 packed 19:10, S1 dispatches 19:25. J1 post-pack holding = 5h55m. Last-job-to-dispatch after J4 = 15m.
Counterfactual: *If* S1 policy allowed partial dispatch or J1 shipped via S2/S3 or solo, J1 could dispatch ~13:55 (25m after pack like S2 benchmark) vs 19:25 actual. Consolidation-attributable extra holding = 19:25-13:55  5h30m. Even vs generous 35m benchmark (S3) = 5h20m.
Assumptions: Pack = ready-to-ship, S1 consolidation requires *both* J1+J4 present (policy constraint), no other S1 delay (customs, transport). Shipment-flattened DFG median `Create->Load 0.8h / Load->Dispatch 0.3h` completely hides this 5h55 intra-shipment wait because it measures shipment lifecycle starting at `Create Shipment`, not job pack time.
Evidence vs conjecture: Temporal precedence (J1 packed 5h40m before J4) plus policy S1 containing both proves J1 wait *coincident* with J4 delay. Whether caused by J4's upstream delays (FIX-A, B2/RACK-7, Lot) is transitive conjecture but strongly plausible via chain.

**Calc 4: CAL-3 calibration delay plausibly associated with J6**
Observation: J6 ready for final test 16:05, J5 tests 16:10-16:35, CAL-3 recalibrated 16:35-17:20, TEST-1 idle 16:35-17:25, J6 tests 17:25-17:50.
Plausibly associated waiting = 17:25-16:05 = 1h20m.
Counterfactual: *If* CAL-3 were not required, or duplicate, or recalibration deferrable/parallelized, J6 could have tested immediately after J5 at 16:35 (or earlier overlapping if TEST-1 allowed parallel). Under that, avoidable wait  50m (16:35-17:25) of TEST-1 idle that aligns exactly with CAL-3 recalibration. Lower bound: 45m of CAL-3 recalibration (16:35-17:20) overlaps idle; 5m additional 17:20-17:25 may be setup.
Assumptions: CAL-3 required for every Final Test (evidence: every Final Test relates to CAL-3), recalibration is mandatory after J5, TEST-1 idle not due to operator break (not logged). Resource feasibility makes CAL-3 necessary condition; we do not claim recalibration *intention* was triggered by J5 vs periodic.

**Calc 5: RACK-7 quarantine delay for B2**
Observation: J4 ready 13:10, J5 ready 14:40, OVEN-1 idle 12:55-14:50, RACK-7 cleaning/quarantine until 14:35, B2 starts 14:50.
Total J4 wait = 1h40m (13:10-14:50), J5 wait = 10m (14:40-14:50). OVEN-1 idle proves machine not blocking.
Counterfactual: *If* RACK-7 had been available at 13:10 (or duplicate rack), B2 could have started with J4 alone at ~13:10-13:25, or waited only for J5 until 14:40. Under single-job dispatch policy, J4 avoidable wait  1h25m (until RACK-7 free 14:35) + 15m load = 1h40m attributable to RACK-7, not OVEN-1. Even if 2-job batch required, wait until J5 14:40 = 1h30m, of which 1h25m overlaps RACK-7 unavailability, leaving only 5m after RACK-7 free before J5 readiness.
Assumptions: B2 requires RACK-7 (supported by 12:05 event type), cleaning/quarantine is blocking resource state, not just informational. Could also be that B2 policy requires J5 regardless of RACK-7, making J5 readiness the binding constraint; data cannot discriminate.

Collectively, Job-flattened median `Inspect->Pack 1.0h` and `Pack->Dispatch 1.1h` average out these extreme synchronization tails, yielding "broadly normal" totals within 1.8 SD.

## 4. What flattening misses

**Job-flattened:**
* Visible: End-to-end Stage->Machine Process->Inspect->Pack->Dispatch edges; frequencies correctly show 6 cases through each. Shows Rework loop (2/6 =33% Inspect->Rework). Performance median hides variance.
* Hidden/Duplicated: Batch Cure event at 12:05 duplicated as 3 separate Job events (`Machine Process` or inferred Batch Cure) triples frequency of batch activity; hides that J1/J2 waited for J3; hides FIX-A wait (no activity between Stage and Machine Process, so delay collapsed into Stage->Machine Process 1.1h); hides L7 Quarantine/Release entirely due to extraction only on direct Job relation; hides shipment consolidation wait (Pack->Dispatch measures job's own pack to dispatch, but not *why* S1 waited - appears as generic 1.1h).
* Misleading DFG conclusion: "Stage->Machine Process median 1.1h normal, so front-end fine" - actually J4's 1h55 FIX-A wait occurs *inside* that edge, invisible. Also "No job >1.8 SD" suggests no outlier, but synchronization wait is systemic across early jobs, not outlier.

**Machine-flattened:**
* Visible: Utilization per machine, typical sequence, gaps between *recorded* machine events.
* Hidden: Tool unavailability (FIX-A, RACK-7, CAL-3) counts as idle, not contention; lot holds; batch readiness waits (OVEN-1 idle 12:55-14:50 looks like spare capacity, not RACK-7 block). Counts interactions as 12 Job-Machine but not waiting time.
* Misleading: "OVEN-1 44% utilization, not bottleneck" while OVEN-1 is the *logical* bottleneck via batching rule despite low utilization. Longest gap 73m understates J1 3h55 wait because gap measured machine-event-to-machine-event, not readiness-to-batch-start.

**Batch-flattened (implied, not supplied):**
* Visible: If flattened on Batch, would show Load Batch -> Batch Cure -> Unload, waiting attributable to synchronization (J1/J2 3h+ wait visible as batch queue). Would show B1/B2 both use RACK-7.
* Hidden: Would duplicate Batch Cure across Jobs if aggregated incorrectly; would hide Job-specific upstream Lot or FIX-A causes that feed into batch readiness; shipment downstream not visible.
* Misleading: Frequency 2 suggests rare; but impact is 5 job participations. Performance metrics averaged across batches hide J4's distinct RACK-7 cause vs J1/J2's J3 arrival cause.

**Tool-flattened (FIX-A, RACK-7, CAL-3):**
* Visible: Acquire->Release lifecycles; queue length before tool; RACK-7 cleaning/quarantine  until 14:35; FIX-A hold 09:00-11:40 overlapping J4 arrival; CAL-3 recalibration blocking TEST-1.
* Hidden in other views: Completely absent from Job/Machine/Shipment summaries. System has no Wait for Tool activity, so contention is inferred, not recorded.
* Misleading if alone: Might attribute 42m CNC-2 idle solely to FIX-A without considering other prerequisites; might double-count tool time as job value-add.

**ComponentLot-flattened (L7/L8):**
* Visible: Quarantine 10:20 -> Release 13:50 on L7; fan-out to C2,C5 and transitively J2,J5; L8 never quarantined explains why J1/J3 not held.
* Hidden in Job flattening due to integration artifact: Events relate to Lot but not consistently to Job, so Job view shows zero lot delay. Job-ComponentLot 4 interactions understates duration.
* Misleading: If pipeline alternatively linked Lot events to Jobs, frequency of `Quarantine Lot` would appear duplicated twice per lot, inflating apparent rework loops. Direction confusion (Lot->Job vs Job->Lot) affects causal graph discovery.

**Shipment-flattened:**
* Visible: Create Shipment -> Load -> Dispatch per shipment, 3 shipments median 0.8h/0.3h looks lean.
* Hidden: Wait of early-packed job for late partner (J1 5h55) not measured because clock starts at Create Shipment; consolidation policy constraint invisible; upstream machine/batch/tool delays that propagate via shipment amplification hidden.
* Misleading: Concludes shipments not bottleneck because per-shipment time short, while S1 is *amplifier* that converts J4's upstream variance into J1's delivery delay.

**Why low machine utilization coexists with long job waiting:** Machines are *not* the pacing resource. Waiting is incurred in synchronization queues *before* machines (Batch formation waiting for last Job, Lot release waiting for QA) and in tool queues (FIX-A, RACK-7, CAL-3) and in post-processing holds (shipment consolidation) while machines sit idle feasible but not *executable* due to missing companion objects. Flattening counts *machine busy* as utilization, but *earliest feasible start* requires conjunction of Job + Component + Tool + Batch + Shipment readiness. Object-centric view reveals AND-join semantics; traditional views assume OR.

## 5. Object-lifecycle evidence

Narratives separate four evidentiary layers: **T** = temporal precedence (A before B), **F** = resource feasibility (B cannot occur without resource R), **P** = policy constraint (business rule requires pooling), **S** = causal speculation (unmeasured linking).

**Narrative 1: Lot quarantine -> split batches -> shipment cascade (L7 - C2/C5 - J2/J5 - B1/B2 - S1/S2/S3 - OVEN-1 - RACK-7)**

*Lifecycle trace:* L7 Quarantine 10:20 (L7,C2,C5,J2,J5)  J2 ready for B1 08:25 *before* quarantine but enters B1 via override  B1 Batch Cure 12:05 (B1,OVEN-1,RACK-7,J1,J2,J3)  J5 held until L7 Release 13:50  J5 ready 14:40  B2 start 14:50 (B2,OVEN-1,RACK-7,J4,J5)  J4 packed 19:10  S1 dispatch 19:25 (S1,J1,J4) holds J1 (packed 13:30) 5h55m  S3 dispatch after J5/J6.

* **T:** Quarantine 10:20 precedes Release 13:50 precedes J5 ready 14:40 precedes B2 start 14:50 precedes J4 pack 19:10 precedes S1 dispatch 19:25.
* **F:** B2 requires both J4+J5+ RACK-7 + OVEN-1; J5 cannot be staged until C5 released. S1 requires both J1+J4 packed.
* **P:** Lot QA policy quarantines entire L7 (both C2 and C5) even if jobs in different batches; supervisor override *policy exception* allowed J2 to bypass, creating differential fate. Batch policy requires B2 to wait for J5 (rather than dispatch single). Shipment policy consolidates J1+J4 regardless of pack time delta.
* **S:** We *speculate* L7 quarantine *caused* J5's 14:40 readiness delay (vs J5 would have been ready ~similar to J2 08:25 absent quarantine). We cannot prove J5's late readiness wasn't independent late stage completion. We also *speculate* B1's inclusion of J2 despite quarantine indicates policy inconsistency that *might* be patched, harming future J2. Transitive speculation: Lot -> Batch -> Shipment cascade is plausible coupling but not proven to be necessary - S1 could have shipped J1 alone under different policy.

**Narrative 2: Fixture contention propagates through batch and shipment (FIX-A - J3 - J4 - CNC-2 - B2 - S1)**

*Lifecycle trace:* J3 acquires FIX-A 09:00  J4 arrives CNC-2 09:50  CNC-2 idle 10:05-10:47  J3 releases FIX-A 11:40  J4 Machine Process 11:45 (J4,C4,CNC-2,FIX-A)  J4 ready for B2 13:10  RACK-7 unavailable until 14:35  B2 start 14:50  J4 pack 19:10  S1 dispatch 19:25 holding J1.

* **T:** FIX-A acquire 09:00 < J4 arrival 09:50 < CNC-2 idle start 10:05 < FIX-A release 11:40 < J4 start 11:45 < J4 ready 13:10 < S1 dispatch 19:25.
* **F:** CNC-2 operation for J4 requires FIX-A (evidence: J4's Machine Process event relates to both CNC-2 and FIX-A). CNC-2 idle proves machine feasible but tool infeasible 10:05-10:47.
* **P:** Single FIX-A inventory (no duplicate) dictates exclusive hold; no preemption.
* **S:** We infer the 42m CNC-2 idle *would* have been used for J4 if FIX-A free (resource feasibility suggests opportunity). We *speculate* the full 1h55 gap is FIX-A-driven, but 5m post-release delay (11:40-11:45) could be setup/transport. We also *speculate* that shortening J3's FIX-A hold (e.g., via SMED) would have shifted entire downstream chain earlier, reducing S1 hold less than 1:1 due to RACK-7 later block - partial mitigation.

**Narrative 3: Tool-batch-machine deadlock and calibration serialization (RACK-7/OVEN-1 - B1/B2 - CAL-3/TEST-1 - J5/J6 - S3)**

*Lifecycle trace:* B1 uses OVEN-1+RACK-7 12:05  OVEN-1 idle 12:55-14:50, RACK-7 cleaning/quarantine until 14:35  B2 start delayed to 14:50 despite J4 ready 13:10  J5 (already Lot-delayed) packs (?) then Final Test ready 16:00  J5 Final Test 16:10-16:35 with CAL-3 on TEST-1  CAL-3 recal 16:35-17:20  TEST-1 idle 16:35-17:25  J6 (ready 16:05) Final Test 17:25-17:50  S3 dispatch 35m after last pack (J6).

* **T:** B1 12:05 < RACK-7 free 14:35 < B2 14:50 < J5 ready 16:00 < J5 test 16:10-16:35 < CAL-3 recal 16:35-17:20 < J6 test 17:25.
* **F:** B2 cannot start without RACK-7 (same Rack as B1)  AND dependency; Final Test cannot start without both TEST-1 *and* CAL-3 (both idle not sufficient alone)  TEST-1 idle with CAL-3 busy is infeasible.
* **P:** Batch processing requires full rack load + cleaning protocol between batches (policy). Calibration policy requires recal after each Final Test (or periodic) blocking tool.
* **S:** We *speculate* B2 could have started earlier with alternative rack, decoupling batches. We *speculate* CAL-3 recal could be overlapped or deferred, allowing J6 to start at 16:35 and finish 17:00, advancing S3 dispatch ~50m. We cannot prove recal duration is reducible; may be fixed. ## 8. Falsification and additional data

**Observations that would weaken top-ranked explanation (Batch + RACK-7 synchronization as systemic coupling):**

1. B1 Batch Cure 12:05 occurred even though OVEN-1 had a scheduled maintenance window 08:30-12:00 that would have blocked any earlier batch regardless of J3 arrival — readiness irrelevant.
2. RACK-7 cleaning/quarantine 12:55-14:35 is actually *post_B1 cleaning* with fixed 2h duration logged as attribute, and OVEN-1 idle is due to that mandatory cure cooldown, not tool share — J4 delay is process physics, not contention.
3. Replicated data shows many other Batches with 3-job payloads dispatch within 20m of last-ready (no 3h tails) — B1 is outlier due to J3 late stage exception, not policy.
4. Readiness timestamps for J1 (08:10) and J2 (08:25) are system-generated at `Release Job` not true material staging — physical staging actually occurred at 11:50 and 11:55, eliminating synchronization wait.
5. J2 override record shows J2's C2 was *exempted* from quarantine and independently released at 08:20, proving L7 quarantine did not affect B1 composition — L7 coupling spurious.
6. Duplicate RACK-7B exists in master data but was not linked to B2 events due to logging error; actual B2 wait was for J5 readiness (J5 stage took until 14:40) not tool — tool bottleneck artifact.

Additional weakenings for overall coupling thesis: If FIX-A has 3 identical fixtures and J4's delay is traced to operator unavailability, or if S1's 5h55 hold is due to truck breakdown not policy, then cross-instance coupling overestimated.

**Additional fields / event types needed to discriminate hypotheses:**

1. **Explicit wait/queue events:** `Wait for Tool` (FIX-A queue entry/exit, RACK-7 request), `Wait for Batch` (Ready for Batch timestamp + Batch Assignment), `Wait for Shipment` (Pack Ready vs Shipment Assigned) — to replace inferred gaps.
2. **Resource state lifecycle for Tools & Machines:** Tool `Available/Busy/Calibration/Cleaning/Quarantine` state transitions as events linked to Tool (+Machine+Batch), with start/end timestamps, reason codes.
3. **Component genealogy & lot linkage completeness:** Mandatory `C contained in L` plus `L event linked to all C` plus derived `L event linked to J via requires` — to eliminate inconsistent Job-Lot linking; include lot exemption/override flag + approver.
4. **Batch policy attributes:** Batch `target size / min size / max wait / creation rule`, OVEN-1 `cure program + load plan`, RACK-7 `capacity + cleaning protocol duration` — to distinguish policy wait from resource wait.
5. **Shipment policy & logistics:** `Shipment creation time`, `Carrier assignment`, `Consolidation rule (must consolidate? latest dispatch deadline)`, `Pack -> Load -> Dispatch` timestamps per Job inside Shipment — to measure Pack-to-Dispatch per job correctly.
6. **Operator / shift / calendar data:** Operator availability, shift breaks, setup times for CNC-2/TEST-1 — to falsify machine-idle attribution vs tool.
7. **Alternative tool inventory & capability matrix:** Count of FIX-A, RACK-7, CAL-3 instances, compatibility per Job/Machine — to assess true contention vs single-instance assumption.
8. **Cost / quality trade-off fields:** Energy cost per OVEN-1 cycle, freight cost per shipment, lot quality test results — to evaluate intervention spillovers (batch splitting vs consolidation).

Without these, any ranking remains associational; with them, we can test AND-join feasibility vs policy choice via controlled flattening comparisons and isolate data-artifact vs operational bottleneck.
