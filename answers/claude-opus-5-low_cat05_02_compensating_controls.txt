## 1. Control-Objective Decomposition

FEP-1 ("preparer ≠ releaser, both human, both independent") is not one rule; it is a bundle of threat-specific objectives. Segregation of duties is the *mechanism*; the objectives below are what the mechanism is bought to achieve. A compensating package can only be assessed against the objectives, not against the mechanism.

**O1 — Unilateral fraudulent diversion.** One person creates a payment to an account they (or a related party) control and pushes it out without any second human ever looking. Threat: intentional, informed, adversarial.
- AV-2: *partially prevents* — catches sanctions hits, recent bank-account changes, duplicate invoices, limit breaches. Blind to a diversion account that was set up long ago and looks clean.
- MG-4: *prevents* if before release/settlement and the manager actually inspects invoice + bank detail + receipt; *detects only* if after settlement.
- RA-7: *detects*; *corrective only inside the ~24h recall window*.
- ED-1: does not address it; it only defines when the mechanism may be suspended, and its conditions (vendor age ≥180d, no recent bank change, AV-2 clean, independent MG-4) are precisely an attempt to re-cover O1 by other means.

**O2 — Unintentional error (wrong amount, wrong payee, duplicate, wrong currency).** No adversary; the second pair of eyes is a proofreading device.
- AV-2: *prevents* well — duplicates, limits, PO match are exactly this class. This is the objective where AV-2 is closest to a true equivalent.
- MG-4: *prevents* if pre-release, though a rubber stamp adds little.
- RA-7: *detects*, and error cases are the ones most likely to be genuinely recoverable (counterparty is a real vendor with no incentive to abscond) — so RA-7 is more corrective here than for O1.
- ED-1: not addressed directly.

**O3 — Fictitious / unperformed goods and services (fabricated receipt, phantom vendor engagement).** Payment is technically perfect; the underlying entitlement is fake.
- AV-2: *fails to address* — explicitly stated: a clean pass is not evidence goods were received. PO match only shows a PO exists.
- MG-4: *prevents only if* the manager reviews the supporting receipt against independent evidence (goods receipt, service report, requester confirmation); otherwise fails.
- RA-7: *detects* — AP-204 is exactly this, found by audit; correction depends entirely on vendor solvency and cooperation, not on the recall window.
- ED-1: not addressed.

**O4 — Collusion between two nominally distinct actors.** Four-eyes is satisfied in form and defeated in substance.
- AV-2: *fails to address* (stated explicitly).
- MG-4: *partially addresses* if the manager is outside the colluding unit and does substantive review; fails if the manager is inside the same reporting line or is the pair's own supervisor.
- RA-7: *detects*, and is the only control that can see *patterns* — repeated pairs, shared workstations, vendor concentration.
- ED-1: irrelevant (ED-1 governs single-operator cases; collusion is a two-operator failure).
This objective is why "distinct users" cannot be equated with OBJECTIVE_MET.

**O5 — Compromised or shared credentials / impersonation.** The log shows two identities; the keystrokes may come from one person. Includes override credentials issued to a manager but used by an operator.
- AV-2: *fails to address* — cannot establish who controlled an account.
- MG-4: *fails* when the manager's own credential is the one being borrowed (AP-202).
- RA-7: *detects* only with technical evidence (workstation/IP/session, authentication logs) that the event log alone does not carry.
- ED-1: not addressed. Note the shared-service-account clause of FEP-1 is a special case of O5: a non-human actor cannot be an independent second pair of eyes.

**O6 — Coercion / undue influence within a reporting line.** Formally distinct actors, but one cannot say no to the other.
- AV-2: fails to address. MG-4: *fails when the manager is the preparer's rating supervisor* — this is m09/u23 in AP-202. RA-7: detects only if independence metadata is analysed. ED-1: encodes this as the "no unresolved conflict of interest" condition.

**O7 — Control-degradation / outage exploitation.** Payments pushed through exactly when AV-2 is down, or with an override, or outside business hours.
- AV-2: by definition absent. MG-4: *can substitute* only if the manual checklist is actually performed and signed. RA-7: detects, and should be triggered automatically by outage. ED-1: condition 5 explicitly voids ED-1 eligibility in this state (AP-208).

**O8 — Recoverability erosion (timing objective).** Even a perfect detective control is worth little after settlement + 24h. Only RA-7 *within* the recall window, or MG-4 *before* settlement, preserves corrective capacity. This is a genuine objective in its own right: two packages with identical coverage but different timing are not equivalent.

## 2. Equivalence and Sufficiency Test

A compensating package P is evaluated against the objective set {O1…O8} weighted by the case's inherent risk. Seven dimensions, each scored **strong / partial / weak / absent**:

1. **Timing (T).** Strong = control completes before irrevocable settlement *and* before release; partial = after release, before settlement; weak = after settlement but inside the recall window; absent = after the recall window. Timing determines whether a control is preventive, salvageable, or purely informational.
2. **Independence (I).** Strong = actor is L3+, outside the preparer/releaser reporting line, no rating authority, no personal relationship; partial = independent on paper, same unit; weak = supervisor/subordinate of the actor being checked; absent = same person, or a shared/service account, or a borrowed credential.
3. **Coverage (C).** Which of O1–O8 the package actually touches. A package can be strong on O2 and empty on O3/O4 — AV-2 alone always is. Coverage is measured against the *risk profile of this payment*, not in the abstract: a EUR 1,800 office-supply payment barely loads O3, a EUR 480,000 new-vendor payment loads O1/O3/O5 heavily.
4. **Overrideability (V).** Can the party being controlled disable the control? A warning overridable by the operator (or by a credential the operator holds) is not a control against that operator — it is a logging feature. Strong = non-overridable block; weak = override possible by an independent L3+ with recorded justification; absent = self-override (AP-202).
5. **Recoverability (R).** Given the defect this package would fail to stop, is money still retrievable? Pre-settlement = full; <24h post-settlement = probable-but-uncertain; >24h with cooperative solvent vendor = partial; >24h with a diversion account = effectively nil.
6. **Evidence quality (E).** Is there a durable, attributable artefact that a third party could re-perform? A `Manager_Ratify` event with no record of *what was reviewed* is weak evidence of review. An unsigned manual checklist (AP-208) is no evidence. Strong evidence names the documents inspected and is timestamped independently of the actor.
7. **Collusion resistance (K).** Does the package add an actor with a *different incentive structure and a different reporting line*? Two operators in one cell add none. Automated controls add K only for the checks they cover.

**Classification rule.**
- **Fully equivalent** — the package attains strong or partial on *every* objective that the original four-eyes control would have covered for this risk profile, with T ≥ partial, I strong, V strong, and K ≥ partial. In practice this is rare: no combination of AV-2 + MG-4 + RA-7 covers O3 and O4 as well as a genuinely independent, substantively engaged second releaser does — but a *pre-release, evidence-based, independent MG-4* comes closest, because it is literally a second human authorizer, merely one who is not the button-presser.
- **Partially equivalent** — the residual gap is confined to objectives with low loading for this case, and corrective capacity is preserved (T ≥ weak with R ≥ probable). Nonconforming in form, tolerable in substance.
- **Merely mitigating** — the package reduces expected loss but leaves a primary objective for this risk profile uncovered, or corrective capacity is already gone at the moment the control acts. Detection without recoverability sits here.
- **Ineffective** — the package is overrideable by the controlled party, or the "independent" actor is not independent, or the controls that fired do not touch any high-loading objective.

**Why "same expected loss" is not the only standard.** Expected loss is a scalar; internal control is not a scalar objective.
- *Variance and tail.* A package that swaps many small errors for a small chance of a catastrophic unrecoverable diversion may hold expected loss constant while destroying the tail properties the control existed to protect (AP-208: one payment, EUR 900,000, no bank-ownership evidence).
- *Recoverability is not fungible with prevention.* EUR 100k lost and recovered is not the same event as EUR 100k never lost: it consumes investigation cost, damages counterparty relationships, and depends on luck.
- *Deterrence and process integrity.* Controls have an ex-ante behavioural effect. Tolerating same-user release "because AV-2 passes" changes what operators attempt next month; expected-loss accounting on a per-case basis cannot see this.
- *Assurance and evidence.* Regulators, auditors, and insurers require demonstrable design and operating effectiveness. A case with zero loss but no reconstructable evidence (AP-208) is a control failure even with realised loss of zero.
- *Epistemic status.* Expected loss requires a probability model. Where the key facts are unknown (was the credential shared? is u12/u13 a designed cell?), the honest output is INDETERMINATE, not a point estimate.
- *Correlated exposure.* Per-case expected loss ignores that the same weak package is being applied across a population; AP-204/AP-209 matter jointly, not severally.

**Is manager action after Release_Payment but before Bank_Settlement preventive, detective, or hybrid?**

I classify it as **hybrid, with preventive weight proportional to the reliability of the stop mechanism**, and I state the semantics explicitly because the answer depends on where one locates "the loss event."

Two defensible semantics exist:
- *Release-anchored:* the loss occurs when the authorising human act completes, because the payment then leaves the actor's control and enters an automated pipeline. Under this reading, anything after `Release_Payment` is detective.
- *Settlement-anchored:* the loss occurs when funds become irrevocable. Under this reading, review before `Bank_Settlement` is preventive, because the defect can still be stopped at zero cost.

I adopt a **settlement-anchored primary semantics with a release-anchored qualifier**, for three reasons. First, the case material itself treats settlement as the irrevocability boundary ("normally irrevocable for internal control purposes") and MG-4 is described as "strongest when performed before release *or* before irrevocable bank settlement" — the standard explicitly admits both. Second, economically, a payment stopped in the settlement queue causes no loss, and a control that reliably produces that result is doing preventive work. Third, treating it as purely detective would erase the material difference between AP-207 (m15 at 14:40, settlement 16:00 — a defect would have been stopped) and AP-208 (m21 a day after settlement — a defect could only have been reported).

The qualifier matters, though, and is why I do not call it fully preventive:
1. The stop mechanism is *conditional*. It requires that an in-flight payment can actually be pulled, that the manager knows how, and that the operations calendar (cut-off times, weekends, cross-border rails) cooperates. None of that is evidenced in this log. Preventive controls should not depend on an untested escalation path.
2. There is an **uncovered window** — 35 minutes in AP-207, 24 minutes in AP-201 — in which the payment is authorised with no second human having looked. If the pipeline had settled faster, the control would have missed entirely. A control whose effectiveness depends on infrastructure latency is not a designed preventive control.
3. The manager's *posture* differs. Reviewing before release is authorisation; reviewing after release is ratification, and ratification carries a documented psychological bias toward confirming a decision already taken. AP-201's `Manager_Ratify` is literally named for this.

Practical scoring rule I apply in Section 3: MG-4 before release = preventive, full credit; MG-4 after release but before settlement = hybrid, roughly the credit of a preventive control discounted for the uncovered window and the untested stop path — enough to support OBJECTIVE_PARTIALLY_MET but not OBJECTIVE_MET; MG-4 after settlement = detective, and it cannot lift a case above PARTIALLY_MET on its own. The event-name distinction in this log (`Manager_Approve` in AP-203/AP-206 vs. `Manager_Ratify` in AP-201/AP-207/AP-202/AP-208) tracks this boundary neatly, and it is not a coincidence that the two `Manager_Approve` cases are the two strongest same-user packages.

## 5. Counterfactual and Residual-Risk Analysis

Probabilities below are qualitative bands (negligible / low / moderate / high). Where a number appears it is labelled **illustrative** and is not derived from data in this log.

**AP-202 — EUR 480,000, self-override, supervisor ratification.**
*Most plausible loss mechanism:* a diversion payment to a related-party account, either originated by u23 or by an external party controlling u23's session, enabled by an override credential that the operator should never have possessed. The bank change two hours before preparation is the classic signature: the payee record was mutated immediately before use, which is why AV-2 flagged it.
*Which control breaks the chain:* the AV-2 warning did break it — for about sixty seconds. The chain was re-welded by the override. The single change that would have prevented this loss is making the bank-change warning non-overrideable by the releasing operator and routing it to an independent L3+ for disposition. Secondarily, RA-7 inside 24 hours would have hit the recall window; at +8 days recovery was hopeless.
*What remains exposed:* everything. Funds are gone. The credential-control question is unresolved, so we cannot say whether the residual exposure is one rogue operator or a systemic credential-sharing practice — the latter would implicate every payment m09's org has released.
*Under a truly independent second releaser:* high probability of prevention. An independent releaser confronted with a bank-change warning on a new vendor for EUR 480k with no receipt would very likely have stopped — unless the releaser were also colluding or were m09 themselves, which is precisely the configuration the override credential simulated. **Illustrative:** if an independent releaser stops such a payment 80–90% of the time, expected loss drops from ~EUR 480k to ~EUR 50–100k; this figure is for ordering priorities only.

**AP-204 — EUR 220,000, fabricated receipt, formally compliant.**
*Most plausible loss mechanism:* either (a) collusion between u12 and u13 to pay a fictitious or inflated consulting engagement, or (b) a single actor operating both credentials from a shared workstation, or (c) both operators being honest and both being deceived by a receipt fabricated upstream by a requester. These three have very different remediations and the log cannot separate them.
*Which control breaks the chain:* none of the deployed controls could — AV-2 is explicitly blind to service delivery, and there was no MG-4 at all. The chain is broken only by an independent confirmation of service delivery from the *requesting* function (a goods-receipt or service-acceptance step by someone with no payment role), or by MG-4 with a mandatory receipt-to-source check. RA-7 detected it, four days late.
*What remains exposed:* recovery from a consulting vendor at +4 days is uncertain and slow. More importantly, 37 joint approvals in 30 days are unexamined — the exposure is a population, not a case.
*Under a truly independent second releaser:* **little change.** This is the key asymmetry. A releaser drawn from outside the pair would still have been shown a plausible-looking fabricated receipt and would still have released. Segregation of duties is weak against O3; only a delivery-confirmation control from a different function is strong against it. Prevention probability under an independent releaser: low-to-moderate.

**AP-208 — EUR 900,000, AV-2 outage, everything late.**
*Most plausible loss mechanism:* business-email-compromise / vendor-impersonation. An 8-month-old vendor whose bank details changed three days earlier, a very large amount, urgency, and the one control that checks bank-account changes conveniently unavailable. Whether or not this particular payment was legitimate, the control state was indistinguishable from a successful BEC.
*Which control breaks the chain:* a hard rule — no release above a threshold while AV-2 is unavailable — is the only reliable break. Second best: a mandatory out-of-band callback to a vendor contact from a pre-outage record, signed, before release. Third: independent MG-4 before settlement, which was available in wall-clock terms (settlement was two hours after Prepare) and was simply not obtained.
*What remains exposed:* the payment cannot be *retrospectively* validated — there is no bank-ownership evidence for the release moment, and confirming today that the vendor received it does not establish that the account was the vendor's at 15:04. This is an unclosable evidence gap, which is exactly why the case is FAILED despite a benign outcome.
*Under a truly independent second releaser:* moderate improvement, not sufficient. A second human might have balked at the bank change, but with AV-2 down neither human had the *means* to verify ownership. This case shows that four-eyes and automated validation are complements, not substitutes: removing one degrades the other.

**AP-203 — EUR 75,000, emergency, pre-release independent approval.**
*Most plausible loss mechanism:* under a same-user emergency release, the generic risk is that u31 pays an account they control under cover of urgency, or that urgency is manufactured to bypass review.
*Which control breaks the chain:* m02's pre-release review of invoice, bank account and service report — it substitutes a genuine independent human judgement for the missing second releaser, and does so with better coverage than a typical releaser would (a service report addresses O3, which most releasers never check). AV-2 covers O2 and the bank-change vector. The pre-existing token addresses manufactured urgency.
*What remains exposed:* O5 only — nothing establishes that u31 personally operated the session; and m02's review is only as good as its (undocumented) depth. Residual: low.
*Under a truly independent second releaser:* essentially no change, and arguably a *downgrade* — a second operator would likely have checked less than an L3+ manager reviewing three source documents. This is the strongest evidence that a compensating package can be substantively equivalent, and that mechanical FEP-1 counting would misclassify it.

**AP-201 — EUR 1,800, same user, no emergency basis.**
*Most plausible loss mechanism:* low-value repeat diversion, or a habituated same-user workflow that later gets applied to a material payment. The per-case loss mechanism is nearly inert; the *process* mechanism is not.
*Which control breaks the chain:* m04's pre-settlement review, plus AV-2. Both worked.
*What remains exposed:* control drift. A same-user release with no emergency token and no ED-1 basis, tolerated because it was small, is how the AP-208 pattern becomes normal. RA-7 at +25 hours also shows the audit SLA is not being met even in easy cases.
*Under a truly independent second releaser:* negligible change in expected loss for this payment; meaningful change in the population, because the option of same-user release would not exist. This case is where the "expected loss is not the only standard" argument does real work.

**AP-206 — EUR 95,000, late token, otherwise clean.**
*Most plausible loss mechanism:* retrofitted emergency justification — an operator prepares a payment they want to push through alone, then obtains a token to legitimise it. The generic risk is not this payment but the precedent.
*Which control breaks the chain:* m11's independent pre-release approval fully covers the substantive risk; the token ordering is a governance control against *future* retrofit, not against this payment's loss.
*What remains exposed:* only the integrity of the ED-1 gate. If two-minute retrofits are tolerated, the gate stops constraining anything.
*Under a truly independent second releaser:* no change in loss; the emergency route would simply not have been used.

**AP-209 — EUR 42,000, the impeached pair.**
*Most plausible loss mechanism:* the AP-204 mechanism repeated and not yet detected — a fabricated or inflated entitlement passing a non-independent pair.
*Which control breaks the chain:* nothing deployed. AV-2 is blind to O3; the pair is the thing in question; RA-7 was timely but found nothing, which under a collusion hypothesis is weak negative evidence unless the audit specifically re-performed delivery confirmation.
*What remains exposed:* unknown magnitude — this is one of 37+ joint approvals.
*Under a truly independent second releaser:* moderate improvement if the concern is O4/O5; little if the concern is O3. The right remediation is rotation of the pairing *plus* independent delivery confirmation, not either alone.

## 6. Evidence and Monitoring Recommendations

**Evidence to collect at source (the log as given cannot support several of the judgements above).**
1. **Review artefacts, not review events.** Every `Manager_Approve` / `Manager_Ratify` must record which documents were opened (invoice ID, bank record version and its last-change timestamp, goods-receipt/service-report ID) and an explicit attestation. Without this, MG-4 is unfalsifiable and rubber-stamping is invisible. This alone would resolve AP-201, AP-206 and AP-207.
2. **Actor attributes at event time**: level (L3+ or not), reporting line, rating relationship to the preparer/releaser, and declared conflicts — snapshotted at the event, not looked up later.
3. **Session and device telemetry** joined to the case: workstation ID, IP, authentication method, MFA assertion, session start. This is the only way to address O5 and the u12/u13 question.
4. **Credential provenance for overrides**: which credential was used, to whom it is issued, whether the human presenter was the assignee. AP-202 is invisible without this.
5. **Vendor master change history**: bank-account change timestamp, changing actor, and the evidence supporting the change (callback record). Bank-change proximity is only meaningful with the change actor attached.
6. **Emergency token lifecycle**: request time, approver, activation time, justification reference, and linkage to an independent incident ticket with its own timestamp.
7. **Control-availability telemetry**: AV-2 uptime as a first-class event stream, so outages are known independently of whether someone logged `Validation_Service_Unavailable`.
8. **Settlement and recall timestamps**, including the actual recall cut-off per payment rail — recoverability windows are rail-specific, and "24 hours" is a planning assumption, not a fact.

**Monitoring rules.** Each is an *alert* with a threshold, an owner, and a defined response.

| Metric | Rule | Rationale | Response |
|---|---|---|---|
| **Same-user release rate** | Per operator and per unit, weekly. Alert if >2% of releases, or any same-user release without a pre-existing emergency token, or any above EUR 100,000 | ED-1 is a narrow permission; a rising rate means it is being used as a workflow | Confirm ED-1 conditions case by case; revoke standing capability if unsupported |
| **AV-2 override rate** | Per operator, per override-credential holder, and per warning type. Alert on any override where the presenter ≠ credential assignee; alert on any operator self-override; alert on override rate >5% or any override on a bank-change warning | Overrideability is the dimension that collapsed in AP-202 | Immediate: block release pending independent L3+ disposition |
| **Late manager approval** | Alert when MG-4 occurs after `Release_Payment`; escalate when after `Bank_Settlement`; report the release→approval interval distribution | Distinguishes preventive from hybrid from detective; the uncovered window is the exposure | Post-settlement ratification triggers mandatory same-day RA-7 |
| **Audit-before-recall-window** | Alert when `Audit_Review` starts >24h after settlement for any same-user, override, outage, or bank-change-proximate payment. Track the share of emergency payments audited within one business day against the 100% target | Detective controls without recoverability are a different (weaker) control; AP-201 at +25h shows the SLA slipping even on easy cases | Re-prioritise the audit queue by recoverability deadline, not by amount |
| **Repeated resource pairs** | Concentration index of (preparer, releaser) pairs per unit. Alert if any pair exceeds ~30% of a unit's volume, or on absolute counts like 37 in 30 days; require documented rotation | Four-eyes value decays toward zero as pairing becomes fixed; this is the AP-204/AP-209 signal | Mandatory rotation; re-perform a sample of the pair's prior approvals |
| **Shared workstation / session** | Alert when Prepare and Release for one case share a device ID, IP, or overlapping session, or when the release follows the preparation within a physically implausible interval on the same device | Directly tests O5; converts a suspicion into a technical finding | Immediate re-performance of the payment; access review |
| **Bank-change proximity** | Hard rule, not an alert: no release within 7 days of a payee bank-account change without independent out-of-band callback verification recorded by someone with no payment role. Alert on any exception | Highest-yield single signal for diversion fraud; present in AP-202 and AP-208 | Block, not warn |
| **Control outage exposure** | Alert on every release while AV-2 is unavailable; hard-block above a threshold (suggest EUR 50,000); require a signed manual checklist with named checks; auto-flag all outage-window payments for 100% RA-7 within 24 hours | AP-208's entire failure is an outage exploited without substitution | Retrospective 100% review of the outage window |
| **Emergency-token ordering** | Alert whenever token activation timestamp ≥ Prepare timestamp, including small gaps; correlate against independent incident-ticket times and clock-skew records | Detects retrofitted justification (AP-206) while allowing for logging latency | Governance review, not enforcement action, unless a pattern emerges |
| **Composite risk trigger** | Any two of: same-user, override, AV-2 outage, bank change <7 days, new vendor <180 days, amount >EUR 100,000 → mandatory pre-settlement independent MG-4 and 24h RA-7 | Single-factor rules missed AP-208, which was flagged on four factors simultaneously | Automatic hold |

**An alert is not proof of misconduct — and this distinction must be built into the process, not merely stated.**
- These metrics measure *control state*, not *intent*. A repeated resource pair may be a documented two-person payment cell in a small subsidiary with no alternative staffing; a shared workstation may be a shared-office reality; a late token may be clock skew; a self-override may be a credential-provisioning defect by IT rather than an operator's act. In every one of these, the control finding stands and the misconduct finding does not follow.
- Consequently: alerts route to a **control-remediation** workstream by default, and cross into an investigative workstream only on defined escalation criteria (confirmed fabricated evidence, related-party linkage, credential misuse by the assignee's knowledge, or a pattern surviving an innocent-explanation review).
- Findings should be phrased as control statements — "the bank-account-change warning was overridden by the releasing operator using a credential assigned to their supervisor; independence of authorisation could not be established" — not as conclusions about persons. In AP-202 I record a control failure and an unresolved credential question; I do not record that u23 committed fraud or that m09 shared a credential, because the evidence does not support either.
- Individuals named in alerts should have a documented opportunity to explain before any adverse inference, and the absence of an explanation should not itself be treated as evidence.
- Aggregate alert rates should be reported to management as *process health*; individual-level alerts should be access-restricted, retained on a defined schedule, and not used for performance evaluation, or the reporting incentives will corrupt the underlying data.

def _same_actor_cases(frame):

    out = set()

        rel = set(grp.loc[grp["concept:name"] == FOUR_EYES_A2, "org:resource"])
        if prep & rel:
            out.add(cid)
    return out

def _first_ts(cid, activities):
    g = df[(df["case:concept:name"] == cid) & (df["concept:name"].isin(activities))]
    return g["time:timestamp"].min() if len(g) else pd.NaT

    if pd.isna(a) or pd.isna(b):
        return None
    return (a - b).total_seconds() / 3600.0

#    post-release/pre-settlement = hybrid, post-settlement = detective)
def _mgr_timing(r):
    if pd.isna(r["t_manager"]):
        return "NO_MANAGER_ACTION"
    if pd.notna(r["t_release"]) and r["t_manager"] < r["t_release"]:
        return "BEFORE_RELEASE_preventive"
    if pd.notna(r["t_settlement"]) and r["t_manager"] < r["t_settlement"]:
        return "AFTER_RELEASE_BEFORE_SETTLEMENT_hybrid"
    if pd.isna(r["t_settlement"]):
        return "AFTER_RELEASE_SETTLEMENT_UNKNOWN"
    return "AFTER_SETTLEMENT_detective"

def _audit_gap(r):

    return _hours(r["t_audit"], anchor)

# -- ED-1 eligibility, condition by condition
def _ed1(r):
    if not r["nominal_four_eyes_violation"]:
        return "N/A_no_single_operator_release"
    fails = []
    if not bool(r["emergency_token"]):
        fails.append("1:no_token")
    elif not bool(r["token_before_prepare"]):
        fails.append("1:token_after_prepare")
    if pd.notna(r["amount_eur"]) and r["amount_eur"] >= 100000:
        fails.append("2:amount>=100k")
    if pd.notna(r["vendor_active_days"]) and r["vendor_active_days"] < 180:
        fails.append("3:vendor<180d")
    if r["flag_bank_change_within_7d"]:
        fails.append("4:bank_change<=7d")
    if r["av2_result"] != "pass":
        fails.append("5:av2_not_clean")
    if r["flag_manager_timing"] in ("NO_MANAGER_ACTION", "AFTER_SETTLEMENT_detective"):
        fails.append("6:no_independent_approval_before_settlement")
    elif r["manager_independent"] is False:
        fails.append("6:manager_not_independent")
    if r["flag_audit_outside_recall_window"] or bool(r["flag_no_audit"]):
        fails.append("7:audit_late_or_missing")
    return "ELIGIBLE" if not fails else "NOT_ELIGIBLE(" + ";".join(fails) + ")"

ev["flag_ed1_eligibility"] = ev.apply(_ed1, axis=1)

# -- repeated (preparer, releaser) pairs across the population
pairs = []
for cid, g in df.groupby("case:concept:name"):
    p = g.loc[g["concept:name"] == FOUR_EYES_A1, "org:resource"]
    r = g.loc[g["concept:name"] == FOUR_EYES_A2, "org:resource"]
    if len(p) and len(r):
        pairs.append((cid, f"{p.iloc[0]}->{r.iloc[0]}"))
pair_df = pd.DataFrame(pairs, columns=["case", "pair"])
counts = pair_df["pair"].value_counts()
pair_df["pair_count_in_extract"] = pair_df["pair"].map(counts)
ev = ev.merge(pair_df, on="case", how="left")
ev["flag_repeated_distinct_pair"] = (
    (ev["pair_count_in_extract"].fillna(0) > 1)
    & (~ev["nominal_four_eyes_violation"])
)

**PM4Py behaviour that cannot be guaranteed across versions**

1. `pm4py.filter_four_eyes_principle` has moved between namespaces (it originated as `pm4py.algo.filtering.log.ltl.ltl_checker.four_eyes_principle` and was promoted to the simplified `pm4py.*` API), and its keyword arguments have varied — some releases expose a `positive`/`retain` parameter whose default determines whether the *violating* or the *conforming* cases are returned. The script therefore computes the same property in pandas, prints both, and warns on divergence rather than silently trusting either. It also degrades gracefully if the call raises.
2. `pm4py.format_dataframe` adds internal helper columns (`@@index`, `@@case_index`, and similar) and may normalise or re-cast the timestamp column; it may also drop or rename columns it does not recognise. The script re-attaches `org:resource` defensively and performs all timing arithmetic on the original `df`, so results do not depend on which helper columns a given release creates.
3. The LTL-family filters generally assume the standard XES keys (`case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`); some versions accept explicit key parameters and some read them from a parameters dict. Feeding a DataFrame that has already passed through `format_dataframe` is the most portable option, which is what the script does.
4. Return type follows input type in recent versions (DataFrame in → DataFrame out), but older releases coerce to an `EventLog` object, for which `["case:concept:name"]` indexing would fail. This is caught by the `try/except`.
5. Timezone handling: `pd.to_datetime(..., utc=True)` is applied before `format_dataframe` so all comparisons are unambiguous. Some PM4Py versions localise naive timestamps to the machine's zone, which would corrupt the 24-hour window arithmetic; parsing as UTC up front avoids it.
6. Nothing in the script depends on process-discovery or conformance-checking algorithms, whose outputs are the least stable across versions. The only PM4Py surface used is one filter and one formatter, both cross-checked or defensively wrapped.
