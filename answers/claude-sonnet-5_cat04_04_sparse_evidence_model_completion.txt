**On bidirectional DFG edges (Credit Check  Engineering Review, Supplier Confirmation  Engineering Review):**
The DFG shows CCER (17) and ERCC (11), and SCER (2) and ERSC (13). A bidirectional edge pair in a *directly-follows* graph built from completion timestamps is consistent with **at least three** distinct generative processes: (a) true concurrency where the faster activity is logged first (S2); (b) genuine case-dependent sequential branching (an XOR of two fixed orders, chosen by an unlogged attribute, consistent with S1 partially applying); (c) an artifact of coarse timestamp granularity plus ingestion-index tie-breaking (S7), which can make truly sequential-but-close events appear in either order. The DFG alone cannot discriminate between these; this is exactly what D7 asserts, and it is the reason three candidate models — not one — are warranted.

# 2. Shared Assumptions

All three models share the following premises, applied uniformly so that differences between candidates are attributable to modeling stance, not inconsistent bookkeeping:

1. **Event semantics.** Every event is a *completion* event (S7). No model claims to represent start times, durations, or true overlap; "concurrency" in the balanced/permissive models is a **control-flow abstraction** representing "no enforced order," not a claim about wall-clock overlap.
2. **Fixed skeleton.** `Register Order` is always first, `Archive Case` is always last (D1), and `Approve Configuration  Release Production  Archive Case` is a fixed, unconditional suffix (100% support in the DFG, D2). All three models hard-code this.
3. **Supplier Confirmation optionality is a merged abstraction.** We cannot separate "legitimately skipped because stocked" (S4) from "should have occurred but was not logged due to integration defect" (S5) — the attribute that would disambiguate this (external/stocked flag) was not exported. All models represent SC as `XOR(SupplierConfirmation, skip)` and this ambiguity is **explicitly not resolved** by the model; it is a known limitation carried into §9's data-collection plan.
4. **Optionality representation.** Optional activities (Supplier Confirmation, Expedite Review) are represented as an XOR between the visible activity and a silent transition (), i.e., the standard "skip" pattern, in both ProcessTree and POWL encodings.
5. **No claim of causal proof.** Nothing in the observed completion order is treated as proof of resource concurrency, business rule enforcement, or causal precedence beyond what D1–D6 already assert at various confidence levels.
6. **Finite, loop-free language.** None of the three candidates contain loops (no activity is known to repeat), consistent with all 30 traces having each activity at most once. This keeps all three languages finite (though combinatorially large for the permissive model), which matters for §8's playout limitations.

# 3. Conservative Candidate

**Inductive bias.** The conservative model encodes a strong preference for *precision over generalization*: it treats the 7 observed variants as the entire admissible language and refuses to interpolate or extrapolate beyond them, even where domain rules (D3, D5, D6) would justify a modest generalization. This is a deliberate "memorization" bias — appropriate when the cost of admitting an unsupported trace (e.g., in a compliance audit) outweighs the cost of rejecting a slightly-different but legitimate future trace.

**Compact formal expression.**

```
model_conservative = XOR(
  SEQ(RO,CC,ER,SC,AC,RP,AR),          # 12
  SEQ(RO,ER,CC,SC,AC,RP,AR),          # 7
  SEQ(RO,CC,ER,AC,RP,AR),             # 4
  SEQ(RO,ER,CC,AC,RP,AR),             # 3
  SEQ(RO,CC,SC,ER,AC,RP,AR),          # 2
  SEQ(RO,CC,ER,SC,EX,AC,RP,AR),       # 1
  SEQ(RO,ER,CC,EX,SC,AC,RP,AR)        # 1
)
```

**PM4Py code.**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO, CC, ER = "Register Order", "Credit Check", "Engineering Review"
SC, EX, AC = "Supplier Confirmation", "Expedite Review", "Approve Configuration"
RP, AR = "Release Production", "Archive Case"

def leaf(label):
    return ProcessTree(label=label)

def op(operator, children):
    node = ProcessTree(operator=operator)
    for c in children:
        c.parent = node
    node.children = children
    return node

def make_seq(labels):
    return op(Operator.SEQUENCE, [leaf(l) for l in labels])

observed_variants = [
    [RO, CC, ER, SC, AC, RP, AR],
    [RO, ER, CC, SC, AC, RP, AR],
    [RO, CC, ER, AC, RP, AR],
    [RO, ER, CC, AC, RP, AR],
    [RO, CC, SC, ER, AC, RP, AR],
    [RO, CC, ER, SC, EX, AC, RP, AR],
    [RO, ER, CC, EX, SC, AC, RP, AR],
]

model_conservative = op(Operator.XOR, [make_seq(v) for v in observed_variants])
```

**Deliberately excluded behavior.**
- Any 8th interleaving of CC/ER/SC/EX not literally observed (e.g., EX with SC-before-EX in the ER-first order).
- Any repositioning of SC relative to CC/ER other than the three positions actually seen.
- Any co-occurrence of "no SC" with "EX present" (never observed together).

**Known underfitting risks.**
- Zero tolerance for benign timestamp-tie reordering (S7): a future case that is operationally identical to V1 but happens to log CC/ER in swapped completion order due to a tie-break artifact would be rejected outright.
- No resilience to the 5–10% missing-SC integration defect (S5): if SC silently drops from the *dominant* variant in a way that doesn't already coincide with V3/V4, fitness collapses for that case even though nothing changed operationally.
- Cannot represent "same combinatorial family, unseen combination" (e.g., CC,ER,SC,EX with a different but equally plausible internal order) — this is the model's core design intent, but it is also its main risk if the true process has more legitimate variability than 30 cases happened to reveal.

**Duplicate labels & scalability.** Within each branch, no label repeats (each activity occurs at most once per variant), so this is not the "duplicate label" pathology associated with loops or repeated tasks in process-tree/Petri-net conversion. However, the *same* labels are re-instantiated as separate leaves across the seven mutually exclusive branches — this is standard and safe for XOR-of-sequences, but it means model size grows **linearly with the number of distinct observed variants**, with zero compression of shared sub-structure (the CC/ER/SC/EX combinatorics are not factored out). If the true process has, say, 24 legitimate combinations (2 CC/ER orders × 2 SC-presence × 2 EX-presence × ~3 EX positions) but only 7 have been observed, this encoding does not "know" that; adding an 8th observed variant requires manually adding a branch, and in the worst case the enumeration approach scales combinatorially rather than compositionally. This is the crux of the conservative model's inductive bias: correctness by enumeration, at the cost of any compositional generalization.

# 4. Balanced Candidate

**Inductive bias.** The balanced model encodes the most defensible middle ground: it takes D3/D4/D6 as structural constraints (hard edges into `Approve Configuration`), treats the CC/ER ordering ambiguity as genuine concurrency per S2 (the majority reading of the bidirectional DFG edges, tempered by D7's caveat), and approximates D5's OR-dependency for Supplier Confirmation using an XOR over two alternative partial orders rather than either (a) ignoring the constraint (full independence) or (b) over-constraining it (AND-join requiring both CC and ER). This is the candidate meant for everyday use precisely because every relaxation beyond the conservative model is tied to a *named* piece of evidence.

**How sequence / concurrency / partial order were decided:**

| Pair | Evidence | Decision |
|---|---|---|
| Credit Check, Engineering Review | S2 (expert claim of parallelism) + symmetric-ish DFG frequencies (17 vs 11) + D7 (cannot be disproven or proven) | **Concurrent** (no edge either direction) — the least assumption-laden reading of a genuinely bidirectional, high-volume DFG pair |
| Supplier Confirmation vs. {CC, ER} | D5 (needs *one*, not both) + OV-EarlySC (CC-only-then-SC observed) + OV-Dominant/OV-Swap (ER-only implicitly satisfied since CC also done) | **OR-dependency**, approximated as **XOR of two partial orders** (branch A: CCSC; branch B: ERSC), since native partial-order semantics only support AND-joins |
| Expedite Review vs. {CC, ER} | D6 ("requires completion of both") — this is a stated AND requirement, unlike SC's OR requirement | **Partial order AND-join**: edges CCEX and EREX in both branches |
| Expedite Review vs. Supplier Confirmation | D6/S6 ("before or after SC") | **Concurrent** (no edge either direction) |

**Compact formal expression.**

```
CoreBlock = XOR( PO_A , PO_B )

PO_A: nodes {CC, ER, SC_opt, EX_opt}
      edges: CCSC_opt, CCEX_opt, EREX_opt
      (no edge CC–ER, no edge SC_opt–EX_opt)

PO_B: nodes {CC, ER, SC_opt, EX_opt}
      edges: ERSC_opt, CCEX_opt, EREX_opt

model_balanced = PO( RO  CoreBlock  AC  RP  AR )
```

**PM4Py (POWL) code.**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

RO, CC, ER = "Register Order", "Credit Check", "Engineering Review"
SC, EX, AC = "Supplier Confirmation", "Expedite Review", "Approve Configuration"
RP, AR = "Release Production", "Archive Case"

def opt(label):
    """Optional-activity pattern: XOR(activity, skip)."""
    return OperatorPOWL(Operator.XOR, [Transition(label=label), SilentTransition()])

def build_branch(sc_predecessor_label):
    cc, er = Transition(label=CC), Transition(label=ER)
    sc_opt, exp_opt = opt(SC), opt(EX)
    po = StrictPartialOrder(nodes=[cc, er, sc_opt, exp_opt])
    if sc_predecessor_label == CC:
        po.order.add_edge(cc, sc_opt)
    else:
        po.order.add_edge(er, sc_opt)
    po.order.add_edge(cc, exp_opt)
    po.order.add_edge(er, exp_opt)
    return po

po_a = build_branch(CC)   # SC depends on Credit Check
po_b = build_branch(ER)   # SC depends on Engineering Review

core_block = OperatorPOWL(Operator.XOR, [po_a, po_b])

ro = Transition(label=RO)
ac = Transition(label=AC)
rp = Transition(label=RP)
ar = Transition(label=AR)

top = StrictPartialOrder(nodes=[ro, core_block, ac, rp, ar])
top.order.add_edge(ro, core_block)
top.order.add_edge(core_block, ac)
top.order.add_edge(ac, rp)
top.order.add_edge(rp, ar)

model_balanced = top
```

*(Note: constructor signatures for `StrictPartialOrder`/`OperatorPOWL` may vary slightly across PM4Py versions; the structure above follows the documented pattern in the prompt's API reminders and is intended to be illustrative of the intended semantics, not a guarantee of byte-for-byte API compatibility.)*

**Deliberately excluded behavior.**
- Expedite Review occurring before both CC and ER complete (violates D6's AND-requirement in both branches).
- Supplier Confirmation depending on *neither* CC nor ER (the OR-join is exclusive-XOR over two AND-branches, so at least one always gates SC).
- More than one Expedite Review occurrence (no loop construct used).

**Known underfitting / overfitting balance risks.**
- The XOR-of-two-branches approximation of an OR-join is a **known simplification**: real business logic might allow SC to be gated by "CC or ER, whichever legitimately finishes first, decided dynamically," which is not exactly representable as a static XOR chosen once per case — this is disclosed as an abstraction, not a proven mechanism.
- The full concurrency assumption for CC/ER rests on S2 (an expert claim), which is contradicted by S1 (another expert claim); see §10 for the alternative interpretation this creates.

# 5. Permissive Candidate

**Inductive bias.** The permissive model maximizes admitted behavior subject only to the high/medium-confidence structural anchors (D1–D4, and the tail-end AND-join at Approve Configuration), while relaxing the *internal* dependency structure among Credit Check, Engineering Review, Supplier Confirmation, and Expedite Review to full concurrency. This is appropriate for exploratory analysis (capacity simulation, discovering blind spots, stress-testing downstream systems) but is explicitly **not** recommended for compliance use, because it knowingly loosens D5 and D6 beyond what any piece of evidence directly supports.

**Compact formal expression.**

```
model_permissive =
  SEQ( RO,
       PARALLEL( CC, ER, XOR(SC, ), XOR(EX, ) ),
       AC, RP, AR )
```

**PM4Py (ProcessTree) code.**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO, CC, ER = "Register Order", "Credit Check", "Engineering Review"
SC, EX, AC = "Supplier Confirmation", "Expedite Review", "Approve Configuration"
RP, AR = "Release Production", "Archive Case"

def leaf(label):
    return ProcessTree(label=label)

def op(operator, children):
    node = ProcessTree(operator=operator)
    for c in children:
        c.parent = node
    node.children = children
    return node

def optional(label):
    return op(Operator.XOR, [leaf(label), ProcessTree()])  # ProcessTree() with label=None => silent (tau)

core = op(Operator.PARALLEL, [leaf(CC), leaf(ER), optional(SC), optional(EX)])

model_permissive = op(Operator.SEQUENCE, [leaf(RO), core, leaf(AC), leaf(RP), leaf(AR)])
```

**Deliberately excluded behavior (boundary of "reasonable").**
- Register Order not first, or Archive Case not last (D1 is high confidence and never relaxed).
- Approve Configuration before Release Production, or Release Production before Archive Case (D2, never relaxed).
- Approve Configuration before *any* of CC, ER, SC(if present), EX(if present) have completed — this AND-join into AC is retained from D3/D4/D6 even though the *internal* ordering among those four is fully relaxed.
- More than one Expedite Review occurrence (still capped at one, per D6's explicit "at most once," which is not in tension with any evidence).

**The reasonable-vs-forbidden boundary, stated explicitly:** the permissive model relaxes D5 (SC needs *one* of CC/ER) to full independence, and relaxes D6's "requires completion of both CC and ER" to "no ordering constraint at all" for Expedite Review. Both relaxations are disclosed as **intentional over-generalizations**, justified only by the goal of exploring the outer envelope of plausible behavior, not by direct evidence. Anything touching D1, D2, or the AND-join at Approve Configuration remains forbidden regardless of exploratory intent, because those rest on high-confidence, 100%-consistent observations (D1, D2) or an explicit multi-source domain rule (D3/D4 converging at AC).

**Known overfitting/underfitting risk (this model risks precision loss, not underfitting).** Because it admits every interleaving of four elements (up to 4! × 2 × 2 combinations before accounting for the fixed skeleton), it will readily "fit" almost any future trace touching this activity set — including operationally implausible ones (e.g., Expedite Review immediately after Register Order, before any check has even started), which is a precision/explainability cost disclosed here rather than discovered by surprise later.

# 7. Comparative Model Matrix

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|
| Expected fitness on the 30 observed cases | Very high ( perfect, by construction) | High (all 7 variants replay as valid interleavings of the two branches) | High (superset of balanced's admitted behavior, should also replay all 30) |
| Expected precision risk | Very low (language  observed set) but the metric is close to tautological here | Lowtomoderate (some extra interleavings within each branch beyond exactly-observed orderings) | High (large added behavior space, several unsupported/undesirable interleavings per §6) |

# 8. Validation Code

```python
import pm4py

# ---------------------------------------------------------------------------
# 1. Reconstruct the 30-case event log from the observed variant counts
# ---------------------------------------------------------------------------
variant_counts = [
    (12, "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (7,  "Register Order,Engineering Review,Credit Check,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (4,  "Register Order,Credit Check,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (3,  "Register Order,Engineering Review,Credit Check,Approve Configuration,Release Production,Archive Case"),
    (2,  "Register Order,Credit Check,Supplier Confirmation,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Expedite Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Engineering Review,Credit Check,Expedite Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
]

trace_strings = []
for count, variant in variant_counts:
    trace_strings.extend([variant] * count)

assert len(trace_strings) == 30

log = pm4py.parse_event_log_string(trace_strings)

# ---------------------------------------------------------------------------
# 2. Assemble the three models
#    (assumes model_conservative, model_balanced, model_permissive
#     were built exactly as in Sections 3-5)
# ---------------------------------------------------------------------------
models = {
    "conservative": model_conservative,
    "balanced": model_balanced,
    "permissive": model_permissive,
}

results = {}

for name, model in models.items():
    print(f"\n=== {name.upper()} ===")

    # 2a. Convert to an accepting Petri net
    net, im, fm = pm4py.convert_to_petri_net(model)

    # 3. Soundness check
    is_sound = pm4py.check_soundness(net, im, fm, print_diagnostics=True)
    print("Sound:", is_sound)

    # 4. Conformance / quality met
