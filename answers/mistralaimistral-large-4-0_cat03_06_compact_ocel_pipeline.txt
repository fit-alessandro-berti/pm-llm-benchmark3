## 1. Modeling assumptions

- **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.
- **E2O qualifier vocabulary:**  
  `created`, `contains`, `added_to`, `reserved`, `involves`, `packed`, `packed_into`, `dispatched`, `carries`, `issued`, `billed`, `recorded`, `paid`, `confirmed`, `closed`.
- **O2O direction convention:** source object  target object; the qualifier describes the relation from the source to the target. Examples: `O100 --contains--> I1`, `P1 --packs--> I1`, `D1 --carries--> P1`, `V1 --bills--> O100`, `M1 --partially_settles--> V1`.
- **Direct relations for logistics and financial events:**  
  I use **source-direct E2O relations** for events that explicitly name or operationally share Orders/Items. Logistics events (`Dispatch Package`, `Confirm Delivery`) relate directly to `Package` and `Delivery` only. Financial events (`Record Payment`) relate directly to `Payment` and `Invoice` only. This keeps the source system facts clean.
- **Preventing analytical propagation from being confused with source facts:**  
  The `relations` table contains only direct source-system E2O links. Analytical propagation through O2O relations is **not** stored in `relations`; it is computed on demand if needed. This separation preserves provenance.
- **Version-dependent PM4Py assumption:**  
  I assume the constructor `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is available. If a PM4Py version differs, only that constructor line should be adjusted, not the data semantics.

### Activities and object types touched

| Activity | Object types touched |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Item, Order |
| Pack Package | Package, Item, Order |
| Dispatch Package | Package, Delivery |

| Confirm Delivery | Delivery |

### Consequential events for convergence/divergence

- **e6 Reserve Stock** and **e7 Pack Package P1** are shared by O100 and O200. They create convergence in the Order view and are the main reason P1 combines items from two orders.
- **e11 Issue Invoice V1** links V1 to both O100 and O200, creating a financial convergence point.
- **e12 Record Payment M1** and **e15 Record Payment M2** link payments to V1, but not directly to Orders, leaving payment allocation implicit.

## 4. Expected flattened behavior

### Order flattening

- **Approximate trace shape:**  
  O100: `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Issue Invoice  Close Order`  
  O200: `Create Order  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order`
- **Copied shared events:** e6, e7, and e11 appear in both O100 and O200 traces.
- **Omitted lifecycle aspects:** Dispatch, Confirm Delivery, and Record Payment are not directly related to Orders, so they are omitted.
- **Likely DFG edges:**  
  `Create Order  Add Item`, `Add Item  Add Item`, `Add Item  Reserve Stock`, `Reserve Stock  Pack Package`, `Pack Package  Pack Package`, `Pack Package  Issue Invoice`, `Issue Invoice  Close Order`.
- **Misleading interpretations:** Flattening duplicates shared events, making it seem each order has its own Reserve Stock and Pack Package. The missing logistics and payment events make the order lifecycle look incomplete. The `Pack Package  Pack Package` edge may suggest two sequential packing steps per order, but actually P1 and P2 are different packages.

### Package flattening

- **Approximate trace shape:**  
  P1: `Pack Package  Dispatch Package`  
  P2: `Pack Package  Dispatch Package`
- **Copied shared events:** None between P1 and P2; e7 and e8 are distinct.
- **Omitted lifecycle aspects:** Item contents, order involvement, and delivery confirmation are omitted.
- **Likely DFG edges:** `Pack Package  Dispatch Package`.
- **Misleading interpretations:** Package lifecycle looks trivial; no visibility into items or orders; delivery confirmation is omitted.

### Delivery flattening

- **Approximate trace shape:**  
  D1: `Dispatch Package  Confirm Delivery`  
  D2: `Dispatch Package  Confirm Delivery`
- **Copied shared events:** None.
- **Omitted lifecycle aspects:** Package contents, orders, and items are omitted.
- **Likely DFG edges:** `Dispatch Package  Confirm Delivery`.
- **Misleading interpretations:** Delivery looks like a simple dispatch-confirm process; no package or order context is visible.

### Invoice flattening

- **Approximate trace shape:**  
  V1: `Issue Invoice  Record Payment  Record Payment`
- **Copied shared events:** None; there is only one invoice.
- **Omitted lifecycle aspects:** Orders billed and payment allocation are omitted.
- **Likely DFG edges:** `Issue Invoice  Record Payment`, `Record Payment  Record Payment` (self-loop).
- **Misleading interpretations:** The invoice trace shows two payments but not which orders they settle; payment allocation is ambiguous.

### Why flattening on Payment would be particularly weak

Each Payment object (`M1`, `M2`) has only one event: `Record Payment`. Flattening on Payment would yield single-event traces, no DFG edges, and no lifecycle. It would not show the relation to the Invoice or the Orders, making the Payment view almost meaningless.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG should show edges based on shared objects:

- `Create Order  Add Item` via Order
- `Add Item  Add Item` via Order O100
- `Add Item  Reserve Stock` via Item
- `Reserve Stock  Pack Package` via Item
- `Pack Package  Pack Package` via Order O100 (e7 and e8 both involve O100)
- `Pack Package  Dispatch Package` via Package
- `Dispatch Package  Confirm Delivery` via Delivery
- `Issue Invoice  Record Payment` via Invoice
- `Issue Invoice  Close Order` via Order

**P1** is central: `Pack Package P1` (e7) shares Items I1, I3 and Orders O100, O200, creating convergence from `Reserve Stock` and divergence to `Dispatch Package`. **V1** is central for the financial flow: `Issue Invoice V1` (e11) shares Orders O100, O200 and Invoice V1, then `Record Payment M1/M2` (e12/e15) share Invoice V1. **M1** and **M2** are Payment objects that appear only in `Record Payment` events, so they are leaves in the OC-DFG. **O100** and **O200** appear in many events, creating multiple edges.

### OTG

The OTG should show object-type co-occurrence edges:

- Order–Item (Add Item, Reserve Stock, Pack Package)
- Item–Package (Pack Package)
- Package–Delivery (Dispatch Package)
- Invoice–Order (Issue Invoice)
- Invoice–Payment (Record Payment)
- Order–Package (Pack Package)

This shows the process spans both logistics and finance.

### ET–OT

The ET–OT graph should connect event types to object types:

- `Create Order`  Order
- `Add Item`  Order, Item
- `Reserve Stock`  Item, Order
- `Pack Package`  Package, Item, Order
- `Dispatch Package`  Package, Delivery
- `Issue Invoice`  Invoice, Order
- `Record Payment`  Payment, Invoice
- `Confirm Delivery`  Delivery
- `Close Order`  Order

### Object-centric Petri net

The object-centric Petri net should show places for object types and transitions for activities. **P1** is a shared package: the transition `Pack Package P1` consumes Items I1, I3 and produces Package P1, synchronizing O100 and O200. **V1** is an invoice: `Issue Invoice V1` consumes Orders O100, O200 and produces Invoice V1; `Record Payment M1/M2` consume Invoice V1 and produce Payment M1/M2. `Close Order O100/O200` occur after `Issue Invoice` but are not directly connected to payments in the E2O relations; the net may show them as connected via Order places or as somewhat independent. The net has **no uniquely determined interpretation**; it may show concurrency between logistics and finance.

### Object-interactions summary

Expected interactions:

- O100 interacts with I1, I2, P1, P2, V1
- O200 interacts with I3, P1, V1
- P1 interacts with I1, I3, D1, O100, O200
- V1 interacts with O100, O200, M1, M2
- M1 and M2 interact with V1

This highlights cross-object collaboration, especially **P1** bridging two orders and **V1** bridging orders and payments.

## 6. Modeling alternatives

### Alternative 1: Source-minimal relations

Only objects explicitly named in the event are related. This would omit O100 from e8 (`Pack Package P2`) because O100 is not named. It would also omit any downstream propagation.  
**Effect on discovery:** Order flattening for O100 would miss `Pack Package P2`; the OC-DFG would lose the `Pack Package  Pack Package` edge via O100. Package and Invoice flattening would be largely unchanged. This reduces noise but loses some order visibility.

### Alternative 2: Full operational involvement

Relate every downstream event to all Orders and Items involved via O2O propagation. For example, `Dispatch P1 in D1` would relate to P1, D1, I1, I3, O100, O200; `Confirm Delivery D1` would relate to D1, P1, I1, I3, O100, O200; `Record Payment M1` would relate to M1, V1, O100, O200.  
**Effect on discovery:** Flattened traces become longer and include logistics/payment events for Orders; the OC-DFG becomes denser with edges like `Dispatch Package  Confirm Delivery` via Items/Orders and `Record Payment  Close Order` via Orders. However, source facts are mixed with derived ones, risking over-interpretation.

### Alternative 3: O2O-propagated analytical relations

Keep `relations` source-direct, but compute propagated E2O links on the fly for analysis. For example, add derived relations from Order to Dispatch via `Package contains Item`.  
**Effect on discovery:** Similar discovery results to full involvement, but with clear provenance. Flattening can be done on enriched relations if desired, while the source relations remain clean. This is a good compromise between fidelity and analytical richness.

## 7. Failure modes

1. **Relation inflation:** Adding propagated links as source facts makes the OC-DFG overly dense, flattening traces too long, and hides true source events.
2. **Missing direct E2O links:** Omitting necessary links (e.g., Order to Pack Package) breaks object-centric discovery, causing disconnected components or missing edges.
3. **Treating O2O propagation as observation:** Confusing derived relations with source facts leads to false causal claims.
4. **Duplicate shared events after flattening:** Shared events like e6/e7 appear in multiple object traces, causing double counting in frequency analysis.
5. **Ambiguous payment allocation:** Payments M1/M2 relate only to V1, not to specific Orders/Items; flattening on Order misses payments, and flattening on Invoice shows payments but not allocation.
6. **Overly short Payment traces:** Payment objects have only one event, so flattening on Payment yields trivial traces and no DFG.
7. **Constructor/API version mismatch:** PM4Py OCEL constructor may differ; the constructor line must be isolated and adjusted without changing data semantics.
8. **False total order for same-time events:** Even though this example has no timestamp ties, if timestamps tie, flattening may impose an arbitrary order; caution is needed.
9. **Ignoring O2O relations in discovery:** Some object-centric discovery algorithms may not fully use O2O relations, leading to incomplete views of cross-object dependencies.
10. **Mixing object types in flattening:** Flattening on a single object type discards other object perspectives, which can hide shared events and cross-object synchronization.
