## 1. Modeling assumptions

* **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. PascalCase singular, OCEL 2.0 convention. Objects: `O100,O200` : `Order`; `I1,I2,I3` : `Item`; `P1,P2` : `Package`; `D1,D2` : `Delivery`; `V1` : `Invoice`; `M1,M2` : `Payment` (12 objects total).
* **E2O qualifier vocabulary:** Qualifiers encode *role in event* and provenance. Primary roles: `created`, `receiving_order`, `added_item`, `reserved_item`, `created_package`, `packed_item`, `dispatched_package`, `carrier_delivery`, `issued_invoice`, `billed_order`, `recorded_payment`, `settled_invoice`, `confirmed_delivery`, `delivered_package`, `closed`. Analytically derived context (not a source-system foreign key) gets suffix `_derived`: e.g. `requesting_order_derived`, `fulfilled_order_derived`, `recipient_order_derived`. This keeps vocabulary small, consistent per `activity+type`, but visually separable.
* **O2O direction conventions:** `source -> target` with active verb. All O2O are directed for graph traversal but interpretable undirected:
  - `Order --contains--> Item`
  - `Package --packs--> Item`
  - `Delivery --carries--> Package`
  - `Invoice --bills--> Order`
  - `Payment --partially_settles / --completes_settlement--> Invoice`
* **Whether logistics / financial events relate directly to Orders and Items:** Hybrid / full-involvement with derivation marking. Logistics: `Reserve Stock`, `Pack Package`, `Dispatch Package`, `Confirm Delivery` relate *directly* to `Order` (+ `Item` where handled) with `_derived` qualifier to allow end-to-end Order traces without extra joins. Financial: `Issue Invoice` relates directly to `Invoice+V1` *and* both `Order`s (billed), because the business fact states V1 bills both. `Record Payment` relates *only* to `Payment+M*` and `Invoice+V1` with `settled_invoice`; NOT directly to `Order`. The indirect Order–Payment link is navigable only via `Payment->Invoice->Order` O2O. This preserves payment-allocation semantics.
* **Trade-off direct source vs. propagated relations:** Direct relations give flattened logs that are locally complete (an Order trace shows reserve/pack/dispatch/confirm) at cost of convergence (one event linked to 4-5 objects) and divergence (shared events duplicated after flattening) and risk of being read as source-system writes. Minimal source-only relations stay faithful to what ERP writes (only the created/handled object) but Order flattening then omits whole logistics phases, DFG appears disconnected, and you need O2O joins for every analysis. Chosen hybrid makes flattening useful while qualifiers + optional `is_source_derived` flag + documentation prevent conflating observation with inference.
* **How to prevent confusion:** 1) `_derived` qualifier suffix, 2) audit table documenting each activity's source vs. derived types, 3) validation that derivation never creates new `eids`/`oids`, 4) recommendation to filter `_derived` when counting source interactions. Timestamp consistency enforces that derivation does not invent activity semantics.
* **Version-dependent PM4Py assumption:** Assumes PM4Py 2.7+ with `OCEL(events,objects,relations,o2o)` dataclass and helpers `ocel_get_object_types`, `ocel_object_type_activities`, `ocel_flattening`, `discover_dfg`, `discover_log_skeleton`, `discover_ocdfg`, `discover_otg`, `discover_etot`, `discover_oc_petri_net`, `ocel_objects_interactions_summary`. The actual constructor/import line is isolated; if `pm4py.objects.ocel.obj.OCEL` moved to `pm4py.ocel.ocel.OCEL` change only that line.

**Consequential event:** `e6 Reserve Stock` (08:30) and `e7 Pack Package P1` (09:00) are structurally critical. Both relate to `O100+O200` simultaneously via `_derived` qualifiers and to `I1+I3` where `P1` contains items from two Orders. They create classic convergence (one event, many objects of same type) and subsequent divergence after flattening. `e11 Issue Invoice V1` similarly converges two Orders onto one Invoice; `e9/e13` propagate P1/D1 through both Orders, so Order-flattened traces will duplicate the same dispatch/confirm events. Without the `_derived` flag these would be indistinguishable from source facts.

## 4. Expected flattened behavior

General mechanism: flattening on `otype` replicates each event once per distinct `oid` of that type linked in E2O, ordering by timestamp, grouping by `oid`. Shared events are copied; events without that type disappear.

* **Order** (`O100`, `O200`):
  - Trace shape O100: `Create Order(e1) -> Add Item I1(e2) -> Add Item I2(e3) -> Reserve Stock(e6) -> Pack P1(e7) -> Pack P2(e8) -> Dispatch P1(e9) -> Dispatch P2(e10) -> Issue Invoice(e11) -> Confirm D1(e13) -> Confirm D2(e14) -> Close Order(e17)` ~11 events. O200: `Create Order(e4) -> Add Item I3(e5) -> Reserve Stock(e6) -> Pack P1(e7) -> Dispatch P1(e9) -> Issue Invoice(e11) -> Confirm D1(e13) -> Close O200(e16)` ~8 events.
  - Copied shared events: e6, e7, e9, e11, e13 appear in *both* traces identically timestamped.
  - Omitted: Payment amounts (e12,e15 absent) because no direct Order link by design – otherwise would falsely split 100 vs 150 per Order.
  - Likely DFG edges: `Add Item -> Reserve Stock`, `Reserve Stock -> Pack Package`, `Pack Package -> Dispatch Package`, `Dispatch Package -> Issue Invoice -> Confirm Delivery -> Close Order`. Self-loops on `Pack Package` for O100 (e7 then e8). Convergence inflates frequency of `Reserve Stock->Pack` to 2 despite single occurrence.
  - Misleading: Suggests sequential per-order reservation when operationally joint; suggests causal order `Dispatch -> Issue Invoice` per Order when invoicing was batch; hides that O100 needed two packages.

* **Package** (`P1`,`P2`):
  - Trace shape P1: `Pack P1(e7) -> Dispatch P1(e9) -> Confirm D1(e13)`; P2: `Pack P2(e8) -> Dispatch P2(e10) -> Confirm D2(e14)`.
  - Copied: none (no package-shared event; P1 distinct from P2).
  - Omitted: Order creation, Item add, Reserve, Invoice/Payment, Order close – so package lifecycle looks isolated, missing why P1 combined cross-order items.
  - DFG: linear chain `Pack -> Dispatch -> Confirm` for each, aggregated shows two parallel variants of length 3. No convergence artifact.
  - Misleading: Implies packages independent, obscures that P1 fulfillment depended on two Orders' items and shared delivery confirmation impacted both Orders.

* **Delivery** (`D1`,`D2`):
  - Trace shape: D1: `Dispatch P1(e9) -> Confirm D1(e13)` with gap 3h; D2: `Dispatch P2(e10) -> Confirm D2(e14)` gap ~23h.
  - Copied: none.
  - Omitted: everything before dispatch and financial events; no visibility into packing or invoicing.
  - DFG: single edge `Dispatch -> Confirm` frequency 2. Skeleton shows strict precedence.
  - Misleading: Flattened log suggests deliveries are unrelated quick shippings; actually D1 carried cross-order consolidated package P1, significant for OT analysis but invisible here.

* **Invoice** (`V1`):
  - Trace shape V1: `Issue Invoice(e11) -> Record Payment M1(e12) -> Record Payment M2(e15)` – 3 events collapsing two payment objects onto one case.
  - Copied: none internally (single case), but conceptually e12/e15 each carry distinct Payment oids flattened away.
  - Omitted: All logistics/order context except e11; no link to which Order contributed to balance.
  - DFG: `Issue Invoice -> Record Payment` with self-loop `Record Payment -> Record Payment` (M1 follower M2). Frequencies hide partial-settlement semantics (100 vs 150).
  - Misleading: Implies linear settlement of one invoice; payment allocation to O100 vs O200 cannot be inferred; analyst might attribute full 250 to single Order if joining flattened Invoice log to Order log naively.

* **Why Payment flattening would be particularly weak:** Each Payment case (`M1`, `M2`) contains exactly one event (`e12` for M1, `e15` for M2) plus possibly shared `settled_invoice` if Payment shared events existed, which they do not. Resulting log has 2 cases of length 1, no ordering, empty DFG, skeleton vacuous (`always`/`never` undefined). All context (which Invoice, which Orders, amount causality, inter-payment interval) and the crucial `partially_settles` vs `completes_settlement` distinction via V1 O2O is lost. Must analyze Payment through Invoice O2O or ET-OT, not alone.

## 5. Expected object-centric structures

* **OC-DFG:** Per-type DFGs superimposed with object-type-colored arcs. Expect strong per-type flows: `Order: Create -> Add* -> Reserve -> Pack* -> Dispatch* -> Issue -> Confirm* -> Close`; `Package: Pack -> Dispatch -> Confirm`; `Invoice: Issue -> Record Payment(loop)`; `Delivery: Dispatch -> Confirm`. Sharing nodes reveal consolidation: `Reserve Stock` has incoming/outgoing edges from both `Order` and `Item` nets, `Pack P1(e7)` appears at intersection of `Order(O100,O200)+Package(P1)+Item(I1,I3)`, indicating divergence. `V1 Issue Invoice` fans out to two `Order` tokens simultaneously. `M1/M2` appear only on `Payment/Invoice` layers, connecting via `V1` node. Filtering on `_derived` qualifiers collapses some cross-type edges, showing sensitivity.

* **OTG (Object Type Graph):** Nodes are types, edges weighted by co-occurrence in events or O2O. Strong triangle `Order—Item—Package` via `contains/packs` (P1 bridges O100 and O200, visible as Item type connecting two Order instances through one Package). `Delivery—Package` 1:1 edges (2). `Invoice` centrally connected to `Order` (2 bills edges) and to `Payment` via settlement edges (2). `Payment` only adjacent to `Invoice`, isolating financial subgraph – matches design where payments not directly linked to Orders. Total object interactions summary will count `Package packs Item=3`, `Invoice bills Order=2`, etc.

* **ET–OT (Event-Type vs Object-Type) graph:** Matrix `activity x object-type` with cell weight = events touching that type. Row `Reserve Stock` shows columns `Item=1 event*2 objects`, `Order_derived=1*2`; `Pack Package` shows `Package=2`, `Item=2 events covering 3 relations`, `Order_derived=2 events covering 3 relations` – high fan-out flag. `Dispatch Package` row spans `Package, Delivery, Order_derived`. `Record Payment` row only `Payment`+`Invoice`, highlighting the deliberate gap vs `Order`. Heatmap immediately spots convergence points (cells >1 object per event).

* **Object-centric Petri net:** Non-uniquely determined (choice of shared places, silent transitions). Expected: one subnet per type (`Order` lifecycle with choice/join for parallel items, `Item` subnet reserved->packed->dispatched, `Package` sequential, `Invoice` pending->settled). Synchronization via shared transitions: `e6/t_reserve` consumes/produces tokens of `Order(O100),Order(O200),Item(I1),Item(I3)` simultaneously; `e7/t_pack_P1` is the most synchronous, requiring two Order + two Item + one Package token; `e11/t_issue_V1` synchronizes `Invoice(V1)` creation with two `Order` tokens (batch billing). Replay will show O100 needs two package tokens but O200 one, exposing imbalance. Second payment `e15/t_record_M2` is modeled as transition that finally enables `completed` place for Invoice; depending on miner, alternative models use loop vs two distinct transitions for `partially/completes`. Must stress model varies with discovery thresholds/place-merging; not singular ground truth.

* **Object-interactions summary:** Tabular counts of `(otype1, otype2)` co-occurring in same event. Predictions: `(Order,Item)` high due to `Add Item+e6/e7`; `(Item,Package)` = packed events (P1 dominates); `(Order,Package)` moderate (derived events); `(Order,Invoice)` =2 (only e11) – confirms invoice consolidation; `(Invoice,Payment)`=2 (e12,e15). Pairwise instance view: `P1` interacts with 2 Orders+2 Items (max degree), `V1` interacts with O100,O200,M1,M2, `M1` only with V1, illustrating star vs bridge roles.

## 6. Modeling alternatives

1. **Source-minimal:** E2O contains only what source system physically updated: e6  only `I1,I3` (no Orders), e7 only `P1,I1,I3` (no Orders), e9/e10 only `P*,D*`, e13/e14 only `D*`. Orders appear only on `Create/Add/Close/Issue Invoice`.
   *Effect:* Order-flattened traces shrink to creation/invoicing/close, losing logistics visibility; DFG for Order misses `Pack/Dispatch/Confirm` edges entirely, so analyst concludes logistics disconnected. OC-DFG shows disjoint subgraphs with bridging only via O2O, forcing O2O-temporal joins for every query; correctness purist but analytically poor.

2. **Full operational involvement (maximal):** Every downstream event explicitly links to all causally upstream objects: e6,e7,e9,e10,e13,e14 all link to both `Orders` and all constituent `Items` (so e9 links to P1,D1,O100,O200,I1,I3 =5-6 objects). Financial payments also directly link to billed Orders (`M1,M2`  O100,O200).
   *Effect:* Maximal completeness, Order traces longest, Payment traces longer (now include Order). But massive relation inflation: convergence 6-fold, flattened Order copies identical timestamps leading to artificial concurrency, DFG overestimates edge frequencies, performance metrics double-count waiting time, ambiguous payment splits cause inflated settlement amounts if summed per Order.

3. **O2O-propagated analytical (virtual):** E2O kept source-minimal, but analysis layer expands relations on-the-fly by traversing O2O at query time (`Order contains Item`  `Pack Package packs Item` transitively implies Order involvement). Qualifier becomes `inferred_via_O2O`, not stored.
   *Effect:* Storage stays lean and provenance clean; OC-DFG via on-demand expansion can mimic hybrid results without persisting derived rows. However flattening without materialization gives minimal traces unless tool supports inference; results now depend on inference depth/cutoff (1 hop vs transitive). Business story unchanged, but reproducibility hinges on documenting inference rules; naive replay may under-report involvement compared to persisted `_derived` approach.

All three describe same retailer process; differences only change which tables an analyst queries, how duplication and edge weights are counted.

## 7. Failure modes

* **Relation inflation:** Adding derived links indiscriminately (e.g., linking dispatch also to every Item) creates 6-object events. Flattened frequencies, sojourn times, and OC-DFG edge weights roughly double-count that instant, suggesting parallelism that never consumed resources.
* **Missing direct E2O links:** Omitting Order context on Reserve/Pack/Dispatch erases cross-order consolidation signal. P1's bridging role becomes discoverable only via two-hop O2O navigation; order-centric KPIs like `time from Reserve to Confirm per Order` become unmeasurable.
* **Treating O2O propagation as observation:** Interpreting inferred `Order--Pack` (via O2O) as if ERP logged an `Order.updated_by_pack` timestamp confuses logical association with physical update. Leads to claims of Order state machine transitions that never existed in audit log.
* **Duplicate shared events after flattening:** Single event `e6 Reserve Stock` becomes two rows (`O100@08:30`, `O200@08:30`). Process mining interprets as two independent reservations in sequence, computes throughput 0 lag, violates true joint execution; variant analysis spuriously shows concurrency.
* **Ambiguous payment allocation:** Linking `M1/M2` directly to Orders invites proportional split assumptions (50/50 or by item value) not in narrative. Any allocation rule invented post-hoc corrupts financial compliance; correct model keeps PaymentInvoiceOrder and leaves allocation unresolved.
* **Overly short Payment traces:** Flattening on `Payment` yields cases of length 1; DFG empty, performance/prediction impossible. Mistaking this for “payment process simple” ignores the essential Invoice-mediated settlement chain visible only object-centrically.
* **Constructor/API version mismatch:** Call `OCEL(events,objects,relations,o2o)` fails if installation expects `OCEL(relations=...)` vs `ocel_e2o` naming, or uses `pm4py.ocel_flattening.apply`. Without isolated fallback, entire pipeline aborts despite semantically correct DataFrames. Fix: adapt import/single line, validate schema, don't rename semantics.
* **False total order for same-time events:** Even though this dataset has no equal timestamps, assuming flattened timestamp order equals causal order is fragile. If two Adds at same instant were ties, alphabetical tie-break would invent precedence. More generally, DFG edges between simultaneous events (e.g., hypothetical same-minute packs of P1/P2) would be arbitrary. Must document that ordering is temporally coincidental, not causal, and rely on object synchronization rather than interleaving.
