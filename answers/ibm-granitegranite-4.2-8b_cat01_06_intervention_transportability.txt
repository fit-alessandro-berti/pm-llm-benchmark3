## 6. Candidate Site B intervention

**Eligibility rules:**  
- Doc Check may start concurrently with Identity Check **only if** Originals Receipt is *already received* (i.e., originals physically or digitally present at Register), **or** if originals are *not legally required* for the case (i.e., case type excludes public-sector/high-value without statutory exception).  
- For cases where originals are legally required (62% volume), Doc Check **must** wait for Originals Receipt event before starting, regardless of ID Check status. Parallelism applies only to Identity Check (which can start immediately after Register); Doc Check starts solely after Originals Receipt.  
- Legal Review cases (40% volume) follow statutory order: Assessment  Legal Review  (if Request Supplement issued)  Document Check restart. Parallelism does not bypass Legal Review; Assessment still waits for both ID and Doc (Doc after Originals Receipt).

**Concurrent tasks & queue controls:**  
- After `Register`, always start `Identity Check` immediately (assigned to ID reviewer pool).  
- After `Originals Receipt` (when required), start `Document Check` immediately (assigned to Doc reviewer pool); if originals not required, start `Document Check` concurrently with `Identity Check` at `Register`.  
- `Assessment` starts only when both `Identity Check` **and** (`Document Check` complete *or* `Request Supplement` resolved for legal cases). For legal cases pending `Legal Review`, `Assessment` waits for `Legal Review` decision *or* supplement clearance; `Legal Review` decision (Approve/Reject) does not block `Document Check` restart if supplement issued.  
- WIP limit: 6 open verification tasks (ID + Doc checks) per reviewer **total** (not per role), enforced at task creation. System logs "verification phase" queue status daily. If queue size 5, new Doc Check requests (for required originals) are queued; ID Check requests are not queued (ID is typically fast).  
- Role responsibilities: ID reviewers handle only `Identity Check`; Doc reviewers handle only `Document Check`; Assessors handle `Assessment`; Legal reviewers handle `Legal Review` and `Request Supplement`. No cross-assignment (no cross-training assumption).

**Legal-review & supplement loop handling:**  
- At `Originals Receipt`, log `originals_received_time`.  
- At `Document Check` start (after `Originals Receipt` for required cases), check `supplement_pending` flag (true if any active `Legal Review` for the case has issued `Request Supplement`). If `supplement_pending` = true, **do not start `Document Check`**; instead, log `doc_start_delayed = true` and place `Document Check` on "supplement-resolved" queue. `Document Check` starts automatically when `Request Supplement` is resolved (i.e., Legal Review issues final Approve/Reject or supplemental docs received).  
- If `Legal Review` issues `Request Supplement` *after* `Document Check` has started (i.e., before completion), stop `Document Check` at first work item (e.g., first doc review step), log `supplement_issued_during_doc`, and restart `Document Check` only after `Request Supplement` resolution. Reuse existing doc evidence; no full redo unless supplement requires new docs.  
- `Assessment` never starts if `Document Check` is pending supplement resolution (i.e., `doc_start_delayed` = true or `supplement_issued_during_doc`).

**Logging requirements:**  
- `Register`: case ID, case type (public/high-value? originals required?), start time.  
- `Originals Receipt`: receipt time (mandatory), channel (digital/physical), "lock_used" flag (true if legacy lock prevented immediate entry; logged by reviewer), "supplement_pending" check result (yes/no).  
- `Identity Check`: start time, end time, reviewer ID.  
- `Document Check`: start time (only logged *after* `Originals Receipt` confirmation and `supplement_pending` = false), end time, reviewer ID, "doc_start_delayed" flag if supplement pending at start. If supplement issued during Doc, log "supplement_issued_at" time and "doc_stop" flag.  
- `Legal Review`: decision time, `Request Supplement` issued? (yes/no), supplement resolution time (when Legal Review finalizes supplement or rejects).  
- `Assessment`: start time (only when ID complete AND Doc complete *or* supplement resolved), end time.  
- All timestamps stored in system time (not local); "lock_used" and "supplement_pending" flags are mandatory for every relevant event. Audit log includes rule check outcome (e.g., "Doc start allowed: originals received? yes; supplement_pending? no  yes").

**POWL-style partial-order (minimal, dependency-preserving):**  
```
Register  Identity Check
Register  Originals Receipt (if originals_required = true)
Originals Receipt  Document Check (if originals_required = true)
Originals Receipt  Document Check (if originals_required = false)  // Doc starts at Register for non-required
Identity Check  Assessment (always)
Document Check  Assessment (only when Doc complete *and* supplement resolved; i.e., not while supplement_pending)
Legal Review  Request Supplement (if issued)
Request Supplement  Document Check (restart only; no Assessment)
Legal Review  Approve / Reject (final decision)
Assessment  Approve / Reject (final)
// Constraint: Assessment requires (Identity Check complete) AND (Document Check complete OR Request Supplement resolved)
// Constraint: Document Check start requires (Originals Receipt received) AND (supplement_pending = false)
// Constraint: WIP 6 verification tasks per reviewer (enforced at task creation UI)
```
> *Note: POWL edges reflect only mandatory precedence; "if" conditions (originals status, supplement flag) are enforced by the logging/rule check at task start, not in the partial order alone. The partial order does not encode WIP or supplement logic—those are operational controls.*

**Pilot explanation (218 words):** The pilot tests the *rule* ("Doc Check starts concurrently with ID Check only when originals are not required and no supplement is pending") at the case level, not the full Site A process copy. It isolates the causal mechanism by randomizing only within the least constrained subgroup (non-required originals, no legal cases), holding all other workflow, queue practices, and IT behavior constant. Primary outcome (median cycle time) targets the observed benefit while secondary outcomes (rework %, overlap accuracy, p90) monitor quality and tail effects. Interference controls ensure no managerial cues (e.g., huddles) or training alter behavior; the UI enforces the rule check (`doc_start_allowed?`) and logs the decision, preventing reviewer override. Safety stops if rework >25% or WIP >8/reviewer (indicating rule failure or bottleneck), protecting against harmful signature. Minimum support (80 cases) ensures detection of realistic median change (~4h), while subgroup tracking (simple vs complex) identifies if tail cases worsen. Transportability analysis uses only pilot logs to compare observed vs optimistic scenario predictions and measure rule fidelity, avoiding extrapolation. This separates *mechanism failure* (e.g., supplement issued before Doc start causing rework) from *implementation failure* (e.g., reviewers ignoring the rule or lock preventing timestamp entry), because logs directly capture rule check outcomes and lock usage, while outcomes measure performance. Thus, the pilot answers: "Does the conditional rule reduce median cycle time without increasing rework or worsening tail, under realistic originals timing?" not "Does copying Site A work?"

## 9. Recommendation

**conditional go**

Transfer *only* the conditional parallelism rule: "Start `Document Check` concurrently with `Identity Check` **only when** (1) originals are **not legally required** for the case, *and* (2) no `Request Supplement` has been issued by `Legal Review` for the case." Do **not** copy Site A’s unconditional parallelism, API upgrade, daily huddles, or FTE count changes. Apply the rule only to the subgroup of cases where originals are not required (~38% of Site B volume); exclude legal-review cases (40%) from parallel Doc start in Phase 1. Maintain all statutory prerequisites (`Originals Receipt` before Doc for required cases, `Legal Review` before final decision), and enforce the 6 open verification tasks WIP limit per reviewer via UI. Do not modify legal review timing or assessment order.

Expected benefits: For ~38% of non-required cases, median cycle time may drop ~5–8h (matching digital-claim-only scenario), reducing waiting before Assessment (from 20h to ~12–15h), improving routine claim throughput without increasing rework if supplement checks are enforced. WIP limits prevent queue buildup, and logging (`doc_start_allowed`, `lock_used`, `supplement_pending`) ensures rule fidelity and measurable overlap. Risks: For the remaining 62% (required originals) and legal cases, parallelism does not apply, so no unintended delay; however, if supplement is issued shortly after Doc start in legal cases, rework could increase (~5–8%), and p90 might worsen slightly for tail cases hitting WIP limits (as seen in bottleneck-shift scenario). These risks are mitigated by the rule check (no Doc start if supplement pending) and WIP monitoring in the pilot.

Trigger evidence for expansion: If the 4-week pilot (80 cases per arm) shows (1) median cycle time  4h in the parallel arm vs control for non-required cases, (2) rework % 5% (vs baseline 17%), and (3) overlap % from logs 90% accuracy vs manual check, and (4) WIP 6 compliance 90%, expand parallelism to include low-complexity required-originals cases (e.g., cases where Originals Receipt delay  ID check time), still with supplement check. Trigger modification if pilot shows rework >10% or p90  >15h in parallel arm; then adjust by adding a 2-hour buffer before Doc start for required cases or stagger Doc start for complex cases. Trigger abandonment if median cycle time does not improve >2h or rework >20% in pilot; then revert to baseline and investigate supplement timing or lock behavior first.

> *Rationale: Site A’s evidence is confounded (API, reviewers, marketing, huddles); direct copy ignores mandatory prerequisites (Originals Receipt for 62% cases) and legal supplement loop. Transportable component is the conditional rule (check originals status + supplement status before Doc start), not the unconditional parallelism. Conditional go tests this rule in the safest subgroup (non-required originals) via a small, rule-focused pilot that isolates mechanism (via randomization), monitors quality (rework, overlap), and uses safeguards (UI rule check, WIP limit). This directly addresses transportability uncertainty while avoiding harmful signatures (tail worsening, rework increase). The recommendation explicitly states what to copy (conditional rule + WIP), what not to copy (unconditional parallelism, co-interventions), first subgroup (non-required), benefits/risks, and clear, evidence-based go/modify/abandon triggers.*
