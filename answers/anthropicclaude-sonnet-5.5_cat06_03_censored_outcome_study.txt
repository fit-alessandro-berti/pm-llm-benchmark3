## 1. Target definition

**Primary target (landmark, activation-conditional default).**

| Element | Definition |
|---|---|
| Unit | One credit application (case) at one landmark, after activity harmonisation and de-duplication. |
| Prediction time | The timestamp of the 3rd canonical event, i.e. first entry into Credit Review (Application Started  Identity/KYC Check  Credit Review). Only information with timestamp  this instant is used. Secondary landmarks: k = 2, 5, and elapsed-time landmarks of 24 h and 72 h after start. |
| Population | Applications that reach the landmark with no decision event (Accepted/Rejected/Withdrawn/Transferred) and no post-decision event yet. Applications that end earlier are reported as "ended before landmark" and are not scored or silently dropped. |
| Outcome | D90 = 1 if the feed records a default within 90 days after Account Activated, and 0 if the feed confirms no default by day 90. Labels are defined only for accounts that are activated. |
| Horizon | 90 days from activation, not from application start. |
| Estimand | _k(x, regime) = P(D90 = 1 \| prefix_k = x, activated under the logged policy of that regime). This is read as "default risk *if* the application becomes an account under the current policy". It is not the default risk of the application. |

**Why this is defensible.**
- D90 is observed, and its semantics are unambiguous for activated accounts.
- The assumptions needed to adjust for label delay and missing feeds are explicit, and some can be probed.
- It supports uses that do not change who gets credit, such as review prioritisation, enhanced monitoring, and early collections readiness.
- It never treats rejected, withdrawn, transferred, or open cases as non-default.
- It answers a narrower question than the lender's wording. The lender must be told this.

**Alternatives that answer different questions.**
- **All-application multi-state or competing outcomes.** Cause-specific hazards or cumulative incidence for Rejected, Withdrawn, Transferred, Activated, and Activated-then-Default, with open cases censored. The estimand P(activated  default  90d after activation \| prefix) equals P(A=1\|x) · (x). It is observable under the current policy and useful for portfolio planning. It is a secondary deliverable, and the decomposition keeps the two sources of uncertainty apart.
- **Time-to-default after activation with right censoring.** A discrete-time hazard or survival model with follow-up truncated at min(activation + 90d, cutoff  reporting lag). It uses recently activated accounts that a binary label would discard, and it gives a full risk curve.
- **Policy-specific counterfactual ("default if every applicant were activated", or under a new threshold).** This needs positivity, no unmeasured confounding of activation, and consistency. Deterministic score thresholds violate positivity, so it is not identified from these data. It is explicitly labelled as requiring stronger assumptions, and it is not the primary target.

## 3. Censoring and missing-label strategy

| Mechanism | Nature | Handling |
|---|---|---|
| Ordinary right censoring (open cases; activated accounts still inside the 90-day window) | Administrative, independent of default given start date | Open cases are censored in the multi-state analysis. In the binary primary analysis, only fully followed-up accounts enter. In the survival analysis, follow-up ends at min(activation + 90d, cutoff  35d). |
| Delayed labels (feed arrives 7–35 days after day 90) | A reporting delay, not a censoring time. A default on day 40 can be unknown on day 100. | Treat as nowcasting. Use as-of label visibility, a 35-day embargo before training, and the conservative censoring time above. Never label "no feed yet" as non-default. |
| Selection through activation | Default is defined only when A=1, and activation depends on score, policy, and applicant behaviour | The primary estimand is conditional on A=1. No extrapolation to rejected, withdrawn, or open cases. The secondary model reports P(A=1\|x) separately. |
| Transfer | A competing event for activation at this lender. It is also possible missing follow-up if the account was activated elsewhere. | In the primary analysis, transfers are outside the estimand. In the multi-state model, transfer is a cause-specific competing event. Sensitivity: use the 60% linked cases, check whether the outcome definition is comparable, and compare linked with unlinked on covariates. |
| Permanently missing feed (partner-enriched) | Probably covariate-dependent and possibly outcome-dependent | See below. |

**Primary strategy.**
1. Restrict to activated accounts with complete follow-up by the as-of date (design-based handling of maturity).
2. Model P(label observed | X_prefix, channel, source_system/partner flag, region, amount, activation month, and post-activation administrative variables). The weight model may use post-activation administrative variables, but the risk model may not.
3. Fit the risk model on labelled rows with weights 1/p_obs, clipped and stabilised.
4. Evaluate with the same weights.

This gives unbiased risk estimates if the label is missing at random given the covariates in the weight model. It is fit separately per regime (pre/post policy).

**Sensitivity analyses.**
- **Bounds and tipping point.** Assume missing-feed accounts have default odds  times those of observed accounts, with   {0.5, 1, 1.5, 2, 3}. Report the range of prevalence, calibration intercept, and AUC/Brier. Also report the worst-case 10.7%–25.0% bounds.
- **Survival version.** A discrete-time hazard or Cox model on all activated accounts, including recent ones (follow-up-censored), compared with the binary primary.
- **Transfer sensitivity** (above).
- **All-application sensitivity.** Bound P(activated  default) under extreme assumptions for the un-exposed cases. For any policy-counterfactual claim, run a Rosenbaum-type or E-value analysis.

**Testability of assumptions.**

| Assumption | Status |
|---|---|
| Positivity of label observation within covariate strata | **Testable.** Check weight distribution and overlap. |
| Missingness depends on observed covariates (partner, channel, region) | **Testable.** Model it and compare covariates of observed and missing accounts. |
| Feed lag  35 days | **Partially testable.** Empirical distribution of `label_available_at  (activation + 90d)`. Lags beyond the window look identical to permanent missingness. |
| Missing-at-random given covariates for the permanent-missing accounts | **Partially testable.** It is untestable from the current data. A random audit sample of missing accounts, for example via a bureau pull, makes it testable. |
| Censoring is independent of default given the covariates | **Partially testable**, for example through hazard diagnostics. |
| No unmeasured confounding of activation, and rejected applicants would behave like activated ones | **Fundamentally untestable.** |
| Outcomes of transferred accounts elsewhere match this lender's definition | **Fundamentally untestable** without the partner's data. |

## 4. Prefix extraction

**Order of operations (enforced in code):**
1. Parse timestamps as UTC.
2. Apply the versioned activity-rename map to map old and new activity names to canonical names.
3. Drop exact duplicates. For migration-period events, also drop events that repeat the same (case, activity) within a small tolerance such as 2 s.
4. Sort by (timestamp, original row order).
5. Truncate at the as-of time.
6. Count positions and cut prefixes.

De-duplication and renaming come *before* counting. Otherwise duplicate rows would shift "event 3" after 15 Oct 2025.

**Fixed event-count prefixes.**
- The prefix is the first k canonical events.
- The prediction time is the timestamp of the k-th event.
- Only columns on an allowlist may enter. Post-prefix columns are never loaded into the feature frame.
- A case with fewer than k events, or with a decision event inside the first k, is not scored at that landmark. It is counted in the flow as "ended or decided before landmark".
- Padding with future events or a "missing" token would hide a censored-by-outcome mechanism, so it is not used.

**Elapsed-time prefixes.**
- The prefix includes events with timestamp  start +  (24 h, 72 h).
- Every case that is still alive has a prefix, even if it is in a wait state. Time-in-state is a feature.
- Events with the same timestamp as the landmark are included only if ordering is reliable. Otherwise use a strict <.
- Use the timestamp, not the calendar day, which fixes the nightly snapshot problem.

**Short cases.** They are reported as competing events before the landmark and appear in the multi-state analysis. This is not a silent filter.

**Document loops.**
- Repeated Request Documents / Credit Review loops are legitimate process content.
- Because a k-event prefix can land inside a loop, run both the raw k-event prefix and a "milestone" prefix (first Credit Review entry). Add loop count and loop duration so that deep loops are a feature, not a prefix-length artefact.
- Near-duplicate loop events are not removed unless they are within the duplicate tolerance and from the migration system.

**Activity renaming.** A versioned mapping table is applied to both training and scoring. Unmapped activity names raise an error instead of passing through. A replay test applies the new names to pre-migration data to confirm that features are invariant.

## 5. Process-aware features

**A. Static case attributes (known at start).** Channel, region, log requested amount, source system, partner flag, start hour and weekday.

**B. Prefix-derived features (computed only from events  prediction time).**
- *Control flow:* last activity, activity counts, variant id or bag of directly-follows pairs, whether the variant is seen in training (unseen-path flag), number of Request Documents events, number of Credit Review entries, rework indicator.
- *Timing:* elapsed time from start, KYC duration, waiting time before first Credit Review, time since the last event, inter-event times, and the time-of-day/weekday of each event.
- *Risk score:* the value as-of the prediction time, the first value, the number of updates, and the change since the first value.
- *Resource and queue:* the resource id of the handling steps (grouped or hashed to avoid memorising individuals), the number of cases currently open in Credit Review at the prediction time, the resource's workload (events handled in the last 24 h), and **experience reconstructed as-of** (prior event count of that resource, time since the resource's first observed event).

**C. Historical reference features (need a reference period and are fit on the training fold only).**
- Directly-follows graph and transition probabilities from training prefixes, and variant frequencies.
- Typical activity durations by channel, for normalising timing.
- Conformance deviation against a reference model discovered on training data.
- Historical default rates by channel/region/month, computed only from cases whose labels were known at the prediction time.
- Resource historical document-request rates.

**D. Cohort and calendar features.** Start week or month (with care), a regime indicator (pre/post 1 Jul 2025), a source-system version indicator (pre/post migration), queue or seasonal load, and the month of year. Regime and system indicators cannot be learned for regimes without labels. They are monitoring covariates, and the model must be evaluated with them removed as well.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final credit decision, so it encodes Accept and the lender's own risk assessment | Not available at the landmark | **Drop** | The decision outcome and the limit encode information after the prediction point |
| `decision_reason` | Set at or after Accept/Reject, a direct outcome proxy | Not available at the landmark | **Drop** | Post-landmark information that also separates rejected from accepted |
| `collection_status` | Updated after activation and can reveal default directly | Not available at the landmark | **Drop** | Target leakage |
| `default_90d` (repeated on events) | The label is repeated on earlier events and can be back-filled | Only as the label, only when `label_available_at  as-of` | **Repair**: mask to the as-of time and use only as target | Otherwise labels leak into features or training as of too early a date |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded, and decision events) | Post-prefix information, outcome-defining | Only events with timestamp  prediction time | **Drop** from features | Prefix cutting removes them. A case with a decision inside the prefix is ineligible. |
| `documents_total` | A nightly snapshot can include uploads later the same day | Only if re-derived from events  prediction time | **Repair** (recompute from timestamped events) or **drop** | Snapshot granularity is coarser than the prediction time |
| Updated `risk_score` | Later updates may incorporate post-landmark information or decision-stage scoring | The latest value with timestamp  prediction time | **Repair** (as-of value, plus first value and update count) | The value as-of the prediction time is legitimate, the final value is not |
| Resource experience | Stored as experience at extraction time, so it contains future activity | Reconstructed from events before the prediction time | **Repair** (recompute as prior event count) or **drop** | The extraction-time value leaks future workload |
| `label_available_at` / label availability | Determines which rows are labelled (selection), and is a post-outcome field | Only for deciding row eligibility and as-of masking | **Keep for pipeline control**, **drop from features** | As a feature, it reveals whether and when a label arrived |
| `data_extract_time` | Constant or extraction-specific, enables time leakage | Not used | **Drop** | No legitimate predictive meaning |
| `source_system`, partner flag | Legitimate at start, but migration and partner mix shift | Known at start | **Keep**, monitored | Also needed for the missing-feed weight model |
| `case:requested_amount`, `channel`, `region` | Region can proxy for protected groups. Policy-relevant. | Known at start | **Keep** with subgroup and fairness review | Legitimate but needs review |
| Renamed or duplicated activities | Duplicates distort counts and k-event prefixes after 15 Oct | Canonical names and de-duplicated | **Repair** | Otherwise "event 3" means different things before and after migration |

## 7. Validation design

**Why a random case split is misleading.**
- It mixes the pre- and post-policy regimes, so the model sees the same prefixes with a different selection and outcome relationship on both sides.
- It mixes migration regimes and lets duplicates and renamed activities land on both sides.
- It lets label maturity leak: labelled cases are older, and training rows can be newer than test rows.
- It lets training on future data inform past predictions, including calendar and queue effects.
- It puts re-entries of transferred cases and repeat applicants on both sides.
- It ignores that post-migration cases are almost entirely unlabelled.

It therefore gives optimistic performance and hides the regime shift. `pm4py.split_train_test` is at most a convenience baseline.

**Primary scheme: rolling-origin backtest with as-of labels.**
For each origin T:
- Training uses cases started before T whose labels are visible at T, with a 35-day embargo.
- Test uses cases started in [T, T+3 months), with labels as they finally mature.
- Weights are re-estimated using only information known at T.

| Fold | Origin | Purpose |
|---|---|---|
| B1 | 1 Jan 2025 | Stability in the old regime |
| B2 | 1 Apr 2025 | Old regime, with more training data |
| B3 | 1 Jul 2025 | **Policy shift.** The model trained pre-policy is tested on the first post-policy cohort (starts 1 Jul to about mid-Sep 2025, limited by maturity) |
| Final | Locked test | The post-policy cohort, evaluated once after the design is fixed |
| Prospective | 2026 | Post-migration cases evaluated as labels mature (Oct–Dec 2025 starts), which is the only way to validate behaviour after the migration |

Report the number of labelled and weighted cases per fold and the resulting confidence-interval widths. Small post-policy folds are expected, and they are reported openly.

**Policy change.** Evaluate pre and post separately, fit a model with and without the regime indicator, and test refit or recalibration using only early post-policy labels. Check the activation rate by risk-score band before and after.

**System migration.**
- A replay test maps renamed activities onto pre-migration data and compares features.
- Compare duplicate rates and feature drift (PSI) before and after 15 Oct.
- Outcome validation after the migration is impossible until labels mature.
- Monitor score distribution and calibration-in-the-large as labels arrive.

**Label maturity.** All metrics are computed on cases with complete follow-up, with weights. A nowcast view compares early and late mature cohorts. The survival version with censoring uses the recent activations.

**Metrics.**
- *Discrimination:* weighted AUROC and PR-AUC (prevalence is about 12.5% and varies by regime).
- *Probabilistic quality:* Brier score, log loss.
- *Calibration:* intercept and slope, reliability curves, expected calibration error, per regime and per subgroup. Calibration matters more than AUC because scores would be read as probabilities.
- *Operational:* capture at the top 5–10% of scores for a given review capacity.
- *Time-to-event version:* time-dependent AUC at 90 days, the IPCW Brier score, and calibration of cumulative incidence.
- *Uncertainty:* block-bootstrap (by start week) confidence intervals, weighted conformal or time-ordered conformal prediction with coverage checks, and abstention or flagging for out-of-support prefixes (low overlap or unseen variants).
- *Sensitivity:* every headline metric recomputed under the tipping-point scenarios.

**Subgroups.** Channel, region, partner versus direct, amount band, risk-score band, source system, regime, and the labelled versus overdue-missing split. Report sample sizes, calibration, and error rates, and mark groups too small for conclusions. Region and similar attributes need a fairness review.

**Distribution shift.** PSI or classifier-based two-sample tests on features over time, alarms when overlap or the weight distribution degrades, and scheduled recalibration.

## 8. Limitations and decision-use boundary

**What the study can claim.**
- Predictive association: among applications that are activated under the current policy, prefix features are associated with 90-day default, with calibrated probabilities where the stated assumptions hold.
- The error of such predictions in the regimes and periods validated.
- The all-application multi-state decomposition (who is activated and how risk splits), under the current policy.

**What it cannot claim.**
- The default risk of rejected, withdrawn, transferred, or open applications. These are undefined or unobserved, not non-default.
- That the score is the risk of "every application". The lender's original wording must be corrected.
- Causal or counterfactual statements ("what would default be if this applicant were accepted or the threshold lowered") without the stronger assumptions above, which are not identified here.
- Performance after the migration until labels mature.
- Correction for feed missingness beyond what covariates and the audit sample allow.

**Three selection and causal distinctions.**
- *Predictive association* is what the model estimates, conditional on activation.
- *Selection effects*: the activated population is chosen by policy and applicant behaviour, so feature effects can be distorted (for example, a high risk score may look harmless because only the best high-score cases were accepted).
- *Counterfactual default risk* requires modelling the un-activated, which these data do not support.

**Ways deployment could change the data-generating process.**
1. **Decline feedback.** If the score is used to reject or down-limit applicants, the labelled population shrinks and shifts. Outcomes for declined cases will never be seen, which creates self-reinforcing selection.
2. **Intervention effects.** Extra monitoring, lower limits, or early collections outreach change the default probability, so post-deployment labels no longer measure the untreated risk.
3. **Behavioural adaptation.** Underwriters may change document-request behaviour or loop patterns, and applicants may withdraw, switch channels, or game inputs, changing the prefix distribution.
4. **Policy and partner changes.** Threshold retuning, new partners, or changes in feed coverage alter selection and missingness.
5. **Process changes.** New systems or activity names alter prefix semantics.

Recommended use: advisory prioritisation and monitoring, with a randomised holdout or a small exploration policy to keep the feedback loop observable, and scheduled recalibration. Not for automated rejection.

## 9. PM4Py-oriented Python implementation skeleton

```python
import numpy as np
import pandas as pd
import pm4py

CASE, ACT, TS = "case:concept:name", "concept:name", "time:timestamp"
EXTRACT = pd.Timestamp("2026-02-15", tz="UTC")
ASOF = EXTRACT                                   # set to an earlier origin T for backtests
HORIZON, FEED_LAG_MAX = pd.Timedelta(days=90), pd.Timedelta(days=35)
DUP_TOL = pd.Timedelta(seconds=2)
POLICY_DATE = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION_DATE = pd.Timestamp("2025-10-15", tz="UTC")
K = 3                                            # Start, KYC, first Credit Review
RENAME = {"KYC Check": "Identity/KYC Check", "Doc Request": "Request Documents"}  # ASSUMPTION: versioned map
FUTURE_ACTS = {"Contract Signed", "Account Activated", "Collections Contact", "Default Recorded"}
DECISION_ACTS = {"Accepted", "Rejected", "Withdrawn", "Transferred"}
ALLOWED = [CASE, ACT, TS, "org:resource", "case:channel", "case:region",
           "case:requested_amount", "risk_score"]            # allowlist: nothing else reaches features
FORBIDDEN = {"final_limit", "decision_reason", "collection_status", "default_90d",
             "label_available_at", "documents_total", "data_extract_time", "resource_experience"}

def load_events(path, asof):
    df = pd.read_csv(path, dtype={CASE: str})
    for c in [TS, "label_available_at", "data_extract_time"]:
        df[c] = pd.to_datetime(df[c], utc=True, errors="coerce")
    df = df.dropna(subset=[CASE, ACT, TS])
    df[ACT] = df[ACT].replace(RENAME)                        # rename BEFORE counting events
    df = pm4py.format_dataframe(df, case_id=CASE, activity_key=ACT, timestamp_key=TS)
    df = df.drop_duplicates([CASE, ACT, TS, "org:resource"])
    df = df.sort_values([CASE, TS], kind="mergesort")        # stable sort keeps file order on ties
    gap = df.groupby([CASE, ACT])[TS].diff()
    df = df[~((gap < DUP_TOL) & (df[TS] >= MIGRATION_DATE))]  # near-duplicates from migration only
    df = df[df[TS] <= asof].copy()                           # as-of truncation of events
    late = df["label_available_at"].isna() | (df["label_available_at"] > asof)
    df.loc[late, "default_90d"] = np.nan                     # label invisible before its feed arrives
    return df.reset_index(drop=True)

def build_case_table(ev, asof):
    first = ev.groupby([CASE, ACT])[TS].min().unstack()
    g = ev.groupby(CASE)
    c = pd.DataFrame({"start": g[TS].min(), "n_events": g.size(), "label": g["default_90d"].last(),
                      "label_at": g["label_available_at"].max(), "source": g["source_system"].first()})
    for act, col in [("Account Activated", "t_act"), ("Rejected", "t_rej"),
                     ("Withdrawn", "t_wd"), ("Transferred", "t_tr")]:
        c[col] = first[act] if act in first else pd.NaT
    c["outcome"] = np.select([c.t_act.notna(), c.t_rej.notna(), c.t_wd.notna(), c.t_tr.notna()],
                             ["activated", "rejected", "withdrawn", "transferred"], default="open")
    act = c.outcome.eq("activated")
    mature = c.t_act + HORIZON + FEED_LAG_MAX
    c["label_state"] = np.select([act & c.label.notna(), act & (mature > asof), act],
                                 ["labeled", "pending_not_mature", "overdue_possible_permanent_missing"],
                                 default="undefined_not_activated")   # NEVER coded as default = 0
    return c

def temporal_split(c, train_end, valid_end, test_end):
    c = c.copy()
    c["split"] = np.select([c.start < train_end, c.start < valid_end, c.start < test_end],
                           ["train", "valid", "test"], default="monitor_only_unlabeled")
    c["regime"] = np.where(c.start < POLICY_DATE, "pre_policy", "post_policy")
    c["sys"] = np.where(c.start < MIGRATION_DATE, "legacy", "migrated")
    # embargo: a training label must be visible when the first validation prediction is made
    c["train_ok"] = (c.split == "train") & c.label.notna() & (c.label_at <= train_end)
    return c

def make_prefixes(ev, k):
    ev = ev[ALLOWED].sort_values([CASE, TS], kind="mergesort").copy()   # post-prefix columns never enter
    ev["pos"] = ev.groupby(CASE).cumcount()
    ev["res_prior_events"] = ev.sort_values(TS, kind="mergesort").groupby(
        "org:resource", dropna=False).cumcount()                        # as-of experience, not extract-time
    pre = ev[ev.pos < k]
    full = pre.groupby(CASE).size().eq(k)                               # short cases are not padded
    bad = pre.loc[pre[ACT].isin(FUTURE_ACTS | DECISION_ACTS), CASE].unique()
    pre = pre[pre[CASE].isin(full[full].index.difference(bad))]
    out = pm4py.get_prefixes_from_log(pre, k, case_id_key=CASE)         # verify behaviour on your pm4py version
    assert out.groupby(CASE).size().max() <= k
    return out

def time_prefix(ev, delta=pd.Timedelta(hours=24)):                      # elapsed-time landmark
    t0 = ev.groupby(CASE)[TS].transform("min")
    return ev[ev[TS] <= t0 + delta]

def prefix_features(pre):
    g = pre.groupby(CASE)
    f = pd.DataFrame({"t0": g[TS].min(), "pred_time": g[TS].max(),
                      "risk_score_asof": g["risk_score"].last(), "n_risk_updates": g["risk_score"].nunique(),
                      "n_doc_requests": g[ACT].apply(lambda s: int((s == "Request Documents").sum())),
                      "res_prior_events": g["res_prior_events"].last(),
                      "channel": g["case:channel"].first(), "region": g["case:region"].first(),
                      "log_amount": np.log1p(g["case:requested_amount"].first()),
                      "variant": g[ACT].agg(tuple)})
    f["elapsed_h"] = (f.pred_time - f.t0).dt.total_seconds() / 3600
    return f

def leakage_audit(feats, pre):
    assert not (set(feats.columns) & FORBIDDEN), "forbidden column in feature table"
    assert not pre[ACT].isin(FUTURE_ACTS | DECISION_ACTS).any(), "future/decision event in prefix"
    assert (pre[TS] <= pre[CASE].map(feats["pred_time"])).all(), "event after prediction time"

if __name__ == "__main__":
    ev = load_events("applications_events.csv", ASOF)
    cases = build_case_table(ev, ASOF)
    cases = temporal_split(cases, *[pd.Timestamp(d, tz="UTC") for d in ("2025-04-01", "2025-07-01", "2025-09-16")])
    flow = cases.groupby(["outcome", "label_state"]).size()             # cohort-flow counts
    print(flow); assert flow.sum() == len(cases)                        # expect 48,000
    pre = make_prefixes(ev, K)
    feats = prefix_features(pre).join(cases[["split", "regime", "sys", "train_ok", "label", "label_state"]])
    leakage_audit(feats.drop(columns=["split", "regime", "sys", "train_ok", "label", "label_state"]), pre)
    print("ended/decided before landmark:", len(cases.index.difference(feats.index)))
    # Reference structures use TRAINING prefixes only (historical reference features)
    tr_ids = feats.index[feats.train_ok]
    tr_pre = pre[pre[CASE].isin(tr_ids)]
    dfg, starts, ends = pm4py.discover_dfg(tr_pre)
    seen = set(pm4py.get_variants(tr_pre))
    feats["unseen_variant"] = ~feats["variant"].map(lambda v: v in seen)
    # extract_temporal_features_dataframe / insert_case_service_waiting_time are deliberately NOT used:
    # the first aggregates windows that include future events, the second needs start/complete lifecycle data.
    # HOOK 1: P(label observed | X, channel, source, amount, activation month) on activated cases
    #         -> weights = 1/p_obs (clipped) for the primary binary model (labeled rows only).
    # HOOK 2: discrete-time hazard / competing-risk model on cases[["start","t_act","t_rej","t_wd","t_tr"]],
    #         follow-up censored at min(t_act + 90d, ASOF - 35d), open cases censored at ASOF.
    # HOOK 3: tipping-point sensitivity re-weights 'overdue_possible_permanent_missing' rows by delta.
    print(feats[feats.split == "test"].groupby(["regime", "label_state"]).size())
```
