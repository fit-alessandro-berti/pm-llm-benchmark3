## 1. Analytical assumptions

### Case Notion, Convergence, and Divergence
In classical process mining, a **case notion** is an atomic projection mechanism that maps every event in a log to exactly one entity instance (a case identifier). This partitions the event log into disjoint, totally ordered sequences (traces), operating under the foundational assumption that each case executes as an independent, isolated instance of the process. In Object-Centric Event Logs (OCEL 2.0), this assumption is recognized as an artificial construct: real-world business executions do not evolve along a single dimension, but across a network of interacting entities of diverse types participating in many-to-many (M:N) relationships.

When an OCEL is flattened onto a single candidate object type $T_{target}$, two structural distortions systematically arise:
- **Convergence (Many-to-One / Many-to-Many upstream-to-downstream mapping):** Convergence occurs when multiple instances of an upstream object type relate to a single downstream event or object instance (e.g., multiple Orders bundled into a single Package, or multiple Packages carried by a single Delivery). During flattening on the upstream object type, the single shared event is replicated across every related upstream case trace. In Directed Follows Graphs (DFGs) and Petri nets, convergence causes artificial activity frequency inflation, fictitious parallel branch synchronization, and spurious cyclic dependencies.
- **Divergence (One-to-Many upstream-to-downstream mapping):** Divergence occurs when a single upstream object instance splits into multiple downstream object instances or events (e.g., an Order splitting across multiple Packages, or an Invoice settled via multiple partial Payment instalments). During flattening on the upstream object type, multiple downstream events of the same activity type appear sequentially or interleaved within a single case trace. In discovered process models, divergence manifests as artificial self-loops, spurious concurrency permutations, and severe throughput-time distortion.

### Treatment of Copied Shared Events
Copied shared events are treated under a dual analytical interpretation:
1. **Empirical Evidence of Multi-Object Collaboration:** Domain-wise, shared events provide direct behavioral evidence of operational batching, logistics consolidation, and shared financial settlements (e.g., joint packaging in $P_3$, consolidated transit in $D_2$, and combined invoicing in $V_2$).
2. **Technical Duplication and Statistical Distortion:** Computationally, when projected onto a traditional single-case log, copied events represent artificial duplication. They violate the independent-and-identically-distributed (i.i.d.) assumptions of statistical process mining, inflate event counts, distort transition probabilities, and bias queueing and waiting time measurements.

### Permitted Analytical Transformations and Relation Propagation
In raw OCEL 2.0, Event-to-Object (E2O) relations represent direct event participation. Without transformation, flattening on an object type extracts only events where that specific object is explicitly listed in the E2O relation set. 

We distinguish between two operational transformation models:
- **Strict Direct E2O Flattening (Default Baseline):** An event $e$ belongs to trace $\sigma_o$ if and only if $o \in \pi_{E2O}(e)$. Under direct E2O, child entities like `Item` or `Package` omit administrative events like `Create Order` ($e_{01}$–$e_{04}$) and `Close Order` ($e_{28}$–$e_{31}$).
- **Propagated / Transitive E2O Flattening (Analytical Sensitivity Variant):** An event $e$ is associated with object $o$ if there exists a directed or undirected path between $o$ and some $o' \in \pi_{E2O}(e)$ in the Object-to-Object (O2O) relational graph (e.g., propagating `Create Order` from $O_1$ to $I_{11}$ and $I_{12}$ via $O_1 \xrightarrow{\text{contains}} I_{11}, I_{12}$). While propagation recovers lifecycle boundaries for subordinate objects, it multiplies convergence and divergence replication across all related entities.

All primary evaluations in Sections 2–5 adhere strictly to the raw, unpropagated E2O relations given in the benchmark snapshot, while relation propagation is evaluated explicitly as an analytical sensitivity check in Section 7.

## 3. Concrete distortion analysis

### 1. Cross-Order Package: Spurious Sequential Packing Self-Loop in Order $O_3$
- **Affected Flattening:** Order ($O_3$).
- **Specific Objects and Events:** Order $O_3$, Packages $P_3$ and $P_4$, Items $I_{31}$ and $I_{32}$; events $e_{13}$ (`Pack Package` $P_3$ with $O_2, O_3, I_{21}, I_{31}$ at 10:12) and $e_{14}$ (`Pack Package` $P_4$ with $O_3, O_4, I_{32}, I_{41}$ at 10:20).
- **Resulting Distortion:** In the flattened trace for $O_3$, two sequential `Pack Package` events occur ($e_{13} \rightarrow e_{14}$). This produces an artificial `Pack Package -> Pack Package` self-loop edge in the Order DFG. In a discovered Petri net or BPMN model, this induces an apparent rework loop or iterative packaging cycle. In reality, $O_3$ never underwent repetitive packing; its two items ($I_{31}$ and $I_{32}$) were packed concurrently or independently into two separate parcels ($P_3$ and $P_4$) to facilitate cross-order batching with $O_2$ and $O_4$.
- **Classification:** **Harmful** for control-flow discovery (falsely signals procedural rework); **Context-dependent** for customer milestone monitoring (correctly signals that $O_3$ required multiple packaging completions before fulfillment).

### 2. Cross-Order Package: Fictitious Temporal Coupling between Unrelated Orders $O_2$ and $O_4$ via $O_3$
- **Affected Flattening:** Order ($O_2, O_3, O_4$).
- **Specific Objects and Events:** Orders $O_2, O_3, O_4$; Packages $P_3, P_4$; Items $I_{21}, I_{31}, I_{32}, I_{41}$; events $e_{07}$ (09:20), $e_{08}$ (09:22), $e_{09}$ (09:23), $e_{10}$ (09:25), $e_{13}$ (10:12), $e_{14}$ (10:20), $e_{16}$ (11:05), $e_{17}$ (11:15).
- **Resulting Distortion:** $P_3$ links $O_2$ and $O_3$; $P_4$ links $O_3$ and $O_4$. In the Order-flattened view, $O_3$'s lead time from `Add Item` to `Dispatch` spans from 09:22 to 11:15 (1h 53m) because $O_3$ must wait for both $P_3$ (packed at 10:12) and $P_4$ (packed at 10:20). Because $P_4$ contains $I_{41}$ from $O_4$, $O_3$'s dispatch via $D_3$ ($e_{17}$) is causally constrained by $O_4$'s picking schedule. Traditional performance mining attributes this entire delay to $O_3$'s internal processing inefficiency, confounding warehouse batch-scheduling constraints with order-specific performance.
- **Classification:** **Harmful.** Masks root-cause bottlenecks by entangling the performance metrics of independent customer orders.

### 3. Consolidated Delivery: Frequency Triplication and Variant Explosion in Delivery $D_2$
- **Affected Flattening:** Order ($O_1, O_2, O_3$).
- **Specific Objects and Events:** Delivery $D_2$, Packages $P_2, P_3$, Orders $O_1, O_2, O_3$; events $e_{16}$ (`Dispatch` $D_2$ at 11:05) and $e_{24}$ (`Confirm Delivery` $D_2$ at 16:00).
- **Resulting Distortion:** $D_2$ consolidates $P_2$ (from $O_1$) and $P_3$ (from $O_2, O_3$). In the real world, $D_2$ was dispatched once ($e_{16}$) and confirmed once ($e_{24}$). Flattening on Order copies $e_{16}$ and $e_{24}$ into $O_1, O_2$, and $O_3$, inflating the perceived execution frequency of dispatch and delivery confirmation by 200% (3 instances each). Furthermore, in $O_1$, $e_{16}$ follows $e_{15}$ (`Dispatch` $D_1$), generating a `Dispatch -> Dispatch` edge and a `Confirm Delivery -> Confirm Delivery` edge ($e_{23} \rightarrow e_{24}$). In $O_2$, only a single dispatch and delivery appear. In $O_3$, $e_{16}$ is followed by $e_{17}$ (`Dispatch` $D_3$). This fragments identical delivery operations into three distinct, complex trace variants.
- **Classification:** **Harmful.** Grossly overcounts transportation workload in business reporting and fragments trace variant analysis into spurious permutations.

### 4. Consolidated Invoicing: Temporal Interleaving and Bidirectional DFG Cycles
- **Affected Flattening:** Order ($O_2, O_3$).
- **Specific Objects and Events:** Invoice $V_2$, Orders $O_2, O_3$, Deliveries $D_2, D_3$; events $e_{19}$ (`Issue Invoice` at 12:05), $e_{22}$ (`Record Payment` at 12:40), $e_{24}$ (`Confirm Delivery` $D_2$ at 16:00), $e_{25}$ (`Record Payment` at Feb 4 09:00), $e_{27}$ (`Confirm Delivery` $D_3$ at Feb 4 10:00).
- **Resulting Distortion:** $V_2$ consolidates billing for $O_2$ and $O_3$. In $O_2$, `Confirm Delivery` ($e_{24}$ at 16:00) occurs *before* final payment `Record Payment` ($e_{25}$ at Feb 4 09:00), producing the path `Confirm Delivery -> Record Payment`. In $O_3$, final delivery confirmation $D_3$ ($e_{27}$ at Feb 4 10:00) occurs *after* $e_{25}$, producing the path `Record Payment -> Confirm Delivery`. In the aggregated Order DFG, this creates a bidirectional cycle (`Confirm Delivery <-> Record Payment`). An analyst mining conformance would infer an uncontrolled, non-deterministic process where billing and delivery have no standard sequence.
- **Classification:** **Harmful** for standard workflow conformance checking; **Context-dependent** for accounting audit (reveals that consolidated billing decouples invoicing cadences from physical deliveries).

### 5. Partial Payments: Self-Loops and Order-to-Cash Duration Distortion
- **Affected Flattening:** Invoice ($V_2$) and Order ($O_2, O_3$).
- **Specific Objects and Events:** Invoice $V_2$, Payments $M_2, M_3$, Orders $O_2, O_3$; events $e_{19}$ (`Issue Invoice` at Feb 3 12:05), $e_{22}$ (`Record Payment` $M_2$ at Feb 3 12:40), $e_{25}$ (`Record Payment` $M_3$ at Feb 4 09:00).
- **Resulting Distortion:** Invoice $V_2$ is settled across two instalments: partial settlement $M_2$ and final settlement $M_3$, spanning 20h 20m. In the Invoice DFG, this generates a legitimate `Record Payment -> Record Payment` self-loop. However, when flattened onto Orders $O_2$ and $O_3$, this financial loop is interleaved with physical fulfillment ($e_{24}, e_{27}$). For $O_2$, if an automated metric measures payment latency as the duration from `Issue Invoice` to the first `Record Payment`, it records 35 minutes; if it measures to the second, it records ~21 hours. Flattening obscures which payment cleared which order obligations.
- **Classification:** **Informative** within the Invoice lifecycle (reflects authentic multi-instalment business terms); **Harmful** within the Order lifecycle (creates ambiguous duration metrics and uninterpretable payment loops).

### 6. Near-Singleton Lifecycle: Degenerate Zero-Flow Process Graph in Payment Flattening
- **Affected Flattening:** Payment ($M_1, M_2, M_3, M_4$).
- **Specific Objects and Events:** Payments $M_1, M_2, M_3, M_4$; events $e_{21}, e_{22}, e_{25}, e_{26}$.
- **Resulting Distortion:** Every Payment object participates in exactly one event ($M_1$ in $e_{21}$, $M_2$ in $e_{22}$, $M_3$ in $e_{25}$, $M_4$ in $e_{26}$). Flattening on Payment yields four 1-event traces: `[Record Payment]`. The resulting DFG consists of a single isolated node with zero edges, zero transitions, and zero cycle time. 100% of the operational and commercial process (ordering, picking, packing, shipping, invoicing, closure) is eliminated.
- **Classification:** **Harmful** if utilized as a standalone process mining case notion; **Context-dependent** if viewed strictly as an instantaneous transaction log, illustrating that point-in-time financial objects cannot anchor end-to-end process discovery.

### 7. Item Flattening: Severe Lifecycle Truncation and Illusory 100% Process Conformance
- **Affected Flattening:** Item ($I_{11}, I_{12}, I_{21}, I_{31}, I_{32}, I_{41}$).
- **Specific Objects and Events:** Items $I_{11}$–$I_{41}$; omitted events $e_{01}$–$e_{04}$ (`Create Order`), $e_{18}$–$e_{20}$ (`Issue Invoice`), $e_{21}, e_{22}, e_{25}, e_{26}$ (`Record Payment`), $e_{28}$–$e_{31}$ (`Close Order`).
- **Resulting Distortion:** Direct E2O flattening on Item discards 15 of 31 events (48.4%). Every item trace displays an identical 4-event sequence: `[Add Item, Pack Package, Dispatch, Confirm Delivery]`. The resulting DFG exhibits 100% trace fitness, zero deviations, and zero apparent rework. An analyst relying on this view would report perfect operational compliance and high efficiency, entirely unaware of split shipments ($O_1$), cross-order packing synchronization holds ($O_3$), consolidated invoicing ($V_2$), payment delays, and open order dwell times.
- **Classification:** **Harmful** when presented as an end-to-end process evaluation (dangerously misleading illusion of perfection); **Informative** only when strictly confined to shop-floor item routing.

### 8. Delivery Flattening: Upstream Latency Blindness and Carrier Dwell-Time Misattribution
- **Affected Flattening:** Delivery ($D_1, D_2, D_3$).
- **Specific Objects and Events:** Deliveries $D_1, D_2, D_3$; Packages $P_1$–$P_4$; events $e_{15}, e_{16}, e_{17}$ (`Dispatch`) and $e_{23}, e_{24}, e_{27}$ (`Confirm Delivery`).
- **Resulting Distortion:** Delivery flattening reduces the log to 3 traces of length 2 (`[Dispatch, Confirm Delivery]`). Delivery $D_3$ exhibits a transit duration of 22h 45m (Feb 3 11:15 to Feb 4 10:00), compared to 3h for $D_1$ and 4h 55m for $D_2$. In the Delivery DFG, $D_3$ appears as a severe carrier delay bottleneck. However, Delivery flattening hides the upstream cause: $D_3$ carried Package $P_4$, which combined items from $O_3$ and $O_4$, was packed late at 10:20, and was held overnight for scheduled morning delivery. The carrier is blamed for a delay driven by warehouse consolidation.
- **Classification:** **Harmful** for root-cause operational bottleneck diagnosis; **Informative** strictly for carrier transit SLA compliance.

## 4. Traditional versus object-centric analysis portfolio

### Recommended Flattened Logs and Safe Scopes
1. **Order-Flattened Log:**
   - *Safe Scope:* Customer-facing order fulfillment lead time (from `Create Order` to `Close Order`), customer order milestone status tracking, customer SLA reporting, and order cancellation/closure auditing.
   - *Prohibited Scope:* Carrier workload calculation, warehouse packaging station capacity planning, and accounts receivable reconciliation.
2. **Item-Flattened Log:**
   - *Safe Scope:* Physical SKU custody tracking, picking-to-packing routing compliance, warehouse station handling times, and unit-level loss/damage investigation.
   - *Prohibited Scope:* End-to-end process discovery, order-to-cash analysis, and commercial compliance.
3. **Package-Flattened Log:**
   - *Safe Scope:* Packaging station throughput, parcel dwell times in staging areas, and parcel-to-carrier handoff efficiency.
   - *Prohibited Scope:* Customer order fulfillment assessment and financial invoice tracking.
4. **Delivery-Flattened Log:**
   - *Safe Scope:* Carrier transit SLA enforcement, route transit duration, and courier turnaround time.
   - *Prohibited Scope:* Upstream warehouse efficiency and customer fulfillment lead time.
5. **Invoice-Flattened Log:**
   - *Safe Scope:* Accounts receivable management, Days Sales Outstanding (DSO), billing-to-payment collection cycle time, and multi-instalment payment tracking.
   - *Prohibited Scope:* Warehouse operations, shipping execution, and physical inventory flows.
6. **Payment-Flattened Log:**
   - *Recommendation:* Do not create a flattened trace log. Maintain Payment as a transactional ledger / dimensional reference table.

### Analytical Questions Requiring Object-Centric Artifacts
- **True Physical and Administrative Execution Frequencies (OC-DFG):** Determining exact activity execution volumes without convergence inflation (e.g., verifying that `Dispatch` executed exactly 3 times across the fleet, touching 4 orders, 6 items, 4 packages, and 3 deliveries).
- **Relational System Architecture (Object Type Graph - OTG):** Visualizing 1:N, N:1, and M:N coupling across business domains (e.g., $O \xrightarrow{1:N} I$, $P \xrightarrow{N:M} I$, $D \xrightarrow{1:N} P$, $V \xrightarrow{N:1} O$, $V \xrightarrow{1:N} M$).
- **Cross-Functional Activity Coupling (Event Type - Object Type Graph - ET-OT):** Revealing organizational handoffs where an activity bridges multiple silos (e.g., `Dispatch` simultaneously binding Order, Item, Package, and Delivery; `Issue Invoice` binding Order and Invoice).
- **Consolidation and Batching Ratios (`ocel_objects_interactions_summary`):** Quantifying supply chain economies of scale, such as items per package (average 1.5), packages per delivery (average 1.33), orders per package (average 1.5), and orders per invoice (average 1.33).
- **Multi-Object Execution Pattern Discovery (`cluster_equivalent_ocel`):** Grouping structurally identical multi-object process executions without generating artificial trace permutations caused by concurrent independent lifecycles.

### Reconciliation Framework for Contradictory Findings
When flattened and object-centric metrics diverge, apply the following three reconciliation rules:
1. **Frequency Reconciliation Rule:** When flattened activity counts exceed raw log counts, calculate the Multi-Object Multiplicity Factor:
   $$M(a) = \frac{N_{\text{flattened}}(a)}{N_{\text{OCEL}}(a)}$$
   The OC-DFG count $N_{\text{OCEL}}(a)$ represents physical execution ground truth; the flattened count $N_{\text{flattened}}(a)$ represents the total object touch count.
2. **Duration and Bottleneck Decomposition Rule:** When a flattened trace indicates high waiting time between two activities (e.g., $O_3$ waiting between `Add Item` and `Dispatch`), project the execution onto the OC-DFG and ET-OT graph to decompose the total latency into:
   - *Intrinsic processing duration* of individual items;
   - *Synchronization dwell time* waiting for sibling items in batch packaging ($P_4$ waiting for $I_{41}$);
   - *Consolidation transit delay* waiting for multi-package carrier dispatch ($D_3$).
3. **Variant Complexity Decomposition Rule:** When a flattened log exhibits a high number of trace variants (e.g., 3 distinct variants across 4 orders), evaluate the OTG to verify whether variance is driven by true procedural deviations or by asynchronous concurrency between decoupled sub-processes (e.g., invoicing occurring in parallel with physical transit).

## 5. Lead-object decision

### Chosen Position
**C. Reject a single lead object for this process.**

### Structured Argument

#### 1. Decision Criteria
- **Relational Topology:** The process exhibits pervasive Many-to-Many (M:N) and One-to-Many (1:N) relationships across both physical and financial domains (Orders split across Packages; Packages combine items from multiple Orders; Deliveries carry multiple Packages; Invoices bundle multiple Orders; Invoices split across multiple Payments).
- **Lifecycle Asynchrony / Orthogonality:** Physical logistics (Item $\rightarrow$ Package $\rightarrow$ Delivery) and financial settlement (Invoice $\rightarrow$ Payment) operate on completely decoupled, asynchronous operational cadences.
- **Information Loss and Distortion Threshold:** Selecting any single candidate object type forces either the omission of >30% of critical business events or the artificial duplication of >25% of shared events, generating severe DFG self-loops and false causal dependencies.

#### 2. Strongest Supporting Evidence
- **Physical Fulfillment Domain:** $O_1$ splits into $P_1$ and $P_2$ (1:N divergence); $P_3$ consolidates items from $O_2$ and $O_3$ (N:1 convergence); $P_4$ consolidates items from $O_3$ and $O_4$ (N:1 convergence); $D_2$ consolidates $P_2$ and $P_3$ across three orders (N:1 convergence). If `Order` is chosen as lead, transportation workload is inflated by 200% and spurious packing self-loops appear. If `Item` or `Package` is chosen, all commercial order creation, invoicing, payment, and closure events (15 of 31 events) are discarded.
- **Financial Settlement Domain:** $V_2$ consolidates billing for $O_2$ and $O_3$ (N:1 convergence) and is settled via two separate payment instalments $M_2$ and $M_3$ (1:N divergence). If `Order` is chosen as lead, payment timing is entangled across unrelated orders. If `Invoice` is chosen, all physical fulfillment is lost.
- **Mathematical Irreducibility:** No single object type can project both the physical fulfillment graph and the financial settlement graph without introducing fatal structural distortions.

#### 3. Strongest Counterargument
- **Enterprise Cognitive and Architectural Alignment:** In enterprise ERP systems (e.g., SAP, Salesforce), executive management, sales compensation, and customer service operate strictly around "The Customer Order" as the foundational commercial unit of account. Rejecting an Order-centric view introduces cognitive friction for business stakeholders and breaks compatibility with traditional single-case process mining tools that demand a single Case ID.

#### 4. Residual Risk
- **Tooling and Skill Adoption Barriers:** Object-centric process mining algorithms (OC-DFG, OC-PN) require specialized software (PM4Py OCEL 2.0 / modern OCPM platforms) and greater analytical maturity from business analysts compared to traditional trace-based dashboards.

#### 5. Conditions Under Which the Decision Would Change
We would abandon Position C and adopt an alternative position if:
- **Condition for Position B (Primary Lead + Secondary Lifecycles):** The enterprise enforces strict business rules eliminating cross-order consolidation (e.g., strict 1:1:1:1 mapping where each order has exactly one package and one invoice, restricting M:N batching to <2% exception handling).
- **Condition for Position A (Single Lead Object):** The analytical mandate is strictly circumscribed to an isolated functional silo (e.g., an audit strictly evaluating carrier transit SLA compliance, where `Delivery` is the sole relevant object).

## 7. Sensitivity and validation plan

### 1. Fractional Event Down-Weighting Scheme for Shared Events
- **Methodology:** In any flattened log projected onto target object type $T$, assign each event instance $e$ in trace $\sigma_o$ a fractional weight inversely proportional to the number of co-related objects of that type:
  $$w(e, o) = \frac{1}{|\pi_{E2O}(e) \cap T|}$$
- **Application to Dataset:** In the Order-flattened log, event $e_{16}$ (`Dispatch` $D_2$) is related to $O_1, O_2, O_3$. Each order trace receives weight $w(e_{16}, O_i) = \frac{1}{3}$. The weighted activity count for `Dispatch` becomes:
  $$W(\text{Dispatch}) = 1.0 \,(e_{15}) + 3 \times \frac{1}{3} \,(e_{16}) + 2 \times \frac{1}{2} \,(e_{17}) = 1 + 1 + 1 = 3.0$$
- **Validation Objective:** Verify whether aggregated activity volumes, operational costs, and queueing estimates stabilize to physical execution ground truth (3 actual dispatches instead of 8 unweighted instances).

### 2. Direct E2O versus Propagated O2O Relation Flattening
- **Methodology:** Construct an augmented event log $\text{OCEL}_{\text{prop}}$ by computing the transitive closure over O2O relations:
  $$\pi_{E2O}^{\text{prop}}(e) = \pi_{E2O}(e) \cup \{ o \mid \exists o' \in \pi_{E2O}(e) \text{ such that } (o', o) \in \text{O2O}^+ \}$$
  Compare direct Item flattening with propagated Item flattening (where $I_{11}$ inherits $e_{01}$ `Create Order`, $e_{18}$ `Issue Invoice`, $e_{21}$ `Record Payment`, and $e_{28}$ `Close Order`).
- **Application to Dataset:** In direct E2O, Item $I_{11}$ contains 4 events. In propagated E2O, $I_{11}$ expands to 8 events.
- **Validation Objective:** Quantify the trade-off between *semantic completeness* (recovering commercial milestones for child objects) and *trace entanglement* (exponential explosion of convergence/divergence replication across all items in an order).

### 3. Lead-Object Permutation and Cross-Perspective Invariance Testing
- **Methodology:** Systematically permute the candidate lead object across all 5 viable types (`Order`, `Item`, `Package`, `Delivery`, `Invoice`) and evaluate performance metrics for perspective invariance:
  $$\Delta_{\text{metric}}(T_1, T_2) = |\text{Metric}_{T_1} - \text{Metric}_{T_2}|$$
- **Application to Dataset:** Measure carrier transit duration under Delivery flattening ($D_1$: 3.0h, $D_2$: 4.9h, $D_3$: 22.75h) versus perceived order fulfillment transit under Order flattening ($O_1$: 5.0h, $O_3$: 22.9h).
- **Validation Objective:** Expose perspective bias and distinguish *perspective-invariant operational facts* (actual vehicle movement) from *projection artifacts* (order-level batching latency).

### 4. Tri-Metric Frequency Comparison in the OC-DFG
- **Methodology:** For every activity node $a$ and edge $(a_1, a_2)$ in the OC-DFG, simultaneously compute and display three distinct frequency metrics:
  1. **Event Execution Count ($N_{\text{events}}$):** The number of distinct event executions ($|E_a|$).
  2. **Unique Object Count ($N_{\text{objects}}$):** The number of distinct physical/commercial entity IDs participating ($|\bigcup_{e \in E_a} (\pi_{E2O}(e) \cap T)|$).
  3. **Total Object Interaction Count ($N_{\text{interactions}}$):** The total sum of object-event bindings ($\sum_{e \in E_a} |\pi_{E2O}(e) \cap T|$).
- **Application to Dataset:** For activity `Dispatch`:
  - $N_{\text{events}} = 3$ ($e_{15}, e_{16}, e_{17}$);
  - $N_{\text{objects}}(\text{Order}) = 4$ ($O_1, O_2, O_3, O_4$);
  - $N_{\text{interactions}}(\text{Order}) = 6$ ($O_1$ in $e_{15}, e_{16}$; $O_2$ in $e_{16}$; $O_3$ in $e_{16}, e_{17}$; $O_4$ in $e_{17}$).
- **Validation Objective:** Directly measure the Batching Multiplicity Ratio ($\frac{N_{\text{interactions}}}{N_{\text{events}}} = \frac{6}{3} = 2.0$ orders/dispatch) and expose multi-object economies of scale without generating distorted flattened graphs.
