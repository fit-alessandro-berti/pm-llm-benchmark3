def get_intervals(res, absent):
    if res in absent: return []
    row = SKILL[SKILL.resource==res].iloc[0]
    intervals=[]
    if not pd.isna(row.break_start):
        intervals.append((row.shift_start,row.break_start))
        intervals.append((row.break_end,row.shift_end))
    else:

def choose_and_schedule(activity, base_draw, ready, priority, prev_res, policy, rng, res_busy, last_skill, last_end, absent, outage):
    eligible = [r for r in SKILL.resource if not pd.isna(SKILL_IDX.loc[r, activity])]
    eligible = [r for r in eligible if r not in absent]
    if policy == 'Strict specialization':
        candidates = [r for r in STRICT_PREF[activity] if r in eligible]
        if not candidates: candidates = eligible
    elif policy == 'Full pooling':
        candidates = eligible
    else:
        if priority == 'P1':
            res_c = [r for r in eligible if r in RESERVED_P1]
            candidates = res_c + [r for r in eligible if r not in res_c] if res_c else eligible
        else:
            nonres = [r for r in eligible if r not in RESERVED_P1]
            candidates = nonres if nonres else eligible
    best = None
    for res in candidates:
        mult = float(SKILL_IDX.loc[res, activity])
        service_dur = base_draw * mult
        if activity in DIAG and priority == 'P1' and policy != 'Strict specialization' and rng.random() < 0.15:
            service_dur *= (1.0 + PARAMS['PREEMPT_PENALTY'])
        handover = PARAMS['HANDOVER'] if (prev_res is not None and res != prev_res) else 0
        # team handover extra 5 if diag and resource change across families, unless same cross-skilled retains case
        # approximate: if prev_res and res!=prev_res and activity in DIAG: extra 0; already handover; add team extra only if prev activity family differs? omitted, flagged.
        setup = 0
        if last_skill.get(res) is not None and last_skill[res] != ACT_FAMILY[activity] and (ready+handover - last_end.get(res, -9999)) < 30:
            setup = PARAMS['SETUP']
        ready2 = ready + handover + setup
        dur_total = service_dur + setup
        start_total, end_total = find_start(res, ready2, dur_total, res_busy, absent, outage, activity)
        if not math.isfinite(start_total):
            continue
        service_start = start_total + setup
        service_end = end_total
        cost = end_total
        if policy == 'Hybrid reserved P1 + overflow':
            if priority == 'P1' and res in RESERVED_P1:
                cost -= 15.0
            if priority != 'P1' and res in RESERVED_P1:
                cost += 30.0
        if policy == 'Full pooling' and prev_res is not None and res == prev_res:
            cost -= 3.0
        rec = (res, start_total, end_total, service_start, service_end, handover, setup, service_dur)
        if best is None or cost < best[0]:
            best = (cost, rec)
    if best is None:
        # no resource available in horizon; return huge delay
        return None
    return best[1]

# 1. Assumptions, objectives, and decision variables

**Observations.** The supplied control flow is Intake -> diagnostic branch(es) -> Validation. ME and ES can be parallel or sequential. Resource speed is a multiplier on the base draw. Shifts, breaks, handover, setup, preemption restart, and limited overtime are given. Priority SLAs are P1 120 min, P2 480 min, P3 1440 min.

**Assumptions.**
- **A1 Demand timing:** Expected arrivals in each two-hour block are treated as independent Poisson counts for simulation; within a block arrivals are uniform. Percentages for priority and case type are multinomial probabilities.
- **A2 Service distribution:** For each activity, first draw ordinary vs complex-tail using the supplied probability. Conditional on that, draw uniformly from the supplied min-max range and multiply by the resource’s speed multiplier. Thus the approximate mean service before multiplier is a mixture of uniform means. This turns ranges into distributions; bounds remain the supplied min/max times the resource multiplier.
- **A3 Complex-tail scenario U4:** “Double” complex-tail probabilities, capped at 1.0.
- **A4 U2 interpretation:** I compare two interpretations. Primary interpretation: for 12:00-16:00, double the type weights for E and ES, then renormalize within the same block while keeping expected total arrivals at the base value. Alternative: if absolute E/ES arrivals also double, electrical/software pressure is materially worse than tabled here.
- **A5 U5:** U1 plus Chen absent plus a 30-minute Intake outage from 09:30-10:00. Intake work attempting to cross that interval waits until 10:00 unless already completed.
- **A6 ME/ES parallelism:** Parallelize only when the case is P1 in the hybrid policy, or when expected critical-path saving is expected to exceed 8 minutes coordination plus likely handover/setup; otherwise execute sequentially. Sequential may use one cross-skilled resource and avoid the 8-minute coordination delay, but lengthens critical path.
- **A7 Preemption:** P1 may preempt a lower-priority diagnostic at most once. The interrupted activity is charged a restart penalty equal to 10% of its remaining active service time. Intake and Validation are not preempted in the base rules. The hybrid policy reserves P1 capacity to reduce the need for preemption.
- **A8 Overtime:** Up to 30 minutes per resource can be used only in fallback mode; base runs do not rely on overtime.
- **A9 Resource utilization:** Utilization is busy working time divided by available shift time excluding breaks. Planned utilization above 90% is operationally fragile.
- **A10 Handover/setup:** Resource change for Intake, diagnostic, or Validation adds 7 minutes. Team change between mechanical and electrical/software adds 5 minutes unless the same cross-skilled resource retains the case. Same-resource skill-family switch within a short window adds 5 minutes setup. Parallel ME/ES adds 8 minutes coordination before Validation.

**Decision variables.**
- Eligibility set for each activity-resource pair.
- Queue discipline and priority score.
- Whether to reserve named resources/capacity for P1.
- ME/ES parallelization threshold.
- Overflow trigger from strict/fixed queues to pooled queues.
- Preemption authorization and restart-penalty tolerance.
- Handover-minimizing continuity rules versus fastest-resource rules.
- Fairness caps or penalties on individual utilization.

**Objective formulations.**
- **O1 Tail/SLA-risk objective:** Lexicographically minimize P1 SLA violations, then minimize the worst-scenario p95 delay, then maximize P2/P3 SLA attainment, subject to max individual utilization preferably below 90% and never structurally above 95% without a clear resilience reason. # 3. Candidate policies

**Policy S: Strict specialization with fixed queues.**
- Intake: Ada, then Farah in the morning; otherwise wait.
- Mechanical: Ben, then Ada as fixed backup; Deepa/Farah only if explicitly listed in the fixed queue and available.
- Electrical: Chen, then Deepa; no dynamic overflow to software/mechanical staff.
- Software: Emil, then Farah until noon, then Chen only as a fixed backup.
- Validation: Deepa, then Ben; other resources only if the fixed queue is empty and the task would otherwise wait beyond the queue threshold.
- Dispatch: FCFS within queue, P1 ahead of lower priorities only inside the same fixed queue. No dynamic cross-family overflow in the base mode.
- Preemption: none by default; if a P1 case is waiting and a lower-priority diagnostic is running, the supervisor may allow one preemption only under an emergency exception.
- Parallelization: ME/ES sequential unless the two fixed primary resources are independently free.
- Handover minimization: strong, because queues are fixed and resources repeat tasks; but this can create severe idle/busy imbalance.
- Main risk: skill-silo congestion, especially Electrical when Chen is absent and Validation/Software during morning surges.

**Policy F: Full pooling to any qualified resource.**
- Eligibility: any resource with nonzero skill for the activity.
- Priority score: P1 first by earliest deadline (arrival+120), then P2 by earliest deadline (arrival+480), then P3; within same priority, use shortest expected remaining processing time, with a handover-continuity bonus for retaining the current case resource.
- Dispatch: choose the eligible resource minimizing estimated completion time plus expected handover/setup penalty. For P1, prefer earliest completion over continuity if the difference exceeds 10 minutes.
- Reservation: none; all capacity is dynamically pooled.
- Preemption: P1 may preempt one lower-priority diagnostic if projected P1 slack < 15 minutes and an eligible resource is immediately available; restart penalty is added.
- Parallelization: ME/ES may run in parallel if two qualified resources can start within 15 minutes and the case is P1 or the expected saved critical path exceeds 8 minutes coordination plus expected handover.
- Handover minimization: prefer same resource when qualified and within 10-15% speed loss; otherwise fastest available.
- Overflow: by definition all qualified resources are available.
- Main risk: high handover/setup burden and potential thrashing; validation may become the new bottleneck.

**Policy H: Hybrid with reserved P1 capacity and controlled cross-skill overflow.**
- Reserved P1 capacity: Ada as P1 responder for Intake/Mechanical/Validation until her break/end; Deepa as P1 cross-skilled responder starting 10:00 for electrical/validation; Emil as P1 electrical/software/validation responder after 12:00. Reserved means these resources receive non-P1 work only when no P1 is waiting and the oldest P1 slack is >30 minutes.
- Non-P1 dispatch: full pooling among non-reserved capacity, but with a handover/setup penalty. Prefer the current resource if qualified; otherwise choose lowest expected completion time among non-reserved resources.
- Overflow trigger: if any priority queue has oldest P1 slack <30 minutes, P1 queue length 2, projected critical skill utilization >85% in the next 60 minutes, or measured utilization >95% in the previous block, allow any qualified resource to take any activity.
- Parallelization: parallelize ME/ES for P1 if two resources can start within 15 minutes; for P2/P3 parallelize only if expected saved critical path exceeds 20 minutes because coordination and handover can erase benefits.
- Preemption: only after overflow has been triggered and only if a P1 would otherwise miss 120 minutes; at most one preemption per case; restart penalty is explicitly charged.
- Handover minimization: same-resource retention is preferred unless slow by more than 15%; skill-family batching is encouraged for non-P1 work to reduce 5-minute setup switches.
- Main risk: reserved capacity can be underused if P1 arrivals are sparse; P3 can be starved during U5 unless protected by a daily minimum completion rule.

# 5. Robust recommendation

**Primary recommendation: Policy H, the hybrid reserved-P1 policy with controlled cross-skill overflow, plus a P1-protective fallback mode for U3/U5 or when P1 queues build.** It offers the best worst-case P1 protection across the supplied shocks while retaining most of the efficiency benefit of pooling. Strict specialization fails because it cannot rebalance Electrical/Validation against Mechanical/Software, and Chen absence or a morning surge creates immediate silo queues. Full pooling is attractive for base mean delay and often for U2, but it has higher handover/setup burden and more preemption/continuity risk, making it less robust and less auditable.

Use these operating rules:
- **Normal mode:** reserved P1 capacity as defined in Policy H; non-P1 pooled but handover-aware.
- **Amber trigger:** oldest P1 slack <30 minutes, P1 queue 2, projected critical-skill queue >85% in next 60 minutes, or max resource utilization >95% in the prior block. Action: enable overflow to all qualified resources, batch non-P1 skill families to reduce setup, and allow P1 ME/ES parallelization when two resources can start within 15 minutes.
- **Red trigger:** oldest P1 slack <15 minutes, P1 queue 3, simultaneous absence/outage flags, or Validation queue >5 cases. Action: pause new P3 diagnostics, keep P2 starts only if projected P2 slack >180 minutes, authorize one preemption per running lower-priority diagnostic if necessary, and use up to 30 minutes overtime per resource.
- **De-escalation:** return to normal mode when P1 queue =0 and oldest P1 slack >45 minutes for 30 minutes.
- **Fairness safeguard:** if a resource exceeds 95% utilization for two consecutive blocks, rotate non-P1 work away unless doing so would threaten P1.

When another policy can be preferable:
- If the sole objective is base-case mean delay and demand is stable, Full Pooling can be preferable because it uses all qualified capacity without reservation idle time.
- If Electrical/Software incidents dominate and the operator can set a narrower reservation, a specialized electrical fast lane may outperform generic P1 reservation.
- If demand is low and audit simplicity is paramount, strict specialization may be acceptable, but it is not robust to Chen absence, morning surge, or long-tail days.

# 6. Secondary effects and implementation risks

- **Gaming of estimates:** Operators may overstate service times or complexity to avoid P1 or improve measured utilization. Mitigate with independent service-time monitoring by resource/activity, outlier review, and separation between planning estimates and actual timestamps.
- **P3 starvation:** Reserved P1 and U5 fallback can indefinitely defer P3. Set a daily minimum P3 completion quota or maximum P3 deferral threshold and backfill P3 when P1 slack is high.
- **Skill erosion:** Strict specialization and narrow reservations reduce cross-skilling. Rotate selected non-P1 tasks and maintain certification for overflow roles, especially Ada/Deepa/Emil cross-skill use.
- **Excessive preemption:** Restart penalty plus handover can make preemption worse than waiting. Preempt only when projected P1 miss is imminent, at most once per case, and log remaining active time and restart penalty.
- **Coordination overhead:** Parallel ME/ES adds 8 minutes before Validation and can increase handovers. Parallelize P1 aggressively but P2/P3 only when the projected saved critical path exceeds coordination plus handover.
- **New bottlenecks at Validation:** Pooling diagnostics may move the bottleneck to Validation. Monitor Validation queue time and reserve Deepa/Ben/Emil capacity if validation waiting rises.
- **Fairness and fragility:** A policy that maximizes throughput by overloading one resource is fragile. Use max-min utilization, >90% alerts, and rotating assignment for non-P1 work.
- **Human interpretability and auditability:** Operators must understand why a case was assigned. Log priority score, eligible set, selected resource, overflow reason, reservation reason, and preemption reason.

    for ws, we in get_intervals(res, absent):
        if we <= ready:
            continue
        start = max(ready, ws)
        while True:
            end = start + dur
            if end > we:
                break
            moved = False
            for bs, be in busy:
                if start < be and end > bs:
                    start = be
                    moved = True
                    break
            if moved:
                continue
            return start, end
    return math.inf, math.inf

def draw_base(activity, tail, rng):
    row = SERVICE[SERVICE["activity"] == activity].iloc[0]
    if rng.random() < tail.get(activity, float(row["complex_tail_prob"])):
        return float(rng.uniform(row["complex_min"], row["complex_max"]))
    return float(rng.uniform(row["ordinary_min"], row["ordinary_max"]))

def gen_cases(scen, seed):
    dem, tail, absent, outage = adjust_scenario(scen)
    rng = np.random.default_rng(seed)
    cases = []
    cid = 0
    for _, row in dem.iterrows():
        n = int(rng.poisson(row["expected_arrivals"]))
        pri_p = np.array([row["P1_pct"], row["P2_pct"], row["P3_pct"]], dtype=float)
        pri_p = pri_p / pri_p.sum()
        typ_p = np.array([row["M_pct"], row["E_pct"], row["S_pct"], row["ME_pct"], row["ES_pct"]], dtype=float)
        typ_p = typ_p / typ_p.sum()
        for _ in range(n):
            arr = BLOCK_START[row["block"]] + rng.uniform(0, 120)
            pri = rng.choice(["P1","P2","P3"], p=pri_p)
            typ = rng.choice(["M","E","S","ME","ES"], p=typ_p)
            cases.append({"case": f"c{cid:04d}", "arrival": float(arr),
                          "priority": pri, "type": typ})
            cid += 1
    return cases, tail, absent, outage

def choose_and_schedule(activity, base_draw, ready, priority, prev_res, policy,
                        rng, res_busy, last_skill, last_end, absent, outage):
    eligible = []
    for res in SKILL["resource"]:
        val = SKILL_IDX.loc[res, activity]
        if (not pd.isna(val)) and (res not in absent):
            eligible.append(res)

    if policy == "Strict specialization":
        candidates = [r for r in STRICT_PREF[activity] if r in eligible]
        if not candidates:
            candidates = eligible
    elif policy == "Full pooling":
        candidates = eligible
    else:  # Hybrid
        if priority == "P1":
            reserved_c = [r for r in eligible if r in RESERVED_P1]
            candidates = reserved_c + [r for r in eligible if r not in reserved_c] if reserved_c else eligible
        else:
            nonres = [r for r in eligible if r not in RESERVED_P1]
            candidates = nonres if nonres else eligible

    best = None
    for res in candidates:
        mult = float(SKILL_IDX.loc[res, activity])
        service_dur = base_draw * mult

        # Explicit preemption approximation: P1 diagnostic may incur one restart penalty.
        if activity in DIAG and priority == "P1" and policy != "Strict specialization" and rng.random() < 0.15:
            service_dur *= (1.0 + PARAMS["PREEMPT_PENALTY"])

        handover = PARAMS["HANDOVER"] if (prev_res is not None and res != prev_res) else 0.0

        setup = 0.0
        if (last_skill.get(res) is not None and
            last_skill[res] != ACT_FAMILY[activity] and
            (ready + handover - last_end.get(res, -9999.0)) < 30.0):
            setup = PARAMS["SETUP"]

        ready2 = ready + handover + setup
        dur_total = service_dur + setup
        start_total, end_total = find_start(res, ready2, dur_total, res_busy, absent, outage, activity)
        if not math.isfinite(start_total):
            continue

        service_start = start_total + setup
        service_end = end_total

        cost = end_total
        if policy == "Hybrid reserved P1 + overflow":
            if priority == "P1" and res in RESERVED_P1:
                cost -= 15.0
            if priority != "P1" and res in RESERVED_P1:
                cost += 30.0
        if policy == "Full pooling" and prev_res is not None and res == prev_res:
            cost -= 3.0

        rec = (res, start_total, end_total, service_start, service_end, handover, setup, service_dur)
        if best is None or cost < best[0]:
            best = (cost, rec)

    return None if best is None else best[1]

def simulate_policy(scen, policy, seed):
    cases, tail, absent, outage = gen_cases(scen, seed)
    rng = np.random.default_rng(seed + 10000)

    res_busy = {r: [] for r in SKILL["resource"]}
    last_skill = {r: None for r in SKILL["resource"]}
    last_end = {r: -9999.0 for r in SKILL["resource"]}
    total_busy = {r: 0.0 for r in SKILL["resource"]}

    events = []
    case_rows = []
    total_handover = 0.0
    total_setup = 0.0
    total_coord = 0.0

    def make_event(case, act, start_min, end_min, res):
        return {
            "case:concept:name": case["case"],
            "concept:name": act,
            "start_timestamp": DAY0 + timedelta(minutes=float(start_min)),
            "time:timestamp": DAY0 + timedelta(minutes=float(end_min)),
            "org:resource": res,
            "lifecycle:transition": "complete",
            "case:priority": case["priority"],
            "case:type": case["type"],
            "policy_version": policy,
        }

    for case in sorted(cases, key=lambda c: c["arrival"]):
        t = case["arrival"]
        prev_res = None

        # Intake
        base = draw_base("Intake", tail, rng)
        rec = choose_and_schedule("Intake", base, t, case["priority"], prev_res, policy,
                                  rng, res_busy, last_skill, last_end, absent, outage)
        if rec is None:
            continue
        res, start_total, end_total, ss, se, ho, setup, svc = rec
        total_handover += ho
        total_setup += setup
        total_busy[res] += end_total - start_total
        last_skill[res] = ACT_FAMILY["Intake"]
        last_end[res] = end_total
        res_busy[res].append((start_total, end_total))
        res_busy[res].sort()
        events.append(make_event(case, "Intake", ss, se, res))
        t = se
        prev_res = res

        # Diagnostic branch(es)
        branches = BRANCHES[case["type"]]
        parallel = False
        if len(branches) > 1:
            if policy == "Full pooling":
                parallel = True
            elif policy == "Hybrid reserved P1 + overflow":
                parallel = (case["priority"] == "P1") or (rng.random() < 0.5)
            else:
                parallel = False

        if parallel:
            branch_ends = []
            branch_recs = []
            for act in branches:
                base = draw_base(act, tail, rng)
                rec = choose_and_schedule(act, base, t, case["priority"], prev_res, policy,
                                          rng, res_busy, last_skill, last_end, absent, outage)
                if rec is None:
                    continue
                res, start_total, end_total, ss, se, ho, setup, svc = rec
                total_handover += ho
                total_setup += setup
                total_busy[res] += end_total - start_total
                last_skill[res] = ACT_FAMILY[act]
                last_end[res] = end_total
                res_busy[res].append((start_total, end_total))
                res_busy[res].sort()
                events.append(make_event(case, act, ss, se, res))
                branch_ends.append(se)
                branch_recs.append((res, se))
            if branch_ends:
                max_i = int(np.argmax(branch_ends))
                t = max(branch_ends) + PARAMS["PAR_COORD"]
                total_coord += PARAMS["PAR_COORD"]
                prev_res = branch_recs[max_i][0]
        else:
            for act in branches:
                base = draw_base(act, tail, rng)
                rec = choose_and_schedule(act, base, t, case["priority"], prev_res, policy,
                                          rng, res_busy, last_skill, last_end, absent, outage)
                if rec is None:
                    continue
                res, start_total, end_total, ss, se, ho, setup, svc = rec
                total_handover += ho
                total_setup += setup
                total_busy[res] += end_total - start_total
                last_skill[res] = ACT_FAMILY[act]
                last_end[res] = end_total
                res_busy[res].append((start_total, end_total))
                res_busy[res].sort()
                events.append(make_event(case, act, ss, se, res))
                t = se
                prev_res = res

        # Validation
        base = draw_base("Validation", tail, rng)
        rec = choose_and_schedule("Validation", base, t, case["priority"], prev_res, policy,
                                  rng, res_busy, last_skill, last_end, absent, outage)
        if rec is None:
            continue
        res, start_total, end_total, ss, se, ho, setup, svc = rec
        total_handover += ho
        total_setup += setup
        total_busy[res] += end_total - start_total
        last_skill[res] = ACT_FAMILY["Validation"]
        last_end[res] = end_total
        res_busy[res].append((start_total, end_total))
        res_busy[res].sort()
        events.append(make_event(case, "Validation", ss, se, res))

        delay = se - case["arrival"]
        case_rows.append({
            "case": case["case"], "priority": case["priority"], "type": case["type"],
            "arrival": case["arrival"], "completion": se, "delay": delay
        })

    cr = pd.DataFrame(case_rows)
    if cr.empty:
        return {}, events

    mean_delay = float(cr["delay"].mean())
    p95_delay = float(cr["delay"].quantile(0.95))
    p1 = cr[cr["priority"] == "P1"]
    p2 = cr[cr["priority"] == "P2"]
    p1_sla = float((p1["delay"] <= 120).mean()) if len(p1) else np.nan
    p2_sla = float((p2["delay"] <= 480).mean()) if len(p2) else np.nan

    utils = []
    for r in SKILL["resource"]:
        av = available_minutes(r, absent)
        if av > 0:
            utils.append(total_busy[r] / av)
    max_util = float(max(utils)) if utils else np.nan
    fairness_range = float(max(utils) - min(utils)) if utils else np.nan
    burden = (total_handover + total_setup + total_coord) / max(1, len(cr))

    metrics = {
        "mean_delay": mean_delay,
        "p95_delay": p95_delay,
        "P1_SLA": p1_sla,
        "P2_SLA": p2_sla,
        "max_util": max_util,
        "fairness_range": fairness_range,
        "handover_setup_per_case": burden,
    }
    return metrics, events

def resilience_label(m):
    if m["P1_SLA"] >= 0.88 and m["P2_SLA"] >= 0.85:
        return "High"
    if m["P1_SLA"] >= 0.75:
        return "Medium"
    return "Low"

def failure_label(policy, scen):
    if policy != "Hybrid reserved P1 + overflow" and scen == "U5":
        return "cascading outage/absence"
    if policy == "Strict specialization":
        return "fixed skill-queue backlog"
    if scen in ("U2","U3"):
        return "electrical/software/validation bottleneck"
    if scen == "U5":
        return "intake outage plus Chen absence"
    return "handover/setup and validation bottleneck"

# 9. Limits and validation plan

What cannot be concluded from expected arrivals and service ranges alone:
- Exact queueing behavior, because arrival process, priority mix, break overlap, and resource assignment are only approximated.
- True tail risk, because the complex-tail mixture is not a fitted empirical distribution and may understate dependence or repeated complex cases.
- Human effects such as learning, fatigue, handover quality, and informal prioritization.
- Whether parallel ME/ES truly saves time, because the supplied process does not quantify resource contention, coordination quality, or the probability of rework after parallel work.
- The absolute benefit of preemption, because restart penalty depends on when interruption occurs; the code uses an explicit approximate penalty and should be calibrated with observed pause/resume data.

Pilot/backtest design:
1. **Offline backtest:** Replay two to four weeks of historical events through Policies S, F, and H using actual arrivals and observed service times, not just supplied ranges. Stratify by priority, case type, time block, and Chen/Ada/Deepa/Emil shift overlap.
2. **Shadow mode:** Run Policy H dispatch recommendations in parallel with current operations for one to two weeks without changing actual assignment. Log eligible set, recommended resource, actual resource, reason, P1 slack, handover burden, and projected SLA. This tests interpretability and data quality before live rollout.
3. **Controlled pilot:** Randomize by time block or queue, not by individual priority, so that P1 cases always receive the best available safety net. For example, alternate weeks or comparable blocks between current fixed queues and Hybrid H. Keep a P1 override for supervisors and predefine red triggers for immediate rollback.
4. **Safety monitoring:** Daily review of P1 misses, P1 queue length, oldest P1 slack, Validation queue, max resource utilization, preemption rate, and handover/setup minutes. Stop or adjust if P1 SLA falls below 90% in two consecutive days or if a resource exceeds 95% utilization for two consecutive blocks.
5. **Scenario drills:** Simulate a 30-minute Intake outage and a Chen absence on a low-volume day first. Then test U1 morning surge with an explicit P1-only fallback before using it in live operations.
6. **Fairness and skill audit:** Track utilization by resource and cross-skill rotation. Ensure that the hybrid policy does not persistently overburden Deepa or Emil, and that reserved-P1 idleness does not cause skill erosion or P3 starvation.
7. **Validation focus:** Because pooling can migrate the bottleneck to Validation, pilot should separately measure Validation queue time and test a reserved Validation responder during afternoon peaks.
