```
def _truncate(times, events, horizon):
    times = np.asarray(times, dtype=float)
    events = np.asarray(events, dtype=int)
    tt = np.minimum(times, horizon)
    ee = np.where(times <= horizon, events, 0)
    return tt, ee

def cif_aalen_johansen(times, events, horizon=H, event_type=1):
    tt, ee = _truncate(times, events, horizon)
    d = pd.DataFrame({'t': tt, 'e': ee})
    event_times = sorted(d.loc[d.e != 0, 't'].unique())
    S = 1.0
    cif = 0.0
    for tm in event_times:
        mask = d.t == tm
        n = int((d.t >= tm).sum())
        d_any = int((d.loc[mask, 'e'] != 0).sum())
        d_int = int((d.loc[mask, 'e'] == event_type).sum())
        if n <= 0: continue
        cif += S * (d_int / n)
        S *= (1.0 - d_any / n)
    return cif, S

def km_probability(times, events, horizon=H):
    tt, ee = _truncate(times, events, horizon)
    ee = np.where(ee == 1, 1, 0)
    d = pd.DataFrame({'t': tt, 'e': ee})
    event_times = sorted(d.loc[d.e == 1, 't'].unique())
    S = 1.0
    for tm in event_times:
        n = int((d.t >= tm).sum())
        d_event = int((d.loc[d.t == tm, 'e'] == 1).sum())
        if n > 0:
            S *= (1.0 - d_event / n)
    return 1.0 - S, S
```

```
def cif_aalen_johansen(times, events, horizon=H, event_type=1):
    """Nonparametric CIF for event_type at horizon, with other positive event codes competing."""
    tt, ee = _truncate_for_horizon(times, events, horizon)
    d = pd.DataFrame({"t": tt, "e": ee})
    event_times = sorted(d.loc[d.e != 0, "t"].unique())
    overall_survival = 1.0
    cif = 0.0
    for tm in event_times:
        mask = d.t == tm
        n_at_risk = int((d.t >= tm).sum())
        d_any = int((d.loc[mask, "e"] != 0).sum())
        d_interest = int((d.loc[mask, "e"] == event_type).sum())
        if n_at_risk <= 0:
            continue
        cif += overall_survival * d_interest / n_at_risk
        overall_survival *= (1.0 - d_any / n_at_risk)
    return cif, overall_survival

def km_probability(times, events, horizon=H):
    """Naive KM probability of event code 1 by horizon, treating all other codes as censored."""
    tt, ee = _truncate_for_horizon(times, events, horizon)
    ee = np.where(ee == 1, 1, 0)
    d = pd.DataFrame({"t": tt, "e": ee})
    event_times = sorted(d.loc[d.e == 1, "t"].unique())

    for tm in event_times:
        n_at_risk = int((d.t >= tm).sum())
        d_event = int((d.loc[d.t == tm, "e"] == 1).sum())
        if n_at_risk > 0:
            survival *= (1.0 - d_event / n_at_risk)
    return 1.0 - survival, survival
```

# 1. SLA estimands and time definitions

**Time origin.** The natural time origin is the `Submit` event, because the SLA is measured as elapsed time from submission.

**Horizon.** The SLA horizon is 72 hours.

**Observed time.** For each case we observe:

- a terminal duration if the case reaches an observed terminal state: `resolved`, `rejected`, `withdrawn`, or `transferred`;
- an age at cutoff if the case is still `open`.

Let:

- `T_R` = time to `Resolve`;
- `T_W` = time to `Withdraw`;
- `T_J` = time to `Reject`;
- `T_X` = time to `Transfer`;
- `C` = observation cutoff age for open cases.

The observed time is `T_obs = min(T_R, T_W, T_J, T_X, C)`, with the observed status identifying which minimum occurred. For terminal rows, `duration_or_age_h` is the terminal time. For open rows, it is `C`.

**Important distinction.** A case can be:

1. **Right-censored**: still capable of resolving after the observed time, e.g. an open case at age 47.
2. **Competing-event terminal**: reaches an internal terminal state other than `Resolve`, e.g. `Withdraw` or `Reject`, which prevents later internal resolution.
3. **Already observed as breached by 72 hours**: we already know it was not resolved by 72, e.g. resolved at 76 hours, open at 92 hours, withdrawn at 27 hours, or transferred at 68 hours under an internal-accountability view.

## Estimands

I define four useful estimands. The first two are the main ones.

### Estimand E1: Probability of not being internally resolved by 72 hours

This is the most direct SLA-compliance estimand:

\[
E1 = P(\text{no internal Resolve by } 72h)
\]

Under a competing-risks formulation, if `Resolve` is the event of interest and `Withdraw`, `Reject`, and possibly `Transfer` are competing terminal events, then:

\[
E1 = 1 - CIF_R(72)
\]

where `CIF_R(72)` is the cumulative incidence of resolution by 72 hours.

**Operational decision matched.** SLA reporting, penalty/credit decisions, customer promise compliance, and management governance. It answers: “By the SLA deadline, did the case fail to reach `Resolve`?”

The treatment of `Transfer` must be explicit because external resolution is unknown.

### Estimand E2: Probability of still being in an active internal open state at 72 hours

This is an occupancy or state-probability estimand:

\[
E2 = P(\text{case is internally open at exactly } 72h)
\]

A case resolved at 76 hours was still open at 72 hours. A case withdrawn at 27 hours was not. A case transferred at 68 hours is not internally open at 72 hours if transfer exits the internal process.

**Operational decision matched.** Workload forecasting, staffing, queue intervention, and alerting. It answers: “How many cases will still require internal work at the SLA horizon?”

### Estimand E3: Probability of late resolution after 72 hours

This can be defined conditionally:

\[
E3 = P(T_R > 72 \mid \text{not terminally resolved or otherwise closed before } 72)
\]

or unconditionally as the cumulative incidence of resolution after 72 hours among all started cases, subject to censoring.

**Operational decision matched.** recovery planning, backlog reduction, and estimating how many breached cases can still be successfully completed.

### Estimand E4: Cause-specific cumulative incidence of non-resolution terminal outcomes

For each competing outcome:

\[
CIF_W(72), CIF_J(72), CIF_X(72)
\]

**Operational decision matched.** process redesign, intake quality, withdrawal prevention, rejection governance, and external-transfer policy.

# 2. Event and censoring encoding

The encoding depends on the estimand. For the primary resolution-SLA estimand E1, I use the following event codes:

- `1` = `Resolve`, event of interest;
- `2` = competing non-resolution terminal event;
- `0` = right-censored.

| Observed status | Time used | E1 resolution event indicator | Competing-risk code | Censoring rule | Sensitivity alternatives |
|---|---:|---|---|---|---|
| `resolved` | observed resolution time | `1` | none | not censored | If resolution occurs after 72h, it is still an observed SLA breach for E1, but a success for eventual resolution. |
| `rejected` | observed rejection time | `0` in base | `Reject` as competing event | Not ordinary censoring in base | Could be treated as censoring only for a hypothetical “resolution if not rejected” estimand; usually operationally wrong for SLA. Could also be treated as SLA failure. |

Sensitivity bounds: best case = external resolution by 72h; worst case = unresolved by 72h. | Acknowledges that the case left internal observation and external outcome is unknown. | Best when external organization may resolve the case but no data are available. Supports bounds rather than false precision. |

A fourth useful variant is **transfer as SLA failure at 72h**, where a transfer before 72h is kept in the denominator until 72h and then treated as unresolved. This is a conservative internal-accountability view.

# 3. Why naive completed-case analysis is biased

A naive analysis using only completed resolved cases would use cases such as `S01`, `S02`, `S03`, `S04`, `S07`, `S13`, `S16`, `S17`, `S18`, `S19`, `S20`, `S27`, and `S28`. That is biased for several reasons.

## Survivor bias

Among the 13 resolved cases, 9 resolved by 72 hours and 4 resolved after 72 hours: `S03` at 76h, `S20` at 74h, `S28` at 88h, and `S13` at 110h. A completed-resolved-only view might say that 9/13, about 69%, of resolved cases met the SLA.

But that conditions on eventual resolution. It ignores cases such as:

- `S08`, transferred at 68h;
- `S09`, open at 92h;
- `S11`, open at 81h;
- `S26`, open at 104h;
- `S25`, open at 79h;
- `S32`, transferred at 96h and therefore unresolved at 72h.

Those cases are precisely the tail-risk population. If open cases eventually resolve, their eventual resolution times are already long. Excluding them understates SLA breach and overstates resolution performance.

From the full 32-case extract, the deterministic observed bounds for E1 are:

- known resolved by 72h: 9 cases;
- known not resolved by 72h: 18 cases;
- unknown because open and younger than 72h at cutoff: 5 cases.

So the observed breach bound is approximately:

\[
[18/32, (18+5)/32] = [56.3\%, 71.9\%]
\]

before making any survival-model assumptions.

## Informative censoring

Open cases are right-censored at the observation cutoff, but that censoring may be informative.

Examples:

- `S11`: P1, open at 81h, last event gap 55h;
- `S26`: P3, open at 104h, last event gap 72h;
- `S25`: P1, open at 79h, last event gap 48h;
- `S09`: P3, open at 92h, last event gap 31h.

These long gaps suggest stalled or dormant cases. Treating them as exchangeable with active open cases such as `S15`, age 35h and last gap 2h, or `S31`, age 23h and last gap 3h, is doubtful.

Transfers are also potentially informative censoring. All observed transfers, `S08`, `S21`, and `S32`, are P1 and escalated. If we censor them and assume they would resolve like non-transferred cases, we remove high-priority, escalated, potentially difficult cases from the risk set.

## Competing risks

Withdrawals and rejections are not merely censored observations if the estimand is internal resolution. They prevent resolution.

Examples:

- rejections: `S05`, `S14`, `S23`;
- withdrawals: `S06`, `S12`, `S22`, `S30`.

Treating these as ordinary censoring would overestimate the probability of resolution because it pretends that rejected or withdrawn cases could still later resolve internally.

## Cohort imbalance and rollout compliance

Cohort B began after an automated-screening and escalation-policy change, but assignment was not randomized and compliance was incomplete.

Cohort B contains more P1 cases than cohort A: `S18`, `S21`, `S25`, `S29`, `S32`, compared with A’s `S04`, `S08`, `S11`. Cohort B also contains many `AutoCheck`-first paths, e.g. `S16`, `S18`, `S19`, `S21`, `S24`, `S25`, `S27`, `S28`, `S29`, `S31`, `S32`, but not all B cases follow the new pattern: `S20`, `S23`, `S26`, and `S30` do not show `AutoCheck` before `Screen`.

Therefore, a raw cohort comparison confounds policy exposure with priority mix, case complexity, escalation behavior, and incomplete compliance.

## Active open cases below versus above 72 hours

Open cases below 72h are not yet observed breaches, but they are at-risk:

- `S10`: age 47h;
- `S15`: age 35h;
- `S24`: age 67h;
- `S29`: age 51h;
- `S31`: age 23h.

Open cases above 72h are already known breaches for E1 and open at 72h for E2:

- `S09`: age 92h;
- `S11`: age 81h;
- `S25`: age 79h;
- `S26`: age 104h.

Also, `S32` transferred at 96h was still unresolved at 72h even though its terminal transfer occurred after the horizon.

A completed-case analysis misses both groups.

# 4. Statistical analysis plan

## Method comparison

### Kaplan-Meier

Kaplan-Meier estimates the survival function for a single event type, treating all other outcomes as censored.

For E1, if `Withdraw`, `Reject`, and `Transfer` are treated as censored, Kaplan-Meier estimates a hypothetical probability of resolution under the assumption that those cases could still resolve like retained cases. That is usually not the operational SLA probability.

Use Kaplan-Meier here only as a sensitivity analysis or for a hypothetical no-competing-events estimand.

### Aalen-Johansen / cumulative incidence function

The Aalen-Johansen estimator gives nonparametric cumulative incidence probabilities in the presence of competing events.

For E1, with `Resolve` as the event of interest and `Withdraw`, `Reject`, and possibly `Transfer` as competing events, the cumulative incidence of resolution by 72h directly supports:

\[
P(\text{not resolved by }72h) = 1 - CIF_R(72)
\]

This is the most coherent nonparametric approach for the primary SLA estimand.

### Cause-specific hazards

Cause-specific hazards model the instantaneous rate of a particular event among cases still at risk. For example, the cause-specific hazard of resolution at time `t` is the rate of resolution among cases still open and not transferred/withdrawn/rejected just before `t`.

Cause-specific models are useful for understanding stage dynamics and for covariate effects on rates, but with only terminal times and prefix order, exact transition hazards are not fully identifiable. Exact activity timestamps would be needed.

### Subdistribution hazards

Fine-Gray subdistribution hazards model covariate effects directly on the cumulative incidence of an event in the presence of competing risks.

They are useful if the target is prediction of the cumulative incidence of resolution or breach by 72h. However, coefficients are not ordinary hazards among the still-open population, and causal interpretation is delicate. With only 32 cases and few events per priority/cohort cell, regression would be unstable.

### Restricted mean time

Restricted mean time up to 72h can summarize expected time spent in a state up to the horizon, for example expected unresolved time or expected time to resolution within 72h.

This is a robust supplementary SLA metric because it avoids some hazards-model assumptions and is interpretable as average hours.

### Landmarking

Landmarking defines prediction times, e.g. 24h, 48h, or 60h, and uses only information known up to the landmark to predict the 72h outcome.

This is process-aware and avoids immortal-time bias. For example, at landmark 48h, a case has a known prefix up to 48h, known current stage, known age, and known inactivity gap. The model then predicts breach conditional on being alive/open at the landmark.

Landmarking is operationally useful for alerts, but exact intermediate timestamps are missing here, so landmark prefixes cannot be fully reconstructed from the supplied extract.

### Multi-state model

A multi-state model represents the process states implied by the prefixes:

Submit, Screen, AutoCheck, Review, Rework, Escalate, and terminal states Resolve, Reject, Withdraw, Transfer.

This is the most process-aware approach and can estimate occupancy probabilities such as E2, probability of being open at 72h.

However, exact transition times between intermediate activities are not supplied. We know the order of activities and total duration or age, but not when each activity occurred. Therefore, a full multi-state hazard model is not identifiable without assumptions or additional timestamps.

## Recommended primary approach

**Primary: Aalen-Johansen cumulative incidence for resolution by 72h, with non-resolution terminal outcomes treated as competing events.**

Justification for these data:

- The primary estimand is a probability by a fixed 72h horizon.
- There are competing terminal outcomes.
- The sample is small, so a nonparametric estimator is safer than regression.
- It does not require intermediate event timestamps.
- It can be stratified descriptively by cohort and priority, with caution.
- It can be run under multiple transfer assumptions.

## Recommended secondary approach

**Secondary: landmark or stage-conditioned occupancy analysis for E2, probability of being open at 72h given current age, current stage, and prefix.**

Justification:

- Operational alerting needs conditional current-state risk, not only retrospective SLA compliance.
- Prefixes provide stage information: current stage, repeated review, rework, escalation, and inactivity gap.
- It avoids using future process events if features are truncated at the landmark or cutoff.
- It can be implemented with bounds or simplified stage groups because exact transition times are missing.

A full multi-state model should be a future extension once exact activity timestamps are available.

## Immortal-time and leakage examples

### Escalation

`Escalate` occurs after case start. If we define a baseline covariate `ever_escalated = yes`, then escalated cases receive credit for surviving until escalation. This is immortal-time bias.

For example:

- `S04`: `Submit>Screen>Escalate>Resolve` at 29h;
- `S11`: `Submit>Screen>Escalate`, open at 81h;
- `S13`: `Submit>Screen>Review>Rework>Review>Escalate>Resolve` at 110h.

If we compare escalated versus non-escalated cases from Submit without treating escalation as time-dependent, we distort both exposure time and risk.

Safe designs:

- time-dependent covariate;
- landmark analysis after escalation;
- multi-state model with escalation as a transition.

### Rework and repeated review

`S07` and `S13` contain `Rework` followed by another `Review`. `S03` contains repeated `Review` due to escalation returning to review.

If we use final `rework_count` or final `review_count` to predict breach at 48h, we may use events that occurred after 48h. That is leakage.

### AutoCheck position

Cohort B includes `AutoCheck` before `Screen` in cases such as `S16`, `S18`, `S19`, `S21`, `S24`, `S25`, `S27`, `S28`, `S29`, `S31`, and `S32`. Cohort A mostly shows `Screen` before `AutoCheck`, e.g. `S01` and `S15`.

This is a process-policy feature, but it is only known after both activities occur. For early prediction, it must be treated as time-dependent or unknown.

# 6. Sensitivity analysis

At least three sensitivity analyses are needed. I recommend four.

## Sensitivity 1: Transfer as internal competing terminal

**Assumption.** `Transfer` terminates internal resolution opportunity. Transfers before 72h count as not internally resolved by 72h.

**Encoding.** Transfer is a competing event at transfer time.

**Expected effect.** This gives an internal-accountability SLA estimate. It is likely conservative for internal SLA breach.

**Conclusions that could reverse.** If instead transfers are assumed externally resolved, cohort B or P1 performance could look better, because transfers include P1 escalated cases such as `S08`, `S21`, and `S32`.

## Sensitivity 2: Transfer as right censoring

**Assumption.** Transferred cases are censored at transfer time and would have had the same future resolution distribution as retained cases.

**Encoding.** Transfer is censored at transfer time.

**Expected effect.** This usually increases the estimated cumulative incidence of resolution compared with the competing-event treatment, because transferred cases are treated as still capable of resolution.

**Why questionable.** Transfers are all P1 and escalated in this extract. That makes non-informative censoring implausible.

**Conclusions that could reverse.** The statement “P1 cases have poor SLA performance” could weaken if transfers are censored, because several P1 cases leave the internal risk set.

## Sensitivity 3: Transfer external bounds

**Assumption.** External outcome unknown. Use bounds:

- best case: transferred cases are externally resolved by 72h;
- worst case: transferred cases are unresolved by 72h;
- intermediate: transfer remains a separate state with external follow-up unknown.

**Encoding.** Best case treats transfer before 72h as resolution; worst case treats it as unresolved or competing failure.

**Expected effect.** Best case lowers SLA breach; worst case raises it.

**Conclusions that could reverse.** The overall breach rate and the apparent effect of escalation could change, because escalation leads to transfer in `S08`, `S21`, and `S32`.

## Sensitivity 4: Withdraw/reject as competing events versus censoring versus SLA failures

**Assumption A.** Withdraw/reject are competing events. This is the operationally coherent base for internal resolution.

**Assumption B.** Withdraw/reject are censored. This estimates a hypothetical resolution probability if those cases remained open.

**Assumption C.** Withdraw/reject are SLA failures for E1. This is similar to competing events for the binary breach probability but may be reported differently in governance.

**Expected effect.** Treating withdrawals and rejections as censored overstates resolution probability. Treating them as competing events or failures gives a stricter SLA view.

**Conclusions that could reverse.** The conclusion “most cases resolve” versus “most cases do not meet the resolution SLA” can change depending on this treatment.

## Sensitivity 5: Informative censoring from long gaps

**Assumption.** Open cases with long `last_event_gap_h` are more likely to breach.

Examples:

- `S11`: gap 55h;
- `S26`: gap 72h;
- `S25`: gap 48h;
- `S09`: gap 31h.

**Sensitivity options.**

- keep ordinary censoring;
- stratify by gap;
- treat very long-gap open cases as likely breaches at 72h;
- use gap as a time-varying covariate in a landmark model.

**Conclusions that could reverse.** The estimated risk of open P1 cases could increase materially if long-gap open cases are treated as stalled rather than exchangeable with active open cases.

# 7. Operational interpretation

## From survival outputs to alerts

For a case currently open at age `a < 72`, the operationally useful quantity is conditional:

\[
P(\text{no Resolve by }72 \mid \text{open at age }a, \text{current prefix})
\]

This can be estimated using landmarking or stage-conditioned survival probabilities once exact timestamps are available.

A practical alerting policy could be:

- **Already breached**: age >= 72h and unresolved. Examples: `S09`, `S11`, `S25`, `S26`. These need remediation, not prediction.
- **High risk**: age < 72h but predicted breach probability above a threshold, e.g. 0.7. Candidates near the horizon include `S24` at 67h and `S29` at 51h, especially if stage or gap is unfavorable.
- **Watch**: moderate predicted breach probability, e.g. 0.3 to 0.7. Examples: `S10`, `S15`, `S31`, depending on stage and gap.
- **External follow-up**: transferred cases such as `S08`, `S21`, and `S32` should trigger external-status requests if SLA accountability spans organizations.

## Workload actions

Estimand E2, probability of being open at 72h, can be converted into expected workload:

\[
\text{Expected open at 72h} = \sum_{i \in \text{active cases}} P_i(\text{open at }72)
\]

This supports staffing and queue rebalancing. Cause-specific probabilities add actionability:

- high withdrawal probability suggests intake or customer-communication intervention;
- high rejection probability suggests screening or evidence-quality intervention;
- high transfer probability suggests external-partner capacity or escalation-policy review;
- high rework probability suggests quality or training intervention.

## SLA governance

For governance, report:

- observed known breaches by 72h;
- bounds due to open cases younger than 72h;
- Aalen-Johansen CIF of resolution by 72h;
- complementary CIFs for withdrawal, rejection, and transfer;
- confidence intervals or bootstrap intervals, especially because the sample is small;
- sensitivity ranges for transfer assumptions.

Do **not** present risk scores or hazard ratios as causal effects of `Escalate`, `Rework`, `AutoCheck`, or cohort. These are observational, post-treatment, and confounded.

For example, escalation appears in difficult cases such as `S08`, `S11`, `S13`, `S21`, `S25`, `S28`, `S29`, and `S32`. A higher breach rate among escalated cases may reflect case complexity, not the effect of escalation.

## Calibration and fairness checks

Calibration should be checked among cases whose 72h outcome is known:

- terminal events before 72h;
- resolution after 72h;
- open cases already older than 72h;
- transfers after 72h, which were unresolved at 72h.

Open cases younger than 72h cannot be used for 72h calibration until follow-up matures.

Checks by priority and cohort:

- calibration slope and intercept by `priority`;
- calibration by `cohort`;
- false-positive and false-negative rates for breach alerts by priority;
- alert burden by priority and cohort;
- whether P1 cases receive timely interventions rather than only more alerts;
- whether cohort B is penalized for policy rollout incompleteness or case-mix differences.

Because P1 is highest priority, fairness is not simply equal error rates. P1 cases may legitimately have different risk, but systematic under-alerting or over-alerting should be investigated.

```python
    s = row["observed_status"]

    if s in ("rejected", "withdrawn"):

        if wr_mode == "censor":
            return t, 0
        if wr_mode == "failure_at_72":

            return (H, 2) if t <= H else (t, 0)

        if transfer_mode == "competing":
            return t, 2
        if transfer_mode == "censor":
            return t, 0
        if transfer_mode == "sla_failure_at_72":

            return (H, 2) if t <= H else (t, 0)

            return (t, 1) if t <= H else (t, 0)

    if s == "open":
        return t, 0

    return t, 0

def known_breach_by_72(row, transfer_mode="competing"):
    """
    Deterministic known/unknown status for E1: no internal Resolve by 72h.
    True = known breach, False = known no breach, None = unknown because open before cutoff and before 72h.
    """
    t = float(row["duration_or_age_h"])
    s = row["observed_status"]

    if s == "resolved":
        return t > H

    if s in ("rejected", "withdrawn"):
        # Non-resolution terminal outcome; if after 72h, it was still unresolved at 72h.
        return True

    if s == "transferred":
        if transfer_mode == "best_external_resolved":
            # If transfer occurs before 72h, best case assumes external resolution by then.
            # If transfer occurs after 72h, the case was unresolved at 72h.
            return t > H
        return True

    if s == "open":
        return True if t >= H else None

    return None

def known_open_at_72(row):
    """
    Deterministic known/unknown status for E2: active internal open state at 72h.
    True = known open at 72h, False = known not open at 72h, None = unknown open case younger than 72h.
    """
    t = float(row["duration_or_age_h"])
    s = row["observed_status"]

    if s == "open":
        return True if t >= H else None

    # Terminal after 72h means the case was still open at 72h.
    return t > H

# No external survival library is assumed.
# The functions below are the fallback implementation.
# If lifelines were available, KaplanMeierFitter could reproduce the naive KM curve,
# but competing-risk CIF would still need custom Aalen-Johansen logic.
# ------------------------------------------------------------------
def _truncate_for_horizon(times, events, horizon):
    times = np.asarray(times, dtype=float)
    events = np.asarray(events, dtype=int)
    tt = np.minimum(times, horizon)
    ee = np.where(times <= horizon, events, 0)
    return tt, ee

def cif_aalen_johansen(times, events, horizon=H, event_type=1):
    """
    Nonparametric cumulative incidence function for event_type at horizon.
    Other positive event codes are competing events. Zero is censoring.
    """
    tt, ee = _truncate_for_horizon(times, events, horizon)
    d = pd.DataFrame({"t": tt, "e": ee})

    event_times = sorted(d.loc[d.e != 0, "t"].unique())
    overall_survival = 1.0
    cif = 0.0

    for tm in event_times:
        mask = d.t == tm
        n_at_risk = int((d.t >= tm).sum())
        d_any = int((d.loc[mask, "e"] != 0).sum())
        d_interest = int((d.loc[mask, "e"] == event_type).sum())

        if n_at_risk <= 0:
            continue

        cif += overall_survival * d_interest / n_at_risk
        overall_survival *= (1.0 - d_any / n_at_risk)

    return cif, overall_survival

def km_probability(times, events, horizon=H):
    """
    Naive Kaplan-Meier probability of event code 1 by horizon,
    treating all other codes as censored.
    """
    tt, ee = _truncate_for_horizon(times, events, horizon)
    ee = np.where(ee == 1, 1, 0)

    d = pd.DataFrame({"t": tt, "e": ee})
    event_times = sorted(d.loc[d.e == 1, "t"].unique())

    survival = 1.0
    for tm in event_times:
        n_at_risk = int((d.t >= tm).sum())
        d_event = int((d.loc[d.t == tm, "e"] == 1).sum())
        if n_at_risk > 0:
            survival *= (1.0 - d_event / n_at_risk)

    return 1.0 - survival, survival
```

# 9. Limitations and additional data

The extract is sufficient for defining estimands and doing nonparametric horizon-based analysis, but it is insufficient for a fully identified process-aware hazard model. The most important missing data are:

1. **Exact event timestamps for every activity.**  
   Currently we know prefix order and total duration or age, but not when `Screen`, `AutoCheck`, `Review`, `Rework`, or `Escalate` occurred. Exact timestamps are needed for time-dependent covariates, landmarking, stage durations, and multi-state hazard estimation.

2. **External outcomes after transfer.**  
   The eventual status of `S08`, `S21`, and `S32` is unknown. Without external resolution times, transfer can only be handled by assumptions, bounds, or separate governance.

3. **Cutoff date and case start dates.**  
   These are needed to understand calendar effects, workload periods, policy rollout timing, and whether open cases mature uniformly.

4. **Follow-up after cutoff for open cases.**  
   Open cases younger than 72h, such as `S10`, `S15`, `S24`, `S29`, and `S31`, cannot be classified at 72h until more time passes.

5. **Reason codes for withdrawal and rejection.**  
   This determines whether they should be treated as customer-initiated exits, process failures, eligibility decisions, or SLA failures.

6. **Assignment mechanism and rollout compliance for cohort B.**  
   Cohort is not randomized. To estimate policy effects, we need eligibility rules, rollout schedule, actual policy exposure, and compliance measures.

7. **Time-varying workload and queue information.**  
   Long gaps such as `S26` with 72h since last event may reflect queue starvation, missing assignments, or external dependencies. Workload data would help distinguish informative censoring from ordinary delay.

8. **Priority definition and triage rules.**  
   P1 is highest priority, but P1 cases may be systematically harder. Priority-specific calibration and fairness checks require enough cases per priority; with only 8 P1 cases, uncertainty is large.

9. **Escalation policy details.**  
   We need to know whether escalation is mandatory, discretionary, automatic, or triggered by predicted risk. This matters for immortal-time bias and causal interpretation.

10. **External SLA ownership.**  
   If transfer passes SLA accountability to another organization, the operational estimand should change from internal resolution to end-to-end resolution. That requires external timestamps and outcome sharing.
