# 1. Assumptions, objectives, and decision variables

I treat the given service-time ranges as operational uncertainty, not as exact deterministic durations.

| Item                  | Assumption used for analysis                                                                                                                                                                                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Arrivals              | Expected arrivals are block-level means. For load calculations I use deterministic expectations; for the Python scaffold I sample Poisson arrivals uniformly within each two-hour block.                                                                                                                 |
| Service times         | Each activity has an ordinary/tail Bernoulli draw. Conditional on ordinary or tail, service time is uniform over the stated range.                                                                                                                                                                       |
| Multipliers           | Actual active service on a resource is `base_service × multiplier`. A multiplier above 1 therefore consumes more resource time and more elapsed time.                                                                                                                                                    |
| Intake and Validation | Required for every case. They can become bottlenecks even though they are shorter than diagnostics, because every case passes through them.                                                                                                                                                              |
| ME and ES cases       | They require both diagnostic branches. Parallel execution shortens elapsed critical path but consumes two resources, creates extra coordination, and often increases handovers. Sequential execution avoids the 8-minute coordination delay and can preserve ownership, but lengthens the critical path. |
| Handover              | A resource change between Intake, diagnostic, or Validation adds 7 elapsed minutes.                                                                                                                                                                                                                      |
| Team transfer         | Moving between mechanical and electrical/software diagnostic families adds 5 minutes unless the same cross-skilled resource retains the case.                                                                                                                                                            |
| Setup                 | If a resource switches diagnostic skill family between consecutive cases, add 5 minutes.                                                                                                                                                                                                                 |
| Preemption            | A P1 case may preempt a lower-priority diagnostic activity. The interrupted lower-priority case can be preempted at most once and receives a restart penalty of 10% of its remaining active service time.                                                                                                |
| Overtime              | Maximum 30 minutes per resource. Planned individual utilization above 90% is considered unfair and fragile.                                                                                                                                                                                              |
| SLA interpretation    | Completion means Intake, all required diagnostic work, and Validation are complete. Targets are elapsed from arrival.                                                                                                                                                                                    |

The main decision variables are: resource eligibility, queue priority, branch parallelization, use of preemption, reservation of P1 capacity, cross-skill overflow thresholds, overtime activation, and continuity preferences.

Two objective formulations are useful because they lead to different “best” policies.

**Objective A: SLA-tail protection.**
Lexicographically protect P1 first, then P2, then P3:

`minimize 1000 × max(0, 0.90 − P1_SLA) + 200 × max(0, 0.90 − P2_SLA) + 50 × max(0, 0.90 − P3_SLA) + p95_elapsed_time + preemption_penalty`

Under this objective, average delay is secondary. A policy that slightly increases mean delay but protects the P1 tail is preferred.

**Objective B: robust and fair operations.**
Minimize worst-case regret across base and U1-U5:

`minimize max_scenario(policy_loss_scenario − best_policy_loss_scenario) + utilization_imbalance + handover/setup_burden + skill_erosion_penalty`

Here a policy is robust if it does not collapse under U1, U3, or U5; avoids chronic individual utilization above 90%; keeps handovers auditable; and degrades gracefully when full SLA compliance is impossible.

The recommendation below mainly uses Objective B with a hard P1-protection constraint from Objective A.

# 3. Candidate policies

Policy 1: **strict specialization with fixed queues**

Operational rule:

| element               | rule                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Eligibility           | Intake: Farah, Ada, Deepa. Mechanical: Ada, Ben. Electrical: Chen, Deepa. Software: Emil. Validation: Ben, Deepa, Emil. |
| Queue order           | P1 before P2 before P3 inside each fixed activity queue; FIFO within priority.                                          |
| Parallelization       | ME and ES are parallel by default because each branch has a fixed queue.                                                |
| Handover minimization | Weak. Handover is accepted as a consequence of fixed queues.                                                            |
| Setup control         | Good within narrow queues, because workers often repeat the same family.                                                |
| Preemption            | Not used except queue priority; an in-progress lower-priority diagnostic is not interrupted.                            |
| Overflow              | No cross-skill overflow except using the fixed multi-person queue for that activity.                                    |
| Explainability        | Very high: “work goes to the team responsible for the activity.”                                                        |
| Main weakness         | Brittle under Chen absence, Software accumulation before Emil starts, and late Mechanical demand.                       |

This policy is stable and easy to audit, but it creates artificial bottlenecks even when qualified slower resources are idle.

Policy 2: **full pooling to any qualified resource with transparent dispatch**

Operational rule:

For every ready task and qualified resource, compute a dispatch score:

`score = priority_weight + SLA_risk + earliest_finish_bonus + continuity_bonus − handover_penalty − setup_penalty − slow_multiplier_penalty`

A concrete version:

| factor                   | operational meaning                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| Priority weight          | P1 outranks P2, P2 outranks P3 unless a lower-priority case is already in severe SLA danger. |
| SLA risk                 | Higher when predicted finish approaches or exceeds deadline.                                 |
| Earliest finish          | Prefer the resource that can complete the task soonest, including break/shift calendars.     |
| Continuity               | Prefer same resource as the previous activity where feasible.                                |
| Handover/setup penalties | Penalize resource changes, team transfers, and diagnostic family switching.                  |
| Slow multiplier penalty  | Avoid using a very slow cross-skilled resource unless the case is at risk.                   |

Parallelization rule:

ME/ES branches are parallel if predicted parallel finish plus 8-minute coordination beats predicted sequential finish by at least 10-15 minutes. Otherwise, keep the case sequential, preferably on the same cross-skilled resource.

Preemption rule:

A P1 task may preempt a lower-priority diagnostic only if:

1. the P1 case is predicted to breach or nearly breach its 120-minute target without preemption;
2. the interrupted activity has enough remaining work for preemption to matter, for example more than 20 active minutes;
3. the interrupted case has not already been preempted;
4. the expected P1 improvement exceeds the 10% restart penalty imposed on the interrupted case.

This policy usually improves mean flow time and uses skills flexibly, but it can create excessive handovers, setup churn, and hidden unfairness if the score is not audited.

Policy 3: **hybrid reserved P1 capacity with controlled cross-skill overflow**

Operational rule:

| element         | rule                                                                                                                                                                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary pools   | Mechanical: Ada/Ben. Electrical: Chen/Deepa. Software: Emil/Chen. Validation: Ben/Deepa/Emil. Intake: Farah/Ada/Deepa.                                                                                                                                |
| P1 reservation  | Keep at least one fast Mechanical-capable slot and one fast E/S-capable slot effectively available for P1 when P1 risk is present. Reservation is released if no P1 is waiting and no P1 arrival-risk trigger is active.                              |
| Queue score     | P1 first; then P2/P3 by projected SLA risk and aging. Add explicit penalties for handover, team transfer, setup, slow multiplier, and utilization imbalance.                                                                                          |
| Overflow        | Allow cross-skill overflow only when predicted queue wait exceeds a threshold or SLA risk is material. Do not send low-risk P3 work to slow cross-skilled resources merely to keep them busy.                                                         |
| Parallelization | P1 ME/ES usually parallel if both branches can start quickly and Validation is not already congested. P2/P3 are sequential by default when slack is healthy; parallel only when predicted finish threatens the SLA or both branch resources are idle. |
| Continuity      | Prefer same resource for sequential multi-branch work when the multiplier penalty is acceptable.                                                                                                                                                      |
| Preemption      | Allowed for P1, but capped and audited. Do not preempt for marginal gains.                                                                                                                                                                            |
| Fairness        | Penalize assigning additional work to a resource whose projected utilization exceeds 90% while another qualified resource is materially below target.                                                                                                 |
| Stress mode     | Under U1/U3/U5 triggers, reserve more capacity for P1 and near-deadline P2, defer safe P3 diagnostics, and reduce parallelization for nonurgent cases.                                                                                                |

This is the recommended family of policies because it keeps the explainability of specialization while avoiding its most fragile queues.

A possible fourth policy, not used as the primary recommendation, is **shortest expected remaining processing time with SLA guardrails**. It minimizes average delay but is dangerous here because it can starve long ME/ES and P3 cases, and it may sacrifice skill development and continuity.

# 5. Robust recommendation

I recommend the **hybrid reserved P1 capacity with controlled cross-skill overflow** as the primary policy.

It dominates strict specialization under robustness because it avoids artificial starvation when one fixed queue is overloaded and another qualified worker is available. It dominates unconstrained full pooling under auditability and fairness because it does not let the dispatch rule silently create excessive handovers, setup churn, or skill erosion.

The recommended operational rule is:

1. **Always protect P1.** P1 cases receive a fast lane through Intake, diagnostics, and Validation. A P1 diagnostic may preempt a lower-priority diagnostic only when the predicted P1 SLA improvement is material.
2. **Use primary specialists first.** Mechanical normally goes to Ada/Ben; Electrical to Chen/Deepa; Software to Emil/Chen; Validation to Ben/Deepa/Emil.
3. **Permit controlled overflow.** Use slower cross-skilled resources only when the queue is at risk, not just because the resource is idle.
4. **Parallelize selectively.** P1 ME/ES cases should often be parallelized. P2/P3 ME/ES cases should be sequential when slack is healthy, especially if sequential execution preserves ownership and avoids the 8-minute coordination delay.
5. **Prevent Validation from becoming the hidden bottleneck.** Do not accelerate diagnostics through parallelism if Validation already has a high-risk queue.
6. **Audit every exception.** Every preemption, overflow assignment, and nonprimary skill use must have a recorded reason.

Recommended switch triggers:

| trigger                                                                                        | action                                                                                                                     |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| P1 predicted p90 completion exceeds 100 minutes                                                | Activate P1 surge mode; reserve fastest diagnostic and Validation slots.                                                   |
| Any P1 waits more than 10-15 minutes before Intake or diagnostic assignment                    | Release nonurgent reservations and allow preemption if beneficial.                                                         |
| Electrical/Software queued work exceeds 85% of next two-hour E/S capacity                      | Allow controlled overflow to Ada/Farah only for at-risk cases; keep low-risk P3 out of slow overflow.                      |
| Validation queued work exceeds 60 base minutes                                                 | Reduce parallelization for P2/P3 ME/ES; direct Ben/Deepa/Emil to Validation until queue normalizes.                        |
| Any worker projected above 90% planned utilization while another qualified worker is below 75% | Add fairness penalty to the dispatch score.                                                                                |
| Handover/setup burden exceeds 15 minutes per case                                              | Tighten continuity preference and reduce full-pooling behavior.                                                            |
| Preemptions exceed about 5-8% of cases or the same queue is repeatedly interrupted             | Restrict preemption to P1 cases with hard SLA risk.                                                                        |
| Chen absent or morning arrivals exceed 1.4× plan                                               | Enter stress mode: P1 plus near-deadline P2 only; defer safe P3 diagnostics transparently.                                 |
| U5-like combined stress                                                                        | Declare degraded service mode. Protect P1, communicate P2/P3 backlog, authorize maximum overtime or temporary E/S support. |

Another policy could be preferable under a different objective. If the organization values interpretability and stable team ownership above SLA tails, strict specialization may be acceptable. If the organization values average delay above fairness and continuity, full pooling may look better. For the stated robust objective, the hybrid policy is the safest default.

# 6. Secondary effects and implementation risks

Several second-order effects matter.

**Gaming of estimates.**
If workers know that complex-tail estimates trigger more capacity or avoid preemption, they may over-label complexity. The policy should log both planned and actual service, compare estimated versus realized durations, and audit systematic bias by team and resource.

**Starvation of P3 work.**
A P1-reservation policy can silently turn P3 into a backlog sink. Add an aging term: after a P3 case has consumed, for example, 50% of its 24-hour SLA, it starts competing with safe P2 cases. Also track P3 p90 and maximum age, not only P1/P2.

**Skill erosion.**
Strict specialization preserves skill depth but reduces resilience. Full pooling preserves resilience but can blur specialization and overload cross-skilled workers. The hybrid policy should set minimum exposure targets, for example allowing controlled nonurgent cross-skill assignments during low-load periods for training.

**Excessive preemption.**
Preemption protects P1 but harms lower-priority flow and worker focus. Because the restart penalty is proportional to remaining active service, preempting long-tail diagnostics is especially costly. The policy should record every preemption reason and require a predicted P1 benefit threshold.

**Coordination overhead.**
Parallel ME/ES branches look attractive on critical path, but every parallel multi-branch case adds 8 minutes before Validation. If Validation is congested, parallel diagnostics may only move waiting time downstream.

**Validation as a new bottleneck.**
All cases require Validation. A policy that accelerates Intake and diagnostics without reserving Validation capacity can create a final queue that damages every SLA class. Validation should have its own queue-risk trigger.

**Fairness.**
Chen, Deepa, and Emil are structurally exposed because they cover the E/S and Validation bottlenecks. Without a fairness term, full pooling can repeatedly assign the hardest or most urgent work to the same flexible people.

**Human interpretability.**
Operators should not see the policy as a black-box optimizer. A usable dispatch explanation should look like: “Assigned to Deepa because the case is P1, Electrical is the bottleneck, Deepa is fastest available, and using Ada would add a slow-skill penalty.”

| Where is the bottleneck migrating?                             | `pm4py.discover_performance_dfg`, compared across base, U1-U5, and policy versions.                                                                                                |
| Which cases violate SLA?                                       | `pm4py.filter_case_performance`, plus priority-specific SLA calculations.                                                                                                          |
| Which assignments are policy exceptions?                       | `pm4py.filter_event_attribute_values` on `assignment_reason`, `overflow_flag`, `preemption_flag`, and `reservation_state`.                                                         |

The key design point is that PM4Py case-level service/waiting outputs are not enough for this problem. The policy needs queue-specific waiting, assignment decision context, and resource eligibility at the time of dispatch.

# Calendar and service utilities

DAY = 1440.0
OVERTIME = 30.0
def hm_to_min(hm):
    h, m = map(int, hm.split(":"))
    return (h - 8) * 60 + m  # day starts at 08:00

for r, d in RESOURCES.items():
    d["shift_min"] = (hm_to_min(d["shift"][0]), hm_to_min(d["shift"][1]) + OVERTIME)
    d["break_min"] = None if d["break"] is None else (hm_to_min(d["break"][0]), hm_to_min(d["break"][1]))

def resource_available_now(resource, t, absent):
    if resource in absent:
        return False
    x = t % DAY
    s, e = RESOURCES[resource]["shift_min"]
    if not (s <= x < e):
        return False
    br = RESOURCES[resource]["break_min"]
    return not (br and br[0] <= x < br[1])

def next_resource_available(resource, t, absent):
    if resource in absent:
        return math.inf
    for _ in range(8):
        day_start = t - (t % DAY)
        x = t % DAY
        s, e = RESOURCES[resource]["shift_min"]
        br = RESOURCES[resource]["break_min"]
        cand = max(t, day_start + s)
        y = cand % DAY
        if y >= e:
            t = day_start + DAY + s
            continue
        if br and br[0] <= y < br[1]:
            cand = day_start + br[1]
            y = cand % DAY
        if y < e and resource_available_now(resource, cand, absent):
            return cand
        t = day_start + DAY + s
    return math.inf

def resource_window_end(resource, t):
    day_start = t - (t % DAY)
    x = t % DAY
    s, e = RESOURCES[resource]["shift_min"]
    br = RESOURCES[resource]["break_min"]
    if br and x < br[0]:
        return day_start + br[0]
    return day_start + e

def activity_available_now(activity, t, scenario_name):
    # U5 has one IT outage preventing Intake from 09:30 to 10:00 on the first day.
    return not (scenario_name == "U5" and activity == "Intake" and 90.0 <= t < 120.0)

def next_activity_available(activity, t, scenario_name):
    if activity_available_now(activity, t, scenario_name):
        return t
    return 120.0  # only defined outage is day-0 09:30-10:00

def activity_window_end(activity, t, scenario_name):
    if scenario_name == "U5" and activity == "Intake" and t < 90.0:
        return 90.0
    return math.inf

def next_available_for_task(resource, activity, t, absent, scenario_name):
    cand = t
    for _ in range(20):
        cand = max(next_resource_available(resource, cand, absent),
                   next_activity_available(activity, cand, scenario_name))
        if math.isinf(cand) or (resource_available_now(resource, cand, absent) and activity_available_now(activity, cand, scenario_name)):
            return cand
        cand += 1e-6
    return math.inf

def calendar_add(resource, activity, start, active_minutes, absent, scenario_name):
    t = next_available_for_task(resource, activity, start, absent, scenario_name)
    rem = active_minutes
    while rem > 1e-9:
        if not (resource_available_now(resource, t, absent) and activity_available_now(activity, t, scenario_name)):
            t = next_available_for_task(resource, activity, t, absent, scenario_name)
        end = min(resource_window_end(resource, t), activity_window_end(activity, t, scenario_name))
        take = min(rem, end - t)
        if take <= 1e-9:
            t = next_available_for_task(resource, activity, t + 1e-6, absent, scenario_name)
            continue
        t += take
        rem -= take
    return t

def active_between(resource, start, end, absent, scenario_name, activity=None):
    # Used for utilization and approximate preemption remaining service.
    t, active = start, 0.0
    while t < end - 1e-9:
        if resource_available_now(resource, t, absent) and (activity is None or activity_available_now(activity, t, scenario_name)):
            nxt = min(resource_window_end(resource, t),
                      activity_window_end(activity, t, scenario_name) if activity else math.inf,
                      end)
            active += max(0.0, nxt - t)
            t = nxt
        else:
            t = max(next_resource_available(resource, t, absent),
                    next_activity_available(activity, t, scenario_name) if activity else t)
            if math.isinf(t):
                return active
    return active

def sample_service(activity, rng, scenario_name):
    spec = SERVICE[activity].copy()
    if scenario_name == "U4":
        spec["tail_p"] = min(1.0, 2.0 * spec["tail_p"])
    if rng.random() < spec["tail_p"]:
        lo, hi = spec["tail"]
    else:
        lo, hi = spec["ordinary"]
    return rng.uniform(lo, hi)

def expected_service(activity, scenario_name="base"):
    spec = SERVICE[activity]
    p = spec["tail_p"] * (2.0 if scenario_name == "U4" else 1.0)
    p = min(1.0, p)
    o = sum(spec["ordinary"]) / 2.0
    c = sum(spec["tail"]) / 2.0
    return (1-p)*o + p*c

def family(activity):
    if activity == "Mechanical": return "M"
    if activity in ("Electrical", "Software"): return "ES"
    return activity

# -----------------------------
# Scenario generation

def scenario_table(name):
    rows = []
    for i, row in enumerate(DEMAND_ROWS):
        block, arr, p1, p2, p3, m, e, s, me, es = row
        probs_p = np.array([p1, p2, p3], dtype=float) / 100.0
        probs_t = np.array([m, e, s, me, es], dtype=float) / 100.0
        if name in ("U1", "U5") and i in (0,1):
            arr *= 1.7
            # Assumption: the +8 p.p. P1 share is funded proportionally by P2/P3.
            old_p1 = probs_p[0]
            probs_p[0] = min(1.0, old_p1 + 0.08)
            rest = 1.0 - probs_p[0]
            old_rest = probs_p[1] + probs_p[2]
            probs_p[1:] = probs_p[1:] / old_rest * rest
        if name == "U2" and i in (2,3):
            probs_t[1] *= 2.0  # E
            probs_t[4] *= 2.0  # ES
            probs_t = probs_t / probs_t.sum()
        rows.append((block, arr, probs_p, probs_t))
    return rows

def generate_cases(seed, scenario_name):
    rng = random.Random(seed)
    cases = {}
    cid = 0
    for i, (block, lam, priop, typep) in enumerate(scenario_table(scenario_name)):
        n = rng.poisson(lam) if hasattr(rng, "poisson") else np.random.default_rng(seed + i * 997).poisson(lam)
        start, end = BLOCKS[i]
        priorities = ["P1", "P2", "P3"]
        types = ["M", "E", "S", "ME", "ES"]
        for _ in range(n):
            cid += 1
            pr = rng.choices(priorities, weights=priop, k=1)[0]
            typ = rng.choices(types, weights=typep, k=1)[0]
            arrival = rng.uniform(start, end)
            cases[f"C{cid:04d}"] = {
                "case_id": f"C{cid:04d}", "arrival": arrival, "priority": pr, "type": typ,
                "target": PRIORITY_TARGET[pr], "due": arrival + PRIORITY_TARGET[pr],
                "preemptions": 0, "complete": False, "finish": None,
                "diag_required": DIAG_FOR_TYPE[typ], "diag_done": [],
                "diag_plan": None, "diag_sequence": [], "last_diag_finish": None,
                "last_diag_resource": None, "last_diag_family": None,
                "intake_resource": None
            }
    return cases, rng

# -----------------------------
# Policy functions
# -----------------------------
def policy_params(policy):
    if policy == "strict_specialization":
        return {"preempt": False, "parallel_bias": "always", "fairness": 0.0}
    if policy == "full_pooling":
        return {"preempt": True, "parallel_bias": "critical_path", "fairness": 0.0}
    if policy == "hybrid_reserved_overflow":
        return {"preempt": True, "parallel_bias": "threshold", "fairness": 0.15}
    raise ValueError(policy)

def eligible_resources(activity, policy, absent):
    if policy == "strict_specialization":
        pool = STRICT_POOLS[activity]
    else:
        pool = [r for r, d in RESOURCES.items() if d["mult"].get(activity) is not None]
    return [r for r in pool if r not in absent and RESOURCES[r]["mult"].get(activity) is not None]

def choose_diag_plan(case, policy, scenario_name):
    req = list(case["diag_required"])
    if len(req) == 1:
        return ("sequential", req)
    if policy == "strict_specialization":
        return ("parallel", req)
    # Expected no-queue critical path: compare parallel coordination against sequential same-case continuity.
    exp = {a: expected_service(a, scenario_name) for a in req}
    par_cp = max(exp.values()) + 8.0
    seq_cp = sum(exp.values())
    if policy == "full_pooling":
        return ("parallel", req) if par_cp + 5.0 < seq_cp else ("sequential", sorted(req, key=lambda a: -exp[a]))
    # Hybrid: reserve parallelism for P1 and at-risk P2; otherwise avoid coordination/handover.
    if case["priority"] == "P1":
        return ("parallel", req) if par_cp < 0.85 * case["target"] else ("sequential", sorted(req, key=lambda a: -exp[a]))
    if case["priority"] == "P2" and seq_cp > 75.0:
        return ("parallel", req)
    return ("sequential", sorted(req, key=lambda a: -exp[a]))

def transition_overhead(case, task, resource, state):
    handover = 0.0
    team_transfer = 0.0
    setup = 0.0
    prev_r = task.get("prev_resource")
    prev_f = task.get("prev_family")
    new_f = family(task["activity"])
    if prev_r is not None and prev_r != resource:
        handover += 7.0
    if prev_f in ("M", "ES") and new_f in ("M", "ES") and prev_f != new_f and prev_r != resource:
        team_transfer += 5.0
    if new_f in ("M", "ES"):
        last_f = state[resource]["last_diag_family"]
        last_case = state[resource]["last_diag_case"]
        if last_f is not None and last_f != new_f and last_case != task["case_id"]:
            setup += 5.0
    return handover, team_transfer, setup

def pair_score(task, resource, now, cases, state, policy, absent, scenario_name):
    c = cases[task["case_id"]]
    h, tt, setup = transition_overhead(c, task, resource, state)
    mult = RESOURCES[resource]["mult"][task["activity"]]
    active = task["remaining_base"] * mult + h + tt + setup
    start = next_available_for_task(resource, task["activity"], now, absent, scenario_name)
    finish = calendar_add(resource, task["activity"], start, active, absent, scenario_name)
    projected_lateness = (finish - c["due"]) / c["target"]
    pr_rank = {"P1": 0, "P2": 1, "P3": 2}[c["priority"]]
    continuity = 0 if task.get("prev_resource") == resource else 1
    util = state[resource]["busy_active"] / max(1.0, state[resource]["available_active_so_far"] + 1.0)
    if policy == "strict_specialization":
        return (pr_rank, task["ready"], finish, continuity)
    if policy == "full_pooling":
        return (pr_rank, max(projected_lateness, -1.0), finish, continuity)
    # Hybrid: P1 first; then projected SLA risk; small fairness term discourages hammering one worker.
    at_risk = 0 if projected_lateness > -0.15 else 1
    fairness_term = policy_params(policy)["fairness"] * util
    # Controlled overflow: discourage slow cross-skill use when not at risk.
    slow_penalty = 0.25 if (mult >= 1.30 and c["priority"] != "P1" and at_risk == 1) else 0.0
    return (0 if c["priority"] == "P1" else 1 + at_risk, projected_lateness + fairness_term + slow_penalty, finish, continuity)

# -----------------------------
# Discrete-event simulation
# -----------------------------
def simulate(policy, scenario_name="base", seed=1, return_log=False):
    absent = {"Chen"} if scenario_name in ("U3", "U5") else set()
    cases, rng = generate_cases(seed, scenario_name)
    state = {r: {"job_id": None, "busy_until": 0.0, "busy_active": 0.0,
                 "available_active_so_far": 0.0, "last_diag_family": None, "last_diag_case": None}
             for r in RESOURCES}
    queue = []
    tasks = {}
    events = []
    event_log = []
    burden = defaultdict(float)
    job_counter = 0
    task_counter = 0

    def push_event(t, typ, payload):
        heapq.heappush(events, (float(t), typ, payload))

    def create_task(case_id, activity, ready, remaining_base=None, prev_resource=None, prev_family=None):
        nonlocal task_counter
        task_counter += 1
        if remaining_base is None:
            remaining_base = sample_service(activity, rng, scenario_name)
        tid = f"T{task_counter:06d}"
        tasks[tid] = {"task_id": tid, "case_id": case_id, "activity": activity,
                      "ready": float(ready), "remaining_base": float(remaining_base),
                      "prev_resource": prev_resource, "prev_family": prev_family}
        queue.append(tid)
        return tid

    # Seed arrivals.
    for cid, c in cases.items():
        push_event(c["arrival"], "arrival", cid)

    def complete_task(job, now):
        r = job["resource"]
        tid = job["task_id"]
        if state[r]["job_id"] != job["job_id"]:
            return  # stale event after preemption
        task = job["task"]
        c = cases[task["case_id"]]
        activity = task["activity"]
        state[r]["job_id"] = None
        state[r]["busy_until"] = now
        state[r]["busy_active"] += job["active_required"]
        if family(activity) in ("M", "ES"):
            state[r]["last_diag_family"] = family(activity)
            state[r]["last_diag_case"] = task["case_id"]
        event_log.append({
            "case:concept:name": task["case_id"], "concept:name": activity,
            "start_min": job["start"], "end_min": now, "org:resource": r,
            "priority": c["priority"], "case_type": c["type"],
            "ready_min": task["ready"], "queue_wait_min": max(0.0, job["start"] - task["ready"]),
            "service_active_min": job["active_required"], "handover_min": job["handover"],
            "team_transfer_min": job["team_transfer"], "setup_min": job["setup"],
            "coordination_min": 0.0, "preempted_segment": False,
            "policy": policy, "scenario": scenario_name
        })
        if activity == "Intake":
            c["intake_resource"] = r
            mode, seq = choose_diag_plan(c, policy, scenario_name)
            c["diag_plan"] = mode
            if mode == "parallel":
                for a in seq:
                    create_task(c["case_id"], a, now, prev_resource=r, prev_family="Intake")
            else:
                c["diag_sequence"] = list(seq[1:])
                create_task(c["case_id"], seq[0], now, prev_resource=r, prev_family="Intake")
        elif activity in ("Mechanical", "Electrical", "Software"):
            c["diag_done"].append(activity)
            c["last_diag_finish"] = max(c["last_diag_finish"] or now, now)
            c["last_diag_resource"] = r
            c["last_diag_family"] = family(activity)
            if c["diag_plan"] == "sequential" and c["diag_sequence"]:
                nxt = c["diag_sequence"].pop(0)
                create_task(c["case_id"], nxt, now, prev_resource=r, prev_family=family(activity))
            elif set(c["diag_done"]) == set(c["diag_required"]):
                coord = 8.0 if c["diag_plan"] == "parallel" and len(c["diag_required"]) > 1 else 0.0
                burden["coordination"] += coord
                create_task(c["case_id"], "Validation", c["last_diag_finish"] + coord,
                            prev_resource=c["last_diag_resource"], prev_family=c["last_diag_family"])
        elif activity == "Validation":
            c["complete"] = True
            c["finish"] = now

    def maybe_preempt(now):
        if not policy_params(policy)["preempt"]:
            return
        # If a ready P1 task exists and no idle qualified resource exists, interrupt one lower-priority diagnostic job.
        ready_p1 = [tasks[tid] for tid in queue if tasks[tid]["ready"] <= now and cases[tasks[tid]["case_id"]]["priority"] == "P1"]
        if not ready_p1:
            return
        for p1task in sorted(ready_p1, key=lambda t: t["ready"]):
            elig = eligible_resources(p1task["activity"], policy, absent)
            idle_now = [r for r in elig if state[r]["job_id"] is None and resource_available_now(r, now, absent)]
            if idle_now:
                continue
            candidates = []
            for r in elig:
                jid = state[r]["job_id"]
                if jid is None:
                    continue
                job = state[r].get("current_job")
                if not job:
                    continue
                low_task = job["task"]
                low_case = cases[low_task["case_id"]]
                if low_task["activity"] not in ("Mechanical", "Electrical", "Software"):
                    continue
                if low_case["priority"] == "P1" or low_case["preemptions"] >= 1:
                    continue
                candidates.append((job["finish"], r, job))
            if not candidates:
                continue
            _, r, job = min(candidates)
            low_task = job["task"]
            low_case = cases[low_task["case_id"]]
            elapsed_active = active_between(r, job["start"], now, absent, scenario_name, low_task["activity"])
            base_done = max(0.0, (elapsed_active - job["overhead"]) / max(RESOURCES[r]["mult"][low_task["activity"]], 1e-9))
            rem_base = max(0.0, low_task["remaining_base"] - base_done)
            penalty_base = 0.10 * rem_base  # explicit restart penalty assumption
            low_case["preemptions"] += 1
            burden["preemption_penalty_base"] += penalty_base
            # Log the interrupted segment.
            event_log.append({
                "case:concept:name": low_task["case_id"], "concept:name": low_task["activity"],
                "start_min": job["start"], "end_min": now, "org:resource": r,
                "priority": low_case["priority"], "case_type": low_case["type"],
                "ready_min": low_task["ready"], "queue_wait_min": max(0.0, job["start"] - low_task["ready"]),
                "service_active_min": max(0.0, elapsed_active), "handover_min": job["handover"],
                "team_transfer_min": job["team_transfer"], "setup_min": job["setup"],
                "coordination_min": 0.0, "preempted_segment": True,
                "policy": policy, "scenario": scenario_name
            })
            state[r]["job_id"] = None
            state[r]["busy_until"] = now
            # Resume remaining base work plus restart penalty, keeping original predecessor context.
            low_task["remaining_base"] = rem_base + penalty_base
            low_task["ready"] = now
            queue.append(low_task["task_id"])
            return

    def dispatch(now):
        nonlocal job_counter
        # update available denominator used by the hybrid fairness score
        for r in RESOURCES:
            state[r]["available_active_so_far"] = active_between(r, 0.0, max(now, 1.0), absent, scenario_name)
        made_assignment = True
        while made_assignment:
            made_assignment = False
            candidates = []
            for tid in list(queue):
                task = tasks[tid]
                if task["ready"] > now:
                    continue
                for r in eligible_resources(task["activity"], policy, absent):
                    if state[r]["job_id"] is None and resource_available_now(r, now, absent):
                        candidates.append((pair_score(task, r, now, cases, state, policy, absent, scenario_name), tid, r))
            if not candidates:
                break
            _, tid, r = min(candidates)
            if tid not in queue or state[r]["job_id"] is not None:
                continue
            task = tasks[tid]
            queue.remove(tid)
            c = cases[task["case_id"]]
            h, tt, setup = transition_overhead(c, task, r, state)
            burden["handover"] += h
            burden["team_transfer"] += tt
            burden["setup"] += setup
            mult = RESOURCES[r]["mult"][task["activity"]]
            active_required = task["remaining_base"] * mult + h + tt + setup
            start = next_available_for_task(r, task["activity"], now, absent, scenario_name)
            finish = calendar_add(r, task["activity"], start, active_required, absent, scenario_name)
            job_counter += 1
            jid = f"J{job_counter:06d}"
            job = {"job_id": jid, "task_id": tid, "task": task, "resource": r,
                   "start": start, "finish": finish, "active_required": active_required,
                   "overhead": h + tt + setup, "handover": h, "team_transfer": tt, "setup": setup}
            state[r]["job_id"] = jid
            state[r]["current_job"] = job
            state[r]["busy_until"] = finish
            push_event(finish, "finish", job)
            made_assignment = True

    # Main event loop.
    safety = 0
    while events and not all(c["complete"] for c in cases.values()) and safety < 200000:
        safety += 1
        now, typ, payload = heapq.heappop(events)
        # Collect simultaneous events.
        same = [(typ, payload)]
        while events and abs(events[0][0] - now) < 1e-9:
            t2, typ2, payload2 = heapq.heappop(events)
            same.append((typ2, payload2))
        for typ, payload in same:
            if typ == "arrival":
                create_task(payload, "Intake", cases[payload]["arrival"], prev_resource=None, prev_family=None)
            elif typ == "finish":
                complete_task(payload, now)
            elif typ == "availability":
                pass
        maybe_preempt(now)
        dispatch(now)
        # If work is queued but all relevant resources are off-shift, wake up at next availability/ready time.
        if queue:
            future_ready = min(tasks[tid]["ready"] for tid in queue if tasks[tid]["ready"] > now) if any(tasks[tid]["ready"] > now for tid in queue) else math.inf
            future_avail = math.inf
            for tid in queue:
                task = tasks[tid]
                for r in eligible_resources(task["activity"], policy, absent):
                    if state[r]["job_id"] is None:
                        future_avail = min(future_avail, next_available_for_task(r, task["activity"], max(now, task["ready"]), absent, scenario_name))
            nxt = min(future_ready, future_avail)
            if math.isfinite(nxt) and (not events or nxt < events[0][0] - 1e-9):
                push_event(nxt, "availability", None)

    # Metrics
    completed = [c for c in cases.values() if c["complete"]]
    flows = np.array([c["finish"] - c["arrival"] for c in completed]) if completed else np.array([math.nan])
    out = {"policy": policy, "scenario": scenario_name, "n_cases": len(cases), "completed": len(completed),
           "mean_delay": float(np.nanmean(flows)), "p95_delay": float(np.nanpercentile(flows, 95))}
    for pr in ("P1", "P2", "P3"):
        subset = [c for c in completed if c["priority"] == pr]
        out[f"{pr}_SLA"] = float(np.mean([(c["finish"] - c["arrival"]) <= c["target"] for c in subset])) if subset else math.nan
    horizon = max([c["finish"] or 0.0 for c in cases.values()] + [720.0])
    utils = {}
    for r in RESOURCES:
        avail = active_between(r, 0.0, horizon, absent, scenario_name)
        utils[r] = state[r]["busy_active"] / avail if avail > 0 else 0.0
    out["max_resource_utilization"] = float(max(utils.values()))
    out["utilization_fairness_cv"] = float(np.std(list(utils.values())) / (np.mean(list(utils.values())) + 1e-9))
    out["handover_setup_burden_per_case"] = float(sum(burden.values()) / max(1, len(cases)))
    out["preemptions"] = int(sum(c["preemptions"] for c in cases.values()))
    out["horizon_minutes"] = float(horizon)
    if return_log:
        base_ts = pd.Timestamp("2026-01-05 08:00")
        log_df = pd.DataFrame(event_log)
        if not log_df.empty:
            log_df["start_timestamp"] = base_ts + pd.to_timedelta(log_df["start_min"], unit="m")
            log_df["time:timestamp"] = base_ts + pd.to_timedelta(log_df["end_min"], unit="m")
            log_df = log_df.sort_values(["case:concept:name", "start_timestamp", "time:timestamp"])
        return out, log_df
    return out

# 9. Limits and validation plan

Several things cannot be concluded from the supplied expected arrivals and service ranges alone.

First, the exact SLA attainment cannot be known without the actual arrival sequence, actual service distributions, correlation between complexity and case type, resource-specific empirical service distributions, and current backlog. The ranges give plausible uncertainty, not a calibrated stochastic model.

Second, expected arrivals do not tell us burstiness. Two blocks with the same expected arrival count can behave very differently if five P1 cases arrive within ten minutes.

Third, the prompt does not specify whether today’s backlog carries into tomorrow or whether this is a one-off demand day. If the base demand repeats daily, the aggregate load suggests chronic overload unless staffing, service times, or policy scope changes.

Fourth, the service-time multipliers are activity-specific but do not capture learning, fatigue, context switching beyond the fixed setup penalty, or morale effects of repeated preemption.

Fifth, the true cost of parallelization depends on coordination quality. The fixed 8-minute coordination cost may understate the real overhead if parallel branches produce conflicting diagnoses.

A safe validation plan:

| phase                  | design                                                                                                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Historical backtest    | Replay historical logs if available using the three policies as counterfactual dispatch rules. Keep original arrivals and service times; vary only assignment and branch policy. |
| Shadow mode            | Run the hybrid policy silently for 2-4 weeks. Record what it would have assigned, but let current operations continue. Compare predicted versus actual SLA risk.                 |
| P1-protected pilot     | Activate the policy only for P1 and high-risk P2 cases. Keep P3 under the existing rule to avoid full-system disruption.                                                         |
| Limited branch pilot   | Test ME/ES parallelization thresholds on a subset of cases. Measure whether the 8-minute coordination assumption is realistic.                                                   |
| Preemption audit pilot | Allow preemption only with supervisor-visible reason codes. Review every preemption for true P1 benefit and lower-priority harm.                                                 |
| Fairness review        | Weekly review of resource utilization, after-hours work, diagnostic family switching, and rejected/overridden assignments.                                                       |
| Stress drills          | Simulate U1, U3, and U5 using recent real logs. Confirm that stress-mode triggers activate before P1 cases breach.                                                               |
| Rollout gate           | Expand only if P1 SLA improves or remains protected, handover/setup burden does not exceed the threshold, and no resource repeatedly exceeds 90% planned utilization.            |

The policy should not be judged only on base-case average delay. A valid pilot should compare P1 tail protection, P2/P3 starvation, handover burden, worker fairness, and bottleneck migration under realistic stress conditions.
