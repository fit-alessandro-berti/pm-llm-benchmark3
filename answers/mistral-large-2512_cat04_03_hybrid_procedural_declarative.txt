# 1. Policy Interpretation and Conflict Resolution

## Material Assumptions
1. **Event Log Completeness**: The event log contains all control-flow activities but may omit emergency authorizations (R6) and case attributes like "emergency" flags.
2. **Resource Attributes**: Events have a `resource` attribute that can be used for segregation-of-duties checks.
3. **Temporal Granularity**: Timestamps are precise to the hour for temporal profile calculations.
4. **Policy Hierarchy**: Legal department requirements (R5) are considered more authoritative than operations exceptions (R6) unless explicitly overridden by management.
5. **Post-Activation Behavior**: The model must handle bank detail changes after activation (R11) but does not need to model subsequent onboarding requests for the same vendor.

## Conflict Resolution: R5 vs R6
**Option 1: Strict Legal Compliance (R5)**
- Enforce that `Obtain Legal Opinion` must occur before `Activate Vendor` in all cases where `Sanctions Escalation` occurs.
- **Compliance Risk**: Operations may need to bypass the system for emergencies, leading to off-system workarounds that reduce auditability.

**Option 2: Conditional Operations Exception (R6)**
- Allow `Activate Vendor` before `Obtain Legal Opinion` only if:
  - The opinion is received within 24 hours, AND
  - An emergency flag is set (even if not logged)
- **Compliance Risk**: Creates a loophole where all activations could claim emergency status, violating R5.

**Option 3: Hybrid Approach (Chosen)**
- **Primary Path**: Enforce R5 (legal opinion before activation) in the procedural model.
- **Exception Handling**: Add a resource/data-aware check that:
  - Flags cases where activation precedes legal opinion
  - Requires manual review of emergency authorization evidence
  - Enforces the 24-hour temporal constraint
- **Justification**: Balances legal compliance with operational flexibility while maintaining auditability.

# 2. Requirement-to-Formalism Mapping

| Requirement | Primary formalism | Exact encoding | Why this formalism | Redundancy or limitation |
|-------------|-------------------|----------------|--------------------|--------------------------|
| R1 | Procedural | Exclusive choice between reject/activate paths | Clear control-flow separation | Also enforced in DECLARE (noncoexistence) for redundancy |
| R2 | Procedural | Separate approval paths with exactly-one semantics | Block-structured choice is natural | DECLARE enforces exactly_one for redundancy |
| R3 | Procedural | Loop with RequestReceive sequence | Block-structured loops handle bounded cycles | Log Skeleton tracks always_before for additional validation |
| R4 | DECLARE | response(Sanctions Escalation, Obtain Legal Opinion) | Declarative handles eventuality well | Procedural model approximates with sequence |
| R5 | Procedural | Sequence: Sanctions Escalation  ...  Obtain Legal Opinion  Activate Vendor | Strict ordering required | DECLARE response rule provides redundancy |
| R6 | Resource/data layer | External check for emergency activation + temporal constraint | Cannot be expressed in activity-only models | Temporal profile monitors 24-hour window |
| R7 | Procedural | Sequence: Run Sanctions Screening  Sanctions Escalation | Simple precedence | Also in Log Skeleton (always_before) |
| R8 | DECLARE | noncoexistence(Enhanced Due Diligence, Manager Approval) | Declarative handles mutual exclusion well | Procedural model has separate paths |
| R9 | Resource/data layer | Four-eyes principle checks | Requires resource attributes | Cannot be expressed in activity-only models |
| R10 | Log Skeleton | activ_freq constraints | Exact occurrence counts | Procedural model enforces at-most-once via structure |
| R11 | Procedural | Post-activation path with Suspend and Verify Bank Account | Complex control-flow | Resource/data layer checks temporal constraints |
| R12 | Temporal profile | Mean/standard deviation for specified pairs | Statistical temporal expectations | Warnings only - not control-flow violations |

# 3. Procedural Backbone

## Formal Description
We use a ProcessTree with the following structure:
```
(Receive Onboarding Request,
  (Capture Master Data,
    Run Sanctions Screening,
    Verify Bank Account),
  Classify Risk,
  ×(Reject Vendor  Close Onboarding,
    (Manager Approval, Activate Vendor),
    (Enhanced Due Diligence, Compliance Approval, Activate Vendor)),
  (Activate Vendor,
    (Change Bank Details  Suspend Vendor  Verify Bank Account),
    Release First Payment),
  Close Onboarding)
```

Key features:
1. Concurrent execution of the three initial checks
2. Exclusive choice after risk classification
3. Clarification loop modeled as a self-loop on Classify Risk
4. Post-activation bank detail change path
5. Strict sequencing for sanctions escalation  legal opinion  activation

## PM4Py Implementation
```python
from pm4py.objects.process_tree import util as pt_util
from pm4py.objects.process_tree import pt_operator as pt_op

# Build the process tree
procedural_model = pt_util.ProcessTree(
    operator=pt_op.Operator.SEQUENCE,
    children=[
        # Start
        pt_util.ProcessTree(label="Receive Onboarding Request"),

        # Concurrent checks
        pt_util.ProcessTree(
            operator=pt_op.Operator.PARALLEL,
            children=[
                pt_util.ProcessTree(label="Capture Master Data"),
                pt_util.ProcessTree(label="Run Sanctions Screening"),
                pt_util.ProcessTree(label="Verify Bank Account")
            ]
        ),

        # Risk classification
        pt_util.ProcessTree(label="Classify Risk"),

        # Clarification loop (approximated as self-loop)
        pt_util.ProcessTree(
            operator=pt_op.Operator.LOOP,
            children=[
                pt_util.ProcessTree(operator=pt_op.Operator.XOR, children=[
                    pt_util.ProcessTree(label="Request Clarification"),
                    pt_util.ProcessTree(label="")  # Skip
                ]),
                pt_util.ProcessTree(label="Receive Clarification")
            ]
        ),

        # Primary outcome choice
        pt_util.ProcessTree(
            operator=pt_op.Operator.XOR,
            children=[
                # Reject path
                pt_util.ProcessTree(
                    operator=pt_op.Operator.SEQUENCE,
                    children=[
                        pt_util.ProcessTree(label="Reject Vendor"),
                        pt_util.ProcessTree(label="Close Onboarding")
                    ]
                ),

                # Low-risk path
                pt_util.ProcessTree(
                    operator=pt_op.Operator.SEQUENCE,
                    children=[
                        pt_util.ProcessTree(label="Manager Approval"),
                        pt_util.ProcessTree(label="Activate Vendor")
                    ]
                ),

                # High-risk path
                pt_util.ProcessTree(
                    operator=pt_op.Operator.SEQUENCE,
                    children=[
                        pt_util.ProcessTree(label="Enhanced Due Diligence"),
                        pt_util.ProcessTree(label="Compliance Approval"),
                        pt_util.ProcessTree(label="Activate Vendor")
                    ]
                )
            ]
        ),

        # Post-activation
        pt_util.ProcessTree(
            operator=pt_op.Operator.SEQUENCE,
            children=[
                pt_util.ProcessTree(label="Activate Vendor"),
                pt_util.ProcessTree(
                    operator=pt_op.Operator.LOOP,
                    children=[
                        pt_util.ProcessTree(operator=pt_op.Operator.XOR, children=[
                            pt_util.ProcessTree(
                                operator=pt_op.Operator.SEQUENCE,
                                children=[
                                    pt_util.ProcessTree(label="Change Bank Details"),
                                    pt_util.ProcessTree(label="Suspend Vendor"),
                                    pt_util.ProcessTree(label="Verify Bank Account")
                                ]
                            ),
                            pt_util.ProcessTree(label="")  # Skip
                        ])
                    ]
                ),
                pt_util.ProcessTree(label="Release First Payment"),
                pt_util.ProcessTree(label="Close Onboarding")
            ]
        )
    ]
)

# Add sanctions escalation path (approximation)
# This is a limitation - we can't perfectly model the eventuality in a process tree
sanctions_escalation = pt_util.ProcessTree(
    operator=pt_op.Operator.SEQUENCE,
    children=[
        pt_util.ProcessTree(label="Sanctions Escalation"),
        pt_util.ProcessTree(label="Obtain Legal Opinion")
    ]
)
# Insert after Run Sanctions Screening in the parallel block
procedural_model.children[1].children[1].children.append(sanctions_escalation)
```

## Explanation
1. **Concurrency**: The three initial checks run in parallel (PARALLEL operator).
2. **Choices**:
   - After classification: reject, low-risk, or high-risk path (XOR)
   - Post-activation: bank detail change or skip (XOR in LOOP)
3. **Clarification Loops**: Modeled as a LOOP with optional Request Clarification and mandatory Receive Clarification. This is an approximation - the process tree cannot enforce that every request must receive a response before proceeding.
4. **Terminal Outcomes**: Close Onboarding follows either rejection or first payment.
5. **Post-Activation**: The bank detail change path is modeled as a loop that can execute zero or one times.
6. **Sanctions Escalation**: Approximated as a sequence after Run Sanctions Screening. The eventuality requirement (R4) is better handled in DECLARE.

## Rule Semantics Table

| Rule | Template | Direction | Semantics |
|------|----------|-----------|-----------|
| Receive Onboarding Request  Capture Master Data | precedence | Forward | Capture Master Data can only occur after Receive Onboarding Request |
| Request Clarification  Receive Clarification | response | Forward | Every Request Clarification must eventually be followed by Receive Clarification |
| Sanctions Escalation  Obtain Legal Opinion | response | Forward | Every Sanctions Escalation must eventually be followed by Obtain Legal Opinion |
| Obtain Legal Opinion  Activate Vendor | precedence | Forward | Activate Vendor can only occur after Obtain Legal Opinion (with R6 exception) |
| Run Sanctions Screening  Sanctions Escalation | precedence | Forward | Sanctions Escalation can only occur after Run Sanctions Screening |
| Enhanced Due Diligence  Manager Approval | noncoexistence | Bidirectional | These activities cannot co-occur in the same case |

## Overlap and Disagreements
1. **always_before vs DECLARE precedence**: The Log Skeleton's always_before is stricter - it requires that if A occurs, B must occur before it, whereas DECLARE precedence only requires that if B occurs, A must have occurred before it.
2. **never_together vs DECLARE noncoexistence**: These are equivalent in this model.
3. **activ_freq**: The Log Skeleton enforces exact occurrence counts, while the procedural model enforces at-most-once via structure.
4. **directly_follows**: This is more restrictive than the procedural model's concurrency - it assumes certain activities must directly follow others, which isn't always true (e.g., the three initial checks can occur in any order).

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),  # 48h ± 24h
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),    # 12h ± 6h
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)        # 72h ± 36h
}
```

## Explanation
Temporal deviations are warnings rather than control-flow violations because:
1. **Business Context**: The temporal expectations are described as "normative" (R12) - they represent best practices rather than strict requirements.
2. **Operational Reality**: External factors (vendor responsiveness, resource availability) may cause delays that shouldn't automatically reject a case.
3. **Risk Management**: Temporal deviations should trigger review but not necessarily prevent completion.
4. **Statistical Nature**: The profile uses means and standard deviations - some variation is expected.

The zeta value of 2.0 means we flag cases where the elapsed time exceeds the mean by more than 2 standard deviations (covering ~95% of expected cases).

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd
from pm4py.objects.log.util import dataframe_utils
from pm4py.objects.conversion.log import converter as log_converter

def check_four_eyes_principle(log):
    """
    Check R9: Verify Bank Account vs approval, Capture Master Data vs Activate Vendor
    Requires: 'concept:name' and 'org:resource' attributes
    """
    df = log_converter.apply(log, variant=log_converter.Variants.TO_DATA_FRAME)

    # Check Verify Bank Account vs approvals
    verify_resources = set(df[df['concept:name'] == 'Verify Bank Account']['org:resource'].unique())
    manager_approval_resources = set(df[df['concept:name'] == 'Manager Approval']['org:resource'].unique())
    compliance_approval_resources = set(df[df['concept:name'] == 'Compliance Approval']['org:resource'].unique())

    approval_resources = manager_approval_resources.union(compliance_approval_resources)

    if verify_resources.intersection(approval_resources):
        return False, "Four-eyes violation: Verify Bank Account and approval performed by same resource"

    # Check Capture Master Data vs Activate Vendor
    capture_resources = set(df[df['concept:name'] == 'Capture Master Data']['org:resource'].unique())
    activate_resources = set(df[df['concept:name'] == 'Activate Vendor']['org:resource'].unique())

    if capture_resources.intersection(activate_resources):
        return False, "Four-eyes violation: Capture Master Data and Activate Vendor performed by same resource"

    return True, "Four-eyes principle satisfied"

def check_emergency_activation(log):
    """
    Check R6: Emergency activation conditions
    Requires: 'concept:name' and 'time:timestamp' attributes
    """
    df = log_converter.apply(log, variant=log_converter.Variants.TO_DATA_FRAME)
    df = dataframe_utils.convert_timestamp_columns_in_df(df)

    # Find cases with activation before legal opinion
    cases_with_issue = set()

    for case_id, case_df in df.groupby('case:concept:name'):
        activation_time = case_df[case_df['concept:name'] == 'Activate Vendor']['time:timestamp'].min()
        opinion_time = case_df[case_df['concept:name'] == 'Obtain Legal Opinion']['time:timestamp']

        if not opinion_time.empty and activation_time < opinion_time.min():
            # Check if opinion arrived within 24 hours
            time_diff = (opinion_time.min() - activation_time).total_seconds() / 3600
            if time_diff > 24:
                cases_with_issue.add(case_id)

    if cases_with_issue:
        return False, f"Emergency activation violation: {len(cases_with_issue)} cases with activation before legal opinion and opinion not received within 24 hours"

    return True, "Emergency activation policy satisfied"

def check_clarification_cycles(log):
    """
    Check R3: Every Request Clarification must receive a response before next request
    Requires: 'concept:name' and 'case:concept:name' attributes
    """
    df = log_converter.apply(log, variant=log_converter.Variants.TO_DATA_FRAME)

    for case_id, case_df in df.groupby('case:concept:name'):
        requests = case_df[case_df['concept:name'] == 'Request Clarification']
        receives = case_df[case_df['concept:name'] == 'Receive Clarification']

        if len(requests) != len(receives):
            return False, f"Clarification cycle violation in case {case_id}: {len(requests)} requests but {len(receives)} responses"

        # Check ordering - each request must be followed by a receive before next request
        request_indices = requests.index.tolist()
        receive_indices = receives.index.tolist()

        for i in range(len(request_indices)):
            if i < len(request_indices) - 1:
                next_request = request_indices[i+1]
                if receive_indices[i] > next_request:
                    return False, f"Clarification cycle violation in case {case_id}: Request at {request_indices[i]} not responded before next request at {next_request}"

    return True, "Clarification cycles satisfied"

def check_bank_detail_changes(log):
    """
    Check R11: If Change Bank Details occurs after activation, Suspend Vendor must follow
    and Verify Bank Account must occur before Release First Payment
    Requires: 'concept:name' and 'case:concept:name' attributes
    """
    df = log_converter.apply(log, variant=log_converter.Variants.TO_DATA_FRAME)

    for case_id, case_df in df.groupby('case:concept:name'):
        activation_idx = case_df[case_df['concept:name'] == 'Activate Vendor'].index
        change_idx = case_df[case_df['concept:name'] == 'Change Bank Details'].index
        suspend_idx = case_df[case_df['concept:name'] == 'Suspend Vendor'].index
        verify_idx = case_df[case_df['concept:name'] == 'Verify Bank Account'].index
        release_idx = case_df[case_df['concept:name'] == 'Release First Payment'].index

        if not activation_idx.empty and not change_idx.empty:
            # Change occurs after activation
            if change_idx.min() > activation_idx.max():
                # Check suspend follows change
                if suspend_idx.empty or suspend_idx.min() < change_idx.max():
                    return False, f"Bank detail change violation in case {case_id}: Change after activation but no subsequent Suspend Vendor"

                # Check verify occurs after suspend and before release
                if not release_idx.empty:
                    relevant_verify = verify_idx[(verify_idx > suspend_idx.max()) & (verify_idx < release_idx.min())]
                    if relevant_verify.empty:
                        return False, f"Bank detail change violation in case {case_id}: No Verify Bank Account after Suspend Vendor and before Release First Payment"

    return True, "Bank detail change policy satisfied"

def resource_data_checks(log):
    """
    Run all resource/data-aware checks
    """
    checks = [
        ("Four-eyes principle", check_four_eyes_principle),
        ("Emergency activation", check_emergency_activation),
        ("Clarification cycles", check_clarification_cycles),
        ("Bank detail changes", check_bank_detail_changes)
    ]

    results = []
    for name, check_func in checks:
        try:
            passed, message = check_func(log)
            results.append((name, passed, message))
        except Exception as e:
            results.append((name, False, f"Check failed with error: {str(e)}"))

    return results
```

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated Enforcement
1. **Reject/Activate Mutual Exclusion**: Enforced in procedural model (XOR), DECLARE (noncoexistence), and Log Skeleton (never_together).
2. **Approval Paths**: The procedural model's exclusive paths are reinforced by DECLARE's noncoexistence rules.
3. **Sanctions Escalation**: The procedural sequence is reinforced by DECLARE response and Log Skeleton always_before.

**Risk**: If the procedural model changes, the declarative layers might become inconsistent. However, this redundancy provides defense in depth.

## Inconsistencies Under Loops
1. **Clarification Cycles**: The procedural model's loop approximation doesn't enforce that every request must receive a response before proceeding. The DECLARE response rule and Log Skeleton directly_follows handle this better.
2. **Post-Activation Changes**: The procedural model's loop for bank detail changes doesn't perfectly capture that Suspend Vendor must follow Change Bank Details before any Release First Payment. The Log Skeleton's directly_follows is more precise here.

## Vacuity in Declarative Rules
1. **Obtain Legal Opinion  Activate Vendor precedence**: This rule has confidence 0.9 due to the R6 exception. In cases without Sanctions Escalation, this rule is vacuously true.
2. **Noncoexistence rules**: These are vacuously true in cases that don't contain both activities.

## Missing Case Attributes
1. **Emergency Flag**: R6 mentions an "emergency" attribute that isn't in the event log. This forces us to either:
   - Be overly strict (enforce R5 always)
   - Be overly permissive (allow all activations before opinions)
   - Implement manual review for all such cases
2. **Risk Classification**: The actual risk level (low/high) isn't logged, so we can't verify that the correct approval path was taken.

## Timestamp-Only Limitations
1. **Resource Availability**: The temporal profile can't distinguish between delays caused by vendor responsiveness vs. internal resource constraints.
2. **Working Hours**: The profile assumes 24/7 operations - in reality, 48 hours might span a weekend.

## Support/Confidence as Normative Truth
1. **Confidence Values**: We set confidence=0.9 for the legal opinion precedence rule to account for R6, but this metadata isn't normative - it's just a modeling choice.
2. **Support Values**: All rules have support=1.0, implying they should hold in all cases. In reality, some rules (like the legal opinion precedence) have legitimate exceptions.

# 10. Deployment Recommendation

## Canonical Representation
1. **Procedural Model**: Use the ProcessTree as the primary representation for:
   - Process documentation
   - Initial conformance checking
   - Simulation and what-if analysis
2. **DECLARE**: Use for:
   - Detecting deviations from expected patterns
   - Handling eventuality constraints (like clarification responses)
   - Monitoring mutual exclusion rules
3. **Log Skeleton**: Use for:
   - Exact occurrence counting
   - Directly-follows relationships
   - Additional validation of ordering constraints
4. **Temporal Profile**: Use for:
   - Statistical monitoring of normative temporal expectations
   - Identifying cases that may need review due to delays
5. **Resource/Data Layer**: Use for:
   - Enforcing segregation of duties
   - Handling emergency activation policy
   - Validating post-activation changes

## Check Order
1. **Procedural Conformance**: First check against the ProcessTree to identify major control-flow violations.
2. **DECLARE Conformance**: Next check against DECLARE rules to catch eventuality and mutual exclusion violations.
3. **Log Skeleton**: Validate occurrence counts and directly-follows relationships.
4. **Temporal Profile**: Check for temporal deviations that may indicate process inefficiencies.
5. **Resource/Data Checks**: Finally, run the resource-aware checks that require additional attributes.

## Handling Contradictions
1. **Layer Priority**:
   - Procedural model violations are most critical (structural problems)
   - DECLARE violations indicate pattern deviations
   - Temporal warnings suggest potential inefficiencies
   - Resource/data violations may indicate fraud or policy exceptions
2. **Surfacing Findings**:
   - **Critical Violations**: Block the case and require manual review (e.g., contradictory terminal outcomes, four-eyes violations)
   - **Policy Exceptions**: Flag for review but allow completion (e.g., emergency activations, temporal deviations)
   - **Warnings**: Log for process improvement analysis (e.g., clarification response times)
3. **User Interface**:
   - Show a timeline view with violations highlighted
   - Provide explanations of which rules were violated and why
   - Allow overrides with justification for policy exceptions
   - Generate reports of temporal deviations for process optimization

## Implementation Architecture
```
Event Log  [Procedural Check]  [DECLARE Check]  [Log Skeleton]  [Temporal Profile]  [Resource/Data Checks]
       
[Conformance Dashboard]  [Violation Aggregator]
       
[Case Management System]  [Override with Justification]
```

This layered approach provides defense in depth while allowing for operational flexibility where needed. The procedural model serves as the "happy path" documentation, while the declarative layers catch deviations and the resource/data checks enforce policies that can't be expressed in activity sequences alone.
