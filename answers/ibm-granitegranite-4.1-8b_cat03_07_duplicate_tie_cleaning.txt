## 1. Duplicatehandling decision tree  

```
START

 Are the events **exactly identical** in all columns
    (including source_event_key, source_seq, payload_hash)?
     Yes  **Drop the later event** (keep only the first).  
         Decision: drop  
     No  go to next question

 Do the events **share a physical occurrence** (same timestamp,
    same set of related objects) but differ in provenance (different source)?
     Yes  **Merge attributes** preserving the richer information.
        If one source provides location data missing in the other, enrich
        the kept event with the missing payload.  
        Decision: merge attributes & relations (keep one canonical eid)  
     No  go to next question

 Do the events describe **different abstraction levels** of the same business transition
    (e.g., detailed WMS packing vs. ERP summary packing)?
     Yes  **Retain both** but add a qualifier (e.g., “detailed” vs. “summary”)
        to the activity label. No deletion.  
        Decision: retain both with refined labels  
     No  go to next question

 Do the events have **the same label** but involve **different objects** (e.g., two picks of distinct items at same time)?
     Yes  **Retain both unchanged** (they are concurrent, distinct events).  
        Decision: retain both unchanged  
     No  go to next question

 Do the events constitute a **harmonization collision** – same label due to mapping,
    yet semantically distinct (e.g., “Validate Order” vs. “Create Order”)?
     Yes  **Quarantine for review**; do not automerge.  
        Decision: quarantine for review  
     No  go to final question

 If none of the above apply  **Unresolved candidate**  **Retain unchanged**.  
    Decision: retain unchanged
```

### Terminal decision actions  

| Terminal node | Action | Rationale |
|---------------|--------|-----------|
| Exact technical duplicate | Drop later event | Eliminates noise without altering semantics |
| Same physical event, multisystem view | Merge attributes & relations | Preserves richer information while avoiding duplicate IDs |
| Different abstraction level | Retain both with qualifiers | Keeps both detailed and summary perspectives |
| Same label but different objects | Retain both unchanged | Concurrency is legitimate |
| Harmonization collision | Quarantine for review | Prevents accidental semantic loss |
| Unresolved | Retain unchanged | Safe default |

## 3. Timestamptie ordering rules  

### Deterministic partialordertototalorder policy  

| Rule | Semantic? | Deterministic fallback | Reasoning |
|------|-----------|------------------------|-----------|
| **Domain constraints** – events that are causally linked by business logic (e.g., `Validate Order`  `Create Order`, `Accept`  `Handover`) must respect the implied order, regardless of timestamp. | Yes | N/A | Prevents misinterpretation of lifecycle. |
| **Withinsource sequence** – `source_seq` is guaranteed to increase for events from the same source system. Use it to order events that share a timestamp but differ in `source_seq`. | Yes | N/A | Captures intrasystem ordering not visible in UTC. |
| **Lifecycle constraints on shared objects** – For objects that have a known progression (e.g., Order  Invoice  Payment), events that collectively involve earlier steps must precede later steps. | Yes | N/A | Guarantees chronological consistency for object lifecycles. |
| **Sourcespecific semantics** – Some sources (e.g., ERP) emit status updates only after the underlying activity finishes; their timestamps may be slightly later. Use these logical constraints to break ties. | Yes | N/A | Aligns with systemspecific behavior. |
| **Ingestion time (fallback)** – If all above are equal and timestamps are identical, order by `ingested_at`. | No (purely deterministic) | Yes | Provides a stable total order without altering business semantics. |
| **Stable fallback order (microseconds)** – Adding microseconds from a monotonically increasing clock (e.g., system monotonic clock) to the UTC timestamp *only after* the deterministic rules are applied, to guarantee uniqueness of the total order. | No (deterministic only) | Yes | Preempting synthetic microseconds before semantic analysis can create a false story because it may imply ordering that does **not** reflect physical causality; the rule is intended solely as a tiebreaker, not as evidence of order. |

### Applicable ordering for the highlighted groups  

#### a) e03 – e07 at 10:00  

1. **Domain constraints** – `Pick Item`  `Pack Package` is a natural flow.  
2. **Withinsource sequence** – `e03` (source_seq100, WMS) precedes `e06` (source_seq110, WMS).  
3. **Lifecycle constraints** – Both `e04` (scanner pick) and `e05` (different item pick) occur before packing, so they must come first.  
4. **Sourcespecific semantics** – `e07` (ERP summary) typically follows the detailed packing; use this to order it after `e06`.  

**Resulting deterministic order within the 10:00 window:**  

```
e03 (WMS pick I1) -> e04 (scanner pick I1, merged) -> e05 (WMS pick I2) ->
e06 (WMS detailed pack) -> e07 (ERP pack summary)
```  

(The exact position of `e04` relative to `e03` can be decided by `source_seq`; if equal we fall back to `ingested_at`.)

#### b) e08 – e10 at 10:15  

1. **Domain constraints** – `Dispatch`  `Accept`  `Handover` is the business flow.  
2. **Withinsource sequence** – `e08` (WMS dispatch, seq120) precedes `e09` (carrier acceptance, seq1) which precedes `e10` (carrier handover, seq2).  
3. **Lifecycle constraints** – All three involve the same Package `P1`; the handover logically follows acceptance.  

Thus the order is already respected and no further tiebreaking is needed:

```
e08 (WMS dispatch) -> e09 (carrier acceptance) -> e10 (carrier handover)
```

#### c) e11 – e16 at 12:00 (after duplicate decisions)  

1. **Domain constraints** – `Create Invoice`  `Authorize Payment`  `Capture Payment`  `Issue Invoice (dual)` is the typical lifecycle.  
2. **Withinsource sequence** – `e11` (ERP invoice, seq40) precedes `e12` (PSP auth, seq400) which precedes `e13` (PSP capture M1) which precedes `e14` (PSP capture M2) which precedes `e15` (ERP summary) finally succeeded by `e16` (BILLING invoice).  
3. **Lifecycle constraints** – Payments must appear before the final ERP summary if the summary refers to cleared payments.  
4. **Sourcespecific semantics** – ERP summary typically occurs after both payment captures; thus `e15` and `e16` are concurrent and their order is resolved by `source_seq` (ERP seq41 vs. BILLING seq77).  

Resulting order:

```
e11 (ERP invoice) -> e12 (PSP auth M1) -> e13 (PSP capture M1) ->
e14 (PSP capture M2) -> e15 (ERP payment summary) -> e16 (BILLING invoice)
```

All timestamp ties are resolved without adding microseconds before the semantic checks, preserving the original timestamps.

## 4. Conservative cleaning pipeline  

**Goal:** retain the maximum amount of granular business information while eliminating only those duplicates that are unequivocally spurious.

1. **Precheck for candidate groups** – group events by exact equality on `(timestamp, activity, source, source_event_key, payload_hash)`.  
2. **Filter exact technical duplicates** – drop all but the earliest `source_seq` per group (preserving `ingested_at` for tiebreak).  
3. **Identify samephysicalevent groups** – using the known reconciliation facts (e.g., e03/e04, e08/e09), merge attributes from the richer source while keeping a single canonical `eid`.  
4. **Flag abstractionlevel pairs** (e06/e07) and **add qualifiers** (`detailed`, `summary`) without merging IDs.  
5. **Retain distinct concurrent events** (e03/e05, e09/e10, e13/e14) unchanged.  
6. **Preserve dualissue pairs** (e11/e16) by merging complementary attributes and tagging the kept event as “dualissue”.  
7. **Enforce deterministic ordering** – apply the rules from Section3 (domain, sequence, lifecycle) and finally fall back to `ingested_at`. Record the final order in a new column `cleaned_timestamp`.  
8. **Store provenance** – for every merged event, attach an `orig_ids` list (commaseparated source_event_key) and a `merge_rule` flag.  

**Expected retained event count**

- Original raw set: 17 events.  
- Exact technical duplicates removed: none besides e03/e04 (one kept, one dropped)  **1**.  
- Samephysicalevent merges: e03/e04 (1), e08/e09 (1).  
- Abstractionlevel refinement: e06/e07 remain both (no count change).  
- All other relationships unchanged.  

**Net:** **172=15** events retained.  

Thus the conservative pipeline yields a clean OCEL of 15 events while preserving semantics, provenance, and the full business lifecycle.

## 5. Aggressive alternatives  

### a) Evidencebased semantic merging  

- **Approach:** Apply the same duplicategroup detection but *automatically* merge any events that share the same timestamp and **any** related object, regardless of source, provided the evidence matrix (e.g., known reconciliation reports) indicates they describe the same physical occurrence.  
- **Implementation:** Use PM4Py’s `ocel_merge_undirected_duplicates` with `properties=["related objects"]`.  
- **Expected retained event count:**  
  - e03/e04, e08/e09, e11/e16, and also treat e13/e14 as a single payment event (aggressive assumption that both are part of the same payment process).  
  - Merges: e03/e04 (1), e08/e09 (1), e11/e16 (1), e13/e14 (1).  
  - Net: **174=13** events.  
- **Most likely semantic damage:** Loss of the distinction between detailed capture (`e13`) and summary (`e14`), conflating two partial payments into one, which may mislead downstream analytics about payment fragmentation.  

### b) Mechanically aggressive PM4Py merging  

- **Approach:** Run `pm4py.ocel_drop_duplicates` without any contextual filtering, causing *all* events that share the same activity and timestamp (even across different objects) to be collapsed into a single event, retaining only the attribute union of the first occurrence.  
- **Implementation:** `ocel = pm4py.drop_duplicates(ocel_raw, params={"by": ["activity", "timestamp"]})`.  
- **Expected retained event count:**  
  - 10:00 window: e03e07 all collapse to a single “Pick Item / Pack Package” event  **6**.  
  - 10:15 window: e08e10 collapse  **3**.  
  - 12:00 window: e11e16 collapse (but since `e11``e16` have same activity “Issue Invoice” and “Authorize Payment” etc., they collapse to 23 events)  **4**.  
  - Net: **1713=4** events.  
- **Most likely semantic damage:** Drastic reduction of granularity, erasing the distinction between different items (I1 vs I2), between partial payments (M1 vs M2), and between WMSdriven dispatch and carrierdriven acceptance. This can break ordering logic and render the OCEL unusable for process mining.  

**Why “have_common_object=True” is insufficient for e13 and e14**  

Both events share OrderO1 and InvoiceV1, satisfying a naïve commonobject filter, yet they *represent different Payment objects* (M1 vs M2). Merging solely on shared objects would collapse two distinct payment fragments into one, introducing **semantic drift**: downstream analyses would interpret a single payment where two independent transactions occurred, distorting metrics such as payment success rates and risk assessments. Hence, additional criteria (e.g., distinct payment IDs, evidential provenance, or lifecycle constraints) must be applied before merging.

## 6. PM4Pyoriented Python implementation  

```python
import copy
import pm4py
from pm4py.objects.ocel.utils import add_index_based_timedelta
from pm4py.objects.ocel.algorithm.utils import get_event_grouping

# ----------------------------------------------------------------------
# 1. Load raw OCEL (assumed to be in variable ocel_raw)
# ----------------------------------------------------------------------
ocel_raw = ...  # OCEL object containing the 'events' DataFrame

# ----------------------------------------------------------------------
# 2. Deep copy for independent scenarios
# ----------------------------------------------------------------------
conservative = copy.deepcopy(ocel_raw)
aggressive_semantic = copy.deepcopy(ocel_raw)
aggressive_pm4py = copy.deepcopy(ocel_raw)

# ----------------------------------------------------------------------
# 3. Precheck for candidate duplicate groups (by exact technical duplicate)
# ----------------------------------------------------------------------
def find_exact_duplicates(events):
    # group by all columns except 'eid'
    return events.drop(columns='eid').groupby(list(events.columns[:-1])).size()

exact_dup_groups = find_exact_duplicates(conservative.events)
# keep first in each group (earliest source_seq as tiebreaker)
exact_dup_groups = exact_dup_groups.reset_index()
exact_dup_groups.rename(columns={0:'count'}, inplace=True)

# ----------------------------------------------------------------------
# 4. Conservative duplicate handling
# ----------------------------------------------------------------------
# a) Drop duplicates (exactly identical)
conservative.events = conservative.events.drop_duplicates(
    subset=[c for c in conservative.events.columns if c not in ['eid', 'ingested_at']],
    keep='first'
)

# b) Merge samephysicalevent groups using known facts
# Example: e03 & e04
canonical = conservative.events.loc[conservative.events['source_event_key'] == 'ER-100'].copy()
scanner = conservative.events.loc[conservative.events['source_event_key'] == 'S-901'].copy()

# enrich canonical with scanner payload (if needed)
canonical['payload_hash'] = canonical['payload_hash'].fillna(scanner['payload_hash'].values[0])
canonical = canonical.drop(columns=['payload_hash'])

# keep canonical as final, mark scanner as duplicate
conservative.events['merge_rule'] = None
conservative.events.loc[canonical.index, 'merge_rule'] = 'merged_with_scanner'
conservative.events.loc[scanner.index, 'merge_rule'] = 'merged_to_canonical'
conservative.events = conservative.events.drop_duplicates(subset='eid', keep='first')

# c) Add qualifiers for abstractionlevel pairs (e06/e07)
conservative.events.loc[conservative.events['eid'] == 'e06', 'activity'] += ' (detailed)'
conservative.events.loc[conservative.events['eid'] == 'e07', 'activity'] += ' (summary)'

# d) Merge dualissue pair (e11/e16) 
dual = conservative.events.loc[(conservative.events['activity'] == 'Issue Invoice') &
                               (conservative.events['eid'].isin(['e11','e16']))]
dual['orig_ids'] = dual['source_event_key'].agg(','.join)
conservative.events.loc[dual.index[0], 'orig_ids'] = dual['orig_ids']
conservative.events.loc[dual.index[1], 'merge_rule'] = 'dual_issue_merge'

# e) Enforce deterministic ordering (domain, sequence, lifecycle, ingestion)
ordered_cols = [
    'source', 'source_seq',
    'related_objects', 'activity', 'timestamp',
    'ingested_at'
]
conservative.events.sort_values(
    by=ordered_cols,
    ascending=[True, True, True, False, True, True],
    inplace=True
)

# f) Add a deterministic index based on the ordering
add_index_based_timedelta(conservative, 'cleaned_timestamp', 'timestamp')

# ----------------------------------------------------------------------
# 5. Evidencebased semantic merging (aggressive but evidencedriven)
# ----------------------------------------------------------------------
# Merge by related objects (e03/e04, e08/e09, e11/e16, e13/e14)
aggressive_semantic.events = aggressive_semantic.events.drop_duplicates(
    subset=['related_objects', 'timestamp'],
    keep='first'
)
# Note: for e13/e14 we further add a rule that merges only when payment_id matches (not true, so we keep both)
# but here we assume evidence forces merge, so we keep the first encountered.
aggressive_semantic.events['merge_rule'] = None
aggressive_semantic.events.loc[aggressive_semantic.events['eid'] == 'e13', 'merge_rule'] = 'merged_with_e14'
aggressive_semantic.events.loc[aggressive_semantic.events['eid'] == 'e14', 'merge_rule'] = 'merged_to_e13'

# ----------------------------------------------------------------------
# 6. Mechanically aggressive PM4Py merging
# ----------------------------------------------------------------------
aggressive_pm4py = pm4py.drop_duplicates(
    aggressive_pm4py,
    params={
        "by": ["activity", "timestamp"],
        "deep": True
    }
)
aggressive_pm4py.events['merge_rule'] = 'aggressively_merged'

# ----------------------------------------------------------------------
# 7. Validation of referential integrity (placeholder function)
# ----------------------------------------------------------------------
def validate_referential_integrity(ocel):
    # simple sanity check: ensure all related objects exist in the OCEL objects list
    for _, row in ocel.events.iterrows():
        for obj in row['related_objects'].split(','):
            if obj not in ocel.objects:
                raise ValueError(f"Missing object in OCEL: {obj}")
    print("Referential integrity validated.")

validate_referential_integrity(conservative)
validate_referential_integrity(aggressive_semantic)
validate_referential_integrity(aggressive_pm4py)

# ----------------------------------------------------------------------
# Output the three cleaned OCELS (conservative, evidencebased, aggressive)
# ----------------------------------------------------------------------
print("Conservative cleaned OCEL size:", len(conservative.events))
print("Semanticmerge cleaned OCEL size:", len(aggressive_semantic.events))
print("AggressivePM4Py cleaned OCEL size:", len(aggressive_pm4py.events))
```

*Explanation of the code*  

- **Deep copies** ensure each scenario starts from the original raw OCEL.  
- **Exact duplicate detection** uses `drop_duplicates` on all columns except `eid` and `ingested_at`.  
- **Samephysicalevent merges** are implemented manually for the known pairs (e03/e04, e08/e09) and via attribute enrichment.  
- **Qualifiers** are added to keep abstractionlevel events distinct.  
- **Dualissue pair** is merged by populating an `orig_ids` column and marking the duplicate with a `merge_rule`.  
- **Deterministic ordering** respects sourcespecific sequence, lifecycle, and finally ingestion time.  
- **Evidencebased merge** collapses events sharing related objects and timestamp, with a manual rule for e13/e14.  
- **Aggressive PM4Py merge** uses `drop_duplicates` with `by=["activity","timestamp"]` to achieve the minimalchange “merged” view.  
- **Validation** checks that every referenced object exists in the OCEL’s object list.

These changes illustrate how the degree of cleaning directly impacts interpretability of the process discovery results.

## 8. Audit trail and reversibility  

**Proposed provenance schema (JSON per event):**

```json
{
  "canonical_eid": "e03",
  "source_event_ids": ["ER-100", "S-901"],
  "merge_rule": "merged_with_scanner",
  "reviewer": "analyst_2025",
  "rule_version": "v1.2",
  "original_activity": "Create Order",
  "refined_activity": "Create Order (enriched)",
  "original_timestamp": "2026-05-18 09:00:00",
  "adjusted_timestamp": "2026-05-18 09:00:00",
  "attributes_retained": {
    "payload_hash": "h-create",
    "related_objects": "O1"
  },
  "discarded_conflicts": {
    "duplicate_eid": "e04",
    "reason": "same physical scan, richer payload in source_event_key 'ER-100'"
  },
  "confidence": 0.95,
  "reasoning": "Known reconciliation report confirms e03 and e04 describe identical scan."
}
```

**Key elements for full reconstruction of the raw view:**

1. **`source_event_ids`** – list of original identifiers that contributed to the canonical event.  
2. **`merge_rule`** – describes *how* the merge was performed (merged with scanner, dual_issue_merge, etc.).  
3. **`attributes_retained`** – shows which columns were kept unchanged.  
4. **`discarded_conflicts`** – explicitly records the eid(s) that were dropped and the rationale.  
5. **`confidence` & `reasoning`** – capture the analyst’s or algorithmic certainty, enabling sensitivity checks.  

**Reconstruction procedure:**  

- Load the cleaned OCEL.  
- For each event, locate its `source_event_ids`.  
- Retrieve the original raw row (or set of rows) from `ocel_raw.events` where `source_event_key` matches any ID in `source_event_ids`.  
- Reinject any dropped rows (marked in `discarded_conflicts`) back into a temporary OCEL, restoring the original multiplicity.  
- Verify that the restored timestamps, activities, and related objects match the original metadata, confirming that the audit trail fully describes the transformation.

This layered provenance ensures that analysts can always trace back from the cleaned model to the raw multiview data, demonstrating **full reversibility**.

## 9. Failure modes and safeguards  

1. **Collapsing distinct partial payments** – Aggressive merging could merge e13 (M1) with e14 (M2), causing downstream reports to overstate payment completeness. *Guard:* enforce a **paymentID uniqueness check** before merging.  

2. **Converting abstractionlevel updates into false rework** – Adding qualifiers without clear business semantics could be misread as iterative corrections (e.g., `Pack Package (detailed)`  `Pack Package (summary)`) leading to spurious loops. *Guard:* require **explicit lifecycle evidence** (e.g., “ERP status after WMS pack”) before splitting abstraction levels.  

3. **Ordering by ingestion time** – If `ingested_at` were mistaken for business time, the timeline would be incorrect. *Guard:* **explicitly disable ingestiontime ordering** except as a final tiebreaker.  

4. **Treating shared objects as proof of duplication** – Objects like OrderO1 appear in many events; assuming they always indicate duplication would erase valid parallel activities (e.g., concurrent picks of different items). *Guard:* **add objectspecific context** (e.g., related items) to the duplicate decision tree.  

5. **Unioning incompatible E2O relations** – Combining unrelated events (e.g., pick and dispatch) because they share a timestamp could create nonsensical edges. *Guard:* **require temporal contiguity and causal direction** (e.g., pick must occur before dispatch) before union.  

6. **Changing durations through synthetic microseconds** – Adding microseconds before semantic analysis could artificially shorten or lengthen intervals, distorting performance metrics. *Guard:* **apply synthetic microtimestamp only after** all semantic ordering rules, and document it as a deterministic tiebreaker, not as causal evidence.  

7. **Losing sourceauthoritative attributes** – Dropping the richer payload from one source when merging could eliminate critical business data (e.g., location info from WMS). *Guard:* **preserve original payloads** in a separate column (`original_payload_hash`) and annotate the merged event with a provenance flag.  

8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups** – Blindly calling `drop_duplicates` on the entire dataset may unintentionally remove legitimate concurrent events (e.g., two picks of different items). *Guard:* **first run a candidategroup precheck** that respects domain constraints, then apply merging only to verified groups.  

By embedding these safeguards—explicit rule versions, confidence scores, and provenance annotations—within the cleaning pipeline, the system minimizes semantic damage while remaining auditable and reversible.
