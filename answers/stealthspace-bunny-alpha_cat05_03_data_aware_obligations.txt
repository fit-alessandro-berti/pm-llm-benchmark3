## 1. Temporal Data Semantics

I reconstruct each case as an append-only sequence of attribute patches and business events.

- **Ordering:** The source-system order is  
  \[
  e \prec f \iff timestamp(e)<timestamp(f)
  \;\lor\;
  [timestamp(e)=timestamp(f)\land event\_index(e)<event\_index(f)].
  \]
  Thus, “before” and “after” are strict temporal relations, including the event-index tie-breaker.
- **Blank cells:** A blank means “no update at this event.” It does not erase the current value. Forward-filling is performed only after sorting within each case by timestamp and `event_index`.
- **Initial unknowns:** If an attribute has never received a known value, it remains unknown. For example, TX-305’s release amount remains unknown; its later settlement amount must not be copied backward.
- **Snapshots:** A state used for an obligation is the state after attribute updates effective no later than the triggering event. A later event’s attributes do not change an already evaluated obligation.
- **Create versus updates:** `Create_Transaction` establishes the initial state. Later nonblank values on update events are effective at those events unless contrary evidence establishes another effective time.
- **Exemption references:** A release’s `exemption_id` is a reference to asserted evidence, not proof that the exemption was approved, in scope, or effective. A later `Record_Exemption` does not backfill the state at an earlier release.
- **Final attributes:** A final-case export is unsuitable for reconstructing historical obligations. TX-311 is the clearest example: the enhanced review occurred while jurisdiction was still `US`; the `DE` update took effect afterward, at the same timestamp but higher `event_index`.

The relevant times are distinct:

| Time concept | Meaning in this assessment |
|---|---|
| **Event time** | When the source system recorded the business event. Used for ordering unless evidence establishes otherwise. |
| **Effective time** | When a transaction attribute or exemption applies. Defaults to event time here. |
| **Record time** | When a database received or displayed the record. This can be later than effective time. |
| **Evidence time** | When credible evidence establishes that an approval or other fact existed. A displayed backdated field is a claim, not automatically reliable evidence time. |

Accordingly, EX-77’s 11:00 database insertion does not make its approval occur at 11:00. Its qualified signature independently supports approval at 09:05. EX-88’s later certificate creation undermines the PDF as proof of approval at 08:50, but it does not conclusively disprove the separate oral-approval claim.

**Materiality convention.** I use R4’s “more than 20 percent” boundary as the quantitative materiality boundary for amount changes. A known increase of 20 percent or less is a data change but not a material increase under that reading; a decrease does not invalidate a review. I treat changes to risk, customer type, jurisdiction, or exemption state as material because no quantitative alternative is supplied. The alternative reading that *any* amount update is material for R1 would change TX-306; it is addressed below.

## 2. Normalized Rule Table

Let \(R\) be a `Release_Funds` event and \(S_R(a)\) the reconstructed value of attribute \(a\) immediately after updates effective no later than \(R\), respecting `event_index`.

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| **R1** | `Release_Funds`; \(S_R(jurisdiction)\neq DE\) and \(S_R(amount)\ge100{,}000\) | A completed `Enhanced_Review` | Review \(\prec R\), and review after the latest material data change; the “after” relation is strict | Foreign/high-value test uses release-state amount and jurisdiction | A matching, valid R1 exemption; no general exemption from other rules | If jurisdiction or amount cannot exclude the trigger, return an indeterminate/review-required result | Release-trigger evidence, current state provenance, review completion, material-change history, and exemption proof if relied upon |
| **R2** | `Release_Funds`; release-state risk is `HIGH` **or** release-state customer type is `PEP` | Both `Enhanced_Review` and `Compliance_Approve` | Relevant review before approval; approval before release | Current risk and customer type at release; relevant changes to those values affect review freshness | None specified; an R1-only exemption does not waive R2 | If either decisive attribute is unknown and the trigger cannot be excluded, review required | Risk/customer-type change history, review scope and completion, approval event and ordering |
| **R3** | Current release jurisdiction is added to the sanctions list after the latest applicable screen and before release | A new `Sanctions_Screen` | List addition \(\prec\) new screen \(\prec R\) | Current jurisdiction at release and sanctions-event history | None specified | Unknown jurisdiction or unresolved sanctions evidence requires review | Jurisdiction-specific list additions, effective times, screen timestamps, screened-list versions |
| **R4** | An amount update after the latest Standard/Enhanced Review has known prior amount \(p\) and new amount \(a\), with \(a>1.20p\) | The affected review is invalid for amount-dependent obligations; a replacement review is needed where still required | Increase must occur after the relevant review and before the dependent release | Amount immediately before and after the update, plus intervening review history | A decrease does not itself invalidate; a qualifying exemption can independently waive R1, but not restore a review’s factual coverage | An increase from unknown amount is not safely classifiable; obtain evidence rather than treat it as zero or low | Immutable amount-change values, effective times, review baseline, review document/version |
| **R5** | An exemption is proposed to waive an obligation | Valid approval by `Head_Compliance`, correct scope, timely effectiveness, unexpired status, and evidence supporting timely approval | Evidence-supported approval must exist by the obligation trigger; `effective_from` may equal the trigger; expiry is treated as an exclusive boundary | Case state at the obligation trigger, not final case state | Only the rules expressly waived by the exemption | Incomplete scope or approval evidence cannot be silently treated as a valid exception | Head-authorized approval evidence, trusted signature/approval time, scope/version, effective/expiry times, revocation history |

### Concise formal pseudo-logic

```text
e  f iff time(e) < time(f)
          or [time(e) = time(f) and event_index(e) < event_index(f)]

state(c, a, e):
    use nonblank attribute updates for case c whose effective order is  e;
    if the event itself is an update, include that update.
    An unseen attribute remains UNKNOWN.

material_amount(update):
    known(old_amount) and known(new_amount)
    and new_amount > 1.20 * old_amount

material_nonamount(update):
    an effective change to risk_level, customer_type,
    jurisdiction, or exemption state

M1(r):
    latest material change  r

M2(r):
    latest change relevant to HIGH/PEP risk and customer-type obligations,  r

ER1(r):
    latest Enhanced_Review e  r
    such that M1(r) does not exist or M1(r)  e
    and e is not invalidated by R4

ER2(r):
    latest Enhanced_Review e  r
    such that M2(r) does not exist or M2(r)  e
    and e is not invalidated by R4

C(r):
    latest Compliance_Approve c  r

SCR(r):
    latest Sanctions_Screen s  r

R1(r):
    if jurisdiction(r) and amount(r) are sufficiently known:
        if jurisdiction(r) != DE and amount(r) >= 100000:
            satisfied iff Valid_Exemption(r, R1)
                         or [ER1(r) exists and ER1(r)  r]
            otherwise violated
        else:
            not triggered
    else:
        REVIEW_REQUIRED

R2(r):
    if risk(r)=HIGH or customer_type(r)=PEP:
        require ER2(r) exists
        and ER2(r)  C(r)  r
    if both decisive values are known and neither trigger holds:
        not triggered
    otherwise, where a trigger cannot be excluded:
        REVIEW_REQUIRED

R3(r):
    let j = jurisdiction(r)
    for every addition u of j with SCR(r)  u  r:
        require a screen s with u  s  r
    A screen at the same timestamp but lower event_index than u
    is still before u and does not satisfy this requirement.

R4(update):
    let p = amount immediately before update
    let a = new amount
    if p and a are known:
        invalidate prior amount-dependent reviews iff a > 1.20*p
        a <= 1.20*p is not an invalidating increase under the stated convention
        a <= p is not an invalidating increase
    else:
        UNCLASSIFIABLE_AMOUNT_CHANGE

Valid_Exemption(w, r, waived_rule):
    approver(w) = Head_Compliance
    and evidence-supported approval time <= time(r)
    and effective_from(w) <= time(r)
    and time(r) < expires(w)
    and jurisdiction(w) = jurisdiction(r)
    and customer_type(w) = customer_type(r)
    and known release amount lies within amount scope(w)
    and the approval evidence credibly establishes timely approval
    and waived_rule is expressly waived

R6(x):
    never replace UNKNOWN with LOW, NONE, zero, or another low-risk default.
    If a decisive predicate remains unresolved, REVIEW_REQUIRED.
    Do not let an unrelated unknown erase an already proven violation.

R7:
    process events in (timestamp, event_index) order.
    Evaluate each obligation using the resulting event-time state.
    Do not revisit a prior release using a later case-final value.
```

The scope of “relevant” for R2 matters. A risk/customer-type change can make an earlier review stale for R2. A jurisdiction change can separately activate or deactivate R1. A small amount change can alter R1’s threshold test without invalidating the review under R4.

## 4. Ambiguities and Alternative Readings

### TX-302 — Late exemption evidence

The report accepts EX-77 because the qualified signature independently supports a timely 09:05 approval. The outage explains why the database record arrived at 11:00.

Rejecting the late database record **alone would not make TX-302 noncompliant**, because the enhanced review at 09:20 already satisfies R1. The result would change only if that review were also shown to be invalid, incomplete, or not to cover the released state.

A separate policy requiring that exemption evidence have been registered before release would produce a different result, but that contemporaneous-registration requirement is not stated in R5.

### TX-305 — Unknown release amount

Evidence that binds EUR 150,000 to the **release instruction at 11:30** would resolve the amount:

- If the existing 11:15 enhanced review covered that released amount, R1 would be satisfied.
- If reliable evidence instead shows a release amount below EUR 100,000, R1 would not trigger.
- If the amount is at least EUR 100,000 but the alleged enhanced review did not actually complete or cover the released value, the result would become `NONCOMPLIANT`.

The later settlement fact alone does not supply that missing historical binding. A reliable settlement record may justify further investigation, but it is not an immutable release payload.

### TX-310 — Contradictory EX-88 evidence

Two defensible decision rules lead to different results:

1. **Report classification: `INDETERMINATE`.**  
   EX-88 may have been orally approved by Head_Compliance at 08:45, but the supplied evidence does not establish the speaker’s identity or authority. The later certificate contradicts the PDF’s displayed approval time without conclusively disproving a separate oral approval.

2. **`NONCOMPLIANT` under a strict evidentiary default.**  
   If unverified, interested-witness claims are assigned no weight and the late database/PDF records cannot prove timely Head approval, EX-88 is not established as valid. The timely Standard Review then leaves R1 unsatisfied.

`JUSTIFIED_EXCEPTION` would require additional evidence, such as:

- an authenticated Head_Compliance oral-approval record;
- confirmation of the approver’s identity and authority at 08:45;
- corroboration independent of the requester; and
- reconciliation with the later certificate rather than reliance on the PDF display field alone.

R5 does not expressly require a digital signature, so the 10:30 certificate invalidates this PDF **as timely proof**; it does not establish that no valid oral approval existed.

Regardless of the historical classification, the system should not treat EX-88 as a proven exception without adjudication.

### TX-311 — Same-timestamp state and release payload

The supplied ordering is unambiguous: index 3 is the enhanced review under `US`; index 4 changes jurisdiction to `DE`. The release therefore occurs under `DE`.

The result would become `NONCOMPLIANT` if an immutable release payload or other authoritative evidence showed `US` as the effective jurisdiction at 16:30. R1 would then apply to EUR 115,000, and the only enhanced review preceded the 16:20 jurisdiction material change.

Alternatively, reliable evidence that customer type was `PEP`, or risk was `HIGH`, at release would activate R2. The existing standard review and compliance approval would not satisfy that rule.

### TX-306 — Materiality interpretation

Under the adopted interpretation, the 4.55% increase is not material under R4, so the 12:15 enhanced review remains valid and R1 is satisfied.

Under the stricter interpretation that **any** amount update is a “material data change” for R1, the required enhanced review would have to follow the 12:30 update. No such review exists, making TX-306 `NONCOMPLIANT` under R1. R2 would remain satisfied. This is why the policy needs an explicit cross-reference between R1’s “material” term and R4’s threshold.

### TX-301 — Change effective time

The default makes the amount increase effective at 08:20. Evidence that the EUR 125,000 amount was actually a later correction whose effective time was after the 08:25 release would materially change the assessment. No such evidence is currently supplied.

def iso(value):
    if value is None or not pd.notna(value):

def snapshot(row):
    result = {}
    for attr in ATTRIBUTES:
        value = row[attr]
        if pd.isna(value):

        elif attr == "amount":

def event_record(row):
    return {
        "time": row["timestamp"],

def precedes(left, right):
    """Strict source order, including event_index tie-breaking."""
    if left is None or right is None:
        return False
    if left["time"] < right["time"]:
        return True
    if left["time"] > right["time"]:
        return False
    return left["index"] < right["index"]


def exemption_assessment(diagnostic):
    wid = diagnostic.get("exemption_id")
    if wid is None or wid not in exemption_by_id:
        return (
            "NOT_CLAIMED",
            False,
            "NOT_APPLICABLE",
            "NOT_APPLICABLE",
            None,
        )

    w = exemption_by_id[wid]
    release_time = pd.Timestamp(diagnostic["release_time"])

    scope_known = (
        diagnostic["jurisdiction"] is not None
        and diagnostic["customer_type"] is not None
        and diagnostic["amount"] is not None
    )
    scope_match = (
        scope_known
        and diagnostic["jurisdiction"] == w["scope_jurisdiction"]
        and diagnostic["customer_type"] == w["scope_customer_type"]
        and diagnostic["amount"] <= float(w["amount_cap"])
    )

    evidence_time = w["approval_evidence_time"]
    strong_evidence = (
        w["evidence_quality"] == "strong"
        and pd.notna(evidence_time)
    )
    time_match = (
        strong_evidence
        and evidence_time <= release_time
        and w["effective_from"] <= release_time
        and release_time < w["expires"]
    )

    if not strong_evidence:
        status = "REVIEW_REQUIRED_EXEMPTION_EVIDENCE"
    elif w["approved_by"] != "Head_Compliance":
        status = "UNSUPPORTED_APPROVER"
    elif not time_match:
        status = "OUTSIDE_EFFECTIVE_TIME"
    elif not scope_match:
        status = "OUTSIDE_OR_UNKNOWN_SCOPE"
    elif w["waives_rule"] != "R1 only":
        status = "UNSUPPORTED_WAIVER_SCOPE"
    else:
        status = "VALID_FOR_R1"

    return (
        status,
        status == "VALID_FOR_R1",
        "TRUE" if scope_match else ("FALSE" if scope_known else "UNKNOWN"),
        "TRUE" if time_match else "FALSE",
        w["evidence_quality"],

## 6. Why Control-Flow-Only Conformance Is Insufficient

PM4Py can establish that an activity sequence matches, or is compatible with, a discovered control-flow model. It does not, by itself, establish that the correct data obligations were active at each event.

1. **Final-state leakage**  
   A process model treats `Create_Transaction` and `Release_Funds` principally as activities. It does not know that TX-301’s amount changed from 80,000 to 125,000 or that TX-311’s jurisdiction changed between review and release. Reading a final-case export can therefore evaluate the wrong state.

2. **Correct order but wrong reviewed state**  
   An enhanced review may precede release yet precede a later material update. The token sequence can look valid even though the review did not cover the data that governed release.

3. **Post-hoc exemption confusion**  
   A late `Record_Exemption` or release reference can be mistaken for timely approval. EX-77 and EX-88 show that record time, displayed approval time, signature creation time, and actual approval evidence can differ.

4. **Material-change invalidation**  
   `Standard_Review  Enhanced_Review  Release_Funds` or `Enhanced_Review  Release_Funds` can be flow-valid while failing R4. The increase percentage is hidden in data attributes, not in activity labels.

5. **Conditional activation**  
   R1 applies only to a non-DE amount of at least EUR 100,000. R2 applies only to HIGH risk or PEP. A fixed model forcing both branches for every case produces false positives; a permissive model that allows either branch produces false negatives.

6. **Review-type conflation**  
   A model allowing `Compliance_Approve` before release may accept TX-307, even though the approval covered only a standard packet and no enhanced review occurred. The required review type is semantic, not merely a permitted next token.

7. **Missing-data equivalence**  
   Known EUR 90,000 and unknown amount can have the same activity sequence but different evidential consequences. A control-flow model generally treats them as equivalent. Treating unknown as low can incorrectly turn `INDETERMINATE` into `COMPLIANT`.

8. **Same-timestamp collapse**  
   Timestamp-only grouping loses the relative order of TX-311’s review and jurisdiction change. A model may accept the same two activities in either order, although the state attached to the review differs.

9. **Sanctions-list semantics**  
   `Sanctions_Screen  Sanctions_List_Update  Release_Funds` is plainly different from `Sanctions_Screen  Sanctions_List_Update  Sanctions_Screen  Release_Funds`. A screen must concern the relevant jurisdiction and the list version effective after the addition.

10. **Branch identity and data scope**  
    An approval following one enhanced review may cover the same HIGH/PEP case, not every branch or every changed amount. Generic model conformance does not establish which obligation, data version, or exemption scope the review/approval actually covered.

11. **Model discovery is descriptive, not prescriptive**  
    An observed-case OCB graph describes what happened in the sample. Absence of a path in a case is not proof that the activity was impossible, and presence of an edge does not prove that every real execution should or did follow it.

A faithful process model would need typed data objects, temporal semantics, and guards or side-by-side verification logic. Even then, evidential authenticity and contradictory evidence would remain human adjudication concerns.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payloads**
   - Store a signed, immutable release instruction containing amount, currency, risk, jurisdiction, customer type, exemption references, and a data-version identifier.
   - Include release instruction ID, creation time, authorization time, actual disbursement time, and payload hash.
   - Never rely on settlement data as an implicit substitute for the release payload.

2. **Separate event, effective, record, and evidence timestamps**
   - Record `event_time`, `effective_from`, `recorded_at`, `observed_at`, and `known_at`.
   - For approvals, record trusted signature/approval time separately from certificate creation and database insertion time.
   - Support authorized retroactive corrections without rewriting original events.

3. **Stable event ordering**
   - Use an immutable event ID, stable source sequence, and per-case ordering key.
   - Never renumber historical events when late arrivals are imported.
   - Define timestamp precision and explicitly use `event_index` for equal timestamps.

4. **Rich attribute-change events**
   - Record old value, new value, reason, source, actor, change ID, effective time, and record time.
   - Distinguish an observed change from a correction whose effective time is earlier.
   - Represent explicit null distinctly from “no update,” with a documented business meaning.

5. **Review-document provenance**
   - Bind each review to the exact data snapshot/hash it examined.
   - Record reviewed rules, relevant risk/customer triggers, reviewer identity and authority, completion time, signature time, and any superseded review.
   - Make `Compliance_Approve` identify the specific review packet and version approved.
   - Automatically mark a review stale/invalidate it when a material amount change occurs.

6. **Policy versioning**
   - Store the policy version applicable at both review and release.
   - Define whether R1 uses R4’s 20% materiality boundary and which non-amount changes count as material.
   - Specify the percentage baseline, comparison precision, unknown-change treatment, and equal-timestamp semantics.

7. **Sanctions-list provenance**
   - Record addition/removal action, jurisdiction, list version, effective time, publication time, and source authority.
   - Bind each sanctions screen to the exact list version and timestamp it screened.
   - Require a new screen when an applicable later list version is effective.

8. **Strong exemption records**
   - Record exemption ID/version, approver identity, approval evidence, signature creation time, effective/expiry times, revocation, record/import time, and evidence provenance.
   - Encode scope and waived rule explicitly, including currency, amount bounds, customer type, and jurisdiction.
   - Do not accept a release reference, displayed backdate, or late database row alone as approval proof.
   - Link the release to the exact exemption version and evidence bundle relied upon.

9. **Explicit uncertainty and evidence adjudication**
   - Represent `UNKNOWN`, `CONTRADICTED`, and `NOT_APPLICABLE` separately.
   - Add a human-adjudication event for disputed exemption evidence.
   - Do not convert an unresolved historical decision into a passed control merely because later evidence was unavailable at ingestion time.

These changes would allow PM4Py to remain useful for sequence and timing diagnostics while moving attribute validity, policy activation, and exemption authenticity into explicit, testable controls.
