## 2. Raw-versus-normalized interpretation

The raw/mapped fitness gap in March reflects a semantic provenance issue: the normative process model expects `Validate Eligibility`, but the migrated system emits `Eligibility Screen` and duplicates `Open Case` events. The recovery of mapped fitness to ~0.90 proves the core sequence of activities (Register -> Eligibility -> Collect -> Assess) remained largely intact after mapping. However, a label mapping only proves that the expected sequence of *recorded* activities matches; it does not prove the underlying business process was unchanged. The migration may have altered user behavior even if the abstract activity name maps perfectly. 

Duplicated technical events and missing resource identifiers affect different process-mining artifacts. Duplicates inflate variant counts and distort Directly-Follows Graphs (DFGs) by inserting spurious edges (e.g., `Open Case -> Register`). Missing resources break resource-handover networks, prevent organizational mining, and bias service-time calculations if missingness correlates with specific activity types or teams. 

The post-May DFG and performance patterns cannot be dismissed as mere logging drift. import pm4py

def process_event_log(log_df: pd.DataFrame):
    """
    Formats and analyzes an event-level dataframe using PM4Py.
    Assumes log_df has columns: case_id, activity, timestamp, resource.
    """
    # 1. Format dataframe for PM4Py
    formatted_df = pm4py.format_dataframe(log_df.copy(), case_id='case_id', 
                                          activity_key='activity', timestamp_key='timestamp',
                                          resource_key='resource')
    
    # 2. Slice time windows (e.g., Pre and Post Migration)
    # Pre-migration: Jan-Feb 2026
    pre_migration = pm4py.filter_time_range(formatted_df, "2026-01-01 00:00:00", "2026-02-28 23:59:59")
    # Post-migration: Mar 2026 onwards
    post_migration = pm4py.filter_time_range(formatted_df, "2026-03-01 00:00:00", "2026-12-31 23:59:59")
    
    # 3. Compute monthly DFGs
    # Example: Discover DFG for pre-migration
    dfg_pre, sa_pre, ea_pre = pm4py.discover_dfg(pre_migration)
    
    # 4. Compute variants
    variants_pre = pm4py.get_variants(pre_migration)
    variants_post = pm4py.get_variants(post_migration)
    
    # 5. Compute temporal profiles
    temporal_profile_pre = pm4py.discover_temporal_profile(pre_migration)
    
    # 6. Optionally discover log skeletons or DECLARE models
    skeleton_pre = pm4py.discover_log_skeleton(pre_migration)
    # declare_model = pm4py.discover_declare(pre_migration) # If supported in PM4Py version
    
    # 7. Compare raw and normalized label mappings without overwriting original log
    # Create a mapped view for normalized analysis
    mapped_df = formatted_df.copy()
    # Apply mapping without destroying original 'activity' column
    mapped_df['activity_mapped'] = mapped_df['activity'].replace({
        'Eligibility Screen': 'Validate Eligibility'
    })
    # Filter out duplicated Open Case events for mapped conformance checking
    mapped_df = mapped_df[~((mapped_df['activity'] == 'Open Case') & (mapped_df.duplicated(subset=['case_id', 'timestamp'], keep='first')))]
    
    # Re-format the mapped df for PM4Py to use the mapped column
    mapped_formatted = pm4py.format_dataframe(mapped_df, case_id='case_id', 
                                              activity_key='activity_mapped', timestamp_key='timestamp',
                                              resource_key='resource')
    
    return {
        "pre_migration_dfg": dfg_pre,
        "pre_migration_variants_count": len(variants_pre),
        "post_migration_variants_count": len(variants_post),
        "temporal_profile": temporal_profile_pre,
        "log_skeleton": skeleton_pre,
        "mapped_log": mapped_formatted
    }

2. IF the `Assess -> Request Info` loop rate exceeds baseline by 50%, THEN segment the event log by supplier to check for incomplete document bundles, BECAUSE supplier API disruptions or staffing issues can generate non-random rework loops.
3. IF p90 cycle time increases by more than 20% while median `Assess` service time remains stable, THEN investigate reconstructed queue waiting times and assessor capacity levels, BECAUSE resource attrition or queueing bottlenecks are driving performance drift rather than service execution delays.
4. IF high-complexity case volume spikes without a corresponding increase in standard cases, THEN compare against historical seasonal baselines, BECAUSE annual renewal seasons cause predictable population drift that should not be mistaken for a new behavioral anomaly.
5. IF missing resource identifiers exceed 2% of events, THEN isolate and exclude affected activities from organizational mining analyses, BECAUSE system migrations can break resource-handover networks and bias service-time calculations.
6. IF high-complexity cases exhibit decreasing waiting times while standard cases exhibit increasing waiting times post-policy change, THEN validate that the priority queue logic is functioning as intended, BECAUSE priority rules intentionally redistribute delay across case classes.
7. IF mapped model fitness declines concurrently with an increase in `Assess -> Senior Assessment` rates, THEN review high-complexity case routing policies and assessor training, BECAUSE persistent behavioral adaptation or seasonal complexity may be forcing standard assessors to escalate cases outside the normative control flow.
