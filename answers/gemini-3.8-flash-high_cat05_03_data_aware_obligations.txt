## 1. Temporal Data Semantics

### State Reconstruction and Sparse Updates (Handling Blanks)
In event logs originating from distributed financial messaging and workflow management systems, event rows represent discrete, sparse delta updates rather than full state snapshots. A blank (or `NaN`) cell in an event record indicates that the corresponding attribute was not modified by that event; it does not indicate that the attribute was cleared or set to null. 

State reconstruction proceeds strictly chronologically within each process instance (case) as an event-driven state machine:
$$\sigma_{i} = \text{update}(\sigma_{i-1}, e_i)$$
where $\sigma_i(a) = e_i(a)$ if $e_i(a)$ is non-blank, and $\sigma_i(a) = \sigma_{i-1}(a)$ otherwise. If an attribute has never been initialized prior to event $e_i$, its value remains `UNKNOWN` ($\bot$).

### Ordering Equal Timestamps (Tie-Breaking)
When multiple events share an identical timestamp $t(e_i) = t(e_j)$, the total execution order is uniquely determined by the source-system sequence identifier `event_index`:
$$e_i \prec e_j \iff \Big(t(e_i) < t(e_j)\Big) \lor \Big(t(e_i) = t(e_j) \land \text{event\_index}(e_i) < \text{event\_index}(e_j)\Big)$$

**Consequence:** State transitions execute sequentially according to `event_index`. Any state change introduced at `event_index` $k$ takes effect immediately and governs all evaluations at `event_index` $k+1$, even if both share the exact same microsecond or second timestamp. In TX-311, `Enhanced_Review` occurs at `event_index = 3` (timestamp `16:20:00Z`), followed by `Update_Jurisdiction` to `DE` at `event_index = 4` (timestamp `16:20:00Z`). Consequently, the review evaluated a `US` transaction, and the jurisdiction changed to `DE` *subsequent* to the review. Sorting naively on timestamps alone introduces race conditions and non-deterministic state evaluation.

### Identification of Material Changes
A "material data change" is an event-time mutation of an underlying business attribute that fundamentally alters the risk profile, regulatory obligations, or validity of prior due diligence:
1. **Material Amount Increase (R4):** An amount increase exceeding $20\%$ relative to the amount evaluated during the most recent `Standard_Review` or `Enhanced_Review` ($\frac{\text{amount}_{\text{new}} - \text{amount}_{\text{reviewed}}}{\text{amount}_{\text{reviewed}}} > 0.20$). Per R4, this invalidates prior reviews for amount-dependent obligations. A decrease does not invalidate prior reviews. An increase from an unknown baseline ($\bot$) cannot be classified as non-material without additional evidence.
2. **Risk Escalation (R2):** Any reclassification of `risk_level` to `HIGH` (e.g., adverse-media hit in TX-303).
3. **Customer Reclassification (R2):** Any update of `customer_type` to Politically Exposed Person (`PEP`) (e.g., beneficial ownership discovery in TX-307).
4. **Jurisdictional Change or Sanctions Addition (R1, R3):** An update modifying `jurisdiction`, or the addition of the current jurisdiction to an active sanctions watchlist prior to funds release (TX-304).

### Treatment of Final Attributes (Anti-Leakage Guarantee)
In relational database reporting, transactions are frequently analyzed using the final case-level state. In process compliance, this constitutes **retrospective data leakage** (look-ahead bias). Rule R7 strictly mandates that obligations must be evaluated using the state active at the moment of the trigger event (`Release_Funds`). Copying final case state backward in time is prohibited. In TX-305, an amount of EUR 150,000 appears at `Settlement_Confirmed` on 2026-04-07; projecting this value backward to `Release_Funds` at 2026-04-06 11:30:00Z violates event-time semantics, as the operational actor acted without an immutable amount payload.

### Multi-Dimensional Temporal Ontology
To resolve discrepancies between system events and legal validity, compliance evaluation distinguishes four orthogonal temporal dimensions:
1. **Event Time ($t_{\text{event}}$):** The physical clock timestamp when an activity occurred in the business domain (e.g., `Release_Funds` executed at 09:40:00Z).
2. **Effective Time ($t_{\text{effective}}$):** The temporal window $[\tau_{\text{start}}, \tau_{\text{expiry}}]$ during which an administrative decision, policy waiver, or classification legally applies (e.g., EX-77 effective from 09:00:00Z to 18:00:00Z).
3. **Record Time ($t_{\text{record}}$):** The system timestamp when the event or record was committed to persistent storage / the database (e.g., EX-77 recorded at 11:00:00Z following an IT outage).
4. **Evidence Time ($t_{\text{evidence}}$):** The timestamp at which an authoritative, cryptographically verifiable, or tamper-evident proof was established (e.g., Qualified Electronic Signature [QES] timestamp token at 09:05:00Z for EX-77 versus certificate creation at 10:30:00Z for EX-88).

**Evidentiary Reconciliation:** A late record time ($t_{\text{record}} > t_{\text{event}}$) does not invalidate an exemption if independent cryptographic evidence establishes that $t_{\text{evidence}} \le t_{\text{event}}$ (TX-302). Conversely, an assertion of earlier effective time ($t_{\text{effective}} \le t_{\text{event}}$) displayed on a backdated document is legally invalid if $t_{\text{evidence}} > t_{\text{event}}$ and lacks disinterested corroboration (TX-310).

### Formal Pseudo-Logic (R1–R7)

Let a trace be an ordered sequence of events $E = \langle e_1, e_2, \dots, e_n \rangle$.  
Define the strict total order $\prec$ over $E$:
$$e_i \prec e_j \iff \Big(t(e_i) < t(e_j)\Big) \lor \Big(t(e_i) = t(e_j) \land \text{event\_index}(e_i) < \text{event\_index}(e_j)\Big)$$

Let $\sigma(e, a)$ denote the latest known value of attribute $a$ at event $e$:
$$\sigma(e_k, a) = \begin{cases} e_k(a) & \text{if } e_k(a) \neq \text{blank} \\ \sigma(e_{k-1}, a) & \text{if } e_k(a) = \text{blank} \land k > 1 \\ \bot & \text{otherwise} \end{cases}$$

Define the predicate $\text{IsMaterialChange}(e)$:
$$\begin{aligned}
\text{IsMaterialChange}(e) \iff & \Big(\text{act}(e) = \text{'Create\_Transaction'}\Big) \\
& \lor \Big(\text{act}(e) = \text{'Update\_Amount'} \land \exists e_r \prec e \text{ s.t. } \text{act}(e_r) \in \{\text{'Enhanced\_Review'}, \text{'Standard\_Review'}\} \\
& \quad \land \forall e_r' (e_r \prec e_r' \prec e \implies \text{act}(e_r') \notin \{\text{'Enhanced\_Review'}, \text{'Standard\_Review'}\}) \\
& \quad \land \sigma(e, \text{amount}) \neq \bot \land \sigma(e_r, \text{amount}) \neq \bot \land \frac{\sigma(e, \text{amount}) - \sigma(e_r, \text{amount})}{\sigma(e_r, \text{amount})} > 0.20\Big) \\
& \lor \Big(\text{act}(e) = \text{'Risk\_Reclassify'} \land \sigma(e, \text{risk\_level}) = \text{'HIGH'}\Big) \\
& \lor \Big(\text{act}(e) = \text{'Update\_Customer\_Type'} \land \sigma(e, \text{customer\_type}) = \text{'PEP'}\Big) \\
& \lor \Big(\text{act}(e) = \text{'Update\_Jurisdiction'}\Big)
\end{aligned}$$

Define exemption validity $\text{ValidExemption}(x, e)$:
$$\begin{aligned}
\text{ValidExemption}(x, e) \iff & (x.\text{approved\_by} = \text{'Head\_Compliance'}) \\
& \land (x.\tau_{\text{effective\_from}} \le t(e) \le x.\tau_{\text{expires}}) \\
& \land (x.\text{jurisdiction} = \sigma(e, \text{jurisdiction})) \\
& \land (x.\text{customer\_type} = \sigma(e, \text{customer\_type})) \\
& \land (\sigma(e, \text{amount}) \neq \bot \land \sigma(e, \text{amount}) \le x.\text{max\_amount}) \\
& \land (x.t_{\text{evidence}} \le t(e) \land x.\text{evidence\_verified} = \text{True})
\end{aligned}$$

#### Rule Formulations at $e_{\text{rel}}$ where $\text{act}(e_{\text{rel}}) = \text{'Release\_Funds'}$:

- **R1 (Foreign High-Value Enhanced Review):**
  $$\begin{aligned}
  \text{Trigger}_{R1}(e_{\text{rel}}) & \iff \sigma(e_{\text{rel}}, \text{jurisdiction}) \neq \text{'DE'} \land \sigma(e_{\text{rel}}, \text{amount}) \ge 100{,}000 \\
  \text{Obligation}_{R1}(e_{\text{rel}}) & \iff \Big(\exists x \, (\sigma(e_{\text{rel}}, \text{exemption\_id}) = x \land \text{'R1'} \in x.\text{waives} \land \text{ValidExemption}(x, e_{\text{rel}}))\Big) \\
  & \quad \lor \Big(\exists e_{\text{er}} \prec e_{\text{rel}} \text{ s.t. } \text{act}(e_{\text{er}}) = \text{'Enhanced\_Review'} \\
  & \quad \land \forall e_m (e_{\text{er}} \prec e_m \prec e_{\text{rel}} \implies \neg \text{IsMaterialChange}(e_m))\Big)
  \end{aligned}$$

- **R2 (High-Risk or PEP Approval):**
  $$\begin{aligned}
  \text{Trigger}_{R2}(e_{\text{rel}}) & \iff \sigma(e_{\text{rel}}, \text{risk\_level}) = \text{'HIGH'} \lor \sigma(e_{\text{rel}}, \text{customer\_type}) = \text{'PEP'} \\
  \text{Obligation}_{R2}(e_{\text{rel}}) & \iff \exists e_{\text{er}}, e_{\text{ca}} \text{ s.t. } \text{act}(e_{\text{er}}) = \text{'Enhanced\_Review'} \land \text{act}(e_{\text{ca}}) = \text{'Compliance\_Approve'} \\
  & \quad \land e_{\text{er}} \prec e_{\text{ca}} \prec e_{\text{rel}}
  \end{aligned}$$

- **R3 (Sanctions-List Update):**
  $$\begin{aligned}
  \text{Trigger}_{R3}(e_{\text{rel}}) & \iff \exists e_{\text{upd}} \prec e_{\text{rel}} \text{ s.t. } \text{act}(e_{\text{upd}}) = \text{'Sanctions\_List\_Update'} \land e_{\text{upd}}(\text{jurisdiction}) = \sigma(e_{\text{rel}}, \text{jurisdiction}) \\
  & \quad \land \forall e_{\text{scr}} \prec e_{\text{upd}} (\text{act}(e_{\text{scr}}) = \text{'Sanctions\_Screen'}) \\
  \text{Obligation}_{R3}(e_{\text{rel}}) & \iff \exists e_{\text{new\_scr}} \text{ s.t. } \text{act}(e_{\text{new\_scr}}) = \text{'Sanctions\_Screen'} \land e_{\text{upd}} \prec e_{\text{new\_scr}} \prec e_{\text{rel}}
  \end{aligned}$$

- **R4 (Material Amount Invalidation):**
  $$\text{Invalidated}(e_{\text{rev}}, e_{\text{amt}}) \iff \text{act}(e_{\text{rev}}) \in \{\text{'Enhanced\_Review'}, \text{'Standard\_Review'}\} \land e_{\text{rev}} \prec e_{\text{amt}} \land \frac{\sigma(e_{\text{amt}}, \text{amount}) - \sigma(e_{\text{rev}}, \text{amount})}{\sigma(e_{\text{rev}}, \text{amount})} > 0.20$$

- **R6 (Missing Data Defeasibility):**
  $$\text{If } \exists a \in \{\text{amount}, \text{jurisdiction}\} \text{ s.t. } \sigma(e_{\text{rel}}, a) = \bot \implies \text{Eval}(R1, e_{\text{rel}}) = \text{INDETERMINATE}$$
  $$\text{If } \exists a \in \{\text{risk\_level}, \text{customer\_type}\} \text{ s.t. } \sigma(e_{\text{rel}}, a) = \bot \implies \text{Eval}(R2, e_{\text{rel}}) = \text{INDETERMINATE}$$

## 4. Ambiguities and Alternative Readings

### TX-305 (Governing Classification: INDETERMINATE)
- **Primary Finding & Basis:** `INDETERMINATE`. At `Release_Funds` (11:30:00Z), the amount attribute was missing ($\bot$). The review dossier noted "review document has no amount" and the release message omitted the amount. Rule R6 explicitly commands: *"Do not silently default missing amount, risk, jurisdiction, or customer type to a low-risk value. Classify as INDETERMINATE when a decisive trigger cannot be established or excluded, unless other evidence resolves it."* Rule R7 prohibits copying the subsequent settlement amount (EUR 150,000 on 2026-04-07) backward into the release event state.
- **Alternative Reading 1 (Retrospective Substantive Noncompliance):** An auditor performing a post-clearing investigation could argue that the financial transaction that cleared the banking network was in fact EUR 150,000. Under this substantive view, R1 was triggered in fact. Because `Enhanced_Review` was conducted blind without amount visibility, the reviewer could not have evaluated the financial exposure. Furthermore, under R4, *"an increase from an unknown amount is not safely classifiable without additional evidence."* Releasing funds with an unverified amount payload is a gross operational control failure, warranting **NONCOMPLIANT**.
- **Alternative Reading 2 (Strict Formal Procedural Compliance):** If the internal clearing system defaults missing payloads to a zero-balance pre-authorization ping or micro-collateral transfer under EUR 10,000, R1 was never triggered at event time. Under a closed-world system assumption where unrecorded triggers do not exist, the case would be deemed **COMPLIANT**.
- **Resolving Evidence Needed:** An immutable, cryptographically signed release payload instruction emitted by payment gateway `rel05` at 11:30:00Z containing the exact target principal transfer amount.

### TX-310 (Governing Classification: NONCOMPLIANT)
- **Primary Finding & Basis:** `NONCOMPLIANT`. Exemption EX-88 displayed an approval time of 08:50:00Z and effective time of 08:00:00Z. However, cryptographic evidence proves that the qualified signing certificate was only created at 10:30:00Z—30 minutes *after* release at 10:00:00Z. Rule R5 dictates: *"the evidence supports that approval existed at the relevant time. A late database record can be evidence of earlier approval, but a displayed backdated field alone is not conclusive."* The only evidence supporting timely approval is oral testimony from the transaction requester, who has an acute personal interest in validating the transaction. The exemption is legally post-hoc.
- **Alternative Reading 1 (INDETERMINATE under Evidentiary Stay):** If corporate compliance governance recognizes emergency verbal approvals from Head_Compliance subject to same-day written ratification, the requester’s testimony creates an unresolved issue of fact. An auditor might suspend determination pending subpoena of Head_Compliance's communications, classifying the case as **INDETERMINATE**.
- **Alternative Reading 2 (JUSTIFIED_EXCEPTION):** If Head_Compliance provides a formal, sworn deposition confirming that verbal approval was granted at 08:45:00Z due to urgent market conditions, and policy allows verbal waivers, the release would be classified as **JUSTIFIED_EXCEPTION**.
- **Resolving Evidence Needed:** Contemporaneous PBX call logs, signed instant-messaging audit trails (e.g., Slack/Teams enterprise vault), or a Head_Compliance portal approval log generated prior to 10:00:00Z.

### TX-302 (Governing Classification: JUSTIFIED_EXCEPTION / COMPLIANT)
- **Primary Finding & Basis:** `JUSTIFIED_EXCEPTION` (or `COMPLIANT`). EX-77 was displayed with approval at 09:05:00Z, effective 09:00:00Z. Crucially, the Qualified Electronic Signature (QES) timestamp token is verified at 09:05:00Z ($t_{\text{evidence}} \le t_{\text{release}}$). The late database insertion at 11:00:00Z was caused by a documented, verified system outage. Therefore, EX-77 was fully effective and valid at release (09:40:00Z). Moreover, `Enhanced_Review` was actually performed at 09:20:00Z without intervening material changes, meaning the case satisfied R1 both directly and via waiver.
- **Alternative Reading 1 (Procedural Noncompliance via Database-Gating Policy):** If the financial institution operates under a strict "central database authority" rule stating that no exemption may be acted upon until successfully committed to the central compliance database (to prevent operational reliance on cached or unverifiable local documents during outages), the release at 09:40:00Z preceded DB commit (11:00:00Z), rendering the release technically **NONCOMPLIANT**.
- **Alternative Reading 2 (Direct Conformance Ignoring Exemption):** Because `Enhanced_Review` was completed by `rev02` at 09:20:00Z, R1 was satisfied on the merits regardless of the exemption, categorizing the case strictly as **COMPLIANT** rather than an exception.
- **Resolving Evidence Needed:** The institution’s written standard operating procedure (SOP) regarding business continuity and whether offline reliance on cryptographic QES tokens is authorized during central system outages.

### TX-311 (Governing Classification: COMPLIANT)
- **Primary Finding & Basis:** `COMPLIANT`. At `Release_Funds` (16:30:00Z), the reconstructed state was `jurisdiction = DE`, `amount = 115000`. The trigger condition for R1 is: *"if the current jurisdiction is not DE and the current amount is at least EUR 100,000"*. Because the jurisdiction at release is `DE`, R1 is not triggered. Furthermore, `Enhanced_Review` was executed at `event_index = 3` (16:20:00Z), followed immediately by `Update_Jurisdiction` to `DE` at `event_index = 4` (16:20:00Z).
- **Alternative Reading 1 (Circumvention / Regulatory Evasion):** The transaction was originally logged as `US` and reviewed under `US` cross-border criteria. Changing the jurisdiction to `DE` at the exact same timestamp after review suggests an attempt to bypass foreign transfer oversight ("jurisdiction shopping"). A substantive risk auditor could view the jurisdiction shift as a material data change that invalidated the review’s premise, asserting that releasing funds under an unreviewed domestic routing is **NONCOMPLIANT**.
- **Alternative Reading 2 (Race Condition / Inverted Order):** If a logging parser ignores `event_index` and sorts events arbitrarily, `Update_Jurisdiction` could be evaluated as preceding `Enhanced_Review`. In that reading, the reviewer evaluated a `DE` transaction, eliminating any suspicion of unreviewed jurisdiction modification.
- **Resolving Evidence Needed:** The commercial contract and SWIFT payment routing instructions confirming whether the beneficiary account was legally domiciled in Germany (`DE`) or merely routed through an intermediary bank.

## 6. Why Control-Flow-Only Conformance Is Insufficient

Pure control-flow process mining formalisms (such as standard Petri nets, directly-follows graphs, and classical propositional DECLARE) evaluate conformance solely on the existence and ordering of activity labels. In data-aware, risk-gated financial processes, this abstraction fundamentally breaks down. Below are six distinct failure modes:

1. **Final-State Leakage (Back-Projection Bias):**
   Standard process mining tools flatten case attributes from the final database state. In TX-305, an amount of EUR 150,000 is recorded at `Settlement_Confirmed` on day two. A control-flow miner that enriches the trace with this static case attribute evaluates the case as having been EUR 150,000 from the start, retroactively fabricating an obligation that the release agent could not have observed at `Release_Funds`. Conversely, if an initial high-risk transaction is negotiated down to a low value before release, final-state evaluation would retroactively excuse a required review that was legally mandatory during execution.

2. **Post-Hoc and Backdated Exemptions (Evidentiary Decoupling):**
   Control flow can only check if an activity named `Record_Exemption` occurred or if an `exemption_id` string exists. In TX-302 and TX-310, the control-flow traces appear identical: both feature `Release_Funds` referencing an exemption, followed by `Record_Exemption` at 11:00:00Z. A control-flow engine cannot distinguish between TX-302 (where a Qualified Electronic Signature was cryptographically anchored at 09:05:00Z prior to release, with delayed recording due to a network outage) and TX-310 (where the signing certificate was fabricated at 10:30:00Z after release, and the displayed time was backdated). Pure control flow is blind to cryptographic integrity and evidence timestamps.

3. **Material Data Changes After Review (Review Invalidation):**
   Control-flow models can check whether `Enhanced_Review` precedes `Release_Funds`. In TX-309, `Enhanced_Review` occurred at 15:25:00Z and `Release_Funds` occurred at 15:35:00Z; DECLARE marks this trace with a fitness of $1.0$ (perfect conformance). However, at 15:28:00Z, `Update_Amount` increased the transaction from EUR 118,000 to EUR 145,000 (+22.88%). Under Policy R4, an increase exceeding 20% invalidates the prior review. Control flow sees an intervening activity label (`Update_Amount`), but cannot evaluate the mathematical ratio between payload values, completely missing the fact that the released payment was unreviewed.

4. **Dynamic Conditional Activation (Data-Driven Branching):**
   In financial compliance, obligations are activated dynamically based on payload thresholds. In TX-301, the trace starts at EUR 80,000 (standard review threshold) and increases to EUR 125,000, dynamically triggering R1. In TX-307, beneficial ownership analysis reclassifies the customer as PEP, dynamically triggering R2. A control-flow model cannot represent that an activity is optional under state $\sigma_1$, mandatory under state $\sigma_2$, and prohibited under state $\sigma_3$. Imposing a static control-flow constraint (e.g., `Enhanced_Review` must precede `Release_Funds`) generates false alarms on legitimate low-risk domestic transactions (such as TX-304 and TX-308), while missing violations on dynamically escalated traces.

5. **Incomplete Observability and Missing Data (Tristate Defeasibility):**
   Classical process conformance is bivalent: a trace either fits or does not fit. Real-world logging frequently encounters partial observability, network drops, and missing fields (TX-305). Under Policy R6, missing data cannot be defaulted to low risk, nor can it be condemned without proof; it must evaluate to `INDETERMINATE`. Control-flow engines cannot handle three-valued logic (True, False, Indeterminate) or distinguish between an obligation that was breached versus an obligation whose trigger condition is unprovable.

6. **Sub-Second Concurrency and Timestamp Tie Inversion:**
   Real-time event streaming systems often produce identical physical timestamps for clustered events. In TX-311, `Enhanced_Review` and `Update_Jurisdiction` to `DE` share the timestamp `16:20:00Z`. Control-flow engines sorting solely on timestamps can arbitrarily reorder these events. If `Update_Jurisdiction` is sorted first, the trace appears as though the reviewer reviewed a domestic German transaction; if sorted second, the review evaluated a foreign US transaction, and jurisdiction changed immediately afterward. Without sub-second sequence numbers (`event_index`) directly tied to point-in-time state transitions, control-flow conformance produces non-deterministic verdicts.

## 7. Recommended Logging and Control Improvements

To eliminate indeterminate classifications, prevent post-hoc backdating, and ensure automated, deterministic compliance verification, the enterprise architecture must implement the following six structural enhancements:

### 1. Cryptographically Signed Immutable Release Payloads
- **Design:** At the invocation of `Release_Funds`, the payment gateway must assemble a canonical JSON/protobuf payload containing the exact execution parameters: `{case_id, release_timestamp, amount, currency, beneficiary_jurisdiction, customer_type, risk_level, applied_exemption_hash}`.
- **Implementation:** The releasing actor and gateway must co-sign this payload using an asymmetric hardware security module (HSM) key. This immutable snapshot is stored in the event log. 
- **Benefit:** Completely eliminates vulnerabilities like TX-305, where an event occurs with missing amounts, preventing retroactive speculation about what financial value was actually authorized.

### 2. Multi-Dimensional Temporal Logging Architecture
Every log record must explicitly persist four separate, immutable temporal columns:
1. `event_timestamp`: Physical clock time of the business action.
2. `effective_from_timestamp` & `effective_until_timestamp`: The business/legal validity window.
3. `record_timestamp`: System database commit time with auto-generated database server clock.
4. `evidence_timestamp`: Cryptographically certified timestamp token (RFC 3161 TSA) from an external timestamping authority.
- **Benefit:** Instantly distinguishes legitimate technical catch-up delays (TX-302) from fraudulent backdating and post-release sham certificates (TX-310).

### 3. Dynamic Rule-Version and Policy Hash Binding
- **Design:** Compliance rule sets (R1–R7) must be version-controlled as code. Every review, approval, and release event must log the active `policy_version_id` and the cryptographic hash of the compliance rule configuration under which the assessment was performed.
- **Benefit:** Guarantees auditability across regulatory policy changes, preventing retro-active enforcement of newly introduced thresholds.

### 4. Structured Exemption Registers with Scope Fingerprinting
- **Design:** Exemptions must be managed in a dedicated, tamper-evident registry (e.g., an append-only verifiable ledger). When an exemption is granted, Head_Compliance’s digital signature must bind directly to the exemption’s exact scope parameters: `SHA-256(jurisdiction || customer_type || max_amount || waiver_rule_id)`.
- **Pre-Release Check:** The operational workflow system must programmatically validate the hash of the referenced exemption against the active register prior to enabling the `Release_Funds` action.
- **Benefit:** Prevents scope creep and eliminates reliance on self-serving oral assertions from transaction requesters.

### 5. Granular Change Provenance and Mutation Vectors
- **Design:** Data updates must not be recorded as detached event labels. Events like `Update_Amount`, `Risk_Reclassify`, and `Update_Jurisdiction` must log:
  - `prior_value` and `new_value`.
  - `delta_percentage` (for amounts).
  - `mutation_reason_code` (e.g., "customer order change", "adverse media hit").
  - `initiator_identity` and `authorizing_party`.
- **Automated Invalidation Hook:** If `delta_percentage > 20%`, the state engine must automatically flag all prior review tokens as `INVALIDATED_BY_MUTATION`, programmatically locking the release gate until a refreshed review task is completed.

### 6. Deterministic Distributed Ordering and Sequence Numbers
- **Design:** Replace uncoordinated client timestamps with monotonically increasing sequence counters (`event_index`) paired with Hybrid Logical Clocks (HLC) or distributed transaction identifiers across microservices.
- **Rule:** The database schema must enforce a compound primary key: `(case_id, hlc_timestamp, event_sequence_no)`.
- **Benefit:** Ensures a strict, total ordering over concurrent events sharing identical wall-clock timestamps (TX-311), eliminating race conditions in conformance pipelines.
