## 1. Consistency rules and evidence model

To repair the OCEL dataset, we apply a hierarchy of evidence standards ranging from technical constraints to business heuristics. These rules guide the abductive reasoning process, distinguishing between what must be true and what is likely true.

**Hard Invariants:**
- **Temporal Ordering:** Events must occur in a sequence consistent with their timestamps (e.g., `Create Order` before `Add Item`). Violations here invalidate the repair.
- **Unique Object IDs:** An object ID (e.g., `ORD-A`) must appear consistently across events.
- **OCEL Schema:** The `observed_related_objects` field must be consistent with the source event type. For instance, a `Record Payment` event cannot list an `Order` as a direct related object unless the schema supports indirect linking via an Invoice.

**Strong Defaults:**
- **Lifecycle Flow:** Standard supply chain lifecycles imply `Create Order`  `Add Item`  `Pack`  `Dispatch`  `Deliver`  `Invoice`  `Payment`.
- **Cardinality Constraints:** `Create Order` relates to exactly one Order. `Dispatch Package` typically relates to one Package and one Delivery, though bulk dispatches may link multiple Packages to one Delivery.
- **Identifier Affinity:** `external_ref` values in events should match `carrier_ref` or `route_hint` in objects (e.g., `N-420` matches `DEL-X`).

**Weak Heuristics:**
- **Arithmetic Consistency:** `total` in Invoice roughly equals sum of `declared_value` in Orders. This is evidence, not proof, due to taxes/fees.
- **Customer Consistency:** `customer` attribute in `Order` and `Invoice` should match.
- **Amount Matching:** Payment amounts often align with Order values or Invoice totals, but partial payments are possible.

**Evidence Against a Repair:**
- **Explicit Exclusion:** If an object is listed in `observed_related_objects`, we cannot contradict it, but we can infer missing relations if an object is absent from the list despite strong heuristic evidence.
- **Wildcard Ambiguity:** `N-42*` in `ev11` provides no definitive match; inferring a specific link without further data risks circular reasoning.

We combine these by prioritizing hard invariants. Strong defaults guide the addition of missing E2O/O2O edges where logical gaps exist. Weak heuristics provide confidence scores for ambiguous cases (e.g., `PAY-2` settlement). We treat `observed_related_objects` as the ground truth for existing edges but allow inference for missing ones where the lifecycle logic is broken (e.g., an unpaid invoice).

## 8. Over-repair warnings

1.  **Arithmetic Over-matching:** Assuming `PAY-2` (130) settles `INV-44` (230) solely because 130 matches `ORD-A` (130). This ignores the possibility that `INV-44` is a bundled invoice for multiple orders where `PAY-2` is a partial payment.
2.  **Wildcard Assumption:** Inferring that `ev11` (`N-42*`) confirms `DEL-Y` (`N-421`) because the prefix matches. This ignores the possibility that `N-42*` is a generic "system" ID unrelated to specific carrier routes.
3.  **Package Aggregation Bias:** Assuming `PK-8` contains `IT-B1` implies a specific business rule (consolidation) that might not hold for other packages. Over-repairing might enforce a "consolidation" pattern where it does not exist.
4.  **Lifecycle Closure:** Forcing `ORD-B` to be confirmed by `ev11` ignores the possibility that `ORD-B` was not delivered or was delivered but the confirmation event was lost/corrupted. This distorts delivery success rates.
5.  **Invoice Scope Expansion:** Adding `INV-44 | bills | ORD-B` assumes the invoice covers the full scope. If `ORD-B` was actually billed separately (e.g., `INV-45` missing from dataset), this repair creates a "phantom" link that masks data quality issues in the source system.
