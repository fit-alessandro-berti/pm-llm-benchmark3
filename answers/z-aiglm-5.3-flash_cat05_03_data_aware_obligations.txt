## 1. Temporal Data Semantics

**State reconstruction (causal replay).** For each case I replay events in the total order `` defined by `(time:timestamp, event_index)` ascending (R7). Each event may update a subset of `{amount, risk_level, jurisdiction, customer_type}`; every other attribute carries forward. The state *snapshot at event e* consists of the last written value of each attribute among events `d  e`. Nothing is copied forward past a snapshot boundary and nothing is copied backward.

**Blank cells.** A blank attribute cell on a nonCreate event means *"no update at this event"* — the previously governing value persists. On a `Create_Transaction`, a blank attribute means the **initial value is genuinely unknown** (there is no prior value to inherit; e.g., TX305's amount). These two meanings are different and are implemented differently: forward-fill propagates only past values; a Createtime blank stays `NULL` forever unless updated later.

**Equal timestamps.** Events sharing a timestamp are sequenced strictly by `event_index` (lower index first). Consequence: in TX311, `(16:20, index 3)` = Enhanced_Review precedes `(16:20, index 4)` = Update_Jurisdiction, so the ER ran under `jurisdiction=US`, and the state at release (16:30) is `DE`. If the tie-break were reversed, the *audit story* of the ER changes, although (see §4) the R1 outcome at release happens to be robust in this instance. Ties make `` a genuine total order, so every "after X and before Y" predicate is decidable without clock-resolution heuristics.

**Material data changes.** I distinguish:
- *Plain change*: any event that writes a tracked attribute (including Create as baseline). Tracked as `last_material_change`.
- *Invalidating change (R4)*: an `Update_Amount` where `new > old × 1.20`, computed against the amount observed at the most recent, not-yet-invalidated Standard_Review/Enhanced_Review ("anchor"). An invalidating increase voids that anchor for amount-dependent obligations until a fresh review. A decrease (TX308) never invalidates. An increase from an unknown prior (not present here, but coded) is *unclassifiable*, not assumed benign.

Interpretive choice (defensible alternatives noted in §4): I read R1's "after the latest material data change" as "after the latest change that is *material for the obligation*", i.e., changes that under R4 would not invalidate the review (decreases, sub20 % increases) do not break the R1 chain; but I compute the strict reading (any write breaks the chain) as a parallel flag.

**Final attributes.** The final row of a case is never projected backward. Example traps handled: TX303's final `risk=HIGH` must not make the 08:xxstyle early events look HIGH-governed; TX311's final `DE` must not make its 16:20 ER look like a review "of DE".

**Four time notions.**
- *Event time*: when the business step actually executed (the log timestamp).
- *Effective time*: when a value or entitlement begins to govern (attribute updates here are effective at their event timestamp per the task instruction; exemption records may declare an earlier `effective_from`).
- *Record time*: when the fact entered the system (`Record_Exemption` at 11:00 for TX302/TX310; log-insert latency).
- *Evidence time*: when corroborating artifacts were cryptographically produced (qualified signature 09:05 for EX77; signingcertificate creation 10:30 for EX88) or measured (settlement 150000 at Apr 07 08:00).

Record time and evidence time can only *support or undermine* a claim that an entitlement existed at some earlier event time; they never retroactively change the governing value at that event time, except where R5 explicitly lets a late database record serve as evidence of earlier approval.

## 4. Ambiguities and Alternative Readings

**TX305 (INDETERMINATE).** Resolution paths: (a) an immutable release payload showing amount  100000  R1 activates; then ER(11:15)  release(11:30) with no intervening change discharges it  COMPLIANT — *provided* the ER demonstrably covered 100000, which today is unknowable because the review document had no amount either; (b) payload < 100000  no trigger  COMPLIANT trivially; (c) a bank-side confirmation that settlement 150000 equals the release amount *plus* tolerances would move the estimate but still leave a temporal bridge problem (settlement is Apr07 evidence at settlement time, not release time). What keeps it INDETERMINATE is that the trigger threshold can neither be established nor excluded — exactly the R6 situation. A different interpretation ("open a mandatory review whenever the amount feed is dead") would manufacture a R1-adjacent violation even below threshold; that is a control recommendation, not a finding.

**TX310 (INDETERMINATE, leaning NONCOMPLIANT).** Flips to **JUSTIFIED_EXCEPTION** if an independent (non-requester) contemporaneous Head_Compliance attestation — email, minted approval ticket, committee minute — with verifiable timestamp  10:00 surfaces, or if the signing infrastructure can prove the 10:30 certificate merely *serialised* a signature operation performed earlier with trusted local time anchors. Flips to **NONCOMPLIANT** if the approver affirms no approval occurred before 10:00, or if policy assigns conclusive weight to the conflicted witness contradiction. The remaining interpretive lever: how much weight an interested party's recollection carries against silence of crypto evidence — I weight it below the certificate, consistent with R5's distrust of self-serving backdating.

**TX302 (addressed explicitly).** Reading A (mine): R1 is discharged by the ER itself, so the late-recorded exemption is redundant; classification COMPLIANT stands even if the outage documentation were questioned. Reading B: if one interprets R1 as *either* ER *or* exemption and further requires that any claimed exemption be evidenced at release, EX77 survives (qualified sig 09:05, hash valid, documented outage per R5's late-record allowance)  JUSTIFIED_EXCEPTION-equivalent, same practical result. Reading C (most punitive): if an org demanded that releases *riding on* exemptions have the exemption registered before release as a control (a hard deadline stricter than R5's evidential test), TX302 would become procedurally defective — but that is an extra-legal house rule, not derivable from R1–R7.

**TX311 (addressed explicitly).** Three levers: (1) *Tie-break*: reversing index order would place the jurisdiction update before the ER — yet the release-time state is DE under both conventions, so the formal R1 outcome is invariant; the tie-break instead determines whether the ER "saw" the US configuration (audit completeness). (2) *Effective time*: the outcome is hostage to the doctrine that the jurisdiction update is effective at its own event timestamp. If the update were shown effective only later (e.g., overnight batch publication), the release would be governed by US/115000  R1 triggers, latest material change 16:20  ER  NONCOMPLIANT draft. (3) *Gaming hypothesis*: a suspicious reading — switch jurisdiction seconds after review — cannot be refuted from this log alone; change-provenance sequencing (§7) is what distinguishes legitimate life-cycle migration from threshold evasion.

**TX306 (alternative reading).** Strict textual reading of R1 ("after the latest *material data change*" = any write) makes the +4.5 % update at 12:30 break the ER chain  NONCOMPLIANT despite R4's <20 % benignity carve-out. I adopt the policy-coherent reading because R4 would be otherwise purposeless, but a regulator with the strict glossary would disagree; the decisive artifact would be the published definition of "material" plus confirmation that Compliance_Approve(12:25) covered an anticipated amount range.

**TX308 (alternative reading).** Same fork: strictly, ER(14:20) precedes the 14:25 write  R1 failure. Substantively, the only change is a 29 % *decrease* that lowers exposure and never enters R4's invalidation logic; also note the boundary case "at least 100000" is inclusive, so even after the decrease R1 is live and relies on the surviving ER.

**TX307 (brief).** Alternative defended interpretation would hold that Head_Compliance approving the packet *knowingly* (13:12, after the 13:05 PEP flag visible to reviewers) substantially satisfies R2's protective intent; the supplied semantic fact ("a Compliance_Approve that reviewed only a standard packet does not cure… unless you defend a different interpretation") permits but burdens this defense. I decline it: R2 conjoins an ER-precondition that never occurred, and the packet's content is admittedly standard.
