# 1. Assumptions, objectives, and decision variables

## Assumptions

- **A1. Demand model.** Expected block arrivals are used as Poisson rates for sampled arrival counts. For the capacity calculations below I use the expected counts; for tail estimates I interpret the service ranges as independent uniform draws. This is labeled as an assumption because the prompt gives only two-hour block expectations, not an arrival distribution.
- **A2. Service-time model.** Each activity draws from the ordinary range with probability `1-p_complex` and from the complex-tail range with probability `p_complex`; the resource multiplier then stretches that base draw. The mean base service times are therefore:
  - Intake: `0.92*6.5 + 0.08*12 = 6.94`
  - Mechanical: `0.85*23 + 0.15*45 = 26.30`
  - Electrical: `0.82*28.5 + 0.18*52.5 = 32.82`
  - Software: `0.80*32.5 + 0.20*62.5 = 38.50`
  - Validation: `0.88*14 + 0.12*28.5 = 15.74`
- **A3. ME/ES branch decision.** The policy chooses parallel or sequential execution. Parallel diagnostic branches add 8 minutes of coordination before Validation but can shorten critical path when two qualified resources are free. Sequential execution avoids the 8-minute coordination delay but can double the diagnostic elapsed time for that case.
- **A4. SLA clock.** The SLA clock starts at case arrival, not at Intake start. “Complete within 120 minutes” means arrival-to-Validation-completion elapsed time.
- **A5. Handover, setup, and preemption.**  
  - Handover = 7 minutes whenever Intake, a diagnostic activity, or Validation changes resource.  
  - An additional 5 minutes is incurred when a case moves between the mechanical team and the electrical/software team, unless the same cross-skilled resource retains the case.  
  - A resource that switches diagnostic skill family between consecutive cases incurs 5 minutes of setup.  
  - P1 preemption is allowed only for diagnostic activities, only once per preempted case, and adds a restart penalty equal to 10% of the remaining active service time.
- **A6. Overtime.** Overtime is capped at 30 minutes per resource per day in all policies. Since the expected load exceeds capacity even in the base scenario, the system is an overloaded prioritization system, not a demand-satisfying system.
- **A7. Uncertainty scenarios.** I treat U5 exactly as U1 plus Chen absence plus a 30-minute Intake-only outage 09:30–10:00. For U1, I renormalize P2/P3 shares after the +8 percentage point P1 shift.

## Objectives

Two objective functions are used to compare policies.

### Objective 1: Tail/SLA-risk objective

Minimize expected weighted SLA shortfall plus a p95 penalty:

\[
\min_{\pi} \; \mathbb{E}\Big[
\sum_{i} w_{p_i} \cdot \max(0, C_i - T_{p_i})^+
+ \lambda \cdot p95(C)
\Big]
\]

Where:

- \(p_i \in \{P1,P2,P3\}\)
- \(w_{P1}=10,\; w_{P2}=3,\; w_{P3}=1\)
- \(T_{P1}=120\) minutes, \(T_{P2}=480\) minutes, \(T_{P3}=1440\) minutes
- \(C_i\) is the case cycle time from arrival to Validation completion

This objective directly penalizes P1 tail misses and gives partial credit for reducing severe lateness.

### Objective 2: Fairness / robustness objective

Minimize a lexicographic worst-case objective:

\[
\min_{\pi} \; \max_{s \in \text{scenarios}} \Big( \beta_1 \cdot MissP1_s + \beta_2 \cdot MissP2_s + \beta_3 \cdot ExcessUtil_s \Big)
\]

with an additional soft penalty:

\[
+ \gamma \cdot \operatorname{std}_r(Utilization_r)
\]

This objective forces the policy to avoid making any one resource consistently overloaded and to protect priority classes in every scenario, not just in the base case.

## Decision variables

- `x_{r,a,t}`: whether resource `r` is assigned to activity type `a` in time block `t`
- Queue discipline and priority score: FIFO, EDD, P1-preemptive, or a hybrid score
- P1 reservation fraction per resource and time block
- Overflow trigger thresholds for cross-skilled assignment
- ME/ES parallelization threshold
- Preemption budget and restart-penalty handling
- Overtime release rule

## Parallel versus sequential branches

ME and ES cases allocate their branch load identically whether parallel or sequential. The difference is critical path and overhead:

- Parallel: two branch activities may run concurrently, but add 8 minutes coordination before Validation and may create more handovers.
- Sequential: no coordination delay, and a same cross-skilled resource can retain the case, saving the 5-minute cross-team handover, but the case’s diagnostic critical path is the sum of both branch service times.

Under high utilization, parallelizing ME/ES can degrade throughput because it puts two jobs on the queue instead of one and adds coordination overhead. In the hybrid policy, parallel execution should only be used when both branch lanes are below a wait threshold.

# 3. Candidate policies

## Policy S — Strict specialization with fixed queues

**Eligibility.** Each activity has a fixed specialist lane:

- Mechanical lane: Ada, Ben, Deepa, Farah
- Electrical lane: Ada, Chen, Deepa, Emil, Farah
- Software lane: Chen, Emil, Farah
- Intake / Validation lane: all resources with relevant skills, but once assigned to a lane, no cross-family overflow is allowed

**Queue discipline.** FIFO within each lane, except P1 can preempt a lower-priority diagnostic activity in that lane at most once. P1 is not sent to another lane.

**Parallelization.** ME and ES branches are dispatched as parallel jobs to their respective fixed lanes. This creates handover and coordination cost but protects specialization.

**Preemption.** P1 may interrupt any lower-priority diagnostic activity in the same lane. The preempted case receives a 10% restart penalty on remaining service time.

**Handover minimization.** No resource-retention logic. Handover is accepted as a fixed process cost.

**Overflow triggers.** None.

## Policy F — Full pooling to any qualified resource

**Eligibility.** Any resource with a nonzero multiplier for the required skill can take the work.

**Queue discipline.** One transparent prioritization queue:

1. P1 cases ahead of P2/P3.
2. Within each priority, earliest SLA deadline first.
3. Within the same deadline class, earliest arrival first.

**Dispatch rule.** When a resource becomes free, take the highest-priority eligible work item. To reduce handovers, the dispatcher first asks whether the previous resource on that case is qualified and idle; if yes, keep the case with the same resource.

**Preemption.** P1 may preempt any qualified resource’s lower-priority diagnostic activity, but only once per preempted case.

**Parallelization.** ME/ES branches run in parallel whenever two qualified resources are available and have load below 85%. Otherwise they run sequentially.

**Handover minimization.** The retention bonus is part of the dispatch score, but pooling still produces many handovers and setup changes.

**Overflow triggers.** None — this is total pooling.
