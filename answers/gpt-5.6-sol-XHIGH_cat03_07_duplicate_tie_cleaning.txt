## 1. Duplicate-handling decision tree

1. **Is there evidence of an exact technical duplicate?**  
   Require the same source identity or replay identifier, payload, business timestamp, activity, and E2O relation set—not merely equal activity and timestamp.
   - **Yes:** keep one deterministic canonical event and **drop** the repeated row. Store the dropped identifier and relation snapshot in the audit trail.
   - **No:** continue.

2. **Do external reconciliation evidence or stable business keys prove that multiple records describe the same physical event?**
   - **Yes:** **merge attributes and relations** into a canonical event. Resolve attributes using source-authority rules; preserve conflicting values as source observations.
   - **No:** continue.

3. **Is one event a summary/status event generated from a detailed transaction?**
   - **Yes, and the business transition is not demonstrably identical:** **retain both with refined labels or qualifiers**, such as `transaction` and `derived_status`.
   - **Yes, and lineage proves they are two observations of exactly one transition:** optionally **merge attributes and relations** in an evidence-based scenario.
   - Otherwise continue.

4. **Did harmonization collapse semantically distinct source activities into one common label?**
   - **Yes:** **retain both with refined labels or qualifiers** based on original source semantics.
   - **No:** continue.

5. **Are these concurrent same-label events associated with different focal objects?**
   - **Yes:** **retain both unchanged**, optionally adding a focal-object discriminator or qualifier. Sharing broader objects such as Order or Invoice is not duplication evidence.
   - **No:** continue.

6. **Is the relationship still unresolved?**
   - **Yes:** **quarantine for review** while retaining the raw records in the immutable source layer. Do not silently select or merge one.
   - **No duplicate relationship:** **retain both unchanged**.

No event in the supplied data is established as an exact technical duplicate. e03/e04 and e11/e16 are supported semantic duplicates, not byte-identical records.

## 3. Timestamp-tie ordering rules

For each original timestamp, construct a directed acyclic graph and topologically sort it. Precedence evidence is applied in this order:

1. **Known domain facts:** for example, e09 precedes e10 and e12 precedes e13. These are semantic.
2. **Within-source `source_seq`:** only compare events from the same source; never compare ERP sequence 30 with PSP sequence 400. This is semantic evidence about source order.
3. **Validated lifecycle constraints on shared focal objects:** pick before pack for the same Item; authorization before capture for the same Payment. These are semantic when the lifecycle model is documented.
4. **Source-specific semantics:** warehouse release before carrier acceptance, and detailed payment messages before their generated ERP summary. These are semantic when supported by interface documentation.
5. **`ingested_at`:** use only to select among otherwise unordered nodes. This is deterministic, not business-semantic.
6. **Stable fallback:** lexical `eid`, or a persisted numeric event index. This is deterministic only.

Cycles or contradictions among semantic rules must be quarantined rather than “resolved” using ingestion time.

After the conservative merges, intended orders are:

- **10:00:** e03/e04 canonical e03  e05  e06  e07. The first two picks are supported by scanner sequence 551/552; both picks precede packing, and e07 is the derived ERP status. If scanner sequence is not accepted as business order, e03 and e05 remain partially unordered, with their displayed order only a fallback.
- **10:15:** e08  e09  e10: warehouse release, carrier acceptance, carrier handover.
- **12:00:** e11/e16 canonical e11  e12  e13  e14  e15. PSP sequence gives e12  e13  e14, and the summary follows the payment messages. If invoice-before-authorization is not a validated lifecycle rule, e11 and e12 are admissibly unordered; displaying e11 first does not prove physical precedence.

Microseconds must be added only after this graph is resolved. Adding them first—for example according to dataframe or ingestion order—turns a technical accident into apparent business causality and creates false nonzero durations. The original timestamp remains the timestamp for performance analysis.

## 4. Conservative cleaning pipeline

1. Deep-copy and normalize the OCEL; preserve immutable raw tables.
2. Add `original_eid`, `original_activity`, `original_timestamp`, `original_source`, and `original_source_event_key`.
3. Generate candidate groups by activity/time, source key, payload hash, and object signatures; do not automatically modify them.
4. Merge only e03/e04 and e11/e16 because external evidence identifies the same physical/business event.
5. Retain e06/e07 as separate abstraction levels.
6. Refine e08/e09 to warehouse release and carrier acceptance, e06/e07 to transaction/status, and e15 to invoice-level payment summary.
7. Keep e05, e13, and e14 as distinct object-level work.
8. Build semantic tie DAGs, topologically sort them, then create an optional adjusted timestamp for software requiring total order.
9. Validate unique event IDs, event-to-object references, object references, and relation/event metadata consistency.

Starting from 17 events, two pairwise merges remove two canonical rows, so the conservative result contains **15 events**. Raw E2O count is 44; because both verified pairs have identical relation sets, the conservative union contains **39 distinct E2O relations**.

## 5. Aggressive alternatives

**Evidence-based semantic merging.** Start from the conservative result and additionally merge e06/e07 using the documented WMS-to-ERP message lineage. Keep e08/e09 distinct and do not merge e15 into either payment. Expected result: **14 events and 37 distinct E2O relations**. The principal damage is loss of the distinction between a detailed packing transaction and an ERP-visible status transition.

**Mechanically aggressive PM4Py merging.** Apply `pm4py.ocel_merge_duplicates(..., have_common_object=True)` to harmonized activity/timestamp groups. Likely merged groups are picks e03/e04/e05, packs e06/e07, dispatches e08/e09, invoices e11/e16, and captures e13/e14/e15. Expected result: approximately **10 events and 28 unioned E2O relations**, subject to PM4Py version and qualifier handling.

Its main damage is severe: separate items, logistics lifecycle transitions, payment objects, and abstraction levels become single events. `have_common_object=True` does not protect e13 and e14: both share O1 and V1, so the predicate succeeds even though one concerns M1 and the other M2. A common broad object is not a common focal object.

A mechanical `ocel_drop_duplicates` comparator is even more dangerous because it may retain only one event’s relations instead of unioning them. It is useful only as a sensitivity benchmark or inside a scope whose candidate groups have already been approved as exact duplicates.

## 6. PM4Py-oriented Python implementation

```python
import copy
import warnings
import pandas as pd
import pm4py

# PM4Py standard OCEL columns. The conceptual eid/activity/timestamp columns
# in the question are represented by these standard names.
EID = "ocel:eid"
ACT = "ocel:activity"
TS = "ocel:timestamp"
OID = "ocel:oid"
OTYPE = "ocel:type"

required_event_columns = {
    EID, ACT, TS, "source", "source_event_key", "source_seq",
    "ingested_at", "payload_hash"
}
missing = required_event_columns - set(ocel_raw.events.columns)
if missing:
    raise ValueError(f"Missing event columns: {sorted(missing)}")


def prepare_ocel(ocel):
    """Deep-copy and add immutable raw-value columns."""
    x = copy.deepcopy(ocel)
    x.events = x.events.copy(deep=True)
    x.relations = x.relations.copy(deep=True)
    x.objects = x.objects.copy(deep=True)

    x.events[TS] = pd.to_datetime(x.events[TS], utc=True)
    x.events["ingested_at"] = pd.to_datetime(
        x.events["ingested_at"], utc=True
    )

    x.events["original_eid"] = x.events[EID]
    x.events["original_activity"] = x.events[ACT]
    x.events["original_timestamp"] = x.events[TS]
    x.events["original_source"] = x.events["source"]
    x.events["original_source_event_key"] = x.events["source_event_key"]

    # Object-valued audit columns deliberately preserve every observation.
    x.events["source_event_ids"] = [
        [eid] for eid in x.events[EID]
    ]
    x.events["source_event_keys"] = [
        [key] for key in x.events["source_event_key"]
    ]
    x.events["source_observations"] = [
        [row.to_dict()] for _, row in x.events.iterrows()
    ]
    x.events["attribute_conflicts"] = [[] for _ in range(len(x.events))]

    if TS in x.relations.columns:
        x.relations["original_timestamp"] = x.relations[TS]
    if ACT in x.relations.columns:
        x.relations["original_activity"] = x.relations[ACT]
    return x


def event_object_sets(ocel):
    return (
        ocel.relations.groupby(EID)[OID]
        .apply(lambda s: frozenset(s.astype(str)))
        .to_dict()
    )


def candidate_precheck(ocel):
    """Report candidates; this function makes no cleaning decision."""
    ev = ocel.events.copy()
    objsets = event_object_sets(ocel)
    ev["_objects"] = ev[EID].map(objsets).map(lambda x: x or frozenset())

    same_label_time = []
    for (act, ts), group in ev.groupby([ACT, TS], sort=True):
        if len(group) <= 1:
            continue
        sets = list(group["_objects"])
        common = set.intersection(*(set(s) for s in sets)) if sets else set()
        same_label_time.append({
            "activity": act,
            "timestamp": ts,
            "eids": sorted(group[EID].tolist()),
            "common_objects": sorted(common),
            "object_sets": {
                r[EID]: sorted(r["_objects"]) for _, r in group.iterrows()
            },
        })

    # Exact-technical *candidates* still require row/relation verification.
    sig_cols = [
        "source", "source_event_key", ACT, TS, "payload_hash", "_objects"
    ]
    exact_candidates = [
        sorted(g[EID].tolist())
        for _, g in ev.groupby(sig_cols, dropna=False)
        if len(g) > 1
    ]
    return same_label_time, exact_candidates


def validate_integrity(ocel):
    ev_ids = set(ocel.events[EID])
    rel_ev_ids = set(ocel.relations[EID])
    if ocel.events[EID].duplicated().any():
        raise ValueError("Duplicate canonical event IDs")
    if not rel_ev_ids <= ev_ids:
        raise ValueError(f"Dangling event references: {rel_ev_ids - ev_ids}")

    if OID in ocel.objects.columns:
        object_ids = set(ocel.objects[OID])
    else:
        object_ids = set(ocel.objects.index.astype(str))
    rel_object_ids = set(ocel.relations[OID])
    if not rel_object_ids <= object_ids:
        raise ValueError(
            f"Dangling object references: {rel_object_ids - object_ids}"
        )
    return True


def sync_relation_event_metadata(ocel):
    """Keep denormalized relation activity/timestamp aligned to events."""
    meta = ocel.events.set_index(EID)
    if ACT in ocel.relations.columns:
        ocel.relations[ACT] = ocel.relations[EID].map(meta[ACT])
    if TS in ocel.relations.columns:
        ocel.relations[TS] = ocel.relations[EID].map(meta[TS])
    return ocel


def merge_verified_pairs(
    ocel,
    pair_specs,
    authority_by_attribute=None,
):
    """
    Merge only externally verified pairs.

    pair_specs contains dictionaries:
      canonical, absorbed, rule, confidence

    The helper requires equal (object ID, object type) relation sets. If
    qualifiers exist and conflict, it refuses the merge. Missing canonical
    attributes are filled; conflicting values remain in source snapshots
    unless an explicit source-authority rule selects one.
    """
    x = copy.deepcopy(ocel)
    ev = x.events.copy(deep=True)
    rel = x.relations.copy(deep=True)
    audit = []
    authority_by_attribute = authority_by_attribute or {}

    protected = {
        EID, ACT, TS, "source", "source_event_key", "source_seq",
        "ingested_at", "payload_hash", "original_eid",
        "original_activity", "original_timestamp", "original_source",
        "original_source_event_key", "source_event_ids",
        "source_event_keys", "source_observations",
        "attribute_conflicts"
    }

    for spec in pair_specs:
        canonical = spec["canonical"]
        absorbed = spec["absorbed"]
        ci = ev.index[ev[EID].eq(canonical)].tolist()
        ai = ev.index[ev[EID].eq(absorbed)].tolist()
        if len(ci) != 1 or len(ai) != 1:
            raise ValueError(f"Missing or non-unique pair: {spec}")
        ci, ai = ci[0], ai[0]

        c_row = ev.loc[ci].copy()
        a_row = ev.loc[ai].copy()

        relation_identity = [OID]
        if OTYPE in rel.columns:
            relation_identity.append(OTYPE)

        c_rel = rel.loc[rel[EID].eq(canonical), relation_identity]
        a_rel = rel.loc[rel[EID].eq(absorbed), relation_identity]
        c_set = set(map(tuple, c_rel.astype(str).to_records(index=False)))
        a_set = set(map(tuple, a_rel.astype(str).to_records(index=False)))
        if c_set != a_set:
            raise ValueError(
                f"Unverified relation union for {canonical}/{absorbed}: "
                f"{c_set} != {a_set}"
            )

        if "ocel:qualifier" in rel.columns:
            cq = rel.loc[rel[EID].eq(canonical), [OID, "ocel:qualifier"]]
            aq = rel.loc[rel[EID].eq(absorbed), [OID, "ocel:qualifier"]]
            if set(map(tuple, cq.fillna("").to_records(index=False))) != \
               set(map(tuple, aq.fillna("").to_records(index=False))):
                raise ValueError("Conflicting E2O qualifiers; review required")

        conflicts = list(ev.at[ci, "attribute_conflicts"])
        for col in ev.columns:
            if col in protected:
                continue
            cv, av = c_row[col], a_row[col]
            c_missing = pd.isna(cv) if not isinstance(cv, (list, dict)) else False
            a_missing = pd.isna(av) if not isinstance(av, (list, dict)) else False

            if c_missing and not a_missing:
                ev.at[ci, col] = av
            elif not c_missing and not a_missing and repr(cv) != repr(av):
                preferred_source = authority_by_attribute.get(col)
                if preferred_source == a_row["source"]:
                    ev.at[ci, col] = av
                conflicts.append({
                    "attribute": col,
                    "canonical_value": cv,
                    "absorbed_value": av,
                    "selected_source": preferred_source or c_row["source"],
                })

        ev.at[ci, "source_event_ids"] = (
            list(ev.at[ci, "source_event_ids"])
            + list(ev.at[ai, "source_event_ids"])
        )
        ev.at[ci, "source_event_keys"] = (
            list(ev.at[ci, "source_event_keys"])
            + list(ev.at[ai, "source_event_keys"])
        )
        ev.at[ci, "source_observations"] = (
            list(ev.at[ci, "source_observations"])
            + list(ev.at[ai, "source_observations"])
        )
        ev.at[ci, "attribute_conflicts"] = conflicts

        relation_snapshot = rel.loc[
            rel[EID].isin([canonical, absorbed])
        ].to_dict("records")
        rel.loc[rel[EID].eq(absorbed), EID] = canonical
        ev = ev.loc[~ev[EID].eq(absorbed)].copy()

        audit.append({
            "canonical_event_id": canonical,
            "absorbed_event_id": absorbed,
            "merge_rule": spec["rule"],
            "confidence": spec["confidence"],
            "relation_snapshot": relation_snapshot,
        })

    rel = rel.drop_duplicates().reset_index(drop=True)
    x.events = ev.reset_index(drop=True)
    x.relations = rel
    x = sync_relation_event_metadata(x)
    validate_integrity(x)
    return x, pd.DataFrame(audit)


def refine_activities(ocel):
    x = copy.deepcopy(ocel)
    refinements = {
        "e06": ("Pack Package — WMS transaction", "detailed_transaction"),
        "e07": ("Pack Package — ERP derived status", "derived_status"),
        "e08": ("Release Package from Warehouse", "warehouse_release"),
        "e09": ("Accept Package by Carrier", "carrier_acceptance"),
        "e15": ("Record Invoice Payment Summary", "invoice_summary"),
    }
    x.events["event_role"] = x.events.get("event_role", pd.Series(
        [None] * len(x.events), index=x.events.index, dtype="object"
    ))
    for eid, (label, role) in refinements.items():
        mask = x.events[EID].eq(eid)
        x.events.loc[mask, ACT] = label
        x.events.loc[mask, "event_role"] = role
    x = sync_relation_event_metadata(x)
    return x


prepared = prepare_ocel(ocel_raw)
candidate_groups, exact_technical_candidates = candidate_precheck(prepared)
print("Same-label/time candidates:", candidate_groups)
print("Exact-technical candidates requiring verification:",
      exact_technical_candidates)

# Independent conservative scenario.
conservative_base = copy.deepcopy(prepared)
conservative, conservative_audit = merge_verified_pairs(
    conservative_base,
    [
        {
            "canonical": "e03", "absorbed": "e04",
            "rule": "reconciliation_same_physical_scan_v1",
            "confidence": "high",
        },
        {
            "canonical": "e11", "absorbed": "e16",
            "rule": "invoice_number_same_issuance_v1",
            "confidence": "high",
        },
    ],
    authority_by_attribute={
        # Applied only if such columns exist in the actual OCEL.
        "warehouse_location": "WMS",
        "invoice_tax_amount": "BILLING",
        "invoice_posting_status": "ERP",
    },
)
conservative = refine_activities(conservative)
validate_integrity(conservative)

# Independent evidence-based scenario: additionally merge packing/status.
evidence_based = copy.deepcopy(conservative)
evidence_based, packing_audit = merge_verified_pairs(
    evidence_based,
    [{
        "canonical": "e06", "absorbed": "e07",
        "rule": "documented_wms_to_erp_pack_lineage_v1",
        "confidence": "medium",
    }],
)
validate_integrity(evidence_based)

# PM4Py drop comparator: justified only as a mechanical sensitivity scenario.
# It is intentionally NOT used to produce the conservative dataset.
warnings.warn(
    "Mechanical drop may remove distinct items/payments and may discard E2O "
    "relations. Do not promote this result without reviewing every group."
)
mechanical_drop_sensitivity = pm4py.ocel_drop_duplicates(
    copy.deepcopy(prepared),
    have_common_object=True,
)
validate_integrity(mechanical_drop_sensitivity)

# Separate mechanically aggressive merge scenario.
warnings.warn(
    "ocel_merge_duplicates with have_common_object=True treats a shared "
    "Order/Invoice as sufficient; e13/e14 can therefore be merged despite "
    "different Payment objects."
)
aggressive_library_merge = pm4py.ocel_merge_duplicates(
    copy.deepcopy(prepared),
    have_common_object=True,
)
validate_integrity(aggressive_library_merge)

# Semantic tie ranks are the result of an externally reviewed DAG/topological
# ordering, not an inference from ingestion order.
ordered_conservative = copy.deepcopy(conservative)
stable_ids = sorted(ordered_conservative.events[EID].astype(str).tolist())
stable_rank = {eid: i for i, eid in enumerate(stable_ids)}

semantic_tie_rank = {
    "e03": 10, "e05": 20, "e06": 30, "e07": 40,
    "e08": 10, "e09": 20, "e10": 30,
    "e11": 10, "e12": 20, "e13": 30, "e14": 40, "e15": 50,
}
ordered_conservative.events["tie_break_rank"] = [
    semantic_tie_rank.get(str(eid), 10000 + stable_rank[str(eid)])
    for eid in ordered_conservative.events[EID]
]

# Sort by business timestamp and the reviewed additional column.
ordered_conservative = pm4py.ocel_sort_by_additional_column(
    ordered_conservative,
    "tie_break_rank",
)

# Only now add synthetic time. original_timestamp remains unchanged.
ordered_conservative = pm4py.ocel_add_index_based_timedelta(
    ordered_conservative
)
ordered_conservative.events["adjusted_timestamp"] = \
    ordered_conservative.events[TS]
ordered_conservative = sync_relation_event_metadata(ordered_conservative)
validate_integrity(ordered_conservative)

assert len(conservative.events) == 15
assert len(evidence_based.events) == 14
```

## 7. Sensitivity analysis

| Dataset | Expected events / E2O | Main analytical effect |
|---|---:|---|
| Raw | 17 / 44 | Observation duplication inflates same-label edges and ET–OT weights |
| Conservative | 15 / 39 | Removes supported duplicate observations while retaining item, payment, lifecycle, and abstraction distinctions |
| Evidence-based | 14 / 37 | Removes the packing transaction/status transition from DFGs as two separate events |
| Aggressive library merge | About 10 / 28 | Collapses different Items, Payments, logistics states, and summaries into union events |

For comparable DFGs, all datasets should use the same reviewed tie policy; otherwise cleaning effects are confounded with arbitrary dataframe order.

- **Order-flattened DFG:** raw data can show `Pick Item  Pick Item` twice, `Pack Package  Pack Package`, `Dispatch Package  Dispatch Package`, `Issue Invoice  Issue Invoice`, and repeated `Capture Payment  Capture Payment`. Conservative cleaning leaves one legitimate `Pick Item  Pick Item` for I1 then I2, changes packing to `WMS transaction  ERP derived status`, changes logistics to `Release  Accept  Handover`, and changes the final payment edge to `Capture Payment  Invoice Payment Summary`. Aggressive merging removes most of these edges entirely.
- **Item-flattened DFG:** raw I1 has a false `Pick Item  Pick Item` caused by e03/e04. Conservative I1 becomes `Pick Item  Pack transaction`; I2 remains `Pick Item  Pack transaction`. Aggressive merging makes one pick event relate to both I1 and I2, hiding that two picks occurred.
- **Payment-flattened DFG:** conservative M1 retains `Authorize Payment  Capture Payment`; M2 retains its separate capture. e15 remains absent because no Payment relation is known. Aggressive merging creates one capture associated with both M1 and M2, falsely suggesting a joint capture.
- **OC-DFG frequency:** duplicate removal lowers counts on `Pick  Pick`, `Issue  Authorize`, and same-label logistics/payment edges. Evidence merging removes the packing transaction-to-status edge. Aggressive merging reduces event frequency while increasing object multiplicity per merged event.
- **ET–OT weights:** examples include `Pick Item–Item` falling from three raw observations to two conservative picks, `Issue Invoice–Invoice` from two to one, and raw `Capture Payment–Order` from three to two after e15 is refined. In the aggressive result, one capture event has two Payment relations, so event-based and relation-based weighting diverge.
- **OTG relations:** most existing object-type adjacencies remain, but aggressive union creates a direct co-occurrence of M1 and M2 in one event. That Payment–Payment interaction did not exist in the raw OCEL. Relation frequencies involving Item, Package, Invoice, and Payment also change.
- **Rework and loops:** raw same-label self-loops can be cross-system duplication or abstraction layers rather than rework. Conversely, the conservative `Pick  Pick` is legitimate repeated work on different Items.
- **Lifecycle/performance:** ordering ties with synthetic microseconds creates artificial positive authorization-to-capture, release-to-accept, and pick-to-pack durations. Performance must use `original_timestamp`, report these intervals as zero-resolution or censored, and avoid claiming the adjusted gaps are measured durations. Merging dispatch events also changes which lifecycle milestone is used to measure delivery lead time.

Concrete interpretation-sensitive patterns include: `Pick  Pick`, `Pick  Pack`, `Pack transaction  ERP status`, `Release  Carrier accept`, `Carrier accept  Handover`, `Issue Invoice  Authorize`, `Authorize  Capture M1`, `Capture M1  Capture M2`, and `Capture M2  Invoice Payment Summary`.

## 8. Audit trail and reversibility

Use an append-only merge ledger containing:

- canonical event ID and all source event IDs;
- source systems and source event keys;
- merge/refinement rule, rule version, reviewer, and review time;
- original and refined activity;
- every original timestamp and adjusted timestamp;
- per-source attribute snapshots;
- selected value and source-authority rule for each merged attribute;
- discarded or unresolved conflicts;
- original and canonical E2O relation snapshots, including qualifiers;
- confidence, evidence reference, and reason.

The raw OCEL remains immutable. A canonical-to-source mapping plus source observation and relation snapshots permits reconstruction by replacing each canonical event with its original rows and relations, restoring original labels and timestamps, and discarding synthetic ordering columns.

## 9. Failure modes and safeguards

1. **Collapsing e13 and e14:** require equality of focal Payment objects, not merely a shared Order or Invoice.
2. **Turning abstraction updates into rework:** refine transaction and derived-status labels before DFG interpretation.
