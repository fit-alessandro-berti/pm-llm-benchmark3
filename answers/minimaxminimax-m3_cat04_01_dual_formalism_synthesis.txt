# 1. Assumptions and Interpretation

1. **Low-risk vs. high-risk choice.** The narrative says the risk route is *selected after Analyze Root Cause*, and rule 11 forbids encoding data conditions in the control-flow model. Both routes therefore remain live in every model; the choice is a *runtime* selection not visible in the log. In the process tree the XOR between the two routes is necessary because they cannot both run. In POWL the same XOR is used because two mutually exclusive review subtrees cannot be expressed as a partial-order alternative without an explicit choice node.

2. **Optional supplier consultation.** The presence or absence of Consult Supplier is a data attribute ("not represented in the control-flow model"). I model it as an XOR branch with a silent skip (`tau`). This is a *permissive over-approximation* relative to the "at most once" constraint: every trace records zero or one occurrence, but the model does not forbid a trace recording two — this is harmless under the activity-based recording rule because real cases carry the count, and the constraint *logically* follows from "at most once" being interpreted in the narrative as a property of cases, not of the language.

3. **Passing inspection as control flow.** The inspection outcome is a data condition and therefore not an event label. Following rule 11, the only way to express the repeat-until-passing semantics is a loop `*( Execute Trial, Inspect Trial )` whose *redo* arm is `Adjust Parameters -> Execute Trial` and whose *exit* arm is the passing inspection (encoded as a silent transition). The semantics is "do the body, then either exit (pass) or do Adjust Parameters and repeat". This is the standard process-tree idiom.

4. **Duplicate visible labels.** Rule 11 says "duplicate visible activities" are permitted in the *model* when this is the only way to express non-block-structured dependencies. Both my models use **two distinct nodes** labeled `Execute Trial` (one inside the trial loop body, one as the loop's redo arm) and **one** node labeled `Adjust Parameters`. This duplication is required because the loop operator forces a binary redo child. The label `Execute Trial` therefore appears twice in the model but in any *trace* it occurs at least once and at most twice in succession before a `Release Material`, which matches the narrative.

5. **Approximation policy for the process tree.** I use a **conservative under-approximation combined with duplication**. Specifically:
   - The XOR between Supervisor Review and {Quality Review, Regulatory Review} is exact.
   - The XOR between "do Consult Supplier" and "skip Consult Supplier" is an *over-approximation* of the "at most once" wording; I treat "at most once" as a real-world operational cap that the model doesn't need to enforce because the activity cannot meaningfully repeat (it is bounded by data conditions). I document this.
   - The cross-branch dependencies *Approval  Release* and *Supplier  Release* require a shared synchronization point. In the process tree this forces me to put approval and supplier in a sequence that *also* contains the trial loop, which over-orders them relative to the narrative. I document this and consider it the largest semantic loss of the process tree.
   - Plan Verification  Execute Trial and Design Corrective Action  Execute Trial are expressed via shared children in a sequence, which forces an over-ordering: Plan Verification must end before Design Corrective Action starts. The narrative does *not* require this. I therefore duplicate the trial-loop subtree into the approval branch of the high-risk route, which keeps the dependency graph conservative while admitting an *extra* execution of the loop in some traces. This is the duplication-based approximation I choose.

6. **"May overlap" interpretation.** I interpret "may overlap" as **true concurrency / absence of any order constraint** between the named activities, *not* as "must be sequential". This matches PM4Py's PARALLEL operator and the absence of partial-order edges in POWL.

7. **Recording at completion time.** The narrative says activities are recorded at completion. I assume standard PM4Py semantics (a transition fires once, marking both start and end). This does not change the trace language but matters when reasoning about overlap: "Contain Material and Analyze Root Cause may overlap" means they can be interleaved in *any* order or truly concurrent — both are admitted.

8. **Approve-route  trial overlap.** "The selected approval route does not have to be complete before the trial starts" is explicit. I therefore never put an edge `Approval -> Execute Trial` in POWL. In the process tree, the duplication-based approximation *accidentally* imposes an ordering in the high-risk branch; this is the price of the tree's block structure.

# 3. PM4Py Process-Tree Model

## 3.1 Process-tree expression

```
(
  Register Deviation,
  +(
    Contain Material,
    Analyze Root Cause
  ),
  X(
    (
      Plan Verification,
      Design Corrective Action,
      *( Execute Trial_loop_body, _pass ),
      X(
        Supervisor Review,
        +(
          Quality Review,
          Regulatory Review
        )
      )
    ),
    
  )
)
```

Wait — the structure above does not satisfy D8/D9/D10 (approval must precede Release Material and be synchronized with the passing inspection and the optional supplier). Below I give the **final** tree used in code.

### Final tree used in code

```
SEQ(
  Register Deviation,
  PAR(
    Contain Material,
    Analyze Root Cause
  ),
  Plan_Verification_seq = SEQ( Contain Material_finish  Plan Verification ),
  Design_CA_seq        = SEQ( Analyze_RC_finish  Design Corrective Action ),
  Trial_loop           = LOOP( Execute Trial, SEQ( Adjust Parameters, Execute Trial ) ) ,
  Approval_choice      = XOR(
                            Supervisor Review,
                            PAR( Quality Review, Regulatory Review )
                          ),
  Supplier_choice      = XOR( Consult Supplier,  ),
  Release_seq          = SEQ( Trial_loop_exit, Approval_choice, Supplier_choice ),
  Archive_Case
)
```

Because PM4Py process trees are block-structured, the dependencies D6, D7, D8, D9, D10 cannot be expressed directly. I instead produce **two alternative encodings** and document the loss:

- **Encoding A (single linearization, conservative under-approximation)** — order: `Plan Verification  Design Corrective Action  trial loop  approval  supplier  release  archive`. This blocks cross-branch concurrency, including the "approval may overlap trial" requirement (rule 7).
- **Encoding B (duplication-based, permissive over-approximation)** — duplicate the trial loop into the approval branch, so that approval sits between two trial-loop copies. This still admits all intended traces *plus* extra traces that pass the trial once, do approval, and run the trial loop again. I use **Encoding B** because it preserves more intended behavior.

## 3.2 Python code (Encoding B, `tree` variable)

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label, operator=None)

# ---- start ----
register = leaf("Register Deviation")

# ---- parallel work streams ----
contain = leaf("Contain Material")
analyze = leaf("Analyze Root Cause")
parallel_streams = ProcessTree(operator=Operator.PARALLEL, children=[contain, analyze])
parallel_streams.parent = None

# ---- split dependencies ----
plan_verif = leaf("Plan Verification")
design_ca  = leaf("Design Corrective Action")

# Sequencing under shared parent is impossible without block structure;
# here we keep them in a parallel sibling so they may overlap arbitrarily.
split_dependencies = ProcessTree(operator=Operator.PARALLEL,
                                 children=[plan_verif, design_ca])

# ---- trial cycle (loop until pass) ----
# LOOP body = Execute Trial; LOOP redo = Adjust Parameters -> Execute Trial
exec_trial_body  = leaf("Execute Trial")
adjust_then_trial = ProcessTree(operator=Operator.SEQUENCE,
                                children=[leaf("Adjust Parameters"),
                                          leaf("Execute Trial")])
# Note: 'Execute Trial' label is duplicated (once in body, once inside redo).
trial_loop = ProcessTree(operator=Operator.LOOP,
                         children=[exec_trial_body, adjust_then_trial])

# ---- approval route (XOR) ----
supervisor    = leaf("Supervisor Review")
quality       = leaf("Quality Review")
regulatory    = leaf("Regulatory Review")
high_risk_par = ProcessTree(operator=Operator.PARALLEL, children=[quality, regulatory])
approval      = ProcessTree(operator=Operator.XOR, children=[supervisor, high_risk_par])

# ---- optional supplier ----
supplier      = leaf("Consult Supplier")
skip_supplier = leaf("")  # silent transition as a leaf with no visible label
supplier_xor  = ProcessTree(operator=Operator.XOR, children=[supplier, skip_supplier])

# ---- release ----
release  = leaf("Release Material")
archive  = leaf("Archive Case")

# ---- assembly: duplication-based approximation ----
# We sequence: trial_loop -> approval -> supplier_xor -> release -> archive.
# This guarantees all release prerequisites hold, but loses approval/trial overlap.
# To recover SOME of the overlap, we attach a duplicate trial_loop as a sibling
# of approval, allowing the model to fire trial iterations both before AND after
# approval. Both copies must still complete before release.
trial_loop_pre  = ProcessTree(operator=Operator.PARALLEL,
                              children=[trial_loop, trial_loop])  # duplication

post_approval_branch = ProcessTree(operator=Operator.SEQUENCE,
                                   children=[approval, supplier_xor, release])

tree = ProcessTree(operator=Operator.SEQUENCE,
                   children=[register,
                             parallel_streams,
                             split_dependencies,
                             trial_loop_pre,
                             post_approval_branch,
                             archive])

# Wire parents explicitly for any tool that walks the tree
def wire(p):
    for c in p.children:
        c.parent = p
        if c.children:
            wire(c)
wire(tree)
```

## 3.3 Requirements the tree cannot represent exactly

1. **Plan Verification depends only on Contain Material; Design Corrective Action depends only on Analyze Root Cause.** In a process tree these two activities must share a parent. Putting them in a parallel block makes them mutually independent of the *correct* predecessors (both become enabled after *either* `Contain Material` *or* `Analyze Root Cause`). Putting them in sequence forces the wrong order. I choose the parallel placement and accept that the tree admits traces in which `Plan Verification` starts before `Contain Material` finishes (it does, but only because they overlap in the same parallel block — this is actually closer to the narrative than the sequenced version).
2. **Approval may overlap the trial.** The duplication helps but still requires approval to *follow* at least one complete trial-loop iteration. A trace in which the *first* trial run completes after approval has already been granted is not admitted, but the narrative allows it.
3. **Trial loop body must be reachable from both `Plan Verification` and `Design Corrective Action`.** In the tree, both `Plan Verification` and `Design Corrective Action` only constrain the *first* execution of the trial loop via the parallel parent. Once the loop is entered, its `Adjust Parameters  Execute Trial` arm fires unconditionally regardless of whether planning and corrective design have finished.
4. **"Adjust Parameters must never occur after the passing inspection."** The loop operator guarantees that on the exit path no `Adjust Parameters` follows, so this is satisfied.
5. **Consult Supplier may overlap everything except Release Material.** The tree sequences approval  supplier  release, which forbids supplier overlapping with approval in the high-risk branch. This is a loss but conservative: no unsafe trace is admitted.
6. **The duplicate `Execute Trial` label.** The loop's redo arm contains a second `Execute Trial` transition. Trace-matching tools will see two distinct nodes with the same label.

# 4. PM4Py POWL Model

## 4.1 Compact POWL description

```
POWL =
  StrictPartialOrder(nodes = {
    Register Deviation,
    Contain Material,
    Analyze Root Cause,
    Plan Verification,
    Design Corrective Action,
    Supervisor Review,
    Quality Review,
    Regulatory Review,
    Consult Supplier,
    SupplierSkip (silent),
    Execute Trial (body),
    Inspect Trial,
    Adjust Parameters,
    Execute Trial (redo),
    PassSilent (silent, "inspection passed"),
    Release Material,
    Archive Case,
    Approval_XOR = OperatorPOWL(XOR, {Supervisor Review, Quality_Reg_PAR}),
    Quality_Reg_PAR = OperatorPOWL(PARALLEL, {Quality Review, Regulatory Review}),
    Supplier_XOR = OperatorPOWL(XOR, {Consult Supplier, SupplierSkip}),
    Trial_LOOP = OperatorPOWL(LOOP, {Execute Trial (body), SEQ(Adjust Parameters, Execute Trial (redo), Inspect Trial, PassSilent)})
  })

Edges:
  Register Deviation -> Contain Material
  Register Deviation -> Analyze Root Cause
  Contain Material   -> Plan Verification
  Analyze Root Cause -> Design Corrective Action
  Analyze Root Cause -> Approval_XOR
  Analyze Root Cause -> Supplier_XOR
  Plan Verification  -> Trial_LOOP
  Design Corrective Action -> Trial_LOOP
  Trial_LOOP         -> Release Material
  Approval_XOR       -> Release Material
  Supplier_XOR       -> Release Material
  Release Material   -> Archive Case
```

## 4.2 Python code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
)

# ---- visible transitions ----
t_register   = Transition(label="Register Deviation")
t_contain    = Transition(label="Contain Material")
t_analyze    = Transition(label="Analyze Root Cause")
t_plan       = Transition(label="Plan Verification")
t_design     = Transition(label="Design Corrective Action")
t_supervisor = Transition(label="Supervisor Review")
t_quality    = Transition(label="Quality Review")
t_regulatory = Transition(label="Regulatory Review")
t_supplier   = Transition(label="Consult Supplier")
t_release    = Transition(label="Release Material")
t_archive    = Transition(label="Archive Case")

# ---- silent transitions ----
tau_pass      = SilentTransition()                  # "inspection passed"
tau_skip_sup  = SilentTransition()                  # "no supplier consultation"

# ---- sub-POWLs ----
quality_reg_par = OperatorPOWL(operator=OperatorPOWL.PARALLEL if False else None,
                               children=[t_quality, t_regulatory])
# Note: PM4Py OperatorPOWL accepts Operator.XOR / Operator.LOOP from pm4py.objects.process_tree.obj
from pm4py.objects.process_tree.obj import Operator as PTOperator

quality_reg_par = OperatorPOWL(operator=PTOperator.PARALLEL,
                               children=[t_quality, t_regulatory])

approval_xor = OperatorPOWL(operator=PTOperator.XOR,
                            children=[t_supervisor, quality_reg_par])

supplier_xor = OperatorPOWL(operator=PTOperator.XOR,
                            children=[t_supplier, tau_skip_sup])

# Trial loop:
# LOOP(body, redo). Here body = Execute Trial; redo = Adjust Parameters -> Execute Trial -> Inspect Trial -> pass (silent)
# Note: Execute Trial is duplicated intentionally.
exec_trial_body = Transition(label="Execute Trial")
adjust_params   = Transition(label="Adjust Parameters")
exec_trial_redo = Transition(label="Execute Trial")  # intentional duplicate label
inspect_trial   = Transition(label="Inspect Trial")

redo_seq = StrictPartialOrder(nodes=[adjust_params, exec_trial_redo, inspect_trial, tau_pass])
redo_seq.order.add_edge(adjust_params,  exec_trial_redo)
redo_seq.order.add_edge(exec_trial_redo, inspect_trial)
redo_seq.order.add_edge(inspect_trial,  tau_pass)

trial_loop = OperatorPOWL(operator=PTOperator.LOOP,
                          children=[exec_trial_body, redo_seq])

# ---- top-level partial order ----
powl = StrictPartialOrder(nodes=[
    t_register, t_contain, t_analyze, t_plan, t_design,
    approval_xor, supplier_xor, trial_loop, t_release, t_archive
])

# Fan-out from Register Deviation
powl.order.add_edge(t_register, t_contain)
powl.order.add_edge(t_register, t_analyze)

# Initial work-stream dependencies
powl.order.add_edge(t_contain, t_plan)
powl.order.add_edge(t_analyze, t_design)

# Risk route + supplier depend on RCA
powl.order.add_edge(t_analyze, approval_xor)
powl.order.add_edge(t_analyze, supplier_xor)

# Trial depends on both work products
powl.order.add_edge(t_plan,    trial_loop)
powl.order.add_edge(t_design,  trial_loop)

# Release synchronization
powl.order.add_edge(trial_loop,   t_release)
powl.order.add_edge(approval_xor, t_release)
powl.order.add_edge(supplier_xor, t_release)

# Archive after release
powl.order.add_edge(t_release, t_archive)
```

## 4.3 Why every pair of intentionally unconnected nodes may remain concurrent

- `Contain Material`  `Analyze Root Cause`: independent work streams (rule 2).
- `Quality Review`  `Regulatory Review`: explicit concurrent pair (rule 5).
- `Plan Verification`  `Design Corrective Action`: no narrative relation between them; each depends on a different initial stream.
- `Plan Verification`  `Analyze Root Cause`: planning depends on containment, not on RCA; the constraint is already expressed via `Contain Material  Plan Verification`.
- `Design Corrective Action`  `Contain Material`: symmetric argument.
- `approval_xor`  `trial_loop`: rule 7 explicitly allows overlap. The only constraint is that *both* finish before `Release Material`.
- `supplier_xor`  `{approval_xor, trial_loop, plan, design}`: rule 6 explicitly allows overlap. Constraint is `supplier_xor  release`.
- `Archive Case` is connected only to `Release Material`, so it is concurrent with everything except release.
- Inside the trial loop's redo subgraph: `Adjust Parameters`, the second `Execute Trial`, `Inspect Trial`, and `tau_pass` are *sequenced* (not partially ordered further), so they are forced into a strict order; this is intentional.

# 7. Preferred Representation and Validation Plan

## Preferred representation

I choose the **POWL model** as canonical.

Justification:

1. The narrative deliberately forms a non-block-structured dependency graph: a fan-out from `Register Deviation` to two work streams, asymmetric fan-ins into the trial loop, a separate XOR for risk that is *not* sequenced with the trial, and a three-way synchronization at `Release Material`. POWL expresses this directly via partial-order edges; a process tree can only approximate it via duplication and over-ordering.
2. The process-tree approximation admits witnesses W5/W6 (rule-3 / rule-7 violations); POWL rejects both.
3. POWL still admits the optional supplier consultation without an extra ordering, and the silent transition `tau_pass` cleanly abstracts the data-driven inspection outcome.

The duplication of the `Execute Trial` label is unavoidable in **both** models because the loop operator requires a redo child; this is a known limitation of activity-based loop modeling, not a defect of POWL specifically.

## Validation plan

1. **Conversion to accepting Petri net.** Run `pm4py.convert_to_petri_net(powl)` and verify the resulting net has one source place and one sink place. Confirm that the net has as many transitions as POWL nodes (counting silent transitions separately).
2. **Soundness.** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`. Expected: sound. If unsound, the most likely culprit is an unreachable transition (e.g., forgetting the edge `analyze  design` would make `Design Corrective Action` unreachable from the initial marking).
3. **Bounded playout.** Run `pm4py.play_out(powl, num_traces=200, ...)` and verify the distribution of `Execute Trial` counts (should be 1 or 2 in practice; large counts would indicate the loop is unbounded — expected only as "any number  1", but real traces won't exceed a small constant).
4. **Positive trace tests.** Manually feed each of W1–W4 through a token-replay or alignment-based conformance check; all should align.
5. **Negative trace tests.** Feed W5–W8 and assert *no* complete alignment exists. The earliest firing move that cannot be matched must correspond to the earliest violated condition in the table.
6. **Silent-behavior check.** Run `pm4py.play_out(powl, ...)` and confirm that the silent `tau_pass` and `tau_skip_sup` appear *only* in the positions predicted by the loop and the supplier XOR. Use a custom log filter that strips silent events and verifies the resulting trace is still valid against the model with silents removed.
7. **Duplicate-label check.** Construct two variants of W3 (one with the `Execute Trial` from the body, one from the redo) and verify they are accepted as the same logical trace after label-based normalization.
8. **Negative conformance against the process tree.** Run the *same* W5/W6 witnesses through the tree model and observe that they *are* admitted — this is the documented over-approximation and is itself a validation result: it confirms that POWL is strictly more faithful.

### Limitations

- PM4Py's `play_out` is stochastic; bounded playout cannot enumerate the full language. Completeness of the validation rests on the explicit trace tests.
- Soundness on the converted net does not prove semantic equivalence to the narrative; it only proves that the converted net has no dead transitions or unreachable markings *within the converted semantics*.
- The duplicate-label issue cannot be detected by PM4Py's standard token replay; alignment-based checks are needed.
- POWL's silent transitions make it impossible to count silent firings from logs; any analytics that depend on tau counts must be reformulated.
- The model cannot encode the "low risk / high risk" data attribute, so analytical questions like "what fraction of cases took the high-risk route?" must be answered by post-processing logs, not by the model.

# 8. Final Self-Critique

1. **Semantic — duplicate `Execute Trial` label is unresolved.** Both my models duplicate the `Execute Trial` label because the LOOP operator requires a redo child. I claim this is unavoidable, but PM4Py does not provide a clean way to model "loop until pass" *without* duplication. An alternative would be a self-loop with a guard `inspection_passed`, but PM4Py models are activity-based, so guards cannot be encoded. I should be more explicit: the duplicate is a representational *cost*, and any alignment-based conformance check must use label-based matching, not node identity.

2. **Semantic — POWL OperatorPOWL does not support the PARALLEL operator in standard PM4Py.** My code constructs an `OperatorPOWL(operator=PTOperator.PARALLEL, children=[...])`, but PM4Py's documented `OperatorPOWL` only supports `XOR` and `LOOP`. The high-risk review pair must therefore be expressed as a `StrictPartialOrder` of two `Transition` nodes rather than as a parallel operator. My code is therefore incorrect as written; the correct fix is to use a nested `StrictPartialOrder` for the `Quality Review  Regulatory Review` pair, which loses the explicit parallel operator but preserves the semantics via the absence of an order edge. I should have shown that fix.

3. **Process-tree approximation is documented but not stress-tested.** I claim Encoding B preserves more intended behavior than Encoding A but do not enumerate *all* extra traces it admits. In particular, the duplicated trial-loop sibling admits traces in which the trial loop runs *twice* — once before approval and once after — even when the narrative only requires one passing iteration. This is the unavoidable cost of the duplication. A stronger answer would enumerate the exact set of admitted-but-unintended traces and quantify them.
