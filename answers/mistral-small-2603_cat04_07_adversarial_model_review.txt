# Critical Review and Third Alternative for Dossier Process Model

---

## # 1. Review Scope and Assumptions

We distinguish **three intended use cases** for the dossier process model:

| Use Case | Purpose | Acceptable Fitness/Precision Trade-off |
|--------|--------|----------------------------------------|
| **Exploration** | Discover common patterns, identify anomalies, support process mining research | High generalization, moderate precision; model may admit plausible but unobserved behavior |
| **Conformance Enforcement** | Detect deviations from policy, trigger corrective actions, audit trails | High precision, strict fitness; model must reject noncompliant behavior even if plausible |
| **Stakeholder Communication** | Provide clear, auditable process maps for business users and auditors | Transparent structure, minimal silent transitions, intuitive semantics |

**Assumptions:**
- The external/internal attribute is missing in logs but is a **business-critical decision point** (P3).
- "Correct Dossier" is a repair action that may invalidate prior checks; the affected-check attribute is missing (P6).
- The process owner expects **deterministic recheck logic** after correction (F6).
- The auditor requires **negative trace validation** (F5).
- The data analyst observes **missing Supplier Review events** and **unseen combinations** in holdout (F4).

> **Use-case-dependent decisions:**
> - For **exploration**, Model S’s permissiveness may be acceptable if users understand it as a "fuzzy map."
> - For **compliance**, neither model is acceptable due to semantic flaws and metric pathologies.
> - For **communication**, clarity and maintainability dominate raw performance.

## # 3. Adversarial Review of Model S

###  Strongest Case for Model S

Model S is **intentionally permissive** and designed for **exploration**, not enforcement (F7). It allows:
- Any order of mandatory checks (`Credit Check`, `Technical Review`) and optional ones (`Supplier Review`, `Expedite Review`).
- Silent transitions via `tau` in `X(...)`, enabling noise tolerance.
- Simple structure: one root process tree with a choice over all activities.

This makes it **robust to missing events and log noise**, which is valuable in early discovery phases.

###  Strongest Case Against Model S

Model S **violates core policy requirements**:

| Trace | Policy Violation | Consequence |
|------|------------------|-------------|
| `Register Dossier  Expedite Review  Credit Check  Technical Review  Manager Approval  Release Order` | Expedite Review before mandatory checks (F1) | Violates P4 and B4 |
| `Register Dossier  Manager Approval  Release Order` | Skips mandatory checks (P2) | Violates B3 |
| `Register Dossier  Credit Check  Technical Review  Credit Check  Manager Approval  Release Order` | Repeated mandatory check without correction (P7, B8) | Suspicious; Model S accepts it | Violates F1 and P7 |
| `Register Dossier  Supplier Review  Expedite Review  Credit Check  Technical Review  Manager Approval  Release Order` | Supplier Review before mandatory checks | May be invalid for internal orders (P3) | Ambiguous semantics |

**Five concrete undesirable behaviors admitted by Model S:**
1. **Skipping mandatory checks** (B3)
2. **Expedite Review before mandatory checks** (B4)
3. **Repeated mandatory checks without correction** (B8)
4. **Supplier Review before mandatory checks** (P3)
5. **Ambiguous correction handling** — Model S has no mechanism to restrict rechecks to affected activities (F6)

> **Conclusion:** Model S is **semantically flawed** for enforcement. Its permissiveness is **not intentional noise tolerance**, but **accidental semantic ambiguity**.

## # 4. Adversarial Review of Model C

###  Strongest Case for Model C

Model C is **audit-ready in structure** and **highly precise on training data** (0.941). It explicitly enumerates:
- All valid orders of mandatory checks.
- Presence/absence of `Supplier Review` based on external/internal (inferred).
- All combinations of `Expedite Review` and `Supplier Review`.
- Correction loops for `Credit Check` or `Technical Review`.

This makes it **precise and detailed**, suitable for **compliance enforcement** if the variants are exhaustive.

###  Strongest Case Against Model C

| Issue | Description | Impact |
|------|-------------|--------|
| **Branch enumeration** | 8 variants, some with duplicate labels (33) | Unmaintainable (F3), violates soundness |
| **Overfitting to training variants** | High training precision (0.941), low holdout fitness (0.744) | Fails on unseen combinations (F4) |
| **Duplicate labels** | Same activity label used in multiple branches  unsound Petri net | Breaks conformance diagnostics, confuses auditors (F3) |
| **No negative trace validation** | Precision computed only on positive traces | May accept invalid behavior; auditor cannot trust (F5) |
| **Correction handling is brittle** | Only supports full recheck of both checks after correction | Cannot model selective recheck (F6) |
| **High runtime** | 0.440s per case vs 0.018s for S | Impractical for real-time systems |
| **No support for Auto Approval in all variants** | Only one branch includes `Auto Approval` | Incomplete policy coverage |

**Example of failure:**
- A valid trace: `Register Dossier  Technical Review  Credit Check  Supplier Review  Expedite Review  Auto Approval  Release Order` (B5)
- Model C may reject it if the branch with `Auto Approval` does not include `Supplier Review` and `Expedite Review` in that order.

> **Conclusion:** Model C is **a memorized variant catalog**, not a generalizable process model. Its high precision is likely an **artifact of training-only evaluation** and **duplicate labels**. It is **not auditable** (F3) and **not maintainable**.

## # 7. Third Alternative: `model_third`

We propose a **hybrid model**: a **block-structured procedural backbone** with **DECLARE-style constraints** and **explicit uncertainty handling**.

### 1. Formal Description

```text
model_third = Block(
  Register Dossier,
  MandatoryBlock(
    Credit Check,
    Technical Review
  ),
  OptionalBlock(
    Supplier Review,
    condition=lambda: is_external(order)
  ),
  OptionalBlock(
    Expedite Review,
    condition=lambda: is_urgent(order),
    precedence=[Credit Check, Technical Review]
  ),
  ApprovalBlock(
    choice_between=[Manager Approval, Auto Approval],
    exactly_one=True
  ),
  Release Order
)

CorrectionHandler(
  Correct Dossier,
  RecheckBlock(
    Credit Check,
    Technical Review,
    condition=lambda: correction_affected('Credit Check') or correction_affected('Technical Review')
  )
)
```

**Semantics:**
- `MandatoryBlock`: Both `Credit Check` and `Technical Review` must occur, in any order.
- `OptionalBlock`: `Supplier Review` only if external; `Expedite Review` only if urgent, and must occur after both mandatory checks.
- `ApprovalBlock`: Exactly one of `Manager Approval` or `Auto Approval` occurs.
- `CorrectionHandler`: After `Correct Dossier`, only the affected checks repeat. If no correction, repeated mandatory checks are forbidden.
- **No silent transitions** except for optional blocks.
- **No duplicate labels**.

### 2. PM4Py Code

```python
from pm4py.objects.process_tree.obj import ProcessTree
from pm4py.objects.process_tree.operator import Operator
from pm4py.objects.process_tree.obj import Operator as Op

# Helper to create leaf
def leaf(name):
    node = ProcessTree(operator=Op.LEAF, label=name)
    return node

# Build MandatoryBlock: Credit Check and Technical Review in any order
mandatory = ProcessTree(operator=Op.XOR)
mandatory.children = [leaf("Credit Check"), leaf("Technical Review")]

# Optional Supplier Review (external)
supplier_opt = ProcessTree(operator=Op.OPTIONAL)
supplier_opt.children = [leaf("Supplier Review")]

# Optional Expedite Review (must follow both mandatory)
expedite_opt = ProcessTree(operator=Op.OPTIONAL)
expedite_opt.children = [leaf("Expedite Review")]

# Approval: exactly one of Manager or Auto
approval = ProcessTree(operator=Op.XOR)
approval.children = [leaf("Manager Approval"), leaf("Auto Approval")]

# Correction handler: Correct Dossier  (Credit Check or Technical Review)
correction = ProcessTree(operator=Op.SEQUENCE)
correction.children = [
    leaf("Correct Dossier"),
    ProcessTree(operator=Op.XOR)
    .add_child(leaf("Credit Check"))
    .add_child(leaf("Technical Review"))
]

# Main process
root = ProcessTree(operator=Op.SEQUENCE)
root.children = [
    leaf("Register Dossier"),
    mandatory,
    supplier_opt,
    expedite_opt,
    approval,
    correction,
    leaf("Release Order")
]

# Convert to Petri net
net, im, fm = pm4py.convert_to_petri_net(root)
```

```python
        "activities": ["Manager Approval", "Auto Approval"],
        "exactly_one": True
    },
    "supplier_only_external": {
        "type": "absence",
        "activity": "Supplier Review",
        "condition": lambda trace: not is_external(trace)
    },
    "no_recheck_without_correction": {
        "type": "absence",
        "pattern": ["Credit Check", "Credit Check"],
        "condition": lambda trace: "Correct Dossier" not in trace
    },
    "no_recheck_without_correction_tech": {
        "type": "absence",
        "pattern": ["Technical Review", "Technical Review"],
        "condition": lambda trace: "Correct Dossier" not in trace
    }
}
```

### 4. Semantics for Key Requirements

| Requirement | Implementation |
|------------|----------------|
| P1: Register Dossier first, Release Order last | Enforced by SEQUENCE |
| P2: Credit Check and Technical Review mandatory | Enforced by XOR block with cardinality 1 |
| P3: Supplier Review only for external | Enforced by optional block with external condition |
| P4: Expedite Review optional, after mandatory | Enforced by optional block with precedence constraint |
| P5: Exactly one approval | Enforced by XOR choice |
| P6: Correct Dossier may repeat checks | Handled by correction block; only affected checks repeat |
| P7: Repeated mandatory check without correction is suspicious | Enforced by absence constraints |

> **Limitation:** The `external/internal` and `affected_check` attributes are missing in logs. We assume:
> - `is_external(trace)` can be inferred from order attributes or supplier ID.
> - `correction_affected(activity)` must be provided by business rules or user input.

## # 11. Dissenting View

While the third alternative improves upon both models in semantics and maintainability, it assumes the existence of two critical attributes—`is_external` and `correction_affected`—that are **not present in the discovery log**. Without these, the model must either:
- **Silently treat all orders as external**, risking over-approval, or
- **Treat all orders as internal**, risking under-approval.

Moreover, the correction logic relies on **business judgment** to determine which checks were affected, which is not captured in the log. This introduces **human-in-the-loop dependency**, potentially delaying approvals and reducing automation.

Additionally, the third alternative **strictly enforces precedence**, which may conflict with real-world exceptions (e.g., expedited internal orders). If such cases exist but are not logged, the model may **over-reject**.

> **What would change my mind:**
> - Evidence that `is_external` can be reliably inferred from order metadata (e.g., supplier ID, order type).
> - A curated set of negative traces that the third alternative **accepts**, demonstrating over-rejection.
> - A pilot deployment showing that the correction logic integrates smoothly with existing ERP workflows.

---

**Final Note:** This review treats metrics as **evidence**, not ground truth. The strongest models are those that **enforce policy correctly**, **generalize to unseen valid behavior**, and **fail loudly on invalid behavior**—not those with the highest fitness or lowest runtime. The third alternative is the only one that meets these criteria, provided the missing attributes are addressed.
