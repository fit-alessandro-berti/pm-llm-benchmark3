

# 1. Assumptions, objectives, and decision variables

**Assumptions:**
1.  **Service Time Distribution:** Uniform distribution within provided ranges (Ordinary/Complex). Expected value = mean of bounds. Complex-tail cases drawn independently with given probability.
2.  **ME/ES Parallelism:** Default parallel execution to reduce critical path unless resource availability forces sequential.
3.  **Preemption:** Preemption occurs only if a P1 case arrives and a P2/P3 diagnostic activity is in progress (no handover mid-intake/validation).
4.  **Queuing Discipline:** First-come-first-served (FCFS) within priority tiers unless policy specifies otherwise.
5.  **Resource Availability:** Resources work within shift hours excluding breaks. Overtime (30min) is applied when demand exceeds capacity but within limits.
6.  **Complexity:** Independent across activities (not correlated by case).

**Decision Variables:**
*   **Assignment Policy:** Skill-based routing vs. skill-agnostic pool.
*   **Parallelism Control:** Thresholds for forcing parallel vs. sequential diagnostic branches.
*   **Reservation Strategy:** Fraction of total capacity allocated specifically to P1 cases.

**Objective Formulations:**
1.  **SLA-Tail Risk Minimization:**
    $$\text{Obj}_1 = \text{Weighted}_{\text{P1}} \cdot \mathbb{I}(\text{Delay} > 120m) + \text{Weighted}_{\text{P2/P3}} \cdot \mathbb{I}(\text{Delay} > \text{Target})$$
2.  **Fairness and Robustness:**
    $$\text{Obj}_2 = \text{Var}(\text{Resource Utilization}) + \text{Max}(\text{Queue Length}) \times \text{Penalty}_{\text{handover}}$$

# 3. Candidate policies

1.  **Strict Specialization (Specialist Queue)**
    *   **Eligibility:** Fixed queues per case type (e.g., Mech only Ben/Ada, Soft only Chen/Emil).
    *   **Dispatch:** FCFS within priority queues.
    *   **Parallelism:** Always sequential (no coordination).
    *   **Pros:** Low handover (7 min), low setup (5 min).
    *   **Cons:** High idle time if queues unbalanced; single point of failure.

2.  **Full Pooling (Generalist Dispatch)**
    *   **Eligibility:** Any resource capable of task.
    *   **Dispatch:** Shortest Expected Remaining Processing Time (SERPT) + Priority.
    *   **Parallelism:** Parallel if resources available; sequential if waiting > 5 min.
    *   **Pros:** Balanced utilization; resilient to absence.
    *   **Cons:** High handover (7-12 min) if handovers frequent.

3.  **Hybrid (P1 Priority Pool)**
    *   **Eligibility:** P1 reserved to Fastest resources (Ada/Farah/Emil). P2/P3 share remaining.
    *   **Dispatch:** P1 preempts P2/P3 on the same resource.
    *   **Parallelism:** Parallel for ME/ES to reduce P1 delay.
    *   **Pros:** Protects P1 SLA; reduces risk of starvation.
    *   **Cons:** High coordination overhead (8 min); potential P2/P3 starvation.

# 5. Robust recommendation

**Recommendation: Hybrid Policy (Policy 3) with Dynamic Parallelism**

**Rationale:** Under U1 (Surge) and U3 (Chen absent), specialization fails because Software capacity collapses. Pooling succeeds in load balancing but risks handover delays and complexity. The Hybrid approach protects the critical P1 SLA using dedicated capacity while leveraging pooling for P2/P3.

**Fallback Mode:** If `handover_burden` > 10% of total time, switch to Specialization temporarily.

**Triggers:**
*   **Switch to Specialization:** If resource availability drops below 70% (e.g., multiple absenteeism).
*   **Switch to Pooling:** If P1 SLA breach rate < 5% but P2/P3 delays exceed 2 hours.

# 6. Secondary effects and implementation risks

1.  **Gaming:** Operators may delay Intake to reset SLA clocks. Mitigate by locking timestamps at event start.
2.  **Starvation:** P2/P3 work may be starved by constant P1 preemption. Track P3 queue duration.
3.  **Skill Erosion:** Generalists may lose depth in Mechanical/Software.
4.  **Coordination Overhead:** Parallel branches require synchronization (8 min). In low-load periods, this wastes time.
5.  **Human Interpretability:** Rules (Parallel vs. Sequential) must be codified in the system UI.

# 7. Monitoring and process-mining design

**Event Log Attributes:**
*   `case:concept:name`
*   `concept:name` (Intake, Diagnostic, Validation)
*   `start_timestamp`, `time:timestamp`
*   `org:resource`
*   `case:case_type`, `case:priority`
*   `decision:policy_version`, `decision:parallel_flag`

**PM4Py Analyses:**
*   **Drift:** `pm4py.discover_bpmn_model` per time block; compare transition probabilities.
*   **Handover Burden:** `pm4py.discover_handover_of_work_network` to visualize inter-resource handovers (7 min penalty).
*   **Service Time:** `pm4py.get_service_time` to track deviations from base distribution (U4 impact).

# 9. Limits and validation plan

**Limits:**
*   Demand is deterministic; real-world arrivals fluctuate (Poisson processes).
*   Service ranges lack variance details (Uniform vs. Triangular).
*   "Complex-tail" probability is independent of resource speed.

**Validation Plan:**
1.  **Pilot:** Run Hybrid policy for P1 only in one shift (08:00-12:00) with 20% capacity reservation.
2.  **Backtest:** Compare simulated P1 SLA attainment against historical P1 data.
3.  **Safety Stop:** Halt policy if P3 SLA breach rate exceeds 30%.
