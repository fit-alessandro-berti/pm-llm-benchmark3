```python
import pandas as pd
import pm4py
from datetime import datetime

# Load
df = pd.read_csv("field_service_events.csv", parse_dates=["timestamp"])

# 1) Normalize renamed diagnosis label before any feature extraction
DIAGNOSIS_ALIASES = {
    "Diagnostic Assessment Completed": "Initial Diagnosis Completed",
}
df["activity"] = df["activity"].replace(DIAGNOSIS_ALIASES)

# Keep canonical activities for variant discovery, but retain UNKNOWN_ACTIVITY for DQ audit
CANONICAL = [
    "Case Created", "Triage", "Initial Diagnosis Completed",
    "Dispatch Technician", "Repair Completed", "Case Closed",
    "Remote Fix", "Order Part", "Part Received", "UNKNOWN_ACTIVITY"
]

# 2) Duplicate handling: audit then drop exact duplicates; be conservative
df = df.sort_values(["case_id", "timestamp", "activity"])
exact_dup = df.duplicated(subset=["case_id", "activity", "timestamp"], keep="first")
dup_audit = (
    df[exact_dup]
    .assign(month=lambda x: x["timestamp"].dt.to_period("M"))
    .groupby("month")
    .size()
    .rename("duplicate_events")
)
df_clean = df[~exact_dup].copy()

# Optional source-specific duplicate rule after 20 Apr 2026 if source column exists
if "source" in df_clean.columns:
    new_dup = (
        (df_clean["source"] == "new") &
        (df_clean["timestamp"] >= pd.Timestamp("2026-04-20")) &
        df_clean.duplicated(subset=["case_id", "activity", "timestamp"], keep="first")
    )
    df_clean = df_clean[~new_dup]

# 3) Format event log
log = pm4py.format_dataframe(
    df_clean,
    case_id="case_id",
    activity="activity",
    timestamp="timestamp"
)

# 4) Event-calendar cohort: all events occurring in month
df_clean["event_month"] = df_clean["timestamp"].dt.to_period("M")
event_calendar = (
    df_clean.groupby("event_month")
    .agg(
        events=("case_id", "size"),
        cases_touched=("case_id", "nunique"),
        unknown_activity_share=("activity", lambda s: (s == "UNKNOWN_ACTIVITY").mean()),
        missing_queue_share=("queue", lambda s: s.isna().mean()) if "queue" in df_clean.columns else ("activity", lambda s: 0.0),
    )
    .reset_index()
)

# 5) Case-start cohort: assign every event to the month of Case Created
case_created = (
    df_clean.loc[df_clean["activity"] == "Case Created", ["case_id", "timestamp"]]
    .groupby("case_id")["timestamp"]
    .min()
    .rename("case_start")
    .reset_index()
)
df_case = df_clean.merge(case_created, on="case_id", how="left")
df_case["start_month"] = df_case["case_start"].dt.to_period("M")

case_start_calendar = (
    df_case.groupby("start_month")
    .agg(
        cases_started=("case_id", "nunique"),
        events_in_cohort=("case_id", "size"),
        unknown_activity_share=("activity", lambda s: (s == "UNKNOWN_ACTIVITY").mean()),
    )
    .reset_index()
)

def edge_elapsed_days(frame, src, dst):
    # median elapsed time from src to next dst within case; auditable, no model
    frames = []
    for cid, g in frame.sort_values("timestamp").groupby("case_id"):
        acts = g["activity"].tolist()
        ts = g["timestamp"].tolist()
        for i, act in enumerate(acts):
            if act == src:
                for j in range(i + 1, len(acts)):
                    if acts[j] == dst:
                        frames.append((ts[j] - ts[i]).total_seconds() / 3600.0)
                        break
                break
    return pd.Series(frames, name="hours").median() if frames else None

def month_process_summary(start_month):
    cases = df_case.loc[df_case["start_month"] == start_month, "case_id"].unique()
    mdf = df_case[df_case["case_id"].isin(cases)]
    if mdf.empty:
        return {}
    mlog = pm4py.format_dataframe(mdf, case_id="case_id", activity="activity", timestamp="timestamp")
    variants = pm4py.get_variants(mlog)
    variant_counts = {k: len(v) for k, v in variants.items()}
    dfg, start_acts, end_acts = pm4py.discover_dfg(mlog)
    perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(mlog)
    temporal = pm4py.extract_temporal_features_dataframe(mlog)
    part_median_h = edge_elapsed_days(mdf, "Order Part", "Part Received")
    remote_median_h = edge_elapsed_days(mdf, "Initial Diagnosis Completed", "Remote Fix")
    return {
        "start_month": str(start_month),
        "cases_started": len(cases),
        "variant_counts": variant_counts,
        "dfg_edges": len(dfg),
        "performance_dfg_edges": len(perf_dfg),
        "order_to_part_received_median_h": part_median_h,
        "diagnosis_to_remote_fix_median_h": remote_median_h,
        "temporal_feature_rows": len(temporal),
    }

months = sorted(df_case["start_month"].dropna().unique())
monthly_process = pd.DataFrame([month_process_summary(m) for m in months])

# Optional pm4py time filtering for event-calendar audit of a month
apr_log = pm4py.filter_time_range(log, datetime(2026, 4, 1), datetime(2026, 5, 1))

# Auditable outputs, not model fitting
summary = {
    "duplicate_audit": dup_audit,
    "event_calendar": event_calendar,
    "case_start_calendar": case_start_calendar,
    "monthly_process": monthly_process,
}
summary
```

import pandas as pd
import pm4py
from datetime import datetime

df = pd.read_csv("field_service_events.csv", parse_dates=["timestamp"])

# Normalize renamed diagnosis label before feature extraction
df["activity"] = df["activity"].replace({
    "Diagnostic Assessment Completed": "Initial Diagnosis Completed",
})

# Duplicate handling: audit first, then remove exact duplicates
df = df.sort_values(["case_id", "timestamp", "activity"])
dup_mask = df.duplicated(subset=["case_id", "activity", "timestamp"], keep="first")
if "source" in df.columns:
    # Extra conservative rule for known new-source duplication window
    dup_mask = dup_mask | (
        (df["source"] == "new") &
        (df["timestamp"] >= pd.Timestamp("2026-04-20")) &
        df.duplicated(subset=["case_id", "activity", "timestamp"], keep="first")
    )
dup_audit = (
    df[dup_mask]
    .assign(month=lambda x: x["timestamp"].dt.to_period("M"))
    .groupby("month")
    .size()
    .rename("duplicate_events")
)
df_clean = df[~dup_mask].copy()

# Format log for PM4Py
log = pm4py.format_dataframe(df_clean, case_id="case_id", activity="activity", timestamp="timestamp")

# Event-calendar cohort: measures activity/system state in the month events occurred
df_clean["event_month"] = df_clean["timestamp"].dt.to_period("M")
event_calendar = (
    df_clean.groupby("event_month")
    .agg(
        events=("case_id", "size"),
        cases_touched=("case_id", "nunique"),
        unknown_activity_share=("activity", lambda s: (s == "UNKNOWN_ACTIVITY").mean()),
    )
    .reset_index()
)
if "queue" in df_clean.columns:
    event_calendar["missing_queue_share"] = (
        df_clean.groupby("event_month")["queue"].apply(lambda s: s.isna().mean()).values
    )

# Case-start cohort: aligns cases with prediction/outcome maturity by start month
case_start = (
    df_clean.loc[df_clean["activity"] == "Case Created", ["case_id", "timestamp"]]
    .groupby("case_id")["timestamp"]
    .min()
    .rename("case_start")
    .reset_index()
)
df_case = df_clean.merge(case_start, on="case_id", how="left")
df_case["start_month"] = df_case["case_start"].dt.to_period("M")
case_start_calendar = (
    df_case.groupby("start_month")
    .agg(cases_started=("case_id", "nunique"), events_in_cohort=("case_id", "size"))
    .reset_index()
)

def edge_median_hours(frame, src, dst):
    hours = []
    for _, g in frame.sort_values("timestamp").groupby("case_id"):
        acts = g["activity"].tolist()
        ts = g["timestamp"].tolist()
        for i, a in enumerate(acts):
            if a == src:
                for j in range(i + 1, len(acts)):
                    if acts[j] == dst:
                        hours.append((ts[j] - ts[i]).total_seconds() / 3600.0)
                        break
                break
    return pd.Series(hours).median() if hours else None

def monthly_process_summary(month):
    mdf = df_case[df_case["start_month"] == month]
    if mdf.empty:
        return {"start_month": str(month)}
    mlog = pm4py.format_dataframe(mdf, case_id="case_id", activity="activity", timestamp="timestamp")
    variants = pm4py.get_variants(mlog)
    dfg, start_acts, end_acts = pm4py.discover_dfg(mlog)
    perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(mlog)
    temporal = pm4py.extract_temporal_features_dataframe(mlog)
    return {
        "start_month": str(month),
        "cases_started": mdf["case_id"].nunique(),
        "variant_counts": {k: len(v) for k, v in variants.items()},
        "dfg_edge_count": len(dfg),
        "performance_dfg_edge_count": len(perf_dfg),
        "order_to_part_received_median_h": edge_median_hours(mdf, "Order Part", "Part Received"),
        "diagnosis_to_remote_fix_median_h": edge_median_hours(mdf, "Initial Diagnosis Completed", "Remote Fix"),
        "temporal_feature_rows": len(temporal),
    }

months = sorted(df_case["start_month"].dropna().unique())
monthly_process = pd.DataFrame([monthly_process_summary(m) for m in months])

# Example event-calendar filter for April schema incident audit
apr_log = pm4py.filter_time_range(log, datetime(2026, 4, 1), datetime(2026, 5, 1))

audit_bundle = {
    "duplicate_audit": dup_audit,
    "event_calendar": event_calendar,
    "case_start_calendar": case_start_calendar,
    "monthly_process": monthly_process,
    "april_event_log_rows": len(apr_log),
}
audit_bundle

## 2. Competing explanations and timeline

**January–March: stable baseline.**  
Observed breach rates are 0.18–0.19, mean predicted risk is 0.18–0.19, AUROC is about 0.81, Brier is about 0.13, ECE is about 0.02–0.03, unknown activity is about 0.2%, missing queue is 1%, and label maturity is 100%. Variant mix and matured variant breach rates are stable. This period is the clean reference baseline.

**April: schema and pipeline incident, not real performance deterioration.**  
Observed breach remains 0.19 and process evidence is stable: `Order Part -> Part Received` is 34h and remote-fix time remains normal. However, mean predicted risk jumps to 0.28, AUROC falls to 0.67, Brier rises to 0.184, ECE rises to 0.110, unknown activity reaches 17%, missing queue reaches 14%, and 18% of cases are unmapped. The rename from `Initial Diagnosis Completed` to `Diagnostic Assessment Completed` caused wrong or missing prediction prefixes, duplicate events, and unknown activities. The May patch helped but did not fully recompute cached features. April should be treated primarily as a data-pipeline failure. It would be falsified as real concept or process drift if rebuilding clean features restores April metrics close to baseline.

**May: residual pipeline repair effects.**  
May labels are mature and observed breach is 0.18, but mean predicted risk is still 0.21, AUROC is 0.78, ECE is 0.05, unknown activity is 2%, and missing queue is 3%. This is consistent with partial recovery after the mapping patch, with residual derived-feature staleness. May is not yet fully clean, but it is much closer to normal than April.

**June: routing-policy and variant-mix change, not necessarily concept drift.**  
The remote-routing policy increases V2 from about 35% to 52%. V2 matured breach is low, about 0.09. A simple mix-adjusted estimate using matured variant breach rates gives roughly:  
`0.30 * 0.16 + 0.52 * 0.09 + 0.18 * 0.35  0.16`, close to the observed 0.15.  
Mean predicted risk is 0.20, so the model does not fully reflect the lower-risk mix. Variant-specific breach rates remain stable, and remote-fix duration remains stable. Therefore June is best explained by process/covariate/intervention drift, not concept drift. Retraining solely because of June would likely be disproportionate; recalibration or mix adjustment is more appropriate.

**July: early supplier performance degradation, especially in V3.**  
Supplier delivery targets begin to fail. `Order Part -> Part Received` rises from 42h in June to 65h in July. V3 matured breach rises from about 0.35 to 0.46. Overall observed breach remains 0.19 because V2 still accounts for 50% of cases and V2 breach remains low. Mean predicted risk is 0.18, close to the overall observed rate, but AUROC falls to 0.76, suggesting the model is not ranking the newly risky V3 cases well. July is primarily process-performance drift with early apparent concept drift for V3.

**August: severe supplier degradation plus V3 mix growth.**  
The supplier issue becomes severe. Part lead time reaches 130h, V3 share rises to 35%, and V3 matured breach reaches 0.64. A mix-adjusted estimate is roughly:  
`0.25 * 0.18 + 0.40 * 0.11 + 0.35 * 0.64  0.31`, close to the observed 0.28 given 93% maturity.  
Mean predicted risk is only 0.19, ECE is 0.12, and AUROC is 0.68. This is not a label-maturity artifact: maturity is still high and the observed breach is already high. August is a real performance and risk deterioration, involving process drift, covariate mix, and likely apparent concept drift because the model’s pre-diagnosis features do not capture the new supplier environment.

**September: overlapping supplier, process, population, and censoring effects.**  
Partner Z is onboarded. Partner Z share is 24%, 58% of Partner Z cases are V3, and Partner Z has higher rural distance and device age, which the model does not use. Part lead time is 148h, V3 share is 42%, and V3 matured breach remains high at 0.61. A rough mix-adjusted estimate is:  
`0.22 * 0.19 + 0.36 * 0.12 + 0.42 * 0.61  0.34`, while observed breach is 0.31 at only 82% maturity. Partner Z observed breach is 0.45 versus 0.27 for others, but Partner Z labels mature more slowly. September is therefore a confounded month: population shift, process/performance drift, covariate drift, possible concept drift, and emerging label censoring are all present. It should not be treated as a single failure.

**October: evaluation is dominated by label maturity and censoring.**  
October has only 55% label maturity, median label delay of 52d, and an outcome API backlog that disproportionately affects longer cases. Observed breach falls to 0.16, but this is not credible as a true improvement because Partner Z share is 27%, V3 share is 41%, and part lead time is 155h. If September’s matured variant risks approximately persisted, the mix-adjusted breach would be roughly:  
`0.23 * 0.19 + 0.35 * 0.12 + 0.41 * 0.61  0.34`.  
The gap between about 0.34 and observed 0.16 is best explained by immature and informatively censored labels. October should not be used as evidence of model failure or process improvement until labels mature.

**Why the failures are not homogeneous:**  
April is a schema/pipeline incident. June is a routing-policy mix change. August–September are real supplier- and population-related risk increases, with possible concept drift. October is heavily confounded by label maturity. A single drift label would misattribute distinct causes and trigger wrong remediation.

## 3. Diagnostic tests

1. **Label-maturity curves and fixed-vintage backtesting**

   - **Method:** For each case-start month, plot the cumulative proportion of labels matured as a function of days since case start or days since promised resolution date. Compute observed breach at fixed observation windows, for example 30, 60, and 90 days. Compare naive cutoff metrics with fixed-vintage metrics and, if possible, Kaplan–Meier or cumulative-incidence estimates for breach.
   - **Expected under label delay/censoring:** September and especially October curves are still rising at the reporting cutoff. Fixed-vintage breach for October is much higher than the naive 0.16. Long-path variants, especially V3 and Partner Z cases, have lower maturity and higher eventual breach.
   - **Expected under real process or concept drift:** Even after fixing the observation window, August and September remain materially higher than January–June. October, once mature, does not show a true drop to 0.16.
   - **Falsification implication:** If October’s fixed-vintage breach remains near 0.16 and maturity curves plateau early, label delay is not the main explanation.

2. **Recomputation after activity-label normalization and duplicate cleaning**

   - **Method:** Map `Diagnostic Assessment Completed` to `Initial Diagnosis Completed`. Remove or flag duplicate events, especially new-source duplicates after 20 April. Rebuild prediction prefixes and derived features such as “number of events before diagnosis” and queue features. Rerun the unchanged model on the repaired April/May data.
   - **Expected under data-pipeline failure:** April mean predicted risk falls from about 0.28 toward 0.18–0.20, AUROC improves toward 0.80, ECE falls, unknown/unmapped shares collapse, and May residual miscalibration improves.
   - **Expected under real concept or process drift:** Cleaning labels and duplicates does not remove the August–September underprediction for V3 or the gap between predicted risk and matured breach.
   - **Falsification implication:** If April metrics remain poor after clean recomputation, the April incident was not only a pipeline issue.

3. **Calibration and discrimination stratified by variant, source, and month**

   - **Method:** Compute AUROC, Brier, ECE, calibration slope, calibration intercept, and mean predicted versus observed breach within strata: V1/V2/V3, old/new source, Partner Z/non-Z, and month. Compare overall metrics with within-stratum metrics.
   - **Expected under covariate/process mix drift:** Overall metrics change, but variant-specific metrics are relatively stable. June’s overall miscalibration is explained by the increased V2 share.
   - **Expected under concept drift:** V3 calibration deteriorates in July–September even after stratifying by variant and available pre-diagnosis features. V1 and V2 remain stable.
   - **Expected under pipeline failure:** April metrics are bad mainly for new-source records, records with unknown activity, or records with missing queue features.
   - **Expected under population shift:** Partner Z stratum is poorly calibrated, while non-Z September cases are closer to baseline.
   - **Falsification implication:** If stratified metrics are stable and only the aggregate changes, concept drift is unlikely.

4. **Comparison of process variants and DFG/performance-DFG edges**

   - **Method:** Discover monthly variants and DFGs from cleaned event logs. Track variant shares, unmapped variants, unknown activities, and edge durations, especially `Order Part -> Part Received`, `Initial Diagnosis Completed -> Remote Fix`, and `Dispatch Technician -> Repair Completed`. Use performance DFG or direct event-timestamp calculations.
   - **Expected under process drift:** V2 share jumps in June; V3 share rises in August–September; `Order Part -> Part Received` rises sharply from July onward; Partner Z routes more cases through V3.
   - **Expected under pipeline failure:** April shows many unknown or unmapped edges, but underlying edge durations for mapped cases remain stable. After normalization, the DFG resembles January–March.
   - **Expected under label censoring:** October process evidence remains bad, with long part lead times and high V3 share, while observed labels appear artificially low.
   - **Falsification implication:** If variant shares and edge durations are stable after cleaning, process drift is not the explanation.

5. **Tests of whether the outcome relationship conditional on the same path changed**

   - **Method:** Compare breach probabilities for cases following the same variant and similar pre-diagnosis feature values across periods. Use matching, stratified logistic regression, or interaction tests such as `V3 * post-July` and `Partner Z * September`. Where actual part lead time is known, condition on it as well.
   - **Expected under no concept drift, only process/performance drift:** V1 and V2 conditional breach rates remain stable. V3 risk differences are largely explained by actual part lead time, supplier status, or Partner Z covariates.
   - **Expected under concept drift:** V3 cases with the same observed pre-diagnosis features and similar paths have higher breach probability after July even after accounting for lead time and partner effects.
   - **Falsification implication:** If adding actual supplier lead time and partner features fully removes the residual V3 risk increase, the issue is omitted-variable/process drift rather than intrinsic concept drift.

6. **Population reweighting or transport-style checks for Partner Z**

   - **Method:** Estimate the probability of being a Partner Z case from observed covariates. Use inverse-probability weighting or entropy balancing to reweight non-Z cases to resemble Partner Z, or train on non-Z data and test on Partner Z. Compare performance before and after adding Partner Z, rural-distance, and device-age features.
   - **Expected under population shift/covariate drift:** Reweighting or adding the missing population features materially reduces the Partner Z performance gap.
   - **Expected under concept drift or unobserved service-level differences:** The Partner Z gap persists after reweighting and after adding available covariates, suggesting a Partner-Z-specific relationship or missing operational variables.
   - **Expected under label censoring:** Partner Z gap changes substantially after maturity correction because Partner Z labels mature more slowly.
   - **Falsification implication:** If Partner Z performance is unchanged after maturity correction and reweighting, simple population mix is not sufficient.

7. **Feature missingness and lineage audits**

   - **Method:** Audit missingness by month and source for queue, activity label, derived event-count features, prediction prefix timestamp, model version, and outcome label timestamp. Trace whether derived features were recomputed after the May patch. Check duplicate rates by source and date.
   - **Expected under pipeline failure:** Missing queue, unknown activity, stale event-count features, and duplicate events spike in April and partially persist in May. Bad predictions concentrate in records with missing or stale lineage.
   - **Expected under genuine drift:** Missingness and lineage are clean, but feature distributions shift because of variant mix, supplier state, or Partner Z population.
   - **Falsification implication:** If lineage is clean and missingness is low, pipeline failure is unlikely for the affected month.

## 4. Recalibration-versus-retraining decision

**Immediate containment**

- Freeze automatic retraining on raw April, September, and October labels.
- Do not treat October’s observed 0.16 breach rate as true performance.
- Repair the event schema first: normalize diagnosis labels, remove duplicates, rebuild prediction prefixes, and recompute cached features.
- Use the clean January–March model as the reference baseline, but apply operational overlays for known high-risk segments: V3 cases, long supplier lead times, and Partner Z rural cases.
- If production decisions cannot wait, use conservative business rules or segment-specific uplifts for V3 and Partner Z until mature labels are available.

**Short-term recalibration**

- Recalibration is appropriate if the main issue is mix shift and the conditional relationship within segments is stable.
- June is a strong candidate for recalibration or prior correction because V2 volume increased but V2-specific breach remained low.
- May can be used for recalibration only after derived features are fully recomputed.
- July can be used cautiously if maturity is confirmed and V3-specific calibration is checked.
- Use isotonic regression, Platt scaling, or beta calibration on mature data. Consider separate calibrators for V1/V2/V3 and for Partner Z once enough mature Partner Z labels exist.

**Feature repair and augmentation**

- Add supplier-state features: part category lead time, supplier SLA status, current backlog, and promised-date buffer.
- Add population features: partner identifier, rural distance, device age, and regional service capacity.
- Add data-quality indicators: source system, unknown activity flag, missing queue flag, duplicate flag, and label-maturity indicator.
- Add routing-policy indicators for the June remote-resolution policy.
- If prediction must occur immediately after diagnosis, use current environmental features rather than future actual lead times, but retain actual lead time for audit and post-diagnosis risk updates.

**Full retraining**

- Retrain only after pipeline repair and label maturity are sufficient.
- Retraining is justified if mature stratified tests show persistent concept drift, especially for V3 or Partner Z after adding supplier and population features.
- Use a rolling training window that excludes immature labels and pipeline-corrupted feature snapshots.
- Validate with fixed-vintage backtests, not only calendar-month cutoffs.

**Segment-specific or variant-specific model justification**

- A global model with variant-specific calibrators is the minimum reasonable response.
- A V3-specific model or V3-heavy risk overlay is justified because V3 has distinct breach dynamics, supplier sensitivity, and high risk.
- A Partner Z-specific model is not yet justified without more mature data and missing-feature collection. A hierarchical or pooled model with Partner Z features and segment calibration is safer.
- V1 and V2 appear stable enough to remain in a shared model, with V2 calibration checked after routing-policy changes.

## 5. Monitoring architecture

**Monitor components**

1. **Predictive performance monitor**
   - Metrics: AUROC, Brier, mean predicted risk, observed breach rate, PSI/KS on predictions.
   - Rule: Trigger formal performance alarms only on mature cohorts or fixed-vintage metrics.

2. **Calibration monitor**
   - Metrics: ECE, calibration slope/intercept, predicted-versus-observed by risk decile.
   - Stratify by variant, partner, source, and month.
   - Rule: Calibration alarms require clean data and sufficient label maturity.

3. **Label-maturity monitor**
   - Metrics: percent mature at 30/60/90 days, median label delay, outcome API backlog, maturity by variant and partner.
   - Rule: If maturity is below threshold, mark all outcome-based metrics as provisional and suppress retraining alarms.

4. **Data-quality monitor**
   - Metrics: unknown activity share, missing queue share, duplicate rate, unmapped variant share, schema mismatches, stale derived-feature rate.
   - Rule: If data quality is bad for a source/month, suppress model-performance alarms for that scope and open a pipeline ticket.

5. **Process-variant monitor**
   - Metrics: V1/V2/V3 shares, unmapped/rare variants, new paths.
   - Rule: Variant-mix alarms trigger process review and covariate reweighting, not automatic retraining.

6. **Performance-DFG monitor**
   - Metrics: median and percentile edge durations, especially `Order Part -> Part Received`, `Initial Diagnosis Completed -> Remote Fix`, and `Dispatch Technician -> Repair Completed`.
   - Rule: Edge-duration alarms trigger operational escalation and feature updates. Retraining is considered only if mature outcome metrics confirm persistent risk gaps.

7. **Population monitor**
   - Metrics: partner share, rural distance, device age, regional distribution, PSI against training population.
   - Rule: Population-shift alarms trigger feature collection and stratified evaluation, not automatic retraining.

8. **Intervention/deployment monitor**
   - Metrics: model version, feature-pipeline patches, routing-policy changes, supplier incidents, Partner Z onboarding dates.
   - Rule: Use annotations to attribute alerts correctly and avoid blaming the model for operational changes.

**Alert dependency logic**

- If **data-quality alarm** is active, suppress model-performance and retraining alarms for the affected source/month.
- If **label-maturity alarm** is active, mark performance metrics provisional and suppress retraining alarms.
- If **process-performance alarm** is active but labels are mature, trigger operational review and feature update before retraining.
- If **population-shift alarm** is active, trigger stratified analysis and reweighting before retraining.
- Trigger retraining only when data quality is acceptable, labels are mature or maturity-adjusted, and stratified mature metrics show persistent concept drift or unexplained calibration failure.

import pandas as pd
import pm4py
from datetime import datetime

# Load local event data
df = pd.read_csv("field_service_events.csv", parse_dates=["timestamp"])

# Normalize renamed diagnosis label before any feature extraction
df["activity"] = df["activity"].replace({
    "Diagnostic Assessment Completed": "Initial Diagnosis Completed",
})

# Duplicate handling: audit first, then remove exact duplicates
df = df.sort_values(["case_id", "timestamp", "activity"])
dup_mask = df.duplicated(subset=["case_id", "activity", "timestamp"], keep="first")

if "source" in df.columns:
    # Extra conservative rule for the known new-source duplication window
    dup_mask = dup_mask | (
        (df["source"] == "new") &
        (df["timestamp"] >= pd.Timestamp("2026-04-20")) &
        df.duplicated(subset=["case_id", "activity", "timestamp"], keep="first")
    )

dup_audit = (
    df[dup_mask]
    .assign(month=lambda x: x["timestamp"].dt.to_period("M"))
    .groupby("month")
    .size()
    .rename("duplicate_events")
)

df_clean = df[~dup_mask].copy()

# Format log for PM4Py
log = pm4py.format_dataframe(
    df_clean,
    case_id="case_id",
    activity="activity",
    timestamp="timestamp"
)

# Event-calendar cohort:
# Interprets activity volume and data quality in the month events occurred.
df_clean["event_month"] = df_clean["timestamp"].dt.to_period("M")
event_calendar = (
    df_clean.groupby("event_month")
    .agg(
        events=("case_id", "size"),
        cases_touched=("case_id", "nunique"),
        unknown_activity_share=("activity", lambda s: (s == "UNKNOWN_ACTIVITY").mean()),
    )
    .reset_index()
)

if "queue" in df_clean.columns:
    event_calendar["missing_queue_share"] = (
        df_clean.groupby("event_month")["queue"]
        .apply(lambda s: s.isna().mean())
        .values
    )

# Case-start cohort:
# Aligns cases with prediction/outcome maturity by the month the case started.
case_start = (
    df_clean.loc[df_clean["activity"] == "Case Created", ["case_id", "timestamp"]]
    .groupby("case_id")["timestamp"]
    .min()
    .rename("case_start")
    .reset_index()

def edge_median_hours(frame, src, dst):
    """Auditable median elapsed time from src to next dst within each case."""
    hours = []
    for _, g in frame.sort_values("timestamp").groupby("case_id"):
        acts = g["activity"].tolist()
        ts = g["timestamp"].tolist()
        for i, a in enumerate(acts):
            if a == src:
                for j in range(i + 1, len(acts)):
                    if acts[j] == dst:
                        hours.append((ts[j] - ts[i]).total_seconds() / 3600.0)
                        break
                break
    return pd.Series(hours).median() if hours else None

def monthly_process_summary(month):
    mdf = df_case[df_case["start_month"] == month]
    if mdf.empty:
        return {"start_month": str(month)}

    mlog = pm4py.format_dataframe(
        mdf,
        case_id="case_id",
        activity="activity",
        timestamp="timestamp"
    )

    variants = pm4py.get_variants(mlog)
    variant_counts = {
        str(k): (len(v) if hasattr(v, "__len__") else int(v))
        for k, v in variants.items()
    }

    dfg, start_acts, end_acts = pm4py.discover_dfg(mlog)
    perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(mlog)
    temporal = pm4py.extract_temporal_features_dataframe(mlog)

    return {
        "start_month": str(month),
        "cases_started": mdf["case_id"].nunique(),
        "variant_counts": variant_counts,
        "dfg_edge_count": len(dfg),
        "performance_dfg_edge_count": len(perf_dfg),
        "order_to_part_received_median_h": edge_median_hours(
            mdf, "Order Part", "Part Received"

        "diagnosis_to_remote_fix_median_h": edge_median_hours(
            mdf, "Initial Diagnosis Completed", "Remote Fix"

        "temporal_feature_rows": len(temporal),
    }

months = sorted(df_case["start_month"].dropna().unique())

## 6. Risks of acting on the wrong diagnosis

| Failure mode | Consequence | Mitigation |
|---|---|---|
| Retraining on immature October or September labels | The model learns that long-path, V3, and Partner Z cases have low breach probability simply because their labels have not matured. This would systematically underpredict future breaches and worsen SLA misses. | Require label-maturity thresholds for training.<br>Use fixed-vintage backtests and survival/censoring adjustments.<br>Exclude or down-weight months with low maturity, especially October. |
| Calibrating around the April pipeline bug | A calibrator may learn to compensate for missing queue values, unknown activities, or stale event-count features. When the pipeline is fixed, the calibration becomes wrong and may hide the root cause. | Quarantine April raw features.<br>Normalize labels, remove duplicates, and recompute derived features before any calibration.<br>Recalibrate only after clean rebuild and stratified validation. |
| Ignoring genuine supplier-driven process or concept drift | If August–September V3 risk is real and not addressed, the model will continue to underpredict breaches for parts-dependent cases. Operational mitigation may also be delayed. | Monitor `Order Part -> Part Received` and supplier SLA metrics.<br>Add supplier lead-time and part-category risk features.<br>Use V3-specific calibration or retraining once mature labels confirm the shift. |
| Attributing Partner Z differences to unfair model behavior without stratified evidence | The organization may incorrectly penalize the model or Partner Z without understanding whether the gap is caused by missing covariates, label censoring, process differences, or true segment-specific risk. | Stratify by partner, variant, region, and maturity.<br>Add rural-distance and device-age features.<br>Use reweighting/transportability checks before deciding on fairness or segment-model actions. |
| Treating October’s low observed breach rate as real improvement | Management might reduce supplier escalation or routing controls based on an artificial improvement caused by label backlog. | Keep label-maturity alarms separate from performance alarms.<br>Report October metrics only as provisional.<br>Re-evaluate after outcome API backlog is cleared and labels mature. |
