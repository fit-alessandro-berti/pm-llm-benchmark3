**Why both DFG directions do not prove concurrency.** The DFG contains both `("Credit Check", "Engineering Review"): 17` and `("Engineering Review", "Credit Check"): 11`. This only shows that, in the completion log, Credit Check sometimes completes before Engineering Review and sometimes after. That bidirectional evidence rules out a strict sequence in one fixed direction, but it does not prove concurrency: the same completion orders could be produced by strictly sequential execution in either order, or by overlapping execution with different completion times. D7 explicitly warns that completion timestamps do not reveal actual concurrency. Therefore, the balanced and permissive models treat Credit Check and Engineering Review as unordered/partially ordered, while the conservative model simply enumerates both observed orders.

# 2. Shared Assumptions

- **Event-completion semantics.** Only completion timestamps are available. The order in the log is completion order, not start order. We do not infer that two activities were concurrent merely because their completion order varies.
- **Missing Supplier Confirmation events.** S5 states that around 5–10% of Supplier Confirmation events may be missing due to an integration problem. All three models treat Supplier Confirmation as optional, but this optionality is an abstraction: it conflates true stocked-component skip (S4) with missing data (S5). We do not model missingness explicitly.
- **Absent external/stocked attribute.** S5 states that the external/stocked attribute was not exported. We cannot condition Supplier Confirmation on it. We represent the uncertainty through control-flow alternatives (optional Supplier Confirmation, and in the permissive model, multiple Supplier Confirmations).
- **Optionality representation.** Optionality is represented by XOR with a silent transition, or by XOR branches in POWL.
- **Common constraints.** All models enforce D1, D2, D3, and D6. D4 is enforced whenever Supplier Confirmation occurs.
- **Activity labels.** Activity labels are treated as unique within a trace, except that the permissive model deliberately allows multiple Supplier Confirmation events.
- **Sample incompleteness.** The 30 observed traces are a sample, not an exhaustive specification of the process.

# 3. Conservative Candidate

**Inductive-bias statement.** The conservative model is an XOR enumeration of exactly the seven observed variants. Its inductive bias is that only behavior directly observed in the log is allowed; no generalization is made beyond the observed traces. High-confidence rules are satisfied, but they are not used to admit unobserved behavior. This minimizes the risk of admitting unsupported behavior at the cost of severe underfitting.

**Compact formal expression.** Let `R = Register Order`, `CC = Credit Check`, `ER = Engineering Review`, `SC = Supplier Confirmation`, `EX = Expedite Review`, `A = Approve Configuration`, `RP = Release Production`, `Ar = Archive Case`.

```
X(
  ->(R, CC, ER, SC, A, RP, Ar),
  ->(R, ER, CC, SC, A, RP, Ar),
  ->(R, CC, ER, A, RP, Ar),
  ->(R, ER, CC, A, RP, Ar),
  ->(R, CC, SC, ER, A, RP, Ar),
  ->(R, CC, ER, SC, EX, A, RP, Ar),
  ->(R, ER, CC, EX, SC, A, RP, Ar)
)
```

**PM4Py code.**

```python
    "->('Register Order','Credit Check','Engineering Review','Approve Configuration','Release Production','Archive Case'),"

    ")"
)

model_conservative = pm4py.parse_process_tree(conservative_tree_string)
```

**Behavior deliberately excluded.**

- Supplier Confirmation after Engineering Review but before Credit Check.
- Expedite Review without Supplier Confirmation.
- Multiple Supplier Confirmation events.
- Any interleaving not exactly matching one of the seven observed variants.
- Supplier Confirmation after Expedite Review when Credit Check precedes Engineering Review.
- Traces with missing Supplier Confirmation in an expedite variant.

**Known underfitting risks.**

- Overfits to the observed variants; poor generalization to unseen but valid traces.
- Brittle to missing Supplier Confirmation events in expedite traces.
- XOR enumeration scales poorly: the number of branches grows with the number of variants, and duplicate labels within a branch would be ambiguous because process-tree leaves with the same label are indistinguishable.

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model prefers partial order and concurrency for activities whose order varies, uses XOR only for genuine optionality or placement uncertainty, and enforces high-confidence rules strictly. It treats Credit Check and Engineering Review as unordered, Supplier Confirmation as optional and allowed after either check, and Expedite Review as optional after both checks and before approval.

**Compact formal expression.** Let `PO(...)` denote a strict partial order. Let `EX? = XOR(tau, EX)`. The model is an XOR of three partial orders:

```
X(
  PO(R, CC, ER, EX?, A, RP, Ar;
     RCC, RER, CCA, ERA,
     CCEX?, EREX?, EX?A,
     ARP, RPAr),

  PO(R, CC, ER, SC, EX?, A, RP, Ar;
     RCC, RER, CCSC, SCA, ERA,
     CCEX?, EREX?, EX?A,
     ARP, RPAr),

  PO(R, CC, ER, SC, EX?, A, RP, Ar;
     RCC, RER, ERSC, SCA, CCA,
     CCEX?, EREX?, EX?A,
     ARP, RPAr)
)
```

**PM4Py code.**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def make_balanced_branch(supplier_after):
    R = Transition("Register Order")
    CC = Transition("Credit Check")
    ER = Transition("Engineering Review")
    A = Transition("Approve Configuration")
    RP = Transition("Release Production")
    AR = Transition("Archive Case")
    EX = Transition("Expedite Review")

    expedite_choice = OperatorPOWL(
        operator=Operator.XOR,
        children=[SilentTransition(), EX],
    )

    nodes = [R, CC, ER, expedite_choice, A, RP, AR]
    edges = [
        (R, CC),
        (R, ER),
        (CC, A),
        (ER, A),
        (CC, expedite_choice),
        (ER, expedite_choice),
        (expedite_choice, A),
        (A, RP),
        (RP, AR),
    ]

    if supplier_after == "CC":
        SC = Transition("Supplier Confirmation")
        nodes.append(SC)
        edges.extend([(CC, SC), (SC, A)])
    elif supplier_after == "ER":
        SC = Transition("Supplier Confirmation")
        nodes.append(SC)
        edges.extend([(ER, SC), (SC, A)])

    po = StrictPartialOrder(nodes=nodes)
    for src, dst in edges:
        po.order.add_edge(src, dst)
    return po


model_balanced = OperatorPOWL(
    operator=Operator.XOR,
    children=[
        make_balanced_branch(None),
        make_balanced_branch("CC"),
        make_balanced_branch("ER"),
    ],
)
```

**How sequence, concurrency, and partial order are decided.**

- **Credit Check and Engineering Review.** Both orders are observed, and S2 says they normally run in parallel. D7 warns that completion order does not prove concurrency. Therefore, the balanced model imposes no edge between Credit Check and Engineering Review; they are unordered/concurrent in the partial order. This avoids choosing S1 over S2.
- **Supplier Confirmation.** D5 says it may begin after either Credit Check or Engineering Review. A single partial-order edge from both checks would impose a join (both required), which is too strict. A single edge from only one check would impose a fixed order. The balanced model uses an XOR of two partial orders: one with `Credit Check  Supplier Confirmation`, and one with `Engineering Review  Supplier Confirmation`. This is an OR-join abstraction: Supplier Confirmation can occur after Credit Check or after Engineering Review, but not before either. It also allows Supplier Confirmation after both, because both branches can produce that case.
- **Expedite Review.** D6 and S6 say it is optional, at most once, requires both Credit Check and Engineering Review, and precedes Approve Configuration. The model uses `XOR(tau, Expedite Review)` with incoming edges from both Credit Check and Engineering Review. It is left unordered with Supplier Confirmation because S6 says Expedite Review may occur before or after Supplier Confirmation.

**Behavior deliberately excluded.**

- Supplier Confirmation before any check.
- Expedite Review before both checks.
- Multiple Expedite Review events.
- Missing Credit Check or Engineering Review.
- Supplier Confirmation after Approve Configuration.
- Release Production before Approve Configuration.
- Archive Case before Release Production.

**Known underfitting risks.**

- The XOR branches duplicate Credit Check and Engineering Review labels; if the true process has more complex OR-joins, the model may underfit.
- It may overgeneralize Supplier Confirmation placement, e.g., admitting Supplier Confirmation after Engineering Review before Credit Check even if that is not actually allowed.
- It does not model multiple Supplier Confirmation events.

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model admits all reasonable combinations consistent with the broad domain rules. It keeps high-confidence rules strict but allows multiple Supplier Confirmation events because S3 says Supplier Confirmation is mandatory for every external component and the external/stocked attribute is absent. This makes it suitable for exploration and sensitivity analysis.

**Compact formal expression.** Let `SC* = XOR(tau, *(SC, tau))` denote zero or more Supplier Confirmation events. Let `EX? = XOR(tau, EX)`. The model is an XOR of two partial orders:

```
X(
  PO(R, CC, ER, SC*, EX?, A, RP, Ar;
     RCC, RER, CCSC*, SC*A, ERA,
     CCEX?, EREX?, EX?A,
     ARP, RPAr),

  PO(R, CC, ER, SC*, EX?, A, RP, Ar;
     RCC, RER, ERSC*, SC*A, CCA,
     CCEX?, EREX?, EX?A,
     ARP, RPAr)
)
```

**PM4Py code.**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def make_permissive_branch(supplier_after):
    R = Transition("Register Order")
    CC = Transition("Credit Check")
    ER = Transition("Engineering Review")
    A = Transition("Approve Configuration")
    RP = Transition("Release Production")
    AR = Transition("Archive Case")
    EX = Transition("Expedite Review")
    SC = Transition("Supplier Confirmation")

    expedite_choice = OperatorPOWL(
        operator=Operator.XOR,
        children=[SilentTransition(), EX],
    )

    supplier_loop = OperatorPOWL(
        operator=Operator.XOR,
        children=[
            SilentTransition(),
            OperatorPOWL(
                operator=Operator.LOOP,
                children=[SC, SilentTransition()],
            ),
        ],
    )

    nodes = [R, CC, ER, supplier_loop, expedite_choice, A, RP, AR]
    edges = [
        (R, CC),
        (R, ER),
        (CC, A),
        (ER, A),
        (CC, expedite_choice),
        (ER, expedite_choice),
        (expedite_choice, A),
        (A, RP),
        (RP, AR),
    ]

    if supplier_after == "CC":
        edges.append((CC, supplier_loop))
    elif supplier_after == "ER":
        edges.append((ER, supplier_loop))

    edges.append((supplier_loop, A))

    po = StrictPartialOrder(nodes=nodes)
    for src, dst in edges:
        po.order.add_edge(src, dst)
    return po


model_permissive = OperatorPOWL(
    operator=Operator.XOR,
    children=[
        make_permissive_branch("CC"),
        make_permissive_branch("ER"),
    ],
)
```

**Boundary between reasonable generalization and forbidden behavior.**

- **Reasonable generalization.** Multiple Supplier Confirmation events (one per external component), any interleaving of Supplier Confirmation and Expedite Review after their prerequisites, either order of Credit Check and Engineering Review, optional Supplier Confirmation, and optional Expedite Review.
- **Forbidden behavior.** Missing Credit Check or Engineering Review, Expedite Review before both checks, Expedite Review after Approve Configuration, Supplier Confirmation after Approve Configuration, Release Production before Approve Configuration, Archive Case before Release Production, multiple Expedite Review events, Supplier Confirmation before Register Order, and any activity after Archive Case.

**Behavior deliberately excluded.**

- Multiple Expedite Review events.
- Expedite Review before both Credit Check and Engineering Review.
- Supplier Confirmation after Approve Configuration.
- Missing Credit Check or Engineering Review.
- Release Production before Approve Configuration.
- Archive Case before Release Production.
- Supplier Confirmation before Register Order.

**Known underfitting risks.**

- May overgeneralize by allowing many Supplier Confirmation events; precision risk.
- The loop may create very long traces with many Supplier Confirmation events, which may be unlikely.
- Does not distinguish true stocked-component skip from missing Supplier Confirmation events.

# 9. Recommendation and Data-Collection Plan

**Recommendation.**

- **Immediate use:** `model_balanced`. It fits all 30 observed cases, respects the high-confidence rules, generalizes reasonably, and is explainable. It is the best compromise between precision and generalization.
- **Sensitivity analysis:** `model_permissive`. It should be used to test the impact of allowing multiple Supplier Confirmation events and broader interleavings. If the permissive model admits many implausible traces, the balanced model is preferred.

**Data-collection plan.**

1. **Collect the external/stocked attribute** for each order. This will distinguish true stocked-component skip from missing Supplier Confirmation events.
2. **Collect start and completion timestamps** for each activity. This will distinguish concurrency from sequence for Credit Check and Engineering Review.
3. **Collect supplier/component identifiers.** This will reveal whether multiple Supplier Confirmation events are possible and whether the permissive model's loop is justified.
4. **Collect expedite reason and requester.** This will clarify when Expedite Review is triggered and whether it is independent of Supplier Confirmation.
5. **Collect traces with known missing Supplier Confirmation events.** This will quantify the missing rate and test robustness.
6. **Maximally informative future traces:**
   - `Register Order, Engineering Review, Supplier Confirmation, Credit Check, Approve Configuration, Release Production, Archive Case` — tests Supplier Confirmation after Engineering Review before Credit Check.
   - `Register Order, Credit Check, Engineering Review, Expedite Review, Approve Configuration, Release Production, Archive Case` — tests Expedite Review without Supplier Confirmation.
   - `Register Order, Credit Check, Engineering Review, Supplier Confirmation, Supplier Confirmation, Approve Configuration, Release Production, Archive Case` — tests multiple Supplier Confirmations.
   - Traces with start timestamps showing overlap of Credit Check and Engineering Review — tests concurrency.
   - Traces with missing Supplier Confirmation events — tests missingness robustness.

These data would directly reduce uncertainty about XOR vs sequence vs concurrency, optionality, and the Supplier Confirmation placement.

# 10. Uncertainty Statement

**Calibrated confidence assessments.**

- **Credit Check and Engineering Review are unordered/concurrent (balanced/permissive).** Confidence: medium-high. Both orders are observed, and S2 supports concurrency. However, D7 warns that completion order does not prove concurrency. Alternative: S1 is correct and the observed Engineering-Review-before-Credit-Check traces are due to logging or data-quality issues; if so, balanced/permissive overgeneralize by allowing Engineering Review before Credit Check.
- **Supplier Confirmation is optional (all models).** Confidence: high that it is optional in the log, but medium that optionality represents true skip versus missing data. Alternative: if missing Supplier Confirmation events are frequent, the optional Supplier Confirmation abstraction may misclassify traces with missing events as no-supplier traces.
- **Supplier Confirmation may occur after either Credit Check or Engineering Review (balanced/permissive).** Confidence: medium. Based on D5 and V5. Alternative: D5 is wrong and Supplier Confirmation actually requires both checks; then balanced/permissive overgeneralize, and a model with Supplier Confirmation after both checks would be more appropriate.
- **Expedite Review requires both checks and precedes approval (all models).** Confidence: medium-high. Based on D6 and S6. Alternative: if D6 is wrong, balanced/permissive may underfit.
- **Multiple Supplier Confirmations are allowed (permissive only).** Confidence: low-medium. Plausible if multiple external components exist, but unobserved. Alternative: if at most one Supplier Confirmation is allowed, the permissive model overgeneralizes.
- **Conservative XOR enumeration exactly matches observed behavior.** Confidence: high for the observed variants, but low for generalization.

**Plausible alternative interpretation that would materially change the recommendation.** If the external/stocked attribute were available and showed that Supplier Confirmation is mandatory for all external components, and if the missing Supplier Confirmation events are actually integration failures, then the balanced model's optional Supplier Confirmation would be too permissive. In that case, a model with Supplier Confirmation mandatory for external cases would be needed, and the recommendation would shift toward a stricter model with explicit missing-data handling. Similarly, if start timestamps showed that Credit Check and Engineering Review are strictly sequential, the balanced/permissive models would overgeneralize, and a sequence model would be preferred.
