### **1. Conformance semantics**
The normative framework distinguishes compliance via **status-based interpretation** rather than absolute graph matching. The four statuses—**mandatory, forbidden, typical, unspecified**—define strict, permissive, common, or ungoverned expectations, respectively. **Closed-world assumptions** apply only to forbidden relations and mandatory edges within explicit scope; all others are **open-world**.

- **Forbidden behavior** is a **hard violation** (e.g., `Cancel Order -> Dispatch Package` is explicitly disallowed).
- **Missing mandatory behavior** is **context-dependent**: If the norm states "every Create Order must eventually Validate Order," but 2 Orders lack this, we must weigh:
  - **Abstraction mismatch**: The norm’s "directly-follows" assumption may oversimplify (e.g., unrecorded review events).
  - **Scope ambiguity**: Are all 2 Orders truly invalid, or is the norm’s scope incomplete?
- **Typical-pattern absence** (e.g., `Issue Invoice -> Write Off`) is **legitimate deviation** if the norm allows exceptions (e.g., credit notes).
- **Unregulated behavior** (e.g., `Reopen Order -> Close Order`) is **not a violation** unless the norm explicitly governs it.
- **Data-quality errors** (e.g., `Sensor Heartbeat` on Invoices) are **not process failures** but artifacts of identifier reuse.
- **Abstraction mismatches** arise when norms use "eventually" (e.g., `Create Order -> Validate Order`) but PM4Py enforces strict adjacency.

**Open-world vs. closed-world**:
- Closed-world: Only forbidden/mandatory edges are enforced *strictly*.
- Open-world: All other relations are **allowed but ungoverned**—no penalty unless the norm later clarifies them.

### **3. Detailed reasoning by model family**

#### **OC-DFG**
- **Established**: Directly-follows relations (e.g., `Create Order -> Validate Order`) with counts.
- **Unestablished**: Intermediate steps (e.g., unrecorded reviews) or scope ambiguities (e.g., "eventually").
- **Counts matter**: 98/100 `Create Order -> Validate Order` suggests compliance, but 2 missing Orders require **abstraction analysis**.
  - *Risk*: Treating "eventually" as "must" leads to false violations.
- **Forbidden violations** (e.g., `Cancel Order -> Dispatch Package`) are **directly detectable**.
- **Typical deviations** (e.g., `Validate Order -> Close Order` vs. `Issue Invoice`) are **allowed** if the norm permits exceptions.

#### **OTG**
- **Established**: Mandatory edges (e.g., `Order -> Item`, `Package -> Delivery`) with weights.
- **Unestablished**: Unspecified edges (e.g., `Order -> Customer`) or forbidden edges (e.g., `Order -> Payment cobirth`).
- **Weights reflect frequency**: 200 `Package -> Delivery` edges confirm compliance, but 7 `object_codeath` edges are **unregulated**.
- **Abstraction mismatch**: Norm requires `object_interaction` for `Dispatch Package`, but carrier references exist—**data-quality or process drift**.

#### **ET–OT**
- **Established**: Event-object mappings (e.g., `Dispatch Package -> Delivery`) with mandatory status.
- **Unestablished**: Unspecified events (e.g., `Manual Compliance Review`) or forbidden events (e.g., `Sensor Heartbeat`).
- **Counts align**: 92 `Record Payment -> Invoice` matches typical status, but 1 `Record Payment -> Payment` is **unapplied cash**.
- **Risk**: Event types like `Sensor Heartbeat` are **forbidden** but appear due to **data-quality errors**.

```python
import pm4py
from pm4py.objects.concept_object import *
from pm4py.objects.concept_object.variants import *

# Load observed log and normative models

}

    ("Order", "object_interaction", "Item", "mandatory"),
    # ... other normative OTG entries
]

    ("Create Order", "Order", "mandatory"),
    # ... other normative ET–OT entries
]

# Discover normative models
norm_ocdfg_graph = pm4py.discover_ocdfg(norm_ocdfg)
norm_otg_graph = pm4py.discover_otg(norm_otg)
norm_etot_graph = pm4py.discover_etot(norm_etot)

# Conformance checks (with status metadata)
oc_conformance = pm4py.conformance_ocdfg(
    ecel,
    norm_ocdfg_graph,
    metric=pm4py.metrics.conformance.sequence_conformance.SequenceConformanceMetric()
)
ot_conformance = pm4py.conformance_otg(
    ecel,
    norm_otg_graph,
    metric=pm4py.metrics.conformance.sequence_conformance.SequenceConformanceMetric()
)
et_conformance = pm4py.conformance_etot(
    ecel,
    norm_etot_graph,
    metric=pm4py.metrics.conformance.event_object_conformance.EventObjectConformanceMetric()
)

# Add semantic classification layer
def classify_conformance(oc_conformance, norm_ocdfg):
    for edge in oc_conformance:
        status = norm_ocdfg.get(edge["id"], {}).get("status", "unspecified")
        if edge["conformance"] == "violation":
            if status == "forbidden":
                yield {"type": "forbidden", "status": status}
            elif status == "mandatory" and edge["conformance"] == "missing":
                yield {"type": "missing_mandatory", "status": status}
        else:
            yield {"type": "typical" if status == "typical" else "unregulated", "status": status}

# Example usage:
for result in classify_conformance(oc_conformance, norm_ocdfg):
    print(result)
```

**Key**: Normative metadata must be **externalized** to PM4Py’s graph structures (e.g., via dictionaries) because PM4Py’s core functions do not preserve status labels.
