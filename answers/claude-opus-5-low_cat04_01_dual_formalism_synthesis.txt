# 1. Assumptions and Interpretation

1. **Event granularity.** Every activity label denotes a single recorded event at *completion* time. "X may start only after Y is complete" therefore becomes "the event X occurs after the event Y" in the trace. "Overlap" between two activities is consequently unobservable at the event level: it collapses into "either order is possible".
2. **"May overlap" = absence of an order constraint.** Because only completion events exist, true physical concurrency and "unordered" are indistinguishable in the language. I model overlap as *interleaving concurrency* (process-tree `+`, POWL unconnected nodes), which is exactly the set of all orderings. No trace is admitted or excluded by this choice that would not also be admitted/excluded by a partial-order-with-arbitrary-interleaving reading.
3. **Risk route.** The low/high risk data condition is *not* modelled as data. It is projected onto an exclusive control-flow choice: `XOR( 'Supervisor Review', AND('Quality Review','Regulatory Review') )`. Consequence: the model cannot express *which* cases are high risk; it only guarantees that exactly one of the two routes is executed, and that in the high-risk route both reviews occur in either order.
4. **Optional supplier consultation.** Represented as `XOR( 'Consult Supplier', tau )` — a silent skip branch. "At most once" is guaranteed because the XOR node is not inside any loop and is not duplicated. The data condition "supplier involved" is again abstracted into a non-deterministic choice.
5. **Inspection outcome abstraction.** `Inspect Trial` carries no pass/fail label. The outcome is projected onto the loop's exit decision: `LOOP( body = ('Execute Trial' -> 'Inspect Trial'), redo = 'Adjust Parameters' )`. Under pm4py loop semantics the body is executed, then *optionally* the redo child followed by the body again, and the loop always terminates with the body. Hence the last event of the loop is always `Inspect Trial`, and `Adjust Parameters` can never follow the passing (final) inspection. This is an *exact* encoding of requirement 8 — the "passing" inspection is by definition the last one.
6. **Duplicate visible labels: not permitted.** Every visible activity label appears exactly once in both models (the loop re-executes the *same* nodes; that is repetition, not duplication). This keeps alignment-based conformance checking and label-based frequency analysis unambiguous. I explicitly reject duplication-based approximation for the process tree (see 7) because duplicating `Consult Supplier` or the approval subtree would make "at most once" unenforceable and would corrupt any label-indexed analysis.
7. **Process-tree approximation policy: conservative under-approximation.** The dependency graph is non-block-structured (approvals and supplier consultation depend only on `Analyze Root Cause`, while `Execute Trial` depends on `Plan Verification` *and* `Design Corrective Action`). No process tree captures this exactly without duplication. I therefore *strengthen* the synchronisation: the whole `{Contain -> Plan Verification} || {Analyze -> Design}` block must complete before the approval / supplier / trial block starts. The resulting language is a strict **subset** of the intended language: the tree never admits a forbidden trace, but it forbids some legitimate ones (e.g. `Supervisor Review` or `Consult Supplier` occurring before `Plan Verification`). Under-approximation is preferred over over-approximation because the model is intended for compliance-style reasoning, where admitting unsafe behaviour is worse than rejecting safe behaviour — provided the rejection is documented, which it is here.
8. **POWL is intended to be exact.** All cross-branch dependencies of the narrative are expressible as edges of a strict partial order over a mix of atomic transitions and XOR/LOOP sub-models, so the POWL model is claimed to be language-equivalent to the intended specification.
9. **Start/end.** `Register Deviation` is the unique first event and `Archive Case` the unique last event in both models.
10. **Release synchronisation.** `Release Material` is preceded by the loop (thus by a passing `Inspect Trial`), by the selected approval route, and by the supplier XOR (whose silent branch imposes no visible obligation). `Archive Case` follows `Release Material`.

# 3. PM4Py Process-Tree Model

## 3.1 Compact expression

```
->(
   'Register Deviation',
   +(
      ->( 'Contain Material', 'Plan Verification' ),
      ->( 'Analyze Root Cause', 'Design Corrective Action' )
   ),
   +(
      X( 'Supervisor Review',
         +( 'Quality Review', 'Regulatory Review' ) ),
      X( 'Consult Supplier', tau ),
      *( ->( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' )
   ),
   'Release Material',
   'Archive Case'
)
```

Mapping to the narrative: the first `+` block is the two initial work streams with their private successors (D2–D7). The second `+` block groups the three obligations that must all be discharged before release — approval route (D9/D10), optional supplier consultation (D12), and the trial cycle (D17–D19) — leaving them mutually unordered so that approvals may interleave freely with the trial (D16). The sequential seam between the two `+` blocks is the deliberate over-synchronisation described in assumption 7.

## 3.2 Python code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def node(operator=None, label=None, parent=None):
    """Create a ProcessTree node and register it with its parent."""
    n = ProcessTree(operator=operator, label=label, parent=parent)
    if parent is not None:
        parent.children.append(n)
    return n


# root: sequence
tree = ProcessTree(operator=Operator.SEQUENCE)

node(label="Register Deviation", parent=tree)

# --- block 1: the two initial work streams -------------------------------
block1 = node(operator=Operator.PARALLEL, parent=tree)

stream_contain = node(operator=Operator.SEQUENCE, parent=block1)
node(label="Contain Material", parent=stream_contain)
node(label="Plan Verification", parent=stream_contain)

stream_analyze = node(operator=Operator.SEQUENCE, parent=block1)
node(label="Analyze Root Cause", parent=stream_analyze)
node(label="Design Corrective Action", parent=stream_analyze)

# --- block 2: approvals || optional supplier || trial loop ---------------
block2 = node(operator=Operator.PARALLEL, parent=tree)

risk_route = node(operator=Operator.XOR, parent=block2)
node(label="Supervisor Review", parent=risk_route)
high_risk = node(operator=Operator.PARALLEL, parent=risk_route)
node(label="Quality Review", parent=high_risk)
node(label="Regulatory Review", parent=high_risk)

supplier_opt = node(operator=Operator.XOR, parent=block2)
node(label="Consult Supplier", parent=supplier_opt)
node(label=None, parent=supplier_opt)          # tau: silent skip branch

trial_loop = node(operator=Operator.LOOP, parent=block2)
cycle = node(operator=Operator.SEQUENCE, parent=trial_loop)   # do-part
node(label="Execute Trial", parent=cycle)
node(label="Inspect Trial", parent=cycle)
node(label="Adjust Parameters", parent=trial_loop)            # redo-part

# --- tail ----------------------------------------------------------------
node(label="Release Material", parent=tree)
node(label="Archive Case", parent=tree)

# `tree` is the finished ProcessTree
print(tree)
```

Parent/child handling is explicit: every child is constructed with `parent=<its parent>` **and** appended to `parent.children`, so the structure is consistent in both directions (pm4py's `__repr__`, conversion and playout rely on `children`; alignment/reduction utilities rely on `parent`). Note that pm4py's `LOOP` takes exactly two children here: the do-part `->(Execute Trial, Inspect Trial)` and the redo-part `Adjust Parameters`; the third implicit exit is handled by the operator semantics.

## 3.3 What the tree cannot represent exactly

The tree is exact for: unique start/end, the two initial concurrent streams, the containment→planning and analysis→design precedences, the exclusive risk route with concurrent high-risk reviews, at-most-once optional consultation, the repeat-until trial cycle with the guarantee that `Adjust Parameters` never follows the last `Inspect Trial`, and the release/archive tail. It is **not** exact for the cross-branch dependencies of requirements 5, 6 and 7. Specifically: (a) `Supervisor Review` / `Quality Review` / `Regulatory Review` only require `Analyze Root Cause`, but the tree additionally requires `Contain Material`, `Plan Verification` and `Design Corrective Action`; (b) `Consult Supplier` only requires `Analyze Root Cause`, but the tree additionally requires the entire first block; (c) `Execute Trial` requires exactly `Plan Verification` and `Design Corrective Action`, which the tree enforces correctly, but only as a side effect of the same over-synchronised seam. All three deviations remove traces; none adds any. The tree language is therefore a proper subset of the intended language — a conservative under-approximation. Making it exact would require duplicating the approval subtree and the supplier choice into several branches (with data-inconsistent copies) or leaving the tree formalism altogether; both were rejected in assumption 6.

# 4. PM4Py POWL Model

## 4.1 Compact description

```
PO = StrictPartialOrder(nodes = {
        RD  = Register Deviation
        CM  = Contain Material
        ARC = Analyze Root Cause
        PV  = Plan Verification
        DCA = Design Corrective Action
        RISK = XOR( Supervisor Review ,
                    StrictPartialOrder({Quality Review, Regulatory Review})  # no edges -> concurrent
                  )
        SUP  = XOR( Consult Supplier , tau )
        TRIAL = LOOP( body = StrictPartialOrder({Execute Trial, Inspect Trial}, ET -> IT),
                      redo = Adjust Parameters )
        RM  = Release Material
        AC  = Archive Case
     })

edges:
  RD  -> CM      RD  -> ARC
  CM  -> PV      ARC -> DCA
  ARC -> RISK    ARC -> SUP
  PV  -> TRIAL   DCA -> TRIAL
  TRIAL -> RM    RISK -> RM     SUP -> RM
  RM  -> AC
```

## 4.2 Python code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# --- atomic transitions ---------------------------------------------------
RD  = Transition(label="Register Deviation")
CM  = Transition(label="Contain Material")
ARC = Transition(label="Analyze Root Cause")
PV  = Transition(label="Plan Verification")
DCA = Transition(label="Design Corrective Action")
SR  = Transition(label="Supervisor Review")
QR  = Transition(label="Quality Review")
RR  = Transition(label="Regulatory Review")
CS  = Transition(label="Consult Supplier")
ET  = Transition(label="Execute Trial")
IT  = Transition(label="Inspect Trial")
AP  = Transition(label="Adjust Parameters")
RM  = Transition(label="Release Material")
AC  = Transition(label="Archive Case")
skip = SilentTransition()

# --- high-risk branch: two concurrent reviews -----------------------------
high_risk = StrictPartialOrder(nodes=[QR, RR])          # deliberately no edge

# --- risk route: exclusive choice -----------------------------------------
RISK = OperatorPOWL(operator=Operator.XOR, children=[SR, high_risk])

# --- optional supplier consultation ---------------------------------------
SUP = OperatorPOWL(operator=Operator.XOR, children=[CS, skip])

# --- trial cycle: repeat-until --------------------------------------------
cycle = StrictPartialOrder(nodes=[ET, IT])
cycle.order.add_edge(ET, IT)
TRIAL = OperatorPOWL(operator=Operator.LOOP, children=[cycle, AP])

# --- root partial order ----------------------------------------------------
powl = StrictPartialOrder(nodes=[RD, CM, ARC, PV, DCA, RISK, SUP, TRIAL, RM, AC])

powl.order.add_edge(RD, CM)
powl.order.add_edge(RD, ARC)
powl.order.add_edge(CM, PV)
powl.order.add_edge(ARC, DCA)
powl.order.add_edge(ARC, RISK)
powl.order.add_edge(ARC, SUP)
powl.order.add_edge(PV, TRIAL)
powl.order.add_edge(DCA, TRIAL)
powl.order.add_edge(TRIAL, RM)
powl.order.add_edge(RISK, RM)
powl.order.add_edge(SUP, RM)
powl.order.add_edge(RM, AC)

print(powl)
```

## 4.3 Why the unconnected pairs may stay concurrent

* `CM` and `ARC`, and everything reachable only from one of them, are unordered because requirement 2 states the two streams proceed independently.
* `PV` and `DCA` belong to different streams; the narrative imposes no relation, so leaving them unordered is faithful (both orders and any interleaving are legal).
* `PV` and `RISK`/`SUP`, and `DCA` and `RISK`/`SUP`: the approvals and the consultation depend on `ARC` only. Any additional edge here would reproduce exactly the over-synchronisation that the process tree suffers from, so their absence is the point of the model.
* `RISK` and `TRIAL` are unordered because requirement 7 explicitly allows the approval route to overlap the trial cycle; both are nevertheless joined at `RM`.
* `SUP` and `TRIAL`, `SUP` and `RISK`: requirement 6 says consultation may overlap design, planning, approvals and trial work, and only constrains it to end before `RM` — captured by the single edge `SUP -> RM`.
* `QR` and `RR` inside `high_risk`: requirement 5 allows either completion order.
* No edge is needed from `RD` to the remaining nodes, or from any node to `AC`, because transitivity of the partial order already derives them (`RD -> CM -> PV -> TRIAL -> RM -> AC`, etc.). Every node is transitively between `RD` and `AC`, so start/end uniqueness holds.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams (CM, ARC) | Both after RD, mutually unordered | `+( ->(CM,PV), ->(ARC,DCA) )` — exact | Unconnected nodes with `RD ->` edges — exact | none | Containment and analysis teams work in parallel as intended. |
| Split into PV / DCA | PV after CM only; DCA after ARC only; PV ∥ DCA | Exact within block 1 | Exact via `CM->PV`, `ARC->DCA` | none | Correct in both. |
| Risk route | XOR of SR vs (QR ∥ RR), enabled after ARC | XOR/parallel structure exact, but enabling delayed until CM, PV, DCA are done | `ARC -> RISK` only — exact | Tree: **overconstrained** (enabling condition too strong) | Tree wrongly flags a compliant case where the supervisor signs off while verification planning is still running; false conformance violations, inflated "rework" statistics. |
| Overlap of approval and trial | Approvals unordered w.r.t. the trial cycle; both joined at RM | Exact — both are children of the same `+` | Exact — no edge between `RISK` and `TRIAL` | none | Both models correctly allow the trial to run while approvals are pending. |
| Optional supplier consultation | At most once, after ARC, before RM, otherwise free | `X(CS, tau)` — at-most-once exact; earliest start delayed to end of block 1 | `XOR(CS, tau)` with `ARC->SUP`, `SUP->RM` — exact | Tree: **overconstrained** on the start condition | Early supplier calls (a common and desirable practice) are reported as deviations by the tree. |
| Repeat-until trial cycle | (ET,IT)+ with AP strictly between cycles; never AP last | `*( ->(ET,IT), AP )` — exact | `LOOP(PO(ET->IT), AP)` — exact | none | Rework loops and the "no adjustment after pass" rule are enforced identically. |
| Release synchronisation | RM after passing IT **and** approval route **and** SUP | Enforced by the sequence seam after block 2 — exact | Three explicit incoming edges — exact | none | Release gate is correct in both; POWL states it as three independent obligations, which is easier to audit. |
| Duplicate-label risk | Each label once | No duplication; loop repeats the same nodes | No duplication | none | Frequency, throughput and alignment analyses remain label-unambiguous. Any duplication-based fix would have destroyed this. |
| Trial start (PV ∧ DCA) | ET after both PV and DCA | Enforced, but as a byproduct of over-synchronising the whole seam | Exactly two edges `PV->TRIAL`, `DCA->TRIAL` | none for this rule; the tree's mechanism causes collateral overconstraint elsewhere | Same verdicts on trial start, different verdicts on approvals/supplier. |

Neither model is *under*constrained: the process-tree language ⊂ POWL language = intended language (under the stated abstractions).

# 7. Preferred Representation and Validation Plan

**Canonical representation: the POWL model.** It expresses every cross-branch dependency directly as an edge of a strict partial order, it needs no duplication and no approximation, and it keeps the three release obligations (`TRIAL`, `RISK`, `SUP`) as independent, individually auditable arcs into `Release Material`. The process tree is retained as a secondary, deliberately conservative artefact — useful for tools that require block structure (tree-based discovery comparison, tree edit distance, hierarchical simplification) — with its under-approximation documented rather than hidden.

Validation plan:

1. **Conversion.** `net_t, im_t, fm_t = pm4py.convert_to_petri_net(tree)` and `net_p, im_p, fm_p = pm4py.convert_to_petri_net(powl)`. Successful conversion is *not* evidence of fidelity; it only makes the next steps possible. Inspect the POWL-derived net manually for the join structure at `Release Material` (three incoming silent arcs) and for the loop entry/exit silent transitions.
2. **Soundness.** `pm4py.check_soundness(net_t, im_t, fm_t, print_diagnostics=True)` and the same for the POWL net. The tree net must be sound by construction (block-structured); a failure there indicates a construction bug. For the POWL net, check specifically for the absence of deadlocks at the `RM` join and proper completion (single token in `fm`).
3. **Bounded / sampled playout.** `log = pm4py.play_out(net_p, im_p, fm_p, parameters={"maxTraceLength": 25, "noTraces": 5000})`. Compute the set of distinct variants; check invariants over all sampled traces: (i) first event is `Register Deviation`, last is `Archive Case`; (ii) `Adjust Parameters` is never the last event of the trial region and is always followed by `Execute Trial`; (iii) `Consult Supplier` occurs at most once and, if present, before `Release Material`; (iv) exactly one of `{Supervisor Review}` / `{Quality Review, Regulatory Review}` patterns occurs; (v) `#Execute Trial == #Inspect Trial == #Adjust Parameters + 1`. Because loop unrolling is unbounded, playout is a sample, not a proof.
4. **Explicit positive/negative tests.** Replay the eight witnesses of section 5 as a hand-built log using `pm4py.conformance_diagnostics_alignments(log, net, im, fm)` against both nets, and assert fitness `== 1.0` exactly for the intended-allowed traces (and for A5 assert the *expected* tree failure, so the approximation is pinned down by a regression test rather than by prose). For each negative trace, assert fitness `< 1.0` and inspect the alignment's first `>>` move — it should coincide with the "earliest violated condition" named in the table.
5. **Silent / duplicate-label check.** (a) Assert `len([t for t in net_p.transitions if t.label is None]) > 0` and that the τ-skip of `SUP` is genuinely bypassable: replay a trace without `Consult Supplier` (A1) and confirm fitness 1.0, i.e. the silent branch is reachable and does not consume a visible move. (b) Assert label uniqueness: `labels = [t.label for t in net.transitions if t.label]; assert len(labels) == len(set(labels))` — this fails immediately if any future refactor introduces duplicated visible labels, which would silently change alignment semantics.
6. **Language-inclusion smoke test.** Replay the tree-playout log against the POWL net and assert fitness 1.0 for every trace (evidence for tree-language ⊆ POWL-language), then replay the POWL-playout log against the tree net and *expect* some traces to fail — collecting them gives an empirical picture of exactly what the approximation costs.
7. **Limitations.** Playout is bounded and sampled, so it cannot prove language equivalence or the absence of exotic interleavings; step 6 gives one-sided evidence only. Alignment-based verdicts depend on the cost function and can mask a violation as a cheap model move. Conversion of POWL to Petri nets introduces silent transitions whose invisible choices may make some negative results harder to localise. Most fundamentally, no amount of control-flow validation can test the data abstractions (risk level, supplier involvement, inspection outcome): a trace with `Supervisor Review` on a genuinely high-risk case is accepted by both models and by every check above.

# 8. Final Self-Critique

1. **Semantic:** the models cannot distinguish a non-deterministic choice from a data-determined one. A high-risk case that only gets a `Supervisor Review` is control-flow-conformant in both models, so conformance checking against either artefact gives a false sense of regulatory assurance. A properly data-aware formalism (DPN, or POWL/tree plus decision mining and guards) is required for the actual compliance question, and I have only documented this gap, not closed it.
2. **Semantic/representational:** the process-tree under-approximation is asymmetric in an unquantified way. I claim the tree language is a proper subset of the intended language, but I only give one witness (A5) and an empirical smoke test (step 6) rather than a proof or a measured coverage figure; the true fraction of legitimate behaviour excluded could be large, which matters if the tree is ever used for discovery comparison or as a normative model.
3. **Modelling:** collapsing "overlap" to interleaved completion events erases genuine parallelism. Requirement 2's "may proceed independently and overlap" and requirement 7's overlap of approvals with the trial are, in this encoding, indistinguishable from strictly sequential execution — so any performance analysis (waiting time, resource contention, true cycle-time savings) built on these models will be misleading unless start events are added to the log and the formalism.
