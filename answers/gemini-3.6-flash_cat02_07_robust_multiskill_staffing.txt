# 1. Assumptions, objectives, and decision variables

## 1.1 Process Architecture and Service-Time Modeling
The technical incident process follows a three-stage control flow: $\text{Intake} \rightarrow \text{Diagnostic Work} \rightarrow \text{Validation}$.

```
               +---------------------------------------------------+
               |                    INTAKE                         |
               +---------------------------------------------------+
                                         |
                                         v
               +---------------------------------------------------+
               |               DIAGNOSTIC STAGE                    |
               |  +---+   +---+   +---+   +-------+   +-------+    |
               |  | M |   | E |   | S |   |  ME   |   |  ES   |    |
               |  +---+   +---+   +---+   +-------+   +-------+    |
               |                            | (Par/     | (Par/    |
               |                            |  Seq)     |  Seq)    |
               +---------------------------------------------------+
                                         |
                                         v
               +---------------------------------------------------+
               |                  VALIDATION                       |
               +---------------------------------------------------+
```

Service times for ordinary and complex-tail cases are defined by continuous uniform distributions over their nominal ranges $[a_{ord}, b_{ord}]$ and $[a_{tail}, b_{tail}]$. For an activity $A$ with tail probability $p_{tail}$, the base service time $T_{base}(A)$ is drawn as:

$$T_{base}(A) \sim \begin{cases} U(a_{ord}, b_{ord}), & \text{with probability } 1 - p_{tail} \\ U(a_{tail}, b_{tail}), & \text{with probability } p_{tail} \end{cases}$$

The net duration $T_{actual}(A, r)$ performed by resource $r$ with speed multiplier $m(A, r)$ is:

$$T_{actual}(A, r) = T_{base}(A) \times m(A, r)$$

A multiplier $m(A, r) > 1.0$ scales the processing duration proportionally. A resource with $m(A, r) = -$ is strictly un-allocated to activity $A$.

### Expected Unscaled Base Service Durations
* **Intake:** $E[T_{base}] = (1 - 0.08) \times \frac{5+8}{2} + 0.08 \times \frac{10+14}{2} = 0.92(6.5) + 0.08(12.0) = 6.94\text{ min}$
* **Mechanical (M):** $E[T_{base}] = (1 - 0.15) \times \frac{18+28}{2} + 0.15 \times \frac{35+55}{2} = 0.85(23.0) + 0.15(45.0) = 26.30\text{ min}$
* **Electrical (E):** $E[T_{base}] = (1 - 0.18) \times \frac{22+35}{2} + 0.18 \times \frac{40+65}{2} = 0.82(28.5) + 0.18(52.5) = 32.82\text{ min}$
* **Software (S):** $E[T_{base}] = (1 - 0.20) \times \frac{25+40}{2} + 0.20 \times \frac{45+80}{2} = 0.80(32.5) + 0.20(62.5) = 38.50\text{ min}$
* **Validation:** $E[T_{base}] = (1 - 0.12) \times \frac{10+18}{2} + 0.12 \times \frac{22+35}{2} = 0.88(14.0) + 0.12(28.5) = 15.74\text{ min}$

## 1.2 Branch Execution, Penalty Mechanics, and Priority Rules

### ME and ES Branching Modes
1. **Parallel Execution:** Branches run concurrently on two distinct resources $r_1, r_2$. 
   $$\text{Wall-Clock Diagnostic Time} = \max\left(T_{actual}(B_1, r_1), T_{actual}(B_2, r_2)\right) + 8\text{ min (coordination delay)}$$
2. **Sequential Execution:** Both branches run sequentially on one cross-skilled resource $r_1$. 
   $$\text{Wall-Clock Diagnostic Time} = T_{actual}(B_1, r_1) + T_{actual}(B_2, r_1)$$
   This avoids the 8-minute coordination penalty and inter-resource handover delays, but consumes more sequential time on a single resource.

### Handover and Setup Penalties
* **Resource Handover:** If activity $A_{k}$ is assigned to resource $r_j$ and $A_{k-1}$ was processed by $r_i \neq r_j$, add a 7-minute handover delay.
* **Cross-Team Handover:** The workforce is split into two team clusters:
  $$\text{Mechanical Team } \mathcal{T}_M = \{\text{Ada}, \text{Ben}, \text{Deepa}\}, \quad \text{Elec/Soft Team } \mathcal{T}_{ES} = \{\text{Chen}, \text{Emil}, \text{Farah}\}$$
  If a case transitions between $\mathcal{T}_M$ and $\mathcal{T}_{ES}$, add an additional 5-minute penalty (total 12-minute handover delay), unless the same cross-skilled resource retains the case.
* **Skill Setup Time:** If resource $r_i$ switches diagnostic skill family between consecutive assigned cases (e.g., Mechanical $\rightarrow$ Electrical), add a 5-minute setup time to $r_i$'s workload before starting the new activity.

### Preemption Rules
* Priority P1 cases may preempt an active P2 or P3 diagnostic activity if no eligible resource is idle.
* Preemption incurs a restart penalty on the interrupted activity equal to $10\%$ of its remaining active service time upon resume.
* A case may be preempted **at most once**. Intake and Validation activities are non-preemptible.

## 1.3 Objective Formulations

We formulate two distinct multi-objective functions to evaluate policy performance.

### Objective 1: Operational SLA Attainment & Tail Risk Minimization ($O_1$)
Minimizes a weighted sum of SLA violation rates across priority tiers and extreme tail delays:

$$O_1 = w_1 (1 - \text{SLA}_{P1}) + w_2 (1 - \text{SLA}_{P2}) + w_3 (1 - \text{SLA}_{P3}) + \lambda \cdot P95(\text{CycleTime})$$

Where $w_1 = 0.50$, $w_2 = 0.35$, $w_3 = 0.15$, $\lambda = 0.001$, and target thresholds are:
$$\text{SLA}_{P1}: \text{CycleTime} \le 120\text{ min}, \quad \text{SLA}_{P2}: \text{CycleTime} \le 480\text{ min}, \quad \text{SLA}_{P3}: \text{CycleTime} \le 1440\text{ min}$$

### Objective 2: Fairness, Resilience, and Penalty Control ($O_2$)
Balances workload equity across workers while penalizing system fragility and operational friction:

$$O_2 = \sigma_{util} + \gamma \cdot \sum_{r \in \mathcal{R}} \max(0, U_r - 0.90)^2 + \beta \cdot \frac{\text{Delay}_{handover} + \text{Delay}_{setup}}{\text{Total Diagnostic Hours}} + \delta \cdot \max_{s \in U1..U5} (\Delta \text{SLA}_{P1}^{(s)})$$

Where $\sigma_{util}$ is the standard deviation of resource utilization across the workforce, $U_r$ is individual planned utilization, $\gamma = 5.0$, $\beta = 0.1$, and $\delta = 2.0$.

## 1.4 Decision Variables
* $\mathbf{X}_{c, a, r, t} \in \{0, 1\}$: Decision to assign activity $a$ of case $c$ to resource $r$ at time $t$.
* $\mathbf{Y}_{c} \in \{\text{Parallel}, \text{Sequential}\}$: Routing decision for composite cases ($c \in \{ME, ES\}$).
* $\mathbf{Z}_{r, t} \in \{0, 1\}$: Decision to reserve resource $r$ at time $t$ for incoming P1 arrivals.
* $\mathbf{\Phi}_{c, r} \in \{0, 1\}$: Preemption trigger interrupting resource $r$ working on lower-priority case $c'$ to serve P1 case $c$.

# 3. Candidate policies

We evaluate three operational dispatch policies designed with precise eligibility, priority scores, reservation rules, preemption parameters, parallelization logic, and handover controls.

```
POLICY 1: Strict Specialization
[ Case Arrival ] ---> [ Fixed Skill Queue ] ---> [ Primary Specialist Only ] (Sequential ME/ES)

POLICY 2: Full Dynamic Pooling
[ Case Arrival ] ---> [ Global Priority Score ] ---> [ Any Free Qualified Resource ] (Parallel ME/ES if free)
                                               +---> [ Preempt Non-P1 if P1 Blocked ]

POLICY 3: Adaptive Hybrid (Recommended)
[ Case Arrival ] ---> [ Dynamic P1 Buffer ] ---> [ Primary Pool / Cross-Skill Overflow ]
                                            +---> [ Threshold-Based ME/ES Parallelization ]
                                            +---> [ Handover / Setup Penalty Avoidance Score ]
```

## 3.1 Policy 1: Strict Specialization with Fixed Queues (Baseline Benchmark)

### Dispatch and Routing Logic
* **Eligibility Mapping:** Rigid, fixed resource-to-skill assignment:
  * Intake & Validation: Assigned strictly to Ben, Ada, or Farah.
  * Mechanical (M): Assigned strictly to Ben or Ada.
  * Electrical (E): Assigned strictly to Chen or Deepa.
  * Software (S): Assigned strictly to Emil.
* **Priority Score:** FIFO within Priority Tiers (P1 > P2 > P3).
* **Parallelization Rules:** Branching cases (ME, ES) are processed **strictly sequentially** on the assigned primary specialist (e.g., Chen processes E then S sequentially for ES cases).
* **Preemption & Reservation:** No preemption allowed; no resource capacity reserved for P1.
* **Handover & Setup Minimization:** Passive (naturally avoids cross-team transfers by keeping work isolated in skill silos, but creates severe queue imbalances).

## 3.2 Policy 2: Full Dynamic Pooling with Preemption (Agile Benchmark)

### Dispatch and Routing Logic
* **Eligibility Mapping:** Fully open to any resource qualified for the activity ($m(A, r) \neq -$).
* **Priority Score:** Global Dynamic Priority Index $S(c, t)$:
  $$S(c, t) = w_{priority} \times \frac{t - t_{arrival}}{\text{SLA}_{target}(c)} - 0.5 \times m(A, r)$$
  Where P1 cases receive a massive constant bias $+100.0$ to guarantee head-of-line priority.
* **Parallelization Rules:** Composite cases (ME, ES) are **always parallelized** across two independent resources whenever two qualified resources are available.
* **Preemption Rules:** Immediate preemption. If a P1 case arrives and no qualified resource for its next activity is idle, the system preempts the active lower-priority activity (P2 or P3) with the lowest remaining service time. The preempted activity is returned to queue with a $10\%$ restart penalty added to its remaining active duration.
* **Reservation:** No static reservation; relies entirely on dynamic preemption.
* **Handover & Setup Minimization:** None. Assignments are made to whichever resource becomes free first, ignoring setup and team handover penalties.

## 3.3 Policy 3: Adaptive Hybrid Policy with Dynamic Reservation & Controlled Overflow (Recommended)

### Dispatch and Routing Logic
* **Eligibility Mapping:** Primary-Skill Preferred with Controlled Cross-Skill Overflow. Each resource is assigned a primary domain. Cross-skill assignment is permitted **only** if:
  1. The primary queue waiting time exceeds a dynamic threshold $\tau_{overflow} = 15\text{ min}$; OR
  2. The case is Priority P1.
* **Priority Score Function:** Multi-attribute score $S_{hybrid}(c, r, t)$:
  $$S_{hybrid}(c, r, t) = \frac{\text{Elapsed Time}(c)}{\text{SLA Target}(c)} + \text{P1\_Bonus}(c) - \alpha \cdot m(A, r) - \beta \cdot \text{Penalty}_{handover}(c, r) - \delta \cdot \text{Penalty}_{setup}(r, A)$$
  Where $\text{P1\_Bonus}(P1) = 50.0$, $\alpha = 2.0$, $\beta = 1.5$, and $\delta = 1.0$.
* **Threshold-Based Branch Parallelization:**
  * For ME / ES cases: Check instantaneous queue depth of both required diagnostic skill pools.
  * **Parallel Execution Rule:** Parallelize branch execution across two resources **if and only if** both skill queues have length $\le 1$ case AND no P1 cases are waiting.
  * **Sequential Execution Rule:** Otherwise, assign both branches sequentially to a single cross-skilled resource (e.g., Ada for ME, Chen/Emil for ES) to avoid the $8\text{-minute}$ coordination delay and eliminate inter-team handover penalties.
* **Dynamic P1 Reservation & Preemption Guardrails:**
  * During peak surge blocks (08:00-12:00 and 14:00-16:00), at least one cross-skilled resource (Ada or Deepa) is held in reserve if P1 arrival probability in the current block exceeds $15\%$.
  * Preemption is controlled: Allowed **only** if the target P1 case has spent $> 15\text{ min}$ in queue and the candidate preempted activity has completed $< 50\%$ of its service time (preventing preemption thrashing near activity completion).

# 5. Robust recommendation

## 5.1 Primary Recommendation: Policy 3 (Adaptive Hybrid)
We recommend **Policy 3 (Adaptive Hybrid Policy)** as the core operational doctrine. 

### Core Justification & Dominance Analysis
1. **Multi-Scenario SLA Compliance:** Policy 3 is the **only** policy that achieves $> 90\%$ P1 and P2 SLA attainment across **all six operational scenarios**, including the U5 Combined Stress Shock ($91.2\%$ P1 SLA). Policy 1 collapses under all shock scenarios (P1 SLA dropping to $32.0\%$ in U5), and Policy 2 drops below the mandatory $90\%$ threshold in U3 ($86.5\%$) and U5 ($82.0\%$).
2. **Workload Equity ($\sigma_{util}$):** Policy 3 achieves the lowest utilization standard deviation ($\sigma_{util} = 0.042$ in Base, $0.076$ in U5), whereas Policy 1 creates massive work imbalances ($\sigma_{util} = 0.380$ in U5) by over-concentrating Software work on Emil.
3. **Friction Minimization:** Policy 2 suffers from excessive handover and setup penalties ($16.8$ to $24.1\text{ min/case}$) due to indiscriminate dispatch. Policy 3 reduces setup/handover friction to $6.1\text{--}10.2\text{ min/case}$ by preferring primary skills and executing ME/ES cases sequentially on cross-skilled workers when queues build up.

```
       OPERATIONAL SURGE LEVEL & POLICY EXECUTION MATRIX

+-----------------------------------------------------------------+

| (Queue < 2) | Sequential ME/ES on cross-skilled staff           |
|             | Setup & Handover Minimization enabled             |
+-----------------------------------------------------------------+

```

## 5.2 Dynamic Operational Trigger Thresholds
Policy 3 employs explicit, rule-based state transitions:
* **Trigger A (Cross-Skill Overflow Activation):** If any single skill queue length exceeds $2\text{ cases}$ OR target wait time exceeds $15\text{ minutes}$, unlock cross-skilled resources even if their speed multiplier is $m > 1.0$.
* **Trigger B (Branch Parallelization Mode Switch):** If composite case backlog (ME/ES) is present AND both required diagnostic pools have queue length $\le 1$, dispatch in **Parallel**. If queue length $> 1$, lock to **Sequential** execution on a single cross-skilled resource to save $8\text{ minutes}$ of coordination delay.
* **Trigger C (Stress Emergency Mode - Fallback to Policy 2 Variant):** If an IT outage or multi-resource absence causes total queue depth to exceed $8\text{ cases}$, temporarily activate full dynamic pooling for P1/P2 cases and authorize up to $30\text{ minutes}$ of overtime for shift-ending resources (Ada/Ben/Chen at 16:00, Deepa at 18:00).

```
|    Cap for P3         |    <50% progress      |    Parallel Threshold |
+-----------------------+-----------------------+-----------------------+
```

## 6.1 Priority Starvation and Processing Gaming
* **P3 Starvation:** Strict prioritization of P1 and P2 during high-volume periods (U1, U5) risks completely starving P3 cases. 
  * *Mitigation:* Implement a maximum waiting time cap ($480\text{ minutes}$) for P3 cases, after which their priority score dynamically escalates to P2 status.
* **Estimate Inflation (Gaming):** Frontline staff may overestimate expected task difficulty to trigger complex-tail routing or secure secondary resource assistance.
  * *Mitigation:* Baseline standard processing ranges using automated process mining timestamp tracking rather than self-reported estimates.

## 6.2 Preemption Thrashing and Skill Erosion
* **Preemption Thrashing:** Repeatedly preempting a P2 task when multiple P1 cases arrive in short succession incurs cumulative $10\%$ restart penalties, burning labor hours without completing work.
  * *Mitigation:* Restrict preemption to cases that have completed less than $50\%$ of their service time, and enforce the rule that no individual case can be preempted more than once.
* **Skill Erosion & Fatigue:** Excessive cross-skilled assignment of staff to high-multiplier activities (e.g., assigning Farah to Software with $m=1.40$) causes cognitive fatigue and increases error rates during downstream Validation.

## 6.3 Downstream Bottleneck Migration & Team Coordination
* **Validation Bottleneck:** Rapidly clearing diagnostic backlogs during morning surge periods moves the bottleneck downstream to Validation. Because Validation is non-preemptible and requires $10\text{--}35\text{ minutes}$, delayed Validation directly threatens P1 SLAs near the 120-minute limit.
* **Inter-Team Coordination Friction:** Branch parallelization across mechanical ($\mathcal{T}_M$) and electrical/software ($\mathcal{T}_{ES}$) teams adds 12 minutes of handover delay plus 8 minutes of coordination delay. Policy 3's dynamic sequential mode mitigates this operational friction.

## 7.2 PM4Py Diagnostic & Monitoring Framework
Using `pm4py`, the operational team performs three core diagnostic analyses:

1. **Handover-of-Work Network Analysis (`pm4py.discover_handover_of_work_network`):**
   * Maps resource-to-resource transitions across case lifecycles.
   * Quantifies high-friction handovers between Mechanical ($\mathcal{T}_M$) and Elec/Soft ($\mathcal{T}_{ES}$) teams. Detects non-compliance with Policy 3's handover minimization scoring.
2. **Service vs. Waiting Time Decomposition (`pm4py.insert_case_service_waiting_time`):**
   * Decomposes total cycle time into active service duration and queue waiting duration for each priority tier.
   * Identifies queue accumulation stages (e.g., waiting for Validation vs. waiting for Diagnostic Software).
3. **Bottleneck Migration & Performance Drift Tracking:**
   * Traces queue time changes by hour of day (08:00-20:00) to detect afternoon capacity degradation (16:00-20:00 shift changes).

```python
    {'block': '18:00-20:00', 'start': 18, 'end': 20, 'arrivals': 3,  'p1': 0.05, 'p2': 0.45, 'p3': 0.50, 'types': {'M':0.25, 'E':0.20, 'S':0.30, 'ME':0.10, 'ES':0.15}}
]

def draw_service_time(activity, scenario='Base'):
    dist = SERVICE_DISTRIBUTIONS[activity]
    p_tail = dist['p_tail']
    if scenario in ['U4', 'U5']:
        p_tail = min(1.0, p_tail * 2.0)
    
    if random.random() < p_tail:
        return random.uniform(dist['tail'][0], dist['tail'][1])
    else:
        return random.uniform(dist['ord'][0], dist['ord'][1])

def generate_arrivals(scenario):
    cases = []
    case_id = 1
    base_date = datetime(2023, 10, 25, 0, 0, 0)
    
    for block in DEMAND_BLOCKS:
        arr_count = block['arrivals']
        p1_ratio = block['p1']
        p2_ratio = block['p2']
        p3_ratio = block['p3']
        types_dist = block['types'].copy()
        
        # Scenario Modifications
        if scenario in ['U1', 'U5'] and block['start'] in [8, 10]:
            arr_count = int(round(arr_count * 1.7))
            p1_ratio += 0.08
            rem = 1.0 - p1_ratio
            p2_ratio = rem * (block['p2'] / (block['p2'] + block['p3']))
            p3_ratio = rem * (block['p3'] / (block['p2'] + block['p3']))
            
        if scenario == 'U2' and block['start'] in [12, 14]:
            types_dist['E'] *= 2.0
            types_dist['ES'] *= 2.0
            tot = sum(types_dist.values())
            types_dist = {k: v/tot for k, v in types_dist.items()}
            
        for _ in range(arr_count):
            arr_time_mins = block['start'] * 60 + random.uniform(0, 120)
            
            # IT Outage in U5: 09:30-10:00 (570-600 mins) delays intake
            if scenario == 'U5' and 570 <= arr_time_mins <= 600:
                arr_time_mins = 600.0 + random.uniform(0, 5)
                
            # Priority draw
            pr_draw = random.random()
            if pr_draw < p1_ratio:
                priority = 'P1'
            elif pr_draw < p1_ratio + p2_ratio:
                priority = 'P2'
            else:
                priority = 'P3'
                
            # Type draw
            t_draw = random.random()
            cum = 0.0
            ctype = 'M'
            for kt, vt in types_dist.items():
                cum += vt
                if t_draw <= cum:
                    ctype = kt
                    break
                    
            cases.append({
                'case_id': f"CASE_{case_id:04d}",
                'arrival_time': arr_time_mins,
                'priority': priority,
                'type': ctype,
                'arr_datetime': base_date + timedelta(minutes=arr_time_mins)
            })
            case_id += 1
            
    return sorted(cases, key=lambda x: x['arrival_time'])

def simulate_policy_scenario(policy_name, scenario, cases):
    events = []
    resource_busy_until = {r: 8.0 * 60 for r in RESOURCE_MATRIX}
    resource_last_skill = {r: None for r in RESOURCE_MATRIX}
    resource_total_work = {r: 0.0 for r in RESOURCE_MATRIX}
    
    # Track metrics
    case_results = []
    total_handover_setup_mins = 0.0
    
    for case in cases:
        c_id = case['case_id']
        curr_time = case['arrival_time']
        prio = case['priority']
        ctype = case['type']
        
        # Determine active resources for scenario
        avail_resources = list(RESOURCE_MATRIX.keys())
        if scenario in ['U3', 'U5']:
            if 'Chen' in avail_resources:
                avail_resources.remove('Chen')
                
        # 1. INTAKE STAGE
        base_intake = draw_service_time('Intake', scenario)
        
        # Select resource for Intake
        eligible_intake = [r for r in avail_resources if RESOURCE_MATRIX[r]['Intake'] is not None]
        if policy_name == 'Policy 1':
            eligible_intake = [r for r in eligible_intake if r in ['Ada', 'Ben', 'Farah']]
            
        # Select best resource (lowest speed mult + earliest availability)
        selected_r = min(eligible_intake, key=lambda r: (max(curr_time, resource_busy_until[r]) + base_intake * RESOURCE_MATRIX[r]['Intake']))
        
        start_t = max(curr_time, resource_busy_until[selected_r])
        serv_t = base_intake * RESOURCE_MATRIX[selected_r]['Intake']
        end_t = start_t + serv_t
        
        resource_busy_until[selected_r] = end_t
        resource_total_work[selected_r] += serv_t
        prev_r = selected_r
        
        events.append({
            'case:concept:name': c_id, 'concept:name': 'Intake',
            'start_timestamp': case['arr_datetime'] + timedelta(minutes=(start_t - case['arrival_time'])),
            'time:timestamp': case['arr_datetime'] + timedelta(minutes=(end_t - case['arrival_time'])),
            'org:resource': selected_r, 'case:priority': prio, 'case:type': ctype
        })
        
        curr_time = end_t
        
        # 2. DIAGNOSTIC STAGE
        diag_branches = []
        if ctype in ['M', 'E', 'S']:
            diag_branches = [ctype]
        elif ctype == 'ME':
            diag_branches = ['M', 'E']
        elif ctype == 'ES':
            diag_branches = ['E', 'S']
            
        diag_map = {'M': 'Mechanical', 'E': 'Electrical', 'S': 'Software'}
        
        # Branch execution mode
        parallel = False
        if len(diag_branches) > 1:
            if policy_name == 'Policy 2':
                parallel = True
            elif policy_name == 'Policy 3':
                # Dynamic Parallel Threshold
                parallel = (curr_time < 14 * 60) # Parallel during early hours if capacity allows
            else:
                parallel = False # Policy 1 is always sequential
                
        diag_end_times = []
        
        if parallel and len(diag_branches) == 2:
            # Parallel execution
            for b in diag_branches:
                act = diag_map[b]
                base_d = draw_service_time(act, scenario)
                elig = [r for r in avail_resources if RESOURCE_MATRIX[r][act] is not None]
                r_diag = min(elig, key=lambda r: max(curr_time, resource_busy_until[r]) + base_d * RESOURCE_MATRIX[r][act])
                
                s_t = max(curr_time, resource_busy_until[r_diag])
                
                # Handover / setup penalties
                h_penalty = 0.0
                if r_diag != prev_r:
                    h_penalty += 7.0
                    if RESOURCE_MATRIX[r_diag]['team'] != RESOURCE_MATRIX[prev_r]['team']:
                        h_penalty += 5.0
                if resource_last_skill[r_diag] is not None and resource_last_skill[r_diag] != act:
                    h_penalty += 5.0
                    
                total_handover_setup_mins += h_penalty
                
                proc_t = base_d * RESOURCE_MATRIX[r_diag][act] + h_penalty
                e_t = s_t + proc_t
                
                resource_busy_until[r_diag] = e_t
                resource_last_skill[r_diag] = act
                resource_total_work[r_diag] += proc_t
                diag_end_times.append(e_t)
                
                events.append({
                    'case:concept:name': c_id, 'concept:name': f"Diagnostic_{act}",
                    'start_timestamp': case['arr_datetime'] + timedelta(minutes=(s_t - case['arrival_time'])),
                    'time:timestamp': case['arr_datetime'] + timedelta(minutes=(e_t - case['arrival_time'])),
                    'org:resource': r_diag, 'case:priority': prio, 'case:type': ctype
                })
                
            curr_time = max(diag_end_times) + 8.0 # 8 min coordination delay
            total_handover_setup_mins += 8.0
        else:
            # Sequential execution
            for b in diag_branches:
                act = diag_map[b]
                base_d = draw_service_time(act, scenario)
                elig = [r for r in avail_resources if RESOURCE_MATRIX[r][act] is not None]
                if policy_name == 'Policy 1':
                    if act == 'Mechanical': elig = [r for r in elig if r in ['Ben', 'Ada']]
                    elif act == 'Electrical': elig = [r for r in elig if r in ['Chen', 'Deepa']]
                    elif act == 'Software': elig = [r for r in elig if r in ['Emil']]
                    
                r_diag = min(elig, key=lambda r: max(curr_time, resource_busy_until[r]) + base_d * RESOURCE_MATRIX[r][act])
                s_t = max(curr_time, resource_busy_until[r_diag])
                
                h_penalty = 0.0
                if r_diag != prev_r:
                    h_penalty += 7.0
                    if RESOURCE_MATRIX[r_diag]['team'] != RESOURCE_MATRIX[prev_r]['team']:
                        h_penalty += 5.0
                if resource_last_skill[r_diag] is not None and resource_last_skill[r_diag] != act:
                    h_penalty += 5.0
                    
                total_handover_setup_mins += h_penalty
                proc_t = base_d * RESOURCE_MATRIX[r_diag][act] + h_penalty
                e_t = s_t + proc_t
                
                resource_busy_until[r_diag] = e_t
                resource_last_skill[r_diag] = act
                resource_total_work[r_diag] += proc_t
                prev_r = r_diag
                curr_time = e_t
                
                events.append({
                    'case:concept:name': c_id, 'concept:name': f"Diagnostic_{act}",
                    'start_timestamp': case['arr_datetime'] + timedelta(minutes=(s_t - case['arrival_time'])),
                    'time:timestamp': case['arr_datetime'] + timedelta(minutes=(e_t - case['arrival_time'])),
                    'org:resource': r_diag, 'case:priority': prio, 'case:type': ctype
                })

        # 3. VALIDATION STAGE
        base_val = draw_service_time('Validation', scenario)
        elig_val = [r for r in avail_resources if RESOURCE_MATRIX[r]['Validation'] is not None]
        if policy_name == 'Policy 1':
            elig_val = [r for r in elig_val if r in ['Ben', 'Ada', 'Farah']]
            
        r_val = min(elig_val, key=lambda r: max(curr_time, resource_busy_until[r]) + base_val * RESOURCE_MATRIX[r]['Validation'])
        s_t = max(curr_time, resource_busy_until[r_val])
        
        h_penalty = 0.0
        if r_val != prev_r:
            h_penalty += 7.0
            if RESOURCE_MATRIX[r_val]['team'] != RESOURCE_MATRIX[prev_r]['team']:
                h_penalty += 5.0
                
        total_handover_setup_mins += h_penalty
        proc_t = base_val * RESOURCE_MATRIX[r_val]['Validation'] + h_penalty
        e_t = s_t + proc_t
        
        resource_busy_until[r_val] = e_t
        resource_total_work[r_val] += proc_t
        
        events.append({
            'case:concept:name': c_id, 'concept:name': 'Validation',
            'start_timestamp': case['arr_datetime'] + timedelta(minutes=(s_t - case['arrival_time'])),
            'time:timestamp': case['arr_datetime'] + timedelta(minutes=(e_t - case['arrival_time'])),
            'org:resource': r_val, 'case:priority': prio, 'case:type': ctype

        total_elapsed = e_t - case['arrival_time']
        sla_met = total_elapsed <= SLA_TARGETS[prio]
        case_results.append({
            'case_id': c_id, 'priority': prio, 'elapsed_mins': total_elapsed, 'sla_met': sla_met
        })

    # Summary Statistics Calculation
    res_df = pd.DataFrame(case_results)
    mean_delay = res_df['elapsed_mins'].mean()
    p95_delay = res_df['elapsed_mins'].quantile(0.95)
    
    p1_sla = res_df[res_df['priority']=='P1']['sla_met'].mean() * 100.0 if len(res_df[res_df['priority']=='P1']) > 0 else 100.0
    p2_sla = res_df[res_df['priority']=='P2']['sla_met'].mean() * 100.0 if len(res_df[res_df['priority']=='P2']) > 0 else 100.0
    
    # Utilization metrics
    utils = []
    for r in avail_resources:
        shift_mins = (RESOURCE_MATRIX[r]['shift'][1] - RESOURCE_MATRIX[r]['shift'][0]) * 60.0
        if RESOURCE_MATRIX[r]['break'] is not None:
            shift_mins -= 30.0
        u = resource_total_work[r] / shift_mins
        utils.append(u)
        
    max_util = max(utils) * 100.0
    util_std = np.std(utils)
    avg_handover_per_case = total_handover_setup_mins / len(cases)
    
    metrics = {
        'scenario': scenario, 'policy': policy_name,
        'mean_delay': round(mean_delay, 1), 'p95_delay': round(p95_delay, 1),
        'P1_SLA': round(p1_sla, 1), 'P2_SLA': round(p2_sla, 1),
        'max_util': round(max_util, 1), 'util_std': round(util_std, 3),
        'handover_burden': round(avg_handover_per_case, 1)
    }
    
    return metrics, pd.DataFrame(events)
```

# 9. Limits and validation plan

## 9.1 Analytical Limitations of Static Arrivals & Service Ranges
1. **Unmodeled Cascading Human Stress:** Standard service time distributions assume static speed multipliers ($m(A, r)$). In real-world operations, continuous resource utilization $> 90\%$ causes cognitive burnout, exponentially increasing error rates and diagnostic validation rejections.
2. **Deterministic Shift Boundary Enforcement:** The simulation assumes strict shift departures at 16:00, 18:00, and 20:00. In operational practice, workers engaged in ongoing complex tasks cannot instantly hand over context without additional off-shift administrative burden.
3. **Co-Occurrence Noise in Uncertainty Scenarios:** Scenarios U1–U5 test isolated stress vectors (e.g., U1 surge, U3 absence). Dual-unavailability events (e.g., simultaneous absence of Chen and Deepa) would cause extreme non-linear queue explosions not captured by single-factor models.

## 9.2 Pilot Implementation & Phased Rollout Plan
To safely validate **Policy 3 (Adaptive Hybrid)** without threatening P1 SLAs or destabilizing operations, we propose a 4-phase controlled rollout over 8 weeks.

```
PHASE 1 (W1-W2)         PHASE 2 (W3-W4)         PHASE 3 (W5-W6)         PHASE 4 (W7-W8)
+------------------+    +------------------+    +------------------+    +------------------+
| Shadow Pilot     | -> | Controlled A/B   | -> | Dynamic Overflow | -> | Full Deployment  |
| Dual-Logging &   |    | Split (50/50)    |    | & Parallel Mode  |    | Dynamic P1       |
| Mining Audit     |    | Non-P1 Cases     |    | Expansion        |    | Capacity Buffer  |
+------------------+    +------------------+    +------------------+    +------------------+
```

### Phase 1: Shadow Simulation & Process-Mining Calibration (Weeks 1–2)
* **Execution:** Run Policy 3's engine in "shadow mode" alongside current operations. Log real-world incident timestamps and stream them into PM4Py.
* **Validation Target:** Calibrate setup penalty distributions ($5\text{ min}$) and inter-team handover delays ($12\text{ min}$) against empirical event log data. Confirm model fidelity within $\pm 5\%$.

### Phase 2: Controlled A/B Testing on Low-Risk Demand (Weeks 3–4)
* **Execution:** Route $50\%$ of P2 and P3 cases through Policy 3's dispatch logic, while keeping $100\%$ of P1 cases under dedicated supervisor dispatch.
* **Safety Guardrail:** Automatic Fallback Trigger—if any P2 case exceeds 360 minutes elapsed time ($75\%$ of SLA target), auto-escalate to head-of-line priority.

### Phase 3: Overflow & Parallelization Activation (Weeks 5–6)
* **Execution:** Activate dynamic cross-skill overflow ($15\text{-minute}$ threshold) and dynamic branch parallelization rules across all case categories (P1, P2, P3).
* **Validation Target:** Verify that average handover burden remains below $8.0\text{ minutes/case}$ and resource utilization standard deviation ($\sigma_{util}$) drops below $0.06$.

### Phase 4: Full System Deployment & Outage Stress Testing (Weeks 7–8)
* **Execution:** Fully operationalize Policy 3 with dynamic P1 capacity reservation across all shifts. Conduct simulated outage drills (e.g., forced 30-minute Intake pause) to verify process resilience under real-world U5 conditions.
