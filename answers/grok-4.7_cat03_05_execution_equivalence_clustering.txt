## 1. Equivalence design space

All four relations below are defined as kernels of total functions from an execution to a signature. Each is therefore reflexive, symmetric, and transitive. None of them treats a local identifier string as meaningful. Externality is meaningful: an identifier that begins with `EXT` is a flag, not a name. The eight logs are totally ordered as written. Same-time events are not present. Where a relation needs a total order, ties are broken by the lexicographic key `(timestamp, activity label, sorted tuple of (externality flag, object type))` after local identifiers have been replaced by first-seen ranks. That tie-break is a function, so it does not damage transitivity. A partial-order reading is the isomorphism of the corresponding labeled pomset; isomorphism is an equivalence as well. No execution pair in X1–X8 changes cluster under tie-break, because no timestamps are tied.

### Activity-sequence equivalence

Two executions are activity-sequence equivalent when the words formed by their activity labels, in timestamp order, are identical.

Preserved: the total order of labels and the repetition of labels. Discarded: object types, object counts, E2O incidence, O2O edges and qualifiers, externality, and every attribute. Consecutive `Add Item` steps stay as two letters because the relation does not stutter-reduce.

Same-time events are totalized by the tie-break above, using activity label only. Under the pomset variant, same-label events with equal timestamps commute, and the signature is a canonical encoding of that pomset.

On these executions the classes are AS-HAPPY = {X1, X2, X5, X6, X7}, AS-CONSOL = {X3}, AS-SPLITPAY = {X4}, AS-RETURN = {X8}. The label multiset induces the same four blocks: no two executions are anagrams of one another.

### Typed structural equivalence

An execution is a finite total order of events, an activity map, an E2O incidence (each event owns a set of objects), an object-type map, an externality flag, and a set of qualified O2O triples. Two executions are typed-structurally equivalent when there is a bijection of their objects that preserves type and externality, carries events in order onto events with the same activity and the same image incidence, and carries qualified O2O triples onto qualified O2O triples. Listing order inside one event is irrelevant because incidence is a set.

Preserved: activity order, repetition, typed E2O, per-type multiplicities, which objects are shared across events, externality, and qualifier vocabulary including `partially_settles`, `completes_settlement`, `replaces`, and `removed_before_dispatch`. Discarded: the spelling of local identifiers and any attributes that were never supplied (amounts, weights, carriers).

Same-time events are totalized by the full tie-break, which uses type and externality and therefore stays inside the isomorphism. Under the pomset variant, the bijection must be an order-embedding of the causal partial order. Either formulation is an equivalence.

Classes: TS-BASE = {X1, X2}, TS-CONSOL = {X3}, TS-SPLITPAY = {X4}, TS-COLOAD = {X5}, TS-JOINTINV = {X6}, TS-SUBST = {X7}, TS-RETURN = {X8}. X1 and X2 match because the swap of `I22` before `I21` is absorbed by the bijection. X7 does not match X1: its Dispatch event also carries an Item, and its O2O graph contains `replaces` and `removed_before_dispatch`.

### Qualified motif equivalence (preferred)

Two executions are motif-equivalent when the function `signature` in Section 2 returns the same 4-tuple `(logistics, finance, boundary, item_exception)`. The tuple is computed from multiplicities, the `EXT` flag, the presence of return activities, selected E2O patterns, and the O2O qualifier set. Concrete graph shape inside a class is discarded.

Preserved: shipment motif, settlement motif, cross-order sharing, and item-lifecycle exception. Discarded: local names, the order of the two `Add Item` events, interleaving of independent pack chains, redundant O2O that only restates E2O (`contains`, `packs`, `carries`, `bills`, `settles`), and the particular external identifier once its type and flag are known.

Same-time Pack events do not change cardinalities or qualifier presence, so the signature is invariant to those ties. The relation stays an equivalence because it is string equality on the tuple.

On X1–X8 the classes coincide with the typed-structural classes: SEM-BASE, SEM-CONSOL, SEM-SPLITPAY, SEM-COLOAD, SEM-JOINTINV, SEM-SUBST, SEM-RETURN, with the same members. Coincidence on a sample of eight is an empirical fact, not an identity of definitions. Typed structural equivalence always implies motif equivalence, because every feature of the tuple is isomorphism-invariant. The converse fails as soon as two non-isomorphic graphs share a motif, for example a consolidated delivery with two packages and another with three. Both would be SEM-CONSOL and would be distinct under typed structure.

### Customer-outcome equivalence (fourth relation)

The signature is `(drop_class, item_fate, billing_mode)` with `drop_class` in `{one, many}`, `item_fate` in `{as_ordered, substituted_or_removed, returned}`, and `billing_mode` in `{exclusive_single, installment, shared_invoice}`. Package count is discarded. External objects that only co-load a package are discarded. Return activities outrank a multi-delivery reading.

Preserved: whether the lead order’s own items move in one drop or several, whether those items are substituted or returned, and whether settlement is a single exclusive payment, an installment pair, or a shared invoice. Discarded: package cardinality, co-loading, event order, local names.

Same-time events do not change the three counts, so ties are irrelevant. The relation is an equivalence.

Classes: COE-ONEDROP = {X1, X2, X3, X5}, COE-INSTALL = {X4}, COE-JOINT = {X6}, COE-SUBST = {X7}, COE-RETURN = {X8}. This partition is coarser than motif equivalence and incomparable with activity-sequence equivalence: activity sequence separates X3 from X1 and merges X6 and X7 into AS-HAPPY, while customer-outcome does the opposite with those pairs.

## 2. Canonical signatures

The preferred signature is renaming-invariant and total. Local objects receive ranks in order of first appearance within each type. The `EXT` prefix is recorded before ranking and is never rewritten onto a local rank. Qualifier endpoints are rewritten through the same map so that qualifier comparison does not see raw names. Event-internal object lists are sorted after ranking.

```python
def signature(ex):
    rank, ext = {}, {}
    def canon(oid, otype):
        is_ext = oid.startswith("EXT")
        k = (is_ext, otype)
        ext[oid] = is_ext
        if oid not in rank:
            rank[oid] = sum(1 for x in rank if ext[x] == is_ext
                            and otype_of[x] == otype) + 1
        return (is_ext, otype, rank[oid])

    n = lambda pred: len({o for ev in ex.events for o in ev.oids if pred(o)})
    activities = [ev.activity for ev in ex.events]
    quals = {q for (q, a, b) in ex.o2o}
    n_pkg = n(lambda o: otype_of[o] == "Package")
    n_del = n(lambda o: otype_of[o] == "Delivery")
    n_pay = n(lambda o: otype_of[o] == "Payment")

    def ev_ext(ev, types):
        return any(oid.startswith("EXT") and otype_of[oid] in types
                   for oid in ev.oids)

    log_ext = any(ev_ext(ev, {"Order", "Item", "Package", "Delivery"})
                  for ev in ex.events if ev.activity in
                  {"Pack Package", "Dispatch", "Return Item"})
    fin_ext = any(ev_ext(ev, {"Order", "Invoice", "Payment"})
                  for ev in ex.events if ev.activity in
                  {"Issue Invoice", "Record Payment"})

    if "Return Item" in activities or "Inspect Return" in activities:
        logistics = "return-repack"
    elif n_pkg >= 2 and n_del >= 2:
        logistics = "split-delivery"
    elif n_pkg >= 2 and n_del == 1:
        logistics = "split-pack/one-delivery"
    elif n_pkg == 1 and n_del == 1:
        logistics = "single"
    else:
        logistics = f"other:{n_pkg}:{n_del}"

    if fin_ext:
        finance = "shared-invoice"
    elif n_pay >= 2 or "partially_settles" in quals:
        finance = "installment"
    elif n_pay == 1:
        finance = "full"
    else:
        finance = f"other-pay:{n_pay}"

    boundary = { (True, True): "shared-both",
                 (True, False): "shared-logistics",
                 (False, True): "shared-finance",
                 (False, False): "isolated" }[(log_ext, fin_ext)]

    item_on_dispatch = any(ev.activity == "Dispatch" and
        any(otype_of[o] == "Item" for o in ev.oids) for ev in ex.events)
    if "Return Item" in activities:
        item_exception = "return"
    elif ({"replaces", "removed_before_dispatch"} & quals) or item_on_dispatch:
        item_exception = "substitution"
    else:
        item_exception = "none"

    # ranks are computed so a caller can also emit an audit key
    for ev in ex.events:
        for oid in ev.oids:
            canon(oid, otype_of[oid])
    return (logistics, finance, boundary, item_exception)
```

`signature(X1) = signature(X2) = (single, full, isolated, none)`. The other six executions each produce a distinct tuple, listed in the table. An audit key may append the sequence of `(activity, sorted canonical incidence)` plus the sorted qualified triples on canonical endpoints. That audit key realizes typed structural equivalence and, on this sample, partitions the eight executions in the same way. The preferred relation uses only the 4-tuple.

## 4. Cluster interpretations

**SEM-BASE** — `(single, full, isolated, none)`. One isolated order gains two items, packs both into one package, hands that package to one delivery, issues one exclusive invoice, and records one settling payment. The commercial document matches the shipment, and the shipment matches what was added. The operational opportunity is straight-through processing: a single pick-pack wave, a single freight leg, a single cash-application step. The risk is low and local (pick accuracy inside one box). Order-level flattening looks harmless here and still misleads if the same rule is reused on the other classes. Item-level flattening represents this cluster poorly: the shared package, delivery, invoice, and payment are convergent, so each item-case duplicates Dispatch and Record Payment. The cluster is stable under local renaming, under swapping the two Add Item events, and under inserting O2O edges that merely restate the event incidence. It is stable under qualifier deletion because it has no qualifiers.

**SEM-CONSOL** — `(split-pack/one-delivery, full, isolated, none)`. Warehouse constraints put I31 and I32 into different packages, and outbound planning puts both packages on D31. The customer receives one drop. Freight can be consolidated; the pack bench cannot treat the order as one handling unit. Order-level flattening represents it poorly: the repeated Pack label looks like rework, and the many-to-one package–delivery incidence disappears. A repair that invents one delivery per package would move the execution into the split-delivery motif; that imputation is not licensed by the log. A repair that keeps both package objects is stable. Renaming is stable. Collapsing the two consecutive Pack events is stable only when their objects are unioned: the result still has two packages and one delivery. Dropping the second Pack event, and its package with it, destroys the cluster.

**SEM-SPLITPAY** — `(split-delivery, installment, isolated, none)`. P41 leaves on D41 before P42 exists; P42 then leaves on D42. Only after both dispatches does V41 appear, settled by M41 (`partially_settles`) and M42 (`completes_settlement`). Two mechanisms are present together: partial shipment, and installment cash application on an already complete shipment. With one execution, those mechanisms cannot be separated, so the cluster must not be narrated as “split shipment causes installments.” Risks are duplicated freight, a service promise measured on the last drop, and cash application that posts M41 as a full settlement and then treats M42 as an overpayment. The opportunity is an explicit ship-complete policy and an installment plan with amounts. Order-level flattening represents it poorly: pack/dispatch repetition looks like a generic loop, the one-to-one package–delivery pairing disappears, and the two qualifiers disappear, so the payments look like duplicates. The cluster is stable under renaming and under redundant O2O. It is sensitive to a repair that merges the two payment events into one amount attribute: logistics stay in the split-delivery class, and the finance coordinate flips from `installment` to `full`. Membership relative to the other seven executions is unchanged either way, because no other execution has two deliveries and no return.

**SEM-COLOAD** — `(single, full, shared-logistics, none)`. Around O5 the label word is the baseline word, and V51 bills only O5. P51 also packs EXT-IA, which belongs to EXT-OA, and D51 is a dispatch of both orders. Consolidation can save a freight leg. The risks are inventory ownership, co-mingled goods, privacy inside one box, and a service-level attribution that charges O5’s clock for another order’s item. Order-level flattening represents it poorly in both directions: dropping EXT-OA and EXT-IA yields a baseline trace, and copying Pack and Dispatch onto both orders double-counts the shipment. The cluster is stable under local renaming. It is unstable under a repair that deletes external objects or retypes EXT-IA as a third local item of O5. The first repair moves it to SEM-BASE; the second invents a three-item order that these data do not contain.

**SEM-JOINTINV** — `(single, shared-invoice, shared-finance, none)`. Logistics are the isolated single-package pattern. V61 bills O6 and EXT-OB, and M61 settles that invoice with no order-level allocation. Joint billing is legitimate when both orders share a buyer and a contract; the log does not say that they do. Until an allocation exists, revenue recognition, tax, receivables ownership, and credit memos have no order to land on. Invoice-level flattening represents it poorly: one case would mix the private logistics of two orders. Order-level flattening that drops EXT-OB represents it poorly in the other direction, by painting V61 as exclusive. The cluster is stable under local renaming and under logistics-side timestamp jitter. It collapses into SEM-BASE if EXT-OB is stripped. Imputing an allocation qualifier would keep the shared boundary and would change a finer finance label; the preferred tuple would still read `shared-invoice`.

**SEM-SUBST** — `(single, substitution, isolated, none)`. The activity word is the baseline word. Pack places I71 and I72 in P71. The qualifier `removed_before_dispatch` then links P71 to I71, `I72 replaces I71`, and Dispatch carries Item I72 together with P71. The box that leaves is not the box that was packed, and the invoice bills the order with no item-level correction. Risks are a customer receiving the substitute, a charge that still reflects I71, and a stock adjustment that never hits I71. There is no separate replacement event in the log, so none is assumed. Order-level flattening represents it poorly: the trace is indistinguishable from SEM-BASE, and both qualifiers are gone. This is the least stable semantic class under data repair. Deleting qualifiers while keeping the Item on Dispatch still yields `substitution` under the signature above. Deleting the Item incidence while keeping the qualifiers does the same. A cleaner that strips both, on the grounds that they look like baseline noise, moves X7 into SEM-BASE. Any compliance use of this cluster has to retain at least one of those two signals.

**SEM-RETURN** — `(return-repack, full, isolated, none)`. Both items leave on P81/D81. I82 comes back on that delivery, is inspected, is repacked into P82, and leaves again on D82. P82 replaces P81 for I82. I81 does not return. One exclusive invoice and one payment sit after the second dispatch, so billing in this log waits out the reverse leg. Risks are a second freight cost, a delayed invoice, and a return that is operationally a new outbound order. The opportunity is a disposition code at Inspect Return (restock versus reship) and a credit rule tied to I82 only. Order-level flattening represents it poorly: two pack/dispatch pairs look like the partial-shipment loop of X4, and the package-replacement edge is lost. Item-level flattening also represents it poorly: I81 and I82 become unrelated cases and the single invoice is duplicated. The cluster is stable while Return Item and Inspect Return remain. If those two events are filtered out as “exception noise,” the remnant has two packages and two deliveries and moves toward SEM-SPLITPAY, still with a single payment. The `replaces` edge on packages is a weak residue and should not be the only key.

## 5. Borderline cases

**X1 versus X2.** Activity-sequence, typed-structural, motif, and customer-outcome equivalence all put them together. The only defensible split is a key that embeds raw identifiers, under which `I11` and `I22` are different objects, or a key that treats “first identifier in the file” as a business priority. The second key is not supported by anything in the log: both added objects are ordinary items, and Pack is a set. Renaming-invariant structure is the right call. The pair is the regression test for a canonicalizer: after ranking, the audit keys must be equal.

**X1 versus X5.** Activity-sequence equivalence merges them. Typed structure and motif equivalence separate them, because Pack and Dispatch contain a second order and a third item, both external, while V51 stays exclusive to O5. Customer-outcome equivalence merges them again, because both local items travel in one drop and the invoice is exclusive; co-loading is intentionally discarded there. A projection that drops every `EXT` object also merges them, into TS-BASE as well as SEM-BASE. The two defensible business definitions are “what did O5’s buyer receive and pay?” (merge) and “whose goods rode in P51?” (split). Logistics costing and privacy need the split. A customer-tracking page can use the merge only if a side count still records co-loaded orders.

**X1 versus X6.** Activity-sequence equivalence merges them. A logistics-only motif merges them and separates X5. A finance-only motif does the opposite: X6 splits, X5 merges. Typed structure and the preferred 4-tuple split X6 from X1 because the invoice and the payment both carry EXT-OB and the settlement has no allocation. Customer-outcome equivalence also splits them, on `billing_mode = shared_invoice`. The disagreement is which boundary is allowed to change the class. A controller who groups “single drop, one box” will hide a revenue-allocation defect. A warehouse supervisor who groups “shared document” will mix an ordinary pack wave with a co-loaded one if X5 is the comparison point. The preferred tuple keeps both boundaries, so X5 and X6 land in different classes and neither lands in SEM-BASE.

**X1 versus X7.** Activity-sequence equivalence merges them. Multiplicity of object types also merges them: both have one order, two items, one package, one delivery, one invoice, one payment, and no external object. Typed structure separates them by the Dispatch–Item incidence and by the qualifiers. Motif equivalence separates them by `item_exception`. Customer-outcome equivalence separates them by `substituted_or_removed`. Two careful analysts can still disagree. One treats the qualifiers and the extra incidence as annotations on a standard fulfillment and reports one happy path. The other treats “packed contents” and “dispatched contents” as different sets and refuses to score X7 as fulfilled-as-ordered. The second reading is the one encoded in SEM-SUBST. The first reading is what a label-only or count-only dashboard will produce, and it is how a substitution ships without an alert.

**X3 versus X4.** Both have two packages and two local items, and both end with the invoice fully settled and every added item dispatched. A final-state reading therefore merges them with each other and with SEM-BASE. A package-count reading also merges X3 with X4 and leaves the baseline outside. Delivery cardinality separates them: one drop versus two. Payment cardinality and the partial/complete qualifiers separate them again. Activity sequence separates them by the word, including the Pack–Dispatch interleaving. A pomset reading that lets independent pack→dispatch chains commute would still separate them, because X3 has one delivery event carrying both packages and X4 has two delivery objects. The interleaving in X4 is one linearization of two chains; it is also consistent with a real precedence (the second item is packed only after the first has left). The log does not say which, so the preferred signature uses delivery cardinality and payment cardinality and does not encode the interleaving. The remaining disagreement is the final-state merge. It is defensible for a “eventually complete” KPI and a poor guide for freight or cash application, which feel every extra drop and every partial posting.

**X4 versus X8.** Both have two packages and two deliveries, so a multi-drop KPI merges them. They diverge on activities (Return Item, Inspect Return), on payment count (two versus one), and on the meaning of the second package: a later partial shipment of a not-yet-packed item, versus a repack of an item that already left and came back. Flattening both to an order-level loop makes the disagreement worse, because both become “Pack and Dispatch happened twice.” A definition based on object counts of Package and Delivery merges them. A definition based on lifecycle motif splits them, which is what SEM-RETURN versus SEM-SPLITPAY records. The split is the operationally serious one: X4 is forward logistics plus installment cash, X8 is reverse logistics plus a second outbound leg, and the staffing, the SLA clock, and the revenue timing differ.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel(ocel, object_type, max_objs=...)` returns a dictionary from an exact lifecycle key to the list of lead-object identifiers that produced it. For each object of the lead type the routine explores the connected event–object neighborhood, stopping at `max_objs` objects, and serializes the ordered activities in that neighborhood together with the typed incidence of those events. The member lists hold raw identifiers. O2O qualifiers and numeric attributes are outside the key unless someone has already copied them into activities or into dummy object types. Two isomorphic orders therefore share a key only when the serializer abstracts object identity. A serializer that writes the raw related-object column into the key makes every order its own cluster: I11 versus I21 is enough. That partition is an identity index. It is too fine for segmentation, reporting, and any compliance rule whose statement is stable under renaming.

Canonicalization should be applied to the members, not by string-editing the raw key. For each lead order, rebuild the Section 2 signature (and, when an audit key is required, the ranked incidence string) on a copy of its neighborhood in which local objects are ranked by first appearance per type and `EXT` is preserved as a flag. Union the member lists that share the new signature. Raw PM4Py blocks may be merged by that step. They should be split only when the raw key ignored a qualifier the audit key is required to see, as with a qualifier-only encoding of X7.

Exact typed equivalence, after that canonicalization, is the right tool when any extra incidence is itself a finding: an Item on Dispatch, a second Order on Issue Invoice, a connected external item inside a package. It is also the right regression check that an extractor still maps X1 and X2 together. It is a poor daily segmenter once legitimate multiplicity variants exist (two versus three packages on one delivery) and once shared invoices or shared containers glue unrelated orders into one component.

`max_objs` makes the key a property of a truncated exploration. These eight neighborhoods are small — between seven and ten objects — so a cap of 16 covers the direct neighborhood of every lead order. The same cap fails as soon as exploration is transitive through EXT-OA or through a shared invoice: the external order’s private events enter the key, two orders with the same local motif diverge because their siblings differ, and a hub customer or a hub container produces a component that hits the cap. Truncation then depends on walk order. Two equivalent orders can receive different prefixes, and an order can lose its payment or its second package and collide with SEM-BASE. Practical use is a depth limit of one event–object step around the lead order, with `max_objs` set just above that neighborhood, so external endpoints are visible as flags and their private downstream lifecycles stay outside the key.

```python
import pm4py
from collections import defaultdict

LEAD = "Order"
raw = pm4py.cluster_equivalent_ocel(ocel, LEAD, max_objs=16)

motif_clusters = defaultdict(list)
audit_clusters = defaultdict(list)
for _raw_key, order_ids in raw.items():
    for oid in order_ids:
        neigh = neighborhood(ocel, oid, depth=1)  # events at distance <= 1
        motif_clusters[signature(neigh)].append(oid)
        audit_clusters[ranked_incidence_key(neigh)].append(oid)

# motif_clusters: operational segments, renaming-invariant
# audit_clusters: typed structure, still renaming-invariant,
# and sensitive to Dispatch–Item incidence even if o2o was dropped
```

`neighborhood` must keep objects whose identifiers start with `EXT` and must not follow those objects into events that do not also involve the lead order. `ranked_incidence_key` is the audit key of Section 2.

## 7. Robustness analysis

**Ignore all O2O qualifiers.** No pair among X1–X8 merges. X7 remains SEM-SUBST because Dispatch still carries an Item. X4 remains an installment because two Payment objects remain, both on V41. X8 remains a return because Return Item and Inspect Return remain; the package-level `replaces` edge is redundant with those activities. The assignment table is unchanged, and the reason for X7 changes: incidence carries the class without the qualifier. The dangerous nearby case is not in the file. If Item were removed from X7’s Dispatch and only `removed_before_dispatch` were left, a qualifier-blind key would move X7 into SEM-BASE and into TS-BASE. Compliance monitoring cannot treat qualifier deletion as a harmless cleanup.

**Ignore external objects.** Delete every object whose identifier starts with `EXT`, and delete O2O triples that mention them. X5’s Pack and Dispatch become a two-item, one-package, one-delivery execution with an exclusive invoice, and X5 joins SEM-BASE and TS-BASE. X6’s Issue Invoice and Record Payment likewise become exclusive, and X6 joins SEM-BASE and TS-BASE. Activity-sequence labels were already shared, so AS-HAPPY is unchanged. Customer-outcome already contained X5; after this deletion X6 joins COE-ONEDROP as well, leaving only X4, X7, and X8 outside. Shared logistics and shared finance are exactly the facts this perturbation erases. A pipeline that “scopes the case to the lead order” by dropping `EXT` will report three cross-order executions as ordinary fulfilled orders.

**Collapse repeated same-label events.** Read as stuttering reduction of consecutive equal labels, with objects unioned onto the surviving event. Every execution begins with two consecutive Add Item events, so every activity word loses one Add Item and relative class boundaries do not move from that fact alone. X3 also has two consecutive Pack events. After stuttering, its activity word equals the shortened AS-HAPPY word, so X3 joins AS-HAPPY. Its object union still contains two packages and one delivery, so SEM-CONSOL and TS-CONSOL survive. X4’s two Record Payment events are consecutive. The activity word loses one payment letter and stays unique because Pack and Dispatch still alternate twice. Union keeps two Payment objects, so the motif stays `(split-delivery, installment, isolated, none)`. X8 has no consecutive repeated label. A stronger rule that discards the second event’s objects, rather than unioning them, is a different perturbation: X3 can lose P32 and fall into SEM-BASE. Union and deletion must not be given the same name.

**Treat Pack and Dispatch order as a partial order.** Take each package’s Pack before its own Dispatch as causal, and treat distinct packages’ chains as concurrent, while Invoice stays after every Dispatch that the total order places before it. Cardinalities, externality, and qualifiers are unchanged, so every SEM class and every TS class on this sample is unchanged: X3 still has one delivery and X4 still has two, and those pomsets are not isomorphic. Activity words that differed only by interleaving would merge; no such pair is in the file. The interleaving of X4 would become equivalent to an unobserved batch recording that packs both packages before either dispatch, provided each chain’s own order and the two delivery objects stay. That merge is not a merge with X3. X8 does not join X4: Return Item and Inspect Return sit on the second chain and are different labels, so the pomset stays different. Partial order is the wrong place to look for instability in this sample. Multiplicity and reverse-logistics labels dominate.

**Treat payment multiplicity as an amount attribute.** Replace X4’s two Record Payment events by one event whose amount is the sum and whose status is “completed,” and drop `partially_settles` / `completes_settlement`. The finance coordinate of X4 flips from `installment` to `full`. The logistics coordinate stays `split-delivery`, so the execution remains a class by itself, now signed `(split-delivery, full, isolated, none)`. It still does not meet X3, which has one delivery, or X8, which has a return. What changes is the story of the class: the log no longer supports an installment finding, and a later single-payment split shipment would share the class. Activity sequence also changes, because one payment label disappears, and the shortened word is still unique. SEM-BASE, SEM-COLOAD, SEM-JOINTINV, and SEM-SUBST are untouched: each already has a single payment.

Taken together, the preferred partition is stable under qualifier deletion and under pack/dispatch partialization, on these eight executions. It is not stable under deletion of external objects (X5 and X6 disappear into the baseline) or under a cleaner that strips both the qualifier and the Dispatch–Item link on X7. Activity-sequence classes move as soon as consecutive Pack events are stutter-reduced. The finest raw-identifier partition moves under every renaming, including the harmless X1/X2 rename.

## 8. Limitations and recommendation

Eight hand-built executions, each deviant motif appearing once, cannot support frequencies, and they cannot unconfound X4. Split delivery and installment settlement co-occur in that single log. A recommendation that speaks of “the partial-shipment cluster” as a cause would over-claim. Qualifiers arrive as notes, not as a guaranteed OCEL table. Amounts are absent, so payment count is only a proxy for installments. No timestamps are tied. The executions are already centered on the lead order; a full log would also contain the private events of EXT-OA and EXT-OB, which a transitive cluster key would swallow.

Use typed structural equivalence, including O2O qualifiers and externality, for compliance monitoring. A shared invoice, a co-loaded external item, and a removal before dispatch are findings even when the activity word is the happy path. The audit key keeps the evidence, not only a motif label. Exactness after identifier ranking is what an audit can reproduce; exactness before ranking collapses to one cluster per order and reproduces nothing.

Use qualified motif equivalence for operational segmentation. Pick-pack, freight, cash application, and returns staffing follow the four coordinates. A two-package consolidation and a three-package consolidation can share a work queue without being isomorphic, which is the gap between SEM-CONSOL and typed structure once real volume appears. On this sample the two partitions match, so the choice is about the next orders, not about X1–X8.

Use typed structural equivalence, stratified by the motif factors, for root-cause analysis. The residue inside SEM-SUBST is the actual edge `removed_before_dispatch` and the Dispatch–Item link; the class label alone cannot distinguish removal from replacement once both occur in the wild. The same discipline splits the X4 conjunction: delivery cardinality and payment cardinality are separate covariates. An opaque cluster identifier, however fine, is a bad cause variable when one block binds two mechanisms.

Use customer-outcome equivalence for descriptive reporting. The question on that page is whether the buyer had one drop, received the items as ordered, and settled an exclusive invoice. Under that question X1, X2, and X3 belong together, and X7 and X8 and X6 do not. The page will hide co-loading (X5 sits inside COE-ONEDROP) and will hide package count. Those facts belong on the operational page.

No single relation serves all four purposes. On these executions the partitions already disagree: activity sequence has four blocks, customer-outcome has five, and motif and typed structure have seven and coincide. Raw identifiers would make eight singletons. Activity sequence hides the substitution and the shared invoice inside AS-HAPPY, which is unacceptable for compliance, and it separates X3 from X1, which a customer report has little reason to do. Customer-outcome hides co-loading and package splits, which operations and compliance both have to see. Motif equivalence is the right queue design and is coarser than the evidence a root-cause review needs once two graphs share a label. Typed structure preserves that evidence and will over-split as soon as ordinary multiplicity varies. The useful practice is to compute the ranked structural key, derive the motif tuple from it, and publish the coarser customer-outcome rollup beside the activity word, with the co-load and substitution counts that the rollup hides written on the same page.
