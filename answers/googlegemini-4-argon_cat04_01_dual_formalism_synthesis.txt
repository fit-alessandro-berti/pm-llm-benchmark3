# 1. Assumptions and Interpretation

1. **Risk Route Representation**: The data-driven decision between low-risk and high-risk routes after `Analyze Root Cause` is modeled as a non-deterministic exclusive choice (`Operator.XOR`). The low-risk branch executes `Supervisor Review`. The high-risk branch executes a concurrent composition of `Quality Review` and `Regulatory Review`, permitting completion in either order.
2. **Optional Supplier Consultation**: The optionality of `Consult Supplier` (occurring 0 or 1 times) is modeled as an exclusive choice (`Operator.XOR`) between the visible transition `Consult Supplier` and a silent skip transition (`tau`). Because data conditions are omitted, this choice is resolved non-deterministically after `Analyze Root Cause` completes.
3. **Abstraction of Passing vs. Failing Inspection**: Because inspection outcomes are not distinct event labels, the trial cycle is modeled using a loop operator (`Operator.LOOP`) where the *do*-body is the sequence `Execute Trial -> Inspect Trial`, and the *redo*-body is `Adjust Parameters`. Under standard PM4Py loop semantics, the *do*-body executes first, followed by zero or more iterations of `(redo, do)`. The final execution of `Inspect Trial` before exiting the loop implicitly represents the passing inspection; any prior execution of `Inspect Trial` followed by `Adjust Parameters` represents a failing inspection. This guarantees that `Adjust Parameters` never occurs after the final (passing) inspection.
4. **Duplicate Visible Labels Policy**: Duplicate visible activity labels are strictly prohibited in both models (`unique label assumption`). While duplicating subtrees could allow a Process Tree to mimic some cross-branch dependencies via enumerating state spaces, it breaks the 1-to-1 mapping between model transitions and business activities, degrades process mining fitness/precision diagnostics, and leads to combinatorial explosion.
5. **Process Tree Approximation Policy**: We adopt a **conservative under-approximation** policy for the Process Tree. The narrative specifies an irreducible non-block-structured DAG (an N-pattern / cross-synchronization): `Contain Material -> Plan Verification` runs in parallel with `Analyze Root Cause -> (Design Corrective Action || Approvals || Consult Supplier)`, and `Execute Trial` synchronizes `Plan Verification` and `Design Corrective Action` while letting `Approvals` and `Consult Supplier` continue concurrently until `Release Material`. Because a Process Tree cannot synchronize a subset of parallel branches mid-stream without synchronizing all of them, the Process Tree forces `Contain Material` and `Analyze Root Cause` to synchronize *before* `Plan Verification`, `Design Corrective Action`, `Approvals`, and `Consult Supplier` begin. It preserves the overlap between `Approvals`, `Consult Supplier`, and the `Trial Loop`, sacrificing only the early start of `Plan Verification` (before `Analyze Root Cause` finishes) and the early start of `Design Corrective Action`/`Approvals`/`Consult Supplier` (before `Contain Material` finishes).
6. **Concurrency vs. Interleaving Interpretation**: Phrases such as "may overlap" and "proceed independently" are interpreted as true concurrency in the structural model (partial-order independence in POWL, `Operator.PARALLEL` in Process Trees), which yields interleaved completion sequences in the recorded event logs (since events are atomic completion timestamps).

# 3. PM4Py Process-Tree Model

### 1. Compact Process-Tree Expression
```text
->(
  'Register Deviation',
  +(
    'Contain Material',
    'Analyze Root Cause'
  ),
  +(
    ->(
      +(
        'Plan Verification',
        'Design Corrective Action'
      ),
      *(
        ->(
          'Execute Trial',
          'Inspect Trial'
        ),
        'Adjust Parameters'
      )
    ),
    X(
      'Supervisor Review',
      +(
        'Quality Review',
        'Regulatory Review'
      )
    ),
    X(
      'Consult Supplier',
      tau
    )
  ),
  'Release Material',
  'Archive Case'
)
```

### 2. Self-Contained Python Construction Code
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator
import pm4py

# Root sequence: Register -> Initial Parallel -> Main Parallel -> Release -> Archive
tree = ProcessTree(operator=Operator.SEQUENCE)

t_register = ProcessTree(label="Register Deviation", parent=tree)
op_init_par = ProcessTree(operator=Operator.PARALLEL, parent=tree)
op_main_par = ProcessTree(operator=Operator.PARALLEL, parent=tree)
t_release = ProcessTree(label="Release Material", parent=tree)
t_archive = ProcessTree(label="Archive Case", parent=tree)

tree.children.extend([t_register, op_init_par, op_main_par, t_release, t_archive])

# 1. Initial Parallel Block: Contain Material || Analyze Root Cause
t_contain = ProcessTree(label="Contain Material", parent=op_init_par)
t_analyze = ProcessTree(label="Analyze Root Cause", parent=op_init_par)
op_init_par.children.extend([t_contain, t_analyze])

# 2. Main Parallel Block: (Plan/Design -> Trial Loop) || Approvals || Optional Supplier
seq_work_trial = ProcessTree(operator=Operator.SEQUENCE, parent=op_main_par)
xor_approval = ProcessTree(operator=Operator.XOR, parent=op_main_par)
xor_supplier = ProcessTree(operator=Operator.XOR, parent=op_main_par)
op_main_par.children.extend([seq_work_trial, xor_approval, xor_supplier])

# 2a. Work and Trial Sequence: (Plan Verification || Design Corrective Action) -> Trial Loop
par_prep = ProcessTree(operator=Operator.PARALLEL, parent=seq_work_trial)
loop_trial = ProcessTree(operator=Operator.LOOP, parent=seq_work_trial)
seq_work_trial.children.extend([par_prep, loop_trial])

t_plan = ProcessTree(label="Plan Verification", parent=par_prep)
t_design = ProcessTree(label="Design Corrective Action", parent=par_prep)
par_prep.children.extend([t_plan, t_design])

# Trial Loop: do (Execute Trial -> Inspect Trial), redo (Adjust Parameters)
seq_do_trial = ProcessTree(operator=Operator.SEQUENCE, parent=loop_trial)
t_adjust = ProcessTree(label="Adjust Parameters", parent=loop_trial)
loop_trial.children.extend([seq_do_trial, t_adjust])

t_exec = ProcessTree(label="Execute Trial", parent=seq_do_trial)
t_insp = ProcessTree(label="Inspect Trial", parent=seq_do_trial)
seq_do_trial.children.extend([t_exec, t_insp])

# 2b. Approval XOR: Supervisor Review XOR (Quality Review || Regulatory Review)
t_sup = ProcessTree(label="Supervisor Review", parent=xor_approval)
par_high_risk = ProcessTree(operator=Operator.PARALLEL, parent=xor_approval)
xor_approval.children.extend([t_sup, par_high_risk])

t_qual = ProcessTree(label="Quality Review", parent=par_high_risk)
t_reg = ProcessTree(label="Regulatory Review", parent=par_high_risk)
par_high_risk.children.extend([t_qual, t_reg])

# 2c. Optional Supplier XOR: Consult Supplier XOR tau
t_supp = ProcessTree(label="Consult Supplier", parent=xor_supplier)
t_tau = ProcessTree(label=None, parent=xor_supplier)
xor_supplier.children.extend([t_supp, t_tau])
```

### 3. Representational Loss and Approximation Analysis
Because Process Trees are strictly block-structured (series-parallel graphs), they cannot exactly represent the cross-branch synchronization (N-pattern/M-pattern) inherent in requirements **D3**, **D4**, **D5**, **D8**, and **D9**. Specifically, in the intended process, `Plan Verification` depends *only* on `Contain Material`, while `Design Corrective Action`, `Approvals`, and `Consult Supplier` depend *only* on `Analyze Root Cause`, yet `Execute Trial` synchronizes `Plan Verification` and `Design Corrective Action` without synchronizing `Approvals` or `Consult Supplier`. In our conservative under-approximation `tree`, the parallel block `+(Contain Material, Analyze Root Cause)` must close before the next block begins. This introduces two artificial precedence constraints (overconstraints):
1. `Plan Verification` cannot start until `Analyze Root Cause` is also complete (even if `Contain Material` finished early).
2. `Design Corrective Action`, `Supervisor/Quality/Regulatory Review`, and `Consult Supplier` cannot start until `Contain Material` is also complete (even if `Analyze Root Cause` finished early).
All downstream concurrency—such as approvals and supplier consultation overlapping with verification planning, corrective action design, and the trial loop—is preserved exactly.

# 4. PM4Py POWL Model

### 1. Compact POWL Description
```text
StrictPartialOrder(
  nodes = {
    t_reg:      'Register Deviation',
    t_contain:  'Contain Material',
    t_analyze:  'Analyze Root Cause',
    t_plan:     'Plan Verification',
    t_design:   'Design Corrective Action',
    xor_app:    X('Supervisor Review', PO({'Quality Review', 'Regulatory Review'}, edges={})),
    xor_supp:   X('Consult Supplier', tau),
    loop_trial: *(PO({'Execute Trial', 'Inspect Trial'}, edges={'Execute Trial' -> 'Inspect Trial'}), 'Adjust Parameters'),
    t_release:  'Release Material',
    t_archive:  'Archive Case'
  },
  edges = {
    t_reg      -> t_contain,
    t_reg      -> t_analyze,
    t_contain  -> t_plan,
    t_analyze  -> t_design,
    t_analyze  -> xor_app,
    t_analyze  -> xor_supp,
    t_plan     -> loop_trial,
    t_design   -> loop_trial,
    loop_trial -> t_release,
    xor_app    -> t_release,
    xor_supp   -> t_release,
    t_release  -> t_archive
  }
)
```

### 2. Self-Contained Python Construction Code
```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator
import pm4py

# Basic transitions
t_reg = Transition(label="Register Deviation")
t_contain = Transition(label="Contain Material")
t_analyze = Transition(label="Analyze Root Cause")
t_plan = Transition(label="Plan Verification")
t_design = Transition(label="Design Corrective Action")
t_release = Transition(label="Release Material")
t_archive = Transition(label="Archive Case")

# Submodel 1: Approval Route -> XOR(Supervisor Review, PO(Quality Review || Regulatory Review))
t_sup = Transition(label="Supervisor Review")
t_qual = Transition(label="Quality Review")
t_reg_rev = Transition(label="Regulatory Review")
po_high_risk = StrictPartialOrder(nodes=[t_qual, t_reg_rev])  # No edges = concurrent

xor_approval = OperatorPOWL(operator=Operator.XOR, children=[t_sup, po_high_risk])

# Submodel 2: Optional Supplier Consultation -> XOR(Consult Supplier, SilentTransition)
t_supp = Transition(label="Consult Supplier")
tau_skip = SilentTransition()
xor_supplier = OperatorPOWL(operator=Operator.XOR, children=[t_supp, tau_skip])

# Submodel 3: Trial Loop -> LOOP(do: PO(Execute Trial -> Inspect Trial), redo: Adjust Parameters)
t_exec = Transition(label="Execute Trial")
t_insp = Transition(label="Inspect Trial")
po_trial_body = StrictPartialOrder(nodes=[t_exec, t_insp])
po_trial_body.order.add_edge(t_exec, t_insp)

t_adjust = Transition(label="Adjust Parameters")
loop_trial = OperatorPOWL(operator=Operator.LOOP, children=[po_trial_body, t_adjust])

# Top-level StrictPartialOrder assembling all nodes and cross-branch dependencies
powl = StrictPartialOrder(
    nodes=[
        t_reg,
        t_contain,
        t_analyze,
        t_plan,
        t_design,
        xor_approval,
        xor_supplier,
        loop_trial,
        t_release,
        t_archive,
    ]
)

# Start dependencies
powl.order.add_edge(t_reg, t_contain)
powl.order.add_edge(t_reg, t_analyze)

# Split stream dependencies
powl.order.add_edge(t_contain, t_plan)
powl.order.add_edge(t_analyze, t_design)
powl.order.add_edge(t_analyze, xor_approval)
powl.order.add_edge(t_analyze, xor_supplier)

# Trial synchronization (waits for both Plan Verification and Design Corrective Action)
powl.order.add_edge(t_plan, loop_trial)
powl.order.add_edge(t_design, loop_trial)

# Release synchronization (waits for Trial Loop, Approvals, and Optional Supplier)
powl.order.add_edge(loop_trial, t_release)
powl.order.add_edge(xor_approval, t_release)
powl.order.add_edge(xor_supplier, t_release)

# Terminal dependency
powl.order.add_edge(t_release, t_archive)
```

### 3. Justification of Intentionally Unconnected Node Pairs
In a `StrictPartialOrder`, the absence of a direct or transitive directed path between two nodes means they are concurrent. Every unconnected pair in `powl` directly reflects intended domain independence:
- **`(t_contain, t_analyze)`**: Narrative Rule 2 explicitly states that `Contain Material` and `Analyze Root Cause` proceed independently and overlap after registration.
- **`(t_contain, t_design)`, `(t_contain, xor_approval)`, `(t_contain, xor_supplier)`**: Root-cause downstream tasks (`Design Corrective Action`, `Approvals`, `Consult Supplier`) depend only on `Analyze Root Cause` (Rules 4, 5, 6), so they can execute even before `Contain Material` completes.
- **`(t_plan, t_analyze)`, `(t_plan, t_design)`**: `Plan Verification` depends only on `Contain Material` (Rule 3) and can occur concurrently with `Analyze Root Cause` and `Design Corrective Action` before synchronizing at `loop_trial`.
- **`(xor_approval, t_plan)`, `(xor_approval, t_design)`, `(xor_approval, loop_trial)`**: Rule 7 states that the approval route does not have to finish before the trial starts and may overlap planning, design, and the trial cycle.
- **`(xor_supplier, t_plan)`, `(xor_supplier, t_design)`, `(xor_supplier, xor_approval)`, `(xor_supplier, loop_trial)`**: Rule 6 states that `Consult Supplier` may overlap corrective-action design, verification planning, approvals, and trial work, synchronizing only at `Release Material`.
- **`(t_qual, t_reg_rev)` inside `po_high_risk`**: Rule 5 specifies that in high-risk cases, `Quality Review` and `Regulatory Review` may occur concurrently and in either completion order.

# 7. Preferred Representation and Validation Plan

### Canonical Representation Choice
The **PM4Py POWL model (`powl`)** is the preferred canonical representation. The material-deviation process contains an intrinsic non-block-structured DAG synchronization pattern (an N/M-pattern) where two parallel upstream activities (`Contain Material` and `Analyze Root Cause`) spawn four downstream branches with asymmetric join points (`Execute Trial` joins two of them; `Release Material` joins the trial loop with the remaining two). Because POWL natively supports `StrictPartialOrder` alongside hierarchical `OperatorPOWL` nodes (`XOR`, `LOOP`), it captures every precedence, concurrency, choice, loop, and synchronization requirement **with 100% behavioral fidelity and zero label duplication**. The Process Tree is forced to serialize the initial parallel block before starting downstream work, rejecting legitimate concurrent executions (such as Witnesses **W4** and **W5**).

### Concrete Validation Plan
To verify both implementations programmatically in PM4Py, execute the following validation pipeline:

1. **Conversion to Accepting Petri Net**:
   Convert both `tree` and `powl` into Petri nets `(net_tree, im_tree, fm_tree) = pm4py.convert_to_petri_net(tree)` and `(net_powl, im_powl, fm_powl) = pm4py.convert_to_petri_net(powl)`. Inspect the resulting nets to confirm that `im` and `fm` are non-empty single-token markings.
2. **Soundness Checking (Workflow Net Verification)**:
   Run `pm4py.check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)` and `pm4py.check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)`. Both must return `True`, confirming the absence of deadlocks, livelocks, dead transitions, and improper completion (leftover tokens at `Archive Case`).
3. **Bounded / Sampled Playout Verification**:
   Generate trace samples using `pm4py.play_out(net_powl, im_powl, fm_powl, parameters={"no_traces": 1000})`. Assert invariant properties over all sampled traces $t$:
   - $t[0] = \text{"Register Deviation"}$ and $t[-1] = \text{"Archive Case"}$ and $t[-2] = \text{"Release Material"}$;
   - $\text{count}(t, \text{"Execute Trial"}) = \text{count}(t, \text{"Inspect Trial"}) = \text{count}(t, \text{"Adjust Parameters"}) + 1$;
   - $\text{count}(t, \text{"Consult Supplier"}) \in \{0, 1\}$.
4. **Explicit Positive and Negative Trace Conformance Tests**:
   Convert Witness traces **W1–W8** into a PM4Py `EventLog` and run token-based replay (`pm4py.conformance_diagnostics_token_based_replay`) and alignments (`pm4py.conformance_diagnostics_alignments`) against both Petri nets:
   - Assert `trace_is_fit == True` for **W1–W5** on `net_powl`.
   - Assert `trace_is_fit == True` for **W1–W3** and `trace_is_fit == False` for **W4–W5** on `net_tree` (confirming the exact boundary of our under-approximation).
   - Assert `trace_is_fit == False` for **W6–W8** on both `net_powl` and `net_tree`.
5. **Silent Transition and Duplicate-Label Audit**:
   Iterate over `net.transitions` for both converted Petri nets:
   - Collect `[t.label for t in net.transitions if t.label is not None]`. Verify that `len(visible_labels) == len(set(visible_labels)) == 14`, proving zero label duplication and full coverage of the 14 narrative activities.
   - Check silent transitions (`t.label is None`) to ensure no pure $\tau$-cycles exist (which would cause infinite zero-cost alignment loops); verify that removing the optional skip $\tau$ in `xor_supplier` makes `Consult Supplier` mandatory in playout.

### Limitations of the Validation Plan
- **Infinite State/Trace Space Due to Loops**: Because the trial loop (`Execute Trial -> Inspect Trial -> Adjust Parameters`) is unbounded, finite playout (`no_traces=1000`) and finite witness suites (**W1–W8**) only sample bounded unfoldings of the loop and cannot exhaustively enumerate all interleaved loop traces.
- **Data-Abstraction Blindness**: Because the models abstract away case attributes (`risk_level`, `supplier_needed`, `inspection_passed`), control-flow validation cannot detect data-control mismatches—for example, a high-risk case illegally taking the `Supervisor Review` branch or `Consult Supplier` being skipped when supplier involvement was mandated by case data.
- **Atomic Event Granularity**: Validating completion-only event traces cannot verify whether two concurrent activities actually overlapped in wall-clock duration (`start` to `complete` interval overlap) versus merely occurring in either sequential order.

# 8. Final Self-Critique

1. **Semantic Weakness — Loss of Data-Driven Determinism (Oracular Choice Abstraction)**:
   In the narrative, the choices between low/high risk, whether to consult a supplier, and whether an inspection passes or fails are determined by case data and physical inspection outcomes. In both our Process Tree and POWL models, these are abstracted as purely non-deterministic control-flow choices (`Operator.XOR` and `Operator.LOOP`). Consequently, the models cannot prevent a "high-risk" case from taking the `Supervisor Review` path, nor can they distinguish between a trace where `Consult Supplier` was legitimately unneeded versus one where it was negligently omitted before `Release Material`.
2. **Semantic Weakness — Atomic Completion Timestamps vs. True Interval Overlap**:
   Narrative Rule 11 states that activities are recorded only at completion time, while Rules 2, 6, and 7 discuss activities "overlapping." Our models represent overlap as structural concurrency, which manifests in completion logs as arbitrary interleaving of completion events. If an activity like `Consult Supplier` starts *before* `Analyze Root Cause` completes (violating Rule 6's start-time constraint) but finishes *after* `Analyze Root Cause` completes, a completion-only event log will record `Analyze Root Cause` followed by `Consult Supplier`, and both models will falsely accept the trace as valid. Capturing true start-after-completion dependencies would require dual life-cycle transitions (`start` and `complete`) for each activity.
3. **Representational Trade-off in the Process Tree Approximation**:
   By choosing a conservative under-approximation for the Process Tree without label duplication, our `tree` rejects valid traces (**W4**, **W5**) where one initial branch progresses into planning or design/review while the other initial branch (`Analyze Root Cause` or `Contain Material`) is still underway. If the business frequently experiences long containment times paired with fast root-cause analysis (or vice versa), using `tree` for automated compliance monitoring would generate false-positive compliance alerts. Conversely, switching to a permissive over-approximation would have risked admitting unsafe execution orders (such as running `Execute Trial` before `Contain Material` finished).
