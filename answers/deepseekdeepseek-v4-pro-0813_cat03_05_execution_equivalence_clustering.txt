```
    event_sigs = []

        type_counts = defaultdict(lambda: [0,0]) # local, external
```

```
from collections import defaultdict, Counter

def canon_event(activity, obj_map):
    # obj_map: dict type -> list of ids
    counts = defaultdict(lambda: [0,0])
    for typ, ids in obj_map.items():
        for oid in sorted(set(ids)):
            if oid.startswith("EXT"):
                counts[typ][1] += 1  # external
            else:
                counts[typ][0] += 1  # local
    return (activity, tuple(sorted((t, local, ext) for t,(local,ext) in counts.items())))

def canon_rel(rel):
    # rel has qualifier, source_type, source_id, target_type, target_id
    return (rel.qualifier,
            rel.source_type, rel.source_id.startswith("EXT"),
            rel.target_type, rel.target_id.startswith("EXT"))

def canonical_signature(events, relations):
    event_sig = tuple(canon_event(e.activity, e.objects) for e in events)
    rel_sig = tuple(sorted(canon_rel(r) for r in relations))
    return (event_sig, rel_sig)
```

## 1. Equivalence design space

I use four equivalence relations, from coarse to fine. The third is my preferred semantic relation.

### 1. Activity-sequence equivalence

**Definition.** Two executions are equivalent iff their timestamp-ordered sequence of activity labels is identical, e.g. `Create Order, Add Item, Add Item, Pack Package, Dispatch, Issue Invoice, Record Payment`.

**Invariants preserved.** Activity labels and their total order.

**Information discarded.** All object types, object identifiers, external-object flags, O2O qualifiers, multiplicities, and object relationships.

**Properties.** Reflexive, symmetric, transitive as defined.

**Concurrency.** With same-time events, I compare the canonical partial order of labels. If two same-time events have identical label signatures, they are treated as commutative; otherwise partial-order isomorphism is required.

### 2. Typed structural equivalence under identifier renaming

**Definition.** Two executions are equivalent iff, after replacing each local object identifier by its object type and sorting object types inside every event, the ordered typed event signatures are identical. Repeated events remain repeated.

Example typed event signature: `Pack Package{Order:1, Item:2, Package:1}`.

**Invariants preserved.** Activity labels, event order, per-event object-type multiplicities, and repeated event structure.

**Information discarded.** Local object identities, external flags, O2O qualifiers, amounts, object attributes, and lifecycle semantics.

**Properties.** Reflexive, symmetric, transitive.

**Concurrency.** The same typed signature is computed on a partial-order representation. Concurrent events with identical typed signatures commute.

### 3. Business-semantic equivalence

**Definition.** Two executions are business-semantic equivalent iff their canonical semantic signatures are equal. The signature preserves:
- ordered event signatures with activity label and, per object type, local count and external count;
- O2O qualifiers normalized to object-type roles and external flags;
- repeated events and lifecycle motifs such as multiple packages, multiple deliveries, returns, replacements, partial payments, and shared external objects.

**Invariants preserved.** Event order, repeated activities, object-type multiplicities, external-object incidence, O2O qualifier types, package/delivery/invoice/payment shape, return/replacement motifs, and cross-order sharing.

**Information discarded.** Local object identifiers, internal attributes, exact timestamps beyond order, precise monetary amounts, and object names.

**Properties.** Reflexive, symmetric, transitive.

**Concurrency.** For same-time events, I compare canonical partial-order signatures; identical same-time event signatures commute.

### 4. Exact object-graph equivalence under renaming

**Definition.** Two executions are equivalent iff there is an isomorphism of the full event-to-object graph after local identifier renaming, preserving activity labels, object types, event order, exact E2O incidence, and qualifiers.

This is the finest reasonable equivalence. It is useful for audit-style root-cause analysis, but usually too fine for business segmentation.

## 2. Canonical signatures

The preferred signature is reproducible and invariant to local identifier renaming. It keeps local object counts, external counts, event order, and normalized O2O qualifiers.

Object types are abbreviated as:
- `O` = Order
- `I` = Item
- `P` = Package
- `D` = Delivery
- `V` = Invoice
- `M` = Payment

In the code below, `events` is an ordered list of `Event` objects. Each `Event` has `activity` and `objects`, where `objects` maps object type to a list of object IDs. Relations are O2O qualifier objects.

```python
from collections import defaultdict

def is_external(oid):
    return oid.startswith("EXT")

def canonical_event(event):
    obj_counts = defaultdict(lambda: [0, 0])  # type -> [local, external]
    for obj_type, ids in event.objects.items():
        for oid in set(ids):
            if is_external(oid):
                obj_counts[obj_type][1] += 1
            else:
                obj_counts[obj_type][0] += 1
    normalized = tuple(sorted(
        (obj_type, local_n, ext_n)
        for obj_type, (local_n, ext_n) in obj_counts.items()
    ))
    return (event.activity, normalized)

def canonical_relation(rel):
    # rel: qualifier, source_type, source_id, target_type, target_id
    return (
        rel.qualifier,
        rel.source_type,
        is_external(rel.source_id),
        rel.target_type,
        is_external(rel.target_id),
    )

def canonical_signature(events, relations):
    event_sig = tuple(canonical_event(e) for e in events)
    rel_sig = tuple(sorted(canonical_relation(r) for r in relations))
    return (event_sig, rel_sig)
```

This signature is the preferred semantic signature. It does not collapse repeated events; it treats `Add Item x2`, `Pack Package x2`, or `Record Payment x2` as distinguishable from a single event. In table signatures below, `x2` is a shorthand for two identical typed event signatures.

## 4. Cluster interpretations

### PS-1 — Clean isolated single shipment

**Signature:** 1 Order, 2 Items, 1 Package, 1 Delivery, 1 Invoice, 1 Payment; no externals; no qualifiers beyond `packs`, `carries`, `bills`, `settles`.

**Business behavior:** A standard order is fully picked, packed into one package, dispatched once, invoiced once, and paid once.

**Operational risks/opportunities:** Low structural risk. The main opportunity is straight-through automation.

**Traditional flattening:** A single-order case model works acceptably here, but it may hide item-level package membership if items can later appear in returns or shared packages.

**Stable under data repair:** Yes. Swapping `Add Item` IDs or correcting item order inside the package should not change the cluster.

### PS-2 — Split package, consolidated delivery

**Signature:** 2 Packages, 1 Delivery, 1 Invoice, 1 Payment.

**Business behavior:** The warehouse packs items separately but ships them as one delivery. The financial side remains standard.

**Operational risks/opportunities:** Risk of package-level damage or loss while the delivery-level tracking remains single. Opportunity to optimize cartonization without changing billing.

**Traditional flattening:** If flattened to one Order case, the fact that one delivery carries two packages may be invisible. If flattened to Package cases, the single order-level invoice may be duplicated.

**Stable under data repair:** Yes, as long as the 1-delivery consolidation is preserved.

### PS-3 — Split package, split delivery, multi-payment

**Signature:** 2 Packages, 2 Deliveries, 1 Invoice, 2 Payments with partial/complete settlement qualifiers.

**Business behavior:** Each package is delivered separately. The invoice is partially settled by one payment and completed by another.

**Operational risks/opportunities:** More delivery and reconciliation risk. Payment-to-delivery allocation is nontrivial. Opportunity exists to track shipment-level completion and payment age separately.

**Traditional flattening:** An Order case shows two payments but may not show which package or delivery is tied to it. A Package case splits the invoice and payment structure artificially.

**Stable under data repair:** Stable if both payment events are preserved. If payment multiplicity is treated only as amount, the cluster loses its financial-risk meaning.

### PS-4 — Cross-order logistics sharing

**Signature:** Pack and Dispatch contain external Order and external Item; O2O says external order contains external item; invoice only bills O5.

**Business behavior:** A package is shared across orders. Items from another order are packed and dispatched together with the lead order, but billing remains local to O5.

**Operational risks/opportunities:** Cost allocation across orders, package damage responsibility, and inter-order dependency are key risks. Opportunity exists to consolidate logistics without creating a shared invoice.

**Traditional flattening:** An Order-centric view hides `EXT-OA` and `EXT-IA`. A Package-centric view may over-share financial events.

**Stable under data repair:** Stable if external flags and cross-order containment qualifiers are retained. If external objects are ignored, it collapses into PS-1.

### PS-5 — Cross-order financial sharing

**Signature:** Invoice and Payment contain external Order; logistics is local and single-package.

**Business behavior:** The order has clean local logistics, but the invoice bills both O6 and an external order. Payment settles the invoice without order-level allocation.

**Operational risks/opportunities:** Revenue allocation, customer account reconciliation, and inter-company clearing are important. Opportunity exists to automate shared invoicing.

**Traditional flattening:** An Order-case view hides `EXT-OB`. An Invoice-case view may detach the financial event from O6 logistics.

**Stable under data repair:** Stable if external flags are kept. If externality is ignored, it collapses into PS-1.

### PS-6 — Replacement/removal at dispatch

**Signature:** Dispatch includes an extra Item; qualifier `removed_before_dispatch` links package to one item; another replacement relation links one item to another.

**Business behavior:** A packed item is removed or substituted before dispatch, but the dispatch still records an item reference. Invoicing and payment remain normal.

**Operational risks/opportunities:** Inventory accuracy, substitution reason, and customer fulfillment exceptions are important. Opportunity exists to capture substitution and removal reasons systematically.

**Traditional flattening:** Activity-label flattening sees a normal fulfillment sequence. The exception is only visible in object relationships and qualifiers.

**Stable under data repair:** Stable only if the `removed_before_dispatch` and replacement qualifiers are preserved.

### PS-7 — Return and repack

**Signature:** Initial pack/dispatch, then Return Item, Inspect Return, second pack, second dispatch; second package replaces first for the returned item.

**Business behavior:** An item is returned after dispatch, inspected, repacked, and dispatched again. The order is invoiced and paid once.

**Operational risks/opportunities:** Reverse logistics cost, inspection quality, package replacement history, and customer return reasons are central.

**Traditional flattening:** An Order case shows many activities but may lose the replacement relationship between packages. A Package case loses the return dependency.

**Stable under data repair:** Stable if `replaces` and return/inspect events are retained.

## 5. Borderline cases

### X1 versus X2

Activity-sequence equivalence sees them as identical because the activity labels are identical. Typed structural equivalence also sees them as identical after object renaming and ignoring the order of the two same-typed `Add Item` events. A definition that preserves exact local object-ID incidence or the order of item IDs inside event collections can disagree and split them. That split is usually overly fine because local IDs encode no business semantics.

### X1 versus X5

Activity-sequence equivalence collapses X1 and X5 because both have the same labels in the same order. Typed structural equivalence separates them because X5 has extra Order and Item objects in Pack and Dispatch. Business-semantic equivalence separates them because the extra objects are external and the package is shared across orders. A defensible but coarser business definition that ignores externality or treats all objects as local could merge them.

### X1 versus X6

X1 and X6 are activity-sequence equivalent. They differ at the business-semantic level because X6 shares an external Order in Issue Invoice and Record Payment. Typed structural equivalence also separates them because the invoice and payment events contain an extra Order object. A definition that treats financial events only as order-level attributes may collapse this distinction, losing the cross-order billing risk.

### X1 versus X7

X1 and X7 are activity-sequence equivalent because labels are the same. Typed structural equivalence separates them because X7 dispatch includes an extra Item. Preferred semantic equivalence separates them more strongly because X7 includes `removed_before_dispatch` and replacement qualifiers. If O2O qualifiers are ignored and the extra dispatch item is discarded, X7 collapses toward X1.

### X3 versus X4

X3 has two packs followed by one consolidated dispatch. X4 alternates pack-dispatch, pack-dispatch and has two payments. Typed structural and business-semantic equivalence separate them. A coarser logistics definition that says “split into two packages” could group them, but then it would ignore important delivery and payment behavior.

### X4 versus X8

Both X4 and X8 contain two dispatch events and multiple pack events. A coarse definition based only on repeated dispatch count could group them. Business-semantic equivalence separates them because X4 is two independent forward shipments with two payments, while X8 is a return/repack exception flow with one payment and a replacement relation.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The PM4Py key structure preserves exact object-centric event-to-object graph information for the selected lead object type. That includes activity labels, object types, object IDs or canonical object roles, and the event-object incidence graph. It may also respect event order and repeated events. This is much richer than a flattened case ID, but it can be too fine when local object identifiers differ without a meaningful process difference.

Raw object identifiers can make exact clusters too fine because two executions with identical structure but renamed IDs, such as X1 and X2, may be split. Exact equivalence is useful for audit-grade structural identity, but not for management segmentation.

Practical process:
1. Run exact clustering with `Order` as the lead object type.
2. Post-process each returned cluster by computing the canonical semantic signature from Section 2.
3. Merge exact clusters that have the same semantic signature.
4. Use `max_objs` to limit huge connected object graphs, but be careful: large packages, invoices, or shared orders may be cut off, producing misleading clusters.

```python
import pm4py
from collections import defaultdict

# Assume `ocel` exists and has Order as lead object type.
exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type='Order'
)

def canonical_signature_for_cluster(cluster):
    # This is a sketch. Extract events and object-type incidence from
    # the cluster DataFrame/OCEL representation; then normalize IDs away.
    sig = []
    for event in cluster.to_dict('records'):
        obj_counts = defaultdict(lambda: [0, 0])
        # Fill obj_counts from event's object_type and object_id columns.
        # Mark external if object_id startswith('EXT').
        sig.append((event['activity'], tuple(sorted(obj_counts.items()))))
    return tuple(sig)

merged = defaultdict(list)
for idx, cluster in enumerate(exact_clusters):
    sig = canonical_signature_for_cluster(cluster)
    merged[sig].append(idx)
```

Exact equivalence is preferable when compliance or root-cause analysis requires every shared object, replacement relation, and external object to be preserved exactly. A coarser business clustering is preferable when summarizing operational variants or building stable segmentations.

`max_objs` and large connected executions may create very large exact keys, especially when a package or invoice contains many items or spans many orders. Large fan-out can explode runtime and produce overly specific clusters. Pre-projecting to domain-relevant object relationships usually helps.

## 7. Robustness analysis

### 1. Ignore all O2O qualifiers

X7 loses its defining replacement/removal meaning. If the extra item in Dispatch is still retained in the typed signature, X7 remains structurally distinct, but the reason is lost. X4 retains two payment events even if partial/completion qualifiers are removed, so it remains separate from X1 and X3. X8 remains distinct because of return/inspect/repack events. Cluster definitions become more syntactic and less semantic.

### 2. Ignore external objects

If external objects are dropped entirely from signatures, X5 and X6 move into the clean baseline cluster PS-1 because their local event shapes become like X1. If external objects are treated as ordinary local objects, X5 and X6 remain distinct but lose their cross-order meaning. This shows that external flags are not cosmetic.

### 3. Collapse repeated same-label events

If repeated same-label events are collapsed while retaining object-type counts, most preferred clusters remain distinguishable because counts still differ. For example, X3 still has two packages and X4 still has two deliveries. If repeated labels are collapsed and counts are also ignored, the clustering becomes much coarser and X1, X3, X5, X6, and X7 may merge, which is usually too coarse for object-centric analysis.

### 4. Treat Pack and Dispatch as a partial order rather than a total order

X3 has two packs before one dispatch. X4 has two separate pack-dispatch chains. A partial-order comparison may ignore the interleaving in X4, but X3 and X4 still differ because X3 has one delivery and X4 has two. X8 also remains distinct due to return and inspection. The main effect is on definitions that are sensitive to intermediate ordering rather than final delivery shape.

### 5. Treat payment multiplicity as an amount attribute rather than structure

X4 then loses its partial-payment/completion-payment distinction. It may be reclassified as “split deliveries, one payment amount” rather than “split deliveries, multi-payment”. It would still not merge with X1 because of the two deliveries, but its financial risk would be underrepresented.

## 8. Limitations and recommendation

One equivalence level cannot be best for all purposes.

- **Compliance monitoring:** Use business-semantic or exact object-graph equivalence with external flags and O2O qualifiers. This preserves shared orders, shared invoices, replacements, and returns.
- **Operational segmentation:** Use business-semantic equivalence. It keeps operationally meaningfully distinct clusters, such as split delivery, cross-order package sharing, and return/repack, without splitting on local IDs.
- **Root-cause analysis:** Use exact object-graph equivalence under renaming, or even raw exact IDs temporarily. It allows inspection of specific package-item and invoice-payment bindings.
- **Descriptive reporting:** Use typed structural equivalence or business-semantic clusters aggregated into readable variant names. Activity-sequence alone is too weak because X1, X5, X6, and X7 look identical at label level but have different object-centric meaning.

The preferred semantic clustering should not be treated as the only correct answer. It is designed to be explicit, stable under local identifier renaming, sensitive to external sharing and lifecycle qualifiers, and coarse enough to aggregate local noise such as X1 versus X2.
