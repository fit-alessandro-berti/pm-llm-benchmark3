## 1. Control-Objective Decomposition

FEP-1 is not a rule for its own sake. Its objective is to make it materially harder for one person to initiate and complete an erroneous or fraudulent disbursement. Decomposing that objective gives the following threat scenarios.

| Threat scenario | AV-2 | MG-4 | RA-7 | ED-1 |
|---|---|---|---|---|
| Clerical error / duplicate / wrong amount / wrong vendor | Prevents duplicate, amount-limit, and basic PO mismatches. | Prevents if a manager substantively checks the invoice and payment details before release. | Detects after the fact; can correct only if still within recall/recovery window. | Caps amount, requires full AV-2 pass, and therefore limits single-operator error exposure. |
| Intentional fraud by preparer to self or related party | Blocking bank ownership, sanctions, or duplicate anomalies may prevent some cases, but it cannot validate commercial reasonableness or detect collusion. | Independent manager review of vendor, bank details, and supporting receipt is the strongest preventive barrier. | Detects after payment, usually after loss unless recall is timely. | Does not remove fraud risk; it only makes the same-user route conditional on other strong controls. |
| Bank-account change / hijacking | Checks bank-account ownership and changes in previous seven days. | Manager should verify bank details before approval. | Detects and may correct if raised before settlement or within recall window. | Prohibits same-user payments when a bank change occurred in previous seven days. |
| Compromised account / stolen credentials | Cannot establish who controlled the account at the time. | An independent manager may stop suspicious payees or unusual instructions. | May detect later through anomalous activity. | A single compromised operator could still pass ED-1 if the conditions are met, so ED-1 is not a substitute for credential hygiene. |
| Collusion between preparer and releaser | Mostly unable to detect collusion. | Helps only if the manager is genuinely independent and reviews substantive evidence. | Can detect repeated pairs, shared workstations, and unusual approval patterns. | Does not address collusion. |
| Supervisor pressure / rubber-stamping / conflict of interest | Does not address human motivation or independence. | Requires manager L3+, no conflict, and substantive review; rubber-stamping is weak. | Can detect unreasonably fast approvals or missing evidence. | Requires an independent manager, but proof of independence must be evidenced. |
| Shared accounts, shared workstations, or credential sharing | Does not know who physically controlled the terminal. | Independent manager may catch anomalies, but cannot see shared credentials. | Repeated pair plus shared workstation is a strong audit indicator. | Does not solve physical or credential-sharing risks. |

## 2. Equivalence and Sufficiency Test

A compensating package should be judged against the control objective, not against the count of activities.

A package is **fully equivalent** if it provides substantially the same assurance as FEP-1 for the specific case risk:

- **Timing:** the last human/automated gate occurs before an irrevocable settlement, ideally before release.
- **Independence:** the actors are distinct humans, are not in a reporting relationship, do not share credentials or workstations, and have no unresolved conflict.
- **Coverage:** the controls check the material risk factors for the case: amount, vendor, bank change, duplicate, sanctions, PO, receipt, and commercial reasonableness.
- **Overrideability:** any override is rare, justified, logged, and requires a different, more senior independent actor.
- **Recoverability:** if the control detects a defect, the payment can still be stopped, recalled, or recovered.
- **Evidence quality:** the control events are recorded contemporaneously with reliable actor identities and timestamps.
- **Collusion resistance:** repeated pairings, shared workstations, and related-party vendor links are treated as warning signs.

A package is **partially equivalent** when it reduces risk materially but leaves one or more gaps. Examples include a manager who approves after release but before settlement, an audit that starts shortly after the 24-hour recall window, or a same-user payment that lacks a formal emergency token but is otherwise low-risk.

A package is **merely mitigating** when it reduces probability or impact but does not replace the four-eyes objective. For example, a clean AV-2 pass alone, or a retrospective audit after settlement, may reduce expected loss but does not provide the independent human barrier that FEP-1 requires.

A package is **ineffective** when the controls are absent, overridden by the same actor, conflicted, too late, or contradicted by evidence of collusion or fraud.

Why “same expected loss” is not the only standard: expected loss is an average. It hides tail risk and the effect of deterrence. Two control designs can have the same expected loss in a model, yet differ in whether fraud can be attributed, whether the process deters insiders, and whether a rare high-severity event can be prevented. The four-eyes objective is also a procedural and accountability control, not only a loss-reduction device.

## 4. Preventive–Detective–Corrective Comparison

| Control | Nature | Timing | Preventive / detective / corrective | Important limits |
|---|---|---|---|---|
| AV-2 | Automated validation | Before release | Preventive for covered checks; can block or warn | Does not verify goods/services receipt, commercial reasonableness, collusion, or compromised-account control. |
| MG-4 | Manager approval/ratification | Before release: preventive. Between release and settlement: hybrid. After settlement: detective only | A manager action between Release_Payment and Bank_Settlement is **hybrid**: it detects that a payment instruction has already been issued, and it can still prevent the final irrevocable transfer by blocking or recalling before settlement. | Must be independent, L3+, and substantive. Rubber-stamping is weak. |
| RA-7 | Retrospective audit and recall | After payment | Detective; becomes corrective only when the defect is found before settlement or within the recall/recovery window | After 24 hours, recovery is uncertain; after settlement, internal control normally treats the payment as irrevocable. |
| ED-1 | Emergency single-operator permission | Conditional permission | Not itself an operating control; it only permits same-user processing when all seven conditions are proven | If any condition is missing, the same-user payment is not authorized. |
| FEP-1 | Four-eyes segregation | Before release | Preventive | If violated, a compensating package must substitute for the missing independent releaser. |

Management action after release but before settlement: I classify it as **hybrid**. It is not purely preventive because the release has already occurred; it is not purely detective because the final settlement can still be stopped. In practice, a manager who reviews between release and settlement is a settlement gate. This is weaker than pre-release approval but materially stronger than post-settlement ratification.

## 5. Counterfactual and Residual-Risk Analysis

**AP-201**
- Most plausible loss mechanism: a single operator makes a small erroneous or self-directed payment without a second human check.
- Control that breaks the chain: the pre-settlement manager review by m04. Because settlement occurs later, m04 can still stop the payment.
- Remaining exposure: if m04 rubber-stamps, or if the payment is outside the recalled window before audit starts, the loss becomes unrecoverable.
- Change with a truly independent second releaser: the same-user convenience would be removed. For a EUR 1,800 low-risk case, the added risk reduction is modest, but the process would be formally stronger.

**AP-202**
- Most plausible loss mechanism: same user uses a supervisor’s override credential to bypass a bank-change/new-vendor warning and pays a related-party vendor without receipt.
- Control that breaks the chain: none effectively. AV-2 flagged the issue, but the override was performed by the same user using the manager’s credential; the manager later ratified and is conflicted.
- Remaining exposure: funds remain unrecovered; the organization also has exposure from the unresolved credential-sharing question.
- Change with a truly independent second releaser: an independent, unconlicted manager would most likely reject or require evidence before releasing a EUR 480,000 payment to a new vendor with a two-hour-old bank change and no receipt.

**AP-204**
- Most plausible loss mechanism: two people who share a workstation and repeatedly work as a pair collude or allow one person to act under the other’s identity, then fabricate a receipt.
- Control that breaks the chain: none. AV-2 does not check receipts, no manager approval exists, and the audit occurs after the recall window.
- Remaining exposure: the full EUR 220,000 outflow is effectively unrecovered, and the same pair remains active.
- Change with a truly independent second releaser: a genuinely separate person, on a separate workstation, without a predetermined pairing, would make fabrication harder. It would not fully stop two people who intentionally collude, so substantive manager review and earlier audit are also needed.

**AP-206**
- Most plausible loss mechanism: an unauthorized same-user payment if the emergency token was actually created after Prepare_Payment.
- Control that breaks the chain: manager m11 approval before release and settlement, plus full AV-2 pass, could stop a defect if m11 detected it.
- Remaining exposure: the uncertainty about token timing. If the token was late, the same-user processing was not authorized, even though the other controls were strong.
- Change with a truly independent second releaser: the token-timing ambiguity would become much less important, because the second releaser would provide the normal segregation.

**AP-207**
- Most plausible loss mechanism: an emergency safety repair payment could be fabricated or misdirected.
- Control that breaks the chain: full AV-2 pass, manager m15 substantive review before settlement, and audit within the recall window.
- Remaining exposure: low. The main gap is whether the emergency token and emergency declaration are documented sufficiently for audit.
- Change with a truly independent second releaser: marginal additional benefit. ED-1 appears valid, and the pre-settlement manager review already provides a strong compensating control.

**AP-208**
- Most plausible loss mechanism: a single operator routes EUR 900,000 to a vendor whose bank changed three days earlier while automated validation is unavailable.
- Control that breaks the chain: none. The bank-change check is unavailable, no signed manual checklist exists, the manager ratifies after settlement, and audit is four days late.
- Remaining exposure: high and unrecoverable. If the bank-account change was malicious, the funds would likely be gone.
- Change with a truly independent second releaser: the second releaser would probably refuse to approve an unvalidated, high-value payment with a recent bank change unless all checks were restored and evidence was signed.

**AP-209**
- Most plausible loss mechanism: no observed loss, but future collusion or impersonation if u12 and u13 are not truly independent.
- Control that breaks the chain: no current loss chain exists. AV-2 passes and audit is timely.
- Remaining exposure: unresolved structural risk from the repeated pair and shared workstation; the organization design is missing.
- Change with a truly independent second releaser: it would require separating the pair, separating workstations, and documenting why this two-person cell is acceptable. That would resolve the current indeterminacy.

## 6. Evidence and Monitoring Recommendations

| Indicator | Monitoring rule | Evidential meaning |
|---|---|---|
| Same-user rate | Track all completed payments where Prepare_Payment and Release_Payment have the same human resource. Separate ED-1-authorized cases from unauthorized cases. | An unauthorized same-user payment is a flag, not automatically proof of fraud, but it must be explained. |
| Override rate | Count AV-2 warnings that are overridden. Flag any override made by the same user who prepared the payment, or any override using another user’s credentials. | An override is a control event, but the identity and authority of the override actor are critical. |
| Late manager approval | Compare Manager_Approve / Manager_Ratify timestamps with Release_Payment and Bank_Settlement. Flag approvals after release and especially after settlement. | Post-release approvals are weaker; post-settlement approvals are detective only. |
| Audit before recall window | Measure time from Release_Payment to Audit_Review. Flag audits that start more than 24 hours after release, or more than one business day after an emergency same-user payment. | A timely audit can still enable recall or recovery; a late audit often cannot. |
| Repeated resource pairs | Count how often two specific resources act as preparer/releaser together. Flag pairs whose volume is disproportionate to the rest of the population. | This is a collusion-risk indicator, not proof of collusion. |
| Shared workstations | Collect workstation/terminal identifiers and session logs. Flag cases where two different resources use the same device within a short interval, especially when one of them is the preparer and releaser. | Shared workstations can indicate credential sharing or impersonation. |
| Bank-change proximity | Flag any payment where the vendor bank account changed in the previous seven days. Require an additional independent manager approval and re-validation. | This is a high-risk condition for misdirection. |
| Control outages | Record any AV-2 outage or validation service unavailability. No payment should release during an outage unless a signed manual checklist and a senior independent manager pre-approval exist. | An outage is not itself misconduct, but it removes a key preventive control. |

Alerts should be treated as leads, not conclusions. A high same-user rate may be caused by poor logging or a poorly designed emergency process. A repeated pair may be an intentional, well-designed two-person payment cell. The monitoring system should trigger investigation and require documented explanations, but it should not automatically label the actors as fraudulent.

    if mgr_before_settle:
        return "between_release_and_settlement"
    if mgr_before_settle is False:
        if not sett.empty and t_mgr >= sett["time:timestamp"].min():
            return "after_settlement"
        return "likely_after_settlement"
    return "unknown"

analysis["manager_timing"] = analysis.apply(
    lambda r: manager_timing_flag(r["case"], r["manager_before_settlement"]),
    axis=1
)

def audit_timing_flag(case_id):
    audit = df[
        (df["case:concept:name"] == case_id) &
        (df["concept:name"] == "Audit_Review")
    ]
    if audit.empty:
        return "n/a_no_audit"
    t_audit = audit["time:timestamp"].min()
    rel = df[
        (df["case:concept:name"] == case_id) &
        (df["concept:name"] == "Release_Payment")
    ]
    if rel.empty:
        return "n/a_no_release"
    hours = (t_audit - rel["time:timestamp"].min()).total_seconds() / 3600
    if hours <= 24:
        return f"within_24h ({hours:.1f}h)"
    return f"after_recall_window ({hours:.1f}h)"

analysis["audit_timing"] = analysis["case"].apply(audit_timing_flag)
