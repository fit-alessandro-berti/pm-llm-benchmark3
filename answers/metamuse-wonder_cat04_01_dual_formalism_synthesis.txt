# 1. Assumptions and Interpretation

1. **Completion-time recording:** Event order is completion order, not start order. A precedence statement "X may start only after Y is complete" therefore implies, in a visible trace, that `Y` appears before the completion of `X`, but does not imply that `X` completes before other independently started activities. Examples below use completion traces, consistent with intended requirement 11.
2. **Low-risk / high-risk choice:** Risk is case data and is not represented as an event. It is abstracted as a control-flow `XOR`: low-risk branch is exactly `Supervisor Review`; high-risk branch is exactly a parallel composition of `Quality Review` and `Regulatory Review`. The model cannot prevent a case whose data says "low" from taking the high branch, or vice versa; data consistency must be checked outside the control-flow model.
3. **Optional supplier consultation:** `Consult Supplier` is represented as `XOR(tau, Consult Supplier)`, where `tau` is a `SilentTransition`/silent leaf. This gives at-most-once occurrence because the label occurs once in each model and is not inside a loop. If selected, ordering constraints place it after `Analyze Root Cause` and before `Release Material`. If not selected, the silent alternative contributes no visible event. Selection depends on unmodeled data.
4. **Passing inspection abstraction:** `Inspect Trial` is a single visible label; "pass" and "fail" are not distinct labels. In the loop `LOOP(do=Execute Trial; Inspect Trial, redo=Adjust Parameters)`, exiting the loop after `Execute Trial, Inspect Trial` is interpreted as the passing inspection, and taking the redo branch is interpreted as failure followed by `Adjust Parameters` and a mandatory new trial cycle. Thus `Adjust Parameters` can never be the last trial-related event before release.
5. **Duplicate visible labels:** No duplicate visible labels are permitted in either submitted model. Every activity label appears at most once syntactically, except that loop repetition legitimately produces multiple occurrences of `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` at runtime. Avoiding duplication simplifies conformance checking, fitness/precision interpretation, and label-based validation.
6. **Process-tree approximation policy:** Conservative **under-approximation**. The process tree must not admit unsafe behavior such as planning before containment, designing before root-cause analysis, releasing before approval, or adjusting after a passing inspection. To achieve block structure it delays some activities until both initial work streams are complete, thereby excluding some intended interleavings. This sacrifices flexibility/recall for safety/precision.
7. **Meaning of "may overlap":** Interpreted as **absence of a precedence constraint**, i.e. true concurrency in the partial-order sense and arbitrary interleaving in trace semantics, not merely nondeterministic sequential choice. In a POWL `StrictPartialOrder`, unconnected nodes may interleave in any order and may be regarded as concurrent. In a process tree, `PARALLEL` (`/\`) has interleaving trace semantics; true simultaneity is not directly observable in completion traces.
8. **Start and end:** Every complete trace starts with `Register Deviation` and ends with `Archive Case`. `Archive Case` occurs only after `Release Material`. Partial/incomplete traces are not considered successful cases.
9. **Trial start:** `Execute Trial` requires completion of both `Design Corrective Action` and `Plan Verification`. It explicitly does **not** require approval completion; approval may finish before, during, or after the trial cycle, provided it finishes before `Release Material`.
10. **Release synchronization:** `Release Material` is a join point. It requires: the trial loop has exited after a passing `Inspect Trial`; the selected approval route has completed; and, if the supplier branch selected the visible activity, `Consult Supplier` has completed. In POWL this is modeled by precedence into `Release Material` from the trial loop, the approval choice node, and the supplier choice node. The supplier-choice edge also applies when the silent branch is taken, but then it imposes no visible delay.

# 3. PM4Py Process-Tree Model

**Compact process-tree expression**

```text
->(
  'Register Deviation',
  /\(
    'Contain Material',
    'Analyze Root Cause'
  ),
  /\(
    ->(
      /\('Plan Verification', 'Design Corrective Action'),
      *(
        ->('Execute Trial', 'Inspect Trial'),
        'Adjust Parameters'
      )
    ),
    X(
      'Supervisor Review',
      /\('Quality Review', 'Regulatory Review')
    ),
    X(tau, 'Consult Supplier')
  ),
  'Release Material',
  'Archive Case'
)
```

**Mapping from expression to narrative**

The outermost sequence enforces registration first and release/archive last. The first parallel block contains containment and analysis. The second parallel block contains three obligations that must all complete before release: (i) planning/design followed by the trial loop, (ii) the risk-route choice, and (iii) the optional supplier choice. Inside the trial branch, planning and design are parallel, then a loop whose body is `Execute Trial -> Inspect Trial` and whose redo is `Adjust Parameters`. PM4Py process-tree loop semantics repeat as body, optionally redo, body, optionally redo, and so on; exit is possible only immediately after the body, which encodes "adjust only after failure and never after the passing inspection." The approval `XOR` chooses either the supervisor leaf or a parallel quality/regulatory subtree. The supplier `XOR(tau, Consult Supplier)` is optional and at most once.

**Self-contained Python code**

```python
import pm4py

tree_string = (
    "->( "
    "'Register Deviation', "
    "/\\( 'Contain Material', 'Analyze Root Cause' ), "
    "/\\( "
    "->( "
    "/\\( 'Plan Verification', 'Design Corrective Action' ), "
    "*( ->( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' ) "
    "), "
    "X( 'Supervisor Review', /\\( 'Quality Review', 'Regulatory Review' ) ), "
    "X( tau, 'Consult Supplier' ) "
    "), "
    "'Release Material', "
    "'Archive Case' "
    ")"
)

tree = pm4py.parse_process_tree(tree_string)
```

No object-constructor parent/child manipulation is used, so no explicit `parent.children` handling is required; `pm4py.parse_process_tree` builds the operator tree and parent links internally. If the model were built with `ProcessTree` constructors instead, each child would need to be appended to `parent.children` and have `child.parent = parent` set explicitly.

**Approximation and unrepresentable requirements**

The tree is a conservative under-approximation caused by block structure. Its central defect is the first parallel block `/\(Contain Material, Analyze Root Cause)` followed sequentially by the second parallel block. In a process tree, a subsequent sibling cannot depend on only one child of a preceding parallel block; it must wait for the whole block to join. Consequently, the tree imposes two unintended precedences: `Plan Verification` waits for `Analyze Root Cause` as well as for `Contain Material`, violating the exact form of D25, and `Design Corrective Action`, the approval route, and `Consult Supplier` all wait for `Contain Material` as well as for `Analyze Root Cause`, violating the exact form of D24. The intended trace in which planning completes while analysis is still running, or design completes while containment is still running, is therefore excluded. Within the post-join region the tree is much more faithful: planning and design are parallel; approval and supplier work are parallel with the trial; the trial loop is exact under the pass/fail abstraction; the parallel join before `Release Material` gives exact release synchronization; and approval can complete after a passing inspection but before release. The tree also cannot represent data-based route selection, supplier-selection criteria, or a genuinely labeled pass/fail outcome; those are abstracted by `XOR` and loop exit as documented. It does not use duplicate labels, so there is no duplicate-label ambiguity, but the price is the initial cross-branch delay.

# 4. PM4Py POWL Model

**Compact POWL description**

```text
StrictPartialOrder root over:
  Register Deviation
  Contain Material
  Analyze Root Cause
  Plan Verification
  Design Corrective Action
  Approval = XOR(Supervisor Review,
                 StrictPartialOrder(Quality Review, Regulatory Review) with no edge)
  Supplier = XOR(SilentTransition, Consult Supplier)
  TrialLoop = LOOP(
                StrictPartialOrder(Execute Trial -> Inspect Trial),
                Adjust Parameters
              )
  Release Material
  Archive Case

Edges:
  Register Deviation -> Contain Material
  Register Deviation -> Analyze Root Cause
  Contain Material -> Plan Verification
  Analyze Root Cause -> Design Corrective Action
  Analyze Root Cause -> Approval
  Analyze Root Cause -> Supplier
  Plan Verification -> TrialLoop
  Design Corrective Action -> TrialLoop
  Approval -> Release Material
  Supplier -> Release Material
  TrialLoop -> Release Material
  Release Material -> Archive Case
```

**Self-contained Python code**

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

register = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
analyze = Transition(label="Analyze Root Cause")
plan = Transition(label="Plan Verification")
design = Transition(label="Design Corrective Action")

supervisor = Transition(label="Supervisor Review")
quality = Transition(label="Quality Review")
regulatory = Transition(label="Regulatory Review")

consult = Transition(label="Consult Supplier")

execute = Transition(label="Execute Trial")
inspect = Transition(label="Inspect Trial")
adjust = Transition(label="Adjust Parameters")

release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

high_risk = StrictPartialOrder(nodes=[quality, regulatory])

approval = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor, high_risk],
)

supplier_choice = OperatorPOWL(
    operator=Operator.XOR,
    children=[SilentTransition(), consult],
)

trial_cycle = StrictPartialOrder(nodes=[execute, inspect])
trial_cycle.order.add_edge(execute, inspect)

trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_cycle, adjust],
)

powl = StrictPartialOrder(
    nodes=[
        register,
        contain,
        analyze,
        plan,
        design,
        approval,
        supplier_choice,
        trial_loop,
        release,
        archive,
    ]
)

powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, approval)
powl.order.add_edge(analyze, supplier_choice)
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)
powl.order.add_edge(approval, release)
powl.order.add_edge(supplier_choice, release)
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(release, archive)
```

**Why intentionally unconnected pairs may remain concurrent**

`Contain Material` and `Analyze Root Cause` are unconnected because requirement 2 explicitly allows overlap. `Quality Review` and `Regulatory Review` are unconnected inside the high-risk partial order because requirement 5 allows either completion order. `Plan Verification` and `Design Corrective Action` are unconnected because they have different single prerequisites and no narrative order between them. `Contain Material` is not connected to `Design Corrective Action`, the approval node, or the supplier node, because those depend on analysis rather than containment. Symmetrically, `Analyze Root Cause` is not connected to `Plan Verification`, because planning depends on containment rather than analysis. The approval node, supplier node, planning/design pair, and trial loop have no pairwise edges among themselves beyond their stated prerequisites: approval may overlap trial, supplier may overlap design/planning/approval/trial, and planning/design may overlap each other. They become related only transitively through prerequisites and through their common successor `Release Material`, which is exactly the intended non-block-structured synchronization.

One semantic caveat should be inspected in the installed PM4Py version: edges into and out of `OperatorPOWL` nodes treat the choice/loop submodel as a unit—its prerequisites must hold before the submodel starts and its completion precedes its successors. That is the intended reading here. For the supplier `XOR`, completion of the silent branch is instantaneous in visible terms, so `Analyze Root Cause -> Supplier -> Release Material` does not create a visible obligation when consultation is skipped.

# 7. Preferred Representation and Validation Plan

**Preferred representation**

The POWL model should be canonical. It expresses the decisive non-block-structured dependencies directly: `Contain Material -> Plan Verification` without forcing `Analyze Root Cause -> Plan Verification`, and `Analyze Root Cause -> Design Corrective Action / Approval / Supplier` without forcing `Contain Material` to precede them. It also expresses trial synchronization, approval/trial overlap, supplier overlap, and release synchronization in one partial order. The process tree remains useful as a conservative, easily visualized workflow approximation, especially for audiences or tools that prefer block structure, but it should not be the source of truth for lead-time analysis or conformance decisions involving early planning/design interleavings such as W4.

**Validation plan**

1. **Construction checks:** Execute both code blocks in a clean Python environment with the target PM4Py version. Assert that `tree` and `powl` are constructed, that every required label occurs exactly once syntactically outside loop repetition, that there is exactly one silent supplier alternative in each model, and that all POWL edges listed in the description were added with `.order.add_edge(...)`.
2. **Conversion to accepting Petri nets where supported:** Run `pm4py.convert_to_petri_net(tree)` and `pm4py.convert_to_petri_net(powl)` and retain the returned net, initial marking, and final marking. Inspect transition labels, silent transitions, source/sink structure, and whether operator submodels were converted as units. Successful conversion is evidence of syntactic/structural convertibility, not proof of semantic fidelity.
3. **Soundness checking:** For each converted net for which an initial and final marking are available, run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`. Investigate dead transitions, improper completion, unbounded places, and silent-transition livelocks. Pay special attention to the loop conversion: the redo path must require a new trial cycle before exit.
4. **Bounded/sampled playout:** Use `pm4py.play_out(...)` on the models or converted nets with bounded trace length and a fixed random seed where the API supports it. Bound length, for example to at most 25 visible events, to keep loop sampling finite. Check that sampled traces never show Plan before Contain in POWL, never show Release before approval in either model, and never show Adjust as the final trial event before Release.
5. **Explicit positive trace tests:** Test W1–W5. Expected result: POWL accepts all five; the tree accepts W1, W2, W3, and W5 but rejects W4. The W4 discrepancy must be documented as known under-approximation, not silently treated as a POWL error. For models that do not directly expose a trace-membership API in the installed version, test via conversion to a Petri net and token-based replay/alignment, or via exhaustive bounded playout plus targeted replay.
6. **Explicit negative trace tests:** Test W6–W8. Expected result: both models reject all three. Record the earliest violated dependency for each rejection rather than only a boolean verdict: W6 = ContainPlan, W7 = ApprovalRelease synchronization, W8 = adjust must be followed by another trial cycle and a passing inspection before release.
7. **Silent-behavior and duplicate-label check:** Enumerate silent transitions in both converted nets and confirm that silent behavior is confined to the optional supplier branch and to internal operator/loop routing introduced by conversion. Verify that removing silent steps from an accepted visible trace does not create an additional visible `Consult Supplier`, does not bypass `Analyze Root Cause -> Supplier -> Release`, and does not allow the supplier branch to repeat. Also check for duplicate visible labels by collecting transition labels from the nets and confirming that duplicates arise only from legitimate loop iteration during playout, not from distinct same-label transitions introduced inadvertently.
8. **Counterexample regression set:** Keep W4 as a permanent regression witness for the tree's known overconstraint, and add mutations such as swapping `Contain Material`/`Plan Verification`, moving `Supervisor Review` after `Release Material`, deleting the second trial after `Adjust Parameters`, and placing `Consult Supplier` after `Release Material`. Each mutation should flip the verdict for the stated reason.

**Limitations of the validation plan**

Soundness of a converted Petri net shows absence of certain structural pathologies; it does not prove that the partial order matches business intent. Bounded playout can miss long loop behaviors and rare interleavings, and random playout is biased by the generator. Trace replay can depend on how silent transitions and operator nodes are converted. None of these checks validates unmodeled data conditions: actual risk level, supplier involvement criteria, or the true pass/fail result of an inspection. Finally, completion-time traces cannot fully recover start-time overlap; two activities whose completions are ordered may still have overlapped in real time.

# 8. Final Self-Critique

1. **Semantic weakness — pass/fail is encoded by loop exit, not by evidence:** Both models treat "the loop exited after Inspect Trial" as a pass and "the redo was taken" as a failure. If an event log records an inspection that failed but no adjustment because the case was abandoned, or an adjustment for an unrelated reason, the abstraction can misclassify behavior. Richer labels such as `Inspect Trial - Pass` and `Inspect Trial - Fail`, or a data-aware model, would be semantically stronger but would violate the instruction not to encode the result as an event label.
2. **Semantic weakness — data-dependent choices are only control-flow alternatives:** The risk `XOR` and supplier `XOR` permit either branch regardless of case attributes. Therefore the models are intentionally incomplete as compliance models: they can detect missing approvals, but not a low-risk case incorrectly sent through the high-risk route. External data validation remains necessary.
3. **Implementation/version weakness — POWL operator-edge semantics need empirical confirmation:** The POWL construction assumes that precedence edges to and from `OperatorPOWL` nodes constrain the whole submodel and that `OperatorPOWL` with `Operator.LOOP` uses the first child as the do-part and the second as redo. PM4Py versions and conversion paths should be checked by executing the validation plan; if a version interprets loop children differently, the trial loop would need restructuring even though the Python might still construct an object.
