## 1. Equivalence design space

I treat each execution as a *connected object-centric execution*: a set of events, a set of objects (each with a type and an `external` flag), an event-to-object (E2O) incidence relation with per-event object roles, an object-to-object (O2O) relation carrying qualifiers, and a timestamp order on events. All eight executions share the lead object type `Order` with exactly one non-external `Order` per execution. I define four equivalence relations of increasing semantic richness. Throughout, "local identifier renaming" means any bijection on the non-external object identifiers within a single execution that preserves object type and the `external` flag; external identifiers (prefix `EXT`) are treated as constants that survive renaming, because they encode a real semantic distinction (a lifecycle centered elsewhere).

**R1 — Activity-sequence equivalence.**
*Definition.* Project each execution to the ordered word of activity labels, dropping all objects, E2O, O2O, and identifiers. Two executions are R1-equivalent iff their words are equal. Ties (same-timestamp events) are resolved by a fixed deterministic tie-break (activity label, then a stable original index); if events are truly concurrent, R1 compares the *multiset of linearizations* or, more conservatively, the label multiset plus a declared canonical order.
*Invariants preserved.* Activity vocabulary, number of occurrences of each activity, and their total order.
*Information discarded.* Everything object-centric: object types, multiplicities, E2O incidence, O2O qualifiers, externality, and which item/package a payment refers to.
*Algebraic properties.* Reflexive, symmetric, transitive (equality of words is an equivalence relation).
*Concurrency handling.* If two events share a timestamp, the canonical linearization removes the ambiguity, so R1 remains an equivalence; without a canonical rule, R1 would compare linearization sets and stay well defined.

**R2 — Typed structural equivalence under identifier renaming.**
*Definition.* Two executions are R2-equivalent iff there exists a type- and externality-preserving isomorphism between their attributed structures: a bijection on events preserving activity label and order, together with a bijection on objects preserving type and `external`, such that E2O incidence (including the per-event set of objects of each type) is preserved. O2O topology is preserved as an unlabeled graph; O2O *qualifiers* are ignored at this level. This is typed graph isomorphism on the joint event/object structure.
*Invariants preserved.* Activity sequence; per-event object-type multiplicities (e.g. "Pack Package touches 2 Items and 1 Package"); the number of objects of each type; the E2O and (unlabeled) O2O topology; externality.
*Information discarded.* Concrete identifiers, O2O qualifiers (`replaces`, `removed_before_dispatch`, `partially_settles`), and any attribute values (amounts).
*Algebraic properties.* Reflexive (identity), symmetric (inverse isomorphism), transitive (composition). It is a genuine equivalence.
*Concurrency handling.* Because the event bijection must preserve order, same-timestamp events are matched under the same canonical linearization as R1; if we instead require only partial-order preservation, R2 becomes coarser (see §7) but remains an equivalence.

**R3 — Business-semantic equivalence (preferred).**
*Definition.* R3 refines R2 with the information R2 throws away *and* deliberately re-coarsens over cosmetic order. Two executions are R3-equivalent iff they have the same **business motif signature**, defined as the tuple of: (a) the E2O incidence pattern quotiented by object type and identifier (as in R2), (b) the *multiset of O2O qualifiers* attached to each typed relation, (c) the presence and role of external objects per event (does this execution consume/share an external Order, Item, Invoice, or Payment?), and (d) the set of *lifecycle motifs* detected: `single-package`, `split-package`, `consolidated-delivery`, `split-delivery`, `partial-payment`, `shared-logistics` (external object inside a Package/Delivery), `shared-financial` (external object inside an Invoice/Payment), `item-substitution` (a `replaces`/`removed_before_dispatch` qualifier), and `return-repack` (a Return/Inspect/repack loop). Interleaving order that does not change these motifs is ignored.
*Invariants preserved.* Everything that changes the *business meaning* of the order-to-cash and order-to-fulfilment story: how many packages/deliveries, whether payment is partial, whether logistics or finance is shared across orders, whether items are substituted, and whether returns occur.
*Information discarded.* Local identifiers, the specific interleaving of independent Pack/Dispatch branches, and item-add order.
*Algebraic properties.* Reflexive, symmetric, transitive: signatures are compared by equality, so R3 is an equivalence. (It is coarser than R2 on order but finer on qualifiers/externality; the two are incomparable, not nested.)
*Concurrency handling.* R3 is order-tolerant by construction for independent branches, so concurrent Pack/Dispatch pairs collapse to the same motif; it is order-sensitive only where order carries meaning (e.g. Return must follow Dispatch to be a return).

**R4 — Financial-outcome equivalence (optional coarse relation).**
*Definition.* Collapse each execution to its terminal financial and fulfilment state: (fully delivered?, fully paid?, shared cost?, net items shipped). Two executions are R4-equivalent iff these outcome flags match, ignoring how the state was reached. Reflexive/symmetric/transitive by equality of the outcome tuple. Useful for descriptive reporting; blind to process risk.

## 2. Canonical signatures

My preferred relation is **R3**. I compute a canonical, rename-invariant signature by (i) canonically ordering events, (ii) replacing each object by its *type + external flag + a role-based positional code* rather than its identifier, and (iii) appending the qualifier multiset and detected motifs.

```python
def canonical_signature(ex, lead_type="Order"):
    # ex.events: list of Event(activity, timestamp, e2o)
    #   e2o: dict object_id -> role/type info via ex.obj_type(id), ex.is_external(id)
    # ex.o2o: list of (src_id, qualifier, dst_id)

    # (1) canonical event order: (timestamp, activity, stable_index)
    events = sorted(ex.events, key=lambda e: (e.timestamp, e.activity, e.orig_index))

    # (2) rename-invariant object codes: type + external flag; identity is a
    #     multiset per type so we never leak local ids, but we DO keep EXT ids
    def obj_code(oid):
        t = ex.obj_type(oid)
        if ex.is_external(oid):
            return ("EXT", t)            # externality preserved, id abstracted
        return ("LOC", t)                # local id discarded, type kept

    event_sig = []
    for e in events:
        # per-type multiplicity of objects touched by this event
        type_mult = {}
        for oid in e.objects:
            key = obj_code(oid)
            type_mult[key] = type_mult.get(key, 0) + 1
        event_sig.append((e.activity, tuple(sorted(type_mult.items()))))

    # (3) O2O qualifier multiset, abstracted to typed endpoints
    o2o_sig = {}
    for (s, q, d) in ex.o2o:
        key = (obj_code(s), q, obj_code(d))
        o2o_sig[key] = o2o_sig.get(key, 0) + 1
    o2o_sig = tuple(sorted(o2o_sig.items()))

    # (4) lifecycle motif detection
    motifs = detect_motifs(events, ex)   # returns a frozenset of motif tags
    #   e.g. {"split-package","consolidated-delivery"} etc.

    return (tuple(event_sig), o2o_sig, motifs)

def detect_motifs(events, ex):
    tags = set()
    packs   = [e for e in events if e.activity == "Pack Package"]
    disps   = [e for e in events if e.activity == "Dispatch"]
    pays    = [e for e in events if e.activity == "Record Payment"]
    tags.add("single-package" if len(packs) == 1 else "split-package")
    tags.add("single-delivery" if len(disps) == 1 else "split-delivery")
    if len(pays) > 1: tags.add("partial-payment")
    if any(ex.is_external(o) and ex.obj_type(o) in ("Order","Item","Package")
           for e in (packs+disps) for o in e.objects): tags.add("shared-logistics")
    if any(ex.is_external(o) and ex.obj_type(o) in ("Order","Invoice","Payment")
           for e in events if e.activity in ("Issue Invoice","Record Payment")
           for o in e.objects): tags.add("shared-financial")
    if any(q in ("replaces","removed_before_dispatch") for (_,q,_) in ex.o2o):
        tags.add("item-substitution")
    if any(e.activity in ("Return Item","Inspect Return") for e in events):
        tags.add("return-repack")
    return frozenset(tags)
```

Two executions are R3-equivalent iff `canonical_signature` values are equal. To obtain **R2** signatures, drop `o2o_sig` (qualifiers) and `motifs`, keeping only `event_sig` plus object-type counts; for **R1**, keep only the tuple of activities. Because the signature is built from sorted, identifier-free codes, it is invariant to local renaming, yet preserves types, multiplicities, external flags, qualifiers, and motifs.

## 3. Cluster assignments

Cluster labels: activity-sequence clusters `A*`, typed-structural clusters `T*`, preferred semantic clusters `S*`.

| Execution | Activity-sequence cluster | Typed-structural cluster | Preferred semantic cluster | Defining signature | Main reason |
|-----------|---------------------------|--------------------------|----------------------------|--------------------|-------------|

## 4. Cluster interpretations

**S1 — Clean single-package order-to-cash (X1, X2).**
*Signature:* one Pack, one Dispatch, one Invoice, one fully-settling Payment, no external objects, no special qualifiers.
*Behavior:* the canonical happy path; all items ship in one package on one delivery, one invoice, paid in full.
*Risk/opportunity:* lowest operational risk; ideal automation target and a good conformance reference model.
*Flattening pitfall:* a per-item flattening would duplicate the Pack/Invoice/Payment events across I11/I12, inflating frequencies and inventing convergence that does not exist.
*Stability:* highly stable; renaming, item-add reorder, and timestamp tie-breaks never move it out of S1.

**S2 — Split-pack, consolidated delivery (X3).**
*Signature:* ≥2 Pack, exactly 1 Dispatch carrying all packages.
*Behavior:* order picked into multiple packages but shipped together (multi-box single shipment).
*Risk/opportunity:* consolidation opportunity realised; watch for one package delaying the whole shipment.
*Flattening pitfall:* an Order-flattening hides that two packages exist; a Package-flattening loses the single-delivery convergence.
*Stability:* stable; the count of Pack events is robust to reordering.

**S3 — Split fulfilment with partial payment (X4).**
*Signature:* 2 Pack, 2 Dispatch, 2 Payment with `partially_settles` + `completes_settlement`.
*Behavior:* order fragmented across shipments and paid in instalments against one invoice.
*Risk/opportunity:* revenue-recognition and dunning risk; higher shipping cost; SLA complexity.
*Flattening pitfall:* flattening on Invoice makes the two payments look like duplicates; flattening on Order loses the payment allocation.
*Stability:* stable if the qualifiers survive repair; if a repair drops payment qualifiers it can degrade toward "two payments" without semantics (see §7).

**S4 — Shared logistics (X5).**
*Signature:* an external Order/Item present inside the Package and Delivery, but the invoice bills only the local order.
*Behavior:* physical consolidation across orders (co-pack/co-ship) while finance stays isolated.
*Risk/opportunity:* cost-saving via shared shipping, but cross-order contamination: a problem with EXT-OA can block P51/D51 and thus O5.
*Flattening pitfall:* Order-flattening drops EXT-OA/EXT-IA entirely, erasing the shared risk; it looks exactly like S1.
*Stability:* stable only if externality is preserved; ignoring EXT collapses it into S1 (§7).

**S5 — Shared finance (X6).**
*Signature:* external Order inside Invoice and Payment; single payment with no order-level allocation.
*Behavior:* one invoice/payment spans two orders (bundled billing) while logistics stays isolated.
*Risk/opportunity:* allocation ambiguity, disputed revenue split, audit difficulty.
*Flattening pitfall:* Order-flattening attributes the whole payment to O6, over-counting revenue; Invoice-flattening loses which orders are co-billed.
*Stability:* stable only with externality preserved; else collapses to S1.

**S6 — Hidden item substitution (X7).**
*Signature:* structurally near-S1 but with `removed_before_dispatch`/`replaces` qualifier and a Dispatch whose Item set differs from the Pack Item set.
*Behavior:* an item packed then removed/substituted before shipping; the customer receives fewer/different items than ordered.
*Risk/opportunity:* silent under-delivery, billing mismatch, customer-satisfaction risk; detectable only via qualifiers and E2O deltas.
*Flattening pitfall:* any flattening that ignores O2O qualifiers renders X7 identical to X1 — the most dangerous blind spot.
*Stability:* unstable under "ignore qualifiers" repair; collapses into S1.

**S7 — Return and repack (X8).**
*Signature:* Return Item + Inspect Return + a second Pack/Dispatch, with `replaces` linking the repacked package.
*Behavior:* reverse logistics; an item is returned, inspected, repacked, and reshipped.
*Risk/opportunity:* cost and lead-time impact; opportunity to detect quality problems; rework loop.
*Flattening pitfall:* Order-flattening turns the loop into a confusing self-loop; Package-flattening loses the `replaces` link between P81 and P82.
*Stability:* stable; the Return/Inspect activities are hard to lose under repair.

## 5. Borderline cases

**X1 vs X2.** Under R1 and R2 and R3 they are equivalent. The only differences are a local rename (O1→O2, etc.) and the *order* in which the two Add Item events occur (I11 before I12 vs I22 before I21). Rename is discarded by every relation above R1's identifier-blindness, and Add-order is a cosmetic total-order artifact over independent events. A defensible *stricter* reading — "Add Item order is meaningful because it reflects customer intent" — would keep them apart under a sequence-strict R1 that does not canonicalize identical labels; a partial-order reading merges them. This is the cleanest illustration that "different local ids ≠ different behavior."

**X1 vs X5.** Under R1 they are equal (same label word). Under R2 and R3 they diverge: X5 injects EXT-OA/EXT-IA into the Package and Delivery, so its E2O incidence and externality signature differ. Two defensible definitions disagree precisely on whether external co-shipping is "the same order process": an activity/lead-object-only view says yes (S1), an externality-aware view says no (S4). The disagreement is the whole point — shared logistics is invisible to label clustering.

**X1 vs X6.** Again R1-equal. X6 shares the *invoice and payment* with EXT-OB. Local object multiplicities around O6 look like X1 (one invoice, one payment), so even a naive typed-multiplicity check could call them equal; only inspecting the *members* of the Invoice/Payment objects (external flag) separates them. A definition that counts objects but ignores externality merges X1/X6; a definition that reads external membership splits them (S1 vs S5). This shows multiplicity alone is insufficient — you need external-membership.

**X1 vs X7.** R1-equal and *structurally* very close (same activity multiset, same object-type counts). They differ only in an O2O qualifier (`removed_before_dispatch`) and in the Dispatch event's Item set (I72 only vs I11,I12). A qualifier-blind R2 could call them equivalent; a qualifier-aware R3 separates them (S1 vs S6). The defensible disagreement is whether "what was actually shipped" is part of process identity — it clearly should be for compliance, but a coarse operational view might ignore it.

**X3 vs X4.** Both split into two packages, so a "package-count" view merges them. But X3 consolidates into one delivery and pays once; X4 splits into two deliveries and pays in two instalments. A logistics-only definition keyed on Pack count merges them; a fulfilment-and-finance definition keyed on Dispatch and Payment multiplicity (with settlement qualifiers) separates them (S2 vs S3). Disagreement hinges on whether delivery/payment fragmentation is a first-class dimension.

**X4 vs X8.** Both contain two Pack and two Dispatch events and thus two "shipping rounds." A structural multiplicity view (2 Pack, 2 Dispatch) could merge them. But X4's second round is *forward* fragmentation of a never-shipped item, whereas X8's second round is *reverse* logistics triggered by Return Item/Inspect Return with a `replaces` qualifier. A definition that ignores the Return/Inspect activities and qualifiers merges them; a motif-aware R3 separates them (S3 vs S7). The disagreement is whether repeated Pack/Dispatch means "planned split" or "rework after failure."

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` groups object-centric executions (connected components of the object graph around a lead object type) whose *derived key* is identical. The key it builds preserves the **exact structure of each execution up to that key**: typically the sequence of activities together with the object types and identifiers participating, i.e. it is close to my R2 but keyed on concrete identifiers rather than a rename-invariant canonical form. Because raw identifiers appear in the key, two executions that are isomorphic after renaming (like X1 and X2) can land in *different* clusters — the exact key is too fine. This is why post-processing is needed: I re-key each execution with the `canonical_signature` of §2, which abstracts local identifiers to type codes while keeping external flags, qualifiers, and motifs, then merge PM4Py clusters that share a canonical key.

*When exact equivalence is preferable:* for deduplication, caching of identical variants, or forensic replay where identifier identity matters, the fine exact key is exactly right. For business segmentation you want the coarser R3.

*`max_objs` / large connected executions:* if a package or invoice is shared across many orders (as in X5/X6 scaled up), the connected component can explode; `max_objs` caps component size, which can *truncate* the very external objects that define S4/S5. So a low cap silently pushes shared executions toward looking isolated (S1), and a high cap can make components huge and clusters ultra-fine. Choose the cap knowingly and record it.

```python
import pm4py
from collections import defaultdict

LEAD = "Order"

# 1. exact clusters from pm4py (keyed on structure incl. raw ids)
clusters = pm4py.cluster_equivalent_ocel(ocel, LEAD, max_objs=1000)

# 2. custom canonicalization: re-key each exact cluster by rename-invariant R3 sig
def r3_key(sub_ocel):
    ex = build_execution_view(sub_ocel, lead_type=LEAD)  # events, e2o, o2o, ext flags
    return canonical_signature(ex, lead_type=LEAD)       # from section 2

semantic = defaultdict(list)
for exact_key, sub_ocel in clusters.items():
    semantic[r3_key(sub_ocel)].append(exact_key)

# 3. aggregation/report: one row per semantic cluster
for sig, members in semantic.items():
    print(motif_label(sig[2]), "| n_exact=", len(members))
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** X7 loses `removed_before_dispatch` and collapses from S6 into S1 (it then looks like a clean order); X4 loses its settlement qualifiers, weakening S3 toward "two anonymous payments"; X8 loses `replaces` but is still separated by its Return/Inspect activities. Net: substitution detection is destroyed; return detection survives. This perturbation is the most damaging to compliance use.

**Ignore external objects.** X5→S1 and X6→S1 because EXT-OA/EXT-IA and EXT-OB vanish; shared logistics and shared finance become invisible. X1, X2 unaffected. This collapses five distinct clusters (S1,S4,S5) into one and is exactly the failure mode of naive Order-flattening.

**Collapse repeated same-label events.** X3's two Pack events fold into one, merging its logistics signature toward S1/single-pack; X4's two Pack/Dispatch/Pay fold, erasing split-fulfilment and partial-payment; X8's two Pack/Dispatch fold but Return/Inspect keep it distinct. Multiplicity-based clusters (S2, S3) are the casualties.

**Treat Pack/Dispatch as a partial order.** X4's interleaving (Pack,Dispatch,Pack,Dispatch) becomes order-indistinguishable from X3's (Pack,Pack,Dispatch) *only if* delivery counts are also ignored; if delivery multiplicity is retained, X3 and X4 stay apart (1 vs 2 Dispatch). Mainly this stabilises X1 vs X2 and prevents spurious splits from interleaving; it does not by itself merge different-motif executions. R3 already assumes this partial-order tolerance, so R3 assignments are unchanged.

**Treat payment multiplicity as an amount attribute.** X4's two payments become "one invoice, amount paid = full via two tranches," so X4's *structural* partial-payment motif disappears and it moves toward S2 structurally, with the instalment fact demoted to an attribute. This is defensible for finance reporting (outcome = paid in full) but hides dunning risk. It shows structure-vs-attribute is a modelling choice, not a fact.

Summary: S1 (X1,X2) is robust under every perturbation; S6 (X7) is the most fragile (dies without qualifiers); S4/S5 (X5,X6) die without externality; S2/S3 (X3,X4) die under label-collapse or amount-recoding; S7 (X8) is robust because it is carried by distinct activities as well as qualifiers.

## 8. Limitations and recommendation

No single equivalence level serves all purposes because the relations trade **fineness against interpretability**, and different questions care about different discarded dimensions.

- **Compliance monitoring:** use the finest business-aware relation, essentially **R3 with qualifiers and E2O deltas preserved** (and ideally exact E2O membership for shipped vs packed items). Compliance is precisely about the differences R1/R2 discard — item substitution (X7), shared billing without allocation (X6), partial settlement (X4). A coarse relation would mask exactly the violations you must catch.

- **Operational segmentation:** use **R3 motifs** (S1–S7) but *without* raw identifiers — you want to route "split-fulfilment," "shared-logistics," and "return-repack" orders to different playbooks. R2 is too fine (it splits X1/X2 pointlessly), R4 is too coarse (it hides process shape).

- **Root-cause analysis:** use a **layered** view: start from R3 clusters to localise the motif, then drop to the *exact* PM4Py key (near-R2 with identifiers) to inspect the specific objects, qualifiers, and interleavings causing the outcome. RCA needs both the semantic grouping and the concrete instance detail, so it deliberately spans two levels.

- **Descriptive reporting:** use the coarse **R4 financial/fulfilment-outcome** relation (delivered? paid in full? shared cost?). Executives want stable, low-cardinality categories; the process-shape distinctions that matter operationally are noise here.

The core limitation is that R1 is object-blind (dangerous if mistaken for object-centric), R2 is identifier-fine (X1≠X2 unless canonicalised), R3 requires reliable qualifiers and externality flags (fragile under data repair), and R4 discards all process risk. Externality and qualifiers are the load-bearing signals: repairs that drop them silently merge semantically different orders, so any chosen level must document which perturbations it tolerates. Because compliance wants maximal detail, reporting wants maximal abstraction, and operations/RCA sit in between, the only coherent practice is to *compute several relations from one canonical signature* and pick the projection per use case rather than committing to a single partition.
