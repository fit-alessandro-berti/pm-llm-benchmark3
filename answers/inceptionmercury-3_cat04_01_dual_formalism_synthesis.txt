# 1. Assumptions and Interpretation

1. Activities are modeled as atomic completion events. A precedence edge `X -> Y` means that `X` must complete before `Y` can complete, and in the intended start-based semantics `Y` cannot start until `X` is complete. Durations and resource availability are not modeled.
2. The low-risk / high-risk decision is represented as an unobserved control-flow XOR alternative after `Analyze Root Cause`. The data condition that determines the route is not represented.
3. The optional supplier consultation is represented as an XOR alternative between a silent skip and `Consult Supplier`. The data condition that determines whether it is selected is not represented. Selecting the silent skip emits no visible label.
4. Inspection pass/fail is abstracted by loop control. After `Execute Trial` -> `Inspect Trial`, choosing the loop redo `Adjust Parameters` represents a failed inspection and starts another trial cycle; skipping the redo represents a passing inspection and exits the loop. Thus the final `Inspect Trial` in a complete trace is the passing inspection.
5. Duplicate visible labels are not permitted. Each non-repeatable activity appears structurally once. `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` may repeat in traces because they are inside the trial loop.
6. The process tree uses a conservative under-approximation: it places the approval route and optional supplier in a second parallel block after the `Plan Verification` / `Design Corrective Action` join. Every trace accepted by the process tree is an intended trace, but some intended traces with early approvals or early supplier consultation are excluded.
7. “May overlap” means true concurrency in the completion-order sense: two activities with no precedence path between them may be interleaved in either order. In the process tree this is expressed with `PARALLEL`; in the POWL model this is expressed by omitting a partial-order edge.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|----|------------------------------|------------------------------|----------|----------|
| 1 | Register Deviation | Contain Material | precedence | Every case starts with Register Deviation |
| 2 | Register Deviation | Analyze Root Cause | precedence | Every case starts with Register Deviation |
| 3 | Contain Material | Plan Verification | precedence | Verification planning waits for containment |
| 4 | Analyze Root Cause | Design Corrective Action | precedence | Corrective-action design waits for root cause |
| 5 | Analyze Root Cause | Selected approval route | precedence | Risk route is selected after root cause |
| 6 | Selected approval route | Release Material | synchronization | Approval route must finish before release |
| 7 | Analyze Root Cause | Consult Supplier, if selected | precedence | Optional supplier starts only after root cause |
| 8 | Consult Supplier, if selected | Release Material | synchronization | Supplier must finish before release |
| 9 | Design Corrective Action | Execute Trial cycle | synchronization | Trial waits for design |
| 10 | Plan Verification | Execute Trial cycle | synchronization | Trial waits for verification planning |
| 11 | Execute Trial | Inspect Trial | precedence | Trial cycle order |
| 12 | Inspect Trial | Adjust Parameters | loop / redo, conditional | Failed inspection triggers adjustment |
| 13 | Adjust Parameters | Execute Trial | loop / redo | Retrial after adjustment |
| 14 | Passing inspection / completed trial cycle | Release Material | synchronization | Release requires a passing Inspect Trial |
| 15 | Release Material | Archive Case | precedence | Archive occurs after release |
| 16 | Low-risk route | High-risk route | XOR choice | Low requires Supervisor Review; high requires Quality and Regulatory Review |
| 17 | Quality Review | Regulatory Review | concurrency | High-route reviews are unordered |
| 18 | Consult Supplier | Other branches | concurrency / may overlap | No order with design, planning, approvals, or trial except root-cause-before and release-after |

# 3. PM4Py Process-Tree Model

The process tree below is the conservative under-approximation described in Section 1.

```text
SEQUENCE(
  "Register Deviation",
  PARALLEL(
    SEQUENCE("Contain Material", "Plan Verification"),
    SEQUENCE("Analyze Root Cause", "Design Corrective Action")
  ),
  PARALLEL(
    LOOP(SEQUENCE("Execute Trial", "Inspect Trial"), "Adjust Parameters"),
    XOR("Supervisor Review", PARALLEL("Quality Review", "Regulatory Review")),
    XOR(tau, "Consult Supplier")
  ),
  "Release Material",
  "Archive Case"
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def attach(parent, child):
    child.parent = parent
    parent.children.append(child)
    return child


tree = ProcessTree(operator=Operator.SEQUENCE)

# 1. Register Deviation
register = ProcessTree(label="Register Deviation")
attach(tree, register)

# 2. Initial parallel work streams
initial = ProcessTree(operator=Operator.PARALLEL)
attach(tree, initial)

containment_stream = ProcessTree(operator=Operator.SEQUENCE)
attach(initial, containment_stream)
contain = ProcessTree(label="Contain Material")
plan = ProcessTree(label="Plan Verification")
attach(containment_stream, contain)
attach(containment_stream, plan)

analysis_stream = ProcessTree(operator=Operator.SEQUENCE)
attach(initial, analysis_stream)
analyze = ProcessTree(label="Analyze Root Cause")
design = ProcessTree(label="Design Corrective Action")
attach(analysis_stream, analyze)
attach(analysis_stream, design)

# 3. Post-join parallel work: trial, approval route, optional supplier
post = ProcessTree(operator=Operator.PARALLEL)
attach(tree, post)

trial_loop = ProcessTree(operator=Operator.LOOP)
attach(post, trial_loop)

trial_cycle = ProcessTree(operator=Operator.SEQUENCE)
attach(trial_loop, trial_cycle)
execute = ProcessTree(label="Execute Trial")
inspect = ProcessTree(label="Inspect Trial")
attach(trial_cycle, execute)
attach(trial_cycle, inspect)

adjust = ProcessTree(label="Adjust Parameters")
attach(trial_loop, adjust)

route = ProcessTree(operator=Operator.XOR)
attach(post, route)
supervisor = ProcessTree(label="Supervisor Review")
attach(route, supervisor)
high = ProcessTree(operator=Operator.PARALLEL)
attach(route, high)
quality = ProcessTree(label="Quality Review")
regulatory = ProcessTree(label="Regulatory Review")
attach(high, quality)
attach(high, regulatory)

supplier = ProcessTree(operator=Operator.XOR)
attach(post, supplier)
skip = ProcessTree(label=None)
attach(supplier, skip)
consult = ProcessTree(label="Consult Supplier")
attach(supplier, consult)

# 4. Release and archive
release = ProcessTree(label="Release Material")
archive = ProcessTree(label="Archive Case")
attach(tree, release)
attach(tree, archive)
```

The `attach` helper makes parent/child handling explicit: every node is appended to its parent’s `children` list and its `parent` attribute is set. The root `tree` therefore has ordered children `[Register Deviation, initial parallel, post-join parallel, Release Material, Archive Case]`.

The tree represents exactly:

- `Register Deviation` first and `Archive Case` last;
- `Contain Material` and `Analyze Root Cause` as concurrent initial streams;
- `Plan Verification` after `Contain Material`;
- `Design Corrective Action` after `Analyze Root Cause`;
- the start of the trial loop after both `Plan Verification` and `Design Corrective Action`;
- the trial loop as `LOOP(SEQUENCE(Execute Trial, Inspect Trial), Adjust Parameters)`;
- low-risk/high-risk choice as XOR between `Supervisor Review` and parallel `Quality Review` / `Regulatory Review`;
- optional supplier as XOR between silent `tau` and `Consult Supplier`;
- release synchronization after all post-join branches complete.

Intended requirements that this tree cannot represent exactly:

- The approval route and supplier consultation cannot be forked directly after `Analyze Root Cause` without duplicating `Analyze Root Cause` or using a non-block-structured join.
- The tree therefore postpones the approval route and supplier consultation until after the `Plan Verification` / `Design Corrective Action` join. This excludes intended behavior in which approvals or supplier consultation start before planning/design are complete.
- The tree cannot represent supplier or approval overlap with the initial containment/root-cause streams or with verification planning / corrective-action design.
- The tree is a conservative under-approximation: it does not admit unsafe early release or trial-before-planning behavior, but it intentionally excludes those early-overlap traces.

# 4. PM4Py POWL Model

The POWL model expresses the intended dependencies directly as a strict partial order. A compact description is:

```text
StrictPartialOrder(
  nodes = {R, C, A, P, D, RouteChoice, SupplierChoice, TrialLoop, Rel, Arc},
  edges =
    R -> C, R -> A,
    C -> P, A -> D,
    A -> RouteChoice, A -> SupplierChoice,
    D -> TrialLoop, P -> TrialLoop,
    TrialLoop -> Rel, RouteChoice -> Rel, SupplierChoice -> Rel,
    Rel -> Arc
)

RouteChoice = XOR(Supervisor Review,
                  StrictPartialOrder({Quality Review, Regulatory Review}))

SupplierChoice = XOR(SilentTransition, Consult Supplier)

TrialLoop = LOOP(StrictPartialOrder(Execute Trial -> Inspect Trial),
                 Adjust Parameters)
```

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# Visible transitions
register = Transition("Register Deviation", "Register Deviation")
contain = Transition("Contain Material", "Contain Material")
analyze = Transition("Analyze Root Cause", "Analyze Root Cause")
plan = Transition("Plan Verification", "Plan Verification")
design = Transition("Design Corrective Action", "Design Corrective Action")
supervisor = Transition("Supervisor Review", "Supervisor Review")
quality = Transition("Quality Review", "Quality Review")
regulatory = Transition("Regulatory Review", "Regulatory Review")
consult = Transition("Consult Supplier", "Consult Supplier")
execute = Transition("Execute Trial", "Execute Trial")
inspect = Transition("Inspect Trial", "Inspect Trial")
adjust = Transition("Adjust Parameters", "Adjust Parameters")
release = Transition("Release Material", "Release Material")
archive = Transition("Archive Case", "Archive Case")

# Silent skip for optional supplier
skip_supplier = SilentTransition("skip_supplier")

# Approval route
high_route = StrictPartialOrder([quality, regulatory])
route_choice = OperatorPOWL(Operator.XOR, [supervisor, high_route])

# Optional supplier
supplier_choice = OperatorPOWL(Operator.XOR, [skip_supplier, consult])

# Trial loop
trial_iteration = StrictPartialOrder([execute, inspect])
trial_iteration.order.add_edge(execute, inspect)
trial_loop = OperatorPOWL(Operator.LOOP, [trial_iteration, adjust])

# Top-level strict partial order
powl = StrictPartialOrder([
    register,
    contain,
    analyze,
    plan,
    design,
    route_choice,
    supplier_choice,
    trial_loop,
    release,
    archive,
])

# Essential precedence constraints
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, route_choice)
powl.order.add_edge(analyze, supplier_choice)
powl.order.add_edge(design, trial_loop)
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(route_choice, release)
powl.order.add_edge(supplier_choice, release)
powl.order.add_edge(release, archive)
```

All intended precedence dependencies are added explicitly with `.order.add_edge(source_node, target_node)`. The only edges inside a submodel are `execute -> inspect` in the trial iteration; the high-route `StrictPartialOrder` has intentionally no edges between `Quality Review` and `Regulatory Review`.

Pairs intentionally left unconnected are concurrent:

- `Contain Material` and `Analyze Root Cause` share only the `Register Deviation` predecessor; no edge exists between them.
- `Plan Verification` and `Design Corrective Action` have no edge between them.
- The approval route and the trial loop have no edge between them, so approvals may overlap trial work.
- The supplier choice has no edge to planning, design, approvals, or the trial loop, so if selected it may overlap all of them.
- `Quality Review` and `Regulatory Review` have no edge between them, so they may complete in either order.
- In general, a pair with no directed path in the strict partial order is intentionally concurrent.

# 5. Behavioral Witnesses

Legend: `R=Register Deviation`, `C=Contain Material`, `A=Analyze Root Cause`, `P=Plan Verification`, `D=Design Corrective Action`, `S=Supervisor Review`, `Q=Quality Review`, `G=Regulatory Review`, `U=Consult Supplier`, `E=Execute Trial`, `I=Inspect Trial`, `X=Adjust Parameters`, `Rel=Release Material`, `Arc=Archive Case`.

| Trace ID | Visible trace | Intended verdict | Process-tree verdict | POWL verdict | Reason |
|----------|---------------|------------------|----------------------|--------------|--------|
| T1 | `R C A P D S E I Rel Arc` | Allowed | Allowed | Allowed | Low-risk baseline; single passing trial; supervisor approval |
| T2 | `R C A P D Q E G I Rel Arc` | Allowed | Allowed | Allowed | High-risk route; Quality and Regulatory overlap trial; no supplier |
| T3 | `R C A U P D S E I Rel Arc` | Allowed | Forbidden | Allowed | Optional supplier starts before P/D; intended overlap; process-tree approximation excludes it |
| T4 | `R C A D P Q E I X E I G Rel Arc` | Allowed | Allowed | Allowed | Two trial iterations separated by Adjust Parameters; high-risk approvals |
| T5 | `R C A P D E Q I G Rel Arc` | Allowed | Allowed | Allowed | High-risk approvals occur around/after trial work |
| F1 | `R C A D S E I P Rel Arc` | Forbidden | Forbidden | Forbidden | Earliest violation: `E` occurs before `P`, so the trial starts before the P/D join is satisfied |
| F2 | `R C A P D Q E I Rel Arc` | Forbidden | Forbidden | Forbidden | Earliest violation: at `Rel`, the selected approval route is incomplete; high route has `Q` but no `G` |
| F3 | `R C A P D S E I X Rel Arc` | Forbidden | Forbidden | Forbidden | Earliest violation: `X` occurs after the final `I` and is not followed by another `E-I` cycle; no passing Inspect Trial precedes release |

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|-------------|--------------------|--------------|------|-----------------------------------|----------------------|
| Initial work streams | `Contain Material` and `Analyze Root Cause` may overlap | First `PARALLEL` block is exact | `R -> C`, `R -> A`, no C/A edge | None | No impact |
| Split dependencies | `P` after `C`; `D` after `A`; P/D unordered | `SEQUENCE(C,P)` and `SEQUENCE(A,D)` in parallel, exact | `C -> P`, `A -> D`, no P/D edge | None | No impact |
| Risk route | Route is selected after `A`; low=S, high=Q parallel G | Route XOR is placed after the P/D join; alternatives are exact, but route start is postponed | `A -> RouteChoice`; `RouteChoice = XOR(S, StrictPartialOrder(Q,G))` | Process tree overconstraints; POWL is exact | Process tree may miss schedules where approval work begins before design/planning finish |
| Approval/trial overlap | Approvals need not finish before trial and may overlap trial | Route and trial loop are in the post-join parallel block, so overlap is possible after P/D; early overlap with P/D is excluded | No edge between `RouteChoice` and `TrialLoop` | Process tree overconstraints; POWL is exact | Process tree underestimates available concurrency and can produce pessimistic cycle-time estimates |
| Optional supplier | Optional, at most once, after `A`, before `Rel`, may overlap other work | `XOR(tau, U)` is in the post-join parallel block; optionality is exact, but start is postponed until after P/D | `A -> SupplierChoice`; `SupplierChoice -> Rel`; no edges to P/D/trial/approvals | Process tree overconstraints; POWL is exact | Process tree cannot model early supplier lead-time overlap with design/planning |
| Repeat-until trial | `E-I` repeats until a passing inspection; `X` only after failed inspections, never after final passing inspection | `LOOP(SEQUENCE(E,I), X)` is exact | `TrialLoop = LOOP(StrictPartialOrder(E->I), X)` is exact | None | Correct retrial and no-adjust-after-pass behavior |
| Release synchronization | `Rel` requires passing inspection, approval route, and selected supplier | Sequence after the post-join parallel block waits for all branches | `TrialLoop -> Rel`, `RouteChoice -> Rel`, `SupplierChoice -> Rel` | None, modulo process-tree route/supplier postponement | No early release occurs in either model |
| Duplicate-label risk | Non-repeatable activities should appear once | No duplicate visible leaves; E/I/X repeat only by loop execution | No duplicate visible transitions; E/I/X repeat only inside loop | None | No spurious repeated A/P/D/S/Q/G/U labels in mining results |

# 7. Preferred Representation and Validation Plan

The preferred canonical representation is the POWL model. The intended behavior is non-block-structured: `Plan Verification` and `Design Corrective Action` come from separate concurrent streams, join to enable the trial, while approvals and optional supplier work may overlap the trial and still synchronize at release. A `StrictPartialOrder` expresses these dependencies directly without duplicating visible activities or postponing valid concurrency. The process tree is a useful conservative approximation, but it is not the preferred representation for fidelity.

Validation plan:

1. Convert both models to accepting Petri nets using `pm4py.convert_to_petri_net(model)`.
2. Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on both converted nets. Soundness checks that each model is internally executable and terminates properly, but it does not prove fidelity to the intended dependency specification.
3. Use bounded or sampled playout with `pm4py.play_out` on both nets. Generate a large sample of complete traces and check each generated trace against the intended dependency oracle.
4. Replay the explicit positive and negative traces `T1`–`T5` and `F1`–`F3` against both converted nets. The expected verdicts are exactly those in Section 5.
5. Perform a silent-behavior and duplicate-label check. Verify that the silent skip in the supplier XOR never emits `Consult Supplier`, and verify that the structural visible label multiset contains each non-repeatable visible label exactly once, with only `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` allowed to repeat through loop execution.
6. Limitations: Petri-net conversion may introduce invisible transitions and may not preserve all POWL boundary semantics exactly; sample playout is not exhaustive; soundness does not imply conformance; and the model has no data perspective for risk class, supplier involvement, or inspection outcome.

# 8. Final Self-Critique

1. The process tree is a deliberate under-approximation. It excludes intended traces where approvals or supplier consultation begin before `Plan Verification` / `Design Corrective Action` are complete. For a stakeholder needing exact behavior, the process tree would be inadequate.
2. The POWL model assumes that partial-order edges to and from `OperatorPOWL` nodes constrain the entire nested submodel. If the PM4Py POWL implementation treats operator-boundary edges differently, the model could require adjustment or additional internal boundary events.
3. The loop abstraction cannot distinguish passing from failing inspections by label. `Inspect Trial` is always the same visible event; the model interprets the choice to execute `Adjust Parameters` as the failure signal and the choice to exit the loop as the pass signal. This is semantically appropriate for the task, but it remains an abstraction and cannot be validated from inspection-result data.
