## 2. Quantitative delay decomposition  

Notation: wait = actual start – earliest feasible start under stated counter-factual.

1. J1 batch-waiting  
   Ready 08:10, B1 cures 12:05.  
   Counter-factual: Oven cycle starts immediately at 08:10.  
   wait = 12:05–08:10 = 3 h 55 min = 235 min.

2. J2 batch-waiting  
   Ready 08:25, same batch start 12:05.  
   wait = 220 min.

3. J4 tool-driven delay (FIX-A)  
   Arrives CNC-2 09:50, could start at 09:50 if FIX-A free.  
   Actual 11:45.  
   wait = 1 h 55 min = 115 min.

4. J1 shipment-consolidation delay  
   Packed 13:30, S1 dispatch 19:25.  
   Counter-factual: dispatch as soon as job packed (ignore 0.3 h load because crate already closed).  
   wait = 5 h 55 min = 355 min.

5. J6 CAL-3 delay  
   Ready 16:05. J5 tests 16:10-16:35, CAL-3 recalibrates 16:35-17:20, J6 tests 17:25-17:50.  
   Counter-factual: test immediately after J5 without recalibration (allowed if two jobs per calibration).  
   Earliest start 16:35, actual 17:25.  
   wait = 50 min.  
   If stricter counter-factual “no calibration between jobs”, wait = 1 h 20 min.

6. Optional – J5 component-lot delay  
   L7 released 13:50, J5 could have started pre-batch prep any time after 10:20 if not quarantined.  
   Observed first post-release activity 13:55.  
   wait  3 h 35 min (illustrative).

No calculation proves causality; they only bound delays attributable to each coupling mechanism.

## 4. What flattening misses  

Job-view  
• Sees each job’s sequence; hides coupling (waiting for batch, tool, shipment).  
• Misleads: “no job is >1.8  slow” so nothing seems wrong.

Machine-view  
• Shows utilisation and gaps; hides why gaps happen (tool unavailable, rack cleaning).  
• Misleads: “machines under-used therefore not a constraint”.

Batch-view  
• Shows cure events but not the readiness dispersion that causes early jobs to wait.  
• Duplicates rack and oven resources unless integrated.

Tool-view  
• Would highlight long holds, but not present in current flattening, so delays invisible.

ComponentLot-view  
• Shows quarantine but missing links to jobs, under-states its impact.

Shipment-view  
• Shows load-dispatch quickly; hides hours that a lone packed job waits for its partner.

Low utilisation yet long waits occur because flow units (jobs) are synchronised by other resources; machines can be idle while jobs queue for a rack, a calibration, or a delayed partner.

## 5. Object-lifecycle evidence  

Narrative A (J1 – Batch – Rack – Oven – Shipment)  
Temporal: J1 ready 08:10  waits 3 h 55 m  Batch B1 cures 12:05  packed 13:30  waits 5 h 55 m  Shipment S1 dispatch 19:25.  
Feasibility: only one RACK-7, so batch cannot start earlier without another rack.  
Policy: shipments must consolidate all items to same customer.  
Causal speculation: A second rack or split shipment would cut 9 h 50 m of J1 lead time.

Narrative B (J4 – Tool – Machine – Batch – Rack)  
Temporal: J4 reaches CNC-2 09:50 but FIX-A held by J3 until 11:40  machine idle 10:05-10:47  J4 machining 11:45  joins Batch B2  rack unavailable until cleaning ends 14:35  batch start 14:50.  
Feasibility: single fixture; rack cleaning policy adds second wait.  
Speculation: duplicate fixture or staggering rack cleaning would reduce cascaded delay.

Narrative C (J6 – Tool – Machine – Shipment – Partner Job)  
Temporal: J6 ready test 16:05  waits for CAL-3 recalibration 16:35-17:20  tests 17:25-17:50  packed 18:05  waits till J5 packed 18:40 and shipment S3 dispatch 19:15.  
Policy: metrology requires calibration every 1 test; consolidation requires both jobs.  
Speculation: extend calibration interval + allow separate shipments would save ~90 min.

## 8. Falsification and additional data  

Observations that would weaken the “rack-batch synchronisation” explanation  
1. Another day where B1 starts within 15 min of first job readiness despite single rack.  
2. Evidence that rack cleaning is a fixed regulatory hold ending exactly 14:35, not a resource limit.  
3. OVEN-1 shows high utilisation on days with similar waiting – would imply other cause.  
4. Jobs not sharing a batch also show 3-4 h waits – indicates broader scheduling problem.  
5. Availability of spare rack in store but not used – suggests policy not capacity.  
6. Jobs sharing a rack but placed in different batches do not exhibit correlated delays.

Additional fields / event types that could discriminate hypotheses  
1. Rack status events (cleaning start/end, maintenance) explicitly time-stamped.  
2. Tool inventory log (fixture availability counts, calibration due date).  
3. Shipment release authorisation timestamps separate from dispatch.  
4. QC lot disposition code and override author identities.  
5. Job priority or due-date attribute to test whether dispatch rule, not resource, causes wait.  
6. Explicit “Wait for Tool/Batch/Partner” planned-queue events entered by operators.  
7. Cost accounting for freight to test impact of split shipments.  
8. Secondary oven utilisation if a second oven occasionally used (control).  
9. Environmental constraints (e.g. cure temperature ramp profiles) that limit batch start.  
10. Product genealogy linking components to customers, clarifying shipment policy drivers.

These additional signals would allow the object-centric model to separate physical constraints from scheduling or data artefacts, strengthening or falsifying each bottleneck hypothesis.
