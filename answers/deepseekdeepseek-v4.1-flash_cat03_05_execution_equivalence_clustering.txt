## 1. Equivalence design space

I use four relations. All are defined as equality of a canonical signature, so each is reflexive, symmetric, and transitive unless I explicitly weaken it.

**1. Activity-sequence equivalence.**  
Definition: for a lead `Order`, project each event to its activity label and keep the timestamp-ordered sequence. Two executions are equivalent if these label sequences are equal. Invariants: activity labels, event count per activity, rough ordering. Discarded: object types, object multiplicities, externality, O2O qualifiers, E2O incidence. Properties: equivalence relation. Concurrency: same-timestamp events are either sorted by a canonical event key for reproducibility or treated as a partial order of labels; total-order sorting can over-distinguish concurrent events.

**2. Typed structural equivalence under identifier renaming.**  
Definition: two executions are equivalent if there is a type-preserving bijection of local object identifiers such that timestamp-ordered events map activity-for-activity and object incidence maps exactly. I preserve object types, event order, E2O incidence, object multiplicities, and external-object flags. Invariants: typed event graph up to local IDs. Discarded: raw IDs, timestamps, O2O qualifiers, amounts, business intent. Properties: equivalence relation. Concurrency: use partial order induced by shared object lifetimes; if a total order is used, same-time events are sorted canonically.

**3. Business-semantic equivalence.**  
Definition: equality of a canonical signature that preserves typed E2O incidence, object multiplicities, external flags, event order or partial order, repeated activities, and O2O qualifiers/lifecycle motifs. Invariants: all structural information above plus qualifiers such as `removed_before_dispatch`, `partial_settles`, `completes_settlement`, `replaces`. Discarded: actual identifiers, exact timestamps, monetary amounts unless encoded as attributes. Properties: equivalence relation. Concurrency: Pack/Dispatch and similar events may be compared as partial order.

**4. Aggregated business-semantic equivalence.**  
Definition: like 3, but repeated payments are collapsed to a payment aggregate and repeated same-label consecutive events are collapsed when object multiplicity is not semantically relevant. Invariants: dominant lifecycle motif. Discarded: payment split and some package/delivery multiplicity. Properties: equivalence relation, but coarser and more assumption-laden.

## 2. Canonical signatures

Preferred signature: business-semantic, lead object type `Order`.

```python
def canonical_signature(ocel, lead_order):
    events = [e for e in ocel.events
              if lead_order in e.object_ids or is_reachable_from_lead(e, lead_order)]
    events = sorted(events, key=lambda e: (e.timestamp, canonical_event_key(e)))

    # First occurrence canonical IDs per object type, preserving EXT as external.
    id_map = {}
    counters = {}
    for e in events:
        for oid in e.object_ids:
            typ = ocel.object_type(oid)
            ext = str(oid).startswith("EXT")
            if oid not in id_map:
                key = (typ, ext)
                counters[key] = counters.get(key, 0) + 1
                id_map[oid] = f"{typ}{'EXT' if ext else ''}#{counters[key]}"

    event_sigs = []
    for e in events:
        slots = {}
        for oid in e.object_ids:
            typ = ocel.object_type(oid)
            ext = str(oid).startswith("EXT")
            slots.setdefault((typ, ext), []).append(id_map[oid])
        slots = {k: tuple(sorted(v)) for k, v in slots.items()}
        event_sigs.append((e.activity, tuple(sorted(slots.items()))))

    o2o_sigs = []
    for rel in ocel.o2o_relations_involving(events):
        o2o_sigs.append((
            id_map.get(rel.source, rel.source),
            rel.qualifier,
            id_map.get(rel.target, rel.target),
            rel.context
        ))

    return hash((tuple(event_sigs), tuple(sorted(o2o_sigs))))
```

For partial-order handling, replace the sorted event list with a canonical partial-order trace: event keys plus happens-before edges from shared objects. For reporting, the total-order signature above is reproducible if same-time events are sorted by event key.

## 4. Cluster interpretations

**S1 — Simple isolated full settlement: X1, X2.** Signature: one package, one delivery, one invoice, one payment, no external sharing or qualifiers. Business: clean make-pack-ship-invoice-collect flow. Risks: low; opportunities: automate straight-through processing. Traditional flattening by activity labels alone would confuse S1 with X5, X6, X7 because their label sequences are identical. Stable under identifier renaming and data repair; not stable if external sharing or replacement qualifiers are ignored.

**S2 — Split packages, consolidated delivery: X3.** Signature: two Pack events, one Dispatch carrying both packages, one payment. Business: multi-package fulfillment but one shipment and one settlement. Risks: package consolidation errors, missing package before dispatch. Opportunity: consolidate shipments. Flattening to one Pack event loses split packing. Stable if package multiplicity is preserved; unstable if same-label Pack events are collapsed and multiplicities ignored.

**S3 — Split deliveries with partial/complete payment: X4.** Signature: interleaved Pack/Dispatch pairs, two payments with `partial_settles` and `completes_settlement`. Business: incremental fulfillment and staged payment. Risks: reconciliation mismatch and delivery-payment misalignment. Opportunity: track partial fulfillments. Flattening to one delivery or one payment destroys the control point. Stable under identifier renaming; less stable if payment multiplicity is treated only as amount.

**S4 — Cross-order logistics sharing: X5.** Signature: Pack/Dispatch include `EXT-OA` and `EXT-IA`. Business: one logistics package serves multiple orders. Risks: allocation ambiguity when one order is delayed or returned. Opportunity: shared shipping cost. Flattening to lead-order-only events hides cross-order dependency. Stable only if external flags are preserved.

**S5 — Cross-order financial sharing: X6.** Signature: Invoice/Payment include `EXT-OB`. Business: one invoice/payment covers multiple orders. Risks: settlement allocation and revenue recognition errors. Opportunity: consolidated billing. Flattening to order-local finance hides shared receivables. Stable only if external flags and shared financial events are preserved.

**S6 — Replacement/removal before dispatch: X7.** Signature: Pack includes both items, Dispatch includes only `I72`, with `removed_before_dispatch` linking package to `I71`. Business: item substitution/removal after packing. Risks: wrong item shipped, inventory mismatch. Opportunity: detect substitutions early. Flattening to activity labels makes it look like S1. Stable if O2O qualifiers and Dispatch item incidence are preserved.

**S7 — Return and repack: X8.** Signature: Return, Inspect, second Pack, second Dispatch, `replaces`. Business: reverse logistics followed by repacking/reshipment. Risks: refund/shipment confusion, duplicate invoicing. Opportunity: closed-loop return analysis. Flattening to one dispatch hides the return loop. Stable if return/inspect and replacement relation are kept.

## 5. Borderline cases

**X1 vs X2.** Activity-sequence and typed-structural definitions agree: they are equivalent after renaming. A stricter raw-ID definition would separate them, but that is usually undesirable because local IDs carry no business meaning.

**X1 vs X5.** Activity-sequence equivalence groups them because labels match. Typed structural and business-semantic definitions separate them because Pack/Dispatch include external Order/Item objects. If one ignores external objects, X5 collapses into X1; if externality matters for compliance, it must not.

**X1 vs X6.** Again label-equivalent. Typed structural separates the Invoice/Payment object incidence: X6 has an extra external Order. If finance sharing is irrelevant, they merge; if settlement allocation matters, they are distinct.

**X1 vs X7.** Label-equivalent and close structurally. Typed structural can separate because X7’s Dispatch includes `Item:I72`. If E2O incidence is ignored and only activity labels are used, they merge. Business semantics strongly separates because `removed_before_dispatch` changes meaning.

**X3 vs X4.** Coarse multi-package definitions may group them: both split packing. Fine definitions separate them because X4 has two Dispatch events and two payments with partial/complete settlement. If delivery multiplicity and payment qualifiers are ignored, they may merge.

**X4 vs X8.** Both have repeated Pack/Dispatch and multiple payments/events. Fine semantics separate because X8 contains Return, Inspect, and a replacement relation. Coarse lifecycle definitions may group them as “non-linear fulfillment,” but that hides reverse logistics.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` typically builds a key for each execution from the connected OCEL substructure around a lead object. The exact key preserves activity labels, object types, E2O incidence, and often raw object identifiers or object-graph topology. Raw identifiers make exact clusters too fine because O1, O2, I11, and I22 are not business distinctions. A post-process should canonicalize IDs by type and first occurrence, preserve `EXT` as an external flag, and optionally add O2O qualifiers.

Exact equivalence is preferable when auditing object-level compliance, e.g., proving that the same package was not shared or that a specific item was replaced. Coarser business clustering is preferable for reporting and segmentation.

`max_objs` or large connected executions can cause truncation or merged giant components. If a shared package connects many orders, a lead-order-centered execution may become very large.

```python
import pm4py
from collections import defaultdict

clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=2000)

business_clusters = defaultdict(list)

for cl in clusters:
    for exec_id in cl:
        # Assume exec_id can be mapped to a lead Order; otherwise infer by lead type.
        order_id = exec_id if str(exec_id).startswith("O") else exec_id[0]
        if ocel.object_type(order_id) != "Order" or str(order_id).startswith("EXT"):
            continue
        sig = canonical_signature(ocel, order_id)   # from Section 2
        business_clusters[sig].append(order_id)

# business_clusters now groups exact PM4Py clusters by business-semantic signature.
```

## 7. Robustness analysis

**Ignore O2O qualifiers.** S6 loses `removed_before_dispatch`; if Dispatch item incidence remains, X7 still differs from X1. S7 loses `replaces` but still has Return/Inspect. X4 loses partial/complete qualifiers but still has two payments. Most preferred clusters remain, but S6 and S7 become less semantically grounded.

**Ignore external objects.** X5 and X6 collapse toward S1 because `EXT-OA`, `EXT-IA`, and `EXT-OB` disappear. X1, X2, X5, X6 become one simple cluster. X7 remains separate because of Dispatch item incidence. This is acceptable only when cross-order effects are out of scope.

**Collapse repeated same-label events.** If consecutive Pack events are collapsed and multiplicities ignored, X3 may merge with S1. X4’s two payments collapse, but its split deliveries remain. X8’s repeated Pack/Dispatch are not consecutive, so it remains distinct. This perturbation is dangerous for fulfillment multiplicity.

**Treat Pack/Dispatch order as partial order.** X4’s interleaving `Pack, Dispatch, Pack, Dispatch` becomes less distinctive; only the dependency `P41 before D41` and `P42 before D42` remains. X3 still has both packs before one dispatch. If delivery multiplicity is also ignored, X3 and X4 may merge.

**Payment multiplicity as amount attribute.** X4’s two payments become one payment object with amount, so X4 may look closer to X3 if delivery splitting is also ignored. If split delivery is preserved, X4 remains distinct.

## 8. Limitations and recommendation

For **compliance monitoring**, use business-semantic equivalence with qualifiers and externality. Replacement, return, and cross-order sharing are control-relevant.

For **operational segmentation**, use a slightly coarser business-semantic clustering: S1, S2/S3, S4, S5, S6, S7. Exact typed structure may be too brittle.

For **root-cause analysis**, use the finest typed-structural or business-semantic equivalence. Keep external objects, O2O qualifiers, item/package incidence, and payment multiplicity.

For **descriptive reporting**, use activity-sequence or aggregated business-semantic clusters. Raw IDs and exact order rarely help executives.

No single equivalence notion is best because compliance needs qualifiers, operations needs stable motifs, root-cause needs detail, and reporting needs compression. The recommended default is business-semantic equivalence with explicit flags for externality and O2O qualifiers, plus configurable collapsing of repeated payments or same-label events only when the business question allows it.
