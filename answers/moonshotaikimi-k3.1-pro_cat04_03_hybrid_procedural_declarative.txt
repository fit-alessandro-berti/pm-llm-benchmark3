# 1. Policy Interpretation and Conflict Resolution

**Material assumptions**

- R1–R11 are treated as hard requirements. In particular, “should” in R2 and R8 is interpreted as mandatory. R12 alone produces warnings rather than automatic rejection.
- The test traces are complete cases. For an ongoing case, an eventual obligation such as R4 is **pending**, not yet a violation, unless a blocking outcome occurs or a stated deadline expires.
- An accepted case contains `Activate Vendor`; a rejected case contains `Reject Vendor`. For R3, `Activate Vendor` and `Reject Vendor` are final outcomes that cannot occur while a clarification is outstanding. `Close Onboarding` is also blocked as a final safeguard.
- The applicable approval is `Manager Approval` on the low-risk route and `Compliance Approval` on the high-risk route. If both or neither occur, the procedural model is already violated; resource checks cannot repair that violation.
- The procedural model below is a **single-pass core model**. Conformance for the test cases is evaluated on its explicit backbone projection, while the original events remain available to the other layers. A procedural pass is therefore not a claim of complete compliance.
- Hours in the test cases are elapsed hours. Temporal-profile matching uses the clarification response matched by the R3 protocol, the first subsequent legal opinion satisfying an escalation’s response obligation, and the first payment following activation.
- The visible log has resources, but it has no verifiable emergency authorization. A missing resource or authorization must never be interpreted as evidence that a control was satisfied.

**R5/R6 conflict**

The policies conflict when activation follows sanctions escalation but precedes the required post-escalation legal opinion.

1. **Strict legal-first resolution:** R5 prevails. After escalation, activation requires an intervening legal opinion. R6 cannot override R5; it may be withdrawn, separately narrowed, or handled outside this process. This is the resolution implemented below.
2. **Guarded emergency-exception resolution:** R5 is deliberately rewritten as “legal opinion before activation, **unless** a verifiable joint emergency authorization existed before activation.” Under that different policy version, R6 permits early activation only with that authorization and an opinion within 24 hours. This is not the conjunction of the original R5 and R6; it is an explicit exception to R5.
3. A dual-view deployment could evaluate both policy versions for management review, but must not combine their results into an unqualified pass.

I choose **strict legal-first** because the log cannot establish the R6 authorization. Its compliance risk is that it can block, or report as noncompliant, an emergency that Operations and Legal actually intended to permit. Conversely, enabling R6 without authoritative external evidence would create the more serious risk of treating an unauthorized sanctions-related activation as compliant merely because an opinion arrived within 24 hours.

# 3. Procedural Backbone

Let `;` denote sequence, `` parallel composition, and `` exclusive choice. The canonical core is:

```text
Receive Onboarding Request ;
(Capture Master Data  Run Sanctions Screening  Verify Bank Account) ;
Classify Risk ;
(
    (Reject Vendor ; Close Onboarding)
   (Manager Approval ; Activate Vendor ; Release First Payment ; Close Onboarding)
   (Enhanced Due Diligence ; Compliance Approval ;
     Activate Vendor ; Release First Payment ; Close Onboarding)
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    return ProcessTree(label=label)


def node(operator, *children):
    tree = ProcessTree(operator=operator)
    for child in children:
        child.parent = tree
        tree.children.append(child)
    return tree


def sequence(*children):
    return node(Operator.SEQUENCE, *children)


checks = node(
    Operator.PARALLEL,
    leaf("Capture Master Data"),
    leaf("Run Sanctions Screening"),
    leaf("Verify Bank Account"),
)

rejected = sequence(
    leaf("Reject Vendor"),
    leaf("Close Onboarding"),
)

low_risk_accepted = sequence(
    leaf("Manager Approval"),
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding"),
)

high_risk_accepted = sequence(
    leaf("Enhanced Due Diligence"),
    leaf("Compliance Approval"),
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding"),
)

outcome = node(
    Operator.XOR,
    rejected,
    low_risk_accepted,
    high_risk_accepted,
)

procedural_model = sequence(
    leaf("Receive Onboarding Request"),
    checks,
    leaf("Classify Risk"),
    outcome,
)
```

- **Concurrency:** The parallel join permits every ordering of the three checks, but `Classify Risk` cannot start until all three have completed.
- **Choices and approvals:** The XOR gives exactly one primary outcome. The accepted branches encode the applicable approval and R2/R8 route exclusions without relying on resource or risk-data guesses.
- **Terminal outcomes:** Rejection leads directly to closure. Both acceptance branches require activation, then first payment, then closure.
- **Clarifications:** There is no hidden clarification-loop approximation. Arbitrarily interleaved clarification cycles are deliberately handled by R3’s external state machine and the DECLARE necessary condition. Putting a loop at only one tree location would incorrectly restrict where clarification may occur.
- **Escalation and legal opinions:** These are also outside the block-structured core because they may interleave with the high-risk route. R4, R5, R6, and R7 govern them.
- **Post-activation behavior:** `Change Bank Details`, `Suspend Vendor`, and R11 re-verification are excluded from this single-pass tree. An R11-enabled deployment needs a scope-aware core/extension composition or a Petri-net extension; blindly feeding an additional required verification into this tree would produce a false core violation.
- For the supplied tests, procedural conformance means aligning the projection onto the twelve backbone activities. The six cross-cutting labels are evaluated elsewhere, not discarded from the overall decision.

# 4. DECLARE Model

```python
def _rule():
    return {"support": 1.0, "confidence": 1.0}


declare_model = {
    "init": {
        "Receive Onboarding Request": _rule(),
    },
    "altresponse": {
        ("Request Clarification", "Receive Clarification"): _rule(),
    },
    "response": {
        ("Sanctions Escalation", "Obtain Legal Opinion"): _rule(),
    },
    "precedence": {
        ("Run Sanctions Screening", "Sanctions Escalation"): _rule(),
    },
    "noncoexistence": {
        ("Reject Vendor", "Activate Vendor"): _rule(),
        ("Manager Approval", "Compliance Approval"): _rule(),
        ("Enhanced Due Diligence", "Manager Approval"): _rule(),
        ("Reject Vendor", "Manager Approval"): _rule(),
        ("Reject Vendor", "Compliance Approval"): _rule(),
    },
}
```

| Rule | Direction and exact intended semantics |
|---|---|
| `init: Receive Onboarding Request` | The first logged activity of a case must be receipt of the request |
| `altresponse(Request Clarification, Receive Clarification)` | Every request needs a later response, and another request cannot occur before the preceding request has been answered. It does **not** require immediate adjacency |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | Every escalation requires an eventual later opinion. Other activities, including activation in the DECLARE layer alone, may intervene |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | An escalation is permitted only if screening occurred earlier. Screening need not lead to escalation |
| `noncoexistence(Reject Vendor, Activate Vendor)` | The two activities cannot both occur anywhere in the case, in either order |
| `noncoexistence(Manager Approval, Compliance Approval)` | The two approvals cannot co-occur; this alone does not require either one |
| `noncoexistence(Enhanced Due Diligence, Manager Approval)` | The high-risk diligence activity and low-risk approval cannot co-occur |
| `noncoexistence(Reject Vendor, Manager Approval)` | Once a case is rejected, the presence of Manager Approval anywhere in that case violates R2, even if the approval happened first |
| `noncoexistence(Reject Vendor, Compliance Approval)` | The corresponding prohibition for Compliance Approval |

`response(A,B)` looks forward from `A`; `precedence(A,B)` looks backward from `B`. `altresponse` is weaker than `chainresponse`, which would require the response to be the immediately following event. `noncoexistence(A,B)` is also stronger and more symmetric for these safety rules than `nonsuccession(A,B)`, which concerns later succession and could miss the reverse order.

The model deliberately omits a naive legal-opinion/activation precedence rule, an unconditional bank-change response, and any claim that noncoexistence implements accepted-case XOR.

```python
log_skeleton = {

    "always_before": {

        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1},
    },
    "directly_follows": set(),
}
```

For `always_before`, `(A,B)` means **A before B**, not immediate succession. The entries encode the initial receipt/join ordering; they do not impose an order among the three concurrent checks. `always_after` is empty rather than duplicating the same constraints in reverse orientation. `never_together` is symmetric, so tuple order there has no directional meaning.

The skeleton is intentionally weaker than the combined policy:

- It duplicates R1, R2/R8 safety prohibitions, and R10, but does not express accepted-case approval XOR, clarification responses, legal ordering, resources, or post-activation change obligations.
- `directly_follows` is empty because backbone sequence does not imply full-log adjacency: clarifications, escalation, and legal opinions may intervene.
- `equivalence` is empty because route-dependent counts and repeated clarification or re-verification make count-equality claims unsafe.
- No exactly-once frequency is assigned to `Verify Bank Account`; doing so would conflict with R11’s possible second verification.

# 6. Temporal Profile

```python
HOUR = 3600

temporal_profile = {
    ("Request Clarification", "Receive Clarification"):
        (48 * HOUR, 24 * HOUR),       # (172800, 86400)
    ("Sanctions Escalation", "Obtain Legal Opinion"):
        (12 * HOUR, 6 * HOUR),        # (43200, 21600)
    ("Activate Vendor", "Release First Payment"):
        (72 * HOUR, 36 * HOUR),       # (259200, 129600)
}

zeta = 2.0
```

For a completed pair with elapsed time \(d\), a deviation is flagged when:

\[
|d-\text{mean}| > 2.0 \times \text{standard deviation}.
\]

The resulting approximate two-sided limits are 0–96 hours for clarification, 0–24 hours for escalation-to-opinion, and 0–144 hours for activation-to-payment. A missing target does not create a duration and must not be treated as temporal compliance with the underlying obligation.

These are warning profiles because R12 explicitly says not to reject automatically. They are not service-level deadlines, proof of legal compliance, or substitutes for R3–R6. In particular, R6’s 24-hour requirement is a separate hard condition when the emergency policy is enabled.

# 7. Resource- and Data-Aware Checks

The following executable-style pseudocode assumes each case is a timestamp-ordered list of dictionaries with `activity`, `hour`, and, where applicable, `resource`. Event index is used to break equal-timestamp ties.

```python
FINAL_OUTCOMES = {
    "Reject Vendor",
    "Activate Vendor",
    "Close Onboarding",
}


def clarification_guard(events):
    """Exact R3 companion to DECLARE altresponse."""
    pending_request = None

    for i, event in enumerate(events):
        activity = event["activity"]

        if activity == "Request Clarification":
            if pending_request is not None:
                return [("fail", i, "second request before response")]
            pending_request = i

        elif activity == "Receive Clarification":
            if pending_request is not None:
                pending_request = None
            # An unsolicited response is not prohibited by R3 itself.

        if activity in FINAL_OUTCOMES and pending_request is not None:
            return [("fail", i, "final outcome with unanswered clarification")]

    if pending_request is not None:
        return [("fail", pending_request, "response missing at case end")]
    return []


def bank_change_guard(events, completed_case=True):
    """R11; indices are occurrence-level, not merely activity-level."""
    activations = [i for i, e in enumerate(events)
                   if e["activity"] == "Activate Vendor"]
    if not activations:
        return []

    first_activation = activations[0]
    changes = [i for i, e in enumerate(events)
               if e["activity"] == "Change Bank Details"
               and i > first_activation]
    suspensions = [i for i, e in enumerate(events)
                   if e["activity"] == "Suspend Vendor"]
    verifications = [i for i, e in enumerate(events)
                     if e["activity"] == "Verify Bank Account"]
    payments = [i for i, e in enumerate(events)
                if e["activity"] == "Release First Payment"]

    findings = []
    for change in changes:
        if completed_case and not any(s > change for s in suspensions):
            findings.append(
                ("fail", change, "no eventual Suspend Vendor")
            )
        # For an ongoing case, the missing suspension is pending, not yet final.

        for payment in payments:
            if payment > change and not any(
                    change < v < payment for v in verifications):
                findings.append(
                    ("fail", payment,
                     "no post-change Verify Bank Account before payment")
                )
    return findings


def compare_resources(left, right, rule, findings):
    left_resource = left.get("resource")
    right_resource = right.get("resource")

    if not left_resource or not right_resource:
        findings.append(("not evaluated", rule, "missing resource"))
    elif left_resource == right_resource:
        findings.append(("fail", rule, "same resource"))


def segregation_of_duties_guard(events):
    findings = []

    verifications = [e for e in events
                     if e["activity"] == "Verify Bank Account"]
    approvals = [e for e in events
                 if e["activity"] in {
                     "Manager Approval", "Compliance Approval"
                 }]

    # A valid core trace has exactly one applicable approval. If an invalid
    # trace has more, checking all is conservative and cannot hide a conflict.
    for verification in verifications:
        for approval in approvals:
            compare_resources(
                verification, approval, "R9 verify/approval", findings
            )

    captures = [e for e in events
                if e["activity"] == "Capture Master Data"]
    activations = [e for e in events
                   if e["activity"] == "Activate Vendor"]

    for capture in captures:
        for activation in activations:
            compare_resources(
                capture, activation, "R9 capture/activation", findings
            )

    return findings


def valid_emergency_authorization(auth, case_id, activation_hour):
    if auth is None:
        return False
    approvers = auth.get("approver_ids", [])
    return (
        auth.get("case_id") == case_id
        and auth.get("jointly_authorized") is True
        and len(set(approvers)) >= 2
        and auth.get("authorized_at_hour") is not None
        and auth["authorized_at_hour"] <= activation_hour
        and auth.get("scope") == "Activate Vendor"
    )


def legal_activation_guard(events, case_id, mode="legal_first", auth=None):
    """R5, or the explicitly versioned R6 exception. R4 is checked separately."""
    escalations = [i for i, e in enumerate(events)
                   if e["activity"] == "Sanctions Escalation"]
    activations = [i for i, e in enumerate(events)
                   if e["activity"] == "Activate Vendor"]
    opinions = [i for i, e in enumerate(events)
                if e["activity"] == "Obtain Legal Opinion"]

    if not escalations or not activations:
        return "pass"  # R5 not triggered; R4 may still apply

    activation = activations[0]  # Additional activations violate R10 separately
    prior_escalations = [e for e in escalations if e < activation]
    if not prior_escalations:
        return "pass"

    escalation = prior_escalations[-1]
    if any(escalation < opinion < activation for opinion in opinions):
        return "pass"

    # Activation happened without the required intervening opinion.
    if mode == "legal_first":
        return "fail"

    assert mode == "emergency_exception"
    later_opinions = [o for o in opinions if o > activation]
    if not later_opinions:
        return "fail"  # On a completed case; otherwise the obligation is pending

    opinion = later_opinions[0]
    elapsed = events[opinion]["hour"] - events[activation]["hour"]
    if elapsed > 24:
        return "fail"

    if auth is None:
        return "policy-dependent"  # Unverifiable; never an automatic pass

    if not valid_emergency_authorization(
            auth, case_id, events[activation]["hour"]):
        return "fail"
    return "pass"
```

`pm4py.filter_four_eyes_principle(...)` can provide an additional diagnostic for a selected verification/approval pair, but it does not select the applicable route, perform the capture/activation comparison, or define missing-resource behavior.

| Required information | Used by | Behavior when missing |
|---|---|---|
| Case ID and activity name | All case-level checks | Quarantine the event/case as a data error; do not guess case membership |
| Reliable event order and timestamps | Ordering, R5/R6, R11, temporal profile | Sequence-only checks may remain possible if order is trustworthy; durations and the 24-hour rule are `not evaluated` |
| `org:resource` on events involved in an applicable R9 comparison | Both segregation-of-duties checks | Return `not evaluated` and block an unqualified overall pass; missing resources are not treated as different |
| External authorization record: case ID, joint-approval evidence, distinct approvers, authorization time, and scope | R6 emergency exception | Irrelevant under strict legal-first; under emergency mode, early activation is unverifiable and must be manually reviewed or failed closed |
| Actual risk classification and authorization context | Validating route appropriateness beyond activity order | Record a blind spot; activity conformance alone cannot prove that a high-risk vendor was not incorrectly sent through the low-risk route |

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement:** R1, R2/R8, and R10 intentionally appear in more than one layer. This improves diagnostics and protects against projection mistakes, but the layers are not independent votes. T8 has one underlying contradictory-outcome problem even though several constraints report it.
- **Layer disagreement is informative:** T4’s procedural pass and resource failure, T5’s projected-core pass and R3 failure, and T6’s DECLARE pass and strict-R5 failure are expected consequences of different expressive power. They must not be “resolved” by majority voting.
- **Loops and occurrence counts:** A exactly-once frequency for `Verify Bank Account` would contradict R11’s required re-verification. Likewise, applying the single-pass core to an extended bank-change history can falsely reject valid behavior. The core and extension need explicit scope boundaries.
- **Repeated-event ordering:** `always_before` and simple precedence are insufficient for R11. The initial verification is before every payment in the supplied traces, but only a verification **after the relevant bank change** can release a later payment.
- **Post-payment scope:** R10 permits only one first payment. If a bank change occurs after that payment, R11’s suspension obligation still applies, but its “later payment” condition may be vacuous within this onboarding model. Allowing further payment cycles would require a broader process scope, not an unexamined relaxation of R10.
- **Vacuity:** Response and precedence rules pass when their triggering activity is absent; noncoexistence passes when neither activity occurs; and `altresponse` passes in cases with no clarification. Noncoexistence also cannot distinguish “exactly one approval” from “no approval.” Temporal `not evaluated` is not evidence of compliance.
- **Eventual obligations in open cases:** Missing legal opinions, clarification responses, or suspensions may be pending rather than violated. Final outcomes and case-completion status matter.
- **Missing case attributes:** The log does not establish the real risk score, whether the selected route matches that score, emergency status, joint authorization, jurisdiction-specific legal requirements, or the adequacy of bank-verification evidence.
- **Timestamp-only limitations:** Durations depend on timestamp quality, time zones, calendars, and pair matching. Equal timestamps need a tie-breaking rule. A timestamp-ordered log also does not disprove that the initial checks were concurrent. Most importantly, timing cannot prove external authorization.
- **Metadata is not normative truth:** The `support = 1.0` and `confidence = 1.0` values are manually supplied conformance metadata, not measurements from T1–T8. A rare emergency rule can be mandatory despite low observed support, while a frequently observed pattern can still violate policy. These models should not be discovered from the test traces and then treated as authoritative merely because they fit them.

# 10. Deployment Recommendation

1. **Canonical procedural representation:** Version the ProcessTree as the single-pass onboarding core. It may be converted to an accepting Petri net for alignment, but the conversion should not silently add clarification, escalation, or post-activation loops. Maintain an explicit registry of cross-cutting activities and scope-aware projection rules.
2. **Authoritative policy bundle:** Deploy the core together with the DECLARE model, Log Skeleton, temporal profile, and external guards under one policy version. The implemented version should record `legal_first` explicitly. Enabling `emergency_exception` requires a separately approved policy version and an authorization-store integration.
3. **Check order:**
   - Validate case identity, activity names, timestamps, required resources, and policy version.
   - Run the procedural core check and inexpensive hard occurrence checks.
   - At decision points, run the hard external guards: pending clarification before activation/rejection, applicable approval and SoD before activation, strict R5 or the authorized R6 exception, and R11 before payment.
   - On completed cases, evaluate remaining eventual obligations, DECLARE, and Log Skeleton constraints. Continue best-effort diagnostics after a failure, but never let later passes erase it.
   - Evaluate temporal profiles last and attach them as warnings. Missing or unevaluable hard evidence must not be converted into a pass.
4. **Overall decision rule:** Any authoritative hard failure gives `fail`. Otherwise, an unevaluated required control blocks an unqualified pass and goes to manual review. If all hard controls pass but a temporal profile deviates, the result is `warning`; otherwise it is `pass`.
5. **Surface contradictions explicitly:** Show the rule ID, authoritative layer, policy version, event indices, timestamps, resources, and earliest decisive event. For example:
   - T4: “Core pass; R9 fail at Manager Approval, Cora/Cora.”
   - T6: “Core and R4 pass; strict R5 fail at activation; R6 exception not active.” Under the alternative policy, separately show “authorization unverifiable; opinion delay 10 hours.”
   - T7: “All hard controls pass; temporal warning, 34 hours versus 24-hour profile boundary.”
   - T8: “Contradictory terminal outcomes at rejection; procedural, DECLARE, and skeleton findings shown as related diagnostics.”

This presentation prevents a procedural or temporal pass from being mistaken for end-to-end compliance and keeps unresolved policy or missing-evidence conditions visible to users.
