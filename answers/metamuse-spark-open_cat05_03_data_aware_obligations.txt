## 1. Temporal Data Semantics

**State reconstruction:** Reconstruct case state as a bi-temporal event-sourced state vector `S(e) = (amount, risk_level, jurisdiction, customer_type)` at each event `e`. `S(e)` = `S(prev_e)` overridden by any non-blank cells of `e`. Blank = no-update / no-information, never interpreted as `NULL`/`delete`. Initial unknown = ``. Values persist until explicitly overridden (forward-fill within case, never backward-fill).

**Handling blanks:** All events other than `Create_Transaction` / `Update_*` / `Risk_Reclassify` typically have all attribute cells blank. They do not reset state. `Release_Funds` payload omitted does **not** mean amount is null; it means `S(release) = S(last_update_before_release)`.

**Ordering equal timestamps:** Total order is `(time:timestamp, event_index)`. `event_index` is authoritative tie-breaker within a millisecond/timestamp. Consequence: In TX-311 `Enhanced_Review (idx3) < Update_Jurisdiction (idx4)` at `16:20:00Z`; any obligation evaluated after `16:20:00Z` sees `jurisdiction=DE` and sees latest review occurring *before* latest material change.

**Material change identification:** A material data change for R1/R4 = `Update_Amount`, `Update_Jurisdiction`, `Update_Customer_Type`, `Risk_Reclassify`, or `Create_Transaction` where the attribute's effective value changes. Amount increase ` = (new-old)/old`. R4 only declares an increase `>20%` as invalidating; decrease never invalidates; `old=`  `` undefined and R4 not safely classifiable as compliant/non-compliant on amount grounds alone.

**Final attributes:** Case-final attributes (e.g. `Settlement_Confirmed 150,000` on TX-305 next day) are **not** the value that governed earlier events. Evaluating `Release_Funds @11:30` using `Settlement @08:00+1d` is retroactive leakage unless there is immutable evidence linking the two payloads.

**Distinguish four times:**
- `event_time` (= `time:timestamp` + `event_index`) – when fact occurred in business process; governing time for `S(e)` and for R1-R3 triggers.
- `effective_time` – when exemption / list / rule claims to be effective from (e.g. `EX-77 effective 09:00`). Must be ` obligation_trigger_time` but alone proves nothing about existence.
- `record_time` – when exemption row is inserted in `Record_Exemption` (`TX-302 11:00`, `TX-310 11:00`). Late `record_time` > `release_time` does not automatically invalidate; it defers to evidence time.
- `evidence_time` – when existence of approval can be cryptographically / independently corroborated: qualified signature timestamp, certificate validity window, hash, witness credibility, outage documentation. Per R5 a displayed `effective_from` field without corroborating `evidence_time  release_time` is inconclusive. A late `record_time` *can* be justified by outage + qualified signature at `09:05` (EX-77) but not by certificate created at `10:30` for document purporting `08:50` (EX-88).

Obligation evaluation: snapshot `S(release)` + latest qualifying control events with `event_time < release_time`, subject to invalidation by any material change with `review_time < change_time < release_time` and `>20%`.

## 4. Ambiguities and Alternative Readings

**General principle:** There is no single canonical answer where evidence is late, missing or contradictory. Classification hinges on whether you require cryptographic `evidence_time  release_time` (R5 strict) and whether you evaluate triggers on `S(release)` only vs. any historical triggering state.

- **TX-302 – Late record vs. timely approval:** 
  - *Our reading (COMPLIANT):* Qualified signature `09:05` + outage doc proves approval existed before `Release 09:40` despite `record 11:00`. Rule explicitly says late DB record *can* be evidence of earlier approval.
  - *What would change result:* If policy required `record_time < release_time` strictly, this would be `NONCOMPLIANT` or `INDETERMINATE` (unrecorded exemption). If `Enhanced_Review` were deemed insufficient (e.g., scope question), outcome would downgrade to `JUSTIFIED_EXCEPTION` via EX-77 still holding. No change with current strong evidence.

- **TX-305 – Missing amount / settlement bridging (INDETERMINATE):**
  - *Our reading:* `amount=` at release  R1 trigger cannot be established per R6; settlement `150k` next day is reliable at settlement time but no immutable link to release payload per semantic fact; ` from unknown not safely classifiable`  INDETERMINATE.
  - *Alternative that would change result to NONCOMPLIANT:* If additional evidence resolved that `settlement amount = release amount` immutably (e.g., signed payment message, monotonic ledger hash, or review document explicitly referencing 150k), then `S(release)=150k 100k` + `CADE`  R1 triggered, `Enhanced_Review @11:15` with no amount unverifiable  `ValidReview` fails  NONCOMPLIANT (HIGH severity). Conversely, if evidence proved amount at release was, say, `50k`, case would become COMPLIANT. Logging fix (immutable payload) is required to make determinate.

- **TX-310 – Post-hoc exemption with backdated field (EX-88):**
  - *Our reading (NONCOMPLIANT):* PDF displayed `08:50` is contradicted by qualified cert `10:30` > `Release 10:00`; witness is interested party  insufficient per R5 last bullet.
  - *What would change result:* 
    1. `JUSTIFIED_EXCEPTION` if organization accepts oral approval doctrine and treats requester's witness as sufficient under local law – then `effective 08:00 10:00` would waive R1.
    2. `INDETERMINATE` if adjudicator treats conflicting evidence (displayed date vs cert creation) as equipoise requiring external verification (CA log, HSM audit). The distinction between `displayed field` and `cryptographic evidence_time` is decisive here vs TX-302 where they align.

- **TX-311 – Same-timestamp ordering & jurisdiction change:**
  - *Our reading (COMPLIANT per S(release)=DE):* R1 evaluated at release using latest known jurisdiction. `16:20 idx4  DE` removes foreign condition; material change after review does not create obligation.

Our confidence Medium reflects this interpretive dependence; stating the `event_index` consequence as required discloses it.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Conditional activation (data guards):** DECLARE `Response(Enhanced_Review, Release_Funds)` or model-based fitness checks fire for every trace, but R1/R2/R3 only fire when `jurisdictionDE  amount100k`, `risk=HIGHPEP`, or `list_update after screen`. Pure control flow yields false positives on TX-307-DE or TX-303-LOW cases and cannot distinguish TX-301 (triggered) from a domestic 80k release that legitimately needs no review.

2. **Final-state leakage / retrospective snapshot:** Standard conformance often enriches events with final case attributes (e.g., settlement amount 150k). Replaying with `amount=150k` at `TX-305 Release 11:30` fabricates a trigger that did not exist in `S(release)=`. Forward-fill-with-no-lookahead is required; model-based replay lacks temporal data scoping.

3. **Post-hoc exemptions / evidence-time vs. record-time:** Control flow sees `Record_Exemption 11:00` after `Release 09:40` as violation of `Precedence(Exemption,Release)` for both TX-302 and TX-310. It cannot differentiate qualified signature `09:05` (strong evidence timely) from cert `10:30` post-dating release (invalid backdate, R5). Both would be mis-classified without `evidence_time  trigger_time` checks.

4. **Material changes after review (R4 invalidation):** `Enhanced 14:20 < Release 14:30` satisfies precedence, so TX-309 looks compliant to a DECLARE checker, yet R4 invalidates the review when `118k145k +22.9%` occurs at `15:28` inside `(Enhanced,Release)`. Conversely TX-308 `decrease 140k100k` should *not* invalidate – a rule every change invalidates would mis-fire. Control flow lacks quantitative effect.

5. **Missing data  low risk (R6 indeterminacy):** Fitness-based techniques typically treat absent amount as not-triggered (implicit closed-world). R6 mandates `INDETERMINATE` when decisive attribute is `` (TX-305). Control-flow-only conflates `unknown` with `0 / LOW / DE`, producing over-confident COMPLIANT verdicts.

6. **Same-timestamp ordering (`event_index`):** Collapsing to timestamp granularity makes `Enhanced 16:20 idx3` and `Update_Jurisdiction 16:20 idx4` concurrent; standard mining assumes arbitrary or parallel semantics. Whether `S(release)=DE` (no R1 obligation) or `S(release)=US` (obligation) hinges on tie-breaker – invisible to control-flow discovery, yet decisive for TX-311.

*Additional:* **Sanctions rescreening (R3)** requires correlating `Sanctions_Screen` vs. `Sanctions_List_Update` *content* (XZ added) and time ordering `screen < list_update < release`; no activity ordering alone captures jurisdiction-specific list membership. **Approval scope** (standard-only packet `TX-307`) requires understanding what the `Compliance_Approve` reviewed – not just that it happened.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payload + hashing:** Log `Release_Funds` with immutable, signed snapshot of decisive attributes `amount, jurisdiction, risk_level, customer_type, rule_version` and hash (e.g., `release_payload_hash`). Prevents settlement-price leakage and enables after-the-fact verification without backward fill (fixes TX-305).

2. **Separate effective / record / evidence / signature timestamps:** For every exemption and data update store: `effective_from`, `record_time`, `signature_time`, `certificate_validity_window`, `signer_id`. Reject displayed backdates where `cert_creation > signature_time` (would have caught EX-88).

3. **Typed attribute updates with provenance:** Replace generic `Update_*` notes with machine-readable `old_value, new_value, change_reason, source_system, changed_by`. Enables automated `>20%` calculation and audit of material vs. non-material changes; log `Standard_Review` scope explicitly.

4. **Rule version and scope pinning:** Attach `policy_rule_version` to every decision event. Scope of exemption should be structured fields `jurisdiction_scope[], cust_scope[], amount_min/max, waived_rules[]` not free text – enables automated `ScopeMatches` checks for R5.

5. **Stable global ordering:** Enforce monotonic `event_id` / `event_index` even when timestamps collide; persist `event_index` as primary sort key and never rely on ingest order. Document that `event_time = (timestamp,event_index)` is authoritative for all ordering constraints (addresses TX-311 ambiguity).

6. **Explicit review packet linkage:** `Compliance_Approve` must reference `review_id` it approves (`approves_enhanced_review_id`) and checklist version; a standard-only approval cannot be mistaken for R2 compliance.

7. **Missing-data explicitness:** Require `amount_source_status  {provided, pending, unavailable}`; distinguish `=unknown` from `0`. Block `Release_Funds` when decisive fields are unavailable or force `INDETERMINATE` workflow with four-eyes override – prevents silent low-risk default (R6).

8. **Sanctions feed versioning:** Log `Sanctions_Screen` with `list_version` checked and `list_update` events with `added_jurisdictions[]`. Automate R3: any `list_version` bump adding current jurisdiction without intervening screen blocks release.

9. **Exemption lifecycle controls:** Require Head_Compliance qualified signature *before* `effective_from`; system should not allow `Release_Funds` referencing exemption whose `evidence_time > now()` or whose scope mismatches `S(release)`; pre-register exemptions prior to use where possible.

10. **Case state reconstruction view:** Provide derived, queryable table `case_state_at_event` (forward-filled) for auditors – never expose final-state snapshot as if it governed earlier events.
