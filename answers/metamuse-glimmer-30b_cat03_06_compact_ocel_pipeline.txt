## 3. Data-model audit
Object type  objects
* Order: O100, O200
* Item: I1, I2, I3
* Package: P1, P2
* Delivery: D1, D2
* Invoice: V1
* Payment: M1, M2

O2O qualifier cardinality
* contains: 3
* packs: 3
* carries: 2
* bills: 2
* partially_settles: 2

Activity  touched object types
* Create Order  Order
* Add Item  Order, Item
* Reserve Stock  Order, Item
* Pack Package  Package, Item, Order
* Dispatch Package  Package, Delivery
* Issue Invoice  Invoice, Order
* Record Payment  Payment, Invoice
* Confirm Delivery  Delivery
* Close Order  Order

Consequential events: e6 Reserve Stock, e7 Pack Package P1, e11 Issue Invoice. They relate to objects from both orders, causing convergence in Order and Invoice views and divergence in Package/Delivery views.

## 4. Expected flattened behavior
Order O100: Create Order  Add Item I1  Add Item I2  Reserve Stock  Pack Package P1  Issue Invoice  Close Order. e6 and e7 are copied into O200 trace as well. Pack Package P2 is absent from O100 direct view; dispatch events are absent unless propagated via O2O. Trace is artificially linear because shared events appear in both cases.

Order O200: Create Order  Add Item I3  Reserve Stock  Pack Package P1  Issue Invoice  Close Order. Same shared events as O100.

Package P1: Pack Package  Dispatch Package. Clean two-step trace. Package P2: Pack Package  Dispatch Package.

Delivery D1: Dispatch Package  Confirm Delivery. Delivery D2: Dispatch Package  Confirm Delivery.

Invoice V1: Issue Invoice  Record Payment M1  Record Payment M2. Both orders are collapsed into one case.

Flattening on Payment is weak: M1 and M2 each have a single event Record Payment, no start/end, no ordering beyond the invoice. The payment process is invisible; only the amount attribute remains.

## 5. Expected object-centric structures
* OC-DFG: shows Create Order  Add Item  Reserve Stock  Pack Package with Order, Item, Package co-occurring. Pack Package P1 connects O100 and O200, revealing shared packaging. Issue Invoice connects to both orders and later to payments.
* OTG: Order connected to Item via contains, to Package via Pack events, to Invoice via bills, to Delivery indirectly via Package. Package connects to Item and Delivery. Invoice connects to Order and Payment.
* ET-OT: Create Order maps to Order only; Reserve Stock and Pack Package map to Order+Item+Package; Issue Invoice maps to Invoice+Order; Record Payment maps to Payment+Invoice.
* Object-centric Petri net: models concurrent flows for orders, packaging and invoicing. P1 creates a synchronization between O100 and O200. V1 synchronizes the two orders for billing and for two partial payments M1, M2.
* Object-interactions summary: high interaction between Order-Item, Order-Package, Invoice-Order, Invoice-Payment. P1 is the hub linking O100, O200, I1, I3. V1 is the hub linking O100, O200, M1, M2.

## 6. Modeling alternatives
* Source-minimal E2O: only objects directly mentioned in the source system. Reduces relation inflation, keeps flattening faithful to source, but hides analytical reachability e.g., Dispatch not linked to Order.
* Full operational involvement: add direct E2O links from Pack/Dispatch/Confirm to Orders/Items via O2O. Makes flattened Order logs richer and more complete, but blurs source vs inferred facts.
* Analytical propagation only: keep relations source-minimal and rely on PM4Py flattening with O2O propagation enabled. Preserves source integrity while still allowing indirect reachability in discovery.

## 7. Failure modes
* Relation inflation from over-linking every downstream event to all related orders.
* Missing direct E2O links for shared events leading to loss of convergence in flattened views.
* Treating O2O propagation as observation, i.e., materialising inferred E2O rows as facts.
* Duplicate shared events after flattening producing artificial loops.
* Ambiguous payment allocation: payments linked only to Invoice, not to Orders, so order-level settlement is unclear.
* Overly short Payment traces with one event per payment object.
* Constructor/API version mismatch changing OCEL signature.
* False total order for same-time events; example avoids ties but real data may need tie-breaking.

## 8. Final semantic checks
* O100 contains I1 and I2 via O2O `contains`; O200 contains I3.
* P1 packs I1 and I3; P2 packs I2 via O2O `packs`.
* D1 carries P1; D2 carries P2 via O2O `carries`.
* V1 bills O100 and O200 via O2O `bills`.
* M1 and M2 partially_settle V1 via O2O.
* e6 Reserve Stock relates to I1, I3, O100, O200; e7 Pack Package P1 relates to P1, I1, I3, O100, O200.
* events has 17 unique eids, objects has 12 unique oids, relations repeat activity and timestamp from events, no orphan ids.
