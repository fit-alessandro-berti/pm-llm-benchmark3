# 1. Model scope and state variables

**Boundary.** The twin covers permit lifecycle from `Submit application` to terminal `Issue permit`/`Reject application`, including applicant/third-party waits inside that interval. Pre-submission effort is outside the baseline boundary but modelled as a shifted activity under D1. Post-permit construction compliance is excluded; any risk from skipping inspection (D2) is therefore an unobserved guardrail, not a modelled outcome. The twin is a *scenario* digital twin: periodically refit from new log extracts, then used offline for intervention comparison, not a real-time controller.

**Level of detail / paradigm.** Calendar-aware discrete-event simulation with three entity types, not independent cases:

| Entity | Key state variables | Why needed |
|---|---|---|
| `PermitCase` | `case_id, case_type, district, architect_id, application_value, requires_fire/environment/public_notice (observed + latent flags), arrival_time, current_activity, loop_count, age, priority/aging_flag, bundle_id, objection_latent (bool, unobserved), stage_results{planning,fire,env,notice,inspection}` | Routing, AND-join at Decision drafting, rework, fairness by district/architect |
| `Architect` (agent) | `architect_id, burst_cluster_id, experience_proxy, submission_rate, bundle of related case_ids, applicant_response_frailty` | Top-20 architects = 31% of demand, same-week bursts, correlated applicant response |
| `InspectionBundle` (dynamic group) | `district, member_case_ids, formed_time, route_district, travel_time, first_case_wait` | Geographic batching (D3) couples cases: one case's wait depends on others |

**Resources and queues.** Separate pools, each with its own queue and calendar, not a single FCFS system: Clerks (5 FTE), Planners (8, 2 Simple-only), Fire (2 FTE Tue–Thu), Environmental (3 FTE, 40% non-permit), Inspectors (4 FTE Tue–Fri), Legal (2 FTE, blocked in council weeks), System (unlimited), Applicant/consultant (unlimited capacity but heavy-tailed response — modelled as delay distribution, not a seizeable resource). Queue discipline per pool is explicit and intervention-dependent (e.g. D6 reserves capacity for aging cases).

**Cross-case dependencies (three mechanisms, all first-class):**
1. *Resource contention* — shared pools induce waiting.
2. *Architect burst process* — related cases arrive clustered; a cluster shock raises arrival rate and correlates applicant-response times.
3. *Shared neighbourhood shock* — objection latent state is drawn per district-week, affecting all Public-notice cases in that district-week; plus InspectionBundle formation couples inspection timing/travel.

**Clock and calendars.** Simulation clock in minutes; service time is *work content*, elapsed completion = calendar-adjusted via `add_work_time(start, work_minutes, calendar)` skipping non-working hours. State includes per-resource `next_available`, per-pool `queue_length, WIP, utilisation`, global `backlog, cases_>threshold`, and calendar exceptions (holidays, council weeks).

# 2. Parameter-estimation plan

**PM4Py usage (log/model handling only, separate from the DES engine).** Use PM4Py for ingestion, discovery, and diagnostics; the DES is hand-built from a `ParameterSet` produced by this stage — PM4Py does not generate the simulation.

1. **Ingest:** build a `pandas.DataFrame` (never `pm4py.read_csv`), then `pm4py.format_dataframe(df, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")`.
2. **Discovery/diagnostics:** `pm4py.discovery.get_variants(log)`, `get_dfg(log)`, `get_performance_dfg(log)`; compare discovered/inferred structure against the supplied process-tree string. Treat the tree string as a *scaffold*: attempt `pm4py.parse_process_tree(...)`, but hand-author the simulator routing graph as source of truth, because the string uses informal `*`/`X`/`tau` notation, leaves `'Completeness rework'` undefined as a distinct activity, and does not encode AND-join, calendars, or case-attribute routing. Validate the hand-authored graph against the DFG and variant frequencies instead of trusting automatic treesimulation conversion.
3. **Conformance:** token-replay/alignment via PM4Py to quantify fitness of the routing graph on the log; report deviations as rare variants (7%) rather than forcing them into the nominal path.

**Arrivals.** Fit a non-homogeneous Poisson process by piecewise-constant intensity `(t) = 0 · month_factor · dow_factor · case_type_mix`, estimated from first-event timestamps per case (mean inter-arrival = case arrival average). Overlay a Neyman–Scott cluster process for architect bursts: parent events for top-20 architects, offspring = related cases within the same week/district. Negative-binomial/quasi-Poisson checks guard against over-dispersion.

**Service vs. waiting (the central identification problem).** Only completion timestamps are reliable. Therefore: (a) estimate *total sojourn* distributions per variant from the log (well identified); (b) bound service time using per-resource inter-completion gaps (sorted completions per `org:resource`) as an upper proxy for busy time, and HR calendars for available capacity; (c) fit work-content distributions (lognormal/gamma/Weibull, chosen by quantile match to the supplied median/p90 table) constrained so that simulated waiting + calendar-adjusted service reproduces both the observed sojourn and the median/p90 table; (d) report all downstream results as sensitive to this split, and carry the split uncertainty into §5. Never present inferred service times as directly observed.

**Branching / routing.** From DFG conditional frequencies and case attributes: logistic models for `requires_fire` (flag + value/area proxy), `requires_environment` (flag + district sensitivity latent), `requires_public_notice` (case type + district). Rework probabilities conditional on case type and preceding activity. Rare variants pooled into an explicit "exception" route with capped loops.

**Applicant/third-party and objections.** `Receive missing documents` delay: fit heavy-tailed lognormal/mixture to requestreceive gaps. Public-notice: fit a *two-component mixture* — fixed 14-day minimum vs. extended component (median far above 14d) — and treat the extended component as the *proxy* for the latent objection state. Objections are never treated as observed events; their probability is a calibrated latent parameter with wide uncertainty (§3, §5).

**Calibration loop.** Fit parameters  run baseline  compare simulated vs. log on variant shares, median/p90 duration by case type, Monday queue proxies, and pool utilisation  adjust  refit. Record every parameter's source (log / HR roster / supplied summary / assumption).

# 3. Assumptions

**Arrivals.** Piecewise-constant NHPP intensity by month × weekday × case type; Monday multiplier 2.2× Wednesday and peak multiplier 1.7× are taken from the summary and refit. Bursts are clustered, not independent Poisson. *Sensitivity flag: high.*

**Service times.** Lognormal work-content per activity × case type, non-preemptive within a working day, calendar-expanded across non-working hours. Review activities (Planning/Fire/Environmental) assumed interruptible at day boundaries (work resumes next available slot); checks/drafting non-preemptive. Distribution family is an assumption, checked against empirical quantiles and alternative families in sensitivity analysis.

**Routing.** Fire required if flag=yes or latent area threshold exceeded (area imputed from `application_value` × case type); Environmental if flag=yes or district latent sensitivity; Public-notice for Complex variance and a fitted fraction of New residential. Decision drafting is an AND-join: it starts only when all applicable predecessor results exist. Planning  Fire  Environmental run in parallel where applicable.

**Resources/calendars.** Calendars as given (Fire Tue–Thu, Legal blocked in council meets, etc.) are deterministic and known. Effective capacity = calendar × FTE × (1  non-permit share). No absenteeism in baseline; stress scenario S1/S3 adds it.

**Rework.** Geometric loop counts with per-activity probabilities, correlated with case complexity (Complex variance > Simple). Rework reason is *not* modelled (unreliable text); the twin models rework *frequency and cost*, not cause. Loop cap (e.g. 3) prevents infinite tails; uncapped sensitivity checked.

**Applicant/third-party response.** Separate heavy-tailed distributions, correlated within architect cluster (same applicant's cases respond similarly). D1 shifts some effort pre-submission: it reduces in-process missing-doc loops but adds a pre-submission delay distribution — the net effect is an open question for the experiment, not an assumption of benefit.

**Cross-case dependencies.** Architect clusters share arrival bursts and response frailty; district-week objection shocks are shared; inspection bundles form when k cases in a district are inspection-ready within a window (D3 changes k/window). Bundle travel time < sum of individual trips but first-case wait increases.

**Non-stationary demand.** Seasonality is periodic (12-month) with the stated peak months; no trend assumed in baseline. Year-2 is generated by repeating the seasonal pattern so interventions are evaluated over full cycles.

**Missing data.** (i) Area threshold, district sensitivity, objection events, rework reasons: latent variables with priors from summaries, wide ranges. (ii) Emergency cases removed from log: assume truncation affects <2% of volume; validation tolerance widened accordingly. (iii) Missing start times: service/wait split is interval-identified only (§2). (iv) Flattened log under-represents cross-case links: architect/district co-occurrence in the log is used as a *lower bound* on true clustering.

# 4. Experiment matrix

Baseline = current process, current calendars, current demand. All interventions compared against baseline under common random numbers (§5).

|---|---|---|---|---|---|

**Stress scenarios** (applied to B0 and to the top-3 finalists, not to all D-items):

| ID | Stress | Factor/level | What it tests |
|---|---|---|---|
| S1 | Demand + capacity shock | Peak multiplier ×1.4 for 6 months; Fire availability 25% | Do D4/D6/D3 survive a surge? |

Expected trade-offs are hypotheses to be tested: e.g. D3 is expected to help inspector utilisation but hurt first-in-bundle wait; D1 helps in-process duration but may worsen total applicant-perceived time; D2's benefit is concentrated in Simple (45% of mix) but its risk is unmeasurable in the log.

# 5. Warm-up, replications, and uncertainty treatment

**Warm-up and run length.** Initialise with an empirical WIP snapshot: sample in-progress cases' stage and age from the log's open cases at several cut points, rather than starting empty (empty start understates early queues). Then run a **6-month warm-up** (discarded) to settle queues, followed by a **24-month measurement run** (two full seasonal cycles) so every intervention faces identical peak/off-peak structure. Cases still in system at run end are treated as **censored**, not dropped — dropping them biases durations downward given the 140–260d tail.

**Replications and seeds.** Pilot (10 reps) to estimate variance of median/p90 duration per scenario; choose replication count `n  (t. · s / E)²` for target half-width E = 5% of median or 2 days, whichever is larger — expect **n  50–100** for p90 stability. Use **common random numbers** across interventions with *separate RNG streams* per subprocess (arrivals, service, applicant response, objection draw), so changing an intervention does not desynchronise unrelated draws. Master `SeedSequence` spawned per (scenario, replication); all seeds logged.

**Intervals.** Report replication-based t-intervals for means, bootstrap intervals for medians/p90/SLA rates, and **paired-difference intervals** (same seed streams) for intervention-vs-baseline effects — the decision-relevant quantity. Distinguish *aleatory* uncertainty (seed variation) from *epistemic* uncertainty (parameter ranges from §3): run an outer parameter-uncertainty loop (bootstrap-refit parameters / prior ranges for latent objection prob., area threshold, service/wait split) around the inner seed loop, and report intervals that include both.

**Heavy tails.** Do not trim or winsorise. Fit mixture/lognormal tails for applicant response and public-notice extension; report p50/p90/p95 and share >180d alongside the mean. Stratify by case type — pooling hides the Complex-variance tail. Sensitivity: re-run finalists with (a) empirical-bootstrap service times instead of fitted lognormal, (b) Pareto tail for applicant delay, (c) objection prob. at prior bounds. If rankings flip, report that explicitly.

**Sensitivity analysis.** One-at-a-time tornado on the ~8 most uncertain parameters (arrival peak multiplier, objection prob., service/wait split, rework prob., Fire availability, bundle window, D1 uptake, D2 threshold), then Morris screening and, for finalists, Sobol indices on the top 3–4. Parameters that dominate ranking uncertainty become measurement priorities.

# 6. Validation strategy

**Face validation.** Structured walkthroughs with clerks, planners, inspectors, legal: animation/trace of representative cases (Simple clean, Complex variance with appeal, batched inspection), checking queue behaviour, calendar effects (Monday spike, council-week Legal block), and AND-join at Decision drafting. Domain experts sign off on routing and queue discipline, not on outputs.

**Event-log replay validation.** Feed the DES the *actual* arrival times and case attributes of a log slice (deterministic replay mode, resources as in baseline) and compare: variant frequencies (²), case-type duration CDFs (KS test), and throughput. This isolates routing/service errors from arrival-model errors. Also run PM4Py conformance (token replay) of the routing graph on the full log to quantify the 7% rare-variant mass the DES must route through the exception path.

**Distributional validation.** Simulated vs. observed per case type: median and p90 duration within provisional tolerances (±15% or 5 days on median, ±20% on p90 — to be ratified before judging pass/fail), variant shares within ±5pp, activity-sequence frequencies from the DFG. Because start times are missing, validate the *joint* (waiting + service) distribution and the per-resource inter-completion gaps, and report the service/waiting split as bounded, not point-validated.

**Resource-utilisation validation.** Simulated pool utilisation vs. HR-derived effective capacity: target ±10pp per pool; specifically check Fire (Tue–Thu) utilisation, Legal council-week idleness, and Monday clerk saturation. Failure here usually indicates calendar or non-permit-share mis-specification.

**Bottleneck validation.** Confirm the simulated bottleneck ranking (expected: Environmental and Planning queues, Legal in council weeks, Inspection in peaks) matches operational evidence (aging-case reviews, Monday spikes). A useful test: the model should *reproduce* the known symptom that Decision drafting frequently waits for review results — if it doesn't, the AND-join or parallelisation is wrong.

**Out-of-sample validation.** Temporal holdout: fit on months 1–14, validate on months 15–18 (which include a peak). District holdout: fit without D5, predict D5 durations using district travel/sensitivity parameters only. Pre-register tolerances and the "fit  adjust  refit" loop to avoid overfitting by endless recalibration. All validation is conditional on the known biases (removed emergency cases, missing objection events): the twin can be *consistent* with the log, never *proven* by it.

# 7. Decision criteria

Metrics computed per scenario, by case type and district, over the 24-month measurement window. Thresholds below are **provisional decision aids to be ratified by the council before selection** — they are anchored to baseline simulation output, not claimed as statutory SLAs.

| Criterion | Metric | Provisional decision range |
|---|---|---|
| Speed (median) | Median end-to-end duration, overall and by case type | Improvement 10% relative on median for target case type, with no case type worsening >5% |
| Speed (tail) | p90/p95 duration; share >180d | p90 must not worsen >5% for any intervention claiming tail benefit (esp. D6, D9); report p95 to expose tail trade-offs |
| SLA compliance | Share within provisional SLA per case type (e.g. Simple 30d, New residential 75d, Commercial 120d, Complex 240d — ratify) | Target 90% per type; an intervention may not buy overall SLA gains by sacrificing one type below 85% |
| Fairness | Max/min district median ratio; D3/D5 vs. others; small vs. top-20 architect median gap | District ratio 1.3; no district's median or p90 worsens >10%; architect gap must not widen >10% (D7 watch) |
| Resource sustainability | Pool utilisation (peak and average); backlog/WIP at run end; cases >90d | Sustainable band 70–85% average; any pool >92% sustained = fragile, veto unless temporary (D4 peak-only); end-of-run backlog must not grow vs. baseline |
| Rework & quality guardrails | Missing-doc loops per case; inspection rework rate; rejection rate | Rejection rate must not rise >2pp for D2/D8 (proxy for late detection); rework loops per case must not rise for D1/D3 |
| Applicant burden | Pre-submission delay (D1) + in-process applicant wait | Total applicant-perceived time reported separately; D1 only counts as a win if *total* (pre + in-process) improves or is neutral |
| Robustness | Ranking across B0 + S1–S4; worst-case regret | Finalist must not rank in bottom half under any stress scenario; prefer minimax-regret over best-case performance |

**Selection rule.** Pareto-screen on (median, p90, fairness, utilisation), apply vetoes (rejection guardrail, >92% utilisation, any district worsening >10%), then rank survivors by paired-difference intervals (§5) — an intervention whose improvement interval includes zero is "promising, not proven." **No claim of exact optimality**: the output is a ranked shortlist with uncertainty and stated assumptions, plus a pilot design (e.g. D2 with audit sampling, D7 with 2–3 architects) for the top candidate before full rollout.

PROCESS_TREE = r"""
->(
  'Submit application',
  *(
    ->(
      'Completeness check',
      X(
        tau,
        ->('Request missing documents','Receive missing documents')
      )
    ),
    'Completeness rework'

def add_timing_columns(df: pd.DataFrame) -> pd.DataFrame:
    """Derive waiting/service PROXIES.

    Only completion timestamps exist, so true service time is NOT
    observable. `time_since_prev` is an upper bound on waiting+service
    for the current activity; `resource_gap` bounds busy time per
    resource. Both are used as identification bounds in calibration,
    never as point estimates of service time.
    """
    df = df.sort_values(["case:concept:name", "time:timestamp"]).copy()
    g = df.groupby("case:concept:name")["time:timestamp"]
    df["prev_activity"] = df.groupby("case:concept:name")["concept:name"].shift(1)
    df["time_since_prev"] = df["time:timestamp"] - g.shift(1)
    r = df.sort_values(["org:resource", "time:timestamp"])
    df["resource_gap"] = (
        r.groupby("org:resource")["time:timestamp"].diff()
        .reindex(df.index)
    )
    return df


def build_pm4py_log(df: pd.DataFrame):
    """Format with PM4Py conventions and run discovery diagnostics."""
    event_log = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )
    variants = get_variants(event_log)          # variant -> count
    dfg = get_dfg(event_log)                    # directly-follows graph
    perf_dfg = get_performance_dfg(event_log)  # (a,b) -> mean timedelta

    # Case arrival average computed on the DataFrame (first event/case),
    # which is unambiguous regardless of PM4Py version-level helpers.
    first = (df.groupby("case:concept:name")["time:timestamp"].min()
               .sort_values())
    arrival_avg = first.diff().mean()          # mean inter-arrival

    try:
        pt = pm4py.parse_process_tree(PROCESS_TREE)
    except Exception as exc:                   # expected: see note above
        log.warning("Process-tree parse failed (%s); using "
                    "hand-authored routing validated vs DFG.", exc)
        pt = None

    return dict(log=event_log, variants=variants, dfg=dfg,
                perf_dfg=perf_dfg, arrival_avg=arrival_avg, tree=pt)

@dataclass
class ParameterSet:
    """All fitted/assumed parameters, with provenance tracked outside."""

    dow_factor: Dict[int, float] = field(default_factory=dict)     # fitted

    rework_prob: Dict[str, float] = field(default_factory=dict)
    objection_prob_by_district: Dict[str, float] = field(default_factory=dict)
    applicant_delay: Tuple[float, float] = (1.6, 0.9)  # lognormal mu, sigma
    top_architect_share: float = 0.31

class Calendar:
    """Work-hours calendar: weekday -> (start_hour, end_hour)."""
    def __init__(self, hours: Dict[int, Tuple[int, int]]):
        self.hours = hours

    def is_working(self, dt: datetime) -> bool:
        h = self.hours.get(dt.weekday())
        return h is not None and h[0] <= dt.hour < h[1]

    def add_work_time(self, start: datetime, work_minutes: float) -> datetime:
        """Advance `start` by work content, skipping non-working time."""
        remaining = timedelta(minutes=work_minutes)
        t = start
        while remaining > timedelta(0):
            if not self.is_working(t):
                t = (t + timedelta(hours=1)).replace(minute=0, second=0)
                continue
            end = t.replace(hour=self.hours[t.weekday()][1], minute=0)
            window = end - t
            if window >= remaining:
                return t + remaining
            remaining -= window
            t = end
        return t


class ArrivalGenerator:
    """NHPP (thinning) x weekday/month factors + architect cluster bursts.

    Placeholder: the intensity function and cluster offspring logic are
    fitted in the estimation stage; here we expose the interface and a
    simple scaled-exponential step so the engine can be wired up.
    """
    def __init__(self, params: ParameterSet):
        self.p = params

    def lam(self, t: datetime, case_type: str) -> float:  # fitted intensity
        return (self.p.month_factor.get(t.month, 1.0)
                * self.p.dow_factor.get(t.weekday(), 1.0)
                * self.p.case_mix[case_type])

    def next_arrival(self, rng, t: datetime) -> Tuple[datetime, Case]:
        raise NotImplementedError("Implement NHPP thinning + cluster process")


class Router:
    """Attribute-based routing + rework decisions (hand-authored graph)."""
    def __init__(self, params: ParameterSet):
        self.p = params

    def route(self, case: Case, iv: Intervention) -> List[str]:
        acts = ["Completeness check", "Planning review"]
        if case.needs_fire:
            acts.append("Fire-safety review")
        if case.needs_env:
            acts.append("Environmental review")
        if case.needs_notice:  # duration: 14d min vs latent-objection tail
            acts.append("Public-notice period")
        skip_insp = (iv.id in ("D2", "D10")
                     and case.case_type == "Simple renovation"
                     and case.value < iv.kwargs.get(
                         "skip_inspection_value_threshold", 50_000))
        if not skip_insp:
            acts += ["Inspection scheduling", "Site inspection"]
        acts += ["Decision drafting"]
        if case.case_type in ("Commercial", "Complex variance"):
            acts.append("Legal check")
        return acts

    def rework(self, activity: str, rng) -> bool:
        return rng.random() < self.p.rework_prob.get(activity, 0.0)

class ExperimentRunner:
    def __init__(self, params: ParameterSet, engine: SimulationEngine):
        self.params = params
        self.engine = engine

    def run_matrix(self, experiments: List[Intervention],
                   replications: int, base_seed: int = 20260101) -> pd.DataFrame:
        """One row per (experiment, replication); paired seeds across
        interventions (common random numbers) for difference CIs."""
        rows = []
        for iv in experiments:
            for rep in range(replications):
                seed = base_seed + 10_000 * rep   # same rep -> same seed
                rows.append(self.engine.run(iv, seed=seed))
        return pd.DataFrame(rows)
