## 1. Normalization Assumptions
- `clock_offset = recorded_clock - true_clock`, where `recorded_clock` is the local displayed time (including rounding/flooring), `true_clock` is the true local time (i.e., UTC time + TZ offset), and `true_UTC = true_clock - TZ_offset` (TZ_offset = UTC offset of the time zone at that moment, e.g., CEST = +2h). Thus `true_local = recorded_local - offset`, and `true_UTC = recorded_local - offset - TZ_offset`.
- Rounding intervals applied **before** clock correction:

## 7. Governance Recommendation
1. **Timestamp storage**: Always store raw local display time (e.g., "10:14"), resolution type ("floor-min"), and source system in UTC with uncertainty metadata (e.g., `utc_low`, `utc_high`, `tz`, `offset_bounds=[a,b]`, `rounding='floor-min'`). Never store only displayed time.
2. **Clock management**:
   - Log periodic NTP offset measurements (e.g., hourly) with timestamp, store as `offset_log[timestamp] = measured_offset`.
   - For mobile/external sources, require app to report estimated entry delay (e.g., "entered X min after event") if user-entered; default max delay = 5 min, stored as `delay_max`.
3. **Time zone & DST**:
   - Use `zoneinfo`/IANA time zones; for ambiguous periods (e.g., 2025-10-26 02:00–02:59 Berlin), store both possible TZ offsets (standard +2h/DST +1h) and a flag if fold is known (e.g., "standard only" per ingestion). When converting, keep interval union over consistent folds.
   - Log fold decision (e.g., "Start event after Alert implies standard fold") with ingestion timestamp.
4. **Lifecycle & provenance**:
   - Each event record includes `case_id`, `activity`, `raw_local`, `resolution`, `offset_bounds`, `confidence` (e.g., "high" for HUB, "medium" for ops), `source_type`.
   - Missing activities (e.g., Investigation_Start) get inferred interval with provenance: "inferred from Containment - [18,25]min per work record".
5. **Provenance controls**:
   - Enforce that "eventually following" pairs (e.g., Alert  Start) have ingestion order logged; use it to prune DST folds and validate duration minima (e.g., Start  Alert).
   - Do not use midpoints for SLA/profile enforcement; use interval reasoning (min/max duration).
6. **Uncertainty handling**:
   - Store intervals, not points.
   - For SLA checks: flag as `CERTAIN VIOLATION` only if max feasible duration > SLA max; `CERTAIN PASS` only if min feasible  SLA min (trivial for S3). Otherwise report `POSSIBLE` with interval bounds.
   - For temporal profile: use zeta as input from ops team (default zeta=2); run interval classification in monitoring. Do not require zeta=1 for enforcement.
7. **Policy on interval overlap**: Interval overlap with band = `POSSIBLE_VIOLATION` is sufficient evidence to trigger review (e.g., alert ops team), but not automatic violation. CERTAIN VIOLATION triggers SLA breach record. DO NOT enforce SLA strictly on possible violations; use intervals to estimate risk (e.g., probability of violation based on interval width).
8. **Tooling**: Implement interval normalization in ingestion pipeline; expose `utc_low`, `utc_high` for each event. PM4Py can be used for point-log conformance demo (with explicit midpoint labeling), but production enforcement uses interval checks described above.

> *Rationale: Keeps raw uncertainty, leverages existing ingestion order for DST, requires minimal evidence for certainty (e.g., clock sync), avoids over-interpreting weak evidence, and separates reasoning (interval) from enforcement (policy with tolerance).*
