## 1. Analytical assumptions

I treat a **case notion** as the choice of one object type whose object IDs become the case IDs. A trace is then built from events that are **directly related** to that object, ordered by timestamp. If one event is directly related to several objects of the chosen type, flattening copies that event into each corresponding case.

I use **convergence** to mean several objects or process branches meeting in one event or object: e.g., `e16` involves O1, O2, O3, P2, P3 and D2; `e19` bills O2 and O3 through V2. I use **divergence** to mean one higher-level object spreading across several lower-level objects or traces: e.g., O1 is split across P1/P2 and D1/D2 by `e11`, `e12`, `e15`, `e16`; O3 participates in both P3/D2 and P4/D3.

Copied shared events are treated as **both evidence and duplication**. They are evidence that a real event had several object participants, but they are duplication when counted as independent case events: `e16` is one Dispatch event, yet in an Order flattening it appears in O1, O2 and O3; in a Package flattening it appears in P2 and P3.

Baseline flattenings use only the supplied E2O relations. I would permit explicit sensitivity transformations that propagate relations through O2O links — e.g., from `D2 carries P3` to the items in P3 and the orders containing those items — but only as labelled analytical variants, because such propagation can manufacture extra participations not present in the direct log.

## 3. Concrete distortion analysis

- **Order flattening — repeated O1 dispatches/confirmations.** O1 has `e15` D1/P1 and `e16` D2/P2/P3, then `e23` and `e24`. A DFG may show two Dispatch and two Confirm activities, resembling rework or repeated delivery. This is harmful if read as failure, but context-dependent/partly informative because the business fact says O1 is split across P1/P2.

- **Order flattening — cross-order package P3.** `e13` packs I21/O2 and I31/O3 into P3; `e16`/`e24` then copy D2 events into O2 and O3. Dispatch and Confirm frequencies are inflated by one shared delivery event counted three times with O1. This is harmful for per-order shipment counts but informative if interpreted as co-packing/consolidation.

- **Order/Package flattening — cross-order package P4.** `e14` packs I32/O3 and I41/O4 into P4; `e17`/`e27` are copied to O3 and O4. In the Order log, O3 also contains the earlier P3/D2 branch, producing an apparent sequential variant through P3/D2 and P4/D3. The sequencing is timestamp-induced and may distort parallelism; it is context-dependent.

- **Delivery flattening — consolidated delivery D2.** `e16` and `e24` form a single D2 case, although D2 carries P2/P3 and directly involves O1/O2/O3. The DFG sees only Dispatch  Confirm, hiding that one confirmation covers three orders. Harmful for customer-level delivery status; informative for carrier-leg performance.

- **Invoice flattening — consolidated invoice V2.** `e19` bills O2 and O3; `e22` and `e25` record M2/M3 against V2. The V2 case has Issue Invoice  Record Payment  Record Payment, which may look like duplicated payment activity. In Order flattening the same events are copied to both O2 and O3, inflating invoice/payment frequencies. Harmful without qualifiers; informative for invoice-level settlement.

- **Invoice/Order flattening — partial payments.** `e22` records M2 as `partially_settles` V2; `e25` records M3 as `completes_settlement` V2. If activity labels are only “Record Payment”, the semantic difference disappears. In O2/O3 traces, `e25` occurs after `e24` Confirm Delivery, creating Confirm  Record Payment, which can bias “late payment” metrics. Context-dependent: it is instalment behaviour, not necessarily a violation.

- **Payment flattening — near-singleton lifecycle.** M1 (`e21`), M2 (`e22`), M3 (`e25`) and M4 (`e26`) each have one event. The log has four one-event traces and no DFG edges. This is harmless for payment counts but severely harmful for end-to-end analysis.

- **Package flattening — uniform short lifecycles.** P1 `e11/e15/e23`, P2 `e12/e16/e24`, P3 `e13/e16/e24`, P4 `e14/e17/e27` all reduce to Pack  Dispatch  Confirm. This hides O1’s split, P3/P4 cross-order composition, V2 and all payments. Safe for package throughput only.

- **Item flattening — fragmented orders.** I11/I12 split O1; I31/I32 split O3 across different packages and deliveries. Events `e18`–`e21`, `e25`, `e26`, `e28`–`e31` are absent. Item traces therefore cannot support order close-time analysis. Informative for item routing, harmful for order lifecycle claims.

- **Any flattened log — copy-count ambiguity.** `e16` is one unique event, but it appears three times in Order flattening, three times in Item flattening for I12/I21/I31, and twice in Package flattening for P2/P3. Reporting “Dispatch frequency” without stating the unit of analysis is misleading.

## 4. Traditional versus object-centric analysis portfolio

I would still create flattened logs, but as **labelled views**:

- **Order log**: primary customer-facing view. Safe for Create-to-Close lead time, number of shipments/invoices per order, and order-level exception finding, provided copied event IDs and object sets are retained.
- **Item log**: safe for item routing and item-level Add-to-Confirm times.
- **Package log**: safe for package handling times; P3/P4 cross-order composition must be read from event payloads or O2O relations.
- **Delivery log**: safe only for dispatch-to-confirm carrier performance, e.g. D1/D2/D3 differences.
- **Invoice log**: safe for issue-to-settlement analysis, especially V2’s M2/M3, if qualifiers are preserved.
- **Payment log**: useful only as a payment register.

Questions about convergence/divergence require object-centric analysis. An **OC-DFG** is needed to see how event types interact without forcing one case notion. An **OTG** is useful for handovers such as O1  P1 at `e11`, P2/P3  D2 at `e16`, and O2/O3  V2 at `e19`. An **ET–OT graph** reveals which event types involve which object types. An **object interaction summary** is needed to preserve qualifiers such as `contains`, `packs`, `carries`, `bills`, `partially_settles` and `completes_settlement`. **Equivalent-execution clustering** is useful to separate structurally different executions, e.g. simple O4 (`e04`,`e10`,`e14`,`e17`,`e20`,`e26`,`e27`,`e31`) from highly shared O3.

Contradictions should be reconciled by unit of analysis. “D2 was dispatched three times” in an Order log and “D2 was dispatched once” in a Delivery log are not contradictory: the former counts case-event copies, the latter counts unique carrier events. I would report unique event counts, case-event copies and object-involvement counts separately.

## 5. Lead-object decision

**Decision: B. Use a primary lead object plus explicitly secondary lifecycles.**

Decision criteria are: temporal coverage, direct event coverage, business accountability, interpretability of shared events, and actionability.

The strongest evidence for Order as primary is coverage. Every event from `e01` to `e31` has at least one direct Order relation, and only Order cases include both Create Order (`e01`–`e04`) and Close Order (`e28`–`e31`). Orders are also the customer-facing unit for the main business outcome.

The strongest counterargument is that Order flattening distorts shared resources. `e16`/`e24` are copied to O1/O2/O3, `e13` and `e14` are cross-order packages, `e19`/`e22`/`e25` are consolidated invoice events for O2/O3, and O1/O3 have split fulfilment. Therefore Order cannot dominate without Package, Delivery and Invoice/Payment secondary views.

Residual risk is that downstream users may ignore annotations and treat copied events as independent. This would inflate Dispatch/Confirm/Payment frequencies and misread V2’s instalments as repeated failures.

I would change to **C** if the dominant analytical goal were consolidation/resource sharing rather than order fulfilment, or if tooling cannot retain event IDs and object sets. I would move toward **A** only in a cleaner future log where each event is directly related to a single order and split/consolidated packages, deliveries and invoices no longer occur.

## 6. PM4Py analysis outline

```python
import pm4py
from collections import Counter

print(ocel)

# ---- Direct E2O frequency inspection ----
extended_table = ocel.get_extended_table()

activity_freq_unique_events = (
    extended_table.drop_duplicates(subset=["ocel:eid"])["ocel:activity"]
    .value_counts()
    .sort_values(ascending=False)
)

activity_freq_relation_copies = (
    extended_table["ocel:activity"]
    .value_counts()
    .sort_values(ascending=False)
)

object_type_summary = (
    extended_table.groupby("ocel:type")
    .agg(
        unique_objects=("ocel:oid", "nunique"),
        direct_relations=("ocel:eid", "count"),
        unique_events=("ocel:eid", "nunique"),
    )
    .sort_values("unique_objects", ascending=False)
)

print("Activity frequency, unique events:")
print(activity_freq_unique_events)
print("Activity frequency, relation copies:")
print(activity_freq_relation_copies)
print("Object-type summary:")
print(object_type_summary)

# ---- Flattened logs and classic PM views: labelled, not treated as ground truth ----
object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flattened_logs = {}
dfg_results = {}
log_skeletons = {}
case_event_copy_counts = {}

for object_type in object_types:
    flat_log = pm4py.ocel_flattening(ocel, object_type)
    flattened_logs[object_type] = flat_log

    dfg_results[object_type] = pm4py.discover_dfg(flat_log)
    log_skeletons[object_type] = pm4py.discover_log_skeleton(flat_log)

    case_event_copy_counts[object_type] = sum(
        1 for trace in flat_log for _ in trace
    )

print("Case-event copy counts by flattening:")
print(case_event_copy_counts)

# Primary flattened view, with secondary lifecycles kept separate
primary_order_log = flattened_logs["Order"]
secondary_item_log = flattened_logs["Item"]
secondary_package_log = flattened_logs["Package"]
secondary_delivery_log = flattened_logs["Delivery"]
secondary_invoice_log = flattened_logs["Invoice"]
secondary_payment_log = flattened_logs["Payment"]

primary_order_dfg = dfg_results["Order"]
primary_order_skeleton = log_skeletons["Order"]

# ---- Object-centric views ----
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot_graph = pm4py.discover_etot(ocel)
object_interaction_summary = pm4py.ocel_objects_interactions_summary(ocel)

# Decision B justifies clustering: order/package/invoice-sharing patterns are heterogeneous.
equivalent_clusters = pm4py.cluster_equivalent_ocel(ocel)

print("OC-DFG, OTG, ET-OT graph, interaction summary, and clusters computed.")
```

## 7. Sensitivity and validation plan

1. **Remove or down-weight copied shared events.** Create a weighted Order DFG where `e13`, `e14`, `e16`, `e17`, `e19`, `e22`, `e24`, `e25` and `e27` are not counted as independent per-order events. Compare Dispatch/Confirm frequencies with the raw Order log. Expect `e16`/`e24` to drop from three copies to one unique event.

2. **Direct versus propagated E2O relations.** Keep the baseline direct log, then propagate through O2O qualifiers such as `contains`, `packs`, `carries`, `bills` and `settles`. Check whether Create Order events are artificially attached to items or whether D2/D3 propagation creates extra object participations. Treat propagated results as exploratory, not as ground truth.

3. **Change the lead object.** Compare Order, Item, Package, Delivery, Invoice and Payment flattenings using the same DFG and skeleton functions. If an edge such as Dispatch  Confirm appears everywhere but Issue Invoice  Record Payment appears only in Order/Invoice views, classify it as view-dependent rather than universal.

4. **Compare event-, object- and involvement-based frequencies.** In the OC-DFG, count `e16` once as an event, once as an event type occurrence, and by object involvement: it directly involves nine objects including O1/O2/O3, I12/I21/I31, P2/P3 and D2. If rankings change between these measures, report the unit explicitly.

5. **Validate against known business facts.** Check that the analysis still exposes O1’s split, P3/P4 cross-order packing, D2 consolidation, V2 consolidation and M2/M3 instalments. If a flattened view hides all five, it should not be used as the sole end-to-end view.
