## 1. Consistency rules and evidence model

Hard invariant
* Referential integrity: every E2O tuple references an existing event id and object id, every O2O tuple references existing objects. No duplicate qualifier direction is created.
* Lifecycle order: Pack Item must not precede Add Item for the same Item, Dispatch Package must not precede Pack Item for the same Package, Confirm Delivery must not precede Dispatch Package for the same Delivery. Timestamps are used as a partial order check.

Strong default
* Create Order  exactly one Order. Add Item  one Order and one Item. Pack Item  one Item and one Package, with a documented scanner-outage exception that allows item-only rows. Dispatch Package  one Package and one Delivery, with a bulk-dispatch exception. Record Payment  exactly one Payment and normally one Invoice, unapplied cash allowed.
* O2O qualifiers are directional and type specific, e.g. `DEL-X carries PK-7` is not `PK-7 carries DEL-X`.

Weak heuristic
* Identifier similarity: external_ref, carrier_ref, scanner_ref, order_hint, route_hint prefixes. `ev10 external_ref N-421?` vs `DEL-Y carrier_ref N-421` and `PK-8 route_hint NORTH` vs `DEL-Y route NORTH`.
* Temporal proximity and order: events for the same object cluster in time.
* Customer and route coherence: `INV-44 customer C17` matches `ORD-A/ORD-B customer C17`. `Confirm Delivery portal_customer C17` matches both orders.
* Amount similarity as evidence not proof: `INV-44 total 230` is numerically equal to `ORD-A declared_value 130 + ORD-B declared_value 100`; `PAY-1 amount 100` plus `PAY-2 amount 130` sums to 230. Fees, discounts and taxes make arithmetic a heuristic only.
* Existing O2O structure: `PK-8 packs IT-A2` already exists, so a second packing for PK-8 is plausible but creates a one-to-many packs relation.

Evidence against a repair
* Cardinality clash: adding a second Delivery to `ev10` would create a many-to-one Dispatch Package which contradicts the strong default.
* Identifier mismatch with a question mark: `ev10 external_ref N-421?` signals uncertainty.
* Ambiguous pattern: `ev11 external_ref N-42*` matches both `DEL-X N-420` and `DEL-Y N-421`. Portal loss of carrier identifier is explicitly allowed.
* Circular reinforcement: inferring O2O `PK-8 packs IT-B1` only because `ev08` was first assumed to involve PK-8, then using the O2O as independent confirmation.

Combination: evidence is combined as calibrated confidence. Identifier + time + route raises confidence; amount similarity alone stays weak; ambiguous patterns and documented exceptions lower confidence and push a relation to provisional or unresolved.

## 8. Over-repair warnings

* Forcing a unique Confirm Delivery to DEL-X because N-42* matches N-420 discards the equally plausible DEL-Y match and ignores the documented portal loss case.
* Using arithmetic equality of invoice total to sum of declared values as proof of billing ORD-B creates a false one-to-many bills relation when fees or partial invoicing exist.
* Allocating PAY-2 to INV-44 solely because amounts sum to the invoice total fabricates a settlement and hides possible unapplied cash or a separate payment.
* Linking ev08 to PK-8 and adding PK-8 packs IT-B1 creates a spurious co-pack that changes the Object Type Graph from one-to-one to one-to-many packs without independent evidence.
* Completing every object lifecycle by adding provisional links for IT-B1, DEL-Y, and PAY-2 makes the log appear more complete but introduces phantom process behavior such as a Confirm Delivery that always follows Dispatch Package for both deliveries.
