## 1. Modeling assumptions

### Object types and capitalization
Six object types, all PascalCase: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.

### E2O qualifier vocabulary
| Activity | Qualifier  Object Type | Rationale |
|----------|------------------------|-----------|
| Create Order | `created`  Order | Order being created |
| Add Item | `order`  Order; `item`  Item | Both the containing order and the item being added |
| Reserve Stock | `reserved_item`  Item; `for_order`  Order | Items reserved; orders affected |
| Pack Package | `package`  Package; `packed_item`  Item; `for_order`  Order | Package, items packed, orders affected |
| Dispatch Package | `package`  Package; `delivery`  Delivery; `dispatched_item`  Item; `for_order`  Order | All participants |
| Issue Invoice | `invoice`  Invoice; `billed_order`  Order | Invoice and billed orders |
| Record Payment | `payment`  Payment; `settles`  Invoice | Payment and invoice settled |
| Confirm Delivery | `delivery`  Delivery; `package`  Package; `delivered_item`  Item; `for_order`  Order | All participants |
| Close Order | `closed`  Order | Order being closed |

### O2O direction conventions
In every O2O row, `ocel:oid` is the "source/parent" and `ocel:oid_2` is the "target/child":
- Order  Item (contains)
- Package  Item (packs)
- Delivery  Package (carries)
- Invoice  Order (bills)
- Payment  Invoice (partially_settles)

### Logistics and financial event relations
- **Logistics events** (Reserve Stock, Pack Package, Dispatch Package, Confirm Delivery) relate directly to Orders AND Items, because the process description states that these events affect both orders. This is the "full operational involvement" policy.
- **Financial events** (Record Payment) relate only to Payment and Invoice objects, NOT to Orders. Payments are recorded against invoices, and the invoice–order link is captured via O2O. This avoids inflating Order traces with financial lifecycle events.

### Preventing relation propagation confusion
Direct E2O source relations are the only rows in the `relations` DataFrame. O2O propagation (e.g., Payment  Invoice  Order) is an analytical inference, not a source fact. The code does not auto-propagate; any propagation must be done explicitly in analysis code, clearly labeled as derived.

### PM4Py version assumption
The code targets **PM4Py  2.7.11** with OCEL 2.0 support. The OCEL constructor `OCEL(events=…, objects=…, relations=…, o2o=…)` is used as specified. If an older PM4Py version uses different parameter names (e.g., `event_df`, `object_df`), only the constructor line needs adjustment; all data semantics remain unchanged. The `discover_otg`, `discover_etot`, and `ocel_objects_interactions_summary` functions may not exist in all versions; the code includes fallback handling.

## 6. Modeling alternatives

### 1. Source-minimal relations
**Policy**: Relate each event ONLY to objects explicitly named in the event description.
- Reserve Stock: only I1, I3 (not Orders)
- Pack Package E07: only P1, I1, I3 (not O100, O200)
- Dispatch Package E09: only P1, D1 (not I1, I3, O100, O200)
- Confirm Delivery E13: only D1 (not P1, I1, I3, O100, O200)

**Effect on discovery**:
- Order traces become much shorter: O100 = [Create Order, Add Item, Add Item, Issue Invoice, Close Order] (5 events)
- Logistics is invisible from the Order perspective
- Package traces are richer: P1 = [Pack Package, Dispatch Package, Confirm Delivery]
- Discovery on Orders shows only creation, item addition, invoicing, and closing—missing the entire logistics backbone- This model is appropriate when the source system only records direct participants

### 2. Full operational involvement (current model)
**Policy**: Relate logistics events to all affected Orders and Items (current approach).
- Order traces include the full lifecycle: creation  item addition  reserve  pack  dispatch  invoice  confirm  close
- This creates rich Order-level DFGs
- Trade-off: more E2O rows (49 vs. ~25 in source-minimal), and shared events appear in multiple traces- This model is appropriate when you want a complete Order-centric view

### 3. O2O-propagated analytical relations
**Policy**: Start with source-minimal E2O, then propagate through O2O to create additional analytical relations.
- Example: Record Payment  V1 (source), V1  O100 (O2O), so analytically Record Payment is also "reachable" from O100
- Implementation: After building source-minimal E2O, run a graph traversal on O2O to add transitive relations, marked with a flag `propagated=True`

**Effect on discovery**:
- Order traces would include Record Payment events (through Invoice)
- But these are inferred, not observed—must be distinguished from source facts
- Risk: conflating observation with inference, leading to misleading DFG edges
- This model is appropriate for analytical dashboards where you want complete visibility, but requires clear labeling

## 7. Failure modes

### 1. Relation inflation
Including too many objects per event. Example: relating Record Payment to all Items in the system through transitive O2O chains. This bloats traces and creates spurious DFG edges.

### 2. Missing direct E2O links
Forgetting to link Pack Package to Package objects. The Package lifecycle becomes invisible, and flattening on Package yields empty traces.

### 3. Treating O2O propagation as observation
If we propagate Record Payment  V1  O100 and then treat Record Payment as if it were directly observed for O100, we create a false impression that the source system recorded a payment against O100. The DFG for Orders would show Issue Invoice  Record Payment  Close Order, suggesting a direct payment step that doesn't exist in the source data.

### 4. Duplicate shared events after flattening
E06 (Reserve Stock) appears in both O100 and O200 traces after flattening. If an analyst counts events without deduplicating, they may overcount shared operations. The DFG edge weights are inflated for edges involving shared events.

### 5. Ambiguous payment allocation
M1 and M2 both settle V1, but we don't record which portion applies to O100 vs. O200. If we tried to allocate payments to orders, any allocation would be guesswork. The OCEL model correctly avoids this by keeping payments at the Invoice level.

### 6. Overly short Payment traces

# OCEL 2.0 Construction and PM4Py Analysis Pipeline

## 1. Modeling assumptions

**Object types and capitalisation.** Six types, all PascalCase: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.

**E2O qualifier vocabulary.** Each qualifier names the semantic role the object plays in the event:

| Qualifier | Used for | Example |
|-----------|----------|---------|
| `created` | Order being created | E01  O100 |
| `order` | Order an item is added to | E02  O100 |
| `item` | Item being added | E02  I1 |
| `reserved_item` | Item whose stock is reserved | E06  I1 |
| `for_order` | Order affected by a logistics/stock event | E06  O100 |
| `packed_item` | Item packed into a package | E07  I1 |
| `dispatched_item` | Item being dispatched | E09  I1 |
| `delivered_item` | Item confirmed delivered | E13  I1 |
| `package` | Package involved in pack/dispatch/confirm | E07  P1 |
| `delivery` | Delivery involved in dispatch/confirm | E09  D1 |
| `invoice` | Invoice being issued | E11  V1 |
| `billed_order` | Order being billed | E11  O100 |
| `payment` | Payment being recorded | E12  M1 |
| `settles` | Invoice settled by a payment | E12  V1 |
| `closed` | Order being closed | E17  O100 |

**O2O direction convention.** `ocel:oid` is the source/parent; `ocel:oid_2` is the target/child. The qualifier reads as a verb phrase from source to target: "Order **contains** Item", "Invoice **bills** Order", "Payment **partially_settles** Invoice".

**Logistics vs. financial event relations.** Logistics events (Reserve Stock, Pack Package, Dispatch Package, Confirm Delivery) relate directly to Orders *and* Items—this is the *full operational involvement* policy. Financial events (Record Payment) relate only to Payment and Invoice objects. The invoice–order link is captured exclusively via O2O. This keeps Order traces focused on the physical lifecycle and Invoice traces on the financial lifecycle.

**Preventing propagation confusion.** The `relations` table contains only direct source-system E2O links. Any O2O-based propagation (e.g., Record Payment  V1  O100) is an analytical inference, not a source fact. It must be performed explicitly in downstream code and clearly labeled as derived.

**PM4Py version assumption.** Target: **PM4Py  2.7.11** with OCEL 2.0 support. The constructor `OCEL(events=..., objects=..., relations=..., o2o=...)` is used. In older versions, parameter names may differ (e.g., `event_df`); only the constructor line needs adjustment. Functions `discover_otg`, `discover_etot`, and `ocel_objects_interactions_summary` are wrapped in `try/except` for version safety.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG annotates each activity-to-activity edge with the set of object types involved:

- **Create Order  Add Item** (Order): the entry-point edge.
- **Add Item  Reserve Stock  Pack Package  Dispatch Package  Confirm Delivery** is the logistics backbone, traversing Order, Item, Package, and Delivery.
- **Issue Invoice  Record Payment** is the financial path, traversing Invoice and Payment.
- **Record Payment has NO edge to any Order activity** in the OC-DFG, because we did not link payments to orders directly. The only path from payments to orders goes through O2O (V1  O100, O200).
- P1 is visible as a convergence point: Pack Package and Dispatch Package both involve items from two orders, which the OC-DFG shows as shared activity nodes annotated with multiple object types.

### OTG (Object-Type Graph)

Expected edges weighted by the number of events that have both object types in their E2O relations:

| Object Type Pair | Co-occurring Events | Weight |

| Confirm Delivery | Order, Item, Package, Delivery |

This bipartite graph shows the "breadth" of each activity. Dispatch Package and Confirm Delivery are the broadest (4 types each), while Create Order and Close Order are the narrowest (1 type). The ET–OT graph makes explicit that Record Payment touches Payment and Invoice but not Order.

### Object-Centric Petri net

The OC Petri net contains one sub-net per object type connected by shared transitions:

- **Order sub-net:** Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Confirm Delivery  Close Order
- **Item sub-net:** Add Item  Reserve Stock  Pack Package  Dispatch Package  Confirm Delivery
- **Package sub-net:** Pack Package  Dispatch Package  Confirm Delivery
- **Delivery sub-net:** Dispatch Package  Confirm Delivery
- **Invoice sub-net:** Issue Invoice  Record Payment
- **Payment sub-net:** Record Payment (single transition)

Shared transitions connect sub-nets where object types co-occur (e.g., Pack Package is shared by Order, Item, and Package). The net does **not** have a uniquely determined interpretation: the exact structure of shared places depends on the mining algorithm's choices about how to connect sub-nets. Different algorithms (e.g., different token-based replay heuristics) may produce structurally different but equally valid Petri nets.

### Object-interactions summary

The summary would highlight:
- **P1** is a key convergence object: it appears in events E07, E09, E13, each of which is related to both O100 and O200. P1 bridges two orders.
- **V1** is a second convergence object: it connects O100 and O200 through E11 (Issue Invoice) and is settled by M1 and M2 through E12 and E15.
- **D1** inherits the convergence of P1 (since D1 carries P1).
- **M1 and M2** are isolated to V1 with no direct order interaction.

## 6. Modeling alternatives

### 1. Source-minimal relations

**Policy.** Relate each event ONLY to objects explicitly named in the event's immediate description:
- Pack Package E07: only P1, I1, I3 (omit O100, O200)
- Dispatch Package E09: only P1, D1 (omit I1, I3, O100, O200)
- Confirm Delivery E13: only D1 (omit P1, I1, I3, O100, O200)

**Impact on discovery.**
- Order traces shrink dramatically. O100: [Create Order, Add Item, Add Item, Issue Invoice, Close Order] (5 events). The entire logistics backbone disappears from the Order view.
- Package traces remain rich: P1 = [Pack Package, Dispatch Package, Confirm Delivery].
- The DFG for Orders shows only creation  item addition  invoicing  closing. An analyst would have no visibility into logistics.
- Fewer E2O rows (~25 vs. 49), cleaner source provenance.

### 2. Full operational involvement (current model)

**Policy.** Relate logistics events to all affected Orders and Items, as implemented above.

**Impact on discovery.**
- Order traces include the full lifecycle: creation  addition  reserve  pack  dispatch  invoice  confirm  close.
- Rich Order-level DFGs with 11 edges.
- Trade-off: shared events inflate inter-trace dependencies (5 events copied into 2 traces each).
- Financial events remain at the Invoice/Payment level, keeping Order traces physically focused.

### 3. O2O-propagated analytical relations

**Policy.** Start with source-minimal E2O, then propagate through O2O to add transitive analytical relations. For example: Record Payment E12  V1 (source), V1  O100 (O2O), so add a derived relation E12  O100 with `propagated=True`.

**Impact on discovery.**
- Order traces now include Record Payment events (through Invoice).
- DFG for Orders: Issue Invoice  Record Payment  Close Order.
- But these are inferred, not observed—if an analyst treats them as source facts, they create a false impression that the source system recorded a payment directly against an order.
- Requires a flag column or separate table to distinguish derived from source relations.
- Useful for analytical dashboards; dangerous for compliance or audit trails.

## 7. Failure modes

### 1. Relation inflation
Including too many objects per event (e.g., relating every logistics event to every Item in the system, not just the items in the relevant package). This bloats traces, creates spurious DFG edges, and makes flattening produce misleading event copies.

### 2. Missing direct E2O links
Forgetting to link Pack Package events to Package objects. The Package flattening produces empty traces, and Package objects become invisible in discovery. Any analysis of the packaging lifecycle becomes impossible.

### 3. Treating O2O propagation as observation
If we propagate Record Payment  V1  O100 and then treat the Record Payment as if it were directly observed for O100, the Order DFG would show Issue Invoice  Record Payment  Close Order, suggesting a direct payment step that does not exist in the source data. This conflates inference with observation.

### 4. Duplicate shared events after flattening
E06 (Reserve Stock) and E07 (Pack Package) each appear in both O100 and O200 traces after flattening on Order. If an analyst counts events without deduplicating by event ID, they overcount shared operations. DFG edge weights for edges involving shared events are inflated by a factor of up to 2.

### 5. Ambiguous payment allocation
M1 and M2 both settle V1, but we do not record which portion applies to O100 vs. O200. If we tried to allocate payments to orders, any allocation would be guesswork. The OCEL model correctly avoids this by keeping payments at the Invoice level, but this means order-level financial analysis is impossible without additional data.

### 6. Overly short Payment traces
M1 and M2 each produce a single-event trace when flattened on Payment. The DFG has zero edges, the log skeleton is trivial, and no process structure can be discovered. Any attempt to analyse payment "lifecycle" at the Payment level is meaningless. The correct level is Invoice.

### 7. Constructor / API version mismatch
PM4Py's OCEL constructor has evolved across versions. Older versions may use `event_df` instead of `events`, may not accept `o2o`, or may require a different import path. The data semantics are independent of the constructor—only the instantiation line needs adjustment. The code isolates this risk with a clear `VERSION NOTE` comment.

### 8. False total order for same-time events
In this example all 17 timestamps are distinct, so no tie-breaking is needed. However, if two events shared a timestamp and were both related to the same object, the flattening would impose an arbitrary order. This could create spurious DFG edges. A robust implementation should include a secondary sort key (e.g., `ocel:eid`) to ensure deterministic ordering.

### 9. Activity name inconsistency
If "Record Payment" were entered as "RecordPayment" or "record payment" in one event, the DFG would show two different activity nodes. The code uses consistent string literals, but production systems should validate activity names against a controlled vocabulary.

### 10. Ignoring timezone offsets
If some timestamps were UTC and others were local time (e.g., UTC+8), the global ordering could be wrong. The code uses explicit UTC timestamps. Production systems should normalise all timestamps to UTC before constructing the OCEL.
