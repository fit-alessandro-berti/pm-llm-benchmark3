## 1. Duplicate-handling decision tree

A safe pipeline should first generate duplicate *candidates*, then classify them. Candidate generation may use equal timestamp, equal harmonized activity, shared objects, payload similarity, natural keys, and source reconciliation reports. Candidate generation must not itself delete anything.

Decision tree:

1. **Is it an exact technical duplicate?**
   Criteria: same source, same `source_event_key`, same original activity, same timestamp, same payload or payload hash, and same E2O relations.
   **Action:** drop redundant copy, preserve all raw IDs in an audit table.
   **Risk if mishandled:** low, unless the “duplicate” is actually a retry with changed payload.

2. **Is there external evidence that two records are the same physical event observed by multiple systems?**
   Criteria: reconciliation report, shared natural key, or trusted source fact; payload may differ because systems enrich differently.
   **Action:** merge attributes and relations into one canonical event, retaining source-specific attributes and provenance.
   **Example:** e03/e04.

3. **Is one event a summary/status update derived from a detailed event?**
   Criteria: one event has fewer objects, later source sequence or generation evidence, and represents an abstraction-level update rather than the physical operation itself.
   **Default action:** retain both with refined labels or qualifiers.
   **Alternative action:** merge only in an explicitly declared abstraction-level scenario.
   **Example:** e06/e07, e13/e15, e14/e15.

4. **Is the apparent duplicate caused by activity harmonization?**
   Criteria: same harmonized activity but distinct source meanings or original source activities.
   **Action:** retain both with refined labels or source qualifiers. Do not merge merely because timestamp, label, and objects match.
   **Example:** e08/e09.

5. **Are the events concurrent same-label events involving different discriminating objects?**
   Criteria: same activity and timestamp, but different Item, Payment, Delivery, Package, or other lifecycle object.
   **Action:** retain both unchanged or with object-specific qualifiers.
   **Example:** e03/e05 and e13/e14. e05 and e14 must not be dropped.

6. **Is the candidate unresolved?**
   Criteria: insufficient evidence to decide whether it is duplicate, derived, or distinct.
   **Action:** retain both, flag for review, and avoid destructive cleaning. Optionally quarantine only for a separate quality-review dataset, not for the main analytical OCEL.

## 3. Timestamp-tie ordering rules

The ordering policy should first build a semantic partial order, then produce a deterministic total order only for tool compatibility.

Semantic rules:

1. **Domain constraints.** Known facts override equal timestamps: e09 precedes e10; e12 precedes e13 for M1; e15 is generated after payment messages.
2. **Within-source sequence.** `source_seq` is meaningful only inside the same source. It can order PSP P-700, P-701, P-702 and carrier C-400 before C-401. It must not compare ERP sequence 40 with PSP sequence 400.
3. **Lifecycle constraints on shared objects.** An item should be picked before the package containing it is packed. Invoice issuance should precede payment capture when the payment refers to that invoice.
4. **Source-specific semantics.** WMS “released from warehouse” and carrier “accepted by carrier” are not the same event, even after harmonization. Their labels should be refined before ordering.

Deterministic but non-semantic rules:

5. **Ingestion time.** Use only as a late tie-breaker when no semantic or source-local order is available. It is not a business timestamp.
6. **Stable fallback order.** Use canonical event ID or a stable hash as the final fallback. This makes repeated runs reproducible without claiming physical truth.

Adding microseconds before deciding the semantic order is dangerous because it turns uncertainty into a false sequence. For example, making e13 one microsecond before e14 may be a deterministic representation, but it does not prove that M1 was physically captured before M2 unless source sequence or domain evidence supports that order. Synthetic microseconds should be stored separately or applied after an explicit ordering column has been constructed; the original timestamp must remain unchanged.

For **e03–e07 at 10:00**, conservative order after merging e03/e04 is:

`e03+e04 Pick Item I1` < `e05 Pick Item I2` < `e06 WMS Pack Package` < `e07 ERP Packing Status`.

The e03/e05 order is supported by scanner sequence if the merged e03 inherits S-901 and e05 is S-902. If scanner sequence is treated as technical rather than behavioral, e03 and e05 can remain unordered peers before e06.

For **e08–e10 at 10:15**:

`e08 Release Package from Warehouse` < `e09 Carrier Accept Package` < `e10 Handover to Carrier`.

The strongest explicit fact is e09 < e10. e08 < e09 is supported by the source-specific meaning of warehouse release versus carrier acceptance, but should still be marked as a domain ordering assumption.

For **e11–e16 at 12:00** after conservative duplicate decisions:

`e11+e16 Issue Invoice` < `e12 Authorize Payment M1` < `e13 Capture Payment M1` < `e14 Capture Payment M2` < `e15 ERP Payment Summary`.

The e13/e14 order is deterministic and source-local via PSP sequence 401 < 402. The distinctness of M1 and M2 is more important than their equal timestamp.

## 4. Conservative cleaning pipeline

The conservative scenario is the default analytical dataset.

Steps:

1. Deep-copy the raw OCEL.
2. Preserve `original_timestamp`, `original_activity`, `source`, `source_event_key`, `payload_hash`, and raw event ID before any changes.
3. Generate candidate groups, but do not clean by group key alone.
4. Merge only strongly supported same-event pairs:

   * e03/e04, based on the reconciliation report.
   * e11/e16, based on invoice V1 and the known cross-system invoice issuance fact.
5. Retain abstraction-level events:

   * keep e06 and e07, but refine e07 to an ERP packing status/update;
   * keep e15, but refine it to an ERP invoice-balance/payment-summary update.
6. Refine harmonized labels:

   * e08 = “Release Package from Warehouse”;
   * e09 = “Carrier Accept Package”;
   * e10 remains “Handover to Carrier”.
7. Keep legitimate concurrency and repeated labels:

   * retain e05 as a distinct I2 pick;
   * retain e14 as a distinct M2 payment capture.
8. Build a semantic ordering graph and then a deterministic order column.
9. Only after the order column is established, create an adjusted timestamp or index-based timedelta for algorithms that require strict ordering.
10. Keep the raw OCEL and the canonicalization map.

Raw event count is 17. The conservative scenario merges e03/e04 and e11/e16, so the expected retained event count is **15**. Raw E2O count is 44. Because e03/e04 share the same three objects and e11/e16 share the same two objects, the canonical E2O count becomes approximately **39**, while the audit/provenance layer still preserves the raw 44 relations.

## 5. Aggressive alternatives

**Scenario A: evidence-based semantic merging.**
This scenario performs the conservative merges and additionally merges e06/e07 into one package-packed business transition. It is defensible only when the intended event abstraction is “package reached packed state,” not “WMS pack transaction plus ERP status update.” The expected retained event count is **14**. E2O count is approximately **37**, because the merged pack event has the union O1, I1, I2, P1 rather than separate detailed and summary records.

Most likely semantic damage: the merged event may imply that ERP observed item-level packing, although e07 only modeled O1 and P1. It also hides the latency or reconciliation gap between operational WMS packing and ERP status propagation.

**Scenario B: mechanically aggressive PM4Py merging.**
A library-level merge based on equal activity/timestamp and `have_common_object=True` can collapse groups such as e03/e04/e05, e06/e07, e08/e09, e11/e16, and e13/e14/e15. The expected retained event count could fall to about **10**, depending on implementation details and column configuration.

Most likely semantic damage: this collapses distinct item picks, hides the warehouse-carrier boundary, merges detailed and summary updates, and can collapse M1 and M2 partial payments into one capture event.

`have_common_object=True` is not enough to protect e13 and e14. They share O1 and V1, but the discriminating objects are M1 and M2. In object-centric logs, shared parent objects are common context, not proof of event identity. A payment capture linked to M1 and another linked to M2 are separate payment-object lifecycle events even if they share the same order, invoice, activity, timestamp, source, and second-level time granularity.

## 6. PM4Py-oriented Python implementation

```python
import copy
import json
import heapq
from collections import defaultdict
import pandas as pd
import pm4py


# ---------- column helpers ----------

def first_existing(df, candidates):
    for c in candidates:
        if c in df.columns:
            return c
    raise KeyError(f"None of these columns found: {candidates}")


def configure_columns(ocel):
    ev = ocel.events
    rel = ocel.relations
    return {
        "eid": first_existing(ev, ["eid", "ocel:eid", "event_id"]),
        "act": first_existing(ev, ["activity", "ocel:activity", "concept:name"]),
        "ts": first_existing(ev, ["timestamp", "ocel:timestamp", "time:timestamp"]),
        "roid": first_existing(rel, ["eid", "ocel:eid", "event_id"]),
        "oid": first_existing(rel, ["oid", "ocel:oid", "object_id"]),
        "oeid": first_existing(ocel.objects, ["oid", "ocel:oid", "object_id"]),
    }


def prepare_ocel(ocel_raw):
    ocel = copy.deepcopy(ocel_raw)
    C = configure_columns(ocel)
    ev = ocel.events.copy()

    ev[C["ts"]] = pd.to_datetime(ev[C["ts"]], utc=True)
    for raw_col, src_col in [
        ("original_timestamp", C["ts"]),
        ("original_activity", C["act"]),
        ("original_eid", C["eid"]),
        ("original_source", "source"),
        ("original_source_event_key", "source_event_key"),
    ]:
        if raw_col not in ev.columns and src_col in ev.columns:
            ev[raw_col] = ev[src_col]

    ocel.events = ev
    return ocel


# ---------- candidate pre-checks ----------

def object_sets_by_event(ocel, C):
    rel = ocel.relations
    return (
        rel.groupby(C["roid"])[C["oid"]]
        .apply(lambda s: tuple(sorted(map(str, s.dropna().unique()))))
        .to_dict()
    )


def candidate_duplicate_report(ocel):
    C = configure_columns(ocel)
    ev = ocel.events.copy()
    objsets = object_sets_by_event(ocel, C)
    ev["_object_set"] = ev[C["eid"]].map(objsets).apply(lambda x: x if isinstance(x, tuple) else tuple())

    rows = []
    for (act, ts), g in ev.groupby([C["act"], C["ts"]], dropna=False):
        if len(g) <= 1:
            continue
        eids = list(g[C["eid"]])
        sets = [set(x) for x in g["_object_set"]]
        any_overlap = any(sets[i] & sets[j] for i in range(len(sets)) for j in range(i + 1, len(sets)))
        all_equal_sets = len({tuple(sorted(s)) for s in sets}) == 1
        rows.append({
            "activity": act,
            "timestamp": ts,
            "candidate_eids": eids,
            "sources": sorted(map(str, g.get("source", pd.Series(dtype=str)).dropna().unique())),
            "payload_hashes": sorted(map(str, g.get("payload_hash", pd.Series(dtype=str)).dropna().unique())),
            "all_object_sets_equal": all_equal_sets,
            "any_object_overlap": any_overlap,
            "note": "candidate only; do not delete without classification"
        })
    return pd.DataFrame(rows)


def exact_technical_duplicate_groups(ocel):
    """
    Strict pre-check for exact technical duplicates. This intentionally does
    not treat cross-system observations or harmonized same-label events as exact.
    """
    C = configure_columns(ocel)
    ev = ocel.events.copy()
    objsets = object_sets_by_event(ocel, C)
    ev["_object_set"] = ev[C["eid"]].map(objsets).apply(lambda x: json.dumps(list(x)))

    keys = [C["act"], C["ts"], "_object_set"]
    for col in ["source", "source_event_key", "payload_hash"]:
        if col in ev.columns:
            keys.append(col)

    groups = []
    for _, g in ev.groupby(keys, dropna=False):
        if len(g) > 1:
            groups.append(list(g[C["eid"]]))
    return groups


# ---------- safe subset use of pm4py.ocel_drop_duplicates ----------

def restrict_to_events(ocel, eids):
    C = configure_columns(ocel)
    eids = set(eids)
    sub = copy.deepcopy(ocel)
    sub.events = sub.events[sub.events[C["eid"]].isin(eids)].copy()
    sub.relations = sub.relations[sub.relations[C["roid"]].isin(eids)].copy()
    return sub


def replace_event_subset(base, candidate_eids, cleaned_subset):
    C = configure_columns(base)
    candidate_eids = set(candidate_eids)
    out = copy.deepcopy(base)
    out.events = pd.concat(
        [
            out.events[~out.events[C["eid"]].isin(candidate_eids)].copy(),
            cleaned_subset.events.copy(),
        ],
        ignore_index=True,
        sort=False,
    )
    out.relations = pd.concat(
        [
            out.relations[~out.relations[C["roid"]].isin(candidate_eids)].copy(),
            cleaned_subset.relations.copy(),
        ],
        ignore_index=True,
        sort=False,
    )
    return out


def safe_exact_drop_with_pm4py(ocel):
    """
    Justified use of pm4py.ocel_drop_duplicates:
    only on strictly pre-classified exact technical duplicate groups.
    In the supplied data this will likely do nothing, which is the correct result.
    """
    groups = exact_technical_duplicate_groups(ocel)
    if not groups:
        return copy.deepcopy(ocel)

    candidate_eids = sorted({eid for group in groups for eid in group})
    sub = restrict_to_events(ocel, candidate_eids)

    # Safe only because the subset contains exact technical duplicates already
    # verified by source/source_event_key/payload_hash/object-set checks.
    sub_clean = pm4py.ocel_drop_duplicates(sub, have_common_object=False)

    return replace_event_subset(ocel, candidate_eids, sub_clean)


# ---------- verified-pair merge ----------

def as_list(x):
    if isinstance(x, list):
        return x
    if isinstance(x, tuple):
        return list(x)
    if x is None:
        return []
    try:
        if pd.isna(x):
            return []
    except Exception:
        pass
    return [x]


def merge_verified_pairs(ocel, merge_specs):
    """
    merge_specs example:
    {
        "e04": {
            "canonical": "e03",
            "rule": "R_SCAN_RECONCILED_V1",
            "confidence": "high",
            "reason": "reconciliation report says same physical scan"
        }
    }
    """
    out = copy.deepcopy(ocel)
    C = configure_columns(out)
    ev = out.events.copy().set_index(C["eid"], drop=False)
    rel = out.relations.copy()

    for absorbed, spec in merge_specs.items():
        canonical = spec["canonical"]
        if canonical not in ev.index or absorbed not in ev.index:
            continue

        c = ev.loc[canonical].copy()
        a = ev.loc[absorbed].copy()

        # Provenance lists.
        c["source_event_ids"] = sorted(set(as_list(c.get("source_event_ids")) + [canonical] +
                                           as_list(a.get("source_event_ids")) + [absorbed]))
        if "source" in ev.columns:
            c["source_list"] = sorted(set(map(str, as_list(c.get("source")) + as_list(a.get("source")))))
        if "source_event_key" in ev.columns:
            c["source_event_key_list"] = sorted(set(map(str, as_list(c.get("source_event_key")) +
                                                        as_list(a.get("source_event_key")))))
        if "payload_hash" in ev.columns:
            c["payload_hash_list"] = sorted(set(map(str, as_list(c.get("payload_hash")) +
                                                   as_list(a.get("payload_hash")))))

        conflicts = {}
        skip = {
            C["eid"], C["act"], C["ts"],
            "source", "source_event_key", "payload_hash",
            "source_event_ids", "source_list", "source_event_key_list", "payload_hash_list",
            "merge_rule", "merge_confidence", "merge_reason", "attribute_conflicts"
        }

        for col in ev.columns:
            if col in skip:
                continue
            cv, av = c.get(col), a.get(col)
            cv_missing = pd.isna(cv) if not isinstance(cv, (list, tuple, dict)) else False
            av_missing = pd.isna(av) if not isinstance(av, (list, tuple, dict)) else False
            if cv_missing and not av_missing:
                c[col] = av
            elif not cv_missing and not av_missing and str(cv) != str(av):
                conflicts[col] = {str(canonical): str(cv), str(absorbed): str(av)}

        old_conflicts = c.get("attribute_conflicts")
        if isinstance(old_conflicts, str):
            try:
                old_conflicts = json.loads(old_conflicts)
            except Exception:
                old_conflicts = {}
        if not isinstance(old_conflicts, dict):
            old_conflicts = {}
        old_conflicts.update(conflicts)

        c["merge_rule"] = spec["rule"]
        c["merge_confidence"] = spec["confidence"]
        c["merge_reason"] = spec["reason"]
        c["attribute_conflicts"] = json.dumps(old_conflicts, sort_keys=True)

        ev.loc[canonical] = c
        ev = ev.drop(index=absorbed)

        # Relation merge: redirect absorbed event relations to canonical event.
        rel.loc[rel[C["roid"]] == absorbed, C["roid"]] = canonical

        # If relation table repeats activity/timestamp, align it with canonical event.
        if C["act"] in rel.columns:
            rel.loc[rel[C["roid"]] == canonical, C["act"]] = c[C["act"]]
        if C["ts"] in rel.columns:
            rel.loc[rel[C["roid"]] == canonical, C["ts"]] = c[C["ts"]]

    # Drop duplicate E2O triples after redirecting relations.
    relation_key = [C["roid"], C["oid"]]
    for optional in ["qualifier", "ocel:qualifier"]:
        if optional in rel.columns:
            relation_key.append(optional)
    rel = rel.drop_duplicates(subset=relation_key).reset_index(drop=True)

    out.events = ev.reset_index(drop=True)
    out.relations = rel
    return out


def refine_labels(ocel):
    out = copy.deepcopy(ocel)
    C = configure_columns(out)
    ev = out.events.copy()
    refinements = {
        "e07": "ERP Packing Status",
        "e08": "Release Package from Warehouse",
        "e09": "Carrier Accept Package",
        "e15": "Update Invoice Balance",
    }
    ev.loc[ev[C["eid"]].isin(refinements.keys()), C["act"]] = ev[C["eid"]].map(refinements).fillna(ev[C["act"]])
    out.events = ev
    return out


# ---------- ordering ----------

def add_semantic_order(ocel, canonical_map=None):
    out = copy.deepcopy(ocel)
    C = configure_columns(out)
    ev = out.events.copy()
    ev[C["ts"]] = pd.to_datetime(ev[C["ts"]], utc=True)
    canonical_map = canonical_map or {}

    def canon(eid):
        return canonical_map.get(eid, eid)

    eids = list(ev[C["eid"]])
    eid_set = set(eids)

    semantic_edges_raw = [
        ("e03", "e05", "scanner/local sequence: I1 pick before I2 pick"),
        ("e04", "e05", "scanner/local sequence: I1 pick before I2 pick"),
        ("e05", "e06", "item picked before package packed"),
        ("e06", "e07", "ERP packing status generated from WMS message"),
        ("e08", "e09", "warehouse release before carrier acceptance"),
        ("e09", "e10", "known carrier acceptance before handover"),
        ("e11", "e12", "invoice before payment authorization"),
        ("e16", "e12", "invoice before payment authorization"),
        ("e12", "e13", "authorization precedes capture for M1"),
        ("e13", "e14", "PSP source sequence 401 before 402"),
        ("e14", "e15", "ERP summary generated after payment messages"),
    ]

    successors = defaultdict(set)
    indegree = {eid: 0 for eid in eids}

    def add_edge(a, b):
        a, b = canon(a), canon(b)
        if a == b or a not in eid_set or b not in eid_set:
            return
        if b not in successors[a]:
            successors[a].add(b)
            indegree[b] += 1

    for a, b, _reason in semantic_edges_raw:
        add_edge(a, b)

    # Add within-source same-timestamp source_seq ordering.
    if "source" in ev.columns and "source_seq" in ev.columns:
        for (_src, _ts), g in ev.dropna(subset=["source_seq"]).groupby(["source", C["ts"]]):
            g = g.sort_values(["source_seq", C["eid"]])
            prev = None
            for eid in g[C["eid"]]:
                if prev is not None:
                    add_edge(prev, eid)
                prev = eid

    # Deterministic fallback. Ingested_at is included only as a late tie-breaker.
    source_priority = {"ERP": 10, "WMS": 20, "SCANNER": 30, "CARRIER": 40, "BILLING": 50, "PSP": 60}
    ev_idx = ev.set_index(C["eid"], drop=False)

    def fallback_key(eid):
        row = ev_idx.loc[eid]
        ing = pd.to_datetime(row["ingested_at"], utc=True, errors="coerce") if "ingested_at" in ev.columns else pd.NaT
        ing_key = ing.value if not pd.isna(ing) else 2**63 - 1
        seq = row["source_seq"] if "source_seq" in ev.columns and not pd.isna(row["source_seq"]) else 10**12
        src = row["source"] if "source" in ev.columns else ""
        return (row[C["ts"]].value, source_priority.get(str(src), 999), seq, ing_key, str(eid))

    # Kahn topological sort with stable heap fallback.
    heap = [(fallback_key(eid), eid) for eid, deg in indegree.items() if deg == 0]
    heapq.heapify(heap)
    ordered = []
    while heap:
        _, eid = heapq.heappop(heap)
        ordered.append(eid)
        for nxt in sorted(successors[eid], key=fallback_key):
            indegree[nxt] -= 1
            if indegree[nxt] == 0:
                heapq.heappush(heap, (fallback_key(nxt), nxt))

    if len(ordered) != len(eids):
        raise ValueError("Semantic ordering graph contains a cycle; inspect ordering rules.")

    order_index = {eid: i for i, eid in enumerate(ordered)}
    ev["semantic_order"] = ev[C["eid"]].map(order_index)
    ev["deterministic_order_key"] = ev[C["ts"]].astype("int64") + ev["semantic_order"]

    out.events = ev
    out = pm4py.ocel_sort_by_additional_column(out, "deterministic_order_key")

    # Only now introduce synthetic deltas for tools requiring strict timestamps.
    out = pm4py.ocel_add_index_based_timedelta(out)
    C2 = configure_columns(out)
    out.events["adjusted_timestamp"] = out.events[C2["ts"]]
    return out


# ---------- validation ----------

def validate_referential_integrity(ocel):
    C = configure_columns(ocel)
    ev_ids = set(map(str, ocel.events[C["eid"]]))
    rel_eids = set(map(str, ocel.relations[C["roid"]]))
    obj_ids = set(map(str, ocel.objects[C["oeid"]]))
    rel_oids = set(map(str, ocel.relations[C["oid"]]))

    assert ocel.events[C["eid"]].is_unique, "Duplicate canonical event IDs"
    assert rel_eids.issubset(ev_ids), f"Relations refer to missing events: {rel_eids - ev_ids}"
    assert rel_oids.issubset(obj_ids), f"Relations refer to missing objects: {rel_oids - obj_ids}"
    return True
```

## 7. Sensitivity analysis

Compare at least four datasets.

**Raw dataset:** 17 events and 44 E2O relations. It preserves all observations but contains duplicate-looking patterns. Order-flattened DFGs may show false `Pick Item -> Pick Item`, `Pack Package -> Pack Package`, `Dispatch Package -> Dispatch Package`, and `Issue Invoice -> Issue Invoice` edges. Item flattening may show I1 picked twice because e03/e04 are duplicated observations. Payment flattening correctly has separate M1 and M2 captures, but timestamp ties require careful ordering.

**Conservative dataset:** 15 events and approximately 39 canonical E2O relations. It removes only e03/e04 and e11/e16 as strongly supported duplicates. Order-flattened DFG becomes cleaner: the false invoice duplicate disappears, I1 has one pick, and logistics labels distinguish warehouse release, carrier acceptance, and handover. Item-flattened DFG should show I1 and I2 each picked before package packing. Payment-flattened DFG keeps M1 and M2 distinct.

**Evidence-based merge dataset:** 14 events and approximately 37 E2O relations. The `Pack Package -> ERP Packing Status` distinction disappears. Order and package DFGs become simpler, but analysts lose the operational-to-ERP propagation step. ET–OT weights for packing may increase at item level if e07’s summary status is unioned with item relations from e06.

**Aggressive library merge dataset:** possibly about 10 events and 28 E2O relations. Order DFG becomes short and tidy, but much of that cleanliness is artificial. It may collapse two item picks into one, merge WMS dispatch with carrier acceptance, and collapse partial payment captures. ET–OT weights become misleading: `Capture Payment` may look like one event related to both M1 and M2; `Pick Item` may look like one event related to both I1 and I2.

Concrete changing edges or patterns include:

1. `Pick Item -> Pick Item`: duplicate artifact for e03/e04, but e03/e05 is a legitimate two-item pattern.
2. `Pick Item -> Pack Package`: frequency changes depending on whether two item picks are retained.
3. `Pack Package -> Pack Package`: false rework unless e07 is refined or merged.
4. `Dispatch Package -> Dispatch Package`: harmonization artifact hiding release versus carrier acceptance.
5. `Carrier Accept Package -> Handover to Carrier`: meaningful edge recovered after label refinement.
6. `Issue Invoice -> Issue Invoice`: disappears after e11/e16 merge.
7. `Authorize Payment -> Capture Payment`: valid for M1, not proof that M2 had the same authorization event.
8. `Capture Payment -> Capture Payment`: may represent two partial captures, not rework.
9. `Capture Payment -> Update Invoice Balance`: summary posting edge retained conservatively but lost if e15 is merged.
10. Object co-occurrence between M1 and M2: aggressive merging can create a false OTG relation by placing both payments on one capture event.

Lifecycle and performance measurements are especially sensitive. Raw data may overstate cycle complexity. Conservative cleaning preserves delays between physical operations and system summaries. Aggressive cleaning shortens apparent lifecycles, hides system latency, and can alter zero-duration concurrency into artificial sequences.

## 8. Audit trail and reversibility

Use an explicit canonicalization table, not just overwritten event rows.

Recommended schema:

| Field                          | Meaning                                                           |
| ------------------------------ | ----------------------------------------------------------------- |
| `canonical_eid`                | Event ID used in the cleaned OCEL                                 |
| `source_eids`                  | Raw event IDs absorbed into or represented by the canonical event |
| `source_systems`               | ERP, WMS, scanner, carrier, billing, PSP                          |
| `source_event_keys`            | Original source keys                                              |
| `payload_hashes`               | All original payload hashes                                       |
| `merge_rule`                   | Rule ID, for example `R_SCAN_RECONCILED_2026_05`                  |
| `rule_version`                 | Versioned cleaning logic                                          |
| `reviewer`                     | Human reviewer or automated rule owner                            |
| `confidence`                   | High, medium, low                                                 |
| `reason`                       | Short explanation of evidence                                     |
| `original_activity_by_source`  | Source-level labels before harmonization/refinement               |
| `refined_activity`             | Cleaned analytical label                                          |
| `original_timestamp_by_source` | Original UTC timestamp for every raw event                        |
| `adjusted_timestamp`           | Deterministic timestamp used only for ordering                    |
| `semantic_order_rank`          | Topological/deterministic order index                             |
| `attributes_retained`          | Attribute-level source-of-truth map                               |
| `discarded_conflicts`          | Conflicting values not used canonically                           |
| `relation_policy`              | Exact, union, retained separate, or blocked                       |
| `raw_relation_ids`             | Raw E2O rows represented by canonical E2O rows                    |

To reconstruct the raw view, the analyst joins `canonical_eid` back to `source_eids`, expands one canonical row into its raw source rows, restores `original_activity_by_source` and `original_timestamp_by_source`, and uses the archived raw E2O relation table. No raw event or raw relation should be physically lost; “dropped” means excluded from the canonical analytical view, not deleted from storage.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments.** e13 and e14 share O1 and V1 but represent M1 and M2. Safeguard: treat Payment object as discriminating for `Capture Payment`.

2. **Converting abstraction-level updates into false rework.** e06/e07 can appear as `Pack Package -> Pack Package`. Safeguard: refine summary labels or model them as status updates.

3. **Ordering by ingestion time.** e15 ingests after PSP messages, but ingestion is still technical. Safeguard: use `ingested_at` only as a deterministic late fallback.

4. **Treating shared objects as proof of duplication.** O1 and V1 are context objects. Safeguard: require discriminating-object and source-fact checks.

5. **Unioning incompatible E2O relations.** Adding M1/M2 to e15 would imply ERP observed payment-object captures. Safeguard: relation merge policy must be rule-specific.

6. **Changing durations through synthetic microseconds.** Synthetic order offsets can distort performance metrics. Safeguard: preserve `original_timestamp` and mark adjusted timestamps as analytical.

7. **Losing source-authoritative attributes.** ERP and billing may each own different invoice fields. Safeguard: use source-of-truth maps and conflict logs.

8. **Applying duplicate functions to the whole OCEL without inspecting groups.** This can merge e05, e14, e08/e09, and e15 incorrectly. Safeguard: run candidate reports first and apply library functions only in scoped scenarios.

9. **Using `source_seq` across systems.** ERP sequence 40 and PSP sequence 400 are not comparable. Safeguard: apply `source_seq` only within a source.

10. **Mistaking harmonized labels for source semantics.** e08 and e09 both say `Dispatch Package`, but source facts distinguish release and acceptance. Safeguard: preserve original labels and refine canonical labels.

11. **Creating false object coupling.** Aggressive merging can make M1 and M2 look jointly involved in one capture. Safeguard: inspect OTG changes after each scenario.

12. **Assuming deterministic total order proves physical order.** A topological sort is a representation, not evidence. Safeguard: store partial-order reasons separately from fallback order keys.
