| **P2 Mandatory checks** | Parallel block `+(CC, TR)` ensures both occur; interleavings allowed. They occur before anything after the loop. |
| **P3 Supplier Review** | Not required by tree; required by `validation_rules["P3_SR_conditional"]` when `meta["external"]=True`. Without meta, model allows missing `SR`; trace stays valid but flagged for review. |
| **P4 Expedite Review** | Optional branch; if chosen, must occur after `+(CC,TR)` because it is after the loop in sequence. Ordering relative to `SR` handled by 5 branches of `X`. Must precede approval because approval is after `X`. |
| **P5 Exactly-one approval** | `X(MA, AA)` enforces exactly one execution of one branch. |
| **P6 Correction / recheck** | `*` loop: after `CD`, `+(CC, TR)` repeats. **Conservative**: both repeat. When `affected_check` is available, `validation_rules["P6_selective_replay"]` can tighten (e.g., allow only `TR` if meta says so). |
| **P7 Suspicious repeat** | Loop entry requires `CD`; no other repetition mechanism exists. If `CC` or `TR` appears twice without `CD`, `P7` rule rejects. |

### 5. Limitations from missing attributes

- **External/Internal (P3):** The model cannot enforce `SR` conditionally; it treats `SR` as optionally allowed. Without joining to an order-master table, we cannot distinguish a valid internal order that skips `SR` from an invalid external order that also skips it.
- **Affected check (P6):** The conservative loop repeats both `CC` and `TR` after any `CD`. This means B6 (only `TR` affected) is structurally rejected by the tree but can be accepted by `validation_rules` if metadata is added later. Until then, the model is **overly restrictive** for selective corrections but **explicit** about that limitation.
- **No hidden mandate:** I do not treat `SR` or selective replay as “optional by design”; they are **conditionally mandatory**, documented in `policy_dict`, and enforced by post-hoc checks, not by silent ignoring.

# 10. Governance Recommendation

- **Model S:** **Retire from enforcement; restrict to exploration only** with explicit “deviation accepted” documentation. It fails P2, P4, and P7 structurally. It may remain as a “high-level overview” visualization if labeled “not policy-complete.”
- **Model C:** **Do not deploy as-is for compliance.** Its branch enumeration, duplicate labels, and holdout collapse make it unmaintainable and overfitted. It may serve as a **temporary audit reference** for observed historical variants only if paired with a negative-suite test, but it should be superseded within one quarter.
- **`model_third`:** **Conditional approval for exploration and provisional enforcement testing**, provided:
  1. External dictionaries (`external_source_flag`, `affected_check`) are joined or at least tracked.
  2. A curated negative trace suite (B3, B4, B8 + synthetic) is run and reported.
  3. The 5-branch optional phase is validated against actual interleavings (ER before/after SR) in the log.
  4. The conservative correction loop is documented as “restrictive until selective metadata is available.”
  5. Stakeholder comprehension is measured with the documented protocol above and achieves   0.6 agreement.
  6. Soundness passes and runtime is measured on full log, not just sample.

**Deployment gate:** `model_third` may replace both originals only after the missing attributes are either (a) ingested into the event log, or (b) managed via an authoritative external master table with audit trail. Until then, it operates as a **structured approximation with explicit gaps**, which is safer than S’s hidden gaps and C’s hidden overfitting.

# 11. Dissenting View

The recommendation to retire both original models and deploy `model_third` with external dictionaries is defensible only if we assume that “better explicit limitations” beats “observed frequency fidelity.” A stronger rebuttal is this: **Model C’s precision (0.941) and explicit sequencing are exactly what an auditor needs when the business rule is “do what we have done, and treat deviations as noncompliant until approved” (F8).** The sharp holdout drop (0.744) may not be overfitting; it may be correct enforcement: unseen combinations of `Auto Approval` with `Supplier Review` and `Expedite Review` *should* be rejected until the process owner approves them. From this view, `model_third`’s 5-branch `X` block is an unnecessary abstraction that introduces unverified flexibility (e.g., allowing `ER` before `SR`) without evidence that those combinations are legally valid—only that they are structurally possible. Furthermore, `model_third`’s reliance on external dictionaries introduces a new failure mode: if the master table is stale, the model silently approves invalid traces or rejects valid ones, and the conformance diagnostics will not distinguish “model error” from “policy error.” Stakeholder comprehension for `model_third`, though better than C, is still lower than S (4.4); if operational adoption is the bottleneck, a precise but unreadable model is useless, but so is a readable model that requires a data-engineering team to maintain side dictionaries.

**What would change my decision:** (1) If the missing `external/internal` and `affected_check` attributes are backfilled for a 12-month window, allowing `model_third` to be validated end-to-end with selective replay and conditional `SR` enforcement; (2) If a negative-suite audit shows that `model_third` accepts B3 or B4 at >5% rate due to alignment slack (indicating hidden permissiveness); (3) If process owners explicitly state they prefer “list approved variants” (C’s philosophy) over “define constraints” (third’s philosophy), in which case C should be retained as a variant repository, not a process model, and `model_third` should be redesigned as a pure DECLARE constraint set rather than a procedural tree. Absent that evidence, I maintain that `model_third` is the safer governance choice, but it is not yet deployment-ready without the attribute integration and negative-suite proof.
