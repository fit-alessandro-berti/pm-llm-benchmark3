# 1. Review Scope and Assumptions

This review treats the two submissions as *candidates for different jobs*, not as two scores on one leaderboard. Four uses are in scope, and they do not share a fitness–precision trade-off.

**Exploration and log diagnosis.** The model is a map of what the log can do, including incomplete cases. High replay fitness and tolerance of missing events are useful. Extra model language is acceptable if analysts can see that it is extra. Model S is aimed at this job; that does not make it a policy model.

**Stakeholder communication and ownership.** The model must be a short, named block structure a process owner can walk. Duplicate labels, XOR-of-variants, and undocumented silent skips fail this job even when numeric simplicity is later “explained.” Informal 1–5 scores are only a weak proxy.

**Simulation and capacity planning.** The model must generate *plausible* futures, not the full shuffle of every optional activity and not only yesterday’s eight variants. Optionality has to be the optionality in the policy (Expedite; Supplier Review when sourcing is unknown), not optional mandatory checks.

**Conformance enforcement and audit.** The language of the model is a control. False negatives (accepting B3/B4/B8) are worse than false positives on unseen but legitimate combinations, *unless* those combinations are sent to a change board rather than silently blocked. Precision against the observed positive log is not precision against policy (F5). Fitness on a log that contains both compliant and incomplete cases is not evidence of control quality.

Assumptions used below: “accepts” means the trace is in the model language (perfect alignment, no log/model moves), not a high fitness number. Process-tree operators have standard semantics: `->` sequence, `+` interleaving of all children, `X` exclusive choice, `*` loop with do/redo, `tau` silent skip. The 80/20 split, alignment costs, and seeds were not published, so every number is treated as an *indication from an unreproducible run*, not as a fact about the process. The log lacks `sourcing ∈ {internal, external}` and `affected_checks`, so no purely control-flow model can implement P3 or P6 exactly; the honest move is to make those decision points explicit and over-approximate *only there*, not to optionalize Credit Check and Technical Review.

# 3. Adversarial Review of Model S

**Strongest case for S.** S is a four-step backbone every owner already knows: register, do some reviews, take exactly one approval, release. The inner AND of four optional activities is robust to the incomplete logging F4 warns about (especially missing Supplier Review) and will not raise a storm of false deviations when a legitimate new interleaving appears. It is fast to align, has no cloned labels, converts to a small sound net, and matches the exploration charter in F7. As a *whiteboard*, it is the only submitted model a non-analyst can correct in a meeting.

**Strongest case against S.** The same construction that produces robustness also *deletes the policy*. Credit Check and Technical Review are not mandatory; they are `X(activity, tau)`. Expedite Review is not constrained to follow both checks; it is a peer of those checks in a partial order. Correct Dossier is absent, so the model cannot represent the only legitimate reason to repeat a check (P6) and cannot *name* the suspicion in P7—it can only fail to generate the suspicious trace. The discovery team’s phrase “robust to missing events” is being used to justify optional *mandatory* work. That is not noise tolerance; it is a different process.

**At least five undesirable or policy-ambiguous traces in L(S):**

1. `Register Dossier, Manager Approval, Release Order` (B3). Both mandatory checks skipped via `tau`. Forbidden.
2. `Register Dossier, Auto Approval, Release Order`. Same hole with the other approval. Forbidden.
3. `Register Dossier, Credit Check, Manager Approval, Release Order`. Technical Review replaced by `tau`. Forbidden under P2.
4. `Register Dossier, Technical Review, Expedite Review, Auto Approval, Release Order`. Credit Check skipped; Expedite after only one check. Forbidden under P2 and P4.
5. `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` (B4). Expedite is enabled at the AND-split, so it may fire first. Forbidden under P4.
6. `Register Dossier, Supplier Review, Expedite Review, Manager Approval, Release Order`. An “external urgent” path with *no* credit or technical work. Ambiguous at best, forbidden under P2.
7. `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order` (B6). Not in L(S) at all. The model does not tolerate this as “noise”; it cannot say it. That is a scope hole, not robustness.

**Intentional tolerance vs accidental semantics.** Optional Supplier Review is a *defensible* control-flow stand-in for a missing `sourcing` attribute (P3), if and only if it is labeled as a data gap. Optional Expedite Review is the policy (P4). Exactly-one approval is correct (P5). Optional Credit Check, optional Technical Review, and peer-ordering of Expedite with those checks are **accidental semantic flaws** (or, worse, deliberate misuse of missing-event robustness). Omitting Correct Dossier is an accidental incompleteness: S is not “permissive about rework”; it is silent about rework. P7 is satisfied only by inability to repeat a label, which also rejects the legitimate B6 family.

# 4. Adversarial Review of Model C

**Strongest case for C.** C is an allow-list of eight fully sequenced variants. On that list, Credit Check and Technical Review always both occur before approval; Expedite never precedes those checks; exactly one approval occurs; Register is first and Release is last. Training precision 0.941 and the “audit-ready / frequent variants” story are the same fact: the model *is* the frequent-variant catalog. In a regulated credit-release setting, F8 is a coherent philosophy—new combinations wait for approval rather than being declared fit because a flower model can replay them. One correction variant is at least acknowledged.

**Strongest case against C.** C is not a process model. It is eight recorded movies joined by a top-level XOR. That design choice explains every other failure.

**Branch enumeration.** Each new legal combination (swap the two checks; add or drop Supplier Review; add or drop Expedite; choose Auto vs Manager; allow one-check or two-check rework; allow a second Correct Dossier) multiplies branches. The submitted XOR is already missing most of that cube. Path 8 is the only Auto Approval branch, and it is hard-wired to `Credit Check → Technical Review` with no supplier, no expedite, and no correction. Path 6 is the only Expedite+Supplier branch, and only in that order, only with Manager Approval, only with Credit-then-Technical. This is why Operations says C rejects legitimate new combinations (F2) and why holdout fitness collapses.

**Duplicate labels.** Thirty-three undocumented clones mean “Credit Check” is not one activity with one owner. Impact analysis, RACI, and IT change become a hunt through copies (F3). Necessary rework copies (a second Credit Check after correction) are buried in accidental copies of Register Dossier and Release Order.

**Unseen combinations.** F4 is visible in the expression: Supplier Review + Auto Approval, Technical-then-Credit + Auto Approval, Expedite after Technical-then-Credit, Expedite before Supplier Review, correction + Auto Approval are all outside the XOR. Those are combinations of *already modeled* activities, not new activity types.

**Correction handling.** The only rework branch forces `Correct Dossier → Credit Check → Technical Review` and then Manager Approval. P6 and F6 require a transparent choice of which check is affected. C both underfits (cannot redo one check; cannot correct twice; cannot correct then auto-approve) and overfits (the one encoded repair is a single movie).

**Holdout degradation.** 0.744 after a claimed identical split is what variant memorization looks like when the holdout is not a clone of the training frequency table. Without seeds we cannot know the exact slice, but the model expression already predicts the direction of the drop.

**Maintainability.** Updating policy (e.g., “Auto Approval may follow the same review set as Manager Approval”) requires adding a handful of near-copy branches and re-cloning every label. There is no single “approval” node to edit.

**Precision as a memorization artifact.** Alignment precision against the same positive training log that supplied the eight movies is close to a tautology: few escaping edges exist because almost nothing is enabled except the next event of a stored variant. F5 is decisive: no curated negative suite was used, so 0.941 does not mean C rejects B3/B4/B8 *as a tested property*—it means C does not wander far from training positives. (It does reject those probes, but by omission of movies, not by a named constraint an auditor can maintain.)

# 6. Likely Metric Pathologies

Ranked by how much they can flip a governance decision if left unchallenged:

1. **Positive-log-only precision (highest decision impact).** F5. C’s 0.941 is “how tightly we hug training positives,” not “how well we reject forbidden behavior.” A board that reads 0.941 as audit-readiness will ship an allow-list that fails B2 and B5. S’s 0.584 is a real warning for enforcement, but the same metric cannot *vindicate* C.

2. **Fitness rewarded by optionalizing mandatory behavior.** S’s 0.992 / 0.981 are what you get when Credit Check and Technical Review may be replaced by `tau`. Alignment then treats B3-like cases as near-perfect. This pathology directly produces F1 and is the reason S must not be chosen from a dashboard.

3. **Train/holdout leakage or split sensitivity.** Same claimed 80/20, no seed, no case ids, no stratification on sourcing (unavailable), correction presence, approval type, or expedite. C’s language is so thin that moving a few B2/B5-like cases across the cut can swing holdout fitness by tens of points. Until the split is published, 0.744 is a directional overfit signal, not a calibrated risk.

4. **Missing-event bias.** F4 says Supplier Review may be missing. S responds by optionalizing *four* activities, two of which are mandatory. That looks like “robustness” in fitness and generalization and is the wrong repair. The unbiased repair is: keep CC/TR mandatory; allow SR to be skipped *and* record a data-quality / attribute gap.

5. **Generalization rewarded by excessive permissiveness.** Token-based generalization likes S’s small shared AND. The unused `tau` and cross-product of reviews inflate the score while encoding B3 and B4. Reading 0.907 as “S will handle the future well” confuses estimator mechanics with policy generalization.

6. **Alignment-cost sensitivity and silent-transition effects (tied).** S has four explicit silent skips plus an AND. Cheap model moves make omitted mandatory checks look fit; expensive log moves would make C look even worse on holdout. Neither team published costs, so the two fitness columns are not known to be on the same scale of “how much skipping is tolerated.”

7. **Duplicated-label effects.** C’s 33 clones change the Petri net used for precision, generalization, simplicity, and runtime, and they break ownership. Some of the precision/simplicity gap is an encoding artifact of XOR-of-traces, not deeper control knowledge.

8. **Runtime confounding by model size.** 0.440 s vs 0.018 s mostly restates “C is a big unfolded net.” Relevant to operations, easy to misread as “precise models are too slow,” which would push the organization back to S.

9. **Stakeholder-score methodology.** Informal 1–5 with no protocol can be reversed by who is in the room. It supports a qualitative claim (C is unreadable) but cannot be used as a numeric weight next to fitness.

**Not ranked as a separate pathology but compounding all of the above:** treating the reported table as ground truth. It is evidence from an unreproducible experiment.

# 7. Third Alternative

`model_third` is a **block-structured POWL backbone** (mandatory work is mandatory) plus a **small DECLARE / attribute dictionary** (P3 and P6, activated when data exist) plus **post-hoc policy checks** (P7 and missing-attribute review). It is not a flower, not an eight-trace XOR, and not “everything optional.”

## 7.1 Compact formal description

Informal language:

1. Always start with Register Dossier and end with Release Order.
2. Then both Credit Check and Technical Review, concurrent (either order), both required. No silent skip.
3. Then zero or more repair cycles: Correct Dossier followed by a visible exclusive choice of recheck set {Credit Check only, Technical Review only, both concurrent}.
4. Then optional Supplier Review and optional Expedite Review, concurrent with each other (either order), both after the check/repair block and both before approval. Expedite therefore cannot precede the mandatory checks.
5. Then exactly one of Manager Approval or Auto Approval.
6. Then Release Order.

Regular-expression sketch over those blocks:

`RD · (CC ∥ TR) · ( CD · (CC | TR | (CC ∥ TR)) )* · (SR? ∥ ER?) · (MA | AA) · RO`

POWL: a strict partial order of those stages; the two mandatory checks form a two-node partial order with no edge (concurrency); the two optional reviews are XOR-with-silent, then placed in a two-node partial order; repair is `LOOP(tau, SEQUENCE(CD, XOR(CC, TR, (CC ∥ TR))))`.

DECLARE / data hooks (not silently compiled into more `tau`s):

- If `sourcing = external` is later logged: existence of Supplier Review between the check block and approval.
- If `sourcing = internal`: absence of Supplier Review.
- If `affected_checks` is later logged after a Correct Dossier: the following recheck set must equal that attribute; extra or missing rechecks become deviations.
- Always: NotCoExistence(Manager Approval, Auto Approval); Succession-style bounds already in the backbone.

Post-hoc detectors (run on the aligned trace, not by optionalizing labels):

- P7: a second Credit Check or Technical Review with no Correct Dossier strictly between the two occurrences is *suspicious*, even if some other model encoding allowed it.
- P3-unknown: a case with SR present/absent and no `sourcing` attribute is *unresolved*, not silently compliant.
- P6-unknown: a repair cycle whose recheck set cannot be matched to `affected_checks` is *unresolved*.

## 7.2 Self-contained PM4Py construction

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

rd = Transition(label="Register Dossier")
cc_init = Transition(label="Credit Check")
tr_init = Transition(label="Technical Review")
cd = Transition(label="Correct Dossier")
cc_re_only = Transition(label="Credit Check")
tr_re_only = Transition(label="Technical Review")
cc_re_both = Transition(label="Credit Check")
tr_re_both = Transition(label="Technical Review")
sr = Transition(label="Supplier Review")
er = Transition(label="Expedite Review")
ma = Transition(label="Manager Approval")
aa = Transition(label="Auto Approval")
ro = Transition(label="Release Order")
tau_loop = SilentTransition()
tau_sr = SilentTransition()
tau_er = SilentTransition()

# P2: both mandatory checks, either order
init_checks = StrictPartialOrder(nodes=[cc_init, tr_init])

# P6: after each Correct Dossier, exactly one explicit recheck set
recheck_both = StrictPartialOrder(nodes=[cc_re_both, tr_re_both])
recheck = OperatorPOWL(operator=Operator.XOR, children=[cc_re_only, tr_re_only, recheck_both])
repair_cycle = OperatorPOWL(operator=Operator.SEQUENCE, children=[cd, recheck])
# LOOP(do, redo): do first, then (redo, do)*  →  0 or more repair cycles
repair_star = OperatorPOWL(operator=Operator.LOOP, children=[tau_loop, repair_cycle])

# P3/P4: SR optional (data gap), ER optional (policy); either order; after checks
opt_sr = OperatorPOWL(operator=Operator.XOR, children=[sr, tau_sr])
opt_er = OperatorPOWL(operator=Operator.XOR, children=[er, tau_er])
optional_reviews = StrictPartialOrder(nodes=[opt_sr, opt_er])

# P5
approval = OperatorPOWL(operator=Operator.XOR, children=[ma, aa])

model_third = StrictPartialOrder(
    nodes=[rd, init_checks, repair_star, optional_reviews, approval, ro]
)
model_third.order.add_edge(rd, init_checks)
model_third.order.add_edge(init_checks, repair_star)
model_third.order.add_edge(repair_star, optional_reviews)
model_third.order.add_edge(optional_reviews, approval)
model_third.order.add_edge(approval, ro)

# Equivalent tree, useful for side-by-side review with Models S and C
model_third_tree_string = """->(
  'Register Dossier',
  +('Credit Check', 'Technical Review'),
  *(
    tau,
    ->(
      'Correct Dossier',
      X(
        'Credit Check',
        'Technical Review',
        +('Credit Check', 'Technical Review')
      )
    )
  ),
  +(
    X('Supplier Review', tau),
    X('Expedite Review', tau)
  ),
  X('Manager Approval', 'Auto Approval'),
  'Release Order'
)"""
# model_third = pm4py.parse_process_tree(model_third_tree_string)  # drop-in fallback
```

## 7.3 Declarative dictionaries and external checks

```python
declare_hooks = {
    "existence_unconditional": ["Register Dossier", "Credit Check", "Technical Review", "Release Order"],
    "exactly_one_of": [["Manager Approval", "Auto Approval"]],
    "precedence_pairs": [
        ("Register Dossier", "Credit Check"),
        ("Register Dossier", "Technical Review"),
        ("Credit Check", "Expedite Review"),
        ("Technical Review", "Expedite Review"),
        ("Credit Check", "Manager Approval"),
        ("Technical Review", "Manager Approval"),
        ("Credit Check", "Auto Approval"),
        ("Technical Review", "Auto Approval"),
    ],
    "attribute_conditioned": [
        {
            "when": {"sourcing": "external"},
            "constraint": "existence",
            "activity": "Supplier Review",
            "window": "after_mandatory_checks_before_approval",
        },
        {
            "when": {"sourcing": "internal"},
            "constraint": "absence",
            "activity": "Supplier Review",
        },
        {
            "when_event": "Correct Dossier",
            "attribute": "affected_checks",
            "constraint": "next_recheck_set_equals_attribute",
            "allowed_sets": [["Credit Check"], ["Technical Review"], ["Credit Check", "Technical Review"]],
        },
    ],
}

def posthoc_policy_flags(trace, case_attrs=None):
    """Return structured flags. Does not alter model_third's language."""
    case_attrs = case_attrs or {}
    flags = []
    activities = [e["concept:name"] for e in trace]

    def last_index(name, before=None):
        sl = activities if before is None else activities[:before]
        return max((i for i, a in enumerate(sl) if a == name), default=-1)

    for check in ("Credit Check", "Technical Review"):
        idxs = [i for i, a in enumerate(activities) if a == check]
        for prev, cur in zip(idxs, idxs[1:]):
            if "Correct Dossier" not in activities[prev + 1:cur]:
                flags.append({"rule": "P7", "severity": "block", "activity": check, "at": cur})

    if case_attrs.get("sourcing") == "external" and "Supplier Review" not in activities:
        flags.append({"rule": "P3", "severity": "block", "reason": "external without Supplier Review"})
    elif case_attrs.get("sourcing") == "internal" and "Supplier Review" in activities:
        flags.append({"rule": "P3", "severity": "block", "reason": "internal with Supplier Review"})
    elif "sourcing" not in case_attrs:
        flags.append({
            "rule": "P3",
            "severity": "review",
            "reason": "sourcing attribute missing; SR optionality is a data gap, not a policy skip",
        })

    for i, a in enumerate(activities):
        if a != "Correct Dossier":
            continue
        affected = None
        if isinstance(trace[i], dict):
            affected = trace[i].get("affected_checks")
        affected = affected or case_attrs.get("affected_checks")
        if not affected:
            flags.append({"rule": "P6", "severity": "review", "at": i,
                          "reason": "Correct Dossier without affected_checks"})
    return flags
```

## 7.4 Explicit semantics

| Requirement | How `model_third` implements it |
|---|---|
| Mandatory checks | `StrictPartialOrder({CC, TR})` with no silent child. Both must occur after Register and before repair/optional reviews/approval. Order is free. |
| Optional Supplier Review | XOR(SR, `tau`) *only after* the check/repair block. Optional because `sourcing` is not in the discovery log, **documented as a gap**, not as “SR is business-optional for everyone.” When the attribute arrives, the DECLARE hook tightens this XOR to existence or absence. |
| Expedite ordering | ER is not a peer of CC/TR. It sits in the later optional-review partial order, so it follows both mandatory checks (and any repairs) and precedes approval. It may precede or follow SR because those two nodes are unordered. |
| Exactly-one approval | XOR(Manager Approval, Auto Approval) as a single named stage. No path has both or neither. |
| Correction / recheck | Loop around a *named* XOR of recheck sets. Repeating a mandatory check without going through Correct Dossier is outside the language. Repeating only the affected check is *expressible*. Which of the three XOR arms is the *true* one remains unresolved until `affected_checks` exists; the unresolved case is flagged, not hidden as `tau`. |

## 7.5 Limitations from missing attributes

- **External/internal.** The backbone cannot require SR on true external cases or forbid it on true internal cases. Optional SR is an *over-approximation of P3*, not a claim that SR is discretionary. Silent optionalization of Credit Check / Technical Review is refused.
- **Affected check.** The XOR over-approximates P6: every syntactically legal recheck set is in the language. B6 is accepted at the control-flow layer and marked `review` until the attribute exists. The opposite wrong-arm choice (redo Credit Check when only Technical Review was affected) is also still in the language.
- **Secondary gaps.** The model sequences SR/ER after the repair loop. A world in which Supplier Review runs *during* an open correction, or Expedite must be redone after a late correction, is not represented. Those are undocumented in P1–P7 and are left to the change board rather than guessed into more `tau`s.
- **Duplicate labels.** Credit Check and Technical Review appear once in the initial AND and again in the repair XOR (two further copies if the “both” arm is counted separately). That is the minimum needed to make rework visible; it is not C’s 33-clone unfolding. Ownership is “the Check activity, initial vs rework occurrence,” which can be documented.

# 9. Validation Experiments

Do not trust another undocumented 80/20. Publish the experiment, then decide.

**A. Reproducible splits and preprocessing.** Fix `random_seed ∈ {7, 21, 42, 77, 99}`. Split on **case id**, never on events. Stratify, as far as the log allows, on: presence of Supplier Review, presence of Expedite Review, presence of Correct Dossier, approval type, and check order (CC before TR vs TR before CC). Write the case-id lists to disk. Preprocessing (lifecycle transition kept, incomplete cases kept or dropped, clock skew) is a checked-in notebook, not a slide.

**B. Attribute-stratified holdout.** Even while `sourcing` and `affected_checks` are missing, hold out by *proxies*: SR-present vs SR-absent; one-check-after-CD vs two-checks-after-CD. When attributes arrive, rebuild the split on the true labels and run the DECLARE hooks.

**C. Curated negative suite (minimum).** B3, B4, B8, A3; both approvals in one case; Release before approval; Expedite before both checks; Credit Check twice with no CD; start at Credit Check; Manager Approval then Auto Approval; empty review block + Auto Approval. A model proposed for compliance is **rejected** if any must-reject trace is in its language.

**D. Curated positive suite (minimum).** B1, B2, B5, B7, A1; TR-then-CC + Manager; CC-TR + ER + Auto (no SR); two repair cycles. A communication or simulation model is **rejected** if it fails these without a written policy citation.

**E. Perturbations.** Independently: drop one SR from SR-present cases; drop one mandatory check (must become a deviation on third and C, a non-event on S); duplicate a Credit Check without inserting CD; insert CD in a random legal position. Report detection rates, not a single fitness delta.

**F. Unseen-combination tests.** Build the Cartesian product of {check order} × {SR yes/no} × {ER yes/no} × {MA, AA} × {0, 1 repair} and remove any product that violates P1–P7. Score each model as accept/reject. This is the real generalization test; token-based generalization is reported *separately* and never as a substitute.

**G. Alignment-cost sensitivity.** Re-run alignments with standard unit costs and with log-move(mandatory check) ≥ 2 × log-move(SR). If S’s fitness advantage disappears when skipping CC/TR is expensive, the advantage was pathology 2.

**H. Soundness and reachability.** Convert every candidate to a Petri net. Require easy soundness. Replay B1–B8 and A1–A3 by construction (play-out / language check), not only by average fitness.

**I. Metrics, kept separate.** Fitness (alignments), precision (alignments) on *training positives*, precision on the **negative suite**, token-based generalization, arc-degree simplicity, median and p95 alignment time, duplicate-label count with a written formula: `(visible transition instances) − (unique labels)`. Never average them.

**J. Stakeholder protocol.** Twelve raters: four operations, four compliance, four IT. Each sees S, C, and third in counterbalanced order, unlabeled. Tasks: (1) mark B1–B8 accept/reject in 10 minutes from the diagram only; (2) point to the node to change if Auto Approval must allow SR; (3) explain what happens after Correct Dossier. Score task accuracy and time, plus a 1–5 confidence item. Report inter-rater agreement. Informal hallway scores are retired.

**K. Decision rule (reject despite pretty aggregates).** Reject for **compliance** if any of: language contains a must-reject probe; language misses a must-accept probe without a cited policy exception; Petri net is unsound; precision was not computed on a negative suite; split seeds and case ids are unpublished; mandatory activities are encoded as `X(a, tau)` without an attribute condition; duplicate-label count is driven by variant unfolding rather than rework. Reject for **exploration** only if holdout fitness is poor *and* residual traces are incomplete logging rather than new policy. Good averages never override a failed B3 or a failed B2.

# 10. Governance Recommendation

**Retire Model S as a control, a simulation of record, and an audit artifact.** It may remain in the exploration toolbox only if it is labeled, in the figure itself, “permissive coverage map — not policy.” F7 is accepted as a *use-case limit*, not as a waiver. Any dashboard that currently shows S’s 0.992 fitness as a health metric must be taken down; that number is the optional-mandatory pathology.

**Retire Model C as “the process model.”** Keep the eight sequences as a **frequent-variant catalog** for operations storytelling and as a source of positive-suite cases. Do not use C for conformance blocking, impact analysis, or ownership. F8 is a valid *change-management* stance, but it must be implemented as a review queue for unseen combinations, not as an XOR of last quarter’s movies branded audit-ready. The 0.941 precision does not survive F5.

**Adopt `model_third` as the candidate system of record for communication and for detective conformance**, not yet for fully automated hard-blocking, subject to the gates below.

Who uses what, until gates pass:

| Use | Allowed now | Not allowed |

**Conditions `model_third` must meet before deployment**

1. Published seeds, case-id splits, preprocessing, and alignment costs (Section 9A, 9G).
2. Sound Petri-net conversion; reachability of B1, B2, B5, B7, A1; unreachability of B3, B4, B8, A3.

# 11. Dissenting View

The conservative choice is to keep Model C as the enforcement language and send every F4 holdout case to a change board. This is a credit-and-release process: an unseen combination is not “unmeasured generalization,” it is work that nobody approved. The third model reopens two holes C closed on purpose. Supplier Review is optional again, so a genuinely external order can reach Release Order whenever the sourcing attribute is still missing—the situation we are in today. The correction XOR accepts every recheck subset, including the wrong one; calling that “transparency” does not stop a false negative. High training precision and a finite list of movies are exactly what an auditor can initial. A POWL with silent loop bodies and cloned check labels will revive alignment-cost games and will not stay readable once counsel asks what is possible after the third Correct Dossier. The 0.744 holdout figure is only an argument against C if those traces are legitimate. That labeling was never done. Until a gold negative suite and the two missing attributes exist, promoting an unscored hybrid over an inspectable allow-list is another discovery-team preference dressed as governance.

**What would change the decision.** If a dual-labeled holdout (compliant vs forbidden, labeled by Compliance, not by fitness) showed that most traces C rejects and the third model accepts are true violations, C would return as the blocking model and the third model would be demoted to explanation. If legal requires an explicit allow-list of variants, the right artifact is C *plus* a maintained variant-addition workflow, not a partial order. If the Section 9J protocol showed owners systematically misreading the recheck XOR, the third model would fail its own communication claim. If `sourcing` and `affected_checks` remain unavailable for another release cycle *and* missing Supplier Review is common on confirmed external cases, even the third model is too weak to detective-block P3 and should stay exploratory on that rule—while S would still remain unacceptable because it optionalizes the mandatory checks.
