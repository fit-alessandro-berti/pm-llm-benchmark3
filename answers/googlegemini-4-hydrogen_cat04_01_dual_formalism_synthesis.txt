# 1. Assumptions and Interpretation

1. **Low-risk vs. high-risk choice:** Because case risk attributes are not encoded as control-flow data guards, the risk route is modeled as an exclusive choice (`XOR`) between a low-risk branch (`Supervisor Review`) and a high-risk branch containing concurrent execution (`PARALLEL` / unconnected partial-order nodes) of `Quality Review` and `Regulatory Review`. Once `Analyze Root Cause` completes, the model nondeterministically selects one route; mixed selections (e.g., `Supervisor Review` together with `Quality Review`) are forbidden.
2. **Optional supplier consultation:** Because supplier involvement depends on unmodeled case data, `Consult Supplier` is modeled as an exclusive choice (`XOR`) between `Consult Supplier` and a silent skip transition ($\tau$). This guarantees at-most-once execution without requiring data conditions.
3. **Abstraction of passing vs. failing inspection:** Inspection outcomes are not distinct event labels. The repeat-until behavior is therefore represented using a structured loop (`LOOP(do, redo)`) with `do = Execute Trial -> Inspect Trial` and `redo = Adjust Parameters`. Every loop iteration ends with `Inspect Trial`; taking the loop exit after `Inspect Trial` represents a passing inspection, whereas taking the `redo` branch represents a failing inspection followed by parameter adjustment and a mandatory new trial cycle. Consequently, `Adjust Parameters` can never occur after the final (passing) `Inspect Trial`.
4. **No duplicate visible labels:** Duplicate visible activity labels are **not permitted** in either canonical model. Every one of the 14 activity labels appears exactly once. This preserves unambiguous 1-to-1 traceability between logged events and model nodes and avoids distorted conformance diagnostics or inflated state spaces.
5. **Process-tree approximation policy:** Because the narrative contains non-block-structured cross-branch dependencies, an exact duplicate-free process tree does not exist. We adopt a **conservative under-approximation** policy ($L(\text{tree}) \subsetneq L(\text{intended})$): the tree never admits unsafe or out-of-order traces (such as starting trials before verification planning or releasing material before approvals complete), at the cost of introducing a synchronization barrier that restricts when `Risk Route` and `Consult Supplier` may start.
6. **Interpretation of "may overlap":** Activities are recorded only at completion time, so true execution intervals are unobservable in traces. "May overlap" is therefore interpreted as **partial-order independence (absence of precedence constraints)**—meaning neither activity must complete before the other begins, and both completion orders are admissible in trace semantics.
7. **Case boundary and atomicity:** Every trace represents a single material-deviation case starting with `Register Deviation` and ending with `Archive Case`, with no concurrent multi-case interference.

# 3. PM4Py Process-Tree Model

1. **Compact process-tree expression**

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->('Analyze Root Cause', 'Design Corrective Action')
  ),
  +(
    *(
      ->('Execute Trial', 'Inspect Trial'),
      'Adjust Parameters'
    ),
    X(
      'Supervisor Review',
      +('Quality Review', 'Regulatory Review')
    ),
    X('Consult Supplier', tau)
  ),
  'Release Material',
  'Archive Case'
)
```

2. **Self-contained Python code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def make_node(operator=None, label=None, children=None):
    node = ProcessTree(operator=operator, label=label)
    if children:
        for child in children:
            child.parent = node
            node.children.append(child)
    return node


# Phase 1: Registration
reg = make_node(label="Register Deviation")

# Phase 2: Parallel containment/planning and root-cause/design streams
contain_plan = make_node(
    operator=Operator.SEQUENCE,
    children=[
        make_node(label="Contain Material"),
        make_node(label="Plan Verification"),
    ],
)

arc_design = make_node(
    operator=Operator.SEQUENCE,
    children=[
        make_node(label="Analyze Root Cause"),
        make_node(label="Design Corrective Action"),
    ],
)

prep_parallel = make_node(
    operator=Operator.PARALLEL,
    children=[contain_plan, arc_design],
)

# Phase 3: Concurrent trial loop, risk-route approval, and optional supplier consultation
trial_body = make_node(
    operator=Operator.SEQUENCE,
    children=[
        make_node(label="Execute Trial"),
        make_node(label="Inspect Trial"),
    ],
)

trial_loop = make_node(
    operator=Operator.LOOP,
    children=[
        trial_body,
        make_node(label="Adjust Parameters"),
    ],
)

high_risk_reviews = make_node(
    operator=Operator.PARALLEL,
    children=[
        make_node(label="Quality Review"),
        make_node(label="Regulatory Review"),
    ],
)

risk_route = make_node(
    operator=Operator.XOR,
    children=[
        make_node(label="Supervisor Review"),
        high_risk_reviews,
    ],
)

opt_supplier = make_node(
    operator=Operator.XOR,
    children=[
        make_node(label="Consult Supplier"),
        make_node(label=None),  # silent tau transition
    ],
)

execution_parallel = make_node(
    operator=Operator.PARALLEL,
    children=[trial_loop, risk_route, opt_supplier],
)

# Phase 4: Release and archiving
release = make_node(label="Release Material")
archive = make_node(label="Archive Case")

# Root process tree
tree = make_node(
    operator=Operator.SEQUENCE,
    children=[reg, prep_parallel, execution_parallel, release, archive],
)
```

3. **Mapping to the narrative:** The root `SEQUENCE` enforces `Register Deviation` first and `Release Material -> Archive Case` last. The first `PARALLEL` block pairs `Contain Material -> Plan Verification` with `Analyze Root Cause -> Design Corrective Action`, synchronizing both branches before `execution_parallel` begins. Inside `execution_parallel`, the `LOOP` encodes `Execute Trial -> Inspect Trial` with `Adjust Parameters` on the redo branch, while `XOR` encodes the risk-route choice and the optional `Consult Supplier` branch runs concurrently with both the trial loop and approvals.

4. **Representational limitations and approximation details:** A duplicate-free process tree can only represent series-parallel (N-free) partial orders. However, the intended dependencies contain embedded **N-posets**, such as `{Plan Verification, Trial Loop, Analyze Root Cause, Risk Route}` where `Plan Verification < Trial Loop`, `Analyze Root Cause < Trial Loop` (via `Design Corrective Action`), and `Analyze Root Cause < Risk Route`, with no other ordering among those four elements (and symmetrically with `Consult Supplier` in place of `Risk Route`). Consequently, `tree` approximates the intended process by placing `risk_route` and `opt_supplier` *after* the `prep_parallel` barrier rather than immediately after `Analyze Root Cause`. This preserves every safety/precedence constraint—including overlap of approvals and `Consult Supplier` with the trial cycle—but introduces two conservative overconstraints: (i) neither `risk_route` nor `Consult Supplier` can start until `Contain Material`, `Plan Verification`, and `Design Corrective Action` have all finished, and (ii) `Consult Supplier` can no longer overlap `Design Corrective Action` or `Plan Verification`.

# 4. PM4Py POWL Model

1. **Compact POWL description**

```text
PO(
  nodes={
    reg: 'Register Deviation',
    contain: 'Contain Material',
    arc: 'Analyze Root Cause',
    plan_ver: 'Plan Verification',
    design_ca: 'Design Corrective Action',
    risk_route: X('Supervisor Review', PO(nodes={'Quality Review', 'Regulatory Review'}, order={})),
    opt_supplier: X('Consult Supplier', tau),
    trial_loop: *(PO(nodes={'Execute Trial', 'Inspect Trial'}, order={'Execute Trial' --> 'Inspect Trial'}), 'Adjust Parameters'),
    release: 'Release Material',
    archive: 'Archive Case'
  },
  order={
    reg --> contain,
    reg --> arc,
    contain --> plan_ver,
    arc --> design_ca,
    arc --> risk_route,
    arc --> opt_supplier,
    plan_ver --> trial_loop,
    design_ca --> trial_loop,
    trial_loop --> release,
    risk_route --> release,
    opt_supplier --> release,
    release --> archive
  }
)
```

2. **Self-contained Python code**

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Leaf transitions
reg = Transition(label="Register Deviation")
contain = Transition(label="Contain Material")
arc = Transition(label="Analyze Root Cause")
plan_ver = Transition(label="Plan Verification")
design_ca = Transition(label="Design Corrective Action")

sup_rev = Transition(label="Supervisor Review")
qual_rev = Transition(label="Quality Review")
reg_rev = Transition(label="Regulatory Review")

consult_sup = Transition(label="Consult Supplier")
tau_sup = SilentTransition()

exec_trial = Transition(label="Execute Trial")
insp_trial = Transition(label="Inspect Trial")
adjust_params = Transition(label="Adjust Parameters")

release = Transition(label="Release Material")
archive = Transition(label="Archive Case")

# Submodel 1: Risk route (low-risk XOR concurrent high-risk)
high_risk_po = StrictPartialOrder(nodes=[qual_rev, reg_rev])
risk_route = OperatorPOWL(
    operator=Operator.XOR,
    children=[sup_rev, high_risk_po],
)

# Submodel 2: Optional supplier consultation
opt_supplier = OperatorPOWL(
    operator=Operator.XOR,
    children=[consult_sup, tau_sup],
)

# Submodel 3: Trial repeat-until loop
trial_body = StrictPartialOrder(nodes=[exec_trial, insp_trial])
trial_body.order.add_edge(exec_trial, insp_trial)

trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, adjust_params],
)

# Top-level strict partial order
powl = StrictPartialOrder(
    nodes=[
        reg,
        contain,
        arc,
        plan_ver,
        design_ca,
        risk_route,
        opt_supplier,
        trial_loop,
        release,
        archive,
    ]
)

# Direct partial-order precedence edges
powl.order.add_edge(reg, contain)
powl.order.add_edge(reg, arc)

powl.order.add_edge(contain, plan_ver)

powl.order.add_edge(arc, design_ca)
powl.order.add_edge(arc, risk_route)
powl.order.add_edge(arc, opt_supplier)

powl.order.add_edge(plan_ver, trial_loop)
powl.order.add_edge(design_ca, trial_loop)

powl.order.add_edge(trial_loop, release)
powl.order.add_edge(risk_route, release)
powl.order.add_edge(opt_supplier, release)

powl.order.add_edge(release, archive)
```

3. **Why every pair of intentionally unconnected nodes may remain concurrent:**
   - **`Quality Review` vs. `Regulatory Review` (inside `high_risk_po`):** Requirement 5 explicitly allows both high-risk reviews to occur concurrently and complete in either order.
   - **`Contain Material` vs. `{Analyze Root Cause, Design Corrective Action, risk_route, opt_supplier}`:** Containment and root-cause analysis are independent streams after `Register Deviation` (Requirement 2). Because `Design Corrective Action`, `risk_route`, and `opt_supplier` depend only on `Analyze Root Cause` (Requirements 4–6), they are free to run concurrently with containment.
   - **`Plan Verification` vs. `{Analyze Root Cause, Design Corrective Action, risk_route, opt_supplier}`:** `Plan Verification` depends solely on `Contain Material` (Requirement 3), so it may proceed concurrently with root-cause analysis, corrective-action design, approvals, and supplier consultation before synchronizing with `Design Corrective Action` at `trial_loop`.
   - **`Design Corrective Action` vs. `{risk_route, opt_supplier}`:** All three branch independently out of `Analyze Root Cause`; `Design Corrective Action` feeds the trial, whereas `risk_route` and `opt_supplier` feed `Release Material` directly (Requirements 4–6).
   - **`risk_route` vs. `{trial_loop, opt_supplier}`:** Requirement 7 states that the selected approval route need not finish before the trial starts and may overlap the trial cycle, and Requirement 6 permits `Consult Supplier` to overlap approvals.
   - **`opt_supplier` vs. `trial_loop`:** Requirement 6 explicitly permits `Consult Supplier` to overlap trial work as long as it finishes before `Release Material`.

# 7. Preferred Representation and Validation Plan

**Canonical representation choice:** **POWL (`powl`)** is the preferred canonical representation. Unlike the process tree—which must either sacrifice intended early-start and overlap concurrency (conservative under-approximation) or duplicate subtrees (harming maintainability and analytics)—POWL captures the non-series-parallel partial order *exactly* using `StrictPartialOrder` edges and `OperatorPOWL` choice/loop nodes, while keeping all 14 activity labels unique. The process tree (`tree`) remains useful only as a block-structured fallback for tooling that strictly requires process trees.

**Concrete validation plan:**

1. **Accepting Petri net conversion:** Convert both `tree` and `powl` to accepting Petri nets via `pm4py.convert_to_petri_net(model)` (producing `(net, initial_marking, final_marking)`), and visually inspect the converted POWL net to confirm that the `AND`-splits after `Register Deviation` and `Analyze Root Cause`, as well as the `AND`-joins before `trial_loop` and `Release Material`, are faithfully synthesized without spurious barriers.
2. **Soundness verification:** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on both converted accepting Petri nets to confirm easy soundness / behavioral soundness (no dead transitions, no deadlocks, guaranteed reachability of the final marking from every reachable marking).
3. **Bounded sampled playout:** Generate synthetic event logs using `pm4py.play_out(model, ...)` on both `tree` and `powl` (capping the number of generated traces, e.g., `no_traces=1000`, and bounding loop repetitions). Verify that every trace generated from `tree` is also replayable on `powl` (empirically corroborating $L(\text{tree}) \subseteq L(\text{powl})$), and verify that `powl` playout produces valid early-review/early-supplier traces such as T3 and T4.
4. **Explicit positive and negative trace testing:** Encode the 8 witnesses (T1–T8) as a `pm4py` `EventLog` and run exact alignments (`pm4py.conformance_diagnostics_alignments`) or token-based replay against both converted Petri nets. Confirm that:
   - T1, T2, T5 achieve fitness $1.0$ on both `tree` and `powl`;
   - T3, T4 achieve fitness $1.0$ on `powl` and fitness $< 1.0$ on `tree`;
   - T6, T7, T8 achieve fitness $< 1.0$ on both `tree` and `powl`, with deviation diagnostics pinpointing the expected earliest violated events (`Execute Trial` for T6, `Release Material` for T7 and T8).
5. **Silent-behavior and duplicate-label audit:** Programmatically inspect all transitions in the converted Petri nets to assert (a) every visible label in the 14-activity alphabet maps to **exactly one** visible transition (zero duplicates), and (b) silent ($\tau$) transitions appear solely for structural routing (XOR selection, optional supplier skip, loop entry/exit, and partial-order joins) and cannot form zero-cost silent cycles (livelocks) or bypass `Release Material` prerequisites.
6. **Limitations of the validation plan:**
   - Finite sampled playout cannot prove full language equivalence or inclusion across unbounded loop iterations.
   - Structural soundness only verifies generic Petri net well-formedness (e.g., option to complete), not alignment with the informal business narrative.
   - Trace replay evaluates completion-time interleavings only and cannot verify true physical interval overlap.
   - Control-flow validation cannot verify whether real cases follow the unmodeled data rules (e.g., that high-risk cases actually trigger `Quality Review` and `Regulatory Review` rather than `Supervisor Review`).

# 8. Final Self-Critique

1. **Completion-time abstraction blurs concurrency and sequencing (semantic weakness):** Because the models represent activities as atomic completion events in an interleaved trace semantics, neither `powl` nor `tree` distinguishes an overlapping execution interval (e.g., `Consult Supplier` started before `Plan Verification` finished) from a strictly sequential execution where `Consult Supplier` waited until `Plan Verification` finished. Modeling explicit `start` and `complete` lifecycle transitions would capture interval overlap precisely, but at the cost of doubling the alphabet and complicating readability.
2. **Unmodeled data correlation permits semantically inconsistent combinations (semantic weakness):** By abstracting away data attributes, both models allow a "high-risk" case in reality to conformally take `Supervisor Review` (or exit the trial loop after one cycle despite a failed inspection), because those rules live in external case data rather than event labels. Without guard expressions or outcome-qualified labels (e.g., `Inspect Trial (Pass)` vs. `Inspect Trial (Fail)`), conformance checking can validate structural ordering but not decision correctness.
3. **Analytic construction without live runtime execution (technical/methodological weakness):** The Python models and validation steps were verified analytically against PM4Py's documented `ProcessTree` and `POWL` semantics rather than executed in a live PM4Py environment here. Minor version-specific API behaviors—such as whether a particular PM4Py release expects only covering edges or explicit transitive closure in `StrictPartialOrder` validation, or how `play_out` bounds `Operator.LOOP` depth—must be confirmed when running the validation script.
