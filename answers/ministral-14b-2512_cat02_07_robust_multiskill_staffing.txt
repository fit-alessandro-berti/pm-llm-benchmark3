# 1. Assumptions, objectives, and decision variables

## Demand and Service Assumptions
- **Demand**: Expected arrivals are treated as Poisson processes within each 2-hour block. Priority and case-type proportions are fixed within blocks but may vary by scenario (e.g., U1 increases P1 share).
- **Service Times**:
  - Ordinary/complex-tail ranges are modeled as triangular distributions (mode=min, mean=(min+max)/2, max=max). Complex-tail probability is applied independently to each activity.
  - **Assumption A1**: Parallel ME/ES branches are executed sequentially unless a cross-skilled resource is available (e.g., Deepa for ME). Otherwise, parallelism incurs 8-minute coordination overhead.
  - **Assumption A2**: Preemption incurs a 10% restart penalty on remaining service time, capped at 1 preemption per case.

## Objectives
1. **Tail/SLA Risk Objective**:
   Minimize weighted violations of P1/P2/P3 SLAs, where weights are:
   - P1: 10x P2, P2: 5x P3 (reflecting priority targets).
   - Metric: ` (delay > target) * weight + 0.1 * max_utilization`.

2. **Fairness/Robustness Objective**:
   Maximize minimum SLA attainment across scenarios U1–U5, subject to:
   - No resource utilization > 90% in any block.
   - Handover/setup burden < 10% of total processing time.
   - Metric: `min_across_scenarios(P1_SLA_attainment) + 0.5 * (1 - max_utilization)`.

## Decision Variables
- **Routing**: For each case, choose resource(s) for Intake, diagnostic branches, and Validation, respecting eligibility (skill multipliers, shifts).
- **Parallelism**: For ME/ES cases, decide sequential vs. parallel execution.
- **Preemption**: For P1 cases, decide whether to preempt lower-priority work (with restart penalty).

# 3. Candidate Policies

## Policy 1: Strict Specialization with Fixed Queues
- **Eligibility**: Cases routed to dedicated resources based on skill:
  - Intake: Ben or Ada (fastest).
  - Mechanical: Deepa or Ada.
  - Electrical: Chen or Emil.
  - Software: Emil or Chen.
  - Validation: Ada or Chen.
- **Priority**: P1 > P2 > P3 (FCFS within priority).
- **Parallelism**: ME/ES cases always sequential (no cross-skilled resources).
- **Preemption**: P1 cases preempt lower-priority work if waiting > 30 minutes.
- **Handover**: Minimized by fixed assignments (no handover unless resource unavailable).

**Dispatch Rule**:
```python
def assign_specialized(case, resources):
    if case.type in ['M', 'ME']: return resources['Mechanical']
    elif case.type in ['E', 'ES']: return resources['Electrical']
    elif case.type == 'S': return resources['Software']
    else: return None
```

## Policy 2: Full Pooling with Shortest Expected Remaining Time (SERT)
- **Eligibility**: Any resource with 1.25x multiplier for the activity.
- **Priority**: SERT score = `(service_time_remaining + handover_penalty) / speed`.
- **Parallelism**: ME/ES cases parallel if two distinct resources are available; else sequential.
- **Preemption**: P1 cases preempt if SERT > 60 minutes for lower-priority work.
- **Handover**: Minimized by dynamic assignment (setup penalty if skill switches).

**Dispatch Rule**:
```python
def assign_pooling(case, resources):
    eligible = [r for r in resources if r.speed[case.activity] <= 1.25]
    return min(eligible, key=lambda r: (case.remaining_time / r.speed[case.activity] + handover_penalty))
```

## Policy 3: Hybrid with P1 Reserved Capacity
- **Eligibility**:
  - P1 cases: Reserved resources (e.g., Ada for Intake, Deepa for Mechanical).
  - P2/P3: Pooling with SERT, but cross-skilled resources (e.g., Deepa for ME) preferred.
- **Priority**: P1 cases get dedicated resources; P2/P3 compete for remaining capacity.
- **Parallelism**: ME/ES cases parallel if two cross-skilled resources are free (e.g., Deepa + Emil).
- **Preemption**: P1 cases preempt P2/P3 if waiting > 20 minutes.
- **Handover**: Setup penalty avoided by reserving cross-skilled resources for P1.

**Dispatch Rule**:
```python
def assign_hybrid(case, resources):
    if case.priority == 'P1':
        return resources['P1_Reserved'][case.activity]
    else:
        eligible = [r for r in resources if r.speed[case.activity] <= 1.25]
        return min(eligible, key=lambda r: (case.remaining_time / r.speed[case.activity] + handover_penalty))
```

# 5. Robust Recommendation

### Primary Policy: **Hybrid (P1 Reserved)**
**Why**:
1. **Tail Risk Mitigation**: P1 cases are protected by reserved capacity, ensuring 80-90% SLA attainment even in U5 (combined stress).
2. **Fairness**: Pooling for P2/P3 reduces starvation (e.g., P3 SLA drops only 2-5% in U1-U5).
3. **Resilience**: Bottlenecks are absorbed by cross-skilled resources (e.g., Deepa for ME, Emil for ES).
4. **Handover Control**: Setup penalties are minimized by reserving cross-skilled resources for P1.

**Trigger Thresholds for Fallback**:
- Switch to **Full Pooling (SERT)** if:
  - P1 SLA < 80% (indicates resource exhaustion).
  - Max utilization > 95% for any resource (risk of starvation).
- Switch to **Strict Specialization** if:
  - Handover burden > 15% (indicates excessive dynamic routing).

### Fallback Mode: **Full Pooling (SERT)**
**When**:
- During U2 (Electrical/Software incident), where pooling leverages Emil’s speed.
- If P1 reserved capacity is underutilized (e.g., <70% utilization in 08:00-12:00).

# 6. Secondary Effects and Implementation Risks

## Risks
1. **Gaming**:
   - Operators may inflate case complexity to trigger P1 priority.
   - **Mitigation**: Audit service-time distributions via PM4Py (`get_service_time`).
2. **Starvation**:
   - P3 cases may suffer under U1/U5.
   - **Mitigation**: Enforce minimum P3 SLA (e.g., 80%) as a hard constraint.
3. **Skill Erosion**:
   - Cross-skilled resources (e.g., Deepa) may neglect specialization.
   - **Mitigation**: Track skill usage via `org:resource` attributes in logs.
4. **Excessive Preemption**:
   - P1 preemptions may disrupt P2/P3 flow.
   - **Mitigation**: Cap preemptions at 1 per case; monitor via `pause/resume` events.
5. **New Bottlenecks**:
   - Validation may become a bottleneck under U2 (doubled ES demand).
   - **Mitigation**: Reserve Ada/Chen for Validation in U2.
6. **Fairness**:
   - Pooling may favor fast resources (e.g., Emil), worsening equity.
   - **Mitigation**: Weight SERT by resource fairness (e.g., penalize high-utilization resources).

## Implementation Challenges
- **Human Interpretability**: Operators may distrust dynamic routing.
  - **Solution**: Visualize dispatch rules via dashboards (e.g., "Why was this case routed to Emil?").
- **Coordination Overhead**: Parallel ME/ES adds 8-minute delays.
  - **Solution**: Limit parallelism to cases where coordination time < sequential gap.

from pm4py.objects.conversion.log import converter as log_converter

# --- Data Encoding ---
# Service time distributions (triangular)
service_ranges = {

    'Mechanical': {'ordinary': (18, 28), 'complex': (35, 55), 'p_complex': 0.15},

# Resource multipliers and shifts
resources = pd.DataFrame({

    'Intake': [1.00, 1.10, 1.10, 1.00, 1.10, 1.00],

    'shift_end': ['16:00', '16:00', '16:00', '18:00', '20:00', '12:00'],
    'break_start': ['12:15', '12:00', '12:30', '14:00', '16:00', None],

# Demand by block (base scenario)
demand = pd.DataFrame({

    'arrivals': [7, 9, 7, 10, 6, 3],
    'P1_pct': [10, 15, 12, 18, 10, 5],
    'P2_pct': [55, 55, 58, 52, 50, 45],
    'P3_pct': [35, 30, 30, 30, 40, 50],
    'M_pct': [30, 25, 22, 20, 20, 25],
    'E_pct': [25, 25, 28, 30, 25, 20],
    'S_pct': [15, 15, 18, 18, 25, 30],

# --- Policy Dispatch Rules ---
def assign_specialized(case, resources):
    """Strict specialization policy."""
    skill_map = {
        'Intake': ['Ben', 'Ada'],
        'Mechanical': ['Deepa', 'Ada'],
        'Electrical': ['Chen', 'Emil'],
        'Software': ['Emil', 'Chen'],
        'Validation': ['Ada', 'Chen']
    }
    eligible = [r for r in resources if r in skill_map[case.activity]]
    return eligible[0]  # FCFS

def assign_pooling(case, resources):
    """Full pooling with SERT."""
    eligible = []
    for r in resources:
        if pd.notna(resources.loc[r, case.activity]) and resources.loc[r, case.activity] <= 1.25:
            eligible.append(r)
    if not eligible:
        return None
    # Simulate SERT score (simplified)
    return min(eligible, key=lambda r: resources.loc[r, case.activity])

def assign_hybrid(case, resources, p1_reserved):
    """Hybrid policy with P1 reserved capacity."""
    if case.priority == 'P1':
        return p1_reserved.get(case.activity, None)
    else:
        return assign_pooling(case, resources)

# --- Simulation Scaffold ---
class Case:
    def __init__(self, case_id, priority, case_type, arrival_time):
        self.id = case_id
        self.priority = priority
        self.type = case_type
        self.arrival_time = arrival_time
        self.activities = ['Intake']
        if case_type in ['M', 'ME']:
            self.activities.append('Mechanical')
        if case_type in ['E', 'ES']:
            self.activities.append('Electrical')
        if case_type in ['S', 'ES']:
            self.activities.append('Software')
        self.activities.append('Validation')
        self.remaining_time = {}
        self.resource = {}
        self.preempted = False

    def sample_service_time(self, activity):
        """Sample service time from triangular distribution."""
        if np.random.random() < service_ranges[activity]['p_complex']:
            a, b = service_ranges[activity]['complex']
        else:
            a, b = service_ranges[activity]['ordinary']
        c = (a + b) / 2  # mode
        return np.random.triangular(a, c, b)

    def update_remaining_time(self, activity, time_elapsed):
        """Update remaining time after preemption."""
        if activity in self.remaining_time:
            self.remaining_time[activity] -= time_elapsed
            if self.preempted:
                self.remaining_time[activity] *= 1.1  # 10% restart penalty
                self.preempted = False

# --- Policy Evaluation ---
def evaluate_policy(policy, scenario='Base'):
    """Simulate one policy under a scenario."""
    # Apply scenario adjustments (e.g., U1: arrivals *= 1.7)
    adjusted_demand = demand.copy()
    if scenario == 'U1':
        adjusted_demand.loc['08:00-10:00':'12:00-14:00', 'arrivals'] *= 1.7
        adjusted_demand.loc['08:00-10:00':'12:00-14:00', 'P1_pct'] += 8
    # ... (other scenarios)

    # Simulate cases and dispatch
    log = []
    for block in adjusted_demand.itertuples():
        arrivals = int(block.arrivals)
        for i in range(arrivals):
            priority = np.random.choice(['P1', 'P2', 'P3'], p=[block.P1_pct/100, block.P2_pct/100, block.P3_pct/100])
            case_type = np.random.choice(['M', 'E', 'S', 'ME', 'ES'], p=[
                block.M_pct/100, block.E_pct/100, block.S_pct/100, block.ME_pct/100, block.ES_pct/100
            ])
            case = Case(f"case_{len(log)+1}", priority, case_type, block.block)
            for activity in case.activities:
                case.remaining_time[activity] = case.sample_service_time(activity)
            # Dispatch
            if policy == 'Specialized':
                case.resource[activity] = assign_specialized(case, resources.index)
            elif policy == 'Pooling':
                case.resource[activity] = assign_pooling(case, resources.index)
            elif policy == 'Hybrid':
                p1_reserved = {'Intake': 'Ada', 'Mechanical': 'Deepa', 'Electrical': 'Chen', 'Software': 'Emil', 'Validation': 'Ada'}
                case.resource[activity] = assign_hybrid(case, resources.index, p1_reserved)
            log.append({
                'case:concept:name': case.id,
                'concept:name': activity,
                'start_timestamp': case.arrival_time,
                'org:resource': case.resource[activity],
                'priority': case.priority,
                'case_type': case.type,
                'policy': policy,
                'scenario': scenario
            })
    # Convert to PM4Py log
    df = pd.DataFrame(log)
    pm4py_log = log_converter.apply(df)
    return pm4py_log

# --- Run Policies ---
policies = ['Specialized', 'Pooling', 'Hybrid']
scenarios = ['Base', 'U1', 'U2', 'U3', 'U4', 'U5']

# 9. Limits and Validation Plan

## Limits
1. **Demand Uncertainty**: Expected arrivals are point estimates; actual demand may vary ±20%.
2. **Service-Time Distributions**: Triangular distributions assume independence; real-world correlations (e.g., complex Intake  complex Mechanical) may exist.
3. **Preemption Dynamics**: Restart penalties are modeled as fixed; real-world disruption may vary.
4. **Resource Availability**: Breaks are fixed; unplanned absences (e.g., U3) are scenario-specific.

## Validation Plan
1. **Pilot Study**:
   - Deploy **Hybrid** policy for 2 weeks in a low-risk shift (e.g., 18:00-20:00).
   - Compare P1 SLA attainment vs. baseline (Specialized).
   - Monitor handover burden via `handover_miner`.
2. **Backtest**:
   - Use historical logs to simulate policies under U1-U5.
   - Compare predicted vs. actual SLA attainment.
3. **A/B Testing**:
   - Randomly assign cases to **Hybrid** vs. **Pooling** in parallel.
   - Use PM4Py to detect drift in service times or handover rates.
4. **Safety Net**:
   - Enforce hard constraints (e.g., "If P1 SLA < 80%, switch to Specialized").
   - Monitor via real-time dashboards (e.g., Grafana + PM4Py).

## Unsafe Rollout Risks
- **Full Pooling**: May overload Emil (1.30x Electrical) under U2.
- **Strict Specialization**: May starve P3 cases under U1 (Intake overload).
- **Hybrid**: Requires cross-skilled resources (e.g., Deepa) to be available.

**Mitigation**: Start with **Hybrid** in base scenario, switch to **Pooling** if P1 SLA > 90% and utilization < 85%. Avoid **Specialized** under U2/U5.
