## **1. Conformance Semantics**

### **Key Distinctions**
1. **Forbidden Behavior**
   - Explicitly prohibited by the norm (e.g., `Cancel Order  Dispatch Package` under **N3**).
   - Closed-world assumption: absence is irrelevant; presence is a violation.
   - *Example*: The two observed `Cancel Order  Dispatch Package` relations are **forbidden** and require immediate remediation.

2. **Missing Mandatory Behavior**
   - Required by the norm but absent in the observed log.
   - Open-world assumption: absence may be due to:
     - **Abstraction mismatch** (e.g., indirect paths not captured in directly-follows).
     - **Data quality** (e.g., missing events in the log).
     - **Temporary noncompliance** (e.g., exceptions not yet documented).
   - *Example*: Two `Create Order  Validate Order` relations are missing (**N1**), but the norm allows indirect paths.

3. **Unexpected but Unregulated Behavior**
   - Observed relations not covered by the norm (status **unspecified** or **typical**).
   - Open-world assumption: absence does not imply violation.
   - *Example*: `Reopen Order  Close Order` (**N6**) is unspecified; its presence is benign.

4. **Typical-Pattern Absence**
   - Common but not mandatory relations missing (e.g., `Issue Invoice  Record Payment` at 92/110).
   - Open-world assumption: deviations may be acceptable if within tolerance (e.g., write-offs, unapplied cash).
   - *Example*: 14 invoices lack successors (**N5**), but write-offs are a legitimate exception.

5. **Likely Data-Quality Error**
   - Artifacts of poor data collection, not process violations.
   - *Examples*:
     - `Sensor Heartbeat  Invoice` (**E10**) is forbidden, but likely a join error.
     - `Dispatch Package` without `Delivery` relation (2/200) may use carrier attributes instead.

6. **Abstraction Mismatch**
   - Norm assumes directly-follows relations, but business reality involves intermediate steps.
   - *Example*: `Create Order  Validate Order` (**N1**) may have unrecorded intermediate reviews.

7. **Insufficient Evidence**
   - Observations too rare or ambiguous to classify.
   - *Example*: `Manual Compliance Review  RiskCase` (3/3) is unspecified but lacks context.

### **Open-World vs. Closed-World Implications**
- **Closed-world**: Only forbidden relations and mandatory edges within scope are enforced. Absence is irrelevant; presence is a violation.
  - *Applies to*: **N3** (forbidden), **N1** (mandatory within scope).
- **Open-world**: All other relations are permissible unless explicitly forbidden or mandatory.
  - *Applies to*: **N2**, **N5**, **N6**, **T3**, **T4**, **E9**.
  - **Risk**: Over-interpretation of missing edges (e.g., assuming `Validate Order  Issue Invoice` is mandatory when it’s typical).

## **3. Detailed Reasoning by Model Family**

### **OC-DFG (Object-Centric Direct-Follows Graph)**
- **Establishes**: Direct transitions between object states (e.g., `Create Order  Validate Order`).
- **Cannot establish**:
  - Indirect paths (e.g., `Create Order  Review  Validate Order`).
  - Temporal gaps (e.g., unrecorded intermediate events).
- **Counts and scopes**:
  - **N1 (Create Order  Validate Order)**: 98/100 conforms; 2/100 may reflect abstraction mismatch.
  - **N3 (Cancel Order  Dispatch Package)**: 2/100 is a **forbidden** violation (closed-world).
- **Abstraction danger**:
  - Norm assumes directly-follows, but business may use intermediate events (e.g., `Manual Compliance Review` between `Create Order` and `Validate Order`).

### **OTG (Object-Transition Graph)**
- **Establishes**: Required interactions (e.g., `Add Item` must link `Order` and `Item`).
- **Cannot establish**:
  - Optional interactions (e.g., `Manual Compliance Review`).
  - Alternative representations (e.g., carrier attributes instead of `Delivery`).
- **Counts and scopes**:
  - **T2 (Package  Delivery)**: 198/200 conforms; 2/200 may use carrier attributes (data-quality edge).
  - **T6 (Order  Payment cobirth)**: 1/100 is **forbidden** (closed-world).
- **Interpretation risk**:
  - Missing `Delivery` for 2 `Dispatch Package` events may not violate **T2** if carrier attributes are normative.

### **ET–OT (Event-Object-Tuple)**
- **Establishes**: Required object creation per event (e.g., `Create Order` must create an `Order`).
- **Cannot establish**:
  - Optional objects (e.g., `RiskCase` in `Manual Compliance Review`).
  - Data-quality errors (e.g., `Sensor Heartbeat  Invoice`).
- **Counts and scopes**:
  - **E10 (Sensor Heartbeat  Invoice)**: 1/100 is **forbidden** but likely a data error (open-world exception).
  - **E8 (Record Payment  Invoice)**: 92/93 conforms; 1/93 may be unapplied cash (typical exception).
- **Abstraction danger**:
  - Norm assumes `Record Payment` always links to `Invoice`, but unapplied cash is an exception.

def classify_conformance(observed, normative, model_type):
    conformance = pm4py.conformance.[model_type](observed, normative)
    # Add semantic classification layer
    for edge in conformance["violations"]:
        edge["semantic_class"] = classify_edge(edge, normative)
    return conformance

def classify_edge(edge, normative):
    if normative[edge]["status"] == "forbidden":
        return "forbidden_behavior"
    elif normative[edge]["status"] == "mandatory" and edge not in observed:
        return "missing_mandatory"
    elif normative[edge]["status"] == "typical" and edge not in observed:
        return "typical_absence"
    else:
        return "unregulated"

# Apply to all models
ocdfg_conformance = classify_conformance(observed_ocdfg, norm_ocdfg, "ocdfg")
otg_conformance = classify_conformance(observed_otg, norm_otg, "otg")
etot_conformance = classify_conformance(observed_etot, norm_etot, "etot")

# Preserve raw diagnostics and add semantic tags
print("OC-DFG Conformance with Semantics:", ocdfg_conformance)
print("OTG Conformance with Semantics:", otg_conformance)
print("ET-OT Conformance with Semantics:", etot_conformance)
