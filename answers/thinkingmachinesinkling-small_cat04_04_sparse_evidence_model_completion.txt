# 2. Shared Assumptions

All three candidates share the following assumptions, which are explicitly disclosed because they affect interpretation of missingness versus true optionality:

1. **Event-completion semantics (S7).** Only the completion timestamp is recorded. If two activities finish in the same second, ingestion index determines log order. All three models therefore treat sequence edges as *completion-order* relationships, not necessarily *start-order* relationships.
2. **Missing Supplier Confirmation is ambiguous (S3–S5).** The absence of SC in 7 traces is interpreted as either (a) a legitimate skip because components are stocked (S4), or (b) an integration omission (S5). None of the models assumes SC absence is always a true skip; rather, conservative treats observed absence as exact, balanced treats SC as genuinely optional, and permissive treats absence as either skip or loss.
3. **No external/stocked attribute (S5).** Because the attribute is not exported, SC optionality is represented as a control-flow alternative (XOR/optional branch) rather than a data-conditional branch. This is an abstraction; if the attribute were available, SC could be made data-dependent.
4. **Activity labels are unique.** “Archive Case” and “Approve Configuration” are distinct; “Expedite Review” is unique.
5. **D1, D2, D3, D6 are hard constraints.** All models enforce: RO first, Arc last, ACRP, both CC/ER before AC, Exp (if present) after both checks and before AC.
6. **At most one Exp (D6).** No model permits repetition of Expedite Review.
7. **Optionality representation.** Optional activities (SC, Exp) are encoded via XOR branches or optional transitions; this abstracts away the underlying “missing data” mechanism.

**Inductive-bias statement:** Generalize to concurrent or overlapping execution of Credit Check and Engineering Review (S2, D7), allow Supplier Confirmation to overlap with them (D5), and permit optional SC/Exp, but enforce hard precedence from D3/D6. Treat log-order ambiguity explicitly: the model is a Partial Order Workflow (POWL) rather than a total order, so both CCER and ERCC are permitted as linear extensions of the same partial order.

**Formal expression:** Sequence of RO; then partial order $\Pi$ over $\{CC, ER\}$ (incomparable); SC is incomparable to CC/ER but ordered before AC; Exp is ordered after both CC and ER; AC after all; then RPArc.

**Exactly how sequence, concurrency, and partial order are decided:**

- **CC vs. ER:** Not sequential because observed variants contain both orders (V1/V2/V3/V4) and D7 explicitly states order does not reveal concurrency. S2 (“run in parallel”) strongly favors concurrency. Therefore they are placed in a **partial order / concurrent block** (incomparable).
- **SC vs. CC/ER:** D4 says SC before AC; D5 says SC need not wait for both. If SC were forced after both, we would exclude V5 (CCSCER) and ignore D5. If SC were forced sequential to one, we would underfit. Therefore SC is placed as **optional and incomparable to CC/ER** (can overlap, can finish after either), but with a required edge SCAC.
- **Exp vs. CC/ER:** D6 is high-confidence: Exp requires both completed. Thus **Exp is sequential after CC and ER** (edges CCExp, ERExp).
- **Exp vs. SC:** D6 / S6 say Exp may occur before or after SC. Thus **SC and Exp are incomparable** to each other (both before AC).

**Self-contained PM4Py code (`model_balanced`):**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
import pm4py

# Define transitions
t_ro = Transition("Register Order")
t_cc = Transition("Credit Check")
t_er = Transition("Engineering Review")
t_sc = Transition("Supplier Confirmation")
t_exp = Transition("Expedite Review")
t_ac = Transition("Approve Configuration")
t_rp = Transition("Release Production")
t_arc = Transition("Archive Case")

# Partial order enforcing hard constraints, managing uncertainty via incomparability
spo = StrictPartialOrder()
# Start
spo.add_edge(t_ro, t_cc)
spo.add_edge(t_ro, t_er)
# Both checks before approval
spo.add_edge(t_cc, t_ac)
spo.add_edge(t_er, t_ac)
# SC optional: must be before AC, but not ordered relative to CC/ER (uncertainty)
spo.add_edge(t_sc, t_ac)
# Exp requires both checks, before AC
spo.add_edge(t_cc, t_exp)
spo.add_edge(t_er, t_exp)
spo.add_edge(t_exp, t_ac)
# Optional presence handled downstream via silent skips in converted net;
# here we include SC and Exp as required nodes but note they can be bypassed
# via XOR branches in the POWL operator wrapper (see below).
# Sequence after AC
spo.add_edge(t_ac, t_rp)
spo.add_edge(t_rp, t_arc)

# Wrap in a sequence-root POWL that allows optional branches via silent transitions
# (This is a conceptual POWL; in practice PM4Py converts partial orders to Petri nets.)
model_balanced = OperatorPOWL(
    operator="sequence",  # root sequence
    children=[
        OperatorPOWL(operator="sequence", children=[t_ro]),
        # Concurrent / unordered block for checks and optional SC
        OperatorPOWL(operator="parallel", children=[
            t_cc, t_er,
            # Optional SC branch: the silent transition allows skip
            OperatorPOWL(operator="xor", children=[t_sc, SilentTransition()]),
        ]),
        # Exp after both checks; optional via XOR
        OperatorPOWL(operator="xor", children=[t_exp, SilentTransition()]),
        t_ac,
        t_rp,
        t_arc
    ]
)

# Note: The exact POWL syntax above represents the intended structure.
# In execution, convert:
# net, im, fm = pm4py.convert_to_petri_net(model_balanced)
```

**Behavior deliberately excluded:** Exp before CC/ER; AC before CC/ER; SC after AC; multiple Exp; RP before AC; RO not at start; traces that have only one of {CC,ER}.

**Known underfitting risks:** Because SC is incomparable to CC/ER, the model may allow SC to finish before either check (arguably violating D5 “after either produced enough info”). The POWL does not encode the “at least one completed” guard precisely; it relies on domain interpretation. Also, true concurrency requires resource-level evidence, which is absent.

# 5. Permissive Candidate

**Inductive-bias statement:** Maximize language coverage consistent with high/medium domain rules; admit any linear extension of the partial order that respects hard precedence constraints; treat SC and Exp as freely interleaved optional activities; assume missing SC is either skip or data loss.

**Formal expression:** $ \rightarrow(R O,\; \wedge(CC,ER,\; \oplus(SC,\tau)),\; \oplus(Exp,\tau),\; AC,\; RP,\; Arc)$, where $\wedge$ denotes concurrency, $\oplus$ denotes XOR with silent skip $\tau$, and ordering between optional branches is flexible.

**Boundary definition:** Reasonable generalization = any trace where (a) RO is first and Arc last; (b) AC is preceded by both CC and ER (and Exp if present); (c) Exp, if present, is preceded by both CC and ER; (d) SC, if present, is before AC; (e) Exp occurs at most once; (f) no activity repeats. **Forbidden:** AC before checks; Exp before both checks; SC after AC; missing ACRP; multiple Exp; RO not first.

**Self-contained PM4Py code (`model_permissive`):**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator
import pm4py

# Optional skip is a silent process tree (label None)
silent = ProcessTree(label=None)

model_permissive = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[
        ProcessTree(label="Register Order"),
        # Concurrent checks with optional SC overlapping them
        ProcessTree(operator=Operator.PARALLEL, children=[
            ProcessTree(label="Credit Check"),
            ProcessTree(label="Engineering Review"),
            ProcessTree(operator=Operator.XOR, children=[
                ProcessTree(label="Supplier Confirmation"),
                silent
            ])
        ]),
        # Optional Exp after both checks; allowed before/after SC
        ProcessTree(operator=Operator.XOR, children=[
            ProcessTree(label="Expedite Review"),
            silent
        ]),
        ProcessTree(label="Approve Configuration"),
        ProcessTree(label="Release Production"),
        ProcessTree(label="Archive Case")
    ]
)

# model_permissive = model_permissive
```

**Behavior deliberately excluded:** Any trace violating D1, D2, D3, D6 (e.g., AC without both checks; Exp before checks; SC after AC). Because SC is inside the first PARALLEL, it technically must finish before Exp starts (sequence after PARALLEL); this is a conservative compromise within the permissive design that prevents SC from occurring after AC.

**Known underfitting risks:** Because SC is inside the PARALLEL, a trace where SC occurs long after ER but before AC is allowed, but SC truly before CC is not explicitly blocked (only blocked by domain interpretation, not by control flow). The model is more complex (nested XOR/PARALLEL) and risks overfitting if interpreted as “anything goes” — hence the explicit boundary above.

# 9. Recommendation and Data-Collection Plan

**Immediate use:** **Balanced (`model_balanced`)**. It respects all high-confidence rules (D1–D3, D6), treats SC/Exp optionality explicitly, and encodes the most plausible generalization (partial order for CC/ER, concurrency with D7 uncertainty) without exploding to the oversized language of the permissive model. It is suitable for process design and sensitivity testing.

**Sensitivity analysis:** **Conservative (`model_conservative`)**. Use it to measure the cost of overfitting: compare fitness/precision differences to see how much of the observed variance is “noise” versus “structure.” If conservative and balanced yield nearly identical fitness on the 30 traces, the additional language of balanced is likely justified; if conservative degrades precision on future logs, concurrency/optionality is needed.

**Data-collection plan to resolve ambiguities:**

1. **Lifecycle timestamps:** Collect `start` and `complete` events, not only completion (addresses D7). If CC and ER have overlapping start times but different end times, concurrency is confirmed; if starts are sequential, S1 may dominate.
2. **Resource/occupancy data:** Capture which resource performs CC and ER. If different resources work simultaneously, concurrency is strongly favored.
3. **External/stocked attribute (S3–S5):** Export the component-type flag. Then distinguish true SC skips (stock) from missing SC (integration failure) and model SC conditionally rather than via abstract XOR.
4. **Expeditereview context:** Capture approval level / urgency flag to confirm D6 prerequisites.
5. **Future maximally informative traces:**
   - A trace where **SC finishes before CC completes** (tests D5 boundary).
   - A trace where **Exp occurs with only one check complete** (tests D6 violation; should be excluded by all).
   - A trace with **identical completion timestamps for CC and ER** with resource overlap (tests concurrency vs. ingestion-order artifact).

# 10. Uncertainty Statement

**Calibrated confidence for major decisions:**

- **CC and ER are concurrent / partial order:** **Medium (60%).** D7 explicitly says unknown; S2 favors concurrency; observed bidirectional DFG supports it; but S1 contradicts it and ingestion artifacts (S7) could create false concurrency.
- **SC is optional (not mandatory):** **Medium-High (75%).** S3 says mandatory for external, but observed absence (7/30) combined with S4 (stock skip) and S5 (missing data) makes mandatory enforcement risky.
- **Exp prerequisites (D6):** **High (85%).** Stakeholder statement S6 aligns with observed traces; no contradictions in log.
- **Conservative XOR enumeration is sufficient:** **Low (40%).** It excludes plausible behavior; mainly useful as sensitivity baseline.
- **Balanced POWL captures true process:** **Medium-High (70%).** Most defensible synthesis, but exact concurrency of CC/ER remains uncertain.

**Plausible alternative interpretation that changes recommendation:**

If **S1 is true** (CC must finish before ER starts) and S2 is false (the “parallel” perception is actually resource-level overlap with sequential handoffs), then CCER is a strict sequence, not concurrency. In this alternative:
- The DFG reverse direction (ERCC: 11) is explained by logging inversions or data errors rather than true reverse execution.
- The **Balanced** model should be revised to a sequence with optional SC/Exp; **Conservative** becomes more accurate; and **Permissive** overfits by admitting concurrent interleavings that do not occur.
- Under this interpretation, recommendation shifts to **Conservative (with SC/Exp optional branches)** for immediate use, because the true language is likely closer to sequential variants than to partial orders. This is why collecting start timestamps (data plan) is critical: it directly distinguishes S1 from S2.
