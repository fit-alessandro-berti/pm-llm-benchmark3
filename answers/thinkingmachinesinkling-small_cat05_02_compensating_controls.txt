Now, **Control-Objective Decomposition**:

Five objectives/threat scenarios:
1. Self-authorization / single-point failure: One individual initiates and approves same potentially erroneous/fraudulent payment (FEP-1 core). Prevented by FEP-1 separation; AV-2 partially (checks but not intent); MG-4 if independent and timely; ED-1 with conditions.
2. Fraudulent vendor / bank-account hijacking: New vendor, changed bank account, sanctions, duplicate. Prevented by AV-2 (duplicate, sanctions, ownership, change); MG-4 (review bank details); RA-7 (detect after); ED-1 (bank change condition).
3. Collusion / override / credential sharing: Two or more actors cooperate, or one overrides controls using shared/compromised credentials. AV-2 weak (override possible); MG-4 weak if supervisor/related; RA-7 detects but late; ED-1 requires specific conditions to limit opportunity.
4. Absence of goods/services / fabricated supporting documentation: Fake invoices, no receipt, fabricated service report. AV-2 does not cover (as noted); MG-4 can detect if manager reviews receipt; RA-7 detects if audit examines documentation; ED-1 doesn't address.
5. Irrevocable settlement / unrecoverable loss: Once bank settles, recovery uncertain. Preventive: MG-4 before settlement, AV-2 before release; Detective: RA-7; Corrective: bank recall within 24h. Timing is critical.

Mapping:
- AV-2: Prevents scenarios 1 (partially), 2 (strong for covered checks), 3 (weak if override used), 4 (none), 5 (indirect by blocking bad releases).
- MG-4: Prevents 1 (independent authorization), 2 (bank review), 4 (receipt review), 5 (if before settlement). Detective if after release but before settlement (hybrid). Fails if rubber-stamp, conflict of interest, after settlement.
- RA-7: Detective for 1-4. Corrective for 5 only if within recall window (24h). Fails if after window.
- ED-1: Conditional permission that bundles 1 (single operator allowed but with extra checks), 2 (amount/vendor/bank conditions), 5 (audit timing). Fails if conditions not fully met.

**Equivalence and Sufficiency Test**:

Define a structured test with dimensions:
- Timing: Is compensation applied before irrevocable action? (Preventive vs detective vs corrective).
- Independence: Is the second actor truly independent? (Not same account, not subordinate/supervisor with conflict, not same workstation/pair).
- Coverage: Does the control cover the specific threat? (AV-2 covers bank/data, not goods; MG-4 covers evidence review; RA-7 covers retrospective; ED-1 covers emergency conditions).
- Overrideability: Can the control be overridden by the same actor? (AV-2 warnings overridden; MG-4 approval can be rubber-stamped).
- Recoverability: Can error be corrected/recalled after control point? (Bank recall window ~24h; audit after settlement is only detective).
- Evidence Quality: Is evidence documented, timestamped, and reviewable? (Manual checklist unsigned is weak; manager ratify without detail is weak).
- Collusion Resistance: Does the control assume separation of actors, and is that separation real? (Same workstation, repeated pairing, shared credentials undermine).

Classification of equivalence:
- Fully equivalent: All dimensions satisfied at sufficient strength for the case's risk; controls are preventive or at least pre-settlement for authorization; independence is real; coverage matches threat; recoverability exists if needed.
- Partially equivalent: Some dimensions met, but gaps exist (e.g., manager after release but before settlement; AV-2 pass but no goods verification; audit timely but after settlement; ED-1 mostly satisfied but one condition uncertain).
- Merely mitigating: Controls reduce likelihood or impact but do not replace separation; high residual risk; late or weak management; no recovery possible.
- Ineffective: Controls absent, overridden, conflicted, or applied after irreversibility; no evidence of actual review.

Why "same expected loss" is not only standard: Controls are also about accountability, deterrence, and compliance with legal/regulatory requirements (e.g., segregation of duties is often mandatory regardless of loss expectation). A package might have same expected loss as nominal but fail audit requirements or create untraceable accountability. Also, tail risks (fraudulent large losses) are not fully captured by average expected loss. The objective includes prevention of one person controlling both sides for non-monetary reasons (integrity, audit trail).

## 1. Control-Objective Decomposition

FEP-1 is not a single “check-box” but a separation-of-duties requirement with a risk-mitigation purpose: *one individual should not both initiate and authorize a transfer, because that collapses initiation and authorization into a single failure point*. The control objectives can be decomposed as:

| # | Threat / Objective | What “four-eyes” is meant to prevent | AV-2 role | MG-4 role | RA-7 role | ED-1 role |
|---|---|---|---|---|---|---|
| O1 | **Self-authorization / single-point control** — one actor prepares and releases without independent review | One person can create and commit an erroneous or fraudulent instruction | Weak / partial: checks data consistency but not intent; overrideable | Strong if independent and timely: introduces second human judgment; weak if rubber-stamp or conflict | Detective: can find error after release; partly corrective only if within recall window | Conditional permission that replaces separation only if all preconditions (token, amount, bank stability, AV pass, manager approval, audit) are met; does not make the objective disappear |
| O2 | **Vendor / bank-account fraud or hijacking** — changed bank details, new vendor, sanctions, duplicates | Transfer to fraudulent or wrong account | Strong for covered checks (duplicate, sanctions, ownership, 7-day change, amount vs limit); weak for unlisted risks | Strong if manager reviews bank details and invoice before settlement; weak if after settlement | Detective: can identify wrong account after payment; corrective only if bank recall succeeds | Explicitly requires no bank change in 7 days, vendor >180 days, amount <100k; fails if conditions violated |
| O3 | **Collusion / credential sharing / compromised account** — two users cooperate, or one uses another’s credential / workstation | Separation of actors is undermined even when names differ | Weak: override credentials can bypass checks; does not detect shared workstations or pairing patterns | Weak if manager is supervisor/related; strong if independent, evidence-based review | Detective: audit may find collusion (fabricated receipt, paired approvals) but often too late | Does not address collusion directly; relies on manager independence and AV-2 |

## 2. Equivalence and Sufficiency Test

A compensating package is **not sufficient merely because several controls exist**; equivalence must be tested against the control objective, not only expected monetary loss.

**Structured equivalence test (six dimensions):**

| Dimension | Fully Equivalent | Partially Equivalent | Merely Mitigating | Ineffective |
|---|---|---|---|---|
| **Timing** | Compensation is preventive or at least pre-settlement for authorization; audit/recall window is respected | Manager after release but before settlement; audit within recall window but after settlement | Audit after recall window; manager after settlement; no recall action | Control applied after irreversibility with no recovery path |
| **Independence** | Second actor is independent by role, hierarchy, and physical/logical access; no supervisor/subordinate or shared credential | Manager independent of preparer/releaser but approval is post-release; no evidence of review depth | Supervisor/related manager; shared workstation; repeated pairing with no organizational design; rubber-stamp approval | Same account/credential; direct conflict of interest (rating/compensation); no separation of actors |
| **Coverage** | Matches the specific threat: AV for bank/data; MG-4 for evidence/review; ED-1 for emergency conditions; audit for retrospective detection | AV-2 passes but goods/services unverified; manager reviews some, not all, evidence | Only automated checks; no human evidence review; audit too late to stop loss | Control does not cover the actual gap (e.g., AV-2 unavailable; no receipt check) |
| **Overrideability** | No override possible by same actor; warning requires separate authorization; manual checklist is independently verified | Warning overridden by same operator; manual checklist present but unsigned/unverified | Operator can disable/block with own credentials; supervisor can ratify without review | Override is routine; controls are bypassed |
| **Recoverability** | Bank recall possible if error found; audit within 24h; settlement not yet irrevocable | Settlement occurred but recall window not yet closed at audit time; settlement prevented by manager | Settlement irrevocable; audit finds defect but recovery uncertain/unattempted | Settlement done; audit long after recall; funds unrecoverable |
| **Evidence quality / Collusion resistance** | Timestamped, documented, reviewable; no repeated pairing; organizational design supports independence | Some evidence present; repeated pairing observed but no proof of misconduct; shared workstation noted | No documentation of review; missing organizational docs; pairing pattern identical to failed cases | Evidence absent or contradictory; credential sharing unresolved |

**Why “same expected loss” is not the only standard:**
- **Legal/regulatory compliance:** Segregation of duties is often a mandatory control (not merely economic). A package that yields the same expected loss but collapses accountability can still violate policy, audit requirements, and regulatory expectations.
- **Tail-risk asymmetry:** Expected loss averages over many cases. A single high-value fraud (e.g., AP-202, AP-208) can cause catastrophic, unrecoverable damage that the average does not capture.
- **Deterrence and traceability:** Independent dual control creates an audit trail and deters fraud. A single-user process with post-hoc manager approval may have a similar statistical loss profile for small errors but offers little deterrence against intentional fraud.
- **Conditional validity:** ED-1 is a *permission*, not a blanket waiver. If conditions are not fully documented and verified (e.g., token timing, bank-change status, manager independence), the exception is invalid regardless of outcome.

| **AV-2 (full pass)** | Before Release  Before Settlement | **Preventive** (blocks/warns before commitment) | **Detective** (logs warnings, flags overrides) | Prevents bad data from reaching release; cannot detect fabricated receipts or collusion intent |
| **AV-2 (warning with override)** | Before Release | **Preventive (attempted)** | **Failed / overridden** | Preventive intent exists, but override by operator nullifies it; becomes detective of override only |
| **AV-2 (unavailable)** | Not executed | **None** | — | Control is absent; no prevention, no detection; highest risk |
| **MG-4 before Release** | Before Release  Before Settlement | **Preventive** (independent authorization of instruction) | — | True second pair of eyes; can reject or modify before commitment |
| **MG-4 after Release, before Settlement** | After Release / Before Settlement | **Detective** (of release action) | **Preventive / Hybrid** (of settlement) | It detects that an erroneous/fraudulent instruction was released; it can still **prevent irrevocable settlement** by canceling/revoking or placing a hold. It is **not fully preventive of the release event**, but it is preventive of the final loss event (settlement) if acted upon promptly. |
| **MG-4 after Settlement** | After Settlement | **Detective** | **Corrective only if recall possible** | Cannot prevent loss; can only initiate recovery / audit; if audit is after recall window, corrective capacity is near-zero |
| **RA-7 within ~24h (before recall closed)** | After Settlement / After Release | **Detective** | **Partly Corrective** | Finds defect; can initiate bank recall if still within window. Corrective only because recall is possible; it does not undo the release authorization |
| **RA-7 >24h / after recall** | After Settlement | **Detective** | **Non-corrective** | Recoverability is uncertain; only serves deterrence, accountability, and process improvement |
| **ED-1 (as package)** | Before Release (token)  Before Settlement (manager)  Within 1 day (audit) | **Preventive (conditional)** | **Detective / Corrective** (audit/recall) | Not a substitute for separation; a tightly bounded exception. If any condition fails, the exception is invalid and the case should be treated as a standard FEP-1 violation without full compensation |

**Chosen semantics for “manager after release but before settlement”:** I classify this as **hybrid (detective of release + preventive of settlement)**. It does not retroactively make the release independently authorized, but it can stop the payment from becoming irrevocable. This is why AP-201 and AP-207 can have partial/meet objectives despite post-release manager action: the critical loss event (settlement) is still gated.

## 5. Counterfactual and Residual-Risk Analysis

**AP-201 (same user u17, 1.8k, manager before settlement)**
- **Likely loss mechanism:** u17 introduces wrong vendor / amount by error; account compromise; or self-payment.
- **Control that breaks chain:** AV-2 (vendor stable, amount low, no duplicate); MG-4 before settlement can cancel.
- **Exposed:** Without independent releaser, a determined actor could attempt a small fraudulent release; manager has only ~28 minutes (08:0608:30) to catch it before settlement at 10:00.
- **Under independent second releaser:** The second human would have needed to approve release at 08:06; if they review details, error is caught earlier, reducing reliance on manager urgency and eliminating same-user initiation.

**AP-202 (same user u23, 480k, override, conflict, late manager)**
- **Likely loss mechanism:** Fraudulent vendor (employee-relative) uses changed bank; operator limit overridden; supervisor coerces/rubber-stamps approval.
- **Control that breaks chain:** None effectively; AV-2 blocked but overridden; MG-4 conflicted and too late; audit too late.
- **Exposed:** High unrecoverable exposure; credential sharing unresolved; vendor fraud not detectable by AV-2; supervisor approval creates false assurance.
- **Under independent second releaser + independent manager:** Second releaser would likely not share override credentials; independent manager (not supervisor) would have rejected bank change and amount; settlement could be delayed until verification; recall possible.

**AP-204 (distinct u12/u13, 220k, fabricated receipt, no manager, shared workstation)**
- **Likely loss mechanism:** Colluding pair approves fabricated consulting invoice; AV-2 passes because vendor/invoice data is clean; receipt is never verified.
- **Control that breaks chain:** None at authorization; audit detects too late.
- **Exposed:** 220k for nonexistent service; organizational design missing; workstation sharing undermines “independence” in practice.
- **Under independent second releaser (true independence):** If u13 were truly independent (different workstation, no repeated pairing, organizational oversight), they could have required receipt and manager sign-off; if collusion is real, structural controls (workstation separation, rotation, mandatory manager review) are needed regardless.

**AP-206 (same user u52, 95k, emergency token after prepare)**
- **Likely loss mechanism:** Rushed payment during outage; error in vendor or amount due to urgency; token created late suggests process circumvention.
- **Control that breaks chain:** AV-2 passes; independent manager m11 approves before settlement; audit within recall window.
- **Exposed:** Emergency justification is unverified; if manager approves quickly due to outage stress, evidence review may be shallow; settlement at 15:00 with audit next morning means recall is possible but not guaranteed.
- **Under independent second releaser:** Would reduce urgency justification; second releaser can verify emergency token validity and documentation before release, reducing reliance on post-release manager approval.

**AP-208 (same user u72, 900k, AV unavailable, checklist unsigned, manager after settlement)**
- **Likely loss mechanism:** Wrong bank account due to recent bank change; fraud or error; no automated ownership verification; manual checklist unsigned; manager ratifies after irrevocable settlement.
- **Control that breaks chain:** None at critical points.
- **Exposed:** 900k unrecoverable; no reliable evidence of bank ownership at release; high tail risk; audit after 5 days is purely historical.
- **Under independent second releaser + restored AV-2:** Second releaser would refuse release without AV-2 or verified checklist; bank change would trigger hold; settlement would be delayed until ownership confirmed; manager would approve before settlement.

**Qualitative ranges (illustrative, not precise probabilities):**
- Low exposure / high control: Loss “unlikely” / “low impact”.
- Moderate exposure / partial control: Loss “possible” / “moderate impact”.
- Critical exposure / failed control: Loss “likely” / “critical impact” with “low recoverability”.

## 6. Evidence and Monitoring Recommendations

**Distinction:** An *alert* is a technical deviation (same user, late approval, missing token). *Proof of misconduct* requires corroboration (credential audit, organizational charts, bank recall records, fabricated document verification).

| Monitoring Rule | Alert Condition | Evidence Needed for Proof / Verdict | What It Tells You |
|---|---|---|---|
| **Same-user rate** | >threshold (e.g., >2% of completed payments; or any non-emergency) | Justification log, ED-1 conditions, manager independence verification | Alert = deviation from FEP-1; proof requires whether ED-1 fully satisfied |
| **Override rate** | AV-2 warning overridden; override credential used | Credential assignment log; whether override required separate authorization; manager review of override reason | Alert = control bypass; proof requires whether override was authorized or shared |
| **Late manager approval** | Manager approves after Release_Payment; critical if after settlement | Timestamp log; settlement time; whether manager blocked/canceled instruction | Alert = timing failure; proof requires whether settlement was prevented |
| **Audit-before-recall-window** | Audit >24h after Release_Payment or after settlement without recall action | Audit timestamp; bank recall attempt log; settlement timestamp | Alert = detective-only / non-corrective; proof requires whether recovery attempted |
| **Repeated resource pairs** | Same (prepare, release) pair exceeds threshold (e.g., >5 in period); shared workstation | Organizational design documents; workstation logs; rotation policy; manager review patterns | Alert = potential collusion cell; proof requires organizational design and access logs; absence of docs raises risk |
| **Shared workstations / credentials** | Distinct users, same workstation; shared override credentials | Workstation logs; identity/access management records; HR/role records | Alert = independence undermined; proof requires credential sharing evidence |
| **Bank-change proximity** | Bank change within 7 days before release | AV-2 log; vendor communication; manual verification notes | Alert = high fraud risk; proof requires whether change was verified as legitimate |
| **Control outages** | AV-2 unavailable / manual checklist unsigned | Service availability logs; checklist signatures; manual verification records | Alert = invasive failure; proof requires whether manual control was actually executed |
| **Emergency token validity** | Token created after Prepare_Payment; token missing | Token log; prepare/release timestamps; outage documentation | Alert = ED-1 precondition failure; proof requires whether emergency was genuine |

**Recommendation:** Do not treat “same user” as automatic failure; verify ED-1 conditions and manager timing. Do not treat “different user” as automatic success; check pairing patterns, workstation sharing, and manager absence (as in AP-204/AP-209).
