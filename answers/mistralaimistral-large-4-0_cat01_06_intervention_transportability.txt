Site A's after diagram is a partial order, but its measured effect was confounded by staffing, API latency, mix shift, huddles, and timestamp changes. ## 6. Candidate Site B intervention

Modified intervention: **Segmented parallel verification with statutory gate**.

- **Eligibility rules**
  - All cases: create `Identity Check` and `Originals Receipt` immediately after `Register` when originals are legally required.
  - Digital/no-originals cases (38%): create `Document Check` immediately after `Register`, in parallel with `Identity Check`.
  - Originals-required cases (62%): do not create an executable `Document Check` until `Originals Receipt` is complete. If the system can represent a blocked task, create `Document Check` in a non-executable blocked state; otherwise create it only upon `Originals Receipt` completion.
  - Legal-review cases: after `Assessment`, route to `Legal Review`; no change to the legal requirement.

- **Tasks that may be created or executed concurrently**
  - `Identity Check` and `Originals Receipt` may run concurrently for all originals-required cases.
  - `Identity Check` and `Document Check` may run concurrently only for no-originals cases.
  - `Identity Check` and `Document Check` may be owned by different specialized reviewers.

- **Statutory prerequisites that remain mandatory**
  - `Register` before all tasks.
  - `Originals Receipt` before `Document Check` when originals are legally required.
  - `Identity Check` and `Document Check` complete before `Assessment`.
  - `Legal Review` for public-sector/high-value cases after `Assessment`.
  - Final `Approve` or `Reject` after `Assessment`, and after `Legal Review` when required.
  - `Notify` after final decision.

- **Queue and WIP controls**
  - Role-specific WIP caps: Identity  6 open tasks per reviewer (24 total); Document  8 per reviewer (56 total); Assessment  10 per assessor (30 total); Legal  8 per reviewer (16 total). Initial caps may be tuned during the pilot.
  - Release `Document Check` for digital cases only when document WIP is below cap; otherwise hold in a ready queue.
  - No priority override for treated cases.
  - Daily huddles review WIP, blocked originals, and assessment/legal queues.

- **Resource responsibilities**
  - Identity reviewers: only `Identity Check`.
  - Document reviewers: only `Document Check`, including repeat after supplement.
  - Assessors: only `Assessment`, including repeat after supplement.
  - Legal reviewers: only `Legal Review` and `Request Supplement`.
  - No cross-role substitution during the pilot unless recorded as a co-intervention.

- **Handling of legal-review and supplement loops**
  - `Legal Review` occurs after `Assessment` for public-sector/high-value cases.
  - If `Legal Review` issues `Request Supplement`, create `Document Check (repeat)` and then `Assessment (repeat)`.
  - `Identity Check` is repeated only if the legal reviewer marks identity evidence as affected.
  - After repeat `Assessment`, route back to `Legal Review`.
  - Track supplement count per case.

- **Logging requirements**
  - Immutable timestamps for task created, released, started, completed, blocked, and handed off.
  - Record originals-required flag, digital/original channel, legal-review flag, complexity stratum, supplement reason, active owner, WIP counts, queue entry/exit, API latency, and back-entry flag.
  - Measure true overlap as the intersection of `[start, complete]` intervals for `Identity Check` and `Document Check`, not merely task creation order.

POWL-style partial-order relation set:

```text
Register < IdentityCheck
Register < DocumentCheckChoice
IdentityCheck < Assessment
DocumentCheckChoice < Assessment
Assessment < LegalChoice
LegalChoice < Notify
Approve < Notify
Reject < Notify

DocumentCheckChoice = XOR(
    DigitalDocument: DocumentCheck,
    OriginalsDocument: OriginalsReceipt < DocumentCheck
)

LegalChoice = XOR(
    NoLegal: DecisionChoice,
    LegalBranch: LegalLoop < DecisionChoice
)

LegalLoop = Loop(
    LegalReview,
    RequestSupplement < DocumentCheckRepeat < AssessmentRepeat < LegalReview
)

DecisionChoice = XOR(Approve, Reject)
```

This preserves the key dependency: `Assessment` waits for both `IdentityCheck` and `DocumentCheckChoice`.

The pilot separates mechanism failure from implementation failure by measuring the intended causal intermediate—true overlap—and the downstream outcomes, not just cycle time. If true overlap is high (e.g., >70% of treated no-originals cases) but waiting before Assessment does not fall, the mechanism is failing: identity and document checks are not independent or prerequisites still bind. If true overlap is low (<50%), the failure is implementation: IT lock, WIP caps, role specialization, or workarounds prevented parallel execution. If overlap is high and waiting falls but assessment/legal queues rise and p90 worsens, the mechanism works locally but the system bottleneck shifted. If overlap is high, waiting falls, but rework/appeals rise, the process is unsafe. Process-mining measures task intervals, queue lengths, WIP, back-entry, and supplement loops by arm and stratum. This allows us to distinguish "parallelization does not work here" from "we did not implement parallelization" and from "parallelization works but harms the tail."

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL
from pm4py.objects.powl.enums import Operator

# ---------- Site A before/after process trees ----------
site_a_before_str = "-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"
site_a_after_str = "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"

site_a_before_tree = pm4py.parse_process_tree(site_a_before_str)
site_a_after_tree = pm4py.parse_process_tree(site_a_after_str)

petri_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(site_a_before_tree)
petri_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(site_a_after_tree)

print("Site A before is workflow net:", pm4py.check_is_workflow_net(petri_a_before))
print("Site A before sound:", pm4py.check_soundness(petri_a_before, im_a_before, fm_a_before))
print("Site A after is workflow net:", pm4py.check_is_workflow_net(petri_a_after))
print("Site A after sound:", pm4py.check_soundness(petri_a_after, im_a_after, fm_a_after))

# ---------- Site B candidate POWL ----------
def act(label):
    return OperatorPOWL(operator=Operator.ACTIVITY, label=label)

register = act("Register")
identity = act("Identity Check")
originals = act("Originals Receipt")
document = act("Document Check")
assessment = act("Assessment")
legal = act("Legal Review")
supplement = act("Request Supplement")
document_repeat = act("Document Check (repeat)")
assessment_repeat = act("Assessment (repeat)")
approve = act("Approve")
reject = act("Reject")
notify = act("Notify")

# Document-check choice: digital no-originals vs originals-required
digital_doc_po = StrictPartialOrder(nodes=[document])
originals_doc_po = StrictPartialOrder(nodes=[originals, document])
originals_doc_po.order.add_edge(originals, document)
document_choice = OperatorPOWL(operator=Operator.XOR_CHOICE, children=[digital_doc_po, originals_doc_po])

# Decision choice
decision_choice = OperatorPOWL(operator=Operator.XOR_CHOICE, children=[approve, reject])

# Legal-review branch with supplement loop.
# Loop(children=[legal, supplement, document_repeat, assessment_repeat]) represents:
# Legal Review -> Request Supplement -> Document Check (repeat) -> Assessment (repeat) -> Legal Review
legal_loop = OperatorPOWL(operator=Operator.LOOP, children=[legal, supplement, document_repeat, assessment_repeat])
legal_branch = StrictPartialOrder(nodes=[legal_loop, decision_choice])
legal_branch.order.add_edge(legal_loop, decision_choice)

# Optional legal review: either no legal review and go to decision, or legal branch then decision
legal_choice = OperatorPOWL(operator=Operator.XOR_CHOICE, children=[legal_branch, decision_choice])

# Main strict partial order.
# Assessment waits for both Identity Check and DocumentCheckChoice.
site_b = StrictPartialOrder(nodes=[register, identity, document_choice, assessment, legal_choice, notify])
site_b.order.add_edge(register, identity)
site_b.order.add_edge(register, document_choice)
site_b.order.add_edge(identity, assessment)
site_b.order.add_edge(document_choice, assessment)
site_b.order.add_edge(assessment, legal_choice)
site_b.order.add_edge(legal_choice, notify)

# Convert POWL to accepting Petri net
petri_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b)

print("Site B is workflow net:", pm4py.check_is_workflow_net(petri_b))
print("Site B sound:", pm4py.check_soundness(petri_b, im_b, fm_b))

# Optional playout
traces_b = pm4py.play_out(petri_b, im_b, fm_b, num_traces=5)
for i, trace in enumerate(traces_b):
    print(f"Trace {i+1}:", [event["concept:name"] for event in trace])

# ---------- What the model cannot encode ----------
# - Data-dependent legal requirements: originals_required and legal_review flags select branches.
# - Resource capacity and WIP limits: 4 identity, 7 document, 3 assessment, 2 legal reviewers.
# - Case locking: legacy system normally allows only one active task owner.
# - Durations, queueing, service-time distributions, and external originals delay.
# - Timestamp back-entry and measurement error.
# - Rework probabilities, appeal rates, and case-mix shifts.
```

## 9. Recommendation

`conditional go`

Transfer the mechanism—parallelize independent verification tasks where legally and operationally possible—not Site A's blanket simultaneous task creation. Do not copy the intervention for originals-required cases: 62% of Site B cases cannot start Document Check until Originals Receipt is complete. The first subgroup should be digital/no-originals cases (38%), especially non-legal-review cases (22.8% of all cases), because they have no statutory originals prerequisite and can achieve true Identity Check and Document Check overlap. For originals-required cases, parallelize Identity Check with Originals Receipt only; keep Document Check gated on Originals Receipt. Legal-review cases (40%) should be included in a second stratum but monitored for legal queue congestion and supplement loops.

Expected benefits: reduced waiting before Assessment, possibly -3 to -6 h median for eligible digital cases, improved p90 if assessment and legal capacity are not saturated. Risks: bottleneck shift to assessment (3 assessors) or legal (2 reviewers), tail worsening, rework/appeal increases, IT lock failure, and measurement artifacts from back-entry. The pilot must require immutable timestamps, multi-open-task capability or a validated workaround, role-specific WIP caps, and stratified randomization.

Expansion triggers: true overlap >70% in treated no-originals cases, median waiting before Assessment falls by 3 h, p90 does not worsen >5%, rework  baseline +1 pp, appeals  baseline +0.5 pp, and no assessment/legal WIP breach. Modification triggers: overlap high but waiting unchanged (mechanism failure), or waiting falls but assessment/legal queues rise (bottleneck shift). Abandonment triggers: true overlap <50%, p90 worsens >10%, rework > baseline +2 pp, appeals > baseline +1 pp, or legal supplement rate > baseline +3 pp. Site A's nine-hour median reduction should not be used as the expected effect; it is confounded by staffing, API latency, mix shift, huddles, and timestamp changes.

## 10. Assumption register

1. **Assumption** — Identity Check and Document Check are logically independent for digital/no-originals cases. **Why needed** — Parallelization only reduces waiting if checks do not require each other's outputs. **How to test** — Process-mining dependency analysis; reviewer interviews; rework-reason audit. **Consequence if false** — Parallelization creates rework or invalid checks; restrict to cases with verified independence.

2. **Assumption** — Originals-required flag is known at registration and legally reliable. **Why needed** — Eligibility for immediate Document Check. **How to test** — Audit registration data against legal requirements. **Consequence if false** — Illegal parallel document checks; stop and gate all Document Check on originals.

3. **Assumption** — Site B's legacy system can be configured or worked around to allow multiple open tasks with immutable timestamps. **Why needed** — True overlap and measurement. **How to test** — IT pilot with test cases; timestamp audit. **Consequence if false** — True overlap cannot be achieved; pilot is implementation-limited.

4. **Assumption** — Identity, document, assessment, and legal capacities remain stable during the pilot. **Why needed** — Isolate parallelization effect. **How to test** — Monitor staffing, leave, utilization. **Consequence if false** — Capacity changes confound effect; adjust or extend.

5. **Assumption** — Digital/no-originals cases are at least 38% and sufficiently homogeneous to power the pilot. **Why needed** — Eligible share and power. **How to test** — Intake data. **Consequence if false** — Pilot underpowered; extend duration or broaden eligibility.

6. **Assumption** — Legal review and supplement loops are downstream and can be modeled as an optional branch with repeat Document Check and Assessment. **Why needed** — Avoid bottleneck/rework surprise. **How to test** — Process mining of legal cases; legal reviewer interviews. **Consequence if false** — Legal congestion worse; add legal capacity or restrict pilot.

7. **Assumption** — Process-mining timestamps and overlap measures are reliable after logging changes. **Why needed** — Measure mechanism and outcomes. **How to test** — Timestamp audit; compare system logs to manual sample. **Consequence if false** — Effect estimates biased; fix logging before pilot.

8. **Assumption** — Case mix and complexity remain stable during the pilot. **Why needed** — Transportability and comparability. **How to test** — Weekly mix dashboard. **Consequence if false** — Mix shift confounds; stratify or adjust.
