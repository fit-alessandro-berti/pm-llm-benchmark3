## 1. Duplicate-handling decision tree

Apply tests in this order and stop at the first sufficiently supported classification. Equality of activity, timestamp, or some objects is evidence for candidacy, never proof.

1. **Exact technical duplicate**
   - Same source system and immutable `source_event_key`, with equivalent business timestamp, activity, and payload. Ingestion ID/time may differ because of redelivery.
   - **Decision:** drop redundant copies after retaining their event IDs and ingestion metadata in the audit record. Keep one canonical event.
   - Payload equality alone is insufficient across systems because enrichment can alter payloads.

2. **Same physical event observed by multiple systems**
   - Supported by reconciliation, a physical scan identifier, invoice number, message lineage, or equivalent business identity.
   - **Decision:** merge attributes and E2O relations into one canonical event. Preserve all source IDs and conflicting values.
   - Payload differences do not defeat this classification when enrichment is documented.

3. **Summary event derived from a detailed event**
   - A source trace, message ID, or documentation shows that one event summarizes another.
   - **Default decision:** retain both, qualify the summary label, and mark `abstraction_level=summary`.
   - **Conditional decision:** merge attributes and relations only when lineage proves that the summary is redundant for the intended analyses. Do not infer missing object relations from the detailed event.

4. **Harmonization collision**
   - Integration assigned one label to semantically different source activities.
   - **Decision:** retain both and restore source-specific refined labels or qualifiers. Do not merge merely because the harmonized labels match.

5. **Concurrent same-label events involving different objects**
   - A discriminating object, such as Item or Payment, identifies separate business occurrences.
   - **Decision:** retain both unchanged and annotate them as distinct occurrences. Sharing an Order or Invoice does not override the discriminating object.

6. **Unresolved candidate**
   - Evidence is contradictory or incomplete.
   - **Decision:** quarantine for review while preserving the raw events. Exclude from high-confidence curated metrics if necessary, but never silently delete.

## 3. Timestamp-tie ordering rules

Build and store a **partial order first**. A total order is only a deterministic serialization of that partial order.

1. **Original business timestamp bucket**  
   Events at different timestamps are ordered by `original_timestamp`. Equal timestamps create a tie group, not proof of simultaneity.

2. **Domain constraints — semantic**  
   Examples: e12 before e13 for M1; e09 before e10; pick before pack; invoice issuance before its payment where the configured V1 lifecycle requires it; release before carrier acceptance.

3. **Within-source sequence — semantic if the source guarantees monotonicity**  
   Compare sequence values only within the same source. After the e03/e04 merge, scanner sequence 551 places the physical I1 scan before scanner event e05 at 552. PSP sequence gives e12e13e14. Never compare WMS 110 directly with PSP 401.

4. **Lifecycle constraints on shared objects — semantic only when validated**  
   For example, P1 cannot be accepted before warehouse release under the configured logistics lifecycle, and V1 must exist before payment under the configured order-to-cash lifecycle. Generic activity-name heuristics are prohibited.

5. **Source-specific semantics — semantic when documented**  
   e07 is a generated status observation and therefore follows e06 in provenance order. e15 follows payment messages. This does not necessarily make either an additional physical transition.

6. **Ingestion time — deterministic/technical**  
   It may break an otherwise unresolved tie for reproducibility, but it is not business evidence and must not become the primary ordering rule.

7. **Stable fallback — deterministic**  
   Use canonical event ID or a content hash. Record that the resulting edge has no semantic basis.

Run cycle detection before serialization. If rules conflict, quarantine the tie group rather than forcing an order. Retain `tie_group_id`, `order_basis`, and the partial-order edges separately.

**10:00 group after merging e04 into e03:**  
Intended order: **e03  e05  e06  e07**. Scanner provenance supports e03 before e05; both picks precede packing; detailed packing precedes its ERP status observation. If scanner-sequence propagation is rejected, e03 and e05 are unordered but both precede e06e07.

**10:15 group:**  
Intended order: **e08  e09  e10**. Release precedes carrier acceptance, and acceptance explicitly precedes handover. Without certifying the release-acceptance lifecycle rule, the admissible partial order is `{e08,e09}  e10`.

**12:00 group after merging e16 into e11:**  
Selected order: **e11  e12  e13  e14  e15**. e12e13 is explicit; e13e14 comes from PSP sequence and does not mean they are the same payment; both captures precede the ERP summary. If invoice-before-payment is not accepted as a lifecycle rule, the constraints are `e12<e13<e14<e15` and `e11<e15`, allowing several topological orders.

Adding microseconds before deciding this semantic order can encode a false story: lexical IDs or arrival order might imply that carrier acceptance physically occurred one microsecond before warehouse release. Synthetic spacing is therefore a tool-compatibility layer only.

    """Filter optional kwargs for nearby PM4Py versions."""
    sig = inspect.signature(fn)

        p.kind == inspect.Parameter.VAR_KEYWORD
        for p in sig.parameters.values()
    )
    if not accepts_var_kw:
        kwargs = {k: v for k, v in kwargs.items() if k in sig.parameters}
    result = fn(*args, **kwargs)
    return args[0] if result is None else result

def validate_ocel(ocel, name):
    cols = core_columns(ocel)
    event_ids = set(ocel.events[cols["eid"]])
    if len(event_ids) != len(ocel.events):
        raise AssertionError(f"{name}: duplicate event IDs")

    if missing_events:
        raise AssertionError(f"{name}: relations reference {missing_events}")

    if hasattr(ocel, "objects") and ocel.objects is not None:
        oid_col = pick_col(ocel.objects, "ocel:oid", "object_id", "oid")
        object_ids = set(ocel.objects[oid_col])
        missing_objects = set(rel[rcols["oid"]]) - object_ids
        if missing_objects:
            raise AssertionError(f"{name}: relations reference {missing_objects}")

    required = [
        "original_timestamp", "original_activity",
        "source", "source_event_key"
    ]
    absent = [c for c in required if c not in ocel.events.columns]
    if absent:
        raise AssertionError(f"{name}: missing provenance columns {absent}")

    return True

## 7. Sensitivity analysis

| Dataset | Events | E2O relations | Main structural interpretation |
|---|---:|---:|---|
| Raw | 17 | 44 | All observations and harmonization collisions remain |
| Conservative | 15 | 39 | Verified scan and invoice duplicates removed; summaries and distinct occurrences retained |
| Evidence-based merge | 14 | 37 | Additionally treats proven e07 as a redundant projection of e06 |
| Aggressive library merge | 10 | 28 if relations are unioned | Same-label/time groups are collapsed whenever any object is shared |

The aggressive relation count is implementation-dependent. A first-row policy may retain fewer than 28 relations and orphan objects; therefore the actual output must be measured and validated.

- **Order-flattened DFG.** Raw can show `Pick ItemPick Item` from e03/e04/e05 and `Capture PaymentCapture PaymentCapture Payment` from e13/e14/e15. Conservative removes the e03/e04 duplicate but retains legitimate I1/I2 picks and M1/M2 captures. Refinement changes `Pack PackagePack Package` into packing followed by an ERP status, and `Dispatch PackageDispatch Package` into release followed by acceptance. Aggressive compression hides these distinctions.
- **Item-flattened DFG.** I1 should show one pick followed by packing; I2 should show its separate pick followed by packing. Aggressive merging can either connect one synthetic pick to both items or lose I2 entirely.
- **Payment-flattened DFG.** M1 should retain `Authorize PaymentCapture Payment`; M2 should retain its own capture. Aggressive merging may attach both payments to one synthetic capture, falsely coupling their lifecycles, or lose M2.
- **OC-DFG and frequencies.** Raw inflates `Pick Item`, `Pack Package`, `Dispatch Package`, `Issue Invoice`, and `Capture Payment` frequencies. Conservative reduces verified duplicates while refined labels prevent false loops. Aggressive reports each group once and understates concurrent work.
- **ET–OT weights.** The weight between `Capture Payment` and Payment falls from two occurrences to one event occurrence under aggressive merging, while that event may union M1 and M2. `Pick Item`–Item similarly changes from two physical picks to one synthetic event.
- **OTG relations.** Unioning e13/e14/e15 creates one event co-relating M1 and M2, falsely suggesting a direct Payment–Payment co-occurrence. Unioning e03/e05 similarly makes I1 and I2 products of one physical pick.
- **Rework and loops.** Raw duplicates appear as repeated work. Conservative refinement exposes status observations as such. e13e14 can still look like a capture loop in an activity-only Order projection, but Payment qualifiers identify partial payments. Aggressive removal of that edge is not evidence that no second payment occurred.
- **Lifecycle and performance.** Duplicates inflate resource utilization and activity counts. Summary events create zero-duration edges unless excluded from transition-time metrics. Synthetic microseconds create artificial waiting/handover durations. Aggressive merging understates parallelism and can change package, item, invoice, and payment cycle times.

Concrete changing patterns include: `e03e04`; `e03/e05` as separate picks; `e06e07`; `e08e09e10`; `e11e16`; `e12e13`; `e13e14`; and `e13/e14e15`.

## 8. Audit trail and reversibility

Store one immutable audit row per decision, including non-merge decisions:

- `audit_id`, `canonical_eid`, and all `source_event_ids`;
- `decision_type`: drop, merge, retain, relabel, quarantine, or order;
- `merge_rule`, rule version, reviewer, evidence URI, confidence, and reason;
- original harmonized activity, native/source activity, and refined activity;
- original timestamp, sort rank, synthetic adjusted timestamp, and ordering-rule path;
- attributes retained from each source, canonical values, and all discarded or conflicting values;
- relation additions, removals, unions, and deliberately un-added inferred relations;
- before/after event and relation hashes;
- status and reversibility timestamp.

To reconstruct the raw view, select all immutable raw rows referenced by `source_event_ids`, bypass canonical mappings and refined labels, restore `original_timestamp` and `original_activity`, and replay raw E2O relations. Raw content hashes verify that reconstruction did not depend on mutable curated rows. A dropped event must therefore be logically dropped from the curated view, never physically deleted from the audit store.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments.** Require equality of discriminating roles such as Payment before merging; explicitly protect e13/e14.
2. **Turning abstraction updates into false rework.** Label e07/e15 as summaries and exclude abstraction edges from rework metrics.
3. **Ordering by ingestion time.** Use ingestion only as a final technical tiebreaker, never as the semantic order.
4. **Treating shared objects as proof.** Common O1/V1 is compatible with, but does not prove, duplication; inspect all object roles.
5. **Unioning incompatible E2O relations.** Union only verified observations of the same event; never add M1/M2 to e15 without evidence.
6. **Changing durations with synthetic microseconds.** Apply spacing only after semantic ordering, preserve the original timestamp, and flag synthetic values.
7. **Losing source-authoritative attributes.** Namespace attributes and record every conflict rather than letting a merge choose silently.
8. **Applying duplicate functions to the whole OCEL.** Run candidate reports first, review groups, and isolate justified calls.
9. **Comparing `source_seq` across systems.** Sequence 100 in WMS and 551 in Scanner have no shared scale; compare only within a source.
10. **Trusting harmonized labels.** Retain native activity names so e08 and e09 remain release and acceptance.
11. **Forcing an inconsistent partial order.** Detect cycles and quarantine conflicts instead of using a stable ID to conceal them.
12. **Assuming a total order is physical truth.** Persist the partial order, tie group, and basis for every serialized edge.
