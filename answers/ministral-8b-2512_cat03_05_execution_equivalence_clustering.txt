# **Object-Centric Execution Clustering for Order Logistics**

---

## **1. Equivalence Design Space**

We define three equivalence relations, each preserving different aspects of the executions while discarding others.

### **1. Activity-Sequence Equivalence**
**Definition:**
Two executions are equivalent if their sequences of activity labels (ignoring object IDs) are identical, including event order and multiplicities.

**Invariants Preserved:**
- Event label sequence (e.g., `Create Order  Add Item  ...`).
- Number of events of each type (e.g., two `Add Item` events).
- No structural or semantic information beyond labels.

**Information Discarded:**
- Object IDs (local or external).
- O2O qualifiers (e.g., `removed_before_dispatch`).
- External object references (`EXT-OA`, `EXT-IA`).
- Event timing (only order matters).

**Properties:**
- Reflexive, symmetric, transitive.
- Does not handle concurrency (assumes total order).

**Example:**
- `X1` and `X2` are equivalent under this relation because their event labels and order match, despite different IDs.
- `X7` differs from `X1` because it includes `Return Item` and `Inspect Return`, which are absent in `X1`.

---

### **2. Typed Structural Equivalence under Identifier Renaming**
**Definition:**
Two executions are equivalent if they have the same **typed object graph structure**, ignoring local object IDs but preserving:
- Object types and multiplicities.
- External object flags (`EXT-*`).
- Event order (but not absolute timestamps).
- E2O (Event-to-Object) incidence (which objects participate in which events).

**Invariants Preserved:**
- Number of `Order`, `Item`, `Package`, etc., objects.
- External object references (e.g., `EXT-OA` appears in `X5` but not `X1`).
- Event-to-object mappings (e.g., `Pack` always involves `Order` and `Item` objects).
- No O2O qualifiers (e.g., `removed_before_dispatch`).

**Information Discarded:**
- Local object IDs (e.g., `O1` vs. `O2`).
- O2O qualifiers (e.g., `I72 replaces I71`).
- Event timing (only order matters).

**Properties:**
- Reflexive, symmetric, transitive.
- Handles renaming but not semantic changes (e.g., `X7`’s `Return Item` is treated like a new event type).

**Example:**
- `X1` and `X2` are equivalent because they have the same structure (same object counts, same event-to-object mappings).
- `X5` differs from `X1` because it includes external objects (`EXT-OA`, `EXT-IA`).

---

### **3. Business-Semantic Equivalence**
**Definition:**
Two executions are equivalent if they exhibit the **same business behavior**, considering:
- **Object lifecycles** (e.g., item replacement, package sharing).
- **External object involvement** (e.g., cross-order logistics).
- **Payment and invoice semantics** (e.g., partial vs. full payment).
- **O2O qualifiers** (e.g., `removed_before_dispatch`).

**Invariants Preserved:**
- **Logistics topology** (how items are packed, delivered).
- **Financial topology** (how invoices are allocated, paid).
- **Lifecycle motifs** (e.g., return  repack  redispatch).
- **External dependencies** (e.g., shared packages or invoices).

**Information Discarded:**
- Local object IDs (treated as irrelevant).
- Absolute event timing (only relative order matters).

**Properties:**
- Reflexive, symmetric, transitive (if defined carefully).
- Requires **qualitative analysis** of event sequences.

**Example:**
- `X1` and `X2` are equivalent because they represent the same baseline process.
- `X3` differs from `X1` because it involves **split packages**.
- `X7` differs from `X1` because it includes **item replacement**.
- `X5` differs from `X1` because it involves **cross-order logistics**.

---

### **4. (Optional) Behavioral Equivalence (Partial Order)**
**Definition:**
Two executions are equivalent if their **causal dependencies** (partial order) are isomorphic, ignoring:
- Local IDs.
- Absolute timing.
- Some O2O qualifiers (if not critical).

**Use Case:**
Helpful for **process mining** where concurrency matters.

**Example:**
- `X3` and `X4` differ in dispatch order (`Pack  Dispatch` vs. `Pack  Dispatch  Pack  Dispatch`), but if we treat `Pack` and `Dispatch` as independent, they might be closer.

## **2. Canonical Signatures**
We define a **canonical signature** for **business-semantic equivalence**, which captures:
- **Object type multiplicities** (e.g., `1 Order`, `2 Items`).
- **External object flags** (e.g., `EXT-OA` present).
- **Event sequences** (order-preserving, but ignoring IDs).
- **O2O qualifiers** (e.g., `removed_before_dispatch`).
- **Lifecycle motifs** (e.g., `Return  Repack`).

### **Python-like Pseudocode**
```python
def get_canonical_signature(execution):
    # Extract object counts
    obj_counts = {
        'Order': 1,
        'Item': len([e for e in execution if 'Add Item' in e.label]),
        'Package': len([e for e in execution if 'Pack' in e.label]),
        'Delivery': len([e for e in execution if 'Dispatch' in e.label]),
        'Invoice': len([e for e in execution if 'Issue Invoice' in e.label]),
        'Payment': len([e for e in execution if 'Record Payment' in e.label]),
    }

    # Check for external objects
    has_external = any('EXT-' in e.label for e in execution)

    # Extract event sequence (ignoring IDs)
    event_sequence = []
    for event in execution:
        # Extract activity label (e.g., "Add Item{Order:O1; Item:I11}"  "Add Item")
        label = event.label.split('{')[0]
        event_sequence.append(label)

    # Check for O2O qualifiers (e.g., "removed_before_dispatch")
    qualifiers = set()
    for event in execution:
        if 'removed_before_dispatch' in event.label:
            qualifiers.add('item_replacement')

    # Check for lifecycle motifs (e.g., Return  Repack)
    has_return = any('Return Item' in e.label for e in execution)
    has_repack = any('Pack' in e.label and 'Return' in e.label for e in execution)

    return {
        'obj_counts': obj_counts,
        'has_external': has_external,
        'event_sequence': event_sequence,
        'qualifiers': qualifiers,
        'has_return': has_return,
        'has_repack': has_repack,
    }
```

## **4. Cluster Interpretations**
### **1. Baseline Single-Package (X1, X2)**
- **Signature:** `obj_counts={Order:1, Item:2, Package:1, Delivery:1, Invoice:1, Payment:1}`, no externals, no qualifiers.
- **Behavior:** Standard order fulfillment—items added, packed into a single package, delivered, invoiced, and paid.
- **Risks/Opportunities:**
  - **Risk:** No redundancy; if the package is lost, the entire order fails.
  - **Opportunity:** Simplest process; easy to automate.
- **Flattening Issue:** Flattening would lose the **object-centric structure** (e.g., which items are in which package).
- **Stability:** Stable under minor ID changes or reordering of `Add Item`.

### **2. Split Packages, Single Delivery (X3)**
- **Signature:** `obj_counts={Package:2, Delivery:1}`, no externals, no qualifiers.
- **Behavior:** Items split into separate packages but consolidated into a single delivery.
- **Risks/Opportunities:**
  - **Risk:** Higher logistics complexity (tracking two packages).
  - **Opportunity:** Faster delivery for some items if split is strategic.
- **Flattening Issue:** Flattening would merge packages, losing tracking granularity.
- **Stability:** Stable unless delivery logic changes.

### **3. Split Packages, Split Deliveries, Partial Payment (X4)**
- **Signature:** `obj_counts={Package:2, Delivery:2, Invoice:1, Payment:2}`, partial payment qualifiers.
- **Behavior:** Items split into separate packages and deliveries; partial payment (e.g., first payment covers part of the invoice).
- **Risks/Opportunities:**
  - **Risk:** Payment reconciliation complexity.
  - **Opportunity:** Flexible payment terms for large orders.
- **Flattening Issue:** Flattening would hide the **partial payment structure**.
- **Stability:** Stable unless payment logic changes.

### **4. Cross-Order Package Sharing (X5)**
- **Signature:** `has_external=True`, `obj_counts={Package:1, EXT-OA:1}`.
- **Behavior:** A package includes items from another order (e.g., bulk shipping).
- **Risks/Opportunities:**
  - **Risk:** Dependency on another order’s logistics.
  - **Opportunity:** Cost savings via shared shipping.
- **Flattening Issue:** Flattening would lose the **cross-order dependency**.
- **Stability:** Stable unless external order changes.

### **5. Cross-Order Invoice Sharing (X6)**
- **Signature:** `has_external=True`, `Invoice` bills two orders.
- **Behavior:** A single invoice covers multiple orders (e.g., bulk billing).
- **Risks/Opportunities:**
  - **Risk:** Payment allocation ambiguity.
  - **Opportunity:** Simplified billing for related orders.
- **Flattening Issue:** Flattening would merge invoices, losing allocation details.
- **Stability:** Stable unless billing rules change.

### **6. Item Replacement (X7)**
- **Signature:** `qualifiers={'item_replacement'}`, `obj_counts={Item:2}`.
- **Behavior:** One item is replaced before dispatch (e.g., last-minute substitution).
- **Risks/Opportunities:**
  - **Risk:** Inventory mismatches if not tracked.
  - **Opportunity:** Flexibility in order fulfillment.
- **Flattening Issue:** Flattening would hide the **replacement event**.
- **Stability:** Unstable if replacement logic varies.

### **7. Return and Repack (X8)**
- **Signature:** `has_return=True`, `has_repack=True`.
- **Behavior:** Item returned, inspected, repacked, and redispatched.
- **Risks/Opportunities:**
  - **Risk:** Delays and additional costs.
  - **Opportunity:** Corrects errors or handles returns gracefully.
- **Flattening Issue:** Flattening would lose the **return-repack-redispatch cycle**.
- **Stability:** Stable if return policies are consistent.

## **5. Borderline Cases Analysis**
### **X1 vs. X2**
- **Activity-sequence:** Equivalent (same labels, same order).
- **Typed-structural:** Equivalent (same object counts, same event-to-object mappings).
- **Business-semantic:** Equivalent (same baseline process).
- **Disagreement:** If we treated `Add Item` order as meaningful (e.g., "first item is critical"), they might differ. But since IDs are irrelevant, they are the same.

### **X1 vs. X5**
- **Activity-sequence:** Equivalent (same labels, same order).
- **Typed-structural:** Different (`X5` has external objects).
- **Business-semantic:** Different (`X5` involves cross-order logistics).
- **Disagreement:** If we ignore externals, they might be grouped together, but business logic treats them differently.

### **X1 vs. X6**
- **Activity-sequence:** Equivalent (same labels, same order).
- **Typed-structural:** Different (`X6` has external invoice billing).
- **Business-semantic:** Different (`X6` involves shared invoicing).
- **Disagreement:** If we ignore financial externals, they might be grouped, but compliance requires distinguishing shared billing.

### **X1 vs. X7**
- **Activity-sequence:** Different (`X7` has `Return Item`).
- **Typed-structural:** Different (`X7` has O2O qualifiers).
- **Business-semantic:** Different (`X7` involves item replacement).
- **Disagreement:** If we ignore qualifiers, they might be grouped, but business logic requires tracking replacements.

### **X3 vs. X4**
- **Activity-sequence:** Different (`X4` has split deliveries and partial payment).
- **Typed-structural:** Different (`X4` has more deliveries and payments).
- **Business-semantic:** Different (`X4` involves partial payment).
- **Disagreement:** If we ignore payment details, they might be grouped as "split packages," but financial semantics differ.

### **X4 vs. X8**
- **Activity-sequence:** Different (`X8` has return and repack).
- **Typed-structural:** Different (`X8` has return-related events).
- **Business-semantic:** Different (`X8` involves return workflow).
- **Disagreement:** If we ignore returns, they might be grouped as "split packages," but return handling is critical.

## **6. Relation to `pm4py.cluster_equivalent_ocel`**
### **What PM4Py Preserves**
- **Exact object-centric event logs** (E2O incidence).
- **Event labels and object IDs** (no aggregation).
- **No semantic interpretation** (e.g., `EXT-OA` is just another ID).

### **Why Raw IDs Make Clusters Too Fine**
- **Problem:** `O1` vs. `O2` are treated as different even if structurally identical.
- **Solution:** Canonicalize by **ignoring local IDs** and focusing on **types, multiplicities, and externals**.

### **Post-Processing Steps**
```python
def canonicalize_ocel(ocel):
    # Group events by label (ignoring IDs)
    event_groups = defaultdict(list)
    for event in ocel:
        label = event.label.split('{')[0]  # Extract "Add Item" from "Add Item{Order:O1; Item:I11}"
        event_groups[label].append(event)

    # Extract object counts per type
    obj_counts = {}
    for event in ocel:
        for obj_type, obj_ids in event.get('objects', {}).items():
            if obj_type not in obj_counts:
                obj_counts[obj_type] = 0
            obj_counts[obj_type] += len(obj_ids)

    # Check for externals
    has_external = any('EXT-' in e.label for e in ocel)

    # Check for qualifiers (e.g., "removed_before_dispatch")
    qualifiers = set()
    for event in ocel:
        if 'removed_before_dispatch' in event.label:
            qualifiers.add('item_replacement')

    return {
        'obj_counts': obj_counts,
        'has_external': has_external,
        'qualifiers': qualifiers,
        'event_sequence': list(event_groups.keys()),  # Order matters
    }

# Example usage
from pm4py.objects.conversion.log import converter as log_converter
from pm4py.objects.ocel.objects import OCEL

ocel = ...  # Load OCEL execution
canonical = canonicalize_ocel(ocel)
clusters = pm4py.cluster_equivalent_ocel([ocel1, ocel2, ...], canonicalize=canonical)
```

### **When Exact Equivalence is Preferable**
- **Compliance monitoring:** Need to detect **exact deviations** (e.g., missing events).
- **Root-cause analysis:** Requires **precise event matching**.

### **When Business Clustering is Better**
- **Operational segmentation:** Group by **process variants** (e.g., "split packages" vs. "single package").
- **Descriptive reporting:** Highlight **key business behaviors** (e.g., returns, shared invoicing).

## **7. Robustness Analysis**
| Perturbation                          | Effect on Cluster Assignments |
|---------------------------------------|-------------------------------|
| **Ignore O2O qualifiers**             | `X7` merges with `X1`; `X8` may merge with `X4`. |
| **Ignore external objects**           | `X5` and `X6` merge with `X1`. |
| **Collapse repeated events**          | `X4`’s two payments become one; may merge with `X1`. |
| **Treat Pack/Dispatch as partial order** | `X3` and `X4` may merge if order is ignored. |
| **Treat payment as amount attribute** | `X4` and `X1` may merge if payment structure is ignored. |

## **8. Limitations and Recommendation**
### **Recommended Equivalence Levels**
| Use Case                     | Recommended Equivalence |
|------------------------------|-------------------------|
| **Compliance Monitoring**     | **Exact structural equivalence** (detect missing events). |
| **Operational Segmentation** | **Business-semantic equivalence** (group by process variants). |
| **Root-Cause Analysis**       | **Typed structural + O2O qualifiers** (identify deviations). |
| **Descriptive Reporting**     | **Business-semantic equivalence** (highlight key behaviors). |

### **Why No Single Equivalence is Best**
- **Compliance** needs **fine-grained matching** (exact IDs, labels).
- **Operations** need **coarse grouping** (business behaviors).
- **Analysis** needs **middle ground** (structural + semantic).

### **Final Suggestion**
Use **business-semantic equivalence** for most purposes, but **fall back to exact equivalence** when compliance or root-cause analysis requires precision.
