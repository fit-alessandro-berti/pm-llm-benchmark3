# 1. Assumptions and Interpretation

1. **Activity labels and completion semantics.** Every activity is an atomic, complete-time event (Requirement 11). "X is complete" and "X occurred" are therefore the same observable event. All ordering constraints below are constraints on the *single* completion event of each activity.

2. **Low-risk / high-risk choice.** The risk level is data not in the control flow, so I model it as an **exclusive choice (XOR)** between two review sub-behaviors: a single `Supervisor Review` branch (low risk) versus a `PARALLEL(Quality Review, Regulatory Review)` branch (high risk). The XOR *is* the abstraction of the data condition: exactly one branch of the approval route occurs per case.

3. **Optional supplier consultation.** `Consult Supplier` is optional and occurs at most once (Requirement 6). I model it as `XOR(Consult Supplier, tau)` — a skippable transition. The "at most once" property is guaranteed because it appears once in the model and is *not* inside a loop. Whether it is selected is data-driven, so the XOR/silent-skip is again the abstraction of an unmodeled data condition.

4. **Abstracting the passing inspection.** Inspection outcomes are not event labels (Requirement 11). A trial cycle is `Execute Trial` then `Inspect Trial`. Failure is abstracted as "loop back and do `Adjust Parameters` then another cycle"; success is abstracted as "exit the loop." I use a `LOOP(body, redo)` where `body = SEQUENCE(Execute Trial, Inspect Trial)` and `redo = Adjust Parameters`. In PM4Py loop semantics, the body executes at least once; after the body, either the loop exits (this is the *passing* inspection) or the redo child executes and the body repeats. Because `Adjust Parameters` is only ever the *redo* child, it can only appear *between* two body executions, never after the final (passing) body execution. This structurally enforces Requirement 8 ("Adjust Parameters must never occur after the passing inspection"): the last event of the loop is always `Inspect Trial`.

5. **Duplicate visible labels.** For the **process tree**, I *permit* one form of duplication only if forced, but my chosen tree avoids duplicating visible activities; the approximation I accept is over-/under-approximation of concurrency, not label duplication. For the **POWL**, no duplicate visible labels are used. I explicitly flag where duplication would otherwise be the alternative (see §3 paragraph and §6 duplicate-label row). Avoiding duplicate labels keeps conformance-checking and frequency statistics interpretable (a duplicated label inflates activity counts and confuses alignment attribution).

6. **Approximation policy for the process tree.** The dependency graph is **non-block-structured** (Requirement 41): `Plan Verification` depends only on `Contain Material`, while `Design Corrective Action` and the approval route depend only on `Analyze Root Cause`; the trial synchronizes `Design Corrective Action` + `Plan Verification` but *not* the approval route, which may overlap the trial and re-synchronizes only at `Release Material`. A process tree can only express series/parallel (block) structures, so these crossing dependencies cannot be captured exactly. I adopt a **permissive over-approximation** for the process tree: I place the two initial streams, the approval route, and the trial in a single `PARALLEL` block so that all legal interleavings are admitted, and I use `SEQUENCE` only where a hard global barrier exists (start `Register Deviation`; end `Release Material` → `Archive Case`). This *admits some traces that violate the fine-grained precedences* (e.g., `Plan Verification` before `Contain Material`, or `Execute Trial` before `Design Corrective Action`). I choose over- rather than under-approximation because under-approximation (serializing the streams) would forbid the genuinely intended overlap, which is the central point of the process; the tree's loss is documented rather than hidden. The POWL model restores the exact precedences.

7. **"May overlap" interpretation.** I interpret "may overlap" as **absence of an order constraint (interleaving concurrency), not mandatory true parallelism**. Two unordered activities may occur in either order or genuinely simultaneously; the model does not *require* overlap, it *permits* it. This matches both PM4Py `PARALLEL` (tree) and `StrictPartialOrder` with no edge between the nodes (POWL): the semantics is "no ordering imposed," which under interleaving equals all shuffles.

8. **Release synchronization.** `Release Material` requires a passing inspection, the completed approval route, and completed supplier consultation if selected (Requirement 9). In the POWL this is expressed by partial-order edges from the loop node, the approval-route node, and the supplier-consultation node into `Release Material`. In the tree it is approximated by putting all those obligations in a `PARALLEL` block that is sequenced *before* `Release Material`, which enforces "all complete before release" but loses the finer per-activity independence.

9. **Scope of enforcement I do not attempt.** I do not attempt to forbid, in the tree, orderings such as "Plan Verification before Contain Material." Those are admitted by the over-approximating tree and are explicitly listed as representational loss. The POWL forbids them.

# 3. PM4Py Process-Tree Model

## 3.1 Compact process-tree expression

```
->(
   'Register Deviation',
   +(                                   # over-approximating parallel of all obligations
      'Contain Material',
      'Plan Verification',
      'Analyze Root Cause',
      'Design Corrective Action',
      X( 'Supervisor Review',
         +( 'Quality Review', 'Regulatory Review' ) ),
      X( 'Consult Supplier', tau ),
      *( ->( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' )
   ),
   'Release Material',
   'Archive Case'
)
```

Legend: `->` SEQUENCE, `+` PARALLEL, `X` XOR, `*` LOOP (first child = body/do, second = redo), `tau` silent.

**Mapping to the narrative.** The outer `->` fixes the global start (`Register Deviation`) and the global tail (`Release Material` → `Archive Case`), enforcing Req 1, Req 9's "all before release," and Req 10. The inner `+` block holds every activity whose precise inter-dependency is a crossing (non-block) constraint. Inside it: the risk route is `X(Supervisor Review, +(Quality Review, Regulatory Review))` (Req 5); the supplier consult is `X(Consult Supplier, tau)` (Req 6, at most once because it is outside any loop); the trial is the loop `*(->(Execute Trial, Inspect Trial), Adjust Parameters)` whose redo child is `Adjust Parameters`, so a failed inspection triggers adjust-then-repeat and the loop always exits on a body completion, i.e. a passing `Inspect Trial` (Req 8; `Adjust Parameters` can never be last). Because the four streams (containment/plan, analysis/design, approvals, trial) sit in one `+`, the tree admits *all* their interleavings — that is the intended overlap — but it does **not** encode the intra-stream precedences (Contain→Plan, Analyze→Design, Design+Plan→Trial). Those are over-approximated away.

## 3.2 Self-contained Python (object constructors, explicit parent/child)

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    return ProcessTree(label=label)


def silent():
    return ProcessTree()  # label=None => tau


def node(operator, children):
    n = ProcessTree(operator=operator)
    for c in children:
        c.parent = n
        n.children.append(c)
    return n


# risk route: XOR( Supervisor Review , PARALLEL(Quality, Regulatory) )
high_risk = node(Operator.PARALLEL,
                 [leaf("Quality Review"), leaf("Regulatory Review")])
risk_route = node(Operator.XOR, [leaf("Supervisor Review"), high_risk])

# optional supplier consultation: XOR( Consult Supplier , tau )
supplier = node(Operator.XOR, [leaf("Consult Supplier"), silent()])

# trial loop: LOOP( SEQ(Execute Trial, Inspect Trial) , Adjust Parameters )
trial_body = node(Operator.SEQUENCE,
                  [leaf("Execute Trial"), leaf("Inspect Trial")])
trial_loop = node(Operator.LOOP, [trial_body, leaf("Adjust Parameters")])

# over-approximating parallel block of all obligations
obligations = node(Operator.PARALLEL, [
    leaf("Contain Material"),
    leaf("Plan Verification"),
    leaf("Analyze Root Cause"),
    leaf("Design Corrective Action"),
    risk_route,
    supplier,
    trial_loop,
])

# outer sequence
tree = node(Operator.SEQUENCE, [
    leaf("Register Deviation"),
    obligations,
    leaf("Release Material"),
    leaf("Archive Case"),
])
```

Every child's `.parent` is set explicitly and appended to `parent.children`, per the API reminder. The helpers are defined in-file (no undefined helpers).

## 3.3 Requirements the tree cannot represent exactly

The tree **cannot** represent the following exactly, and represents them only through the permissive over-approximation of §1.6:

- **D5 Contain Material → Plan Verification**: both sit as independent leaves in the same `+`, so the tree admits `Plan Verification` occurring *before* `Contain Material`.
- **D6 Analyze Root Cause → Design Corrective Action**, and **D7 Analyze → Approval Route / D10 Analyze → Consult Supplier**: the tree does not force analysis before design, approvals, or supplier consult; e.g. `Supervisor Review` may appear before `Analyze Root Cause`.
- **D13/D14 Design + Plan → Execute Trial (synchronization)**: the trial loop is a sibling leaf-subtree in the `+`, so the tree admits `Execute Trial` before either `Design Corrective Action` or `Plan Verification`.
- **D18/D19 selective release synchronization**: the tree does enforce that *all* obligations complete before `Release Material` (because the whole `+` precedes it), which is actually *stronger/correct* for release but is achieved by lumping, and it cannot express that approvals may overlap the trial *while still preceding release only* — the lumping happens to be sound for release but loses the independence structure elsewhere.

What the tree **does** represent exactly: global start/end (D1, D20, D21), the risk XOR and high-risk concurrency (D8, D9), supplier optionality and at-most-once (D11), the repeat-until trial with `Adjust Parameters` never last (D15–D17), and "all obligations before release" (a superset-correct rendering of D18/D19). The net effect is a **language superset**: every intended trace is accepted, plus extra ones that violate D5, D6, D7, D13, D14.

# 4. PM4Py POWL Model

## 4.1 Compact POWL description

```
StrictPartialOrder over nodes:
  RD  = Register Deviation
  CM  = Contain Material
  PV  = Plan Verification
  ARC = Analyze Root Cause
  DCA = Design Corrective Action
  APP = OperatorPOWL(XOR)[ Supervisor Review ,
                          StrictPartialOrder{ Quality Review , Regulatory Review }  # no edge => concurrent
                        ]
  SUP = OperatorPOWL(XOR)[ Consult Supplier , SilentTransition ]
  TRL = OperatorPOWL(LOOP)[ StrictPartialOrder{ ET -> IT } , Adjust Parameters ]
  RM  = Release Material
  AC  = Archive Case

order edges (precedences):
  RD -> CM,  RD -> ARC
  CM -> PV
  ARC -> DCA,  ARC -> APP,  ARC -> SUP
  DCA -> TRL,  PV -> TRL           # trial synchronizes design + plan
  TRL -> RM,  APP -> RM,  SUP -> RM   # release synchronizes trial + approvals + supplier
  RM -> AC
```

Every pair of nodes **not** connected by a (transitive) edge is concurrent. In particular: `CM`/`ARC` (D4), `PV` vs `DCA`/`APP`/`SUP` (planning stream independent of analysis stream), `APP` vs `TRL` (approvals overlap the trial, D19/Req 7), `SUP` vs `DCA`/`APP`/`TRL` (supplier overlaps design, approvals, and trial, Req 6). Inside `APP`'s high-risk branch, `Quality Review` and `Regulatory Review` have no edge, so they are concurrent in either order (D9).

## 4.2 Self-contained Python

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# --- leaf transitions ---
RD  = Transition(label="Register Deviation")
CM  = Transition(label="Contain Material")
PV  = Transition(label="Plan Verification")
ARC = Transition(label="Analyze Root Cause")
DCA = Transition(label="Design Corrective Action")
RM  = Transition(label="Release Material")
AC  = Transition(label="Archive Case")

# --- approval route: XOR( Supervisor , PO{Quality || Regulatory} ) ---
sup_rev = Transition(label="Supervisor Review")
qual = Transition(label="Quality Review")
reg  = Transition(label="Regulatory Review")
high_risk = StrictPartialOrder(nodes=[qual, reg])   # no edge => concurrent
APP = OperatorPOWL(operator=Operator.XOR, children=[sup_rev, high_risk])

# --- optional supplier consult: XOR( Consult Supplier , tau ) ---
consult = Transition(label="Consult Supplier")
skip = SilentTransition()
SUP = OperatorPOWL(operator=Operator.XOR, children=[consult, skip])

# --- trial loop: LOOP( PO{ExecuteTrial -> InspectTrial} , AdjustParameters ) ---
et = Transition(label="Execute Trial")
it = Transition(label="Inspect Trial")
cycle = StrictPartialOrder(nodes=[et, it])
cycle.order.add_edge(et, it)
adj = Transition(label="Adjust Parameters")
TRL = OperatorPOWL(operator=Operator.LOOP, children=[cycle, adj])

# --- root strict partial order ---
powl = StrictPartialOrder(nodes=[RD, CM, PV, ARC, DCA, APP, SUP, TRL, RM, AC])

# start fan-out
powl.order.add_edge(RD, CM)
powl.order.add_edge(RD, ARC)
# containment stream
powl.order.add_edge(CM, PV)
# analysis stream fan-out
powl.order.add_edge(ARC, DCA)
powl.order.add_edge(ARC, APP)
powl.order.add_edge(ARC, SUP)
# trial synchronizes design + plan
powl.order.add_edge(DCA, TRL)
powl.order.add_edge(PV, TRL)
# release synchronizes trial + approvals + supplier
powl.order.add_edge(TRL, RM)
powl.order.add_edge(APP, RM)
powl.order.add_edge(SUP, RM)
# archive
powl.order.add_edge(RM, AC)
```

## 4.3 Why intentionally unconnected nodes may remain concurrent

In a `StrictPartialOrder`, the language is every linear extension of the order relation; two nodes with no path between them impose no mutual ordering and thus interleave freely (true "may overlap," §1.7). The intentional non-edges are:

- **CM ↔ ARC**: the two initial streams are independent (D4); neither should constrain the other.
- **PV ↔ {ARC, DCA, APP, SUP}**: planning depends *only* on containment (D5), so it is deliberately unordered w.r.t. the analysis stream and its descendants except where a later join (TRL, RM) reunites them.
- **APP ↔ TRL**: approvals may overlap the trial (Req 7/D19); they re-synchronize only at `RM`.
- **SUP ↔ {DCA, APP, TRL}**: supplier consultation may overlap corrective design, approvals, and trial (Req 6); its only downstream constraint is `SUP → RM` (D12).
- **DCA ↔ APP**: design and approvals both follow analysis but have no mutual dependency.
- **Quality ↔ Regulatory** (inside APP): concurrent high-risk reviews in either order (D9).

Every such non-edge is *intended*: adding an edge would over-constrain and forbid legitimate overlap. The edges that *are* present are exactly the precedences D1–D3, D5, D6, D7, D10, D13, D14, D18, D19, D20; the loop and XOR operators carry D8, D9, D11, D15–D17.

# 7. Preferred Representation and Validation Plan

## Canonical representation

I choose the **POWL model** as canonical. Justification: the process is explicitly non-block-structured (Req 41), and the POWL `StrictPartialOrder` expresses each crossing precedence (D5, D6, D13, D14, D18, D19) *directly* with an edge, while the process tree can only approximate them and, as shown by T6/T7, admits illegal traces. The POWL preserves the exact intended language; the tree is retained only as a required, documented over-approximation and as a bridge to Petri-net tooling.

## Validation plan

1. **Conversion to accepting Petri nets.** Convert both models: `net, im, fm = pm4py.convert_to_petri_net(tree)` and `pnet, pim, pfm = pm4py.convert_to_petri_net(powl)`. POWL→Petri-net conversion materializes the partial order (typically via silent routing transitions); inspect the number of silent transitions and places introduced, since these are where hidden behavior can creep in.

2. **Soundness checking.** `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` for each converted net. Expect soundness (option to complete, no dead transitions, proper completion). If the POWL conversion reports unsoundness, that flags a modeling/tool artifact to investigate rather than a proof of correctness.

3. **Bounded / sampled playout.** `log = pm4py.play_out(net, ...)` with a bound on trace count/length (e.g. `parameters` limiting loop unrollings) to sample the languages of both models. Because the trial loop is unbounded, cap iterations (e.g. ≤3) so playout terminates; record the sampled trace set for each model.

4. **Explicit positive/negative trace tests.** Encode T1–T5 as an event log and run alignment/conformance (`pm4py.conformance_diagnostics_alignments`) against each model — expect fitness 1.0 on the POWL for all five, and on the tree for all five. Encode T6, T7, T8 and expect the **POWL to reject** T6, T7, T8 (fitness < 1) and the **tree to reject only T8** (accepting T6, T7). This test operationalizes the over-approximation claim: a passing result *confirms* the documented loss rather than disproving it.

5. **Silent-behavior / duplicate-label check.** (a) Silent: after POWL→Petri-net conversion, enumerate `tau` transitions and confirm via playout that no `tau`-only path produces an empty or premature-completion trace (guards the supplier-skip `SilentTransition` and any routing taus). Specifically test the *skip* path: a trace with no `Consult Supplier` must still be accepted, and a trace with two `Consult Supplier` events must be **rejected** (verifies "at most once"). (b) Duplicate labels: assert that each visible activity label appears in exactly one transition of each net (`len([t for t in net.transitions if t.label==L]) == 1`), confirming no accidental duplication was introduced by conversion, which would corrupt frequency and alignment statistics.

6. **Loop back-edge check.** Generate traces with 0, 1, 2 `Adjust Parameters` events and confirm: (i) `AP` never appears as the last trial event, (ii) every trace ends the trial segment on `Inspect Trial`, verifying D17.

## Limitations of the validation plan

- **Playout is sampling, not proof.** Bounded playout with capped loop unrollings cannot demonstrate that *no* forbidden trace exists — it can only find counterexamples or fail to. Soundness and successful conversion are *evidence to inspect*, not fidelity proofs (per the quality criteria).
- **Conversion artifacts.** POWL→Petri-net and tree→Petri-net introduce silent transitions; conformance on the net measures the *net's* language, which may differ subtly from the source model's intended partial-order semantics (e.g. concurrency vs. interleaving diamonds). Discrepancies must be attributed carefully.
- **Data conditions are unmodeled.** Because risk level, supplier selection, and inspection outcome are abstracted to XOR/loop choices, no test can validate that the *correct* branch was chosen for a given case — only that the branch structure is admissible.
- **State-space size.** Full reachability/soundness with many concurrent unordered activities can be expensive; the plan relies on structural soundness checks plus sampling rather than exhaustive model checking.

# 8. Final Self-Critique

1. **(Semantics) The process tree's over-approximation is broad, not surgical.** By lumping all obligations into a single `+`, the tree drops *every* intra-stream precedence at once (PV/CM, DCA/ARC, trial synchronization, CS placement), not just the one crossing dependency that is truly inexpressible. A more careful tree could have preserved, e.g., `->(Contain Material, Plan Verification)` and `->(Analyze Root Cause, Design Corrective Action)` as blocks and only over-approximated the *trial-vs-approval* join, tightening the language considerably. My chosen tree therefore admits more spurious traces (T6, T7) than strictly necessary; I traded tightness for a uniformly simple, clearly-documented approximation.

2. **(Semantics) POWL loop exit vs. the "passing inspection" abstraction is asserted, not exhaustively demonstrated.** I rely on PM4Py `LOOP` semantics (body ≥1, redo on back-edge) to guarantee `Adjust Parameters` is never last and the final body ends on `Inspect Trial`. If the concrete POWL→Petri-net conversion implements the loop with an extra silent exit that could interleave `Adjust Parameters` differently, my claim D17 would need re-checking; I flagged this in the validation plan but did not prove it here.

3. **(Construction/API) Constructor keyword and semantics assumptions may not match the installed PM4Py version exactly.** I assumed `OperatorPOWL(operator=..., children=[...])`, `StrictPartialOrder(nodes=[...])`, and `Transition(label=...)`/`SilentTransition()` signatures, and that `OperatorPOWL` accepts `Operator.XOR`/`Operator.LOOP`. Minor version differences (argument names, whether nodes must be added before edges, or whether `StrictPartialOrder` auto-adds transitive edges) could require small adjustments; the code is written to the documented reminders but has not been executed in this environment.
