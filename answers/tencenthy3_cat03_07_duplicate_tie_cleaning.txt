## 3. Timestamp-tie ordering rules

We define a deterministic total order over events that share `timestamp`. Priority:

1. **Domain constraints (semantic).** Explicit known order: `Authorize Payment` before `Capture Payment` for the same payment (e12 < e13); warehouse release before carrier acceptance before handover (e08 < e09 < e10); invoice issuance before payment events.
2. **Lifecycle constraints on shared objects (semantic).** A `Pick Item` for I1/I2 must precede `Pack Package` that contains those items (e03/e05 before e06). `Issue Invoice` on V1 precedes payment events on V1.
3. **Source-specific semantics (semantic).** When the harmonized label hides distinct actions, use `original_activity` and source knowledge: e08 is release, e09 is accept, e10 is handover.
4. **Within-source sequence (partially semantic, mainly deterministic).** `source_seq` orders events from the same system (e.g., scanner 551 before 552). Useful only when no cross-source semantic rule exists.
5. **Ingestion time (deterministic only).** `ingested_at` is a technical fallback, never a primary business order.
6. **Stable fallback (deterministic only).** Lexicographic `eid` or `source`+`source_seq` to guarantee a total order.

Adding synthetic microseconds *before* deciding semantic order encodes a false story: it implies e04 happened milliseconds after e03, or that e05 happened after both picks, creating fictitious delays between physically simultaneous scans. It can also imply an invoice-to-payment gap based on arbitrary tie-breaks. Therefore we keep `original_timestamp` untouched and treat any `sort_key` microtime as a convention, not a measured time.

**Intended admissible orders**

- **e03–e07 at 10:00:** Picks must precede pack. One admissible total order is `e03 (pick I1) < e05 (pick I2) < e06 (pack detail) < e07 (pack summary)`. The reverse pick order `e05 < e03 < e06 < e07` is equally admissible; the two picks are concurrent.
- **e08–e10 at 10:15:** Mandatory semantic order `e08 < e09 < e10`.
- **e11–e16 at 12:00 after duplicate decision:** Canonical invoice `e11` (with e16 provenance) precedes `e12`; then `e13` and `e14` are concurrent captures; `e15` follows as summary. Thus `e11 < e12 < {e13, e14} < e15`. If e16 is retained as a separate row, place it adjacent to e11 with stable fallback.

exact_groups = ocel_exact.events.groupby(["payload_hash","source_event_key"]).filter(lambda g: len(g)>1)
assert len(exact_groups)>0
ocel_exact = pm4py.ocel_drop_duplicates(ocel_exact)  # justified: exact technical duplicates only
validate_referential_integrity(ocel_exact)

# ---- aggressive library merge scenario ----
ocel_aggr = copy.deepcopy(ocel_raw)
print("WARNING: ocel_merge_duplicates with broad key may merge e13/e14 and e08/e09 erroneously")
ocel_aggr = pm4py.ocel_merge_duplicates(ocel_aggr, have_common_object=True)
validate_referential_integrity(ocel_aggr)

## 7. Sensitivity analysis

**Raw (17 events, ~45 E2O rows).** Order-flattened DFG shows duplicate `Issue Invoice` (e11,e16) and same-label `Dispatch Package` (e08,e09). Item-flattened DFG for I2 contains only e05 pick and pack via e06. Payment-flattened DFG shows two concurrent captures e13,e14 and a separate ERP capture e15.

**Conservative (15 events, ~40 E2O rows).** Exact duplicates removed, but all distinct activities preserved. Order-DBG loses the false duplicate invoice edge; OTG for V1 has one issuance node linked to both sources via attributes. `Pick Item  Pack Package` remains correct for both items.

**Evidence-based merge (13–14 events).** Packing loop `Pack Package  Pack Package` disappears because e06/e07 merged. ERP summary e15 may vanish, so `Capture Payment  Record Payment Summary` edge is lost. Payment-flattened DFG becomes tighter but loses the summary node used by ERP-centric analysts.

**Aggressive library merge (10–13 events).** e08/e09 collapse, removing carrier-accept semantics. If object identity is ignored, e13/e14 collapse, so the parallel partial-payment pattern vanishes. e05 may be dropped if activity+timestamp key is used, causing Item-flattened DFG for I2 to miss a pick.

**Six concrete edges/patterns whose interpretation changes**
1. `Pick Item  Pick Item` (e03e05): retained in conservative; missing if e05 dropped.
2. `Pick Item  Pack Package` for I2: present only if e05 retained.
3. `Pack Package  Pack Package` (e06e07): loop in raw, removed by merge.
4. `Dispatch Package  Dispatch Package` (e08e09): false loop unless labels refined.
5. `Issue Invoice  Authorize Payment`: doubled in raw, corrected after e11/e16 merge.
6. `Capture Payment  Capture Payment` (e13e14): parallel payments in conservative; collapsed erroneously in aggressive.
7. `Capture Payment  Record Payment Summary` (e13/e14e15): lost if e15 dropped.

ET–OT weights shift: `Dispatch Package` weight on Delivery object falls after e09 relabel; OTG path for P1 shortens under aggressive merge.

## 8. Audit trail and reversibility

Proposed provenance schema (one row per merge or refinement):

- `canonical_eid`
- `source_event_ids` (list of merged eids)
- `merge_rule` (e.g., “verified_physical_scan”, “invoice_cross_system”)
- `reviewer_or_rule_version`
- `original_activity` (per source)
- `original_timestamp` (per source)
- `attributes_retained_from_each_source` (mapping)
- `discarded_conflicts` (e.g., conflicting location fields)
- `confidence` and `reason`

An analyst reconstructs the raw view by exploding merged events back to per-source rows using `source_event_ids`, restoring `original_activity` and `original_timestamp`, and re-inserting the original relations. Because `ocel_raw` is never modified, the raw OCEL remains the ultimate backup.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments** (e13/e14): require full object identity including M1/M2.
2. **Converting abstraction-level updates into false rework** (e06/e07, e08/e09): refine labels; never merge summaries with details in conservative mode.
3. **Ordering by ingestion time**: ingestion is only a fallback, never primary.
4. **Treating shared objects as proof of duplication**: e13/e14 share O1,V1; use complete object sets and business keys.
5. **Unioning incompatible E2O relations**: do not add M objects to e15; union only when object genuinely present.
6. **Changing durations through synthetic microseconds**: keep `original_timestamp`; mark sort_key as convention.
7. **Losing source-authoritative attributes**: merge with source prefixes; archive dropped rows.
8. **Applying duplicate functions to the whole OCEL without inspection**: pre-check candidate groups; quarantine unverified pairs.
9. **Dropping e05 or e14 via activity+timestamp matching**: exempt events with distinct object identity.
