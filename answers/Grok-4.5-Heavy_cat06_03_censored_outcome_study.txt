## 1. Target definition

**Primary target.**  
- **Unit of analysis:** credit application case (`case:concept:name`).  
- **Prediction time \(\tau\):** after a fixed early prefix (first \(k=3\)–\(5\) events, or first occurrence of Credit Review) or after a fixed elapsed time from Application Started (e.g., 3/7/14 days), provided the case has not yet reached any terminal decision or activation.  
- **Horizon:** 90 days after Account Activated.  
- **Population:** applications that reach Account Activated and whose `default_90d` label has fully matured by a configurable analysis cutoff (accounting for the observed 7–35-day external feed delay).  
- **Estimand:** the predictive distribution \(P(\text{default_90d}=1 \mid \text{prefix up to }\tau)\) among the subpopulation selected for activation under the historical policy. This is a conditional predictive association, not a marginal probability of default for every application and not a counterfactual “would-default-if-activated” quantity for rejected or withdrawn cases.  

**Why operationally and statistically defensible.** Default is only defined after activation; the available labels match this population exactly. The resulting score can still be applied to every incoming application and interpreted as “estimated default risk *if activated*, given early process signals.” Selection into activation is made explicit in the estimand rather than ignored or fabricated.  

**Credible alternative.** Multi-state / competing-risks outcome for *all* applications that reach \(\tau\): the eventual disposition belongs to \(\{\text{Activated-NoDefault},\ \text{Activated-Default},\ \text{Rejected},\ \text{Withdrawn},\ \text{Transferred},\ \text{Right-censored/Open/Immature}\}\). The quantity of primary interest is the probability of the Activated-Default path. This answers a broader process-outcome question and uses the full 48 000 cases, but requires stronger modelling of all transitions, transfer linkage, and permanent missing feeds. It is therefore treated as the main secondary analysis rather than the primary target.

A pure counterfactual “default if activated under a different policy” is acknowledged but not adopted; it demands untestable assumptions about the activation mechanism.

## 2. Cohort construction

**Inclusion for primary labelled analysis cohort**  
- Application started between 1 Jan 2024 and 31 Dec 2025.  
- Reaches “Account Activated”.  
- Label maturity: `label_available_at` \(\le\) analysis cutoff (or, equivalently, activation timestamp + 90 days + 35-day delay buffer \(\le\) cutoff). Default cutoff = data-extraction date 15 Feb 2026; stricter earlier cutoffs are used for training folds.  
- No permanent missing-outcome-feed flag (partner-originated cases are flagged via `source_system` and examined in sensitivity).  
- Successful linkage if the case was transferred (primary analysis excludes unlinked transfers from the activated set).  

**Exclusion / competing / censored strata**  
- Rejected, Withdrawn: competing terminals (default undefined).  
- Still-open at extract: right-censored for terminal outcome.  
- Activated but immature (label not yet available): right-censored for `default_90d`.  
- Unlinked transfers or permanent missing feeds: competing event or selectively unobserved (sensitivity recovers the ~60 % linkable subset).  

**As-of rules.** All features and events are evaluated strictly at or before \(\tau\). Labels are used only when matured by the analysis cutoff. Policy-change (1 Jul 2025) and migration (15 Oct 2025) dates define strata or interaction features; primary temporal splits respect these boundaries.

**Cohort-flow table (exhaustive partition of the 48 000 applications)**

| Stage / Category | Count | Disposition for primary analysis |
|------------------|------:|----------------------------------|
| Applications started (1 Jan 2024 – 31 Dec 2025) | 48 000 | Full population |
| └ Still-open at extract (15 Feb 2026) | 5 100 | Right-censored (no terminal outcome) |
| └ Rejected | 9 100 | Competing terminal (not activated; not labelled non-default) |
| └ Withdrawn | 5 700 | Competing terminal |
| └ Transferred | 2 900 | Competing / selectively unobserved (~60 % linkable; elevated permanent missing feeds for partners) |
| └ Activated, label immature (incl. delayed feed) | 3 600 | Right-censored for `default_90d` |
| └ Activated + matured label available | 21 600 | Primary labelled cohort (18 900 non-default + 2 700 default) |

The 21 600 cases are further restricted by temporal maturity and start-date windows for each train/validation/test fold.

## 3. Censoring and missing-label strategy

**Distinctions**  
- Ordinary right censoring: still-open applications; activated accounts whose 90-day horizon has not yet elapsed.  
- Delayed labels: external feed arrives 7–35 days after the 90-day horizon (`label_available_at`).  
- Selection through activation: the dominant mechanism; default is observed only for the selected subpopulation.  
- Transfer: treated primarily as a competing terminal event; the 60 % linkage table permits partial recovery of outcomes under a new identifier (sensitivity).  
- Permanently missing outcome feeds (especially partner-originated): non-ignorable missingness mechanism; higher risk of informative missingness.

**Primary analysis strategy.** Complete-case analysis on the matured activated cohort (the 21 600 after temporal maturity filters). The estimand is explicitly conditional on activation. Temporal train/validation/test splits by case start time are used; selection is acknowledged rather than “corrected” away.

**Sensitivity analyses**  
1. Multi-state competing-risks model on all cases that reach \(\tau\), treating Rejected/Withdrawn/Transferred/Open as competing events and Activated-Default as the event of interest.  
2. Survival analysis (time-to-default from activation) that includes the 3 600 immature activated cases as right-censored observations.  
3. Inverse-probability-of-activation weighting: model \(P(\text{activate}\mid\text{prefix}+\)static attributes) on the larger set of cases that reach \(\tau\), then re-weight the labelled activated sample.  
4. Recover outcomes for the linkable transfer subset; compare complete-case versus recovered results.  
5. Restrict or stratify by pre-/post-policy-change and pre-/post-migration windows; or treat permanent missing feeds as a separate category / worst-case sensitivity.

**Assumptions**  
- Testable: empirical distribution of label delays; pre-/post-policy differences in activation rates, feature distributions and default rates; linkage success rates by covariates.  
- Partially testable: association of missing-feed indicators with observed early features (MAR-like checks).  
- Fundamentally untestable: the full selection mechanism into activation (unmeasured confounders); counterfactual default under an alternative activation policy; whether partner missingness is informative of the missing default itself (MNAR).

## 4. Prefix extraction

Prefixes are generated so that no event or attribute after the prediction time \(\tau\) can enter the feature table.

- **Fixed event-count prefixes.** For \(k\in\{3,4,5\}\) retain only cases that possess at least \(k\) events whose \(k\)-th event precedes any Accept/Reject/Withdraw/Transfer/Contract-Signed/Account-Activated event. Prefix = the first \(k\) events.  
- **Elapsed-time prefixes.** For \(\tau\in\{3,7,14\}\) days from Application Started, take all events with timestamp \(\le\) start \(+\tau\) provided the case has not yet terminated.  
- **Short cases.** Cases that terminate before \(k\) (or before \(\tau\)) are excluded from that particular prefix length for the primary (activated) analysis; they remain available for the multi-state alternative.  
- **Document loops / rework.** All events that fall inside the prefix window are retained; the number of “request-documents” or return-to-Credit-Review transitions becomes a rework feature.  
- **Activity renaming (post-15 Oct 2025).** A canonical mapping dictionary is applied to `concept:name` before prefix extraction. Occasional migration duplicates (identical case, activity, near-identical timestamp and resource) are deduplicated by keeping the earliest.  
- **Implementation.** After `pm4py.format_dataframe`, convert to an event log and call `pm4py.get_prefixes_from_log` (or an equivalent group-by + cum-count filter). Immediately after extraction, drop every row whose timestamp exceeds the prefix end-time and null-out any post-decision columns.

## 5. Process-aware features

All features are required to be available at \(\tau\).

- **Static case attributes** (known at or near Application Started): `case:channel`, `case:region`, `case:requested_amount`, partner-origin flag from `source_system`.  
- **Prefix-derived control-flow:** activity counts / set of activities so far, partial variant, number of Credit-Review visits, number of document-request loops (rework), presence of Identity/KYC.  
- **Timing:** elapsed time from start to \(\tau\), mean/median inter-event times, time-of-day / day-of-week of the last event, sojourn indicators if service/waiting times can be derived from consecutive events.  
- **Resource / queue:** `org:resource` identifiers (or entropy of resources) observed in the prefix; concurrent-case proxies only if constructed from historical cases as-of \(\tau\). Resource experience is *not* taken from the extraction-time value.  
- **Cohort / calendar:** start month/quarter, indicator for start (or \(\tau\)) before/after the 1 Jul 2025 policy change, before/after the 15 Oct 2025 migration, days since policy change.  
- **risk_score:** only the value(s) recorded on events \(\le\tau\) (last known or simple trajectory summary).  
- **Historical reference data** (computed solely from training-period cases as-of \(\tau\)): recent regional activation rates, average early risk_score of similar requested-amount bands, etc.  

`documents_total` is either lagged to the previous calendar day or replaced by the count of document-related events inside the prefix. Features that require post-\(\tau\) information are never computed.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|-------------------------|----------------------|-------------------------|------------------|-----------|
| `final_limit` | High – populated only after final credit decision | Only if already known and timestamped \(\le\tau\) (rare for early prefixes) | Drop | Directly encodes acceptance and terms; unavailable early |
| `decision_reason` | High – appears at or after Accept/Reject | \(\le\tau\) | Drop | Reveals terminal decision |
| `collection_status` | Critical – updated after activation; can encode default | After Account Activated | Drop | Direct or near-direct outcome leakage |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | Critical look-ahead | Events with `time:timestamp` \(\le\tau\) only | Drop / filter | Standard temporal leakage |
| `documents_total` (nightly snapshot) | Medium–High – may include same-day later uploads | Value as-of previous calendar day or strictly \(\le\tau\) | Repair (lag) or drop | Same-day leakage risk |
| `risk_score` (updated) | Medium – later updates reflect additional information | Last (or trajectory of) value(s) with timestamp \(\le\tau\) | Keep (repaired) | Valid once restricted to prefix observations |
| Resource experience | High – stored as experience at extraction time, not event time | Reconstruct as-of event timestamp from historical data if available; otherwise unavailable | Drop (or repair if historical table exists) | Extraction-time value leaks future tenure |
| `default_90d` / `label_available_at` | Critical if used as feature | Never as feature; only as target after maturity check | Drop from features | Pure label leakage |
| `org:resource` | Low when only identifier is used | Available at event time \(\le\tau\) | Keep | Contemporaneous process resource |
| `case:requested_amount`, `case:channel`, `case:region` | Low (static early attributes) | Known at Application Started | Keep | Pre-prediction |
| `source_system` / partner flag | Medium (selection into missing feeds) | Known early | Keep (for diagnostics & subgroup) | Essential for missingness analysis |

Any derived feature that inadvertently aggregates post-\(\tau\) information is regenerated from the prefix log only.

## 7. Validation design

**Primary scheme.** Strictly temporal split by case start time, never a random case split.  
Illustrative windows (adjustable once exact maturity counts are known):  
- Train: starts 1 Jan 2024 – 31 Mar 2025 (pre-policy, fully mature).  
- Validation: starts 1 Apr 2025 – 30 Jun 2025 (pre-policy, later).  
- Test: starts 1 Jul 2025 – 30 Sep 2025 (post-policy, pre-migration, labels matured by extract).  
A separate post-migration hold-out is examined if sufficient mature cases exist. Rolling-origin or expanding-window back-testing is used for additional robustness.

**Why a random case split is misleading.** It mixes pre- and post-policy periods (different selection probabilities and outcome relationships), pre- and post-migration periods (activity-name changes and occasional duplicates), and cases of differing label maturity. Temporal dependence, concurrent process evolution and concept drift are ignored, producing optimistically biased performance estimates.

**Additional safeguards.**  
- Label maturity is enforced for every evaluation fold (activation + 90 d + delay buffer \(\le\) fold-specific cutoff).  
- Performance is reported overall and stratified by policy period, migration period, channel, region, requested-amount quantile and early risk-score tercile.  
- Distribution shift is monitored (Population Stability Index or Kolmogorov–Smirnov on key features; activation-rate and default-rate drift).  
- Calibration is examined via reliability diagrams, calibration slope/intercept and expected calibration error; these are critical for an early-warning risk score.

**Metrics.**  
- Primary binary target: ROC-AUC, PR-AUC (class imbalance \(\approx\) 12.5 %), Brier score, calibration metrics, cost-sensitive recall/precision at operating points relevant to the lender.  
- Survival sensitivity: concordance index, time-dependent AUC, integrated Brier score.  
- Multi-state alternative: multi-class log-loss, one-vs-rest AUC for the Activated-Default class, or cause-specific concordance.

## 8. Limitations and decision-use boundary

The study can claim a well-calibrated predictive association between early process prefixes and 90-day default *among applications that historically reached activation under the observed policy*. It cannot claim:

- a marginal default probability for every application;  
- a counterfactual default risk for applications that were rejected, withdrawn or left open (those outcomes are undefined under the observed policy without strong, untestable assumptions);  
- a causal effect of intervening on early process signals;  
- transportability to a new activation policy, partner mix or process design without re-calibration and monitoring.

Selection effects are intrinsic: the model learns the relationship that holds for the selected activated subpopulation.  

**Three ways deployment can change the data-generating process**  
1. If high predicted risk triggers early rejection or extra scrutiny, the composition of future activated accounts shifts toward lower-risk cases; subsequent labels and the relationship between prefixes and default change (feedback / selection intensification).  
2. Staff or applicants may alter behaviour once the monitoring system is known (gaming of resource assignment, document-upload patterns, or risk-score-related actions), invalidating control-flow and timing features.  
3. Process or policy changes (new activities, altered document loops, revised credit thresholds, different partner platforms) alter the distribution of prefixes and the activation–default relationship, producing concept drift that the original model does not automatically track.

Continuous monitoring of activation rates by predicted-risk band, feature drift and calibration is therefore required after deployment.

## 9. PM4Py-oriented Python implementation skeleton

```python
"""
Uncertainty-aware predictive process monitoring skeleton.
Assumptions (marked): activation selection is treated as defining the
population; label delay buffer = 35 days; activity-name mapping must be
supplied for post-migration repair; resource experience at extract time
is dropped.
Later connection points for survival / competing-risk models are commented.
"""

import pandas as pd
import numpy as np
from datetime import timedelta
import pm4py
from pm4py.objects.conversion.log import converter as log_converter

# ------------------------------------------------------------------
# 0. Configuration
# ------------------------------------------------------------------
CUTOFF = pd.Timestamp("2026-02-15")
DELAY_BUFFER = timedelta(days=35)
POLICY_CHANGE = pd.Timestamp("2025-07-01")
MIGRATION = pd.Timestamp("2025-10-15")
PREFIX_LEN = 4
TRAIN_END = pd.Timestamp("2025-03-31")
VAL_END   = pd.Timestamp("2025-06-30")
# TEST = starts after VAL_END that still mature by CUTOFF

# ------------------------------------------------------------------
# 1. Load & format
# ------------------------------------------------------------------
df = pd.read_csv("applications_events.csv", parse_dates=[
    "time:timestamp", "label_available_at", "data_extract_time"
])
df = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# Canonical activity mapping for post-migration rename (fill with real map)
ACTIVITY_MAP = {}  # e.g. {"OldCreditReview": "Credit Review", ...}
df["concept:name"] = df["concept:name"].replace(ACTIVITY_MAP)

# Deduplicate occasional migration duplicates
df = df.sort_values(["case:concept:name", "time:timestamp"])
df = df.drop_duplicates(
    subset=["case:concept:name", "concept:name", "time:timestamp", "org:resource"],
    keep="first"
)

# ------------------------------------------------------------------
# 2. Case-level start, activation, terminal, maturity (as-of CUTOFF)
# ------------------------------------------------------------------
case_stats = df.groupby("case:concept:name").agg(
    start_time=("time:timestamp", "min"),
    end_time=("time:timestamp", "max"),
    n_events=("concept:name", "count"),
    last_activity=("concept:name", "last"),
    default_90d=("default_90d", "first"),          # repeated on events when known
    label_available_at=("label_available_at", "first"),
    source_system=("source_system", "first"),
    channel=("case:channel", "first"),
    region=("case:region", "first"),
    requested_amount=("case:requested_amount", "first"),
).reset_index()

# Activation time (first occurrence)
act = (df[df["concept:name"] == "Account Activated"]
       .groupby("case:concept:name")["time:timestamp"].min()
       .rename("activation_time"))
case_stats = case_stats.merge(act, left_on="case:concept:name", right_index=True, how="left")

# Terminal type (simplified rules; expand as needed)
def terminal_type(row):
    if pd.notna(row["activation_time"]):
        return "Activated"
    if row["last_activity"] in {"Rejected", "Withdrawn", "Transferred"}:
        return row["last_activity"]
    if row["end_time"] >= CUTOFF - timedelta(days=1):
        return "StillOpen"
    return "Other"

case_stats["terminal"] = case_stats.apply(terminal_type, axis=1)
case_stats["is_activated"] = case_stats["terminal"] == "Activated"
case_stats["is_mature"] = (
    case_stats["is_activated"]
    & case_stats["label_available_at"].notna()
    & (case_stats["label_available_at"] <= CUTOFF)
)
# Alternative maturity: activation + 90d + buffer
# case_stats["is_mature"] = (
#     case_stats["is_activated"]
#     & (case_stats["activation_time"] + timedelta(days=90) + DELAY_BUFFER <= CUTOFF)
# )

# Cohort counts (section 2 flow)
print("=== Cohort flow (as-of cutoff) ===")
print(case_stats["terminal"].value_counts(dropna=False))
print("Mature activated (primary labelled):", case_stats["is_mature"].sum())
print("of which default_90d=1:", case_stats.loc[case_stats["is_mature"], "default_90d"].sum())

# ------------------------------------------------------------------
# 3. Temporal split by case start time (never random)
# ------------------------------------------------------------------
case_stats["split"] = "test"
case_stats.loc[case_stats["start_time"] <= TRAIN_END, "split"] = "train"
case_stats.loc[
    (case_stats["start_time"] > TRAIN_END) & (case_stats["start_time"] <= VAL_END),
    "split"
] = "val"
# Further restrict each split to mature labels for supervised evaluation
labelled = case_stats[case_stats["is_mature"]].copy()
print("\nTemporal split sizes (mature activated only):")
print(labelled.groupby("split").size())

# ------------------------------------------------------------------
# 4. Prefix extraction (fixed length) without future leakage
# ------------------------------------------------------------------
# Keep only mature activated cases for primary model
train_cases = set(labelled.loc[labelled["split"] == "train", "case:concept:name"])
df_train = df[df["case:concept:name"].isin(train_cases)].copy()

log_train = pm4py.convert_to_event_log(df_train)
# Fixed-length prefixes; filter later to ensure k-th event precedes activation
prefixes = pm4py.get_prefixes_from_log(log_train, PREFIX_LEN)

# Convert prefixes back to dataframe for feature engineering
pref_df = pm4py.convert_to_dataframe(prefixes)

# Prediction time = timestamp of last event in each prefix
pred_times = (pref_df.groupby("case:concept:name")["time:timestamp"]
              .max().rename("pred_time"))
pref_df = pref_df.merge(pred_times, left_on="case:concept:name", right_index=True)

# Strict temporal filter: drop any residual post-pred events (safety)
pref_df = pref_df[pref_df["time:timestamp"] <= pref_df["pred_time"]]

# ------------------------------------------------------------------
# 5. Feature table – only information available at pred_time
# ------------------------------------------------------------------
# Drop known leaky columns immediately
leaky_cols = [
    "final_limit", "decision_reason", "collection_status",
    "default_90d", "label_available_at", "data_extract_time"
]
feat_cols_to_drop = [c for c in leaky_cols if c in pref_df.columns]
pref_df = pref_df.drop(columns=feat_cols_to_drop, errors="ignore")

# Example process-aware aggregates (prefix-derived)
def prefix_features(g):
    return pd.Series({
        "n_events": len(g),
        "n_unique_acts": g["concept:name"].nunique(),
        "n_credit_review": (g["concept:name"] == "Credit Review").sum(),
        "n_doc_requests": g["concept:name"].str.contains("document", case=False, na=False).sum(),
        "elapsed_hours": (g["time:timestamp"].max() - g["time:timestamp"].min()).total_seconds() / 3600,
        "last_risk": g["risk_score"].iloc[-1] if "risk_score" in g else np.nan,
        # resource experience deliberately omitted – extract-time only
    })

X = pref_df.groupby("case:concept:name").apply(prefix_features).reset_index()
# Join static attributes & target (target only for mature cases)
X = X.merge(
    labelled[["case:concept:name", "default_90d", "channel", "region",
              "requested_amount", "start_time", "split"]],
    on="case:concept:name", how="inner"
)
# Policy indicator (known at start)
X["post_policy"] = (X["start_time"] >= POLICY_CHANGE).astype(int)

# ------------------------------------------------------------------
# 6. Leakage-audit checks
# ------------------------------------------------------------------
print("\n=== Leakage audit ===")
assert "final_limit" not in X.columns, "final_limit leaked into features"
assert "collection_status" not in X.columns, "collection_status leaked"
assert "default_90d" in X.columns, "target missing"
# Verify no future timestamps survived
assert (pref_df["time:timestamp"] <= pref_df["pred_time"]).all()
print("Leakage checks passed (final_limit, collection_status, future events absent).")
print("Feature matrix shape:", X.shape)
print("Default rate in train:", X.loc[X["split"]=="train", "default_90d"].mean())

#   duration = min(90, (censor_time - activation_time).days)
```
