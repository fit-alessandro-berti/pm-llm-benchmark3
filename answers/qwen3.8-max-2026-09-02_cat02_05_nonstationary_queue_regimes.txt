Change-point heuristic:
```python
def best_single_changepoint(dates, values, min_seg=3):
    values=np.asarray(values,float)
    n=len(values)
    best={'sse_full': ((values-values.mean())**2).sum()}
    best_sse=best['sse_full']
    for k in range(min_seg, n-min_seg):
       left=values[:k]; right=values[k:]
       sse=((left-left.mean())**2).sum()+((right-right.mean())**2).sum()
       if sse < best_sse:
          best_sse=sse; best={'split_after':dates[k-1], 'left_mean':left.mean(), 'right_mean':right.mean(), 'sse':sse}
    best['sse_reduction_pct'] = 100*(best['sse_full']-best_sse)/best['sse_full'] if best_sse<best['sse_full'] else 0
    return best
```

```python
def autocorr(x, lag=1):
    x=np.asarray(x, dtype=float)
    if len(x) <= lag: return np.nan
    xm=x-x.mean()
    denom=np.sum(xm**2)
    if denom==0: return np.nan
    return np.sum(xm[:-lag]*xm[lag:])/denom
```

```python
def best_single_changepoint(dates, values, min_seg=3):
    x=np.asarray(values, dtype=float)
    n=len(x)
    full_sse=float(np.sum((x-x.mean())**2))
    best={"variable": None, "split_after_date": None, "left_mean": np.nan, "right_mean": np.nan, "sse_reduction_pct":0.0}
    best_sse=full_sse
    for k in range(min_seg, n-min_seg):
        left=x[:k]; right=x[k:]
        sse=np.sum((left-left.mean())**2)+np.sum((right-right.mean())**2)
        if sse < best_sse:
            best_sse=sse
            best={"split_after_date": str(dates[k-1].date()), "left_mean": left.mean(), "right_mean": right.mean(), "sse_reduction_pct": 100*(full_sse-sse)/full_sse if full_sse>0 else 0}
    return best
```

# 1. Data audit and estimands

The supplied data are **daily aggregates**, not an event log. They are sufficient for regime discovery, directional queueing diagnostics, and bounded estimates, but they are not sufficient for a fully specified stochastic queueing model.

## Opening-hours convention

- Service center open: **07:00–19:00**, i.e. **12 opening hours = 720 minutes** per day.
- `arrivals` and `completed` are treated as counts during opening hours.
- Arrival intensity:  
  \[
  \lambda_A = \frac{\text{arrivals}}{12\text{ opening hours}}
  \]
  reported as cases/day and cases/opening-hour.
- Completion intensity:  
  \[
  \lambda_C = \frac{\text{completed}}{12\text{ opening hours}}
  \]
  This is observed system throughput, not necessarily same-day arrival throughput because completed cases may have arrived earlier.

## Queueing estimands

| Quantity | Definition used here | Unit | Main limitation |
|---|---:|---:|---|
| Arrival intensity | `arrivals / 12h` | cases/hour or cases/day | No intraday exact timestamps in daily table |
| Completion intensity | `completed / 12h` | cases/hour or cases/day | Completions may belong to prior-day backlog |
| Service-time behavior | `median_service_min`, `p90_service_min` | minutes of active handling | Mean service time is not observed; median is not mean |
| WIP | `mean_wip` from 15-minute snapshots | cases in system | Snapshot window and overnight treatment are not fully specified |
| Capacity | `staff_fte` as concurrent available FTEs | servers / FTEs | Available capacity is not the same as busy capacity |
| Capacity pressure proxy | \(\rho_{\text{med}} = \lambda_A \cdot \text{median service} / c\), \(\rho_{\text{p90}} = \lambda_A \cdot \text{p90 service} / c\) | dimensionless Erlang-like index | Not true utilization because mean service time is unknown |
| Net inventory change | `arrivals - completed` | cases/day | Positive values indicate backlog building, absent losses |

## Assumptions used in this analysis

I label these explicitly because the aggregates do not fully determine them.

- **A1 — Opening-window rate basis:** Arrival and completion rates are scaled by 12 opening hours, not 24 hours.
- **A2 — WIP snapshot window:** `mean_wip` is assumed to represent the opening-hours system population unless stated otherwise. If snapshots include closed hours, Little’s-Law interpretations over opening hours become less direct.
- **A3 — No losses:** There is no evidence of abandonment or rejection, so net `arrivals - completed` is interpreted as backlog change.
- **A4 — Representative vectors are illustrative:** The four hourly vectors are representative examples, not necessarily exact reconstructions of the daily rows.
- **A5 — Intervention assignment:** Because the staffing intervention began sometime during 2026-04-29 but the exact time was not logged, 2026-04-29 is assigned to the intervention regime in the primary segmentation. This is a necessary but uncertain boundary choice.
- **A6 — Service percentiles are case-mix summaries:** Daily medians and p90s are summarized across days by unweighted daily means unless otherwise noted. They are not case-weighted pooled percentiles.
- **A7 — Complex percentage applies to arrivals:** `complex_pct` is treated as a daily arrival-mix indicator, while recognizing it could reflect a coding change rather than only true work-content change.

## Threats to naive inference

At least five important threats are present.

1. **Nonstationarity and regime changes.**  
   The series contains weekday/weekend cycles, an outage, post-outage recovery, a large case-mix shift around 2026-04-20, and a staffing intervention beginning 2026-04-29. A pooled stationary queueing model would mix incompatible operating conditions.

2. **Median and p90 service times are not mean service times.**  
   Queueing capacity calculations require mean service time \(E[S]\). The data provide only medians and p90s. Using the median as if it were the mean would usually understate load for right-skewed service distributions. Using p90 as if it were the mean would overstate load in many settings but can be useful as a stress index.

3. **Open population and carry-over backlog.**  
   Completed cases need not have arrived on the same day. Cases can carry over overnight. The backlog at 07:00 is not supplied. Over the 28 days, total arrivals exceed total completions by **110 cases**, so the system did not begin and end in the same backlog state unless there were unobserved losses or pre-period backlog differences.

4. **Intraday information is hidden or inconsistent.**  
   The daily table hides hourly burstiness. The representative hourly vectors show burstiness, especially on 2026-04-21. Also, the stated `peak_08_10_pct` is not literally reconcilable with the representative vectors under the stated bin convention. For example, the 2026-04-07 vector gives only about 17% of arrivals in 08:00–09:59 if bins are interpreted literally, while the table reports 31%. Therefore `peak_08_10_pct` should be treated as a directional aggregate, not as a precisely reconstructed hourly metric.

5. **Measurement and coding ambiguity.**  
   `complex_pct` may reflect a real case-mix shift, a coding/documentation change, or both. `staff_fte` is concurrently available capacity, not necessarily productive busy time. `outage_min` is only given for one day, and the intervention time is not logged.

6. **Serial dependence and weekly seasonality.**  
   Daily rows are not independent. Weekends are structurally different from weekdays, and multi-day regimes persist. Naive daily independence would understate uncertainty and overstate the information content of 28 rows.

The primary segmentation is deliberately operational: it separates **day type**, **outage**, **recovery**, **case-mix shift**, and **staffing intervention**. It is not claimed to be the unique correct segmentation.

The capacity-pressure numbers below are **arrival-based proxy indices**, not true utilizations:

\[

\[

The outage day is **not** treated as a normal high-throughput regime. Its completion intensity is suppressed by lost capacity, not by low demand. The following two weekdays are treated as **recovery**, because completions exceed arrivals and WIP falls. Recovery throughput is therefore partly the processing of accumulated backlog, not a sustainable steady-state completion rate.

The 2026-04-29 intervention boundary is uncertain. If the intervention began late in the day, 04-29 is a blended day. However, the direction of the effect is still visible on 04-30 and 05-01: higher staffing, completions above arrivals, falling WIP, and slightly lower service percentiles.

# 3. Alternative segmentation

A materially different segmentation is a **case-mix-first segmentation**. Instead of starting from calendar events and staffing changes, it treats the jump in `complex_pct` as the dominant regime boundary.

| Alternative regime | Dates | Operational story | Key estimates |
|---|---|---|---:|
| **Low-complex period** | 2026-04-06 to 04-19 | The case mix is mostly simple; the outage and immediate recovery are treated as temporary shocks inside an otherwise low-complex operating environment. | arrivals 84.6/day; completions 83.0/day; median 27.4 min; p90 53.6 min; WIP 23.6; staff 5.07; complex 22.4% |
| **High-complex period** | 2026-04-20 to 05-03 | The dominant change is a shift toward complex variants, higher service percentiles, higher peak concentration, and higher WIP. The staffing intervention is interpreted as a response to this mix shift, not as a separate regime by itself. | arrivals 95.4/day; completions 89.1/day; median 34.5 min; p90 63.5 min; WIP 36.1; staff 5.21; complex 43.3% |

Within the high-complex period, one would still separate weekdays, weekends, pre-intervention backlog building, and post-intervention recovery for staffing decisions. But the primary explanatory variable is the mix shift.

## Strengths of the alternative segmentation

- It captures the largest persistent change in the data: complex pct rises from roughly **22%** to **43%**, median service rises from about **27** to **35** minutes, and mean WIP rises from about **24** to **36** cases.
- It avoids over-attributing changes to the staffing intervention when the intervention may be endogenous to the mix shift.
- It is more robust to the unknown exact intervention time on 2026-04-29.

## Weaknesses of the alternative segmentation

- It hides the outage and recovery transients. The outage day and post-outage recovery are operationally important and should not be averaged into a generic low-complex regime for capacity planning.
- It cannot distinguish whether `complex_pct` reflects a real change in work content or a coding/documentation change. If the latter, the segmentation may describe recording behavior more than physical processing.
- It blends backlog-building and backlog-clearing phases inside the high-complex period, which weakens queueing-law interpretation.

## Comparison with the primary segmentation

The primary segmentation is better for **operational control**: it isolates outage, recovery, intervention, and weekday/weekend staffing differences. The alternative segmentation is better for **strategic diagnosis**: it emphasizes the persistent case-mix or coding change that appears to drive service-time and WIP increases. Both are defensible; they answer different questions.

## Three ways pooled summaries obscure behavior

### 1. Weekday/weekend composition

The pooled average arrival rate is about **90 cases/day**, but this is a mixture of:

- weekdays: about **108 cases/day**;
- weekends: about **45 cases/day**.

That is a factor of roughly **2.4**. A pooled M/M/c or M/G/c model using 90/day would misrepresent both weekday congestion and weekend idleness. Staffing also differs sharply: weekday staff is about **6.15 FTE**, while weekend staff is about **2.63 FTE**. Pooled averages describe neither regime well.

### 2. Complex-case mix and service-time behavior

The low-complex and high-complex periods have materially different service behavior:

- median service rises from **27.4** to **34.5** minutes, about **+26%**;
- p90 service rises from **53.6** to **63.5** minutes, about **+18%**;
- mean WIP rises from **23.6** to **36.1**, about **+53%**;
- staff rises only slightly, from **5.07** to **5.21** FTE.

A pooled estimate would suggest a moderate average service time around **31 minutes**, hiding the fact that the later period has both heavier service tails and higher WIP. If the complex increase is real, pooled staffing will under-provision the later regime. If it is a coding change, pooled statistics still hide a change in recorded process behavior.

### 3. Outage, recovery, and staffing intervention

The outage day and recovery days can severely distort pooled weekday statistics:

- normal baseline weekday completions: about **99.6/day**;

# 5. Burstiness, autocorrelation, and stationarity

## Representative hourly vectors

The four representative hourly vectors are not enough to fit a full stochastic arrival or service process, but they show important differences.

| Representative day | Note | Arrival Fano | Arrival CV | Completion Fano | Completion CV |
|---|---|---:|---:|---:|---:|
| 2026-04-07 | ordinary weekday candidate | 2.96 | 0.59 | 1.56 | 0.43 |
| 2026-04-15 | outage approximately 11:00–14:00 | 3.79 | 0.66 | 2.06 | 0.65 |
| 2026-04-21 | bursty post-mix-change weekday | 9.28 | 0.98 | 0.90 | 0.33 |
| 2026-04-25 | weekend candidate | 1.18 | 0.53 | 0.72 | 0.45 |

The Fano factor here is the variance-to-mean ratio across the 12 hourly bins. The coefficient of variation is standard deviation divided by mean. These are descriptive of the intraday shape, not proof of a point-process distribution, because the hourly rate is not stationary within the day.

Key observations:

- The ordinary weekday is already somewhat peaked, with arrival Fano about **3**.
- The outage day has a normal-looking arrival shape but a completion vector distorted by zero completions during the outage.
- The post-mix-change weekday 2026-04-21 is strongly bursty, with arrival Fano about **9.3** and CV close to **1**. Completions are much smoother, with Fano below **1**, suggesting the queue absorbed arrival bursts.
- The weekend day is flatter and lower volume.

A pooled hourly Poisson assumption would be especially poor for the post-mix-change weekday. Burstiness increases waiting time risk even if average utilization is unchanged.

## Daily overdispersion

Using all 28 daily arrival counts:

- mean daily arrivals  **90.0**;
- variance  **870**;
- Fano factor  **9.7**;
- CV  **0.33**.

But this high dispersion is largely compositional. Restricting to the 20 weekdays:

- mean weekday arrivals  **108.0**;
- variance  **68**;
- Fano factor  **0.63**;
- CV  **0.08**.

Thus the pooled daily arrival process looks highly overdispersed mainly because weekdays, weekends, outage, recovery, and mix-shift days are mixed together. Within ordinary weekdays, arrivals are much more regular.

## Serial dependence

Daily rows are not independent. A simple autocorrelation calculation on daily arrivals gives approximately:

- lag-1 autocorrelation  **0.4**;
- lag-7 autocorrelation  **0.7**.

The lag-7 value is consistent with strong weekly seasonality. `mean_wip`, `complex_pct`, and `staff_fte` also persist over several days, so tests that assume independent daily observations would be misleading.

## Change-point evidence

There are visible changes:

- **2026-04-15**: completion collapse and WIP jump due to outage.
- **2026-04-16 to 04-17**: recovery, completions exceed arrivals.
- **2026-04-20**: persistent jump in `complex_pct`, service percentiles, peak concentration, and WIP.
- **2026-04-29 onward**: staffing increases and WIP begins to decline.

In particular, one-day anomalies such as the outage are not always well captured by a two-segment mean-shift model.

## Why four representative days are insufficient

The four hourly vectors cannot establish a full stochastic model because:

- they are selected representatives, not a random sample;
- they do not provide exact dates/times for every event;
- they do not provide service start/end times;
- they do not provide initial queue length;
- they do not provide exact outage start/end or intervention start;
- they do not establish whether burstiness is exogenous or induced by backlog release.

Event-level data would be needed for a defensible arrival process, service process, and queue-discipline model.

# 6. Little's-Law applicability matrix

Little’s Law is:

\[
L = \lambda W
\]

where \(L\) is average number in system, \(\lambda\) is long-run throughput, and \(W\) is average flow time. With daily aggregates:

- \(L\) is approximated by `mean_wip`.
- \(\lambda\) is usually approximated by completions per opening hour when the window is near inventory balance, because completions are observed departures.
- \(W\) is then an **implied total flow time**, including waiting and possibly carry-over time. It is **not** active service time.
- The median service time must not be substituted for \(W\).

The implied flow times below use:

\[
W = \frac{\text{mean WIP}}{\text{completions per opening hour}}
\]

The unit is **opening-hours** if WIP is measured during opening hours. If WIP includes closed hours or if overnight carry-over is material, the interpretation becomes more complicated.

| Window / regime | Boundary stability | Throughput proxy | WIP comparability | Carry-over risk | Stationarity assessment | Implied flow-time calculation | Verdict |
|---|---|---|---|---|---|---|---|
| **Pooled all 28 days** | Not stable: net +110 cases over period; regime mix | Completions 86.0/day = 7.17/h | Mixed weekday/weekend and mixed regimes | High | Not stationary | Diagnostic only: 29.9 / 7.17 = **4.16 h = 250 min** | **not defensible** |
| **Baseline weekdays, Apr 06–10 and Apr 13–14** | Approximately stable: net +0.6/day | Completions 99.6/day = 8.30/h; arrivals nearly equal | Comparable opening-hour WIP across similar weekdays | Moderate | Approximate; intraday variation remains | 20.3 / 8.30 = **2.45 h = 147 min** | **approximate only** |
| **Baseline weekends pre-mix, Apr 11–12 and Apr 18–19** | Approximately stable: net +0.25/day | Completions 41.5/day = 3.46/h | Comparable weekend WIP | Moderate | Approximate but small sample | 13.8 / 3.46 = **3.98 h = 239 min** | **approximate only** |
| **Outage day, Apr 15** | Highly unstable: capacity shock, WIP jump | Completions 58/day = 4.83/h, suppressed by outage | WIP spike not comparable to normal operation | High | Not stationary | Diagnostic only: 47 / 4.83 = **9.72 h = 583 min** | **not defensible** |
| **Post-outage recovery weekdays, Apr 16–17** | Unstable but clearing: net about -15/day | Completions 120.5/day = 10.04/h; includes backlog processing | WIP high but falling | High | Not stationary | Diagnostic only: 43.5 / 10.04 = **4.33 h = 260 min** | **approximate only** |
| **High-complex weekdays pre-intervention, Apr 20–24 and Apr 27–28** | Unstable: backlog building, net +13.4/day | Completions 100.6/day = 8.38/h; arrivals 114/day are not equal to throughput | WIP rising and high | High | Not stationary | Diagnostic only: 44.3 / 8.38 = **5.28 h = 317 min** | **not defensible** |

## Interpretation

No window is fully “applicable” in the strict steady-state Little’s-Law sense because the aggregates lack exact initial/final backlog, exact opening WIP, and full intraday stationarity. The most defensible approximate windows are the baseline weekday and baseline weekend windows because net inventory change is small. Recovery windows can be interpreted as finite-horizon diagnostics, but their completion rates include backlog processing and should not be treated as sustainable throughput.

The implied flow times are much larger than the median active service times. That is not an error: Little’s Law estimates total time in system, including waiting and possibly overnight carry-over, while the supplied service times exclude waiting.

# 7. Operational implications

## Staffing recommendations

1. **Use regime-based staffing, not pooled averages.**  
   Baseline weekdays appear roughly stable around **6 FTE** with WIP near **20**. High-complex weekdays before the intervention had similar staffing but WIP above **40**, indicating that the same staff level was insufficient for the new mix.

2. **Maintain intervention-level weekday capacity until WIP stabilizes.**  
   The intervention period shows completions above arrivals and falling WIP. A reasonable exit condition is not merely one or two days of completions exceeding arrivals, but a sustained return to WIP near baseline levels, for example weekday WIP around **20–25**, with arrivals and completions approximately balanced.

3. **Increase high-complex weekend capacity.**  
   Pre-intervention high-complex weekends had only **2.5 FTE**, median service around **35–36** minutes, and p90 around **83** minutes. The later weekend staff level of **3.0 FTE** is more consistent with the higher-complex weekend workload.

4. **Do not treat recovery throughput as permanent capacity.**  
   Completion rates of about **120/day** during recovery reflect backlog drawdown. They should not be used to justify permanently lower staffing once the backlog is cleared.

## Backlog recovery recommendations

- Track `arrivals - completed` and `mean_wip` jointly. A positive net inventory change with high WIP is a backlog-building warning.
- During recovery, protect extra capacity until WIP returns to target. Removing surge capacity too early can cause the backlog to rebuild.
- After an outage, explicitly plan catch-up capacity. The outage day shows that lost completion capacity creates a multi-day effect.

## Peak smoothing recommendations

- The high-complex period has higher `peak_08_10_pct`, rising from roughly **30%** in baseline weekdays to about **46%** in pre-intervention high-complex weekdays. Even allowing for definition ambiguity, the direction is clear: arrivals became more concentrated.
- The 2026-04-21 representative vector shows strong burstiness. If similar bursts are common, appointment scheduling, arrival caps, callback queues, or triage/fast-track for simple cases could reduce waiting.
- Consider a dedicated complex-case team or specialist pool. The p90/median ratio increases in the high-complex period, suggesting heavier tails and greater variability.

## Data-collection recommendations

The current aggregates are useful but insufficient for a rigorous queueing model. The center should collect:

1. Event-level timestamps: arrival, queue entry, service start, service end, completion.
2. Case identifiers and variant/classification, including complex versus simple.
3. Exact outage start/end and intervention start/end.
4. Opening backlog at 07:00 and closing backlog at 19:00.
5. Staff schedules, breaks, and actual concurrent availability.
6. Snapshot WIP over a clearly defined window, including whether closed hours are included.
7. Validation of the `peak_08_10_pct` definition against hourly counts.

## Policy that looks beneficial under pooled averages but risky under segmented view

A pooled view might support reducing weekday staffing toward the overall average of about **5.1 FTE**, because pooled average completions are only about **86/day** and pooled pressure using median service looks moderate. Under the segmented view, this is risky. High-complex weekdays before the intervention had arrivals around **114/day**, median-based pressure around **0.94**, p90-based pressure above **2**, and WIP above **40**. A small staff reduction in that regime would likely push the system into persistent backlog growth. Similarly, using recovery-day completion rates of about **120/day** to justify cutting intervention staffing would be risky because those completions are partly backlog drawdown, not sustainable steady-state throughput.

```python
def summarize(df, label):
    if len(df) == 0:
        return None

    arr = df["arrivals"].mean()
    comp = df["completed"].mean()
    med = df["median_service_min"].mean()
    p90 = df["p90_service_min"].mean()
    wip = df["mean_wip"].mean()
    staff = df["staff_fte"].mean()

    return pd.Series({
        "regime": label,
        "n_days": len(df),
        "arrivals_per_day": arr,
        "completions_per_day": comp,
        "arrivals_per_open_hour": arr / 12.0,
        "completions_per_open_hour": comp / 12.0,
        "median_service_min": med,
        "p90_service_min": p90,
        "mean_wip": wip,
        "staff_fte": staff,
        "complex_pct": df["complex_pct"].mean(),
        "peak_pct": df["peak_08_10_pct"].mean(),
        "net_arr_minus_comp": df["net_arr_minus_comp"].mean(),
        "wip_per_fte": wip / staff if staff else np.nan,
        "pressure_median": arr * med / (staff * OPEN_MIN) if staff else np.nan,
        "pressure_p90": arr * p90 / (staff * OPEN_MIN) if staff else np.nan,
    })

def dispersion(vec):

    m = x.mean()
    v = x.var(ddof=0)

        "mean": m,
        "var": v,
        "fano": v / m if m > 0 else np.nan,
        "cv": np.sqrt(v) / m if m > 0 else np.nan,
    }

# 6. Simple serial-dependence indicators for daily sequences.
#    These are descriptive only; daily rows are not independent.
# ----------------------------------------------------------------------------
def autocorr(x, lag=1):
    x = np.asarray(x, dtype=float)
    if len(x) <= lag:
        return np.nan
    xm = x - x.mean()
    denom = np.sum(xm ** 2)
    if denom == 0:
        return np.nan
    return np.sum(xm[:-lag] * xm[lag:]) / denom

serial_rows = []
for c in ["arrivals", "completed", "mean_wip", "complex_pct", "staff_fte"]:
    serial_rows.append({
        "variable": c,
        "lag1_autocorr": autocorr(daily[c].values, 1),
        "lag7_autocorr": autocorr(daily[c].values, 7),
    })

# ----------------------------------------------------------------------------
# 7. Transparent single change-point heuristic.
#    For each variable, choose the split that minimizes within-segment SSE.
#    This is a heuristic, not ground truth, and it favors mean shifts over
#    one-day anomalies.
# ----------------------------------------------------------------------------
def best_single_changepoint(dates, values, min_seg=3):
    x = np.asarray(values, dtype=float)
    n = len(x)
    full_sse = float(np.sum((x - x.mean()) ** 2))

    best = {
        "split_after_date": None,
        "left_mean": np.nan,
        "right_mean": np.nan,
        "sse_reduction_pct": 0.0,
    }
    best_sse = full_sse

    for k in range(min_seg, n - min_seg):
        left = x[:k]
        right = x[k:]
        sse = np.sum((left - left.mean()) ** 2) + np.sum((right - right.mean()) ** 2)

        if sse < best_sse:
            best_sse = sse
            split_date = dates.iloc[k - 1]
            best = {
                "split_after_date": str(split_date.date()) if hasattr(split_date, "date") else str(split_date),
                "left_mean": left.mean(),
                "right_mean": right.mean(),
                "sse_reduction_pct": (
                    100.0 * (full_sse - sse) / full_sse if full_sse > 0 else 0.0
                ),
            }

    return best

cp_rows = []
for c in ["arrivals", "completed", "mean_wip", "complex_pct", "staff_fte", "peak_08_10_pct"]:
    cp = best_single_changepoint(daily["date"], daily[c])
    cp["variable"] = c
    cp_rows.append(cp)

]
print("\nSingle change-point heuristic, not definitive ground truth")
print(cp.round(2).to_string(index=False))

# 8. Little's Law diagnostics for explicitly chosen windows.
#    These are opening-hour estimates using completions as throughput proxy.
#    They are not substitutes for event-level flow-time measurement.
# ----------------------------------------------------------------------------
def little_window(df, label, throughput_col="completed"):
    L = df["mean_wip"].mean()
    throughput_day = df[throughput_col].mean()
    throughput_hour = throughput_day / 12.0
    W_hour = L / throughput_hour if throughput_hour > 0 else np.nan

    return pd.Series({
        "window": label,
        "n_days": len(df),
        "L_mean_wip": L,
        "throughput_cases_per_day": throughput_day,
        "throughput_cases_per_open_hour": throughput_hour,
        "implied_flow_time_hours": W_hour,
        "implied_flow_time_min": W_hour * 60.0,
        "net_change_per_day": df["net_arr_minus_comp"].mean(),
        "throughput_proxy": throughput_col,
    })

windows = [
    ("baseline_weekday", daily["primary_regime"] == "1_baseline_weekday", "completed"),
    ("baseline_weekend_pre", daily["primary_regime"] == "2_baseline_weekend_pre", "completed"),
    ("post_outage_recovery_weekday", daily["primary_regime"] == "4_post_outage_recovery_weekday", "completed"),
    ("high_complex_weekday_pre", daily["primary_regime"] == "5_high_complex_weekday_pre", "completed"),
    ("intervention_recovery_weekday", daily["primary_regime"] == "7_intervention_recovery_weekday", "completed"),
    ("all_days_diagnostic", pd.Series(True, index=daily.index), "completed"),
]

little_rows = []
for label, mask, throughput_col in windows:
    little_rows.append(little_window(daily[mask], label, throughput_col))

little = pd.DataFrame(little_rows)

verdict_map = {
    "baseline_weekday": "approximate only",
    "baseline_weekend_pre": "approximate only",
    "post_outage_recovery_weekday": "approximate only, finite-horizon recovery",
    "high_complex_weekday_pre": "not defensible as steady state",
    "intervention_recovery_weekday": "approximate only, finite-horizon recovery",
    "all_days_diagnostic": "not defensible as single stationary regime",
}
little["verdict"] = little["window"].map(verdict_map)

print("\nLittle's Law diagnostics for explicit windows")
print(little.round(2).to_string(index=False))
```
