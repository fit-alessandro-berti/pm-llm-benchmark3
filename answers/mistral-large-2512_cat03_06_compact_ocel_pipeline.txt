# OCEL 2.0 Construction and Analysis Pipeline

## 1. Modeling assumptions

**Object types and capitalization:**
- `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment` (PascalCase for types, uppercase IDs)

**E2O qualifier vocabulary:**
- `created_for` (Order creation)
- `contains` (OrderItem)
- `reserved_for` (Stock reservation)
- `packed_in` (ItemPackage)
- `dispatched_in` (PackageDelivery)
- `billed_by` (OrderInvoice)
- `partially_settles` (PaymentInvoice)
- `completes_settlement` (PaymentInvoice when full)
- `confirmed_for` (Delivery confirmation)
- `closed_for` (Order closure)

**O2O direction conventions:**
- Left-to-right: sourcetarget (e.g., OrderItem means "Order contains Item")
- Qualifiers describe the relationship from left to right

**Logistics and financial event relations:**
- Logistics events (reserve, pack, dispatch, confirm) relate directly to Orders and Items they operationally affect
- Financial events (issue invoice, record payment) relate directly to Orders and Invoices
- This balances source-system fidelity with analytical utility

**Preventing analytical propagation confusion:**
- Direct E2O relations represent actual system observations
- O2O relations represent static business relationships
- Analytical propagation (e.g., "this Package event affects Order O100") is derived during discovery, not stored

**PM4Py version assumption:**
- Using PM4Py 2.7.x with OCEL 2.0 support
- If using older versions, would need to adjust constructor call to `OCEL(events=events, objects=objects, relations=relations, o2o=o2o, parameters={"debug": False})`

## 3. Data-model audit

**Object types and their objects:**
| Object Type | Objects               |
|-------------|-----------------------|
| Order       | O100, O200            |
| Item        | I1, I2, I3            |
| Package     | P1, P2                |
| Delivery    | D1, D2                |
| Invoice     | V1                    |
| Payment     | M1, M2                |

**O2O qualifiers and cardinality:**
| Qualifier               | Count |
|-------------------------|-------|
| contains                | 3     |
| packs                   | 3     |
| carries                 | 2     |
| bills                   | 2     |
| partially_settles       | 1     |
| completes_settlement    | 1     |

**Activities and touched object types:**
| Activity            | Object Types Touched                     |
|---------------------|-------------------------------------------|
| Create Order        | Order                                     |
| Add Item            | Order, Item                               |
| Reserve Stock       | Order, Item                               |
| Pack Package        | Package, Order, Item                      |
| Dispatch Package    | Delivery, Package, Order                  |
| Issue Invoice       | Invoice, Order                            |
| Record Payment      | Payment, Invoice                          |
| Confirm Delivery    | Delivery, Order                           |
| Close Order         | Order                                     |

**Consequential events for convergence/divergence:**
- **e6 (Reserve Stock)**: First event affecting multiple orders (O100, O200) and items (I1, I3)
- **e7 (Pack Package P1)**: Combines items from two orders (I1 from O100, I3 from O200)
- **e11 (Issue Invoice V1)**: Bills both orders together
- **e12/e15 (Record Payments)**: Partial payments settling the same invoice

## 4. Expected flattened behavior

**Order flattening:**
- *Trace shape*: 2 traces (O100, O200) with 9-10 events each
- *Copied shared events*: Reserve Stock, Pack Package P1, Dispatch P1, Issue Invoice, Confirm Delivery D1
- *Omitted aspects*: Package and Delivery lifecycles not fully visible
- *Likely DFG edges*: Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Confirm Delivery  Close Order
- *Misleading interpretations*: May suggest independent order processing when packages actually combine items

**Package flattening:**
- *Trace shape*: 2 traces (P1, P2) with 3-4 events each
- *Copied shared events*: Pack Package (shared for P1 across orders)
- *Omitted aspects*: Order and Item details not fully visible
- *Likely DFG edges*: Pack Package  Dispatch Package  Confirm Delivery
- *Misleading interpretations*: May hide that P1 contains items from two orders

**Delivery flattening:**
- *Trace shape*: 2 traces (D1, D2) with 2 events each
- *Copied shared events*: None (each delivery is unique)
- *Omitted aspects*: Package contents and order relationships
- *Likely DFG edges*: Dispatch Package  Confirm Delivery
- *Misleading interpretations*: May suggest deliveries are independent when they serve the same invoice

**Invoice flattening:**
- *Trace shape*: 1 trace (V1) with 3 events
- *Copied shared events*: Issue Invoice (shared across orders)
- *Omitted aspects*: Order and payment details not fully visible
- *Likely DFG edges*: Issue Invoice  Record Payment (M1)  Record Payment (M2)
- *Misleading interpretations*: May hide that the invoice bills two orders

**Why Payment flattening would be weak:**
- Only 2 payment objects (M1, M2) with 1 event each
- No lifecycle beyond creation
- Would produce extremely short traces (1 event each)
- No meaningful process behavior to discover
- Would hide the relationship to the invoice and orders

## 5. Expected object-centric structures

**OC-DFG:**
- Should show convergence at:
  - Pack Package (P1 combines I1 from O100 and I3 from O200)
  - Issue Invoice (V1 bills both O100 and O200)
  - Record Payment (M1 and M2 both settle V1)
- Should show divergence at:
  - Dispatch Package (P1D1, P2D2)
  - Confirm Delivery (D1 and D2 confirm at different times)
- P1 should appear as a convergence point between O100 and O200

**OTG (Object Type Graph):**
- Should show strong connections:
  - Order  Item (contains)
  - Order  Invoice (billed_by)
  - Invoice  Payment (settles)
  - Package  Item (packs)
  - Delivery  Package (carries)
- Should show that Order connects to both Package and Delivery indirectly

**ET–OT (Event Type - Object Type):**
- Should show:
  - Reserve Stock affects both Order and Item
  - Pack Package affects Package, Order, and Item
  - Issue Invoice affects Invoice and Order
  - Record Payment affects Payment and Invoice
- Should reveal that most events touch multiple object types

**Object-centric Petri net:**
- Should model:
  - Parallel paths for O100 and O200 until Pack Package P1
  - Synchronization at Invoice creation
  - Payment settlement as a separate branch
  - Delivery confirmation as parallel paths
- P1 should appear as a place where O100 and O200 converge
- V1 should appear as a synchronization point for payments

**Object-interactions summary:**
- Should show:
  - O100 interacts with I1, I2, P1, P2, D1, D2, V1
  - O200 interacts with I3, P1, D1, V1
  - P1 interacts with I1, I3, D1, O100, O200
  - V1 interacts with O100, O200, M1, M2
- Should reveal that P1 is the most "connected" object (5 interactions)
- Should show that M1 and M2 only interact with V1

## 6. Modeling alternatives

**1. Source-minimal relations:**
- Only relate events to objects they directly create or modify
- Example: Pack Package would only relate to Package (not Order or Item)
- *Effect*: Would require analytical propagation to understand full impact
- *Discovery impact*: OC-DFG would show less convergence, OTG would be sparser
- *Business story*: Still accurate but less immediately interpretable

**2. Full operational involvement:**
- Relate every event to all objects it could possibly affect
- Example: Confirm Delivery would relate to Delivery, Package, Item, Order, Invoice
- *Effect*: Would create very dense relations
- *Discovery impact*: OC-DFG would show more edges, potentially obscuring true convergence
- *Business story*: Accurate but may suggest more synchronization than actually exists

**3. O2O-propagated analytical relations:**
- Store only direct relations, derive others via O2O
- Example: Pack Package relates to Package and Item, but Order relation is derived via ItemOrder
- *Effect*: Would reduce stored relations but increase discovery computation
- *Discovery impact*: Similar to current approach but with different performance characteristics
- *Business story*: Equivalent but may have different edge weights in discovery

## 7. Failure modes

**1. Relation inflation:**
- Adding too many E2O relations, making the model overly complex
- Example: Relating every event to every object type it might affect
- *Consequence*: Discovery algorithms may produce cluttered, hard-to-interpret results

**2. Missing direct E2O links:**
- Omitting important direct relationships
- Example: Not relating Pack Package to Orders
- *Consequence*: Would require analytical propagation, potentially missing important insights

**3. Treating O2O propagation as observation:**
- Using O2O relations to infer E2O relationships that weren't actually observed
- Example: Assuming Pack Package affects Order because ItemOrder exists
- *Consequence*: May create false convergence in discovery results

**4. Duplicate shared events after flattening:**
- Shared events appearing multiple times in flattened logs
- Example: Reserve Stock appearing in both O100 and O200 traces
- *Consequence*: May inflate frequency counts and create false process patterns

**5. Ambiguous payment allocation:**
- Not clearly modeling which payments settle which invoices
- Example: Not using qualifiers like "partially_settles"
- *Consequence*: Would make it impossible to analyze payment patterns

**6. Overly short Payment traces:**
- Modeling payments as single-event objects
- Example: Only recording payment creation, not lifecycle
- *Consequence*: Would make payment analysis nearly impossible

**7. Constructor/API version mismatch:**
- Using incompatible PM4Py versions with different OCEL constructors
- Example: Using PM4Py 2.2.x with OCEL 2.0 data
- *Consequence*: Would fail to construct the OCEL or produce incorrect results

**8. False total order for same-time events:**
- While this example has no timestamp ties, in general:
- Not handling events with identical timestamps properly
- Example: Two events at 08:30:00 with no defined order
- *Consequence*: Discovery algorithms might impose arbitrary ordering

## 8. Final semantic checks

**1. Order-Item containment:**
- Verify that O2O contains exactly:
  - O100I1, O100I2, O200I3 (contains)
- And that relations show Add Item events for each

**2. Package-Item packing:**
- Verify that O2O contains exactly:
  - P1I1, P1I3, P2I2 (packs)
- And that Pack Package events relate to the correct packages and items

**3. Delivery-Package carrying:**
- Verify that O2O contains exactly:
  - D1P1, D2P2 (carries)
- And that Dispatch Package events relate to the correct deliveries and packages

**4. Invoice-Order billing:**
- Verify that O2O contains exactly:
  - V1O100, V1O200 (bills)
- And that Issue Invoice relates to V1, O100, and O200

**5. Payment-Invoice settlement:**
- Verify that O2O contains:
  - M1V1 (partially_settles)
  - M2V1 (completes_settlement)
- And that Record Payment events relate to the correct payments and invoice

**6. Shared events:**
- Verify that Reserve Stock (e6) relates to both O100 and O200
- Verify that Pack Package P1 (e7) relates to both O100 and O200
- Verify that Issue Invoice (e11) relates to both O100 and O200
- Verify that Confirm Delivery D1 (e13) relates to both O100 and O200
