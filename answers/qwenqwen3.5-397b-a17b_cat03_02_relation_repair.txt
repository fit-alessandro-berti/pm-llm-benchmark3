## 1. Consistency rules and evidence model

To evaluate potential repairs, I establish a hierarchy of reliability for the available evidence. These rules guide the assignment of confidence scores and the construction of repair bundles.

**Hard Invariants**
1.  **Referential Integrity:** An event cannot relate to an object ID that does not exist in the object table.
2.  **Temporal Order:** An object cannot be related to an event occurring before the object's creation event (e.g., an Item cannot be packed before it is added to an order).
3.  **Unique Identifiers:** If an external reference (e.g., `carrier_ref`) matches exactly between an event attribute and an object attribute, this is treated as a definitive link unless contradicted by timestamp impossibility.

**Strong Defaults**
1.  **Arithmetic Consistency:** If an Invoice total equals the sum of Order declared values exactly (230 = 130 + 100), this is strong evidence of a billing relation, though taxes or discounts could theoretically alter this.
2.  **Identifier Prefixes:** Scanner references (e.g., `PK8-1`, `PK8-2`) sharing a package ID prefix imply relation to that package, even if the object ID is missing in the relation table.
3.  **Payment Settlement:** Payments typically settle Invoices rather than Orders directly when an Invoice object exists in the lifecycle.

**Weak Heuristics**
1.  **Customer Context:** Events referencing a customer (e.g., `portal_customer=C17`) likely relate to all active orders for that customer at that time, but this is not guaranteed (partial deliveries exist).
2.  **Route Matching:** Packages and Deliveries sharing a route hint (e.g., `NORTH`) are likely related, but multiple deliveries can share a route.
3.  **Lifecycle Completion:** While desirable, completeness is not proof. An object lacking a downstream relation (e.g., Order without Invoice) may represent a cancelled or pending state.

**Evidence Against a Repair**
1.  **Cardinality Violations:** If a Package is already marked as "sealed" or "dispatched" in the lifecycle, adding new Items to it violates physical constraints.
2.  **Contradictory Attributes:** If a Payment amount exceeds the Invoice total without evidence of overpayment, the relation is suspect.
3.  **Temporal Gaps:** If a Delivery confirmation occurs before the Dispatch event, the relation is invalid.

**Combination Strategy**
I combine identifier similarity (exact match > prefix match), temporal proximity (events within minutes are likely related), and amount matching (exact sum > approximate) to weigh repairs. Existing O2O structure is treated as ground truth unless it contradicts event data (e.g., if an event says `PK-8` packed `IT-B1` but O2O says `PK-7` packs `IT-B1`, the event takes precedence as the operational record). I avoid circular reasoning by not inferring an O2O relation solely because an E2O relation was hypothesized; each requires independent justification (e.g., scanner ID for O2O, event log for E2O).

2.  **Invoice Attribution Error:** Assuming `INV-44` bills `ORD-B` (P05) based on arithmetic ignores potential fees. If `ORD-B` was invoiced separately but lost, linking it here merges two financial processes, skewing revenue-per-order metrics.
3.  **Delivery Confirmation Bias:** Linking `ev11` to `DEL-Y` (Bundle B) assumes simultaneous delivery. If `DEL-Y` was delayed, this repair hides the delay in the process model, making delivery performance appear better than it was.
4.  **Payment Misallocation:** Linking `PAY-2` to `INV-44` (P07) assumes partial payment logic. If `PAY-2` was actually a refund or a payment for a different invoice (e.g., previous month), this repair incorrectly closes the financial lifecycle of `INV-44`.
5.  **Event Duplication in Flattening:** If `ev12` (Issue Invoice) is linked to both ORD-A and ORD-B, flattening on Order will duplicate the `Issue Invoice` event in the event log. This inflates the frequency of invoicing activities when analyzing Order cases, potentially suggesting bottlenecks that do not exist.
