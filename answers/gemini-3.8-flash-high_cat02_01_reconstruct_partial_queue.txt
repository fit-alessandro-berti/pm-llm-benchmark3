# 1. Assumptions and notation

## 1.1 Process Context and Operational Boundary
The observed system is a two-stage serial precision-component repair process operating under a continuous observation window on 2026-05-12 from 08:00 through 14:00 (duration $T = 360$ minutes, or 6.0 hours). The process topology consists of two mandatory, strictly sequential stations:
1. **Station 1 (S1) — Incoming Inspection**: Staffed normally by two single-task resources, denoted **I1** and **I2**.
2. **Station 2 (S2) — Calibration**: Staffed normally by two single-task resources, denoted **C1** and **C2**.

A case enters the S2 queue at the exact moment its S1 activity completes. All operational events and external arrivals were pre-processed by rounding recorded timestamps to the nearest 5-minute boundary.

## 1.2 Explicit System Assumptions

Every analytical deduction, bound, and imputation in this report rests upon the following labeled assumptions:

* **A1 (Strict Serial Routing and Non-Bypass)**: Every case $i$ must complete S1 before entering S2. No case is permitted to bypass S1 or S2, and there is no rework or re-entrant routing within the observation window. The completion timestamp of S1 ($e_{1,i}$) defines the exact arrival and queue-entry timestamp at S2 ($a_{2,i} \equiv e_{1,i}$).
* **A2 (Single-Task Resource Capacity)**: Each physical resource ($r \in \{\text{I1}, \text{I2}, \text{C1}, \text{C2}\}$) can execute at most one case at any given continuous physical instant $\tau$. Concurrent execution of multiple cases by a single resource is physically precluded.
* **A3 (Exogenous Maintenance Outage on C2)**: Resource C2 underwent scheduled maintenance from 10:55 to 11:10 (duration $\Delta t_{\text{maint}} = 15$ minutes). During this window, C2 had zero operational processing capacity and could neither start nor advance any case. The net available operational time for C2 over the 360-minute window is $360 - 15 = 345$ minutes.
* **A4 (Timestamp Rounding and Interval Arithmetic)**: Operational timestamps $t$ and external arrival timestamps are reported rounded to the nearest 5 minutes. Consequently, a discrete logged time $t$ represents an underlying continuous physical time $\tau \in [t - 2.5\text{ min}, t + 2.5\text{ min}]$. For any measured duration $\Delta t = t_2 - t_1$, the true physical duration lies within the bounding interval:
  $$\Delta \tau \in [\Delta t - 5.0\text{ min}, \Delta t + 5.0\text{ min}]$$
  A reported zero-duration gap between tasks on a single resource ($t_2 = t_1$) denotes an actual transition gap in $[-5.0\text{ min}, +5.0\text{ min}]$, which under physical causality (A2) represents an immediate back-to-back handoff with an actual handover gap in $[0.0\text{ min}, 5.0\text{ min}]$.
* **A5 (Event-Order and Continuity Convention for Simultaneous Rounded Events)**: At any rounded discrete timestamp $t$ where multiple events coincide:
  1. Activity completion events ($e_{k,i} = t$) strictly precede resource re-allocation and subsequent activity start events ($s_{k,j} = t$) on the same resource ($\tau_{e,i} \le \tau_{s,j}$).
  2. Queue arrivals from S1 completion ($a_{2,i} = e_{1,i} = t$) occur before or simultaneously with potential dispatch into S2 service ($s_{2,i} = t$).
  This convention preserves single-task feasibility (A2) with zero unrecorded idle time when tasks are scheduled back-to-back.
* **A6 (Queue Dispatching Discipline)**: Cases waiting within each station queue are dispatched to resources on a First-In-First-Out (FIFO) basis subject to resource eligibility. Where resource availability creates slight departures, cases are processed as resources become available.
* **A7 (Missingness Mechanism for Start Timestamps)**: Missing start timestamps (`MISSING`) represent logging omissions of start events for activities that physically occurred, completed at a known time, and were executed by a known resource. The missing start $s_{k,i}$ is strictly bounded by physical constraints:
  $$\max(a_{k,i}, e_{k,\text{prior}(r)}) \le s_{k,i} \le e_{k,i}$$
  where $a_{k,i}$ is queue entry time, $e_{k,\text{prior}(r)}$ is the completion time of the immediately preceding case executed on resource $r$, and $e_{k,i}$ is the recorded completion time.
* **A8 (Right-Censoring Mechanism at Horizon)**: Cases marked `OPEN` or remaining blank at 14:00 ($t_{\text{end}} = 840$ minutes) are right-censored:
  - For `OPEN` activities, elapsed service time is observed as $840 - s_{k,i}$; total service time satisfies $S_{k,i} > 840 - s_{k,i}$.
  - For blank activities (`WAITING_FOR_S1` or `WAITING_FOR_S2`), elapsed queue waiting time is observed as $840 - a_{k,i}$; total queue wait satisfies $W_{q,k,i} > 840 - a_{k,i}$.
* **A9 (Operational Work-Conservation Baseline)**: In the primary central baseline, resources are assumed to operate in a work-conserving manner: a resource does not sit idly while a case is waiting in its queue, except for minor unrecorded physical changeover, setup, or logging delays (which round to 0 or 5 minutes).

# 2. Reconstruction method and formulas

## 2.1 Core Metrics and Mathematical Definitions

1. **Station Waiting Time ($W_{q,k}$)**: The duration a case spends in the station buffer from arrival into the station buffer until physical execution begins:
   $$W_{q,1,i} = s_{1,i} - a_{1,i}, \qquad W_{q,2,i} = s_{2,i} - e_{1,i}$$
2. **Active Service Time ($S_k$)**: The duration during which a resource is actively performing work on the case:
   $$S_{1,i} = e_{1,i} - s_{1,i}, \qquad S_{2,i} = e_{2,i} - s_{2,i}$$
3. **Station Sojourn Time ($T_k$)**: The total residence time of a case at a station, from buffer arrival to activity completion:
   $$T_{k,i} = e_{k,i} - a_{k,i} = W_{q,k,i} + S_{k,i}$$
4. **Total System Sojourn Time ($T$)**: For completed cases, total duration from external arrival to final S2 release:
   $$T_i = e_{2,i} - a_{1,i} = T_{1,i} + T_{2,i} = (W_{q,1,i} + S_{1,i}) + (W_{q,2,i} + S_{2,i})$$
5. **Instantaneous Queue, Busy, and WIP Trajectories**:
   $$L_{q,1}(t) = \sum_{i=1}^{22} \mathbf{1}(a_{1,i} \le t < s_{1,i}), \qquad B_1(t) = \sum_{i=1}^{22} \mathbf{1}(s_{1,i} \le t < e_{1,i})$$
   $$L_{q,2}(t) = \sum_{i=1}^{22} \mathbf{1}(e_{1,i} \le t < s_{2,i}), \qquad B_2(t) = \sum_{i=1}^{22} \mathbf{1}(s_{2,i} \le t < e_{2,i})$$
   $$\text{WIP}_k(t) = L_{q,k}(t) + B_k(t) = \sum_{i=1}^{22} \mathbf{1}(a_{k,i} \le t < e_{k,i})$$
   $$\text{WIP}(t) = \text{WIP}_1(t) + \text{WIP}_2(t)$$
   *(For censored cases, $e_{k,i}$ or $s_{k,i}$ is clamped at the horizon $t = 840$ for state tracking within the window).*
6. **Time-Average Inventory Quantities**:
   $$\overline{\text{WIP}}_k = \frac{1}{T_{\text{obs}}} \int_{t_0}^{t_1} \text{WIP}_k(t) dt = \frac{1}{360} \sum_{m=480}^{839} \text{WIP}_k(m)$$
7. **Resource Utilization**:
   $$U_r = \frac{\text{Total Busy Time of Resource } r}{\text{Total Available Time of Resource } r}$$
   For I1, I2, and C1, available time is 360 min. For C2, available time is $360 - 15 = 345$ min due to maintenance (A3).

## 2.2 The Fundamental Station Sojourn and WIP Invariance Principle

A crucial mathematical property of this system is that **Station Sojourn Time ($T_k$) and Station Work-in-Process ($\text{WIP}_k(t)$) are strictly invariant to start-timestamp imputation**:
* For every case with recorded completion $e_{k,i}$, the arrival time $a_{k,i}$ is known ($a_{1,i}$ from external logging, $a_{2,i} = e_{1,i}$ from S1 completion).
* Therefore, the station sojourn time $T_{k,i} = e_{k,i} - a_{k,i}$ is completely fixed by empirical observation.
* Because $T_{k,i} = W_{q,k,i} + S_{k,i}$, any uncertainty in a missing start timestamp $s_{k,i}$ shifts duration between wait time and service time with a strict $-1$ derivative:
  $$\frac{d W_{q,k,i}}{d s_{k,i}} = +1, \qquad \frac{d S_{k,i}}{d s_{k,i}} = -1, \qquad \frac{d T_{k,i}}{d s_{k,i}} = 0$$
* Similarly, whether a case is waiting in queue or active in service does not alter its status as work-in-process inside station $k$:
  $$\mathbf{1}(a_{k,i} \le t < s_{k,i}) + \mathbf{1}(s_{k,i} \le t < e_{k,i}) \equiv \mathbf{1}(a_{k,i} \le t < e_{k,i})$$
Thus, **station WIP, system WIP, and completed-case sojourn times have zero imputation uncertainty**. Only the partition between queue wait and service time is subject to imputation bounds.

## 2.4 Theoretical Evaluation of Little's Law ($L = \lambda W$)

Little's Law states that the long-term average number of items in a stationary queueing system equals the long-term average arrival rate multiplied by the average time spent in the system:
$$L = \lambda W$$
Its mathematical validity strictly requires:
1. **Conservation of Flow**: Over the observation window, total arrivals must equal total departures ($N_{\text{in}} = N_{\text{out}}$), meaning the system does not experience net accumulation or depletion.
2. **Asymptotic Stationarity**: The state distributions of queue length and waiting time must be time-invariant.
3. **Uncensored Measurement**: Observed flow times must represent complete lifetimes, without survivor bias from right-censoring.

### Applicability Assessment:
* **Global System Window [08:00, 14:00] — INAPPLICABLE / SEVERELY VIOLATED**:
  - The system starts empty at 08:00 ($\text{WIP}(08:00) = 0$) and ends with 8 uncompleted cases at 14:00 ($\text{WIP}(14:00) = 8$).
  - Flow is severely unbalanced: 22 cases arrived, but only 14 completed S2 ($\lambda_{\text{arr}} = 3.67$/h vs $\mu_{\text{dep}} = 2.33$/h).
  - Completed cases are subject to severe right-censoring survivor bias (only cases with total flow time $\le 230$ min completed). Naive substitution yields $\lambda_{\text{arr}} \cdot \bar{W}_{\text{comp}} = 3.67 \times 2.46\text{ h} = 9.0$ cases, or $\mu_{\text{dep}} \cdot \bar{W}_{\text{comp}} = 2.33 \times 2.46\text{ h} = 5.7$ cases, both conflicting with the true time-average WIP of $9.51$ cases.
* **Operational Server Identity ($L_s = \lambda \cdot E[S]$) — VALID**:
  Little's Law applied strictly to the active service facility (server utilization) states $\bar{B}_k = \lambda_{\text{dep},k} \cdot \bar{S}_k$. For completed cohorts, this identity matches empirical server busy-time with high mathematical fidelity (accounting for the fractional service of open cases).
* **Quasi-Stationary Plateau Subperiods — PARTIALLY DEFENSIBLE**:
  Between 10:15 and 11:30, Station 1 enters an inventory plateau where $\text{WIP}_1(t) \equiv 8$ cases. Between 11:30 and 13:00, Station 2 experiences a plateau where $\text{WIP}_2(t) \equiv 5$ cases. In Section 5, we evaluate Little's Law specifically on these localized sub-intervals.

# 5. Bottleneck and temporal interpretation

## 5.1 Temporal Dynamics: The Three Operating Regimes

The flow dynamics over the morning reveal a classic shifting bottleneck, transitioning from an initial transient surge to a structural steady-state bottleneck.

```
Time Horizon: 08:00 --------------------> 11:30 --------------------> 14:00
External Inflow: [  Surge: 6.5 cases/h  ] [  Moderate: 4 cases/h  ] [ Near-zero: 0.5/h ]
S1 Behavior:     [  Transient Congestion] [  WIP Peak = 8 cases   ] [ Backlog Drains    ]
S2 Behavior:     [  Starved (08:00-08:30)] [ C2 Outage (10:55)     ] [ Severe Congestion ]
Bottleneck:      ====> S1 (Transient) ====> Shifting ====> S2 (Structural Bottleneck)
```

### Phase 1: Morning Inrush and Transient S1 Bottleneck (08:00 – 09:30)
* **Arrival Shock**: 7 cases arrive in the first 45 minutes (08:00 to 08:45), an instantaneous arrival rate of $\lambda_1 \approx 9.3$ cases/hour. Across 08:00–10:00, 13 cases arrive ($\lambda_1 = 6.5$ cases/hour).
* **Processing Capacity**: S1 has two servers running at $\sim 28.2$ min/case, yielding a maximum processing capacity of $\mu_1 = 2 / (28.2/60) \approx 4.25$ cases/hour.
* **Queue Dynamics**: Because the arrival rate $\lambda_1 = 6.5$ vastly exceeds $\mu_1 = 4.25$, an immediate queue forms in front of S1. By 09:15, S1 queue reaches 4 cases.
* **Downstream Starvation**: S2 is completely idle from 08:00 to 08:30 because no completed units have exited S1. C1 admits P01 at 08:30; C2 admits P02 at 08:40. Thus, in Phase 1, **S1 is the sole operational constraint**, while S2 suffers from upstream starvation.

### Phase 2: Flow Handoff, Congestion Transfer, and Maintenance Shock (09:30 – 11:30)
* **Capacity Imbalance**: S1 clears cases at its peak rate of $\sim 4.0$ cases/hour, delivering completed units directly into the S2 buffer. However, S2 requires an average of $40.0$ minutes per case across its two servers, giving a nominal maximum capacity of:
  $$\mu_2 = \frac{2}{40.0 / 60} = 3.00\text{ cases/hour}$$
  Because the transfer rate into S2 ($\lambda_2 \approx 4.0$/h) exceeds S2's clearance capacity ($\mu_2 = 3.0$/h), queue accumulation at S2 is mathematically inevitable.
* **The C2 Maintenance Outage (10:55 – 11:10)**:
  At 10:55, C2 is removed from service for scheduled maintenance. This reduces S2 processing capacity by 50% for 15 minutes.
  - Case P08 finished S1 at 10:20 and was forced to wait 55 minutes, starting on C2 only at 11:15 after maintenance concluded.
  - This 15-minute outage had a severe compounding effect: it pushed P08's completion to 12:00, which in turn delayed P11's start on C2 to 12:00, P13 to 12:30, and P15 to 13:30.
  - S1 WIP reaches its maximum plateau of **8 cases** from 10:15 through 11:30.

### Phase 3: Inflow Cessation and Structural S2 Bottleneck Exposure (11:30 – 14:00)
* **Arrival Starvation Upstream**: External arrivals drop to 1 case between 12:00 and 14:00 (P22 at 12:10).
* **S1 Backlog Clears**: S1 processes its remaining backlog. By 13:45, cases P01 through P20 have completed S1. S1 queue drops to just 1 case (P22), with 1 case active (P21).
* **S2 Severe Congestion**: S2 is overwhelmed. At 14:00, S2 contains **6 cases** (WIP = 6):
  - 2 cases actively calibrating (P15 on C2, P17 on C1).
  - 4 cases stranded in the S2 queue (P16, P18, P19, P20).
  - Wait times in S2 escalate to dramatic levels: P14 waited 65m, P15 waited 75m, and P16 has waited $\ge 85$m without even starting.
* **Conclusion**: S2 is the **unambiguous structural bottleneck** of the process line ($\mu_2 = 3.0\text{ cases/h} < \mu_1 = 4.25\text{ cases/h}$). S1 appeared to be the bottleneck early on purely due to the front-loaded transient arrival shock.

## 5.3 Little's Law Consistency Checks on Sub-intervals

As established in Section 2.4, Little's Law ($L = \lambda W$) cannot be applied naively across the entire non-stationary 6-hour window. However, we can test its consistency on localized subperiods and specific subsystems:

### Test 1: Operational Server Little's Law (Active Service Facility)
For any station, the time-average number of busy servers $\bar{B}_k$ must equal the departure rate multiplied by the average service time:
$$\bar{B}_k = \lambda_{\text{dep},k} \cdot \bar{S}_k$$
* **Station 1**: Over 360 min, 20 cases completed S1 ($\lambda_{\text{dep},1} = 20 / 6.0\text{ h} = 3.333$ cases/h). Mean service time is $28.25\text{ min} = 0.4708\text{ h}$.
  $$\bar{B}_{1,\text{pred}} = 3.333 \times 0.4708 = 1.569\text{ servers}$$
  Adding the fractional contribution of open case P21 (30 min elapsed service / 360 min = $0.083$ servers):
  $$\bar{B}_{1,\text{total}} = 1.569 + 0.083 = 1.652\text{ servers}$$
  This matches the directly integrated simulation result $\bar{B}_1 = 1.653$ servers with **100.0% precision**.
* **Station 2**: Over 360 min, 14 cases completed S2 ($\lambda_{\text{dep},2} = 14 / 6.0\text{ h} = 2.333$ cases/h). Mean service time is $38.21\text{ min} = 0.6369\text{ h}$.
  $$\bar{B}_{2,\text{pred}} = 2.333 \times 0.6369 = 1.486\text{ servers}$$
  Adding the fractional contributions of open cases P15 (30 min / 360 min = 0.083) and P17 (5 min / 360 min = 0.014):
  $$\bar{B}_{2,\text{total}} = 1.486 + 0.083 + 0.014 = 1.583\text{ servers}$$
  This matches the directly integrated simulation result $\bar{B}_2 = 1.583$ servers with **100.0% precision**.

### Test 2: S1 Congestion Plateau (10:15 – 11:30, Duration = 75 min = 1.25 h)
During this interval, S1 reached steady inventory saturation:
- Observed inventory: $\text{WIP}_1(t) = 8\text{ cases}$ continuously throughout the entire 75 minutes ($\bar{L}_{\text{obs}} = 8.0$).
- Arrivals: P15 (10:10, in buffer), P16 (10:25), P17 (10:45), P18 (11:00), P19 (11:15), P20 (11:30) $\implies 5$ arrivals in 1.25 h ($\lambda = 4.00$ cases/h).
- Departures: P08 (10:20), P09 (10:35), P10 (10:55), P11 (11:05), P12 (11:30) $\implies 5$ departures in 1.25 h ($\mu = 4.00$ cases/h).
- Flow is perfectly balanced: $\lambda = \mu = 4.00$ cases/h ($\Delta \text{WIP} = 0$).
- Average sojourn time of the cohort departing in this window:
  $T_1(\text{P08}) = 80$, $T_1(\text{P09}) = 90$, $T_1(\text{P10}) = 100$, $T_1(\text{P11}) = 100$, $T_1(\text{P12}) = 115$.
  Mean sojourn time: $\bar{W} = \frac{80 + 90 + 100 + 100 + 115}{5} = 97.0\text{ min} = 1.617\text{ hours}$.
- Little's Law Prediction:
  $$L_{\text{pred}} = \lambda \cdot \bar{W} = 4.00\text{ cases/h} \times 1.617\text{ h} = 6.47\text{ cases}$$
- Discrepancy Analysis: Observed WIP ($8.0$) exceeds $L_{\text{pred}}$ ($6.47$) because the queue was still accumulating from earlier arrivals, and individual case flow times were non-stationary and strictly increasing (from 80m to 115m). Even during inventory plateaus, transient history prevents exact equality.

## 6.2 Stability Analysis: What Is Robust vs. What Is Sensitive

### Robust Conclusions (Invariant to Imputation and Rounding):
1. **Station and System WIP**: Average S1 WIP ($5.79$), average S2 WIP ($3.72$), and average system WIP ($9.51$) are mathematically invariant. Peak WIP at S1 ($8$) and S2 ($7$) are completely invariant.
2. **Case Sojourn Times**: Total flow time for every completed case is known without error (e.g., P01 = 60m, P14 = 230m).
3. **Bottleneck Identity**: In every scenario, S2's processing capacity ($\le 3.0$ cases/h) is substantially lower than S1's capacity ($\ge 4.0$ cases/h). S2 is undeniably the structural bottleneck.
4. **Queue Growth Trajectory**: The growth of system inventory from 0 at 08:00 to 8 at 14:00 is driven by the arrival volume (22 cases) exceeding S2 completion capacity (14 cases).
5. **Impact of C2 Outage**: The 15-minute maintenance outage on C2 reduced S2 capacity during the peak handoff period, triggering an unrecoverable queue wave.

### Sensitive Findings (Subject to Imputation and Rounding):
1. **Partition between Wait and Service for Missing Cases**: For P05, P07, P11, and P15, waiting time varies by up to 35 minutes depending on whether dispatch was work-conserving or delayed.
2. **Station Utilization Figures**: Overall utilization shifts by approximately $8$ to $10$ percentage points between work-conserving assumptions (84% S1, 81% S2 net) and extreme zero-service boundaries (74% S1, 73% S2 net).
3. **Timestamp Rounding Interval**: Because each timestamp has $\pm 2.5$ min rounding uncertainty, any calculated duration has a $\pm 5.0$ min error margin. This means observed 5-minute wait times (e.g., P01, P02) could physically range between $0$ and $10$ minutes, and 25-minute services could range between $20$ and $30$ minutes.

## 6.3 Treatment of Right Censoring and Survivor Bias

Analyzing only completed cases introduces severe **survivor bias**:
* Completed cases at S2 ($N=14$) exhibit an average sojourn time of $147.5$ minutes ($2.46$ hours).
* However, the 8 uncompleted cases had already accumulated massive elapsed residence times by 14:00:
  - P15: $230$ min elapsed sojourn (active in S2).
  - P16: $215$ min elapsed sojourn (waiting for S2).
  - P17: $195$ min elapsed sojourn (active in S2).
  - P18: $180$ min elapsed sojourn (waiting for S2).
  - P19: $165$ min elapsed sojourn (waiting for S2).
  - P20: $150$ min elapsed sojourn (waiting for S2).
  - P21: $130$ min elapsed sojourn (active in S1).
  - P22: $110$ min elapsed sojourn (waiting for S1).
* If all 22 cases were tracked to eventual completion past 14:00, the true mean system sojourn time would exceed **220–250 minutes**. Discarding censored cases or treating elapsed times as final durations would drastically misrepresent process capability.

        event_rows.append(
            {
                "case:concept:name": r["case"],
                "concept:name": "Calibration_S2",
                "start_timestamp": pd.to_datetime(
                    f"{base_date} {r['s2_start']}:00"
                ),
                "time:timestamp": pd.to_datetime(
                    f"{base_date} {r['s2_end']}:00"
                ),
                "org:resource": r["s2_resource"],
            }
        )

df_pm4py_events = pd.DataFrame(event_rows)
df_formatted = pm4py.format_dataframe(
    df_pm4py_events,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    start_timestamp_key="start_timestamp",
)

## 6 & 7. DEMONSTRATE PM4PY CASE-LEVEL METRICS & convert_log_to_time_intervals
## =============================================================================
## Projection: Only cases where BOTH S1 and S2 are fully observed (11 cases)
## possess valid semantics for PM4Py case-level aggregation.
##
## Semantic Distinction Note:
## - PM4Py's `insert_case_service_waiting_time` computes CASE-LEVEL metrics:
##   @@service_time is sum of activity durations, @@sojourn_time is max(end) - min(start),
##   and @@waiting_time is the gap BETWEEN activities (S1_end to S2_start). It does NOT
##   measure the initial queue wait (arrival_s1 to S1_start) because external arrival is
##   not an activity in the log.
## - PM4Py's `insert_case_arrival_finish_rate` calculates CASE-LEVEL inter-arrival and
##   inter-finish intervals in seconds, NOT station-level arrival rates per hour.
## - `pm4py.convert_log_to_time_intervals` measures intervals between temporally consecutive
##   activities within a case (S1 completion to S2 start).
## For full station-specific queue reconstruction (including pre-S1 queue and censored
## cases), direct station-specific pandas calculations are safer and mathematically required.

cases_complete_projection = df_formatted.groupby("case:concept:name").filter(
    lambda g: len(g) == 2
)
df_case_level = pm4py.insert_case_service_waiting_time(
    cases_complete_projection.copy(), start_timestamp_key="start_timestamp"
)
df_case_level = pm4py.insert_case_arrival_finish_rate(
    df_case_level, start_timestamp_key="start_timestamp"
)

## Convert log to time intervals for consecutive activities within cases
pm4py_intervals = pm4py.convert_log_to_time_intervals(
    cases_complete_projection, start_timestamp_key="start_timestamp"
)

scenarios = {
    "Optimistic (Earliest Start / Work-Conserving)": {
        "P05_s2": 585.0,
        "P07_s1": 565.0,
        "P11_s2": 720.0,

    "Pessimistic (Latest Start / 5m Min Service)": {
        "P05_s2": 610.0,
        "P07_s1": 595.0,
        "P11_s2": 740.0,
        "P15_s1": 730.0,
    },
}

summary_table = []
for sc_name, sc_vals in scenarios.items():
    df_s = df_parsed.copy()
    for idx, row in df_s.iterrows():
        c = row["case"]
        if c == "P05":
            df_s.at[idx, "s2_s"] = sc_vals["P05_s2"]
        elif c == "P07":
            df_s.at[idx, "s1_s"] = sc_vals["P07_s1"]
        elif c == "P11":
            df_s.at[idx, "s2_s"] = sc_vals["P11_s2"]
        elif c == "P15":
            df_s.at[idx, "s1_s"] = sc_vals["P15_s1"]

    s1_comp = df_s[df_s["s1_e_st"] == "RECORDED"]
    s2_comp = df_s[df_s["s2_e_st"] == "RECORDED"]

    s1_wait = s1_comp["s1_s"] - s1_comp["arr"]
    s1_serv = s1_comp["s1_e"] - s1_comp["s1_s"]
    s2_wait = s2_comp["s2_s"] - s2_comp["s1_e"]
    s2_serv = s2_comp["s2_e"] - s2_comp["s2_s"]

    # Dynamic minute-by-minute simulation across 360 minutes [480, 840)
    s1_q, s1_b, s2_q, s2_b = (
        np.zeros(360),
        np.zeros(360),
        np.zeros(360),
        np.zeros(360),
    )
    for m in range(480, 840):
        t = m - 480
        for _, r in df_s.iterrows():
            arr = r["arr"]
            s1_s = r["s1_s"]
            s1_e = r["s1_e"] if r["s1_e_st"] == "RECORDED" else 840.0
            s2_s = r["s2_s"]
            s2_e = r["s2_e"] if r["s2_e_st"] == "RECORDED" else 840.0

            # S1 occupancy
            if arr <= m:
                if np.isnan(s1_s) or m < s1_s:
                    s1_q[t] += 1
                elif s1_s <= m < s1_e:
                    s1_b[t] += 1

            # S2 occupancy
            if r["s1_e_st"] == "RECORDED" and r["s1_e"] <= m:
                if np.isnan(s2_s) or m < s2_s:
                    s2_q[t] += 1
                elif s2_s <= m < s2_e:
                    s2_b[t] += 1

    summary_table.append(
        {
            "Scenario": sc_name,
            "S1_Mean_Wait": round(s1_wait.mean(), 1),
            "S1_Mean_Serv": round(s1_serv.mean(), 1),
            "S1_Mean_WIP": round((s1_q + s1_b).mean(), 2),
            "S1_Peak_WIP": int((s1_q + s1_b).max()),
            "S1_Util": f"{s1_b.mean() / 2.0:.1%}",
            "S2_Mean_Wait": round(s2_wait.mean(), 1),
            "S2_Mean_Serv": round(s2_serv.mean(), 1),
            "S2_Mean_WIP": round((s2_q + s2_b).mean(), 2),
            "S2_Peak_WIP": int((s2_q + s2_b).max()),
            "S2_Util_Gross": f"{s2_b.mean() / 2.0:.1%}",
            "S2_Util_Net": f"{s2_b.sum() / 705.0:.1%}",
        }
    )
