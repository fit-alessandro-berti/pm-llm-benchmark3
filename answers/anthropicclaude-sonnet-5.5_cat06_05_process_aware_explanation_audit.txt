## 2. Process-model consistency checks

**A. Prefix-time availability (point-in-time replay)**
- Every feature in a registry declares its source events, `as_of` logic and mutability.
- Test 1: recompute each feature from the log truncated at t0 and compare it with the stored value. Any difference is a leak.
- Test 2 (perturbation): delete or shuffle post-t0 events. Feature values and attributions must not change.
- Test 3: require `max(source_ts) <= t0` and `max(source_seq) <= seq(t0)`. A feature with no timestamp fails closed (for example `risk_score_current`, `final_handler_team`).
- Test 4: screen for label proximity with single-feature AUC, to catch circular features such as `total_case_duration_hours`.
- Limitation: replay only verifies event-derived features. Warehouse snapshots need their own version history.

**B. Activity-order feasibility**
- Encode declarative constraints from policy, not from mined frequency:
  - Coverage follows Registered.
  - Closed is terminal, so nothing follows it.
  - Appeal requires a prior Partial or Deny decision.
  - A second decision requires an Appeal in between.
  - Received follows Requested, and Validated follows Received.
  - Damage Assessment precedes a non-Withdrawn decision. A Withdrawn decision is exempt.
- Run alignment or token replay on prefix and full traces. This flags the ClosedDamage pattern as a violation.
- Limitation: the model is simplified, so conformance does not prove the data is right. Parallel fraud and loops need explicit modelling.
- Footprint and DFG checks help find candidate violations, but a frequent edge is not a rule. A rare, legal path such as an appeal or a fast track is not an error, and a frequent edge such as CoverageFraud can still be non-normative. SMEs should review the mined candidates.

**C. Same-timestamp ambiguity**
- Detect ties per case. Without a reliable sequence index, treat the tied events as an unordered set.
- Enumerate the permutations the model allows. If a feature or pattern depends on the order, mark it ambiguous and quarantine it, rather than tie-breaking by alphabet or ingestion order.
- Ties at t0 need the same handling, because the prefix boundary must be defined by sequence, not time alone. Conservatively exclude events tied with the coverage check.

**D. Complete-trace detection**
- Statically analyze SQL and code for aggregates over `case_id` with no time predicate.
- Flag names containing `total`, `final`, `any`, `current`, `last`, `variant`.
- Run the truncation-invariance test from A.

**E. Enabled, impossible, or future-possible classification**
- For each activity or pattern an explanation cites, compute its state at t0 against the model:
  - Observed: in the prefix.
  - Enabled next: for example Documents Requested, Damage Assessment, possibly Fraud Investigation if a trigger exists.
  - Future-reachable but not enabled: Documents Received, Decision, Closed.
  - Conditional: Appeal, which requires a prior Partial or Deny.
  - Impossible: violates constraints (for example Closed before Damage).
- Rule: SHAP inputs must be observed at t0. Future activities may appear only in clearly labelled scenario forecasts, never as attributions.

**F. Repeated Settlement Decision events**
- Give each decision an instance number (decision_seq).
- Validate that a second decision is preceded by an Appeal, which is preceded by a first decision of Partial or Deny.
- A second decision without that chain is an error. With it, the repeat is semantically legitimate but still post-t0.
- A coarse activity label alone cannot distinguish the two cases.

## 3. Alternative feature interpretations

The four standards differ:
- **Predictive validity** requires availability at t0, process consistency, and out-of-time performance.
- **Causal interpretation** requires an identification argument, such as confounder control or intervention evidence. SHAP does not provide this.
- **Operational actionability** requires that someone can change the feature before the outcome, and that doing so changes the outcome.
- **Fairness review** asks whether a proxy produces disparate error or treatment, regardless of predictive value.

A feature can pass the first and fail the other three.

**Defensible predictive signal** (`initial_damage_complexity`; `initial_reserve` if versioned; `claimant_channel` if timestamped; `prior_claim_count` after repair)
- May claim: at t0 these features are associated with breach risk and improve discrimination and calibration.
- May not claim: that they cause delay, that changing the reserve or channel would change the outcome, or that complexity is the mechanism.

**Process-state or congestion signal** (`queue_length_at_t0`; `elapsed_since_registration_at_t0`; `assigned_team_at_t0` after repair; `resource_role_at_t0`)
- May claim: higher queues and longer intake latency indicate less capacity or less remaining slack at the decision point. These are candidates for operational levers.
- May not claim: a quantified causal effect of queue length without a capacity model, or that "already-old claims" are intrinsically riskier (elapsed is mainly intake latency). A team effect requires controlling for case mix.

**Proxy requiring fairness or robustness review** (`claimant_region`, `claimant_channel`, and possibly employee experience after repair)
- May claim: predictive association, with subgroup performance, calibration and error rates reported.
- May not claim: that region or channel drives delay, or that customers should be treated differently. Test mediators such as repair-network coverage, which is more actionable.
- Do not simply delete them. Deletion can hide disparities (other features can proxy them) and lose legitimate signal. Keep them only where the use is justified and monitored.

**Drift or calendar proxy** (`calendar_week`)
- May claim: the period correlates with operating conditions.
- May not claim: that week 52 is inherently worse. Decompose into holiday, policy regime and staffing, and test across years.

**Unusable until lineage is repaired**
- `final_handler_team`, `risk_score_current`, `last_resource_role`, `same_day_document_count_snapshot`, employee experience, `prior_claim_count`, and any pattern with tied timestamps.
- May claim: nothing about them at t0.
- Post-t0 outcome and path features (`total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, and all five sequence patterns) are not repairable as t0 inputs. They can only be used for post-hoc analysis.

4. Version mutable fields (risk score, reserve, team, employee experience) in a history table. Retire closure-populated warehouse fields as model inputs.

**Priority 6: monitoring**
12. Monitor schema drift, null rates, late-arriving events, timestamp-tie rates, and the conformance violation rate.
