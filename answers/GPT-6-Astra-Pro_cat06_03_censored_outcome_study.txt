## 1. Target definition

**The primary study should predict application pathways under the observed lending policy, not assign a hypothetical default label to every applicant.** Rejection prevents the observed credit exposure; it does not demonstrate that the applicant would have repaid an activated account. This is a selective-label problem, not merely an imbalanced classification problem. ([Proceedings of Machine Learning Research][1])

I would use a **multi-state, policy-dependent target** with two clocks.

Let \(S\) be application start, \(A\) activation time, and \(H=S+90\) days. The additional **90-day application-resolution window is a study-design assumption**, introduced to replace the unbounded word “eventually” with an evaluable operational horizon. Preserve the warehouse’s separate definition of default within 90 days after activation.

The mutually exclusive target states are:

| State                                  | Definition                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Rejected                               | Rejection is the first application exit and occurs by \(H\).                                                                    |
| Withdrawn                              | Withdrawal is the first application exit and occurs by \(H\).                                                                   |
| Transferred                            | Transfer is the first exit from the lender’s local process and occurs by \(H\).                                                 |
| Unresolved at day 90                   | No activation, rejection, withdrawal, or transfer has occurred by \(H\). This includes accepted-but-not-activated applications. |
| Activated, then default within 90 days | Activation is the first exit and occurs by \(H\), followed by `default_90d = 1`.                                                |
| Activated, no default within 90 days   | Activation occurs by \(H\), with a certified, complete `default_90d = 0` outcome.                                               |

An application activating after \(H\) belongs to “unresolved at day 90” for this particular target, even when its later account outcome becomes known.

**Prediction time and population.** Produce a baseline prediction immediately after `Application Started` for every reconstructible application. Evaluate a separate update after the third canonical business event, provided no final decision or application exit has occurred. A 24-hour update is another prespecified landmark. These later predictions concern the applications still eligible at that landmark—not automatically all 48,000 applications.

**Unit of analysis.** One original application per prediction landmark, not one event. All landmarks and known linked identifiers remain in the same evaluation group.

**Estimand.** For eligible applications at prediction time \(\tau\), estimate

$$
p_j(h,\pi)=P(Z=j\mid \mathcal H_\tau=h,\text{eligible at }\tau,\pi),
$$

where \(\mathcal H_\tau\) contains only information available by \(\tau\), and \(\pi\) denotes the historical policy environment. The six probabilities sum to one.

This answers an operational question: **“What pathway is this application likely to follow under the lending process being observed?”** It does not purport to answer “Would this person default if we granted them credit?” Its longest substantive outcome window is 180 days after application start, followed by reporting delay—not 90 days after the prediction.

**Credible alternatives.**

A narrower alternative is

$$
q(h,\pi)=P(\texttt{default\_90d}=1\mid A\le H,\mathcal H_\tau=h,\pi).
$$

This predicts default **among applications that activate within the application horizon**. It is useful for the activated portion of the portfolio, but cannot be interpreted as a validated risk estimate for rejected applicants.

A counterfactual alternative would specify default under an intervention that activates credit at a particular time, amount, and set of terms. That requires assumptions about unmeasured selection, support, and treatment consistency. A propensity model or imputed “reject label” does not establish those assumptions. ([Proceedings of Machine Learning Research][2])

## 2. Cohort construction

**Start with the application registry and full event history, not the labeled export.** Include all original applications started between 1 January 2024 and 31 December 2025, regardless of eventual disposition, label availability, channel, or prefix length.

The supplied reconciliation is:

| Snapshot group                       | Applications | Label and observation status                                                      | Treatment in the study                                                                                |
| ------------------------------------ | -----------: | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Activated, labeled non-default       |       18,900 | Observed, mature binary outcome                                                   | Eligible for the non-default activated state when activation occurred within the application horizon. |
| Activated, labeled default           |        2,700 | Observed, mature binary outcome                                                   | Eligible for the default activated state under the same horizon rule.                                 |
| Rejected                             |        9,100 | Default under activation is unobserved and counterfactual                         | Observed competing application exit; never populate `default_90d = 0`.                                |
| Withdrawn                            |        5,700 | No observed activated-account default outcome                                     | Observed competing exit; retain as withdrawal.                                                        |
| Transferred                          |        2,900 | Local exit observed; downstream follow-up selectively available                   | Competing exit for the primary local-process target.                                                  |
| Still open                           |        5,100 | Application follow-up incomplete or application unresolved                        | Right-censored when day 90 has not been observed; otherwise “unresolved at day 90.”                   |
| Activated, outcome not yet available |        3,600 | Horizon incomplete or feed delayed; persistent missingness requires investigation | Activation contributes to pathway estimation; default outcome remains unknown.                        |
| **Total**                            |   **48,000** | **21,600 labeled; 26,400 omitted from the current ML export**                     | **All retained in the master cohort.**                                                                |

These are **snapshot categories**, not counts of the six horizon-specific target states. Allocating them to those states requires event dates. For example, a currently rejected case may already have been unresolved at its application-day-90 horizon.

The supplied data contain 25,200 observed activated accounts. The labeled export represents 45% of all applications, and its \(2{,}700/21{,}600=12.5\%\) default proportion describes only labeled activated accounts.

**As-of rules.** Maintain three separate times:

* The prediction timestamp controls predictor availability.
* The model-fit or evaluation cutoff controls which outcome labels are available.
* The event-coverage boundary controls how far application states can be established.

Application-event follow-up ends at the earlier of the analysis cutoff and **31 December 2025**. Extraction on 15 February 2026 does not establish that an apparently open application remained open throughout January and February. Conversely, a certified outcome feed available in February can establish a 90-day account outcome extending into January, despite the shorter event window.

Exclude or quarantine only documented problems: irreconcilable identifiers, missing starts, impossible chronology, conflicting exits or labels, or prefixes whose order cannot be reconstructed. Report each exclusion separately. Do not exclude an entire application merely because it has no third-event prefix.

Assume case identifiers uniquely identify original local application episodes; verify that assumption. Use known transfer links to group related identifiers for leakage control. Do not silently stitch only the linked 60% into an apparently representative enterprise-wide cohort.

Finally, **permanently missing feeds have no supplied count**. They must be reconciled within the existing groups or identified as a discrepancy in the registry/export reconciliation—not added as an invented eighth population.

## 3. Censoring and missing-label strategy

**Ordinary right censoring.** An application with no observed exit before the event-coverage boundary contributes an observed period without an exit. Its last event is not automatically its censoring date: under verified continuous platform coverage, observation continues through the coverage boundary. Absence of events is informative only when coverage is established.

**Delayed labels.** An activated account may have completed its 90-day horizon without its feed having arrived. This is reporting delay, not evidence of non-default. Track `activation + 90 days`, actual `label_available_at`, and feed status separately. Use the supplied 35-day upper end of the common delay range as an initial buffer, **not a guaranteed maximum**.

**Selection through activation.** Activation is an outcome of the first-stage process. Rejected and withdrawn applications do not belong in the activated-account default likelihood. No inverse-activation weighting is necessary to define the primary observed-pathway estimand; such weighting would answer a different question and require stronger assumptions.

**Transfer.** Transfer is an observed competing exit for the primary local-process target. For an enterprise-wide target, it instead creates a continuation and follow-up problem. Those are different estimands; they should not be mixed within one analysis.

**Permanently missing feeds.** An old activated account with no label is not ordinary administrative censoring. Partner-dependent missingness may be informative. “Overdue and unresolved” is an appropriate data status; “permanently missing” requires additional evidence.

### Primary analysis

Use a factorized model rather than a six-class classifier trained only on complete outcomes:

1. Fit application-exit hazards for activation, rejection, withdrawal, and transfer. Include right-censored applications through their observed follow-up; retain document loops in prefix histories.
2. Fit the binary 90-day default component among applications activating within the application horizon, using maturity-supported cohorts and an explicit feed-observation adjustment.

Competing-event probabilities must be calculated jointly. Treating competing exits as ordinary censoring and interpreting one minus Kaplan–Meier as default incidence would answer the wrong probability question. ([PubMed Central (PMC)][3])

Writing \(p_A(h)\) for activation by \(H\), the two activated-state probabilities are

$$
p_{\mathrm{activated,default}}(h)=p_A(h)q(h),
\qquad
p_{\mathrm{activated,no\ default}}(h)=p_A(h)[1-q(h)].
$$

An activated case with an unknown default outcome still contributes information about activation. It provides no fabricated binary repayment label.

For the default component, start with cohorts satisfying

$$
S+90+90+35\le t_{\text{fit}},
$$

so inclusion is not determined merely by unusually fast activation or unusually prompt reporting. Within these cohorts, actual label availability is still required. Estimate observation probabilities among **all eligible activated accounts**, including those without labels, using source, vintage, prefix information, and appropriate observation metadata. Activation dates may enter maturity rules and observation weights; they must not enter the deployed early-prefix feature vector.

Inverse-observation weighting requires conditional independence of missingness and the unobserved outcome, given the adjustment variables, plus positive observation probabilities. Weight truncation, overlap diagnostics, and effective sample sizes are necessary, but do not prove the assumptions. ([arXiv][4])

The binary feed alone does **not** establish exact default times or continuous default-free surveillance. Therefore, do not fit an account-level default-time survival model by treating missing labels as survival up to extraction. That alternative needs actual default-onset dates and verified observation intervals.

### Sensitivity analyses and assumptions

Use a pattern-mixture sensitivity analysis in which missing activated accounts have, for example, 0.5, 1, 2, or 4 times the conditional default odds of comparable observed accounts. These are scenarios, not estimated facts. Examine how calibration, portfolio risk, and action rankings change, especially for partner-originated accounts. Such analyses explicitly vary assumptions about nonignorable missingness. ([PubMed Central (PMC)][5])

As a transparent finite-cohort bound, the supplied 25,200 observed activated accounts have an eventual 90-day default proportion between

$$
\frac{2,700}{25,200}=10.7\%
\quad\text{and}\quad
\frac{2,700+3,600}{25,200}=25.0\%.
$$

This is **not a confidence interval**, not the primary horizon-specific estimand, and not a bound on counterfactual default for all applicants.

Also repeat the analysis with longer reporting buffers and an enterprise-transfer continuation specification. Report changes in the evaluated population alongside changes in metrics.

Chronology, conflicting labels, observed delay distributions, known-link consistency, and source-specific observation rates are testable or auditable. Independent censoring and stability across vintages are only partially assessable. Outcome-dependent permanent missingness, missing-at-random transfer linkage, and default under hypothetical activation are not identifiable from this export alone.

## 4. Prefix extraction

Use a source-specific, versioned activity dictionary and define an approved business-event vocabulary before counting events.

**Fixed event-count landmarks.** Evaluate \(k=1\) and \(k=3\) separately. A \(k=3\) prediction occurs immediately after the third eligible event, not at the end of a retrospectively shortened trace. PM4Py’s `get_prefixes_from_log` returns prefixes **up to** the requested length, retaining shorter traces; consequently, exact-\(k\) eligibility must be checked explicitly. ([GitHub][6])

A case rejected after two events retains its start prediction but has no pre-decision third-event prediction. An open case with two events has not yet reached that landmark. Neither should be silently converted into a completed three-event example.

**Elapsed-time landmarks.** At \(S+24\) hours, collect all events available by that timestamp and score applications still eligible then—even when no recent event occurred. “Time since last observed event” is a valid feature; using the eventual next-event time is not.

**Loops and order.** Preserve repeated document requests and review visits. They are potential signals, not automatically duplicate records. Deduplicate only when event identity or source provenance establishes duplicate delivery. Without an event ID or reliable sequence field, flag tied timestamps and quarantine only the affected ordered prefixes.

**Availability.** Ideally, an event is eligible only when both its occurrence and ingestion timestamps precede prediction. The supplied schema lacks ingestion history. A retrospective replay must therefore state the approximation that event timestamps represent availability, and separately assess late-arrival and backfill risk.

Do not use eventual trace length, ultimate variant, final activity, or full-case duration to construct an early prefix. Keep repeated landmarks together and evaluate them separately, or explicitly weight applications so document-heavy cases do not dominate through many examples.

## 5. Process-aware features

**Static application attributes.** Initial channel, region, and requested amount are candidates only when their original values are preserved. A `case:` prefix in a column name is not proof of immutability. Use the initial submitted amount rather than a subsequently revised warehouse value.

**Prefix-derived features.** Include the current activity, observed activity counts, short activity sequences, review revisits, document-request/receipt patterns, elapsed application age, inter-event gaps, time since last activity, number of observed resources, and observed resource changes. Call repeated reviews “revisits,” not proven defective rework. Preserve the distinction between an unanswered document request and a completed document cycle.

Use the latest **historically recorded** risk score within the prefix, its age, and previous prefix-observed changes only after lineage verification. Do not backfill early missing values from later events.

**Features requiring historical reference data.** Candidate features include work-in-progress at the prediction timestamp, arrivals during preceding hours, resource workload, historical activity-transition frequencies, and source-specific reporting reliability. Compute them from information already available at prediction, across the full application population—not just labeled accounts.

A single timestamp per event does not identify service time versus queue waiting. Consequently, do not interpret inter-event duration as pure waiting or invoke `insert_case_service_waiting_time` as though start/complete lifecycle intervals were supplied.

Historical resource experience needs employment and role records with effective dates. Outcome-based reference statistics also need label-availability cutoffs. Calendar aggregates must use completed past intervals, not totals from the current day or week that include later activity.

Include prediction-date policy and migration indicators for monitoring and, where supported, modeling. **An indicator does not teach a model the effect of a policy regime absent from its training data.**

Add a **suffix-invariance test**: appending, removing, or changing post-prefix events must not change the extracted feature vector. Passing it does not establish historical correctness of an already overwritten field; that needs lineage evidence.

## 7. Validation design

Use a temporal, delayed-outcome backtest rather than a random split. One conservative primary schedule is:

| Component                | Application-start window   | Information rule                                                                                                           |
| ------------------------ | -------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Training                 | January–September 2024     | Fit candidate models on 1 October 2024 using only information available then.                                              |
| Validation               | October 2024               | Generate predictions with those frozen models at the eligible landmarks.                                                   |
| Outcome-accrual interval | November 2024–14 June 2025 | Retain these cases in the registry; do not use them to tune the primary frozen comparison.                                 |
| Selection/calibration    | 15 June 2025               | Use only validation outcomes available by this date.                                                                       |
| Test                     | 15 June–31 December 2025   | Apply the selected model/calibrator prospectively in the replay; assess available truth at the supplied extraction cutoff. |

The long accrual interval is deliberate. An application started on 31 October 2024 can require until **3 June 2025** for the application window, account outcome window, and a 35-day reporting buffer. This avoids selecting validation cases simply because they resolve quickly.

The initial default component will have a smaller maturity-supported training population than the process component; report its actual size. Keep the primary model frozen through testing to expose deterioration. Separately run monthly rolling-origin refits, each respecting its own training cutoff and label availability. Do not compare those refits using outcomes unavailable when the respective model was fitted.

**Policy and migration.** Report test results separately for 15–30 June, 1 July–14 October, and 15 October–31 December 2025. Also identify applications spanning the policy change: the policy at their eventual decision can differ from the policy at their prefix. Use the latter as a predictor; the former is diagnostic metadata unless already known.

**Maturity limitation.** With the chosen target and the common-delay buffer, approximately **15 July 2025** is the latest application-start date with full nominal 215-day accrual by 15 February 2026. Actual feed availability remains necessary. Later cohorts may contribute observed exits and some completed account outcomes, but cannot be presented as a fully observed headline test set. Post-migration default calibration is therefore particularly provisional.

Administrative censoring weights cannot manufacture outcomes where a new regime has no follow-up support. Report maturity-supported results, partial-follow-up results, and missingness sensitivity results separately.

**Metrics.** Evaluate application-exit cumulative incidence and calibration at prespecified horizons, together with censoring-adjusted Brier scores. For fully accrued multi-state predictions, use multiclass Brier score and log loss, adjusted for the remaining outcome-observation mechanism. Censoring-adjusted Brier estimation requires an appropriate censoring model. ([PubMed][7])

For the activated default component, report weighted Brier score, calibration intercept/slope, reliability plots, AUROC, and precision–recall performance. Evaluate both conditional default risk \(q\) and the all-application joint probability \(p_Aq\). Do not let a strong rejection classifier conceal a poorly calibrated default component.

Report metrics, observation rates, event counts, and uncertainty by channel, region, amount band, source/partner origin, policy era, migration era, and landmark eligibility. Cluster uncertainty by application/known linked journey and assess calendar-block variation. Small subgroups should receive intervals and support warnings, not precise rankings.

A random case split mixes policy and system regimes, permits training on information later than test predictions, and can place linked journeys on both sides. It also does nothing to correct selective labeling. Known linked groups crossing temporal boundaries should be purged or otherwise handled without moving future records into training; the unlinked portion remains a limitation.

## 8. Limitations and decision-use boundary

The study can estimate **historical-policy-dependent pathway probabilities**, and conditional activated-account default risk within its supported populations and missingness assumptions. It can assess whether early process histories contain useful warning signals and identify where label coverage prevents reliable evaluation.

It cannot establish that rejection proves repayment ability, recover default under activation for every rejected applicant, demonstrate complete enterprise-wide follow-up from 60% transfer linkage, or prove post-migration calibration from selectively matured outcomes.

Predictive associations also need careful interpretation. Repeated document requests might indicate complexity, cautious review, missing information, or a resource problem. Resource assignment and region can encode selection and operational practices rather than applicant repayment characteristics. Observed default differences across policy periods can reflect changed exposure selection, changed terms, changed behavior, or changed measurement.

Deployment can alter the data-generating process in several ways:

* Changing approval thresholds changes who receives credit and therefore who becomes labeled.
* Warnings can trigger more reviews, additional documents, altered limits, or earlier intervention, changing both prefixes and outcomes.
* Workload redistribution and transfer decisions can change waiting times, activation timing, partner exposure, and feed missingness.
* Preventive servicing can avert defaults that the model would otherwise have correctly forecast.

Use the initial model in **shadow mode or governed operational review**, not as a stand-alone basis for automated rejection. Log predictions, model versions, availability timestamps, interventions, policy versions, and reasons for non-intervention. Prioritize complete source-level outcome accounting and historical feature lineage before claiming better discrimination solves the business problem.

## 9. PM4Py-oriented Python implementation skeleton

The skeleton keeps predictor data separate from outcome metadata, defaults to the third-event update, and also constructs start-landmark coverage. `ALIASES` and `GROUP_MAP` must be populated from approved mapping/linkage data; empty dictionaries are not evidence that those risks are absent. The PM4Py calls follow its maintained formatting, prefix, and DFG APIs. ([Process Intelligence Solutions][8])

```python
import pandas as pd
import pm4py

C, A, T, R = 'case:concept:name', 'concept:name', 'time:timestamp', 'org:resource'
UTC = lambda s: pd.Timestamp(s, tz='UTC')
SNAP, FIT, SELECT = UTC('2026-02-16') - pd.Timedelta(nanoseconds=1), UTC('2024-10-01'), UTC('2025-06-15')
VAL_END, POLICY, K = UTC('2024-11-01'), UTC('2025-07-01'), 3
END = UTC('2026-01-01') - pd.Timedelta(nanoseconds=1)
D90, D125 = pd.Timedelta(days=90), pd.Timedelta(days=125)
EXIT = {'Account Activated': 'activated', 'Rejected': 'rejected',
        'Withdrawn': 'withdrawn', 'Transferred': 'transferred'}
STOP = set(EXIT) | {'Accepted', 'Contract Signed', 'Collections Contact', 'Default Recorded'}
SAFE = [C, A, T, R, 'source_system']
ALIASES, GROUP_MAP = {}, {}  # Approved (source, raw activity) -> canonical; ID -> linked journey.
# ASSUMPTIONS: UTC/offset-aware times, complete event coverage, immutable certified labels.
# Event timestamp approximates availability; true historical replay needs ingestion/version data.
raw = pd.read_csv('applications_events.csv', dtype={C: 'string', A: 'string'})
for col in [T, 'label_available_at', 'data_extract_time']:
    raw[col] = pd.to_datetime(raw[col], utc=True, errors='raise')
assert raw[[C, A, T, 'data_extract_time']].notna().all().all()
SNAP = min(SNAP, raw['data_extract_time'].max())  # Never advance beyond this export.
assert (raw['label_available_at'].isna() | raw['label_available_at'].le(raw['data_extract_time'])).all()
raw['default_90d'] = pd.to_numeric(raw['default_90d'], errors='raise')
lab = raw.loc[raw['default_90d'].notna(), [C, 'default_90d', 'label_available_at']].drop_duplicates()
assert lab['default_90d'].isin([0, 1]).all() and lab['label_available_at'].notna().all()
assert lab.groupby(C)['default_90d'].nunique().le(1).all(), 'Reconcile revised/conflicting labels.'
lab = lab.sort_values('label_available_at').drop_duplicates(C).set_index(C)
base = raw[SAFE].copy()  # Targets and potentially overwritten attributes never enter PM4Py.
base[A] = [ALIASES.get((s, a), a) for s, a in zip(base['source_system'], base[A])]
print('Activities requiring mapping sign-off:', sorted(base[A].unique()))
base = pm4py.format_dataframe(base, case_id=C, activity_key=A, timestamp_key=T)
base = base.sort_values([C, T], kind='stable')
print('Potential tied/duplicate events:', int(base.duplicated([C, T], keep=False).sum()))

def asof(cut: pd.Timestamp):
    e = base.loc[base[T].between(UTC('2024-01-01'), min(cut, END))].copy()
    m = e.loc[e[A].eq('Application Started')].groupby(C)[T].min().to_frame('start')
    assert set(e[C]) <= set(m.index), 'Missing starts/left-truncated cases need reconciliation.'
    assert e.groupby(C)[T].min().eq(m['start']).all(), 'Events precede the registered start.'
    route = e.loc[e[A].isin(EXIT)].drop_duplicates(C).set_index(C)
    assert e.loc[e[A].isin(EXIT)].groupby(C)[A].nunique().le(1).all(), 'Conflicting exits.'
    m['exit_at'], m['exit_type'] = route[T], route[A].map(EXIT)
    m['activation'] = e.loc[e[A].eq('Account Activated')].groupby(C)[T].min()
    m['boundary_at'] = e.loc[e[A].isin(STOP)].groupby(C)[T].min()
    m['censor_at'], m['app_horizon'] = min(cut, END), m['start'] + D90
    m['default_horizon'] = m['activation'] + D90
    m['route_stop'] = m[['exit_at', 'censor_at', 'app_horizon']].min(axis=1)
    m = m.join(lab.loc[lab['label_available_at'].le(cut)])
    m['label_mature'] = m['default_horizon'].le(cut) & m['default_90d'].notna()
    m['y90'] = m['default_90d'].where(m['label_mature'])
    m['feed_state'] = 'undefined_without_activation'
    active = m['activation'].notna()
    m.loc[active, 'feed_state'] = 'horizon_incomplete'
    m.loc[active & m['default_horizon'].le(cut), 'feed_state'] = 'feed_pending'
    m.loc[active & (m['activation'] + D125).le(cut), 'feed_state'] = 'feed_overdue_unknown'
    m.loc[m['label_mature'], 'feed_state'] = 'observed'
    by_h = m['exit_at'].le(m['app_horizon'])
    m['route_event'] = by_h  # Right-censor route duration at route_stop otherwise.
    m['state'] = pd.Series(pd.NA, index=m.index, dtype='string')
    m['state_available_at'] = pd.Series(pd.NaT, index=m.index, dtype='datetime64[ns, UTC]')
    competing = by_h & m['exit_type'].isin(['rejected', 'withdrawn', 'transferred'])
    m.loc[competing, 'state'] = m.loc[competing, 'exit_type']
    m.loc[competing, 'state_available_at'] = m.loc[competing, 'exit_at']
    unresolved = ~by_h & m['app_horizon'].le(m['censor_at'])
    m.loc[unresolved, 'state'], m.loc[unresolved, 'state_available_at'] = 'unresolved90', m.loc[unresolved, 'app_horizon']
    observed = by_h & active & m['label_mature']
    m.loc[observed, 'state'] = m.loc[observed, 'y90'].map({0: 'activated_no_default90', 1: 'activated_default90'})
    m.loc[observed, 'state_available_at'] = m.loc[observed, ['label_available_at', 'default_horizon']].max(axis=1)
    m['snapshot_group'] = m['exit_type'].fillna('still_open')
    m.loc[active, 'snapshot_group'] = 'activated_unlabeled'
    m.loc[m['label_mature'], 'snapshot_group'] = m.loc[m['label_mature'], 'y90'].map({0: 'labeled_nondefault', 1: 'labeled_default'})
    return e, m

def prefixes(e, m, k=1, hours=None):
    boundary = e[C].map(m['boundary_at'])
    pre = e.loc[boundary.isna() | e[T].lt(boundary), SAFE].copy()
    if hours is None:
        p = pm4py.get_prefixes_from_log(pre, length=k, case_id_key=C)
        n = p.groupby(C).size()
        tau = p.groupby(C)[T].max().loc[n.eq(k)]  # PM4Py retains shorter traces: exclude here.
    else:
        tau = m['start'] + pd.Timedelta(hours=hours)  # Score despite absence of recent events.
        p = pre.loc[pre[T].le(pre[C].map(tau))].copy()
    eligible = tau.le(m['censor_at']) & tau.lt(m['app_horizon'])
    eligible &= m['boundary_at'].isna() | tau.lt(m['boundary_at'])
    tau = tau.loc[eligible.reindex(tau.index).fillna(False)]
    tied = pre.loc[pre.duplicated([C, T], keep=False)]

    p = p.loc[p[C].isin(tau.index) & p[T].le(p[C].map(tau))].copy()
    g = p.groupby(C)
    X = g.agg(n_events=(A, 'size'), n_activities=(A, 'nunique'), n_resources=(R, 'nunique'),
              last_activity=(A, 'last'), source=('source_system', 'last'))
    X['elapsed_hours'] = (tau - m['start']).dt.total_seconds() / 3600
    X['idle_hours'] = (tau - g[T].max()).dt.total_seconds() / 3600
    X['repeat_reviews'] = p[A].eq('Credit Review').groupby(p[C]).sum().sub(1).clip(lower=0)
    prev = g[R].shift()
    X['resource_changes'] = (p[R].notna() & prev.notna() & p[R].ne(prev)).groupby(p[C]).sum()
    X['policy_v2'], X['post_migration'] = tau.ge(POLICY).astype(int), tau.ge(UTC('2025-10-15')).astype(int)
    X['weekday'] = tau.dt.dayofweek
    assert p[T].le(p[C].map(tau)).all() and not p[A].isin(STOP).any()
    return X, p, tau
```
