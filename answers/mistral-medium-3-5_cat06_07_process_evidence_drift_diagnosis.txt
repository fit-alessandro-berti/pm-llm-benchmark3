## 2. Competing explanations and timeline

### **Jan–Mar: Stable Baseline**
- **Metrics**: AUROC ~0.81, Brier ~0.131, ECE ~0.024. Breach rates stable (V1: 0.15–0.16, V2: 0.10–0.11, V3: 0.30–0.32).
- **Process**: DFG edges stable (e.g., `Order PartPart Received`: 28–35h). No pipeline issues.
- **Conclusion**: No drift. Model performs well.

### **Apr: Pipeline Break**
- **Metrics**: AUROC drops to 0.67, ECE spikes to 0.110, mean predicted risk jumps to 0.28 (vs. observed 0.19).
- **Process**: 18% unmapped variants, 17% `UNKNOWN_ACTIVITY`, 14% missing queue feature. Diagnosis label renamed on Apr 1; pipeline initially ignored new label.
- **Conclusion**: **Data-pipeline failure** dominates. Model inputs are corrupted (wrong event prefixes, missing features). Not concept/process drift.

### **May: Partial Recovery**
- **Metrics**: AUROC recovers to 0.78, ECE improves to 0.050, but mean risk (0.21) still overestimates observed (0.18).
- **Process**: Patch deployed on May 6 remaps labels, but cached features (e.g., "number of events before diagnosis") not fully backfilled. Unmapped variants drop to 1%.
- **Conclusion**: **Residual pipeline issues** (incomplete backfill) + minor **covariate drift** (V3 share rises to 22%). Not yet concept drift.

### **Jun: Routing Policy Change**
- **Metrics**: AUROC 0.79 (stable), Brier 0.139, ECE 0.060. Observed breach rate drops to 0.15 (V2 share jumps to 52%).
- **Process**: New remote-routing policy increases V2 usage. V2 breach rate remains low (0.09).
- **Conclusion**: **Process drift** (routing mix change) but **no concept drift**—model still discriminates well (AUROC stable). Lower breach rate is real (V2 is faster).

### **Jul: Supplier Delays Begin**
- **Metrics**: AUROC drops to 0.76, Brier rises to 0.151. V3 breach rate jumps to 0.46.
- **Process**: `Order PartPart Received` median time spikes to 65h (vs. 42h in Jun). Label maturity still 100%.
- **Conclusion**: **Concept drift** for V3 (supplier delays change the relationship between features and breach risk). V1/V2 metrics stable.

### **Aug–Sep: Overlapping Drifts**
- **Metrics**: AUROC 0.68 (Aug), 0.66 (Sep); Brier 0.1970.214; ECE 0.1200.140. Observed breach rate 0.280.31.
- **Process**:
  - **Process drift**: `Order PartPart Received` worsens to 130h (Aug), 148h (Sep).
  - **Population shift**: Partner Z onboarded in Sep (24% share), with 58% V3 usage and higher rural/device-age (unmodeled features).
  - **Concept drift**: V3 breach rate 0.64 (Aug), 0.61 (Sep) vs. 0.35 (Jun).
- **Conclusion**: **All three drifts overlap**:
  - **Process drift**: Supplier delays lengthen V3 resolution.
  - **Population shift**: Partner Z introduces harder cases (rural/old devices).
  - **Concept drift**: Model underestimates risk for V3 (AUROC drops sharply for V3; see Section 3).

### **Oct: Label Censoring Dominates**
- **Metrics**: Label maturity 55%, median label delay 52d. Observed breach rate 0.16 (likely underestimated).
- **Process**: Outcome API backlog affects long-resolution paths (V3). Partner Z share 27%.
- **Conclusion**: **Label delay/censoring** confounds all metrics. AUROC 0.64 is unreliable. **Do not trust Oct for training or evaluation**.

### **Why Not Homogeneous?**
- **Apr**: Pipeline failure (fixable with data cleaning).
- **Jun**: Process drift (routing change) without concept drift.
- **Aug–Sep**: Genuine concept/process/population shifts (requires model updates).
- **Oct**: Label maturity issue (ignore until labels mature).

2. **Calibration Monitors**

   - Reliability diagrams.
3. **Label-Maturity Monitors**
   - % label maturity by month/variant.
   - Median/90th percentile label delay.
   - Alert if maturity <80% or delay >45d.
4. **Data-Quality Monitors**
   - `UNKNOWN_ACTIVITY` share, missing feature rates.
   - Duplicate event counts.
   - Schema consistency (e.g., activity label renames).
5. **Process-Variant Monitors**
   - Variant distribution shifts (e.g., V3 share >40%).
   - New/unmapped variants.
6. **Performance-DFG Monitors**
   - Median time for critical edges (`Order PartPart Received`, `DiagnosisDispatch`).
   - Alert if edge time >2x baseline.
7. **Population Monitors**
   - Partner Z share, rural/device-age feature distributions.
   - PSI for Partner Z vs. others.
8. **Intervention/Deployment Monitors**
   - Track deployment dates (e.g., May 6 patch, Jun 1 policy).
   - Correlate metric changes with interventions.

### **Alert Dependencies**
- **Label-delay alarm**  **Do not trigger retraining**. Instead:
  - Freeze affected months for training.
  - Escalate to outcome API team.
- **Pipeline failure alarm** (e.g., `UNKNOWN_ACTIVITY` >5%)  **Recompute features** before retraining.
- **Process drift alarm** (e.g., `Order PartPart Received` >100h)  **Investigate concept drift** for V3.
- **Population shift alarm** (Partner Z share >20%)  **Stratify metrics** and consider segment-specific models.

```python
import pandas as pd
import pm4py
from datetime import datetime

def extract_monthly_process_evidence(events_path, start_date="2026-01-01", end_date="2026-10-31"):
    # Load and preprocess
    df = pd.read_csv(events_path)
    df = pm4py.format_dataframe(df, case_id="case_id", activity_key="activity", timestamp_key="timestamp")

    # Normalize diagnosis labels (handle Apr 2026 rename)
    df["activity"] = df["activity"].replace({
        "Diagnostic Assessment Completed": "Initial Diagnosis Completed",
        "UNKNOWN_ACTIVITY": None  # Mark for filtering
    })
    df = df.dropna(subset=["activity"])  # Remove UNKNOWN_ACTIVITY

    # Remove duplicates (keep first occurrence per case+activity+timestamp)
    df = df.sort_values(["case_id", "timestamp"]).drop_duplicates(
        subset=["case_id", "activity", "timestamp"], keep="first"
    )

    # Filter time range
    df = pm4py.filter_time_range(df, start_date, end_date)

    # Extract monthly summaries
    monthly_summaries = []
    for month in pd.date_range(start_date, end_date, freq="MS"):
        month_str = month.strftime("%Y-%m")
        month_df = pm4py.filter_time_range(df, month_str, (month + pd.offsets.MonthEnd(0)).strftime("%Y-%m-%d"))

        if len(month_df) == 0:
            continue

        # Case-start cohort (all cases starting in the month)
        case_starts = month_df[month_df["activity"] == "Case Created"]["case_id"].unique()
        case_start_df = month_df[month_df["case_id"].isin(case_starts)]

        # Event-calendar cohort (all events in the month)
        event_calendar_df = month_df

        # Variant analysis
        variants = pm4py.get_variants(case_start_df)
        variant_dist = variants["variant"].value_counts(normalize=True).to_dict()

        # DFG and performance DFG
        dfg = pm4py.discover_dfg(case_start_df)
        perf_dfg = pm4py.discover_performance_dfg(case_start_df)

        # Temporal features (e.g., time between diagnosis and dispatch)
        temporal_features = pm4py.extract_temporal_features_dataframe(case_start_df)

        # Label maturity (if outcome data is available)
        # Assume a separate outcomes_df with case_id and breach_label
        # outcomes_df = pd.read_csv("outcomes.csv")
        # label_maturity = outcomes_df[outcomes_df["case_id"].isin(case_starts)]["breach_label"].notna().mean()

        monthly_summaries.append({
            "month": month_str,
            "cases_started": len(case_starts),
            "variants": variant_dist,
            "dfg_edges": {edge: perf_dfg[edge]["mean"] for edge in perf_dfg},
            "median_diagnosis_to_dispatch": temporal_features[
                temporal_features["feature"] == "time:from:Initial Diagnosis Completed:to:Dispatch Technician"
            ]["value"].median() if "time:from:Initial Diagnosis Completed:to:Dispatch Technician" in temporal_features["feature"].values else None,
            # "label_maturity": label_maturity,
            "unknown_activity_share": (month_df["activity"].isna().mean()) * 100
        })

    return pd.DataFrame(monthly_summaries)
```
