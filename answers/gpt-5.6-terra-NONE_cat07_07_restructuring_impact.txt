# 4. Risks invisible in average cycle time

1. **Tail latency can worsen while the average improves.**  
   Centralization may accelerate routine cases and reduce the mean or median cycle time, while a smaller group of difficult cases waits much longer in shared queues. Monitor P90, P95, and queue-aging measures, especially for technical, legal/risk, security, and high-complexity cases.

2. **High-complexity cases can be disproportionately harmed.**  
   The proposed routing explicitly sends all high-complexity cases to the Technical Shared Service. If that queue becomes congested, the group most dependent on expertise experiences longer waits and more handoffs. A stable overall average can simply reflect a larger volume of easy cases moving faster.

3. **Loss of local knowledge may not appear immediately.**  
   North and South currently use embedded technical specialists in stable, context-rich loops. Removing those specialists may not raise cycle time at first because experienced staff still know how to work around the change. Over time, local caseworkers may make more unnecessary referrals, produce poorer handoff notes, and lose confidence in handling borderline technical issues.

4. **Fairness problems can be masked by aggregate performance.**  
   Customers requiring language support, regional accommodation, or more complex explanation may need additional clarification after centralized review. If their cases form a minority, their delays can be invisible in overall averages. Compare waiting time, rework, SLA misses, and outcomes by `customer_segment`, `location`, `case_complexity`, and `required_specialty`.

5. **Learning and skill development can erode.**  
   Embedded specialists currently transfer knowledge through repeated local interactions. Centralization can remove this informal learning channel. The process may become efficient in the short run but increasingly dependent on a small shared-service group. Lower local resource similarity with technical work and rising referral rates for similar cases are warning signs.

6. **Accountability can become fragmented.**  
   A case can be locally owned for customer communication, centrally reviewed for technical advice, centrally approved for decisions, and locally implemented. If responsibilities are not explicit, cases can sit in queues because each party believes another party owns the next action. This may manifest as increased waiting time, reassignment count, repeated approvals, and “clarification” handover reasons rather than a higher average cycle time.

7. **Exception handling can degrade.**  
   Standardized routing works best for standardized work. Edge cases—regional policy variation, incomplete customer evidence, special accommodations, unusual technical configurations—often require informal collaboration. A centralized model may push these cases into repeated queue loops or unofficial side channels not captured cleanly in the main workflow.

8. **Resilience may shift from local weakness to central fragility.**  
   Pooling can make individual-team absences less harmful, particularly helping East. But it also makes a shared-service absence, system outage, or demand surge affect all locations simultaneously. Average performance during normal weeks does not show performance under stress.

9. **Apparent handover reduction may be misleading.**  
   Fewer recorded direct handovers do not necessarily mean fewer coordination costs. A shared queue can hide many internal transfers, status checks, and reassignments. Evaluate queue dwell time, internal reassignment, repeated queue entries, and subcontracting patterns, not just total handover counts.

10. **Quality may be delayed rather than improved.**  
   Centralized difficult Quality Check can identify defects consistently, but if it occurs late and is capacity-constrained, rework may happen later in the case lifecycle. This can preserve or even improve early activity throughput while worsening customer-visible completion quality and late-stage rework.

# 5. Pilot design

## Pilot scope

Use a phased pilot rather than a full rollout.

- **Phase 0: Baseline and instrumentation, 6–8 weeks**
  - Standardize event definitions for queue entry, queue start, queue completion, advice return, approval ownership, reassignment, handover reason, and rework.
  - Ensure `team`, `location`, `required_specialty`, `priority`, `case_complexity`, `customer_segment`, `local_expertise_flag`, `handover_reason`, and `reassignment_count` are complete.
  - Record the shared queue as a queue and, where possible, record the actual specialist resource performing work; otherwise queue-level handovers can conceal internal workload distribution.

- **Phase 1: Technical Shared Service pilot, 8–12 weeks**
  - Pilot centralized technical routing for a limited subset, such as high-complexity cases in East plus one carefully selected slice of North or South.
  - Do **not** simultaneously centralize technical work, legal/risk triage, difficult quality checking, and approvals. Staging makes causal interpretation possible.
  - Retain embedded local technical escalation capacity during the pilot, perhaps as a defined “rapid local consultation” path for urgent or context-sensitive cases.

- **Phase 2: Shared approval pilot**
  - Add shared approval only after the technical pilot demonstrates acceptable tail waits, rework, ownership clarity, and fairness.
  - Keep legal/risk as a separate monitored queue initially because current utilization is already 91–93%; avoid combining new triage work with already-near-capacity specialist work without capacity evidence.

## Comparison group

Use a contemporaneous comparison design:

- **Treatment group:** pilot cases/teams routed through the Technical Shared Service.
- **Control group:** comparable cases continuing with embedded technical support.
- Prefer a staged rollout where one team starts later, enabling a difference-in-differences comparison.
- Because East is already overloaded, do not use East alone as proof of success. Compare:
  - East before versus after,
  - East pilot cases versus similar East non-pilot cases where possible,
  - North/South pilot slices versus North/South control slices,
  - high-complexity versus lower-complexity cases,
  - technical-specialty versus non-technical cases.

## Pre/post observation window

- **Pre-period:** at least 8–12 weeks, ideally covering normal demand cycles and month-end effects.
- **Pilot period:** 8–12 weeks minimum, long enough to observe queue stabilization and early rework.
- **Post-period:** at least 8–12 weeks after process stabilization for lagging outcomes, including rework and quality outcomes.
- Analyze weekly trends rather than only aggregate before/after averages.

## Required segmentation

Every pilot dashboard should stratify results by:

- `team` and `location`: North, South, East;
- `case_complexity`: especially high-complexity versus low/medium;
- `required_specialty`: technical, legal, risk, security, and none;
- `customer_segment`: including proxies for language, regional accommodation, or vulnerability if available;
- `priority`;
- `local_expertise_flag`;
- `handover_reason`;
- staffing/absence periods and demand peaks.

## Guardrail metrics

Do not judge the pilot by average cycle time alone. Set guardrails before launch.

| Area | Guardrail examples |
|---|---|
| Queueing | P90/P95 technical and approval waiting time must not exceed baseline local-specialist waits by a pre-agreed tolerance; queue-aging threshold breaches trigger review. |
| Complex work | High-complexity SLA miss rate must not worsen relative to matched baseline/control cases. |
| Quality | Rework after technical review, approval, or quality check must not exceed baseline/control by a defined margin. |
| Fairness | No material worsening in P90 wait, SLA miss, rework, or outcome quality for any team or customer segment after adjustment for complexity and priority. |
| East benefit | East should show measurable relief in technical waits or high-complexity cycle-time tail; otherwise pooling is not solving its primary starting problem. |
| North/South protection | North/South must not show deterioration in complex-case tail performance or regional-accommodation outcomes. |
| Role clarity | Reassignment counts, “clarification” handovers, and staff-reported ownership ambiguity must remain below thresholds. |
| Resilience | Pilot must include a controlled peak-volume or absence-period review; performance cannot be assessed only in steady-state weeks. |
| Capacity | Legal/Risk utilization and queue wait must remain within safe operating bounds before adding more work to those queues. |

## Staff feedback collection

Collect both structured and qualitative evidence:

- Weekly short pulse survey for local caseworkers, supervisors, shared-service specialists, and quality staff.
- Questions on:
  - clarity of case ownership;
  - adequacy of handoff information;
  - ability to obtain timely technical advice;
  - local learning opportunities;
  - frequency of workarounds or unofficial escalation;
  - perceived impact on customers with regional/language needs.
- Run case-review sessions for:
  - high-complexity SLA misses;
  - repeated handoff loops;
  - rework after centralized advice;
  - complaints or adverse outcomes.
- Treat recurring qualitative themes as process evidence, even if they are not fully represented in the event log.

## Rollback or adjustment triggers

Pause, narrow, or reverse the pilot if any of the following persists for more than a defined review period:

- P90/P95 shared-service wait rises above guardrails;
- high-complexity or specialty-case SLA misses materially worsen;
- rework after shared technical review or shared approval rises materially;
- North/South lose performance while East gains only marginally;
- a customer segment experiences statistically and operationally meaningful worse wait, rework, or outcomes;
- reassignment and repeated referral loops rise sharply;
- Legal/Risk queue utilization or queue aging indicates saturation;
- staff report persistent unclear ownership or inability to resolve customer-facing issues;
- a stress event demonstrates that the central queue is a single point of failure.

Adjustment options include adding specialist capacity, separating legal/risk from technical queues, reintroducing local rapid-consultation capacity, changing routing thresholds, reserving queue capacity for high-priority complex cases, or delaying shared approval centralization.

# 6. Recommendation

**Recommendation: modify the design and pilot it in phases before any full rollout.**

The proposal has plausible benefits:

- East is likely to benefit from pooled technical capacity because E_Tech is already at 82% utilization and East has the slowest median and tail cycle times.
- Standardized routing and approvals may reduce avoidable variation.
- Cross-team absence cover may improve if the shared service is staffed and managed as a true capacity pool.

However, the proposed design combines several high-risk changes at once:

- technical centralization;
- legal/risk routing expansion despite Legal/Risk already being near capacity;
- difficult quality-check centralization;
- shared approval;
- removal of local supervisory capacity.

That combination makes it difficult to determine whether a deterioration comes from technical queues, approval queues, legal/risk scarcity, lost local expertise, or unclear ownership. It also risks converting East’s local bottleneck into an organization-wide bottleneck.

Management should proceed only if it adopts the following conditions:

1. **Pilot technical pooling before centralizing all related functions.**
2. **Keep Legal/Risk capacity separate and explicitly protected** until demand, utilization, and queue-tail evidence show that additional routing volume is sustainable.
3. **Preserve a local rapid-consultation and escalation path** for high-context, regional, language-sensitive, or urgent cases during the transition.
4. **Define end-to-end ownership explicitly:** local caseworker ownership of the customer/case, shared-service accountability for advice turnaround and quality, and clear approval decision rights.
5. **Use distributional and fairness guardrails:** P90/P95 waiting time, high-complexity SLA misses, rework, reassignment loops, team-level differences, and customer-segment differences.
6. **Evaluate East, North, and South separately.** Success in East cannot justify a rollout if North/South lose the local expertise that currently supports strong performance.
7. **Treat utilization cautiously.** A 15% utilization increase is not inherently a gain if it creates saturation, long queue tails, or reduced resilience.

Management should **not** infer success from an early reduction in average cycle time, a lower direct handover count, or fewer cross-team transfers. Those results can occur while difficult cases wait longer, local capability erodes, accountability fragments, or disadvantaged customer segments experience worse service. Full rollout should require evidence that the shared model improves or at least protects tail performance, quality, fairness, and resilience—not merely average throughput.

```python
"""
Illustrative PM4Py-style analysis sketch.

Assumptions:
- before_df and after_df are pandas DataFrames with columns:
  case:concept:name, concept:name, time:timestamp, org:resource,

- Exact return types and parameter names can vary by PM4Py version.
  The sketch shows the intended analysis logic.

import pandas as pd
import numpy as np
import pm4py

CASE_ID = "case:concept:name"
ACTIVITY = "concept:name"
TIMESTAMP = "time:timestamp"
RESOURCE = "org:resource"

# -------------------------------------------------------------------
# 1. Preparation and basic case-level features
# -------------------------------------------------------------------

def prepare_log(df: pd.DataFrame) -> pd.DataFrame:
    df = df.copy()
    df[TIMESTAMP] = pd.to_datetime(df[TIMESTAMP], utc=True, errors="coerce")
    df = df.dropna(subset=[CASE_ID, ACTIVITY, TIMESTAMP])
    df = df.sort_values([CASE_ID, TIMESTAMP])

    # PM4Py dataframe formatting
    df = pm4py.format_dataframe(
        df,
        case_id=CASE_ID,
        activity_key=ACTIVITY,
        timestamp_key=TIMESTAMP
    )

    # Optional: normalize categories so before/after comparisons are consistent
    for col in [
        "team", "location", "required_specialty", "priority",
        "case_complexity", "customer_segment", "handover_reason",
        "local_expertise_flag"
    ]:
        if col in df.columns:
            df[col] = df[col].fillna("UNKNOWN").astype(str)

    return df


before = prepare_log(before_df)
after = prepare_log(after_df)


def add_case_cycle_time(df: pd.DataFrame) -> pd.DataFrame:
    """Add case start/end/cycle duration in hours to each event row."""
    x = df.copy()
    case_times = (
        x.groupby(CASE_ID)[TIMESTAMP]
        .agg(case_start="min", case_end="max")
        .reset_index()
    )
    case_times["cycle_hours"] = (
        case_times["case_end"] - case_times["case_start"]
    ).dt.total_seconds() / 3600.0
    return x.merge(case_times, on=CASE_ID, how="left")


before = add_case_cycle_time(before)
after = add_case_cycle_time(after)

# If SLA policy is known, attach SLA hours by priority or another policy table.
sla_map = {
    "high": 72,
    "medium": 120,
    "low": 240,
}
for df in [before, after]:
    df["sla_hours"] = df["priority"].str.lower().map(sla_map).fillna(120)
    df["sla_miss"] = df["cycle_hours"] > df["sla_hours"]


# -------------------------------------------------------------------
# 2. Segmentation helper
# -------------------------------------------------------------------

def segment(df, team=None, complexity=None, specialty=None, customer_segment=None):
    """Filter while keeping PM4Py-compatible dataframe structure."""
    out = df.copy()

    if team is not None:
        out = pm4py.filter_event_attribute_values(
            out, "team", {team}, level="event", retain=True
        )

    if complexity is not None:
        out = pm4py.filter_event_attribute_values(
            out, "case_complexity", {complexity}, level="event", retain=True
        )

    if specialty is not None:
        out = pm4py.filter_event_attribute_values(
            out, "required_specialty", {specialty}, level="event", retain=True
        )

    if customer_segment is not None:
        out = pm4py.filter_event_attribute_values(
            out, "customer_segment", {customer_segment}, level="event", retain=True
        )

    return out

def handover_edge_table(df):
    """
    Explicit directly-follows resource handover table.
    Useful where a shared queue is represented as an activity/resource
    and one needs transparent edge counts and waiting times.
    """
    x = df.sort_values([CASE_ID, TIMESTAMP]).copy()

    x["next_resource"] = x.groupby(CASE_ID)[RESOURCE].shift(-1)
    x["next_activity"] = x.groupby(CASE_ID)[ACTIVITY].shift(-1)
    x["next_timestamp"] = x.groupby(CASE_ID)[TIMESTAMP].shift(-1)

    x["wait_after_event_hours"] = (
        x["next_timestamp"] - x[TIMESTAMP]
    ).dt.total_seconds() / 3600.0

    edges = x.dropna(subset=["next_resource"]).copy()
    edges = edges[edges[RESOURCE] != edges["next_resource"]]

    out = (
        edges.groupby([RESOURCE, "next_resource"])
        .agg(
            handover_count=(CASE_ID, "size"),
            median_wait_hours=("wait_after_event_hours", "median"),
            p90_wait_hours=("wait_after_event_hours",
                            lambda s: np.nanquantile(s.dropna(), 0.90)
                            if len(s.dropna()) else np.nan),
            unique_cases=(CASE_ID, "nunique")
        )
        .reset_index()
        .sort_values("handover_count", ascending=False)
    )
    return out


before_handover_edges = handover_edge_table(before)
after_handover_edges = handover_edge_table(after)

# Queue-specific waiting time:
# If explicit events exist, e.g. "Technical Shared Queue Enter" and
# "Specialist Review Start", calculate the elapsed time between them.
def activity_transition_waits(df, from_activity, to_activity):
    x = df.sort_values([CASE_ID, TIMESTAMP]).copy()
    x["next_activity"] = x.groupby(CASE_ID)[ACTIVITY].shift(-1)
    x["next_time"] = x.groupby(CASE_ID)[TIMESTAMP].shift(-1)

    transitions = x[
        (x[ACTIVITY] == from_activity) &
        (x["next_activity"] == to_activity)
    ].copy()

    transitions["wait_hours"] = (
        transitions["next_time"] - transitions[TIMESTAMP]
    ).dt.total_seconds() / 3600.0

    return transitions

def quantile_summary(series):
    s = pd.Series(series).dropna()
    if len(s) == 0:
        return {}
    return {
        "n": len(s),
        "mean": s.mean(),
        "p50": s.quantile(0.50),
        "p90": s.quantile(0.90),
        "p95": s.quantile(0.95),
        "max": s.max()
    }

def rework_analysis(df):
    # PM4Py helper identifies cases/activities with rework patterns.
    rework_per_activity = pm4py.get_rework_cases_per_activity(
        df,
        activity_key=ACTIVITY,
        case_id_key=CASE_ID
    )

    # Event-log flag-based rate:
    rework_by_group = (
        df.groupby(["team", "case_complexity", "required_specialty"])
        .agg(
            cases=(CASE_ID, "nunique"),
            flagged_rework=("rework_flag", "mean")
        )
        .reset_index()
    )

    # Repeat activity count within case:
    event_counts = (
        df.groupby([CASE_ID, ACTIVITY])
        .size()
        .reset_index(name="activity_visits")
    )
    repeated = event_counts[event_counts["activity_visits"] > 1]

    return rework_per_activity, rework_by_group, repeated
```
