## 1. Analytical assumptions

I treat a **case notion** as the object type whose instances become cases after flattening. If flattening is performed on `Order`, each order (`O1`–`O4`) becomes a case; if flattening is performed on `Package`, each package (`P1`–`P4`) becomes a case. I use only the supplied direct event–object relations as the default evidence base. I do **not** silently propagate relations through object–object edges.

I interpret **convergence** as the analytical effect in which distinct business objects or cases are forced to share the same event, case node, or lifecycle fragment after flattening. Examples are `e13` being copied into both `O2` and `O3`, or `D2` hiding the fact that one delivery serves several orders. I interpret **divergence** as the opposite effect: one logical business transaction is split into multiple cases, repeated events, or parallel-looking branches. Examples are `O1` being split across `P1` and `P2`, or `V2` being settled by two payment events, `e22` and `e25`.

Copied shared events are treated as **both evidence and duplication**. They are evidence that a given object participated in an activity. For example, `e16` is valid evidence that `O1`, `O2`, and `O3` were all affected by the same dispatch. However, if the three case copies of `e16` are counted as three independent dispatches, the flattening duplicates the same operational fact. Therefore, unique event identifiers should be used for operational frequency, while case copies should be used only for case-perspective analysis.

I would permit analytical transformations only when made explicit. These include: propagating relations through O2O links as a sensitivity variant; enriching `Record Payment` with the payment relation qualifier, so that `M2` and `M3` are not treated as indistinguishable repetitions; and down-weighting shared events that are copied into multiple cases.

## 3. Concrete distortion analysis

1. **Cross-order package `P3` duplicated in Order flattening**  
   Affected flattening: `Order`. Event `e13` (`Pack Package`) is directly related to `O2` and `O3`. When flattened by order, `e13` is copied into both order cases. The DFG may show two independent `Add Item -> Pack Package` transitions, one for `O2` and one for `O3`, inflating packing frequency. This hides the fact that one physical package was packed once for two orders. The effect is **harmful** for capacity and cost analysis, but **informative** for order-status tracking.

2. **Cross-order package `P4` hidden in Package flattening**  
   Affected flattening: `Package`. `P4` has events `e14`, `e17`, and `e27`. As a package case, it appears as a simple `Pack Package -> Dispatch -> Confirm Delivery` lifecycle. However, `e14` is directly related to `O3`, `O4`, `I32`, and `I41`. The package view hides that one package affects two orders. This is **informative** for package handling but **harmful** if the analyst wants to know how many orders are impacted by a delay to `P4`.

3. **Cross-order package `P3` convergence in Item flattening**  
   Affected flattening: `Item`. Event `e13` is copied into both `I21` and `I31`. The item DFG may show two item cases converging on the same packing event. This is useful for identifying consolidation, but if case copies are counted independently, the packing activity is overrepresented. The effect is **context-dependent**: good for item traceability, misleading for activity frequency.

4. **Consolidated delivery `D2` in Delivery flattening**  
   Affected flattening: `Delivery`. `D2` contains only `e16` and `e24`. The delivery case looks like a simple two-step lifecycle. However, `e16` and `e24` also involve `O1`, `O2`, `O3`, `I12`, `I21`, `I31`, `P2`, and `P3`. The delivery view hides that one transport leg serves three orders and two packages. If dispatch-to-confirmation time from `e16` to `e24` is used as an order-level KPI, it may incorrectly suggest that all three orders experienced the same delivery performance. This is **informative** for carrier performance but **harmful** for order-level SLA analysis.

5. **Consolidated invoice `V2` in Order flattening**  
   Affected flattening: `Order`. Events `e19`, `e22`, and `e25` are copied into both `O2` and `O3` because `V2` bills both orders. The order DFG may show `Issue Invoice` and `Record Payment` occurring once per order, making billing effort appear doubled. In reality, one invoice was issued and one invoice was partially settled and later completed. This is **harmful** for accounting workload analysis but **informative** for showing that both orders reached financial settlement.

6. **Partial payments on invoice `V2` in Invoice flattening**  
   Affected flattening: `Invoice`. `V2` has `e19` (`Issue Invoice`), `e22` (`Record Payment` for `M2`), and `e25` (`Record Payment` for `M3`). Because both payment events have the same activity label, the flattened invoice log may show `Issue Invoice -> Record Payment -> Record Payment`. This can be interpreted as duplicate payment, payment rework, or a long-delayed second payment. The interval from `e22` to `e25` is substantial, so performance analysis may show a long settlement tail. The effect is **context-dependent**: it is informative if instalments are legitimate, harmful if the two payments are mistakenly treated as errors.

7. **Near-singleton lifecycle in Payment flattening**  
   Affected flattening: `Payment`. Each payment object has only one directly related event: `M1` with `e21`, `M2` with `e22`, `M3` with `e25`, `M4` with `e26`. The resulting cases are single-event cases. DFG discovery and log skeleton discovery become degenerate. The partial-payment relationship between `M2` and `M3` is visible only through their shared relation to `V2`, not through the payment case sequence. This is **harmful** for process discovery but can still be useful for counting payment events.

8. **Order `O1` split across `P1` and `P2` in Order flattening**  
   Affected flattening: `Order`. `O1` has two pack events (`e11`, `e12`), two dispatch events (`e15`, `e16`), and two confirmation events (`e23`, `e24`). The order case may look like repeated or parallel logistics steps. This is **informative** because `O1` is genuinely split, but **harmful** if the repeated activities are interpreted as rework rather than split fulfilment.

9. **Order `O3` receiving multiple confirmations in Order flattening**  
   Affected flattening: `Order`. `O3` participates in `e24` through `P2`/`P3`/`D2` and in `e27` through `P4`/`D3`. The order case therefore contains two `Confirm Delivery` events before `Close Order` at `e30`. If an analyst defines order completion at the first confirmation, `O3` may appear complete at `e24`; if completion requires all items, completion is only after `e27`. This is **context-dependent** and can create performance bias in order lead time.

10. **Shared dispatch `e16` in Package flattening**  
   Affected flattening: `Package`. Event `e16` is copied into both `P2` and `P3`. The package DFG may count one operational dispatch as two package-level dispatch transitions. This inflates edge frequency if case copies are treated as independent events. The effect is **harmful** for unique-event frequency analysis but **informative** for understanding how many packages were affected by one dispatch.

## 4. Traditional versus object-centric analysis portfolio

I would still create several flattened logs, but each should be used only for questions that match its case notion.

The **Order flattening** should be created because it is the best available view for order accountability. It can safely answer: when was each order created, when were items added, when did the order receive dispatch/confirmation events, when was it invoiced or payment-related, and when was it closed? It can also show split fulfilment for `O1` and multi-branch fulfilment for `O3`. It should not be used to count unique packing, dispatch, invoicing, or payment operations without de-duplicating event identifiers.

The **Package flattening** should be created for warehouse and transport execution questions. It can safely answer: how long from pack to dispatch to confirmation for `P1`–`P4`? It can also show that `P2` and `P3` share `e16` and `e24`. It should not be used to infer order lead times or financial settlement.

The **Invoice flattening** should be created for accounts-receivable questions. It can safely answer: how long from invoice issue to settlement, and whether an invoice has one or more payment events? It is especially useful for `V2`, where `e22` and `e25` show partial and completing settlement. It should not be used to infer whether goods were delivered.

The **Delivery flattening** should be created only for transport-leg performance. It can answer dispatch-to-confirmation duration for `D1`, `D2`, and `D3`. It should not be used for order or item lead times because it hides upstream steps and consolidation content.

The **Item flattening** is useful for item traceability and for detecting physical convergence, such as `I21` and `I31` sharing `e13`. It should not be treated as an end-to-end business case because item cases stop at delivery confirmation and lack invoice/payment/close events.

The **Payment flattening** should generally not be used for process discovery. It is too fragmented. Payment objects should instead be treated as financial events linked to invoices and orders.

Object-centric techniques are required for questions that cross object types. An **OC-DFG** is needed to show how orders, items, packages, deliveries, invoices, and payments interact without forcing one case notion. An **OTG** is useful to identify type-level relationships, such as multiple orders converging on one invoice or one delivery. An **ET–OT graph** or event-to-object-type graph is useful to identify activities that touch many object types, such as `e16`, which touches three orders, three items, two packages, and one delivery. An **object interaction summary** is needed to identify multi-object events such as `e13`, `e14`, `e16`, `e19`, `e22`, `e24`, and `e25`. Equivalent-execution clustering may be used cautiously for order-centric pattern discovery, but only after acknowledging that shared events can make different orders look similar.

Contradictions should be reconciled by asking which object type owns the KPI. If order flattening shows many `Record Payment` events but invoice flattening shows fewer invoices, the invoice view should dominate for billing workload. If package flattening shows short pack-to-confirm times but order flattening shows long order lead times, the difference should be attributed to pre-packing, post-delivery, or financial closure time. The object-centric view should be used to locate the shared events causing the discrepancy.

## 5. Lead-object decision

**Position: B. Use a primary lead object plus explicitly secondary lifecycles.**

I select **Order** as the primary lead object, but only with explicit secondary lifecycles for `Package`, `Delivery`, `Invoice`, and `Payment`. I do not claim that Order is the only correct case notion. Rather, it is the most defensible primary view for end-to-end accountability.

**Decision criteria.** The lead object should have: end-to-end lifecycle coverage; business accountability; direct participation in both physical and financial events; and enough specificity to support order-level compliance. It should also allow secondary views to correct many-to-many distortions.

**Strongest supporting evidence.** Only order instances have direct events from creation to closure. `O1` includes `e01`, `e05`, `e06`, `e11`, `e12`, `e15`, `e16`, `e18`, `e21`, `e23`, `e24`, and `e28`. `O2` includes `e02`, `e07`, `e13`, `e16`, `e19`, `e22`, `e24`, `e25`, and `e29`. `O3` and `O4` similarly connect creation, item addition, logistics, invoicing/payment where applicable, and closure. This makes Order the strongest single object for asking whether a customer request was fulfilled.

**Strongest counterargument.** Order flattening duplicates shared events and can therefore distort operational frequency. For example, `e16` is copied into `O1`, `O2`, and `O3`; `e19`, `e22`, and `e25` are copied into `O2` and `O3`. If these copies are counted as independent activities, the log overstates dispatch, invoicing, and payment work. Also, `V2` cannot be cleanly split between `O2` and `O3` without additional allocation rules.

**Residual risk.** Even with secondary lifecycles, analysts may accidentally treat order-case copies as independent operational events. They may also infer that `O2` and `O3` are independently paid when in fact they share one invoice and one settlement sequence. Another risk is that order-centric clustering may group orders together because they share consolidation events rather than because their underlying processes are truly similar.

**Conditions for changing the decision.** If the primary question is warehouse throughput, `Package` should become the lead object. If the question is carrier performance, `Delivery` should lead. If the question is accounts receivable, `Invoice` should lead. If payment allocation or instalment management becomes central and richer payment attributes are available, a payment/invoice hybrid may be preferable. If shared events dominate the log and orders cannot be meaningfully separated, I would reject a primary order lead and move fully to object-centric analysis.

## 7. Sensitivity and validation plan

First, I would compare **case-copy counts against unique event counts**. For each flattened log, shared events such as `e13`, `e14`, `e16`, `e19`, `e22`, `e24`, and `e25` should be identified. A variant should be created in which shared events are down-weighted or counted once per unique event identifier. If the DFG changes substantially, the original flattened frequencies are driven by duplication rather than by additional operational work.

Second, I would compare **direct E2O relations with an explicitly propagated-relation variant**. For example, order closure could be propagated from `O1` to `I11` and `I12` through `contains`, or invoice events could be propagated from `O2`/`O3` to their items. This would test whether item lifecycles become meaningfully more complete or whether propagation merely invents artificial participation. Propagation should never be used silently.

Third, I would **change the lead object** and compare the resulting KPIs. For example, order lead time for `O3` from `e03` to `e30` should be compared with package lifecycle for `P3` from `e13` to `e24`, invoice lifecycle for `V2` from `e19` to `e25`, and delivery lifecycle for `D2` from `e16` to `e24`. Contradictions should be interpreted as evidence of different case notions, not as errors in the data.

Fourth, I would compare **frequency metrics based on event copies, unique events, and object counts in the OC-DFG**. For example, `e16` appears once as a unique event, twice in package flattening because of `P2` and `P3`, three times in order flattening because of `O1`, `O2`, and `O3`, and once in delivery flattening because of `D2`. These differences must be reconciled before making frequency claims.

Fifth, I would validate **lifecycle completeness**. Order cases should normally start with `Create Order` and end with `Close Order`. Package cases should start with `Pack Package` and end with `Confirm Delivery`. Invoice cases should start with `Issue Invoice` and end with a settlement event. Payment cases should be expected to be singleton cases in this snapshot. Any algorithm that treats these different lifecycle lengths as comparable needs explicit normalization.

Sixth, I would test the effect of **payment qualifier enrichment**. The activity label `Record Payment` hides the difference between `M2` (`partially_settles`) and `M3` (`completes_settlement`). If the labels are changed to `Record Partial Payment` and `Record Completing Payment`, the invoice DFG and log skeleton may change from an apparent repeated-payment pattern to a legitimate instalment pattern. This check is important because the distortion is semantic, not merely structural.
