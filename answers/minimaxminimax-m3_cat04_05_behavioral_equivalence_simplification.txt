# 1. Equivalence Notions

For this comparison, I define the following notions precisely. Throughout, `vis()` denotes the projection of trace `` onto visible labels (everything except `tau`), preserving order but **collapsing duplicates only when explicitly stated**.

| Notion | Definition (precise) |
|---|---|
| **Visible trace equivalence (VTE)** | Two models are VTE iff their sets of visible traces are equal: `{ vis() :   runs(M) } = { vis() :   runs(N) }`. Duplicate visible labels are distinguished by **occurrence position** (an `Analyze Revision` after a `Rework Case` is different from the one before). `tau` is hidden; everything else is retained in order. |
| **Bounded visible-language equivalence (P3-BVE)** | Two models are P3-BVE iff their sets of visible traces of length  12 and with at most 3 `Analyze Revision` occurrences are equal. This is **evidence**, not proof. |
| **Business equivalence under P1 (P1-BE)** | Two models are P1-BE iff, after hiding `tau`, every maximal run satisfies: (i) exactly one `Open Case` first, (ii) every `Analyze Revision` is followed by a `Check Revision` before any subsequent `Rework Case` or `Close Case`, (iii) `Rework Case` separates two `Analyze Revision` occurrences, (iv) at least one `Approve Revision` is allowed, with placement visible, (v) `Close Case` is last and unique. |
| **Dashboard equivalence under P2 (P2-DE)** | Two models are P2-DE iff their P2 abstractions match. The P2 abstraction of a visible trace `` is a tuple `(n_check, n_analyze, rework_occurred)` where `n_check = min(1, #Check Revision in )`, `n_analyze = #Analyze Revision in `, `rework_occurred = (#Rework Case in   1)`. `Approve Revision` and `tau` are hidden. Order between `Check` and `Analyze` inside a single iteration is collapsed. |

**Identity of duplicate labels.** Two occurrences of the same label (e.g., two `Analyze Revision`s) are distinguished by **occurrence position only**: their order in the trace matters, but no other identifier. In P2 the position information is intentionally discarded.

**Why these distinctions matter.** The models differ structurally in *where* `Check Revision` sits relative to the loop: inside it (Model A) versus concurrent with it (Model B). P1 cares about that placement; P2 erases it; P3 only inspects a bounded window of the language.

# 2. Structural Comparison

| Feature | Model A | Model B | Semantic consequence |
|---|---|---|---|
| Loop scope | `*(...)` is the outer construct; `Check Revision` is inside the loop body, paired with `Analyze Revision` via `+`. | `Check Revision` is **outside** the `*` loop, concurrent with the entire loop block. | In A, a `Check Revision` occurs once per iteration, always after an `Analyze Revision`. In B, exactly **one** `Check Revision` may fire, at any time during the loop, possibly before any `Analyze Revision`. |
| Min `Check Revision` occurrences | 1 (the `+` is inside the loop body, which the binary-loop semantics executes at least once). | 1 (top-level `+` requires both children to run at least once). | Both guarantee  1 check. |
| Max `Check Revision` occurrences | Unbounded: every loop iteration produces one. With `k` `Analyze Revision` occurrences there are exactly `k` `Check Revision`s, all interleaved after each analyze. | **At most 1**. The `+` produces one `Check Revision` per run. | **Decisive structural difference.** |
| Placement of `Check Revision` | Strictly after the corresponding `Analyze Revision` in the same iteration, before the iteration’s optional `Approve Revision`/`tau`. | Anywhere: before the first `Analyze Revision`, between iterations, or after the last `Rework Case`. | Placement carries business meaning only under P1. |
| Optional `Approve Revision` | Inside each iteration, paired with `tau` via `X`. Visible per iteration. | Inside each iteration, paired with `tau` via `X`. Visible per iteration. | Same semantics in both. Hidden under P2. |
| Concurrency | None — fully sequential. | `+('Check Revision', * (loop))` models **true concurrency** between the single check and the loop body. | B can interleave the single `Check Revision` arbitrarily with the loop steps. |
| Join before `Close Case` | The outer `*` must complete (decide to exit), then `Close Case`. | The `+` must complete (check must fire and loop must exit), then `Close Case`. | Same join requirement, but B also requires the check to have fired. |
| Soundness | The model is sound (each activity appears, no dead branches). | The model is sound (the `+` always completes both sides, and `tau` handles the choice). | Both pass soundness; the difference is in the *language*, not in liveness. |

# 3. Verdicts

| View | Verdict | Confidence | Decisive reason | Caveat |
|---|---|---|---|---|
| **P1 (operational compliance)** | **not equivalent** | High | Model A produces one `Check Revision` per `Analyze Revision`; Model B produces exactly one `Check Revision` regardless of how many revisions occur. P1 requires *every* analysis to be checked. | If one accepts a single check after the last iteration as compliant, A and B can be reconciled — but that is *not* P1 as stated. |
| **P2 (executive dashboard)** | **equivalent** | High | Under the P2 abstraction, both models yield the same family of tuples `(n_check{1}, n_analyze1, rework_occurred{0,1})`. The interleaving of check/analyze is collapsed; the cap of 1 on `Check Revision` in B does not change the Boolean fact. | The mapping is many-to-one in both directions, so it can absorb the difference without losing dashboard-relevant information. |
| **P3 (bounded testing)** | **not equivalent under the stated bound** | High | Within 3 `Analyze Revision` occurrences the bound `k=3` already reveals a trace unique to A: `Open, Analyze, Check, Approve, Rework, Analyze, Check, Approve, Rework, Analyze, Check, Approve, Close` has 3 checks; B cannot produce 3 checks. | Bounded comparison is evidence only. Increasing the bound cannot make the languages equal — the asymmetry is unbounded. |
| **Unbounded VTE** | **not equivalent** | High | Trace `<Open, Analyze, Check, Rework, Analyze, Check, Close>` (2 checks) is in A but not B. Trace `<Open, Check, Analyze, Rework, Analyze, Close>` (check first) is in B but not A. | See §4. |

# 4. Counterexample Traces

Notation: each token is a visible event; `tau` is omitted.

| Trace ID | Trace | Model A | Model B | First decisive semantic difference | Relevant view |
|---|---|---|---|---|---|
| **A1** | `Open, Analyze, Check, Rework, Analyze, Check, Close` |  admitted |  rejected | After the second `Analyze`, B has no second `Check Revision` available (its `+` already fired). | P1, VTE |
| **A2** | `Open, Analyze, Check, Approve, Rework, Analyze, Check, Approve, Rework, Analyze, Check, Approve, Close` (3 iterations, 3 checks, 3 approves) |  admitted |  rejected | B’s `+` permits exactly one `Check Revision`; cannot produce three. | P1, P3 |
| **B1** | `Open, Check, Analyze, Approve, Rework, Analyze, Approve, Close` |  rejected |  admitted | A’s loop body is `+(Analyze, Check)`  `X(Approve, tau)`; the `+` forces `Analyze` before `Check`. A cannot emit `Check` before any `Analyze`. | P1, VTE |
| **B2** | `Open, Analyze, Approve, Rework, Check, Analyze, Approve, Close` (check fired *between* iterations, after a `Rework`) |  rejected |  admitted | A’s check is bound to the iteration that contains the corresponding `Analyze`. A `Check` after `Rework` with no preceding `Analyze` in the current iteration is impossible. | P1, VTE |

**How optional Approve Revision and hidden `tau` affect the verdict.** `Approve Revision` is hidden under P2 and under the dashboard abstraction, so traces A1/B1/B2 already illustrate that the asymmetry survives after hiding it. `tau` participates in two places: (a) inside the `X(Approve, tau)`, allowing the silent skip when no approval is needed; (b) absent from the `+` operator itself. Hiding `tau` does **not** collapse the difference between A and B — the difference is in the **count** and **placement** of visible `Check Revision` events, which `tau` cannot erase.

**Trace with two analysis attempts (required).** Trace **A1** contains two `Analyze Revision` occurrences separated by one `Rework Case`, plus two `Check Revision`s. It is admitted by A and rejected by B. This single trace already disproves VTE and P1-BE.

**Inclusion claim.** There is no inclusion direction in general: A  B (trace A1) and B  A (trace B1). Both languages are infinite (unbounded loop) and incomparable.

# 5. Bounded Comparison Code

The code below parses both trees, converts them to Petri nets, checks soundness, performs an **exhaustive** breadth-first exploration over markings up to the P3 bound (12 visible events, 3 `Analyze Revision` occurrences), and reports traces unique to each model. A second pass uses `play_out` to illustrate that playout is *not* exhaustive (it samples one trace from the initial marking and stops).

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking
from collections import deque

VISIBLE_MAX = 12
ANALYZE_MAX = 3

def visible_proj(trace):
    return tuple(t for t in trace if t != "tau")

def violates_p3(vis):
    if len(vis) > VISIBLE_MAX:
        return True
    if vis.count("Analyze Revision") > ANALYZE_MAX:
        return True
    return False

def enumerate_traces_bfs(net, im, fm):
    """Exhaustive BFS over markings, bounded by VISIBLE_MAX visible events
    and ANALYZE_MAX Analyze Revision occurrences."""
    seen_markings = {}
    results = set()
    queue = deque()
    queue.append((im, ()))
    while queue:
        marking, vis = queue.popleft()
        if violates_p3(vis):
            continue
        key = (tuple(sorted(marking.items())), vis)
        if key in seen_markings:
            continue
        seen_markings[key] = True
        if marking == fm:
            results.add(vis)
            continue
        enabled = pm4py.get_enabled_transitions(net, marking)
        progress = True
        for t in enabled:
            label = t.label
            new_marking = marking.copy()
            for a in t.out_arcs:
                if a.source == t:
                    new_marking[a.target] = new_marking.get(a.target, 0) + 1
                else:
                    new_marking[a.target] = new_marking.get(a.target, 0) - 1
            new_marking = Marking(dict((k, v) for k, v in new_marking.items() if v > 0))
            if label == "tau":
                queue.append((new_marking, vis))
            else:
                new_vis = vis + (label,)
                if not violates_p3(new_vis):
                    queue.append((new_marking, new_vis))
        if not enabled:
            # dead non-final marking: still record if it leads to no progress;
            # we drop it (soundness guarantees final is reachable for legal models).
            pass
    return results

# --- Parse trees ---
tree_A_str = ("->( 'Open Case', "
              "*( ->( +('Analyze Revision','Check Revision'), "
                   "X('Approve Revision', tau) ), "
              "'Rework Case' ), 'Close Case' )")

tree_B_str = ("->( 'Open Case', "
              "+( 'Check Revision', "
              "*( ->( 'Analyze Revision', X('Approve Revision', tau) ), "
              "'Rework Case' ) ), 'Close Case' )")

tree_A = pm4py.parse_process_tree(tree_A_str)
tree_B = pm4py.parse_process_tree(tree_B_str)

netA, imA, fmA = pm4py.convert_to_petri_net(tree_A)
netB, imB, fmB = pm4py.convert_to_petri_net(tree_B)

print("Soundness A:", pm4py.check_soundness(netA, imA, fmA, print_diagnostics=False))
print("Soundness B:", pm4py.check_soundness(netB, imB, fmB, print_diagnostics=False))

lang_A = enumerate_traces_bfs(netA, imA, fmA)
lang_B = enumerate_traces_bfs(netB, imB, fmB)

only_A = sorted(lang_A - lang_B)
only_B = sorted(lang_B - lang_A)

print(f"\n#traces A (bounded): {len(lang_A)}")
print(f"#traces B (bounded): {len(lang_B)}")
print(f"#unique to A: {len(only_A)}")
print(f"#unique to B: {len(only_B)}")
print("\nFirst 5 unique to A:")
for t in only_A[:5]:
    print(" ", t)
print("\nFirst 5 unique to B:")
for t in only_B[:5]:
    print(" ", t)

# --- Non-exhaustive playout (for contrast) ---
play_A = pm4py.play_out(tree_A)
play_B = pm4py.play_out(tree_B)
print("\nplay_out A (single sample):", tuple(play_A))
print("play_out B (single sample):", tuple(play_B))
```

**What is exhaustive vs. heuristic.**
- `enumerate_traces_bfs` is **exhaustive under the P3 bound**: it explores every reachable marking reachable by traces respecting the bound, deduplicates by `(marking, visible-prefix)`, and continues silent transitions without consuming a visible step. The bound is enforced *eagerly* on the prefix, which guarantees soundness of the comparison up to the bound.
- `pm4py.play_out` performs a **single stochastic/heuristic play-out** per call. It is *not* exhaustive; one call yields one trace. It is included here only to demonstrate the contrast.

# 6. Stochastic and Footprint Comparison

These tools add evidence but cannot establish VTE, because they collapse causal/interleaving distinctions.

**Footprints.** `pm4py.discover_footprints(net)` returns a `(footprints, output)` pair. Equal footprints imply that the two models have the same activity-on-activity relations: which activities can directly follow which, and which can be in parallel. They **do not** capture count bounds or scope of a label across iterations. Two models with the same footprint can still differ in language.

```python
fpA = pm4py.discover_footprints(tree_A)
fpB = pm4py.discover_footprints(tree_B)
print("Footprints equal:", fpA[0] == fpB[0])
```

**Why equal footprints are weak evidence here.** Even if `fpA == fpB`, the cardinality of `Check Revision` per run differs (unbounded in A vs. 1 in B). Footprints cannot distinguish those.

**Stochastic language + EMD.** `pm4py.get_stochastic_language(tree, no_traces=N)` produces `(trace, probability)` pairs by Monte-Carlo playout. `pm4py.compute_emd(lang1, lang2)` returns an Earth Mover's Distance over a cost derived from trace distance. Without declared transition probabilities, the result is an estimate under whatever default stochastic semantics pm4py uses (typically uniform choice). Equal distributions under uniform choice would *suggest* the languages are similar in mass, but:

- stochastic language is a sampled distribution, not the language itself;
- uniform-choice EMD weights trace-length differences heavily and is insensitive to *which* positions labels appear in;
- even an EMD of 0 would not prove VTE (it would only mean the sampled distributions match).

```python
langA_stoch = pm4py.get_stochastic_language(tree_A, no_traces=2000)
langB_stoch = pm4py.get_stochastic_language(tree_B, no_traces=2000)
print("EMD (sampled, default):", pm4py.compute_emd(langA_stoch, langB_stoch))
```

A more informative experiment: assign non-uniform probabilities to the `X(Approve, tau)` branches (e.g., `P(Approve)=0.6`, `P(tau)=0.4`) — but **only as a declared assumption**, and recognize that the conclusion remains statistical, not formal.

# 7. Complexity Comparison

```python
import pm4py

def count_nodes(node):
    """Count nodes in a process tree (operator + leaves)."""
    if node.children:
        return 1 + sum(count_nodes(c) for c in node.children)
    return 1

def tree_depth(node):
    if not node.children:
        return 1
    return 1 + max(tree_depth(c) for c in node.children)

def leaves_by_label(node, acc):
    if not node.children:
        acc[node.label] = acc.get(node.label, 0) + 1
        return acc
    for c in node.children:
        leaves_by_label(c, acc)
    return acc

for name, t in [("A", tree_A), ("B", tree_B)]:
    leaves = leaves_by_label(t, {})
    visible_leaves = sum(v for k, v in leaves.items() if k != "tau")
    silent_leaves = leaves.get("tau", 0)
    duplicates = sum(v - 1 for v in leaves.values() if v > 1)
    print(f"Model {name}:")
    print(f"  node count   = {count_nodes(t)}")
    print(f"  depth        = {tree_depth(t)}")
    print(f"  visible leaves = {visible_leaves}")
    print(f"  silent leaves  = {silent_leaves}")
    print(f"  duplicate labels = {duplicates}")
    net, im, fm = pm4py.convert_to_petri_net(t)
    print(f"  simplicity_petri_net = {pm4py.simplicity_petri_net(net, im, fm)}")
```

**Structural comparison (derived from the trees, exact):**

| Metric | Model A | Model B |
|---|---|---|
| Process-tree nodes | 10 | 10 |
| Depth | 5 | 5 |
| Visible leaves | 6 (`Open`, `Analyze`, `Check`, `Approve`, `Rework`, `Close`) | 6 (same set) |
| Silent leaves (`tau`) | 1 | 1 |
| Duplicate labels in source | 1 (`tau` appears once, but `Analyze`, `Check`, `Approve` are each referenced once; no duplicate label in the *literal* tree) | 1 (same) |
| `simplicity_petri_net(net, im, fm)` | lower (more places/transitions because the loop wraps the `+`) | slightly higher (the `+` is at top level, fewer cross-cutting arcs) |

Both models are **equally complex at the process-tree level**. The real simplification must come from the **business abstraction** (next section), not from rewriting the tree mechanically.

# 8. Simplified Model

**Target semantics: P2 (executive dashboard).** P1 has a clear semantic demand that no simple rewrite can preserve; P3 is bounded evidence; P2 is the only view under which the two originals are equivalent and that genuinely rewards simplification. I therefore propose a model whose P2-abstraction is identical to the original family, but whose process tree is shallower.

The dashboard needs only: (i) `Open Case` first, (ii) 1 `Analyze Revision`, (iii) 1 `Check Revision`, (iv) optional `Rework Case`, (v) `Close Case` last. `Approve Revision` and `tau` are hidden. Concurrency between `Check` and `Analyze` is collapsed.

### Compact tree / POWL

```text
->(
  'Open Case',
  *(
    ->(
      'Analyze Revision',
      'Rework Case'      -- wrapped to make "rework separates iterations"
    )
  ),
  'Check Revision',       -- at least one check (post-loop guarantee via X)
  'Close Case'
)
```

More precisely, expressed so the PM4Py parser accepts it:

```python
simplified_model = pm4py.parse_process_tree(
    "->( 'Open Case', "
    "*( ->( 'Analyze Revision', 'Rework Case' ) ), "
    "'Check Revision', "
    "'Close Case' )"
)
```

### Preservation table

| Property | Original A | Original B | Simplified | Status |
|---|---|---|---|---|
| `Open Case` first, `Close Case` last |  |  |  | **exact** |
|  1 `Analyze Revision` |  |  |  | **exact** |
|  1 `Check Revision` |  |  |  (one placed post-loop) | **exact** under P2 |
| `Rework Case` separates iterations |  |  |  (in the loop body) | **exact** under P2 |
| One `Check Revision` per iteration (P1) |  |  |  | **lost** (this is intentional — P2 does not preserve it) |
| `Check Revision` may precede first `Analyze` |  |  |  | **abstracted** under P2 |
| `Approve Revision` visible per iteration |  |  |  (removed) | **lost** (P2 hides it) |
| `tau` (silent skip of approval) | present | present | absent | **abstracted** under P2 |
| Dashboard tuple `(n_check{1}, n_analyze1, rework{0,1})` |  |  |  | **exact** |

### Regression traces (must be admissible)

| Trace | A | B | Simplified | Verdict |
|---|---|---|---|---|
| `Open, Analyze, Check, Close` |  |  |  | preserved |
| `Open, Analyze, Rework, Analyze, Check, Close` |  |  |  | preserved |
| `Open, Check, Analyze, Rework, Analyze, Close` |  |  |  | **negative for A only**; simplified admits it under P2 |

### Negative traces (must be rejected by the simplified model)

| Trace | Simplified | Why rejected |
|---|---|---|
| `Open, Close` |  | No `Analyze Revision`, no `Check Revision`. |
| `Open, Analyze, Close` |  | No `Check Revision` (P2 requires 1). |
| `Open, Analyze, Check, Rework, Close` |  | `Rework Case` is followed immediately by `Close Case` with no second `Analyze Revision` — the loop body is `Analyze, Rework`, so a `Rework` must be followed by another iteration or exit; here the body runs once then exits cleanly, *but* the `Check Revision` in this simplified model sits after the loop. Reordering is allowed because we declared P2 semantics. **This negative trace is rejected because the simplified model fixes `Check` after the loop.** |

**Why this simplification is justified.** The simplification preserves exactly the information P2 cares about and discards the information P2 does not care about. It is smaller in *behavioral* space, not in tree node count (the node count is comparable), but it is **easier to communicate**: stakeholders can read "analyze, maybe rework, then one check, then close."

# 9. Final Recommendation

| View | Recommended original | Reasoning |
|---|---|---|
| **P1 (compliance)** | **Model A** | Compliance requires a check after every analysis; only A guarantees that. |
| **P2 (dashboard)** | **Either A or B** — they are P2-DE-equivalent. Use **the simplified model** instead, because it is easier to read and matches the dashboard tuple exactly. | The simplification removes irrelevant detail and reduces the surface area for misinterpretation. |
| **P3 (bounded testing)** | Both can be exercised; bounded exploration is appropriate for nightly regression but **must not be the only artifact**. The bounds (12 visible events, 3 analyses) are insufficient to detect AB divergence in the unbounded case once the loop runs more than three times. Use bounded comparison as **a smoke test**, not as a proof of equivalence. | The asymmetry is unbounded, so any finite bound eventually admits counterexamples on both sides once the bound grows. |

**Should the simplified model replace either original?** For the dashboard use case, **yes**. For compliance, **no** — it loses the per-iteration check guarantee. For testing, **no** — it loses the optional approval visibility that auditors may want.

**Warnings about the limits of bounded comparison.**
1. P3 evidence is conditional on the bound; widening the bound can only increase, never decrease, the set of counterexamples.
2. Equal footprints and small EMD do not imply trace equivalence; they imply coarse structural similarity.
3. Stochastic language and EMD depend on (typically unspecified) transition probabilities; conclusions drawn from them inherit the same uncertainty.
4. Soundness guarantees that every activity can complete but says nothing about *how many times* a label may repeat — the very dimension on which A and B differ.
