## 1. Temporal Data Semantics

**State reconstruction.** Each case is a time-ordered sequence of events. The *case state* at any event *e* is the set of attribute values known to be effective at *e*'s timestamp, determined by applying updates in `(timestamp, event_index)` order and forward-filling only from non-blank cells. A blank cell in the CSV means "no update at this event," not "set to null." The previous known value persists.

**Forward-fill only.** Attributes are propagated forward from the event that sets them. Future values are never copied backward. If an attribute has never been set by the time of the event under evaluation, it remains unknown.

**Same-timestamp ordering.** When two events share a timestamp, `event_index` is the tie-breaker. Lower `event_index` is processed first. The consequence: the state visible to the later-`event_index` event includes the earlier-`event_index` update. This is decisive for TX-311, where Enhanced_Review (index 3) sees jurisdiction = US, while Release_Funds (index 5, later timestamp) sees jurisdiction = DE after the Update_Jurisdiction (index 4).

**Material data change.** An amount update is *material* (R4) when the new amount exceeds 120 % of the amount known at the time of the latest Standard_Review or Enhanced_Review. A decrease is never material by itself. An increase from an unknown amount is unclassifiable.

**Final attributes.** The final case state is not assumed to have governed earlier events. Each obligation is evaluated against the state at the relevant trigger event (typically Release_Funds), and each prior event's conditions are evaluated against the state at that prior event.

**Four time layers distinguished.**
- *Event time* — the timestamp on the event row; when the event occurred.
- *Effective time* — when an attribute change or exemption takes effect; defaults to event time unless evidence proves otherwise.
- *Record time* — when a database row was inserted (e.g., `Record_Exemption` at 11:00); may differ from effective time.
- *Evidence time* — when supporting proof (e.g., a digital signature) was created; determines whether evidence existed at the relevant obligation time.

**TX-310 (NONCOMPLIANT).** Two independent paths fail: (1) only Standard_Review exists, not Enhanced_Review; (2) exemption EX-88 is not validly evidenced at release time. *Alternative reading:* if an independent witness (not the requester) confirmed oral approval at 08:45, or if a qualified signature predating 10:00 were found, the exemption might be established under R5. Additionally, if the signing certificate creation at 10:30 were shown to be a re-keying of an earlier valid signature (not a new signature), the evidence time could be argued to predate release.

**TX-311 (COMPLIANT).** R1 is evaluated at Release_Funds using the state at that event. **TX-307 (NONCOMPLIANT).** *Alternative reading:* if one argued that Compliance_Approve "approved standard review packet" implicitly included an Enhanced_Review component, the semantic fact explicitly forecloses this: "a Compliance_Approve that reviewed only a standard packet does not cure the absence of Enhanced_Review." ## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A control-flow model sees the trace as an ordered list of activity names. It cannot prevent an analyst (or an automated forward-fill) from assuming the final jurisdiction or amount applied at every prior event. TX-311's jurisdiction is DE at release but US at Enhanced_Review; control flow cannot detect this state transition or its consequence for R1.

2. **Post-hoc exemptions.** Exemption records may be inserted after release (TX-302 at 11:00, TX-310 at 11:00). A control-flow check that sees `Record_Exemption` in the trace cannot determine whether the exemption was *evidentially valid* at release time. It would either always accept or always reject the exemption, missing the distinction between a qualified signature at 09:05 (TX-302) and a signing certificate created at 10:30 after release (TX-310).

3. **Material changes after review.** Control flow can express "Enhanced_Review precedes Release_Funds" but cannot express "Enhanced_Review must be *after* the latest amount increase exceeding 20 %." TX-309 has an Enhanced_Review before Release_Funds, so a pure precedence check passes, but the second amount increase (145 000 > 1.2 × 118 000) invalidates it. R4 requires comparing data values, not just activity ordering.

4. **Conditional activation.** R1 triggers only when jurisdiction  DE and amount  100 000. R2 triggers only when risk = HIGH or customer = PEP. A control-flow model has no notion of attribute-based conditions. TX-311 would be flagged non-compliant by a blind "Enhanced_Review before Release" rule even though R1 is not triggered because jurisdiction = DE.

5. **Missing data.** TX-305 has no amount at release. Control flow sees `Enhanced_Review` before `Release_Funds` and might pass the case. But R6 requires classifying it as INDETERMINATE because the R1 trigger cannot be confirmed or excluded without the amount. Control flow has no representation for "unknown attribute value."

6. **Same-timestamp ordering.** TX-311 has Enhanced_Review and Update_Jurisdiction at the same timestamp. Control-flow ordering by timestamp alone is ambiguous; `event_index` is needed. Many conformance checkers either ignore sub-second ordering or use log insertion order, which may not match `event_index`. R7 explicitly requires `event_index` as the tie-breaker, which is a data-level concern.

7. **Review-type distinction.** Control flow treats `Standard_Review` and `Enhanced_Review` as distinct activities, but a naive model might accept either as satisfying "review before release." TX-307 has Standard_Review before Release_Funds and Compliance_Approve before Release_Funds, so a control-flow model might pass it. R2 specifically requires *Enhanced_Review*, and the semantic fact that Standard  Enhanced is a domain rule, not a control-flow pattern.

8. **Sanctions list dynamics.** R3 requires comparing the Sanctions_List_Update event time to the last Sanctions_Screen and the release time. Control flow can express "Sanctions_Screen before Release_Funds," but it cannot express "a *new* Sanctions_Screen is required only when a list update occurred after the *previous* screen." TX-304 would pass a simple "Sanctions_Screen precedes Release_Funds" check even though the screen predates the list update.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payload.** At Release_Funds, persist a cryptographically signed snapshot of all governing attributes (amount, risk, jurisdiction, customer type, exemption reference) as they existed at the release decision time. This eliminates final-state leakage and post-hoc reinterpretation. TX-305's ambiguity would be resolved if the release payload contained the amount.

2. **Separate effective, record, and signature timestamps.** For every exemption and attribute change, log three timestamps: `effective_time` (when the change takes effect), `record_time` (when the database row was inserted), and `evidence_time` (when the supporting proof was created, e.g., qualified-signature creation). This would make TX-310's exemption clearly invalid (signature at 10:30 > release at 10:00) without forensic analysis.

3. **Explicit rule version per event.** Tag each event with the policy version under which it was evaluated. When rules change, this prevents retroactive conformance analysis from applying the wrong version.

4. **Exemption scope as structured fields.** Store exemption scope (jurisdiction, customer type, amount ceiling, waived rule) as structured, queryable fields rather than free text. Join exemption scope to the case state at release time programmatically.

5. **Change provenance and reason codes.** Every Update_* event should record the previous value, the new value, the actor, and a reason code. This makes R4 material-change detection deterministic: the ratio can be computed without reconstructing intermediate state.

6. **Mandatory amount at obligation-bearing events.** Require non-blank amount, risk, jurisdiction, and customer type at Release_Funds (and at Enhanced_Review). If any value is unavailable, block the release and create a `Data_Gap` event. This converts TX-305 from INDETERMINATE to a blocked workflow with a clear remediation path.

7. **Stable, monotonic event ordering.** Ensure `event_index` is globally unique within a case and strictly monotonic. Log it as an integer column that never resets. For same-timestamp events, add an explicit `sequence_within_timestamp` field to avoid ambiguity in downstream tools.

8. **Enhanced_Review scope capture.** Record whether an Enhanced_Review covered the standard review packet or was a standalone enhanced review. This prevents a Compliance_Approve of a standard packet from being mistaken for enhanced approval (TX-307).

9. **Sanctions list version reference.** At each Sanctions_Screen, record the sanctions list version (hash or ID) that was checked. At Sanctions_List_Update, record the list version and affected jurisdictions. R3 conformance then becomes a join on list version rather than temporal inference.

10. **Exemption approval evidence link.** Require a qualified digital signature (or equivalent tamper-evident proof) for every exemption, with the signature creation time recorded. Reject exemptions whose only evidence is a backdated display field or a non-independent witness statement. This would make TX-310 deterministically NONCOMPLIANT and TX-302 deterministically COMPLIANT.
