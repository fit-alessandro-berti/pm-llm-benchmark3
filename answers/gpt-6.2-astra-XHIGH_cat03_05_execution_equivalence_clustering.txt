## 1. Equivalence design space

Take the displayed execution as the observation window, rooted at its designated Order. An external object participates in that window without bringing its entire history into it. Use the listed order as temporal precedence. If exact timestamp ties occur in real data, use an unordered block for each tie. Treat O2O notes as positive evidence. For example, two recorded payments establish a count of two, but only X4's qualifiers establish which payment completed settlement.

**Activity-sequence equivalence (A).** Project each event to its activity, form a sorted multiset of labels for each time block, and compare the resulting sequences of blocks for equality. This preserves activity order across blocks and the number of occurrences of every label, including identical labels within a block. It discards identifiers, participants, object types, relations, and elapsed time. Tied labels can permute freely within their block. Equality of these sequences is reflexive, symmetric, and transitive.

**Typed structural equivalence (T).** Two executions are equivalent if there are bijections on their events and on their objects that preserve the lead, object types, local/external status, event labels, time-block order, every event-to-object (E2O) incidence, and the directed, qualified O2O facts, including any item to which a relation is scoped. Require preservation in both directions. Objects with the same type can exchange names only if one consistent mapping works everywhere. This preserves cardinalities, object reuse, and which events share participants. It discards identifier spellings, timestamp distances, and incidental row order within ties. Tied events can be matched in either order subject to their incidences. The identity, inverse, and composition of witness bijections give reflexivity, symmetry, and transitivity, respectively.

**Business-semantic equivalence (B, preferred).** Compute the signature in section 2 for each execution and compare the signatures for equality. They describe initial packing and repacking loads, delivery consolidation, payment multiplicity, cross-order participation by business function, and evidence of settlement or exception motifs. This discards most chronology, identifier spellings, and distinctions among relations outside the selected features. For example, reversing the order in which two independent packages are packed leaves their loads intact. Only the return motif needs a chain of strictly ordered events. Ties alone cannot establish that chain. Equality of signatures is reflexive, symmetric, and transitive. It also gives a versionable segmentation rule without a similarity threshold.

## 2. Canonical signatures

Write the signature as `P / D / M ; flags`. Each of the first three fields is a sorted tuple with one entry per relevant object, so two packages with the same load contribute two entries. P counts distinct **local** items observed at packing per package, including a new package used for repacking. D counts distinct packages dispatched per delivery. M counts distinct payments recorded per issued invoice. A joint invoice counts once. Count participants from the indicated events, which avoids relying on routine O2O facts being repeated in every note.

In the pseudocode, `ids(e,t)` is the set of participants of type `t` in event `e`, and `objects(E,t)` is their union across events. All fact tests run within x and match the supplied direction, endpoint types, and qualifier. Flags are positive evidence only.

```python
def signature(x):
    pack = events(x, "Pack Package")
    send = events(x, "Dispatch")
    issue = events(x, "Issue Invoice")
    pay = events(x, "Record Payment")

    def partners(E, obj, typ):
        return {v for e in E if obj in participants(e) for v in ids(e, typ)}

    packages = objects(pack, "Package")
    deliveries = objects(send, "Delivery")
    invoices = objects(issue, "Invoice")
    payments = {v: partners(pay, v, "Payment") for v in invoices}
    P = sorted(len({i for i in partners(pack, p, "Item") if not external(i)})
               for p in packages)
    D = sorted(len(partners(send, d, "Package")) for d in deliveries)
    M = sorted(len(payments[v]) for v in invoices)

    flags = set()
    if any(external(o) for e in pack + send for o in participants(e)):
        flags.add("L")  # shared logistics
    if (any(external(o) for e in issue + pay for o in participants(e))
        or any(fact(v, "bills", o) for v in invoices for o in external_orders(x))):
        flags.add("F")  # shared finance
    if any(a != b and fact(a, "partially_settles", v)
                  and fact(b, "completes_settlement", v)
           for v in invoices for a in payments[v] for b in payments[v]):
        flags.add("S")
    if (has_fact(x, "Item", "replaces", "Item")
        or has_fact(x, "Package", "removed_before_dispatch", "Item")):
        flags.add("U")
    if witnessed_return_chain(x):
        flags.add("R")
    return tuple(P), tuple(D), tuple(M), tuple(sorted(flags))
```

For `witnessed_return_chain`, seek six events in strictly increasing time blocks. Pack an item i in package p, dispatch p on delivery d, return i on d, inspect i, pack i in a different package q, and dispatch q. Match repeated variables by object identity within the execution. Dispatch need only mention the package. This distinguishes X8's second trip for the same item from X4's first trip for a different item. All operations use typed membership, identity comparisons, supplied external status, counts, and sorted outputs. Any consistent identifier renaming therefore leaves the signature unchanged.

## 4. Cluster interpretations

- **B1 Standard — [2] / [1] / [1].** A single package and delivery serve both items, followed by one invoice and payment. This is a reference group for measuring ordinary handling effort. A case per item can double-count the common packing operation. The assignment survives identifier repair, removing duplicate relation rows, and swapping indistinguishable item additions.
- **B2 Consolidated — [1,1] / [2] / [1].** Packing requires two handling units, while transport consolidates them. Measure packing workload per package and transport workload per delivery. A case per package counts the common dispatch twice if case totals are added. Reordering the two packing events is harmless. Merging the two package identities destroys the consolidation evidence.
- **B3 Split fulfillment and settlement — [1,1] / [1,1] / [2], S.** Fulfillment proceeds in two dispatches. The first payment leaves an outstanding balance and the second completes settlement. Both shipment tracking and invoice reconciliation matter. An invoice-only trace misses the shipment split, while an order-label trace cannot identify which invoice each payment concerns. The signature survives deduplication by genuine payment ID. Deduplication by activity and invoice alone loses a real installment.
- **B4 Shared logistics — [2] / [1] / [1], L.** One package serves two orders, while the observed invoice bills only the lead. Shared transport offers consolidation savings and creates a risk of charging the full dispatch cost to both orders. A case per order duplicates the shared dispatch across cases. The assignment survives renaming with boundary roles retained. Removing external participants makes it look standard.
- **B5 Shared finance — [2] / [1] / [1], F.** Logistics follow the baseline, but one payment settles a joint invoice. Attributing a payment amount to O6 requires allocation evidence. An order-level financial trace can credit both orders with the entire payment. The cluster survives deduplication of repeated billing links while either joint billing or shared financial participation remains visible.
- **B6 Substitution — [2] / [1] / [1], U.** I72 replaces I71, which is removed before dispatch. Counting initial packing incidences as shipped units overstates what went out. A case per package showing only activity names hides the change in contents. Equivalent qualifier spellings can be normalized safely. Losing both item-level exception qualifiers changes the preferred assignment.
- **B7 Return and repack — [1,2] / [1,1] / [1], R.** The second dispatch handles an inspected return. Its workload and delay belong to rework. A case per delivery separates the outbound and recovery trips and obscures the continuing identity of I82. The assignment survives loss of the package-replacement qualifier because the events witness the chain. Losing the item link on the return can break that witness.

## 5. Borderline cases

- **X1 versus X2.** Map I11 to I22 and I12 to I21, then map the sole object of each remaining type to its counterpart. Both item additions and the joint pack match. Literal record equality would split them and is defensible for testing whether an export was reproduced verbatim. Every renaming-invariant execution criterion on the supplied facts must group them. There is no business distinction in the lexical order of the IDs.
- **X1 versus X5.** A lead-order label trace groups them. Boundary-aware incidence separates a two-item local package from a three-item package with an external participant. The lead's own item count is two in both cases.
- **X1 versus X6.** A logistics-only comparison groups them even with full package and delivery detail. Invoice scope separates them. The single payment settles V61, but its existence cannot establish the amount attributable to O6.
- **X1 versus X7.** Package, delivery, and payment counts agree. A qualifier-aware comparison detects replacement and removal. Even without O2O facts, T sees an extra Item participant at X7's dispatch. That incidence alone does not establish the reason for removal.
- **X3 versus X4.** A warehouse comparison based on items per package groups both as two one-item packs. A transport comparison finds one two-package delivery versus two one-package deliveries. Finance independently separates one payment from two qualified settlements.
- **X4 versus X8.** A delivery-capacity comparison counts two one-package deliveries in each. An item-lifecycle comparison separates the first dispatch of each of two items in X4 from a second journey for I82 in X8. Dispatch count alone cannot price the inspection and repacking work.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The function groups executions extracted around objects of the chosen lead type. Read its exact key as an ordered tuple of event records. In typed incidence notation, each record is `(activity, ((type, IDs at this event), ...))`, with the participant collections in a consistent order. This records *which* objects occur together at each event and whether the same identifier recurs later. Repeated activities occupy separate positions. Absolute timestamps, payment amounts, O2O qualifiers, and an explicit business interpretation of externality are outside this comparison. A timestamp can affect event order without its value being part of the key. Two different linearizations of a tie can therefore yield different keys.

Identifier equality matters at the point the key is built. With raw IDs, even the first entries for X1 and X2 involve different Orders. Type-local renaming can remove that accidental distinction. A lexical tie-break among otherwise indistinguishable objects can still depend on their original names. For exact typed isomorphism, one reproducible, if expensive, solution is to enumerate type- and role-preserving numberings, serialize the lead, time blocks, E2O and qualified O2O under each, and take the lexicographic minimum. Sort event records within ties. For business clustering, compute section 2 on **each member** and regroup. Exact buckets may need splitting when members differ on a qualifier absent from the library key.

This runnable outline illustrates post-processing with a smaller custom key. It aggregates the library's members by the numbers of participating packages, deliveries, invoices, and payments, a capacity view that can merge several B groups.

```python
from collections import defaultdict
import pm4py

exact = pm4py.cluster_equivalent_ocel(ocel, "Order", max_objs=10000)
capacity_groups = defaultdict(list)
for members in exact.values():
    for run in members:
        rel = run.relations
        counts = rel.groupby(run.object_type_column)[run.object_id_column].nunique()
        key = tuple(int(counts.get(t, 0))
                    for t in ("Package", "Delivery", "Invoice", "Payment"))
        capacity_groups[key].append(run)
```

For the preferred groups, retain the root and original ownership metadata during extraction and replace the capacity key with `signature(run)` on the corresponding lead window. Check the window against the specified boundary. Following shared objects into a neighbor's entire lifecycle can change counts. A finite `max_objs` limits the objects considered and can leave intended executions unrepresented. Verify the returned lead count and execution sizes before reporting frequencies from a bounded run. Large connected neighborhoods increase extraction cost and key size, especially when shared objects appear in several lead windows. Exact keys suit regression checks on activity order and event participation, where merging a changed dispatch with the baseline would hide the change being tested.

## 7. Robustness analysis

- **Erase all O2O qualifiers.** Keep endpoint types and E2O. B6 loses U and merges into B1. B3 loses S but remains distinct through its two payments, and B7 retains its event-based return witness. Shared logistics and finance remain observable through external E2O. The activity partition is unchanged. X7 still differs structurally from X1 at dispatch.
- **Remove external objects and their incident links.** With no separate retained sharing indicator, B4 and B5 both merge into B1. No event disappears in these examples because each still has the lead participant. This repair changes the conclusion about isolation without changing any activity sequence.
- **Collapse consecutive identical labels.** Run-length compression of the label view merges A2 into A1 because the two successive packs in X3 become one. A3 still has alternating packing and dispatch, and A4 still has the return activities. B assignments persist when compression retains the underlying object incidences per occurrence. Replacing two packing records with a union of their participants can falsely associate each package with both items in X3.
- **Use a partial order for packing and dispatch.** Require each package's pack to precede its dispatch, and retain the return and inspection dependencies for a repacked item. Drop incidental precedence between different packages, even when they share a lead. X4's first dispatch need no longer precede the second pack. No preferred clusters merge here. X3 has a joint dispatch, X4 has two independent package trips, and X8 has return-dependent rework.
- **Summarize payments by amount.** Replacing payment identities and settlement stages with a final invoice total would hide the financial distinction between one payment and installments of the same total. X4 would still have split deliveries. No amounts are supplied, so equality of payment totals across these executions cannot be tested.

## 8. Limitations and recommendation

Use **qualified typed structure** for compliance monitoring where the rule concerns participants, substitutions, or settlement stages. Include amounts or deadlines explicitly when the rule uses them. Use **business signatures** for operational segmentation so staffing, transport costing, and reconciliation can distinguish the relevant kinds of work. For **root-cause analysis**, start from a semantic exception group and inspect its full typed executions with original timestamps, identifiers, and qualifiers available for drill-down. A signature identifies the observed return pattern but cannot explain why the customer returned I82. For **descriptive reporting** of activity paths, use activity-sequence classes and label the unit as lead Orders. A1 counts five orders following one recorded path, even though only two belong to the standard semantic cluster. The four uses require different evidence and different units of comparison.
