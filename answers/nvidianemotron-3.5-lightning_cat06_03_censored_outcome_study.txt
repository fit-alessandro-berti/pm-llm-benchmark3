## 1. Target definition

**Primary prediction target:**  
*90day default status within 90 days of Account Activation, predicted as of a configurable prediction point defined by the event prefix (e.g., after the first N events or at the completion of the Credit Review activity). The unit of analysis is the individual credit application (case). The population for which the target is defined are applications that eventually reach Account Activated; for all other applications the default outcome is left undefined (not coded as “nondefault”). The estimand is the marginal probability of default within 90 days of activation, conditional on the observed prefix at prediction time, with rightcensoring for activated accounts where the 90day window has not yet elapsed by the prediction cutoff.*

**Why this is defensible:**  
- It respects the selective observation mechanism: default can only be observed after activation, so we never impute a label for rejected/withdrawn/transferred/open cases.  
- It isolates the predictive question the business can act on: “given the early events we see, which eventuallyactivated accounts are likely to default in the next 90 days?”  
- It explicitly separates *activation selection* from *outcome prediction*, avoiding the ecological fallacy of treating the observed label as applicable to all applications.

**Credible alternative target (multistate / competingoutcome):**  
Define a 3state outcome for every application as of the prediction point:  
(a) `default_90d` – default within 90 days of activation (only for eventuallyactivated cases);  
(b) `non_default_after_activation` – activated and no default within 90 days;  
(c) `competing_outcome` – rejected, withdrawn, transferred, or stillopen at prediction, with no observed activation or default.  
This answers “what is the distribution of observed outcomes across all applications under the current policy?” but requires stronger assumptions if one wishes to interpret (c) as a defaultrisk proxy. It is useful for policylevel reporting but not for an earlywarning model that must operate on prefixes before activation is known.

## 4. Prefix extraction

**Prediction point:** Defined per case as the timestamp of the last event in the prefix (e.g., the `concept:name` that completes the chosen prefix length). No events after this timestamp are used to compute features or the label.

**Fixedeventcount prefixes:**  
- Choose a small, businessmeaningful count (e.g., first 4 events after `Application Started`).  
- Use `pm4py.get_prefixes_from_log(log, length=n)` to generate fixedlength prefixes.  
- Short cases (fewer than n events) are kept asis; the prefix length attribute records the actual number of events.

**Elapsedtime prefixes:**  
- Use all events occurring within a fixed window after application start (e.g., first 30 calendar days).  
- Generated by filtering `time:timestamp <= start_time + 30d`.  
- Same shortcase handling: prefix length reflects actual events within the window.

**Handling repetitive document loops:**  
- The process contains `Identity/KYC Check`  request documents  return to Credit Review one or more times.  
- Abstract these to canonical activity names; for prefix purposes, collapse consecutive repetitions of the same activity into a single occurrence *or* keep the count as a separate feature (`rework_count`) but do not let repeated document checks alter the logical prefix sequence.

**Activity renaming after 15 Oct 2025:**  
- A system migration renamed several activities and created occasional duplicate events.  
- Construct a mapping table `activity_old  activity_new` based on the migration date.  
- Apply the mapping *before* prefix extraction: all events with `time:timestamp > 20251015` have their `concept:name` replaced per the map; duplicates are deduplicated by `(case:concept:name, time:timestamp, org:resource)`.  
- Prefixes built from postmigration data are therefore comparable to premigration prefixes.

**No futurelooking:** The prefix and all derived features are computed *only* from events  prediction point. Events such as `Contract Signed`, `Account Activated`, `Collections Contact`, and `Default Recorded` are excluded from feature calculation and from the labelmaturity check until the prediction point is reached.

Using it encodes the outcome’s magnitude. | Available only after approval/activation. | **Drop** for prefixbased prediction. | Directly reveals approved credit amount, which is downstream of default risk and highly predictive. |
| `decision_reason` | **Severe leakage** – contains explicit approval/ rejection rationale; often includes “income insufficient” or “credit history” that correlates with default. | Populated at or after Accept/Reject. | **Drop** or keep only preactivation version (if available before decision). | Encodes the final decision; would trivialize the task if used as a feature. |
| `collection_status` | **Moderate–severe leakage** – updated after activation; may already contain “payments overdue” or “default flag” that reveals outcome. | Populated after activation and may directly reveal default. | **Drop** for prefix prediction; keep only as a *posthoc* validation check. | Directly tracks collection activity; futurelooking w.r.t. prediction prefix. |
| **Future events** (e.g., `Contract Signed`, `Account Activated`, `Default Recorded`) | **Severe leakage** – these are the very events that define the target horizon. Including any of their timestamps or counts as features predicts the label by construction. | N/A – by definition after prediction point. | **Drop** entirely from prefix feature set. | Prevents “peeking” at the outcome path. |
| `documents_total` (nightly snapshot) | **Potential leakage** – snapshot taken at extraction time may include documents uploaded the same day as the nominal prediction time, encoding latearriving information. | Available at extraction; may include sameday uploads. | **Repair**: truncate to `documents_total_up_to_prediction_cutoff`; flag `documents_same_day_as_prediction`. | The snapshot’s timing can misalign with the true prediction asof moment. |
| `risk_score` (updated at several events) | **Moderate leakage** – later updates may incorporate information that becomes available only after the prefix (e.g., final underwriting outcomes). Use only the *initial* risk score at first event, or version it with a cutoff timestamp. | May be updated multiple times. | **Keep**: `initial_risk_score` (first event). **Repair/ Drop**: any `risk_score` value whose `event_timestamp > prediction_point`. | Early risk score is arguably a legitimate predictive signal; later updates are not available at prediction time. |
| `resource experience` (at extraction time) | **Bias (not leakage per se)** – experience reflects staffing at Feb2026, not at event time. May confound timing effects. | Stored at extraction. | **Repair**: compute `experience_at_event = extraction_time – event_time`; keep only if within reasonable window, otherwise flag `experience_mismatch`. | Using extractiontime experience as if it were eventtime experience biases durationrelated features. |
| `label_available_at` | **Transparency tool** – not a model feature, but essential for defining censoring and delayedlabel logic. | Present in every row. | **Keep** as metadata; used to flag immature labels. | Enables honest treatment of missing outcomes rather than imputing them. |

## 7. Validation design

**Temporal backtesting (rollingorigin) scheme:**  
1. **Training window:** Applications started 1Jan2024 – 30Jun2025 (covers prepolicychange and early postchange periods).  
2. **Validation fold:** Applications started 1Jul2025 – 30Sep2025 (captures the new creditpolicy threshold shift).  
3. **Test fold 1:** Applications started 1Oct2025 – 31Dec2025 (covers systemmigration period; activityrename mapping applied).  
4. **Test fold 2 (labelmaturity holdout):** Applications started 1Jan2026 – 15Feb2026 (the extraction window); used only to assess calibration of the 90day default probability, since many activated cases from late2025 will have immature `default_90d` labels.  

Splits are **by case start time**, not random. This ensures that (a) no future policy change is included in training, (b) migrationinduced artifacts are isolated to specific folds, (c) labelmaturity effects are examined across folds, and (d) distribution shift between periods is measurable.

**Why a random case split is misleading:**  
- It would mix pre and postpolicychange applications, conflating different activityoutcome relationships.  
- It would place migratedrenamed cases alongside premigration cases, breaking prefix comparability.  
- It would intermix cases with mature labels and immature labels, inflating apparent performance (the model could “cheat” by learning labelavailability patterns rather than true default signals).  
- It ignores the temporal ordering of activation and outcome collection, violating the causal timing of the business process.

**Evaluation metrics (appropriate to the censoring/competingrisk target):**  
- **Timedependent AUC / ROC** (Heagerty & Zheng) for censored survival data, computed at 30, 60, and 90 days postactivation.  
- **Integrated Brier score** with inverseprobabilityofcensoring weights (IPCW) to assess overall accuracy while accounting for rightcensoring.  
- **Calibrationin-the-large** and **calibration slope** from a Coxbased predictedvsobserved comparison in decile risk groups.  
- **Cumulative incidence function (CIF)** plots and **subdistribution Brier score** for the competingrisk (nonactivated states) evaluation.  
- **PrecisionRecall AUC** on the activated subset, especially relevant given the imbalanced default rate (12% among activated).  

All metrics are computed *only* on activated accounts with known or censored 90day status, never on the full 48k cohort as if all were labeled.

## 8. Limitations and decisionuse boundary

**What the study can claim:**  
- A statistically valid association between earlyprefix patterns and the probability of 90day default *among accounts that eventually become activated*, under the observed creditpolicy and systemoperation conditions of the observation window.  
- Calibrated risk scores for earlywarning purposes, with explicit quantification of censoring and competingrisk structures.  
- Identification of processlevel red flags (e.g., repeated document loops, long timetocreditreview) that correlate with higher default hazard.

**What the study cannot claim:**  
- Absolute default probability for *all* credit applications, because default is undefined for rejected, withdrawn, transferred, and stillopen cases without activationpolicy assumptions.  
- A causal effect of early events on default risk; the model captures predictive association, not counterfactual impact.  
- Generalizability to future periods with different policies, partner ecosystems, or customer segments without retraining and validation.

**Three ways deployment could change the datagenerating process (DGP):**  
1. **Policy revision:** New creditthresholds or underwriting criteria alter the activityoutcome relationship (e.g., stricter thresholds reduce default rates but also change the prefix distribution).  
2. **Partner onboarding:** Adding or removing partner platforms changes the transfer fraction, linkage completeness, and proportion of permanently missing outcome feeds, distorting the competingrisk structure.  
3. **Applicant behavioral response:** If the earlywarning model is deployed and applicants modify their behavior (e.g., withdrawing earlier, providing more documents upfront), the prefix distributions shift, creating a feedback loop that invalidates static feature importance and calibration.  

All deployment decisions should rerun the temporal backtest on the most recent 6month window and recompute calibration before refreshing the production model.
