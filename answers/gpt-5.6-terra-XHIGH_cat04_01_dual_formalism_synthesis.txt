# 1. Assumptions and Interpretation

1. Activities are represented by their completion events. A trace is therefore a linearization of a concurrent execution; an order between two completion events does not by itself prove that the underlying activities did not overlap.

2. The low-risk/high-risk decision is represented as an exclusive control-flow choice:
   - low risk: `Supervisor Review`;
   - high risk: both `Quality Review` and `Regulatory Review`.
   The model does not contain the data condition that selects the branch.

3. Supplier involvement is represented as an XOR between `Consult Supplier` and a silent transition ``. Thus, supplier consultation is optional, occurs at most once, and is invisible when absent. The data condition selecting it is external to the model.

4. Inspection outcomes are abstracted structurally. In the loop, an `Inspect Trial` followed by `Adjust Parameters` is interpreted as a failed inspection. The final `Inspect Trial` that exits the loop is interpreted as the passing inspection, even if approvals or supplier consultation still complete before `Release Material`.

5. No structural duplication of visible labels is used. Each named activity has one visible node in each model. The labels `Execute Trial` and `Inspect Trial` may occur repeatedly in a trace because their nodes are inside a loop, not because multiple cloned nodes exist.

6. The process tree uses a **conservative under-approximation**. It preserves all safety constraints but forces approvals and any selected supplier consultation to complete before trial execution. This excludes intended traces in which approvals or supplier consultation overlap the trial cycle.

7. “May overlap” is interpreted as genuine concurrency: there is no causal precedence relation between the activities, provided all stated prerequisites are met. In a completion-event trace, this appears as either allowed completion order or interleaving.

8. High-risk reviews are assumed to be mandatory as a pair: a high-risk case cannot complete with only one of `Quality Review` or `Regulatory Review`.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D1 | Register Deviation | Contain Material; Analyze Root Cause | Precedence and fork | Every case begins with registration; containment and analysis may then proceed independently. |
| D2 | Contain Material | Analyze Root Cause | No order / concurrency | Neither activity depends on completion of the other. |
| D3 | Contain Material | Plan Verification | Precedence | Verification planning may start only after containment completes. |
| D4 | Analyze Root Cause | Design Corrective Action | Precedence | Corrective-action design requires completed root-cause analysis. |
| D5 | Analyze Root Cause | Selected approval route | Precedence | The low/high-risk approval route is selected after analysis. |
| D6 | Approval route | Supervisor Review or {Quality Review, Regulatory Review} | XOR choice | Low risk requires Supervisor Review; high risk requires both Quality and Regulatory Review. |
| D7 | Quality Review | Regulatory Review | No order / concurrency | In high-risk cases, both reviews are required but may complete in either order or overlap. |
| D8 | Analyze Root Cause | Supplier-choice submodel | Precedence and optionality | Supplier consultation is either absent or occurs once after analysis. |
| D9 | Consult Supplier | Plan Verification, Design Corrective Action, approvals, trial cycle | No order except release gate | When selected, supplier consultation may overlap these activities, but must finish before release. |
| D10 | Plan Verification and Design Corrective Action | Trial cycle | Synchronizing precedence | `Execute Trial` may begin only after both planning and design are complete. |
| D11 | Approval route and supplier-choice submodel | Trial cycle | No precedence | Approvals and supplier consultation do not have to complete before the trial cycle; they may overlap it. |
| D12 | Execute Trial | Inspect Trial | Precedence | Every trial execution is followed by its inspection. |
| D13 | Failed Inspect Trial | Adjust Parameters  next Execute Trial | Conditional loop-back | A failed inspection causes adjustment and another trial iteration. |
| D14 | Passing Inspect Trial, selected approval route, selected supplier consultation | Release Material | Synchronizing precedence | Release requires a passing final inspection, completed approvals, and completed supplier consultation if selected. |
| D15 | Release Material | Archive Case | Precedence | Archiving is the final activity. |

# 3. PM4Py Process-Tree Model

The following notation uses `->` for sequence, `+` for parallelism, `X` for XOR, `*` for loop, and `` for a silent activity.

```text
->(
  "Register Deviation",
  +(
    ->("Contain Material", "Plan Verification"),
    ->(
      "Analyze Root Cause",
      +(
        "Design Corrective Action",
        X(
          "Supervisor Review",
          +("Quality Review", "Regulatory Review")
        ),
        X(, "Consult Supplier")
      )
    )
  ),
  *(
    ->("Execute Trial", "Inspect Trial"),
    "Adjust Parameters"
  ),
  "Release Material",
  "Archive Case"
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    """Create a visible leaf when label is a string, or a silent leaf for None."""
    return ProcessTree(label=label)


def op(operator, *children):
    """
    Construct an operator node and explicitly maintain both child and parent links.
    """
    parent = ProcessTree(operator=operator)
    parent.children = []

    for child in children:
        parent.children.append(child)
        child.parent = parent

    return parent


# Visible leaves
register_deviation = leaf("Register Deviation")
contain_material = leaf("Contain Material")
analyze_root_cause = leaf("Analyze Root Cause")
plan_verification = leaf("Plan Verification")
design_corrective_action = leaf("Design Corrective Action")

supervisor_review = leaf("Supervisor Review")
quality_review = leaf("Quality Review")
regulatory_review = leaf("Regulatory Review")

consult_supplier = leaf("Consult Supplier")
supplier_absent = leaf(None)  # silent  branch

execute_trial = leaf("Execute Trial")
inspect_trial = leaf("Inspect Trial")
adjust_parameters = leaf("Adjust Parameters")

release_material = leaf("Release Material")
archive_case = leaf("Archive Case")


# High-risk route requires both reviews; their completion order is unconstrained.
high_risk_reviews = op(
    Operator.PARALLEL,
    quality_review,
    regulatory_review,
)

# Low-risk versus high-risk route.
risk_route = op(
    Operator.XOR,
    supervisor_review,
    high_risk_reviews,
)

# Optional supplier consultation.
supplier_choice = op(
    Operator.XOR,
    supplier_absent,
    consult_supplier,
)

# After analysis, design, approval, and optional supplier work may overlap.
post_analysis_work = op(
    Operator.PARALLEL,
    design_corrective_action,
    risk_route,
    supplier_choice,
)

analysis_stream = op(
    Operator.SEQUENCE,
    analyze_root_cause,
    post_analysis_work,
)

containment_stream = op(
    Operator.SEQUENCE,
    contain_material,
    plan_verification,
)

# The two initial streams may overlap after registration.
initial_parallel_work = op(
    Operator.PARALLEL,
    containment_stream,
    analysis_stream,
)

# Loop body is one Execute Trial -> Inspect Trial iteration.
# Taking the redo branch means the inspection failed and parameters are adjusted.
trial_cycle = op(
    Operator.LOOP,
    op(
        Operator.SEQUENCE,
        execute_trial,
        inspect_trial,
    ),
    adjust_parameters,
)

# Conservative process-tree approximation:
# all initial work, including approvals and any supplier consultation,
# must complete before the trial loop begins.
tree = op(
    Operator.SEQUENCE,
    register_deviation,
    initial_parallel_work,
    trial_cycle,
    release_material,
    archive_case,
)
```

This tree exactly represents registration first, archiving last, the two initial work streams, containment-before-planning, analysis-before-design and approvals, low/high-risk choice, concurrent high-risk reviews, optional supplier consultation, repeated trial cycles, and no adjustment after the final loop-exiting inspection.

Its deliberate loss is the cross-branch release synchronization pattern. Because a basic process tree cannot naturally express “approval and supplier work may continue concurrently with a trial but must finish before release” without either duplication or a more elaborate encoding, the tree joins all initial work before starting the trial loop. Consequently:

- `Supervisor Review`, `Quality Review`, and `Regulatory Review` must finish before `Execute Trial`;
- selected `Consult Supplier` must finish before `Execute Trial`;
- intended traces where approvals or supplier consultation overlap trial work are rejected.

This is a conservative under-approximation: it excludes valid timing flexibility but does not admit an unsafe release.

# 4. PM4Py POWL Model

```text
HighRiskReviews =
  SPO{ "Quality Review" || "Regulatory Review" }

RiskRoute =
  XOR("Supervisor Review", HighRiskReviews)

SupplierChoice =
  XOR(, "Consult Supplier")

TrialCycle =
  LOOP(
    SPO{ "Execute Trial" < "Inspect Trial" },
    "Adjust Parameters"
  )

POWL =
  SPO{
    "Register Deviation",
    "Contain Material",
    "Analyze Root Cause",
    "Plan Verification",
    "Design Corrective Action",
    RiskRoute,
    SupplierChoice,
    TrialCycle,
    "Release Material",
    "Archive Case";

    "Register Deviation" < "Contain Material",
    "Register Deviation" < "Analyze Root Cause",
    "Contain Material" < "Plan Verification",
    "Analyze Root Cause" < "Design Corrective Action",
    "Analyze Root Cause" < RiskRoute,
    "Analyze Root Cause" < SupplierChoice,
    "Plan Verification" < TrialCycle,
    "Design Corrective Action" < TrialCycle,
    TrialCycle < "Release Material",
    RiskRoute < "Release Material",
    SupplierChoice < "Release Material",
    "Release Material" < "Archive Case"
  }
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


# Atomic visible transitions
register_deviation = Transition(label="Register Deviation")
contain_material = Transition(label="Contain Material")
analyze_root_cause = Transition(label="Analyze Root Cause")
plan_verification = Transition(label="Plan Verification")
design_corrective_action = Transition(label="Design Corrective Action")

supervisor_review = Transition(label="Supervisor Review")
quality_review = Transition(label="Quality Review")
regulatory_review = Transition(label="Regulatory Review")

consult_supplier = Transition(label="Consult Supplier")
supplier_absent = SilentTransition()

execute_trial = Transition(label="Execute Trial")
inspect_trial = Transition(label="Inspect Trial")
adjust_parameters = Transition(label="Adjust Parameters")

release_material = Transition(label="Release Material")
archive_case = Transition(label="Archive Case")


# High-risk approval route: both review transitions exist with no edge between them.
high_risk_reviews = StrictPartialOrder(
    [quality_review, regulatory_review]
)

# Low-risk is one supervisor review; high-risk is the concurrent two-review submodel.
risk_route = OperatorPOWL(
    Operator.XOR,
    [supervisor_review, high_risk_reviews],
)

# Supplier consultation is optional and produces no visible event when absent.
supplier_choice = OperatorPOWL(
    Operator.XOR,
    [supplier_absent, consult_supplier],
)

# One iteration of the trial body.
trial_body = StrictPartialOrder(
    [execute_trial, inspect_trial]
)
trial_body.order.add_edge(execute_trial, inspect_trial)

# LOOP(body, redo): execute the body once; redo with Adjust Parameters to repeat.
trial_cycle = OperatorPOWL(
    Operator.LOOP,
    [trial_body, adjust_parameters],
)

# Top-level partial order. Composite nodes are used directly so that dependencies
# apply to the selected risk route and supplier choice as whole submodels.
powl = StrictPartialOrder(
    [
        register_deviation,
        contain_material,
        analyze_root_cause,
        plan_verification,
        design_corrective_action,
        risk_route,
        supplier_choice,
        trial_cycle,
        release_material,
        archive_case,
    ]
)

# Registration and the two independently progressing initial work streams.
powl.order.add_edge(register_deviation, contain_material)
powl.order.add_edge(register_deviation, analyze_root_cause)

# Split dependencies.
powl.order.add_edge(contain_material, plan_verification)
powl.order.add_edge(analyze_root_cause, design_corrective_action)

# Risk route and supplier choice both occur only after analysis.
powl.order.add_edge(analyze_root_cause, risk_route)
powl.order.add_edge(analyze_root_cause, supplier_choice)

# Trial starts only after verification planning and corrective-action design.
powl.order.add_edge(plan_verification, trial_cycle)
powl.order.add_edge(design_corrective_action, trial_cycle)

# Release synchronizes the independently progressing obligations.
powl.order.add_edge(trial_cycle, release_material)
powl.order.add_edge(risk_route, release_material)
powl.order.add_edge(supplier_choice, release_material)

# Final archive.
powl.order.add_edge(release_material, archive_case)
```

The loop semantics supplies the cyclic behavior that a `StrictPartialOrder` must not encode directly: `Execute Trial  Inspect Trial`, then either exit the loop as a passing inspection or execute `Adjust Parameters` and repeat the body. Adding strict-order edges from inspection to adjustment and from adjustment back to execution would create an invalid cycle in the partial order, so the `OperatorPOWL(Operator.LOOP, ...)` is the appropriate representation.

The intentionally unconnected node pairs may remain concurrent whenever both are selected:

- `Contain Material` and `Analyze Root Cause` are independent after registration.
- `Plan Verification` is independent of analysis-side work once containment is complete.
- `Design Corrective Action`, the selected approval route, and the selected supplier-choice branch are mutually unordered after analysis.
- `Quality Review` and `Regulatory Review` have no edge in the high-risk submodel.
- The trial cycle has no edge from either the approval route or supplier-choice submodel; it therefore may overlap either after its own prerequisites are satisfied.
- Release and archive are not left unconnected from any mandatory predecessor; their synchronization edges are explicit.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and analysis may overlap after registration. | Exact: parallel containment/planning and analysis-side branches. | Exact: both have registration as predecessor and no edge between them. | None in either model. | Both permit parallel case handling. |
| Planning and design dependencies | Containment precedes planning; analysis precedes design; planning and design have no mutual dependency. | Exact. | Exact. | None in either model. | Avoids premature planning or design while retaining independent work. |
| Risk route | Low risk uses Supervisor Review; high risk uses both Quality and Regulatory Review. | Exact control-flow alternative. | Exact control-flow alternative. | Data classification itself remains external in both models. | A wrong business risk classification is not detected by control flow alone. |
| High-risk review ordering | Quality and Regulatory Review may overlap and may complete in either order. | Exact through parallel operator. | Exact through an edge-free high-risk partial order. | None. | Prevents needless serialization of high-risk approvals. |
| Approval/trial overlap | Trial needs planning and design, not completed approvals. | Overconstrained: all approvals finish before the trial begins. | Exact: no approval-route-to-trial edge. | Process tree under-approximates valid behavior. | The tree can falsely report legitimate fast trial execution as nonconformant. |
| Optional supplier consultation | Optional once, after analysis, may overlap other work, but required before release if selected. | Optionality and post-analysis constraint are exact; overlap with trial is lost. | Exact through XOR with `SilentTransition` and release synchronization. | Process tree under-approximates supplier/trial overlap. | Supplier coordination may appear to delay trials more than the intended process requires. |
| Repeat-until trial behavior | Execute then inspect; failure adjusts and repeats; final passing inspection exits the loop. | Exact under the loop-exit-means-pass abstraction. | Exact under the same abstraction. | Inspection outcome data is not observable from labels alone. | Auditing a specific pass/fail decision requires additional data attributes. |
| Release synchronization | Passing trial, completed approvals, and selected supplier consultation are all required before release. | Safety is preserved, but approval and supplier obligations have already been forced before trial. | Exact independent synchronization at release. | Process tree overconstrains timing; POWL does not. | The process tree loses intended overlap and may misstate lead time. |
| Duplicate-label risk | One structural node per visible activity; trial labels may recur by looping. | No structural visible-label duplication. | No structural visible-label duplication. | No deliberate duplication-based approximation. | Lower alignment ambiguity than a clone-heavy tree encoding. |

# 7. Preferred Representation and Validation Plan

The preferred canonical representation is the **POWL model**. It directly expresses the central non-block-structured requirement: planning and design jointly enable trial execution, while approvals and optional supplier work may independently continue until they synchronize only at release. The process tree is useful for tools requiring process-tree input, but it should be documented as a conservative operational view rather than the canonical behavior.

Validation plan:

1. Convert both models where the installed PM4Py version supports conversion:

   ```python
   import pm4py

   tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)
   powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   ```

2. Run accepting-Petri-net soundness checks and inspect diagnostics rather than treating a Boolean result as proof of fidelity:

   ```python
   pm4py.check_soundness(tree_net, tree_im, tree_fm, print_diagnostics=True)
   pm4py.check_soundness(powl_net, powl_im, powl_fm, print_diagnostics=True)
   ```

3. Perform bounded or sampled playout. Because the trial loop is unbounded, use a practical maximum trace length or explicitly limit trial iterations to, for example, one through three iterations during testing. Inspect whether sampled POWL traces include:
   - both low-risk and high-risk alternatives;
   - either high-risk review completion order;
   - absent and present supplier consultation;
   - approval and supplier completion after trial start but before release.

4. Replay the five positive witnesses against the POWL accepting net and require accepting completion. Replay the three forbidden witnesses and require that they cannot reach the final marking without deviations. Repeat against the process-tree net, with the explicit expected discrepancy that A2 is rejected by the conservative tree.

5. Test silent behavior specifically:
   - A low-risk trace with no `Consult Supplier` must be accepted through the `SilentTransition` supplier-absent branch.
   - A trace containing `Consult Supplier` after `Release Material` must be rejected.
   - Generated logs must not expose a visible event corresponding to the silent supplier-absent branch.

6. Test duplicate-label behavior specifically:
   - Traverse the source POWL/tree structures and verify that each non-loop activity label occurs structurally once.
   - Verify that repeated `Execute Trial` and `Inspect Trial` events arise only from repeated loop execution, not from duplicate visible transitions created by the source model.
   - Inspect converted-net visible transition labels because conversion may introduce multiple Petri-net transitions with the same visible label even when the source model did not deliberately clone nodes.

7. Limitations:
   - Bounded playout cannot prove correctness for unbounded trial retries.
   - Petri-net soundness does not prove that the net preserves every intended concurrency relation.
   - Neither model validates risk classification, supplier-selection data, or actual inspection results; those require data-aware validation outside the activity-only control-flow model.
   - PM4Py conversion behavior may vary by version, especially for POWL operators and silent transitions.

# 8. Final Self-Critique

1. The POWL model relies on the semantic convention that loop exit denotes a passing inspection. This is appropriate for the activity-only specification but does not make pass/fail outcomes independently observable in an event log.

2. The process tree intentionally sacrifices valid approval/trial and supplier/trial overlap. It is safe but can materially distort throughput analysis, conformance results, and perceived approval lead time.

3. The Python construction follows the stated PM4Py interfaces, but exact constructor and conversion behavior can vary across PM4Py releases; the model should be executed and converted in the target environment before operational adoption.
