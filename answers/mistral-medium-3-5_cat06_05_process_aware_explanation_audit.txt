## 2. Process-model consistency checks

**Validation Suite Design:**
1. **Prefix-Time Availability Check**
   - *Method*: For each feature, verify that all source data timestamps are  `t0` (prediction time).
   - *Tools*: Use a `prefix_filter` to reconstruct features using only events up to `t0`. Compare against original feature values.
   - *Limitation*: Does not catch mutable features (e.g., `risk_score_current`) without versioning.

2. **Activity-Order Feasibility (DFG/Alignment Check)**
   - *Method*: For sequence patterns, validate against the normative process model (e.g., `Claim Closed` cannot precede `Damage Assessment Completed`).
   - *Tools*: Use a **Declarative Process Model** (e.g., Declare/LTL) to check:
     - `Response(Claim Registered, Coverage Check Completed)` (must hold).
     - `Precedence(Damage Assessment Completed, Claim Closed)` (must hold).
     - `Exclusive Choice` between fast track and evidence cycles.
   - *Limitation*: DFG edges may not capture semantic rules (e.g., `Settlement Decision Recorded` can repeat after `Appeal`).

3. **Same-Timestamp Ambiguity Check**
   - *Method*: Flag cases where events in a sequence pattern share timestamps but lack a sequence index.
   - *Tools*: Query for `event_pairs` with `timestamp1 = timestamp2` and `sequence_index IS NULL`.
   - *Action*: Exclude such patterns or assign conservative ordering (e.g., alphabetical).

4. **Complete-Trace Feature Detection**
   - *Method*: Audit feature lineage to identify any use of:
     - Future events (e.g., `appeal_seen_anywhere`).
     - Aggregations over full traces (e.g., `num_document_requests_total`).
   - *Tools*: Feature-store metadata (e.g., `computation_time` field) or SQL dependency analysis.

5. **Enabled/Impossible Activity Check**
   - *Method*: At `t0`, the enabled activities are:
     - `Damage Assessment Completed` (fast track).
     - `Documents Requested` (evidence cycle).
     - `Fraud Investigation Opened` (if triggered).
   - *Action*: Exclude explanations referencing impossible activities (e.g., `Appeal` at `t0`).

6. **Repeated Settlement Decision Semantics**
   - *Method*: Verify that `Settlement Decision Recorded` appears twice only in traces with `Appeal` between them.
   - *Tools*: Check for `Settlement Decision Recorded -> Appeal -> Settlement Decision Recorded` subsequences.

**Limitations**:
- Alignment checks assume the normative model is correct; real processes may deviate.
- Prefix checks may miss features derived from mutable state (e.g., `queue_length_at_t0` with ±5 min tolerance).

## 5. Recommendations for explanation validation

**Prioritized Plan:**

1. **Feature-Store Design (Critical)**
   - Implement **temporal versioning** for all features (e.g., `feature_value_at_timestamp`).
   - Store **computation metadata** (e.g., `source_events_used`, `extraction_time`).
   - Enforce **prefix-only computation** for predictive features (no full-trace aggregations).

2. **Historical Feature Timestamps (Critical)**
   - Audit all features for:
     - **Mutability**: Ensure features like `risk_score` are frozen at `t0`.
     - **Lineage**: Verify SQL/ETL logic (e.g., `prior_claim_count` must use `claim_created_at < t0`).
   - Add **feature timestamps** to the store (e.g., `feature_as_of`).

3. **Prefix-Only Recomputation (High)**
   - Recompute all features using **only events  `t0`** for validation.
   - Compare against original features to detect leakage (e.g., `full_trace_variant_id` vs. `prefix_variant_id`).

4. **Process-Conformance Tests (High)**
   - **Alignment Checks**: Validate sequence patterns against the normative process model (e.g., using **ProM** or **Celonis**).
   - **Declarative Constraints**: Enforce rules like:
     - `Precedence(Claim Registered, Coverage Check Completed)`.
     - `Response(Coverage Check Completed, Damage Assessment Completed OR Documents Requested)`.
   - **Impossible Activity Detection**: Flag explanations referencing activities not enabled at `t0` (e.g., `Appeal`).

5. **Calibration After Feature Removal (Medium)**
   - Retrain the model **without leaked features** (e.g., `total_case_duration_hours`).
   - Recompute SHAP values to ensure explanations are **prefix-consistent**.
   - Monitor **performance drift** (e.g., AUC, Brier score) post-removal.

6. **Explanation Stability (Medium)**
   - Test explanation consistency across:
     - **Subgroups** (e.g., by `claimant_region`).
     - **Time windows** (e.g., pre/post policy change).
   - Use **counterfactual testing**: Perturb prefix-available features (e.g., `queue_length_at_t0`) and check if explanations update plausibly.

7. **Proxy/Fairness Analysis (Medium)**
   - **Fairness Audits**: Test for disparate impact by `claimant_region`, `channel`, etc. (e.g., using **AIF360** or **Fairlearn**).
   - **Proxy Detection**: Identify features that may encode sensitive attributes (e.g., `region`  socioeconomic status).
   - **Robustness Checks**: Evaluate if proxy relationships hold under **distribution shifts** (e.g., new regions).

8. **Monitoring for Schema/Process Drift (Low)**
   - **Schema Drift**: Alert on new/removed features or changes in feature computation logic.
   - **Process Drift**: Monitor for:
     - New activity sequences (e.g., `Fraud Investigation` before `Coverage Check Completed`).
     - Changes in activity frequencies (e.g., sudden spike in `Documents Requested`).
   - **Explanation Drift**: Track SHAP value shifts for top features over time.
