# 1. Objectives and constraints

## Purpose

The policy is a decision-support rule for assigning each awaiting activity to a primary resource, or to a supervised pair where one person prepares/drafts and another is accountable for the final decision. It is not intended to produce a single mathematically obvious optimum. Weights and thresholds are governance choices that must be reviewed with worker representatives because the same assignment can be fast for the process but unfair, risky for quality, or damaging to learning and continuity.

## Objectives

1. **Meet SLA and reduce waiting risk**, especially for urgent/high-priority cases, without creating hidden queues elsewhere.
2. **Protect quality and reduce rework/appeals** by matching sufficient skill to complexity.
3. **Balance workload and overtime risk**, using open cases, hours remaining, and expected service time.
4. **Preserve continuity where it has value**, because handovers on complex cases add waiting and can increase rework.
5. **Develop skills safely**, giving trainees real but supervised work on lower-risk cases.
6. **Improve resilience**, avoiding over-concentration in scarce Security, Approval, Diagnosis, and Rework specialists.
7. **Remain explainable and auditable**, recording a short reason code for every assignment and allowing human challenge or override.

## Hard safety and compliance constraints

These cannot be traded away for throughput:

- **Skill 0 means not allowed**, even with supervision. For example, Eva and Jonas have Security skill 0; they may observe a Security Review for learning, but they may not be assigned responsibility for it.
- **Security Review:** only skill 3 may act alone, or skill 1–2 only under explicit supervision by R7_Gita or R8_Hugo.
- **Final Approval:** skill 2–3 must finalize. Skill 1 may prepare work but may not finalize.
- **High/urgent priority:** no primary assignment below skill 2 unless supervised and the supervisor is accountable.
- **Batch cap:** no resource receives more than 4 new assignments in one decision batch; supervision load must also be counted in workload monitoring even if it is lighter than primary work.
- **No unsafe overtime forcing:** a deferred case may be assigned for later work, but the policy must not require immediate overtime to meet its internal sequencing.
- **Complete explanation data:** every assignment must record `assignment_reason`, supervisor if any, and the workload snapshot used at the time.

## Soft constraints and trade-offs

- Avoid new work for resources with overtime risk “high” unless an urgent SLA leaves no safer eligible alternative.
- For high-complexity, high-handover-cost cases, prefer the current owner unless that owner is skill 0–1, unsupervised, or demonstrably unable to meet the SLA.
- At least 20% of normal/low-priority assignments should support a documented training priority when SLA slack permits.
- Quality Check batching is preferred only for normal/low priority with more than 24 hours of SLA remaining.
- Prefer the lowest sufficient skill for low-complexity routine work, preserving scarce specialists for complex or urgent work.
- Keep a human override route. A dispatcher or worker may challenge an assignment, but overrides of hard constraints are prohibited; if nobody is eligible, the case waits and escalates rather than being assigned unsafely.

# 2. Assignment policy

## General approach

Assignments are made in SLA-driven order, but scored case by case. Urgent and high-priority cases are considered first so capacity is reserved for them before lower-priority training or batch work fills the day.

```text
for each case in order of priority, then SLA remaining, then complexity:
    candidates = all resources
    candidates = remove skill-0 resources for the required skill
    candidates = remove resources that would breach activity-specific rules
                 e.g. Security unsupervised skill <3
                 e.g. Approval finalizer skill <2
                 e.g. high-priority primary skill <2 without supervisor
    candidates = remove resources already at batch cap of 4
    candidates = penalise or defer resources with high overtime risk
                 unless no other eligible candidate exists for an urgent case

    for each remaining candidate:
        compute SLA feasibility score
        compute skill-match score
        compute continuity / handover-cost score
        compute workload and overtime-fairness score
        compute training score
        compute resilience / bottleneck score

    choose highest total score
    if best candidate is skill 1 for a suitable case:
        require a named supervisor with skill 2-3
        if no supervisor is available, remove the trainee candidate
    if no candidate is eligible:
        escalate to duty manager; do not assign skill 0
    record assignment_reason and workload_snapshot
```

## Scoring components

The following illustrative weights sum to 1. They are starting points for discussion, not universal constants. Urgent cases increase the weight on SLA feasibility and skill; low-priority cases increase weight on fairness, training, and resilience.

**Total score**

`0.25 × skill match + 0.20 × SLA feasibility + 0.15 × continuity + 0.15 × workload fairness + 0.10 × training value + 0.10 × resilience + 0.05 × context fit`

### Eligibility filtering

- Remove skill 0.
- For Security, allow skill 3 alone, or skill 1–2 only with Gita or Hugo as named supervisor.
- For Approval, the finalizer must be skill 2–3; skill 1 can be preparer only.
- For high/urgent work, skill 1 requires supervision; for normal/low work, skill 1 requires supervision and adequate SLA slack.
- Remove candidates at the 4-assignment batch cap or without enough usable hours for a same-day start.

### SLA urgency scoring

Estimate whether the case can finish in time:

`feasibility = SLA remaining  expected waiting  expected service  expected handover delay`

Cases with small or negative feasibility rise in priority. The policy also sequences work: an assigned low-priority case may be queued for later, while urgent cases are started first.

### Skill-match scoring

- Skill 2 is treated as competent and sufficient for many cases.
- Skill 3 receives a bonus that increases with complexity, urgency, and regulatory sensitivity.
- Skill 1 receives a score only when supervised, the case is not urgent, complexity is not extreme, and SLA slack comfortably exceeds expected service plus supervision time.
- The policy avoids using a specialist for a trivial low-complexity case if a competent resource is available, preserving scarce capacity.

### Continuity and handover-cost scoring

- Bonus for retaining the current owner, especially where handover cost is high, complexity is high, or reassignment count is already 2 or more.
- Penalty increases with `handover_cost_band` and with reassignment count.
- Crossing from 2 to more than 2 reassignments is treated as a warning because historical evidence links this to higher rework and appeals.
- A handover is allowed when the owner is under-skilled for the activity, overloaded, high-overtime-risk, or the case is urgent and a specialist can act directly.
- Every non-continuity assignment must generate a short handover note from the previous owner.

### Workload and overtime fairness scoring

Use `current open cases`, `hours remaining today`, expected service time, existing supervision load, and overtime risk. The score falls as open cases rise or hours remaining fall. Resources with overtime risk “high” are normally excluded from new primary assignments in this batch. Their existing cases are not automatically removed, because that would create disruptive handovers; instead, they receive no additional work unless the SLA is urgent and no safer alternative exists.

### Training and development scoring

A training bonus applies only when all of the following hold:

- The resource’s documented training priority matches the required skill.
- The resource is below specialist level, typically skill 1, or skill 2 seeking broader competence.
- The case is normal/low priority, or high priority only if supervised and SLA slack is generous.
- A supervisor is available.
- The assignment is not needed to rescue an urgent SLA.

Training is framed as supported practice with review gates, not as unreviewed cheap labour.

### Resilience and bottleneck avoidance

- Penalise assignments that repeatedly consume the same scarce specialists, especially in Security and Approval.
- Preserve at least some same-day capacity among Security, Diagnosis, Approval, and Rework specialists where possible.
- Count supervision as partial workload so that a specialist does not become a hidden bottleneck.
- Where a scarce skill has only two specialists, distribute work across both when SLA and continuity allow.
- Encourage shadowing for future capability, but never confuse shadowing with accountable assignment.

## Tie-breaking

If scores are close, apply this order:

1. Higher SLA feasibility.
2. Retention of current owner.
3. Lower open-case count.
4. Lower overtime risk.
5. Higher relevant skill for complex cases; lower sufficient skill for routine cases.
6. Lower supervision burden.
7. Lower resource identifier, for deterministic auditability.

## Exception handling

- **No eligible resource:** escalate; never assign skill 0 to Security or a skill-1 finalizer to Approval.
- **Trainee without supervisor:** remove the trainee or reassign to a competent resource.
- **Specialist absence or overload:** reassign only with a handover note; prefer a competent resource with a specialist review over a full specialist transfer if that protects continuity.
- **Supervisor bottleneck:** if specialist supervision queues grow, a competent skill-2 reviewer may supervise lower-complexity training work, with spot checks by the specialist.
- **Worker challenge:** a worker may flag overload, a skill gap, or a missing context item. The dispatcher must record the challenge and either adjust the assignment or record why the original assignment stands.
- **Reassignment threshold:** a third reassignment requires duty-manager review because of the observed rework and appeal risk.

| Dimension | Proposed explainable dynamic policy | First-available routing | Specialist-only routing |

| Error and rework risk | Uses skill 2 as sufficient for routine work and skill 3 for high complexity. Trainees are supervised and gated. The proposed policy does not dominate both baselines on every measure. First-available routing may beat it on raw first-touch speed in a quiet period, and specialist-only routing may beat it on the first attempt for a very complex case. The proposed policy is preferable when the organisation values completed work without rework, safe supervision, sustainable workload, and future capability as part of throughput.

# 5. Explanation to workers

> **How we assign work**
>
> We try to match the right person to the right case at the right time. Urgent and complex work goes to someone with the necessary skill and enough time to do it properly. Routine work can go to someone who is competent, which helps us keep specialists available for the difficult cases.
>
> If you already own a case, we normally keep it with you, especially when changing owner would mean repeating explanations or losing important context. Sometimes we may move a case away from you if you are already overloaded, at risk of overtime, or if the next step needs a specialist skill. That is not a judgement on your work; it is about protecting your workload and the customer’s deadline.
>
> Training assignments are supported practice. If you are building a skill, you will work on a lower-risk case with a named supervisor who reviews the work with you. Supervision is there to support learning and quality, not to monitor or punish you. You will not be given accountable responsibility for Security work or final approvals unless you have the required skill level.
>
> Your current workload, the time you have left today, and any overtime risk are part of the decision. If an assignment looks wrong, unsafe, or too much, tell the dispatcher. You can ask for a review, a supervisor, a handover note, or a different sequence of work. The aim is safe, fair, and explainable assignments, with room for human judgement.

# 6. Process-mining audit indicators

The audit should use the event-log fields `case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`, `required_skill`, `case_priority`, `sla_deadline`, `case_complexity`, `current_owner`, `team`, `assignment_reason`, `reassignment_count`, `workload_snapshot`, and `handover_cost_band`. Results should be stratified by priority, complexity, activity, and team, and reported in aggregate rather than as individual league tables.

| Indicator | Definition using the log | Alert or interpretation |
|---|---|---|
| Handover frequency | Percentage of activity instances where `org:resource` differs from the previous resource on the same case, or from the recorded `current_owner` at assignment. | Rising handover rate, especially on high-complexity cases, suggests continuity is not being protected. |
| Reassignment count | Distribution of `reassignment_count` per case; share of cases with count greater than 2. | Any case above 2 requires review because historical evidence links this to higher rework and appeals. |
| Skill mismatch | Join each assignment to a versioned skill matrix. Measure share assigned at skill 0, skill 1 unsupervised, Approval finalized by skill 1, and Security handled by skill 1–2 without Gita/Hugo supervision. | Skill 0 or unauthorized finalization should be zero. Skill-1 assignments outside normal/low priority need case review. |
| Workload distribution | New assignments per resource per batch, open cases from `workload_snapshot`, standard deviation, range, and a concentration measure such as Gini or Herfindahl index. Add supervision assignments as partial load. | Growing spread, repeated use of the same resources, or hidden supervisor overload indicates unfair allocation. |
| Overtime risk exposure | Share of new primary assignments to resources flagged overtime risk “high”; events outside normal hours; negative or near-zero hours remaining in `workload_snapshot`. | Should be near zero except for justified urgent exceptions with a recorded reason. |
| SLA misses | Compare completion timestamp with `sla_deadline`; report miss rate and near-miss rate by priority. Also compute waiting plus service time after assignment. | Investigate urgent misses first, then high-priority cases with high handover cost. |
| Rework and appeal after assignment | Count later “Rework Correction” activities, returns to earlier activities in the process graph, and appeal outcomes by assigned skill, handover band, and reassignment count. | Compare supervised trainee work with specialist work and continuity with handover work; do not judge trainees without adjusting for case complexity. |
| Training assignment share | Among normal/low cases, percentage where the assignee’s documented training priority matches `required_skill` and a supervisor is recorded. | Target at least 20%; in the current batch the formal share is 2 of 9, or 22%. |
| Specialist bottleneck indicators | Waiting time, service time, queue length, and utilisation for Security, Approval, Diagnosis, and Rework; share of cases waiting for one of the two Security specialists; supervisor queue length. | Long waits for Security or Approval indicate a resilience problem even if average waiting time looks acceptable. |
| Deviations from policy | Replay the policy from the logged snapshot and compare its recommendation with the actual `org:resource` and `assignment_reason`. Report hard-rule breaches separately from soft-score deviations and human overrides. | Hard breaches should be zero. Repeated soft deviations may mean the weights, not the workers, need adjustment. |
| Continuity rate | Percentage of assignments where the primary resource equals `current_owner`, stratified by complexity and handover band. | Low continuity on high-complexity/high-handover cases requires explanation. |
| Realised handover delay | Median waiting time between ownership change and the next substantive activity, by `handover_cost_band` and complexity. | Compare with the historical median of about 2.7 hours for high-complexity ownership changes. |
| Supervision effectiveness | For supervised skill-1 assignments, measure service time, rework, supervisor review waiting time, and downstream appeals. | Long supervisor queues can erase the benefit of training assignments. |

# 7. PM4Py implementation sketch

The following is an implementation sketch rather than production code. It shows how the logged data can be prepared, how resource behaviour can be discovered, and how the deployed policy can be replayed for audit.

```python
import pm4py
import pandas as pd

log = pd.read_csv("assignment_log.csv")
log["time:timestamp"] = pd.to_datetime(log["time:timestamp"])

df = pm4py.format_dataframe(
    log,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource"
)

df = pm4py.filter_event_attribute_values(
    df, "case_priority", ["urgent", "high", "normal", "low"]
)

df = pm4py.insert_case_service_waiting_time(df, case_id="case:concept:name")
service_time = pm4py.get_service_time(df, activity="Technical Diagnosis", resource="R3_Celine")

handover_network = pm4py.discover_handover_of_work_network(df)
working_together = pm4py.discover_working_together_network(df)
resource_similarity = pm4py.discover_activity_based_resource_similarity(df)
roles = pm4py.discover_organizational_roles(df)
batches = pm4py.discover_batches(df)

performance_dfg = pm4py.discover_performance_dfg(
    df,
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource"
)

variants = pm4py.get_variants(df)
pm4py.save_vis_sna(handover_network, "handover_network.svg")

skill_matrix = {
    "R8_Hugo": {"Security": 3, "Rework": 3, "Quality": 3},
    "R6_Farid": {"Approval": 3, "Negotiation": 3, "Diagnosis": 1},
    "R3_Celine": {"Diagnosis": 3, "Rework": 3, "Eligibility": 2}
}

training_priority = {
    "R6_Farid": "Diagnosis",
    "R1_Amal": "Diagnosis",
    "R2_Bruno": "Quality"
}

def eligible(resource, activity, required_skill, supervised):
    skill = skill_matrix.get(resource, {}).get(required_skill, 0)
    if skill == 0:
        return False
    if required_skill == "Security":
        return supervised or skill == 3
    if activity == "Final Approval":
        return skill >= 2
    return skill >= 2 or supervised

def policy_score(case, resource, supervisor=None):
    skill = skill_matrix.get(resource, {}).get(case["required_skill"], 0)
    skill_score = skill / 3
    continuity_score = 1.0 if resource == case["current_owner"] else 0.0
    workload_score = 1.0 / (1.0 + case["open_cases"][resource])
    training_score = 1.0 if training_priority.get(resource) == case["required_skill"] else 0.0
    return (
        0.25 * skill_score
        + 0.15 * continuity_score
        + 0.15 * workload_score
        + 0.10 * training_score
    )

recommendations = []
for _, case in df.drop_duplicates("case:concept:name").iterrows():
    candidates = [
        resource for resource in skill_matrix
        if eligible(resource, case["concept:name"], case["required_skill"], supervised=False)
    ]
    best = max(candidates, key=lambda r: policy_score(case, r))
    recommendations.append({
        "case:concept:name": case["case:concept:name"],
        "recommended_resource": best,
        "actual_resource": case["org:resource"],
        "assignment_reason": case["assignment_reason"]
    })

audit = pd.DataFrame(recommendations)
audit["deviation"] = audit["recommended_resource"] != audit["actual_resource"]
```

In a fuller implementation, the score function would use versioned skill data, expected service and waiting times from `get_service_time` and the inserted service/waiting fields, handover patterns from `discover_handover_of_work_network`, collaboration patterns from `discover_working_together_network`, resource similarity from `discover_activity_based_resource_similarity`, role patterns from `discover_organizational_roles`, batch behaviour from `discover_batches`, and timing by activity and resource from `discover_performance_dfg`. Case filtering with `filter_event_attribute_values` and `filter_case_performance` would allow SLA, rework, and bottleneck analyses to be separated by priority, complexity, team, and handover band.
