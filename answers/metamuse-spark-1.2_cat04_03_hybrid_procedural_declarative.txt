# 1. Policy Interpretation and Conflict Resolution

**Material assumptions:**

* **A1 - Closed activity vocabulary:** The 18 labels given are authoritative. No synthetic `Emergency Authorization` event exists in the log.
* **A2 - Stable backbone interpretation:** Requirements 1-5 are *control-flow* invariants. All other requirements are cross-cutting and orthogonal to the block-structure.
* **A3 - Activity-only vs. attributed events:** `Activity@hour[resource]` is the log form. `hour` is the only timestamp; `resource` is available but optional. No `case attribute = emergency` or `risk_level` is logged. Any rule referring to *joint authorization* or *risk* is therefore **not recoverable from activity sequences alone**.
* **A4 - Termination semantics:** `Close Onboarding` is terminal. `Reject Vendor` and `Activate Vendor` are mutually exclusive decisions. `Release First Payment` is conditional on activation.
* **A5 - Time semantics:** `hour` is integer hours since case start. Temporal expectations (R12) are stochastic, not normative.
* **A6 - Resource semantics:** Segregation-of-duties (R9) refers to the *actual performer* attribute `resource`. Missing resource => cannot evaluate SoD, must be flagged as `not evaluated`, not silently passed.

**R5 / R6 Conflict:**

* **R5 (Legal):** `Sanctions Escalation  Obtain Legal Opinion  Activate Vendor` - strict `precedence` under all circumstances. `( Sanctions Escalation  (Obtain Legal Opinion before Activate Vendor))`.
* **R6 (Operations):** `Activate Vendor` *may* precede `Obtain Legal Opinion` if externally jointly authorized, provided `Obtain` arrives within 24h after activation. Log contains no emergency flag, so conformance cannot distinguish authorized emergency from violation.

> Both cannot be encoded as activity-only control-flow simultaneously. Combining them silently as `response(Sanctions Escalation, Obtain Legal Opinion)` discards Legal's safety property; combining as `precedence(Obtain, Activate)` discards the operational emergency path and creates false positives.

**Two defensible resolutions:**

* **Resolution A - Strict / Legal-authoritative (chosen for implemented model):** Encode R5 authoritatively in DECLARE as `response(Sanctions Escalation, Obtain Legal Opinion)` **and** `precedence(Obtain Legal Opinion, Activate Vendor)` conditioned on `Sanctions Escalation`. Treat R6 as an *external, attributed exception* that is invisible to conformance. Activations before opinion always fail DECLARE; an auxiliary resource/data check whitelists them *only* if an out-of-band authorization register can be consulted. Compliance risk: operations emergency cases will be flagged as violations unless manually overruled; no missed legal violations. Chosen because safety-critical and auditable.
* **Resolution B - Permissive / Operations-tolerant:** Encode only `response(Sanctions Escalation, Obtain Legal Opinion)` and drop the precedence. Add a data-aware check `if Sanctions Escalation in trace and Activate Vendor before Obtain Legal Opinion then require (Activate, Obtain)  24h`. DECLARE never fails on order. Compliance risk: Legal's `precedence` is downgraded to a warning; a non-emergency early activation that obtains an opinion at 23h would incorrectly pass, creating regulatory exposure.

**Choice for this model:** **Resolution A** implemented. `declare_model` enforces strict precedence; the `Resource- and Data-Aware` layer implements the 24h compensating check as a `policy-dependent` override. T6 therefore `fail` under the canonical model and `pass/warning` under Resolution B (see §8).

# 3. Procedural Backbone

### 1. Compact formal description

```
SEQ(
  Receive Onboarding Request,
  PAR( Capture Master Data, Run Sanctions Screening, Verify Bank Account ),
  Classify Risk,
  LOOP( body=Classify Risk, redo= SEQ(Request Clarification, Receive Clarification) )? // optional clarification cycles before decision
  XOR(
    SEQ( Reject Vendor, Close Onboarding ),
    SEQ(
      XOR(
        SEQ( Manager Approval ), // low-risk
        SEQ( Enhanced Due Diligence, Compliance Approval ) // high-risk
      ),
      Activate Vendor,
      Release First Payment,
      Close Onboarding
    )
  )
)
```
Post-activation behavior (`Change Bank Details  Suspend Vendor  re-Verify  Release`) is **deliberately excluded** from the tree (see explanation).

### 2. Self-contained PM4Py code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label): 
    return ProcessTree(label=label)

# leaves
recv = leaf("Receive Onboarding Request")
cap = leaf("Capture Master Data")
run = leaf("Run Sanctions Screening")
ver = leaf("Verify Bank Account")
cls = leaf("Classify Risk")
req = leaf("Request Clarification")
rec = leaf("Receive Clarification")
edd = leaf("Enhanced Due Diligence")
mgr = leaf("Manager Approval")
com = leaf("Compliance Approval")
act = leaf("Activate Vendor")
rej = leaf("Reject Vendor")
pay = leaf("Release First Payment")
clo = leaf("Close Onboarding")
tau = ProcessTree(label=None)  # silent skip for optional clarification

# PAR: captures concurrent checks after receipt
par_checks = ProcessTree(operator=Operator.PARALLEL, children=[cap, run, ver])

# Clarification loop: zero or more Request/Receive cycles before decision
# LOOP semantics: body executed at least once, redo optional
clarif_seq = ProcessTree(operator=Operator.SEQUENCE, children=[req, rec])
clarif_loop = ProcessTree(operator=Operator.LOOP, children=[tau, clarif_seq]) 
# LOOP(tau, clarif_seq) = execute tau, optionally redo clarif_seq repeatedly -> 0..* cycles

# Low vs High risk routes
low = ProcessTree(operator=Operator.SEQUENCE, children=[mgr])
high = ProcessTree(operator=Operator.SEQUENCE, children=[edd, com])
route = ProcessTree(operator=Operator.XOR, children=[low, high])

accepted = ProcessTree(operator=Operator.SEQUENCE, children=[route, act, pay, clo])
rejected = ProcessTree(operator=Operator.SEQUENCE, children=[rej, clo])

decision = ProcessTree(operator=Operator.XOR, children=[rejected, accepted])

procedural_model = ProcessTree(
    operator=Operator.SEQUENCE, 
    children=[recv, par_checks, cls, clarif_loop, decision]
)
```

`procedural_model` is an accepting ProcessTree (convertible to Petri net via `pm4py.convert_to_petri_net`).

### 3. Explanation

* **Concurrency:** `PAR(Capture, Run, Verify)` after `Receive` captures requirement 2. Any interleaving is allowed; `Classify Risk` requires all three via preceding `SEQUENCE`.
* **Choices:** Three-way primary outcome encoded as `XOR( reject, seq(low, activate...), seq(high, activate...))`  implements requirements 4. `noncoexistence(Manager, Compliance)` from DECLARE reinforces the low/high split if the XOR is bypassed.
* **Clarification loops:** Implemented as `LOOP(tau, RequestReceive)` after `Classify`. **Approximation disclosed:** True specification allows clarification *any time* after the three checks and before any final outcome, including before `Classify`. The tree restricts loops to after `Classify` to keep block-structure; pre-`Classify` clarifications (as in T2/T5) are therefore accepted by DECLARE but may cause procedural `fail` if strictly aligned. We treat the tree as the *canonical happy path* and delegate strict R3 to DECLARE/external checks (authoritative).
* **Terminal outcomes:** `Close Onboarding` after either `Reject` or `Release`; tree ensures `Release` only on accepted branch. `Activate/Reject` at most once by tree structure.
* **Post-activation deliberately excluded:** `Change Bank Details`, `Suspend Vendor`, and re-`Verify` create a non-block-structured cycle (`Activate  (Change  Suspend  Verify  Release)*`) that would require a Petri net with arbitrary places or POWL partial orders. Including it in a ProcessTree would force artificial `LOOP` nesting and duplicate `Verify`/`Release`, obscuring the backbone. Therefore R11 is excluded from procedural and handled declaratively/externally.

If POWL were used, the same structure applies with explicit `partial_order` edges: `Receive  {Capture, Run, Verify}  Classify  {Request  Receive}*  XOR(decision)  Close`, with `POWL` enabling non-block `Change  Suspend` precedence edges.

**Rule semantics table:**

| Template | Key (source,target) | Direction | Semantics | Why this template vs alternatives |
|---|---|---|---|---|
| `noncoexistence(A,B)` | `(Activate, Reject)` | symmetric | A and B never co-occur in same trace. | `noncoexistence` = `¬(A  B)`. Weaker than `nonsuccession` (which allows B before A). Correct for mutual exclusion. |
| `noncoexistence` | `(EDD, Manager)` / `(Compliance, Manager)` | symmetric | Low vs high risk approval exclusion (R8) | Same rationale. |
| `noncoexistence` | `(Reject, Manager)` / `(Reject, Compliance)` | symmetric | No approval in rejected case (R2 approx) | Captures `Reject  Approval` forbidden; not equivalent to `precedence` which would require order. |
| `altresponse(A,B)` | `(Request, Receive)` | `AB` | If `Request` occurs, `Receive` must eventually occur before the *next* `Request`; no two `Request`s without `Receive`. | `response` allows `Request, Request, Receive` (violates R3). `chainresponse` would require *immediately next* event to be `Receive` (too strong). `altresponse` is exact for R3. |
| `precedence(A,B)` | `(Request, Receive)` | `B requires A before` | If `Receive` occurs, `Request` must have occurred before (no spontaneous receives). | Complement to `altresponse`; `precedence`  `response` (response is `A  B`, precedence is `B  ¹A`). Both needed. |
| `precedence` | `(Run, Escalation)` | `B requires A` | Escalation only after Screening (R7) | `response(Run, Escalation)` would be wrong (Screening does *not* require Escalation). `succession` would be too strong. |
| `precedence` | `(Obtain, Activate)` | `B requires A` | If `Activate` occurs, `Obtain` must have been before (R5 strict Res.A) | `response(Escalation, Obtain)` alone does not enforce order; `succession` would require Escalation whenever Activate occurs (false). `chainprecedence` would require immediate predecessor (too strong). |
| `response(A,B)` | `(Escalation, Obtain)` | `AB` | Escalation must be followed by Obtain eventually (R4) | `precedence(Obtain, Escalation)` would invert direction. `responded_existence` would allow Obtain *before* Escalation only. |
| `response` | `(Change, Suspend)` | `AB` | Change after activation eventually requires Suspend (R11 part) | Conservative; full R11 needs ordering relative to Verify/Release (beyond DECLARE). |

Confidence values `<1.0` indicate conservative approximations expected to generate false positives when the condition is conditional (e.g., `precedence(Obtain, Activate)` is 0.85 because it fires even without Escalation).

**Overlap / Disagreement:**

* **Orientation:** `always_before(A,B)` means *if B occurs, A was before*; `always_after(B,A)` is the mirror. We populate both consistently (e.g., `Receive` always before `Close`  `Close` always after `Receive`).
* **With procedural:** `always_before(Receive, Capture/Run/Verify)` duplicates the `SEQ(Receive, PAR(...))` order; Log Skeleton is trace-based and will still pass if parallelism is serialized differently.
* **With DECLARE:** `never_together` duplicates `noncoexistence` rules (R1,R8,R2). Declaration is evaluated per rule confidence; skeleton is strict frequency. Slight redundancy is intentional: DECLARE for comprehensive diagnostics, skeleton for cardinality (`activ_freq`) which DECLARE cannot enforce.
* **Disagreement on optional activities:** Skeleton allows 0/1 for approvals/Escalation/Obtain, whereas strict procedural tree requires exactly one path. Skeleton is more permissive and therefore authoritative for R10; procedural is authoritative for intended happy path.

# 6. Temporal Profile

```python
# mean and std in seconds; zeta = 2.0 => allowed interval [mean - 2*std , mean + 2*std] clamped at 0
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48*3600, 24*3600),   # 172800 ± 86400  -> 0h to 96h
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12*3600, 6*3600),     # 43200 ± 21600   -> 0h to 24h
    ("Activate Vendor", "Release First Payment"): (72*3600, 36*3600),        # 259200 ± 129600 -> 0h to 144h
}
zeta = 2.0
```

**Why warnings, not automatic violations:** R12 is explicitly described as *normative enough to flag but not automatically reject*. Means and standard deviations are empirical expectations with variance; system latency, weekends, or emergency workflows legitimately deviate. Enforcing them as control-flow (`chainresponse` with delay) would conflate performance with correctness and amplify false positives due to: clock skew, batch processing, and the timestamp-only limitation (no business calendar). Therefore `pm4py.conformance_temporal_profile(..., zeta=2.0)` is run last, its output is `warning`, and it never drives the overall `fail` verdict; it surfaces as *SLA breach* for operational follow-up. Under `zeta=2`, ~95% of normal variation passes; extreme deviations (T7 escalationopinion 34h >24h) are flagged.

# 7. Resource- and Data-Aware Checks

Required attributes: `case:concept:name` (or `case_id`), `concept:name` (activity), `time:timestamp` (or `hour` derived), `org:resource` (performer). `emergency_authorization` (boolean/external registry) required for R6 override; if missing, check returns `policy-dependent`.

**Missing attribute policy:** If `org:resource` missing, SoD check returns `not evaluated` with reason `missing_resource`; case is not auto-passed. If `time:timestamp` missing, temporal check `not evaluated`. If external auth missing, R6 override `not evaluated`  strict R5 applies.

```python
import pandas as pd
from pm4py.filter_four_eyes_principle import filter_four_eyes_principle  # if available

def check_sod_verify_vs_approval(log_df: pd.DataFrame):
    """R9a: Verify Bank Account resource != approval resource (Manager or Compliance)."""
    violations = []
    for case_id, trace in log_df.groupby("case:concept:name"):
        ver_res = set(trace[trace["concept:name"]=="Verify Bank Account"]["org:resource"].dropna())
        appr_res = set(trace[trace["concept:name"].isin(["Manager Approval","Compliance Approval"])]["org:resource"].dropna())
        if not ver_res or not appr_res:
            continue  # not evaluated if missing - handled by caller
        if ver_res & appr_res:
            violations.append((case_id, f"SoD violation: Verify {ver_res}  Approval {appr_res}"))
    return violations
    # pm4py alternative: filter = filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval") + same for Compliance

def check_sod_capture_vs_activate(log_df: pd.DataFrame):
    """R9b: Capture Master Data resource != Activate Vendor resource."""
    violations = []
    for case_id, trace in log_df.groupby("case:concept:name"):
        cap = trace[trace["concept:name"]=="Capture Master Data"]["org:resource"].dropna().unique()
        act = trace[trace["concept:name"]=="Activate Vendor"]["org:resource"].dropna().unique()
        if len(cap)==0 or len(act)==0:
            continue
        if set(cap) & set(act):
            violations.append((case_id, f"SoD: Capture {cap} == Activate {act}"))
    return violations

def check_clarification_pending(log_df: pd.DataFrame):
    """R3 authoritative: no pending Request before next Request or before final outcome."""
    violations = []
    for case_id, trace in log_df.sort_values("time:timestamp").groupby("case:concept:name"):
        pending = 0
        for _, ev in trace.iterrows():
            act = ev["concept:name"]
            if act == "Request Clarification":
                if pending > 0:
                    violations.append((case_id, "Request before prior Receive closed"))
                pending += 1
            elif act == "Receive Clarification":
                if pending == 0:
                    violations.append((case_id, "Receive without pending Request"))
                else:
                    pending -= 1
            elif act in ("Activate Vendor","Reject Vendor","Close Onboarding") and pending>0:
                violations.append((case_id, f"Final outcome {act} with pending clarification"))
    return violations

def check_emergency_policy(log_df: pd.DataFrame, auth_registry: dict = None):
    """
    R5/R6: if Sanctions Escalation present and Activate  Obtain, 
    allow only if external auth True and (Activate,Obtain) 24h.
    Returns policy-dependent if auth missing.
    """
    import pandas as pd
    results = {}
    for case_id, trace in log_df.sort_values("time:timestamp").groupby("case:concept:name"):
        seq = list(trace["concept:name"])
        if "Sanctions Escalation" not in seq:
            continue
        has_activate = "Activate Vendor" in seq
        has_obtain = "Obtain Legal Opinion" in seq
        if not (has_activate and has_obtain):
            continue
        t_act = trace[trace["concept:name"]=="Activate Vendor"]["time:timestamp"].min()
        t_obt = trace[trace["concept:name"]=="Obtain Legal Opinion"]["time:timestamp"].min()
        if t_act < t_obt:
            delta_h = (t_obt - t_act).total_seconds()/3600 if hasattr(t_obt, "total_seconds") else (t_obt - t_act)/3600
            # if auth_registry is None -> cannot decide, strict R5 applies
            auth = auth_registry.get(case_id) if auth_registry else None
            if auth is None:
                results[case_id] = ("policy-dependent", f"Activate before Obtain ={delta_h:.1f}h, no auth attribute - strict R5 FAIL, permissive PASS if 24h")
            elif auth is True and delta_h <= 24:
                results[case_id] = ("pass-emergency", f"Emergency authorized ={delta_h:.1f}h 24h")
            else:
                results[case_id] = ("fail", f"Early activation ={delta_h:.1f}h auth={auth}")
    return results

def check_r11_change_bank(log_df: pd.DataFrame):
    """R11: Change after Activate  Suspend later and re-Verify before next Release."""
    violations = []
    for case_id, trace in log_df.sort_values("time:timestamp").groupby("case:concept:name"):
        evs = trace.reset_index()
        for i, row in evs.iterrows():
            if row["concept:name"]=="Change Bank Details":
                # check if there exists Activate before this Change
                has_act_before = any(evs.iloc[:i]["concept:name"]=="Activate Vendor")
                if not has_act_before:
                    continue
                after = evs.iloc[i+1:]
                if not any(after["concept:name"]=="Suspend Vendor"):
                    violations.append((case_id, "Change after Activate without subsequent Suspend"))
                # any later Release must have Verify between Change and Release
                for j, r2 in after[after["concept:name"]=="Release First Payment"].iterrows():
                    segment = evs.iloc[i+1:j]
                    if not any(segment["concept:name"]=="Verify Bank Account"):
                        violations.append((case_id, "Release after Change without re-Verify"))
    return violations
```

All checks are executable-style on a `pm4py`-converted DataFrame (`pm4py.convert_to_dataframe(log)`) with `time:timestamp` derived from `hour`.

# 9. Contradictions, Redundancies, and Blind Spots

* **Duplicated enforcement:** R1, R7, R8 are enforced in *three* layers (procedural XOR/PAR, DECLARE `noncoexistence`/`precedence`, Log Skeleton `never_together`/`always_before`). Duplication is intentional but can produce conflicting diagnostics (e.g., a trace may violate `always_before` while satisfying `precedence` if frequency allows). Canonical layer must be defined (see §10).
* **Inconsistent constraints under loops / post-activation changes:** R10 (`1`) and R2 (`exactly one approval`) become inconsistent if `LOOP` or post-activation `ChangeVerifyRelease` cycles re-enter approval or payment. Procedural tree prevents re-entry, but DECLARE `response(Change,Suspend)` + skeleton `activ_freq Verify {1,2}` explicitly allow a second `Verify` and second `Release`, which the tree forbids. Without scoping (`Release` 1 vs `Release` after `Change` = exception), combined model is unsatisfiable for legitimate re-payment.
* **Vacuity:** All `response`/`precedence` rules are vacuously true when antecedent never occurs. E.g., `response(Escalation, Obtain)` passes in T1/T3/T4 where no Escalation occurs, masking missing opinion cases where Escalation was *expected* but not logged. Similarly `precedence(Obtain, Activate)` vacuous when no Activate. Need *existence* checks or case-attribute-triggered obligations to avoid vacuous passes; we deliberately do not add `existence(Sanctions Escalation)` because escalation is optional.
* **Missing case attributes:** Low/high risk decision, emergency authorization, joint authorization, and legal opinion deadline are not logged. R2, R5/R6, and R11 conditional logic cannot be evaluated correctly without them. Activity-only approximations (`noncoexistence`, `precedence`) are conservative and produce false positives (R5) or false negatives (R6). Resource SoD also fails if `org:resource` missing; we surface `not evaluated` rather than silent pass.
* **Timestamp-only limitations:** `temporal_profile` uses wall-clock hours only, ignoring business calendars, time zones, and case start vs business start. Mean/std dev are descriptive, not contractual; `zeta=2` still flags ~5% of normal cases. It also cannot enforce *deadlines* (e.g., opinion within 24h emergency) as hard constraints; that belongs in the data layer. Clock skew or coarse hourly granularity (as in test data) limits precision.
* **Support/confidence as normative truth risk:** `support=1.0` in `declare_model` does not mean the rule holds empirically with support 1.0; it is *metadata* from discovery, not a truth assertion. Using `confidence=1.0` normatively suggests universal validity, but our approximations (e.g., `precedence(Obtain,Activate)` confidence 0.85) deliberately lower confidence to signal conservatism. Consumers must not interpret high support as legal validity; otherwise discovered patterns are mistaken for prescribed policy.

# 10. Deployment Recommendation

**Canonical representations:**

* **Procedural backbone:** *Petri net / ProcessTree* is canonical for *intended* control-flow (Receive  PAR checks  Classify  XOR decision  Close). It is the reference for happy-path mining and simulation.
* **Policy layer:** **DECLARE is authoritative for activity-order obligations** (R1,R3,R4,R7,R8) and **External validation layer is authoritative for resource, data, and conditional obligations** (R2,R5/R6,R9,R11). Log Skeleton is authoritative for **cardinality** (R10) and auxiliary trace invariants. Temporal profile is **never authoritative** - advisory warnings only.

**Conformance check order (layered, fail-fast but exhaustive for diagnostics):**

1. **Structural integrity:** Validate log schema (activities, timestamps, resources). Flag `not evaluated` where attributes missing.
2. **Procedural conformance** (`pm4py.conformance_alignments` or `token_replay` against `procedural_model`): Checks happy-path conformance, yields `pass/fail` for backbone deviations (e.g., T8). Continue even if fail to collect declarative diagnostics.
3. **DECLARE conformance** (`pm4py.conformance_declare(log, declare_model)`): Apply strict Resolution A. Record failures with violated rule and confidence. For T6, produce dual verdict (strict vs permissive) via second run without `precedence(Obtain,Activate)`.
4. **Log-Skeleton conformance** (`pm4py.conformance_log_skeleton`): Validate `activ_freq`, `never_together`, `always_before/after`. Surfaces multiplicity violations.
5. **Resource / data-aware checks** (§7): Run SoD, pending clarification, emergency-policy, and R11 checks on DataFrame. This layer can **override** DECLARE on policy-dependent cases: if DECLARE fails solely on R5 precedence but data layer shows `24h` and external auth registry confirms joint authorization, escalate to human review instead of auto-reject.
6. **Temporal profile** (`pm4py.conformance_temporal_profile(log, temporal_profile, zeta=2.0)`): Run last; emit `warning` list per case (e.g., T7). Never flips overall `pass` to `fail`.

**Surfaced findings:**

* UI separates **Errors** (Procedural/DECLARE skeleton fail + data SoD fail) from **Warnings** (temporal) and **Policy-Dependent** (R5/R6 conflict). T6 appears as `Policy-Dependent: Legal precedence violated but emergency window satisfied - requires manual attestation of joint authorization` with both verdicts shown.
* Contradictory findings (e.g., procedural pass but DECLARE fail as in T5) are not merged; user sees `Earliest decisive violation: DECLARE altresponse(Request,Receive)` with trace highlighting the pending Request.
* All `not evaluated` due to missing attributes are shown explicitly to avoid silent non-compliance.
