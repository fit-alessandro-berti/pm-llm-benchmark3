## **1. Duplicate-handling decision tree**
The tree distinguishes duplicates based on **semantic alignment**, **object relationships**, and **source authority**:

```
Root: Check for exact technical duplicates (payload_hash + timestamp + source_event_key)
 Exact match  Drop (e.g., e03/e04 if payload_hash differs despite timestamp)
 Same timestamp, same activity, shared objects 
    Same payload  Quarantine (e.g., e03/e04: WMS enrichment conflict)
    Different payload  Retain both with qualifiers (e.g., "WMS-pick" vs. "Scanner-pick")
    Summary vs. detail  Merge attributes (e.g., e06/e07: WMS detail + ERP summary)
 Same timestamp, different activity 
    Harmonization collision  Retain both with provenance (e.g., e08/e09: "Dispatch" vs. "Accept")
    Concurrent distinct events  Retain both (e.g., e03/e05: separate picks)
 No shared objects  Unresolved (e.g., e13/e14: distinct payments)
```

## **3. Timestamp-tie ordering rules**
**Rules (semantic  deterministic):**
1. **Lifecycle constraints**: e.g., `e09` (acceptance) must precede `e10` (handover).
2. **Within-source sequence**: `source_seq` is only meaningful per system (e.g., WMS `e03` > `e06`).
3. **Object ownership**: `e06` (WMS) must precede `e07` (ERP) if WMS is authoritative for packing.
4. **Ingestion time**: Fallback for unresolved ties (e.g., `e04` ingested after `e03`).
5. **Stable fallback**: Microseconds are **not** added—only used if no other rule applies.

**Ordering examples:**
- **e03–e07 (10:00)**:
  `e03` (WMS-pick)  `e05` (Scanner-pick)  `e06` (WMS-pack)  `e07` (ERP-summary).
- **e08–e10 (10:15)**:
  `e08` (WMS-dispatch)  `e09` (Carrier-accept)  `e10` (Carrier-handover).
- **e11–e16 (12:00)**:
  `e11` (ERP-invoice)  `e12` (PSP-auth)  `e13` (PSP-capture)  `e14` (PSP-capture)  `e15` (ERP-summary)  `e16` (Billing-invoice).

**Why microseconds are dangerous**: They could artificially order `e04` (10:00:03) before `e03` (10:00:01), violating physical reality.

## **4. Conservative cleaning pipeline**
**Steps:**
1. **Pre-check**: Use `pm4py.ocel_drop_duplicates` on exact matches (e.g., `payload_hash + timestamp`).
2. **Qualified retention**: For same-timestamp events, retain both with qualifiers (e.g., `e03` as "WMS-pick").
3. **Merge summaries**: For `e06/e07`, merge attributes but preserve source provenance.
4. **Order by rules**: Apply lifecycle constraints first, then `source_seq`, then ingestion time.
5. **Provenance**: Store original `eid`, `source`, and `source_event_key` in a metadata table.

**Expected retained events**: ~20–25 (e.g., 17 after merging `e06/e07` and `e11/e16`).

## **6. PM4Py-oriented Python implementation**
```python
import pm4py
from copy import deepcopy
import pandas as pd

def clean_ocel_conservative(ocel_raw):
    # Step 1: Drop exact duplicates
    df = pm4py.ocel_drop_duplicates(ocel_raw, attribute_name="payload_hash")
    # Step 2: Retain qualified pairs (e.g., e03/e04)
    df = df[df['timestamp'] == df['original_timestamp']]
    df = df[df['activity'] == df['original_activity']]
    # Step 3: Merge summaries (e.g., e06/e07)
    df = merge_summary_events(df)
    # Step 4: Order by rules
    df = pm4py.ocel_sort_by_additional_column(
        df,
        attribute_name="custom_order",
        column_name="source_seq",
        column_name_2="ingested_at"
    )
    return df

def merge_summary_events(df):
    # Example: Merge e06 (WMS) and e07 (ERP)
    summary_events = df[df['activity'] == 'Pack Package']
    summary_events = summary_events.groupby('source_event_key').first().reset_index()
    df = pd.merge(df, summary_events, on='source_event_key', how='left')
    return df

# Custom verified-pair merge for e11/e16
def merge_invoice_events(df):
    invoice_events = df[df['activity'].isin(['Issue Invoice'])]
    invoice_events = invoice_events.merge(
        invoice_events.groupby('source_event_key').first(),
        on='source_event_key',
        suffixes=('_erp', '_billing')
    )
    return invoice_events
```

## **9. Failure modes & safeguards**
1. **Collapsing payments**: Aggressive merge of `e13/e14` via `have_common_object`.
2. **False rework**: Merging `e06/e07` without lifecycle context.
3. **Ingestion-time ordering**: Violates business rules (e.g., `e04` before `e03`).
4. **Unioning relations**: Merging `e08/e09` without preserving `D1` provenance.
5. **Microsecond bias**: Artificially ordering `e04` before `e03`.
6. **Source-authority loss**: Dropping `e14` due to `e15` merging.
7. **DFG misalignment**: Flattening `e06/e07` breaks WMS granularity.
8. **No provenance**: Blindly applying `pm4py` without manual review.

**Safeguards**:
- Always use `original_timestamp` as fallback.
- Audit `OC-DFG` for loops after merging.
- Validate `E2O` relations post-processing.
