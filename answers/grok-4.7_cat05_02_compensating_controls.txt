## 1. Control-Objective Decomposition

FEP-1 is a segregation rule aimed at one outcome: a single human must not both initiate and authorize an erroneous or fraudulent transfer. A different user id on `Release_Payment` is only one way to pursue that outcome. AV-2, MG-4, RA-7, and ED-1 cover different slices of it, and a clean event does not travel outside its slice.

| Threat | AV-2 | MG-4 | RA-7 | ED-1 |
|---|---|---|---|---|
| Single-operator input error (wrong invoice, duplicate, amount above the operator’s own limit, basic PO mismatch) | **Prevents** when it blocks; **detects** when it warns. Coverage is exactly the coded checks. | **Prevents** if an independent manager actually compares invoice, amount, and PO before settlement. A rubber stamp does not. | **Detects** on review. **Corrects** only while recall or cancellation is still possible. | Does not inspect the invoice. It **prevents** an unpermitted same-user path only when all seven conditions are enforced. |
| Single-operator diversion (operator pays a beneficiary they control) | **Partial prevention**: sanctions, bank-account ownership, and a bank-account change in the prior seven days. It does not establish who controlled a compromised account. | **Prevents** diversion it can see from bank details and payee identity, if independent and timely. | **Detects** after the fact. **Corrects** only inside the recall window. | Allows one operator only inside a low-amount, stable-vendor, stable-bank envelope, and only with the other conditions. Outside that envelope it is not a permission. |
| Collusion, or one person operating both roles (shared workstation, shared credential, dedicated pair that never challenges) | **Fails**. Collusion and compromised-account control are outside its design. | **Fails** when the manager is the colluding party, has an unresolved conflict, or whose credential is used by the operator. **Prevents** only a genuinely separate reviewer. | **Detects** some collusive results (a fabricated receipt) if the auditor re-performs substance. **Does not prove** who colluded. **Corrects** only inside the recall window. | **Fails** against operator–manager collusion. A token does not create independence. |
| Recently changed or unverified beneficiary account | **Prevents or warns** on a seven-day bank change and on ownership, when the service is up and the result is not overridden. | **Prevents** if bank details are actually reviewed before settlement. | **Detects** late. Recall is the only ordinary **correction**, and only for about 24 hours after the transfer. | Condition 4 **forbids** the same-user permission when a bank change occurred in the prior seven days. A token does not waive that condition. |
| Unsupported commercial payment (no receipt, fabricated service evidence, unreasonable consulting charge) | **Fails** for receipt and commercial reasonableness. A full pass is evidence only of duplicate, sanctions, ownership, seven-day bank change, operator limit, and basic PO match. | **Prevents** when the manager reviews the receipt or service report before settlement. **Fails** when the approval event has no such review. | **Detects** this class; AP-204 shows that it can. **Corrects** only if the finding lands inside the recall window. | Does not test goods received. Condition 6 borrows MG-4’s substance. Condition 5 borrows AV-2 and therefore still does not prove receipt. |
| Control bypass at the moment of release (validation outage, warning override, credential borrowed from the manager, settlement racing the reviewer) | **Fails open** if the service is down or the warning is overridden by the person who benefits. Overrideability is part of the control design, not a footnote. | **Prevents** the loss if a separate manager can still withhold settlement. **Fails** after irrevocable settlement. Post-release timing leaves a race. | **Detective** after settlement. Contingently **corrective** inside the bank recall window if the audit finishes in time to act. | **Fails open** unless token timing, amount, vendor age, bank stability, a live clean AV-2, pre-settlement independent approval, and one-business-day audit are all true together. It is a conditional permission, not a disappearance of the four-eyes objective. |

Two timing facts govern the whole set. For internal control, bank settlement is the irrevocable step, even if a court might later unwind it. The bank can usually recall a transfer for about 24 hours; after that, recovery is uncertain. A control that fires only after that window is an accountability record.

## 2. Equivalence and Sufficiency Test

Equivalence asks whether the package still delivers an independent challenge to the threats that FEP-1 exists to stop, before the transfer becomes irreversible, with evidence a reviewer can inspect. Sufficiency asks whether what remains uncovered is acceptable for that case’s inherent risk. A case can have a small ex post loss and still fail sufficiency, because sufficiency is judged on the exposure that existed when someone could still stop the money.

**Fully equivalent.** All of the following hold.

- **Timing.** An independent human decision with the power to stop the transfer occurs before irrevocable settlement. For a same-user release, the emergency token was active before `Prepare_Payment`.
- **Independence.** The challenger is not the preparer or releaser, is not a shared service credential, and has no unresolved conflict. User ids on a shared workstation, or a pair that repeatedly “approves” together without a documented cell design, do not satisfy this by themselves.
- **Coverage.** Every material threat raised by the case facts has a control that is actually capable of seeing it. A full AV-2 pass covers six technical checks. It does not cover goods received, commercial reasonableness, collusion, or account compromise.
- **Overrideability.** A warning was not overridden. If it was, the overrider is an independent manager acting under their own identity, with a recorded reason. The preparer using a manager’s credential is a failed override design.
- **Recoverability.** Where the human challenge is after release, settlement has not happened, and a substantive audit is completed with enough of the recall window left to act. An audit timestamp that merely starts at the edge of the window is thin corrective capacity.
- **Evidence quality.** The record shows what was reviewed (invoice, bank details, receipt or service report), not only that an activity named approval or ratification exists.
- **Collusion resistance.** No unresolved common-mode indicator sits on the only two humans in the chain. ED-1’s seven conditions, where used, all hold. ED-1 does not waive the objective; it is one route to meet it.

**Partially equivalent (technically nonconforming, but tolerable).** The material threats for that case were still challenged by an independent human before irrevocability, AV-2’s relevant checks actually ran, inherent risk is inside a modest band (stable vendor, no recent bank change, amount well inside the EUR 100,000 emergency ceiling, no contrary defect), and the gaps are formal or marginal: missing token on a convenience payment, review scope incompletely recorded, or audit at the edge of recall. The permission breach remains reportable. Partial equivalence is not a standing waiver for the next same-user payment.

**Merely mitigating.** At least one control reduces a real vector, but the case’s dominant threat is still open at settlement. A full AV-2 pass mitigates duplicates and bank-change risk while leaving a fabricated receipt untouched. A late audit mitigates impunity while leaving the money gone. Mitigation is credited to the control that worked. It is not promoted to equivalence of the package.

**Ineffective.** The control that could break the causal chain is absent, overridden by the beneficiary, conflicted, timed after irrevocability and after the recall window, or formally present but blind to the threat that materialized. Ex post discovery that the payee was legitimate does not reopen the chain. A distinct user id with impaired independence and a defect that passed through settlement is ineffective for the objective, even though nominal FEP-1 holds.

**Why matching expected loss is not enough.** Expected loss collapses timing, coverage, independence, and tails into one product.

- **Decision rights.** FEP-1 and ED-1 allocate authority. A convenient same-user payment that happens to be correct still spent an authority the operator did not have.
- **Coverage.** Two packages with the same average loss on duplicates are not equivalent if one of them cannot see a fabricated receipt.
- **Reversibility.** A euro before settlement and the same euro after the recall window are not the same exposure. Settlement changes the shape of the loss, not only its probability.
- **Common-mode failure.** A second user id operated from the same session, or a manager credential held by the preparer, is one failure mode. Two independent people are two. Equal historical loss rates do not make those designs equivalent.
- **Accountability.** A package that cannot show who was in a position to stop the payment fails even when the amount is right.
- **Precedent.** Tolerating a stream of convenience bypasses destroys the base rate that makes a true emergency visible.
- **Appetite is applied after those tests, not instead of them.** Amount, vendor age, and bank stability decide whether a residual uncovered threat is tolerable. They do not decide the classification alone. EUR 1,800 with an independent pre-settlement review and EUR 1,800 with no second human at all are different control results. EUR 900,000 that later proves genuine is still a failed control if nobody reliable checked the new bank account before settlement.

Mapping used below: fully equivalent → `OBJECTIVE_MET`; partially equivalent → `OBJECTIVE_PARTIALLY_MET`; ineffective against the dominant threat, or merely mitigating while exposure stays outside appetite → `OBJECTIVE_FAILED`; dominant mechanism stopped before completion → `LOSS_PREVENTED_BEFORE_COMPLETION`; a fact that would move the case across those boundaries is unresolved → `INDETERMINATE`.

## 4. Preventive–Detective–Corrective Comparison

**Semantics chosen.** A control is classified against two different targets, and the label follows the target it can still affect.

- Against the **release decision**, anything after `Release_Payment` is detective. The release has already been made.
- Against **irrevocable loss**, an independent manager who can still withhold `Bank_Settlement` is preventive. The usual 24-hour bank recall is contingently corrective: it corrects only if someone finishes the investigation and the bank accepts the recall in time. After that window, the same audit activity is detective only. Exceptional litigation is not treated as control capacity.
- A manager action **after release and before settlement** is therefore **hybrid**: detective on the release, preventive on the loss. ED-1 condition 6 uses the loss target (“before bank settlement”), so a substantive hybrid review can complete ED-1. It remains weaker than a pre-release approval because settlement can race the reviewer. AP-207 had that race and won it (ratify 14:40, settle 16:00). A process that settled at release would have made the same event purely detective.

## 5. Counterfactual and Residual-Risk Analysis

Ranges below are qualitative. None is a measured probability.

**AP-202.** The plausible mechanism is beneficiary diversion: a new vendor, a bank account changed two hours before prepare, no receipt, an operator-limit warning, and a later link from that account to an employee’s relative. AV-2 broke the information problem and then lost the decision, because u23 overrode the warning with m09’s credential. m09’s ratification could not break the chain two days later, and the 12 May audit sat outside recall. Funds stayed out. A truly independent second releaser, using their own identity and unable to borrow m09’s credential, would likely have refused a EUR 480,000 first payment to a hours-old bank account with no receipt. What would remain is forged supporting paperwork good enough to persuade an honest releaser, and the unresolved question of whether m09 was a participant. The conflict means m09 was never a valid substitute for that second releaser.

**AP-204.** The plausible mechanism is an unsupported consulting payment backed by a fabricated service receipt, passed by two ids that share a workstation and a very high joint volume. AV-2’s full pass is the expected result on that mechanism, because receipt fraud is outside its checks. No manager was in the chain. RA-7 broke the detection problem and missed the recovery problem: the finding on 8 May is outside the usual recall window, and no recovery is recorded. An independent releaser outside the u12/u13 pair, required to tie the receipt to a real engagement, would likely have stopped a crude fabrication and might still have accepted a polished forgery. What remains even then is commercial-reasonableness judgment on consulting, which neither FEP-1 nor AV-2 settles. The pair’s denial is compatible with negligence and with collusion; both leave the same control gap.

**AP-205.** The plausible mechanism is a duplicate pay of EUR 12,000 to an established vendor. AV-2’s block broke the chain before release, and cancellation closed the item. An independent second releaser would probably also have stopped an obvious duplicate, but the case does not depend on that. What remains exposed is the next invoice from u44 that is not a duplicate: the attempted same-user release shows the path was open, and AV-2 would not supply a goods-receipt check.

**AP-208.** The plausible mechanism, which did not mature into a loss, is payment of EUR 900,000 to a vendor only eight months old whose bank account had changed three days earlier, released by one operator while ownership validation was down and the manual checklist was unsigned. Nothing in the executed package broke that chain before the 16:00 settlement. m21’s next-day ratification and the 9 May audit were outside reliable correction. A truly independent second releaser would likely have halted release until bank ownership was re-established, because the amount and the recent bank change are visible without AV-2. What remains is a shared waiver culture: if the second person is trained to release whenever the service is down and the checklist is blank, independence of identity does not restore the check. Ex post legitimacy removes realized loss. It does not show that the chain was broken.

**AP-201.** The plausible mechanism is a small convenience error or a low-value diversion on a six-year office-supply vendor with no bank change. AV-2 broke the technical slice (duplicate, limit, ownership, recent bank change, sanctions, basic PO). m04’s 08:30 review could still break the human slice before the 10:00 settlement. The audit could barely have supported a recall and is not the control that makes this tolerable. A truly independent second releaser would have removed the permission breach and added little loss reduction, because inherent risk and the pre-settlement review were already low. That small loss delta is why expected-loss matching is the wrong sole test: authority and precedent still differ. What remains is review depth. The record says m04 reviewed, and it does not say that invoice, bank details, and receipt were all in that review.

**AP-209.** The plausible mechanism, imported from the same pair’s same-day behavior, is another thinly challenged payment, here EUR 42,000 to a five-year vendor with no bank change. In this case no defect was found, and the 05 May 10:00 audit was still inside the recall window, so detective capacity could have broken a chain if a defect had been present. Whether u13 already broke it is unknown. Replacing u13 with a releaser outside that pair and that workstation would likely reduce the common-mode risk that AP-204 demonstrates, and would change little if u12 and u13 are already an honest designed cell. Those two futures are why the case stays indeterminate. What remains either way is receipt testing: AV-2’s pass does not provide it.

**AP-203, as the contrasting emergency.** The plausible mechanism is an overstated or misdirected EUR 75,000 machine-repair payment under outage pressure. m02’s pre-release review of invoice, bank account, and service report is the break, with AV-2 covering the technical slice and the same-day audit holding corrective capacity that was not needed. A separate releaser would likely add little beyond m02’s documented review. Residual risk is a low-indicator collusion between u31 and m02, which ED-1 does not remove.

## 6. Evidence and Monitoring Recommendations

Collect these as case attributes, not as extra activities that automatically “pass” a case.

- Token-service issue time, incident id, and incident open time, from the token system, compared with `Prepare_Payment`.
- Manager level, conflict-of-interest flag (including who sets whose rating), and an attestation of which artifacts were opened: invoice, bank details, receipt or service report.
- Override credential owner, acting user, and reason text.
- Vendor master start date, and the bank-account change timestamp plus the ownership evidence that existed at release.
- Workstation, session, and source host for prepare and release.
- `Bank_Settlement` in the event log for every completed payment. AP-201 and AP-203 currently depend on narrative times.
- Audit procedure checklist, start, and completion. Today’s `Audit_Review` timestamp cannot show whether condition 7 was completed or only opened.
- Bank recall request and result.
- A designed-cell register if a standing pair such as u12/u13 is legitimate. Until that exists, concentration stays an exception signal.

Monitoring rules, each an alert and not proof of misconduct:

- **Same-user rate.** Report the weekly count and rate of completed payments whose preparer equals releaser, with denominator equal to completed releases, not attempts. Alert every completed same-user release whose token was not active before prepare. A rate threshold that allows a steady convenience bypass will hide the pattern AP-201 represents. Keep AP-205 in a separate “attempted and blocked” series so cancellations do not dilute the completed-payment rate.
- **Override rate.** Alert on every `Override_Warning`. Raise severity immediately when the acting resource is the preparer or the credential owner differs from the actor, as in AP-202. The alert proves a bypass of AV-2. It does not, alone, prove fraud or that the credential owner consented.
- **Late manager approval.** Alert when the earliest `Manager_Approve` or `Manager_Ratify` is after `Bank_Settlement`, or when a same-user release has no independent manager event before settlement. Split the metric into before release, hybrid (after release, before settlement), and after settlement. Hybrid is not automatically late under ED-1; after settlement is.
- **Audit before the recall window.** For every same-user release, override, recent bank change, or validation outage, alert if no audit completion exists by settlement plus 24 hours. Track hours of recall window remaining at audit start. AP-201 (about one hour at the recorded time) and AP-207 (about four hours if that timestamp is only a start) must not look identical in the dashboard. A timely event is not proof the auditor re-performed receipt or payee tests.
- **Repeated resource pairs.** Over a rolling 30 days, alert on pair count and on the pair’s share of each releaser’s payments. Thirty-seven joint payments by u12 and u13 would clear any reasonable investigation threshold. The alert is a design-or-collusion question. AP-209 shows why the pair alert cannot be a finding: the same pair can appear on a payment with no defect and a timely audit.
- **Shared workstations.** Alert when prepare and release user ids differ but host or session evidence coincides, and when one host dominates a pair. Identity segregation with a shared session is a common-mode failure signal, not proof that one person operated both ids.
- **Bank-change proximity.** Alert on any payment whose beneficiary account changed in the prior seven days, matching AV-2’s window, and use a higher severity inside 24 hours (AP-202, two hours) than inside seven days (AP-208, three days). Combine with new-vendor and override flags. The alert is a reason to confirm ownership. It is not proof of diversion; AP-208’s change sat inside the window and the payment was later legitimate.
- **Control outages.** Alert on `Validation_Service_Unavailable` followed by `Release_Payment` without a later full AV-2 pass and without a signed manual checklist attributed to a second person. Prefer a hard release-stop while AV-2 is down. An outage-plus-release alert proves the gate was open. It does not prove the payment was wrong.

Use the alerts as inputs to the section 2 test. A case moves toward a misconduct investigation only with evidence beyond the activity pattern: credential custody, authorship of a fabricated receipt, or beneficiary kinship. Until then the right operational states are “permission breach,” “independence not established,” “exposure accepted,” or “loss prevented.”

## 7. PM4Py and pandas Checking Code

The block reconstructs the log in memory, asks PM4Py for the nominal four-eyes split, and separately flags the blocked attempt. Flags are evidence. They do not emit `OBJECTIVE_MET`, `OBJECTIVE_FAILED`, or any other verdict from section 3. In particular, the code will mark AP-203 and AP-207 as nominal same-user violations even though the control objective is met, and it will mark AP-204 as a nominal pass even though the objective failed.

PM4Py behavior that this environment cannot guarantee across versions:

- `filter_four_eyes_principle` has, in several 2.x releases, default `positive=True`, which **keeps cases that satisfy** four-eyes and drops violators. The script therefore passes `parameters={"positive": False}` to collect violators, and it always recomputes the same-user completed set in pandas. Some versions ignore `positive`, accept only an `EventLog`, or live under `pm4py.algo.filtering` rather than the top-level wrapper. The printed PM4Py id list must be reconciled to the pandas list before anyone relies on it.
- Pair logic differs by version: any occurrence versus time-ordered occurrence, first pair versus any same-resource pair, and whether a case missing `Release_Payment` is dropped or treated as vacuously compliant. AP-205 uses `Attempt_Release`, so a filter on `Release_Payment` must not be read as a judgment on AP-205 either way.
- `format_dataframe` may sort rows, keep or drop extra columns, and coerce timestamps to naive UTC. The script pre-parses UTC and also strips timezone on the PM4Py copy for that reason. Resource column `org:resource` is the usual default; it is not reattached by row position after formatting, because sorting would misalign it.

def _as_utc(value):
    ts = pd.to_datetime(value, utc=True)
    if isinstance(ts, pd.Series):
        return ts
    return ts


def _first_time(frame, case_id, activities):
    sub = frame[
        (frame["case:concept:name"] == case_id)
        & (frame["concept:name"].isin(activities))
    ]
    if sub.empty:
        return pd.NaT
    return sub["time:timestamp"].min()


def _case_ids_from_pm4py(result):
    if isinstance(result, pd.DataFrame):
        column = (
            "case:concept:name"
            if "case:concept:name" in result.columns
            else result.columns[0]
        )
        return set(result[column].astype(str).unique())
    ids = set()
    for trace in result:
        attributes = getattr(trace, "attributes", {}) or {}
        if "concept:name" in attributes:
            ids.add(str(attributes["concept:name"]))
    return ids


def pm4py_violating_ids(pm_log):
    """Return (ids, note). positive=False is not stable across PM4Py versions."""
    try:
        filtered = pm4py.filter_four_eyes_principle(
            pm_log,
            "Prepare_Payment",
            "Release_Payment",
            parameters={"positive": False},
        )
        return (
            _case_ids_from_pm4py(filtered),
            "pm4py.filter_four_eyes_principle(..., parameters={'positive': False})",
        )
    except Exception as exc:  # version skew: signature, positive flag, or log type
        return set(), f"parameterized four-eyes call failed: {type(exc).__name__}: {exc}"


def pandas_completed_pairs(frame):
    prepare = (
        frame.loc[frame["concept:name"] == "Prepare_Payment",
                  ["case:concept:name", "time:timestamp", "org:resource"]]
        .sort_values("time:timestamp")
        .groupby("case:concept:name", as_index=False)
        .first()
        .rename(columns={"time:timestamp": "prepare_time", "org:resource": "preparer"})
    )
    release = (
        frame.loc[frame["concept:name"] == "Release_Payment",
                  ["case:concept:name", "time:timestamp", "org:resource"]]
        .sort_values("time:timestamp")
        .groupby("case:concept:name", as_index=False)
        .first()
        .rename(columns={"time:timestamp": "release_time", "org:resource": "releaser"})
    )
    return prepare.merge(release, on="case:concept:name", how="inner")

    activities = raw.groupby("case:concept:name")["concept:name"].agg(lambda s: set(s))
    blocked_attempts = sorted(
        case_id
        for case_id, names in activities.items()
        if "Attempt_Release" in names
        and "Automated_Validate_Block" in names
        and "Release_Payment" not in names
    )

    print()
    print("PM4Py note:", pm_note)
    print("PM4Py nominal violating case ids (version-sensitive):", sorted(pm_ids))
    print("Pandas completed same-user case ids:", sorted(pandas_violations))
    print("Symmetric difference PM4Py vs pandas:", sorted(pm_ids.symmetric_difference(pandas_violations)))
    print("Attempted but blocked releases (not Release_Payment):", blocked_attempts)

    pair_counts = (
        pairs.groupby(["preparer", "releaser"]).size().rename("pair_case_count").reset_index()
    )
    pairs = pairs.merge(pair_counts, on=["preparer", "releaser"], how="left")
    pairs["repeated_pair"] = pairs["pair_case_count"] >= 2

    facts = CASE_FACTS.copy()
    facts["emergency_token_time"] = _as_utc(facts["emergency_token_time"])

    for case_id, case_events in raw.groupby("case:concept:name"):
        prepare_time = _first_time(case_events, case_id, ["Prepare_Payment"])
        release_time = _first_time(case_events, case_id, ["Release_Payment"])
        attempt_time = _first_time(case_events, case_id, ["Attempt_Release"])
        manager_time = _first_time(
            case_events, case_id, ["Manager_Approve", "Manager_Ratify"]
        )
        audit_time = _first_time(case_events, case_id, ["Audit_Review"])
        names = set(case_events["concept:name"])
        if "Automated_Validate" in names and "Automated_Validate_Warning" not in names:
            av_from_log = "full_pass_event"
        elif "Automated_Validate_Warning" in names:
            av_from_log = "warning_event"
        elif "Automated_Validate_Block" in names:
            av_from_log = "block_event"
        elif "Validation_Service_Unavailable" in names:
            av_from_log = "unavailable_event"
        else:
            av_from_log = "no_av_event"
        override_actor = case_events.loc[
            case_events["concept:name"] == "Override_Warning", "org:resource"
        ]
        rows.append(
            {
                "case:concept:name": case_id,
                "prepare_time": prepare_time,
                "release_time": release_time,
                "attempt_time": attempt_time,
                "manager_time": manager_time,
                "audit_time": audit_time,
                "av_event_class": av_from_log,
                "override_actor": override_actor.iloc[0] if len(override_actor) else pd.NA,
                "released": pd.notna(release_time),
            }
        )
    timing = pd.DataFrame(rows)

    evidence = (
        timing.merge(pairs, on="case:concept:name", how="left")
        .merge(facts, on="case:concept:name", how="left")
    )

    evidence["token_before_prepare"] = (
        evidence["emergency_token_time"].notna()
        & evidence["prepare_time"].notna()
        & (evidence["emergency_token_time"] < evidence["prepare_time"])
    )
    evidence.loc[
        evidence["token_time_quality"].isin(
            ["logged_after_prepare_disputed", "stated_active_time_unknown"]
        ),
        "token_before_prepare",
    ] = pd.NA

    evidence["amount_below_100k"] = evidence["amount_eur"] < 100000
    evidence["vendor_tenure_at_least_180d"] = evidence["vendor_days"] >= 180

    def manager_timing(row):
        if pd.isna(row["manager_time"]):
            return "none"
        if pd.notna(row["release_time"]) and row["manager_time"] <= row["release_time"]:
            return "before_release"
        if pd.notna(row["settlement_time"]) and row["manager_time"] <= row["settlement_time"]:
            return "after_release_before_settlement"
        if pd.isna(row["settlement_time"]) and pd.notna(row["release_time"]):
            return "after_release_settlement_unknown"
        if pd.notna(row["settlement_time"]) and row["manager_time"] > row["settlement_time"]:
            return "after_settlement"
        return "unclassified"

    evidence["manager_timing"] = evidence.apply(manager_timing, axis=1)

    def hours_before(later, earlier):
        if pd.isna(later) or pd.isna(earlier):
            return pd.NA
        return (later - earlier) / pd.Timedelta(hours=1)

    evidence["audit_hours_after_release"] = [
        hours_before(a, r) for a, r in zip(evidence["audit_time"], evidence["release_time"])
    ]
    evidence["audit_hours_after_settlement"] = [
        hours_before(a, s) for a, s in zip(evidence["audit_time"], evidence["settlement_time"])
    ]
    evidence["recall_hours_remaining_at_audit"] = [
        (24 - h) if pd.notna(h) else pd.NA
        for h in evidence["audit_hours_after_settlement"]
    ]
    # Weekend-only business calendar. Company holidays are not in the record.
    evidence["audit_by_next_business_day_close"] = [
        pd.notna(release) and pd.notna(audit) and (
            audit <= (release.normalize() + pd.tseries.offsets.BDay(1)
                      + pd.Timedelta(hours=23, minutes=59, seconds=59))
        )
        for release, audit in zip(evidence["release_time"], evidence["audit_time"])
    ]
    evidence["audit_inside_24h_of_settlement"] = [
        pd.notna(h) and h <= 24 for h in evidence["audit_hours_after_settlement"]
    ]
    evidence["av_clean_no_override"] = evidence["av_result"].eq("full_pass") & ~evidence[
        "override_by_preparer"
    ].fillna(False)
    evidence["manager_before_settlement"] = evidence["manager_timing"].isin(
        ["before_release", "after_release_before_settlement"]
    )
    evidence["same_user_override"] = evidence["override_by_preparer"].fillna(False) & (
        evidence["override_actor"] == evidence["preparer"]
    )

    # Strict preliminary ED-1 screen. Unknown token or unknown review => not True.
    # This is an evidence screen, not an authorization decision.
    def ed1_screen(row):
        if not bool(row["released"]) or not bool(row["same_user_completed"]):
            return "not_a_completed_same_user_payment"
        checks = [
            row["token_before_prepare"] is True,
            bool(row["amount_below_100k"]),
            bool(row["vendor_tenure_at_least_180d"]),
            row["bank_change_7d"] is False,
            bool(row["av_clean_no_override"]),
            (row["manager_independent"] is True) and bool(row["manager_before_settlement"]),
            row["review_substantive"] is True,
            bool(row["audit_by_next_business_day_close"]),
        ]
        if any(v is pd.NA for v in [
            row["token_before_prepare"],
            row["manager_independent"],
            row["review_substantive"],
        ]):
            return "unknown_input"
        return "screen_pass" if all(checks) else "screen_fail"

    evidence["ed1_evidence_screen"] = evidence.apply(ed1_screen, axis=1)
    evidence["judgment_status"] = "UNSCORED_EVIDENCE"

    columns = [
        "case:concept:name",
        "preparer",
        "releaser",
        "same_user_completed",
        "repeated_pair",
        "pair_case_count",
        "shared_workstation_concern",
        "amount_eur",
        "amount_below_100k",
        "vendor_tenure_at_least_180d",
        "bank_change_7d",
        "token_time_quality",
        "token_before_prepare",
        "av_result",
        "av_event_class",
        "av_clean_no_override",
        "same_user_override",
        "manager_timing",
        "manager_independent",
        "conflicted_manager",
        "review_substantive",
        "manager_before_settlement",
        "settlement_source",
