## 1. Interaction-graph description

An object-centric view is best modeled as a **typed interaction hypergraph**: objects are nodes, and each event is a hyperedge relating multiple objects (or equivalently an event-node connected to many object-nodes). Cross-instance “bottlenecks” here are mostly **dependency structures** (AND-joins, shared tools, shared lots, consolidation policies) rather than a single saturated machine.

### Important node types
- **Job**: J1–J6 (case-like instances).
- **Component**: C1–C6 (job-specific inputs).
- **ComponentLot**: L7, L8 (coupling via shared material governance).
- **Batch**: B1, B2 (synchronization objects).
- **Machine**: CNC-2, OVEN-1, TEST-1 (capacity objects).
- **Tool**: FIX-A, RACK-7, CAL-3 (capacity/eligibility objects).
- **Shipment**: S1–S3 (post-pack coupling objects).
- **Event (derived)**: e.g., `E_B1_Cure@12:05` (used to represent multi-object relations explicitly).

### Important edge types / qualifiers
- **Structural O2O (observed)**: `requires` (Job→Component), `contains` (Lot→Component), `batches` (Batch→Job), `consolidates` (Shipment→Job).
- **Event–object (observed)**: `relates_to` (Event→Object). Key because one event can bind many jobs/tools/machines at once.
- **State / governance (observed but sometimes inconsistently linked)**: `Quarantine Lot`, `Release Lot`, tool “cleaning/quarantine”, `Calibrate`.
- **Derived dependency (inferred)**: `waits_for` (Job→{Batch start / Tool availability / Shipment partner}) and `depends_on` (Job→Job via shared object). These are not logged as activities.

### Higher-order motifs (multi-type, >2 object types)
1) **Batch AND-join with shared equipment**: (Job readiness) ∧ (RACK-7 available) ∧ (OVEN-1 scheduled) ⇒ `Batch Cure` for B1/B2. Early-ready jobs inherit the lateness of the last-ready job and/or shared rack state.
2) **Tool-gated machine processing**: (Job at CNC-2) ∧ (FIX-A available) ⇒ `Machine Process`. A held tool can create *machine idleness with job waiting* despite moderate utilization.
3) **Lot-governance coupling with asymmetric enforcement**: L7 quarantine/release relates to {C2, C5, J2, J5}. Supervisor override lets J2 “escape” the hold while J5 does not, creating variance and hard-to-predict spillovers.
4) **Shipment consolidation barrier**: dispatch of S1 depends on completion/packing of multiple jobs; early packed jobs (J1) wait for late partners (J4) even when shipping activities are fast once started.
5) **Calibration-induced eligibility gap**: TEST-1 may be idle while CAL-3 is recalibrated; job waiting is driven by tool eligibility, not test machine capacity.

### Which edges are direct observations vs inferred
- **Direct (observed)**: the provided O2O relations (`requires/contains/batches/consolidates`) and the multi-object timing facts (e.g., `Batch Cure` at 12:05 relates to B1, OVEN-1, RACK-7, J1–J3, C1–C3; lot quarantine/release at 10:20/13:50; FIX-A acquire/release; CAL-3 recalibration).
- **Inferred**: any “waiting” or “blocking” relation (e.g., J4 waiting for FIX-A; J1 waiting for J4 via S1). These are supported by temporal alignment but not explicitly recorded as wait events.

## 2. Quantitative delay decomposition

Below, each number is a **conditional** delay decomposition that depends on an explicit counterfactual assumption; none is a causal proof.

### (A) Synchronization-induced waiting in Batch B1 (OVEN-1 + RACK-7)

**Given**: B1 starts at 12:05; readiness times: J1 08:10, J2 08:25, J3 11:55.

1) **J1 total pre-batch wait**:
- Calculation: \(12{:}05 - 08{:}10 = 3\text{h }55\text{m}\).
- Synchronization component (waiting for latest-ready job J3):
  - \(11{:}55 - 08{:}10 = 3\text{h }45\text{m}\).
- Residual “start overhead after last-ready”:
  - \(12{:}05 - 11{:}55 = 10\text{m}\).
- **Counterfactual assumption**: B1’s start time is driven by an AND-join that waits until all batched jobs are ready; the 10m residual is loading/setup that would occur even if J1 were alone.

2) **J2 total pre-batch wait**:
- Calculation: \(12{:}05 - 08{:}25 = 3\text{h }40\text{m}\).
- Synchronization component (waiting for J3):
  - \(11{:}55 - 08{:}25 = 3\text{h }30\text{m}\).
- Residual overhead:
  - \(12{:}05 - 11{:}55 = 10\text{m}\).
- **Counterfactual assumption**: same as above; additionally assumes J2’s readiness timestamp is trustworthy and comparable to J3’s.

Interpretation: even with **OVEN-1 not fully utilized**, B1 imposes multi-job waiting because the controlling constraint is **co-readiness + shared rack** rather than oven busy time.

### (B) Delay plausibly associated with FIX-A for J4 at CNC-2

**Given**: J3 holds FIX-A 09:00–11:40; J4 reaches CNC-2 at 09:50; CNC-2 is idle 10:05–10:47; J4 `Machine Process` starts 11:45 and uses FIX-A.

3) **J4 “arrival-to-process-start” delay**:
- Calculation: \(11{:}45 - 09{:}50 = 1\text{h }55\text{m}\).
- Plausible FIX-A–gated portion using the strongest alignment cue (tool release then immediate start):
  - From earliest plausible start during observed CNC idleness (10:05) to tool release (11:40): \(11{:}40 - 10{:}05 = 1\text{h }35\text{m}\).
  - Residual from tool release to process start: \(11{:}45 - 11{:}40 = 5\text{m}\).
- **Counterfactual assumption**: if FIX-A had been available by ~10:05 (and no other hidden prerequisites), J4 could have started during the documented CNC idle window; the 1h35m reflects “waiting while the gating tool is held elsewhere.”

This decomposition is **consistent** with tool contention but could alternatively reflect unobserved setup, programming, staffing, or priority rules.

### (C) Delay imposed on J1 by S1 consolidation

**Given**: J1 packed at 13:30; J4 packed at 19:10; S1 dispatches at 19:25. Other shipments dispatch 25–35 min after the last job is packed.

4) **J1 pack-to-dispatch wait under consolidation**:
- Calculation: \(19{:}25 - 13{:}30 = 5\text{h }55\text{m}\).
- “Excess” waiting relative to typical post-pack dispatch lag:
  - If baseline lag is 25m: expected \(13{:}55\), excess \(19{:}25 - 13{:}55 = 5\text{h }30\text{m}\).
  - If baseline lag is 35m: expected \(14{:}05\), excess \(19{:}25 - 14{:}05 = 5\text{h }20\text{m}\).
- **Counterfactual assumption**: absent consolidation with J4, J1 would follow the same load/dispatch cadence as S2/S3 (25–35m after last pack), and carrier availability is not the binding constraint.

### (D) Delay plausibly associated with CAL-3 for J6 at TEST-1

**Given**: J6 ready for final test at 16:05; J5 tests 16:10–16:35; CAL-3 recalibrated 16:35–17:20; J6 tests 17:25–17:50; TEST-1 idle 16:35–17:25.

5) **J6 readiness-to-test-start wait**:
- Calculation: \(17{:}25 - 16{:}05 = 1\text{h }20\text{m}\).

6) **Portion plausibly attributable to CAL-3 recalibration** (eligibility gap while TEST-1 is idle):
- Calculation: \(17{:}25 - 16{:}35 = 50\text{m}\).
- **Counterfactual assumption**: if CAL-3 were available/valid immediately after J5 finishes at 16:35 (or a spare calibrated CAL-3 existed), J6 would start promptly; the 50m captures “machine idle but job waiting due to tool eligibility.”

### (E) Additional explicit decomposition: Batch B2 start (RACK-7 cleaning vs job synchronization)

**Given**: J4 ready 13:10; J5 ready 14:40; B2 starts 14:50; OVEN-1 idle 12:55–14:50; RACK-7 “cleaning/quarantine” until 14:35.

7) **J4 pre-batch wait for B2**:
- Total: \(14{:}50 - 13{:}10 = 1\text{h }40\text{m}\).
- Decomposition:
  - Rack unavailability: \(14{:}35 - 13{:}10 = 1\text{h }25\text{m}\).
  - Waiting for partner job readiness after rack returns: \(14{:}40 - 14{:}35 = 5\text{m}\).
  - Load/start overhead: \(14{:}50 - 14{:}40 = 10\text{m}\).
- **Counterfactual assumption**: B2 can only start when both the required rack is available and all batched jobs are ready; OVEN-1 idleness indicates oven capacity was not the limiting resource during this window.

## 4. What flattening misses

### Job viewpoint (Job-flattened log/DFG)
- **Visible**: within-job control-flow (Release→Stage→Process→Inspect→Pack→Dispatch), rework frequency, median edge times.
- **Hidden/duplicated**:
  - Hides *synchronization barriers* (batch start waits), *tool eligibility waits* (FIX-A, CAL-3), and *post-pack consolidation waits* (shipment partners).
  - Duplicates multi-object events: a single `Batch Cure` hyperedge becomes three per-job events, masking that the jobs were synchronized.
  - Can entirely omit lot governance events (Quarantine/Release) depending on relation extraction.
- **Misleading conclusion**: “No job outlier ⇒ no systemic bottleneck.” In reality, coupling can create **high variance and cascading delays** while keeping total durations within ~2 SD when the sample is small and delays are shared rather than concentrated in one job.

### Machine viewpoint (Machine-flattened summary)
- **Visible**: machine sequences and logged utilization, longest gaps between *machine events*.
- **Hidden/duplicated**:
  - Hides whether a machine is idle because of *no demand* vs *demand blocked by missing tool/batch/lot policy*.
  - Utilization ignores waiting that happens “before the machine” (e.g., jobs ready but rack quarantined) and may miss unlogged setup/cleaning.
- **Misleading conclusion**: “Utilization 44–58% ⇒ capacity is fine.” Low utilization can coexist with long job waiting when the true constraint is an **AND-condition** (machine + specific tool + synchronized cohort + governance).

### Batch viewpoint (Batch-flattened)
- **Visible**: batch start/cure times and batch membership (B1 with J1–J3; B2 with J4–J5).
- **Hidden/duplicated**:
  - Can hide how long early jobs waited *to enter* the batch and why one job was late.
  - Low frequency (“only 2 batches”) can look unimportant despite large waiting impact per batch.
- **Misleading conclusion**: “Batching is rare ⇒ minimal effect.” Here, each batch creates an **AND-join** with hours of induced waiting.

### Tool viewpoint (Tool-flattened)
- **Visible**: holds and state changes (FIX-A acquire/release; CAL-3 recalibrate; RACK-7 cleaning/quarantine).
- **Hidden/duplicated**:
  - If jobs are not consistently linked to tool state events, the tool log looks like maintenance noise.
  - Without explicit “wait” events, you cannot see the queue, only the tool occupancy timeline.
- **Misleading conclusion**: “Machines are idle so tools aren’t limiting.” The evidence shows the reverse: machines idle **because** tools are limiting.

### ComponentLot viewpoint (ComponentLot-flattened)
- **Visible**: governance (Quarantine Lot 10:20; Release Lot 13:50) and which components/jobs are co-affected.
- **Hidden/duplicated**:
  - If extraction omits lot↔job links, lot holds disappear from job traces and cannot explain waiting.
  - Overrides create “policy vs reality” divergence: the lot view says “blocked,” but one job proceeded anyway.
- **Misleading conclusion**: “Lot events don’t affect flow.” For J5, the lot release is a plausible gating condition; for J2, the override creates exceptional coupling patterns.

### Shipment viewpoint (Shipment-flattened DFG)
- **Visible**: Create Shipment→Load→Dispatch with short medians.
- **Hidden/duplicated**:
  - Hides *pre-load waiting of already packed jobs* for their shipment partners (J1 waiting for J4 inside S1).
  - Treats shipment execution as fast, conflating “shipment processing time” with “job waiting time for shipment completion.”
- **Misleading conclusion**: “Shipping is fast.” Shipping activities can be fast while shipment **policies** create hours of waiting.

### Why low machine utilization can coexist with long job waiting
Because the limiting constraints are often **combinatorial** (e.g., OVEN-1 *and* RACK-7 *and* all batch members ready; CNC-2 *and* FIX-A; TEST-1 *and* CAL-3 validity), a single missing prerequisite can stall a job while leaving the primary machine idle. Flattenings that only see machine events interpret idleness as “no bottleneck,” but OCEL reveals **blocked demand** rather than absent demand.

## 5. Object-lifecycle evidence

### Narrative A: B1 synchronization couples J1/J2/J3 via {B1, OVEN-1, RACK-7, components}
- **Temporal precedence (observed)**:
  - J1 ready for batch at 08:10; J2 at 08:25; J3 at 11:55.
  - `E_B1_Cure@12:05` relates to {B1, OVEN-1, RACK-7, J1, J2, J3, C1, C2, C3}.
- **Resource feasibility (observed/inferred)**:
  - Feasible curing requires OVEN-1 and RACK-7 simultaneously; B1 uses both.
  - J1/J2 feasibility without J3 is unknown (policy-dependent), but the event binds all three jobs at once.
- **Policy constraints (inferred)**:
  - Batch policy likely enforces a cohort (fill-to-3 or planned set B1); otherwise J1/J2 could have been processed earlier.
  - Shared RACK-7 implies only one curing setup at a time; this creates cross-batch coupling too.
- **Causal speculation (clearly speculative)**:
  - If B1 is scheduled to wait for all members, then J3’s later readiness (11:55) is a direct driver of J1/J2 waiting (3h30–3h45 synchronization component). If instead readiness timestamps are optimistic, the delay could come from earlier unobserved constraints (e.g., component availability), not from J3.

### Narrative B: FIX-A contention delays J4 at CNC-2 and spills into shipment S1, delaying J1
- **Temporal precedence (observed)**:
  - J3 holds FIX-A 09:00–11:40.
  - J4 reaches CNC-2 at 09:50; CNC-2 is idle 10:05–10:47.
  - J4 `Machine Process` starts 11:45 and relates to {J4, C4, CNC-2, FIX-A}.
  - J1 packed at 13:30; J4 packed at 19:10; S1 dispatches at 19:25.
- **Resource feasibility (observed/inferred)**:
  - J4 processing on CNC-2 requires FIX-A; FIX-A is infeasible for J4 before 11:40 if it is single-instance and exclusively held by J3.
  - Shipment S1 dispatch requires both consolidated jobs (J1 and J4) to be ready under a consolidation policy.
- **Policy constraints (inferred)**:
  - Lack of explicit `Wait for Tool` activity suggests the system models tool waits implicitly; this can cause planners to miss FIX-A as a gating resource.
  - S1 consolidation appears to hold dispatch until late partner is packed (J4 at 19:10).
- **Causal speculation (clearly speculative)**:
  - If FIX-A unavailability prevented J4 from using the 10:05–10:47 CNC idle window, then FIX-A contention contributes ~1h35–1h40 delay to J4’s machining start. If that delay propagates through downstream steps to the 19:10 packing time, it can indirectly impose a multi-hour delay on J1 via S1 (5h20–5h30 excess wait beyond typical shipping cadence). Alternative explanations include carrier pickup schedules or downstream non-tool constraints driving J4’s late pack.

### Narrative C: Lot L7 governance + rack state + calibration policy couple “independent” jobs {J2,J5,J6} across stages and shipments
- **Temporal precedence (observed)**:
  - L7 contains {C2, C5}. `E_L7_Quarantine@10:20` and `E_L7_Release@13:50` relate to {L7, C2, C5, J2, J5}.
  - J2 proceeds into B1 before release via supervisor override (recorded elsewhere); J5 does not proceed until after release.
  - For B2: J4 ready 13:10; RACK-7 unavailable until 14:35; J5 ready 14:40; B2 starts 14:50; OVEN-1 idle 12:55–14:50.
  - For testing: J5 tests 16:10–16:35; CAL-3 recalibrates 16:35–17:20; J6 tests 17:25–17:50 with TEST-1 otherwise idle 16:35–17:25.
- **Resource feasibility (observed/inferred)**:
  - A quarantined lot makes components administratively infeasible unless overridden; this affects feasibility of downstream job steps even if machines are free.
  - B2 feasibility requires both RACK-7 and the batched jobs; CAL-3 calibration affects feasibility of `Final Test` for J6 despite TEST-1 idleness.
- **Policy constraints (inferred)**:
  - Governance: quarantine/release policy (plus overrides) creates inconsistent coupling—some jobs bypass, others wait.
  - Tool state policy: rack cleaning/quarantine blocks batching independently of oven capacity.
  - Calibration policy: recalibration window blocks testing throughput without consuming TEST-1 processing time.
  - Shipping: S3 consolidates {J5, J6}; if consolidation is enforced similarly to S1, J5 could also end up waiting for J6’s delayed test (not directly timestamped here).
- **Causal speculation (clearly speculative)**:
  - The same root cause (“policy/eligibility constraints outside the machine logs”) plausibly explains why OVEN-1 and TEST-1 show idle periods while jobs are waiting. However, without explicit queue-entry/exit logs, it remains uncertain whether J5’s readiness at 14:40 is driven mainly by lot release at 13:50, by upstream processing, or by scheduling priorities.

## 6. Intervention portfolio and spillovers

The goal is not to “fix a bottleneck” but to **reduce coupling strength**, make constraints observable, and prevent spillovers across jobs that look independent in flattenings.

Intervention | Target mechanism | Expected benefit | Helped objects | Potentially harmed objects | New cost/risk | Perverse-incentive metric | Object-centric evaluation design
---|---|---|---|---|---|---|---
Start-time cap for batches (e.g., “start when ≥k ready or after T minutes”) | Batch synchronization | Reduce J1/J2-type waits; lower variance in lead time | J1, J2 (B1); J4 (B2) | J3 (may lose coordination), OVEN-1 energy efficiency | More changeovers/smaller loads; quality risk if underfilled | “Batch fill rate” could incentivize waiting longer | Stepped-wedge across weeks: compare readiness→batch-start waiting per Job in OCEL; control for product mix
Add a second rack or “swap rack” process (pre-cleaned rack inventory) | RACK-7 single-point gating + cleaning quarantine | Remove 1h25 rack-driven delay for B2-like cases | B2 jobs (J4,J5); all oven batches | Cleaning team workload; risk of rack mix-ups | Capex + contamination risk | “Racks cleaned/day” could incentivize shallow cleaning | Alternate assignments by batch (RACK-7 vs spare): measure OVEN idle while jobs ready; defect rate monitoring
Tool reservation/checkout + explicit wait logging for FIX-A (and/or add another FIX-A) | Shared-tool contention (FIX-A) + hidden queues | Reduce CNC idle-with-wait; improve schedule predictability | J4, CNC-2; any FIX-A-requiring jobs | J3 if deprioritized; maintenance budget | Capex; governance for tool calibration | “Tool utilization” may encourage hoarding | Before/after with instrumented “request/grant/release” events; OCEL measure time-from-arrival-at-CNC to process-start conditional on tool state

## 8. Falsification and additional data

### Observations that would weaken the top-ranked explanation (batch synchronization + rack gating)
1) **Readiness timestamps are not trustworthy**: if an audit shows J1/J2 were not truly “ready for batch” at 08:10/08:25 (e.g., still missing components or awaiting inspection), then the 3h40–3h55 “sync wait” is overstated.
2) **OVEN-1 was not actually available**: if additional (unrecorded) oven work or long setup/maintenance occurred between 08:10 and 12:05, then batching may not be the binding constraint.
3) **RACK-7 is not uniquely required**: if another rack could have been used (or was used but not linked), then rack gating is weaker.
4) **Batch policy mandates full cohort for safety/quality**: if curing requires all three (B1) together for traceability or thermal reasons, then waiting is policy-driven and “avoidable” only by changing that policy (with quality risk).
5) **J3 lateness does not precede B1 start in general**: if across more data B1-like batches often start without waiting for the last job (or the last job is not consistently the one that determines start), then synchronization is not the dominant mechanism.
6) **Jobs do substantial work during the supposed waiting windows**: if J1/J2 have intervening events between 08:10 and 12:05 indicating they were not idle/queued for batch, then the delay attribution to synchronization is wrong.
7) **Queue evidence contradicts tool/batch gating**: if explicit queue-entry/exit data shows J1/J2 were never in the oven queue before 11:55, the coupling is upstream, not at batching.
8) **Carrier schedule explains S1 timing**: if a fixed pickup at ~19:25 exists regardless of partner jobs, then the “consolidation delay” for J1 is mostly a calendar constraint rather than coupling to J4.

### Additional fields / event types to discriminate among hypotheses
1) **Explicit wait-state events**: `Wait for Batch`, `Wait for Tool`, `Wait for Shipment`, `Wait for Lot Release` with a reason code and queue identifier.
2) **Batch policy attributes**: planned membership, minimum fill, maximum wait, scheduled start, operator/shift, and any “batch timeout” decisions.
3) **Tool inventory and state telemetry**: unique tool instance IDs, location, cleaning/quarantine start/end, calibration validity windows, and reservation/checkout logs (especially for FIX-A, RACK-7, CAL-3).
4) **Lot governance details**: quarantine reason, risk level, partial release events, component-level status changes, and links from lot decisions to job authorizations.
5) **Override events as first-class records**: who overrode, which lot/tool constraint, justification, and the downstream exceptions it creates.
6) **Shipment policy and carrier constraints**: consolidation rule, pickup windows, customer-requested ship dates, and “ship-split” decisions; plus explicit `Job Loaded` events per job per shipment.
7) **Setup/changeover and maintenance events**: start/end times for setups on CNC-2/OVEN-1/TEST-1 to separate “machine idle” from “machine unavailable.”
8) **Staffing/shift calendar and dispatching priorities**: operator availability and job priority changes to test the alternative “human scheduling bottleneck” hypothesis.
