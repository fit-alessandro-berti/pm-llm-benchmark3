# 1. Executive Verdict

The net is structurally a workflow net: `source` is the unique source, `sink` the unique sink, and every node lies on a source-to-sink path. It should not be expected to be sound with respect to `im` and exact `fm`. The principal defect is that `t_join_waived` consumes only `p_waived`; unlike `t_join_normal`, it does not synchronize with `p_analysis_done`. Consequently, authorization can occur before analysis. If authorization occurs first, the analysis branch remains executable and eventually leaves an unconsumable token in `p_analysis_done`; if analysis occurs first, that token is already stranded when authorization reaches `sink`. Thus the net may place a token in `sink`, but cannot reach the exact final marking on the waiver route. The business consequence is both premature authorization and improper completion with residual work.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source  t_register  p_ready` | Start and register one case | Converts the sole initial token into one ready token | Correct single-case initiation |
| `p_ready  t_split  {p_analysis, p_review}` | AND-split: start mandatory analysis and review choice in parallel | Produces one token in each branch | Correct parallel initiation |
| `p_analysis  t_analyze  p_analysis_done` | Mandatory analysis | Analysis remains enabled independently of the review outcome | Correct locally, but its result is ignored by the waiver join |
| `p_review  t_standard_review  p_review_done` | Select and perform standard review | Competes with waiver for the single token in `p_review`, so only one review outcome can be selected | Correct XOR choice by conflict |
| `p_review  t_waive_review  p_waived` | Select and formally record waiver | Also consumes the sole review token, excluding standard review | Correctly records a distinct visible waiver outcome |
| `{p_analysis_done, p_review_done}  t_join_normal  p_decision` | Synchronize analysis with completed standard review | Proper two-input AND-join | Normal route waits for both prerequisites |
| `p_waived  t_join_waived  p_decision` | Intended to synchronize analysis with waiver | Has only the waiver input; it neither waits for nor consumes `p_analysis_done` | Premature authorization and a residual analysis token |
| `p_decision  t_authorize  sink` | Authorize after prerequisites and complete | Authorization depends only on a token in `p_decision` | Safe on the normal route, unsafe on the waiver route |
| `im = [source]`, `fm = [sink]` | Exact initial and final markings | Final acceptance requires one token in `sink` and no token elsewhere | Waiver executions can mark `sink` without reaching `fm` |
| Whole graph | Workflow-net structure | Unique source/sink; every place and transition occurs on some directed source-to-sink path | Workflow-net status does not imply behavioral soundness |

Every node is structurally on a source-to-sink path. In particular, `p_analysis_done` is on a path through `t_join_normal`, even though that path is unavailable after the review token has selected the waiver alternative. This distinction between graph reachability and marking reachability explains why the net can be a workflow net while unsound.

# 3. Marking-Based Counterexample

A legal sequence exposing premature authorization is:

```text
t_register, t_split, t_waive_review, t_join_waived,
t_authorize, t_analyze
```

Markings below list only places with nonzero token counts.

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `{source: 1}` | `t_register` | This is exactly `im`. |
| 1 | `t_register` | `{p_ready: 1}` | `t_split` | Case is registered. |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | One token has been created in each parallel branch. |
| 3 | `t_waive_review` | `{p_analysis: 1, p_waived: 1}` | `t_analyze`, `t_join_waived` | Review choice is consumed and waiver is recorded; analysis remains pending. |
| 4 | `t_join_waived` | `{p_analysis: 1, p_decision: 1}` | `t_analyze`, `t_authorize` | The defective one-input join permits a decision before analysis. |
| 5 | `t_authorize` | `{p_analysis: 1, sink: 1}` | `t_analyze` | A token exists in `sink`, but this is not exact `fm` because `p_analysis` is also marked. |
| 6 | `t_analyze` | `{p_analysis_done: 1, sink: 1}` | none | Analysis can occur after authorization, violating order. Its result is stranded, so exact `fm` is unreachable. |

The residual token in `p_analysis_done` cannot be consumed. Its only outgoing transition is `t_join_normal`, which additionally requires a token in `p_review_done`. The review token was consumed by `t_waive_review`, so no standard review can subsequently produce that token.

Analysis can instead occur before authorization:

```text
t_register, t_split, t_waive_review, t_analyze,
t_join_waived, t_authorize
```

The last marking is again:

```text
{p_analysis_done: 1, sink: 1}
```

Thus doing analysis earlier avoids the temporal violation but not improper completion. A sink token alone is not acceptance under the declared exact final marking.

The standard-review route does not exhibit this defect:

```text
t_register, t_split, t_analyze, t_standard_review,
t_join_normal, t_authorize
```

It reaches exactly `{sink: 1}` because `t_join_normal` consumes both branch-completion tokens.

# 4. Minimal-Repair Alternatives

Use the following unit-cost model:

- adding or removing one arc: cost 1;
- adding or removing one place: cost 1;
- adding or removing one transition: cost 1;
- changing a visible label: cost 1.

An arc redirection counts as one removal plus one addition. The cost measures model edits, not implementation lines.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| **A. Add analysis to the waiver join** | Add arc `p_analysis_done  t_join_waived` | **1** | Fully preserves mandatory analysis, visible standard review/waiver distinction, and authorization ordering | `t_join_waived` becomes a two-input synchronization and consumes both completion tokens | Two silent joins have similar synchronization roles; future maintainers must update both consistently |
| **B. Merge both review outcomes into the normal synchronization** | Remove `t_waive_review  p_waived`; add `t_waive_review  p_review_done`; remove `p_waived  t_join_waived`; remove `t_join_waived  p_decision`; remove place `p_waived`; remove transition `t_join_waived` | **6** | Fully preserves mandatory analysis and keeps the visible waiver event distinguishable in traces | Both visible review alternatives produce the common semantic state “review requirement resolved”; there is only one join | The marking no longer records which outcome occurred after the visible event; downstream place-based logic cannot distinguish them |
| **C. Make analysis optional under waiver — explicit policy change** | Remove arc `t_split  p_analysis`; add arc `t_standard_review  p_analysis`; add arc `t_waive_review  p_waived` is already present, so no edit there | **2** | Preserves the standard path’s requirement that analysis and standard review both complete before authorization | **Changes policy:** selecting waiver means no analysis token is created; standard review creates the analysis work token | Analysis no longer starts in parallel with review, and waiver explicitly bypasses analysis; this contradicts the stated business intent |

Repair A is globally minimal among arc/place/transition edits that preserve the current topology and mandatory analysis on the waiver route. At least one structural edit is necessary because the existing waiver route can fire without consuming or testing the analysis token; adding the missing input arc corrects both waiting and cleanup in one edit. No zero-edit repair can change behavior.

Repair B is behaviorally equivalent at the visible-trace level for this isolated model but structurally distinct: it normalizes both review outcomes into one completion place and one join. Its six edits are minimal for fully deleting the waiver-specific place and join under the stated model-element cost: two incident arcs, one incoming redirection, two nodes, and the join’s output arc must be removed or replaced as listed.

Repair C ties neither A nor B. It is included as a genuinely semantic alternative, not as a recommendation. Its two edits are sufficient to eliminate the orphaned analysis token while adopting a different policy and sequencing: analysis becomes conditional on standard review rather than mandatory and parallel.

# 5. Corrected PM4Py Code

The selected implementation is Repair A.

register = PetriNet.Transition("t_register", "Register Case")

# 6. Diagnostic and Reachability Code

This block assumes both the original `net`, `im`, `fm` and the repaired variables from Section 5 exist.

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking


def marking_by_name(marking):
    return {
        place.name: count
        for place, count in marking.items()
        if count
    }


def transition_by_name(petri_net, transition_name):
    matches = [
        t for t in petri_net.transitions
        if t.name == transition_name
    ]
    if len(matches) != 1:
        raise ValueError(
            f"Expected one transition named {transition_name!r}, "
            f"found {len(matches)}"
        )
    return matches[0]


def enabled_names(petri_net, marking):
    return sorted(
        t.name
        for t in pm4py.get_enabled_transitions(petri_net, marking)
    )


def fire_named(petri_net, marking, transition_name):
    transition = transition_by_name(petri_net, transition_name)
    enabled = set(pm4py.get_enabled_transitions(petri_net, marking))

    if transition not in enabled:
        raise RuntimeError(
            f"{transition_name} is not enabled at "
            f"{marking_by_name(marking)}; enabled: "
            f"{enabled_names(petri_net, marking)}"
        )

    result = Marking(marking)

    for arc in transition.in_arcs:
        weight = getattr(arc, "weight", 1)
        result[arc.source] -= weight
        if result[arc.source] == 0:
            del result[arc.source]

    for arc in transition.out_arcs:
        weight = getattr(arc, "weight", 1)
        result[arc.target] += weight

    print(
        f"fired {transition_name}: {marking_by_name(result)}; "
        f"enabled={enabled_names(petri_net, result)}"
    )
    return result


def run_diagnostics(title, petri_net, initial_marking, final_marking):
    print(f"\n=== {title} ===")
    print(
        "workflow net:",
        pm4py.check_is_workflow_net(petri_net)
    )
    print("soundness diagnostics:")
    soundness_result = pm4py.check_soundness(
        petri_net,
        initial_marking,
        final_marking,
        print_diagnostics=True
    )
    print("soundness result:", soundness_result)
    print(
        "initially enabled:",
        sorted(
            t.name
            for t in pm4py.get_enabled_transitions(
                petri_net, initial_marking
            )
        )
    )
    reachability_graph = pm4py.convert_to_reachability_graph(
        petri_net,
        initial_marking,
        final_marking
    )
    print(
        "reachability graph created:",
        type(reachability_graph).__name__
    )
    return reachability_graph


original_rg = run_diagnostics("ORIGINAL", net, im, fm)
repaired_rg = run_diagnostics(
    "REPAIRED", repaired_net, repaired_im, repaired_fm
)

print("\n=== Original waiver counterexample ===")
m = Marking(im)
print(
    "start:",
    marking_by_name(m),
    "enabled=",
    enabled_names(net, m)
)
for name in [
    "t_register",
    "t_split",
    "t_waive_review",
    "t_join_waived",
    "t_authorize",
    "t_analyze",
]:
    m = fire_named(net, m, name)

print("\n=== Repaired waiver route ===")
m = Marking(repaired_im)
print(
    "start:",
    marking_by_name(m),
    "enabled=",
    enabled_names(repaired_net, m)
)
for name in [
    "t_register",
    "t_split",
    "t_waive_review",
]:
    m = fire_named(repaired_net, m, name)

# This intentionally demonstrates that the repaired join is disabled.
try:
    m = fire_named(repaired_net, m, "t_join_waived")
except RuntimeError as exc:
    print("expected rejection:", exc)

for name in [
    "t_analyze",
    "t_join_waived",
    "t_authorize",
]:
    m = fire_named(repaired_net, m, name)

print(
    "repaired route reaches exact final marking:",
    m == repaired_fm
)
```

Qualitatively, both models should pass the structural workflow-net check. The original should fail soundness because the waiver branch permits improper completion and leaves a reachable stranded token. The repaired net should pass soundness: either review choice can synchronize with completed analysis, authorize, and reach exact `repaired_fm`. Diagnostic text and return structure may vary with PM4Py version, so no particular undocumented diagnostic keys should be assumed.

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability:** In selected Repair A, standard review and waiver remain separate visible transitions with different labels and separate completion places. Event logs can therefore distinguish them. Repair B also preserves visible-event distinction, although the post-event marking merges both outcomes into `p_review_done`.

- **Silent-transition clarity:** Repair A retains two silent joins that both consume `p_analysis_done` but differ in their review input. They do not create duplicate traces for one case because the review transitions conflict over a single token: only one join can obtain its corresponding review token. Nevertheless, two silent joins can confuse maintainers or model visualizations. Repair B is structurally simpler in this respect.

- **Limits of soundness:** Soundness establishes behavioral completion properties relative to the markings; it does not prove every business rule. A sound model could still mislabel events, omit required data checks, permit unauthorized actors, or implement the policy-changing Repair C.

- **Positive regression traces:** Test both interleavings for each outcome:
  - analysis then standard review, join, authorization;
  - standard review then analysis, join, authorization;
  - analysis then waiver, join, authorization;
  - waiver then analysis, join, authorization.
  
  Each should end at exactly `{sink: 1}`.

- **Negative regression traces:** Reject:
  - waiver followed by `t_join_waived` before analysis;
  - standard review followed by `t_join_normal` before analysis;
  - `t_authorize` before either appropriate join;
  - both `t_standard_review` and `t_waive_review` in one case;
  - any completed execution with tokens outside `sink`.

- **Detecting analysis bypass:** Enumerate or model-check reachable markings and assert that whenever `t_authorize` is enabled or has fired, `t_analyze` previously fired. Structurally, verify every transition producing `p_decision` consumes `p_analysis_done`. Trace-based conformance tests should reject `Register Case  Record Review Waiver  Authorize Case`.

# 8. Final Recommendation

Deploy **Repair A: add `p_analysis_done  t_join_waived`**. It is the unique one-edit correction among the presented alternatives, preserves the stated policy exactly, retains separate visible waiver and standard-review outcomes, restores proper synchronization, and consumes every parallel-branch token before authorization. Its small diff also reduces migration and review risk.

Use **Repair B** as the fallback if maintainability or model simplicity is prioritized. Mapping both visible review outcomes to a common `p_review_done` place gives one synchronization point and avoids maintaining parallel silent joins. Its trade-off is loss of outcome identity in the post-review marking, though event traces remain distinguishable.

Do not deploy Repair C unless business owners explicitly approve making analysis optional under waiver and accept that analysis no longer starts in parallel on the standard route. Regardless of the chosen repair, gate deployment on soundness diagnostics plus trace-level regression tests; soundness by itself does not establish compliance with the mandatory-analysis policy.
