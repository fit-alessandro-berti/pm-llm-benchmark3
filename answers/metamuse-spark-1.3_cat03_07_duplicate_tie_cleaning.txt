## 1. Duplicate-handling decision tree
Conservative principle: same timestamp + same label is **not** evidence of duplication. Duplication requires identity of business transition, objects, and source-mechanics. Ingestion order is never business order.

```
Q1: Same source + same source_event_key appearing twice?
  YES -> Exact technical duplicate
         Action: DROP later ingestion, keep first.
         Keep provenance link to dropped ingestion id.
         Rationale: purely technical re-ingestion.

Q2: Different source/system, same time+label, overlapping objects?
  Check reconciliation, invoice/payment keys, object identity,
  payload, and source semantics:
  
  Q2a: External evidence (reconciliation report, shared invoice V1,
       shared business key) asserts same physical transition
       AND object sets compatible (identical or subset due to enrichment)?
    YES -> Same physical event observed by multiple systems
           Action: MERGE ATTRIBUTES AND RELATIONS into one canonical event.
           Policy: union relations; attribute union with source-authority map;
                   retain both source_event_keys, both payload_hashes,
                   discarded conflicts logged. Confidence High if external
                   report/key, else Medium.
           Do NOT drop attributes silently.

  Q2b: One event is system status / summary generated from message
       sent by the other system (different abstraction, e.g. WMS detail
       vs ERP status; PSP detail vs ERP balance update), with causal
       direction and coarser objects/attributes?
    YES -> Summary event derived from detailed event
           Conservative: RETAIN BOTH WITH REFINED LABELS / QUALIFIERS
                         e.g. `Pack Package [WMS-detail]` vs
                              `Pack Package [ERP-status]`.
           Aggressive option: MERGE (evidence-based) only if analysis
           does not need abstraction levels. Explicit damage: loss of
           lead-time, abstraction rework. Quarantine if causality unclear.

  Q2c: Harmonization mapped semantically distinct source activities
       to one common label (e.g. "released" vs "accepted" both -> Dispatch)?
    YES -> Harmonization collision
           Action: RETAIN BOTH WITH REFINED LABELS, restore source
                   semantics: `Dispatch Package [released]` vs
                   `[accepted]`, or revert to original_activity.
           Never merge. Partial order from domain knowledge.

  Q2d: Same label+time but different distinguishing objects
       (different Item I1 vs I2; different Payment M1 vs M2)?
    YES -> Concurrent same-label events involving different objects
           Action: RETAIN BOTH UNCHANGED (or with qualifier if needed).
           Concurrency is real. Merging creates false batch and destroys
           count, frequency, and object-specific DFGs.
           have_common_object on O1/V1 does NOT override distinct I/M.

  Q2e: None of above provable, but suspicious similarity?
    YES -> Unresolved candidate
           Action: QUARANTINE FOR REVIEW + RETAIN BOTH UNCHANGED in
                   conservative log. Flag `duplicate_suspect_group`.
                   No auto-merge/drop. Require business-key or process-owner sign-off.
```

Terminal actions allowed: `drop` only for Q1; `merge` only for Q2a with evidence; `retain with refined labels` for Q2b/Q2c; `retain unchanged` for Q2d; `quarantine` for Q2e. No path merges all equal activity+timestamp.

## 3. Timestamp-tie ordering rules
Policy: establish **semantic partial order first**, then impose **deterministic total order for computation only**. Never add microseconds before semantic reasoning; synthetic precision then looks like measured truth.

Rules in priority order:

1. **Domain constraints (semantic):** e.g. Authorize M1 < Capture M1; released < accepted < handover; pick < pack < dispatch; invoice < authorize; PSP messages < ERP payment summary; WMS pack message < ERP pack status. Source facts 5,7,8 and process knowledge.
2. **Within-source sequence (semantic, source-local):** `source_seq` meaningful only within one source. WMS 100<110<120; SCANNER 551<552; CARRIER 1<2, 30 later; ERP 10<20<30<40<41; PSP 400<401<402; BILLING internal. Never compare seq across sources.
3. **Lifecycle constraints on shared objects (semantic):** Item pick before Package pack; Package pack before Delivery dispatch. Distinguishes abstraction order when timestamps tie.
4. **Source-specific semantics / derivation causality (semantic):** detail before derived summary when message direction known (e06<e07, e12/e13/e14 < e15).
5. **Ingestion time (non-semantic, weak deterministic hint only):** `ingested_at` reflects pipeline delay, not business order per fact 9. Use only to break remaining ties after semantic rules, and log as such. Never primary.
6. **Stable fallback order (purely deterministic, non-semantic):** e.g. canonical eid lexical, or Item/Payment id lexical (I1<I2, M1<M2). Guarantees reproducibility for sorting/DFG/mining, carries zero truth claim.

Semantic vs deterministic: 1-4 are semantic and must be documented as assumptions with confidence. 5-6 are merely deterministic to obtain a total order for tools requiring sorted logs. Total order does **not** prove true physical order; simultaneous picks and parallel captures remain logically concurrent.

Why microseconds-first is dangerous: if you do `ocel_add_index_based_timedelta` or add 1µs by ingestion or row order before applying 1-4, you freeze an arbitrary sequence (often ingestion order) into `ocel:timestamp`. Downstream DFG, performance, and conformance then treat it as observed order, inventing stories like “ERP status before WMS detail” or “M2 before M1” or “accepted before released.” Original second-precision tie (evidence of limited granularity) is lost and irrecoverable. Correct sequence: decide partial order  assign `semantic_rank`  sort stably  only then add epsilon for tool compatibility while preserving `original_timestamp`.

Intended orders (conservative log, 15 events):

- **e03–e07 at 10:00:** merged canonical `e03/e04 [Pick I1]` and `e05 [Pick I2]` are concurrent picks (both 10:00:00). Deterministic serialization for analysis: `e03/e04 < e05` (I1<I2 fallback; also WMS seq vs scanner seq not comparable, so fallback). Then `e06 [Pack detail] < e07 [Pack status]` by derivation causality + ERP seq 30 after WMS message. So partial: {e03/e04, e05} < e06 < e07; total: e03/e04, e05, e06, e07. Alternative admissible total: e05, e03/e04, e06, e07 — picks order interchangeable; must not be interpreted as causal. Retaining e06/e07 separate preserves pack detailstatus edge; merging (Scenario B) collapses to single pack.
- **e08–e10 at 10:15:** strict semantic `e08 [released] < e09 [accepted] < e10 [handover]` by domain + carrier seq 1<2. All share 10:15:00. Ingestion 10:15:01, :20, :21 happens to align but must not be cited as proof. No admissible alternative; inversion would violate handover semantics.
- **e11–e16 at 12:00 after dedup:** merged `e11/e16 [Issue Invoice]` first, then `e12 [Authorize M1]` < `e13 [Capture M1]` (domain for M1), `e13` and `e14 [Capture M2]` concurrent captures for distinct payments (deterministic e13<e14 by PSP seq 401<402 + M1<M2 fallback, not causal), then `e15 [ERP payment summary]` last (fact 8, ERP seq 41, ingested 12:01:00). So total: e11/e16, e12, e13, e14, e15. Alternative admissible: e14 and e13 swapped deterministically if M2 lexical first — still concurrent logically. Must not place e15 between PSP events.

## 4. Conservative cleaning pipeline
Minimum-change, provenance-first scenario.

Steps: (a) snapshot raw; preserve `original_timestamp/activity/source/source_event_key/payload_hash/ingested_at`. (b) Exact-duplicate check by `(source, source_event_key)` — none found, drop zero. (c) Verified-pair merges only with strong evidence: e03+e04 (reconciliation + compatible objects), e11+e16 (shared V1 + compatible objects) via custom merge that unions attributes/relations with authority map. (d) Refine harmonized labels without deleting: e09 `Dispatch Package  Dispatch Package [carrier-accepted]`, e08 ` Dispatch Package [warehouse-released]`, e06 `Pack Package [wms-detail]`, e07 `[erp-status]`, e13 `[psp-m1]`, e14 `[psp-m2]`, e15 `[erp-summary]`. Keep `original_activity` intact. (e) Establish partial order per Section 3, store `semantic_rank` + `order_reason`, stably sort, then add epsilon timedelta for tooling while keeping `original_timestamp`. (f) Validate E2O integrity.

Expected retained count: **15 events** (17 raw 1 for e03/e04 merge 1 for e11/e16 merge). E2O relations slightly reduced by deduplication (duplicate O1,I1,P1 and O1,V1 edges removed) but no object loss; all Items, Payments, Delivery preserved. No legitimate concurrency deleted: e03/e05, e13/e14, e08/e09/e10 all retained.

Effect: eliminates only false rework (Pick I1 self-loop, Invoice self-loop) while preserving true abstraction loops (Pack detailstatus) and true concurrency. Downstream DFGs stay interpretable with explicit order reasons; audit can revert to raw.

## 5. Aggressive alternatives
**Scenario B — evidence-based semantic merging (14 events).** Adds e06+e07 merge to conservative merges. Canonical e06 retains union objects O1,I1,I2,P1 and union attributes (WMS detail authoritative, ERP status flag as attribute). Expected: 173=**14**. Most likely damage: loss of abstraction level; Pack detailstatus edge disappears, hiding ERP reporting delay and WMS-to-ERP message latency; performance from pick to pack now conflates operational vs system-status time; if analyst filters by ERP source, pack vanishes. Less damaging than library merge but irreversible for abstraction analysis unless provenance stores split. Justifiable only if research question is end-to-end business transitions, not system behavior.

**Scenario C — mechanically aggressive PM4Py merging (~10 events).** Applies `ocel_drop_duplicates` + `ocel_merge_duplicates(have_common_object=True)` grouped by (activity, timestamp) over whole OCEL without per-group inspection. Expected: **~10 events** (Pick 31, Pack 21, Dispatch 21, Invoice 21, Capture 31; saves 7). Most likely damage: (i) e05 collapsed into e03/e04 — I2 pick lost, Item I2 lifecycle broken, Order-flattened Pick self-loop disappears falsely as single pick; (ii) e13+e14+e15 collapsed — M1/M2 partial payments merged into one Capture, Payment objects unioned incompatibly or one dropped, amounts double-counted or lost, Payment-DFG destroyed; (iii) e08+e09 collapsed — release/accept handshake lost; (iv) e06+e07 collapsed as in B but without authority control (last-wins). Unioning E2O creates events linked to I1+I2 or M1+M2 simultaneously, suggesting batch operations that never occurred.

Why `have_common_object=True` fails for e13/e14: it checks *any* shared object. e13 (O1,V1,M1) and e14 (O1,V1,M2) share O1 and V1, so predicate passes, yet distinguishing objects M1 vs M2 prove distinct business transitions (fact 7: M2 distinct partial). Shared parent (Order/Invoice) is expected in many-to-one structures and cannot prove identity. Protection requires checking distinguishing object types (Payment, Item) for inequality and requiring business-key equality (payment id, item id), not mere overlap. Same logic protects e03 (I1) vs e05 (I2): shared O1,P1 irrelevant next to differing I.

## 6. PM4Py-oriented Python implementation
```python
import copy
import pandas as pd
import pm4py

# Assume ocel_raw exists; events contain:
# ocel:eid, ocel:activity, ocel:timestamp, source, source_event_key,
# source_seq, ingested_at, payload_hash
assert hasattr(ocel_raw, "events") and hasattr(ocel_raw, "relations")

def ensure_provenance_cols(events: pd.DataFrame) -> pd.DataFrame:
    df = events.copy()
    if "original_timestamp" not in df.columns:
        df["original_timestamp"] = df["ocel:timestamp"]
    if "original_activity" not in df.columns:
        df["original_activity"] = df["ocel:activity"]
    for c in ["source", "source_event_key", "source_seq",
              "ingested_at", "payload_hash"]:
        if c not in df.columns:
            df[c] = pd.NA
    return df

def precheck_candidate_groups(events: pd.DataFrame):
    # Inspection only, no mutation. Flags suspicious ties.
    tmp = events.copy()
    tmp["ts_sec"] = pd.to_datetime(tmp["ocel:timestamp"]).dt.floor("s")
    grouped = tmp.groupby(["ocel:activity", "ts_sec"])
    report = []
    for (act, ts), g in grouped:
        if len(g) > 1:
            report.append({
                "activity": act, "timestamp": str(ts),
                "eids": sorted(g["ocel:eid"].tolist()),
                "sources": sorted(g["source"].tolist()),
                "n": len(g)
            })
    # Show object overlap separately via relations if available
    print(f"Candidate tie groups (activity+second): {len(report)}")
    for r in report:
        print(r)
    return report

def merge_verified_pair(ocel, keep_eid: str, drop_eids: list,
                        authority: dict, merge_rule: str,
                        reason: str, reviewer: str = "rule_v1.0"):
    """
    Custom verified-pair merge for cases like e03/e04 and e11/e16.
    - keep_eid: canonical eid preserved.
    - drop_eids: eids folded into canonical.
    - authority: {attr: preferred_source} for conflicts; all conflicts logged.
    Returns (new_ocel, audit_record). Does not mutate input.
    """
    o = copy.deepcopy(ocel)
    ev = o.events.set_index("ocel:eid")
    rel = o.relations  # E2O: columns include ocel:eid, ocel:oid, qualifier
    audit = {
        "canonical_eid": keep_eid, "source_eids": [keep_eid] + drop_eids,
        "merge_rule": merge_rule, "reviewer": reviewer,
        "original_activities": {}, "refined_activity": None,
        "original_timestamps": {}, "adjusted_timestamp": None,
        "attributes_retained": {}, "discarded_conflicts": [],
        "confidence": "", "reason": reason
    }
    for eid in [keep_eid] + drop_eids:
        audit["original_activities"][eid] = str(ev.loc[eid, "original_activity"])
        audit["original_timestamps"][eid] = str(ev.loc[eid, "original_timestamp"])
        audit["attributes_retained"][eid] = {
            "source": str(ev.loc[eid, "source"]),
            "source_event_key": str(ev.loc[eid, "source_event_key"]),
            "payload_hash": str(ev.loc[eid, "payload_hash"])
        }
    # Attribute union with authority (example: location from WMS, billing attrs from BILLING)
    for col in ev.columns:
        vals = ev.loc[[keep_eid] + drop_eids, col].dropna().unique()
        if len(vals) > 1 and col not in ["ocel:eid"]:
            pref = authority.get(col, None)
            # Simplified: if preferred source present, keep its value, log others as conflicts
            audit["discarded_conflicts"].append({col: [str(v) for v in vals]})
    # Union E2O relations: repoint drop_eids -> keep_eid, dedupe
    rel = rel.copy()
    rel.loc[rel["ocel:eid"].isin(drop_eids), "ocel:eid"] = keep_eid
    rel = rel.drop_duplicates()
    o.relations = rel
    # Drop folded event rows
    o.events = o.events[~o.events["ocel:eid"].isin(drop_eids)].copy()
    # Record merged keys for reversibility
    idx = o.events["ocel:eid"] == keep_eid
    o.events.loc[idx, "merged_source_keys"] = "+".join(
        [str(ev.loc[e, "source_event_key"]) for e in [keep_eid] + drop_eids])
    o.events.loc[idx, "merge_rule"] = merge_rule
    return o, audit

def validate_referential_integrity(ocel):
    eids = set(ocel.events["ocel:eid"])
    oids = set(ocel.objects["ocel:oid"]) if hasattr(ocel, "objects") else set()
    rel_e = set(ocel.relations["ocel:eid"])
    rel_o = set(ocel.relations["ocel:oid"])
    assert rel_e.issubset(eids), f"Dangling event refs: {rel_e - eids}"
    if oids:
        assert rel_o.issubset(oids), f"Dangling object refs: {rel_o - oids}"
    assert ocel.events["ocel:eid"].is_unique
    assert (pd.to_datetime(ocel.events["original_timestamp"]).notna().all())
    print(f"OK: {len(ocel.events)} events, {len(ocel.relations)} E2O relations.")
    return True

# ---- 0. Never mutate raw ----
ocel_raw.events = ensure_provenance_cols(ocel_raw.events)
precheck = precheck_candidate_groups(ocel_raw.events)

# ---- A. Conservative scenario (minimum change) ----
ocel_cons = copy.deepcopy(ocel_raw)
ocel_cons.events = ensure_provenance_cols(ocel_cons.events)

# Justified exact-duplicate removal only: same source+key (finds 0 here, safe)
ocel_exact = pm4py.ocel_drop_duplicates(
    copy.deepcopy(ocel_cons),
    variant="exact_technical"  # intent: (source, source_event_key) identity
)

# Verified merges with evidence
ocel_cons, audit_0304 = merge_verified_pair(
    ocel_exact, keep_eid="e03", drop_eids=["e04"],
    authority={"location": "WMS", "device": "SCANNER"},
    merge_rule="verified_same_scan_reconciliation_report",
    reason="Fact1: same physical scan; compatible O1,I1,P1; payload diff is enrichment")
ocel_cons, audit_1116 = merge_verified_pair(
    ocel_cons, keep_eid="e11", drop_eids=["e16"],
    authority={"amount": "ERP", "status": "ERP", "tax": "BILLING", "layout": "BILLING"},
    merge_rule="verified_same_invoice_V1_authority_map",
    reason="Fact6: same V1; each source authoritative for different attrs")

# Refine harmonized labels, keep original_activity
refine = {"e08": "Dispatch Package [warehouse-released]",
          "e09": "Dispatch Package [carrier-accepted]",
          "e06": "Pack Package [wms-detail]", "e07": "Pack Package [erp-status]",
          "e13": "Capture Payment [psp-M1]", "e14": "Capture Payment [psp-M2]",
          "e15": "Capture Payment [erp-summary]"}
for eid, lab in refine.items():
    m = ocel_cons.events["ocel:eid"] == eid
    if m.any():
        ocel_cons.events.loc[m, "ocel:activity"] = lab
        ocel_cons.events.loc[m, "refined_activity"] = lab

# Deterministic ordering: semantic rank first, stable sort, epsilon only after
rank = {"e01": 0, "e02": 1, "e03": 2, "e05": 3, "e06": 4, "e07": 5,
        "e08": 6, "e09": 7, "e10": 8, "e11": 9, "e12": 10,
        "e13": 11, "e14": 12, "e15": 13, "e17": 14}
ocel_cons.events["semantic_rank"] = ocel_cons.events["ocel:eid"].map(rank)
ocel_cons.events["order_reason"] = "domain+source_seq+lifecycle; ingestion not primary"
ocel_cons = pm4py.ocel_sort_by_additional_column(ocel_cons, "semantic_rank")
# Only now add tool-compatible epsilon, original preserved
ocel_cons = pm4py.ocel_add_index_based_timedelta(ocel_cons, epsilon_days=1e-9)
validate_referential_integrity(ocel_cons)

# ---- B. Evidence-based merge (separate copy) ----
ocel_evidence = copy.deepcopy(ocel_cons)
# Merge e07 summary into e06 detail (explicit trade-off, abstraction loss)
ocel_evidence, audit_0607 = merge_verified_pair(
    ocel_evidence, keep_eid="e06", drop_eids=["e07"],
    authority={"detail": "WMS", "status_flag": "ERP"},
    merge_rule="evidence_derived_summary_fold",
    reason="Fact3: ERP status derived from WMS message; fold only if abstraction not needed")

# ---- C. Aggressive library merge (separate copy, WARNING) ----
ocel_aggr = copy.deepcopy(ocel_raw)
ocel_aggr.events = ensure_provenance_cols(ocel_aggr.events)
# WARNING: applies grouping by (activity, timestamp, common object) globally.
# Collapses e03/e04/e05, e06/e07, e08/e09, e11/e16, e13/e14/e15 despite
# distinct Item/Payment objects sharing O1/V1. Demonstrates semantic damage.
ocel_aggr = pm4py.ocel_merge_duplicates(ocel_aggr, have_common_object=True)
validate_referential_integrity(ocel_aggr)
```

## 7. Sensitivity analysis
Compare raw (17), conservative (15), evidence-merge (14), aggressive (~10). Event count and E2O relation count fall monotonically, but information loss is non-linear.

Event/E2O: raw has duplicate edges (O1,I1,P1 twice for e03/e04; O1,V1 twice for e11/e16). Conservative removes 2 events + ~5 duplicate E2O edges, preserving all objects (O1,I1,I2,P1,D1,V1,M1,M2). Evidence removes one more event + I-detail vs summary distinction (unioned E2O masks abstraction). Aggressive removes 7 events, unions incompatible relations (I1+I2 on one Pick; M1+M2 on one Capture), inflating per-event ET–OT degree while deflating total frequency — classic false batch.

Order-flattened DFG (Order O1): raw shows `Pick Item  Pick Item` (e03e04e05) and `Pack  Pack` and `Dispatch  Dispatch  Handover` and `Issue  Issue` loops plus `Capture  Capture` chain. Conservative cleans Pick I1 loop (single Pick I1  Pick I2 edge remains, correctly indicating two picks) and Invoice loop, but retains `Pack [detail]  Pack [status]` and `Dispatch [released]  Dispatch [accepted]` — true handshake, not rework. Evidence erases Pack self-loop (single Pack), hiding reporting lag. Aggressive erases all same-label loops, falsely suggesting one pick, one pack, one dispatch, one capture — throughput looks faster, variance vanishes.

Item-flattened DFG: raw/conservative/evidence correctly show I1: PickPack and I2: PickPack as parallel branches (no I1I2 edge). Aggressive merges Picks, so I1 and I2 appear picked together in one event, then packed together — loses pick concurrency and per-item lead time; item-level performance (pick-to-pack) becomes identical for I1/I2 by construction.

Payment-flattened DFG: M1 lifecycle AuthorizeCapture visible in raw/conservative/evidence; M2 only Capture. Conservative retains M1 vs M2 separation, so Payment-DFG has two disconnected traces. Aggressive merges e13/e14(/e15) into one Capture linked to both M1+M2, creating false shared transition and breaking payment-level filtering; M1 authorize appears to authorize both payments.

OC-DFG edges/frequency: raw overcounts `PickPack` and `IssueAuthorize` due to duplicates. Conservative normalizes frequencies to business truth. Aggressive undercounts and creates spurious high-degree nodes (one Capture with 3× objects). ET–OT weights (events per object type) drop for Order/Package/Invoice in aggressive, while per-event object fan-out spikes — misleading object-interaction metrics.

OTG relations: raw/conservative show Package P1 linked to two Picks + Pack + Dispatch chain; Delivery D1 linked to Dispatch×2 + Handover. Aggressive collapses to Pick×1 + Dispatch×1, understating handover complexity.

Apparent rework/loops: raw suggests rework everywhere (Pick, Pack, Dispatch, Invoice, Capture). Conservative resolves Pick-I1 and Invoice as duplication, confirms Pack detailstatus and Dispatch releaseaccept as non-rework staging. Aggressive claims zero rework — false cleanliness.

Lifecycle/performance: raw second-precision ties give zero durations within 10:00, 10:15, 12:00 blocks; ingestion-based ordering would invent negative or spurious delays. Conservative epsilon-after-order yields small deterministic gaps but preserves `original_timestamp` for honest performance (report ties as 1s granularity). Aggressive shortens end-to-end (fewer events) and erases WMSERP and PSPERP lags, biasing bottleneck analysis away from integration delay.

Six concrete edges/patterns whose interpretation changes: (1) `Pick Item  Pick Item` (Order view) — raw false I1 rework vs conservative true I1I2 concurrency vs aggressive erased; (2) `Pack [detail]  Pack [status]` — retained as abstraction in conservative, erased in evidence/aggressive; (3) `Dispatch [released]  Dispatch [accepted]  Handover` — harmonization restored in conservative, collapsed to single Dispatch in aggressive; (4) `Issue Invoice  Authorize Payment` — duplicated invoice predecessor in raw, single in conservative, unchanged in aggressive but with wrong frequency; (5) `Authorize M1  Capture M1` vs `Capture M1  Capture M2` — concurrent distinct payments in conservative, single merged Capture in aggressive; (6) `Capture (PSP)  Capture [ERP-summary]` — derivation edge preserved in conservative/evidence, merged away in aggressive, hiding ERP posting delay.

## 8. Audit trail and reversibility
Provenance is first-class, stored in event table + separate audit log, never overwriting raw.

Schema per canonical event (`audit_log` row + event columns):
- `canonical_eid` (e.g. e03, e11) + `source_eids` list ([e03,e04]).
- `merge_rule` (e.g. `verified_same_scan_reconciliation_report`, `verified_same_invoice_V1_authority_map`, `evidence_derived_summary_fold`, `exact_technical_drop`, `none_retained`, `relabel_only`) + `rule_version` / `reviewer` (analyst id or `rule_v1.0`).
- `original_activity` and `refined_activity` (e.g. Dispatch Package  Dispatch Package [carrier-accepted]); `original_timestamp` (second precision, immutable) and `adjusted_timestamp` (epsilon-shifted for sorting) + `semantic_rank` + `order_reason`.
- `attributes_retained_from_each_source`: map source{attrs kept} + authority (e.g. locationWMS, taxBILLING) + `payload_hash` per source.
- `discarded_conflicts`: list of {attr: [values], chosen, reason} — no silent last-wins.
- `confidence` (High/Medium/Low) + `reason` (free text citing facts 1–10).
- `e2o_before/after`: relation sets unioned/deduped; `qualifiers` preserved.
- Flags: `duplicate_suspect_group`, `derived_from`, `quarantine`.

Implementation: `original_*` columns immutable; `merged_source_keys`, `merge_rule` on canonical event; dropped eids retained in audit + optional `tombstone` table (never deleted from raw snapshot). Epsilon column `adjusted_timestamp` distinct from `original_timestamp`.

Reconstruction: analyst loads `ocel_raw` snapshot (deep copy preserved) or reverses pipeline via audit: split merged canonicals by `source_eids`, restore `original_activity/timestamp` from audit, re-expand E2O from `e2o_before`, drop `semantic_rank/adjusted_timestamp`, re-sort by `original_timestamp + source_seq`. All scenarios reproducible by rule version; conservativeraw is lossless, evidence/aggressiveraw via same inverse because conflicts logged.

## 9. Failure modes and safeguards
1. **Collapsing distinct partial payments (e13/e14/e15):** grouping by activity+timestamp merges M1 vs M2. Safeguard: require equality on distinguishing object type (Payment id); treat shared O1/V1 as insufficient; retain separate.
2. **Converting abstraction-level updates into false rework or false singletons:** e06/e07 as PackPack loop misread as rework, or merged hiding status lag. Safeguard: refined labels `[detail]/[status]`, derivation link, keep both conservatively.
3. **Ordering by ingestion time:** ingested_at reflects pipeline, not business (fact 9); e07 (10:01:00) after e06 is coincidental, e09 (:20) after e08 (:01) not causal proof. Safeguard: ingestion is last-resort deterministic hint only; primary is domain + source_seq + lifecycle.
4. **Treating shared objects as proof of duplication:** `have_common_object=True` passes for e13/e14 via O1/V1 and e03/e05 via O1/P1. Safeguard: pre-check object overlap + distinguishing-object inequality; never auto-merge on overlap alone.
5. **Unioning incompatible E2O relations:** merging e15 (no Payment) with e13 (M1) creates event linked to M1+M2 or invoice-only Capture with payments. Safeguard: relation-compatibility check (subset vs conflicting distinct ids); quarantine on mismatch.
6. **Changing durations through synthetic microseconds:** epsilon-before-reasoning freezes arbitrary order as truth, corrupting lead times (pickpack, PSPERP). Safeguard: decide semantic partial order first, preserve `original_timestamp`, add timedelta only after sorting, document as non-semantic.
7. **Losing source-authoritative attributes:** last-wins merge of e11/e16 or e03/e04 drops BILLING tax or WMS location. Safeguard: authority map + union + conflict log; validate no nulling of authoritative fields.
8. **Applying duplicate functions to whole OCEL without inspecting candidate groups:** blanket `ocel_drop/merge_duplicates` merges e05, e14, e08/e09. Safeguard: mandatory `precheck_candidate_groups` (activity+second+object diff), per-group decision table, deep-copy scenario isolation, referential-integrity validation; aggressive scenario only on copy with explicit warning.
