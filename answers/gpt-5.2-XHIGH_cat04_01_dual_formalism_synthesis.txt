# 1. Assumptions and Interpretation

1. The **low-risk vs high-risk** distinction is represented as an explicit **XOR choice** taken after `Analyze Root Cause`: either the case requires exactly one `Supervisor Review` (low risk) or it requires both `Quality Review` and `Regulatory Review` (high risk). The models do not encode risk data, so both branches are nondeterministically available after analysis.
2. **Optional supplier consultation** is represented as an **XOR between a silent skip and `Consult Supplier`**, guaranteeing it occurs **at most once**. When selected, it may complete at any point after `Analyze Root Cause` but must complete before `Release Material`.
3. Because **inspection outcomes are not event labels**, “passing inspection” is abstracted by **loop termination**: the **final** `Inspect Trial` that exits the loop is interpreted as the **passing** inspection. Taking the redo branch (`Adjust Parameters`) represents a **failing** inspection and forces another `Execute Trial`–`Inspect Trial` iteration.
4. **Duplicate visible labels** (other than the intended repetition of the trial activities through the loop) are **not used**. In particular, `Analyze Root Cause` is not duplicated to simulate cross-branch dependencies.
5. **Process-tree approximation policy**: a **conservative under-approximation** (overconstraining rather than admitting unsafe behavior). Concretely, the tree delays the start of approvals and supplier consultation until after both `Plan Verification` and `Design Corrective Action` complete, because a block-structured tree cannot directly encode “approvals start after analysis, trial starts after plan+design, and release joins all” without either duplication or additional synchronization.
6. “**May overlap**” is interpreted as **true concurrency at completion-time semantics**: there is **no required completion-time order** between the overlapping activities, so any interleaving consistent with the explicit precedence constraints is allowed.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D1 | START | Register Deviation | Start | Every case starts by registering the deviation. |
| D2 | Register Deviation | Contain Material | Precedence | Containment work begins after case registration. |
| D3 | Register Deviation | Analyze Root Cause | Precedence | Root-cause analysis begins after case registration. |
| D4 | Contain Material | Analyze Root Cause | Concurrency (no order) | After registration, containment and analysis may proceed independently and overlap. |
| D5 | Contain Material | Plan Verification | Precedence | Verification planning can start only after containment completes. |
| D6 | Analyze Root Cause | Design Corrective Action | Precedence | Corrective-action design can start only after analysis completes. |
| D7 | Analyze Root Cause | Approval Route (XOR) | Precedence + Choice | Risk route is selected after analysis. |
| D8 | Approval Route (low-risk branch) | Supervisor Review | Mandatory activity | Low-risk cases require supervisor review. |
| D9 | Approval Route (high-risk branch) | Quality Review + Regulatory Review | AND (both), concurrent | High-risk cases require both reviews; they may occur concurrently and finish in either order. |
| D10 | Analyze Root Cause | Consult Supplier (optional) | Optional + Precedence | Supplier consultation may be selected after analysis and occurs at most once. |
| D11 | Plan Verification + Design Corrective Action | Execute Trial (loop entry) | Synchronization (AND-join) | Trial may start as soon as both work products are complete. |
| D12 | Execute Trial | Inspect Trial | Precedence (per iteration) | Each trial iteration is executed then inspected. |
| D13 | Inspect Trial (fail) | Adjust Parameters → next Execute Trial | Loop/redo | A failed inspection triggers parameter adjustment and another trial iteration. |
| D14 | Inspect Trial (pass) | Exit loop (no Adjust Parameters after) | Loop exit constraint | Adjust Parameters must never occur after the passing inspection. |
| D15 | Approval Route | Trial Cycle | Concurrency (no order) | Approvals do not have to be complete before trial starts and may overlap the trial cycle. |
| D16 | Consult Supplier (if selected) | Release Material | Precedence | Supplier consultation must be complete before releasing material. |
| D17 | Passing Inspect Trial + Approval Route completion (+ Consult Supplier if selected) | Release Material | Synchronization (AND-join) | Release requires a passing inspection and completion of all selected obligations. |
| D18 | Release Material | Archive Case | Precedence + End | Archiving happens after release; it ends the case. |

# 3. PM4Py Process-Tree Model

**Process-tree expression (approximate):**

```text
->('Register Deviation',
  +(->('Contain Material','Plan Verification'),
    ->('Analyze Root Cause','Design Corrective Action')),
  +(X(tau,'Consult Supplier'),
    X('Supervisor Review',+('Quality Review','Regulatory Review')),
    *(->('Execute Trial','Inspect Trial'),'Adjust Parameters')),
  'Release Material',
  'Archive Case')
```

**Python (constructs `tree`):**

```python
import pm4py

tree_expr = "->('Register Deviation',+(->('Contain Material','Plan Verification'),->('Analyze Root Cause','Design Corrective Action')),+(X(tau,'Consult Supplier'),X('Supervisor Review',+('Quality Review','Regulatory Review')),*(->('Execute Trial','Inspect Trial'),'Adjust Parameters')),'Release Material','Archive Case')"

tree = pm4py.parse_process_tree(tree_expr)
```

**Mapping to the narrative.** The first parallel block models the two initial work streams after registration: `Contain Material → Plan Verification` and `Analyze Root Cause → Design Corrective Action`. The second parallel block models the three obligations that must all complete before release: (i) optional supplier consultation (`tau` vs `Consult Supplier`), (ii) the risk-dependent approval route (`Supervisor Review` vs parallel `Quality Review` and `Regulatory Review`), and (iii) the repeat-until trial loop `*( (Execute Trial → Inspect Trial), Adjust Parameters )`. Finally, `Release Material → Archive Case` closes the case.

**Unavoidable/explicit approximations in the tree.** The intended model allows approvals and (if selected) `Consult Supplier` to start immediately after `Analyze Root Cause` and overlap with `Plan Verification` and `Design Corrective Action`, while the process tree forces all approvals and supplier consultation to occur only after both `Plan Verification` and `Design Corrective Action` are finished (because they are placed in a later block following the first parallel join); therefore intended traces where a review or supplier consultation completes “early” (before PV or DCA) are excluded. As required by the prompt, the tree also cannot encode data-driven conditions (low vs high risk, supplier involvement) or the inspection outcome; it represents them through explicit XOR branching and nondeterministic loop exit, interpreting the final `Inspect Trial` as the passing inspection.

# 4. PM4Py POWL Model

**Compact POWL description (faithful partial order):**

```text
Nodes:
  RD='Register Deviation'
  CM='Contain Material'
  ARC='Analyze Root Cause'
  PV='Plan Verification'
  DCA='Design Corrective Action'
  supplier_opt = XOR(tau, 'Consult Supplier')
  approval = XOR('Supervisor Review', PO{ 'Quality Review' || 'Regulatory Review' })
  trial_loop = LOOP( PO('Execute Trial' -> 'Inspect Trial'), 'Adjust Parameters' )
  RM='Release Material'
  AC='Archive Case'

Partial-order edges:
  RD -> CM, RD -> ARC
  CM -> PV
  ARC -> DCA, ARC -> supplier_opt, ARC -> approval
  PV -> trial_loop, DCA -> trial_loop
  trial_loop -> RM, supplier_opt -> RM, approval -> RM
  RM -> AC
```

**Python (constructs `powl`):**

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# Visible activities
rd = Transition("Register Deviation")
cm = Transition("Contain Material")
arc = Transition("Analyze Root Cause")
pv = Transition("Plan Verification")
dca = Transition("Design Corrective Action")
sr = Transition("Supervisor Review")
qr = Transition("Quality Review")
rr = Transition("Regulatory Review")
cs = Transition("Consult Supplier")
et = Transition("Execute Trial")
it = Transition("Inspect Trial")
ap = Transition("Adjust Parameters")
rm = Transition("Release Material")
ac = Transition("Archive Case")

# High-risk approvals: Quality and Regulatory are concurrent (no edge)
high_risk = StrictPartialOrder([qr, rr])

# Risk route choice (low vs high)
approval = OperatorPOWL(Operator.XOR, [sr, high_risk])

# Optional supplier consultation (skip vs consult)
supplier_opt = OperatorPOWL(Operator.XOR, [SilentTransition(), cs])

# Trial iteration body: Execute -> Inspect
trial_body = StrictPartialOrder([et, it])
trial_body.order.add_edge(et, it)

# Repeat-until loop: (Execute->Inspect) then either exit or (Adjust) and repeat
trial_loop = OperatorPOWL(Operator.LOOP, [trial_body, ap])

# Root partial order (cross-branch dependencies expressed with edges)
powl = StrictPartialOrder([rd, cm, arc, pv, dca, supplier_opt, approval, trial_loop, rm, ac])

powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)

powl.order.add_edge(cm, pv)
powl.order.add_edge(arc, dca)

powl.order.add_edge(arc, supplier_opt)
powl.order.add_edge(arc, approval)

powl.order.add_edge(pv, trial_loop)
powl.order.add_edge(dca, trial_loop)

powl.order.add_edge(trial_loop, rm)
powl.order.add_edge(approval, rm)
powl.order.add_edge(supplier_opt, rm)

powl.order.add_edge(rm, ac)
```

**Why intentionally unconnected nodes may remain concurrent.** No edge is added between `Contain Material` and `Analyze Root Cause` because they are explicitly allowed to overlap after registration; `Plan Verification` has only the dependency `Contain Material → Plan Verification`, so it may overlap analysis-related work; `Design Corrective Action`, `approval`, and `supplier_opt` all depend only on `Analyze Root Cause`, so they may overlap each other and may also overlap `Plan Verification`; `trial_loop` depends on both `Plan Verification` and `Design Corrective Action` but has no direct order relation with `approval` or `supplier_opt`, allowing approvals and (optional) supplier consultation to overlap the trial cycle; finally, in the high-risk submodel, `Quality Review` and `Regulatory Review` are left unconnected to permit either completion order and true concurrency.

# 7. Preferred Representation and Validation Plan

**Preferred canonical representation: the POWL model.** The narrative’s defining difficulty is the non-block-structured dependency pattern (plan depends on containment, design+approvals depend on analysis, trial depends on plan+design, release synchronizes trial/approvals/supplier). POWL can express these cross-branch dependencies directly with partial-order edges while preserving intended overlap; the process tree necessarily overconstrains or duplicates behavior to fit block structure.

**Validation plan (concrete, tool-supported):**

- **Convert to accepting Petri nets (where supported)**: `net_t, im_t, fm_t = pm4py.convert_to_petri_net(tree)` and `net_p, im_p, fm_p = pm4py.convert_to_petri_net(powl)`.
- **Soundness checking of converted nets**: run `pm4py.check_soundness(net_p, im_p, fm_p, print_diagnostics=True)` (and likewise for the tree-derived net) to detect deadlocks, dead tasks, or non-workflow structure introduced by conversion.
- **Bounded / sampled playout**: use `pm4py.play_out(...)` on each model/net with a small maximum trace length and bounded loop repetitions to sample interleavings; explicitly sample both risk branches and both supplier choices.
- **Explicit positive/negative trace tests**: turn the eight witness traces into a tiny event log and check fitness (e.g., via alignments or token-based replay) against each converted net; verify that A1–A4 are accepted by both models, A5 is rejected only by the tree, and F1–F3 are rejected by both.
- **Silent / duplicate-label targeted check**: inspect the converted net(s) for silent transitions introduced by XOR/parallel joins (e.g., `tauSplit`, `tauJoin`, `skip_*`) and confirm they do not enable skipping required visible obligations; also assert that visible labels are unique outside the trial loop and that no duplicated `Analyze Root Cause` (or other non-loop activity) appears in sampled playout traces.
- **Limitations**: bounded playout cannot exhaust all interleavings (especially with concurrency and loops); Petri-net conversion may add silent routing transitions that preserve language but obscure causal explanations; soundness does not prove semantic equivalence to the narrative; and data-dependent semantics (risk classification, supplier-selection policy, inspection result) remain outside pure control-flow validation.

# 8. Final Self-Critique

1. The process tree is a deliberate under-approximation: it delays approvals and supplier consultation until after `Plan Verification` and `Design Corrective Action`, excluding intended early-completion interleavings (e.g., witness A5).
2. Even the POWL model necessarily treats low/high risk, supplier involvement, and pass/fail inspection as nondeterministic control-flow choices; it cannot enforce that “the right branch” is taken for a given case without adding data-aware constraints.
3. The witness set is illustrative rather than exhaustive; it does not prove full equivalence, and subtle interleavings (e.g., approvals completing between trial iterations under high risk while supplier consultation is also active) are not explicitly enumerated or tested here.
