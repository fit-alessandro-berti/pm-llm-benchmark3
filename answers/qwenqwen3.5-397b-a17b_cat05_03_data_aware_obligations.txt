## 1. Temporal Data Semantics

To assess compliance accurately, we must reconstruct the state of the case at every relevant moment, specifically at the `Release_Funds` event. The following semantic principles apply:

*   **State Reconstruction:** Attributes (amount, risk, jurisdiction, customer_type) are stateful. A blank cell in the event log indicates **no change** from the previous value, not a nullification. We forward-fill attributes within each `case:concept:name` group ordered by `time:timestamp` and `event_index`.
*   **Event Time vs. Record Time:** `time:timestamp` represents the event time (when the action occurred in the system). `Record_Exemption` events may have a later record time than the effective approval time. We rely on external evidence (signatures, logs) to establish the **Effective Time** of an exemption.
*   **Effective Time of Updates:** Attribute updates (e.g., `Update_Amount`) are effective immediately at their `time:timestamp` unless evidence suggests otherwise.
*   **Same-Timestamp Ordering:** When multiple events share a `time:timestamp`, `event_index` determines the sequence. State changes occurring at a higher `event_index` do not affect obligations triggered by events at a lower `event_index` within the same timestamp.
*   **Final State Fallacy:** The final attribute values in a case (e.g., after settlement) do not retroactively govern earlier events (e.g., release). We evaluate obligations using the **latest known value at the relevant event**.
*   **Missing Data:** If a decisive attribute (like amount for R1) is unknown at the trigger event and cannot be inferred from prior reliable events, the compliance status is `INDETERMINATE`. We do not default to low-risk assumptions.

// Let State(c, t) be the attribute values for case c at time t (indexed by event_index)
// Let Events(c) be the ordered sequence of events for case c

// R1: Foreign High-Value Enhanced Review
FOR EACH e IN Events(c) WHERE e.name == 'Release_Funds':
    jurisdiction := State(c, e).jurisdiction
    amount := State(c, e).amount
    IF jurisdiction != 'DE' AND amount >= 100000:
        last_review := MAX(ev.time WHERE ev.name == 'Enhanced_Review' AND ev.time < e.time)
        last_change := MAX(ev.time WHERE ev.name == 'Update_Amount' AND ev.time < e.time AND change > 20%)
        exemption_valid := CHECK_EXEMPTION(c, e.time, 'R1')
        IF NOT (last_review > last_change AND exemption_valid):
            FLAG_NONCOMPLIANT('R1')

// R2: High-Risk or PEP Approval
FOR EACH e IN Events(c) WHERE e.name == 'Release_Funds':
    risk := State(c, e).risk_level
    ctype := State(c, e).customer_type
    IF risk == 'HIGH' OR ctype == 'PEP':
        review := MAX(ev.time WHERE ev.name == 'Enhanced_Review' AND ev.time < e.time)
        approve := MAX(ev.time WHERE ev.name == 'Compliance_Approve' AND ev.time < e.time)
        IF NOT (review EXISTS AND approve > review):
            FLAG_NONCOMPLIANT('R2')

// R3: Sanctions List Update
FOR EACH e IN Events(c) WHERE e.name == 'Release_Funds':
    screen := MAX(ev.time WHERE ev.name == 'Sanctions_Screen' AND ev.time < e.time)
    list_update := MAX(ev.time WHERE ev.name == 'Sanctions_List_Update' AND ev.time < e.time)
    IF list_update > screen:
        new_screen := MAX(ev.time WHERE ev.name == 'Sanctions_Screen' AND ev.time > list_update AND ev.time < e.time)
        IF NOT new_screen EXISTS:
            FLAG_NONCOMPLIANT('R3')

// R4: Material Amount Change
FOR EACH e IN Events(c) WHERE e.name == 'Update_Amount':
    prev_amount := State(c, e.prev_event).amount
    curr_amount := State(c, e).amount
    IF prev_amount IS KNOWN AND (curr_amount - prev_amount) / prev_amount > 0.20:
        INVALIDATE_REVIEWS_AFTER(e.time)

// R5: Exemption Validity
FUNCTION CHECK_EXEMPTION(case, time, rule):
    ex := GET_EXEMPTION(case, time)
    IF ex.approval_signature_time <= time AND ex.scope_matches(rule) AND ex.not_expired(time):
        RETURN TRUE
    RETURN FALSE

    *   *Alternative:* If the signature timestamp is deemed unreliable without a chain-of-custody log, the case becomes NONCOMPLIANT because the system record did not exist at release.
*   **TX-305 (Missing Amount):**
    *   *Current Reading:* INDETERMINATE. The amount is unknown at `Release_Funds`. R1 cannot be evaluated.
    *   *Alternative:* If policy allows using Settlement data as a proxy for Release data (retroactive validation), the case becomes NONCOMPLIANT (150k > 100k, no Enhanced Review). However, this violates event-time semantics.
*   **TX-310 (Backdated Exemption):**
    *   *Current Reading:* INDETERMINATE. The PDF claims 08:50 approval, but the cryptographic certificate is 10:30 (post-release). The witness is biased.
    *   *Alternative:* If organizational policy accepts witness testimony for amounts under 500k, this could be JUSTIFIED_EXCEPTION. If policy requires cryptographic proof before release, it is NONCOMPLIANT.
*   **TX-311 (Same-Timestamp Ordering):**
    *   *Current Reading:* COMPLIANT. `event_index` 3 (Review) happens before `event_index` 4 (Jurisdiction Change to DE). At release, Jurisdiction is DE, exempting R1.
    *   *Alternative:* If the system clock granularity is too coarse and `event_index` is not trusted as a true sequence, one might argue the Review occurred under DE jurisdiction (if updates were batched). This would still be COMPLIANT (Review exists), but the reasoning changes. If the order were reversed (Jurisdiction change before Review), the Review would be on DE (exempt), still Compliant. The critical ambiguity is if the Review was *required* when it happened (US) vs when released (DE). R1 triggers at Release. At Release, it is DE. So R1 is not triggered.

## 6. Why Control-Flow-Only Conformance Is Insufficient

Relying solely on control-flow conformance (e.g., BPMN, DECLARE) fails in this context due to six distinct modes:

1.  **Final-State Leakage:** Control-flow models often validate the existence of an event in the trace, regardless of *when* it occurred relative to data changes. A model might see `Enhanced_Review` and `Release_Funds` and pass, missing that the Review happened before a material Amount Increase (TX-301).
2.  **Post-Hoc Exemptions:** Control flow cannot distinguish between an exemption recorded at 11:00 and approved at 09:00. It sees the `Record_Exemption` event and might assume validity, ignoring the signature timestamp evidence required by R5 (TX-310).
3.  **Material Changes After Review:** Standard conformance checks do not track attribute values. It cannot detect that an `Update_Amount` event invalidates a prior `Review` event (R4), leading to false compliance on TX-309.
4.  **Conditional Activation:** Rules like R1 only trigger if `amount >= 100k` and `jurisdiction != DE`. Control-flow models treat all traces equally, unable to branch logic based on payload data (TX-311 vs TX-301).
5.  **Missing Data:** A control-flow model assumes events carry valid data. It cannot flag `INDETERMINATE` when a critical attribute like `amount` is missing at the trigger event (TX-305).
6.  **Same-Timestamp Ordering:** Control-flow typically sorts by timestamp only. It cannot enforce logic dependent on `event_index` when timestamps are identical, potentially reversing the causal order of Review vs. Jurisdiction Change (TX-311).

## 7. Recommended Logging and Control Improvements

To make future compliance decisions determinate and automatable, the following improvements are recommended:

*   **Immutable Release Payloads:** The `Release_Funds` event must contain a signed snapshot of all governing attributes (amount, jurisdiction, risk, customer_type) at the exact moment of release. This prevents reliance on forward-filled history.
*   **Triple-Timestamping:** All events, especially exemptions and approvals, must record: (1) `event_time` (system receipt), (2) `effective_time` (business validity), and (3) `signature_time` (cryptographic proof).
*   **Rule Versioning:** Logs should reference the specific policy version (e.g., `policy_v2.1`) active at the time of the event to handle rule changes.
*   **Exemption Scope in Log:** The `Record_Exemption` event should explicitly list the waived rules (e.g., `waives: [R1]`) and the matching criteria (e.g., `scope: amount<=250k`) to allow automated validation.
*   **Change Provenance:** `Update_` events should include `previous_value` and `reason_code` to facilitate R4 calculations without needing to query prior state.
*   **Stable Event Ordering:** Use logical clocks (e.g., Lamport timestamps) or strictly monotonic sequence IDs alongside UTC timestamps to resolve same-timestamp ambiguities definitively without relying on `event_index` which may be DB-specific.
