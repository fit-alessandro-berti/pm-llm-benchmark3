# 1. Objectives and constraints

The policy optimizes several objectives that are partly in tension:

- **Short-term throughput**: assign work quickly enough to avoid unnecessary waiting.
- **SLA protection**: protect urgent and high-priority cases from delay and rework.
- **Error/rework reduction**: match required skills to case difficulty and activity rules.
- **Workload fairness**: avoid concentrating new work on a few resources or overloading high-overtime-risk staff.
- **Skill development**: use safe, lower-risk cases for documented training priorities.
- **Continuity of case ownership**: avoid handovers when they create waiting, rework, or appeal risk.
- **Resilience**: avoid creating specialist bottlenecks and single points of failure.

Hard constraints are treated as safety/compliance filters. Soft preferences are scored and trade off against each other.

### Hard constraints

1. A resource with skill level **0** for an activity is not eligible.
2. **Security Review** must be performed by skill level 3, or by skill level 1–2 only under explicit supervision by **R7_Gita** or **R8_Hugo**.
3. **Final Approval** must be performed by skill level 2–3. Skill level 1 may prepare but not finalize.
4. No high-priority case may be assigned to skill level below 2 unless supervised.
5. No resource may receive more than **4 new assignments** in the current decision batch.
6. Quality Check may be batched only when priority is normal/low and SLA time remaining is above 24 hours.
7. For high-complexity cases with high handover cost, continuity is preferred unless the current owner has skill 0/1 and no supervision is feasible.
8. High-overtime-risk resources should not receive new non-urgent work if a safer alternative exists.
9. At least 20% of normal/low-priority assignments should support documented training priorities if SLA risk remains acceptable.

### Soft preferences

- Prefer higher skill level, but not at the cost of overload or unnecessary handover.
- Prefer current owner when reassignment count or handover cost is high.
- Prefer resources with low open cases, enough remaining hours, and low overtime risk.
- Prefer training assignments on normal/low-priority cases with comfortable SLA buffers.
- Distribute scarce specialists so that Security, Approval, Diagnosis, Quality, and Rework do not queue behind one person.

# 2. Assignment policy

The policy is rule-first, score-second. Candidates must pass hard eligibility and safety filters. Survivors are ranked with an explainable score.

### Pseudocode

```text
for each case c:
    sort cases by urgency_score(c) descending

for each case c:
    candidates = []

    for each resource r:
        # 1. Eligibility filtering by skill and rule constraints
        if skill_matrix[r][c.required_skill] == 0:
            continue
        if violates_activity_rule(c, r):
            continue
        if c.high_priority and skill_matrix[r][c.required_skill] < 2:
            if not supervised_by_competent(r, c):
                continue

        # 2. Workload filter
        if r.new_assignments >= 4:
            continue

        # 3. Overtime-risk filter
        if r.overtime_risk == "high" and c.priority != "urgent":
            if safer_alternative_exists(c, r):
                continue

        # 4. Continuity/handover filter
        if c.complexity >= 0.70 and c.handover_cost == "high":
            if r != c.current_owner:
                if not current_owner_weak_and_supervision_feasible(c):
                    penalty = large
                else:
                    penalty = moderate

        # 5. Score candidate
        score = (
            w_urgency * urgency_fit(r, c)
            + w_skill * skill_match(r, c)
            + w_continuity * continuity_score(r, c)
            + w_workload * workload_score(r, c)
            + w_overtime * overtime_score(r, c)
            + w_training * training_score(r, c)
            + w_resilience * resilience_score(r, c)
        )

        candidates.append((score, r))

    if candidates:
        assign c to candidate with highest score
        tie-break:
            1. current owner
            2. lower open cases
            3. lower overtime risk
            4. higher skill level
    else:
        create supervised exception pair with specialist
        record exception reason
```

### Scoring definitions

- **SLA urgency scoring**  
  ```text
  urgency_score = priority_weight(priority) * exp(-SLA_hours_remaining / horizon)
  ```
  Urgent/high-priority cases get larger weights, and shorter deadlines increase urgency.

- **Skill-match scoring**  
  ```text
  skill_match =
      1.0 if skill level 3
      0.7 if skill level 2
      0.4 if skill level 1 supervised
      0.0 if not allowed
  ```

- **Continuity / handover-cost scoring**  
  ```text
  continuity_score =
      +0.6 if resource == current_owner
      -0.4 if handover_cost == "high" and resource != current_owner
      -0.2 if reassignment_count >= 2 and resource != current_owner
      -0.1 * reassignment_count
  ```

- **Workload and overtime fairness scoring**  
  ```text
  workload_score =
      -0.1 * max(0, open_cases - 8)
      -0.2 * max(0, 4 - hours_remaining)
      -0.3 if overtime_risk == "high"
      -0.1 if overtime_risk == "medium"
  ```

- **Training/development scoring**  
  ```text
  training_score =
      +0.4 if resource.training_priority == required_skill
      +0.2 if priority in {normal, low} and SLA_remaining > 24
      +0.2 if supervised by a specialist
  ```

- **Resilience / bottleneck avoidance**  
  ```text
  resilience_score =
      -0.3 if using a scarce specialist when a competent non-specialist also exists
      -0.2 if resource has >= 3 new assignments already
  ```

The scores are intentionally simple so each assignment can be explained as a combination of visible reasons: deadline pressure, skill fit, ownership continuity, workload, training, and bottleneck avoidance.

# 5. Explanation to workers

Assignments are made using a small number of transparent rules:

- Is the person allowed to do the activity?
- Is the person currently the owner, and would keeping ownership reduce risk?
- Is the workload reasonable today?
- Is there a safe training opportunity?
- Is the deadline close enough that specialist help is needed?

When someone is assigned as a supervised pair, it is not because they are not trusted. It is because the activity has a safety or compliance rule that requires supervision, or because the case is a good development opportunity with enough time buffer.

When a case is moved away from its current owner, it is usually because the current owner has high overtime risk, very high current workload, or because a safer specialist/training assignment exists. It is not a punishment.

When a resource receives fewer assignments, it is often because their load or overtime risk is already high. The goal is to keep the whole team healthy and avoid pushing risk into next week.

Training assignments are chosen only when the case has enough SLA buffer and supervision is available. We would rather develop skills on low-risk cases than on urgent ones.

)

# Auditing assignments against policy indicators
assignment_log = pd.read_csv("assignments.csv")
resource_skill = pd.read_csv("resource_skill_matrix.csv")

audit = assignment_log.merge(
    resource_skill,
    left_on="org:resource",
    right_on="Resource"
)

# Handover rate
handover_rate = (
    audit["org:resource"] != audit["current_owner"]
).mean()

# Skill mismatch
skill_mismatch_rate = (
    audit["assigned_skill_level"] < audit["minimum_required_skill"]
).mean()

# Training share
normal_low_assign = audit[audit["case_priority"].isin(["normal", "low"])]
training_share = normal_low_assign["supports_training"].mean()

# Overtime risk exposure
high_overtime_exposure = (
    audit["overtime_risk"] == "high"
).mean()

# Specialist bottleneck indicator: queue length before Security and Approval
security_queue = audit[
    (audit["required_skill"] == "Security")
].groupby("org:resource").size()

approval_queue = audit[
    (audit["required_skill"] == "Approval")
].groupby("org:resource").size()

print({
    "handover_rate": handover_rate,
    "skill_mismatch_rate": skill_mismatch_rate,
    "training_share": training_share,
    "high_overtime_exposure": high_overtime_exposure,
    "security_queue": security_queue.to_dict(),
    "approval_queue": approval_queue.to_dict()
})
