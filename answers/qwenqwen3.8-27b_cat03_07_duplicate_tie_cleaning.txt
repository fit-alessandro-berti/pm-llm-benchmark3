```
                comps.append({'eids':[row['eid']], 'objs':objs})
        groups.extend([c['eids'] for c in comps if len(c['eids']) > 1])

def merge_verified_pair(ocel, keep_eid, drop_eid, rule, confidence, reason):
    df = df_of(ocel).copy()
    k = df[df['eid'] == keep_eid].iloc[0]
    d = df[df['eid'] == drop_eid].iloc[0]
    objs = set(str(k['related_objects']).split(', ')) | set(str(d['related_objects']).split(', '))
    ids = list(dict.fromkeys([keep_eid, drop_eid] +
                             [x for x in str(k['source_event_ids']).split('|') if x] +
                             [x for x in str(d['source_event_ids']).split('|') if x]))
    df.loc[df['eid'] == keep_eid, 'related_objects'] = ', '.join(sorted(objs))
    df.loc[df['eid'] == keep_eid, 'source_event_ids'] = '|'.join(ids)
    df.loc[df['eid'] == keep_eid, 'merge_rule'] = rule
    df.loc[df['eid'] == keep_eid, 'merge_confidence'] = confidence
    df.loc[df['eid'] == keep_eid, 'merge_reason'] = reason
    df = df[df['eid'] != drop_eid]
    set_df(ocel, df)
    return ocel

def add_dedup_key(ocel):

                       '|' + df['original_activity'].astype(str))
    set_df(ocel, df)
    return ocel

def assign_order_key(ocel, constraints, source_priority):
    df = df_of(ocel).copy()
    df['order_rank'] = df.index
    for _ in range(len(df)):
        for a, b in constraints:
            ia = df.index[df['eid'] == a]
            ib = df.index[df['eid'] == b]
            if len(ia) and len(ib):
                ia, ib = ia[0], ib[0]
                if df.loc[ia, 'order_rank'] >= df.loc[ib, 'order_rank']:
                    df.loc[ib, 'order_rank'] = df.loc[ia, 'order_rank'] + 1
    df['source_priority'] = df['source'].map(source_priority).fillna(99)
    df = df.sort_values(['timestamp', 'order_rank', 'source_priority', 'eid']).reset_index(drop=True)
    df['order_key'] = df.index.astype(str)
    set_df(ocel, df)
    return ocel

    return True
```

## 1. Duplicate-handling decision tree

Candidate trigger: two or more events share timestamp, harmonized activity, source system proximity, or related objects.

1. **Same `source_event_key` and `payload_hash`?**  
   - Yes: **exact technical duplicate** caused by re-ingestion or replay.  
   - Action: **drop** the later technical copy; retain its identifier in provenance.

2. **No. Do reconciliation facts or a business key prove the same physical event observed by multiple systems?**  
   - Yes: **same physical event observed by multiple systems**.  
   - Action: **merge attributes and relations** into one canonical event; retain all source identifiers, original labels, timestamps, and payload hashes.

3. **No. Is one event explicitly derived from another as a summary, status update, or aggregate?**  
   - Yes: **summary event derived from a detailed event**.  
   - Conservative action: **retain both with refined labels or qualifiers**.  
   - Evidence-based action: may merge only if the summary adds no independent business fact.  
   - If derivation is uncertain: **quarantine for review**.

4. **No. Do the events have the same harmonized label but different source semantics?**  
   - Yes: **harmonization collision between semantically distinct source activities**.  
   - Action: **retain both with refined labels or qualifiers**; do not merge.

5. **No. Are they same-label events at the same timestamp but involving different object instances?**  
   - Yes: **concurrent same-label events involving different objects**.  
   - Action: **retain both unchanged**; use object relations to distinguish them.

6. **No. Are source facts sufficient to establish separate lifecycle steps, even with tied timestamps?**  
   - Yes: distinct lifecycle events.  
   - Action: **retain both unchanged** or with refined labels; encode known precedence as a partial-order constraint.

7. **Otherwise: unresolved candidate.**  
   - Action: **quarantine for review**; do not silently drop or merge.

## 3. Timestamp-tie ordering rules

| Rule type | Examples | Semantic or deterministic |
|---|---|---|
| Domain constraints | e12 Authorize Payment precedes e13 Capture Payment for M1; e09 Carrier Accept precedes e10 Handover | Semantic |
| Lifecycle constraints on shared objects | Picks for P1 before Pack for P1; Invoice V1 before payment events for V1 | Semantic if process model supports it; otherwise weak |
| Source-specific semantics | e06 WMS pack detail precedes e07 ERP pack summary; payment captures precede e15 ERP payment summary | Semantic |
| Within-source sequence | Same source and same timestamp: lower `source_seq` first, e.g., CARRIER e09 seq 1 before e10 seq 2 | Semi-semantic; use only when source sequence is trustworthy |
| Ingestion time | `ingested_at` may reveal late arrival, but is not business time | Deterministic only; excluded from primary order |
| Stable fallback | Source priority, then `eid`, then `source_event_key` | Merely deterministic |

The total order is a **deterministic representation**, not proof of physical causality. Adding synthetic microseconds before resolving semantic constraints can encode a false story: for example, forcing e03 before e05 creates an apparent Pick I1  Pick I2 dependency; forcing e08 before e09 creates a false WMS-release-to-carrier-acceptance duration; forcing e13 before e14 suggests M1 caused M2; forcing e15 after e14 makes the ERP summary appear dependent on M2 specifically. In DFGs, such artificial sequencing creates direct-follow edges, apparent rework, and distorted performance metrics that do not exist in the business process.

## 4. Conservative cleaning pipeline

The conservative pipeline is minimum-change and provenance-first.

1. Deep-copy the raw OCEL; never mutate the raw object.
2. Preserve `original_timestamp`, `original_activity`, `source`, `source_event_key`, `payload_hash`, and `ingested_at`.
3. Run a candidate-group pre-check before any duplicate function.
4. Merge only strongly supported cross-system duplicates: e03/e04 and e11/e16.
5. Use `pm4py.ocel_drop_duplicates` only for exact technical duplicates identified by source key, payload hash, original timestamp, and original activity.
6. Refine labels where harmonization is misleading:
   - e07  `Pack Package (ERP summary)`
   - e08  `Dispatch Package (WMS release)`
   - e09  `Carrier Accept`
   - e15  `Payment Summary (ERP)`
7. Build a partial order from semantic constraints, then convert it to a deterministic total order using stable fallback.
8. Sort by the derived `order_key`, then add index-based timedelta as a derived metric only.
9. Validate referential integrity and provenance completeness.

```python
import copy
import pandas as pd
import pm4py


def df_of(ocel):
    return ocel.get_dataframe()


def set_df(ocel, df):
    ocel.set_dataframe(df)
    return ocel


def add_original_columns(ocel):
    df = df_of(ocel).copy()
    df["original_timestamp"] = df["timestamp"]
    df["original_activity"] = df["activity"]
    for col in ["source", "source_event_key", "payload_hash", "ingested_at", "related_objects"]:
        if col not in df.columns:
            df[col] = ""
    if "related objects" in df.columns:
        df["related_objects"] = df["related objects"].fillna("")
    df["source_event_ids"] = df["source_event_key"].astype(str)
    df["merge_rule"] = ""
    df["merge_confidence"] = ""
    df["merge_reason"] = ""
    return set_df(ocel, df)


def candidate_groups(ocel):
    """Pre-check: group same timestamp/activity events that share at least one object."""
    df = df_of(ocel)
    groups = []
    for (_, _), g in df.groupby(["timestamp", "activity"]):
        comps = []
        for _, row in g.iterrows():
            objs = set(str(row["related_objects"]).split(", "))
            for c in comps:
                if objs & c["objs"]:
                    c["eids"].append(row["eid"])
                    c["objs"] |= objs
                    break
            else:
                comps.append({"eids": [row["eid"]], "objs": objs})
        groups.extend([c["eids"] for c in comps if len(c["eids"]) > 1])
    return groups


def merge_verified_pair(ocel, keep_eid, drop_eid, rule, confidence, reason):
    """
    Custom verified-pair merge.
    Keeps `keep_eid`, unions object relations, records provenance, and removes `drop_eid`.
    """
    df = df_of(ocel).copy()
    k = df[df["eid"] == keep_eid].iloc[0]
    d = df[df["eid"] == drop_eid].iloc[0]

    objs = set(str(k["related_objects"]).split(", ")) | set(str(d["related_objects"]).split(", "))
    ids = list(dict.fromkeys(
        [keep_eid, drop_eid]
        + [x for x in str(k["source_event_ids"]).split("|") if x]
        + [x for x in str(d["source_event_ids"]).split("|") if x]
    ))

    df.loc[df["eid"] == keep_eid, "related_objects"] = ", ".join(sorted(objs))
    df.loc[df["eid"] == keep_eid, "source_event_ids"] = "|".join(ids)
    df.loc[df["eid"] == keep_eid, "merge_rule"] = rule
    df.loc[df["eid"] == keep_eid, "merge_confidence"] = confidence
    df.loc[df["eid"] == keep_eid, "merge_reason"] = reason
    df = df[df["eid"] != drop_eid]
    return set_df(ocel, df)


def add_dedup_key(ocel):
    df = df_of(ocel).copy()
    df["dedup_key"] = (
        df["source"].astype(str)
        + "|" + df["source_event_key"].astype(str)
        + "|" + df["payload_hash"].astype(str)
        + "|" + df["original_timestamp"].astype(str)
        + "|" + df["original_activity"].astype(str)
    )
    return set_df(ocel, df)


def assign_order_key(ocel, constraints, source_priority):
    """
    Convert partial-order constraints into a deterministic order_key.
    This does not prove true physical order.
    """
    df = df_of(ocel).copy()
    df["order_rank"] = df.index

    for _ in range(len(df)):
        for a, b in constraints:
            ia = df.index[df["eid"] == a]
            ib = df.index[df["eid"] == b]
            if len(ia) and len(ib):
                ia, ib = ia[0], ib[0]
                if df.loc[ia, "order_rank"] >= df.loc[ib, "order_rank"]:
                    df.loc[ib, "order_rank"] = df.loc[ia, "order_rank"] + 1

    df["source_priority"] = df["source"].map(source_priority).fillna(99)
    df = df.sort_values(["timestamp", "order_rank", "source_priority", "eid"]).reset_index(drop=True)
    df["order_key"] = df.index.astype(str)
    return set_df(ocel, df)


def validate(ocel, raw):
    df = df_of(ocel)
    rdf = df_of(raw)
    assert df["eid"].is_unique
    assert set(df["source_event_key"]).issubset(set(rdf["source_event_key"]))
    raw_keys = set(rdf["source_event_key"])
    for _, row in df.iterrows():
        for sk in str(row["source_event_ids"]).split("|"):
            if sk:
                assert sk in raw_keys, f"missing provenance key {sk}"
    return True


# Raw OCEL is treated as immutable.
ocel_base = add_original_columns(copy.deepcopy(ocel_raw))

# Conservative scenario
ocel_cons = copy.deepcopy(ocel_base)

ocel_cons = add_dedup_key(ocel_cons)
ocel_cons = pm4py.ocel_drop_duplicates(ocel_cons, columns=["dedup_key"])

df = df_of(ocel_cons).copy()
df.loc[df["eid"] == "e07", "activity"] = "Pack Package (ERP summary)"

constraints = [
```

## 7. Sensitivity analysis

**Raw: 17 events, 44 E2O relations.**  
Order-flattened DFG shows repeated same-label edges: PickPick, PackPack, DispatchDispatch, IssueIssue, CaptureCapture. Item-flattened DFG shows I1 Pick duplicated by e03/e04 and I2 Pick separate. Payment-flattened DFG shows M1 AuthorizeCapture and M2 Capture only; e15 has no Payment object. OC-DFG frequencies are inflated by cross-system duplicates. ET–OT weights show Capture PaymentPayment weight 2, Payment SummaryPayment weight 0. OTG relations keep Package, Invoice, and Payment lifecycles separate but noisy. Apparent rework is high because tied timestamps and duplicate labels create immediate repeats. Lifecycle and performance measurements include zero-second durations and duplicate-event noise.

**Conservative: 15 events, 39 E2O relations.**  
Order-flattened DFG removes e03/e04 Pick duplicate and e11/e16 Issue duplicate, but may still show PickPick for e03/e05 and CaptureCapture for e13/e14. Item-flattened DFG clarifies that Pick I1 and Pick I2 are distinct. Payment-flattened DFG preserves M1 and M2 separately. OC-DFG frequencies decrease for duplicate Pick and Issue edges. ET–OT weights remain semantically stable: Capture PaymentPayment remains 2; Payment SummaryPayment remains 0. OTG relations retain Pack detail and ERP summary as separate states. Apparent rework decreases but does not disappear unless object-flattened views are used. Lifecycle and performance measurements are more stable because original timestamps are preserved and only two strong duplicates are removed.

**Evidence-based merge: 14 events, 37 E2O relations.**  
Order-flattened DFG removes PackPack by merging e07 into e06. Item-flattened DFG is unchanged from conservative. Payment-flattened DFG is unchanged from conservative. OC-DFG loses the WMS Pack  ERP Pack-summary edge and replaces it with a single Pack event carrying merged attributes. ET–OT weights for PackPackage may remain similar, but source-specific event-type weights change. OTG relations collapse the Package lifecycle state from detailed pack to ERP-acknowledged pack. Apparent rework is lower, but system propagation is hidden. Lifecycle and performance measurements hide WMS-to-ERP latency.

**Aggressive guarded PM4Py merge: 14 events, 36 E2O relations.**  
This variant merges e03/e04, e11/e16, and e08/e09 while protecting e05/e14 by requiring identical object sets. Order-flattened DFG removes DispatchDispatch but collapses WMS release and carrier acceptance. Item-flattened DFG remains protected. Payment-flattened DFG remains protected. OC-DFG loses the WMS Dispatch  Carrier Accept edge. ET–OT weights for DispatchDelivery may remain, but the carrier acceptance event type disappears. OTG relations collapse the Package/Delivery transition from warehouse release to carrier acceptance. Apparent rework decreases, but a real cross-system transition is lost. Lifecycle and performance measurements hide warehouse-to-carrier handoff latency.

If the unguarded aggressive library merge is used, expected count is 10 events and 28 E2O relations. It drops e05 and e14, collapses Pick I1/I2, collapses Capture M1/M2, and makes Payment-flattened DFG show one Capture event with two Payment objects.

Concrete edges or patterns whose interpretation changes:

1. **Pick Item(e03)  Pick Item(e04)**: technical/cross-system duplicate in raw; removed in conservative.
2. **Pick Item(I1)  Pick Item(I2)**: legitimate concurrent picks; must not be interpreted as rework.
3. **Pack Package(e06)  Pack Package(e07)**: WMS detail to ERP summary; not rework if labels are refined.
4. **Dispatch Package(e08)  Dispatch Package(e09)**: WMS release to carrier acceptance; not rework, but easily collapsed.
5. **Carrier Accept(e09)  Handover to Carrier(e10)**: true carrier sequence; disappears if e09 is merged into e08.
6. **Capture Payment(e13)  Capture Payment(e14)**: concurrent M1/M2 payments; not evidence that M1 caused M2.
7. **Issue Invoice(e11)  Issue Invoice(e16)**: cross-system duplicate; not invoice reissue.
8. **Capture Payment(e13/e14)  Payment Summary(e15)**: settlement propagation; merging e15 into one capture loses invoice-level summary.

## 8. Audit trail and reversibility

Provenance schema:

| Field | Purpose |
|---|---|
| `canonical_event_id` | Stable ID of the retained event |
| `source_event_ids` | All raw eids/source keys merged into the canonical event |
| `source_event_keys` | Original system keys, e.g., ER-100, W-77 |
| `merge_rule` | Rule name, e.g., `same_physical_scan`, `same_invoice_issuance` |
| `rule_version` | Version of the cleaning rule set |
| `reviewer_or_auto` | Human reviewer or automated rule identifier |
| `original_activity` | Activity label before harmonization or refinement |
| `refined_activity` | Final activity label used in analysis |
| `original_timestamp` | Business timestamp preserved unchanged |
| `adjusted_timestamp_or_order_key` | Deterministic ordering artifact, if any |
| `attributes_by_source` | Which attributes came from which source |
| `discarded_conflicts` | Conflicting attribute values and resolution reason |
| `confidence` | High/medium/low confidence in the decision |
| `reason` | Human-readable justification |

An analyst can reconstruct the raw view by treating the raw OCEL as immutable. For each canonical event, the analyst joins `source_event_ids` back to the raw event table. If a merge occurred, the canonical event is split into its original source events, restoring original labels, timestamps, attributes, and object relations. If a technical duplicate was dropped, the dropped raw row is restored. Refined labels are replaced by `original_activity`. The deterministic `order_key` and derived timedelta columns are removed, leaving the original business timestamps and source order only.

## 9. Failure modes and safeguards

| Failure mode | Safeguard |
|---|---|
| Collapsing distinct partial payments e13/e14 | Require Payment-object equality or explicit reconciliation key; validate Payment-flattened DFG |
| Converting abstraction-level updates into false rework | Retain summary events with refined labels; mark derived edges separately |
| Ordering by ingestion time | Exclude `ingested_at` from `order_key`; use only for late-arrival diagnostics |
| Treating shared objects as proof of duplication | Shared objects trigger candidate review only; merge requires business key or reconciliation evidence |
| Unioning incompatible E2O relations | Do not union Payment objects into e15; preserve object-type compatibility and source authority |
| Changing durations through synthetic microseconds | Preserve original timestamps; store synthetic order as `order_key`, not as business timestamp |
| Losing source-authoritative attributes | Use attribute authority matrix; store all source values and discarded conflicts |
| Applying duplicate functions to whole OCEL without inspection | Run candidate-group pre-check, dry-run, validation, and quarantine before merge/drop |
| Canonical ID bias | Canonical ID is an artifact; provenance must allow reconstruction of all source events |
| Misusing `source_seq` across systems | Use `source_seq` only within the same source and only as fallback or weak evidence |
