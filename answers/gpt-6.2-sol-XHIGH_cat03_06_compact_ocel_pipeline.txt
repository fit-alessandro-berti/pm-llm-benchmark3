## 1. Modeling assumptions

- The six object types are `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Each object ID identifies one object across the entire log. All event timestamps are UTC.
- E2O qualifiers name the object's role in the event. For Orders they are `created_order`, `receiving_order`, `involved_order`, `billed_order`, and `closed_order`. For Items they are `added_item`, `reserved_item`, and `packed_item`. The remaining roles are `packed_package`, `dispatched_package`, `dispatch_delivery`, `confirmed_delivery`, `issued_invoice`, `credited_invoice`, and `recorded_payment`.
- O2O goes from the subject to the object of the qualifier. The directions are Order → Item for contains, Package → Item for packs, Delivery → Package for carries, Invoice → Order for bills, and Payment → Invoice for partially settles. Both payments receive `partially_settles`. A total of 250 was recorded, and the invoice balance is unspecified.
- The base E2O table records the participants stated for each event. Reservation E06 and P1 packing E07 each directly link both Orders and both affected Items. P2 packing E08 directly links P2 and I2. Dispatch links a Package and a Delivery, and confirmation links a Delivery. Invoice issue links V1 and both Orders, and payment recording links V1 and the individual Payment. The business paths from P2 packing, dispatch, confirmation, and payments to Orders remain available through O2O.
- Broader E2O coverage makes downstream context visible in an Order trace and changes its directly-follows counts. If that context is needed, derive it in a separate analysis copy and label each added link with its origin, traversal path, and a derived qualifier. The pipeline below runs all discoveries on the base E2O table. The O2O table retains business direction and roles.
- The pipeline targets a PM4Py build that exposes the requested functions at the top level and accepts the stated OCEL constructor. The construction call is isolated. For a version that exposes O2O through a different parameter or a supported field on the OCEL instance, adapt that construction point and supply the same four tables. The flattened DataFrames use PM4Py's standard case, activity, and timestamp columns.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

EID = "ocel:eid"
ACTIVITY = "ocel:activity"
TIMESTAMP = "ocel:timestamp"
OID = "ocel:oid"
OTYPE = "ocel:type"
OID_2 = "ocel:oid_2"
QUALIFIER = "ocel:qualifier"

events = pd.DataFrame(
    [
        ("E01", "Create Order",      "2026-04-06T08:00:00Z", None),
        ("E02", "Add Item",          "2026-04-06T08:05:00Z", None),
        ("E03", "Add Item",          "2026-04-06T08:06:00Z", None),
        ("E04", "Create Order",      "2026-04-06T08:10:00Z", None),
        ("E05", "Add Item",          "2026-04-06T08:12:00Z", None),
        ("E06", "Reserve Stock",     "2026-04-06T08:30:00Z", None),
        ("E07", "Pack Package",      "2026-04-06T09:00:00Z", None),
        ("E08", "Pack Package",      "2026-04-06T09:05:00Z", None),
        ("E09", "Dispatch Package", "2026-04-06T10:00:00Z", None),
        ("E10", "Dispatch Package", "2026-04-06T10:15:00Z", None),
        ("E11", "Issue Invoice",    "2026-04-06T11:00:00Z", None),
        ("E12", "Record Payment",   "2026-04-06T11:30:00Z", 100),
        ("E13", "Confirm Delivery", "2026-04-06T13:00:00Z", None),
        ("E14", "Confirm Delivery", "2026-04-07T09:00:00Z", None),
        ("E15", "Record Payment",   "2026-04-07T10:00:00Z", 150),
        ("E16", "Close Order",       "2026-04-07T10:30:00Z", None),
        ("E17", "Close Order",       "2026-04-07T10:35:00Z", None),
    ],
    columns=[EID, ACTIVITY, TIMESTAMP, "amount"],
)
events[TIMESTAMP] = pd.to_datetime(events[TIMESTAMP], utc=True)
events["amount"] = events["amount"].astype("Int64")

objects = pd.DataFrame(
    [
        ("O100", "Order"),
        ("O200", "Order"),
        ("I1", "Item"),
        ("I2", "Item"),
        ("I3", "Item"),
        ("P1", "Package"),
        ("P2", "Package"),
        ("D1", "Delivery"),
        ("D2", "Delivery"),
        ("V1", "Invoice"),
        ("M1", "Payment"),
        ("M2", "Payment"),
    ],
    columns=[OID, OTYPE],
)

participants = {
    "E01": [("O100", "created_order")],
    "E02": [("O100", "receiving_order"), ("I1", "added_item")],
    "E03": [("O100", "receiving_order"), ("I2", "added_item")],
    "E04": [("O200", "created_order")],
    "E05": [("O200", "receiving_order"), ("I3", "added_item")],
    "E06": [
        ("I1", "reserved_item"),
        ("I3", "reserved_item"),
        ("O100", "involved_order"),
        ("O200", "involved_order"),
    ],
    "E07": [
        ("P1", "packed_package"),
        ("I1", "packed_item"),
        ("I3", "packed_item"),
        ("O100", "involved_order"),
        ("O200", "involved_order"),
    ],
    "E08": [("P2", "packed_package"), ("I2", "packed_item")],
    "E09": [("P1", "dispatched_package"), ("D1", "dispatch_delivery")],
    "E10": [("P2", "dispatched_package"), ("D2", "dispatch_delivery")],
    "E11": [
        ("V1", "issued_invoice"),
        ("O100", "billed_order"),
        ("O200", "billed_order"),
    ],
    "E12": [("M1", "recorded_payment"), ("V1", "credited_invoice")],
    "E13": [("D1", "confirmed_delivery")],
    "E14": [("D2", "confirmed_delivery")],
    "E15": [("M2", "recorded_payment"), ("V1", "credited_invoice")],
    "E16": [("O200", "closed_order")],
    "E17": [("O100", "closed_order")],
}
event_object_links = pd.DataFrame(
    [
        (event_id, object_id, qualifier)
        for event_id, links in participants.items()
        for object_id, qualifier in links
    ],
    columns=[EID, OID, QUALIFIER],
)
relations = (
    event_object_links.merge(
        events[[EID, ACTIVITY, TIMESTAMP]], on=EID, how="left",
        validate="many_to_one",
    )
    .merge(objects, on=OID, how="left", validate="many_to_one")
    [[EID, ACTIVITY, TIMESTAMP, OID, OTYPE, QUALIFIER]]
)

o2o = pd.DataFrame(
    [
        ("O100", "I1", "contains"),
        ("O100", "I2", "contains"),
        ("O200", "I3", "contains"),
        ("P1", "I1", "packs"),
        ("P1", "I3", "packs"),
        ("P2", "I2", "packs"),
        ("D1", "P1", "carries"),
        ("D2", "P2", "carries"),
        ("V1", "O100", "bills"),
        ("V1", "O200", "bills"),
        ("M1", "V1", "partially_settles"),
        ("M2", "V1", "partially_settles"),
    ],
    columns=[OID, OID_2, QUALIFIER],
)

assert len(events) == 17 and len(objects) == 12
assert events[EID].notna().all() and events[EID].is_unique
assert objects[OID].notna().all() and objects[OID].is_unique
assert events[ACTIVITY].notna().all() and objects[OTYPE].notna().all()
assert events[TIMESTAMP].notna().all() and events[TIMESTAMP].dt.tz is not None

assert relations[EID].isin(events[EID]).all()
assert relations[OID].isin(objects[OID]).all()
assert events[EID].isin(relations[EID]).all()
assert o2o[OID].isin(objects[OID]).all()
assert o2o[OID_2].isin(objects[OID]).all()
assert relations[QUALIFIER].notna().all() and o2o[QUALIFIER].notna().all()

event_lookup = events.set_index(EID)
for column in (ACTIVITY, TIMESTAMP):
    pd.testing.assert_series_equal(
        relations[column], relations[EID].map(event_lookup[column]),
        check_names=False,
    )
pd.testing.assert_series_equal(
    relations[OTYPE], relations[OID].map(objects.set_index(OID)[OTYPE]),
    check_names=False,
)
assert not relations.duplicated().any()
assert not relations.duplicated([EID, OID]).any()  # One role per pair here.
assert not o2o.duplicated().any()

# PM4Py OCEL construction point.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)
print(events[ACTIVITY].value_counts().sort_index())
print(objects[OTYPE].value_counts().sort_index())
print(pm4py.ocel_get_object_types(ocel))
print(pm4py.ocel_object_type_activities(ocel))

flat_logs = {}
dfgs = {}
log_skeletons = {}
for object_type in ("Order", "Package", "Delivery", "Invoice"):
    flat_log = pm4py.ocel_flattening(ocel, object_type)
    flat_logs[object_type] = flat_log
    dfgs[object_type] = pm4py.discover_dfg(flat_log)  # Edges, starts, ends.
    log_skeletons[object_type] = pm4py.discover_log_skeleton(flat_log)

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocpn = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

```

## 4. Expected flattened behavior

| Flattening | Case | Chronological event IDs |
|---|---|---|
| Order | O100 | E01 → E02 → E03 → E06 → E07 → E11 → E17 |
| Order | O200 | E04 → E05 → E06 → E07 → E11 → E16 |
| Package | P1 | E07 → E09 |
| Package | P2 | E08 → E10 |
| Delivery | D1 | E09 → E13 |
| Delivery | D2 | E10 → E14 |
| Invoice | V1 | E11 → E12 → E15 |

- **Order.** There are 13 flattened rows for 10 distinct source events. E06, E07, and E11 each appear once for O100 and once for O200. Create Order → Add Item, Add Item → Reserve Stock, Reserve Stock → Pack Package, Pack Package → Issue Invoice, and Issue Invoice → Close Order each have frequency 2. Add Item → Add Item has frequency 1 because O100 contains I1 and I2. The Order view omits P2 packing, both dispatches, delivery confirmations, and payment records. Its Issue Invoice → Close Order edge is case-level adjacency, so reading it as immediate closure after billing would hide intervening work. Counting the shared rows as independent operations would overcount reservations, P1 packing, and invoice issuance.
- **Package.** Both cases give Pack Package → Dispatch Package, for frequency 2. Each event enters only one Package case. The trace signatures are identical even though P1 combines Items from both Orders and P2 contains only I2. The view omits upstream Order and Item work and downstream delivery confirmation. Ending at dispatch describes the projection's boundary. The corresponding deliveries have separate confirmation events.
- **Delivery.** Both cases give Dispatch Package → Confirm Delivery, for frequency 2. Each dispatch belongs to one Delivery case. E09 and E10 also appear in the separate Package projection. The view omits packing, item membership, Order creation and closure, invoicing, and payments. The identical activity sequences could obscure a substantial difference in elapsed time. D1 confirms after 3 hours, and D2 after 22 hours 45 minutes.
- **Invoice.** The single case gives Issue Invoice → Record Payment → Record Payment, with both edges occurring once. E11 appears once in this case and also appears in both Order cases. E12 and E15 are two distinct payments. The view omits Order closure and fulfillment, and the repeated payment activity cannot establish how amounts were assigned to Orders or whether the invoice balance reached zero.

The log skeletons describe the observed traces. For example, both Order cases have a Create Order before Close Order and show one or two occurrences of Add Item. The Package and Delivery skeletons each see two copies of the same activity sequence across their respective cases, and the Invoice skeleton sees a count of two payments in one case. This sample supports descriptions of the observed behavior. Business rules for future cases require additional evidence.

Flattening on **Payment** gives two one-event cases, M1 with E12 and M2 with E15. Record Payment is both the start and end activity, and the DFG has no directly-follows edges. That projection loses the ordered sequence on V1 that links invoice issuance and both payment records.

## 5. Expected object-centric structures

- **OC-DFG.** Directly-follows evidence is organized by object type. Reserve Stock → Pack Package is supported by the same event pair (E06, E07) on two Orders and on two Items. This yields two object-specific successions within each type and one distinct event pair. I2 instead follows Add Item → Pack Package. Package succession connects packing to dispatch on P1 and P2, and Delivery succession connects dispatch to confirmation on D1 and D2. V1 supports Record Payment → Record Payment, while M1 and M2 each contribute a single Payment occurrence.
- **OTG.** The discovered Object Type Graph aggregates object interactions and observed lifecycle relationships by type. Co-participation connects Order–Item, Order–Package, Item–Package, Package–Delivery, Order–Invoice, and Invoice–Payment, with same-type Order–Order and Item–Item interactions as well. The Order–Package interaction has weight 2 because E07 connects P1 with both O100 and O200. The Order–Order interaction has weight 1 because the same pair shares E06, E07, and E11. The graph also shows Invoice → Payment as a descendant relation because each payment first appears in an event shared with the already active V1. The directed settlement facts are Payment → Invoice in O2O.
- **ET–OT graph.** The event-type to object-type graph weights participation by E2O row counts. Pack Package has 2 Package links, 3 Item links, and 2 Order links, with both Order links on E07. Issue Invoice has 1 Invoice link and 2 Order links, all on E11. Record Payment has 2 links to each of the Payment and Invoice types, coming from one Payment and one Invoice on each payment event.
- **Object-centric Petri net.** Inspect the type-specific flows around shared activities. Pack Package can connect the Package and Item flows with Order involvement observed for P1. Dispatch Package links Package and Delivery behavior. Issue Invoice connects the Orders' progression to V1's observed start, and Record Payment connects Invoice behavior to the separate Payment lifecycles. The tested build marks multiple-object participation for Order at Reserve Stock, Pack Package, and Issue Invoice, and for Item at Reserve Stock and Pack Package. Interpret those markings against individual occurrences. E07 has two Orders and E08 has zero. Per-type discovery and synchronization can generalize these sparse traces in several ways.
- **Object-interactions summary.** Shared-event evidence includes P1 meeting I1, I3, O100, and O200 on E07, the two Orders meeting V1 on E11, and V1 meeting M1 on E12 and M2 on E15. The two payments share an invoice through separate events. The summary reports both orientations of each co-event object pair, giving 54 rows in this example. Group by event and unordered pair when counting each pair once per event.

## 6. Modeling alternatives

| E2O policy | Example change and discovery effect |
|---|---|
| Source-minimal foreign keys | In a system that records Reservation against Items, Packing against Package and Items, and Invoice Issue against V1, retain only those links for the three activities. The shared Order context can be recovered through the Item and invoice O2O links. Order flattening would show creation, item addition, and closure, with Add Item → Close Order in both traces. OC-DFG and ET–OT would lose direct Order participation at these three activities. |
| Curated operational involvement | Add O100 to P2 packing. For dispatch and confirmation, link the relevant Package, its Items, and the Orders served by those Items, using role-specific qualifiers. D1 activity then enters both Order traces, and D2 activity enters O100's trace. Fulfillment appears before and after invoice issue in the Order DFG, and shared logistics events contribute to both cases. Package traces gain Dispatch Package → Confirm Delivery. |
| O2O-propagated analytical relations | Starting with the base log, follow the directed Invoice → Order `bills` edge from the invoice credited by each payment event. Give the resulting Order links a derived qualifier and retain their path. Both Order traces then gain Issue Invoice → Record Payment → Record Payment → Close Order. The resulting Order payment counts measure invoice context per Order, while the event table still records two payments totaling 250. |

## 7. Failure modes

1. **Relation inflation.** Traversing the whole connected component would spread events through the shared invoice and package. It could attach D2 confirmation to O200, whose only Item is in P1.
2. **Missing direct E2O links.** Dropping O200 from the base E06 or E07 removes a stated participant from the Order flattening and Order OC-DFG. O2O membership alone does not add the missing event to those views.
3. **Propagation interpreted as observation.** A derived Order link on E12 says that the event credits an invoice that bills the Order. Treating it as a captured Order transaction overstates the source evidence.
4. **Duplicate counts after flattening.** Counting E06, E07, or E11 in the Order projection counts two case appearances per event. Use the source event IDs for operation-level counts. DFG frequency counts case-level succession.
5. **Ambiguous payment allocation.** Assigning 100 to O100 and 150 to O200, or splitting either amount between them, requires allocation data. Summing a propagated amount over the two Order cases would count 500 for 250 in recorded payments.
6. **Overly short Payment traces.** The two singleton cases can suggest a trivial process if read on their own. V1's trace carries the billing and installment sequence.
7. **Constructor or API version mismatch.** An incompatible release can reject the O2O argument or lack a named discovery function. Check the build's signatures and constructor support. An OCEL constructed without O2O would lose the directed business relationships.
8. **Artificial ordering of ties.** These 17 timestamps are distinct. In a larger log, sorting two simultaneous events by row position or lexical ID creates a deterministic order with potentially artificial DFG edges. Use a trusted source sequence if available and disclose the ordering policy otherwise.
9. **Broken relational integrity.** Orphan IDs, duplicate E2O rows, or stale copies of event metadata can alter counts or chronology. The joins and assertions check references, uniqueness, activities, types, and timestamps.
10. **Overgeneralization from sparse traces.** Two matching Package traces and one Invoice trace give little evidence of mandatory transitions or fixed multiplicities. Treat the skeleton and net as discoveries from this sample.

## 8. Final semantic checks

- The event table contains E01 through E17 exactly once, with UTC timestamps and the stated activity counts. Every E2O row repeats the matching event activity and timestamp and uses the referenced object's type.
- There are 12 objects, 34 E2O rows, and 12 O2O rows. Each E2O pair is unique under this role policy, and every reference resolves.
- O100 contains I1 and I2, and O200 contains I3. The joins through Items show P1 serving O100 and O200 and P2 serving O100 alone.
- E06 links exactly I1, I3, O100, and O200. E07 links the same four objects plus P1. E08 links P2 and I2.
- D1 carries P1, with E09 at dispatch and E13 at confirmation on April 6. D2 carries P2, with E10 at dispatch on April 6 and E14 at confirmation on April 7.
- E11 issues one invoice, V1, and links both billed Orders. V1 has two outgoing `bills` links.
- E12 links M1 and V1 with amount 100, and E15 links M2 and V1 with amount 150. Amounts appear on those two event rows alone. Both directed settlement edges end at V1.
- E16 closes only O200 at 10:30 UTC on April 7, and E17 closes only O100 at 10:35 UTC. Both occur after the second payment and both delivery confirmations.
