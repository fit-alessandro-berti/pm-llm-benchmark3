# 1. Model scope and state variables

The twin should represent the municipal permit operation from portal submission through permit/rejection, including applicant and third-party delays, review decisions, rework, calendar effects, and the handoff of related cases. Its purpose is comparative planning under uncertainty. It is not a causal proof that an intervention will work, nor a substitute for safety, legal, or equity review.

Use a discrete-event simulation with event times in calendar time and work performed only when the responsible resource is available. Simulate at least the case level and the shared-work level: cases compete for municipal queues, while architect cohorts, neighborhood objection episodes, and inspection batches create dependencies across cases. Keep human service time separate from queueing, nonworking-calendar time, and external response time.

**Entities and state**

- **Permit case:** ID; type; district; architect; value/area where available; submission time; applicable review flags; prior-violation status; neighborhood or objection-group identifier if available; current activity/state; activity entry and service start/end times; assigned resource; review outcomes; rework count and reason; inspection readiness/no-show status; decision; and completion time. Preserve “unknown” separately from “no” for attributes such as violations, area, environmental sensitivity, and objection status.
- **Applicant/architect cohort:** architect ID, related submissions and their times, document response behavior, and (for D7) appointment-slot choice. Do not assume every application by an architect is related; represent observed or probabilistic links.
- **Neighborhood/objection episode:** shared district/area or project grouping, latent objection state and timing, affected cases, and public-notice extension. This is latent where the log has no objection event; it must not be presented as observed data.
- **Inspection batch:** district/route, eligible cases, planned visit date, batch size, travel time, readiness, no-shows, and the wait incurred by cases held for batching.
- **Municipal resource and queue:** resource pool, skills/case eligibility, shift and exception calendar, work-in-progress, queue priority, task duration, and planned absences/capacity reservations. Pools include clerks, planners (including the simple-case restriction), fire reviewers, environmental reviewers (net of non-permit duties), inspectors, and legal officers. System activities have effectively unlimited capacity.

Represent the process as a conditional, partly parallel workflow. Completeness and review rework are loops; fire, environmental, legal, and public-notice steps are conditional; applicable reviews and inspection are prerequisites for decision drafting. The decision outcome and rework transitions depend on case attributes and prior results. Model applicant document response, appeal, and readiness as external processes rather than municipal work. Public-notice minimum duration is calendar time; extensions are driven by a latent objection process and the council calendar where applicable.

At minimum, state includes simulation date; seasonal/day/hour arrival intensity; open-case backlog by state and age; current shared-resource availability; calendar exceptions; architect-level submission history; district-level inspection queue and route; and neighborhood-level latent objection state. Carry open cases and their state across simulation boundaries. Record every simulated activity start/end and state transition so the same process-mining summaries used for the observed log can be calculated from simulated runs.

# 2. Parameter-estimation plan

Use the full 18-month event log plus its extraction-window boundaries, HR-derived calendars, routing rules, and targeted data-quality review. The two-case excerpt illustrates structure, not a sufficient estimation sample. Preserve case attributes and timestamps during cleaning; deduplicate only with documented rules. Check event order, missing IDs, timestamp anomalies, case completion/censoring, and changes in logging practice. Use a time-based training/holdout split and stratify summaries by case type, district, season, and known routing flags where sample size permits.

**PM4Py handling.** Load the CSV with pandas, then call `pm4py.format_dataframe` with the actual case ID, activity, and timestamp columns. Convert the formatted frame to an event log when using log APIs. Use PM4Py to inspect variants, discover a directly-follows graph (DFG), and compute performance DFG summaries; use these as descriptive and conformance aids, not as the simulation engine or as proof of causal dependencies. A flattened trace imposes an order on concurrent work, so validate inferred concurrency and dependencies against routing knowledge. The supplied process tree is a compact structural sketch. It does not fully encode attribute-based routing, resource assignment, external response, objection effects, or the exact rework triggers. Parse it if supported, document parse limitations, and implement these rules explicitly in the simulator.

**Arrivals.** Estimate case arrivals from Submit application events using the known observation window, not merely the first-to-last case span if the extraction boundaries are available. Fit a non-homogeneous arrival process with hour-of-day, weekday, month/season, district, and case-type effects. Reconcile fitted relative effects with the reported 1.7x peak-season rate and Monday-to-Wednesday 2.2x ratio. Model bursts from frequent architects with a clustered or cohort-conditioned component (for example, architect-specific propensity and correlated weekly submissions), rather than treating every case as independent. Bootstrap weeks or seasons to quantify uncertainty and preserve the observed case mix and clustering.

**Service and waiting.** For activities with lifecycle start and completion records, calculate service duration from each activity's own start/end and waiting from its start minus the previous prerequisite completion or queue-entry time. With completion-only records, timestamps identify elapsed time between logged events but cannot identify the current activity's service time or its queue time. Do not label inter-event elapsed time as service. Use the empirical service summaries as priors/initial estimates, and estimate remaining splits through targeted time studies, system audit logs, or explicit resource/queue reconstruction. Fit distributions by activity and relevant case/resource/district strata when supported; compare empirical resampling with plausible positive distributions (for example, lognormal or gamma). Preserve observed medians and tails rather than fitting one average to all cases. Public-notice minimums and work calendars need explicit deterministic/calendar components, not a generic service-time fit.

**Routing and rework.** Derive observed branch rates from completed, sufficiently mature cases, conditional on case type, flags, district, value/area, prior outcome, and process history. Use known rules as constraints: required fire/environmental review and public notice should not be inferred solely from event absence when the relevant fields are incomplete. Estimate conditional branch/rework probabilities with shrinkage or hierarchical models for sparse segments; carry uncertainty forward. Audit unstructured rework text with a coded sample and report inter-rater agreement. Use repeat visits, loops, appeals, and outcomes to estimate rework frequency and path-specific costs. Missing emergency cases and censored/in-flight cases need sensitivity adjustments.

**Resources and cross-case effects.** Treat HR calendars as the initial capacity schedule and reconcile them with observed starts/completions and known leave/meeting exceptions. Estimate task eligibility and resource allocation from event resource labels, but avoid treating the observed assignment policy as optimal. Calibrate queueing and utilization jointly against wait distributions and backlog. Estimate applicant-response distributions separately from municipal service using request-to-receipt intervals, conditioned on case type, architect, and number/type of missing items; use heavy-tail methods and account for right-censoring. Estimate inspection travel/no-show and batching effects from route/district and visit data if available. Estimate architect and district/neighborhood clustering from linked cases; where links or objections are absent, run alternate dependency scenarios rather than claiming a point estimate.

# 3. Assumptions

These are starting assumptions to be tested and replaced as better evidence becomes available.

- **Arrivals:** Arrivals follow a calendar-dependent, non-homogeneous process. Weekday and seasonal effects persist over a planning horizon unless a stress scenario changes them. Architect propensity creates within-week correlated bursts; the 31% top-20 share is a calibration target, not a claim that future shares are fixed.
- **Service times:** Municipal task durations are positive and activity-specific, with case/resource/district effects where evidence supports them. Empirical service medians and p90s are calibration targets. Completion-only records do not reveal service duration; initial splits from elapsed time must be treated as uncertain and tested. The public-notice minimum is calendar time, not reviewer labor.
- **Routing:** Known conditional rules take precedence over missing event evidence. A missing review event is not automatically proof that review was unnecessary. Incomplete threshold, sensitivity, and violation attributes are represented as unknown and explored through plausible route probabilities.
- **Resources/calendars:** Staff work only in their stated shifts and eligible pools; non-permit time, part-time availability, public holidays, council meeting weeks, and field-visit days reduce capacity. Calendars are applied in local operating time with explicit time-zone and holiday conventions. Unplanned absence is added only if supported or as a sensitivity factor.
- **Rework:** Rework probability depends on activity, case type, observed outcome, and other supported predictors. Uncoded reasons are not treated as a single cause. Appeals and applicant corrections consume their own external time and may generate further municipal work.
- **Applicant/third-party response:** Applicant and consultant response are separate, potentially heavy-tailed processes, not municipal service. Document-checker effects on both error probability and applicant effort are uncertain and are varied in experiments. No response is not silently converted into immediate response.
- **Cross-case dependencies:** Cases can share architect behavior, neighborhood objection shocks, and district-level inspection routes. Linkage is probabilistic when identifiers are inadequate. Batch savings come with a modeled wait-for-batch cost; related cases do not become one case or lose individual outcomes.
- **Non-stationary demand:** The reported seasonal and weekday multipliers are initial constraints. The model preserves calendar seasonality over its horizon and tests a sustained peak and changes in mix. Do not extrapolate an 18-month seasonal pattern as certain long-run demand.
- **Missing data:** Objections, activity starts, some routing attributes, rework reasons, and rare emergencies are missing or biased. Treat unobserved values as latent/uncertain and run alternative plausible specifications. Correct for censoring where possible; do not infer that absent cases/events never occurred.

# 4. Experiment matrix

Run all policies against the same baseline demand scenarios and use paired random streams where possible. For each intervention, document its operational rule, implementation lag, uptake, eligibility, staffing/capacity, and any induced applicant or staff behavior. The expected trade-offs below are hypotheses, not results.

| Run | Factors and levels | Expected trade-offs to measure |
|---|---|---|
| B0 Baseline | Current routing, capacity, calendars, and batching; fitted demand | Reference for duration, queues, cost/capacity, fairness, and backlog. |
| D1 Document checker | Off/on; vary uptake and reduction in missing-document probability, with applicant effort time | Fewer correction loops and clerk touches may shorten cases; pre-submission effort or abandonment may rise. |

Use a staged design: first run baseline and single-policy comparisons; then screen combinations and stress cases; then run a small factorial or response-surface design on the most influential uncertain factors (uptake, eligibility error, batch window, arrivals, and capacity). Include implementation cost and staff hours in the comparison. Where a policy requires a legal or safety prerequisite, report that as a feasibility gate, not as a tunable performance score.

# 5. Warm-up, replications, and uncertainty treatment

This is a seasonal, finite-horizon service system, so do not discard a conventional arbitrary warm-up and pretend the remaining model starts empty. Prefer initializing each run from an observed snapshot of open cases, queue positions, completed work, and calendar state at the chosen start date. If that is unavailable, replay at least one prior seasonal cycle to build a plausible backlog, then score a separate evaluation period; test sensitivity to the initialization. Preserve cases still open at the end and continue a run-out period long enough to estimate their completion outcomes. A 24-month evaluation horizon captures two annual cycles; report monthly and seasonal results as well as the full-horizon summary.

Start with at least 100 independent replications per scenario, then increase the count adaptively until the 95% interval for key paired policy differences is narrow enough for the decision thresholds (for example, relative half-width below 5% for mean backlog and a decision-useful absolute width for p90 duration). Record and publish random seeds. Use common random numbers for paired policy comparisons, with separate streams for arrivals, service requirements, applicant delays, routing/objection events, and resource absences. Ensure policy branches do not accidentally shift unrelated random draws.

Report point estimates and 95% confidence intervals for mean measures and paired differences. Use replication-level or cluster bootstrap intervals for medians, p90/p95, SLA fractions, and fairness gaps; resample at the week/architect/neighborhood level where that is the dependence unit. Propagate parameter uncertainty as well as process randomness: draw uncertain routing probabilities, missing-start service splits, objection rates, and response-time tails from calibrated ranges/posteriors across outer-loop runs. Label Monte Carlo intervals separately from parameter uncertainty intervals.

Heavy-tailed response, notice, rework, and complex-case durations require special care. Use empirical resampling with tail-aware bootstrapping or compare several plausible tail distributions; account for right censoring and do not truncate outliers simply to improve fit. Report p90 and p95 with uncertainty, examine exceedance probabilities and maximum/backlog measures, and include tail-parameter sensitivity. Use enough replications to stabilize tails, and show when intervals remain too wide for a confident ranking.

# 6. Validation strategy

- **Face validation:** Walk through representative simple, new residential, commercial, and complex-variance cases with clerks, reviewers, inspectors, legal officers, and applicants where possible. Check paths, eligibility, dependencies, calendars, rework triggers, batching, and policy implementation with operational owners. Review rare exceptions separately.
- **Event-log replay validation:** Replay observed arrivals, case attributes, and (where available) observed route/branch outcomes to check timestamp ordering and state transitions. Compare a replay model with unconstrained simulation: the former checks implementation, while it does not independently validate counterfactual behavior. Reconcile duplicate, missing, censored, and emergency-case handling.
- **Distributional validation:** On held-out periods, compare activity/variant frequencies, route shares, case-type and district cycle-time distributions, activity elapsed-time distributions, interarrival patterns, response-time tails, rework counts, and completion/censoring rates. Compare medians, p90/p95, and empirical CDFs, not only averages. Where starts are absent, validate elapsed-time distributions and mark service/wait splits as weakly identified.
- **Resource-utilization validation:** Compare simulated working hours, utilization by pool and calendar period, queue lengths, overtime/idle periods, and cases handled per FTE with HR calendars and observed resource labels. Reconcile the environmental 40% non-permit reservation and fire-reviewer weekday availability. A model that matches durations by silently allowing off-calendar work fails validation.
- **Bottleneck validation:** Check predicted queues and wait contributions against observed wait summaries and staff explanations. Verify known pressure points: Monday completeness spikes, planning waits, specialized review queues, district travel, legal meeting interruptions, and objection-linked notice tails. Perturb capacity or arrivals and confirm changes are directionally plausible, then look for bottleneck migration.
- **Out-of-sample validation:** Fit/calibrate on an earlier period and evaluate on later months that include different seasonal demand. Also hold out architects/districts where possible to test generalization beyond repeated cohorts. Validate outcomes and backlog trajectories by case type. Recalibrate only with a documented version change; retain the previous specification and its forecast error.

Maintain a validation report with observed-versus-simulated plots/tables, acceptance tolerances set with the municipality, known failures, and uncertainty. A model that matches historical summaries is not automatically validated for a policy that changes applicant behavior, compliance, or staff priorities.

# 7. Decision criteria

Set final service-level targets and acceptable trade-offs with the municipality, applicants, and legal/safety owners before ranking. Use the following as an initial decision rule for screening, not as claimed statutory standards.

- **Duration:** Report median, p90, and p95 end-to-end calendar duration by case type, district, and intervention eligibility; also decompose municipal queue/service, calendar closure, and external response time. Prefer a policy only if its paired 95% interval supports a practically meaningful benefit, initially at least a 10% or 2-calendar-day median reduction for the intended segment, while p90 does not worsen by more than 5% or 3 days in any protected segment without an accepted reason.
- **SLA compliance:** Define target days by case type with stakeholders and report fraction completed within target and confidence intervals. Screen out policies that reduce compliance by more than 2 percentage points in any case type or district unless an explicit, approved trade-off applies. Show simple and complex cases separately; aggregate SLA can mask harm.
- **Fairness:** Track median and p90 by district, case type, architect-cohort size, and relevant applicant groups if lawful and available. Set a guardrail such as no district median increasing by more than 10% and no widening of the worst-to-best district p90 gap by more than 5 days. Check appointment access, checker effort, and missing-attribute error rates for disparate burdens. Do not equate architect volume with applicant deservingness.
- **Resources and cost:** Report utilization, overtime, travel hours, service hours, cost, and queue age by pool. As an initial operational range, sustained utilization around 80–85% may be manageable; investigate periods above 90% with growing queues and below 50% for dedicated capacity. Calendar and skill constraints mean a single average utilization threshold is not decisive. Include temporary staffing and implementation costs.
- **Rework and safety:** Report missing-document loops, review/inspection rework, appeals, reversals, no-shows, and any safety/compliance proxy. D2 and D8 require hard feasibility gates on eligibility/classification quality and legally required checks; a duration gain cannot compensate for unsafe or unlawful bypass. Track checker-induced applicant burden and false alerts for D9.
- **Backlog and robustness:** Measure open cases by age/state, arrivals versus completions, peak queue, and time to return to baseline after a shock. Reject a policy whose backlog grows persistently under baseline demand or fails to recover within a locally agreed period after stress. Require the sign of the intended benefit to hold in a clear majority of plausible parameter draws (for example, at least 80%) and no unacceptable tail or fairness harm in the stress scenarios.

Choose a Pareto-efficient set of feasible policies across duration, equity, cost/capacity, rework/safety, and robustness. If alternatives trade off, present those trade-offs and uncertainty for decision-makers; do not declare an exact optimum from uncalibrated or weakly identified counterfactuals.

# 8. Python skeleton

The following is a data/model-handling scaffold, not a calibrated simulator. It uses pandas for CSV ingestion and `pm4py.format_dataframe` with the conventional case/activity/timestamp keys. PM4Py summaries are kept separate from the simulation interfaces. Event timestamps in the excerpt are completions; therefore the code calculates inter-event elapsed time, but leaves service and queue waiting unknown unless an activity start timestamp is supplied.

def prepare_log(raw: pd.DataFrame):
    raw = raw.copy()
    raw[TIMESTAMP] = pd.to_datetime(raw[TIMESTAMP], utc=True)
    # PM4Py normalizes/sets the conventional log attributes and sorts events.
    formatted = pm4py.format_dataframe(
        raw,
        case_id=CASE,
        activity_key=ACTIVITY,
        timestamp_key=TIMESTAMP,
    )
    event_log = pm4py.convert_to_event_log(formatted)
    return formatted, event_log


PROCESS_TREE = """
->(
  'Submit application',

    ->(
      'Completeness check',

def pm4py_diagnostics(event_log):
    # These describe the observed flattened log; they do not encode all
    # attribute-driven routing or cross-case dependencies.
    variants = pm4py.get_variants(event_log)
    dfg, start_activities, end_activities = pm4py.discover_dfg(event_log)
    performance_dfg, perf_starts, perf_ends = pm4py.discover_performance_dfg(
        event_log,
        activity_key=ACTIVITY,
        timestamp_key=TIMESTAMP,
        case_id_key=CASE,
    )
    try:
        process_tree = pm4py.parse_process_tree(PROCESS_TREE)
        tree_note = "Parsed sketch; validate its semantics against explicit routing rules."
    except Exception as exc:
        # Parser grammar/version differences are possible. The string also
        # omits data-dependent gates and is not sufficient as executable policy.
        process_tree = None
        tree_note = f"Tree parse unavailable ({exc}); use explicit simulator routing."

    return {
        "variants": variants,
        "dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
        "performance_dfg": performance_dfg,
        "performance_starts": perf_starts,
        "performance_ends": perf_ends,
        "process_tree": process_tree,
        "tree_note": tree_note,
    }


def add_observed_timing_columns(events: pd.DataFrame) -> pd.DataFrame:
    """Derive only what timestamps identify; do not call gaps service time."""
    out = events.sort_values([CASE, TIMESTAMP]).copy()
    previous_completion = out.groupby(CASE)[TIMESTAMP].shift(1)
    out["elapsed_from_previous_completion_hours"] = (
        out[TIMESTAMP] - previous_completion
    ).dt.total_seconds() / 3600.0
    out["service_hours"] = np.nan
    out["waiting_hours"] = np.nan

    if "start_timestamp" in out.columns:
        out["start_timestamp"] = pd.to_datetime(out["start_timestamp"], utc=True)
        out["service_hours"] = (
            out[TIMESTAMP] - out["start_timestamp"]
        ).dt.total_seconds() / 3600.0
        out["waiting_hours"] = (
            out["start_timestamp"] - previous_completion
        ).dt.total_seconds() / 3600.0
        # First event in a case has no preceding completion; its queue entry
        # must come from a separately defined arrival or queue-entry time.
    return out


def arrival_summary(events: pd.DataFrame,
                    observation_start: Optional[pd.Timestamp] = None,
                    observation_end: Optional[pd.Timestamp] = None) -> dict[str, float]:
    submits = events.loc[events[ACTIVITY].eq("Submit application"), TIMESTAMP]
    submits = pd.to_datetime(submits, utc=True).sort_values()
    mean_interarrival_days = submits.diff().dt.total_seconds().mean() / 86400.0
    result = {
        "n_submissions": float(len(submits)),
        "mean_interarrival_days": float(mean_interarrival_days),
        "rate_from_interarrivals_per_day": (
            float(1.0 / mean_interarrival_days)
            if mean_interarrival_days and mean_interarrival_days > 0 else np.nan
        ),
    }
    if observation_start is not None and observation_end is not None:
        window_days = (
            pd.Timestamp(observation_end) - pd.Timestamp(observation_start)
        ).total_seconds() / 86400.0
        result["rate_per_day_in_extraction_window"] = (
            len(submits) / window_days if window_days > 0 else np.nan
        )
    # For the 18-month log, pass extraction boundaries; do not estimate its
    # rate from this tiny excerpt or from event-completion endpoints.
    return result

class ExperimentRunner:
    def __init__(self, parameter_draws, calendars, initial_state):
        self.parameter_draws = parameter_draws
        self.calendars = calendars
        self.initial_state = initial_state

    def run(self, experiment_matrix, seeds):
        results = []
        for experiment in experiment_matrix:
            for seed in seeds:  # pair the same seed across policy comparisons
                config = TwinConfig(
                    start=experiment["start"],
                    end=experiment["end"],
                    policy=experiment["policy"],
                    seed=seed,
                )
                twin = DigitalTwin(config, self.parameter_draws, self.calendars)
                simulated_log = twin.run(self.initial_state)
                results.append((experiment["name"], seed, simulated_log))
        return results
