Here’s a structured design addressing the business question while avoiding misleading outcome estimates. The primary target focuses on **default risk among activated accounts**, with explicit handling of selection effects and censoring. Alternative formulations are provided for context.

---

## 1. Target Definition
### **Primary Target**
- **Prediction Target**: Probability of 90-day default *among accounts that are eventually activated*.
  - Defined as `P(default_90d = 1 | activated, observed_prefix)`.
  - **Prediction Time**: Time of the last event before `Account Activated` (or a fixed prefix length, e.g., 5 events).
  - **Horizon**: 90 days post-activation.
  - **Unit of Analysis**: Activated accounts (cases with `Account Activated` event).
  - **Population**: All applications started between 1/1/2024–12/31/2025, with activation occurring before 12/31/2025.
  - **Estimand**: Causal risk of default *conditional on activation*, not unconditional risk across all applications.

### **Alternative Targets**
1. **Multi-State Target (All Applications)**
   - Predicts 4 outcomes: `default`, `non-default`, `withdrawn`, `rejected`.
   - **Question**: "What is the probability of each outcome given the observed prefix?"
   - **Limitation**: Requires strong assumptions about counterfactual default risk for non-activated cases (e.g., rejected applicants may have higher unobserved risk).

2. **Time-to-Default with Right Censoring**
   - Models time from activation to default, censoring at 90 days or data-extraction date.
   - **Question**: "What is the survival probability of avoiding default by day 90?"
   - **Limitation**: Ignores selection into activation; assumes censored cases are comparable to observed defaults.

3. **Policy-Specific Counterfactual**
   - Estimates `P(default_90d | activated, prefix)` *as if* all applications were activated (e.g., via inverse probability weighting).
   - **Question**: "What would the default rate be if the activation policy were relaxed?"
   - **Limitation**: Requires modeling activation policy and untestable assumptions about unobserved defaults.

**Why Primary Target?**
- Operationally defensible: Default is only observable post-activation.
- Avoids counterfactual assumptions about non-activated cases.
- Aligns with business request ("early warning for activated accounts").

---

## 2. Cohort Construction
### **Inclusion/Exclusion Rules**
- **Included**:
  - Applications started 1/1/2024–12/31/2025.
  - **Activated accounts**: Cases with `Account Activated` event before 12/31/2025 *and* `default_90d` known by 2/15/2026.
  - **Censored activated accounts**: Cases with `Account Activated` before 12/31/2025 but `default_90d` still missing (label not yet mature).
  - **Non-activated cases**: Rejected/withdrawn/transferred/open cases (excluded from primary target but tracked for sensitivity analysis).

- **Excluded**:
  - Applications started after 12/31/2025 (future data).
  - Cases with `Account Activated` after 12/31/2025 (no 90-day horizon by extraction).

### **Cohort-Flow Table**

| Activated (labeled)          | 21,600 | 18,900 non-default, 2,700 default                                      |

## 3. Censoring and Missing-Label Strategy
### **Types of Missingness**
1. **Right Censoring**:
   - Activated accounts with `default_90d` missing due to delayed feed (3,600 cases).
   - **Strategy**: Treat as censored at 90 days post-activation (survival analysis).
2. **Delayed Labels**:
   - `default_90d` arrives 7–35 days after horizon (e.g., 125–129 days post-activation).
   - **Strategy**: Use `label_available_at` to exclude future events from prefix features.
3. **Selection Through Activation**:
   - Default risk is only observable for activated cases.
   - **Strategy**: Primary target is conditional on activation; sensitivity analysis compares activated vs. non-activated prefixes.
4. **Transfer as Competing Event**:
   - Transferred cases may have missing outcomes (40% unlinked).
   - **Strategy**: Exclude from primary cohort; flag as "competing risk" in sensitivity analysis.
5. **Permanently Missing Feeds**:
   - Partner-originated accounts with no outcome feed.
   - **Strategy**: Exclude from primary cohort; document as "unobserved" in limitations.

### **Primary Analysis Strategy**
- **Survival Analysis (Cox Proportional Hazards)**:
  - Model time-to-default for activated accounts, censoring at 90 days or label availability.
  - **Assumptions**:
    - Censoring is independent of default risk (testable via Kaplan-Meier curves).
    - Activation policy is stable (testable via pre/post-policy change splits).

### **Sensitivity Analysis**
1. **Inverse Probability Weighting (IPW)**:
   - Weight activated cases by inverse probability of activation (requires modeling activation policy).
   - **Assumption**: Unobserved defaults for non-activated cases are comparable to observed defaults.
2. **Competing Risks Model**:
   - Treat rejection/withdrawal as competing events; estimate subdistribution hazard.
   - **Assumption**: Default risk for non-activated cases is ignorable (strong).
3. **Stratified Analysis**:
   - Compare default rates by activation status, prefix length, and policy period.

**Testable Assumptions**:
- Censoring independence (via survival curves).
- Policy stability (via pre/post-1/7/2025 splits).
**Partially Testable**:
- Activation policy (via prefix features predicting activation).
**Untestable**:
- Counterfactual default risk for non-activated cases.

## 4. Prefix Extraction
### **Rules**
1. **Fixed Event-Count Prefix**:
   - Use last `N` events before `Account Activated` (e.g., `N=5`).
   - **Handling Repeated Loops**: Collapse consecutive `Credit Review`  `Document Request` cycles into a single "document loop" event.
   - **Activity Renaming**: Map renamed activities (post-10/15/2025) to original names using a lookup table.
2. **Elapsed-Time Prefix**:
   - Use all events up to `T` days before activation (e.g., `T=7` days).
   - **Short Cases**: Pad with `NULL` events if prefix length is insufficient.
3. **Future Event Exclusion**:
   - Exclude events after `Account Activated` (including `Contract Signed`, `Collections Contact`).
   - **Label Availability**: Ensure no events after `label_available_at` are included.

### **PM4Py Implementation**
```python

        "prefix_length": 5,  # Last 5 events before activation

# Collapse document loops (example: merge consecutive Credit Review + Document Request)
def collapse_loops(trace):
    i = 0
    while i < len(trace) - 1:
        if (trace[i]["activity"] == "Credit Review" and
            trace[i+1]["activity"] == "Document Request"):
            trace[i]["activity"] = "Document Loop"
            del trace[i+1]
        else:
            i += 1
    return trace

prefixes = [collapse_loops(trace) for trace in prefixes]
```

## 6. Leakage Audit
| **Feature/Data Element**       | **Leakage/Bias Risk**                                                                 | **Valid Availability Rule**                                                                 | **Action**       | **Rationale**                                                                                     |
|--------------------------------|---------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|------------------|---------------------------------------------------------------------------------------------------|
| `final_limit`                  | Directly reveals credit decision (leaks future).                                      | Only available after `Accepted`/`Rejected` event.                                           | **Drop**         | Post-decision; cannot be known at prediction time.                                                |
| `decision_reason`              | May encode post-decision logic (e.g., "insufficient income").                          | Only available after `Credit Review` completes.                                             | **Drop**         | Future event; not available at prefix end.                                                       |
| `collection_status`            | Directly reveals default (leaks target).                                              | Only available after `Account Activated`.                                                   | **Drop**         | Post-activation; cannot be used for early warning.                                                |
| Future events (post-prefix)    | Any event after `Account Activated` or `label_available_at`.                          | Exclude all events after prefix end.                                                       | **Drop**         | Future leakage.                                                                                   |
| `documents_total` (nightly)   | May include documents uploaded after nominal prediction time.                          | Only use if `timestamp`  prediction time.                                                  | **Repair**       | Filter by time; otherwise drop.                                                                   |
| Updated `risk_score`           | Later updates may reflect post-decision adjustments.                                  | Use only `risk_score` from events  prediction time.                                       | **Repair**       | Freeze at prefix end.                                                                              |
| Resource experience            | Stored at extraction time, not event time.                                            | Use employee experience at event time (requires historical data).                           | **Repair**       | Current data is stale; must reconstruct historical experience.                                    |
| `label_available_at`           | Indicates when `default_90d` is known.                                               | Use to exclude future events from prefix.                                                  | **Keep**         | Needed to enforce temporal validity.                                                              |
| `source_system`                | May correlate with unobserved default risk (e.g., partner-originated accounts).       | Include as a feature (but document as proxy for missing data).                             | **Keep**         | Useful for subgroup analysis.                                                                    |

## 7. Validation Design
### **Temporal Split**
- **Train**: Applications started 1/1/2024–6/30/2025 (pre-policy change).
- **Validation**: Applications started 7/1/2025–9/30/2025 (post-policy change, pre-migration).
- **Test**: Applications started 10/1/2025–12/31/2025 (post-migration).
- **Label Maturity**: Exclude cases where `default_90d` arrives after test period.

### **Backtesting Scheme**
1. **Monthly Refit**:
   - Retrain model monthly on rolling 6-month window.
   - Evaluate on next 30 days of activated accounts.
2. **Policy Change Check**:
   - Compare performance pre/post-1/7/2025.
   - If performance drops, investigate feature drift (e.g., `risk_score` distribution).
3. **Label Maturity Check**:
   - Track proportion of censored cases in validation set.
   - If >20% censored, consider excluding or weighting by censoring probability.

### **Evaluation Metrics**
- **Primary**: Brier score (probability calibration) + AUC-ROC (discrimination).
- **Censoring-Aware**: Concordance index for survival models.
- **Subgroup**: Default rates by `source_system`, `policy_period`, and `requested_amount`.

### **Why Not Random Split?**
- Violates temporal independence (e.g., policy changes affect all cases).
- Mixes pre/post-migration data, obscuring system artifacts.

---

## 8. Limitations and Decision-Use Boundary
### **What the Study Can Claim**
- **Predictive Association**: The model identifies prefixes associated with higher/lower default risk *among activated accounts*.
- **Risk Stratification**: Can rank applications by predicted default probability at activation.

### **What It Cannot Claim**
- **Unconditional Default Risk**: Cannot estimate default risk for rejected/withdrawn cases without strong assumptions.
- **Causal Effect of Activation**: Cannot prove that relaxing activation would change default rates.
- **Generalizability to Future Policy**: Assumes activation policy and default mechanisms remain stable.

### **Deployment Risks**
1. **Policy Drift**: If credit thresholds change, prefix-default associations may shift.
2. **Label Lag**: Delayed feeds may require dynamic model updates.
3. **Activation Bias**: If the model is used to influence activation, it may induce selection bias.

## 9. PM4Py-Oriented Implementation Skeleton
```python
import pandas as pd
import pm4py
from pm4py.objects.log.util import dataframe_utils
from pm4py.objects.conversion.log import converter as log_converter
from pm4py.algo.discovery.alpha import algorithm as alpha_miner
from pm4py.objects.log.util import dataframe_utils
from pm4py.objects.log.importer.xes import importer as xes_importer
from datetime import datetime, timedelta

# --- Data Loading and Preprocessing ---
def load_and_preprocess_data(filepath):
    df = pd.read_csv(filepath, parse_dates=["time:timestamp"])
    df = df.rename(columns={
        "case:concept:name": "case_id",
        "concept:name": "activity",
        "time:timestamp": "timestamp"
    })
    return df

# --- Cohort Construction ---
def build_cohorts(df, cutoff_date="2025-12-31"):
    # Identify activated cases with known labels
    activated = df[df["activity"] == "Account Activated"]
    activated = activated[activated["case_id"].isin(
        df[df["default_90d"].notna()]["case_id"]
    )]
    activated = activated[activated["timestamp"] <= pd.to_datetime(cutoff_date)]

    # Identify censored activated cases (label not yet available)
    censored = df[df["activity"] == "Account Activated"]
    censored = censored[censored["case_id"].isin(
        df[df["default_90d"].isna()]["case_id"]
    )]
    censored = censored[censored["timestamp"] <= pd.to_datetime(cutoff_date)]

    # Non-activated cases (rejected/withdrawn/transferred/open)
    non_activated = df[~df["case_id"].isin(activated["case_id"].unique())]
    non_activated = non_activated[non_activated["timestamp"] <= pd.to_datetime(cutoff_date)]

    return {
        "activated": activated,
        "censored": censored,
        "non_activated": non_activated
    }

# --- Prefix Extraction ---
def extract_prefixes(df, case_id_col="case_id", activity_col="activity", timestamp_col="timestamp"):
    # Convert to PM4Py log
    log = log_converter.apply(
        df,
        case_id=case_id_col,
        activity_key=activity_col,
        timestamp_key=timestamp_col
    )

    # Get prefixes (last 5 events before activation)
    prefixes = pm4py.get_prefixes_from_log(
        log,
        parameters={
            "prefix_length": 5,
            "filter": lambda trace: "Account Activated" in trace
        }
    )

    # Collapse document loops
    def collapse_loops(trace):
        i = 0
        while i < len(trace) - 1:
            if (trace[i]["activity"] == "Credit Review" and
                trace[i+1]["activity"] == "Document Request"):
                trace[i]["activity"] = "Document Loop"
                del trace[i+1]
            else:
                i += 1
        return trace

    prefixes = [collapse_loops(trace) for trace in prefixes]
    return prefixes

# --- Leakage Audit ---
def audit_leakage(df, prefix_end_col="prefix_end_time"):
    leakage_risk = {
        "final_limit": {
            "risk": "High (post-decision)",
            "valid_rule": "Only use if timestamp <= prefix_end_time",
            "action": "Drop"
        },
        "decision_reason": {
            "risk": "High (post-decision)",
            "valid_rule": "Only use if timestamp <= prefix_end_time",
            "action": "Drop"
        },
        "collection_status": {
            "risk": "High (post-activation)",
            "valid_rule": "Never use",
            "action": "Drop"
        },
        "documents_total": {
            "risk": "Medium (nightly updates)",
            "valid_rule": "Only use if timestamp <= prefix_end_time",
            "action": "Repair (filter by time)"
        }
    }
    return leakage_risk

# --- Temporal Validation Split ---
def temporal_split(df, start_col="timestamp", train_end="2025-06-30", val_end="2025-09-30"):
    train = df[df[start_col] <= pd.to_datetime(train_end)]
    val = df[(df[start_col] > pd.to_datetime(train_end)) &
             (df[start_col] <= pd.to_datetime(val_end))]
    test = df[df[start_col] > pd.to_datetime(val_end)]
    return train, val, test

# --- Main Pipeline ---
if __name__ == "__main__":
    # Load data
    df = load_and_preprocess_data("applications_events.csv")

    # Build cohorts
    cohorts = build_cohorts(df)
    print("Cohort sizes:")
    print(f"Activated: {len(cohorts['activated'].drop_duplicates('case_id'))}")
    print(f"Censored: {len(cohorts['censored'].drop_duplicates('case_id'))}")
    print(f"Non-activated: {len(cohorts['non_activated'].drop_duplicates('case_id'))}")

    # Extract prefixes for activated cases
    prefixes = extract_prefixes(df)
    print(f"Extracted {len(prefixes)} prefixes.")

    # Leakage audit
    leakage_risk = audit_leakage(df)
    print("\nLeakage Audit:")
    for feature, details in leakage_risk.items():
        print(f"{feature}: {details['action']} ({details['risk']})")

    # Temporal split (example: split by case start time)
    train, val, test = temporal_split(df)
    print(f"\nTemporal split sizes:")
    print(f"Train: {len(train)} cases")
    print(f"Validation: {len(val)} cases")
    print(f"Test: {len(test)} cases")
```

### **Key Assumptions in Code**
1. **Prefix End Time**: Assumes `prefix_end_time` is derived from the last event before `Account Activated`.
2. **Document Loop Collapse**: Simplifies repeated `Credit Review`  `Document Request` cycles.
3. **Temporal Split**: Relies on `timestamp` column for case-level splits (not event-level).
4. **Leakage Handling**: Drops post-prefix columns entirely; in practice, may need to reconstruct historical `risk_score`.

### **Next Steps for Survival Modeling**
- Replace the prefix extraction with `pm4py.get_event_attributes` to extract features for survival models.
- Use `lifelines` or `scikit-survival` for censoring-aware modeling, linking to PM4Py features via `pandas` DataFrames.
