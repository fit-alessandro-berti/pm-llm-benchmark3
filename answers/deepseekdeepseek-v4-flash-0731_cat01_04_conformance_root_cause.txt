## 7. Provisional conclusion

The measured conformance collapse is primarily a compound data-provenance and model-versioning event, not evidence that employees suddenly became noncompliant. The sharp Jun-Jul drop from 93% to 32% fitting traces is largely explained by three artifacts: the UI label replacement `Classify`  `Risk Screen`, the new gateway-injected technical event `Queue Routed`, and the ETL change that caused `Notify` to appear before `Decision`. Each preprocessing step recovered fitness in a logical order: label mapping to 58%, technical-event removal to 81%, and source-sequence ordering to 89%. The manual audit confirming that sampled reversed events were actually decision-first supports the timestamp defect.

A separate real compliance concern remains. After preprocessing, about 11% of Jun-Jul and a larger share of Aug-Sep traces still contain unexplained moves. The August policy change introduced `Supervisor Sign-off` for high-value claims, and the normative model was not updated. Adding an optional sign-off branch raises Aug-Sep fitness from 66% to 86%, but it is too permissive because it allows sign-off for all cases, not only cases above EUR 50,000. Additionally, enhanced-review traces without `Compliance Check`—25 in Jun-Jul and 30 in Aug-Sep—have not been confirmed as true bypasses or missing events. These residuals could indicate either extraction failures or genuine noncompliance.

Confidence: high (80-85%) that the initial conformance collapse was caused by label, technical-event, and timestamp artifacts. Confidence that a real compliance problem persists is moderate-low (30-40%), because the evidence is unresolved and business outcomes are stable.

Immediate actions: IT should maintain a technical-event registry and map `Risk Screen` to `Classify` in the extraction layer; process owners should version the normative model immediately after any policy change; compliance should conduct a source-system audit of the missing compliance-check cases and review `Manual Override` usage. We must not claim that employees are noncompliant based only on alignment residuals, nor claim that the unchanged appeal rate proves no compliance problem exists.

## 8. Model-governance recommendation

1. **Model versioning**: Every policy change must trigger a formal normative-model version release, including a diff against the current model and an effective-date timestamp; conformance checking must always reference the model version valid for the event-log period.

2. **Event-semantic contract**: Define an explicit contract for each activity label: business meaning, UI label, source-system field, and expected actor; any UI rename or label change must be published with a mapping table before the new log data flows into conformance.

3. **Technical-event policy**: Create a separate registry for technical/system events such as `Queue Routed`; these events must carry a `category=technical` flag and be filtered or marked with a dedicated attribute before process-mining analysis.

4. **Timestamp provenance**: For every event, store both business time and ingestion time, plus a source sequence number; conformance and order analysis must use the business-time/source-sequence ordering unless a documented exception is approved.

5. **Data-aware constraints**: When process rules depend on case attributes, encode those rules as guards in the model or as separate conformance constraints; a control-flow-only extension that permits an activity for all cases is insufficient and will overgeneralize.

6. **Post-release validation**: After any UI, gateway, ETL, or policy release, run a small conformance test against a reference dataset using both the old and new model versions; compare DFGs and variant distributions before declaring the release production-safe.
