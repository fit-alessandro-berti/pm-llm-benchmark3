# 4. Network and Conformance Analyses

### **PM4Py Code Examples**

#### **Filter Four-Eyes Violations**
```python
import pm4py

# Load event log (assuming 'log' is a pandas DataFrame)
log = pm4py.format_dataframe(event_attribute_key="time:timestamp", case_attribute_key="case:concept:name", attributes={"org:resource": "resource", "lifecycle:transition": "activity"})

# Filter violations: same resource for Create PO and Approve PO
violations_create_po_approve_po = pm4py.filter_four_eyes_principle(
    log,
    ["Create Purchase Order", "Approve Purchase Order"],
    case_attribute_key="case:concept:name",
    resource_attribute_key="org:resource"
)
print(violations_create_po_approve_po)
```

#### **Discover Handover, Working-Together, and Subcontracting Networks**
```python
# Handover network (who hands off to whom)
handover_network = pm4py.discover_handover_of_work_network(log, case_attribute_key="case:concept:name", resource_attribute_key="org:resource")

# Working-together network (co-occurrence in same case)
working_network = pm4py.discover_working_together_network(log, case_attribute_key="case:concept:name", resource_attribute_key="org:resource")

# Subcontracting network (loops or repeated interactions)
subcontracting_network = pm4py.discover_subcontracting_network(log, case_attribute_key="case:concept:name", resource_attribute_key="org:resource")
```

#### **Compare Emergency vs. Non-Emergency Cases**

#### **Declarative Rule for Retrospective Justification**
```python
# Define rule: Emergency Override must be followed by Retrospective Justification by a different resource within 3 days
rule = pm4py.declare(
    log,
    [
        ("Emergency Override", "Retrospective Justification"),
        ("org:resource", "!=")  # Different resources
    ],
    case_attribute_key="case:concept:name",
    time_attribute_key="time:timestamp",
    max_time=3 * 86400  # 3 days
)
violations = pm4py.conformance_declare(log, rule)
```

**Internal Audit Report: Review of Procurement-to-Payment Event Log**
*Confidential – For Management Use Only*

**Objective**
This report assesses patterns in the procurement-to-payment event log for potential control exceptions, focusing on four-eyes violations, fast approvals, and vendor concentration. The analysis distinguishes between legitimate process variations (e.g., emergency handling) and potential data-quality or control risks.

**Key Findings**
1. **Control Exceptions**:
   - **Four-eyes violations** were detected in 42 cases where the same resource created and approved purchase orders (primarily Buyer_Carla/Approver_Gita and Buyer_Dan/Manager_Hugo). While 88% of these cases were flagged as emergencies, 18% lacked timely retrospective justifications by a different resource. Additionally, 17 same-resource retrospective justifications exhibited identical timestamps, raising data-quality concerns.
   - **Fast approvals** (median 8–10 minutes) for emergency cases involving Buyer_Carla and Buyer_Dan were consistent with documented emergency protocols. However, 16 cases involving VendorMaster_Lena and AP_Kim for vendor family V-77x combined fast approvals with manual process concentration (83% of cases), warranting further review.

2. **Informal Specialization**:
   - Buyer_Carla and Buyer_Dan demonstrate specialization in emergency medical supplies and facilities repairs, respectively, with approval patterns aligned to their roles. Approver_Gita and Manager_Hugo are delegated for urgent cases, and their involvement in subcontracting loops (e.g., GitaCarlaGita) appears to reflect emergency clarification rather than rubber-stamping.

3. **Data-Quality Issues**:
   - **Shared-account mapping**: The org:resource field for 23 emergency approvals shows Approver_Gita’s account, despite detailed audit trails indicating assistant involvement. This suggests legacy system errors.
   - **Source-system limitations**: Manual_upload cases (83% for V-77x) lack digital audit trails, and legacy_ERP mappings conflate bot and human approvers in 1800+ cases. These issues obscure true approval paths.

4. **Most Concerning Subgroup**:
   The **Buyer_Carla + Approver_Gita** cluster stands out due to:
   - High volume of four-eyes violations (42 cases),
   - Fast approvals (84 cases with 8-min median),
   - Subcontracting loops (36 cases),
   - Late retrospective justifications (18%),
   - Data-quality flags (shared-account issue, manual_upload concentration).

**Recommendations**
1. **Immediate Review**:
   - Audit the **12 retrospective justifications** with identical timestamps for substance and compliance with the three-day rule.
   - Verify **vendor contracts** for Buyer_Carla’s emergency suppliers to confirm pre-approved terms and authority for fast-track approvals.
   - Cross-check **access logs** for Approver_Gita’s shared account to reconcile entered_by vs. org:resource discrepancies.

2. **Process Improvements**:
   - Implement **automated alerts** for same-resource approvals and retrospective justification delays.
   - Address **data-quality gaps** by:
     - Resolving legacy_ERP mapping errors to distinguish bot and human approvers.
     - Standardizing manual_upload processes to include digital audit trails (e.g., timestamps, approver signatures).
   - Clarify **emergency protocols** to ensure retrospective justifications are entered by different resources within the required timeframe.

3. **Monitoring**:
   - Track **fast approvals** in routine pairs (Aline/Elena, Boris/Felix) to detect deviations from norms.
   - Monitor **subcontracting loops** for Buyer_Dan/Manager_Hugo and VendorMaster_Lena/AP_Kim to assess escalation patterns.

**Limitations**
This analysis relies on event log data, which may be incomplete due to:
- **Source-system limitations** (e.g., manual_upload lacks digital trails),
- **Mapping errors** (e.g., legacy_ERP conflates bot and human resources),
- **Retrospective justifications** entered in bulk after quarter close.
Physical documents (e.g., vendor contracts, approval forms) and access logs are essential for a complete assessment.
