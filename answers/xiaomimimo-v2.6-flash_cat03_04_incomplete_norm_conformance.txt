## 1. Conformance semantics

**Forbidden behavior** is a relation explicitly marked `forbidden` in the norm (closed-world). Any positive count is a violation regardless of count or rarity.

**Missing mandatory behavior** applies when a relation marked `mandatory` within its stated scope has a count below the expected maximum. Because the norm is closed-world only for mandatory columns, a shortfall is a violation candidate, but scope qualifiers (e.g., "externally shipped packages") and abstraction level (directly-follows vs. eventual) must be checked before confirming.

**Unexpected but unregulated behavior** covers any observed relation absent from all four status rows for that object/relation. Under the open-world assumption, absence from the norm means the norm offers no judgment; it is neither compliant nor non-compliant.

**Typical-pattern absence** applies when a `typical` relation shows partial coverage. The norm explicitly allows exceptions; a shortfall is noteworthy but not a violation unless the exception itself triggers a separate rule.

**Likely data-quality error** is assigned when contextual evidence (e.g., a suspect join on a reused identifier) suggests the observed edge does not faithfully represent the real-world situation.

**Abstraction mismatch** is assigned when a business rule that holds at the "eventually" level does not hold at the directly-follows level because the model is too coarse or too fine for the norm's phrasing.

**Insufficient evidence** is used when the summary alone cannot decide whether a gap is a process issue, a data issue, or an abstraction artifact.

**Open-world vs. closed-world:** The norm is closed-world only for `forbidden` relations and for `mandatory` columns within scope. Everything else — including `typical`, `unspecified`, and relations not listed at all — is open-world: absence or presence yields no automatic verdict. This prevents mislabeling unregulated edges (e.g., `Reopen Order -> Close Order`, `Package object_codeath Delivery`) as violations.

## 3. Detailed reasoning by model family

### OC-DFG

**Can establish:** Which directly-follows relations exist between activities on the same object type, their counts, and whether specific forbidden or mandatory pairs appear.

**Cannot establish:** Whether an "eventually" rule holds when intermediate activities intervene; whether a missing edge means the activity never happened or was merely not *directly* followed; whether scope qualifiers (e.g., "externally shipped") are correctly applied without external metadata.

**Counts and scope:** N1's 98/100 is a shortfall, but the additional context explicitly flags an abstraction concern — an unrecorded review event between create and validate would break direct succession while still satisfying the business rule. N4's 198/200 concerns *externally shipped* packages; if the 2 exceptions aren't external, the count could be 100%. N3's 2 violations are unaffected by abstraction because no lawful intermediate activity can follow cancellation before dispatch — the forbidden relation fires on *any* dispatch after cancel.

**Cross-abstraction concern:** The danger of interpreting an "eventually expected" rule as a directly-follows rule is that every legitimate intermediate activity (review, invoicing, fulfilment steps) produces a false positive. N1 says orders should "eventually enter validation," but the summary approximates this with direct succession. The 2 missing cases must be tested with multi-step traces before being called violations. Conversely, N3 (forbidden) is safe under direct succession but even *safer* under eventual semantics — forbidden relations must hold at all abstraction levels.

### OTG

**Can establish:** Which object types are connected by which relationship (interaction, co-birth, co-death) in the object type graph.

**Cannot establish:** Whether an edge should exist for a specific object instance, or whether an edge's absence is meaningful without scope information.

**Counts and scope:** T6 (forbidden co-birth of Order and Payment) has exactly 1 edge — a clear violation. T1 and T2 are present and mandatory-satisfied. T3 (typical Invoice-Payment) is present at weight 92, consistent with partial payment coverage in N5. The `Package object_codeath Delivery` edge (7) is entirely unregulated; co-death is not mentioned by any norm. Under open-world, it receives no verdict.

**Cross-abstraction concern:** An OTG edge being present doesn't mean every pair of those object types interact; it means the *type-level* graph has the edge. A forbidden OTG edge (T6) means the *type-level relationship* exists somewhere in the log, which is sufficient to flag it, though the count (1) tells us the scale.

### ET–OT

**Can establish:** Which object types are linked to which event types, with weights.

**Cannot establish:** Whether the link is semantically correct (the Sensor Heartbeat case shows why — a wrong join creates a technically present but semantically false edge).

**Counts and scope:** E2 (Add Item  Order) at 1448 vs. 1450 for Add Item  Item reveals 2 events with an incomplete object mapping. E6 (Dispatch Package  Delivery) at 198/200 aligns with the OC-DFG gap for N4, and the carrier-attribute context suggests the Delivery object exists but wasn't linked — a data-lineage issue. E8 (Record Payment  Invoice) at 92/93 involves the single unlabeled unapplied-cash event. E10 (Sensor Heartbeat  Invoice) at 1 is explicitly forbidden but suspected to be a DQ error — here, the norm violation and the DQ diagnosis coincide: either way, the edge must be removed or the process stopped.

**Cross-abstraction concern:** The same real-world situation can be conforming in OC-DFG but non-conforming in ET–OT (or vice versa). For example, the 2 orders missing `Create Order -> Validate Order` in OC-DFG might show both `Create OrderOrder` and `Validate OrderOrder` in ET–OT (E1 is satisfied), meaning the *object linkage* is fine but the *sequence* is questionable — or the abstraction is too strict.

def classify(raw_diag, norm_meta):
    """
    Walk raw PM4Py diagnostics, look up the status in norm_meta,
    and emit one of:
      FORBIDDEN_VIOLATION, MANDATORY_GAP, TYPICAL_DEVIATION,
      UNREGULATED, CONFORMING, NEEDS_INVESTIGATION
    Returns a new list; never mutates raw_diag.
    """
    classified = []
    for item in raw_diag:
        norm_id = item.get("norm_id")          # PM4Py may expose this
        status  = norm_meta.get(norm_id, {}).get("status", "unspecified")
        observed = item.get("observed", True)

            verdict = "UNREGULATED"

            verdict = "CONFORMING"

        classified.append({
            "norm_id": norm_id,
            "status":  status,
            "verdict": verdict,
            "raw":     item,                   # preserved for audit
        })
    return classified
