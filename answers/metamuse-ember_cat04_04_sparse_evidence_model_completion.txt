## Why both DFG directions do not prove concurrency

A DFG aggregates directly-follows information across cases and loses start times, durations, resources, and case-level context. The pair CE and EC can be produced by two sequential subprocesses used in different proportions, by two teams, by a completion race between concurrent activities, or by ingestion-order artefacts under S7. Thus, both directions are not sufficient evidence for concurrency. Conversely, genuinely concurrent activities could produce only one completion direction if one is systematically shorter, so both directions are not necessary evidence either. To establish overlap, lifecycle start and completion intervals for individual activity instances are required.

# 2. Shared Assumptions

- **Completion-order semantics.** Every candidate models the logged order of activity completions. It does not model starts, waiting time, duration, or resource use. A partial order in these models therefore means that completion orders are not constrained, not that the activities demonstrably overlapped.
- **Shared structural core.** A is first, both C and E occur before P, P precedes R, and R precedes Z. S and X, when present, occur before P. No candidate allows an activity to repeat, a loop, an abort path, or a missing P.
- **Missing Supplier Confirmation events.** If an S event occurred in the source process but was not exported, the underlying process trace and the logged trace differ. The candidates model the observable log language. Therefore, optional S means “S may be absent from the trace,” not “the process proved that S was unnecessary.”
- **Absent external/stocked attribute.** Because the attribute was not exported, none of the candidates can express “S is mandatory if external and optional if stocked.” S is represented by a free XOR choice between S and a silent skip. This is an explicit abstraction: it overgenerates for external cases, where S may be mandatory, and it cannot identify which observed S absences are stocked skips or logging failures.
- **Optionality representation.** In the POWL candidates, S? means XOR(S, tau), and X? means XOR(X, tau), where tau is a `SilentTransition`. Tau is not an observed event and does not represent a case ending.
- **No other hidden attributes are assumed.** Resources, priorities, component counts, check outcomes, and supplier identities are not available and are not encoded.
- **Independence and stability.** Cases are treated as independent traces from one broadly stable process. Apparent order variation is treated as process variation, not as concept drift, although drift cannot be excluded from these data.

# 3. Conservative Candidate

## Inductive bias

The conservative candidate adopts a near-closed-world inductive bias: only the seven observed completion orders are admitted, with no attempt to generalize to unseen interleavings, unseen combinations of optionality, or unseen positions of X. Its central trade-off is deliberately to sacrifice generalization in favour of precision on the observed sample and to make every novel trace a visible deviation. It is therefore an audit baseline rather than a plausible generative model of the underlying process, and a future case that differs in even one completion position will be rejected even if that difference is operationally legitimate.

## Formal expression

```text
model_conservative ::=
  XOR(
    SEQ(A,C,E,S,P,R,Z),
    SEQ(A,E,C,S,P,R,Z),
    SEQ(A,C,E,P,R,Z),
    SEQ(A,E,C,P,R,Z),
    SEQ(A,C,S,E,P,R,Z),
    SEQ(A,C,E,S,X,P,R,Z),
    SEQ(A,E,C,X,S,P,R,Z)
  )
```

Type: PM4Py ProcessTree.

## PM4Py code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(activity):
    return ProcessTree(activity=activity)

def sequence(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def xor(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

RO = "Register Order"
CC = "Credit Check"
ER = "Engineering Review"
SC = "Supplier Confirmation"
EX = "Expedite Review"
AP = "Approve Configuration"
RP = "Release Production"
END = "Archive Case"

variants = [
    (RO, CC, ER, SC, AP, RP, END),
    (RO, ER, CC, SC, AP, RP, END),
    (RO, CC, ER, AP, RP, END),
    (RO, ER, CC, AP, RP, END),
    (RO, CC, SC, ER, AP, RP, END),
    (RO, CC, ER, SC, EX, AP, RP, END),
    (RO, ER, CC, EX, SC, AP, RP, END),
]

model_conservative = xor(*[
    sequence(*[leaf(activity) for activity in variant])
    for variant in variants
])
```

## Behavior deliberately excluded

- Every complete trace other than the seven strings above.
- S before any principal check, S after P, repeated S, and S in any context other than V1, V2, V5, V6, or V7.
- X without S, X between a principal check and S other than the V7 context, and X in the V6 context with the C/E order reversed.
- E–S–C ordering, C–X–E ordering, or E–X–C ordering.
- Any change to A first, P before R, or R before Z.
- All future interleavings caused by duration variation, ingestion ties, corrected logs, or new component types.

## Known underfitting risks

- It will reject legitimate combinations formed by separately observed features, such as X without S or X after an S that occurs between C and E.
- Any newly observed interleaving of C, E, S, and X will be treated as nonconforming even if it follows the domain rules.
- It cannot represent a corrected or late-arriving S event without adding a new branch.
- With only two X cases, its X behaviour is especially brittle.

## Duplicate labels and scalability

The XOR enumeration intentionally repeats the same activity labels across sibling branches. ProcessTree representations normally favour unique labels, and PM4Py conversion may create duplicate-labelled transitions or, depending on version and converter behaviour, map or merge labels in ways that make reconciliation ambiguous. A converted net therefore needs empirical checking; it should not be assumed automatically to preserve exactly the seven-trace language. A deployment-grade conservative artifact could instead be represented as a POWL XOR of distinct sequence objects or as an explicit finite-language automaton. Enumeration is also poorly scalable: seven branches already require about fifty leaves for thirty cases, and the number of interleavings grows combinatorially as more orderings are observed.

# 4. Balanced Candidate

## Inductive bias

The balanced candidate generalizes by retaining the high- and medium-confidence precedence rules while treating contested orderings as partial orders rather than as hard sequences. It assumes the principal checks are both required before approval, S is conditionally or optionally present before approval, X is optional and follows both principal checks, and the relative completion order of activities that are not precedence-constrained is not informative about causality or overlap. To encode the low-to-medium-confidence rule that S follows at least one principal check, it uses a latent XOR between two partial orders: in one branch S follows C, and in the other S follows E. The branch is an abstraction for an OR-precedence, not a claim that the process explicitly selects a branch.

## Formal expression

```text
S? = XOR(S, tau)
X? = XOR(X, tau)

PO_balanced(first, second) =
  partial order on {first, second, S?, X?}
  with first  S?, first  X?, second  X?

model_balanced ::=
  A ; XOR(PO_balanced(C,E), PO_balanced(E,C)) ; P ; R ; Z
```

Type: PM4Py POWL, using a sequence containing an XOR of two `StrictPartialOrder` objects.

## PM4Py code

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

def optional(activity):
    return OperatorPOWL(
        operator=Operator.XOR,
        children=[Transition(label=activity), SilentTransition()],
    )

def balanced_branch(first_label, second_label):
    branch = StrictPartialOrder()
    first = Transition(label=first_label)
    second = Transition(label=second_label)
    supplier = optional("Supplier Confirmation")
    expedite = optional("Expedite Review")
    for node in (first, second, supplier, expedite):
        branch.order.add_node(node)
    branch.order.add_edge(first, supplier)
    branch.order.add_edge(first, expedite)
    branch.order.add_edge(second, expedite)
    return branch

middle = OperatorPOWL(
    operator=Operator.XOR,
    children=[
        balanced_branch("Credit Check", "Engineering Review"),
        balanced_branch("Engineering Review", "Credit Check"),
    ],
)

model_balanced = OperatorPOWL(
    operator=Operator.SEQUENCE,
    children=[
        Transition(label="Register Order"),
        middle,
        Transition(label="Approve Configuration"),
        Transition(label="Release Production"),
        Transition(label="Archive Case"),
    ],
)
```

## Decision between sequence, concurrency, and partial order

| Activity pair | Balanced decision | Justification and rejected alternative |
|---|---|---|
| C vs E | Partial order: incomparable | Both completion orders occur in 19 and 11 cases respectively. A CE sequence would reject the E-first traces and rely on S1, which is contradicted as a completion rule. A claim of actual overlap is not made because D7 and S7 do not provide start intervals. |
| C vs S | OR-precedence through XOR of two partial orders | V5 shows S completing after C and before E. A rule requiring S after both checks is therefore rejected. In one branch CS; in the other, C is incomparable with S. |
| E vs S | Symmetric OR-precedence | D5 is symmetric in the two principal checks, and V5 supports S after one check before the other. The symmetric E–S–C trace is unobserved but is the balanced generalization. |
| S vs X | Partial order: incomparable | V6 has S before X and V7 has X before S. Neither sequence is retained as a hard rule. |
| C vs X | Sequence: CX | D6 and S6 both require X after both principal checks, and both observed X traces complete after both C and E. |
| E vs X | Sequence: EX | Same evidence as CX. |
| Middle activities vs P | Sequence: all middle activities before P | D3 requires C and E before P; D4 places S before P; D6/S6 places X before P. |
| P vs R | Sequence: PR | D2 is high confidence and all 30 traces have P followed by R. |
| R vs Z | Sequence: RZ | All 30 traces end with R followed by Z, and D1 identifies Z as the end. |
| A vs middle activities | Sequence: A before the middle section | All traces start with A and D1 is high confidence. |

The POWL partial order is used as a compact representation of unconstrained completion order. It should not be read as proof that C and E, or S and X, were executed concurrently. For the completion-trace language, incomparability and an XOR of the two possible sequences are often observationally similar, but the partial order composes more naturally with optional S and X interleavings.

## Behavior deliberately excluded

- S completing before both C and E.
- X completing before either C or E has completed.
- S or X after P.
- Missing C or missing E.
- Repeated S or repeated X.
- R before P, Z before the end, or any activity after Z.

## Known underfitting risks

- If S can legitimately be initiated immediately after A, balanced will falsely reject early-S traces.
- If the X precondition applies to check starts rather than completions, balanced will falsely reject X completing between C and E.
- If X can occur more than once, or S can occur once per component rather than once per case, balanced will underfit.
- If a principal check is genuinely waived for some order type, balanced will underfit.

# 5. Permissive Candidate

## Inductive bias

The permissive candidate trusts only the strongest structural rules and treats the weaker ordering rules as soft hypotheses rather than hard constraints. It retains A first, both principal checks before P, all middle activities before P, and P before R before Z, but allows S anywhere in the middle section and weakens the X precondition from “after both checks” to “after at least one check.” It is intentionally an upper-bound exploration model: it is designed to reveal which future traces would be disputed under the balanced interpretation, not to endorse every trace it admits.

## Formal expression

```text
S? = XOR(S, tau)
X? = XOR(X, tau)

PO_permissive(first, second) =
  partial order on {first, second, S?, X?}
  with only first  X?

model_permissive ::=
  A ; XOR(PO_permissive(C,E), PO_permissive(E,C)) ; P ; R ; Z
```

Type: PM4Py POWL.

## PM4Py code

```python
        Transition(label="Archive Case"),
    ],
)
```

## Boundary between reasonable generalization and forbidden behavior

Inside the permissive boundary are all middle-section interleavings in which C and E both occur before P, S and X occur at most once before P, and X follows at least one principal check. This includes early S, X after only one completed check, and all S/X orderings not excluded by those constraints.

Outside the boundary remain: a trace not starting with A; a missing C, E, or P; C or E after P; S or X after P; X before both principal checks have completed; repeated middle activities; R before P; any activity after Z; and any new activity label. The boundary therefore still reflects D1–D4 and the broad before-P placement of X, while relaxing the contested D5 and the completion-based reading of D6.

## Behavior deliberately excluded

- X as the first middle activity before either principal check.
- S or X after P.
- Missing C, E, or P.
- Repeated S or X.
- R before P.
- Z not as the final activity.

## Known underfitting risks

- If supplier confirmation legitimately occurs after approval for some order types, permissive will underfit.
- If X can occur more than once, or S once per component, permissive will underfit.
- If a principal check can be waived, or release can occur without approval in an emergency path, permissive will underfit.
- Its underfitting risk is low for the observed label set, but that is achieved by accepting many potentially undesirable interleavings.

# 7. Comparative Model Matrix

|---|---|---|---|

# 8. Validation Code

The following code is self-contained. It reconstructs the log, rebuilds all three models, converts them to Petri nets, performs soundness and alignment-based metric calculations, performs bounded sampled playout, and evaluates a manually defined trace suite.

Important limitation: alignment fitness, precision alignments, token-based replay generalization, and sampled playout do not exhaustively decide language inclusion for general Petri nets. A trace with imperfect alignment is not thereby proved outside the language, and a finite playout sample cannot prove that one candidate’s language is included in another’s. If the conservative ProcessTree conversion merges duplicate labels, the suite may detect gross discrepancies but cannot prove that the net preserves exactly seven traces.

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

RO = "Register Order"
CC = "Credit Check"
ER = "Engineering Review"
SC = "Supplier Confirmation"
EX = "Expedite Review"
AP = "Approve Configuration"
RP = "Release Production"
END = "Archive Case"

def leaf(activity):
    return ProcessTree(activity=activity)

def sequence_tree(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def xor_tree(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

def optional(activity):
    return OperatorPOWL(
        operator=Operator.XOR,
        children=[Transition(label=activity), SilentTransition()],
    )

def balanced_branch(first_label, second_label):
    branch = StrictPartialOrder()
    first = Transition(label=first_label)
    second = Transition(label=second_label)
    supplier = optional(SC)
    expedite = optional(EX)
    for node in (first, second, supplier, expedite):
        branch.order.add_node(node)
    branch.order.add_edge(first, supplier)
    branch.order.add_edge(first, expedite)
    branch.order.add_edge(second, expedite)
    return branch

def permissive_branch(first_label, second_label):
    branch = StrictPartialOrder()
    first = Transition(label=first_label)
    second = Transition(label=second_label)
    supplier = optional(SC)
    expedite = optional(EX)
    for node in (first, second, supplier, expedite):
        branch.order.add_node(node)
    branch.order.add_edge(first, expedite)
    return branch

observed_variants = [
    (RO, CC, ER, SC, AP, RP, END),
    (RO, ER, CC, SC, AP, RP, END),
    (RO, CC, ER, AP, RP, END),
    (RO, ER, CC, AP, RP, END),
    (RO, CC, SC, ER, AP, RP, END),
    (RO, CC, ER, SC, EX, AP, RP, END),
    (RO, ER, CC, EX, SC, AP, RP, END),
]

model_conservative = xor_tree(*[
    sequence_tree(*[leaf(activity) for activity in variant])
    for variant in observed_variants
])

model_balanced = OperatorPOWL(
    operator=Operator.SEQUENCE,
    children=[
        Transition(label=RO),
        OperatorPOWL(
            operator=Operator.XOR,
            children=[
                balanced_branch(CC, ER),
                balanced_branch(ER, CC),
            ],
        ),
        Transition(label=AP),
        Transition(label=RP),
        Transition(label=END),
    ],
)
```

# 9. Recommendation and Data-Collection Plan

## Recommendation

Use **model_balanced** for immediate operational monitoring. It admits every observed trace, respects the high- and medium-confidence rules, represents S absence as an explicit abstraction, and avoids the false precision of treating contested stakeholder claims as hard sequences. It should initially be used as a conformance-monitoring and triage model, not as an automatic hard gate: early-S and early-X deviations should trigger review rather than automatic rejection, because D5 and the completion-based reading of D6 are not secure.

Use **model_permissive** for sensitivity analysis. For each new case, classify it as conforming to both balanced and permissive, conforming only to permissive, or conforming to neither. The middle category isolates exactly the disputed behaviour—early S or X after only one principal check—and should drive targeted data collection and stakeholder clarification. Retain **model_conservative** as a lower-bound novelty detector: a trace outside even the conservative language is definitionally new relative to the current sample, but novelty alone should not be equated with noncompliance.

## Data-collection plan

Collect a consecutive cohort rather than only selected examples, so prevalence estimates are not biased. Any targeted enrichment, such as collecting all X cases, should be analysed separately from prevalence.

| Data to collect | Concrete fields | Ambiguity resolved |
|---|---|---|
| Lifecycle intervals | Case ID, activity-instance ID, activity, start timestamp, completion timestamp, ingestion timestamp, source system, and actor/team | Distinguishes CE start sequence from overlap and completion race; distinguishes S start after one check from S completion after one check; tests whether X’s precondition concerns starts or completions. |
| Component and supplier requirement | Component ID, external/stocked/mixed status, supplier-required flag, reason, stock reservation, and supplier ID | Separates S3, S4, and S5; permits a conditional model in which external orders require S and stocked orders do not. |
| Supplier event reconciliation | Supplier-system event ID, integration batch ID, late-arriving flag, reconciliation status, and explicit “no supplier required” marker | Distinguishes a true skip from a missing S event; estimates missingness by supplier and component type instead of relying on absence. |
| Expedite decision data | Trigger timestamp, reason, requester, linked C and E result IDs, and linked S status at trigger time | Tests whether X is triggered after check starts, check completions, or supplier status, and whether S is actually a prerequisite. |
| Check and approval results | C result, E result, result timestamp, approver, approval decision, and release timestamp | Tests whether P is gated by results rather than merely by activity occurrence, and whether D2 is a genuine dependency. |
| Resource and team context | Team, role, queue, and work centre for each activity instance | Tests whether CE and EC completion orders come from different sequential subgroups rather than from concurrent work. |

## Maximally informative future evidence

| Future evidence | Hypotheses distinguished | Interpretive consequence |
|---|---|---|
| A E S C P R Z, with start and completion intervals | Symmetric OR-precedence for S versus C-specific precedence | Repeated occurrences support the balanced branch structure; systematic absence in E-first cases would support a C-specific rule. |
| A S C E P R Z or A S E C P R Z, with S start after A but S completion after a check | D5 applied at start versus D5 applied at completion | Completion order alone would be misleading; the start interval determines whether balanced is underfitting. |
| A S C E P R Z with S both starting and completing before either check | Balanced OR-precedence versus permissive early supplier contact | Repeated cases would falsify balanced as a true process model and support permissive for S. |
| A C X E P R Z or A E X C P R Z, with X start after one check | D6 as a completion precondition versus a start or partial-information precondition | Such cases would show that balanced must be relaxed for X, or that the logged completion order is not the relevant precondition. |
| A C E X P R Z | X independent of S versus X requiring S | Repeated cases support the balanced optional-S structure; absence would not by itself prove dependence because X is rare. |
| Known-external cases with no logged S, reconciled against the supplier system | S3 mandatory S versus S5 missing events | Source-system S events prove logging missingness; confirmed absence proves a compliance or process exception. |
| Known-stocked cases with an S event | S4 as a categorical skip versus S as sometimes used for stocked orders | Shows whether “stocked” is a deterministic skip condition or merely a tendency. |
| C and E lifecycle intervals that never overlap | S1 sequential starts versus S2 parallel work | Trace order cannot distinguish these hypotheses; intervals can. |
| C and E intervals that overlap with either completion order | Actual concurrency versus reversed sequential paths | Supports the engineering lead’s interpretation, though the completion-trace language may remain unchanged. |
| A C E P S R Z | D4, S before P | Any genuine occurrence falsifies the shared before-P placement and requires revision of all three candidates. |

Some hypotheses are observationally equivalent in completion traces. In particular, no completion trace can distinguish “C and E are concurrent” from “the process chooses either CE or EC,” because both generate the same two completion orders. Likewise, no trace can distinguish “S was skipped” from “S occurred but was not logged.” Lifecycle and attribute data are therefore more valuable than simply collecting more completion traces.

## Alternative interpretation that would change the recommendation

The most consequential alternative is that S absences are predominantly clustered logging failures rather than stocked skips. If supplier-system reconciliation showed that external and stocked cases alike almost always had an S event in the source system, then S3 would be closer to universal, S4 would be a mistaken generalization, and balanced optional S would be unsafe as a compliance model. In that case, the recommendation would change: balanced could remain a model of the observable log, but it should not be used for compliance until a conditional model is built with the external/stocked attribute and a separate missing-event mechanism. Deviations would be classified as logging defects or supplier-confirmation failures rather than legitimate skips. This alternative is plausible because the stated 5–10% missingness rate is approximate, may be clustered by supplier or integration batch, and cannot be assigned to individual cases from the current export.
