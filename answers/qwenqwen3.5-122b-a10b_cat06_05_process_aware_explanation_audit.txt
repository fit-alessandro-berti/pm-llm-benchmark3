## 2. Process-model consistency checks

To validate explanations and features against the normative process, the following validation suite is required:

1.  **Prefix-Time Availability Check:**
    *   **Method:** For every feature $f$, verify `feature_timestamp <= t0`.
    *   **Role:** Prevents temporal leakage (e.g., `total_case_duration`).
    *   **Limitation:** Relies on accurate metadata timestamps; does not detect logical impossibility.

2.  **Activity-Order Feasibility (Conformance Checking):**
    *   **Method:** Use **Alignments** or **Footprint Matrices** to check if a sequence pattern (e.g., `Claim Closed -> Damage Assessment`) exists in the process model.
    *   **Role:** Detects impossible sequences (e.g., Closed before Assessment).
    *   **Limitation:** A frequent edge in the DFG (Directly Follows Graph) does not imply a normative rule; it may indicate data noise or parallelism errors.

3.  **Same-Timestamp Ambiguity Resolution:**
    *   **Method:** Check event logs for `timestamp` equality. If `Claim Closed` and `Damage Assessment` share a timestamp, verify the `sequence_index`.
    *   **Role:** Resolves ordering uncertainty when clocks are coarse.
    *   **Limitation:** If `sequence_index` is missing (as in Case Z), the pattern is uninterpretable.

4.  **Complete-Trace vs. Prefix-Trace Filter:**
    *   **Method:** Flag features derived from `full_trace` (e.g., `variant_id`, `appeal_seen_anywhere`).
    *   **Role:** Ensures prediction models do not "see the future."
    *   **Limitation:** Requires strict separation of training data generation pipelines.

5.  **Semantic Legitimacy of Repeated Events:**
    *   **Method:** Verify if `Settlement Decision Recorded` occurs twice. Check if the second occurrence is linked to an `Appeal` event.
    *   **Role:** Ensures the model distinguishes between initial denial and appeal reconsideration.
    *   **Limitation:** Requires event log enrichment to link decisions to appeals.

6.  **Prefix-Only Recalculation:**
    *   **Method:** Re-run feature engineering logic on the truncated trace ending at $t_0$.
    *   **Role:** Confirms if the feature value changes when future events are hidden.
    *   **Limitation:** Computationally expensive for high-volume logs.

    *   **Priority:** Medium. Detects features that implicitly depend on future events (e.g., `variant_id`).

4.  **Process-Conformance Tests:**
    *   Integrate a process mining engine to validate sequence patterns. Reject any pattern that violates the normative process model (e.g., `Closed -> Assessment`).
    *   **Priority:** High. Prevents impossible explanations like Case Z.

5.  **Calibration After Feature Removal:**
    *   Retrain the model after removing leaked features (`total_case_duration`, `appeal_seen`). Monitor AUC and calibration drift.
    *   **Priority:** High. Ensures model performance does not collapse when leakage is removed.

6.  **Explanation Stability:**
    *   Monitor SHAP values over time. If feature importance shifts drastically after fixing lineage, investigate data drift.
    *   **Priority:** Medium. Ensures explanations remain consistent.

7.  **Proxy/Fairness Analysis:**
    *   Conduct bias audits on `claimant_region` and `claimant_channel`. If these features disproportionately impact protected groups, apply fairness constraints or remove them from individual explanations.
    *   **Priority:** Medium. Mitigates regulatory and reputational risk.

8.  **Monitoring for Schema or Process Drift:**
    *   Alert if new activity types appear in the log or if `queue_length` statistics shift (indicating system changes).
    *   **Priority:** Low. Maintains long-term model validity.
