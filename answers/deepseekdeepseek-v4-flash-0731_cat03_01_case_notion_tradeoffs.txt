## 1. Analytical assumptions

- **Case notion**: A case is a trace of events grouped by a single object of a chosen type, using the direct event-to-object (E2O) relations as given. Events are ordered by timestamp; each event is copied into the trace of every object of that type to which it is directly related.
- **Convergence**: The situation where a single event is directly related to multiple objects of the *same* type. When flattening on that type, the event is replicated into every corresponding case, causing duplication and potentially inflating activity frequencies.
- **Divergence**: The situation where a single object of the chosen type participates in multiple, logically independent subprocesses (e.g., an order split across two packages, or a delivery consolidating multiple packages). In a flattened trace, these subprocesses appear as a single sequential or parallel path, which may obscure independence.
- **Copied shared events**: I treat them as both (a) duplication, because they inflate counts and may create false dependencies, and (b) informative, because they reveal that the event is shared across multiple cases, which is a real characteristic of the process. However, the duplication must be explicitly accounted for in any analysis.
- **Analytical transformations**: I will not silently propagate relations through the objectobject graph. I will only use the direct E2O relations as they are given, unless I explicitly propose a derived relation (e.g., “ordertopackage via item”) and state its purpose. In the sensitivity plan, I will consider a propagatedrelation variant to test how it affects results.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs to still create** (with explicit caveats):
- **Order flattening**: Useful for highlevel order lifecycle queries (e.g., “How long does an order take from creation to close?”). However, it must be used with the understanding that shared events are duplicated and independent subprocesses are merged. It can safely answer questions about orderspecific attributes (e.g., which orders were closed late) but not about activity frequencies.
- **Item flattening**: Answers itemlevel logistics questions (e.g., “Which item was delayed in dispatch?”). It is safe for path analysis of individual items, but frequency counts for shared events are inflated.
- **Package flattening**: Answers packagelevel questions (e.g., “Which packages were consolidated?”). It is safe for package duration, but not for overall process.
- **Invoice flattening**: Answers financial questions (e.g., “How many payments did invoice V2 have?”). It is safe for invoicelevel payment schedules.

**Questions that require objectcentric approaches**:
- **Frequency of activities without duplication**: Use an OCDFG (objectcentric DFG) that counts each event once, regardless of how many objects are related.
- **Dependencies between independent subprocesses**: Use an OTG (objecttoobject graph) to see how orders, packages, and deliveries interact.
- **Time analysis across object types**: Use ETOT (eventtoobject graph) to trace how events relate to multiple objects over time.
- **Clustering of equivalent executions**: Use `pm4py.cluster_equivalent_ocel` to identify groups of orders that share similar patterns (e.g., orders that are split vs. not split) without forcing a single case notion.

**Reconciling contradictory findings**:
- If the orderflattened DFG shows a high frequency of `Dispatch`, but the OCDFG shows only one dispatch for the consolidated delivery, we should trust the OCDFG for frequency and use the orderflattened log only for orderspecific attributes.
- If the orderflattened log shows a sequential pattern (e11e12) for O1, but the object interaction summary shows that P1 and P2 are independent, we should treat the sequence as an artifact of flattening, not a real dependency.

## 5. Lead-object decision

I choose **C. Reject a single lead object for this process.**

**Decision criteria**:
- The process contains multiple, crosscutting object types with complex manytomany relationships (ordersitems, orderspackages, packagesdeliveries, ordersinvoices).
- No single object type provides a complete, distortionfree view of the entire process.
- The order object type is the most complete, but it suffers from severe duplication and merging of independent subprocesses.
- The other object types (item, package, delivery, invoice, payment) are too narrow or suffer from singleton lifecycles.

**Strongest supporting evidence**:
- Order O1 is split across two packages (P1, P2) and two deliveries (D1, D2). This creates a divergent trace where two independent flows are merged.
- Order O3 is involved in both P3 and P4, and also in a consolidated invoice V2. This leads to duplication of shared events and mixing of package and financial subprocesses.
- Payment flattening produces singleton traces, making it useless for process discovery.
- The objectinteraction graph (if computed) would show a dense network of relations, indicating that no single “lead” object can represent the whole process without losing crucial information.

**Strongest counterargument**:
- The order object is the natural business entity; an order is what the customer cares about, and it has a clear lifecycle from creation to close. One might argue that flattening on order, despite duplication, gives a reasonable overview, and the duplication can be corrected by weighting events (e.g., counting each event once per order, but adjusting for shared events). However, this would require a custom transformation that goes beyond simple flattening.

**Residual risk**:
- If we reject a single lead, we must rely on objectcentric techniques that are more complex and may require additional tooling. There is also a risk that analysts, used to traditional process mining, will find it difficult to interpret OCDFG or OTG results without a clear case notion.

**Conditions under which I would change my decision**:
- If the process were simplified (e.g., each order had exactly one item, one package, one delivery, one invoice, and one payment), then order flattening would be sufficient and a single lead would be defensible.
- If the analysis were limited to a specific subprocess (e.g., only package logistics), then package flattening would be appropriate.
- If we could eliminate duplication by using an eventdeduplication step (e.g., counting each event only once per unique combination of order and package), then order flattening might become viable.
