```python
# =============================================================================
# OCEL 2.0-style construction + PM4Py object-centric analysis pipeline
# Retail fulfillment micro-scenario: 2 orders, 3 items, 2 packages,
# 2 deliveries, 1 invoice, 2 payments.
#
# Self-contained: builds all tables in memory, no file/network access.
# Recommended environment: Python >= 3.9, pandas >= 1.5, pm4py >= 2.7.9
# =============================================================================

import sys
import pandas as pd
import pm4py

try:                                  # --- OCEL import, version-isolated -----
    from pm4py import OCEL            # pm4py >= 2.7 exposes OCEL top-level
except ImportError:                   # pragma: no cover -- legacy locations
    from pm4py.objects.ocel.obj import OCEL   # 2.3.x - 2.6.x


# -----------------------------------------------------------------------------
# A/B. Table builders ---------------------------------------------------------
# -----------------------------------------------------------------------------

TIMEZONE = "UTC"

def T(stamp: str) -> pd.Timestamp:
    """Build a timezone-aware timestamp."""
    return pd.Timestamp(stamp, tz=TIMEZONE)


_EVENT_ROWS: list[dict] = []          # staged events
_RELATION_ROWS: list[dict] = []       # staged E2O rows
_EVENTS_BY_EID: dict[str, dict] = {}  # fast lookup for denormalisation


def add_event(eid: str, activity: str, timestamp: str, **attrs) -> str:
    """Register one event; extra keyword arguments become event attributes."""
    if eid in _EVENTS_BY_EID:
        raise ValueError(f"duplicate event id {eid}")
    row = {"ocel:eid": eid, "ocel:activity": activity,
           "ocel:timestamp": T(timestamp)}
    row.update(attrs)                 # e.g. amount=... for payments
    _EVENT_ROWS.append(row)
    _EVENTS_BY_EID[eid] = row
    return eid


def relate(eid: str, oid: str, otype: str, qualifier: str,
           origin: str = "source") -> None:
    """
    Add one E2O relation row.  The row repeats the event's activity and
    timestamp verbatim (requirement D).  `origin` records whether the row is
    a source-system fact or an analytically propagated relation.
    """
    ev = _EVENTS_BY_EID[eid]
    _RELATION_ROWS.append({
        "ocel:eid": eid,
        "ocel:activity": ev["ocel:activity"],      # denormalised on purpose
        "ocel:timestamp": ev["ocel:timestamp"],    # denormalised on purpose
        "ocel:oid": oid,
        "ocel:type": otype,
        "ocel:qualifier": qualifier,
        "origin": origin,
    })
```

```python
def instantiate_ocel(events, objects, relations, o2o):
    """
    Single isolation point for PM4Py-version-dependent construction.

    pm4py >= 2.7 (OCEL 2.0-style): OCEL(events=..., objects=..., relations=..., o2o=...)
      * relations requires ocel:eid/activity/timestamp/oid/type(/qualifier)
    Older pm4py (<=2.6) exposes OCEL too but derives E2O differently; if your
    version chokes on the `o2o` argument or on the `ocel:qualifier` column:
        * drop `ocel:qualifier` from relations and `o2o` entirely -> OCEL 1.x style
        * or upgrade: pip install -U pm4py
    Semantics of the tables themselves never change.
    """
    return OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

ocel = instantiate_ocel(events, objects, relations, o2o)
```

## 1. Modeling assumptions

**Object types (exact capitalization, singular PascalCase)**

`Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment` — 12 object identifiers in total (O100, O200; I1–I3; P1, P2; D1, D2; V1; M1, M2).

**Event identification** — E01 … E17, in chronological narrative order, unique strings, all timestamps timezone-aware (`Asia/...` none — everything `UTC`).

**E2O qualifier vocabulary.** A qualifier states the *role/state change the event inflicts on that particular object*. Twenty-two terms in six families (used verbatim in the code):

| Family | Qualifiers (object it attaches to) |
|---|---|
| Creation/modification | `created` (Order), `added_to_order` (Item), `extended_with_item` (Order), `closed` (Order) |
| Stock | `stock_reserved` (Item), `stock_reservation_shared` (Order — the explicitly asserted *joint* reservation) |
| Packing | `packed` (Package), `item_packed` (Item), `order_stock_packed` (Order) |
| Shipping | `dispatched` (Package), `carrier` (Delivery), `item_shipped` (Item, *propagated*), `order_shipment_started` (Order, *propagated*) |
| Arrival | `delivery_confirmed` (Delivery), `package_delivered`, `item_delivered`, `order_fulfilled` (all *propagated*) |
| Financial | `issued` (Invoice), `billed` (Order), `item_covered_by_invoice` (Item, *propagated*), `recorded` (Payment), `partially_settles` (Invoice) |

**O2O direction convention.** A row `(ocel:oid=A, ocel:oid_2=B, ocel:qualifier=q)` reads left-to-right: “A q B” (subject  predicate  object). Examples: `O100 contains I1`, `P1 packs I1`, `D1 carries P1`, `V1 bills O100`, `M1 partially_settles V1`.

**Richness policy (the decisive choice).** I implement a *hybrid*: source-system facts for whatever the narrative asserts, plus a **deterministic one-hop propagation** over the O2O ground truth for logistics/billing milestones (dispatch and confirmation reach the packed items and their orders; issuing the invoice reaches the covered items). Trade-off:

- *Direct-source-only* relations are epistemically clean but leave the Order lane disconnected from shipping/billing, so flattened Order traces and the OC-DFG lose almost the whole fulfillment story.
- *Propagated* relations make order journeys analyzable but are **derivations, not observations**. Two safeguards prevent epistemic laundering: (1) every relation carries an extra audit column `origin  {source, propagated}`, and (2) propagation is restricted to an explicit, small rule set. **Payments are never propagated**: splitting 100 + 150 monetary units over two orders would be speculation, so payments relate only to `Payment` and `Invoice` (also carrying `partially_settles`, matching the narrative; `completes_settlement` would only be justified if the invoice total were known to be exactly 250).

**Version-dependent PM4Py assumption.** Target `pm4py >= 2.7.9` (OCEL 2.0-style `OCEL(events=..., objects=..., relations=..., o2o=...)`, `ocel_get_object_types`, `ocel_object_type_activities`, `ocel_flattening`, `discover_dfg`, `discover_log_skeleton`, `discover_ocdfg`, `discover_oc_petri_net`, `ocel_objects_interactions_summary`). `discover_otg` and `discover_etot` exist only in very recent releases; they are called through a guarded helper. The single constructor call is isolated in `instantiate_ocel()` with adaptation notes (e.g., on older builds drop `o2o`/`ocel:qualifier` for an OCEL-1.x flavor, or drop the extra `origin` column if a strict build rejects extra columns — semantics of the tables never change).

```python
def add_event(eid: str, activity: str, timestamp: str, **attrs) -> str:
```

## 4. Expected flattened behavior

**Order.** Traces: O100 with 12 events (Create, Add, Add, Reserve, Pack, Pack, Dispatch, Dispatch, Issue Invoice, Confirm, Confirm, Close), O200 with 8 (Create, Add, Reserve, Pack, Dispatch, Issue, Confirm, Close)  2 variants. Five shared events (E06, E07, E09, E11, E13) are copied into both traces. Approximate DFG edges: CreateAdd×2; AddAdd and AddReserve; ReservePack×2; PackPack (O100 only) and PackDispatch; DispatchDispatch (O100 only) and DispatchIssue; IssueConfirm×2; ConfirmConfirm (E13E14) and ConfirmClose×2. Misleading aspects: doubled weights on shared-event edges suggest batch/synchronised behavior that is really two orders coinciding; the identity of the two packed/shipped packages vanishes (you cannot see that 10:00-dispatch  10:15-dispatch covered different consignments); payments appear nowhere (policy!), so cash-delivery lag is invisible; PackPack could be misread as a re-packing loop.

**Package.** P1: PackDispatchConfirm (3 events); P2: same shape (3 events); 1 variant, DFG edges weight 2 each. Copy-sharing: none. Misleading: packages look independent and identical, hiding that P1 straddles two orders; arrival-date variance (13:00 vs next-day 09:00) is the only differentiation and is pure timestamp, not control flow.

**Delivery.** D1 and D2 each: DispatchConfirm (2 events), DFG edge weight 2. Misleading: perfectly symmetric shapes obscure cargo mix (D1 carries the mixed package) and falsely suggest a rigid service contract with exactly one leg per delivery.

**Invoice.** V1: IssueRecordPaymentRecordPayment (3 events, 1 variant). DFG edges IssueRecordPayment (M1), RecordPaymentRecordPayment (M2). Misleading: implies an instalment cadence/rule ("exactly two payments") that the data cannot guarantee; the qualifying relations (bill, settle) and the invoiced orders/items disappear from the activities themselves.

**Why Payment flattening is particularly weak.** Each payment object occurs in exactly one event (E12  M1, E15  M2). Result: two single-event traces, an empty DFG (zero directly-follows edges), a degenerate skeleton, start=end at the same activity, and all discriminating information stranded in attributes (`amount`) and timestamps. Because we (correctly) refused to propagate payments to orders, there is no other object lens that recovers the money story — the analyst must join against the Invoice flattening or traverse the O2O `bills`/`partially_settles` graph, i.e., the Payment view alone supports no process discovery whatsoever.

## 5. Expected object-centric structures

**OC-DFG.** Six per-type lanes. The Order lane reproduces the order-flattened DFG (branching at Pack/Dispatch for O100 vs O200, doubled weights on E06/E07/E09/E11/E13-adjacent edges). The Package lane is the clean PackDispatchConfirm chain; the Delivery lane DispatchConfirm; the Invoice lane IssuePaymentPayment; the Payment lane is an isolated activity node with no arcs — the graphic proof that payments are endpoints, not transitions. Qualifier-aware edges additionally distinguish e.g. Dispatch"item_shipped" (Item lane) from Dispatch"carrier" (Delivery lane). P1's story appears as weight-bearing arcs shared by no other object; O100 will visibly carry two parallel shipment streams where O200 carries one.

**OTG.** A compact type-level graph: a dense physical cluster (Order–Item strongest, Order–Package, Package–Item, Package–Delivery, Delivery–Order, Item–Delivery via the propagated links) bridged into a thin financial cluster (Order–Invoice=1 event, Invoice–Payment=2 events, Item–Invoice). Crucially, **Order–Payment has zero direct interaction**, and P1–V1 interact only indirectly through items/orders: the OTG makes the "economic network hangs off the physical network" architecture visible at a glance.

**ET–OT graph.** Bipartite activities×types: "Dispatch Package" and "Confirm Delivery" emerge as degree-4 hubs (Package, Delivery, Item, Order), "Pack Package" as degree 3, while "Create Order", "Close Order" sit at degree 1 and "Record Payment" is confined to the {Payment, Invoice} corner. It directly answers: which activities fuse which streams — the answer being logistics, emphatically not payments.

**Object-centric Petri net.** Expect (configuration-dependent — *not* one uniquely determined interpretation): a Package subnet that is essentially sequential, a Delivery subnet likewise, a Payment subnet of a single transition, an Invoice subnet admitting arbitrarily many Record Payment occurrences (loop), and an Order subnet that must tolerate both the O100 and O200 regimes, hence concurrency/XOR around the Pack and Dispatch phases. Correlation places/arcs wire these subnets together wherever objects co-occur — most thickly around Pack Package and Dispatch Package (P1 acting as bridge between O100 and O200). Read it as a candidate discipline to be validated by replay, not as ground truth.

**Object-interactions summary.** Pairwise co-participation counts confirm the narrative: (P1,O100) and (P1,O200) at 3 shared events each (E07, E09, E13); (P2,O100) 3; (V1,O100)=(V1,O200)=1; (V1,M1)=(V1,M2)=1; O100–I1 and O100–I2 heavy; and conspicuously **no (M\*,O\*) pairs and no (M1,M2) pair** even though M1+M2 jointly settle V1 — demonstrating that payment-to-order and payment-to-payment linkage exists only through O2O traversal (`bills`, `partially_settles`), i.e., analyst-mediated inference, never as observed event co-membership.

## 6. Modeling alternatives

1. **Source-minimal policy** (only what the narrative literally states: 34 E2O rows). Delivery confirmations stop touching packages/items/orders; dispatch stops touching orders/items; O100's trace shrinks to {E01,E02,E03,E06,E07,E11,E17}, its DFG losing almost all logistics arcs; Order–Delivery OTG edges vanish entirely. Discovery results become siloed and epistemically bulletproof, but the coordinated fulfillment story (mixed package P1!, joint reservation E06 is the sole survivor of convergence) disappears from activity-space and survives only in O2O.
2. **Full-operational-involvement policy** (everything plausibly coupled is a direct relation): payments also relate to both orders (and possibly items), dispatch to all goods on the vehicle, confirmations to invoices, etc. Consequences: flattened order traces gain copied payment events (two payments per order), DFG weights inflate multiplicatively, "Record Payment" obtains arcs to "Close Order" that never happened as *observed per-order* behavior, and divergence/convergence counts explode. Same business story, wildly inflated statistical story — ideal for hiding the actual signal behind noise.
3. **Fully O2O-propagated analytical policy** (transitive closure: every event reaches every O2O-reachable object, rewritten qualifiers, no `origin` concept): Order lanes become maximally rich (payments reachable if one also propagates Invoicebackwards), each event replicated up to N×N times. Enables per-order financial reconciliation without joins, but flattening duplication worsens (multiplied frequencies), and — most dangerously — generated rows become indistinguishable from telemetry, permanently contaminating any audit of "what did the source system actually record".
4. *(Bonus, opposite direction)* **Qualifier-collapse policy**: replace the 22-term vocabulary by a generic `involved`. Visually simpler OC-DFGs, but the Item-lane reservations vs deliveries vs invoicing blur into indistinguishable arcs; comparative analytics over qualifier distributions (which a real retailer would want) die.

The implemented pipeline sits deliberately between (1) and (3): source fidelity, plus exactly the one-hop derivations that make order/package/delivery/invoice lenses interpretable, each derivation signed in `origin`.

## 7. Failure modes

1. **Relation inflation** — unrestrained propagation turns 17 events into hundreds of effective pairs; DFG/OC-DFG weights multiply, and apparent process masses are artifacts. Mitigate with bounded, declared rules and origin tagging.
2. **Missing direct E2O links** — the source-minimal extreme disconnects lanes; flattened Delivery traces lose the notion that confirmations ever concerned anything beyond themselves; the OC-DFG decomposes into components. Cross-check that every narrated coupling exists somewhere (relations *or* O2O).
3. **Treating O2O propagation as observation** — silently deriving `order_fulfilled` rows and later reporting "orders fulfilled at 13:00" as measured fact. Mitigation: `origin` column, replayable rule set, exclusion of speculative domains (payments).
4. **Duplicate shared events after flattening** — E06/E07/E09/E11/E13 each occur twice per order-lens; naive frequency dashboards report 10–12 activities where the raw log has 17. Always reconcile flattened totals against source counts.
5. **Ambiguous payment allocation** — assigning M1 or M2 (100/150 units) proportionally to O100/O200 fabricates revenue attribution; any down-stream profit metric inherits the fiction. Keep payments invoice-bound; if allocation is unavoidable, surface it as an assumption parameter.
6. **Overly short Payment traces** — single-event traces yield empty DFGs and vacuous skeletons; conformance checking against them is meaningless. Use the interactions summary or invoice-centric views for financial diagnosis.
7. **Constructor/API version mismatch** — `OCEL(...)` kwargs, qualifier support, `discover_otg`/`discover_etot`, or validator strictness differ across pm4py releases; extra columns (our `origin`) may be rejected by strict builds. Mitigation: isolated constructor, guarded optional calls, and an upgrade-first fallback documented in `instantiate_ocel`.
8. **False total order for same-time events** — this dataset deliberately has no timestamp ties, but flattened copies share timestamps by construction, and any future data with ties forces arbitrary, often alphabetical, ordering that discovery mistakes for causality. Mitigations: sub-minute resolution, explicit sequence attributes, and never reading lexically ordered DFGs between equal-time events as sequence.
9. **Attribute blind spots** — `amount` rides on events only; aggregating per order requires joins that flattened logs cannot express; forgetting this produces unit-mismatched sums.
10. **Qualifier overload** — 22 qualifiers fragment OC-DFG arcs per type×qualifier pair; on bigger logs disable qualifier separation for the overview and re-enable it for diagnostics.
