### Conservative Model ProcessTree

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def create_conservative_model():
    def act(label):
        t = ProcessTree()
        t.label = label
        return t
    
    def tau():
        t = ProcessTree()
        t.label = None
        return t
    
    def xor(*children):
        t = ProcessTree()
        t.operator = Operator.XOR
        t.children = list(children)
        for c in children:
            c.parent = t
        return t
    
    def seq(*children):
        t = ProcessTree()
        t.operator = Operator.SEQUENCE
        t.children = list(children)
        for c in children:
            c.parent = t
        return t
    
    RO, CC, ER, SC, ExR, AC, RP, Arch = (
        act("Register Order"), act("Credit Check"), act("Engineering Review"),
        act("Supplier Confirmation"), act("Expedite Review"), act("Approve Configuration"),
        act("Release Production"), act("Archive Case")
    )
    
    # Create fresh activity instances for each branch    def branch(*labels):
        acts = [act(l) for l in labels]
        return seq(*acts)
    
    v1 = branch("Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case")
    v2 = branch("Register Order", "Engineering Review", "Credit Check", "Supplier Confirmation", "Approve Configuration", "Release Production", "Archive Case")
```

```python
    """Create an XOR (exclusive choice) operator node."""
    t = ProcessTree()
```

**Why bidirectional DFG edges do not prove concurrency.** A frequency DFG with both AB and BA edges only tells us that in some traces A appears before B, and in others B appears before A. This is equally consistent with: (i) *true concurrency* — A and B are parallel and completion order varies (S2); (ii) *XOR with both outcomes* — the process explores both orderings across different case types without any concurrency; (iii) *overlapping lifecycles* — both start nearly simultaneously but one finishes first depending on workload, with neither "causing" the other; (iv) *misattributed events* — completion-order logging (S7) or ingestion-index tie-breaking reorders activities that were actually simultaneous. The DFG encodes *co-occurrence* and *relative order*, not *causal dependency* or *parallel execution*. Concurrency in process mining additionally requires either start-time evidence (absent per S7) or a model that deliberately chooses to represent the unordered region as interleaving — which is an inductive bias, not a data-driven fact.

All orderings in traces reflect completion order, which may differ from execution-start order. This means a trace "CC, ER" could represent CC started first and finished first, or CC and ER running in parallel with CC finishing first.

2. **Missing Supplier Confirmation events.** Absent SC events conflate two distinct phenomena: (a) legitimate optionality — stocked-component orders skip SC (S4); (b) data loss — approximately 5–10% of SC events are missing due to integration failure (S5). Because the external/stocked attribute was not exported, we cannot distinguish (a) from (b) at the trace level. All three models represent SC optionality through a control-flow alternative (XOR with ); we disclose that this abstraction merges real optionality with potential missingness. Sensitivity analysis (Section 9) will address how treating the 7 SC-absent traces as pure missing data would change the model.

3. **Absent external/stocked attribute.** The model cannot condition SC presence on order type. Consequently, SC optionality is modeled as unconditional (XOR(SC, )) rather than guarded by a data condition. If the attribute were available, a data-aware model could distinguish "SC required (external)" from "SC skipped (stocked)".

4. **Optionality representation.** Optional activities are represented as XOR between the activity and a silent transition ( / `SilentTransition`). This is a standard control-flow encoding of optionality. It means the model can produce traces where the activity is present *or absent*, but never *multiple* times (unless a loop operator is added — none of the three models use loops).

5. **Fixed start and end.** D1 is enforced as a hard constraint: Register Order is the only start, Archive Case is the only end. No model admits traces beginning or ending with any other activity.

6. **Expedite Review multiplicity.** D6 states ExR occurs at most once. Since each model includes exactly one ExR node (or one XOR branch containing it), multiplicity is naturally bounded at 1.

7. **Trace-level granularity.** All 30 traces are treated as complete, correctly sequenced cases. No trace is discarded for quality reasons. The sample size (n=30) is small enough that rare behaviors (Expedite Review, SC-before-ER) are based on single-digit counts.

8. **Label identity.** Activity labels are treated as unique and unambiguous. There is no concern about homonyms across organizational units.

# 3. Conservative Candidate

## Inductive-Bias Statement

The conservative model applies *strict empirical fidelity*: it admits exactly the seven observed trace variants and nothing else. Its inductive bias is that any behavior not witnessed in the 30-case sample is unproven and must be excluded. This approach minimizes the risk of admitting false behavior (high precision) at the cost of generalization: any unobserved-but-valid process variant will be rejected. The model makes no interpretation of D5, D6, or the S1/S2 conflict — it simply encodes what was seen. This is the most *auditable* model: every admitted trace maps directly to a counted variant.

## Compact Formal Expression

$$\mathcal{M}_{\text{cons}} = \bigoplus_{i=1}^{7} \sigma_i$$

where $\oplus$ denotes exclusive choice (XOR) and $\sigma_i$ is the $i$-th observed variant:

| $i$ | $\sigma_i$ |
|---|---|
| 1 | $RO \to CC \to ER \to SC \to AC \to RP \to \text{Arch}$ |
| 2 | $RO \to ER \to CC \to SC \to AC \to RP \to \text{Arch}$ |
| 3 | $RO \to CC \to ER \to AC \to RP \to \text{Arch}$ |
| 4 | $RO \to ER \to CC \to AC \to RP \to \text{Arch}$ |
| 5 | $RO \to CC \to SC \to ER \to AC \to RP \to \text{Arch}$ |
| 6 | $RO \to CC \to ER \to SC \to ExR \to AC \to RP \to \text{Arch}$ |
| 7 | $RO \to ER \to CC \to ExR \to SC \to AC \to RP \to \text{Arch}$ |

## PM4Py Code

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def _act(label: str) -> ProcessTree:
    """Create a ProcessTree leaf node for an activity label."""
    node = ProcessTree()
    node.label = label
    node.operator = None
    node.children = []
    return node


def _seq(*children: ProcessTree) -> ProcessTree:
    """Create a SEQUENCE operator node."""
    node = ProcessTree()
    node.operator = Operator.SEQUENCE
    node.children = list(children)
    for c in children:
        c.parent = node
    return node


def _xor(*children: ProcessTree) -> ProcessTree:
    """Create an XOR (exclusive choice) operator node."""
    node = ProcessTree()
    node.operator = Operator.XOR
    node.children = list(children)
    for c in children:
        c.parent = node
    return node


def _branch(*labels: str) -> ProcessTree:
    """Create a sequential chain of activities from labels."""
    return _seq(*(_act(l) for l in labels))


# ---- Activity labels ----
RO   = "Register Order"
CC   = "Credit Check"
ER   = "Engineering Review"
SC   = "Supplier Confirmation"
ExR  = "Expedite Review"
AC   = "Approve Configuration"
RP   = "Release Production"
Arch = "Archive Case"

# ---- Seven observed variants as XOR branches ----
v1 = _branch(RO, CC, ER, SC, AC, RP, Arch)
v2 = _branch(RO, ER, CC, SC, AC, RP, Arch)
v3 = _branch(RO, CC, ER, AC, RP, Arch)
v4 = _branch(RO, ER, CC, AC, RP, Arch)
v5 = _branch(RO, CC, SC, ER, AC, RP, Arch)
v6 = _branch(RO, CC, ER, SC, ExR, AC, RP, Arch)
v7 = _branch(RO, ER, CC, ExR, SC, AC, RP, Arch)

model_conservative = _xor(v1, v2, v3, v4, v5, v6, v7)
```

## Behavior Deliberately Excluded

- Any trace where SC appears in an ordering not exactly matching one of the 7 variants (e.g., `RO, ER, CC, SC, ExR, …` — SC before ExR with ER first).
- Any trace where ExR appears without the exact SC/ExR combination observed (e.g., `RO, CC, ER, ExR, SC, …` — CC first with ExR before SC).
- Any trace where ExR appears without SC (e.g., `RO, CC, ER, ExR, AC, RP, Arch`) — this is a plausible pattern admitted by balanced/permissive but not observed.
- Any SC ordering not explicitly enumerated (e.g., `RO, SC, CC, ER, …` — SC before CC).
- Any behavior not literally equal to one of the 7 variant strings.

## Known Underfitting Risks

- **Zero generalization.** The model's language is exactly 7 traces. Any real-world variant not in this set (even one fully consistent with domain rules) will be rejected. If the process legitimately produces `RO, ER, CC, SC, ExR, AC, RP, Arch` (a combination of V2's CC/ER order with V7's ExR/SC order), the model rejects it.
- **Duplicate labels inflate the net.** Each of the 7 XOR branches creates its own copy of all 8 activity labels  7×7 = 49 activity transitions (8 × 7 = 56 total, minus shared structure where applicable) in the Petri net. This hurts structural simplicity metrics and makes the net hard to read. Token replay may exhibit label-ambiguity: when replaying "Register Order," the replayer must choose among 7 possible transitions.
- **Scalability.** If the process generates 200 variants (common in flexible workflows), the XOR would have 200 branches. The Petri net would have ~1,600 transitions. Process mining precision metrics degrade; the model becomes unmanageable.
- **Sensitive to noise.** A single mislogged event in the source data would create a unique variant, and the model would encode that noise as legitimate behavior.
- **Fails to resolve D5/D7.** By simply copying observed traces, the model implicitly endorses S1 (CC before ER) for 19 traces and S2 (ER before CC) for 11, without acknowledging that this is an artifact of completion-order logging, not evidence about process structure.

# 4. Balanced Candidate

## Inductive-Bias Statement

The balanced model applies *moderate generalization with explicit uncertainty management*. It accepts that Credit Check and Engineering Review are structurally unordered (D7: we cannot distinguish concurrency from sequence from overlap), that Supplier Confirmation is optional but must follow at least Credit Check (the tightest constraint supported by observed evidence without over-relying on the weak D5), and that Expedite Review is optional with well-defined preconditions (D6). Its inductive bias is toward a *partial order* that is as permissive as the evidence supports while respecting all medium-to-high confidence domain rules. The model discloses its key uncertainty (CC/ER ordering, SC optionality conflated with missingness) through structure rather than through prose caveats alone.

## Compact Formal Expression

$$\mathcal{M}_{\text{bal}} = \text{PO}(V,\; R_{\text{bal}})$$

where $V = \{RO,\; CC,\; ER,\; (SC|\tau),\; (ExR|\tau),\; AC,\; RP,\; \text{Arch}\}$ and

$$R_{\text{bal}} = \{(RO,CC),\;(RO,ER),\;(RO,SC^?),\;(RO,ExR^?),\;(CC,AC),\;(ER,AC),\;(CC,SC^?),\;(CC,ExR^?),\;(ER,ExR^?),\;(ExR^?,AC),\;(SC^?,AC),\;(AC,RP),\;(RP,\text{Arch})\}$$

Here $SC^?$ denotes the optional node (XOR of SC and ), $ExR^?$ likewise. **No edge exists between CC and ER** (D7). **No edge exists between $SC^?$ and $ExR^?$** (S6). **No edge exists between ER and $SC^?$** (D5 / V5 allows SC before ER).

## Decision Between Sequence, Concurrency, and Partial Order

| Pair | Decision | Rationale |
|---|---|---|
| CC vs. ER | **Partial order: no edge** (unordered, freely interleavable) | D7 explicitly states completion order cannot reveal concurrency. V1, V3, V5, V6 show CC before ER; V2, V4, V7 show ER before CC. S1 (sequence CCER) and S2 (parallel) conflict. A hard CCER sequence would reject 11 observed traces; a hard ERCC sequence would reject 19. The only non-arbitrary choice compatible with all data and both stakeholder claims is *no constraint*. This is not a claim of concurrency — it is a *decision to leave the relationship underdetermined.* |
| CC/ER vs. SC | **Partial order: CC  SC, no ER  SC edge** | V5 (CC, SC, ER) proves SC can precede ER, ruling out ER  SC as a hard edge. Every observed trace with both CC and SC has CC before SC (V1, V5, V6), so CC  SC is safe. D5 says SC may begin after *either* CC or ER — CC  SC honors the "after CC" part of this without over-reading the ambiguous "either." The balanced model deliberately does *not* encode "after ER or after CC, whichever is first" because a pure partial order cannot express disjunctive ("or") constraints; doing so would require an XOR/OR node that adds structural complexity and is not clearly supported. |
| SC vs. ExR | **Partial order: no edge** | V6 (SC before ExR) and V7 (ExR before SC) both observed. S6 explicitly states ExR may be before or after SC. No constraint is warranted. |
| CC/ER vs. ExR | **Partial order: CC  ExR and ER  ExR** | D6 (medium confidence): ExR "requires completion of both Credit Check and Engineering Review." Both are enforced as hard incoming edges to the optional ExR node. |
| All pre-approval activities vs. AC | **Partial order:  AC** | D3 (medium-to-high): CC and ER before AC. D4 (medium): SC before AC. D6 (medium): ExR before AC. All three edges are present. |
| AC  RP  Arch | **Strict sequence** | D1 and D2 (high confidence). Always observed together. |

## PM4Py Code

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# ---- Transitions ----
RO   = Transition("Register Order")
CC   = Transition("Credit Check")
ER   = Transition("Engineering Review")
SC   = Transition("Supplier Confirmation")
ExR  = Transition("Expedite Review")
AC   = Transition("Approve Configuration")
RP   = Transition("Release Production")
Arch = Transition("Archive Case")
tau  = SilentTransition()

# ---- Optional wrappers ----
SC_opt  = OperatorPOWL(Operator.XOR, [SC,  tau])   # SC or skip
ExR_opt = OperatorPOWL(Operator.XOR, [ExR, tau])    # ExR or skip

# ---- Build partial order ----
model_balanced = StrictPartialOrder(
    nodes=[RO, CC, ER, SC_opt, ExR_opt, AC, RP, Arch]
)

_bal_edges = [
    # Register Order first (D1)
    (RO, CC), (RO, ER), (RO, SC_opt), (RO, ExR_opt),
    # Pre-approval constraints
    (CC, AC), (ER, AC),                # D3: both checks before approval
    (CC, SC_opt),                      # D5: SC after CC (not after ER — allows V5)
    (CC, ExR_opt), (ER, ExR_opt),      # D6: ExR after both checks
    (ExR_opt, AC),                     # D6: ExR before approval
    (SC_opt, AC),                      # D4: SC before approval
    # No edge: CC  ER (D7 uncertainty)
    # No edge: SC_opt  ExR_opt (S6: either order)
    # Post-approval sequence
    (AC, RP), (RP, Arch),              # D1, D2
]

for _src, _dst in _bal_edges:
    model_balanced.order.add_edge(_src, _dst)
```

## Behavior Deliberately Excluded

- `RO, SC, CC, ER, AC, RP, Arch` — SC before CC. Violates edge (CC, SC_opt). The balanced model assumes SC does not begin until CC has completed (tightest constraint supported by observed data without reading D5 liberally).
- `RO, CC, ER, AC, SC, RP, Arch` — SC after AC. Violates edge (SC_opt, AC) (D4: SC before Approve Configuration).
- `RO, ExR, CC, ER, AC, RP, Arch` — ExR before both checks. Violates edges (CC, ExR_opt) and (ER, ExR_opt) (D6).
- `RO, CC, ER, AC, ExR, RP, Arch` — ExR after AC. Violates edge (ExR_opt, AC) (D6).
- `RO, CC, RP, AC, Arch` — RP before AC. Violates edge (AC, RP) (D2).

## Known Underfitting Risks

- **CC  SC may be over-constraining.** If D5's "either CC or ER" means SC can start after ER alone (without waiting for CC), then a trace `RO, ER, SC, CC, AC, RP, Arch` would be valid but is rejected by the balanced model (violates CC  SC). This trace is unobserved but consistent with D5's literal reading.
- **Missingness conflation.** The XOR(SC, ) encoding admits traces without SC. If S5's 5–10% missing SC events explains some of V3/V4, the model overstates SC optionality (real-world fitness on corrected data would be < 1.0 for the no-SC branches).
- **CC/ER unordered admits interleavings with no causal justification.** If S1 is actually correct (CC before ER is a hard requirement), the balanced model is *too permissive* — it admits 11 traces (V2, V4, V7 patterns) that shouldn't exist. The model cannot distinguish "unordered because truly flexible" from "ordered but the log doesn't reveal it."
- **ExR may be under-constrained.** D6 says ExR "may occur before or after Supplier Confirmation." The balanced model allows this (no SC/ExR edge). But if domain rules later tighten to "ExR must follow SC," the model would need revision.

# 5. Permissive Candidate

## Inductive-Bias Statement

The permissive model applies *maximum generalization within explicitly defined domain-rule boundaries*. It respects only the highest-confidence rules (D1, D2, D3) and the compliance-critical ExR constraints (D6), while deliberately relaxing D4 (SC-before-AC) and D5 (SC-after-CC) as medium and low-to-medium confidence rules respectively. Its inductive bias is that the observed sample may not cover all legitimate process behavior, and that domain rules with medium or lower confidence should be treated as soft constraints rather than hard ones — except where compliance requires enforcement (D6). This model is designed for *exploration*: it reveals what behavior would be admitted if we are wrong about D4 and D5, helping stakeholders identify which relaxations are dangerous.

## Compact Formal Expression

$$\mathcal{M}_{\text{perm}} = \text{PO}(V,\; R_{\text{perm}})$$

where $V = \{RO,\; CC,\; ER,\; (SC|\tau),\; (ExR|\tau),\; AC,\; RP,\; \text{Arch}\}$ and

$$R_{\text{perm}} = \{(RO,CC),(RO,ER),(RO,SC^?),(RO,ExR^?),(CC,AC),(ER,AC),(CC,ExR^?),(ER,ExR^?),(ExR^?,AC),(SC^?,RP),(AC,RP),(RP,\text{Arch})\}$$

Compared to $R_{\text{bal}}$: **removed** $(CC,SC^?)$ (D5 relaxed — SC need not follow CC), **removed** $(SC^?,AC)$ (D4 relaxed — SC may follow AC), **added** $(SC^?,RP)$ (SC must still precede Release Production as a weaker domain boundary).

## Boundary Between "Reasonable Generalization" and "Forbidden"

| Rule | Confidence | Status in Permissive Model | Reasoning |
|---|---|---|---|
| D1: RO start, Arch end | High | **Forbidden to violate** | Always observed; structural invariant of every process |
| D2: AC before RP | High | **Forbidden to violate** | Always observed; releasing production before approval is a compliance violation |
| D3: CC and ER before AC | Medium-to-high | **Forbidden to violate** | Approving without completing checks is a control failure; observed in all 30 traces |
| D4: SC before AC | Medium | **Relaxed**: SC before RP (not AC) | If SC is a post-approval supplier confirmation step, D4 may be too strict. Relaxing allows traces like `…AC, SC, RP…` |
| D5: SC after either CC or ER | Low-to-medium | **Relaxed**: SC unconstrained relative to CC/ER | Low confidence; the "either … or" reading is ambiguous; SC may start as soon as RO completes if the supplier needs early lead time |
| D6: ExR after CC+ER, before AC | Medium | **Forbidden to violate** | Compliance rule (S6); expediting without principal checks is risky |
| D7: Unknown | Unknown | **Acknowledged** (no CC/ER edge, same as balanced) | Cannot be resolved from data |

**The boundary:** Behavior is *forbidden* if it violates D1, D2, D3, or D6. Behavior is *admitted but should be flagged* if it involves SC in an unusual position (before CC, after AC, but before RP). Behavior that would violate D1–D3 or D6 is treated as *clearly undesirable* regardless of domain confidence levels.

## Behavior Deliberately Excluded

- `RO, ExR, CC, ER, AC, RP, Arch` — ExR before CC/ER. Violates D6 edges (CC, ExR_opt) and (ER, ExR_opt).

- **SC placed anywhere after RO and before RP is overly permissive.** A trace like `RO, SC, CC, ER, AC, RP, Arch` — where supplier confirmation happens before any check has even started — may be operationally impossible (you cannot confirm supplier delivery before knowing what's being built). The model admits this because D5 is relaxed.
- **SC after AC may violate a genuine control requirement.** If D4 is correct (SC must precede approval), then `RO, CC, ER, AC, SC, RP, Arch` represents approving a configuration before confirming supplier availability — a risk. The permissive model admits this.
- **Combined SC freedom (before CC *and* after AC) creates a very large language.** For an 8-activity partial order with SC essentially floating, the number of admissible interleavings grows combinatorially. Precision will be noticeably lower than balanced.
- **False sense of completeness.** Stakeholders reviewing this model might conclude "everything possible is modeled" when in fact loops, retries, re-approvals, and conditional branching (e.g., ExR trigger conditions) are all absent.

```python
# --- Helper functions for ProcessTree ---
def _act(label):
    n = ProcessTree(); n.label = label; n.operator = None; n.children = []
    return n

def _seq(*ch):
    n = ProcessTree(); n.operator = Operator.SEQUENCE
    n.children = list(ch)
    for c in ch: c.parent = n
    return n

def _xor(*ch):
    n = ProcessTree(); n.operator = Operator.XOR
    n.children = list(ch)
    for c in ch: c.parent = n
    return n

def _branch(*labels):
    return _seq(*(_act(l) for l in labels))
```

# 9. Recommendation and Data-Collection Plan

## Recommendation

**For immediate use: `model_balanced`.**

The balanced model offers the best combination of fitness (1.0 on all 30 cases), defensible precision, and explicit uncertainty handling. It respects every rule with medium-to-high confidence (D1, D2, D3, D4, D6), encodes D5 conservatively (CCSC without over-reading the ambiguous "either"), and transparently leaves CC/ER unordered in response to D7's explicit statement that the data cannot resolve this question. Its partial-order structure is compact (8 nodes, 13 edges), making it the most explainable of the three non-trivial models. Every design choice maps to a specific evidence item.

**For sensitivity analysis: `model_permissive`.**

The permissive model should be run in parallel to answer: *"If D4 and D5 are wrong, what behavior would we admit, and does any of it cause compliance problems?"* Specifically, replay compliance violations (e.g., `RO, CC, ER, AC, SC, RP, Arch`) against the permissive model to see whether they are flagged. If the permissive model *does not* flag them, it tells you that D4 relaxation creates a real audit gap. The conservative model serves as a third data point for *overfitting detection*: any trace accepted by conservative but not balanced (there are none, by construction) would be a red flag; any trace rejected by conservative but accepted by balanced indicates a valid generalization.

## Plausible Alternative Interpretation That Would Materially Change the Recommendation

**If S1 is correct and S2 is wrong** — i.e., Credit Check truly must complete before Engineering Review starts — then the balanced model's "no edge between CC and ER" is an over-generalization that *admits 11 invalid traces* (V2, V4, V7 all have ER before CC). Under this interpretation:

1. The observed ER-before-CC traces must be explained by something other than process structure — most likely **completion-order logging artifacts** (S7: activities with identical timestamps ordered by ingestion index; or overlapping lifecycles where CC and ER start simultaneously but ER finishes first despite CC having started first).
2. The correct model would be a **strict sequence** $CC \to ER$, collapsing the 7 variants into perhaps 4 (eliminating the ER-first branches as log artifacts).
3. The balanced model's precision would drop (it admits behavior that S1 says cannot happen), and the conservative model (which *includes* the ER-first branches) would be encoding log noise as process structure.
4. **Recommendation would change**: instead of the balanced model, I would recommend a *revised balanced model* with CCER as a hard edge, and V2/V4/V7 reclassified as logging artifacts pending start-time confirmation.

**What data would resolve this:** start timestamps for CC and ER across  100 additional cases. If `CC_complete < ER_start` holds universally  S1 correct  add CCER edge. If `ER_start < CC_complete` in any case  overlap exists  unordered is correct. If `CC_complete  ER_start` within clock resolution  ambiguous, keep unordered with a documented caveat.

A second material alternative: **if the integration problem (S5) turns out to affect far more than 5–10% of SC events**, then the 7 SC-absent traces may all be data artifacts, SC would be mandatory (not optional), and the balanced model's XOR(SC, ) would overstate optionality. In that case, SC should be *required* whenever the order type is external (a data-conditional model), and unconditional optionality would only apply to stocked orders. This would make the balanced model's language smaller (no SC-absent branches for external orders) and increase precision — but require the external/stocked attribute to be available.
