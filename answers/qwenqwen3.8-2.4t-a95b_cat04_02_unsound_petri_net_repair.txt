```
from pm4py.objects.petri_net.obj import Marking

def format_marking(marking):
    return {p.name: n for p, n in sorted(marking.items(), key=lambda kv: kv[0].name) if n > 0}

def enabled_names(net, marking):
    return sorted(t.name for t in pm4py.get_enabled_transitions(net, marking))

def fire_named_transition(net, marking, transition_name, verbose=False):
    enabled = pm4py.get_enabled_transitions(net, marking)
    trans = next((t for t in net.transitions if t.name == transition_name), None)
    if trans is None:
        raise ValueError(f"Transition {transition_name} not in net")
    if trans not in enabled:
        raise ValueError(f"{transition_name} not enabled in marking {format_marking(marking)}")
    new_marking = Marking()
    for p, count in marking.items():
        if count > 0:
            new_marking[p] = count
    for arc in trans.in_arcs:
        src = arc.source
        if new_marking.get(src, 0) < 1:
            raise ValueError(...)
        new_marking[src] -= 1
        if new_marking[src] == 0:
            del new_marking[src]
    for arc in trans.out_arcs:
        tgt = arc.target
        new_marking[tgt] = new_marking.get(tgt, 0) + 1
    if verbose: print(...)
    return new_marking

def play_sequence(net, marking, sequence, label):
    print(f"--- Playing {label} ---")
    m = marking
    print("Initial", format_marking(m), enabled_names(net,m))
    for name in sequence:
       try:
          m = fire_named_transition(net,m,name, verbose=True)
       except ValueError as e:
          print("Blocked:", e)
          break
    print("Final marking", format_marking(m), "equals fm?", format_marking(m)=={p.name:1 for p in fm?})
    return m
```

```
import pm4py
from pm4py.objects.petri_net.obj import Marking

def nonzero_marking(m):
    return {p.name: n for p, n in m.items() if n > 0}

def marking_equal(m, target):
    return {p: n for p,n in m.items() if n>0} == {p:n for p,n in target.items() if n>0}

def get_transition_by_name(net, name):
    for t in net.transitions:
        if t.name == name:
            return t
    raise KeyError(name)

def fire_named_transition(net, marking, t_name):
    t = get_transition_by_name(net, t_name)
    enabled = pm4py.get_enabled_transitions(net, marking)
    if t not in enabled:
        raise ValueError(f"{t_name} is not enabled; marking={nonzero_marking(marking)}; enabled={sorted(x.name for x in enabled)}")
    new_m = Marking()
    for p, n in marking.items():
        if n > 0:
            new_m[p] = n
    for arc in t.in_arcs:
        p = arc.source
        if new_m.get(p, 0) <= 0:
            raise ValueError(...)
        new_m[p] -= 1
        if new_m[p] == 0:
            del new_m[p]
    for arc in t.out_arcs:
        p = arc.target
        new_m[p] = new_m.get(p, 0) + 1
    return new_m

def play_sequence(net, initial_marking, target_marking, sequence, label):
    print(f"=== {label} ===")
    m = initial_marking
    print(f"initial: {nonzero_marking(m)} enabled: {sorted(t.name for t in pm4py.get_enabled_transitions(net, m))}")
    for t_name in sequence:
        try:
            m = fire_named_transition(net, m, t_name)
            print(f"fired {t_name}: {nonzero_marking(m)} enabled: {sorted(t.name for t in pm4py.get_enabled_transitions(net, m))}")
        except ValueError as e:
            print(f"blocked at {t_name}: {e}")
            return m, False
    print(f"final marking equals target? {marking_equal(m, target_marking)}")
    return m, marking_equal(m, target_marking)
```

# 1. Executive Verdict

The accepting Petri net is structurally a workflow net: it has a unique source (`source`) and sink (`sink`), and every node has a directed source-to-sink path. It should not be expected to be sound. The principal defect is the waiver join: `t_join_waived` has only `p_waived` as input, so it neither waits for nor consumes the analysis result. After a waiver, `t_authorize` can fire before `t_analyze`; if analysis is done before or after the waiver join, a token remains in `p_analysis_done` or `p_analysis` and cannot be consumed. Business consequence: waiver cases may be authorized without mandatory analysis, or they finish with stray tokens instead of the exact final marking.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `im` | Unique start place with initial token | Correct: `source` has no input arc and initially one token | None by itself |
| `t_register`, `p_ready`, `t_split` | Register case, then start analysis and review in parallel | `t_split` correctly produces one token into `p_analysis` and one into `p_review` | None by itself; it creates the two parallel obligations |
| Analysis branch: `p_analysis`  `t_analyze`  `p_analysis_done` | Mandatory analysis activity and completion marker | `t_analyze` consumes `p_analysis` and produces `p_analysis_done`; originally only `t_join_normal` consumes `p_analysis_done` | On waiver path, analysis completion token can become stranded, or analysis can be ignored entirely |
| Review choice: `p_review`  `t_standard_review` / `t_waive_review` | Exclusive choice between standard review and waiver | Both transitions compete for the single `p_review` token; firing one disables the other | Structurally behaves as an XOR choice, but downstream synchronization differs |
| Standard review path: `p_review_done`  `t_join_normal` | Standard-review completion feeds authorization after analysis | `t_join_normal` requires both `p_analysis_done` and `p_review_done` | Correct behavior on standard-review path |
| Waiver path: `p_waived`  `t_join_waived` | Waiver outcome should complete review and synchronize with analysis | `t_join_waived` requires only `p_waived`; it has no input from the analysis branch | Waiver join can fire before analysis, and it leaves analysis tokens unconsumed |
| Joins to `p_decision` | Merge the two possible review outcomes and enable authorization | Two independent silent joins write to the same `p_decision` place; normal join is an AND-join, waiver join is not | `t_authorize` can be enabled by an incomplete waiver path |
| `p_decision`, `t_authorize`, `sink`, `fm` | Authorize only after analysis and selected review outcome; final marking has only `sink` token | `t_authorize` fires whenever `p_decision` has a token, regardless of how that token was produced | Sink token can coexist with leftover `p_analysis` or `p_analysis_done`; exact `fm` not reached |
| Source-to-sink path condition | Every node should lie on some structural source-to-sink path | Structurally yes: every place/transition has a directed path from `source` and to `sink` | Workflow-net check can pass even though the waiver path is behaviorally broken |

# 3. Marking-Based Counterexample

## Counterexample 1: waiver enables authorization before mandatory analysis

Legal firing sequence:

```text
t_register
t_split
t_waive_review
t_join_waived
t_authorize
t_analyze
```

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `{source: 1}` | `{t_register}` | Initial marking `im` |
| 1 | `t_register` | `{p_ready: 1}` | `{t_split}` | Case registered |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `{t_analyze, t_standard_review, t_waive_review}` | Parallel branch tokens are created: one for analysis, one for review choice |
| 3 | `t_waive_review` | `{p_analysis: 1, p_waived: 1}` | `{t_analyze, t_join_waived}` | Review waiver is recorded while analysis has not occurred |
| 4 | `t_join_waived` | `{p_analysis: 1, p_decision: 1}` | `{t_analyze, t_authorize}` | Waiver join did not wait for analysis; authorization is already enabled |
| 5 | `t_authorize` | `{p_analysis: 1, sink: 1}` | `{t_analyze}` | A token exists in `sink`, but the marking is not exactly `fm` because `p_analysis` remains |
| 6 | `t_analyze` | `{p_analysis_done: 1, sink: 1}` | `` | Analysis happens too late; the `p_analysis_done` token cannot be consumed |

At step 5, `t_authorize` has occurred before `t_analyze`, violating the mandatory-analysis rule. At step 5 there is already a token in `sink`, but the exact final marking `fm = {sink: 1}` has not been reached because `p_analysis` remains. At step 6 the remaining `p_analysis` token can be consumed by `t_analyze`, but this only creates `p_analysis_done`. That token cannot be consumed because `t_join_normal` also requires `p_review_done`, which does not exist on the waiver path, and `t_join_waived` has no input arc from `p_analysis_done`.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| R1: synchronize waiver join with analysis completion | Add one arc: `p_analysis_done -> t_join_waived` | `1` | Analysis remains mandatory; waiver remains an alternative review outcome; authorization occurs only after both analysis and selected review outcome | `t_join_waived` now requires both `p_waived` and `p_analysis_done`; it consumes the analysis-done token and blocks authorization until analysis has occurred | Silent join remains unobservable; if future policy wants waiver to skip analysis, this repair blocks that policy; shared `p_analysis_done` input to two joins relies on the review choice remaining exclusive |
| R2: waiver cancels pending analysis before analysis starts | Add one arc: `p_analysis -> t_waive_review` | `1` | Standard path still requires analysis; standard and waiver remain distinguishable; net becomes sound | Business policy changes: waiver no longer requires analysis. Waiver consumes the pending analysis token and can occur only before `t_analyze`; once analysis starts, waiver is disabled and standard review is required | Violates the original mandatory-analysis rule; visible waiver transition silently cancels analysis; waiver after analysis becomes impossible, which may not match operational practice |

Under this edit-cost model, both repairs are minimal because they each have cost `1`. Zero edits cannot be a repair: the original net admits the counterexamples above and therefore is not sound. The two cost-1 repairs tie numerically but are behaviorally distinct:

- R1 fixes the missing synchronization while preserving the stated business policy.
- R2 fixes soundness by changing the business policy so that a waiver cancels the pending analysis token before analysis starts.

A tempting naive edit such as adding `p_waived -> t_join_normal` is not sufficient as a one-arc repair, because Petri-net transition inputs are conjunctive: `t_join_normal` would then require both `p_review_done` and `p_waived`, making it impossible unless both review outcomes occurred. An OR-style merge requires either separate joins, as in R1, or an explicit review-completed construction with additional places/transitions and higher edit cost.

# 6. Diagnostic and Reachability Code

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking


def nonzero_marking(marking):
    return {p.name: n for p, n in marking.items() if n > 0}


def equal_marking(marking, target):
    left = {p: n for p, n in marking.items() if n > 0}
    right = {p: n for p, n in target.items() if n > 0}
    return left == right


def enabled_transition_names(net, marking):
    return sorted(t.name for t in pm4py.get_enabled_transitions(net, marking))


def transition_by_name(net, name):
    for t in net.transitions:
        if t.name == name:
            return t
    raise ValueError(f"Transition '{name}' not found in net.")


def fire_named_transition(net, marking, name):
    t = transition_by_name(net, name)
    enabled = pm4py.get_enabled_transitions(net, marking)

    if t not in enabled:
        raise ValueError(
            f"Transition '{name}' is not enabled. "
            f"Marking: {nonzero_marking(marking)}. "
            f"Enabled: {enabled_transition_names(net, marking)}."
        )

    new_marking = Marking()
    for p, n in marking.items():
        if n > 0:
            new_marking[p] = n

    for arc in t.in_arcs:
        p = arc.source
        if new_marking.get(p, 0) == 0:
            raise ValueError(f"Missing token in place '{p.name}' for transition '{name}'.")
        new_marking[p] -= 1
        if new_marking[p] == 0:
            del new_marking[p]

    for arc in t.out_arcs:
        p = arc.target
        new_marking[p] = new_marking.get(p, 0) + 1

    return new_marking


def play_sequence(net, initial_marking, target_marking, sequence, label):
    print(f"=== {label} ===")
    m = initial_marking
    print(f"initial: {nonzero_marking(m)} | enabled: {enabled_transition_names(net, m)}")

    for name in sequence:
        try:
            m = fire_named_transition(net, m, name)
            print(f"after {name}: {nonzero_marking(m)} | enabled: {enabled_transition_names(net, m)}")
        except ValueError as exc:
            print(f"blocked at {name}: {exc}")
            break

    print(f"reached target marking? {equal_marking(m, target_marking)}")
    print()
    return m


original_bad_waiver_before_analysis = [
```

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability of waiver and standard review**
  - R1 preserves the visible distinction: `t_standard_review` and `t_waive_review` remain separate labeled activities. The standard and waiver outcomes are still distinguishable in an event log.
  - R2 also preserves the visible distinction, but the waiver transition now has a hidden side effect: it cancels the pending analysis token. If analysis is expected to appear in the log, R2 changes the expected log pattern.

- **Duplicate behavior and silent-transition confusion**
  - R1 adds no visible transitions. The silent transitions `t_split`, `t_join_normal`, and `t_join_waived` remain unobservable. This does not create duplicate visible traces by itself, but it can make internal routing harder to observe directly from logs.
  - R1 keeps two silent joins feeding the same `p_decision` place. This is acceptable here because the review choice consumes a single `p_review` token, so both review outcomes cannot occur. However, if a later edit allows both standard review and waiver, the shared `p_analysis_done` input could become a real conflict.
  - R2 may be more confusing operationally because the visible activity `Record Review Waiver` silently cancels the planned analysis. Users may think analysis is still pending when the model has already removed it.

- **Soundness is not proof of business alignment**
  - R2 demonstrates this clearly: it can be sound, but it violates the original business rule that analysis is mandatory. Soundness checks proper completion, absence of dead tokens, and absence of dead transitions; they do not prove that the net encodes all business obligations.
  - Even R1, while policy-preserving, should be validated against required trace rules. Soundness alone does not prove that all desired business traces are present or that all forbidden business traces are absent.

- **Positive traces to regression-test for R1**
  - Standard review after analysis:
    ```text
    Register Case, Perform Analysis, Perform Standard Review, Authorize Case
    ```
  - Standard review before analysis:
    ```text
    Register Case, Perform Standard Review, Perform Analysis, Authorize Case
    ```
  - Waiver after analysis:
    ```text
    Register Case, Perform Analysis, Record Review Waiver, Authorize Case
    ```
  - Waiver before analysis:
    ```text
    Register Case, Record Review Waiver, Perform Analysis, Authorize Case
    ```

- **Negative traces to regression-test for R1**
  - Waiver and authorization without analysis:
    ```text
    Register Case, Record Review Waiver, Authorize Case
    ```
    must be blocked.
  - Standard review and authorization without analysis:
    ```text
    Register Case, Perform Standard Review, Authorize Case
    ```
    must be blocked.
  - Analysis and authorization without a review outcome:
    ```text
    Register Case, Perform Analysis, Authorize Case
    ```
    must be blocked.
  - Double review outcomes, such as:
    ```text
    Register Case, Perform Analysis, Perform Standard Review, Record Review Waiver, Authorize Case
    ```
    must be blocked because the single review token has already been consumed.

- **Detecting accidental bypass of mandatory analysis**
  - For the model, add a regression test that replays all minimal source-to-sink traces and asserts that every trace containing `Authorize Case` also contains `Perform Analysis`.
  - For logs, use conformance checking or a temporal rule: each case with `Authorize Case` must have a prior `Perform Analysis` event.
  - Structurally, under R1, `t_authorize` can only become enabled through a join that consumes `p_analysis_done`. If a future edit removes the arc `p_analysis_done -> t_join_waived`, the regression test and soundness check should catch the bypass.

# 8. Final Recommendation

Deploy Repair R1: add the missing arc `p_analysis_done -> t_join_waived`. It is minimal under the stated edit-cost model and preserves the original business policy: analysis remains mandatory even when the review is waived. It prevents authorization before analysis and ensures the analysis-completion token is consumed on the waiver path, allowing the case to reach the exact final marking. It also keeps the standard-review and waiver activities distinguishable.

Use Repair R2 only as a fallback if the business explicitly changes the policy to allow a waiver to cancel mandatory analysis. R2 is also a one-arc repair and can be sound, but it changes semantics: waiver becomes possible only before analysis starts, and once analysis has started, standard review becomes required. It should not be deployed under the stated intent.

If the future requirement is “waiver may occur after analysis, but analysis is optional under waiver,” neither minimal repair is sufficient; implement a larger explicit OR-join or review-completed construction. Regardless of the selected repair, add regression tests for both valid interleavings and forbidden traces, especially waiver plus authorization without analysis.
