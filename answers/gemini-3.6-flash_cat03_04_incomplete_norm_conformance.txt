## 1. Conformance Semantics

Object-centric process mining (OCPM) requires evaluating execution traces, relational structures, and activity bindings against normative definitions that represent open-world operational rules rather than exhaustive process graphs. Standard conformance checking often treats missing model elements as explicit violations. In open-world norm evaluation, absence from a normative specification is not inherently noncompliant. To evaluate object-centric behavior accurately, we define seven distinct deviation classes:

```
                  
                            Observed Behavior              
                  
                                       
            
                                                                 
                               
  Explicitly Normed                                      Not Specified     
                               
                                                                  
                  
                                                                         
[Forbidden]     [Mandatory]          [Typical]     [Unexpected /       [Insufficient
 Violation       Evaluated           Evaluated     Unregulated]          Evidence]
                                        
                   
                                             
        [Missing      [Abstraction [Typical-  [Data-Quality
        Mandatory]     Mismatch]   Pattern     Error]
                                   Absence]
```

1. **Forbidden behavior**: An event, transition, or relation explicitly prohibited by a `forbidden` normative rule (e.g., N3, T6, E10). These represent hard compliance violations or operational system integrity failures.
2. **Missing mandatory behavior**: A relation or transition marked `mandatory` that is missing within its explicit scope (e.g., E2, E6), where no higher-level abstraction mismatch or missing attribute context explains the absence.
3. **Unexpected but unregulated behavior**: Relationships or transitions present in the logs but absent from the normative spec, falling under an `unspecified` scope or open-world assumption (e.g., N6, T4, T5, E9). These are permitted unless explicitly forbidden.
4. **Typical-pattern absence**: Deviations from `typical` rules (e.g., N2, N5, T3). Absence of a typical pattern indicates operational variation (e.g., write-offs, open credit) rather than noncompliance.
5. **Likely data-quality error**: Anomalies driven by ETL, key collisions, missing attributes, or bad data joins rather than actual physical process execution (e.g., E10 key reuse, missing E8 invoice link due to improper unapplied cash tagging).
6. **Abstraction mismatch**: A false nonconformance artifact where a directly-follows graph (DFG) misinterprets an eventually-follows requirement because intermediate unmodeled or optional activities occurred (e.g., N1 where `Manual Compliance Review` breaks directly-follows continuity).
7. **Insufficient evidence**: Observations where graph-level summaries cannot distinguish between a process violation, an unmodeled valid variant, or an attribute-logging gap without underlying trace-level event payloads.

### Closed-World vs. Open-World Assumptions

* **Closed-World Semantics** apply **strictly** to:
  * Relations explicitly marked `forbidden` (any observed occurrence is an immediate violation).
  * Mandatory event-to-object (ET–OT) bindings for specified event types (e.g., an `Add Item` event *must* bind to both `Order` and `Item`).

* **Open-World Semantics** apply to all unspecified relations and unmodeled graph topologies. The absence of an activity transition (e.g., `Validate Order -> Issue Invoice`) or an edge type (e.g., `Package object_codeath Delivery`) from the normative specification does not imply prohibition. Unmodeled behavior is treated as unregulated and permitted by default unless it infringes upon a forbidden constraint.

## 3. Detailed Reasoning by Model Family

```

                        MODEL FAMILY CAPABILITIES                       

        OC-DFG                   OTG                   ET–OT          

 • Activity Sequences   • Object Topological   • Event-to-Object      
   per Object Type        Interactions           Cardinality          
 • Directly-Follows     • Cobirth / Codeath    • Mandatory Object     
   Transitions            Relationships          Bindings per Event   

```

### OC-DFG (Object-Centric Directly-Follows Graph)

* **What it can establish**: OC-DFG isolates activity sequencing along the isolated timeline of each individual object type. It identifies direct activity-to-activity transitions (e.g., `Cancel Order -> Dispatch Package`) and evaluates them against mandatory, forbidden, or typical successor definitions.
* **What it cannot establish**: OC-DFG cannot evaluate object interaction cardinalities, cross-object lifecycle synchronization, or indirect (eventually-follows) dependencies. It cannot determine if an intermediate unmodeled event caused an apparent violation of a direct sequence.
* **Counts and scopes**:
  * *N3 Violation*: 2 instances of `Cancel Order -> Dispatch Package` are observed. Because N3 is **forbidden**, these represent explicit process violations where canceled orders resulted in physical shipments.
  * *N1 Abstraction Mismatch*: 98 of 100 newly created orders exhibit `Create Order -> Validate Order`. The 2 missing instances directly correlate with the 3 observed `Create Order -> Manual Compliance Review` events.
* **Abstraction Danger (Directly-Follows vs. Eventually-Follows)**:
  Interpreting an eventually-expected business rule (e.g., "Every order must eventually be validated") via a directly-follows abstraction creates false positives. If an order passes through an intermediate step—such as `Manual Compliance Review`—the directly-follows edge `Create Order -> Validate Order` is broken, even though the order conforms to the overarching business intent. Direct edges enforce immediate succession; using them for high-level business constraints conflates routing variations with process noncompliance.

### OTG (Object Topology Graph)

* **What it can establish**: OTG models static and dynamic structural relationships between object types, including interaction counts (`object_interaction`), joint creation (`object_cobirth`), and joint destruction (`object_codeath`).
* **What it cannot establish**: OTG cannot capture process execution order, activity context, event-level timing, or compliance with temporal business logic.
* **Counts and scopes**:
  * *T6 Violation*: 1 edge of `(Order, object_cobirth, Payment)` is observed. Because T6 is explicitly **forbidden**, this represents a structural compliance failure (order creation and payment receipt bound to the same birth event).
  * *T1 & T2 Compliance*: `(Order, object_interaction, Item)` (1450 edges) and `(Package, object_interaction, Delivery)` (200 edges) satisfy mandatory interaction requirements.
  * *Unregulated Edges*: `(Package, object_codeath, Delivery)` (7 edges), `(Order, object_interaction, Customer)` (100 edges), and `(Order, object_interaction, RiskCase)` (3 edges) are unmodeled in the norm. Under open-world assumptions, these are non-violating, legitimate operational interactions.

### ET–OT (Event Type to Object Type Graph)

* **What it can establish**: ET–OT establishes mandatory object entity presence during specific event executions. It ensures that an event is correctly bound to all required object instances (e.g., `Dispatch Package` must bind to both `Package` and `Delivery`).
* **What it cannot establish**: ET–OT cannot establish activity order, multi-step lifecycle requirements, or state-transition correctness.
* **Counts and scopes**:
  * *E10 Violation*: 1 instance of `Sensor Heartbeat -> Invoice` is observed. Explicitly **forbidden**, this represents a severe relational error (telemetry stream linked to financial entities).
  * *E6 Violation / Missing Mandatory*: 200 `Dispatch Package` events occurred, with 200 `Package` bindings (E5 compliant), but only 198 `Delivery` bindings observed (E6). Two dispatch events failed the mandatory object edge requirement.
  * *E2 Missing Mandatory*: 1450 `Add Item` events bound to `Item` (E3 compliant), but only 1448 bound to `Order` (E2). Two events lack mandatory order context.
  * *E8 Absence / Data Quality*: 93 `Record Payment` events yielded 93 `Payment` bindings (E7 compliant) but only 92 `Invoice` bindings. Because these events were not typed as `unapplied cash`, this violates mandatory rule E8 unless reclassified.

## 5. PM4Py Conformance Code Sketch

```python
import pm4py
from pm4py.objects.ocel.obj import OCEL


def evaluate_ocpm_conformance(ocel: OCEL, norm_ocdfg: dict, norm_otg: tuple, norm_etot: tuple):
    """Evaluates Object-Centric Process Mining conformance against normative definitions

    preserving raw PM4Py outputs and superimposing open-world semantics.
    """
    # 1. RAW PM4PY DISCOVERY
    discovered_ocdfg = pm4py.discover_ocdfg(ocel)
    discovered_otg = pm4py.discover_otg(ocel)
    discovered_etot = pm4py.discover_etot(ocel)

    # 2. RAW PM4PY CONFORMANCE DIAGNOSTICS
    # PM4Py raw functions output structural graph differences without business semantics
    raw_diag_ocdfg = pm4py.conformance_ocdfg(discovered_ocdfg, norm_ocdfg)
    raw_diag_otg = pm4py.conformance_otg(discovered_otg, norm_otg)
    raw_diag_etot = pm4py.conformance_etot(discovered_etot, norm_etot)

    # 3. SEMANTIC CLASSIFICATION LAYER
    # Normative metadata MUST be maintained outside standard graph data structures
    # Metadata maps edges/bindings to status: 'mandatory', 'forbidden', 'typical', 'unspecified'
    norm_meta = {
        "forbidden_ocdfg": [("Cancel Order", "Dispatch Package", "Order")],
        "forbidden_otg": [("Order", "object_cobirth", "Payment")],
        "forbidden_etot": [("Sensor Heartbeat", "Invoice")],
        "mandatory_etot": [
            ("Add Item", "Order"),
            ("Dispatch Package", "Delivery"),
            ("Record Payment", "Invoice"),
        ],
        "typical_ocdfg": [
            ("Validate Order", "Close Order", "Order"),
            ("Issue Invoice", "Record Payment", "Invoice"),
        ],
    }

    semantic_findings = {
        "forbidden_violations": [],
        "missing_mandatory": [],
        "typical_variances": [],
        "unregulated_allowed": [],
        "abstraction_mismatches": [],
    }

    # Evaluate OC-DFG Observed Edges
    # PM4Py discovered_ocdfg contains edges as keys: (act1, act2, obj_type)
    for edge, count in discovered_ocdfg.get("edges", {}).items():
        act1, act2, ot = edge
        if (act1, act2, ot) in norm_meta["forbidden_ocdfg"]:
            semantic_findings["forbidden_violations"].append(
                {
                    "layer": "OC-DFG",
                    "edge": edge,
                    "count": count,
                    "rule": "N3 Violation",
                }
            )
        elif edge not in norm_ocdfg.get("edges", {}):
            # Open-world evaluation: Unmodeled edges are unregulated, not violations
            semantic_findings["unregulated_allowed"].append(
                {"layer": "OC-DFG", "edge": edge, "count": count}
            )

    # Evaluate ET-OT Observed Bindings
    # discovered_etot maps (event_type, object_type) -> count
    for binding, count in discovered_etot.items():
        ev_type, obj_type = binding
        if (ev_type, obj_type) in norm_meta["forbidden_etot"]:
            semantic_findings["forbidden_violations"].append(
                {
                    "layer": "ET-OT",
                    "binding": binding,
                    "count": count,
                    "rule": "E10 Violation",
                }
            )

    # Evaluate Mandatory Gaps (Comparing Expected Counts vs Discovered)
    # Example checking E6: Dispatch Package -> Delivery
    dispatch_count = sum(
        c
        for b, c in discovered_etot.items()
        if b[0] == "Dispatch Package" and b[1] == "Package"
    )
    delivery_dispatch_count = discovered_etot.get(
        ("Dispatch Package", "Delivery"), 0
    )

    if delivery_dispatch_count < dispatch_count:
        gap = dispatch_count - delivery_dispatch_count
        semantic_findings["missing_mandatory"].append(
            {
                "layer": "ET-OT",
                "rule": "E6",
                "missing_count": gap,
                "context": "Dispatch Package missing Delivery object context",
            }
        )

    # Return raw diagnostics alongside the interpreted business findings
    return {
        "raw_pm4py_diagnostics": {
            "ocdfg": raw_diag_ocdfg,
            "otg": raw_diag_otg,
            "etot": raw_diag_etot,
        },
        "semantic_interpretation": semantic_findings,
    }
```

## 6. Norm-Completeness Assessment

```

                      NORM-COMPLETENESS ASSESSMENT                      

 Norm Gap / Ambiguity   Operational Risk       Proposed Status        

 1. Direct vs. Event.   False nonconformance   Mandatory              
 2. Unapplied Cash      Financial misclass.    Typical                
 3. Attribute-Delivery  System friction        Mandatory (Refined)    
 4. Codeath Definition  Lifecycle leakage      Typical                
 5. Write-Off Pathways  Audit noise            Typical                
 6. Sensor Isolation    Security bypass        Forbidden              

```

1. **Abstraction Gap: Direct vs. Eventually-Follows for N1 (`Create Order -> Validate Order`)**
   * *Operational Risk*: Misinterpreting valid compliance reviews as workflow failures, leading to incorrect performance penalties.
   * *Proposed Clarification*: Redefine N1 to specify that `Create Order` must *eventually* be followed by `Validate Order` within the Order lifecycle, allowing intermediate compliance/review activities.
   * *Status*: **Mandatory** (Eventually-follows).

2. **Attribute-Based Conditional Scope for E8 (`Record Payment -> Invoice`)**
   * *Operational Risk*: False positive compliance alerts generated when unapplied cash payments are recorded without invoice linkages.
   * *Proposed Clarification*: Expressly exempt payment events where attribute `payment_type == 'unapplied_cash'` from mandatory invoice binding.
   * *Status*: **Typical** (Conditional exception).

3. **Fallback Rule for E6 (`Dispatch Package -> Delivery`)**
   * *Operational Risk*: Operational blockage where physical shipments with valid carrier references in log attributes are rejected for lacking an explicit Delivery relational entity.
   * *Proposed Clarification*: `Dispatch Package` must bind to a `Delivery` object *or* contain a non-null `carrier_tracking_ref` event attribute.
   * *Status*: **Mandatory** (Refined definition).

4. **Lifecycle Co-Termination (`Package object_codeath Delivery`)**
   * *Operational Risk*: Unmonitored asynchronous object termination leading to orphan delivery objects remaining active in systems after package destruction/receipt.
   * *Proposed Clarification*: Define explicit `object_codeath` expectations between `Package` and `Delivery` upon execution of `Confirm Delivery`.
   * *Status*: **Typical**.

5. **Financial Edge Completeness for Billing (`Validate Order -> Issue Invoice` and `Write Off`)**
   * *Operational Risk*: Unmonitored revenue leakage where validated orders bypass billing without triggering compliance alerts.
   * *Proposed Clarification*: Incorporate `Validate Order -> Issue Invoice` as a normative sequence, and explicitly declare `Issue Invoice -> Write Off` as an acceptable alternative path for bad debt.
   * *Status*: **Typical**.

6. **System Scope Boundaries for Telemetry (`Sensor Heartbeat`)**
   * *Operational Risk*: Cross-domain data contamination where IoT streams overwrite or corrupt transactional audit trails.
   * *Proposed Clarification*: Explicitly state that `Sensor Heartbeat` events are forbidden from binding to *any* financial or sales entity (`Invoice`, `Order`, `Payment`).
   * *Status*: **Forbidden**.

3. **Mandatory Binding Gaps (Findings 4 & 5)**: Quarantine the 2 `Dispatch Package` events lacking delivery bindings and 2 `Add Item` events lacking order bindings to prevent downstream billing errors.

1. **Financial Event Reclassifying (Finding 6)**: Audit the 1 `Record Payment` event lacking an invoice binding. If verified as unapplied cash, update the event log attribute `payment_type = 'unapplied_cash'`.

### Phase 4: Norm Revision

2. **Scope Inclusion**: Update the normative spec to include `Validate Order -> Issue Invoice` as a typical transition and formalize `Package object_codeath Delivery`.

### Phase 5: Monitoring

The evaluation of this process snapshot yields the following boundaries of certainty:

* **Robust Conclusions**: 
  1. The 2 occurrences of `Cancel Order -> Dispatch Package` represent severe, unambiguous process violations (N3) that present immediate operational and financial risk.
  2. The single `(Order, object_cobirth, Payment)` edge is a structural violation of T6.
  3. The vast majority of standard operations (98/100 order validations, 198/200 package dispatches, 92/110 invoice payments) conform fully to expected business execution.

* **Conclusions Contingent on Norm Incompleteness**:
  1. The 72 `Validate Order -> Issue Invoice` transitions, 3 `Manual Compliance Review` workflows, and 7 `Package-Delivery codeath` events are classified as conforming, unregulated behavior solely due to the open-world assumption. If the norm is subsequently revised to closed-world, these paths would require formal model inclusion.
  2. The 2 missing direct `Create Order -> Validate Order` sequences are confirmed to be abstraction artifacts rather than noncompliant order handling, contingent on accepting eventually-follows semantics for N1.

* **Conclusions Contingent on Suspected Data-Quality Issues**:
  1. The `Sensor Heartbeat -> Invoice` relation (E10) cannot be conclusively proven as a malicious activity or system failure from graph data alone; it strongly exhibits the profile of an ETL numeric primary key join collision.
  2. The missing `Record Payment -> Invoice` binding (E8) and 2 missing `Dispatch Package -> Delivery` bindings (E6) depend on whether unparsed event attributes (unapplied cash flags, carrier tracking numbers) are accepted as valid object surrogates.

* **Unresolvable from Graph Summaries Alone**:
  Graph-level summaries cannot resolve whether the 2 unlinked `Add Item` events represent active customer session updates or orphaned transaction rollbacks, nor can they confirm whether physical inventory was lost in the 2 cancelled order dispatches without direct inspection of trace payloads, system transaction logs, and physical inventory audits.
