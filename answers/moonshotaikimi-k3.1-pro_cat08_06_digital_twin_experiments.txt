# 1. Model scope and state variables

## Boundary and modeling approach

The twin should be a **stochastic, discrete-event, resource-constrained simulation**, not a process model with independently sampled end-to-end durations. It should support two modes:

1. **Historical/nowcasting mode:** initialize from observed arrivals, open cases, backlog, resource calendars, and in-progress branches. This supports validation and short-term operational forecasts.
2. **What-if mode:** generate demand and case attributes, apply a policy scenario, and compare interventions against a paired baseline.

The main boundary is portal submission through permit issue or rejection, including in-scope inspection, legal, planning, and appeal-driven rework. For D1, the boundary should optionally begin at **application-ready/pre-submission work**, so that faster municipal processing cannot conceal additional applicant effort or delayed portal submission. Initial-decision time and time-to-final-resolution after appeal should be reported separately.

Out of scope are construction execution, detailed document contents, and emergency decisions removed from the log. Results should therefore not be generalized to emergency permitting without additional data.

Two clocks are necessary:

- **Elapsed/calendar time** for applicant responses, statutory notice periods, objection extensions, holidays, and end-to-end durations.
- **Municipal working time** for resource service, queues, shifts, and calendar-dependent capacity.

## Process representation

A case may have several active branches, so a single `current_activity` field is insufficient. The statechart should represent:

- Repeated completeness checks and missing-document loops.
- Planning review with conditional fire and environmental branches, potentially overlapping in time.
- Optional public notice with a statutory minimum and a separate, latent objection-extension mechanism.
- Inspection scheduling, geographic batching, applicant readiness, no-shows, travel, and inspection rework.
- Decision drafting enabled only when every applicable review, notice, and inspection result is available in the required version.
- Optional legal check, planning/legal/inspection rework, and appeal-driven reopening.
- Issue or rejection.

The supplied process tree is a useful control-flow sketch, but not a complete executable specification. In particular, it omits some stated rework paths, and the excerpt repeats `Completeness check` without recording `Completeness rework`. The latter should be treated as an abstract loop-back unless domain staff confirm that it is a real activity.

## Resources, queues, and calendars

The baseline capacity model should include:

- **Clerks:** 5 FTE, Monday–Friday 08:00–16:00. On Mondays, one clerk is dedicated to portal support, leaving at most four for other clerk work.
- **Planners:** 8 FTE, Monday–Friday 09:00–17:00. Two are Simple-renovation-only; the skill matrix must specify which planners can perform planning review and decision drafting for each case type.
- **Fire reviewers:** 2 FTE-equivalent, Tuesday–Thursday only.
- **Environmental reviewers:** 3 FTE, but centrally only about 60% of their time is available for permit work. Non-permit duties should reduce calendar capacity rather than merely inflate service times.
- **Inspectors:** 4 FTE, field visits Tuesday–Friday. Travel occupies inspector capacity and depends on district and routing, with longer D3/D5 travel.
- **Legal officers:** 2 FTE, unavailable for ordinary work during council-meeting weeks, with an explicit urgent-case exception.
- **System tasks:** effectively unlimited capacity, although scheduled automation delays may still exist.
- **Inspection schedulers:** capacity is not specified. It should be estimated or treated as an explicit sensitivity assumption rather than silently assumed infinite.

Each activity queue starts when the case is genuinely ready, not simply when the preceding logged event completed. Baseline queue discipline can begin as role-specific FIFO with documented exceptions; appointment, batching, aging, and legal-pre-check policies then modify it. Waiting should emerge from demand, service, calendars, and scheduling decisions.

## Cross-case dependencies

The simulation should explicitly couple cases through:

1. **Architect submission sessions:** related applications arrive in bursts, with correlated attributes and potentially correlated applicant behavior.
2. **Shared municipal resources:** all cases compete for the same role-specific calendars and skill pools.
3. **Geographic objection clusters:** related public-notice cases may share a latent objection propensity or random effect, without requiring identical durations.
4. **Inspection bundling:** only ready and compatible cases can be bundled. Batching reduces travel but may delay the first case, and one no-show can affect the route.
5. **Decision synchronization:** a case waits for its applicable parallel branches; one delayed environmental or legal result can block downstream work.

A practical twin would refresh its open-case snapshot and recent parameters weekly or nightly, version the calibration, and monitor drift. What-if runs should use a frozen snapshot and parameter version so that policy comparisons are reproducible.

# 2. Parameter-estimation plan

## Log and model handling with PM4Py

Use the full 18-month log for estimation; the two-case excerpt is only a software smoke test.

1. Read CSV data with pandas, parse timestamps, standardize time zones, check duplicate events, and preserve repeated activity instances.
2. Use `pm4py.format_dataframe` with the supplied case, activity, and timestamp keys, followed by `pm4py.convert_to_event_log`.
3. Use PM4Py variants to quantify common paths and repeated-activity patterns.
4. Use the DFG for structural diagnostics and the performance DFG for descriptive directly-follows timing.
5. Parse the supplied tree where supported and compare it with aligned log behavior. Token replay or alignments can identify unexplained repetitions, skipped branches, and deviations.
6. Use PM4Py again on simulated event logs so that simulated and historical behavior can be compared with the same diagnostics.

A performance-DFG edge time is generally an aggregate elapsed time between directly following events. It is **not automatically activity service time or queue waiting time**, especially with parallel branches and off-log applicant delays.

## Arrivals and case attributes

Estimate a marked, non-stationary arrival process rather than one exponential interarrival distribution:

- Start with submission timestamps and estimate a baseline intensity by month/season, weekday, hour, holiday proximity, and any evident trend or policy regime.
- Treat the given 1.7 seasonal multiplier and Monday/Wednesday ratio of 2.2 as strong descriptive constraints to check, not necessarily permanent coefficients. Eighteen months provides limited repetition of annual seasonality.
- Test a non-homogeneous Poisson model against overdispersed alternatives. If daily counts remain overdispersed, use a negative-binomial/Cox formulation or an empirical block model.
- Represent large architects separately as **submission-session processes**: session arrival, number of cases per session, within-session timing, and joint case attributes. The top-20 architects’ 31% share and same-week bursts should be reproduced.
- Sample case type, district, architect, value, routing flags, and related-case group from an empirical joint or hierarchical model. Independent marginal sampling would destroy important correlations.
- Retain an empirical/block-bootstrap alternative, resampling whole architect-weeks or calendar weeks, to preserve bursts and serial dependence.

The PM4Py case-arrival average is a descriptive statistic only and should not parameterize this arrival process.

## Routing, branching, and rework

- Estimate the probability and number of completeness loops by case type, architect, and other observable attributes.
- Use observed variants, activity presence, and alignments to estimate fire, environmental, public-notice, legal, and final-decision routing.
- Use hierarchical logistic models or smoothed empirical probabilities to avoid unstable estimates for rare case-type/district combinations.
- For fire routing, condition on `requires_fire`; separately bound or multiply impute the unobserved building-area threshold. For environmental routing, distinguish observed requirements from incomplete district sensitivity.
- Estimate public-notice probability separately from objection behavior. Complex variance and New residential require different models.
- Identify rework from repeated stages and model-specific subsequences, not merely from variant names. Estimate stage-specific rework hazards and loop counts by case type, age, and relevant attributes.
- Specify which results are invalidated by each rework type. For example, planning rework may require only repeated planning work in some cases but may invalidate dependent reviews in others.
- Use unstructured rework text only after a reliable human-coded sample is available. Until then, rework mechanisms and intervention effects should remain uncertain.

Rare “other” variants should be represented by a smoothed exception model or empirical trace templates, not discarded.

## Service time, waiting time, and external delays

For an activity instance, distinguish:

- `ready_time`: all control-flow and external prerequisites are satisfied;
- `start_time`: municipal work actually begins;
- `end_time`: work completes;
- service work, calendar blocking, queue waiting, and post-completion blocking.

Where start and completion timestamps exist:

1. Calculate raw service elapsed time and convert it to working time using the appropriate calendar.
2. Fit activity-specific distributions conditional on case type, district, resource group, and relevant case attributes.
3. Compare empirical, lognormal, gamma, Weibull, and mixture models using quantiles and holdout predictive performance. The supplied medians and p90s are constraints for fitting and validation, not sufficient distribution estimates by themselves.
4. Include case-complexity and, where supported, architect/district random effects so that activities within a difficult case are not implicitly independent.

Waiting should normally be an **emergent simulation output**. Historical waiting estimates are used to infer queue discipline, calibrate unresolved capacity assumptions, and validate the baseline. Sampling both historical waiting and resource-queue waiting would double count delay.

With completion-only timestamps, service and waiting are not uniquely identifiable. The analysis should:

- Use the subset with reliable lifecycle timestamps and targeted time studies where possible.
- Use the empirical service summaries as informative constraints.
- Treat `end_time - ready_time` as a composite of waiting, service, and calendar blocking.
- Estimate plausible decompositions through multiple imputation or bounded calibration, including a missingness model because missing starts may depend on resource or activity.
- Carry alternative decompositions into sensitivity analysis rather than reporting one precise split.

Special handling is required for:

- **Applicant document response:** request-to-receive elapsed time, modeled separately from municipal queues and calendars.
- **Environmental consultant reports:** third-party delay where applicable, distinct from reviewer service.
- **Public notice:** statutory timer plus possible extension, not an ordinary staffed service activity.
- **Inspection:** service, travel, applicant readiness, and no-shows as separate components.
- **Decision drafting:** ready only at the required synchronization point.

## Calendars and utilization

Reconstruct role-specific capacity by day or shift from the HR calendars, including holidays, council weeks, fire-review days, environmental non-permit reservations, and inspector field days. Validate the activity-to-role and skill mappings with operations staff.

Utilization should be calculated as municipal busy hours divided by hours actually available for permit work. Completion-only event data cannot provide a reliable standalone estimate of historical utilization, so HR capacity, workload samples, and independent operational records are needed.

## Dependencies and missing objections

Estimate architect-session and inspection-related dependency structure from case attributes and timestamps, while recognizing that the flattened log may understate it. Supplement with architect, geographic, inspection-route, and objection-register data if available.

For objections, use a latent-variable or scenario model. A mixture of short, near-minimum notices and long notices may inform plausible parameter ranges, but it does not identify objection prevalence uniquely. Long durations must not be relabeled as observed objections. D9 should therefore be evaluated under low, central, and high objection/extension assumptions.

# 5. Warm-up, replications, and uncertainty treatment

## Initialization, warm-up, and horizon

Because demand and calendars are non-stationary, there is no single steady-state warm-up that is appropriate for every start date.

- **Preferred approach:** initialize from an observed WIP snapshot, including each open case’s completed branches, current ready state, age, public-notice status, and outstanding external responses.
- **If no snapshot exists:** use a central 12-month spin-up ending on the same calendar date as the evaluation start, with 6- and 18-month sensitivity runs. Initialize backlog and resource queues from the spin-up, not from an empty system.
- Assess warm-up using backlog volume and age profile, queue waits, utilization, and completion-cohort behavior. Stable mean throughput alone is insufficient.
- Use at least a 12-month evaluation horizon to cover the seasonal cycle, followed by up to 12 months of completion follow-up for long Complex variance and appeal cases.
- Do not discard long cases merely because they began during warm-up or remain open at the end. Report mature arrival cohorts, end-of-horizon backlog, and censored durations. Survival estimates can complement complete-case results.

## Replications and seeds

- Begin with approximately 40 paired replications per scenario and increase sequentially, potentially to 100–200 for tail-sensitive comparisons.
- Stop when precision is adequate, for example: roughly ±2 days or ±3% for the primary median, ±5–8 days or ±5–10% for p90, and ±1 percentage point for major SLA differences. These are illustrative targets and may be relaxed for rare, highly variable strata.
- Use independent replication seeds, with named random streams for arrivals, attributes, service, routing, applicant responses, dependencies, and policy-specific noise.
- Use common random numbers for baseline/intervention pairs. Analyze paired effects so that a favorable random arrival week is not mistaken for policy benefit.
- Store seeds, calendar versions, parameter draws, scenario definitions, and code versions. Do not select a seed because it produces a desirable ranking.

For conditional Monte Carlo error, report 95% confidence intervals. Paired replication bootstrap intervals are useful for quantiles and other non-normal metrics. If Bayesian parameter models are used, distinguish posterior credible intervals from these confidence intervals.

## Parameter uncertainty and sensitivity

Separate three kinds of uncertainty:

1. **Case-level variability:** different applicants and cases experience very different outcomes; report prediction intervals and distributional results.
2. **Monte Carlo error:** uncertainty from a finite number of simulation replications.
3. **Parameter/model uncertainty:** uncertain service/wait decomposition, seasonality, missing routing attributes, calendars, objections, and dependencies.

Propagate the third category using outer parameter draws and inner replications. Block-bootstrap weeks and architect clusters rather than independent events, and repeat results across multiple imputations. Where no posterior model is used, call the resulting intervals bootstrap or scenario-uncertainty intervals, not credible intervals.

Sensitivity analysis should include:

- Service-time scale and case-complexity correlation.
- Missing-start decompositions and actual permit-duty capacity.
- Arrival overdispersion, seasonal multipliers, and architect burst size.
- Rework and no-show probabilities.
- Fire-area and environmental-sensitivity imputation.
- Objection prevalence, extension tail, and D9 effectiveness.
- D1 false-clear/applicant effort, D2 eligibility and quality effect, and D3 batching waits.
- Understated cross-case dependence.

A practical sequence is one-at-a-time diagnostic checks, Morris or Latin-hypercube screening, and more detailed global or break-even analysis for influential parameters. Report whether intervention rankings change.

## Heavy-tailed durations

Do not use normal approximations based only on mean and standard deviation. Applicant response, public-notice extension, environmental delay, and complex appeal/rework paths may require empirical tails, mixtures, or lognormal/heavier-tailed models. Avoid arbitrary truncation or baseline winsorization; trimmed-tail scenarios may be shown only as sensitivity analyses. Emphasize medians, p90/p95, SLA exceedance, backlog age, and uncertainty around those quantities.

| **Face validation** | Walk clerks, planners, inspectors, legal officers, environmental staff, and permit applicants’ representatives through state diagrams, calendars, queues, and sample simulated traces. Specifically confirm branch release rules, decision synchronization, rework invalidation, batching feasibility, council-week behavior, and the legal/safety constraints of D2, D8, and D9 |
| **Event-log replay validation** | Align historical traces to the reference/extended model and quantify unexplained skips, repetitions, and ordering deviations. Replay simulated traces in the same way. Check that simulated logs do not contain impossible orders or missing mandatory branches. Parsing the tree or obtaining high fitness alone is not timing validation |
| **Distributional validation** | Compare arrivals, case mix, architect bursts, variant frequencies, completeness-loop counts, branch probabilities, service-time subsets, activity-to-activity elapsed times, case duration median/p90/p95, SLA rates, rework, rejection, and open-case censoring. Stratify by case type, major variant, district, and season. Use QQ plots and tail comparisons in addition to averages |
| **Resource-utilization validation** | Compare simulated busy hours and capacity with HR availability, time studies, inspection visit counts, overtime, and any independent workload records. Check Monday clerk capacity, Tuesday–Thursday fire work, environmental permit availability, and legal council closures. Completion-only timestamps cannot independently prove utilization validity |
| **Bottleneck validation** | Reproduce Monday clerk spikes, planning queues by case type/district, environmental/legal interaction, inspection peak backlog, and calendar-driven legal delays. Examine whether the simulated bottleneck shifts in the same circumstances staff describe. Use backlog, queue age, and WIP as well as waiting time |
| **Dependency validation** | Compare architect-week session sizes, same-week related applications, bundle sizes, travel per visit, and waiting-versus-travel trade-offs. Validate objection-cluster assumptions externally if possible; otherwise label them unvalidated scenarios |
| **Out-of-sample validation** | A reasonable initial split is the first 12 months for calibration and the last 6 for temporal testing, supplemented by rolling-origin tests and district/architect holdouts. Never tune on the final holdout. Test both a conditional simulation using observed arrivals/calendars and a fully generative simulation |

Illustrative calibration targets—subject to sample size and municipal agreement—might be common-variant shares within 2–3 percentage points, major case-type medians within 5–10%, p90 within 10–20%, and independently measured utilization within 5–10 percentage points. Complex tails and poorly observed quantities need wider intervals. Failure on an important tail or bottleneck should not be hidden by good aggregate fitness.

Counterfactual interventions cannot be fully validated against the baseline log. Their mechanisms should be validated through pilots, phased implementation, or expert review, followed by recalibration. The twin should not be declared valid for emergency cases, observed objections, or precise resource utilization where the required data do not exist.

# 7. Decision criteria

For each case, report both:

- \(T_{\text{portal}}\): portal submission to initial decision and, separately, to final resolution.
- \(T_{\text{total}}\): application-ready/pre-submission start to final resolution, including D1 applicant effort where relevant.

Also report service/touch time, municipal queue waiting, applicant/third-party delay, and calendar/statutory delay separately.

| Metric group | Decision measures and guardrails |
|---|---|
| **Duration and SLA** | Median, p90, and p95 by case type and major variant; SLA compliance against municipality-defined case-type targets; time spent beyond SLA; initial-decision and final-resolution measures |
| **Backlog and flow** | Completions, open WIP, backlog volume and age profile, oldest-case age, peak backlog, and weeks required to return to the pre-peak backlog/age range |
| **Quality and rework** | Completeness loops, planning/inspection/legal rework, no-shows, appeals, rejection, false-clear or false-triage outcomes where modeled, and additional review effort |
| **Resources and cost** | Utilization by role and week, peak queue load, travel hours, overtime/temporary-staff cost, cost per completed case, and cost per additional SLA-compliant case or day of p90 reduction |
| **Fairness** | Case-mix-adjusted duration and SLA by district, including D3/D5; top-20 versus other architects; appointment-slot access; batching delay for sparse districts; and outcomes for small/simple applicants |
| **Robustness** | Effects under parameter draws and S1–S5, probability of achieving a practical benefit, worst credible backlog/SLA outcome, and sensitivity of rankings to stakeholder weights |

A possible selection rule, to be agreed before seeing rankings, is:

1. **Hard gates:** no violation of statutory notice, legal review, safety, or environmental requirements. D2 cannot be operationally recommended without reliable violation-history eligibility and an accepted risk framework.
2. **Practical effectiveness:** for a targeted intervention, look for approximately a 5–10% median improvement or 10–15% p90 improvement, or an SLA gain of at least several percentage points, with an uncertainty interval that does not indicate a trivial effect. These are screening ranges, not universal laws.
3. **No material harm:** for example, investigate if a non-target case type loses more than about 2 SLA percentage points, its p90 rises more than 5%, rework rises by more than 1 percentage point or 5% relative, or a district/architect fairness gap worsens materially.
4. **Capacity and recovery:** avoid policies that leave a critical pool above roughly 85–90% of available capacity for sustained periods without backlog recovery, or above 95% during prolonged peaks. Utilization is a warning measure, not something to maximize.
5. **Robust value:** prefer interventions with positive practical benefit in most parameter draws and no hard-gate failure under stress. Examine performance at both 80% and 90% probability-of-benefit requirements to show ranking sensitivity.
6. **Portfolio choice:** present cost, equity, risk, and performance on a Pareto frontier. D10 should be selected only if its joint simulated benefit justifies its combined cost and implementation risk, not because individual benefits appear additive.

The result should be a defensible shortlist and implementation/pilot plan, not a claim of exact optimality.

def load_and_format_log(csv_text: str):
    """Use pandas for CSV I/O, then PM4Py for formatting/conversion."""
    raw = pd.read_csv(StringIO(csv_text))
    raw[TS] = pd.to_datetime(raw[TS], errors="raise")

    frame = pm4py.format_dataframe(
        raw,
        case_id=CASE,
        activity_key=ACT,
        timestamp_key=TS,
    )
    frame = frame.sort_values([CASE, TS], kind="stable").reset_index(drop=True)
    event_log = pm4py.convert_to_event_log(frame)
    return frame, event_log


def add_timing_columns(frame: pd.DataFrame) -> pd.DataFrame:
    """
    Add only identifiable timing quantities.

    The excerpt has one timestamp per event, so service and actual waiting
    remain unknown. If start:timestamp and ready:timestamp are available,
    raw service and waiting can be calculated. Calendar adjustment and
    parallel-branch ready-time construction belong in the estimation pipeline.
    """
    out = frame.sort_values([CASE, TS], kind="stable").copy()
    out["previous_case_event_timestamp"] = out.groupby(CASE)[TS].shift()
    out["elapsed_since_previous_event_s"] = (
        out[TS] - out["previous_case_event_timestamp"]
    ).dt.total_seconds()

    out["service_time_s"] = np.nan
    out["waiting_time_s"] = np.nan
    out["start_minus_previous_completion_s"] = np.nan

    if "start:timestamp" in out.columns:
        starts = pd.to_datetime(out["start:timestamp"], errors="coerce")
        out["service_time_s"] = (out[TS] - starts).dt.total_seconds()

        # Descriptive proxy only: invalid as true waiting on parallel paths.
        out["start_minus_previous_completion_s"] = (
            starts - out["previous_case_event_timestamp"]
        ).dt.total_seconds()

        # A proper ready/queue timestamp makes the queue-wait calculation possible.
        ready_col = next(
            (c for c in ("ready:timestamp", "queue:timestamp")
             if c in out.columns),
            None,
        )
        if ready_col is not None:
            ready = pd.to_datetime(out[ready_col], errors="coerce")
            out["waiting_time_s"] = (starts - ready).dt.total_seconds()

    return out


def parse_reference_tree(text: str):
    parser = getattr(pm4py, "parse_process_tree", None)
    if parser is None:
        print(
            "This PM4Py version has no top-level parse_process_tree. "
            "Retain the text as a reference and construct/validate a tree "
            "with a supported PM4Py importer; do not simulate from the DFG."
        )
        return None

    try:
        return parser(text)
    except Exception as exc:
        # Do not silently replace the reference model with a discovered model.
        print(f"Reference tree not parsed: {exc}")
        print(
            "The string is simplified: it omits planning/legal/appeal paths "
            "and uses an abstract completeness-rework label."
        )
        return None

class DigitalTwinEngine:
    def __init__(
        self,
        parameters: TwinParameters,
        arrivals: ArrivalGenerator,
        router: Router,
        scheduler: CalendarResourceScheduler,
    ):
        self.parameters = parameters
        self.arrivals = arrivals
        self.router = router
        self.scheduler = scheduler

    def run(self, scenario: Scenario, seed: int) -> dict[str, Any]:
        # Named streams support common random numbers without letting a new
        # policy consume and alter every baseline random-number sequence.
        root = np.random.SeedSequence(seed)
        stream_names = (
            "arrivals",
            "attributes",
            "service",
            "routing",
            "responses",
            "dependencies",
            "policy_specific",
        )
        streams = dict(zip(stream_names, root.spawn(len(stream_names))))
        arrival_rng = np.random.default_rng(streams["arrivals"])

        # The full implementation would:
        # 1. Load the WIP snapshot or spin up initial backlog.
        # 2. Generate application-ready demand and portal submission behavior.
        # 3. Advance case branch tokens and external elapsed-time timers.
        # 4. Schedule municipal work through CalendarResourceScheduler.
        # 5. Create latent objection scenarios without logging them as observed.
        # 6. Emit case outcomes plus start/complete/ready event DataFrames.
        _ = arrival_rng
        raise NotImplementedError(
            "Connect a discrete-event kernel; return simulated events, "
            "case metrics, queue/backlog series, and resource utilization."
        )


class ExperimentRunner:
    def __init__(self, engine: DigitalTwinEngine):
        self.engine = engine

    def run_paired(
        self,
        scenarios: list[Scenario],
        n_replications: int,
        base_seed: int = 20260301,
    ) -> pd.DataFrame:
        rows = []
        replication_seeds = np.random.SeedSequence(base_seed).spawn(
            n_replications
        )

        for replication, seed_sequence in enumerate(replication_seeds):
            # Same exogenous seed for every scenario in this replication.
            rep_seed = int(
                seed_sequence.generate_state(1, dtype=np.uint32)[0]
            )
            for scenario in scenarios:
                output = self.engine.run(scenario, seed=rep_seed)
                rows.append(
                    {
                        "replication": replication,
                        "scenario": scenario.name,
                        "seed": rep_seed,
                        "output": output,
                    }
                )

        # A reporting layer should compute paired effects and uncertainty
        # intervals rather than treating the object column as final results.
        return pd.DataFrame(rows)
