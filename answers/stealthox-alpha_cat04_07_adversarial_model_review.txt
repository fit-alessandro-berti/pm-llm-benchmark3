# 1. Review Scope and Assumptions

**Submission context.** Two candidate models were discovered from a control-flow-only event log that lacks the `external/internal` sourcing attribute (P3) and the `affected check` attribute (P6). All reported metrics are **unaudited evidence**: no seeds, no preprocessing code, no alignment-cost settings, and no held-out case identifiers were published. I treat the stakeholder policy statements P1–P7 and the probe assessments B1–B8 as the governing specification, and the metrics as signals to be interrogated, not scores to be maximized.

**Use cases distinguished.** The acceptable fitness/precision trade-off is use-case-relative, and the board must decide per use case, not in aggregate:

| Use case | Dominant risk | Fitness role | Precision role | Gating criterion |
|---|---|---|---|---|
| Exploration / hypothesis generation | Misleading structure | High weight | Low weight | Soundness + holdout fitness floor |
| Stakeholder communication | False consensus | Moderate | Moderate | Documented comprehension test |
| Conformance monitoring (human review of flags) | Alert fatigue / blind spots | Balanced | Balanced, incl. negatives | Calibration of flag rates |
| Compliance enforcement (hard gate) | Fail-open admissions | Floor only | **Specificity on forbidden behavior is gating** | Zero admissions of forbidden traces |
| Simulation / what-if | Unrealistic dynamics | Low | Low | Attribute and resource fidelity |

Under this lens: Model S is defensible only for exploration; Model C is defensible only as a fail-closed interim control; neither is adequate for enforcement as submitted. A model that scores well on aggregate metrics but admits forbidden behavior (S) or rejects policy-valid behavior (C) fails the enforcement gate regardless of its averages. I compute **no weighted aggregate score** anywhere in this review; where a decision rule is needed I use lexicographic gating (Section 9, E10).

**Semantic assumptions used throughout.** Model S's `+` is read as PM4Py's parallel/partial-order composition over four `X(activity, tau)` blocks: each of Credit Check, Technical Review, Supplier Review, Expedite Review may occur **zero or one time, in any interleaving**, between Register Dossier and the approval XOR. An empty-edge `StrictPartialOrder` reading yields the same acceptance set; a *sequential* reading of `+` would contradict standard process-tree operator semantics and the discovery team's own fitness claims, so it is rejected. Model C is an XOR over eight fixed sequences; acceptance is exact membership. These readings are stated precisely so the probe matrix in Section 5 is reproducible.

# 3. Adversarial Review of Model S

**Strongest case for Model S.** It is sound by construction, fast, comprehensible, and almost perfectly fits both training and holdout data despite missing Supplier Review events — exactly the robustness-to-incomplete-logs property the discovery team claims. As an *exploration baseline* it is genuinely useful: it establishes the trivial envelope of behavior and quantifies how much structure the log supports (via the precision gap). Its high generalization score correctly flags that C is brittle.

**Strongest case against Model S.** Its permissiveness is not confined to genuinely optional behavior; it destroys the policy's mandatory core. Concrete admitted behaviors:

| # | Admitted trace | Why undesirable |
|---|---|---|
| U1 | `Register Dossier, Manager Approval, Release Order` (= B3) | Approval with **zero** checks; direct violation of P2. Forbidden by policy. |
| U2 | `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` (= B4) | Expedite Review before the mandatory checks; violates P4's ordering constraint. |
| U3 | `Register Dossier, Supplier Review, Auto Approval, Release Order` | External-flavored flow with no Credit or Technical Check; violates P2 regardless of how P3 is resolved. |
| U4 | `Register Dossier, Supplier Review, Expedite Review, Manager Approval, Release Order` | Both "reviews" with neither mandatory check; Expedite ordering violated. |
| U5 | `Register Dossier, Credit Check, Expedite Review, Auto Approval, Release Order` | Expedited **auto**-approval. P4/P5 are superficially satisfied, but whether urgent cases may auto-approve is a business decision the model cannot even express — permanently policy-ambiguous. |
| U6 | Any trace containing `Correct Dossier`, e.g. `RD, CC, TR, Correct Dossier, TR, MA, RO` | Not in the alphabet at all. Every real corrective-maintenance case is non-fitting — yet training fitness is 0.992, which is only possible if correction events were filtered out by undisclosed preprocessing. This is a data-governance red flag, not a model virtue. |

**Intentional noise tolerance vs accidental semantic flaws.** The `tau` on Supplier Review is *defensible* noise tolerance: P3 makes SR conditional on an attribute the log lacks, and F4 reports SR events going missing, so a skip-tolerant SR is a rational discovery response. Everything else is an *accidental semantic flaw*: the `tau`s on Credit Check and Technical Review optionalize mandatory behavior (P2); the absence of any ordering edges makes P4 unenforceable; the absence of Correct Dossier makes P6/P7 unrepresentable; and the model cannot distinguish "event skipped legitimately" from "event lost by logging," so it launders data-quality defects into apparent fitness. Model S is not a loose version of the true process; it is a different, weaker process.

# 4. Adversarial Review of Model C

**Strongest case for Model C.** Within its eight branches it enforces P1, P2 (both check orders are represented), P5, and it rejects B3, B4, and B8. It contains no silent transitions, so nothing is skipped invisibly; it is sound by construction; and the variant list doubles as human-readable documentation of dominant behavior. In a fail-closed posture, its false negatives are visible and escalatable, whereas S's false positives are silent.

**Strongest case against Model C.**

- **Branch enumeration does not scale and systematically under-covers.** Eight branches for a process with 5 binary/n-ary degrees of freedom (check order × SR × ER × approval type × correction scope × correction count) means the language is a sparse sample of the policy's legal space. Concrete gaps: Auto Approval appears in exactly **one** branch (CCTR, nothing else); there is no SR+AA, no ER+AA, no TR-first+ER combination anywhere. Probe B2 (`RD, TR, CC, AA, RO`) — assessed **valid** — is therefore *rejected*, as is B5. Two of the four policy-valid probes fail.
- **High training precision is substantially a memorization artifact.** Precision-on-training-log measures how much of the model's language the training log visits; a model assembled from that log's frequent variants wins by construction (compounded by F5: no negative suite). The honest tests — held-out precision and negative-suite specificity — were not run. The lopsided approval coverage (7× MA vs 1× AA) is a fingerprint of frequency-driven enumeration, not of policy.
- **Holdout degradation (0.744) conflates two defects.** Part is genuine over-narrowness (unseen legal combinations). Part is fragility to missing events: with no `tau` anywhere, a single dropped SR event turns a perfectly compliant external case into a deviating trace. C's advocates (F8) read the number as "unseen = noncompliant"; the data analyst (F4) shows it is partly "unseen = unlogged."
- **Correction handling is rigid and policy-incomplete.** Exactly one correction pattern exists (both checks repeated, once, MA-only). B6 — a TR-only recheck, *policy-valid if the correction affected Technical Review* — is rejected. Multi-cycle corrections are impossible. P6's decision ("which checks were affected?") is not represented, merely frozen into one historical pattern (F6).
- **Duplicate labels and maintainability.** By my count the tree instantiates 48 leaf occurrences over 9 labels (~39 duplicates under the natural convention; the reported 33 matches no convention I could reconstruct — the definition is unpublished). Duplicate labels fragment the converted net, complicate alignment diagnostics and ownership mapping (F3), and make every change multiplicative: adding one new check or one new approval rule touches many branches, inviting inconsistent edits (F2).

Verdict: C is audit-*shaped* but not audit-ready. Its precision number certifies fidelity to a training sample, not compliance.

Acceptance reasoning: **Model S** = RD first, RO last, exactly one approval, each of {CC, TR, SR, ER}  1 time, any interleaving (see §1 assumptions). **Model C** = exact membership in the eight enumerated sequences. Both derivations are mechanical; the only interpretive dependency is S's `+`, discussed in §1, and it does not affect any cell below.

| Probe | Model S accepts? | Model C accepts? | Policy assessment | Consequence for review |
|---|---|---|---|---|
| B1 `RD,CC,TR,MA,RO` | **Yes** (blocks fire, MA chosen) | **Yes** (branch 1) | valid | Consistent; no discrimination. |
| B2 `RD,TR,CC,AA,RO` | **Yes** (any order; AA allowed) | **No** — AA exists only in branch 8 with CCTR | valid | **C commits a policy false negative on a basic valid case.** Independently disqualifying for enforcement, alongside B5. |
| B3 `RD,MA,RO` | **Yes** (all four blocks take `tau`) | **No** | forbidden | **S admits forbidden behavior** — disqualifying for any enforcement or monitoring-as-gate use. |

| B6 `RD,CC,TR,CD,TR,MA,RO` | **No** — Correct Dossier not in alphabet | **No** — only branch 7 has CD, and it repeats both checks | policy-dependent (valid iff correction affected TR alone) | Both originals reject a possibly-valid trace and neither can *represent the deciding condition*. **Uncertainty statement.** No cell above depends on loop or silent-transition edge cases: S contains no loops, C contains no silences. The sole caveat is the reading of S's `+` (§1); under the sequential misreading, S would additionally reject B2/B4/B5/B7 — but that reading is inconsistent with standard operator semantics and with S's reported fitness profile, so it is not adopted.

# 6. Likely Metric Pathologies

All ten requested pathologies, then a ranking.

1. **Train/holdout leakage & split sensitivity.** Same claimed 80/20 split, but no seed, no preprocessing code, no case-level guarantee, no hashed holdout IDs. Event-level splitting would leak context and inflate both fitnesses; temporal splits introduce drift. C's 0.744 could shift materially under a different legitimate split. *Unverifiable as reported.*
2. **Missing-event bias.** F4 says SR events may be missing; the log also lacks the P3/P6 attributes. Complete models (C) are punished for log gaps; permissive models (S) are rewarded for absorbing them. Both submissions are partly *artifacts of instrumentation failure*, discovered behavior included.
3. **Positive-log-only precision.** Precision against observed traces cannot detect admission of forbidden behavior (B3/B4 never occurred, presumably, so S pays nothing for them). The auditor (F5) is right: without a curated negative suite, "precision" answers the wrong question for compliance.
4. **Fitness rewarded by optionalizing mandatory behavior.** Fitness increases monotonically with language size toward the log's superset. S's 0.992/0.981 is substantially purchased by `tau`-skipping CC/TR — the exact opposite of the behavior the policy mandates.
5. **Generalization rewarded by excessive permissiveness.** Token-based generalization credits unseen behavior; *-models maximize it. S's 0.907 is therefore not evidence of good generalization without a paired specificity measure.
6. **Memorization-inflated precision (C).** Training-log precision for a model enumerated from that log's frequent variants is close to tautological; the 0.941 certifies sample fidelity, not policy fidelity.
7. **Alignment-cost sensitivity.** Under uniform costs, S's skip of CC costs one model-move; under compliance-weighted costs (e.g., skip CC  reorder), S's fitness would collapse on U1/U3-type traces and rankings could flip. Undisclosed cost settings make both teams' numbers non-comparable and non-reproducible.
8. **Duplicate-label effects.** C's ~39 same-labeled leaf instances (reported as an unreproducible "33") fragment the net: diagnostics attach to transition instances rather than activities, breaking ownership mapping and some replay behaviors (F3). S's "0" is nearly tautological for a tree without repetition.
9. **Silent-transition effects.** S's `tau`s make skips cheap or free in standard cost schemes, hiding both legitimate optionality and data loss; they also degrade the diagnosability of deviations. C's zero-`tau` design has the mirror-image pathology (brittleness).
10. **Stakeholder-score methodology.** Informal 1–5 with no protocol, n, randomization, or validation items; confounded by presentation format. Directionally plausible (F3 corroborates), but not decision-grade.
11. **Runtime confounding.** C's 0.440 s median reflects state-space size and duplicate labels, not intrinsic cost of precision; a factored model of the same language aligns faster. Medians also hide deviation-case tails. Operational footnote only.

**Ranked by likely decision impact** (the decision at stake is enforcement adoption):

1. Positive-log-only precision — masks the exact failure mode enforcement cares about.
2. Fitness inflated by optionalization — makes S look compliant when it is the least compliant artifact on the table.
3. Missing-event bias & missing attributes — the common root cause distorting both submissions and all metrics computed from the log.
4. Non-reproducible split — the holdout number that damns C cannot be audited.
5. Memorization-inflated training precision — props up C's headline claim.
6. Generalization-permissiveness artifact — props up S's headline claim.
7. Alignment-cost sensitivity — rank-flipping power, undisclosed settings.
8. Duplicate-label effects — real maintenance/diagnostics risk (F3), lower decision urgency.
9. Silent-transition accounting — feeds pathologies 2 and 4.
10. Stakeholder-score methodology — suggestive only.
11. Runtime confounding — immaterial to governance.

# 7. Third Alternative

**Strategy chosen:** a **block-structured procedural backbone** (POWL) that encodes everything knowable from control flow, plus a **declarative overlay + post-hoc policy checks** for the two attribute-dependent rules (P3, P6) and the suspicion rule (P7). Uncertainty is surfaced as explicit case statuses (`valid / review / suspicious / invalid`) — never resolved by silently optionalizing activities.

### 7.1 Compact formal description

Alphabet  = {RD, CC, TR, SR, ER, CD, MA, AA, RO}. Backbone grammar:

```
T        := RD · CHECKS · CORR* · POST · APPROVAL · RO
CHECKS   := CC  TR                      -- each exactly once, any interleaving (P2)
CORR     := CD · RECHECK                 -- correction cycle (P6)
RECHECK  := CC | TR | (CC  TR)          -- NON-EMPTY recheck subset
POST     := SR?  ER?                    -- each 0..1, mutually unordered (P3/P4)
APPROVAL := MA  AA                      -- exactly one (P5)
```

Declarative overlay (evaluated per completed case):

- **R1 (P7):** for X  {CC, TR}, any occurrence of X after its first requires  1 CD strictly between consecutive occurrences. Violation  status `suspicious`.
- **R2 (P3, gated):** if `sourcing == external` then SR must occur. While the attribute is unlogged, absence of SR  flag `supplier_review_unverified` (status `review`), never auto-pass.
- **R3 (P6, gated):** if `affected_checks` is logged, each CD's subsequent recheck set must equal it; otherwise flag `correction_scope_unverified`.
- **R4/R5 (defense-in-depth):** exactly one approval; approval preceded by 1 CC and 1 TR (structurally guaranteed; asserted anyway).

### 7.2 Self-contained PM4Py code (`model_third`)

```python
import pm4py
from pm4py.objects.powl.obj import Transition, SilentTransition, OperatorPOWL, StrictPartialOrder
from pm4py.objects.process_tree.obj import Operator

T = lambda label: Transition(label=label)
S = lambda: SilentTransition()

# ---- P2: mandatory checks, either completion order (concurrent block, no edges) ----
initial_checks = StrictPartialOrder(nodes=[T("Credit Check"), T("Technical Review")])

# ---- P6: one correction cycle = Correct Dossier then a NON-EMPTY recheck subset ----
recheck = OperatorPOWL(operator=Operator.XOR, children=[
    T("Credit Check"),
    T("Technical Review"),
    StrictPartialOrder(nodes=[T("Credit Check"), T("Technical Review")]),
])
cd = T("Correct Dossier")
correction = StrictPartialOrder(nodes=[cd, recheck])
correction.order.add_edge(cd, recheck)

# zero-or-more corrections: LOOP(do=silent, redo=correction) behaves as correction*
# (portability fallback if a PM4Py version dislikes a silent 'do':
#  XOR(silent, LOOP(correction, silent)))
corrections = OperatorPOWL(operator=Operator.LOOP, children=[S(), correction])

# ---- P3/P4: optional SR and ER after the check phase, mutually unordered ----
sr_opt = OperatorPOWL(operator=Operator.XOR, children=[T("Supplier Review"), S()])
er_opt = OperatorPOWL(operator=Operator.XOR, children=[T("Expedite Review"), S()])
post_reviews = StrictPartialOrder(nodes=[sr_opt, er_opt])

# ---- P5: exactly one approval ----
approval = OperatorPOWL(operator=Operator.XOR,
                        children=[T("Manager Approval"), T("Auto Approval")])

# ---- backbone: RD -> checks -> corrections* -> post-reviews -> approval -> RO ----
rd, ro = T("Register Dossier"), T("Release Order")
model_third = StrictPartialOrder(
    nodes=[rd, initial_checks, corrections, post_reviews, approval, ro])
o = model_third.order
o.add_edge(rd, initial_checks)
o.add_edge(initial_checks, corrections)
o.add_edge(corrections, post_reviews)
o.add_edge(post_reviews, approval)
o.add_edge(approval, ro)

net3, im3, fm3 = pm4py.convert_to_petri_net(model_third)
pm4py.check_soundness(net3, im3, fm3, print_diagnostics=True)   # record result; do not assume
```

### 7.3 Declarative dictionary and external checks

```python
DECLARE_RULES = {
    "init": ["Register Dossier"],
    "end": ["Release Order"],
    "precedence": {                       # target <- required predecessors
        "Credit Check":     ["Register Dossier"],
        "Technical Review": ["Register Dossier"],
        "Correct Dossier":  ["Credit Check", "Technical Review"],
        "Manager Approval": ["Credit Check", "Technical Review"],
        "Auto Approval":    ["Credit Check", "Technical Review"],
        "Release Order":    ["Manager Approval", "Auto Approval"],
    },
    "exclusive_choice": [["Manager Approval", "Auto Approval"]],
    "intervening_constraint": {           # P7: between consecutive X's there must be a CD
        "Credit Check": "Correct Dossier",
        "Technical Review": "Correct Dossier",
    },
    "attribute_participation": {          # P3 — active only once 'sourcing' is logged
        "Supplier Review": {"attr": "sourcing", "equals": "external",
                            "mode": "flag_until_attribute_available"},
    },
    "attribute_scope": {                  # P6 — active only once 'affected_checks' is logged
        "Correct Dossier": {"attr": "affected_checks",
                            "rule": "recheck_set == affected_checks",
                            "mode": "flag_until_attribute_available"},
    },
}

CHECKS = {"Credit Check", "Technical Review"}

def validate_case(events, attrs=None, conformance_fn=None):
    """events: ordered activity labels of one completed case.
    Returns {'status': valid|review|suspicious|invalid, 'violations': [...], 'flags': [...]}."""
    attrs = attrs or {}
    violations, flags = [], []

    # 0) backbone conformance: single-case alignment against model_third;
    #    conformance_fn must wrap pm4py.conformance_diagnostics_alignments.
    if conformance_fn is not None and not conformance_fn(events):
        return {"status": "invalid", "violations": ["backbone_nonconforming"], "flags": []}

    # R1 — P7 suspicion: uncorrected repetition of a mandatory check
    for x in CHECKS:
        idxs = [i for i, e in enumerate(events) if e == x]
        for prev, cur in zip(idxs, idxs[1:]):
            if not any(e == "Correct Dossier" for e in events[prev:cur]):
                violations.append(("P7_suspicious_repeat", x, cur))

    # R2 — P3: supplier-review obligation (gated on missing attribute)
    if "Supplier Review" not in events:
        if attrs.get("sourcing") == "external":
            violations.append(("P3_missing_supplier_review_external", None))
        elif attrs.get("sourcing") is None:
            flags.append(("P3_sourcing_unverified", None))

    # R3 — P6: correction scope (gated on missing attribute)
    cd_idx = [i for i, e in enumerate(events) if e == "Correct Dossier"]
    affected = attrs.get("affected_checks")
    if cd_idx and affected is None:
        flags.append(("P6_scope_unverified", len(cd_idx)))
    if cd_idx and affected is not None and len(affected) == len(cd_idx):
        all_chk = [i for i, e in enumerate(events) if e in CHECKS]
        for k, ci in enumerate(cd_idx):
            nxt = min([i for i in all_chk if i > ci], default=len(events))
            if {e for e in events[ci:nxt] if e in CHECKS} != set(affected[k]):
                flags.append(("P6_scope_mismatch", k))

    # R4/R5 — defensive assertions of structurally guaranteed properties
    ap = [e for e in events if e in {"Manager Approval", "Auto Approval"}]
    if len(ap) != 1:
        violations.append(("P5_approval_cardinality", len(ap)))

    status = ("invalid" if any(v[0].startswith(("backbone", "P3_missing", "P5_"))
                               for v in violations)
              else "suspicious" if violations
              else "review" if flags else "valid")
    return {"status": status, "violations": violations, "flags": flags}
```

### 7.4 Explicit semantics

- **Mandatory checks (P2):** CC and TR each occur exactly once in the initial concurrent block, before any approval; further occurrences only via CD. Not optional, not skippable.
- **Optional Supplier Review (P3):** 0–1 occurrences, positioned after the check/correction phase. Optionality is *policy-derived* (attribute-conditioned), and the condition is carried as an explicit obligation/flag — not as a free skip.
- **Expedite Review ordering (P4):** 0–1 occurrences, after both mandatory checks (hence after corrections settle), before approval, either side of SR (unordered block).
- **Exactly-one approval (P5):** XOR of MA/AA, plus defensive cardinality assertion.
- **Correction/recheck (P6/P7):** CD is reachable only after the initial check phase completes; each CD is followed by a non-empty recheck subset; multiple correction cycles are allowed; recheck scope is verified against `affected_checks` when available, flagged otherwise; uncorrected repetition is structurally impossible *and* independently flagged by R1.

### 7.5 Limitations caused by the missing attributes

1. **P3 cannot be enforced**, only flagged, until `sourcing` is logged; external cases without SR will sit in `review` purgatory. This is honest ignorance, not solved by pretending SR is free.
2. **P6 cannot be verified**, only flagged, until `affected_checks` is logged; the model accepts any non-empty recheck subset and routes scope doubts to humans.
3. **SR position is a modeled assumption** (post-check block). If the business confirms SR may precede checks, the partial order must be widened — a one-line change, but a policy decision first (see probe A4).
4. The concurrent CHECKS block permits true simultaneity; workflow engines will serialize it. Harmless, but worth documenting.
5. Block-structured reuse of CC/TR creates a small number of duplicate leaf labels (~4 excess instances vs ~39 in Model C). They must be registered and covered in the diagnostics mapping; eliminating them entirely requires non-tree editing, out of scope here.
6. The `LOOP(silent, X)` idiom should be smoke-tested on the pinned PM4Py version; the XOR-wrapped fallback is provided.
7. No resource, timing, or data-payload semantics — the model is not yet a simulation asset.

def stratified_case_split(log, test_frac=0.2, seed=SEED):
    rnd = random.Random(seed)

        for t in trs[:cut]: test.append(t)

**E4 — Missing/duplicate-event perturbation.** Delete each SR (then CC, TR) occurrence with probability p  {0.05…0.5}; duplicate events similarly. Plot fitness-vs-p per model. ```python
def perturb_delete(log, label, p, seed=7):
    rnd = random.Random(seed); out = EventLog()
    for t in log:
        nt = EventLog()(t.__class__) if False else type(t)(attributes=dict(t.attributes))
        for e in t:
            if e["concept:name"] == label and rnd.random() < p:
                continue
            nt.append(e)
        out.append(nt)
    return out

**E10 — Decision rule (lexicographic gate, no aggregates).**

```python
def governance_gate(rep, use_case):
    if not rep["sound"]:
        return "REJECT"
    if use_case == "enforcement":
        if rep["negative_rejection_rate"] < 1.0:            return "REJECT"   # fail-open
        if rep["plausible_acceptance"] < 0.95:              return "REJECT"   # fail-closed harm
        if rep["fitness_holdout_calibrated"] < 0.90:        return "REJECT"
        return "ADMIT_MONITOR_FIRST"
    if use_case == "exploration":
        return "ADMIT" if rep["fitness_holdout"] >= 0.80 else "REJECT"
    return "ADMIT_WITH_CAVEATS"
```

A model is **rejected despite good aggregates** if any gate fails — e.g., perfect average metrics with a single admitted forbidden trace, an unreproducible holdout number, or a failed soundness check.

# 10. Governance Recommendation

1. **Exploration / hypothesis generation:** **Model S may be used immediately**, explicitly labeled "permissive baseline — not a representation of policy." Its value is as a reference envelope and as the contrast that quantifies log structure. It must never be wired to any gate, dashboard flag, or automation.
2. **Compliance enforcement:** **Neither original model is admissible.** Model S fails open on B3/B4-class behavior — disqualifying per se. Model C fails closed on demonstrably valid behavior (B2, B5) and cannot express P6 — its rejections would generate override traffic and erode trust (F2). Model C is additionally unmaintainable (F3) and its headline precision is a training-set artifact (F5).
3. **Interim control (until the third alternative passes its gates):** run a **manual checklist derived from P1–P7** — not Model C as an automated blocker, and never Model S.
4. **Third alternative:** deploy `model_third` in **monitor mode** (tri-state verdicts logged, nothing blocked) for at least one reporting cycle; review flag rates and false-alarm burden; then promote to enforcement only after the Section 9 gates pass, including 100 % rejection of the forbidden suite and  95 % acceptance of the plausible-valid suite.
5. **Retirement:** archive Model C as a **variant catalog** (it is genuinely useful documentation of frequent behavior) and remove it from active service. Retain Model S solely as the exploratory baseline. Both are superseded for production purposes.
6. **Conditions precedent for `model_third` deployment:** (a) logging extended with `sourcing` and `affected_checks` (plus correctioncase linkage) — this is the root-cause fix; (b) E1–E10 executed by a second engineer from published artifacts with reproduced values; (c) soundness verified on the pinned PM4Py version; (d) duplicate-leaf inventory registered; (e) business ruling on A4 (SR position); (f) documented rollback plan and quarterly re-discovery cadence.

# 11. Dissenting View

I dissent from retiring Model C for compliance and from the confidence placed in the hybrid. First, the third model's compliance power lives partly in Python post-hoc checks outside the formal model. Unlike the Petri-net backbone, that code has no soundness guarantee, no alignment semantics, and no tool support; it is shadow logic, and shadow logic is how audit trails rot. Second, the board weighs fail-open and fail-closed errors asymmetrically. Model C's false negatives inconvenience operations; the hybrid's flag-and-pass defaults — like Model S's silence — expose the firm to unvetted credit risk. Until sourcing and affected-check attributes are actually logged, every conditional rule in the hybrid is decorative; a strict model that escalates everything anomalous to a human may be the only honest interim control. Third, the hybrid's comprehension advantage is anecdotal; a partial order plus a declarative overlay plus tri-state verdicts may bewilder operations more than eight enumerable variants. Fourth, we risk months of validation theater while the root defect — two missing log attributes — could be fixed by a one-week instrumentation sprint, after which rediscovery on complete data might obsolete both submissions. I would run Model C in blocking mode with a fast manual-override lane, instrument the log, and revisit. Change my mind with: production-sampled false-negative rates for C below agreed tolerance on a curated plausible suite; formally verified post-hoc checks; and protocol-measured comprehension favoring the hybrid.

**Additional evidence that would change my decision:**

- Independent replication of every reported metric from published seeds, code, and hashed holdout IDs, reproducing the values within a stated tolerance — restoring trust in the evidence base.
- An override-log analysis showing Model C's production rejections are overwhelmingly genuinely noncompliant (low successful-override rate), which would recast its "false negatives" as correct rejections.
- Machine-checked verification of the post-hoc rule engine (R1–R5), or its replacement by declarative constraints supported by an existing model checker — removing the shadow-logic objection.
- Completed attribute instrumentation plus a re-discovery on enriched data that recovers the hybrid's structure automatically, proving the design reflects the process rather than reviewer preferences.
- A pre-registered comprehension study in which the hybrid matches or beats Model C under the Section 9 (E9) protocol.
