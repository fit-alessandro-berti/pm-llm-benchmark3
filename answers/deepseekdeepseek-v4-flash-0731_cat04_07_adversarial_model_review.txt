# 1. Review Scope and Assumptions

I distinguish four use cases because they change what “good” means:

- **Exploration / discovery triage**: high recall, speed, and readability are valuable; moderate over-permissiveness is tolerable if the model is explicitly non-authoritative.
- **Conformance enforcement / compliance**: the model is used to block or flag noncompliant behavior. Here false acceptance of forbidden behavior is unacceptable; fitness and precision only matter after policy correctness is checked.
- **Simulation / what-if analysis**: the model should generate only plausible cases, so it must be reasonably complete and precise; optionalizing mandatory behavior would corrupt the simulated distribution.
- **Stakeholder communication / audit**: the model must be understandable and maintainable by process owners, IT, and auditors, not only by discovery analysts.

These use cases explain why I do not aggregate the reported metrics into one number. A single weighted score would require choosing weights that are different for exploration vs. compliance. I keep all metrics disaggregated.

# 3. Adversarial Review of Model S

## Strongest case for Model S

Model S is understandable at a glance. Its structure is:

```text
Register Dossier
 optional checks in parallel
 one approval
 Release Order
```

It is fast, simple, and gets high fitness and generalization scores. For an initial exploratory conversation, it can show users which activities are common without pretending to be a compliance rule.

## Strongest case against Model S

The same optionality that gives it high fitness also destroys policy control. The construction `X('Credit Check', tau)` inside a parallel block makes **every check optional**. This is not “robustness to missing events”; it is a semantic claim that skipping mandatory checks is ordinary behavior.

At least five concrete undesirable or policy-ambiguous behaviors admitted by Model S:

- `Register Dossier, Manager Approval, Release Order` — skips both mandatory checks.
- `Register Dossier, Credit Check, Manager Approval, Release Order` — skips Technical Review.
- `Register Dossier, Technical Review, Manager Approval, Release Order` — skips Credit Check.
- `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` — Expedite happens before mandatory checks.
- `Register Dossier, Supplier Review, Expedite Review, Manager Approval, Release Order` — both mandatory checks skipped while optional reviews occur.

Model S also has no `Correct Dossier`. This is not a permissiveness problem, but it is a semantic incompleteness: all legitimate correction traces such as `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order` cannot be parsed.

The distinction matters: allowing one missing event around a fixed mandatory backbone could be noise tolerance; replacing a mandatory check with `X(activity, tau)` is not noise tolerance — it is accidental semantic optionalization.

# 4. Adversarial Review of Model C

## Strongest case for Model C

Model C has a clear “variant list” semantics. It enforces the two mandatory checks in two supported orders, includes Supplier Review only in known external-like variants, includes exactly one approval, includes a correction variant, and rejects obviously forbidden traces such as `Register Dossier, Manager Approval, Release Order`.

Its high alignment precision on the training log is not meaningless: it shows the model is much closer than S to the observed positive variants.

## Strongest case against Model C

The model is an enumeration of eight traces, not a process model. Any legitimate behavior outside those exact eight traces is rejected. The observed holdout fitness collapse from 0.973 to 0.744 is consistent with this.

Concrete weaknesses:

- It rejects `Register Dossier, Technical Review, Credit Check, Auto Approval, Release Order`, which is explicitly valid under P2 and P5.
- It rejects `Register Dossier, Technical Review, Credit Check, Supplier Review, Expedite Review, Auto Approval, Release Order`, which is a plausible external urgent case.
- It supports only one correction variant: `Correct Dossier` followed by both `Credit Check` and `Technical Review`. It cannot represent a correction that affects only Technical Review.
- It has no conditional handling for external/internal orders. Supplier Review appears only in some random-looking branches, because the attribute was missing from discovery.
- It converts to a Petri net with many duplicate labels, increasing alignment cost and ambiguity. The reported duplicate-label count of 33 is a red flag for label-splitting overfitting.
- Its high precision is an artifact of memorizing training variants. A model that memorizes eight traces can have high precision on those traces while failing legitimate unseen combinations.

Therefore C is “precise” only with respect to observed positive traces, not with respect to policy.

# 6. Likely Metric Pathologies

The following pathologies are ranked roughly by likely decision impact.

1. **Fitness rewarded by optionalizing mandatory behavior.** Model S’s high fitness is not a virtue; it is earned by allowing mandatory checks to be skipped. This is the most dangerous pathology for compliance use.
2. **Missing-event bias.** If an event is missing from the log due to data capture error, Model S treats it as a lawful skip. Model C treats it as noncompliance. A compliance evaluation must separate “missing event” from “activity not executed.”
3. **Positive-log-only precision.** Precision was computed only on observed positive traces. No curated negative suite was used, so B3 and B4 would never be tested. High precision in C can be memorization; low precision in S is not the only reason to reject S.
4. **Train/holdout leakage or split sensitivity.** Neither team supplied seeds, preprocessing code, alignment-cost parameters, or the exact holdout cases. The C drop from 0.973 to 0.744 could be partially caused by an unlucky split.
5. **Duplicated-label effects.** Model C’s duplicate labels cause alignment algorithms to explore many branch assignments, inflating runtime and possibly making fitness/precision unstable.
6. **Alignment-cost sensitivity.** With different log-move/model-move costs, S and C scores could change materially. A mandatory check skipped by S can be hidden by choosing `tau` as a model move instead of a log move.
7. **Generalization rewarded by excessive permissiveness.** S’s token-based generalization is high because the model can produce many unseen traces. That is only desirable if the unseen traces are legal; many are not.
8. **Silent-transition effects.** Both X(activity, tau) and loop/repair silence can create invisible paths that alignments traverse. Silent transitions can inflate fitness and deflate precision in ways that are hard to explain to stakeholders.
9. **Stakeholder-score methodology.** An informal 1–5 score with no protocol cannot support a governance decision. Users may prefer the simpler model because they do not realize it allows forbidden behavior.
10. **Runtime confounding by model size.** C’s slower runtime is an artifact of its size and duplicate labels, not a measure of conformance quality.

# 7. Third Alternative

I choose a **block-structured procedural backbone with explicit uncertainty and post-hoc policy checks**. This is safer than Model S and more maintainable than Model C.

## 1. Compact formal description

Let:

- `R` = Register Dossier
- `C` = Credit Check
- `T` = Technical Review
- `S` = Supplier Review
- `E` = Expedite Review
- `Corr` = Correct Dossier
- `M` = Manager Approval
- `A` = Auto Approval
- `Rel` = Release Order
- `` = silent skip (`tau`)

The main model is:

```text
model_third =
  seq(
    R,
    par(C, T),
    par(
      RepairLoop,
      OptionalReviewBlock
    ),
    choice(M, A),
    Rel
  )
```

where:

```text
RepairLoop =
  choice(
    ,
    loop(
      seq(Corr, par(choice(C, ), choice(T, ))),
      
    )
  )

OptionalReviewBlock =
  par(
    choice(S, ),
    choice(E, )
  )
```

Semantics:

- `par(C, T)` means both mandatory checks are required and may occur in either order.
- `OptionalReviewBlock` allows S and E to be absent or present, in either order, after the mandatory checks and before approval.
- `RepairLoop` allows zero or more corrections. Each correction body is `Corr` followed by an optional recheck of C and/or T.
- Because the affected-check attribute is missing, the recheck block permits any subset of `{C, T}`. The external post-hoc check is the place where the missing attribute is explicitly treated as “unknown,” not as a free pass.

## 3. Declarative dictionaries / external checks

The process tree cannot see missing attributes. I therefore add policy checks outside the process tree:

```python
def correction_repeat_policy(event_names):
    last_correct = -1
    last_pos = {}
    for i, act in enumerate(event_names):
        if act == "Correct Dossier":
            last_correct = i
        elif act in ("Credit Check", "Technical Review"):
            if act in last_pos and last_pos[act] > last_correct:
                return False, f"suspicious repeated {act} at index {i}"
            last_pos[act] = i
    return True, None

def supplier_requirement(source_is_external, event_names):
    # If source is unknown, return None, meaning "unknown", not "pass".
    if source_is_external is None:
        return None
    if source_is_external:
        return "Supplier Review" in event_names
    return True
```

If an `affected_check` attribute is later added, the external check should require, for each `Correct Dossier`, exactly the checks listed in that correction’s affected set. Until then, the model returns `unknown` for exact affected-check semantics.

## 4. Explicit semantics

- **Mandatory checks**: `C` and `T` both occur before any optional reviews or corrections and before approval. They can be in either order.
- **Supplier Review**: optional in the base model because the external/internal attribute is missing. If the source is known to be external, `Supplier Review` is mandatory; the base model cannot express that without the attribute.
- **Expedite Review**: optional, occurs after the mandatory checks, before approval, and can occur before or after Supplier Review because the optional review block is parallel.
- **Approval**: `choice(M, A)` before `Release` enforces exactly one approval.
- **Correction/recheck behavior**: `RepairLoop` allows zero or more correction cycles. Each cycle is `Correct Dossier` followed by possible rechecks of C/T. A repeated C/T without a preceding `Correct Dossier` is rejected by the external check, not by the process tree alone.

## 5. Limitations caused by missing attributes

- Without `source` (external/internal), no model can distinguish an internal order that correctly skips Supplier from an external order that incorrectly skips Supplier.
- Without `affected_check`, no model can know whether a correction should repeat C only, T only, or both. The base model permits all three possibilities; the external check can only detect repeated checks without a prior correction.
- I do **not** solve this by making every activity optional. Mandatory checks remain mandatory in the backbone. Only the genuinely conditional Supplier Review and the genuinely unknown affected-check subset are left open.

The final decision rule should be:

- The model is rejected if soundness checks fail.
- The model is rejected if any curated negative trace is accepted.
- The model is rejected if any valid policy probe from B1–B8 is rejected, unless the rejection is explicitly due to a missing attribute and the result is reported as `unknown`.
- The model is rejected if holdout fitness is below 0.90 on a reproducible variant-stratified split, unless the cause is documented as missing-event bias.
- Alignment-cost sensitivity must be reported. If changing costs from `(1,1)` to `(2,1)` changes acceptance on policy probes, the model’s conformance diagnostics are not stable enough for enforcement.

# 10. Governance Recommendation

- **Model S**: retire for compliance. It may be used only in a clearly labeled exploratory sandbox, and even then it should be accompanied by a warning that it treats mandatory checks as optional.
- **Model C**: do not use as the compliance model. It may be archived as a documented snapshot of frequent variants, but it is not maintainable and rejects legitimate unseen behavior.
- **Third alternative**: conditionally approved. It may be used for exploration and simulation immediately after soundness checks, and for compliance only after the validation program in Section 9 is completed.

Conditions for compliance deployment of the third alternative:

1. `check_soundness` returns sound.
2. Zero acceptance of B3, B4, B8, and other curated negatives.
3. Acceptance of B1, B2, B5, B7, B6 (with appropriate `affected_check` caveat).
4. Reproducible holdout fitness and precision results are published with seed and preprocessing.
5. External checks are versioned and code-reviewed, especially `correction_repeat_policy` and `supplier_requirement`.
6. Stakeholder comprehension is measured with a documented protocol and is not worse than Model S.
7. Runtime per case is acceptable for the intended operational scale.

# 11. Dissenting View

The strongest objection to my recommendation is that the third alternative has the same epistemic disease as Model S: it makes Supplier Review optional and rechecks optional because attributes are missing. A process owner could see “conformant” for an external order that skipped Supplier, or for a correction that repeated no check at all. That is not audit-ready. Model C at least fails closed: if a behavior is not enumerated, it is noncompliant. For a compliance-first organization, retaining C may be safer than deploying a model that silently returns “unknown” as “pass.” My proposed external checks are code, and code can be version-skewed, bypassed, or not run.

I would change my decision if the logs are enriched with the external/internal and affected-check attributes, and the third alternative still passes a stratified holdout with high fitness and zero negative acceptance. I would also change if the board formally accepts that missing attributes must produce `unknown` rather than `pass`, and operational procedures force a manual review whenever the external check returns `unknown`. Without those safeguards, the third alternative is a better discovery model than S, but not yet a better compliance model than C.
