# 1. Assumptions and Interpretation

1. **Activity lifecycle abstraction.** Each visible transition represents activity completion. A precedence \(A < B\) is therefore the activity-based abstraction of “\(B\) may start only after \(A\) completes.” Actual start times and durations are not modeled.
2. **Enabling is not urgency.** “May start as soon as” means that an activity becomes enabled when its prerequisites are complete; it does not require immediate execution.
3. **Risk route.** Low risk versus high risk is represented by an XOR: either `Supervisor Review`, or a high-risk submodel containing both `Quality Review` and `Regulatory Review`. The model does not contain a risk-data guard, so the choice is nondeterministic from the control-flow perspective.
4. **Supplier consultation.** Supplier involvement is represented by `XOR(, Consult Supplier)`. Thus consultation is optional, and its visible activity can occur at most once. The case-data condition selecting the branch is not encoded.
5. **Inspection result.** In the trial loop, every `Inspect Trial` followed by `Adjust Parameters` is interpreted as a failed inspection. The final `Inspect Trial`, which is not followed by adjustment, is interpreted as the passing inspection.
6. **Duplicate visible labels.** PM4Py can technically contain multiple model nodes with the same visible label, but neither model below uses static duplicate visible nodes. Repeated `Execute Trial` and `Inspect Trial` events come from repeated execution of the same loop body.
7. **Process-tree approximation policy.** The process tree is a **conservative under-approximation without visible-label duplication**. It introduces a block boundary after both `Plan Verification` and `Design Corrective Action`. Consequently, approvals and supplier consultation cannot occur before that boundary, even though the intended process permits them earlier. The tree does not admit behavior that is unsafe under the stated control-flow rules.
8. **Concurrency interpretation.** “May overlap” is interpreted as absence of a causal order—true concurrency at the model level—not merely a preselected serial order. Recorded traces are linearizations of that concurrency, and completion-only events cannot prove that execution intervals physically overlapped.
9. **Completion and termination.** A completed case has finitely many trial iterations and eventually exits the loop after an inferred passing inspection. Infinite operational looping and fairness are outside the finite-trace semantics used here.

| D21 | Release Material | Archive Case | Precedence | Archiving follows release. |
| D22 | Archive Case | End | Unique end | No visible activity occurs after archiving in a complete case. |

# 3. PM4Py Process-Tree Model

The notation below uses `` for sequence, `` for parallel, `×` for XOR, `` for the standard process-tree loop `(do, redo)`, and `` for a silent leaf.

```text
(
  'Register Deviation',
  (
    ('Contain Material', 'Plan Verification'),
    ('Analyze Root Cause', 'Design Corrective Action')
  ),
  (
    (
      ('Execute Trial', 'Inspect Trial'),
      'Adjust Parameters'
    ),
    ×(
      'Supervisor Review',
      ('Quality Review', 'Regulatory Review')
    ),
    ×(, 'Consult Supplier')
  ),
  'Release Material',
  'Archive Case'
)
```

The first parallel block preserves the two independent initial streams and their local dependencies. Its completion is an approximating barrier. After that barrier, the trial loop, selected review route, and supplier option run in parallel and are joined before release. The loop language is:

```text
Execute Trial, Inspect Trial,
(Adjust Parameters, Execute Trial, Inspect Trial)*
```

Self-contained construction code:

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def activity(label):
    """Construct one visible process-tree leaf."""
    return ProcessTree(label=label)


def silent_activity():
    """Construct one silent process-tree leaf."""
    return ProcessTree()


def operator_node(operator, *children):
    """
    Construct an operator node and explicitly maintain both sides
    of every parent/child relationship.
    """
    parent = ProcessTree(operator=operator)
    for child in children:
        parent.children.append(child)
        child.parent = parent
    return parent


# Initial work streams
contain_stream = operator_node(
    Operator.SEQUENCE,
    activity("Contain Material"),
    activity("Plan Verification"),
)

analysis_stream = operator_node(
    Operator.SEQUENCE,
    activity("Analyze Root Cause"),
    activity("Design Corrective Action"),
)

initial_phase = operator_node(
    Operator.PARALLEL,
    contain_stream,
    analysis_stream,
)

# Risk route
high_risk_route = operator_node(
    Operator.PARALLEL,
    activity("Quality Review"),
    activity("Regulatory Review"),
)

risk_route = operator_node(
    Operator.XOR,
    activity("Supervisor Review"),
    high_risk_route,
)

# Optional supplier consultation
supplier_option = operator_node(
    Operator.XOR,
    silent_activity(),
    activity("Consult Supplier"),
)

# Repeat-until-pass trial skeleton:
# do (redo do)* = (Execute, Inspect) (Adjust, Execute, Inspect)*
trial_iteration = operator_node(
    Operator.SEQUENCE,
    activity("Execute Trial"),
    activity("Inspect Trial"),
)

trial_loop = operator_node(
    Operator.LOOP,
    trial_iteration,
    activity("Adjust Parameters"),
)

# Reviews and consultation may overlap the trial after the approximating barrier.
post_design_phase = operator_node(
    Operator.PARALLEL,
    trial_loop,
    risk_route,
    supplier_option,
)

tree = operator_node(
    Operator.SEQUENCE,
    activity("Register Deviation"),
    initial_phase,
    post_design_phase,
    activity("Release Material"),
    activity("Archive Case"),
)

assert tree.parent is None
```

At the completion-event abstraction, the tree represents the start/end rules, the local containment-to-planning and analysis-to-design dependencies, the risk XOR, concurrent high-risk reviews, optional supplier activity, repeat-until skeleton, trial/review overlap, and release synchronization. The non-block-structured timing is not exact: the sequence boundary after `initial_phase` forces the selected approval route and supplier consultation to wait for both `Plan Verification` and `Design Corrective Action`. In the intended process, reviews and consultation need only wait for `Analyze Root Cause`, so they may occur while planning or design is still in progress. Consultation therefore cannot overlap planning or design in this tree, although it can overlap reviews and trial work. Risk data, supplier-selection data, inspection outcomes, actual starts, durations, and physical overlap are also not encoded. The resulting visible language is a conservative subset of the intended control-flow language.

# 4. PM4Py POWL Model

Here `PO(N,E)` denotes a strict partial order over nodes \(N\) with precedence edges \(E\). Unconnected nodes are concurrent.

```text
HighRisk =
  PO(
    nodes = {Quality Review, Regulatory Review},
    edges = {}
  )

RiskRoute =
  XOR(Supervisor Review, HighRisk)

Supplier =
  XOR(, Consult Supplier)

Iteration =
  PO(
    nodes = {Execute Trial, Inspect Trial},
    edges = {Execute Trial < Inspect Trial}
  )

Trials =
  LOOP(Iteration, Adjust Parameters)

Root =
  PO(
    nodes = {
      Register Deviation,
      Contain Material,
      Analyze Root Cause,
      Plan Verification,
      Design Corrective Action,
      RiskRoute,
      Supplier,
      Trials,
      Release Material,
      Archive Case
    },
    edges = {
      Register Deviation < Contain Material,
      Register Deviation < Analyze Root Cause,
      Contain Material < Plan Verification,
      Analyze Root Cause < Design Corrective Action,
      Analyze Root Cause < RiskRoute,
      Analyze Root Cause < Supplier,
      Plan Verification < Trials,
      Design Corrective Action < Trials,
      RiskRoute < Release Material,
      Supplier < Release Material,
      Trials < Release Material,
      Release Material < Archive Case
    }
  )
```

Self-contained construction code:

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


# Atomic visible activities
register = Transition("Register Deviation")
contain = Transition("Contain Material")
analyze = Transition("Analyze Root Cause")
plan = Transition("Plan Verification")
design = Transition("Design Corrective Action")

supervisor_review = Transition("Supervisor Review")
quality_review = Transition("Quality Review")
regulatory_review = Transition("Regulatory Review")

consult_supplier = Transition("Consult Supplier")
supplier_skip = SilentTransition()

execute_trial = Transition("Execute Trial")
inspect_trial = Transition("Inspect Trial")
adjust_parameters = Transition("Adjust Parameters")

release = Transition("Release Material")
archive = Transition("Archive Case")


# High-risk route: both reviews are required and intentionally unordered.
high_risk_route = StrictPartialOrder(
    nodes=[quality_review, regulatory_review]
)

# Risk-data condition is abstracted as an XOR.
risk_route = OperatorPOWL(
    Operator.XOR,
    [supervisor_review, high_risk_route],
)

# Supplier involvement is abstracted as a silent/visible XOR.
supplier_option = OperatorPOWL(
    Operator.XOR,
    [supplier_skip, consult_supplier],
)

# One trial iteration.
trial_iteration = StrictPartialOrder(
    nodes=[execute_trial, inspect_trial]
)
trial_iteration.order.add_edge(execute_trial, inspect_trial)

# Standard do/redo loop:
# iteration (adjustment iteration)*
trial_loop = OperatorPOWL(
    Operator.LOOP,
    [trial_iteration, adjust_parameters],
)

# Root non-block-structured partial order.
powl = StrictPartialOrder(
    nodes=[
        register,
        contain,
        analyze,
        plan,
        design,
        risk_route,
        supplier_option,
        trial_loop,
        release,
        archive,
    ]
)

# Start and initial fork
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# Independent local dependencies
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)

# Analysis-dependent obligations
powl.order.add_edge(analyze, risk_route)
powl.order.add_edge(analyze, supplier_option)

# The trial waits for both work products
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# Release synchronization
powl.order.add_edge(risk_route, release)
powl.order.add_edge(supplier_option, release)
powl.order.add_edge(trial_loop, release)

# Unique end
powl.order.add_edge(release, archive)
```

The intentionally unconnected pairs correspond to missing business dependencies:

- The containment/planning stream and analysis/design stream have no cross-edge: `Contain Material` is unordered with `Analyze Root Cause` and `Design Corrective Action`, while `Plan Verification` is unordered with `Analyze Root Cause` and `Design Corrective Action`.
- The risk route, after its required analysis predecessor, remains unordered with containment, planning, design, supplier consultation, and trial work. This lets reviews finish before or during those activities.
- The supplier option, after analysis, remains unordered with containment, planning, design, the review route, and trial work.
- The risk route, supplier option, and trial loop are pairwise unordered but all precede release.
- `Quality Review` and `Regulatory Review` have no internal edge because both are required and either may complete first.
- Every other necessary order is present directly or follows transitively. Lack of an edge permits concurrency or either completion order; it does not require actual overlap.

# 5. Behavioral Witnesses

Aliases used below are: `RD` = Register Deviation, `CM` = Contain Material, `AR` = Analyze Root Cause, `PV` = Plan Verification, `DC` = Design Corrective Action, `SR` = Supervisor Review, `QR` = Quality Review, `RR` = Regulatory Review, `CS` = Consult Supplier, `ET` = Execute Trial, `IT` = Inspect Trial, `AP` = Adjust Parameters, `RM` = Release Material, and `AC` = Archive Case.

| Trace ID | Visible trace | Intended verdict | Process-tree verdict | POWL verdict | Reason |
|---|---|---|---|---|---|
| A1 | RD, CM, PV, AR, DC, ET, SR, IT, RM, AC | Allowed | Allowed | Allowed | Low-risk case. Planning and design finish before the trial; supervisor review completes during the trial interval in this completion ordering; the final `IT` is inferred to pass. |
| A2 | RD, AR, CM, DC, PV, QR, ET, RR, IT, RM, AC | Allowed | Allowed | Allowed | High-risk case. Both reviews occur, with trial work interleaved between their completions. |
| A3 | RD, AR, DC, CM, PV, ET, CS, IT, SR, RM, AC | Allowed | Allowed | Allowed | Supplier consultation is selected once, after analysis and before release, and is interleaved with the trial. |
| A4 | RD, CM, AR, PV, DC, SR, ET, IT, AP, ET, IT, RM, AC | Allowed | Allowed | Allowed | The first `IT` is inferred to fail, `AP` occurs, and a second execution–inspection cycle ends with the inferred passing inspection. |
| A5 | RD, AR, SR, CM, PV, DC, ET, IT, RM, AC | Allowed | Forbidden by approximation | Allowed | `SR` is valid immediately after analysis, but the tree’s artificial phase barrier does not permit reviews until both `PV` and `DC` are complete. The tree first rejects at `SR`. |
| F1 | RD, AR, CM, PV, ET, DC, SR, IT, RM, AC | Forbidden | Forbidden | Forbidden | The earliest violation is `ET`: `DC` has not completed, so the two-input prerequisite for the trial is unsatisfied. |
| F2 | RD, AR, DC, CM, PV, ET, QR, IT, RM, AC | Forbidden | Forbidden | Forbidden | The prefix is feasible until `RM`; at release, the route is incomplete. `QR` alone is neither the low-risk route nor the required pair `QR` and `RR`. |
| F3 | RD, AR, DC, CM, PV, SR, ET, IT, RM, CS, AC | Forbidden | Forbidden | Forbidden | Because `CS` appears, consultation was selected, so `RM` violates the supplier synchronization before consultation completes. In online conformance checking, the first unmatched event may be the later `CS`, because the no-supplier prefix through `RM` is otherwise feasible. |

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and analysis are both after registration and otherwise independent. | Exact through a parallel block. | Exact through two outgoing precedence edges with no edge between the activities. | None at the atomic completion level. | Either stream may progress first, and their completions may be interleaved. |
| Split dependencies into planning/design | Planning depends only on containment; design depends only on analysis. | Local dependencies are exact, but both branches must finish before the next block starts. | Dependencies are stated directly without a shared phase join. | Process tree is overconstrained globally and therefore under-approximates traces. | The tree may incorrectly flag early reviews or early supplier consultation even when their real prerequisite is satisfied. |
| Risk route | XOR between one supervisor review and a high-risk route requiring both quality and regulatory reviews. | Exact control-flow XOR with a parallel high-risk branch. | Exact control-flow XOR with an unordered high-risk partial order. | Both are under-specified with respect to case data. | A structurally fitting trace does not prove that the route matched the case’s actual risk classification. |
| Approval and trial overlap | The trial waits for planning and design, but not for reviews; reviews may overlap the trial. | Review route and trial are parallel after the approximating barrier. | Route and trial are directly unordered. | Tree is partly overconstrained because reviews cannot occur before the planning/design barrier; POWL has no such added order. | The tree can reject legitimate early-review behavior, although it still permits review/trial overlap after the barrier. |
| Optional supplier consultation | Zero or one consultation, after analysis and before release; it may overlap planning, design, reviews, and trials. | Optional and at most once, but forced after planning and design. It can overlap reviews and trials. | Optional and at most once, with only analysis-before and consultation-option-before-release constraints. | Process tree overconstraint; both omit the data guard. | The tree can create false deviations for early supplier engagement. Neither model verifies whether consultation was actually required by case data. |
| Trial prerequisite | First execution requires both planning and design. | Exact: the second parallel block is entered only after both are complete. | Exact through two incoming edges to the trial loop. | No control-flow loss. | Premature trial execution is rejected by both models. |
| Repeat-until behavior | Execute–inspect; on failure adjust and repeat; final inspection passes and has no following adjustment. | Exact visible skeleton using `LOOP(do, redo)`. | Exact visible skeleton using `OperatorPOWL.LOOP`. | Inspection outcomes are semantically under-specified in both. | The models enforce the right activity pattern but cannot compare the inferred pass/fail interpretation with inspection data. |
| Release synchronization | Release waits for final trial completion, the selected route, and the selected supplier branch. | Exact through completion of the parallel block before release. | Exact through three incoming precedence edges to release. | None at the selected control-flow-branch level. | Missing reviews, an unfinished trial cycle, or selected consultation after release are rejected. |
| Start and end | Registration is first; archive is after release and is last. | Exact through top-level sequence. | Exact through graph reachability: registration precedes all work and all work reaches release before archive. | None for complete finite traces. | Cases with visible work before registration or after archive are rejected. |
| Duplicate-label risk | Repetition should mean trial-loop repetition, not multiple ambiguous definitions of an activity. | One visible leaf per label; loop re-fires the same trial leaves. | One visible transition per label; loop re-fires the same trial transitions. | No intentional duplication. Conversion tools may still introduce multiple internal or same-labelled net transitions. | Event-to-transition mapping remains comparatively clear, but converted models should still be inspected for label ambiguity. |
| Actual physical overlap | Activities may run simultaneously. | Parallel operators admit interleaved completion orders but have no duration semantics. | Incomparability expresses true causal concurrency, but visible logs remain linearizations. | Both under-specify lifecycle timing. | Neither model alone can prove that two activities physically overlapped; start/complete lifecycle events would be needed. |

# 7. Preferred Representation and Validation Plan

The **POWL model is the canonical representation**. Its root partial order directly expresses the non-block-structured dependency graph: planning and design have different predecessors, the trial joins those work products, reviews and consultation remain independent, and release joins all outstanding obligations. The process tree is useful as a conservative, easily understandable approximation, but its artificial phase barrier should not be treated as the authoritative business rule.

A concrete validation plan is:

1. **Static structural checks**
   - Confirm that every intended activity label occurs exactly once as a static visible node in each source model.
   - Compute the transitive closure of the POWL root order and assert key relations such as:
     - `Contain Material < Plan Verification`;
     - `Analyze Root Cause < Design Corrective Action`;
     - both `Plan Verification` and `Design Corrective Action < trial_loop`;
     - route, supplier option, and trial loop `< Release Material`.
   - Assert the absence of unintended reachability between the route and trial, route and planning, supplier and trial, and the two high-risk reviews.

2. **Conversion to accepting Petri nets**
   - Where supported by the installed PM4Py version, convert both models:
     ```python
     tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)
     powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
     ```
   - Inspect the resulting initial and final markings and verify that archive is on every successful completion path.

3. **Soundness checking**
   - Run:
     ```python
     pm4py.check_soundness(
         tree_net, tree_im, tree_fm, print_diagnostics=True
     )
     pm4py.check_soundness(
         powl_net, powl_im, powl_fm, print_diagnostics=True
     )
     ```
   - Investigate dead transitions, deadlocks, livelocks, residual tokens, and improper completion. A successful soundness result is necessary evidence but is not evidence that the model matches the narrative.

4. **Bounded and sampled playout**
   - Use `pm4py.play_out(...)` on the source models or converted nets.
   - Bound exploration to, for example, 40 visible events and at most three adjustments per sampled trace; sample enough traces to cover both risk branches, both supplier branches, both high-risk review orders, and zero through three loop repetitions.
   - Check invariants on every generated complete trace:
     - first event is registration and last is archive;
     - every execution has the two work products before it;
     - release has a preceding complete route;
     - consultation, if present, occurs exactly once before release;
     - each adjustment lies between an inspection and a later execution–inspection pair.

5. **Explicit trace tests**
   - Encode the eight witness traces as PM4Py traces using the `concept:name` event attribute.
   - Use accepting-net replay or zero-deviation alignments as the membership criterion.
   - Require the POWL model to accept A1–A5 and reject F1–F3.
   - Require the process tree to accept A1–A4, reject A5 for the documented approximation reason, and reject F1–F3.
   - Add generated variants with regulatory review before quality review and with two or three adjustments.

6. **Silent-behavior and duplicate-label checks**
   - Verify complete executions both with and without `Consult Supplier`.
   - Check that the supplier skip is silent, cannot bypass the risk route or trial obligations, and does not belong to a silent-only cycle.
   - Verify that consultation cannot fire twice and that selecting the silent branch prevents a later consultation.
   - Count visible source nodes by label and report any duplicate-labelled transitions introduced by Petri-net conversion. Distinguish legitimate repeated firing of the loop transitions from static duplicate transitions.

7. **Limits of validation**
   - Bounded playout cannot prove properties for an unbounded number of trial repetitions.
   - Soundness does not prove fidelity to risk data, supplier data, or inspection results.
   - Conversion may introduce silent transitions or alter the shape in ways that require semantic inspection.
   - Completion-only traces cannot validate start-time dependencies, durations, or actual temporal overlap.
   - Alignment acceptance demonstrates language membership under a particular PM4Py semantics and configuration, not correctness of the omitted data guards.

# 8. Final Self-Critique

1. The POWL model is faithful only at the control-flow and completion-event level; it cannot enforce that the chosen route, supplier branch, or inferred inspection outcome agrees with real case data.
2. Treating incomparability as true concurrency does not establish physical overlap. Some narrative start-time constraints are only approximated by completion precedence.
3. POWL constructor and conversion support can vary across PM4Py releases, so the code may require minor version-specific adaptation even though it follows the stated APIs.
