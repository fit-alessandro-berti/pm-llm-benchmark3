# 5. PM4Py role-discovery and similarity code

The following Python pseudocode demonstrates how to leverage PM4Py while mitigating the risks of naïve frequency clustering. It emphasizes joining organizational mining with case complexity and substitution metadata.

```python
import pandas as pd
import pm4py

# 1. Load and Format Data
# Assume 'log_df' contains the event log with required columns
log_df = pm4py.format_dataframe(
    log_df, 
    case_id='case:concept:name', 
    activity_key='concept:name', 
    timestamp_key='time:timestamp',
    resource_key='org:resource'
)

# Ensure custom attributes are preserved for later joining
# case_complexity, temporary_substitution, escalation_level

# 2. Discover Organizational Roles (Naïve Baseline)
# This uses activity-based similarity by default in many implementations
roles_naive = pm4py.discover_organizational_roles(log_df, method='activity_based')

# 3. Discover Resource Similarity (Cosine)
# Returns a matrix or dataframe of similarity scores
similarity_matrix = pm4py.discover_activity_based_resource_similarity(log_df)

# 4. Discover Handover and Working Together Networks
# Crucial for identifying bridging roles like R13_Mateo
hotw_network = pm4py.discover_handover_of_work_network(log_df)
working_together = pm4py.discover_working_together_network(log_df)

# 5. Enrich with Case Complexity and Substitution Data
# PM4Py org mining does not natively weight by case complexity.
# We must aggregate case-level metrics per resource and join.

# Aggregate case complexity per resource
resource_complexity = log_df.groupby('org:resource')['case_complexity'].median().reset_index()
resource_complexity.columns = ['org:resource', 'median_complexity']

# Aggregate temporary substitution flags
# Assuming 'temporary_substitution' is an event attribute indicating if this event 
# occurred during a known substitution period
substitution_counts = log_df[log_df['temporary_substitution'] == True].groupby('org:resource').size().reset_index(name='substitution_events')

# Merge with role discovery output
roles_enriched = roles_naive.merge(resource_complexity, on='org:resource', how='left')
roles_enriched = roles_enriched.merge(substitution_counts, on='org:resource', how='left')

# 6. Refined Clustering Logic (Custom)
# Avoid over-interpreting frequency. Weight complexity higher for specialist roles.
def adjust_role_assignment(row):
    # Example logic: If complexity > 0.7 and volume is low, force 'Specialist' role
    if row['median_complexity'] > 0.75 and row['event_count'] < 200:
        return 'Critical_Specialist'
    # If substitution events are high but core activity differs, mark as 'Shadow'
    if row['substitution_events'] > 10 and row['primary_activity'] not in ['A7', 'A8']:
        return 'Shadow_Role'
    return row['discovered_role']

roles_enriched['refined_role'] = roles_enriched.apply(adjust_role_assignment, axis=1)

# 7. Validation against Handover Network
# Check if 'Critical_Specialist' receives handovers from 'Generalist'
# This validates the hierarchy without assuming it from titles
critical_receivers = hotw_network[hotw_network['sink'].isin(roles_enriched[roles_enriched['refined_role']=='Critical_Specialist']['org:resource'])]
```

**Key Considerations in Code:**
*   **Complexity Join:** Standard `discover_organizational_roles` ignores `case_complexity`. The manual join is required to distinguish R03 from R04.
*   **Substitution Flag:** The code assumes a pre-processed flag for substitution periods. Without this, R07's pricing work looks like normal behavior rather than contingency.
*   **Handover Validation:** Using `hotw_network` validates authority (who sends work to whom) rather than just who does the work.
