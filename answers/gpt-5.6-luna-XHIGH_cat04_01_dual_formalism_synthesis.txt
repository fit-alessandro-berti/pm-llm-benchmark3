# 1. Assumptions and Interpretation

1. A visible event denotes the completion of its activity. Thus, a precedence edge `A -> B` means that `A` has completed before `B` can start; in a completion-only trace this appears as `A` before `B`.
2. The risk route is an XOR selected after `Analyze Root Cause`: the low-risk branch is `Supervisor Review`, and the high-risk branch is a partial order containing both `Quality Review` and `Regulatory Review`. There is no data label for the risk value; the selected control-flow branch is its abstraction.
3. Supplier involvement is modeled as `XOR(tau, Consult Supplier)`. The silent branch means that the supplier is not selected. The visible branch contains one `Consult Supplier` activity, so it is optional and can occur at most once. Its selection is treated as external case data, not as a condition evaluated by the model.
4. A trial iteration is `Execute Trial -> Inspect Trial`. An `Inspect Trial` followed by `Adjust Parameters` is interpreted as a failed inspection. The last `Inspect Trial`, namely the one after which the loop exits and release can eventually occur, is interpreted as passing. Pass/fail is therefore a control-flow interpretation and is not an additional visible event.
5. No duplicate visible activity nodes are introduced. `Execute Trial` and `Inspect Trial` can appear repeatedly because of the loop, but those repetitions are executions of one loop body rather than duplicated model labels or duplicated branches.
6. “May overlap” means true concurrency at the model level, represented by the absence of an ordering constraint. Because the observations are completion traces, concurrency is observed as any legal linearization of the concurrent completions; it does not assert simultaneous wall-clock timestamps.
7. The process tree uses a conservative under-approximation. It preserves the safety constraints and the required visible ordering, but serializes several activities that the narrative allows to overlap. It therefore excludes intended traces rather than admitting a trace that releases material unsafely.
8. The POWL code uses the PM4Py POWL convention in which `OperatorPOWL(Operator.LOOP, [body, redo])` executes `body` once, may take `redo`, and then repeats `body`; it may exit after any completed body. This is the two-child body/redo loop convention, distinct from the three-child process-tree loop convention.

# 3. PM4Py Process-Tree Model

The tree deliberately joins the initial parallel branch before starting the planning/design branch, and then serializes approvals, supplier consultation, and trial work. `LOOP(body, redo, exit)` uses the standard process-tree three-child convention: the body is one trial iteration, `Adjust Parameters` is the redo child, and `tau` is the exit child.

```text
SEQ(
  Register Deviation,
  PAR(Contain Material, Analyze Root Cause),
  PAR(Plan Verification, Design Corrective Action),
  XOR(
    Supervisor Review,
    PAR(Quality Review, Regulatory Review)
  ),
  XOR(tau, Consult Supplier),
  LOOP(
    SEQ(Execute Trial, Inspect Trial),
    Adjust Parameters,
    tau
  ),
  Release Material,
  Archive Case
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    """Create one visible process-tree leaf."""
    return ProcessTree(label=label)


def tau():
    """An unlabeled process-tree leaf is the silent transition tau."""
    return ProcessTree()


def pt(operator, *children):
    """Create an operator and explicitly establish both child directions."""
    parent = ProcessTree(operator=operator)
    parent.children = list(children)
    for child in parent.children:
        child.parent = parent
    return parent


tree = pt(
    Operator.SEQUENCE,
    leaf("Register Deviation"),
    pt(
        Operator.PARALLEL,
        leaf("Contain Material"),
        leaf("Analyze Root Cause"),
    ),
    pt(
        Operator.PARALLEL,
        leaf("Plan Verification"),
        leaf("Design Corrective Action"),
    ),
    pt(
        Operator.XOR,
        leaf("Supervisor Review"),
        pt(
            Operator.PARALLEL,
            leaf("Quality Review"),
            leaf("Regulatory Review"),
        ),
    ),
    pt(
        Operator.XOR,
        tau(),
        leaf("Consult Supplier"),
    ),
    pt(
        Operator.LOOP,
        pt(
            Operator.SEQUENCE,
            leaf("Execute Trial"),
            leaf("Inspect Trial"),
        ),
        leaf("Adjust Parameters"),
        tau(),
    ),
    leaf("Release Material"),
    leaf("Archive Case"),
)
```

This tree represents registration, the first two-way overlap, the low/high approval choice, optional supplier consultation, the repeat-until-pass pattern, release, and archive. It cannot represent the intended non-block-structured timing exactly. In particular, it forces both `Contain Material` and `Analyze Root Cause` to finish before either planning or design starts; it consequently excludes planning that overlaps analysis and design that overlaps containment. It also forces both planning and design to finish before the approval route begins, forces the entire approval route to finish before the first trial, and places supplier consultation in a serial slot rather than allowing it to overlap planning, approvals, or trials. These are conservative exclusions. The tree does not encode the external risk, supplier-selection, or inspection-result data; it represents them through XOR and loop alternatives.

# 4. PM4Py POWL Model

The POWL model has one root strict partial order whose nodes are activities or submodels. The high-risk approval submodel has quality and regulatory review as unordered nodes. The supplier submodel is an XOR with a silent alternative. The trial submodel has an ordered iteration as its body and `Adjust Parameters` as its redo behavior.

```text
APPROVAL_ROUTE = XOR(
  Supervisor Review,
  SPO[Quality Review, Regulatory Review | no edge between them]
)

SUPPLIER_OPTION = XOR(tau, Consult Supplier)

TRIAL_LOOP = LOOP(
  SPO[Execute Trial, Inspect Trial | Execute Trial -> Inspect Trial],
  Adjust Parameters
)

POWL_ROOT = SPO[
  Register Deviation, Contain Material, Analyze Root Cause,
  Plan Verification, Design Corrective Action,
  APPROVAL_ROUTE, SUPPLIER_OPTION, TRIAL_LOOP,
  Release Material, Archive Case
  |
  Register Deviation -> Contain Material,
  Register Deviation -> Analyze Root Cause,
  Contain Material -> Plan Verification,
  Analyze Root Cause -> Design Corrective Action,
  Analyze Root Cause -> APPROVAL_ROUTE,
  Analyze Root Cause -> SUPPLIER_OPTION,
  Plan Verification -> TRIAL_LOOP,
  Design Corrective Action -> TRIAL_LOOP,
  APPROVAL_ROUTE -> Release Material,
  SUPPLIER_OPTION -> Release Material,
  TRIAL_LOOP -> Release Material,
  Release Material -> Archive Case
]
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


def activity(label):
    return Transition(label)


# The high-risk branch is a strict partial order with no edge between
# these two nodes, so either completion order is legal.
quality_review = activity("Quality Review")
regulatory_review = activity("Regulatory Review")
high_risk_approval = StrictPartialOrder(
    [quality_review, regulatory_review]
)

supervisor_review = activity("Supervisor Review")
approval_route = OperatorPOWL(
    Operator.XOR,
    [supervisor_review, high_risk_approval],
)

# The silent XOR branch means that supplier consultation was not selected.
consult_supplier = activity("Consult Supplier")
supplier_option = OperatorPOWL(
    Operator.XOR,
    [SilentTransition(), consult_supplier],
)

# In POWL, LOOP([body, redo]) exits after a completed body or takes the
# redo child before another body execution.
execute_trial = activity("Execute Trial")
inspect_trial = activity("Inspect Trial")
trial_iteration = StrictPartialOrder([execute_trial, inspect_trial])
trial_iteration.order.add_edge(execute_trial, inspect_trial)
adjust_parameters = activity("Adjust Parameters")
trial_loop = OperatorPOWL(
    Operator.LOOP,
    [trial_iteration, adjust_parameters],
)

register_deviation = activity("Register Deviation")
contain_material = activity("Contain Material")
analyze_root_cause = activity("Analyze Root Cause")
plan_verification = activity("Plan Verification")
design_corrective_action = activity("Design Corrective Action")
release_material = activity("Release Material")
archive_case = activity("Archive Case")

powl = StrictPartialOrder(
    [
        register_deviation,
        contain_material,
        analyze_root_cause,
        plan_verification,
        design_corrective_action,
        approval_route,
        supplier_option,
        trial_loop,
        release_material,
        archive_case,
    ]
)

# Root-level dependencies. Every intended dependency is an explicit edge.
powl.order.add_edge(register_deviation, contain_material)
powl.order.add_edge(register_deviation, analyze_root_cause)
powl.order.add_edge(contain_material, plan_verification)
powl.order.add_edge(analyze_root_cause, design_corrective_action)
powl.order.add_edge(analyze_root_cause, approval_route)
powl.order.add_edge(analyze_root_cause, supplier_option)
powl.order.add_edge(plan_verification, trial_loop)
powl.order.add_edge(design_corrective_action, trial_loop)
powl.order.add_edge(approval_route, release_material)
powl.order.add_edge(supplier_option, release_material)
powl.order.add_edge(trial_loop, release_material)
powl.order.add_edge(release_material, archive_case)
```

There is intentionally no edge between `Contain Material` and `Analyze Root Cause`, between `Plan Verification` and `Design Corrective Action`, or between `Quality Review` and `Regulatory Review`. There is also no edge from the approval route to the trial loop, and no edge from the supplier option to planning, design, approvals, or the trial loop. For any such pair that is not related by a transitive path, the strict partial order leaves the pair concurrent, so either completion order is available. The existing edges still apply transitively: for example, both planning and design must precede the trial loop even though they are unordered relative to each other, and all three of the trial loop, approval route, and supplier option must precede release.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and root-cause analysis both follow registration and may overlap. | `PAR(Contain, Analyze)` captures both orders, but its join delays all later work. | Separate root nodes with only registration-to-each edges capture the same concurrency and allow downstream work to start as soon as its own prerequisite is met. | Tree is exact for the two-stream relation but overconstrains their downstream timing. POWL matches. | The tree can delay planning or design and make cycle-time analysis pessimistic. |
| Split dependencies into planning and design | Planning waits only for containment; design waits only for analysis. | Both are placed after a join of containment and analysis, so each waits for too much. | `Contain -> Plan` and `Analyze -> Design` are independent edges. | Tree overconstrains; POWL is faithful. | The tree can hide early verification planning or corrective-action work that would be operationally useful. |
| Risk route | Low risk is one supervisor review; high risk is concurrent quality and regulatory review, selected after analysis. | XOR and the high-risk parallel branch are correct, but the whole route is delayed until planning and design finish. | XOR is after analysis; the high-risk SPO has no quality/regulatory edge. | Tree overconstrains start time; POWL matches the stated route semantics. | The tree may report avoidable approval latency; POWL supports realistic overlap. |
| Approval overlap with trial | The trial needs planning and design, not completed approval. | The sequence puts approval before the trial, rejecting T2 and T5. | No approval-to-trial edge; both independently precede release. | Tree overconstrains; POWL matches. | The tree can prevent a legitimate early trial and misrepresent lead time. |
| Optional supplier consultation | It is selected at most once after analysis, may overlap work, and must precede release when selected. | XOR with tau gives correct cardinality, but its serial position is after approval and before trial. | XOR with `SilentTransition`, analysis-to-option, and option-to-release edges directly expresses the condition. | Tree overconstrains timing; POWL is faithful under the data-choice abstraction. | The tree can delay supplier engagement; POWL preserves scheduling flexibility while protecting release. |
| Repeat-until behavior | Each failed inspection causes adjustment and another execute/inspect cycle; a passing inspection exits. | Three-child loop encodes body, redo, and silent exit; it cannot inspect a data value. | Two-child POWL loop encodes body and redo with implicit exit; it also abstracts the result. | Neither is underconstrained for the stated trace abstraction, but both omit the actual inspection predicate. | Conformance can validate ordering, not whether a real inspection result justified the exit. |
| Release synchronization | Release waits for a passing trial, the selected approval route, and selected supplier consultation. | Serial placement guarantees all prerequisites but imposes an unnecessary total order. | Three explicit incoming edges to release form the required synchronization. | Tree is safe but overconstrained; POWL matches. | The tree may suppress safe parallel completion and distort throughput estimates. |
| Duplicate-label risk | Activities are recorded by visible label, while trial activities repeat through a loop. | No duplicated visible leaves; the loop repeats one body. | No duplicated visible transitions; the loop repeats the same transition objects. | Neither structurally duplicates labels, but both make iteration identity invisible in a label-only log. | Replay must distinguish legitimate loop repetition from accidental duplicate model branches. |

# 7. Preferred Representation and Validation Plan

POWL is the preferred canonical representation. Its root strict partial order expresses the independently progressing obligations and the release synchronization without forcing a block structure. Its nested XORs express the risk and supplier alternatives, and its loop expresses repeat-until-pass. The process tree remains useful as a conservative, block-structured fallback, but it is not an equivalent serialization of the intended behavior.

A concrete validation plan is:

1. Convert each model to an accepting Petri net where the installed PM4Py version supports the conversion:
   ```python
   import pm4py

   tree_net, tree_im, tree_fm = pm4py.convert_to_petri_net(tree)
   powl_net, powl_im, powl_fm = pm4py.convert_to_petri_net(powl)
   ```
   Treat successful conversion as only a construction result, not as evidence that the conversion preserved the intended semantics.
2. Run soundness diagnostics on both converted nets and inspect the diagnostics as well as the Boolean result:
   ```python
   pm4py.check_soundness(
       tree_net, tree_im, tree_fm, print_diagnostics=True
   )
   pm4py.check_soundness(
       powl_net, powl_im, powl_fm, print_diagnostics=True
   )
   ```
   Check that every reachable marking can terminate at the archive completion and that no converted silent branch creates a deadlock.
3. Perform bounded or sampled playout from each model/net, limiting the number of generated traces and the maximum number of loop iterations. Confirm that generated traces contain registration first, archive last, valid route alternatives, and no adjustment after the final inspection.
4. Replay or align all five positive witnesses T1–T5 and require acceptance by the POWL model. Replay F1–F3 and require rejection, recording the first violated edge or missing route/synchronization condition. Run the same tests against the process tree and retain the deliberate T2/T5 rejections as evidence of its conservative approximation.
5. Check silent behavior explicitly: project silent transitions out of playout traces and verify that the silent supplier branch produces no `Consult Supplier` event, while the visible branch produces exactly one. Inspect the converted net for unlabeled transitions and verify that the only visible repeated labels arise from the trial loop, not from duplicated visible nodes.
6. Use pairwise order tests on sampled traces: confirm both `Contain Material`/`Analyze Root Cause` orders, both high-risk review orders, and traces in which approval or supplier work completes before and after trial work. Also verify that no sample violates `Contain -> Plan`, `Analyze -> Design`, either prerequisite to the trial loop, or any of the three incoming release edges.

This plan cannot prove unbounded loop behavior by finite playout. Petri-net soundness checks the converted model, not its faithfulness to unrepresented case data. Completion traces cannot validate actual overlap durations, and the pass/fail abstraction cannot establish that a real inspection passed. Finally, different PM4Py releases may expose small POWL conversion or loop-construction differences, so the constructed object and converted net should be inspected in the target runtime.

# 8. Final Self-Critique

1. The POWL code assumes the two-child PM4Py POWL loop convention; a PM4Py release with a different loop arity would require a small API adaptation.
2. Semantically, neither model represents the actual risk, supplier-selection, or inspection-result predicates; it only represents their control-flow alternatives and therefore cannot validate whether a particular case was correctly classified.
3. The conservative tree is safe but materially incomplete: it rejects legitimate overlap traces, so it should not be used to estimate the full process’s attainable throughput or concurrency.
