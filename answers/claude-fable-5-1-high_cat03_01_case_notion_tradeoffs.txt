## 1. Analytical assumptions

**Case notion.** The rule that assigns each event to trace identifiers so a classical log can be built. Flattening on object type T: for each object o of type T, the trace of o is the timestamp-ordered list of events e with (e, o) in the E2O relation. Events with no object of type T vanish; events related to k objects of type T are written into k traces.

**Convergence.** One event relates to several objects of the case type and is copied. Example: e16 (Dispatch) relates to O1, O2, O3, so the Order log holds three copies of one physical dispatch of D2.

**Divergence.** One case object relates to several objects of another type that each pass through the same activities, so the trace repeats activities whose mutual order carries no process meaning. Example: O1 contains I11 and I12, packed (e11, e12), dispatched (e15, e16) and confirmed (e23, e24) separately, producing Pack→Pack, Dispatch→Dispatch and Confirm Delivery→Confirm Delivery edges that describe two parallel item sub-lifecycles, not rework.

**Copied shared events.** Both evidence and duplication, depending on the question. For "was O2 dispatched?" the copy of e16 in O2's trace is evidence. For "how many dispatches did the warehouse perform?" it is duplication: there were three Dispatch events (e15, e16, e17), not the six the Order log shows. I therefore always carry two counts per activity, distinct event identifiers and trace-rows, and treat their gap as a diagnostic.

**Permitted transformations.**
1. *Direct E2O only (default).* Payments never see Issue Invoice, Packages never see Add Item, Deliveries never see Pack Package.
2. *Explicit propagation through O2O (opt-in, labelled).* E.g. attach e18 to M1 via `M1 settles V1`, or e05/e06 to P1/P2 via `packs`. Always compared against the direct variant (Section 7). Never done silently, because the O2O graph here is one connected component (O1–P2–D2–P3–O3–P4–O4 plus invoices and payments), so unrestricted propagation attaches every event to every object.
3. *Weighting.* Each trace-row of a shared event may be weighted 1/k, k being the number of case objects related to the event (e16 contributes 1/3 to each of O1, O2, O3).
4. *No event invention*, even where a "Create Delivery" would make lifecycles more natural.

## 3. Concrete distortion analysis

1. **Cross-order package P3 in the Order flattening (harmful for frequencies, informative for coverage).** e13 (Pack Package, P3) is written into both O2 and O3, as are e16 and e24. The Order log reports Pack Package 6 times against 4 real packing events and Dispatch/Confirm Delivery 6 each against 3. A "packages per hour" KPI from this log is inflated by 50%. The copies remain correct evidence that both orders were handled by P3.

2. **Cross-order package P4 in the Item and Package flattenings (context-dependent).** I32 (O3) and I41 (O4) have identical traces (e09/e10→e14→e17→e27) and P4 looks like every other package. Neither log reveals that O4's only item waited to be packed with another order's item, nor that O4's confirmation (e27, 10:00 on 4 Feb) is the same event as O3's second confirmation. Fine for per-parcel dwell time; blind to "does consolidation delay small orders?".

3. **P3 produces false equivalence in the Item flattening (harmful).** I21 (O2) and I31 (O3) share every event after Add Item. The Item log shows 6 traces, 1 variant, 100% conformance, suggesting a perfectly standardised process, although three of four packages (P3, P4, and O1's split across P1/P2) involve non-trivial packaging decisions. Homogeneity is an artefact of an object type that participates in four activity types and none of the decision events.

4. **Consolidated delivery D2 in the Order flattening (harmful).** e16 and e24 are each written into O1, O2, O3. The edge Dispatch→Issue Invoice appears in O1 (e16→e18), O2 (e16→e19) and O3 (e17→e19), but O1 and O2 share the same start event, so a performance DFG averages three durations from two independent dispatches and overstates confidence in "55 minutes from dispatch to invoicing". In the Delivery flattening D2 is a two-event trace whose 4h55m transit cannot be recognised as consolidated, because the link to P2 and P3 is only in O2O.

5. **Consolidated invoice V2 in the Order flattening (harmful trap).** e19, e22, e25 are copied into O2 and O3, so both orders show Issue Invoice→Record Payment→…→Record Payment. An analyst reads "O2 was paid in two instalments" and likewise for O3. The E2O table cannot support that: M2 (`partially_settles V2`) may have covered exactly O2's share and M3 exactly O3's. The Order log manufactures an order-level payment finding that exists only at invoice level, and counts Record Payment 6 times against 4 payments.

6. **Partial payment creates a pseudo-loop in the Order flattening (harmful).** O2: …e22 Record Payment→e24 Confirm Delivery→e25 Record Payment. O3: …e24 Confirm Delivery→e25 Record Payment→e27 Confirm Delivery. The DFG holds Record Payment→Confirm Delivery (e22→e24 in O2, O3; e25→e27 in O3) and Confirm Delivery→Record Payment (e24→e25 in O2, O3). Opposite edges between the same activities look like a control-flow loop ("payment triggers re-delivery"); in reality two independent lifecycles (V2's instalments, D2/D3's deliveries) interleave on the same orders. The same instalments in the Invoice flattening (V2: e19→e22→e25) are informative, because there the second payment genuinely follows the first on the same object.

7. **Near-singleton lifecycles of Payment and Delivery (context-dependent).** The Payment log has four one-event traces (e21, e22, e25, e26): no edges, zero durations. The Delivery log has three two-event traces; a log skeleton reports "Dispatch always followed by Confirm Delivery" from three observations. The trap is believing the process for these objects has been mined when only start and end timestamps have been tabulated. The legitimate use is transit time: D3's 22h45m against D1's 3h is real.

8. **Divergence self-loops on O1 and O3 in the Order flattening (harmful if read as rework).** O1 yields Add Item→Add Item (e05→e06), Pack→Pack (e11→e12), Dispatch→Dispatch (e15→e16), Confirm→Confirm (e23→e24); O3 yields e08→e09, e13→e14, e16→e17. A discovered model will contain self-loops that readers interpret as repeated packing or repeated dispatch attempts. They mean only "the order had two items handled separately". The Item flattening removes them entirely.

9. **Batch closing hides delivery-time variance (harmful for performance).** All Close Order events fall within 11:00–11:10 on 4 Feb (e28–e31), so Create→Close is about 26h for every order (O1 26h00m, O2 26h03m, O3 26h01m, O4 26h04m) although O1's last confirmation was 16:00 on day 1 and O4's 10:00 on day 2. Order lead time shows no variance and conceals an 18-hour spread. Confirm Delivery→Close Order (O1, O3, O4) and Record Payment→Close Order (O2, e25→e29) carry waiting times that are scheduling artefacts.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs to create.**

- *Order log.* Create it: the only log with full coverage and genuine start and end. Safe questions: was each order created, invoiced, paid at least once, delivered at least once, closed; items per order (Add Item rows are never shared); Create→Close lead time with the batch caveat. Unsafe: frequencies of Pack, Dispatch, Confirm, Record Payment; any "the order was paid/dispatched twice" statement.
- *Item log.* Create it as the physical-flow log. Safe: Add Item→Pack waiting (45–57 min for all six items), Pack→Dispatch, Dispatch→Confirm, item lead-time distribution (4h45m to 24h37m). Unsafe: anything about consolidation or orders.
- *Invoice log.* Create it as the financial-flow log. Safe: time to first payment, time to full settlement (V2: 20h55m), share of invoices with more than one payment. Unsafe: attributing payments to orders.
- *Delivery log.* Only as a transit-time table, not for discovery.
- *Package and Payment logs.* Do not create as event logs; keep `ocel.objects` and `ocel.o2o` rows (package composition via `packs`, settlement qualifiers) as attribute tables.

**Questions needing object-centric artefacts.**

- *OC-DFG:* real Dispatch events versus orders served (events vs unique vs total objects); Pack Package→Dispatch annotated per type so Package (4 events) and Order (6 rows) appear side by side.
- *OTG:* which types co-occur in events. It will show Order–Item, Order–Package, Order–Delivery, Order–Invoice, Order–Payment, Item–Package, Item–Delivery, Package–Delivery, Invoice–Payment, and no Invoice–Delivery or Payment–Delivery edge, which directly refutes the loop in distortion 6.
- *ET–OT graph:* Payment appears only in Record Payment, Delivery only in Dispatch and Confirm Delivery: the formal statement of the near-singleton problem before any log is built.
- *Object interaction summary:* the pairs (O1, O2), (O1, O3), (O2, O3), (O3, O4) that share events, the direct measure of Order-log convergence.
- *Equivalent-execution clustering:* whether any order's neighbourhood is isolable. The O2O graph is one component, so clustering on Order should return a single execution; that is itself the finding that no order here is an independent case.

**Reconciling contradictions.** The OC-DFG "events" count is the truth for activity frequencies; the flattened count is the truth for "how many case objects were touched". Flattened performance is accepted only for edges whose endpoints are not shared with other cases of the same type (Create Order→Add Item is safe; Dispatch→Issue Invoice for O1/O2 is not). Each contradiction is recorded as (question, flattened answer with unit, OC answer with unit) rather than resolved by picking a winner.

## 5. Lead-object decision

**Position B. Order is the primary lead object; Item, Invoice and Delivery are explicitly secondary lifecycles; Package and Payment are attribute tables.**

**Decision criteria.** (i) Event coverage; (ii) genuine start and end events; (iii) convergence load (share of copied rows); (iv) divergence load; (v) alignment with the "order fulfilment" question; (vi) whether distortions are removable by a documented transformation or are structural.

**Strongest supporting evidence.** Order is the only type related to all 31 events (Item misses 15, Invoice 24, Package 21, Delivery 25, Payment 27) and the only one with creation (e01–e04) and closing (e28–e31) events. Its convergence load, 11 of 42 rows, is measurable and correctable: weighting by 1/k or reading the OC-DFG "events" count restores 3 Dispatch, 4 Pack, 3 Confirm Delivery, 4 Record Payment. Its divergence is confined to O1 and O3 and disappears when the physical leg is delegated to the Item lifecycle.

**Strongest counterargument.** Three of four orders share packing, dispatch and confirmation events with another order (O2–O3 via P3, O3–O4 via P4, O1–O2–O3 via D2), and two share an invoice and both its payments. The order is not the unit of execution for six of eight activity types; it is a commercial wrapper around consolidated physical and financial units. That argues for Position C: only the interaction graph is trustworthy. The Order log's four variants for four traces also offer no aggregation benefit.

**Residual risk.** After down-weighting, semantic traps remain: the Record Payment↔Confirm Delivery pseudo-loop, the "each order paid twice" reading, and batch-closing lead-time compression. They must be flagged in every deliverable; the risk is a downstream reader receiving the log without the flags.

**Conditions for change.** Move to C if, in the full log, more than roughly half of packages or invoices are cross-order, because corrected Order frequencies would then be dominated by weights rather than observations. Move to A if cross-order consolidation vanishes, leaving only benign multi-item divergence. Make Item primary if the sponsor's questions are exclusively warehouse throughput and transit, since Item has no divergence and its copies are true item-level facts.

## 6. PM4Py analysis outline

```python
import pandas as pd
import pm4py

# --- 0. Raw inspection -----------------------------------------------------
print(ocel)
activity_freq = ocel.events["ocel:activity"].value_counts()          # true event counts
object_type_freq = ocel.objects["ocel:type"].value_counts()
ot_activities = pm4py.ocel_object_type_activities(ocel)                # ET-OT as dict
objects_per_event_type = pm4py.ocel_objects_ot_count(ocel)
temporal_summary = pm4py.ocel_temporal_summary(ocel)
objects_summary = pm4py.ocel_objects_summary(ocel)

# Convergence load: number of objects of each type per event
rel = ocel.relations
objs_per_event_per_type = (rel.groupby(["ocel:eid", "ocel:type"])["ocel:oid"]
                              .nunique().unstack(fill_value=0))
shared_events_by_type = (objs_per_event_per_type > 1).sum()             # Order: 9 shared events

# --- 1. Flattened logs (direct E2O only) -----------------------------------
object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flat = {ot: pm4py.ocel_flattening(ocel, ot) for ot in object_types}

flat_stats = {}
for ot, df in flat.items():
    rows = len(df)
    unique_events = df["ocel:eid"].nunique() if "ocel:eid" in df.columns else None
    flat_stats[ot] = dict(rows=rows, unique_events=unique_events,
                          copies=(rows - unique_events) if unique_events else None,
                          cases=df["case:concept:name"].nunique(),
                          variants=len(pm4py.get_variants(df)))
flat_stats_df = pd.DataFrame(flat_stats).T   # expected Order: 42 rows / 31 unique / 11 copies

# --- 2. Classical discovery on the logs we keep ----------------------------
dfg_order, sa_order, ea_order = pm4py.discover_dfg(flat["Order"])
perf_dfg_order, _, _ = pm4py.discover_performance_dfg(flat["Order"])
dfg_item, sa_item, ea_item = pm4py.discover_dfg(flat["Item"])
dfg_invoice, sa_invoice, ea_invoice = pm4py.discover_dfg(flat["Invoice"])
dfg_delivery, sa_delivery, ea_delivery = pm4py.discover_dfg(flat["Delivery"])

# Divergence artefacts (Pack->Pack, Dispatch->Dispatch, ...) and candidate pseudo-loops
order_self_loops = {k: v for k, v in dfg_order.items() if k[0] == k[1]}
order_bidirectional = {k: v for k, v in dfg_order.items()
                       if (k[1], k[0]) in dfg_order and k[0] != k[1]}

skeleton_order = pm4py.discover_log_skeleton(flat["Order"], noise_threshold=0.0)
skeleton_item = pm4py.discover_log_skeleton(flat["Item"], noise_threshold=0.0)
skeleton_invoice = pm4py.discover_log_skeleton(flat["Invoice"], noise_threshold=0.0)
# Delivery skeleton is computed only to document that 2-event traces make it vacuous
skeleton_delivery = pm4py.discover_log_skeleton(flat["Delivery"], noise_threshold=0.0)

# --- 3. Object-centric artefacts -------------------------------------------
ocdfg = pm4py.discover_ocdfg(ocel)
ocdfg_act_events = ocdfg["activities_ot"]["events"]
ocdfg_act_unique_objects = ocdfg["activities_ot"]["unique_objects"]
ocdfg_act_total_objects = ocdfg["activities_ot"]["total_objects"]
ocdfg_edges_events = ocdfg["edges"]["event_couples"]
ocdfg_edges_unique = ocdfg["edges"]["unique_objects"]
ocdfg_edges_total = ocdfg["edges"]["total_objects"]

otg = pm4py.discover_otg(ocel)      # expect no Invoice-Delivery / Payment-Delivery interaction
etot = pm4py.discover_etot(ocel)    # Payment only in Record Payment; Delivery only in Dispatch/Confirm
interactions = pm4py.ocel_objects_interactions_summary(ocel)
order_order_interactions = interactions[
    (interactions["ocel:type"] == "Order") & (interactions["ocel:type_2"] == "Order")]
# expected pairs: (O1,O2), (O1,O3), (O2,O3), (O3,O4)

# --- 4. Equivalent-execution clustering on the primary lead object (Position B) --
# Used as an isolability test: O2O is one connected component, so a single
# cluster is expected and is treated as a finding, not as a segmentation.
order_clusters = pm4py.cluster_equivalent_ocel(ocel, "Order")
n_order_clusters = len(order_clusters)

# --- 5. Cross-check: flattened rows vs true events per activity -----------
count_table = pd.DataFrame({
    "true_events": activity_freq,
    "order_rows": flat["Order"]["concept:name"].value_counts(),
    "item_rows": flat["Item"]["concept:name"].value_counts(),
    "package_rows": flat["Package"]["concept:name"].value_counts(),
}).fillna(0).astype(int)
# Expected: Dispatch 3 / 6 / 6 / 4; Record Payment 4 / 6 / 0 / 0
# Every frequency is reported with its unit; no graph above is treated as self-explanatory.
```

## 7. Sensitivity and validation plan

1. **Down-weight or remove copied shared events in the Order log.** Attach weight 1/k to each row, k from `objs_per_event_per_type["Order"]`. Weighted frequencies should fall to Dispatch 3.0, Pack 4.0, Record Payment 4.0, Confirm Delivery 3.0, matching `activity_freq`. Removal test: keep each shared event only in the lexicographically first related order and note which DFG edges vanish (O2's Dispatch→Issue Invoice, since e16 stays with O1; O3's Confirm Delivery→Record Payment, since e24 stays with O1 and e25 with O2). Edges that vanish are convergence-dependent and are not reported as process behaviour.

2. **Direct E2O versus explicitly propagated relations.** Build a propagated OCEL by adding, via `ocel.o2o`, Add Item events to the Package that `packs` the item, Issue Invoice events to each Payment that settles the invoice, and Pack Package events to the Delivery that `carries` the package. Expected: Package traces gain a measurable pre-packing wait (I11 45m for P1, I12 53m for P2); Payment traces become Issue Invoice→Record Payment, but M2 and M3 both inherit e19, introducing a convergence that did not exist; Delivery D2 inherits e12 and e13 and acquires a Pack→Pack self-loop absent from the direct log. Any conclusion that flips between variants ("deliveries show packing rework") is a transformation artefact and is discarded.

3. **Change the lead object.** Re-run the Section 6 pipeline with Item as primary, then Invoice. Compare coverage (31/31 vs 16/31 vs 7/31), performance edges that should agree across leads once copies are recognised as the same event (Dispatch→Confirm per item, package and delivery must all yield D1 3h, D2 4h55m, D3 22h45m), and conclusions supported by only one lead ("two-instalment settlement" is Invoice-only; "Pack→Pack on multi-item orders" is Order-only). Single-lead conclusions are labelled lead-dependent.

4. **Events versus unique versus total objects in the OC-DFG.** For the Order type, expected values: Dispatch 3/4/6, Pack Package 4/4/6, Confirm Delivery 3/4/6, Record Payment 4/4/6, Issue Invoice 3/4/4, Create Order 4/4/4. Where the three coincide (Create Order, Add Item, Close Order) the Order flattening is trustworthy for that activity; where they diverge, the flattened count equals total objects and is relabelled "order-touches". For Item, Dispatch 3/6/6 shows that Item-log inflation is entirely convergence, never divergence.

5. **Interleaving and batch tests.** Check `otg` and `interactions` for any event where a Payment or Invoice co-occurs with a Delivery; expected none, so the Record Payment↔Confirm Delivery edges in `dfg_order` (only O2 and O3, explained by e25 falling between e24 and e27) are documented as interleaving and excluded from control-flow models. Separately, compare the spread of Close Order timestamps (e28–e31, 10 minutes) with the spread of last Confirm Delivery per order (18 hours); if the former is an order of magnitude smaller, redefine lead time as Create Order→last Confirm Delivery (O1 7h00m, O2 6h58m, O3 24h56m, O4 24h54m).
