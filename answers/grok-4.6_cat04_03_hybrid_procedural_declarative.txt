# 1. Policy Interpretation and Conflict Resolution

Material assumptions used throughout the hybrid model:

1. A case is **accepted** iff `Activate Vendor` occurs and **rejected** iff `Reject Vendor` occurs. Those two labels are intended as mutually exclusive terminals of the decision after `Classify Risk`.
2. Every complete case starts with `Receive Onboarding Request` and ends with exactly one `Close Onboarding`.
3. The three fact-finding activities `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` are mandatory, concurrent, and happen once before classification. An additional `Verify Bank Account` is allowed only on the post-activation bank-change path (R11).
4. Clarification is a paired dialogue. Several cycles are allowed, but each `Request Clarification` must be closed by a later `Receive Clarification` before the next request and before any of `Activate Vendor`, `Reject Vendor`, or `Close Onboarding`.
5. `Sanctions Escalation` and `Obtain Legal Opinion` are an optional legal side-path, not part of the stable procedural backbone.
6. `Change Bank Details` and `Suspend Vendor` are a post-activation exception path, not part of the backbone.
7. “Applicable approval” means `Manager Approval` on the low-risk route and `Compliance Approval` on the high-risk route.
8. The event log is assumed to carry `concept:name`, `time:timestamp`, and `org:resource`. It does **not** carry an emergency flag or a joint-authorization attribute (explicit in R6).
9. Test timestamps are hours from case start; temporal-profile parameters are stored in seconds (`hours × 3600`).
10. R12 deviations are **warnings**, never automatic control-flow failures.
11. Procedural conformance is evaluated on a **projection** onto the process-tree alphabet (and, for R11, after dropping any post-activation re-verification). Otherwise optional legal and bank-change events would be false move-on-log deviations.
12. `Release First Payment` occurs at most once (R10), so R11’s “later payment” mainly guards a change inserted **between** activation and the single payment, and only secondarily acts as a defensive rule if R10 is already broken.
13. Standard DECLARE cannot express “if *A* occurred, then *B* must precede *C*”. Approximations are labelled as such and are never silently treated as exact.

**R5 / R6 conflict.** R5 is a universal precedence obligation: after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` in every case. R6 carves out an emergency exception that is **invisible in the log** (joint authorization is off-log) and replaces precedence with a 24-hour responded-existence SLA. An activity-only model cannot satisfy both.

**Resolution A — Legal-strict (implemented default).** Encode R4 as DECLARE `response`. Approximate R5 by forbidding `Obtain Legal Opinion` after `Activate Vendor` (`nonsuccession`). Treat R6 as an off-log exception workflow: a compliance officer may override a precedence failure only with evidence that lives outside PM4Py. The 24-hour gap is still computed as an informational check, but it does not license the ordering.

**Resolution B — Operations-permissive (documented alternative).** Drop the `nonsuccession` approximation. Keep only R4 (`response`). If activation precedes the opinion after an escalation, require an emergency/authorization attribute and `Obtain Legal Opinion` within 24 hours. Because those attributes are absent from the log, the automated result is a **data-quality warning**, not a proven pass.

**Choice and compliance risk.** The implemented dictionaries follow **Resolution A**. Sanctions and legal opinions are high-regret controls; an activity-only engine that “passes” T6 would be pretending to see an authorization the log cannot show. The compliance risk of A is **false non-compliance on genuine emergencies** and a predictable operational workaround (not logging the escalation, or activating in a shadow process). The risk of B is the dual false negative: unauthorized early activations become indistinguishable from authorized ones. The two policies are never merged into one constraint.

# 3. Procedural Backbone

## Compact formal description

Let `τ` be the silent activity. The language of the backbone is the process tree

```
→(
  Receive Onboarding Request,
  ∧(Capture Master Data, Run Sanctions Screening, Verify Bank Account),
  *(τ, →(Request Clarification, Receive Clarification), τ),
  Classify Risk,
  ×(
    →(Reject Vendor, Close Onboarding),
    →(Manager Approval, Activate Vendor, Release First Payment, Close Onboarding),
    →(Enhanced Due Diligence, Compliance Approval, Activate Vendor, Release First Payment, Close Onboarding)
  )
)
```

Alphabet of the tree (projection set):

`{Receive Onboarding Request, Capture Master Data, Run Sanctions Screening, Verify Bank Account, Request Clarification, Receive Clarification, Classify Risk, Enhanced Due Diligence, Manager Approval, Compliance Approval, Reject Vendor, Activate Vendor, Release First Payment, Close Onboarding}`.

Projected **out**: `Sanctions Escalation`, `Obtain Legal Opinion`, `Change Bank Details`, `Suspend Vendor`, and any `Verify Bank Account` after the first `Activate Vendor`.

## PM4Py code

```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree


def leaf(label):
    return ProcessTree(label=label)


def tau():
    return ProcessTree(label=None)


def node(operator, *children):
    tree = ProcessTree(operator=operator)
    tree.children = list(children)
    for child in children:
        child.parent = tree
    return tree


procedural_model = node(
    Operator.SEQUENCE,
    leaf("Receive Onboarding Request"),
    node(
        Operator.PARALLEL,
        leaf("Capture Master Data"),
        leaf("Run Sanctions Screening"),
        leaf("Verify Bank Account"),
    ),
    node(
        Operator.LOOP,
        tau(),  # do
        node(
            Operator.SEQUENCE,
            leaf("Request Clarification"),
            leaf("Receive Clarification"),
        ),  # redo
        tau(),  # exit
    ),
    leaf("Classify Risk"),
    node(
        Operator.XOR,
        node(
            Operator.SEQUENCE,
            leaf("Reject Vendor"),
            leaf("Close Onboarding"),
        ),
        node(
            Operator.SEQUENCE,
            leaf("Manager Approval"),
            leaf("Activate Vendor"),
            leaf("Release First Payment"),
            leaf("Close Onboarding"),
        ),
        node(
            Operator.SEQUENCE,
            leaf("Enhanced Due Diligence"),
            leaf("Compliance Approval"),
            leaf("Activate Vendor"),
            leaf("Release First Payment"),
            leaf("Close Onboarding"),
        ),
    ),
)
```

A silent-exit loop with three children is used so the model matches PM4Py’s usual `*(do, redo, exit)` shape. Semantically `*(τ, Request→Receive, τ)` is zero or more complete clarification pairs.

## Concurrency, choices, loops, terminals, exclusions

- **Concurrency.** After receipt, the three checks are a true AND-split/AND-join. Any interleaving is legal; `Classify Risk` is not enabled until all three have fired.
- **Choices.** After classification the model is a three-way XOR: reject, low-risk (`Manager Approval` only), or high-risk (`Enhanced Due Diligence` then `Compliance Approval`). That is the positive half of R2 and R8.
- **Clarification loops.** Only complete `Request Clarification → Receive Clarification` pairs, and only **between** the AND-join and `Classify Risk`. This is a **block-structured approximation**. It accepts T2 (pairs after all three checks, before classify) and rejects T5 (unanswered request). It does **not** generate a request that is still open during the parallel checks, nor a clarification cycle after classification. Those residual cases are left to DECLARE + the custom unmatched-request scan.
- **Terminals.** Rejection goes to `Close Onboarding` without payment. Acceptance always does `Activate Vendor → Release First Payment → Close Onboarding`. The XOR makes R1 structural.
- **Deliberately excluded.** `Sanctions Escalation` / `Obtain Legal Opinion` (R4–R7, and the R5/R6 conflict) and `Change Bank Details` / `Suspend Vendor` / extra `Verify Bank Account` (R11). Putting them in the tree would either over-linearize a side-path or require non-block-structured skip links that a process tree cannot state honestly.

If an accepting Petri net is required at deploy time, convert with `pm4py.convert_to_petri_net(procedural_model)` and keep the same projection.

| Rule | Direction and semantics |
|---|---|
| `init(Receive Onboarding Request)` | First event of every case is receipt |
| `exactly_one` on start, capture, screening, classify, close | Each occurs once; not “at most once” for the optional terminals |
| `existence(Verify Bank Account)` | At least one verification; a later extra verify (R11) remains legal |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | **Response (R4):** every escalation is eventually followed by an opinion. No claim that the opinion is immediately next (`chainresponse` would be wrong). No claim that the opinion precedes activation (that is R5) |
| `response(Request Clarification, Receive Clarification)` | Weaker half of R3: every request is eventually answered. Other activities may intervene |
| `altresponse(Request Clarification, Receive Clarification)` | **Alternate response:** after a request, a receive occurs **before the next request**. Stronger than `response`; weaker than `chainresponse` (T2 has a 26-hour gap with no interleaved modelled events, but the rule must still allow interleaving) |
| `response(Activate Vendor, Release First Payment)` and `precedence` of the same pair | Together these are **succession**: payment occurs iff it is after activation, on complete accepted cases. Written as the two halves so the table can name them |
| `response(Change Bank Details, Suspend Vendor)` | Partial R11: a change is eventually followed by a suspension. Does not test “after activation” |
| `response(Reject Vendor, Close Onboarding)` / `response(Release First Payment, Close Onboarding)` | Both terminals drain to close |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | **Precedence (R7):** if escalation occurs, screening already occurred. Not `chainprecedence` |
| `precedence` of each check before `Classify Risk` | Classification cannot start with an open check |
| `precedence(Classify Risk, {Reject, Manager, EDD})` | No decision activity before classification |
| `precedence(Enhanced Due Diligence, Compliance Approval)` | High-risk order |
| `nonsuccession(Activate Vendor, Obtain Legal Opinion)` | **Legal-strict approximation of R5**, not `noncoexistence`: the two labels may share a case, but the opinion may not occur **after** activation. Different from `noncoexistence` (which T7 must pass) and from `precedence(Obtain Legal Opinion, Activate Vendor)` (which T1/T2 must pass). **Not used under Resolution B** |
| `noncoexistence` pairs | **Noncoexistence**, not `nonsuccession`: the banned labels may not share a case in either order. Covers R1, the negative half of R2, R8, and “no payment on a rejected case” |

Templates **not** used, on purpose: `chainresponse` / `chainsuccession` (they demand adjacency the policy does not demand); `succession(Sanctions Escalation, Obtain Legal Opinion)` (would force opinion ⇒ escalation, which is not stated); `precedence(Obtain Legal Opinion, Activate Vendor)` (would force an opinion on every activation).

**Orientation.** For every pair `(A, B)`:

- `always_before(A, B)` means “if *B* occurs, *A* has already occurred” (DECLARE-precedence direction).
- `always_after(A, B)` means “if *A* occurs, *B* occurs later” (DECLARE-response direction).
- `never_together(A, B)` is symmetric; the written order is only a tuple encoding.
- `equivalence(A, B)` means the two labels occur equally often in every case (including 0 = 0).

**What is populated, and why.** Equivalence of the clarification pair is the count half of R3. Equivalence of activate and first payment is the backbone plus R10 (rejected cases contribute 0 = 0). `activ_freq` is the only honest encoding of R10’s “at most once” and of “verify may repeat after a bank change”. `never_together` mirrors the DECLARE `noncoexistence` set. `always_before(Activate Vendor, Change Bank Details)` encodes the R11 trigger “if a change occurs, activation was earlier”.

**`directly_follows` is empty on purpose.** An allow-list DFG would have to close under every interleaving of the three checks, every optional legal insertion point (T6 vs T7), and the emergency order `Activate Vendor → Obtain Legal Opinion`. A partial allow-list would fail legal traces. PM4Py’s checker treats a present empty set as “no DF pair is allowed”, which would fail T1–T8. Deployment must therefore **disable the DF check when the set is empty** (treat empty as unconstrained, not as a universal ban).

**Overlap and disagreement with the other layers.**

- Agree with DECLARE: `always_after(Sanctions Escalation, Obtain Legal Opinion)` ≡ R4 `response`; `always_before(Run Sanctions Screening, Sanctions Escalation)` ≡ R7 `precedence`; `never_together` ≡ `noncoexistence`.
- Agree with the tree: start, AND-join before classify, XOR mutex, at-most-once terminals.
- **Policy-neutral on R5/R6.** The skeleton does **not** contain `always_before(Obtain Legal Opinion, Activate Vendor)` (that would fail T1/T2) and does **not** contain a “never after activation” pair for the opinion. T6 therefore **passes** the skeleton under both resolutions. The Legal-strict `nonsuccession` lives only in DECLARE, so DECLARE and the skeleton **disagree on T6 under Resolution A**. That disagreement is intentional: the skeleton stays observational; the chosen legal policy is an overlay.
- `equivalence(Request, Receive)` is stricter than `altresponse` on counts and will fail T5 even if someone removed the DECLARE rule.
- `activ_freq` for `Verify Bank Account` is looser than the tree (which generates exactly one) and is reconciled by the projection rule in §3.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800.0, 86400.0),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200.0, 21600.0),
    ("Activate Vendor", "Release First Payment"): (259200.0, 129600.0),
}
zeta = 2.0
```

Means and standard deviations are the R12 hour figures converted with `× 3600`. A pair `(A, B)` is scored only when a completed *A*→*B* instance exists in the case. A deviation is flagged when `|elapsed − mean| > zeta × std`, i.e. outside the two-sigma band.

| Pair | Band at `zeta = 2.0` |
|---|---|
| Request → Receive | 48h ± 48h → `[0h, 96h]` |
| Escalation → Opinion | 12h ± 12h → `[0h, 24h]` |
| Activate → First payment | 72h ± 72h → `[0h, 144h]` |

**Why these are warnings, not control-flow failures.** R12 is explicit: compliance wants the delays flagged, not used as automatic rejection. Waiting time is also a poor proxy for authorization (R6’s 24-hour emergency SLA is a **different** clock: activate→opinion, not escalation→opinion). A case can be legally ordered and still late (T7), or timely and still illegally ordered (T6 under Resolution A). Mixing those signals into the process tree or DECLARE would collapse a performance KPI into a soundness constraint and would make T7 look like the same class of defect as T8.

# 7. Resource- and Data-Aware Checks

Required attributes: `case:concept:name`, `concept:name`, `time:timestamp`. R9 additionally needs `org:resource`. R6 additionally needs attributes the log **does not contain** (`emergency`, `joint_authorization`). Missing `time:timestamp` disables R5/R6/R11/R12. Missing `org:resource` on either endpoint of a four-eyes pair disables that SoD verdict and raises a data-quality finding; it is **not** rewritten as a DECLARE fail.

```python
import pandas as pd
import pm4py

HOUR = 3600
EMERGENCY_SLA_HOURS = 24

APPROVALS = ("Manager Approval", "Compliance Approval")
TERMINALS = ("Activate Vendor", "Reject Vendor", "Close Onboarding")


def _sorted_case(df, case_id):
    c = df[df["case:concept:name"] == case_id].copy()
    return c.sort_values("time:timestamp")


def _resources(case_df, activity):
    return list(case_df.loc[case_df["concept:name"] == activity, "org:resource"])


def _times(case_df, activity):
    return list(case_df.loc[case_df["concept:name"] == activity, "time:timestamp"])


def check_r9_four_eyes(log_or_df):
    """
    R9. Fail-closed only when both activities are present and both resources
    are present and equal. Missing resource => not_evaluated + data-quality.
    """
    df = pm4py.convert_to_dataframe(log_or_df) if not isinstance(log_or_df, pd.DataFrame) else log_or_df
    findings = []

    # Library filter: keeps cases where the two activities have different resources.
    # It ignores cases that lack one of the two activities. We still handle
    # "applicable approval" ourselves because the second activity is route-dependent.
    _ = pm4py.filter_four_eyes_principle(log_or_df, "Verify Bank Account", "Manager Approval")
    _ = pm4py.filter_four_eyes_principle(log_or_df, "Verify Bank Account", "Compliance Approval")
    _ = pm4py.filter_four_eyes_principle(log_or_df, "Capture Master Data", "Activate Vendor")

    for case_id, cdf in df.groupby("case:concept:name"):
        cdf = cdf.sort_values("time:timestamp")
        verify_res = _resources(cdf, "Verify Bank Account")
        capture_res = _resources(cdf, "Capture Master Data")
        activate_res = _resources(cdf, "Activate Vendor")
        present_approvals = [a for a in APPROVALS if a in set(cdf["concept:name"])]

        def missing(vals):
            return any(v is None or (isinstance(v, float) and pd.isna(v)) or v == "" for v in vals)

        if activate_res:
            if not capture_res or missing(capture_res) or missing(activate_res):
                findings.append((case_id, "R9-capture-activate", "not_evaluated"))
            elif set(capture_res) & set(activate_res):
                findings.append((case_id, "R9-capture-activate", "fail"))
            else:
                findings.append((case_id, "R9-capture-activate", "pass"))

        if present_approvals:
            if not verify_res or missing(verify_res):
                findings.append((case_id, "R9-verify-approval", "not_evaluated"))
            else:
                ok = True
                uneval = False
                for appr in present_approvals:
                    appr_res = _resources(cdf, appr)
                    if missing(appr_res):
                        uneval = True
                    elif set(verify_res) & set(appr_res):
                        ok = False
                if uneval:
                    findings.append((case_id, "R9-verify-approval", "not_evaluated"))
                else:
                    findings.append((case_id, "R9-verify-approval", "pass" if ok else "fail"))
    return findings


def check_r3_unmatched_requests(df):
    """Close the DECLARE gap: no terminal while a request is unanswered."""
    findings = []
    for case_id, cdf in df.groupby("case:concept:name"):
        open_req = 0
        status = "pass"
        for _, ev in cdf.sort_values("time:timestamp").iterrows():
            name = ev["concept:name"]
            if name == "Request Clarification":
                if open_req > 0:
                    status = "fail"  # next request before receive (also altresponse)
                open_req += 1
            elif name == "Receive Clarification":
                open_req = max(0, open_req - 1)
            elif name in TERMINALS and open_req > 0:
                status = "fail"
                break
        if open_req > 0:
            status = "fail"
        findings.append((case_id, "R3-unmatched", status))
    return findings


def check_r5_legal_strict(df):
    """Resolution A. Activity-only but not a standard DECLARE template."""
    findings = []
    for case_id, cdf in df.groupby("case:concept:name"):
        esc = _times(cdf, "Sanctions Escalation")
        act = _times(cdf, "Activate Vendor")
        opi = _times(cdf, "Obtain Legal Opinion")
        if not esc or not act:
            findings.append((case_id, "R5", "pass"))
            continue
        if not opi or min(opi) >= min(act):
            findings.append((case_id, "R5", "fail"))
        else:
            findings.append((case_id, "R5", "pass"))
    return findings


def check_r6_emergency(df):
    """
    Resolution B. Cannot pass from the log: emergency attributes do not exist.
    If activation precedes opinion after escalation:
      - missing attributes => warning (cannot prove authorization)
      - if opinion exists, also report whether the 24h SLA held.
    """
    findings = []
    emergency_col = "emergency" if "emergency" in df.columns else None
    auth_col = "joint_authorization" if "joint_authorization" in df.columns else None

    for case_id, cdf in df.groupby("case:concept:name"):
        esc = _times(cdf, "Sanctions Escalation")
        act = _times(cdf, "Activate Vendor")
        opi = _times(cdf, "Obtain Legal Opinion")
        if not esc or not act:
            findings.append((case_id, "R6", "pass"))
            continue
        early = (not opi) or (min(act) < min(opi))
        if not early:
            findings.append((case_id, "R6", "pass"))
            continue
        sla_ok = bool(opi) and ((min(opi) - min(act)).total_seconds() <= EMERGENCY_SLA_HOURS * HOUR)
        if emergency_col is None or auth_col is None:
            findings.append((case_id, "R6", "warning"))  # missing enabling attributes
            findings.append((case_id, "R6-24h", "pass" if sla_ok else "fail"))
            continue
        row0 = cdf.iloc[0]
        authorized = bool(row0[emergency_col]) and bool(row0[auth_col])
        findings.append((case_id, "R6", "pass" if authorized and sla_ok else "fail"))
    return findings


def check_r11_bank_change(df):
    findings = []
    for case_id, cdf in df.groupby("case:concept:name"):
        evs = list(cdf.sort_values("time:timestamp")["concept:name"])
        if "Activate Vendor" not in evs:
            findings.append((case_id, "R11", "pass"))
            continue
        i_act = evs.index("Activate Vendor")
        status = "pass"
        for i, name in enumerate(evs):
            if name != "Change Bank Details" or i < i_act:
                continue
            if "Suspend Vendor" not in evs[i + 1 :]:
                status = "fail"
            later_pay = [j for j, n in enumerate(evs) if n == "Release First Payment" and j > i]
            for j in later_pay:
                if "Verify Bank Account" not in evs[i + 1 : j]:
                    status = "fail"
        findings.append((case_id, "R11", status))
    return findings
```

When `org:resource` is absent, `filter_four_eyes_principle` cannot justify a pass; the wrapper records `not_evaluated`. When the emergency columns are absent — the actual situation in this scenario — Resolution B **cannot** return `pass` for an early activation; it returns `warning`. Resolution A does not grant a pass from a 24-hour arrival alone.

# 9. Contradictions, Redundancies, and Blind Spots

**Duplicated enforcement.** R1, R2’s negative half, and R8 are written three times (tree XOR, DECLARE `noncoexistence`, skeleton `never_together`). R4/R7 are written twice (DECLARE + skeleton). R10 is in the tree **and** in `activ_freq`. Duplication is useful only if layers can be switched off independently; if all layers are AND-ed, a single disputed rule (especially R5) will be counted as several failures and look more severe than T5 or T8.

**Loops and post-activation changes.** The tree’s clarification loop is block-structured and sits only before classify. A request after classify could satisfy DECLARE `altresponse` and still fail the tree — or, conversely, Request → Activate → Receive would satisfy `altresponse` and fail the custom R3 scan. R11’s extra `Verify Bank Account` would break a naïve (unprojected) tree replay while remaining legal in `activ_freq`. R10’s “payment at most once” makes a literal second “later payment” already illegal, so R11’s re-verify clause is either a guard on the **same** payment after a post-activation change, or a dead letter. Encoding both rules without stating that reading produces an inconsistent exception path.

**Vacuity.** `precedence(Run Sanctions Screening, Sanctions Escalation)`, `response(Sanctions Escalation, Obtain Legal Opinion)`, and every `noncoexistence` pair involving a label that never fires are vacuously true on T1–T5 and T8. Vacuous success is not evidence that the sanctions path was tested. `init` + `exactly_one(Receive Onboarding Request)` is similarly uninformative on a log that was extracted with that start activity by construction.

**Missing case attributes.** R6’s entire enabling condition is off-log. R9 disappears if `org:resource` is stripped. There is no `risk_tier` attribute, so the model infers low-risk vs high-risk from which approval appears — it cannot detect “classified high-risk but took the manager route” as a data error, only as a control-flow choice. There is no `emergency` bit, so T6 cannot be proven compliant.

**Timestamp-only limitations.** All clocks are case-relative event timestamps. They do not distinguish waiting time from service time, ignore business calendars, and treat a 2-hour activate→pay (T7) as statistically unusual-but-in-band rather than as a possible backdated pair. The R12 band for activate→pay is so wide (`[0, 144]h`) that only extreme delays warn. The R6 24-hour SLA uses a **different** pair (activate→opinion) than the R12 pair (escalation→opinion); T6 is inside both, T7 breaches only R12.

**Support / confidence are not normative truth.** Every rule is stored with `support = 1.0` and `confidence = 1.0` because this is a **prescribed** policy model, not a mined one. Feeding these dictionaries into a discovery evaluator, or presenting 1.0 confidence to auditors as if the log had empirically validated R5, would launder a design choice (Legal-strict `nonsuccession`) into a statistical fact. Under Resolution B the same field would still say 1.0 on a strictly weaker model. Confidence must not be used as a tie-breaker between R5 and R6.

**Blind spots the hybrid still has.** No rule sees the off-log joint authorization. No rule knows who “the applicable approval” is except by which approval label appears. `directly_follows` is intentionally mute. Standard DECLARE cannot state R3’s “before any final outcome” or R5 exactly; both depend on the custom layer. Projecting legal events out of the tree means a case that **only** contains sanctions activity and never returns to the backbone can still look procedurally healthy on the projection if the remaining labels fit.

# 10. Deployment Recommendation

**Canonical procedural representation.** Keep `procedural_model` as the process tree above. At runtime convert it to an accepting Petri net for alignments (`pm4py.convert_to_petri_net`), but treat the tree as the editable source. Always project the case onto the tree alphabet, and drop post-activation extra verifications, before alignment. Never fold R5, R6, R9, R11, or R12 into the net “for convenience”.

**Authoritative policy layer.** Hard compliance is the **conjunction** of (i) projected procedural fitness, (ii) DECLARE under the **currently selected** legal policy (Resolution A or B — a named configuration flag, not a blended dictionary), and (iii) the custom checks in §7 for everything activity-only models cannot say (R3 unmatched requests, R5 exact order, R6 authorization, R9, R11). The log skeleton is a **diagnostic twin**: it should be run, but a skeleton-only fail that already has a DECLARE/tree explanation is not a second business verdict. Temporal profile is advisory.

**Check order.**

1. Schema: required columns present? Missing `org:resource` / timestamps / (under B) emergency fields → data-quality record, do not invent a control-flow fail.
2. Projected procedural alignment.
3. DECLARE (`pm4py.conformance_declare`) with the active R5/R6 profile.
4. Log skeleton (`pm4py.conformance_log_skeleton`) with the empty-`directly_follows` guard from §5.
5. Custom R3 / R5 / R6 / R9 / R11 (including `filter_four_eyes_principle` as a helper, not as the only SoD implementation).
6. Temporal profile last (`pm4py.conformance_temporal_profile(..., zeta=2.0)`), mapped exclusively to warnings.

**Surfacing contradictions.** Do not AND the six columns into a single traffic light until a human has seen the layer breakdown. In particular:

- If DECLARE (Resolution A) fails T6-style `nonsuccession` and the R6 informational check shows a 24-hour-compliant early opinion, label the case **`policy-dependent: R5 vs R6`**, not “DECLARE broken”.
- If the tree fails and DECLARE passes (or the reverse) on clarification placement, show both and name the approximation.
- If SoD fails (T4) or terminals conflict (T8), those are decisive regardless of temporal health.
- If only R12 fires (T7), the case is **accepted-with-warning**.

The configuration flag `legal_policy ∈ {strict, operations}` must be versioned next to `declare_model`. Switching it swaps the `nonsuccession` block and the decisiveness of `check_r6_emergency`; it must not silently rewrite T6 into a pass without recording that the authorization was never in the log.
