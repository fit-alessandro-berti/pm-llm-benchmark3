## 1. Analytical assumptions

I interpret a **case notion** as a projection of the OCEL onto one selected object type. Each object of that type becomes one case, and every event is assigned to every case whose object appears in the event’s direct E2O relation. The flattened log is therefore a projection, not the original object-centric structure.

I use these working definitions:

- **Convergence**: one event is directly related to two or more objects of the selected type. Flattening copies that event into each corresponding case. Example: in an Order flattening, `e13` is copied to both `O2` and `O3`.
- **Divergence**: one case contains several occurrences of the same activity or several sub-objects, so parallel or multi-instance behaviour is linearised. Example: `O1` contains two `Pack Package` events (`e11`, `e12`), two `Dispatch` events (`e15`, `e16`), and two `Confirm Delivery` events (`e23`, `e24`).

I treat **copied shared events as both evidence and duplication**. They are evidence because, for example, `e13` genuinely concerns both `O2` and `O3`: each order is part of package `P3`. They are also duplication because they are not independent observations; counting them as separate events inflates activity frequencies and variant support. In quantitative comparisons I will use both raw copies and a down-weighted variant.

My default analytical transformation is to use the **given E2O relations only**, without silent propagation through O2O links. I do permit, as explicit robustness checks:

- propagation of events along O2O relations, e.g. adding `e11`, `e12`, `e13` to the delivery traces of `D1`, `D2`, `D3` because deliveries carry packages;
- weighting copied events by `1 / number of related objects of the chosen type`;
- deduplicating by event ID for unique-event analyses.

No additional events are invented.

## 3. Concrete distortion analysis

1. **Cross-order package `P3` under Order flattening.**  
   `e13` is directly related to `O2`, `O3`, `I21`, `I31`, and `P3`. In the Order flattening, `e13` is copied to both `O2` and `O3`. The `Pack Package` frequency in the order log becomes 6 instead of 4. The edge `Add Item  Pack Package` therefore receives two copies that are actually one physical package. This is harmful for counting packages or packing work; it is informative if we want to show that both orders are legitimately involved in `P3`.

2. **Cross-order package `P4` under Item flattening.**  
   `e14`, `e17`, and `e27` are related to both `I32` and `I41`. In the Item flattening, the combined `P4`/`D3` journey is copied into two item cases. The `Dispatch` and `Confirm Delivery` frequencies in the item log become 6 each, even though there are only three physical deliveries. The item log also makes `I32` and `I41` look identical, hiding that they come from `O3` and `O4` and were deliberately consolidated. Harmful for unique delivery counts; informative for per-item logistics.

3. **Consolidated delivery `D2` under Package flattening.**  
   `e16` and `e24` are related to both `P2` and `P3`. In the Package flattening, `D2` appears twice: once in the `P2` trace and once in the `P3` trace. The DFG edge `Dispatch  Confirm Delivery` is counted twice for the same trip. This inflates delivery frequency and makes `D2` look like two delivery jobs. Harmful if the question is “how many delivery trips occurred”; informative if the question is “which packages were on that trip”.

4. **Consolidated invoicing `V2` under Order flattening.**  
   `e19`, `e22`, and `e25` are copied to both `O2` and `O3`. The order log therefore shows `Issue Invoice` four times instead of three, and `Record Payment` six times instead of four. More importantly, both `O2` and `O3` appear to have their own two-payment invoice. In reality there is one invoice, `V2`, covering both orders. This is harmful for financial totals; it is informative only as evidence that both orders are jointly liable.

5. **Partial payment of `V2` under Order versus Invoice flattening.**  
   In the Invoice flattening, `V2` has a clean trace: `e19 Issue Invoice  e22 Record Payment (M2)  e25 Record Payment (M3)`. In the Order flattening, `O2` and `O3` also contain both payments, but the trace is interrupted by `e24 Confirm Delivery`: `e19  e22  e24  e25  e29/e30`. A naive analyst could infer that the delivery happened between two separate payments, or that each order paid twice. The `M2`/`M3` qualifiers are essential to interpret this correctly. Context-dependent: informative with object qualifiers, harmful without them.

6. **Near-singleton lifecycle under Payment flattening.**  
   `M1`, `M2`, `M3`, and `M4` each have exactly one related event: `e21`, `e22`, `e25`, `e26`. Flattening on Payment produces four singleton traces. The DFG has no edges, and no start/end distinction can be made. This is not a process; it is an object inventory. Harmful if chosen as lead object for end-to-end analysis.

7. **Order `O1` split across packages and deliveries.**  
   `O1` has two `Pack Package` events (`e11`, `e12`), two `Dispatch` events (`e15`, `e16`), and two `Confirm Delivery` events (`e23`, `e24`). In the Order flattening, these appear as sequential repeated activities, producing direct same-activity edges: `Pack Package  Pack Package`, `Dispatch  Dispatch`, `Confirm Delivery  Confirm Delivery`. The five-minute gap between `e15` and `e16` is not a control-flow wait; it is simply the time until the second physical package is dispatched. Harmful for process discovery; informative for detecting that `O1` was physically split.

8. **Delivery `D2` under Delivery flattening misses packing.**  
   The `D2` trace contains only `e16` and `e24`. The packing events `e12` and `e13` are not related to `D2`, so they are absent. The resulting DFG starts at `Dispatch`, giving no indication that `P2` and `P3` were packed before the trip. A delivery-focused analysis may therefore understate the end-to-end fulfilment time for the orders in `D2`. Harmful if used as a full orderfulfilment view; useful for pure transit-time analysis.

9. **Item flattening truncates the commercial lifecycle.**  
   The longest item trace has four events, e.g. `I11`: `e05  e11  e15  e23`. There is no `Create Order`, `Issue Invoice`, `Record Payment`, or `Close Order`. This makes every item look successful and simple, hiding that `O1` was not closed until `e28`, and that `O2`/`O3` were linked to the multi-instalment invoice `V2`. Harmful for end-to-end conclusions; useful only for physical flow questions.

## 4. Traditional versus object-centric analysis portfolio

The following flattened logs should still be created, but only for narrow questions:

- **Order flattening**: for commercial/customer KPIs such as order open-to-close time, split shipments, and per-order invoice/payment visibility. Use it with the clear caveat that cross-order events are duplicated.
- **Package flattening**: for physical package journey times and for identifying consolidated packages `P3` and `P4`. Down-weight or deduplicate `e16`/`e24` when counting unique delivery trips.
- **Delivery flattening**: for transit-time analysis of `D1`, `D2`, `D3`. It is safe for that narrow purpose because no event duplication occurs.
- **Invoice flattening**: for billing and payment timing, especially the two-instalment settlement of `V2`.
- **Item flattening**: for per-item lead times from `Add Item` to `Confirm Delivery`; do not use it for order or financial analysis.
- **Payment flattening**: do not use for process discovery; keep only as an object lookup table.

Questions that require object-centric techniques:

- Which orders/items co-occur in one package or delivery? Use `pm4py.ocel_objects_interactions_summary` or the OTG.
- How do order, package, delivery, invoice, and payment lifecycles interleave? Use `pm4py.discover_otg` and `pm4py.discover_etot`.
- What are the unique, non-duplicated activity frequencies? Use the OC-DFG with event IDs rather than flattened copies.
- Which object behaviours are equivalent across the log? Use `pm4py.cluster_equivalent_ocel`, e.g. to group the six item lifecycles or the four payment singletons.
- What is the actual consolidation structure of `P3`, `P4`, `D2`, and `V2`? Use the O2O graph and object interaction summary.

To reconcile contradictory flattened and object-centric views, the original E2O/O2O relations should be treated as ground truth. For example, the Order flattening says `O2` and `O3` each have two `Record Payment` events, while the Invoice flattening says `V2` has two payments in total. Both are true only under different views: the former is a responsibility projection, the latter is the unique financial transaction. Whenever counts are needed, compute unique event IDs from the OCEL first, then multiply or project as needed.

## 5. Lead-object decision

**Position B: Use a primary lead object plus explicitly secondary lifecycles.**

Decision criteria:

- Coverage of the full end-to-end business process: creation, physical fulfilment, invoicing, payment, delivery, closure.
- Faithfulness to unique events and objects, avoiding excessive duplication.
- Ability to answer the main stakeholder question: “what happened to each order, and where did it interact with other orders?”
- Transparency about the process’s many-to-many structure, especially `P3`, `P4`, `D2`, and `V2`.

Strongest supporting evidence:

- Only the **Order** object type is related to every phase of the process. `O1`–`O4` appear in `Create Order`, `Add Item`, `Pack Package`, `Dispatch`, `Issue Invoice`, `Record Payment`, `Confirm Delivery`, and `Close Order`. Item/package/delivery/invoice/payment flattenings all omit at least one major phase.
- Therefore Order is the natural narrative lead for an end-to-end analysis.
- However, Order flattening alone is not defensible. The cross-order relations are too central: `P3`, `P4`, `D2`, and `V2` all involve multiple orders, and every shared event is copied. To avoid losing the unique physical/financial views, secondary lifecycles on Package, Delivery, and Invoice must be used.

Strongest counterargument:

- Cross-order events make even the Order view a distorted projection. `O2` and `O3` appear to share payment events, but there is no physical order-level object that corresponds to the entire `P3`/`D2`/`V2` flow. A stakeholder who wants to know “what really happened” could be misled by an Order-only log.
- This is the strongest reason to reject a single lead object entirely.

Residual risk:

- Treating Order as primary may still lead users to over-weight order-level KPIs and under-use the object-centric structure.
- There is also a tie ambiguity: `e21` and `e23` both have timestamp `2026-02-03 12:30`, so the order trace for `O1` may change if tie-breaking changes.
- The two-payment structure of `V2` could still be misread in the Order flattening unless the `M2`/`M3` qualifiers are kept.

Conditions under which I would change the decision:

- If the process had one-to-one relations between orders, items, packages, deliveries, invoices, and payments, I would choose **A** and use Order as the single lead.
- If the question were purely physical logistics, I would choose **A** with Package or Delivery as the lead.
- If the question were purely financial settlement, I would choose **A** with Invoice as the lead.
- If the organisation explicitly wanted no single narrative and was willing to work directly with object-centric graphs, I would choose **C**.

## 6. PM4Py analysis outline

```python
# Assume `ocel` already exists as a PM4Py OCEL object.
import pm4py

# ------------------------------------------------------------------
# 1. Inspect the OCEL and basic frequencies
# ------------------------------------------------------------------
print(ocel)

activity_freq = ocel.relations.groupby("event_activity").agg(
    event_count=("event_id", "nunique")
)
object_type_freq = ocel.objects.groupby("ocel_type").agg(
    object_count=("object_id", "nunique")
)
print("Activity frequency (unique events):\n", activity_freq)
print("Object type frequency (unique objects):\n", object_type_freq)

# ------------------------------------------------------------------
# 2. Flattening diagnostics: one classical log per object type
# ------------------------------------------------------------------
object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flattened_logs = {}

for ot in object_types:
    log = pm4py.ocel_flattening(ocel, ot)
    flattened_logs[ot] = log

    dfg = pm4py.discover_dfg(log)
    skeleton = pm4py.discover_log_skeleton(log)
    variants = pm4py.get_variants(log)

    print(f"\n=== Flattened on {ot}: {len(log)} cases ===")
    print("DFG:", dfg)
    print("Log skeleton:", skeleton)
    print("Variants:", variants)

# Compare total event copies across flattened logs
for ot, log in flattened_logs.items():
    copy_count = sum(len(trace) for trace in log)
    print(f"{ot}: total flattened event copies = {copy_count}")

# ------------------------------------------------------------------
# 3. Object-centric discovery
# ------------------------------------------------------------------
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

print("\nOC-DFG:\n", ocdfg)
print("\nObject Type Graph (OTG):\n", otg)
print("\nEvent-to-Object-Type Graph (ET-OT):\n", etot)
print("\nObject interaction summary:\n", interactions)

# Equivalent OCEL clustering: justified because our decision is to use
# Order as the primary narrative but keep secondary lifecycles explicit.
clusters = pm4py.cluster_equivalent_ocel(ocel)
print("\nEquivalent OCEL clusters:\n", clusters)

# The graphs above are not to be inspected visually as a substitute for
# semantic interpretation. Compare their numeric outputs: event counts,
# edge frequencies, performance values, object cardinalities, and clusters.
```

## 7. Sensitivity and validation plan

1. **Remove or down-weight copied shared events.**  
   Construct an Order flattening where every event is weighted by `1 / number of related order objects`. For example, `e13` gets weight 0.5, `e16` weight 1/3, `e24` weight 1/3. Recompute DFG frequencies and variant support. This directly tests how much the cross-order packages, deliveries, and invoices dominate the Order view.

2. **Compare direct E2O relations with a propagated-relation variant.**  
   Build a second Delivery flattening in which O2O relations are propagated: add `e11` to `D1`, add `e12` and `e13` to `D2`, and add `e14` to `D3`, because deliveries carry packages. Compare the resulting DFG edges and performance times with the direct-E2O delivery log. This helps quantify the truncation caused by starting a delivery case at `Dispatch`.

3. **Change the lead object.**  
   Run the full flattening and object-centric discovery with each of the six object types as lead. Compare the resulting variants, bottleneck edges, and lifecycle lengths. If the main conclusions change dramatically across leads, this supports the decision that no single object type is sufficient.

4. **Compare frequency metrics based on events, unique objects, and total objects.**  
   For `Pack Package`, compute:
   - unique event count: 4 (`e11`–`e14`);
   - unique package objects: 4 (`P1`–`P4`);
   - total related object occurrences: e.g. `e13` has 5 related objects, `e14` has 5, `e11` and `e12` have 3 each, giving 16 total object occurrences;
   - order-flattened event copies: 6.
   This comparison reveals how different metrics inflate or hide consolidation.

5. **Timestamp tie-resolution sensitivity.**  
   `e21` and `e23` both have timestamp `2026-02-03 12:30`. Reorder them by event ID versus by insertion order and observe whether `O1`’s DFG changes between `Record Payment  Confirm Delivery` and `Confirm Delivery  Record Payment`. This validates that the analysis is not dependent on an arbitrary tie-breaking rule.
