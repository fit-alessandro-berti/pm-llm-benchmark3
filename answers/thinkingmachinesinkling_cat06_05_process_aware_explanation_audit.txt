- For each feature used in explanation, verify timestamp field <= t0 (coverage check completed time).

- Check SQL filters (e.g., prior_claim_count filter claim_created_at < t0).

## 2. Process-model consistency checks

A concrete validation suite should combine **normative rules**, **prefix alignment**, **feature-lineage audit**, and **data-quality screening**, with explicit roles and limitations.

**A. Prefix-time availability audit (Feature Lineage)**
- For every feature in an explanation, verify `feature_store.event_timestamp <= t0` and `extraction_timestamp <= t0`.
- Inspect SQL predicates directly (e.g., `claim_created_at < t0` for prior claims; `upload_timestamp <= t0` for documents).
- Flag mutable warehouse fields (`final_handler_team`, `risk_score_current`, `last_resource_role`, `initial_reserve`) that lack `valid_from`/`valid_to` snapshots.

**B. Normative activity-order feasibility (Declarative / Petri-net checks)**
- Encode the simplified process as a partial order and declarative constraints:
  - `Claim Registered`  `Coverage Check Completed`
  - `Coverage Check Completed`  `{Damage Assessment Completed, Documents Requested}`
  - `Settlement Decision Recorded`  `{Appeal (only if first is Partial/Deny), Claim Closed}`
  - `Claim Closed` is terminal and must be last.
- For each sequence pattern in the explanation:
  - `Claim Closed -> Damage Assessment Completed`: violates terminal rule  **process-impossible**.
  - `Appeal -> Settlement Decision Recorded`: respects “appeal precedes reconsideration”  **normatively valid**, but both are post-`t0`.
  - `Documents Requested -> Documents Received`: valid within evidence cycle  **normatively valid**, but post-`t0`.
  - `Damage Assessment Completed -> Settlement Decision Recorded`: valid  **normatively valid**, but post-`t0`.
- **Limitation**: These rules are prescriptive; they do not alone prove leakage, but they block impossible explanations.

**C. Same-timestamp ambiguity resolution**
- For event pairs with identical timestamps (Case Z: `Claim Closed` and `Damage Assessment Completed`), require a reliable `ingestion_sequence_index`.
- If the index is missing, declare the directional order **unknown**; do not allow `X -> Y` patterns.
- Apply a tie-break rule only when the index is present and audited.

**D. Complete-trace usage detection (Prefix truncation test)**
- Compute feature values on the full trace and on the prefix truncated exactly at the `Coverage Check Completed` event (including its sequence index).
- If values differ (`full_trace_variant_id`, `num_document_requests_total`, `appeal_seen_anywhere`, `total_case_duration_hours`), the feature uses complete-trace information and is inadmissible at `t0`.
- For pattern features, restrict mining to the prefix window.

**E. Enabled / Impossible / Future-possible classification at `t0`**
- At the prefix `[Claim Registered, Coverage Check Completed]`, build the enabled-activity set:
  - **Enabled now**: `Damage Assessment Completed` (fast track) or `Documents Requested` (evidence); `Fraud Investigation Opened` only if a trigger is already recorded `<= t0`.
  - **Not enabled / future-possible**: `Settlement Decision`, `Appeal`, `Claim Closed` (require intermediate steps).
  - **Impossible in explanation**: any feature referencing `Claim Closed` before `Settlement Decision`.
- For repeated `Settlement Decision`: declare semantically legitimate **only if** an `Appeal` event exists between them and the first decision is `Partial` or `Deny`. At `t0`, no decision has occurred, so referencing a second decision or an appeal is always leakage.

**F. Data-quality screening with DFG and footprint (limitations noted)**
- Compute the **directed-follows graph (DFG)** and **footprint matrix** from the full log.
- Use these descriptively to flag anomalous edges (e.g., a frequent `Claim Closed -> Damage Assessment Completed` edge in the data).
- **Limitation**: A frequent DFG edge is **not** a normative rule. The normative model (B) takes precedence; DFG is only for identifying data-quality issues (timestamp misordering, missing indices) that require manual review.

**G. Prefix alignment conformance**
- Align the observed prefix `[Registered, Coverage Completed]` to the normative model.
- Compute fitness; it should be 1.0 for this prefix if no deviation exists.
- If feature extraction requires activities not in the aligned prefix (e.g., `Claim Closed`), the alignment fails, signaling leakage.

## 3. Alternative feature interpretations

After removing or repairing leaked features, the surviving signals fall into five classes. The standards differ across **predictive validity** (does it improve the forecast at `t0`?), **causal interpretation** (does it mechanistically drive delay?), **operational actionability** (can we intervene on it?), and **fairness review** (does it proxy protected or sensitive characteristics?).

**Defensible predictive signal**
- *Examples*: `initial_damage_complexity`, `elapsed_since_registration_at_t0`, `queue_length_at_t0` (system state), `initial_reserve` (if timestamp verified).
- *What may be claimed*: These are measured at or before `t0` and show statistical association with breach risk. High complexity and long queues predict longer paths; short elapsed time predicts more remaining budget.
- *What may not be claimed*: They are not deterministic causal mechanisms for any specific claim. We cannot say “high complexity causes this claim to breach” or “the queue caused this delay”; we can only say they shift the predicted risk distribution.

**Process-state or congestion signal**
- *Examples*: `queue_length_at_t0`, `resource_role_at_t0` (if repaired).
- *What may be claimed*: They describe the operational environment at the moment of prediction. High congestion predicts systemic bottlenecks.
- *What may not be claimed*: They do not establish a claim-specific causal chain. Action should be system-level (capacity management, triage), not claim-level blame.

**Proxy requiring fairness/robustness review**
- *Examples*: `claimant_region` (R4), `claimant_channel` (`Broker`), `prior_claim_count_before_t0` (after SQL repair).
- *What may be claimed*: They are predictive correlates in the training data.
- *What may not be claimed*: They are not direct operational causes. `Region` likely stands in for repair-network density, language access, or socioeconomic barriers; `Broker` may proxy claim subtype or documentation quality; prior claims may reflect chronic conditions or fraud risk. They must be audited for disparate impact and should not be used to penalize claimants without decomposing into actionable, non-protected operational variables.

**Drift/calendar proxy**
- *Examples*: `calendar_week` (e.g., week 52).
- *What may be claimed*: The model detects temporal variation in risk.
- *What may not be claimed*: It is not that “week 52 causes delay.” It captures aligned holiday closures, year-end staffing, or policy changes. To be interpretable and robust, it must be accompanied by explicit indicators (`holiday_flag`, `policy_version`) rather than treated as an intrinsic temporal cause.

**Unusable until lineage is repaired**
- *Examples*: `total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team`, `num_document_requests_total`, `full_trace_variant_id`, `same_day_document_count_snapshot`, `risk_score_current`, `last_resource_role`, `final_decision`, `prior_claim_count_before_t0` (current SQL), `initial_reserve` (if timestamp `> t0`).
- *What may be claimed*: Nothing credible until repaired. They are either future outcomes (`duration`, `appeal`, `decision`, `close` patterns), mutably defined (`risk_score_current`), mislourced (`last_resource_role`), or contaminated by post-`t0` data (`snapshot`, `prior_claim` SQL, `variant_id`).
- *What may not be claimed*: They should not appear in any explanation, model input, or operational report in their current form. Repair requires timestamped snapshots, prefix-only computation, SQL filter correction, or complete removal.

## 5. Recommendations for explanation validation

**Priority 1 — Feature-store design with point-in-time correctness**
Implement a feature store that requires `event_timestamp`, `extraction_timestamp`, and `feature_version` for every value. Separate “current warehouse” tables from “historical at event” tables. Enforce that any feature used at `t0` (immediately after `Coverage Check Completed`) has `event_timestamp <= t0`. This prevents silent leakage through fields like `final_handler_team` or `risk_score_current`.

**Priority 2 — Historical feature timestamps and mutable-field snapshots**
For mutable fields (`risk_score`, `reserve`, `team assignment`, `employee experience`), store snapshot histories (`valid_from`, `valid_to`). For document counts, store event-level upload timestamps rather than nightly batches. Repair the `prior_claim_count` SQL to `claim_created_at < t0`. Without this, lineage defects will continue to contaminate explanations.

**Priority 3 — Prefix-only recomputation pipeline**
At prediction time, truncate the event log exactly at the `Coverage Check Completed` event (respecting sequence index). Recompute all variant IDs, pattern counts, “anywhere” flags, and aggregates solely on this prefix. For the cases shown, the correct prefix is `[Claim Registered, Coverage Check Completed]`, so the variant should be `REG-COV` and document-request counts should be zero. Block any feature whose value changes between the prefix and the full trace.

**Priority 4 — Process-conformance and explanation-validation suite**
Encode the normative process as declarative rules (e.g., `Claim Closed` is terminal; `Appeal` requires prior `Partial`/`Deny`). For each explanation:
- Check feature references against the enabled/impossible/future-possible set at `t0`.
- Apply prefix alignment; reject explanations that require future activities.
- Use DFG/footprint only for data-quality screening (e.g., flagging `Claim Closed -> Damage Assessment Completed` as suspicious), not as normative rules.
- Reject directional patterns when the ingestion sequence index is missing.

**Priority 5 — Calibration and model update after feature removal**
Remove all critical-leakage features (`total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team` in its current form, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, and future-pattern encodings). Retrain or recalibrate on the admissible set (`queue_length`, `initial_damage_complexity`, `region` with review, `reserve` if timestamp-corrected, `elapsed_since_registration_at_t0`, repaired `prior_claim_count`, `channel`). Monitor discrimination (AUC) and calibration reliability; predictive power should be retained through legitimate entry conditions and system-state signals.

**Priority 6 — Explanation stability checks**
Generate SHAP or pattern-based explanations across bootstrap samples of similar prefixes. If rankings shift wildly (e.g., `region` dominates in one sample and `queue` in another without structural reason), investigate multicollinearity or hidden leakage. Ensure that directionality is consistent with process logic (e.g., longer queue  higher risk).

**Priority 7 — Proxy/fairness analysis**
For `claimant_region`, `claimant_channel`, and repaired `prior_claim_count`, compute correlations with available protected attributes and operational decompositions (e.g., repair-network distance, language, claim subtype). Document that predictive importance is not operational actionability: reducing risk requires capacity and triage interventions, not changing claimant region or channel. Conduct regular disparate-impact audits.

**Priority 8 — Monitoring for schema and process drift**
Monitor feature distributions by `calendar_week` to detect holiday/policy shifts explicitly. Monitor ingestion completeness (sequence index missing rates) and same-timestamp ambiguity rates. Monitor SQL filter integrity automatically (e.g., alert when `extraction_date` is used instead of event timestamp). Alert immediately when explanations reference activities not enabled at `t0` (`Appeal`, `Claim Closed`, `Settlement Decision`), indicating either leakage or model degradation.
