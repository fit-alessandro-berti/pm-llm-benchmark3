# 1. Equivalence Notions

Let the visible alphabet be:

```text
O  = Open Case
A  = Analyze Revision
C  = Check Revision
P  = Approve Revision
R  = Rework Case
Z  = Close Case
```

`tau` is invisible. A complete visible trace is the sequence of visible labels produced from a complete run after deleting all `tau` occurrences.

**Duplicate visible labels.** In the ordinary trace language, duplicate labels are distinguished by **occurrence position**, not by transition identity. For example, `A ... A` means two visible occurrences of the same label. Under P2, however, repeated `Check Revision` events are deliberately collapsed to the Boolean fact “a check occurred.”

**Visible trace equivalence after hiding `tau`.**
Two models are visible-trace equivalent iff their complete visible trace languages are equal after erasing `tau`. This is a strict label-sequence comparison: same labels, same multiplicities, same order.

Using the standard binary-loop semantics, the visible language of Model A is:

```text
L_A = O · I · (R · I)* · Z
I   = (A · C | C · A) · (P | ε)
```

So every loop iteration contains exactly one `Analyze Revision`, exactly one `Check Revision`, and optional `Approve Revision` after both analysis/check activities have completed.

The visible language of Model B is:

```text
L_B = O · shuffle(C, J · (R · J)*) · Z
J   = A · (P | ε)
```

Here there is exactly one `Check Revision` for the whole parallel block, while the loop can contain one or more analysis attempts.

**Bounded visible-language equivalence under P3.**
Let:

```text
B = { complete visible traces t | len(t) <= 12 and count_A(t) <= 3 }
```

Models are P3-equivalent iff:

```text
L_A ∩ B = L_B ∩ B
```

This is exhaustive only inside that bound. It is not a proof of unbounded equivalence.

**Business-relevant equivalence under P1.**
For P1, the relevant unit is an analysis attempt. `Rework Case` separates attempts. A trace satisfies the P1 compliance abstraction iff, between `Open Case` and `Close Case`:

1. there is at least one analysis attempt;
2. each attempt has exactly one `Analyze Revision`;
3. each attempt has its own `Check Revision` before the next `Rework Case` or `Close Case`;
4. `Rework Case` appears only between completed attempts;
5. `Approve Revision` is optional but visible and remains attached to the attempt in which it occurs;
6. `tau` is ignored.

Under this P1 abstraction, the decisive question is not whether the two diagrams share the same activity labels, but whether every analysis attempt has its own check. Model A does; Model B does not once there is more than one analysis attempt.

A stricter operational interpretation could additionally require `Analyze Revision` before `Check Revision`. Under that stricter interpretation, Model A is also too weak because its `+('Analyze Revision', 'Check Revision')` allows `Check Revision` before `Analyze Revision`.

**Abstracted dashboard equivalence under P2.**
Define the P2 abstraction:

```text
α₂(t) =
(
  first(t) == O,
  last(t) == Z,
  count_A(t),
  count_C(t) >= 1,
  count_R(t) >= 1
)
```

`Approve Revision`, `tau`, exact `Analyze`/`Check` interleaving, and repeated `Check Revision` occurrences beyond the Boolean “some check occurred” are hidden. Under this abstraction, duplicate `Check Revision` labels are not counted as distinct dashboard facts.

`Approve Revision` is optional because of `X('Approve Revision', tau)`. Choosing `tau` removes the approval from the visible trace; it does not remove `Analyze Revision`, `Check Revision`, `Rework Case`, `Open Case`, or `Close Case`. This matters because no-approval traces such as `Open, Analyze, Check, Close` are valid in both models, but visible approval placement still distinguishes the models: Model B can place `Check Revision` after a visible approval, while Model A cannot.

# 5. Bounded Comparison Code

The code below performs exhaustive bounded exploration over the accepting Petri net state space. It does not use random playout for the equivalence verdict. PM4Py documents `parse_process_tree` for process-tree strings with operators such as sequence, parallel, xor, and binary loop, `convert_to_petri_net` for producing an accepting Petri net triple, and `check_soundness` for WF-net soundness checking; the code also uses enabled-transition exploration rather than sampling. ([pm4py-source.readthedocs.io][1])

```python
from collections import deque
import pm4py
from pm4py.objects.petri_net import semantics as petri_semantics

MODEL_A = """
-> (
  'Open Case',
  * (
    -> (
      + ( 'Analyze Revision', 'Check Revision' ),
      X ( 'Approve Revision', tau )
    ),
    'Rework Case'
  ),
  'Close Case'
)
"""

MODEL_B = """
-> (
  'Open Case',
  + (
    'Check Revision',
    * (
      -> (
        'Analyze Revision',
        X ( 'Approve Revision', tau )
      ),
      'Rework Case'
    )
  ),
  'Close Case'
)
"""

MAX_VISIBLE_EVENTS = 12
MAX_ANALYZE = 3
ANALYZE = "Analyze Revision"


def transition_visible_label(t):
    """
    PM4Py silent transitions usually have label None.
    This also treats textual 'tau' as silent defensively.
    """
    label = getattr(t, "label", None)
    if label is None:
        return None
    if str(label).lower() == "tau":
        return None
    return str(label)


def marking_key(marking):
    """
    Explicit, stable marking key.
    Keeps only positive token counts and sorts by place name.
    """
    return tuple(
        sorted((getattr(place, "name", str(place)), count)
               for place, count in marking.items()
               if count)
    )


def bounded_visible_language(net, initial_marking, final_marking,
                             max_visible_events=12,
                             max_analyze=3):
    """
    Exhaustive BFS over markings, bounded by visible trace length
    and number of Analyze Revision occurrences.

    Important:
    - Silent transitions do not increase visible length.
    - The visited key is (marking, visible_trace), not just marking,
      because loops can revisit the same marking with a different trace.
    - Silent cycles are controlled because the same (marking, trace)
      state is not revisited.
    - A trace is accepted only when the current marking equals the
      final marking explicitly.
    """
    final_key = marking_key(final_marking)

    queue = deque()
    queue.append((initial_marking, tuple()))

    visited = set()
    visited.add((marking_key(initial_marking), tuple()))

    accepted = set()

    while queue:
        marking, trace = queue.popleft()
        m_key = marking_key(marking)

        if m_key == final_key:
            accepted.add(trace)
            continue

        enabled = pm4py.get_enabled_transitions(net, marking)

        for transition in enabled:
            label = transition_visible_label(transition)

            if label is None:
                new_trace = trace
            else:
                if len(trace) + 1 > max_visible_events:
                    continue
                if label == ANALYZE and trace.count(ANALYZE) + 1 > max_analyze:
                    continue
                new_trace = trace + (label,)

            new_marking = petri_semantics.execute(transition, net, marking)
            if new_marking is None:
                continue

            state_key = (marking_key(new_marking), new_trace)
            if state_key not in visited:
                visited.add(state_key)
                queue.append((new_marking, new_trace))

    return accepted


def print_trace_set(title, traces):
    print(f"\n{title}: {len(traces)} traces")
    for tr in sorted(traces, key=lambda x: (len(x), x)):
        print("  - " + " -> ".join(tr))


# 1. Parse both process trees.
tree_a = pm4py.parse_process_tree(MODEL_A)
tree_b = pm4py.parse_process_tree(MODEL_B)

# 2. Convert both trees to accepting Petri nets.
net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)

# 3. Check soundness.
sound_a = pm4py.check_soundness(net_a, im_a, fm_a, print_diagnostics=True)
sound_b = pm4py.check_soundness(net_b, im_b, fm_b, print_diagnostics=True)

print("Soundness A:", sound_a)
print("Soundness B:", sound_b)

# 4-6. Exhaustively derive bounded visible languages and compare.
print("\nExploration mode: EXHAUSTIVE bounded BFS over Petri-net markings.")
print("This is not random playout and not heuristic sampling.")
print(f"Bounds: len(trace) <= {MAX_VISIBLE_EVENTS}, "
      f"count('Analyze Revision') <= {MAX_ANALYZE}")

lang_a = bounded_visible_language(
    net_a, im_a, fm_a,
    max_visible_events=MAX_VISIBLE_EVENTS,
    max_analyze=MAX_ANALYZE
)

lang_b = bounded_visible_language(
    net_b, im_b, fm_b,
    max_visible_events=MAX_VISIBLE_EVENTS,
    max_analyze=MAX_ANALYZE
)

only_a = lang_a - lang_b
only_b = lang_b - lang_a
common = lang_a & lang_b

print("\nBounded language sizes")
print("  |A|       =", len(lang_a))
print("  |B|       =", len(lang_b))
print("  |A ∩ B|   =", len(common))
print("  |A \\ B|   =", len(only_a))
print("  |B \\ A|   =", len(only_b))
print("  Equivalent under P3?", lang_a == lang_b)

print_trace_set("Traces unique to Model A", only_a)
print_trace_set("Traces unique to Model B", only_b)

# Optional diagnostic only:
# pm4py.play_out(tree_a, ...) or pm4py.play_out(net_a, im_a, fm_a, ...)
# would generate a sample or bounded playout log depending on parameters.
# Such playout is useful for finding witnesses, but absence of a witness
# in a sample is not evidence of equivalence.
```

For the given formal trees, the bounded-language arithmetic is:

```text
Model A:
  k = 1 analysis: 4 traces
  k = 2 analyses: 16 traces
  k = 3 analyses: 64 traces minus 8 traces with length 13
  total: 76

Model B:
  k = 1 analysis: 5 traces
  k = 2 analyses: 20 traces
  k = 3 analyses: 60 traces
  total: 85

Common bounded traces:
  4

Unique to A:
  72

Unique to B:
  81
```

The four common bounded traces are the one-analysis traces where Model B’s single global check happens before approval or where approval is absent:

```text

Open Case, Analyze Revision, Check Revision, Approve Revision, Close Case
Open Case, Check Revision, Analyze Revision, Approve Revision, Close Case
```

# 6. Stochastic and Footprint Comparison

`pm4py.discover_footprints(...)` can add coarse behavioral evidence: it can show local relations such as directly-follows, causality, conflict, and parallelism. It is useful for quickly detecting that `Check Revision` has a different structural relationship in the two models. However, equal footprints would not establish trace equivalence because footprints are an abstraction: they do not preserve full global ordering constraints, loop cardinalities, or “one check per analysis attempt” requirements. PM4Py documents footprint discovery as producing a footprint object from a log or model. ([pm4py-source.readthedocs.io][2])

`pm4py.get_stochastic_language(...)` and `pm4py.compute_emd(...)` can add evidence if a probability model is declared or if stochastic languages are estimated from logs. They do not replace language equivalence. A low Earth Mover’s Distance says that two probability distributions over traces are close under the chosen distance; it does not say their supports are equal. A zero EMD over a sampled or bounded empirical language can still miss unobserved traces. PM4Py’s manual-style API reference describes `get_stochastic_language` as returning a stochastic language and `compute_emd` as computing Earth Mover’s Distance between two stochastic languages. ([GitHub][3])

```python
import pm4py

# Reuse tree_a, tree_b, net_a, im_a, fm_a, net_b, im_b, fm_b
# from Section 5.

# Footprints: useful evidence, not proof of trace-language equivalence.
fp_a_tree = pm4py.discover_footprints(tree_a)
fp_b_tree = pm4py.discover_footprints(tree_b)

print("Footprints A:")
print(fp_a_tree)

print("\nFootprints B:")
print(fp_b_tree)

print("\nFootprints equal?", fp_a_tree == fp_b_tree)


# Stochastic comparison option 1:
# Use PM4Py stochastic language if the object and PM4Py version support it.
# Interpret probabilities only if you accept the probability assumptions used
# by that PM4Py call or if the model/log is explicitly stochastic.
try:
    stochastic_a = pm4py.get_stochastic_language(net_a, im_a, fm_a)
    stochastic_b = pm4py.get_stochastic_language(net_b, im_b, fm_b)

    print("\nPM4Py stochastic language A:")
    print(stochastic_a)

    print("\nPM4Py stochastic language B:")
    print(stochastic_b)

    print("\nEMD:")
    print(pm4py.compute_emd(stochastic_a, stochastic_b))

except Exception as exc:
    print("\nStochastic-language extraction was not used:")
    print(type(exc).__name__, exc)


# Stochastic comparison option 2:
# A declared bounded diagnostic distribution.
# This is NOT a process probability model.
# It says: "uniform over the exhaustive bounded trace set from P3."
def uniform_over_bounded_language(trace_set):
    if not trace_set:
        return {}
    p = 1.0 / len(trace_set)
    return {trace: p for trace in trace_set}


bounded_uniform_a = uniform_over_bounded_language(lang_a)
bounded_uniform_b = uniform_over_bounded_language(lang_b)

bounded_emd = pm4py.compute_emd(bounded_uniform_a, bounded_uniform_b)
print("\nBounded uniform EMD diagnostic:", bounded_emd)
print("Interpretation: distance between declared uniform distributions "
      "over the P3-bounded languages, not a proof of full equivalence.")
```

Even if footprints were equal or the EMD were low, the counterexample traces in Section 4 would remain decisive for visible-language and P1/P3 non-equivalence.

# 7. Complexity Comparison

For process-tree structure, I use:

```text
node count  = operator nodes + leaf nodes
depth       = maximum number of nodes on a root-to-leaf path, root depth = 1
visible leaf = leaf with a visible label
silent leaf  = tau / None leaf
duplicate-label count = sum over visible labels max(0, occurrences(label) - 1)
```

Exact structural counts derived from the two tree expressions:

| Metric                         | Model A | Model B |
| ------------------------------ | ------: | ------: |
| Process-tree node count        |      12 |      12 |
| Operator nodes                 |       5 |       5 |
| Visible leaves                 |       6 |       6 |
| Silent leaves                  |       1 |       1 |
| Distinct visible labels        |       6 |       6 |
| Duplicate visible-label leaves |       0 |       0 |
| Max depth, root depth = 1      |       5 |       6 |
| Parallel operator count        |       1 |       1 |
| Binary loop count              |       1 |       1 |
| XOR count                      |       1 |       1 |

Model B is structurally deeper because the parallel operator wraps the entire loop, whereas in Model A the loop is directly under the root sequence and the parallel operator is inside the loop body.

Code to compute the structural counts:

```python
from collections import Counter
import pm4py

def is_silent_label(label):
    return label is None or str(label).lower() == "tau"

def process_tree_stats(tree):
    stats = {
        "nodes": 0,
        "operator_nodes": 0,
        "visible_leaves": 0,
        "silent_leaves": 0,
        "max_depth_root_1": 0,
        "operator_counts": Counter(),
        "visible_label_counts": Counter(),
    }

    def rec(node, depth):
        stats["nodes"] += 1
        stats["max_depth_root_1"] = max(stats["max_depth_root_1"], depth)

        children = list(getattr(node, "children", []) or [])
        operator = getattr(node, "operator", None)
        label = getattr(node, "label", None)

        if children:
            stats["operator_nodes"] += 1
            stats["operator_counts"][str(operator)] += 1
            for child in children:
                rec(child, depth + 1)
        else:
            if is_silent_label(label):
                stats["silent_leaves"] += 1
            else:
                stats["visible_leaves"] += 1
                stats["visible_label_counts"][str(label)] += 1

    rec(tree, 1)

    stats["distinct_visible_labels"] = len(stats["visible_label_counts"])
    stats["duplicate_visible_label_leaves"] = sum(
        max(0, count - 1)
        for count in stats["visible_label_counts"].values()
    )

    return stats


tree_a = pm4py.parse_process_tree(MODEL_A)
tree_b = pm4py.parse_process_tree(MODEL_B)

print("Tree stats A:", process_tree_stats(tree_a))
print("Tree stats B:", process_tree_stats(tree_b))
```

For converted-Petri-net simplicity, use PM4Py’s metric on the exact net produced by the PM4Py version being used. I would not report a numeric value without running the same conversion and metric implementation, because process-tree-to-Petri-net conversion details can affect the resulting net structure. The `simplicity_petri_net` API is documented as computing a simplicity metric for a Petri net. ([GitHub][3])

```python
net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)

simplicity_a = pm4py.simplicity_petri_net(net_a, im_a, fm_a)
simplicity_b = pm4py.simplicity_petri_net(net_b, im_b, fm_b)

print("Petri-net simplicity A:", simplicity_a)
print("Petri-net simplicity B:", simplicity_b)
```

# 8. Simplified Model

The most appropriate target, in my view, is a **P1-refined operational compliance model**: every analysis attempt should be checked in that attempt, and the check should occur after the analysis. This is slightly stricter than Model A, because Model A allows `Check Revision` before `Analyze Revision` due to local parallelism.

A compact process tree is:

```text
->(
  'Open Case',
  *(
    ->(
      'Analyze Revision',
      'Check Revision',
      X('Approve Revision', tau)
    ),
    'Rework Case'
  ),
  'Close Case'
)
```

Its visible language is:

```text
L_S = O · K · (R · K)* · Z
K   = A · C · (P | ε)
```

Self-contained PM4Py assignment:

```python
import pm4py

SIMPLIFIED_MODEL = """
-> (
  'Open Case',
  * (
    -> (
      'Analyze Revision',
      'Check Revision',
      X ( 'Approve Revision', tau )
    ),
    'Rework Case'
  ),
  'Close Case'
)
"""

simplified_model = pm4py.parse_process_tree(SIMPLIFIED_MODEL)
simplified_net, simplified_im, simplified_fm = pm4py.convert_to_petri_net(simplified_model)

print(pm4py.check_soundness(
    simplified_net,
    simplified_im,
    simplified_fm,
    print_diagnostics=True
))
```

Structural comparison:

| Metric                         | Model A | Model B | Simplified model |
| ------------------------------ | ------: | ------: | ---------------: |
| Process-tree node count        |      12 |      12 |               11 |
| Operator nodes                 |       5 |       5 |                4 |
| Visible leaves                 |       6 |       6 |                6 |
| Silent leaves                  |       1 |       1 |                1 |
| Max depth, root depth = 1      |       5 |       6 |                5 |
| Parallel operator count        |       1 |       1 |                0 |
| Binary loop count              |       1 |       1 |                1 |
| XOR count                      |       1 |       1 |                1 |
| Duplicate visible-label leaves |       0 |       0 |                0 |

This model is structurally simpler than both originals because it removes the parallel operator and has one fewer process-tree node. It is not merely visually simpler; it removes a semantic ambiguity about whether a check may precede the analysis.

Preservation table:

| Property                                      | Preservation by simplified model | Explanation                                                                                                                            |
| --------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `Open Case` first, `Close Case` last          | exact                            | Same outer sequence.                                                                                                                   |
| At least one `Analyze Revision`               | exact                            | Binary loop executes its first child once before exit.                                                                                 |
| At least one `Check Revision`                 | exact                            | Every first-child execution contains one check.                                                                                        |
| One check per analysis attempt                | exact                            | Each loop iteration has exactly one `Analyze Revision` followed by exactly one `Check Revision`.                                       |
| `Rework Case` separates attempts              | exact                            | `Rework Case` is the redo child of the binary loop.                                                                                    |
| Optional approval                             | exact for P1-refined semantics   | Each attempt may choose `Approve Revision` or `tau`.                                                                                   |
| Approval visibility                           | exact                            | `Approve Revision` remains visible when chosen.                                                                                        |
| Model A’s local `Analyze`/`Check` concurrency | lost intentionally               | The simplified model rejects `Check Revision` before `Analyze Revision`.                                                               |
| Model B’s global single-check behavior        | lost intentionally               | The simplified model is per-attempt, not global.                                                                                       |
| P2 dashboard abstraction                      | preserved                        | It still gives open first, close last, `n` analyses, at least one check, and rework iff `n >= 2`; repeated checks are collapsed by P2. |
| P3 visible-language equivalence to A or B     | not preserved                    | It rejects some bounded traces admitted by A and many admitted by B.                                                                   |

| Regression ID | Trace                                                                                                                                        | Reason                                       |

| S-pos-1       | `Open Case, Analyze Revision, Check Revision, Close Case`                                                                                    | One auto-approved attempt.                   |

| S-neg-4     | `Open Case, Analyze Revision, Rework Case, Check Revision, Close Case`                   | Rework occurs before the first attempt is checked.                                                    |

# 9. Final Recommendation

For **P1 operational compliance**, Model A is the better original model because the check is inside the revision loop and therefore repeats per analysis attempt. Model B is not suitable for P1 when more than one analysis attempt is possible, because it models only one global `Check Revision`. If the business meaning is “an analysis must be completed and then checked,” use the simplified P1-refined model instead of either original.

For **P2 executive dashboarding**, Models A and B are equivalent only after the stated abstraction. Both reduce to the same dashboard facts: `Open Case` first, `Close Case` last, at least one analysis, at least one check, the number of analyses, and whether rework occurred. Either original can feed that dashboard if the transformation really hides approvals and collapses repeated checks to a Boolean. The simplified P1-refined model also preserves this P2 dashboard abstraction.

For **P3 bounded testing**, Models A and B are not equivalent. The counterexamples are already inside the bound, so the bounded test is decisive for non-equivalence. The warning is the opposite case: if a bounded comparison finds no difference, it is only evidence within the chosen limits, not a proof of unbounded equivalence.

The simplified model should replace Model A only if the organization agrees that `Check Revision` should follow `Analyze Revision` rather than run concurrently. It should replace Model B only if Model B’s single global check was not intentional. If the business truly wants one case-level check concurrent with all revisions, then Model B is semantically appropriate for that different purpose, but it should not be described as equivalent to Model A under operational compliance.
