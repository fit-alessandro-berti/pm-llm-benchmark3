# 2. Shared Assumptions

All three candidates share the following foundation:

1. **Event-completion semantics.** The log records the *end* of each activity (S7). No start-time or duration information is available, so any “before” relation is interpreted as “completed before the other started/completed,” not “started before.”
2. **Start and end are fixed.** `Register Order` is the unique start (`D1`, S5); `Archive Case` is the unique end (`D1`).
3. **Release requires approval.** `Release Production` never occurs without `Approve Configuration` (`D2`).
4. **Both principal checks precede approval.** `Credit Check` and `Engineering Review` both have edges into `Approve Configuration` (`D3`).
5. **Missing-data abstraction for `Supplier Confirmation`.** Because the `external/stocked` attribute is absent (S5) and 5–10% of `SC` events may be integration failures, `SC` presence/absence is represented as a **control-flow alternative** (`XOR` with a `SilentTransition`) rather than a deterministic absence. This means the model admits both “deliberately skipped” and “missing event” without distinguishing them.
6. **Optionality of `Expedite Review`.** `EXP` is represented as `XOR(EXP, SilentTransition)` (`D6`).
7. **No repetition assumed.** No loops (`*`) are included because repetition is unobserved and unsupported by domain rules.
8. **No hidden activities.** Only the eight labeled activities appear in the control-flow graph.

The three models differ only in how they treat **interleaving freedom** among `CC`, `ER`, `SC`, and `EXP`, and in how aggressively they generalize beyond the 7 observed variants.

# 3. Conservative Candidate

**Inductive-bias statement.**  
We treat the 30 traces as an almost exhaustive enumeration of permitted behavior. Only the exact 7 interleavings observed in the log are admitted. We do **not** infer concurrency (`+`), partial-order freedom, or hidden loops. Optional absence of `SC` is permitted **only** in the two patterns where it is observed (`V3`, `V4`), and `EXP` is permitted **only** in the two patterns `V6` and `V7`. This minimizes false-positive generalization but risks severe underfitting if the true process allows any interleaving consistent with `D3`–`D6`.

**Compact formal expression.**  
`( RO , X( V1 , V2 , V3 , V4 , V5 , V6 , V7 , ( AC , ( RP , AR ) ) ) )` where each `Vi` is the exact sequence of middle activities seen in variant *i*.

**Self-contained PM4Py code (`model_conservative`).**

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Exact middle-activity sequences for the 7 observed variants
v1 = "->('Credit Check', ->('Engineering Review', 'Supplier Confirmation'))"
v2 = "->('Engineering Review', ->('Credit Check', 'Supplier Confirmation'))"
v3 = "->('Credit Check', 'Engineering Review')"
v4 = "->('Engineering Review', 'Credit Check')"
v5 = "->('Credit Check', ->('Supplier Confirmation', 'Engineering Review'))"
v6 = "->('Credit Check', ->('Engineering Review', ->('Supplier Confirmation', 'Expedite Review')))"
v7 = "->('Engineering Review', ->('Credit Check', ->('Expedite Review', 'Supplier Confirmation')))"

# XOR enumeration of all variants with shared suffix
xor_middle = "X(" + ",".join([v1, v2, v3, v4, v5, v6, v7]) + ")"
full_str = "->('Register Order', ->(" + xor_middle + ", ->('Approve Configuration', ->('Release Production', 'Archive Case'))))"

model_conservative = pm4py.parse_process_tree(full_str)
```

**Behavior deliberately excluded.**
- Any ordering of `CC` and `ER` other than the five observed (`CC-ER`, `ER-CC`, `CC-SC-ER`, `CC-ER-SC`, `ER-CC-EXP-SC`, etc.).
- Concurrent execution that produces a different completion-ingestion order.
- `SC` absent in a trace whose other activities match a variant that normally includes `SC` (e.g., a “missing data” version of `V1`).
- `EXP` occurring in any position other than exactly `V6` or `V7`.
- Repetition, loops, or any trace with more/fewer than the observed activity multiset per variant.

**Known underfitting risks.**
- **Parallel execution rejection:** If `CC` and `ER` truly run in parallel (S2) and complete in either ingestion order, the conservative model accepts only the two observed orders, rejecting valid parallel traces that happen to complete in an unobserved slot ordering.
- **Missing-data rejection:** If `SC` is missing in `V1` due to an integration failure (S5), the conservative model rejects the trace entirely, even though the underlying process was correct.
- **Future variant rejection:** Any future case with `SC` placed between `ER` and `EXP` but not matching `V6`/`V7` exactly will be rejected.

# 4. Balanced Candidate

**Inductive-bias statement.**  
The balanced model encodes the most plausible structural generalization: `CC` and `ER` are concurrent (no ordering edge) based on S2, bidirectional DFG, and the ambiguity declared in D7; `SC` is optional and free to interleave (approximating D5); `EXP` is optional, requires both checks (`CC  EXP` and `ER  EXP`), precedes `AC`, and is unordered with respect to `SC` (S6). Absence is abstracted via `SilentTransition` nodes inside `XOR` operators; we do **not** claim that a silent path means “stocked component” versus “integration failure.” This model aims for high fitness on the 30 cases while admitting a well-defined, constrained superset of traces.

**How sequence, concurrency, and partial order are decided.**

| Pair / Activity | Decision | Justification |
|---|---|---|
| `CC` vs `ER` | **Concurrent** (no ordering edge in POWL) | DFG shows both directions; S2 states parallel execution is normal; S7/D7 prevent proving sequence; S1 is contradicted by 11 traces. |
| `SC` vs checks (`CC`/`ER`) | **Partial order / free interleaving** (edges `RO  SC` and `SC  AC` only) | D5 says `SC` “need not wait for both.” Without OR-join semantics, the safest balanced approximation is to allow `SC` anytime after `RO` and require it before `AC`. |
| `EXP` vs checks | **Sequence dependency** (edges from both `CC` and `ER` to `EXP`) | D6 is medium confidence and uncontradicted: `EXP` requires both checks finished. |
| `EXP` vs `SC` | **Partial order / no edge** | S6 explicitly allows either ordering; V6 and V7 confirm both. |
| `SC` presence | **Optional (`XOR`)** | S3/S4/S5 together make mandatory presence indefensible; V3/V4 confirm absence is real. |
| `EXP` presence | **Optional (`XOR`)** | Only 2/30 traces contain it (`D6`). |

**Compact formal expression (POWL).**  
A single partial order with nodes `{RO, CC, ER, XOR_SC, XOR_EXP, AC, RP, AR}` and edges: `ROCC`, `ROER`, `ROXOR_SC`, `CCAC`, `ERAC`, `XOR_SCAC`, `CCXOR_EXP`, `ERXOR_EXP`, `XOR_EXPAC`, `ACRP`, `RPAR`. `XOR_SC` and `XOR_EXP` are `OperatorPOWL(XOR, [Activity, SilentTransition])`.

**Self-contained PM4Py code (`model_balanced`).**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition, Operator
)

# Core activities
ro  = Transition("Register Order")
cc  = Transition("Credit Check")
er  = Transition("Engineering Review")
sc  = Transition("Supplier Confirmation")
exp = Transition("Expedite Review")
ac  = Transition("Approve Configuration")
rp  = Transition("Release Production")
ar  = Transition("Archive Case")

# Optional nodes abstracted via XOR + silent skip
xor_sc = OperatorPOWL(operator=Operator.XOR,
                     children=[sc, SilentTransition()])
xor_exp = OperatorPOWL(operator=Operator.XOR,
                      children=[exp, SilentTransition()])

# Partial order: concurrent checks, optional interleaved nodes,
# both checks required for approval and for expedite review
po = StrictPartialOrder()
for n in [ro, cc, er, xor_sc, xor_exp, ac, rp, ar]:
    po.nodes.add(n)

po.order.add_edge(ro, cc)
po.order.add_edge(ro, er)
po.order.add_edge(ro, xor_sc)   # D5: may begin after start; free interleaving
po.order.add_edge(cc, ac)
po.order.add_edge(er, ac)
po.order.add_edge(xor_sc, ac)   # D4: if present, before approval
po.order.add_edge(cc, xor_exp)  # D6: requires both checks
po.order.add_edge(er, xor_exp)
po.order.add_edge(xor_exp, ac)  # D6: before approval
po.order.add_edge(ac, rp)       # D2
po.order.add_edge(rp, ar)       # D1 end

model_balanced = po
```

**Behavior deliberately excluded.**
- `AC` occurring before both `CC` and `ER` are completed.
- `EXP` occurring before either `CC` or `ER` is completed.
- `SC` occurring after `AC`.
- Multiple executions of `EXP` (not enforced structurally, but the single-node representation excludes loops).
- Any repetition of activities (no loop operators).

**Known underfitting risks.**
- If `SC` actually requires at least one check to finish before it can start (a stricter reading of D5), the balanced model is slightly too permissive by allowing `SC` immediately after `RO`. This is disclosed.
- If `CC` and `ER` are actually strictly sequential (S1 is correct despite contradictions), the concurrent representation overfits parallel interleavings.
- The model does not distinguish “stocked component” (`S4`) from “missing integration event” (`S5`) inside the silent branch.

# 5. Permissive Candidate

**Inductive-bias statement.**  
The permissive model admits **every** trace that respects the broad domain rules `D1`–`D6` with minimal structural restriction. `CC` and `ER` remain concurrent (no ordering edge); both are required for `AC` and `EXP`; `SC` and `EXP` are optional; `SC` is allowed anywhere between `RO` and `AC`; `EXP` is allowed anywhere between the completion of both checks and `AC`; there is **no ordering constraint** between `SC` and `EXP`. This captures “reasonable but unobserved combinations” (e.g., `SC` running before any check completes, or `EXP` occurring in a trace where `SC` is entirely absent due to missing data).

**Boundary: reasonable generalization vs. forbidden behavior.**
- **Admitted (generalization):** Any interleaving of `CC`, `ER`, `SC`, `EXP` such that `RO` is first, both checks occur before `AC`, `SC` (if present) is before `AC`, `EXP` (if present) is after both checks and before `AC`, and `AC  RP  AR`.
- **Forbidden:** `RO` not first; `AR` not last; `AC` before both checks; `EXP` before both checks; `SC` after `AC`; repetition/loops; any activity outside the eight-label alphabet.

**Compact formal expression (POWL).**  
Same node set as balanced, but with **fewer restrictive edges**: `RO` connects to all four middle nodes (`CC`, `ER`, `XOR_SC`, `XOR_EXP`); `CC` and `ER` connect to `AC` and to `XOR_EXP`; `XOR_SC` and `XOR_EXP` connect to `AC`; `AC  RP  AR`. There is **no edge** between `XOR_SC` and `XOR_EXP`, and no edge forcing `SC` to wait for any check.

**Self-contained PM4Py code (`model_permissive`).**

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition, Operator
)

ro  = Transition("Register Order")
cc  = Transition("Credit Check")
er  = Transition("Engineering Review")
sc  = Transition("Supplier Confirmation")
exp = Transition("Expedite Review")
ac  = Transition("Approve Configuration")
rp  = Transition("Release Production")
ar  = Transition("Archive Case")

xor_sc = OperatorPOWL(operator=Operator.XOR, children=[sc, SilentTransition()])
xor_exp = OperatorPOWL(operator=Operator.XOR, children=[exp, SilentTransition()])

po = StrictPartialOrder()
for n in [ro, cc, er, xor_sc, xor_exp, ac, rp, ar]:
    po.nodes.add(n)

# Broad start: all middle activities may begin after RO
po.order.add_edge(ro, cc)
po.order.add_edge(ro, er)
po.order.add_edge(ro, xor_sc)
po.order.add_edge(ro, xor_exp)

# Approval requires both checks and any present optional nodes
po.order.add_edge(cc, ac)
po.order.add_edge(er, ac)
po.order.add_edge(xor_sc, ac)
po.order.add_edge(xor_exp, ac)

# Expedite still requires both principal checks (D6)
po.order.add_edge(cc, xor_exp)
po.order.add_edge(er, xor_exp)

# Tail constraints
po.order.add_edge(ac, rp)
po.order.add_edge(rp, ar)

model_permissive = po
```

**Behavior deliberately excluded.**
- Any trace where `AC` precedes `RP`.
- Any trace where `EXP` is executed before both `CC` and `ER`.
- Any trace with `SC` after `AC`.
- Traces with activities outside the eight-label set or with repetition.

**Known underfitting risks.**
- **None for the intended scope:** By design, this model does not underfit; it is intended to overfit in precision. The risk is **false inclusion** (low precision), not false exclusion.
- If the true process actually requires `SC` only after `ER` has produced information (`D5` stricter reading), this model is too permissive.

# 9. Recommendation and Data-Collection Plan

**Immediate-use recommendation:** **Balanced (`model_balanced`)**.  
It respects all high-confidence rules (`D1`, `D2`, `D3`, `D6`), encodes the engineering view of concurrent checks (`S2`) without over-committing to strict sequence (`S1` is contradicted), and abstracts missing `SC` events through an explicit silent branch (`S5`). Its structural simplicity is sufficient for operational monitoring.

**Sensitivity-analysis recommendation:** **Permissive (`model_permissive`)** together with **Conservative (`model_conservative`)**.  
Use the conservative model as a **lower-bound sensitivity check**: if a future trace is rejected by conservative but accepted by balanced/permissive, it signals novel interleaving rather than rule violation. Use the permissive model as an **upper-bound** to see the full range of behavior allowed by `D1`–`D6`; any trace admitted by permissive but not by balanced highlights where the balanced partial order is too restrictive.

**Concrete data-collection plan to resolve ambiguities:**

| Ambiguity to resolve | Data / attribute to collect | Why it helps | Most informative future traces |
|---|---|---|---|
| `CC` vs `ER`: concurrent, sequential, or overlapping? (`D7`) | **Start timestamps** (not just completion); lifecycle status (`start`, `suspend`, `resume`). | Reveals true overlap. If both are `start`ed simultaneously, concurrency is confirmed (`+`). If `ER` always starts after `CC` `complete`, `S1` is validated. | A trace where `CC` starts, then `ER` starts before `CC` ends, then both complete in either ingestion order. |
| `SC` optionality: true skip (`S4`) vs missing event (`S5`) vs mandatory (`S3`)? | **`component_type`** (`external` vs `stocked`) on the order; **integration audit log** for `SC` events. | Allows labeling each absence as “legitimate skip” or “missing data.” | A `stocked` order with no `SC` event (confirms `S4`); an `external` order with no `SC` event but audit shows failed call (confirms `S5`). |
| `SC` dependency: requires one check or both? (`D5`) | **Supplier confirmation request timestamp** and **check-completion timestamp**. | If `SC` request is always after at least one check completes, D5 is stricter; if sometimes before any check completes, D5 is loose. | A trace where `SC` starts before either `CC` or `ER` completes (tests broad interpretation). |
| `EXP` conditions and ordering (`D6`, `S6`) | **`expedite_flag`** and **timestamp of `EXP`** relative to `SC`. | Confirms whether `EXP` can appear without `SC`, and whether it requires a specific check outcome. | Trace A: `EXP` after `SC`. Trace B: `EXP` with `SC` absent. Trace C: `EXP` with only one check completed (should be forbidden). |

# 10. Uncertainty Statement

**Calibrated confidence in major modeling decisions:**

| Decision | Confidence | Rationale / Alternative |
|---|---|---|
| `RO` start / `AR` end (`D1`) | **99%** | Unanimous in all 30 traces; no stakeholder contradiction. |
| `AC` before `RP` (`D2`) | **99%** | Unanimous (30/30); high domain confidence. |
| Both `CC` and `ER` required before `AC` (`D3`) | **85%** | No counter-example in log, but S5 missing-data risk means one check could be hidden; also `S1` challenges ordering, not presence. **Alternative:** If one check is sometimes truly skipped, `D3` fails. |
| `SC` before `AC` if present (`D4`) | **80%** | Always observed when present (20/20 with `SC`); but presence itself is ambiguous. |
| `SC` need not wait for both (`D5`) | **60%** | Only 2 traces (`V5`) place `SC` between checks; S2 supports flexibility; but S3 implies dependency on external-part status. **Alternative:** `SC` may actually require both checks (stricter `D5`). |
| `CC` and `ER` concurrent (`S2`, `D7`) | **55%** | Bidirectional DFG and expert opinion support it, but S7 (only completion stamps) means sequential overlap or ingestion ordering artifacts cannot be ruled out. **Alternative (material change):** If `S1` is correct and `CC  ER` is strict sequence, then the balanced/permissive partial orders are wrong and should be replaced by a sequential `(CC, ER)` block. This would **materially change the recommendation** in favor of a sequential model for operational monitoring. |
| `EXP` conditions (`D6`) | **70%** | Only 2 observations, but S6 is consistent and uncontradicted; missing-data risk applies. |
| Missing-data abstraction (`S5`) | **75%** | Integration failure is admitted by data engineer; without audit logs, we cannot distinguish true absence from missing event. |

**Plausible alternative interpretation that changes the recommendation:**  
If future start-timestamp data confirm `S1` (strict `CC  ER` sequence) and reject `S2` (parallel execution), the concurrent representation of `CC` and `ER` in both `balanced` and `permissive` becomes an overfitting artifact. In that case, the **conservative** model’s explicit sequential branches (`V1` and `V2`) would actually be closer to ground truth, and the recommendation should shift to a **sequential ProcessTree** (`(CC, ER)` or `(ER, CC)` with appropriate XOR for ordering ambiguity). Until such data are collected, the balanced concurrent model remains the best abductive compromise because it does not commit to either strict order, but this is precisely the central uncertainty.
