# OCEL 2.0 Repair Analysis: Multi-Bundle Abductive Reasoning

## 1. Consistency Rules and Evidence Model

### Hard Invariants (HI)
1. **HI-1**: An object cannot exist without being created by some event (no orphan objects without creation events)
2. **HI-2**: E2O relations must reference valid event IDs and object IDs present in the log
3. **HI-3**: O2O relations must reference valid object pairs from the log
4. **HI-4**: Object IDs must be unique within their type space

### Strong Defaults (SD)
1. **SD-1**: Create Order should relate to exactly one Order object (Domain Rule 1)
2. **SD-2**: Add Item should relate to one Order and one Item (Domain Rule 2)
3. **SD-3**: Dispatch Package normally relates to one Package and one Delivery (Domain Rule 4)
4. **SD-4**: Record Payment relates to exactly one Payment and normally one Invoice (Domain Rule 7)
5. **SD-5**: Lifecycle ordering must be temporally consistent (Order  Item  Package  Delivery  Invoice  Payment)
6. **SD-6**: Items belong to exactly one Order via O2O 'contains'
7. **SD-7**: Packages pack items from potentially multiple orders, but typically one order dominates

### Weak Heuristics (WH)
1. **WH-1**: Matching identifier prefixes (e.g., "PK-8" in ev08 scanner_ref suggests PK-8 involvement)
2. **WH-2**: Temporal proximity of events with similar objects suggests related processing
3. **WH-3**: Amount arithmetic matching suggests financial relationships but doesn't prove them (e2e INV-44=230, ORD-A=130+ORD-B=100)
4. **WH-4**: Customer matching across objects suggests business relationship (C17 appears in ORD-A, ORD-B, INV-44, ev11)
5. **WH-5**: Route consistency (NORTH appears in PK-7, PK-8, DEL-X, DEL-Y)
6. **WH-6**: External reference patterns ("N-420", "N-421", "N-42*") suggest carrier relationships
7. **WH-7**: Missing O2O where E2O exists suggests data quality issue rather than semantics

### Evidence Combination Strategy
I combine evidence hierarchically: hard invariants act as filters (any repair violating them is rejected). Strong defaults provide the baseline structure, with departures requiring explicit justification. Weak heuristics guide probability assignments when multiple repairs satisfy hard and strong constraints. When heuristics conflict (e.g., arithmetic matches ORD-B to INV-44, but no E2O evidence exists), I treat the conflict as informative about uncertainty rather than resolving it.

**Identifier similarity** weighs most heavily when prefixes show systematic patterns (PK-8/scanner_ref=PK8-2) and less when partial (N-42* could match N-420 or N-421). **Temporal evidence** constrains lifecycle ordering but simultaneous events (ev09/ev10 both at 10:00) allow multiple interpretations. **Amount matching** is weak evidence because domain rule 6 explicitly warns about fees and discounts. **Customer matching** is moderate evidence for grouping but doesn't imply specific O2O relations. **Route matching** weakly suggests DEL-Y carries PK-8 (both NORTH) but doesn't prove it.

## 3. Alternative Repair Bundles

### Bundle A: Conservative/Minimum-Change Repair

**Philosophy**: Add only relations with strong direct evidence; leave ambiguous cases unresolved.

**ev08 and PK-8**: Accept P01 (E2O ev08PK-8, confidence 0.85). The scanner_ref="PK8-2" is strong evidence. O2O PK-8 packs IT-B1 (P09, confidence 0.85) based on the same scanner reference. This gives PK-8 a clear pack event with IT-B1.

**ev10 and DEL-X/DEL-Y**: Leave unresolved. The external_ref="N-421?" has explicit uncertainty (question mark). Do not add any E2O relation. This means PK-8 is packed (ev08) but never dispatched—an incomplete lifecycle that reflects genuine data ambiguity.

**ev11 and delivery objects**: Accept no delivery E2O. ev11 confirms ORD-A only (already observed). Domain rule 5 explicitly allows portal confirmation by customer/order when carrier identifier is lost. The wildcard "N-42*" is too ambiguous to resolve.

**INV-44 and ORD-B**: Leave unresolved. No E2O relation added to ev12. The arithmetic match (230=130+100) is noted but treated as insufficient per domain rule 6. INV-44 bills only ORD-A (already observed). ORD-B remains unbilled—a business anomaly worth investigating.

**PAY-2 and INV-44**: Accept no relation. PAY-2 has no E2O to INV-44 or any other object. This represents unapplied cash or a payment whose allocation is deferred. The arithmetic matching (130) with ORD-A's declared_value is noted but not acted upon.

**Lifecycle coherence**: Conservative bundle produces incomplete but honest lifecycles. ORD-A flows OrderItemsPackageDelivery(confirmation)InvoicePayment (complete). ORD-B flows OrderItem but then stalls—item packed (PK-8 via IT-B1) but package never dispatched, never billed, never confirmed. PK-8 is packed but never dispatched. DEL-Y is created but never used. PAY-2 floats unapplied. This bundle prioritizes avoiding false precision over achieving closure.

### Bundle B: Bulk Dispatch with North Route Inference

**Philosophy**: Assume the two simultaneous Dispatch events (ev09, ev10) represent a coordinated bulk dispatch, and the route hints resolve delivery assignments.

**ev08 and PK-8**: Same as Bundle A—accept P01 and P09. PK-8 packs IT-B1.

**ev10 and DEL-X/DEL-Y**: Accept P02 (E2O ev10DEL-Y, confidence 0.60). Despite the question mark, the pattern "N-421?" strongly suggests DEL-Y (carrier_ref=N-421). Both ev09 and ev10 occur at identical timestamps (10:00) with route NORTH, suggesting a single truck receiving two deliveries. Add O2O DEL-Y carries PK-8 (P10, confidence 0.60). This completes PK-8's dispatch lifecycle.

**ev11 and delivery objects**: Accept dual confirmation—ev11 relates to both DEL-X and DEL-Y. Since ev11's external_ref="N-42*" uses a wildcard, it could represent a batch confirmation of both N-420 and N-421. Add E2O ev11DEL-X (P04, confidence 0.40) and ev11DEL-Y (P05, confidence 0.35). The ORD-A reference in ev11's portal_customer field covers both deliveries since both carry ORD-A items (IT-A1 in PK-7/DEL-X, IT-A2 in PK-8/DEL-Y). ORD-B's item IT-B1 also travels in PK-8/DEL-Y, implicitly confirmed.

**INV-44 and ORD-B**: Accept P07/P11 (E2O ev12ORD-B, O2O INV-44 bills ORD-B, confidence 0.65). The arithmetic match (130+100=230) combined with same customer C17 and the bundle's assumption that both orders shipped together makes this plausible. INV-44 now bills both ORD-A and ORD-B.

**PAY-2 and INV-44**: Accept P08/P12 (E2O ev14INV-44 for PAY-2, O2O PAY-2 settles INV-44, confidence 0.70). With INV-44 billing both orders (total 230), PAY-1 (100) and PAY-2 (130) perfectly settle the invoice. The two payments arriving 30 minutes apart suggests staged payment.

**Lifecycle coherence**: Bundle B produces complete lifecycles for all objects. ORD-A: OrderItemsPackages (split across PK-7, PK-8)Deliveries (DEL-X, DEL-Y)ConfirmationInvoicePayments. ORD-B: OrderItemPackage (PK-8 with ORD-A's IT-A2)Delivery (DEL-Y)InvoicePayment. Both packages dispatch, both deliveries confirm, invoice covers both orders, payments settle invoice. This bundle prioritizes explanatory completeness using available hints.

### Bundle C: Single Delivery with Scanner Reassignment

**Philosophy**: The scanner_ref in ev08 is misleading; IT-B1 was actually packed in PK-7 alongside IT-A1.

**ev08 and PK-8**: Reject P01. Instead, accept that ev08 represents a scanner outage scenario (domain rule 3). The scanner_ref="PK8-2" might be a corrupted read. Add E2O ev08PK-7 (confidence 0.45) and O2O PK-7 packs IT-B1 (confidence 0.45). PK-8 remains unpacked and possibly a data artifact or cancelled package. The gross_weight evidence weakly supports this: PK-7=3.1 could accommodate two items, PK-8=2.9 might be empty or single-item.

**ev10 and DEL-X/DEL-Y**: Accept P03 (E2O ev10DEL-X, confidence 0.30). This makes ev09 and ev10 both dispatch DEL-X—possibly a two-stage dispatch (e.g., scan then load confirmation). DEL-Y remains unused (potential cancelled delivery). PK-7 is dispatched twice but carries both items.

**ev11 and delivery objects**: Accept ev11DEL-X only (P04, confidence 0.40). DEL-Y needs no confirmation as unused. The ORD-A confirmation covers all ORD-A items now in DEL-X.

**INV-44 and ORD-B**: Same as Bundle B—accept P07/P11 (confidence 0.65). Both orders are complete and billable.

**PAY-2 and INV-44**: Same as Bundle B—accept P08/P12 (confidence 0.70).

**Lifecycle coherence**: Bundle C creates a simpler physical flow. ORD-A items both go to PK-7 (where IT-A1 was originally, IT-B1 joins from scanner reassignment), then PK-8 is unused. ORD-B's only item merges into ORD-A's package. DEL-X carries everything. DEL-Y is vestigial. Invoice and payments proceed as Bundle B. This bundle prioritizes minimizing distinct delivery objects at the cost of overriding scanner evidence.

## 5. Lifecycle and Cardinality Audit (Bundle A)

### Order Objects
**ORD-A lifecycle**: Create Order (ev01)  Add Items (ev03, ev04)  Items packed (ev06PK-7, ev07PK-8)  Package dispatched (ev09DEL-X)  Delivery confirmed (ev11)  Invoiced (ev12INV-44)  Payment (ev13PAY-1). **Plausible and complete**. ORD-B is an orphan after packing—its item sits in PK-8 which never dispatches. This is suspicious but honest: the data genuinely lacks dispatch, confirmation, and billing events for ORD-B. The O2O 'contains' relation (added in repair) is supported by ev05 E2O but no downstream O2O bridges exist.

### Item Objects
**IT-A1**: E2O created in ev03 (ORD-A), packed in ev06 (PK-7). O2O: ORD-A contains IT-A1; PK-7 packs IT-A1. **Complete lifecycle through packaging**. Independent E2O and O2O confirmation.

**IT-A2**: E2O created in ev04 (ORD-A), packed in ev07 (PK-8). O2O: ORD-A contains IT-A2; PK-8 packs IT-A2. **Complete through packaging**. No delivery confirmation exists for PK-8, so IT-A2's delivery status is unknown.

**IT-B1**: E2O created in ev05 (ORD-B), packed in ev08 (PK-8, provisionally accepted). O2O: ORD-B contains IT-B1 (added); PK-8 packs IT-B1 (added). **Complete through packaging**. Orphan from ORD-B's missing downstream lifecycle.

### Package Objects
**PK-7**: E2O created in ev06 (packs IT-A1), dispatched in ev09 (DEL-X). O2O: PK-7 packs IT-A1; DEL-X carries PK-7. **Complete lifecycle**. Well-supported by both E2O and O2O evidence.

**PK-8**: E2O created in ev07 (packs IT-A2), also packs IT-B1 via ev08 (provisionally accepted). **No dispatch event**. O2O: PK-8 packs IT-A2 and IT-B1 (added). **Orphan package**—packed but never dispatched. If ev08 is correct, PK-8 holds items from two orders but has no carrier.

### Delivery Objects
**DEL-X**: E2O dispatch in ev09 (carries PK-7). Delivery confirmed in ev11 (ORD-A, via portal). O2O: DEL-X carries PK-7. **Complete lifecycle**. DEL-X carries only PK-7, which contains only IT-A1—but ORD-A also has IT-A2 in PK-8. This means DEL-X confirms ORD-A without carrying all its items. Domain rule 5 allows confirmation by order even if partial delivery, but this is a mild inconsistency.

**DEL-Y**: E2O: none. O2O: none. **Orphan object**—created as an object with route_hint=NORTH and carrier_ref=N-421 but never used in any event. Possibly a planned delivery that was cancelled or merged.

### Invoice and Payment Objects
**INV-44**: E2O created in ev12 (bills ORD-A). O2O: INV-44 bills ORD-A; PAY-1 settles INV-44. **Complete lifecycle**. INV-44 bills only ORD-A (declared_value=130) but total=230, leaving 100 unexplained. Could represent fees, taxes, or combined billing where ORD-B's portion isn't explicitly linked.

**PAY-2**: E2O recorded in ev14 (no related objects). **Orphan payment**—amount=130 recorded but not linked to any invoice or order. Represents unapplied cash or a payment whose target invoice exists outside this log fragment.

### Circular Reasoning Check
The repair adds O2O "ORD-B contains IT-B1" based on ev05 E2O, then uses this O2O to confirm ORD-B's involvement in downstream reasoning (e.g., PK-8 carries ORD-B items). This creates mild circularity: the O2O edge depends entirely on the E2O edge, yet we might treat the O2O edge as independent confirmation. **[CIRCULAR]** The O2O edges for PK-8IT-B1 and ORD-BIT-B1 are both inferred from the same ev08/ev05 E2O evidence—they don't provide independent support.

from copy import deepcopy

# events_df: columns [ocel:eid, ocel:timestamp, ocel:activity, ocel:type:...]
# objects_df: columns [ocel:oid, ocel:type, ocel:ovmap:...]
# relations_df: columns [ocel:eid, ocel:oid, ocel:qualifier]

e2o_additions = pd.DataFrame([
    {
        'ocel:eid': 'ev08',
        'ocel:oid': 'PK-8',
        'ocel:qualifier': 'packs',
        'confidence': 0.85
    }

    {
        'ocel:oid': 'PK-8',
        'ocel:oid_2': 'IT-B1',
        'ocel:qualifier': 'packs',
        'confidence': 0.85
    },
    {
        'ocel:oid': 'ORD-B',
        'ocel:oid_2': 'IT-B1',
        'ocel:qualifier': 'contains',

    [relations_orig, e2o_additions[['ocel:eid', 'ocel:oid', 'ocel:qualifier']]],
    ignore_index=True

o2o_repaired = pd.concat(
    [o2o_orig, o2o_additions[['ocel:oid', 'ocel:oid_2', 'ocel:qualifier']]],

if orphan_eids or orphan_oids:
    raise ValueError(f"Referential integrity violated: events={orphan_eids}, objects={orphan_oids}")

# 5. Duplicate check
dupes = relations_repaired.duplicated(subset=['ocel:eid', 'ocel:oid', 'ocel:qualifier'])
if dupes.any():
    print(f"Warning: {dupes.sum()} duplicate relations detected")
    relations_repaired = relations_repaired[~dupes]

# 6. Construct OCEL object
# Note: OCEL constructor signature varies by pm4py version
# For pm4py >= 2.7.0, use:

    events=events_orig,  # events unchanged
    objects=objects_df,
    relations=relations_repaired,
    o2o=o2o_repaired
)
# For older versions, might need:
# ocel = pm4py.format.ocel_from_dataframes(events_orig, objects_df, relations_repaired)

# 7. Process mining discoveries

## 8. Over-Repair Warnings

### 1. **Forcing ev11 to confirm both deliveries creates false delivery confirmation**
In Bundle B, making ev11 confirm both DEL-X and DEL-Y assumes the wildcard "N-42*" matches both N-420 and N-421. If ev11 actually confirmed only one delivery (or neither), process mining would show a spurious Confirm DeliveryDispatch Package frequency of 2 instead of 1, making the process appear more reliable than it is. Downstream, delivery performance metrics would be inflated.

### 2. **Linking PAY-2 to INV-44 based on arithmetic risks masking payment anomalies**
If PAY-2 (130) actually represents a partial payment for a different invoice, or a duplicate payment, or a prepayment, forcing it to settle INV-44 with PAY-1 creates a false "perfect settlement" pattern. Accounts receivable process mining would miss a potential collections issue where invoices are paid in fragments.

### 3. **Assigning all ORD-A items to one delivery assumes consolidated shipping**
Bundle C's assumption that IT-B1 was packed into PK-7 (overriding scanner evidence) would make DEL-X appear to carry both ORD-A and ORD-B items. If these were actually separate shipments, downstream analysis of delivery utilization would show PK-7 as handling 3 items across 2 orders—a false consolidation pattern that could mislead warehouse optimization efforts.

### 4. **Adding ORD-B to INV-44 creates phantom billing relationship**
If ORD-B was actually billed separately (with its own invoice outside this log fragment), adding it to INV-44 creates a false many-to-one Order-to-Invoice relationship. Invoice flattening would show INV-44 covering two orders, inflating invoice processing metrics and potentially hiding that ORD-B's real invoice is missing from the log.

### 5. **Completing PK-8 dispatch via ev10 masks package loss scenarios**
The fact that PK-8 has no dispatch event in the original log could indicate the package was lost, damaged, or cancelled. Bundle B's repair would create a complete PackageDeliveryConfirmation chain for PK-8, erasing evidence of a potential logistics failure. Process mining would show 100% dispatch reliability instead of flagging PK-8 as an exception requiring investigation.

### 6. **Cross-bundle: Over-connecting ORD-B creates false process compliance**
Across Bundles B and C, fully connecting ORD-B's lifecycle makes the process appear perfectly compliant—every order flows through all activities. But the original log strongly suggests ORD-B encountered problems: its item was packed in a package that never dispatched. This could indicate a real business problem (item damaged during packing, order cancelled post-packing, package lost on loading dock). Repairs that erase this signal would prevent process mining from detecting the deviation and identifying its root cause.

### 7. **Assuming scanner_ref always identifies the correct package**
Both Bundle A and B trust scanner_ref="PK8-2" as reliable evidence for PK-8. If this scanner reference was corrupted (as domain rule 3 warns), PK-8 might not be the correct package. An aggressive repair would lock in this relation, while Bundle C correctly raises the alternative but with lower confidence. Over-trusting scanner data could misattribute items to wrong packages, creating downstream inventory discrepancies in process analysis.

### 8. **Circular enrichment danger via O2O enrichment tools**
If a user runs PM4Py's `ocel_o2o_enrichment` after any repair, the tool would transitively infer O2O relations: from PK-8 packs IT-B1 and DEL-Y carries PK-8, it would infer DEL-Y carries IT-B1, then from ORD-B contains IT-B1, it would connect DEL-Y to ORD-B. Each enrichment step uses repaired relations as ground truth, creating a cascade where a single 0.85-confidence edge spawns multiple unqualified edges. The conservative approach (Bundle A) deliberately leaves gaps to prevent this cascade.
