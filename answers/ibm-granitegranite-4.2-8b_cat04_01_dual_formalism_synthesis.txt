# 1. Assumptions and Interpretation

1. **Lowrisk / highrisk choice** – The risk level is chosen by external case data and is not encoded in the model. It is represented as an `XOR` branch immediately after *Analyze Root Cause*: either the `Supervisor Review` node (lowrisk) or a `PARALLEL` of `Quality Review` and `Regulatory Review` nodes (highrisk). Both branches are always present in the tree; at runtime one of them must be taken. The model cannot branch on runtime data, so the choice is static in the tree structure (i.e., the model admits both possibilities).

2. **Optional supplier consultation** – For simplicity and faithfulness, we approximate “optional” by always performing `Consult Supplier` (i.e., the activity is mandatory in the model). This is a permissive overapproximation for optionality: all allowed traces produced by the model include `Consult Supplier`. The approximation does not admit unsafe behaviour (the supplier node always finishes before *Release Material*, as enforced by dependencies). In the intended process, some cases may omit supplier consultation; our model therefore underrepresents those traces (i.e., it excludes the possibility of omitting supplier).

3. **Passing inspection abstraction** – No event label for “inspectpass” or “inspectfail” is used. Instead, the model contains two possible paths after the first `Inspect Trial`:
   * `PassBranch`: `Release Material` (and later `Archive Case`) directly follows `Inspect Trial`.
   * `FailBranch`: `Adjust Parameters`  `Execute Trial`  `Inspect Trial`  `Release Material` (and `Archive Case`).  
   The tree therefore cannot model more than one adjustment (i.e., more than two trial cycles). This is a conservative underapproximation: intended behaviour that repeats adjustments beyond the first failure is not generated by the tree, but the tree never allows `Adjust Parameters` after a passing inspection (the `FailBranch` always inserts `Adjust Parameters` before the second `Inspect Trial`).

4. **Duplicate visible labels** – Multiple occurrences of the same activity label (e.g., two `Execute Trial` nodes, two `Inspect Trial` nodes) are permitted. The model explicitly allows a second trial cycle via the `FailBranch`.

5. **Approximation policy for the processtree** – Conservative underapproximation:
   * The loop of trial iterations is limited to at most one adjustment (i.e., at most two trial cycles). This excludes intended behaviour with 2 adjustments but never admits an adjustment after a passing inspection.
   * All approval activities (`Supervisor Review`, `Quality Review`, `Regulatory Review`) must complete **before** the trial block starts. This respects “may overlap” in spirit (approvals and trial can be scheduled concurrently in reality) but imposes a stricter sequential constraint for simplicity. It does not admit unsafe interleavings (e.g., `Release Material` before approvals are done), because `Release Material` always appears after the trial block in the tree.
   * Optional supplier consultation is always included (see 2).  
   The tree thus underrepresents (a) cases that omit supplier consultation and (b) cases that require 2 trial iterations with adjustments.

6. **“May overlap” interpretation** – Interpreted as *absence of a strict order constraint* in the intended process. In the tree we use `PARALLEL` operators to allow concurrency at high granularity (e.g., `Contain Material``Analyze Root Cause`, `Quality Review``Regulatory Review`). However, because the tree is activitybased and must be linearised for a single trace, we place the trial block **after** the initial parallel block, thereby requiring that all containment/analysis and approval/design activities finish before the trial starts. This respects the safety guarantee (no unsafe overlap) but is stricter than the literal “may overlap”.

**Explanation of partialorder edges and concurrency:**

- Edges enforce all “must precede” relations (e.g., `Contain  Plan`, `AnalRC  Design`, etc.).
- No edge is added between `Contain` and `AnalRC`, allowing them to be concurrent.
- No edge between `QualRev` and `RegRev`, allowing them to be concurrent (highrisk branch).

- The edge `InspectT1  AdjP` forces that if the first inspection fails (i.e., the fail branch is taken), `Adjust Parameters` must occur before the second trial. The edge `InspectT1  RelM` is also present (for the pass branch), but a linear extension that chooses `AdjP` will necessarily place `AdjP` after `InspectT1` and before `ExecT2`; a linear extension that chooses `RelM` will place `RelM` after `InspectT1`. In practice, a trace that includes `AdjP` must place it after `InspectT1`; a trace that does not include `AdjP` simply omits it and places `RelM` after `InspectT1`. - All nodes appear in the set; `ArchC` depends on `RelM`, ensuring archiving occurs last.

- Because we do not include silent transitions or duplicate node names for repeated trials beyond the second trial, the model implicitly underapproximates loops longer than one adjustment (only one `AdjP` node exists). This matches the processtree approximation and is conservative (no unsafe behaviour).

5. **Silentbehavior / duplicatelabel check** – Since there are no silent events, the check focuses on verifying that multiple occurrences of `Execute Trial`/`Inspect Trial` appear correctly (i.e., the net/POWL does not collapse them). A simple test: generate a trace with two trial cycles and verify that the net produces two `Execute Trial` tokens in sequence.

6. **Limitations** – The validation plan cannot automatically verify the loop bound (2 adjustments) because the model only contains one `Adjust Parameters` node. Thus it will accept traces with only one adjustment but will not reject traces with two adjustments (since they cannot be represented). This limitation reflects the underapproximation and must be acknowledged. Additionally, the conversion to a Petri net may lose some partialorder nuances if the net generator does not preserve all edges; manual inspection of the net structure is required.

# 8. Final Self-Critique

1. **Supplier always included** – The model assumes `Consult Supplier` is mandatory, which underrepresents the true optionality. While this does not admit unsafe behaviour, it excludes legitimate cases where supplier consultation is not needed. A more precise POWL could use an optional node with a silent transition or a conditional choice, but within the given API and without data conditions, the simplest approximation was to always include it.

2. **Trial loop limited to one adjustment** – The processtree and POWL together allow at most one `Adjust Parameters` node, which cannot model cases requiring two or more adjustments. This underapproximation correctly never admits an adjustment after a passing inspection, but it fails to capture the full intended repeatuntil behaviour for 2 failures. A future model could introduce a `LOOP` operator with a guard based on inspection result, but since inspection outcome cannot be encoded as an event label, a precise loop representation remains an open approximation issue.

3. **Approvals must finish before trial in the tree** – The tree places the trial block after the initial parallel block, imposing that all containment/analysis, design, and approvals complete before any trial activity. While this guarantees safety (no release before approvals), it overconstrains concurrency compared to the intended “may overlap” phrasing. The POWL model partially alleviates this by allowing approvals to be interleaved with trial (no edge from approvals to trial), but the tree’s linearisation still forces approvals to precede trial for every trace it generates. This discrepancy between the tree and POWL could cause confusion when interpreting process visualisations; a more faithful tree would require a `PARALLEL` between the approval block and the trial block after both design and verification are ready.

These three weaknesses concern semantics (optionality, loop length, concurrency) rather than Python syntax, aligning with the requirement to list at least one semantic weakness.
