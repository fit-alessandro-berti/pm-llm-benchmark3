## 1. Target definition
**Primary target (operational, directly supported by the stored label)**  
- **Unit of analysis**: one credit application case (`case:concept:name`).  
- **Prediction time**: an early-warning prefix end \(t_p\) (e.g., after first \(k\) pre-decision events or after elapsed time \(\Delta\) from `Application Started`), constructed with an **as-of** rule (Section 4).  
- **Horizon**: 90 days **after** `Account Activated` (activation timestamp \(t_a\)).  
- **Target variable**: \(Y=\mathbb{1}[\text{default occurs within }(t_a, t_a+90d]]\), i.e., the warehouse `default_90d` which exists only for activated accounts.  
- **Population**: applications that **eventually activate** under the observed policy/process (\(A=1\)).  
- **Estimand**: conditional default risk among activated accounts under the observed selection and follow-up mechanisms:  
  \[
  \Pr(Y=1 \mid X_{0:t_p}, A=1)
  \]
  where \(X_{0:t_p}\) are features available at \(t_p\).

**Why this is defensible**: `default_90d` is undefined for rejected/withdrawn/open applications. Conditioning on eventual activation preserves honest target semantics and avoids inventing “non-default” labels for cases never exposed to credit.

**Credible alternative targets (answer different questions)**  
- **Alternative A (all applications; competing outcomes / multi-state)**: predict probabilities of terminal outcomes within a fixed window from application start (e.g., 180 days): {Rejected, Withdrawn, Transferred, Activated→Default within 90d, Activated→No default within 90d, Censored/Open}. This answers “what happens under current policy,” not “default risk if activated.”  
- **Alternative B (policy-specific counterfactual)**: “default within 90d if activated” for every application, including those rejected/withdrawn. This requires strong causal assumptions (exchangeability/transportability) largely untestable from this export; it must be labeled as counterfactual if attempted.

## 2. Cohort construction
**Inclusion rules (base cohort)**  
- Include **all 48,000** applications with `Application Started` between **2024-01-01** and **2025-12-31**.  
- Use events up to the extraction cutoff \(t_{asof}=\) **2026-02-15** (from `data_extract_time`), but construct prefixes/features with as-of rules so no post-\(t_p\) data enter features.

**Exclusion / consolidation rules (data quality + identifiers)**  
- **Migration duplicates (15 Oct 2025)**: drop exact duplicates (same case, activity, timestamp, resource, source_system) and flag near-duplicates for audit.  
- **Activity renaming**: map renamed activities to canonical names so variants and DFGs are comparable across time.  
- **Transfers**: treat `Transferred` as a competing terminal event for the originating case. Where linkage exists (~60%), optionally run a secondary “linked journey” analysis that follows the new identifier; otherwise treat follow-up as broken and do not impute default.

**Label observation rule**  
- A `default_90d` label is considered **observed** at \(t_{asof}\) only if:
  - `default_90d` is non-missing, and  
  - `label_available_at ≤ t_{asof}` (respects delayed feeds).

**Cohort-flow table (accounts for all 48,000 applications)**

## 3. Censoring and missing-label strategy
**Mechanisms to distinguish**  
- **Ordinary right censoring (process)**: still-open applications at \(t_{asof}\) (5,100) have not reached a terminal state.  
- **Ordinary right censoring (follow-up)**: activated accounts whose 90-day window is incomplete at \(t_{asof}\) (subset of 3,600).  
- **Delayed labels**: 90-day window complete but external feed delay means `label_available_at > t_{asof}` (subset of 3,600).  
- **Selection through activation**: \(Y\) exists only if \(A=1\); unconditional “default for every application” is not identified without counterfactual assumptions.  
- **Transfer**: competing terminal event; partial linkage creates lost follow-up.  
- **Permanently missing feeds**: especially partner-originated activated accounts; likely **MNAR** rather than benign censoring.

**Primary analysis strategy**  
- Keep the **primary estimand conditional on activation** and train/evaluate the default model among activated accounts.  
- Explicitly model label observation among activated accounts:
  - Classify activated cases into `observed`, `not_yet_90d`, `delayed_feed`, `missing_feed_suspected` using activation time and `label_available_at`.  
  - Use **inverse probability of label-observation weighting** (IPCW/IPLW) for evaluation (and optionally training): estimate \(p(\text{label observed} \mid t_a, \text{source_system}, \text{channel}, \text{region})\) and weight observed cases by \(1/p\). This mitigates bias from recency and systematic delays.  
- Report selection transparently: also estimate \(\Pr(A=1 \mid X_{0:t_p})\) and, if needed operationally, the **policy-dependent** joint quantity \(\Pr(A=1,Y=1 \mid X)=\Pr(A=1 \mid X)\Pr(Y=1 \mid X,A=1)\) (explicitly not counterfactual).

**Sensitivity analyses**  
- **Missing-feed bounds (MNAR)**: re-estimate default rates/metrics under extreme assumptions for `missing_feed_suspected` activated cases (all non-default vs all default), or vary an odds-ratio multiplier.  
- **Transfer handling**: compare (i) treat transfers as competing outcomes; (ii) censor at transfer; (iii) follow linked transfers and re-attribute outcomes to origin.  
- **Policy change robustness**: fit/validate separately pre- vs post-1 Jul 2025; compare calibration and base-rate shifts.

**Assumption testability**  
- **Partially testable**: delay depends on activation date/system rather than unobserved default after conditioning (compare older cohorts with early vs late label arrival).  
- **Untestable from this export**: counterfactual default for rejected/withdrawn; outcomes under changed acceptance/transfer policies; full MNAR mechanisms without external audits.

## 4. Prefix extraction
**As-of prefixing rule**: for each case and prediction point \(t_p\), use only events with `time:timestamp ≤ t_p` and only attributes valid at or before \(t_p\).

**Early-warning (pre-decision) truncation**  
- Define `stop_activities` = {Accepted, Rejected, Withdrawn, Transferred, Contract Signed, Account Activated, Collections Contact, Default Recorded}.  
- For pre-decision prediction, truncate each trace at the first stop activity and exclude the stop event itself; then generate prefixes.

**Fixed event-count prefixes**  
- For \(k \in \{2,3,5,8\}\), take the first \(k\) events from the pre-decision truncated trace.  
- **Short cases**: keep shorter prefixes and include `prefix_len` (recommended) or exclude with explicit coverage reporting.

**Elapsed-time prefixes**  
- For \(\Delta \in \{1h,24h,3d,7d\}\), include all events with timestamp \(≤\) (case start \(+\Delta\)), still truncated pre-decision.

**Handling loops, renaming, duplicates**  
- Rework loops (documents ↔ review) are kept and summarized (counts, time spent).  
- Apply deterministic activity-name mapping across the 15 Oct 2025 migration and remove duplicates so loops are not inflated by artifacts.

## 5. Process-aware features
**Static case attributes**  
- `case:channel`, `case:region`, `case:requested_amount`, `source_system`, start-time calendar features (month, weekday), policy-era indicator (start ≥ 2025-07-01).

**Control-flow (prefix-derived)**  
- Prefix length; last activity; activity counts/indicators; variant id/tuple (or hashed variant).  
- Rework: number of `Documents Requested`, number of returns to `Credit Review`, number of cycles.

**Timing (prefix-derived)**  
- Elapsed time since start; time since last event; inter-event time stats; time-to-KYC completion if observed.  
- Approximate waiting/sojourn summaries from timestamps (explicitly not true service times without start/end timestamps).

**Resource / handoff / queue proxies (as-of)**  
- Distinct resources, handoff count, concentration metrics.  
- Workload proxy at \(t_p\): recent count of other cases in `Credit Review` in same region/channel (computed only from events ≤ \(t_p\)).

**Risk-score dynamics (as-of)**  
- `risk_score_last` within prefix, number of updates, delta (last-first). Audit for backfill.

**Features requiring historical reference**  
- Resource experience at event time (needs HR history; extraction-time experience is biased).  
- `documents_total` snapshot (if present): must be lagged or recomputed from timestamped uploads to avoid same-day leakage.

## 6. Leakage audit
| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Post-decision; can be backfilled; encodes acceptance/terms | Only valid after final accept/limit-setting event | **Drop** (early warning) | Prevents learning the decision/terms instead of risk |
| `decision_reason` | Populated at/after Accept/Reject; near-direct decision reveal | Only after accept/reject timestamp | **Drop** (early warning) | Not available at \(t_p\); tautological |
| `collection_status` | Post-activation; can directly reveal default/collections | Only after activation and collections events | **Drop** | Direct outcome leakage |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | Post-treatment info; trivializes prediction | Only events with `time:timestamp ≤ t_p`; for early warning, \(t_p\) precedes stop activities | **Repair** by truncation | Enforces as-of perspective |
| `documents_total` (nightly snapshot) | Same-day leakage (includes later uploads) | Use lagged snapshot (≥1 day) or recompute from timestamped uploads ≤ \(t_p\) | **Repair or drop** | Prevents “future-within-day” leakage |
| Updated `risk_score` | Updates/backfill risk | Use last observed within prefix; audit first-non-null time vs milestones | **Keep with as-of rule + audit** | Legitimate dynamic signal if truly observed then |
| Resource experience (extraction-time) | Look-ahead: tenure increases; mismeasured at event time | Only valid if reconstructed as-of event timestamp | **Repair if possible; else drop** | Avoids future-tenure leakage and bias |
| `default_90d` | Label leakage | Never a predictor; use only for label construction | **Drop** | Prevents learning the answer key |
| `label_available_at` | Encodes maturity/latency; correlates with partner/missingness | Use only for censoring/label-availability modeling | **Drop** as predictor | Avoids learning feed latency |
| `data_extract_time` | Recency proxy; encodes maturity artifacts | Metadata only | **Drop** | Prevents shortcut learning |

## 7. Validation design
**Why not random splitting**  
- Mixes regimes across **1 Jul 2025 policy change** and **15 Oct 2025 migration**, inflating performance.  
- Ignores **label maturity**, making missing-label mechanisms differ across splits.

**Primary temporal backtesting (as-of aware)**  
- Split by **case start time** and filter labels by `label_available_at` at each evaluation as-of.  
- Rolling-origin folds such as:
  - Train on starts Jan–Dec 2024; validate Jan–Mar 2025.  
  - Train Apr 2024–Jun 2025; validate Jul–Sep 2025 (post-policy).  
  - Use Oct–Dec 2025 primarily for **process drift + prefix integrity** checks post-migration; evaluate default only for the subset with observed labels by the evaluation as-of (or schedule a later extraction for full outcome evaluation).

**Label maturity and censoring in evaluation**  
- For binary `default_90d` metrics: evaluate on activated cases with `label_available_at ≤ evaluation_asof`.  
- Report censored/missing proportions by activation month and `source_system`; use IPCW-weighted metrics as sensitivity where delays are substantial.

**Metrics (primary target)**  
- AUROC, AUPRC; Brier score; calibration intercept/slope; reliability curves.  
- Operational metrics at fixed alert volume (e.g., top 1% highest-risk activated accounts).  
- Subgroup calibration and missing-label rates by channel/region/source_system.

**Shift and robustness checks**  
- Report performance/calibration pre- vs post-policy.  
- Post-migration: compare variant mix and DFG/performance-DFG statistics; measure feature drift (PSI/KS).  
- Track missing-feed and transfer-linkage rates over time as part of model risk management.

## 8. Limitations and decision-use boundary
**What can be claimed**  
- Predictive association for **activated accounts**: early-prefix process signals related to `default_90d` among cases that activate under the observed policy.  
- Honest accounting of delayed/missing outcomes and selection via activation.

**What cannot be claimed**  
- Not a counterfactual “default risk for every application”; rejected/withdrawn cases have undefined `default_90d`.  
- Not causal effects of changing acceptance thresholds, document requests, staffing, or routing.  
- Partner-related missing feeds may be MNAR; corrections are sensitivity-based.

**How deployment can change the data-generating process**  
- **Selection feedback**: changing acceptance/limits changes who activates and the conditional outcome distribution.  
- **Process interventions**: alerts can trigger extra checks/document requests, altering prefixes and outcomes.  
- **Resource/routing changes**: staffing high-risk cases differently changes both features and outcomes (concept drift).  
- **Channel/partner mix shifts**: changes missing-feed patterns and calibration across domains.

**Decision-use boundary**  
- Use as a risk signal for **activated-portfolio management** (review prioritization, monitoring intensity, limit setting) with periodic recalibration and drift monitoring; do not present as counterfactual statements about applicants who would be rejected.

## 9. PM4Py-oriented Python implementation skeleton
```python
import numpy as np
import pandas as pd
import pm4py

CASE = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"

AS_OF = pd.Timestamp("2026-02-15")
HORIZON_DAYS = 90
MAX_FEED_DELAY_DAYS = 35
PREFIX_LEN = 5

STOP_ACTIVITIES = {
    "Accepted", "Rejected", "Withdrawn", "Transferred",
    "Contract Signed", "Account Activated",
    "Collections Contact", "Default Recorded",
}

LEAKY_COLS = {
    "default_90d", "label_available_at", "collection_status",
    "final_limit", "decision_reason", "data_extract_time",
}

def first_time(df, activities):
    m = df[ACT].isin(activities)
    return df.loc[m].groupby(CASE)[TS].min()

def last_nonnull(s):
    s = s.dropna()
    return s.iloc[-1] if len(s) else np.nan

df = pd.read_csv(
    "applications_events.csv",
    parse_dates=[TS, "label_available_at", "data_extract_time"],
)
df = df.sort_values([CASE, TS])

# --- Migration cleanup (rename + de-duplicate) ---
rename_map = {
    # Fill after inspecting renamed labels around 2025-10-15
    # "KYC Verification": "Identity/KYC Check",
}
if rename_map:
    df[ACT] = df[ACT].replace(rename_map)
df = df.drop_duplicates(subset=[CASE, ACT, TS, "org:resource", "source_system"])

# --- Case-level timeline table as-of AS_OF ---
case_tbl = pd.DataFrame(index=df[CASE].unique())
case_tbl["case_start"] = df.groupby(CASE)[TS].min()
case_tbl["t_activate"] = first_time(df, {"Account Activated"})
case_tbl["t_reject"] = first_time(df, {"Rejected"})
case_tbl["t_withdraw"] = first_time(df, {"Withdrawn"})
case_tbl["t_transfer"] = first_time(df, {"Transferred"})

def terminal_state(r):
    if pd.notna(r["t_reject"]):
        return "rejected"
    if pd.notna(r["t_withdraw"]):
        return "withdrawn"
    if pd.notna(r["t_transfer"]):
        return "transferred"
    if pd.notna(r["t_activate"]):
        return "activated"
    return "open"

case_tbl["terminal_state"] = case_tbl.apply(terminal_state, axis=1)

# Observed label as-of AS_OF (respects delayed feeds)
df_lab = df[pd.notna(df.get("default_90d"))].copy()
df_lab = df_lab[df_lab["label_available_at"] <= AS_OF]
case_tbl["default_90d_obs"] = df_lab.sort_values(TS).groupby(CASE)["default_90d"].last()
case_tbl["label_observed"] = case_tbl["default_90d_obs"].notna()
case_tbl["mature_by_time"] = (
    pd.notna(case_tbl["t_activate"])
    & (case_tbl["t_activate"] + pd.Timedelta(days=HORIZON_DAYS + MAX_FEED_DELAY_DAYS) <= AS_OF)
)

print("Cohort counts:")
print(
    case_tbl.assign(n=1)
    .groupby(["terminal_state", "label_observed", "mature_by_time"])["n"]
    .sum()
    .reset_index()
)

# --- Build pre-decision stream to prevent post-prefix events from entering features ---
stop_time = first_time(df, STOP_ACTIVITIES)
df = df.merge(stop_time.rename("stop_time"), left_on=CASE, right_index=True, how="left")
df_pred = df[(df["stop_time"].isna()) | (df[TS] < df["stop_time"])].copy()

# Drop leaky columns (protect against backfilled case attributes)
for c in LEAKY_COLS:
    if c in df_pred.columns:
        df_pred = df_pred.drop(columns=c)

# Approximate waiting/sojourn times from timestamps (no true start timestamps available)
df_pred = pm4py.insert_case_service_waiting_time(
    df_pred,
    activity_key=ACT,
    timestamp_key=TS,
    case_id_key=CASE,
    start_timestamp_key=TS,
)

# PM4Py formatting + fixed-length prefixes
df_pred = pm4py.format_dataframe(df_pred, case_id=CASE, activity_key=ACT, timestamp_key=TS)
pref_obj = pm4py.get_prefixes_from_log(df_pred, length=PREFIX_LEN, case_id_key=CASE)
df_pref = pref_obj if isinstance(pref_obj, pd.DataFrame) else pm4py.convert_to_dataframe(pref_obj)
df_pref = df_pref.sort_values([CASE, TS])

# Prefix feature table (examples; extend with rework/queue features as needed)
feat = df_pref.groupby(CASE).agg(
    prefix_len=(ACT, "size"),
    prefix_dur_s=(TS, lambda s: (s.max() - s.min()).total_seconds()),
    last_act=(ACT, "last"),
    n_resources=("org:resource", pd.Series.nunique),
    risk_score_last=("risk_score", last_nonnull),
    waiting_time_sum_s=(
        "@@waiting_time",
        lambda s: float(pd.to_timedelta(s).dt.total_seconds().sum()) if s.notna().any() else 0.0,
    ),
).reset_index()

static_cols = ["case:channel", "case:region", "case:requested_amount", "source_system"]
static = df_pref.groupby(CASE)[[c for c in static_cols if c in df_pref.columns]].first().reset_index()
feat = feat.merge(static, on=CASE, how="left")

# Attach labels (default defined only for activated cases)
labels = case_tbl.reset_index().rename(columns={"index": CASE})[
    [CASE, "terminal_state", "case_start", "t_activate", "default_90d_obs", "label_observed", "mature_by_time"]
]
model_df = feat.merge(labels, on=CASE, how="left")

# Temporal split by case start time (primary validation must be temporal)
train_end = pd.Timestamp("2025-06-30")
val_end = pd.Timestamp("2025-09-30")
model_df["split"] = np.select(
    [
        model_df["case_start"] <= train_end,
        (model_df["case_start"] > train_end) & (model_df["case_start"] <= val_end),
    ],
    ["train", "val"],
    default="test",
)

# Process descriptors on train only (for drift and process-aware diagnostics)
train_cases = set(model_df.loc[model_df["split"] == "train", CASE])
df_train_log = df_pred[df_pred[CASE].isin(train_cases)]
variants = pm4py.get_variants(df_train_log, case_id_key=CASE, activity_key=ACT, timestamp_key=TS)
dfg, start_acts, end_acts = pm4py.discover_dfg(df_train_log, case_id_key=CASE, activity_key=ACT, timestamp_key=TS)
print(f"Train variants: {len(variants)} | DFG edges: {len(dfg)}")

# Temporal summary (useful for detecting policy/migration shifts; not necessarily a predictor)
weekly = pm4py.extract_temporal_features_dataframe(
    df_pred, grouper_freq="W", activity_key=ACT, timestamp_key=TS, case_id_key=CASE
)
print("Weekly temporal summary (head):")
print(weekly.head())

# Leakage guard: ensure leaky columns did not sneak into df_pred
bad = [c for c in ["final_limit", "decision_reason", "collection_status", "default_90d", "label_available_at"] if c in df_pred.columns]
if bad:
    raise RuntimeError(f"Leaky columns present in prefix stream: {bad}")

# (PM4Py does not provide survival modeling; use external libraries while preserving the as-of cohort logic above).
```
