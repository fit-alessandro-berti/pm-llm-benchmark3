# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

- **A1.** The activity labels in the event log are the canonical alphabet. "Verify Bank Account" is a single activity, even though it can be re-executed (R11).
- **A2.** `Receive Onboarding Request` is mandatory and exactly once per case.
- **A3.** The three pre-classification checks are concurrent in the procedural sense, but every case contains all three.
- **A4.** "High-risk" and "low-risk" are operational labels. The procedural signal is the **approval type** that follows `Classify Risk`: `Manager Approval`  low-risk; `Enhanced Due Diligence` + `Compliance Approval`  high-risk.
- **A5.** "Several request/response cycles are possible" is interpreted as zero-or-more, in order, with the closing `Receive Clarification` of the last cycle occurring before any terminal outcome.
- **A6.** R9 ("the applicable approval") means: in an accepted case, the *actual* approval resource must differ from the *Verify Bank Account* resource. In a rejected case, R9 is vacuous because there is no applicable approval.
- **A7.** R10 ("at most once") is interpreted as "0 or 1" in `activ_freq` for the affected activities.
- **A8.** The temporal profile pairs are the **only** ones Compliance has declared normative. Other elapsed-time pairs are descriptive, not normative.
- **A9.** R5 and R6 are stakeholder statements, not jointly consistent in all traces. The conflict is real and must be surfaced, not silently averaged.
- **A10.** "Joint authorization outside the event log" means the conformance engine **cannot** verify R6 from the log alone; an external attribute (`case:emergency_authorized`, signed by Compliance + Operations) must be joined in.

## Two resolutions of the R5 / R6 conflict

```python
    rp.children.append(ProcessTree(label="Close Onboarding", parent=rp))
    outcome_xor.children.append(rp)

    # 5b. Low-risk path
    lp = ProcessTree(operator=Operator.SEQUENCE, parent=outcome_xor)
    for lbl in ("Manager Approval", "Activate Vendor",
                "Release First Payment", "Close Onboarding"):
        lp.children.append(ProcessTree(label=lbl, parent=lp))
    outcome_xor.children.append(lp)

    # 5c. High-risk path
    hp = ProcessTree(operator=Operator.SEQUENCE, parent=outcome_xor)
    for lbl in ("Enhanced Due Diligence", "Compliance Approval",
                "Activate Vendor", "Release First Payment",
                "Close Onboarding"):
        hp.children.append(ProcessTree(label=lbl, parent=hp))
    outcome_xor.children.append(hp)

    root.children.append(outcome_xor)
    return root

procedural_model = build_procedural_model()
```

## 3.3 Explanation of design choices

- **Concurrency.** `PARALLEL(Capture Master Data, Run Sanctions Screening, Verify Bank Account)` reflects the cross-cutting nature of these checks and tolerates the interleavings seen in T1–T8 (e.g. T2 starts with `Run Sanctions Screening` before `Capture Master Data`).
- **Clarification loop.** `XOR(, LOOP(SEQ(Request, Receive), ))` allows zero or more cycles, each cycle ending with `Receive Clarification` (the `do` child is the *whole* cycle, not a single activity). The outer `XOR` makes the loop optional. PM4Py's `LOOP` with `SEQ` as the `do`-child enforces "every `Request` is followed by a `Receive` before the next iteration." This is an **approximation**: a fully faithful encoding would also require "the last `Receive` precedes any terminal outcome," which the tree enforces only by *position* (the loop is a child of the root sequence, before the outcome `XOR`). We therefore duplicate the obligation in DECLARE (§4) and in the Log Skeleton (`equivalence(Request Clarification, Receive Clarification)`).
- **Choice.** A three-way `XOR` models the mutually exclusive outcomes. R1 and R2 are partly structural here, but the Log Skeleton and DECLARE layers are the *authoritative* enforcers, because the tree does not see resources (R9) and cannot express "exactly one approval" cleanly.
- **Terminal outcomes.** `Reject Vendor` and `Activate Vendor` are each followed by exactly one `Close Onboarding`; the tree's structure makes the second `Close` a foreign activity.
- **Deliberately excluded.**
  - `Sanctions Escalation` and `Obtain Legal Opinion` are excluded because their ordering relative to `Activate Vendor` is the R5/R6 conflict. Encoding the strict precedence in the tree would force resolution A.
  - `Change Bank Details` and `Suspend Vendor` are excluded because they are conditional post-activation lifecycle events. Modelling them as an unbounded loop after `Activate Vendor` would block the `Close Onboarding` that the backbone requires and would be a block-structuring violation.

## 4.1 Rule-direction table

| Rule | Direction | Semantics |
|---|---|---|
| `init(Receive Onboarding Request)` | unary | Every trace starts with this activity. |
| `existence(...)` | unary | Each listed activity must occur in every trace. |
| `exactly_one(...)` | unary | Each listed activity occurs exactly once. |
| `response(Request Clarification, Receive Clarification)` | binary (R3) | If `Request Clarification` occurs, `Receive Clarification` must occur *later* in the same trace. |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | binary (R4) | Conditional obligation: every escalation must eventually produce a legal opinion. |
| `response(Change Bank Details, …)` | binary (R11) | A change forces a suspend and a re-verify. |
| `precedence(Manager Approval, Activate Vendor)` | binary (R2) | `Activate Vendor` cannot occur unless a `Manager Approval` already occurred in the same trace. |
| `precedence(Obtain Legal Opinion, Activate Vendor)` `confidence=0.5` | binary (R5, contested) | Same direction as R2 but with halved confidence because the rule is **overridable** by the emergency branch. PM4Py reports it as a soft violation; the resource layer arbitrates. |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | binary (R7) | Escalation is gated by the screening. |
| `precedence(Capture Master Data, Classify Risk)` (and siblings) | binary | All three checks must precede classification. |
| `precedence(Verify Bank Account, Release First Payment)` | binary (R11) | No release without a (possibly repeated) verification. |
| `noncoexistence(Activate Vendor, Reject Vendor)` | binary (R1) | `{Activate, Reject}` is forbidden in any trace. |
| `noncoexistence(Manager Approval, Reject Vendor)` | binary (R2) | A rejected trace carries no approval. |
| `noncoexistence(Manager Approval, Compliance Approval)` | binary (R2, R8) | At most one of the two approvals. |
| `noncoexistence(Enhanced Due Diligence, Manager Approval)` | binary (R8) | The high-risk and low-risk branches never mix. |
| `responded_existence(Activate Vendor, Manager Approval)` `confidence=0.5` and analog for `Compliance Approval` | binary (R2) | If `Activate Vendor` occurs, **at least one** of the approvals must have occurred. The XOR is built from two disjuncts, each with `confidence = 0.5`. |

`response` vs `precedence`: `response(A, B)` is *forward-looking* (A  B later); `precedence(A, B)` is *backward-looking* (B  A earlier). `noncoexistence` is *symmetric* (both forbidden). The table distinguishes these explicitly.

`altresponse` / `chainsuccession` are deliberately empty: their stricter semantics (strict alternation / immediate adjacency) would over-constrain the clarification cycle and the high-risk sequence. We rely on the procedural tree for adjacency and on `response` / `equivalence` for the clarification alternation.

**Notes on overlap and orientation.** The pair orientation is the Log Skeleton convention: `("A", "B")` is symmetric for `equivalence` and `never_together`, and directed (`A before B`) for `always_before`, `always_after`, `directly_follows`. Several pairs duplicate DECLARE (`Manager Approval  Activate Vendor`, `Reject  Activate`); this is intentional — the Log Skeleton is **authoritative for R1, R2's mutual-exclusion aspect, R8, and R10**, while DECLARE is authoritative for *conditional* obligations (R3, R4, R7, R11). `directly_follows(Activate Vendor, Release First Payment)` is conservative: it will flag T6 because `Obtain Legal Opinion` is interleaved; we therefore override the flag with the resource-layer R6 check before raising a hard violation (see §8).

# 6. Temporal Profile

```python
# zeta = 2.0
temporal_profile = {
    ("Request Clarification",   "Receive Clarification"):  (48 * 3600,  24 * 3600),
    ("Sanctions Escalation",    "Obtain Legal Opinion"):   (12 * 3600,   6 * 3600),
    ("Activate Vendor",         "Release First Payment"):  (72 * 3600,  36 * 3600),
}
```

**Why temporal deviations are warnings, not control-flow violations.** The temporal profile is a *stochastic* description of the typical case; it is calibrated to a population mean and standard deviation, not a contract. Compliance itself states that the three pairs are "normative enough to flag but not automatically reject." Treating them as hard control-flow edges would (i) require timestamps to be perfectly comparable across resources and time zones, (ii) couple conformance to the data-quality of the log, and (iii) duplicate the deterministic obligations already encoded in DECLARE (`response`, `precedence`). The `zeta = 2.0` band corresponds to a ~95% confidence interval under a Gaussian assumption, which is a reasonable but **soft** threshold. We therefore surface `pm4py.conformance_temporal_profile(...)` output as warnings in §8 and route hard violations to the resource layer.

# 7. Resource- and Data-Aware Checks

The following checks operate on a `pandas` event log. They are layered *after* the activity-only checks because they may need external joins. Each check is annotated with the attributes it requires and the fallback when the attribute is missing.

```python
import pandas as pd
from datetime import timedelta
import pm4py

# Required columns:
#   case:concept:name   — case id
#   concept:name        — activity
#   time:timestamp      — pandas Timestamp
#   org:resource        — performer
# Optional column (joined from an external system for R6 / R9-Sign):
#   case:emergency_authorized  — bool, default False
#   case:legal_signer          — resource id of the legal co-signer

# ---------------------------------------------------------------------------
# R9 — Segregation of duties
# ---------------------------------------------------------------------------
def check_r9_sob(df: pd.DataFrame) -> list[tuple[str, str]]:
    """Return (case_id, message) for every SoD violation."""
    out = []
    required = {"org:resource"}
    if "org:resource" not in df.columns:
        return [("*", "R9 not evaluable: org:resource missing")]
    for case_id, case in df.groupby("case:concept:name"):
        res_of = {a: case.loc[case["concept:name"] == a, "org:resource"].tolist()
                  for a in ("Capture Master Data", "Verify Bank Account",
                            "Manager Approval", "Compliance Approval",
                            "Activate Vendor")}
        # Rule (a): Verify Bank Account resource  applicable approval resource
        if res_of["Verify Bank Account"] and res_of["Manager Approval"]:
            if res_of["Verify Bank Account"][-1] == res_of["Manager Approval"][-1]:
                out.append((case_id, "R9(a): Verify Bank Account and Manager Approval by same resource"))
        if res_of["Verify Bank Account"] and res_of["Compliance Approval"]:
            if res_of["Verify Bank Account"][-1] == res_of["Compliance Approval"][-1]:
                out.append((case_id, "R9(a): Verify Bank Account and Compliance Approval by same resource"))
        # Rule (b): Capture Master Data resource  Activate Vendor resource
        if res_of["Capture Master Data"] and res_of["Activate Vendor"]:
            if res_of["Capture Master Data"][-1] == res_of["Activate Vendor"][-1]:
                out.append((case_id, "R9(b): Capture Master Data and Activate Vendor by same resource"))
    return out

# Equivalent one-liner for R9(a) using the built-in primitive:
def filter_r9_four_eyes(df: pd.DataFrame):
    """Demonstrates pm4py.filter_four_eyes_principle for R9(a)."""
    return pm4py.filter_four_eyes_principle(
        df, activity1="Verify Bank Account", activity2="Manager Approval"
    )

# ---------------------------------------------------------------------------
# R6 — Emergency activation with 24-hour opinion
# ---------------------------------------------------------------------------
def check_r6_emergency(df: pd.DataFrame,
                       max_lag: timedelta = timedelta(hours=24)) -> list[tuple[str, str]]:
    """Return (case_id, message) for every R6 violation or confirmation."""
    out = []
    if "case:emergency_authorized" not in df.columns:
        # Without the flag, R6 cannot be invoked; surface this honestly.
        return [("*", "R6 not evaluable: case:emergency_authorized missing")]
    for case_id, case in df.groupby("case:concept:name"):
        flag = case["case:emergency_authorized"].iloc[0]
        act  = case.loc[case["concept:name"] == "Activate Vendor", "time:timestamp"]
        op   = case.loc[case["concept:name"] == "Obtain Legal Opinion", "time:timestamp"]
        esc  = case.loc[case["concept:name"] == "Sanctions Escalation", "time:timestamp"]
        if flag and not act.empty and not esc.empty:
            # Emergency path: opinion must arrive within max_lag AFTER activation
            if op.empty:
                out.append((case_id, "R6 violation: emergency activation, no opinion recorded"))
            else:
                lag = (op.iloc[0] - act.iloc[0])
                if lag < timedelta(0):
                    out.append((case_id, f"R6 ok: opinion preceded activation by {-lag}"))
                elif lag <= max_lag:
                    out.append((case_id, f"R6 ok: opinion arrived {lag} after activation (24h)"))
                else:
                    out.append((case_id, f"R6 violation: opinion arrived {lag} after activation (>24h)"))
    return out

# ---------------------------------------------------------------------------
# R10 — At-most-once (defence-in-depth; Log Skeleton already enforces it)
# ---------------------------------------------------------------------------
def check_r10_at_most_once(df: pd.DataFrame) -> list[tuple[str, str]]:
    out = []
    for a in ("Reject Vendor", "Activate Vendor", "Release First Payment"):
        counts = df[df["concept:name"] == a].groupby("case:concept:name").size()
        for case_id, n in counts.items():
            if n > 1:
                out.append((case_id, f"R10 violation: {a} occurred {n} times"))
    return out

# ---------------------------------------------------------------------------
# R11 — Post-activation change  suspend  re-verify before next payment
# ---------------------------------------------------------------------------
def check_r11_post_activation(df: pd.DataFrame) -> list[tuple[str, str]]:
    out = []
    for case_id, case in df.groupby("case:concept:name"):
        case = case.sort_values("time:timestamp")
        names = case["concept:name"].tolist()
        if "Change Bank Details" not in names:
            continue
        # The first change is the one we monitor for the canonical pattern.
        try:
            i = names.index("Change Bank Details")
        except ValueError:
            continue
        after = names[i+1:]
        if "Suspend Vendor" not in after:
            out.append((case_id, "R11 violation: Change Bank Details without Suspend Vendor"))
        # Any later Release First Payment must be preceded by another Verify
        verifies = [j for j, n in enumerate(after) if n == "Verify Bank Account"]
        releases = [j for j, n in enumerate(after) if n == "Release First Payment"]
        for r in releases:
            if not any(v < r for v in verifies):
                out.append((case_id, "R11 violation: Release First Payment after Change without re-verify"))
                break
    return out
```

# 9. Contradictions, Redundancies, and Blind Spots

1. **Duplicated enforcement.** R1, R2's mutual-exclusion aspect, and R8 appear in both DECLARE (`noncoexistence`) and the Log Skeleton (`never_together`). This is intentional: declarative engines cross-validate, and a future change to one layer should not silently relax the other. The deployment pipeline (§10) runs both and reports a violation only when the *authoritative* layer fails.

2. **R5 / R6 inconsistency under loops.** The procedural tree is a strict ordering; R6 demands a *time-bounded* exception. The hybrid model resolves this by moving R6 entirely to the resource layer and lowering the DECLARE confidence for R5. A trace can pass the procedural check (no foreign activity, no forbidden pair) yet still be policy-pending because the emergency flag is missing — exactly the T6 situation.

3. **R11 vacuity under a single verification.** If a case has exactly one `Verify Bank Account` and no `Change Bank Details`, the Log Skeleton pair `always_before(Verify Bank Account, Release First Payment)` is satisfied trivially. A buggy case that *omits* the verification before the first payment would also be caught by `directly_follows(Activate, Release)` *only if* the payment is adjacent, which is the typical pattern. The pair is therefore not fully defensive — `Release First Payment` is preceded by `Activate Vendor` in the tree, but the *re*-verify after a change is the contract; we rely on DECLARE `response(Change Bank Details, Verify Bank Account)` for that branch.

4. **Tight coupling of `Activate` and `Release`.** The procedural tree's `SEQ(Activate, Release, Close)` makes `Release First Payment` look mandatory after activation. R10 says it occurs *at most once*, but the backbone does not make it conditional on demand. The Log Skeleton's `activ_freq` allows 0; the procedural tree does not. This is an *approximation* — the tree is a happy-path backbone, not a normative contract. Authoritative enforcement of "release may be skipped" lives in `activ_freq`.

5. **Missing case attributes.** `case:emergency_authorized` and the dual-signer identifiers are absent from the log. R6 is therefore not evaluable end-to-end; the system can only flag that the case *might* be eligible for the emergency path and route it to a manual queue. Likewise, R9's SoD check returns "not evaluable" if `org:resource` is missing — common in privacy-redacted exports.

6. **Timestamp-only limitations.** `conformance_temporal_profile` assumes a single global clock and Gaussian residuals. Cross-region vendors and DST boundaries routinely produce false positives. We therefore treat deviations as warnings, never as automatic rejects, and keep the deterministic R5 / R6 obligations in DECLARE / resource layer where they belong.

7. **Support / confidence as normative truth.** A `confidence = 0.5` precedence (R5) is not "half-enforced"; it is a *signal* that the rule is contested. Using these numbers as hard thresholds in a downstream dashboard would invite violations to slip through. The deployment recipe (§10) treats low-confidence DECLARE rules as warnings that always require human arbitration.

8. **The procedural tree cannot see resources.** A four-eyes violation (T4) passes the procedural model cleanly. This is the strongest argument for keeping R9 in a separate layer rather than encoding it as a procedural attribute.

# 10. Deployment Recommendation

1. **Canonical procedural representation.** PM4Py process tree as in §3, attached to the variable `procedural_model`. The tree is the *narrative* of the case and the reference for documentation and training; it is **not** the source of truth for control-flow obligations.

2. **Authoritative policy layer (in evaluation order).**
   1. **Procedural** — `pm4py.conformance_diagnostics_token_based_replay(log, procedural_model)` (or the equivalent tree replay). Foreign activities and structural mismatches are reported here.
   2. **DECLARE** — `pm4py.conformance_declare(log, declare_model)`. Hard violations are raised; `confidence < 1.0` rules are surfaced as warnings.
   3. **Log Skeleton** — `pm4py.conformance_log_skeleton(log, log_skeleton)`. Authoritative for R1, R2 (mutual exclusion), R8, R10.
   4. **Temporal profile** — `pm4py.conformance_temporal_profile(log, temporal_profile, zeta=2.0)`. Always warnings.
   5. **Resource / data layer** — §7. Authoritative for R6, R9, R10 (defence-in-depth), R11.

3. **Order of evaluation and contradictory findings.** The conformance service runs the five layers in the order above and merges findings into a single case-level report:
   - A **hard fail** in any layer short-circuits to `fail`.
   - A **warning** in a lower layer is *added* to a procedural / DECLARE pass, yielding `warning`.
   - A **policy-dependent** verdict (only T6 today) is reported as such, with the *out-of-band* attribute surfaced by name so that Legal + Operations can clear it manually.
   - All findings carry the *earliest decisive event* (case id + activity + timestamp + resource) so that a human auditor can navigate to the violation without re-running the analysis.

4. **Surface to users.**
   - The dashboard shows four badges per case: *Structure* (procedural), *Policy* (DECLARE), *Skeleton* (Log Skeleton), *Time* (temporal), and a separate *Resource* tab for SoD / emergency verdicts.
   - Low-confidence DECLARE rules are rendered with an amber "contested" tag that links to the §1 conflict explanation.
   - Every contradictory finding between two layers (e.g. T6 passes procedural, fails DECLARE under R5) is reported in a dedicated *Cross-layer* panel so that model drift or layer misconfiguration can be detected early.
