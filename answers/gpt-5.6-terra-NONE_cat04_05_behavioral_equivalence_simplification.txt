# 1. Equivalence Notions

Let `vis()` remove silent `tau` transitions from an execution sequence ``. A complete visible trace is the sequence of visible labels produced by an execution from the initial marking to the final marking.

Duplicate labels are distinguished by **occurrence position in a trace**: for example, two occurrences of `Check Revision` are two separate events in the sequence. They are not distinguished by transition identity once projected to labels, unless explicitly stated otherwise. Under P2, repeated checks are further collapsed to one Boolean fact.

## Visible trace equivalence after hiding `tau`

Models \(M_A\) and \(M_B\) are visible-trace equivalent iff:

\[
L_{vis}(M_A) = L_{vis}(M_B)
\]

where:

\[
L_{vis}(M) =
\{vis(\sigma) \mid \sigma \text{ is a complete execution of } M\}
\]

`Approve Revision` remains visible. Only `tau` is hidden.

## Bounded visible-language equivalence under P3

Let \(L_{P3}(M)\) be the complete visible traces of model \(M\) satisfying both:

- visible trace length is at most 12;
- `Analyze Revision` occurs at most three times.

Then P3 bounded equivalence is:

\[
L_{P3}(M_A) = L_{P3}(M_B)
\]

This is a finite, test-oriented comparison. Equality under P3 does **not** prove unbounded visible-trace equivalence.

## Business-relevant equivalence under P1

P1 observes every visible event occurrence and its ordering, including repeated `Check Revision`, repeated `Analyze Revision`, `Rework Case`, and optional visible `Approve Revision`.

A P1-observable trace must satisfy the intended revision-cycle rule:

- each `Analyze Revision` occurrence has its own subsequent `Check Revision`;
- that check occurs before the following `Rework Case`, if any, or before `Close Case`;
- `Rework Case` separates analysis attempts;
- `Approve Revision`, if present, remains attributable to the revision attempt in which it occurs.

Two models are P1-equivalent only if they admit the same compliant operational traces, including the placement and multiplicity of checks and approvals.

## Abstracted dashboard equivalence under P2

Define the dashboard abstraction \(D\) of a complete visible trace \(t\) as:

\[
D(t) =
(
\text{Open-first},
\text{Close-last},
\#Analyze,
\exists Check,
\exists Rework
)
\]

where:

- `Open-first` means the first event is `Open Case`;
- `Close-last` means the final event is `Close Case`;
- \(\#Analyze\) is the number of `Analyze Revision` occurrences;
- \(\exists Check\) is whether at least one `Check Revision` occurs;
- \(\exists Rework\) is whether at least one `Rework Case` occurs;
- all `Approve Revision` occurrences and silent transitions are ignored;
- the exact interleaving of `Analyze Revision` and `Check Revision` is ignored;
- repeated checks are collapsed to the Boolean fact “a check occurred.”

The models are dashboard-equivalent iff:

\[
\{D(t) \mid t \in L_{vis}(M_A)\}
=
\{D(t) \mid t \in L_{vis}(M_B)\}
\]

Under this abstraction, both models produce the same dashboard states:

\[
(\text{true}, \text{true}, n, \text{true}, n > 1)
\quad \text{for all } n \ge 1
\]

because both require at least one check, permit any positive number of analyses, and have a rework iff there is more than one analysis attempt.

# 2. Structural Comparison

| Feature | Model A | Model B | Semantic consequence |
|---|---|---|---|
| Loop scope | The loop body contains `+('Analyze Revision', 'Check Revision')` followed by optional approval. | The loop contains only `Analyze Revision` followed by optional approval. `Check Revision` is outside the loop, in parallel with the whole loop. | A has one check per analysis revision; B has one overall check for the entire case. |
| Minimum `Check Revision` occurrences | One, because the loop body executes once and every loop body contains one check. | One, because the parallel branch contains one check. | Both require at least one check overall. |
| Maximum `Check Revision` occurrences | Unbounded: one per loop-body execution. | Exactly one. | Visible trace languages differ as soon as there are two revision attempts. |
| Possible placement of `Check Revision` | In each revision attempt, concurrent with that attempt’s analysis; must finish before optional approval and before that iteration’s rework/exit. | May occur at any time after `Open Case` and before the parallel join that precedes `Close Case`; it may occur before all analyses, between attempts, or after all analyses. | B permits checks that are not associated with each analysis attempt. |
| `Approve Revision` occurrences | Optional once per revision attempt. Thus zero through unboundedly many approvals are possible. | Optional once per revision attempt. Thus zero through unboundedly many approvals are possible. | Approval multiplicity is the same, but its relationship to the single global check differs. |
| Concurrency | Per iteration: `Analyze Revision` and `Check Revision` may interleave within an iteration. | One global `Check Revision` branch runs concurrently with the entire loop. | B permits global check placement across reworks and across multiple analysis attempts. |
| Rework behavior | After an iteration completes, the loop may exit or execute `Rework Case` and start another checked analysis iteration. | After an analysis/approval iteration completes, the loop may exit or execute `Rework Case` and start another iteration; the sole check branch may still be unfinished. | In B, a rework can occur before the one check. In A, each preceding analysis is checked before rework. |
| Join before `Close Case` | The loop must finish before `Close Case`. There is no separate check branch outside the loop. | Both the one-check branch and the revision loop must complete before `Close Case`. | B cannot close before its sole check completes, but it can perform many analyses before that check. |
| First possible post-open visible event | `Analyze Revision` or `Check Revision`. | `Analyze Revision` or `Check Revision`. | Superficially similar at the first iteration only. |
| Two-analysis behavior | Necessarily includes two checks, one in each iteration. | Necessarily includes only one check total. | This is the decisive structural and behavioral difference. |

# 3. Verdicts

| View | Verdict | Confidence | Decisive reason | Caveat |
|---|---|---:|---|---|
| P1 operational compliance | not equivalent | High | Model A enforces one check per analysis revision before rework or closure; Model B has exactly one global check and permits rework or multiple analyses before it. | If P1 were weakened to require merely one case-level check, B could be acceptable, but that is not the stated rule. |
| P2 executive dashboard | equivalent only under stated abstraction | High | Both yield the same abstract dashboard tuples: any positive analysis count, a check exists, and rework exists exactly when analysis count exceeds one. | The result depends on collapsing repeated checks and ignoring check/analyze ordering and approvals. |
| P3 bounded testing view | not equivalent | High | The difference is observable within the stated bound; for example, two analyses require two checks in A but only one in B. | This bounded result is sufficient to refute equivalence, but bounded testing alone would not prove unbounded equivalence if no witness were found. |

# 4. Counterexample Traces

All traces below are complete visible traces. `tau` from the optional approval choice is omitted. The outer `Open Case` and `Close Case` sequence is included.

| Trace ID | Trace | Model A | Model B | First decisive semantic difference | Relevant view |
|---|---|---|---|---|---|
| A-only-1 | `Open Case, Check Revision, Analyze Revision, Rework Case, Check Revision, Analyze Revision, Close Case` | admitted | not admitted | A has two loop iterations and therefore two checks. B has exactly one `Check Revision` transition. | P1, P3 |
| A-only-2 | `Open Case, Analyze Revision, Check Revision, Approve Revision, Rework Case, Analyze Revision, Check Revision, Close Case` | admitted | not admitted | The second revision in A has its own check. B cannot produce two checks. | P1, P3 |
| B-only-1 | `Open Case, Analyze Revision, Rework Case, Analyze Revision, Check Revision, Close Case` | not admitted | admitted | In B, the global check can occur after a rework and after the second analysis. A requires a check before the first rework. | P1, P3 |
| B-only-2 | `Open Case, Check Revision, Analyze Revision, Rework Case, Analyze Revision, Approve Revision, Close Case` | not admitted | admitted | B performs one early global check, then allows a second analysis with no second check. A requires a check in the second iteration. | P1, P3 |
| B-only-3 | `Open Case, Analyze Revision, Approve Revision, Rework Case, Analyze Revision, Check Revision, Close Case` | not admitted | admitted | The first analysis reaches approval and rework before any check. A’s parallel check must complete before approval and rework for that iteration. | P1, P3 |
| A-only-3 | `Open Case, Analyze Revision, Check Revision, Rework Case, Check Revision, Analyze Revision, Approve Revision, Close Case` | admitted | not admitted | Again, A has a separate check in each iteration; B has only one. | P1, P3 |

The two directions are both non-inclusions:

\[
L_{vis}(A) \nsubseteq L_{vis}(B)
\]

because A can contain two or more `Check Revision` occurrences, while B contains exactly one.

\[
L_{vis}(B) \nsubseteq L_{vis}(A)
\]

because B can execute `Rework Case` before the single check, or can perform a second analysis after the one global check without another check. A cannot: every iteration’s parallel block must complete before that iteration’s `Rework Case` or loop exit.

## Effect of optional approval and hidden `tau`

`X('Approve Revision', tau)` means each revision attempt can either:

- visibly execute `Approve Revision`; or
- take `tau`, yielding no visible approval.

Hiding `tau` does not eliminate the behavioral difference:

- A still has one visible `Check Revision` per analysis iteration.
- B still has exactly one visible `Check Revision` globally.

Approval can create additional traces, but it does not repair B’s missing per-revision check discipline. It also provides further P1 distinctions: in A, approval is only reachable after that iteration’s check has completed; in B, an approval may occur before the global check.

# 5. Bounded Comparison Code

The following code uses PM4Py process-tree parsing and conversion to accepting Petri nets. It performs an **exhaustive bounded breadth-first exploration** over reachable markings, subject to:

- at most 12 visible events;
- at most three `Analyze Revision` events;
- a finite silent-transition safety bound;
- exact equality with the final marking for acceptance.

The silent bound is a practical termination guard. For these sound process trees, silent behavior is acyclic enough for the intended exploration. If a model contained silent loops, a finite silent bound would make the procedure bounded rather than globally exhaustive.

```python
import pm4py
from collections import deque

TREE_A = """->(
  'Open Case',
  *(
    ->(
      +('Analyze Revision', 'Check Revision'),
      X('Approve Revision', tau)
    ),
    'Rework Case'
  ),
  'Close Case'
)"""

TREE_B = """->(
  'Open Case',
  +(
    'Check Revision',
    *(
      ->(
        'Analyze Revision',
        X('Approve Revision', tau)
      ),
      'Rework Case'
    )
  ),
  'Close Case'
)"""

MAX_VISIBLE_EVENTS = 12
MAX_ANALYZE_EVENTS = 3

# Defensive guard for models with silent cycles. It is intentionally generous
# relative to these small trees.
MAX_SILENT_STEPS = 50


def marking_key(marking):
    """
    Canonical, hashable representation of a PM4Py Marking.
    Uses place names plus object identity as a fallback for duplicate names.
    """
    return tuple(sorted(
        (getattr(place, "name", repr(place)), id(place), count)
        for place, count in marking.items()
        if count != 0
    ))


def is_final_marking(marking, final_marking):
    return marking == final_marking


def transition_label(transition):
    """
    PM4Py uses transition.label == None for silent transitions in most versions.
    Some conversions may expose tau-like names; only labels are visible here.
    """
    return transition.label


def fire_transition(net, marking, transition):
    """
    PM4Py normally provides execute; import it explicitly for compatibility.
    """
    from pm4py.objects.petri_net import semantics
    return semantics.execute(transition, net, marking)


def exhaustive_bounded_visible_language(
    net,
    initial_marking,
    final_marking,
    max_visible_events=12,
    max_analyze_events=3,
    max_silent_steps=50,
):
    """
    Exhaustive over all states within the stated visible and analyze bounds,
    plus max_silent_steps as a practical guard.

    State includes:
      - marking;
      - visible trace prefix;
      - number of Analyze Revision occurrences;
      - number of silent transitions fired.

    A trace is recorded only when the current marking equals final_marking.
    """
    accepted = set()

    # Include trace in state because the same marking can be reached through
    # different visible histories, both of which matter for language comparison.
    queue = deque()
    queue.append((initial_marking, tuple(), 0, 0))

    visited = set()

    while queue:
        marking, trace, analyze_count, silent_steps = queue.popleft()

        state_key = (
            marking_key(marking),
            trace,
            analyze_count,
            silent_steps,
        )
        if state_key in visited:
            continue
        visited.add(state_key)

        if is_final_marking(marking, final_marking):
            accepted.add(trace)

        # Do not extend visible behavior past the visible bound.
        # Silent transitions may still be needed to reach final marking.
        for transition in pm4py.get_enabled_transitions(net, marking):
            label = transition_label(transition)
            next_marking = fire_transition(net, marking, transition)

            if label is None:
                if silent_steps >= max_silent_steps:
                    continue
                queue.append((
                    next_marking,
                    trace,
                    analyze_count,
                    silent_steps + 1,
                ))
            else:
                if len(trace) >= max_visible_events:
                    continue

                next_analyze_count = analyze_count + (
                    1 if label == "Analyze Revision" else 0
                )
                if next_analyze_count > max_analyze_events:
                    continue

                queue.append((
                    next_marking,
                    trace + (label,),
                    next_analyze_count,
                    silent_steps,
                ))

    return accepted


def print_language(title, language):
    print(f"\n{title}: {len(language)} traces")
    for trace in sorted(language, key=lambda x: (len(x), x)):
        print("  " + " -> ".join(trace))


def build_accepting_net(tree_string):
    tree = pm4py.parse_process_tree(tree_string)
    net, initial_marking, final_marking = pm4py.convert_to_petri_net(tree)
    return tree, net, initial_marking, final_marking


def main():
    tree_a, net_a, im_a, fm_a = build_accepting_net(TREE_A)
    tree_b, net_b, im_b, fm_b = build_accepting_net(TREE_B)

    print("Soundness A:")
    print(pm4py.check_soundness(net_a, im_a, fm_a, print_diagnostics=True))

    print("\nSoundness B:")
    print(pm4py.check_soundness(net_b, im_b, fm_b, print_diagnostics=True))

    lang_a = exhaustive_bounded_visible_language(
        net_a, im_a, fm_a,
        max_visible_events=MAX_VISIBLE_EVENTS,
        max_analyze_events=MAX_ANALYZE_EVENTS,
        max_silent_steps=MAX_SILENT_STEPS,
    )
    lang_b = exhaustive_bounded_visible_language(
        net_b, im_b, fm_b,
        max_visible_events=MAX_VISIBLE_EVENTS,
        max_analyze_events=MAX_ANALYZE_EVENTS,
        max_silent_steps=MAX_SILENT_STEPS,
    )

    only_a = lang_a - lang_b
    only_b = lang_b - lang_a
    common = lang_a & lang_b

    print(f"\nP3 bounds: visible <= {MAX_VISIBLE_EVENTS}, "
          f"Analyze Revision <= {MAX_ANALYZE_EVENTS}")

    print(f"\nCommon traces: {len(common)}")
    print_language("Unique to Model A", only_a)
    print_language("Unique to Model B", only_b)

    if not only_a and not only_b:
        print("\nResult: equal under the explored bounds.")
        print("Warning: this would be bounded evidence only, not a proof "
              "of unbounded equivalence.")
    else:
        print("\nResult: NOT bounded-visible-language equivalent under P3.")
        print("The displayed traces are complete-trace witnesses.")


if __name__ == "__main__":
    main()
```

A random alternative would be:

```python
# This is NOT exhaustive: it samples playouts and may miss rare interleavings.
sampled_a = pm4py.play_out(pm4py.parse_process_tree(TREE_A))
sampled_b = pm4py.play_out(pm4py.parse_process_tree(TREE_B))
```

Random or heuristic playout is useful for smoke testing, but it cannot establish P3 equality because absence of a sampled witness is not absence from the bounded language.

# 6. Stochastic and Footprint Comparison

## Footprints

`pm4py.discover_footprints(...)` can compare coarse behavioral relations such as sequence, parallelism, and exclusiveness between labels. It can provide useful diagnostic evidence:

```python
tree_a = pm4py.parse_process_tree(TREE_A)
tree_b = pm4py.parse_process_tree(TREE_B)

net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)

footprints_a = pm4py.discover_footprints((net_a, im_a, fm_a))
footprints_b = pm4py.discover_footprints((net_b, im_b, fm_b))

print("Footprints A:", footprints_a)
print("Footprints B:", footprints_b)
```

Expected qualitative difference:

- A exposes recurring local concurrency between `Analyze Revision` and `Check Revision`.
- B exposes concurrency between the single `Check Revision` and the entire loop, potentially including `Rework Case` and later analysis attempts.

Equal footprints would still not establish trace equivalence because footprints are pairwise or relation-oriented summaries. They generally do not preserve:

- counts of repeated labels;
- loop-scoped obligations;
- complete-trace language;
- higher-order dependencies such as “every analysis has its own check.”

For example, B’s “exactly one global check” versus A’s “one check per iteration” is a multiplicity property that footprints may not represent precisely.

## Stochastic languages

`pm4py.get_stochastic_language(...)` can estimate or derive a language distribution when a stochastic source is available. A model alone does not determine meaningful probabilities unless one declares a policy for choices and interleavings.

For example, one may explicitly declare an artificial simulation policy:

- choose enabled transitions uniformly;
- cap visible length and loop executions;
- generate a specified number of playouts.

That policy is an analysis assumption, not a property of the original models.

Illustrative code, subject to PM4Py version-specific parameter names:

```python
# Example only: probabilities are induced by the playout mechanism,
# not supplied by the business models themselves.

tree_a = pm4py.parse_process_tree(TREE_A)
tree_b = pm4py.parse_process_tree(TREE_B)

# In some PM4Py versions, get_stochastic_language accepts a process tree or net.
# Consult the installed PM4Py version for playout parameters and seed handling.
stochastic_a = pm4py.get_stochastic_language(tree_a)
stochastic_b = pm4py.get_stochastic_language(tree_b)

print(stochastic_a)
print(stochastic_b)
```

Before interpreting results, declare:

1. loop exit probability;
2. optional approval probability;
3. concurrency scheduling/interleaving policy;
4. trace-length truncation policy.

Without those declarations, comparing probability distributions is not business-semantic evidence.

## Earth Mover’s Distance

If two stochastic languages are represented compatibly, PM4Py can compute Earth Mover’s Distance:

```python
emd_value = pm4py.compute_emd(stochastic_a, stochastic_b)
print("EMD:", emd_value)
```

A low EMD does not establish trace equivalence:

- it may arise because distinct traces have low probability;
- truncation may omit long-loop differences;
- different trace supports can still have small transport distance;
- EMD depends on the selected ground distance between traces;
- it depends on the declared or inferred probabilities.

Conversely, a high EMD can support the claim that operational behavior differs under the chosen probability model, but it is still not a proof of language inequality unless the underlying support difference is directly inspected.

# 7. Complexity Comparison

The following counts treat each process-tree operator and each leaf as one node. `tau` is a silent leaf. Duplicate-label count means the number of repeated visible-label occurrences beyond the first occurrence of a given label in the tree.

## Derived structural counts

| Metric | Model A | Model B | Comparison |
|---|---:|---:|---|
| Process-tree nodes | 13 | 13 | Equal syntactic node count. |
| Maximum operator/leaf depth, root at depth 0 | 4 | 4 | Equal depth. |
| Visible leaves | 6 | 6 | Equal visible-leaf count. |
| Silent leaves | 1 | 1 | Equal silent-leaf count. |
| Visible labels with duplicate tree leaves | 0 | 0 | Neither tree repeats a visible leaf syntactically. |
| Duplicate-label count beyond first occurrence | 0 | 0 | Repetition arises dynamically through looping, not duplicate leaves. |
| Dynamic maximum checks | Unbounded | 1 | Major behavioral, not syntactic, difference. |
| Dynamic maximum analyses | Unbounded | Unbounded | Both loop. |
| Petri-net simplicity | Compute with PM4Py | Compute with PM4Py | Conversion structure may differ despite equal tree counts. |

Although the raw tree counts are equal, Model A is operationally more structured because the check is inside the loop. Model B is not simpler by node count; it merely has a different concurrency scope.

## Structural-count code

```python
import pm4py
from collections import Counter


def children_of(node):
    # PM4Py ProcessTree nodes expose children as a list.
    return list(getattr(node, "children", []) or [])


def is_leaf(node):
    return len(children_of(node)) == 0


def label_of(node):
    return getattr(node, "label", None)


def count_process_tree(tree):
    all_nodes = []
    leaves = []

    def visit(node, depth):
        all_nodes.append((node, depth))
        kids = children_of(node)
        if not kids:
            leaves.append(node)
        for child in kids:
            visit(child, depth + 1)

    visit(tree, 0)

    visible_labels = []
    silent_leaves = 0

    for leaf in leaves:
        label = label_of(leaf)
        if label is None or label == "tau":
            silent_leaves += 1
        else:
            visible_labels.append(label)

    label_counter = Counter(visible_labels)
    duplicate_beyond_first = sum(
        count - 1 for count in label_counter.values() if count > 1
    )

    return {
        "node_count": len(all_nodes),
        "max_depth": max(depth for _, depth in all_nodes),
        "leaf_count": len(leaves),
        "visible_leaves": len(visible_labels),
        "silent_leaves": silent_leaves,
        "visible_label_counter": label_counter,
        "duplicate_label_count_beyond_first": duplicate_beyond_first,
    }


tree_a = pm4py.parse_process_tree(TREE_A)
tree_b = pm4py.parse_process_tree(TREE_B)

print("A tree metrics:", count_process_tree(tree_a))
print("B tree metrics:", count_process_tree(tree_b))

net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)

print("A Petri-net simplicity:",
      pm4py.simplicity_petri_net(net_a, im_a, fm_a))
print("B Petri-net simplicity:",
      pm4py.simplicity_petri_net(net_b, im_b, fm_b))
```

`simplicity_petri_net(...)` should be reported from the installed PM4Py version rather than assumed here, because metric implementation and conversion details can vary by version.

# 8. Simplified Model

## Target semantics: P2 executive dashboard

P2 is the appropriate target for simplification because it intentionally discards:

- per-revision check multiplicity;
- exact placement of checks;
- approval occurrences;
- silent behavior;
- detailed interleavings.

A P1-preserving simplification should retain the loop-scoped check obligation and is therefore close to Model A. A single compact model cannot preserve P1’s per-iteration compliance semantics while also collapsing checks to the P2 Boolean fact as executable behavior.

## Compact process tree

```text
->(
  'Open Case',
  +(
    'Check Revision',
    *(
      'Analyze Revision',
      'Rework Case'
    )
  ),
  'Close Case'
)
```

This model is structurally simpler than both originals:

- 8 nodes, versus 13 nodes;
- maximum depth 3, versus 4;
- 5 visible leaves, versus 6;
- 0 silent leaves, versus 1;
- no optional approval branch.

It preserves P2 exactly, but not P1.

## PM4Py code

```python
import pm4py

SIMPLIFIED_TREE = """->(
  'Open Case',
  +(
    'Check Revision',
    *(
      'Analyze Revision',
      'Rework Case'
    )
  ),
  'Close Case'
)"""

simplified_model = pm4py.parse_process_tree(SIMPLIFIED_TREE)

simplified_net, simplified_im, simplified_fm = pm4py.convert_to_petri_net(
    simplified_model
)

print(pm4py.check_soundness(
    simplified_net,
    simplified_im,
    simplified_fm,
    print_diagnostics=True
))
```

## Preservation table

| Property | Status | Explanation |
|---|---|---|
| `Open Case` first | exact | Sequence root forces it first. |
| `Close Case` last | exact | Sequence root forces it last after the parallel block completes. |
| At least one `Analyze Revision` | exact | Binary loop body executes once. |
| At least one `Check Revision` | exact | Parallel branch contains one mandatory check. |
| Dashboard count of analyses | exact | Loop body executes once or more; each body has one analysis. |
| Dashboard fact “any rework occurred” | exact | Rework occurs iff the loop repeats, hence iff there are at least two analyses. |
| Repeated checks collapsed to Boolean | exact at P2 abstraction | The simplified model has one check, matching the dashboard’s Boolean observation. |
| Exact check/analyze interleaving | abstracted | P2 intentionally ignores it. |
| `Approve Revision` occurrences | lost | P2 hides approvals; P1 does not. |
| One check per analysis revision | lost | The simplified model has one case-level check, not one check per iteration. |
| Approval after iteration-specific check | lost | Approval is removed. |
| P1 operational compliance | not preserved | The model permits multiple analyses/reworks with a single check. |
| P3 visible-language equivalence to A or B | not preserved | It is deliberately a P2 abstraction, not a P3 trace-language replacement. |

## Regression traces

These traces are accepted by the simplified model and have valid P2 dashboard summaries.

| Type | Trace |
|---|---|
| Regression 1 | `Open Case, Check Revision, Analyze Revision, Close Case` |
| Regression 2 | `Open Case, Analyze Revision, Check Revision, Close Case` |
| Regression 3 | `Open Case, Analyze Revision, Rework Case, Check Revision, Analyze Revision, Close Case` |
| Regression 4 | `Open Case, Check Revision, Analyze Revision, Rework Case, Analyze Revision, Rework Case, Analyze Revision, Close Case` |
| Negative 1 | `Open Case, Analyze Revision, Close Case` — rejected because the mandatory check has not occurred. |
| Negative 2 | `Open Case, Check Revision, Close Case` — rejected because the loop requires at least one analysis. |
| Negative 3 | `Open Case, Analyze Revision, Rework Case, Close Case` — rejected because the rework branch requires another analysis iteration and the check branch must also complete. |

For P2, each positive regression trace maps to one of the intended dashboard states:

- one analysis, check occurred, no rework;
- two analyses, check occurred, rework occurred;
- three analyses, check occurred, rework occurred.

# 9. Final Recommendation

- **P1 operational compliance:** use **Model A**. It is the only original model that enforces a separate `Check Revision` for every analysis attempt before rework or closure. Model B is unsuitable because its single global check can occur too early, too late, or only once across multiple revisions.

- **Simplified model:** do not replace Model A with the simplified model for operational execution or compliance. The simplified model is appropriate only as a dashboard-oriented abstraction or reporting model. Finally, bounded comparison is valuable for finding concrete witnesses and regression tests, but it is not a proof of unbounded equivalence. In this case the bounded witnesses already refute equivalence; in a case with no bounded witness, further formal language reasoning or unbounded state-space analysis would still be required.
