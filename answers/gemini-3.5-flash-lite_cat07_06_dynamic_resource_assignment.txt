# 1. Objectives and constraints

Designing a dynamic resource-assignment policy requires balancing competing operational goals. We categorize them into **Safety/Compliance Constraints** (hard limits that must never be breached) and **Preference Trade-offs** (competing optimization dimensions).

### Optimization Objectives
1. **Short-Term Throughput:** Minimize cycle times and clear cases rapidly, prioritizing urgent deadlines.
2. **Skill Development:** Strategically allocate training opportunities (skill level 1-2 cases) to resources based on their designated training priority, provided SLA risk is low.
3. **Workload Fairness:** Distribute open cases and remaining hours fairly to prevent burnout and uneven queue buildup.
4. **Continuity of Case Ownership:** Minimize unnecessary handovers, which historical data links to a 1.8x higher rework rate, a 1.4x higher appeal rate, and a median 2.7-hour waiting penalty for high-complexity cases.
5. **SLA Risk:** Minimize SLA breaches by prioritizing tasks nearing their deadlines.
6. **Resilience:** Avoid creating artificial bottlenecks in high-demand roles (e.g., Security, Approval) and protect resources flagged with high overtime risk.

### Safety and Compliance Constraints (Hard Rules)
- **C1 (Skill & Safety):** No high-priority case may be assigned to a skill level below 2 unless under explicit supervision.
- **C2 (Security Specialization):** Security Review must be performed by skill level 3, or by skill level 1–2 only under explicit supervision by R7_Gita or R8_Hugo.
- **C3 (Approval Governance):** Final Approval must be performed by skill level 2–3. Skill level 1 may prepare but not finalize.
- **C4 (Batching Rules):** Quality Check may be batched only when priority is normal/low and SLA time remaining > 24h.
- **C5 (Overtime Protection):** Do not assign work to resources with `overtime_risk="high"` unless SLA risk is urgent (`urgent` priority or < 4h remaining) and no safer alternative exists.
- **C6 (Batch Load Cap):** No resource should receive more than 4 new assignments in the current decision batch.

# 2. Assignment policy

The proposed policy uses a multi-factor scoring function combined with hard filtering gates.

### Pseudocode & Scoring Framework

```text
For each case C in Queue:
    1. Filter out resources where skill == 0 (not allowed).
    2. Apply Hard Constraints (C1 - C5):
       - If Case priority == urgent and Resource skill < 2 (and not supervised): exclude.
       - If Activity == Security Review and Skill < 3 and Supervisor (R7/R8) unavailable: exclude.
       - If Activity == Final Approval and Skill < 2: exclude.
       - If Resource overtime_risk == "high" and Case SLA > 4h and priority != urgent: exclude.
       - If Resource batch assignment count >= 4: exclude.

    3. For each eligible Resource R, compute the composite utility score:
       
       Score(C, R) = 
             w1 * SLA_Urgency_Score(C)
           + w2 * Skill_Match_Score(C, R)
           + w3 * Continuity_Score(C, R)
           + w4 * Workload_Fairness_Score(R)
           + w5 * Training_Bonus(C, R)
           - w6 * Overtime_Penalty(R)
           - w7 * Handover_Cost_Penalty(C, R)

    4. Select Resource R* with the maximum Score(C, R*).
    5. Update Resource R* load and batch assignment count.
```

### Sub-Score Definitions
- **SLA Urgency Score:** $\max(0, 1 - \frac{\text{SLA\_hours\_remaining}}{48}) \times \text{Priority\_Multiplier}$ (where urgent = 3.0, high = 2.0, normal = 1.0, low = 0.5).
- **Skill Match Score:** Normalised resource skill score (0 to 3 scale mapped to 0.0 to 1.0).
- **Continuity Score:** $+1.0$ if $R == \text{C.current\_owner}$ and complexity/handover cost is high; $0.0$ otherwise.
- **Workload Fairness Score:** Inverse of current open cases and remaining hours today, normalized across the team.
- **Training Bonus:** $+0.8$ if the case required skill matches the resource’s `training_priority`, case priority is normal/low, and SLA risk is low.
- **Overtime Penalty:** High penalty ($-\infty$ or heavy negative weight) if `overtime_risk == "high"` and SLA conditions do not justify an exception.
- **Handover Cost Penalty:** Scaled penalty based on the `handover_cost_band` (high = heavy penalty, low = negligible) if changing owners on a high-complexity case.

# 6. Process-mining audit indicators

To ensure the policy executes correctly and safely in practice, process mining indicators are tracked over the event log using PM4Py metrics:

1. **Handover Frequency:** Measured via `pm4py.discover_handover_of_work_network` to detect excessive bouncing of cases between resources.
2. **Reassignment Count:** Average `reassignment_count` per case variant, flagging workflows exceeding 2 reassignments.
3. **Skill Mismatch Rate:** Proportion of events where resource skill score == 1 on high-priority or high-complexity cases without a recorded supervisor.
4. **Workload Distribution:** Gini coefficient of `workload_snapshot` and open cases per resource across teams.
5. **Overtime Risk Exposure:** Percentage of tasks assigned to resources with `overtime_risk == "high"` outside of defined urgent SLA exceptions.
6. **SLA Misses:** Percentage of cases where `timestamp > sla_deadline`, segmented by priority.
7. **Rework/Appeal Rate:** Frequency of `Rework Correction` loops correlated with prior assignment reasons.
8. **Training Assignment Share:** Percentage of normal/low priority tasks allocated to resources matching their `training_priority` (Target: $\ge 20\%$).
9. **Specialist Bottleneck Indicators:** Average queue waiting time before `Security Review` and `Final Approval` using `pm4py.insert_case_service_waiting_time`.
10. **Policy Deviation Rate:** Frequency with which manual overrides bypass the dynamic policy recommendation.

# 7. PM4Py implementation sketch

The following Python pseudocode demonstrates how event log data and process mining indicators are integrated to audit and refine the resource assignment policy.

```python
import pandas as pd
import pm4py

# 1. Load and format event log data
df = pd.read_csv("service_process_log.csv")
log = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource",
)

# 2. Discover handover of work networks to audit continuity and routing friction
handover_net = pm4py.discover_handover_of_work_network(log)
print("Handover of Work Network edges:", len(handover_net["edges"]))

# 3. Discover working together and organizational roles for resource similarity
working_together = pm4py.discover_working_together_network(log)
resource_similarity = pm4py.discover_activity_based_resource_similarity(log)
organizational_roles = pm4py.discover_organizational_roles(log)

# 4. Measure service and waiting times to identify bottlenecks (e.g., Security & Approval)
log_with_times = pm4py.insert_case_service_waiting_time(
    log,
    case_id_key="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
)

# 5. Discover performance DFG to evaluate cycle times across variants
dfg, start_activities, end_activities = pm4py.discover_performance_dfg(log_with_times)

# 6. Filter event log by performance or attributes to audit policy compliance
# Example: Filter cases with high reassignments or SLA breaches
variants = pm4py.get_variants(log)
high_rework_cases = pm4py.filter_event_attribute_values(
    log, "reassignment_count", ["2", "3"], level="case"
)

# 7. Visualize Social Network Analysis (SNA) for auditing collaboration and workload
sa, sn = pm4py.discover_working_together_network(log)
# pm4py.save_vis_sna(sa, "working_together_sna.png")

print("PM4Py audit pipeline executed successfully. Indicators ready for review.")
```
