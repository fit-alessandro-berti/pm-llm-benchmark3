# 3. Consequences for performance analysis

- **G1 (Genuine simultaneous batch):** No bias. Waiting time, service time, and utilization are accurately reflected.
- **G2 (Start batching):** Overestimates service time for later items in the batch (since their recorded start time is prematurely set to the batch start). Underestimates waiting time for later items.
- **G3 (End batching):** Overestimates service time for earlier items (since their recorded complete time is delayed to the batch end).
- **G4 (Sequential batching):** Accurate service times. Waiting time between items in the sequence will appear as zero, which is accurate for the process but might obscure upstream bottlenecks if treated as a single batch.
- **G5 (Shared-account artifact):** If treated as a single resource, utilization will appear to exceed 100%, and service times will overlap impossibly. Bottleneck detection will be skewed by the false assumption of a single worker's capacity.
- **G6 (End-of-shift data entry):** Creates massive inflation of waiting time (items appear to wait in queue until 17:00) and near-zero service time (start and complete are both 17:00). This completely invalidates bottleneck and utilization metrics. The inflated waiting time occurs because the system assumes the item was sitting idle from its queue arrival until the arbitrary 17:00 start time. The near-zero service time occurs because the start and complete timestamps are logged simultaneously at the end of the shift, rather than reflecting the actual physical duration of the work.
- **G7 (Timestamp coarsening):** Introduces quantization noise. Service times will appear as multiples of 15 minutes, and waiting times will be artificially grouped.
- **G8 (Queue accumulation):** Accurate service times, but waiting times will include the downtime from the capacity loss (safety check). This is a genuine operational delay, not a logging artifact, but must be contextualized to avoid blaming the resource for the queue.

# 5. Robustness and alternative explanations

- **Resource IDs trusted vs. shared accounts:** If `analyst_pool` (G5) is trusted as a single physical worker, the overlapping timestamps imply impossible multitasking or a massive data error. Treating it as a shared account resolves the anomaly, revealing concurrent work by multiple individuals.
- **Timestamps exact vs. interval-censored:** If G7 timestamps are treated as exact, it appears as a simultaneous batch of 5 items processed in exactly 15 minutes. Treating them as interval-censored (due to the 15-minute precision) reveals that the work was likely sequential but rounded to the nearest quarter-hour boundary.
- **Three cases where the same temporal pattern supports multiple physical explanations:**
  1. **Identical start and complete times (G1 vs. G7):** This pattern can indicate a genuine simultaneous batch (G1, automated cell) or severe timestamp coarsening/rounding (G7, legacy MES).
  2. **Overlapping intervals (G5):** This can indicate a shared-account artifact (multiple people working concurrently under one ID) or a single worker genuinely multitasking/context-switching between cases.
  3. **Identical start, sequential complete (G2):** This can indicate start batching (clicking "begin group" for all items before working sequentially) or a scenario where a worker starts multiple tasks simultaneously but finishes them at different times due to varying complexity.

# 6. Data-collection redesign

1. **Resource/Badge Identity:** Eliminate shared logins (like `analyst_pool`). Require individual badge scans or unique logins to accurately measure individual utilization and concurrency.
2. **Execution vs. Recording Timestamps:** Ensure all systems capture the actual physical execution time, not just the database insertion time. For manual forms (G6), implement auto-save or intermediate status buttons to prevent end-of-shift bulk logging.
3. **Timestamp Precision Metadata:** Upgrade legacy systems (G7) to record timestamps with at least 1-second precision. If impossible, explicitly log the rounding rules as metadata so analysts can apply interval censoring.
4. **Group/Batch Identifiers:** For genuine batches (G1) and start batches (G2), introduce a unique `batch_id` field. This explicitly links items processed together, removing the need to infer batches purely from timestamps.
5. **Pause/Resume Events:** Implement pause/resume tracking to differentiate between active service time and downtime/interruptions, particularly useful for understanding queue accumulation (G8).
6. **Source Clocks:** Synchronize clocks across all systems (e.g., safety system and scanner in G8) using a central NTP server to prevent artificial queue times or negative durations.

# 7. Final adjudication

- **High confidence:** G1 (genuine simultaneous batch), G4 (sequential batching). These can be used directly for performance analysis.
- **Exclude or interval-censor in queue analysis:** G6 (exclude entirely from service/waiting time analysis due to end-of-shift bulk logging), G7 (interval-censor to account for 15-minute rounding).
- **Require operational validation:** G2 (validate if start batching is a UI artifact or physical reality), G3 (validate if end batching is just delayed form submission), G5 (validate the number of concurrent users in the shared account), G8 (validate clock sync and exact downtime duration before calculating queue times).
