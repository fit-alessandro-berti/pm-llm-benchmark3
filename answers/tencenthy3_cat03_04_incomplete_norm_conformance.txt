## 1. Conformance semantics

We classify an observation using the norm’s explicit status labels and the stated scope, moderated by the open-/closed-world stance.

- **Forbidden behavior** is any observed relation that matches a norm relation explicitly marked `forbidden` (N3, T6, E10). The norm is closed-world for forbidden relations: presence is a violation regardless of low frequency.
- **Missing mandatory behavior** occurs when a `mandatory` relation’s scope applies but the observed graph lacks the required edge or object binding for some instances (e.g., N1, N4, T1, T2, E2, E6, E8). Because the norm is closed-world only for mandatory columns inside scope, absence is prima facie nonconformance, but must be evaluated against scope and abstraction.
- **Unexpected but unregulated behavior** covers observed edges whose status is `unspecified` or simply absent from the norm (e.g., T4, T5, N6, E9). The norm is open-world here; such relations are not violations.
- **Typical-pattern absence** applies to `typical` relations (N2, N5, T3) where some instances lack the directly-follows or interaction edge. Legitimate exceptions are expected; severity is low unless patterns shift.
- **Likely data-quality error** is assigned when contextual evidence suggests misjoins, identifier reuse, or missing attributes rather than process breach (e.g., E10 Sensor Heartbeat–Invoice, possibly E6 missing Delivery).
- **Abstraction mismatch** occurs when a norm states an eventual state requirement (N1 “eventually enter validation”) but the model family records only directly-follows edges, producing apparent gaps.
- **Insufficient evidence** means graph counts alone cannot prove event-level causality, timestamps, or object identity.

Open-world assumptions protect unmodeled but legitimate behavior; closed-world assumptions force action on forbidden and in-scope mandatory gaps.

## 3. Detailed reasoning by model family

### OC-DFG
The OC-DFG family establishes directly-follows frequencies between activities for an object type. It can show that `Cancel Order  Dispatch Package` occurred for 2 Orders (N3 violation) and that `Pack  Dispatch` occurred for 198/200 packages (N4). It cannot establish state-based properties such as “eventually validated” because it only records adjacent activities. Counts matter: 98/100 for N1 is high, but the two missing edges may be an artifact of the directly-follows abstraction. N1 is mandatory but scoped as “eventually enter validation”; the summary approximates this with a directly-follows edge. Interpreting an “eventually expected” rule as a directly-follows rule creates false nonconformance, especially given the note that an unrecorded review event may sit between creation and validation. A relation can be conforming at the business-state level (Order eventually validated) yet suspicious at the DFG level (no direct edge). Conversely, `Validate  Issue Invoice` (72) is present but unregulated; it is not a deviation despite absence from N2. `Reopen  Close` (1) is explicitly N6 `unspecified` and must not be flagged.

### OTG
The OTG family establishes object interactions, co-birth, and co-death. It confirms mandatory T1 (Order–Item 1450) and T2 (Package–Delivery 200), and reveals forbidden T6 (Order–Payment cobirth 1). It cannot establish which event type produced the interaction; thus T2 appearing 200 times does not conflict with E6’s 198 at the event level—OTG may include interactions from confirmation events. Unspecified edges T4 (Customer 100) and T5 (RiskCase 3) are open-world permitted. The `object_codeath` edges (7) are unregulated; the norm says nothing about codeath, so they are benign. The danger is assuming OTG weight alone proves event-level mandatory compliance; only ET–OT can confirm per-event bindings.

### ET–OT
ET–OT binds event types to object types. It confirms most mandatory edges (E1, E3, E4, E5, E7) but exposes gaps: E2 Add ItemOrder 1448/1450, E6 DispatchDelivery 198/200, E8 Record PaymentInvoice 92/93. These are mandatory in scope; absence must be discussed, not dismissed. However, E8 allows unapplied cash if explicitly typed; the one missing Invoice link is not labeled, so it sits between violation and legitimate exception. Forbidden E10 appears once, but context strongly suggests data error. Unspecified E9 (RiskCase 3) and unlisted Manual Compliance ReviewCustomer 3 are not violations. A relation can be conforming at OTG (Package–Delivery 200) yet suspicious at ET–OT (Dispatch event lacking Delivery), illustrating abstraction-level divergence.

## 6. Norm-completeness assessment

1. **N1 eventually vs directly-follows** – Risk: false violations from DFG strictness. Clarify as state-reachability mandatory with allowed intermediate events; keep `mandatory`.
2. **N4 scope “externally shipped”** – Risk: internal packages falsely breach. Clarify with object attribute `ship_external`; mandatory only if true, else `unspecified`.
3. **E8 unapplied-cash exception unlabeled** – Risk: legitimate payments flagged. Clarify: `typical` if event typed “Unapplied Cash”; otherwise `mandatory` Invoice link required.
4. **T6 Order–Payment cobirth forbidden** – Risk: rejects valid prepayment-at-order channels. Clarify: `forbidden` for standard sales, `unspecified` for cash-on-create retail.
5. **No norm on object_codeath** – Risk: lifecycle termination inconsistencies invisible. Clarify explicitly `unspecified` to avoid silent assumptions.
6. **N2 typical lacks intermediate model** – Risk: incomplete compliance view of fulfilment. Clarify `typical` with explicit allowed intermediates (Invoice, Dispatch).
7. **No frequency tolerance** – Risk: rare counts over-escalated. Clarify `unspecified` statistical bands; severity should scale with volume.
