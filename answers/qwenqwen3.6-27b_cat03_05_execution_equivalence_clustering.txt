## 1. Equivalence design space

### 1. Activity-sequence equivalence ($E_{seq}$)
- **Definition:** Two executions are equivalent if the sequence of activity labels is identical. Object identifiers, types, O2O relations, and event timestamps are ignored.
- **Invariants preserved:** Activity labels, their relative order, and repetition counts.
- **Information discarded:** Object topology, external sharing, qualifiers, payment/invoice multiplicities, exact timing.
- **Properties:** Reflexive, symmetric, transitive.
- **Concurrency handling:** Events sharing a timestamp are treated as an unordered multiset; the sequence is defined over these multisets. If timestamps are absent, a total order is assumed from the input list.

### 2. Typed structural equivalence under identifier renaming ($E_{struct}$)
- **Definition:** Two executions are equivalent if their event-object incidence graphs are isomorphic under a bijection that preserves activity labels, object types, O2O relations, and causal dependencies. Local identifiers are renamed to canonical placeholders.
- **Invariants preserved:** Graph topology, object types, multiplicities, activity labels, O2O edges, and partial order of events.
- **Information discarded:** Specific identifier values, absolute timestamps, and non-structural metadata.
- **Properties:** Reflexive, symmetric, transitive (graph isomorphism is an equivalence relation).
- **Concurrency handling:** Modeled as a partial order. Isomorphism must preserve reachability; simultaneous events are unordered in the signature but must map to simultaneous events in the other execution.

### 3. Business-semantic equivalence ($E_{sem}$)
- **Definition:** Two executions are equivalent if they share the same lifecycle motif, defined by: (a) packaging strategy (single vs. split), (b) delivery consolidation, (c) financial settlement pattern (single vs. partial, isolated vs. shared), (d) presence of reverse logistics or substitutions, and (e) cross-order external sharing in logistics or finance.
- **Invariants preserved:** Object multiplicities per lifecycle phase, external-object flags, O2O qualifiers (e.g., `removed_before_dispatch`), payment/invoice counts, and high-level causal motifs.
- **Information discarded:** Exact event ordering within non-causal steps, specific IDs, and minor structural variations that do not alter business outcome.
- **Properties:** Reflexive, symmetric, transitive by construction (defined via a mapping to a finite feature space).
- **Concurrency handling:** Irrelevant for motif extraction; only causal dependencies that affect outcomes (e.g., return before repack) are preserved. Simultaneous independent steps are collapsed.

## 2. Canonical signatures

The preferred relation is $E_{sem}$. The signature maps an execution to a hashable tuple invariant to identifier renaming.

```python
def compute_semantic_signature(ocel_trace):
    """
    ocel_trace: list of dicts with keys 'activity', 'objects': {type: [ids]}, 
                and optional 'qualifiers': set
    Returns: tuple representing business-semantic motif
    """
    acts = [e['activity'] for e in ocel_trace]
    pkg_count = acts.count('Pack Package')
    del_count = acts.count('Dispatch')
    inv_count = acts.count('Issue Invoice')
    pay_count = acts.count('Record Payment')
    
    has_return = any(a in ('Return Item', 'Inspect Return') for a in acts)
    has_replace = any('removed_before_dispatch' in e.get('qualifiers', set()) 
                      for e in ocel_trace if e['activity'] == 'Dispatch')
    
    ext_logistics = False
    ext_finance = False
    for e in ocel_trace:
        if e['activity'] in ('Pack Package', 'Dispatch'):
            if any('EXT' in str(obj) for objs in e['objects'].values() for obj in objs):
                ext_logistics = True
        if e['activity'] in ('Issue Invoice', 'Record Payment'):
            if any('EXT' in str(obj) for objs in e['objects'].values() for obj in objs):
                ext_finance = True
                
    partial_payment = pay_count > 1  # Assumes count > 1 implies partial settlement
    
    return (
        tuple(sorted(acts)),           # activity multiset (order-invariant for motif)
        pkg_count, del_count, inv_count, pay_count,
        has_return, has_replace,
        ext_logistics, ext_finance, partial_payment
    )
```
This signature discards exact ordering but preserves multiplicities, external flags, qualifiers, and repetition. It is stable under local ID renaming and directly supports $E_{sem}$ clustering.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py's `cluster_equivalent_ocel` groups executions that share an identical key structure: exact activity labels, exact object identifiers, exact O2O relations, and exact event ordering. It preserves the full incidence graph without abstraction.

Raw object identifiers make clusters too fine because auto-incrementing IDs or system-generated UUIDs create artificial distinctions between identical business cases. This prevents generalization and inflates cluster counts.

To canonicalize, one must strip IDs, replace them with type-indexed placeholders, sort object lists, and hash the resulting structure. Post-processing should merge clusters that differ only by ID permutation.

Exact equivalence is preferable for forensic auditing, physical item tracing, or compliance checks where every identifier matters. Business clustering is better for process mining, resource planning, and pattern discovery.

`max_objs` limits the number of objects considered per execution. Large connected executions may be truncated, breaking structural equivalence and causing false splits. Practical use requires balancing completeness with computational feasibility.

```python
import pm4py
from collections import defaultdict

def canonicalize_ocel(ocel):
    """Replace local IDs with canonical placeholders, preserve EXT flags."""
    id_map = {}
    counter = defaultdict(int)
    for case in ocel['cases']:
        for obj_type, obj_ids in case['objects'].items():
            for oid in obj_ids:
                if oid not in id_map:
                    if oid.startswith('EXT'):
                        id_map[oid] = oid  # preserve external IDs
                    else:
                        counter[obj_type] += 1
                        id_map[oid] = f"{obj_type}_{counter[obj_type]}"
```

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** X7 loses its replacement signal and merges into S_Baseline. The semantic partition loses granularity for substitution tracking. Useful for high-level volume reporting, harmful for quality control.
- **Ignore external objects:** X5 and X6 lose their cross-order flags, merging into S_Baseline. Clusters become purely intra-order. This simplifies analysis but hides collaboration/shared-resource patterns critical for network optimization.
- **Collapse repeated same-label events:** X4's two `Record Payment` events become one. The partial-payment motif disappears, merging X4 into X3/X1 structurally. Financial milestone tracking is lost; acceptable for activity-frequency analysis, unacceptable for billing reconciliation.
- **Treat Pack/Dispatch order as partial order:** X3, X4, and X8 become more similar if interleaving doesn't matter. Structural clusters coalesce into broader "multi-package" groups. Improves robustness to logging delays but obscures workflow sequencing (e.g., pack-then-dispatch vs. dispatch-then-repack).
- **Treat payment multiplicity as amount attribute:** If two payments are summed into one total, X4's financial motif aligns with X1. The cluster boundary shifts from structural to monetary. This is realistic for finance systems that net settlements, but breaks operational visibility into payment behavior.

## 8. Limitations and recommendation

No single equivalence notion serves all purposes because each optimizes for different trade-offs between precision, generalization, and domain relevance.

- **Compliance monitoring:** Use *Typed structural equivalence*. Exact graph isomorphism ensures no deviation in object routing or external sharing goes unnoticed. Qualifiers and IDs are preserved to audit liability and data lineage.
- **Operational segmentation:** Use *Business-semantic equivalence*. Grouping by lifecycle motifs (split packaging, cross-order sharing, returns) aligns with warehouse planning, shipping contracts, and resource allocation. It abstracts away noise while preserving decision-relevant patterns.
- **Root-cause analysis:** Use *Activity-sequence equivalence* augmented with qualifier tracking. Starting from identical activity flows allows isolating where deviations (e.g., missing dispatch, extra return) occur. Structural context is added only when tracing object-level failures.
- **Descriptive reporting:** Use a *coarse semantic aggregation* (e.g., forward vs. reverse, single vs. multi-package). High-level dashboards require stability and interpretability; fine-grained structural splits would overwhelm stakeholders with technical artifacts.

The tension arises because compliance demands exactness, operations demand generalization, debugging demands traceability, and reporting demands simplicity. A robust object-centric analytics pipeline should compute multiple equivalence levels in parallel, routing executions to the appropriate cluster granularity based on the downstream use case.
