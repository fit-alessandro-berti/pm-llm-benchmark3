## 1. Modeling assumptions

**Object types and capitalization.** I use exactly these object types: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`.

**E2O qualifier vocabulary.** The event-to-object qualifiers are role-like and activity-specific:

| Object type | E2O qualifiers used                                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `Order`     | `created_order`, `receiving_order`, `shared_order`, `fulfillment_order`, `fulfilled_order`, `delivered_order`, `billed_order`, `closed_order` |
| `Item`      | `added_item`, `reserved_item`, `packed_item`, `fulfilled_item`, `delivered_item`                                                              |
| `Package`   | `packed_package`, `dispatched_package`, `delivered_package`                                                                                   |
| `Delivery`  | `dispatch_delivery`, `confirmed_delivery`                                                                                                     |
| `Invoice`   | `issued_invoice`, `partially_settled_invoice`, `completely_settled_invoice`                                                                   |
| `Payment`   | `recorded_payment`                                                                                                                            |

**O2O direction conventions.** The first object in `ocel:oid` is the grammatically active/container/settling object, and `ocel:oid_2` is the target/contained/settled object: `Order contains Item`, `Package packs Item`, `Delivery carries Package`, `Invoice bills Order`, and `Payment partially_settles` or `completes_settlement` of `Invoice`. I do not insert reverse O2O rows.

**Direct downstream relations.** I use a moderately rich E2O model. Logistics events are related not only to the directly handled `Package` or `Delivery`, but also to the affected `Order` and `Item` objects when the package/order/item lineage is operationally relevant. Financial events are more conservative: `Issue Invoice` links to `Invoice` and both `Order` objects, while `Record Payment` links only to the `Payment` and `Invoice`, not directly to `Order` or `Item`, because the narrative does not allocate M1 or M2 across O100 and O200.

**Source facts versus analytical enrichment.** The `relations` table has an extra audit column, `relation_origin`, with values `source_stated` and `lineage_enriched`. The mandatory OCEL relation rows remain usable by PM4Py, while the audit column prevents a reviewer from confusing directly stated event-object participation with enrichment based on the known O2O lineage. I do not run automatic O2O propagation in the construction.

**PM4Py version assumption.** The code assumes that `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is available, as requested. That line is isolated because some older PM4Py `OCEL` constructor signatures shown in documentation accept `events`, `objects`, and `relations` but not an `o2o` keyword; in such versions, the adjustment should be limited to construction/attachment of `o2o`, not to the four DataFrames. PM4Py’s OCEL flattening treats the chosen object type as cases and returns the events related to those objects, so duplicated shared events after flattening are expected rather than data errors. ([PM4Py Documentation][1])

## 4. Expected flattened behavior

PM4Py flattening creates a traditional log using one selected object type as the case notion; each object of that type receives the events related to it. That means a single shared event can appear in several flattened cases, which is correct for object-centric data but dangerous if interpreted as event duplication in the source system. ([PM4Py Documentation][2])

Flattening on `Payment` is particularly weak here. The payment cases would be `M1: Record Payment` and `M2: Record Payment`, each with a single event. A DFG would have no meaningful directly-follows behavior, and the important fact—that `M1` and `M2` jointly settle `V1`—lives in O2O and the invoice-centered view rather than in payment-object lifecycles.

## 5. Expected object-centric structures

**OC-DFG.** The OC-DFG should reveal different directly-follows structures per object type instead of forcing one case notion. For `Order`, it should show order creation, item addition, shared reservation, logistics, invoicing, delivery confirmation, and closure. For `Package`, it should show `Pack Package→Dispatch Package→Confirm Delivery`. For `Invoice`, it should show `Issue Invoice→Record Payment→Record Payment`. The key insight is that `P1` creates cross-order logistics coupling between `O100` and `O200`, while `V1` creates financial coupling between the same two orders. PM4Py documents OC-DFG discovery as an object-centric directly-follows graph from an OCEL. ([PM4Py Documentation][3])

**OTG.** The object-type graph should show strong connections among `Order`, `Item`, `Package`, and `Delivery` in the logistics part, plus `Order–Invoice` and `Invoice–Payment` in the financial part. | Alternative policy                 | What changes in E2O                                                                                                                                                                                                                   | How discovery results change                                                                                                                                                                                                      | Business story unchanged?                                                                                          |

| **Source-minimal relations**       | Link events only to objects explicitly named in the event sentence. For example, `Dispatch Package P1 in Delivery D1` would link only `P1` and `D1`; `Confirm Delivery D1` might link only `D1`.                                      | Order flattening becomes much shorter and may omit dispatch/confirmation. Package and delivery views become cleaner but less connected. OC-DFG has fewer cross-type synchronizations.                                             | Yes. `P1` still packs `I1` and `I3`; the relationships are just in O2O rather than direct E2O.                     |
| **Full operational involvement**   | Link every downstream logistics and financial event to all causally affected `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and possibly `Payment` objects. However, payment events would be copied into both order cases, possibly suggesting both orders independently received both payments. | Yes, but the analysis becomes more interventionist and less faithful to source-system granularity.                 |
| **O2O-propagated analytical view** | Store a source-minimal `relations` table, then create a separate analytical relation table by traversing O2O links, such as `Payment→Invoice→Order` or `Delivery→Package→Item→Order`.                                                 | Discovery on raw relations is sparse and auditable; discovery on propagated relations is richer. Comparing both views shows how much behavior is due to observation versus analytical inference.                                  | Yes. This is often the cleanest governance option when source facts and analytical reachability must be separated. |
| **State-change-only E2O policy**   | Link an event only to objects whose lifecycle state changes. `Issue Invoice` changes `V1`, perhaps not `Order`; `Confirm Delivery` changes `Delivery`, perhaps not `Order` or `Item`.                                                 | Flattened traces become very short for context objects. ## 7. Failure modes

| Failure mode                                 | Why it matters here                                                                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Relation inflation**                       | If every event is linked to every reachable object, `O100`, `O200`, `P1`, `V1`, `M1`, and `M2` can become over-connected. Flattened frequencies then overstate how often work occurred per case. |
| **Missing direct E2O links**                 | If `E07` is not related to both `O100` and `O200`, the cross-order nature of `P1` becomes invisible in order flattening and weaker in object-centric discovery.                                  |
| **Treating O2O propagation as observation**  | A relation inferred from `Delivery→Package→Item→Order` is not the same as an event record explicitly containing the order ID. Mixing them without provenance damages auditability.               |
| **Duplicate shared events after flattening** | `E06`, `E07`, `E09`, `E11`, and `E13` can appear in both order cases. This is expected in flattening but wrong if counted as separate source executions.                                         |
| **Ambiguous payment allocation**             | `M1=100` and `M2=150` settle `V1`, which bills both orders. The dataset does not say how much of either payment belongs to `O100` or `O200`.                                                     |
| **Overly short Payment traces**              | `M1` and `M2` each have one event. Payment flattening gives almost no behavioral process model, even though payments are important financially.                                                  |
| **Constructor/API version mismatch**         | Some PM4Py versions may expose `OCEL` or `o2o` support differently. The constructor line should be adjusted without changing `events`, `objects`, `relations`, or `o2o`.                         |
| **False total order for same-time events**   | This example has no timestamp ties, but real OCELs often do. Sorting equal timestamps arbitrarily can create fake DFG edges.                                                                     |
| **Timezone-naive timestamps**                | Dropping UTC awareness can shift or misorder events when logs from different systems are merged.                                                                                                 |
| **Payment amount modeled as object**         | Modeling `100` or `150` as objects would violate the semantics: amounts are event attributes of `Record Payment`, not process objects.                                                           |
| **Wrong O2O direction**                      | Reversing `V1 bills O100` into `O100 bills V1` or `M1 partially_settles V1` into `V1 partially_settles M1` changes the business meaning of the graph.                                            |
| **Qualifier inconsistency**                  | Using both `settles_partial` and `partially_settled_invoice` for the same role would make filtering and auditing unnecessarily fragile.                                                          |
