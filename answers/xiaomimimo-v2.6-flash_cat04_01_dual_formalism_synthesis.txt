# 1. Assumptions and Interpretation

1. **Risk route as a control-flow choice, not a data condition.** The low-risk / high-risk decision is modelled as an exclusive choice (`XOR`) whose *entry* is ordered immediately after `Analyze Root Cause`. The low branch contains exactly `Supervisor Review`; the high branch contains exactly `Quality Review` **and** `Regulatory Review` composed as an unordered pair (concurrency, either completion order). No attribute named "risk" exists in either model, per requirement 11; the route is observable in a trace only through *which* review labels appear, and exactly one branch must be taken (the route cannot be empty).

2. **Supplier consultation as a silent optionality.** `Consult Supplier` is modelled as `XOR(, Consult Supplier)`, where `` is a silent (unobservable) leaf/`SilentTransition` representing "the case data did not select a supplier consultation". Because the leaf appears exactly once under exactly one `XOR`, "at most once" is enforced *structurally*, not by a data guard. `` never appears in a projected trace, so optional and non-selected cases are indistinguishable at the level of visible traces only by the presence/absence of `Consult Supplier`.

3. **"Passing inspection" is inferred structurally, not from a label.** Since `Inspect Trial` carries no outcome label, the model defines *the passing inspection* as **the last `Inspect Trial` of the repeat-until construct**, i.e. the one that is not followed by `Adjust Parameters`. The loop guarantees every `Inspect Trial` except the last is followed by `Adjust Parameters`, and `Release Material` is ordered *after the loop node*, hence after the passing inspection. Requirement 8 ("no `Adjust Parameters` after the passing inspection") is therefore satisfied by construction rather than by a data condition.

4. **Duplicate visible labels are permitted by the notation but are not used in either delivered model.** Each of the 14 labels occurs exactly once in the process-tree structure and exactly once in the POWL structure (repetition of `Execute Trial`, `Inspect Trial`, `Adjust Parameters` comes only from the loop, which is intended). I show in §3 that an *exact* process tree would require up to 12-fold duplication of whole submodels; that construction is rejected (see assumptions 5 and 8).

5. **Approximation policy for the process tree: conservative under-approximation.** The tree is guaranteed to generate only traces that the intended specification admits (`L(tree)  L(intended)`); some intended interleavings are dropped. Concretely, the approval route and `Consult Supplier` are placed *after* the join of both work products, so they may not complete before `Plan Verification` and `Design Corrective Action` are complete. Nothing unsafe is admitted.

6. **"May overlap" is interpreted as true concurrency**, i.e. as the *absence of an order constraint between completions*, not merely as "either may be finished by release time". Because activities are recorded at completion time (requirement 11), concurrency is observed as arbitrary interleaving of completion events subject to each activity's own predecessors. Every `` below means "no precedence edge exists".

7. **Trace model.** A trace is a finite linear order of *completion* events over the visible alphabet; `X  Y` in a trace means "`X` completed before `Y` completed". If `X` must complete before `Y` *starts* (requirement 3), then necessarily `X  Y` in every trace, so completion-level precedence is a sound (slightly coarser) formalisation of the start-level rules.

8. **POWL is the canonical model; the process tree is a derived rendering.** The POWL model is claimed to be *exact* (`L(powl) = L(intended)`); the process tree is explicitly *not*. The tree's loss is a deliberate, documented trade for a single-copy, duplicate-label-free, block-structured artifact.

9. **"Approval route complete"** means *all* activities of the selected branch have completed (`Supervisor Review`, or both `Quality Review` and `Regulatory Review`), not merely that the branch was entered.

10. **Loop convention.** `LOOP(body, redo)` is read as `body (redo body)*`: `body` executes at least once, and every `redo` is followed by another `body`. Under this convention the last activity of a loop instance is always the last activity of `body`. This convention is stated because the pm4Py child-order convention is version-dependent (see §8).

```
  par( seq( Contain Material , Plan Verification ),
       seq( Analyze Root Cause , Design Corrective Action ) ),
  par( xor( Supervisor Review ,
            par( Quality Review , Regulatory Review ) ),
       xor( tau , Consult Supplier ),
       loop( seq( Execute Trial , Inspect Trial ) ,
             Adjust Parameters ) ),
  Release Material ,
  Archive Case
)
```

Reading: segment 1 registers the case; segment 2 runs the two work streams concurrently
(`Contain  Plan` vs `Analyze  Design`) and joins them; segment 3 runs the approval
route, the optional supplier consultation and the repeat-until trial *concurrently* and
joins them; segment 4 releases; segment 5 archives.

## 3.2 Self-contained Python construction

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


# ---------- factories with explicit parent/child wiring ----------------------
def activity(label):
    """Visible activity leaf (a ProcessTree with an operator of None)."""
    return ProcessTree(label=label)


def silent():
    """tau: operator is None and label is None -> unobservable leaf."""
    return ProcessTree()


def node(operator, children, name=""):
    """Internal node; children are inserted AND their .parent is set."""
    n = ProcessTree(operator=operator, children=list(children), label=name)
    for child in n.children:
        child.parent = n
    return n


# ---------- visible activities ---------------------------------------------
reg   = activity("Register Deviation")
cont  = activity("Contain Material")
ana   = activity("Analyze Root Cause")
plan  = activity("Plan Verification")
des   = activity("Design Corrective Action")
sup   = activity("Supervisor Review")
qual  = activity("Quality Review")
regul = activity("Regulatory Review")
cons  = activity("Consult Supplier")
exex  = activity("Execute Trial")
insp  = activity("Inspect Trial")
adj   = activity("Adjust Parameters")
rel   = activity("Release Material")
arch  = activity("Archive Case")
tau   = silent()

# ---------- two independent work streams (requirement 2) --------------------
stream_plan   = node(Operator.SEQUENCE, [cont, plan])    # D05
stream_design = node(Operator.SEQUENCE, [ana,  des])     # D06
streams       = node(Operator.PARALLEL, [stream_plan, stream_design])  # D04, D10

# ---------- risk route (requirement 5) --------------------------------------
high_route = node(Operator.PARALLEL, [qual, regul])       # D09, concurrent
route      = node(Operator.XOR, [sup, high_route])        # D08

# ---------- optional supplier consultation (requirement 6) ------------------
supplier_opt = node(Operator.XOR, [tau, cons])            # D11, D12

# ---------- repeat-until trial (requirement 8) ------------------------------
# loop(body, redo) == body (redo body)*  -> last element of the loop is Inspect Trial
trial_body = node(Operator.SEQUENCE, [exex, insp])        # D18
trial      = node(Operator.LOOP, [trial_body, adj])       # D19, D20, D21

# ---------- release synchronisation (requirement 9) -------------------------
# PAR join forces route AND supplier-option AND trial to finish before Release Material
sync = node(Operator.PARALLEL, [route, supplier_opt, trial])   # D22, D23, D24

# ---------- whole case (requirements 1 and 10) ------------------------------
tree = node(Operator.SEQUENCE, [reg, streams, sync, rel, arch])
```

`tree` is now a `ProcessTree` whose root operator is `SEQUENCE` with five children; every
internal child has `child.parent` pointing at its parent, so the object graph is consistent
for conversion and visualisation.

## 3.3 What the tree cannot represent exactly

The tree is a **conservative under-approximation**: every trace it generates satisfies all
28 dependency rows of §2, but it drops intended interleavings. Specifically:

* **Requirement 5 loses its *timing*, not its *structure*.** `xor(Supervisor, par(Quality, Regulatory))`
  is exact as a choice and as a concurrency, but because it sits in the *third* sequence
  segment, no review may **complete** before the join of `par(seq(Contain, Plan), seq(Analyze, Design))`,
  i.e. before *both* `Plan Verification` and `Design Corrective Action` are finished. The
  specification only requires reviews to start after `Analyze Root Cause`.
* **Requirement 6 loses three of its four stated overlaps for `Consult Supplier`.** The
  supplier leaf is in the third segment, so it may overlap approvals (D17) and trial work
  (D16) but **may not** overlap `Design Corrective Action`, `Plan Verification` or
  `Contain Material` (D10/D16), and it may not complete before those work products exist.
* Everything else is exact: start/end (D01, D28), `Contain  Analyze` (D04), `Contain  Plan`
  (D05), `Analyze  Design` (D06), the risk choice and `Quality  Regulatory` (D08, D09),
  the cross-branch trial join (D13, D14), the approval–trial and supplier–trial overlaps
  (D15, D16), the repeat-until loop with no `Adjust Parameters` after the passing inspection
  (D18–D21), the three-way release synchronization (D22–D24) and `Release  Archive` (D27).
* **No behaviour outside the intended language is added** — that is the point of choosing
  under- rather than over-approximation.

**Why not exact?** An exact tree is *possible in principle but unreasonably complex.*
The approval route and `Consult Supplier` may lie on either side of the only cut a tree can
make — the cut between the work-product block `{Contain, Plan, Analyze, Design}` and the
trial block — and each must be placed independently:

* low risk: `Supervisor Review  {before, after}` (2) × `Consult Supplier  {before, after}` (2) = **4** variants;
* high risk: `Quality Review` and `Regulatory Review` each  {before, after} (4; the two may
  genuinely be split, e.g. `…, Analyze, Quality Review, Contain, Plan, Design, Execute Trial,
  Inspect, Regulatory Review, Release, Archive`) × `Consult Supplier` (2) = **8** variants.

That is **12 whole-model variants** under a top-level `XOR`,  135 visible leaves and  95
internal nodes, with every label duplicated up to 12 times. Although `L(exact-tree) =
L(intended)` would hold, the duplication destroys analytability (ambiguous alignments,
biased directly-follows statistics, "at most once" no longer checkable structurally — see §6,
row 8). I therefore reject it and keep a single-copy tree with a documented, witnessed loss
(trace **A5** below).

# 4. PM4Py POWL Model

## 4.1 Compact POWL description

```
powl = StrictPartialOrder { nodes:
    Register Deviation, Contain Material, Analyze Root Cause, Plan Verification,
    Design Corrective Action, route, supplier, trial,
    Release Material, Archive Case }

route    = OperatorPOWL( XOR , [ Supervisor Review ,
                                 StrictPartialOrder{ Quality Review || Regulatory Review } ] )
           -- the inner StrictPartialOrder has NO edge: Quality and Regulatory are concurrent,
               so either completion order is admitted (D09).

supplier = OperatorPOWL( XOR , [ SilentTransition() , Consult Supplier ] )
           -- tau = "case data did not select a supplier consultation" (D12).

trial    = OperatorPOWL( LOOP , [ StrictPartialOrder{ Execute Trial -> Inspect Trial } ,
                                  Adjust Parameters ] )
           -- LOOP(body, redo) == body (redo body)*: Adjust Parameters is always followed by
               another Execute Trial, hence never after the passing inspection (D21),
               and the loop node completes at the passing Inspect Trial (D22).

edges (.order.add_edge):
    Register Deviation          -> Contain Material
    Register Deviation          -> Analyze Root Cause
    Contain Material            -> Plan Verification
    Analyze Root Cause          -> Design Corrective Action
    Analyze Root Cause          -> route
    Analyze Root Cause          -> supplier
    Plan Verification           -> trial          \  cross-branch join: the trial
    Design Corrective Action    -> trial          /  waits for BOTH work products (D13, D14)
    trial                       -> Release Material   \  three-way release
    route                       -> Release Material   |  synchronisation (D22-D24)
    supplier                    -> Release Material   /
    Release Material            -> Archive Case
    (+ Register Deviation -> * and * -> Archive Case made explicit)
    -- deliberately ABSENT: route->trial, supplier->trial, route<->supplier,
       Contain/Plan <-> Analyze/Design/route/supplier  (D04, D10, D15, D16, D17)
```

## 4.2 Self-contained Python construction

```python
from pm4py.objects.process_tree.obj import Operator          # XOR / LOOP enum
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# ---------- visible transitions --------------------------------------------
t_reg   = Transition("Register Deviation")
t_cont  = Transition("Contain Material")
t_ana   = Transition("Analyze Root Cause")
t_plan  = Transition("Plan Verification")
t_des   = Transition("Design Corrective Action")
t_sup   = Transition("Supervisor Review")
t_qual  = Transition("Quality Review")
t_regul = Transition("Regulatory Review")
t_cons  = Transition("Consult Supplier")
t_exex  = Transition("Execute Trial")
t_insp  = Transition("Inspect Trial")
t_adj   = Transition("Adjust Parameters")
t_rel   = Transition("Release Material")
t_arch  = Transition("Archive Case")

# ---------- high-risk route: Quality and Regulatory concurrent ---------------
high_route = StrictPartialOrder(nodes=[t_qual, t_regul])   # NO edge on purpose (D09)

# ---------- risk route: exactly one branch (D08) -----------------------------
route = OperatorPOWL(Operator.XOR, [t_sup, high_route])

# ---------- optional supplier consultation (D11, D12) -----------------------
supplier = OperatorPOWL(Operator.XOR, [SilentTransition(), t_cons])

# ---------- repeat-until trial (D18-D21) ------------------------------------
trial_body = StrictPartialOrder(nodes=[t_exex, t_insp])
trial_body.order.add_edge(t_exex, t_insp)                  # D18
trial = OperatorPOWL(Operator.LOOP, [trial_body, t_adj])   # D19, D20, D21

# ---------- root partial order ----------------------------------------------
root_nodes = [t_reg, t_cont, t_ana, t_plan, t_des,
              route, supplier, trial, t_rel, t_arch]
root = StrictPartialOrder(nodes=root_nodes)

# start rule (D01, D02, D03) and end rule (D27, D28) made explicit
middle = [t_cont, t_ana, t_plan, t_des, route, supplier, trial, t_rel]
for source_node, target_node in [(t_reg, n) for n in middle] + \
                               [(n, t_arch) for n in middle]:
    root.order.add_edge(source_node, target_node)
root.order.add_edge(t_reg, t_arch)

# stream 1: Contain -> Plan (D05)
root.order.add_edge(t_cont, t_plan)

# stream 2: Analyze -> Design (D06)
root.order.add_edge(t_ana, t_des)

# approvals and supplier consultation depend on analysis only (D07, D11)
root.order.add_edge(t_ana, route)
root.order.add_edge(t_ana, supplier)

# cross-branch join: the trial waits for BOTH work products (D13, D14)
root.order.add_edge(t_plan, trial)
root.order.add_edge(t_des, trial)

# three-way release synchronisation (D22, D23, D24)
root.order.add_edge(trial, t_rel)
root.order.add_edge(route, t_rel)
root.order.add_edge(supplier, t_rel)

# end rule (D27)
root.order.add_edge(t_rel, t_arch)

powl = root
```

The remaining pairs (`t_reg  t_plan`, `t_cont  trial`, `t_ana  t_rel`, …) are implied by
transitive closure of the edges above; `StrictPartialOrder` treats `order` as a transitively
closed DAG, so no separate edge is required for them.

## 4.3 Why every intentionally unconnected pair may remain concurrent

At root level there are 10 nodes (45 pairs). 13 pairs are deliberately left unordered, plus
1 inside `high_route`; all other pairs are ordered either directly or transitively.

| Unconnected pair | Why it may stay concurrent |
|---|---|
| `Contain Material`  `Analyze Root Cause` | D04 / Req. 2: the two streams must overlap. |
| `Contain Material`  `Design Corrective Action` | Design depends on `Analyze` only (D06), containment is on the other stream. |
| `Contain Material`  `route` | Reviews depend on `Analyze` only (D07). |
| `Contain Material`  `supplier` | Supplier consultation depends on `Analyze` only (D11). |
| `Plan Verification`  `Analyze Root Cause` | Planning depends on containment only (D05). |
| `Plan Verification`  `Design Corrective Action` | The two work products are independent (D10). |
| `Plan Verification`  `route` | Planning must precede the *trial*, not the reviews (D15 is absent by design). |
| `Plan Verification`  `supplier` | Req. 6 lets supplier work overlap verification planning. |
| `Design Corrective Action`  `route` | Req. 7: approval need not be complete before the trial; design and approval are independent obligations. |
| `Design Corrective Action`  `supplier` | Req. 6: supplier consultation may overlap corrective-action design. |
| `route`  `supplier` | Req. 6: supplier consultation may overlap approvals. |
| **`route`  `trial`** | **Req. 7: the approval route may overlap the trial cycle — the load-bearing non-block-structured edge that must NOT be added.** |
| `supplier`  `trial` | Req. 6: supplier consultation may overlap trial work. |
| `Quality Review`  `Regulatory Review` (inside `high_route`) | Req. 5: concurrent, either completion order. |

Every other pair is connected: `Register Deviation` precedes everything, `Archive Case`
follows everything, `Contain  Plan  trial  Release`, `Analyze  {Design, route, supplier}
 (trial/Release)`, and `route / supplier / trial  Release  Archive`.

# 7. Preferred Representation and Validation Plan

## 7.1 Canonical representation: the POWL model

I designate **`powl`** as canonical, for three reasons:

1. **Fidelity.** It is the only delivered model claimed (and argued, edge by edge in §4.3) to
   satisfy `L(powl) = L(intended)`. The cross-branch dependencies — trial gated by *both*
   work products, release gated by *three* independently progressing obligations, and the
   deliberately absent `routetrial` edge — are expressed directly as partial-order edges
   instead of being simulated by block structure.
2. **Explicitness of what is *not* ordered.** In POWL, concurrency is the absence of an edge,
   so the load-bearing freedoms (D04, D10, D15, D16, D17, D09) are visible in the source.
   In a process tree they are visible only as an absence of a `seq`, which is easy to
   misread and impossible to audit against §2.
3. **Loss transparency.** The process tree is retained as a *rendering for stakeholders who
   need block structure* (e.g. BPMN export), explicitly tagged as a conservative
   under-approximation with a named witness (A5).

Construction success is treated as **evidence to inspect, not proof**: the code below is a
checklist, and its outputs are meant to be read, not merely to run without exception.

## 7.2 Validation plan

**(a) Conversion to accepting Petri nets.**

```python
import pm4py

net_p, im_p, fm_p = pm4py.convert_to_petri_net(powl)   # canonical model
net_t, im_t, fm_t = pm4py.convert_to_petri_net(tree)    # approximate rendering

# also convert the compact expression route, to compare artefacts:
# net_e, im_e, fm_e = pm4py.convert_to_petri_net(tree)
```

Inspect the produced nets: count visible transitions (expect 14 per net, no duplicates),
confirm `Adjust Parameters` has exactly one input place shared with the loop's output place,
and confirm the release place has three distinct input arcs (the three-way join).

**(b) Soundness checking.**

```python
pm4py.check_soundness(net_p, im_p, fm_p, print_diagnostics=True)
pm4py.check_soundness(net_t, im_t, fm_t, print_diagnostics=True)
```

Expect *sound* (proper completion, no dead transitions, no dead markings) for both. **A sound
net proves only that every reachable state can terminate; it says nothing about business
fidelity.** Treat a "sound" result as permission to continue, not as validation.

**(c) Boundedness and sampled playout.**

* Check place boundedness (place invariants / coverability) — the loop must not accumulate
  tokens, i.e. the net should be 1-safe or at least bounded; an unbounded result signals a
  mis-wired loop join.
* Sample: `pm4py.play_out(powl, ...)` and `pm4py.play_out(tree, ...)` with a large sample
  (parameter names vary by pm4Py version; fall back to `pm4py.play_out(net_p, im_p, fm_p)`).
* **Subset evidence:** every trace sampled from `tree` must obtain alignment fitness `1.0`
  against `net_p`. This is the empirical counterpart of the claimed `L(tree)  L(powl)`;
  it is evidence, not proof, because sampling cannot be exhaustive over an unbounded loop.

**(d) Explicit positive and negative trace tests.**

```python
log = <the eight witnesses of §5 as an EventLog, tagged positive/negative>

fit_p = pm4py.fitness_alignments(log, net_p, im_p, fm_p)
fit_t = pm4py.fitness_alignments(log, net_t, im_t, fm_t)
```

Expected outcomes, read per trace rather than only as a log average:

| Set | `net_p` (POWL) | `net_t` (tree) |
|---|---|---|
| A1–A4 | `log_fitness == 1.0` | `log_fitness == 1.0` |
| **A5** | `log_fitness == 1.0` | **`< 1.0`**  this row is the deliberate, expected divergence |
| F1–F3 | `< 1.0` | `< 1.0` |

Also run `pm4py.conformance_diagnostics_alignments(trace, net, im, fm)` on F1–F3 and confirm
the sync/move costs localise at the activity named in the "earliest violated condition" column
of §5 (`Execute Trial` for F1, `Release Material` for F2, `Adjust Parameters` for F3). A
fitness value below 1.0 *without* localisation at the expected activity means the net is
violating a *different* constraint than the one we think we are testing.

**(e) Checks aimed specifically at silent behaviour and duplicated labels.**

* **Static duplicate-label check.** Walk the tree leaves and the POWL transitions and assert
  `Counter(labels) == 1` for all 14 labels; assert exactly one node with `label is None`.
* **Dynamic "at most once" check.** Over all sampled traces: `count("Consult Supplier")  {0,1}`;
  `count("Register Deviation") == count("Archive Case") == 1`.
* **Silent-transition isolation (language projection).** Build two sibling models from `powl`
