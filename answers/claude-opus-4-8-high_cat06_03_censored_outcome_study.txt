Uncertainty-Aware Predictive Process Monitoring for 90-Day Default Early Warning

Framing note. The lender's phrasing — "predict 90-day default from the first few events of every application" — hides a deep identification problem. Default within 90 days after Account Activated is only *defined* for accounts that are activated. Rejected, withdrawn, transferred, and still-open applications were never exposed to credit, so they have no observed 90-day default outcome; labeling them "non-default" is not conservative, it is a fabricated label that corrupts both the numerator and denominator of any risk estimate. Activation is itself an outcome of the credit process and is correlated with risk, so the 21,600 labeled rows are a *selected* subpopulation, not a random sample of applications. The design below therefore separates (a) what is directly estimable from the observed policy, (b) what requires selection-correction assumptions, and (c) what requires explicit counterfactual assumptions, and it keeps an as-of, no-peeking-into-the-future discipline throughout.


## 1. Target definition

Primary target (operationally defensible, minimal assumptions).
- Estimand: P(default within 90 days after Account Activated | prefix features known at prediction time, application is eventually activated under the prevailing credit policy).
- Unit of analysis: one credit application (one case), not one event.
- Population: applications that are activated and whose 90-day horizon plus the delayed outcome feed have matured on or before the as-of cutoff. This is an *activation-conditional* target: it predicts default risk among applications that the current policy would activate.
- Prediction time: a fixed, causally-clean decision point defined per case as the timestamp of the k-th event or the elapsed-time cutoff (see §4), which must be at or before Credit Review's final decision. No event at or after Accept / Contract Signed / Account Activated may contribute features. The default operating point is "prefix up to and including Credit Review, before the accept/reject decision is emitted."
- Horizon: 90 days after Account Activated; a label is "mature" only when time:timestamp of activation + 90 days + the delayed-feed allowance (up to 35 days) <= as-of cutoff.
- Positive label: default_90d = 1 (default observed within 90 days). Negative label: activated, matured, and no default. Everything else is *not* a negative — it is censored, competing, or undefined (see §2–§3).
- Why defensible: it conditions on exactly the population for which the outcome is observed and well-defined, so the target has honest semantics ("of the applications we would activate, which default early?"). It is directly useful as an early-warning score to gate or price accepted applications. Its known limitation — it does not generalize to rejected/withdrawn populations — is stated openly rather than hidden by mislabeling.

Credible alternative target (answers a different question).
- Multi-state / competing-outcomes target for *all* applications: from the prediction prefix, model the joint distribution over terminal states {Activated-and-default, Activated-and-no-default, Rejected, Withdrawn, Transferred, Still-open/administratively-censored}. This answers "what is the probable trajectory of any application?" rather than "will an activated account default?" It does not require pretending non-activated cases are non-defaults, because default is only one branch inside the Activated arm. It is the honest way to use all 48,000 cases, at the cost of a more complex label space and no single "default probability" for a rejected case.
- A further alternative, explicitly stronger: a *policy-specific counterfactual* target P(would default if activated) for every application, including rejected ones. This requires an activation/ignorability assumption (that, conditional on observed pre-decision features, activation is as-good-as-random) which is not testable from these data and is almost certainly violated because officers use unrecorded judgment. It is listed as a stretch target requiring sensitivity analysis, never as the primary estimand.

A time-to-default-after-activation formulation with right censoring (survival) is the natural refinement of the primary target when we want the 3,600 not-yet-matured activated accounts to contribute partial information (§3).


## 2. Cohort construction

As-of rule. Freeze everything to a configurable as_of_cutoff (default = data_extract_time = 15 Feb 2026). A case's label is usable only if label_available_at <= as_of_cutoff. Features use only events with time:timestamp <= the case's prediction time. Cohort membership (activated? terminal state? mature?) is evaluated as of the cutoff, so re-running with an earlier cutoff reproduces the information state at that date (needed for backtesting).

Inclusion (primary activation-conditional target). Case is included as *labeled* iff: (i) an Account Activated event exists with timestamp <= cutoff; (ii) activation_time + 90d + feed_allowance <= cutoff so the label is matured; (iii) the case has a valid pre-decision prefix of the required length/time. All other cases are retained in the master frame but assigned a status other than labeled.

Exclusion / status assignment. No case is deleted; each of the 48,000 is tagged. Partner-originated activated accounts flagged permanently-missing-feed are excluded from the labeled set (they cannot be scored honestly) but kept for missingness analysis. Duplicate events from the Oct-2025 migration are de-duplicated before status is computed.

Cohort-flow table (accounts for all 48,000).

| Bucket | N | Status in study | Role |
| --- | --- | --- | --- |
| Applications started | 48,000 | master frame | denominator |
| Activated, matured, no default | 18,900 | Labeled negative | primary training/eval |
| Activated, matured, default | 2,700 | Labeled positive | primary training/eval |
| Activated, not yet matured (feed/horizon pending) | 3,600 | Right-censored (survival) / excluded from binary | partial info in survival arm |
| Rejected | 9,100 | Competing outcome — outcome undefined under activation | NOT labeled non-default; used in multi-state / selection model |
| Withdrawn | 5,700 | Competing outcome (applicant-driven) | NOT labeled; selection model |
| Transferred | 2,900 | Competing event + missing follow-up (linkage ~60%) | NOT labeled; ~1,740 linkable for outcome recovery, ~1,160 unrecoverable |
| Still open at cutoff | 5,100 | Administratively right-censored | multi-state; may mature at later cutoff |
| Total | 48,000 | — | reconciles |

Reconciliation: 18,900 + 2,700 + 3,600 + 9,100 + 5,700 + 2,900 + 5,100 = 48,000. The current ML export (21,600 = 18,900 + 2,700) is only 45% of applications and 88% of *activated-matured* accounts; the base default rate within the labeled set is 2,700 / 21,600 = 12.5%, but this rate is not the application-level default rate and must never be reported as such.


## 3. Censoring and missing-label strategy

Mechanisms, kept distinct.
- Ordinary right censoring: 5,100 still-open and 3,600 not-yet-matured cases. The event simply has not happened / matured by the cutoff. Assumed non-informative *given covariates and calendar time* — partially testable by checking whether censoring times are independent of risk features within strata.
- Delayed labels: the outcome feed arrives 7–35 days after the 90-day horizon. A case can be activated and past 90 days yet still unlabeled. Handled by the feed_allowance in maturity and by a delayed-label survival treatment; testable by inspecting the empirical label_available_at − (activation+90d) distribution.
- Selection through activation: only activated cases have a default outcome. Activation is decided by the same officers/policy using pre-decision signals, so the labeled set is a risk-selected sample. This is the central issue. It is *not* fully testable from these data (the missing outcomes for rejected cases are the exact quantity we cannot see); it is only addressable under explicit assumptions.
- Transfer as competing event / missing follow-up: transfer removes a case from our observation. For ~60% with linkage we can attempt to recover the downstream outcome; for the remaining ~40% follow-up is missing not-at-random (partner-originated cases have elevated permanent-missing probability). Treat transfer primarily as a competing event; the linkage-recovered subset supports a sensitivity analysis only.
- Permanently missing outcome feeds: partner-originated activated accounts whose feed never arrives. These are missing-not-at-random and cannot be imputed reliably; they are excluded from the labeled set and reported as a coverage gap, with their share broken out by source_system.

Primary analysis. Fit the activation-conditional binary/survival model on the labeled matured activated cases, with the honest scope "risk among activated accounts." Use a discrete-time or Cox survival model for time-to-default-after-activation with right censoring so that the 3,600 not-yet-matured activated cases contribute censored information (they add follow-up up to their observed time without being forced to 0). Report the estimand as activation-conditional; do not extrapolate to rejected/withdrawn populations.

Sensitivity analyses.
1. Selection correction: a two-stage / inverse-probability-of-activation reweighting (or Heckman-style selection model) using only pre-decision prefix features to model the activation propensity, to probe how much the activation-conditional risk could differ from an application-level counterfactual. Report as a bound / stress test, explicitly assumption-dependent (ignorability of activation given observed pre-decision covariates — fundamentally untestable here).
2. Transfer-recovery: refit including the ~60% linkable transfers with recovered outcomes, and compare, to gauge transfer-induced bias direction.
3. Policy-split refit: fit separately pre- and post-1-Jul-2025 (see §7) to see whether the prefix→outcome relationship is stable.
4. Missing-feed bounds: Manski-style worst/best-case bounds over the permanently-missing partner accounts to show how wide the uncertainty is when MNAR cannot be corrected.

Testability summary. Non-informative censoring given covariates: partially testable. Delayed-label distribution: testable. Activation ignorability and MNAR missing feeds: fundamentally untestable from these data — hence bounds and sensitivity rather than point claims.


## 4. Prefix extraction

Principle: a prefix contains only events with time:timestamp <= prediction_time, and prediction_time is strictly before the Accept/Reject decision emission. Nothing at/after the decision (final_limit population, decision_reason, Contract Signed, Account Activated, Collections, Default Recorded) may enter a prefix.

Fixed event-count prefixes. Generate prefixes of length k (e.g., k = 3 covering Application Started → KYC → Credit Review) using pm4py.get_prefixes_from_log with case-sorted, timestamp-ordered events. Because the document-request loop repeats Credit Review, also define k relative to the *first* Credit Review rather than the last, and cap prefixes so they never cross the decision event.

Elapsed-time prefixes. Alternatively cut at case_start + Δ (e.g., Δ = 5 days) to reflect "first few days" decisioning; use whichever events fall in [start, start+Δ]. Report both because event-count and time-count prefixes have different leakage and coverage profiles.

Short cases. Cases that reach a terminal decision in fewer than k events (fast rejects/withdrawals) have truncated prefixes; keep them with an is_short flag and pad with explicit "not-yet-occurred" indicators rather than imputed values. They are informative about the process, not to be dropped silently.

Repeated document loops. Count Credit Review revisits and document-request cycles as rework features (§5) but ensure the prefix cut is placed *before* the decision even when many loops occur; the loop count up to the cut is a legitimate feature, later loops are not.

Activity renaming (Oct-2025 migration). Apply a canonical activity map so pre- and post-migration names collapse to one label before prefix extraction, and drop migration-created duplicate events (same case, activity, timestamp within tolerance) so loop counts and prefix lengths are not inflated.


## 5. Process-aware features (all evaluated as of prediction time)

Static case attributes (known at start): case:channel, case:region, case:requested_amount, source_system. Available from Application Started.

Prefix-derived control-flow features: sequence/variant of the prefix (via pm4py.get_variants on the prefix log), number of Credit Review revisits, number of document-request cycles, whether KYC completed, prefix length, presence of specific early activities. Only from events at/before the cut.

Timing features: elapsed time start→KYC, KYC→Credit Review, inter-event gaps, time-of-day/day-of-week of first events, total elapsed at cut. Derivable with pm4py.extract_temporal_features_dataframe and pm4py.insert_case_service_waiting_time — but only over the truncated prefix log, never the full case, so waiting/service times cannot embed post-decision durations.

Resource / queue features: identity of officers on the prefix (org:resource), officer workload/queue length at event time computed from concurrent open cases, hand-off count. Resource experience must be reconstructed as-of the event time, not extraction time (see leakage audit) or dropped.

Rework features: loop counts, repeated-activity ratio, number of returns to Credit Review — all truncated at the cut.

Cohort / calendar features: application start month, pre/post-1-Jul-2025 policy regime flag, pre/post-15-Oct-2025 migration flag. These are known at start and are essential covariates for shift handling.

Historical reference features (require external reference data, computed with strict as-of windows): region/channel base rates, officer historical decision mix — all computed from data strictly *before* the case's prediction time to avoid look-ahead. risk_score is usable only at its value as of the cut (the earliest pre-decision update), never the final updated value.


## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
| --- | --- | --- | --- | --- |
| final_limit | Populated only after final credit decision; encodes the accept decision and terms → target leakage and selection leakage | Only if a value exists before prediction_time (it never does) | Drop | It is a post-decision field; its presence itself signals activation. |
| decision_reason | Populated at/after Accept/Reject; directly encodes the decision outcome | Available only at/after decision, which is after the cut | Drop for prefix model | Using it is circular — it is (part of) the label of the decision step. |
| collection_status | Updated after activation; can directly reveal default | Never available at prediction time | Drop | This is essentially the outcome; classic target leakage. |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | Occur after prediction point; some are the outcome itself | Exclude all events with timestamp > prediction_time | Drop from features | Prefix discipline; these define the label, not inputs. |
| documents_total (nightly snapshot) | Same-calendar-day snapshot may include documents uploaded *after* the nominal prediction time | Use only a point-in-time count of documents with upload timestamp <= prediction_time | Repair (recompute from event-level upload times, not the nightly rollup) | The daily aggregate silently leaks intra-day future uploads. |
| risk_score (updated at several events) | Later updates may reflect post-decision or near-decision information | Use only the value from events with timestamp <= prediction_time (typically the first/earliest pre-decision value) | Repair (take as-of value; version the score) | Updated scores can encode the decision or post-activation signals. |
| Resource experience | Stored as experience at extraction time, not event time → future information about the officer | Recompute experience as of each event's timestamp from tenure/history | Repair, else Drop | Extraction-time experience leaks the future and biases toward extraction date. |
| Label availability (default_90d / label_available_at) | default_90d repeated on events including post-outcome events; label_available_at is a maturity field | Use default_90d only as the target; never as a feature; gate on label_available_at <= cutoff | Keep as target only | Repeating the label on events is direct leakage if treated as input. |
| Activity names (post-15-Oct-2025) | Renaming + duplicate events distort control-flow/loop features | Canonicalize names and de-duplicate before feature build | Repair | Prevents spurious variant/rework signal tied to migration date. |
| Transferred-case linkage / recovered outcome | Recovered outcomes exist only for ~60%, MNAR | Use only in labeled sensitivity arm, never silently merged | Keep (sensitivity only) | Avoids biased outcome recovery contaminating primary. |


## 7. Validation design

Temporal, as-of backtesting — not a random split.
- Split by case start time, not randomly. E.g., train on applications started in H1-2024..Q1-2025, validate on ~Q2-Q3-2025, test on later starts, each scored only with information available as of a rolling cutoff. A random case split leaks calendar/policy/migration information across folds and lets the model borrow future-regime signal, producing optimistic, non-deployable estimates.
- Policy change (1-Jul-2025): treat as a regime boundary. Report performance separately pre/post and use a policy-flag covariate; prefer a test period entirely in one regime, plus a cross-regime test to measure transfer. The same prefix has different selection and outcome relationships across the boundary, so pooled metrics can mislead.
- System migration (15-Oct-2025): after canonicalizing names, verify that variant distributions are comparable across the boundary; report a migration-robustness check.
- Label maturity: only score cases whose labels are mature as of each fold's cutoff; a case that is unlabeled at the validation cutoff must not be borrowed from a later extract. This enforces a realistic "information available then" evaluation.
- Calibration: because the operating decision is a probability threshold, report calibration (reliability curves, ECE) and recalibrate per regime; a discriminating-but-miscalibrated score is dangerous for lending.
- Subgroup performance: report metrics by case:channel, case:region, source_system (esp. partner vs. own origination given missing-feed bias), and pre/post-policy. Watch for partner-originated coverage gaps.
- Distribution shift: monitor prefix-variant drift and feature drift (PSI) between train and later periods; report performance decay over time as a deployment expectation.
- Metrics. For the binary activation-conditional target: AUROC and, more importantly given 12.5% prevalence, AUPRC, plus calibration and decision-curve / cost-weighted utility at the intended threshold. For the survival formulation: time-dependent AUC / concordance (C-index) and integrated Brier score with proper censoring weights. Always report the labeled-population scope alongside metrics.
- pm4py.split_train_test may be mentioned as a convenience baseline only; the primary implementation uses the time-based split above.


## 8. Limitations and decision-use boundary

What the study *can* claim. Among applications the current policy would activate (in a given regime), it estimates the predictive association between early prefix features and 90-day default, with honest handling of censoring and maturity. It can rank activated accounts for early-warning triage and be calibrated for threshold decisions within that population.

What it *cannot* claim. It does not estimate the default risk of rejected, withdrawn, or transferred applications; those outcomes are undefined under activation and were never observed. It is not an application-level "everyone's default probability." Any number for a would-be-rejected applicant is counterfactual and depends on untestable activation-ignorability, so it is reported only as a bounded sensitivity result, never as a point prediction driving action.

Predictive association vs. selection vs. counterfactual. The primary score is an *association* within a *selected* population; it conflates true risk with the activation policy's selection. Selection-corrected and Manski-bound results indicate how far the counterfactual application-level risk could lie from the activation-conditional estimate, and that gap is not resolvable from these data.

At least three ways deployment changes the data-generating process.
1. Selection feedback: if the score gates activations, the future activated population changes, so today's activation-conditional estimand no longer matches tomorrow's population (covariate and label shift).
2. Gaming / behavior change: applicants and officers adapt to known early-warning triggers (e.g., altering document timing or channel), shifting prefix distributions.
3. Policy coupling: using the score to change thresholds re-creates the exact 1-Jul-2025-style regime break, so pre-deployment metrics overstate post-deployment performance; continuous recalibration and monitored backtesting are required.
Additional: transfer/partner routing may change if the score influences referrals, worsening the missing-feed coverage.


## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import numpy as np
import pm4py

# ---- Config (as-of discipline) --------------------------------------------
CSV_PATH = "applications_events.csv"
AS_OF_CUTOFF = pd.Timestamp("2026-02-15")   # configurable; earlier = backtest
FEED_ALLOWANCE = pd.Timedelta(days=35)      # delayed outcome feed
HORIZON = pd.Timedelta(days=90)
PREFIX_K = 3                                # Started -> KYC -> Credit Review
POLICY_CHANGE = pd.Timestamp("2025-07-01")
MIGRATION = pd.Timestamp("2025-10-15")

# Events that must NEVER contribute to a prediction-time prefix / features.
POST_DECISION_ACTS = {"Accepted", "Contract Signed", "Account Activated",
                      "Collections Contact", "Default Recorded"}
# Columns populated only at/after the decision or outcome -> drop from features.
LEAKY_COLS = ["final_limit", "decision_reason", "collection_status",
              "default_90d", "label_available_at"]

# ---- Load & canonicalize ---------------------------------------------------
df = pd.read_csv(CSV_PATH)
for c in ["time:timestamp", "label_available_at", "data_extract_time"]:
    if c in df.columns:
        df[c] = pd.to_datetime(df[c], errors="coerce", utc=False)

# Canonical activity map to undo the 15-Oct-2025 renaming (assumption: mapping
# below reflects the rename; extend per data dictionary).
RENAME_MAP = {"CreditReview": "Credit Review", "KYC": "Identity/KYC Check"}
df["concept:name"] = df["concept:name"].replace(RENAME_MAP)

# Drop migration-created duplicate events (same case/activity/timestamp).
df = df.drop_duplicates(subset=["case:concept:name", "concept:name",
                                "time:timestamp"]).copy()

# Standardize to a pm4py event log dataframe.
df = pm4py.format_dataframe(df, case_id="case:concept:name",
                            activity_key="concept:name",
                            timestamp_key="time:timestamp")
df = df.sort_values(["case:concept:name", "time:timestamp"])

# ---- Case-level state as of cutoff ----------------------------------------
def first_time(g, act):
    m = g.loc[g["concept:name"] == act, "time:timestamp"]
    return m.min() if len(m) else pd.NaT

rows = []
for cid, g in df.groupby("case:concept:name", sort=False):
    start = g["time:timestamp"].min()
    act_t = first_time(g, "Account Activated")
    rej_t = first_time(g, "Rejected")
    wdr_t = first_time(g, "Withdrawn")
    trf_t = first_time(g, "Transferred")
    lbl_at = g["label_available_at"].min() if "label_available_at" in g else pd.NaT
    # Terminal state (competing outcomes; NOT collapsed to non-default).
    if pd.notna(act_t):          terminal = "activated"
    elif pd.notna(rej_t):        terminal = "rejected"
    elif pd.notna(wdr_t):        terminal = "withdrawn"
    elif pd.notna(trf_t):        terminal = "transferred"
    else:                        terminal = "open"
    # Label maturity (activation-conditional target).
    mature = (pd.notna(act_t) and pd.notna(lbl_at)
              and lbl_at <= AS_OF_CUTOFF
              and (act_t + HORIZON + FEED_ALLOWANCE) <= AS_OF_CUTOFF)
    # Read label ONLY for matured activated cases (never invent negatives).
    y = np.nan
    if mature and "default_90d" in g:
        vals = g["default_90d"].dropna().unique()
        y = float(vals[0]) if len(vals) else np.nan
    rows.append(dict(case=cid, start=start, activation=act_t, terminal=terminal,
                     mature=mature, label=y,
                     source_system=g.get("source_system", pd.Series([np.nan])).iloc[0]))
cases = pd.DataFrame(rows)

# Cohort status: labeled / censored / competing / not_yet_mature.
def status(r):
    if r.terminal == "activated" and r.mature and not np.isnan(r.label):
        return "labeled"
    if r.terminal == "activated":               return "activated_not_mature"  # right-censored
    if r.terminal == "open":                    return "administratively_censored"
    if r.terminal == "transferred":             return "competing_transfer"
    return f"competing_{r.terminal}"            # rejected / withdrawn
cases["status"] = cases.apply(status, axis=1)
print("COHORT FLOW (must reconcile to N applications):")
print(cases["status"].value_counts(dropna=False))
print("Labeled default rate (activation-conditional, NOT app-level):",
      cases.loc[cases.status == "labeled", "label"].mean())

# ---- Time-based split by CASE START (not random) --------------------------
labeled = cases[cases.status == "labeled"].sort_values("start")
q = labeled["start"].quantile([0.6, 0.8])
def fold(t):
    if t <= q.iloc[0]: return "train"
    if t <= q.iloc[1]: return "val"
    return "test"
labeled["fold"] = labeled["start"].map(fold)
# ASSUMPTION: keep policy regimes separable; carry a regime flag for §7 checks.
labeled["policy_regime"] = np.where(labeled["start"] < POLICY_CHANGE, "pre", "post")
# Convenience baseline only (NOT the primary split):
# train_log, test_log = pm4py.split_train_test(df, train_percentage=0.8)

# ---- Prefix extraction (no peeking past the decision) ---------------------
# Build a strictly pre-decision event log, then take fixed-length prefixes.
def pre_decision(g):
    dec = g.loc[g["concept:name"].isin(POST_DECISION_ACTS), "time:timestamp"]
    cut = dec.min() if len(dec) else g["time:timestamp"].max()
    return g[g["time:timestamp"] < cut]
pre_df = df.groupby("case:concept:name", group_keys=False).apply(pre_decision)
prefix_log = pm4py.get_prefixes_from_log(pre_df, length=PREFIX_K)  # fixed-count

# Control-flow context for justification (interpretation is clear here):
dfg, sa, ea = pm4py.discover_dfg(prefix_log)          # prefix directly-follows
variants = pm4py.get_variants(prefix_log)             # prefix variants as features
# Temporal features over the TRUNCATED prefix only (never full case):
temporal = pm4py.extract_temporal_features_dataframe(prefix_log)
# Elapsed-time prefix alternative would cut at start + Delta (see design §4).

# ---- Feature table with leakage prevention --------------------------------
# Only pre-decision events; drop leaky columns; take as-of risk_score.
feat_src = prefix_log.copy()
for c in LEAKY_COLS:
    if c in feat_src.columns:
        feat_src = feat_src.drop(columns=c)
def build_features(g):
    return pd.Series({
        "prefix_len": len(g),
        "n_credit_review": (g["concept:name"] == "Credit Review").sum(),
        "n_doc_requests": (g["concept:name"] == "Request Documents").sum(),
        "elapsed_to_cut": (g["time:timestamp"].max()
                           - g["time:timestamp"].min()).total_seconds() / 86400.0,
        # as-of risk_score = earliest pre-decision value, not the updated one:
        "risk_score_asof": (g["risk_score"].dropna().iloc[0]
                            if "risk_score" in g and g["risk_score"].notna().any()
                            else np.nan),
        # documents_total: recompute from event-level uploads <= cut, not the
        # nightly rollup (which leaks same-day future uploads).
    })
features = (feat_src.groupby("case:concept:name")
            .apply(build_features).reset_index()
            .rename(columns={"case:concept:name": "case"}))

# ---- Leakage-audit check ---------------------------------------------------
# Hard guarantee: no post-decision activity survived into the feature source.
assert not feat_src["concept:name"].isin(POST_DECISION_ACTS).any(), \
    "LEAKAGE: post-decision event entered feature source"
assert not any(c in features.columns for c in LEAKY_COLS), \
    "LEAKAGE: outcome/decision column in feature table"

# ---- Assemble modeling frame (labeled, matured, activation-conditional) ----
model_df = (labeled.merge(features, on="case", how="left"))
# NEXT STEPS (not fitted here):
#   * Binary classifier on model_df[fold=="train"] -> predict `label`.
#   * OR discrete-time / Cox SURVIVAL for time-to-default-after-activation so the
#     `activated_not_mature` (right-censored) cases contribute follow-up.
#     (pm4py has NO survival API; connect lifelines / scikit-survival here.)
#   * Sensitivity: IP-of-activation weights from pre-decision features to probe
#     the counterfactual application-level target (untestable ignorability).
#   * Report AUPRC + calibration by fold, policy_regime, and source_system.
print("Model frame:", model_df.shape,
      "| folds:", model_df["fold"].value_counts().to_dict())
```

Notes on the skeleton. It never invents negative labels: only matured activated cases receive a 0/1, and every other bucket keeps a censoring/competing status that reconciles to the full application count. Prefixes are cut strictly before the decision event, leaky columns and post-decision events are asserted out of the feature source, documents_total and risk_score are flagged for as-of recomputation, the split is by case start time (with split_train_test shown only as a commented baseline), and the survival/competing-risk step is marked as an external connection rather than a fabricated PM4Py function.
