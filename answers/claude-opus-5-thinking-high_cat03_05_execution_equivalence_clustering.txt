## 1. Equivalence design space

An execution is the connected object-centric fragment centred on one lead `Order` o*, written X = (E, O, type, ext, lab, ≤, R, Q, q2o): events E, objects O, type: O → ObjectTypes, ext: O → {0,1} (1 iff the identifier is `EXT`-prefixed, i.e. the object's lifecycle is centred elsewhere), labels lab, timestamp order ≤, E2O incidence R with qualifier map Q, and qualified O2O triples q2o.

**≈A — activity-sequence equivalence.** X ≈A Y iff lin(X) = lin(Y), the string of labels ordered by ≤. Preserved: activity vocabulary, Parikh vector, label order. Discarded: object types and counts, E2O incidence, O2O topology and qualifiers, externality — everything object-centric. Reflexive, symmetric and transitive, being equality of a derived value. Concurrency: ties make lin ill-defined, so same-timestamp events are ordered deterministically by (label, canonical object signature); the variant ≈A^po instead compares the labelled Hasse diagram of the timestamp interval order up to isomorphism. Reported only as a baseline, not as the object-centric answer.

**≈T — typed structural equivalence under identifier renaming.** X ≈T Y iff there are bijections β: O_X → O_Y and γ: E_X → E_Y with (i) lab(γ(e)) = lab(e); (ii) type(β(o)) = type(o) and ext(β(o)) = ext(o); (iii) (e,o) ∈ R_X ⇔ (γ(e), β(o)) ∈ R_Y with equal E2O qualifiers; (iv) (o, ψ, o′) ∈ q2o_X ⇔ (β(o), ψ, β(o′)) ∈ q2o_Y; (v) β(o*_X) = o*_Y; and γ preserves order. Preserved: the whole labelled structure — types, per-type multiplicities, incidence degrees, qualifiers, externality, ordering. Discarded: identifier strings and any convention encoded in them (line numbers, warehouse codes). Isomorphism-induced, hence reflexive, symmetric and transitive. Concurrency: ≈T^tot requires γ to preserve the total order, ≈T^po only the partial order induced by strict timestamp inequality, so equal or untrustworthy timestamps may be permuted. ≈T^po is the honest default when Pack and Dispatch are stamped by different systems.

**≈B — business-semantic equivalence (preferred).** X ≈B Y iff α(X) = α(Y), where α = (episodes, deliveries, packaging_mode, reshipment, reverse_flow, settlement, invoices, shared_logistics, shared_finance, composition_change): `episodes` = number of maximal Pack⁺→Dispatch cycles; `packaging_mode` ∈ {single, multi_consolidated, multi_split} from package count and whether one Dispatch covers all packages; `reshipment` = 1 iff some Item lies in ≥2 Packages; `reverse_flow` = 1 iff a return/inspection motif is present; `settlement` ∈ {none, full_single, installments} from payment count plus `partially_settles`; `shared_logistics`/`shared_finance` = 1 iff an external object is incident to a Pack/Dispatch resp. Invoice/Payment event; `composition_change` ∈ {stable, substitution, removal, return_repack} from `replaces`, `removed_before_dispatch`, `repacks`. Preserved: fulfilment shape, boundary integrity, settlement completeness, rework and substitution. Discarded: counts above the bucket thresholds, exact interleavings, which item sat in which package, timestamps. Being equality of a computed signature rather than "similarity below a threshold", it is reflexive, symmetric and transitive — deliberately, since edit-distance clustering here would be intransitive and would chain X1–X7 together through X5 and X6. Concurrency: α is order-insensitive except for `episodes`, counted by object flow rather than temporal adjacency, and `reverse_flow`, which requires a Return incident to an existing Delivery — a causal constraint, not a timestamp artefact.

**≈L — lifecycle-motif equivalence (optional fourth).** Equality of the multiset of per-object lifecycle strings, aggregated per type, with `EXT` objects kept as separate types. It sees convergence and divergence but not the full graph, and sits strictly between ≈A and ≈T.

## 2. Canonical signatures

Two layers: a renaming-invariant structural core by colour refinement on the typed, qualified execution graph, with individualisation-refinement as an exact tie-break (these executions have well under 20 objects, so exactness is cheap); then the abstraction α.

```python
from collections import Counter
import json

def initial_colors(X):
    # local identifiers never enter a colour; type, externality and leadership do
    return {o: ("T", X.type[o], int(X.ext[o]), o == X.lead) for o in X.objects}

def refine(X, col):
    while True:
        new = {}
        for o in X.objects:
            e2o = sorted((X.lab[e], X.eq.get((e, o), ""), X.layer[e])
                         for e in X.events if (e, o) in X.R)
            out = sorted((psi, col[p]) for (s, psi, p) in X.o2o if s == o)
            inn = sorted((psi, col[s]) for (s, psi, p) in X.o2o if p == o)
            new[o] = (col[o], tuple(e2o), tuple(out), tuple(inn))
        classes = {c: i for i, c in enumerate(sorted(set(new.values()), key=str))}
        cand = {o: classes[new[o]] for o in X.objects}
        if partition_of(cand) == partition_of(col):
            return cand
        col = cand

def canonical_colors(X):
    col = refine(X, initial_colors(X))
    while any(n > 1 for n in Counter(col.values()).values()):
        cell = min(c for c, n in Counter(col.values()).items() if n > 1)
        best = None
        for o in sorted([p for p in X.objects if col[p] == cell], key=str):
            trial = refine(X, {p: (col[p], p == o) for p in X.objects})
            form = structural_form(X, trial)
            if best is None or form < best[0]:
                best = (form, trial)
        col = best[1]
    return col

def structural_form(X, col):
    events = []
    for e in order_key(X):                       # layer, then label, then incidence
        inc = sorted((X.type[o], col[o], X.eq.get((e, o), ""))
                     for o in X.objects if (e, o) in X.R)
        events.append((X.layer[e], X.lab[e], tuple(inc)))
    o2o = sorted((col[s], psi, col[p]) for (s, psi, p) in X.o2o)
    mult = sorted(Counter((X.type[o], int(X.ext[o])) for o in X.objects).items())
    return json.dumps([events, o2o, mult], sort_keys=True, default=str)

def structural_signature(X, partial_order=True):
    # X.layer[e] = index in the total order, or the topological layer of the
    # timestamp interval order when partial_order is True
    X = with_layers(X, partial_order)
    return "STRUCT:" + structural_form(X, canonical_colors(X))

def semantic_signature(X):
    pkgs, items, dlv = objs(X, "Package"), objs(X, "Item"), objs(X, "Delivery")
    packs_of = {i: {p for p in pkgs
                    if (p, "packs", i) in X.o2o or (p, "repacks", i) in X.o2o}
                for i in items}
    carried = {d: {p for p in pkgs if (d, "carries", p) in X.o2o} for d in dlv}
    pays, quals = objs(X, "Payment"), {psi for (_, psi, _) in X.o2o}
    labels = set(X.lab.values())
    a = dict(
        episodes=len(dlv),
        deliveries=len(dlv),
        packaging_mode=("single" if len(pkgs) <= 1
                        else "multi_consolidated"
                        if any(len(v) > 1 for v in carried.values())
                        else "multi_split"),
        reshipment=int(any(len(v) > 1 for v in packs_of.values())),
        reverse_flow=int(bool({"Return Item", "Inspect Return"} & labels)),
        settlement=("none" if not pays else "installments"
                    if len(pays) > 1 or "partially_settles" in quals
                    else "full_single"),
        invoices=len(objs(X, "Invoice")),
        shared_logistics=int(any(X.ext[o] for e in X.events
                                 if X.lab[e] in ("Pack Package", "Dispatch")
                                 for o in incident(X, e))),
        shared_finance=int(any(X.ext[o] for e in X.events
                               if X.lab[e] in ("Issue Invoice", "Record Payment")
                               for o in incident(X, e))),
        composition_change=("return_repack" if "repacks" in quals else
                            "substitution" if "replaces" in quals else
                            "removal" if "removed_before_dispatch" in quals
                            else "stable"),
    )
    return "SEM:" + json.dumps(a, sort_keys=True)
```

`structural_signature` decides ≈T in both variants via the flag; `semantic_signature` decides ≈B. Both are pure functions of the execution, so clustering is grouping by string equality and is fully reproducible.

## 4. Cluster interpretations

**S1 — clean isolated single-shipment (X1, X2, X3).** One delivery, one invoice, one full payment, no external objects, stable composition: the happy path, whether the goods travel in one carton or several. It is the volume baseline against which other clusters' cost premium is measured, and the S1.a/S1.b split quantifies multi-carton handling inside an identical customer experience. Risk: X3's second carton is invisible in order-level KPIs, so packaging waste hides here. Flattening on `Package` turns X3 into two unrelated shipments and loses the consolidation into D31; item-flattening fabricates divergence. Stable: deduplicating item rows or normalising timestamps does not move these executions.

**S2 — fragmented fulfilment with instalment settlement (X4).** Two shipment episodes over disjoint items, two deliveries, two payments on one invoice: the order is fulfilled in waves, plausibly from stock availability, and cash arrives in tranches. Risks: higher freight per order, two chances of delivery failure, an open receivable between M41 and M42; the opportunity is spotting the availability pattern early and either consolidating or promising split delivery. Order-flattening hides which delivery carried which item. Only moderately stable: a repair merging M41 and M42 into one amount degrades `settlement` to `full_single` and drifts X4 into S1 unless the tranche count is kept as a feature.

**S3 — logistics boundary crossing (X5).** Local finance, external Order and Item inside packing and dispatch: one carton and one truck movement serving two orders. The consolidation is a genuine saving worth measuring, but a defect or delay in D51 propagates to an order invisible from O5, and cost allocation between O5 and EXT-OA is arbitrary unless modelled. Order-flattening renders X5 identical to X1, erasing the point; item-flattening either injects a phantom EXT-IA into O5's trace or drops it. Weakly stable: the cluster survives only if extraction retains external objects, so scoping executions to a single order destroys it.

**S4 — financial boundary crossing (X6).** Local logistics, shared Invoice and Payment, no allocation qualifier: consolidated or account-level billing, which cuts invoice and dunning cost but makes revenue and cash unattributable per order, so order profitability, per-order DSO and any "paid" check are unsound — "settles V61 without an order-level allocation" is the audit finding. Order-flattening double-counts Issue Invoice and Record Payment across O6 and EXT-OB, inflating revenue. Weakly stable: it hinges on external-object retention, and a repair that fabricates an allocation moves X6 into S1.

**S5 — composition change before dispatch (X7).** X1's labels and multiplicities, but `replaces`, `removed_before_dispatch` and an Item directly incident to Dispatch: an item was substituted or pulled from the carton late, so only I72 shipped while V71 bills the whole order. Risk: over-billing and a promised-versus-delivered mismatch, invisible to activity-level conformance checking; opportunity: a precise detector of late substitution problems. Every flattening misrepresents it, since flattening drops qualifiers and makes X7 indistinguishable from X1. Least stable cluster: it exists only while qualifiers survive extraction.

**S6 — post-delivery reverse flow and rework (X8).** Two deliveries, a Return anchored to an existing Delivery, an inspection, and an Item in two Packages: the return-and-reship loop, with a cost profile like S2 but a defect rather than availability as its cause. Costs are double freight plus inspection labour and dissatisfaction; the opportunity is attributing loops to item, carrier or route. Delivery-flattening splits it into two unrelated shipments and destroys the return link; item-flattening shows I82 shipped twice with no explanation. Highly stable, since extra labels and item reuse across packages both survive repair.

## 5. Borderline cases

**X1 vs X2.** ≈A, ≈T and ≈B all merge them; only a relation that reads identifiers separates them. That is defensible exactly once: if `I11`/`I12` encode order-line positions, X2 is a genuine reordering of line entry and a check on "lines entered in catalogue order" must distinguish them. Absent such a documented convention, treating the swap as meaningful breaks renaming invariance and yields a partition of singletons.

**X1 vs X5.** Label-equivalent and locally multiplicity-equivalent. An order-scoped analyst who projects to the lead object sees the same execution and merges them; an analyst who types externality sees a co-owned Package and Delivery plus a foreign Item in the carton and separates them. The disagreement is about scope: X5's *order* behaved normally, X5's *fulfilment* did not. Both are true, which is why the flag and not the identifier carries the distinction.

**X1 vs X6.** The same tension mirrored into finance, with a sharper consequence. Merging is defensible for delivery-performance analysis, where X6 is unremarkable; separating is mandatory for revenue analysis, because "one order, one invoice, one payment" is false for X6 and any per-order cash figure from a flattened log is wrong. Note that ≈A and type-level ≈L merge X1, X5, X6 and X7; only externality-aware relations split them.

**X1 vs X7.** Treat E2O incidence on Dispatch as derived — a delivery trivially touches the items in its packages — and discard qualifiers, and X7 ≈T X1. Treat each E2O assertion and qualifier as first-class, and the extra incidence naming I72 together with `removed_before_dispatch` on I71 says the delivered scope is one item while the billed scope is two. Both readings follow from defensible conventions about redundancy in E2O; only the second catches the over-billing.

**X3 vs X4.** Both have two packages, so a warehouse-centric equivalence keyed on packaging granularity merges them. A customer- and cash-centric equivalence keyed on deliveries and settlement separates them: X3 is one shipment and one payment, X4 two shipments and two tranches. My α takes the second view, and this pair shows why "number of Pack events" is a poor clustering feature alone.

**X4 vs X8.** Both show two Pack/Dispatch pairs and merge under any relation that only counts logistics events — what naive collapsing of repeated labels produces. Two features separate them: direction, since X8's Return and Inspect are causally anchored to D81, and item reuse, since `reshipment` = 1 for X8 (I82 in P81 and P82) but 0 for X4's disjoint items. Merging is defensible for a pure freight-cost model, two shipments either way, but wrong for root-cause work, where the drivers are stock-outs versus fulfilment defects.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel(ocel, object_type, max_objs=...)` partitions the process executions associated with objects of the given type and returns a dictionary keyed by a string describing the execution, whose values are the equivalent sub-logs. The key encodes the execution's ordered activity labels together with the object types and counts involved; it does not in general preserve O2O qualifiers, which package carried which item, the distinction between locally and externally owned objects, or the partial order behind the timestamps. Grouping is exact string equality on that key.

Raw object identifiers make exact clusters too fine in two ways. Directly, if identifiers enter the key then every execution is its own class, since O1…O8 differ by construction; the useful invariance is typed multiplicity, not identity. Indirectly, identifiers leak into orderings: X1 and X2 differ only in which item comes first, so any key serialising related objects in identifier order splits two isomorphic executions. Canonicalisation must sort object references by a structurally computed colour, never by name.

Post-processing: recompute `structural_signature` on each sub-log to replace the library string with a genuinely renaming-invariant key; recompute `semantic_signature` and re-group, which merges classes differing only in package count (X1/X3) and splits classes differing only in externality (X1/X5/X6); keep the semantic → structural → sub-log mapping so any coarse cluster can be drilled down.

Exact equivalence is preferable when the question is literal structural identity: regression-testing an extraction pipeline, deduplicating variants before manual inspection, or driving a full-fidelity variant explorer. Coarser business clustering wins for segmentation, KPI comparison and root-cause hypotheses, where a partition of singletons carries no information.

`max_objs` bounds objects per execution because executions can explode — X5 and X6 are the mechanism, since a shared Package or Invoice transitively connects O5 to EXT-OA and O6 to EXT-OB, and those to further orders. A low bound truncates executions so keys depend on which objects survived, which is non-deterministic unless truncation order is fixed; a high bound lets connected executions swallow much of the log so every execution becomes unique. I recommend a radius-limited neighbourhood that includes external objects but does not expand through them, a deterministic truncation order, and a truncation flag on the signature so truncated and complete executions are never silently compared.

```python
import json
from collections import defaultdict
import pm4py

LEAD_TYPE = "Order"

clusters = pm4py.cluster_equivalent_ocel(ocel, LEAD_TYPE, max_objs=30)

structural, semantic = defaultdict(list), defaultdict(list)
for pm4py_key, sublogs in clusters.items():
    for sub in sublogs:
        X = build_execution(sub, lead_type=LEAD_TYPE)   # E2O from sub.relations, O2O from sub.o2o
        X = tag_external(X, predicate=lambda oid: str(oid).startswith("EXT"))
        s_key = structural_signature(X, partial_order=True)    # section 2
        b_key = semantic_signature(X)                          # section 2
        structural[s_key].append((X.lead, pm4py_key))
        semantic[b_key].append((X.lead, s_key))

report = {b: {"n_executions": len(v),
              "n_structural_variants": len({s for _, s in v}),
              "example_orders": sorted({o for o, _ in v})[:5]}
          for b, v in semantic.items()}
print(json.dumps(report, indent=2, sort_keys=True))
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** S5 loses its evidence: `composition_change` falls back to `stable` and X7's semantic signature equals X1's, though ≈T still separates them through the extra Item incidence on Dispatch — an argument for promoting anomalous E2O degree to a motif of its own. X4 survives, since two Payment objects imply instalments without `partially_settles`. X8 survives via Return/Inspect and item reuse, provided `repacks` is replaced by the derivable "item in two packages".

**Ignore external objects.** X5 and X6 become identical to X1 at every level, collapsing S3 and S4 into S1 and reducing eight executions to four semantic clusters. This is the most destructive perturbation and exactly what order-flattening does; it shows that externality, unlike identity, is load-bearing semantics belonging in every signature.

**Collapse repeated same-label events.** Collapsing consecutive duplicates makes X3 ≈A-equivalent to X1, harmless for ≈B since packages are counted from objects, not events. Collapsing all repeats to sets is far worse: X4 loses its second Dispatch and second Payment and falls into S1, while X8 loses its second episode but keeps Return/Inspect. Clustering on collapsed labels therefore cannot see fragmentation or instalment settlement and must not drive cost segmentation.

**Treat Pack and Dispatch order as a partial order.** X4's four logistics events become two concurrent branches, so every interleaving of (Pack P41, Dispatch D41) with (Pack P42, Dispatch D42) merges into one class — a robustness gain, since the recorded interleaving is largely a scan-timing artefact. X3 stays distinct from X4 because its two Pack branches join into a single Dispatch, and join structure survives partial-order isomorphism. X8 is not relaxed away: Return Item references D81, so the causal order between episodes is retained. Under ≈A^po, X3 and X4 stop being distinguished by label order alone — another reason not to cluster on labels.

**Treat payment multiplicity as an amount attribute.** If M41 and M42 are repaired into one Payment with an amount and `tranches=2`, X4's remaining structural difference from X1 is only deliveries and packages, and `settlement` must be read from the attribute rather than object count. α tolerates this, but the cluster becomes attribute-dependent, making S2 the least stable forward-flow cluster. The lesson: when structure is normalised into attributes, the equivalence must be re-derived from those attributes or clusters silently merge.

Across the five perturbations, S1, S2 and S6 survive at least four; S3 and S4 die with external objects; S5 dies with qualifiers.

## 8. Limitations and recommendation

For **compliance monitoring**, use ≈T with qualifiers and externality (the structural signature, partial-order variant). Compliance statements here are relational — each Invoice bills exactly one Order, each dispatched Item was packed and not removed, each Payment allocates to an Order — and are decided by E2O and O2O structure, not activity sequences. Only this level separates X1 from X6 and X7, which is where the findings are.

For **operational segmentation**, use ≈B: six interpretable groups with distinct cost and risk drivers, stable under timestamp noise, merging X1–X3 so the volume baseline is not fragmented by packaging detail. Segmentation needs classes populous enough to compare, which the finest partition never provides.

For **root-cause analysis**, use ≈B as the entry point but retain the drill-down to structural signatures, i.e. the nested key (semantic, structural). Causes live in what α discards: which item was substituted in X7, which delivery the X8 return came from, which order shares X5's carton. A flat single level either hides the cause or leaves one execution per class with no comparison group.

For **descriptive reporting**, use ≈A^po or ≈L annotated with the semantic cluster distribution. Four label classes are what fits on a slide, and the annotation stops the reader concluding that X1, X5, X6 and X7 are the same process, which the label view alone strongly suggests.

No single notion serves all four, because the requirements conflict: compliance needs maximal relational sensitivity and tolerates many small classes; segmentation needs few populous classes and therefore abstraction; root-cause work needs both at once, achievable only as a hierarchy rather than a partition; reporting needs classes matching vocabulary the audience already has. The relations also disagree about what "the execution" is — order-scoped views merge X5 and X6 with X1, boundary-aware views cannot — and that scope decision is a modelling choice, not a fact about the data, so calling one clustering *the* correct one is really a claim about the question asked. Compute all three levels from one canonical core, publish the mapping between them, and report the sensitivities (external objects for S3/S4, qualifiers for S5, payment normalisation for S2) alongside every cluster-based number.
