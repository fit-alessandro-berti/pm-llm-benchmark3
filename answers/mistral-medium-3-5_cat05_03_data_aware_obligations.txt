## 1. Temporal Data Semantics
- **State Reconstruction**: For each event, the state is the latest non-blank value of each attribute (amount, risk_level, jurisdiction, customer_type, exemption_id) up to that event's timestamp. Blanks mean "no update" (retain prior value).
- **Same-Timestamp Ordering**: Use `event_index` as a tie-breaker. Lower `event_index` occurs first.
- **Material Changes**: A change is material if it affects the evaluation of any rule (e.g., amount increase >20%, jurisdiction added to sanctions list, risk_level  HIGH).
- **Final Attributes**: The final case state is irrelevant for compliance; only the state at the time of each event matters.
- **Event Time vs. Effective Time**: Attribute updates are effective at their `time:timestamp` unless evidence (e.g., exemption approval timestamp) explicitly overrides this.
- **Evidence Time**: Late records (e.g., `Record_Exemption` after `Release_Funds`) may provide evidence of earlier approval but do not retroactively alter event-time state unless corroborated (e.g., qualified signatures).

## 6. Why Control-Flow-Only Conformance Is Insufficient
1. **Final-State Leakage**: Control-flow checks (e.g., "Enhanced_Review  Release_Funds") ignore that the state at `Release_Funds` may differ from the state at `Enhanced_Review` (e.g., TX-309’s amount increase).
2. **Post-Hoc Exemptions**: Exemptions recorded after `Release_Funds` (e.g., TX-302’s `Record_Exemption` at 11:00) cannot be validated by control flow alone; evidence timestamps are required.
3. **Material Changes After Review**: A 25% amount increase after `Enhanced_Review` (TX-309) invalidates the review, but control flow would still see `Enhanced_Review  Release_Funds` as valid.
4. **Conditional Activation**: Rules like R1 depend on dynamic attributes (amount, jurisdiction). Control flow cannot encode data-dependent conditions.
5. **Missing Data**: If `amount` is missing at `Release_Funds` (TX-305), control flow cannot determine if R1 applies.
6. **Same-Timestamp Ordering**: TX-311’s `Enhanced_Review` and `Update_Jurisdiction` share a timestamp. Control flow cannot resolve the order without `event_index`.

## 7. Recommended Logging and Control Improvements
1. **Immutable Release Payloads**: Include a cryptographic hash of the release payload (amount, jurisdiction, etc.) in the `Release_Funds` event to prevent tampering.
2. **Effective/Record/Signature Timestamps**: Distinguish:
   - `effective_time`: When the change logically applies (e.g., exemption approval).
   - `record_time`: When the event was logged.
   - `signature_time`: When a qualified signature was applied (for exemptions).
3. **Rule Versioning**: Log the version of each policy rule (R1–R7) in effect at the time of the event.
4. **Exemption Scope Clarity**: Explicitly log the scope (jurisdiction, customer_type, amount range) and the rules waived by each exemption.
5. **Change Provenance**: For every attribute update, log:
   - The previous value.
   - The source of the change (e.g., "customer request", "system update").
6. **Stable Event Ordering**: Enforce global monotonic timestamps with sub-millisecond precision or use `event_index` as a tie-breaker.
7. **Sanctions List Versioning**: Log the version of the sanctions list at the time of `Sanctions_Screen` and `Sanctions_List_Update`.
8. **Unknown Value Handling**: Explicitly mark unknown attributes (e.g., `amount=null` with a reason) instead of leaving them blank.
