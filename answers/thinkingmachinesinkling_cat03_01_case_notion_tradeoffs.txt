## 1. Analytical assumptions

**Case notion.** I treat the case notion as the object type whose unique instances become the rows of a traditional event log. Each case is a trace of activities ordered by timestamp, and every event assigned to that case is copied into the trace if and only if the event’s direct E2O relation includes an object of the case-defining type.

**Convergence versus divergence.**  
- **Convergence** occurs when one event is linked to multiple objects of the case-defining type (e.g., e13 relates to both O2 and O3). When flattening on Order, that event is duplicated into both traces. This inflates event frequencies and can create false causal edges if the copies are ordered differently relative to other events.  
- **Divergence** occurs when a single case trace contains activities that belong to independent sub-lifecycles of other related objects. For example, an Order case for O3 includes packaging events for P3 (with O2/I21/I31) and P4 (with O4/I32/I41), dispatch events for D2 and D3, and delivery confirmations for both deliveries. The trace is not a linear process but an interleaved merge.

**Status of copied shared events.** I treat them as **both** genuine evidence and synthetic duplication. They are genuine evidence because e16 genuinely involves O1, O2, and O3 together in D2; removing them entirely would erase the consolidation fact. However, in a flattened log they become synthetic duplicates that distort frequency metrics, create spurious loops in discovered DFGs, and make variant counts unreliable.

**Permitted analytical transformations.** By default I use only the direct E2O relations given in the table. I explicitly permit, for comparative purposes, a **propagated-relation variant** in which event-object relations are extended through one-step O2O links (e.g., through *packs*, *contains*, *carries*, or *bills*). This is not applied silently; it is proposed as a sensitivity check in Section 7.

**Distortion 2 – Cross-order package P4: divergence in Order O3 trace.**  
*Affected flattening:* Order. *Cited objects/events:* e13 (P3) and e14 (Pack Package, O3,O4,I32,I41,P4), both present in O3’s trace; e16/e17 and e24/e27 follow.  
O3’s trace contains two *Pack Package* events (e13 at 10:12, e14 at 10:20) linked to two different packages with different co-orders and items. The discovered DFG for O3 will likely contain *Pack Package*  *Pack Package* or parallel branches, which is not a process loop but a divergence artifact. O3 also has two *Dispatch* events (e16 for D2, e17 for D3) and two *Confirm Delivery* events (e24, e27). This makes O3 appear to have a repeated fulfillment cycle, when in reality it is split across two independent logistics streams. The effect is **context-dependent**: it correctly signals split shipment, but a linear process model will misinterpret it.

**Distortion 3 – Cross-order package P3: duplication in Item flattening.**  
*Affected flattening:* Item. *Cited objects/events:* I21 and I31; e13, e16, e24.  
Because I21 and I31 are both in P3, they share e13, e16, and e24. In the Item log, both I21 and I31 have near-identical traces: *Add Item* (e07/e08)  *Pack Package* (e13)  *Dispatch* (e16)  *Confirm Delivery* (e24). The event duplication means that *Pack Package* is counted twice in frequency metrics for these two items, even though only one package was assembled. More subtly, the correlation between I21 and I31 (they are always co-packed in this snapshot) is hidden: they appear as independent parallel cases rather than coupled items. The effect is **informative** for parallel-flow visibility but **harmful** if used to compute per-item cycle time without normalization.

**Distortion 4 – Cross-order package P4: interpretive trap in Package flattening.**  
*Affected flattening:* Package. *Cited objects/events:* P4 (e14, e17, e27); O3 is also in P3/D2.  
In the Package log, P4’s trace is clean and complete: *Pack*  *Dispatch*  *Confirm Delivery*. An analyst might conclude that P4’s on-time delivery (e27 at 10:00 on 2026-02-04) implies successful fulfillment for its constituent orders O3 and O4. However, O3’s fulfillment is only half-complete in P4; the other half (P3 in D2) was confirmed earlier (e24 at 16:00 on 2026-02-03). The Package log hides this split, creating an **interpretive trap**: package-level success does not map directly to order-level success. This is **harmful** if the Package log is used alone to report order fulfillment status.

**Distortion 5 – Consolidated delivery D2: consolidation bucket in Delivery flattening.**  
*Affected flattening:* Delivery. *Cited objects/events:* D2; e16 (Dispatch, O1,O2,O3,I12,I21,I31,P2,P3,D2); e24 (Confirm Delivery, same set).  
The D2 case contains exactly two events. The DFG is trivial (*Dispatch*  *Confirm Delivery*), and with only three delivery cases total (D1, D2, D3), statistical inference is weak. The performance metric “delivery time” (11:05 to 16:00, ~4h 55m) is accurate for the vehicle/load, but it serves three orders. Normalizing per order divides the duration conceptually, but the log provides no structural basis for that division. The divergence is **conceptual**: D2 is treated as one process instance, yet it consolidates three independent order deliveries. The effect is **context-dependent**: excellent for fleet management, misleading for per-order service-level analysis.

**Distortion 6 – Consolidated delivery D2: spurious repetition in Order traces.**  
*Affected flattening:* Order. *Cited objects/events:* O1, O2, O3; e15/e23 (D1) versus e16/e24 (D2).  
O1 experiences two dispatches (e15 at 11:00 for D1; e16 at 11:05 for D2) and two confirmations (e23 at 14:00; e24 at 16:00). O2 and O3 experience only the D2 pair. In the Order DFG, this creates edges such as *Dispatch*  *Dispatch* and *Confirm Delivery*  *Confirm Delivery*, which can be mistaken for loops or rework. The frequency of *Dispatch* in the Order log is inflated: e15 (1 copy), e16 (3 copies), e17 (2 copies), totaling six copies for three physical dispatch actions. This is **harmful** for variant analysis: O1’s variant looks like a repetition pattern that does not exist in the physical process.

**Distortion 7 – Consolidated invoicing V2: merged financial lifecycles.**  
*Affected flattening:* Invoice and Order. *Cited objects/events:* V2; e19 (Issue Invoice O2,O3,V2); e22 (Record Payment O2,O3,V2,M2); e25 (Record Payment O2,O3,V2,M3).  
In the Invoice log, V2 correctly shows *Issue Invoice*  *Record Payment* (partial)  *Record Payment* (complete), capturing the installment correctly. However, in the Order log, e19, e22, and e25 are copied into both O2 and O3. Both orders therefore display identical financial traces, and the fact that they share a single invoice is not structurally represented—only visible in the event object lists. The divergence is that two orders are merged into one financial stream; the convergence duplicates that stream back into both orders. The DFG for Order may show *Issue Invoice*  *Record Payment*  *Record Payment*, suggesting installment is a standard order-level pattern, without revealing it applies to a shared bill. This is **harmful** for credit-risk or revenue-recognition analysis tied to individual orders.

**Distortion 8 – Partial payments M2/M3: broken sequence in Payment flattening.**  
*Affected flattening:* Payment. *Cited objects/events:* M2 (e22, *partially_settles* V2) and M3 (e25, *completes_settlement* V2).  
In the Payment log, M2 and M3 are separate cases, each containing exactly one event. There is no edge linking them, despite M3 logically completing M2’s settlement of V2. The qualifier (*partially_settles* vs. *completes_settlement*) preserves the semantic distinction, but the case separation breaks the temporal and logical sequence. By contrast, the Invoice log preserves the sequence (e22 before e25). This is **harmful** for settlement-pattern discovery: an analyst using the Payment log alone might treat M2 and M3 as independent, unrelated payments for different obligations.

**Distortion 9 – Near-singleton lifecycle: Payment flattening collapses to points.**  
*Affected flattening:* Payment. *Cited objects/events:* M1 (e21), M2 (e22), M3 (e25), M4 (e26).  
Every Payment case contains exactly one *Record Payment* event. The log skeleton is a single node; the DFG has no edges; trace duration is zero for all four cases. Although each event carries rich relational context (e.g., e22 links O2, O3, V2, M2), that context is invisible in the case sequence. The lifecycle is truncated to an instantaneous point, hiding all preceding fulfillment and invoicing context. This is the most extreme distortion: **harmful** for any process-oriented question, though it remains useful for counting settlement transactions by qualifier.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs that should still be created.**  
Given the analysis goals, I recommend creating all six flattened logs, but treating them as **specialized views**, not as competing “correct” logs:
- **Order-flattened** (primary under Decision B) for customer-journey and split-shipment visibility.
- **Item-flattened** for SKU-level warehouse tracking.
- **Package-flattened** for logistics consolidation analysis.
- **Delivery-flattened** for transportation performance.
- **Invoice-flattened** for billing and settlement patterns.
- **Payment-flattened** should be created only for frequency inspection of settlement types; it should **not** be used for process discovery.

**Questions each flattened log can answer safely.**  
- **Order:** “What is the total calendar time from Create Order to Close Order for each order?” (accurate, though ambiguous for O3 regarding which delivery counts). “How many orders experience more than one delivery confirmation?” (count traces with duplicated Confirm Delivery).  
- **Item:** “What is the average time from Add Item to Confirm Delivery for items in single-item packages versus shared packages?” (compare I11 vs. I21/I31).  
- **Package:** “What is the cycle time from Pack to Confirm Delivery for P3 versus P4?” “What proportion of packages contain items from more than one order?” (P3 and P4).  
- **Delivery:** “What is the average dispatch-to-confirmation lag for D1, D2, and D3?” (exact, because each delivery case has unique events).  
- **Invoice:** “What is the settlement duration for single-order invoices (V1, V3) versus consolidated invoices (V2)?” “How often do payments occur in installments?” (only V2).  
- **Item/Package:** “Are co-packed items always delivered together?” (check I21/I31 traces).

**Questions that require object-centric methods.**  
- **Cross-object correlation:** “Does consolidation in P3 delay the delivery confirmation of O2 relative to O3, or vice versa?”  Requires an **OC-DFG** (`pm4py.discover_ocdfg`) linking Order and Package, or an **OTG** (`pm4py.discover_otg`) to see the O2P3D2 path versus O3P3/P4D2/D3.  
- **Interaction quantification:** “How frequently do orders share packages, deliveries, invoices, or payments?”  **Object interaction summary** (`pm4py.ocel_objects_interactions_summary`) provides direct counts (e.g., P3 links O2 and O3; D2 links O1,O2,O3; V2 links O2,O3).  
- **True variant discovery without duplication:** “What are the genuinely distinct fulfillment patterns if shared events are counted once per physical occurrence?”  **Equivalent execution clustering** (`pm4py.cluster_equivalent_ocel`) on Order can reveal whether O2 and O3 are execution-equivalent because they share P3, D2, and V2.  
- **Event-to-object graph structure:** “Which events act as bridges between logistics and financial objects?”  **ET-OT graph** (`pm4py.discover_etot`) reveals that e16 connects logistics objects (P2,P3,D2) with financial-ancestor objects (O1,O2,O3), while e19 connects O2,O3 to V2.

**Reconciling contradictory findings.**  
If the Order DFG shows a loop *Pack Package*  *Pack Package* (from Distortion 2), but the OTG shows P3 and P4 as separate nodes both linked to O3, the reconciliation is explicit: the “loop” is divergence, not repetition. The Order trace merges two package lifecycles; the OTG separates them.  
If the Order log reports six *Dispatch* events but the Delivery log reports only three, reconciliation uses the interaction summary: e16 and e17 are shared events (e16 relates to D2 only, but copied to O1,O2,O3; e17 to D3 copied to O3,O4). Normalizing Order-frequency by dividing by the number of related orders per event (e.g., e16 count divided by 3) aligns the counts.  
If Payment clustering separates M2 and M3 but Invoice clustering keeps them together, the reconciliation is semantic: the case notion determines whether settlement is seen as a point transaction or a temporal installment sequence.

## 5. Lead-object decision

**Position: B. Use a primary lead object (Order) plus explicitly secondary lifecycles.**

**Decision criteria.**  
1. **Universal presence:** Every event e01–e31 includes at least one Order. No other object type achieves this (Item is absent from financial events; Package is absent from invoicing; Delivery is absent from order creation; Invoice and Payment are absent from logistics).  
2. **Business contract orientation:** The Order is the customer-facing entity that initiates and closes the process (e01, e28).  
3. **Financial closure linkage:** Only Order has direct paths (through shared events) to Invoice (e18–e20) and, via Invoice, to Payment (e21–e26), and explicit Close Order events (e28–e31).  
4. **Controllability:** Divergence and convergence are severe but can be managed by annotating shared events and maintaining secondary lifecycles.

**Strongest supporting evidence.**  
Order O1 demonstrates the value of the primary view: it captures split fulfillment across P1/D1 and P2/D2 (e11,e15,e23 vs. e12,e16,e24), invoicing (e18,e21), and closure (e28) within one trace. The presence of O1–O4 in every event means that selecting Order avoids the near-total truncation seen in Payment or the partial coverage seen in Delivery.

**Strongest counterargument.**  
O3’s Order trace is severely distorted by divergence: it includes e13 (P3 with O2/I21/I31), e14 (P4 with O4/I32/I41), e16/e24 (D2 with O1,O2,O3,P2,P3), e17/e27 (D3 with O3,O4,P4), and shared financial events e19/e22/e25 (V2 with O2,O3). The trace is not a linear fulfillment process but a merged stream of two packages, two deliveries, and a shared invoice. Convergence duplicates e13, e16, e19, e24, and e25, inflating frequencies and creating false loops (Distortions 2, 6, 7). If the primary goal were logistics optimization, Package or Delivery would be cleaner; if the goal were pure settlement analysis, Invoice would suffice.

**Residual risk.**  
Even with secondary lifecycles, analysts may misinterpret duplicated events in the primary Order log as independent occurrences (e.g., treating O2 and O3 as having separate invoices). Performance metrics for split orders (especially O3) remain ambiguous: “time to delivery” could mean D2 (16:00 on 2026-02-03) or D3 (10:00 on 2026-02-04). The interaction summary must always be consulted alongside the flattened log.

**Conditions under which I would change the decision.**  
- If the business question shifts exclusively to logistics consolidation (e.g., “How efficiently are vehicles loaded?”), I would switch the primary lead to **Delivery** (D) or **Package** (P) and treat Order as secondary.  
- If cross-order consolidation were eliminated in future data (all P, D, V relate 1:1 to O), divergence and convergence would collapse, and I would move to **A** (Order alone).  
- If divergence became unmanageable even with annotations—e.g., if every order shared every package and every delivery—then I would reject the premise entirely (**C**) and rely solely on multi-object views (OC-DFG, OTG, ET-OT) without a flattened primary.

## 7. Sensitivity and validation plan

**Check 1: Removing or down-weighting copied shared events.**  
Create a reduced Order log (`log_order_reduced`) in which events linked to more than one Order are retained only for the lowest-ID order (e.g., e16 kept for O1 only; e13 kept for O2 only; e19 kept for O2 only). Re-run `discover_dfg` and `discover_log_skeleton`. Expected result: the spurious loops *Dispatch*  *Dispatch* and *Confirm Delivery*  *Confirm Delivery* (Distortion 6) should disappear or weaken. Compare the frequency of *Pack Package* in the reduced log (should be closer to the physical count of 4) versus the full Order log (inflated by shared events). This validates that divergence artifacts are driven by duplication, not by true repetition.

**Check 2: Direct E2O relations versus explicitly propagated relations.**  
Build `ocel_prop` by extending each event’s object set through one-step O2O paths: e.g., for e15 (O1,I11,P1,D1), propagate through *packs* (P1I11, already present) and *carries* (D1P1, already present). More meaningfully, for e18 (O1,V1), propagate through *bills* (V1O2,O3? No, V1 bills O1 only), but for e19 (O2,O3,V2), propagate through V2 to its payments M2/M3 (not in e19). The key comparison is running `discover_ocdfg` and `discover_etot` on both `ocel` and `ocel_prop`. If propagated edges appear (e.g., linking Order events directly to Payment objects that were never in the direct E2O set), the OTG will show additional arcs. This reveals whether hidden O2O paths materially alter the process model, confirming whether direct E2O analysis is sufficient or whether silent propagation is necessary.

**Check 3: Changing the lead object for discovery.**  
Re-run the full pipeline using `log_package` and `log_item` as primary inputs to `discover_dfg` and `discover_log_skeleton`. Compare:  
- **Trace lengths:** Order traces are long and interleaved; Package traces are consistently 3 events; Item traces are 4 events but truncated; Payment traces are 1 event.  
- **Variant counts:** Order will yield many more variants due to divergence; Package should yield exactly 4 linear variants (P1–P4).  
- **Skeleton structures:** Order skeleton will show parallel/conflicting edges; Package skeleton should be a strict chain.  
This validates that the choice of lead object determines whether the discovered model is linear (Package) or merged (Order).

**Check 4: Comparing frequency metrics in OC-DFG.**  
Using `pm4py.discover_ocdfg(ocel, object_type="order")`, compute or manually compare three frequency metrics for key activities:  
- **Event-based:** Each occurrence of an event is counted once regardless of related objects (e.g., e13 = 1; e16 = 1).  
- **Unique-object-based (per type):** For Order-related counts, sum the unique orders per event (e13: O2,O3  2; e16: O1,O2,O3  3).  
- **Total-object-based:** Sum all related objects (not restricted to the target type).  
Compare the frequency of *Pack Package* (e11–e14) and *Dispatch* (e15–e17) across these metrics. The discrepancy quantifies the convergence effect: event-based counts are correct for physical actions, but unique-object-based counts inflate by the number of shared orders. This check ensures that any performance or frequency claim in the report specifies which counting rule was used, avoiding unsupported conclusions.

**Additional reconciliation check:** Compare `interactions` (object interaction summary) against the duplicated-event counts in each flattened log. For example, the interaction summary should report that O2 and O3 co-occur in P3, D2, V2, M2, and M3. If the Order log shows identical event copies for both orders, but the interaction summary confirms shared participation, the contradiction is resolved: duplication is an artifact of flattening, not of independent execution.
