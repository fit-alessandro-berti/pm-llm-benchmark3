## 1. Modeling assumptions

- **Object types and capitalization** are exactly:
  - `Order`: O100, O200
  - `Item`: I1, I2, I3
  - `Package`: P1, P2
  - `Delivery`: D1, D2
  - `Invoice`: V1
  - `Payment`: M1, M2
- Capitalization is part of the object type identity. There is no separate object for a monetary amount; payment amounts are event attributes.

### E2O qualifier vocabulary

Each qualifier describes the role of the object in the event, not a static relationship:

| Activity family | Qualifiers |
|---|---|
| Order creation/closing | `creates_order`, `closes_order` |
| Add Item | `adds_item`, `added_to_order` |
| Reserve Stock | `reserves_item`, `reserved_for_order` |
| Pack Package | `packs_item`, `packs_package`, `packs_for_order` |
| Dispatch Package | `dispatches_package`, `assigns_delivery` |
| Confirm Delivery | `confirms_delivery` |
| Issue Invoice | `issues_invoice`, `bills_order` |
| Record Payment | `records_payment`, `applies_to_invoice` |

### O2O conventions

All O2O rows are directed from the semantic subject/container to the target:

- `Order -> Item` with `contains`
- `Package -> Item` with `packs`
- `Delivery -> Package` with `carries`
- `Invoice -> Order` with `bills`
- `Payment -> Invoice` with `partially_settles` or `completes_settlement`

No inverse O2O rows are stored. If an analysis needs the reverse direction, it must traverse the graph explicitly.

### Direct versus propagated E2O relations

The canonical `relations` table contains only declared operational participation:

- Add, reserve, and pack events directly involve the relevant Orders and Items.
- E07 is directly connected to both O100 and O200 because the narrative explicitly says the P1 packing event relates to both.
- E08 is connected to O100 as the declared order-fulfillment scope of packing I2.
- Dispatch events directly involve their Package and Delivery, but not their Items or Orders.
- Delivery confirmations directly involve only the Delivery.
- Invoice issuance directly involves V1, O100, and O200.
- Payment records directly involve their Payment object and V1, but not Orders or Items.
- No graph-derived Order or Item rows are added to dispatch, delivery-confirmation, or payment events.

Thus, transitive involvement can be recovered analytically through O2O, but is not represented as though it were an observed source-system E2O relation. If propagated rows are later needed, they should be placed in a separate DataFrame or given qualifiers beginning with `derived:`.

The label `M2 -> V1 : completes_settlement` is a modeling assumption that the last stated installment completes V1. Because no invoice total is supplied, this cannot be verified arithmetically; a stricter accounting interpretation could label M2 as `partially_settles` instead.

### PM4Py assumption

The code assumes a current PM4Py 2.x API exposing the named top-level object-centric functions and the OCEL constructor shown below. It also assumes that `pm4py.ocel_flattening` uses direct E2O membership rather than automatically traversing O2O. If a PM4Py release has a different constructor signature or import location, only the isolated constructor line—and possibly the import—needs adjustment; the four DataFrames retain the same semantics.

        make_event("E03", "Add Item", "2026-04-06 08:06:00"),
        make_event("E04", "Create Order", "2026-04-06 08:10:00"),
        make_event("E05", "Add Item", "2026-04-06 08:12:00"),

## 4. Expected flattened behavior

These predictions assume the direct-E2O flattening semantics stated in Section 1. A PM4Py version configured to traverse O2O transitively would produce richer flattened logs.

### Order flattening

- **Trace shape**
  - O100:  
    `Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Pack Package  Issue Invoice  Close Order`
  - O200:  
    `Create Order  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order`
- **Copied shared events**
  - E06 `Reserve Stock`, E07 `Pack Package`, and E11 `Issue Invoice` are each copied into both Order traces.
  - There is still only one physical occurrence of each in the OCEL.
- **Omitted lifecycle aspects**
  - Dispatch, delivery confirmation, and both payment records are absent because they have no direct E2O link to Order.
  - Item, package, delivery, and payment identities are not represented as ordinary case activities.
- **Likely DFG**
  - Start: `Create Order`
  - `Create Order  Add Item`
  - `Add Item  Add Item`
  - `Add Item  Reserve Stock`
  - `Reserve Stock  Pack Package`
  - `Pack Package  Pack Package`
  - `Pack Package  Issue Invoice`
  - `Issue Invoice  Close Order`
  - End: `Close Order`
- **Likely log skeleton**
  - One creation, reservation, invoice, and closure per order.
  - Add Item and Pack Package have variable occurrence counts because O100 has two of each and O200 has one.
- **Misleading interpretations**
  - The two consecutive `Add Item` or `Pack Package` activities for O100 are not rework loops; they concern different items and packages.
  - `Issue Invoice  Close Order` looks direct, although deliveries and payments happen between them in the OCEL.
  - Absence of payment or delivery activities must not be read as failure to pay or deliver.

### Package flattening

- **Trace shape**
  - P1: `Pack Package  Dispatch Package`
  - P2: `Pack Package  Dispatch Package`
- **Copied shared events**
  - No event is shared by P1 and P2, so there is no copied event between the two Package cases.
- **Omitted lifecycle aspects**
  - Item reservation, delivery confirmation, invoicing, payment, and order closing are absent.
  - P1’s mixed-order contents are not visible from the two activity names alone.
- **Likely DFG**
  - Start: `Pack Package`
  - `Pack Package  Dispatch Package`
  - End: `Dispatch Package`
- **Likely log skeleton**
  - One packing before one dispatch for each package.
- **Misleading interpretations**
  - P1 and P2 appear structurally identical, although P1 combines O100 and O200 while P2 belongs only to O100.
  - Dispatch is not proof of confirmed delivery.

### Delivery flattening

- **Trace shape**
  - D1: `Dispatch Package  Confirm Delivery`
  - D2: `Dispatch Package  Confirm Delivery`
- **Copied shared events**
  - No event is shared between D1 and D2.
  - E09 and E10 also appear in the Package flattening because they directly involve both object types.
- **Omitted lifecycle aspects**
  - Packing, order composition, invoicing, payment, and closing are absent.
- **Likely DFG**
  - Start: `Dispatch Package`
  - `Dispatch Package  Confirm Delivery`
  - End: `Confirm Delivery`
- **Likely log skeleton**
  - Dispatch precedes confirmation once for each delivery.
- **Misleading interpretations**
  - The model correctly shows that D2 takes much longer to confirm than D1, but it cannot explain whether the delay is caused by P2, O100, the carrier, or another factor.

### Invoice flattening

- **Trace shape**
  - V1: `Issue Invoice  Record Payment  Record Payment`
- **Copied shared events**
  - There is only one Invoice object, so no event is copied between multiple Invoice cases.
  - E11 is reused in the Order flattening; E12 and E15 would also be reused in a Payment flattening.
- **Omitted lifecycle aspects**
  - Delivery confirmations and order closures are absent.
  - The DFG does not use the 100 and 150 payment amounts, even if those attributes remain on the flattened events.
- **Likely DFG**
  - Start: `Issue Invoice`
  - `Issue Invoice  Record Payment`
  - `Record Payment  Record Payment`
  - End: `Record Payment`
- **Likely log skeleton**
  - One invoice issuance followed by two payment records.
- **Misleading interpretations**
  - The `Record Payment  Record Payment` edge does not mean that one payment was repeated or corrected; it represents distinct M1 and M2 events.
  - Sequence alone cannot establish which part of the payment belongs to O100 or O200.
  - The flattening generally does not expose the `partially_settles` versus `completes_settlement` O2O distinction.

### Why Payment flattening is especially weak

Payment flattening produces two singleton traces:

- M1: `Record Payment`
- M2: `Record Payment`

There are no directly-follows edges, no invoice issuance in either trace, and no order allocation. The amounts 100 and 150 may survive as event attributes, but traditional DFG and log-skeleton discovery do not use them to reconstruct V1’s balance. The object-centric representation is therefore much stronger for payment analysis than a Payment-flattened log.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG should expose different per-object-type behavior without splitting the OCEL into unrelated source logs:

- **Order:** the O100 and O200 paths shown in Section 4, including repeated Add/Pack activities for O100.
- **Item:**
  - I1 and I3: `Add Item  Reserve Stock  Pack Package`
  - I2: `Add Item  Pack Package`
- **Package:** `Pack Package  Dispatch Package` for P1 and P2.
- **Delivery:** `Dispatch Package  Confirm Delivery` for D1 and D2.
- **Invoice:** `Issue Invoice  Record Payment  Record Payment` for V1.
- **Payment:** only singleton `Record Payment` occurrences for M1 and M2.

P1 is the logistics convergence point for O100 and O200, while V1 is the financial convergence point. M1 and M2 create the Invoice-level payment sequence, but the Payment object type itself has no internal sequence.

### OTG

The object-type graph should show the structural neighborhoods among object types. If it is based on O2O, the main structure is:

`Delivery — Package — Item — Order — Invoice — Payment`

If it is based on event co-membership, it should also show direct activity-level neighborhoods such as:

- Order–Item through Add, Reserve, and Pack;
- Order–Package and Item–Package through Pack;
- Package–Delivery through Dispatch;
- Order–Invoice through Issue Invoice;
- Invoice–Payment through Record Payment.

In either interpretation, P1 and V1 are instance-level bridges. An OTG generally does not encode timestamp ordering or the fact that D1 is confirmed before D2.

### ET–OT graph

The expected bipartite event-type/object-type associations are:

| Event type | Object types |
|---|---|
| Create Order | Order |
| Add Item | Item, Order |
| Reserve Stock | Item, Order |
| Pack Package | Package, Item, Order |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery |
| Close Order | Order |

This makes the convergence activities easy to identify: Reserve Stock, Pack Package, and Issue Invoice span multiple object types. It also makes clear that there is no direct Order–Delivery or Order–Payment event participation in the chosen model.

### Object-centric Petri net

The object-centric Petri net should suggest typed synchronization points:

- A packing transition synchronizes a Package token with Item and Order tokens. For P1, E07 involves I1, I3, O100, and O200 together.
- Dispatch synchronizes P1 with D1 and P2 with D2.
- Issue Invoice synchronizes V1 with O100 and O200.
- Each Record Payment transition synchronizes one Payment token—M1 or M2—with V1.
- Delivery confirmations can be asynchronous: D1 is confirmed on 2026-04-06, while D2 is confirmed the following morning.
- M1 occurs before either confirmation, while M2 occurs after both confirmations and before either order closes.
- O200 closes five minutes before O100.

The exact arc cardinalities, concurrency, routing constructs, and treatment of repeated activities depend on PM4Py’s discovery algorithm and parameters. The object-centric Petri net therefore does **not** have one uniquely determined interpretation.

### Object-interactions summary

The exact output schema can vary by PM4Py release, but it should highlight:

- E07 as the largest interaction: P1, I1, I3, O100, and O200.
- E06 as a four-object interaction between I1, I3, O100, and O200.
- E11 as the V1/O100/O200 financial interaction.
- E12 as M1–V1 and E15 as M2–V1.
- E09 and E10 as Package–Delivery interactions.
- E13 and E14 as singleton direct-E2O events, even though D1 and D2 have static O2O links to packages.

The summary should show that M1 and M2 do not interact directly with each other; they are connected through their separate events against V1.

## 6. Modeling alternatives

### 1. Strict source-minimal relations

Only objects explicitly recorded by the source event are linked. Under an especially strict version, E08 would link only P2 and I2, omitting O100 unless the source explicitly records the order.

- **Discovery effect:** Order traces become shorter and may omit P2 packing. Logistics and finance appear fragmented.
- **Benefit:** every E2O row has direct source evidence.
- **Cost:** important operational scope is left to downstream joins and can be overlooked.

The implemented model is source-scoped but declares packing’s order fulfillment scope explicitly.

### 2. Full operational involvement

Every operationally affected object is directly linked. For example:

- E09 would link P1, D1, I1, I3, O100, and O200.
- E13 would link D1, P1, I1, I3, O100, and O200.
- E12 and E15 could link M1/M2, V1, O100, and O200.

- **Discovery effect:** Order flattening becomes nearly end-to-end and includes dispatch, delivery, and payment.
- **Benefit:** no manual transitive traversal is needed for order-centric analysis.
- **Cost:** the OC-DFG and Petri net become denser and may suggest synchronization that was never directly observed.

### 3. O2O-propagated analytical relations

The canonical E2O table remains source-scoped, but a separate analytical relation layer is derived by traversing O2O. For example, D1 confirmation can be propagated through `D1  P1  I1/I3`, followed by reverse traversal of `O100/O200  I1/I3`.

- **Discovery effect:** configurable propagation depth can create Order, Item, Package, or Delivery views with selected lifecycle context.
- **Benefit:** provenance remains explicit if propagated rows use `derived:` qualifiers.
- **Cost:** if copied into the canonical `relations` table without labeling, inferred participation becomes indistinguishable from source evidence.

### 4. Primary-object-only policy

Each event receives one principal object: packing belongs to Package, dispatch to Delivery or Package, invoicing to Invoice, and payment to Payment.

- **Discovery effect:** flattened traces become extremely sparse and shared operational events largely disappear.
- **Benefit:** very little relation inflation.
- **Cost:** it poorly represents E06, E07, and E11, whose multi-object nature is central to the process.

### 5. Explicit financial allocation

If remittance rules were known, M1 and M2 could be linked to O100 and O200 using allocated amounts.

- **Discovery effect:** Order flattening includes payments and can compare order-level settlement timing.
- **Benefit:** financially complete order views.
- **Cost:** without actual allocation rules, this falsely distributes M1’s 100 units and M2’s 150 units between O100 and O200.

None of these alternatives changes the 17 business events or the stated object structure; they change which participation relationships are asserted or derived.

## 7. Failure modes

1. **Relation inflation**  
   Linking every downstream event to every ancestor makes Order traces appear complete, but it can create unsupported synchronization and inflated activity frequencies. For example, directly linking E13 to both O100 and O200 would make one D1 confirmation look like an explicit two-order event.

2. **Missing direct E2O links**  
   The chosen source-scoped policy omits delivery and payment from Order flattening. A user might incorrectly conclude that O100 or O200 was never delivered or paid.

3. **Treating O2O propagation as observation**  
   A transitive path from D1 to O100 is analytically useful, but it is not evidence that the source system directly recorded O100 in E13. Propagated rows need separate names or qualifiers.

4. **Duplicate shared events after flattening**  
   E06, E07, and E11 are copied into both Order traces. Summing events across flattened logs would count these shared occurrences twice even though the OCEL contains each only once.

5. **Ambiguous payment allocation**  
   V1 bills both O100 and O200, but there is no rule allocating M1’s 100 units or M2’s 150 units to either order. Even the assumed `completes_settlement` label does not provide order-level allocation.

6. **Overly short Payment traces**  
   M1 and M2 flatten to singleton traces. Such a log has no meaningful DFG edges and cannot explain invoice issuance, settlement progress, or order allocation.

7. **Constructor or API version mismatch**  
   PM4Py releases may move the OCEL class, alter constructor keywords, or change flattening semantics. The constructor is isolated in the pipeline so the semantic tables can remain unchanged.

8. **False total order for same-time events**  
   This example has no timestamp ties, so timestamp sorting is unambiguous. In a larger log, equal timestamps should not be ordered arbitrarily by event ID or input position because that can introduce unsupported DFG edges.

9. **Timezone normalization errors**  
   Mixed aware and naive timestamps, or conversion to a local timezone, can reorder events. The input uses UTC-aware timestamps consistently.

10. **Treating static O2O as temporal**  
    The row `P1 packs I1` has no timestamp. It should not be interpreted as true before E07 or after order closing unless a validity interval is added.

11. **Ignoring qualifiers during discovery**  
    Traditional DFGs generally use only activity names. `Record Payment  Record Payment` therefore hides the distinction between M1, M2, partial settlement, and completion.

12. **Non-global object identifiers**  
    If two object types reused an ID such as O100, E2O and O2O references would become ambiguous. The validation requires object IDs to be globally unique.
