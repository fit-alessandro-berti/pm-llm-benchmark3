## 1. Interaction-graph description

The system is best modeled as a typed, multi-relational interaction graph in which nodes carry an object type and edges carry a qualifier plus (where known) a shared event and timestamp. The six jobs look independent when projected onto a single object type, but they are stitched together through *shared* non-Job objects. The coupling lives in those shared nodes, not in the Job-to-Job edges (of which there are none).

**Important node types.** Job (J1–J6), Component (C1–C6), ComponentLot (L7, L8), Machine (CNC-2, OVEN-1, TEST-1), Tool (FIX-A, RACK-7, CAL-3), Batch (B1, B2), Shipment (S1, S2, S3). Machines, Tools, Lots, Batches, and Shipments are the "coupling" node types because each touches multiple Jobs.

**Important edge types and qualifiers.**
- `Job –requires→ Component` (O2O, structural, one-to-one here).
- `ComponentLot –contains→ Component` (O2O; L7⊇{C2,C5}, L8⊇{C1,C3}). This is the hidden channel that links J2↔J5 and J1↔J3 through material provenance.
- `Batch –batches→ Job` (B1⊇{J1,J2,J3}, B2⊇{J4,J5}). A batch is a synchronization barrier: its start time is bounded below by the *latest*-ready member.
- `Shipment –consolidates→ Job` (S1⊇{J1,J4}, S2⊇{J2,J3}, S3⊇{J5,J6}). A shipment is a synchronization barrier at the *dispatch* end.
- Event-participation (E2O) edges from shared events to many objects, e.g. the single `Batch Cure` at 12:05 relates to B1, OVEN-1, RACK-7, J1, J2, J3, C1, C2, C3.
- Resource-hold edges inferred from acquire/release: `Job –holds→ Tool` (J3 holds FIX-A 09:00–11:40), `Job –uses→ Machine`, `Batch –uses→ Tool` (both B1 and B2 use RACK-7).

**Three higher-order motifs (each >2 object types).**
1. **Batch-oven-rack barrier**: {J1,J2,J3}–Batch B1–Machine OVEN-1–Tool RACK-7 co-participate in one `Batch Cure` event. Three jobs, one batch, one machine, one tool, three components: a 6+ object hyperedge.
2. **Lot fan-out**: L7–contains–{C2,C5}; C2–required-by–J2; C5–required-by–J5; plus `Quarantine Lot`/`Release Lot` events relating L7,C2,C5,J2,J5. One lot couples two jobs that are otherwise in different batches (J2∈B1, J5∈B2) and different shipments (S2, S3).
3. **Tool-then-machine handoff**: J3–holds–FIX-A (09:00–11:40) while J4–uses–CNC-2 and also needs FIX-A; the `Machine Process` for J4 relates J4,C4,CNC-2,FIX-A. Job, Tool, Machine, Component in one contention chain.
4. **Shipment-cross-batch coupling** (bonus): S1 consolidates J1 (∈B1) and J4 (∈B2); the dispatch barrier links jobs from two different batches and two different lots.

**Direct observations vs. inferred.**
- *Direct*: all O2O relations; batch-cure timestamps and readiness times (B1 table, B2 text); FIX-A acquire 09:00 / release 11:40; CNC-2 idle 10:05–10:47; CAL-3 recalibration 16:35–17:20 and test windows; pack times 13:30 (J1) and 19:10 (J4); dispatch S1 19:25; RACK-7 "cleaning/quarantine until 14:35"; `Quarantine Lot` 10:20 and `Release Lot` 13:50.
- *Inferred*: tool holds derived from acquire/release; that J4's wait is *caused* by FIX-A (no explicit `Wait for Tool` activity exists); that batch waiting equals ready-to-start gap ("if readiness is trusted"); the J2/J5 lot linkage (an "alternative integration pipeline would relate these events"); any waiting derived from machine-event gaps.

**Compact edge-list.**
```
J1 requires C1 ; J2 requires C2 ; J3 requires C3 ; J4 requires C4 ; J5 requires C5 ; J6 requires C6
L7 contains C2 ; L7 contains C5 ; L8 contains C1 ; L8 contains C3
B1 batches J1,J2,J3 ; B2 batches J4,J5
S1 consolidates J1,J4 ; S2 consolidates J2,J3 ; S3 consolidates J5,J6
BatchCure@12:05 -> {B1,OVEN-1,RACK-7,J1,J2,J3,C1,C2,C3}
BatchCure@14:50 -> {B2,OVEN-1,RACK-7,J4,J5,...}
J3 holds FIX-A [09:00,11:40] ; J4 uses CNC-2+FIX-A (MachineProcess@11:45)
QuarantineLot@10:20 -> {L7,C2,C5,J2,J5} ; ReleaseLot@13:50 -> {L7,C2,C5,J2,J5}
FinalTest needs CAL-3 ; CAL-3 recal [16:35,17:20]
```

## 2. Quantitative delay decomposition

Every figure below is a *counterfactual-conditional* quantity, not proof of cause.

**(a) B1 synchronization waiting for J1.** Counterfactual: if J1 could have cured the instant it was ready and readiness timestamps are trusted. J1 ready 08:10, cure 12:05 → **3 h 55 min** of waiting attributable to the batch barrier. Of this, only the span until the last member's readiness (J3 at 11:55) is *pure synchronization*; 08:10→11:55 = 3 h 45 min is "waiting for slowest sibling," and 11:55→12:05 = 10 min is oven/loading latency shared by all.

**(b) B1 synchronization waiting for J2.** Same assumption. J2 ready 08:25, cure 12:05 → **3 h 40 min**. Note the lot caveat: the `Release Lot` for L7 is 13:50, *after* the 12:05 cure, yet J2 cured early via a **supervisor override** recorded in a separate system. So J2's true "avoidable" wait is bounded by policy, not material: its 3 h 40 min is genuine batch-sync waiting, but it also silently bypassed a quarantine that held J5.

**(c) FIX-A delay for J4.** Counterfactual: if a second FIX-A (or earlier release) existed, J4's `Machine Process` could have begun when the machine was free. J4 reached CNC-2 at 09:50; CNC-2 was idle 10:05–10:47; FIX-A released by J3 at 11:40; J4 machining started 11:45. Plausible fixture-attributable delay = start − arrival = 11:45 − 09:50 = **1 h 55 min**. A tighter lower bound uses the fixture release: 11:45 − 11:40 = 5 min is unavoidable handoff, so **≈1 h 50 min** is plausibly fixture-blocked. Caveat: the 10:05–10:47 idle (42 min) shows the machine was *not* the constraint; but there is no `Wait for Tool` event, so causality is inferred, not recorded.

**(d) S1 consolidation delay for J1.** Counterfactual: if J1 could ship alone (or with an already-ready partner). J1 packed 13:30; S1 dispatched 19:25 → **5 h 55 min** of finished-goods dwell, driven by J4 (packed 19:10) + 15 min consolidation (19:25 − 19:10). So ≈5 h 40 min of J1's dwell is "waiting for shipment partner J4," and 15 min is create/load/dispatch latency. This dwell is *invisible* in the shipment flattening, which only measures Create→Load→Dispatch.

**(e) CAL-3 delay for J6.** Counterfactual: if CAL-3 recalibration were not interposed between J5 and J6, or a second calibration tool existed. J6 ready 16:05; TEST-1 idle 16:35–17:25; J6 tested 17:25. Plausible CAL-3-attributable delay = 17:25 − 16:05 = **1 h 20 min**. Decompose: J5 occupied TEST-1 until 16:35 (25 min of J6's wait is machine occupancy), recal 16:35–17:20 (45 min), then 17:20→17:25 = 5 min handoff. So **≈45 min** is specifically the recalibration barrier and 25 min is ordinary queueing behind J5.

**(f) B2 rack-availability delay (bonus).** OVEN-1 idle 12:55–14:50 (1 h 55 min) but RACK-7 in cleaning/quarantine until 14:35. J5 ready 14:40, B2 starts 14:50. Counterfactual: with a spare rack, B2 could have started when its last member (J5) was ready → best case ~14:40+load. The oven's idleness (115 min) is *tool-caused*, not capacity-caused: rack release at 14:35 gates the batch, not the oven. J4 (ready 13:10) waited 14:50 − 13:10 = **1 h 40 min**, of which the 13:10–14:35 span (1 h 25 min) overlaps rack unavailability.

## 4. What flattening misses

**Job viewpoint.** *Visible*: per-job activity sequence, rework loop (Inspect→Rework, 2×), that no job is >1.8σ from mean. *Hidden/duplicated*: it drops the `Batch Cure`, `Quarantine Lot`, `Release Lot`, and shipment-partner waits because they are shared events not "directly related to the Job at source." *Misleading conclusion*: "throughput is balanced; no bottleneck," when 3h40–3h55 of B1 waiting is simply not modeled.

**Machine viewpoint.** *Visible*: utilization and longest event gap (OVEN-1 73 min). *Hidden*: waiting that occurs *off-machine* (jobs queued waiting for a tool or lot). It also can *duplicate* a shared cure event across the machine timeline vs. the batch timeline. *Misleading conclusion*: "OVEN-1 at 44% has spare capacity"—true for the oven, false for flow, since the constraint is RACK-7 and member readiness.

**Batch viewpoint.** *Visible*: the synchronization barrier and per-member wait (the B1 table). *Hidden*: *why* the last member was late (lot quarantine, tool). *Misleading conclusion*: "shrink batches"—but B2 shows the gate was RACK-7 cleaning, not batch size.

**Tool viewpoint.** *Visible*: hold intervals (FIX-A 09:00–11:40), rack cleaning windows, CAL-3 recal. *Hidden*: which *job* was blocked (no `Wait for Tool` event) so blame is inferred. *Misleading conclusion*: "FIX-A utilization is fine" while it silently serializes J3 then J4.

**ComponentLot viewpoint.** *Visible*: quarantine/release lifecycle and the L7↔{J2,J5} coupling. *Hidden*: it is "inconsistently linked to jobs," so counts (Job–ComponentLot = 4) understate impact; J2's override is in another system entirely. *Misleading conclusion*: "lots don't affect jobs" because Job flattening never sees them.

**Shipment viewpoint.** *Visible*: Create→Load→Dispatch timing (fast: 0.8h+0.3h). *Hidden*: how long an already-packed job (J1) waits for a partner (J4). *Misleading conclusion*: "shipping is efficient (1.1h)" while J1 actually dwelt ≈5h55.

**Why low utilization + long waiting coexist.** Utilization measures a *resource's* busy fraction; job waiting is a *flow* property created by synchronization barriers (batch, shipment) and *serialized secondary resources* (single FIX-A, single RACK-7, single CAL-3). A resource can sit idle (OVEN-1 12:55–14:50) precisely because a *different* shared object (RACK-7 cleaning until 14:35) blocks the work. Idle machines and long queues are two symptoms of the same coupling, not a contradiction.

## 5. Object-lifecycle evidence

**Narrative A — J4 through Tool, Machine, Batch, Shipment.**
- *Temporal precedence*: J4 arrives CNC-2 09:50; CNC-2 idle 10:05–10:47; J3 releases FIX-A 11:40; J4 machines 11:45; later J4 packed 19:10; S1 dispatch 19:25.
- *Resource feasibility*: only one FIX-A exists; J3 held it; J4 could not machine without it. RACK-7 also gated B2 (cleaning until 14:35).
- *Policy constraint*: J4 must ship with J1 in S1 (consolidation rule).
- *Causal speculation*: FIX-A *likely* caused ~1h50 of J4's delay, but the machine's own idle window shows the fixture, not CNC-2, was the constraint—unprovable without a `Wait for Tool` record.

**Narrative B — J5 through ComponentLot, Batch, Machine, Tool, Shipment.**
- *Temporal precedence*: L7 quarantined 10:20; released 13:50; J5 ready-for-batch 14:40; B2 cure 14:50; J5 final test 16:10–16:35; S3.
- *Resource feasibility*: C5∈L7, so J5 physically cannot proceed while L7 is quarantined; RACK-7 also needed for B2.
- *Policy constraint*: quarantine hold on L7; J5 (unlike J2) did **not** get a supervisor override; S3 consolidates J5+J6.
- *Causal speculation*: the lot quarantine *plausibly* set J5's whole downstream chain late, but because lot events are inconsistently linked to jobs, the Job view attributes J5's lateness to nothing at all.

**Narrative C — J1 through Batch, Machine, Tool, Shipment (+Lot).**
- *Temporal precedence*: J1 ready 08:10; B1 cure 12:05 (with OVEN-1, RACK-7); J1 packed 13:30; S1 dispatch 19:25.
- *Resource feasibility*: C1∈L8 (not quarantined), so material was fine; J1's delay is barrier-driven, not material-driven.
- *Policy constraint*: batch B1 (wait for J3 readiness 11:55) then shipment S1 (wait for J4).
- *Causal speculation*: J1 is "double-synchronized"—penalized once at the batch entry (3h55) and again at the shipment exit (5h55 dwell), *neither* visible in the Job flattening. The compounding is the strongest example of cross-instance coupling.

## 6. Intervention portfolio and spillovers

**I1 — Reduce synchronization: dynamic/smaller cure batches (split B1 by readiness).**
- Target: batch synchronization. Benefit: J1/J2 avoid ~3h40–3h55 waiting behind J3.
- Helped: early-ready jobs (J1,J2,J4). Harmed: oven throughput; more cures raise OVEN-1 load and RACK-7 turnovers (rack is already a gate).
- Cost/risk: energy per cure, more RACK-7 cleaning cycles. Perverse metric: "average batch wait" improves while total oven hours and rack contention worsen.
- OC evaluation: compare Batch–Job per-member wait distribution *and* Batch–Tool interaction count before/after; watch RACK-7 cleaning frequency.

**I2 — Address tools: add a second FIX-A (and a spare RACK-7).**
- Target: shared-tool contention. Benefit: J4 saves ~1h50; B2 no longer gated by rack cleaning (saves J4/J5 up to ~1h25).
- Helped: J4,J5. Harmed: capital budget; possibly J3 loses priority claim.
- Cost/risk: tool purchase, calibration/quarantine for the new rack. Perverse metric: "tool utilization" *drops* (looks worse) even though flow improves.
- OC evaluation: Job–Tool interaction timing (acquire→use gap) and Batch–Tool availability windows pre/post.

**I3 — Shipment policy: allow single-job or ready-partner dispatch (cutoff-based release).**
- Target: shipment consolidation. Benefit: J1 avoids ≈5h40 finished-goods dwell.
- Helped: early-packed jobs (J1). Harmed: freight cost/consolidation savings; more shipments.
- Cost/risk: higher logistics spend. Perverse metric: "Create→Load→Dispatch time" stays great while shipment *count* and cost balloon—optimize the wrong KPI.
- OC evaluation: Shipment–Job "packed-to-dispatch dwell" per job (a new derived metric), not the existing Create→Load→Dispatch DFG.

**I4 — Improve logging (not operations): add explicit `Wait for Tool`, `Quarantine/Release Lot→Job` links, and packed-to-dispatch events.**
- Target: data-integration artifacts. Benefit: converts inferred delays into measured ones; lets J2/J5 lot coupling and J4 fixture wait appear in Job views.
- Helped: analysts, all future root-causing. Harmed: none operationally.
- Cost/risk: instrumentation effort; the supervisor-override side system must be integrated. Perverse metric: "number of logged waits" could be gamed to look busy.
- OC evaluation: recompute Job flattening after re-integration; check that previously-missing events now attach to J2,J5,J4.

**I5 — Reduce serialization on CAL-3: pre-stage a second calibrated tool or schedule recal off the critical path.**
- Target: tool/maintenance serialization. Benefit: J6 saves ≈45 min recal wait.
- Helped: tail jobs (J5,J6). Harmed: maintenance cadence/quality risk if recal is deferred.
- Cost/risk: second CAL-3 or calibration slippage. Perverse metric: "TEST-1 utilization" rises but test *quality* (calibration currency) could silently degrade.
- OC evaluation: Tool–Job (CAL-3) inter-test gap and recal placement relative to job readiness.

**I6 (bonus) — De-quarantine faster / segregate lots: expedite L7 release or single-source components per job.**
- Target: component-lot coupling. Benefit: J5 no longer chained to L7 timing; removes the incentive for risky supervisor overrides (as J2 used).
- Helped: J2,J5. Harmed: quality assurance rigor (quarantine exists for a reason).
- Cost/risk: quality escapes. Perverse metric: "lot release time" pressure could cause premature release.
- OC evaluation: ComponentLot–Job event linkage and override frequency pre/post.

## 8. Falsification and additional data

**Six observations that would weaken the top-ranked (batch synchronization) explanation.**
1. Readiness timestamps are unreliable (e.g., "ready 08:10" is a scheduling placeholder, not a physical state)—then the 3h55 is an artifact.
2. OVEN-1 requires a minimum fill or a fixed cure schedule, making 12:05 the earliest *feasible* start regardless of members → the wait is capacity/policy, not synchronization.
3. Splitting B1 in a historical case showed *no* throughput gain (jobs still late) → barrier wasn't binding.
4. J3's late readiness (11:55) is itself caused by the L8 lot or FIX-A, meaning lot/tool is upstream and batch is a symptom.
5. Per-member waits are uncorrelated with batch membership across many days → synchronization is not systematic.
6. The oven can cure jobs individually at similar cost/time, i.e., batching is a reporting convention, not a physical constraint.

**Six additional fields/event types that would discriminate among hypotheses.**
1. Explicit `Wait for Tool` (with job, tool, start/end) — separates fixture contention (rank 2) from machine capacity (rank 6) for J4.
2. Consistent `Quarantine Lot`/`Release Lot → Job` linkage — turns rank 3 from inferred to measured for J2/J5; integrates the supervisor-override side system.
3. Oven minimum-batch / cure-schedule constraint field — tests whether B1's 12:05 was policy-forced (falsifier #2).
4. Packed-to-dispatch per-job timestamps in the shipment log — quantifies rank 4 dwell (J1's 5h55) directly instead of via pack/dispatch subtraction.
5. RACK-7 and CAL-3 availability/maintenance calendars with reason codes — attributes OVEN-1 idle (12:55–14:50) and TEST-1 idle (16:35–17:25) to tools vs. capacity.
6. Job priority / due-date and readiness-provenance fields — distinguishes genuine physical readiness from scheduling placeholders (falsifier #1) and reveals whether "waiting" is intentional sequencing.

Additional useful fields: setup-vs-run split on CNC-2 (to interpret 10:05–10:47 idle), lot single-sourcing flags, and a shipment cutoff/SLA field to judge whether consolidation dwell is intentional.
