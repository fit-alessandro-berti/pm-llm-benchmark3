# Simulation-Based Digital Twin for the Municipal Building-Permit Process

## 1. Model scope and state variables

### 1.1 Twin boundary

**Inside the boundary**

- The permit lifecycle from portal submission to `Issue permit` / `Reject application`, including all rework loops (completeness, inspection, legal, appeal).
- Municipal resource pools with calendars: clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, schedulers, plus "system" (unlimited).
- Queues in front of every human activity, with queue discipline and prioritization rules (a policy lever, D6).
- Applicant and third-party (consultant, objector) response processes, modeled as *delay servers* with their own heavy-tailed distributions, explicitly **not** consuming municipal capacity.
- Cross-case coupling: architect submission bursts, district inspection batching, neighborhood objections spanning related cases, council-meeting calendar shocks that block many cases simultaneously.
- Non-stationary arrivals: seasonal (Mar–May, Sep–Nov at 1.7×), weekday (Mon 2.2× Wed), and burst structure from the top-20 architects.

**Outside the boundary (exogenous inputs, not simulated endogenously)**

- Macroeconomic drivers of construction demand — represented by scenario multipliers on the arrival intensity rather than a causal submodel.
- Court appeals after final rejection, HR hiring pipelines, and IT platform failures — entered as stress scenarios.
- Emergency decisions removed from the log — see §3.9; modeled only as a small unmodeled-load allowance.

### 1.2 Level of detail

A **discrete-event, resource-constrained, activity-level** model. One simulated event = one activity instance (start, end) plus explicit queue-entry timestamps. This is deliberately *finer* than the log, because the log frequently lacks start timestamps: the simulator generates the (queue-entry, start, complete) triple, and only the observable projection (complete timestamps, plus starts where available) is compared to reality during validation. Sub-activity detail (e.g., individual document fields) is out of scope; it does not affect any of D1–D10 except D1, where it is abstracted into a "submission completeness quality" scalar.

### 1.3 Entities

| Entity | Key attributes |
|---|---|
| `Case` (permit application) | `case_id`, `case_type` ∈ {Simple renovation, New residential, Commercial, Complex variance}, `district` ∈ {D1..D5+}, `architect_id`, `application_value`, latent `building_area`, latent `env_sensitive`, `requires_fire`, `requires_environment`, `requires_public_notice`, `prior_violations` (latent, D2), `submission_quality` (latent, drives missing-doc loop), `objection_flag` (latent, drives notice length), `arrival_time`, `sla_clock`, `rework_counts` per loop, current marking/state |
| `Architect` | `architect_id`, size class (top-20 vs. tail), burst process state, portfolio of open cases |
| `District` | travel-time matrix entry, environmental-sensitivity propensity, objection propensity, batching group |
| `Bundle` | set of cases eligible for a batched inspection trip; formation window, district, inspector assignment |
| `ObjectionEvent` | latent entity attached to a public-notice period, possibly linked to several cases in the same neighborhood/window |
| `ResourcePool` / `ResourceUnit` | pool id, FTE, calendar, skill/eligibility set, non-permit reservation fraction |
| `WorkItem` | (case, activity) pair with `enqueue_time`, `start_time`, `complete_time`, `resource`, priority key |

### 1.4 State variables

**Per case:** current control-flow marking (a token multiset over the process-tree/Petri-net semantics — important because the `+(...)` block means Planning / Fire / Environmental can be concurrently enabled), set of *completed review obligations*, `pending_reviews` counter used to gate `Decision drafting`, rework counters, elapsed calendar time, elapsed *working* time, and a flag for whether the case is currently blocked on an applicant/third party rather than on the municipality (critical for fair SLA measurement).

**Per queue:** ordered work-item list, length, age of oldest item, and per-case-type composition.

**Per resource pool:** number of units on-shift now, number busy, per-unit remaining shift time, non-permit reservation consumption (environmental reviewers), current geographic position/route load (inspectors).

**Global:** simulation clock, calendar object (weekday, holiday, council-meeting week), current seasonal intensity multiplier, backlog by activity and case type, in-progress WIP, and the active experiment configuration.

### 1.5 Resources, queues and calendars

- **Clerks**: 5 FTE, Mon–Fri 08:00–16:00; on Mondays one clerk is withdrawn to portal support → effective 4 FTE on the day with the highest arrivals. This interaction (peak demand ∧ reduced capacity) is a first-order driver of the completeness-check waiting spike and must not be averaged away.
- **Planners**: 8 FTE, Mon–Fri 09:00–17:00, with a *skill constraint*: 2 planners serve only Simple renovation. Modeled as an eligibility matrix, not a single pool. D6 converts one general planner into a daily "aging-case" server with a priority queue.
- **Fire reviewers**: 2 FTE, Tue–Thu only → a 3-day service window inside a 7-day cycle; queue drains in bursts, so waiting has a sawtooth pattern, not an exponential one.
- **Environmental reviewers**: 3 FTE Mon–Fri with 40% of capacity reserved for non-permit duties. Model as 3 units with a *preemptive-resume reservation calendar* (or equivalently 1.8 effective FTE with correct variance) — the two are **not** equivalent for tail behavior, so use explicit reservation blocks.
- **Inspectors**: 4 FTE, field Tue–Fri; service = travel + on-site. Travel drawn from a district-pair matrix with D3/D5 inflation; batching reduces per-case travel but delays the first case in a bundle.
- **Legal officers**: 2 FTE, blocked during council-meeting weeks except urgent cases → a calendar with recurring full-week outages, producing the long Complex-variance tail.
- **Schedulers**: small pool; service is short (20 min) but they are the control point for batching (D3).
- **System**: infinite server, near-zero service time.
- **Applicant / third party**: infinite-server delay stations with heavy-tailed delays (`Receive missing documents`, consultant reports, objection filing). Never consume municipal FTE.

Queue discipline: FIFO by default within (activity, eligible pool), with configurable priority keys (case type, age, SLA slack) so that D6 and prioritization stress tests are one-line configuration changes.

### 1.6 Cross-case dependencies (explicitly modeled)

1. **Architect bursts** — arrivals are *not* a plain non-homogeneous Poisson process. Top-20 architects generate correlated batches: a Markov-modulated / cluster (Neyman–Scott-style) arrival process where an architect "burst event" spawns *k* correlated applications in the same week, same district, same case type with high probability. This inflates queue variance far beyond Poisson and is the main reason D7 (appointment slots) can help.
2. **Inspection batching** — a bundle-formation policy: when ≥2 open cases share district and are inspection-ready within a window *W*, they may be grouped. Payoff = shared travel; cost = the earliest-ready case waits up to *W*. This creates a genuine coupling of case sojourn times and is the whole content of D3.
3. **Neighborhood objections** — an objection is a latent event attached to a (district, time-window) neighborhood. When triggered, it can extend the public-notice period for *all* concurrent related cases, and can trigger legal rework. This is a shared-shock dependency, not an i.i.d. per-case coin flip.
4. **Shared calendar shocks** — council-meeting weeks and holidays simultaneously freeze legal checks and notice periods across all cases, synchronizing backlog build-up and release.
5. **Shared resource contention** — the ordinary but essential coupling: Commercial cases occupying legal officers delay Complex-variance cases (the "legal and environmental queues interact" note).

## 2. Parameter-estimation plan

### 2.1 Role of PM4Py vs. the simulation engine

PM4Py is used for **log ingestion, conformance, model handling, and descriptive statistics**; it is *not* used as the simulation engine. Concretely:

- `pm4py.format_dataframe(df, case_id='case:concept:name', activity_key='concept:name', timestamp_key='time:timestamp')` to normalize the DataFrame; `pm4py.convert_to_event_log` when an object-based API is needed.
- `pm4py.parse_process_tree(...)` for the process-tree string, then `pm4py.convert_to_petri_net(tree)` to obtain (net, im, fm) for replay.
- `pm4py.get_variants` / `pm4py.get_variants_as_tuples` for variant shares; `pm4py.discover_dfg`, `pm4py.discover_performance_dfg` for frequency and performance edges; `pm4py.discover_petri_net_inductive` on filtered sublogs as a cross-check against the supplied tree.
- `pm4py.conformance_diagnostics_alignments` (or token-based replay) to measure how well the given tree explains the log and to *locate* deviations, which are then treated as candidate model-scope extensions rather than noise.
- `pm4py.get_case_arrival_avg`, `pm4py.get_case_duration` / `pm4py.get_all_case_durations`, `pm4py.get_event_attribute_values` for descriptive inputs.
- `pm4py.filter_event_attribute_values` / `pm4py.filter_time_range` to build per-case-type, per-district and per-period sublogs — every parameter below is estimated **stratified**, never pooled.

The simulator itself is a hand-written discrete-event engine (SimPy or a custom event heap). PM4Py's built-in stochastic Petri-net simulation is intentionally *not* the production engine: it does not represent multi-pool calendars, batching, cross-case shocks, or attribute-dependent routing at the fidelity required here. It may still be used as a sanity baseline for the control-flow-only projection.

### 2.2 Arrivals

- Build a case-level table (first event per case) and fit a **non-homogeneous intensity** λ(t) = λ₀ · s(month) · w(weekday) · h(holiday) using a log-linear Poisson/negative-binomial GLM with month, weekday, and holiday indicators. Negative binomial is preferred over Poisson because architect bursts create over-dispersion; the estimated dispersion is itself a calibration target.
- Separate the **top-20 architect** stream: estimate (i) burst arrival rate per architect, (ii) burst size distribution (zero-truncated geometric/negative-binomial), (iii) within-burst district/case-type concordance. The tail architects are modeled as an ordinary NHPP.
- Validate by comparing simulated vs. observed weekly arrival counts, the Monday/Wednesday ratio (target ≈ 2.2), the season ratio (target ≈ 1.7), and the index of dispersion of weekly counts.
- Case-attribute generation: sample `case_type` from the observed mix (45/28/17/10), then `district`, `application_value`, `requires_*` **conditionally** on case type and architect via an empirical conditional distribution or a small Bayesian network — not independently, since these attributes are strongly correlated.

### 2.3 Service times vs. waiting times (the central measurement problem)

Many activities have only completion timestamps. Therefore the observable quantity is the *inter-completion* gap, which conflates waiting, service, and blocked-on-applicant time. Approach:

1. **Where start timestamps exist** (a resource subset), directly estimate service-time distributions and use them as the reference. Check for selection bias: those resources may be systematically different (newer systems, different activity mix), so compare their case mix to the whole.
2. **Where they do not**, treat service time as latent and estimate it by a **deconvolution / hierarchical Bayesian model**: observed gap = queueing delay (predicted by the simulator's own queue state) + service + calendar downtime. Practically, this becomes a *calibration* step (§2.8): choose service-time parameters so that simulated total gaps match observed gap distributions, with the informative prior coming from the resources that do log starts.
3. **Never** silently assign the entire gap to service time — that would double-count congestion, because the simulator regenerates queueing endogenously. This is the single most common failure mode in permit-process twins and is flagged as a limitation wherever waiting/service split is reported.
4. Fit **right-skewed families** (log-normal, gamma, Weibull; generalized Pareto for the tail above a threshold) to service times, stratified by activity × case type × district where sample size allows (require ≥ ~200 observations per stratum, else pool up a hierarchy with shrinkage). The provided median/p90 pairs are used to seed parameters — e.g. for a log-normal, μ = ln(median) and σ = ln(p90/median)/1.2816 — and then refined against the full empirical distribution.
5. **Calendar-aware durations**: convert wall-clock gaps to *business-time* gaps using the resource calendar before fitting, otherwise weekend/holiday effects are absorbed into the service distribution and then double-counted when the simulator re-applies the calendar.

### 2.4 Waiting times

Waiting is an **output**, not an input. The empirical medians in the brief (1.5d before completeness check, 7d before legal check, etc.) are *validation targets*, not parameters. The only exception is exogenous waiting that is genuinely not queue-driven: fixed public-notice minimum (14d), council-meeting blocking, and applicant response — those are modeled directly.

### 2.5 Branching probabilities

- Estimate routing probabilities **conditionally on case attributes** via logistic regression / decision trees on the case table: P(fire | case_type, value, district, requires_fire), P(environmental | ...), P(public notice | ...), P(legal check | ...), P(reject | ...).
- Because `building_area` and district environmental sensitivity are incomplete, these models will show residual unexplained variation. Represent it as a **latent binary variable with an estimated prevalence** and propagate its uncertainty (§5.5), rather than pretending `requires_fire=yes` is a complete rule.
- Cross-check the fitted routing against `pm4py.get_variants` shares: the simulated variant-share vector should reproduce the 26/19/18/13/8/9/7 table within a tolerance band.

### 2.6 Rework

- Completeness loop: estimate the distribution of the number of `Completeness check` repetitions per case, conditional on architect class and case type. It is not geometric in practice — large architects have systematically lower loop probability — so fit a per-case Bernoulli with covariates plus an overdispersion term; D1's effect is a shift in this covariate model.
- Inspection rework: estimate P(rework | district, case type, inspector) and the number of repetitions from the `*( ->(Inspection scheduling, Site inspection), Inspection rework)` loop counts in the log.
- Legal/appeal rework: rework *reasons* are free text and unreliable, so rework is modeled as an unlabeled hazard, with the caveat that interventions targeting specific rework causes (implicitly D8, D9) cannot be validated against reason codes. This is stated as a known limitation, and a text-coding pilot on a sample of cases is recommended as a data-collection action.

### 2.7 Resource calendars and capacity

- HR-derived calendars are the prior. **Reconstruct an empirical calendar from the log** (`org:resource` × completion timestamp histograms by hour-of-day and day-of-week) and compare. Where they disagree — e.g. fire reviewers show Friday completions despite a Tue–Thu HR calendar — trust the log for *when work happens* and HR for *nominal capacity*, and record the discrepancy as a calibration uncertainty.
- Estimate effective utilization per pool from the log (busy time / available time using inferred service times). If implied utilization exceeds ~1, the service-time estimates are too high or the calendar too narrow — a useful internal consistency check.
- Council-meeting weeks: extract from the municipal calendar (external data) and confirm against a drop in `Legal check` completions.

### 2.8 Dependencies

- **Architect coupling**: measure, per week, the count of applications per architect; estimate burst-size distribution and within-burst attribute concordance. Test for correlation between cases sharing an architect (e.g., correlation of completeness-rework indicators) — this quantifies "submission-quality" as an architect-level random effect.
- **Geographic batching**: detect existing implicit batching by looking for same-inspector, same-district site inspections on the same day; estimate the realized travel saving as the difference in inter-inspection gaps within vs. across districts.
- **Objections**: *not observed*. Estimate a latent mixture on public-notice duration — a point mass near the 14-day minimum plus a heavy-tailed component — and interpret the mixture weight as an *estimate* of objection prevalence with wide uncertainty. Never write "objection occurred" into the log.

### 2.9 Global calibration

After per-component estimation, run a calibration loop (simulated method of moments / approximate Bayesian computation) over the small set of poorly-identified parameters (latent service times, objection prevalence, applicant-response tail index, batching window). The distance function combines: variant shares, median and p90 case duration per variant group, per-activity waiting medians, and resource utilizations. Retain the *posterior sample* of parameters, not a single point estimate, so that intervention comparisons carry parameter uncertainty (§5.5).

## 3. Assumptions

### 3.1 Arrivals
- Arrivals follow a non-homogeneous, over-dispersed process with multiplicative seasonal, weekday and holiday components, plus an additive architect-burst cluster component.
- Seasonality is assumed stable year-to-year over the 18-month window (weakly supported — only ~1.5 seasonal cycles are observed; treated as a sensitivity factor).
- Portal submissions arrive at any hour; the Monday spike is a behavioral effect of applicants, not of municipal opening hours.
- No feedback from municipal performance to arrival rate (no balking/deterrence). Plausible for permits, which are legally mandatory; documented as a structural assumption.

### 3.2 Service times
- Service times are independent given (activity, case type, district, resource pool), right-skewed, and drawn from log-normal/gamma bodies with generalized-Pareto tails.
- Service times are calendar-suspended: work pauses outside shifts and resumes, rather than continuing overnight.
- No learning curve or fatigue effect within the horizon; no systematic speed-up under high load (no "hurrying"). The latter is a known real effect and is tested as a sensitivity.
- Site inspection service = travel + on-site; travel depends on district and, when batched, on route composition.

### 3.3 Routing
- Routing decisions are made at case creation for the deterministic drivers (`requires_fire`, `requires_environment`, case type) and stochastically at the branch point for the incompletely-observed drivers (area threshold, environmental sensitivity), using attribute-conditional probabilities.
- `Decision drafting` is gated on completion of *all applicable* reviews (Planning, Fire, Environmental, Public notice, Inspection) — a synchronization join, not a race.
- The `+(...)` construct is interpreted as true concurrency with independent resource contention, meaning the effective duration of the review block is the maximum of the branch completions, not the sum.
- Reject/issue split depends on case type and prior rework history.

### 3.4 Resources and calendars
- Pools are homogeneous within a skill class except for the explicit planner skill split; individual resource speed differences exist in the data but are absorbed into the service-time variance (documented simplification; per-resource random effects are a sensitivity).
- The Monday clerk withdrawal, fire Tue–Thu window, environmental 40% reservation, inspector Tue–Fri field days, and legal council-week outages are all hard calendar constraints.
- Vacation and sick leave reduce effective FTE by an assumed 10–15% uniformly; this is a calibration parameter, since HR calendars do not capture it.
- No overtime except for a stress scenario; no cross-training except where an intervention introduces it.

### 3.5 Rework
- Rework probability depends on case type, district, architect class, and (for inspection) applicant readiness; it is assumed *not* to increase with the number of prior loops beyond the second loop (weak evidence; sensitivity tested).
- The completeness loop and inspection loop are bounded in the simulator (e.g., max 5 iterations) to prevent non-terminating cases; the truncation rate is reported and must stay far below the observed tail mass.
- Rework causes are unlabeled; interventions cannot be credited with cause-specific reductions beyond what is assumed explicitly.

### 3.6 Applicant / third-party response
- `Receive missing documents` is applicant-driven with a heavy-tailed delay (median 5d, long right tail), modeled as log-normal or Weibull with a shape < 1, plus a small probability of abandonment/withdrawal.
- Applicant response times are longer around holidays and are architect-class dependent (large architects respond faster).
- Consultant reports feeding environmental review are an exogenous delay, not a municipal queue.
- These delays consume no municipal capacity and are **excluded from SLA clocks** under a "stop-the-clock" convention; both stop-the-clock and total-elapsed metrics are reported, because the choice materially changes which intervention looks best (D1 in particular).

### 3.7 Cross-case dependencies
- Architect-level random effects induce correlation in submission quality and rework across a given architect's cases.
- Inspection bundling is only allowed within a district and within a formation window *W*; bundle size is capped by inspector day capacity.
- Objection shocks are neighborhood-and-time correlated, affecting sets of concurrent public-notice cases.
- Cases do not otherwise compete for non-resource entities (no shared physical file, no dependency between a permit and its neighbor's outcome) — a simplification.

### 3.8 Non-stationary demand
- Demand non-stationarity is exogenous and known in the baseline (seasonal multipliers as estimated); scenario runs perturb it.
- Capacity is *not* automatically adjusted to demand in the baseline — the current organization is assumed to run fixed calendars, which is why peak-season backlog accumulates. D4 is precisely the relaxation of this assumption.
- The system does not reach steady state within a year; therefore terminating-simulation methodology with multi-year horizons and seasonal alignment is used, not steady-state analysis (§5).

### 3.9 Missing data
- Missing start timestamps → service/waiting split is *inferred*, with uncertainty carried through; all reported waiting-time results are labeled as model-derived, not measured.
- Objections are **latent**: prevalence and effect are estimated from the public-notice duration mixture and reported with wide credible intervals. D9's benefit is therefore the most uncertain of all interventions and is reported as a range, not a point estimate.
- Removed emergency decisions → the log under-represents load by an unknown small fraction; an assumed 1–3% hidden load is added and varied in sensitivity analysis.
- Incomplete `building_area` / environmental sensitivity → routing has irreducible stochasticity; D8's estimated benefit is conditional on the assumed classifier accuracy, which is itself a factor in the experiment matrix.
- The flattened, case-centric log under-represents dependencies; therefore dependency parameters lean on external knowledge (architect ids, district geography) and are treated as the weakest-identified part of the model.

## 4. Experiment matrix

All experiments use common random numbers (CRN) against the baseline. "Expected trade-off" is a *hypothesis to be tested*, not a claim.

| ID | Scenario | Factors and levels | Primary mechanism | Expected trade-off / risk |
|---|---|---|---|---|
| B0 | **Baseline (as-is)** | calibrated parameters; 2 seeds sets × 30 reps | — | Reference for all comparisons; must pass §6 validation before any comparison is reported |
| B1 | Baseline, no-batching counterfactual | batching ∈ {off} | isolates existing implicit batching | Diagnostic only |
| E1 | **D1 Pre-submission checker** | adoption ∈ {40%, 70%, 95%}; missing-doc-loop reduction ∈ {30%, 55%, 75%}; added applicant pre-effort ∈ {0.5d, 2d, 5d} | fewer completeness loops | Cuts clerk load and the 19% "missing docs" variant, but shifts delay upstream to the applicant; under total-elapsed metrics the gain may largely vanish; risk of excluding low-capability applicants (equity) |
| E2 | **D2 No-inspection for low-risk Simple** | value threshold ∈ {€30k, €50k, €75k}; violation-history availability ∈ {full, partial}; post-hoc audit rate ∈ {0%, 10%} | removes inspection step for ~a large share of the 45% Simple segment | Large median reduction for Simple and inspector capacity freed for others; risk = undetected non-compliance; audit rate must be modeled as a quality cost, not ignored |
| E3 | **D3 District-batched inspection** | window *W* ∈ {2d, 5d, 10d}; max bundle ∈ {2, 3, 5}; districts ∈ {all, D3+D5 only} | travel amortization | Throughput ↑ and D3/D5 waiting ↓, but the first case in each bundle waits longer → tail and fairness may worsen while the median improves |
| E4 | **D4 Temporary peak inspector** | +1 FTE in {Mar–May}, {Mar–May & Sep–Nov}, {all peak + 1 month lag} | capacity added where demand spikes | Directly attacks the seasonal backlog; cost per case avoided is the key metric; risk of ramp-up/onboarding lag (modeled as 3 weeks at 50% productivity) |
| E5 | **D5 Parallel legal pre-check (Commercial, Complex)** | start legal pre-check at {after Planning review, after review block}; pre-check catches {40%, 70%} of legal issues early | removes legal from the critical path | Cuts the 68d/140d variants, but increases legal officer load (some pre-checks are wasted on cases later rejected) → legal utilization may saturate; interaction with council-week outage is the crux |
| E6 | **D6 Reserved planner for aging cases** | age threshold ∈ {30d, 60d, 90d}; reservation ∈ {0.5, 1.0 FTE} | tail-focused prioritization | Compresses p90/p99 and improves fairness, at a small cost to median for fresh cases; classic tail-vs-median trade; risk of starvation oscillation if threshold too low |
| E7 | **D7 Architect appointment slots** | slot coverage ∈ {top-20 only, top-50}; Monday smoothing ∈ {2.2× → 1.5×, → 1.1×} | arrival-variance reduction | Reduces clerk queue spikes with *zero* added capacity — usually high value-per-cost; risk = architect non-compliance, and benefit collapses if adoption is low |
| E8 | **D8 Environmental triage** | classifier sensitivity/specificity ∈ {0.95/0.70, 0.90/0.85, 0.80/0.95} | fewer unnecessary environmental reviews | Cuts the 8d environmental wait, but false negatives = missed environmental risk; must be reported as an explicit error-cost frontier, never as a pure win |
| E9 | **D9 Objection early-warning** | assumed objection prevalence ∈ {low, central, high} (from §2.8 posterior); detection lead time ∈ {5d, 15d}; mitigation effectiveness ∈ {20%, 50%} | shortens the objection-driven notice tail | Potentially large tail benefit for Complex variance, but built on latent, unobserved events → **widest uncertainty band of all interventions**; recommended output is "value of information," motivating objection-event logging |
| E10 | **D10 Combined D1+D2+D3+D4** | each component at its central level; also a 2⁴ fractional design | interaction study | Effects are expected to be **sub-additive**: D2 and D4 both free inspector capacity, so their combination yields less than the sum; must be quantified, not assumed |
| E11 | Combined tail-focused: D5+D6+D9 | central levels | attacks long-duration segments | Tests whether tail interventions compose |
| E12 | Combined front-end: D1+D7 | central levels | attacks arrival/quality variance | Cheapest bundle; likely best cost-effectiveness |
| S1 | **Stress: demand surge** | arrival multiplier ×1.3 and ×1.6 sustained 12 months; peak ratio to 2.2× | capacity shock | Identifies which interventions degrade gracefully vs. collapse; tests for backlog instability (ρ→1) |
| S2 | **Stress: resource loss** | −1 inspector for 3 months; −1 legal officer for 2 months (2 of 2 → 1); both simultaneously | capacity shock | Legal is the thinnest pool (2 FTE + council outages) → likely the fragility point; tests D5's exposure |
| S3 | **Stress: objection wave** | objection prevalence ×3 in two districts for 6 months | correlated shock | Tests D9 and the public-notice submodel; expect Complex-variance p90 blow-up |

Factor levels are crossed only where interactions are plausible (E10's fractional factorial, E1×S1, E4×S1, E3×S2); elsewhere one-factor-at-a-time with CRN keeps the run count tractable.

## 5. Warm-up, replications, and uncertainty treatment

### 5.1 Terminating vs. steady-state framing

Because demand is strongly seasonal and interventions are evaluated over a policy horizon, the model is treated as a **terminating simulation over a 3-year horizon** with seasonally aligned start dates, not as a steady-state study. Reporting is done per rolling 12-month window so that each reported figure spans a full seasonal cycle.

### 5.2 Warm-up / initialization bias

- The system starts non-empty. Two complementary approaches:
  1. **Initial-condition seeding**: initialize WIP from a real snapshot — the actual set of open cases at a chosen date, with their current activity and elapsed time. This is the preferred approach for a digital twin and removes most warm-up bias.
  2. **Warm-up truncation**: additionally discard the first 6 months (chosen via Welch's graphical procedure on backlog and case-duration series, averaged over ≥10 pilot replications, with a moving-average window). Because long cases run 140–260 days, a warm-up shorter than ~2× the p90 Complex-variance duration will bias results downward.
- Report a warm-up sensitivity: results at 4, 6, and 9 months of truncation should agree within the Monte Carlo error.

### 5.3 Run length and replications

- Horizon: 3 years + 6 months warm-up.
- Replications: start with 30 per scenario; then choose *n* by the **sequential precision rule** — continue until the half-width of the 95% CI for the primary metric (mean case duration by case type, and p90 for Complex variance) is below a target (e.g., ≤ 2% of the mean for medians, ≤ 5% for p90). Heavy-tailed p90/p99 metrics typically need 100–300 replications; budget accordingly.
- **Common random numbers** across scenarios, with *separate, dedicated random streams* per stochastic component (arrivals, each service-time distribution, routing, rework, travel, objections, applicant response). Independent streams are essential: without them, an intervention that changes the number of draws in one component desynchronizes all others and destroys the variance reduction.
- Seeds: record a base seed per replication; stream seeds derived deterministically (e.g., counter-based PRNG such as PCG64 `SeedSequence.spawn`) so every run is exactly reproducible and auditable.

### 5.4 Confidence / credible intervals

- Within-parameter (Monte Carlo) uncertainty: replication-based CIs; for differences between scenarios, use **paired** CIs on the per-replication difference under CRN (much tighter than independent CIs).
- Multiple comparisons across 10+ interventions: apply Bonferroni/Holm correction, or better, use **multiple comparisons with the best (MCB)** / ranking-and-selection procedures to identify the subset of interventions that could plausibly be best at a given confidence level, rather than declaring a single winner.
- Parameter uncertainty: propagate the calibration posterior (§2.9) by running the intervention set for each of ~200 posterior draws → **credible intervals** that combine parameter and Monte Carlo uncertainty. Report both: "MC-only" intervals will be much narrower and would be misleading on their own.

### 5.5 Sensitivity analysis

- **Local/OAT** for well-understood parameters (FTE counts, calendar hours, thresholds).
- **Global (Sobol / Morris screening)** over the ~15 most uncertain parameters — latent service-time levels, objection prevalence, applicant-response tail index, rework hazards, hidden-load fraction, batching travel savings — to rank which uncertainties actually drive the intervention ranking. Parameters that dominate variance become data-collection priorities (an explicit **value-of-information** output).
- **Structural sensitivity**: re-run key comparisons under alternative model structures (join semantics for Decision drafting; preemptive vs. non-preemptive environmental reservation; FIFO vs. priority queueing) to show that conclusions are not artifacts of one modeling choice.

### 5.6 Heavy-tailed durations

- Fit tails explicitly: peaks-over-threshold with a generalized Pareto above a chosen threshold (chosen by mean-excess plots), body from a log-normal/gamma. Do **not** rely on empirical resampling alone for the tail — the 18-month log has few extreme cases and bootstrapping cannot generate values beyond the observed maximum.
- Apply a **physically justified truncation** (e.g., statutory maximum decision periods) rather than letting an unbounded Pareto generate absurd durations; report the truncation mass.
- Estimate tail metrics with **quantile estimators plus bootstrap CIs** rather than sample means; report p50/p75/p90/p95 and, where relevant, conditional tail expectation (mean duration of the worst 10%) which is more stable than p99.
- Use **variance reduction targeted at the tail** where feasible (importance splitting for rare long-path cases) and always report the Monte Carlo error on tail statistics — a p90 with a ±25% interval must not be presented as a decision-grade number.

## 6. Validation strategy

### 6.1 Face validation
Structured walkthroughs with clerks, planners, fire/environmental reviewers, inspectors, and legal officers. Present animated case journeys and the queueing story ("Monday spike + one clerk on portal support → 1.5d wait"), and ask specifically about behaviors the log cannot show: informal prioritization, urgent-case handling, when inspectors actually batch, how objections really propagate. Document every disagreement as either a model change or a stated assumption.

### 6.2 Event-log replay validation
- Parse the process tree and convert to a Petri net; run `pm4py.conformance_diagnostics_alignments` on the real log to quantify fitness and to see which deviations the nominal model cannot explain (e.g., emergency decisions, skipped legal checks). Any deviation class exceeding a small share must be added to the simulation model rather than discarded.
- Then run the **reverse check**: replay the *simulated* log against the same net. Simulated traces must be (near-)perfectly fitting by construction, and any deviation reveals an implementation bug in the routing logic. This "simulation-to-model conformance" test is a cheap and effective structural regression test.
- Compare simulated vs. observed **variant shares** and DFG edge frequencies (e.g., cosine similarity of the DFG frequency vectors, and the share of observed DFG edges reproduced).

### 6.3 Distributional validation
- Compare simulated vs. observed distributions of: total case duration overall and per case type; per-variant-group median and p90 against the supplied table (26%/12d/24d, 18%/48d/95d, 8%/140d/260d, etc.); per-activity inter-completion gaps; number of completeness loops; number of inspection loops.
- Use Q-Q plots and two-sample statistics (Kolmogorov–Smirnov, Anderson–Darling for tail sensitivity, Wasserstein distance for a scale-aware summary). With 31,200 cases, formal tests will reject on trivial differences, so the decision rule is based on **effect size** (e.g., relative error of each decile < 10%, p90 within 15%) rather than p-values.
- Validate seasonality: simulated monthly throughput profile vs. observed; Monday/Wednesday arrival ratio; weekly-count over-dispersion.

### 6.4 Resource-utilization validation
- Compare simulated pool utilizations against utilizations implied by the log (inferred busy time / calendar-available time), per pool, per month.
- Check the specific structural signatures: fire-reviewer work concentrated Tue–Thu with sawtooth queue length; environmental effective capacity ≈ 60% of nominal; legal throughput dropping to near zero in council weeks; clerk utilization peaking Monday–Tuesday.
- Cross-check headcount: simulated concurrent-active resources per pool must never exceed FTE on shift.

### 6.5 Bottleneck validation
- Compute a performance DFG (`pm4py.discover_performance_dfg`) on both real and simulated logs and compare the ranking of the slowest edges. The bottleneck *ordering* matters more than absolute values: the model is only useful for intervention comparison if it reproduces which steps dominate delay (currently: applicant response, public notice, environmental and legal waits, inspection waits).
- Verify that the model reproduces known **interaction** bottlenecks — "legal and environmental queues interact" for Commercial, "council calendar dependent" for Complex variance — by checking correlations between queue lengths, not just marginal waits.
- Perturbation test: add 1 FTE to each pool one at a time in the model; the resulting sensitivity ranking should match practitioner intuition about where capacity hurts most. Disagreement is a strong warning sign.

### 6.6 Out-of-sample validation
- **Temporal hold-out**: calibrate on the first 12 months, validate on the last 6 — which happen to include a different seasonal phase. This is the single most important test, because it checks whether the non-stationary structure generalizes rather than being fitted noise.
- **Segment hold-out**: hold out one district (e.g., D5) or one case type from calibration and check predictive accuracy there, testing whether the attribute-conditional structure transfers.
- **Backlog trajectory test**: predict the observed open-case backlog trajectory over the hold-out period from the initial snapshot — a demanding dynamic test that marginal-distribution matching can pass while a structurally wrong model fails.
- **Prospective validation**: after deployment, run the twin forward monthly and score its predictions against realized outcomes (continuous validation), with drift alarms on arrival intensity, case mix, and per-activity waits. A digital twin is only "valid" as of its last recalibration.

**Explicit caveat carried into all reporting:** until B0 passes §6.2–§6.6, no intervention comparison is published. Even afterwards, results are *relative rankings under stated assumptions with uncertainty bands*, never claims of optimality.

## 7. Decision criteria

### 7.1 Primary metrics

| Metric | Definition | Target/threshold |
|---|---|---|
| Median case duration | p50 total elapsed, per case type | Simple ≤ 15d, New residential ≤ 45d, Commercial ≤ 60d, Complex ≤ 120d |
| Tail duration | p90 and p95, per case type; also CTE-10% | p90 improvement ≥ 10% relative to B0 for the target segment |
| Municipal-time duration | duration excluding applicant/third-party blocked time | Reported alongside total; guards against interventions that only shift delay to applicants |
| SLA compliance | % of cases decided within the statutory/local limit per case type | ≥ 90% per case type; no case type below 80% |
| Throughput / backlog | cases completed per month; open backlog and its trend at end of horizon | Backlog must be non-increasing year-over-year in the baseline demand scenario |
| Resource utilization | per pool, monthly | Target band 70–85%; > 90% flags fragility, < 50% flags waste |
| Rework rate | completeness loops per case; inspection rework rate | D1 must reduce completeness loops ≥ 30% to justify its applicant cost |
| Fairness | duration ratio p50 and p90 across districts, and top-20 architects vs. tail architects | Max/min district p90 ratio ≤ 1.25; no *worsening* of the ratio vs. B0 |
| Robustness | rank stability and metric degradation under S1–S5 | Intervention must not make any stress scenario worse than B0 |

### 7.2 Fairness in particular

Batching (D3) and prioritization (D6) are the interventions most likely to improve aggregate metrics while harming a subgroup. Therefore every scenario is scored on the **distribution across districts and architect classes**, not just the aggregate. An intervention that improves overall p50 by 8% while raising D5's p90 by 20% is rejected or must be paired with a compensating rule. Similarly, D1 and D7 must be checked for disadvantaging small/occasional applicants (low digital capability) — an equity constraint that a pure efficiency metric would miss.

### 7.3 Decision rule (lexicographic with tolerances)

1. **Feasibility gate**: no pool utilization > 92% in the central scenario; no case type SLA < 80%; no fairness ratio worse than B0 by more than 5%; no safety/compliance metric (D2 audit failures, D8 false negatives) above the agreed tolerance.
2. **Dominance screen**: discard interventions dominated on (median, p90, SLA, cost) by another.
3. **Cost-effectiveness**: rank surviving options by cost per case-day saved and per SLA-point gained, where cost includes FTE, IT, and applicant burden.
4. **Robustness filter**: require that the intervention remains in the top tier across ≥ 80% of the calibration-posterior draws (§5.4) and does not degrade under S1–S5.
5. **Selection**: recommend the robust, cost-effective, fairness-neutral-or-better subset — presented as a *set* of statistically indistinguishable candidates when the MCB procedure cannot separate them.

### 7.4 Confidence qualifiers on specific interventions

- **D9** results are conditioned on latent objection parameters; the recommendation is expected to be "instrument objections first" (value-of-information) rather than "implement now."
- **D2** and **D8** are risk-shifting rather than pure-efficiency interventions; they must be decided with a compliance-risk owner, using the model to quantify the error frontier, not to make the risk-appetite call.
- **D1** improvement measured on total elapsed time may be much smaller than on municipal time; both are reported and the difference is the honest headline.

def load_dataframe(csv_text: Optional[str] = None, path: Optional[str] = None) -> pd.DataFrame:
    """Load the log with pandas. NOTE: there is no pm4py.read_csv; CSV reading
    is pandas' job, and pm4py.format_dataframe only normalizes the columns."""
    if path is not None:
        df = pd.read_csv(path)
    else:
        df = pd.read_csv(io.StringIO(csv_text or LOG_EXCERPT))
    df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])
    return df


def format_log(df: pd.DataFrame) -> pd.DataFrame:
    """Normalize to PM4Py conventions."""
    df = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )
    return df


def parse_model() -> Tuple[Any, Any, Any, Any]:
    """Parse the simplified process tree and convert it to an accepting Petri net.

    LIMITATIONS of the simplified string (must be stated to stakeholders):
      * The loop operator *(A, B) in PM4Py means "do A, then optionally B then A
        again". The redo children 'Completeness rework' / 'Inspection rework' are
        therefore modeled as explicit activities, whereas in reality rework is a
        *reason-coded* return that the log does not label reliably.
      * The tree carries NO data perspective: the X(tau, 'Fire-safety review')
        choices are silent XORs, while in reality they are driven by
        requires_fire / building_area / district sensitivity. Branching
        probabilities must therefore be attached externally (see RoutingModel).
      * The tree carries NO resource, calendar, queueing or time perspective, and
        no cross-case dependency (architect bursts, inspection bundling,
        objections). It constrains control flow only.
      * Legal-check-after-appeal and the appeal loop are not represented at all.
      * Consequently the tree is used for conformance checking and structural
        regression tests, NOT as the executable simulation model.
    """
    tree = pm4py.parse_process_tree(PROCESS_TREE_STR)
    net, im, fm = pm4py.convert_to_petri_net(tree)
    return tree, net, im, fm


def descriptive_statistics(df: pd.DataFrame) -> Dict[str, Any]:
    """Variants, DFG, performance DFG, arrival rate, durations."""
    stats: Dict[str, Any] = {}

    stats["variants"] = pm4py.get_variants(df)
    stats["n_variants"] = len(stats["variants"])

    dfg, start_acts, end_acts = pm4py.discover_dfg(df)
    stats["dfg"] = dfg
    stats["start_activities"] = start_acts
    stats["end_activities"] = end_acts

    perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(df)
    stats["performance_dfg"] = perf_dfg  # mean duration (s) per directly-follows edge

    # Average inter-arrival time between case starts (seconds).
    stats["case_arrival_avg"] = pm4py.get_case_arrival_average(df)
    stats["case_durations"] = pm4py.get_all_case_durations(df)

    stats["activities"] = pm4py.get_event_attribute_values(df, "concept:name")
    stats["resources"] = pm4py.get_event_attribute_values(df, "org:resource")
    return stats


def conformance_report(df: pd.DataFrame, net, im, fm) -> Dict[str, Any]:
    """Both directions: real log vs. model, and (later) simulated log vs. model."""
    return {
        "alignments": pm4py.conformance_diagnostics_alignments(df, net, im, fm),
        "fitness": pm4py.fitness_alignments(df, net, im, fm),
    }


def add_timing_columns(df: pd.DataFrame) -> pd.DataFrame:
    """Derive per-event timing columns.

    IMPORTANT LIMITATION: many human activities log only a completion timestamp.
    Without 'start_timestamp' we can only compute the *inter-completion gap*,
    which conflates queueing wait + service + calendar downtime + third-party
    delay. We therefore expose `gap_to_prev` explicitly and only compute a true
    service time where a start timestamp exists. The waiting/service split for
    the remaining activities is INFERRED during calibration (see
    ParameterEstimator.calibrate) and must never be reported as measured.
    """
    df = df.sort_values([CASE_KEY, TS_KEY]).copy()
    df["gap_to_prev"] = (
        df.groupby(CASE_KEY)[TS_KEY].diff().dt.total_seconds()
    )
    if "start_timestamp" in df.columns:
        st = pd.to_datetime(df["start_timestamp"])
        df["service_time_s"] = (df[TS_KEY] - st).dt.total_seconds()
        # waiting = time from previous completion (or enablement) to own start
        df["waiting_time_s"] = (
            st - df.groupby(CASE_KEY)[TS_KEY].shift()
        ).dt.total_seconds()
    else:
        df["service_time_s"] = np.nan
        df["waiting_time_s"] = np.nan
    df["service_time_observed"] = df["service_time_s"].notna()
    return df


def case_table(df: pd.DataFrame) -> pd.DataFrame:
    """One row per case with attributes + arrival time, for arrival/routing models."""
    attrs = ["case_type", "district", "architect_id", "application_value",
             "requires_fire", "requires_environment", "requires_public_notice"]
    attrs = [a for a in attrs if a in df.columns]
    g = df.sort_values(TS_KEY).groupby(CASE_KEY)
    out = g.first()[attrs].copy()
    out["arrival_time"] = g[TS_KEY].min()
    out["end_time"] = g[TS_KEY].max()
    out["duration_s"] = (out["end_time"] - out["arrival_time"]).dt.total_seconds()
    out["n_completeness_checks"] = (
        df[df[ACT_KEY] == "Completeness check"].groupby(CASE_KEY).size()
        .reindex(out.index).fillna(0).astype(int)
    )
    return out.reset_index()

# ---------- engine ----------------------------------------------------------

class PermitSimulator:
    """Event-driven engine. Owns the clock, the event heap and all submodels."""

    def __init__(self, params: Dict[str, Any], policy: PolicyConfig,
                 seed_sequence: np.random.SeedSequence,
                 initial_wip: Optional[List[Case]] = None):
        # Independent streams per component -> preserves common random numbers
        # across scenarios even when an intervention changes the draw counts.
        streams = seed_sequence.spawn(6)
        self.rng_arrivals = np.random.default_rng(streams[0])
        self.rng_service = np.random.default_rng(streams[1])
        self.rng_routing = np.random.default_rng(streams[2])
        self.rng_rework = np.random.default_rng(streams[3])
        self.rng_travel = np.random.default_rng(streams[4])
        self.rng_dependency = np.random.default_rng(streams[5])
        self.policy = policy
        self.params = params
        self.initial_wip = initial_wip or []
        # submodels wired here (arrivals, routing, durations, resources, deps)

    def run(self, horizon_days: float, warmup_days: float) -> "SimulationResult":
        raise NotImplementedError

    def to_event_log(self) -> pd.DataFrame:
        """Emit the simulated log in PM4Py column conventions so that Part A's
        descriptive and conformance functions can be reused verbatim for
        validation (simulated-log-vs-model replay, variant comparison, DFG
        comparison)."""
        raise NotImplementedError


@dataclass
class SimulationResult:
    event_log: pd.DataFrame
    case_table: pd.DataFrame
    utilization: Dict[str, float]
    backlog_series: pd.DataFrame

    def kpis(self) -> Dict[str, float]:
        """p50/p90/p95 duration by case type, SLA compliance, municipal-only
        duration, rework rate, fairness ratios, end-of-horizon backlog."""
        raise NotImplementedError

class ParameterEstimator:

    def __init__(self, df: pd.DataFrame):

        raise NotImplementedError

    def fit_routing(self) -> Dict[str, Any]:
        raise NotImplementedError

    def fit_rework(self) -> Dict[str, Any]:
        raise NotImplementedError

    def fit_dependencies(self) -> Dict[str, Any]:
        raise NotImplementedError

    def calibrate(self, targets: Dict[str, Any], n_posterior: int = 200) -> List[Dict[str, Any]]:
        """Simulated method of moments / ABC over the weakly identified
        parameters (latent service levels, objection prevalence, applicant
        tail index, batching savings). Returns a POSTERIOR SAMPLE, not a point
        estimate, so intervention comparisons carry parameter uncertainty."""
        raise NotImplementedError


@dataclass
class Experiment:
    name: str
    policy: PolicyConfig
    demand_multiplier: float = 1.0
    resource_overrides: Dict[str, int] = field(default_factory=dict)
    n_replications: int = 30


class ExperimentRunner:
    """Runs the matrix of §4 with common random numbers and paired comparisons."""

    def __init__(self, params_posterior: List[Dict[str, Any]], base_seed: int = 20260806):
        self.params_posterior = params_posterior
        self.base_seed = base_seed

    def run(self, experiments: List[Experiment], horizon_days: float = 3 * 365,
            warmup_days: float = 180) -> pd.DataFrame:
        rows = []
        for exp in experiments:
            for rep in range(exp.n_replications):
                # Same (base_seed, rep) across experiments -> CRN.
                ss = np.random.SeedSequence([self.base_seed, rep])
                params = self.params_posterior[rep % len(self.params_posterior)]
                sim = PermitSimulator(params, exp.policy, ss)
                res = sim.run(horizon_days, warmup_days)
                rows.append({"experiment": exp.name, "replication": rep, **res.kpis()})
        return pd.DataFrame(rows)

    def paired_comparison(self, results: pd.DataFrame, baseline: str = "B0") -> pd.DataFrame:
        """Per-replication differences vs. baseline, with bootstrap CIs and a
        Holm / MCB correction across the intervention set."""
        raise NotImplementedError


def main() -> None:
    # --- Part A: PM4Py log & model handling -------------------------------
    df = format_log(load_dataframe())
    df = add_timing_columns(df)
    tree, net, im, fm = parse_model()
    stats = descriptive_statistics(df)
    conf = conformance_report(df, net, im, fm)
    print("variants:", stats["n_variants"],
          "| avg inter-arrival (s):", stats["case_arrival_avg"],
          "| fitness:", conf["fitness"])

    # --- Part C: estimation + calibration ---------------------------------
    est = ParameterEstimator(df)
    posterior = est.calibrate(targets={"variant_shares": stats["variants"]})

    # --- Part C: experiment matrix ----------------------------------------
    experiments = [
        Experiment("B0", PolicyConfig()),
        Experiment("E1_D1", PolicyConfig(d1_presubmission_checker=True,
                                         d1_adoption=0.7, d1_loop_reduction=0.55,
                                         d1_extra_applicant_effort_days=2.0)),
        Experiment("E2_D2", PolicyConfig(d2_skip_inspection=True)),
        Experiment("E3_D3", PolicyConfig(d3_district_batching=True)),
        Experiment("E4_D4", PolicyConfig(d4_temp_inspector=True)),
        Experiment("E10_D10", PolicyConfig(d1_presubmission_checker=True, d1_adoption=0.7,
                                           d1_loop_reduction=0.55,
                                           d2_skip_inspection=True,
                                           d3_district_batching=True,
                                           d4_temp_inspector=True)),
        Experiment("S1_surge", PolicyConfig(), demand_multiplier=1.3),
        Experiment("S2_resource_loss", PolicyConfig(),
                   resource_overrides={"legal": 1, "inspectors": 3}),
    ]
    runner = ExperimentRunner(posterior)
    results = runner.run(experiments)
    print(runner.paired_comparison(results))
    # NOTE: no ranking is published before B0 passes the validation battery of
    # §6, and results are reported as relative rankings with uncertainty bands,
    # never as proven optima.


if __name__ == "__main__":
    main()

### Notes on the skeleton

- **No `pm4py.read_csv`**: CSV loading is pandas; `pm4py.format_dataframe` only normalizes column names to `case:concept:name` / `concept:name` / `time:timestamp`.
- **Clean separation**: Part A touches PM4Py only; Part B has no PM4Py import dependency. The one deliberate bridge is `PermitSimulator.to_event_log()`, which emits a log in PM4Py conventions so the *same* descriptive and conformance code validates real and simulated logs — this is what makes §6.2's bidirectional replay check cheap.
- **Service/waiting are never collapsed**: `add_timing_columns` exposes `gap_to_prev` separately and flags which service times are actually observed; the split is inferred in `calibrate`, and every downstream report inherits that caveat.
- **Objections stay latent**: `DurationModel.public_notice_duration` and `DependencyManager.sample_objection_shock` sample an unobserved flag from an estimated prevalence; nothing reads an objection column from the log.
- **Independent RNG streams** per component preserve common random numbers across scenarios even when an intervention changes how many draws each component consumes.

---

## Closing caveat

This design produces **relative comparisons of interventions under explicitly stated assumptions, with quantified uncertainty** — not optimal policies. Several key parameters (the waiting/service split, objection prevalence and effect, cross-case dependency strength, hidden emergency load) are inferred rather than observed. Before any recommendation is acted upon, the baseline must pass the validation battery in §6, and the highest-value immediate action is often not an intervention at all but a **data-collection change**: log activity start timestamps, record objection events as first-class events, and code rework reasons. Those three changes would shrink the widest uncertainty bands in this study more than any additional modeling effort.
