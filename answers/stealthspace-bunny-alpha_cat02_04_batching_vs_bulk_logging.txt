# 1. Cluster diagnoses

The distinction between **physical batching**, **operational batching**, and **logging batching** is essential. Identical timestamps may identify a fixture load, a group button, a folder submission, or merely timestamp quantization. They do not establish which physical activities overlapped.

**Assumptions and measurement conventions**

- **A1 — Interval convention:** Execution intervals are treated as half-open, \([start, complete)\). Consequently, a case ending at 10:09 and another starting at 10:09 do not overlap. Zero-length intervals contain no execution time.
- **A2 — Clock comparability:** Queue, execution, and recording times are provisionally compared on one timeline because all observations are supplied for the same date. Clock synchronization is not established, especially for the safety system in G8.
- **A3 — Precision is not accuracy:** A “1 min” field identifies the source’s granularity, not an error bound. The interval-censoring interpretations in this answer are explicitly conditional on the fields representing quantization cells.
- **A4 — Reported service time:** Unless stated otherwise, “service time” means the logged `complete  start`, not verified active processing time. Pause/resume information is unavailable.
- **Confidence** below refers to confidence in the **first-ranked explanation**, not certainty about every underlying physical action.

- **Start equality** supports a common launch/setup mechanism more directly than it supports physical parallelism.
- **End equality** supports common finalization or submission more directly than simultaneous execution.

- **Recording lag** measures insertion delay, not queue waiting or active processing.
- A PM4Py batch label is a detector result under a merge rule, not a measurement of workstation capacity or physical simultaneity.

## Why G6 produces both inflated waiting and near-zero service

G6 is a characteristic **lifecycle-field contamination** pattern:

1. `queue_arrival` records entry into the upstream process at different times.
2. The bulk form writes the same lifecycle value, 17:00, into every case’s `start` and `complete`.
3. A conventional queue metric consequently treats all cases as waiting until 17:00, producing a mean wait of about **103.43 min**.
4. A conventional service metric records **0 min**, making the cases appear instantaneous.

Those two results are internally linked artifacts, not independent performance findings. A short, genuine bulk-close action can legitimately have a short form duration, but that duration belongs primarily to the **form action**, not automatically to each ticket’s complete lifecycle. Actual ticket work might have occurred before 17:00, during the backlog, or through another unlogged system. G6 should not be used to estimate physical service capacity without those boundaries.

# 4. PM4Py and pandas analysis

The following script:

- Preserves all **38 rows**, including the seven zero-duration G6 rows.
- Retains suspect semantics through explicit flags rather than deleting or imputing them.
- Uses the documented interval-log semantics, where `start == complete` is permitted.
- Runs batch discovery for merge distances of **1, 15, and 60 seconds**, and minimum batch sizes of **2 and 3**.
- Calculates the overlap rate independently as  
  \[
  \frac{\text{unordered positive-time interval pairs that overlap}}
       {\text{all unordered interval pairs}}
  \]
  separately within each cluster/resource. This is a pair-overlap rate, not a probability of concurrency.
- Uses half-open intervals for overlap and excludes zero-duration intervals from serial-adjacency detection.
- Preserves negative queue-wait diagnostics rather than clipping them to zero.
- Reports PM4Py’s version-specific category strings rather than hard-coding expected labels as observations.

def precision_seconds(text):
    match = re.fullmatch(r"\s*(\d+)\s*(sec|min)\s*", str(text), flags=re.I)
    if not match:
        return None
    amount = int(match.group(1))
    return amount if match.group(2).lower() == "sec" else amount * 60


def equality_share(values):
    values = values.dropna()
    if values.empty:
        return float("nan")
    modal_value = values.mode().iloc[0]
    return float(values.eq(modal_value).mean())


def max_simultaneous(intervals):
    # Ends precede starts at the same timestamp under the half-open convention.
    events = []
    for start, complete in intervals:
        if pd.notna(start) and pd.notna(complete):
            events.append((start, 1))
            events.append((complete, -1))
    events.sort(key=lambda event: (event[0], event[1]))
    active = 0
    peak = 0
    for _, change in events:
        active += change
        peak = max(peak, active)
    return peak


def lag_summary(lag_seconds):
    lag_seconds = lag_seconds.dropna()
    if lag_seconds.empty:
        return "unknown"
    return "/".join(
        f"{value:g}s"
        for value in (
            lag_seconds.min(),
            lag_seconds.median(),
            lag_seconds.max(),
        )
    )


def independent_diagnostics(group):
    g = group.sort_values(["queue_arrival", "sequence_no"])
    intervals = list(zip(g["start"], g["complete"]))
    pair_count = 0
    overlap_count = 0

    for left, right in combinations(intervals, 2):
        a_start, a_complete = left
        b_start, b_complete = right
        if any(pd.isna(x) for x in [a_start, a_complete, b_start, b_complete]):
            continue
        pair_count += 1
        # Zero-duration [t,t) intervals do not overlap.
        if a_start < b_complete and b_start < a_complete:
            overlap_count += 1

    # Exact touch transitions among successive POSITIVE-duration intervals.
    positive_intervals = [
        interval for interval in intervals
        if pd.notna(interval[0])
        and pd.notna(interval[1])
        and interval[1] > interval[0]
    ]
    adjacent = sum(
        left[1] == right[0]
        for left, right in zip(positive_intervals, positive_intervals[1:])
    )
    possible_transitions = max(len(positive_intervals) - 1, 0)

    lag = (
        (g["recorded_at"] - g["complete"])
        .dt.total_seconds()
    )

    wait = (
        (g["start"] - g["queue_arrival"])
        .dt.total_seconds()
        / 60
    )
    first_start = g["start"].min()
    backlog_at_first_start = int(
        (g["queue_arrival"] <= first_start).sum()
    )

    whole_minute_fields = (
        g["start"].dt.minute.eq(0)
        & g["start"].dt.second.eq(0)
        & g["complete"].dt.minute.eq(0)
        & g["complete"].dt.second.eq(0)
    )

    return {
        "cluster": g["cluster"].iloc[0],
        "resource": g["resource"].iloc[0],
        "n_cases": len(g),
        "unknown_lifecycle_n": int(
            g[["start", "complete"]].isna().any(axis=1).sum()
        ),
        "zero_duration_n": int(g["zero_duration"].sum()),
        "start_equal_share": equality_share(g["start"]),
        "end_equal_share": equality_share(g["complete"]),
        "n_start_groups": g["start"].nunique(dropna=True),
        "n_end_groups": g["complete"].nunique(dropna=True),
        "resource_overlap_rate": (
            overlap_count / pair_count if pair_count else float("nan")
        ),
        "resource_peak_overlap_n": max_simultaneous(intervals),
        "adjacent_positive_transition_fraction": (
            adjacent / possible_transitions
            if possible_transitions else float("nan")
        ),
        "rec_lag_min_med_max": lag_summary(lag),
        "precision_s": precision_seconds(g["precision"].iloc[0]),
        "whole_minute_start_complete_fields_n": int(whole_minute_fields.sum()),
        "queue_wait_mean_min": wait.mean(),
        "queue_negative_wait_n": int(wait.lt(0).sum()),
        "queue_arrival_span_min": (
            (g["queue_arrival"].max() - g["queue_arrival"].min())
            .total_seconds() / 60
        ),
        "queue_backlog_at_first_start_n": backlog_at_first_start,
        "queue_arrivals_after_first_start_n": int(
            (g["queue_arrival"] > first_start).sum()
        ),
        "identity_note": (
            "SHARED_POOL" if g["resource"].iloc[0] == "analyst_pool"
            else "identifier_only"
        ),
    }

# 5. Robustness and alternative explanations

## Trusted resource IDs versus shared-account sensitivity

| Resource assumption | Conclusions preserved or strengthened | Conclusions that change or become unidentifiable |
|---|---|---|
| **Trust resource IDs as individual workers, except RBT-7’s documented four-item capacity** | G4, G6, and G8 cannot contain uninterrupted active overlap of their displayed positive-duration cases on one worker. G2’s four overlapping intervals challenge one-worker execution unless they are template/group times. G5’s four-way overlap exceeds the stated three-analyst capacity. | Per-person utilization cannot be obtained for G2, G3, G4, G6, G7, or G8. G3’s full active intervals are incompatible with one worker if all endpoints are literal execution times; bulk completion resolves the apparent conflict. G1 cannot be treated as a one-slot resource. |
| **Treat a broader set of IDs as potentially shared as a stress test** | G5 becomes an ordinary pooled-resource problem with plausible concurrency by up to three analysts, except for its four-way interval. G1 remains a multi-capacity automated resource. | G2, G3, G6, G7, and G8 could accommodate physical overlap if their IDs are actually shared, but there is no supplied evidence that they are shared. Overlap alone is not grounds to relabel them. A unique-looking ID is not, conversely, absolute proof of one physical person. |

The principal robustness lesson is that **resource-ID sensitivity changes the admissibility of concurrency, not the observed timestamp pattern**. It should not be used to manufacture a preferred process model.

## Exact timestamps versus interval-censored timestamps

- **Exact-timestamp interpretation:** G7 contains five identical execution intervals and four negative naive queue waits. Those results are data-quality alarms, not credible physical performance.
- **Conditional interval interpretation:** If G7’s fields represent the documented quarter-hour cells, each true start is in \([14:00,14:15)\), and each true completion is in \([14:15,14:30)\). The ordering of the rounded rows remains available, but exact service durations, waits, and concurrency are not identified.
- **Minute-granularity sensitivity:** If G2 or G3 fields represent 1 min cells, their displayed equal endpoints should be varied across their cells. A bulk group start or folder end can remain exactly common in reality; the test must not assume that quantization necessarily created the tie.
- **Second-granularity fields:** The 1 sec fields in G1, G4, and G8 support finer matching tests, but do not establish clock accuracy or the absence of a smaller systematic timestamp assignment.
- **Clock sensitivity:** For G8, any offset between queue arrival, T-H, and the safety clock changes backlog duration and even whether all cases were waiting before work began.

## Temporal patterns supporting multiple physical explanations

1. **G1: Four identical 09:00–09:03 intervals**
   - Four items could be processed concurrently on the documented four-item fixture.
   - One fixture cycle could contain four serial suboperations while source fields expose only fixture-level start and end.
   - A common setup could cause four case-level starts to be written simultaneously.
   - The temporal pattern alone cannot distinguish these mechanisms.

2. **G2: One common start with four different ends**
   - Four items could be inspected simultaneously following one group launch.
   - One inspector could work serially on suboperations within a group, with 10:00 propagated to every case and only later completions differentiated.
   - A common setup event could be combined with staggered actual execution.
   - The single group button favors common start batching, but does not select the physical alternative.

3. **G3: Distinct starts with one common end**
   - Reviews could occur concurrently, followed by one folder submission.
   - A shared administrative completion or authorization checkpoint could overwrite several case endpoints.
   - One reviewer could have performed different subsets over the half-hour, with the final event representing folder closure rather than simultaneous task completion.
   - The folder-submission explanation does not establish how many reviewers actually participated.

4. **G6: Seven zero-duration records at the same form time**
   - T-F could genuinely perform one short bulk-close action.
   - Seven separate electronic closures could each complete very quickly.
   - The form could assign 17:00 to all fields while physical closure occurred earlier or elsewhere.
   - These alternatives imply very different meanings for waiting, service, and throughput.

5. **G7: Five identical quarter-hour records**
   - Five manual measurements could have been performed serially over short intervals within the half-hour envelope.
   - An assistant-assisted simultaneous measurement session is also possible.
   - All starts and ends could have been rounded from staggered execution.
   - No supplied group identifier or raw timestamp establishes either physical explanation.

# 6. Data-collection redesign

**Priority 0 — Correct lifecycle semantics and collect actual execution events.**

- Record separate event types for:
  - work eligible/ready;
  - execution start;
  - active work;
  - pause and resume;
  - execution completion;
  - administrative approval;
  - form submission;
  - database insertion.
- For PLC work, capture fixture load, cycle start/end, and item-level state transitions.
- For T-B, store group-begin time separately from each item’s actual inspection start and end.
- For T-C, store individual review completion separately from folder finalization.
- For T-F, capture the bulk form action once and associate it with individual case-closure events. Zero duration should be accepted only when a genuinely instantaneous event is measured, not used as a default.
- For G7, preserve raw higher-resolution measurements or emit explicit timestamp intervals and the rounding rule.

**Priority 0 — Preserve human and equipment identity.**

- Retain badge or authenticated user identity at event time, not only a login.
- For pooled systems, emit both `account_id` and `person_id`.
- Separate workstation identity from worker identity.
- Publish capacity explicitly:
  - RBT-7: four-item fixture capacity;
  - analyst pool: actual analysts present or assigned;
  - inspection and review stations: whether simultaneous human work is possible.
- A shared account should remain in the log as a data-quality attribute, not be silently expanded into invented workers.

**Priority 0 — Synchronize and document clocks.**

- Store timezone, clock source, and synchronization status for PLC, tablets, desktops, scanners, upstream queue systems, and safety systems.
- Measure or estimate the safety-to-T-H offset rather than aligning timestamps by visual proximity.
- Record upstream queue-arrival clock provenance so that G8’s backlog calculations are conditional on comparability.
- Preserve `sequence_no`, but do not use it to replace timestamps or prove temporal ordering across systems.

**Priority 1 — Capture group and operational context.**

- Add a group/batch identifier and group-membership table.
- Record group creation, group launch, common setup duration, individual service, group release, and bulk submission separately.
- Distinguish a fixture batch, an inspection group, a review folder, a manual close form, and a collection of cases merely processed in sequence.
- G4 in particular needs a batch identifier before its sequential pattern can be called an operational batch rather than ordinary serial work.

**Priority 1 — Make queue analysis operational rather than timestamp-only.**

- Record the time work became eligible, not only the upstream arrival.
- Capture dispatch, workstation release, downtime, setup, and queue-state changes.
- Log whether a waiting case was technically available but awaiting common setup, a safety check, a folder, or a shift-end action.
- This would distinguish G8 capacity loss from ordinary early arrivals and expose the administrative backlog represented by G6.

**Priority 1 — Improve timestamp metadata.**

- For every field, document:
  - native precision;
  - whether it is rounded, truncated, defaulted, or manually entered;
  - the rounding direction;
  - estimated accuracy and clock uncertainty;
  - whether blank means unknown, not started, not completed, or not applicable.
- Do not treat increased display precision as increased accuracy.
- Retain zero-duration, missing, and out-of-order events with explicit semantic flags.

**Priority 2 — Add auditable state-change records.**

- Record lifecycle field changes with both the business-event time and database insertion time.
- Keep immutable raw events and an auditable correction history.
- Provide a data dictionary distinguishing lifecycle event time, source event time, and reporting time.
- Validate that recorded values correspond to actual state transitions rather than merely successful form saves.

# 7. Final adjudication

**High-confidence interpretations of the supplied temporal structures**

- **G1:** A four-case operational batch with a common cell start/end is highly evident. Parallel four-item processing is plausible and supported by the stated fixture capacity, but the fixture load and real item endpoints require validation.
- **G2:** Common group launch/start batching is strongly supported. Physical concurrency and the correct per-item service times remain unresolved.
- **G3:** Common end batching/folder finalization is strongly supported. Individual review completion must not be equated with the common 11:30 endpoint.
- **G4:** Back-to-back serial processing is strongly supported under the stated resource and clock assumptions. There is insufficient evidence for a logical batch.
- **G7:** Timestamp coarsening is established with very high confidence. The exact physical execution pattern is not identified.
- **G5:** Shared-account attribution is established. Up to three-way physical concurrency is plausible, but four-way uninterrupted activity is incompatible with the stated headcount.

**Exclusion or interval-censoring decisions for queue analysis**

- **G6:** Exclude the common form timestamps from conventional physical service and queue-performance calculations. Retain the cases for data-quality and administrative-batch analysis. Reporting waiting until 17:00 is acceptable only when explicitly labeled **waiting until bulk form action**. Do not use the zeros as service observations.
- **G7:** Interval-censor the lifecycle times. Preserve the negative naive waits as a quality diagnostic. Do not turn them into positive waiting times without an explicit start-distribution or execution model.
- **G2 and G3:** Use interval-censored sensitivity analysis for physical service. G2’s common start and G3’s common end can remain genuine group events, so neither cluster should be discarded merely because those events are operational.
- **G5:** Do not discard the cases. Exclude the pool-level resource from person-level utilization until identity and actual work assignment are known.
- **G8:** Do not discard the queue. Withhold a safety-related capacity-loss conclusion until queue, T-H, and safety clocks are aligned. Its post-15:38 serial work pattern is much more defensible than its explanation for the preceding period.

**Clusters requiring operational validation before physical performance conclusions**

- **G1:** Actual fixture membership and serial/parallel cycle behavior.
- **G2:** Item-level execution and inspection capacity.
- **G3:** Individual review completion, folder finalization, and reviewer identity.
- **G4:** Whether common setup or a real logical batch exists outside the displayed chain.
- **G5:** Badge attribution, pauses, and the apparent fourth concurrent case.
- **G6:** The meaning of the bulk form and actual ticket-closure work.
- **G7:** Raw or interval-qualified measurement times.
- **G8:** Workstation availability, queue-clock alignment, and the safety-system clock offset.

The central adjudication is therefore not “batch versus no batch.” It is that the data exhibit several different mechanisms: **G1 plausibly combines fixture batching with common setup; G2 and G3 are operational start/end batches; G4 and G8 are serial patterns; G5 is a pooled-identity problem; G6 is an administrative bulk-submission artifact; and G7 is a timestamp-resolution problem.** Each requires a different performance interpretation, and none of the PM4Py batch labels alone resolves those semantics.
