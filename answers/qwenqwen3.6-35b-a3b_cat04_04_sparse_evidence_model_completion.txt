- **Forbidden behavior:** Exp without prior CC & ER; RP without AC; Archive without RP; multiple Exp; SC after AC; CC or ER after AC.

**PM4Py code (POWL, relaxed):**
```python

# Permissive model: POWL
po_perm = StrictPartialOrder()
t = {name: Transition(name) for name in ["RO","CC","ER","SC","Exp","AC","RP","Archive"]}

# Minimal constraints: only enforce hard prerequisites
po_perm.add_edge(t["RO"], t["CC"])
po_perm.add_edge(t["RO"], t["ER"])
po_perm.add_edge(t["CC"], t["AC"])
po_perm.add_edge(t["ER"], t["AC"])
po_perm.add_edge(t["SC"], t["AC"])
po_perm.add_edge(t["CC"], t["Exp"])
po_perm.add_edge(t["ER"], t["Exp"])
po_perm.add_edge(t["Exp"], t["AC"])
po_perm.add_edge(t["AC"], t["RP"])
po_perm.add_edge(t["RP"], t["Archive"])

t["SC"].is_optional = True
t["Exp"].is_optional = True

model_permissive = po_perm
```

**Deliberately excluded behavior:**
- Exp before CC or ER completes
- RP before AC completes
- Archive before RP completes
- Multiple Exp events
- SC after AC completion

# 9. Recommendation and Data-Collection Plan

**Recommendation:**
- **Immediate use:** `model_balanced`. It offers the best trade-off between precision and generalization, explicitly encodes the likely concurrency of CC/ER, respects D1–D6, and remains auditable. It aligns with stakeholder S2 while acknowledging D7’s caution.
- **Sensitivity analysis:** `model_conservative`. Use it to test compliance strictness and measure how much behavior is rejected if concurrency is disallowed. Compare fitness/precision drops to quantify the cost of assuming sequential checks.

**Data-Collection Plan to Resolve Ambiguities:**
1. **Collect start timestamps** alongside completion timestamps. This directly distinguishes concurrency from weak sequential preference (resolves D7/S1 vs S2).
2. **Export the `component_type` (external/stocked) attribute.** This separates true optionality from missing SC events (resolves S3/S4 vs S5).
3. **Log integration health metrics.** Track SC event drop rates per system to quantify the 5–10% missingness (resolves S5).
4. **Maximally informative future traces:** 
   - Cases where CC and ER start simultaneously but finish hours apart.
   - Cases where SC starts before either check completes.
   - Cases with multiple Exp events (to test D6’s “at most once” rule).
   - Cases where Exp runs concurrently with SC.
   These traces would definitively distinguish XOR, sequence, concurrency, and optionality hypotheses.

# 10. Uncertainty Statement

**Calibrated confidence assessment:**
- `CC/ER concurrency`: 65% confidence. Bidirectional DFG + S2 support it, but completion logs alone cannot rule out weak sequential preference.
- `SC optionality`: 80% confidence. Strongly supported by D4, S3/S4, and 10/30 missing SC cases.
- `Exp prerequisites`: 75% confidence. D6 is explicit, but only 2 observed cases limit statistical certainty.
- `Missing SC abstraction`: 50% confidence. Conflates data quality with business logic; true separation requires attribute logging.

**Plausible alternative interpretation:** If S1 (Finance) is correct and `Credit Check` strictly precedes `Engineering Review`, the balanced/permissive models would overgeneralize concurrency. The conservative model would then be more accurate, and the recommendation would shift to `model_conservative` for compliance-critical deployments. This alternative would materially change the model structure from an AND fork to a strict sequence, reducing generalization but increasing auditability.
