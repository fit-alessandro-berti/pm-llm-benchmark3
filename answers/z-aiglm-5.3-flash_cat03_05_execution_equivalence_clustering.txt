```python
import hashlib
from collections import Counter
import pandas as pd
import pm4py

LEAD_TYPE   = "Order"     # lead object type
EXT_MARK    = "EXT"

def _tokens(rows) -> str:
    """Type-level, multiplicity-aware token string for one event,
    with '*' marking foreign-root (EXT) objects."""
    c = Counter(f"{t}{'*' if str(o).startswith(EXT_MARK) else ''}"
                for t, o in zip(rows["ocel:otype"], rows["ocel:oid"]))
    return ",".join(f"{k}x{n}" for k, n in sorted(c.items()))

def _sequence(ocel, oid):
    """Deterministic linearization of the events of the execution rooted at oid."""
    rel, ev = ocel.relations, ocel.events
    eids = set(rel.loc[rel["ocel:oid"] == oid, "ocel:eid"])
    ev_i = ev[ev["ocel:eid"].isin(eids)]
    rel_i = rel[rel["ocel:eid"].isin(eids)].groupby("ocel:eid")
    out = []
    for r in (ev_i.sort_values(["ocel:timestamp", "ocel:activity"],
                               kind="mergesort")).itertuples():
        out.append((r.ocel_activity, _tokens(rel_i.get_group(r.ocel_eid))))
    return out

def _qual_flags(ocel, oid):
    """Business motifs read from qualified O2O links (PM4Py>=2.3: ocel.o2o)."""
    try:
        o2o = ocel.o2o
        q = set(o2o.loc[o2o["ocel:oid"] == oid, "ocel:qualifier"])
    except AttributeError:
        q = set()
    return q

def business_signature(ocel, oid) -> str:
    parts = _sequence(ocel, oid)
    text  = "|".join(f"{a}[{t}]" for a, t in parts)
    flags = []
    pays = sum(1 for a, _ in parts if a == "Record Payment")
    if pays != 1:                       flags.append(f"PAY_PATTERN_{pays}")
    if "Return Item" in text:           flags.append("RETURN_REPACK")
    if "Orderx2" in text or "*" in text:
        shared_at_log = any(a in ("Pack Package", "Dispatch") for a, _ in parts
                            if ("Orderx2" in _ or "*" in _))
        flags.append("SHARE_LOG" if shared_at_log else "SHARE_FIN")
    if "removed_before_dispatch" in _qual_flags(ocel, oid):
        flags.append("SUBST_PRE_DISPATCH")
    blob = text + "#" + ",".join(sorted(flags))
    return hashlib.sha1(blob.encode()).hexdigest()[:10]

# ---- PM4Py native exact classes -------------------------------------------
exact = pm4py.cluster_equivalent_ocel(ocel, LEAD_TYPE)        # DataFrame: ocel:oid, cluster

orders = (exact["ocel:oid"].tolist() if "ocel:oid" in exact.columns
          else list(exact.index))

sig_by_order = {o: business_signature(ocel, o) for o in orders}

# ---- Custom canonicalization/aggregation step -----------------------------
uniq = list(dict.fromkeys(sig_by_order.values()))            # order-stable dedupe
name = {k: f"S{i}" for i, k in enumerate(uniq)}

result = pd.DataFrame({"order_oid": orders})
if "cluster" in exact.reset_index().columns or True:

                                  if c != "ocel:oid" and c not in ("index",)],
```

# Object-Centric Execution Clustering: X1–X8

Throughout, the **lead** of each execution is its `Order` object; "foreign-root" objects are those whose id begins `EXT`, i.e., objects owned by another Order execution.

## 1. Equivalence design space

### R1 — Activity-sequence equivalence (lead-scoped trace equality)
**Definition.** Project each execution to the string of activity labels of events incident to the lead Order, ordered by timestamp; ties broken deterministically by (label, sorted multiset of related object types, original log order). XY iff the strings are identical. A cheaper variant **R1** uses only the label *Parikh vector* (multiset, no order).
**Preserved:** which activities ran for the lead order, how often, in what order.
**Discarded:** object types and multiplicities, externality, all O2O facts (topology, qualifiers, settlement semantics).
**Properties:** reflexive, symmetric, transitive (string/vector equality). 
**Concurrency:** the ordered variant is sensitive to logging jitter among same-time events (tie-break decides); R1 tolerates concurrency by forgetting order.

### R2 — Typed structural equivalence (renaming-invariant isomorphism)
**Definition.** Model an execution as a typed hypergraph: nodes = objects, colored by object type and by an externality bit (`EXT` or local); hyperedges = events labeled by activity, each carrying an incident-type multiset; hyperedges arranged in the recorded total order (ties broken canonically). XY iff there is a bijection  on objects preserving (type, externality bit) and mapping lead to lead, inducing an order-preserving one-to-one map on events with equal typed incident multisets.
**Preserved:** full E2O incidence, per-event object multiplicity, externality flags, repeated events, event order.
**Discarded:** concrete local ids (by construction), attribute values (e.g., payment amounts), and **all** O2O knowledge — both derived topology and qualifiers. This blindness is deliberate and consequential: X7 is  to X1.
**Properties:** an equivalence relation (isomorphism of labeled structures). 
**Concurrency:** with total-order encoding, same-time events are linearized canonically; alternatively define DAG-isomorphism where timestamp ties create antichains (noted where relevant).

### R3 — Business-semantic equivalence (preferred)
**Definition.** XY iff R2-fingerprints are equal **and** the following semantic layers agree:
- *Externality profile:* which event families involve foreign-root objects — `SHARE_LOG` (sharing at Pack/Dispatch: pooled logistics) vs `SHARE_FIN` (sharing at Invoice/Payment: consolidated billing), independently flagged;
- *Settlement pattern:* number of payments per invoice and whether partials are distinguished (`partially_settles` / `completes_settlement`);
- *Motif flags from qualified O2O and shape:* `SUBST_PRE_DISPATCH` (a qualified removal/replacement edge detaches an item pre-dispatch), `RETURN_REPACK` (return/inspect/repack/dispatch loop or `replaces` edge), `CONSOLIDATED_DISPATCH` (one delivery, several packages), `MULTIWAVE_OUTBOUND`, `SPLIT_PACKING`.
Unknown qualifiers fall into a fixed bucket `OTHER`; every abstraction is thus a total function, so fingerprint equality is a genuine equivalence relation (reflexive, symmetric, transitive).
**Preserved:** everything in R2 plus the three semantic layers above.
**Discarded:** finer qualifier vocabulary beyond the closed dictionary; monetary amounts (only payment counts); elapsed times; id spellings.
**Concurrency:** computed on the canonical linearization; a partial-order mode (causal closure induced by shared objects, quotient over commuting same-time events) is available and only weakens X4's internal ordering, not its cluster (§7).

## 2. Canonical signatures

The signature for R3 is reproducible and renaming-invariant by construction: **raw local identifiers are never emitted**; only (type, multiplicity) with `*` marking foreign-root objects. Legally a code block belongs to §6, but the core scheme is:

```python
def event_fingerprint(activity, relation_rows):
    c = Counter(f"{t}{'*' if str(o).startswith('EXT') else ''}"
                for t, o in zip(relation_rows['ocel:otype'], relation_rows['ocel:oid']))
    return activity, ",".join(f"{k}x{n}" for k, n in sorted(c.items()))
```

Canonical event sequence: events incident to the lead Order, sorted by `(timestamp, activity, fingerprint)`; joined; concatenated with `"#"` and the sorted semantic-flag set; hashed. Compact notation used in the tables below: `CO`=Create Order, `AI`=Add Item, `PP`=Pack Package, `DI`=Dispatch, `IV`=Issue Invoice, `PA`=Record Payment, `RT`=Return Item, `IN`=Inspect Return; `superscript²` = two events of that label; shape `pkg/dlv/inv/pay`; `ext  {—, LOG, FIN}`.

## 4. Cluster interpretations

**S0 — standard fulfillment** (X1, X2). Private package/delivery/invoice/payment in one pass. Opportunity: this is the golden template for conformance baselining. Flattening by Order handles it perfectly. Stable: insensitive to any reasonable repair except event-drop by incomplete extractors.

**S1 — split-pack, consolidated dispatch** (X3). Items couldn't co-pack but ship together; single financial close. Risk: carrier surcharges and pick errors; opportunity: consolidation KPIs. Flattening by Order loses *which* packages were co-delivered (package-delivery binding). Stable: robust to qualifier loss; depends on correctly recording package multiplicity on Dispatch.

**S2 — staggered waves, partial settlement** (X4). Fulfillment spread over dispatch waves; one invoice settled incrementally. Risk: credit exposure between waves; SLA per wave. Traditional flattening by Order yields an odd double-dispatch case and conflates the two settlement steps; flattening by Item duplicates the invoice. Semi-stable: if partial payments are repaired into one aggregated amount event (or vice versa) the cluster regresses toward S1 — an explicitly repair-dependent boundary.

**S3 — pooled logistics** (X5). This order's shipment physically travels with a neighboring order's items. Risk/opportunity: freight-cost allocation, contamination and return-routing complexity. Flattening by Order hides the sharing entirely; flattening by Item splits the shared package across two cases and double-counts Pick/Pack. Fragile: any extraction window that truncates foreign references regresses X5 to S0 silently.

**S4 — consolidated billing** (X6). Finance is shared: one invoice/payment spanning two orders. Risks: revenue attribution, dunning, disputes. Flattening by Order mis-books 100% of revenue to the leading order. Fragile in the same way as S3, and additionally dependent on capturing the second Order on financial events — often the first thing lost in ETL.

**S5 — silent substitution** (X7). Net shipped goods differ from ordered goods, yet the event log matches S0 exactly. Compliance-critical: warranty/fraud/quality investigation trigger. Every flattening loses it, because the fact lives solely in a qualified O2O link. Most fragile cluster: disappears under qualifier-blind ingestion, and would *relocate* (not vanish) if substitutes were modeled as Remove+Add events.

**S6 — return-and-repack loop** (X6 counterpart on logistics quality) (X8). Delivered item returned, inspected, repacked, reshipped, then billed once. Risks: product quality, reverse-logistics cost; opportunity: quality-score signals. Flattening produces a confusing "double dispatch" case indistinguishable from a data error. Stable: distinct activity vocabulary and shape survive most repairs.

## 5. Borderline cases

**X1 vs X2.** Any renaming-invariant relation merges them; an *identifier-literal* equivalence (forensic replay against a concrete database schema) legitimately separates them, because primary keys matter when reconciling logs to ledgers. We discard literal ids per constraint, but the disagreement is genuine, not sloppy.

**X1 vs X5.** R1 merges (identical label strings); R3 splits (SHARE_LOG). A defensible opposing view — "customer-promise equivalence," analyzing what the recipient experiences — also merges them: same deliverables, same timeline; sharing is an internal cost matter. Which definition wins depends on whether the unit of analysis is interaction integrity or customer outcome.

**X1 vs X6.** Mirror image on the financial side. Revenue-recognition or dunning processes must split (an invoice covering two orders breaks per-order arithmetic); a coarse operations dashboard may merge, since the local event flow is untouched. Note the asymmetric danger: flattening by Order silently *misrepresents* X6 rather than merely simplifying it.

**X1 vs X7.** R1 and R2 both merge — there is literally no structural delta without qualifiers. R3 splits via SUBST_PRE_DISPATCH. A qualifier-blind pipeline (typical flattened history tables) is *forced* to merge; that is defensible when qualifier capture is known-unreliable, but it imports a real audit gap: net quantities shipped differ.

**X3 vs X4.** A coarse "split-shipment family" semantics merges both — root cause identical (items not co-packable), remediation similar. A cash-flow-aware semantics separates them: X4 opens credit exposure and doubles delivery SLAs. Partial-order treatment softens but does not erase the divide: once Pack–Dispatch interleavings are quotiented by E2O-causality, the surviving discriminators are delivery and payment multiplicity — exactly the features a "shipping-shape-only" abstraction chooses to forget.

**X4 vs X8.** Both exhibit two outbound waves with two packages. A logistics-agnostic finance abstraction merges them — indeed X8 has fewer payments (1 vs 2), so a payment-count view also merges them wrongly-by-coincidence; meanwhile the motif-aware R3 separates them because X8 carries a reverse-logistics loop, and a logistics-shape-only view would separate them because X8's waves are unplanned rework, not planning. Two defensible definitions disagree, in opposite directions, depending on whether they look at money or at rework.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

- **What the key preserves.** PM4Py builds, for each object of the chosen type, its execution (the events in which the object participates, with their related objects) and hashes a serialized form of it: activity labels, per-event related-object participation, and event ordering per recorded timestamps. It does **not** incorporate O2O qualifiers/derived relations, attribute values, or any externality semantics; identifier normalization is up to you.
- **Why raw ids make it too fine.** Because related objects enter the serialization with their concrete identifiers, X1 and X2 land in different classes despite being twin executions; timestamp ties and incidental serialization choices fragment further. Exact classes here approach the singleton partition — sound but unusable for segmentation.
- **Canonicalization/post-processing.** Strip local ids (emit type×multiplicity, keep `EXT` marks), fix a deterministic tie-break, overlay semantic flags from qualified O2O and settlement counts, then merge PM4Py classes whose members share the canonical signature (a well-defined many-to-one refinement quotient).
- **When exact is better.** Data-lineage audits, transformer regression tests, dedup verification, and any reconciliation where a single differing reference is a finding. Coarser business clustering wins for segmentation/reporting.
- **`max_objs` and scale.** Performance guards that cap processed lead objects turn large connected components into sampling problems: rare-but-material patterns (like S5) can be absent from results purely by the cap, and hub events (a Delivery carrying packages for dozens of orders) fan out, inflating per-execution extraction cost quadratically. Decompose by connected component and cache canonical keys per lead object.

```python
import hashlib
from collections import Counter
import pandas as pd
import pm4py

LEAD_TYPE, EXT_MARK = "Order", "EXT"
LOG_ACTS = {"Pack Package", "Dispatch"}
FIN_ACTS = {"Issue Invoice", "Record Payment"}

def _tokens(rows):                                   # type*multiplicity, '*' = foreign-root
    c = Counter(f"{t}{'*' if str(o).startswith(EXT_MARK) else ''}"
                for t, o in zip(rows["ocel:otype"], rows["ocel:oid"]))
    return ",".join(f"{k}x{n}" for k, n in sorted(c.items()))

def _seq(ocel, oid):                                 # lead-scoped, deterministically ordered
    rel, ev = ocel.relations, ocel.events
    eids = set(rel.loc[rel["ocel:oid"] == oid, "ocel:eid"])
    rel_by = {k: g for k, g in rel[rel["ocel:eid"].isin(eids)].groupby("ocel:eid")}
    out = []
    for r in (ev[ev["ocel:eid"].isin(eids)]
              .sort_values(["ocel:timestamp", "ocel:activity"], kind="mergesort")
              .itertuples()):
        out.append((r.ocel_activity, _tokens(rel_by[r.ocel_eid])))
    return out

def _qualifiers(ocel, oid):                          # PM4Py >= 2.3: qualified O2O links
    try:
        q = ocel.o2o
        return set(q.loc[q["ocel:oid"] == oid, "ocel:qualifier"])
    except AttributeError:
        return set()

def business_signature(ocel, oid):                   # custom canonicalization (R3)
    parts = _seq(ocel, oid)
    text = "|".join(f"{a}[{t}]" for a, t in parts)
    flags = []
    pays = sum(1 for a, _ in parts if a == "Record Payment")
    if pays != 1:                          flags.append(f"PAY_{pays}")
    if any(a == "Return Item" for a, _ in parts): flags.append("RETURN_REPACK")
    if any(("Order*" in t or "Orderx2" in t) and a in LOG_ACTS for a, t in parts):
                                           flags.append("SHARE_LOG")
    if any(("Order*" in t or "Orderx2" in t) and a in FIN_ACTS for a, t in parts):
                                           flags.append("SHARE_FIN")
    if "removed_before_dispatch" in _qualifiers(ocel, oid):
                                           flags.append("SUBST_PRE_DISPATCH")
    return hashlib.sha1((text + "#" + ",".join(sorted(flags))).encode()).hexdigest()[:10]

# ---- PM4Py native exact equivalence (column names vary by version) ----------
exact = pm4py.cluster_equivalent_ocel(ocel, LEAD_TYPE)          # e.g., index=oid, col='cluster'

orders = list(exact.index) if exact.index.name is not None else list(exact["ocel:oid"])
sig = {o: business_signature(ocel, o) for o in orders}

# ---- Aggregation: merge exact classes into business classes -----------------
uniq = list(dict.fromkeys(sig.values()))
label = {k: f"S{i}" for i, k in enumerate(uniq)}

result = pd.DataFrame({"order_oid": orders})
result["pm4py_exact"] = result["order_oid"].map(
    lambda o: exact.loc[o].iloc[0] if hasattr(exact, "loc") else None)
result["business_sig"] = result["order_oid"].map(sig)
result["business_cluster"] = result["business_sig"].map(label)

print(result.groupby("business_cluster")["order_oid"].apply(list))   # expected: S0:{O1,O2}, … S6:{O8}
assert result.groupby("pm4py_exact")["business_cluster"].nunique().max() <= \
       len(exact), "merge must be a coarsening, never a split"
```

## 7. Robustness analysis

- **Ignore all O2O qualifiers.** S5 (X7) collapses into S0 — its entire existence rests on `removed_before_dispatch`. S2 also loses its *documented* partial-settlement basis, though payment multiplicity still keeps it apart from S1. Nothing else moves.
- **Ignore external objects.** S3 and S4 regress to S0; the clustering degenerates to {S0…}, S1, S2, S6. Cross-order phenomena are the least robust signal in most pipelines, which is an argument for enforcing EXT-marker propagation during ETL, not for ignoring them.
- **Collapse repeated same-label events.** With counts kept, only adjacency effects vanish (harmless here). With presence-only collapse (dedupe), X1X3X5X6X7 and X4 joins via `PA²`, leaving effectively S0-family vs S6 — a useful reminder that bag-of-activity views are *flat*, barely object-centric, and destroy exactly the multiplicities that carry business meaning.
- **Partial order for Pack/Dispatch.** Replacing total order by E2O-causal partial order lets X4's two waves interleave freely; its canonical DAG-form gains order-insensitivity to logging jitter, but cluster membership is unchanged (delivery/payment multiplicity still separates it). X3, whose two Packs already precede a single Dispatch causally, is unaffected. Recommended default: partial order inside clusters, total order only within the canonical hash if one needs stricter stability guarantees.
- **Payments as amount attribute.** If partial payments are summed into one logical settlement (a legitimate ledger repair), X4's PAY-2 flag dissolves and X4 drifts toward the coarse S_spl family; if amounts are *retained as a typed attribute* but event structure kept, X4 stays separate with an added "settled_in_k_transfers" descriptor. Choose the convention up front; do not let extractors decide implicitly.

## 8. Limitations and recommendation

- **Compliance monitoring:** use the *strict* end of R3 (full qualifier layer + externality + settlement pattern). Losing a substitution or a shared invoice is a control failure; tiny clusters are an acceptable price.
- **Operational segmentation:** R3 as defined here — semantically motivated, moderately granular — balances actionability with homogeneity of costs/risks.
- **Root-cause analysis:** start from a coarse R3 (e.g., S_spl family, motif flags as drill-down facets), refine downward; pure fine-grained equivalence buries cause patterns in noise, pure coarse ones average away the cause.
- **Descriptive reporting:** R1 enriched with externality presence/absence gives managers familiar, explainable "process variants."

No single level serves all four: compliance demands preservation (few false merges), segmentation demands population balance, root-cause demands hierarchy, and reporting demands legibility. Equivalence is therefore a *dial tied to purpose* — the error to avoid is not picking a point on the dial, but pretending the finest end (raw ids or exact hashes) is neutral ground rather than the least informative choice for almost every analytical question.
