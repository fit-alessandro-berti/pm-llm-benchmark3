### 4.1 Four-Eyes Violation Filtering

```python
import pm4py
import pandas as pd

# Load and format
df = pm4py.format_dataframe(
    event_log_df,
    case_id='case:concept:name',
    activity_key='concept:name',
    timestamp_key='time:timestamp',
    resource_key='org:resource'
)

# --- Rule 1: Create Purchase Order + Approve Purchase Order by same human ---
# Exclude bots from the check
human_resources = [r for r in df['org:resource'].unique()
                   if not r.startswith('Bot_')]

four_eyes_po = pm4py.filter_four_eyes_principle(
    df,
    activity1='Create Purchase Order',
    activity2='Approve Purchase Order',
    # Filter to human resources only
    resource_key='org:resource',
    timestamp_key='time:timestamp',
    case_id_key='case:concept:name',
    activity_key='concept:name'
)
# The returned object contains cases where the SAME resource
# performed both activities.  Further filter to human resources.

# --- Rule 2: Change Vendor Bank Details + Payment Approval ---
four_eyes_bank = pm4py.filter_four_eyes_principle(
    df,
    activity1='Change Vendor Bank Details',
    activity2='Payment Approval'
)

# --- Alternative: manual four-eyes check for more control ---
def manual_four_eyes_check(df, act1, act2):
    """Return cases where the same human resource performed both act1 and act2."""
    a1 = df[df['concept:name'] == act1][['case:concept:name', 'org:resource']].drop_duplicates()
    a2 = df[df['concept:name'] == act2][['case:concept:name', 'org:resource']].drop_duplicates()
    merged = a1.merge(a2, on=['case:concept:name', 'org:resource'], how='inner')
    # Exclude bots
    merged = merged[~merged['org:resource'].str.startswith('Bot_')]
    return merged

violations_po = manual_four_eyes_check(df, 'Create Purchase Order', 'Approve Purchase Order')
violations_bank = manual_four_eyes_check(df, 'Change Vendor Bank Details', 'Payment Approval')
violations_justification = manual_four_eyes_check(
    df, 'Emergency Override', 'Retrospective Justification'
)
```

# 6. Cautious Audit-Report Wording

**Observations on Procurement-to-Payment Process Compliance and Data Integrity**

Our analysis of the procurement-to-payment event log for the last quarter identified several control-exception patterns and data-quality limitations that warrant targeted follow-up. We emphasize that these observations reflect process deviations and evidential gaps; we have not identified direct evidence of fraud or intentional misconduct.

**Most Concerning Cluster.** The highest-priority area involves 44 cases in the vendor-master and accounts-payable process related to vendor family V-77x. In these cases, bank-detail changes and payment approvals were performed by a narrow resource pair (VendorMaster_Lena and AP_Kim), with unusually fast turnaround (median 17 minutes versus a global median of 7.8 hours), 83 percent of entries originating from manual uploads rather than the integrated ERP, and a high concentration in a single vendor family that recently underwent a banking-platform migration. Nine of these cases involved the same individual or tightly paired individuals performing both the bank-change and payment-approval steps, representing a four-eyes control exception. A missing linkage between maintenance tickets and procurement cases in the event log prevents automated reconciliation. We recommend independent confirmation of V-77x's current bank details and a manual review of the bank-change authorization documentation for these 44 cases.

**Emergency Procurement Channel.** We also identified 226 cases where the normal separation between PO creation and PO approval was bypassed, predominantly in emergency medical supplies and weekend facilities repairs. Approximately 80 to 88 percent of these cases carry an emergency flag consistent with a documented rush channel. However, 17 cases involving Emergency Override followed by Retrospective Justification performed by the same individual—including 12 that appear to have been batch-entered after quarter close—suggest that the compensating control requiring a different reviewer may not be operating effectively. We recommend confirming the existence and currency of the emergency-procurement policy and verifying the original timestamps of the retrospective justifications against migration logs.

**Data-Quality Limitations.** Several analytical conclusions are constrained by data-quality issues. A shared approver account ("Approver_Gita") and a resource-mapping error in the legacy ERP system reduce the reliability of resource-level attributions. Twelve retrospective-justification events share identical timestamps and appear to have been migrated from an offline spreadsheet. These limitations do not indicate wrongdoing but reduce the confidence with which resource-level controls can be assessed. We recommend that IT remediate the mapping error and that the shared account be decommissioned in favor of individual credentials with role-based access.

**Overall Assessment.** The emergency-handling and routine procurement patterns are largely consistent with expected operations, subject to the policy-confirmation steps noted above. The vendor-master bank-change cluster lacks a clear benign explanation at this stage and should be prioritized for document-level verification before the next reporting cycle.
