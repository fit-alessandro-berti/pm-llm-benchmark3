## 2. Equivalence and Sufficiency Test

Evaluating compensating control packages requires moving beyond simple activity counting or identical expected monetary loss. A control package must be assessed on its capacity to meet the underlying risk-mitigation objectives of FEP-1.

### 2.1 Sufficiency Criteria Framework

A compensating control package is classified under one of four equivalence tiers based on seven key dimensions:

```
                  +--------------------------------------------------------+
                  |         COMPENSATING CONTROL EVALUATION TIERS          |
                  +--------------------------------------------------------+
                                              |
     +-------------------+--------------------+--------------------+-------------------+
     |                   |                    |                    |                   |
     v                   v                    v                    v                   v
+------------------+ +------------------+ +------------------+ +------------------+
| Fully Equivalent | | Part. Equivalent | | Merely Mitigating| |   Ineffective    |
| - Pre-settlement | | - Pre-settlement | | - Post-settlement| | - Post-settlement|
| - Independent    | | - Minor gap      | | - Partial recovery| | - Uncontrolled   |
| - Complete cover | | - Low residual   | | - High tail risk | | - Severe breach  |
+------------------+ +------------------+ +------------------+ +------------------+
```

1. **Timing (Pre-settlement vs. Post-settlement):** Controls operating prior to bank settlement are preventive regarding external cash outbound exposure. Controls operating post-settlement are purely detective and partially corrective.
2. **Independence:** Segregation must be structural and hierarchical. A reviewer who reports to the operator (or vice versa) suffers from inherent conflict of interest. Shared credentials or physical workstations destroy independence.
3. **Coverage Depth:** Controls must cover both technical validity (AV-2 syntax/sanctions) and commercial legitimacy (three-way match, proof of delivery).
4. **Overrideability:** Controls where warnings can be bypassed by the same operator without independent dual-authorization offer low preventive assurance.
5. **Recoverability Window:** Detective controls executing within 24 hours of release retain corrective capacity via bank recall. Post-24-hour detection drops recoverability toward zero.
6. **Evidence Quality:** Verifiable electronic trails (signed PO, independent bank confirmation) outweigh unverified approvals or unsigned checklists.
7. **Collusion Resistance:** Controls must detect or impede co-located operators or repeated exclusive pairings acting in concert.

### 2.2 Equivalence Definitions

*   **Fully Equivalent:** Replaces FEP-1 with zero increase in net loss exposure or unmitigated risk pathways. Requires pre-settlement independent authorization (MG-4), fully operational automated checks (AV-2), and verified evidence of delivery.
*   **Partially Equivalent:** Preserves financial integrity before bank settlement but exhibits minor procedural defects (e.g., emergency token generated immediately after preparation, or ratification occurring post-release but prior to settlement).
*   **Merely Mitigating:** Reduces expected loss or probability of failure but leaves significant residual risk open (e.g., detective audit within 24 hours after settlement occurs without pre-settlement manager review).
*   **Ineffective:** Fails to prevent settlement, lacks independent oversight, permits unverified overrides, or conducts reviews after the bank recall window closes.

### 2.3 Why "Same Expected Loss" Is Insufficient

Evaluating equivalence purely by expected monetary loss ($\text{Exposure} \times \text{Probability of Failure}$) is inadequate in corporate control architecture for five reasons:
1. **Tail Risk and Asymmetry:** Expected loss conceals low-probability, catastrophic-impact events (e.g., AP-202 EUR 480k, AP-208 EUR 900k).
2. **Regulatory & Audit Governance:** Statutory frameworks require structural segregation of duties regardless of statistical risk modeling.
3. **Collusion and Fraud Adaptability:** Fraudulent actors adapt to static risk models; once an override mechanism is known to bypass dual authorization, exploit probability approaches 1.0.
4. **Systemic Trust and Deterrence:** Preventive controls serve as a structural deterrent. Replacing them with detective controls shifts the burden to uncertain legal recovery processes.
5. **Evidence Decay:** Post-hoc investigations suffer from information asymmetry and evidentiary decay, reducing the true probability of recovery below theoretical estimates.

### 4.2 Classification Semantics of Pre-Settlement Manager Ratification

A manager ratification occurring **after `Release_Payment` but before `Bank_Settlement`** (e.g., AP-201, AP-207) operates as a **Hybrid Control (Detective of Process, Preventive of Loss)**:

```
[ Prepare_Payment ] ---> [ Release_Payment ] ---> [ Manager_Ratify ] ---> [ Bank_Settlement ]
                                  |                      |                      |
                                  v                      v                      v
                          Process Violation      Detective Action       Preventive Barrier
                          (FEP-1 Breached)       (Catches Violation)    (Stops External Loss)
```

1. **Detective with respect to internal process flow:** Because the release action was taken by a single user without prior dual approval, a procedural violation has already occurred at the timestamp of `Release_Payment`. The manager's review detects this unratified state.
2. **Preventive with respect to external financial settlement:** Bank settlement is the point of financial irrevocability. Because the manager ratifies and confirms the transaction before the settlement window closes, the control successfully prevents unvalidated corporate funds from leaving the banking boundary.

## 6. Evidence and Monitoring Recommendations

### 6.1 Automated Indicator & Rule Definitions

To maintain robust governance, the system must deploy automated monitoring rules targeting process anomalies.

```
                   +--------------------------------------------------+
                   |          CONTINUOUS MONITORING ENGINE            |
                   +--------------------------------------------------+
                                            |
      +-------------------+-----------------+-------------------+-------------------+
      |                   |                 |                   |                   |
      v                   v                 v                   v                   v
+--------------+   +--------------+  +--------------+   +--------------+   +--------------+
| RULE-01      |   | RULE-02      |  | RULE-03      |   | RULE-04      |   | RULE-05      |
| Emergency    |   | Override     |  | Post-Release |   | Pair         |   | Outage       |
| Rate > 2%    |   | Velocity     |  | Approval     |   | Concentration|   | Overrides    |
+--------------+   +--------------+  +--------------+   +--------------+   +--------------+
```

1. **RULE-01: Emergency Token Utilization Rate**
   * *Threshold:* Any business unit exceeding a 2% emergency payment ratio over a rolling 30-day period.
   * *Logic:* `Count(ED-1 Payments) / Count(Total Payments) > 0.02`. Flags operational convenience abuse.
2. **RULE-02: Override Velocity and Identity Anomaly**
   * *Threshold:* Any user overriding >1 AV-2 warning per week or using credentials associated with a direct line manager.
   * *Logic:* Alert instantly on `Override_Warning` where `Resource(Override) != Active_Session_User` or `Resource(Override) == Manager_ID`.
3. **RULE-03: Post-Release Approval Delay**
   * *Threshold:* `Manager_Ratify` timestamp occurring after `Release_Payment`.
   * *Logic:* Flag any transaction where `Timestamp(Manager_Ratify) > Timestamp(Release_Payment)`. High-severity alert if `Timestamp(Manager_Ratify) > Timestamp(Bank_Settlement)`.
4. **RULE-04: Resource Pair Concentration (Collusion Risk)**
   * *Threshold:* Any pair of resources `(u_i, u_j)` handling >15% of each other's payments or >20 joint approvals per month.
   * *Logic:* Calculate pair frequency matrix $M_{ij}$. Flag pair if $M_{ij} / \sum M_{i} > 0.15$.
5. **RULE-05: Workstation / Session Correlation**
   * *Threshold:* `Prepare_Payment` and `Release_Payment` executed from identical IP addresses or system session IDs within 60 minutes, even if user accounts differ.
6. **RULE-06: Bank Modification Proximity**
   * *Threshold:* Any payment > EUR 50,000 released within 7 days of a bank account modification where AV-2 was bypassed or unavailable.
7. **RULE-07: Control Outage Release Block**
   * *Threshold:* `Release_Payment` executed while `AV-2` status is `Validation_Service_Unavailable`. Automated hard-block required.

### 6.2 Anomaly Alert vs. Conclusive Misconduct

It is vital for audit teams to distinguish between system alerts and proof of delinquency:
* **Automated Anomaly Alert (e.g., AP-206, AP-209):** Indicates a statistical outlier or procedural deviation (e.g., tight timing, repeated pairing, missing token pre-step). It establishes *heightened risk exposure* requiring investigation, but does not prove fraudulent intent or financial loss.
* **Conclusive Proof of Misconduct (e.g., AP-202):** Requires corroborating multi-source evidence proving intent or illegal action—such as credential theft, fabricated receipt documentation verified by vendors, or unauthorized funds routing to an employee-linked account.

### 7.1 PM4Py Behavioral & Version Notes
1. **`pm4py.filter_four_eyes_principle` Execution:** In PM4Py version 2.x and 3.x, `filter_four_eyes_principle` examines trace transitions between two named activities and returns a filtered log/dataframe containing traces where the `org:resource` attribute remains identical across both events.
2. **Handling System/Null Resources:** If system events (e.g., `Automated_Validate`) contain empty or missing resource fields, pandas converts them to `NaN`. They must be explicitly mapped to `"SYSTEM"` prior to passing to PM4Py; otherwise, resource comparison logic may emit unexpected null matches.
3. **Evidence vs. Verdict Distinction:** The Python code block extracts raw factual indicators (e.g., timestamp differences, resource equality, token pre-existence). It provides empirical evidence for audit review but **does not output the final compliance verdict**, which requires contextual reasoning across independence, commercial intent, and residual risk tiers.
