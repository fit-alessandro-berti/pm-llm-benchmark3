## 1. Modeling assumptions

- **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Object IDs are exactly `O100`, `O200`, `I1`, `I2`, `I3`, `P1`, `P2`, `D1`, `D2`, `V1`, `M1`, and `M2`.
- **E2O qualifier convention:** qualifiers are read from the event’s perspective. The vocabulary is:
  - `creates`, `closes` for Orders;
  - `adds` for an Item and `adds_to` for its Order;
  - `reserves` for an Item and `reserves_for` for an Order;
  - `packs` for an Item, `packs_into` for a Package, and `packs_for` for an explicitly involved Order;
  - `dispatches` for a Package and `dispatches_in` for a Delivery;
  - `issues` for an Invoice and `bills` for an Order;
  - `records` for a Payment and `applies_to` for its Invoice;
  - `confirms` for a Delivery.
- **O2O directions:** only the stated direction is stored, without inverse rows or transitive closure:
  - Order  Item: `contains`;
  - Package  Item: `packs`;
  - Delivery  Package: `carries`;
  - Invoice  Order: `bills`;
  - Payment  Invoice: `partially_settles` or `completes_settlement`.
- **Settlement convention:** I interpret the two installments together as settling V1, so M1 uses `partially_settles` and M2 uses `completes_settlement`. This does not allocate either payment to an Order. If completion is not actually known, M2 should instead use `partially_settles`; no other table needs to change.
- **Direct downstream relations:** `relations` contains explicit narrative involvement, not inferred lifecycle context:
  - E06 and E07 directly include O100 and O200 because their sharing is explicit.
  - E08 includes only P2 and I2; O100 is derivable through O2O but is not added as an observed E2O fact.
  - Dispatch and delivery-confirmation events include only their explicitly mentioned Packages and Deliveries, not propagated Orders or Items.
  - E11 includes V1, O100, and O200. Payment events include only their Payment and V1, not the billed Orders.
- **Source facts versus analytical propagation:** O2O composition is never silently converted into E2O evidence. This keeps source-style relations sparse and faithful, but means some flattened Order lifecycles are incomplete. If propagation is needed for an analysis, it should be materialized in a separate table, with qualifiers such as `derived:o2o` and path provenance, rather than overwriting `relations`.
- **PM4Py assumption:** the code targets a PM4Py release with the OCEL 2.0 constructor and the named top-level discovery functions. The constructor call is marked as the version seam. If an older release has a different constructor, use its documented mechanism for attaching O2O, or upgrade PM4Py; do not drop O2O or change the table semantics. Namespaced discovery or visualization calls can likewise be adjusted independently.

## 3. Data-model audit

**Objects**

| Object type | Objects |
|---|---|
| Order | O100, O200 |
| Item | I1, I2, I3 |
| Package | P1, P2 |
| Delivery | D1, D2 |
| Invoice | V1 |
| Payment | M1, M2 |

**O2O qualifiers**

| Qualifier | Direction | Cardinality |
|---|---|---:|
| `contains` | Order  Item | 3 |
| `packs` | Package  Item | 3 |
| `carries` | Delivery  Package | 2 |
| `bills` | Invoice  Order | 2 |
| `partially_settles` | Payment  Invoice | 1 |
| `completes_settlement` | Payment  Invoice | 1 |

**Direct E2O object types by activity**

| Activity | Object types touched directly |
|---|---|
| Create Order | Order |
| Add Item | Order, Item |
| Reserve Stock | Order, Item |
| Pack Package | Package, Item, and Order—Order only on E07 |
| Dispatch Package | Package, Delivery |
| Issue Invoice | Invoice, Order |
| Record Payment | Payment, Invoice |
| Confirm Delivery | Delivery |
| Close Order | Order |

E07 is especially consequential: its five relations make P1’s packing a shared, cross-order event. Removing its Order links would erase that convergence from Order flattening; adding broad propagated links would instead spread it into many additional object lifecycles. E06 is a four-object shared stock-reservation event, while E11 is the financial convergence of O100 and O200 on V1. The contrast between E07 and the much narrower E08 is also essential.

## 4. Expected flattened behavior

**Order**

- Approximate traces:
  - O100: Create Order  Add Item  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order.
  - O200: Create Order  Add Item  Reserve Stock  Pack Package  Issue Invoice  Close Order.
- E06, E07, and E11 are each copied into both Order traces. They remain single events in the source OCEL, but contribute two flattened event occurrences across the two traces.
- O100’s projection omits E08/P2, both dispatches, both delivery confirmations, and both payments. This is a consequence of the direct-relation policy, not a claim that those things are irrelevant to O100.
- Likely DFG edges are Create Order  Add Item, Add Item  Add Item, Add Item  Reserve Stock, Reserve Stock  Pack Package, Pack Package  Issue Invoice, and Issue Invoice  Close Order.
- Misleading readings include “each order had its own reservation, P1 packing, and invoice issuance,” “O100 had no second package,” and “Close Order was causally or temporally immediate after Issue Invoice.” The last edge is only a directly-follows edge in a sparse projection.

**Package**

- P1 and P2 should each have approximately Pack Package  Dispatch Package.
- No event is copied between the two Package traces. E07 is shared with Orders and Items, but it still belongs to only one Package trace, P1’s.
- Delivery confirmation, item/order composition, invoicing, payment, and order closure are omitted.
- The likely DFG is simply Pack Package  Dispatch Package, with Pack Package as start and Dispatch Package as end.
- The identical activity shapes hide the main business distinction: P1 combines I1 and I3 across O100 and O200, whereas P2 contains only I2. The projection also makes packages appear to end at dispatch.

**Delivery**

- D1 should be Dispatch Package  Confirm Delivery using E09 and E13; D2 should have the same activity shape using E10 and E14.
- There are no shared events copied between D1 and D2.
- Packing, package contents, orders, invoicing, and payments are omitted.
- The likely DFG is Dispatch Package  Confirm Delivery.
- The common shape hides both the different elapsed times and the fact that D1 carries cross-order P1 while D2 carries P2.

**Invoice**

- V1 should have one trace: Issue Invoice  Record Payment  Record Payment, corresponding to E11, E12/M1, and E15/M2.
- There is only one Invoice object, so there is no copying across multiple Invoice traces.
- Logistics, delivery confirmation, order closure, and the per-order billing split are absent from the activity trace.
- Likely DFG edges are Issue Invoice  Record Payment and Record Payment  Record Payment.
- The self-loop means two payment activities on V1, not that M1 was recorded twice. An activity-level DFG also ignores the 100/150 amounts and cannot justify an allocation between O100 and O200.

Flattening on **Payment** would be particularly weak: M1 and M2 would normally become two singleton Record Payment traces. There would be no internal DFG edges, no invoice issuance, and no visibility of the other payment. That is an artifact of flattening only direct Payment relations, not evidence that the payments are unrelated.

All log skeletons here are learned from only one or two traces per requested type. Their constraints are descriptive of this tiny example, not validated normative process rules.

## 5. Expected object-centric structures

- **OC-DFG:** It should expose the type-specific activity structure without reducing the OCEL to independent Order, Item, Package, Delivery, Invoice, and Payment logs. E06 and E07 provide the basis for recognizing shared behavior involving O100, O200, I1, and I3; E07 and P1 mark the cross-order packing convergence. Subsequent dispatch/delivery behavior separates into P1/D1 and P2/D2. E11 converges billing on V1, followed by E12/M1 and E15/M2 on the Invoice/Payment side. Because downstream propagation was not materialized, the OC-DFG need not show an Order-to-Delivery or Order-to-Payment chain.
- **OTG:** This is a type-level connectivity summary, not an instance graph. It should place Order, Item, Package, and Delivery on the logistics side and connect Order with Invoice and Payment on the financial side. P1 and V1 are important instance-level hubs, but an OTG does not name them directly. Exact edges can depend on whether the implementation emphasizes E2O interactions, O2O connectivity, or both.
- **ET–OT graph:** It should closely mirror the activity/type audit: Reserve Stock connects to Order and Item; Pack Package connects to Package, Item, and, through E07, Order; Issue Invoice connects to Invoice and Order; Record Payment connects to Invoice and Payment. Its type-level projection hides that E07 has five related objects while E08 has only two.
- **Object-centric Petri net:** A reasonable reading is that shared Reserve Stock, Pack Package, and Issue Invoice activities can synchronize behavior across object types, while V1 supports two Record Payment occurrences and O100/O200 have distinct Close Order events. However, the precise places, silent transitions, guards, and synchronization pattern depend on the discovery variant. There is **no uniquely determined interpretation**. In particular, the model should not be read as proving that M1 pays O100, M2 pays O200, or that either Close Order causally waits for D2’s confirmation or M2.
- **Object-interactions summary:** Multi-object activities should stand out. Reserve Stock involves four objects, Issue Invoice three, and Pack Package aggregates a five-object E07 with a two-object E08. This helps locate P1-style convergence and V1-style sharing. M1 and M2 each directly interact with V1 and their own Payment object; the summary does not supply a per-order payment allocation.

## 6. Modeling alternatives

1. **Source-minimal E2O relations.** Store only primary transaction payloads and explicit source foreign keys. For example, E06 could reference only I1/I3, E07 only P1/I1/I3, and E11 only V1, while Add Item retains its explicit Order context. Order flattening would then lose the shared reservation, packing, and billing events, and discovery would show much less synchronization. The underlying business story would be unchanged, but the OCEL would answer fewer order-centric questions.

2. **Full operational involvement.** Add direct `involves`-style links for every Order or Item whose work is considered advanced. E08 could include O100; dispatch and confirmation events could include their related Items and Orders; payments could include both billed Orders. Order traces would become much more end-to-end, but shared D1 and V1-related events would be copied into multiple flattened traces. Discovery could also misleadingly suggest that both Orders experienced or paid every payment event.

3. **Separately materialized O2O-propagated analytical relations.** Keep the baseline `relations` unchanged and derive a second view using explicit paths. For example, Confirm Delivery D1 could be propagated through D1  P1  I1/I3 and then to O100/O200; D2’s confirmation would reach O100 through P2/I2. Payments could reach O100/O200 through V1. Qualifiers and provenance should mark these rows as derived. Discovery would become richer but more densely connected, and the derived rows must not be described as source-system observations.

4. **Question-specific enrichment.** Propagate only logistics relations for a delivery-analysis view, or only V1-to-Order relations for a financial-analysis view. This limits relation inflation and makes each discovered model easier to interpret, but results from differently enriched views are not directly comparable.

## 7. Failure modes

1. **Relation inflation:** Full propagation can make later events touch large sets of Orders, Items, Packages, and financial objects. Activities then appear artificially broadly connected, and flattened frequencies increase without any new business events.
2. **Missing direct E2O links:** Sparse source relations can omit genuine analytical context. In this baseline, Order flattening omits P2, deliveries, and payments; conversely, accidentally dropping E07’s Order links would hide P1’s explicit cross-order nature.
3. **Treating O2O propagation as observation:** O2O states composition or settlement structure, not which objects an event originally referenced. Static O2O can also be unsafe for temporal propagation in datasets where relationships change over time.
4. **Duplicate shared events after flattening:** E06, E07, and E11 occur once in the OCEL but appear in both Order traces. DFG frequencies and performance calculations over the flattened log therefore must not be interpreted as original event counts.
5. **Ambiguous payment allocation:** V1 bills two Orders, but no per-order split is supplied. Propagating M1’s 100 or M2’s 150 to both Orders does not allocate those amounts, and M2’s settlement qualifier does not resolve the ambiguity.
6. **Overly short Payment traces:** Singleton Payment traces can produce an empty-looking DFG. Extending them with arbitrary financial events would be unjustified; Invoice flattening is the more informative view for the installment sequence.
7. **Constructor/API version mismatch:** Dropping `o2o` merely to make an older constructor run would silently change the model. The constructor or discovery namespace should be adapted explicitly, with the four tables left intact.
8. **False total order for same-time events:** This example has no timestamp ties, but in general sorting by event ID or stable input order is not evidence of causality. Flattening tied events into one order can create spurious DFG edges.
9. **Activity-label conflation:** “Pack Package” combines E07 and E08, while “Record Payment” combines M1 and M2. Activity-only DFGs and skeletons lose object identity, qualifiers, and payment amounts unless those details are inspected separately.
10. **Overinterpreting a tiny discovered model:** Two Orders and one Invoice do not establish general loops, mandatory synchronizations, or normative log-skeleton constraints. The object-centric Petri net and skeletons require the same caution as the DFGs.

## 8. Final semantic checks

1. `events` has exactly 17 unique IDs E01–E17, all timestamps are UTC-aware, and `objects` has exactly the 12 stated IDs under the six stated types.
2. E12 and E15 carry event attributes `amount = 100` and `amount = 150`; there is no Amount object and no fabricated per-order payment allocation.
3. E06’s relation set is exactly I1, I3, O100, and O200, with the stated qualifiers and the same activity/timestamp as E06 in `events`.
4. E07 relates exactly P1, I1, I3, O100, and O200. E08 relates only P2 and I2, demonstrating that O100 was not silently propagated into E08.
5. Dispatch and confirmation relations contain only their explicit Package/Delivery objects; payment events contain only M1/V1 or M2/V1. Thus no derived downstream Order or Item relations have been mixed into the baseline.
6. The O2O table shows P1 packing I1 and I3, P2 packing I2, D1 carrying P1, D2 carrying P2, and V1 billing both O100 and O200. It contains no inverse or transitive convenience rows.
7. M1 points to V1 with `partially_settles`; M2 uses `completes_settlement` only under the stated collective-settlement interpretation.
8. There are 34 nonduplicated E2O rows and 12 nonduplicated O2O rows. Every relation references existing event/object IDs, repeats its event’s activity and timestamp exactly, and uses the object type recorded in `objects`.
9. E16 closes O200 at 2026-04-07 10:30 UTC and E17 closes O100 at 10:35 UTC; neither close event is shared or reassigned to the other Order.
