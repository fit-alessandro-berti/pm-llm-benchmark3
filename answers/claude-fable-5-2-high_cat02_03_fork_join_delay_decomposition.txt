# 1. Delay-decomposition definitions

**Notation.** Case index `c` (F01..F12), branch index `i ∈ {A, B, C}`. Logged timestamps: `arr_c`, `fork_c`, `s_{c,i}` (branch start), `e_{c,i}` (branch end), `fs_c`, `fe_c` (final start/end). All durations are in minutes.

| Symbol | Formula | Meaning | Status |
|---|---|---|---|
| `U_c` | `fork_c − arr_c` | upstream elapsed time before fork release (upstream queue + service, not separable) | observed |
| `Q_{c,i}` | `s_{c,i} − fork_c` | branch-specific queue wait | observed, conditional on A3 |
| `S_{c,i}` | `e_{c,i} − s_{c,i}` | branch active service | observed, conditional on A2 |
| `O_{c,i}` | `Q_{c,i} + S_{c,i} = e_{c,i} − fork_c` | branch completion offset from the fork | observed |
| `J_c` | `max_i e_{c,i}` | `join_ready` | derived, conditional on A1 |
| `K_c` | `{ i : e_{c,i} = J_c }`, label `k(c)` = first member in the fixed order A, B, C | critical branch (set if tied; each member gets credit `1/|K_c|`) | derived |
| `W_{c,i}` | `J_c − e_{c,i} ≥ 0` | branch synchronization wait after completion (0 for the critical branch) | derived |
| `M_c` | `J_c −` second-largest `e_{c,i}` | criticality margin = largest gain in `J_c` obtainable by accelerating the critical branch alone | derived |
| `T^FJ_c` | `J_c − fork_c = max_i O_{c,i} = Q_{c,k(c)} + S_{c,k(c)}` | elapsed fork-join stage time | derived |
| `D_c` | `fs_c − J_c` | downstream waiting before F ("queue" only if A4 holds) | derived |
| `F_c` | `fe_c − fs_c` | final service | observed |
| `T_c` | `fe_c − arr_c` | total case flow time | observed |

**Additive elapsed-time identity (no double counting).**

`T_c = U_c + T^FJ_c + D_c + F_c = U_c + Q_{c,k(c)} + S_{c,k(c)} + D_c + F_c`

Only the critical branch's queue and service enter the elapsed-time ledger, because the three branches occupy the same clock interval `[fork_c, J_c]`.

**Why summing synchronization waits double counts.** For every branch separately, `Q_{c,i} + S_{c,i} + W_{c,i} = T^FJ_c`. Summing this over the three branches gives

`Σ_i (Q_{c,i} + S_{c,i} + W_{c,i}) = 3 · T^FJ_c`, hence `Σ_i W_{c,i} = 3 · T^FJ_c − Σ_i O_{c,i}`.

The waits of different branches overlap in clock time, so `Σ_i W_{c,i}` is a quantity in *branch-minutes* (work-in-progress held idle), not in elapsed minutes. Example F07: A waits 10:30–10:55 (25 min) and C waits 10:03–10:55 (52 min); A's wait lies entirely inside C's. Their sum, 77, exceeds the whole stage time of 75. Adding everything naively gives `20 + (0+30+5) + (50+45+18) + (25+0+52) + 15 + 20 = 280` versus a true flow time of 130; the excess is exactly the stage time counted three times instead of once (`20 + 3·75 + 15 + 20 = 280`).

I therefore keep two ledgers and never mix them:

- **Elapsed-time ledger** (adds up to flow time): `U`, critical-branch `Q`, critical-branch `S`, `D`, `F`.
- **Branch-time ledger** (adds up to `3 · T^FJ`): all `Q_{c,i}`, `S_{c,i}`, `W_{c,i}`. In aggregate: `355 + 1292 + 549 = 2196 = 3 × 732`.

**Assumptions (labelled).**

- **A1 – AND-join rule is exact.** `join_ready` is not logged; I need the stated rule to set it to the latest branch completion. If an unlogged step sits between the branches and F (hand-over, dossier assembly), it is absorbed into `D_c`.
- **A2 – No preemption.** Start-to-end is treated as active service. Needed because only start and end are logged; `S` is therefore an upper bound on true hands-on work.
- **A3 – `fork_release` is a genuine, common earliest-start time for all three branches.** Needed to interpret `s_{c,i} − fork_c` as queueing. Note the observation that `A_start = fork_release` in all 12 cases, so I cannot exclude that `fork_release` is logged as "first branch start"; in that case A's queue would be zero by construction and hidden A waiting would sit inside `U_c`.
- **A4 – Waiting before F is a queue.** Needed to call `D_c` "downstream queueing". The data argue against taking this at face value (section 3).
- **A5 – One-minute accuracy.** Each duration carries about ±1 min. No exact ties occur and the smallest margin is 5 min, so the critical-branch labels do not depend on rounding.
- **A6 – Ceteris paribus counterfactuals.** When one duration is changed, all other logged durations are held fixed. Needed because the log contains no information on how queues react to changed load.

**Worked calculations.**

**F02** (B-critical through queueing)
- `U = 08:25 − 08:05 = 20`.
- A: `Q = 08:25 − 08:25 = 0`, `S = 09:15 − 08:25 = 50`, ends 09:15.
- B: `Q = 08:45 − 08:25 = 20`, `S = 09:25 − 08:45 = 40`, ends 09:25.
- C: `Q = 08:30 − 08:25 = 5`, `S = 08:50 − 08:30 = 20`, ends 08:50.
- `J = max(09:15, 09:25, 08:50) = 09:25` → critical branch B; runner-up A, margin `09:25 − 09:15 = 10`.
- Sync waits: `W_A = 10`, `W_B = 0`, `W_C = 35`.
- `T^FJ = 09:25 − 08:25 = 60 = Q_B + S_B = 20 + 40`.
- `D = 09:40 − 09:25 = 15`; `F = 10:00 − 09:40 = 20`.
- `T = 20 + 60 + 15 + 20 = 115 = 10:00 − 08:05`. ✔
- Remark: B's service (40) is shorter than A's (50); B is critical only because of its 20-minute queue.

**F04** (C-critical through a queue spike)
- `U = 08:55 − 08:35 = 20`.
- A: `Q = 0`, `S = 50`, ends 09:45. B: `Q = 09:05 − 08:55 = 10`, `S = 30`, ends 09:35. C: `Q = 09:30 − 08:55 = 35`, `S = 09:52 − 09:30 = 22`, ends 09:52.
- `J = max(09:45, 09:35, 09:52) = 09:52` → critical branch C; runner-up A, margin 7.
- Sync waits: `W_A = 7`, `W_B = 17`, `W_C = 0`.
- `T^FJ = 57 = Q_C + S_C = 35 + 22`.
- `D = 10:10 − 09:52 = 18`; `F = 20`.
- `T = 20 + 57 + 18 + 20 = 115 = 10:30 − 08:35`. ✔
- Remark: even deleting C's whole queue would save at most 7 min at the join, because A's 50-minute floor takes over at 09:45.

**F07** (longest case)
- `U = 09:40 − 09:20 = 20`.
- A: `Q = 0`, `S = 50`, ends 10:30. B: `Q = 10:10 − 09:40 = 30`, `S = 10:55 − 10:10 = 45`, ends 10:55. C: `Q = 5`, `S = 18`, ends 10:03.
- `J = 10:55` → critical branch B; runner-up A, margin 25.
- Sync waits: `W_A = 25`, `W_B = 0`, `W_C = 52` (sum 77 > stage time 75: the double-counting example of section 1).
- `T^FJ = 75 = 30 + 45`.
- `D = 11:10 − 10:55 = 15`; `F = 20`.
- `T = 20 + 75 + 15 + 20 = 130 = 11:30 − 09:20`. ✔

**F11** (A-critical)
- `U = 10:40 − 10:20 = 20`.
- A: `Q = 0`, `S = 50`, ends 11:30. B: `Q = 10:50 − 10:40 = 10`, `S = 30`, ends 11:20. C: `Q = 5`, `S = 18`, ends 11:03.
- `J = 11:30` → critical branch A; runner-up B, margin 10.

**Reading the table.**

- *Service alone misleads.* A has the largest mean service (50 vs 37.5 vs 20.2) yet is critical in only 2 cases. B's service never exceeds 45, so on service alone B would never beat A's 50; it is B's queue (mean 19.2) that pushes its completion offset to a mean of 56.7 and a maximum of 75.
- *B controls the variation and the tail.* B is critical in 8 of 12 cases, in all five cases with flow time ≥ 120, and both 75-minute stage times (F07, F12) combine B's longest queue (30) with its longest service (45). B's margins sum to 120 of the 147 margin-minutes (82%).
- *A is the floor.* A's offset is exactly 50 in every case and A is the runner-up in all 10 cases where it is not critical. The mean stage time of 61.0 is a 50-minute A floor plus 11.0 minutes of excess caused by B (8 cases) or C (2 cases). The 11.0 is also A's mean synchronization wait: finished assays wait for the other branches.
- *C is slack except for exceptions.* C's mean synchronization wait of 30.4 minutes is the largest, i.e. it normally finishes far too early to matter. It became critical twice (F04, F08), both times with an unusual queue (35 and 25 against a median of 5) and somewhat longer service (22 and 30), and both times by a small margin (7 and 5).

**Ties and near-ties (reported honestly).**

- No exact ties in the observed data; the deterministic rule (A before B before C, fractional credit) was not triggered at baseline.
- Three cases are decided by only 5 minutes: F01 (A over B), F08 (C over A), F10 (B over A). Treating these as ambiguous, the critical counts become ranges: B 7–9, A 1–4, C 1–2. B leads under every resolution.
- A and C are tied on critical frequency (2 each) and nearly tied on margin sums (15 vs 12 minutes). On those two metrics alone I cannot rank them with 12 cases.

**Reasoned influence ranking.**

1. **B** – strongest control of total completion time at the margin: most frequent critical branch, sole driver of the long cases, and by far the largest attainable gain (120 margin-minutes). The lever is its queue, not its service.
2. **A** – second, as the structural floor: rarely the last to finish today, but the runner-up 10 times, so it caps what any improvement to B or C can deliver and becomes the dominant critical branch as soon as B improves (section 4). If the question were "which branch explains the *level* of stage time", A would rank first (600 of 732 stage-minutes lie under its 50-minute floor); for "which branch moves completion time if changed", it ranks second.
3. **C** – third: critical twice by small margins, driven by case-specific queue spikes, with large slack otherwise. Its separation from A rests on A's runner-up role rather than on critical frequency, where they tie.

**Does the final station mask branch effects?**

Observations on the final station:

- Every case waits between 8 and 20 minutes after `join_ready` (mean 14.67), although the two resources are busy only 56.6% of the observed span (240 service-minutes over 2 × 212).
- F1 and F2 alternate strictly in case order (F01→F1, F02→F2, ...).
- Splitting each wait into "own assigned resource still busy" and "resource idle, case ready, nothing starts":

|---|---:|---:|---:|---:|
| F01 | 8 | 0 | 8 | 0 |
| F02 | 15 | 0 | 15 | 0 |
| F03 | 15 | 0 | 15 | 0 |
| F04 | 18 | 8 | 10 | 0 |
| F05 | 10 | 10 | 0 | 10 |
| F06 | 15 | 0 | 15 | 0 |
| F07 | 15 | 0 | 15 | 0 |
| F08 | 15 | 15 | 0 | 0 |

Interpretation (hypotheses, not observations):

- At most 73 of 176 minutes (41%) coincide with the assigned resource being busy, and only 25 minutes (14%) with both resources being busy. The majority of the wait is not explained by observed occupancy. Candidates: a hand-over or transport lag, a release rhythm, pre-assignment of cases to F1/F2 (suggested by the alternation), resource calendars, or unlogged other work.
- The downstream wait does not shrink when the stage is long (correlation −0.24, weak), so there is no sign that it routinely absorbs branch delay. But in 6 cases (F04, F05, F08, F09, F10, F11) the assigned resource is busy at `join_ready`, so for those cases an earlier `join_ready` would not translate one-for-one into an earlier start unless the predecessor on that resource also moves. Masking is therefore partial and case-specific; section 4 quantifies it.

# 4. Counterfactual redesign analysis

**Translating a change in `join_ready` into flow time requires a model of the final station.** I report three, because the data cannot choose between them:

- **M0 – fixed release (lower bound for branch changes).** If F starts are driven by a schedule or by resource calendars, earlier `join_ready` saves nothing.
- **M1 – pass-through.** Each case keeps its observed downstream wait; flow-time saving equals the join gain.
- **M2 – resource replay.** Each case keeps its observed resource and position; `start = max(new join_ready, previous end on that resource) + observed idle gap`. This reproduces the observed schedule exactly at baseline. It lets resource blocking mask gains, but also lets gains propagate to later cases on the same resource, so M2 can exceed M1; M1 is not an upper bound.

All numbers below are estimates under A6. Final service stays at 20 minutes.

| CF1: A service −20% (50 → 40) | 15 (2) | 15 / 1.25 | 5 / 0.42 | 130 / 130 | 0.5 / 9.5 / 2 |

Half-minute values arise from halving odd queue lengths; under one-minute timestamp accuracy they should be read as ±1.

**CF1 – reduce A service by 20%.**

- *Direct benefit:* only the two A-critical cases. F01 gains 5 (B becomes critical at 08:55, so half of A's 10-minute reduction is wasted); F11 gains the full 10 and ends in an exact A = B tie at 11:20 (recorded as A by the tie rule, credited 0.5 each).
- *Zero benefit:* the 8 B-critical cases (F02, F03, F05, F06, F07, F09, F10, F12) and the 2 C-critical cases (F04, F08).
- *Ceiling:* the join gain of 15 equals A's entire margin sum, so no further A acceleration can add anything while B and C stay as they are.
- *Masking:* under M2, F11's gain disappears because F1 is busy with F09 until 11:50; total saving drops from 15 to 5 minutes. Under M0 it is 0.
- *Secondary effects:* no effect on the longest cases; A's mean synchronization wait rises from 11.0 to 19.75 minutes (assays finish earlier and wait longer, which may matter if results or samples age); about 120 minutes of A capacity are freed across the 12 cases. Because A's duration is exactly 50 in all cases it may be a fixed protocol time, in which case a 20% cut may not be technically available (hypothesis).

**CF2 – reduce B queue delay by 50%.**

- *Direct benefit:* the 8 B-critical cases gain at the join: F02 10, F03 10, F05 10, F06 15, F07 15, F09 12.5, F10 5, F12 15 (sum 92.5).
- *Truncated benefit:* in F05 (10 of 12.5) and F10 (5 of 10) A becomes critical before the full B reduction is realized; F02 and F06 end in exact A = B ties.
- *Zero direct benefit:* F01 and F11 (A critical), F04 and F08 (C critical).
- *Tail:* the maximum flow time falls from 130 to 115; F07 and F12 each gain 15.
- *Masking and knock-on (M2):* F06 realizes only 8 of its 15 because F2 is still occupied by F04, but cases that had no join gain benefit indirectly because their predecessors on the same resource finish earlier (F04 +8, F08 +8, F11 +15). Net: 122 minutes under M2 versus 92.5 under M1, and 0 under M0.
- *Diminishing returns:* removing the *whole* B queue yields a join gain of 120, so the second half of the reduction is worth only 27.5 minutes. After full removal B is never critical (A 10, C 2).
- *Secondary effects:* criticality shifts to an even A/B split (5 / 5 / 2), making A the next constraint; mean synchronization wait falls for A (11.0 → 3.3) and C (30.4 → 22.7) and rises slightly for B (4.3 → 6.2); the final station receives cases earlier and closer together. How the queue is cut matters: extra B capacity lowers B utilization, whereas re-prioritization may push delay onto work that is not in this log.

**CF3 – add final-station capacity or otherwise reduce downstream waiting.**

- *CF3a, capacity only:* if a third resource removes resource blocking but the unexplained idle gap remains, the saving is the blocked part: F04 8, F05 10, F08 15, F09 15, F10 5, F11 20 = 73 minutes (6.08 per case). Six cases (F01, F02, F03, F06, F07, F12) get nothing because their assigned resource was already idle, and the maximum flow time stays at 130. If F1 and F2 are in fact already pooled, the capacity-attributable part is only 25 minutes (2.1 per case).
- *CF3b, pooling plus release on `join_ready` with the existing two resources:* 171 of the 176 minutes disappear (14.25 per case); only F11 still waits 5 minutes because three cases are ready between 11:30 and 11:35. Every case benefits (8 to 20 minutes), independent of which branch is critical. Maximum flow time 130 → 115.
- *CF3c, third resource plus immediate start:* 176 minutes; the extra resource adds just 5 minutes over CF3b in this sample and would lower utilization to roughly 38%.
- *Cases with zero benefit because another branch is critical:* none; this change acts after the join and leaves the critical-branch mix unchanged (2 / 8 / 2).
- *Secondary effects and caveat:* the result depends entirely on whether the idle gap is removable. If it is a necessary hand-over (transport, file assembly, mandatory checks), CF3b overstates the gain and the realistic figure lies between 25 and 73 minutes. Faster release also removes the buffer that currently hides branch variability from the decision makers.

**Additional counterfactuals.**

- *CF4, cap C's queue at 5:* join gain 12 (F04 7, F08 5), limited by A's floor; under M2 both gains are fully masked because F2 is busy in both cases. C improvements have the weakest case.
- *CF5, CF1 and CF2 together:* join gain 117.5 versus 15 + 92.5 = 107.5 separately. The extra 10 minutes (F01 +2.5, F05 +2.5, F10 +5) show that at an AND-join, improvements to the two near-critical branches are complements: each releases gains the other would have truncated.
- *CF6, CF2 plus CF3b:* 268.5 minutes, i.e. mean flow time 115.25 → 92.9 (−19.4%) and maximum 130 → 100.

**Answer to the masking question.** Final-station behaviour masks branch improvements partially and unevenly: fully under M0, case by case under M2 (F11 in CF1, F04 and F08 in CF4, F06 in CF2), not at all under M1. Since the larger part of the downstream wait is not capacity-related, changing the release behaviour at F is what makes branch gains convert reliably.

# 5. Recommended redesigns and risks

**Recommendation 1 – Cut the Machine Stress Test queue (B), aimed at the long tests.**

- *What:* reduce B waiting through scheduling and, if needed, capacity. The observed pattern suggests where to look: B queue and B service are positively correlated (0.57); the 30-minute tests waited 5–10 minutes while the 45-minute tests waited 20–30, and B is not served in release order (F08, released at 09:55, starts at 10:00, before F07, released at 09:40, starts at 10:10). A plausible reading is separate machine classes or priorities (hypothesis).
- *Flow-time tail:* the strongest lever on the tail. A 50% cut takes the maximum from 130 to 115 and removes 10–15 minutes from each of the five longest cases; estimated mean saving 7.7 (M1) to 10.2 (M2) minutes per case, 0 if F releases on a fixed rhythm.
- *Throughput:* arrivals are regular (about one case per 15 minutes) and every case completes, so output is arrival-limited in this sample; expect lower work-in-progress rather than more output. By Little's law, 4 cases/hour × 115.25 minutes ≈ 7.7 cases in process; each 10 minutes saved removes about 0.67 cases of WIP.
- *Resource utilization:* unknown for B (no resource identifiers). If the cut comes from added machines, B utilization falls; if from re-sequencing, utilization is unchanged but other work may wait longer.
- *New bottlenecks:* A. After a 50% cut A is critical in 5 cases, after full removal in 10, and the gain saturates at 120 minutes. Only then does accelerating A pay off (CF5). The final station will also see more closely spaced arrivals.
- *Synchronization effects:* total idle branch-minutes at the join fall from 549 to about 387; A and C results wait less, B results slightly more.
- *Pilot and measure first:* log B queue-entry time, machine identifier and test class; confirm whether the long tests share a constrained machine; trial one sequencing rule or one additional slot for the long class for a limited period; track B queue by class, critical-branch share, margin distribution, `join_ready` offset and end-to-end flow time, and watch A's critical share as the leading indicator of saturation.

**Recommendation 2 – Change the release behaviour at the final station before adding capacity: pool F1/F2 and trigger F on `join_ready`.**

- *What:* make `join_ready` an explicit logged event that immediately offers the case to whichever of F1/F2 is free, replacing the apparent alternating pre-assignment.
- *Flow-time tail:* every case benefits; the ceiling is 14.25 minutes per case with the existing two resources (171 of 176 minutes) and the maximum falls from 130 to 115. Combined with Recommendation 1 the estimate is a maximum of 100 and a mean of 92.9.
- *Throughput:* station capacity is 6 cases/hour against roughly 4 arriving, so throughput is not constrained there; the gain is earlier decisions and lower WIP.
- *Resource utilization:* the same 240 service-minutes; observed utilization of 56.6% (about 67% at a steady four cases per hour) leaves room, which is why a third resource adds only 5 minutes in this sample. Capacity alone, without changing release behaviour, yields 25–73 minutes in total and no tail improvement.
- *New bottlenecks:* F1/F2 lose slack that may currently be used for unlogged tasks; if Recommendation 1 bunches arrivals, short genuine queues will appear (F11's residual 5 minutes is the first sign).
- *Synchronization effects:* none on the branches. It removes the post-join buffer, so branch lateness becomes visible immediately at F and branch improvements pass through to flow time.
- *Risks:* the idle gap may be necessary work (hand-over, document assembly, a mandated waiting period) or a calendar effect; then the achievable gain is much smaller. Pooling may conflict with specialization of F1 and F2.
- *Pilot and measure first:* for a limited period record the `join_ready` moment, a reason code for each wait before F, and what F1/F2 do while idle in the log; then pilot pooled assignment on one shift and compare the blocked-versus-gap split, utilization and flow time.

**Deliberately not recommended as first steps:** accelerating A on its own (ceiling 15 minutes in total, none in the long cases) and general C improvements (ceiling 12 minutes, fully masked under M2). For C, a targeted look at why F04 and F08 waited 35 and 25 minutes is cheap and sufficient.

FS = pd.Timedelta(minutes=20)       # final service kept as observed (20 min everywhere)


def branch_ends(a_service_factor=1.0, b_queue_factor=1.0, c_queue_cap=None):
    """Recompute branch completion times; every other duration stays as observed."""
    e = pd.DataFrame(index=df.index)
    e["A"] = df["fork_release"] + pd.to_timedelta(
        d["A_queue"] + a_service_factor * d["A_service"], unit="m")
    e["B"] = df["fork_release"] + pd.to_timedelta(
        b_queue_factor * d["B_queue"] + d["B_service"], unit="m")
    cq = d["C_queue"] if c_queue_cap is None else d["C_queue"].clip(upper=c_queue_cap)
    e["C"] = df["fork_release"] + pd.to_timedelta(cq + d["C_service"], unit="m")
    return e


def final_pass_through(jr):
    """M1: every case keeps its observed downstream wait (final station neutral)."""
    return jr + pd.to_timedelta(d["downstream_queue"], unit="m")


def final_replay(jr):
    """M2: same resource and same per-resource order as observed;
    start = max(join_ready, previous end on that resource) + observed idle gap.
    Reproduces the observed schedule exactly when jr is the observed join_ready."""
    start = pd.Series(pd.NaT, index=df.index, dtype="datetime64[ns]")
    for _, grp in df.sort_values("final_start").groupby("final_resource"):
        prev = None
        for c in grp.index:
            base = jr[c] if prev is None else max(jr[c], prev)
            start[c] = base + pd.Timedelta(minutes=float(d.loc[c, "gap"]))
            prev = start[c] + FS
    return start


def final_pooled_fifo(jr, servers, lag=0.0):
    """M3: pooled, work-conserving FIFO on join_ready with `servers` resources
    and a fixed handover lag (0 = start the moment a resource and the case are ready)."""
    free = [pd.Timestamp.min] * servers
    start = pd.Series(pd.NaT, index=df.index, dtype="datetime64[ns]")
    for c in jr.sort_values(kind="stable").index:
        k = min(range(servers), key=lambda i: free[i])
        start[c] = max(jr[c] + pd.Timedelta(minutes=lag), free[k])
        free[k] = start[c] + FS
    return start

                          "max_min": round(v["max"] / 60.0, 2)}

# 7. Limits of inference

- **Sample size and window.** Twelve cases from one morning with regular arrivals. All percentages, correlations and "tail" statements are descriptive of this sample; no confidence intervals are meaningful, and three critical-branch labels rest on 5-minute margins. F01 enters an apparently empty system (its upstream time and downstream wait are the smallest observed), so a warm-up effect is likely.
- **Causality.** "Critical" means last to complete, not cause of delay. B's queue may itself be caused by product mix, shared machines, upstream release timing or work outside this log. The queue–service correlation in B (0.57) and the co-occurrence of long C waits with short B tests (F04, F08) are patterns in 12 cases, not established mechanisms. All counterfactuals hold other durations fixed (A6); real queues react to changed load.
- **Branch resource capacity.** There are no resource identifiers for A, B or C. Observed concurrency (A 4, B 4, C 3) is only a lower bound on capacity. A's zero queue does not prove spare capacity (see A3). In C, F04 and F08 waited while no C work was observed (09:03–09:15 and 10:03–10:15) and were overtaken by later-released cases; I cannot tell whether that reflects unlogged work, absent staff, missing documents or a priority rule. In B, I cannot distinguish a non-FIFO discipline from separate machine classes.
- **Preemption and true service.** Only start and end are logged. Interruptions, pauses, batching or multitasking inside an interval are invisible, so "service" is an upper bound on active work and "queue" a lower bound on waiting. A's identical 50 minutes in every case suggests a fixed-duration procedure, but that is a hypothesis.
- **Meaning of `fork_release` and upstream time.** Whether all three branches could genuinely start at `fork_release` is assumed, not observed. Upstream elapsed time (20 minutes in 11 cases, 15 in one) cannot be split into queue and service and looks schedule-like.
- **`join_ready` is derived.** If the join needs anything beyond the three completions, the true ready time is later and part of the "downstream wait" is really stage time.
- **Queue or release policy at F.** The timestamps cannot identify why cases wait before F. Most of the wait occurs while at least one resource shows no logged activity, which is compatible with a hand-over lag, a release rhythm, pre-assignment to F1/F2, calendars or unlogged tasks, and incompatible with a pure work-conserving pooled queue. The split "73 blocked / 103 gap" depends on assuming cases are tied to their observed resource; under pooling it is "25 / 151". Consequently the three final-station models (M0, M1, M2) bracket rather than pin down how much branch improvement reaches total flow time, and the CF3 savings range from 25 to 176 minutes depending on what the wait really is.
- **Measurement precision.** One-minute accuracy gives roughly ±1 minute per duration; this does not alter any ranking here, but half-minute counterfactual values and differences of 1–2 minutes should not be over-read.
- **Scope.** Costs, quality outcomes, rework, release-decision results and the effect of redesigns on other products or shifts are not in the data, so the recommendations are prioritized hypotheses to pilot, not proven improvements.
