# 1. Review Scope and Assumptions

I distinguish four uses:

1. **Exploration and discovery:** A tolerant model may help analysts inspect incomplete or noisy logs. High fitness can be useful even when the model is not normative, provided deviations and missing events are not reclassified as permitted behavior.
2. **Conformance enforcement and audit:** The model must preserve mandatory controls, reject known forbidden behavior, and return **uncertain/manual review** rather than “compliant” where required attributes are unavailable.
3. **Simulation and forecasting:** The model needs sound control flow plus defensible routing probabilities, data conditions, resource rules, and rework frequencies. Neither submission currently provides these.
4. **Stakeholder communication and change impact analysis:** Compact, compositional rules are preferable to global variant enumeration, but simplicity must not erase mandatory controls.

The acceptable fitness/precision trade-off therefore depends on use. For exploration, Model S’s high fitness and low runtime may be useful. For enforcement, optionalizing mandatory checks is unacceptable regardless of fitness. Conversely, Model C’s conservative false rejections might be temporarily tolerable in a manually reviewed whitelist, but its rejection of explicitly valid combinations means it should not be called a faithful policy model.

I assume standard PM4Py process-tree semantics:

- `->` is sequence;
- `+` is parallel execution of all children;
- `X` is exclusive choice;
- `tau` is silent;
- a visible leaf normally executes at most once unless enclosed in a loop;
- acceptance means complete-trace acceptance, not merely fitting a prefix.

The source attribute and affected-check attribute are genuinely unavailable unless enriched from another system.

# 3. Adversarial Review of Model S

**Strongest case for Model S**

Model S is compact, fast, and understandable. It captures:

- fixed registration and release endpoints;
- either approval mechanism;
- optional Supplier and Expedite Reviews;
- arbitrary order among selected review activities;
- tolerance of missing events.

For exploratory analysis of an incomplete event log, these properties can be valuable. Its holdout fitness suggests it is less sensitive to new combinations than Model C. Its low duplicate-label count also makes structural ownership and change analysis easier.

**Strongest case against Model S**

Its apparent robustness comes partly from changing mandatory policy into optional behavior. Under standard semantics, all four parallel children may choose `tau`, and any selected visible children may occur in any interleaving. Consequently, it admits at least the following undesirable or unresolved traces:

1. `Register Dossier, Manager Approval, Release Order`  
   Both mandatory checks are skipped.

2. `Register Dossier, Credit Check, Auto Approval, Release Order`  
   Technical Review is skipped.

3. `Register Dossier, Technical Review, Manager Approval, Release Order`  
   Credit Check is skipped.

4. `Register Dossier, Expedite Review, Manager Approval, Release Order`  
   Both checks are skipped while Expedite Review still occurs.

5. `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   Expedite Review precedes both mandatory checks.

6. `Register Dossier, Credit Check, Expedite Review, Technical Review, Auto Approval, Release Order`  
   Expedite Review occurs before completion of both checks.

7. `Register Dossier, Supplier Review, Manager Approval, Release Order`  
   Supplier Review does not compensate for the missing mandatory checks.

8. For an order known to be internal:  
   `Register Dossier, Credit Check, Technical Review, Supplier Review, Auto Approval, Release Order`  
   This is policy-ambiguous or forbidden if P3 means Supplier Review occurs iff the order is external.

Model S also rejects all correction traces because `Correct Dossier` is absent, and it rejects legitimate corrected rechecks as well as suspicious uncorrected repeats.

**Intentional tolerance versus accidental semantic flaws**

- The `tau` choices appear to be intentional tolerance for missing events. That can be appropriate in an **observation/noise model**, but not in the normative policy language.
- Making Credit Check and Technical Review optional is therefore intentional noise tolerance with an unacceptable enforcement consequence.
- Placing Expedite Review in the same parallel block as the mandatory checks is a separate semantic flaw: it confuses optionality with ordering.
- Making Supplier Review unconditionally optional is an explicit approximation forced by missing source data, but the approximation must produce an uncertainty status rather than silent compliance.
- Omitting correction behavior is underfitting, not permissiveness.

The advocate is correct that low precision may be acceptable for exploration. It does not follow that Model S is suitable for audit or enforcement.

# 4. Adversarial Review of Model C

**Strongest case for Model C**

Model C is a conservative whitelist of eight familiar variants. Every branch:

- starts and ends correctly;
- includes both mandatory checks;
- contains exactly one approval;
- places Expedite Review, when present, after both checks;
- avoids an uncorrected repeated mandatory check.

Its high training precision is consistent with enabling little behavior outside the enumerated training variants. In a temporary, manually governed whitelist where unlisted behavior is routed for review rather than automatically declared illegal, this conservatism can reduce false acceptance.

**Strongest case against Model C**

Model C enumerates global traces rather than composing local policy decisions. This creates several pathologies:

- **Alternate check order, approval type, Supplier Review, and Expedite Review are coupled accidentally.** For example, Auto Approval is available only on the exact `Credit Check, Technical Review` branch without Supplier, Expedite, or correction.
- **Supplier Review is not data-conditioned.** It appears only in selected Manager Approval branches and cannot establish P3.
- **Expedite Review is only available with Manager Approval and `Credit Check` before `Technical Review`.** It does not support Expedite before Supplier Review, despite P4.
- **Correction is hard-coded once and always repeats both checks.** It excludes Credit-only and Technical-only rechecks, multiple corrections, Auto Approval after correction, and Supplier/Expedite combinations with correction.
- **Duplicate labels are distributed across global branches.** A change to Credit Check, approval ownership, or a review ordering rule must be inspected in many copies.
- **Unseen combinations are rejected even when all constituent choices are independently allowed by policy.** This directly matches F2 and F4.
- **The large holdout decline is consistent with variant memorization.** It may be conservative, but it is not a general policy representation.
- **High training precision may be an artifact.** Enumerating frequent positive variants naturally suppresses unobserved combinations. Positive-log-only precision cannot tell whether the suppressed combinations are actually forbidden.

Model C is therefore not “audit-ready” merely because it is precise on its training log. An audit-ready model must trace each restriction to policy, represent conditions such as sourcing, and have tested behavior on curated negative cases.

# 6. Likely Metric Pathologies

Ranked by likely governance impact:

1. **Policy-blind fitness and permissive generalization.** Model S is rewarded for optionalizing mandatory checks. The same broad language can inflate holdout fitness and token-based generalization while admitting B3 and B4. This is the largest decision risk.
2. **Positive-log-only precision.** Neither precision score tests curated forbidden behavior. C may look precise simply because it memorizes observed variants; S’s low precision does not identify which extra behaviors are harmful.
3. **Missing-event bias.** Missing Supplier events, and potentially missing mandatory checks, blur the distinction between process behavior and observation failure. Encoding missingness as policy optionality makes data defects appear compliant.
4. **Split sensitivity and possible leakage.** There is no evidence of actual leakage, but it cannot be excluded. The absent seeds, case manifests, preprocessing, and tuning history make the 80/20 claim non-reproducible. F4 indicates strong combination imbalance in the holdout.
5. **Alignment-cost sensitivity.** A low cost for log moves can make missing modeled activities look harmless; a low model-move cost can make skipped observed activities cheap. Different treatment of visible, silent, and duplicate-labeled transitions can materially change fitness and diagnostics.
6. **Unseen-combination pathology.** Random case splits may leave entire cross-products—such as Supplier × Auto × alternate order—out of training. C treats these as unrelated global variants rather than compositions of known choices.
7. **Duplicated-label effects.** C’s duplicate labels create multiple possible synchronous/model moves and alignment ties. They can increase runtime, obscure which branch caused a deviation, and distort token visitation used by some generalization measures.
8. **Silent-transition effects.** Model S’s `tau` choices make mandatory skips free in the model language. Silent routing also increases alignment ambiguity and can alter converted-net simplicity. Silent transitions are legitimate for optional Supplier/Expedite behavior, but not as an undocumented substitute for missing-event handling.
9. **Runtime confounded by model size and setup.** C is expected to be slower because of branch count and duplicate transitions, but the reported median also depends on trace length, hardware, caches, heuristic settings, timeouts, and multiprocessing. Tail latency is unreported.
10. **Stakeholder-score methodology.** The informal score likely captures a real readability difference, but it is not a validated comprehension measure. Participants may prefer a simple model even when they misunderstand its permissions.

A separate but important issue is **metric implementation comparability**. “Same PM4Py installation” does not imply the same conversion, parameterization, preprocessing, or log partition.

# 7. Third Alternative

I recommend a **balanced POWL backbone with explicit data-policy checks**. Its normative decision is the intersection of:

1. the procedural language of `model_third`; and
2. the attribute and uncertainty rules in `policy_constraints`.

It is not merely the raw Petri-net acceptance result.

**Compact formal description**

Let:

- `C` = initial Credit Check;
- `T` = initial Technical Review;
- `S?` = optional structural occurrence of Supplier Review;
- `E?` = optional Expedite Review;
- `A = Manager Approval XOR Auto Approval`;
- `K = Correct Dossier ; (Credit Check XOR Technical Review XOR (Credit Check || Technical Review))`;
- `K*` = zero or more correction/recheck cycles.

The partial-order backbone is:

```text
Register Dossier < C
Register Dossier < T
Register Dossier < S?
C < K*
T < K*
K* < E?
E? < A
S? < A
A < Release Order
```

`C` and `T` are unordered relative to each other. `S?` is unordered relative to checks, corrections, and Expedite Review, but must precede approval when present. Thus Expedite can occur before or after Supplier Review.

The `K* < E?` relation is a conservative interpretation that Expedite Review should use the latest corrected dossier and latest required rechecks. This detail should be ratified because P4 does not explicitly discuss corrections.

**Self-contained PM4Py construction**

```python
import pm4py

from pm4py.objects.powl.obj import (
    Transition,
    SilentTransition,
    OperatorPOWL,
    StrictPartialOrder,
)
from pm4py.objects.process_tree.obj import Operator


def xor(*children):
    return OperatorPOWL(
        operator=Operator.XOR,
        children=list(children),
    )


def partial_order(nodes, edges=()):
    po = StrictPartialOrder(nodes=list(nodes))
    for source, target in edges:
        po.order.add_edge(source, target)
    return po


# Fixed endpoints and initial mandatory checks
register = Transition(label="Register Dossier")
credit_initial = Transition(label="Credit Check")
technical_initial = Transition(label="Technical Review")
release = Transition(label="Release Order")

# Structurally optional, with policy conditioning handled below
supplier_optional = xor(
    Transition(label="Supplier Review"),
    SilentTransition(),
)

expedite_optional = xor(
    Transition(label="Expedite Review"),
    SilentTransition(),
)

approval = xor(
    Transition(label="Manager Approval"),
    Transition(label="Auto Approval"),
)

# One correction must be followed by Credit only, Technical only, or both.
credit_only = Transition(label="Credit Check")
technical_only = Transition(label="Technical Review")

credit_both = Transition(label="Credit Check")
technical_both = Transition(label="Technical Review")
both_rechecks = partial_order(
    nodes=[credit_both, technical_both],
    edges=[],  # Either recheck order is allowed.
)

recheck_set = xor(
    credit_only,
    technical_only,
    both_rechecks,
)

correct = Transition(label="Correct Dossier")
one_correction_cycle = partial_order(
    nodes=[correct, recheck_set],
    edges=[(correct, recheck_set)],
)

# LOOP(body, silent redo) gives one or more cycles; the outer XOR permits zero.
one_or_more_corrections = OperatorPOWL(
    operator=Operator.LOOP,
    children=[one_correction_cycle, SilentTransition()],
)
correction_phase = xor(
    SilentTransition(),
    one_or_more_corrections,
)

# Main POWL model
model_third = partial_order(
    nodes=[
        register,
        credit_initial,
        technical_initial,
        supplier_optional,
        correction_phase,
        expedite_optional,
        approval,
        release,
    ],
    edges=[
        (register, credit_initial),
        (register, technical_initial),
        (register, supplier_optional),

        (credit_initial, correction_phase),
        (technical_initial, correction_phase),

        # Conservative "latest checks before Expedite" interpretation.
        (correction_phase, expedite_optional),

        (expedite_optional, approval),
        (supplier_optional, approval),

        (approval, release),
    ],
)

# Applicable structural validation
net_third, im_third, fm_third = pm4py.convert_to_petri_net(model_third)
pm4py.check_soundness(
    net_third,
    im_third,
    fm_third,
    print_diagnostics=True,
)
```

The correction block uses a small number of duplicate labels locally. This is materially different from copying whole end-to-end variants: the duplicates are confined to the three possible affected-check sets.

An external checker can preserve uncertainty rather than treating missing attributes as permission:

```python
def evaluate_policy(trace, case_attributes=None, activity_key="concept:name"):
    """
    Returns:
        {
          "status": "conformant" |
                    "conditionally_conformant" |
                    "nonconformant",
          "violations": [...],
          "uncertainties": [...]
        }

    case_attributes may contain:
      - source_type: "external" or "internal"
      - affected_checks_by_correction:
          e.g. [{"Technical Review"}, {"Credit Check"}]
    """
    case_attributes = case_attributes or {}

    def activity(event):
        return event if isinstance(event, str) else event[activity_key]

    names = [activity(event) for event in trace]
    violations = []
    uncertainties = []

    allowed = {
        "Register Dossier",
        "Credit Check",
        "Technical Review",
        "Supplier Review",
        "Expedite Review",
        "Correct Dossier",
        "Manager Approval",
        "Auto Approval",
        "Release Order",
    }

    if not names:
        violations.append("Empty trace")
        return {
            "status": "nonconformant",
            "violations": violations,
            "uncertainties": uncertainties,
        }

    unknown = [name for name in names if name not in allowed]
    if unknown:
        violations.append(f"Unexpected activities: {unknown}")

    if names[0] != "Register Dossier" or names.count("Register Dossier") != 1:
        violations.append("Register Dossier must occur exactly once and first")

    if names[-1] != "Release Order" or names.count("Release Order") != 1:
        violations.append("Release Order must occur exactly once and last")

    approval_positions = [
        i for i, name in enumerate(names)
        if name in {"Manager Approval", "Auto Approval"}
    ]
    if len(approval_positions) != 1:
        violations.append("Exactly one approval activity is required")
        approval_index = len(names)
    else:
        approval_index = approval_positions[0]
        if approval_index != len(names) - 2:
            violations.append("Approval must be immediately before Release Order")

    positions = {
        name: [i for i, observed in enumerate(names) if observed == name]
        for name in allowed
    }

    correction_positions = positions["Correct Dossier"]
    first_correction = (
        correction_positions[0] if correction_positions else approval_index
    )

    # Initial mandatory checks must precede any correction and approval.
    for check in ("Credit Check", "Technical Review"):
        if not positions[check]:
            violations.append(f"Missing mandatory {check}")
        elif positions[check][0] >= first_correction:
            violations.append(
                f"Initial {check} must precede the first correction"
            )
        elif positions[check][0] >= approval_index:
            violations.append(f"{check} must precede approval")

    # Each correction defines one segment ending at the next correction/approval.
    observed_recheck_sets = []
    assigned_recheck_positions = set()

    for ordinal, correction_index in enumerate(correction_positions):
        end = (
            correction_positions[ordinal + 1]
            if ordinal + 1 < len(correction_positions)
            else approval_index
        )
        segment = [
            (i, names[i])
            for i in range(correction_index + 1, end)
            if names[i] in {"Credit Check", "Technical Review"}
        ]
        selected = [name for _, name in segment]
        selected_set = set(selected)
        observed_recheck_sets.append(selected_set)
        assigned_recheck_positions.update(i for i, _ in segment)

        if selected_set not in (
            {"Credit Check"},
            {"Technical Review"},
            {"Credit Check", "Technical Review"},
        ):
            violations.append(
                f"Correction {ordinal + 1} has no valid recheck set"
            )

        if selected.count("Credit Check") > 1:
            violations.append(
                f"Correction {ordinal + 1} repeats Credit Check more than once"
            )
        if selected.count("Technical Review") > 1:
            violations.append(
                f"Correction {ordinal + 1} repeats Technical Review more than once"
            )

    # Every check beyond the initial occurrence must belong to a correction segment.
    for check in ("Credit Check", "Technical Review"):
        for repeated_position in positions[check][1:]:
            if repeated_position not in assigned_recheck_positions:
                violations.append(
                    f"Repeated {check} without a preceding applicable correction"
                )

    # Compare observed rechecks to the affected-check decision when available.
    affected = case_attributes.get("affected_checks_by_correction")
    if correction_positions:
        if affected is None:
            uncertainties.append(
                "Affected-check attribute unavailable for correction validation"
            )
        elif len(affected) != len(correction_positions):
            violations.append(
                "Number of affected-check declarations does not match corrections"
            )
        else:
            for ordinal, (expected, observed) in enumerate(
                zip(affected, observed_recheck_sets), start=1
            ):
                if set(expected) != observed:
                    violations.append(
                        f"Correction {ordinal}: observed rechecks {observed} "
                        f"do not equal affected checks {set(expected)}"
                    )

    # Supplier condition is data-dependent.
    supplier_count = len(positions["Supplier Review"])
    if supplier_count > 1:
        violations.append("Supplier Review may occur at most once")

    source_type = case_attributes.get("source_type")
    if source_type == "external":
        if supplier_count != 1:
            violations.append(
                "External order requires exactly one Supplier Review"
            )
    elif source_type == "internal":
        if supplier_count != 0:
            violations.append(
                "Internal order must not contain Supplier Review"
            )
    else:
        uncertainties.append(
            "Source type unavailable; P3 cannot be conclusively evaluated"
        )

    # All reviews/corrections precede approval.
    for name in {
        "Credit Check",
        "Technical Review",
        "Supplier Review",
        "Expedite Review",
        "Correct Dossier",
    }:
        if any(i >= approval_index for i in positions[name]):
            violations.append(f"{name} occurs at or after approval")

    # Expedite is optional, unique, and follows the latest required rechecks.
    expedite_positions = positions["Expedite Review"]
    if len(expedite_positions) > 1:
        violations.append("Expedite Review may occur at most once")
    elif expedite_positions:
        latest_check = max(
            positions["Credit Check"] + positions["Technical Review"]
        )
        if expedite_positions[0] <= latest_check:
            violations.append(
                "Expedite Review must follow the latest required checks"
            )

    status = (
        "nonconformant"
        if violations
        else "conditionally_conformant"
        if uncertainties
        else "conformant"
    )
    return {
        "status": status,
        "violations": violations,
        "uncertainties": uncertainties,
    }
```

**Explicit semantics and limitations**

- Credit Check and Technical Review are mandatory and unordered.
- Supplier Review is structurally optional only because source data are absent. Its normative requirement remains conditional; unknown sourcing yields uncertainty, not compliance.
- Expedite Review is optional, after the latest required checks, before approval, and unordered with Supplier Review.
- Approval is exactly one of Manager Approval and Auto Approval.
- Every correction is followed by Credit-only, Technical-only, or both rechecks; corrections can repeat.
- The observed recheck set cannot be verified as the correct affected set without the missing attribute.
- P3 cannot be fully automated until source type is captured or joined from an authoritative order system.
- Missing events remain observation-quality problems. They should be represented through alignment diagnostics or probabilistic observation models, not by weakening the policy language.

```python
import numpy as np
import pandas as pd
from sklearn.model_selection import StratifiedShuffleSplit

CASE = "case:concept:name"
ACTIVITY = "concept:name"
TIME = "time:timestamp"


def case_features(df):
    def summarize(group):
        acts = group.sort_values(
            [TIME, "event_index"], kind="mergesort"
        )[ACTIVITY].tolist()

        credit = acts.index("Credit Check") if "Credit Check" in acts else 10**9
        technical = (
            acts.index("Technical Review")
            if "Technical Review" in acts else 10**9
        )

        return pd.Series({
            "approval": (
                "auto" if "Auto Approval" in acts
                else "manager" if "Manager Approval" in acts
                else "none"
            ),
            "supplier": "Supplier Review" in acts,
            "expedite": "Expedite Review" in acts,
            "correction": "Correct Dossier" in acts,
            "check_order": "C_first" if credit < technical else "T_first",
        })

    features = df.groupby(CASE, sort=True).apply(summarize)
    features["stratum"] = features.astype(str).agg("|".join, axis=1)
    return features


def reproducible_split(df, seed):
    features = case_features(df)

    # Rare strata must be merged using a published deterministic rule.
    counts = features["stratum"].value_counts()
    features.loc[
        features["stratum"].isin(counts[counts < 2].index),
        "stratum",
    ] = "__rare__"

    splitter = StratifiedShuffleSplit(
        n_splits=1,
        test_size=0.20,
        random_state=seed,
    )
    indices = np.arange(len(features))
    train_i, test_i = next(
        splitter.split(indices, features["stratum"])
    )

    train_cases = set(features.index[train_i])
    test_cases = set(features.index[test_i])

    train_df = df[df[CASE].isin(train_cases)].copy()
    test_df = df[df[CASE].isin(test_cases)].copy()
    return train_df, test_df, sorted(train_cases), sorted(test_cases)
```

**10. Rejection rule**

A compliance candidate is rejected despite favorable aggregate metrics if any of the following occurs:

- it accepts a ratified hard-negative trace violating P1, P2, P4, P5, or P7;
- it labels a case fully compliant when P3 or P6 cannot be evaluated because required data are absent;
- it rejects an explicitly ratified positive probe because of accidental branch coupling;
- it is unsound or has reachable post-release behavior;
- results cannot be reproduced from the published split and configuration;
- alignment conclusions change materially under reasonable, pre-registered cost settings without an adjudication rule.

Performance and false-rejection thresholds should be approved before examining the final test set.

# 10. Governance Recommendation

- **Model S:** May be retained as an exploratory replay baseline with a prominent warning that its language is not policy. It must not drive automated compliance, audit attestations, or simulation of authorized behavior. Retire it as a candidate normative model.
- **Model C:** Do not deploy as the general compliance model. Retire it from production consideration because it rejects explicitly valid and plausible compositional behavior and is difficult to maintain. Its eight branches may remain as regression fixtures or a temporary manual-review whitelist, not as a complete policy definition.
- **Third alternative:** Advance as the candidate governance model, but not yet as fully automated compliance enforcement.

Before deployment, the third alternative must:

1. pass the curated positive, negative, and conditional suites;
2. pass soundness and reachability checks after conversion;
3. have the conservative correction/Expedite ordering ratified;
4. capture or authoritatively join the external/internal source attribute;
5. capture the affected-check decision for every correction, or route corrected cases to manual review;
6. publish reproducible preprocessing, splits, cost settings, and version information;
7. meet approved runtime and false-rejection service levels;
8. expose structural conformance, data-policy conformance, and uncertainty as separate results;
9. pass the documented stakeholder comprehension test.

Until the missing attributes are resolved, the third model can support monitoring and triage, but P3- or P6-dependent cases must not receive an unqualified “compliant” decision.

# 11. Dissenting View

**Rebuttal**

The recommendation may be too quick to retire Model C and too willing to elevate an unmeasured hybrid. Compliance systems often operate under a closed-world rule: only expressly approved paths are automated, while new combinations require change control. Under that governance model, C’s low holdout fitness is not necessarily a defect; it may correctly identify behavior that operations has adopted without formal authorization. Its high training precision is valuable because false acceptance of a control violation can be more costly than manually reviewing a legitimate exception. By contrast, the third alternative creates compositional permissions that were not all demonstrated in the log, imposes a new “corrections before Expedite” interpretation, and relies on external code and attributes that do not currently exist. Its local duplicate labels and loop may also create alignment ambiguity that has not been benchmarked. Model S remains the proven low-cost exploratory option, while C provides an immediately understandable whitelist at the trace level even if its diagram is cumbersome. A safer sequence could therefore retain S for analysis and C for conservative enforcement, add missing branches only after approval, and postpone the third alternative until its soundness, runtime, negative-suite performance, and data integrations are established. Replacing a tested whitelist with an elegant but unvalidated abstraction could increase rather than reduce governance risk.

**Evidence that would change my decision**

I would reconsider Model C if the policy board explicitly adopted a closed-world variant whitelist, resolved B2’s contradiction, demonstrated that the rejected holdout cases were unauthorized, and showed acceptable maintenance and runtime under reproducible tests. I would reconsider Model S for broader use only if the task were formally limited to observation-noise exploration and no output could be interpreted as compliance. I would withdraw or revise the third alternative if curated testing exposed unsafe loop behavior, stakeholders rejected its correction semantics, required attributes could not be obtained, or its hybrid decisions were not reproducible across reasonable alignment-cost profiles.
