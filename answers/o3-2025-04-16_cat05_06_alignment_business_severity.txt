## 1. Materiality Framework  

Severity scale (1 low  5 critical) combines the following dimensions; the highest applicable level drives the rating.

1. Control objective breached – financial-statement accuracy, fraud prevention, customer notification, regulatory SLA.  
2. Amount / exposure – absolute € value and whether reversibility is feasible.  
3. Timing – whether an upstream control could still catch the error before payment or reporting.  
4. Customer / regulatory harm – monetary loss, complaint, legal duty-to-report.  
5. Recurrence – isolated vs. systematic.  
6. Evidence reliability – logging gap vs. proven misconduct.  
7. Model scope – deviation caused by model myopia is rated lower unless it hides a real risk.

Confidence (High / Medium / Low) expresses how sure we are that the observed alignment really maps to the underlying business fact. Missing evidence, label-mapping issues, or mutable links lower confidence but do not in themselves raise severity.

## 3. Repeated Deviation Patterns  

1. Duplicate-notification retries  
   • 74 cases, e.g., CL-603  
   • Low business risk; noise clutters dashboards  
   • Cause: connector retry logic logs success twice  
   • Confidence: High  
   • Owner: Integration team  

2. External-adjuster “missing Assess Loss”  
   • 9 high-value cases incl. CL-606  
   • Risk: documentary/audit gap, medium severity  
   • Cause: interface lacks event hand-off or ID correlation  
   • Confidence: Medium (2 cases have weak IDs)  
   • Owner: Claims Operations & IT integration  

3. Label mapping ‘Assess Damage’ vs. ‘Assess Loss’  
   • Appears in CL-611 and likely more after mapping change  
   • Risk: reporting misclassification, low severity  
   • Cause: vocabulary drift; mapping table updated late  
   • Owner: Data governance  

4. Auto Approve despite disqualifying data (P1/P2)  
   • 4 cases inc. CL-610  
   • Risk: control failure; amounts small-to-moderate so far  
   • Cause: data rule not enforced in workflow engine  
   • Owner: Risk & Workflow configuration  

5. Premature Pay Claim before approval  
   • At least CL-604; search needed for others  
   • Risk: severe (funds left org without approval)  
   • Cause: UI allowed direct payment; missing hard check  
   • Owner: Finance / Application security  

6. Out-of-scope Deny / Withdraw paths  
   • Majority of raw-cost 4 cases (CL-607, CL-612)  
   • Risk: low, but hides real conformance picture  
   • Cause: model scoped only for payable claims  
   • Owner: Process modelling CoE

## 4. Causal Hypotheses and Evidence Tests  

1. CL-602 missing Fraud Screen  
   H1: Fraud Screen skipped.  
   H2: Performed but not logged.  
   Test: search fraud-tool API calls; interview analyst; look for case ID in fraud DB.

2. CL-604 premature payment  
   H1: User bypassed workflow via legacy payment screen.  
   H2: Message queue timing caused out-of-order logs.  
   Test: compare bank SWIFT timestamp with system DB commit; check for async logging lag.

3. Auto Approve with recent bank change (pattern 4)  
   H1: Rule exists but reads wrong source field.  
   H2: Rule missing; policy relies on manual control.  
   Test: inspect BPMN decision table; simulate “bank change within 7 days”.

4. External-adjuster gap (pattern 2)  
   H1: Interface never implemented.  
   H2: Implemented but case-ID mapping lost when adjuster created new reference.  
   Test: reconcile adjuster PDF metadata with case table; check middleware logs.

5. Duplicate Notify (pattern 1)  
   H1: Connector retries after 200-OK not recognised.  
   H2: Business configured dual channels (portal + e-mail).  
   Test: correlate to connector error codes; sample content difference.

6. Label drift Assess Damage / Assess Loss  
   H1: UI wording changed; backend key unchanged.  
   H2: Two distinct subprocesses that should be modelled separately.  
   Test: look at user role, duration, and documents for both labels.

## 6. Why Alignment Cost Is Not Business Risk  

1. CL-602: raw cost 1 but €480 k high-risk fraud-screen failure – critical.  
2. CL-604: raw cost 3 yet funds paid before approval – maximum severity.  
3. CL-610: raw cost 0 while data condition violates P1 – hidden risk because model lacks data guards.  
4. CL-601: raw cost 3 from UI noise; zero policy impact.  
5. CL-606: raw cost 1 but audit evidence missing; medium severity.  

Reasons:  
• Cost function is uniform; it ignores amount, risk flags, and policy overlay.  
• Hidden  moves allow model to “repair” some serious gaps cheap (CL-604 second Pay Claim).  
• Duplicate telemetry inflates cost without risk (CL-601).  
• Data-aware conditions are outside control-flow fitness (CL-610).  
• Evidence stored in external systems may satisfy policy yet incur M() moves (CL-608).  

Therefore alignment cost is at best a first-pass anomaly indicator.

## 7. PM4Py Reproduction and Aggregation Code
```python
import pm4py
from pm4py.objects.process_tree import process_tree as pt
from pm4py.algo.conformance.alignments.petri import algorithm as align_algo
from pm4py.util import xes_constants as xes
import pandas as pd

# 1. parse process tree
tree_str = "-> ( 'Register Claim', 'Validate Coverage', 'Assess Loss', X ( -> ( 'Fraud Screen', 'Manual Approve' ), 'Auto Approve' ), 'Pay Claim', 'Notify Claimant' )"
tree = pm4py.parse_process_tree(tree_str)

# 2. convert to accepting Petri net
net, im, fm = pm4py.convert_to_petri_net(tree)

# 3. minimal illustrative event log (3 cases to keep snippet short)
log_txt = """
<log xes.version="2.0">
  <trace>
    <string key="concept:name" value="CL-601"/>
    <event><string key="concept:name" value="Register Claim"/></event>
    <event><string key="concept:name" value="Validate Coverage"/></event>
    <event><string key="concept:name" value="Assess Loss"/></event>
    <event><string key="concept:name" value="Auto Approve"/></event>
    <event><string key="concept:name" value="Pay Claim"/></event>
    <event><string key="concept:name" value="Notify Claimant"/></event>
  </trace>
  <trace>
    <string key="concept:name" value="CL-604"/>
    <event><string key="concept:name" value="Register Claim"/></event>
    <event><string key="concept:name" value="Validate Coverage"/></event>
    <event><string key="concept:name" value="Assess Loss"/></event>
    <event><string key="concept:name" value="Pay Claim"/></event>
    <event><string key="concept:name" value="Fraud Screen"/></event>
    <event><string key="concept:name" value="Manual Approve"/></event>
    <event><string key="concept:name" value="Notify Claimant"/></event>
  </trace>
</log>
"""
log = pm4py.read_xes_string(log_txt)

# 4. run standard alignment (warning: may differ from authoritative list)
res = align_algo.apply_log(log, net, im, fm)

# 5. build supplied move summary into DataFrame
supplied = [
    ("CL-601","L(Open Workbench)",1,1200,"LOW"),
    ("CL-602","M(Fraud Screen)",1,480000,"HIGH"),
    ("CL-603","L(Notify Claimant)",1,3200,"LOW"),
    ("CL-604","L(Pay Claim)",1,90000,"MEDIUM"),
    ("CL-610","Tau+All synchronous",0,4500,"LOW"),
]
sup_df = pd.DataFrame(supplied, columns=["case","move","raw_cost","amount","risk"])

# 6. aggregate example
agg = sup_df.groupby("move").agg(
    cases = ("case","count"),
    total_eur = ("amount","sum"),
    avg_raw_cost=("raw_cost","mean")
).reset_index()

print("Example alignment results:", res)
print("\nAggregated supplied move patterns:\n", agg)

# 7. Note: Narrative risk prioritisation remains manual per sections 2-6.
```
