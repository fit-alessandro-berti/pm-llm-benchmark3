## 1. Target definition

**Why the request cannot be taken literally.** "90-day default for every application" is observed for only part of the population. Of 48,000 applications, 25,200 (52.5%) were ever activated and 21,600 (45.0%) have a matured label. For rejected, withdrawn and unlinked transferred applications the outcome is not a hidden zero: no credit was extended, so `default_90d` is undefined under the observed policy. Coding all omitted cases as non-default would report a 5.6% rate (2,700 / 48,000) instead of 12.5% among matured accounts (2,700 / 21,600), and would teach a model that "looks like a reject" means "safe".

**Primary formulation (A): 90-day default among applications that are activated under the prevailing policy, predicted from an early prefix.**

| Element | Definition |
|---|---|
| Unit of analysis | One credit application (one case after de-duplication and transfer linkage). One row per case and prediction point; results are reported per prediction point. |
| Prediction time `t0` | Timestamp of the third canonical event (in the nominal flow: Application Started -> Identity/KYC Check -> first Credit Review), provided no decision event has occurred. Secondary points: k = 2, 4, 5 events and start + 1, 3, 7 days. |
| Outcome | `D90 = 1` if a default is recorded within 90 days after `Account Activated`. The clock starts at activation, not at `t0`. |
| Horizon | 90 days after activation, with activation required within `A_max` days of application start. `A_max` is fixed in advance from the start-to-activation distribution of old cohorts (45 days is used below as a placeholder). Observation of the label needs up to 35 further days. |
| Population | Applications started from 1 January 2024, still undecided at `t0`, and activated on this platform within `A_max`, under the credit policy in force (before versus from 1 July 2025). |
| Estimand | `pi(x, r)` = P(D90 = 1 given X(t0) = x, activated within `A_max`, policy regime r), plus its calibration and discrimination among activated accounts of the evaluation period. |
| Score semantics | "If this application is booked under the current policy, this is its probability of default within 90 days of activation." |

Why this is defensible:

- **Statistically:** it is identified from data in which the outcome actually exists. It needs assumptions only about label maturity and missing feeds among activated accounts, not about applicants who were never exposed.
- **Operationally:** every application can be scored at `t0`, and the score supports actions on applications that proceed to booking: routing to senior review, targeted document requests, onboarding checks, collections capacity planning.
- **Honest boundary:** the estimand conditions on a future event (activation) and on the selection policy. It is therefore a policy-specific predictive quantity, not applicant creditworthiness, and it changes when the policy changes (as on 1 July 2025).

Each prediction is delivered as a triple: the conditional default probability with an interval, the estimated activation probability, and a support flag. Applications whose prefix resembles almost exclusively rejected cases get "outside support" instead of a number.

**Alternative targets and the different questions they answer.**

- **B. Multi-state target for all applications.** State at start + W days in {activated, rejected, withdrawn, transferred, still open}, optionally with the joint cumulative incidence "activated and defaulted within 90 days". It is defined for every application under the observed policy and answers "what will happen to this application and how many booked defaults will the pipeline produce", which is a volume and capacity question. A rejected application contributes no booked default because the event did not occur, not because the applicant is a good risk. I use B as a companion model, never as a substitute label.
- **C. Time to default after activation with right censoring.** Estimates `S(t | x)` for any `t`, uses the not-yet-mature accounts, and answers "when", not only "whether". It is the main secondary analysis because it is the only way to learn from recent post-policy accounts.
- **D. Policy-specific counterfactual target.** "Default within 90 days if this application were activated on specified terms." This is what the informal request means for rejected cases. It requires consistency, no unmeasured confounding of the accept decision given the prefix, and positivity. Reviewers see information that is not in the log, some prefix regions are always rejected, and for withdrawn applicants "if activated" is not even a realistic intervention. It is reported only as a labeled exploratory analysis.

## 2. Cohort construction

**Two cutoffs.** `C_event` = 31 December 2025 (last observed event) and `C_label` = 15 February 2026 (labels known). Both are parameters, so the same code can replay any earlier as-of date.

**Inclusion rules**

1. First canonical event is `Application Started`, with timestamp between 1 January 2024 and `C_event`.
2. The case is at risk at the prediction point: it has reached `t0` by `C_event` and no Accepted, Rejected, Withdrawn, Transferred or later event has a timestamp at or before `t0`.
3. For the primary outcome analysis: activated within `A_max` of start, and design-mature, meaning `activation + 90 days + 35 days <= C_label`. With the current cutoff this is activation on or before 13 October 2025.
4. To avoid selecting fast activators among recent starters: start date at or before `C_label - 125 days - A_max` (29 August 2025 with the 45-day placeholder).

**Exclusion rules**

- Test or dummy cases, cases with impossible ordering (activation before start), and left-truncated cases whose first event is not `Application Started`. The last group often indicates a transfer re-entry and goes to the linkage step.
- Exact and near-duplicate events are removed before any counting. Cases are never removed because of duplicates.
- No exclusion based on outcome availability other than the date rule in inclusion rule 3.

**As-of rules**

- Maturity is decided by date arithmetic only, never by "label is not null". A default is knowable as soon as it happens, while a non-default is knowable only after day 90 plus the feed lag. Accounts activated between 14 October and 10 November 2025 can already carry a label, and such early labels are likely to be enriched in defaults.
- A label may enter a training set for backtest origin `O` only if `label_available_at < O`.
- Every feature value must come from an event with timestamp at or before `t0`. Reference statistics use only events and labels known before `t0`.
- Terminal state is evaluated at `C_event`. "Open" means no terminal event by then, which is censoring, not an outcome.
- `data_extract_time` must be constant; several values would mean mixed snapshots.

**Cohort flow (all 48,000 applications)**

| Stratum | N | % | Status | Use in primary analysis (A) | Use in companion analyses |
|---|---:|---:|---|---|---|
| Activated, matured, non-default | 18,900 | 39.4 | Labeled | Outcome = 0 after re-checking the date rule | B: activated; C: event-free at 90 days |
| Activated, matured, default | 2,700 | 5.6 | Labeled | Outcome = 1 | B: activated; C: event at observed time |
| Activated, 90-day outcome or feed not matured | 3,600 | 7.5 | Not yet mature: right-censored or delayed label, possibly including permanently missing feeds | Excluded from the binary outcome; scored; never coded 0 | C: right-censored at `C_event`; overdue ones handled by weighting and bounds |
| Rejected | 9,100 | 19.0 | Competing outcome for activation; default selectively unobserved and undefined under the observed policy | Scored at `t0`; no outcome label | B: state "rejected"; D: counterfactual only |
| Withdrawn | 5,700 | 11.9 | Competing outcome; default undefined (applicant-driven non-exposure) | Scored at `t0`; no outcome label | B: state "withdrawn" |
| Transferred | 2,900 | 6.0 | Competing event on this platform plus missing follow-up; about 1,740 linkable (60%) and about 1,160 not | Scored at `t0`; no outcome label | B: state "transferred"; linked cases used in sensitivity only |
| Still open at extraction | 5,100 | 10.6 | Right-censored for the terminal state | Scored if at risk at `t0`; no outcome label | B: censored; split into recent in-progress and stale |

Derived analysis sets, counted by the pipeline and not assumed:

| Set | Rule | Expected relation to the snapshot |
|---|---|---|
| S0 | All started applications | Must equal 48,000 after de-duplication |
| S1 | At risk at `t0` | Subset of S0; attrition reported by eventual state |
| S2 | Primary cohort (inclusion rules 1–4) | Subset of the 25,200 activated |
| S3 | S2 with label present | Should be close to, and not larger than, the 21,600 export; any gap is investigated |

Two plausibility notes. If activations were uniform over the 24 months (about 1,050 per month), activations after 13 October 2025 alone would explain roughly 2,700 of the 3,600 immature accounts, leaving several hundred overdue or feed-missing; this is a back-of-envelope figure that the pipeline must replace with a measured one. And 5,100 open cases equal about 2.5 months of arrivals, so many are probably stale rather than in progress; cases with no event for longer than a high percentile of historical inter-event gaps are flagged "stale-open" and kept as their own state, not relabeled as withdrawn.

## 3. Censoring and missing-label strategy

| Mechanism | Where it occurs | Nature | Primary handling | Testability |
|---|---|---|---|---|
| Ordinary right censoring | Activated accounts with less than 90 days of follow-up at the cutoff; open cases for the terminal state | Administrative; driven by calendar entry date | Excluded from the binary outcome by the date rule; kept as censored observations in the survival and multi-state analyses | Partially testable: compare covariate mix and early hazards across entry months. Fails if hazard drifts with calendar time, which the policy change makes likely, so analyses are stratified by regime. |
| Delayed labels | Horizon elapsed, feed arrives 7–35 days later | Reporting delay, possibly outcome-dependent | Maturity requires the full 35-day lag; training folds use `label_available_at` | Testable: empirical distribution of `label_available_at - (activation + 90 days)` by outcome, channel and period on old cohorts |
| Selection through activation | 22,800 non-activated applications | Outcome undefined under the observed policy, not missing | Handled by the estimand (conditioning on activation), with an activation model for support checks; no imputation | The existence and strength of selection are testable. Whether rejected applicants would default like accepted ones with the same prefix is fundamentally untestable here. |
| Transfer | 2,900 cases | Competing event for activation on this platform, plus missing follow-up elsewhere | Competing state in B; outside the population of A | Partially testable: linked versus unlinked transfers can be compared on prefix features; outcomes of the unlinked 40% are untestable |
| Permanently missing outcome feed | Design-mature activated accounts with no label, concentrated in partner-originated accounts | Missing outcome among exposed accounts; plausibly missing not at random | Inverse-probability-of-observation weights from a model of "label observed" on activation-time covariates (channel, source system, region, activation month, amount band), with truncated weights | Dependence on observed covariates is testable. Internal `Default Recorded` and `collection_status` events give a partial cross-check for accounts without a feed. Dependence on the unobserved outcome itself is untestable. |

**Primary analysis strategy.** Binary `D90` on the design-mature primary cohort, weighted for missing feeds, with all non-activated cases kept in the scored population but outside the outcome analysis. Uncertainty is reported at two levels: sampling uncertainty (bootstrap by case within calendar blocks) and identification uncertainty (the bounds below).

**Secondary analysis.** Discrete-time hazard or Cox model for time from activation to default, censored at `min(activation + 90 days, C_event)`. This uses the immature accounts and is the only outcome evidence for accounts activated after 13 October 2025.

**Sensitivity analyses**

1. **Worst-case bounds.** Setting all 3,600 immature or missing outcomes to 0 or to 1 gives 10.7% to 25.0% default among the 25,200 activated (2,700 / 25,200 to 6,300 / 25,200), against 12.5% complete-case. The same bounds are computed per subgroup, especially for partner channels.
2. **Tipping-point analysis for missing feeds.** Assume the odds of default among accounts with missing feed are delta times the odds among comparable observed accounts, for delta in {0.5, 1, 1.5, 2, 3}, and report the delta at which calibration or subgroup conclusions change.
3. **Maturity definition.** Repeat with feed lags of 7 and 21 days and with the naive "label not null" rule, to quantify the bias of early-arriving positive labels.
4. **Transfers.** Four variants: competing event (primary); linked 60% followed to the partner outcome; linked cases weighted by inverse linkage probability; transfers excluded.
5. **Activation window.** `A_max` of 30, 45 and 60 days.
6. **Selection.** Reweight activated accounts by inverse activation propensity to the all-applicant population, and analyse the band of applications whose accept decision flipped at the 1 July 2025 threshold change. Both are labeled counterfactual and exploratory.
7. **Stale-open cases** treated alternatively as censored and as withdrawn-like.

**Assumption status**

- Testable: label-delay distribution; consistency of labels within a case; reproduction of the 21,600 export; dependence of feed missingness and of activation on observed covariates.
- Partially testable: independence of administrative censoring; representativeness of linked transfers; missing-at-random feeds given covariates (through the internal event cross-check).
- Fundamentally untestable: default risk of rejected and withdrawn applicants had they been activated; outcomes of unlinked transfers; missingness that depends on the unreported outcome.

## 4. Prefix extraction

**Preparation before any prefix is cut**

- Normalise timestamps to UTC, then sort by case, timestamp and a stable tie-breaker (original row index).
- Map activity names to a canonical vocabulary using a versioned dictionary covering pre- and post-migration names. Unknown names stop the pipeline; they are not silently passed on as new activities.
- Remove duplicates: same case, canonical activity, timestamp and resource, plus a tolerance rule for near-duplicates. This must happen before counting events, otherwise a duplicate shifts the k-th event after 15 October 2025 and the same k means different things before and after migration. Removed counts are logged by month.

**Fixed event-count prefixes**

- For k in {2, 3, 4, 5}: the prefix is the first k events and the prediction time is the timestamp of event k.
- `pm4py.get_prefixes_from_log` truncates long cases but returns cases with fewer than k events unchanged, and it relies on row order. The pipeline therefore sorts first and afterwards keeps only cases with exactly k events in the prefix.
- A prefix containing a decision or later activity is dropped for that k: the case is no longer undecided, so an "early warning" there would mostly read off the decision.

**Elapsed-time prefixes**

- For delta in {1, 3, 7} days: prediction time is start + delta and the prefix is every event with timestamp at or before it.
- A case is in the risk set only if start + delta is at or before `C_event` and the case is still undecided at that time.
- These prefixes carry information that count-based prefixes cannot: idle time since the last event and "nothing has happened yet". Attribute values are taken as the last value recorded at or before the prediction time.

**Short cases.** Cases that end or are decided before a prediction point are not padded and not predicted at that point. An attrition table per prediction point shows how many cases leave the risk set and into which final state. Because the population changes with k, results are also compared on the common set of cases at risk at the longest prefix.

**Repeated document loops.** Loops are not collapsed; each Request Documents -> Credit Review cycle stays in the prefix and is counted as rework. Since a fixed k then corresponds to different process stages, a milestone variant ("at first Credit Review", "at return from first document request") is run as a robustness check. When several prefixes per case are pooled in one model, all prefixes of a case stay in the same split and rows are weighted by one over the number of prefixes.

**Activity renaming.** The canonical mapping is validated by comparing directly-follows graphs and prefix variants of early prefixes before and after 15 October 2025; edges or variants that appear only afterwards indicate an unmapped rename or residual duplicates.

## 5. Process-aware features

**Static case attributes (known at application start)**

- `case:channel`, `case:region`, `case:requested_amount`, taken as the first recorded value; the pipeline checks that they are constant within a case, because repeated case columns can be overwritten with later values.
- Start weekday, hour and month.

**Prefix-derived features (events at or before `t0` only)**

- Control flow: last activity, activity counts, directly-follows pair counts, canonical prefix variant, whether KYC was repeated, whether the prefix deviates from the nominal order.
- Timing: elapsed time since start, KYC duration, waiting time before first Credit Review, inter-event gaps, idle time at prediction time, out-of-hours indicators.
- Rework: number of document requests so far, time spent in loops, time since the last request.
- Resource and queue: resources seen so far, number of handovers, recent load of the handling resource computed from events before `t0`.
- Risk score: first value, latest value as of `t0`, change, number of updates.

**Features that require historical reference data (all computed as-of)**

- Queue state at `t0`: number of cases waiting in Credit Review, arrivals in the trailing 24 hours and 7 days.
- Resource experience recomputed from the log: events handled before `t0`. It is left-truncated at 1 January 2024, so it measures recent experience, not tenure.
- Trailing acceptance and withdrawal rates by channel and resource, using only cases resolved before `t0`.
- Trailing default rates by channel or region, using only labels with `label_available_at` before `t0`; these therefore lag by at least four months.
- Variant frequency and typical step durations from the training window, to express a prefix as "unusual" or "slow".

**Cohort and calendar features**

- Policy-regime indicator, days since policy change, application month, migration indicator.
- The migration indicator and `source_system` are used as stratifiers and drift monitors, not as learned effects: no account whose prefix lies after the migration has a mature label yet, so their effect on default cannot be estimated.

Some of these features mainly predict activation (for example the reviewer or the queue) and only indirectly predict default. Feature attributions are therefore reported separately for the activation model and the default model.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final decision; presence encodes acceptance, value encodes the underwriter's risk view | Not available at any pre-decision prediction point | Drop | Post-decision by definition; could only be used in a separate model anchored at activation |
| `decision_reason` | Populated at or after Accept/Reject; encodes the decision and its motivation | Not available before the decision | Drop | Direct label proxy for activation and strongly related to default |
| `collection_status` | Updated after activation; can state the default directly | Not available before activation | Drop from features; use only to cross-check outcomes | Target leakage |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | Reveal selection and outcome | Only events with timestamp at or before `t0` | Drop from prefixes; keep in the outcome and state tables | They define the target and the competing states |
| Whole-case aggregates (case length, total duration, final variant) | Computed over the full trace | Recompute on the prefix | Repair | Long traces indicate loops and decisions that happen later |
| `documents_total` | Nightly snapshot can include documents uploaded later the same day | Use the previous night's snapshot (strictly before the date of `t0`), or rebuild a count from document events up to `t0` | Repair, otherwise drop | Same-day look-ahead of up to 24 hours |
| Updated `risk_score` | Later updates may follow document loops or the decision; a case-level "latest" value is future information | Last non-null value on an event at or before `t0`; also the first value | Repair | The as-of value is legitimate and important |
| Resource experience | Stored as of extraction, so it contains up to two years of future experience and differs by cohort age | Recompute from events before `t0`, or join an HR table with validity dates | Repair, otherwise drop | Extraction-time value is correlated with calendar time and thus with label maturity |
| `default_90d` repeated on events | The label is written on early events of the case | Never a feature | Drop | Target itself |
| `label_available_at` (label availability) | Its presence and timing encode the outcome, because defaults become known earlier | Used only to build as-of training sets and to study delays | Drop from features; keep as design variable | Prevents training on labels that were not yet known |
| `data_extract_time` | Constant or snapshot identifier; with mixed snapshots it encodes cohort age | Not a feature | Drop; check that it is constant | No predictive meaning at decision time |
| `source_system` | Changes at migration and for partner or transferred cases; proxy for period and for feed missingness | Value on events at or before `t0` | Keep as stratifier only | Its relation to default cannot be learned before post-migration labels mature |
| Activity names and duplicates after migration | Renames create artificial new variants; duplicates shift event positions | Canonical mapping and de-duplication before prefixing | Repair | Otherwise the model learns the migration date |
| Repeated `case:` attributes | May hold final, overwritten values | First value at or before `t0` | Repair | For example an amended requested amount |
| Target encodings, scalers, variant frequencies | Fitted on all data they leak test outcomes and future periods | Fit on training cases with labels available before the fold origin | Repair | Standard as-of discipline |
| Transfer link or new identifier | Reveals that a transfer will happen; the same applicant may appear in two splits | Use only for grouping cases and for outcome follow-up | Drop from features; keep for grouping | Avoids applicant-level leakage across splits |
| Membership in the labeled export | Equals "activated and matured" | Never a filter or feature at scoring time | Drop | Selection indicator |

The code enforces this with a column whitelist, a list of forbidden columns, assertions on event times and activities inside prefixes, and a single-feature association check against the label.

## 7. Validation design

**What the calendar allows.** Mature labels exist only for activations up to 13 October 2025. Two consequences follow:

- Post-policy evidence is thin. With the 45-day placeholder for `A_max`, eligible post-policy starters are those from 1 July to 29 August 2025. Under uniform arrivals and unchanged rates this is roughly 3,900 applications, 2,100 activations and 260 defaults; the real numbers must come from the pipeline, and confidence intervals will be wide.
- No account whose prefix lies after the 15 October 2025 migration has a mature label. Outcome performance after migration cannot be validated from this extract and I will not claim it.

**Scheme**

1. **Rolling-origin backtest (deployment-realistic).** Origins at 1 January, 1 April and 1 July 2025. At each origin the model is trained only on cases whose labels were available before the origin, which means activations up to 29 August 2024, 27 November 2024 and 26 February 2025 respectively. It is tested on applications started in the following three months (for the last origin: 1 July to 29 August 2025). The gap of about 170 days between the last usable training start and the origin is not an artificial embargo; it is the real label delay.
2. **Final hold-out (retrospective).** Train on starts in 2024, tune and calibrate on starts from January to April 2025, test separately on May–June 2025 (pre-policy starts) and from July 2025 (post-policy starts). This uses labels that were not all available at the test dates and is reported as retrospective, not as achievable live performance.
3. **Policy change.** The model deployed on 1 July 2025 would have been trained entirely on pre-policy accounts; the first post-policy labels arrive between 6 October and 3 November 2025. Results are reported for the pre-policy model on post-policy cases, and for recalibration once post-policy labels exist. Cases started before but decided after 1 July are flagged as straddlers and shown separately. Regime by decision date is used only for stratification, since it is unknown at `t0`.
4. **System migration.** Label-free checks on prefixes after 15 October 2025: feature drift (population stability index, Kolmogorov–Smirnov), prefix-variant and directly-follows comparison, score distribution, and duplicate rates. The activation and competing-outcome model can be validated after migration because those states resolve within weeks. The default model gets only censored early-default evidence from the survival analysis.
5. **Prospective confirmation.** A re-extract on or after 5 May 2026 gives mature labels for all activations up to 31 December 2025, and the frozen model and analysis plan are then evaluated on post-migration accounts.

**Why a random case split is misleading here**

- It puts post-policy and post-migration cases into training and pre-policy cases into test, so it measures interpolation within a mixture instead of forecasting.
- It uses labels that would not have been available at prediction time.
- Concurrent cases share reviewers, queues and calendar effects, so train and test are dependent.
- Linked or re-entered applications of the same applicant can fall on both sides.
- It hides calibration drift, which is the main risk when thresholds change.

`pm4py.split_train_test` is run once as a baseline, only to show the size of this optimism.

**Metrics**

- Primary target, among activated accounts and weighted for missing feeds: Brier score and Brier skill score, log loss, calibration intercept and slope, reliability curves and calibration-in-the-large by activation month, area under the ROC curve, area under the precision–recall curve (base rate about 12.5%), recall and precision in the top decile, and net benefit at the thresholds the business would act on.
- Survival analysis: time-dependent AUC and censoring-weighted Brier score at 30, 60 and 90 days, and a concordance index that accounts for censoring.
- Competing-outcome model: multiclass log loss and calibration of each state's cumulative incidence.
- All metrics are given per prediction point, with bootstrap intervals by case, and repeated under the sensitivity scenarios of section 3, so that each headline number has both a sampling interval and an assumption range.

**Calibration.** Fit calibration on the most recent mature slice before each origin, check it on the next period, and report recalibration needs after the policy change. Scores are not presented as probabilities for subgroups where calibration cannot be checked.

**Subgroups.** Channel (partner versus direct), region, amount band, policy regime, source system, prefix type, and number of document loops. Each subgroup is reported with its number of defaults; groups with too few events get intervals only, without ranking claims. Partner-originated accounts are always shown with their missing-feed rate and bounds.

**Distribution shift.** Monthly monitoring of feature drift, a classifier that tries to tell training from test period, default rate by activation month, activation rate by score band before and after the policy change, and the share of scored applications flagged outside support.

## 8. Limitations and decision-use boundary

**What the study can claim**

- How well early process prefixes rank and calibrate 90-day default among accounts that were activated under the historical policies, with stated sampling intervals and assumption ranges.
- How selection into activation, withdrawal and transfer depends on early prefixes.
- How sensitive the results are to label maturity, missing feeds and transfer handling.

**What it cannot claim**

- The default risk of rejected, withdrawn or unlinked transferred applicants. Their outcomes do not exist in the data.
- That features cause default. A long document loop associated with default may reflect reviewer suspicion, not an effect of the loop.
- Performance after the system migration, or stable performance under the post-July policy beyond a short window.
- Validity for partner-originated accounts beyond the bounds, as long as their feeds are missing more often.

**Three levels that must not be mixed**

- Predictive association: the relation between prefix and default among activated accounts. This is what the study estimates.
- Selection effects: activated accounts are those that reviewers and thresholds let through. A feature can look protective only because risky applicants with that feature were rejected. Moving the threshold changes the relation, as on 1 July 2025.
- Counterfactual default risk: what would happen if a given application were activated. This needs the untestable assumptions of formulation D and is not delivered by the primary analysis.

**Decision-use boundary.** The score may prioritise review effort, trigger checks and inform monitoring of applications that are heading towards booking. It must not be used as an automatic reject or accept rule, as a risk estimate for populations the policy has never accepted, or as evidence that rejected applicants are low risk.

**How deployment could change the data-generating process**

1. If the score influences accept decisions, it changes who is activated, so future labels are selected by the model itself.
2. If high scores trigger extra document requests or senior review, rework counts, timing and resource features change meaning, and these are model inputs.
3. If high-score accounts get earlier collections contact or lower limits, defaults are prevented and the model appears to over-predict.
4. Longer handling of flagged applications can increase withdrawals and shift the activated population.
5. Applicants, brokers or partners can adapt channel and document behaviour once the triggers become known.
6. Routing flagged cases to partners changes the transfer mechanism and the share of outcomes with missing feeds.

Monitoring after deployment therefore needs a logged record of score, action taken and policy version, and ideally a small randomly chosen group handled without the score, so that later evaluation is not confounded by the model's own influence.

The rename dictionary, the 45-day activation window, the split dates and the column names `documents_total` and `resource_experience` are assumptions to be replaced.

raw[ACT] = raw[ACT].str.strip().replace(RENAME)             # canonical names BEFORE prefix positions are counted
raw = raw[raw[TS] <= EVENT_CUTOFF]
n_raw = len(raw)
raw = raw.drop_duplicates(subset=[CASE, ACT, TS, RES])      # exact duplicates; near-duplicates need a tolerance rule
print("duplicate events removed:", n_raw - len(raw))
log = pm4py.format_dataframe(raw, case_id=CASE, activity_key=ACT, timestamp_key=TS)
log = log.sort_values([CASE, TS, "@@index"], kind="stable").reset_index(drop=True)
# As-of replacement for extraction-time resource experience: events the resource handled BEFORE this event
# (left-truncated at the start of the log, so interpret as "recent experience / load", not tenure).
log["res_load_asof"] = log.sort_values([TS, "@@index"], kind="stable").groupby(RES).cumcount()

# ---- 2. Case table as of the cutoffs --------------------------------------------------------------------------
def first_ts(activities):
    return log.loc[log[ACT].isin(activities)].groupby(CASE)[TS].min()

g = log.groupby(CASE)
cases = pd.DataFrame({"start": g[TS].min(), "first_act": g[ACT].first(), "last_event": g[TS].max()})
cases["activated_at"], cases["default_at"] = first_ts(["Account Activated"]), first_ts(["Default Recorded"])
cases["rejected_at"], cases["withdrawn_at"] = first_ts(["Rejected"]), first_ts(["Withdrawn"])
cases["transferred_at"], cases["stop_at"] = first_ts(["Transferred"]), first_ts(STOP)
known = log[log["default_90d"].notna() & (log["label_available_at"] <= LABEL_ASOF)]   # label known as of LABEL_ASOF
assert known.groupby(CASE)["default_90d"].nunique().le(1).all(), "conflicting labels within a case"
cases = cases.join(known.groupby(CASE).agg(default_90d=("default_90d", "last"),
                                           label_available_at=("label_available_at", "min")))
cases["horizon_end"] = cases["activated_at"] + HORIZON
cases["mature"] = cases["horizon_end"] + FEED_LAG <= LABEL_ASOF     # date arithmetic only, never "label is not null"
act = cases["activated_at"].notna()
cases["state"] = np.select(                                         # first matching condition wins
    [act & ~cases["mature"],                    # administrative censoring or label still inside the feed-lag window
     act & cases["default_90d"].isna(),         # overdue: candidate permanently missing feed -> IPCW / bounds
     act & (cases["default_90d"] == 1), act,
     cases["rejected_at"].notna(), cases["withdrawn_at"].notna(), cases["transferred_at"].notna()],
    ["activated_not_mature", "activated_feed_missing", "activated_default", "activated_non_default"] + EXITS,
    default="open_at_cutoff")                   # exits/open are competing or censored states, never "non-default"
# Survival view (connect lifelines / scikit-survival later; PM4Py has no survival estimator).
fu_end = cases["horizon_end"].clip(upper=EVENT_CUTOFF)              # event-log follow-up ends at EVENT_CUTOFF
cases["event_90d"] = cases["default_at"] <= cases["horizon_end"]
cases["surv_days"] = (cases["default_at"].where(cases["event_90d"], fu_end) - cases["activated_at"]).dt.days
# Primary cohort: started early enough that activation AND label maturity were possible for every member.
start_ok = cases["start"] <= LABEL_ASOF - FEED_LAG - HORIZON - MAX_ACT_DELAY
cases["primary"] = (start_ok & cases["mature"] & (cases["first_act"] == "Application Started")
                    & (cases["activated_at"] - cases["start"] <= MAX_ACT_DELAY))
cases["y"] = cases["default_90d"].where(cases["primary"])           # NaN = undefined, censored or missing; never 0

# ---- 3. Temporal split by case start (pm4py.split_train_test is random: baseline comparison only) --------------
T0, T1, T2 = (pd.Timestamp(d, **UTC) for d in ("2024-01-01", "2025-01-01", "2025-05-01"))
s0 = cases["start"]
cases["split"] = np.select([s0 < T0, s0 < T1, s0 < T2, s0 < POLICY_CHANGE],
                           ["left_truncated", "train", "valid", "test_pre_policy"], default="test_post_policy")
late = (cases["split"] == "train") & cases["primary"] & ~(cases["label_available_at"] < T1)
cases.loc[late, "split"] = "purged_label_unknown_at_train_asof"     # label was not yet known when validation begins

# ---- 4. Prefixes: fixed event count and elapsed time ----------------------------------------------------------
def fixed_prefix(k):
    pref = pm4py.get_prefixes_from_log(log[PREFIX_COLS], length=k, case_id_key=CASE)   # post-prefix columns dropped
    pref = pref[pref.groupby(CASE)[ACT].transform("size") == k]     # shorter cases are returned whole: not at risk
    decided = pref.loc[pref[ACT].isin(STOP), CASE].unique()         # outcome of the decision already inside prefix
    return pref[~pref[CASE].isin(decided)]

def time_prefix(delta):
    ev = log[PREFIX_COLS].join(cases[["start", "stop_at"]], on=CASE)
    t_pred = ev["start"] + delta
    at_risk = (t_pred <= EVENT_CUTOFF) & ~(ev["stop_at"] <= t_pred)  # observable and still undecided at t_pred
    return ev[at_risk & (ev[TS] <= t_pred)].assign(t_pred=t_pred).drop(columns=["start", "stop_at"])

def features(pref):
    g = pref.groupby(CASE)
    t_pred = g["t_pred"].first() if "t_pred" in pref else g[TS].max()
    X = pd.DataFrame({
        "t_pred": t_pred,
        "elapsed_h": (t_pred - g[TS].min()).dt.total_seconds() / 3600,
        "idle_h": (t_pred - g[TS].max()).dt.total_seconds() / 3600,  # > 0 only for elapsed-time prefixes
        "n_events": g.size(),
        "n_doc_requests": pref[ACT].eq("Request Documents").groupby(pref[CASE]).sum(),   # rework loops so far
        "n_reviews": pref[ACT].eq("Credit Review").groupby(pref[CASE]).sum(),
        "n_resources": g[RES].nunique(),
        "last_res_load_asof": g["res_load_asof"].last(),
        "risk_first": g["risk_score"].first(), "risk_asof": g["risk_score"].last(),      # last non-null <= t_pred
        "channel": g["case:channel"].first(), "region": g["case:region"].first(),
        "requested_amount": g["case:requested_amount"].first(),      # ASSUMPTION: first value = value at application
    })
    X["post_policy"], X["post_migration"] = X["t_pred"] >= POLICY_CHANGE, X["t_pred"] >= MIGRATION  # stratifiers
    return X

# ---- 5. Leakage audit -----------------------------------------------------------------------------------------
def leakage_audit(X, pref):
    assert not set(FORBIDDEN) & (set(X.columns) | set(pref.columns)), "post-decision or label column leaked"
    assert not pref[ACT].isin(STOP).any(), "decision or post-activation event inside a prefix"
    assert (pref[TS] <= pref[CASE].map(X["t_pred"])).all(), "event later than prediction time"
    assert not (cases["stop_at"].reindex(X.index) <= X["t_pred"]).any(), "case already decided at prediction time"
    assert (X["t_pred"] <= EVENT_CUTOFF).all(), "prediction time after the observation window"
    num = X.select_dtypes("number").join(cases["y"]).dropna(subset=["y"])
    print("max |corr(feature, y)| - investigate anything close to 1:", num.corr()["y"].drop("y").abs().max())

pref3 = fixed_prefix(3)     # primary point: Application Started -> Identity/KYC Check -> first Credit Review
X3 = features(pref3)
leakage_audit(X3, pref3)
pref_3d = time_prefix(pd.Timedelta(days=3))
leakage_audit(features(pref_3d), pref_3d)
table = X3.join(cases[["state", "primary", "y", "split", "surv_days", "event_90d"]])
stage2 = table[table["primary"] & table["y"].notna()]   # P(default_90d | prefix, activated); refit per backtest origin
