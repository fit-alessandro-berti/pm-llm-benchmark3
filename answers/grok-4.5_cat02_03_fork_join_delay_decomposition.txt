# 1. Delay-decomposition definitions

All times are absolute timestamps on the same day. For case \(c\) and branch \(i \in \{A,B,C\}\):

| Quantity | Formula |
|---|---|
| Upstream elapsed | \(\mathrm{upstream}_c = \mathrm{fork\_release}_c - \mathrm{arrival}_c\) |
| Branch queue | \(q_{c,i} = \mathrm{start}_{c,i} - \mathrm{fork\_release}_c\) |
| Branch service | \(s_{c,i} = \mathrm{end}_{c,i} - \mathrm{start}_{c,i}\) |
| Join ready | \(\mathrm{join\_ready}_c = \max_i \mathrm{end}_{c,i}\) |
| Critical branch(es) | \(\arg\max_i \mathrm{end}_{c,i}\) (ties listed jointly) |
| Branch sync wait | \(w_{c,i}^{\mathrm{sync}} = \mathrm{join\_ready}_c - \mathrm{end}_{c,i}\) |
| Fork–join stage elapsed | \(T_c^{\mathrm{FJ}} = \mathrm{join\_ready}_c - \mathrm{fork\_release}_c = \max_i (q_{c,i}+s_{c,i})\) |
| Downstream queue | \(d_c = \mathrm{final\_start}_c - \mathrm{join\_ready}_c\) |
| Final service | \(s_c^F = \mathrm{final\_end}_c - \mathrm{final\_start}_c\) |
| Total flow time | \(TFT_c = \mathrm{final\_end}_c - \mathrm{arrival}_c\) |

**Identity (no double-counting of calendar time):**
\[
TFT_c = \mathrm{upstream}_c + T_c^{\mathrm{FJ}} + d_c + s_c^F.
\]
Also \(T_c^{\mathrm{FJ}} = q_{c,i^*} + s_{c,i^*}\) for any critical branch \(i^*\), and for every branch
\[
q_{c,i}+s_{c,i}+w_{c,i}^{\mathrm{sync}} = T_c^{\mathrm{FJ}}.
\]

**Why summing all branch synchronization waits double-counts elapsed time.**  
Each \(w_{c,i}^{\mathrm{sync}}\) is a *per-branch* idle interval after that branch finishes. These intervals overlap on the calendar: if A finishes at \(t_A\), B at \(t_B\), and C (critical) at \(t_C=\mathrm{join\_ready}\), then A waits the whole \([t_A,t_C]\) while B waits \([t_B,t_C]\). The *elapsed* synchronization span is only \(t_C - \min_i t_i\), a single interval. Summing \(\sum_i w_{c,i}^{\mathrm{sync}}\) therefore counts overlapping parallel waits multiple times and does **not** equal any segment of \(TFT_c\). Only the max-based stage time \(T_c^{\mathrm{FJ}}\) (or the critical branch’s \(q+s\)) enters the additive decomposition of flow time. Sync waits are useful for *resource* idle accounting, not for partitioning case flow time.

**Assumption A1.** Branches may start only at/after `fork_release`; observed \(q_{c,i}\ge 0\) is treated as branch-specific queueing (resource contention or release jitter), not measurement error.  
**Assumption A2.** `join_ready` is exactly \(\max_i \mathrm{end}_{c,i}\) (AND-join; no early release of F).  
**Assumption A3.** \(d_c = \mathrm{final\_start}-\mathrm{join\_ready}\) is interpreted as downstream queueing under the model; §7 notes it could also reflect policy.

# 4. Counterfactual redesign analysis

**Method (stated assumptions).**  
- **CF1:** Multiply every \(s_A\) by 0.8  new \(s_A'=40\); keep A_start fixed so A_end' = A_start + 40. Recompute join_ready', critical branch, \(T_{FJ}'\), and — under a **static downstream** assumption — keep the observed `final_start` if still \(\ge\) join_ready', else set final_start' = join_ready' (no negative queue). Final service unchanged.  
  *Assumption CF-D1 (static F schedule):* Observed final_start times are treated as exogenous resource calendar slots; only binding when join moves past the old start. This is a lower-bound on system-wide benefit and can **overstate residual downstream queue**.  
- **CF2:** Multiply every \(q_B\) by 0.5; B_start' = fork + 0.5\(q_B\); B_end' = B_start' + \(s_B\) (service unchanged). Same join/downstream logic as CF1.  
- **CF3:** Eliminate downstream queue: final_start' = join_ready (observed), final_end' = join_ready + 20. Branches unchanged. Interprets “add F capacity / remove F queue.”

Per-case time savings = \(TFT - TFT'\). Secondary effects on F utilization are qualitative under CF-D1.

**Correction of downstream logic (important):**  
If final_start is a fixed slot (resource busy until then), earlier join_ready only increases measured \(d_c\); **TFT does not improve** until join_ready was the binding constraint on final_start. Under pure “F starts as soon as free and join ready,” we need a resource model.  

**Two bounding interpretations:**

| Bound | Rule | Meaning |
|---|---|---|
| **Optimistic (O)** | final_start' = join_ready' + 0; ignore F contention | Max possible flow-time benefit of branch speedup |
| **Pessimistic / slot (P)** | final_start' = max(join_ready', observed final_start) | Branch speedup helps TFT only if it was delaying past the historical F start |

Under **(P)** CF1: only cases where old final_start = join_ready (zero down_q) could gain — **none** in the data have \(d_c=0\). So **pessimistic aggregate saving = 0**. Under **(O)**: saving = reduction in join_ready (and TFT drops 1:1).

Optimistic CF1 join reductions: F01: 5 min (AB critical), F11: 10 min (A was critical; new join = B_end 11:20). **Total optimistic saving: 15 min across 12 cases; mean 1.25 min/case. 10 of 12 cases: zero benefit** because B or C remains critical.

**Direct benefit:** only A-critical cases (and only the amount until the second-longest branch).  
**Zero-benefit cases:** 10/12.  
**Secondary:** Reducing A may free lab capacity (not observable); may make B’s queue the clearer bottleneck; F congestion largely masks TFT gains under (P).

# 5. Recommended redesigns and risks

## Redesign R1 — Attack B queueing (primary branch bottleneck)

**Actions:** Measure why B starts 5–30 min after fork (shared stress-test machine? setup? batching?). Options: dedicated B capacity, setup reduction, priority for cases whose A/C already done or near done, or parallelize B fixtures.

**Expected effects:**  
- **Throughput:** Higher B capacity raises process throughput if B was starving the join; F may then become binding.  
- **Flow-time tail:** Should cut the right tail (F07/F12-like 75 min FJ stages); largest TFT cases are B-critical.  
- **Utilization:** B busy time per case unchanged if only queue falls; wait waste drops.  
- **New bottlenecks:** A’s constant 50 min becomes critical more often (seen in CF2). F downstream queue may grow if joins arrive earlier in a burst.  
- **Synchronization:** Mean C and A sync waits fall when join moves earlier with B; less idle after early C completion only if join actually moves.  
- **Pilot / measure first:** (1) B resource count and calendar busy/idle from start–end overlaps; (2) cause of q_B (arrival clustering vs single slow resource); (3) correlation of q_B with time of day; (4) pilot priority rule for one B lane and track join_ready and TFT for 2 weeks.

## Redesign R2 — Absorb or remove final-station queue + protect against A floor

**Actions:** (a) Add flexibility at F (cross-train, third resource at peak, or dynamic assignment instead of strict F1/F2 alternation if that is policy); (b) only after B queue is improved, trim A service (method, automation, 20% target from CF1) so the new critical floor drops.

**Expected effects:**  
- **Throughput:** Extra F capacity raises throughput when join_ready batches arrive; alone it does not speed branches.  
- **Flow-time tail / mean:** CF3-scale gains (~15 min mean) if queues are true waits; combines with R1 for additive optimistic gains.  
- **Utilization:** Current F utilization is moderate on average but peaked; added capacity lowers utilization and queue.  
- **New bottlenecks:** Upstream preparation (`upstream` ~20 min stable) or A service.  
- **Synchronization:** Clearing d_c does not change sync waits inside the fork–join; combined with R1 it reduces time cases sit fully complete before F.  
- **Pilot / measure first:** (1) Distinguish queue vs policy (is F intentionally delayed for batch release/quality gates?); (2) reconstruct F1/F2 Gantt from final_start/end — idle gaps vs overlaps; (3) small pilot of “start F at join_ready when a resource is free” and compare d_c and TFT; (4) do **not** invest heavily in A reduction until B queue is down, else most A speedup yields zero case-level TFT benefit (CF1).

**Joint note:** Speeding a non-critical branch does not reduce that case’s TFT (max-based join). Rank interventions by critical frequency × reducible \(q+s\) on the critical path, then by downstream mask. R1 then R2 matches that order. Avoid summing sync waits as a KPI for flow time.

    df[f"{br}_sojourn"] = df[f"{br}_queue"] + df[f"{br}_service"]

    df[f"{br}_sync"] = minutes(df["join_ready"] - df[f"{br}_end"])

df["final_service"] = minutes(df["final_end"] - df["final_start"])

# 3. Critical branch — deterministic tie handling: list all maximizers sorted
def critical_branch(row):
    ends = {"A": row["A_end"], "B": row["B_end"], "C": row["C_end"]}
    m = max(ends.values())
    winners = sorted([k for k, v in ends.items() if v == m])
    return "+".join(winners)  # e.g. "A+B" on ties; single letter otherwise

def recompute(join_ready, arrival, final_start_obs, final_svc, mode="optimistic"):
    """mode optimistic: F starts at join_ready (ignore contention).
       mode pessimistic: final_start = max(join_ready, observed final_start)."""
    if mode == "optimistic":
        fs = join_ready
    else:
        fs = np.maximum(join_ready, final_start_obs)
    fe = fs + pd.to_timedelta(final_svc, unit="m")
    tft = minutes(fe - arrival)
    down = minutes(fs - join_ready)
    return fs, fe, down, tft

# 7. Limits of inference

1. **Causality.** Timestamps show association (B often last; large \(q_B\) co-occurs with long TFT) but not why queues form. Unobserved causes include shared machines, staffing, defects, or priority rules. Counterfactuals assume ceteris paribus independence of other branches’ times — likely false if the same staff multi-task across A/B/C.

2. **Branch resource capacity.** Only F has named resources (F1, F2). A/B/C have no resource IDs or multiplicity. Overlapping A intervals across cases cannot be attributed to 1 vs N lab benches; \(q_A=0\) always may mean dedicated capacity or that A is never contended relative to fork release. Idle time vs capacity cannot be separated from case data alone.

3. **Work preemption and multitasking.** Complete-event timestamps give start and end only. We cannot see pauses, preemption, or split work. “Service” is wall-clock sojourn of the activity, not pure busy time. Sync wait might include undocumented rework holds.

4. **Downstream wait: queue vs policy.** \(d_c=\mathrm{final\_start}-\mathrm{join\_ready}\ge 0\) is consistent with a queue, but also with batching, quality gates, shift policies, or intentional delay until both F resources are scheduled. Alternation of F1/F2 looks like load balancing or assignment policy, not proof of FCFS multi-server queueing. Without idle/busy resource logs or rule documentation, labeling \(d_c\) as pure congestion is an assumption (A3).

5. **Fork release semantics.** `fork_release  arrival` is stable (~20 min) but the upstream preparation content is unobserved. Whether branches *may* start earlier than logged fork is unknown.

6. **External arrivals and stability.** Twelve cases on one day cannot identify steady-state throughput limits, time-of-day seasonality, or long-run utilization. Peak clustering around late morning may not generalize.

7. **Counterfactual interference.** Speeding B may change when cases hit F and thus other cases’ \(d_c\) (queueing externalities). Optimistic bounds ignore this; full simulation would need a resource model not identifiable from these columns alone.

8. **Tie and measurement granularity.** Data are to one minute; true simultaneous ends could be masked. Sync waits of a few minutes may be clock rounding.

**Bottom line:** The max-based decomposition and critical-frequency ranking are well identified from the log under the stated AND-join rule. Causal redesign impact and true F “queue” nature are only partially identified; pilots should instrument resource-level busy/idle calendars and explicit start policies before large capacity spends.
