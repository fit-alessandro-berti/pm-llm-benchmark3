## 1. Consistency rules and evidence model  

1.1 Hard invariants  
H-1  Every event id and object id occurring in a relation must exist in the log.  
H-2  An O2O qualifier is directional and unique per (source, target, qualifier).  
H-3  No event may violate the declared cardinality in the domain description (e.g. Create-Order  1 Order, never a Package).  

1.2 Strong defaults  
D-1  “Pack Item’’ events normally reference one Item and one Package.  
D-2  “Dispatch Package’’ events normally reference one Package and one Delivery.  
D-3  “Record Payment’’ events normally reference one Payment and one Invoice.  
D-4  If an O2O edge exists (e.g. PK-7 packs IT-A1) an E2O edge with the same two objects is much more likely than an unrelated pairing.  
D-5  Matching identifier prefixes (N-420/ev09, N-421/ev10) are 0.8-strength evidence.

1.3 Weak heuristics  
W-1  Matching amounts (100 + 130 = 230) suggest but do not prove invoicing.  
W-2  Deliveries on the same route and timestamp can be bulked together.  
W-3  A Package that already “packs’’ items for Order X is likely to be dispatched on the same Delivery that eventually fulfils Order X.  

1.4  Evidence against repairs  
A-1  Linking the same Payment to two different Invoices would violate real-world banking.  
A-2  Introducing edges that make DEL-Y carry nothing or make PK-8 orphaned contradicts lifecycle intuition.  
A-3  Using only arithmetic equality to link ORD-B to INV-44 would be circular because the amounts in INV-44 were taken from the orders in the first place.

Combination logic  
• Hard invariants must always hold.  
• A candidate edge supported by 2 strong defaults or 1 strong default + 1 weak heuristic gets confidence 0.7.  
• If a candidate is contradicted by any A-rule the confidence is forced below 0.4.

Bundle A – Conservative/minimum change  
• ev08 gets PK-8 (P1) and PK-8 packs IT-B1 (P2).  
• ev10 links to DEL-Y (P3) and DEL-Y carries PK-8 (P4).  
• ev11 left as is; no delivery edge.

• ev14 and PAY-2 both linked to INV-44 (P7, P8).  
Lifecycle: every Item now sits in exactly one Package; every Package is carried by exactly one Delivery; ORD-B is now billed; INV-44 is fully paid.

Bundle B – Bulk-dispatch interpretation  
• P1 and P2 identical to Bundle A.  
• ev10 links to DEL-X (reject P3, accept P5).  DEL-X now carries PK-7 & PK-8.  DEL-Y remains unused (possibly cancelled label).  
• ev11 is related to DEL-X (accept P9).  
• INV-44 stays billed only to ORD-A (reject P6).  
• PAY-2 remains unapplied cash (remove P7, P8).  
Lifecycle: ORD-B still awaiting invoicing; Payment 2 sits unallocated; Delivery object usage is consolidated.

Bundle C (short) could additionally assume an *express* invoice for ORD-B issued later, but is omitted for brevity.

## 5. Lifecycle and cardinality audit (Bundle A)

Order  
• ORD-A: created, populated with items, partially delivered, invoiced and fully paid – lifecycle complete.  
• ORD-B: created, item packed, shipped, now billed – coherent.  

Item  
• Each of the three items is created, packed once and never re-packed. No orphan items.  

Package  
• PK-7 and PK-8 each carry 1 item and are dispatched once. No package travels twice, satisfying D-2.  

Delivery

• DEL-Y now carries PK-8 and is dispatched; confirmation still missing – acceptable open tail.  

Invoice  
• INV-44 bills two orders, receives two payments, balance zero. Supported by both E2O (ev12, ev14) and O2O (PAY-1, PAY-2).  

Payment  
• PAY-1 and PAY-2 each appear in exactly one Record-Payment event and settle one invoice – no duplication.  

Suspicious relationships

• No circular reasoning: we did not rely on P6 to justify P8 or vice-versa.

## 6. Downstream process-mining effects  

Unrepaired log  
• OC-DFG lacks edge “Pack Item  Dispatch Package’’ for IT-B1 because ev08 had no package link.  
• PK-8 appears orphaned in OTG; DEL-Y appears isolated.  
• INV-44 under-counts linked orders; Payment 2 appears as an isolated object.  

Bundle A  
• New OTG edges: PK-8  DEL-Y (carries), INV-44  ORD-B (bills).  
• OC-DFG acquires a second “Pack Item  Dispatch Package’’ occurrence, slightly increasing concurrency measures.  
• Flattening on Order now pulls in both payments when grouping by Invoice, yielding correct financial completeness.  
• ET–OT graph will show two payments per invoice instead of one payment + one orphan object.  

Bundle B  
• OTG: DEL-X now carries two packages; degree of DEL-Y drops to zero.  
• OC-DFG counts a single Dispatch event covering two packages, so frequency of “Dispatch Package’’ stays 2 events but 3 package relations; concurrency on Delivery increases.  
• Order flattening still shows ORD-B not yet invoiced – may trigger conformance alerts downstream.  
• Payment 2 remains isolated, inflating “Record Payment’’ without matching financial closure.  

Specific edges that differ  
• DEL-Y carries PK-8 (Bundle A only) vs DEL-X carries PK-8 (Bundle B).  
• INV-44 bills ORD-B and PAY-2 settles INV-44 (Bundle A), absent in Bundle B.  

## 7. PM4Py-oriented validation outline  

```python
import pandas as pd
from copy import deepcopy
import pm4py

# 0. Clone originals
events_fixed   = deepcopy(events)
objects_fixed  = deepcopy(objects)
relations_fixed = deepcopy(relations)
o2o_fixed      = deepcopy(o2o)

# 1. Append Bundle-A E2O additions
new_e2o = pd.DataFrame(
    [["ev08", "PK-8", "package"],
     ["ev10", "DEL-Y", "delivery"],
     ["ev14", "INV-44", "invoice"]],
    columns=["ocel:eid", "ocel:oid", "ocel:qualifier"])
relations_fixed = pd.concat([relations_fixed, new_e2o], ignore_index=True)

# 2. Append Bundle-A O2O additions
new_o2o = pd.DataFrame(
    [["PK-8",  "IT-B1", "packs"],
     ["DEL-Y", "PK-8",  "carries"],
     ["INV-44","ORD-B", "bills"],
     ["PAY-2", "INV-44","settles"]],
    columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"])
o2o_fixed = pd.concat([o2o_fixed, new_o2o], ignore_index=True)

# 3. Integrity checks
duplicates = relations_fixed.duplicated(["ocel:eid", "ocel:oid", "ocel:qualifier"]).any()
assert not duplicates, "Duplicate E2O detected"
assert set(relations_fixed["ocel:eid"]).issubset(events_fixed["ocel:eid"])
assert set(relations_fixed["ocel:oid"]).issubset(objects_fixed["ocel:oid"])
assert set(o2o_fixed["ocel:oid"]).issubset(objects_fixed["ocel:oid"])

# 4. Build OCEL (version dependent)
ocel_fixed = pm4py.read_ocel_from_df(
    events_fixed,
    objects_fixed,
    relations_fixed,
    o2o_fixed,
    parameters={"stop_when_duplicate": True}
)

# 5. Discover graphs
ocdfg = pm4py.discover_ocdfg(ocel_fixed)
otg   = pm4py.discover_otg(ocel_fixed)
etot  = pm4py.discover_etot(ocel_fixed)

# 6. Flattenings
flat_order    = pm4py.ocel_flattening(ocel_fixed, "Order")
flat_delivery = pm4py.ocel_flattening(ocel_fixed, "Delivery")

print("Integrity OK, graphs built.")
```

(The `read_ocel_from_df` call name may differ between PM4Py versions.)

## 8. Over-repair warnings  

1. Forcing ev11 to reference both DEL-X and DEL-Y would create a many-to-one confirmation never supported by user portals.  
2. Linking INV-44 to ORD-B solely on arithmetic equality might conceal future credit-note events.  
3. Assuming PAY-2 settles two different invoices would invent impossible double spending.  
4. Attaching PK-8 to both DEL-X and DEL-Y would duplicate physical shipment of the same carton.  
5. Fabricating an O2O edge “DEL-Y carries PK-7’’ just to balance package counts would make the OTG falsely symmetric and distort throughput calculations.
