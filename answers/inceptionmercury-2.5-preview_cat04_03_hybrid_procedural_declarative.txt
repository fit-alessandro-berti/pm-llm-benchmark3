

# 1. Policy Interpretation and Conflict Resolution

**Assumptions:**
1.  **Process Backbone:** The core flow requires concurrent data gathering (Capture, Screening, Bank Verify) before risk classification. Classification drives the outcome path.
2.  **Clarification Loops:** Clarification requests must be resolved before the case proceeds to final classification or termination (R3).
3.  **Resources:** Specific task segregation is required (R9).
4.  **Sanctions Escalation:** Requires Legal Opinion before activation (R5).

**R5/R6 Conflict Resolution:**
The R5 requirement (Legal Opinion must precede Activation after Sanctions Escalation) contradicts R6 (Emergency Activation allowed outside Log, Legal Opinion within 24 hours). Since the event log lacks an "emergency" flag or authorization attribute, we cannot technically validate R6 within the conformance model.

*Resolution Options:*
1.  **Strict (R5 Dominant):** Enforce R5 as a hard constraint. Any violation is flagged as a non-compliance error. R6 is handled by manual audit outside the system.
2.  **Tolerant (R6 Dominant):** Allow the sequence `Escalation -> Activate -> Opinion` but enforce the 24-hour deadline (from R6 text) via temporal rules.

**Chosen Resolution:** Option 1 (Strict).
**Reasoning:** Automated models cannot detect "joint authorization" without attributes. Tolerating R5 violations without evidence of emergency authorization increases legal and compliance risk.
**Compliance Risk:** This choice increases false positives (flagging emergency cases as violations). Users must rely on external audit logs to approve emergency exceptions.

# 3. Procedural Backbone

**Formal Description:**
The backbone is a Process Tree with a parallel block (Capture, Screen, Verify), followed by Classify, followed by an XOR split (Reject, Manager Approval, High-Risk Path). Both Approval branches converge to Activate, then Release First Payment, then Close Onboarding. Clarification loops occur before Classify.

**PM4Py Code:**
```python
from pm4py.process_tree.process_tree import ProcessTree
from pm4py.process_tree.node import Node, OperationType

# Simplified representation of Process Tree structure
procedural_model = ProcessTree(
    operation=OperationType.XOR,
    children=[
        ProcessTree(operation=OperationType.AND, children=[
            ProcessTree(operation=OperationType.AND, children=[
                Node("Receive Onboarding Request"),
                Node("Capture Master Data"),
                Node("Run Sanctions Screening"),
                Node("Verify Bank Account"),
                Node("Request Clarification"), # Loop approximated here
                Node("Receive Clarification"),
                Node("Classify Risk"),
                Node("Sanctions Escalation")
            ]),
            ProcessTree(operation=OperationType.XOR, children=[
                Node("Reject Vendor"),
                ProcessTree(operation=OperationType.AND, children=[
                    Node("Manager Approval"),
                    Node("Obtain Legal Opinion"),
                    Node("Enhanced Due Diligence"),
                    Node("Compliance Approval")
                ]),
                Node("Activate Vendor"),
                Node("Release First Payment"),
                Node("Close Onboarding")
            ])
        ])
    ]
)
# Note: In practice, use PM4Py converter for structured trees. 
# This is an approximation to show structure.
```
**Explanation:**
- **Concurrency:** Capture, Screen, Verify modeled in `AND` before `Classify Risk`.
- **Choices:** `XOR` between `Reject Vendor` and approval paths.
- **Clarification Loops:** Approximated as `AND` before `Classify Risk` in tree. In a strict tree, a true loop is difficult without explicit loops; this assumes clarifications clear before classification.
- **Terminal Outcomes:** `Close Onboarding` follows `Reject Vendor` OR `Release First Payment`.
- **Post-Activation:** Changes (`Change Bank Details`, `Suspend Vendor`) are excluded from backbone as exceptions.

**Overlap Explanation:**
- **always_before:** Enforces R7 (Screening -> Escalation).
- **never_together:** Enforces R1 (Reject vs Activate) and R8 (Manager/Compliance exclusions). This creates redundancy with DECLARE's `noncoexistence` checks.
- **activ_freq:** Enforces R10 (exactly one).
- **Disagreement:** Declarative models enforce "eventually" (response), while Skeleton enforces hard structural constraints (`never_together`).

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd

def check_resource_segregation(log_df):
    # R9: Verify Bank vs Approval; Capture vs Activate
    # Find Verify Bank activity
    verify = log_df[log_df['activity'] == 'Verify Bank Account']
    # Find Approvals
    approvals = log_df[log_df['activity'].isin(['Manager Approval', 'Compliance Approval'])]
    # Check Resources
    violation = False
    if not verify.empty and not approvals.empty:
        verify_res = verify['resource'].values[0]
        approver = approvals['resource'].values[0]
        if verify_res == approver:
            violation = True
    return violation

def check_emergency_policy(log_df):
    # R6: Check if Activate occurs before Legal Opinion when Escalation happened
    esc = log_df[log_df['activity'] == 'Sanctions Escalation']
    act = log_df[log_df['activity'] == 'Activate Vendor']
    opinion = log_df[log_df['activity'] == 'Obtain Legal Opinion']
    
    # if Escalation occurred
    if not esc.empty:
        act_time = act['time'].values[0] if not act.empty else float('inf')
        opinion_time = opinion['time'].values[0] if not opinion.empty else float('inf')
        
        # If Activate before Opinion
        if act_time < opinion_time:
            # In real audit, check for 'emergency' attribute in event log
            # If missing, flag as violation
            return "Violation: Activation before Legal Opinion without Emergency Flag"
    return None
```

# 9. Contradictions, Redundancies, and Blind Spots

- **Redundancy:** R1 (Activate vs Reject) and R8 (Manager vs Compliance) are enforced in both DECLARE (`noncoexistence`) and Log Skeleton (`never_together`). This wastes compute but increases confidence.
- **Inconsistency under Loops:** R3 (Clarification loop) is difficult to enforce in DECLARE (which is event-ordering). The Process Tree approximation assumes clarification loops clear; if clarification repeats indefinitely, the tree blocks.
- **Vacuity:** In T4, DECLARE noncoexistence (R8) passes because Manager Approval was executed (no EDD). The "no-co-occur" constraint is trivially satisfied.
- **Missing Attributes:** R6 requires an "emergency" flag absent in the event log. We cannot distinguish emergency from violation without manual annotation.
- **Timestamp Limitations:** R12 checks time, but does not consider weekends or holidays.
- **Metadata Risk:** High support/confidence in DECLARE does not imply compliance; it only reflects the historical log.

# 10. Deployment Recommendation

**Canonical Representation:** Process Tree (for control flow).
**Authoritative Policy Layer:** Resource/Data Layer + DECLARE (for structural constraints).

**Order of Checks:**
1.  **Control Flow (Tree):** Fast filter for valid start/end sequences.
2.  **Resource Layer:** Critical for segregation of duties (R9).
3.  **Declarative:** Validates logic (R4, R5).
4.  **Temporal:** Flags warnings (R12).

**Handling Contradictions:**
-   **Hard vs Soft:** Resource/Control failures block downstream steps (Hard violations). Temporal flags trigger user alerts but allow flow.
-   **Layer Conflict:** If Process Tree passes but DECLARE fails (e.g., sequence valid but violates R5), the DECLARE result is authoritative for compliance reporting.
-   **Reporting:** Present findings with "Reason Codes" (e.g., "SOD Violation: R9", "Late Check-in: R12").
