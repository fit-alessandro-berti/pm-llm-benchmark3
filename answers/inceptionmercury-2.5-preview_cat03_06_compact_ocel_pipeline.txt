### 1. Modeling assumptions

- **Object types**: Order, Item, Package, Delivery, Invoice, Payment (Capitalized as standard OCEL).
- **E2O qualifiers**: `associated_with`. This is neutral for all events. We trust O2O for semantic relations like `contains` or `settles`.
- **O2O direction**: Source-to-Target (e.g., Order contains Item).
- **Logistics and financial relations**: Payment M1 relates directly to Invoice V1. Invoice relates to Orders via O2O. Events relating to P1 (shared) link to both Orders in E2O relations (E6, E7, E9).
- **Propagation**: Analytical relations (e.g., Payment linked to Order) are inferred via O2O chains, not duplicated in E2O.
- **Version assumption**: The `OCEL` constructor uses DataFrames directly, matching PM4Py 2.3+ structure.

### 4. Expected flattened behavior

- **Order (O100)**: Trace includes Create, Add I1, Add I2, Shared Stock, Shared Pack P1, Shared Dispatch D1, Confirm D1, Close.
- **Order (O200)**: Trace includes Create, Add I3, Shared Stock, Shared Pack P1, Shared Dispatch D1, Confirm D1, Close (earlier than O100).
- **Package (P1)**: Trace includes Add Item I1, Add Item I3, Pack P1, Dispatch P1.
- **Package (P2)**: Trace includes Add Item I2, Pack P2, Dispatch P2.
- **Shared Events**: Events like `Reserve Stock` appear twice per trace if not carefully handled.
- **Omitted Lifecycles**: Payment lifecycle is excluded unless Invoice is flattened.
- **Misleading Interpretations**: Flattening on O100 might suggest the process finishes only when O100 closes (April 7), ignoring O200 finished earlier.
- **Payment Flattening**: Weak because M1 and M2 are separate objects with short traces (e.g., `Record Payment` and no subsequent events), offering no process view.

### 5. Expected object-centric structures

- **OC-DFG**: Shows two parallel Order branches merging at `Reserve Stock` and `Pack Package` (P1). Payment is isolated until V1 is reached.
- **OTG**: Order connects to Item; Package connects to Item; Delivery connects to Package. A bridge exists V Payment -> Invoice -> Order.
- **ET–OT**: Event types map cleanly to Objects (e.g., `Create Order`  `Order`).
- **Object-Centric Petri Net**: Places for objects; shared events (like `Pack Package`) consume multiple object tokens.
- **Interactions**: P1 is the central hub linking O100 and O200; V1 links payments to both orders.

### 6. Modeling alternatives

1. **Source-minimal**: E2O only links Event to its primary object (e.g., E6 links only to `I1` and `I3` not Orders).
    *   *Impact*: OC-DFG loses the cross-order concurrency view unless O2O is aggressively propagated.
2. **Full operational**: Events like E7 relate to I1, I3, P1, O100, and O200 explicitly in E2O (no reliance on O2O).
    *   *Impact*: Simplifies flattening but inflates relation table size.
3. **Propagated**: E2O relations include inferred links (e.g., `Record Payment` relates to O100).
    *   *Impact*: Creates redundancy; flattening on Order shows unrelated payment steps that were originally on Invoice.

### 7. Failure modes

1. **Relation inflation**: Adding O100 explicitly to `Record Payment` event relations.
2. **Missing E2O links**: E7 `Pack Package` not linking to O200.
3. **Treating propagation as observation**: Adding `M1` as related to `O100` in E2O.
4. **Duplicate shared events**: Flattened log has E7 twice in O100 trace.
5. **Ambiguous payment allocation**: Assuming M1 pays O100 specifically without explicit O2O.
6. **Overly short Payment traces**: Flattening M1 results in 1-event trace.
7. **API version mismatch**: PM4Py version changes constructor signatures.
8. **False total order**: Timestamp ties treated as strict sequence, breaking parallelism.

### 8. Final semantic checks

1. O100 and O200 both exist and are linked to V1.
2. P1 contains I1 and I3.
3. E6 (Reserve Stock) has timestamp before packing events.
4. Payment M1 and M2 are distinct entities linked to V1.
5. No events relate to items that were never added to orders (e.g., I3 must relate to O200).
6. O200 closes before O100 (10:30 UTC < 10:35 UTC on 2026-04-07).
