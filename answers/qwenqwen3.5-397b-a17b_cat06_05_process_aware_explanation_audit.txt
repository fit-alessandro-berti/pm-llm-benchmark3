## 2. Process-model consistency checks

To ensure explanations align with the normative process and prediction horizon, the following validation suite must be implemented:

1.  **Prefix-Time Availability Check (Oracle Test):**
    *   **Role:** Verify that every feature value used in a prediction at $t_0$ is derived exclusively from events with timestamps $\le t_0$.
    *   **Method:** Replay the feature generation pipeline using a "time-travel" database snapshot as of $t_0$. Compare against production values.
    *   **Limitation:** Requires historical data versioning; cannot detect logical leakage where a feature is technically timestamped before $t_0$ but logically implies future knowledge (e.g., `final_handler_team`).

2.  **Activity-Order Feasibility (Conformance Checking):**
    *   **Role:** Detect impossible sequences like `Claim Closed` before `Damage Assessment`.
    *   **Method:** Align event logs against a Petri Net or BPMN model of the normative process. Flag traces with fitness < 1.0.
    *   **Limitation:** A frequent DFG edge is not a rule; deviations happen (e.g., withdrawals). However, hard constraints (Close must be last) must be enforced.

3.  **Same-Timestamp Ambiguity Resolution:**
    *   **Role:** Resolve ordering when timestamps are identical (e.g., Case Z).
    *   **Method:** Enforce reliance on a monotonic `sequence_index` or `event_id` rather than raw timestamps for ordering logic.
    *   **Limitation:** Legacy systems may lack sequence indices; requires ingestion layer updates.

4.  **Complete-Trace Information Scan:**
    *   **Role:** Identify features aggregating the full trace (e.g., `full_trace_variant_id`, `total_case_duration`).
    *   **Method:** Static code analysis of feature definitions to flag aggregations without time-bounds (e.g., `COUNT(*)` vs `COUNT(CASE WHEN ts <= t0)`).
    *   **Limitation:** Cannot detect semantic leakage in joined tables (e.g., `final_handler_team`).

5.  **Enabled vs. Future-Possible Activity Check:**
    *   **Role:** Ensure explanations do not reference activities impossible at $t_0$.
    *   **Method:** At $t_0$ (post-Coverage Check), `Appeal` is structurally impossible (requires Decision). `Fraud Investigation` is possible but not yet occurred.
    *   **Limitation:** Requires a machine-readable process schema.

6.  **Repeated Decision Semantics Validation:**
    *   **Role:** Verify legitimacy of multiple `Settlement Decision Recorded` events.
    *   **Method:** Check if a second decision is preceded by an `Appeal` event. If not, flag as data error.
    *   **Limitation:** Does not validate the *content* of the decision, only the structural validity.

## 3. Alternative feature interpretations

The surviving or repairable signals must be reclassified to prevent causal misinterpretation.

| Class | Features | What MAY be claimed | What MAY NOT be claimed |
|---|---|---|---|
| **Defensible Predictive Signal** | `initial_damage_complexity`, `elapsed_since_registration_at_t0` | These states correlate with higher processing time requirements. | That complexity *causes* the breach; it may be correlated with unmeasured factors (e.g., missing parts). |
| **Process-State / Congestion** | `queue_length_at_t0` | High queue load is associated with slower processing times system-wide. | That the queue *caused* this specific claim's delay; individual handling time varies. |
| **Proxy Requiring Fairness/Robustness Review** | `claimant_region`, `claimant_channel` | These attributes improve statistical accuracy in the current environment. | That region/channel are *drivers* of delay; this risks encoding socioeconomic bias or network disparities. |
| **Drift / Calendar Proxy** | `calendar_week` | Certain periods correlate with higher breach rates (holidays, policy changes). | That the week number itself causes delay; this is a confounder for staffing or policy effects. |
| **Unusable Until Lineage Repaired** | `prior_claim_count`, `same_day_document_count` | None until SQL logic and refresh timestamps are fixed. | None. Using them currently violates the $t_0$ horizon. |

**Note on Causality:** Predictive importance (SHAP) measures association, not intervention. Reducing `queue_length` might not reduce breach risk if the queue is long *because* complex claims are arriving. Explanations must use "associated with increased risk" rather than "causes delay."

## 5. Recommendations for explanation validation

1.  **Feature-Store Design with Lineage Tracking:**
    *   Implement a feature store that enforces `creation_timestamp` and `valid_from`/`valid_to` windows.
    *   Every feature must carry a metadata tag indicating its "look-ahead" window (must be $\le 0$ for real-time prediction).

2.  **Historical Feature Timestamps:**
    *   Audit all joined tables (e.g., `queue_length`, `risk_score`). Ensure joins are performed on `event_time` rather than `extraction_date`.
    *   Store the exact snapshot version used for each prediction to enable reproducibility.

3.  **Prefix-Only Recomputation Pipeline:**
    *   Establish a "shadow mode" pipeline that recalculates features using only data available at $t_0$.
    *   Run this nightly against production predictions to detect drift between "training features" (often full trace) and "serving features" (prefix only).

4.  **Process-Conformance Tests:**
    *   Integrate conformance checking into the data ingestion layer. Traces violating hard constraints (e.g., `Close` before `Assessment`) should be quarantined for manual review, not fed to the model.
    *   Use sequence indices to resolve same-timestamp ambiguities automatically.

5.  **Calibration After Feature Removal:**
    *   Retrain the model excluding all critical leakage features (`duration`, `appeal`, `variant_id`).
    *   Expect a drop in AUC; recalibrate probability thresholds to maintain precision/recall balance without relying on outcome leakage.

6.  **Explanation Stability Monitoring:**
    *   Monitor SHAP values for "impossible" features. If `appeal_seen_anywhere` reappears as important, trigger an alert.
    *   Track explanation divergence between the "full trace" model and the "prefix-only" model.

7.  **Proxy/Fairness Analysis:**
    *   Conduct a disparate impact analysis on `claimant_region` and `claimant_channel`.
    *   If these features drive significant risk separation, document the business justification or consider constrained modeling to prevent discriminatory outcomes.

8.  **Monitoring for Schema or Process Drift:**
    *   Monitor the frequency of "unknown" process variants. A spike may indicate a process change (e.g., new fraud step) that invalidates current feature definitions.
    *   Alert on changes in the distribution of `queue_length` or `calendar_week` effects to detect policy or seasonal shifts.
