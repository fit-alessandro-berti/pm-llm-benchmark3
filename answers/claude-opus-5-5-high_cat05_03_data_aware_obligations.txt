## 1. Temporal Data Semantics

**Event order.** Within a case, events are totally ordered by the pair (time:timestamp, event_index), compared lexicographically. I write `e ≺ e'` for "e happens strictly before e'", meaning same case and either `ts(e) < ts(e')`, or equal timestamps and `idx(e) < idx(e')`. `e ⪯ e'` means `e ≺ e'` or `e = e'`. The sort is stable and explicit. I never rely on file row order or on pm4py's internal row index. Cross-case ties (for example, a global sanctions-list event at the same second as a case event) cannot be resolved by `event_index`, which is only meaningful within a source-system timestamp. Such ties are treated conservatively, as "not shown to be covered."

**State reconstruction.** Case state is a vector of the attributes amount, risk_level, jurisdiction and customer_type. The value of attribute *a* at event *e* is:

`val(a, e)` = the value carried by the latest event `e* ⪯ e` whose cell for *a* is non-blank; otherwise `UNKNOWN`.

The state is right-continuous. An update is effective at its own event's timestamp and position, and it is visible to that event and to every later one. It is never visible to earlier events, because only forward-fill is used (no backward fill and no case-level broadcast).

**Blanks.** A blank cell means "no update at this event." It is never read as null, "none," LOW, RETAIL, DE, or 0. If an attribute has never been set, its value is `UNKNOWN` (⊥). ⊥ is a third truth-relevant value, not a low-risk default (R6).

**Non-state columns.**
- The `jurisdiction` cell on `Sanctions_List_Update` names the jurisdiction added to the list. It is a payload of an external event, not an update to the transaction's jurisdiction. It is kept in a separate `listed_jurisdiction` field and excluded from forward-fill.
- An `exemption_id` on `Release_Funds` or `Record_Exemption` is a claim or reference. It is not proof of validity.
- `note` is free-text evidence. For example, "review document has no amount" and "approved standard review packet" matter for review coverage.

**Material change.** Materiality is defined per obligation and always relative to what the governing review actually saw:
- **Amount (R1/R4).** An increase counts if `amount_now > 1.2 × val(amount, review)`. The baseline is the amount at the review, measured cumulatively. It is not measured against the previous update, so salami-sliced increases still count. A decrease is not material. Invalidation is sticky: a later decrease does not revive an invalidated review. If the baseline at the review is ⊥, any later amount is *unclassifiable*, not "non-material."
- **Jurisdiction (R1).** A change to a different non-DE jurisdiction is material, because the review did not cover it. A change to DE is *de-scoping*: it removes the R1 trigger rather than creating new unreviewed risk.
- **Risk profile (R2).** The *onset* of the condition (a change into risk_level = HIGH, or customer_type = PEP) is material. The relevant Enhanced_Review must follow the latest onset.

**Final attributes.** The last value in a case is only evidence about the time it was recorded. It is never projected backward onto the release. For example, TX-305's settlement amount of 150,000 on 04-07 is not the release amount on 04-06. TX-311's final DE is not the jurisdiction the Enhanced_Review saw.

**Four kinds of time.**

| Time | Meaning | Example |
|---|---|---|
| Event time | The log timestamp at which the activity or update happened | Release_Funds TX-310 at 10:00 |
| Effective time | When a fact holds for rule purposes. For attributes, this is the event time unless evidence establishes otherwise. For exemptions, it is `effective_from`/`expires` in the register. | EX-88 effective 08:00 |
| Record time | When the fact was written to a system of record | Record_Exemption at 11:00 for both exemptions |
| Evidence time | The earliest time at which independent, tamper-evident evidence proves the fact existed | EX-77: qualified signature at 09:05. EX-88: no earlier than 10:30, when the signing certificate was created. |

The governing principle is that a fact counts at time *t* only if its **evidence time ≤ t**. A later record time does not defeat earlier evidence (EX-77). A displayed field does not create evidence time on its own (EX-88). An effective_from date earlier than the proven approval cannot make an exemption valid before it demonstrably existed.

**Further conventions.**
- A single activity event is treated as its completion, because there is no lifecycle attribute.
- Amounts are treated as EUR.
- "Before release" means strictly `≺ Release_Funds`.
- Absent events are treated as absent (log completeness), except where the log itself signals incompleteness, for example "amount feed unavailable."

| R7 | Every obligation | Evaluate on `val(·, trigger)` | `≺` is lexicographic on (ts, event_index); state the consequence of every tie | Latest known value at the relevant event | n/a | n/a | Stable sequence numbers |

**Formal pseudo-logic.** The notation is Datalog-like with Kleene three-valued truth {T, F, U}. `e ≺ e'` means *e strictly precedes e'* in the order defined above, and `⪯` is its reflexive version. All quantifiers range over events of the same case unless marked *global*.

```text
Order & state (R7)
  e ≺ e'  :-  case(e)=case(e'), (ts(e)<ts(e') ; ts(e)=ts(e'), idx(e)<idx(e')).
  val(a,e) = upd(a,e*)  where e* = max≺ { e' ⪯ e | upd(a,e') ≠ blank, e' is a state event };  else ⊥.
  -- no clause lets val(a,e) depend on any e'' with e ≺ e''  (no backward flow)
  -- comparisons with ⊥ evaluate to U (Kleene); U ∧ F = F, U ∨ T = T.

R4 (review invalidation; direction: review v BEFORE change m BEFORE trigger r)
  Invalid(v,r) = T  :-  act(v)∈{SR,ER}, ∃m: v ≺ m ≺ r, upd(amt,m) > 1.2·val(amt,v).
  Invalid(v,r) = U  :-  val(amt,v)=⊥, ∃m: v ≺ m ≺ r, upd(amt,m)≠blank.
  -- decreases never make Invalid true; invalidation is not undone by later decreases.

R1 (direction: ER e BEFORE release r; every material change m BEFORE e)
  Trig1(r)     = act(r)=Release ∧ val(jur,r)≠DE ∧ val(amt,r) ≥ 100000          (F if jur=DE or amt<100000)
  JurMat(e,r)  = ∃m: e ≺ m ≺ r, upd(jur,m) ∉ {val(jur,e), DE}
  CoverER(e,r) = act(e)=ER ∧ e ≺ r ∧ ¬Invalid(e,r) ∧ ¬JurMat(e,r)
  Ok1(r)       = ¬Trig1(r) ∨ ∃e CoverER(e,r) ∨ ∃x Exempt(x,R1,r)
  Viol1(r)     = Trig1(r)=T ∧ Ok1(r)=F

R2 (direction: onset o BEFORE ER e BEFORE approval c BEFORE release r)
  Cond2(e)  = val(risk,e)=HIGH ∨ val(ctype,e)=PEP
  onset(r)  = max≺ { o ⪯ r | Cond2(o)=T ∧ (o first event ∨ Cond2(pred(o))≠T) }
  Ok2(r)    = ¬Cond2(r) ∨ ∃e,c: act(e)=ER ∧ act(c)=CA ∧ onset(r) ≺ e ≺ c ≺ r ∧ Covers(c,e)
  Covers(c,e) = T unless evidence shows c approved a different (e.g. standard) packet
  Viol2(r)  = Cond2(r)=T ∧ Ok2(r)=F

R3 (direction: list update u BEFORE release r; required screen s AFTER u and BEFORE r)
  Listed(j,u) :- act(u)=Sanctions_List_Update, listed(u)=j.          -- global event, not case state
  Viol3(r) = ∃u: Listed(val(jur,r),u) ∧ u ≺g r ∧ ¬∃s (act(s)=Screen ∧ u ≺g s ≺g r)
  -- ≺g: global order by ts; equal-ts cross-case pairs are treated as "not covered"
  -- equivalently: the latest screen precedes the latest relevant list update

R5 (direction: proven approval time ≤ trigger time; record time unconstrained)
  Exempt(x,O,r) = approver(x)=Head_Compliance ∧ O ∈ waives(x)
                ∧ effective_from(x) ≤ ts(r) < expires(x)
                ∧ scope_j(x)=val(jur,r) ∧ scope_c(x)=val(ctype,r) ∧ val(amt,r) ≤ cap(x)
                ∧ evidenceTime(approval(x)) ≤ ts(r)
  evidenceTime(approval(x)) = min{ t | an independent, tamper-evident item proves approval existed at t }
     -- QES trusted timestamp with a certificate valid at t: yes; outage-explained later DB insert: corroborates
     -- displayed date alone: no; uncorroborated statement by an interested party: no
  Defeasibility: Exempt defeats Viol1 only if Exempt = T.  Exempt = U does not discharge;
                 the burden of proof is on the party invoking the exemption.

R6 / classification
  NONCOMPLIANT        :- ∃k Viol_k(r)=T.
  INDETERMINATE       :- ¬NONCOMPLIANT, ∃k (Trig_k=U ∨ Ok_k=U).
  JUSTIFIED_EXCEPTION :- all Ok_k=T, ∃k discharged only via Exempt.
  COMPLIANT           :- all Ok_k=T without relying on an exemption.
```

## 4. Ambiguities and Alternative Readings

**TX-305 (INDETERMINATE).**
- *What would make it COMPLIANT:*
  - an immutable release payload (payment message or ledger posting) showing the release amount < 100,000, which means R1 was never triggered. The 150k settlement would then be a separate post-release amendment issue.
  - or a payload showing ≥ 100,000 together with evidence that the Enhanced_Review assessed that amount, and an upstream audit trail showing no amount change between 11:15 and 11:30.
- *What would make it NONCOMPLIANT:*
  - evidence that the release amount was ≥ 100k and the ER did not assess the amount (its document has no amount, so it cannot be an enhanced review of a high-value transfer),
  - or evidence that the amount was set or increased after 11:15.
- *Rejected reading:* treating settlement = release amount (150k ≥ 100k, ER present, so COMPLIANT). This copies a later value backward, which R7 forbids. It is also only a hypothesis ("may equal"), and there is no immutable release payload.
- *Dominance argument:* every world consistent with a *complete* log is either untriggered or covered. Only worlds with an unlogged change, or an ER that did not cover the amount, are violations. Because the log itself declares the amount feed unavailable, completeness cannot be assumed. Substantively the case is probably compliant, but the evidence is deficient, so it stays INDETERMINATE.

**TX-310 (NONCOMPLIANT; the most contestable case).**
- *Reasoning:* the deviation (no ER for a triggered R1) is established. The exception is defeasible and must be proven. The only timely-looking evidence (the displayed 08:50) is affirmatively contradicted by the 10:30 certificate creation.
- *Would become JUSTIFIED_EXCEPTION* with independent pre-10:00 evidence of Head_Compliance approval: a workflow log, email or chat from Head_Compliance, a recorded call, or an earlier signed version of the document. It would also need a benign explanation for the 10:30 certificate, such as certificate rotation followed by re-signing of an already-approved document, with the earlier version preserved. This also presupposes that policy accepts oral or informal approval. If written approval is required, oral approval cannot cure the case.
- *Would become INDETERMINATE* under a "presumption of validity of registered exemptions" evidentiary standard, where the auditor must prove absence of approval. I reject this because R5 places the burden on the exemption ("the evidence supports that approval existed at the relevant time").
- *Would become NONCOMPLIANT with Critical severity* if forensic review shows deliberate backdating, which would be a separate misconduct finding.

**TX-302 (COMPLIANT).**
- *Would become JUSTIFIED_EXCEPTION* if the 09:20 Enhanced_Review turned out to be only a start event, incomplete, or about another transaction. EX-77 would then discharge R1, since its evidence time (QES at 09:05) precedes the trigger.
- A naive record-time reading (the exemption "exists" only from 11:00) would invalidate EX-77. The case would still be COMPLIANT through the ER, so the result is robust.
- It would be NONCOMPLIANT only if both the ER were invalid and the QES or hash were impeached.

**TX-311 (COMPLIANT).**
- *Tie-breaker consequence:* because event_index 3 precedes 4, the ER saw jurisdiction US and amount 115k, after the 16:10 increase. The switch to DE comes after the review.
- *Reversed order* (jurisdiction change before the ER): the ER sees DE, R1 is untriggered at release, and the case is still COMPLIANT. The outcome does not depend on the tie-break under the primary reading.
- *"Sticky activation plus any change is material" reading:* the obligation activated at 16:10 persists, and any later data change requires re-review. The ER at #3 then precedes a data change at #4, so it is not "after the latest material data change," giving NONCOMPLIANT. Under this reading the tie-break is decisive: the reversed order would be compliant. I reject it because a move to DE removes the R1 risk rather than adding unreviewed risk, and R4 frames materiality as risk-increasing.
- *Change is erroneous or evasive:* if the change to DE is invalid, the true jurisdiction is US and R1 is triggered at release. The ER at 16:20 still follows the last material change (16:10), so the case remains COMPLIANT, though with a separate data-integrity finding. If event_index reflected ingestion order rather than business order, the order would be uncertain, but the result would not change.

**Other cases.**
- **TX-304:** if the list update had a later *effective* time than its publication (for example, effective 09:00), or if the release gateway screens against the live list at release and logs that screen, R3 would not be violated, giving COMPLIANT. Without such evidence the 08:30 event time governs.
- **TX-306:** under the stricter reading "any post-review change invalidates reviews/approvals," the 12:30 update would force a re-review, giving NONCOMPLIANT. R4's 20% threshold and the "amount-dependent" wording support COMPLIANT. R2 does not depend on amount at all.
- **TX-308:** if the threshold were exclusive (> 100k), R1 would be untriggered, which is still COMPLIANT. If the amount were not EUR, recompute at the release-time FX rate. The result could flip only if the amount fell below the threshold and no ER existed, which is not the case here.
- **TX-307:** it would become COMPLIANT only if evidence showed the "Standard_Review" was in fact conducted to the enhanced standard (a mislabelled activity) and the CA covered that packet. The semantic facts reject curing by a standard packet.
- **TX-309:** the step-wise (+22.9%) and cumulative-from-ER (+22.9%) baselines agree. If the 15:28 update were shown to be a correction back to a value the ER already assessed (provenance), the case could become COMPLIANT. Nothing in the log says so.

def annotate_material_changes(g):
    """R4 relative to the latest review of either type: >20% cumulative increase vs the reviewed amount."""

    for _, e in g.iterrows():
        tags = []
        if e[ACT] == "Create_Transaction":
            tags.append("INITIAL")
        elif e[ACT] in ("Standard_Review", "Enhanced_Review"):
            reviewed, base_amt = True, e["cur_amount"]
        elif is_state_event[e.name]:
            new_amt, new_jur = e["upd_amount"], e["upd_jurisdiction"]
            if pd.notna(new_amt):
                if not reviewed:
                    tags.append("PRE_REVIEW_CHANGE")
                elif pd.isna(base_amt):
                    tags.append("UNCLASSIFIABLE_FROM_UNKNOWN")
                elif new_amt > base_amt * (1 + MATERIAL_INCREASE):
                    tags.append("MATERIAL_INCREASE")
                else:
                    tags.append("NON_MATERIAL_AMOUNT")
            if pd.notna(new_jur) and new_jur != prev_jur:

            if pd.notna(e["upd_risk_level"]) or pd.notna(e["upd_customer_type"]):

        prev_jur = e["cur_jurisdiction"]
        status.append("|".join(tags))
    g["change_class"] = status
    return g

def er_validity_for_r1(g, er, release):
    """Is the ER still valid for amount/jurisdiction-dependent R1 at this release?"""
    if er is None:
        return "NO_ER", None
    after = g[(g.seq > er.seq) & (g.seq < release.seq)]
    amt_upd = after[after["upd_amount"].notna()]
    if pd.isna(er["cur_amount"]):
        return ("UNCLASSIFIABLE_FROM_UNKNOWN", amt_upd.iloc[0][TS]) if len(amt_upd) else ("AMOUNT_BASIS_UNKNOWN", None)
    hit = amt_upd[amt_upd["upd_amount"] > er["cur_amount"] * (1 + MATERIAL_INCREASE)]
    if len(hit):
        return "INVALIDATED_BY_AMOUNT", hit.iloc[0][TS]
    jur_upd = after[after["upd_jurisdiction"].notna() & (after["upd_jurisdiction"] != er["cur_jurisdiction"])
                    & (after["upd_jurisdiction"] != HOME_JURISDICTION)]
    if len(jur_upd):
        return "INVALIDATED_BY_JURISDICTION", jur_upd.iloc[0][TS]
    return "VALID", None


def evaluate_exemptions(g, release):
    rows = []
    for ex_id in g["exemption_id"].dropna().unique():  # later records are admissible evidence
        reg = EXEMPTIONS[EXEMPTIONS["exemption_id"] == ex_id]
        if reg.empty:
            rows.append((ex_id, "NOT_IN_REGISTER", None))
            continue
        ex = reg.iloc[0]
        t = release[TS]
        scope_ok = (release["cur_jurisdiction"] == ex.scope_jurisdiction
                    and release["cur_customer_type"] == ex.scope_customer_type
                    and pd.notna(release["cur_amount"]) and release["cur_amount"] <= ex.scope_max_amount)
        formal_ok = (ex.approved_by == "Head_Compliance" and ex.effective_from <= t < ex.expires_at)
        if not (scope_ok and formal_ok):
            status = "INVALID_SCOPE_OR_TERMS"
        elif pd.notna(ex.verified_approval_ts) and ex.verified_approval_ts <= t:
            status = "VALID"
        elif pd.notna(ex.uncorroborated_claim_ts) and ex.uncorroborated_claim_ts <= t:
            status = "CONTESTED_UNPROVEN"
        else:
            status = "NOT_ESTABLISHED"
        rows.append((ex_id, status, ex.verified_approval_ts))
    return rows

        f"{e[ACT]}@{e[TS]:%m-%d %H:%M}:" + ",".join(f"{c}={e[c]}" for c in STATE_COLS if pd.notna(e[f'upd_{c}']))

**What the code does, and its limits.**
- *Labels.* The code emits `machine_label` values of `NONCOMPLIANT_CANDIDATE`, `COMPLIANT_CANDIDATE`, `EXCEPTION_CANDIDATE`, or `REVIEW_REQUIRED`. It derives them from rule predicates evaluated on event-time state and evidence timestamps. There is no per-case lookup.
- *TX-310.* It is labelled `REVIEW_REQUIRED` (`VIOLATED_UNLESS_EXEMPTION_PROVEN`) because weighing an interested witness against a certificate timestamp is a human evidential judgment. The narrative classification in §3 applies the burden-of-proof rule and concludes NONCOMPLIANT.
- *TX-305.* It is labelled `REVIEW_REQUIRED` because the R1 trigger is unknown. The `naive_final_state_r1` column shows that a final-state check would wrongly treat it as triggered and covered.
- *DECLARE demo.* The unconditional precedence constraints give TX-302 and TX-309 (compliant and noncompliant) the same deviation fitness of 0.5. They flag TX-304 for a missing ER that R1 never required, since 60k is below the threshold. They pass TX-307's CA even though it covered a standard packet. They pass TX-309's stale ER. They cannot express "if amount ≥ 100k at release," "after the latest material change," "unless an exemption was proven at release time," or unknown values.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage, and its twin, stale initial state.** Control-flow checks usually filter or condition on case-level attributes. The final value then gets broadcast backward:
   - TX-305's settlement amount (150k) makes R1 look triggered and satisfied at release.
   - TX-311's final DE hides that the ER reviewed a US transaction.
   - The creation-time snapshot is equally wrong: TX-307 created as RETAIL would miss PEP, and TX-301 created at 80k would miss R1.

   Obligations must be evaluated on `val(a, trigger)`, which needs a state-reconstruction step that control-flow models lack.
2. **Conditional activation.** R1 and R2 are active only when data conditions hold at the activation event. Plain DECLARE `precedence(Enhanced_Review, Release_Funds)` is unconditional. It over-reports (TX-304 at 60k, MEDIUM, CORPORATE has no ER obligation at all) and cannot switch obligations on and off within a case, as when the R1 condition held in TX-311 at 16:10 and stopped holding at 16:20 #4. Data-aware (MP-)Declare activation conditions are needed, and they must be evaluated on reconstructed state, not on the event payload alone, because the release event carries no amount.
3. **Material changes after review (data-defined invalidation).** "ER after the latest material change" refers to an event defined by *comparing* two states: `amt(m) > 1.2 × amt(ER)`. Precedence is satisfied by any earlier ER, so TX-309 passes a trace check despite a +22.9% post-review increase. TX-306 would fail a naive "no update between ER and release" check despite an immaterial +4.5%. Correlation conditions across events, with cumulative baselines and sticky invalidation, are outside control-flow semantics.
4. **Post-hoc exemptions and evidence time.** The trace shows `Record_Exemption` *after* release for both TX-302 and TX-310. Order-based checks either reject both or accept both. The real distinction lies in evidence quality (QES at 09:05 versus a certificate created at 10:30) and in the gap between record time, effective time and evidence time, none of which exist as trace positions. Conversely, a backdated record inserted before release would pass a control-flow check.
5. **Missing data and three-valued outcomes.** A trace either fits or does not fit. TX-305's unknown amount has to become a pass or a fail, which either silently defaults to low risk (breaching R6) or invents a violation. INDETERMINATE needs Kleene or partial-information semantics.
6. **Same-timestamp ordering.** TX-311's ER and jurisdiction update share 16:20. Discovery and conformance tools order events by timestamp and then by an arbitrary internal index. If rows are shuffled, reloaded, or merged from two systems, the order flips. Any reading that makes ordering decisive (the sticky reading in §4) then yields a different verdict. Tie-breakers must be explicit data (event_index, sequence numbers), and the verdict's sensitivity to them must be tested.
7. **Label semantics versus content.** `Compliance_Approve` in TX-307 satisfies a precedence constraint by label but approved a standard packet. `Standard_Review` versus `Enhanced_Review` is likewise a matter of content. Control-flow cannot check *what* an activity covered (packet ID, reviewed state).
8. **External, cross-case events.** Sanctions-list updates are global objects, not case events. R3 is a join of the transaction's current jurisdiction with list events in a time window. It is object-centric, not single-case control-flow. Naively forward-filling the list event's `jurisdiction` cell would even corrupt case state.
9. **Aggregated fitness hides severity.** Deviation counts or fitness (for example, 0.5 for both TX-302 and TX-309) make no distinction between a sanctions breach, a stale review, and a harmless redundancy. Conformance must yield rule-level verdicts with severity.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payload.** Every `Release_Funds` should carry a hashed, write-once snapshot of amount, currency, FX rate, jurisdiction, customer_type, risk_level, the IDs of the reviews, approvals and screens relied on, the exemption IDs invoked, the sanctions-list version, and the policy or rule version evaluated. This would decide TX-305 immediately.
2. **Reviewed-state snapshots.** Every `Standard_Review`/`Enhanced_Review` should record review type, packet ID, lifecycle (start and complete), and the attribute values reviewed. A review without an amount should not be completable for an amount-dependent obligation. `Compliance_Approve` should reference the ER ID and packet type it approves.
3. **Bitemporal attribute changes with provenance.** Record each change as its own event carrying the old and new values, valid (effective) time, transaction (record) time, actor, source system, reason code, and approver. Changes that de-scope an obligation after review, like TX-311's jurisdiction change to DE, should require four-eyes approval. Use an explicit status such as `amount_status=UNAVAILABLE` rather than a blank.
4. **Exemption evidence model.** The register should hold approver identity and role, a trusted-timestamp-authority signature time, the signing certificate's serial number and validity start, a document hash, effective_from and expires, record time, and a structured scope (jurisdiction, customer type, amount cap, currency, waived rule IDs). It should also link to an incident ticket when record time lags approval, as with the EX-77 outage. Reject any effective_from earlier than the proven approval, and flag any displayed approval time that precedes certificate validity, as with EX-88.
5. **Stable event ordering.** Add a monotonic per-case sequence number, plus a global ingestion sequence or Lamport clock for cross-case and external events. Use sub-second timestamps, and keep source-system and ingestion times separate. Checks should fail rather than guess when the order is not total.
6. **Sanctions-list events as first-class objects.** Record list version, jurisdiction or entity added, publication time and effective time. Each `Sanctions_Screen` should record the list version it used. A release gate should compare the current list version with the one last screened and force a rescreen, which would have prevented TX-304.
7. **Rule versioning.** Log the policy version, thresholds (100k, 20%), and the materiality definition in force at each trigger, so that results can be reproduced after policy changes.
8. **Preventive gates, not just detective checks.**
   - Block release when a trigger attribute is unknown (TX-305).
   - Automatically require a new ER after a >20% cumulative increase since the last review (TX-301, TX-309).
   - Require an ER and a linked CA whenever risk becomes HIGH or the customer becomes PEP (TX-303, TX-307).
   - Allow an exemption to be invoked only if it is in the register with verified signature time ≤ now. During outages, use a documented fallback that yields a trusted timestamp (the EX-77 pattern, not the EX-88 pattern).
9. **Continuous checking.** Run the event-time state reconstruction and the rule predicates from §5 as a streaming monitor. Emit INDETERMINATE and REVIEW_REQUIRED cases to a human queue with the decisive evidence attached, and record the resolution and its evidence as new events.
