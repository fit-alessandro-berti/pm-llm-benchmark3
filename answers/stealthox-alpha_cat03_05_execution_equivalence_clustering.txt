## 1. Equivalence design space

Throughout, an *execution* is the set of events in which the lead `Order` object participates, plus the induced object graph (E2O incidence, O2O/qualified relations). Abbreviations: CO=Create Order, AI=Add Item, PP=Pack Package, DI=Dispatch, IV=Issue Invoice, RP=Record Payment, RI=Return Item, IR=Inspect Return.

**R1 — Activity-sequence equivalence (act).**
*Definition:* Map each execution to the ordered label trace of lead-participating events in timestamp order; E act F iff traces are equal.
*Preserves:* activity labels, repetition, linear order.
*Discards:* all object types, identifiers, multiplicities, externality, qualifiers, E2O incidence beyond lead membership.
*Properties:* equality of sequences  reflexive, symmetric, transitive.
*Concurrency:* relies on the given total order; a stable variant compares multisets of labels per timestamp bucket, making it insensitive to tie-breaking within a bucket.

**R2 — Typed structural equivalence (iso).**
*Definition:* Build a typed bipartite graph: event nodes labeled by activity; object nodes labeled by (type, external-flag); edges for E2O incidence; qualified relations as labeled edges. Replace local identifiers by fresh variables. E iso F iff an isomorphism exists that preserves labels, types, external flags, incidence, and qualified-relation labels (optionally also the temporal order of event nodes).
*Preserves:* structure, type multiplicities, externality, qualifiers, repeated events as distinct nodes.
*Discards:* concrete identifiers, timestamps (unless order edges are added), attribute values.
*Properties:* graph isomorphism is reflexive, symmetric, transitive.
*Concurrency:* default isomorphism ignores time entirely; the order-preserving variant treats simultaneous events as interchangeable siblings.

**R3 — Business-semantic equivalence (sem) — preferred.**
*Definition:* Equality of a semantic feature vector (Section 2): activity multiset; per-event (type, externality) participation profiles; distributions such as items-per-pack, packages-per-dispatch, payments-per-invoice; external-participation pattern; qualified-relation label set; lifecycle-motif flags (return loop, inspection, dispatch-touches-item).
*Preserves:* decision-relevant aggregates and motifs.
*Discards:* exact interleaving of independent phases, identifiers, timestamps, attribute values (unless promoted to features).
*Properties:* equality of vectors  reflexive, symmetric, transitive.
*Concurrency:* inherently order-insensitive; simultaneous events contribute identically to counts and profiles.

**R4 — Typed directly-follows equivalence (df), auxiliary.**
*Definition:* Sequence over lead events of pairs (activity, multiset of participating (type, external-flag)); equality elementwise. A cheap approximation of R2 that keeps per-event type multiplicities but not global graph structure. It is an equivalence (sequence equality) and coincides with R2 on this dataset, though in general iso is strictly finer. Concurrency: same bucket-multiset relaxation as R1.

## 2. Canonical signatures

Signature scheme for **R3**, invariant to local identifier renaming, deterministic (all sets sorted, counters frozen):

```python
from collections import Counter

def semantic_signature(ex, lead="Order"):
    evs = ex.events                                  # chronological
    acts = tuple(sorted(Counter(e.activity for e in evs).items()))

    def loc(e, t):   return [i for i in e.ids_of(t) if not i.startswith("EXT")]
    def ext_t(e):    return {t for t, ids in e.participants()
                               if any(i.startswith("EXT") for i in ids)}
    def touches(e, x): return x in e.ids()

    pack_sizes = tuple(sorted(len(loc(e, "Item"))
                              for e in evs if e.activity == "PP"))
    disp_loads = tuple(sorted(len(loc(e, "Package"))
                              for e in evs if e.activity == "DI"))
    invoices   = [i for e in evs if e.activity == "IV" for i in e.ids_of("Invoice")]
    pay_per_inv = tuple(sorted(
        sum(1 for e in evs if e.activity == "RP" and any(touches(e, v) for v in invoices)
            and touches(e, v)) for v in invoices))

    ext_pattern = tuple(sorted((e.activity, t) for e in evs for t in ext_t(e)))
    qualifiers  = tuple(sorted({q for r in ex.relations if r.qualifier
                                  for q in [r.qualifier]}))       # any qualified edge
    motifs = tuple(sorted(m for m, f in {
        "return_loop":        any(e.activity == "RI" for e in evs),
        "inspection":         any(e.activity == "IR" for e in evs),
        "dispatch_touches_item": any(e.activity == "DI" and loc(e, "Item")
                                     for e in evs)}.items() if f))
    return (acts, pack_sizes, disp_loads, pay_per_inv,
            ext_pattern, qualifiers, motifs)

def cluster_executions(execs):                       # reproducible IDs
    seen, out = {}, []
    for ex in execs:
        s = semantic_signature(ex)
        out.append((ex.name, seen.setdefault(s, f"S{len(seen)+1}")))
    return out
```

Deliberate abstractions: identifiers are erased (only the `EXT` prefix survives as a flag); timestamps are discarded; only *distributional* structure (sizes, loads, payments-per-invoice) is kept; qualifiers are kept as an unordered set. Ordering inside independent phases is intentionally ignored; the activity multiset still pins the phase inventory.

## 4. Cluster interpretations

**S1 — Clean single-flow (X1, X2).** One package, one delivery, one invoice, one payment; no external entanglement. Low risk; benchmark segment for cycle-time and margin. Flattening per order represents it perfectly. Stable under any reasonable data repair; only exotic identifier-semantics assumptions would break it.

**S2 — Consolidated multi-pack (X3).** Fulfillment split at packing but consolidated at transport. Opportunity: freight-cost optimization; risk: partial pack delays hold the joint dispatch. Order-flattening is fine; package-flattening duplicates the Dispatch event. Stable: pack grouping is explicit in E2O.

**S3 — Phased shipment with partial settlement (X4).** Ship-as-ready with installment billing. Risks: dunning complexity, revenue-recognition timing; opportunity: earlier cash inflow. Invoice-flattening collapses the two payments and destroys partiality; order-flattening shows interleaving but loses paymentinvoice allocation in a flat activity log. Stability is medium-high: even without qualifiers, two RP events signal it, but "partial vs. duplicate payment" then becomes ambiguous.

**S4 — Logistics-shared execution (X5).** Physical consolidation across orders (multi-order picking). Opportunities: cost savings; risks: mis-shipment attribution, one order's delay blocking another, capacity accounting double-count. Any single-order flattening either drops EXT-OA's contribution or duplicates events across two cases; a package-centered case notion is required. Stability depends entirely on `EXT` flag hygiene: misflagged externality silently merges this into S1/S2.

**S5 — Finance-shared execution (X6).** Consolidated invoicing/payment across orders. Major risk: revenue cannot be attributed to O6 from this log alone (M61 settles V61 with no order-level allocation) — a compliance and margin-analysis hazard. Order-flattening double-counts invoice value; correct representation needs allocation keys. Stability: fragile to allocation-repair choices (adding allocation events would change the signature), robust to identifier renaming.

**S6 — Substitution at dispatch (X7).** An item was removed before shipping; the customer receives less than invoiced-for unless downstream compensation exists. Risks: warranty claims, fraud, silent short-shipping. Pure activity flattening shows a normal order; only E2O incidence at Dispatch plus the qualifier reveal it. Stability is conditional: strip the qualifier *and* the DispatchItem edge and it collapses into S1 — the most dangerous silent merge in the corpus.

**S7 — Return-and-repack loop (X8).** Reverse logistics with inspection and re-dispatch. Risks: quality signals, restocking cost; opportunities: recovery rate tracking. Order-flattening renders it indistinguishable from S3-style splitting (two packs, two dispatches); the return semantics live only in activity labels and the `replaces` qualifier. Highly stable: explicit events carry the motif.

## 5. Borderline cases

**X1 vs X2.** Equal under all four relations. A definition could disagree only by treating identifier order as meaningful (e.g., ids encoding catalog priority); per the task constraints, local ids are declared non-semantic. If the two AI events shared a timestamp, the bucketed variant of R1 still yields equality.

**X1 vs X5.** act declares them equal; iso/sem do not. The disagreement is between a *local-pipeline view* (project out foreign participants: O5's own pipeline looks baseline) and a *whole-execution accountability view* (shared capacity must be visible). Both are defensible; the choice should follow the question — internal SLA analysis favors merging, cost/revenue attribution favors splitting.

**X1 vs X6.** Analogous on the financial side, with a sharper edge: even a payment-allocation-aware semantics cannot attribute M61 to O6. A definition requiring *attributable* settlement splits X6 from X1; one requiring only "some invoice covering the order was settled" merges them. Data-repair policy (introducing allocations) would flip the answer.

**X1 vs X7.** act equal. An O2O-topology-only structural definition (ignoring E2O detail at Dispatch) also merges them; R2 with full E2O and R3 with the substitution motif split them. Merging is defensible if qualifiers are known to be noisy operational annotations; splitting is mandatory for warranty/fraud monitoring. This is the clearest case where "same labels, different facts."

**X3 vs X4.** Both are multi-package. A *package-granularity* semantics ("more than one pack  split shipment") merges them; a *cash-cycle* semantics separates them (one settlement vs. partial payments). Under a partial-order reading, X3 is two concurrent packs feeding one dispatch, X4 is two independent packdispatch chains — a concurrency-tolerant definition emphasizes X4's independence, another source of principled disagreement.

**X4 vs X8.** Identical shipment counts (2 packs, 2 dispatches). A logistics-load equivalence merges them; a lifecycle-motif equivalence separates them (reverse loop, inspection, `replaces` vs. installments). Even "number of outbound dispatches" counts both equally — right for load KPIs, wrong for quality KPIs, since X8's second dispatch is re-fulfillment of a returned item.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel(ocel)` assigns each object an integer cluster such that objects in the same cluster have *exactly equivalent* event fingerprints: essentially the multiset of (activity, co-involved object identifiers) over the object's related events, as exposed in the returned DataFrame (`ocel:oid`, `ocel:type`, cluster column). Because raw identifiers like `I11` vs `I21` enter the fingerprint, two structurally identical orders almost never match — exact clusters degenerate to near-singletons. Remedy: canonicalize identifiers to (type, external-flag, rank-of-first-appearance) and re-key clusters by the canonical signature, merging pm4py clusters that share one. Exact equivalence remains preferable for identifier-level auditing, duplicate/alias detection, and ETL regression tests. Regarding scale: fingerprints grow with event degree; a hub event touching many objects glues large populations into one giant exact cluster or exhausts memory, and any `max_objs`-style subsampling biases which equivalences are discoverable — filter to the lead type and cap degrees first.

```python
import pm4py, pandas as pd
from collections import Counter

LEAD = "Order"

def canonical_fingerprint(rel: pd.DataFrame, oid) -> tuple:
    g = rel[rel["ocel:oid"] == oid]
    fp, rank = [], {}
    for eid, ev in g.groupby("ocel:eid", sort=True):
        ev = ev.sort_values("ocel:timestamp") if "ocel:timestamp" in ev else ev
        prof = Counter()
        for _, r in ev.iterrows():
            k = ((r["ocel:type"], str(r["ocel:oid"]).startswith("EXT")))
            rank.setdefault(k, len(rank))                 # rename-invariant ranks
            prof[(k, rank[k])] += 1
        fp.append((ev["ocel:activity"].iloc[0], tuple(sorted(prof.elements()))))
    return tuple(fp)

def semantic_clusters(ocel) -> pd.DataFrame:
    exact = pm4py.cluster_equivalent_ocel(ocel)           # exact, id-sensitive
    cl_col = next(c for c in exact.columns if "cluster" in c.lower())
    rel, rows, sig2id = ocel.relations, [], {}
    leads = exact.loc[exact["ocel:type"] == LEAD]
    for oid, ex_cl in zip(leads["ocel:oid"], leads[cl_col]):
        s = canonical_fingerprint(rel, oid)               # custom canonicalization
        cid = sig2id.setdefault(s, len(sig2id))           # merge across exact clusters
        rows.append({"ocel:oid": oid, "exact_cluster": ex_cl, "semantic_cluster": cid})
    return pd.DataFrame(rows)
```

## 7. Robustness analysis

- **Ignore O2O qualifiers:** X4 stays in S3 via payment multiplicity but loses the partial/duplicate nuance; X7 keeps S6 only through the `dispatch_touches_item` motif — a qualifier-only definition would drop it into S1 (the dangerous merge). S7 is unaffected (`replaces` is redundant with explicit events).
- **Ignore external objects:** deleting EXT participants turns X5 into exactly X1's profile and X6 likewise  S4, S5 dissolve and sharing risk becomes invisible. Merely *unflagging* (keeping the extra order/item nodes) keeps them structurally distinct — the perturbation's effect hinges on deletion vs. unflagging.
- **Collapse repeated same-label events:** multiplicity is the sole separator for X3 and X4, so both fold into an enlarged S1; X8 survives (new activity labels). Activity clusters A, B, C merge.
- **Partial order for Pack/Dispatch:** X3's two packs become concurrent; X4 becomes two independent chains. Clusters are unchanged (counts and fan-in/fan-out still differ), but the PO view removes spurious splits from timestamp tie-breaking and sharpens the X3-vs-X4 contrast as joint-vs-independent dispatch.
- **Payments as amounts (optional):** aggregating M41+M42 into one logical settlement with an amount attribute moves X4 toward a "split shipment, single settlement" profile adjacent to S2; feasible only if amounts exist, otherwise the structural two-payment signal must be kept.

## 8. Limitations and recommendation

- **Compliance monitoring:** qualified typed-structural equivalence (R2 with qualifiers). Shared invoices, substitutions, and partial settlements are exactly the facts an auditor must not miss; false merges are costlier than false splits.
- **Operational segmentation:** the preferred semantic equivalence (R3). Motifs map directly to playbooks (expedite consolidated freight, monitor allocation of shared invoices, flag short-ships).
- **Root-cause analysis:** coarse-to-fine — stratify by activity-sequence or outcome first, then refine within strata using semantic features; starting fine drowns analysts in identifier noise, starting coarse hides the mechanism.
- **Descriptive reporting:** activity-sequence equivalence; stable, explainable, robust to data-quality drift.

No single notion suffices because the relations trade off sensitivity to *irrelevant* variation (identifiers, tie-breaking) against sensitivity to *decision-relevant* variation (sharing, qualifiers, multiplicity), and the four purposes weight these errors differently: compliance penalizes merges, reporting penalizes fragmentation, operations needs stable actionable groups, and diagnosis needs a controllable zoom. The recommended practice is the layered scheme above with R3 as the default lens and explicit, documented escalation to R2 whenever money, liability, or provenance is at stake.
