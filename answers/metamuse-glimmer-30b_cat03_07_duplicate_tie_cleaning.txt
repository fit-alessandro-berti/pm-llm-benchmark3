## 1. Duplicate-handling decision tree

1. Exact technical duplicate?
   * Same `source`, `source_event_key`, `source_seq` and identical payload hash -> drop duplicate technical row, keep first. Provenance retained in ingestion log.

2. Same physical event observed by multiple systems?
   * Reconciliation report or business key match: same activity, same timestamp window, same object set, payloads differ only by enrichment.
   * Terminal: merge attributes and relations into canonical event, retain both source identifiers. Confidence high if external report exists.

3. Summary event derived from a detailed event?
   * Same order/package/invoice objects, summary activity harmonized to same label, ERP summary timestamp >= detail timestamp, no fine-grained objects.
   * Terminal: retain both with refined labels/qualifiers, e.g. `Pack Package [WMS detail]` vs `Pack Package [ERP summary]`. Do not drop.

4. Harmonization collision between semantically distinct source activities?
   * Same harmonized label, same objects, different source semantics, e.g. WMS release vs carrier accept.
   * Terminal: retain both with refined labels or qualifiers. Do not merge.

5. Concurrent same-label events involving different objects?
   * Same activity and timestamp, object sets differ in at least one identifying object, e.g. different Item or Payment.
   * Terminal: retain both unchanged. Object-level concurrency is legitimate.

6. Unresolved candidate?
   * Overlap on objects and time but no external evidence.
   * Terminal: quarantine for review, retain both unchanged, flag confidence low.

All decisions preserve `original_timestamp`, `original_activity`, `source`, `source_event_key` and store them in provenance.

## 3. Timestamp-tie ordering rules

Priority, semantic first, deterministic second:

1. Domain constraints: known business precedence, e.g. `Authorize Payment` before `Capture Payment` for same Payment, carrier handover after carrier accept.
2. Lifecycle constraints on shared objects: pick before pack before dispatch for same Package; issue invoice before payment capture for same Invoice.
3. Within-source sequence: `source_seq` is authoritative inside one source. Used only when timestamps tie and no domain constraint.
4. Source-specific semantics: WMS release precedes carrier accept for same Package/Delivery even with equal timestamp.
5. Ingestion time: weak tie-breaker only when 1-4 are silent. Never primary business order.
6. Stable fallback: lexicographic `eid`.

Semantic rules 1-4 encode real business knowledge. Rules 5-6 are merely deterministic.

Adding microseconds before semantic ordering encodes a false story: it manufactures a duration where none is known, creates artificial performance metrics, and makes a total order look factual. The original timestamp must stay unchanged; any synthetic offset must be stored in a separate `order_key` column.

Intended orders

* e03–e07 at 10:00: picks before packs. Merged e03/e04 = Pick I1. e05 = Pick I2 concurrent. Admissible total order: e03/e04, e05, e06, e07. Picks may be permuted. e06 before e07 by message causality.
* e08–e10 at 10:15: e08 `Dispatch Package [WMS release]` -> e09 `Dispatch Package [CARRIER accept]` -> e10 `Handover to Carrier`. Domain constraint forces e09 before e10, source semantics forces e08 before e09.
* e11–e16 at 12:00 after merge: canonical invoice e11/e16. e12 Authorize Payment M1 before e13 Capture Payment M1. e14 Capture Payment M2 concurrent with e13. e15 Payment Summary after both captures. Admissible order: invoice, e12, e13, e14, e15 with e13 before e15 and e14 before e15.

    ev = ev[ev['eid']!=drop_eid]
    ev.loc[len(ev)] = merged_attrs
    # update E2O relations union
    # ... simplified
    ocel.events = ev

## 9. Failure modes and safeguards

* Collapsing distinct partial payments because common order/invoice object masks payment object difference.
* Converting abstraction-level updates into false rework by dropping summary events.
* Ordering by ingestion time as primary business order, reversing real causality.
* Treating shared objects as proof of duplication without checking object-set equality.
* Unioning incompatible E2O relations when merging events with different object cardinalities.
* Changing durations through synthetic microseconds, creating false performance KPIs.
* Losing source-authoritative attributes during union without conflict logging.
* Applying duplicate functions to whole OCEL without inspecting candidate groups, leading to mass over-merging.

Safeguards: verified-pair whitelist, object-set exact match for merges, preserve original columns, quarantine unresolved candidates, and always evaluate DFG sensitivity before publishing.
