# 1. Executive Verdict
It is a workflow net: one source, one sink, and every place and transition lies on a source-to-sink path. It should not be expected to be sound. The split correctly creates parallel analysis and review tokens, and the standard-review path correctly synchronizes both at `t_join_normal`; the waiver path does not. `t_join_waived` has only `p_waived` as input, so it never requires `p_analysis_done`. Consequently, authorization can fire before analysis and leave the analysis token unconsumed. The business consequence is a waived case can be authorized without mandatory analysis, and the case cannot then reach the exact final marking `fm`, despite a token reaching `sink`.

# 2. Structural Diagnosis
| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `im = {source=1}`, `fm = {sink=1}` | Start with one case token and finish with exactly one sink token | Structurally correct workflow-net markings | A token in `sink` is not sufficient for proper completion if other tokens remain elsewhere |
| `t_register` and `p_ready` | Register the case and make it ready for parallel work | Ordinary sequential token movement | No material defect by itself |
| `t_split` | Silent AND-split into analysis and review branches | One token in `p_ready` produces one token in each of `p_analysis` and `p_review` | Correctly creates two obligations that must later be synchronized |
| Analysis branch: `p_analysis -> t_analyze -> p_analysis_done` | Mandatory analysis running in parallel with review | The token is independently enabled and can be delayed; its completion token is consumed only by `t_join_normal` | Analysis can remain pending while the waiver branch advances, and `p_analysis_done` can become stranded |
| Review alternatives: `t_standard_review` and `t_waive_review` | Exclusive choice between standard review and waiver | Both consume the single `p_review` token and produce mutually exclusive outcome tokens in `p_review_done` or `p_waived` | Locally this is a proper choice; the defect arises because the two outcomes enter different and unequal synchronizers |
| `t_join_normal` | AND-join analysis completion with standard-review completion | Requires both `p_analysis_done` and `p_review_done` before producing `p_decision` | Correct on the standard-review route |
| `t_join_waived` | Intended AND-join analysis completion with waiver | Has only `p_waived` as input and produces `p_decision` without requiring `p_analysis_done` | It is effectively a pass-through, not a synchronization; this permits authorization before analysis and improper completion |
| `t_authorize` and `sink` | Final authorization after analysis and a review outcome | Enabled by any token in `p_decision`, regardless of which join produced it | Authorization can be reached through the unsynchronized waiver route |
| Source-to-sink connectivity | Workflow-net structural condition | There is one source place, one sink place, and every place and transition lies on at least one directed source-to-sink path | The workflow-net check can pass even though behavioral soundness fails; path existence does not show that parallel obligations are synchronized |

# 3. Marking-Based Counterexample
The following legal firing sequence follows the waiver route and shows that `t_authorize` can fire before `t_analyze`:

`t_register, t_split, t_waive_review, t_join_waived, t_authorize, t_analyze`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — | `{source=1}` | `t_register` | Initial marking `im` |
| 1 | `t_register` | `{p_ready=1}` | `t_split` | Case is ready for the parallel split |
| 2 | `t_split` | `{p_analysis=1, p_review=1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | One token is created in each parallel branch |
| 3 | `t_waive_review` | `{p_analysis=1, p_waived=1}` | `t_analyze`, `t_join_waived` | The review token is consumed by the waiver, but the analysis token remains pending |
| 4 | `t_join_waived` | `{p_analysis=1, p_decision=1}` | `t_analyze`, `t_authorize` | `t_authorize` is enabled although `p_analysis_done=0`; this is the bypass |
| 5 | `t_authorize` | `{p_analysis=1, sink=1}` | `t_analyze` | A token exists in `sink`, but the marking is not the exact final marking `fm={sink=1}` |
| 6 | `t_analyze` | `{p_analysis_done=1, sink=1}` | none | The leftover analysis-completion token cannot be consumed |

` t_authorize` can also occur after `t_analyze`. From step 4, firing `t_analyze` before `t_authorize` gives `{p_analysis_done=1, p_decision=1}`; then `t_authorize` gives `{p_analysis_done=1, sink=1}`. Thus neither ordering repairs the defect.

The leftover token cannot be consumed because `p_analysis_done` has only one outgoing arc, to `t_join_normal`. That transition also requires `p_review_done`. The latter can be produced only by `t_standard_review`, which requires `p_review`; the unique `p_review` token was already consumed by `t_waive_review`, and no arc recreates `p_review`. Therefore `t_join_normal` is permanently disabled from the defective marking. Since `sink` has no outgoing arc, the marking cannot evolve to exactly `fm`.

**Second counterexample.** Even if analysis is completed before authorization, the waiver route still strands the analysis-completion token:

`t_register, t_split, t_waive_review, t_analyze, t_join_waived, t_authorize`

This reaches `{p_analysis_done=1, sink=1}`, which is not `fm` and has no enabled transition. Hence the problem is not merely that users might authorize too early; the waiver synchronization itself never consumes the analysis result.

# 4. Minimal-Repair Alternatives
**Edit-cost model.** Each added or removed arc, place, transition, or label change costs 1. Reusing an existing element costs 0. This equal-weight model measures structural change, not modeling elegance or business risk.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| **Repair B — proper two-input waiver join** | Add one arc: `p_analysis_done -> t_join_waived`. No other changes. | 1 | Mandatory analysis, exclusive review choice, all places, transitions, labels, and the distinction between `p_waived` and `p_review_done` | Waiver now waits for both analysis and waiver before `p_decision`; standard route is unchanged | `p_analysis_done` has two competing consumers, and the net retains two silent joins producing `p_decision`; this relies on the exclusivity of the single review token |
| **Repair A — single merged outcome join** | Rewire waiver output: delete `t_waive_review -> p_waived`, add `t_waive_review -> p_review_done`; delete `p_waived`, `t_join_waived`, `p_waived -> t_join_waived`, and `t_join_waived -> p_decision`. | 6 | Mandatory analysis, exclusive review choice, distinct visible transition labels, and one AND-join at `t_join_normal` | Visible successful behavior is equivalent to Repair B, but internally both review outcomes use `p_review_done` | Greater structural churn; `p_review_done` conflates standard completion and waiver at place level, and deleting the waiver-specific place weakens state-based audit distinction |

**Minimality justification.** Repair B is uniquely minimal under the stated equal-weight model. Zero edits cannot be valid because the original counterexample remains legal. Therefore every valid structural repair costs at least 1, and Repair B attains that lower bound with exactly one added arc. Repair A costs 6 and is therefore not edit-minimal. There is no tie under the primary edit-count model. Repair A could become preferable under a secondary criterion that penalizes redundant silent joins or shared consumers, but that is a maintainability preference rather than a smaller edit.

# 6. Diagnostic and Reachability Code
This block assumes the original `net`, `im`, and `fm`, together with `repaired_net`, `repaired_im`, and `repaired_fm`, already exist.

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking


def nonzero(marking):
    return {
        place.name: tokens
        for place, tokens in marking.items()
        if tokens
    }


def fire_named_transition(net, marking, transition_name):
    transitions_by_name = {t.name: t for t in net.transitions}
    if transition_name not in transitions_by_name:
        raise ValueError(f"Unknown transition: {transition_name}")

    transition = transitions_by_name[transition_name]
    enabled = pm4py.get_enabled_transitions(net, marking)

    if transition not in enabled:
        enabled_names = sorted(t.name for t in enabled)
        raise RuntimeError(
            f"{transition_name} is not enabled from "
            f"{nonzero(marking)}; enabled={enabled_names}"
        )

    new_marking = Marking()
    for place, tokens in marking.items():
        if tokens:
            new_marking[place] = tokens

    for arc in net.arcs:
        weight = getattr(arc, "weight", 1)
        if arc.target == transition:
            remaining = new_marking.get(arc.source, 0) - weight
            if remaining > 0:
                new_marking[arc.source] = remaining
            elif arc.source in new_marking:
                del new_marking[arc.source]

    for arc in net.arcs:
        weight = getattr(arc, "weight", 1)
        if arc.source == transition:
            new_marking[arc.target] = (
                new_marking.get(arc.target, 0) + weight
            )

    print(f"{transition_name} -> {nonzero(new_marking)}")
    return new_marking


def replay(net, marking, transition_names):
    current = marking
    for transition_name in transition_names:
        current = fire_named_transition(net, current, transition_name)
    return current


print("ORIGINAL workflow-net check:")
print(pm4py.check_is_workflow_net(net))

print("ORIGINAL soundness check:")
print(pm4py.check_soundness(net, im, fm, print_diagnostics=True))

print(
    "ORIGINAL enabled transitions at im:",
    [t.name for t in pm4py.get_enabled_transitions(net, im)],
)

original_rg = pm4py.convert_to_reachability_graph(net, im, fm)
print("ORIGINAL reachability graph generated:", type(original_rg).__name__)

print("REPAIRED workflow-net check:")
print(pm4py.check_is_workflow_net(repaired_net))

print("REPAIRED soundness check:")
print(
    pm4py.check_soundness(
        repaired_net, repaired_im, repaired_fm, print_diagnostics=True
    )
)

print(
    "REPAIRED enabled transitions at repaired_im:",
    [t.name for t in pm4py.get_enabled_transitions(repaired_net, repaired_im)],
)

repaired_rg = pm4py.convert_to_reachability_graph(
    repaired_net, repaired_im, repaired_fm
)
print("REPAIRED reachability graph generated:", type(repaired_rg).__name__)

counterexample = [
    "t_register",
    "t_split",
    "t_waive_review",
    "t_join_waived",
    "t_authorize",
]

print("Replaying the defective waiver sequence on the ORIGINAL net:")
original_end = replay(net, im, counterexample)
print("Original end marking:", nonzero(original_end))
print("Original end equals fm:", nonzero(original_end) == nonzero(fm))
print(
    "Original firing can continue with:",
    [t.name for t in pm4py.get_enabled_transitions(net, original_end)],
)

print("Replaying the same sequence on the REPAIRED net:")
try:
    replay(repaired_net, repaired_im, counterexample)
    print("ERROR: repaired net unexpectedly allowed premature authorization")
except RuntimeError as exc:
    print("Repaired net correctly blocked premature authorization:", exc)

proper_waiver_sequence = [
    "t_register",
    "t_split",
    "t_waive_review",
    "t_analyze",
    "t_join_waived",
    "t_authorize",

print("Replaying a proper waiver sequence on the REPAIRED net:")
repaired_end = replay(repaired_net, repaired_im, proper_waiver_sequence)
print("Repaired end marking:", nonzero(repaired_end))
```

Expected qualitative difference: the original should pass the workflow-net check but fail soundness because of improper completion and failure to complete from markings containing a sink token plus a leftover analysis token. The repaired net should pass both checks. Its reachability graph should contain no dead marking combining `sink` with an unconsumed `p_analysis` or `p_analysis_done` token, and the replay helper should reject `t_authorize` on the waiver route until analysis has completed.

# 7. Repair Trade-Offs and Residual Risks
**Distinguishability of waiver and standard review.** In Repair B the visible labels `Perform Standard Review` and `Record Review Waiver` remain distinct, as do the outcome places `p_review_done` and `p_waived`. Event logs and current markings therefore still distinguish the selected outcome. Repair A would preserve the transition labels but merge the outcome place, making marking-only monitoring less informative.

**Silent transitions and duplicate behavior.** The repaired net still contains the silent split and two silent joins. In a correct execution, the split fires once and exactly one join fires once: the single `p_review` token produces exactly one review outcome, while analysis produces exactly one `p_analysis_done` token. Thus Repair B does not create duplicate authorization in the given net. Nevertheless, two silent transitions feeding `p_decision` can confuse future modelers, and silent behavior cannot be counted directly from visible event labels. If a third review outcome is later added, the modeler must either add another competing join or refactor to a merged outcome place.

**Soundness is not a business-rule proof.** Soundness concerns workflow completion properties; it does not by itself prove that the labels, task order, or mandatory-task policy are correct. For example, an alternative net could become sound by adding a cancellation transition that discards the analysis token, while still violating the mandatory-analysis rule. Conversely, the repaired net must still be checked against the intended trace language.

**Regression traces.** Positive traces, expressed by visible labels, should include `Register Case, Perform Analysis, Perform Standard Review, Authorize Case`, with analysis and standard review allowed in either order because they are parallel; and `Register Case, Perform Analysis, Record Review Waiver, Authorize Case`, again allowing analysis before or after the waiver declaration provided it occurs before authorization. Negative traces should include waiver without analysis, standard review without analysis, analysis without any review outcome, both review outcomes, and authorization before analysis. Token replay should reject negative traces as not properly completed.

**Detecting an accidental bypass.** Use three complementary controls: replay traces and reject any accepted trace lacking `Perform Analysis` before `Authorize Case`; query logs for authorizations without a preceding analysis event; and inspect reachable markings or model-change tests to confirm that no route produces `p_decision` without first consuming `p_analysis_done`. After every structural edit, rerun the counterexample replay and verify that `t_authorize` is not enabled merely because the waiver branch has completed.

# 8. Final Recommendation
Deploy Repair B. A single added arc, `p_analysis_done -> t_join_waived`, makes the waiver branch a genuine two-input synchronization while preserving every place, transition, label, and the distinct `p_waived`/`p_review_done` outcomes. It therefore has the smallest regression and rollback surface. On the waiver route, `t_join_waived` can then fire only after both `t_analyze` and `t_waive_review`; on the standard route, `t_join_normal` already imposes the same requirement. No visible labels change; the only ordering change is mandatory analysis before authorization on the waiver route.

Keep Repair A as fallback. It consolidates synchronization into `t_join_normal` and removes the redundant silent waiver join, which may suit a modeling standard that disallows one place feeding two competing joins. However, it deletes more elements and merges waiver into `p_review_done`, weakening place-level distinction. Promote A only if that governance concern outweighs B's one-arc minimality; do not deploy both. Gate deployment on workflow-net and soundness checks plus positive and negative case tests.
