## 1. Target definition

**The core problem.** "Default within 90 days" is only physically defined for a case that was *exposed to credit*, i.e. that reached `Account Activated`. A rejected, withdrawn, transferred or still-open application has no observed 90-day default state — not because the value is missing, but because the event that starts the risk clock never occurred. Treating those cases as `default_90d = 0` would not be imputation; it would be redefining the label into "activated AND defaulted", which conflates *approval propensity* with *credit risk* and produces a model that mostly predicts the bank's own historical policy.

**Primary formulation — activation-conditional default with right censoring (a two-stage, selection-aware target).**

- **Unit of analysis:** one credit application case (`case:concept:name`), taken once, at a fixed prefix-based prediction point. Not one row per prefix at scoring time; prefixes are used for training/evaluation replication but each case contributes at most one observation per prefix length k, and evaluation is aggregated per k.
- **Prediction time τ(c):** the timestamp of the k-th event of the case (primary k = 3, i.e. through the first `Credit Review`), with k = 2 and k = 5 as secondary operating points, plus an elapsed-time variant (§4). Every feature must be computable from information physically recorded at or before τ(c).
- **Horizon:** 90 calendar days after `Account Activated`, i.e. the risk clock starts at activation, not at τ(c). Formally the survival time is T = time from activation to first default event, and the binary target is 1{T ≤ 90d}.
- **Population:** all applications started in the observation window whose prefix of length k is fully observed at τ(c) and whose τ(c) precedes the as-of cutoff. Rejected/withdrawn/transferred/open cases are **in** the modelling population — they are not deleted; they enter as cases whose activation indicator A = 0 (no risk exposure), or as competing/censoring events, depending on the estimand below.
- **Estimand (primary):**

  Y(c) = 1{ activated within the application window } × 1{ default occurs within 90 days of activation }, and the quantity modelled is

  **P(default within 90d of activation | prefix_k, A = 1, policy regime R)** — the *risk of default among applications that this lender's policy actually activates*, estimated with explicit handling of (i) right censoring in the 90-day clock, (ii) label-delay maturity, and (iii) permanently missing outcome feeds.

  Concretely the model is a discrete-time / Cox-type survival model on activated cases, with the population-level early-warning score reported as the product decomposition

  score(c) = P̂(A = 1 | prefix_k) × P̂(T ≤ 90 | prefix_k, A = 1),

  where the first factor is an *activation-propensity* model estimable on all 48,000 applications and the second is the credit-risk model. The two factors are reported separately as well as multiplied, because they answer different business questions and because presenting only the product hides which factor drives a high score.

- **Why this is defensible.** The second factor is exactly the quantity the lender can act on with an activation policy in force: "given we would activate this application, how likely is early default?" It is estimable without counterfactual assumptions about rejected applicants, and it is the quantity that governs pricing, limit-setting and early collections triage. The first factor is fully observed for everyone and therefore leakage-free with respect to selection. The decomposition also makes the selection explicit rather than burying it in a mislabeled 0.

**Alternative target A — multi-state / competing-outcome model over all applications.** Model the application as a multi-state process with absorbing states {Rejected, Withdrawn, Transferred, Activated→Default, Activated→No-default-by-90d} and a transient "open" state, and estimate the *cumulative incidence function* of "activated-and-defaults-within-90d" among all applications started. This answers **"what fraction of incoming applications end up as an early default under current policy?"** — a portfolio/volume question, not a per-applicant risk question. It is honest (rejection is a competing event, not a non-default), and it needs no counterfactual assumption, but its output cannot be used to decide whether a *given* borderline application is risky, because a low cumulative incidence can mean "safe" or "would have been rejected anyway". Recommended as a secondary reported model, since it is the correct frame for the "predict default for every application" phrasing the lender used.

**Alternative target B — policy-specific counterfactual default ("would this applicant default if we activated them?").** This is what the lender probably *wants*, and it is the one requiring the strongest assumptions: no unmeasured confounding between the underwriter's decision and default given the prefix features (i.e. the analyst sees everything the underwriter saw), plus positivity (every prefix stratum has non-trivial activation probability). Neither holds here: underwriters use manual judgement and documents not captured in the event log, and the highest-risk prefix strata have activation probability near zero after the 1 July 2025 policy change. It is therefore reported only as a **clearly labelled sensitivity analysis** (IPW / doubly-robust reweighting to the all-applications population, with overlap diagnostics and trimming), never as the headline number.

**Alternative target C — time-to-default after activation with right censoring** is not really an alternative but the *implementation* of the primary target: modelling T directly rather than the binary 1{T ≤ 90} lets the 3,600 immature accounts and the recently-activated accounts contribute their observed exposure instead of being dropped, which materially reduces the maturity-induced selection.

## 2. Cohort construction

**As-of discipline.** Two clocks must be distinguished and both enforced:
- **Feature as-of time** = τ(c), the k-th event timestamp. Nothing recorded after τ(c) may enter X.
- **Label as-of time** = the analysis cutoff C (configurable). A case's outcome is usable only if `activation_time + 90d + feed_delay ≤ C`. Because the external feed arrives 7–35 days late, the *conservative* label-maturity cutoff is activation + 125 days; the *optimistic* one is activation + 97 days. Both are run.

Given extraction on 15 Feb 2026 and event window ending 31 Dec 2025, the conservative maturity boundary for activations is **13 Oct 2025**; activations after that date are treated as administratively censored even if a label happens to be present, because for them a present label is a *fast-feed* label and fast feeds are non-random (partner-originated accounts are slow/never).

**Inclusion.**
1. Case has an `Application Started` event with timestamp in [2024-01-01, 2025-12-31].
2. Case has at least k events observed at or before min(τ_max, C) — otherwise it cannot form a length-k prefix (see §4 for the short-case rule).
3. Case is not a known duplicate arising from the 15 Oct 2025 migration (deduplicated on case id + normalized activity + timestamp rounded to the second + resource).
4. Case is not a *downstream* re-entry of a transferred case under a new identifier where linkage is known — the linked pair is collapsed into a single case keyed by the original identifier.

**Exclusion (documented, not silent).**
- Cases whose entire trace lies before the observation window (left truncation) — none expected, but checked.
- Cases with non-monotone timestamps that cannot be repaired.
- For the *risk-model* stage only: cases with A = 0. These remain in the activation-propensity stage and in the multi-state model.

**Cohort-flow table (all 48,000 applications accounted for).**

| # | Stratum | n | Activation exposure | Label status for the 90d default target | Role in study |
|---|---|---|---|---|---|
| 0 | Applications started 2024-01-01 → 2025-12-31 | 48,000 | — | — | Full denominator |
| 1 | Activated, outcome matured and present in export | 21,600 | Yes | **Labeled**: 18,900 event-free, 2,700 default | Risk model training/eval; also A=1 in propensity model |
| 2 | Activated, 90d horizon or feed not yet matured | 3,600 | Yes | **Not yet mature / delayed label** — censored at min(C − activation, 90d) | Contributes exposure to survival model; A=1 in propensity model; NEVER a 0 |
| 3 | Rejected and closed | 9,100 | No | **Undefined under activation** (competing/terminal event) | Competing event in multi-state model; A=0 in propensity model; counterfactual only under Target B |
| 4 | Withdrawn by applicant | 5,700 | No | **Undefined** (competing event, applicant-driven → plausibly informative) | Same as above; separate competing cause |
| 5 | Transferred to partner/specialist | 2,900 | No under our book | **Undefined + selectively unobservable**; ~1,740 (60%) linkable, ~1,160 opaque | Competing event; linked subset used for sensitivity on informative transfer |
| 6 | Still open at extraction | 5,100 | Unknown | **Administratively right censored in the application process** | Included in multi-state model with censored process state; excluded from risk model |
| — | Total | **48,000** | | | |

Derived totals: activated = 21,600 + 3,600 = **25,200** (52.5% of applications); non-activated terminal = 17,700; process-censored = 5,100. Naive activation rate among *resolved* applications = 25,200 / 42,900 = 58.7%; the naive labeled-export-only rate of 2,700/21,600 = 12.5% default is therefore **a default rate among activated-and-fast-feed accounts**, not among applications, and not even among activated accounts.

A second flow table is produced per prefix length k and per policy regime (pre/post 2025-07-01, pre/post 2025-10-15), since a case can be present at k = 2 and absent at k = 5.

## 3. Censoring and missing-label strategy

**Mechanism taxonomy.** These are genuinely different and must not be collapsed into one "missing label" bucket.

1. **Ordinary right censoring (administrative).** An activated account whose 90-day window has not closed by C. Non-informative *given* activation date; handled exactly by survival methods. Affects part of stratum 2 and any activation after 2025-10-13 under the conservative rule. Assumption (independent censoring given covariates) is **partially testable** — we can check that censored and uncensored accounts have similar covariate distributions after conditioning on activation date, but not that hazards agree post-censoring.

2. **Delayed labels (reporting lag, 7–35 days).** A label is *eventually* observed but not yet. If the analyst simply uses "label present at extraction", the observed cohort is biased toward fast-reporting segments. Handled by (a) enforcing the maturity cutoff rather than the label-presence indicator, and (b) modelling the lag distribution from `label_available_at` − (activation + 90d) so the maturity rule can be set at a chosen quantile (e.g. 95th) rather than the max. **Testable** on matured history.

3. **Selection through activation.** Only activated cases have a defined outcome, and activation is a *decision based on risk*. This is the dominant bias. It is **not** censoring: for a rejected applicant there is no latent-but-hidden 90-day default event on our book; the quantity would be counterfactual. Handled by conditioning (primary target), by competing-risks cumulative incidence (secondary), and only by IPW/doubly-robust extrapolation in the labelled counterfactual sensitivity. The no-unmeasured-confounding assumption behind that extrapolation is **fundamentally untestable** from these data; positivity/overlap *is* testable and is expected to fail in the tails.

4. **Transfer as competing event vs. missing follow-up.** Two readings, and the data cannot distinguish them:
   - *Competing event reading (primary):* a transferred application never becomes an account on our book, so it terminates the application process without activation. Cumulative incidence treats it as a competing cause. This is the operationally correct reading for our own book.
   - *Missing-follow-up reading:* the customer really did get credit, just elsewhere, so the "true" credit outcome exists but is off-book. Only ~60% linkable, and linkage availability is very likely correlated with partner identity and hence with risk. Handled as a **sensitivity analysis**: (i) linked-only analysis, (ii) IPW on linkage probability estimated from `source_system`, region, channel, and amount, (iii) tipping-point bounds where the unlinked 1,160 transfers are assigned default rates from 0.5× to 3× the observed linked rate.
   The MAR-given-observed assumption behind (ii) is **untestable**; the bounds in (iii) are assumption-free but wide, and their width is itself a reportable result.

5. **Permanently missing outcome feeds** (elevated for partner-originated activated accounts). This is *not* censoring — waiting longer never resolves it, so survival methods that treat it as censoring at last contact will be biased if missingness correlates with default. Handled by: an explicit `feed_ever_expected` flag derived from `source_system`; a missingness model P(feed observed | prefix, source_system, activation date); primary analysis using inverse-probability-of-observation weights within the activated cohort; and a **manski-style bounding** sensitivity where permanently-unfed accounts are set all-default then all-non-default to bracket the achievable estimate. If the bracket is wider than the decision-relevant difference, that is the honest finding.

**Primary analysis strategy.** Discrete-time survival (complementary log-log or discrete hazard on daily/weekly intervals from activation to day 90) fitted on the activated cohort, with:
- administrative censoring at min(90d, C − activation − lag_q95);
- inverse-probability-of-observation weights for permanently-missing feeds;
- policy-regime indicator and regime-specific calibration;
- a separate activation-propensity model on all 48,000 for the decomposition in §1.

**Sensitivity analyses (at minimum).**
- S1: competing-risk cumulative incidence (Fine–Gray or Aalen–Johansen) over all 48,000 with rejection/withdrawal/transfer as competing causes — checks whether conclusions about *which prefixes are risky* survive reframing.
- S2: transfer linkage sensitivity (linked-only / IPW / tipping-point bounds).
- S3: label-maturity sensitivity (optimistic 97d vs conservative 125d cutoff; refit and compare AUC/calibration).
- S4: counterfactual Target B via IPW to the all-application population, reported with overlap diagnostics, trimming at propensity ∈ [0.05, 0.95], and an explicit "requires untestable exchangeability" banner.
- S5: pre-/post-2025-07-01 refit to quantify policy-change-induced instability.

**Assumption ledger.** Testable: label-lag distribution, duplicate/rename repair correctness, overlap/positivity, covariate balance of censored vs uncensored, temporal stability of feature distributions. Partially testable: independence of censoring given covariates (checkable on observed region only); MAR of the outcome feed (checkable only via proxies such as whether missingness predicts pre-activation risk score). Fundamentally untestable: no unmeasured confounding in the underwriting decision; the default behaviour of rejected applicants; the on-book default behaviour of unlinked transfers.

## 4. Prefix extraction

**Rule zero: as-of reconstruction.** Sort events by `time:timestamp` within case (stable tiebreak on an ingestion sequence when timestamps tie to the second — common after the migration). For prefix length k, τ(c) = timestamp of event k. Build the feature row from events 1..k only, and from *attribute values as recorded at or before τ(c)* — the column-level rule in §6 matters as much as the row-level rule, because a case-level column such as `final_limit` is repeated on every row including early ones in many warehouse exports. The pipeline therefore *nulls out* post-prefix-only columns on the retained prefix rows rather than trusting that early rows are clean.

**Fixed event-count prefixes.** k ∈ {2, 3, 5}. k = 3 (Started → KYC → first Credit Review) is the primary operating point: it is the earliest point at which a credit-relevant decision context exists and it is reached by essentially every case. Larger k buys information but shrinks and biases the population (only cases with document loops or slow processing reach k = 8), so per-k cohorts and per-k performance are always reported separately; performance is never averaged across k.

**Elapsed-time prefixes.** Complementary and, for an "early warning" product, arguably more faithful to deployment: τ(c) = case start + Δ for Δ ∈ {24h, 72h, 7d}, using all events with timestamp ≤ τ(c). This makes the prediction point comparable across cases and removes the length-bias of event-count prefixes (a case with many events in 24h is *itself* a signal, which the event-count view accidentally conditions away). Both variants are built; the time-based one is used for the headline early-warning claim, the event-count one for process-analytic comparability.

**Short cases.** A case that terminates before reaching k events (e.g. rejected at KYC in two events) is *not* silently dropped from the study. For the event-count view it is excluded from the k-cohort but is recorded in the k-cohort flow table as "terminated before k", and it remains in the multi-state/competing-risk analysis. For the elapsed-time view it is fully included with whatever events occurred before Δ, plus an explicit `already_terminal_at_tau` flag — since a case already rejected at 24h is trivially a non-activation, these are either excluded from the risk model or handled by the propensity stage, never mislabelled.

**Repeated document loops.** The `Credit Review → Request Documents → Credit Review` cycle is a genuine signal, not noise. It is preserved in the trace and summarized by features (§5): loop count so far, time in loop, whether the case is currently mid-loop at τ(c). Prefixes are never collapsed or deduplicated across loop iterations, because doing so would erase the rework signal; variant analysis uses both the raw variant and a loop-collapsed variant (A B C+ → A B C) so that variant counts remain interpretable.

**Activity renaming and duplicates (15 Oct 2025).** A pre-processing normalization layer maps post-migration activity labels back to a canonical vocabulary via an explicit, reviewed mapping dictionary (never fuzzy string matching alone). Validation: compare the DFG and activity-frequency profile in the 8 weeks before and after the migration under the mapping; a correct mapping should leave control-flow structure broadly stable, and any residual structural break is reported rather than smoothed away. Duplicates are removed on (case, canonical activity, timestamp, resource) with a tolerance window (e.g. identical activity by the same resource within 1 second), and the count removed is reported per week so that a spike at migration is visible. A `migration_regime` indicator is retained as a feature-audit variable — if it is predictive, that is evidence of residual data artifacts, not of credit risk.

## 5. Process-aware features

All features are stamped with the availability rule "computable from events 1..k and from reference data whose own as-of time ≤ τ(c)".

**Static case attributes (known at case start).** `case:channel`, `case:region`, `case:requested_amount`, log(amount), amount percentile *within the trailing 90-day application population as of τ(c)* (not the whole-history percentile — that peeks), `source_system`, application weekday/hour, and partner-origination flag.

**Prefix-derived control flow.** Canonical activity sequence of the prefix; prefix variant id (with a rare-variant bucket fitted on training data only); number of distinct activities; whether KYC completed; number of `Credit Review` visits so far; number of `Request Documents` loops so far; currently-mid-loop indicator; whether any rework/back-jump occurred; n-gram indicators for the last two activities; directly-follows edges present in the prefix scored against a training-period DFG (e.g. minimum edge frequency in the prefix = "how unusual is this path so far").

**Timing.** Elapsed time since case start at τ(c); inter-event durations (each transition, plus mean/max/std); time to first Credit Review; longest idle gap; fraction of elapsed time spent waiting vs. in active service (from a service/waiting decomposition); business-hours-adjusted durations; whether any duration exceeds the training-period 90th percentile for that transition.

**Resource / queue.** Handling resource identity for KYC and first Credit Review (hashed, with a rare-resource bucket); number of distinct resources so far; number of handovers; **as-of** resource workload — count of other cases that resource had open in the 24h before τ(c), computed from the event log with a strict `< τ(c)` filter; system-level congestion — number of applications started but unresolved in the 7 days before τ(c); queue position proxy = rank of arrival time among cases arriving that day. Note the explicit repair for `org:resource` experience in §6: experience must be recomputed as "events handled by this resource strictly before τ(c)", never taken from the extraction-time HR field.

**Rework / conformance.** Loop counts as above; number of self-loops; a conformance score of the prefix against a process model discovered **on the training window only** (fitness of the prefix as a partial trace); deviation flags for unexpected orderings (e.g. Credit Review before KYC).

**Cohort / calendar.** Policy regime indicator (pre/post 2025-07-01); migration regime indicator (pre/post 2025-10-15), used for audit and for regime-aware calibration rather than as a free predictor; application-month; trailing-window cohort statistics as of τ(c) — e.g. the observed activation rate and observed maturity rate of applications started in the previous 30 days, using only outcomes already matured at τ(c) (this is the one family of features that requires historical reference data and must be built with a rolling, backward-only window to avoid target leakage through cohort aggregates).

**Explicitly excluded from features:** anything in §6 marked drop, plus any aggregate computed over the full dataset (global target encoding, global scaling statistics). All encoders, imputers and scalers are fitted inside the temporal training fold only.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep / repair / drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after the final credit decision; its non-null status alone reveals that the case was accepted, and its value encodes the underwriter's risk assessment. Warehouse exports often repeat it on all rows of the case, including the prefix rows. | Available only at/after the Accept event; for k=3 prefixes it is never legitimately available. | **Drop** for the risk model at prefix time. May be used as an outcome-side descriptor or as a feature in a *post-activation* model with prediction point = activation. | Its presence is a near-deterministic function of activation, which is the very selection we are trying to model. |
| `decision_reason` | Populated at or after Accept/Reject; directly encodes the label-adjacent decision and, for rejections, the exact selection mechanism. | At/after the credit-decision event only. | **Drop** at prefix time. Retain for cohort auditing and for describing the selection process qualitatively. | Using it would let the model read the decision it is supposed to anticipate. |
| `collection_status` | Updated after activation and "may directly reveal default" — this is outcome leakage in the strongest sense. | Strictly post-activation, post-outcome. | **Drop** entirely from the feature space. Use only as a cross-check/derivation source for the label itself. | A model with this field would report near-perfect AUC and be worthless. Any pipeline that scores >0.95 AUC should be assumed to have re-admitted it. |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | Present in the same event file; any prefix built by grouping the whole case, or any case-level aggregate such as trace length or total duration, imports them. | Only events with `time:timestamp ≤ τ(c)` may contribute to any feature, count, duration, variant, DFG, or conformance score. | **Repair** — enforce a hard row filter before feature construction, and forbid whole-case aggregates. | The most common and most silent leak: "number of events in case" and "case duration" are future-dependent by construction. |
| `documents_total` (nightly snapshot) | Same-calendar-day granularity means it can include documents uploaded *after* τ(c) on the same day — a partial-day look-ahead that correlates with how the case later progressed. | Only the snapshot whose as-of timestamp is strictly ≤ τ(c) — in practice the previous night's snapshot. | **Repair** — lag by one snapshot (use previous-day value), or replace with an event-derived document count reconstructed from `Request Documents`/upload events with strict `< τ(c)` filtering. | Snapshot granularity coarser than prediction granularity is a classic same-day leak; the event-derived version is preferable because its as-of semantics are exact. |
| `risk_score` (updated at several events) | The column carries the *latest* value; later updates incorporate the underwriter's post-review judgement and possibly post-decision information. | Only the most recent value recorded at an event with timestamp ≤ τ(c); if no such event exists, the value is genuinely missing. | **Repair** — take as-of value via a backward-looking join on the event stream; add `risk_score_age` and `risk_score_n_updates_so_far` as features; add a missing indicator rather than imputing forward from the future. | The score is legitimately useful early; only its *later revisions* leak. |
| Resource experience (stored at extraction time) | Extraction-time experience is a function of everything the resource did after τ(c), so it embeds future workload and tenure; it also correlates with the calendar period, creating a spurious time trend. | Recompute as a running count/tenure from the event log using only events strictly before τ(c). | **Repair** — recompute as-of; drop the warehouse field. | Using extraction-time tenure gives 2024 cases their 2026 experience values, a direct temporal leak. |
| Label availability (`default_90d` presence, `label_available_at`) | Presence of a label is itself informative: it depends on maturity, on feed speed, and on partner origination — so filtering to "label present" silently selects a non-random, lower-risk-feed subpopulation. Using `label_available_at` as a feature would be a direct outcome-side leak. | Never a feature. Used only to (a) define maturity as of C, and (b) fit the observation-probability model for weighting. | **Drop as feature / keep as design variable.** | The whole selection problem of this study is encoded in this column; it must drive the design, not the features. |
| `data_extract_time` | Constant per export; if it varies it encodes vintage and hence maturity. | Design variable only. | **Drop** as a feature. | Pure artifact of the export process. |
| Case-level cohort aggregates (e.g. regional default rate) | Computed over the full dataset they include future and out-of-fold outcomes. | Rolling backward window ending at τ(c), fitted within the training fold. | **Repair** — rolling, backward-only, out-of-fold. | Target encoding is the second most common silent leak after future events. |
| Post-migration activity labels | Renamed activities perfectly separate the post-2025-10-15 period, so any label-based feature can proxy for calendar time and hence for maturity/label-presence. | Canonical vocabulary applied before feature construction. | **Repair** via mapping; keep `migration_regime` for audit only. | A "predictive" renamed activity is a data artifact, not risk. |

**Automated audit checks in the pipeline:** (i) assert no retained event row has timestamp > τ(c); (ii) assert the forbidden column set is absent from the final feature matrix; (iii) single-feature AUC screen — any feature above ~0.80 alone is quarantined for manual review; (iv) train a "detector" model to predict `label_present` from the features — high accuracy indicates the feature space encodes the selection/maturity mechanism.

## 7. Validation design

**Why a random case split is misleading here.** Four independent reasons, each sufficient on its own: (1) the credit policy changed on 2025-07-01, so a random split trains on post-change cases and tests on pre-change ones and vice versa, inflating apparent performance relative to the only regime that matters (the future one); (2) the migration on 2025-10-15 created renamed activities and duplicates, and a random split lets the model learn migration artifacts from test-period-adjacent data; (3) label maturity is a function of calendar time — random splitting puts mature 2024 cases in test and immature 2025 cases in train, so the test set is systematically easier and older; (4) cohort-level aggregates and resource identities recur across cases, so random splitting shares information across folds. Random splitting also silently answers "can I interpolate within my history?" when the deployment question is "can I extrapolate to next quarter?".

**Primary scheme — rolling-origin temporal backtest, split on case *start* time** (not on activation or label time, because at scoring time only the start is known):

| Fold | Train starts | Gap (embargo) | Test starts | Notes |
|---|---|---|---|---|
| F1 | 2024-01 → 2024-09 | 125d | 2025-01 → 2025-03 | pre-policy-change regime |
| F2 | 2024-01 → 2024-12 | 125d | 2025-04 → 2025-06 | last pre-change test |
| F3 | 2024-01 → 2025-03 | 125d | 2025-07 → 2025-09 | **policy-change stress fold** — train regime ≠ test regime |
| F4 | 2024-01 → 2025-06 | 125d | 2025-10 → 2025-12 | **migration fold**; heavy censoring, evaluate with survival metrics only |

The **embargo gap** of 125 days (90d horizon + 35d max feed lag) between the end of training labels and the start of the test period reproduces the real deployment constraint: at deployment time you can only have trained on cases whose labels had already matured. Without it, backtest performance is optimistic by roughly one label-maturity period. Fold F4's test cases are largely immature at C, so it is evaluated on censoring-aware metrics (and partially on a *shortened* horizon, e.g. 30-day default, reported as a different quantity, not as the 90-day number).

**Policy change.** Report metrics separately for pre- and post-2025-07-01 test cases; fit F3 explicitly as a regime-transfer test. If discrimination holds but calibration breaks across the change, the deployment recommendation is recalibration-on-a-schedule, not retraining from scratch. A regime indicator is included in the model with regime-specific intercept so calibration drift is separated from ranking drift.

**System migration.** Evaluate on post-migration test data with the canonical mapping applied; additionally run a negative-control experiment predicting `migration_regime` from the features — if it is easily predictable, the mapping is incomplete and the F4 results are not trustworthy.

**Label maturity.** Every fold is run under both the optimistic (97d) and conservative (125d) maturity rules; the difference is reported as a maturity-sensitivity band around each metric. Cases not mature at the fold's cutoff enter as censored observations in the survival evaluation rather than being dropped.

**Metrics.** For the primary censored target: time-dependent AUC / C-index (Uno's, with IPCW to correct for censoring) at 90 days; IPCW-Brier score and the integrated Brier score over [0, 90d] as the proper scoring rule; calibration of the predicted 90-day cumulative incidence against a Kaplan–Meier / Aalen–Johansen estimate within predicted-risk deciles (calibration curve plus calibration slope/intercept, not just a single ECE number). For the activation-propensity stage: ordinary AUC and calibration on all applications. For the multi-state model: cause-specific cumulative-incidence calibration. Business-facing: alert precision and captured-default share at realistic review capacities (top 1%, 5%, 10% of applications per week), computed *per week* so that capacity is defined the way operations would define it. Naive uncensored accuracy/AUC on the 21,600 labeled rows is reported only as a clearly-flagged baseline showing how much optimism the naive design introduces.

**Subgroups.** Metrics broken out by `case:channel`, `case:region`, `source_system` (partner vs. own origination — the group with elevated permanently-missing feeds), requested-amount quartile, and policy regime. Report both discrimination and calibration per subgroup; a model that is well-calibrated overall and badly calibrated for partner-originated accounts is not deployable for those accounts. Because outcome observation itself differs by `source_system`, subgroup metrics there are also reported under the missing-feed bounding analysis.

**Distribution shift monitoring.** PSI/KL on feature distributions and on prefix-variant distributions between training and each test window; DFG-level comparison (edge frequency deltas) as a process-drift monitor; a train-vs-test discriminator AUC as a summary shift statistic. Post-deployment, monitor score distribution, activation-rate-by-score-band, and (with the necessary lag) realized default by score band, with an explicit understanding that the last of these is only available 125 days late.

## 8. Limitations and decision-use boundary

**What the study can claim.**
- A calibrated estimate of 90-day default risk **among applications the lender's policy activates**, as a function of information available in the first few events, valid for the policy regime it was trained/recalibrated on.
- A calibrated estimate of **activation propensity** from the same early prefix, on the full application population.
- Cause-specific cumulative incidence of "activated-and-early-default" among all applications, useful for volume and provisioning planning.
- Quantified bounds on how much the conclusions could move under plausible transfer-linkage and missing-feed mechanisms.

**What it cannot claim.**
- It cannot estimate the default risk of applications that were rejected, withdrawn, or transferred. Those quantities are not identified from these data at any sample size. Any number offered for them rests on the untestable exchangeability assumption of Target B and must be presented with that label attached.
- It cannot be used to argue that the current underwriting policy is optimal or suboptimal, because the training data contains only outcomes generated under that policy — the model has never seen what happens when a currently-rejected profile is activated.
- It cannot support "expanding approvals into the low-score tail": that is precisely the region where positivity fails and where the model extrapolates rather than predicts.
- It cannot be treated as a causal model of the drivers of default. High-loop-count or slow-processing prefixes may predict default because they proxy for the underwriter's suspicion, not because process delay causes default.

**Three distinctions to keep separate.**
1. *Predictive association* — "prefixes like this are followed by default more often, under the observed policy." This is what the model delivers.
2. *Selection effects* — "prefixes like this are rarely activated, so the activated ones are atypical." This is why the conditional risk among activated cases can look *lower* for objectively riskier profiles (only the exceptionally good ones survive screening) — a genuine and counterintuitive inversion that must be explained to stakeholders before any threshold is set.
3. *Counterfactual default risk* — "if we activated this applicant, they would default with probability p." Not identified here.

**Three ways deployment changes the data-generating process.**
1. **Policy feedback / self-fulfilling selection.** If the score is used to reject, the high-score region stops producing activations, so future training data contains no outcomes there; the model's estimate in that region freezes at its deployment-time value and silently degrades. Mitigation: a small randomized or discretion-override exploration quota, or at minimum systematic logging of overrides, so the high-score region retains some observed outcomes.
2. **Behavioural adaptation.** Applicants, brokers and partner channels learn which early-process patterns trigger scrutiny and adjust — fewer document loops, faster submissions, channel-shopping. Features that encode process behaviour are exactly the ones most susceptible to being gamed, and their predictive value will decay faster than static attributes.
3. **Operational reallocation.** If high scores trigger extra manual review or earlier collections contact, the process itself changes: durations, resource assignment, and even the realized default rate change, so the model degrades its own targets and its own features simultaneously. Mitigation: define features on the pre-intervention part of the process, monitor DFG drift, and hold out an untreated control stream where legally and operationally possible.
4. (Additional) **Transfer-policy shift.** If scoring changes which cases are transferred to partners, the composition of the opaque 40%-unlinked transfer population changes, invalidating the sensitivity bounds computed on historical data.

**Decision-use boundary.** Recommended uses: triage and prioritization of manual review, early collections readiness, portfolio provisioning under the current policy, and monitoring. Not recommended without further work: automated adverse action / automated rejection, approval-boundary expansion, pricing in the low-overlap tail, and any use on partner-originated accounts until the missing-feed bounds are shown to be decision-irrelevant for that segment. Fair-lending review of subgroup calibration is a prerequisite for any customer-facing use, and the selection effects in point 2 above make naive subgroup comparisons misleading in both directions.

## 9. PM4Py-oriented Python implementation skeleton

```python
"""
Censored-outcome early-warning study: data engineering + audit pipeline.
Builds an as-of, leakage-audited prefix feature table with survival-ready labels.
Model fitting (discrete-time survival / competing risks) is intentionally out of scope;
the hand-off points are marked with `# --> SURVIVAL HOOK`.
"""
import numpy as np
import pandas as pd
import pm4py

CSV = "applications_events.csv"
ANALYSIS_CUTOFF = pd.Timestamp("2026-02-15")      # data_extract_time; configurable
HORIZON_DAYS = 90
FEED_LAG_Q95_DAYS = 35                            # conservative; estimate from label_available_at
POLICY_CHANGE = pd.Timestamp("2025-07-01")
MIGRATION_DATE = pd.Timestamp("2025-10-15")
PREFIX_K = 3                                      # primary operating point (Start -> KYC -> Credit Review)

# Columns that are only populated at/after the credit decision or activation.
# ASSUMPTION: warehouse repeats these on every event row of a case -> must be nulled per-prefix.
POST_DECISION_COLS = ["final_limit", "decision_reason", "collection_status", "default_90d",
                      "label_available_at", "data_extract_time"]

# Canonical activity vocabulary; the migration on 2025-10-15 renamed several activities.
# ASSUMPTION: mapping is reviewed by domain experts, not fuzzy-matched.
RENAME_MAP = {
    "App Started": "Application Started", "KYC Check": "Identity/KYC Check",
    "Credit Assessment": "Credit Review", "Doc Request": "Request Documents",
    "Contract Signature": "Contract Signed", "Account Opened": "Account Activated",
}
ACT_ACTIVATED, ACT_REJECTED = "Account Activated", "Rejected"
ACT_WITHDRAWN, ACT_TRANSFERRED = "Withdrawn", "Transferred"
TERMINALS = {ACT_ACTIVATED, ACT_REJECTED, ACT_WITHDRAWN, ACT_TRANSFERRED}


def load_events(path=CSV):
    df = pd.read_csv(path, parse_dates=["time:timestamp", "label_available_at", "data_extract_time"])
    df["concept:name"] = df["concept:name"].replace(RENAME_MAP)          # normalize renames FIRST
    # Migration created occasional duplicate events -> dedupe on identity tuple (report the count).
    before = len(df)
    df = df.drop_duplicates(subset=["case:concept:name", "concept:name", "time:timestamp", "org:resource"])
    print(f"[dedupe] removed {before - len(df)} duplicate event rows")
    df = df.sort_values(["case:concept:name", "time:timestamp"], kind="mergesort")
    df["ev_idx"] = df.groupby("case:concept:name").cumcount() + 1
    return pm4py.format_dataframe(df, case_id="case:concept:name",
                                  activity_key="concept:name", timestamp_key="time:timestamp")


def build_case_index(df, cutoff=ANALYSIS_CUTOFF):
    """Case-level start / activation / terminal / censoring / label-maturity, as of `cutoff`."""
    g = df.groupby("case:concept:name")
    idx = pd.DataFrame({"start": g["time:timestamp"].min(), "last_seen": g["time:timestamp"].max()})

    def first_ts(act):
        s = df.loc[df["concept:name"] == act].groupby("case:concept:name")["time:timestamp"].min()
        return idx.index.map(s)

    for act, col in [(ACT_ACTIVATED, "activation_time"), (ACT_REJECTED, "rejected_time"),
                     (ACT_WITHDRAWN, "withdrawn_time"), (ACT_TRANSFERRED, "transferred_time")]:
        idx[col] = pd.to_datetime(pd.Series(first_ts(act), index=idx.index))

    idx["activated"] = idx["activation_time"].notna()
    # A case is "open" if it reached no terminal activity at all by the cutoff.
    term = df[df["concept:name"].isin(TERMINALS)].groupby("case:concept:name")["concept:name"].first()
    idx["terminal"] = idx.index.map(term).fillna("Open")

    # Label maturity: conservative rule = activation + horizon + feed lag <= cutoff.
    mature_at = idx["activation_time"] + pd.Timedelta(days=HORIZON_DAYS + FEED_LAG_Q95_DAYS)
    idx["label_mature"] = idx["activated"] & (mature_at <= cutoff)

    lab = df.dropna(subset=["default_90d"]).groupby("case:concept:name")["default_90d"].max()
    idx["default_90d_raw"] = idx.index.map(lab)
    # NEVER fillna(0): a missing label is not a non-default.
    idx["label_observed"] = idx["default_90d_raw"].notna() & idx["label_mature"]

    # Survival view: exposure clock starts at activation, capped at the horizon and at the cutoff.
    exposure = (np.minimum(cutoff, idx["activation_time"] + pd.Timedelta(days=HORIZON_DAYS))
                - idx["activation_time"]).dt.days
    idx["exposure_days"] = exposure.clip(lower=0)
    idx["event_default"] = (idx["default_90d_raw"] == 1) & idx["label_observed"]
    idx["right_censored"] = idx["activated"] & ~idx["label_observed"]      # admin censoring OR missing feed
    # Permanently-missing feed is NOT censoring; flag it separately for IPW / bounding.
    idx["feed_at_risk"] = idx.index.map(df.groupby("case:concept:name")["source_system"].first()).eq("partner")
    idx["policy_regime"] = np.where(idx["start"] >= POLICY_CHANGE, "post", "pre")
    idx["migration_regime"] = np.where(idx["start"] >= MIGRATION_DATE, "post", "pre")
    return idx


def cohort_flow(idx):
    """All applications accounted for -- no silent drops."""
    def bucket(r):
        if r["activated"] and r["label_observed"]:  return "1_labeled_activated"
        if r["activated"]:                          return "2_activated_not_mature_or_missing_feed"
        if r["terminal"] == ACT_REJECTED:           return "3_rejected_competing"
        if r["terminal"] == ACT_WITHDRAWN:          return "4_withdrawn_competing"
        if r["terminal"] == ACT_TRANSFERRED:        return "5_transferred_competing_or_offbook"
        return "6_open_process_censored"
    idx = idx.assign(cohort=idx.apply(bucket, axis=1))
    print(idx.groupby(["cohort", "policy_regime"]).size().unstack(fill_value=0))
    assert len(idx) == idx["cohort"].notna().sum(), "cases lost from the flow table"
    return idx


def temporal_split(idx, train_end, test_start, test_end):
    """Split by CASE START time; embargo = horizon + feed lag reproduces deployment maturity."""
    embargo = pd.Timedelta(days=HORIZON_DAYS + FEED_LAG_Q95_DAYS)
    assert test_start - train_end >= embargo, "embargo gap too small -> optimistic backtest"
    train = idx.index[(idx["start"] <= train_end) & idx["label_mature"]]
    test = idx.index[(idx["start"] >= test_start) & (idx["start"] <= test_end)]
    # pm4py.split_train_test(log, 0.8) exists as a convenience baseline but is NOT used here:
    # a random split leaks across the 2025-07-01 policy change and the 2025-10-15 migration.
    return list(train), list(test)


def as_of_prefixes(df, k=PREFIX_K):
    """Fixed event-count prefixes via pm4py, then a hard as-of filter on rows AND columns."""
    pref = pm4py.get_prefixes_from_log(df, length=k)          # keeps first k events per case
    tau = pref.groupby("case:concept:name")["time:timestamp"].max().rename("tau")
    pref = pref.merge(tau, on="case:concept:name")
    pref = pref[pref["time:timestamp"] <= pref["tau"]]        # row-level: no future events
    for c in POST_DECISION_COLS:                              # column-level: no future attributes
        if c in pref.columns:
            pref[c] = np.nan
    # Cases terminating before k events are excluded HERE but stay in the cohort flow table.
    full = pref.groupby("case:concept:name").size().eq(k)
    return pref[pref["case:concept:name"].isin(full[full].index)]


def elapsed_time_prefixes(df, delta_hours=72):
    """Elapsed-time variant: comparable prediction point across cases, no length bias."""
    start = df.groupby("case:concept:name")["time:timestamp"].transform("min")
    tau = start + pd.Timedelta(hours=delta_hours)
    out = df[df["time:timestamp"] <= tau].copy()
    out["tau"] = tau[df["time:timestamp"] <= tau]
    for c in POST_DECISION_COLS:
        if c in out.columns:
            out[c] = np.nan
    return out


def build_features(pref, idx):
    """Prefix-derived control-flow / timing / rework features. All strictly <= tau."""
    g = pref.groupby("case:concept:name")
    f = pd.DataFrame({
        "tau": g["time:timestamp"].max(),
        "n_events": g.size(),
        "n_distinct_act": g["concept:name"].nunique(),
        "n_credit_review": g["concept:name"].apply(lambda s: (s == "Credit Review").sum()),
        "n_doc_loops": g["concept:name"].apply(lambda s: (s == "Request Documents").sum()),
        "n_resources": g["org:resource"].nunique(),
        "elapsed_h": (g["time:timestamp"].max() - g["time:timestamp"].min()).dt.total_seconds() / 3600.0,
        "max_gap_h": g["time:timestamp"].apply(lambda s: s.diff().dt.total_seconds().max() / 3600.0),
        # risk_score: AS-OF value only (last update at or before tau), plus staleness + update count.
        "risk_score_asof": g["risk_score"].last(),
        "risk_score_n_upd": g["risk_score"].apply(lambda s: s.notna().sum()),
        "channel": g["case:channel"].first(),
        "region": g["case:region"].first(),
        "requested_amount": g["case:requested_amount"].first(),
        "source_system": g["source_system"].first(),
    })
    # Prefix variant id (rare buckets must be fitted on TRAIN only, downstream).
    f["prefix_variant"] = pm4py.get_variants(pref).keys().__class__ and \
        g["concept:name"].apply(lambda s: " -> ".join(s))
    # Timing enrichment; interpretation is safe because it is computed on the PREFIX log only.
    tmp = pm4py.extract_temporal_features_dataframe(pref)
    f = f.join(tmp.select_dtypes("number").groupby(pref["case:concept:name"]).mean(), rsuffix="_tmp")
    # Resource experience must be recomputed as-of, NOT taken from the extraction-time HR field.
    # (left as an explicit backward-looking join over the full event stream)
    return f.join(idx[["policy_regime", "migration_regime", "activated", "label_observed",
                       "event_default", "exposure_days", "right_censored", "feed_at_risk"]])


def leakage_audit(feature_table):
    forbidden = set(POST_DECISION_COLS) | {"collection_status", "final_limit", "decision_reason"}
    present = forbidden & set(feature_table.columns)
    assert not present, f"LEAKAGE: post-outcome columns in feature table: {present}"
    # Any event timestamp beyond tau would be a row-level leak.
    assert feature_table["tau"].notna().all()
    # Detector check: if the features predict label availability well, they encode the selection
    # /maturity mechanism rather than credit risk. Report, do not silently pass.
    print("[audit] label_observed rate by source_system:")
    print(feature_table.groupby("source_system")["label_observed"].mean())
    print("[audit] activation rate by policy regime:")
    print(feature_table.groupby("policy_regime")["activated"].mean())


if __name__ == "__main__":
    ev = load_events()
    idx = cohort_flow(build_case_index(ev))
    # Control-flow sanity + migration artifact check (pre vs post DFG comparison).
    dfg, sa, ea = pm4py.discover_dfg(ev[ev["time:timestamp"] < MIGRATION_DATE])
    dfg2, _, _ = pm4py.discover_dfg(ev[ev["time:timestamp"] >= MIGRATION_DATE])
    print(f"[migration] DFG edges before={len(dfg)} after={len(dfg2)} "
          f"(large asymmetry => rename map incomplete)")

    pref = as_of_prefixes(ev, k=PREFIX_K)
    feats = build_features(pref, idx)
    leakage_audit(feats)

    tr, te = temporal_split(idx, pd.Timestamp("2025-03-31"),
                            pd.Timestamp("2025-07-01"), pd.Timestamp("2025-09-30"))
    print(f"[split] train={len(tr)} test={len(te)} (policy-change stress fold)")

    # --> SURVIVAL HOOK (stage 2): discrete-time hazard / Cox on rows where activated == True,
    #     duration = exposure_days, event = event_default, censored = right_censored,
    #     weights = 1 / P(feed observed | source_system, prefix) for permanently-missing feeds.
    # --> COMPETING-RISK HOOK: Aalen-Johansen / Fine-Gray over ALL cases with causes
    #     {activated-default, activated-no-default, rejected, withdrawn, transferred}, open = censored.
    # --> PROPENSITY HOOK (stage 1): P(activated | prefix features) on all 48,000 applications;
    #     the reported early-warning score is P(activate) x P(default | activate), reported
    #     alongside both factors so the selection component stays visible.
    # NOTE: pm4py provides no survival/competing-risk estimator; use lifelines/scikit-survival here.
    feats.to_parquet("prefix_features_k3.parquet")
