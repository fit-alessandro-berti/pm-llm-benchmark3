* **Exploration / process understanding**: maximize recall, tolerate permissiveness, human readable.
* **Conformance enforcement / audit**: must forbid policy violations, precision and soundness dominate, fitness to unseen compliant behaviour matters.
* **Simulation / capacity planning**: needs soundness, realistic ordering, no deadlocks.
* **Stakeholder communication**: simplicity and faithful policy semantics.

Fitness/precision trade-off therefore changes with use. Exploration rewards high fitness + generalisation even at cost of precision. 6. Alignment-cost sensitivity
7. Stakeholder score methodology

# 7. Third Alternative

**Design choice:** Block-structured POWL backbone with explicit declarative guards for policy points that cannot be inferred from control flow due to missing attributes.

1. Compact formal description

`Register Dossier -> AND(Credit Check, Technical Review) -> PostChecks -> XOR(Manager Approval, Auto Approval) -> Release Order`

PostChecks is a StrictPartialOrder over optional `Supplier Review` and optional `Expedite Review` with constraints:
`Credit Check < Expedite Review`, `Technical Review < Expedite Review`, `Expedite Review < Approval`, `Credit Check < Supplier Review`, `Technical Review < Supplier Review`, `Supplier Review < Approval`. Expedite and Supplier are unordered relative to each other.

Correction is modelled as an optional loop:
`Correct Dossier` may occur after initial checks and before approval, and must be followed by at least one repeat of `Credit Check` or `Technical Review`. No check may repeat without a preceding `Correct Dossier`.

2. PM4Py code

```python
import pm4py
from pm4py.objects.powl.obj import POWL, Transition, OperatorPOWL, StrictPartialOrder

register = Transition('Register Dossier')
credit = Transition('Credit Check')
technical = Transition('Technical Review')
supplier = Transition('Supplier Review')
expedite = Transition('Expedite Review')
manager = Transition('Manager Approval')
auto = Transition('Auto Approval')
release = Transition('Release Order')

checks = OperatorPOWL(operator=OperatorPOWL.AND, children=[credit, technical])
approval = OperatorPOWL(operator=OperatorPOWL.XOR, children=[manager, auto])

# optional activities with optionality via XOR with silent
from pm4py.objects.powl.obj import SilentTransition
tau = SilentTransition()

supplier_opt = OperatorPOWL(operator=OperatorPOWL.XOR, children=[supplier, tau])
expedite_opt = OperatorPOWL(operator=OperatorPOWL.XOR, children=[expedite, tau])

post = StrictPartialOrder(nodes=[supplier_opt, expedite_opt, approval])
post.order.add_edge(checks, supplier_opt)
post.order.add_edge(checks, expedite_opt)
post.order.add_edge(expedite_opt, approval)
post.order.add_edge(supplier_opt, approval)

model_third = OperatorPOWL(operator=OperatorPOWL.Sequence, children=[
    register,
    checks,
    post,
    release
])
```

3. Declarative guards required because attributes missing

```python
declare_constraints = {
    'mandatory': [
        'precedence(Register Dossier, Credit Check)',
        'precedence(Register Dossier, Technical Review)',
        'responded_existence(Credit Check, Manager Approval)',
        'responded_existence(Technical Review, Manager Approval)'
    ],
    'expedite_order': [
        'precedence(Credit Check, Expedite Review)',
        'precedence(Technical Review, Expedite Review)',
        'precedence(Expedite Review, Manager Approval)',
        'precedence(Expedite Review, Auto Approval)'
    ],
    'approval_xor': [
        'xor(Manager Approval, Auto Approval)'
    ],
    'no_repeat_without_correct': [
        'absence(>1 Credit Check without Correct Dossier)',
        'absence(>1 Technical Review without Correct Dossier)'
    ],
    'correction': [
        'responded_existence(Correct Dossier, Credit Check or Technical Review)'
    ]
}
```

4. Explicit semantics
* P1 satisfied by sequence start/end.
* P2 mandatory AND, order free.
* P3 Supplier optional, no attribute condition.
* P4 Expedite after both checks, before approval, unordered vs Supplier.
* P5 exactly one approval via XOR.
* P6 correction loop allows partial recheck; exact affected check unknown, so we enforce at least one recheck.
* P7 repeat without Correct Dossier forbidden by declare guard.

Limitations: external/internal attribute missing  Supplier Review remains optional for all cases. Affected-check attribute missing  correction semantics is approximated.

# 9. Validation Experiments

* Reproducible splits: stratified by case start month, seed 42, 80/20, published preprocessing script.
* Attribute-stratified holdout: split by external/internal proxy if available.
* Curated negative suite: 30 traces violating each P1-P7, e.g., approval before checks, Expedite before checks, repeat without correction.
* Perturbation tests: random event deletion 5/10/20% to measure missing-event bias.
* Unseen-combination tests: generate all permutations of optional activities respecting constraints.
* Alignment-cost sensitivity: sweep log/move costs.
* Soundness: `pm4py.check_soundness(net, im, fm)`.
* Metrics reported separately: fitness_alignments, precision_alignments, generalization_tbr, simplicity_petri_net.

PM4Py skeletons:

```python
net, im, fm = pm4py.convert_to_petri_net(model_third)
pm4py.check_soundness(net, im, fm, print_diagnostics=True)
fitness = pm4py.fitness_alignments(log_holdout, net, im, fm)

generalization = pm4py.generalization_tbr(log_train, log_holdout, net, im, fm)
```

Decision rule: reject model if negative suite recall >0, or holdout fitness <0.90 with precision <0.85, or soundness fails.

# 10. Governance Recommendation

* Model S: may be used for exploration only, with explicit disclaimer that it permits policy violations. Must not be used for conformance enforcement.
* Model C: retire for production. High training precision is memorisation, holdout degradation and duplicate labels make it unmaintainable.
* Third alternative: candidate for compliance after validation experiments pass: holdout fitness 0.90, precision on curated negative suite 0.95, soundness holds, stakeholder comprehension 3.5 with documented protocol. Deploy with declarative guards enforced at runtime.

# 11. Dissenting View

The third alternative adds complexity and declarative guards that business users will not understand, replicating Model C's comprehension problem. The missing external/internal and affected-check attributes mean any control-flow model is fundamentally under-specified; the safest operational stance is Model S for exploration and manual review, with Model C as an audit reference for known variants. Imposing partial orders and XORs will simply shift false negatives from Model C to new edge cases, while the declarative layer introduces a second source of truth that is hard to test. We would need full attribute logging before any enforcement model is justified.

Evidence needed to change: production logs with external/internal flag and affected-check attribute for 3 months, a curated negative suite agreed by compliance, and a reproducible A/B conformance trial showing third alternative reduces false positives vs Model S without increasing false negatives vs Model C.
