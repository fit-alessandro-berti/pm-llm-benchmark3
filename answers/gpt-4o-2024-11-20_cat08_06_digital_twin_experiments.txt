# 1. Model Scope and State Variables

**Boundary**:  
The digital twin encompasses the end-to-end building-permit process, starting from the application submission through to the issuance or rejection of the permit. Non-stationary demand, resource calendars, cross-case dependencies, rework, and interactions between related cases are modeled. Applicant and third-party responses are partially exogenous but included.

**Entities and State Variables**:  
1. **Cases**:  
   - Attributes: `case_id`, `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`.
   - State variables: current activity, timestamps, rework count, SLA compliance status, linkage with other cases (e.g., same architect, geographic grouping).
  
2. **Resources**:  
   - Groups: Clerks, Planners, Fire-safety reviewers, Environmental reviewers, Inspectors, Legal officers, System tasks.
   - State: availability (calendar-driven), queue length, assigned tasks, utilization.

3. **Queues**:  
   - Queues linked to each activity/resource pair.
   - Attributes: waiting cases, queue discipline (e.g., FIFO or priority-based).

4. **Calendars**:  
   - Resource-specific calendars (e.g., public holidays, peak/off-peak schedules, district-specific inspection travel).

5. **Cross-case Interactions**:  
   - Architect-based bursts: downstream delays for related cases in batching/inspection.
   - Neighborhood objections: longer public-notice durations when objections occur.

**Dynamic States (Simulation Clock)**:  
- Case progression through activities.
- Resource allocation based on priorities and calendar constraints.
- Captured waiting times, service times, and rework triggers.
- System-level statistics (e.g., backlog, SLA violations, resource utilization).

# 2. Parameter-Estimation Plan

1. **Arrival Rates**:  
   - Use PM4Py's **`split_log_to_periods`** to partition logs by time intervals (e.g., weekdays, months). 
   - Apply seasonality analysis using Fourier decomposition or time-series modeling to capture non-stationary patterns.

2. **Service and Waiting Times**:  
   - Aggregate logged timestamps using **`calculate_service_time`**, **`calculate_waiting_time`**, and calendar adjustments for missing start timestamps.
   - Disaggregate service/waiting times using median, p90 percentiles, and analyze heavy-tailed distributions with clustering.

3. **Routing Probabilities**:  
   - Derive frequencies of branches from process mining over the log using the discovery of variants and Directly-Follows Graphs (DFGs).

4. **Rework Probabilities**:  
   - Analyze rework-triggering activities (e.g., Planning Review logs with subsequent rework loops).
   - Infer frequencies and cause analysis using textual patterns from "rework reasons" and statistical clustering.

5. **Resource Calendars**:  
   - Match logged timestamps to HR data for resource-specific patterns (e.g., working days, holidays). Adjust manually as needed for generic rules (e.g., fire reviewers operating three days a week).

6. **Cross-Case Dependencies**:  
   - Use architect frequency analysis (e.g., identify top 20 architects by applications/week).
   - Estimate objection-related "bursts" via deviations in Public-notice durations.

7. **Policy-Specific Factors**:  
   - For interventions such as batching rules (D3), use conditional probability analysis on inspection logs grouped by district.
   - For D2, filter historical Simple Renovation cases that meet the low-risk criteria.

Custom preprocessing helps handle missing or incomplete data while enriching dependency statistics.

---

# 3. Assumptions

### **Arrivals**:
- Non-stationary arrivals follow observed weekday and seasonal patterns.
- Architect-driven submission bursts are modeled via discrete arrival shocks.
  
### **Service Times**:  
- Missing service start times are extrapolated using inferred queue delays.
- Empirical service times approximate triangular or log-normal distributions due to skewness.

### **Routing**:  
- Exact Fire/Environment/Public-notice trigger rules are estimated from empirical demand and not assumed exhaustive.

### **Resources/Calendars**:  
- HR-estimated calendars are accurate to daily granularity.
- Peak month inspector assumes constant availability during peak.

### **Rework**:  
- Rework process is assumed independent of any prior rework to simplify state transitions.

### **Applicant/Third-Party Response**:  
- Applicant delays (e.g., missing documents) are approximated by heavy-tailed distributions.

### **Cross-Case Dependencies**:  
- Inspections grouped by district assume similar travel times per batch.

### **Non-Stationary Demand**:  
- Forecast seasonal multipliers are accurate to ±5% for experiment ranges.

### **Missing Data**:  
- Public-notice objections are inferred solely from duration deviations.

# 5. Warm-Up, Replications, and Uncertainty Treatment

- **Warm-up**: Run for one simulated year to stabilize initial queues.
- **Run length**: Three simulated years (rolling with historical seasonality).
- **Replications**: 25 per experiment with fixed random seeds.
- **Uncertainty**: 
  - Use Beta PERT or empirical bootstraps for durations.
  - Sensitivity analysis on applicant response rates and objection severity.

---

# 6. Validation Strategy

- **Face Validation**: Collaborate with municipal experts.
- **Event-Log Replay**: Compare current system logs vs. simulated process traces.
- **Distributional Validation**: KS-tests on waiting/service time distributions.
- **Bottleneck Validation**: Compare predicted blocking/resource starvation events to HR metrics.
- **Out-of-Sample Validation**: Simulate unseen high-demand periods.

---

# 7. Decision Criteria

- **Median Duration**: Case type SLAs.
- **Tail Duration**: p95 for fairness.
- **Resource Utilization**: Avoid exceeding 90%.
- **Equity**: Minimize geographic delays.
- **Rework Rates**: Percent of cases reworked.
- **Backlogs**: Queue length variation.
