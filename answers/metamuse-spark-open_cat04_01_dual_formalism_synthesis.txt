# 1. Assumptions and Interpretation
1. **Low-risk / high-risk choice as control-flow XOR.** Risk is data, not an event. It is abstracted as `×( Supervisor Review, ( Quality Review, Regulatory Review))`. `×` is exclusive choice; high-risk branch is `(QR,RR)` with no order, i.e. concurrent and either completion order, matching rule 5. Frequency/semantics of the choice are not modelled.
2. **Optional supplier consultation as XOR with silent skip.** Rule 6: at most once, data-dependent. Modeled as `×( Consult Supplier, )` in the tree and as `OperatorPOWL(XOR, [CS, SilentTransition()])` in POWL. The position in the order encodes `ARC  OptCS` and `OptCS  RM`. Absence of edges to `PV/DCA/Approvals/TrialLoop` encodes “may overlap” as absence of order constraint.
3. **Passing inspection abstracted as LOOP exit.** Rule 8: `ET  IT  [AP  ET  IT]*` until pass. No distinct `pass/fail` events exist. Abstracted as `( (ET,IT), AP)` / `LOOP( PO(ETIT), AP)`. Loop body is `ETIT`; redo is `AP`. This guarantees `AP` never occurs after the final passing `IT` and that `ETIT` is atomic in order, while losing the data condition that distinguishes failing vs passing inspections.
4. **Duplicate visible labels: conceptually permitted, avoided in canonical models.** Duplication can simulate non-block-structured joins in trees but inflates log frequencies, distorts conformance, fitness, and discovery metrics, and creates ambiguous diagnostics. The primary tree presented uses **no duplication**; duplication is discussed only as an approximation alternative and its analytical consequences are documented in §6.
5. **Approximation policy for the process tree: conservative under-approximation.** An exact tree is impossible without exponential blow-up/duplication because `PV` depends on `CM`, `DCA/Approvals` depend on `ARC`, `Trial` depends on `PVDCA`, but `Approvals` must **not** be ordered before `Trial` (rule 7) while `Release` is an AND-join of `Trial+Approvals+OptCS`. Any block-structured tree must either force `Approvals` before `Trial` or force `Approvals` after `DCAPV`. We exclude some intended interleavings (approval-trial overlap, CS-trial overlap) rather than admit unsafe interleavings such as `ET` before `PV/DCA`. Rationale: material-release safety dominates flexibility.
6. **“May overlap” = true concurrency = absence of precedence.** In POWL this is direct: if no `order.add_edge(a,b)` nor `ba` is asserted, `a||b` may interleave arbitrarily or execute concurrently; completion-time logging only imposes order when explicitly constrained. In the tree this is `` (parallel interleaving) – weaker but the standard tree interpretation.
7. **Atomic completion semantics.** Activities are recorded at completion. `ab` means completion of `a` precedes start of `b`. Concurrent means start and completion intervals may overlap; logged order is an interleaving consistent with the partial order.
8. **Release synchronization and framing.** `RD` is global predecessor, `AC` is global successor: `RD*RMAC` via transitivity. `RM` is an AND-join: `TrialLoopRM`, `RiskChoiceRM`, `OptCSRM`. In the tree this join is sequentialized due to block structure; in POWL it is exact.

Approximation paragraph: This tree cannot represent the non-block-structured cross-branch dependencies exactly. It **over-constrains** by forcing the entire `ARC`-subtree (`DCA`, `RiskChoice`, `OptCS`) to complete before the trial loop starts, contrary to rules 6–7 which allow `RiskChoice` and `CS` to overlap `PV/DCA` and the trial cycle and require only `PVDCA` before `ET`. Concretely: (i) `SR/QR/RR  ET` is enforced though intended `Approvals || Trial`; (ii) `CS  ET` is enforced though intended `CS || Trial` with only `CSRM`; (iii) `Approvals` and `CS` are artificially synchronized with `PV/DCA` via the outer `((CM,PV),(ARC,…))`  subsequent `SEQ`, so `PV||RiskChoice` is partly lost. The model remains safe (never allows `ET` before `PV/DCA`, never allows `RM` before approvals/trial) but **under-constrains flexibility**: allowed traces where approvals or supplier consultation interleave with or follow the start of the trial are excluded. A permissive alternative would place `RiskChoice` and `OptCS` in `` with `Trial` after the `PVDCA` join, but then approvals would be forced to start after `PVDCA` rather than after `ARC` alone. Duplicating visible labels (e.g. duplicating `QR/RR/SR` in both pre-trial and trial-parallel positions) could admit both early and late starts but introduces duplicate-label ambiguity, double-counting, and unsound conformance diagnostics; it is therefore deliberately avoided here.

# 4. PM4Py POWL Model
Compact POWL description:

```text
POWL = StrictPartialOrder(
  nodes = {
    RD = Register Deviation,
    CM = Contain Material,
    ARC = Analyze Root Cause,
    PV = Plan Verification,
    DCA = Design Corrective Action,
    RiskChoice = XOR( SR=Supervisor Review, High=PO(QR=Quality Review, RR=Regulatory Review) ), // High: PO with no edges => QR||RR
    OptCS = XOR( CS=Consult Supplier,  ),
    TrialLoop = LOOP( Body=PO(ET=Execute Trial  IT=Inspect Trial), Redo=AP=Adjust Parameters ),
    RM = Release Material,
    AC = Archive Case
  },
  order = {
    RDCM, RDARC,
    CMPV,
    ARCDCA, ARCRiskChoice, ARCOptCS,
    DCATrialLoop, PVTrialLoop,
    TrialLoopRM, RiskChoiceRM, OptCSRM,
    RMAC
  }
)
// Absence of edge = concurrency (e.g. CM||ARC, PV||DCA, PV||RiskChoice, DCA||RiskChoice, RiskChoice||TrialLoop, OptCS||TrialLoop, OptCS||PV/DCA)
```

Self-contained Python (assigns to `powl`, uses required API, explicit edges):

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator  # Operator.XOR, Operator.LOOP

# Visible transitions
rd = Transition(label="Register Deviation")
cm = Transition(label="Contain Material")
arc = Transition(label="Analyze Root Cause")
pv = Transition(label="Plan Verification")
dca = Transition(label="Design Corrective Action")
sr = Transition(label="Supervisor Review")
qr = Transition(label="Quality Review")
rr = Transition(label="Regulatory Review")
cs = Transition(label="Consult Supplier")
et = Transition(label="Execute Trial")
it = Transition(label="Inspect Trial")
ap = Transition(label="Adjust Parameters")
rm = Transition(label="Release Material")
ac = Transition(label="Archive Case")
tau = SilentTransition()  # for optional CS

# High-risk concurrent approvals: PO with no edges => QR || RR
highRiskPO = StrictPartialOrder(nodes=[qr, rr])
# No order added => concurrent, either completion order

# Risk route choice (data abstraction)
riskChoice = OperatorPOWL(operator=Operator.XOR, operands=[sr, highRiskPO])

# Optional supplier consultation: at most once
optCS = OperatorPOWL(operator=Operator.XOR, operands=[cs, tau])

# Trial cycle body ET->IT
trialBody = StrictPartialOrder(nodes=[et, it])
trialBody.order.add_edge(et, it)

# Repeat-until loop: do trialBody, redo ap on failure, exit on pass => AP never after final IT
trialLoop = OperatorPOWL(operator=Operator.LOOP, operands=[trialBody, ap])

# Top-level partial order - all cross-branch dependencies expressed directly
powl = StrictPartialOrder(nodes=[rd, cm, arc, pv, dca, riskChoice, optCS, trialLoop, rm, ac])

# Required precedence edges
powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)
powl.order.add_edge(cm, pv)
powl.order.add_edge(arc, dca)
powl.order.add_edge(arc, riskChoice)
powl.order.add_edge(arc, optCS)
powl.order.add_edge(dca, trialLoop)
powl.order.add_edge(pv, trialLoop)
powl.order.add_edge(trialLoop, rm)
powl.order.add_edge(riskChoice, rm)
powl.order.add_edge(optCS, rm)
powl.order.add_edge(rm, ac)
```

Every required `order.add_edge` is present above.

Why every intentionally unconnected pair may remain concurrent: POWL semantics interprets absence of a (transitive) path as concurrency. This is desired for:

- `CM || ARC`: no edge between them  independent initial streams, either interleaving, overlap.
- `PV || ARC` and `PV || DCA`/`PV || RiskChoice`/`PV || OptCS`: `PV` depends only on `CM`; `DCA/RiskChoice/OptCS` depend only on `ARC`  may overlap verification planning with root-cause analysis, design, approvals, supplier work.
- `DCA || RiskChoice`/`DCA || OptCS`/`RiskChoice || OptCS`: all share predecessor `ARC` but no order between them  design, approvals, supplier consultation may overlap.
- `RiskChoice || TrialLoop` and `OptCS || TrialLoop`: only downstream join is `RM`; no edge to/from `TrialLoop`  approvals and supplier work may overlap the entire trial cycle while still required before release.
- `QR || RR` inside `highRiskPO`: no edge  either completion order, possibly concurrent.
- `ET || RiskChoice` etc. via transitivity: `TrialLoop` internally enforces `ETIT`, but no cross-edge to approvals/CS  trial cycles may interleave with approvals/CS.

All these absences are explicitly intended by rules 2, 6, 7 and the deliberately non-block-structured pattern.

# 7. Preferred Representation and Validation Plan
**Canonical representation: POWL.**

Defense: POWL expresses the non-block-structured pattern directly via a strict partial order. It captures (i) true concurrency of initial streams, (ii) split `CMPV` / `ARCDCA` dependencies, (iii) XOR risk routing with concurrent high-risk reviews, (iv) optional `CS` with `ARCCSRM` yet `CSTrialApprovals`, (v) `Trial` join on `PVDCA` only, and (vi) `ApprovalsTrial` with AND-join at `RM`—all without duplication or exclusion. The tree is retained only as a conservative, easily convertible fallback for engines requiring block structure, at the documented cost of forbidding compliant concurrent approvals/trial. For compliance-critical material-release analysis, fidelity to the AND-join and overlap rules outweighs tree convertibility.

Concrete validation plan:

- **Conversion to accepting Petri net (where supported):**
  ```python

  net_pow, im_pow, fm_pow = pm4py.convert_to_petri_net(powl)  # POWL  net
  net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)  # tree  net
  ```
  Inspect that `powl` conversion succeeds; if unsupported version, fall back to `powl` simulation-based checks. Tree conversion must succeed; compare net size (places/transitions) vs POWL net to quantify approximation cost.

- **Soundness checking of converted nets:**

- **Limitations of the validation plan:**
  - Conversion success  semantic fidelity; syntactic soundness does not prove that partial-order edges match intended business rules—trace tests are essential.
  - Playout is sampling-based and loop-bounded; it cannot prove absence of disallowed behavior, only provide evidence; exhaustive state-space exploration is infeasible for LOOP with unbounded iterations.
  - Conformance via replay on completion-time logs conflates concurrency with interleaving; true simultaneity cannot be distinguished from arbitrary order without start timestamps.
  - Silent transitions (`` for `OptCS`) are invisible in logs; fitness may be 1.0 even if silent routing is mis-modelled, requiring structural inspection of the net.
  - Data conditions (risk level, inspection pass/fail, supplier involvement) are abstracted away; validation cannot detect incorrect XOR resolution frequencies or AP triggered without true failure.

# 8. Final Self-Critique
1. **Semantic residual: inspection outcome is erased.** Both models abstract `Inspect Trial` pass/fail as loop exit vs redo. Business reality distinguishes a failed `IT` (followed by `AP`) from a passed `IT` (followed by `RM`). Without distinct events or data guards, an auditor cannot differentiate a trace where `AP` was correctly triggered by failure from a spurious `AP`, nor verify that the final `IT` was indeed passing. A more precise model would require explicit outcome labels or data-aware guards, at the cost of leaving the activity-based paradigm.

2. **Semantic residual: POWL still idealizes “may overlap” as pure absence of order.** Real material handling has resource constraints: `Contain Material` may physically block `Execute Trial` start, or a single quality engineer cannot perform `QR` and `RR` truly concurrently despite the model allowing it. The POWL model is permissive on concurrency and may admit resource-conflicting interleavings that are operationally infeasible, i.e., slight **underconstraint** from a performance/resource perspective.

3. **Syntactic/analytical limitation: loop boundedness and silent-skip diagnostics remain weak.** The `LOOP(PO(ETIT), AP)` is unbounded; validation relies on bounded playout and cannot prove liveness (eventual passing inspection). Moreover, the tree’s `×(CS,)` introduces a silent transition that may be conflated with other silent constructs during Petri-net conversion, making diagnosis of “supplier not involved” traces ambiguous in conformance dashboards. A log containing no `CS` could be conformant via silent skip even when business expected supplier involvement—silent behavior checks mitigate but do not fully resolve this.
