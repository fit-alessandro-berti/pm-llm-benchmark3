## 2. Processmodel consistency checks  

A validation suite should enforce the following checks for every prediction at `t0` (immediately after **Coverage Check Completed**):

| Check | Description | Implementation | Limitations |
|-------|-------------|----------------|-------------|
| **Prefixtime availability** | Verify that every feature listed in the explanation is computed from events **t0**. | • Create a feature matrix `features_at_t0 = events_with_timestamp <= t0`. <br>• Flag any column not present (e.g., `final_decision`, `risk_score_current`). | Does not address logical impossibility (e.g., reversed activity order). |
| **Activityorder feasibility** | Ensure the causal chain implied by local or sequence explanations respects the process DFG (e.g., “Claim Closed” cannot precede “Damage Assessment Completed”). | • Build a directedgraph of allowed transitions from the normative process (RFC, DFG). <br>• Run a graph walk from the observed prefix to the featurereferenced activity; reject edges not in the graph. | The DFG is a **specification**, not a hard rule; rare exceptions (e.g., parallel investigations) must be explicitly modeled. |
| **Sametimestamp ambiguity** | Detect events sharing exact timestamps and lacking a reliable sequence index; treat them as indeterminate for ordering. | • Identify rows where `timestamp == t0` and `sequence_index` is NULL. <br>• For such rows, either (a) discard the feature, (b) enforce a deterministic tiebreak (e.g., alphabetical event name), or (c) store a separate “parallelprocess” flag. | Tiebreakers may introduce bias; must be documented. |
| **Completetrace usage** | Scan feature definitions for any aggregation over the *full* case trace (e.g., totals, IDs, variant IDs). | • Regex scan of feature pipelines for `FULL_TRACE_` or `COUNT(*) OVER (PARTITION BY claim_id)`. <br>• Mark as “leakage” if not filtered to `<= t0`. | Some tracelevel summaries (e.g., “has ever had a fraud investigation”) can be permissible if the *first occurrence* is captured; finetune accordingly. |
| **Enabledvsfuturepossible** | Verify that the explanation does not assert an activity that is **enabled** at `t0` (can happen) versus **futurepossible** but not yet enabled (e.g., “Appeal will open”). | • For each referenced activity, query the DFG: is there a directed path from the current prefix to that activity? <br>• Flag “futurepossible” as leakage unless the explanation explicitly states “probability of future event”. | This check is complemented by a **probability** qualifier; strict binary decisions may be too restrictive. |
| **Repeat Settlement Decision postappeal** | Confirm that explanations mentioning “Settlement Decision Recorded” after an appeal correctly reference the *second* decision (appealderived) and not the initial decision. | • If the explanation includes a count of `Settlement Decision Recorded` events, verify the count matches the allowed maximum (2). <br>• Ensure the timing respects the process rule (appeal must occur after Partial or Deny). | Does not cover edge cases where a withdrawal occurs before an appeal; needs explicit rule. |

**Execution flow:**  
1. **Load prefix** (Claim Registered  Coverage Check Completed).  
2. **Apply Prefixtime availability**  drop leakage features.  
3. **Run Activityorder feasibility**  reject impossible patterns.  
4. **Check Sametimestamp ambiguity**  flag or reorder.  
5. **Screen Completetrace usage**  enforce timestamp filter.  
6. **Enabledvsfuturepossible**  label as “allowed” or “leakage”.  
7. **Validate repeat decision**  ensure narrative aligns with semantics.

These checks form a **processconformance test** suite that can be automated in a CI pipeline to guard against drift in both feature definition and process updates.

## 3. Alternative feature interpretations  

| Classification | Surviving or repairable signals | What may be claimed | What **cannot** be claimed |
|----------------|--------------------------------|---------------------|----------------------------|
| **Defensible predictive signal** | `queue_length_at_t0`, `initial_damage_complexity`, `claimant_region`, `calendar_week` (after fairness audit), `elapsed_since_registration_at_t0` | These features, when properly timestamped, can be used to predict breach probability **without implying causation**. They reflect current system load, claim difficulty, geographic risk, seasonal effects, and age of claim. | They **cannot** be used to prescribe operational actions (e.g., “increase staff”) without additional costbenefit analysis. |
| **Processstate or congestion signal** | `queue_length_at_t0`, `num_document_requests_total` (if filtered), `full_trace_variant_id` (prefix version), `same_day_document_count_snapshot` (if presnapshot) | Indicate realtime system pressure or typical pathway, useful for **alerting** and **capacity planning**. | They **cannot** be interpreted as direct causes of delay; they are *observed* states, not *drivers*. |
| **Proxy requiring fairness/robustness review** | `claimant_region`, `calendar_week` (drift proxy), `initial_reserve` (if not att0) | Offer baseline risk stratification but must be examined for **disparate impact** on protected groups. | Claims of *“region drives claim severity”* must be backed by statistical parity analysis; otherwise they risk bias. |
| **Drift / calendar proxy** | `calendar_week` | Captures seasonal policy changes; can improve model calibration during those periods. | Should not be used as a **standalone** predictor for breach without accounting for underlying policy shifts. |
| **Usable only after lineage repair** | `total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team`, `risk_score_current`, `last_resource_role`, `full_trace_variant_id` (completetrace), `prior_claim_count_before_t0` (SQL fix needed) | Once the lineage fixes (e.g., correct timestamps, proper subqueries) these features become admissible **only for postclosure** analyses. | They **cannot** appear in any earlytime explanation; they remain “postmortem” features. |

**Interpretation notes**

- **Predictive validity** requires that the feature be observable **at or before** the prediction instant and that its relationship to breach be statistically robust (e.g., via SHAP).  
- **Causal interpretation** is prohibited unless the feature is part of a rigorously designed experiment or a welljustified process rule (e.g., “queue length affects processing time”).  
- **Operational actionability** stems from a *policy* that can be enacted (e.g., “reduce queue length” if a causal link is established). Purely predictive signals are insufficient.  
- **Fairness review** demands that any proxy (region, week) be examined for disparate impact and possibly mitigated (e.g., reweighting).

## 5. Recommendations for explanation validation  

**Prioritized Plan**

1. **Featurestore Governance**  
   - **Timestamp Enforcing Schema**: Mandate a `recorded_at` column for every feature; enforce that `recorded_at <= prediction_timestamp`.  
   - **Versioning & Lineage**: Tag each feature with the pipeline version that generated it; store a “definition snapshot” to detect drift automatically.  

2. **PrefixOnly Recomputation**  
   - Build a **dedicated “earlytime” feature bundle** that is recomputed **immediately before** each batch of predictions, guaranteeing that only `t0` events are included.  
   - Automate rerun on any schema change (e.g., addition of a new fulltrace flag).  

3. **ProcessConformance Tests** (as described in Section2)  
   - Integrate the **seven checks** into the nightly CI pipeline.  
   - Produce a **daily audit report** highlighting any violations; set thresholds (critical=block, high=alert).  

4. **Lineage Repair & Feature Redefinition**  
   - **Immediate actions**:  
     - Replace `total_case_duration_hours`, `appeal_seen_anywhere`, `final_handler_team`, `risk_score_current`, `last_resource_role`, `full_trace_variant_id` with **historical equivalents** if available, otherwise **remove** them from earlytime models.  
     - Correct `prior_claim_count_before_t0` SQL to `< t0`.  
   - **Mediumterm**:  
     - Develop a **prefixderived variant ID** that captures the first few steps (Coverage  FastTrack vs Evidence Loop) and retains it for risk modeling.  
     - Create an **earlytime proxy for reserve** (`estimated_reserve_at_registration`) to substitute for the postclosure amount.  

5. **Calibration & Explanation Stability**  
   - After any feature removal, **recalibrate** the model (e.g., Platt scaling) to maintain probability interpretation.  
   - Run **explanation drift monitoring**: compare SHAP importance distributions across consecutive prediction windows; flag large shifts.  

6. **Proxy / Fairness Review**  
   - Schedule **quarterly fairness audits** for region, calendar week, and any other protected attribute.  
   - Apply **disparate impact analysis** and, if necessary, **reweight** or **drop** the proxy.  

7. **Monitoring for Schema / Process Drift**  
   - **Automated alerts** on new events (e.g., introduction of “Policy Change” flag) that could invalidate existing patterns.  
   - **Periodic businessprocess reviews** (e.g., every six months) to ensure the DFG matches operational reality; update the conformance tests accordingly.  

8. **Documentation & Governance**  
   - Maintain a **living “Explanation Governance Charter”** that records:  
     - Which features are permissible at `t0`.  
     - The narrative style (predictive vs causal).  
     - Accountability owners for each feature flag.  
   - Publish **model cards** that list provenance, intended use, limitations, and fairness considerations for each predictive model.
