## 1. Decision rule

### 1.1 Eligibility gate (all conditions must hold)

| Criterion | Rule |
|---|---|
| **Process stage** | Case must be at or before `Diagnosis Complete`. Cases at `Resolution Work` or later are ineligible regardless of predicted risk. |
| **Slot availability** | Total interventions today  (available slots  reserve). The default reserve is 1 slot; the duty manager may override to 0 only in writing. |
| **Alert novelty** | A case is eligible on its *first* alert. On a *second* alert it is eligible only if no swarm has been issued since the prior alert. On a *third or later* alert it is eligible **only** if a materially new event (new data source, customer upload, severity reclassification) has occurred since the last alert *and* no swarm has been issued since that event. Pure model-refresh repeats without new data are logged but suppressed from the action queue. |
| **Data quality** | Cases with imputed or missing live features are eligible but receive a data-quality penalty in scoring (see below). Cases whose only signal is an imputed feature and whose risk jump is entirely explained by the imputation are flagged for manual review before a slot can be committed. |

### 1.2 Calibration adjustments to predicted probability

The raw model output `p_now` is an observational prediction. Before using it in any calculation, apply a segment-specific bias correction derived from recent back-tests. These corrections represent the *best available estimate* of direction and magnitude but are themselves uncertain; the policy should track residual calibration error over time.

| Segment | Back-test finding | Adjustment to `p_now` | Confidence in adjustment |
|---|---|---|---|
| SME | Under-predicts by 0.04–0.09 | **Add 0.065** (midpoint) | Moderate (small validation sample) |
| Strategic Enterprise | Over-predicts by 0.05–0.12 | **Subtract 0.085** (midpoint) | Moderate-high (recent workflow redesign may still be settling) |
| Public Sector | Broadly acceptable | **No correction** | Moderate (moderate sample size) |
| Non-Native-Language Support | Unknown direction and magnitude | **No correction, but apply a ±0.10 uncertainty band** | Low (sparse sample, both calibration and effects uncertain) |

The adjusted probability `p_adj` is used for all downstream calculations. It is **not** treated as the true breach probability; it is the current best central estimate.

### 1.3 Causal discount on intervention effect ranges

The supplied "estimated absolute risk reduction from a swarm" ranges are derived from observational or quasi-experimental analysis. They are **not** guaranteed causal effects. To guard against optimistic bias, each range is multiplied by a segment-specific causal-reliability factor before taking the midpoint or bounds:

| Segment | Causal-reliability factor | Rationale |
|---|---|---|
| SME | 0.80 | Reasonable calibration but small intervention-effect sample |
| Strategic Enterprise | 0.75 | Model over-prediction suggests effects may also be overstated; workflow redesign is recent |
| Public Sector | 0.85 | Acceptable calibration; moderate sample |
| Non-Native-Language | 0.65 | Sparse sample; both calibration and effect estimates are unreliable |

Define `p_adj` = midpoint of the supplied range × causal-reliability factor. Define `p_low` and `p_high` analogously for scenario analysis.

### 1.4 Priority score

For each eligible case *i*, compute the expected net direct value of the swarm:

```
PS_i = p_adj_i × V_i  C_swarm  (1  p_adj_i) × B_i
```

where:
- `V_i` = value of avoiding breach
- `C_swarm` = €450 (fixed swarm cost)
- `B_i` = false-alarm burden for case *i* (incurred when the swarm is triggered but the case would not have breached)
- `(1  p_adj_i)`  probability the intervention is a false alarm

Then apply modifiers:

```
PS_adjusted_i = PS_i × DQ_i × TE_i × NH_i
```

| Modifier | Values | Meaning |
|---|---|---|
| **DQ** (data quality) | 1.0 if all features complete; **0.70** if a key feature is imputed; 0.50 if the segment has sparse calibration | Penalizes unreliable signals |
| **TE** (time eligibility) | 1.0 if the case has  2 hours to deadline AND is at Triage or Diagnosis Started with room for the 45-min swarm to take effect; **0.50** if < 2 hours to deadline at Triage (insufficient downstream time); 0.00 if past Diagnosis Complete | Accounts for whether intervention can plausibly help |
| **NH** (novelty/history) | **1.0** for first alert or any alert with materially new data; **0.0** for a repeated alert with no new event and no prior swarm (suppress); **0.5** for a repeated alert with no new event but where a prior swarm *was* already delivered (forbidden from re-swarming anyway) | Prevents mechanical re-alerting from consuming capacity |

### 1.5 Minimum thresholds and portfolio constraints

- **Individual threshold:** A case must have `PS_adjusted > €0` in the base scenario to be eligible for a slot. This ensures each intervention has positive expected value on its own terms before considering spillover.
- **Marginal spillover test:** Before allocating the *k*-th slot, subtract the estimated marginal spillover cost of that slot from the candidate's `PS_adjusted`. If the result is negative, do not allocate that slot to that candidate. Marginal spillover per slot  6 affected diagnosis-stage cases × 0.02 (midpoint) × average breach value of affected cases.
- **Reserve rule:** Default is 1 slot held in reserve. The duty manager may reduce the reserve to 0 only for cases where `PS_adjusted > €5,000` AND the case is within 2 hours of Diagnosis Complete.
- **Portfolio cap:** No more than 3 slots used on a single shift unless all 4 candidates have `PS_adjusted > €3,000` and the marginal spillover test passes for each.

### 1.6 Priority ordering for allocation

After filtering by eligibility and thresholds, rank candidates by `PS_adjusted` descending. Allocate slots greedily, applying the marginal spillover test at each step. Stop when slots are exhausted or no remaining candidate passes the marginal test.

### Key observation

The portfolio is net positive in the base and optimistic scenarios but negative in the adverse scenario. This asymmetry is driven by two factors:

1. **Spillover is a fixed cost per slot regardless of whether the direct intervention works.** Even if a swarm fails, it still consumes specialist time and delays other cases. This means the *downside of a wasted slot is amplified by the spillover externality.*

2. **I-02 is the most fragile selection.** If the SE calibration issue is worse than modeled, or if the case's breach was driven by factors the swarm cannot address, the slot is wasted. However, I-02 is time-critical (3h buffer, Diagnosis Started): not acting also has a cost (likely breach at p_adj  0.575, value €25k, expected loss  €14,375 without intervention).

The expected value of intervening on I-02 (base case: +€2,120 direct) is lower than the expected loss from not intervening (expected breach cost = 0.575 × 25,000 = €14,375). Even after accounting for the possibility of the swarm failing, the *opportunity cost of inaction* supports the intervention.

**Sensitivity note:** If the average breach value of spillover-affected cases is lower than €12,000 (e.g., €8,000), the base-case spillover drops to €2,880 and the net rises to +€6,288. If higher (e.g., €18,000), spillover rises to €6,480 and the net drops to +€2,688. The policy is moderately sensitive to this parameter, which should be monitored.

## 4. Repeated alerts and temporal policy

### 4.1 Alert lifecycle

```
New alert fires
    
     First alert on this case?  Eligible (score normally)
    
     Prior alert exists AND materially new event since last alert?
           YES  Eligible (score normally)
           NO   Is this a model-refresh repeat (same inputs)?
                   YES  SUPPRESS: log, do not present to decision-maker
                   NO   Has a swarm been issued since last alert?
                           YES  SUPPRESS (re-swarm forbidden)
                           NO   LOW PRIORITY: score with NH = 0.5
    
     Prior swarm exists AND materially new event?
            YES  RE-ENTRY: eligible (score normally, but flag for duty manager approval)
            NO   FORBIDDEN: log only
```

### 4.2 Cool-down rules

| Rule | Parameter | Rationale |
|---|---|---|
| **Suppression cool-down** | If a model-refresh repeat fires within 30 minutes of a prior identical alert (same p ± 0.02, same stage, no new data), it is suppressed for 2 hours. | Prevents alert fatigue from the 30-min refresh cadence. |
| **Re-entry cool-down** | After a swarm is delivered, the case enters a 4-hour cool-down during which new alerts are suppressed UNLESS a materially new event occurs (customer upload, severity change, new error code). | Prevents re-swarming on stale signals; respects the "normally forbidden" rule. |
| **Escalation cool-down** | If a suppressed case's `p_now` increases by  0.10 relative to the last *actionable* alert, the suppression is overridden and the case re-enters the eligible pool. | Prevents suppression from masking genuine deterioration. |

## 5. Fairness and feedback-loop risks

### 5.1 Value-based prioritization may starve lower-value cases

The priority score multiplies risk reduction by breach value. This means a high-value Strategic Enterprise case (I-08, €100k) can dominate even with low risk reduction and high uncertainty, while a lower-value SME case (I-07, €5k) with higher risk reduction and better calibration is perpetually deprioritized.

**Concrete safeguards:**

- **Reserve one "equity slot" per shift** (when total slots  4): dedicate one slot to the highest-PS case among segments with below-median breach value, provided PS > €0. In this shift, this would mean ensuring SME cases are not systematically excluded. Today, the SME cases (I-05, I-07, I-10) are excluded for substantive reasons (suppression, time constraint, lower PS), not purely value-based starvation. But over many shifts, the pattern could emerge.

- **Track slot allocation by segment over rolling 30-day windows.** If any segment receives fewer than its "share" of interventions (proportional to its share of breach-risk-adjusted case volume) for two consecutive windows, trigger a management review.

- **Cap the value multiplier.** Consider capping `V_i` in the priority score at the 90th percentile of the portfolio's breach-value distribution. This prevents extreme-value cases from monopolizing slots while still allowing value to influence ranking. For this portfolio, the cap would be ~€60,000, which would reduce I-08's PS from €3,275 to ~€1,960 (closer to I-01's level), making the allocation more balanced.

### 5.2 Uncertainty for Non-Native-Language Support (I-09)

I-09 is the only case in the NNL segment. The calibration and intervention-effect estimates are both unreliable. Applying a conservative DQ penalty (0.50) and causal-reliability factor (0.65) reduces its PS to €941, effectively excluding it from the active portfolio.

**Risk:** If the NNL model is *under*-predicting (as SME models do), I-09 may be at higher risk than shown, and the intervention may be more effective than discounted. The policy could systematically under-serve NNL cases.

**Concrete safeguards:**

- **Treat NNL as a "shadow SME" for calibration purposes** until a dedicated back-test is completed. Apply the SME adjustment (+0.065) as a floor for `p_adj`, and use the SME causal-reliability factor (0.80) instead of 0.65 if the case involves a language pair for which any historical intervention data exists.

- **Mandate manual specialist review** (not a formal swarm) for any NNL case with `p_now > 0.60` within 3 hours of deadline. This provides a lower-cost intervention pathway that does not consume a swarm slot.

- **Flag I-09 for the duty manager** with a note: "NNL segment — calibration uncertain. Current PS is €941 after penalties. If any corroborating signal emerges (e.g., specialist confirms difficulty communicating with customer), recommend immediate escalation regardless of PS."

### 5.3 Differential calibration across segments

The calibration corrections (§1.2) are point estimates of a range. SME under-prediction could be as low as 0.04 or as high as 0.09; SE over-prediction could be 0.05 or 0.12. This means:

- A case at `p_now = 0.55` in the SME segment has a true breach probability somewhere in [0.59, 0.64].
- A case at `p_now = 0.55` in the SE segment has a true breach probability somewhere in [0.43, 0.50].

At equal `p_now`, the SME case is at *higher* actual risk. The policy correctly applies different adjustments, but the *width* of the uncertainty band differs by segment. SE's band is wider (±0.035 around the correction), which means SE cases' priority scores have higher variance.

**Concrete safeguards:**

- **Report priority scores with confidence intervals.** For this shift, I-04's PS ranges from approximately €3,800 (lower bound of effect, pessimistic calibration) to €10,200 (upper bound, optimistic calibration). Decision-makers should see this range, not just the point estimate.

- **Flag any segment where the calibration correction has not been updated in > 90 days** as "stale." For SE specifically, the recent workflow redesign means the correction may change rapidly; schedule a re-backtest within 30 days.

### 5.4 Selective intervention changes future training labels

If the policy intervenes on high-risk cases, those cases are *more likely to be resolved on time* (if the intervention works). This creates a biased training set: the model learns that cases with features resembling I-04 and I-02 tend to have lower breach rates — but only because they were intervened upon. Untreated cases retain their "natural" breach outcomes.

Over time, this feedback loop will cause the model to **under-predict breach risk for cases that look like past intervention candidates**, leading to fewer alerts for those case types — precisely the cases where intervention is most valuable.

**Concrete safeguards:**

- **Log every intervention decision** (including the counterfactual: "would have been intervened upon but for the slot constraint") and tag the outcome with the intervention status. Use this tagged data for a separate "intervention-adjusted" model that estimates breach probability *conditional on no intervention* (the causal estimand).

- **In the short term**, apply a "feedback adjustment" to `p_now` for cases that closely resemble past intervention targets: if a case's feature vector is within a Mahalanobis distance of 1.5 from a recently intervened case's features, flag it for manual review of whether the model is under-predicting due to feedback contamination.

- **Periodically retrain** the model on a "what-if" dataset: for intervened cases, use the model's pre-intervention prediction as the counterfactual breach probability rather than the observed outcome. This preserves the signal in the training data.

### 5.5 Spillover harms may systematically fall on untreated groups

The spillover from swarming increases breach probability for 6 non-intervened diagnosis-stage cases. If the diagnosis queue is disproportionately populated by certain segments (e.g., SME cases are more numerous but lower value), those segments bear the spillover cost while higher-value SE cases receive the intervention benefit.

In this shift, the diagnosis-stage cases are I-02 (SE, intervened), I-06 (PS), and I-09 (NNL). If the 4 unlisted diagnosis-stage cases are predominantly SME, the spillover falls disproportionately on SME.

**Concrete safeguards:**

- **Track the distribution of spillover-affected cases by segment** over rolling 30-day windows. If any segment's breach rate increases by more than 2 percentage points relative to its pre-intervention baseline, trigger a review of whether the intervention policy is creating a systematic externality.

- **Where possible, reduce spillover by staggering interventions.** If 2 cases need swarming, deliver them sequentially (45 min apart) rather than simultaneously. This reduces the peak congestion and allows the queue to partially recover. Today's 3 interventions should be staggered: I-04 at 12:15, I-02 at 13:00, I-01 at 13:45 (adjusted based on time criticality — I-02 may need to go first given its 3h buffer).

- **Compensate affected cases proactively.** When a swarm is deployed, automatically flag the 6 affected diagnosis-stage cases for priority monitoring. If any of them breaches and the breach is plausibly attributable to the swarm-induced delay (i.e., the case had < 1 hour of slack before the delay was applied), log it as a "policy-attributable breach" for retrospective cost accounting.

## 6. Monitoring and recalibration plan

### 6.1 Operational monitoring (real-time, per shift)

| Metric | Frequency | Threshold for action |
|---|---|---|
| **Slot utilization rate** | Per shift | If > 75% of available slots are used for 5 consecutive shifts, the reserve policy may be too aggressive — review whether the minimum-PS threshold should be raised. |
| **Alert volume** | Per shift | If average alert volume exceeds 15 per shift, the model may be over-triggering. Review calibration and consider raising the alert threshold. |
| **Suppression rate** | Per shift | If > 40% of alerts are suppressed (repeated-unchanged), the refresh cadence is too frequent or the alert threshold is too low. |
| **Intervention-to-diagnosis latency** | Per case | Track time from swarm completion to Diagnosis Complete. If this latency is increasing, the swarm may be less effective at accelerating diagnosis (possible process drift). |
| **Spillover-affected case breach rate** | Per shift | Compare breach rate of non-intervened diagnosis-stage cases in shifts with  2 interventions vs. shifts with 0–1 interventions. If the difference exceeds 5 percentage points, the spillover model is under-estimating. |

### 6.2 Predictive monitoring (weekly)

| Metric | Method | Action trigger |
|---|---|---|
| **Segment-level calibration** | Brier score and calibration curves by segment, computed weekly on the past 7 days of outcomes | If any segment's calibration error exceeds the back-test estimate by > 0.03 for 2 consecutive weeks, update the calibration correction. |
| **Probability stability** | Track the distribution of `p_now` for each segment. If the mean shifts by > 0.05 in a week, investigate whether the model is drifting or the case mix is changing. | If drift is confirmed, accelerate re-training. |
| **Priority score distribution** | Monitor the distribution of PS_adjusted across segments. If one segment's median PS is consistently < 50% of the portfolio median, investigate whether the calibration or effect estimates are suppressing that segment. | Adjust calibration or causal-reliability factor if evidence supports it. |

### 6.3 Causal-effect monitoring (monthly)

This is the most critical and most difficult monitoring task. The goal is to estimate the *actual causal effect* of the swarm intervention, separate from the model's observational predictions.

| Method | Description | Timeline |
|---|---|---|
| **Regression discontinuity on PS threshold** | Cases just above and just below the intervention threshold are similar in observable characteristics but differ in treatment. Compare their breach outcomes. This provides a local average treatment effect (LATE) estimate. | Begin after 50+ cases have been scored near the threshold (est. 2–3 months). |
| **Slot-constraint natural experiment** | On shifts where more cases exceeded the threshold than slots were available, the "marginal" case (highest PS among untreated) is a natural control for the "infra-marginal" case (lowest PS among treated). Compare outcomes. | Begin after 30+ such shifts (est. 2–4 months). |
| **Randomized reserve slot** | On 10% of shifts (randomly selected), do not hold a reserve slot — use all 4 slots. On another 10%, hold 2 reserve slots instead of 1. Compare portfolio-level breach rates across conditions. This measures the marginal value of an additional slot, including spillover. | Implement within 1 month; analyze after 50+ shifts per condition. |
| **Instrumental variable: congestion shocks** | Use exogenous variation in queue length (e.g., due to upstream incidents, time of day, or staffing fluctuations) as an instrument for whether a swarm was delivered. Cases that happen to be assessed when the queue is shorter are more likely to receive a swarm. | Requires careful identification; begin analysis after 3+ months of data. |

### 6.4 Capacity monitoring (daily)

| Metric | Action |
|---|---|
| **Specialist utilization** | Track the fraction of specialist time spent on swarms vs. regular diagnosis. If swarm time exceeds 25% of total specialist capacity, the intervention policy is crowding out normal work. Reduce the number of daily slots or add specialist capacity. |
| **Queue delay attribution** | For each diagnosis-stage case that breaches, decompose the delay into: (a) inherent case complexity, (b) swarm-induced queue delay, (c) other. If (b) accounts for > 15% of total delay across breaches, the spillover is too costly and the slot cap should be reduced. |
| **Regulatory incident frequency** | Track how often the reserved slot is actually needed for regulatory incidents. If the reserve is used < 20% of shifts, consider reducing the reserve to 0 on a permanent basis (while maintaining the override capability). |

### 6.5 Fairness monitoring (monthly)

| Metric | Method | Action trigger |
|---|---|---|
| **Intervention rate by segment** | Compute the fraction of eligible cases that receive a swarm, by segment, adjusted for case volume and risk level. | If any segment's intervention rate is < 50% of the rate predicted by its risk profile alone (i.e., after controlling for PS), investigate whether the calibration or effect penalties are too harsh for that segment. |
| **Breaches attributable to spillover, by segment** | Track which segments' cases are in the diagnosis queue when swarms are deployed and whether their breach rates are elevated. | If one segment accounts for > 50% of spillover-attributable breaches despite being < 30% of diagnosis-queue volume, the spillover is regressive. Consider segment-specific slot caps or priority adjustments. |
| **Outcome label contamination rate** | Estimate the fraction of training labels that are contaminated by intervention (i.e., cases where the observed outcome  the counterfactual outcome under no intervention). | If > 15% of labels are contaminated, the model's predictive accuracy will degrade. Accelerate the causal-adjustment retraining plan. |
| **NNL case outcomes** | Track all NNL cases' outcomes regardless of whether they were intervened upon. Compare breach rates to the model's predictions. | If NNL cases breach at rates significantly different from predictions (> 10 pp), update the NNL calibration correction and re-evaluate the DQ and causal-reliability penalties. |

### 6.6 Decision to change the threshold or allocation rule

The policy should be formally reviewed and potentially revised when any of the following occur:

1. **Calibration drift:** Any segment's weekly calibration error exceeds the current correction by > 0.03 for 3 consecutive weeks  update correction and recompute PS for all cases.

2. **Effect-size revision:** New causal-effect estimates (from §6.3 methods) differ from the current causal-reliability factors by > 25%  update the causal discount factors.

3. **Spillover model revision:** Observed spillover differs from the 0.01–0.03 per-case-per-slot model by > 50%  update the spillover parameters and re-run the marginal spillover test.

4. **Capacity change:** If specialist headcount changes, or if the average swarm duration changes by > 10 minutes, update the slot cap and congestion model.

5. **Fairness alert:** Any fairness trigger from §6.5 fires  convene a review panel (operations, data science, customer management) within 5 business days to assess whether the allocation rule needs structural change.

6. **Quarterly policy review:** Regardless of triggers, conduct a full review every quarter. This includes: re-estimating all calibration corrections, causal discounts, spillover parameters, and fairness metrics; assessing whether the priority-score formula weights should be re-tuned; and evaluating whether the reserve-slot policy remains appropriate.
