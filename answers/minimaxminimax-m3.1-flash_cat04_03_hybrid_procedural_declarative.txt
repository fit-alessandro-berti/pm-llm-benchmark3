```python
def _plans(node, seq_, base):
    """All match plans of `node` inside seq_[base:].

    A plan is a tuple (end, indices): `end` is the position just after the last
    consumed event, `indices` is the tuple of consumed positions (in order).
    """
    label = getattr(node, "_label", None)
    children = list(getattr(node, "_children", []) or [])
    if label in (SILENT, "", None):
        return {(base, ())}
    if children:
        if label == "+":
            current = {(base, ())}
            for child in children:
                nxt = set()
                for end, idx in current:
                    for e2, idx2 in _plans(child, seq_, end):
                        nxt.add((e2, idx + idx2))
                current = nxt
            return current
        if label == "x":
            out = set()
            for child in children:
                out |= _plans(child, seq_, base)
            return out
        if label == "o":
```

```python
    out = []
    for (a, b), (mu, sigma) in temporal_profile.items():
        deltas = []
        for case_id, g in df.sort_values("timestamp").groupby("case_id"):
            ta = g.loc[g.activity==a, "timestamp"].tolist()
            tb = g.loc[g.activity==b, "timestamp"].tolist()
```

```python
from pm4py.objects.process_tree import ProcessTree

SILENT = "tau"   # invisible branch (no event emitted)

# ---------------------------------------------------------------- builders
def _attach(parent, child):
    """Attach child to parent, tolerating PM4Py minor API differences."""
    add = getattr(parent, "add", None)
    if callable(add):
        try:
            add(child)
            return
        except TypeError:
            pass
    parent._children.append(child)
    child._parent = parent

def _node(label, children=()):
    t = ProcessTree(label=label)
    for c in children:
        _attach(t, c)
    return t

def act(a):            return _node(a)
def seq(*c):           return _node("+", c)
def par(*c):           return _node("o", c)
def exc(*c):           return _node("x", c)
def loop(body):        return _node("*", (body,))
def opt(node):         return exc(node, _node(SILENT))
```

## 1.2 The R5 / R6 conflict

* **R5 (Legal):** "after `Sanctions Escalation`, `Obtain Legal Opinion` **must precede** `Activate Vendor` **under all circumstances**."
* **R6 (Operations):** "emergency activation **may** occur before `Obtain Legal Opinion`, but only when jointly authorized **outside the event log**; the opinion must then arrive within 24 hours."

These are **not** jointly satisfiable as written: R5 quantifies over *all circumstances*, R6 asserts a circumstance in which the order is inverted. R6 is therefore not a refinement of R5 but a *contradiction* of it, and — critically — the discriminator between the two policies is **not present in the event log** (A8). No activity-only formalism can decide which policy applies to a given case, because the deciding evidence is external.

Three resolutions were considered.

### Resolution 1 — "Legal-strict" (R5 is the law, R6 is a documented deviation)
`precedence(Obtain Legal Opinion, Activate Vendor)` is a hard, unconditional constraint in DECLARE and in the Log Skeleton. An activation before the opinion is a violation. The emergency path exists only as a *manual waiver* handled outside the automated pipeline (a waiver must be attached to the case before the pipeline will pass it; if the pipeline sees no waiver, it fails closed).
*Compliance risk:* legitimate emergency activations (e.g., a low-value vendor with a payment deadline, sanction match pending legal review) become false rejections. Operationally this creates pressure to reclassify sanction cases as low risk — i.e. it *increases* sanctions risk, which is the opposite of the intent of R5. It also creates an incentive to suppress the `Sanctions Escalation` event, since escalation is what triggers the precedence rule.

### Resolution 2 — "Operations-lenient" (R6 is a conditional exception; R5 is demoted)
The precedence is demoted to a *best-practice flag*; the hard rules become (i) the 24-hour opinion deadline and (ii) a mandatory manual evidence check. Any activation-before-opinion case is routed to a review queue rather than rejected.
*Compliance risk:* the control becomes "trust the actor". Because the log contains no emergency attribute and no authoriser identity, **every** pre-opinion activation is unverifiable from the log; the exception degenerates into "whoever fires the event". This is the classic unverifiable-exception failure mode: the "joint authorisation outside the log" is never reconciled back to the case.

### Resolution 3 — "Evidence-gated exception" (hybrid; **implemented**) 
The two policies are **not** merged. They are kept as two *labelled, versioned* branches with a single decision point:

* **Default (normative) policy** = R5. The precedence constraint stays in DECLARE and in the Log Skeleton as a hard rule. This is what the automated pipeline enforces.
* **Exception policy** = R6, *narrowed* to an evidenced, time-boxed deviation. The exception is **not** encoded as a DECLARE/skeleton rule (no activity-only formalism can express it); it is evaluated in the attribute-aware layer, which requires a case attribute `emergency_authorization = {authorized: bool, reference: str, authorizers: [2 distinct ids], authorized_at: ts}` plus the 24-hour deadline measured from the activation timestamp.
* **Fail-closed default.** If the attribute is missing or incomplete, the case is treated as an **unevidenced** R5 violation (legal-strict outcome) — it is *not* silently passed, and it is *not* silently waived.
* A waived case is reported as `conformant under waiver R6 (reference …)`, never as plain `pass`, so that the population of waived activations is auditable.

*Compliance risk of the chosen resolution:* it is only as good as the **external waiver register**. If that register is not reconciled with the event log (e.g. by case id), the exception path becomes un-auditable and the model silently degrades into Resolution 2. Mitigations built into the design: (a) every waived case is counted and reported separately; (b) the waiver reference is mandatory so the register can be joined; (c) a "waiver without event" reconciliation job runs in the opposite direction (register entry  case must exist and must contain an activation). Residual risk: the 24-hour deadline is evaluated on *start* timestamps only (A1), so an opinion "started" at +23h59m and finished at +30h would be accepted.

## 1.3 Other interpretive decisions (non-conflicting)

* **R2** is split: the *negative* half ("never both approvals", "no approval in a rejected case") is a clean activity-level constraint and is encoded declaratively; the *positive* half ("exactly one approval in an accepted case") is a **conditional cardinality over a set**, which no activity-only template can express — it is delegated to the attribute-aware layer.
* **R3**'s "before the next clarification request" is a *pairing* condition ("response must fall between two consecutive requests"). DECLARE's `altresponse` would forbid multiple cycles and `chainresponse` would over-constrain adjacency; neither is used. The condition is enforced in the attribute-aware layer using timestamps.
* **R11**'s "another `Verify Bank Account` must occur before any later `Release First Payment`" is an *at-least-one-occurrence-in-between* constraint. It is not expressible in DECLARE, in a process tree, or in a Log Skeleton, because none of them can talk about counts between two activities. It is delegated to the attribute-aware layer.

# 3. Procedural Backbone

## 3.1 Compact formal description

Notation: `` sequence, `` parallel, `×` exclusive choice, `` zero-or-more loop, `?` optional (silent  branch), `[]` loop body.

```
Receive Onboarding Request
   ( [Capture Master Data  Run Sanctions Screening  Verify Bank Account]      [Request Clarification  Receive Clarification] )
   Classify Risk
   ( Sanctions Escalation )?
   ×
       [Request Clarification  Receive Clarification]  Reject Vendor  Close Onboarding
       [Clarification]  Manager Approval  [Clarification]  Activate Vendor  Release First Payment  Close Onboarding
       [Clarification]  Enhanced Due Diligence  Compliance Approval  [Clarification]  Activate Vendor  Release First Payment  Close Onboarding
```

Semantics in words: the case starts with a single intake event; the three intake checks run concurrently while zero or more clarification cycles may run in parallel with them; the clarification loops must all be closed before the corresponding terminal step; classification needs all three checks; escalation may be raised immediately after classification; exactly one of three mutually exclusive routes is taken; the low-risk route needs `Manager Approval`, the high-risk route needs `Enhanced Due Diligence`  `Compliance Approval`; activation follows the applicable approval, payment follows activation, close follows rejection or payment.

**Disclosed approximations** (block-structure limits):
1. **Clarification cycles are positional.** The tree offers a clarification loop *during intake* (parallel to the three checks) and *inside each outcome branch* (before the approval, and between approval and activation). A cycle raised after activation, or one interleaved *inside* the three-check block in a way the parallel shuffle cannot express, is not representable  the declarative layer (R3) and the external pending-clarification check are the safety net for those positions.
2. **`Obtain Legal Opinion`, `Change Bank Details` and `Suspend Vendor` are modelled as "side activities"** that the procedural matcher tolerates and reports but does not positionally constrain, because their admissible position is exactly what R5/R6/R11 make conditional. Their ordering is therefore owned by DECLARE and the external layer, not by the tree.
3. **Post-activation change management is deliberately excluded** from the procedural backbone (§3.4).

## 3.2 Self-contained PM4Py code

```python
"""
Canonical procedural model for CONTROLLED VENDOR ONBOARDING.
Artifact: pm4py.objects.process_tree.ProcessTree  ->  variable `procedural_model`
The conformance matcher below is part of this model package because PM4Py does not
ship a stable public process-tree conformance API; its semantics are documented
(strict contiguity for sequences, arbitrary shuffle for parallel, backtracking XOR/loop).
"""
from pm4py.objects.process_tree import ProcessTree

SILENT = "tau"          # invisible branch: consumes no event

# ------------------------------------------------------------------ builders
def _label_of(node):
    for attr in ("_label", "label"):
        v = getattr(node, attr, None)
        if v is not None:
            return v
    return None

def _children_of(node):
    for attr in ("_children", "children"):
        v = getattr(node, attr, None)
        if v is not None:
            return list(v)
    return []

def _attach(parent, child):
    add = getattr(parent, "add", None)
    if callable(add):
        try:
            add(child)
            return
        except TypeError:
            pass
    parent._children.append(child)
    child._parent = parent

def _node(label, children=()):
    t = ProcessTree(label=label)
    for c in children:
        _attach(t, c)
    return t

def act(a):        return _node(a)
def seq(*c):       return _node("+", c)     # "+"  = sequence
def par(*c):       return _node("o", c)     # "o"  = parallel
def exc(*c):       return _node("x", c)     # "x"  = exclusive choice
def loop(body):    return _node("*", (body,))# "*"  = zero-or-more loop
def opt(node):     return exc(node, _node(SILENT))

# ------------------------------------------------------------------- model
CLARIFICATION = seq(act("Request Clarification"), act("Receive Clarification"))

procedural_model = seq(
    act("Receive Onboarding Request"),
    par(
        par(
            act("Capture Master Data"),
            act("Run Sanctions Screening"),
            act("Verify Bank Account"),
        ),
        loop(CLARIFICATION),                       # clarification cycles during intake
    ),
    act("Classify Risk"),
    opt(act("Sanctions Escalation")),              # optional, after classification (A6)
    exc(
        seq(loop(CLARIFICATION),
            act("Reject Vendor"), act("Close Onboarding")),
        seq(loop(CLARIFICATION),
            act("Manager Approval"), loop(CLARIFICATION),
            act("Activate Vendor"), act("Release First Payment"), act("Close Onboarding")),
        seq(loop(CLARIFICATION),
            act("Enhanced Due Diligence"), act("Compliance Approval"), loop(CLARIFICATION),
            act("Activate Vendor"), act("Release First Payment"), act("Close Onboarding")),
    ),
)

# Activities whose *position* is governed by conditional policy (R5/R6/R11),
# not by the routing backbone. They are reported, not positioned.
SIDE_ACTIVITIES = {"Obtain Legal Opinion", "Change Bank Details", "Suspend Vendor"}

# ----------------------------------------------------------------- matcher
def _free(node, seq_, base):
    """Plans of `node` inside seq_[base:]; the first consumed index may be > base.
       A plan is (end_position, tuple_of_consumed_indices)."""
    label, kids = _label_of(node), _children_of(node)
    if label in (SILENT, "", None):
        return {(base, ())}
    if kids:
        if label == "+":
            cur = {(base, ())}
            for child in kids:
                nxt = set()
                for end, idx in cur:
                    for e2, i2 in _free(child, seq_, end):
                        nxt.add((e2, idx + i2))
                cur = nxt
            return cur
        if label == "x":
            out = set()
            for child in kids:
                out |= _free(child, seq_, base)
            return out
        if label == "o":
            return _parallel_plans(kids, seq_, base)
        if label == "*":
            out, frontier = {(base, ())}, {(base, ())}
            while frontier:
                nxt = set()
                for end, idx in frontier:
                    for e2, i2 in _free(kids[0], seq_, end):
                        if i2:
                            nxt.add((e2, idx + i2))
                nxt -= out
                out |= nxt
                frontier = nxt
            return out
    return {(i + 1, (i,)) for i in range(base, len(seq_)) if seq_[i] == label}

def _strict(node, seq_, base):
    """Like _free, but the node's first consumed event must be exactly at `base`."""
    label, kids = _label_of(node), _children_of(node)
    if label in (SILENT, "", None):
        return {(base, ())}
    if kids:
        if label == "+":
            cur = {(base, ())}
            for child in kids:
                nxt = set()
                for end, idx in cur:
                    for e2, i2 in _strict(child, seq_, end):
                        nxt.add((e2, idx + i2))
                cur = nxt
            return cur
        if label == "x":
            out = set()
            for child in kids:
                out |= _strict(child, seq_, base)
            return out
        if label == "o":
            return _parallel_plans(kids, seq_, base)
        if label == "*":
            out, frontier = {(base, ())}, {(base, ())}
            while frontier:
                nxt = set()
                for end, idx in frontier:
                    for e2, i2 in _strict(kids[0], seq_, end):
                        if i2:
                            nxt.add((e2, idx + i2))
                nxt -= out
                out |= nxt
                frontier = nxt
            return out
    return {(base + 1, (base,))} if base < len(seq_) and seq_[base] == label else set()

def _parallel_plans(kids, seq_, base):
    """Parallel = arbitrary interleaving: the union of the children's index sets must be
       exactly the contiguous region [base, end)."""
    child_plans = [_free(k, seq_, base) for k in kids]
    results = set()
    def rec(i, used, end):
        if i == len(kids):
            if end > base and set(used) == set(range(base, end)):
                results.add((end, tuple(sorted(used))))
            return
        for e2, idx2 in child_plans[i]:
            if not set(idx2).isdisjoint(used):
                continue
            rec(i + 1, used | set(idx2), max(end, e2))
    rec(0, set(), base)
    return results

def procedural_check(events):
    """events: list of (activity, timestamp) in timestamp order for ONE case.
       Returns (conformant: bool, report: dict)."""
    stripped, sides = [], []
    for a, t in events:
        (sides if a in SIDE_ACTIVITIES else stripped).append((a, t))
    labels = [a for a, _ in stripped]
    ok = any(end == len(labels) and set(idx) == set(range(len(labels)))
             for end, idx in _strict(procedural_model, labels, 0))
    return ok, {"side_activities": sides, "stripped": stripped}
```

## 3.3 Explanation of the modelled behaviour

* **Concurrency.** The three intake checks form one parallel block; the parallel semantics is an arbitrary interleaving (shuffle) of the three single-activity branches, so `T2`'s order *screening  verify  capture* is accepted even though the tree lists *capture  screening  verify*. The clarification loop runs as a **parallel sibling** of the check block, so a clarification cycle may be opened while screening is still running *or* after all three checks have finished, but it must be **closed before `Classify Risk`** (this is what makes T5 non-conformant at the procedural level).
* **Choices.** After classification there is one exclusive choice with three branches. Because it is a choice and not a sequence, the model *structurally* forbids `Activate Vendor` and `Reject Vendor` in the same case (R1) and forbids `Enhanced Due Diligence` together with `Manager Approval` (R8). Note the low-risk branch cannot be taken together with the high-risk branch, so `Manager Approval` and `Compliance Approval` are structurally exclusive (R2, first half).
* **Clarification loops.** A loop is `[Request Clarification  Receive Clarification]`: zero or more *completed* cycles. A cycle whose response never arrives cannot be exited, so it blocks the rest of the case — exactly the T5 defect. A loop placed *in parallel* with the checks models "clarification while the checks run"; loops placed inside the outcome branches model "clarification after classification but before the terminal step" and "clarification between approval and activation". The response must be the **immediately following** activity of the request inside the loop body (strict contiguity) — a conservative reading of R3's "before the next clarification request".
* **Terminal outcomes.** Each branch ends in `Close Onboarding`; the low- and high-risk branches end with `Release First Payment` after `Activate Vendor`. There is no path that both rejects and activates, and no path that closes without an outcome.
* **Post-activation behaviour — deliberately excluded.** `Change Bank Details` / `Suspend Vendor` / re-verification (R11) are **not** in the procedural backbone. Reasons: (i) the backbone is declared stable and does not contain change management; (ii) the R11 semantics ("a change *after activation*", "a later payment") is a *conditional, count-based* obligation that a block-structured tree cannot express without duplicating the whole post-activation branch; (iii) modelling it would break the backbone statement "Close Onboarding follows either rejection or first payment" (a suspended case closes after a suspension). R11 is therefore owned by DECLARE (`response` for the suspension) and by the external layer (the re-verification counting rule). The activities are tolerated by the matcher as **reported side activities**, so a case containing them is still checked by the other three layers.

### 4.1 Rule-by-rule semantics

| Template & pair | Direction / semantics | Requirement | Notes & limitations |
|---|---|---|---|
| `existence(Receive Onboarding Request)` | unary; activity must occur 1× | backbone 1 | — |
| `existence(Close Onboarding)` | unary; must occur 1× | backbone 5 | — |
| `init(Receive Onboarding Request)` | unary; the activity must be the **first** event of the trace | backbone 1 | Stronger than existence; fails if any other activity precedes intake |
| `exactly_one((Activate Vendor, Reject Vendor))` | **set** cardinality: exactly one of the two activities occurs in the whole trace | R1, backbone 4 | Fails T8 (both). Deliberately *not* `exactly_one(("Manager Approval","Compliance Approval"))`: that would reject every rejected case (T3) |
| `responded_existence((Request Clarification, Receive Clarification))` | binary; **a  b occurs somewhere in the trace** (existence, not order) | R3 | This is the rule that catches T5. It is *not* vacuous when the request occurred |
| `responded_existence((Sanctions Escalation, Obtain Legal Opinion))` | a  b exists | R4 | — |
| `responded_existence((Change Bank Details, Suspend Vendor))` | a  b exists | R11 | — |
| `coexistence((Enhanced Due Diligence, Compliance Approval))` | binary; **a  b and b  a** (both or neither) | backbone 4 (high-risk route) | Detects an "abandoned EDD" case. Confidence 0.9: assumes EDD is only performed on the high-risk route (A4) |
| `response((Request Clarification, Receive Clarification))` | binary; **every** occurrence of a is followed (later, not necessarily immediately) by b | R3 | Strictly weaker than `chainresponse`; deliberately chosen so that several cycles are allowed (see §4.2) |
| `response((Sanctions Escalation, Obtain Legal Opinion))` | every escalation is eventually followed by an opinion | R4 | — |
| `response((Change Bank Details, Suspend Vendor))` | every change is eventually followed by a suspension | R11 | With `activ_freq` allowing up to 2 changes, this implies one suspension per change — the strict reading of R11 |
| `precedence((Run Sanctions Screening, Sanctions Escalation))` | binary; **if both occur, a is before b** (b may not precede a) | R7 | Ordering only, no existence implication |
| `precedence((Obtain Legal Opinion, Activate Vendor))` | if both occur, the opinion is before the activation | **R5** | **Policy switch:** under Resolution 2 this pair must be removed (and the skeleton pair too) — otherwise the model contradicts R6. | `precedence((Receive Clarification, Activate Vendor))` | if both occur, the response precedes the activation | R3 | **Vacuous** when no clarification occurred; it cannot detect a *missing* response — that is why T5 additionally needs `responded_existence` and the external pending check |
| `precedence((Receive Clarification, Reject Vendor))` | same, for the reject outcome | R3 | — |
| `succession((Enhanced Due Diligence, Compliance Approval))` | **response + precedence**: every EDD is followed by a compliance approval, and a compliance approval can only occur after an EDD | backbone 4 | — |
| `succession((Manager Approval, Activate Vendor))` | every manager approval leads to an activation; no activation without a preceding manager approval *in the ordering sense* | backbone 4/5 | Note: it does **not** imply that an activation requires a manager approval (that is the conditional part of R2, handled externally) |
| `succession((Compliance Approval, Activate Vendor))` | same for the high-risk route | backbone 4/5 | — |
| `succession((Activate Vendor, Release First Payment))` | every activation is followed by a payment | backbone 5, R10 | **Known tension** with R11's suspension path (activation  change  suspend  close, no payment). Flagged in §9 |
| `succession((Reject Vendor, Close Onboarding))` | every rejection is followed by a close | backbone 5 | — |
| `succession((Release First Payment, Close Onboarding))` | every payment is followed by a close | backbone 5 | — |
| `altresponse((Sanctions Escalation, Obtain Legal Opinion))` | every escalation is followed by an opinion **and** no escalation occurs after an opinion (no second cycle) | R4 + A7 | Consistent with `activ_freq {0,1}`. **Not** used for clarification, because it would forbid multiple clarification cycles |
| `noncoexistence((Activate Vendor, Reject Vendor))` | the two never occur in the same trace | R1 | Same fact as `exactly_one` — the `exactly_one` version additionally requires *one* of them (completeness) |
| `noncoexistence((Manager Approval, Compliance Approval))` | never both | R2, R8 | — |
| `noncoexistence((Manager Approval, Reject Vendor))` | never both | R2 | — |
| `noncoexistence((Compliance Approval, "Reject Vendor"))` | never both | R2 | — |
| `noncoexistence((Enhanced Due Diligence, Manager Approval))` | never both | R8 | — |
| `nonsuccession((Reject Vendor, Release First Payment))` | **adjacency-level**: the payment must not *immediately* follow a rejection | R1/R2 hygiene | Much weaker than `noncoexistence`; a rejection and a payment separated by other events would pass it — hence the `noncoexistence`/`never_together` companions |
| `nonsuccession((Activate Vendor, Reject Vendor))` and the reverse | the two terminal outcomes must not directly follow each other | R1 | T8 violates the first (Reject@10 directly follows Activate@9) |

### 4.2 Why `chainresponse` / `altresponse` / `chainprecedence` are **not** used for clarification

* `chainresponse(Request Clarification, Receive Clarification)` would require the response to be the **immediately next** event. R3 allows other work between request and response, so this over-constrains (false positives).
* `altresponse(Request Clarification, Receive Clarification)` forbids any request that follows a response — i.e. it forbids **several cycles**, which R3 explicitly permits ("Several request/response cycles are possible").
* The precise requirement ("the response must fall *between* two consecutive requests, and before the final outcome") is a *pairing* constraint that DECLARE cannot express; it is delegated to the attribute-aware layer (§7).
* `chainprecedence`/`chainsuccession` were considered for the "opinion before activation" rule, but `precedence` is the correct template there because the *distance* between opinion and activation is unconstrained (only the order matters).

### 5.1 Orientation conventions (every pair)

* **`always_before`**: `(a, b)` means **a always precedes b** whenever both occur in a trace. This is the same orientation as PM4Py's skeleton discovery output.
* **`always_after`**: populated with the **transpose** of `always_before`, i.e. `(x, y)  always_after`  *y always precedes x*. This is the orientation PM4Py's discovery produces when it derives `always_after` from `always_before`. If a build interprets `always_after` in the opposite orientation, the pair list must be negated; the *verdicts* are unchanged, because the two relations are mutual transposes.
* **`never_together`**: `(a, b)` is an **unordered** co-occurrence prohibition — the pair is written once; `(a,b)` and `(b,a)` are equivalent.
* **`activ_freq`**: maps an activity to the **set of allowed occurrence counts**; `0` must be listed explicitly for optional activities.
* **`directly_follows`**: `(a, b)` = b **directly** follows a (adjacent events).

### 5.2 Justification and layer interactions

* **`equivalence` is empty on purpose.** Log-Skeleton equivalence means two activities occur in a strict 1:1 correspondence in every trace. That is *not* the relation between `Manager Approval` and `Compliance Approval` — they are **exclusive alternatives**, not equivalents (using `equivalence` for them would be a category error and would silently permit one approval to substitute for the other). No two activities in this process are 1:1-correlated across all traces (e.g. `Activate Vendor` and `Release First Payment` co-occur only in accepted cases, while `Close Onboarding` occurs in rejected cases too).
* **Overlap with the procedural layer.** Every `always_before` pair and every `never_together` pair is a projection of the process tree's routing; the skeleton is therefore a *derived* artefact and should be generated from the tree, not maintained by hand (see §10). Its independent value is `activ_freq`, which the tree expresses only implicitly.
* **Overlap with DECLARE.** `always_before(("Obtain Legal Opinion","Activate Vendor"))` duplicates `precedence`; `never_together` duplicates `noncoexistence`. These duplications are deliberate as a *regression* net: the skeleton is cheap to check and catches model drift.
* **Disagreement 1 — conditional obligations.** The skeleton has **no** conditional cardinality. It cannot express "if a request occurred, a response must occur", so **T5 passes the skeleton and fails DECLARE**. This is a structural blind spot, not a contradiction.
* **Disagreement 2 — the emergency exception.** Under Resolution 2, `always_before(("Obtain Legal Opinion","Activate Vendor"))` becomes *wrong* and would produce a false positive for a properly authorised emergency activation. It must be removed together with the DECLARE `precedence` pair, as one atomic policy-version change.
* **Disagreement 3 — loops.** `always_before(("Change Bank Details","Suspend Vendor"))` assumes the change precedes the suspension. With `activ_freq` allowing two changes, a second change *after* a suspension flips the order and violates the pair. Either cap `Change Bank Details` at `{0,1}` or drop this pair and rely on DECLARE `response` (recommended: keep the pair, cap the count at 1, and let the external layer handle repeated changes).
* **`directly_follows` is deliberately minimal.** `("Activate Vendor","Release First Payment")` is **not** asserted, because R11 explicitly permits an intervening bank-change / re-verification cycle between activation and payment; asserting the adjacency would contradict R11. The two terminal adjacencies are asserted because no activity can intervene there under any rule.
* **`activ_freq` for `Verify Bank Account` = {1, 2}** is the only place in the whole model where the *second* occurrence of an activity is explicitly allowed; it is the skeleton-level expression of R11's re-verification requirement.

# 6. Temporal Profile

```python
# Model mean / standard deviation in SECONDS (PM4Py's temporal profile expects seconds).
temporal_profile = {
    ("Request Clarification", "Receive Clarification"):   (48 * 3600, 24 * 3600),   # 172800 s, 86400 s
    ("Sanctions Escalation", "Obtain Legal Opinion"):      (12 * 3600,  6 * 3600),   #  43200 s, 21600 s
    ("Activate Vendor", "Release First Payment"):         (72 * 3600, 36 * 3600),   # 259200 s, 129600 s
}
zeta = 2.0
```

**Rule used for the flags** (stated explicitly because PM4Py's internal variant differs): for every profiled pair, collect the elapsed time from each occurrence of the first activity to the **next** occurrence of the second activity in the same case; the pair is flagged when
`|observed_mean  model_mean| > zeta × model_`.
The **model**  is used as the tolerance band (with one observation per case, the *observed*  is 0 or undefined and would turn every non-exact match into a flag). PM4Py's `pm4py.conformance_temporal_profile(log, temporal_profile, zeta=2.0)` is still called for cross-checking; §7 shows both.

| Pair | Band (2) | T1 | T2 | T3 | T4 | T5 | T6 | T7 | T8 |
|---|---|---|---|---|---|---|---|---|---|
| `Request Clarification  Receive Clarification` | 48 h ± 48 h  0–96 h | n/e | 26 h (22 h) **pass** | n/e | n/e | no response  n/e | n/e | n/e | n/e |
| `Sanctions Escalation  Obtain Legal Opinion` | 12 h ± 12 h  0–24 h | n/e | n/e | n/e | n/e | n/e | 17 h (+5 h) **pass** | **34 h (+22 h)  warning** | n/e |
| `Activate Vendor  Release First Payment` | 72 h ± 72 h  0–144 h | 71 h (1 h) **pass** | 84 h (+12 h) **pass** | n/e | 61 h (11 h) **pass** | 71 h (1 h) **pass** | 77 h (+5 h) **pass** | 2 h (70 h) **pass** (0.97  of tolerance) | n/e |

### 6.1 Why temporal deviations are warnings, not control-flow violations

1. **The policy says so.** R12 explicitly defines the table as "normative enough to flag but not automatically reject".
2. **The statistic is not estimable per case.** With one case per trace, the *observed* mean is a single observation and the observed  is undefined; a "deviation" is therefore an outlier flag, not a statistical test. Using it as a hard rule would reject cases that are perfectly conformant in control flow (T7's opinion is correctly ordered and correctly caused).
3. **Different semantics from control flow.** A deviation says "this pair was slower than we expected", not "the process was done wrong". Mixing the two would make the reporting layer's severity hierarchy meaningless.
4. **Interaction with the emergency exception.** Under R6 the opinion must arrive within **24 h** — a *hard deadline*. Note that the temporal profile's expectation (12 h ± 12 h) and the R6 deadline (24 h) are different instruments: the deadline belongs in the attribute-aware layer as a pass/fail check, the profile as a warning. T6 satisfies both (17 h, inside the 2 band); T7 satisfies the ordering (R5) but violates the *profile* (34 h) — and would also violate the R6 deadline if it had been an emergency activation (34 h > 24 h).
5. **Ordering of evaluation.** Temporal flags are computed *after* the hard checks and are attached to the case as annotations, so that a case that already fails control flow is not additionally "sentenced" for being slow.

# 7. Resource- and Data-Aware Checks

Required attributes: event-level `case_id`, `activity`, `timestamp` (start), `resource`; case-level `emergency_authorization{authorized, reference, authorizers[], authorized_at}` (optional but expected). PM4Py's default `resource` attribute name is `resource`; case attributes live in `log.cases[case_id].attributes`.

```python
import pandas as pd
import pm4py

# ---------------------------------------------------------------- utilities
def to_frame(log):
    df = log.to_dataframe() if hasattr(log, "to_dataframe") else pm4py.convert_to_dataframe(log)
    df = df.rename(columns={"concept:name": "activity", "time:timestamp": "timestamp",
                            "case:concept:name": "case_id"})
    if "case_id" not in df.columns:
        df = df.rename(columns={"case:concept:name": "case_id"})
    df["timestamp"] = pd.to_datetime(df["timestamp"], utc=True)
    return df.sort_values(["case_id", "timestamp"]).reset_index(drop=True)

def resource_available(df):
    return "resource" in df.columns and df["resource"].notna().all()

def case_attrs(log):
    return {cid: dict(getattr(case, "attributes", {}) or {})
            for cid, case in getattr(log, "cases", {}).items()}

def _tidy(series):
    return series.dropna().sort_values()

# ------------------------------------------------- R9: segregation of duties
def four_eyes_violations(df, activity1, activity2):
    """Cases in which the SAME resource performs both activities."""
    if not resource_available(df):
        return {"status": "not evaluated",
                "reason": "event attribute 'resource' missing or partially null",
                "cases": set()}
    a = df.loc[df.activity == activity1, ["case_id", "resource"]]
    b = df.loc[df.activity == activity2, ["case_id", "resource"]]
    m = a.merge(b, on="case_id", suffixes=("_a", "_b"))
    bad = m[m.resource_a == m.resource_b]
    return {"status": "evaluated", "cases": set(bad.case_id),
            "detail": bad[["case_id", "resource_a", "resource_b"]].to_dict("records")}

def four_eyes_pm4py(log, activity1, activity2):
    """PM4Py cross-check: removes cases where the two activities share a resource."""
    kept = pm4py.filter_four_eyes_principle(log, activity1, activity2)
    return set(log.case_id) - set(kept.case_id)

R9_PAIRS = [("Verify Bank Account", "Manager Approval"),
            ("Verify Bank Account", "Compliance Approval"),
            ("Capture Master Data", "Activate Vendor")]

def check_r9(df, log=None):
    findings = []
    for a1, a2 in R9_PAIRS:
        res = four_eyes_violations(df, a1, a2)
        for cid in sorted(res["cases"]):
            findings.append({"case_id": cid, "requirement": "R9", "rule": f"{a1} != {a2}",
                             "severity": "violation"})
        if res["status"] != "evaluated":
            findings.append({"case_id": "*", "requirement": "R9",
                             "rule": f"{a1} != {a2}", "severity": "not evaluated",
                             "reason": res["reason"]})
    return findings

# ------------------------------------- R5 / R6: legal opinion vs emergency path
def check_emergency_waiver(log, policy="evidence_gated", window_hours=24):
    """policy: 'legal_strict' | 'operations_lenient' | 'evidence_gated' (default)."""
    df, attrs = to_frame(log), case_attrs(log)
    rows = []
    for cid, g in df.groupby("case_id"):
        activate = opinion = None
        for a, t in zip(g.activity, g.timestamp):
            if a == "Activate Vendor":        activate = t
            if a == "Obtain Legal Opinion":   opinion = t
        if activate is None:
            continue
        waiver = attrs.get(cid, {}).get("emergency_authorization")
        if opinion is not None and opinion < activate:
            rows.append({"case_id": cid, "verdict": "pass",
                         "reason": "R5 precedence satisfied; no waiver needed"})
            continue
        # activation precedes the opinion  ->  emergency path
        if waiver is None:
            verdict = "fail" if policy in ("legal_strict", "evidence_gated") else "warning"
            rows.append({"case_id": cid, "verdict": verdict, "waived": False,
                         "reason": "activation before legal opinion and NO recorded joint "
                                   "authorisation (fail-closed)"})
            continue
        ok = (bool(waiver.get("authorized")) and waiver.get("reference")
              and len(set(waiver.get("authorizers") or [])) >= 2)
        if not ok:
            rows.append({"case_id": cid, "verdict": "fail", "waived": False,
                         "reason": "waiver present but incomplete: need authorized=True, "
                                   "reference, and >= 2 distinct joint authorizers"})
            continue
        if opinion is None:
            rows.append({"case_id": cid, "verdict": "fail", "waived": False,
                         "reason": f"legal opinion missing; {window_hours}h deadline expired"})
            continue
        delta_h = (opinion - activate).total_seconds() / 3600.0
        if delta_h > window_hours:
            rows.append({"case_id": cid, "verdict": "fail", "waived": False,
                         "reason": f"opinion arrived {delta_h:.1f}h after activation "
                                   f"(> {window_hours}h)"})
        else:
            rows.append({"case_id": cid, "verdict": "pass", "waived": True,
                         "reason": f"R6 emergency waiver {waiver.get('reference')} honoured; "
                                   f"opinion after {delta_h:.1f}h (<= {window_hours}h)"})
    return pd.DataFrame(rows)

# ------------------------------------------- R2 / R10: outcome & approval counts
def check_outcome_counts(df):
    rows = []
    for cid, g in df.groupby("case_id"):
        c = g.activity.value_counts().to_dict()
        n_act, n_rej = c.get("Activate Vendor", 0), c.get("Reject Vendor", 0)
        n_mgr, n_cmp = c.get("Manager Approval", 0), c.get("Compliance Approval", 0)
        n_pay, n_appr = c.get("Release First Payment", 0), n_mgr + n_cmp
        problems = []
        if n_act + n_rej != 1:
            problems.append("terminal outcome is not exactly one of Activate/Reject")
        if n_appr > 1:
            problems.append("more than one approval in the case")
        if n_act == 1 and n_appr != 1:
            problems.append("activated case without exactly one approval (R2)")
        if n_rej == 1 and n_appr != 0:
            problems.append("rejected case carries an approval (R2)")
        if n_pay > 1:
            problems.append("Release First Payment occurred more than once (R10)")
        if n_act > 1 or n_rej > 1:
            problems.append("Activate/Reject occurred more than once (R10)")
        rows.append({"case_id": cid, "verdict": "fail" if problems else "pass",
                     "problems": problems})
    return pd.DataFrame(rows)

# ------------------------------- R3: clarification must be answered in time
def check_pending_clarification(df):
    rows = []
    for cid, g in df.groupby("case_id"):
        reqs = _tidy(g.loc[g.activity == "Request Clarification", "timestamp"])
        resp = _tidy(g.loc[g.activity == "Receive Clarification", "timestamp"])
        outcomes = _tidy(g.loc[g.activity.isin(["Activate Vendor", "Reject Vendor"]), "timestamp"])
        first_outcome = outcomes.iloc[0] if len(outcomes) else None
        problems = []
        for i, t_req in enumerate(reqs):
            next_req = reqs.iloc[i + 1] if i + 1 < len(reqs) else None
            bound = first_outcome
            if next_req is not None and (bound is None or next_req < bound):
                bound = next_req
            good = resp[(resp > t_req) & (resp < bound)].size > 0 if bound is not None \
                   else (resp > t_req).any()
            if not good:
                problems.append(f"Request Clarification at {t_req} not answered before "
                                f"the next request / the final outcome")
        rows.append({"case_id": cid, "verdict": "fail" if problems else "pass",
                     "problems": problems})
    return pd.DataFrame(rows)

# ------------------------------------------------- R11: change management
def check_change_management(df):
    rows = []
    for cid, g in df.groupby("case_id"):
        ts = list(zip(g.activity, g.timestamp))
        activate = next((t for a, t in ts if a == "Activate Vendor"), None)
        changes = [t for a, t in ts if a == "Change Bank Details"
                   and (activate is None or t > activate)]
        suspends = [t for a, t in ts if a == "Suspend Vendor"]
        payments = [t for a, t in ts if a == "Release First Payment"]
        verifies = [t for a, t in ts if a == "Verify Bank Account"]
        problems = []
        for t in changes:
            if not any(s > t for s in suspends):
                problems.append(f"bank change at {t} is never followed by Suspend Vendor")
            for p in [p for p in payments if p > t]:
                if not any(t < v < p for v in verifies):
                    problems.append(f"payment at {p} after the bank change at {t} without a "
                                    f"re-verification of the bank account")
        rows.append({"case_id": cid, "verdict": "fail" if problems else "pass",
                     "problems": problems})
    return pd.DataFrame(rows)

# ------------------------------------------------------- R12: temporal flags
def evaluate_temporal_profile(df, temporal_profile, zeta=2.0):
    out = []
    for (a, b), (mu, sigma) in temporal_profile.items():
        deltas = []
        for cid, g in df.groupby("case_id"):
            ta = _tidy(g.loc[g.activity == a, "timestamp"]).tolist()
            tb = _tidy(g.loc[g.activity == b, "timestamp"]).tolist()
            for t in ta:
                later = [x for x in tb if x > t]
                if later:
                    deltas.append((min(later) - t).total_seconds())
        if not deltas:
            out.append({"pair": (a, b), "n": 0, "status": "not evaluated"})
            continue
        obs_mean = sum(deltas) / len(deltas)
        dev = abs(obs_mean - mu)
        status = "warning" if dev > zeta * sigma else "pass"
        out.append({"pair": (a, b), "n": len(deltas), "observed_mean_s": obs_mean,
                    "model_mean_s": mu, "model_sd_s": sigma,
                    "deviation_s": dev, "threshold_s": zeta * sigma, "status": status})
    return pd.DataFrame(out)

# ------------------------------------------------------------- orchestration
def validate_case(log, policy="evidence_gated", temporal_profile=None, zeta=2.0):
    df = to_frame(log)
    report = {
        "procedural": None,                 # filled by the §3 matcher
        "declare": pm4py.conformance_declare(log, declare_model),
        "skeleton": pm4py.conformance_log_skeleton(log, log_skeleton),
        "r9_resource": check_r9(df, log),
        "emergency": check_emergency_waiver(log, policy=policy),
        "counts": check_outcome_counts(df),
        "clarification": check_pending_clarification(df),
        "change_management": check_change_management(df),
    }
    if temporal_profile is not None:
        report["temporal"] = evaluate_temporal_profile(df, temporal_profile, zeta)
    return report
```

### 7.1 Required attributes and missing-attribute behaviour

| Check | Required attributes | If an attribute is missing |
|---|---|---|
| R9 four-eyes (verify  approval; capture  activate) | `resource`, `activity`, `case_id` | Verdict **`not evaluated`** + a data-quality alert. **Never** silently "pass": a missing resource attribute must not be read as "different resources". If only *some* rows lack `resource`, the affected cases are `not evaluated`, the others are evaluated. |
| R9 cross-check via `pm4py.filter_four_eyes_principle` | `resource` (PM4Py default attribute name) | PM4Py silently produces an empty/over-inclusive result if `resource` is absent — therefore the explicit pairwise check above is the authoritative one and the PM4Py call is used only as a cross-check. |
| R5/R6 emergency condition | case attribute `emergency_authorization{authorized, reference, authorizers[2], authorized_at}`; event `timestamp` | With `legal_strict`/`evidence_gated`: **fail closed**  the case is reported as an R5 violation *plus* a data-quality note "no waiver evidence found". With `operations_lenient`: `warning` + mandatory manual review. The chosen policy is recorded with the finding so that the verdict is reproducible. |
| R6 24-hour deadline | event `timestamp` for activation and opinion | `not evaluated` (cannot compute an elapsed time without timestamps). |
| R2 / R10 counting | `activity`, `case_id` | `not evaluated` if activity labels cannot be matched. |
| R3 pending clarification | `timestamp`, `activity` | `not evaluated`; note that DECLARE's `responded_existence` still catches a *missing* response, but not a *late* one. |
| R11 re-verification | `timestamp`, `activity` | `not evaluated`. |
| R12 temporal | `timestamp` | The pair is reported `not evaluated` (no observations). |

# 9. Contradictions, Redundancies, and Blind Spots

### 9.1 Duplicated enforcement across layers
* **R1** is enforced by four independent mechanisms: the procedural exclusive choice, DECLARE `exactly_one` + `noncoexistence`, the skeleton `never_together`, and the external counting check. A single defect therefore yields up to four findings. Mitigation: the reporting layer must key findings on `(requirement_id, earliest_violating_event_timestamp)` and collapse duplicates into one finding with a list of "also detected by" sources. Otherwise users learn to ignore alerts, which is the most expensive failure mode of a compliance tool.
* **R10** (at-most-once) is implied by the tree (each leaf occurs once), by `activ_freq`, and by the external counting check. Keep the skeleton as the *authoritative* owner and let the tree be silent.
* **R7** and the "opinion before activation" rule are each enforced structurally *and* declaratively *and* by the skeleton. The duplication is cheap (skeleton/DECLARE checks are O(trace length)) and worth keeping as a regression net, but only the tree should be considered the *definition*.

### 9.2 Constraints that become inconsistent under loops or post-activation change
* **`always_before(("Change Bank Details","Suspend Vendor"))`** vs. `activ_freq {"Change Bank Details": {0,1,2}}`: two changes with one suspension can invert the order and violate the pair. Fix: cap the count at `{0,1}` or drop the ordering pair and rely on DECLARE `response`.
* **`altresponse(("Sanctions Escalation","Obtain Legal Opinion"))`** forbids a second escalation after the opinion. If re-escalation is business-real, this rule must be relaxed to `response` only — and then `activ_freq` must change too.
* **`succession(("Activate Vendor","Release First Payment"))`** conflicts with the R11 suspension path (activation  change  suspension  close, with no payment). The backbone says "Close follows rejection *or* first payment", so a suspended case has no legal close path. This is a genuine policy hole, not a modelling error: it needs a decision (does a suspended vendor close without a payment?).
* **`chainresponse` would have destroyed the clarification loop** (§4.2): its "b is not directly preceded/followed by a" clause forbids repeated cycles. Any future addition of chain templates must be reviewed against the loop semantics.
* **The emergency exception (R6) is incompatible with the skeleton's `always_before(("Obtain Legal Opinion","Activate Vendor"))` and DECLARE's `precedence` pair.** Keeping one and dropping the other creates a *split-brain* model that reports the same case as conformant and non-conformant. The two must be switched atomically, with a policy version stamped on every finding.

### 9.3 Vacuity in declarative rules
* `precedence(("Receive Clarification","Activate Vendor"))` is **vacuous** whenever no clarification happened, and — worse — it is vacuous *in exactly the case it was meant to catch* (T5 has no response, so the precedence rule cannot fire; only `responded_existence` and the external pending check catch it).
* `responded_existence`/`response`/`coexistence`/`precedence` are vacuous whenever their trigger activity is absent (no escalation  R4/R5 rules are never exercised; no change  R11 rules are never exercised).
* R9's four-eyes rules are vacuous for rejected cases (no approval, no activation) — T3 reports "no resource finding" for a reason that has nothing to do with the case being clean.
* `activ_freq` entries for absent optional activities are satisfied by `0  {0,1}`.
* Consequence: **"no findings"  "compliant"**. Every conformance report must therefore also publish *coverage*: which rules were actually exercised (non-vacuously) for this case, and which were skipped because the trigger activity was absent. A case with 0 findings and 2 exercised rules is not the same as a case with 0 findings and 14 exercised rules.

### 9.4 Missing case attributes
The log contains no case-level attributes at all. Consequently: the R6 emergency authorisation, the joint authorisers, the waiver reference, the risk class (low/high), the organisational unit, the business value, the approval authority level, and the regulatory regime are all invisible. Without the risk class, the "low-risk route" vs "high-risk route" can only be *inferred* from the activities performed, so a case that was mis-classified but processed consistently looks conformant. Without end timestamps, `Close Onboarding` cannot be used to compute cycle time, and "concurrency" cannot be distinguished from "near-simaneity". Recommended additions to the capture process: `case:emergency_authorization` (JSON), `case:risk_class`, `case:business_unit`, `case:approval_matrix_version`, plus event attributes `time:endtimestamp` and `org:unit`.

### 9.5 Timestamp-only limitations
* Start-time-only data means the "12 h escalation  opinion" figure mixes *queueing* with *work time*; a case where the legal department received the escalation at h1 and answered at h13 would be flagged identically to one that sat idle.
* The 24-hour emergency deadline is measured from activation *start* to opinion *start*; an opinion started at +23 h 59 min and finished at +30 h passes the check. This is a real loophole in the deadline as specified and should be closed by using an end timestamp or an explicit "received" timestamp.
* Clock skew across systems (screening vs. legal vs. payments) can manufacture or mask deviations of a few minutes; the 12 h ± 6 h profile is robust to that, the 24 h deadline is not.
* Temporal profiles are computed from *consecutive* occurrences; a second escalation after an opinion would pair differently than expected.

### 9.6 The risk of treating support/confidence metadata as normative truth
`support` and `confidence` are artefacts of **model mining** (how often and how consistently a pattern was observed in a sample log). They are **not** policy weights, and `pm4py.conformance_declare` does **not** read them: the checker is strictly Boolean. Using them as a severity or as a soft threshold would create the illusion of graded compliance ("confidence 0.9  90 % compliant"), which is not a meaningful statement and is actively dangerous in an audit. In this model they are used only as *documentation of assumption strength* — e.g. `confidence 0.9` on `coexistence(("Enhanced Due Diligence","Compliance Approval"))` records "this rule is inferred from a single observation (T2/T6/T7), not from an explicit policy sentence". Enforcement is unaffected: every rule in the dictionary is enforced at full strength or not at all. A stricter governance rule would be to *reject* any model whose rules carry `support`/`confidence` fields, precisely so that nobody can later reinterpret them as risk scores.

### 9.7 Other blind spots
* **Side-activity tolerance can hide a missing mandatory activity.** Because `Obtain Legal Opinion` is stripped before procedural matching, a case with *no* opinion at all would still be procedurally conformant. The obligation is carried solely by DECLARE `responded_existence` — a single point of failure that is not defended by any structural redundancy.
* **The procedural tree cannot see "the same case did two intake rounds".** `Capture Master Data` occurring twice violates `activ_freq {1}` but is invisible to the tree (the second occurrence would simply fail to match).
* **Absence of data is not evidence of compliance.** A case with only two events (`Receive Onboarding Request`, `Close Onboarding`) satisfies `init`, `existence` and most DECLARE rules while violating the entire backbone. The tree catches it; the declarative layers largely do not. This argues for running the procedural check **first** (see §10).

# 10. Deployment Recommendation

### 10.1 Canonical representation and ownership

| Artefact | Role | Who owns it | Change policy |
|---|---|---|---|
| `procedural_model` (ProcessTree) | **Canonical routing definition.** The single normative statement of "what may follow what". | Process owner (Operations) + Compliance sign-off | Versioned; the Log Skeleton is *generated* from it, not maintained by hand |
| `declare_model` | **Authoritative cross-cutting obligation layer** (eventual responses, ordering, exclusivity). | Compliance / Legal | Versioned **together with** the policy resolution (legal-strict vs. operations-lenient); the R5 `precedence` pair and the skeleton counterpart are switched atomically |
| `log_skeleton` | **Derived regression view** + authoritative `activ_freq` (occurrence counts). | Generated from the tree; hand-maintained only for the count allowances | Regenerated on every tree change; never used as the sole source of a finding |
| `temporal_profile` | **Soft expectation set**; produces warnings only. | Ops analytics | Re-estimated quarterly from the log; never used to reject |
| Attribute-aware layer (§7) | **Authoritative** for resources, case attributes, waivers, counting, and "counts between" rules. | Compliance engineering + Internal Audit | The waiver register interface is the critical dependency; it must be reconciled in both directions |

### 10.2 Order of conformance checks

1. **Data-quality gate (blocking).** Verify presence and completeness of `case_id`, `activity`, `timestamp`, `resource`, and — if any case carries an activation-before-opinion pattern — the `emergency_authorization` case attribute. If a required attribute is missing, the case is reported `not evaluated` for the affected checks and a **data-quality ticket** is raised. A missing attribute must never be interpreted as compliance.
2. **Procedural / control-flow conformance** (`procedural_model`). Cheapest, most precise, and it rejects grossly malformed traces (e.g. an intake-to-close case) that would otherwise "pass" the declarative layers vacuously. Produces the case's structural route label (`reject` / `low-risk` / `high-risk`), which the later layers use as context.
3. **DECLARE conformance** (`declare_model`). Produces the cross-cutting obligation findings (R3, R4, R5, R8, R11-obligation).
4. **Log Skeleton conformance** (`log_skeleton`). Cheap regression net; its `activ_freq` findings (R10, R3-count caps) are the authoritative ones; its ordering findings are de-duplicated against DECLARE.
5. **Temporal profile** (`temporal_profile`, `zeta = 2.0`). Computed *after* the hard checks, attached as annotations. A case that already failed control flow is not additionally reported for slowness; a case that passes everything may still carry timing warnings.
6. **Resource / attribute / counting checks** (§7): four-eyes (R9), outcome-and-approval counting (R2, R10), pending clarification (R3), change management (R11), emergency waiver and 24-hour deadline (R5/R6). These are the most expensive and the ones that require external evidence; they must run last because their verdicts are conditional on evidence that may downgrade an earlier hard finding.
7. **Reconciliation job (nightly).** Waiver register  event log (every registered emergency must map to a real case with a pre-opinion activation) *and* event log  waiver register (every pre-opinion activation must map to a registered waiver). This is what keeps Resolution 3 from decaying into Resolution 2.

### 10.3 How contradictory findings must be surfaced

* **One conformance record per case**, with a severity hierarchy: *control-flow violation* > *resource / segregation-of-duties violation* > *cross-cutting obligation violation* > *temporal warning* > *data-quality note*.
* **De-duplication** by `(requirement_id, earliest_violating_event_timestamp)`; the record lists all layers that detected the same defect ("detected by: procedural, DECLARE") so the user sees one finding with multiple confirmations rather than four findings.
* **Explicit status vocabulary** — never a bare "compliant / non-compliant":
  * `conformant` — all exercised rules satisfied;
  * `conformant with waiver (R6, ref …)` — satisfied only because an evidenced, time-boxed exception applied;
  * `violation` — a hard rule was broken (with requirement id, earliest violating event, and the layer that owns the rule);
  * `not evaluable` — required attributes or evidence are missing (with the missing item named);
  * `warning` — a statistical or best-practice deviation;
  * `policy-dependent` — the verdict changes with the R5/R6 resolution in force (T6).
* **Policy version stamping.** Every record carries `policy_version` and `resolution_id` (`legal-strict` / `evidence-gated` / `operations-lenient`). A T6-like case inspected under a different resolution must not silently change its verdict in the dashboard: the record shows *both* the deterministic part (DECLARE rules excluding R5) and the conditional part (R5 + waiver evidence).
* **Never auto-reject on a temporal warning or on a waived case.** Rejection decisions stay with a human reviewer; the tool's job is to present the earliest decisive violation, the supporting evidence, and — where relevant — the *competing* finding (e.g. "R5 precedence violated **but** a joint authorisation exists: route to emergency review, not to rejection").
* **Coverage reporting.** Each case shows which rules were exercised versus skipped, so that "no findings" is never read as "fully compliant" when the case simply never triggered half the rules (§9.3).
