## 2. Competing Explanations and Timeline

### **January–March: Baseline Stability**
- **Process**: Standard variants (V1: 45%, V2: 35%, V3: 20%) with stable breach rates (V1: 0.16, V2: 0.10, V3: 0.30–0.32).
- **Predictive**: AUROC = 0.81–0.82, Brier = 0.13, ECE = 0.02–0.025. Predicted risk (0.18–0.19) matches observed breach (0.18–0.19).
- **Pipeline**: No issues. Labels mature at 100% with 32–34d delay.
- **Hypothesis**: No drift. Model performs as expected.

### **April: Pipeline Catastrophe**
- **Process**: V1 drops to 37%, V2 to 29%, V3 to 16%, but **18% unmapped** due to label renaming (`Initial Diagnosis Completed`  `Diagnostic Assessment Completed`).
- **Predictive**: Mean predicted risk **spikes to 0.28** (vs. 0.19 in March), AUROC drops to **0.67**, Brier to 0.184, ECE to 0.110.
- **Evidence**:
  - `UNKNOWN_ACTIVITY` = 17%, missing queue features = 14%.
  - Pipeline audit confirms **prefix features built incorrectly** due to label mismatch.
  - Observed breach (0.19) aligns with May’s (0.18) after patch, suggesting **no real concept drift**.
- **Hypothesis**: **Pipeline failure** (schema change + caching bug) caused **covariate drift in feature extraction**, not true process/concept drift.
- **Falsification**: If April’s observed breach had been **higher than May’s**, concept drift would be plausible. But it wasn’t.

### **May: Partial Recovery**
- **Process**: Variants return to near-baseline (V1: 43%, V2: 34%, V3: 22%), unmapped drops to 1%.
- **Predictive**: Metrics improve (AUROC = 0.78, Brier = 0.146), but **not fully back to baseline** (ECE = 0.050 vs. 0.022–0.025 in Jan–Mar).
- **Evidence**:
  - Pipeline patch deployed, but **cached features not fully backfilled** (e.g., "number of events before diagnosis").
  - **No process or concept changes** detected.
- **Hypothesis**: **Residual pipeline artifacts** (e.g., stale features) caused **calibration drift**, not true drift.
- **Falsification**: If May’s breach rate had been **higher than April’s**, concept drift would be suspected.

### **June: Routing Policy Change (Process Drift)**
- **Process**: **V2 remote resolution jumps to 52%** due to new routing policy. V1 drops to 30%, V3 stable at 18%.
- **Predictive**: AUROC = 0.79, Brier = 0.139, ECE = 0.060. **Predicted risk (0.20) > observed breach (0.15)**.
- **Evidence**:
  - **No change in V1/V2 breach rates** (V1: 0.16, V2: 0.09).
  - **Remote fix times unchanged** (3.8–4.6h).
  - **No supplier or concept drift** detected.
- **Hypothesis**: **Process drift** (routing shift) caused **covariate drift** (more V2 cases with lower breach risk), but **no concept drift** because the relationship between features and outcomes remained stable for each variant.
- **Falsification**: If V2’s breach rate had **increased**, concept drift would be plausible.

### **July–August: Supplier Concept Drift**
- **Process**:
  - V3 share rises to **35% (July)  42% (August)**.
  - **DFG edge `Order Part  Part Received` degrades**: 65h (July)  130h (August).
- **Predictive**:
  - **August**: Observed breach = 0.28 (vs. 0.19 predicted), AUROC = 0.68, Brier = 0.197, ECE = 0.120.
  - **V3 breach rate spikes to 0.64** (vs. 0.30–0.35 in Jan–June).
- **Evidence**:
  - **Supplier performance** is the only external change.
  - **No pipeline or population shifts** in July–August.
- **Hypothesis**: **Concept drift** in V3 due to **supplier-induced lead-time changes**. The model’s relationship between `Order Part` and breach risk became invalid.
- **Falsification**: If V1/V2 breach rates had also risen, a broader concept drift would be suspected.

### **September: Overlapping Drifts**
- **Process**:
  - **Partner Z onboarded (24% of cases)**, routing **58% to V3** (vs. 36% for others).
  - V3 share = 42%, V1 = 22%, V2 = 36%.
  - **DFG edge `Order Part  Part Received` = 148h** (vs. 130h in August).
- **Predictive**:
  - Observed breach = 0.31, predicted risk = 0.21, AUROC = 0.66, Brier = 0.214.
  - **Partner Z breach rate = 0.45** (vs. 0.27 for others).
- **Evidence**:
  - **Population shift** (Partner Z) + **process drift** (V3-heavy) + **concept drift** (supplier).
  - Missing features (rural distance, device age) likely worsen performance.
- **Hypothesis**: **Overlapping drifts**:
  1. **Population shift** (Partner Z’s higher-risk profile).
  2. **Process drift** (V3 dominance).
  3. **Concept drift** (supplier delays).
- **Falsification**: If Partner Z’s breach rate had been **similar to others**, population shift would be less likely.

### **October: Label Maturity Confounding**
- **Process**: No new process changes.
- **Predictive**:
  - Observed breach = 0.16, predicted risk = 0.23, AUROC = 0.64, Brier = 0.205.
  - **Label maturity = 55%**, median delay = 52d.
- **Evidence**:
  - **Outcome API backlog** affects long-resolution cases (V3-heavy).
  - **Partner Z share = 27%**, but labels are immature.
  - **No stable breach rate estimate** possible.
- **Hypothesis**: **Label delay/censoring** dominates. Observed breach is **not comparable** to mature months.
- **Falsification**: If October’s maturity had been >90%, the observed breach might reflect true drift.

---
**Key Distinctions**:
- **April**: Pipeline failure (not drift).
- **June**: Process drift (routing change)  concept drift.
- **August–September**: Overlapping **concept drift (supplier)**, **process drift (V3)**, and **population shift (Partner Z)**.
- **October**: **Label maturity** confounds all other signals.

## 3. Diagnostic Tests

### **A. Label Maturity and Fixed-Vintage Backtesting**
**Test**:
- Plot **label maturity curves** by month (e.g., % of cases with mature labels at cutoff +30d, +60d, +90d).
- Run **fixed-vintage backtests** (e.g., train on Jan–Mar, test on April–October, stratified by maturity).
**Expected Results**:
- **Under label delay hypothesis**: October’s AUROC/Brier will improve as maturity increases (e.g., +60d cutoff).
- **Under concept drift hypothesis**: August–September’s performance will **not** improve with maturity (true drift persists).

### **B. Pipeline Normalization and Duplicate Cleaning**
**Test**:
- **Recompute April’s features** after:
  1. Normalizing `Initial Diagnosis Completed`  `Diagnostic Assessment Completed`.
  2. Removing duplicates (applied retroactively to April).
  3. Recalculating "events before diagnosis" feature.
- Compare April’s metrics **before/after** fix.
**Expected Results**:
- **Under pipeline failure hypothesis**: April’s AUROC/Brier will **match May’s** after fix.
- **Under concept drift hypothesis**: April’s metrics would still differ from May’s.

### **C. Calibration and Discrimination by Variant/Source**
**Test**:
- Stratify **AUROC, Brier, ECE** by:
  - **Variant** (V1, V2, V3).
  - **Source** (Partner Z vs. others).
  - **Month**.
- Plot **calibration curves** (predicted vs. observed breach) for each group.
**Expected Results**:
- **Under concept drift (V3)**: V3’s calibration will degrade in August–September, while V1/V2 remain stable.
- **Under population shift (Partner Z)**: Partner Z’s calibration will be poor in September–October, but V1/V2 will be unaffected.

### **D. Process Variant and DFG/Performance-DFG Analysis**
**Test**:
- Extract **DFG and performance-DFG** for each month.
- Compare:
  - Median time on `Order Part  Part Received` (supplier performance).
  - Median time on `Diagnosis  Remote Fix` (should be stable).
- Overlay with **breach rates by variant**.
**Expected Results**:
- **Under supplier concept drift**: V3’s breach rate will correlate with `Order Part  Part Received` time.
- **Under routing process drift**: V2’s breach rate will remain stable despite higher volume.

### **E. Outcome Relationship Conditional on Path**
**Test**:
- For each variant, fit a **separate model** on Jan–March data.
- Test on April–October, **conditional on following the same path** (e.g., only V3 cases that ordered parts).
- Compare **AUROC/Brier** to the global model.
**Expected Results**:
- **Under concept drift**: V3’s conditional performance will drop in August–September.
- **Under pipeline failure**: April’s conditional performance will improve after pipeline fix.

### **F. Population Reweighting for Partner Z**
**Test**:
- Use **transport-style reweighting** to adjust Partner Z’s distribution to match non-Partner Z.
- Compare breach rates/predictions **before/after reweighting**.
- Check for **feature overlap** (e.g., rural distance vs. device age).
**Expected Results**:
- **Under population shift**: Reweighting will reduce Partner Z’s breach rate disparity.
- **Under unfairness**: Reweighting will **not** eliminate the gap (indicating missing features).

### **G. Feature Missingness and Lineage Audit**
**Test**:
- Audit **feature provenance** for:
  - `UNKNOWN_ACTIVITY` cases (April).
  - Missing queue features (April).
  - Rural distance/device age (Partner Z).
- Recompute features with **lineage tracking** (e.g., `dlt` or `feast`).
**Expected Results**:
- **Under pipeline failure**: April’s missing features will resolve after fix.
- **Under missing data**: Partner Z’s features will remain missing until added.

### **Model Strategy**
- **Segment-Specific Models**:
  - **V3-only model** for supplier-sensitive cases (retrain monthly).
  - **Global model** for V1/V2 (recalibrate quarterly).
- **Justification**:
  - V3’s concept drift is **supplier-driven** and **isolated**.
  - V1/V2 show **no drift** and can share a model.
- **Risk**: If V3’s drift spreads to V1/V2, a unified model may be needed.

## 5. Monitoring Architecture

### **Design**
The architecture separates **predictive monitoring**, **data quality**, and **process drift** to avoid false alarms. Key components:

1. **Predictive Monitors**:
   - **AUROC/Brier/ECE** by variant/source (daily).
   - **Calibration curves** (weekly).
   - **Predicted vs. observed breach rate** (daily).

2. **Label Maturity Monitors**:
   - **Maturity curves** (e.g., % mature labels at +30d, +60d).
   - **Median label delay** (weekly).
   - **Alert if maturity <80%** (blocks training).

3. **Data Quality Monitors**:
   - **`UNKNOWN_ACTIVITY` share** (>5% triggers audit).
   - **Missing feature rate** (>10% triggers recomputation).
   - **Duplicate event rate** (monthly).

4. **Process Variant Monitors**:
   - **Variant distribution shifts** (e.g., V3 >40% triggers supplier alert).
   - **DFG/performance-DFG** for critical edges (`Order Part  Part Received`).

5. **Population Monitors**:
   - **Partner Z share** (>20% triggers feature audit).
   - **Breach rate by source** (Partner Z vs. others).

6. **Intervention/Deployment Monitors**:
   - **Pipeline changes** (e.g., label renaming).
   - **Supplier performance** (DFG edge delays).

### **Alert Dependencies**
- **Label maturity alarm**  **Blocks training** but does not trigger retraining.
- **Data quality alarm**  **Triggers feature recomputation** before retraining.
- **Concept drift alarm (AUROC drop + calibration error)**  **Triggers variant-specific retraining**.
- **Pipeline failure alarm**  **Excludes affected months from training**.

### **Python Code Sketch**
```python
import pandas as pd
import pm4py
from pm4py.format_dataframe import dataframe_to_eventlog
from pm4py.discovery import discover_dfg, discover_performance_dfg
from pm4py.filtering import filter_time_range
from pm4py.conversion.log import variant_to_df

# Load and normalize data
df = pd.read_csv("field_service_events.csv")
df["diagnosis_activity"] = df["activity"].str.replace(
    "Diagnostic Assessment Completed", "Initial Diagnosis Completed", regex=False
)

# Handle duplicates (April+)
df = df.sort_values(["case_id", "time:timestamp"])
df = df.drop_duplicates(subset=["case_id", "activity"], keep="first")

# Event log for process mining
event_log = dataframe_to_eventlog(df, case_id="case_id", activity_key="activity", timestamp_key="time:timestamp")

# Monthly cohorts
for month in ["2026-01", "2026-02", ..., "2026-10"]:
    # Case-start cohort (all cases starting in month)
    start_cohort = filter_time_range(event_log, start_timestamp=f"{month}-01", end_timestamp=f"{month}-31")

    # Event-calendar cohort (all events in month, regardless of case start)
    calendar_cohort = filter_time_range(event_log, start_timestamp=f"{month}-01", end_timestamp=f"{month}-31")

    # Process discovery
    dfg = discover_dfg(start_cohort)
    perf_dfg = discover_performance_dfg(start_cohort)

    # Variant analysis
    variants = pm4py.get_variants(start_cohort)
    variant_df = variant_to_df(variants)

    # Temporal features
    temporal_features = pm4py.extract_temporal_features_dataframe(start_cohort)

    # Save monthly summaries
    monthly_summary = {
        "month": month,
        "variant_distribution": variant_df["variant"].value_counts(normalize=True).to_dict(),
        "dfg_edges": dfg.edges().to_dict(),
        "performance_dfg": perf_dfg.to_dict(),
        "temporal_stats": temporal_features.describe().to_dict(),
    }
    pd.DataFrame([monthly_summary]).to_csv(f"monthly_audit_{month}.csv")
```

## 6. Risks of Acting on the Wrong Diagnosis

### **1. Retraining on Immature Labels (October)**
**Risk**:
- Using October’s data (55% maturity) to retrain would **bias the model toward false negatives** (underestimating breach risk for long-tail cases).
- **False positive**: Model appears to "improve" due to censoring, but real performance degrades when labels mature.
**Mitigation**:
- **Enforce maturity thresholds** (>90%) before training.
- **Backtest on fixed vintages** (e.g., train on Jan–Aug, test on Sep–Oct).

### **2. Calibrating Around a Pipeline Bug (April)**
**Risk**:
- If April’s pipeline issues were misdiagnosed as **concept drift**, recalibration would **compensate for bad features**, leading to a model that works only for April’s artifacts.
- **False positive**: Model appears calibrated but fails on clean data.
**Mitigation**:
- **Audit feature provenance** before recalibration.
- **Compare April’s metrics before/after pipeline fix**.

### **3. Ignoring Supplier-Driven Concept Drift (August–September)**
**Risk**:
- If V3’s supplier-induced drift was attributed to **population shift (Partner Z)** or **process drift**, the wrong features would be added (e.g., rural distance instead of supplier lead time).
- **False negative**: Model remains miscalibrated for V3.
**Mitigation**:
- **Stratify by variant** before investigating.
- **Test supplier lead-time features** in isolation.

### **4. Attributing Partner Z’s Shift to Unfairness Without Stratified Evidence**
**Risk**:
- If Partner Z’s higher breach rate was assumed to reflect **model bias** without checking:
  - **Process differences** (58% V3 vs. 36% for others).
  - **Supplier performance** (V3’s DFG edge degradation).
  - **Feature overlap** (rural distance vs. device age).
- **False positive**: Model is retrained with unnecessary fairness constraints.
**Mitigation**:
- **Reweight Partner Z’s distribution** to match others.
- **Check if breach rate gap closes** after adjusting for V3 exposure.

---
**Summary**: The strongest approach **triangulates** pipeline issues (April), process changes (June), supplier concept drift (August–September), and label maturity (October) using **stratified diagnostics** and **fixed-vintage backtests**. Acting on a single diagnosis risks misattribution.
