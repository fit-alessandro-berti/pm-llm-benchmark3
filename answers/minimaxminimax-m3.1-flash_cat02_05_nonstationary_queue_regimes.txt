def sse(x):
    x = np.asarray(x, float)
    if len(x) == 0: return 0.0
    m = x.mean()
    return float(((x-m)**2).sum())

def best_single_split(x, min_len=3):
    x = np.asarray(x, float); n = len(x)
    best = None
    for k in range(min_len, n-min_len+1):
        gain = sse(x) - (sse(x[:k]) + sse(x[k:]))
        if best is None or gain > best[1]:
            best = (k, gain)
    k, gain = best
    pre, post = x[:k], x[k:]
    return {"split_index": k, "split_after_date": None, "gain": gain,
            "mean_pre": pre.mean(), "mean_post": post.mean(),
            "cohens_d": (post.mean()-pre.mean())/np.sqrt((pre.var(ddof=1)+post.var(ddof=1))/2)}

Change-point code:

```python
def _seg_sse(x):
    x = np.asarray(x, float)
    return float(((x - x.mean())**2).sum()) if len(x) else 0.0

def _best_split(x, min_len=3):
    x = np.asarray(x, float); n = len(x)
    total = _seg_sse(x); best = (None, -np.inf, None)
    for k in range(min_len, n - min_len + 1):
        gain = total - (_seg_sse(x[:k]) + _seg_sse(x[k:]))
        if gain > best[1]:
            best = (k, gain, x[:k].mean(), x[k:].mean())
    return best

def binary_segmentation(x, dates, max_bp=3, min_len=3):
    x = np.asarray(x, float)
    bounds = [0, len(x)]; out = []
    for _ in range(max_bp):
        best = None
        for bi in range(len(bounds)-1):
            a, b = bounds[bi], bounds[bi+1]
            if b - a < 2*min_len: continue
            k, gain, mp, mq = _best_split(x[a:b], min_len)
            if gain > 0 and (best is None or gain > best[1]):
                best = (gain, a+k, mp, mq, a, b)
        if best is None: break
        gain, cut, mp, mq, a, b = best
        pos = bounds.index(a)
        bounds = bounds[:pos+1] + [cut] + bounds[pos+1:]
        out.append({"split_after": str(dates[cut-1].date()), "next_day": str(dates[cut].date()),
                    "gain": round(gain,1), "mean_pre": round(mp,2), "mean_post": round(mq,2),
                    "std_effect_d": round((mq-mp)/np.sqrt((x[a:cut].var(ddof=1)+x[cut:b].var(ddof=1))/2),2)})
    return out
```

## 1.4 Threats to naive inference (8 of them)

1. **Non-stationarity from four different causes** (demand, mix/coding, capacity, backlog) that a single pooled mean averages into a meaningless midpoint.
2. **Boundary mismatch**: `arrivals` and `completed` count different populations (carry-over), so    systematically; the difference is the backlog, not "demand".
3. **Censoring**: the outage truncates 3 of 12 service hours on 04-15 (a *censored observation*, not a rate); the "completed" count for any day is right-censored at 19:00 for cases still open.
4. **Compositional confounding (Simpson)**: weekday/weekend composition changes from week to week, so pooled weekly means move for reasons unrelated to behaviour.
5. **Measurement/coding change coincident with the mix shift** (04-20) — the "complex share" regressor and the throughput accounting both change at the same instant; a pooled regression of service time on mix is therefore partly an artefact of the common time trend.
6. **Serial dependence / non-independent rows**: the weekly cycle, backlog momentum (WIP lag-1  +0.47) and regime persistence make the 28 daily rows far fewer effective independent observations; naive standard errors are overstated.
7. **Aggregation destroys the burstiness that drives waiting time**: medians/p90s of service time and daily totals cannot express the hourly batch structure visible on 04-21 (34 arrivals in 09:00–10:00, 24 in 13:00–14:00).
8. **Capacity definition ambiguity**: FTE-hours  handling-minutes. Under a realistic 75–85 % availability for breaks/admin, the load figures I report (§2.3) rise by a factor 1.18–1.33 and the "already infeasible" regimes become more so.
9. **Mean vs median**: the table supplies medians and p90s; E[S] is never observed, and E[S]  median, so every work-content figure below is a **lower bound**.
10. **Unlogged intervention time**: 04-29 is a partial-treatment day; any before/after contrast that includes it is confounded.

# 2. Primary regime segmentation

## 2.1 Design principle

I segment on **observable, operationally distinct states**, and I keep the four confounded drivers (demand volume, case mix/coding, capacity, backlog) *separable* wherever the data allow. The primary segmentation has **nine mutually exclusive day-level regimes** that group into three families: (i) pre-mix baseline, (ii) shock and recovery, (iii) post-mix, split by the staffing intervention.

## 2.4 Explicit treatment of the outage and its recovery

- **R2 (04-15) is not a throughput regime.** Its completion rate (4.83/h) is a *censored* quantity: 180 of 720 minutes had no service. I never use 04-15 in a rate, a utilisation, or a Little's-Law calculation.
- **R3 (04-16/17) is a clearance regime, not a capacity regime.** Completions (120.5/d) exceed arrivals (105.5/d) because ~50 cases of backlog were being worked off. The 84 % completed-work load it sustained is a realistic *drain* benchmark, and it was achieved with 7.0/6.5 FTE — exactly the staffing profile later used for the "intervention".
- **R4 (04-18/19) is the discharge of the shock**: the queue balance stops growing (net 0) but a residual  +22 cases survives into the following week.
- **The elevated service times during R2–R3 are a case-selection signature.** Active handling time cannot grow because of waiting; it grows because the cases actually being handled are the older/more complex ones (A10). This is diagnostic evidence that `median_service_min` is computed over *handled* cases.
- **Do not read R3 as evidence that the pre-intervention queue was stable**: it is the most productive two days in the dataset and it was produced by a backlog, not by demand.

## 2.5 The 04-29 boundary problem

Three things change on 04-29 *simultaneously*: (i) staffing (6.0  7.0 FTE, and weekend 2.5  3.0), (ii) median service time (35  32.7) and complex share (45  44, falling), (iii) the daily balance flips from +13.4 to 6. Because the implementation time is unlogged, 04-29 contains both untreated and treated hours. **The improvement after 04-29 is therefore not attributable to the staffing change alone**: it could be (a) the extra FTE, (b) a genuine easing of the complex mix, (c) a partial rollback of the 04-20 coding change, or (d) draining ~18–28 carried cases. Any causal claim needs a design that separates these (see §7).

# 3. Alternative segmentation

## 3.1 Alternative A — two regimes split at 04-20 ("mix-shift segmentation")

- **A1:** 2026-04-06  2026-04-19 (14 d): "pre-mix / pre-shift".
- **A2:** 2026-04-20  2026-05-03 (14 d): "post-shift, post-intervention".

**Operational story it tells:** *"The centre changed its work and the queue became unstable; the April staffing change was a mitigation, not a regime of its own."* Everything after 04-20 is one regime whose story is "new work + more staff".

**Strengths:** balanced cells (14/14); captures the single dominant level shift (every regime-defining metric steps at 04-20); simple to communicate; does not manufacture spurious fine structure from 1–3 day cells; robust to the exact intervention date.

**Weaknesses:** (i) it **lumps the outage and recovery with normal operation** — A1 contains a 180-min outage and a 2-day clearance; (ii) it **mixes weekday and weekend** — A2 contains 10 weekdays and 4 weekend days at 2.5–3.0 FTE, so its means are composition-dependent; (iii) it **cannot separate the mix effect from the intervention effect**, because both sit in A2 — the entire "improvement" of the intervention is treated as noise; (iv) it implies the mix shift is the cause of the throughput deficit, which the WIP/balance divergence (§1.3d) makes doubtful.

## 3.2 Alternative B — state-based (operational-state) segmentation

Classify each day by *state* rather than by date: (i) **under-loaded** (04-06  04-14 weekdays, 04-11/12), (ii) **shock/clearance** (04-15  04-19), (iii) **saturated** (04-20  04-28), (iv) **stabilised** (04-29  05-03).

**Operational story:** *"This is a capacity-constrained queue that went from under-loaded to saturated in one step; the April intervention bought back the margin."* This segmentation maps one-to-one onto **control actions** (staff, batch scheduling, recovery protocol) and, unlike a date-based split, could be computed prospectively from live metrics — a scheduler could classify each day in real time.

**Strengths:** operationally actionable; explicitly separates *cause* (state) from *calendar* (when); makes the recovery protocol visible as its own state.
**Weaknesses:** thresholds are arbitrary (where does "saturated" begin?); retrospective classification leaks hindsight; states are continuous, so boundaries are inherently fuzzy; it does not identify *why* the state changed (demand? mix? coding?), which is precisely the question the centre must answer.

## 3.3 Alternative C — intraday-shape segmentation (arrival morphology)

Cluster the hourly vectors by *shape* rather than volume: (i) **single-hump, smooth** (04-07; lag-1 ACF  +0.69), (ii) **double-burst / batch-like** (04-21; peaks of 34 and 24 in two non-adjacent hours, lag-1 ACF  0.14), (iii) **flat plateau** (04-25; lag-1  +0.80, Fano 1.18).

**Operational story:** *"Waiting time is driven by the *shape* of arrivals, not their count; 04-21's 115 arrivals behave nothing like 04-07's 101."*
**Strengths:** shape-based metrics are far more stable than daily totals and map directly to peak-smoothing policy; it would have flagged 04-21 as anomalous *within* a week.
**Weaknesses:** n = 4 with **one instance per cluster and no replication** — shape effects cannot be separated from day-specific noise; and §1.3(c) shows the vectors conflict with `peak_08_10_pct`, so the shape evidence is itself uncertain.

## 3.4 Comparison

| Criterion | Primary (9 regimes) | Alternative A (2) | Alternative B (states) | Alternative C (shape) |
|---|---|---|---|---|
| Separates demand vs mix vs capacity vs backlog | Yes, partially (mix/coding still entangled) | No | Partly (by construction) | No |
| Handles the outage explicitly | Yes (R2/R3) | No | Yes | No |
| Treats the intervention as its own regime | Yes (R7/R8) | No | Partly | No |
| Cell sizes / statistical power | Weak (n = 1–7 per cell) | Strong (n = 14) | Weak–moderate | Very weak (n = 1 each) |
| Simpson/composition control | Good | Poor | Moderate | n/a |
| Operational actionability | Good | Low | High | Medium (peak smoothing only) |
| Risk of over-fitting noise | Moderate | Low | Moderate | High |

**Decision:** keep the primary segmentation for estimation, but (i) carry Alternative A as the *robustness check* (if a conclusion survives only under fine segmentation, treat it as provisional), and (ii) carry Alternative B's state labels as the operational vocabulary, because they are what a scheduler can act on daily.

## 4.3 Obfuscation #2 — the complex mix (a textbook Simpson reversal)

Correlation between `complex_pct` and `median_service_min`:

|---|---:|

Pooling inflates a *within-regime* association of essentially zero into +0.91, because both variables step at the same calendar instant (04-20). # 5. Burstiness, autocorrelation, and stationarity

## 5.1 Hourly vectors: dispersion and shape

For count data, the Fano factor (var/mean) **is** the index of dispersion I; the CV and the peak-to-mean ratio add shape information. The CI is the exact Poisson-referenced interval for I with n = 12 (²., = 21.92; ²., = 3.816).

| Day | mean/h | var/h | **Fano = I** | 95 % CI for I (Poisson reference) | CV | peak/mean | top-2 h share | lag-1 ACF | max cumulative gap |
|---|---:|---:|---:|---|---:|---:|---:|---:|---:|
| 2026-04-07 (weekday) | 8.42 | 25.54 | **2.78** | 1.52 – 8.74 | 0.60 | 2.38 | 0.36 | **+0.69** | 6 |
| 2026-04-15 (outage) | 8.75 | 36.19 | **3.79** | 2.07 – 11.92 | 0.69 | 2.51 | 0.37 | **+0.71** | 30 (truncated) |
| 2026-04-21 (post-mix) | 9.58 | 96.99 | **9.28** | 5.08 – 29.19 | 1.03 | **3.55** | 0.50 | **0.14** | 27 |
| 2026-04-25 (weekend) | 4.25 | 5.48 | **1.18** | 0.65 – 3.71 | 0.54 | 1.88 | 0.29 | **+0.80** | 8 |

Interpretation, with the uncertainty kept visible:

- **All four are overdispersed relative to Poisson (I > 1)**, but for 04-07, 04-15 and 04-25 the 95 % interval *includes* 1 — with 12 bins per day, these data cannot reject a Poisson arrival process. Only **04-21 (I = 9.28, CI 5.1–29.2)** is unambiguously non-Poisson, and even there the excess is driven by **two bins out of twelve** (34 at 09:00–10:00 and 24 at 13:00–14:00).
- **04-21's structure is not "bursty customer arrival"; it is a batch-release pattern.** Two separated spikes with a *negative* lag-1 autocorrelation (0.14) is the signature of a point/batch process, not of a smooth demand hump. Hypothesis (H1): bulk case-creation events (uploads, batch referrals, a scheduled job) land on the hour. Hypothesis (H2): the 34-case hour is an upstream *re-scan* of already-known cases, inflating `arrivals` without creating new work — which would also help explain the arrivals/completions divergence of §1.3(d). These have opposite policy implications (smooth the batch vs fix the counting), and the supplied data cannot separate them.
- **Shape differs by regime even at equal volume.** 04-07 and 04-21 carry almost the same daily count (101 vs 115) but opposite autocorrelation signs (+0.69 vs 0.14) and a 3.3× difference in Fano. A single Poisson/queueing fit over weekdays would average these and describe neither.
- The weekend vector's near-Poisson dispersion (I = 1.18) with a long plateau (08:00–12:00) and *no* pronounced peak explains why weekend load is as high as weekday load (§4.6 #6): the arrivals are spread over few servers at a rate that 2.5 FTE cannot absorb once case durations lengthen.

## 5.2 The daily sequence: dispersion, dependence, non-stationarity

- **Day-to-day arrival counts are *under*-dispersed**, not over-dispersed. Weekday arrivals in R0: mean 100.14, sd 4.77  **I = 0.23**, CV 0.048. A Poisson process would give I  1. I  1 means the daily volume is essentially a *schedule*, not a random draw: the variance of "demand" is tiny, and all the stochastic behaviour lives in (a) the intraday shape and (b) service/mix. Any model that puts a Poisson error term on daily arrivals and then attributes deviations to demand will be mis-specified.
- **Strong serial dependence in the state variables.** Post-mix window (04-20  05-03): lag-1 autocorrelation of `mean_wip`  **+0.47** (backlog momentum: a case that is late today is likely late tomorrow), and of the daily balance  **+0.78 raw**. The raw balance autocorrelation is inflated by the level trend; after first-differencing it falls to  **0.10**, i.e. the daily imbalance is mildly mean-reverting around a *shifting* mean. The 28 rows therefore carry far fewer than 28 effective degrees of freedom — significance tests and confidence intervals computed on 28 iid daily means are invalid.
- **The outage creates a shock-plus-drain signature**: net +47 on 04-15 (robust z  +5.5 against a MAD of 5.5), then 17 and 13 on the two recovery days (robust z  2.3, 1.8). A model fitted without the outage would see this as a permanent regime change; a model fitted without the recovery days would see a permanent *collapse* in throughput.
- **Change points (heuristic, hypothesis-generating only).** A piecewise-constant mean segmentation with minimum segment length 3 applied to the standard series yields, reproducibly:
  - `complex_pct`: single dominant step at **2026-04-20**, pre-mean 22.4 %  post-mean 43.3 %, with **no overlap** between the two value sets (max pre = 27 %, min post = 39 %). Standardised effect  5.5  — the cleanest signal in the data.
  - `median_service_min`: step at **2026-04-20**, 27.4  34.5 min (+26 %), effect  2.2 .
  - `p90_service_min`: step at **2026-04-20**, 53.6  80.5 min (+50 %) — dispersion rose more than the level, so this is *not* a pure scale shift.
  - `mean_wip`: change at **2026-04-15** (shock) and a level shift at **2026-04-20**; a further downward step after **2026-04-29**.
  - `staff_fte`: level shifts at 04-16 (recovery boost, 6.0  7.0) and 04-29 (6.0  7.0 weekday, 2.5  3.0 weekend), with weekend levels 2.5  3.0 on 05-02.
  These are *candidate* boundaries from a mean-shift heuristic; they are **not** validated by any likelihood/BIC comparison, they are sensitive to the minimum-segment-length choice, and the 04-20 "change point" is at least as likely a **coding change** as a process change (§1.3d). The heuristic cannot distinguish "the work changed" from "the recording changed" — which is precisely why the primary segmentation treats 04-20 as a *joint* process/measurement boundary.

## 5.3 Why four representative days cannot establish a stochastic model

1. **No replication.** There is exactly one instance of each morphology (weekday hump, outage weekday, post-mix burst, weekend plateau). A shape effect and a day-specific artefact are perfectly confounded.
2. **The estimator is unstable at n = 12.** The Fano factor has a 95 % CI spanning a factor of ~5.7 at n = 12; the 04-25 CI (0.65–3.71) contains every value from mild under-dispersion to strong over-dispersion. Nothing about the *distribution* is identified.
3. **Batch vs stochastic is not identified.** A single hour with 34 arrivals is equally consistent with a compound-Poisson batch process, a deterministic batch release, or a counting artefact. The three imply different queueing models (M/G/1 with batch arrivals vs M/X/1 with a smooth rate vs no true arrival at all).
4. **The vectors are "representative", not actual (§1.3a–c)**: they reconcile with daily totals but conflict with both `mean_wip` and `peak_08_10_pct`, so their role is illustrative.
5. **No service-time distribution.** Median and p90 do not identify a mean, let alone a variance; Kingman's/VUT approximations need CV_a and CV_s, and CV_s is not identified (only the p90/median ratio, 1.87  2.37, is observable).
6. **No resource/queue routing data.** Nothing here distinguishes one-server-with-queue from multi-stage with rework; the "complex variant" may add *steps* (variation) or *parallel* work (no waiting).

**Conclusion:** the data support *descriptive regime identification* and *capacity-pressure accounting*. They do **not** support a queueing-law claim (M/M/c, M/G/c, Kingman's VUT, or a fitted simulation) at any level of rigour.

# 6. Little's-Law applicability matrix

**Statement of what is being computed.** For a candidate window *W* (a set of consecutive opening hours), L = mean number in system = time-average of `mean_wip` over the window;  = throughput proxy = mean daily completions ÷ 12 h; **W = L/** is the mean residence time of the **population resident during the window**, in hours. It is *not* the flow time of the window's arrivals, and it is *not* the median service time (25 min in R0 versus 146 min implied flow time). Boundary conditions: no service occurs 19:00–07:00, so a case entering at 18:50 contributes to L but cannot complete inside the window; the 07:00 backlog N is unknown (A6), so the estimate is **censored at both window edges**. Throughput proxy choice: *completions* (not arrivals) is used wherever the window is closing or draining, because completions measure work actually released; *arrivals* is used where the queue is growing, because arrivals then measure true offered load. Where they disagree materially, the estimate is flagged.

# 7. Operational implications

## 7.1 Staffing

- **Size capacity on work content, not on case counts.**  (cases per staff-hour) is essentially unchanged between baseline weekdays (1.41) and post-intervention weekdays (1.40) while the work content per staff-hour rose from 35.2 to 45.8 min (59 %  76 % of nominal minutes). A rule like "keep 1.4 cases per FTE-hour" is satisfied and would still let the queue fail. The working KPI should be ` (cases × E[S]) ÷ available handling minutes`, with a target  80 % and an alarm at 85 %.
- **Required capacity under the post-mix regime.** R5 demand at 35-min median: 114 × 35 = 3 990 min/day of work. To hold 80 % of *effective* minutes at 85 % availability (612 effective min per FTE-day): 3 990 ÷ 0.80 ÷ 612  **8.1 FTE on weekdays**; at 75 % availability  **9.2 FTE**. The April intervention added 1.0 FTE (6.0  7.0) and 0.5 FTE at weekends, which closed the balance at R7 demand (115/day, median 32.7) but leaves only  4–7 pp of margin over the 80 % target. **But** if part of the 04-20 "mix shift" is a coding artefact (§1.3d), this requirement is overstated by an unknown factor — so *validate the coding change before hiring against it*.
- **Weekends are not slack.** Weekend load is 63 % (baseline)  **93 % (post-mix)** of nominal minutes at 2.5 FTE, and 78 % at 3.0 FTE. The weekend is the lowest-volume regime and among the tightest, and it is where the residual backlog is stored (balance  +22 carried into the following week). Options: lift weekend FTE by 0.5–1.0 on Fri/Sat, or move complex-variant intake to weekdays.
- **Do not staff from the outage day.** The 04-16 configuration (7.0 FTE, 84 % completed-work load) is the best-observed *drain* template and it was achieved with one extra FTE plus a 50-case backlog. Recovery capacity should be pre-authorised and released on a trigger (see §7.2), not improvised.

## 7.2 Backlog recovery

- **Instrument it with the balance, not with completions.** Daily `completed` is ambiguous (recovery vs new work). The balance `(arrivals  completed)` is interpretable: it moved +5  +52 (outage)  +22 (recovered)  +128 (saturated)  +110 (post-intervention). Use the balance as the trigger and completions only as the response.
- **Pre-authorise a drain protocol** modelled on 04-16/17: +1 FTE, and expect a run-rate of  17 cases/day of clearance at  84 % completed-work load. Then set an explicit target, e.g. "return the balance to its pre-shift level ( +22) within 3 working days", and report both the balance and the WIP.
- **Close the measurement gap.** The 110-case unreconciled residual must be explained before any recovery target is credible — if it is a counting artefact, the "backlog" partly does not exist, and recovery plans built on it would chase a phantom.

## 7.3 Peak smoothing

- The daily metric says the 08:00–09:59 share rose from  27 % (pre) to  38 % (post), peaking at 50 % on 04-27; the hourly vectors show the post-mix day is actually **multi-burst** (04-21: 34 arrivals at 09–10 *and* 24 at 13–14, lag-1 ACF 0.14). Both point the same way: **the problem is concentrated intraday arrivals, not daily volume**.
- Actions: (i) cap or re-phase the 09:00–10:00 intake window (the single most concentrated hour in the dataset); (ii) **stagger batch releases** off the hour and away from the morning peak — if H1 (batch releases) is right, a single scheduler change removes most of the 34-arrival spike; (iii) smooth arrivals into a single pooled server group if the complex path can be decoupled from the simple path; (iv) reconcile `peak_08_10_pct` with the true intraday profile before setting a target — the current metric and the hourly vectors disagree by a factor of ~2 in the morning concentration.
- Do **not** set a peak target from the current data alone: the metric is unreconciled (§1.3c), and the vectors are representative rather than actual.

## 7.4 Data collection (the highest-return action)

The single greatest analytical gain available is a **case-level event log** with: `case_id`, `activity` (with sub-steps for the complex variant), `timestamp` (start/finish), `resource_id`, `queue/priority`, `complex_flag` **with a versioned definition**, `arrival_source` (including batch/upload identifiers), and `outage intervals` with exact start/end. Add: a **07:00 and 19:00 census** of open cases (to close the balance identity), **end-of-day WIP** (not only the 15-min mean), hourly snapshot series (not only the mean), and the *actual* intervention implementation timestamp.

With that log: `pm4py.extract_temporal_features_dataframe` yields per-case durations and enables the direct measurement of flow time (replacing every L/ estimate in §6); `pm4py.get_case_arrival_average` tests the batch hypothesis (mean inter-arrival vs the hourly counts) and quantifies true arrival overdispersion; `pm4py.insert_case_arrival_finish_rate` provides a per-case finish rate relative to arrival, which is the correct KPI for the intervention (it separates "new work finished" from "old backlog cleared"); variant analysis (frequency traces / process tree) would establish whether the complex share is a real mix shift or a relabelling, i.e. it would *settle* the central ambiguity of this dataset.

## 7.5 Policies that look good pooled but are risky under a segmented view

| Policy | Pooled view | Segmented view | Verdict |
|---|---|---|---|

# ---------------------------------------------------------------- 6. CHANGE-POINT HEURISTIC
def _sse(x):
    x = np.asarray(x, float)
    return float(((x - x.mean())**2).sum()) if len(x) else 0.0

def _best_split(x, min_len=3):
    x = np.asarray(x, float); n = len(x); total = _sse(x); best = (None, -np.inf, np.nan, np.nan)
    for k in range(min_len, n - min_len + 1):
        gain = total - (_sse(x[:k]) + _sse(x[k:]))
        if gain > best[1]:
            best = (k, gain, x[:k].mean(), x[k:].mean())
    return best

def binary_segmentation(x, dates, max_bp=3, min_len=3):
    """HYPOTHESIS-GENERATING heuristic only (piecewise-constant mean, no significance test,
       no model comparison).  It cannot distinguish a process change from a coding change."""
    x = np.asarray(x, float); bounds = [0, len(x)]; out = []
    for _ in range(max_bp):
        best = None
        for bi in range(len(bounds)-1):
            a, b = bounds[bi], bounds[bi+1]
            if b - a < 2*min_len:
                continue
            k, gain, mp, mq = _best_split(x[a:b], min_len)
            if gain > 0 and (best is None or gain > best[1]):
                best = (gain, a+k, mp, mq, a, b)
        if best is None:
            break
        gain, cut, mp, mq, a, b = best
        pos = bounds.index(a)
        bounds = bounds[:pos+1] + [cut] + bounds[pos+1:]
        sd = np.sqrt((x[a:cut].var(ddof=1) + x[cut:b].var(ddof=1))/2)
        out.append(dict(split_after=str(dates[cut-1].date()), first_new_day=str(dates[cut].date()),
                        gain=round(gain,1), mean_pre=round(mp,2), mean_post=round(mq,2),
                        std_effect_d=round((mq-mp)/sd,2) if sd > 0 else np.nan))
    return out

---

**Summary of what I would tell the centre.** The data show one clean step change (2026-04-20: mix/coding + service time + peak concentration, ~2.2–5.5 ) preceded by a shock-and-drain episode (2026-04-15  04-19) and followed by a capacity intervention whose effect is confounded with a mix/coding drift and with backlog recovery. The queue was work-content-saturated in the post-mix window (93 % of nominal staff-minutes, deficit 13.4 cases/day) and only partly relieved by the April staffing change (76 % arrivals-based / 80 % completed-work). Pooled averages conceal this because weekday/weekend composition shifts weekly (pooled demand "10.5 %" while weekday demand is "+0.9 %"), because mix and service time step together (pooled r = +0.91 vs within-regime r  +0.12), because recovery days inflate throughput (only  29 % of the post-intervention throughput gain is genuine), and because the pooled Little's-Law value (4.16 h) describes no actual regime. Before any queueing-law claim is made, two things must be fixed in the data: the **110-case unreconciled gap** between arrivalscompletions and observed WIP, and the **definition conflict** between `peak_08_10_pct` and the hourly vectors.
