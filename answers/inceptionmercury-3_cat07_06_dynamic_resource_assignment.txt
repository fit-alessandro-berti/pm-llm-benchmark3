# 1. Objectives and constraints

There is no single optimum assignment. The policy is a satisficing rule: it tries to keep the process safe, understandable, and fair while also being reasonably fast. The optimization objectives are:

- Deliver cases before their SLA deadlines, especially urgent/high-priority cases.
- Minimize rework, appeals, and handover-related waiting.
- Use resources at a sustainable level without creating overtime hotspots.
- Develop skills through low-risk work and supervision.
- Preserve continuity for complex cases where the current owner already has context.
- Avoid creating specialist bottlenecks in Security and Approval.
- Remain explainable to workers and auditable from the event log.

Hard constraints are compliance/safety rules and must not be violated:

1. No resource may receive more than 4 new assignments in this decision batch.
2. High-priority cases cannot be assigned to a resource with skill below 2 unless there is explicit supervision.
3. Security Review must be performed by skill 3, or by skill 1–2 only under explicit supervision by R7_Gita or R8_Hugo.
4. Final Approval must be performed by skill 2–3. Skill 1 may prepare, but not finalize.
5. Resources with overtime risk = “high” should not receive new work unless the case is urgent and no safer alternative exists.
6. High-complexity cases with high handover cost should stay with the current owner unless the owner has skill 0/1 and no supervision is feasible.
7. Quality Check can be batched only when priority is normal/low and the SLA time remaining is greater than 24 hours.

Soft constraints are preferences, not safety rules:

- Keep at least 20% of normal/low-priority assignments aligned with documented training priorities, when SLA risk remains acceptable.
- Spread work across teams and resources.
- Avoid unnecessary handovers, especially on complex cases.
- Preserve specialist capacity for urgent specialist work.
- Use supervision as a development tool, not as a permanent replacement for required skill.

# 2. Assignment policy

The policy is a weighted scoring algorithm with hard eligibility filters. The weights represent current priorities; they should be reviewed using process-mining indicators.

## Eligibility filtering

For each case, filter resources by:

- `resource.skill[required_skill] > 0`.
- Security rule: if skill < 3, the resource is only eligible with R7_Gita or R8_Hugo as supervisor.
- Approval rule: for Final Approval, require skill >= 2.
- High-priority rule: if priority is `urgent` or `high`, skill < 2 requires a supervisor.
- Overtime rule: exclude `high` overtime-risk resources unless the case is urgent and no other resource is available.
- Batch cap: exclude resources that already have 4 new assignments in this decision batch.

## Scoring

For each eligible resource:

\[
\text{total} = 0.30 \cdot \text{urgency} + 0.25 \cdot \text{skill\_match} + 0.20 \cdot \text{continuity} + 0.15 \cdot \text{workload} + 0.05 \cdot \text{training} + 0.05 \cdot \text{resilience}
\]

### SLA urgency score

- SLA <= 4 hours: 1.0
- SLA 4–8 hours: 0.8
- SLA 8–24 hours: 0.6
- SLA > 24 hours: 0.4

The score is increased by 0.1 for `urgent` priority and 0.05 for `high` priority.

### Skill-match score

- Specialist skill 3: 1.0
- Competent skill 2: 0.7
- Trainee skill 1: 0.4
- Skill 0: not eligible

### Continuity / handover-cost score

- Same as current owner: 1.0
- Different owner, low handover cost: 0.8
- Different owner, medium handover cost: 0.5
- Different owner, high handover cost: 0.2
- If reassignment_count > 2, subtract 0.1.

### Workload and overtime fairness score

\[
\text{workload} = 0.5 \cdot \left(1 - \frac{\text{open\_cases}}{\max(\text{open\_cases})}\right) + 0.3 \cdot \frac{\text{hours\_remaining}}{\max(\text{hours\_remaining})} + 0.2 \cdot \text{overtime\_factor}
\]

Overtime factor: low = 1.0, medium = 0.7, high = 0.3.

### Training / development score

For normal/low-priority cases only:

- Skill level 1 and training priority matches the required skill: 1.0
- Skill level 2 and training priority matches the required skill: 0.8
- Shadowing or supervised preparation is also counted as 0.5 when explicitly arranged.

For urgent/high-priority cases, the training score is 0 unless the case is supervised and the resource already has skill >= 2.

### Resilience / bottleneck avoidance score

- If a resource already has another case with the same required skill in this batch, subtract 0.2.
- If the resource is one of few specialists in a bottleneck skill, prefer not to stack all bottleneck work on that resource.
- Prefer resources with a wider skill profile when scores are otherwise close.

## Tie-breaking and exception handling

Use the following tie-breakers in order:

1. Lower current open cases.
2. Lower overtime risk.
3. More hours remaining.
4. Same team as the current owner.
5. Less recent assignment load in the current batch.

If no resource passes the eligibility filter:

- Relax soft training and fairness weights.
- Allow a high-overtime resource only for urgent SLA risk.
- Allow skill 1 with explicit supervision if the activity is not a safety-critical gate.
- Log any exception with an `assignment_reason` value such as `override_sla`, `override_overtime`, or `override_supervision`.

# 4. Comparison with baseline policies

| Metric | First-available routing | Specialist-only routing | Proposed explainable policy |
|---|---|---|---|
| Expected throughput | High in the short term because idle resources are used quickly | High for repeatable specialist tasks, but queues build at Security and Approval | Slightly lower because of supervision and continuity, but less rework means higher effective throughput |
| SLA risk | Moderate average waiting, but high risk for specialist cases if a low-skill resource gets them | Good for specialist SLAs, but specialist queues can cause missed deadlines | Good: urgency is explicitly weighted, and safety-critical work is filtered first |
| Error/rework risk | High: skill mismatch and handovers create rework | Low for immediate errors, but high handover rates on complex cases increase rework | Medium-low: continuity and skill match reduce rework; training cases create some supervised risk |
| Fairness of workload | Uses open cases, but ignores overtime risk and specialism; can overload R6/R10/R3 | Very unfair to specialists, especially R6/R7/R8/R10 | Fairer: batch cap, overtime avoidance, and workload scores spread work |
| Skill development | Largely accidental | Specialists stay specialists; trainees rarely get meaningful work | Deliberate training assignments and shadowing, e.g. C009 and C015 |
| Continuity of case ownership | Weak: every case can be given to any resource | Weak: high-skill resource may take over cases from owners with context | Strong for high-handover-cost cases: C001, C007, C016 remain with owners |
| Resilience to absence or bottlenecks | Fragile: everyone has shallow skill coverage | Very fragile if one specialist is absent | More resilient: supervision and cross-training create backup paths, but still depends on R7/R8/R6/R10 |

No policy is universally best. If short-term throughput is the only goal, first-available can win. If immediate error minimization is the only goal, specialist-only can win. The proposed policy sacrifices some speed and specialist perfection to preserve continuity, develop skills, and avoid overtime hotspots.

# 5. Explanation to workers

This policy is like a traffic controller for work.

First, we have non-negotiable safety gates. Security Review must be done by, or explicitly supervised by, a security specialist. Final Approval must be done by someone approved to finalize. High-priority cases are not used for unplanned training.

After those gates, the system looks at four practical questions:

- How much time is left before the deadline?
- Who has the right skill for this activity?
- Who already knows this case and its history?
- How much are people already carrying today?

We try not to move cases unnecessarily. Moving a case costs time and can create mistakes. This matters most for complex cases where the current owner already understands the situation.

We also avoid giving new work to people already at high overtime risk. That is not a comment on their performance. It is a way to protect the whole team from fatigue and errors.

Training is part of the work. Normal and low-priority cases are used as learning opportunities when possible. Supervision counts as real work. If you are asked to supervise a trainee, that is an assignment, not a distraction.

If the policy makes an exception, it is logged and reviewable. No worker should feel singled out. The policy is meant to match the right work to the right person at the right time, not to judge individual value.

# 6. Process-mining audit indicators

Use the event log after deployment to compute these indicators:

1. **Handover frequency**  
   Count the number of times `org:resource` changes between consecutive events for the same case. Compare before and after the policy.

2. **Reassignment count**  
   Track `reassignment_count` per case. Flag cases with more than 2 reassignments.

3. **Skill mismatch**  
   For each event, compare `required_skill` to the assigned resource’s skill matrix. Report the share of work done by skill below 2, or below the required skill.

4. **Workload distribution**  
   Compute the Gini coefficient, or standard deviation, of open cases and new assignments across resources. Target a balanced distribution.

5. **Overtime risk exposure**  
   Measure the total hours assigned to resources with overtime risk = “high”. Also track cases where actual hours exceed remaining hours.

6. **SLA misses**  
   Measure the percentage of cases completed after `sla_deadline`, broken down by `case_priority`.

7. **Rework/appeal after assignment**  
   Count cases that contain repeated activities after assignment, or that appear again as rework. Use `concept:name` sequences to identify loops.

8. **Training assignment share**  
   Calculate the percentage of normal/low-priority assignments that are either:
   - assigned to a resource whose training priority matches the required skill, or
   - explicitly linked to shadowing/supervision.

9. **Specialist bottleneck indicators**  
   For Security and Approval, monitor average waiting time, queue length, and utilization of R6/R7/R8/R10. A growing queue indicates specialist overload.

10. **Deviations from assignment policy**  
    Audit the `assignment_reason` column. Count overrides and compare logged reasons to the policy algorithm.

11. **Handover cost realized**  
    Use `insert_case_service_waiting_time` to measure actual waiting time after an owner change, compared with the predicted `handover_cost_band`.

12. **Process performance before/after**  
    Use `discover_performance_dfg` to compare service time and waiting time by activity before and after the policy.

# 7. PM4Py implementation sketch

The PM4Py code below shows how the event log can be used to support policy design and auditing.

```python
import pm4py
import pandas as pd

# Load and format the event log
df = pd.read_csv("process_event_log.csv")

log = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource"
)

log = pm4py.convert_to_event_log(log)

# Organizational discovery
handover_net = pm4py.discover_handover_of_work_network(log)
working_net = pm4py.discover_working_together_network(log)
resource_sim = pm4py.discover_activity_based_resource_similarity(log)
roles = pm4py.discover_organizational_roles(log)
batches = pm4py.discover_batches(log)

# Performance-related views
service_time = pm4py.get_service_time(log)
log_with_wait = pm4py.insert_case_service_waiting_time(log)
perf_dfg = pm4py.discover_performance_dfg(log)
variants = pm4py.get_variants(log)

# Save organizational networks for visual audit
pm4py.save_vis_sna(handover_net, "handover_network.html")
pm4py.save_vis_sna(working_net, "working_together_network.html")

# Filter examples
urgent_log = pm4py.filter_event_attribute_values(
    log,
    "case_priority",
    "urgent",
    level="case"
)

late_cases = pm4py.filter_case_performance(
    log,
    min_case_duration=0,
    max_case_duration=...  # use SLA/performance thresholds
)

# Example audit metric: skill mismatch
skill_matrix = {
    "R1_Amal": {"Eligibility": 3, "Diagnosis": 1, ...},
    # ... full matrix
}

def skill_mismatch_share(log):
    mismatches = 0
    total = 0
    for trace in log:
        for event in trace:
            required = event.get("required_skill")
            resource = event.get("org:resource")
            if required and resource:
                total += 1
                actual = skill_matrix.get(resource, {}).get(required, 0)
                if actual < 2:
                    mismatches += 1
    return mismatches / total if total else 0

# Example audit metric: handover count
def count_handovers(log):
    handovers = 0
    for trace in log:
        previous_resource = None
        for event in trace:
            resource = event.get("org:resource")
            if previous_resource and resource and resource != previous_resource:
                handovers += 1
            previous_resource = resource
    return handovers

# The learned indicators can be used to recalibrate the policy weights:
# - handover network edge weights -> handover cost penalties
# - role discovery -> eligibility groups
# - performance DFG -> activity/resource service time estimates
# - batches -> valid batching opportunities
# - SLA filters -> urgency thresholds
```

The PM4Py outputs are not only for offline reporting. They can be used to tune the policy’s weights, to validate that `assignment_reason` decisions match actual outcomes, and to detect when the policy needs adjustment.
