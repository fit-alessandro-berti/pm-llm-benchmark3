### Why Bidirectional Edges in a DFG Do Not Prove Concurrency

Observing both directions in a frequency DFG—specifically `("Credit Check", "Engineering Review"): 17` and `("Engineering Review", "Credit Check"): 11`, as well as `("Engineering Review", "Supplier Confirmation"): 13` and `("Supplier Confirmation", "Engineering Review"): 2`, and `("Supplier Confirmation", "Expedite Review"): 1` and `("Expedite Review", "Supplier Confirmation"): 1`—is **necessary under interleaving concurrency**, but **insufficient to prove concurrency**. At least five non-concurrent mechanisms can generate bidirectional directly-follows pairs:

1. **Context-dependent XOR routing (sequential heterogeneity):** Standard orders may execute `CC -> ER` sequentially while engineering-heavy orders execute `ER -> CC` sequentially; pooling both subpopulations creates a 2-cycle in the DFG without any case ever executing them in parallel.
2. **Overlapping execution vs. true parallelism:** One check may strictly start after the other starts, yet finish earlier due to shorter service duration, inverting completion order even under sequential dependency of initiation.
3. **Timestamp coarseness and ingestion tie-breaking (S7):** If `CC` and `ER` complete within the same clock granularity (e.g., same second or batch flush), ingestion order determines which event appears first in the log, fabricating reverse edges.
4. **Unobserved rework or loops:** In general event logs, `A -> B` followed by `B -> A` can arise from rework (`A -> B -> A`), though here multiplicity is 1 per trace.
5. **Missing intermediate events (S5):** Omitting an event (e.g., a missing `SC`) collapses `A -> SC -> B` into `A -> B`, creating spurious directly-follows edges across the gap.

# 2. Shared Assumptions

All three candidate models share the following explicit modeling assumptions and abstractions:

1. **Event-completion semantics:** Each activity label represents an atomic **completion** event, not an execution interval. Ordering relations (`A -> B` in sequence or partial order) constrain observed completion order rather than true start-to-start or finish-to-start causality (D7, S7).
2. **Missing `Supplier Confirmation` events (S5):** Around 5–10% of `SC` events may be lost in transit. In the 30-case log, 7/30 traces (23.3%) lack `SC`—more than expected from integration loss alone, implying a mixture of legitimate stocked orders (S4) and missing-event external orders (S5). Because no event-level reliability flag exists, all three models treat observed `no-SC` traces as structurally valid rather than noisy/corrupted traces to be discarded.
3. **Absent `external/stocked` attribute (S5):** Because the component sourcing attribute was not exported, **data guards cannot be expressed**. All three models abstract away the missing case attribute by representing `external` vs. `stocked` routing purely as **control-flow alternatives** (structural branching). This is an intentional data-less abstraction: it cannot prevent an external-component order from taking a `no-SC` path.
4. **Representation of optionality:** In `model_balanced` and `model_permissive`, optionality of `SC` and `Exp` is modeled via silent transitions (`XOR(activity, tau)` / `OperatorPOWL(Operator.XOR, [Transition, SilentTransition])`). We explicitly disclose that `XOR(SC, tau)` **conflates true domain optionality** (S4: stocked components) **with fault tolerance for logging loss** (S5: missing `SC` events), whereas `XOR(Exp, tau)` represents genuine domain optionality (D6).
5. **Fixed boundary and post-approval tail (D1, D2):** All models fix `Register Order` as the unique start activity and `Approve Configuration -> Release Production -> Archive Case` as a strict sequential suffix, reflecting both high-confidence domain rules (D1, D2) and 30/30 empirical agreement.

# 3. Conservative Candidate

### Inductive-Bias Statement
The conservative candidate adopts an **empirical-closure (minimum-generalization) inductive bias**: it treats the observed variant set as the best available boundary of legitimate behavior when causal, attribute, and concurrency evidence is incomplete. Rather than hypothesizing unobserved interleavings from low- or medium-confidence rules (such as D5 or S2), it prioritizes **precision and empirical fidelity**, ensuring that no trace structure is admitted unless that exact completion sequence appeared in the 30 observed cases.

### Compact Formal Expression
Using standard Process Tree operator notation (`->` sequence, `X` exclusive choice):

```text
->(
  Register Order,
  X(
    ->(Credit Check, Engineering Review, Supplier Confirmation),
    ->(Engineering Review, Credit Check, Supplier Confirmation),
    ->(Credit Check, Engineering Review),
    ->(Engineering Review, Credit Check),
    ->(Credit Check, Supplier Confirmation, Engineering Review),
    ->(Credit Check, Engineering Review, Supplier Confirmation, Expedite Review),
    ->(Engineering Review, Credit Check, Expedite Review, Supplier Confirmation)
  ),
  Approve Configuration,
  Release Production,
  Archive Case
)
```

### PM4Py Code (`model_conservative`)

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def _pt_node(operator=None, label=None, children=None):
    node = ProcessTree(operator=operator, label=label)
    if children:
        for child in children:
            child.parent = node
            node.children.append(child)
    return node


_observed_middle_variants = [
    ["Credit Check", "Engineering Review", "Supplier Confirmation"],
    ["Engineering Review", "Credit Check", "Supplier Confirmation"],
    ["Credit Check", "Engineering Review"],
    ["Engineering Review", "Credit Check"],
    ["Credit Check", "Supplier Confirmation", "Engineering Review"],
    ["Credit Check", "Engineering Review", "Supplier Confirmation", "Expedite Review"],
    ["Engineering Review", "Credit Check", "Expedite Review", "Supplier Confirmation"],
]

_middle_branches = [
    _pt_node(Operator.SEQUENCE, children=[_pt_node(label=act) for act in seq])
    for seq in _observed_middle_variants
]

model_conservative = _pt_node(
    Operator.SEQUENCE,
    children=[
        _pt_node(label="Register Order"),
        _pt_node(Operator.XOR, children=_middle_branches),
        _pt_node(label="Approve Configuration"),
        _pt_node(label="Release Production"),
        _pt_node(label="Archive Case"),
    ],
)
```

*Note on duplicate labels and scalability:* This XOR-enumeration structure duplicates activity labels across branches (`Credit Check` appears 7 times, `Engineering Review` 7 times, `Supplier Confirmation` 5 times, `Expedite Review` 2 times). In the converted Petri net, each occurrence becomes a distinct transition sharing a label, which prevents a one-to-one mapping between a domain activity and a single net element, introduces alignment ambiguity (multiple transitions explain the same event), and scales linearly in model size with the number of distinct variants—making it brittle if additional valid interleavings appear later.

### Behavior Deliberately Excluded
- All unobserved interleavings of `CC`, `ER`, `SC`, and `Exp`, including plausible combinations such as `RO, ER, CC, SC, Exp, AC, RP, Arch`, `RO, CC, ER, Exp, SC, AC, RP, Arch`, `RO, CC, SC, ER, Exp, AC, RP, Arch`, and `RO, CC, ER, Exp, AC, RP, Arch`.
- `ER` triggering `SC` before `CC` (`RO, ER, SC, CC, AC, RP, Arch`).
- `SC` completing prior to both `CC` and `ER`.
- Any violation of D1–D4 or D6 (skipping `CC`/`ER`, `Exp` before `CC`/`ER`, reordering `AC -> RP -> Arch`, repetitions).

### Known Underfitting Risks (and Overfitting Balance)
While the dominant flaw of `model_conservative` is **severe overfitting** (zero generalization beyond the 7 observed variants, virtually guaranteeing fitness drops on future valid cases), it still exhibits **data-blind underfitting** in one specific respect: because the `external/stocked` attribute is missing (S5), the two `no-SC` branches (`CC, ER` and `ER, CC`) allow an external-component order—whose `SC` event was lost or illegally skipped (S3)—to replay with 100% fitness without flagging a compliance violation.

# 4. Balanced Candidate

### Inductive-Bias Statement
The balanced candidate adopts a **parsimonious partial-order (minimal-evidence generalization) inductive bias**: it avoids duplicate-label enumeration and extracts the tightest acyclic partial order (POWL) that reproduces all 30 observed cases while honoring all medium-to-high-confidence domain rules (D1–D4, D6, S2, S6). Where evidence is low-to-medium or empirically uninstantiated—specifically whether `ER` alone can precede `SC` (D5)—it remains cautious by retaining the empirically supported ordering `CC -> SC` observed in 22/22 `SC`-containing traces.

### Compact Formal Expression
Let `SC_opt = X(Supplier Confirmation, tau)` and `Exp_opt = X(Expedite Review, tau)`. `model_balanced` is a POWL `StrictPartialOrder` over `{RO, CC, ER, SC_opt, Exp_opt, AC, RP, Arch}` with precedence edges:

```text
RO -> CC
RO -> ER
CC -> SC_opt
CC -> Exp_opt
ER -> Exp_opt
SC_opt -> AC
Exp_opt -> AC
AC -> RP
RP -> Arch
```

### Decision Rationale: Sequence, Concurrency, and Partial Order
- **`Credit Check` and `Engineering Review` (Concurrency: `CC || ER`):** A strict sequence (`CC -> ER` per S1 or `ER -> CC`) would fail on 11 or 19 traces respectively. Given the 19:11 empirical split and S2's explanation of parallel checks, leaving `CC` and `ER` unordered in a partial order captures both completion orders cleanly. (We cannot distinguish true parallelism from mixed sequential subpopulations from completion logs alone per D7, so partial-order concurrency is the least biased encoding.)
- **`Supplier Confirmation` (Partial Order: `CC -> SC_opt`, `SC_opt || ER`, `SC_opt || Exp_opt`, `SC_opt -> AC`):** Putting `SC_opt` strictly after `AND(CC, ER)` would break V5 (`CC, SC, ER`). Putting `SC_opt` completely parallel to `CC` and `ER` would admit `SC` before both checks and `ER, SC, CC`, neither of which was observed and which D5 only weakly supports. Because `CC` preceded `SC` in **22/22** observed traces containing `SC`, imposing `CC -> SC_opt` while leaving `SC_opt` concurrent with `ER` and `Exp_opt` yields the minimal non-block-structured partial order consistent with all data and rules. Notably, this structure **cannot** be expressed in a duplicate-free `ProcessTree`.
- **`Expedite Review` (Partial Order: `{CC, ER} -> Exp_opt -> AC`, `Exp_opt || SC_opt`):** Directly encodes D6 and S6 (`Exp` optional, at most once, gated on completion of both `CC` and `ER`, preceding `AC`, and unordered with `SC` per V6 and V7).

### PM4Py Code (`model_balanced`)

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

_ro = Transition("Register Order")
_cc = Transition("Credit Check")
_er = Transition("Engineering Review")
_sc_opt = OperatorPOWL(Operator.XOR, [Transition("Supplier Confirmation"), SilentTransition()])
_exp_opt = OperatorPOWL(Operator.XOR, [Transition("Expedite Review"), SilentTransition()])
_ac = Transition("Approve Configuration")
_rp = Transition("Release Production")
_arch = Transition("Archive Case")

model_balanced = StrictPartialOrder([_ro, _cc, _er, _sc_opt, _exp_opt, _ac, _rp, _arch])

model_balanced.order.add_edge(_ro, _cc)
model_balanced.order.add_edge(_ro, _er)
model_balanced.order.add_edge(_cc, _sc_opt)
model_balanced.order.add_edge(_cc, _exp_opt)
model_balanced.order.add_edge(_er, _exp_opt)
model_balanced.order.add_edge(_sc_opt, _ac)
model_balanced.order.add_edge(_exp_opt, _ac)
model_balanced.order.add_edge(_ac, _rp)
model_balanced.order.add_edge(_rp, _arch)
```

### Behavior Deliberately Excluded
- Any trace where `SC` completes before `CC` completes, including `RO, ER, SC, CC, AC, RP, Arch` and `RO, SC, CC, ER, AC, RP, Arch`.
- Any trace where `Exp` completes before both `CC` and `ER` complete (D6, S6).
- Any trace skipping `CC` or `ER` (D3), skipping or reordering `AC -> RP -> Arch` (D1, D2), or repeating any activity (D6).

### Known Underfitting Risks
1. **Conflating missing `SC` with stocked skips:** Like all data-less candidates, `SC_opt` admits `no-SC` traces for external orders whose `SC` event was lost (S5) or improperly omitted (S3).
2. **Unobserved `Exp` combinations:** Admits `Exp` without `SC` (`CC, ER, Exp`) and `ER, CC, SC, Exp` even though only 2 `Exp` cases were observed (both with `SC`), which could overgeneralize if `Exp` only ever occurs on external-component escalations.
3. **False concurrency if S1 + S7 holds:** If `CC` and `ER` are actually sequential in some cases or split across two distinct subprocesses, modeling `CC || ER` everywhere underfits case-type restrictions.

# 5. Permissive Candidate

### Inductive-Bias Statement
The permissive candidate adopts a **broad-domain-consistency (exploratory) inductive bias**: it accepts that a 30-case sample is too small to observe all valid interleavings—especially given low-to-medium confidence rule D5 (that `SC` may start after *either* `CC` or `ER` yields sufficient intermediate information) and completion-only logging (D7, S7). Consequently, it uses a clean, duplicate-free block-structured `ProcessTree` that relaxes `CC -> SC` and allows `SC` to complete concurrently with the `CC || ER` and `Exp` block, while strictly preserving the high- and medium-confidence invariants (D1, D2, D3, D4, D6, S6).

### Compact Formal Expression
```text
->(
  Register Order,
  +(
    X(Supplier Confirmation, tau),
    ->(
      +(Credit Check, Engineering Review),
      X(Expedite Review, tau)
    )
  ),
  Approve Configuration,
  Release Production,
  Archive Case
)
```

### PM4Py Code (`model_permissive`)

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

    if children:
        for child in children:
            child.parent = node
            node.children.append(child)
    return node


_sc_opt_pt = _pt_node(
    Operator.XOR,
    children=[_pt_node(label="Supplier Confirmation"), _pt_node()],

_exp_opt_pt = _pt_node(
    Operator.XOR,
    children=[_pt_node(label="Expedite Review"), _pt_node()],

model_permissive = _pt_node(
    Operator.SEQUENCE,
    children=[
        _pt_node(label="Register Order"),
        _pt_node(
            Operator.PARALLEL,
            children=[
                _sc_opt_pt,
                _pt_node(
                    Operator.SEQUENCE,
                    children=[
                        _pt_node(
                            Operator.PARALLEL,
                            children=[
                                _pt_node(label="Credit Check"),
                                _pt_node(label="Engineering Review"),
                            ],
                        ),
                        _exp_opt_pt,
                    ],
                ),
            ],
        ),
        _pt_node(label="Approve Configuration"),
        _pt_node(label="Release Production"),
        _pt_node(label="Archive Case"),
    ],
)
```

### Boundary Between Reasonable Generalization and Forbidden Behavior
- **Reasonable generalization (admitted):**
  - All 12 traces of `model_balanced` (including all 7 observed variants and unobserved interleavings of `CC || ER`, `Exp || SC`).
  - `SC` completing after `ER` and before `CC` (`RO, ER, SC, CC, ...`), directly reflecting D5's rule that `ER` alone may trigger `SC`.
  - `SC` completing prior to *both* `CC` and `ER` completions (`RO, SC, CC, ER, ...`), justified under completion-only semantics (D7, S7) when `CC` or `ER` emits preliminary info early (D5) and `SC` finishes while the longer checks are still completing, or when ingestion tie-breaking reorders same-timestamp completions.
- **Forbidden behavior (boundary remains enforced):**
  - Any skipping of `CC` or `ER` (D3).
  - `Exp` occurring before completion of *both* `CC` and `ER` (D6, S6).
  - `SC` or `Exp` occurring after `AC` (D4, D6).
  - Reordering or omitting `RO`, `AC`, `RP`, or `Arch` (D1, D2).
  - Executing any activity more than once (D6, empirical multiplicity = 1).

### Behavior Deliberately Excluded
- Bypassing `Credit Check` or `Engineering Review` (e.g., `RO, CC, SC, AC, RP, Arch`).
- `Expedite Review` before both principal checks complete (e.g., `RO, CC, Exp, ER, AC, RP, Arch`).
- Post-approval deviations (`RO, CC, ER, RP, AC, Arch`, or `SC`/`Exp` after `AC`).
- Rework loops / repeated checks or repeated `Expedite Review`.

### Known Underfitting Risks
1. **Weakening D5 at completion level:** Admitting `RO, SC, CC, ER, AC, RP, Arch` allows `SC` to finish before *any* principal check has finished; if D5 actually requires *completion* of at least one check, this admits invalid early confirmations.
2. **Over-permitting `ER -> SC -> CC`:** If procurement in reality always waits for `Credit Check` (risk control) before contacting suppliers, admitting `ER, SC, CC` masks a control violation.
3. **Data-blind `no-SC` and `Exp`-without-`SC` paths:** Shares the attribute-blind underfitting of `model_balanced`, plus a wider combinatorial space (18 valid traces vs. 12 in Balanced and 7 in Conservative) that lowers precision on small logs.

# 8. Validation Code

The script below is completely self-contained. Note two analytical limitations explicitly:
1. **Sampled playout cannot prove language inclusion or equality:** `pm4py.play_out` draws a finite stochastic sample from the Petri net. Observing an expected trace proves it is reachable, but *failing* to sample a trace never proves it is excluded, and sampled playout never proves language inclusion—especially for models with loops (infinite languages), even though our three candidates here happen to be acyclic.
2. **Conformance APIs do not compare whole languages:** Alignment-based fitness/precision and conformance diagnostics evaluate observed or manually supplied traces against a net; they cannot exhaustively compare two Petri nets' languages in the general case. Exact per-trace membership checking below uses `conformance_diagnostics_alignments` (`fitness == 1.0` iff the trace is in the net's language).

```python
from collections import Counter
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)


# ---------------------------------------------------------------------
# 1. Reconstruct the 30-case event log via pm4py.parse_event_log_string
# ---------------------------------------------------------------------
variant_counts = [
    (12, "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (7,  "Register Order,Engineering Review,Credit Check,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (4,  "Register Order,Credit Check,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (3,  "Register Order,Engineering Review,Credit Check,Approve Configuration,Release Production,Archive Case"),
    (2,  "Register Order,Credit Check,Supplier Confirmation,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Expedite Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Engineering Review,Credit Check,Expedite Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
]

trace_strings = [trace for count, trace in variant_counts for _ in range(count)]
assert len(trace_strings) == 30

log = pm4py.parse_event_log_string(trace_strings)
observed_variant_set = {trace for _, trace in variant_counts}


# ---------------------------------------------------------------------
# 2. Construct the three candidate models
# ---------------------------------------------------------------------
def pt_node(operator=None, label=None, children=None):
    node = ProcessTree(operator=operator, label=label)
    if children:
        for child in children:
            child.parent = node
            node.children.append(child)
    return node


# 2a. Conservative (ProcessTree: exact XOR enumeration of observed middles)
observed_middles = [
    ["Credit Check", "Engineering Review", "Supplier Confirmation"],
    ["Engineering Review", "Credit Check", "Supplier Confirmation"],
    ["Credit Check", "Engineering Review"],
    ["Engineering Review", "Credit Check"],
    ["Credit Check", "Supplier Confirmation", "Engineering Review"],
    ["Credit Check", "Engineering Review", "Supplier Confirmation", "Expedite Review"],
    ["Engineering Review", "Credit Check", "Expedite Review", "Supplier Confirmation"],
]
model_conservative = pt_node(
    Operator.SEQUENCE,
    children=[
        pt_node(label="Register Order"),
        pt_node(
            Operator.XOR,
            children=[
                pt_node(Operator.SEQUENCE, children=[pt_node(label=a) for a in seq])
                for seq in observed_middles
            ],
        ),
        pt_node(label="Approve Configuration"),
        pt_node(label="Release Production"),
        pt_node(label="Archive Case"),
    ],
)

# 2b. Balanced (POWL StrictPartialOrder)
ro = Transition("Register Order")
cc = Transition("Credit Check")
er = Transition("Engineering Review")
sc_opt = OperatorPOWL(Operator.XOR, [Transition("Supplier Confirmation"), SilentTransition()])
exp_opt = OperatorPOWL(Operator.XOR, [Transition("Expedite Review"), SilentTransition()])
ac = Transition("Approve Configuration")
rp = Transition("Release Production")
arch = Transition("Archive Case")

model_balanced = StrictPartialOrder([ro, cc, er, sc_opt, exp_opt, ac, rp, arch])
model_balanced.order.add_edge(ro, cc)
model_balanced.order.add_edge(ro, er)
model_balanced.order.add_edge(cc, sc_opt)
model_balanced.order.add_edge(cc, exp_opt)
model_balanced.order.add_edge(er, exp_opt)
model_balanced.order.add_edge(sc_opt, ac)
model_balanced.order.add_edge(exp_opt, ac)
model_balanced.order.add_edge(ac, rp)
model_balanced.order.add_edge(rp, arch)

# 2c. Permissive (ProcessTree: SC_opt parallel to SEQ(AND(CC, ER), Exp_opt))
model_permissive = pt_node(
    Operator.SEQUENCE,
    children=[
        pt_node(label="Register Order"),
        pt_node(
            Operator.PARALLEL,
            children=[
                pt_node(
                    Operator.XOR,
                    children=[pt_node(label="Supplier Confirmation"), pt_node()],
                ),
                pt_node(
                    Operator.SEQUENCE,
                    children=[
                        pt_node(
                            Operator.PARALLEL,
                            children=[
                                pt_node(label="Credit Check"),
                                pt_node(label="Engineering Review"),
                            ],
                        ),
                        pt_node(
                            Operator.XOR,
                            children=[pt_node(label="Expedite Review"), pt_node()],
                        ),
                    ],
                ),
            ],
        ),
        pt_node(label="Approve Configuration"),
        pt_node(label="Release Production"),
        pt_node(label="Archive Case"),
    ],
)

candidates = {
    "Conservative": model_conservative,
    "Balanced": model_balanced,
    "Permissive": model_permissive,
}


# ---------------------------------------------------------------------
# 3 & 4 & 5. Convert to Petri net, check soundness, metrics, playout
# ---------------------------------------------------------------------
petri_models = {}

for name, model in candidates.items():
    print(f"\n==================== {name.upper()} ====================")
    net, im, fm = pm4py.convert_to_petri_net(model)
    petri_models[name] = (net, im, fm)

    soundness = pm4py.check_soundness(net, im, fm, print_diagnostics=True)
    print("Soundness check result:", soundness)

    fitness = pm4py.fitness_alignments(log, net, im, fm)
    precision = pm4py.precision_alignments(log, net, im, fm)
    generalization = pm4py.generalization_tbr(log, net, im, fm)
    simplicity = pm4py.simplicity_petri_net(net, im, fm)

    print("Alignment Fitness:", fitness)
    print("Alignment Precision:", precision)
    print("TBR Generalization:", generalization)
    print("Petri Net Simplicity:", simplicity)

    # Sampled playout (stochastic finite sample; cannot prove language inclusion)
    sim_log = pm4py.play_out(net, im, fm, no_traces=500)
    sim_variants = Counter(
        ",".join(evt["concept:name"] for evt in trace) for trace in sim_log
    )
    unseen_sampled = [v for v in sim_variants if v not in observed_variant_set]
    print(
        f"Sampled 500 traces -> {len(sim_variants)} distinct variants "
        f"({len(unseen_sampled)} unobserved)."
    )
    for uv in unseen_sampled[:5]:
        print(f"  [Unobserved sample x{sim_variants[uv]}] {uv}")


# ---------------------------------------------------------------------
# 6. Manual Positive/Negative Trace Suite Verification
# ---------------------------------------------------------------------
test_cases = [
    (
        "T1_observed_V5",
        "Register Order,Credit Check,Supplier Confirmation,Engineering Review,Approve Configuration,Release Production,Archive Case",
        {"Conservative": True, "Balanced": True, "Permissive": True},
    ),
    (
        "T2_unobserved_balanced_ER_CC_SC_Exp",
        "Register Order,Engineering Review,Credit Check,Supplier Confirmation,Expedite Review,Approve Configuration,Release Production,Archive Case",
        {"Conservative": False, "Balanced": True, "Permissive": True},
    ),
    (
        "T3_unobserved_balanced_no_SC_with_Exp",
        "Register Order,Credit Check,Engineering Review,Expedite Review,Approve Configuration,Release Production,Archive Case",
        {"Conservative": False, "Balanced": True, "Permissive": True},
    ),
    (
        "T4_permissive_only_ER_SC_CC",
        "Register Order,Engineering Review,Supplier Confirmation,Credit Check,Approve Configuration,Release Production,Archive Case",
        {"Conservative": False, "Balanced": False, "Permissive": True},
    ),
    (
        "T5_permissive_only_early_SC",
        "Register Order,Supplier Confirmation,Credit Check,Engineering Review,Approve Configuration,Release Production,Archive Case",
        {"Conservative": False, "Balanced": False, "Permissive": True},
    ),
    (
        "T6_forbidden_Exp_before_ER",
        "Register Order,Credit Check,Expedite Review,Engineering Review,Approve Configuration,Release Production,Archive Case",
        {"Conservative": False, "Balanced": False, "Permissive": False},
    ),
    (
        "T7_forbidden_RP_before_AC",
        "Register Order,Credit Check,Engineering Review,Release Production,Approve Configuration,Archive Case",
        {"Conservative": False, "Balanced": False, "Permissive": False},
    ),
    (
        "T8_forbidden_missing_ER",
        "Register Order,Credit Check,Supplier Confirmation,Approve Configuration,Release Production,Archive Case",
        {"Conservative": False, "Balanced": False, "Permissive": False},
    ),
]

test_log = pm4py.parse_event_log_string([t[1] for t in test_cases])

print("\n==================== TEST SUITE CHECK ====================")
for name, (net, im, fm) in petri_models.items():
    diags = pm4py.conformance_diagnostics_alignments(test_log, net, im, fm)
    for (tc_id, _, expected_map), diag in zip(test_cases, diags):
        admitted = diag["fitness"] >= 1.0 - 1e-9
        expected = expected_map[name]
        status = "PASS" if admitted == expected else "FAIL"
        print(f"[{status}] {name:12s} | {tc_id:38s} | admitted={admitted} (expected={expected})")
```

# 9. Recommendation and Data-Collection Plan

### Model Recommendation
- **Immediate operational use (`model_balanced`):** `model_balanced` provides the best bias-variance tradeoff for immediate monitoring and conformance checking. It fits 30/30 observed cases, avoids duplicate-label fragility, remains compact and explainable, tolerates missing `SC` events across all check/expedite combinations, and avoids admitting unsubstantiated early-`SC` paths (`ER -> SC -> CC` or `SC` before checks) while flagging true rule violations (missing checks, premature `Exp`, post-`AC` reorderings).
- **Sensitivity analysis (`model_permissive`):** Run `model_permissive` in parallel for exploratory diagnostics and false-positive triage. Any incoming trace rejected by `model_balanced` but accepted by `model_permissive` (specifically `SC` before `CC`) isolates the exact empirical boundary of D5 rather than indicating a severe D1–D4/D6 failure. *(Additionally, `model_conservative` can be retained purely as a historical regression check.)*

### Data-Collection Plan to Resolve Ambiguities
1. **Export missing case attributes (resolves S3, S4, S5):**
   - `component_sourcing_type` (`external`, `stocked`, `mixed`): separates legitimate `SC` skipping (S4) from procurement non-compliance (S3) and logging drops (S5).
   - `credit_outcome`, `engineering_complexity`, `expedite_reason`: tests whether `CC`/`ER` ordering or `Exp` presence depends on case subtype (heterogeneous sequential routing vs. uniform concurrency).
2. **Add lifecycle transitions and high-resolution timestamps (resolves D7, S1 vs. S2, S7):**
   - Capture `start` and `complete` timestamps (`lifecycle:transition` in XES) at millisecond precision plus a monotonic server-side sequence ID.
   - This directly tests S1 (`ER_start >= CC_complete`) vs. S2 (overlapping `[CC_start, CC_complete]` and `[ER_start, ER_complete]` intervals) and exposes whether `SC` actually *starts* mid-check (D5) or only after completion.
3. **Instrument integration audit logs for `Supplier Confirmation` (resolves S5):**
   - Log API request/acknowledgment IDs (`sc_requested`, `sc_ack_failed`) or dead-letter queue counts so the 5–10% missingness can be reconstructed or flagged as technical faults rather than control-flow skips.

### Maximally Informative Future Traces (Active Discrimination)
Collecting and auditing the following specific trace patterns (paired with the new attributes and `start`/`complete` timestamps) will maximally distinguish the competing hypotheses:

1. **`RO, ER, SC, CC, AC, RP, Arch` (with `component_sourcing_type=external`):**
   - *Distinguishes:* `model_balanced` (rejects) vs. `model_permissive` (accepts), and tests D5 (`ER` sufficient to enable `SC` without waiting for `CC`).
2. **`RO, SC, CC, ER, AC, RP, Arch` (with `start`/`complete` timestamps):**
   - *Distinguishes:* `model_permissive` (accepts) vs. a strict "at least one check must *complete* before `SC`" model. If `SC_start` precedes both `CC_start` and `ER_start`, even D5 is violated; if `SC_start` follows `CC_start` while `CC` is still running, D5's "preliminary information" reading is confirmed.
3. **`RO, CC, ER, Exp, AC, RP, Arch` (stratified by `external` vs. `stocked`):**
   - *Distinguishes:* Legitimate stocked-expedite without `SC` vs. an integration drop on expedited external orders; tests whether `Exp` is independent of `SC`.
4. **`RO, ER, CC, SC, Exp, AC, RP, Arch`:**
   - *Confirms:* That `CC || ER` independence extends to expedited cases (currently unobserved in V6/V7).
5. **Traces with `CC` and `ER` `start`/`complete` timestamps on both `CC -> ER` and `ER -> CC` completion orders:**
   - *Distinguishes:* True concurrency (overlapping intervals, S2) vs. context-dependent XOR sequencing (non-overlapping intervals with varying order) vs. S7 ingestion-index artifacts (identical `complete` timestamps).

# 10. Uncertainty Statement

### Calibrated Confidence Assessment

| Modeling Decision | Confidence Level | Calibration Rationale |
| :--- | :--- | :--- |
| **Start (`RO`) and post-approval tail (`AC -> RP -> Arch`)** | **Very high (95–99%)** | Supported by 30/30 cases and high-confidence rules D1 and D2. Residual 1–5% uncertainty reflects rare emergency/manual bypasses unseen in a 30-case sample. |
| **Both `CC` and `ER` mandatory before `AC`** | **High (85–90%)** | Supported by 30/30 cases and medium-to-high rule D3 ("should"). Leaves minor uncertainty for exceptional pre-approved/repeat-order fast tracks. |
| **Modeling `SC` as structurally optional (`XOR(SC, tau)`)** | **High for necessity (~90%), Low-to-moderate (~50%) for domain meaning** | Given absent `external/stocked` data and 7/30 `no-SC` traces, structural optionality is unavoidable; however, we cannot calibrate what fraction of the 7 traces are stocked (S4) vs. lost events (S5). |
| **`CC` and `ER` concurrent (`CC || ER`) vs. sequential/guarded** | **Moderate (65–75%)** | 19 vs. 11 split strongly rejects a single rigid sequence across all logged orders (unless S7 artifacts dominate), and S2 explains parallelism, but D7 prevents ruling out hidden subtype-specific sequential paths. |
| **`Exp` optional, `<= 1`, after both `CC` and `ER`, `Exp || SC`** | **Moderate-to-high (70–80%)** | Explicitly backed by D6 and S6 and corroborated by V6 and V7, though empirical support is only `n = 2` traces. |
| **`CC -> SC` ordering (Balanced) vs. `ER` enabling `SC` (Permissive)** | **Low-to-moderate (45–60% for `CC -> SC`)** | Although 22/22 `SC` traces follow `CC`, `n = 22` is modest, V5 (`CC, SC, ER`) occurred only twice, and D5 explicitly states `ER` can also trigger `SC`. |

### Plausible Alternative Interpretations That Would Materially Change the Recommendation

1. **S1 Policy Enforcement Masked by S7 Ingestion Artifacts or Non-Compliance:**
   Suppose the Finance Manager (S1) is correct that `Credit Check` is a strict prerequisite for `Engineering Review` in compliant operations, and the 11 `ER -> CC` traces arose either because both automated checks completed within the same timestamp bucket and were ordered by ingestion index (S7), or because a subset of engineers prematurely bypassed `CC`. Under this interpretation, modeling `CC || ER` in `model_balanced` introduces **severe underfitting** by legitimizing non-compliant behavior. The recommendation would shift from `model_balanced` to a **guarded or sequential compliance model (`CC -> ER`)** that treats `ER -> CC` as a deviation requiring investigation until `start` timestamps refute S1.

2. **Higher-Than-Reported `SC` Event Loss Combined with Rare Stocked Orders:**
   Suppose stocked-component orders are actually rare (<5% of volume) and most of the 7/30 (23.3%) `no-SC` traces reflect a broader integration outage than the data engineer estimated (S5), meaning almost all cases are subject to S3's mandatory `SC` rule. Under that interpretation, treating `no-SC` as freely acceptable in `model_balanced` and `model_permissive` creates an unacceptable **compliance blind spot** for procurement. The recommendation would change to **requiring mandatory `SC` alerting** (flagging `no-SC` cases as provisional anomalies) until the `external/stocked` attribute is restored.
