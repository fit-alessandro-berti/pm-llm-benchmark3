## 1. Conformance semantics

I separate six diagnostic classes:

- **Forbidden behavior**: an explicitly forbidden relation/event link is observed. Because the norm is closed-world for forbidden relations, this is nonconforming unless the observation is a false positive, model artifact, or data-quality error. Examples: N3 `Cancel Order -> Dispatch Package`, T6 `(Order, object_cobirth, Payment)`, E10 `Sensor Heartbeat -> Invoice`.
- **Missing mandatory behavior**: a mandatory relation is absent within its stated scope. I must check scope and abstraction before calling it a violation. Example: N1 is mandatory for newly created Orders, but the summary uses directly-follows as an approximation for “eventually enters validation.”
- **Unexpected but unregulated behavior**: the relation is absent from the norm or explicitly unspecified. Absence from the normative edge set is not noncompliance. Examples: `Validate Order -> Issue Invoice`, `Manual Compliance Review -> Customer`, `Package object_codeath Delivery`, `Reopen Order -> Close Order`.
- **Typical-pattern absence**: a typical relation is missing, but exceptions are legitimate. Examples: N2, N5, T3. These are lower severity and often require business context, not immediate escalation.
- **Likely data-quality error**: the observed edge is more plausibly caused by identifier reuse, bad joins, missing references, or event grouping than by real behavior. The `Sensor Heartbeat -> Invoice` edge strongly suggests this.
- **Abstraction mismatch**: the model family is too coarse or too strict. A directly-follows OC-DFG cannot prove that a validation event never happened if an unrecorded review event intervened.
- **Insufficient evidence**: graph summaries alone cannot decide whether a cancellation preceded a dispatch, whether co-birth is a real business event, or whether an unlabeled payment is unapplied cash.

Open-world logic matters. The norm is closed-world only for explicitly forbidden relations and mandatory relations within scope. Typical relations may legitimately be absent; unspecified relations are outside the norm. Therefore, `Reopen Order -> Close Order`, `Manual Compliance Review -> Customer`, and `Package object_codeath Delivery` are not violations merely because they are not normative edges.

## 3. Detailed reasoning by model family

### OC-DFG

OC-DFG can establish direct-follows counts between event types for a given object type. It cannot establish eventual behavior, causality, temporal ordering beyond the abstraction, final-state semantics, or whether an intervening event explains a gap. Counts matter more when the norm is mandatory and scope is clear. N3 is the strongest OC-DFG finding because it is explicitly forbidden: 2 Orders show `Cancel Order -> Dispatch Package`. Even there, I need event-level evidence to prove the same Order was cancelled before dispatch and not a link error.

N4 requires `Pack Package -> Dispatch Package` for externally shipped Packages. The count is 198 of 200. If the two missing are not externally shipped, they are out of scope. If they are external, this is a mandatory gap or abstraction mismatch. N1 is the clearest danger of over-reading directly-follows. The norm says every newly created standard Order should eventually enter validation. The summary approximates that with direct-follows. The two missing cases may have an unrecorded review event between creation and validation. Thus N1 is a mandatory rule with an abstraction caveat, not proof of two violations.

N2 and N5 are typical. `Validate Order -> Close Order` at 83 and `Issue Invoice -> Record Payment` at 92 of 110 may be normal; intermediate invoice, review, fulfilment, credit notes, write-offs, and open credit terms are legitimate. `Validate Order -> Issue Invoice` is not normative but is business-plausible and unregulated. `Reopen Order -> Close Order` is explicitly unspecified under N6.

### OTG

OTG can establish object-to-object edges such as interaction, co-birth, and co-death. It cannot prove event-instance conformance, temporal direction, or whether the relation is semantically correct. T1 `(Order, object_interaction, Item)` at 1450 is mandatory and appears satisfied at aggregate level, but it should be reconciled with Add Item events. T2 `(Package, object_interaction, Delivery)` at 200 is mandatory and appears satisfied at aggregate level; the separate ET–OT gap for `Dispatch Package -> Delivery` still needs event-level repair. T3 is typical; 92 Invoice–Payment interactions may reflect applied payments, while unapplied cash can exist.

T6 is forbidden and observed once: `(Order, object_cobirth, Payment)`. This is high severity because the norm explicitly forbids orders and payments being born in the same business event. However, one co-birth edge may be an event-grouping artifact or an import error. T4 and T5 are unspecified. `(Order, object_interaction, Customer)` and `(Order, object_interaction, RiskCase)` are therefore not violations. `Package object_codeath Delivery` is unregulated; codeath is not addressed by the norm, so 7 such edges are benign from this norm’s perspective.

A relation can be conforming at one abstraction and suspicious at another. For example, `Package -> Delivery` interaction is present for T2, but an event-level `Dispatch Package -> Delivery` gap can still matter for E6. Similarly, `Order -> Customer` is frequent but unregulated here, while the same customer relation could be mandatory under another policy.

### ET–OT

ET–OT can establish whether an event type instance is linked to an object type. It cannot establish multiplicity, role, correct object identity, or whether the link is semantically valid. E1, E3, E4, E5, and E7 appear conforming. E2 is anomalous: `Add Item -> Order` is 1448 while `Add Item -> Item` is 1450. That suggests two Add Item events lack an Order link, which is mandatory unless the events are out of scope or the relation is missing due to data quality. E6 is also anomalous: `Dispatch Package -> Delivery` is 198 of 200. The carrier reference is a plausible data-quality alternative, but the norm still requires a Delivery relation for each Dispatch Package event.

E8 is nuanced. `Record Payment -> Invoice` is mandatory except events explicitly typed as unapplied cash; none are so typed. The observed count is 92 of 93. Finance says unapplied cash is possible, but because the event is not labeled, this is either a missing mandatory relation or an unlabeled exception. It should not be dismissed, but it also should not be called a high-severity violation until the payment is examined.

E10 is forbidden and observed once: `Sensor Heartbeat -> Invoice`. The context says it was produced by a join on a reused numeric identifier and is suspected data-quality error. Even so, it is a high-priority data-quality and compliance signal because a sensor stream must never be linked to financial objects. E9 is unspecified; `Manual Compliance Review -> RiskCase` is legitimate rare interaction. `Manual Compliance Review -> Customer` is not governed by E9 and is not a violation solely because it is absent from the normative edge set.

The key abstraction warning is that an “eventually expected” business rule is not the same as a directly-follows rule. N1, N2, N4, and N5 all require care. A missing direct-follows edge may be a legitimate intervening event, not a process violation.
