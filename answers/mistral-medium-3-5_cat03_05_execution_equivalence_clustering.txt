## 1. Equivalence design space

### 1.1 Activity-sequence equivalence
- **Definition**: Two executions are equivalent if their sequences of activity labels (ignoring object identifiers and O2O notes) are identical.
- **Invariants preserved**: Order of activities, activity names.
- **Information discarded**: Object types, identifiers, multiplicities, O2O qualifiers, external objects.
- **Properties**: Reflexive, symmetric, transitive.
- **Concurrency handling**: Assumes total order; concurrent events would break equivalence unless explicitly ordered.

### 1.2 Typed structural equivalence under identifier renaming
- **Definition**: Two executions are equivalent if their object-centric graphs (nodes = objects, edges = O2O relations) are isomorphic after renaming local identifiers. External objects (EXT-*) are treated as distinct.
- **Invariants preserved**: Object types, multiplicities, O2O relations (excluding qualifiers), external object participation.
- **Information discarded**: Specific identifiers, O2O qualifiers (e.g., `removed_before_dispatch`), event timestamps.
- **Properties**: Reflexive, symmetric, transitive.
- **Concurrency handling**: Ignores event order; focuses on structural relations.

### 1.3 Business-semantic equivalence
- **Definition**: Two executions are equivalent if they share:
  - The same lifecycle motifs (e.g., "single package dispatch," "split deliveries").
  - The same multiplicities of key objects (e.g., number of packages, invoices).
  - The same treatment of external objects (shared vs. isolated).
  - The same O2O qualifiers (e.g., replacement, return).
- **Invariants preserved**: Business logic (e.g., partial payments, cross-order sharing), object roles.
- **Information discarded**: Exact identifiers, minor event reorderings (if semantically irrelevant).
- **Properties**: Reflexive, symmetric, transitive (if motifs are consistently defined).
- **Concurrency handling**: Partial orders may be preserved if they affect semantics (e.g., Pack before Dispatch).

### 1.4 Optional: Behavioral equivalence with partial orders
- **Definition**: Extends business-semantic equivalence by requiring that causal dependencies (e.g., Pack  Dispatch) are preserved, but allows independent events to be reordered.
- **Use case**: Useful for detecting deviations in process flow while ignoring irrelevant timing.

## 2. Canonical signatures
For **business-semantic equivalence**, we define a canonical signature as a tuple:
`(lead_object_type, object_multiplicities, external_objects, o2o_qualifiers, lifecycle_motifs)`

**Pseudocode**:
```python
def canonical_signature(execution):
    # Parse events and O2O notes
    objects = set()
    external_objects = set()
    o2o_qualifiers = set()
    lifecycle_motifs = set()
    multiplicities = {"Item": 0, "Package": 0, "Delivery": 0, "Invoice": 0, "Payment": 0}

    for event in execution.events:
        for obj_type, obj_ids in event.objects.items():
            for obj_id in obj_ids.split(","):
                if obj_id.startswith("EXT"):
                    external_objects.add(obj_id)
                else:
                    objects.add((obj_type, obj_id))
                multiplicities[obj_type] += 1

    # Extract O2O qualifiers (e.g., "replaced", "returned")
    for note in execution.o2o_notes:
        if "replaces" in note or "removed_before_dispatch" in note:
            o2o_qualifiers.add("replacement")
        if "Return" in note:
            o2o_qualifiers.add("return")

    # Detect lifecycle motifs
    if multiplicities["Package"] > 1:
        lifecycle_motifs.add("split_packages")
    if multiplicities["Delivery"] > 1:
        lifecycle_motifs.add("split_deliveries")
    if multiplicities["Payment"] > 1:
        lifecycle_motifs.add("partial_payment")
    if external_objects:
        lifecycle_motifs.add("cross_order_sharing")

    return (
        "Order",
        tuple(sorted(multiplicities.items())),
        tuple(sorted(external_objects)),
        tuple(sorted(o2o_qualifiers)),
        tuple(sorted(lifecycle_motifs))
    )
```

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**PM4Py's approach**:
- Preserves exact object identifiers, activity labels, and timestamps.
- **Problem**: Raw identifiers make clusters too fine (e.g., X1 and X2 would differ).

**Canonicalization steps**:
1. Replace local identifiers with placeholders (e.g., `Order:O1`  `Order:O`).
2. Group by lead object type (`Order`).
3. Aggregate O2O relations (e.g., count packages per order).

**Python outline**:
```python
from pm4py.objects.ocel import cluster_equivalent_ocel

def cluster_orders(ocel):
    # Step 1: Canonicalize local identifiers
    for obj in ocel.objects:
        if not obj["id"].startswith("EXT"):
            obj["id"] = obj["type"] + ":CANON"

    # Step 2: Cluster by equivalence
    clusters = cluster_equivalent_ocel(ocel, parameters={"max_objs": 10})

    # Step 3: Post-process (e.g., merge clusters with same signature)
    canonical_clusters = {}
    for cluster_id, executions in clusters.items():
        sig = canonical_signature(executions[0])  # Use our function from Section 2
        canonical_clusters.setdefault(sig, []).extend(executions)

    return canonical_clusters
```

**When to use exact equivalence**:
- Debugging or auditing where exact object identities matter.
- **Coarser clustering**: Better for business monitoring (e.g., compliance).

**Impact of `max_objs`**:
- Large connected components (e.g., X5 with many EXT objects) may be excluded if `max_objs` is small.

## 8. Limitations and recommendation

| Purpose | Recommended Equivalence | Reason |
|---------|-------------------------|--------|
| Compliance monitoring | Business-semantic | Must detect cross-order sharing (X5/X6) and replacements (X7). |
| Operational segmentation | Typed-structural | Groups by logistics/finance patterns (e.g., split deliveries). |
| Root-cause analysis | Behavioral (partial orders) | Needs causal dependencies (e.g., Pack  Dispatch). |
| Descriptive reporting | Activity-sequence | High-level trends (e.g., "80% of orders are baseline"). |

**Why no single notion is best**:
- **Compliance**: Needs fine-grained semantics (e.g., external objects).
- **Operations**: Needs structural patterns (e.g., package counts).
- **Root-cause**: Needs temporal/causal details.
- **Reporting**: Needs simplicity (activity labels suffice).

**Key trade-off**: Precision vs. interpretability. Business-semantic equivalence balances both but requires careful definition of motifs and qualifiers.
