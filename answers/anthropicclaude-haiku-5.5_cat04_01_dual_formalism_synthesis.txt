# 1. Assumptions and Interpretation

1. **Abbreviations used in traces.** RD = Register Deviation, CM = Contain Material, RC = Analyze Root Cause, PV = Plan Verification, CA = Design Corrective Action, SR = Supervisor Review, QR = Quality Review, GR = Regulatory Review, CS = Consult Supplier, ET = Execute Trial, IT = Inspect Trial, AP = Adjust Parameters, RM = Release Material, AC = Archive Case.

2. **Observation and precedence.** Only completions are recorded. An edge X  Y means that X completes before Y starts. A case is one run. Cases do not interact.

3. **"May overlap" means absence of an order constraint.** Both models allow interleavings and simultaneous execution. Observable traces record only completions, so they show linearizations. Neither model claims to observe true overlap. Where a Petri-net view is used, concurrency is read as independent enabling.

4. **Low/high risk.** Each case takes exactly one route: SR (low) or QR  GR (high). This is an XOR over case properties. No data condition is encoded in the model. The route is entered after RC in the intended model. The process tree places the XOR in its second phase, which is an approximation (see §3). The POWL places it after RC.

5. **Optional supplier consultation.** The model uses XOR(CS, skip), where skip is a silent transition. CS is not inside a loop, so it occurs at most once. Selection is a case property and is not encoded. CS may start after RC and must complete before RM.

6. **Passing inspection is not an event label.** The passing inspection is abstracted as the loop exit point. The trial loop may exit after any IT. An IT followed by AP is a failed inspection. The IT that is not followed by AP is the passing one. Consequences:
   - AP can never be the last trial-related event before exit. This is the required "no AP after passing inspection" property.
   - The model cannot forbid "exit after a failed inspection." That condition is a data assumption: the process engine must guarantee that the loop exits only on pass.

7. **Duplicate visible labels.** Not permitted in either model. Each visible label occurs in exactly one model node. Repetition arises only from the LOOP operator. Traces therefore contain repeated labels (ET, IT, AP) that correspond to iterations of the same node. Silent transitions are unlabeled and never appear in traces.

8. **Approximation policy for the process tree.** Conservative under-approximation in the second phase. The approval route and CS are placed after the completion of both phase-one streams (PV and CA). This over-constrains the start times of these activities. No tree trace violates an intended dependency. Every intended precedence is preserved; some intended interleavings are excluded.

9. **POWL.** Intended to be exact with respect to the dependency set in §2. No approximation is applied, apart from the outcome abstraction in item 6.

10. **Multiplicity and liveness.** Each approval activity executes at most once per case. Every case reaches Archive Case. The empty trace is excluded. Trial iteration is finite (fairness).

# 3. PM4Py Process-Tree Model

## Compact expression

```text
SEQ(
  RD,
  PAR( SEQ(CM, PV), SEQ(RC, CA) ),
  PAR(
    LOOP( SEQ(ET, IT), AP ),
    XOR( SR, PAR(QR, GR) ),
    XOR( CS, tau )
  ),
  RM,
  AC
)
```

Legend: SEQ = sequence, PAR = parallel, XOR = exclusive choice, LOOP(do, redo) = do, then optionally redo and do again, tau = silent step.

## Python code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def activity(label):
    """Visible leaf. Each label appears exactly once in the tree."""
    node = ProcessTree(operator=None, label=label)
    node.children = []  # leaves carry no children
    return node


def silent():
    """Invisible leaf (tau). Used as the skip branch of optional supplier consultation."""
    node = ProcessTree(operator=None, label=None)
    node.children = []
    return node


def operator_node(operator, *children):
    """Internal node. Children are inserted and parent pointers are set explicitly."""
    node = ProcessTree(operator=operator, label=None)
    node.children = []
    for child in children:
        child.parent = node
        node.children.append(child)
    return node


tree = operator_node(
    Operator.SEQUENCE,
    activity("Register Deviation"),
    operator_node(
        Operator.PARALLEL,
        operator_node(
            Operator.SEQUENCE,
            activity("Contain Material"),
            activity("Plan Verification"),
        ),
        operator_node(
            Operator.SEQUENCE,
            activity("Analyze Root Cause"),
            activity("Design Corrective Action"),
        ),
    ),
    operator_node(
        Operator.PARALLEL,
        operator_node(
            Operator.LOOP,
            operator_node(
                Operator.SEQUENCE,
                activity("Execute Trial"),
                activity("Inspect Trial"),
            ),
            activity("Adjust Parameters"),
        ),
        operator_node(
            Operator.XOR,
            activity("Supervisor Review"),
            operator_node(
                Operator.PARALLEL,
                activity("Quality Review"),
                activity("Regulatory Review"),
            ),
        ),
        operator_node(
            Operator.XOR,
            activity("Consult Supplier"),
            silent(),
        ),
    ),
    activity("Release Material"),
    activity("Archive Case"),
)
tree.parent = None  # root

# Sanity check: 14 visible labels, each exactly once, plus one silent leaf.
def _leaves(node):
    if not node.children:
        return [node]
    return [leaf for child in node.children for leaf in _leaves(child)]

_visible = [n.label for n in _leaves(tree) if n.label is not None]
assert len(_visible) == len(set(_visible)) == 14
assert sum(1 for n in _leaves(tree) if n.label is None) == 1
```

The string expression in this section is a documentation aid. The tree is built directly with object constructors, so `pm4py.parse_process_tree` is not used. Its string syntax varies across versions, and the expression is not guaranteed to round-trip.

## Mapping to the narrative

- The outer SEQ enforces RD first and AC last, and places RM before AC.
- The first PAR gives independent streams CMPV and RCCA. It lets them interleave, which covers D3, D4, D5, and D6.
- The second PAR contains the trial loop, the risk XOR, and the supplier XOR. Its entry is after the first PAR completes, so every activity in it waits for PV and CA.
- The trial loop LOOP(SEQ(ET, IT), AP) produces (ET IT)(AP ET IT)*. The exit occurs after IT, so AP never follows the final IT.
- The risk XOR gives exactly one route. QR and GR run concurrently in the high route.
- XOR(CS, tau) makes supplier consultation optional and at most once. Since it sits in the second PAR, CS may overlap the trial and approvals.
- RM follows the second PAR, so it waits for the trial, the approval route, and CS if selected.

## Exact and approximated requirements

The tree represents the following exactly:
- RD first and AC last (D22).
- CM  RC (D3), with CM  PV (D4) and RC  CA (D5).
- PV  CA (D6). Both PV and CA are required before ET (D12, D13).
- ET starts only after PV and CA (the first PAR is a complete join).
- The trial loop, including the no-AP-after-final-IT property (D14–D17).
- XOR between SR and QR  GR, with QR  GR in either order (D7–D9).
- CS at most once, and CS completes before RM (D10, D11).
- Release synchronization: the trial, the approval route, and CS (if selected) complete before RM (D20).
- Overlap of the trial loop with the approval route and with CS (D18, D19), within the second phase.

The tree represents the following only through approximation:
- **D7 (route after RC):** the risk route is entered only after PV and CA complete. The intended model allows it to start as soon as RC completes. The tree rejects routes that complete before PV or CA, for example the trace RD, CM, RC, GR, QR, PV, CA, ET, IT, RM, AC.
- **D10 (CS after RC):** CS is also deferred to the second phase. The tree rejects supplier consultation that overlaps CM, PV, or CA.
- **D18 and D19 (overlap with design and planning):** the approval route and CS cannot overlap PV or CA. This is a restriction of concurrency.
- The approximation is conservative. Every tree trace satisfies every intended dependency. The tree admits no forbidden behavior, but it excludes some intended behavior.

# 4. PM4Py POWL Model

## Compact description

```text
Root = SPO over nodes {RD, CM, RC, PV, CA, RISK, SUP, TRIAL, RM, AC}
  edges:
    RD -> CM,   RD -> RC
    CM -> PV
    RC -> CA
    RC -> RISK,   RC -> SUP
    CA -> TRIAL,  PV -> TRIAL
    TRIAL -> RM,  RISK -> RM,  SUP -> RM
    RM -> AC

RISK  = XOR( SR, SPO{ QR, GR } with no edge )
SUP   = XOR( CS, SilentTransition )
TRIAL = LOOP( do = SPO{ ET -> IT }, redo = AP )
```

## Python code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# Visible activities
register_deviation = Transition("Register Deviation")
contain_material = Transition("Contain Material")
analyze_root_cause = Transition("Analyze Root Cause")
plan_verification = Transition("Plan Verification")
design_corrective = Transition("Design Corrective Action")
supervisor_review = Transition("Supervisor Review")
quality_review = Transition("Quality Review")
regulatory_review = Transition("Regulatory Review")
consult_supplier = Transition("Consult Supplier")
execute_trial = Transition("Execute Trial")
inspect_trial = Transition("Inspect Trial")
adjust_parameters = Transition("Adjust Parameters")
release_material = Transition("Release Material")
archive_case = Transition("Archive Case")

# High-risk route: QR and GR are unordered (concurrent, either completion order).
high_risk_route = StrictPartialOrder(nodes=[quality_review, regulatory_review])

# Risk choice: exactly one of low (SR) or high (QR  GR).
risk_route = OperatorPOWL(
    operator=Operator.XOR,
    children=[supervisor_review, high_risk_route],
)

# Optional supplier consultation, at most once: XOR(CS, silent skip).
supplier_option = OperatorPOWL(
    operator=Operator.XOR,
    children=[consult_supplier, SilentTransition()],
)

# Trial cycle body: ET before IT.
trial_body = StrictPartialOrder(nodes=[execute_trial, inspect_trial])
trial_body.order.add_edge(execute_trial, inspect_trial)

# Repeat-until: do = (ET -> IT), redo = AP. Exit occurs after an IT.
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_body, adjust_parameters],
)

# Top-level partial order with explicit cross-branch dependencies.
powl = StrictPartialOrder(
    nodes=[
        register_deviation,
        contain_material,
        analyze_root_cause,
        plan_verification,
        design_corrective,
        risk_route,
        supplier_option,
        trial_loop,
        release_material,
        archive_case,
    ]
)

o = powl.order
o.add_edge(register_deviation, contain_material)   # D1
o.add_edge(register_deviation, analyze_root_cause) # D2
o.add_edge(contain_material, plan_verification)    # D4
o.add_edge(analyze_root_cause, design_corrective)  # D5
o.add_edge(analyze_root_cause, risk_route)         # D7
o.add_edge(analyze_root_cause, supplier_option)    # D10
o.add_edge(design_corrective, trial_loop)          # D12
o.add_edge(plan_verification, trial_loop)          # D13
o.add_edge(trial_loop, release_material)           # D20 (trial pass)
o.add_edge(risk_route, release_material)           # D20 (approval route)
o.add_edge(supplier_option, release_material)      # D11, D20 (supplier)
o.add_edge(release_material, archive_case)         # D21
```

## Justification of intentional concurrency

- **contain_material  analyze_root_cause.** Both start after registration. No intended order exists between them (D3).
- **plan_verification  analyze_root_cause, plan_verification  design_corrective, contain_material  design_corrective.** PV depends only on CM. CA depends only on RC. Neither depends on the other stream's partner (D4–D6).
- **risk_route  contain_material, plan_verification, design_corrective.** The route depends only on analysis. Its completion before release is enforced by the edge to release (D7).
- **risk_route  trial_loop.** Approval may overlap the trial cycle (D18).
- **supplier_option  contain_material, plan_verification, design_corrective, risk_route, trial_loop.** Supplier consultation may start after analysis and overlap design, planning, approval, and trial (D19). Its completion before release is enforced by the edge to release.
- **quality_review  regulatory_review.** The high route runs both in either order (D9).
- **trial_loop  contain_material.** Not ordered in the intended model. The trial cannot start before PV and CA, and PV requires CM. Overlap with CM is therefore constrained transitively, not by a direct edge.

# 7. Preferred Representation and Validation Plan

## Canonical representation

I choose the **POWL model** as the canonical representation, for three reasons:
1. It expresses the cross-stream edges (CMPV, RCCA, RCrisk, RCCS, D/Ptrial, trial/risk/CSrelease) directly. A process tree cannot express these without duplicating or restructuring nodes.
2. It is exact with respect to the intended dependency set in §2, apart from the outcome abstraction.
3. Its loops and choices are explicit operators, so the repeat-until and optional-supplier semantics are local and inspectable.

The process tree is retained as an export format that approximates the canonical model. It is a conservative under-approximation. Any use of the tree for compliance must state that it excludes the approval and supplier overlaps.

## Validation plan

1. **Conversion to accepting Petri nets.** Convert the POWL with `pm4py.convert_to_petri_net(powl)` and the tree with `pm4py.convert_to_petri_net(tree)`, where supported. Each conversion returns a net with initial marking `im` and final marking `fm`. Verify that the net has exactly one source and one sink, and that all transitions carry the intended labels.

2. **Soundness checking.** Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on each converted net. Soundness must hold for both nets: option to complete, proper completion, and no dead transitions. Note that a passing check does not confirm fidelity, only that the net can complete cleanly.

3. **Bounded playout.** Enumerate traces up to a length bound (for example 20 events) and a loop-iteration bound (for example, at most three AP occurrences). Compare the sets of traces from the POWL net and the tree net. The expected result is that the tree trace set is a strict subset of the POWL set. Any tree trace missing from the POWL set is a bug. The playout signature (`pm4py.play_out`) differs across versions, so verify it before use.

4. **Positive tests.** W1–W5 must appear in the POWL-derived trace set. W1, W2, W5 must appear in the tree set. W3 and W4 must be absent from the tree set (this is the expected approximation).

5. **Negative tests.** F1–F3 must be absent from both sets. Additional negative tests:
   - RD, CM, RC, PV, CA, ET, IT, AP, RM, AC (AP after the final IT). Must be absent from both sets.
   - RD, CM, RC, PV, CA, RM, AC (release without trial). Must be absent.
   - RD, CM, RC, PV, CA, ET, IT, SR, RM, AC with CS present twice, for example RD, CM, RC, PV, CA, CS, CS, ET, IT, SR, RM, AC. Must be absent (at most once).

6. **Silent-behavior check.** Count, across playouts, the number of traces with and without CS. Both must occur. Confirm that the silent skip does not produce empty or duplicated CS traces. Confirm that every trace contains exactly one of the two risk routes, and that the silent leaf never blocks release (CS is absent from traces where skip is chosen, and RM still occurs).

7. **Duplicate-label check.** Construct a mutant in which a second transition labelled "Inspect Trial" is added in parallel with the trial loop. Label-based replay accepts traces that should be rejected. For example, RD, CM, RC, PV, CA, ET, IT, IT, RM, AC is accepted by the mutant, because the second IT can be attributed to the mutant transition. The check is that the uniqueness assertion (`len(labels) == len(set(labels))`) fails on the mutant, and that the trace-set comparison detects the extra trace.

8. **Oracle comparison.** Implement a small independent checker for the §2 dependencies directly on visible traces, with completion-based precedence. Compare its verdicts on the playout set with the net-based verdicts.

## Limitations of the validation

- Only completions are observable. Overlap and true concurrency cannot be verified from the trace set. The checks confirm only the order constraints that are visible.
- Pass and fail outcomes are not observable. The check that AP never follows the final IT is structural, and cannot test whether exit occurs on a real pass.
- Bounded playout cannot prove that an infinite-loop property holds. It tests only the bounded language.
- Soundness and conversion success do not prove fidelity to the business process. They establish internal well-formedness.
- The oracle and the models share the same author's interpretation of §1, so they can share a misreading.

# 8. Final Self-Critique

1. **Semantic weakness (most important).** The process tree's phase-two barrier is a conservative under-approximation, and it is not merely a syntax artifact. It delays the risk route and supplier consultation until both PV and CA finish. This forbids the intended early review of root cause (W3) and early supplier engagement during design (W4). The approximation is safe, since no forbidden trace is admitted. However, the business effect is real: cases that could have been reviewed earlier are held back. The analysis of this trade-off is limited to the trace-level evidence in W3 and W4. I have not measured how often the constraint is binding in practice.

2. **Observational limit on overlap claims.** Completion-only traces cannot distinguish true concurrency from fast sequential execution. W1 is described as "approval during the trial cycle," but the trace shows only that SR completes between ET and IT. Both interleaving and true concurrency would produce this trace. My claims about overlap are therefore claims about permitted order, not about observed parallel execution.

3. **Unverified code and API details.** I have not executed the Python code. Several details are assumed rather than confirmed for a particular PM4Py version: the keyword signatures of `ProcessTree`, `OperatorPOWL`, and `StrictPartialOrder`; whether `pm4py.convert_to_petri_net` accepts POWL objects in the installed version; and the signature of `pm4py.play_out`. The witness verdicts were derived by hand from the intended semantics and the operator semantics, not by running a checker. These are plausible and internally consistent, but they should be verified before the model is relied upon.
