# 1. Assumptions, objectives, and decision variables

This section makes the modelling choices explicit. The prompt supplies ranges, percentages, and expected arrivals, but not full distributions or a historical event log, so several labelled assumptions are necessary.

## Demand and service assumptions

- **A1. Arrival process.** For stochastic calculations and the Python simulation, expected arrivals in each two-hour block are treated as Poisson means. For hand calculations, expected arrivals are used directly. This is needed because only expected arrivals are supplied.
- **A2. Service-time distributions from ranges.** Each “ordinary” and “complex-tail” range is treated as a uniform distribution. For hand calculations, midpoints are used. For simulation, a draw is made from the appropriate uniform range.
- **A3. Complex-tail probability.** For each activity, the complex-tail probability is applied independently per case and activity. In U4, diagnostic complex-tail probabilities double, capped at 1.0.
- **A4. Resource multipliers.** A multiplier is applied multiplicatively to the base service draw. A multiplier of 1.25 means the activity consumes 25% more resource time.
- **A5. Average-multiplier estimates.** For approximate capacity calculations, average skill multipliers are used. Actual policy simulations sample resources according to policy-specific dispatch rules.
- **A6. ME/ES parallelism.** Parallel execution reduces elapsed diagnostic time but consumes two resources and adds 8 minutes of coordination. Sequential execution avoids the 8-minute coordination delay and can avoid handover/team-move delay if the same cross-skilled resource retains the case, but it increases the case critical path.
- **A7. U2 interpretation.** “E and ES demand doubles from 12:00–16:00; proportions are renormalized” is interpreted as the expected number of E and ES cases doubling in those blocks, with the total expected arrivals increasing accordingly. An alternative interpretation would keep total arrivals fixed and only renormalize the type mix; that would make U2 less severe.
- **A8. Handovers and setups.** The 7-minute handover, 5-minute mechanical/electrical-software team move, 5-minute setup, and 8-minute parallel coordination are treated as deterministic delays. Setup is applied when a resource switches diagnostic skill family between consecutive cases, not between branches of the same case.
- **A9. Preemption.** P1 preemption is allowed only for diagnostic work, at most once per preempted case. The restart penalty is approximated as 10% of the remaining active service time. Because the exact remaining time depends on fine-grained scheduling, the Python model approximates remaining time as half of the diagnostic resource load for a preempted case.
- **A10. Overtime.** Overtime is a limited buffer of up to 30 minutes per resource per day. In hand calculations it is treated as a resilience buffer, not as base capacity. In the Python model, overtime is added to a resource’s capacity only if that resource’s sampled load exceeds regular available time.

## How ranges become distributions or bounds

For an activity with ordinary range \([a,b]\), complex-tail range \([c,d]\), and complex-tail probability \(p\):

- Simulation draws:
  \[
  S =
  \begin{cases}
  U(a,b), & \text{with probability } 1-p \\
  U(c,d), & \text{with probability } p
  \end{cases}
  \]
- Hand calculations use:
  \[
  E[S] \approx (1-p)\frac{a+b}{2} + p\frac{c+d}{2}
  \]
- Bounds can be constructed from minimum ordinary and maximum tail values, but the spread is wide. Therefore the analysis prefers midpoint estimates plus explicit uncertainty ranges.

## ME/ES parallelism decision

Parallelism is not treated as always optimal. The decision depends on priority, resource availability, and policy.

- **Parallel** is favoured for P1 cases when the elapsed-time saving is worth the extra resource consumption and 8-minute coordination.
- **Sequential** is favoured for P2/P3 cases when the system is congested, especially if a cross-skilled resource can retain the case and avoid handover/team-move penalties.
- For ME, sequential execution on one cross-skilled resource can avoid:
  - 7-minute handover between resources,
  - 5-minute mechanical/electrical-software team move,
  - 8-minute parallel coordination.
  The trade-off is a longer case critical path.
- For ES, the extra 5-minute mechanical/electrical-software team move does not apply because Electrical and Software are both in the electrical/software team, but sequential same-resource execution can still avoid handover and coordination.

## Objective formulations

At least two objective functions are useful.

### Objective 1: SLA/tail-risk objective

This objective prioritizes P1 protection and tail delay.

\[
\min_{\pi}
\left[
w_1 \Pr(P1 > 120)
+ w_2 \Pr(P2 > 480)
+ w_3 \Pr(P3 > 1440)
+ w_4 \text{P90 delay}
+ w_5 \text{mean delay}
\right]
\]

where \(\pi\) is a staffing/routing policy. A reasonable weighting for an incident process is \(w_1 > w_2 > w_3\), because P1 cases have the tightest target.

### Objective 2: fairness/robustness objective

This objective penalizes fragile base-case solutions that fail under shocks.

\[
\min_{\pi}
\max_{s \in \{\text{base}, U1,\dots,U5\}}
\left[
\alpha_s \text{P90 delay}_s
+ \beta_s \max_r U_{r,s}
+ \gamma_s (1 - F_s)
+ \delta_s \text{SLA violation}_s
\right]
\]

where:

- \(U_{r,s}\) is utilization of resource \(r\) in scenario \(s\),
- \(F_s\) is a fairness index, for example \(1 - \text{normalized std}(U_{r,s})\),
- \(\max_r U_{r,s}\) penalizes operational fragility,
- the max over scenarios enforces robustness.

A policy that minimizes base-case mean delay but collapses in U1 or U5 is not robust under this second objective.

## Decision variables

The main decision variables are:

1. Eligibility set for each activity.
2. Priority/dispatch score.
3. Reservation of P1 capacity.
4. Preemption trigger and target selection.
5. Parallel versus sequential branch choice.
6. Handover/setup minimization preference.
7. Overflow trigger from specialized queues to pooled resources.
8. Overtime use.

# 3. Candidate policies

Three concrete policies are compared. They are described operationally, not merely by labels.

## Policy 1: Strict specialization with fixed queues, “SPEC”

### Eligibility

- Intake and Validation: any available resource with Intake/Validation skill.
- Mechanical: only Mechanical-qualified resources.
- Electrical: only Electrical-qualified resources.
- Software: only Software-qualified resources.
- No deliberate cross-skill overflow.

### Priority rule

- Within each queue: P1 first, then P2, then P3.
- P1 may preempt a lower-priority diagnostic activity only within the same skill queue.
- Preemption is allowed at most once per preempted case.

### Parallelization

- ME/ES parallelized for P1 and, if resources appear idle, for some P2 cases.
- P3 cases are usually sequential to avoid coordination overhead.

### Handover/setup behaviour

- Setup burden is relatively low because queues are skill-specific.
- Handover burden can be high because Intake, diagnostic, and Validation may be performed by different resources.
- ME/ES cases often require two resources, causing coordination overhead.

### Overflow trigger

- None. This is the defining limitation.

### Operational strength

- Simple to explain.
- Low skill-switching overhead.
- Clear ownership.

### Operational weakness

- Poor resilience when one skill queue is congested.
- Poor response to U2, U3, and U5.
- P1 cases can wait behind lower-priority cases in a scarce skill queue.

## Policy 2: Full pooling with transparent dispatch, “POOL”

### Eligibility

- Any active resource with the required skill is eligible.
- Cross-skilled resources can move between Mechanical, Electrical, and Software queues.
- Intake and Validation are fully pooled among all resources.

### Dispatch score

For a job \(j\) and eligible resource \(r\), compute:

\[
\text{Score}(j,r) =
\text{PriorityWeight}_j
+ \text{SLAUrgency}_j
- \text{EstimatedFinish}(j,r)
- 2 \times \text{ExpectedHandoverSetup}(j,r)
- 10 \times I(U_r > 0.90)
\]

where:

- PriorityWeight is 1000 for P1, 200 for P2, 0 for P3.
- SLAUrgency increases as time-to-deadline decreases.
- EstimatedFinish uses expected remaining service time adjusted by resource multiplier.
- ExpectedHandoverSetup penalizes assignments that would cause handover or setup.
- The utilization penalty discourages overloading already busy resources.

The job is assigned to the eligible resource with the highest score, equivalently earliest adjusted finish with priority and penalty adjustments.

### Preemption

- P1 may preempt P3 diagnostic work if no eligible resource is available within 10 minutes.
- P1 may preempt P2 only if P2 has ample SLA slack, for example more than 6 hours remaining.
- Preempted case receives the 10% remaining-service restart penalty.
- A case is preempted at most once.

### Parallelization

- ME/ES parallelized for P1 if two qualified resources can start within about 15 minutes.
- P2/P3 ME/ES cases are usually sequential if a cross-skilled resource can retain the case.
- Parallelization is suppressed if the system is already above 90% utilization in the relevant skill groups.

### Handover minimization

- If sequential ME/ES can be retained by one cross-skilled resource, that assignment is preferred.
- Otherwise, the dispatcher chooses the resource with lowest combined finish-time and handover/setup penalty.

### Overflow trigger

- Implicit and continuous: any qualified resource may take any job.

### Operational strength

- Best load balancing.
- Best response to local skill shortages.
- Strong P1 protection through priority and preemption.

### Operational weakness

- Higher setup and handover churn.
- More complex to audit unless dispatch decisions are logged.
- Risk of excessive preemption if thresholds are too aggressive.

## Policy 3: Hybrid P1 protection with controlled overflow, “HYBRID”

### Eligibility

- P1 cases: pooled across all qualified resources.
- P2/P3 cases: initially handled by skill-specific queues.
- Controlled overflow for P2/P3 when queue wait exceeds thresholds.

### P1 reservation

- During 08:00–12:00 and 14:00–16:00, reserve one Electrical/Software-capable resource for P1 work when the P1 queue is nonempty.
- If Chen is present, Chen is the preferred reserved E/S resource.
- If Chen is absent, Emil is preferred for Software/Electrical reservation; Ada or Deepa may be used for Electrical reservation.
- Reserved resource may take P2/P3 only if idle for more than 15 minutes and no P1 is expected soon.

### Overflow triggers for P2/P3

Overflow from specialized queue to pooled qualified resources occurs when:

- Mechanical queue wait exceeds 30 minutes.
- Electrical queue wait exceeds 45 minutes.
- Software queue wait exceeds 45 minutes.
- Intake or Validation queue wait exceeds 15 minutes.
- Block-level utilization exceeds 90%.

### Preemption

- P1 may preempt P3 diagnostic work if projected P1 delay exceeds 20 minutes.
- P2 preemption is avoided unless P1 SLA risk is severe.
- Preemption is limited to once per case.

### Parallelization

- P1 ME/ES cases parallelize if two qualified resources are available.
- P2/P3 ME/ES cases prefer sequential execution, especially if a cross-skilled resource can retain the case.
- Parallelization is suppressed when E/S utilization exceeds 90%.

### Handover minimization

- Sequential same-resource retention is preferred for P2/P3 ME/ES cases.
- Handover is accepted for P1 if it reduces elapsed time.

### Operational strength

- Protects P1 better than SPEC.
- Less setup churn than POOL.
- More auditable than full pooling because overflow and reservation triggers are explicit.

### Operational weakness

- Reserved capacity can appear idle.
- P2/P3 cases can be delayed.
- Requires monitoring to avoid starvation.

# 5. Robust recommendation

## Primary recommendation: HYBRID with crisis fallback to POOL

The recommended primary policy is **Policy 3: Hybrid P1 protection with controlled overflow**.

It is recommended under the robustness/fairness objective because:

1. It protects P1 cases better than strict specialization.
2. It avoids the full setup/preemption churn of full pooling under normal conditions.
3. It has explicit overflow triggers, making it easier for operators to audit.
4. It performs reasonably across U1–U5, especially compared with SPEC.
5. It can degrade gracefully into full pooling during crisis periods.

## Fallback mode: crisis POOL

The system should switch from HYBRID to POOL when any of the following triggers hold:

- Rolling 30-minute P1 queue length exceeds 2.
- Predicted P1 SLA attainment for the next 60 minutes falls below 90%.
- Electrical/Software utilization exceeds 110% for more than 20 minutes.
- Chen is absent and Software queue wait exceeds 30 minutes for P1 or 60 minutes for P2.
- Intake backlog exceeds 15 minutes during a surge block.

Return to HYBRID when:

- P1 queue length is below 1 for 30 minutes.
- Electrical/Software utilization is below 90% for 30 minutes.
- Predicted P1 SLA attainment is above 95% for the next hour.

## Parallelization thresholds

Recommended parallelization rule:

- P1 ME/ES: parallel if two qualified resources can start within 10–15 minutes.
- P2 ME/ES: parallel only if the relevant skill groups are below 80% utilization.
- P3 ME/ES: sequential by default.
- If Electrical/Software utilization exceeds 90%, restrict parallelization to P1 only.

## Overtime thresholds

Use overtime when:

- End-of-block backlog exceeds 20% of remaining shift capacity.
- P1 cases are at risk of missing SLA.
- The next arrival block is expected to be high-load.
- A scarce resource, especially Software-capable, is required to bridge a staffing cliff.

Do not rely on overtime as structural capacity; it is a shock absorber.

## When another policy would be preferable

- **POOL is preferable** if the objective is purely minimizing average delay and the organization accepts higher setup/preemption overhead. It may also be preferable during U3 or U5 if P1 is already protected and the main problem is P2/P3 backlog.
- **SPEC is preferable** only in unusually low-demand periods, when skill depth and low setup overhead matter more than resilience, or when cross-skilled work is operationally unsafe.

# 6. Secondary effects and implementation risks

## Gaming of estimates

If dispatch uses estimated service times or predicted SLA risk, staff may have incentives to misclassify cases:

- Overstating complexity to obtain more time.
- Understating complexity to avoid being preempted.
- Splitting work into artificial activities to reset clocks.

Mitigation:

- Log planned versus actual service time by activity and resource.
- Use case-type and priority audits.
- Make estimates model-driven rather than manually editable where possible.

## Starvation of P3 work

HYBRID and POOL can both starve P3 cases during repeated P1 surges.

Mitigation:

- Add aging: P3 priority score increases after 6 hours, then more sharply after 12 hours.
- Reserve a small P3 protection window, for example one non-P1 slot per hour when P3 backlog exceeds a threshold.
- Monitor P3 completion rate and maximum P3 age.

## Skill erosion

If pooling always assigns work to the fastest qualified resources, other resources may lose practice.

Mitigation:

- Use a fairness penalty in dispatch.
- Rotate non-urgent diagnostic work to qualified but less-utilized resources.
- Track skill usage by resource and skill family.

## Excessive preemption

Preemption protects P1 but imposes a 10% restart penalty and can create cascading delays.

Mitigation:

- Limit preemption to once per case.
- Prefer preempting P3 over P2.
- Avoid preempting activities with less than 10 minutes remaining unless P1 is extremely urgent.
- Monitor preemptions per hour and penalty minutes per case.

## Coordination overhead

Parallel ME/ES cases save elapsed time but add 8 minutes of coordination and consume two resources.

Mitigation:

- Parallelize P1 only when resources are genuinely available.
- Prefer sequential same-resource execution for P2/P3 when utilization is high.
- Track coordination minutes per case type.

## New bottleneck at Validation

If diagnostics are accelerated, Validation may become the bottleneck because all cases require Validation and all resources perform it.

Mitigation:

- Monitor Validation queue length and waiting time separately.
- Reserve Validation capacity when diagnostic completion rate spikes.
- Avoid assigning the same resource to consecutive long diagnostic jobs if Validation queue is growing.

## Fairness and workload balance

Without fairness controls, Ada, Chen, Emil, or Deepa may become overused depending on scenario.

Mitigation:

- Track resource utilization by block.
- Penalize assignments to resources above 90% utilization.
- Use overtime fairly, not always on the same individuals.

## Human interpretability

Operators need to understand why a case was assigned.

Recommended explanation format:

- “Assigned to Chen because P1 case, Electrical skill required, earliest finish, no setup penalty.”
- “Sequential ME chosen because system utilization >90%; avoids 8-minute coordination.”
- “Preemption triggered because P1 projected delay 35 minutes; preempted P3 Software activity.”

# 7. Monitoring and process-mining design

## Event attributes required

The event log should contain at least:

- `case:concept:name`: case identifier.
- `concept:name`: activity name, for example Intake, Mechanical, Electrical, Software, Validation, Handover, Setup, PreemptionPause, PreemptionResume.
- `start_timestamp`: activity start.
- `time:timestamp`: activity end or event timestamp.
- `org:resource`: resource identifier.
- `priority`: P1/P2/P3.
- `case_type`: M/E/S/ME/ES.
- `policy_version`: SPEC/POOL/HYBRID and version number.
- `scenario_or_shock_flag`: base/U1/U2/U3/U4/U5 or live shock label.
- `queue_entry_timestamp`: when the activity entered its queue.
- `assignment_decision_timestamp`: when dispatcher assigned the resource.
- `eligible_resource_set`: resources eligible at assignment time.
- `dispatch_score`: score or explanation.
- `skill_used`: Mechanical/Electrical/Software/Intake/Validation.
- `planned_service_minutes`: expected service before actual observation.
- `actual_service_minutes`: actual active service.
- `resource_multiplier`: multiplier applied.
- `handover_minutes`: handover delay.
- `team_move_minutes`: extra 5-minute team-move delay.
- `setup_minutes`: setup delay.
- `coordination_minutes`: 8-minute parallel coordination.
- `preempted`: boolean.
- `preemption_penalty_minutes`: restart penalty.
- `pause_timestamp` and `resume_timestamp`: for interrupted activities.
- `sla_clock_start`: arrival time.
- `sla_deadline`: 120/480/1440 minutes.
- `sla_met`: boolean.
- `parallel_branch`: true/false or branch identifier.

## Deployment indicators

Monitor:

1. P1 SLA attainment over rolling 30/60 minutes.
2. P2 and P3 SLA attainment over rolling 4/24 hours.
3. Mean and P90 delay by priority and case type.
4. Queue length by activity and skill.
5. Resource utilization by two-hour block.
6. Utilization fairness index.
7. Handover rate per case.
8. Setup rate per resource shift.
9. Parallel coordination rate for ME/ES.
10. Preemption rate and preemption penalty minutes.
11. Validation waiting time.
12. Overtime used per resource.
13. Policy mode changes: HYBRID versus POOL.
14. Dispatch overrides by human supervisors.

## PM4Py analyses

### Service and waiting time analysis

Use case-level service/waiting functions to understand end-to-end time, but calculate stage-specific metrics separately because parallel branches can distort case-level sums.

Useful analyses:

- Mean service time by activity.
- Mean waiting time between Intake and diagnostic start.
- Mean waiting time between diagnostic completion and Validation.
- P95 service time by activity and case type.

### Handover-of-work network

Use `pm4py.discover_handover_of_work_network` to identify excessive resource transitions. A robust policy should reduce unnecessary handovers relative to SPEC while not creating excessive setup churn relative to POOL.

### Bottleneck migration

Split the log into time windows, for example two-hour blocks or morning/afternoon/evening. Compare:

- Queue waiting by activity.
- Resource utilization.
- Service time distributions.
- Handover frequency.
- Validation delay.

This reveals whether bottlenecks move from morning Intake to midday Electrical/Software or evening Validation.

### Drift detection

Compare planned versus actual service time by week or scenario. Drift may indicate:

- Increasing case complexity.
- Skill degradation.
- Resource fatigue.
- Incorrect multiplier assumptions.
- Policy gaming.

### Conformance checking

Compare observed control flow against the expected process:

- Intake before diagnostic.
- Diagnostic before Validation.
- ME/ES branch completeness.
- No missing Validation.
- Preemption pause/resume pairs.

def available_minutes_in_block(resource, block_start, block_end):
    s = max(resource["start"], block_start)
    e = min(resource["end"], block_end)
    if s >= e:
        return 0.0
    mins = float(e - s)
    if resource["break_start"] is not None:
        bs = max(resource["break_start"], s)
        be = min(resource["break_end"], e)
        if be > bs:
            mins -= float(be - bs)
    return max(0.0, mins)

def scenario_expected_rows(scenario):
    rows = []
    for _, row in DEMAND.iterrows():
        exp = float(row["expected_arrivals"])
        p1 = float(row["P1_pct"])
        p2 = float(row["P2_pct"])
        p3 = float(row["P3_pct"])

        if scenario in ["U1", "U5"] and row["block_start"] < 240:
            exp *= 1.7
            p1 = min(100.0, p1 + 8.0)
            rem = 100.0 - p1
            old = p2 + p3
            if old > 0:
                p2 = p2 * rem / old
                p3 = p3 * rem / old

        type_counts = {t: exp * float(row[f"{t}_pct"]) / 100.0 for t in TYPE_ACTS}

        if scenario == "U2" and row["block_start"] in [240, 360]:
            type_counts["E"] *= 2.0
            type_counts["ES"] *= 2.0

        total_type = sum(type_counts.values())
        if total_type <= 0:
            continue
        type_probs = {k: v / total_type for k, v in type_counts.items()}

        priority_sum = p1 + p2 + p3
        if priority_sum <= 0:
            priority_probs = {"P1": 0.0, "P2": 0.0, "P3": 1.0}
        else:
            priority_probs = {"P1": p1 / priority_sum, "P2": p2 / priority_sum, "P3": p3 / priority_sum}

        rows.append(
            {
                "block_start": int(row["block_start"]),
                "expected_arrivals": float(total_type),
                "priority_probs": priority_probs,
                "type_probs": type_probs,
            }
        )
    return rows


def sample_cases(scenario, seed):
    rng = np.random.default_rng(seed)
    rows = scenario_expected_rows(scenario)
    cases = []
    cid = 0
    for row in rows:
        n = rng.poisson(max(0.0, row["expected_arrivals"]))
        for _ in range(int(n)):
            arrival = row["block_start"] + float(rng.uniform(0, 120))
            pr = np.array([row["priority_probs"][k] for k in ["P1", "P2", "P3"]], dtype=float)
            pr = pr / pr.sum()
            priority = rng.choice(["P1", "P2", "P3"], p=pr)

            ty = np.array([row["type_probs"][k] for k in ["M", "E", "S", "ME", "ES"]], dtype=float)
            ty = ty / ty.sum()
            ctype = rng.choice(["M", "E", "S", "ME", "ES"], p=ty)

            base_services = {}
            for act in ["Intake", "Mechanical", "Electrical", "Software", "Validation"]:
                p = tail_probability(act, scenario)
                is_tail = rng.random() < p
                lo, hi = SERVICE[act]["tail" if is_tail else "ordinary"]
                base_services[act] = float(rng.uniform(lo, hi))

            cases.append(
                {
                    "case_id": f"{scenario}_s{seed}_c{cid}",
                    "arrival": float(arrival),
                    "block_start": min(int(arrival // 120) * 120, 600),
                    "priority": priority,
                    "type": ctype,
                    "base_services": base_services,
                }
            )
            cid += 1
    return sorted(cases, key=lambda x: x["arrival"])


def choose_resource(activity, resources, priority, policy, rng, block_start, exclude=None):
    eligible = []
    weights = []
    for r in resources:
        mult = r["skills"].get(activity)
        if mult is None:
            continue
        if exclude is not None and r["name"] in exclude:
            continue
        avail = available_minutes_in_block(r, block_start, block_start + 120)
        if avail <= 0:
            continue
        w = avail / max(0.1, float(mult))
        if policy != "Specialization" and priority == "P1":
            w /= max(0.1, float(mult))
        if policy == "Specialization":
            w = avail
        eligible.append(r)
        weights.append(w)

    if not eligible:
        for r in resources:
            mult = r["skills"].get(activity)
            if mult is None:
                continue
            if exclude is not None and r["name"] in exclude:
                continue
            eligible.append(r)
            weights.append(1.0 / max(0.1, float(mult)))

    if not eligible:
        return None

    weights = np.array(weights, dtype=float)
    weights = weights / weights.sum()
    idx = rng.choice(len(eligible), p=weights)
    return eligible[idx]


def maybe_setup(resource_name, activity, setup_state, policy):
    fam = FAMILY[activity]
    prev = setup_state.get(resource_name)
    if prev is None or prev == fam:
        return 0.0
    return 5.0 * POLICIES[policy]["setup_factor"]


def decide_parallel(case, policy, rng):
    if case["type"] not in ["ME", "ES"]:
        return False
    p = case["priority"]
    if policy == "Specialization":
        return p in ["P1", "P2"]
    if policy == "Pooling":
        return p == "P1" or (p == "P2" and rng.random() < 0.35)
    if policy == "Hybrid":
        return p == "P1"
    return False


def dummy_resource(activity):
    return {"name": "Unassigned", "skills": {activity: 1.30, "Intake": 1.30, "Validation": 1.30}}


def process_case(case, policy, resources, setup_state, rng, scenario):
    block_start = case["block_start"]

    intake_res = choose_resource("Intake", resources, case["priority"], policy, rng, block_start)
    if intake_res is None:
        intake_res = dummy_resource("Intake")
    intake_service = case["base_services"]["Intake"] * float(intake_res["skills"].get("Intake", 1.3))

    handover_pre_diag = 0.0
    handover_between = 0.0
    handover_pre_val = 0.0
    setup = 0.0
    coordination = 0.0
    parallel = False
    branches = []

    acts = TYPE_ACTS[case["type"]]

    if len(acts) == 1:
        act = acts[0]
        res = choose_resource(act, resources, case["priority"], policy, rng, block_start)
        if res is None:
            res = dummy_resource(act)

        setup += maybe_setup(res["name"], act, setup_state, policy)
        if res["name"] != intake_res["name"]:
            handover_pre_diag += 7.0

        service = case["base_services"][act] * float(res["skills"].get(act, 1.3))
        branches.append({"activity": act, "resource": res["name"], "service": service})
        diag_duration = service
        last_resources = {res["name"]}
        setup_state[res["name"]] = FAMILY[act]

    else:
        act1, act2 = acts
        parallel = decide_parallel(case, policy, rng)

        if parallel:
            coordination = 8.0
            res1 = choose_resource(act1, resources, case["priority"], policy, rng, block_start)
            if res1 is None:
                res1 = dummy_resource(act1)

            res2 = choose_resource(act2, resources, case["priority"], policy, rng, block_start, exclude={res1["name"]})
            if res2 is None:
                res2 = choose_resource(act2, resources, case["priority"], policy, rng, block_start)
            if res2 is None:
                res2 = dummy_resource(act2)
            if res2["name"] == res1["name"]:
                res2 = {"name": f"Unassigned_{act2}", "skills": {act2: 1.30}}

            setup += maybe_setup(res1["name"], act1, setup_state, policy)
            setup += maybe_setup(res2["name"], act2, setup_state, policy)

            if res1["name"] != intake_res["name"]:
                handover_pre_diag += 7.0
            if res2["name"] != intake_res["name"]:
                handover_pre_diag += 7.0

            s1 = case["base_services"][act1] * float(res1["skills"].get(act1, 1.3))
            s2 = case["base_services"][act2] * float(res2["skills"].get(act2, 1.3))

            branches = [
                {"activity": act1, "resource": res1["name"], "service": s1},
                {"activity": act2, "resource": res2["name"], "service": s2},
            ]
            diag_duration = max(s1, s2) + coordination
            last_resources = {res1["name"], res2["name"]}
            setup_state[res1["name"]] = FAMILY[act1]
            setup_state[res2["name"]] = FAMILY[act2]

        else:
            retention_prob = POLICIES[policy]["retention_prob"]
            cross_resources = [
                r
                for r in resources
                if r["skills"].get(act1) is not None
                and r["skills"].get(act2) is not None
                and available_minutes_in_block(r, block_start, block_start + 120) > 0
            ]

            same = False
            if policy != "Specialization" and cross_resources and rng.random() < retention_prob:
                same = True
                weights = []
                for r in cross_resources:
                    avail = available_minutes_in_block(r, block_start, block_start + 120)
                    w = avail / max(0.1, float(r["skills"][act1])) / max(0.1, float(r["skills"][act2]))
                    if case["priority"] == "P1":
                        w /= max(0.1, float(r["skills"][act1])) * max(0.1, float(r["skills"][act2]))
                    weights.append(w)
                weights = np.array(weights, dtype=float)
                weights = weights / weights.sum()
                res = cross_resources[int(rng.choice(len(cross_resources), p=weights))]

                setup += maybe_setup(res["name"], act1, setup_state, policy)
                if res["name"] != intake_res["name"]:
                    handover_pre_diag += 7.0

                s1 = case["base_services"][act1] * float(res["skills"].get(act1, 1.3))
                s2 = case["base_services"][act2] * float(res["skills"].get(act2, 1.3))
                branches = [
                    {"activity": act1, "resource": res["name"], "service": s1},
                    {"activity": act2, "resource": res["name"], "service": s2},
                ]
                diag_duration = s1 + s2
                last_resources = {res["name"]}
                setup_state[res["name"]] = FAMILY[act2]

            if not same:
                res1 = choose_resource(act1, resources, case["priority"], policy, rng, block_start)
                if res1 is None:
                    res1 = dummy_resource(act1)

                eligible_act2_count = sum(1 for r in resources if r["skills"].get(act2) is not None)
                exclude2 = {res1["name"]} if eligible_act2_count > 1 else None
                res2 = choose_resource(act2, resources, case["priority"], policy, rng, block_start, exclude=exclude2)
                if res2 is None:
                    res2 = dummy_resource(act2)

                setup += maybe_setup(res1["name"], act1, setup_state, policy)
                setup += maybe_setup(res2["name"], act2, setup_state, policy)

                if res1["name"] != intake_res["name"]:
                    handover_pre_diag += 7.0

                if res2["name"] != res1["name"]:
                    handover_between += 7.0
                    if TEAM[act1] != TEAM[act2] and ("MECH" in [TEAM[act1], TEAM[act2]]):
                        handover_between += 5.0

                s1 = case["base_services"][act1] * float(res1["skills"].get(act1, 1.3))
                s2 = case["base_services"][act2] * float(res2["skills"].get(act2, 1.3))
                branches = [
                    {"activity": act1, "resource": res1["name"], "service": s1},
                    {"activity": act2, "resource": res2["name"], "service": s2},
                ]
                diag_duration = s1 + s2 + handover_between
                last_resources = {res1["name"], res2["name"]}
                setup_state[res1["name"]] = FAMILY[act1]
                setup_state[res2["name"]] = FAMILY[act2]

    val_res = choose_resource("Validation", resources, case["priority"], policy, rng, block_start)
    if val_res is None:
        val_res = dummy_resource("Validation")
    if val_res["name"] not in last_resources:
        handover_pre_val += 7.0
    val_service = case["base_services"]["Validation"] * float(val_res["skills"].get("Validation", 1.3))

    case.update(
        {
            "intake_resource": intake_res["name"],
            "intake_service": intake_service,
            "branches": branches,
            "diag_duration": diag_duration,
            "validation_resource": val_res["name"],
            "validation_service": val_service,
            "handover_pre_diag": handover_pre_diag,
            "handover_between": handover_between,
            "handover_pre_val": handover_pre_val,
            "setup": setup,
            "coordination": coordination,
            "parallel": parallel,
            "resource_load": intake_service + sum(b["service"] for b in branches) + val_service,
            "diag_resource_load": sum(b["service"] for b in branches),
        }
    )
    return case


def compute_utils(cases, resources, scenario, policy):
    block_load = {b: 0.0 for b in BLOCK_STARTS}
    skill_load = {b: {a: 0.0 for a in DIAG_ACTS} for b in BLOCK_STARTS}
    p1_count = {b: 0 for b in BLOCK_STARTS}
    count = {b: 0 for b in BLOCK_STARTS}

    for c in cases:
        b = c["block_start"]
        block_load[b] += c["resource_load"]
        for br in c["branches"]:
            if br["activity"] in DIAG_ACTS:
                skill_load[b][br["activity"]] += br["service"]
        count[b] += 1
        if c["priority"] == "P1":
            p1_count[b] += 1

    cap_block = {
        b: sum(available_minutes_in_block(r, b, b + 120) for r in resources)
        for b in BLOCK_STARTS
    }
    if scenario == "U5":
        # Approximate the 09:30-10:00 intake outage as reduced effective capacity in first block.
        cap_block[0] = max(1.0, cap_block[0] - 30.0)

    eff_utils = {}
    for b in BLOCK_STARTS:
        util_total = block_load[b] / max(1.0, cap_block[b])
        skill_utils = []
        for act in DIAG_ACTS:
            cap = sum(
                available_minutes_in_block(r, b, b + 120)
                for r in resources
                if r["skills"].get(act) is not None
            )
            if cap > 0:
                skill_utils.append(skill_load[b][act] / cap)
        max_skill = max(skill_utils) if skill_utils else 0.0

        if policy == "Specialization":
            eff = max(util_total, max_skill)
        elif policy == "Pooling":
            eff = 0.65 * util_total + 0.35 * max_skill
        else:
            eff = 0.80 * util_total + 0.20 * max_skill
        eff_utils[b] = min(2.5, eff)

    p1_share = {b: (p1_count[b] / count[b] if count[b] > 0 else 0.0) for b in BLOCK_STARTS}
    return eff_utils, p1_share, block_load, cap_block


def wait_from_util(util, stage, priority, policy):
    util = max(0.0, min(2.5, float(util)))
    if util < 1.0:
        congestion = util / max(0.15, 1.0 - util)
    else:
        congestion = 6.0 + (util - 1.0) * 8.0
    congestion = min(18.0, congestion)
    base = 8.0 * congestion

    stage_factor = {"Intake": 0.7, "Diagnostic": 1.0, "Validation": 0.8}[stage]
    pol_factor = {"Specialization": 1.25, "Pooling": 0.85, "Hybrid": 0.95}[policy]
    if priority == "P1":
        pri_factor = 0.75 if policy == "Specialization" else 0.55
    elif priority == "P2":
        pri_factor = 1.0
    else:
        pri_factor = 1.2

    return max(2.0, base * stage_factor * pol_factor * pri_factor)


def finalize_cases(cases, eff_utils, p1_share, policy, scenario, rng):
    for c in cases:
        util = eff_utils[c["block_start"]]
        intake_wait = wait_from_util(util, "Intake", c["priority"], policy)
        diag_wait = wait_from_util(util, "Diagnostic", c["priority"], policy)
        val_wait = wait_from_util(util, "Validation", c["priority"], policy)

        if scenario == "U5":
            if 90 <= c["arrival"] < 120:
                intake_wait += 30.0
            elif 60 <= c["arrival"] < 90:
                intake_wait += 10.0

        preempted = False
        penalty = 0.0
        if POLICIES[policy]["preempt"] and c["priority"] != "P1" and c["diag_resource_load"] > 0:
            prob = min(0.5, max(0.0, (util - 0.85) * 0.8) + 0.4 * p1_share.get(c["block_start"], 0.0))
            if rng.random() < prob:
                preempted = True
                # Approximation: preempted roughly halfway; penalty is 10% of remaining active service.
                penalty = 0.1 * 0.5 * c["diag_resource_load"]

        pre_diag_delay = c["handover_pre_diag"] + c["setup"]
        total = (
            intake_wait
            + c["intake_service"]
            + pre_diag_delay
            + diag_wait
            + c["diag_duration"]
            + c["handover_pre_val"]
            + val_wait
            + c["validation_service"]
            + penalty
        )

        c.update(
            {
                "intake_wait": intake_wait,
                "diag_wait": diag_wait,
                "val_wait": val_wait,
                "pre_diag_delay": pre_diag_delay,
                "pre_val_delay": c["handover_pre_val"],
                "preempted": preempted,
                "preemption_penalty": penalty,
                "total_elapsed": total,
            }
        )


def evaluate_policy(template_cases, policy, scenario, seed):
    rng = np.random.default_rng(seed + POLICY_SALT[policy])
    resources = active_resources(scenario)
    setup_state = {}
    cases = []

    for c0 in template_cases:
        c = copy.deepcopy(c0)
        c = process_case(c, policy, resources, setup_state, rng, scenario)
        cases.append(c)

    eff_utils, p1_share, block_load, cap_block = compute_utils(cases, resources, scenario, policy)
    finalize_cases(cases, eff_utils, p1_share, policy, scenario, rng)

    if not cases:
        return {
            "mean_delay": np.nan,
            "p90_delay": np.nan,
            "P1_SLA": np.nan,
            "P2_SLA": np.nan,
            "max_resource_utilization": np.nan,
            "utilization_fairness": np.nan,
            "handover_setup_burden": np.nan,
            "preemption_penalty_mean": np.nan,
            "resilience_score": np.nan,
            "n_cases": 0,
        }, cases

    df = pd.DataFrame(cases)
    mean_delay = float(df["total_elapsed"].mean())
    p90_delay = float(np.percentile(df["total_elapsed"], 90))

    def sla_pct(priority, limit):
        sub = df[df["priority"] == priority]
        if len(sub) == 0:
            return np.nan
        return float(100.0 * (sub["total_elapsed"] <= limit).mean())

    p1_sla = sla_pct("P1", 120)
    p2_sla = sla_pct("P2", 480)

    load = {}
    for c in cases:
        load[c["intake_resource"]] = load.get(c["intake_resource"], 0.0) + c["intake_service"]
        for br in c["branches"]:
            load[br["resource"]] = load.get(br["resource"], 0.0) + br["service"]
        load[c["validation_resource"]] = load.get(c["validation_resource"], 0.0) + c["validation_service"]

    utils = []
    for r in resources:
        base_cap = daily_available(r)
        res_load = load.get(r["name"], 0.0)
        cap = base_cap + (OVERTIME_LIMIT if res_load > base_cap else 0.0)
        if cap > 0:
            utils.append(res_load / cap)

    max_util = max([max(utils) if utils else 0.0] + list(eff_utils.values()))
    if len(utils) >= 2 and np.mean(utils) > 0:
        fairness = float(1.0 - min(1.0, np.std(utils) / max(0.01, np.mean(utils))))
    else:
        fairness = 1.0

    overhead_cols = ["handover_pre_diag", "handover_between", "handover_pre_val", "setup", "coordination"]
    handover_setup_burden = float(df[overhead_cols].sum(axis=1).mean())
    preemption_penalty_mean = float(df["preemption_penalty"].mean())
    resilience_score = float(1.0 / (1.0 + p90_delay / 480.0))

    metrics = {
        "mean_delay": mean_delay,
        "p90_delay": p90_delay,
        "P1_SLA": p1_sla,
        "P2_SLA": p2_sla,
        "max_resource_utilization": float(max_util),
        "utilization_fairness": fairness,
        "handover_setup_burden": handover_setup_burden,
        "preemption_penalty_mean": preemption_penalty_mean,
        "resilience_score": resilience_score,
        "n_cases": int(len(df)),
    }
    return metrics, cases


def build_event_log(cases, scenario, policy):
    rows = []
    deadline_map = {"P1": 120, "P2": 480, "P3": 1440}

    for c in cases:
        cid = c["case_id"]
        arrival = BASE_DATE + pd.Timedelta(minutes=float(c["arrival"]))
        deadline = deadline_map[c["priority"]]
        sla_met = c["total_elapsed"] <= deadline

        common = {
            "case:concept:name": cid,
            "priority": c["priority"],
            "case_type": c["type"],
            "scenario": scenario,
            "policy": policy,
            "sla_deadline_min": deadline,
            "sla_met": sla_met,
            "parallel": c.get("parallel", False),
        }

        # Intake
        intake_start = arrival + pd.Timedelta(minutes=float(c["intake_wait"]))
        intake_end = intake_start + pd.Timedelta(minutes=float(c["intake_service"]))
        rows.append(
            {
                **common,
                "concept:name": "Intake",
                "start_timestamp": intake_start,
                "time:timestamp": intake_end,
                "org:resource": c["intake_resource"],
                "actual_service_min": c["intake_service"],
                "planned_service_min": c["base_services"]["Intake"],
            }
        )

        # Diagnostic start after intake, diagnostic waiting, pre-diagnostic handover/setup.
        diag_start = intake_end + pd.Timedelta(minutes=float(c["diag_wait"] + c["pre_diag_delay"]))

        if c.get("parallel", False):
            for br in c["branches"]:
                bstart = diag_start
                bend = bstart + pd.Timedelta(minutes=float(br["service"]))
                rows.append(
                    {
                        **common,
                        "concept:name": br["activity"],
                        "start_timestamp": bstart,
                        "time:timestamp": bend,
                        "org:resource": br["resource"],
                        "actual_service_min": br["service"],
                        "planned_service_min": c["base_services"][br["activity"]],
                    }
                )
            val_start = diag_start + pd.Timedelta(
                minutes=float(c["diag_duration"] + c["val_wait"] + c["pre_val_delay"])
            )
        else:
            current = diag_start
            for i, br in enumerate(c["branches"]):
                if i > 0:
                    current = current + pd.Timedelta(minutes=float(c["handover_between"]))
                bstart = current
                bend = bstart + pd.Timedelta(minutes=float(br["service"]))
                rows.append(
                    {
                        **common,
                        "concept:name": br["activity"],
                        "start_timestamp": bstart,
                        "time:timestamp": bend,
                        "org:resource": br["resource"],
                        "actual_service_min": br["service"],
                        "planned_service_min": c["base_services"][br["activity"]],
                    }
                )
                current = bend
            val_start = current + pd.Timedelta(minutes=float(c["val_wait"] + c["pre_val_delay"]))

        val_end = val_start + pd.Timedelta(minutes=float(c["validation_service"]))
        rows.append(
            {
                **common,
                "concept:name": "Validation",
                "start_timestamp": val_start,
                "time:timestamp": val_end,
                "org:resource": c["validation_resource"],
                "actual_service_min": c["validation_service"],
                "planned_service_min": c["base_services"]["Validation"],
            }
        )

    return pd.DataFrame(rows)

# 9. Limits and validation plan

## What cannot be concluded from the supplied data alone

The supplied expected arrivals and service ranges are not sufficient to conclude exact SLA attainment. In particular:

1. **Arrival variability is unknown.** Expected arrivals are not enough to determine queue lengths; burstiness matters.
2. **Service-time distribution shape is unknown.** Uniform ranges are an assumption; real service times may be skewed or correlated.
3. **Case-type and priority correlations are unknown.** Complex cases may be more likely to be P1 or to require multiple branches.
4. **Resource behavior is unknown.** The model assumes resources follow dispatch rules, but real operators may batch work, defer handovers, or override priorities.
5. **Handover/setup durations are fixed in the prompt but may vary in practice.**
6. **Preemption dynamics are hard to infer without a fine-grained event log.** The restart penalty depends on exact remaining service time.
7. **Parallel branch coordination may depend on resource experience and case complexity.**
8. **Overtime acceptance and fatigue effects are unknown.**
9. **Validation may become a hidden bottleneck if diagnostics are accelerated.**
10. **The base scenario may already be infeasible under midpoint assumptions, but lower-bound service times could make it feasible.** Therefore policy conclusions should be expressed as robustness trade-offs, not certainties.

## Pilot design

A safe pilot should proceed in stages.

### Stage 1: shadow mode

Run HYBRID and POOL dispatch recommendations in shadow mode for 2–4 weeks.

- Do not force assignments.
- Log what the policy would have recommended.
- Compare recommended assignments with actual assignments.
- Estimate counterfactual delay using historical event logs.

Success criteria:

- No increase in P1 SLA violations.
- No increase in handover/setup burden beyond a pre-agreed threshold.
- Improved P90 delay or reduced resource imbalance.

### Stage 2: controlled rollout

Roll out HYBRID on selected shifts or case types.

- Protect P1 cases with manual override authority.
- Keep P3 aging rules active.
- Limit preemption to P3 initially.
- Monitor every 30 minutes.

Stopping rules:

- P1 SLA rolling below 85% for two consecutive hours.
- Preemption rate exceeding a safe threshold.
- Validation queue growing faster than diagnostic completion.
- Resource fairness index falling below an agreed threshold.

### Stage 3: A/B or switchback test

If operationally feasible, use switchback testing by time window:

- HYBRID during some two-hour blocks.
- POOL during others.
- Randomize or rotate blocks to reduce confounding.
- Keep P1 protection rules constant.

### Backtesting plan

Use historical event logs to backtest:

1. Reconstruct queue entry times.
2. Reconstruct eligible resource sets.
3. Estimate service times from actual active durations.
4. Simulate HYBRID and POOL dispatch decisions.
5. Compare predicted SLA attainment, P90 delay, utilization, and handover burden.
6. Calibrate waiting/preemption assumptions before live deployment.

The validation goal is not to prove one policy universally best, but to identify which policy best satisfies the chosen objective: P1 SLA protection, tail-risk reduction, fairness, and resilience under the supplied uncertainty scenarios.
