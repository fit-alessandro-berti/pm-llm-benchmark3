## 1. Analytical assumptions

**Case notion:** I interpret a case notion as a projection function `flatten(OCEL, OT)` that groups events by the identity of objects of type `OT` to which they are *directly* related via E2O. The resulting classical log contains one trace per object instance `o in OT`. If an event `e` relates to `k` objects of type `OT`, `e` appears in `k` traces (copied). Order within a trace is by timestamp. No inference is automatic.

**Convergence:** A convergence pattern exists when `|E2O(e)  OT| > 1` . Flattening on `OT` then duplicates `e` `k` times. The frequency of activity `a = act(e)` is inflated by `k` relative to the OCEL event count. The DFG will show frequency `k` where OCEL shows `1`, and performance metrics computed on replicated timestamps will overweight that event.

**Divergence:** A divergence pattern exists when a single object `o in OT` is related to multiple distinct events with the same activity (or with activities that are causally independent but forced into a linear order by the single trace). This creates artificial directly-follows edges, self-loops, or spurious orderings that hide true concurrency/independence. Classic example: `O1` related to `e11(P1)` and `e12(P2)` - two `Pack Package` events for the same order, creating an `Pack -> Pack` self-loop that does not exist at package granularity.

**Treatment of copied shared events:** I treat them as *both*: duplication is real evidence that the event touches multiple cases (informative about synchronization/consolidation), and distortion if counted as `k` independent occurrences (harmful for frequency, variant, and performance analysis). The analytical stance is therefore: never delete duplication silently; quantify it, report both event-level and object-level frequencies, and check sensitivity by down-weighting.

**Analytical transformations permitted:**
1.  **Direct E2O only (baseline):** Use the table as given. No propagation.
2.  **Explicit O2O-propagation variant (for sensitivity only):** Propagate relations via O2O qualifiers e.g., `Order --contains--> Item --packs--> Package --carries--> Delivery` and `Order --bills--> Invoice --settles--> Payment`. When used, it will be labelled `PROPAGATED` and compared to `DIRECT`. I do not silently propagate in the main comparison, because propagation creates its own divergence (e.g., `e01 Create Order O1` would be attributed to `I11,I12,P1,P2,D1,D2,V1,M1`, artificially inflating pre-package lifecycles for Delivery/Payment).
3.  **Down-weighted duplication:** Assign weight `1/k` to each copy of a convergent event for frequency/performance re-estimation. This is a diagnostic, not a correction.

## 3. Concrete distortion analysis

**D1 - Cross-order Package P3 duplicated across orders (Convergence  Frequency inflation, DFG distortion) - Harmful if unweighted.**
*Affected flattening:* Order.
*Objects/Events:* `P3` packs `I21(O2)` + `I31(O3)` at `e13` `Pack Package O2,O3,I21,I31,P3`. E2O contains `O2` and `O3`, so `e13` is copied into trace `O2` and trace `O3`.
*Distortion:* DFG on Order shows edge `Add Item -> Pack Package` with count 2 for `e13` where OCEL has 1 real packing action. Variant analysis will count two distinct order variants containing `Pack Package`, inflating `Pack Package` frequency from 4 to 6 (+50%). Performance aggregation that averages `Add Item(O2)->Pack` and `Add Item(O3)->Pack` double-counts same timestamp `2026-02-03 10:12`, biasing mean packing lead time toward V2-clustered orders. Informative that orders share packing, harmful as independent evidence.

**D2 - Cross-order Package P4 duplicated across orders (Convergence + Divergence entanglement) - Harmful.**
*Affected flattening:* Order and Item.
*Objects/Events:* `e14` `Pack Package O3,O4,I32,I41,P4` copied to `O3`+`O4` on Order flattening, to `I32`+`I41` on Item flattening. For `O3`, this is its *second* `Pack Package` after `e13`, creating divergence.
*Distortion:* Order DFG creates self-loop `Pack Package -> Pack Package` for O3 (`e13->e14`) with timestamp gap 8 minutes, suggesting sequential packing of one order, when in reality `e13` and `e14` pack *different* item sets sharing O3 vs O4. At Item level, same event is less distorting (each item has single pack) but still duplicated count 2. Analyst flattening on Order who sees self-loop may infer rework; in OC-DFG, edges are `Pack(P3) -> Dispatch(D2)` and `Pack(P4) -> Dispatch(D3)` distinct.

**D3 - Consolidated Delivery D2 involving three orders (Convergence across 3, Most severe shared-event copy) - Harmful.**
*Affected flattening:* Order (primary), also implicit for Item/Package to lesser degree.
*Objects/Events:* `e16` `Dispatch O1,O2,O3,I12,I21,I31,P2,P3,D2` and `e24` `Confirm Delivery O1,O2,O3,I12,I21,I31,P2,P3,D2` with qualifier `carries` `D2->P2,P3`. Both events relate to `O1,O2,O3`.
*Distortion:* Order flattening triplicates `e16` and `e24` (3 copies each). DFG counts `Dispatch -> Confirm Delivery` 3 times where there is one physical shipment. Variant frequency shows 3 cases sharing same timestamps `11:05` and `16:00`, creating artificial conformance of 75% of orders sharing identical dispatch time, hiding that `O1`'s `P1/D1` was separate (`e15` 11:00). Performance averaged over Order will overweight D2's transit time (4h55m) by factor 3 vs D1 (3h) and D3 (22h45m). On Delivery flattening, no duplication - D2 appears as single case `Dispatch->Confirm` 4h55m, revealing true consolidation benefit. The discrepancy between Order-averaged transit ( (3h + 3*4h55m + 2*22h45m)/6 ) vs Delivery-averaged transit is diagnostic of convergence bias.

**D4 - Split Order O1 across two packages/deliveries (Divergence hidden when not using Order, inflated when using Package/Delivery) - Context-dependent.**
*Affected flattening:* Order vs Package/Delivery.
*Objects/Events:* `O1` contains `I11->P1->D1` (`e11,e15,e23`) and `I12->P2->D2` (`e12,e16,e24`). `e11`/`e12` are two `Pack` events for same order; `e15`/`e16` are two `Dispatch`.
*Distortion:* Order flattening shows `Pack->Pack` and `Dispatch->Dispatch` + `Confirm->Confirm` divergence for O1 trace: `e11(10:00)->e12(10:10)->e15(11:00)->e16(11:05)->e23(14:00)->e24(16:00)`. Naive sequential reading implies O1 was dispatched twice sequentially, missing that `I11` delivered at 14:00 while `I12` delivered at 16:00 (split delivery). Package/Delivery flattening hides split entirely: P1/D1 trace shows only I11, P2/D2 trace includes O1 but mixed with O2/O3; the fact O1 is split is lost unless analyst joins O2O. Harmful if SLA is per order (partial delivery considered late), informative if KPI is per item.

**D5 - Consolidated Invoice V2 bills O2+O3 (Convergence in finance) - Harmful for revenue attribution.**
*Affected flattening:* Order.
*Objects/Events:* `e19` `Issue Invoice O2,O3,V2` where `V2 bills O2` and `V2 bills O3` via O2O. Duplicated to O2 and O3 traces.
*Distortion:* Order DFG shows `Issue Invoice` frequency 4 (vs 3 real). Variant with V2 appears twice. Financial performance `Issue->Record Payment` time from `e19(12:05)` to `e22(12:40)` will be counted twice, overweighting V2 in order-level Days Sales Outstanding. Invoice flattening shows single `V2: e19->e22->e25` with correct consolidated pattern; Order flattening suggests each order has its own invoice, misleading profitability per order. Tax/vat analysis per invoice requires OC-DFG where `Issue Invoice` connects to *two* Order objects.

**D6 - Partial payments for V2 (Divergence on Invoice, Convergence on Order double-count) - Informative but trap for naïve metrics.**
*Affected flattening:* Invoice (divergence), Order (convergence).
*Objects/Events:* `M2 partially_settles V2` at `e22` (`O2,O3,V2,M2`) and `M3 completes_settlement V2` at `e25` (`O2,O3,V2,M3`). On Invoice `V2`, sequence is `e19(12:05)->e22(12:40)->e25(09:00 next day)` with qualifier change.
*Distortion:* Invoice DFG will contain self-loop `Record Payment -> Record Payment` (count 1) and two distinct edges from `Issue Invoice`. No issue if qualifiers are kept, but if flattened without qualifier, analyst may treat as rework/duplicate payment. On Order flattening, *both* payments are duplicated to O2 and O3  4 `Record Payment` occurrences for V2 where OCEL has 2. Frequency inflation 100%. Performance: `e22->e25` gap 20h20m will be counted twice (once per order), suggesting two independent 20h payment cycles rather than one shared settlement cycle. Harmful if `AVG payment delay` is reported, informative that split payment exists - requires object-centric view retaining `M2` vs `M3`.

**D7 - Near-singleton lifecycle for Payment (Lifecycle truncation) - Harmful as case notion.**
*Affected flattening:* Payment.
*Objects/Events:* `M1 e21`, `M2 e22`, `M3 e25`, `M4 e26` each isolated. Each trace length =1, no directly-follows relation.
*Distortion:* DFG discovery yields empty graph; `discover_log_skeleton` yields no precedence. Any performance or variant analysis is vacuous. An analyst comparing case lengths might conclude "Payment is simplest process" vs Order (6-9 events), conflating model simplicity with truncation. Demonstrates that trace length alone must never justify lead-object choice; Payment is *short* because object participates in only one activity type (`Record Payment`), not because process is simple. Context-dependent: useful for counting/amount analysis, useless for control-flow.

**D8 - Delivery and Invoice flattenings hide pre- and post-conditions (Artificial lifecycle truncation + O2O propagation temptation) - Context-dependent / Harmful if propagated naively.**
*Affected flattening:* Delivery and Invoice.
*Objects/Events:* `D2` has no `Create Order` or `Close Order` in DIRECT E2O; `V2` has no `Pack`/`Dispatch`/`Confirm Delivery`. Real gap: `e16 Dispatch 11:05` occurs before `e19 Issue Invoice 12:05`, but Delivery trace sees only `11:05->16:00`, Invoice trace sees only `12:05->12:40->09:00 next day`.
*Distortion:* If analyst propagates via O2O (`D2->P2->I12->O1` etc.) to artificially elongate traces, DFG would create spurious edges `Confirm Delivery -> Issue Invoice` or `Dispatch -> Issue Invoice` that belong to *order* lifecycle but are inferred via multi-hop links. Comparing DIRECT vs PROPAGATED variant shows dramatic change: Delivery trace length goes from 2 to ~8 events, but with false concurrency (e.g., `e01 Create Order O1` linked to D2 via `P2`). The trap is to think propagation "fixes" truncation; it instead mixes granularities and creates divergence where Delivery is linked to three orders' creation events. Must keep views separate and use OC-DFG/ET-OT to see cross-type dependencies.

**(Bonus D9 - Confirm Delivery triplication distorts SLA compliance)** Order flattening copies `e24` to O1,O2,O3, making it appear three orders were confirmed at 16:00. If SLA is `Close Order` after confirmation, the gap `e24->e29/e30` (19h05m) triple-counts, pulling average close delay. Invoice/Delivery flattenings show true single confirmation per shipment - reconciliation requires weighting by unique `Delivery` or `Confirm Delivery` event IDs, not by order copies.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs that should still be created (with explicit annotation, not as ground truth):**

1.  **Order-flattened log:** Keep for *order SLA* questions only: `Create Order -> Close Order` duration, split-order handling (O1 two packs), end-to-end variant for O1 vs O4. Safe questions: "What % of orders have >1 package?" (answer via divergence count on Order: O1 and O3 have 2 packs). "Order lead time distribution?" with note that shared logistics/finance events are weighted by `1/k`. Unsafe: pack utilization, delivery consolidation efficiency, invoice-to-cash per legal invoice, payment settlement pattern. Must report both raw and down-weighted metrics.
2.  **Item-flattened log:** Keep for item flow diagnostics: "Do items from different orders share a package?" (P3,P4) and item-level pack-to-dispatch time. Safe for throughput at picking station. Unsafe for order closure or finance.
3.  **Package-flattened log:** Keep for packing/dispatch performance: `Pack -> Dispatch` per package, identifying cross-order packages (P3,P4). Safe for packaging efficiency. Truncation means not for end-to-end.
4.  **Delivery-flattened log:** Keep for transit time: `Dispatch -> Confirm Delivery` per delivery (D1 3h, D2 4h55m, D3 22h45m). Safe for logistics carrier KPI. Unsafe for upstream/downstream.
5.  **Invoice-flattened log:** Keep for finance audit: `Issue Invoice -> Record Payment (1 or 2 steps)` per invoice, detecting partial payments (V2). Safe for `Days to settle` per invoice (V1 30min, V2 first payment 35min, final 20h55m after issue, V3 21h20m). Unsafe for logistics SLAs.

**Payment-flattened log:** Create only to demonstrate truncation; do not use for discovery. Use for payment count/amount if needed, but not for sequencing.

All flattened logs must carry attribute `orig_event_id` and `duplication_factor k` to allow de-duplication. Variants should be reported as `event-level` vs `object-level` frequencies.

**Questions that require object-centric models:**

*   End-to-end questions touching >1 object type: e.g., "How does delivery consolidation D2 affect invoice settlement V2 for O2+O3?" requires **OC-DFG** (`pm4py.discover_ocdfg`) where `Dispatch(D2)` connects `P2->O1` and `P3->O2,O3`, and `Issue Invoice(V2)` connects `O2,O3`. OC-DFG shows frequency as `(events, unique objects, total objects)` revealing that `Dispatch` activity touches 6 item objects but only 3 delivery objects.
*   Object interaction/consolidation degree: **OTG** (`pm4py.discover_otg`) and **object interactions summary** (`pm4py.ocel_objects_interactions_summary`) quantify that `Package` interacts with 2 orders for P3/P4, `Delivery` interacts with 2 packages for D2, `Invoice` interacts with 2 orders for V2. Cannot be seen in any single flattened log.
*   Activity–object type involvement: **ET–OT graph** (`pm4py.discover_etot`) shows `Pack Package` involves Order+Item+Package together; `Record Payment` involves Order+Invoice+Payment together, clarifying why truncation occurs elsewhere.
*   Equivalent execution clustering: Use `pm4py.cluster_equivalent_ocel` to group executions that are isomorphic with respect to Order as lead but with shared events counted once, to avoid overcounting variants that differ only by duplication factor.

**Reconciling contradictory findings:**

*   Always compare `event-centric` count (unique `e16` =1) vs `object-centric` count (total objects =3 for Order, 2 for Package, 1 for Delivery). If Order-flattened says `Dispatch` frequency 7 but OC-DFG says 3 events / 7 total Order objects / 4 total Package objects / 3 total Delivery objects, flag convergence bias.
*   When DFG edge `Pack->Pack` appears only in Order-flattened but not in OC-DFG or Item/Package DFG, label it as divergence artifact, not rework.
*   When performance differs (Order-averaged dispatch-to-confirm ~13h vs Delivery-averaged ~10h16m), report both and explain weighting. Use down-weighted (`1/k`) recalculation to reconcile.
*   Use Log Skeleton on flattened logs to test precedence claims, but validate precedence in OC-DFG with object-type-colored edges; a precedence that holds for Order but not for Delivery/Invoice is type-specific, not universal.
*   Decision rule: if a finding disappears when `PROPAGATED` vs `DIRECT` or when weight `1/k` applied, treat it as flattening artifact, not business rule.

## 5. Lead-object decision

**Position C. Reject a single lead object for this process.** (Position B – primary Order + secondaries – is operationally similar but we explicitly reject dominance; if a primary must be named for reporting, it is Order *only* as a reporting anchor, not as analytical ground truth. The wording here satisfies C: no single OT explains end-to-end without severe distortion.)

**Decision criteria:**
1.  Coverage of end-to-end activity types (does OT trace include order creation to cash to closure?)
2.  Uniqueness (no systematic convergence requiring duplication)
3.  Divergence cost (does one object force unrelated events into linear order?)
4.  Lifecycle completeness vs truncation (does object participate in >2 phases?)
5.  Business question generality (can questions about package consolidation, delivery consolidation, consolidated invoicing, and split payments be answered without secondary objects?)

| Criterion | Order | Item | Package | Delivery | Invoice | Payment |
|---|---|---|---|---|---|---|
| Coverage | 8/8 activities but via duplication | 4/8 | 3/8 | 2/8 | 2/8 | 1/8 |
| Uniqueness | fails (7 convergent events) | partial fails | passes | passes | passes | passes |
| Divergence | medium | low | low | none | high for V2 | none |
| Truncation | none | high (finance) | high | severe | severe | total |
| Generality | appears general but hides consolidation | not | not | not | not | not |

No OT passes all five.

**Strongest supporting evidence for rejection:**
*   *Cross-order structures are core business:* `P3(I21+ I31)`, `P4(I32+I41)`, `D2(P2+P3)` spanning O1-O3, and consolidated `V2(O2+O3)` with two payments `M2+M3`. Any single OT forces copying or deletion of these structures. Order flattening triplicates `e16/e24`; Delivery flattening deletes packing/invoicing; Invoice flattening deletes logistics; Item/Package flattenings delete finance/closure. The OCEL's value is precisely in these many-to-many links, which flattening destroys.
*   *No OT has stable 1:1 lifecycle:* Order has convergence (harmful duplication), Invoice has divergence (split payment self-loop), Delivery/Package/Payment have truncation to 2/1 activities. Choosing any one silently prioritizes one department's view (sales vs warehouse vs finance) and misleads the others.

**Strongest counterargument (why Order tempts as lead):**
Order is the only OT that appears from `Create Order e01-e04` to `Close Order e28-e31`, with all four orders closing. It yields longest traces (6-9 events) and looks “end-to-end.” For classic Order-to-Cash reporting, Order is the natural case ID demanded by stakeholders. With down-weighting `1/k`, Order-based performance can approximate end-to-end lead time. Rejecting it may feel unintuitive to business users.

**Residual risk if C is adopted:**
Risk of over-complexity and stakeholder confusion; object-centric graphs (OC-DFG, OTG) are harder to communicate than a single DFG. There is still a need for an anchor for case counting (e.g., “how many orders?” =4). Mitigation: use Order as *counting* anchor for order-level KPIs but forbid using it alone for control-flow or performance averaging without indicating duplication.

**Conditions under which decision would change:**
*   Change to **B (Order as primary)** if process is redesigned so that `Package` and `Delivery` become strictly 1 order : 1 package : 1 delivery (no P3/P4, no D2 consolidation) and `Invoice` becomes 1:1 with Order (no V2 consolidation) and payments are single (`M2` only). Then convergence risk drops to zero, divergence remains only split O1 which is manageable; Order would then be defensible as lead with Package/Delivery as attributes.
*   Change to **A (Package or Delivery as lead)** if analysis scope is permanently narrowed to warehouse-only or transport-only, and end-to-end is explicitly out of scope.
*   Change to **A (Invoice as lead)** if scope is only finance audit `Issue->Settle`.
*   If an explicit `Order->Package->Delivery` propagation with validated many-to-one semantics and causal timestamp guarantees were business-validated and duplication is resolved via event slicing (e.g., sub-events per order), a propagated Order log could become lead - but this must be modeled, not assumed.

In short, with current consolidation and split patterns, any single lead distorts; the honest model is object-centric with multiple lifecycles synchronized at shared events `e13,e14,e16,e17,e19,e22,e24,e25`.

## 7. Sensitivity and validation plan

**S1 - Remove / down-weight copied shared events.**
*Method:* For each flattened log, compute duplication factor `k = |E2O(e)  OT|` using original E2O. Create down-weighted view where each copy contributes `1/k` to frequency and performance. Recompute DFG frequencies and mean `Dispatch->Confirm` and `Issue->Payment` durations with weighted vs unweighted averages.
*Expectation:* Order-flattened `Pack Package` 64 weighted, `Dispatch` 73, `Record Payment` 74. Weighted DFG converges to OC-DFG event counts. If key edge `Pack->Pack` self-loop frequency drops from 2 to <0.5 weighted, label it artifact. Report both weighted and unweighted KPIs; a business conclusion that flips between them is flagged as convergence-sensitive.

**S2 - Compare DIRECT E2O vs explicitly PROPAGATED (O2O) variant.**
*Method:* Generate two OCELs: `OCEL_direct` (as given) and `OCEL_prop` where E2O is closed via O2O (`Order.contains Item`, `Package.packs Item`, `Delivery.carries Package`, `Invoice.bills Order`). Flatten Delivery and Invoice on both variants and compare trace length, DFG edges, and `Create Order->Pack` precedence.
*Expectation:* Delivery trace length 2~7, Invoice 2-3~7. New edges `Create Order -> Dispatch` appear only in propagated view via multi-hop. Validate against timestamps: does `e01 Create Order O1 09:00` logically precede `e16 Dispatch D2 11:05` for *all* orders in D2? `O2` creation `09:02` and `O3` `09:04` also precede, but `O1` containment via `P2` is fine while `O2` via `P3` is also fine – propagation creates convergence again (D2 linked to 3 order creations). Sensitivity passes only if propagated edges are confirmed by domain; otherwise keep DIRECT and use OC-DFG for cross-type ordering.

**S3 - Change the lead object and compare frequency metrics per OT.**
*Method:* For a fixed activity e.g., `Dispatch`, compute three metrics from OC-DFG: `events` (unique e16,e15,e17 =3), `unique_objects` per OT (Orders=4 distinct orders involved, Packages=4, Deliveries=3), `total_objects` (Order total =1+3+2=6 copies, Package total=4). Compare to flattened frequencies: Order log says 7, Package says 4, Delivery says 3.
*Expectation:* Discrepancy pattern diagnoses bias type: `events < total_objects` signals convergence; `events < unique_objects` signals many-to-many. Re-run for `Issue Invoice` (events=3, unique Orders=4, total Orders=4) vs Order flattened 4. Validate that finance KPIs use `events` or `unique Invoice` denominator, not `total Order` denominator. If changing lead from Order to Delivery changes conclusion "average transit time increased," conclusion is lead-sensitive and must be reported with per-OT denominator.

**S4 - Lifecycle completeness and performance bias check (near-singleton detection).**
*Method:* For each OT, compute coverage `|activities appearing with OT| / |all activities|` and mean trace length. Compare `Payment` (1.0), `Delivery` (2.0), `Invoice` (2.33) to thresholds. For performance, compute end-to-end `Create Order -> Close Order` time using Order-flattened (O1 2 days 2h, O2 1 day 2h03m, O3 1 day 2h01m, O4 1 day 2h04m) vs naive Delivery/Inovice attempt (fails: no Close). Also compute `Dispatch->Confirm` per OT: Order-weighted vs Delivery-true.
*Expectation:* Truncated OTs will show artificially low variance and cannot answer end-to-end question; attempting to does not become valid with more data. Validate by showing Log Skeleton invariants differ: Order skeleton shows `Create Order always before Close Order`, Delivery skeleton shows no relation. If analyst reports overall process time using Delivery or Payment, sensitivity fails - flag as truncation bias.

*Additional validation:* Cross-check object interaction summary: ensure interpretation of `P3` and `P4` cross-order, `D2` consolidation (2 packages), `V2` consolidation (2 orders) matches O2O qualifiers `packs`, `carries`, `bills`. Any flattened insight contradicting `interactions` table (e.g., "every package belongs to one order") is rejected.

All checks must be grounded in identifiers `O1-O4, I11-I41, P1-P4, D1-D3, V1-V3, M1-M4, e01-e31`; generic process-mining heuristics without citing these are insufficient.
