## 1. Temporal Data Semantics

- **State reconstruction:** For each case, attributes (`amount`, `risk_level`, `jurisdiction`, `customer_type`) are reconstructed by strictly forward-filling the last explicitly updated value within the ordered event stream. Ordering is by `(time:timestamp, event_index)`. A blank cell is *not* a null assignment; it means the event did not update that attribute, so the previously known value persists.
- **No backward copy:** The final case-level attribute values are never projected to earlier events. Earlier events are evaluated only against values known at or before their own `(time, event_index)` position.
- **Equal timestamps:** When two events share a `time:timestamp`, `event_index` is the strict tie-breaker. An event with a smaller `event_index` is earlier for both state propagation and temporal ordering constraints.
- **Material change:** A *material data change* is any `Update_*` event that changes `risk_level`, `jurisdiction`, or `customer_type`, or any `Update_Amount` that increases the amount by more than 20% relative to the amount last seen at the relevant review. A decrease is not material. An increase from an unknown amount is not safely classifiable.
- **Final attributes vs event-time attributes:** The “current” value at `Release_Funds` is the forward-filled snapshot at the release event’s `(time, event_index)`, including any same-timestamp updates with a smaller `event_index`.
- **Event time, effective time, record time, evidence time:**
  - *Event time* = `time:timestamp` of the logged activity.
  - *Effective time* = for attribute updates, the event time unless evidence shows another effective time; for exemptions, the claimed `effective_from`.
  - *Record time* = when the record entered the system (e.g., `Record_Exemption` at 11:00 after an outage).
  - *Evidence time* = when supporting proof exists (e.g., qualified-signature timestamp, certificate creation time). Late record time alone does not prove early effective time.

### Concise pseudo-logic (Datalog-like, temporal)

Let `before((t1,i1),(t2,i2))`  `t1 < t2  (t1 = t2  i1 < i2)`.

```
state(c, A, V, t, i) :-
    event(c, Act, t0, i0, A=V)  before((t0,i0),(t,i)) 
    ¬ event(c, Act2, t1, i1, A=V2) with (t0,i0) < (t1,i1) < (t,i)

R1(c, release r=(t,i)) :-
    state(c,'jurisdiction',J,t,i), J  'DE',
    state(c,'amount',A,t,i), A  100000
      e=Enhanced_Review(c,te,ie):
         before(e,r)  (no material_change m with before(m,e))
       exempt(c,ex,R1,t,i)

R2(c, r=(t,i)) :-
    state(c,'risk_level',R,t,i)='HIGH'  state(c,'customer_type',C,t,i)='PEP'
      e=Enhanced_Review(c,te,ie), a=Compliance_Approve(c,ta,ia):
         before(e,a)  before(a,r)

R3(c, r=(t,i)) :-
     u=Sanctions_List_Update(c,tu,iu, jur=J) with
       latest_screen s=Sanctions_Screen(c,ts,is) before u,
       before(u,r), state(c,'jurisdiction',J,t,i)
      s2=Sanctions_Screen(c,ts2,is2):
         before(u,s2)  before(s2,r)

R4(c, review v=(tv,iv), r=(t,i)) :-
     u=Update_Amount(c,tu,iu, amt=Au) with
       before(v,u)  before(u,r)  Au > 1.2 * amount_at(v)
     review_invalid(v)

R5 exempt(c,ex,R1,t,i) :-
    register(ex).approved_by='Head_Compliance' 
    register(ex).effective_from  t 
    register(ex).expires > t 
    register(ex).jur = state(c,'jurisdiction',t,i) 
    register(ex).cust = state(c,'customer_type',t,i) 
    state(c,'amount',t,i)  register(ex).max_amt 
    evidence_time(ex)  t  not contradicted_by_later_cert

R6(c, obl) :- decisive_attr_missing(obl)  classify INDETERMINATE
R7 :- shared timestamp resolved by event_index
```

## 4. Ambiguities and Alternative Readings

### TX-305 (INDETERMINATE)
- If an immutable release payload or signed settlement instruction proved `amount  100,000`, R1 would trigger; because `Enhanced_Review` already occurred before release, the case would likely be **COMPLIANT**.
- If such evidence proved `amount < 100,000`, R1 would not trigger and the case would be **COMPLIANT**.
- If the missing amount were supplemented by a finding that no review occurred, it would be **NONCOMPLIANT**. The absence of an immutable release amount is the sole reason for `INDETERMINATE`.

### TX-302 (JUSTIFIED_EXCEPTION)
- If the qualified signature timestamp were distrusted (e.g., clock skew), EX-77 might be deemed invalid; however, `Enhanced_Review` at 09:20 still satisfies R1, so the case would remain **COMPLIANT**, not NONCOMPLIANT.
- If EX-77 scope had not matched (e.g., amount >250k), the exemption would not waive, but the existing `Enhanced_Review` would still satisfy R1. The classification is robust; the exemption is an additional defensive control.

### TX-310 (NONCOMPLIANT under strict evidence rule)
- If an independent, corroborated approval record (e.g., Head_Compliance system log or a signing certificate created before 10:00) confirmed EX-88, the exemption would be valid and the case would become **JUSTIFIED_EXCEPTION**.
- If the requester’s oral approval were accepted despite bias, or if the backdated PDF were treated as conclusive, the same **JUSTIFIED_EXCEPTION** result would follow.
- Conversely, if an `Enhanced_Review` were later discovered to have existed before release, R1 would be satisfied even without the exemption. The current NONCOMPLIANT result hinges on (a) no Enhanced_Review and (b) invalid exemption evidence.

### TX-311 (COMPLIANT)
- If `event_index` were ignored, the same-timestamp `Enhanced_Review` and `Update_Jurisdiction` would be ambiguous. But because the forward-filled jurisdiction at release is `DE`, R1 is not triggered regardless.
- If the jurisdiction update had been to a non-DE value *after* the review (`event_index` greater than the review) and R1 were otherwise triggered, the “review after latest material change” condition would fail, potentially making the case **NONCOMPLIANT**. Under the actual logged order, that does not occur.
- If the amount increase had occurred *after* the `Enhanced_Review`, R4 would invalidate the review; here the increase precedes the review, so the review remains valid.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage / backward copying:** A control-flow or case-level view might use the final `jurisdiction = DE` for TX-311 from the start. Correct temporal evaluation requires recognizing the earlier `US` state and the same-timestamp update order.
2. **Post-hoc exemptions and record time vs evidence time:** TX-302 and TX-310 both have `Record_Exemption` after `Release_Funds`. A pure flow check sees “exemption after release” and flags a violation, but TX-302 is valid because the signature evidence time predates release, whereas TX-310 is invalid because the certificate was created after release.
3. **Material changes after review:** TX-309 has `Enhanced_Review` before `Release_Funds`, which satisfies a control-flow `Response` constraint, but a >20% amount increase after the review invalidates it under R4. TX-301’s `Standard_Review` is similarly invalidated.
4. **Conditional activation:** R1 only triggers for `jurisdiction  DE` and `amount  100,000`; R2 only for `HIGH`/`PEP`. Control-flow constraints cannot evaluate these data predicates without payload-aware state.
5. **Missing or unknown data:** TX-305 contains `Enhanced_Review` and `Release_Funds`, so a flow check looks compliant, but the amount is unknown at release; R6 requires `INDETERMINATE`, not automatic compliance.
6. **Same-timestamp ordering:** TX-311 has `Enhanced_Review` and `Update_Jurisdiction` at the same timestamp. Collapsing events to a timestamp-only trace loses the `event_index` order and creates false ambiguity about whether the review preceded the material change.
7. **Review-type semantics:** TX-307 has `Standard_Review` and `Compliance_Approve`, which may satisfy a generic “review before release” constraint, but R2 explicitly requires `Enhanced_Review`, not `Standard_Review`.
8. **External state changes:** TX-304’s `Sanctions_List_Update` is not a transaction-internal activity in the usual sense; a trace-only model may not relate it to the prior `Sanctions_Screen` and the later release.

---

## 7. Recommended Logging and Control Improvements

- **Immutable release payload:** Require `Release_Funds` to carry a signed snapshot of `amount`, `jurisdiction`, `risk_level`, `customer_type`, `rule_version`, and referenced `exemption_id`. This prevents missing-amount cases like TX-305 and blocks final-state leakage.
- **Separate timestamp dimensions:** Record `event_time`, `effective_time`, `record_time`, and `evidence_time` (e.g., signature/certificate time) as distinct attributes. Do not infer approval time from late database inserts alone.
- **Exemption proofs at approval time:** Store the qualified-signature timestamp and hash with the exemption entity. Reject backdated `effective_from` values unless corroborated by an evidence-time stamp earlier than the obligation trigger.
- **Mandatory attribute completeness:** Block `Create_Transaction` or `Release_Funds` when `amount`, `jurisdiction`, `risk_level`, or `customer_type` is unknown; if a feed is unavailable, move the case to a hold state rather than releasing with blanks.
- **Stable total ordering:** Use a globally monotonic `event_id` or logical clock instead of relying only on second-resolution UTC plus `event_index`. This makes same-timestamp ordering (TX-311) unambiguous.
- **Material-change provenance:** For every `Update_*` event, record previous value, new value, reason, and actor. Automatically mark dependent reviews as invalid when an increase >20% occurs.
- **Rule-version and scope attributes:** Stamp each event with the policy version and the evaluated rule set, so later reviewers can distinguish R1/R2/R3 semantics across time.
- **Sanctions-feed integration:** Emit `Sanctions_List_Update` with an effective list version and link `Sanctions_Screen` events to the list version they used, enabling automated R3 checks.
- **Review validity events:** Have `Enhanced_Review` and `Standard_Review` record the reviewed amount, jurisdiction, risk, and customer type, plus a review validity expiration, so R4 and R1 can be evaluated without reconstructing history.
