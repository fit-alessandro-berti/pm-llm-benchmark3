# 1. Assumptions and Interpretation

1. **Low-risk / high-risk choice:** Represented as an `XOR` split after `Analyze Root Cause`. Low-risk selects `Supervisor Review`; high-risk selects a concurrent pair (`Quality Review` || `Regulatory Review`) launched via a silent start node.
2. **Optional supplier consultation:** Represented as an `XOR` between `Consult Supplier` and a silent skip (`SilentTransition`). It is included in both models so that the “skipped” path is explicit.
3. **Passing inspection abstraction:** The loop exit is not a visible event label; the loop operator allows exit after `Inspect Trial`. The “fail” path is taken only through `Adjust Parameters`, ensuring `Adjust Parameters` never follows a passing inspection.
4. **Duplicate visible labels:** Not permitted. Every visible activity appears exactly once; silent nodes (`tau`, `skip_supplier`, `high_risk_start`) represent non-visible routing.
5. **Process-tree approximation policy:** **Conservative restriction / permissive over-approximation hybrid with block-structural delay.** The tree forces `Plan Verification` and `Design Corrective Action` into an initial parallel block, then forces approvals and supplier work into a second synchronization parallel block with the trial. This excludes some intended early interleavings (approvals/supplier starting before design/planning finish) but never admits an unsafe ordering.
6. **“May overlap” interpretation:** Interpreted as **true concurrency (absence of ordering edges)**, not just arbitrary interleaving. Concurrent nodes have no `add_edge` between them in POWL and are placed in `PARALLEL` nodes in the tree.
7. **Loop semantics in tree:** `LOOP(do_part, redo_part)` where `do_part` = `SEQUENCE(Execute Trial, Inspect Trial)` and `redo_part` = `Adjust Parameters`. This yields the required “repeat until pass” behavior.
8. **Tree synchronization:** `Release Material` is placed after a `PARALLEL` that contains both the trial loop and the approval/supplier block, so release waits for all three obligations.

```python
t_qual  = Transition("Quality Review")
t_regul = Transition("Regulatory Review")
t_cons  = Transition("Consult Supplier")
t_tau   = Transition("tau")               # silent skip for optional supplier
t_exec  = Transition("Execute Trial")
t_insp  = Transition("Inspect Trial")
t_adj   = Transition("Adjust Parameters")
t_rel   = Transition("Release Material")
t_arc   = Transition("Archive Case")

# --- sub-tree: contain -> plan ---
seq_cp = ProcessTree(operator=Operator.SEQUENCE)
seq_cp.children = [t_cont, t_plan]
t_cont.parent = seq_cp
t_plan.parent  = seq_cp

# --- sub-tree: analyze -> design ---
seq_ad = ProcessTree(operator=Operator.SEQUENCE)
seq_ad.children = [t_ana, t_des]
t_ana.parent  = seq_ad
t_des.parent  = seq_ad

# --- approval route: XOR(low=supervisor, high=parallel(qual,regul)) ---
par_qual_reg = ProcessTree(operator=Operator.PARALLEL)
par_qual_reg.children = [t_qual, t_regul]
t_qual.parent  = par_qual_reg
t_regul.parent = par_qual_reg

xor_approval = ProcessTree(operator=Operator.XOR)
xor_approval.children = [t_sup, par_qual_reg]
t_sup.parent        = xor_approval
par_qual_reg.parent = xor_approval

# --- supplier option: XOR(consult, skip) ---
xor_supp = ProcessTree(operator=Operator.XOR)
xor_supp.children = [t_cons, t_tau]
t_cons.parent = xor_supp
t_tau.parent  = xor_supp

# --- synchronization block: approvals || supplier (both concurrent with trial) ---
par_sync_approval = ProcessTree(operator=Operator.PARALLEL)
par_sync_approval.children = [xor_approval, xor_supp]
xor_approval.parent = par_sync_approval
xor_supp.parent     = par_sync_approval

# --- trial loop: do (exec -> inspect), redo (adjust) ---
do_trial = ProcessTree(operator=Operator.SEQUENCE)
do_trial.children = [t_exec, t_insp]
t_exec.parent = do_trial
t_insp.parent = do_trial

loop_trial = ProcessTree(operator=Operator.LOOP)
loop_trial.children = [do_trial, t_adj]
do_trial.parent = loop_trial
t_adj.parent   = loop_trial

# --- synchronization parallel: loop || (approvals || supplier) ---
par_sync = ProcessTree(operator=Operator.PARALLEL)
par_sync.children = [loop_trial, par_sync_approval]
loop_trial.parent       = par_sync
par_sync_approval.parent = par_sync

# --- initial parallel: (contain->plan) || (analyze->design) ---
par_init = ProcessTree(operator=Operator.PARALLEL)
par_init.children = [seq_cp, seq_ad]
seq_cp.parent = par_init
seq_ad.parent = par_init

# --- root sequence ---
root = ProcessTree(operator=Operator.SEQUENCE)
root.children = [t_reg, par_init, par_sync, t_rel, t_arc]
t_reg.parent  = root
par_init.parent = root
par_sync.parent = root
t_rel.parent   = root
t_arc.parent   = root

tree = root
```

Approximation disclosure:
- **Delayed approvals / supplier:** In the tree, both the approval route and `Consult Supplier` are placed inside `par_sync`, which starts only after `par_init` completes. Thus approvals and supplier consultation cannot begin until both `Design Corrective Action` and `Plan Verification` are finished. The narrative permits them immediately after `Analyze Root Cause`. This is a **conservative exclusion** of valid interleavings.
- **Loop abstraction:** The loop is binary (`LOOP(do, redo)`) with `do` being the `SEQUENCE` of trial and inspection. This captures “repeat until pass” correctly, but the exit condition (passing inspection) is implicit.
- **Optional supplier:** The `XOR` with `tau` allows skipping; `tau` is visible in the tree structure but represents absence.
- **No data conditions:** Risk level, inspection result, and supplier selection are not encoded; the tree includes all control-flow alternatives.

# 4. PM4Py POWL Model

Compact description:
- Root `StrictPartialOrder` containing all transition, silent, and operator nodes.
- `Operator.XOR` for risk route (`op_risk`) and supplier option (`op_supp`).
- `Operator.LOOP` for the trial cycle (`loop_op`).
- Partial-order edges express: `Register`  initial concurrency; `Contain`  `Plan`; `Analyze`  `Design`, `op_risk`, `op_supp`; `Design` / `Plan`  `loop_op`; `loop_op`, `op_risk` descendants, and supplier descendants all converge on `Release`; `Release`  `Archive`.
- Concurrency is expressed by missing edges (e.g., `Quality Review` || `Regulatory Review`; trial || approvals).

Python construction (`powl`):

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py import Operator

# --- transitions ---
t_reg   = Transition("Register Deviation")
t_cont  = Transition("Contain Material")
t_ana   = Transition("Analyze Root Cause")
t_plan  = Transition("Plan Verification")
t_des   = Transition("Design Corrective Action")
t_sup   = Transition("Supervisor Review")
t_qual  = Transition("Quality Review")
t_regul = Transition("Regulatory Review")
t_cons  = Transition("Consult Supplier")
t_exec  = Transition("Execute Trial")
t_insp  = Transition("Inspect Trial")
t_adj   = Transition("Adjust Parameters")
t_rel   = Transition("Release Material")
t_arc   = Transition("Archive Case")

# --- silent nodes ---
s_high  = SilentTransition("high_risk_start")  # launches concurrent approvals
s_skip  = SilentTransition("skip_supplier")     # supplier skipped path

# --- operators ---
op_risk = OperatorPOWL(Operator.XOR, [t_sup, s_high])
op_supp = OperatorPOWL(Operator.XOR, [t_cons, s_skip])
loop_op = OperatorPOWL(Operator.LOOP, [t_exec, t_insp, t_adj])

# --- root partial order ---
nodes = [
    t_reg, t_cont, t_ana, t_plan, t_des,
    op_risk, t_sup, s_high, t_qual, t_regul,
    op_supp, t_cons, s_skip,
    loop_op, t_exec, t_insp, t_adj,
    t_rel, t_arc
]
powl = StrictPartialOrder(nodes)

# --- precedence edges ---
powl.order.add_edge(t_reg, t_cont)
powl.order.add_edge(t_reg, t_ana)
powl.order.add_edge(t_cont, t_plan)
powl.order.add_edge(t_ana, t_des)
powl.order.add_edge(t_ana, op_risk)
powl.order.add_edge(t_ana, op_supp)

# trial prerequisites (cross-branch synchronization)
powl.order.add_edge(t_des, loop_op)
powl.order.add_edge(t_plan, loop_op)

# risk route expansion
powl.order.add_edge(op_risk, t_sup)
powl.order.add_edge(op_risk, s_high)
powl.order.add_edge(s_high, t_qual)
powl.order.add_edge(s_high, t_regul)

# supplier expansion
powl.order.add_edge(op_supp, t_cons)
powl.order.add_edge(op_supp, s_skip)

# release synchronization: waits for loop exit, approval path, supplier path
powl.order.add_edge(t_sup,    t_rel)
powl.order.add_edge(t_qual,  t_rel)
powl.order.add_edge(t_regul, t_rel)
powl.order.add_edge(t_cons,  t_rel)
powl.order.add_edge(s_skip,  t_rel)
powl.order.add_edge(loop_op, t_rel)

# case closure
powl.order.add_edge(t_rel, t_arc)
```

Why unconnected pairs may remain concurrent:
- `t_cont` and `t_ana`: No edge in either direction; both depend only on `t_reg`.
- `t_qual` and `t_regul`: Both depend only on `s_high`; no mutual edge.
- `loop_op` and `op_risk` / `op_supp`: `loop_op` depends on `t_des` and `t_plan`; `op_risk` and `op_supp` depend only on `t_ana`. Once prerequisites are satisfied, they run without ordering constraints.
- `t_exec` / `t_insp` / `t_adj`: Encapsulated inside `loop_op`; internal repetition is managed by the loop operator, not by acyclic root edges.

# 7. Preferred Representation and Validation Plan

**Canonical choice: POWL.** It expresses the non-block-structured cross-branch dependencies (trial waiting on design/planning, approvals overlapping trial, supplier synchronization) directly via partial-order edges and missing-edge concurrency, without forcing a hierarchical block structure. The tree is retained only for comparison and demonstrates where hierarchical approximation fails.

**Concrete validation plan:**

1. **Conversion to Petri net:** `net, im, fm = pm4py.convert_to_petri_net(powl)`. Inspect the net to verify that `Quality Review` and `Regulatory Review` have independent input/output arcs (concurrency) and that `Release Material` has multiple input places (synchronization).
2. **Soundness check:** `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`. Expect sound (no deadlocks, no dead transitions, proper termination) given the explicit start/end and synchronization.
3. **Bounded / sampled playout:** `pm4py.play_out(powl, variant=...)` or `play_out(net, ...)` to generate traces. Sample at least 50 traces and inspect that:
   - `Consult Supplier` appears in ~some proportion but never more than once per trace.
   - `Adjust Parameters` never appears after the final `Inspect Trial`.
4. **Explicit positive trace tests:** Replay T1–T4 (allowed) through the POWL and converted net; confirm acceptance.
5. **Explicit negative trace tests:** Replay T6–T8 (forbidden); confirm rejection at the earliest violating activity.
6. **Silent / duplicate-label check:** Inspect generated traces to verify that `SilentTransition` nodes (`high_risk_start`, `skip_supplier`) and `tau` do not appear in visible trace logs. Confirm that visible labels (`Register Deviation` through `Archive Case`) occur at most once per trace (except loop repetitions for `Execute`/`Inspect`/`Adjust`).
7. **Tree approximation check:** Replay T5 through `tree`; confirm rejection, documenting that the tree’s conservative block structure excludes the valid early-approval interleaving.
8. **Limitations:** The validation relies on control-flow replay; it does **not** validate data conditions (low vs high risk, pass vs fail, supplier selection). Those remain abstracted. Also, `pm4py.convert_to_petri_net` for POWL may introduce silent transitions that obscure direct visibility of loop iterations.

# 8. Final Self-Critique

1. **Tree approximation weakens fidelity:** By placing approvals and supplier consultation inside the synchronization `PARALLEL`, the tree conservatively excludes all traces where those activities begin before both `Design Corrective Action` and `Plan Verification` finish. This is a semantic loss, not just syntactic.
2. **POWL loop representation ambiguity:** The loop is constructed with three children (`t_exec`, `t_inspect`, `t_adj`) inside `Operator.LOOP`. If PM4Py’s internal POWL parser expects a binary loop (`do`, `redo`), conversion or replay may misinterpret the internal ordering, particularly the placement of `Inspect Trial`. This is a semantic risk for validation.
3. **Data abstraction eliminates case-level reasoning:** Risk level, inspection outcome, and supplier involvement are modeled purely through control-flow alternatives (`XOR`, `LOOP`). Consequently, the model admits traces that combine incompatible data states (e.g., a “low-risk” path that includes `Quality Review` via interleaving, though the `XOR` prevents execution of both branches in one trace, the absence of data guards means analysis tools cannot correlate case attributes with paths). This is a fundamental semantic limitation of control-flow-only modeling.
