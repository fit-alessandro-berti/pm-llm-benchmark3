```
import pandas as pd
from collections import Counter

rows = [ ... ]
columns = [...]
df = pd.DataFrame(rows, columns=columns)
df['duration_or_age_h'] = df['duration_or_age_h'].astype(float)
df['terminal'] = df['observed_status'] != 'open'

HORIZON = 72.0

def cif_at_horizon(times, codes, horizon=HORIZON, cause=1):
    times = pd.Series(list(times)).astype(float)
    codes = pd.Series(list(codes)).astype(int)
    data = pd.DataFrame({'time': times, 'code': codes})
    risk = len(data)
    S = 1.0
    cif = 0.0
    if risk == 0:
        return 0.0, 0.0, 0
    for t, g in data.groupby('time', sort=True):
        if t > horizon:
            break
        n = risk
        if n <= 0:
            break
        d_cause = int((g['code'] == cause).sum())
        d_other = int(((g['code'] > 0) & (g['code'] != cause)).sum())
        d_censor = int((g['code'] == 0).sum())
        d_all = d_cause + d_other
        if d_all > 0:
            cif += S * (d_cause / n)
            S *= (1.0 - d_all / n)
        risk -= d_all + d_censor
    return cif, S, risk

def km_survival(times, events, horizon=HORIZON):
    times = pd.Series(list(times)).astype(float)
    events = pd.Series(list(events)).astype(int)
    data = pd.DataFrame({'time': times, 'event': events})
    risk = len(data)
    S = 1.0
    if risk == 0:
        return 0.0, 0
    for t, g in data.groupby('time', sort=True):
        if t > horizon:
            break
        n = risk
        if n <= 0:
            break
        d = int(g['event'].sum())
        c = int((g['event'] == 0).sum())
        if d > 0:
            S *= (1.0 - d / n)
        risk -= d + c
    return S, risk

def encode_scenario(frame, transfer_mode):
    out = frame.copy()
    out['time'] = out['duration_or_age_h'].astype(float)
    out['resolve_code'] = 0
    out['terminal_event'] = 0
    m_res = out['observed_status'] == 'resolved'
    out.loc[m_res, 'resolve_code'] = 1
    out.loc[m_res, 'terminal_event'] = 1
    m_nonres = out['observed_status'].isin(['withdrawn', 'rejected'])
    out.loc[m_nonres, 'resolve_code'] = 2
    out.loc[m_nonres, 'terminal_event'] = 1
    m_tr = out['observed_status'] == 'transferred'
    out.loc[m_tr, 'terminal_event'] = 1
    if transfer_mode == 'censor':
        out.loc[m_tr, 'resolve_code'] = 0
    elif transfer_mode == 'competing_failure':
        out.loc[m_tr, 'resolve_code'] = 2
    elif transfer_mode == 'external_success':
        m_tr_before = m_tr & (out['time'] <= HORIZON)
        m_tr_after = m_tr & (out['time'] > HORIZON)
        out.loc[m_tr_before, 'resolve_code'] = 1
        out.loc[m_tr_after, 'resolve_code'] = 2
    else:
        raise ValueError(...)
    return out
```

```
def cif_at_horizon(times, codes, horizon=HORIZON, cause=1):
    data = pd.DataFrame({"time": pd.Series(list(times)).astype(float), "code": pd.Series(list(codes)).astype(int)})
    risk = len(data)
    S = 1.0
    cif = 0.0
    if risk == 0:
        return 0.0, 0.0, 0
    for t, g in data.groupby("time", sort=True):
        if t > horizon:
            break
        n = risk
        if n <= 0:
            break
        d_cause = int((g["code"] == cause).sum())
        d_other = int(((g["code"] > 0) & (g["code"] != cause)).sum())
        d_censor = int((g["code"] == 0).sum())
        d_all = d_cause + d_other
        if d_all > 0:
            cif += S * (d_cause / n)
            S *= (1.0 - d_all / n)
        risk -= d_all + d_censor
    return cif, S, risk
```

# 1. SLA estimands and time definitions

**Time origin.** The natural time origin is the `Submit` event, because the SLA is defined as 72 elapsed hours from `Submit`.

**Time scale.** Use continuous elapsed hours from `Submit`. For terminal rows, `duration_or_age_h` is the time from `Submit` to the terminal event. For `open` rows, it is the age at the observation cutoff.

**Horizon.** The SLA horizon is 72 hours. Some estimands also need a post-72-hour landmark or a cutoff-based follow-up horizon.

**Administrative cutoff.** The extract is frozen at one observation cutoff. Open cases are administratively right-censored at their observed age, unless their age is already at least 72 hours, in which case their status at 72 hours is known.

**Important distinction.**

- **Right censoring** means the case has not yet been observed to reach the relevant event by the cutoff, but could still reach it later. Example: an open case aged 47 hours.
- **Competing events** are observed terminal outcomes that prevent the event of interest under the internal process. Examples: `Withdraw`, `Reject`, and, depending on the estimand, `Transfer`.
- **Already-observed breaches** are cases where the case is known to have failed the 72-hour resolution condition by the data cutoff. Examples: resolved at 76 hours, or open at 92 hours.

## Estimand 1: Probability of not being resolved by 72 hours

**Definition.**  
Let \(T_R\) be the time to internal `Resolve`. The estimand is:

\[
P(T_R > 72 \text{ or no internal resolution by 72})
\]

Equivalently, this can be expressed as:

\[
1 - F_{\text{Resolve}}(72)
\]

where \(F_{\text{Resolve}}(72)\) is the cumulative incidence function for internal resolution by 72 hours in a competing-risks framework.

**Operational use.**  
This is the most direct customer-facing SLA-compliance estimand. It answers: *what is the probability that a case will not be internally resolved within the SLA window?* It is useful for SLA reporting, proactive triage, and staffing decisions before the 72-hour deadline.

**Assumption label A1.** Internal `Resolve` by 72 hours is success. `Withdraw`, `Reject`, and `Transfer` are not automatically equivalent to success; their treatment must be specified.

## Estimand 2: Probability of still having no terminal disposition at 72 hours

**Definition.**  
Let \(T_T\) be the time to any internal terminal disposition: `Resolve`, `Withdraw`, `Reject`, or `Transfer`. The estimand is:

\[
P(\text{case is still open/in progress at 72 hours})
\]

This is a state-occupation probability for the nonterminal/open state at 72 hours.

**Operational use.**  
This estimand matches backlog and workload management. It asks: *how much unresolved, still-active internal work is likely to remain at the SLA horizon?* It is useful for identifying tail risk, stale cases, and capacity pressure, independent of whether some cases will later terminate as withdrawals or rejections.

**Assumption label A2.** `Transfer` is an internal terminal disposition because internal observation stops at transfer. Whether the external organization later resolves the case is unknown.

## Estimand 3: Landmark probability of late resolution after 72 hours

**Definition.**  
Among cases that are still under internal observation and unresolved at 72 hours, estimate:

\[
P(\text{Resolve after 72 hours} \mid \text{unresolved and internally observable at 72 hours})
\]

This should be estimated with a 72-hour landmark to avoid immortal-time bias.

**Operational use.**  
This supports recovery actions for breached cases: *among cases that have already failed the 72-hour resolution target, how many are still likely to be resolved later, and how quickly?*

## Example contributions under each estimand

The four examples requested are: resolved at 76 hours, open at 92 hours, withdrawn at 27 hours, and transferred at 68 hours. In the supplied data these correspond approximately to `S03`, `S09`, `S06`, and `S08`.

# 2. Event and censoring encoding

The following encoding uses these codes for the resolution estimand:

- `1` = internal `Resolve` event.
- `2` = competing non-resolution terminal event.
- `0` = right-censored / still under observation for the relevant estimand.

For the “still no terminal disposition” estimand:

- `1` = any internal terminal disposition.
- `0` = still open/in progress or censored before terminal disposition.

| observed status | time used | resolution estimand code | no-terminal-disposition code | default competing-risk role | sensitivity alternatives |
|---|---:|---:|---:|---|---|
| `resolved` | duration to `Resolve` | `1` | `1` | event of interest for resolution; terminal disposition for open-state estimand | if resolution occurs after 72h, it is still an observed breach of resolution-by-72 |
| `withdrawn` | duration to `Withdraw` | `2` | `1` | competing terminal event for resolution; terminal disposition for open-state estimand | if withdrawal is outside operational control, treat as competing exit or censoring rather than SLA failure |
| `rejected` | duration to `Reject` | `2` | `1` | competing terminal event for resolution; terminal disposition for open-state estimand | if rejection is a desired fast-fail outcome, it may be treated as a competing success or censoring for SLA failure |
| `open` | age at cutoff | `0` | `0` | right-censored before terminal event; if age >= 72, known unresolved/open at 72 | if `last_event_gap_h` is large, treat as informative censoring, worst-case failure, or separate stale state |
| `transferred`, assumption T1: administrative censoring | duration to `Transfer` | `0` | `0` if estimating active internal work; otherwise `1` if transfer is considered terminal internal disposition | loss to internal follow-up; assumes transfer is non-informative conditional on history | usually too optimistic if transfers are complex or selected |
| `transferred`, assumption T2: competing failure / internal terminal exit | duration to `Transfer` | `2` | `1` | competing event for resolution; terminal disposition for open-state estimand | appropriate when internal SLA success requires internal resolution and transfer means the internal process failed to complete |
| `transferred`, assumption T3: external-outcome bound | duration to `Transfer` | best-case: `1` if transfer occurs before 72h and external resolution is assumed; worst-case: `2` | `1` | bounded imputation for unknown external outcome | best-case assumes external organization resolves within SLA; worst-case assumes no external resolution by 72h |

**Transfer assumptions in more detail.**

1. **T1: Transfer as administrative censoring.**  
   This treats transfer like loss to follow-up. It is defensible only if the reason for transfer is unrelated to the future probability of resolution, conditional on observed history. That is unlikely here because escalated and complex cases appear among transfers, for example `S08`, `S21`, and `S32`.

2. **T2: Transfer as competing failure / terminal internal disposition.**  
   This is operationally conservative for internal SLA. If the internal organization cannot resolve the case and hands it away, the case is not internally resolved by 72h. This is usually the best default for internal SLA governance.

3. **T3: External-outcome bounds.**  
   Because the external outcome is unknown, one can bound the estimand. Best-case: all transfers before 72h are externally resolved by 72h. Worst-case: no transferred case is resolved by 72h. These bounds show how much the SLA conclusion depends on the unobserved external process.

# 3. Why naive completed-case analysis is biased

A naive analysis that uses only completed resolved cases is biased in several ways.

## Survivor bias

If we analyze only resolved cases, we condition on success. The resolved cases in the data are:

- Cohort A: `S01`, `S02`, `S03`, `S04`, `S07`, `S13`.
- Cohort B: `S16`, `S17`, `S18`, `S19`, `S20`, `S27`, `S28`.

This ignores cases that terminated early without resolution, such as `S05` rejected at 9 hours, `S12` withdrawn at 15 hours, and `S23` rejected at 11 hours. It also ignores open cases that may breach SLA, such as `S09`, `S11`, `S25`, and `S26`, and transferred cases such as `S08`, `S21`, and `S32`.

A resolved-only mean duration may make cohort B look faster than cohort A, but that comparison is conditional on reaching `Resolve`. It does not estimate the probability of SLA breach.

## Informative censoring

Open cases are not merely incomplete rows. Their gaps may be informative.

Examples:

- `S11` is open at 81 hours with a last-event gap of 55 hours.
- `S26` is open at 104 hours with a last-event gap of 72 hours.
- `S25` is open at 79 hours with a last-event gap of 48 hours.
- `S09` is open at 92 hours with a last-event gap of 31 hours.

These cases may be stalled. Treating them as ordinary non-informative right censoring assumes that their future resolution behavior is similar to cases with comparable observed history, which may be false.

Transfers also create likely informative censoring. For example, `S08` is a P1 escalated case transferred at 68 hours, and `S32` is a P1 escalated case transferred at 96 hours. If escalation and transfer are markers of complexity, censoring transfers may remove difficult cases from the risk set and overstate internal SLA performance.

## Competing risks

`Withdraw`, `Reject`, and `Transfer` can prevent internal resolution. If these are treated as ordinary censoring in a Kaplan-Meier analysis of resolution, the estimated probability of resolution will generally be biased upward.

For example:

- `S06` withdrawn at 27 hours.
- `S14` rejected at 63 hours.
- `S22` withdrawn at 44 hours.
- `S30` withdrawn at 70 hours.

These cases cannot later become internal resolutions. They should be competing events for the internal-resolution estimand, not simple censored observations.

## Cohort imbalance and rollout compliance

Cohort B began after a policy change, but assignment was not randomized and rollout compliance was incomplete.

Observed complications:

- Cohort B has more P1 cases than cohort A: `S18`, `S21`, `S25`, `S29`, `S32` versus `S04`, `S08`, `S11`.
- Some cohort B cases do not show `AutoCheck` in the prefix, for example `S20`, `S23`, `S26`, and `S30`.
- Some cohort A cases do show `AutoCheck`, for example `S01` and `S15`.

Therefore, `cohort` is not a clean treatment variable. It is a proxy for a partially implemented policy. Any cohort comparison should be stratified or adjusted carefully, and causal claims should be avoided unless the assignment mechanism is better understood.

## Open cases below versus above 72 hours

Open cases below 72 hours are still capable of meeting the SLA:

- `S10` open at 47 hours.
- `S15` open at 35 hours.
- `S24` open at 67 hours.
- `S29` open at 51 hours.
- `S31` open at 23 hours.

Open cases at or above 72 hours are already known to be unresolved at the SLA horizon:

- `S09` open at 92 hours.
- `S11` open at 81 hours.
- `S25` open at 79 hours.
- `S26` open at 104 hours.

For the probability of not being resolved by 72 hours, the latter group is already observed to have failed the resolution-by-72 condition. They should not be treated as if their 72-hour status is unknown.

# 4. Statistical analysis plan

## Kaplan-Meier

Kaplan-Meier estimates the survival function for a single event type, treating other outcomes as censored.

**Use here.** It can be used for the probability of still having no terminal disposition by 72 hours if all terminal dispositions are treated as events.

**Problem.** If used for resolution while treating `Withdraw`, `Reject`, and `Transfer` as censored, it will usually overestimate the probability of resolution because competing events are treated as if they could still become resolutions.

## Aalen-Johansen / cumulative incidence function

The Aalen-Johansen estimator estimates state probabilities in a multi-state or competing-risks setting. For this task, it can estimate:

- cumulative incidence of `Resolve` by 72 hours;
- cumulative incidence of competing non-resolution outcomes by 72 hours;
- probability of remaining open/in progress at 72 hours.

**Use here.** This is the most appropriate nonparametric approach for the primary SLA estimands because it respects competing risks and does not require dropping open cases.

## Cause-specific hazards

A cause-specific hazard model estimates the instantaneous rate of a particular event among cases still at risk of that event.

**Use here.** Useful for understanding how covariates affect the rate of resolution versus competing exits. It can be extended to time-dependent covariates.

**Caution.** The data are small, and several covariates such as `Escalate` and `Rework` are post-baseline. A time-aware design is required.

## Subdistribution hazards

Fine-Gray subdistribution hazard models directly model the cumulative incidence of an event in the presence of competing risks.

**Use here.** Potentially useful if the goal is prediction of absolute SLA breach probability rather than etiologic hazard interpretation.

**Caution.** With only 32 cases and many competing outcomes, subdistribution models will be unstable. They should not be the primary method unless more data are available.

## Restricted mean time

Restricted mean survival time or restricted mean time lost up to 72 hours can summarize average time spent without resolution or without terminal disposition within the SLA window.

**Use here.** Useful as a secondary summary because it is less dependent on a single binary threshold and can be compared by cohort or priority. With competing risks, restricted mean time can be computed from area under the relevant CIF or state-probability curves.

## Landmarking

Landmarking defines a fixed time, such as 24 hours, stage completion, or 72 hours, and analyzes only cases still at risk at that landmark using features known by that time.

**Use here.** Important for process-aware covariates such as `Escalate`, `Rework`, repeated `Review`, and current stage. These occur after case start and cannot safely be treated as baseline covariates.

A 72-hour landmark is especially useful for estimating late resolution among cases that have already breached the resolution-by-72 target.

## Multi-state model

A multi-state model would represent activities such as `Screen`, `AutoCheck`, `Review`, `Rework`, `Escalate`, and terminal states such as `Resolve`, `Withdraw`, `Reject`, and `Transfer`.

**Use here.** Conceptually ideal because the prefixes contain process structure.

**Limitation.** The supplied data provide only the full prefix and the terminal/cutoff duration. Exact intermediate event timestamps are not supplied. Therefore, transition-specific hazards between activities cannot be reliably estimated without additional assumptions or additional data.

## Recommended primary approach

**Primary estimand:** probability of not being internally resolved by 72 hours.

**Primary estimator:** Aalen-Johansen cumulative incidence for internal `Resolve` by 72 hours, with `Withdraw`, `Reject`, and `Transfer` treated as competing terminal events under the default internal-SLA assumption.

**Why.** This matches the operational SLA question, handles competing risks, keeps open cases in the risk set, and avoids the survivor bias of completed-case analysis. It is also nonparametric, which is important given the small sample.

## Recommended secondary approach

**Secondary estimand:** probability of still having no terminal disposition at 72 hours, plus a 72-hour landmark analysis of late resolution.

**Secondary estimator:** state-occupation/Kaplan-Meier-style estimate for no terminal disposition by 72 hours, and landmark cumulative incidence for post-72 resolution among cases unresolved and internally observable at 72 hours.

**Why.** The first secondary estimand supports workload and stale-case management. The landmark analysis supports recovery decisions for breached cases while avoiding immortal-time bias.

# 5. Process-aware features and stage hazards

The prefixes are useful for process-aware covariates, but most of them are time-dependent. They should not be used as baseline predictors unless they are known at the prediction time.

## Proposed features

| feature | derivation from prefix/data | type | risk / interpretation |
|---|---|---|---|
| priority | supplied field | baseline | P1 is highest priority; may be confounded with complexity |
| cohort | supplied field | baseline proxy | not randomized; rollout compliance incomplete |
| initial path pattern / variant | full prefix, e.g. `Submit>Screen>Review>Resolve` | process pattern | useful descriptively; full prefix may leak future if used for early prediction |
| current stage | last observed activity for open cases | time-varying | appropriate only if evaluated at current time |
| ever escalated | prefix contains `Escalate` | time-varying / post-treatment | cannot be baseline unless landmarked after escalation time |
| escalation timing | position of `Escalate` in prefix or time since `Submit` | time-varying | exact timing not supplied; ordinal position is weak proxy |
| repeated review | count of `Review` occurrences | time-varying / post-treatment | may indicate difficulty or rework loop |
| rework count | supplied `rework_count` | time-varying / post-treatment | likely a mediator of delay, not a baseline cause |
| AutoCheck exposure | prefix contains `AutoCheck`, and whether before/after `Screen` | time-varying / policy exposure | rollout incomplete; not safely baseline without landmark |
| inactivity gap | `last_event_gap_h` for open cases | time-varying | strong candidate for informative censoring or stale-case alerting |
| path length | number of activities in prefix | process complexity | can leak outcome if terminal activity is included |
| terminal state | `Resolve`, `Withdraw`, etc. | outcome | must not be used as predictor |

## Immortal-time and leakage risks

`Escalate` is a clear example of immortal time. A case must remain active until escalation occurs. If we compare escalated versus non-escalated cases using a baseline covariate `escalated=yes`, we give escalated cases credit for surviving until escalation. Early failures that never had the chance to be escalated are incorrectly assigned to the non-escalated group.

Examples:

- `S03` reaches `Escalate` only after `Submit>Screen>Review`, then later resolves at 76 hours.
- `S05` is rejected at 9 hours and never has the opportunity to be escalated.
- `S11` is open at 81 hours with prefix `Submit>Screen>Escalate`; escalation status is known, but the exact escalation time is not supplied.

Safe designs:

- use landmark prediction, for example at 24 hours, at stage completion, or at 72 hours;
- use time-dependent covariates where escalation status changes from no to yes at the actual escalation time;
- avoid using the full terminal prefix to predict early SLA breach.

Leakage also occurs if features derived from the full prefix include information that would not be known at prediction time. For example, knowing that a case eventually has `Rework` before `Resolve` is not available at the moment the case first enters `Review`.

## Proposed state-transition representation

The following is a textual multi-state representation consistent with the observed prefixes.

- `Submit` -> `Screen` or `AutoCheck`
- `Screen` -> `AutoCheck`, `Review`, `Escalate`, `Resolve`, `Reject`, `Withdraw`
- `AutoCheck` -> `Screen`, `Review`, `Escalate`, `Resolve`
- `Review` -> `Resolve`, `Reject`, `Withdraw`, `Rework`, `Escalate`, `Transfer`
- `Rework` -> `Review`
- `Escalate` -> `Resolve`, `Review`, `Transfer`
- `Resolve` = absorbing internal success
- `Withdraw` = absorbing internal non-resolution
- `Reject` = absorbing internal non-resolution
- `Transfer` = absorbing from the internal system, external outcome unknown

The open state is not an activity label in the prefix but represents the case being in transit between the last observed activity and the next event or cutoff.

# 6. Sensitivity analysis

At least three sensitivity analyses are needed because transfers, withdrawals/rejections, informative censoring, and cohort policy effects are all ambiguous.

## Sensitivity 1: Base internal-SLA analysis

**Transfers.** Treated as competing terminal failures for internal resolution.  
**Withdrawals/rejections.** Treated as competing terminal non-resolution events.  
**Open cases below 72h.** Right-censored at age.  
**Open cases at/above 72h.** Known unresolved at 72h; contribute to unresolved-at-72 risk.  
**Cohort/priority.** Stratified, not interpreted causally.

**Purpose.** This is the conservative operational SLA view. It answers whether the internal organization resolved the case within 72 hours.

**Likely qualitative effect.** This will usually produce a higher breach probability than completed-case analysis because it includes competing non-resolution outcomes and unresolved open cases.

## Sensitivity 2: Internal-control / transfer-censored analysis

**Transfers.** Censored at transfer time.  
**Withdrawals/rejections.** Still competing events for resolution.  
**Open cases.** Same as base analysis.

**Purpose.** This estimates a hypothetical probability of resolution if transferred cases had remained under internal observation. It is not the same as operational SLA performance because transfers are removed from the risk set.

**Likely qualitative effect.** If transferred cases are more complex, this analysis may overstate resolution probability. It may also change cohort comparisons because cohort B has two transfers, `S21` and `S32`, while cohort A has one, `S08`.

## Sensitivity 3: External-outcome bounds and informative open gaps

**Transfers.** Use best-case and worst-case bounds.

- Best-case: transfers before 72h are assumed externally resolved by 72h.
- Worst-case: transfers before 72h are assumed unresolved by 72h.

**Open cases below 72h.** Use bounds:

- optimistic: all open cases below 72h resolve before 72h;
- pessimistic: all open cases below 72h remain unresolved by 72h.

**Long-gap open cases.** Consider cases with large `last_event_gap_h`, such as `S11`, `S25`, `S26`, and `S09`, as stale or high-risk. In a conservative analysis, they may be treated as failures or routed to a separate stale state.

**Withdrawals/rejections.** Compare:

- competing failure treatment;
- censoring treatment if withdrawal/rejection is outside SLA responsibility;
- separate cause-specific reporting.

**Cohort policy.** Compare:

- cohort as assigned;
- cohort stratified by priority;
- actual observed `AutoCheck` exposure by landmark, rather than cohort label.

**Qualitative conclusions that could reverse.**

1. **Cohort B may appear better or worse.** Resolved-only durations may favor B, but once transfers, open-above-72 cases, and priority mix are included, the conclusion may reverse.
2. **Escalation may appear harmful or protective.** If escalation is used as a baseline covariate, it suffers immortal-time bias. A landmark or time-dependent analysis may change the direction.
3. **The SLA problem may appear to be driven by open tail risk or by terminal non-resolution.** If withdrawals/rejections are treated as failures, terminal non-resolution is large. If they are treated as exits, the unresolved open tail becomes more important.
4. **The policy effect of automated screening may appear positive, neutral, or negative.** Because rollout compliance was incomplete and cohort assignment was not randomized, the apparent effect can change depending on whether analysis uses cohort, actual `AutoCheck` exposure, or priority-stratified comparisons.

# 7. Operational interpretation

Survival outputs should be used as decision support, not as causal scores.

## Alerts

A practical alerting rule can be built from landmarked risk estimates and process features.

Examples:

- At 48 hours, if the estimated probability of not being resolved by 72 hours is high and the case is still in `Review`, trigger a manual review.
- If a case is in `Escalate` and has a large `last_event_gap_h`, trigger follow-up. For example, `S10` has gap 19 hours, `S09` has gap 31 hours, `S25` has gap 48 hours, `S11` has gap 55 hours, and `S26` has gap 72 hours.
- If a case is open beyond 72 hours, it should be treated as an SLA recovery case, not as a normal active case. The open-above-72 cases here are `S09`, `S11`, `S25`, and `S26`.

## Workload actions

The “still no terminal disposition at 72 hours” estimand supports capacity planning. If this probability is high for a cohort or priority class, the operation should expect backlog and may need to reallocate reviewers or escalate stale cases.

For transferred cases, operational action should be separated into internal SLA governance and external follow-up. Internally, transfer may count as failure to resolve. Externally, the organization may need a follow-up agreement with the receiving organization because the eventual outcome is unknown.

## SLA governance

For governance, report multiple views:

- cumulative incidence of internal resolution by 72 hours;
- probability of not being resolved by 72 hours;
- probability of still being open at 72 hours;
- cumulative incidence of transfer by 72 hours;
- late-resolution recovery rate after 72 hours;
- stratification by priority and cohort.

This avoids hiding the cause of SLA failure. For example, a team may have good resolution speed among non-transferred cases but poor SLA performance because many P1 cases are transferred or remain stale.

## Calibration and fairness checks

Because risk estimates may be used for triage, calibration and fairness checks are necessary.

- Calibrate predicted risk against observed outcomes by priority and cohort.
- Check whether P1 cases are systematically over- or under-predicted. This matters because P1 cases in the data include several transfers and open-above-72 cases.
- Check cohort A versus cohort B carefully because cohort is confounded with policy rollout and priority mix.
- Do not present risk scores as causal effects of escalation, rework, or automated screening. These are process events that occur after case start and may be consequences of case difficulty.

Uncertainty should be shown explicitly. With only 32 cases, confidence intervals or bootstrap intervals will be wide, and any subgroup conclusion should be treated as tentative.

```python
def cif_at_horizon(times, codes, horizon=HORIZON, cause=1):
    """
    Simple Aalen-Johansen-style cumulative incidence for one cause.

    codes:
      0 = censoring
      1 = cause of interest
      2 = competing event

    Returns:
      cif_cause, survival_no_event, risk_after_processing_horizon
    """
    data = pd.DataFrame({
        "time": pd.Series(list(times)).astype(float),
        "code": pd.Series(list(codes)).astype(int)
    })

    risk = len(data)
    survival = 1.0
    cif = 0.0

    if risk == 0:
        return 0.0, 0.0, 0

    for t, g in data.groupby("time", sort=True):
        if t > horizon:
            break

        n = risk
        if n <= 0:
            break

        d_cause = int((g["code"] == cause).sum())
        d_other = int(((g["code"] > 0) & (g["code"] != cause)).sum())
        d_censor = int((g["code"] == 0).sum())
        d_all_events = d_cause + d_other

        if d_all_events > 0:
            cif += survival * (d_cause / n)
            survival *= (1.0 - d_all_events / n)

        risk -= d_all_events + d_censor

    return cif, survival, risk


def km_survival(times, events, horizon=HORIZON):
    """
    Kaplan-Meier survival for a single event indicator.

    events:
      1 = terminal event for the estimand
      0 = censoring / still in nonterminal state
    """
    data = pd.DataFrame({
        "time": pd.Series(list(times)).astype(float),
        "event": pd.Series(list(events)).astype(int)
    })

    risk = len(data)
    survival = 1.0

    if risk == 0:
        return 0.0, 0

    for t, g in data.groupby("time", sort=True):
        if t > horizon:
            break

        n = risk
        if n <= 0:
            break

        d = int(g["event"].sum())
        c = int((g["event"] == 0).sum())

        if d > 0:
            survival *= (1.0 - d / n)

        risk -= d + c

    return survival, risk

# 3. Encoding for at least two estimands and three transfer scenarios.
#
# Estimand 1: probability of not being resolved by 72h.
#             Estimated as 1 - CIF_resolve(72).
#
# Estimand 2: probability of still having no terminal disposition at 72h.
#             Estimated by KM survival where terminal dispositions are events.
#
# Transfer scenarios:
#   censor:            transfer treated as administrative censoring
#   competing_failure: transfer treated as competing terminal non-resolution
#   external_success:  best-case assumption: transfers before 72h are
#                      assumed externally resolved by transfer time
# ------------------------------------------------------------------

def encode_scenario(frame, transfer_mode):
    out = frame.copy()
    out["time"] = out["duration_or_age_h"].astype(float)

    # Resolution estimand codes:
    # 0 = censor, 1 = Resolve, 2 = competing non-resolution
    out["resolve_code"] = 0

    # No-terminal-disposition estimand:
    # 1 = terminal internal disposition, 0 = still open/censored
    out["terminal_event"] = 0

    m_res = out["observed_status"] == "resolved"
    out.loc[m_res, "resolve_code"] = 1
    out.loc[m_res, "terminal_event"] = 1

    m_nonres = out["observed_status"].isin(["withdrawn", "rejected"])
    out.loc[m_nonres, "resolve_code"] = 2
    out.loc[m_nonres, "terminal_event"] = 1

    m_tr = out["observed_status"] == "transferred"

    if transfer_mode == "censor":
        # Sensitivity: transfer is loss to internal follow-up.
        out.loc[m_tr, "resolve_code"] = 0
        out.loc[m_tr, "terminal_event"] = 0

    elif transfer_mode == "competing_failure":
        # Default internal-SLA view: transfer prevents internal resolution.
        out.loc[m_tr, "resolve_code"] = 2
        out.loc[m_tr, "terminal_event"] = 1

    elif transfer_mode == "external_success":
        # Best-case bound: transfers observed before 72h are assumed
        # externally resolved by their transfer time. Transfers after 72h
        # cannot help resolution by 72h.
        out.loc[m_tr, "terminal_event"] = 1
        m_tr_before = m_tr & (out["time"] <= HORIZON)
        m_tr_after = m_tr & (out["time"] > HORIZON)
        out.loc[m_tr_before, "resolve_code"] = 1
        out.loc[m_tr_after, "resolve_code"] = 2

    else:
        raise ValueError("Unknown transfer_mode.")

    return out


def summarize_encoded(enc, horizon=HORIZON):
    cif_resolve, survival_resolve, risk_after = cif_at_horizon(
        enc["time"], enc["resolve_code"], horizon=horizon, cause=1
    )

    cif_nonresolve, _, _ = cif_at_horizon(
        enc["time"], enc["resolve_code"], horizon=horizon, cause=2
    )

    open_no_terminal, _ = km_survival(
        enc["time"], enc["terminal_event"], horizon=horizon
    )

    # Cases observed to or beyond the horizon under this encoding.
    observed_to_72 = int(
        (
            (enc["time"] >= horizon)
            | ((enc["time"] <= horizon) & ((enc["resolve_code"] > 0) | (enc["terminal_event"] > 0)))
        ).sum()
    )

    return {
        "n": len(enc),
        "observed_or_at_risk_to_72": observed_to_72,
        "resolve_by_72": cif_resolve,
        "not_resolved_by_72": 1.0 - cif_resolve,
        "nonresolve_terminal_by_72": cif_nonresolve,
        "open_no_terminal_by_72": open_no_terminal,
        "risk_after_horizon": risk_after,
    }

# 7. 72-hour landmark: late resolution among cases unresolved and
#    internally observable at 72h. This avoids using post-72 events
#    as baseline predictors.
# ------------------------------------------------------------------

def landmark_late_resolution(frame, horizon=HORIZON):
    landmark_rows = []

    for r in frame.itertuples():
        t = float(r.duration_or_age_h)
        status = r.observed_status

        # Cases known to be open at/after 72h: censored after landmark.
        if status == "open" and t >= horizon:
            landmark_rows.append((r.case, t - horizon, 0))

        # Cases resolving after 72h: late-resolution events.
        elif status == "resolved" and t > horizon:
            landmark_rows.append((r.case, t - horizon, 1))

        # Cases transferred after 72h: competing exits after landmark.
        elif status == "transferred" and t > horizon:
            landmark_rows.append((r.case, t - horizon, 2))

        # If any withdrawal/rejection occurred after 72h, treat as competing.
        elif status in ["withdrawn", "rejected"] and t > horizon:
            landmark_rows.append((r.case, t - horizon, 2))

    lm = pd.DataFrame(landmark_rows, columns=["case", "time_since_72", "code"])

    if len(lm) == 0:
        return {"n_landmark": 0}

    max_t = float(lm["time_since_72"].max())

    cif_late, _, _ = cif_at_horizon(
        lm["time_since_72"], lm["code"], horizon=max_t, cause=1
    )

    cif_competing, _, _ = cif_at_horizon(
        lm["time_since_72"], lm["code"], horizon=max_t, cause=2
    )

    return {
        "n_landmark": len(lm),
        "observed_late_resolutions": int((lm["code"] == 1).sum()),
        "cif_late_resolution_by_cutoff": round(cif_late, 3),
        "cif_competing_after_72": round(cif_competing, 3),
        "max_followup_after_72_h": round(max_t, 1),
    }

print("\n=== 72-hour landmark: late resolution among unresolved cases observable at 72h ===")
print(landmark_late_resolution(df))

def normalize_variant_key(k):
    if isinstance(k, tuple):
        return k
    if isinstance(k, list):
        return tuple(k)
    if isinstance(k, str):
        return tuple(k.split(">")) if ">" in k else (k,)
    try:
        return tuple(k)
    except Exception:
        return (str(k),)


def manual_variant_counts(log_obj):
    counts = Counter()
    for trace in log_obj:
        acts = []
        for event in trace:
            act = None
            if isinstance(event, dict):
                act = event.get("concept:name")
            elif hasattr(event, "get"):
                try:
                    act = event.get("concept:name")
                except Exception:
                    act = None
            elif hasattr(event, "__getitem__"):
                try:
                    act = event["concept:name"]
                except Exception:
                    act = None
            if act is None:
                act = str(event)
            acts.append(act)
        counts[tuple(acts)] += 1
    return counts
```

# 9. Limitations and additional data

The biggest limitation is that the extract provides only the full prefix and one terminal/cutoff duration. That is enough for terminal-time survival estimands and control-flow description, but not enough for reliable transition-level process mining.

**Highest-priority missing data.**

1. **Exact event timestamps for every activity.**  
   Needed to estimate stage-transition hazards, time-dependent covariates, escalation timing, and true multi-state models. Without them, features such as escalation timing and repeated review can only be approximated by sequence order.

2. **External outcomes after transfer.**  
   Needed to know whether transferred cases are eventually resolved, rejected, withdrawn, or remain open externally. Without this, transfer assumptions dominate the SLA tail-risk estimate.

3. **Cutoff date and submission dates.**  
   Needed to distinguish calendar-time effects, policy rollout periods, seasonal workload, and left truncation or right censoring structures.

4. **Time-varying workload and staffing.**  
   Needed to explain long event gaps and to separate case complexity from resource starvation.

5. **Assignment mechanism for cohort B.**  
   Needed before making causal claims about the automated-screening and escalation-policy change. Randomization or a credible quasi-experimental design is missing.

6. **Rollout compliance data.**  
   Needed to know which cases were actually intended to receive automated screening, which received it in practice, and why some cases deviated from the intended path.

7. **Reasons for withdrawal, rejection, and transfer.**  
   Needed to decide whether these outcomes are SLA failures, competing exits, or desirable process outcomes.

8. **Priority change history.**  
   If priority can change after submission, the supplied priority may be post-baseline and could introduce leakage or confounding.

With those data, the recommended next step would be a landmarked multi-state survival model with time-dependent process covariates, calibrated by priority and cohort, and with explicit external-outcome modeling for transferred cases.
