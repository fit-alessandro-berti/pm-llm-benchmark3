## 6. Candidate Site B intervention
Eligibility rules  
• Case has digital documents OR originals already scanned on receipt.  
• Case is not flagged “public-sector > €100 k” (legal review mandatory) in phase 1.  

Concurrent tasks  
• Upon Registration, create Identity Check immediately.  
• Create Document Check only if originals flag = “not required” or “arrived”.  
• Identity and Document may execute in any order; both must finish before Assessment.  

Statutory prerequisites remaining mandatory  
• When originals legally required, Document Check task appears only after `Originals Receipt`.  
• Assessment still waits for both verifications.  
• Legal Review loop unchanged.  

Queue & WIP controls  
• Max 4 open Identity tasks per identity reviewer; max 6 open Document tasks per document reviewer.  
• Daily 09:00 huddle reviews WIP and stuck originals.  

Resource responsibilities  
• Roles unchanged; cross-training not yet enabled.  

Handling of Legal Review & supplement loop  
• If Legal Review issues Request Supplement, reopen Document Check only (Identity assumed stable).  

Logging requirements  
• System patch allows dual active owners; mandatory live start/complete stamping with 2-minute SLA.  

POWL-style partial order  
{Register}  
Register  <  Identity Check  
Register  <  Originals Receipt? (conditional edge)  
(Register  (Originals NotRequired  Originals Received))  <  Document Check  
{Identity Check, Document Check}    Assessment  
Assessment  {Approve, Reject, Legal Review}  
Legal Review  {Request Supplement, Approve, Reject}  
Request Supplement  Document Check (loop)  
{Approve, Reject}  Notify

## 7. Pilot for transport learning
| design element | specification | causal purpose | operational safeguard | process-mining measurement |
|---|---|---|---|---|
| Unit of assignment | individual case | eliminates team spill-over | IT flag per case | case attribute `treatment` in event log |
| Randomisation | 1:1 Bernoulli after Registration among eligible digital cases | unbiased causal effect | automated allocator; hide status from reviewers | compare control & treated |
| Eligible strata | digital claims, originals-not-required, non-public sector | isolates modifiable path | statutory compliance | stratum tag in log |
| Treatment versions | V1 = simple parallel tasks; V2 = parallel + huddles (roll after 4 weeks) | identify co-intervention value | staged rollout | version tag |
| Primary outcome | cycle time (RegistrationNotify) | effect on throughput | SLA monitor | time diff per case |
| Secondary outcomes | wait-to-Assessment, p90 cycle, rework %, appeals | mechanism check | weekly dashboards | attribute queries |
| Interference controls | identity/doc reviewers can serve both arms | minimise contamination | randomise continuously to maintain mix | resource_id in log |
| Power logic | detect 5 h median reduction with 90 % power; need ~550 pairs; expect achieved in 6 weeks | statistical validity | extend duration if arrivals dip | sequential log power calc |
| Duration | 8 weeks or 1,200 eligible cases | allow steady-state learning | early stop if harm | interim trend plots |
| Stop rules | halt if p90 cycle >15 h or rework >4 pp | safety | daily KPI alert | automated check |
| Transport analysis | compare pilot causal estimates with Site A derived priors via Bayesian hierarchical model | quantify external validity | none | export anonymised log |

Pilot explanation (220 words)  
The pilot randomises at the case level inside the legally unconstrained digital stratum, cleanly separating mechanism failure (parallel tasks do not create real overlap or reduce waits) from implementation failure (IT lock, stamping errors). By logging live timestamps and treatment flags we can compute (1) the difference in measured overlap, showing whether the structural change took effect; and (2) subsequent waits and cycle time. If overlap increases but waits do not fall, the mechanism fails because another bottleneck—e.g., assessor queue—dominates. If overlap fails to increase, implementation or IT constraints are at fault. The version switch that adds daily huddles tests whether queue discipline is an indispensable co-intervention, replicating part of Site A’s environment. Negative spill-overs are monitored through aggregate WIP and p90 tail metrics in the control arm; a surge would signal capacity theft. By embedding process-mining queries, we obtain high-resolution causal diagnostics without halting routine operations.

```python
import pm4py
from pm4py.objects.process_tree import obj as pt_obj
from pm4py.objects.powl.obj import POWL, POWLNode, AND, XOR, LOOP, SEQ
from pm4py.algo.conformance.woflan import algorithm as woflan

#################
# Site A BEFORE #
#################
a_before = pt_obj.ProcessTree()
root = pt_obj.ProcessTree(label=None, operator=pt_obj.Operator.SEQ, parent=None)
a_before = root
for lbl in ['Register', 'Identity Check', 'Document Check', 'Assessment']:
    child = pt_obj.ProcessTree(label=lbl, parent=root)
    root.children.append(child)
# XOR for decide
xor = pt_obj.ProcessTree(operator=pt_obj.Operator.XOR, parent=root)
xor.children.append(pt_obj.ProcessTree(label='Approve', parent=xor))
xor.children.append(pt_obj.ProcessTree(label='Reject', parent=xor))
root.children.append(xor)
root.children.append(pt_obj.ProcessTree(label='Notify', parent=root))

net_before, imap_before, fm_before = pm4py.convert_to_petri_net(a_before)

################
# Site A AFTER #
################
a_after = pt_obj.ProcessTree()
root2 = pt_obj.ProcessTree(operator=pt_obj.Operator.SEQ)
a_after = root2
root2.children.append(pt_obj.ProcessTree(label='Register', parent=root2))
# parallel gateway
par = pt_obj.ProcessTree(operator=pt_obj.Operator.PARALLEL, parent=root2)
par.children.append(pt_obj.ProcessTree(label='Identity Check', parent=par))
par.children.append(pt_obj.ProcessTree(label='Document Check', parent=par))
root2.children.append(par)
root2.children.append(pt_obj.ProcessTree(label='Assessment', parent=root2))
xor2 = pt_obj.ProcessTree(operator=pt_obj.Operator.XOR, parent=root2)
xor2.children.append(pt_obj.ProcessTree(label='Approve', parent=xor2))
xor2.children.append(pt_obj.ProcessTree(label='Reject', parent=xor2))
root2.children.append(xor2)
root2.children.append(pt_obj.ProcessTree(label='Notify', parent=root2))

net_after, imap_after, fm_after = pm4py.convert_to_petri_net(a_after)

###############
# Site B POWL #
###############
b_powl = POWL()
# create nodes
n_reg = POWLNode('Register')
n_id  = POWLNode('Identity Check')
n_orig = POWLNode('Originals Receipt')
n_doc = POWLNode('Document Check')
n_assess = POWLNode('Assessment')
n_legal = POWLNode('Legal Review')
n_reqsup = POWLNode('Request Supplement')
n_appr = POWLNode('Approve')
n_rej  = POWLNode('Reject')
n_not  = POWLNode('Notify')

# add nodes
for n in [n_reg,n_id,n_orig,n_doc,n_assess,n_legal,n_reqsup,n_appr,n_rej,n_not]:
    b_powl.add_node(n)

# partial orders
b_powl.add_order(n_reg, n_id)
b_powl.add_order(n_reg, n_orig)
# Document waits for either originals OR rule: model as order from both
b_powl.add_order(n_orig, n_doc)
b_powl.add_order(n_id, n_doc)      # identity may finish first but is not required
# AND-join before assessment
b_powl.add_order(n_id, n_assess)
b_powl.add_order(n_doc, n_assess)
# XOR after assessment
b_powl.add_order(n_assess, n_legal)
b_powl.add_order(n_assess, n_appr)
b_powl.add_order(n_assess, n_rej)
# legal branch
b_powl.add_order(n_legal, n_reqsup)
b_powl.add_order(n_reqsup, n_doc)  # loop back
b_powl.add_order(n_legal, n_appr)
b_powl.add_order(n_legal, n_rej)
# final notify
b_powl.add_order(n_appr, n_not)
b_powl.add_order(n_rej, n_not)

# Convert to Petri net
```

## 9. Recommendation
conditional go

Parallelising identity and document verification can shorten Site B cycle time, but only in the subset of cases where statutory and technical conditions allow genuine overlap. Copying Site A wholesale would create premature document tasks for the 62 % of cases that must await physical originals; they would clutter queues, breach the single-lock rule, and likely shift the bottleneck to assessment and legal review.  
Therefore the proposal should proceed conditionally and incrementally:

1. Phase 1 applies to digital, originals-not-required, non-public-sector claims (38 % of volume). Here the logical gate is identical to Site A’s and the expected median cycle-time gain is 7–11 hours with p90 gain of 6–10 hours, based on the pilot scenarios.  
2. An IT configuration that permits two concurrent active owners is mandatory; without it the likelihood of benefit falls below 20 %.  
3. Daily 09:00 queue huddles and per-role WIP caps replicate Site A’s co-interventions that probably contributed 30 % of the observed improvement.  
4. Expansion to originals-required cases should occur only if (a) the median wait-for-originals falls below the identity service time, or (b) scanning on arrival enables equivalent concurrency.  
5. Parallelisation should not be applied to public-sector/high-value cases until legal-review capacity and supplement-loop metrics prove stable; otherwise tail risk of >10 hours remains.  

Green-light for the constrained pilot is recommended because downside risk is limited by WIP caps and stop-rules, and learning value is high. A negative or harmful pilot will signal either mechanism failure (no increase in overlap) or implementation failure (IT lock) and will prevent a costly full-scale roll-out. Evidence thresholds: continue only if the 95 % CI for median cycle-time reduction exceeds 4 hours and rework does not rise >2 pp; otherwise modify or abandon.
