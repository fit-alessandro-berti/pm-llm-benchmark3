# 3. Candidate policies

I define three implementable policies. All assume that Intake is always performed by the leastloaded qualified resource (prefer same resource who will do diagnostics if possible), and Validation by the same resource when sensible. Preemption of lowerpriority diagnostic work by P1 is allowed only if the estimated finish time of the P1 case would exceed its SLA otherwise. The preempted work suffers the 10% restart penalty.

#### Policy A: Strict specialisation with fixed queues
- Each skill (Mech, Elec, Soft) has its own queue containing all diagnostic activities of that type.
- Eligible resources are those with multiplier <  (finite) for that skill, assigned to the respective queue exclusively (they cannot crosstrain).  
- For ME cases: the Mechanical and Electrical activities are **sequential** (first Mech then Elec, or viceversa by deterministic rule: always Mech then Elec). The same resource may do both if crossskilled (Ada, Deepa), avoiding handover penalty.  
- For ES cases: sequential, Electrical then Software.  
- Dispatch rule: when a resource becomes idle, it picks the highestpriority activity in its queue (P1 > P2 > P3), with earliest arrival as tiebreaker. If the resource is crossskilled (e.g., Ada for Mech/Elec), it chooses the activity that leaves the smallest sum of queue lengths for both skills.  
- No crossskill overflow: if a queue is empty and another has work, the resource remains idle.  
- Setup penalty: skillfamily switch between consecutive cases (e.g., from Mechanical to Electrical) triggers 5min setup.

**Rationale:** pure specialisation without coordination delays in multibranch cases (if same resource) and minimal handover, but risk of idle resources and poor load balancing.

#### Policy B: Full pooling with clever dispatch
- All diagnostic activities share a single priority queue, regardless of skill requirement.  
- Any resource can work on any activity for which they are qualified (the skill matrix).  
- Dispatch rule: when idle, the resource selects the activity that maximises a **priorityweighted criticality score**:
  ```
  score = priority_weight * (SLA_remaining / expected_processing_time_by_this_resource)
  ```
  where `priority_weight(P1)=5, P2=2, P3=1`. This seeks to minimise SLA violation risk.  
- For multibranch cases, a **parallelisation decision** is made at the moment the case’s Intake finishes: if at least two eligible resources are available simultaneously and the expected parallel completion (max of branch durations plus 8min coordination) is shorter than the sequential path with current queue conditions, the branches run in parallel; otherwise sequential.  
- Handover is allowed; the system tries to minimise handover by assigning the same resource to Intake and first diagnostic if possible, and then to Validation, subject to availability.  
- Setup penalties apply on skillfamily switch.

**Rationale:** maximises utilisation and reduces waiting time through pooling, but introduces more handover and setup delays; highpriority work may be delayed if many lowerpriority activities are in progress.

#### Policy C: Hybrid with reserved P1 capacity and controlled overflow (the recommended policy)
- Two virtual pools: **Core** and **Overflow**.  
  - Core resources: Ada (Mech/Elec), Chen (Elec/Soft), Deepa (Mech/Elec), Emil (Elec/Soft) – they handle all activities but with P1reserved capacity.  
  - Overflow resources: Ben (Intake/Validation only, not skilldiagnostic) and Farah (all skills, but slow multipliers) act as flex capacity.  
- **Reservation mechanism:** each core resource reserves a portion of its capacity for P1 work. Specifically, the dispatch algorithm ensures that at any moment, the total number of P1 cases being processed or waiting is  number of core resources. If a P1 case arrives and all core resources are busy with lowerpriority work, the lowestpriority activity among them (if P2/P3) is preempted to free a core resource.  
- **Overflow trigger:** if any nonP1 queue (Mech, Elec, Soft) exceeds a threshold (e.g., 2 cases), and an overflow resource (Farah) has spare capacity, Farah is assigned to that queue even if she is slower, to prevent backlog. Ben is used only for Intake/Validation; if Intake queue grows, Ben helps.  
- **Multibranch handling:** parallelisation is decided dynamically using the same logic as Policy B but with a preference for parallel when core resources are available, to exploit crossskill parallelism without long delays.  
- **Setup and handover minimisation:** Intake and first diagnostic are assigned to the same resource when possible; crossskill switch penalty is only paid when switching between skill families on the core resource, and the dispatcher discourages frequent switches unless needed.

This hybrid aims to combine the SLA protection of specialisation (via reservation) with the utilisation and flexibility of pooling, while controlling the overhead of handover.

# 6. Secondary effects and implementation risks

- **P3 starvation:** In stressed scenarios, P1 and P2 work can consume all capacity, leaving P3 cases perpetually delayed. Policy C mitigates this by allowing Farah and idle core resources to serve P3 when P1P2 queues are below thresholds, but there is a risk of indefinite postponement. A “maximum wait boost” that escalates priority after a certain wait time should be added.  
- **Preemption cascades:** If many P1 cases arrive in a short burst, repeated preemptions can multiply restart penalties, leading to unstable effective workload. Policy C limits preemption to at most one per case and uses reservation to avoid multiple simultaneous preemptions.  
- **Skill erosion:** Fixed specialisation (Policy A) encourages narrow skills, while policy C’s crossskill overflow may provide onthejob training, but also risks slower processing because crosstrained resources perform with high multipliers (e.g., Farah 1.40). This must be monitored; if skill multipliers improve with practice, the policy could adapt.  
- **Validation bottleneck:** If many cases finish diagnostics simultaneously (especially after parallelisation), the Validation stage can become a bottleneck because only Ada, Ben, Chen, Deepa, Emil, Farah can validate (most are needed for diagnostics too). Policy C’s reservation of Ben for Intake/Validation and Farah’s flexibility help, but under very high load, a separate Validation pool might be needed.  
- **Gaming:** Operators might artificially delay starting a lowpriority activity to keep a resource “reserved” for a future P1, reducing overall throughput. Clear dispatch rules with no discretionary hold time prevent this.  
- **Human interpretability:** The P1 reservation threshold and overflow trigger must be displayed on dashboards so dispatchers understand decisions; otherwise trust erodes.  
- **Cost of overtime:** Policy C occasionally triggers overtime to finish a latestarted activity within the 30min limit. If overtime is expensive, a penalty term in the dispatch score could discourage it.

7. **Policy drift:** log the `assignment_policy` field and track how often the system exits “core” mode; a rising trend indicates overload.  
8. **SLA dashboards:** using PM4Py’s caselevel attributes, build a realtime monitor that shows the fraction of P1 cases completed within 120min in the last hour; trigger alerts if it falls below 90%.

Monitoring design should include a “live process mining” loop that updates daily after each shift, comparing actual vs. simulated performance to recalibrate overflow thresholds.

def draw_service_time(activity, complex_mult=1.0):
    """Draw service time in minutes from mixture distribution."""
    sr = service_ranges[activity]
    if random.random() < sr['p'] * complex_mult:   # complex_mult for U4
        low, high = sr['complex']
    else:
        low, high = sr['ordinary']
    return random.uniform(low, high)

    return base_time * mult

def shift_available(clock, resource, overtime_used=None):
    """Return True if resource is on shift, not on break, and within overtime limit."""
    start, end = shifts[resource]
    # overtime can extend up to 30 min beyond end

    if clock < start or clock > max_end:

            return False
    # if past end, check overtime limit
    if clock > end:
        if overtime_used is not None and overtime_used.get(resource, 0) >= 30:
            return False
    return True

            sorted_cases = sorted(waiting_queues[act], key=lambda cid: (0 if cases[cid].priority=='P1' else 1 if cases[cid].priority=='P2' else 2, cases[cid].arrival))

                elif self.policy == 'C':  # hybrid

# 9. Limits and validation plan

**Limits of the supplied data**  
- Only twohour arrival blocks are given; actual instantaneous patterns (bursts) could worsen queueing.  
- Servicetime ranges without shape information might hide heavy tails beyond the complextail mixture.  
- No correlation between case type and priority is assumed; they are independent.  
- Setup and handover delays are constant, while in reality they depend on case complexity.  
- Resource breaks are fixed; in reality they may shift slightly.  
- Overtime behaviour and human batching decisions are not modelled.  
- IT outage only affects Intake start; indirect effects (rework, confusion) are ignored.

**Validation pilot design**  
I propose a **threephase rollout** using a championchallenger approach:

1. **Phase 1 – Historical shadow run:** Replay one month of historical event logs (if available) with the three policies in simulation, using actual arrival times and case attributes. Compare simulated SLA attainment against actuals to calibrate servicetime distributions and handover parameters. Ensure the model accurately predicts existing specialisation performance (Policy A).  
2. **Phase 2 – Controlled live test:** For one week, implement Policy C on a subset of cases (e.g., 20% randomly, but all P1 cases must remain under current policy for safety). Use a switchback design: on odd hours, route cases via Policy C; even hours use existing policy. Log all assignment decisions and outcomes. Monitor P1 SLA realtime with an alert threshold at 85% (higher than final target to trigger early stop). Compare mean delay and fairness without disturbing critical work.  
3. **Phase 3 – Full rollout with fallback:** If Phase2 demonstrates P1 SLA  90% for at least 4 out of 5 working days, enable Policy C for all cases. Keep the fallback P1only mode on standby, triggered by a sustained P1 queue above 2 for 15min. Run for two weeks, then compare against Phase1 shadow run and previous month performance.  

During all phases, continuously mine the event log with PM4Py to detect drift in service times (complextail day), handover burden, and bottleneck shifts. This design protects P1 cases throughout, limits exposure to an untested policy, and provides clean counterfactual evidence.
