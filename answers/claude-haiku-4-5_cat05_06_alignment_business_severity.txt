# Insurance Claim Payment Process Alignment Analysis

---

## 1. Materiality Framework

### Definition of Severity Dimensions

**Control Objective:** Prevent unauthorized, fraudulent, or policy-violating payments while maintaining compliant notification and audit integrity.

**Materiality Thresholds:**
- **Amount exposure**: EUR 5,000–50,000 (moderate); >EUR 50,000 (high)
- **Policy-overlay breach severity**:
  - P3 (payment before approval): *Critical* — irreversible control failure, regulatory/fiduciary violation
  - P2 (HIGH-risk or >EUR 50,000 without fraud/manual screens): *High* — policy violation with financial/reputational exposure
  - P1 (auto-approval when ineligible): *High* — circumvention of fraud/change-of-beneficiary controls
  - P4 (notification >24h or missing): *Medium–High* — customer harm, regulatory non-compliance (varies by jurisdiction)

**Reversibility:**
- Payment executed and accepted by bank: *irreversible*  critical
- Approval absent but payment pending: *reversible* if recalled before settlement
- Notification delayed or missing: *reversible* if sent within grace period

**Timing Evidence Quality:**
- Log timestamps with millisecond precision: *high confidence*
- Manual approver's verbal statement, no documented fraud check: *low confidence*
- External adjuster document post-dated to case: *medium confidence*, depends on document-to-case linkage stability
- Missing event in core log but present in external system (CRM, portal): *medium confidence*, requires cross-system validation

**Customer/Regulatory Harm:**
- Payment to HIGH-risk claim without fraud screen: reputational, compliance, anti-money-laundering (AML) exposure
- Delayed notification (>24h): regulatory penalty (GDPR-adjacent, insurance directives in EU); customer frustration
- Denied/withdrawn claims misaligned to payable model: scope misclassification, not necessarily operational harm

**Recurrence Signal:**
- Single occurrence in month: isolated incident, investigate root cause
- 4+ cases in 12 cases: systemic pattern, requires control redesign or model fix

**Model Scope Uncertainty (P6):**
- Denied and withdrawn claims fall outside model M0 design intent
- Alignment cost on out-of-scope cases inflates aggregate cost without indicating control failure
- Treat denied/withdrawn separately; flag as scope mismatch, not operational risk

### Confidence vs. Severity

| Dimension | Confidence (certainty of diagnosis) | Severity (business impact) |
|-----------|-------------------------------------|---------------------------|
| Definition | Do we have reliable evidence that the described deviation occurred? | How much harm (financial, compliance, reputational, customer) results from the deviation? |
| Low confidence | Manual statement, missing document link, unclear timestamp | Isolated, reversible, EUR 800 claim |
| High confidence | Synchronous log+model match, bank settlement timestamp | Irreversible, >EUR 50,000, HIGH-risk, policy breach |
| Examples | CL-602 verbal fraud check; CL-608 mutable CRM link | CL-604 payment before approval; CL-610 bank change + auto-approve |

**Key insight:** Low-confidence findings must not drive high-severity remediation; high-severity findings with moderate confidence warrant immediate investigation *and* preventive control.

## 3. Repeated Deviation Patterns

### Pattern 1: **Data-Conditional Policy Failures (Auto-Approve Violations of P1)**

**Cases:** CL-610

**Frequency & Scale:**
- CL-610: 1 confirmed in sample
- Pattern evidence: "Four cases have a fully synchronous Auto Approve path despite violating P1 or P2"
- **Extrapolation:** ~4/12 cases = ~33% of sampled claims

**Business Risk:**
- **Financial**: Unauthorized payment to HIGH-risk or recently-changed beneficiary accounts; potential fraud, money laundering, or account-takeover scenarios
- **Regulatory**: AML (FATF/EU 5th Directive), anti-fraud compliance, know-your-customer (KYC) violations
- **Reputational**: If fraudulent claim pays, insurer faces recovery action and regulatory sanction

**Root Cause Hypothesis:**
1. Auto-approval engine does not query or check beneficiary-bank-change timestamp before approving
2. Data freshness issue: beneficiary table not synced with approval module
3. Time-window logic bug: system checks 7-day window from claim *date*, not from *payment execution time*
4. Deliberate override by operational user circumventing control (low likelihood)

**Confidence:** High — CL-610 timestamps and P1 policy are explicit.

**Owner:** Risk & Compliance + IT (Approval Engine Development)

**Preventive Control:**
- Before Auto Approve, query beneficiary table and enforce 7-day-no-change condition in code
- Flag AUTO_APPROVE_INELIGIBLE in workflow if condition fails
- Implement real-time beneficiary monitoring / alert on change

### Pattern 2: **Fraud Screen Evidence Gap (Missing or Unverified Fraud Checks)**

**Cases:** CL-602, and implied by CL-604 (MEDIUM risk claim with no Fraud Screen logged)

**Frequency & Scale:**
- CL-602: EUR 480k, HIGH risk, beneficiary change — no Fraud Screen evidence, verbal claim only
- CL-604: EUR 90k, MEDIUM risk — no Fraud Screen logged (may not be mandatory for MEDIUM, but combined with P3 violation, it is a control gap)
- Pattern evidence: "Fraud Screen may have been informal/verbal, not logged"

**Business Risk:**
- **Financial**: High-value fraudulent claims (EUR 480k, EUR 90k) bypass automated and manual fraud checks
- **Regulatory**: AML, sanctions screening, fraud-prevention documentation required
- **Reputational**: Insurer reputation damaged if fraud is discovered post-payment

**Root Cause Hypothesis:**
1. Fraud screen is performed informally (phone call, spreadsheet) and not logged in core system
2. Fraud-screen system is external (third-party vendor) and does not integrate with case log
3. Approver assumes fraud check was done earlier and does not verify
4. Process design allows verbal approval without documented evidence trail

**Confidence:** Moderate — CL-602 approver's statement is unverified; no external fraud-check audit trail was retrieved.

**Owner:** Fraud & AML team + Process Design

**Detective Control:**
- Mandatory Fraud Screen log entry for claims >EUR 50k or HIGH risk
- Automated integration with third-party fraud-check provider (e.g., Lexis Nexis, Equifax, sanctions databases)
- Approval cannot proceed without Fraud Screen log evidence

### Pattern 3: **Notification Delivery Evidence Gap (External System, Weak Linkage)**

**Cases:** CL-603 (duplicate), CL-608 (external CRM, mutable link)

**Frequency & Scale:**
- CL-603: "74 cases in month have `L(Notify Claimant)` immediately after sync notification with same message ID; all attributed to one retrying connector"
- CL-608: EUR 250k claim, notification only in CRM with mutable text-field linkage
- **Extrapolation:** ~74 + CL-608 = ~75/month notifications have evidence-linkage or retry issues

**Business Risk:**
- **Regulatory**: P4 requires notification within 24h; if evidence is weak, compliance is unverifiable
- **Customer**: Delayed or undelivered notifications harm claimant experience
- **Audit**: Weak evidence (mutable link) fails in regulatory audit or litigation

**Root Cause Hypothesis:**
1. Notification system is asynchronous/multi-system (core log + portal + CRM); no unified event logging
2. Retry logic in transport layer generates duplicate log events
3. CRM linkage is ad-hoc (text field, no foreign key or cryptographic binding)

**Confidence:** High for CL-603 (connector issue explicitly identified); Moderate for CL-608 (mutable link structure).

**Owner:** Notification Operations + IT (Integration/CRM)

**Detective/Corrective Control:**
- Implement idempotent notification logging: suppress duplicate messages with same ID
- Enforce immutable case-notification linkage in CRM (foreign key, hash-based identifier)
- Centralize notification audit trail (core system of record for all notifications, regardless of delivery channel)

### Pattern 4: **External Assessment Evidence Gap (Logging Mismatch)**

**Cases:** CL-606, and pattern evidence: "Nine high-value cases have `M(Assess Loss)` and external-adjuster document; two lack stable document-to-case identifier"

**Frequency & Scale:**
- CL-606: EUR 75k, HIGH risk, external adjuster assessment at 10:05, no core-log Assess Loss event
- Pattern: 9 cases with external adjuster docs; 2 have unstable identifiers
- **Extrapolation:** ~2/9 = ~22% of external-adjuster cases have weak linkage

**Business Risk:**
- **Audit**: Assessment evidence exists but is not linked to case; auditor cannot verify compliance
- **Legal**: If claim is disputed, evidence admissibility depends on document-to-case linkage integrity

**Root Cause Hypothesis:**
1. External adjuster system is separate platform (not integrated); assessment report generated independently
2. Case-management system does not auto-ingest adjuster reports; no ETL pipeline
3. Manual linking (user types case ID in adjuster report or vice versa) is error-prone
4. Adjuster document ID is different from case ID; linking is text-based or unreliable

**Confidence:** Moderate–High (CL-606 shows missing core-log event; external evidence likely exists but is not formally linked).

**Owner:** Claims Management + External Adjuster Vendor

**Preventive Control:**
- Implement automated import of external adjuster reports into case log (web service, EDI, or file drop)
- Enforce immutable, unique document-to-case binding (UUID or cryptographic hash)
- Log Assess Loss event in core system when external assessment is received and linked

### Pattern 5: **Payment-Before-Approval Sequencing Violation (P3 Critical)**

**Cases:** CL-604

**Frequency & Scale:**
- CL-604: EUR 90k, payment at 10:03, approval at 10:20 (17-minute gap, payment before approval)
- Pattern evidence: "Payment before the applicable approval is a severe control failure even if the model alignment can repair it cheaply"
- **Extrapolation:** 1/12 sample; unknown frequency in broader population (likely rare but high-impact)

**Business Risk:**
- **Financial**: Payment executed without authorization, potential fraud or operational error
- **Regulatory**: Fiduciary duty and internal-control violations; audit finding
- **Reversibility**: If bank settlement is final, payment cannot be recalled; funds are at risk

**Root Cause Hypothesis:**
1. Payment system processes transactions asynchronously; approval workflow is separate and slower
2. Approval task was drafted/initiated before payment but logged after payment execution
3. Timestamp synchronization issue between systems (payment and approval subsystems)
4. Manual workaround: user initiated payment pending approval approval was entered post-hoc to reconcile

**Confidence:** High — timestamps are explicit; bank accepted payment (irreversible).

**Owner:** Payments Team + Workflow Orchestration

**Immediate Action:**
- Attempt transaction reversal if not yet settled (call counterparty bank)
- Forensic review of approval timestamp (was it truly recorded at 10:20, or is the timestamp incorrect?)
- Implement blocking control: Payment activity should fail if Fraud Screen + Manual Approve not yet completed and timestamped

### Pattern 6: **Model Scope Mismatch (Out-of-Scope Workflows)**

**Cases:** CL-607 (Deny Claim), CL-612 (Withdraw Claim)

**Frequency & Scale:**
- CL-607, CL-612: 2/12 sample with Deny/Withdraw
- Pattern evidence: "Denied and withdrawn cases account for most alignments with raw cost >= 4"
- **Extrapolation:** Out-of-scope cases contribute disproportionately to alignment cost; likely 10–20% of population if denials/withdrawals are handled in the same system

**Business Risk:**
- **None**: Denied and withdrawn claims do not involve unauthorized payments; they are valid workflow outcomes
- **Assessment Contamination**: If out-of-scope cases are included in operational-risk metrics, they inflate aggregate cost and distract from real control violations

**Root Cause Hypothesis:**
- Process model M0 was designed for payable claims; denial and withdrawal workflows are valid insurance processes but are not modeled
- Disagreement on scope (process owner vs. model owner)

**Confidence:** High — denied and withdrawn claims are explicitly documented.

**Owner:** Process Modeling / Requirements

**Corrective Action:**
- Define scope explicitly: M0 is for payable claims only (Assess Loss  Approval  Pay  Notify)
- Create separate models for denial workflow and withdrawal workflow
- Filter out-of-scope cases in conformance analysis

## 4. Causal Hypotheses and Evidence Tests

### Hypothesis 1: CL-610 — Auto-Approve Logic Does Not Query Beneficiary-Bank-Change Table

**Competing Hypotheses:**
1. **H1a (Control Bypass):** Auto-Approve engine ignores beneficiary-change data; developers did not implement P1 logic
2. **H1b (Data Freshness):** Beneficiary-change table is not synchronized with approval module in real-time; approval engine queries stale data
3. **H1c (Time-Window Bug):** Logic checks 7-day window from claim *date*, not from *payment execution time*
4. **H1d (Operational Override):** Approval was escalated to auto-approval by manual override after initial eligibility check

**Evidence Discrimination Tests:**
- **Test 1a:** Retrieve approval engine source code and search for `beneficiary_change` OR `payment_change` checks. If not found, H1a is likely. If found, verify logic is correct (7-day window from payment time, not claim date).
- **Test 1b:** Compare timestamps of beneficiary-change table refresh vs. approval execution (10:02). If refresh is >1 hour before approval, H1b is possible.
- **Test 1c:** Run a test case with known beneficiary change; observe which approval path is taken. If auto-approval is triggered despite change within 7 days, H1c or H1a is confirmed.
- **Test 1d:** Check approval task metadata (created, modified, assigned, completed by, comments). If comments show manual escalation (e.g., "Risk OK, auto-approve"), H1d is indicated.

**Expected Outcome:** H1a or H1c most likely (development/design gap); H1b less likely (data freshness issues are rare in modern systems); H1d unlikely (would require visible log evidence of override).

---

### Hypothesis 2: CL-602 — Fraud Screen Performed Informally or by External Vendor, Not Logged in Core

**Competing Hypotheses:**
1. **H2a (Unlogged Informal Process):** Fraud check was done verbally or on paper; case handler did not log the activity in core system
2. **H2b (External Vendor Gap):** Third-party fraud-check system (e.g., SEON, Equifax, sanctions database) performed the check; vendor does not send results back to core log

## 6. Why Alignment Cost Is Not Business Risk

Alignment cost, as measured by edit distance under a uniform cost function (cost 1 per visible log/model move), is decoupled from business risk in at least seven dimensions:

### 6.1 **Data-Aware Policy Violations with Zero Alignment Cost**

**Case CL-610: Auto-Approve with Beneficiary-Bank Change within 7 Days**

- **Alignment cost: 0** (fully synchronous, Auto Approve path is in the process tree)
- **Business risk: High (4/5)** (AML/fraud exposure, P1 violation)
- **Reason**: Process tree permits Auto Approve, so the model-log alignment is perfect. But P1 is a *data-aware policy*: "no beneficiary-bank change occurred during previous 7 days." The process tree does not encode data conditions; it allows Auto Approve unconditionally. The approval engine failed to check the beneficiary-change table, violating the policy. Yet the alignment cost is zero because the process-tree transition occurred.
- **Implication**: Raw alignment cost is blind to data-conditional policies. A conformance algorithm that respects the alignment may assign zero cost to a claim that violates P1 in practice.

---

### 6.2 **Policy Violation with Reversible Sequencing, Masqueraded by Low Cost**

**Case CL-604: Payment Before Approval (17-minute gap)**

- **Alignment cost: 3** (two Pay Claim moves, one missing Fraud Screen)
- **Business risk: Critical (5/5)** (irreversible control violation, P3 breach)
- **Reason**: The cost of 3 is distributed across multiple moves:
  - `L(Pay Claim, c=1)` @ 10:03 (log event, model does not expect it yet)
  - `M(Fraud Screen, c=1)` (model expects it, log has no event)
  - `M(Pay Claim, c=1)` @ 10:20 (model expects it after approval, log has it before)
  
  The total cost of 3 might seem manageable in a portfolio of 12 cases, but the *order* of the visible moves is the critical problem: **payment before approval is irreversible and unrecoverable.** The cost function does not weight sequencing violations (edit distance does not distinguish "payment before approval" from "approval missing one detail"). A high-consequence irreversible violation is treated the same as a cosmetic label mismatch if the edit distance is similar.

---

### 6.3 **Hidden Moves Are Technically Free but May Mask Missing Controls**

**Case CL-605: Silent Transition Before Auto Approve**

- **Alignment cost: 0** (tau hidden move is free)
- **Business risk: 1/5** (harmless; technical fit)
- **Reason**: The Petri-net conversion introduces a hidden transition (tau) for internal routing logic. This is legitimate in formal models: a hidden transition allows the model to match the log without consuming a log event. But if the hidden transition is intended to represent a control step (e.g., an internal fraud check) that is not logged, then the cost-0 fit is misleading. The claim passes through the hidden transition into Auto Approve, but the control is not visible or auditable.
- **Implication**: Zero-cost hidden moves are technically correct but can obscure missing audit trails. A compliance auditor sees Auto Approve outcome but has no visibility into the intermediate tau step.

---

### 6.4 **Out-of-Scope Cases Inflate Aggregate Cost Without Indicating Control Risk**

**Cases CL-607 (Deny Claim) and CL-612 (Withdraw Claim)**

- **Alignment costs: 4, 4**
- **Business risk: 1/5** each (no payment, no control failure)
- **Reason**: The process model M0 was designed for payable claims. Denial and withdrawal are valid claim-lifecycle endpoints but are not in M0. When a claim is denied, the log has `Deny Claim` event, but the model expects `Assess Loss  Approve  Pay`. The alignment cost is high (4 per case) because multiple model steps are missing or log steps are unexpected.
  
  Yet there is **zero control risk**: no payment occurred, no policy was violated. The claim was correctly denied. The high alignment cost reflects a *model scope issue*, not an operational deviation.

- **Implication**: If the portfolio includes 20% denial/withdrawal cases, the aggregate alignment cost is inflated by ~20%. Portfolio managers may mistakenly prioritize "fixing" denial/withdrawal workflows based on high cost, when in fact they should exclude out-of-scope cases or build separate models.

---

### 6.5 **Missing-But-External Evidence Penalized as Model Mismatch**

**Case CL-606: External Adjuster Assessment Not in Core Log**

- **Alignment cost: 1** (missing Assess Loss in core log)
- **Business risk: 2–3/5** (moderate; substantive assessment exists externally)
- **Reason**: The external adjuster performed loss assessment and signed a report at 10:05. The core case-management system has no Assess Loss log event, so the alignment requires `M(Assess Loss, c=1)` — model expects it, log does not have it. This costs 1.
  
  But the business control is satisfied: EUR 75k and HIGH risk requires Assess Loss + Fraud Screen + Manual Approve, and all three occurred (assessment via external adjuster, fraud screen logged, manual approval logged). The evidence exists; it is just not in the core log.

- **Implication**: Alignment cost penalizes data-integration gaps, not control failures. A more sophisticated conformance algorithm would accept external evidence if a stable link exists. The cost-1 penalty is an artifact of system architecture (external adjuster not integrated), not a process deviation.

---

### 6.6 **Duplicate/Retry Telemetry Inflates Cost Without Adding Risk**

**Case CL-603: Duplicate Notify Claimant Events (Same Message ID)**

- **Alignment cost: 1**
- **Business risk: 1/5** (duplicate is harmless; first notification was delivered)
- **Reason**: The claimant received notification once; the log shows two Notify Claimant events due to transport-layer retry. The alignment cost is 1 for the second log event (unexpected in model, which expects one notification). Across 74 cases in the month, this is 74 units of alignment cost.
  
  But the business outcome is identical: claimant was notified once within 24 hours. P4 is satisfied. The cost reflects a *logging/telemetry artifact*, not a business deviation.

- **Implication**: Aggregate alignment cost across the portfolio includes 74 units of cost-1 penalty for idempotent retries, which should be recognized as technical noise and filtered out. If filtering is applied, portfolio cost drops ~20% with zero reduction in actual risk.

---

### 6.7 **Event-Label Mismatch Treated as Control Gap, Not Data-Integration Mismatch**

**Case CL-611: Assess Damage vs. Assess Loss**

- **Alignment cost: 2** (one log event `Assess Damage`, one model mismatch `M(Assess Loss)`)
- **Business risk: 1–2/5** (label only; substantive assessment is correct)
- **Reason**: The core system logged activity as `Assess Damage` (internal terminology). The process model uses `Assess Loss` (standardized terminology). Both refer to the same business activity. The alignment cost is 2 (one log/model mismatch + one model mismatch), but the control is correct: EUR 62k + HIGH risk received Fraud Screen + Manual Approve before payment.
  
  The cost reflects an ETL/data-mapping gap, not a process deviation.

- **Implication**: If the data-mapping table is fixed retroactively, the cost should drop to 0. Alignment cost is sensitive to naming conventions, which are downstream from control design. A governance or terminology change can reduce alignment cost without any change in control effectiveness.

---

### 6.8 **Cost-Function Design: Uniform Unit Cost Obscures Magnitude Differences**

**Comparison of CL-602 vs. CL-603:**

| Case | Amount | Risk | Cost | Policy Breach | Business Impact |
|---|---|---|---|---|---|
| CL-602 | EUR 480k | HIGH | 1 (missing Fraud Screen) | P2 (unverified fraud check) | Irreversible payment, unverifiable approval |
| CL-603 | EUR 3.2k | LOW | 1 (duplicate notify) | None | Duplicate log event only |

- **Reason**: Both have alignment cost 1. But CL-602 is a critical fraud/AML exposure at EUR 480k, while CL-603 is a harmless duplicate. The uniform cost function treats them equally. A business-aware cost function would weight CL-602 as cost 10–100 (amount + risk + irreversibility) and CL-603 as cost 0.1 (idempotent, harmless).

---

### 6.9 **Reversibility Is Not Captured in Alignment Cost**

**CL-604 (Payment Before Approval) vs. CL-609 (Compliant Auto-Approval):**

| Case | Amount | Sequencing | Reversibility | Alignment Cost | Business Severity |
|---|---|---|---|---|---|
| CL-604 | EUR 90k | Payment @ 10:03, approval @ 10:20 | **Irreversible** (bank accepted) | 3 | Critical (5) |
| CL-609 | EUR 18k | All correct order | N/A | 0 | Compliant (1) |

- **Reason**: CL-604 has cost 3 but critical severity because the payment is irreversible (bank settlement). CL-609 has cost 0 and low severity. But a case with a *reversible* out-of-order activity (e.g., approval recorded after payment but payment is pending/not settled) would also have cost 3 but lower severity because it can be corrected.

  Alignment cost does not distinguish irreversible (settled payment) from reversible (pending approval/payment).

---

### Summary: Why Raw Cost Fails

| Dimension | Example | Cost Reflects | Business Risk Reflects | Decoupling |
|---|---|---|---|---|
| **Data-aware policies** | CL-610 (beneficiary change) | Model-tree conformance | P1 data conditions | Zero cost, high risk |
| **Sequencing/irreversibility** | CL-604 (payment before approval) | Edit distance | Control failure + settlement finality | Cost 3 masks critical breach |
| **Out-of-scope workflows** | CL-607, CL-612 (deny/withdraw) | Model coverage gap | Non-issue (no payment) | Cost 4, risk 1 |
| **External evidence** | CL-606 (adjuster report) | Log-to-model alignment | Data-integration gap, control is sound | Cost 1, risk 2 |
| **Idempotent duplicates** | CL-603, 74 cases (retry) | Log telemetry artifacts | Harmless technical noise | Cost 74/month, risk 0 |
| **Label mismatch** | CL-611 (Assess Damage) | ETL/naming convention | Control is correct | Cost 2, risk 1 |
| **Hidden moves** | CL-605 (tau transition) | Technical fitting | Audit-trail invisibility | Cost 0, potential risk if undocumented |
| **Uniform cost function** | CL-602 (EUR 480k) vs. CL-603 (EUR 3.2k) | Same cost per move | Magnitude-dependent exposure | Cost 1 for both, severity 5 vs. 1 |

## 7. PM4Py Reproduction and Aggregation Code

```python
import pandas as pd
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.petri_net.obj import PetriNet, Marking
from pm4py.objects.petri_net import semantics
from pm4py.objects.log.obj import EventLog, Event
from datetime import datetime, timedelta
import io

# ============================================================================
# 1. Parse Process Tree from Supplied Notation
# ============================================================================

# The normative process tree:
# -> ( 'Register Claim', 'Validate Coverage', 'Assess Loss', 
#      X ( -> ( 'Fraud Screen', 'Manual Approve' ), 'Auto Approve' ), 
#      'Pay Claim', 'Notify Claimant' )

# Build the tree programmatically (note: pm4py parse_process_tree requires proper string format)
# We construct it manually here for clarity.

def build_normative_tree():
    """
    Build the process tree for the normative control-flow model.
    Uses nested operators: 
      -> (sequence) : left XOR right (explicit ordering)
      X (XOR) : exclusive choice
    """
    # Create leaf nodes
    register = ProcessTree(operator=None, label="Register Claim")
    validate = ProcessTree(operator=None, label="Validate Coverage")
    assess = ProcessTree(operator=None, label="Assess Loss")
    fraud_screen = ProcessTree(operator=None, label="Fraud Screen")
    manual_approve = ProcessTree(operator=None, label="Manual Approve")
    auto_approve = ProcessTree(operator=None, label="Auto Approve")
    pay = ProcessTree(operator=None, label="Pay Claim")
    notify = ProcessTree(operator=None, label="Notify Claimant")
    
    # Build internal nodes
    # fraud_then_approve = -> (Fraud Screen, Manual Approve)
    fraud_then_approve = ProcessTree(
        operator=Operator.SEQUENCE,
        children=[fraud_screen, manual_approve]
    )
    
    # approval_choice = X ( -> (Fraud Screen, Manual Approve), Auto Approve)
    approval_choice = ProcessTree(
        operator=Operator.XOR,
        children=[fraud_then_approve, auto_approve]
    )
    
    # main_sequence = -> (Register, Validate, Assess, approval_choice, Pay, Notify)
    main_sequence = ProcessTree(
        operator=Operator.SEQUENCE,
        children=[register, validate, assess, approval_choice, pay, notify]
    )
    
    return main_sequence

tree = build_normative_tree()
print("Process Tree built successfully.")
print("Tree structure (via str): ", str(tree))

def create_event_log_from_dict(case_dict):
    """Create pm4py EventLog from case dictionary."""
    log = EventLog()
    base_time = datetime(2024, 1, 15, 10, 0, 0)
    
    for case_id, case_info in case_dict.items():
        events = case_info['events']
        for i, event_name in enumerate(events):
            evt = Event()
            evt['case:concept:name'] = case_id
            evt['concept:name'] = event_name
            evt['time:timestamp'] = base_time + timedelta(minutes=i)
            evt['lifecycle:transition'] = 'complete'
            log.append(evt)
    
    return log
```
