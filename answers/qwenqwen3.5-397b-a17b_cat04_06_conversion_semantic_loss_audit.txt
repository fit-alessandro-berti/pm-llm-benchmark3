# 6. Visual-Semantics Review

Even if the underlying Petri net is behaviorally acceptable, the BPMN rendering introduces specific risks of misinterpretation:

1.  **Parallel vs. Exclusive Gateways**: The BPMN converter might infer a Parallel Gateway for the `Assess Risk` / `Prepare Evidence` split. However, if the layout engine positions them sequentially, a stakeholder might assume a required order. Annotations should explicitly label the gateway as "Parallel (AND)".
2.  **Silent Routing Nodes**: The `Skip Legal` silent transition in POWL becomes an invisible path in BPMN. In some renderers, this looks like a direct sequence flow, while the `Legal Review` path looks like a detour. This might suggest `Legal Review` is the "normal" path and skipping is exceptional, whereas POWL treats them as equal XOR branches. Documentation must state that the branch is optional with no default preference.
3.  **Loop Visualization**: BPMN standardizes loops using a marker on the activity or a loop task. If the converter expands the loop into a structured XOR-join-split pattern, the "DO-WHITE" semantics (execute at least once) might be visually confused with a "WHILE-DO" (check first) if the gateway placement is ambiguous.
4.  **Layout Ordering**: Graph layout algorithms often minimize edge crossings, which can reorder concurrent branches vertically. A viewer might interpret the top branch as "first". A note on the diagram should clarify: "Vertical position does not imply temporal order."
5.  **Synchronization Visibility**: The join before `Release Change` requires both branches. In BPMN, this is a Parallel Join. If the converter simplifies this to a simple merge (due to tool limitations), it implies `Release` can happen after *either* branch. The visual style of the gateway (plus sign vs. empty diamond) must be audited.

# 7. Rejection Criteria

A conversion result must be rejected or quarantined if any of the following six conditions are met:

1.  **Unsoundness**: The resulting Petri net fails `pm4py.check_soundness` (e.g., deadlocks or improper completion).
2.  **Loss of Synchronization**: The `Release Change` activity becomes enabled after only *one* of the predecessor branches (Legal or Verification) completes, violating **JOIN-01**.
3.  **Collapse of Optionality**: The `Legal Review` becomes mandatory (no silent path exists to `Release`), violating **OPT-01**.
4.  **Loop Entry Violation**: The model allows `Release Change` without at least one execution of `Configure Trial`, violating **LOOP-03**.
5.  **Final Marking Mismatch**: A valid trace does not end in the exact final marking defined by `Archive Change` (e.g., tokens remain in the verification loop), violating **FIN-01**.
6.  **Interleaving Restriction**: The model forces `Assess Risk` to strictly precede `Prepare Evidence` (or vice versa), removing the concurrency defined in **CONC-01**.

# 8. Canonical Representation Recommendation

**Authoritative Representation**: **POWL**.
The POWL model is the source of truth. It explicitly defines the partial order, silent transitions, and loop operators without the ambiguity of graphical layout or block-structure constraints.

**Derivative Artifacts**:
- **Accepting Petri Net**: This is the primary semantic carrier. It should be stored alongside the POWL for validation purposes but is considered derivative because it is a transformation of the POWL logic.
- **BPMN Diagram**: This is strictly for stakeholder visualization. It is the least authoritative and must always be accompanied by validation evidence.

**Validation Evidence**:
Every derivative BPMN artifact must be accompanied by:
1.  The **Soundness Report** (`check_soundness` output).
2.  The **Footprint Comparison** log showing equivalence with the source Petri net.
3.  A **Disclaimer** stating that layout does not imply order.

**Process Tree Intermediate**:
A process-tree intermediate should **not be allowed** for this specific model as a standard pipeline. As demonstrated in Pipeline 2, the concurrency and synchronization pattern (Assess/Prepare merging into Verification/Legal) is likely not block-structured. Forcing it into a tree would require approximations that violate semantic invariants (e.g., introducing artificial dependencies).

**Avoiding Round-Trip Drift**:
Future edits should be made directly to the POWL source. Editing the BPMN and converting back to POWL is prohibited, as BPMN lacks the expressive power to capture the `StrictPartialOrder` semantics precisely, leading to drift.

# 9. Residual Uncertainty

Even if every test passes, the following claims cannot be established:

1.  **Performance Equivalence**: The validation confirms behavioral equivalence (traces), but not performance characteristics (e.g., token game efficiency, state space explosion potential in the converted net).
2.  **Data Flow Semantics**: POWL and the Petri net control flow do not capture data dependencies (e.g., does `Inspect Trial` require data from `Prepare Evidence`?). This is outside the scope of the conversion validation.
3.  **Organizational Assignment**: The conversion preserves control flow, but any implicit organizational rules (e.g., "Legal Review must be done by a different actor than Assess Risk") are not modeled in POWL and thus cannot be validated in the BPMN output.
