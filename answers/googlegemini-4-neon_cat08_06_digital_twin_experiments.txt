# 1. Model scope and state variables

## Digital twin architecture and boundary
To evaluate interventions under non-stationary demand, calendar constraints, and cross-case interactions, the digital twin should be designed as a **hybrid Discrete-Event Simulation (DES) with an explicit entity-interaction layer**, decoupled from but calibrated by a **PM4Py process-mining pipeline**. Rather than a closed-loop historical replay, the twin operates in two synchronized modes:
1. **Policy-evaluation mode**: Evaluates interventions (D1–D10) over multi-year seasonal horizons using calibrated stochastic generators.
2. **Operational shadow mode**: Initializes directly from the municipality’s current Work-In-Progress (WIP) snapshot to forecast short-to-medium-term backlogs (3–6 months).

- **Inside the model boundary**: Portal intake (including pre-submission screening friction for D1 and appointment slotting for D7), completeness checks and missing-document loops, parallel technical reviews (Planning, Fire-safety, Environmental), Public-notice periods with latent neighborhood objections, district-aware inspection scheduling and field travel, decision drafting with synchronization joins, Legal checks (plus parallel legal pre-checks for D5), permit issuance/rejection, and post-review/inspection/legal/appeal rework loops. External actors (applicants, environmental consultants, objecting neighbors) are represented as explicit delay/shock processes separate from municipal labor.
- **Outside the model boundary**: Macroeconomic housing cycles (treated as exogenous demand-multiplier scenarios), upstream architectural design prior to portal interaction, post-permit construction monitoring, judicial litigation beyond administrative appeals, and rare emergency decisions removed from the log (excluded from nominal calibration, though testable as an exogenous capacity-siphon stress scenario).

## Level of detail and entities
The simulation operates at the **individual application (case) and individual resource-unit level**, tracking concurrent activity tokens per case (so parallel reviews and D5 legal pre-checks synchronize cleanly before `Decision drafting`).

- **Case (Permit Application)**:
  - Static attributes: `case_id`, `case_type` (`Simple renovation`, `New residential`, `Commercial`, `Complex variance`), `district` (`D1`–`Dn`), `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, `prior_violations_flag`, `parcel_cluster_id`.
  - Latent attributes: `area_exceeds_threshold`, `district_env_sensitive`, `missing_doc_propensity`, `objection_triggered`.
  - Dynamic attributes: `submission_ts`, `active_tokens` (set of enabled/in-progress stages), `completed_reviews` (join tracker), `rework_counts` (dict by stage: completeness, planning, inspection, legal, appeal), `sla_target_days`, `urgent_flag`, `inspection_batch_id`.
- **Architect entity**: `architect_id`, `volume_tier` (top-20 high-volume vs. standard), `burst_cluster_rate`, `doc_completeness_skill`, `active_pending_requests` (allows modeling response contention when one architect receives multiple document requests simultaneously).
- **District / Neighborhood cluster entity**: `district_id`, `inspection_travel_profile` (elevated for `D3`, `D5`), `env_sensitivity_rate`, `active_objection_wave` (shared shock state affecting overlapping public-notice cases in the same cluster).
- **Inspection batch entity**: `batch_id`, `district_id`, `architect_id` (optional), `member_case_ids`, `created_ts`, `max_wait_deadline`, `scheduled_date`, `estimated_route_travel_time`.

## System state variables, resources, queues, and calendars
- **Global state variables**: Simulation clock $t$, calendar context (`month`, `day_of_week`, `is_holiday`, `is_council_week`, `is_peak_season`), WIP counts by `(stage, case_type, district)`, queue lengths and oldest-case age per queue, and active neighborhood objection flags.
- **Resources, queues, and calendars**:
  - **Clerks (5 FTE)**: Mon–Fri 08:00–16:00; 1 FTE diverted to portal support on Mondays (leaving 4 FTE for `Completeness check` / `Request missing documents` on peak intake days). Queue discipline: FIFO.
  - **Planners (8 FTE)**: Mon–Fri 09:00–17:00; 2 FTE restricted exclusively to `Simple renovation`, 6 FTE general-purpose (handling `Planning review`, `Decision drafting`, and planning rework). Under D6, 1 general FTE/day is ring-fenced for aging cases exceeding an age threshold.
  - **Fire reviewers (2 FTE eq.)**: Tue–Thu only; dedicated FIFO/priority queue for `Fire-safety review`.
  - **Environmental reviewers (3 FTE)**: Mon–Fri; 40% of capacity reserved for non-permit duties (modeled via scheduled background capacity blocks or competing non-permit arrivals). Under D8, split into fast-track triage and full-review queues.
  - **Inspectors (4 FTE; +1 temp FTE in peak months under D4)**: Field visits Tue–Fri; travel time depends on `district`. Under D3, cases enter a district holding buffer until either a target batch size is reached or a maximum wait-time cap expires.
  - **Legal officers (2 FTE)**: Mon–Fri, unavailable during council-meeting weeks except for `urgent_flag=True` cases. Under D5, accepts early pre-check tokens for `Commercial` and `Complex variance`.
  - **System tasks**: Unlimited capacity (`Submit application`, `Receive missing documents` intake, `Issue permit`, timer triggers).
  - **External infinite-server delay pools**: Applicant missing-document response, environmental consultant report turnaround, and Public-notice / objection resolution periods (run on wall-clock calendar days, not municipal shift hours, except where council hearings gate objection closure).

## Cross-case dependencies
A simple independent-case DES would miss key variance drivers in this municipality. The twin explicitly models four cross-case coupling mechanisms:
1. **Architect submission bursts and correlated quality**: Top-20 architects (31% of volume) submit clustered applications within the same week, often in the same district. Applications from the same architect share correlated document-completeness quality and can compete for the architect’s own turnaround bandwidth when multiple missing-document requests occur concurrently.
2. **Correlated neighborhood objections**: Objection shocks occur at the *parcel-cluster / neighborhood* level rather than purely independently per case. When an objection wave activates in a neighborhood, all overlapping `Public-notice period` cases in that cluster experience correlated duration extensions and elevated downstream legal/appeal rework risk.
3. **Geographic and architect-based inspection batching**: Bundling cases from the same district (and optionally same architect) reduces marginal inspector travel time—critical in `D3` and `D5`—but introduces a synchronization waiting delay for earlier-arriving cases in the bundle.
4. **Resource-pool and specialization spillovers**: Shared general planners, environmental reviewers, and legal officers create cross-type congestion (e.g., Commercial/Complex rework consuming general planner hours delays New residential `Decision drafting`), mitigated partially by dedicated Simple-renovation planners.

# 2. Parameter-estimation plan

## Role of PM4Py in log and model handling
PM4Py serves as the standardized ingestion, structural discovery, and conformance backbone, separated cleanly from the simulation engine:
1. **Log standardization**: Load raw CSV/Parquet extracts via `pandas` and standardize with `pm4py.format_dataframe` (`case:concept:name`, `concept:name`, `time:timestamp`).
2. **Control-flow discovery and audit**: Extract variant distributions (`pm4py.get_variants`), frequency and performance Directly-Follows Graphs (`pm4py.discover_dfg`, `pm4py.discover_performance_dfg`), and an empirical process tree via Inductive Miner (`pm4py.discover_process_tree_inductive`). Compare this empirical model against the provided simplified nominal tree (parsed via `pm4py.parse_process_tree`) using conformance checking (alignments / token-based replay on Petri nets via `pm4py.convert_to_petri_net`) to surface structural omissions—specifically undocumented rework loops after `Planning review`, `Legal check`, and appeals, as well as the absence of explicit `'Completeness rework'` / `'Inspection rework'` events in the raw log.
3. **Arrival and sojourn baseline extraction**: Compute baseline inter-arrival summaries (`pm4py.statistics.traces.generic.pandas.case_arrival`) and case/edge sojourn times, then export structured feature tables to statistical estimation modules (`statsmodels`, `scipy`, `scikit-learn`).

## Component-by-component estimation strategy

### 1. Arrivals and demand bursts
- **Non-stationary baseline**: Fit a Generalized Linear Model (Negative Binomial to capture overdispersion) to hourly/daily arrival counts excluding top-20 clusters, with predictors for month (capturing the 1.7x March–May and September–November surge), day-of-week (capturing the 2.2x Monday vs. Wednesday ratio), hour-of-day, and public holidays.
- **Architect bursts**: Partition the top-20 `architect_id` streams and fit a **compound Poisson / Neyman–Scott cluster process** (or marked Hawkes process): estimate cluster initiation rate, cluster size distribution (number of related applications submitted in the same week), intra-week arrival offsets, and within-cluster correlation of `district` and `case_type`.
- **Attribute generation**: Estimate the joint distribution of `(case_type, district, application_value, requires_fire, requires_environment, requires_public_notice)` conditional on `architect_id` tier using empirical copulas or stratified conditional tables.

### 2. Service times vs. waiting times (addressing missing start timestamps)
Because many human activities only log completion timestamps, raw inter-event intervals measure **sojourn time** (queue waiting + off-shift calendar gaps + external delays + true service time). Collapsing these into a single service-time distribution would violate capacity physics and invalidate staffing or scheduling interventions (e.g., D4, D6, D7). Estimation therefore proceeds in three layers:
1. **Direct estimation where available**: For activities with logged start and completion timestamps (or system logs), fit parametric distributions (Log-normal, Gamma, Weibull) via Maximum Likelihood Estimation (MLE) stratified by `case_type`.
2. **Calendar-adjusted deconvolution**: Remove non-working intervals (using HR calendars) between the enabling predecessor completion and the activity completion. Identify **low-congestion observations** (periods where estimated WIP in that role's queue is $\le$ active FTE) to approximate pure service-time distributions and check consistency against the empirical medians/p90s (e.g., Planning 3.5h / 14h).
3. **Simulation-Based Calibration (SBC / Approximate Bayesian Computation)**: Parameterize unobserved service-time distributions by `(case_type, district)` anchored to the empirical medians/p90s, and calibrate shape/scale parameters by minimizing Wasserstein distance between simulated and observed activity sojourn distributions (including waiting-time medians: e.g., 1.5d Clerks, 6d Planning, 8d Environmental, 8d Inspection) under the fixed HR calendars.
4. **External response times**: Estimate `Request missing documents -> Receive missing documents` directly as a pure external waiting distribution (heavy-tailed Log-normal/Burr, median 5d, calendar-day basis) without municipal resource contention.

### 3. Routing and branching probabilities
- Perform **decision mining** at each branching point (`requires_fire`, `requires_environment`, `requires_public_notice`, `Legal check`, `Issue permit` vs. `Reject application`) using regularized logistic regression or gradient-boosted trees trained on case attributes.
- **Latent triggers**: Because building area and full environmental sensitivity data are missing, estimate residual trigger rates $P(\text{Fire} \mid \text{requires\_fire}=\text{no}, \text{case\_type}, \text{value})$ and $P(\text{Env} \mid \text{requires\_env}=\text{no}, \text{district}, \text{case\_type})$ as calibrated Bernoulli probabilities matching observed review volumes.

### 4. Rework probabilities and loop structure
- Estimate stage-specific rework probabilities for `Completeness`, `Planning`, `Inspection`, `Legal`, and `Appeal` as functions of `case_type`, `architect_id` (hierarchical random effect), `district`, and prior rework count $k$ (checking for diminishing or escalating repeat-loop hazards).
- Because rework reasons are unstructured text, draw a stratified sample (e.g., 500 rework cases) for light manual/LLM-assisted coding into *minor administrative fix* vs. *major substantive redesign* to parameterize a two-component rework-duration mixture.

### 5. Resource calendars and effective capacity
- Initialize calendars from HR rosters (FTEs, weekdays, holiday schedules, council-meeting weeks, Monday clerk portal diversion, Simple-only planners, 40% non-permit environmental reservation).
- Cross-check HR rosters against empirical completion-timestamp histograms by `(org:resource, day_of_week, hour)` to detect batch-logging artifacts, unplanned absenteeism rates, and whether the 40% non-permit environmental workload behaves as fixed blocks (e.g., 2 days/week) or continuous competing interruptions.

### 6. Cross-case dependencies and latent objections
- **Latent objections**: Since objection events are absent, fit a **two-component mixture model** to `Public-notice period` duration:
  - *Component 0 (No objection)*: tightly concentrated near the 14-day statutory minimum.
  - *Component 1 (Objection occurred)*: heavy-tailed distribution extending to 60+ days (capturing the 60d p90).
  Estimate each case’s posterior probability of belonging to Component 1, then measure temporal-spatial clustering of Component-1 cases within the same `district` and overlapping notice windows to calibrate the **shared neighborhood shock hazard** and its spillover to `Legal check` / `Appeal`.
- **Inspection travel and batching**: Estimate district-level travel premiums (`D3`, `D5`) from site-inspection sojourn tails and municipal GIS road-distance matrices; estimate applicant no-show probabilities from the 9% inspection-rework variant share.

# 3. Assumptions

### Arrivals
- Background submissions from non-top-20 architects follow an inhomogeneous Poisson process conditional on month, day-of-week, and holiday indicators.
- Top-20 architects generate clustered bursts within a rolling 7-day window; intervention D7 (appointment slots) shifts Monday arrivals to Tue–Thu with partial compliance (e.g., 50%–75% adoption among top-20 architects, 10%–25% among others) rather than eliminating total weekly volume.
- Under D1 (pre-submission checker), total submission volume remains roughly constant (or declines slightly if ineligible proposals self-filter), while applicant preparation time shifts upstream before `Submit application`.

### Service times
- True human service times are independent of instantaneous queue length in the baseline (no unmodeled speed-up/cutting corners under load, though testable in sensitivity analysis).
- Activity processing that spans the end of a workday pauses at shift end and resumes at the next shift start (work-conserving), except `Site inspection`, which is non-preemptive (an inspector completes a dispatched visit before ending the shift).
- System tasks (`Submit application`, `Issue permit`) have negligible service times (seconds to minutes) and effectively infinite concurrency.

### Routing
- `Decision drafting` acts as an AND-join waiting for all required parallel reviews (`Planning`, `Fire`, `Environmental`), `Public-notice period`, and `Site inspection` to complete; if a review triggers major rework, dependent downstream milestones pause or re-trigger accordingly.
- Under D2 (`Simple renovation`, `application_value < EUR 50,000`, no prior violations), skipping `Site inspection` carries a small, explicitly parameterized post-hoc audit/compliance risk rather than zero risk.
- Under D5 (parallel legal pre-check for `Commercial` and `Complex variance`), legal pre-check can start once `Planning review` reaches an interim milestone (or completes), saving serial queue time unless late technical/environmental changes invalidate the pre-check and force a legal redo.

### Resources and calendars
- HR-derived rosters accurately represent nominal shift windows, supplemented by an empirically calibrated unplanned-absence/leave factor (e.g., 8%–12% across roles).
- The 40% non-permit duty for Environmental reviewers is non-deferrable in the baseline and consumes capacity proportionally throughout the week.
- Legal officers suspend non-urgent permit work entirely during council-meeting weeks; urgent escalations (e.g., statutory deadline imminent) can access a capped urgent slot.
- Under D4, the temporary peak-month inspector requires a brief onboarding/ramp-up period (e.g., 80% productivity in week 1) and is available strictly during peak windows (Mar–May, Sep–Nov).

### Rework
- Rework probabilities depend on `case_type`, `architect_id`, stage, and rework iteration $k$, with a soft cap on repeat loops (after e.g. 3–4 loops, rejection probability rises sharply).
- D1 (pre-submission checker) reduces completeness-rework probability by an uncertain factor (e.g., 35%–65%, explored via epistemic sensitivity) without directly reducing technical Planning or Inspection rework.
- Rework returns preferentially to the original planner/inspector where available (familiarity effect), falling back to the general pool if wait exceeds a threshold.

### Applicant and third-party response
- Applicant document turnaround (`Request -> Receive missing documents`) and external environmental consultant reports are unaffected by municipal staffing levels and follow calendar days rather than municipal office hours.
- Heavy tails in applicant response reflect genuine applicant abandonment/financing delays and are truncated or administratively closed only if a statutory expiration limit (e.g., 90–180 days) is triggered.

### Cross-case dependencies
- Related cases from the same architect submitted in a burst share a correlated latent document-quality score.
- Neighborhood objections follow a cluster-level hazard: once triggered in a parcel cluster, co-located active `Public-notice` cases face an elevated conditional objection probability.
- Under D3 (district batching), bundling $k$ inspections in the same district reduces total travel time sublinearly (e.g., fixed transit to district + smaller intra-district hops), bounded by a maximum batch size (e.g., 4–5 visits/day) and a maximum wait timeout (e.g., 5–7 business days) to prevent starvation in low-volume districts.

### Non-stationary demand
- Seasonal multipliers (1.7x in Mar–May and Sep–Nov vs. Jan–Feb) and weekday multipliers (2.2x Mon vs. Wed) persist across the 24-month evaluation horizon, with year-over-year volume drift tested only in stress scenarios.
- Case-type mix stays stationary across seasons unless perturbed in stress scenarios (or modulated slightly if empirical data shows spring spikes are heavier in `Simple renovation` / `New residential`).

### Missing data
- Missing start timestamps are non-adversarial (missing by IT-system design per role rather than selectively censored on slow cases); deconvolved service times accurately represent the full role population.
- Missing objection events are identifiable in distribution via the 14-day minimum vs. 60-day p90 mixture structure of `Public-notice period`, acknowledging higher uncertainty in small districts.
- Removed rare emergency decisions represent a small share of cases ($<2\%$) and do not distort nominal routing, though their capacity impact on Planners/Legal is tested as a stress scenario.
- Missing `prior_violations` history (needed for D2 eligibility) is approximated via a calibrated Bernoulli eligibility rate by `case_type` and `architect_id` until integrated with enforcement records.

# 5. Warm-up, replications, and uncertainty treatment

## Warm-up approach and run length
Because demand has a strong annual seasonal cycle (1.7x spring/autumn waves) and Complex variance cases exhibit a 260-day p90 duration, the system never settles into a time-invariant steady state, yet starting empty-and-idle severely understates initial backlog and long-tail aging.
- **Policy-comparison runs**: Use a **12-month warm-up period** (one complete seasonal cycle, verified via Welch’s moving-average graphical diagnostic across pilot replications on WIP and rolling p90 duration to confirm that initial transient bias has vanished and multi-month Complex cases populate all queues), followed by a **24-month data-collection window** (two full seasonal cycles so seasonal backlog carryover between years is captured). Cases entering near the end of month 36 are tracked via a **6-month cooldown/drain window** (only for completing already-submitted cases, not recording new entrants) to prevent right-censoring bias on long-tail Complex variance durations.
- **Operational shadow-mode runs**: Bypass artificial warm-up by initializing directly from the live WIP snapshot (active cases, current stage, elapsed age, scheduled batches) and simulating forward 3–6 months.

## Replications and random-number management
- **Variance reduction via Common Random Numbers (CRN)**: Assign independent, synchronized random streams per replication using `numpy.random.SeedSequence` (separate substreams for background arrivals, architect clusters, case attributes, service times, rework draws, objection waves, and travel times). Every scenario (B0, D1–D11) in replication $r$ faces the exact same arrival stream and external shocks, substantially shrinking variance on paired policy differences ($\Delta = Y_{\text{policy}} - Y_{\text{B0}}$).
- **Replication count**: Run a pilot of $n_0 = 20$ replications per scenario to estimate the sample standard deviation $s$ of the noisiest primary KPI (Complex variance p90 duration and SLA compliance). Determine final replications sequentially via:
  $$n \ge \left(\frac{t_{n_0-1,\,1-\alpha/2} \cdot s}{\epsilon}\right)^2$$
  targeting a relative half-width $\epsilon \le 3\%$ on medians and $\le 5\%$ on p90s (typically $n = 50\text{--}100$ replications per configuration).

## Separating stochastic vs. parameter (epistemic) uncertainty
Reporting only Monte Carlo stochastic CIs would be misleading because key parameters—deconvolved service times, latent objection probabilities, and prospective policy efficacy (e.g., how much D1 cuts missing docs)—carry substantial epistemic uncertainty.
- **Two-level (nested) uncertainty quantification**:
  - *Outer loop (epistemic)*: Draw $M = 40$ parameter vectors using **Latin Hypercube Sampling (LHS)** across calibrated posterior intervals and plausible intervention-effect ranges (e.g., D1 efficacy $\in [35\%, 65\%]$, D5 invalidation rate $\in [10\%, 25\%]$).
  - *Inner loop (aleatoric)*: Run $R = 15\text{--}25$ CRN replications per outer draw.
  - Report **95% predictive/credible intervals** combining both variance components, alongside the probability of net improvement $P(\Delta_{\text{KPI}} < 0)$ across outer draws.
- **Multiple comparisons**: Apply **Benjamini–Hochberg FDR control** (or Bonferroni/Indifference-Zone Ranking & Selection when comparing all pairs against B0) so chance fluctuations across D1–D11 are not mistaken for true improvements.

## Sensitivity analysis and heavy-tailed durations
- **Global sensitivity analysis**: Compute **Partial Rank Correlation Coefficients (PRCC)** and **Sobol first/total-order indices** over the LHS outer runs to rank which uncertain assumptions (e.g., Environmental 40% non-permit load, D1 efficacy, neighborhood objection coupling) most affect policy rankings.
- **Handling heavy tails**:
  - Do not rely on sample means or Gaussian $t$-intervals alone for skewed durations (e.g., `Receive missing documents`, `Public-notice period`, `Complex variance` tail).
  - Estimate medians, p90, p95, and **Conditional Value-at-Risk (CVaR$_{90}$: mean duration of the worst 10% of cases)** using **cluster-level percentile/BCa bootstrap** (resampling at the replication level rather than individual cases, respecting cross-case dependence).
  - Inspect tail-index sensitivity (comparing Log-normal vs. Weibull vs. generalized Pareto/Burr tails) to ensure extreme outliers are driven by realistic operational mechanisms (objection + council week + rework) rather than unbounded distribution artifacts.

# 6. Validation strategy

No policy recommendation should be treated as credible until the twin passes six complementary validation layers:

1. **Face validation (domain-expert review)**
   - Conduct structured workshops with clerks, planners, fire/environmental reviewers, inspectors, legal officers, and representative architects.
   - Review process animations, simulated calendar blocks (e.g., Monday clerk portal-support dip, Tue–Thu Fire schedule, Legal council-week freeze), and individual synthetic case histories (e.g., a D3 New residential case bundled for inspection vs. a Complex variance case hit by an objection wave) to verify operational realism.

2. **Event-log replay validation (structural and trace fidelity)**
   - Feed the exact historical 18-month arrival timestamps and observed case attributes deterministically into the twin.
   - Export simulated event logs in XES/CSV format and run PM4Py conformance checks (`pm4py.conformance_diagnostics_alignments`, variant comparisons, and DFG diffs) against the historical log.
   - Confirm that variant shares match empirical benchmarks (e.g., 26% simple clean, 19% simple missing docs, 9% inspection rework) within $\pm 2\text{--}3$ percentage points, and verify that AND-join constraints before `Decision drafting` are respected.

3. **Distributional validation (marginal and temporal fidelity)**
   - Compare simulated vs. empirical end-to-end duration distributions—overall and stratified by `case_type`, `variant group`, and `district`—using Q-Q plots, two-sample **Kolmogorov–Smirnov (KS)**, **Anderson–Darling** (tail-sensitive), and **Wasserstein distance** metrics.
   - Verify target quantiles against empirical summaries (e.g., Simple clean median 12d / p90 24d; Commercial median 68d / p90 130d; Complex variance median 140d / p90 260d).
   - Validate **temporal dynamics**: confirm that Monday submission spikes produce the observed Tuesday–Wednesday clerk backlog wave and that Mar–May / Sep–Nov arrival waves generate realistic seasonal WIP accumulation and decay.

4. **Resource-utilization validation**
   - Cross-check simulated role-level utilization, active hours, travel-time shares (for inspectors), and non-permit time shares (for environmental reviewers) against HR timesheets, inspector mileage/route logs, and empirical activity-timestamp density per resource.
   - Investigate discrepancies: e.g., if simulated clerks show 45% utilization while observed clerk waiting is 1.5 days, this flags either underestimated service times, unmodeled non-permit duties, or batch-processing behavior.

5. **Bottleneck validation**
   - Verify that simulated queue waiting-time medians and bottleneck rankings reproduce historical hotspots: Environmental (8d), Inspection (8d, especially D3/D5), Legal (7d, spiking around council weeks), Planning (6d), Decision drafting (5d), Fire (4d), and Clerks (1.5d, spiking post-Monday).
   - Confirm that dynamic bottlenecks shift realistically across seasons (peak vs. trough months) and across case types.

6. **Out-of-sample (temporal holdout) and shadow validation**
   - **Temporal holdout**: Calibrate all parameters strictly on **months 1–12** of the 18-month log, warm-start the twin with the actual WIP state at the end of month 12, and predict **months 13–18** (covering a seasonal wave and holidays) out of sample. Evaluate whether observed monthly throughput, WIP, medians, and p90s fall inside the twin’s 90%/95% predictive intervals.
   - **Prospective pilot / shadow validation**: Before municipality-wide rollout of structural changes (e.g., D2 or D3), pilot the policy in one or two districts (e.g., D3) for 8–12 weeks and test whether empirical shifts match twin predictions; recalibrate behavioral parameters (e.g., architect compliance, objection mediation efficacy) iteratively.

# 7. Decision criteria

Because a simulation model contains calibrated approximations and unmodeled political/legal values, the twin should **not** claim an "exact optimum." Instead, selection should use a **multi-objective Pareto and satisficing framework** (hard guardrails + ranked preference metrics + robustness across stress scenarios):

| Criterion | Primary Metrics | Target / Guardrail Range | Rationale & Nuance |
| :--- | :--- | :--- | :--- |
| **Cycle-time performance (Median & Tail)** | Median, p90, p95, and CVaR$_{90}$ end-to-end duration (overall & by `case_type`) | $\ge 15\%\text{--}25\%$ reduction in overall p90; **no case type's p90 degrades by $> 5\%$** | Prevents policies that speed up Simple renovations while starving Complex or Commercial permits. |
| **SLA compliance by case type** | % of cases completed within target SLA (illustrative targets: Simple $\le 20\text{d}$, Res $\le 60\text{d}$, Comm $\le 90\text{d}$, Complex $\le 180\text{d}$) | Target thresholds: Simple $\ge 90\%$, Res $\ge 85\%$, Comm $\ge 80\%$, Complex $\ge 75\%$ (or $+10\text{--}15$ pp gain over B0) | Directly reflects statutory/municipal service commitments per segment. |
| **Fairness across districts & architects** | (a) Max-to-min district median/p90 wait ratio; (b) Top-20 vs. non-top-20 architect median wait gap | District ratio $\le 1.25$ (must not worsen for D3/D5 or small districts under D3); architect gap within $\pm 10\%$ | Ensures D3 batching does not starve low-volume districts and D7 appointment slots do not penalize small/homeowner applicants. |
| **Resource utilization & sustainability** | Effective utilization per role (normal months & peak months) | **75%–85%** normal-month operating band; **$\le 92\%$** peak-month ceiling; D4 temp FTE peak utilization $\ge 65\%$ | Utilization $> 90\%$ triggers nonlinear queueing instability and staff burnout; low peak utilization signals D4 is redundant if D2+D3 suffice. |
| **Rework & quality guardrails** | Stage-specific rework rates (Completeness, Inspection, Legal, Appeal) | Completeness rework down $\ge 25\%$ (under D1); downstream Inspection/Legal/Appeal rework increase **$\le +1.5$ pp** | Guards against D2 (skipped inspections), D5 (premature legal pre-check), or D8 (aggressive triage) shifting defects downstream. |
| **Backlog & aging WIP** | Peak WIP level, % of WIP aging $> 1.5\times$ SLA, post-peak recovery time | Aging WIP share reduced $\ge 30\%$; post-May/Nov backlog clears back to baseline within **4–6 weeks** | Measures operational stability and prevents year-over-year backlog drift. |
| **Robustness & cost-effectiveness** | Worst-case regret across S1–S4; $P(\text{net gain})$ across epistemic LHS draws; annual cost per p90-day saved | Net-positive on primary KPIs in $\ge 90\%$ of epistemic draws; avoids unstable backlog blow-up under S1/S2; favorable benefit-to-cost ratio (including applicant effort under D1/D7) | Favors resilient portfolios (e.g., balanced full-chain D11 vs. inspection-heavy D10) over fragile point optima. |

**Selection rule**: Filter out any intervention violating a hard guardrail (burnout utilization $>92\%$, fairness degradation, or downstream rework spike), identify the **non-dominated Pareto frontier** across `(p90 reduction, SLA compliance, total cost, stress-scenario regret)`, and present the top 2–3 portfolios with explicit trade-off profiles to municipal leadership.

class ProcessMiningAnalyzer:
    """
    Handles event-log ingestion, PM4Py structural discovery, process-tree parsing,
    and timing feature extraction cleanly separated from simulation logic.
    """

    def __init__(self, df: pd.DataFrame) -> None:
        self.raw_df = df.copy()
        self.log_df = pm4py.format_dataframe(
            self.raw_df,
            case_id="case:concept:name",
            activity_key="concept:name",
            timestamp_key="time:timestamp",
        )
        self.log_df = self.log_df.sort_values(
            ["case:concept:name", "time:timestamp"]
        ).reset_index(drop=True)

    @classmethod
    def from_csv_string(cls, csv_text: str) -> "ProcessMiningAnalyzer":
        # Note: PM4Py has no pm4py.read_csv; load with pandas first.
        df = pd.read_csv(io.StringIO(csv_text))
        return cls(df)

    def parse_nominal_tree(self, tree_str: str) -> Any:
        """
        Parses the simplified process tree string using pm4py.parse_process_tree.

        Known semantic limitations of this simplified tree vs. the real process:
        1. Synthetic loop-back labels ('Completeness rework', 'Inspection rework')
           do not appear in the raw event log (e.g., P001 loops directly from
           'Receive missing documents' back to 'Completeness check').
        2. Rework loops after 'Planning review', 'Legal check', and applicant
           appeals are omitted from the tree and must be modeled in the engine.
        3. Data-dependent routing guards (e.g., requires_fire, D2 value < 50k),
           dynamic parallelization (D5 legal pre-check), and cross-case joins
           (D3 district batching, correlated objections) cannot be represented
           by a pure control-flow process tree alone.
        """
        normalized = " ".join(tree_str.split())
        return pm4py.parse_process_tree(normalized)

    def discover_summary_artifacts(self) -> Dict[str, Any]:
        """Computes variants, DFG, performance DFG, and average case arrival interval."""
        variants = pm4py.get_variants(self.log_df)
        dfg, start_acts, end_acts = pm4py.discover_dfg(self.log_df)
        perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(self.log_df)

        # Case arrival average in seconds (illustratively computed on the full log;
        # for production calibration, stratify by month, day-of-week, and architect tier).
        case_arrival_avg_sec = pandas_case_arrival.get_case_arrival_average(self.log_df)

        return {
            "variants": variants,
            "dfg": dfg,
            "start_activities": start_acts,
            "end_activities": end_acts,
            "performance_dfg": perf_dfg,
            "case_arrival_avg_sec": case_arrival_avg_sec,
        }

    def compute_timing_columns(
        self, start_timestamp_col: Optional[str] = "start_timestamp"
    ) -> pd.DataFrame:
        """
        Computes elapsed sojourn time per event, and true service/waiting times
        ONLY if start timestamps are present. Explicitly avoids collapsing
        waiting time and service time when only completion timestamps exist.
        """
        df = self.log_df.copy()
        df["prev_complete_ts"] = df.groupby("case:concept:name")["time:timestamp"].shift(1)
        df["sojourn_since_prev_sec"] = (
            df["time:timestamp"] - df["prev_complete_ts"]
        ).dt.total_seconds()

        if start_timestamp_col and start_timestamp_col in df.columns:
            df[start_timestamp_col] = pd.to_datetime(df[start_timestamp_col])
            df["service_time_sec"] = (
                df["time:timestamp"] - df[start_timestamp_col]
            ).dt.total_seconds()
            df["waiting_time_sec"] = (
                df[start_timestamp_col] - df["prev_complete_ts"]
            ).dt.total_seconds()
        else:
            warnings.warn(
                "No start_timestamp column found: 'sojourn_since_prev_sec' conflates "
                "queue waiting, calendar off-hours, external delays, and service time. "
                "Leaving 'service_time_sec' and 'waiting_time_sec' as NaN; use "
                "calendar-aware deconvolution / simulation-based calibration.",
                UserWarning,
            )
            df["service_time_sec"] = np.nan
            df["waiting_time_sec"] = np.nan

        return df

        self, role: str, sim_day: int, day_of_week: int, month: int, is_council_week: bool
    ) -> float:

        # Placeholder logic illustrating calendar rules:
        if day_of_week >= 5:  # Weekend
            return 0.0
        if role == "clerk":
            cap = self.base_fte[role] - (1 if day_of_week == 0 else 0)
        elif role == "fire":
            cap = self.base_fte[role] if day_of_week in (1, 2, 3) else 0
        elif role == "environmental":
            cap = self.base_fte[role] * 0.60  # 40% non-permit duties

class RoutingAndDependencyEngine:
    """
    Handles data-aware routing, latent triggers (unobserved area/env sensitivity),
    correlated neighborhood objection shocks, and D3 district inspection batching.
    """

    def __init__(self, rng: np.random.Generator, config: InterventionConfig) -> None:
        self.rng = rng
        self.config = config
        self.district_inspection_buffers: Dict[str, List[PermitCase]] = {}
        self.active_cluster_objections: Dict[str, float] = {}  # cluster_id -> shock_end_day

    def requires_site_inspection(self, case: PermitCase) -> bool:
        if (
            self.config.d2_skip_simple_inspection
            and case.case_type == "Simple renovation"
            and case.application_value < 50_000
            and not case.prior_violations
        ):
            return False
        return True

    def sample_public_notice_duration_days(self, case: PermitCase, current_day: float) -> float:
        """
        Models latent (unobserved) objection events as a two-component mixture
        coupled across co-located cases in the same parcel cluster.
        """
        base_prob = 0.18 if case.case_type == "Complex variance" else 0.08
        # Spatial-temporal coupling: elevate hazard if cluster has an active objection wave
        if self.active_cluster_objections.get(case.parcel_cluster_id, -1.0) >= current_day:
            base_prob = min(0.85, base_prob * 2.5)

        effective_prob = min(
            0.95,
            base_prob * self.config.objection_shock_multiplier * (1.0 - self.config.d9_objection_reduction),
        )
        if self.rng.random() < effective_prob:
            case.latent_objection_triggered = True
            self.active_cluster_objections[case.parcel_cluster_id] = current_day + 30.0
            # Heavy-tailed objection extension beyond 14-day statutory minimum
            return 14.0 + float(self.rng.lognormal(mean=3.2, sigma=0.65))
        return 14.0

    def try_form_inspection_batch(
        self, case: PermitCase, current_day: float
    ) -> Optional[List[PermitCase]]:
        """
        Placeholder for D3 district batching: accumulates cases by district until
        batch size or max-wait timeout is reached, trading early wait for lower travel.
        """
        if not self.config.d3_district_batching:
            return [case]
        buf = self.district_inspection_buffers.setdefault(case.district, [])
        buf.append(case)
        oldest_wait = current_day - buf[0].arrival_time
        if len(buf) >= self.config.d3_batch_size or oldest_wait >= self.config.d3_max_batch_wait_days:
            batch = buf[: self.config.d3_batch_size]
            self.district_inspection_buffers[case.district] = buf[self.config.d3_batch_size :]
            return batch
        return None

class ExperimentRunner:
    """Executes Baseline, D1–D10, and Stress Scenarios with CRN replications."""

    def __init__(self, base_seed: int = 202601) -> None:
        self.base_seed = base_seed

    def run_matrix(
        self, scenarios: List[InterventionConfig], n_replications: int = 50
    ) -> pd.DataFrame:
        records: List[Dict[str, Any]] = []
        # Reuse identical SeedSequence per replication index across scenarios (CRN)
        rep_seeds = np.random.SeedSequence(self.base_seed).spawn(n_replications)

        for cfg in scenarios:
            for rep_idx, sseq in enumerate(rep_seeds):
                sim = PermitDigitalTwinSimulator(config=cfg, seed_seq=sseq)
                metrics = sim.run()
                records.append({"scenario": cfg.name, "replication": rep_idx, **metrics})
        return pd.DataFrame(records)
