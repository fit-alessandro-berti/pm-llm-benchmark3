# 1. Review Scope and Assumptions

I review Model S and Model C as a member of a model-governance board, treating the reported metrics as *evidence produced under an undocumented protocol*, not as ground truth. Before interpreting anything, I distinguish four intended use cases, because the "right" fitness/precision trade-off is not a property of a model in the abstract — it is a property of a model *relative to a decision*.

- **U1 — Exploration / discovery.** The model is a lens for analysts to see what happened. Here high recall of real behavior (fitness, generalization) matters most; low precision is tolerable because the model is descriptive, not normative. False accepts cost little; false rejects (hiding real behavior) cost a lot.
- **U2 — Conformance enforcement / compliance.** The model is a gate. A trace that the model accepts is treated as "allowed." Here precision *against a curated negative suite* and *semantic correctness of the accepted language* dominate. A single wrongly-accepted forbidden trace (e.g., approval with no Credit Check) is a compliance failure regardless of aggregate fitness. Over-rejection is annoying but safe.
- **U3 — Simulation / prediction.** The model generates plausible futures (throughput, load). Here calibrated generalization matters: it must reproduce the *distribution* of legitimate variants, not just the observed set, and must not fabricate impossible orderings.
- **U4 — Stakeholder communication.** The model is a shared picture. Simplicity and comprehension dominate; formal metrics are almost irrelevant, but *faithfulness* (the picture must not lie about mandatory steps) still binds.

**How use case changes the trade-off.** For U1 I would accept Model-S-like permissiveness. For U2 I would reject any model whose *accepted language* includes forbidden traces, even at 0.99 fitness, and I would prefer over-restriction plus an explicit exception path. For U3 I need behavior *between* Model S (too broad) and Model C (too narrow): the legitimate but unseen recombinations in F4/B5 must be generatable. For U4 both models fail differently — S is comprehensible but misleading, C is faithful-but-unreadable.

**Assumptions.** (a) The process-tree operators are standard PM4Py: `->` sequence, `+` concurrency (AND, interleaving), `X` exclusive choice, `tau` silent. (b) `X('Credit Check', tau)` therefore means "Credit Check *or nothing*," i.e., the activity is optional. (c) P1–P7 and B1–B8 encode current business policy and take precedence over metrics when they conflict. (d) Metrics are not comparable across models unless the split, seeds, alignment costs, and held-out cases are identical and published; the dossier states they are not. (e) I will not average the eight measures into a scalar; where I must summarize, I keep the disaggregated view.

# 3. Adversarial Review of Model S

Model S:
```text
->( 'Register Dossier',
    +( X('Credit Check', tau), X('Technical Review', tau),
       X('Supplier Review', tau), X('Expedite Review', tau) ),
    X('Manager Approval','Auto Approval'),
    'Release Order' )
```

**Strongest case for S.** It is sound, simple, fast, and comprehensible. It correctly fixes P1 (Register first, Release last) and P5 (exactly one approval, via the top-level `X`). Its concurrency block gracefully absorbs missing events and arbitrary check orderings, which is exactly what you want for **U1 exploration** on a noisy log with the missing external/internal attribute (P3). Its holdout fitness (0.981) and generalization (0.907) reflect that it does not shatter on unseen legitimate recombinations — the very cases (F4/B5) that break C.

**Strongest case against S.** The `+( X(a,tau), ... )` construction makes *every* check simultaneously optional and unordered. This is not principled noise-tolerance; it is a semantic collapse of the policy. It cannot express "mandatory," "must precede," or "required-only-if-external." For **U2 enforcement** it is disqualifying: it accepts forbidden traces as first-class legal behavior.

Concrete undesirable/ambiguous behaviors it admits (with traces):

- **S-a — Approval with no mandatory checks (violates P2).** `Register Dossier, Manager Approval, Release Order` — both checks took their `tau` branch. This is exactly probe B3 (forbidden), yet S accepts it.
- **S-b — Expedite before mandatory checks (violates P4).** `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` — the AND block interleaves freely, so Expedite may precede both checks. This is B4 (forbidden), accepted.
- **S-c — Supplier Review on an order with nothing else, or Expedite with no checks.** `Register Dossier, Supplier Review, Auto Approval, Release Order` — approval with zero mandatory checks and an optional-only body.
- **S-d — Skipping one mandatory check only.** `Register Dossier, Credit Check, Auto Approval, Release Order` — Technical Review silently skipped. Half-compliant, still forbidden by P2.
- **S-e — Expedite present but mandatory checks absent.** `Register Dossier, Expedite Review, Auto Approval, Release Order` — P4 requires Expedite to *follow* both mandatory checks; here they never occur.
- **S-f — Repeated mandatory check with no correction is *not even representable as suspicious*.** `Register Dossier, Credit Check, Technical Review, Credit Check, Manager Approval, Release Order` (B8): the AND block does not loop, so S actually *rejects* this — but it also cannot model the legitimate corrected-recheck (B6), so it gets the right verdict on B8 for the wrong reason and the wrong verdict on B6.

**Permissiveness attribution.** S-a, S-b, S-d, S-e are **accidental semantic flaws**: optionalizing mandatory steps and freely interleaving Expedite are modeling errors, not intentional noise tolerance. Only the tolerance of *ordering variation between the two mandatory checks* (Credit↔Technical, P2 allows either order) and tolerance of missing *Supplier Review* (P3, attribute-missing) are defensible as intentional noise/uncertainty handling. The advocate's claim (F7) that "low precision is fine for exploration" is valid *only if S is fenced to U1 and never used as a gate*.

# 4. Adversarial Review of Model C

Model C is an `X(...)` over eight fully-enumerated sequences.

**Strongest case for C.** Every branch it accepts is, on inspection, policy-plausible: it enforces P2 (both checks present before approval), respects P4 (Expedite after checks, before approval), P5 (each branch has exactly one approval), includes a correction/recheck branch, and distinguishes Supplier-Review (external) branches. Its training precision (0.941) reflects that it does not accept much beyond real behavior. For **U2** on the *exact* variants it encodes, it is a defensible allow-list, and the advocate's stance (F8, "unseen = noncompliant until approved") is a legitimate conservative posture *if* the process is truly closed-world.

**Strongest case against C.**

- **Branch enumeration.** Eight hand-listed sequences cannot cover the combinatorics: two check orders × {Supplier yes/no} × {Expedite yes/no} × {Manager/Auto} alone is 2×2×2×2 = 16 legitimate skeletons, before corrections. C lists 8, so it *structurally omits* legitimate combinations — e.g., external + Auto Approval, or Technical-first + Supplier + Expedite.
- **Unseen legitimate combinations (F4, B5).** B5 = `Register, Technical, Credit, Supplier, Expedite, Auto, Release` is a plausible external/urgent case. C has **no** branch with Supplier+Expedite+Auto, so it rejects B5. This is the mechanism behind the 0.744 holdout fitness: much of that "failure" is C rejecting *legitimate* recombinations, not catching noncompliance.
- **Holdout degradation.** 0.973 → 0.744 is the signature of *memorized variants*: the model fits what it saw and cannot align novel-but-valid orderings. High training precision is thus partly an **artifact of memorization**, not of principled tightness.
- **Duplicate labels (33) and impact analysis (F3).** Each activity appears in many branches, so "who owns Credit Check?" or "change the Credit Check rule" requires editing it in N places. Duplicate labels also destroy arc-degree simplicity (0.281) and complicate alignment (33 candidate transitions per label → runtime 0.440 s).
- **Correction handling (F6, B6).** C encodes exactly one correction branch (Correct → Credit → Technical). It cannot express P6's real options: correction affecting *only* Credit Check, *only* Technical Review, or *both*. So B6 (`Correct, Technical` only) is **rejected** by C even though it is valid when the correction affected Technical Review alone. C is simultaneously too rigid (one recheck shape) and unable to represent the affected-check semantics.
- **Maintainability.** Adding one legitimate variant means adding a whole branch; the model grows linearly in variants and becomes unauditable — the opposite of "audit-ready."

**Verdict on the "precision" claim.** C's 0.941 precision and low holdout fitness together are the classic overfitting diagnosis: precise on the training positives because it *is* the training positives, brittle everywhere else. Precision measured only against observed positives (F5) cannot credit C for *correctly rejecting* negatives, because none were tested — so the number overstates its enforcement value.

# 5. Behavior-Probe Matrix

Reasoning is from the model expressions. For S, "accepts" means a perfect (cost-0) alignment exists given optional-and-interleaved checks and top-level exclusive approval. For C, "accepts" means the trace equals one of the eight listed sequences (silent transitions: none, so matching is exact-sequence).

| Probe | Model S accepts? | Model C accepts? | Policy assessment | Consequence for review |
|---|---|---|---|---|
| B1 `Reg,Credit,Tech,Mgr,Rel` | Yes | Yes (branch 1) | valid | Baseline; both correct. |
| B2 `Reg,Tech,Credit,Auto,Rel` | Yes | **No** — C has no Technical-first + Auto branch (only Credit-first Auto, branch 8) | valid | C wrongly rejects a valid trace → confirms C's enumeration gap. |
| B3 `Reg,Mgr,Rel` | **Yes** (both checks → tau) | No | forbidden | S wrongly accepts → S unusable for enforcement. |
| B4 `Reg,Expedite,Credit,Tech,Mgr,Rel` | **Yes** (AND interleaves) | No (no branch starts Expedite) | forbidden | S wrongly accepts P4 violation; C correct. |
| B5 `Reg,Tech,Credit,Supplier,Expedite,Auto,Rel` | Yes | **No** (no Supplier+Expedite+Auto branch) | plausible valid external/urgent | S right for wrong reasons; C wrongly rejects legitimate recombination (F4). |
| B6 `Reg,Credit,Tech,Correct,Tech,Mgr,Rel` | **No** — S's AND block has no loop/Correct-Dossier activity at all | **No** — C's only correction branch is `Correct,Credit,Tech` | valid *iff* correction affected Technical alone | Both fail; neither represents affected-check semantics (F6). |
| B7 `Reg,Credit,Tech,Supplier,Mgr,Rel` | Yes | Yes (branch 3) | valid external | Both correct. |
| B8 `Reg,Credit,Tech,Credit,Mgr,Rel` | **No** (no loop; second Credit unmatchable) | No (no such branch) | suspicious/forbidden without correction | Both reject — but S rejects because it *cannot* repeat any check, not because it detects "suspicious." |

**Uncertainty stated precisely.** (i) B3/B4 acceptance by S depends on the standard reading of `X(a,tau)` as "a is optional" and `+` as free interleaving; if a nonstandard cost model penalized `tau` branches this could change, but under default PM4Py alignment costs, S accepts them at cost 0. (ii) For C, I assume no silent transitions and exact-sequence matching; because C has zero `tau`, any trace not literally one of the eight is a nonzero-cost alignment (rejected under a "cost-0 = accept" rule). (iii) S contains no `Correct Dossier` node at all, so B6 is rejected with certainty. (iv) C's `Supplier Review`/`Expedite` optionality exists only where a branch encodes it, so all "missing branch" rejections above are certain from the listing.

# 6. Likely Metric Pathologies

Ranked by likely decision impact (highest first).

1. **Positive-log-only precision (F5) — highest impact.** Precision was computed against observed positive traces with *no curated negative suite*. This is the single most decision-distorting flaw: it lets S look "merely imprecise" while it actually accepts forbidden traces (B3, B4), and it credits C's memorization as "precision." Any enforcement decision built on these precision numbers is unsafe.
2. **Fitness rewarded by optionalizing mandatory behavior.** S's 0.992/0.981 fitness is partly *bought* by making Credit/Technical optional. High fitness here is a symptom of a defect, not evidence of quality. Directly inverts the naive "higher fitness = better" reading.
3. **Generalization rewarded by excessive permissiveness.** Token-based generalization (S 0.907) structurally favors permissive/looping models and penalizes enumerated branches (C 0.412). It cannot distinguish "generalizes to legitimate behavior" from "accepts everything."
4. **Train/holdout leakage or split sensitivity.** No seeds, no held-out list, no preprocessing code. C's sharp 0.973→0.744 drop and S's flat 0.981 are both consistent with an unlucky/hard split or leakage. Because the split is unpublished, *none* of the holdout comparisons are trustworthy as-is.
5. **Missing-event bias (P3, F4).** The external/internal attribute is absent, and some Supplier Review events "may be missing." A model that skips Supplier Review will score *higher fitness* on such logs regardless of correctness, systematically rewarding permissiveness on exactly the attribute we cannot observe.
6. **Duplicated-label effects.** C's 33 duplicate labels inflate alignment ambiguity and depress simplicity; the metric penalizes a legitimate (if clumsy) modeling choice and interacts with runtime. "Definition undocumented" makes the 33 itself uninterpretable.
7. **Alignment-cost sensitivity.** Fitness/precision both depend on move-on-log vs move-on-model vs silent-move costs, none disclosed. S's silent transitions make it especially cost-sensitive (cheap `tau` skips). Results could shift materially under different cost vectors.
8. **Silent-transition effects.** S's four `tau` branches let alignments "skip" cheaply, mechanically raising fitness and lowering precision; C has none, so the two are being scored under structurally different alignment regimes.
9. **Stakeholder-score methodology.** "Informal 1–5," no protocol, no n, no blinding, plausibly collected by the discovery team. Comprehension may reward S *for hiding obligations*. Low evidentiary weight until re-run (§9).
10. **Runtime confounding by model size — lowest impact.** 0.018 s vs 0.440 s largely reflects branch/label count, not process efficiency; it is a cost input, not a quality axis, and is dominated by correctness for any governance decision.

# 7. Third Alternative

**Strategy chosen:** a **block-structured procedural backbone (POWL / process tree) + declarative and data/policy checks applied post-hoc.** The backbone captures what control-flow can honestly express from the log; the declarative layer and external checks capture the obligations the log *cannot* (external/internal attribute, affected-check semantics, negative behavior). This is safer than S (mandatory is mandatory) and more generalizable/maintainable than C (no branch enumeration, no duplicate-label sprawl).

## 7.1 Compact formal description

Backbone `model_third` (partial order):

- `Register Dossier` → (concurrency of the two mandatory checks) → optional `Expedite Review` → exactly-one approval → `Release Order`.
- **Mandatory checks:** `Credit Check` and `Technical Review` are *both required* and *unordered* (P2): modeled as a partial order with no edge between them but both preceding downstream nodes.
- **Optional Supplier Review:** modeled as `X(Supplier Review, tau)` — genuinely optional (P3) because the external/internal attribute is missing; the *policy* "required iff external" is enforced by a data-aware check, not silently dropped.
- **Expedite Review:** `X(Expedite Review, tau)`, ordered *after both mandatory checks* and *before approval* (P4). It is unordered w.r.t. Supplier Review (P4: "before or after").
- **Exactly-one approval:** `X(Manager Approval, Auto Approval)` (P5).
- **Correction/recheck:** a bounded loop `*(recheck_body, tau)` where `recheck_body = -> (Correct Dossier, X(Credit Check, Technical Review, +(Credit Check,Technical Review)))`, i.e., after a correction, re-run *only* Credit, *only* Technical, or *both* (P6). A repeated mandatory check *not* preceded by `Correct Dossier` is **not** in the backbone language and is caught as suspicious (P7) by a declarative rule.

Declarative/data layer (checked outside the net):
- `existence(Credit Check) ≥ 1`, `existence(Technical Review) ≥ 1` (redundant safety net for P2).
- `precedence(Expedite Review ← Credit Check ∧ Technical Review)` and `Expedite before approval` (P4).
- `exactly-one({Manager Approval, Auto Approval})` (P5).
- `if order.external == true then existence(Supplier Review) ≥ 1` (P3, data-aware; *cannot* be checked without the attribute — see limitations).
- `response(Correct Dossier → recheck of affected checks)`; `absence(repeated mandatory check without preceding Correct Dossier)` (P6, P7).

## 7.2 Self-contained PM4Py code (assigns `model_third`)

```python
import pm4py
from pm4py.objects.powl.obj import (
    Transition, SilentTransition, OperatorPOWL, StrictPartialOrder,
)
from pm4py.objects.process_tree.obj import Operator

# --- leaf activities ---
reg      = Transition(label="Register Dossier")
credit   = Transition(label="Credit Check")
tech     = Transition(label="Technical Review")
release  = Transition(label="Release Order")

# optional Supplier Review: X(Supplier Review, tau)  (P3, attribute missing -> optional)
supplier_opt = OperatorPOWL(operator=Operator.XOR,
                            children=[Transition(label="Supplier Review"),
                                      SilentTransition()])

# optional Expedite Review: X(Expedite Review, tau)  (P4)
expedite_opt = OperatorPOWL(operator=Operator.XOR,
                            children=[Transition(label="Expedite Review"),
                                      SilentTransition()])

# exactly-one approval: X(Manager Approval, Auto Approval)  (P5)
approval = OperatorPOWL(operator=Operator.XOR,
                        children=[Transition(label="Manager Approval"),
                                  Transition(label="Auto Approval")])

# correction body: Correct Dossier -> (only Credit | only Technical | both)  (P6)
corr        = Transition(label="Correct Dossier")
recheck_one = OperatorPOWL(operator=Operator.XOR, children=[
    Transition(label="Credit Check"),
    Transition(label="Technical Review"),
    OperatorPOWL(operator=Operator.AND, children=[
        Transition(label="Credit Check"),
        Transition(label="Technical Review"),
    ]),
])
correction_body = StrictPartialOrder(nodes=[corr, recheck_one])
correction_body.order.add_edge(corr, recheck_one)          # correction precedes recheck
# bounded correction loop: LOOP(do=correction_body, redo=tau) -> 0..n corrections
correction_loop = OperatorPOWL(operator=Operator.LOOP,
                               children=[correction_body, SilentTransition()])

# --- backbone partial order (mandatory checks concurrent & unordered, P2) ---
po = StrictPartialOrder(nodes=[reg, credit, tech, supplier_opt,
                               expedite_opt, correction_loop, approval, release])

# Register first (P1)
po.order.add_edge(reg, credit)
po.order.add_edge(reg, tech)
# both mandatory checks precede Expedite (P4) and precede approval (P2/P5)
po.order.add_edge(credit, expedite_opt)
po.order.add_edge(tech,   expedite_opt)
po.order.add_edge(credit, approval)
po.order.add_edge(tech,   approval)
# Supplier optional, unordered vs Expedite (P4) but before approval
po.order.add_edge(reg, supplier_opt)
po.order.add_edge(supplier_opt, approval)
# correction loop sits after the checks, before approval
po.order.add_edge(credit, correction_loop)
po.order.add_edge(tech,   correction_loop)
po.order.add_edge(correction_loop, approval)
# Expedite before approval (P4); approval before release (P1/P5)
po.order.add_edge(expedite_opt, approval)
po.order.add_edge(approval, release)

model_third = po  # <-- the main model

# convert + soundness (must be checked, not assumed)
net, im, fm = pm4py.convert_to_petri_net(model_third)
# pm4py.check_soundness(net, im, fm, print_diagnostics=True)
```

Note on `Credit Check`/`Technical Review` reuse inside `recheck_one`: these are label *repetitions* required to express P6's affected-check recheck. That is a *deliberate, bounded* duplicate (only within the correction loop), not C-style enumeration across whole traces.

## 7.3 Declarative dictionaries / external checks

```python
# DECLARE-style constraints checked with a log-scanning function (post-hoc, per trace).
declare_constraints = {
    "existence":   ["Credit Check", "Technical Review"],          # P2
    "exactly_one_of": ["Manager Approval", "Auto Approval"],      # P5
    "precedence":  [("Credit Check", "Expedite Review"),          # P4
                    ("Technical Review", "Expedite Review")],
    "before":      [("Expedite Review", "APPROVAL"),              # P4 (approval = either)
                    ("Register Dossier", "ANY"),                  # P1
                    ("APPROVAL", "Release Order")],               # P1/P5
    "data_conditional_existence": [                               # P3 (needs attribute)
        {"if": ("order.external", True), "require": "Supplier Review"}],
    "response":    [("Correct Dossier", "AFFECTED_RECHECK")],     # P6
    "forbidden":   ["repeated_mandatory_check_without_correction"],  # P7
}

def policy_check(trace, attrs):
    """Return list of violated constraint names. External checks that the
    control-flow model cannot enforce (P3 data-aware, P6 affected-check, P7)."""
    violations = []
    labels = [e["concept:name"] for e in trace]
    # P2
    for a in declare_constraints["existence"]:
        if a not in labels: violations.append(f"missing:{a}")
    # P5 exactly-one approval
    n_appr = sum(labels.count(a) for a in ["Manager Approval", "Auto Approval"])
    if n_appr != 1: violations.append("approval_not_exactly_one")
    # P4 expedite ordering
    if "Expedite Review" in labels:
        i = labels.index("Expedite Review")
        if "Credit Check" not in labels[:i] or "Technical Review" not in labels[:i]:
            violations.append("expedite_before_mandatory")
    # P7 repeated mandatory without preceding correction
    for chk in ["Credit Check", "Technical Review"]:
        idxs = [k for k, l in enumerate(labels) if l == chk]
        for j in idxs[1:]:
            if "Correct Dossier" not in labels[:j]:
                violations.append(f"suspicious_repeat:{chk}")
    # P3 data-aware supplier requirement (only if attribute present)
    if attrs.get("order.external") is True and "Supplier Review" not in labels:
        violations.append("missing_supplier_for_external")
    elif attrs.get("order.external") is None:
        violations.append("UNVERIFIABLE:external_attribute_missing")
    return violations
```

## 7.4 Explicit semantics

- **Mandatory checks:** both present, either order (partial order, no edge between them; declarative `existence` as backstop). *Not* optional — this is the core fix over S.
- **Optional Supplier Review:** `X(Supplier Review, tau)` in the backbone (structurally optional because the external flag is missing), *plus* a data-conditional rule that would make it mandatory for external orders once the attribute exists.
- **Expedite Review ordering:** after *both* mandatory checks, before approval, unordered vs Supplier (P4) — enforced by partial-order edges and a redundant precedence rule.
- **Exactly-one approval:** `X(Manager, Auto)` in the backbone; `exactly_one_of` rule as backstop (P5).
- **Correction/recheck:** bounded loop; after `Correct Dossier`, re-run only-Credit / only-Technical / both (P6). A repeated mandatory check without a preceding correction is outside the backbone language and flagged by the `suspicious_repeat` rule (P7).

## 7.5 Limitations from missing attributes

- **External/internal (P3):** without the attribute, the backbone can only make Supplier Review *optional*; it *cannot* enforce "required iff external." I therefore emit an explicit `UNVERIFIABLE` verdict rather than silently accepting or rejecting. This is a data-collection gap, not a model choice.
- **Affected-check (P6/B6):** without an "affected check" attribute, the model *permits* only-Credit / only-Technical / both rechecks but cannot *verify* that the recheck matches the actual correction. B6's true validity ("valid only if the correction affected Technical alone") is therefore `UNVERIFIABLE` until the attribute is logged; the model does not fabricate a verdict.
- I explicitly do **not** solve missing data by optionalizing everything: only the two genuinely-unobservable obligations (Supplier-if-external, affected-check) are downgraded to optional-plus-flag; all other mandatory semantics remain enforced.

| B4 (Expedite first) | **Yes** | No | No (ordering edges) | forbidden — S wrongly accepts. |
| B5 (Supplier+Expedite+Auto) | Yes | **No** | Yes | valid recombination — C wrongly rejects. |
| B6 (Correct, Tech only) | No | **No** | Yes-but-UNVERIFIABLE | valid iff correction hit Technical; third is honest. |
| B7 (external, Manager) | Yes | Yes | Yes | valid — all correct. |
| B8 (repeat Credit, no correction) | No (wrong reason) | No | No + "suspicious" flag (right reason) | suspicious/forbidden — third gives the right reason. |

**Three adversarial traces I add to distinguish the third alternative:**

- **T1 — Corrected double-recheck of both.** `Register, Credit, Technical, Correct Dossier, Credit, Technical, Manager Approval, Release`. **S:** No (no loop). **C:** Yes (this is C's one correction branch). **Third:** Yes (loop, both-recheck). *Distinguishes:* Third and C both accept the corrected case, but T2/T3 separate them.
- **T2 — Correction affecting only Credit.** `Register, Credit, Technical, Correct Dossier, Credit, Auto Approval, Release`. **S:** No (no Correct node). **C:** **No** (its only correction branch reruns both, and uses Manager not Auto). **Third:** Yes (only-Credit recheck + Auto). *Distinguishes:* Third supports P6's finer-grained recheck and free approval choice; C cannot.
- **T3 — External + Expedite + Auto, Technical-first.** `Register, Technical, Credit, Supplier, Expedite, Auto, Release` (= B5-style). **S:** Yes (but also accepts junk). **C:** **No** (no such branch). **Third:** Yes (partial order permits it) and marks `UNVERIFIABLE:external` if attribute absent. *Distinguishes:* Third generalizes to legitimate recombinations *without* S's over-acceptance.

# 9. Validation Experiments

No new metric *results* are fabricated below; these are the experiments and code skeletons to *produce* them.

- **Reproducible splits.** Publish `random_state`, the exact held-out case IDs, and all preprocessing (filtering, dedup, attribute handling). Run k-fold (k=5) with fixed seeds so holdout drops (like C's 0.973→0.744) can be attributed to split vs model.
- **Attribute-stratified holdout.** Stratify by (external/internal *once collected*), by presence of Expedite, and by approval type, so we test each subpopulation instead of an aggregate that hides F4-type failures.
- **Curated negative suite (fixes F5).** A hand-built set of forbidden traces (B3, B4, S-a…S-e, plus P7 violations). Precision/enforcement is scored as *rejection rate on negatives*, reported separately from positive fitness.
- **Missing-event & duplicate-event perturbation.** Randomly drop Supplier Review (P3) and inject spurious repeats (P7); measure how each model's fitness moves. A model whose fitness *rises* when mandatory events are dropped is penalized.
- **Unseen-combination tests.** Generate legitimate recombinations not in training (playout of the third model's backbone, filtered by `policy_check`) and measure fitness; this is where C should fail and third/S should pass.
- **Alignment-cost sensitivity.** Sweep move-on-model / move-on-log / silent-move costs and report metric ranges, not point values.
- **Soundness & reachability.** `check_soundness` on every converted net; verify no deadlocks and proper completion.
- **Report axes separately.** Fitness, precision (vs positives *and* vs negatives), generalization, simplicity — never a single blended score.
- **Stakeholder comprehension protocol.** Fixed task set (e.g., "is trace X allowed?"), n≥15 blinded raters not on the discovery team, inter-rater agreement reported, comprehension separated from *agreement-with-policy*.
- **Decision rule.** A model is **rejected regardless of aggregate metrics** if it accepts *any* curated negative trace (for enforcement use) OR misrepresents a mandatory step, OR is unsound. Good averages cannot buy back a single accepted forbidden trace.

Code skeletons:

```python
import pm4py

def evaluate(model, log, negatives):
    net, im, fm = pm4py.convert_to_petri_net(model)
    assert pm4py.check_soundness(net, im, fm)[0], "unsound model"
    fit  = pm4py.fitness_alignments(log, net, im, fm)
    prec = pm4py.precision_alignments(log, net, im, fm)          # vs positives
    gen  = pm4py.generalization_tbr(log, net, im, fm)
    simp = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")
    # negative-suite rejection rate (the missing F5 piece):
    neg_diag = pm4py.conformance_diagnostics_alignments(negatives, net, im, fm)
    reject_rate = sum(1 for d in neg_diag if d["fitness"] < 1.0) / len(neg_diag)
    return dict(fitness=fit, precision=prec, generalization=gen,
                simplicity=simp, negative_rejection=reject_rate)

def cost_sensitivity(model, log, cost_grid):
    net, im, fm = pm4py.convert_to_petri_net(model)
    results = {}
    for costs in cost_grid:  # each: dict of move costs
        params = {"align_variant": "state_equation_a_star", **costs}
        results[str(costs)] = pm4py.fitness_alignments(log, net, im, fm, **params)
    return results
```

# 10. Governance Recommendation

- **Model S — exploration only, fenced.** Approve for **U1 (exploration)** and rough **U4 (communication)** *with a printed disclaimer that it does not enforce mandatory checks*. **Reject for U2 (compliance)** unconditionally: it accepts B3, B4, and S-a…S-e. Do not retire it, but demote it and lock it out of any gate.
- **Model C — do not deploy as an allow-list; candidate for retirement.** It rejects legitimate behavior (B2, B5, T3), cannot express P6 (B6, T2), and its precision is an artifact of memorization measured against positives only (F5). It may remain as a *reference catalog of known-frequent variants* but should be retired as a governance model in favor of the third alternative once the latter passes §9.
- **Third alternative — recommended path for U2/U3, pending validation.** Deploy the backbone + declarative/data checks for enforcement and simulation *only after* it meets these conditions:
  1. `check_soundness` passes on the converted net;
  2. 100% rejection on the curated negative suite (B3, B4, S-a…S-e, P7 violations);
  3. positive fitness on attribute-stratified holdout ≥ S's, with the negative-rejection advantage documented;
  4. the external/internal and affected-check attributes are added to the log (or the `UNVERIFIABLE` verdicts are formally accepted by the board as manual-review triggers);
  5. stakeholder comprehension re-measured under the §9 protocol at an acceptable level.
- **Cross-cutting condition:** no model is certified for compliance on the current metrics alone; the negative-suite and reproducible-split experiments are prerequisites for *any* certification.

# 11. Dissenting View

**Rebuttal to my own recommendation (≈210 words).** The third alternative may be over-engineering a problem the business does not have. Its safety rests on a declarative layer and two `UNVERIFIABLE` verdicts that push real decisions onto manual reviewers — arguably worse than a clear, if imperfect, automated answer. Every "UNVERIFIABLE" is operational friction, and reviewers will rubber-stamp them, recreating Model S's permissiveness with extra steps. Meanwhile, Model C's advocate (F8) has a serious point: if this is a closed, regulated process, "unseen behavior is noncompliant until approved" is not overfitting — it is *policy*. Under that reading, C's holdout "degradation" is C doing its job, and B2/B5 rejections are correct pending sign-off. My third model, by *generalizing* to unseen recombinations, may legitimize behavior no one has actually approved. Furthermore, my model reuses `Credit Check`/`Technical Review` labels inside the correction loop — the very duplicate-label pattern I criticized in C — and its partial-order-to-Petri-net conversion could introduce silent-transition alignment quirks I dismissed in S. Simplicity and comprehension (where C scores 1.9) matter for adoption; a POWL-plus-DECLARE-plus-Python stack scores worse than C on maintainability for a non-PM team.

**What would change my mind.** (1) Evidence the process is genuinely closed-world with a formal change-approval workflow → I would favor C's allow-list posture. (2) A negative-suite evaluation showing my third model accepts *any* forbidden trace → I would retract it. (3) Data showing manual `UNVERIFIABLE` reviews are ignored in practice → I would drop the data-conditional layer for a stricter default-deny. (4) Collection of the external/internal and affected-check attributes → this removes the dissent's strongest lever and confirms the third model.
