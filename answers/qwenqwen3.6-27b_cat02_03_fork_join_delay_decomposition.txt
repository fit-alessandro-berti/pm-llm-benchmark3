# 1. Delay-decomposition definitions

Let $c$ index a case and $i \in \{A, B, C\}$ index a branch. All times are in minutes from a common epoch.

| Component | Formula | Interpretation |
|---|---|---|
| `upstream_elapsed` | $U_c = \text{fork\_release}_c - \text{arrival}_c$ | Time before parallel work is permitted |
| `i_queue` | $Q_{c,i} = \text{i\_start}_c - \text{fork\_release}_c$ | Waiting for branch resource after fork |
| `i_service` | $S_{c,i} = \text{i\_end}_c - \text{i\_start}_c$ | Active processing time for branch $i$ |
| `join_ready` | $J_c = \max_i(\text{i\_end}_c)$ | Earliest time all branches are complete |
| `i_sync_wait` | $W_{c,i} = J_c - \text{i\_end}_c$ | Idle time branch $i$ waits for others to finish |
| `fork_join_elapsed` | $FJ_c = J_c - \text{fork\_release}_c$ | Duration of the parallel stage |
| `downstream_queue` | $DQ_c = \text{final\_start}_c - J_c$ | Waiting for final-station resource |
| `final_service` | $FS_c = \text{final\_end}_c - \text{final\_start}_c$ | Active processing at F |
| `total_flow_time` | $TF_c = \text{final\_end}_c - \text{arrival}_c$ | End-to-end case duration |

**Why summing synchronization waits double counts:**  
The synchronization waits $W_{c,A}, W_{c,B}, W_{c,C}$ are *concurrent*, not sequential. By definition, $\max_i W_{c,i} = 0$ (the critical branch finishes exactly at $J_c$). Summing them would count overlapping idle time multiple times. The true elapsed time for the parallel stage is $FJ_c = \max_i(Q_{c,i} + S_{c,i})$, which already absorbs the critical branch's queue+service and implies zero sync wait for that branch. Non-critical branches' sync waits are "wasted" relative to case completion but do not extend $TF_c$.

# 5. Recommended redesigns and risks

**Redesign 1: Stabilize Branch B queueing (dedicated lane or priority routing)**
- *Throughput/Flow-time tail*: Directly targets the primary source of variability. Reducing B queue variance will compress the right tail of `join_ready` and lower P90 flow time.
- *Resource utilization*: B resource utilization may decrease slightly as idle queue time vanishes; monitor to avoid over-provisioning.
- *New bottlenecks*: If B queue drops consistently below ~10 min, A's fixed 50-min service will become critical more often. Consider parallelizing A or staggering fork_release.
- *Synchronization effects*: C's sync wait will increase modestly, but this is harmless idle time.
- *Pilot/Measurement*: Track B arrival patterns at the fork, measure queue drivers (e.g., setup times, material availability), and run a 2-week priority-routing pilot before permanent lane allocation.

**Redesign 2: Decouple final-station congestion with a small buffer or parallel F resource**
- *Throughput/Flow-time tail*: Eliminates downstream queueing variability, making flow time predictable and directly tied to branch completion. Reduces peak waiting times.
- *Resource utilization*: F1/F2 utilization will smooth out; buffer inventory may rise slightly.
- *New bottlenecks*: Branch variability becomes fully visible. If F capacity is increased without addressing B queueing, WIP may accumulate at the fork-join point.
- *Synchronization effects*: No change to branch sync waits, but release policy becomes more transparent.
- *Pilot/Measurement*: Implement a 2-case buffer pool before F, measure WIP aging, and track whether F resource utilization drops below 80%. If so, consider load-balancing branches instead of expanding F.

# 7. Limits of inference

- **Causality of queue delays**: Timestamps show *when* B queues, not *why*. Queueing could stem from shared resources, upstream batching, material shortages, or operator scheduling. Process mining alone cannot isolate root causes.
- **Branch resource capacity**: We observe start/end times but not resource constraints. A, B, and C could share a pool, have dedicated stations, or be human-driven with variable availability. Capacity limits and utilization rates are unobservable without resource logs.
- **Work preemption**: Complete-event timestamps assume continuous processing. If branches are interrupted, resumed, or paused, `service` time overestimates actual work and underestimates hidden waiting.
- **Final-station waiting nature**: `downstream_queue` assumes F1/F2 are resource-constrained queues. Alternatively, waiting could reflect a release policy (e.g., quality gate, batch accumulation, or shift handover). Distinguishing policy-driven delays from capacity-driven congestion requires policy documentation or resource-state logs.
- **Measurement rounding**: One-minute accuracy masks sub-minute variability, which can distort queue/service boundaries in tightly coupled processes.
- **External dependencies**: Branches may depend on external systems (labs, vendors, IT approvals) not captured in the log, meaning observed delays could partially reflect upstream ecosystem constraints rather than internal process design.
