# 1. Equivalence Notions

To formally compare Model A and Model B, we define the following equivalence notions based on explicit observation boundaries and business abstractions. 

- **Visible trace equivalence after hiding `tau`**: Two models are equivalent if their sets of complete visible traces (projected by removing silent `tau` transitions) are identical. Duplicate visible labels are distinguished by their occurrence position in the trace. This is a strictly interleaving semantics view.
- **Bounded visible-language equivalence under P3**: Two models are equivalent if their sets of complete visible traces of length at most 12, containing at most three `'Analyze Revision'` occurrences, and with all `tau` transitions hidden, are identical. Duplicate visible labels are distinguished by occurrence position. Bounded equivalence provides evidence of similarity but does not prove unbounded equivalence.
- **Business-relevant equivalence under P1**: Equivalence is defined by the operational compliance rule: every `'Analyze Revision'` must have its own corresponding `'Check Revision'` before the next `'Rework Case'` or `'Close Case'`. Thus, the number of checks must equal the number of analyses. Duplicate labels are distinguished by their pairing and temporal separation.
- **Abstracted dashboard equivalence under P2**: Equivalence is defined after hiding `'Approve Revision'` and `tau`, and collapsing all `'Check Revision'` occurrences to a single Boolean event "a check occurred". The resulting language consists of `'Open Case'`, followed by interleavings of `'Analyze Revision'` (repeated $n$ times) and `'Rework Case'` (repeated $n-1$ times, strictly separating analyses), followed by `'Close Case'`. Labels are distinguished by activity identity, but the count of checks is ignored.

**Explanation of optional Approve and hidden `tau`:**
The `X('Approve Revision', tau)` block means approval is optional. When `tau` is chosen and hidden, the visible trace skips approval. However, in Model A, the `->(..., X(...))` sequence forces the concurrent block `+(Analyze, Check)` to finish *before* proceeding to the optional approval or loop exit (Rework). Thus, `Check` strictly precedes `Rework` in A. In Model B, the `Check` is lifted outside the loop entirely, allowing it to lazily complete at any time, even after several Reworks. This shifts the language fundamentally.

```python
import pm4py
from collections import deque

def get_bounded_visible_traces(tree, max_len=12, max_analyze=3):
    net, im, fm = pm4py.convert_to_petri_net(tree)
    # BFS over markings
    queue = deque()
    queue.append((im, []))
    visited = set()
    traces = set()
    
    # Helper to serialize marking for visited set
    def marking_to_str(m):
        return tuple(sorted(m.items()))
    
    while queue:
        marking, trace = queue.popleft()
        
        # Check if final marking is reached
        if marking == fm:
            traces.add(tuple(trace))
            continue
            
        state = marking_to_str(marking)
        if state in visited:
            continue
        visited.add(state)
        
        enabled = pm4py.get_enabled_transitions(net, marking)
        for t in enabled:
            # Bounding conditions
            if len(trace) >= max_len:
                continue
            if trace.count('Analyze Revision') >= max_analyze and t.label == 'Analyze Revision':
                continue
            
            new_marking = pm4py.execute_transition(net, marking, t) # if not available, manually compute
            # In some pm4py versions, transition firing is done via petri net semantics:
            # new_marking = utils.petri_utils.add_marking(marking, utils.petri_utils.consume(...))
            # For simplicity in this script, we use a dummy function assuming pm4py handles it,
            # but realistically you need to manually fire transitions in pm4py objects.
            
            # Since standard pm4py lacks a direct 'execute_transition' returning a new marking easily,
            # we use a simulated fire:
            def fire_transition(net, marking, transition):
                new_m = marking.copy()
                for arc in transition.in_arcs:
                    new_m[arc.source] -= 1
                    if new_m[arc.source] == 0:
                        del new_m[arc.source]
                for arc in transition.out_arcs:
                    new_m[arc.target] = new_m.get(arc.target, 0) + 1
                return new_m

            new_marking = fire_transition(net, marking, t)
            
            new_trace = list(trace)
            if t.label is not None and t.label != 'tau' and t.label != 'None':
                new_trace.append(t.label)
                
            queue.append((new_marking, new_trace))
            
    return traces

# Define models
model_a_str = "->( 'Open Case', *( ->( +('Analyze Revision', 'Check Revision'), X('Approve Revision', tau) ), 'Rework Case' ), 'Close Case' )"
model_b_str = "->( 'Open Case', +( 'Check Revision', *( ->( 'Analyze Revision', X('Approve Revision', tau) ), 'Rework Case' ) ), 'Close Case' )"

model_a = pm4py.parse_process_tree(model_a_str)
model_b = pm4py.parse_process_tree(model_b_str)

# Exhaustive BFS bounded exploration
traces_a = get_bounded_visible_traces(model_a)
traces_b = get_bounded_visible_traces(model_b)

unique_a = traces_a - traces_b
unique_b = traces_b - traces_a

print("Traces unique to A (Bounded):")
for t in unique_a:
    print(t)

for t in unique_b:
    print(t)
```

**Why this is insufficient:** Footprints abstract away the exact multiplicity of loops and concurrency boundaries. For instance, both A and B have `'Open Case'` followed by `'Analyze Revision'`, and both have `'Analyze Revision'` and `'Check Revision'` as parallel. Footprints would likely label them as highly similar or identical, failing to capture that A allows multiple checks while B allows only one. 

`pm4py.get_stochastic_language` and `pm4py.compute_emd` could measure distance based on assigned transition probabilities. A low Earth Mover's Distance (EMD) means the trace distributions are similar. However, without explicitly defined transition probabilities (e.g., choosing `tau` vs `Approve` with 50% chance), the language is arbitrary. Even with a low EMD, the existence of structurally impossible traces (like multiple checks in B) means they are not trace equivalent.

```python
import pm4py

def count_tree_metrics(tree_str):
    tree = pm4py.parse_process_tree(tree_str)
    
    def traverse(node, depth=0):
        count = 1
        max_depth = depth
        visible = 0
        silent = 0
        dup_labels = []
        
        if node.label:
            visible = 1
            dup_labels.append(node.label)
        elif node.operator is None: # tau
            silent = 1
            
        for child in node.children:
            c, d, v, s, dl = traverse(child, depth + 1)
            count += c
            max_depth = max(max_depth, d)
            visible += v
            silent += s
            dup_labels.extend(dl)
            
        return count, max_depth, visible, silent, dup_labels

    count, depth, visible, silent, labels = traverse(tree)
    
    from collections import Counter
    duplicates = {k: v for k, v in Counter(labels).items() if v > 1}
    
    return {
        "node_count": count,
        "depth": depth,
        "visible_leaves": visible,
        "silent_leaves": silent,
        "duplicate_labels": duplicates
    }
```

# 9. Final Recommendation

- **For P1 (Operational Compliance):** Only **Model A** is suitable. Model B fails the strict requirement that every analysis must have its own check.
- **For P2 (Executive Dashboard):** Both models are suitable. However, the **Simplified Model** is strongly recommended as it removes the hidden optional behavior (`Approve/tau`) that adds unnecessary complexity to the dashboard view, reducing the node count to 10 and depth to 5.
- **For P3 (Bounded Testing):** Neither model is interchangeable. Testing should use the specific model that corresponds to the actual system architecture (either check-per-iteration or check-per-case).

**Warning on Bounded Comparison:** 
Bounded comparison (as performed in the P3 view) is a heuristic testing technique, not a formal proof of equivalence. While it guarantees that no counterexamples exist within the specified bounds (e.g., $\le 12$ events), infinite-state systems like loops may exhibit divergent behavior outside these bounds. Structural or semantic abstractions (like footprints or language projections) must be used to prove unbounded equivalence, as bounded exploration alone is insufficient.
