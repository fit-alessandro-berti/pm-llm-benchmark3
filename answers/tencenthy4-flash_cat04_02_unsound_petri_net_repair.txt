# 1. Executive Verdict

The net is structurally a workflow net: source and sink are unique and every node lies on some source-to-sink path. It should not be expected to be sound, and it is not sound. The principal defect is the waiver synchronization: `t_join_waived` consumes only `p_waived`, so a waiver token creates `p_decision` without waiting for or consuming the analysis token. After `t_register`, `t_split`, `t_waive_review`, and the silent waiver join, both `t_analyze` and `t_authorize` are enabled. Authorization can therefore occur before mandatory analysis; if analysis fires later its token becomes `p_analysis_done` with no usable outgoing path. The net can reach `sink` plus a leftover token, so exact `fm` is not guaranteed.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `t_register`, `p_ready`, `t_split` | Register one case and fork analysis and review in parallel. | Correct AND-split: after `t_split`, one token is in `p_analysis` and one in `p_review`. | Parallel tokens are created as intended; the defect is downstream. |
| `p_analysis`, `t_analyze`, `p_analysis_done` | Mandatory analysis branch; `p_analysis_done` should witness that analysis is complete. | Structurally produces the analysis-completion token. | `p_review`, `t_standard_review`, `p_review_done` | Standard review outcome. | Correctly consumes the review token and produces `p_review_done`, one input of `t_join_normal`. | Standard path can synchronize with analysis via `t_join_normal`. |
| `p_review`, `t_waive_review`, `p_waived` | Formally recorded waiver outcome, alternative to standard review. | Correctly consumes the same `p_review` token, so standard and waiver are locally exclusive. But `p_waived` feeds a one-input `t_join_waived`. | Waiver can produce `p_decision` without analysis. |
| `t_join_normal` | Join analysis completion and standard review completion. | Actual two-input synchronization: `p_analysis_done` and `p_review_done`. Fires to `p_decision`. | Correct for standard review cases. |

# 4. Minimal-Repair Alternatives

Edit-cost model:

- Add or remove one arc: cost `1`.
- Add or remove one place: cost `1`.
- Add or remove one transition: cost `1`.
- Redirecting an arc is counted as removal plus addition: cost `2`.
- Renaming visible labels is not used.
- A repair is minimal if no edit can be removed while preserving the stated behavior of that repair.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| **R1: proper two-input waiver join** | Add arc `p_analysis_done -> t_join_waived`. | `1` | Yes. Analysis remains mandatory on waiver path; standard and waiver remain internally distinguishable by `p_review_done` vs `p_waived`. | `t_join_waived` is enabled only after both waiver and analysis completion. `t_authorize` cannot fire with `p_analysis` or `p_analysis_done` left. | `p_analysis_done` is shared by `t_join_normal` and `t_join_waived`; correctness relies on `p_review` being consumed by exactly one review transition. |
| **R2: collapse waiver into common review synchronization** | Add `t_waive_review -> p_review_done`; remove `t_waive_review -> p_waived`; remove `p_waived -> t_join_waived`; remove `t_join_waived -> p_decision`; remove transition `t_join_waived`; remove place `p_waived`. | `6` | Mostly. Analysis remains mandatory because `t_join_normal` still needs `p_analysis_done`; waiver remains visible through transition label if labels are logged. | Waiver no longer has a distinct token place or silent join. All cases use `t_join_normal`. | If the waiver label is hidden or not persisted, the waiver variant becomes invisible after review. Reduced auditability. |
| **R3: explicit policy change — analysis optional under waiver** | Add transition `t_skip_analysis_for_waiver`; add arcs `p_analysis -> t_skip_analysis_for_waiver`, `p_waived -> t_skip_analysis_for_waiver`, `t_skip_analysis_for_waiver -> p_decision`; also add `p_analysis_done -> t_join_waived`. | `5` | No: deliberately changes policy. Standard review still requires analysis, but waiver may skip it. | Waiver-without-analysis traces become accepted. The skip transition consumes both the analysis wait token and the waiver token, so it leaves no branch token behind. | Compliance risk: if the skip transition is silent, an analysis bypass is not visible in the event log. This should only be deployed after explicit policy approval. |

Minimality justification:

- **R1 is globally minimal among policy-preserving repairs.** With zero edits the defect remains. At least one enabling condition must change. Adding `p_analysis_done -> t_join_waived` is one arc and is sufficient. Other one-edit changes either leave the bypass, break standard completion, or introduce a new deadlock.
- **R2 is minimal for the common-join behavior.** To route waiver through `t_join_normal`, waiver must produce `p_review_done`; the old `p_waived` output must be removed; and the obsolete `p_waived`/`t_join_waived` bypass, including incident arcs, must be removed to keep a workflow net.
- **R3 is minimal for the explicitly changed optional-analysis policy.** A new skip behavior needs a transition and at least three arcs to consume `p_analysis` and `p_waived` and produce `p_decision`; preserving the firing order where `t_analyze` happens first additionally requires `p_analysis_done -> t_join_waived`.
- There is no cost tie among these repairs.

repaired_im[source] = 1

import pm4py
from pm4py.objects.petri_net.obj import Marking


def clone_marking(marking):
    cloned = Marking()
    for place, tokens in marking.items():
        if tokens:
            cloned[place] = tokens
    return cloned


def enabled_names(net, marking):
    return sorted(t.name for t in pm4py.get_enabled_transitions(net, marking))


def marking_text(net, marking):
    parts = []
    for p in sorted(net.places, key=lambda x: x.name):
        if marking.get(p, 0):
            parts.append(f"{p.name}:{marking[p]}")
    return "{" + (", ".join(parts) if parts else "empty") + "}"


def print_marking(label, net, marking):
    print(f"{label}: {marking_text(net, marking)}; enabled={enabled_names(net, marking)}")


def fire_named(net, marking, transition_name):
    transition = next((t for t in net.transitions if t.name == transition_name), None)
    if transition is None:
        raise ValueError(f"No transition named {transition_name}")

    enabled = pm4py.get_enabled_transitions(net, marking)
    if transition not in enabled:
        raise RuntimeError(
            f"Cannot fire {transition_name}; enabled={enabled_names(net, marking)}"
        )

    for arc in transition.in_arcs:
        place = arc.source
        amount = getattr(arc, "weight", 1)
        if amount is None:
            amount = 1
        marking[place] = marking.get(place, 0) - amount
        if marking[place] == 0:
            del marking[place]

    for arc in transition.out_arcs:
        place = arc.target
        amount = getattr(arc, "weight", 1)
        if amount is None:
            amount = 1
        marking[place] = marking.get(place, 0) + amount

    return marking

# 7. Repair Trade-Offs and Residual Risks

- **Waiver vs standard distinguishability:** R1 preserves it. Standard cases produce `p_review_done`; waiver cases produce `p_waived`. The silent transitions `t_join_normal` and `t_join_waived` remain separate. After `t_authorize`, however, both variants converge at `sink`, so long-term distinction depends on logged visible labels.
- **Silent-transition confusion:** The joins are not visible in event logs. A visible trace such as `Register Case`, `Record Review Waiver`, `Perform Analysis`, `Authorize Case` will not show whether the silent join occurred correctly. Replay/conformance must therefore rely on the net model, not just visible trace ordering.
- **Shared `p_analysis_done`:** In R1, `p_analysis_done` can feed either join. This is safe in the intended net because `p_review` is consumed either by `t_standard_review` or by `t_waive_review`, so only one review outcome token exists. If external code injects duplicate tokens, a wrong join could leave a review-outcome token behind.
- **Soundness is not enough:** A sound model can still encode the wrong policy. For example, R3 would also be sound but intentionally allows analysis to be skipped under waiver. Soundness checks token completion properties; it does not prove that “Perform Analysis” is mandatory or that “Record Review Waiver” has the intended compliance meaning.
- **Positive traces to regression-test:**
  - `Register Case`, `Perform Analysis`, `Perform Standard Review`, `Authorize Case`.
  - `Register Case`, `Perform Standard Review`, `Perform Analysis`, `Authorize Case`.
  - `Register Case`, `Perform Analysis`, `Record Review Waiver`, `Authorize Case`.
  - `Register Case`, `Record Review Waiver`, `Perform Analysis`, `Authorize Case`.
- **Negative traces to regression-test:**
  - `Register Case`, `Perform Standard Review`, `Authorize Case` — no analysis.
  - `Register Case`, `Record Review Waiver`, `Authorize Case` — no analysis.
  - `Register Case`, `Authorize Case` — no review outcome.
  - `Register Case`, `Record Review Waiver`, `Perform Standard Review`, `Authorize Case` — impossible second review branch.
- **Detecting accidental bypass of mandatory analysis:** Check reachability for any marking where `p_decision` or `sink` is marked while `p_analysis` or `p_analysis_done` is also marked. Also check that every transition path from `p_waived` to `p_decision` passes through `p_analysis_done`. In the repaired net, `p_decision` should only be reached after `p_analysis_done` has been consumed by a join.

# 8. Final Recommendation

Deploy **R1**, the one-arc repair adding `p_analysis_done -> t_join_waived`. It is the smallest possible policy-preserving correction, keeps waiver and standard review structurally distinguishable, and directly enforces the rule that authorization follows both analysis completion and the selected review outcome. It also preserves all visible labels and the original model structure.

Use **R2** as a fallback if the organization prefers a single common synchronization point and does not need `p_waived` as an explicit audit state. R2 is more invasive but conceptually simple: both review outcomes feed `p_review_done`, and only `t_join_normal` authorizes.

Do **not** deploy R3 unless the business explicitly approves changing the policy to make analysis optional under waiver. Soundness would not make that policy change acceptable.
