## 1. Duplicate-handling decision tree

Start with candidate groups, not with global duplicate removal. Candidate groups are created from: exact source keys, same canonical activity, same timestamp, overlapping related objects, original source activity, payload hashes, ingestion time, and external reconciliation keys.

1. **Exact technical duplicate?**  
   Same source, same `source_event_key`, same payload hash, same timestamp, same related objects.
   - **If fully identical:** drop the secondary technical copy; retain one canonical event; preserve duplicate IDs in provenance.
   - **If key/payload conflict exists:** quarantine for review; do not silently drop.

2. **Same physical event observed by multiple systems?**  
   Supported by reconciliation, same natural business key, same discriminating objects, explainable payload differences.
   - **Decision:** merge attributes and relations into one canonical event; retain source-level provenance.  
   - Example: e03/e04.

3. **Summary event derived from a detailed event?**  
   One event is a later, coarser status update generated from another system’s detailed transaction; fewer objects or fewer attributes.
   - **Conservative decision:** retain both with refined labels or qualifiers.
   - **Evidence-based optional decision:** merge only when the analytical view explicitly wants one business transition and derivation is proven.
   - **If derivation is uncertain:** quarantine or retain both as unresolved candidates.  
   - Examples: e06/e07, e13/e15, e14/e15.

4. **Harmonization collision between semantically distinct source activities?**  
   Same canonical label but different original activities or known different business meanings.
   - **Decision:** retain both with refined labels or qualifiers; if mapping is clearly wrong, quarantine for remapping.  
   - Example: e08/e09.

5. **Concurrent same-label events involving different objects?**  
   Same activity and timestamp, but discriminating child objects differ, such as item or payment identifiers.
   - **Decision:** retain both unchanged or with object-specific qualifiers. Do not merge.  
   - Examples: e03/e05, e13/e14.

6. **Unresolved candidate?**  
   Overlapping objects and labels but insufficient evidence.
   - **Decision:** quarantine for review, or retain both with a candidate-duplicate flag. Do not delete.

## 3. Timestamp-tie ordering rules

The pipeline should convert a partial order into a deterministic total order only after semantic evidence has been applied. The rules are prioritized as follows.

1. **Domain constraints — semantic.**  
   Explicit business precedence: e12 must precede e13 for payment M1; e09 precedes e10; picks precede pack for the picked items; pack precedes dispatch; dispatch precedes delivery confirmation; e15 is generated after payment messages.

2. **Within-source sequence — semantic/deterministic evidence.**  
   `source_seq` is meaningful only inside one source. It can order scanner e04 before e05, PSP e12 before e13 before e14, carrier e09 before e10, and ERP e11 before e15. It is not comparable across sources.

3. **Lifecycle constraints on shared objects — semantic.**  
   Object state transitions constrain order: Item picked before Package packed; Package packed before Dispatch; Invoice issued before payment capture if accepted as business policy; Payment authorized before capture.

4. **Source-specific semantics — semantic.**  
   ERP e07 is a status derived from WMS e06; ERP e15 is a summary after PSP payment messages; carrier acceptance differs from warehouse release.

5. **Ingestion time — deterministic only.**  
   `ingested_at` may be used only as a late tie-breaker after semantic and source-sequence rules. It must not be treated as business time.

6. **Stable fallback order — deterministic only.**  
   If all semantic evidence is exhausted, use a stable hash or lexicographic order of `source`, `source_event_key`, and `eid`. This guarantees reproducibility, not truth.

Adding microseconds before deciding the semantic order is dangerous because process-mining algorithms interpret timestamp order as behavior. Synthetic subsecond differences turn true concurrency or unknown ordering into a false precise sequence. That can create artificial loops, false precedence, and distorted waiting times.

Intended conservative orders:

- **10:00 group, e03–e07:**  
  Deterministic intended order: e03  e05  e06  e07.  
  e03 and e05 are semantically concurrent picks, but e03 is chosen first because merged scanner provenance includes e04 with sequence 551 before e05 sequence 552. e06 precedes e07 because e07 is derived from the WMS pack message. An admissible alternative allows e03/e05 to swap.

- **10:15 group, e08–e10:**  
  Deterministic intended order: e08  e09  e10.  
  e09 before e10 is semantic. e08 before e09 is lifecycle-based if warehouse release must precede carrier acceptance; otherwise they are concurrent and the order is deterministic only.

- **12:00 group after duplicate decisions:**  
  e16 is merged into e11. Deterministic intended order: e11  e12  e13  e14  e15.  
  e12 before e13 is semantic. e13/e14 are distinct payment captures; their order is deterministic by PSP sequence, not by business necessity. e15 follows e13/e14 because it is an ERP summary generated after payment messages. An admissible alternative allows e13/e14 to swap and, if invoice-before-payment is not accepted, allows e11 to be concurrent with payment events.

## 4. Conservative cleaning pipeline

The conservative pipeline performs minimum change and avoids semantic deletion.

1. Snapshot the raw OCEL and work only on deep copies.
2. Preserve original fields: `original_timestamp`, `original_activity`, `source`, `source_event_key`, `source_seq`, `ingested_at`, `payload_hash`, and original related objects.
3. Generate candidate duplicate groups and inspect them before any removal.
4. Remove or merge only strongly supported duplicates:
   - merge e03/e04 as one verified physical pick;
   - merge e11/e16 as one verified invoice issuance.
5. Preserve abstraction-level events:
   - keep e06 and e07 separate, with qualifiers such as `Pack Package (WMS detail)` and `Pack Package (ERP summary)`;
   - keep e15 separate as `Capture Payment (ERP invoice summary)`;
   - keep e08 and e09 separate as `Dispatch Package (Warehouse Release)` and `Dispatch Package (Carrier Acceptance)`.
6. Refine harmonized labels where justified, but keep original labels.
7. Apply semantic partial ordering, then deterministic fallback ordering.
8. Store concurrency flags and ordering reasons. A synthetic adjusted timestamp may be added for technical sorting, but the original timestamp remains unchanged.
9. Validate referential integrity and write an audit log.

Expected retained event count: **15**.  
Retained canonical events: e01, e02, e03, e05, e06, e07, e08, e09, e10, e11, e12, e13, e14, e15, e17.  
Removed or merged away: e04 into e03, e16 into e11. e05 and e14 are explicitly retained.

## 5. Aggressive alternatives

### Scenario A: Evidence-based semantic merging

This scenario merges only where there is stronger business evidence that two records represent one business transition at the desired analysis granularity.

Merges:

- e03/e04: verified same physical scan.
- e11/e16: verified same invoice issuance.
- e06/e07: WMS detailed pack and ERP pack status are treated as one business packing transition.

Expected retained event count: **14**.

Likely semantic damage:

- The ERP packing status loses its independent abstraction-level existence.
- ERP-to-WMS latency becomes invisible.
- If analysts need to distinguish warehouse execution from ERP status propagation, the merged event hides that gap.
- e08/e09 should still not be merged because warehouse release and carrier acceptance are different lifecycle steps.

### Scenario B: Mechanically aggressive PM4Py merging

This scenario mimics a library merge using canonical activity, timestamp, and possibly object overlap, without verified pair review. If `have_common_object=True` is used, events can be merged merely because they share some objects.

Likely merges:

- e03/e04/e05 merged because all share O1 and P1.
- e06/e07 merged.
- e08/e09 merged.
- e11/e16 merged.
- e13/e14/e15 merged because all share O1 and V1.

Expected retained event count: approximately **10**, depending on library behavior.

Most likely semantic damage:

- e05 is absorbed into a generic pick, hiding the second item pick.
- e14 is absorbed into a generic capture, hiding the partial payment M2.
- e08/e09 merging conflates warehouse release and carrier acceptance.
- e15 merging makes an ERP invoice-level summary look like an actual PSP capture.
- Object cardinality is distorted: one capture event may appear to settle two payments.

`have_common_object=True` is not sufficient to protect e13 and e14. They share O1 and V1, but they represent different Payment objects, M1 and M2. A common-object test sees overlap and may incorrectly infer duplication. Duplicate detection must check discriminating child objects, source event keys, amounts, payment identifiers, and payload semantics. Shared parent objects are evidence of relation, not evidence of duplicate event identity.

## 6. PM4Py-oriented Python implementation

```python
import copy
import warnings
import datetime as dt
import pandas as pd
import pm4py

EVENT_ID = "ocel:eid"
ACTIVITY = "ocel:activity"
TIMESTAMP = "ocel:timestamp"

PROTECTED_COLUMNS = {
    EVENT_ID,
    TIMESTAMP,
    ACTIVITY,
    "original_timestamp",
    "original_activity",
    "original_source",
    "original_source_event_key",
    "original_source_seq",
    "original_ingested_at",
    "original_payload_hash",
    "original_related_objects",
}


def _as_list(value):
    if value is None:
        return []
    if isinstance(value, (list, tuple, set)):
        return list(value)
    return [value]


def _is_missing(value):
    try:
        return pd.isna(value)
    except Exception:
        return value is None


def normalize_columns(ocel):
    rename_map = {
        "eid": EVENT_ID,
        "activity": ACTIVITY,
        "timestamp": TIMESTAMP,
    }
    ocel.events = ocel.events.rename(
        columns={k: v for k, v in rename_map.items() if k in ocel.events.columns}
    )
    return ocel


def preserve_originals(ocel):
    ev = ocel.events.copy()

    ev["original_timestamp"] = pd.to_datetime(ev[TIMESTAMP])
    ev["original_activity"] = ev[ACTIVITY]
    ev["original_source"] = ev["source"]
    ev["original_source_event_key"] = ev["source_event_key"]
    ev["original_source_seq"] = ev["source_seq"]
    ev["original_ingested_at"] = ev["ingested_at"]
    ev["original_payload_hash"] = ev["payload_hash"]
    ev["original_related_objects"] = ev["related_objects"].apply(
        lambda objects: tuple(sorted(_as_list(objects)))
    )

    ev["merged_from"] = ev[EVENT_ID].apply(lambda eid: [eid])
    ev["source_event_keys"] = ev.apply(
        lambda row: [(row["source"], row["source_event_key"])], axis=1
    )
    ev["payload_hashes"] = ev["payload_hash"].apply(lambda h: [h])
    ev["attribute_conflicts"] = [{} for _ in range(len(ev))]

    ocel.events = ev
    return ocel


def precheck_candidate_groups(ocel):
    ev = ocel.events.copy()
    ev["object_set"] = ev["related_objects"].apply(lambda x: frozenset(_as_list(x)))

    exact = (
        ev.groupby(["source", "source_event_key", "payload_hash"])[EVENT_ID]
        .apply(list)
        .reset_index()
    )
    exact = exact[exact[EVENT_ID].apply(len) > 1]

    same_label_time = (
        ev.groupby([ACTIVITY, TIMESTAMP])[EVENT_ID]
        .apply(list)
        .reset_index()
    )
    same_label_time = same_label_time[same_label_time[EVENT_ID].apply(len) > 1]

    same_label_time_objects = (
        ev.groupby([ACTIVITY, TIMESTAMP, "object_set"])[EVENT_ID]
        .apply(list)
        .reset_index()
    )
    same_label_time_objects = same_label_time_objects[
        same_label_time_objects[EVENT_ID].apply(len) > 1
    ]

    return {
        "exact_technical_duplicates": exact.to_dict(orient="records"),
        "same_activity_timestamp_groups": same_label_time.to_dict(orient="records"),
        "same_activity_timestamp_object_groups": same_label_time_objects.to_dict(
            orient="records"
        ),
    }


def merge_verified_events(ocel, canonical_eid, duplicate_eids, rule_name, log=None):
    ev = ocel.events.copy()
    duplicate_eids = list(duplicate_eids)

    canonical_mask = ev[EVENT_ID] == canonical_eid
    duplicate_mask = ev[EVENT_ID].isin(duplicate_eids)

    if not canonical_mask.any() or not duplicate_mask.any():
        return ocel

    canonical_idx = ev[canonical_mask].index[0]

    for dup_idx in ev[duplicate_mask].index:
        dup = ev.loc[dup_idx]

        for col in ev.columns:
            if col in PROTECTED_COLUMNS or col == "related_objects":
                continue

            canonical_value = ev.at[canonical_idx, col]
            duplicate_value = dup[col]

            if _is_missing(canonical_value) and not _is_missing(duplicate_value):
                ev.at[canonical_idx, col] = duplicate_value
            elif (
                not _is_missing(canonical_value)
                and not _is_missing(duplicate_value)
                and str(canonical_value) != str(duplicate_value)
            ):
                conflicts = ev.at[canonical_idx, "attribute_conflicts"]
                if not isinstance(conflicts, dict):
                    conflicts = {}
                conflicts[col] = {
                    "canonical": canonical_value,
                    "duplicate": duplicate_value,
                    "duplicate_eid": dup[EVENT_ID],
                    "rule": rule_name,
                }
                ev.at[canonical_idx, "attribute_conflicts"] = conflicts

        merged_objects = set(_as_list(ev.at[canonical_idx, "related_objects"])) | set(
            _as_list(dup["related_objects"])
        )
        ev.at[canonical_idx, "related_objects"] = sorted(merged_objects)

        ev.at[canonical_idx, "merged_from"] = sorted(
            set(_as_list(ev.at[canonical_idx, "merged_from"]) + [dup[EVENT_ID]])
        )

        existing_keys = _as_list(ev.at[canonical_idx, "source_event_keys"])
        existing_keys.append((dup["source"], dup["source_event_key"]))
        ev.at[canonical_idx, "source_event_keys"] = sorted(set(existing_keys))

        ev.at[canonical_idx, "payload_hashes"] = sorted(
            set(_as_list(ev.at[canonical_idx, "payload_hashes"]) + [dup["payload_hash"]])
        )

        if hasattr(ocel, "relations") and ocel.relations is not None:
            rel = ocel.relations.copy()
            rel.loc[rel[EVENT_ID] == dup[EVENT_ID], EVENT_ID] = canonical_eid
            ocel.relations = rel.drop_duplicates()

    ocel.events = ev[~duplicate_mask].copy()

    if log is not None:
        log.append(
            {
                "canonical_eid": canonical_eid,
                "merged_eids": duplicate_eids,
                "rule_name": rule_name,
                "timestamp": dt.datetime.utcnow().isoformat(),
            }
        )

    return ocel


def refine_event(ocel, eid, refined_activity, qualifier):
    mask = ocel.events[EVENT_ID] == eid
    ocel.events.loc[mask, ACTIVITY] = refined_activity
    ocel.events.loc[mask, "activity_qualifier"] = qualifier
    return ocel


def apply_known_order(ocel, ordered_eids):
    rank = {eid: idx for idx, eid in enumerate(ordered_eids)}
    ocel.events["order_rank"] = (
        ocel.events[EVENT_ID].map(rank).fillna(999999).astype(int)
    )
    ocel.events["order_reason"] = ocel.events[EVENT_ID].map(
        lambda eid: "semantic_plus_deterministic" if eid in rank else "stable_fallback"
    )
    ocel = pm4py.ocel_sort_by_additional_column(ocel, "order_rank")
    return ocel


def add_synthetic_tiebreak(ocel):
    # Original timestamp must already be preserved.
    ocel.events["pre_synthetic_timestamp"] = ocel.events[TIMESTAMP]
    ocel = pm4py.ocel_add_index_based_timedelta(ocel, dt.timedelta(microseconds=1))
    ocel.events["adjusted_timestamp"] = ocel.events[TIMESTAMP]
    return ocel


def validate_referential_integrity(ocel, scenario_name):
    ev = ocel.events
    problems = []

    if ev[EVENT_ID].duplicated().any():
        problems.append("duplicate event identifiers remain")

    known_objects = set()
    if hasattr(ocel, "objects") and ocel.objects is not None:
        oid_col = (
            "ocel:oid"
            if "ocel:oid" in ocel.objects.columns
            else ocel.objects.columns[0]
        )
        known_objects = set(ocel.objects[oid_col])

    for _, row in ev.iterrows():
        for oid in _as_list(row.get("related_objects", [])):
            if known_objects and oid not in known_objects:
                problems.append(f"unknown object {oid} referenced by {row[EVENT_ID]}")

    return {
        "scenario": scenario_name,
        "valid": len(problems) == 0,
        "problems": problems,
    }


# Independent scenario copies; ocel_raw is not modified.
ocel_conservative = copy.deepcopy(ocel_raw)
ocel_evidence = copy.deepcopy(ocel_raw)
ocel_aggressive = copy.deepcopy(ocel_raw)

merge_log = []

for scenario in [ocel_conservative, ocel_evidence, ocel_aggressive]:
    normalize_columns(scenario)
    preserve_originals(scenario)

candidate_report = precheck_candidate_groups(ocel_conservative)

# Conservative scenario: exact technical deduplication only.
# Justified because the key includes source, source_event_key, and payload_hash.
ocel_conservative = pm4py.ocel_drop_duplicates(
    ocel_conservative,
    attr_names=["source", "source_event_key", "payload_hash"],
)

# Conservative verified pair merges.
ocel_conservative = merge_verified_events(
    ocel_conservative,
    canonical_eid="e03",
    duplicate_eids=["e04"],
    rule_name="verified_physical_scan",
    log=merge_log,
)

ocel_conservative = merge_verified_events(
    ocel_conservative,
    canonical_eid="e11",
    duplicate_eids=["e16"],
    rule_name="verified_invoice_issuance",
    log=merge_log,
)

# Conservative label refinement.
ocel_conservative = refine_event(
    ocel_conservative, "e03", "Pick Item", "verified WMS+Scanner"
)
ocel_conservative = refine_event(
    ocel_conservative, "e05", "Pick Item", "scanner distinct I2"
)
ocel_conservative = refine_event(
    ocel_conservative, "e06", "Pack Package", "WMS detail"
)
ocel_conservative = refine_event(
    ocel_conservative, "e07", "Pack Package", "ERP summary"
)
ocel_conservative = refine_event(
    ocel_conservative, "e08", "Dispatch Package", "warehouse release"
)
ocel_conservative = refine_event(
    ocel_conservative, "e09", "Dispatch Package", "carrier acceptance"
)
ocel_conservative = refine_event(
    ocel_conservative, "e13", "Capture Payment", "PSP M1"
)
ocel_conservative = refine_event(
    ocel_conservative, "e14", "Capture Payment", "PSP M2"
)
ocel_conservative = refine_event(
    ocel_conservative, "e15", "Capture Payment", "ERP invoice summary"
)
ocel_conservative = refine_event(
    ocel_conservative, "e11", "Issue Invoice", "verified ERP+Billing"
)

conservative_order = [
    "e01", "e02", "e03", "e05", "e06", "e07",
    "e08", "e09", "e10", "e11", "e12",
    "e13", "e14", "e15", "e17",
]

ocel_conservative = apply_known_order(ocel_conservative, conservative_order)
ocel_conservative = add_synthetic_tiebreak(ocel_conservative)

# Evidence-based scenario: merge verified pairs plus derived pack summary.
ocel_evidence = merge_verified_events(
    ocel_evidence,
    canonical_eid="e03",
    duplicate_eids=["e04"],
    rule_name="verified_physical_scan",
    log=merge_log,
)

ocel_evidence = merge_verified_events(
    ocel_evidence,
    canonical_eid="e11",
    duplicate_eids=["e16"],
    rule_name="verified_invoice_issuance",
    log=merge_log,
)

ocel_evidence = merge_verified_events(
    ocel_evidence,
    canonical_eid="e06",
    duplicate_eids=["e07"],
    rule_name="derived_pack_summary_merge",
    log=merge_log,
)

evidence_order = [
    "e01", "e02", "e03", "e05", "e06",
    "e08", "e09", "e10", "e11", "e12",
    "e13", "e14", "e15", "e17",
]

ocel_evidence = apply_known_order(ocel_evidence, evidence_order)
ocel_evidence = add_synthetic_tiebreak(ocel_evidence)

# Aggressive scenario: library merge with explicit warning.
warnings.warn(
    "Aggressive PM4Py merge is destructive. It may merge e03/e05, e13/e14, "
    "and e13/e15 because of shared activity, timestamp, or parent objects.",
    UserWarning,
)

# Do NOT rely on have_common_object=True as a duplicate proof.
ocel_aggressive = pm4py.ocel_merge_duplicates(
    ocel_aggressive,
    attr_names=[ACTIVITY, TIMESTAMP],
)

ocel_aggressive.events = ocel_aggressive.events.sort_values(
    [TIMESTAMP, "original_source", "original_source_event_key", EVENT_ID]
).reset_index(drop=True)

ocel_aggressive.events["order_rank"] = ocel_aggressive.events.index
ocel_aggressive = pm4py.ocel_sort_by_additional_column(ocel_aggressive, "order_rank")
ocel_aggressive = add_synthetic_tiebreak(ocel_aggressive)

integrity_reports = [
    validate_referential_integrity(ocel_conservative, "conservative"),
    validate_referential_integrity(ocel_evidence, "evidence_based"),
    validate_referential_integrity(ocel_aggressive, "aggressive_library"),
]

summary = {
    "candidate_report": candidate_report,
    "merge_log": merge_log,
    "event_counts": {
        "raw": len(ocel_raw.events),
        "conservative": len(ocel_conservative.events),
        "evidence_based": len(ocel_evidence.events),
        "aggressive": len(ocel_aggressive.events),
    },
    "integrity_reports": integrity_reports,
}
```

## 7. Sensitivity analysis

Expected approximate counts:

| Dataset | Event count | E2O relation count | Main effect |
|---|---:|---:|---|
| Raw | 17 | 44 | All observations retained, including duplicates and abstraction-level events |
| Conservative | 15 | 39 | Removes only verified duplicates; preserves abstraction and concurrency |
| Evidence-based merge | 14 | 37 | Also merges derived pack summary; reduces abstraction-level duplication |
| Aggressive library merge | ~10 | ~28 | Collapses concurrent and summary events based on label/time/object overlap |

**Order-flattened DFG for Order O1**  
Raw O1 contains all events, so the flattened case can show repeated Pack, repeated Dispatch, and repeated Capture activities. Conservative still shows e06/e07 and e08/e09 as separate refined steps, but removes duplicate pick and duplicate invoice. Evidence-based removes the Pack duplication. Aggressive flattening looks cleaner but hides distinct business steps.

**Item-flattened DFG**  
Raw I1 has both e03 and e04 before e06, making the I1 pick appear duplicated. Conservative fixes this by merging e03/e04. I2 remains visible through e05. Aggressive merging may merge e03/e04/e05 into one Pick event connected to both I1 and I2, destroying the item-level distinction.

**Payment-flattened DFG**  
Conservative retains M1 as Authorize Payment  Capture Payment and M2 as Capture Payment only. e15 is not attached to M1 or M2, correctly reflecting that it is invoice-level. Aggressive merging may create one Capture Payment event connected to both M1 and M2, falsely suggesting one payment operation covered both partial payments.

**OC-DFG edges and frequency metrics**  
Raw frequencies overstate repeated observations. Conservative reduces duplicate frequencies. Aggressive reduces frequencies by collapsing distinct events, which can make rare behavior appear singular and hide process variants.

**ET–OT weights**  
Event-type-to-object-type weights change materially. For example, Pick Item–Item weight drops from three raw pick-item observations to two conservative observations. Capture Payment–Payment weight changes from two separate capture-payment relations to potentially one merged capture event connected to two payments in the aggressive scenario.

**OTG relations**  
Object-type graph cardinalities change. Aggressive merging can make one Capture Payment event connect Invoice V1 to both Payment M1 and Payment M2, changing the apparent Invoice-Payment settlement pattern. It can also make one Pick Item event connect Order O1 to both Items I1 and I2, hiding separate pick operations.

**Apparent rework or loops**  
Raw and conservative datasets may show apparent repeated activities. These are often abstraction-level duplicates, not true rework. Aggressive merging removes the repeats but by deleting semantics rather than explaining them.

**Lifecycle and performance measurements**  
Merging e06/e07 removes the ERP status delay. Merging e13/e14/e15 removes payment-summary latency. Synthetic microseconds can create false subsecond durations between events that were truly concurrent.

Concrete edges or patterns whose interpretation changes:

1. `Pick Item  Pack Package` on I1/P1: raw shows duplicate pick pressure; conservative shows one verified pick.
2. `Pack Package  Pack Package` or repeated Pack in Order flattening: abstraction duplication, not necessarily rework.
3. `Dispatch Package  Dispatch Package`: raw/conservative may look like duplicate dispatch; refined labels reveal warehouse release followed by carrier acceptance.
4. `Dispatch Package  Handover to Carrier`: depends on whether e09 or e08 is ordered before e10.
5. `Authorize Payment  Capture Payment` for M1: preserved in conservative; distorted if aggressive merge attaches authorization to a merged multi-payment capture.
6. `Capture Payment  Capture Payment`: raw/conservative shows multiple captures or summary; aggressive collapses partial payments.
7. `Issue Invoice  Authorize Payment`: frequency changes after merging e11/e16.
8. `Pick Item  Pick Item` concurrency for I1/I2: preserved conservatively; lost aggressively.

## 8. Audit trail and reversibility

Provenance should be stored in an append-only table, for example `event_provenance`.

Fields:

- `canonical_eid`
- `source_eids`
- `merge_rule`
- `rule_version`
- `reviewer_or_automatic_engine`
- `original_activity`
- `refined_activity`
- `original_timestamp`
- `adjusted_timestamp`
- `timestamp_adjustment_reason`
- `ordering_reason`
- `attributes_retained_by_source`
- `discarded_or_conflicting_attributes`
- `relations_added`
- `relations_removed`
- `confidence`
- `reason_text`

For merged events, the canonical event stores the list of merged source event IDs. The original attribute values from each source are retained in a JSON-like field, not overwritten. Conflicting attributes are stored side by side with source attribution.

An analyst can reconstruct the raw view by:

1. Reading the raw snapshot.
2. Expanding each canonical event using `source_eids`.
3. Restoring original activity, timestamp, source, and source event key from the provenance archive.
4. Reversing relation union operations using source-specific relation records.
5. Replacing refined labels with original labels.
6. Removing synthetic adjusted timestamps.

This makes cleaning reversible and auditable.

## 9. Failure modes and safeguards

| Failure mode | Semantic damage | Safeguard |
|---|---|---|
| Collapsing distinct partial payments e13/e14 | M1 and M2 become one payment; financial reconciliation fails | Require Payment-object identity and PSP keys before merging |
| Converting abstraction-level updates into false rework | e06/e07 or e08/e09 appear as repeated activities | Retain qualifiers and abstraction flags; merge only in explicit scenario |
| Ordering by ingestion time | Delayed systems appear to happen later in business process | Use ingestion only as final deterministic fallback |
| Treating shared objects as proof of duplication | e13/e14 share O1/V1 but are distinct payments | Use discriminating child objects, not only parent objects |
| Unioning incompatible E2O relations | Merged event gains objects it never observed | Merge relations only after verified event identity; store relation provenance |
| Changing durations through synthetic microseconds | Concurrency becomes false precise sequence | Preserve original timestamp; mark adjusted timestamp as technical |
| Losing source-authoritative attributes | Billing or ERP authoritative fields overwritten | Source-prefixed attribute retention and conflict storage |
| Applying duplicate functions globally | Library removes semantically distinct same-time events | Pre-check candidate groups and use verified-pair merges |
| Misusing `source_seq` across systems | Invalid cross-source ordering | Use `source_seq` only within the same source |
| Quarantine fatigue | Unresolved duplicates silently accepted | Track unresolved candidates and require review before final release |
