# 1. Policy Interpretation and Conflict Resolution
Assumptions: (a) every case begins with Receive Onboarding Request and ends with Close Onboarding; (b) clarification request/response pairs may iterate; (c) “accepted case” means any trace that reaches Activate Vendor; (d) resource attributes are reliable when present; (e) timestamps are wall-clock hours from case start; (f) R11 post-activation behavior is outside the core onboarding backbone.  
Two resolutions of R5/R6: (1) strict precedence—Obtain Legal Opinion must precede Activate Vendor whenever Sanctions Escalation occurs; (2) emergency override—activation may precede the opinion when an external joint-authorization flag (absent from the log) is asserted.  
Chosen resolution: enforce strict precedence (resolution 1) inside the declarative layer and treat any activation-before-opinion trace as a hard violation; the emergency path is handled only by an external data-aware check that returns “policy-dependent” when the flag is missing. Compliance risk: legitimate emergency activations will be incorrectly flagged, requiring manual override.

# 3. Procedural Backbone
1. Compact formal description: Process tree  
   (Receive Onboarding Request,  
     +(Capture Master Data, Run Sanctions Screening, Verify Bank Account),  
     Classify Risk,  
     ×(Reject Vendor, (Manager Approval, Activate Vendor), (Enhanced Due Diligence, Compliance Approval, Activate Vendor)),  
     Release First Payment?, Close Onboarding)  
   Clarification loop and Sanctions Escalation are omitted from the tree (non-block-structured) and placed in DECLARE. Post-activation Change Bank Details/Suspend Vendor behavior is excluded.

2. PM4Py code:
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator
procedural_model = ProcessTree(operator=Operator.SEQUENCE)
start = ProcessTree(label="Receive Onboarding Request")
procedural_model.children.append(start)
par = ProcessTree(operator=Operator.PARALLEL)
par.children = [ProcessTree(label="Capture Master Data"),
                ProcessTree(label="Run Sanctions Screening"),
                ProcessTree(label="Verify Bank Account")]
procedural_model.children.append(par)
procedural_model.children.append(ProcessTree(label="Classify Risk"))
choice = ProcessTree(operator=Operator.XOR)
rej = ProcessTree(label="Reject Vendor")
low = ProcessTree(operator=Operator.SEQUENCE)
low.children = [ProcessTree(label="Manager Approval"), ProcessTree(label="Activate Vendor")]
high = ProcessTree(operator=Operator.SEQUENCE)
high.children = [ProcessTree(label="Enhanced Due Diligence"), ProcessTree(label="Compliance Approval"), ProcessTree(label="Activate Vendor")]
choice.children = [rej, low, high]
procedural_model.children.append(choice)
procedural_model.children.append(ProcessTree(label="Release First Payment"))
procedural_model.children.append(ProcessTree(label="Close Onboarding"))
```

3. Concurrency is expressed by the parallel operator; exclusive choice after Classify Risk encodes the three outcomes; clarification loops and Sanctions Escalation ordering are deliberately excluded because they are non-block-structured.

| Rule | Direction & semantics |
|------|-----------------------|
| response(Request Clarification, Receive Clarification) | every request must be followed (eventually) by a response |
| precedence(Receive Clarification, Request Clarification) | a new request may occur only after the previous response |
| precedence(Obtain Legal Opinion, Activate Vendor) | activation forbidden before legal opinion when escalation occurred |
| noncoexistence(Reject Vendor, Activate Vendor) | mutual exclusion of terminal outcomes |

# 7. Resource- and Data-Aware Checks
```python
# four-eyes on approval
def check_four_eyes(df, act1, act2):
    return pm4py.filter_four_eyes_principle(df, act1, act2)  # requires 'resource' column

# R9 & R11
def check_sod_and_emergency(df):
    required = ['case:concept:name', 'concept:name', 'time:timestamp', 'resource']
    if not all(c in df.columns for c in required):
        return "missing attributes – cannot evaluate"
    # emergency policy (R6)
    if "Sanctions Escalation" in df['concept:name'].values:
        esc_time = df[df['concept:name']=="Sanctions Escalation"]['time:timestamp'].min()
        act_time = df[df['concept:name']=="Activate Vendor"]['time:timestamp'].min()
        if act_time < esc_time:
            return "policy-dependent (emergency flag missing)"
    return "ok"
```

# 9. Contradictions, Redundancies, and Blind Spots
R1 and R10 duplicate terminal mutual exclusion across DECLARE and log skeleton. R3 response/precedence pair becomes vacuous if clarification never occurs. DECLARE rules lose context after Activate Vendor, making R11 impossible to enforce declaratively. Resource checks require the ‘resource’ attribute; when absent the check returns “missing attributes”. Timestamp-only temporal profiles cannot distinguish business-day versus calendar time. Treating support/confidence values as normative truth risks over-constraining future variants that legitimately deviate.

# 10. Deployment Recommendation
Canonical procedural representation is the ProcessTree. Authoritative policy layer is the DECLARE model for control-flow constraints and the resource/data layer for four-eyes and emergency rules. Run order: procedural  DECLARE  log skeleton  temporal profile  resource/data checks. Contradictory findings are surfaced as a layered report that lists the first failing layer and all subsequent violations, allowing analysts to decide overrides for policy-dependent cases.
