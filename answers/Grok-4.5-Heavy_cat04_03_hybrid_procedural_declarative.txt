# 1. Policy Interpretation and Conflict Resolution

**Material assumptions**
- The three concurrent checks (Capture Master Data, Run Sanctions Screening, Verify Bank Account) are mandatory before Classify Risk; their internal order is free.
- Risk class is not an explicit attribute; it is inferred solely from the path taken after Classify Risk (Manager Approval = low-risk; Enhanced Due Diligence + Compliance Approval = high-risk; Reject Vendor = rejection).
- Clarification cycles (Request Clarification / Receive Clarification) may interleave after the concurrent checks and before any terminal decision; multiple matched cycles are allowed.
- Sanctions Escalation is optional, may appear after Run Sanctions Screening (and possibly after Classify Risk), and is independent of the primary risk path.
- Post-activation activities (Change Bank Details, Suspend Vendor, re-Verify Bank Account) are exceptional and outside the stable onboarding backbone.
- No event attributes exist for risk level, emergency flag, or joint authorization. Resource identifiers are present in the supplied test logs.
- Temporal expectations (R12) are soft normative signals only.
- “Accepted case” means a case containing Activate Vendor; “rejected case” means a case containing Reject Vendor.

**R5 / R6 conflict – two possible resolutions**

**Resolution A (strict legal / chosen for the implemented model)**  
Whenever Sanctions Escalation has occurred, Obtain Legal Opinion must precede Activate Vendor. Any inverted order is a hard control-flow / data-layer violation. The emergency exception described in R6 is treated as an external, offline authorization that cannot be verified from the event log; therefore activity-only formalisms never allow the inversion.

**Resolution B (operations-friendly)**  
Activation before Obtain Legal Opinion is permitted after Escalation, provided the opinion arrives within 24 h. The case is flagged “policy-dependent” and requires external evidence of joint authorization. Temporal profile supplies the 24 h check; control-flow layers stay silent on order.

**Chosen resolution and compliance risk**  
Resolution A is implemented. Because the log contains neither an emergency attribute nor a joint-authorization token, any automated allowance of the inverted order would silently accept potentially non-compliant cases. The residual risk is that genuine emergency activations will be flagged as non-conforming until offline evidence is attached and an override recorded. This prioritizes legal auditability over operational flexibility.

|-------------|-------------------|----------------|--------------------|--------------------------|
| R1 | DECLARE + Log Skeleton | noncoexistence(Activate Vendor, Reject Vendor); never_together same pair | Mutual exclusion of terminals is a classic binary declarative constraint | Also enforced by procedural XOR; Log Skeleton reinforces frequency |
| R2 | DECLARE + Log Skeleton + data layer | noncoexistence(Manager Approval, Compliance Approval), noncoexistence(each approval, Reject Vendor); activ_freq {0,1}; external “exactly one approval iff Activate” | Activity-only cannot express “exactly one of two alternatives conditioned on acceptance” | Procedural XOR already chooses one path; data layer is authoritative for the conditional exactness |
| R3 | DECLARE + Log Skeleton | response + altresponse(Request Clarification, Receive Clarification); always_after same pair | Response / alternate-response capture eventual and intervening matching | Vacuous when no Request occurs; multi-cycle matching still needs careful altresponse |
| R4 | DECLARE + Log Skeleton | response(Sanctions Escalation, Obtain Legal Opinion); always_after same | Classic response | Overlaps with temporal mean; vacuous when Escalation absent |
| R5 | Resource/data-aware layer | If Escalation ∈ trace ∧ Activate ∈ trace then Opinion exists and ts(Opinion) < ts(Activate) | Conditional precedence cannot be expressed by pure activity DECLARE without over-constraining non-escalated cases | Activity-only formalisms are blind; external check is authoritative |
| R6 | Resource/data-aware layer (external) | Same inverted-order detection as R5; missing emergency/authorization attributes → fail under chosen Resolution A | Attribute absence makes the exception unobservable | Temporal 24 h check still applied as warning |
| R7 | DECLARE + Log Skeleton | precedence(Run Sanctions Screening, Sanctions Escalation); always_before same | Unconditional precedence | Strong overlap between layers |
| R8 | DECLARE + Log Skeleton | noncoexistence(EDD, Manager), noncoexistence(Compliance, Manager) | Binary exclusion | Also implied by procedural XOR |
| R9 | Resource/data-aware layer | Four-eyes: resource(Verify Bank Account) ≠ resource(applicable approval); resource(Capture Master Data) ≠ resource(Activate Vendor) | Pure activity sequences cannot see resources | Requires org:resource attribute; missing → not evaluated or conservative fail |
| R10 | Log Skeleton | activ_freq Activate/Reject/Release = {0,1} | Frequency constraints are native to Log Skeleton | DECLARE lacks a clean “at-most-one” template for optional activities |
| R11 | DECLARE + data layer | response(Change Bank Details, Suspend Vendor); external re-Verify-before-later-Release check | Response captures eventual Suspend; interleaving with re-Verify is data-dependent | At-most-one Release (R10) simplifies the “later payment” clause |
| R12 | Temporal profile | three pairs with (mean, std) in seconds; zeta = 2.0 | Soft temporal expectations are the intended use of the temporal profile | Explicitly warnings, never hard fails |

Authoritative layer for each requirement is the one listed first when multiple appear.

# 3. Procedural Backbone

**Compact formal description**  
Sequence(  
  Receive Onboarding Request,  
  Parallel(Capture Master Data, Run Sanctions Screening, Verify Bank Account),  
  Classify Risk,  
  XOR(  
    Sequence(Reject Vendor, Close Onboarding),  
    Sequence(Manager Approval, Activate Vendor, Release First Payment, Close Onboarding),  
    Sequence(Enhanced Due Diligence, Compliance Approval, Activate Vendor, Release First Payment, Close Onboarding)  
  )  
)

**Self-contained PM4Py code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

procedural_model = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[
        ProcessTree(label="Receive Onboarding Request"),
        ProcessTree(
            operator=Operator.PARALLEL,
            children=[
                ProcessTree(label="Capture Master Data"),
                ProcessTree(label="Run Sanctions Screening"),
                ProcessTree(label="Verify Bank Account"),
            ]
        ),
        ProcessTree(label="Classify Risk"),
        ProcessTree(
            operator=Operator.XOR,
            children=[
                ProcessTree(
                    operator=Operator.SEQUENCE,
                    children=[
                        ProcessTree(label="Reject Vendor"),
                        ProcessTree(label="Close Onboarding"),
                    ]
                ),
                ProcessTree(
                    operator=Operator.SEQUENCE,
                    children=[
                        ProcessTree(label="Manager Approval"),
                        ProcessTree(label="Activate Vendor"),
                        ProcessTree(label="Release First Payment"),
                        ProcessTree(label="Close Onboarding"),
                    ]
                ),
                ProcessTree(
                    operator=Operator.SEQUENCE,
                    children=[
                        ProcessTree(label="Enhanced Due Diligence"),
                        ProcessTree(label="Compliance Approval"),
                        ProcessTree(label="Activate Vendor"),
                        ProcessTree(label="Release First Payment"),
                        ProcessTree(label="Close Onboarding"),
                    ]
                ),
            ]
        ),
    ]
)
```

**Explanation**  
- Concurrency of the three checks is expressed by PARALLEL; the subsequent sequence forces Classify Risk only after all three complete.  
- The three primary outcomes are exclusive (XOR).  
- Clarification cycles, Sanctions Escalation, Obtain Legal Opinion, Change Bank Details and Suspend Vendor are deliberately excluded. They are cross-cutting / optional / post-activation and would force incorrect block-structure approximations.  
- For conformance evaluation of full logs that contain those extra activities, the recommended practice is to project the log onto the set of labels that appear in the ProcessTree before calling the procedural checker. Without projection the pure tree rejects any extra activity; the hybrid design therefore treats the ProcessTree as a backbone structural check only.

**Rule semantics table**

| Template | Pair / activity | Direction & meaning |
|----------|-----------------|---------------------|
| init / exactly_one | Receive Onboarding Request, Classify Risk, Close Onboarding, three checks | Must start the case / occur exactly once |
| noncoexistence | (Activate, Reject), (Manager, Compliance), (Manager, EDD), (approvals, Reject) | The two activities never appear together in the same case |
| response | A → B | After every occurrence of A an occurrence of B must eventually follow |
| altresponse | Request Clarification → Receive Clarification | Same as response, plus no second Request may appear before the matching Receive |
| precedence | A → B | Every occurrence of B is preceded by an occurrence of A |

Response is “eventually after”; precedence is “must have occurred earlier”; alternate response strengthens response against intervening duplicates; noncoexistence is symmetric exclusion (distinct from nonsuccession, which only forbids order).

**Overlap / disagreement notes**  
- never_together and activ_freq duplicate DECLARE noncoexistence and the frequency aspects of R10; retained for reinforcement.  
- always_after mirrors DECLARE response; orientation is identical (A must be followed by B).  
- always_before mirrors DECLARE precedence for R7.  
- No directly_follows constraints: concurrency of the three checks and the free interleaving of optional activities would make most DF pairs brittle.  
- Verify Bank Account frequency deliberately allows 2 to accommodate the re-verification required by R11.

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600),

```

Temporal deviations are treated as warnings, never as automatic control-flow violations, because R12 explicitly states that Compliance regards them as “normative enough to flag but not automatically reject.” The hybrid design therefore surfaces them via `pm4py.conformance_temporal_profile(..., zeta=2.0)` while leaving the hard accept/reject decision to the other layers.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement**: R1, R7, R8 and the response pairs appear in both DECLARE and Log Skeleton. This is intentional reinforcement, not contradiction; the two formalisms will always agree on these pairs under the chosen encodings.
- **Loops and post-activation**: Clarification multi-cycles and Change-Bank re-verification make pure frequency {0,1} unsafe for Verify Bank Account; the Log Skeleton therefore allows {0,1,2}. A second Release after a post-activation Change would violate R10, so the model never has to handle “later payment” interleaving beyond the single-Release case.
- **Vacuity**: response and always_after are vacuously true when the source activity is absent. This is correct for optional Escalation/Clarification but can hide missing obligations if the analyst forgets to inspect existence separately.
- **Missing case attributes**: emergency, joint authorization and explicit risk class are absent; therefore R5/R6 and the exact “one-approval-iff-accepted” part of R2 cannot be decided from the activity sequence alone.
- **Timestamp-only limitations**: temporal profile only sees pairs that actually occur in the observed order; an inverted pair never produces a numeric deviation, only a missing-pair observation that must be caught by the data-aware layer.
- **Support/confidence metadata**: setting support = confidence = 1.0 turns every DECLARE rule into a hard constraint. Treating those numbers as empirical discovery results would be incorrect; they are normative design choices.

# 10. Deployment Recommendation

- **Canonical procedural representation**: the ProcessTree given in section 3 (projected onto its own alphabet for conformance).  
- **Authoritative policy layer**: the resource/data-aware validation layer for all conditional, resource and attribute-dependent rules (R5, R6, R9, exact R2, full R11). DECLARE and Log Skeleton are authoritative for the pure activity constraints they encode.  
- **Recommended check order**:  
  1. Project log onto backbone activities → procedural conformance.  
  2. Full-log DECLARE.  
  3. Full-log Log Skeleton.  
  4. Temporal profile (warnings only).  
  5. Resource/data-aware checks (four-eyes, conditional legal order, clarification matching, post-activation).  
- **Surfacing contradictory findings**: each layer returns its own verdict. A dashboard should present a vector of results rather than a single Boolean, highlight the earliest decisive violation, and explicitly label any “policy-dependent” outcome that requires offline evidence. Overrides must be recorded with the external authorization token so that the audit trail remains complete.
