## 1. Modeling assumptions

* **Object types and capitalization:** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Singular capitalization is used consistently in `objects`, `relations`, flattening calls, and analysis dictionaries.
* **E2O qualifier vocabulary:**

  * Order lifecycle/context: `created_order`, `order_context`, `billed_order`, `financial_order_context`, `closed_order`
  * Item lifecycle: `added_item`, `reserved_item`, `packed_item`, `shipment_item`, `delivered_item`
  * Package and delivery lifecycle: `packed_package`, `dispatched_package`, `dispatch_delivery`, `confirmed_delivery`, `carried_package`
  * Finance: `issued_invoice`, `recorded_payment`, `payment_against_invoice`
* **O2O direction convention:** `ocel:oid` is the aggregate, carrier, or financial actor; `ocel:oid_2` is its component or target. Thus an Order `contains` an Item, a Package `packs` an Item, a Delivery `carries` a Package, an Invoice `bills` an Order, and a Payment settles an Invoice. The direction is a business-relation convention, not temporal causality.
* **Downstream E2O richness:** the OCEL used for discovery is analytically enriched. Logistics events are directly related in `relations` to the affected Packages, Deliveries, Items, and Orders. Payment events are related to their Payment, Invoice, and both billed Orders. Financial events are not propagated to Items because no item-level billing or payment allocation is supplied.
* **Source versus analytical relations:** every E2O row has an additional `relation_origin` attribute. Explicit narrative facts use `source`; O2O-derived context uses `derived:o2o`. The separate `source_relations` and `derived_relations` views allow sensitivity analysis. PM4Py discovery is deliberately run on all 53 enriched rows, but the 34 source rows remain distinguishable from the 19 derived rows.
* **Settlement assumption:** M1 is labeled `partially_settles`; M2 is labeled `completes_settlement`. This assumes the second installment completes cumulative settlement of V1. If “partial payments settling V1” does not imply full settlement, M2’s qualifier can be changed to `partially_settles` without changing any event or object identity.
* **Version assumption:** the pipeline targets the current PM4Py high-level API. The current `OCEL` constructor accepts `events`, `objects`, `relations`, and `o2o`; the constructor call is isolated so that only that line needs adapting for a materially different PM4Py version. The current `discover_dfg` returns the DFG, start frequencies, and end frequencies as a tuple, while `discover_log_skeleton` accepts a DataFrame directly.

The most consequential relation sets are:

* **e06, Reserve Stock:** joins I1/O100 and I3/O200 before packaging, establishing genuine cross-order operational convergence.
* **e07, Pack Package P1:** connects P1, I1, I3, O100, and O200. It is the first event at which the cross-order consolidation exists as a package-level fact.

## 4. Expected flattened behavior

Current PM4Py flattening treats objects of the selected type as cases and selects events through their direct E2O links. It does not traverse the O2O table automatically. It also selects object/event identifiers for the projection rather than carrying relation-level qualifiers or `relation_origin` into the traditional log. Consequently, the enriched E2O policy determines which downstream events appear. 

### Order flattening

**O100** should have approximately this trace:

`Create Order → Add Item → Add Item → Reserve Stock → Pack Package → Pack Package → Dispatch Package → Dispatch Package → Issue Invoice → Record Payment → Confirm Delivery → Confirm Delivery → Record Payment → Close Order`

**O200** should have:

`Create Order → Add Item → Reserve Stock → Pack Package → Dispatch Package → Issue Invoice → Record Payment → Confirm Delivery → Record Payment → Close Order`

The events copied into both Order cases are e06, e07, e09, e11, e12, e13, and e15. They remain the same OCEL event identifiers, but a traditional flattened log contains one row in each related Order case.

Likely DFG edges are:

* Frequency 2: `Create Order → Add Item`, `Add Item → Reserve Stock`, `Reserve Stock → Pack Package`, `Pack Package → Dispatch Package`, `Dispatch Package → Issue Invoice`, `Issue Invoice → Record Payment`, `Record Payment → Confirm Delivery`, `Confirm Delivery → Record Payment`, and `Record Payment → Close Order`.
* Frequency 1: `Add Item → Add Item`, `Pack Package → Pack Package`, `Dispatch Package → Dispatch Package`, and `Confirm Delivery → Confirm Delivery`.

What is omitted is the identity of I1/I2/I3, P1/P2, D1/D2, V1, M1, and M2 as interacting objects; the distinction between P1’s cross-order branch and P2’s single-order branch; O2O qualifiers; and source-versus-derived E2O provenance.

The self-loops are particularly misleading. `Pack Package → Pack Package` is not package rework; it is O100’s two distinct packages. Likewise, the two dispatches and two confirmations correspond to two logistics branches. Summing `payment_amount` over the Order-flattened DataFrame would also double-count each shared payment globally: e12 appears once under O100 and once under O200, as does e15. Moreover, assigning the full 250 units to each Order would be an unsupported allocation.

### Package flattening

Both P1 and P2 should have:

`Pack Package → Dispatch Package → Confirm Delivery`

Likely DFG edges are:

* `Pack Package → Dispatch Package`: frequency 2
* `Dispatch Package → Confirm Delivery`: frequency 2

No event is copied between P1 and P2 within this flattening. The view omits stock reservation, the Orders containing the Items, the identity and count of packed Items, the carrying Delivery identity as an object relation, invoicing, payment, and Order closure.

The major distortion is that P1 and P2 appear behaviorally identical. The trace does not show that P1 consolidates I1 and I3 from O100 and O200, while P2 contains only I2 from O100.

### Delivery flattening

D1 and D2 should each have:

`Dispatch Package → Confirm Delivery`

The likely DFG contains only:

* `Dispatch Package → Confirm Delivery`: frequency 2

No event is copied between D1 and D2. The view omits packing, reservation, cargo composition, Order context, invoicing, payment, and Order closure.

D1 and D2 therefore look structurally interchangeable despite D1 carrying the cross-order P1 and D2 carrying only P2. The long elapsed time of D2 can still be observed from timestamps, but the business reason or cargo topology is absent.

### Invoice flattening

V1 should have:

`Issue Invoice → Record Payment → Record Payment`

Likely DFG edges are:

* `Issue Invoice → Record Payment`: frequency 1
* `Record Payment → Record Payment`: frequency 1

There is only one Invoice case, so there is no cross-Invoice copying. The flattening omits M1 and M2 as distinct Payment objects, their O2O qualifiers, and any allocation of payment value to O100 versus O200.

The `Record Payment → Record Payment` self-loop can easily be misread as payment rework or duplication. In the OCEL, it represents two different Payment objects and two installments.

### Log-skeleton implications

At zero noise, Package and Delivery flattenings will produce extremely rigid constraints because their two traces are identical. The Invoice skeleton is based on only one trace and will strongly encode one invoice issuance followed by exactly two payment occurrences. The Order skeleton has only two cases and may encode accidental regularities, including exactly two payments per Order and activity-occurrence sets such as one-or-two Add, Pack, Dispatch, and Confirm events. These are descriptions of this tiny sample, not reliable general rules.

### Why Payment flattening is weak

M1 and M2 would each be a singleton case containing only `Record Payment`. There would be no directly-follows edge, no meaningful temporal lifecycle, and a nearly trivial log skeleton. Flattening does not traverse M1/M2 → V1 → Orders through O2O, so Invoice issuance and Order closure would not enter the Payment traces automatically. The important semantics are in Payment–Invoice O2O links and payment event attributes, not in Payment-local control flow.

## 5. Expected object-centric structures

### OC-DFG

PM4Py’s OC-DFG is a composition of directly-follows behavior for the separate object types, while retaining object-centric frequency notions and event/object associations. 

Expected type-specific behavior includes:

* **Item:** I1 and I3 follow `Add Item → Reserve Stock → Pack Package → Dispatch Package → Confirm Delivery`. I2 skips reservation in the supplied log and follows `Add Item → Pack Package → Dispatch Package → Confirm Delivery`. Thus the Item OC-DFG should include:

  * `Add Item → Reserve Stock`: 2
  * `Reserve Stock → Pack Package`: 2
  * `Add Item → Pack Package`: 1
  * `Pack Package → Dispatch Package`: 3
  * `Dispatch Package → Confirm Delivery`: 3
* **Package:** the two-edge chain found in the Package flattening.
* **Delivery:** `Dispatch Package → Confirm Delivery`.
* **Invoice:** `Issue Invoice → Record Payment → Record Payment`.
* **Payment:** two starts and two ends at `Record Payment`, but no Payment-type directly-follows edge.
* **Order:** the richer graph with repeated Add, Pack, Dispatch, and Confirm behavior described above.

P1’s importance is not merely that a Pack event exists. The same e07 occurrence concerns one Package, two Items, and two Orders. Likewise, e09 and e13 carry P1’s multi-object context into dispatch and delivery. V1 similarly connects one Invoice to O100 and O200, with M1 and M2 contributing two payment events to the Invoice and Order perspectives.

### OTG

In the current PM4Py implementation, `discover_otg` aggregates five graph families—object interaction, descendants, inheritance, cobirth, and codeath—derived from E2O co-occurrence and lifecycle position. It does **not** directly convert the explicit `o2o` table and its business qualifiers into OTG edges. 

Under the enriched E2O policy, it should nevertheless expose:

* Order–Item, Order–Package, Package–Item, Delivery–Package, Delivery–Item, and Delivery–Order interaction patterns.
* Invoice–Order and Payment–Invoice/Order patterns around V1, M1, and M2.
* An Order–Order interaction because O100 and O200 participate in seven common events.
* Descendant-like relations from O100/O200 to later-created logistics and financial objects.
* Descendant relations from V1 to M1 and M2 because V1 already exists when each Payment first appears.
* An inferred inheritance edge from V1 to M2: e15 is the last event of V1’s observed lifecycle and the first event of M2’s lifecycle. That is a lifecycle-derived pattern, not a claim that Invoice business identity is transferred to the Payment.

For undirected graph families such as interaction, cobirth, and codeath, tuple orientation can be based on object-ID ordering. It should not be interpreted as the business direction encoded by `contains`, `packs`, `bills`, or `settles`.

### Object-centric Petri net

The current discovery implementation obtains object-type behavior from the OC-DFG and per-type flattenings, mines per-type models using an Inductive Miner variant, and combines them into an object-centric net. 

Expected structural tendencies are:

* `Reserve Stock` must accommodate one event involving two Items and two Orders.
* `Pack Package` must accommodate P1 joining two Items and two Orders, while P2 joins one Item and one Order.
* `Dispatch Package` and `Confirm Delivery` have multiplicity for the Item and Order types because P1 concerns two of each.
* `Issue Invoice` synchronizes V1 with O100 and O200.
* `Record Payment` occurs once for M1 and once for M2, each time involving V1 and both Orders.
* O100’s Package and Delivery behavior has two branches, whereas O200 has one.

The O2O qualifiers `partially_settles` and `completes_settlement` are not separate event activities. A discovered net based on the supplied event labels therefore need not distinguish the first installment from the settlement-completing installment.

There is no uniquely determined object-centric Petri-net interpretation here. The tiny sample, the relation-enrichment policy, the Inductive Miner variant, noise settings, and multiplicity thresholds can all change routing and variable-arc choices while remaining consistent with the same observations.

### Object-interactions summary

The current summary emits one row for every ordered combination of an event, one related object, and another related object. Thus an event with (n) related objects contributes (n(n-1)) rows. 

For this enriched OCEL:

* The expected total is **158 ordered interaction rows**, corresponding to 79 unordered event-specific object pairs.
* e09 and e13 each involve six objects and therefore contribute 30 rows each.
* e07 involves five objects and contributes 20 rows.
* e12 and e15 each involve four objects and contribute 12 rows each.
* O100 and O200 co-occur in seven events.
* P1 co-occurs with O100 in three events and with O200 in three events: pack, dispatch, and confirmation.
* V1 co-occurs with each Order in three events: invoice issuance and both payment recordings.
* M1 and M2 do not directly interact because they never participate in the same event, even though both point to V1 through O2O.

## 6. Modeling alternatives

| Policy                                          | E2O rule                                                                                                                                           | Expected effect on discovery                                                                                                                                                                                                                      |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Source-minimal literal relations**            | Use only the 34 rows marked `source`. Do not add downstream Order/Item links unless the event description explicitly states them.                  | Order traces lose P2 packing, dispatch/confirmation context, and payment events derived through V1. Item traces stop at packing unless dispatch and confirmation explicitly name Items. ET–OT weights and interaction graphs become much sparser. |
| **Full operational involvement as source fact** | Relate every event to every object operationally affected and label all such rows as observed.                                                     | Discovery topology resembles the chosen enriched model, but provenance disappears. Dense interaction and ET–OT results may be mistaken for direct source capture even when generated through joins.                                               |
| **O2O-propagated analytical layer**             | Keep a canonical source-only OCEL and generate a separate E2O closure for analysis, recording origin, path, propagation depth, and policy version. | Source and enriched OC-DFGs can be compared directly. One-hop propagation may show Package-to-Item context; deeper propagation can also reach Orders. Results become explicitly policy-dependent rather than silently inflated.                   |
| **Financially conservative policy**             | Link payment events only to M1/M2 and V1. Retain V1 → O100/O200 in O2O, but do not add payment-to-Order E2O without allocation evidence.           | Invoice behavior is unchanged, but Order traces omit payment events. ET–OT loses the four `Record Payment–Order` incidences, and Payment–Order interactions disappear. The business story remains intact while avoiding implied allocation.       |
| **Lifecycle-owner policy**                      | Link an event only to objects whose own state is directly changed; use O2O for contextual structure.                                               | Package and Delivery flattenings remain useful, but Order and Item flattenings become shorter. This favors clean local lifecycles at the cost of weak cross-object synchronization in algorithms that do not traverse O2O.                        |

The selected construction is a provenance-preserving compromise between source-minimal and O2O-propagated analysis: source rows remain identifiable, while the default discovery run receives the richer operational context.

## 7. Failure modes

1. **Relation inflation.** Propagating every event across the full connected O2O component would make almost every downstream event touch almost every object. ET–OT weights, interaction counts, and multiplicity estimates would then reflect the propagation rule more than the process.

2. **Missing direct E2O links.** The opposite error is assuming flattening or discovery will automatically traverse `o2o`. Current flattening selects direct E2O links for the chosen object type; an Order will not inherit a Payment event solely because Payment → Invoice → Order exists in O2O. 

3. **Treating O2O propagation as observation.** A derived relation such as e12 → O100 is analytically reasonable but not equivalent to a source record explicitly attaching M1 to O100. Removing `relation_origin` would erase that distinction.

4. **Duplicate shared events after flattening.** e06, e07, e09, e11, e12, e13, and e15 appear in both Order cases. Traditional event counts and attribute sums can therefore exceed the number or value of unique source events.

5. **Ambiguous payment allocation.** V1 bills both Orders, but no split of the 100 and 150 units is supplied. Relating each payment to both Orders expresses context, not allocation. Neither Order can defensibly be assigned the full amount or an assumed 50/50 share.

6. **Overly short Payment traces.** Each Payment object has only one event. Payment flattening cannot reveal invoice issuance, cumulative settlement, or Order closure unless those events are explicitly propagated to Payment objects, which would introduce another modeling assumption.

7. **Constructor or API version mismatch.** A different PM4Py version may expose a different constructor location, return format, or visualization signature. The DataFrames should remain unchanged; only the isolated constructor or wrapper calls should be adapted. The current constructor explicitly supports `o2o`. 

8. **False total order for same-time events.** This example has no timestamp ties, but a general pipeline must not convert arbitrary row order into causal order when two events share a timestamp. `source_sequence` may represent ingestion order; it is not automatically business precedence.

9. **Incorrect event-table ordering for lifecycle-derived graphs.** Current descendant, inheritance, cobirth, and codeath graph routines iterate the event-table order. If `events` were not chronologically ordered, the OTG could infer incorrect “seen/unseen,” first-event, or last-event relations. 

10. **O2O direction reversal.** Encoding I1 → O100 as `contains`, or V1 → M1 as `partially_settles`, would contradict the declared direction convention even though referential integrity still passed.

11. **Qualifier inconsistency.** Using `packed_item` for P1 in one event and `packed_package` for the same role elsewhere would make qualifier-based analysis unreliable. Qualifiers should express the object’s role in that event.

12. **Denormalization drift.** Because `relations` repeats activity and timestamp, manual construction can attach the right event ID but the wrong activity or time. The merge-based validation prevents this.

13. **Payment-value double counting.** Summing `payment_amount` over the complete relations table is especially dangerous: the same event amount is repeated conceptually across multiple object associations. Monetary aggregation should begin from unique rows in `events`, followed by an explicit allocation rule if object-level attribution is needed.

14. **Overfitting a tiny log.** Two Orders, two Packages, two Deliveries, and one Invoice are insufficient for robust behavioral generalization. Exact DFG frequencies and zero-noise skeleton constraints are descriptive, not statistically stable.

15. **Expecting O2O business qualifiers in the OTG or OCPN.** The current OTG is derived from E2O-based object graph families, and OCPN discovery is driven mainly by object-type event behavior. Neither automatically turns `bills`, `packs`, or `completes_settlement` into labeled process transitions. 

16. **Overstating settlement completion.** The qualifier `completes_settlement` for M2 is an explicit assumption. If V1’s total is not known to be 250, the safer qualifier for M2 is also `partially_settles`.
