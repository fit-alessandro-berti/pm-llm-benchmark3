## 6. Candidate Site B intervention

Start with newly registered cases with no originals requirement, complete usable digital documents, independently executable checks, and a tested multi-owner workflow. Include legal and complexity status in the eligibility record; start with non-legal, lower-complexity cases to limit downstream exposure. Later test originals-required cases separately: start identity and arrange or await originals after registration, but do not release or execute document checking until receipt and all other applicable prerequisites are satisfied. If system support or case readiness fails, use the current lawful process and record the reason. The proposal to execute both checks immediately for every case is therefore unsuitable.

Create identity and document tasks together only when both are eligible; otherwise create the identity task and a receipt-tracking item, then create or release the document task on verified receipt. Task creation must not imply permission to perform a legally blocked check. Identity and document specialists own their respective tasks; assessors and legal reviewers retain their separate responsibilities. Assessment begins only after both verification results are complete and valid. Required legal review follows assessment. A supplement request returns the case to document checking and reassessment as needed, followed by legal review again before a final decision. A legal reviewer must determine whether legal review is required and what renewed checks are needed. Approve or reject is followed by notification.

Set and record pool-specific WIP and admission caps from observed capacity, not by copying A's six-task limit. Use a common age-aware priority policy across pilot arms, reserve capacity for repeats and older cases, and monitor verification, assessment and legal queues, including non-pilot work. Log assignment, eligibility and reasons, actual task availability/start/end, owner, receipt and evidence version, legal and loop decisions, lock failures, back-entry time, queue entry/exit, and outcome timestamps. Capture actual event time separately from entry time and audit a sample against source records.

A partial-order specification for an originals-required case is: `Register < Identity Check`; `Register < Originals Receipt < Document Check`; `{Identity Check, Document Check} < Assessment`; for cases requiring legal review, `Assessment < Legal Review`, with `Legal Review < Request Supplement < Document Check (repeat) < Assessment (repeat) < Legal Review` when a supplement requires both repeated checks; after required reviews and repeats, `Approve XOR Reject < Notify`. For cases without an originals requirement, replace the receipt prerequisite by document readiness after registration. Other lawful variants of the loop may repeat only the checks actually needed.

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.powl.obj import (
    Transition, SilentTransition, StrictPartialOrder, OperatorPOWL,
)
from pm4py.objects.process_tree.obj import Operator

# PM4Py's strict partial order must contain the transitive closure.
def partial_order(nodes, edges):
    model = StrictPartialOrder(nodes)
    reach = set(edges)
    while True:
        new = {(a, d) for a, b in reach for c, d in reach if b is c} - reach
        if not new:
            break
        reach |= new
    for source, target in reach:
        model.order.add_edge(source, target)
    return model


def sequence(*nodes):
    return partial_order(list(nodes), [
        (nodes[i], nodes[i + 1]) for i in range(len(nodes) - 1)
    ])


site_a_before = pm4py.parse_process_tree(
    "->( 'Register', 'Identity Check', 'Document Check', 'Assessment', "
    "X( 'Approve', 'Reject' ), 'Notify' )"
)
site_a_after = pm4py.parse_process_tree(
    "->( 'Register', +( 'Identity Check', 'Document Check' ), "
    "'Assessment', X( 'Approve', 'Reject' ), 'Notify' )"
)

register = Transition('Register')
identity = Transition('Identity Check')
document = Transition('Document Check')
assessment = Transition('Assessment')
notify = Transition('Notify')

# Receipt occurs on the originals-required branch; tau represents no receipt.
receipt_choice = OperatorPOWL(Operator.XOR, [
    Transition('Originals Receipt'), SilentTransition()
])

# LOOP(body, redo) executes Legal Review, then may repeat the redo and body.
# This candidate's supplement path repeats both checks after the request.
redo = sequence(
    Transition('Request Supplement'),
    Transition('Document Check'),
    Transition('Assessment'),
)
legal_loop = OperatorPOWL(Operator.LOOP, [Transition('Legal Review'), redo])
legal_choice = OperatorPOWL(Operator.XOR, [legal_loop, SilentTransition()])
decision = OperatorPOWL(Operator.XOR, [
    Transition('Approve'), Transition('Reject')
])

site_b = partial_order(
    [register, identity, receipt_choice, document, assessment,
     legal_choice, decision, notify],
    [
        (register, identity),
        (register, receipt_choice),
        (receipt_choice, document),
        (identity, assessment),   # assessment waits for identity
        (document, assessment),   # and for document verification
        (assessment, legal_choice),
        (legal_choice, decision),
        (decision, notify),
    ],
)
site_b.validate_partial_orders()

for name, model in [('A before', site_a_before),
                    ('A after', site_a_after), ('B candidate', site_b)]:
    net, initial_marking, final_marking = pm4py.convert_to_petri_net(model)
    print(name, 'workflow net:', pm4py.check_is_workflow_net(net))
    sound, diagnostics = pm4py.check_soundness(net, initial_marking, final_marking)
    print(name, 'sound:', sound)

# The receipt and legal XORs are unguarded abstractions: this model cannot
# enforce data-dependent originals or mandatory legal-review rules. Enforce
# those in the case system and verify them using case attributes. The model
# also omits role capacities, queues, WIP limits, case locks, task durations,
# evidence validity and timestamp reliability. The supplement branch models
# repeats of both document checking and assessment; actual rules can require
# only a subset and need a richer guarded model. Soundness is a structural
# property and does not establish legal compliance or operational feasibility.
```

The code was checked with the locally installed PM4Py 2.7.23.4: all three conversions returned workflow nets and passed its soundness check. The B model is an unguarded control-flow abstraction: for example, it admits skipping legal review even for a case that legally requires it, so its output must not be used as a compliance decision engine.

## 9. Recommendation

**conditional go**

Transfer the principle of starting independent, legally enabled work early and joining the results before assessment. Pilot it first for newly registered, lower-complexity cases with complete digital documents, no originals requirement, no mandatory legal review, and independently executable checks. This subgroup offers a direct test of whether two specialist pools can actually work concurrently without introducing receipt or legal-review constraints into the initial test. Its exact share is unknown and must be measured before choosing a sample. Use a supported multi-owner workflow and independently verify that work actually overlaps.

Do not copy simultaneous execution for every case or assume that Site A's nine-hour median improvement is causal. At B, identity can begin while required originals are in transit, but document checking must wait for their receipt. Mandatory legal review and supplement loops must remain intact. A's mix change, API upgrade, two additional reviewers and huddles make its aggregate before/after improvement inseparable from parallelization. B's specialist queues and single-owner lock also make its treatment implementation materially different.

A plausible initial benefit is earlier assessment readiness for some digital-ready claims, potentially reducing their cycle times. The size is uncertain; a fixed assessor pool can turn the gain into a downstream queue, while legal congestion, repeated work and back-entry can worsen the tail or mask a failed implementation. Track the mean, median and p90, queue ages, non-pilot cases, rework and complete 90-day appeals alongside audited fidelity. Preserve capacity for older cases and repeats.

Expand to additional strata only if the randomized comparison shows a meaningful benefit with uncertainty narrow enough for the predefined decision threshold, reliable true overlap, intact statutory gates and no unacceptable tail, quality or spillover harm. Test originals-required and legal-review cases as separate versions with their own controls. Modify the rollout if lock failures, low fidelity or a specific bottleneck explain poor results; recheck after the repair. Abandon the policy for a subgroup if a valid, adequately supported test shows no worthwhile benefit or unacceptable harm despite faithful execution, or if its legal and system prerequisites cannot be satisfied.

## 10. Assumption register

1. **Check independence for initial cases** — needed for concurrent execution to avoid invalid work — audit inputs and dependencies before assignment and inspect invalidations — if false, exclude dependent cases or enforce the relevant order.
2. **Originals and legal flags are accurate at registration** — needed for lawful eligibility and routing — compare flags against case files and legal decisions — if false, correct classification and pause affected routing until reliable.
3. **Multi-owner execution can be supported and audited** — needed to realize true overlap — test locks, ownership and actual work times on a sample — if false, repair the system or retain sequential execution.
4. **Measured event times approximate actual work times** — needed to interpret overlap and waits — compare source records and observations with event and entry timestamps — if false, improve instrumentation and qualify process-mining estimates.
5. **Randomization and allocation are implemented as recorded** — needed for a valid policy comparison — audit assignment, exclusions, crossover and baseline balance — if false, investigate bias and rerandomize or redesign rather than claim a clean effect.
6. **Shared queues can be controlled or interference measured** — needed to interpret case-level assignment effects — track pool workloads and non-pilot outcomes and test for spillovers — if false, use independent or randomized team/time blocks and adjust inference.
7. **Baseline data support planning of quantile and subgroup precision** — needed to set sample size and duration — use case-level distributions, simulations, completion patterns and realized eligible counts — if false, extend enrollment or restrict claims to supported outcomes and strata.
8. **The evaluated policy and conditional mechanisms remain applicable during expansion** — needed to generalize pilot effects beyond its sampled conditions — monitor case mix, staffing, systems and stratum-specific outcomes after rollout — if false, re-estimate locally and limit or revise expansion.
