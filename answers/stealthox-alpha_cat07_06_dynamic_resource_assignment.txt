# 1. Objectives and constraints

## Optimization objectives (in priority order)

1. **SLA protection** – every case completes before `sla_deadline`; urgent/high cases get scheduling precedence.
2. **Error and rework prevention** – skill level must match case risk (complexity × priority), because historical evidence shows mismatches add ~3.3h service time and >2 reassignments multiply rework by 1.8×.
3. **Continuity of ownership** – minimize handovers where they are expensive (high complexity, high handover-cost band, already-reassigned cases).
4. **Workload fairness and sustainability** – balance open cases and committed hours; protect high-overtime-risk workers.
5. **Skill development** – use safe, low-risk cases to grow documented training priorities (20% of normal/low assignments when SLA-safe).
6. **Short-term throughput** – a goal, but deliberately *not* the maximand; it is traded off against objectives 1–5.
7. **Resilience** – avoid single-person dependencies per activity; keep backup capability warm.

## Hard constraints (safety/compliance — never traded away)

| # | Constraint |
|---|---|
| H1 | Max **4 new assignments** per resource per decision batch |
| H2 | No high/urgent-priority case to skill <2 **unless formally supervised** |
| H3 | **Security Review**: skill 3 only, or skill 1–2 under explicit supervision by R7_Gita/R8_Hugo (skill-0 participation only via a signed, logged training exception) |
| H4 | **Final Approval**: finalized only at skill 2–3; skill 1 may prepare only |
| H5 | **Overtime guard**: no *new* work to overtime-risk="high" resources unless the case is urgent and no safer alternative exists |
| H6 | **Batching** (Quality Check) only if priority  {normal, low} **and** SLA remaining > 24h |
| H7 | Continuity override: high-complexity + high-handover-cost cases stay with the owner **unless** owner skill 1 and supervision is infeasible |

## Soft preferences (traded off via explicit weights)

- Start-soonest / slack maximization (throughput proxy)
- Continuity and low handover cost
- Fairness of load distribution
- Training value
- Bottleneck avoidance / capability redundancy

The weights are **calibrated from the event log** (Section 7) and reviewed with workers — they are policy parameters, not hidden magic.

# 2. Assignment policy

## Architecture: filtered greedy scoring + repair pass

Each case gets a **scored, fully explained** decision. Every score component maps to a human-readable reason string that is written to the log's `assignment_reason` field, so every assignment is auditable after the fact.

## Pseudocode

```text
POLICY_ASSIGN_BATCH(queue, resources):

  # ---------- Phase 0: preprocessing ----------
  sort queue by (priority_rank, sla_remaining)          # urgent first
  for r in resources: batch_new[r]  0

  # ---------- Phase 1: hard eligibility filter ----------
  ELIGIBLE(r, c):
    F1 skill floor:
         Security Review : skill==3, OR skill in {1,2} with named supervisor Gita/Hugo,
                           OR signed training-exception (skill 0) with supervisor
         Final Approval  : skill>=2 to finalize (skill 1 may be "preparer" role)
         all others      : skill>=1; and skill>=2 if priority in {high, urgent} unless supervised
    F2 capacity: open_cases[r] + batch_new[r] <= CAP_SOFT(6)
                 hours_remaining[r] >= est_service(c, r) * 1.2   # congestion buffer
    F3 overtime guard: NOT (overtime_risk[r]=="high") UNLESS c.priority=="urgent"
                       and no non-high alternative exists  (log justification code)
    F4 batch rule: batching permitted only if priority in {normal,low} and sla_remaining>24h
    return F1..F4 all true

  # ---------- Phase 2: scoring (all components normalized 0..1) ----------
  score(r, c):
    # SLA urgency fit: will this resource realistically finish in time?
    slack = sla_remaining(c)  est_queue_wait(r)  est_service(c, r)
    UrgencyFit  = clamp(slack / sla_remaining(c), 1, 1)

    # Skill match: enough competence, no specialist hoarding on easy work
    needed      = 2 + (1 if complexity(c) > 0.7 else 0)
    SkillFit    = {1:0.4, 2:0.8, 3:1.0}[skill(r,c.activity)]
                   0.1 * max(0, skill(r,c.activity)  needed)   # surplus discount

    # Continuity / handover cost
    if r == current_owner(c): ContinuityFit = 1.0
    else:
      band_w = {low:0.15, medium:0.35, high:0.60}[handover_cost_band(c)]
      ContinuityFit = 1  band_w*(0.5+0.5*complexity(c))  0.1*reassignment_count(c)

    # Workload & overtime fairness
    FairnessFit = 1  normalize(open_cases[r] + committed_hours[r]/CAP_HOURS)
                  + 0.05 * (1  same_activity_share_today(r))    # spread, don't pile

    # Training / development
    TrainingFit = 0.8 if c.activity == training_priority[r]
                       and c.priority in {normal, low}
                       and named_supervisor_exists(r, c) with supervisor skill>=3
                       and UrgencyFit > 0.2        # never train at SLA expense
                  else 0

    # Resilience / bottleneck avoidance
    ResilienceFit = 1  activity_concentration(r, c.activity)   # share of this activity
                    # done by r over trailing 30 days, from event log

    TOTAL = 0.30*UrgencyFit + 0.20*SkillFit + 0.20*ContinuityFit
          + 0.15*FairnessFit + 0.10*TrainingFit + 0.05*ResilienceFit
    return TOTAL, reason_string(top-2 components + exception codes)

  # ---------- Phase 3: greedy assignment ----------
  for c in sorted queue:
    cand = [r for r in resources if ELIGIBLE(r,c)]
    if cand empty  EXCEPTION_LADDER(c)
    r* = argmax score;  commit;  batch_new[r*] += 1;  log(reason_string)

  # ---------- Phase 4: repair pass ----------
  for pairs (c1,c2) with different owners:
    if swapping owners improves sum(TOTAL) and violates no hard constraint  swap, re-log

  # ---------- Phase 5: tie-breaking (deterministic, auditable) ----------
  tie_break order: fewer open cases  lower overtime-risk class
                    same team as current owner  resource ID (lexicographic)

EXCEPTION_LADDER(c):            # never a silent breach
  E1 supervised upgrade (pair trainee with specialist)
  E2 authorized overtime with logged justification
  E3 borrow adjacent resource via activity-similarity network (Section 7)
  E4 proactive SLA-renegotiation alert to process owner
```

**Socio-technical safeguards:** workers see the reason string for every assignment; they can flag corrections ("context not transferred", "supervisor unavailable") which become logged deviation events feeding weight recalibration. Weights are reviewed monthly with team leads — the policy is a negotiated instrument, not an oracle.

# 4. Comparison with baseline policies

| Dimension | First-available | Specialist-only | Proposed dynamic policy |
|---|---|---|---|
| **Expected throughput** | Highest immediately (always picks idlest hands) but eroded downstream by rework from mismatches | Lowest — specialist queues throttle the whole flow (evidence: known Security/Approval queues) | Near first-available short-term; better effective throughput because fewer loops and handover delays |
| **SLA risk** | Moderate: fast starts, but skill mismatches stretch service time (~+3.3h) on hard cases | High at peaks: urgent items wait behind the one specialist (e.g., all approvals stacking on Farid) | Lowest: slack-aware matching, urgency-first sequencing, pre-agreed overflow paths (EvaFarid) |
| **Error/rework risk** | Worst: routine handling of complex work; would e.g. put Security on non-specialists | Best short-term; but specialist fatigue and queues create indirect errors | Close to specialist-only on critical cases (C001, C002, C016), deliberately tolerant on routine ones (C013) |
| **Fairness of workload** | Poor: dumps everything on whoever is momentarily lightest (here: Jonas, Farid) creating a new bottleneck | Poor: concentrates on the best-skilled few; burnout risk | Enforced: caps, overtime guards; this batch actively *relieves* Bruno, David, Iris |
| **Skill development** | None (accidental at best) | Negative — specialists hoard work; trainees never practice | Structured: 20% quota, named supervisors, logged development goals (C009, C015) |
| **Continuity of ownership** | Ignored entirely | Incidental (specialist sometimes = owner) | Explicit rule (H7): C016/C007 kept; C001 moved only because the rule's own exception applies |
| **Resilience to absence/bottlenecks** | Fragile: load follows the idle, creating instant key-person dependencies | Extreme key-person risk: one absence stalls Security or Approval | Diversified via concentration penalty + activity-similarity network identifies warm backups |

**Where the baselines genuinely win — no single optimum exists:** first-available is preferable when tasks are homogeneous and low-complexity (matching overhead buys nothing); specialist-only is preferable when error cost is catastrophic and volume is low (e.g., a compliance-critical review with slack). The proposed policy dominates *on this mixed, SLA-bound, multi-objective queue*, but it pays a real price: ~7 handovers in this batch, some avoidable in pure throughput terms (C006, C010), and it depends on supervisors actually being available. If supervision collapses as a practice, the training track (C009, C015) degrades into risk and should be paused.

# 6. Process-mining audit indicators

| Indicator | Definition / formula | Target | Log source |
|---|---|---|---|
| **Handover frequency** | Handovers per case = (# directly-follows pairs (a,r)(a,r) with rr) / #cases; stratify by complexity band |  trend; 0 on high-complexity/high-band cases | Handover-of-work SNA |
| **Reassignment count** | Mean `reassignment_count`; % cases with count >2 | Mean <1.5; %>2 <10% (1.8× rework evidence) | Case attribute |
| **Skill mismatch** | % events where `skill(resource, required_skill)` < required floor, weighted by priority; separate counter for unsupervised high-priority mismatches | 0 for high/urgent unsupervised | Join log  skill matrix |
| **Workload distribution** | Gini coefficient / std of daily open cases and committed hours per resource; # cap-4 breaches | Gini declining; breaches = 0 | `workload_snapshot` |
| **Overtime-risk exposure** | % new assignments to OT-risk="high" resources without a logged justification code | <5%, all justified | Assignment records + resource registry |
| **SLA misses** | % cases with completion timestamp > `sla_deadline`, by priority; plus near-miss rate (slack <10%) | Urgent: 0; high: <5% | Timestamps vs `sla_deadline` |
| **Rework/appeal after assignment** | % cases with repeated activities or appeal events within 30 days, stratified by reassignment count and owner-change-on-high-complexity | Confirm/decay the 1.8×/1.4× effects under new policy | Variants + follow-up events |
| **Training assignment share** | % normal/low assignments tagged training **verified** by co-execution of doer + supervisor in the log | 20%; supervision verification = 100% | `assignment_reason` + co-presence |
| **Specialist bottlenecks** | Waiting time before Security/Approval (from performance DFG); utilization of the skill-3 pool; queue age | Waiting trend ; no skill-3 resource >85% utilized | Performance DFG |
| **Policy deviations** | % decisions where executed assignee  policy replay recommendation; classified by reason code (emergency, stale data, human override) | <10%, 100% with reason codes | Replay engine vs log |

# 7. PM4Py implementation sketch

```python
import pandas as pd
import pm4py

# ---------- Load & format ----------
df = pd.read_csv("service_log.csv")
df = pm4py.format_dataframe(
    df,
    case_col="case:concept:name",
    activity_col="concept:name",
    timestamp_col="time:timestamp"
)  # org:resource, required_skill, ... carried through as event attributes

# ---------- Resource networks (resilience & continuity analysis) ----------

pm4py.save_vis_sna(handover_net, "handover_network.png")

                                       aggregate="mean")           # est_service() inputs

# feed empirical service times per (activity, skill-level) into the scoring function

                if any(act in v for act in ["Technical Diagnosis"]) and v.count("Technical Diagnosis") > 1}

    df, "concept:name", ["Security Review"], level="event", retain=True)

    df, min_performance=0, max_performance=3 * 3600)  # cases resolved < 3h -> SLA-pressure segment

# ---------- Batching audit (rule H6) ----------

              .rename(columns={"level_0": "org:resource", "level_1": "required_skill"}),
              on=["org:resource", "required_skill"], how="left")
ev["mismatch"] = ev["skill"] < 2  # refine with per-activity floors & supervision flags
mismatch_rate = ev.loc[ev["case_priority"].isin(["high", "urgent"]), "mismatch"].mean()

# ---------- Policy replay: deviation indicator ----------
# assign_case(case_ctx, resource_pool) is the scoring function from Section 2, wrapped as a module
deviations = []
for case_id, grp in df.groupby("case:concept:name"):
    ctx = build_case_context(grp)               # owner, SLA, complexity, band, ...
    recommended = policy.assign_case(ctx, resource_pool_snapshot(grp))

    if recommended.resource != executed:
        deviations.append({"case": case_id, "recommended": recommended.resource,
                           "executed": executed, "reason": recommended.reason})
deviation_rate = len(deviations) / df["case:concept:name"].nunique()

# ---------- Weight calibration (offline, quarterly) ----------

```

This closes the loop: the log validates the policy's assumptions (handover penalties, mismatch costs, batching behavior), the replay engine quantifies deviations, and the calibrated weights keep the policy aligned with measured outcomes rather than intuition — while the reason strings keep every decision explainable to the people doing the work.
