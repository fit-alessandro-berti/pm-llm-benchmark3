# Simulation-Based Digital Twin for Building-Permit Process Interventions

## 1. Model scope and state variables

### Digital twin boundary
The twin models the municipal building-permit value stream from portal submission through final issue/reject, including applicant and third-party response delays that affect cycle time. It excludes upstream pre-application advisory (except when intervention D1 adds a pre-submission checker) and downstream construction compliance. External legal appeals beyond a single rework loop are represented statistically, not as full court processes. Council-meeting calendars and public holidays are in scope because they gate Legal check and Public-notice period.

### Level of detail
- **Case-level discrete-event simulation (DES)** with activity instances as work items.
- Mixed **push/pull** semantics: municipal activities compete for scarce calendar-constrained resources; applicant/third-party steps are delay distributions not competing for municipal FTE.
- **Semi-aggregate resources** (pools by role) with skill tags (e.g., Simple-only planners), not individual named-person fidelity beyond pool size—except where architect_id and district drive bundling.
- Explicit **queues and calendars**; service vs waiting split retained wherever estimable.
- **Cross-case entities**: architect bundles, district inspection batches, neighborhood-objection proxies affecting public-notice duration.

### Entities
| Entity | Description |
|--------|-------------|
| Case | Permit application with type, district, architect_id, value, flags (fire/env/notice), risk/violation attributes |
| WorkItem | Activity instance on a case (state: created, queued, in_service, waiting_external, done, rework) |
| ResourcePool | Clerks, planners, fire, environmental, inspectors, legal, system |
| Bundle | Temporary grouping of cases (same architect+district or same district for inspection) |
| Calendar | Weekly shift patterns, peak-season overlays, council blackouts, holidays |
| ObjectionProxy | Latent factor extending public-notice; not observed event-by-event |

### State variables
**Per case:** `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, `prior_violations`, `arrival_time`, `stage`, `pending_predecessors` (AND-join of parallel reviews), `rework_counts` by stage, `objection_drawn`, `bundle_id`, `sla_clock`, `age_priority_flag`.

**Per work item:** activity name, enqueue time, service start, service end, assigned resource, waiting_external flag.

**Global / system:** time-varying arrival intensity (t, dow, season), queue lengths by activity and skill, resource busy/off-shift state, backlog by case type and district, inspection batch boards by district, architect open-case sets, council_meeting_week flag, cumulative issued/rejected counts.

**Resources & queues:** one queue per activity (or shared role queue with activity-specific service distributions); priority can be FCFS, aging-threshold (D6), or batch-ready (D3). System activities have unlimited capacity.

**Calendars:**  
- Clerks 5 FTE Mon–Fri 08:00–16:00 (1 portal-support Monday).  
- Planners 8 FTE Mon–Fri 09:00–17:00 (2 Simple-only).  
- Fire 2 FTE Tue–Thu.  
- Environmental 3 FTE Mon–Fri at 60% permit capacity.  
- Inspectors 4 FTE field Tue–Fri; travel by district.  
- Legal 2 FTE with council-week near-shutdown.  
- Peak-month temporary inspector (D4) overlays calendar.

**Cross-case dependencies (required, not optional):**
1. **Architect bursts:** correlated arrivals; optional inspection/document bundling.  
2. **District inspection batching (D3):** reduce travel, possibly delay first case in batch.  
3. **Neighborhood objections:** shared latent shock can elongate public-notice for co-located cases (proxy model; events not in log).  
4. **Resource contention:** common pools couple otherwise independent cases.  
5. **Policy D2:** skips inspection conditionally—changes inspector load and downstream joins.

The model is **not** an independent-case simulator: arrival generation, batch boards, and shared calendars couple cases continuously.

## 2. Parameter-estimation plan

### Log / model handling with PM4Py
1. Load the event log as a **pandas DataFrame** (CSV/Parquet via `pd.read_csv` / `pd.read_parquet`). Do **not** use a nonexistent `pm4py.read_csv`.
2. `pm4py.format_dataframe(df, case_id="case:concept:name", activity_key="concept:name", timestamp_key="time:timestamp")` then `pm4py.convert_to_event_log` if EventLog API is needed.
3. Discover/compare structure: variants (`pm4py.get_variants`), directly-follows graph (`pm4py.discover_dfg`), performance DFG (`pm4py.discover_performance_dfg`), and optionally align to the provided process tree via `pm4py.parse_process_tree` on the simplified string—treating the string as a **control-flow scaffold**, not a complete executable model (parallel joins, data-dependent XOR, and cross-case logic live in the DES layer).
4. Case attributes (`case_type`, `district`, `architect_id`, etc.) stay as dataframe columns for stratified estimation.
5. Separate modules: `pm_analytics.py` (PM4Py + pandas estimates)  parameter objects  `des_engine.py` (simulation). PM4Py is **not** the simulation engine.

### Arrivals (non-stationary)
- Estimate daily/ hourly counts stratified by `case_type`, weekday, and month (or ISO week).
- Fit a **time-varying Poisson / NHPP** with multiplicative seasonality: (t) =  · s_month(t) · s_dow(t) · s_hour(t), with March–May and Sep–Nov  1.7× Jan–Feb and Monday  2.2× Wednesday as calibration targets (re-estimate from full 18-month log, do not hard-code blindly).
- **Architect burst process:** fit cluster process—e.g., primary arrivals of “architect submission episodes” plus offspring size distribution for same-week related applications (top-20 architects = 31% share). Retain empirical `architect_id` frequency or a Zipf/Pareto head + bulk tail.
- Interarrival generation in sim: thinning or piecewise-constant hourly rates; mark each case with attributes drawn from empirical conditional distributions.

### Service times vs waiting times
- Where only completion timestamps exist, **do not collapse** service and wait into one sojourn without documentation.
- Method: (a) if start stamps exist for a subset, estimate service from startcomplete and wait from previous_completestart; (b) for missing starts, use resource busy-time reconstruction / queueing inversion cautiously, or fit sojourn and impose a **service prior** from the timed subset and expert calendar (median service table given). Tag parameters with `observed_start=True/False`.
- Fit distributions per activity × case_type (lognormal / gamma / phase-type); keep p50/p90 targets from the summary table; heavy tails via mixture or Pareto tail beyond p90.
- Travel time for Site inspection: regression on district (D3/D5 longer) + batch size.

### Branching probabilities
- From log attributes and observed path frequencies: P(missing docs | type), P(fire), P(environment), P(public notice), P(legal check), P(reject | type, path), stratified by `case_type` and available flags.
- For thresholds not in log (building area), use proxy: `requires_fire` / value / type logistic model; mark as uncertain for sensitivity.
- Process-tree XOR/tau branches calibrated to empirical frequencies, not uniform.

### Rework
- Loop probabilities after Planning, Inspection, Legal, and appeal from variant analysis and repeat activity counts in case traces.
- Rework reason text is unreliable  model **stage-specific geometric/ rework probability**, optionally covariate-driven (type, objections proxy), not NLP-based reasons.
- Bound max rework iterations to avoid explosive tails; excess mass goes to “rare long-tail” mixture.

### Resource calendars
- Primary source: HR-reconstructed calendars (as given)—**not** inferred solely from events.
- Validate against observed completion hour-of-week heatmaps; adjust effective FTE (env 40% non-permit; fire part-week; legal council weeks).
- Holidays and council-meeting weeks as calendar exceptions from municipal schedule data.

### Dependencies
- Architect multi-case: estimate P(bundle-eligible), same-week co-submission rates.
- Inspection batching potential: co-occurrence of ready-to-inspect cases by district/day.
- Objection proxy: calibrate public-notice duration mixture (point mass at 14d minimum + long component); correlate shocks within district-time windows without inventing false objection events.

### External / applicant times
- `Receive missing documents` delay from requestreceive empirical distribution (heavy-tailed, median ~5d).
- No-shows / applicant readiness before inspection: estimate from scheduleinspect gaps and cancellations if flagged; else scenario parameters.

### Outputs of estimation
Versioned `Parameters` object: arrival model, branch tables, service distros, wait residuals (if used), calendar specs, rework matrix, dependency kernels, uncertainty metadata (sample sizes, missing-start rates).

## 3. Assumptions

### Arrivals
- NHPP with multiplicative month × weekday × hour effects estimated from 18 months; future years keep same seasonality unless stress scenarios change it.
- Case-type mix stationary at 45/28/17/10% unless an intervention changes intake (D1 may shift completeness mix, not type mix).
- Architect bursts modeled as clustered marks; new architects draw from empirical size distribution.

### Service times
- Service distributions independent of queue length (no speed-up/slow-down) except explicit batch travel reduction.
- Missing start timestamps: service means anchored to timed subset + expert medians; residual sojourn attributed to waiting—**limitation explicitly propagated to uncertainty analysis**.
- System tasks (Issue permit, portal receive) ~ unlimited capacity, low variance.

### Routing
- Process tree is a simplified scaffold: AND of Planning / optional Fire / optional Environmental is real; Decision drafting waits for all required predecessors (explicit join state).
- Fire/environment/public-notice requirements follow case flags plus noisy proxies where data incomplete; misclassification rate is a sensitivity parameter.
- D2 skip-inspection rule uses `application_value < 50000`, `case_type=Simple renovation`, and `prior_violations=False`; violation flag partially synthetic if absent from log.

### Resources / calendars
- HR calendars are ground truth for shift presence; productivity within shift is constant on average.
- Environmental pool: 60% time available for permit work.
- Legal: non-urgent work halted in council-meeting weeks; urgent fraction is a small calibrated share.
- One Monday clerk dedicated to portal support reduces completeness capacity that day—modeled as skill split.

### Rework
- Rework probabilities constant within case type and stage unless policy changes information quality (D1 reduces missing-doc loops; D9 may reduce late objection-driven rework).
- Unstructured rework reasons ignored for routing; only stage recurrence used.
- Appeals lumped into post-decision or pre-issue rework probability with long delay.

### Applicant / third-party response
- Applicant delays are exogenous i.i.d. draws (possibly type-dependent), not resource-constrained inside the municipality.
- D1 increases pre-submit applicant effort (outside cycle time or as pre-arrival delay KPI) but reduces in-process missing-doc probability and Receive delays.
- Consultant reports for environmental review folded into environmental service/wait mixture.

### Cross-case dependencies
- Inspection batching (D3) trades travel time against synchronization delay; batch window is a policy parameter.
- Architect same-district cases may share inspection appointments when D3 or architect bundling enabled.
- Objection shocks are **latent** correlated duration multipliers on public-notice—not simulated as observed log events.
- Log flattening underrepresents dependencies  dependency intensity calibrated conservatively and stress-tested upward.

### Non-stationary demand
- Seasonality and Monday spikes are first-class in arrival generation; steady-state mean busy-period analysis is insufficient alone.
- Peak temporary inspector (D4) only in months where s_month  threshold (e.g., 1.7× baseline months).

### Missing data
- Objection events missing  never treat public-notice long durations as fully explained observed causes; use mixture + sensitivity.
- Rare emergencies removed from log  tail risk slightly understated; add optional tail inflation scenario.
- Start timestamps missing  service/wait split uncertain; report both sojourn-based and split-based calibrations.
- Building area / environmental sensitivity incomplete  probabilistic requirement model with uncertainty.
- No claim that calibrated sim equals ground truth without validation (§6).

## 5. Warm-up, replications, and uncertainty treatment

### Warm-up
- Start empty **or** from a mid-year snapshot of WIP estimated from log (preferred for non-stationary systems).
- Warm-up length: **90 calendar days** minimum, diagnosed via MSER-5 or Welch on backlog and in-system cases; extend if peak season starts inside warm-up.
- KPIs computed only on cases **arrived after warm-up** and **completed before horizon  truncation buffer**, with residual WIP reported separately.

### Run length
- **18–24 simulated months** after warm-up to cover two peak cycles (Mar–May, Sep–Nov) and winter troughs; matches log span for comparability.
- For stress S1–S4, same horizon.

### Replications and seeds
- **R  30** independent replications per experiment (pilot for variance; increase if CI width on p90 duration > policy-relevant threshold).
- Master seed s; replication r uses seed s+r; **common random numbers (CRN)** synchronized across policies for arrival streams, attribute marks, and external delays to reduce pairwise variance.
- Separate streams: arrivals | attributes | municipal service | external delays | objection latent | rework vs accept.

### Confidence / credible intervals
- Report replication means of KPIs with **t-based 95% CIs**; for percentiles (p90 cycle time), use percentile-of-replication-percentiles or batching.
- Optional Bayesian layer: posterior over branch probs and service parameters from log  draw parameters per replication (second-order uncertainty).

### Sensitivity analysis
- One-at-a-time and Morris/Sobol screening on: missing-doc reduction (D1), batch window (D3), peak inspector availability, objection long-tail weight, service/wait imputation mode, fire/env requirement noise, rework probs.
- Tornado charts for top KPIs; **robust ranking**: fraction of parameter draws in which policy A beats B.

### Heavy-tailed durations
- Do not rely on sample means alone; track p50, p75, p90, p95, and conditional tail expectation above p90.
- Use log-scale diagnostics; Winsorize only for variance-reduction diagnostics, never as sole reported KPI.
- Rare-variant mixture (7% “other”) retained; optional importance sampling for Complex variance tails.
- Cap pathological rework loops; count capped cases as tail incidents.

### Non-stationarity
- Never average away month effects in primary KPIs; report **by season and by arrival month** as well as global.
- Compare B0 vs B0-SS to quantify error from ignoring non-stationarity.

## 6. Validation strategy

### Face validation
- Workshops with clerks, planners, inspectors, legal officers: walk through process tree, calendars, batching rules, D2 eligibility, and sample Gantt traces from the sim.
- Confirm that Monday spikes, fire Tue–Thu constraints, and council blackouts “look right.”

### Event-log replay validation
- Replay historical cases through the control-flow scaffold (token-based replay / alignments via PM4Py) to measure fitness of the simplified tree; document deviations (extra skips, hidden activities).
- Soft replay: feed historical arrivals and attributes into DES with historical resource calendars; compare simulated activity enablement order to log order (not expecting perfect timestamp match).

### Distributional validation
- Calibrate on first 12 months; hold out last 6 months (see out-of-sample).
- Compare sim vs log: cycle-time CDF by case_type, activity sojourn p50/p90, waiting before Planning/Inspect/Legal, public-notice duration mixture, rework frequencies, variant share table (7 groups).
- Two-sample tests (KS, quantile-quantile plots) and earth-mover distance on key distributions; tolerance bands agreed with municipality (e.g., median cycle time within 10%, p90 within 15% on major types).

### Resource-utilization validation
- Simulated utilization by role and weekday vs inferred utilization from HR + completion intensity.
- Queue spike timing after Mondays; fire-reviewer midweek load; inspector travel time share by district.

### Bottleneck validation
- Rank activities by waiting contribution and resource congestion; match qualitative expert ranking (planning wait, inspection wait, legal, environmental).
- Congestion fingerprints under peak months should surface the same bottlenecks as log performance DFG.

### Out-of-sample validation
- Train parameters on months 1–12; simulate months 13–18 with frozen params + realized holiday/council calendar; score predictive accuracy on arrivals (if not re-fit), cycle times, backlog trajectory.
- Intervention models cannot be fully validated historically if policies are new: use **partial historical analogues** (e.g., periods with extra inspector overtime as weak D4 proxy) and sensitivity, not claimed proof.

### Dependency validation
- Compare simulated same-architect same-week multi-case rates and district co-inspection opportunities to log co-occurrence statistics.
- Public-notice: validate duration mixture only—not fabricated objection events.

### Explicit non-claims
Validation supports **adequacy for comparative ranking under stated assumptions**, not exact optimality or perfect prediction of untested policies.

## 7. Decision criteria

### Primary metrics (per experiment, post-warm-up)
| Metric | Stratification | Direction |
|--------|----------------|-----------|
| Median cycle time | Global + case_type |  |
| p90 / p95 cycle time | Global + case_type |  |
| SLA compliance | e.g. Simple  30d, New res  90d, Commercial  120d, Complex  180d (municipality-tunable) |  |
| Tail mass | P(cycle > 2× SLA) |  |
| Backlog trajectory | Peak WIP, weeks above threshold |  |
| Rework rate | Loops per case by stage |  |
| Resource utilization | By role; flag >85% sustained or <40% waste | Balance |
| Inspector travel hours | Total and per case |  |
| Fairness | Cycle-time gap across districts; small vs top architects |  disparity |
| Applicant effort | Pre-submit time (D1), appointment wait (D7) | Context |
| Cost proxy | Extra FTE-months (D4), IT/process cost scores for D1/D9 |  |

### Thresholds / selection rules (illustrative; finalize with municipality)
1. **Dominance filter:** drop policies that worsen p90 for any major case_type by >5% vs B0 without compensating SLA gain elsewhere.
2. **SLA target:** achieve 90% SLA on Simple and 80% on New residential in normal demand; 75% Commercial; no Complex p90 blow-up >10% vs B0 unless explained.
3. **Tail equity:** median district gap in cycle time  15% of global median; no district’s p90 worsens >10% under D3 batching.
4. **Utilization:** no pool with sustained replication-mean utilization >90% in peak months (burnout/ risk); temp inspector cost only if peak SLA lift  X percentage points.
5. **Robustness:** policy remains in top-3 rank under S1–S3 and under service/wait imputation sensitivity (S5) for composite score.
6. **Composite score:** weighted sum  
   `0.25·norm(median)+0.25·norm(p90)+0.20·SLA+0.10·fairness+0.10·(1rework)+0.10·cost_inverse`  
   with CRN paired tests; require significant improvement vs B0 (e.g. 95% CI on difference excludes 0) before recommending.
7. **Package rule:** recommend D10 (or other combo) only if interaction gain  50% of sum of standalone gains or if it uniquely meets SLA under S1; else prefer smaller Pareto-efficient subset (e.g. D1+D2+D4).

### Decision output
- Pareto front of interventions on (median, p90, cost, fairness).
- Recommended primary package + fallback under budget constraint.
- **Do not claim exact optimality**—recommend “best among evaluated under validation envelope.”

"""
Building-permit digital twin — analytics + simulation skeleton.
PM4Py is used for log/model handling only; DES is separate.
"""

from __future__ import annotations

import math
import random
from dataclasses import dataclass, field
from typing import Any, Dict, List, Optional, Tuple
from enum import Enum
from copy import deepcopy

import numpy as np
import pandas as pd

# ---------------------------------------------------------------------------
# PM4Py imports (log/model analytics only — not the DES engine)
# ---------------------------------------------------------------------------
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree

# Optional discovery helpers (version-dependent paths may vary slightly)
try:
    from pm4py.statistics.variants.log import get as variants_get
except Exception:  # pragma: no cover - version flexibility
    variants_get = None


# =============================================================================
# 1. Log loading & PM4Py formatting (no pm4py.read_csv)
# =============================================================================

ILLUSTRATIVE_LOG_ROWS = [
    {
        "case:concept:name": "P001",
        "concept:name": "Submit application",
        "time:timestamp": "2026-01-02 09:12:00",
        "org:resource": "portal",
        "case_type": "New residential",
        "district": "D3",
        "architect_id": "A17",
        "application_value": 480000,
        "requires_fire": "yes",
        "requires_environment": "no",
        "requires_public_notice": "yes",
    },
    # ... additional excerpt rows would follow; truncated for brevity in skeleton
]


def load_event_log_dataframe(path: Optional[str] = None) -> pd.DataFrame:
    """Load log via pandas. Never call pm4py.read_csv (not a reliable API)."""
    if path is None:
        df = pd.DataFrame(ILLUSTRATIVE_LOG_ROWS)
    else:
        if path.endswith(".parquet"):
            df = pd.read_parquet(path)
        else:
            df = pd.read_csv(path)
    df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])
    return df


def format_log_for_pm4py(df: pd.DataFrame) -> pd.DataFrame:
    """Apply PM4Py dataframe formatting conventions."""
    formatted = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )
    return formatted


PROCESS_TREE_STRING = (
    "->('Submit application',*(->('Completeness check',X(tau,->('Request missing documents',"
    "'Receive missing documents'))),'Completeness rework'),+('Planning review',X(tau,'Fire-safety review'),"
    "X(tau,'Environmental review')),X(tau,'Public-notice period'),*(->('Inspection scheduling',"
    "'Site inspection'),'Inspection rework'),'Decision drafting',X(tau,'Legal check'),"
    "X('Issue permit','Reject application'))"
)


def parse_process_tree_scaffold(tree_str: str = PROCESS_TREE_STRING) -> ProcessTree:
    """
    Parse the simplified process tree string.

    Limitations:
    - Data-dependent XOR guards (requires_fire, etc.) are NOT in the string.
    - Cross-case bundling, calendars, and joins on parallel review results are NOT
      fully expressed; they must be implemented in the DES layer.
    - tau branches need empirical probabilities from the log.
    - Rework loop exit probabilities are not parameterized in the string.
    """
    tree = pm4py.parse_process_tree(tree_str)
    return tree


@dataclass
class LogAnalyticsResult:
    variants: Dict[Any, int]
    dfg: Any
    performance_dfg: Any
    case_arrival_avg_per_day: float
    framed: pd.DataFrame
    service_waiting: pd.DataFrame
    tree: Optional[ProcessTree]


def enrich_service_waiting_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Derive inter-event sojourn; attempt service/wait split only if start
    timestamps exist. Otherwise sojourn is tagged as undifferentiated.

    Limitation: many human activities lack start stamps — do not silently
    treat sojourn as service time.
    """
    out = df.sort_values(["case:concept:name", "time:timestamp"]).copy()
    out["prev_ts"] = out.groupby("case:concept:name")["time:timestamp"].shift(1)
    out["sojourn_from_prev_hours"] = (
        out["time:timestamp"] - out["prev_ts"]
    ).dt.total_seconds() / 3600.0

    if "start_timestamp" in out.columns:
        out["service_hours"] = (
            out["time:timestamp"] - pd.to_datetime(out["start_timestamp"])
        ).dt.total_seconds() / 3600.0
        out["waiting_hours"] = (
            pd.to_datetime(out["start_timestamp"]) - out["prev_ts"]
        ).dt.total_seconds() / 3600.0
        out["timing_quality"] = "start_and_complete"
    else:
        out["service_hours"] = np.nan
        out["waiting_hours"] = np.nan
        out["timing_quality"] = "complete_only_sojourn"
    return out


def run_pm4py_analytics(df_raw: pd.DataFrame) -> LogAnalyticsResult:
    """PM4Py-based log/model handling — separated from simulation engine."""
    framed = format_log_for_pm4py(df_raw)
    tree = parse_process_tree_scaffold()

    # Variants
    variants = pm4py.get_variants(framed)

    # DFG + performance DFG
    dfg, sa, ea = pm4py.discover_dfg(framed)
    try:
        performance_dfg, psa, pea = pm4py.discover_performance_dfg(framed)
    except Exception:
        performance_dfg, psa, pea = None, None, None

    # Case arrival average (cases per day)
    case_starts = (
        framed.groupby("case:concept:name")["time:timestamp"].min().sort_values()
    )
    if len(case_starts) > 1:
        span_days = (
            case_starts.iloc[-1] - case_starts.iloc[0]
        ).total_seconds() / 86400.0
        case_arrival_avg_per_day = len(case_starts) / max(span_days, 1e-6)
    else:
        case_arrival_avg_per_day = float("nan")

    service_waiting = enrich_service_waiting_columns(framed)

    return LogAnalyticsResult(
        variants=variants,
        dfg=(dfg, sa, ea),
        performance_dfg=(performance_dfg, psa, pea),
        case_arrival_avg_per_day=case_arrival_avg_per_day,
        framed=framed,
        service_waiting=service_waiting,
        tree=tree,
    )

def run_experiment(
    analytics: LogAnalyticsResult,
    intervention: InterventionConfig,
    n_replications: int = 30,
    master_seed: int = 42,
) -> pd.DataFrame:
    rows = []
    base_params = estimate_parameters_from_analytics(analytics, intervention)
    for r in range(n_replications):
        seed = master_seed + r
        # CRN: same seed offset scheme across interventions
        sim = DigitalTwinSimulator(deepcopy(base_params), seed=seed)
        # Peak inspector calendar mutation for D4 would be applied here
        metrics = sim.run()
        metrics["replication"] = r
        metrics["experiment"] = intervention.name
        rows.append(metrics)
    return pd.DataFrame(rows)
