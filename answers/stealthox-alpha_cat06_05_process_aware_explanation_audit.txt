## 1. Leakage and temporal-consistency findings

**Context:** t0 = immediately after the first `Coverage Check Completed`. The prefix at t0 contains only `Claim Registered  Coverage Check Completed`. Anything derived from later events, from closure-time warehouse fields, or from unversioned mutable records is inadmissible. Note also that rank-1 importance (`total_case_duration_hours`, 0.44) is a monotone function of the label itself (breach  duration > 10 days), which distorts all other SHAP values in this model; even "valid" features' attributions are unreliable until retraining.

| Item | Finding type | Severity | Why | Required remediation |
|---|---|---|---|---|
| `total_case_duration_hours` (G1) | Target leakage (label-derived) | **Critical** | Computed after closure; breach is *defined* by duration vs. the 10-day target. Rank-1 "importance" is the leak, not insight. | Remove permanently; audit all features computed from post-t0 timestamps; retrain. |
| `appeal_seen_anywhere` (G2, X) | Future-event leakage (complete trace) | **Critical** | An appeal requires a prior Partial/Deny decision — impossible by t0. +0.26 in Case X is pure hindsight. | Drop as input. If appeal propensity matters, build a separate forward-looking sub-model, never feed realized appeals back. |
| `final_handler_team` (G3) | Outcome-adjacent leakage / unversioned slowly-changing dimension | **High** | Populated at closure; only 65% coincide with the t0 assignment; no availability timestamp  an uncontrolled mix of past and future information. | Replace with `team_assigned_at_t0` from the assignment log; add `valid_from`/`valid_to` history. |
| `num_document_requests_total` (G4) | Future-event leakage; structurally zero at t0 | **Critical** | Counted over the full trace. Evidence cycles begin *after* Coverage Check, so at t0 the prefix count is identically 0 — the model can only have learned from future values. | Drop. A repaired prefix count is constant 0 and carries no information. |
| `queue_length_at_t0` (G5, X, Y) | Valid congestion signal (minor tolerance caveat) | **Low** | Timestamped snapshot, ±5 min tolerance; genuinely available at t0. | Keep; persist the snapshot timestamp; monitor tolerance mismatches. |

## 2. Process-model consistency checks

Proposed suite: **T0-Suite**, run in CI on every feature/explanation change and monthly over full history.

**Check A — Prefix-time availability (point-in-time parity).**
Replay each historical trace to t0; recompute every feature twice: once on the full trace, once on the trace truncated to events with `(event_ts, seq_idx)  t0`, joined against point-in-time dimension tables. Assert equality within tolerance. Any delta = leakage finding. *Limitation:* depends on trustworthy `event_time` metadata; late-arriving/backfilled events can fake availability, and leaks via tables outside the lineage graph are invisible — pair with a static lineage scan.

**Check B — Activity-order feasibility.**
Build the footprint (directly-follows) matrix from the normative model and diff it against the log's matrix. Flag log bigrams absent from the model (e.g., `Claim Closed  Damage Assessment Completed`). Quantify per-trace fitness via token replay or alignments; quarantine low-fitness traces from feature derivation. *Limitations:* real logs contain noise; alignment cost weights are judgment calls; and **a frequent DFG edge is descriptive, not normative** — promoting an edge to a rule requires process-owner sign-off, not frequency alone (e.g., `Decision  Decision` is rare but legal via appeal).

**Check C — Same-timestamp ambiguity.**
Detect event pairs with identical timestamps; require a deterministic total order `(event_ts, sequence_index, ingestion_id)`. Stress test: permute tied events N times, recompute pattern features and local explanations; if attributions flip (as they will for Case Z's pattern), blacklist the feature until the index is backfilled. *Limitation:* even a present index may reflect source-system ordering errors; prefer business lifecycle attributes where available.

**Check D — Complete-trace usage detection.**
Static: parse feature SQL / dbt DAG for references to closure-time tables, full-trace window functions, post-t0 aggregates. Dynamic canary: append synthetic post-t0 events (appeal, decision, close) to a prefix and assert t0 features are invariant.

**Check E — Enabled / impossible / future-possible at t0.**
Maintain the process state machine. `enabled(t0)` after Coverage Check = {`Damage Assessment Completed` (fast track), `Documents Requested`, `Fraud Investigation Opened` (if trigger met)}. Tag every explanation element as *enabled-now*, *future-possible*, or *impossible-before-final-decision* (Appeal, Claim Closed, any Settlement Decision). Explanations citing impossible-or-future items are rejected or auto-rewritten.

**Check F — Repeated Settlement Decision legitimacy.**
Declarative constraints: a second `Settlement Decision Recorded` is valid only if preceded by `Appeal` after a first decision (chain: DEC  (APP  DEC)\*  CLOSE). The variant encoder must canonicalize appeal loops so legitimate appeal cases are not flagged anomalous and variant ids do not explode. *Limitation:* declarative rules are permissive; calibrate support/confidence thresholds with process owners.

**Gate:** explanations may reach user-facing surfaces only if Checks A, C, D, E pass for every displayed driver.

## 3. Alternative feature interpretations

**Defensible predictive signal** — `initial_damage_complexity`, `elapsed_since_registration_at_t0`, `initial_reserve` (once timestamp-verified), `prior_claim_count_before_t0` (after SQL fix), `employee_experience` (after point-in-time fix), `same_day_document_count_at_t0` (after fix, though likely 0 and uninformative at t0).
*May claim:* "In training data, this value was associated with higher/lower breach risk, holding other features fixed." *May not claim:* causation, guarantees, or individual-level judgments.

**Process-state / congestion signal** — `queue_length_at_t0`, `team_assigned_at_t0` (repaired), `role_active_at_t0` (repaired), `fraud_investigation_open_by_t0` (only if event  t0).
*May claim:* current operational state correlates with delay; generates testable intervention hypotheses (staffing, triage). *May not claim:* "congestion causes breaches" without an experiment; SHAP magnitudes are not elasticities.

**Proxy requiring fairness/robustness review** — `claimant_region`, `claimant_channel` (and language if introduced).
*May claim:* statistical association, documented for governance. *May not claim:* causal "delay driver" stories, customer-facing blame, or use as the sole adverse reason code. *Must do:* subgroup calibration and error-gap analysis, indirect-discrimination review, necessity test, and consider replacing with measurable operational mediators (e.g., repair-network capacity at t0).

**Drift/calendar proxy** — `calendar_week`, preferably decomposed into `policy_era` + `holiday_flag`.
*May claim:* period-specific association valid within observed regimes. *May not claim:* stable "bad weeks" or extrapolation across the policy change.

**Unusable until lineage repaired (some never)** — `total_case_duration_hours` and `final_decision` (**never** — they are the label/outcome); `appeal_seen_anywhere` (**never** as a t0 input); `num_document_requests_total` (useless at t0 even repaired); `full_trace_variant_id` (replace with prefix variant); `final_handler_team`, `risk_score_current`, `last_resource_role` (usable only after point-in-time repair); all five reported sequence patterns as specified (all reference post-t0 events; replace with prefix-derived patterns such as registrationcoverage latency or a pre-t0 fraud flag). Until repaired, *nothing* may be claimed about them.

## 5. Recommendations for explanation validation

**P0 — Stop the bleeding (this sprint).**
1. Purge label/outcome features (`total_case_duration_hours`, `final_decision`, `appeal_seen_anywhere`, full-trace variant, full-trace document count) from training *and* serving; retrain. Expect a discrimination drop — publish the honest baseline rather than the inflated one.
2. Redesign the feature store around a single point-in-time API: bitemporal storage (`event_time` vs. `ingestion_time`), every feature carrying explicit `as_of` semantics; forbid extraction-date joins (fixes `prior_claim_count`, `employee_experience`).
3. Backfill historical feature timestamps: `valid_from`/`valid_to` for mutable fields (`risk_score`, team assignment, resource role); stored snapshot timestamps for queue and document counts.

**P1 — Rebuild trust (1–2 months).**
4. Prefix-only recomputation harness: replay historical t0s, recompute all features from prefixes, diff against production values to quantify leakage magnitude; rebuild training sets from prefix replay.
5. Calibration after feature removal: recalibrate (isotonic/Platt) on time-based validation splits; track Brier/ECE; re-derive operating thresholds against the 10-day target and communicate the change to consumers.
6. Process-conformance tests in CI: footprint/alignment/declarative suite (Checks B, E, F), the same-timestamp policy (Check C), and the canary counterfactual test (Check D). Failures block promotion of any explanation.

**P2 — Explanation quality (quarter).**
7. Explanation stability: perturbation tests, seed variance, tied-event permutation sensitivity; publish stability metrics next to SHAP output; auto-reject explanations that flip under tied-event shuffles.
8. Proxy/fairness analysis for `claimant_region`, `claimant_channel`, language: mutual information with sensitive attributes, subgroup calibration and error gaps, necessity testing (does removal materially hurt?), and a documented decision to keep-with-documentation, transform to an operational mediator, or drop. Governance sign-off required for any customer-facing reason code.

**P3 — Continuous assurance.**
9. Monitoring: feature-distribution drift (PSI), schema-change alerts, process-drift detection (variant drift, novel DFG edges, rising alignment costs), and policy-change/holiday annotations fed into calendar features. Quarterly re-audit of top-k importances for re-emergent leakage; shadow-mode evaluation for any new feature before it can appear in an explanation.
10. Explanation-layer guardrail: a linter that routes every displayed driver through the availability (A/C/D) and enabled-activity (E) checks before it reaches a user, so "predictive" is never silently rendered as "causal" or "actionable."
