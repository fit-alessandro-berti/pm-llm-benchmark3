## 1. Temporal Data Semantics

### State Reconstruction
- **Blanks**: A blank cell in the event log indicates no update to that attribute at the event timestamp. The last known state is forward-filled from earlier events within the same case.
- **Changing Attributes**: Attributes like `amount`, `risk_level`, `jurisdiction`, and `customer_type` are mutable over time. Their values at a specific event must be reconstructed based on preceding updates.
- **Final Attributes**: The state at the end of the case does not retroactively apply to earlier events unless explicitly established through evidence or rules.
- **Material Changes**: Significant changes to attributes (e.g., an `amount` increase > 20% or `jurisdiction` update) may invalidate prior reviews depending on timing and rule specifics.
- **Effective vs. Event Time**: Each attribute update takes effect at its event timestamp unless evidence suggests an earlier or later effective time. Late database records or approvals are assessed separately for evidential reliability.
  
### Equal Timestamps
When two events share the same timestamp, `event_index` governs their ordering. For instance, two updates at the same timestamp but different indexes are resolved sequentially within that moment.

### Event Time, Effective Time, Record Time, Evidence Time
- **Event Time**: The recorded time when the event occurred in the system.
- **Effective Time**: When the change actually took effect, which may be earlier/later than the event time (e.g., due to delayed evidence or approvals).
- **Record Time**: Timestamp when the event was entered into the database.
- **Evidence Time**: The time when evidence for an event, approval, or exemption is dated, which may differ from the event or record time.

### Rule Logic

- **R1**:  
  ```prolog
  release_funds(Case) :- amount(Case, A), jurisdiction(Case, J), A >= 100000, J != DE,
                         enhanced_review(Case, T1), T1 > last_change(Case), 
                         not valid_exemption(Case, R1), 
                         occurs_before(T1, release_funds(Case)).
  ```
- **R2**:  
  ```prolog
  release_funds(Case) :- (risk_level(Case, HIGH) ; customer_type(Case, PEP)),
                         enhanced_review(Case, T1), compliance_approve(Case, T2),
                         occurs_before(T1, T2), occurs_before(T2, release_funds(Case)).
  ```
- **R3**:  
  ```prolog
  release_funds(Case) :- jurisdiction(Case, J), added_to_sanctions_list(J, T1),
                         sanctions_screen(Case, T2),
                         occurs_before(T1, T2), occurs_before(T2, release_funds(Case)).
  ```
- **R4**:  
  ```prolog
  invalid_review(Case) :- amount_increased_over_20_percent(Case),
                          review(Case, T), T < last_increase(Case).
  ```
- **R5**:  
  ```prolog
  valid_exemption(Case, Rule) :- exemption(Case, E), approved(E, Head_Compliance),
                                 scope_matches(E, Case), effective(E, T),
                                 T <= obligation_trigger_time(Case, Rule).
  ```
- **R6**:  
  ```prolog
  indeterminate(Case) :- missing_required_data(Case, Data),
                         not inferable(Case, Data).
  ```
- **R7**:  
  ```prolog
  evaluate(Case) :- occurs_before(event(Case, E1), event(Case, E2), TimeOrder),
                    snapshot_at(event(Case, E), State).
  ```

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-State Leakage**: Control-flow cannot propagate changing attributes forward/backward adequately.  
2. **Post-Hoc Exemptions**: Late evidence cannot alter past control-flow faithfully.  
3. **Material Changes**: Control dependencies may break when `amount`, `risk`, or `jurisdiction` changes.  
4. **Conditional Activation**: Rules based on data constraints (e.g., thresholds) cannot be modeled.  
5. **Missing Data**: Defaulting to normal paths skips nuanced considerations, violating policy principles.  
6. **Same-Timestamp Ordering**: Events with the same timestamp must preserve `event_index`, which control-flow lacks.

---

## 7. Recommended Logging and Control Improvements

1. **Immutable Release Payloads**: Log final release data as immutable snapshots.  
2. **Comprehensive Change Provenance**: Record rationale for all material data changes.  
3. **Effective/Record Timestamp Separation**: Distinguish effective and log timestamps.  
4. **Rule Versioning**: Capture the version of policy rules applied.  
5. **Ordered Event IDs**: Assign a globally unique, timestamp-resilient ordering field.  
6. **Exemption Clear Definitions**: Augment exemptions with explicit scopes and signatures.
