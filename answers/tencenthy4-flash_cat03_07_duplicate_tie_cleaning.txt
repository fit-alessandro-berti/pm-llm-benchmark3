## 1. Duplicate-handling decision tree

Apply tests in this order; stop at the first terminal decision.

1. **Exact technical duplicate?** Same original event identity or identical business timestamp, activity, source, source event key, payload hash, and E2O relation set.
   - **Decision:** drop one copy, keeping a provenance pointer to the absorbed event ID.
   - No such pair is present in the supplied raw table.

2. **Same physical event observed by multiple systems?** Explicit reconciliation evidence states that two records describe one physical occurrence, even if payloads differ because of enrichment.
   - **Decision:** merge attributes and relations into one canonical event; retain both original IDs, sources, labels, payload hashes, and source event keys in provenance.
   - Examples: e03/e04; e11/e16 under invoice V1.

3. **Summary event derived from detailed event?** One record is ERP/status/balance-level summary generated from another system’s transaction, but has its own lifecycle meaning or lacks the detailed object dimension.
   - **Decision, conservative:** retain both with refined labels/qualifiers; do not merge by default.
   - **Decision, evidence-based option:** merge into the detailed event only when the summary has no independent lifecycle value and the relation is one-to-one.
   - Examples: e06/e07; e13/e14/e15.

4. **Harmonization collision between semantically distinct source activities?** Different source activities were mapped to one common label.
   - **Decision:** retain both with refined labels or qualifiers describing source semantics.
   - Examples: e08 = warehouse release, e09 = carrier acceptance.

5. **Concurrent same-label events involving different objects?** Same activity and timestamp but different item/payment/delivery object identity.
   - **Decision:** retain both, preferably qualify by object or sub-type.
   - Examples: e03/e05 for I1/I2; e13/e14 for M1/M2.

6. **Unresolved candidate?** Equal activity/timestamp/object overlap but no reliable domain evidence.
   - **Decision:** quarantine for review in a separate review table; do not delete for analysis.

## 3. Timestamp-tie ordering rules

Use a partial-order-first policy. The resulting total order is an analysis convention, not proof of true physical order.

**Semantic rules:**

1. **Domain constraints:** activity meaning defines order where known: e08 warehouse release before e09 carrier acceptance before e10 handover; e12 authorization before e13 capture; invoice issuance before payment.
2. **Source-specific semantics:** use the meaning of harmonized activities before relying on labels. e08 and e09 are not interchangeable despite both being labeled Dispatch Package.
3. **Within-source sequence:** `source_seq` may order events only inside the same source. Valid examples: e04  e05 in SCANNER; e12  e13  e14 in PSP; e09  e10 in CARRIER. Invalid: comparing e03’s WMS sequence with e06’s ERP sequence.
4. **Lifecycle constraints on shared objects:** pick of I1/I2 before pack of I1/I2; pack before dispatch; M1 authorization before M1 capture. Shared objects constrain lifecycle but do not prove duplicate status.
5. **Derived-summary ordering:** ERP summaries generated from downstream messages are placed after the detailed events they summarize: e06  e07; e13/e14  e15.

**Deterministic-only rules:**

6. **Ingestion time:** may break remaining ties, but is technical metadata and must never be the primary business order.
7. **Stable fallback:** sort by original timestamp, semantic rank, source priority, zero-padded `source_seq`, `source_event_key`, then `eid`.

Adding microseconds before semantic reasoning encodes a false story: it turns concurrency, equal-second timestamps, and derived summaries into a precise duration and causal sequence. Microseconds are acceptable only as a downstream display/indexing device after semantic order is established, and `original_timestamp` must remain unchanged.

- **10:00, conservative:** e03/e04 merged into e03; e05; e06; e07.  
  Equivalent if e04 retained: {e03,e04} tied physical scan block, then e05, e06, e07.

- **12:00, conservative:** e11/e16 merged invoice issuance  e12 authorize M1  e13 capture M1  e14 capture M2  e15 ERP summary.

# ---------- generic helpers ----------

def get_event_col(ocel, canonical_attr, *fallbacks):
    c = getattr(ocel, canonical_attr, None)
    if c in ocel.events.columns:
        return c
    for f in fallbacks:
        if f in ocel.events.columns:
            return f
    raise KeyError(f"Could not find event column for {canonical_attr}; tried {fallbacks}")

def eid_col(ocel):
    c = getattr(ocel, "event_id_column", "ocel:eid")
    return c if c in ocel.events.columns else None

def event_ids(ocel):
    c = eid_col(ocel)
    if c is not None:
        return ocel.events[c].astype(str)
    return pd.Series(ocel.events.index.astype(str), index=ocel.events.index)

def mask_eid(ocel, eid):
    c = eid_col(ocel)
    if c is not None:
        return ocel.events[c].astype(str) == str(eid)
    return ocel.events.index.astype(str) == str(eid)

    for c in [getattr(ocel, "event_id_column", "ocel:eid"), "ocel:eid", "eid"]:
        if c in ocel.relations.columns:
            return c
    raise KeyError("No event-id column found in OCEL relations")

    for c in [getattr(ocel, "object_id_column", "ocel:oid"), "ocel:oid", "oid"]:
        if c in ocel.relations.columns:

    if getattr(ocel, "object_id_column", "ocel:oid") in ocel.objects.columns:

        src_rank = SOURCE_PRIORITY.get(src, 99)
        seq = str(row.get("source_seq", "")).zfill(6)
        key = str(row.get("source_event_key", ""))
        fallback.append(f"{src_rank:02d}|{seq}|{key}|{ids.loc[i]}")

    ord_df = pd.DataFrame(
        {"ts": ev[ts].values, "base": base.values, "fb": fallback},
        index=ev.index
    ).sort_values(["ts", "base", "fb"], kind="mergesort")

    ord_df["order_rank"] = range(len(ord_df))
    ev["order_rank"] = ord_df["order_rank"]
    ev["order_basis"] = "semantic constraints, then deterministic tie-break"
    out.events = ev
    return out

def sort_by_additional_column_safe(ocel, column):
    fn = pm4py.ocel_sort_by_additional_column
    sig = inspect.signature(fn)

    for name in ["column", "additional_column", "attribute_name", "key"]:
        if name in sig.parameters:
            result = fn(ocel, **{name: column})
            return result if result is not None else ocel

    if "parameters" in sig.parameters:
        result = fn(ocel, parameters={"column": column})
        return result if result is not None else ocel

    result = fn(ocel, column)
    return result if result is not None else ocel

def add_index_timedelta_safe(ocel):
    # Called only AFTER establish_semantic_order(). Original timestamp is preserved.
    try:
        result = pm4py.ocel_add_index_based_timedelta(ocel)
    except TypeError:
        result = pm4py.ocel_add_index_based_timedelta(ocel, parameters={})
    return result if result is not None else ocel

def pm4py_merge_duplicates_aggressive(ocel):
    params = {
        "merge_attributes": True,
        "merge_objects": True,
        "have_common_object": True
    }
    fn = pm4py.ocel_merge_duplicates
    sig = inspect.signature(fn)

    kwargs = {k: v for k, v in params.items() if k in sig.parameters}
    unknown = {k: v for k, v in params.items() if k not in kwargs}

    if "parameters" in sig.parameters:
        kwargs["parameters"] = unknown

    try:
        result = fn(ocel, **kwargs)
    except TypeError:
        result = fn(ocel, parameters=params)
    return result if result is not None else ocel

| Dataset | Events / E2O | Flattened DFG effects | OCEL-sensitive effects |
|---|---:|---|---|
| Raw | 17 / 44 | Order DFG contains duplicate Pick, Pack, Dispatch, Invoice, Capture steps. Item DFG has two I1 picks and one I2 pick. Payment DFG has M1 capture and M2 capture. | OC-DFG and ET–OT weights are inflated by repeated observations. OTG creates redundant O1–I1–P1 links. Many zero-duration same-second transitions. |

| Evidence-based merge | 14 / 37 | Pack  Pack disappears; detail and ERP status become one activity. Pick  Pick and Capture M1  Capture M2 remain. | Pack ET–OT weight changes; ERP status abstraction lost. Lifecycle shorter but simpler. |
| Aggressive library merge | ~10 / ~28 | Pick  Pick, Pack  Pack, Dispatch  Dispatch, and Capture  Capture largely disappear. Apparent process becomes deceptively linear. | False OTG links: merged pick links I1/I2; merged capture links M1/M2 and ERP summary. ET–OT and OC-DFG frequencies no longer represent event occurrences. |

Concrete interpreted patterns:

1. **Pick Item  Pick Item:** true distinct I1/I2 picks in conservative data; false duplicate scan loop in raw; removed entirely by aggressive merge.
2. **Pack Package  Pack Package:** raw suggests pack rework; conservative labels it detail  ERP summary; evidence/aggressive remove it.
3. **Dispatch Package  Dispatch Package:** raw hides two logistics meanings; conservative becomes release  carrier acceptance; aggressive removes both observations.
4. **Dispatch Package  Handover to Carrier:** conservative preserves release  acceptance  handover; aggressive collapses acceptance into release.
5. **Issue Invoice  Issue Invoice:** raw duplicate-system effect; conservative merge removes it.
6. **Capture Payment  Capture Payment:** conservative represents distinct M1/M2 captures plus ERP summary; aggressive merge hides partial-payment distinction.
7. **Authorize Payment M1  Capture Payment M1:** preserved only if M1 relation is protected.
8. **M1–M2 co-occurrence:** appears only after unsafe unioning relations; it is not supported by raw business facts.

Durations and lifecycle metrics change materially: raw has many zero-second transitions; conservative semantic ranking gives small ordered transitions without pretending exact sub-second times; `ocel_add_index_based_timedelta` creates synthetic durations that must not be interpreted physically.

Also retain a canonical-to-raw mapping table. To reconstruct the raw view:

1. Start from the audit table and canonical events.
2. Expand each absorbed `source_event_id` back into its original event row using stored original activity, timestamp, source, source key, payload hash, and attributes.
3. Restore original E2O relations from stored relation additions/removals.
4. Drop synthetic `order_rank` and indexed timestamps.
5. Reapply the original event IDs and labels.

If complete raw rows are also archived, reconstruction is exact; the audit table explains why each transformation occurred.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments:** safeguard: never merge e13/e14; require identical Payment object or explicit evidence.
2. **Turning abstraction updates into rework:** safeguard: refine e07/e15 labels before DFG mining.
3. **Ordering by ingestion time:** safeguard: use ingestion only after semantic constraints, never as primary business order.
4. **Treating shared objects as proof of duplication:** safeguard: shared O1/V1 is review evidence only; e13/e14 prove why.
5. **Unioning incompatible E2O relations:** safeguard: union only when events are verified one physical/business event; otherwise retain relations per event.
6. **Changing durations through synthetic microseconds:** safeguard: keep `original_timestamp`; label adjusted timestamps as derived.
7. **Losing source-authoritative attributes:** safeguard: store source-specific fields before overwriting canonical attributes.
8. **Applying duplicate functions to the whole OCEL:** safeguard: run candidate pre-check and verified-pair logic first.
9. **Using harmonized labels as semantics:** safeguard: preserve `original_activity` and add refined labels for e08/e09.
10. **Using `source_seq` across systems:** safeguard: compare sequence values only within the same source.
11. **Assuming equal timestamps imply concurrency or identity:** safeguard: separate semantic concurrency from deterministic tie-breaking.
12. **Deleting legitimate same-label events:** safeguard: never merge equal activity/timestamp alone; e05 and e14 must remain.
