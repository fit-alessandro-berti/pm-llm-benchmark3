## 1. Duplicate-handling decision tree

- **Exact technical duplicate** (same `source`, `source_event_key`, `payload_hash`):
  - Decision: **Drop**. Keep one instance and record the dropped `eid` in the audit trail.
- **Same physical event observed by multiple systems** (different `source`, overlapping `related objects`, known reconciliation facts):
  - Decision: **Merge attributes and relations**. Retain one canonical event, preserving conflicting payloads as list-valued attributes.
- **Summary event derived from a detailed event** (one event has fewer objects and is ingested later, representing a system status update from a downstream message):
  - Decision: **Retain both with refined labels or qualifiers**. Append qualifiers like `(Summary)` or `(Status)` to the summary event to preserve abstraction levels.
- **Harmonization collision between semantically distinct source activities** (same mapped activity label but different original source meanings and lifecycle positions):
  - Decision: **Retain both with refined labels or qualifiers**. Rename to reflect the true source semantics (e.g., `(WMS Release)` vs. `(Carrier Accept)`).
- **Concurrent same-label events involving different objects** (same activity and timestamp but distinct disjoint object subsets, like distinct items or payments):
  - Decision: **Retain both unchanged**.
- **Unresolved candidate** (similar events but lacking evidence or domain rules to prove a relationship):
  - Decision: **Quarantine for review**. Do not modify until a human or domain rule resolves the tie.

## 3. Timestamp-tie ordering rules

To define a deterministic partial-order-to-total-order policy, we apply the following rules in priority order:
1. **Domain constraints** (Semantic): Known business rules (e.g., `e10` must follow `e09`; `e12` must precede `e13`).
2. **Within-source sequence** (Semantic): `source_seq` defines intra-system ordering (e.g., WMS `e03` -> `e06` -> `e08`).
3. **Lifecycle constraints on shared objects** (Semantic): An object must complete a lower-level state before moving to a higher-level state (e.g., `P1` must be packed (`e06`/`e07`) before it is dispatched (`e08`)).
4. **Source-specific semantics** (Semantic): Transition meanings dictate order (e.g., warehouse release (`e08`) precedes carrier acceptance (`e09`), which precedes handover (`e10`)).
5. **Stable fallback order** (Deterministic): Alphabetical/numerical sorting of `eid`.
6. **Ingestion time** (Deterministic, non-semantic): Used *only* to sequence events if no other deterministic fallback exists, but never as primary business order.

**Why adding microseconds before deciding the semantic order can encode a false story:** 
Arbitrarily injecting microseconds to break ties bypasses semantic analysis. If we assign `e09` a synthetic microsecond before `e08`, we encode the false story that the carrier accepted the package before the warehouse released it. Deterministic tie-breaking must be the *output* of semantic ordering, not a replacement for it. Synthetic timestamps should only be added *after* the order is established, to satisfy systems that require strictly unique timestamps, without altering the visible business sequence.

**Intended orders:**
- **e03–e07 at 10:00:** `e03` (merged with e04), `e05` (concurrent with e03), `e06` (pack details), `e07` (pack summary). Admissible order: `e03`, `e05`, `e06`, `e07`.
- **e08–e10 at 10:15:** `e08` (WMS release), `e09` (Carrier accept), `e10` (Handover). Admissible order: `e08`, `e09`, `e10`.
- **e11–e16 at 12:00:** `e11` (merged with e16), `e12` (authorize), `e13` (capture M1), `e14` (capture M2), `e15` (ERP summary). Admissible order: `e11`, `e12`, `e13`, `e14`, `e15` (or `e11`, `e12`, `e14`, `e13`, `e15`).

def verified_pair_merge(ocel, e1_key, e2_key, canonical_eid):
    """
    Custom merge logic for proven multi-source physical duplicates.
    Retains attributes from both, unions E2O relations.
    """
    events_df = ocel.events.copy()
    relations_df = ocel.relations.copy()
    
    e1_idx = events_df[events_df['source_event_key'] == e1_key].index[0]
    e2_idx = events_df[events_df['source_event_key'] == e2_key].index[0]
    
    # Preserve e2 payload as list in e1

    events_df.loc[e1_idx, 'merged_sources'] = f"{events_df.loc[e1_idx, 'source']};{events_df.loc[e2_idx, 'source']}"

    relations_df = relations_df[relations_df['ocel:eid'] != e2_oid]
    
    ocel.events = events_df
    ocel.relations = relations_df
    return ocel

## 8. Audit trail and reversibility

**Provenance Schema:**
- `canonical_eid`: The retained event ID (e.g., `e03`).
- `source_eids`: JSON array of original event IDs merged into this canonical event (e.g., `["e03", "e04"]`).
- `merge_rule`: The rule applied (e.g., `SamePhysicalEventMultiSource`, `LabelRefinement`, `None`).
- `reviewer_or_rule_version`: ID of the human reviewer or rule engine version (e.g., `v1.2`).
- `original_activity`: The raw activity label (e.g., `Dispatch Package`).
- `refined_activity`: The updated activity label (e.g., `Dispatch Package (WMS Release)`).
- `original_timestamp`: The original UTC timestamp (e.g., `2026-05-18 10:15:00`).
- `adjusted_timestamp`: The deterministic timestamp used for sorting (e.g., `2026-05-18 10:15:00.000008`).
- `attributes_retained`: JSON map of attributes kept from each source (e.g., `{"ERP": "h-invoice-erp", "BILLING": "h-invoice-billing"}`).
- `discarded_conflicts`: JSON array of conflicts that were resolved by dropping data (e.g., `["payload_hash mismatch"]`).
- `confidence`: Float between 0 and 1.
- `reason`: Textual justification for the decision.

**Reconstruction of the raw view:**
An analyst can reconstruct the raw OCEL by joining the cleaned `events` table with the audit trail table on `canonical_eid`. By iterating over the `source_eids`, the analyst can explode the canonical events back into their original `eid`s. The `original_activity` and `original_timestamp` columns allow the analyst to restore the exact pre-cleaning state. The `discarded_conflicts` and `attributes_retained` provide full transparency into any semantic data loss.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments:** Failing to recognize `e13` and `e14` as distinct because they share `V1` and `O1`. 
   *Safeguard:* Always check the specific Payment object (`M1` vs `M2`) before merging.
2. **Converting abstraction-level updates into false rework:** Merging or dropping `e07` or `e15` without labels, or treating them as loops.
   *Safeguard:* Use refined labels to distinguish summary events from detailed events.
3. **Ordering by ingestion time:** Using `ingested_at` to order `e08`, `e09`, `e10`, which would place the carrier acceptance before the WMS release.
   *Safeguard:* Explicitly exclude `ingested_at` from semantic ordering rules.
4. **Treating shared objects as proof of duplication:** Assuming `e03` and `e05` are duplicates because they share `O1`, `P1`, and the timestamp.
   *Safeguard:* Require exact object set matches or strong domain rules for duplicate classification.
5. **Unioning incompatible E2O relations:** Merging `e15` (which lacks `M1`/`M2`) with `e13` and dropping the Payment objects, losing the link between `V1` and `M1`.
   *Safeguard:* Never drop relations from detailed events when merging with summary events.
6. **Changing durations through synthetic microseconds:** Assigning arbitrary microseconds to `e12` and `e13` that alter the perceived authorization-to-capture delay.
   *Safeguard:* Add microseconds only as a secondary deterministic column, preserving the original timestamp for duration calculations.
7. **Losing source-authoritative attributes:** Dropping `e16` without keeping the billing system's invoice payload, which might hold the canonical tax calculation.
   *Safeguard:* Custom merge functions must store discarded payloads in a list-valued attribute.
8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups:** Using `pm4py.ocel_merge_duplicates` globally, which blindly collapses `e13` and `e14`.
   *Safeguard:* Pre-group candidates and apply verified custom merges before using any library-wide mechanical functions.
