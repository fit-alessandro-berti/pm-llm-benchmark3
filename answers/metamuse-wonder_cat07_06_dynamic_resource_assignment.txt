# 1. Objectives and constraints

There is no single optimum here. Specialist routing minimises errors today but creates Security and Approval queues; first-available routing minimises waiting today but increases handovers, mismatches and rework tomorrow; continuity minimises handover cost but can perpetuate a weak skill match — the evidence given quantifies both sides: $>2$ reassignments $\rightarrow$ 1.8x rework, 1.4x appeals; handover on high-complexity cases $+$2.7h waiting; keeping a weak-skilled owner $+$3.3h service time and more rework. The policy below therefore optimises a *weighted, auditable bundle*, with weights shifting by SLA urgency and complexity, and with hard rules that no score can override.

## Objectives (to be balanced, in shifting priority order)

1. **Meet SLAs and protect urgent/high-value cases** — throughput where delay is costly.
2. **Minimise error, rework and appeal risk** — skill match, especially on complex cases.
3. **Preserve continuity of case ownership** — avoid handovers where they are expensive or repeated.
4. **Fair, sustainable workload** — open cases, hours remaining, overtime risk, and new assignments per batch.
5. **Skill development** — route suitable work to trainees *safely*, so today's bottleneck does not become permanent.
6. **Resilience** — avoid single-person dependency on scarce skills (Security, Approval, Diagnosis); keep more than one credible route per activity.

## Hard constraints — safety / compliance (never traded away)

- **H1 Skill floor:** skill 0 = never assigned. Security Review: skill 3 only, or skill 1–2 *only* under named supervision by R7_Gita or R8_Hugo. Final Approval: finaliser must be skill 2–3; skill 1 may prepare, not finalise.
- **H2 Trainee protection:** no high-priority case to skill $<2$ unless supervised by a named skill-3 resource who retains accountability.
- **H3 Batch cap:** max 4 new assignments per resource per decision batch.
- **H4 Overtime protection:** no new work to overtime-risk = "high" resources unless the case is urgent *and* no safer alternative exists; any such exception must be logged with a reason.
- **H5 Mandatory escalation:** urgent case with no eligible, non-overloaded resource escalates to a human duty manager rather than silently breaking H1–H4.

## Soft constraints — preference trade-offs (scored, explainable)

- **S1 Continuity:** prefer current owner, weighted by `handover_cost_band`, complexity and `reassignment_count` (penalty grows steeply at $\ge 3$ reassignments).
- **S2 Workload fairness:** prefer lower open cases / more hours remaining, not merely first-free.
- **S3 Training:** $\ge 20\%$ of normal/low-priority assignments should serve a *documented* training priority, provided SLA risk stays acceptable (H5 in the scenario brief).
- **S4 Batching:** Quality Check may be batched only if priority is normal/low and SLA remaining $>24$h.
- **S5 Bottleneck avoidance:** penalise piling work onto scarce-skill resources when a competent alternative exists; reserve some specialist capacity for incoming urgent work.

# 2. Assignment policy

Design principles: (i) hard-filter first, score second — a high score can never resurrect an ineligible resource; (ii) every score component is a named, worker-visible reason; (iii) weights are *dynamic* — SLA urgency and complexity change what matters; (iv) every assignment writes `assignment_reason`, supervisor (if any), score breakdown, and any exception to the event log.

```text
POLICY Assign(queue, resources, skill_matrix, log_history):
  FOR each case, ordered by SLA urgency (most urgent first):

    # ---- Stage 1: eligibility filtering (hard rules) ----
    candidates = resources WHERE skill[required_skill] > 0
    IF activity == "Security Review":
        keep skill == 3, OR skill in {1,2} WITH available supervisor in {R7,R8}
    IF activity == "Final Approval":
        finaliser skill in {2,3}; skill == 1 allowed only as "prepare" role
    IF priority == high/urgent AND skill < 2 AND no supervisor available:
        remove candidate
    IF overtime_risk == "high" AND priority != urgent:
        remove candidate        # H4; urgent exceptions logged, not silent
    IF new_assignments_this_batch == 4: remove candidate     # H3
    IF hours_remaining < estimated_service_time(activity, complexity,
                                                from historical service times):
        remove candidate
    IF candidates empty: ESCALATE to duty manager; do not relax H1/H2

    # ---- Stage 2: scoring (each term normalised 0..1) ----
    FOR each candidate r:
      sla_fit      = feasibility: can r start + finish before deadline,
                     given queue ahead of this case?  (1 = comfortable)
      skill_match  = skill(r)/3, boosted if complexity > 0.7
                     (specialist premium on complex work)
      continuity   = 1 if r == current_owner
                     else 1 - handover_penalty(band, complexity,
                                                 reassignment_count)
                     # penalty ~0 for low/none, steep if count>=3
      fairness     = 1 - normalised(open_cases, hours_used,
                                    overtime_risk, batch_load)
      training     = 1 if required_skill == r.training_priority
                        AND priority in {normal, low}
                        AND (skill(r) >= 2 OR supervised)
                        AND sla_fit acceptable
                     else 0   # never let training endanger an SLA
      resilience   = 1 - bottleneck_penalty:
                     penalise if r is one of <=2 holders of a scarce
                     skill AND a competent alternative exists;
                     reward building a second competent holder

      # dynamic weights: urgency raises sla/skill, complexity raises
      # skill/continuity, slack raises training/fairness
      w = weights(priority, complexity, sla_remaining)
      score = w1*sla_fit + w2*skill_match + w3*continuity
            + w4*fairness + w5*training + w6*resilience

    # ---- Stage 3: tie-breaking & exceptions ----
    rank by score; tie-break in order:
        (a) current owner, (b) lower open cases,
        (c) documented training priority, (d) lower overtime risk,
        (e) earliest available — never by personal favour
    IF winner is skill 1-2 on Security / skill 1 preparing Approval /
       trainee on any high-priority case:
        attach named supervisor; supervisor keeps accountability;
        record supervised_pair in log
    IF winner != current_owner AND handover_cost == high:
        require reason code (e.g. "owner skill 1 on urgent complex
        security case") — handover must be justified, not accidental
    IF Quality Check AND priority in {normal,low} AND sla > 24h:
        optionally batch with same-resource Quality cases
    WRITE to log: assignment, supervisor, score components,
                  assignment_reason, exception flags
  RETURN assignments
```

Key behaviours this produces: urgent/complex cases gravitate to specialists *or* to a competent owner (continuity can beat a marginal skill gain); slack cases become the training and fairness-relief pool; scarce specialists are deliberately *not* given work a competent colleague can do, preserving surge capacity.

# 4. Comparison with baseline policies

| Criterion | First-available | Specialist-only | Proposed dynamic policy |
|---|---|---|---|
| Expected throughput | Good short-term: queues drain to whoever is free; but mismatch-driven rework quietly eats the gain | Poor–mixed: excellent per-case speed, but Security/Approval queues (few skill-3 holders) become the constraint | Good: urgent work is expedited, routine work flows to competent (not only specialist) staff; batching adds Quality throughput |
| SLA risk | Low for the average case, high tail risk: an urgent Security case can land on a merely-available worker | High for scarce-skill activities: C001-type cases wait behind every other Security case at Gita/Hugo | Lowest tail risk: SLA feasibility is scored first for urgent cases; specialists are *reserved* rather than consumed by routine work |
| Error / rework risk | Highest: ignores specialisation beyond skill 0; C007 would likely gain a 4th handover | Lowest per case handled, but delay-induced rushed work and queue pressure offset some benefit | Low: skill premium scales with complexity; supervision makes trainee work safe instead of forbidden or reckless |
| Fairness of workload | Superficially fair (fewest open cases) but unfair in substance: ignores hours, overtime risk, case difficulty — David (14 cases) looks "available" by some measures | Unfair: loads Gita, Hugo, Farid, Celine relentlessly; high-overtime staff unaffected only by luck | Explicitly scored: open cases, hours, overtime risk, batch cap; high-overtime staff protected with logged exceptions only (David/C003) |
| Skill development | Accidental: trainees get whatever is free, including work they should not touch | None: trainees never touch real work, so scarcity is permanent | Deliberate: $\ge$20% of slack work routed to documented training priorities, supervised (C009, C010, C015) |
| Continuity of ownership | Worst: maximises handovers; repeats the $>2$-reassignment rework pattern | Mixed: often overrides the owner in pursuit of the top skill score | Explicitly priced: continuity wins unless owner skill is 0/1, supervision is infeasible, or overload justifies a medium-cost move (C014) |
| Resilience to absence / bottlenecks | Fragile in a hidden way: broad but shallow capability, lots of context-switching | Most fragile: if Hugo or Gita is absent, Security stops; single points of failure are the design | Strongest: competent tier is used and grown, specialists keep surge headroom, shadowing/supervision builds second holders of scarce skills |

Honest caveat: the proposed policy is more complex to run and explain than either baseline, and its advantage depends on the skill matrix and workload data being kept honest and current. Its per-case decisions will occasionally be slower than first-available (C009) or less "perfect" than specialist-only (C016) — that is the price of the other objectives, paid deliberately and visibly.

# 5. Explanation to workers

> **How your next case is chosen — and why**
>
> When a case is ready for its next step, we first check who is *allowed and safe* to do it: the right skill level, supervision where the rules require it (for example, Security and Final Approval work), and enough time left in your day. No score or algorithm can override those safety rules.
>
> After that, we weigh a few things openly: how urgent the case is, how well it matches your skills, whether you already own the case (handing over costs the customer time, so we avoid it unless there's a good reason), how much you already have on, and — for quieter work — whether the case would help you build a skill you've said you want to develop. That's why you may sometimes get a case that isn't your strongest skill: it's a planned, supervised learning case, and a named specialist backs you up. It's also why you may *not* get a case in your best skill: we deliberately keep some specialist capacity free so an urgent case never has to queue behind routine work.
>
> If you're already carrying a heavy load or are at risk of overtime, the system steers new work away from you. Occasionally it will still keep a case with you — for instance, if you're the specialist who already owns it and moving it would harm the customer — and when that happens, the reason is recorded and your manager should discuss it with you, not just let the system decide silently.
>
> Every assignment carries a written reason you can see. If an assignment looks wrong — wrong skill, too much load, a learning case you're not ready for — challenge it. Overrides are allowed, they're logged, and they help us improve the rules. This system is here to make the fairness of work visible, not to rank or punish anyone: no one's performance is judged by these scores.

# 6. Process-mining audit indicators

Review weekly (operational) and monthly (policy). All indicators computable from the stated event-log columns.

| Indicator | Definition (from log fields) | Warning signal |
|---|---|---|
| Handover frequency | Share of events where `org:resource` $\ne$ `current_owner` of previous event in case; handovers per case, by activity/team (`handover_cost_band` split) | Rising share, especially high-band handovers without reason codes |
| Reassignment count | Distribution of `reassignment_count` per case at completion; % cases with $>2$ | $>2$ share rising toward the 1.8x-rework regime |
| Skill mismatch | % events where performer skill (matrix joined on `required_skill`) $<$ 2; % high-priority events with skill $<$ 2 unsupervised; Security/Approval rule violations | Any hard-rule violation; mismatch concentrated on one team |
| Workload distribution | Open cases and assigned hours per resource per day from `workload_snapshot`; Gini coefficient / max–min spread; assignments per batch vs cap of 4 | Persistent top-decile concentration; cap breaches |
| Overtime risk exposure | % new assignments to `overtime risk = high` resources, split urgent/non-urgent, with exception reasons | Non-urgent assignments to high-risk staff $>$ 0 without justification |
| SLA misses | % cases completing after `sla_deadline`, by `case_priority`, activity, assigned resource skill tier | Urgent misses; misses following trainee or handover assignments |
| Rework / appeal after assignment | Rate of Rework Correction events and repeat-activity loops within a case, grouped by reassignment count, handover occurrence, performer skill tier, supervised vs not | Rework rate for reassigned/mismatched cases vs kept-owner baseline drifts up |
| Training assignment share | % normal/low-priority assignments where `required_skill` matches assignee's training priority (from `assignment_reason`), supervised share thereof | $<$ 20% over a month, or training occurring on high-priority work |
| Specialist bottleneck indicators | Queue length and waiting time for Security/Approval/Diagnosis; utilisation of skill-3 holders; % specialist time spent on routine (low-complexity) cases | Specialist waiting time rising while specialists do routine work — the scarcity trap |
| Deviations from assignment policy | % events whose `assignment_reason` is missing, an override, or inconsistent with the logged score/rule outcome; override rate by manager/team | Overrides $>$ ~10%, missing reasons, or overrides systematically favouring/penalising individuals |

Any indicator breach triggers review of *weights or data quality first* (stale skill matrix? wrong workload snapshot?) before blaming individuals.

# 7. PM4Py implementation sketch

The log is used in two loops: *learn* (estimate service times, handover costs, bottleneck structure to calibrate the scorer) and *audit* (Section 6 indicators on the deployed policy).

```python
import pm4py
import pandas as pd

# --- Load & format -------------------------------------------------------
log_df = pd.read_csv("event_log.csv")
log_df["time:timestamp"] = pd.to_datetime(log_df["time:timestamp"])
log = pm4py.format_dataframe(
    log_df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp")

# --- Resource structure: who hands over to whom, who works together ------
handover_net   = pm4py.discover_handover_of_work_network(log)   # handover cost / continuity risk
together_net   = pm4py.discover_working_together_network(log)   # natural supervisor pairs
similarity     = pm4py.discover_activity_based_resource_similarity(log)  # backup resources
roles          = pm4py.discover_organizational_roles(log)       # validate skill matrix vs reality
pm4py.view_sna(handover_net)          # or pm4py.save_vis_sna(...) for audit reports

# Frequent (activity, resource) pairs seen in the nets but absent from the
# skill matrix => matrix is stale; pairs in the matrix never seen in the
# log => claimed skill is unproven. Feed both back to HR review.

# --- Performance calibration ---------------------------------------------
perf_dfg, start_acts, end_acts = pm4py.discover_performance_dfg(log)
# waiting hotspots between activities -> where handovers hurt most

log = pm4py.insert_case_service_waiting_time(log)   # adds service/waiting per case
service = pm4py.get_service_time(log)               # per-activity service-time estimates
# -> used by the policy for: hours feasibility (Stage 1) and
#    handover_penalty calibration (compare waiting after owner change
#    vs kept-owner, per complexity band)

batches = pm4py.discover_batches(log)   # check Quality batching behaviour & legality

# --- Audit slices ---------------------------------------------------------
urgent   = pm4py.filter_event_attribute_values(log, "case_priority",
                                               ["urgent", "high"])
security = pm4py.filter_event_attribute_values(log, "concept:name",
                                               ["Security Review"])
slow     = pm4py.filter_case_performance(log, 0, 7*24*3600)  # long-running cases
variants = pm4py.get_variants(log)      # e.g. loops signalling rework after reassignment

# Indicator examples:
# skill mismatch  = join events to skill matrix on required_skill/org:resource,
#                   flag skill<2 or Security/Approval rule breaks
# training share  = normal/low cases whose assignment_reason cites training
# deviations      = rows with assignment_reason missing or marked "override",
#                   cross-checked against handover_net (unexpected handovers)
```

**Closed loop:** monthly, the audit indicators and the learned networks/times are compared with the scorer's assumptions — e.g., if `discover_handover_of_work_network` shows a growing R3$\rightarrow$R8 handover channel with rising waiting time in the performance DFG, the continuity penalty for that channel is raised; if role discovery shows Jonas now routinely performs Diagnosis competently, his matrix entry — not just his score — is updated. The policy stays explainable because every parameter change traces to a named, inspectable mining result rather than to a black-box retraining.
