## 1. Conformance semantics

I treat the norm as **open-world except where the specification explicitly closes it**. In practice:

- **Forbidden behavior**: any observed relation matching a forbidden norm ID is a violation if the observation is confirmed as a real business event and within scope. Forbidden edges are closed-world: their absence is never a violation.
- **Missing mandatory behavior**: a mandatory relation is required only when the stated scope applies. An absent edge is a candidate violation, but I do not call it a violation until I have ruled out abstraction mismatch, incomplete event capture, or a legitimate exception.
- **Unexpected but unregulated behavior**: relations not covered by any normative row are deliberately outside the norm. They receive no compliance weight; they may still be useful for process discovery or future norm revision.
- **Typical-pattern absence**: a typical status means the pattern is desirable but not required. Absence, or a substitute pattern such as a write-off, is compatible with the norm if a legitimate exception exists.
- **Likely data-quality error**: an observation that is more plausibly a join artifact, missing-link problem, or identifier collision than a business act. I quarantine it until verified; if verified, it may become a forbidden or mandatory finding.
- **Abstraction mismatch**: the graph summary uses directly-follows edges while the norm states an eventual expectation. A missing direct edge can therefore be an artifact of the abstraction, not a process failure.
- **Insufficient evidence**: counts alone cannot establish causation, object identity, scope membership, or exception status. Findings in this class are monitored, not escalated.

This means that closed-world reasoning applies only to forbidden relations already present and to mandatory columns within their scope. For all other observations, absence from the norm is not noncompliance.

## 3. Detailed reasoning by model family

### OC-DFG

The OC-DFG family establishes object-level event transitions. It can show how often one event type directly follows another within the lifecycle of an object type. That is useful for mandatory and forbidden direct-flow rules, and for typical pattern monitoring.

It cannot establish **eventual compliance** from a direct-follows graph alone. N1 says every newly created standard Order should *eventually* enter validation, while the observed summary approximates this with a directly-follows edge. If an order has `Create Order  Manual Compliance Review  Validate Order`, the direct edge `Create Order  Validate Order` is absent, but the Order is still conforming at the eventual level. The same reasoning applies to N4: `Pack Package  Dispatch Package` may be absent because other event types occur between packing and dispatch, while the package was still packed before shipment.

The central danger is treating an “eventually expected” rule as a directly-follows rule. That conflation produces false violations for legitimate intermediate events and false confidence when a direct edge exists but the eventual property is not checked. The manually observed counts should therefore be interpreted as diagnostic summaries, not as normative verdicts.

### OTG

The OTG model family establishes persistent relationships between object types, usually through shared events or object interactions. It can show that an Order and an Item are connected, or that a Package and a Delivery are connected. It is therefore well suited for checking mandatory relation existence such as T1 and T2.

OTG cannot establish per-event object attachment. For example, the OTG edge `(Package, object_interaction, Delivery)` has weight 200, which appears conforming to T2. But the ET–OT summary shows only 198 Dispatch Package events with a Delivery object. The OTG edge may aggregate pair interactions across events, so it can hide event-level gaps. Similarly, `(Order, object_interaction, Item)` has weight 1450, but only 1448 Add Item events have an Order object. A relation can be conforming at the OTG abstraction and suspicious at the ET–OT abstraction. The correct interpretation is that OTG and ET–OT answer different questions: OTG says the object-to-object relation exists; ET–OT says each individual event carried the required object link.

### ET–OT

The ET–OT model family establishes which object types participate in each event type. This is the closest model to the mandatory event-object columns in E1–E10. It can detect missing object associations per event type, such as `Dispatch Package` events without a Delivery, or `Add Item` events without an Order.

It cannot establish causal ordering, object identity correctness, or whether an object link was generated by a real business interaction or by a data-quality artifact. It also cannot decide whether a missing Invoice link on a Record Payment event is a violation or a legitimate unapplied-cash exception. That distinction must come from event attributes and process context.

Counts and scopes matter. For E2 and E3, the scope is every Add Item event. If there are 1450 Add Item–Item links and 1448 Add Item–Order links, two events are missing the mandatory Order object. That is suspicious, but the two events may be extraction errors rather than process failures. For E8, one Record Payment event lacks an Invoice. Because the norm only accepts unapplied cash when explicitly typed, and this event is not typed, the formal conformance result is a mandatory-edge gap. If finance later confirms unapplied cash, the same observation becomes a legitimate typical exception. This illustrates how an observation can be a violation under one norm interpretation and conforming under another.

def classify_against_norms(observed_graph, norm_meta):
    """Separate semantic layer. Does not mutate raw PM4Py results."""
    semantic = []
    for key, (status, scope) in norm_meta.items():
        count = observed_graph.get(key, 0)
        row = {
            "relation": key,
            "observed_count": count,
            "status": status,
            "scope": scope,

            row["semantic"] = "typical_pattern" if count > 0 else "typical_absent"
        else:
            row["semantic"] = "unregulated"
        semantic.append(row)
    return semantic

## 6. Norm-completeness assessment

1. **Eventual versus directly-follows semantics.** N1 and N4 state eventual expectations, but the summaries use direct-follows edges. Operational risk: false violations for legitimate intermediate events. Clarification: define mandatory conformance as object-lifecycle reachability; retain direct-follows only as a diagnostic abstraction. Status: mandatory for the eventual property; direct-follows reporting is explicitly not a standalone violation.

2. **Scope definitions.** “Standard Order” and “externally shipped Package” are not precisely defined. Operational risk: objects may be incorrectly included in or excluded from mandatory checks. Clarification: add object attributes such as `order_type` and `shipment_scope`. Status: mandatory for scope determination.

3. **Exception labels for N5 and E8.** Write-offs, credit notes, open credit terms, and unapplied cash are legitimate but are not explicitly labeled in the snapshot. Operational risk: genuine payments or receivables cannot be distinguished from missing data. Clarification: require an event attribute or object state such as `exception_type` or `payment_allocation`. Status: typical for the exception itself; mandatory for labeling it.

4. **OTG versus ET–OT relationship semantics.** The summary contains apparent contradictions, such as 200 OTG Package–Delivery edges but only 198 Dispatch Package–Delivery event links. Operational risk: a relation may appear compliant at one abstraction while a mandatory event-object link is missing. Clarification: define OTG as an aggregate object-pair graph and ET–OT as event-level participation; use the event-level check for E2, E6, and E8. Status: mandatory.

5. **Cross-object forbidden paths.** N3 forbids a package dispatch after cancellation of the same Order, but the summary does not show how Packages are linked to Orders. Operational risk: forbidden paths may be missed if the join key is wrong. Clarification: require a stable `package.order_id` reference and event timestamps/order state. Status: mandatory.

6. **Data-quality artifacts.** The Sensor Heartbeat–Invoice edge is caused by a reused numeric identifier. Operational risk: data joins can create fake forbidden findings and erode trust in conformance output. Clarification: enforce identifier namespace validation and quarantine suspicious joins before normative interpretation. Status: mandatory data-quality control.

7. **Frequency and tolerance bands.** The norm states no minimum frequencies or statistical tolerance bands. Operational risk: rare benign behavior may be escalated incorrectly. Clarification: establish monitoring baselines and escalation thresholds outside the normative specification. Status: explicitly unspecified for the norm; monitoring is a separate operational practice.

## 7. Investigation and remediation plan

**Immediate containment**
- **N3 (highest severity):** identify the two cancelled Orders with later dispatch events. Block any further shipment activity for those Orders, confirm whether packages are recoverable, and notify operations and customer service.
- **T6 (second highest severity):** isolate the event where an Order and Payment were born together. Suspend any automated process that creates both objects in one event, and inspect the source integration for misused lineage logic.
- **E10:** quarantine the Sensor Heartbeat–Invoice relation and enforce unique identifiers before any further object-centric analysis.

**Data repair**
- Repair the two Dispatch Package events that lack Delivery links by using the carrier references to create or attach Delivery objects.
- Repair the two Add Item events that lack Order links, if the Order identifiers exist in event payloads.
- Label the single Record Payment event as unapplied cash or link it to the correct Invoice.
- Re-run ET–OT and OTG discovery after data repair and reconcile the counts.

**Process investigation**
- Trace the two Orders missing CreateValidate; determine whether Manual Compliance Review occurred before validation.
- Trace the two externally shipped Packages missing PackDispatch; determine whether they were never packed or the direct edge was interrupted by intermediate events.
- Review the 14 invoices with no observed successor to separate open credit terms, write-offs, and genuinely unpaid invoices.

**Norm revision**
- Add explicit eventual-vs-direct semantics for N1 and N4.
- Define exception labels for N5 and E8.
- Specify the join keys and event-object requirements for N3, T2, and E6.
- Decide whether Manual Compliance Review–Customer and Package codeath edges should be formalized or remain explicitly unspecified.

**Monitoring**
- Track weekly counts of forbidden edges, missing mandatory event-object links, and suspected data-quality artifacts.
- Use run charts to derive baselines; escalate only when a statistical or business threshold is crossed.

## 8. Uncertainty statement

Robust conclusions: the observations of Cancel Order  Dispatch Package, Order object_cobirth Payment, and Sensor Heartbeat  Invoice are the only explicitly forbidden graph edges in the snapshot. If the object links are true business events, N3 and T6 are high-severity violations; E10 is more plausibly a data-quality error. The unspecified relations such as Reopen  Close, Manual Compliance Review  Customer, and Package codeath are not violations under the current norm.

Conclusions that depend on norm incompleteness: mandatory-edge gaps for N1 and N4 depend on whether “eventually” rather than “directly follows” is the correct semantics. The missing Invoice on one Record Payment depends on whether the unapplied-cash exception is typed.

Conclusions that depend on suspected data-quality issues: the two missing Delivery links, the two missing Order links, the Sensor Heartbeat edge, and the disagreement between OTG counts and ET–OT counts.

What cannot be decided from graph summaries alone: causal order, whether an object ID was reused incorrectly, whether a missing object link reflects a process failure or an extraction failure, and whether the 14 invoices without successors are delinquent or legitimate open terms. These require event attributes, source-system audit logs, and business confirmation.
