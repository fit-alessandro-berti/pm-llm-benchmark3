## 2. Process-model consistency checks

A concrete validation suite must distinguish **what is possible in the process** from **what is observed in data**, and must enforce **prefix-time admissibility**.

1. **Prefix-time availability audit (event-log check)**  
   For each feature, extract the maximum event timestamp used in its computation (e.g., latest `Document Received`, `Assessment Completed`, `Settlement Decision`, `Close`). Reject the feature for `t0` explanation if `max_timestamp > t0`. For `total_case_duration_hours`, `full_trace_variant_id`, `appeal_seen_anywhere`, and `final_handler_team`, this audit will flag critical failure.

2. **Activity-order feasibility (footprint / DFG + normative constraints)**  
   Build a normative footprint: `Claim Registered`  `Coverage Check Completed`; from there enabled activities are either `Damage Assessment Completed` (fast track) or `Documents Requested`; `Fraud Investigation` is enabled after a trigger but not required; `Settlement Decision Recorded` requires prior assessment/evidence; `Appeal` requires prior `Partial`/`Deny`; `Claim Closed` requires final decision or `Withdrawn`. Check sequence patterns: `Claim Closed  Damage Assessment Completed` violates this footprint; it can only appear due to timestamp collision or ingestion error. **Limitation:** A frequent DFG edge (e.g., `Appraisal  Settlement`) is not a normative rule; only the declared order constraints are.

3. **Same-timestamp ambiguity check**  
   For every event pair with identical timestamps (Case Z: `Claim Closed` and `Damage Assessment Completed`), check for a reliable sequence index. If missing, the order is undefined. Reject any sequence-pattern explanation that depends on that pair. Optionally apply a conservative ordering (e.g., process-knowledge ordering) and flag uncertainty.

4. **Complete-trace feature detection**  
   Inspect feature-store SQL / logic: does the query include events with `timestamp > t0` or reference `case_end_time`? For `full_trace_variant_id`, `num_document_requests_total`, `appeal_seen_anywhere`, `final_handler_team`, and `last_resource_role`, the answer is yes. Create a “prefix-only” mirror pipeline that computes features using only events with `event_time <= t0`.

5. **Enabled / impossible / future-possible at `t0`**  
   At `t0` (immediately after first `Coverage Check Completed`), determine enabled activities:
   - Enabled: `Damage Assessment Completed` (if fast-track authorized); `Documents Requested`; `Fraud Investigation Opened` (if trigger met).
   - Future-possible: `Settlement Decision Recorded`; `Appeal`; `Claim Closed`.
   - Impossible at `t0`: `Claim Closed`; `Appeal` (requires prior decision); second `Settlement Decision` (requires first decision + appeal).
   Any explanation referring to impossible activities (`Claim Closed`, `Appeal` as observed) is invalid; any explanation referring to future-possible activities must be labeled as “potential future pathway,” not current state.

6. **Repeated `Settlement Decision Recorded` validation**  
   Check that second occurrence is preceded by `Appeal` and that first decision was `Partial` or `Deny`. If a case shows `DEC  CLOSE` with a second `DEC` but no `Appeal`, flag semantic inconsistency. Use sequence conformance (e.g., token replay or Declare rules: `Response(Appeal, Decision)`).

## 5. Recommendations for explanation validation

**Priority 1 — Feature-store design and provenance**  
Build a feature store that distinguishes `raw_event`, `derived_feature`, and `timestamp_of_knowledge`. Every derived feature must record: (a) the set of source events, (b) the maximum `event_time` used, (c) the extraction/as-of time (`t0`). Features requiring events after `t0` must be automatically excluded from the predictive pipeline at `t0`.

**Priority 2 — Historical feature timestamps and prefix-only recomputation**  
Recompute the entire feature matrix using only events with `timestamp <= t0`. For `prior_claim_count_before_t0`, enforce `< t0`; for `same_day_document_count_snapshot`, use `received_time <= t0`; for `final_handler_team`, use assignment event at `t0`; for `queue_length`, validate the snapshot is within ±5 min of `t0`. After repair, retrain/recalibrate; expect performance drop and do not report original SHAP values.

**Priority 3 — Process-conformance and prefix checks**  
Implement prefix-based conformance: for each case at `t0`, check that the prefix `REG-COV` conforms to allowed next activities (`Damage Assessment` or `Documents Requested`, etc.). Use footprint/Declare rules, not just frequent DFG edges, to enforce that `Appeal` requires `Partial`/`Deny`, that `Claim Closed` requires final decision, and that `Damage Assessment` precedes `Settlement`. Reject sequence-pattern explanations that violate normative precedence.

**Priority 4 — Same-timestamp and ambiguity handling**  
Require sequence index for all events. Where index is missing and timestamps collide (Case Z), do not derive sequence patterns; instead flag and use conservative ordering only if external process rules demand it. Document uncertainty in explanations.

**Priority 5 — Calibration and explanation stability**  
After removing leaked features (`duration`, `full_trace_variant_id`, `appeal_seen_anywhere`, future `final_decision`), recalibrate the model. Monitor explanation stability: local SHAP values should change smoothly as the prefix lengthens; if they jump discontinuously because a future event becomes visible, that indicates leakage.

**Priority 6 — Proxy/fairness analysis and causal boundary**  
Audit `claimant_region`, `channel`, and reserve proxies for disparate impact. Separate predictive validity (allowed) from operational actionability (requires mechanism) and causal claims (requires intervention design). Always include a “causal claim boundary” statement in explanations: predictive association is shown; causal effect and operational efficacy are not established.

**Priority 7 — Monitoring for schema/process drift**  
Monitor `calendar_week` for policy/holiday shifts; if new evidence cycles or fraud triggers change, update the normative process model and feature definitions. Alert if `queue_length` snapshot timing drifts or if `same_day` refresh changes; if `final_handler_team` warehouse logic changes, break the lineage. Maintain a drift log linking feature provenance to process changes.

**Priority 8 — Explanation validation pipeline**  
Before publishing any explanation, run an automated audit script that checks: (i) all feature event times <= `t0`; (ii) no sequence pattern violates normative order; (iii) no future-possible activities are presented as observed; (iv) mutable un-timestamped scores are excluded; (v) fairness-sensitive proxies are flagged; (vi) causal language is absent. Only pass after audit.
