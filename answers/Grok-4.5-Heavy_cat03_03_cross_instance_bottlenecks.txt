## 1. Interaction-graph description

The typed interaction graph is multi-partite with the following important node types:  
Job {J1…J6}, Component {C1…C6}, ComponentLot {L7, L8}, Machine {CNC-2, OVEN-1, TEST-1}, Tool {FIX-A, RACK-7, CAL-3}, Batch {B1, B2}, Shipment {S1, S2, S3}.

Important edge types and qualifiers (drawn from the supplied O2O relations plus the timing evidence):  
- Job —requires→ Component (direct, frequency 6)  
- ComponentLot —contains→ Component (direct)  
- Batch —batches→ Job (direct)  
- Shipment —consolidates→ Job (direct)  
- Job —uses→ Tool (inferred from acquire/release timestamps for FIX-A and CAL-3; direct for RACK-7 via batch events)  
- Job —processed_on→ Machine (inferred from process/test/cure events)  
- Batch —occupies→ Machine + Tool (B1 and B2 both occupy OVEN-1 and RACK-7)  
- ComponentLot —quarantines/releases→ Component (and inconsistently → Job)

At least three higher-order motifs:  
1. Batch-synchronization motif: Batch ↔ Job* ↔ Machine ↔ Tool (B1 links J1/J2/J3 to OVEN-1 and RACK-7; the single Batch Cure event at 12:05 simultaneously relates all six objects).  
2. Tool-contention motif: Job ↔ Tool ↔ Machine (J3 holds FIX-A while J4 waits at CNC-2; J5 holds CAL-3 while J6 waits at TEST-1).  
3. Lot-release coupling motif: ComponentLot ↔ Component* ↔ Job* (L7 simultaneously affects C2/J2 and C5/J5; the Quarantine Lot / Release Lot events are only partially projected onto the Job view).  
4. Consolidation motif: Shipment ↔ Job* (S1 forces J1, already packed at 13:30, to wait for J4).

Edges that are inferred: waiting times “attributable to batch synchronization,” the causal link from FIX-A hold to CNC-2 idle gap, the attribution of TEST-1 idle time to CAL-3 recalibration, and any Job–ComponentLot edge that an alternative integration pipeline would have materialised but the primary extraction did not.

## 2. Quantitative delay decomposition

All calculations use only the supplied timestamps. Each result is presented under an explicit counterfactual; none is claimed as proven causality.

1. Avoidable / synchronisation-induced waiting for J1 in B1  
   Ready 08:10, B1 starts 12:05 → 3 h 55 min.  
   Counterfactual: if the batch policy allowed start as soon as the first ready job arrived (or if RACK-7 / OVEN-1 could have been allocated earlier), the 3 h 55 min would not have been incurred. (Evidence table itself labels the figure “Waiting attributable to batch synchronization if readiness is trusted.”)

2. Avoidable / synchronisation-induced waiting for J2 in B1  
   Ready 08:25, B1 starts 12:05 → 3 h 40 min.  
   Same counterfactual as above.

3. Delay plausibly associated with FIX-A for J4  
   J3 releases FIX-A at 11:40; J4’s Machine Process on CNC-2 starts at 11:45. CNC-2 was already idle from 10:05–10:47.  
   Measured gap from end of CNC-2 idle window to process start: 58 min.  
   Counterfactual: if FIX-A had been free when J4 reached CNC-2 (09:50), the process could have started at or shortly after the observed idle window (≈10:47), eliminating the 58 min.

4. Delay imposed on J1 by S1 consolidation  
   J1 packed 13:30; S1 dispatches 19:25 → 5 h 55 min.  
   Counterfactual: if the shipment policy allowed dispatch of a ready job without waiting for its consolidation partner, J1 would have left at or near 13:30 + loading time.

5. Delay plausibly associated with CAL-3 for J6  
   J6 ready ≈16:05; Final Test starts 17:25. CAL-3 is recalibrated 16:35–17:20 after J5 finishes.  
   Measured wait from ready time to test start: ≈1 h 20 min, of which the recalibration occupies 45 min and the subsequent idle-to-start gap is 5 min.  
   Counterfactual: if CAL-3 had not required recalibration after every use (or if a second calibrator existed), J6 could have started immediately after J5 released TEST-1 (≈16:35), eliminating ≈50 min.

Additional calculation (RACK-7 cleaning spill-over into B2):  
OVEN-1 idle 12:55–14:50 (1 h 55 min) while RACK-7 is in “cleaning/quarantine” until 14:35.  
Counterfactual: if RACK-7 cleaning had finished by 12:55, B2 could have started as soon as J4 was ready (13:10), reducing the idle interval by roughly 1 h 25 min.

## 4. What flattening misses

**Job flattening**  
Visible: ordinary activity sequence (Release → Stage → Machine Process → Inspect → Pack/Rework → Dispatch) and per-job cycle times (none extreme).  
Hidden/duplicated: batch-synchronisation waits, tool-acquisition waits, post-pack shipment waits, lot-quarantine events (explicitly omitted by the extraction rule), and any multi-job coupling.  
Misleading conclusion: “no individual job is an outlier, therefore the process is healthy.”

**Machine flattening**  
Visible: utilisation percentages, typical sequences, longest inter-event gaps.  
Hidden: why the gaps exist (tool or rack unavailable, batch not yet complete).  
Misleading conclusion: “machines are under-utilised, therefore capacity is not the problem” – correct but incomplete; the true constraints sit one level above the machine.

**Batch flattening** (if performed)  
Visible: the two batch start events and the jobs they contain.  
Hidden: the readiness times of the constituent jobs and the shared-tool (RACK-7) cleaning state that delayed B2.  
Misleading conclusion: “batches are infrequent, therefore low impact” (the Interaction Summary already warns against this inference).

**Tool flattening**  
Visible: acquire/release pairs for FIX-A and the recalibration interval for CAL-3.  
Hidden: the jobs that were blocked while the tool was held, and the fact that RACK-7 is also a tool shared across batches.  
Misleading conclusion: tool occupancy looks modest until the waiting jobs are linked.

**ComponentLot flattening**  
Visible: Quarantine Lot and Release Lot for L7.  
Hidden: which jobs are blocked (because the primary extraction did not project the events onto Jobs) and the supervisor override that allowed J2 to proceed.  
Misleading conclusion: lot events appear isolated from the job life-cycle.

**Shipment flattening**  
Visible: Create → Load → Dispatch with short medians.  
Hidden: how long already-packed jobs wait for their consolidation partners (5 h 55 min for J1).  
Misleading conclusion: “shipment process is fast.”

Low machine utilisation coexists with long job waiting because the machines are frequently idle for lack of a complementary shared resource (RACK-7, FIX-A, CAL-3) or because a batch policy forces early-ready jobs to wait for late-ready siblings. The waiting is therefore synchronisation and contention delay, not queueing for scarce machine time.

## 5. Object-lifecycle evidence

Narrative A – B1 synchronisation cascade (Job, Batch, Machine, Tool, Component, Shipment)  
Temporal precedence: J1 ready 08:10, J2 08:25, J3 11:55; single Batch Cure at 12:05 on OVEN-1 with RACK-7; later J1 packed 13:30, waits in S1 until 19:25.  
Resource feasibility: OVEN-1 and RACK-7 must be jointly free; only one rack is recorded.  
Policy constraints: batch policy requires all three jobs before start.  
Causal speculation: the 3 h 55 min and 3 h 40 min waits are the direct consequence of the policy plus the shared rack; the subsequent S1 wait is an independent consolidation policy.

Narrative B – FIX-A contention (Job, Tool, Machine, Component)  
Temporal precedence: J3 acquires FIX-A 09:00–11:40; J4 arrives at CNC-2 09:50; CNC-2 idle 10:05–10:47; J4 process starts 11:45 (relating J4, C4, CNC-2, FIX-A).  
Resource feasibility: only one FIX-A exists.  
Policy constraints: no recorded “Wait for Tool” activity; acquisition is exclusive.  
Causal speculation: the 58 min gap after the observed idle window is most economically explained by the late release of FIX-A; alternative explanations (operator absence, material) are not contradicted by the data but are less parsimonious.

Narrative C – L7 quarantine + CAL-3 chain (ComponentLot, Component, Job, Batch, Tool, Machine, Shipment)  
Temporal precedence: L7 quarantined 10:20 (C2, C5, J2, J5); released 13:50; J2 already inside B1 by supervisor override; J5 waits, joins B2 at 14:50; later J5 tests 16:10–16:35, CAL-3 recalibrated 16:35–17:20, J6 tests 17:25–17:50; both enter S3.  
Resource feasibility: single CAL-3; single RACK-7 for B2.  
Policy constraints: lot-release gate; mandatory recalibration after Final Test; shipment consolidation.  
Causal speculation: the lot event created a common-mode delay for two otherwise independent jobs; the override broke the coupling for J2 only; the subsequent CAL-3 recalibration serialised J5 and J6. The data show precedence and resource exclusion but do not prove that an earlier lot release would have accelerated the entire chain.

## 6. Intervention portfolio and spillovers

1. Dynamic / size-1 batching on OVEN-1 (or rack-aware release)  
   Target: batch synchronisation.  
   Expected benefit: eliminate 3–4 h waits for early-ready jobs in B1.  
   Helped: J1, J2 (and analogous future jobs).  
   Harmed: possibly J3 if single-job curing is less efficient; oven utilisation may fall further.  
   New cost/risk: more frequent rack cleaning cycles; thermal-profile validation for single jobs.  
   Perverse-incentive metric: “batch count” or “oven starts per day” (could encourage trivial batches).  
   Object-centric evaluation: compare pre/post distribution of (batch-start – min readiness) across all Batch–Job edges; monitor RACK-7 occupancy.

2. Duplicate or pre-position critical tools (second FIX-A, second CAL-3, or second RACK-7)  
   Target: shared-tool contention.  
   Expected benefit: remove the 58 min FIX-A gap and the ≈50 min CAL-3 serialisation.  
   Helped: J4, J6 and future jobs that share the same tools.  
   Harmed: capital and maintenance cost; possible increase in calibration labour.  
   New cost/risk: tool-identity errors if the second unit is not perfectly interchangeable.  
   Perverse-incentive metric: “tool utilisation %” (could discourage releasing a tool early).  
   Object-centric evaluation: measure idle-time of Machine while Tool is held by another Job; track Tool–Job acquire/release intervals.

3. Ship-when-ready (or two-tier consolidation) policy for S1-type shipments  
   Target: shipment consolidation.  
   Expected benefit: remove the 5 h 55 min wait of J1.  
   Helped: early-packed jobs (J1 and analogues).  
   Harmed: transport cost if partial shipments become frequent; possible later jobs lose volume discounts.  
   New cost/risk: more complex routing; higher per-shipment fixed cost.  
   Perverse-incentive metric: “on-time shipment count” (could encourage shipping empty or near-empty).  
   Object-centric evaluation: (dispatch time – pack time) distribution per Shipment–Job edge; total logistics cost per Job.

4. Mandatory bidirectional linking of ComponentLot events to every affected Job (logging improvement)  
   Target: data-integration artefacts.  
   Expected benefit: make lot-induced waits visible in Job-centric views; eliminate the need for supervisor overrides that hide coupling.  
   Helped: analytic transparency for J2/J5-type situations.  
   Harmed: none operationally; slight extra logging effort.  
   New cost/risk: over-linking if a lot event is only partially relevant.  
   Perverse-incentive metric: “number of linked objects per event” (could encourage spurious links).  
   Object-centric evaluation: completeness of ComponentLot–Job edges before/after; fraction of quarantine intervals that appear in Job waiting-time features.

5. Explicit “Wait for Tool / Wait for Batch / Wait for Lot” activities in the event log  
   Target: observability of all three higher-ranked mechanisms.  
   Expected benefit: future DFGs and performance analyses will surface the true waiting reasons instead of silent gaps.  
   Helped: every subsequent process-mining study.  
   Harmed: none; minor logging overhead.  
   New cost/risk: noisy or inconsistently recorded wait events.  
   Perverse-incentive metric: “wait-event count” (could encourage artificial waits).  
   Object-centric evaluation: compare waiting-time features extracted from explicit wait events versus inferred gaps; measure reduction in unexplained Machine idle time.

## 8. Falsification and additional data

Observations that would weaken the top-ranked (batch-synchronisation) explanation:  
1. Evidence that J1 or J2 performed useful parallel work during the 3–4 h window (the wait was not pure idle).  
2. Discovery that OVEN-1 / RACK-7 were occupied by a higher-priority unlogged batch.  
3. Documentation that the 12:05 start time was dictated by a thermal or quality window independent of job readiness.  
4. Measurement showing that single-job curing produces unacceptable quality or energy cost, making synchronisation mandatory.  
5. Proof that the readiness timestamps themselves are unreliable (sensor lag > 30 min).  
6. Observation that identical long waits occur for single-job batches, eliminating the synchronisation hypothesis.

Additional fields or event types that would discriminate among the hypotheses:  
1. Explicit “Wait for Tool”, “Wait for Batch”, “Wait for Lot Release” activity labels with start/end timestamps.  
2. Tool-identity and calibration-state attributes on every Final Test and Machine Process event.  
3. Operator or shift identifiers on idle gaps (to test the alternative “operator absence” explanation).  
4. Full bidirectional O2O links from every ComponentLot event to all affected Jobs (removing the integration artefact).  
5. Shipment policy parameters (minimum fill rate, latest-accept time) attached to each Create Shipment event.  
6. Energy or quality metrics per batch size (to evaluate the true cost of de-synchronisation).  
7. RACK-7 cleaning start/end events with reason codes.  
8. A “supervisor override” event type that records which coupling constraint was deliberately broken.

These data would allow quantitative separation of policy-induced synchronisation, pure resource contention, and analytic projection artefacts.
