## 1. Temporal Data Semantics

Basis: the policy rules, event log, exemption register, and additional semantic facts are taken from the uploaded source. 

I reconstruct each case as an event-time state machine ordered by `(time:timestamp, event_index)`. A blank attribute cell means “no update at this event,” so it is forward-filled from the latest prior known value within the same case. It is never treated as a nullifying update.

Final-state leakage is explicitly disallowed. For example, TX-305’s `Settlement_Confirmed` amount of EUR 150,000 is reliable at settlement time, but it cannot be copied backward to `Release_Funds` because the release message has no immutable amount payload. Similarly, a late `Record_Exemption` event is not automatically the time of approval; it is a record-time event that may or may not evidence an earlier approval.

I distinguish four time notions:

| Time notion    | Meaning in this assessment                                                       | Consequence                                                                                                    |
| -------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Event time     | The event’s `time:timestamp` in the log.                                         | Attribute updates are effective at this time unless evidence says otherwise.                                   |
| Effective time | A business-valid-from time, especially for exemptions.                           | An exemption may be effective before it is recorded, but only if evidence supports that approval existed then. |
| Record time    | When a fact was inserted or recorded, e.g. `Record_Exemption`.                   | Record time can lag effective time; it is not enough by itself to prove timely approval.                       |
| Evidence time  | When supporting evidence became trustworthy, e.g. qualified signature timestamp. | For EX-77 this supports timely approval; for EX-88 it undermines the displayed pre-release approval time.      |

For equal timestamps, I use `event_index` as the tie-breaker. TX-311 is the key example: `Enhanced_Review` has event_index 3 and `Update_Jurisdiction` has event_index 4 at the same timestamp, so the jurisdiction update to DE occurred after the enhanced review but before release.

Material amount changes are assessed relative to the latest `Standard_Review` or `Enhanced_Review`. An increase of more than 20 percent after that review invalidates the review for amount-dependent obligations. A decrease does not by itself invalidate the review. An increase from an unknown amount is not safely classifiable.

Missing amount, risk, jurisdiction, or customer type is not defaulted to low risk. If a decisive trigger cannot be established or excluded, the classification is `INDETERMINATE`.

Formal pseudo-logic:

* Define `before(e1,e2)` as `(timestamp(e1), event_index(e1)) < (timestamp(e2), event_index(e2))` within the case.
* Define `state(c, attr, e)` as the latest nonblank value of `attr` in case `c` at an event `u` where `u <= e` under the event ordering.
* Define `Release(c,r)` where event `r` has activity `Release_Funds`.

R1:
`R1_trigger(c,r)` is true when `Release(c,r)`, `state(c,jurisdiction,r) != DE`, and `state(c,amount,r) >= 100000`.

`R1_satisfied(c,r)` is true when either:

1. there exists `er` such that `activity(er)=Enhanced_Review`, `before(er,r)`, and no invalidating material amount/jurisdiction change relevant to R1 occurs between `er` and `r`; or
2. there exists `ex` such that `ValidExemption(ex,c,r,R1)`.

If the jurisdiction is known non-DE but amount is unknown, `R1_trigger` is unknown rather than false.

R2:
`R2_trigger(c,r)` is true when `state(c,risk_level,r)=HIGH` or `state(c,customer_type,r)=PEP`.

`R2_satisfied(c,r)` is true when there exist `er` and `ca` such that `activity(er)=Enhanced_Review`, `activity(ca)=Compliance_Approve`, `before(er,ca)`, `before(ca,r)`, and `er` occurs after the latest risk/customer-type change that made R2 applicable. A `Compliance_Approve` over only a standard packet does not satisfy this unless explicitly reinterpreted.

R3:
Let `screen` be the latest `Sanctions_Screen` before release. Let `lu` be a `Sanctions_List_Update` adding the current release jurisdiction. R3 is triggered if `before(screen,lu)` and `before(lu,r)`. It is satisfied only if a later `Sanctions_Screen` exists with `before(lu,new_screen)` and `before(new_screen,r)`.

R4:
For the latest review `rev` in `{Standard_Review, Enhanced_Review}` before release, let `amount_at_review = state(c,amount,rev)`. If a later amount update before release has `new_amount > 1.2 * amount_at_review`, then `rev` is invalid for amount-dependent obligations. If `amount_at_review` is unknown, the effect is indeterminate.

R5:
`ValidExemption(ex,c,r,rule)` requires: `approved_by=Head_Compliance`, `effective_from <= obligation_trigger_time`, `release_time < expires`, scope matches release-time jurisdiction/customer type/amount, `ex` waives the relevant rule, and evidence supports that approval existed at the relevant time. Displayed backdating alone is insufficient.

R6:
If a decisive state value is unknown and no other evidence resolves it, the rule result is `INDETERMINATE`, not compliant.

R7:
All state snapshots use event-time reconstruction only. No final case attribute is copied backward.

## 4. Ambiguities and Alternative Readings

TX-305 is the central `INDETERMINATE` case. If the release payload or bank instruction showed EUR 150,000 at 11:30, R1 would be triggered. The case would then need a judgment about whether the 11:15 `Enhanced_Review` is valid despite the note that the review document has no amount. If the release amount was below EUR 100,000, R1 would not trigger. The next-day settlement amount is suggestive but not decisive because the source explicitly says there is no immutable release payload.

TX-302 involves late record time but strong earlier evidence. If one naively treated the 11:00 `Record_Exemption` as the approval time, the exemption would appear post-release. That would be wrong here because the qualified signature timestamp is 09:05 and the outage explains the late database insertion. In any case, TX-302 also had an `Enhanced_Review` at 09:20 before the 09:40 release, so it remains compliant even without relying on EX-77. If an audit taxonomy classifies any release referencing a valid waiver as an exception, TX-302 could be labelled `JUSTIFIED_EXCEPTION`; I classify it as `COMPLIANT` because the substantive R1 review obligation was also met.

TX-310 is not missing the trigger: R1 clearly applies because AE is non-DE and the amount is EUR 200,000. The ambiguity is the attempted exemption. If there were a contemporaneous Head Compliance approval record, a pre-release qualified signature, or independent corroboration of the oral approval, EX-88 could become a `JUSTIFIED_EXCEPTION`. If the control standard requires cryptographic approval before release, it is plainly noncompliant. I classify it as `NONCOMPLIANT` under an audit-evidence standard because the only strong timestamp is after release and the witness is the requester.

TX-311 depends on same-timestamp ordering. Because event_index 3 precedes event_index 4, the jurisdiction changed to DE after the enhanced review but before release. The release-time jurisdiction is DE, so R1 is not triggered. If the jurisdiction update had an explicit effective time after release, then release jurisdiction would remain US and R1 would trigger; even then, the 16:20 enhanced review after the 16:10 amount increase would likely satisfy R1 unless another material change occurred. If a reviewer ignored event_index and treated same-timestamp events as unordered, TX-311 would become less certain.

TX-308 depends on whether a decrease is treated as material. A literal but over-strict reading of “after latest material data change” could demand a new enhanced review after the decrease from EUR 140,000 to EUR 100,000. I reject that reading because R4 explicitly says a decrease does not by itself invalidate a review. Reviewing the higher amount is at least as conservative for the amount-dependent R1 obligation.

TX-307 could change only under a different interpretation of the approval packet. The source says a `Compliance_Approve` that reviewed only a standard packet does not cure the absence of `Enhanced_Review` unless a different interpretation is defended. On the supplied facts, there is no evidence that the standard packet was functionally equivalent to enhanced review, so R2 remains breached.

TX-306 has a small post-approval amount increase. If the policy required renewed compliance approval after any amount change, TX-306 would need a new approval. But R4 sets the invalidation threshold at more than 20 percent for amount-dependent obligations, and the increase from EUR 220,000 to EUR 230,000 is far below that threshold.

    if updates.empty:
        return False, False, pd.NaT, basis
    if is_unknown(basis):
        return False, True, updates.iloc[-1]["time:timestamp"], basis
    over_20 = updates[updates["amount"] > 1.2 * float(basis)]
    if over_20.empty:
        return False, False, pd.NaT, basis
    return True, False, over_20.iloc[-1]["time:timestamp"], basis

def r1_active_at(row):
    if row is None:
        return pd.NA
    return r1_trigger(row["amount_state"], row["jurisdiction_state"])

def diagnose_case(case_id, sub):
    release_rows = sub[sub["concept:name"].eq("Release_Funds")]
    if release_rows.empty:
        return None
    release = release_rows.iloc[-1]
    ro = release["event_order"]
    before = sub[sub["event_order"] < ro]

    latest = {}
    for act in ["Standard_Review", "Enhanced_Review", "Compliance_Approve", "Sanctions_Screen"]:
        latest[act] = last_row(before[before["concept:name"].eq(act)])
    latest_review = last_row(before[before["concept:name"].isin(["Standard_Review", "Enhanced_Review"])])
    latest_material = last_row(before[before["state_changed"]])

    r1 = r1_trigger(release["amount_state"], release["jurisdiction_state"])
    r2 = r2_trigger(release["risk_level_state"], release["customer_type_state"])

    r4_latest, r4_unknown, r4_time, r4_basis_amount = gt20_amount_increase_after(
        sub, latest_review, ro
    )
    r4_after_er, r4_after_er_unknown, _, _ = gt20_amount_increase_after(
        sub, latest["Enhanced_Review"], ro
    )

    r1_activated_after_er = (
        latest["Enhanced_Review"] is not None and
        r1_active_at(latest["Enhanced_Review"]) is not True and
        r1 is True
    )
    r1_enhanced_ok = (
        r1 is True and
        latest["Enhanced_Review"] is not None and
        not r4_after_er and
        not r4_after_er_unknown and
        not r1_activated_after_er
    )

    latest_r2_change = last_row(before[before["risk_level_changed"] | before["customer_type_changed"]])
    er = latest["Enhanced_Review"]
    ca = latest["Compliance_Approve"]
    r2_er_ok = er is not None and (
        latest_r2_change is None or er["event_order"] > latest_r2_change["event_order"]
    )
    r2_ca_ok = er is not None and ca is not None and ca["event_order"] > er["event_order"]
    r2_ok = (r2 is True and r2_er_ok and r2_ca_ok)

    screen = latest["Sanctions_Screen"]
    current_jurisdiction = release["jurisdiction_state"]
    if screen is not None and not is_unknown(current_jurisdiction):
        relevant_updates = before[
            (before["concept:name"].eq("Sanctions_List_Update")) &
            (before["jurisdiction"].eq(current_jurisdiction)) &
            (before["event_order"] > screen["event_order"])
        ]
    else:
        relevant_updates = before.iloc[0:0]
    latest_list_update = last_row(relevant_updates)
    r3 = latest_list_update is not None
    r3_rescreen_ok = True
    if r3:
        rescreens = before[
            (before["concept:name"].eq("Sanctions_Screen")) &
            (before["event_order"] > latest_list_update["event_order"])
        ]
        r3_rescreen_ok = not rescreens.empty

    release_exemption = release["exemption_id"]
    ex_scope_ok = False
    ex_evidence_timely = False
    ex_human_review_needed = False
    if not is_unknown(release_exemption):
        hit = exemptions[exemptions["exemption_id"].eq(release_exemption)]
        if not hit.empty:
            ex = hit.iloc[0]
            ex_scope_ok = (
                "R1" in ex["waives"] and
                ex["approved_by"] == "Head_Compliance" and
                ex["effective_from"] <= release["time:timestamp"] < ex["expires"] and
                release["jurisdiction_state"] == ex["jurisdiction_scope"] and
                release["customer_type_state"] == ex["customer_type_scope"] and
                not is_unknown(release["amount_state"]) and
                release["amount_state"] <= ex["amount_max"]
            )
            ex_evidence_timely = bool(
                ex_scope_ok and
                ex["signature_ts"] <= release["time:timestamp"] and
                ex["evidence_strength"] == "strong"
            )
            ex_human_review_needed = bool(ex_scope_ok and not ex_evidence_timely)

    decisive_unknown = bool(
        is_unknown(release["amount_state"]) or r1 is pd.NA or r2 is pd.NA or r4_unknown or r4_after_er_unknown
    )
    potential_noncompliance = (
        (r1 is True and not (r1_enhanced_ok or ex_evidence_timely)) or
        (r2 is True and not r2_ok) or
        (r3 and not r3_rescreen_ok)
    )

    if decisive_unknown or ex_human_review_needed:
        automated_assessment = "REVIEW_REQUIRED"
    elif potential_noncompliance:
        automated_assessment = "POTENTIAL_NONCOMPLIANCE"
    else:
        automated_assessment = "NO_ISSUE_COARSE"

    return {
        "case": case_id,
        "release_time": release["time:timestamp"],
        "release_event_index": release["event_index"],
        "amount_at_release": release["amount_state"],
        "risk_at_release": release["risk_level_state"],
        "jurisdiction_at_release": release["jurisdiction_state"],
        "customer_type_at_release": release["customer_type_state"],
        "release_exemption_id": release_exemption,
        "r1_trigger": r1,
        "r1_enhanced_ok_coarse": r1_enhanced_ok if r1 is True else pd.NA,
        "r1_valid_exemption_by_evidence": ex_evidence_timely,
        "r2_trigger": r2,
        "r2_ok_coarse": r2_ok if r2 is True else pd.NA,
        "r3_trigger": r3,
        "r3_rescreen_ok": r3_rescreen_ok if r3 else pd.NA,
        "r4_gt20_after_latest_review": r4_latest,
        "r4_unknown_increase_after_latest_review": r4_unknown,
        "latest_standard_review_time": event_time(latest["Standard_Review"]),
        "latest_enhanced_review_time": event_time(latest["Enhanced_Review"]),
        "latest_compliance_approve_time": event_time(latest["Compliance_Approve"]),
        "latest_sanctions_screen_time": event_time(latest["Sanctions_Screen"]),
        "latest_sanctions_list_update_time": event_time(latest_list_update),
        "latest_material_change_time": event_time(latest_material),
        "review_amount_basis_for_r4": r4_basis_amount,
        "r4_gt20_time": r4_time,
        "amount_unknown_at_release": is_unknown(release["amount_state"]),
        "exemption_scope_display_ok": ex_scope_ok,
        "exemption_evidence_timely": ex_evidence_timely,
        "exemption_human_review_needed": ex_human_review_needed,
        "automated_assessment": automated_assessment,
    }

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. Final-state leakage: a classical trace check might attach the settlement amount in TX-305 to the release, but event-time semantics do not permit copying the next day’s settlement state backward.

2. Post-hoc exemptions: control flow can see `Record_Exemption` after release, but it cannot decide whether the approval actually existed earlier. EX-77 is supported by a timely qualified signature; EX-88 is not.

3. Material changes after review: a trace containing `Enhanced_Review -> Release_Funds` looks compliant, but TX-309 is not compliant because the amount increased by more than 20 percent after enhanced review.

4. Conditional activation: `Enhanced_Review` is not required for every release. TX-307 has no R1 trigger because it is domestic and below EUR 100,000, but it does trigger R2 because the customer became PEP.

5. Missing data: a control-flow model cannot express “unknown amount means indeterminate, not compliant.” TX-305 needs evidence review, not a pass or fail based only on its activity sequence.

6. Same-timestamp ordering: TX-311 requires `event_index` to decide whether the jurisdiction update occurred before or after the enhanced review. A pure activity sequence may lose this distinction.

7. Review type semantics: `Standard_Review` and `Enhanced_Review` are different. A control-flow abstraction that treats both as “review” would wrongly clear TX-307 or TX-301.

8. Packet lineage: `Compliance_Approve` is not enough unless it approves the relevant enhanced review. TX-307’s approval of a standard packet does not satisfy R2.

9. Global or cross-cutting facts: sanctions-list updates are not ordinary case-local progress steps. TX-304’s noncompliance depends on the current jurisdiction and the timing/content of the list update.

10. Exemption scope: even if an exemption event appears in the trace, its jurisdiction, customer type, amount cap, rule waiver, expiry, approval role, and evidence quality must match.

## 7. Recommended Logging and Control Improvements

Log an immutable release payload for every `Release_Funds` event: amount, currency, jurisdiction, risk level, customer type, exemption ID, sanctions-list version, review IDs relied upon, rule version, and a payload hash. This would resolve TX-305-type ambiguity.

For every attribute update, store old value, new value, effective time, record time, source system, actor, provenance, reason code, and whether the value was validated or provisional. Blank cells should be avoided in audit exports; use explicit “no update” versus “unknown at source” flags.

For reviews, record the reviewed snapshot ID: amount, jurisdiction, risk level, customer type, documents reviewed, sanctions-list version, and applicable rule triggers at the time of review. `Enhanced_Review` should not be only an activity label; it should identify the obligation scope it covers.

For `Compliance_Approve`, require a reference to the exact `Enhanced_Review` and packet version approved. Store approver role, approval timestamp, signature timestamp, and whether the approval was for a standard or enhanced packet.

For exemptions, store structured fields: exemption ID, waived rule IDs, jurisdiction scope, customer-type scope, amount cap, effective_from, expires_at, approved_by, approval event time, record time, qualified signature timestamp, certificate metadata, and backfill/outage reason. Displayed approval time should be separate from cryptographic evidence time.

For sanctions screening, log the sanctions-list version screened against, the response payload, jurisdictions covered, screening completion time, and any list-update event with added/removed jurisdictions, effective time, publication time, and source.

For event ordering, maintain a stable per-case and preferably global sequence number in addition to timestamps. `event_index` should be mandatory and unique within a case timestamp. Same-timestamp ties should never rely on display order.

Finally, emit a machine-readable compliance-decision event before release: triggered rules, required controls, satisfied controls, missing evidence, exemption evaluation result, reviewer override if any, and the exact policy/rule version used.
