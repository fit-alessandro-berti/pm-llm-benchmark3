# 1. SLA estimands and time definitions

**Time origin:** `Submit` event (case start).
**Time horizon:** 72 hours (SLA deadline).
**Event of interest:** `Resolve` (operational success).
**Competing terminal events:** `Withdraw`, `Reject`, `Transfer` (external resolution unknown).
**Censoring:** Observation cutoff at data freeze; cases still open at cutoff are right-censored.

### Definitions of estimands:
1. **Probability of not being resolved by 72 hours (P72):**
   - Binary outcome: 1 if `duration_or_age_h > 72` or case is still open at cutoff, else 0.
   - *Interpretation:* Directly measures SLA breach risk at the 72-hour horizon.
   - *Contribution examples:*
     - Case S03 (resolved at 76h): contributes 1 (breach).
     - Case S09 (open at 92h): contributes 1 (breached by observation).
     - Case S05 (withdrawn at 27h): contributes 0 (terminal event before 72h).
     - Case S08 (transferred at 68h): contributes 1 under conservative assumption (external outcome unknown).

2. **Cumulative incidence of resolution after 72 hours (CIF72):**
   - Probability of resolving *after* 72 hours, accounting for competing risks (withdrawal/rejection/transfer).
   - *Interpretation:* Quantifies delayed resolution risk while acknowledging cases may exit via other paths.
   - *Contribution examples:*
     - Case S03: contributes to CIF72 at 76h (resolved after 72h).
     - Case S09: contributes to CIF72 at 72h (still open, treated as unresolved).
     - Case S05: contributes 0 (resolved before 72h).
     - Case S08: contributes to CIF72 under assumption that transfer implies unresolved at 72h.

**Why not "probability of still having no terminal disposition at 72 hours"?**
This is equivalent to P72 but conflates open cases with breaches. P72 explicitly ties to the SLA breach definition.

# 2. Event and censoring encoding

| Observed Status | Event Indicator | Competing-Risk Code | Censoring Rule | Sensitivity Alternatives for `Transferred` |
|-----------------|-----------------|---------------------|----------------|-------------------------------------------|
| resolved        | 1 (resolved)    | 0                   | N/A            | N/A                                       |
| withdrawn       | 0               | 1 (withdrawal)      | N/A            | N/A                                       |
| rejected        | 0               | 2 (rejection)       | N/A            | N/A                                       |
| transferred     | 0               | 3 (transfer)        | N/A            | *Scenario 1:* Treat as resolved at transfer time (conservative for SLA). |
|                 |                 |                     |                | *Scenario 2:* Treat as censored at transfer time (external outcome unknown). |
|                 |                 |                     |                | *Scenario 3:* Treat as unresolved at 72h (worst-case for SLA breach). |

**Notes:**
- Competing risks are mutually exclusive and exhaustive for terminal events.
- `Transferred` requires explicit treatment due to unknown external outcomes. Scenarios 1–3 reflect different operational assumptions about external resolution timeliness.

# 3. Why naive completed-case analysis is biased

**Survivor bias:**
- Cases resolved *before* 72h (e.g., S01 at 18h) are included in completed-case analysis, but cases resolved *after* 72h (e.g., S03 at 76h) are excluded. This overestimates SLA compliance.

**Informative censoring:**
- Open cases with long `last_event_gap_h` (e.g., S11 at 55h gap) may be more likely to breach the SLA, but naive analysis drops them. Cases like S09 (open at 92h) are informative about tail risk.

**Competing risks:**
- Cases withdrawn/rejected early (e.g., S05 at 27h) are treated as "success" in naive analysis, ignoring that they never reached `Resolve`.

**Cohort imbalance:**
- Cohort B has more escalations (e.g., S18, S21) and longer durations (e.g., S26 open at 104h), suggesting policy changes may have increased complexity or delays. Naive analysis ignores this.

**Active open cases below vs. above 72h:**
- Cases like S15 (open at 35h) are below the SLA horizon but still at risk; cases like S26 (open at 104h) are above and breached. Naive analysis treats both as "incomplete" without distinguishing risk.

# 4. Statistical analysis plan

| Method                     | Pros                                                                 | Cons                                                                 | Recommendation                     |
|----------------------------|----------------------------------------------------------------------|----------------------------------------------------------------------|------------------------------------|
| **Kaplan-Meier (KM)**      | Simple, non-parametric estimate of P72.                              | Ignores competing risks; overestimates resolution probability.      | *Primary for P72* (univariate).    |
| **Aalen-Johansen (AJ)**    | Accounts for competing risks; estimates CIF72.                      | Requires correct competing-risk encoding.                            | *Primary for CIF72*.               |
| **Cause-specific hazards** | Separates effects of covariates on resolution vs. withdrawal/rejection/transfer. | Less intuitive for operational decisions.                            | *Secondary for hazard interpretation*. |
| **Subdistribution hazards**| Directly models CIF; useful for policy evaluation.                  | Sensitive to model misspecification.                                | *Secondary for CIF72 sensitivity*. |
| **Restricted Mean Survival Time (RMST)** | Summarizes tail risk in time units (e.g., mean hours beyond 72h). | Less interpretable for binary SLA decisions.                        | *Tertiary for tail risk*.          |
| **Landmarking**            | Updates risk sets at intermediate horizons (e.g., 48h).             | Complex; may not add value over AJ for this task.                   | Not recommended.                   |
| **Multi-state model**      | Captures transitions between stages (e.g., `Review`  `Escalate`).  | Requires strong assumptions about state dependencies.               | *Primary for process-aware features*. |

**Justification:**
- **KM** is ideal for the primary estimand (P72) due to simplicity and alignment with SLA breach definition.
- **AJ** is critical for CIF72 to avoid overestimating resolution risk by ignoring competing events.
- Multi-state models are recommended to incorporate process-aware features (e.g., escalation timing) and address immortal-time bias.

# 5. Process-aware features and stage hazards

### Feature derivation from prefixes:
| Feature                     | Type               | Definition                                                                 | Leakage Risk? | Example Cases                     |
|-----------------------------|--------------------|----------------------------------------------------------------------------|---------------|-----------------------------------|
| `current_stage`             | Time-varying       | Last activity in prefix (e.g., `Review`, `Escalate`).                      | No            | S03: `Review`  `Escalate`  `Review`  `Resolve` |
| `rework_count`              | Baseline/time-varying | Count of `Rework` in prefix.                                              | No            | S07, S13: `rework_count=1`        |
| `escalated`                 | Time-varying       | Binary flag for presence of `Escalate` in prefix.                          | Yes (if used as baseline covariate) | S04, S08: `escalated=yes`         |
| `inactivity_gap_h`          | Time-varying       | `last_event_gap_h` at current time.                                        | No            | S11: 55h gap                      |
| `path_pattern`              | Baseline           | Sequence of activities (e.g., `Submit>Screen>Review>Escalate`).            | No            | S03: `Submit>Screen>Review>Escalate>Review>Resolve` |
| `time_to_escalate_h`        | Time-varying       | Time from `Submit` to first `Escalate` (if present).                       | Yes (if used as baseline) | S04: escalated at 29h              |
| `review_count`              | Time-varying       | Count of `Review` activities in prefix.                                    | No            | S02: `Review` once                |

### State-transition diagram (text representation):
```
[Submit]  [Screen]  (AutoCheck | Review | Reject | Withdraw | Escalate)
AutoCheck  (Screen | Resolve)
Review  (Escalate | Rework | Resolve | Withdraw | Reject)
Escalate  (Review | Transfer | Resolve)
Rework  Review
Transfer  (external resolution unknown)
Resolve/Withdraw/Reject  terminal
```

**Leakage risks:**
- `escalated` and `time_to_escalate_h` are time-varying; using them as baseline covariates would introduce immortal-time bias. They should be modeled as time-dependent covariates in multi-state models.

# 6. Sensitivity analysis

| Scenario                     | Treatment of `Transferred` | Treatment of Withdrawal/Rejection | Informative Censoring | Cohort Effects |
|------------------------------|----------------------------|-----------------------------------|-----------------------|----------------|
| **Baseline**                 | Scenario 2 (censored at transfer) | Treated as competing risks        | Adjust for `last_event_gap_h` | Stratify by cohort/priority |
| **Conservative SLA**         | Scenario 3 (unresolved at 72h) | Treated as competing risks        | Ignore gaps           | Ignore cohorts  |
| **External Resolution Optimistic** | Scenario 1 (resolved at transfer) | Treated as competing risks        | Adjust for gaps       | Ignore cohorts  |

**Qualitative conclusions that could reverse:**
- If transfers (e.g., S08, S21) are assumed to resolve externally within 72h (Scenario 1), P72 may decrease significantly.
- If open cases with long gaps (e.g., S11, S25) are more likely to breach, ignoring `last_event_gap_h` may underestimate tail risk.
- If Cohort B's escalations (e.g., S18, S21) are due to policy changes that *reduce* delays, ignoring cohort effects may overestimate SLA risk.

---

# 7. Operational interpretation

**Converting survival outputs to actions:**
1. **Alerts:**
   - Trigger an alert if P72 > threshold (e.g., 10%) for a cohort/priority group.
   - Use CIF72 to estimate workload: e.g., 5% of P2 cases in Cohort B resolve after 72h, requiring follow-up resources.

2. **Workload actions:**
   - Prioritize cases with `current_stage=Escalate` and high `inactivity_gap_h` (e.g., S11) for manual review.
   - For cases with `rework_count > 0` (e.g., S07), allocate additional review capacity.

3. **SLA governance:**
   - Track RMST beyond 72h to quantify average delay for breached cases.
   - Use multi-state models to identify stages where delays accumulate (e.g., `Review`  `Escalate`).

**Calibration and fairness:**
- **Priority:** Ensure P72 and CIF72 are calibrated within each priority level (P1/P2/P3). For example, P1 cases may have lower P72 due to faster escalation.
- **Cohort:** Compare Cohort A vs. B to detect policy effects. If Cohort B has higher P72, investigate whether escalation policies introduced delays.
- **Bias checks:** Ensure features like `escalated` are not proxies for unobserved confounders (e.g., case complexity).

# 2. Encode estimands and transfer scenarios
def encode_data(df, transfer_scenario="censored"):
    """Encode event indicators and competing risks."""
    df = df.copy()
    # Define event indicators
    df["event"] = 0
    df.loc[df["observed_status"] == "resolved", "event"] = 1

    # Competing risks: 0=resolved, 1=withdrawn, 2=rejected, 3=transferred
    df["competing_risk"] = 0
    df.loc[df["observed_status"] == "withdrawn", "competing_risk"] = 1
    df.loc[df["observed_status"] == "rejected", "competing_risk"] = 2
    if transfer_scenario == "censored":
        df.loc[df["observed_status"] == "transferred", "competing_risk"] = 3
        df.loc[df["observed_status"] == "transferred", "event"] = 0  # censored
    elif transfer_scenario == "conservative":
        df.loc[df["observed_status"] == "transferred", "event"] = 0
        df.loc[df["observed_status"] == "transferred", "competing_risk"] = 0  # treat as unresolved at 72h
    elif transfer_scenario == "optimistic":
        df.loc[df["observed_status"] == "transferred", "event"] = 1  # resolved at transfer time
        df.loc[df["observed_status"] == "transferred", "competing_risk"] = 0

    # Time to event/censoring: min(duration_or_age_h, 72) for P72; full duration for CIF
    df["time_to_event"] = np.where(df["event"] == 1, df["duration_or_age_h"], df["duration_or_age_h"])
    df["time_to_event"] = np.minimum(df["time_to_event"], 72)  # P72 horizon

    # Censoring: open cases are censored at duration_or_age_h (but not beyond 72h for P72)
    df["censoring"] = np.where(df["observed_status"] == "open", 1, 0)
    df["censoring_time"] = np.where(df["censoring"] == 1, df["duration_or_age_h"], df["time_to_event"])

    # Features from prefixes
    df["current_stage"] = df["prefix"].str.split(">").str[-1]
    df["has_escalate"] = df["prefix"].str.contains("Escalate")
    df["rework"] = df["rework_count"] > 0
    df["inactivity_gap"] = df["last_event_gap_h"]
    return df

# 3. Fit models
def fit_models(df, estimand="P72"):
    if estimand == "P72":
        # Kaplan-Meier for P72
        kmf = KaplanMeierFitter()
        kmf.fit(df["time_to_event"], event_observed=df["event"], label="P72")
        return kmf
    elif estimand == "CIF72":
        # Aalen-Johansen for CIF
        ajf = AalenJohansenFitter()
        ajf.fit(df["time_to_event"], event=df["competing_risk"], label="CIF72")
        return ajf

# 9. Limitations and additional data

**Missing data needs:**
1. **Exact event timestamps:** Current data only provides `duration_or_age_h` and `last_event_gap_h`. Without timestamps, we cannot:
   - Model time-varying covariates accurately (e.g., `time_to_escalate_h`).
   - Account for workload fluctuations or staffing changes.
   - Validate assumptions about `last_event_gap_h` (e.g., is a 55h gap due to inactivity or data lag?).

2. **External outcomes after transfer:** For transferred cases (e.g., S08, S21), we need:
   - Confirmation of external resolution timeliness to refine transfer scenarios.
   - Data on whether transfers are escalated cases or routine hand-offs.

3. **Cohort rollout compliance:** The prompt notes non-randomized assignment and incomplete rollout. We need:
   - Assignment mechanism details (e.g., which cases were escalated due to policy vs. manual override).
   - Compliance metrics (e.g., % of cases that should have been escalated but weren't).

4. **Cutoff/start dates:** Without start dates, we cannot:
   - Validate `duration_or_age_h` (e.g., is 92h for S09 due to a long review or late data collection?).
   - Model calendar-time effects (e.g., seasonality, policy changes).

5. **Time-varying workload:** Data on staffing, queue lengths, or case complexity would help:
   - Distinguish between process inefficiencies and resource constraints.
   - Model interactions between workload and escalation policies.

**Suggested data additions:**
- Event-level timestamps (start/end times for each activity).
- External resolution data for transferred cases.
- Assignment compliance logs (e.g., escalation triggers).
- Priority-specific SLA definitions (e.g., P1 cases may have a 48-hour SLA).
