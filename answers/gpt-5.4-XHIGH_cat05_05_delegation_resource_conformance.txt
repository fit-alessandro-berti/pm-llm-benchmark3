## 2. Rule Interpretation
- `RR1`: Fail when the normalized human who performed `Draft_Change_Request` is the same normalized human who performed `Approve_Change` in the same case. Alias normalization is mandatory first. A service account never counts as a distinct human.
- `RR2`: Fail when the normalized human who performed `Implement_Change` is the same normalized human who performed `Verify_Implementation`. If the verifier is a service account without reliable human attribution, the result is not “pass”; it is an identity/evidence problem.
- `RR3`: For a `HIGH`-risk case with `emergency=false`, `Approve_Change` must be done by Asha as QM or by a delegate whose delegation is valid at the event timestamp. Validity requires interval coverage, scope coverage, any required principal-absence condition, and no prohibited subdelegation.
- `RR4`: For a `HIGH`-risk case with `emergency=true`, the initial approval may come from Diego as IC or a valid IC delegate. That exception is justified only if the emergency flag and safety rationale are credible. A QM or valid QM delegate must then perform `Retrospective_QM_Review` within two business days.
- Business days for `RR4`: use the site business calendar, excluding weekends and with no site holiday in the period. For the Tuesday 2026-08-11 emergency approvals, the second business day ends on Thursday 2026-08-13 at 23:59:59 UTC.
- Principal action while on leave: leave is evidence that a delegate may be needed, but it does not strip the principal of authority. If the principal personally acts and the identity evidence is good enough, the act can still be authorized. At the same time, a proved principal action can weaken or defeat an “principal absent/unavailable” condition for overlapping delegated acts.
- Later database entry: a database record created after the event does not by itself retro-create authority. It can corroborate an earlier delegation only when independent contemporaneous evidence, such as the signed 2026-08-09 PDF for D-QM-01, shows the delegation existed before use.
- `RR5`: service accounts are non-human resources. They help only when mapped to an authorized person with reliable session evidence. Otherwise they create a technical conformance gap and an evidential gap.
- `RR6`: repeated pairs, reciprocal approvals, shared workstations, and dense handovers are risk indicators only. They justify investigation, not a collusion finding.

Event-time role logic matters throughout. Eva is an Independent Verifier through 2026-08-11 23:59 only; from 2026-08-12 onward she is a Quality Engineer. That does not automatically create an RR1/RR2 breach, but it weakens the underlying “independent verification” objective after 2026-08-12.

Network interpretation should stay cautious. A handover edge such as Clara -> Ben or Diego -> Eva can reflect normal routing in a specialized production cell. A working-together edge can reflect staffing concentration rather than collusion. Those PM4Py networks are useful for targeting review, not for proving misconduct.

    return any(active_in_interval(r.start, r.end, moment) for r in subset.itertuples())


def principal_absence_status(principal, moment):
    abs_rows = absence_windows[absence_windows["human"] == principal]
    pres_rows = presence_evidence[presence_evidence["human"] == principal]
    absent = any(active_in_interval(r.start, r.end, moment) for r in abs_rows.itertuples())
    present = any(active_in_interval(r.start, r.end, moment) for r in pres_rows.itertuples())
    if absent and present:
        return "ambiguous_present_while_nominally_absent"
    if absent:
        return "absent"
    return "not_absent"


def evaluate_delegations(delegate, required_role, activity_name, scope_value, moment):
    rows = []
    subset = delegations[
        (delegations["delegate"] == delegate) & (delegations["delegated_role"] == required_role)
    ]
    for d in subset.itertuples():
        reasons = []
        valid = True
        if not active_in_interval(d.start, d.end, moment):
            valid = False
            reasons.append("outside_interval")
        if d.scope != scope_value:
            valid = False
            reasons.append("scope_mismatch")
        if activity_name not in d.activities:
            valid = False
            reasons.append("activity_not_covered")
        if d.status == "invalid_prohibited_subdelegation":
            valid = False
            reasons.append("prohibited_subdelegation")
        absence_status = principal_absence_status(d.principal, moment)
        if d.principal_absence_required and absence_status != "absent":
            valid = False
            reasons.append(f"principal_condition={absence_status}")
        rows.append(
            {
                "delegation": d.delegation,
                "valid": valid,
                "principal": d.principal,
                "absence_status": absence_status,
                "status": d.status,
                "reasons": ";".join(reasons) if reasons else "ok",
            }
        )
    return rows


def add_business_days_deadline(start_ts, business_days):
    day = start_ts.normalize()
    added = 0
    while added < business_days:
        day += pd.Timedelta(days=1)
        if day.weekday() < 5:
            added += 1
    return day + pd.Timedelta(hours=23, minutes=59, seconds=59)

    if row["risk"] == "HIGH" and not row["emergency"]:
        return "QM"
    if row["risk"] == "HIGH" and row["emergency"]:

    return None

def call_pm4py_with_supported_args(fn, df_arg, **arg_values):
    params = inspect.signature(fn).parameters
    kwargs = {next(iter(params)): df_arg}
    aliases = {
        "activity_key": ["activity_key"],
        "case_id_key": ["case_id_key", "case_id"],
        "timestamp_key": ["timestamp_key"],
        "resource_key": ["resource_key"],
        "activity1": ["activity1", "activity_a", "first_activity"],
        "activity2": ["activity2", "activity_b", "second_activity"],
        "activity": ["activity"],
        "keep_violations": ["keep_violations"],
    }
    for canonical_name, value in arg_values.items():
        for actual_name in aliases.get(canonical_name, [canonical_name]):
            if actual_name in params:
                kwargs[actual_name] = value
                break
    return fn(**kwargs)

## 6. Control Improvements
- Require delegations to be created in the controlled system before first use, with immutable timestamps, machine-readable scope, allowed activities, and explicit subdelegation settings.
- Record principal absence or formal unavailability as its own controlled interval, separate from HR leave, so delegation conditions can be tested directly at event time.
- Bind delegations to exact change categories and, for emergency IC delegation, to a specific incident ID such as `CI-44`, not just to a generic scope label.
- Maintain an authoritative alias map and feed the normalized human identity into the QMS and process-mining layer so self-approval cannot hide behind alternate usernames.
- Eliminate shared service-account use for approvals and verifications. If technical service accounts must remain, require immediate step-up individual authentication and preserve that linkage in the audit trail.
- Enforce verifier-role checks at execution time. If “independent verifier” is a required control role, the workflow should block verification when the actor lacks an active verifier assignment.
- Add automatic escalation for emergency cases: when a HIGH-risk emergency is approved, start a visible deadline timer and notify QM coverage if retrospective review is not completed by the second business day.
- Monitor pair concentration and reciprocal approvals statistically, but treat them as review triggers rather than misconduct findings. Where concentration persists, rotate approvers or require sampled second-line review.
- Retain synchronized VPN, workstation, badge, FIDO, screen-lock, and endpoint telemetry long enough to resolve identity disputes with defensible evidence.
