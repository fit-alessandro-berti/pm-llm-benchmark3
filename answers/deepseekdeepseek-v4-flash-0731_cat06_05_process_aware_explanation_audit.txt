- **Same-timestamp ambiguity check**: For events with identical timestamps, we require a reliable sequence index (e.g., event ID). If missing, we apply domain constraints to infer order (e.g., Claim Closed cannot precede Damage Assessment). If no inference is possible, the event pair is flagged as ambiguous and excluded from pattern mining.

- **Complete-trace vs. prefix check**: Automatically label any feature that is computed from the full trace (e.g., `total_case_duration_hours`, `appeal_seen_anywhere`) and reject it at prediction time. This can be done by checking the feature definition against the event log and the `t0` cutoff.

- **Enabled vs. impossible vs. future-possible**: At `t0`, we check whether an activity is enabled (i.e., its preconditions are met based on the prefix), impossible (violates process rules), or merely future-possible (not yet known). For example, an appeal is not enabled at `t0` because no settlement decision has been made; it is future-possible but not a valid predictor.

- **Repeated Settlement Decision check**: Verify that a second `Settlement Decision Recorded` event is preceded by an `Appeal` event. If not, it is a conformance violation. This ensures that explanations using repeated decisions are semantically legitimate.

**Limitations**: A frequent DFG edge (e.g., `Claim Closed -> Damage Assessment Completed`) is not automatically a normative rule; it may be a data artifact. Declarative checks (e.g., using LTL or SCIFF) can specify constraints, but they require a clear process definition. Alignment-based conformance is computation-heavy but robust.
