# Digital Twin Design for Building-Permit Process Simulation

## 1. Model Scope and State Variables

### Boundary and Level of Detail
The digital twin models the end-to-end building-permit process for four case types: Simple renovation, New residential, Commercial, and Complex variance. It captures interactions between cases, such as shared architects, neighborhood objections, and geographic inspector visits. The model operates at the level of individual cases, tracing each step from application submission to permit or rejection.

### Entities
- **Case**: Represented by its unique case concept name, type, and associated attributes.
- **Stakeholders**: Applicants, architects, clerks, planners, fire/safety reviewers, environmental reviewers, inspectors, legal officers, and system components (e.g., decision-making software).
- **Resources**: Human resources (e.g., clerks, planners, inspectors) and system resources (e.g., software tools).
- **Events**: Actions such as 'Submit application', 'Request missing documents', 'Fire-safety review', etc.

### State Variables
- **Case Status**: Current step in the process (e.g., 'Completeness check', 'Decision drafting').
- **Case Attributes**: Type, district, architect ID, application value, inspection requirements, etc.
- **Resource Availability**: Availability status of clerks, planners, inspectors, legal officers, and inspectors.
- **Queue Lengths**: Waiting times for each activity.
- **Policy Parameters**: Active policies (e.g., pre-submission document checker, inspection batching).

### Resources and Queues
- **Human Resources**: Clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers.
- **System Resources**: Decision-making software, databases.
- **Queues**: Waiting periods for each activity type (e.g., Completeness check, Request missing documents).

### Cross-Case Dependencies
- **Architect Collaboration**: Multiple applications by the same architect can be bundled for inspection.
- **Neighborhood Objections**: Can affect several related cases, extending public-notice periods.
- **District Travel Times**: Inspection travel times vary by district, affecting inspection scheduling.

### Dependencies
- **Resource Availability**: Resource calendars influence activity start times.
- **Policy Changes**: Interventions can alter routing and dependencies between activities.
- **Demand Variability**: Non-stationary demand impacts arrival rates and workload distribution.

## 2. Parameter-Estimation Plan

### Data Preparation
- **Log Handling**: Use pandas to load and format the event log. PM4Py can be used for process mining, but direct reading of the log file is done with pandas.
- **Data Extraction**: Extract relevant fields such as case type, timestamps, resource IDs, and decision outcomes.

### Arrival Rates
- **Non-Stationary Demand**: Estimate daily and weekly arrival rates using historical data. Model demand as a time-varying Poisson process.
- **Seasonal Patterns**: Capture seasonal peaks (March-May, September-November) using moving averages or time-series decomposition.

### Service Times
- **Empirical Analysis**: Extract service times from the event log for activities with recorded timestamps. Use statistical distributions (e.g., exponential, log-normal) to model service times.
- **Rework Times**: Estimate rework times by analyzing the time difference between consecutive activities for the same case.

### Waiting Times
- **Queue Analysis**: Calculate waiting times for each activity type using the timestamps. Identify bottlenecks by analyzing the distribution of waiting times.
- **Burst Analysis**: Identify submission bursts (e.g., Monday submissions) and analyze their impact on queues.

### Routing Probabilities
- **Conditional Probabilities**: Estimate the probability of routing to different activities based on case attributes (e.g., requires_fire, requires_environment).
- **Policy Impact**: Model the impact of policy changes on routing, such as the new rule for Simple renovation permits.

### Resource Calendars
- **Availability Modeling**: Use the provided resource calendars to model availability. Incorporate breaks, holidays, and council meeting weeks into the model.
- **Travel Time Adjustments**: Adjust resource availability based on district-specific travel times.

### Rework and Dependencies
- **Rework Rates**: Estimate rework rates by analyzing the frequency of activities that lead to rework (e.g., 'Request missing documents').
- **Dependency Modeling**: Model dependencies between cases, such as bundled inspections for architect-related cases.

### Missing Data
- **Handling Gaps**: For missing timestamps, use interpolation or imputation methods based on surrounding data. Clearly document assumptions made for missing data.

### Tools and PM4Py
- **PM4Py**: Use PM4Py for process mining activities, such as parsing the process tree and extracting statistical summaries.
- **Pandas**: Use pandas for data manipulation and preprocessing of the event log.
- **Simulation Engine**: Use a simulation framework (e.g., SimPy) for modeling the digital twin.

## 4. Experiment Matrix

## 5. Warm-up, Replications, and Uncertainty Treatment

### Warm-up Approach
- **Initialization**: Start the simulation with a warm-up period (e.g., 500 cases) to allow resource availability to stabilize.
- **Steady-State**: After the warm-up, transition to steady-state simulation to capture long-term behavior.

### Replications
- **Number of Replications**: Run at least 100 replications for each experiment to ensure statistical significance.
- **Random Seeds**: Use different random seeds for each replication to account for variability in random events (e.g., arrival times).

### Uncertainty Treatment
- **Confidence Intervals**: Calculate confidence intervals for performance metrics (e.g., median duration, waiting times) using bootstrapping.
- **Sensitivity Analysis**: Perform sensitivity analysis on key parameters (e.g., arrival rates, resource availability) to understand their impact on outcomes.
- **Heavy-Tailed Distributions**: Use appropriate statistical methods to model heavy-tailed service times and waiting times.

## 5. Validation Strategy

### Face Validation
- **Domain Experts**: Validate the model with process experts to ensure the model accurately represents the real-world process.
- **Stakeholder Feedback**: Gather feedback from stakeholders (e.g., applicants, clerks) to validate assumptions and identify missing aspects.

### Event-Log Replay Validation
- **Replay Simulation**: Replay the event log through the digital twin model and compare the simulated outcomes with the actual log.
- **Metric Comparison**: Compare simulated metrics (e.g., median duration, waiting times) with those from the actual log.

### Distributional Validation
- **Service Time Distributions**: Compare the distributions of service times and waiting times in the simulation with those in the log.
- **Rework Rates**: Validate rework rates and patterns in the simulation against those observed in the log.

### Resource-Utilization Validation
- **Resource Utilization**: Compare resource utilization (e.g., clerk hours, inspector hours) in the simulation with historical data.
- **Queue Lengths**: Validate queue lengths and waiting times in the simulation against observed data.

### Bottleneck Validation
- **Bottleneck Identification**: Identify bottlenecks in the process (e.g., activities with high waiting times) and validate their presence in the simulation.
- **Impact Analysis**: Analyze the impact of interventions on identified bottlenecks.

### Out-of-Sample Validation
- **New Data Testing**: Test the model with new, unseen data to assess its generalizability.
- **Policy Evaluation**: Evaluate the performance of each intervention on out-of-sample data to ensure robustness.

## 6. Decision Criteria

### Metrics
- **Median and Tail Duration**: Median and p90 durations for each case type and process step.
- **SLA Compliance**: Percentage of permits issued within statutory time limits.
- **Fairness**: Distribution of processing times across districts and architect types.
- **Resource Utilization**: Utilization rates of human resources and system resources.
- **Rework and Backlog**: Rates of rework and backlog of cases.

### Thresholds
- **Median Duration**: Target median durations for each activity type (e.g., < 12 days for Completeness check).
- **SLA Compliance**: Target SLA compliance rate (e.g., 95% of permits within 60 days).
- **Fairness**: Variance in processing times across districts and architects should be within acceptable limits.
- **Resource Utilization**: Resource utilization should be balanced, avoiding over- or under-allocation.

### Decision Matrix
- **Primary Criteria**: Median duration and SLA compliance.
- **Secondary Criteria**: Resource utilization, fairness, and robustness to demand variability.
- **Trade-off Analysis**: Evaluate trade-offs between different interventions, considering both benefits and costs.
