Shared causal mechanisms include the dependence of `waiting_before_assessment` on upstream completion times and capacities, which directly influences overall `cycle_time`. In both environments, rework loops and available assessment capacities act as critical limiters on throughput and flow.

However, major site-specific mechanisms prevent a direct transfer. Site B is constrained by statutory limits (`S_originals_required`) enforcing a strict delay before document checks can begin for 62% of claims. Furthermore, `S_IT_case_lock` mechanically prevents simultaneous work, and `S_role_specialization` necessitates handoffs across distinct resource pools, in contrast to Site A's unified, cross-trained workforce.

The effect of the intervention (`treatment_parallelization`) on `true_overlap` and subsequently cycle time is heavily modified by `originals_required`, `digital_documents`, and the `IT_case_lock`. Parallel task assignment will only result in concurrent execution if the case is digital, the IT lock is bypassed, and specialized resources are available simultaneously.

Consequently, duplicating the control-flow diagram does not guarantee transportability. Updating the software to launch parallel tasks at Site B will not generate actual overlap if the system physically locks out the second worker, or if the document reviewer must wait 18 hours for mailed originals. Site A’s observed 9-hour cycle time reduction was massively confounded by API upgrades, extra FTEs, and simpler cases. Transporting the nominal control flow without resolving these physical and statutory modifiers will fail.

## 6. Candidate Site B intervention

**Process Specification**:
- **Eligibility rules**: Only cases definitively identified as 100% digital at Registration are eligible for parallel verification.
- **Concurrent tasks**: Identity Check and Document Check may be created and executed concurrently strictly for eligible digital cases.
- **Statutory prerequisites**: Originals Receipt MUST strictly precede Document Check for the remaining 62% of cases (non-digital).
- **Queue and WIP controls**: Implement team-level WIP limits. Upstream release is paused if Assessment or Legal queues exceed predefined thresholds.
- **Resource responsibilities**: Specialized teams are maintained (4 identity, 7 document reviewers); no cross-training is assumed.
- **Handling of loops**: If Legal Review issues a Request Supplement, the case reverts to a strict sequential mode to prevent duplicate concurrent inquiries.
- **Logging requirements**: IT lock issues must be resolved either via system update allowing multi-read/single-write, or via strict check-in/check-out rules enforcing real-time timestamps (no back-dating).

**Compact POWL-style description**:
```text
IF Digital:
  Registration < {Identity Check, Document Check}
ELSE:
  Registration < {Identity Check, Originals Receipt}
  Originals Receipt < Document Check

{Identity Check, Document Check} < Assessment
Assessment < {Approve, Reject, Legal Review}
Legal Review < {Approve, Reject, Request Supplement}
Request Supplement < Sequential Rework
```

| design element | specification | causal purpose | operational safeguard | process-mining measurement |
|---|---|---|---|---|
| unit of assignment | Individual case (upon Registration) | Isolate case-level effect. | Prevents system-wide queue collapse. | Case ID tracking. |
| randomization | Randomized 1:1 (control vs parallel) | Eliminate confounding by time/mix. | Gradual rollout. | Randomization timestamp. |
| eligible strata | STRICTLY digital-only claims | Test mechanism where legally permitted. | Prevents statutory violations. | Channel attribute = digital. |
| treatment versions | Control (sequential), Tx (parallel) | Compare standard to new flow. | N/A | Treatment variant flag. |
| outcomes | Primary: Wait before Assessment. | Measure true bottleneck reduction. | Track defect rate. | Activity timestamps. |
| interference controls | Separate queues or capacity tags | Prevent Tx cases starving Control. | Dedicated pilot staff if needed. | Resource workload logs. |
| power / support | 400 digital cases per arm | Detect 2h difference in median. | N/A | Sample size monitoring. |
| duration | 4 weeks | Capture weekly seasonality. | Stop if Assessment queue > 50. | Trace duration. |
| stop rules | Halt if rework > 20% or IT locks cause back-entry. | Prevent systemic quality failure. | Daily dashboard review. | Back-entry detection (0s delta). |
| transportability | Compare to Site A's digital subset | Validate transport graph assumptions. | N/A | Effect size delta. |

The pilot explicitly separates mechanism failure from implementation failure by restricting the eligible strata strictly to digital claims. This eliminates statutory blockers (the requirement for original documents) as a mechanism failure. Randomizing at the case level ensures that arrival mix and downstream capacities affect both control and treatment equally, preventing the severe confounding seen at Site A (where +2 FTE, API upgrades, and a simpler mix inflated the apparent treatment effect).

Implementation failure—such as the IT case lock forcing staff to work sequentially while back-dating timestamps to simulate concurrency—is monitored via strict process-mining measurements (e.g., checking for zero-second intervals between check-in and check-out). Interference controls ensure that parallel cases do not flood the assessment queue and starve the sequential control cases. This segmented design guarantees that if true overlap fails to materialize, we can attribute it cleanly to either a physical queueing limit (mechanism) or an IT/behavioral block (implementation), rather than a statutory restriction.

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, Transition, OperatorPOWL, Operator

def build_models():
    # 1. constructs Site A's before and after process trees using pm4py.parse_process_tree(...)
    tree_a_before = pm4py.parse_process_tree("-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )")
    tree_a_after = pm4py.parse_process_tree("-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )")
    
    # 2. converts both to accepting Petri nets with pm4py.convert_to_petri_net(...)
    net_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(tree_a_before)
    net_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(tree_a_after)
    
    # 3. constructs a reasonable Site B candidate using POWL classes from pm4py.objects.powl.obj
    reg = Transition(label="Register")
    id_chk = Transition(label="Identity Check")
    doc_chk = Transition(label="Document Check")
    assess = Transition(label="Assessment")
    
    legal = Transition(label="Legal Review")
    req_supp = Transition(label="Request Supplement")
    appr = Transition(label="Approve")
    rej = Transition(label="Reject")
    notify = Transition(label="Notify")
    
    # 4. explicitly sets POWL order edges so that Assessment waits for both identity and document verification
    order = StrictPartialOrder(nodes=[reg, id_chk, doc_chk, assess])
    order.add_edge(reg, id_chk)
    order.add_edge(reg, doc_chk)
    order.add_edge(id_chk, assess)
    order.add_edge(doc_chk, assess)
    
    # Constructing optional legal-review branch with a supplement loop
    legal_loop = OperatorPOWL(operator=Operator.LOOP, children=[legal, req_supp])
    direct_decision = OperatorPOWL(operator=Operator.XOR, children=[appr, rej])
    legal_decision = OperatorPOWL(operator=Operator.SEQUENCE, children=[legal_loop, direct_decision])
    decisions = OperatorPOWL(operator=Operator.XOR, children=[direct_decision, legal_decision])
    
    site_b_powl = OperatorPOWL(operator=Operator.SEQUENCE, children=[order, decisions, notify])
    
    # 5. converts the POWL model to an accepting Petri net
    net_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b_powl)
    
    # 6. checks workflow-net or soundness properties
    is_wf = pm4py.check_is_workflow_net(net_b)
    print(f"Site B model is workflow net: {is_wf}")
    try:
        is_sound = pm4py.check_soundness(net_b)
        print(f"Site B model is sound: {is_sound}")
    except AttributeError:
        pass
    
    # 7. optionally performs playout with pm4py.play_out(...) and prints sample traces
    log = pm4py.play_out(net_b, im_b, fm_b)
    if log:
        print("Sample trace:", [event["concept:name"] for event in log[0]])
        
    # 8. comments on what the model cannot encode:
    # The POWL structural model represents an idealized control flow.
    # It CANNOT encode:
    # - Data-dependent legal requirements (e.g., waiting for physical originals for 62% of cases).
    # - Resource capacity constraints (specialized pools: 4 identity, 7 document reviewers).
    # - IT case locks that physically block simultaneous work despite structural parallelism.
    # - Time durations, queueing logic, and arrival rates that dictate actual cycle times.
```

## 9. Recommendation

conditional go

**What should be transferred**: The fundamental concept of executing `Identity Check` and `Document Check` concurrently.

**What should not be copied**: Do NOT blindly copy the parallel intervention to all cases. Do not assume the 9-hour cycle time reduction observed at Site A will materialize, as their results were heavily confounded by API upgrades, additional headcount, and a simplified case mix. Do not attempt to merge resource pools into a cross-trained group without extensive union and HR review, as Site B's specialized roles operate under different constraints.

**Which subgroup should enter first**: Strictly limit the intervention to digital-only claims (the 38% where original documents are not legally required).

**Expected benefits and risks**: For the digital subgroup, we expect a modest median cycle time reduction (1-3 hours) driven by reduced wait times before Assessment, assuming IT locks are resolved. Risks include severe bottleneck shifts: if identity and document checks complete faster, cases will pile up at Assessment and Legal Review, potentially increasing the p90 cycle time despite minor average improvements. Furthermore, the IT case lock presents a high risk of "fake concurrency," where workers back-date entries to bypass system constraints, corrupting process mining data without generating true operational overlap.

**What evidence would trigger expansion, modification, or abandonment**:
- *Expansion*: If the pilot demonstrates >50% true operational overlap in digital cases, no increase in back-entry timestamps, and a statistically significant reduction in `waiting_before_assessment` without triggering an assessment queue explosion, consider expanding IT-lock fixes to other verification stages.
- *Modification*: If true overlap remains low but queues shift, implement explicit WIP limits to govern the release of concurrent tasks. If IT locks physically prevent simultaneous work, modify the system architecture to allow multi-user access for specific verification tasks.
- *Abandonment*: If the pilot shows increased rework, massive assessment queue backlogs (bottleneck shift), or if workers systematically violate the original-document statutory requirement in an attempt to achieve concurrency targets, abandon the parallelization attempt immediately.
