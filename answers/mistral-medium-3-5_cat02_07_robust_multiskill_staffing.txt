# 1. Assumptions, objectives, and decision variables

### **Assumptions**
1. **Service-time distributions**: Ranges are interpreted as uniform distributions (e.g., Intake ~ U[5,8] for ordinary cases). Complex-tail cases are drawn from their respective ranges with the given probability.
2. **Parallel vs. sequential ME/ES**: For ME/ES cases, parallel execution is chosen if at least two qualified resources are available; otherwise, sequential execution is forced. Parallel branches incur 8 minutes of coordination delay before Validation.
3. **Preemption**: Only P1 cases can preempt lower-priority (P2/P3) diagnostic activities. Preemption occurs at the start of a new P1 arrival if no idle qualified resource is available. The 10% restart penalty applies to the remaining service time of the preempted activity.
4. **Handover/setup delays**: Applied deterministically when conditions are met (e.g., 7 minutes for resource change, +5 minutes for cross-team moves unless the same cross-skilled resource retains the case).
5. **Resource availability**: Breaks are fixed and non-negotiable. Overtime is capped at 30 minutes per resource.
6. **Dispatch ties**: Broken by shortest expected remaining processing time (SERPT) among eligible resources.

### **Objectives**
1. **SLA Risk Minimization**:
   - Minimize the weighted sum of SLA violations (P1: 120 min, P2: 480 min, P3: 1440 min) with weights proportional to priority (e.g., 3:2:1 for P1:P2:P3).
   - Include tail risk via `p95_delay` to penalize outliers.
2. **Fairness-Robustness**:
   - Maximize the minimum utilization fairness (1 - Gini coefficient of resource utilization) across all scenarios.
   - Penalize policies where any resource exceeds 90% utilization in >20% of scenarios.

### **Decision Variables**
- **Staffing**: Fixed (given resources), but policies may reserve capacity (e.g., dedicate Farah to P1).
- **Routing**: Assignment rules (specialization, pooling, hybrid).
- **Parallelization**: Threshold for ME/ES parallel vs. sequential (e.g., parallel if 2 cases in diagnostic queue).
- **Preemption**: Enable/disable for P1, with restart penalty.
- **Handover minimization**: Prefer same-resource retention where possible.

# 3. Candidate policies

### **Policy 1: Strict Specialization (SS)**
- **Eligibility**: Fixed queues per skill:
  - Intake: Ada, Ben, Deepa, Farah.
  - Mechanical: Ada, Ben, Deepa, Farah.
  - Electrical: Ada, Chen, Deepa, Emil, Farah.
  - Software: Chen, Emil, Farah.
  - Validation: Ada, Ben, Chen, Deepa, Farah.
- **Priority**: P1 > P2 > P3 within each queue. Preemption allowed for P1.
- **Parallelization**: ME/ES always sequential (no cross-skill overflow).
- **Handover**: Minimized by sticking to fixed queues, but cross-team moves (e.g., Mechanical  Electrical) incur +5 min.
- **Overflow**: None (cases wait in their fixed queue).

**Pros**: Simple, predictable, low coordination overhead.
**Cons**: Poor load balancing; bottlenecks may form in one skill while others are idle.

---

### **Policy 2: Full Pooling (FP)**
- **Eligibility**: Any qualified resource can pick any case (no fixed queues).
- **Priority**: Dynamic priority score = `P1: 1000, P2: 500, P3: 100` + `1/(expected remaining time)` (SERPT).
- **Parallelization**: ME/ES parallel if 2 qualified resources are idle; else sequential.
- **Preemption**: P1 can preempt P2/P3 diagnostic activities (with 10% restart penalty).
- **Handover**: Avoid by preferring same-resource retention (if eligible for next activity).
- **Setup**: 5-minute penalty if a resource switches skill families (e.g., Mechanical  Electrical).

**Pros**: Maximizes throughput, balances load.
**Cons**: High handover/setup overhead; complex to audit; risk of starvation for P3.

---
### **Policy 3: Hybrid with Reserved P1 Capacity (HY)**
- **Eligibility**:
  - **P1 cases**: Reserved for Farah (cross-skilled) and Emil (E/S). If both busy, overflow to next fastest eligible resource.
  - **P2/P3 cases**: Full pooling among remaining resources.
- **Priority**: P1 always first; P2/P3 use SERPT.
- **Parallelization**: ME/ES parallel for P1 if possible; sequential for P2/P3 to reduce coordination.
- **Preemption**: Only for P1, and only if no reserved resource is free.
- **Handover**: Minimize for P1 by sticking to Farah/Emil where possible.
- **Fairness**: Cap utilization of any resource at 90% (reject overflow if exceeded).

**Pros**: Protects P1 SLAs, balances fairness, reduces handover for high-priority cases.
**Cons**: May underutilize reserved resources; P2/P3 may suffer.

            service_time_data.at[i, 'complex_prob'] *= 2
    elif scenario == 'U5':
        # U1 + U3 + IT outage 09:30-10:00 (Intake blocked)
        for i, block in enumerate(demand['block']):
            if block in ['08:00-10:00', '10:00-12:00']:
                demand.at[i, 'expected_arrivals'] = int(demand.at[i, 'expected_arrivals'] * 1.7)
                demand.at[i, 'P1_pct'] += 8
                demand.at[i, 'P2_pct'] -= 4
                demand.at[i, 'P3_pct'] -= 4
        skill_speed_data.loc[skill_speed_data['resource'] == 'Chen', 'shift_start'] = '00:00'
        skill_speed_data.loc[skill_speed_data['resource'] == 'Chen', 'shift_end'] = '00:00'

    # Generate arrivals
    arrivals = []
    for _, row in demand.iterrows():
        start_hour, end_hour = map(int, row['block'].split('-'))
        start_time = datetime(2023, 1, 1, start_hour, 0)
        end_time_block = datetime(2023, 1, 1, end_hour, 0)
        n_arrivals = int(row['expected_arrivals'])
        # Distribute arrivals uniformly in the block
        for _ in range(n_arrivals):
            delta = np.random.uniform(0, (end_time_block - start_time).total_seconds())
            arrival_time = start_time + timedelta(seconds=delta)
            # Assign priority and case type
            priority = np.random.choice(['P1', 'P2', 'P3'],
                                       p=[row['P1_pct']/100, row['P2_pct']/100, row['P3_pct']/100])
            case_type = np.random.choice(['M', 'E', 'S', 'ME', 'ES'],
                                         p=[row['M_pct']/100, row['E_pct']/100, row['S_pct']/100,
                                            row['ME_pct']/100, row['ES_pct']/100])
            arrivals.append({
                'arrival_time': arrival_time,
                'priority': priority,
                'case_type': case_type,
                'case_id': f"INC-{case_counter:04d}"
            })
            case_counter += 1
    arrivals.sort(key=lambda x: x['arrival_time'])

    # Track resource states: {resource: {'available_at': datetime, 'current_activity': None}}
    resource_states = {row['resource']: {'available_at': datetime(2023, 1, 1, 8, 0), 'current_activity': None}
                       for _, row in skill_speed_data.iterrows()}

    # Track case states: {case_id: {'current_activity': None, 'prev_resource': None, 'prev_activity': None, 'start_time': None}}
    case_states = {}

    # Process arrivals
    for arrival in arrivals:
        case_id = arrival['case_id']
        case_states[case_id] = {
            'current_activity': None,
            'prev_resource': None,
            'prev_activity': None,
            'start_time': None,
            'preempted': False,
            'restart_penalty': 0.0,
            'parallel_branches': False
        }
        current_time = arrival['arrival_time']
        priority = arrival['priority']
        case_type = arrival['case_type']

        # Determine activities for this case
        activities = ['Intake']
        if case_type == 'M':
            activities.append('Mechanical')
        elif case_type == 'E':
            activities.append('Electrical')
        elif case_type == 'S':
            activities.append('Software')
        elif case_type == 'ME':
            activities.append('Mechanical')
            activities.append('Electrical')
        elif case_type == 'ES':
            activities.append('Electrical')
            activities.append('Software')
        activities.append('Validation')

        # Process each activity in sequence
        for i, activity in enumerate(activities):
            # For ME/ES, decide parallel vs. sequential
            if case_type in ['ME', 'ES'] and i == 1:  # First diagnostic activity
                # Check if parallel is possible (policy-dependent)
                if policy == 'FP' and len(get_eligible_resources(activity, policy)) >= 2:
                    # Parallel execution
                    case_states[case_id]['parallel_branches'] = True
                    # For simplicity, we'll simulate sequential here (parallel would require more complex logic)
                    pass

            # Find eligible resources
            eligible = get_eligible_resources(activity, policy)
            # Filter by availability
            available_resources = []
            for resource in eligible:
                if is_resource_available(resource, current_time) and \
                   resource_states[resource]['available_at'] <= current_time:
                    available_resources.append(resource)

            # If no resources available, wait for the first to free up
            if not available_resources:
                # Find the earliest available resource
                earliest_time = min(resource_states[r]['available_at'] for r in eligible)
                current_time = earliest_time
                available_resources = [r for r in eligible if resource_states[r]['available_at'] <= current_time]

            # Select resource based on policy
            if policy == 'SS':
                # Strict specialization: first eligible
                selected_resource = available_resources[0]
            elif policy == 'FP':
                # Full pooling: shortest expected remaining time (simplified: pick fastest)
                # Here, we pick the resource with the lowest multiplier for this activity
                selected_resource = min(available_resources,
                                        key=lambda r: apply_multiplier(r, activity))
            elif policy == 'HY':
                # Hybrid: P1 reserved for Farah/Emil if available
                if priority == 'P1':
                    reserved = [r for r in ['Farah', 'Emil'] if r in available_resources]
                    if reserved:
                        selected_resource = reserved[0]
                    else:
                        selected_resource = min(available_resources,
                                                key=lambda r: apply_multiplier(r, activity))
                else:
                    selected_resource = min(available_resources,
                                            key=lambda r: apply_multiplier(r, activity))

            # Calculate service time
            is_complex = is_complex_case(activity)
            base_service = sample_service_time(activity, is_complex)
            multiplier = apply_multiplier(selected_resource, activity)
            service_time = base_service * multiplier

            # Add handover/setup delay
            handover_delay = 0
            if case_states[case_id]['prev_resource'] is not None:
                handover_delay += add_handover_delay(
                    case_states[case_id]['prev_resource'],
                    selected_resource,
                    case_states[case_id]['prev_activity'],
                    activity
                )
                handover_delay += add_setup_delay(
                    selected_resource,
                    case_states[case_id]['prev_activity'],
                    activity
                )

            # Start time (current_time + handover_delay)
            start_time = current_time + timedelta(minutes=handover_delay)
            end_time = start_time + timedelta(minutes=service_time)

            # Check for preemption (only for diagnostic activities and P1)
            if activity in ['Mechanical', 'Electrical', 'Software'] and priority == 'P1':
                # Check if any lower-priority case is running on this resource
                for other_case, state in case_states.items():
                    if state['current_activity'] == activity and \
                       state['prev_resource'] == selected_resource and \
                       other_case != case_id:
                        # Preempt the other case
                        other_priority = next(a['priority'] for a in arrivals if a['case_id'] == other_case)
                        if other_priority in ['P2', 'P3']:
                            # Calculate remaining time for the preempted case
                            remaining_time = (resource_states[selected_resource]['available_at'] - datetime.now()).total_seconds() / 60
                            restart_penalty = 0.1 * remaining_time
                            case_states[other_case]['preempted'] = True
                            case_states[other_case]['restart_penalty'] += restart_penalty
                            # Requeue the preempted case
                            # (Simplified: we'll just delay its end time)
                            resource_states[selected_resource]['available_at'] = start_time + timedelta(minutes=service_time + restart_penalty)
                            break

            # Update resource state
            resource_states[selected_resource]['available_at'] = end_time
            resource_states[selected_resource]['current_activity'] = activity

            # Update case state
            case_states[case_id]['current_activity'] = activity
            case_states[case_id]['prev_resource'] = selected_resource
            case_states[case_id]['prev_activity'] = activity
            case_states[case_id]['start_time'] = start_time

            # Log the event
            event_log.append({
                'case:concept:name': case_id,
                'concept:name': activity,
                'start_timestamp': start_time,
                'time:timestamp': end_time,
                'org:resource': selected_resource,
                'priority': priority,
                'case_type': case_type,
                'is_complex': is_complex,
                'preempted': case_states[case_id]['preempted'],
                'restart_penalty': case_states[case_id]['restart_penalty'],
                'handover_delay': handover_delay,
                'parallel_branches': case_states[case_id]['parallel_branches'],
                'policy_version': policy,
                'scenario_flag': scenario
            })

            # Update current_time for next activity
            current_time = end_time

    # Convert to DataFrame
    log_df = pd.DataFrame(event_log)
    log_df = pm4py.format_dataframe(log_df, case_id='case:concept:name', activity_key='concept:name',
                                     timestamp_key='time:timestamp')
    return log_df

# 9. Limits and validation plan

### **Limits of the Analysis**
1. **Deterministic Approximations**:
   - Service times are sampled, but the simulation uses a single seed. **Limit**: Does not capture full variability.
   - **Impact**: Underestimates tail risk (p95_delay may be lower than reality).
2. **Simplified Parallelism**:
   - ME/ES parallel execution is not fully modeled (would require tracking multiple threads per case).
   - **Impact**: Underestimates throughput for parallel cases.
3. **Preemption Logic**:
   - Preemption is simplified (only checks at activity start). Real-world preemption could occur mid-activity.
   - **Impact**: Restart penalties may be underestimated.
4. **Static Demand**:
   - Arrivals are generated from expected values; no stochastic variability in demand.
   - **Impact**: Bottlenecks may appear/shift differently in reality.
5. **No Learning Effects**:
   - Assumes static service-time distributions; real resources may improve over time.
   - **Impact**: Overestimates long-term delays.

### **Validation Plan**
1. **Pilot Study**:
   - **Duration**: 2 weeks.
   - **Scope**: Run HY policy on 20% of cases (randomly selected), with SS as control.
   - **Metrics**:
     - P1 SLA attainment (target: 90% within 120 min).
     - Mean/p95 delay for all priorities.
     - Resource utilization (cap at 90%).
     - Handover/setup minutes per case (target: <5 min).
   - **Safety**:
     - If P1 SLA drops below 85%, revert to SS.
     - Monitor Validation queue length; if >5 cases, trigger emergency mode.

2. **Backtesting**:
   - **Data**: Historical incident logs (if available) with similar case types.
   - **Method**:
     - Replay logs under SS, FP, HY policies using the simulation.
     - Compare predicted vs. actual delays/SLAs.
   - **Success Criteria**:
     - Predicted SLA attainment within ±5% of actual.
     - Predicted bottlenecks match historical observations.

3. **Stress Testing**:
   - **Scenarios**: Inject U1-U5-like shocks into the pilot.
   - **Example**:
     - Simulate a morning surge (U1) and measure P1 SLA.
     - If HY maintains P1 SLA 80%, it passes; else, refine reservation rules.

4. **Human-in-the-Loop**:
   - **Feedback**: Survey operators on policy interpretability and fairness.
   - **Adjustments**:
     - If >30% of operators find HY confusing, simplify rules (e.g., fixed P1 reservations).

5. **Process Mining**:
   - **Post-Pilot**:
     - Use `pm4py.discover_heuristics_net` to check for new loops (e.g., preemption cycles).
     - Use `pm4py.get_service_time` to detect skill erosion (e.g., Farah’s Software times increasing).
   - **Alerts**:
     - Trigger if Validation queue time >30 min for >5 cases in a row.
