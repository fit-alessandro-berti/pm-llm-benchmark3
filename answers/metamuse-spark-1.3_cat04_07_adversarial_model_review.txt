# 1. Review Scope and Assumptions
This review is for a model-governance board deciding what, if anything, can be deployed from two discovery submissions for custom-order dossiers.

We distinguish four use cases because they invert the fitness / precision trade-off:

- **Exploration / discovery:** Goal is to see what happened, support stakeholder discussion, tolerate noise and missing events. High fitness / recall is valued, low precision is tolerable **if disclosed**. A permissive model is acceptable as a map, not as a gate.
- **Conformance enforcement / audit:** Goal is to decide compliant vs non-compliant, block release, trigger investigation. Precision, specificity against negatives, and correct handling of mandatory, ordering, and exactly-one constraints dominate. High fitness achieved by optionalizing mandatory steps is a failure, not a success.
- **Simulation / prediction / resourcing:** Goal is to generate plausible futures. Requires soundness, reasonable generalization to unseen combinations, and explicit uncertainty where attributes are missing. Memorized enumeration misleads simulation.
- **Stakeholder communication / maintenance:** Goal is understandable, ownable, updatable model. Branch enumeration with 33 duplicate labels fails even if fitness/precision look good on training.

Assumptions:

- P1-P7 and probes B1-B8 are policy statements to test against, not complete ground truth. B5 is stated as plausible valid, B6 as conditional.
- Reported metrics are unverified: same 80/20 split claimed but no seeds, no preprocessing code, no alignment costs, no held-out case IDs, no negative suite.
- Log deficiencies are material: no `external/internal` attribute for P3, no `affected-check` attribute for P6, and suspected missing `Supplier Review` events per F4.
- We do not average scores. Trade-offs are use-case dependent and pathologies can make a high aggregate actively dangerous for compliance.

Acceptable trade-off by use:

- Exploration: fitness >= high, precision can be moderate-low if limitations are labeled; simplicity/comprehensibility matter.
- Enforcement: fitness and precision must both be high on stratified holdout **and** on curated negatives; a model that buys fitness by making `Credit Check`/`Technical Review` optional, or buys precision by memorizing training variants, is rejected for enforcement even if its aggregate looks best.

# 3. Adversarial Review of Model S
**Model S expression:** `->(Register, +(X(Credit,tau), X(Technical,tau), X(Supplier,tau), X(Expedite,tau)), X(Manager,Auto), Release)`

Semantics assumed: `->` sequence, `+` parallel (interleaved), `X(...,tau)` optional skip. No `Correct Dossier`, no loop. Each visible label appears at most once.

**Strongest case for S:**

- Robust to missing events and order variation (P2 allows either check order; log has missing Supplier per F4). Parallel-optional replays almost anything without alignment gymnastics, hence 0.992/0.981 fitness and 0.018s runtime.
- Compact, no duplicates, high comprehension (4.4). Good as conversation starter and for initial exploration where the goal is recall, not gating.
- Correctly captures exactly-one approval `X(Manager,Auto)` and first/last `Register`/`Release` (P1,P5).
- For simulation of happy-path throughput where corrections are filtered out, simplicity helps.

**Strongest case against S:**

- It confuses *noise tolerance* with *policy*. It achieves fitness by deleting policy: mandatory checks become optional, ordering becomes parallel, correction is deleted entirely. This is accidental semantic flaw, not principled tolerance.
- Precision 0.584 on positives-only already signals large escaping behavior; true specificity against negatives (B3,B4,B8) would be far worse.
- It cannot distinguish internal vs external (but then allows `Supplier` always optionally, violating least-privilege for internal orders) and cannot represent P6/P7 correction semantics at all.
- Advocate claim F7 ("low precision acceptable because exploratory") is valid **only if** model is labeled exploratory and never used for release gating. Current risk is function creep into enforcement because fitness looks good.

**At least five concrete undesirable / policy-ambiguous admitted behaviors (traces):**

1. **Skips both mandatory checks — forbidden per P2/F1, but accepted:** `Register, Manager Approval, Release Order` [B3]. Reason: each `X(...,tau)` can choose `tau` in parallel block. This alone vetoes S for compliance.
2. **Skips one mandatory check — forbidden, but accepted:** `Register, Credit Check, Manager Approval, Release Order` and `Register, Technical Review, Auto Approval, Release Order`. Reason: independent optionalization.
3. **Expedite before checks — forbidden per P4/F1, but accepted:** `Register, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order` [B4]. Reason: `+` allows any interleaving; no precedence `checks -> Expedite`.
4. **Supplier + Expedite without any mandatory check — forbidden, but accepted:** `Register, Supplier Review, Expedite Review, Manager Approval, Release Order`. Reason: combination of 1+3. Also ambiguous for P3: internal order should not have `Supplier`, but S permits it optionally with no attribute guard.
5. **Skips approval? No — correctly requires one. But permits internal/external confusion and urgent without checks:** `Register, Credit Check, Auto Approval, Release Order` without `Technical Review` but with `Auto` (risky auto-approval without full checks). More generally any subset: `Register, Expedite Review, Auto Approval, Release Order`.
6. **Bonus — rejects legitimate correction behavior (under-permissive where it should be permissive):** `Register, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order` [B6] and any trace containing `Correct Dossier` or a repeated check is **rejected** because `Correct` label absent and no loop. So S is simultaneously over-permissive on mandatory/ordering and under-permissive on P6/P7. The over-permissiveness is accidental (tau + parallel), not intentional noise tolerance. Intentional tolerance would keep `Credit`/`Technical` mandatory in the model but allow alignment deviations to be flagged as deviations, not as compliant.

Distinction: Intentional noise tolerance = model says "required" but diagnostics allow log deviation with cost (visible violation). Accidental flaw = model says "optional/any-order" so violation is invisible (fits with no cost). S does the latter.

# 4. Adversarial Review of Model C
**Model C expression:** `X` of 8 fixed `->` sequences, each with concrete order, no parallelism, no `tau` except via branch choice, only one correction pattern (V7: repeat both checks, Credit-first), only one `Auto` pattern (V8: Credit-first, no Supplier, no Expedite).

**Strongest case for C:**

- On training distribution it is precise (0.941) and fits well (0.973). For audit of frequent, already-seen variants, it mirrors reality and will flag deviations for human review. Duplicate enumeration makes each variant readable in isolation.
- It respects some policy fragments: never skips both checks, never places `Expedite` before checks in its 8 branches, respects `Register-first/Release-last` and exactly-one approval (each branch has one approval then release).
- If unseen behavior truly should be treated as noncompliant until approved (F8 advocate view), low holdout fitness is a feature: closed-world enforcement.

**Strongest case against C (and why precision is likely memorization artifact):**

- **Branch enumeration:** Instead of learning `Credit || Technical` (parallel) + optional `Supplier`/`Expedite` + `XOR approval`, it enumerates cross-product fragments. This causes combinatorial explosion: to cover 2 check orders x 2 Supplier options x 2 Expedite options x 2 approvals x selective corrections would need dozens of branches; only 8 are present, so large legitimate space is missing (F2,F4).
- **Duplicate labels (33):** Same activity appears in many branches. After `convert_to_petri_net`, alignments face massive ambiguity (which `Credit` occurrence to map to?), inflating runtime (0.44s), fragmenting state for precision calculation (each duplicate creates its own context, reducing escaping edges  inflated precision), and destroying maintainability/ownership (F3): changing `Technical Review` ownership requires editing 7+ places; impact analysis must consider all bindings.
- **Unseen combinations rejected:** Holdout 0.744 drop + F4 (`Supplier+Auto+alternate order` absent from training) + B2/B5 failures below show C rejects legitimate novelty. Examples: `Technical-first + Auto` (B2 valid) has no branch; `Supplier+Expedite+Auto` (B5 plausible valid) has no branch; `Supplier+Expedite` with Technical-first has no branch. High training precision therefore measures "remembers training variants," not "understands policy."
- **Correction handling (P6/P7):** Only V7 `...Credit, Technical, Correct, Credit, Technical, Manager...` is allowed. It does not allow Technical-first correction, single-check repeat (B6 conditional-valid: only `Technical` repeats), `Supplier`/`Expedite` interaction with correction, or `Auto` after correction. It also does not enforce P7 (repeat without `Correct` is rejected only by accident of enumeration, not by explicit rule; any new repeat pattern would need a new branch).
- **Maintainability:** Adding a new legitimate combination (e.g., `Technical-first + Supplier + Expedite + Auto`) requires a new branch + new duplicates + re-validation. Deleting a forbidden pattern requires auditing all branches. No declarative rule to update.
- **F8 rebuttal:** Treating all unseen as noncompliant is defensible for a denylist/gate, but then the model should be an explicit allowlist with governance for approval of new variants, not presented as a discovered general process with 0.941 precision. Moreover, operations cost of false-positive noncompliance (blocking legitimate external/urgent orders) is high, and auditor note F5 means C was never tested on true negatives, so its false-positive vs true-positive trade-off is unknown.

In short: C is audit-ready only for the closed world of frequent training variants. It is not generalizable, not maintainable, and its precision is inflated by state fragmentation from duplicates and by evaluating only on positives.

# 6. Likely Metric Pathologies
Ranked by likely decision impact (1 = most dangerous for governance):

1. **Fitness rewarded by optionalizing mandatory behavior (critical).** S's 0.992/0.981 is achieved by `X(...,tau)` on mandatory checks. Alignment fitness does not penalize a model for *allowing* skips; it rewards replayability. For enforcement this inverts quality: higher fitness = less compliant. Decision impact: could cause board to deploy S as compliant gate that lets unchecked dossiers through.
2. **Positive-log-only precision (critical).** Per F5, precision 0.584/0.941 measures escaping behavior relative to observed positives only, not rejection of curated forbiddens (B3,B4,B8). C's 0.941 looks audit-ready but was never tested on negatives; S's 0.584 understates its danger (true specificity worse). Decision impact: false confidence in C, false tolerance for S.
3. **Train/holdout leakage / split sensitivity (high).** No seeds, preprocessing, costs, or case IDs. 80/20 claim unverifiable. If split is random without stratification by external/urgent/correction, holdout may be attribute-shifted (F4 notes novel combos). C's 0.744 may reflect sampling variance, not stable generalization. Conversely, S's stability may be artifact of permissiveness, not robustness. Decision impact: holdout gap cannot adjudicate without reproducible stratified splits.
4. **Missing-event bias (high).** F4 warns Supplier events may be missing. Discovery then learns Supplier as optional/infrequent; alignments explain missing Supplier as `tau` skip at low cost. This rewards S (optional Supplier) and punishes precise models that require Supplier for externals. Without external/internal attribute, no metric can distinguish "correctly skipped for internal" vs "missing data." Decision impact: both models' Supplier semantics are unvalidated.
5. **Duplicated-label effects (high for C).** 33 duplicates fragment states, inflate precision (fewer escaping edges per duplicated context), deflate simplicity, explode alignment search (0.44s) and diagnostics ambiguity (which occurrence violated?). Comparisons of precision/fitness/runtime across 0 vs 33 duplicates are apples-to-oranges. Decision impact: C's precision/runtime numbers are not comparable to S's; maintainability veto stands regardless.
6. **Silent-transition effects (high for S).** Four `tau` skips + parallel create many silent paths. Depending on alignment cost for silent vs log/model moves, fitness can be gamed, precision depressed, and generalization inflated. Undocumented costs make 0.992 vs 0.973 meaningless. Decision impact: S's metrics are cost-sensitive and non-reproducible.
7. **Generalization rewarded by excessive permissiveness (medium-high).** Token-based 0.907 for S is structural: parallel-optional nets trivially generalize. It does not test selective correction (P6) or exactly-one approval under novelty. Decision impact: board must not read S's generalization as correctness.
8. **Alignment-cost sensitivity (medium-high).** Without cost matrix (sync vs log-move vs model-move vs tau), fitness/precision can flip. E.g., high model-move cost would punish S's skips less? Actually skips via tau are silent, not model-moves, so cheap. Low log-move cost would forgive C's missing branches partially. Decision impact: all alignment numbers are conditional and currently unverifiable.
9. **Runtime confounding by model size (medium).** 0.018s vs 0.440s largely reflects search space (small parallel-optional vs 8-branch duplicates), not implementation quality. Decision impact: relevant for deployment cost, but not as quality signal. C's cost matters for real-time use and for re-validation loops.
10. **Stakeholder-score methodology (medium for communication, low for compliance).** Informal 1-5 with no protocol, blinding, or task-based comprehension test. S's 4.4 may reflect familiarity bias and failure to notice missing enforcement; C's 1.9 reflects size, not necessarily incorrectness. Decision impact: cannot justify enforcement deployment; must be re-measured with documented protocol if communication claim is needed.

Overall: the most decision-relevant pathologies are those that make good numbers mean bad policy (1,2) and those that make numbers incomparable (3,5,6,8).

# 7. Third Alternative
Strategy: **block-structured procedural backbone (POWL) + DECLARE / data / post-hoc policy checks.** Rationale: procedural backbone enforces what log supports (P1,P2,P5, ordering, exactly-one, correction loop skeleton); declarative layer enforces what procedural backbone over-approximates (selective repeat P6, no-repeat-without-correction P7, Expedite precedence, Supplier attribute guard) and makes uncertainty explicit where attributes are missing.

## 7.1 Compact formal description (`model_third`)

- `REGISTER first, RELEASE last, APPROVAL exactly-one before RELEASE.`
- `MANDATORY = Credit Check AND Technical Review` (both required, any order, concurrent).
- `SUPPLIER_OPT = Supplier Review XOR tau`, `EXPEDITE_OPT = Expedite Review XOR tau`, both positioned **after** MANDATORY and **before** APPROVAL, concurrent with each other (any order, both/neither allowed procedurally; attribute/policy layer restricts).
- `APPROVAL = Manager Approval XOR Auto Approval`.
- `CHECKS = partial-order { MANDATORY -> SUPPLIER_OPT, MANDATORY -> EXPEDITE_OPT }` (no edge between supplier/expedite).
- `LOOP = do CHECKS, redo Correct Dossier` (i.e., `CHECKS (Correct CHECKS)*`): correction can repeat; each iteration must contain at least one mandatory recheck (enforced declaratively because procedural loop repeats whole block).
- `ROOT = Register -> LOOP -> Approval -> Release` as strict partial order.

This is safer than S (mandatory enforced, ordering enforced, correction represented, no silent skipping of mandatory) and more generalizable/maintainable than C (2 orders + 4 Supplier/Expedite combos + 2 approvals + arbitrary correction iterations covered by ~10 nodes, zero duplicate labels, no enumeration).

## 7.2 Self-contained PM4Py code (main model = `model_third`)

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# --- visible transitions ---
t_register = Transition(label="Register Dossier")
t_credit   = Transition(label="Credit Check")
t_tech     = Transition(label="Technical Review")
t_supplier = Transition(label="Supplier Review")
t_expedite = Transition(label="Expedite Review")
t_manager  = Transition(label="Manager Approval")
t_auto     = Transition(label="Auto Approval")
t_correct  = Transition(label="Correct Dossier")
t_release  = Transition(label="Release Order")

# --- mandatory parallel (both required, any order) ---
mandatory = StrictPartialOrder(nodes=[t_credit, t_tech])
# no edge between credit and tech => concurrent, both required

# --- optional supplier / expedite (XOR with silent) ---
supplier_opt = OperatorPOWL(operator=Operator.XOR, children=[t_supplier, SilentTransition()])
expedite_opt = OperatorPOWL(operator=Operator.XOR, children=[t_expedite, SilentTransition()])

# --- exactly-one approval ---
approval = OperatorPOWL(operator=Operator.XOR, children=[t_manager, t_auto])

# --- checks block: mandatory before optionals; optionals concurrent ---
checks = StrictPartialOrder(nodes=[mandatory, supplier_opt, expedite_opt])
checks.order.add_edge(mandatory, supplier_opt)
checks.order.add_edge(mandatory, expedite_opt)
# no edge supplier_opt <-> expedite_opt => any order / parallel

# --- correction loop: CHECKS (Correct CHECKS)* ---
# POWL LOOP children = [do, redo]; semantics: do (redo do)*
loop = OperatorPOWL(operator=Operator.LOOP, children=[checks, t_correct])

# --- root sequence via partial order ---
model_third = StrictPartialOrder(nodes=[t_register, loop, approval, t_release])
model_third.order.add_edge(t_register, loop)
model_third.order.add_edge(loop, approval)
model_third.order.add_edge(approval, t_release)

# optional: soundness / conversion sanity
# net, im, fm = pm4py.convert_to_petri_net(model_third)
# print(pm4py.check_soundness(net, im, fm, print_diagnostics=True))
```

Notes: `model_third` has zero duplicate visible labels, 9 visible transitions + 2 silent skips, no enumeration. Parallelism is via partial-order absence of edges, not via `+` with silent mandatory skips.

## 7.3 Declarative dictionaries / external checks required

Procedural backbone alone still over-approximates (allows Supplier for internal, allows whole-block repeat where P6 wants selective repeat, allows Expedite/Supplier interleaving details). Enforce explicitly:

```python
declare_rules = [
    {"template": "Precedence", "a": "Credit Check", "b": "Expedite Review",
     "desc": "Expedite must follow Credit (P4)"},
    {"template": "Precedence", "a": "Technical Review", "b": "Expedite Review",
     "desc": "Expedite must follow Technical (P4)"},
    {"template": "Precedence", "a": "Credit Check", "b": "Manager Approval",
     "desc": "Approval after Credit"},
    {"template": "Precedence", "a": "Technical Review", "b": "Manager Approval",
     "desc": "Approval after Technical"},
    {"template": "Precedence", "a": "Credit Check", "b": "Auto Approval",
     "desc": "Auto still requires checks (B2 valid only with checks)"},
    {"template": "ExactlyOne", "activities": ["Manager Approval", "Auto Approval"],
     "desc": "P5 exactly one approval"},
    {"template": "Response", "a": "Correct Dossier", "b": "Credit Check|Technical Review",
     "desc": "After Correct, at least one mandatory recheck before approval (P6 skeleton)"},
    {"template": "NotWithout", "forbidden_repeat_without": ["Credit Check", "Technical Review"],
     "requires": "Correct Dossier", "desc": "P7: repeat without Correct is suspicious"},
]

def check_trace(trace_activities, external_flag=None, affected=None):
    """Post-hoc policy check. Returns (verdict, reasons)."""
    reasons = []
    # P2 mandatory
    if "Credit Check" not in trace_activities or "Technical Review" not in trace_activities:
        # allow single-recheck iteration? full-trace must contain both at least once
        reasons.append("Missing mandatory check (P2)")
    # P4 expedite ordering
    if "Expedite Review" in trace_activities:
        e = trace_activities.index("Expedite Review")
        if not ("Credit Check" in trace_activities[:e] and "Technical Review" in trace_activities[:e]):
            reasons.append("Expedite before both checks (P4)")
    # P5 exactly one
    if sum(a in trace_activities for a in ["Manager Approval","Auto Approval"]) != 1:
        reasons.append("Approval exactly-one violated (P5)")
    # P7 repeat without correction
    for act in ["Credit Check","Technical Review"]:
        if trace_activities.count(act) > 1 and "Correct Dossier" not in trace_activities:
            reasons.append(f"Repeat {act} without Correct (P7 suspicious)")
    # P6 selective repeat transparency
    if "Correct Dossier" in trace_activities and affected is None:
        reasons.append("Correct without affected-check attribute: UNCERTAIN, requires manual attestation which check was affected (P6)")
    if "Correct Dossier" in trace_activities and affected is not None:
        # e.g. affected={"Technical Review"} then B6 valid, repeat of Credit would be over-recheck (flag)
        pass
    # P3 supplier guard
    if "Supplier Review" in trace_activities and external_flag is None:
        reasons.append("Supplier present but external/internal unknown: UNCERTAIN (P3/missing data)")
    if "Supplier Review" in trace_activities and external_flag is False:
        reasons.append("Supplier for internal order: review (P3)")
    if external_flag is True and "Supplier Review" not in trace_activities:
        reasons.append("External without Supplier: possible missing event (F4), do not auto-fail")
    verdict = "PASS" if not reasons else ("UNCERTAIN" if any("UNCERTAIN" in r or "missing event" in r for r in reasons) else "FAIL")
    # Any FAIL reasons dominate; UNCERTAIN requires human/data fix
    if any("Missing mandatory" in r or "Expedite before" in r or "exactly-one" in r or "without Correct" in r for r in reasons):
        verdict = "FAIL"
    return verdict, reasons
```

Governance use: POWL backbone gates gross violations (missing checks, wrong order, missing approval); `check_trace` gates P6/P7/P3 nuances and returns `UNCERTAIN` rather than silently passing when attributes are missing.

## 7.4 Explicit semantics

- **Mandatory checks (P2):** `mandatory` partial order requires both `Credit` and `Technical` at least once per `CHECKS` execution, any order, no `tau` skip. Unlike S, cannot choose `tau` to skip. First iteration must contain both; recheck iterations should contain at least one (declarative `Response`).
- **Optional Supplier (P3):** `supplier_opt = XOR(Supplier, tau)` after mandatory, before approval, concurrent with expedite. Procedurally optional because external/internal unknown; policy layer flags `Supplier+internal` and `external-without-Supplier` as review/`UNCERTAIN`, not auto-pass.
- **Expedite ordering (P4):** Edges `mandatory -> expedite_opt -> approval` plus DECLARE `Precedence`. Must follow both checks, precede approval. May occur before/after Supplier (no edge between them). Unlike S, `Expedite-first` is rejected; unlike C, both `Supplier->Expedite` and `Expedite->Supplier` interleavings accepted.
- **Exactly-one approval (P5):** `XOR(Manager, Auto)` exactly once between loop and release. No skip, no duplication. Both check orders compatible with both approvals (fixes C's missing `Technical-first+Auto`).
- **Correction/recheck (P6/P7):** `LOOP(CHECKS, Correct)` allows zero or more `Correct -> CHECKS` cycles. Procedurally repeats whole block (over-approximation); declaratively requires at least one mandatory recheck after each `Correct` and forbids repeats without `Correct`. Single-check repeat (B6) is procedurally accepted as partial execution? Strict POWL loop repeats full `CHECKS` shape, so single-check repeat needs either partial-repeat tolerance in checking or loop-body refinement once `affected-check` data exists. Interim: accept `Correct + single recheck` as compliant **only if** `affected` attests it, otherwise `UNCERTAIN` — transparent, unlike S (rejects all) or C (requires both).

## 7.5 Limitations from missing attributes

- Without `external/internal`, Supplier optionality cannot be enforced; third alternative must stay permissive procedurally and `UNCERTAIN` on Supplier traces. Cannot solve by making Supplier mandatory (would false-fail internals) or forbidden (would false-fail externals). Requires logging fix.
- Without `affected-check`, selective repeat cannot be validated automatically; loop must allow broader repeats plus manual attestation. Silent treatment as "any repeat allowed" would hide over-rechecks; silent treatment as "both must repeat" (C) would false-fail B6-valid.
- Missing Supplier events (F4) mean even attribute-stratified tests will show false `external-without-Supplier`; must be treated as data-quality `UNCERTAIN`, not noncompliance, until capture is fixed. No model can fix this alone.

Do not solve missing data by optionalizing everything (S's error) or by enumerating observed combos (C's error). Make uncertainty explicit.

# 10. Governance Recommendation
- **Exploration:** **Model S may be used, with label.** It is fast, simple, readable. Conditions: watermark as "exploratory map — does NOT enforce mandatory checks/ordering/corrections," never connected to release gating, always accompanied by disclaimer that `Correct Dossier` is absent and skips are model artifacts. Prefer third alternative's backbone for exploration once validated, because it shows mandatory vs optional honestly.
- **Compliance / enforcement / auto-release gating:** **Neither S nor C may be used.** S is unsafe (admits B3,B4 and all skip variants as compliant). C is overfit, unmaintainable (33 duplicates, 0.44s/case, 0.744 holdout, rejects B2/B5 legitimate), and its 0.941 precision is a positives-only memorization artifact (F5). Deploying C would block legitimate external/urgent orders and create unmanageable variant debt; deploying S would approve unchecked dossiers.
- **Retire or quarantine:** **Quarantine C from production; retire S from any enforcement-adjacent use.** C may be retained read-only as training-variant catalog for audit forensics, not as normative model. S may be retained for teaching/exploration only. Both must not be cited as evidence of compliance until E0-E10 pass.
- **Third alternative promotion conditions (must all meet before deployment even for piloted gating):**
  1. Reproducible E0-E10 run with published seeds, case IDs, costs, preprocessing; soundness passes; per-stratum fitness/precision reported.
  2. Zero duplicate visible labels maintained; simplicity and runtime within operational budget (target near S, far below C).
  3. Zero false-accepts on curated negatives (B3,B4,skip-one, dual-approval, repeat-without-Correct); correct accepts on B1,B2,B5,B7 and conditional B6 with attestation.
  4. Unseen-combination tests demonstrate acceptance of legitimate novelty (B2/B5/A2) while rejecting forbidden permutations.
  5. Logging fixes roadmapped: add `external/internal` and `affected-check` attributes; until then Supplier/correction verdicts remain `UNCERTAIN` requiring human attestation, not auto-pass. Missing Supplier handling documented as data-quality path.
  6. Documented comprehension protocol shows users correctly distinguish mandatory vs optional, ordering, exactly-one, and correction rules.
  7. Cost-sensitivity analysis shows ranking stable; post-hoc `check_trace` rules versioned and owned (compliance owns P2/P5/P7, operations owns P3/P4/P6).
  8. Pilot in advisory (human-in-loop) mode first: model proposes PASS/FAIL/UNCERTAIN, auditor samples; auto-enforcement only after false-accept/false-reject rates meet board thresholds.

In short: keep S as sketch, shelve C as catalog, invest in third (backbone + explicit uncertainty + policy checks) with data fixes.

# 11. Dissenting View
The board is over-engineering. Model C already achieves 0.941 precision and mirrors what actually happens; its holdout dip merely proves it refuses to bless unseen behavior, which is exactly what an auditor wants until new variants are approved. Adding Supplier-Auto or Technical-first-Auto branches as they appear is normal maintenance, not a flaw, and duplicates are an implementation detail the tool can hide. Model S, meanwhile, is loved by users (4.4) and fast; Proceeding with C for enforcement plus S for exploration gives us both safety and usability today, whereas the proposed hybrid adds POWL complexity, DECLARE rules no one owns, and UNCERTAIN verdicts that push work back to humans. If unseen combos are truly legitimate, approve them case-by-case and append branches; that is governance. Do not delay enforcement for ideal attributes we may never log.

What would change this dissent into agreement with the majority recommendation: publish reproducible stratified splits showing C's holdout failures are legitimate business (B2/B5 with external/urgent flags) rather than noise, plus a curated negative suite where S false-accepts B3/B4 at scale and C maintains low false-accepts without exploding to dozens of branches; demonstrate that adding the missing 10+ legitimate combos to C preserves precision without runtime or duplicate blowup and passes soundness; and show that logging external/internal and affected-check is infeasible, forcing us to accept enumeration as the only auditable control. Absent that evidence — especially if C needs constant branching to avoid blocking valid orders, or if positives-only precision collapses once negatives are tested — the dissent fails and the third alternative with explicit uncertainty is the only defensible path.
