## 1. Temporal Data Semantics

**State reconstruction.** The log is an update stream, not a set of case snapshots. Blank `amount`, `risk_level`, `jurisdiction`, and `customer_type` cells mean "no update at this event," *not* null, not default, and not "unknown cleared." State is reconstructed per case by sorting by `time:timestamp` then `event_index` (source order within a timestamp) and forward-filling each attribute (`ffill`, pandas `groupby(case).ffill()`) from the event that set it. The state governing an event is the state *after* applying that event's own attribute update(s) and *all* strictly earlier updates (including same-timestamp events with lower `event_index`). An event never sees updates from its future.

**Equal timestamps.** `time:timestamp` alone is not a total order. Where timestamps tie, `event_index` is the tie-breaker, and this can be decisive: in TX-311, the `Enhanced_Review` (index 3) precedes `Update_Jurisdiction` to DE (index 4) at 16:20, so the review was performed under US jurisdiction and the DE state only governs from index 4 onward, including the release at 16:30. Any tool that sorts only on timestamp or uses an unstable sort may silently invert these.

**Material changes.** A "material data change" for R1/R4 purposes is the latest event before release that changes a field a rule depends on: an amount increase of >20% relative to the amount *at the time of the relevant review* (not relative to case creation), a jurisdiction change, a risk reclassification, or a customer-type change. Amount comparisons are computed pairwise between the review-time snapshot and subsequent update events, using the latest known amount at each point. Decreases never invalidate (R4). An increase whose baseline amount is unknown is *not* classifiable as material or immaterial (R4/R6).

**Final attributes are not event-time attributes.** The last known amount/risk/jurisdiction per case (e.g., a case-level XES attribute) must not be back-projected. TX-311 ended as DE; that does not make its 16:20 review a "DE review." TX-305 ended with a EUR 150,000 settlement; that does not establish EUR 150,000 at release.

**Four distinct time notions.**
- *Event time*: when the activity occurred in the process (e.g., `Release_Funds` at 09:40).
- *Effective time*: when a value/approval is claimed to take effect (e.g., EX-77 `effective_from` 09:00). An attribute update in the log is treated as effective at its event timestamp unless explicit evidence establishes another effective time.
- *Record time*: when a record was written to the system of record (e.g., `Record_Exemption` at 11:00). Record time may lag event/effective time (outage, TX-302) and therefore neither proves nor disproves earlier effectiveness.
- *Evidence time*: when the supporting artefact was created/signed (e.g., a qualified signature timestamp at 09:05, or a signing certificate created at 10:30). Evidence time is what lets us test whether a claimed effective time is corroborated or contradicted. A *displayed* date is an assertion; a qualified timestamp or certificate-creation time is evidence about that assertion.

**Missing data (R6).** Missing amount/risk/jurisdiction/customer-type are propagated as unknown (`NaN` in code), never defaulted to LOW/domestic/small. If a decisive trigger can neither be established nor excluded at release, the case is INDETERMINATE, not COMPLIANT.

**Exemptions (R5).** An exemption counts only if all five conditions hold, including that evidence supports approval existing at the relevant time. A late database record (`Record_Exemption` after release) can be *evidence of* earlier approval if corroborated by independent evidence-time artefacts; a backdated displayed field alone is not conclusive, and contradictory evidence-time artefacts (certificate created after release) undermine it.

**Formal pseudo-logic** (temporal/Datalog-like; `` = "strictly precedes in (timestamp, event_index) order"; `State(c,e,f)` = latest known value of field `f` for case `c` at event `e`; `AtRelease(c)` = the release event of `c`):

```
% R4 — material increase; baseline is amount at the review event
MaterialIncrease(c, r, u) :-
    Review(r, c, kind  {Standard, Enhanced}),
    AmountUpdate(u, c), r  u,
    State(c, r, amount) = A0, A0 known, State(c, u, amount) = A1, A1 > 1.20 * A0.
MaterialIncreaseUnknown(c, r, u) :-
    Review(r, c, _), AmountUpdate(u, c), r  u, State(c, r, amount) unknown.

% Validity of a review at release: no material increase after it, before release
ValidReview(c, rev, rel) :-
    Enhanced_Review(rev, c), rev  rel,
    NOT EXISTS u: MaterialIncrease(c, rev, u) AND u  rel.

% R1 — trigger, satisfaction, exemption, violation, indeterminacy
R1_Triggered(c, rel) :-
    AtRelease(c) = rel, State(c, rel, jurisdiction) != DE,
    State(c, rel, amount) >= 100000.
R1_Satisfied(c, rel) :-
    R1_Triggered(c, rel),
    ( EXISTS rev: ValidReview(c, rev, rel)
      OR ValidExemption(c, rel, waives=R1) ).
R1_Violation(c, rel) :- R1_Triggered(c, rel), NOT R1_Satisfied(c, rel).
R1_Indeterminate(c, rel) :-
    AtRelease(c) = rel,
    (State(c, rel, amount) unknown OR State(c, rel, jurisdiction) unknown),
    NOT R1_Violation-established-by-other-means(c, rel).

% R2 — both events, ordered: Enhanced_Review  Compliance_Approve  Release
R2_Triggered(c, rel) :-
    AtRelease(c) = rel,
    (State(c, rel, risk) = HIGH OR State(c, rel, customer_type) = PEP).
R2_Satisfied(c, rel) :-
    R2_Triggered(c, rel),
    EXISTS rev, app: Enhanced_Review(rev, c), Compliance_Approve(app, c),
                     rev  app, app  rel.
R2_Violation(c, rel) :- R2_Triggered(c, rel), NOT R2_Satisfied(c, rel).
% A Compliance_Approve over a Standard-only packet does not satisfy R2 (no Enhanced_Review exists).

% R3 — re-screen strictly after list update, strictly before release
R3_Violation(c, rel) :-
    AtRelease(c) = rel, SanctionsListUpdate(lu, c, adds=J),
    State(c, rel, jurisdiction) = J, lu  rel,
    LatestScreenBefore(c, lu) = s (s  lu),
    NOT EXISTS s2: Sanctions_Screen(s2, c), lu  s2, s2  rel.

% R5 — defeasible validity; strong evidence defeats backdating objections,
%     contradictory evidence-time defeats reliance on displayed dates
ValidExemption(c, rel, waives) :-
    Exemption(x, approved_by=Head_Compliance, eff, exp, scope),
    eff <= time(rel), time(rel) < exp,
    ScopeMatches(scope, State(c, rel, jurisdiction),
                       State(c, rel, customer_type), State(c, rel, amount)),
    EvidenceSupportsApprovalAt(x, time(rel)).   % e.g. qualified signature  release
ExemptionContested(x) :-
    Exemption(x), EvidenceTimeArtefact(x, t_created), t_created > time(release referencing x),
    NOT IndependentCorroboration(x).            % displayed date alone is not corroboration

% R6/R7 are meta-rules: unknown decisive fields block Violation/Satisfied
% conclusions and yield INDETERMINATE; all State() lookups are point-in-time.
```

Note the direction discipline: reviews must be *after* the last material change and *before* release; approvals *after* the relevant enhanced review and *before* release; re-screens *after* the list update and *before* release; exemptions effective *at or before* the trigger and unexpired *at* the trigger. Reversing any of these is a different (wrong) rule.

## 4. Ambiguities and Alternative Readings

**TX-302 (COMPLIANT — alternative: JUSTIFIED_EXCEPTION).** The classification turns on whether a valid-but-unneeded exemption makes a case a "justified exception." On the facts the Enhanced_Review independently satisfies R1, so COMPLIANT is the cleaner label; if an organisation classifies any release *referencing* an exemption as exception-governed, it would be JUSTIFIED_EXCEPTION. What would change the analysis: if the 09:20 Enhanced_Review were shown to be invalid for another reason (e.g., performed on stale data), EX-77's strong evidence (qualified signature 09:05, documented outage) would carry the case as JUSTIFIED_EXCEPTION rather than NONCOMPLIANT. Conversely, if the signature were invalid, the case would *still* be COMPLIANT via the review — the exemption is not load-bearing here. This is the control case showing late *record* time (11:00) is compatible with timely *effective* approval when evidence time corroborates it.

**TX-305 (INDETERMINATE).** Two gaps combine: (i) the release-time amount is unknown, so the R1 trigger (CA  DE is known; amount  100k is not) can neither be established nor excluded; (ii) with an unknown baseline, no amount increase can be classified under R4, so even the validity scope of the 11:15 Enhanced_Review is unknowable. Evidence that would resolve it: an immutable release payload or payment instruction showing the amount actually released (if <100k  COMPLIANT via no trigger / if 100k with no intervening material change after a review that demonstrably covered that amount  possibly COMPLIANT; if 100k and the amount only became that large after the review  NONCOMPLIANT). A mere assertion that "settlement usually equals release amount" would lower, but not eliminate, indeterminacy unless backed by a control guaranteeing equality. Interpretation change that would alter the result: a policy amendment making settlement amount presumptively the release amount — that is a rule change (R6 override), not something an analyst may assume.

**TX-310 (INDETERMINATE — alternative: NONCOMPLIANT).** This is the genuinely contested exemption. Strict reading: R5 requires that "the evidence supports that approval existed at the relevant time"; the only artefact's evidence time (certificate created 10:30) *contradicts* the displayed 08:50 approval, and the oral-approval witness is the transaction requester with an interest in the release. On a burden-of-proof reading (the party invoking an exception must prove it), TX-310 is NONCOMPLIANT. Defeasible reading: oral Head_Compliance approval at 08:45 is possible, the effective window and scope match, and absence of a timely signature does not logically prove absence of approval — hence INDETERMINATE pending further evidence. I classify INDETERMINATE because the evidence is contradictory rather than merely absent, but flag that a regulator applying "exception must be affirmatively evidenced" would reach NONCOMPLIANT on identical facts. Evidence that would resolve it: telephony/meeting logs, an email or ticket timestamped before 10:00 referencing the approval, testimony from a disinterested witness, or certificate-authority records showing the certificate *renewed* (not first created) at 10:30 over an earlier signing key. Note the asymmetry with TX-302: there, evidence time (09:05 signature) *precedes* release and corroborates; here it *follows* release and contradicts.

**TX-311 (COMPLIANT — alternative readings).** Three readings are defensible and they happen to converge on outcome but not on reasoning, which matters for audit: (a) *Release-snapshot reading (adopted)*: R1 conditions on jurisdiction "at Release_Funds"; at 16:30 jurisdiction is DE, so R1 never triggers — COMPLIANT regardless of the review. (b) *Historical-trigger reading*: if the obligation attaches when the case first becomes foreign-and-high-value (16:10, US/115k) and persists until discharged, the Enhanced_Review at 16:20 discharged it (it post-dates the material increase), so still COMPLIANT — but the *ordering within the timestamp becomes load-bearing for a different reason*: had the jurisdiction update (index 4) preceded the review (index 3), the review would have been a DE-state review and the same conclusion holds here only because a US-state enhanced review is at least as stringent. (c) *Anti-avoidance reading*: a jurisdiction change to DE minutes before release could be treated as requiring evidence of genuine relocation; the log gives no provenance for the change (no note). Evidence that would change the result: proof the DE update was erroneous or backdated (then state at release is US and, still, the 16:20 review satisfies R1 — so outcome remains COMPLIANT, showing this case is robust); or a policy version defining R1's trigger over the case history rather than at release combined with invalidation of reviews upon jurisdiction change (then the DE change at index 4, after the review, would be a material change post-review  NONCOMPLIANT). Same-timestamp consequence to state explicitly: because index 3  index 4, the review cannot be credited as a review *of the DE state*; under the adopted rule that does not matter, under reading (c) it would.

**TX-307 (additional case — interpretation sensitivity).** The finding rests on the stipulated semantic fact that a Compliance_Approve over a standard packet does not cure a missing Enhanced_Review. If an organisation instead reads R2 as requiring "an approval, plus the best review performed" or treats Standard_Review + Compliance_Approve as functionally equivalent for a EUR 70,000 DE transaction, TX-307 would flip to COMPLIANT. That reading is not adopted because the rule text requires *both* named events and the log's notes explicitly describe the approval as covering a standard packet; but the rule should be amended if the business intends proportionality by amount.

**TX-306 (additional case — boundary sensitivity).** COMPLIANT depends on +4.5% being non-material and on `hc02`'s Compliance_Approve counting as *the* R2 approval (the rule does not require Head_Compliance for R2 approvals, unlike exemption approvals under R5). If a policy required Compliance_Approve specifically by Head_Compliance, or aggregated *cumulative* increases since review rather than per-update increases, facts like TX-309's two-step increases would need re-examination; in TX-306 there is only one small increase, so the result is stable, but the threshold semantics (per-update vs cumulative-since-review) should be pinned down — TX-309 is NONCOMPLIANT under either semantics, TX-306 under neither exceeds 20%.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** Token replay, alignments, and DECLARE checkers evaluate activity sequences; if a checker (or an analyst exporting case attributes) attaches the *final* case state to every event, TX-311 becomes "a DE case" throughout and TX-305 becomes "a EUR 150,000 case" at release. Both conclusions are artefacts: the DE value only exists from event index 4 onward, and the 150,000 only exists at next-day settlement. Control-flow conformance has no notion of "value as of this event" at all.

2. **Post-hoc exemptions and evidence time.** TX-302 and TX-310 have *identical control flow* (review-ish event, release referencing an exemption, `Record_Exemption` after release). One is corroborated by a qualified signature at 09:05 and a documented outage; the other is contradicted by a certificate created at 10:30 and supported only by an interested witness. No activity-order model can distinguish them, because the decisive facts (signature time, certificate creation, witness interest) are not activities in the trace. A naive checker either accepts both exemptions (wrong for TX-310 under a strict burden) or rejects both for "record after release" (wrong for TX-302).

3. **Material changes after review.** TX-306 (+4.5% after review) and TX-309 (+22.9% after the Enhanced_Review) have the same activity pattern `Enhanced_Review  Update_Amount  Release_Funds`. Control flow sees both as conforming ("review before release"); the data rule separates them via a value-relative threshold computed against the amount *at review time*. Similarly TX-308's post-review *decrease* is harmless — invisible to any sequence-based check.

4. **Conditional activation.** R1 and R2 are not universal precedence constraints; they switch on data conditions at release (foreign + 100k; HIGH or PEP). A DECLARE model stating "Enhanced_Review must precede Release_Funds" would falsely flag legitimate standard cases (e.g., a small DE retail release), while a model omitting it would pass TX-301 and TX-310. TX-307 shows the subtler version: PEP status activated R2 mid-case at 13:05, after case creation as RETAIL — activation time is a data event, not a control-flow branch.

5. **Missing data.** In TX-305 the amount is absent at creation, review, and release. Control-flow conformance is bivalent: a trace either satisfies a template or not, and missing attributes are typically ignored or defaulted (to 0, to "LOW", to the case's final value). All three defaults fabricate a verdict. Compliance semantics need a third truth value — INDETERMINATE — driven by *which* decisive fields are unknown, which no sequence checker produces.

6. **Same-timestamp ordering.** TX-311 contains an Enhanced_Review and a jurisdiction change at the identical timestamp 16:20, ordered only by `event_index`. Timestamp-granularity sorting (or any unstable sort in a conformance tool) can invert them, changing which state the review "saw." Control-flow tools that treat same-timestamp events as simultaneous or arbitrarily ordered cannot even state this distinction, let alone audit it.

7. **(Additional) Review *type* and *content* vs activity label granularity.** TX-307 contains a review and an approval in the "right" order, yet the approval covered only a standard packet and no Enhanced_Review exists. Unless the model distinguishes review types *and* links approval scope to review scope, it passes a case R2 fails. Likewise R3 (TX-304) requires a screen *after a list-content change by an external system*; the trigger is a change in reference data, not a case activity pattern.

8. **(Additional) Cross-case / reference-data triggers.** The sanctions list update is global reference data injected into one case's log. Per-case trace conformance assumes obligations arise from the case's own activities; R3's obligation arises from the *intersection* of external list state and case jurisdiction at a point in time.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payload.** At `Release_Funds`, write a hash-sealed snapshot of the exact values the release decision used: amount, currency, jurisdiction, risk_level, customer_type, rule version, and the IDs of the reviews/approvals/exemptions relied upon. This single change resolves TX-305-type indeterminacy and makes release-time state auditable without reconstruction.

2. **Separate effective, record, and evidence/signature timestamps on every artefact.** Exemptions (and reviews/approvals) should carry `effective_from`, `recorded_at`, `approved_at` (system-generated, not user-typed), qualified-signature timestamp, and certificate identifier/validity window. Displayed/backdatable fields should be non-authoritative. This directly prevents TX-310-type disputes and lets TX-302-type late records be validated mechanically.

3. **Structured exemption scope and linkage.** Log exemption scope machine-readably (jurisdiction, customer-type, amount cap, rules waived, approver role) and require the release event to reference the exemption ID *and* the system to validate scope + expiry + approver at release time, blocking or escalating on mismatch rather than relying on post-hoc registers.

4. **Change provenance for material attributes.** Every amount/jurisdiction/risk/customer-type update should carry source system, reason code, actor, prior value, new value, and effective time. Material-change invalidation (R4) should be computed and logged by the system at update time ("this change invalidates review R-123"), and releases blocked until re-review, rather than reconstructed by auditors.

5. **Rule versioning.** Stamp each case and each evaluation-relevant event with the policy/rule version and threshold set in force (e.g., EUR 100,000, 20% materiality, per-update vs cumulative semantics). Rule changes then never retroactively reclassify cases silently.

6. **Stable global ordering.** Emit a monotonically increasing, case-unique sequence number (as `event_index` here) alongside timestamps, forbid timestamp-only ordering in downstream tools, and log clock-source/precision. Same-timestamp dependencies (TX-311) should additionally be linked by explicit `caused_by`/`supersedes` references where order is semantically load-bearing.

7. **Explicit unknowns.** Replace silent blanks in source feeds with explicit `value_status  {KNOWN, UNAVAILABLE, NOT_APPLICABLE}` plus an outage/feed reference. A release attempted with a decisive field `UNAVAILABLE` should be hard-blocked or routed to manual compliance with a logged override (approver, rationale) — converting INDETERMINATE findings into either resolved data or accountable exceptions.

8. **Screening and reference-data events.** Log sanctions-list version/delta (jurisdictions added/removed, list effective time) as first-class events linkable to cases, and record which list version each `Sanctions_Screen` ran against. Re-screening obligations (R3) then become automatically checkable, and "clear at screening time" (TX-304) is provable rather than asserted.

9. **Review content binding.** Each review/approval should record the state snapshot it reviewed (amount, risk, jurisdiction, customer type, list version) and its snapshot hash. Approvals should declare the packet type reviewed (standard vs enhanced), eliminating TX-307-type ambiguity about what an approval actually covered.

10. **Pre-release control gate.** Implement R1–R5 as a system-enforced pre-release check over the point-in-time state (not as detective audit): release is technically impossible without a valid, non-invalidated Enhanced_Review/approval chain, a post-list-update screen where triggered, or a scope-matching, evidence-backed exemption — with any override generating a high-severity, fully attributed exception event.
