- Temporal precedence: J3 acquires FIX-A 09:00 -> J4 arrives CNC-2 09:50 -> CNC-2 idle 10:05-10:47 -> J3 releases 11:40 -> J4 starts 11:45 -> J4 ready for B2 13:10 -> B2 start 14:50 (after RACK-7 14:35) -> J4 pack 19:10 -> S1 dispatch 19:25.
- Resource feasibility: FIX-A capacity 1, CNC-2 capacity 1; both cannot serve J3+J4 concurrently. OVEN-1 idle but RACK-7 cleaning extends B2 wait.
- Policy constraints: FIX-A assignment rule (no preemption), batch consolidation requires J4+J5, shipment consolidation requires J1+J4.
- Causal speculation: fixture contention plausibly delayed J4 by ~100m (strong temporal overlap, machine idle proof). That delay pushed J4's batch readiness later, but B2 was anyway blocked by RACK-7 to 14:35, so fixture delay may have been absorbed partially (slack). Shipment wait for J1 (5h55m) is then partly downstream of fixture via J4 pack time, but also independent shipment policy choice.

**Narrative C - CAL-3 recalibration -> TEST-1 serialization -> S3 delay:**
- Temporal precedence: J5 ready 16:00 -> test 16:10-16:35 -> CAL-3 recal 16:35-17:20 -> TEST-1 idle 16:35-17:25 -> J6 ready 16:05, tests 17:25-17:50.
- Resource feasibility: TEST-1 can test any job but each test requires CAL-3; CAL-3 recalibration occupies tool, making TEST-1 starved despite being available.
- Policy constraints: calibration required after each test per quality policy; no second CAL-3; sequential test schedule.
- Causal speculation: recalibration plausibly serialized J6 after J5 (direct resource feasibility). If policy allows recalibration overlap with next job preparation or deferral, 50m could be saved. Alternative: J6 waiting may be due to missing operator not CAL-3, but idle alignment with recalibration window is strong evidence for tool-induced.

Each narrative spans >=4 types: A: Job-Component-ComponentLot-Batch-Machine-Shipment; B: Job-Tool-Machine-Batch-Shipment; C: Job-Tool-Machine-Shipment.

## 8. Falsification and additional data

**Six observations that would weaken top-ranked explanation (batch synchronization + RACK-7):**
1. B1 readiness timestamps are not trusted: J1/J2 were not actually ready at 08:10/08:25 (e.g. missing staging, operator absent), so 3h55/3h40 wait is data artifact not policy.
2. RACK-7 quarantine 12:55-14:35 is logging artifact: RACK-7 was available earlier but cleaning status not updated, and OVEN-1 idle was due to operator shortage not tool.
3. OVEN-1 technology requires full batch of 3: curing J1/J2 alone would have caused quality failure, so waiting for J3 was unavoidable and not "avoidable" as calculated.
4. Alternative trace shows many batches start with 1-2 jobs without delay during same period, indicating B1 was exception not systemic synchronization rule.
5. J3's late readiness 11:55 is due to J3 genuinely needing FIX-A for 160m (normal), so root cause is upstream tool not batch policy; B1 wait disappears if J3 tool hold shortened, making fixture primary.
6. Post-intervention (add second RACK) yields no reduction in Job ready->start time, indicating bottleneck shifts to lot release or shipment, not batch.

**Six additional fields/event types to discriminate hypotheses:**
1. Explicit `Ready for batch` qualification reason and `Wait for Batch` / `Wait for Tool` activity with start/end timestamps linked to both Job and Batch/Tool objects.
2. Tool lifecycle events: `FIX-A Acquire`, `FIX-A Release` with job link + `RACK-7 Clean Start/End` linked to Batch and Machine, to replace inferred gaps.
3. Operator/Resource availability events and shift calendars linked to Machine/Tool to separate tool blocking from staffing gaps.
4. ComponentLot quarantine reason code, override authorization ID, and consistent Job linkage (ensure every L7 event relates to J2/J5 in OCEL), plus safety stock levels per Component.
5. Shipment policy flag: `mustConsolidate` vs `allowSplit`, plus contractual due date and actual `Packed Ready` vs `Load` timestamps per Job-Shipment edge.
6. Per-job priority/cost and OVEN-1 recipe feasibility matrix (which jobs can share batch), plus energy/cost per batch run to quantify trade-off of smaller batches.

Collecting these would allow causal attribution beyond temporal succession and test whether low machine utilization truly masks tool/batch/shipment coupling.
