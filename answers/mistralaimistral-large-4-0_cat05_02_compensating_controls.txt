## 1. Control-Objective Decomposition

FEP-1 is not merely “two different user IDs.” Its control objective is to prevent one person from both initiating and authorizing an erroneous or fraudulent transfer. That objective can be decomposed into the following threat scenarios:

| Objective / threat scenario | AV-2 | MG-4 | RA-7 | ED-1 |
|---|---|---|---|---|
| **O1 — Single actor makes an unintentional error** (wrong amount, duplicate invoice, wrong vendor) and both prepares and releases | Prevents many cases: duplicate, amount limit, PO match, sanctions, bank ownership | Prevents if independent and before release/settlement | Detects after; corrects only if within recall window | Permits only with conditions |
| **O2 — Single actor intentionally frauds** (fictitious vendor, changed bank account, colluding beneficiary) | Prevents some cases: bank-change check, sanctions, bank ownership | Prevents if independent and reviews bank details and supporting evidence | Detects after; may be too late | Conditions reduce but do not eliminate risk |
| **O3 — Urgency/emergency is used to bypass four-eyes** | Prevents if operational | Prevents if independent before settlement | Detects after | Controlled emergency path; conditions must hold |
| **O4 — Two nominally distinct actors are not independent** (shared credentials, shared workstation, collusion, repeated pairing) | Fails to detect collusion | Fails if manager is conflicted or rubber-stamps | Detects after | Not applicable; ED-1 is a single-operator permission |
| **O5 — Payment is released before independent review but before irrevocable settlement** | Prevents if before release | Hybrid: detective of release, preventive of settlement | Detects after | Requires manager before settlement |
| **O6 — Defect is detected only after settlement/recall window** | Prevents some before release | Can correct if before settlement | Fails as corrective if too late | Requires audit within one business day |
| **O7 — AV-2 is overridden or unavailable** | Fails if overridden or unavailable | Can compensate if independent and thorough | Detects after | Requires AV-2 pass without override |
| **O8 — Manager approval is rubber-stamped or conflicted** | Independent system check but limited | Fails if not truly independent | Detects after | Requires independent manager |

ED-1 is a permission with conditions, not a control that itself prevents loss. It relies on AV-2, MG-4, and RA-7.

## 2. Equivalence and Sufficiency Test

A compensating-control package should be judged against the control objective, not against the number of activities performed.

### Fully equivalent

A package is fully equivalent when it addresses the same threat scenarios with:

- **Timing:** preventive before release or before irrevocable bank settlement.
- **Independence:** no conflict of interest, no shared credentials, no self-override.
- **Coverage:** relevant risks are checked — bank change, duplicate, amount, vendor, receipt, commercial reasonableness.
- **Overrideability:** overrides require independent approval and are logged.
- **Recoverability:** audit occurs before the recall window closes.
- **Evidence quality:** documented review of invoice, bank details, and supporting receipt.
- **Collusion resistance:** not defeated by two-person collusion or shared workstations.

### Partially equivalent

A package is partially equivalent when it meets some dimensions but not others. Examples:

- Manager approval occurs after release but before settlement.
- AV-2 passes, but receipt of goods/services is not verified.
- Audit is timely, but the manager was not independent.
- Independence of the two users is uncertain because of shared workstations or repeated pairing.

### Merely mitigating

A control is merely mitigating when it reduces likelihood or severity but does not reliably prevent or detect the loss. Examples:

- Late audit after the recall window.
- Rubber-stamped manager approval.
- Unsigned manual checklist during an AV-2 outage.

### Ineffective

A package is ineffective when:

- There is no independent check.
- The control was absent, overridden, or bypassed.
- The only review occurred after irrevocable settlement.

### Why “same expected loss” is not the only standard

Two control packages can have the same expected loss but different control quality. A late audit after the recall window may have the same expected loss as no audit in a narrow model, but it fails the corrective objective. A rubber-stamped approval may have the same expected loss as no approval, but it creates false assurance and weakens deterrence. Preventive controls stop loss before it occurs, preserve evidence, reduce recovery costs, and are more resilient to collusion. Therefore, equivalence must be judged on timing, independence, coverage, overrideability, recoverability, evidence quality, and collusion resistance — not only on expected loss.

## 4. Preventive–Detective–Corrective Comparison

|---|---|---|---|---|---|---|---|---|
| AV-2 | Before release | System; can be overridden | Duplicate, sanctions, bank ownership, bank changes, amount, PO match; not receipt or commercial reasonableness | Can be overridden by manager credential | N/A (preventive) | Clean pass strong only for covered checks | Low; does not detect collusion | Preventive |

| RA-7 | After release | Auditor independent | Depends on audit scope | N/A | Only if within recall window | Strong if timely | Detective | Detective/corrective |
| ED-1 | Conditional | Via MG-4 | Emergency conditions | N/A | Via RA-7 | Depends on token logs | Not addressed | Permission framework |

### Manager action before settlement but after Release_Payment

I classify this as **hybrid**:

- **Detective with respect to Release_Payment:** the release has already occurred.
- **Preventive with respect to irrevocable bank settlement:** the manager can still stop the payment before final settlement.
- **Potentially corrective:** if the manager finds a defect, the payment can be stopped or recalled.

This is why AP-201 and AP-207 are not automatically failures: the manager acted before settlement. But it is not fully equivalent to a true second releaser before release, because the release event itself was not independently authorized.

## 6. Evidence and Monitoring Recommendations

Recommended monitoring rules:

- **Same-user rate:** monitor the percentage of completed payments where preparer equals releaser. Alert on any same-user completed payment outside ED-1, or above a low threshold such as 1%.
- **Override rate:** monitor AV-2 warnings and overrides. Alert on any override by the preparer, any use of another person’s override credential, or any override without independent manager approval.
- **Late manager approval:** alert when manager approval occurs after release or after settlement. Require manager approval before irrevocable settlement.
- **Audit-before-recall-window:** monitor audit delay from release. Alert if audit begins more than 24 hours after release, or more than 12 hours for high-risk payments.
- **Repeated resource pairs:** monitor preparer/releaser pair frequency. Alert if the same pair processes an unusual number of payments, such as more than 20 in 30 days.
- **Shared workstations:** monitor login and workstation logs. Alert if the preparer and releaser use the same workstation.
- **Bank-change proximity:** alert if a vendor bank account changed within the previous seven days. Require enhanced independent verification.
- **Control outages:** monitor AV-2 availability. Alert on any release during an outage. Require a signed manual checklist with independent sign-off.

These are **alerts, not proof of misconduct**. An alert should trigger investigation and evidence collection, not an automatic conclusion of fraud.

Recommended evidence to retain:

- Emergency token creation logs and system clock synchronization records.
- AV-2 pass/warning/block logs and override credential usage.
- Manager review notes, including what was reviewed: invoice, bank details, receipt.
- Workstation and credential login logs.
- Bank account change records and bank ownership verification.
- Audit workpapers and recall/stop records.
- Organizational design documents for payment cells and segregation of duties.
