# 3. Consequences for performance analysis

### General Bias Mechanisms
*   **Waiting Time (Queue to Start):**
    *   **Inflated:** When `start` is artificially delayed due to batching (e.g., G1, G2, G6), the interval between `queue_arrival` and `start` captures waiting for the batch to form, not just the resource queue.
    *   **Deflated:** If `queue_arrival` is the only arrival indicator but `start` is rounded up (G7), waiting time is underestimated.
*   **Service Time (Start to Complete):**
    *   **Underestimated:** If `complete` is a bulk submission time (G3, G6) and work finished earlier, service time is truncated.
    *   **Overestimated:** If `start` is a batch start time but work began later (G1), or `complete` is rounded down (G7), service time is distorted.
*   **Resource Utilization:**
    *   **Artificially High:** Shared accounts (G5) make the resource appear busy even if multiple analysts share it, but `resource` is `analyst_pool`.
    *   **Artificially Low:** If `start`/`complete` are identical (G6), utilization calculation (Duration/Available) yields zero service time, masking actual resource load.
*   **Bottleneck Detection:**
    *   **False Positives:** G6 creates a bottleneck at 17:00 (zero service, high queue wait).
    *   **False Negatives:** G7 hides variance; G1 hides individual worker variability within the batch.

### Specific G6 Discussion (Inflated Waiting + Near-Zero Service)
G6 data (`manual_bulk_form`, `start`=17:00, `complete`=17:00) creates a specific analytical trap.
1.  **Inflated Waiting:** The `queue_arrival` times range from 14:05 to 16:25. The `start` is 17:00 for all. Calculated waiting time = 17:00 - 14:05 = 2h 55m for the first case. This suggests a massive bottleneck. In reality, the operator likely collected all 7 tickets and submitted them at 17:00. The "waiting" is actually **administrative batching delay**, not resource contention.
2.  **Near-Zero Service:** `start` = 17:00, `complete` = 17:00. Calculated service time = 0 minutes. This implies the resource (T-F) did nothing. In reality, the work was performed prior to 17:00. This creates a **zero-duration anomaly** that breaks throughput calculations (Throughput = 1 / Service Time = Infinity).
3.  **Resolution:** Treat `complete` as "Batch Submission". Service time should be estimated from `queue_arrival` to `complete` minus `batch_setup_time`, or exclude `start`/`complete` and use `recorded_at` to infer duration if available.

# 5. Robustness and alternative explanations

### Resource Identity Trust
*   **Trusted (G1, G2, G4, G6, G7, G8):** If `resource` is trusted (e.g., RBT-7 is a physical machine), identical `start`/`complete` strongly implies physical concurrency or batching.
*   **Shared Account (G5):** If `analyst_pool` is treated as a single resource, utilization is 100% during 13:00-13:30. If treated as 3 analysts, utilization is 33%. This changes bottleneck detection significantly.

### Timestamp Exactness vs. Interval Censoring
*   **Exact (G1, G4, G8):** 1-second precision allows detection of true concurrency.
*   **Censored (G2, G3, G5, G6, G7):** 1-minute or 15-minute precision hides variance.
    *   *Example:* G7 shows 14:00-14:15. The actual variance could be 13:45-14:30. The "batch" might be a rounded representation of a serial process.
    *   *Example:* G6 shows 17:00-17:00. With 1-minute precision, actual work could be 16:59-17:01. However, the `recorded_at` uniformity (17:01) suggests a submission event, not work events.

### Three Cases with Multiple Physical Explanations
1.  **G1 (Apply label):**
    *   *Explanation A:* Genuine simultaneous batch (Machine holds 4 items).
    *   *Explanation B:* Automated operator fed 4 items sequentially at 09:00, but machine processed them in parallel.
    *   *Differentiation:* Check `recorded_at`. If machine logs are synced with operator, it's A. If operator logs are synced, it's B.
2.  **G5 (Root-cause analysis):**
    *   *Explanation A:* Shared account artifact (One analyst logged in, did all work).
    *   *Explanation B:* Three analysts on shared VDI, working concurrently (Multitasking).
    *   *Differentiation:* Badge-level identity retention (currently missing). If logs show overlapping `recorded_at` from different users, it's B.
3.  **G6 (Close ticket):**
    *   *Explanation A:* End batching / Bulk submission (7 tickets closed at end of shift).
    *   *Explanation B:* Manual delay (Operator worked on tickets but didn't click "Complete" until 17:00).
    *   *Differentiation:* Source `manual_bulk_form` vs `manual_form`. Bulk form implies A.

# 6. Data-collection redesign

1.  **Execution Timestamps:** Replace `recorded_at` with `execution_timestamp` (system clock at moment of action). This decouples database insertion time from work time.
2.  **Recording Timestamps:** Log `start` and `complete` events at the *moment* the state changes, not when the batch is submitted.
3.  **Source Clocks:** Synchronize all `source` clocks (PLC, tablet, MES) to a central NTP source to resolve "different clocks" issues (G8).
4.  **Resource/Badge Identity:** Replace `analyst_pool` with badge ID or user ID. If shared accounts are unavoidable, log `session_id` alongside `resource`.
5.  **Group/Batch Identifiers:** Include a `batch_id` field if multiple items are processed together (G1, G2). This distinguishes "batch start" from "individual start".
6.  **Workstation Capacity:** Log `queue_size` or `fixture_status` (e.g., "Fixture Full") to justify batching.
7.  **Pause/Resume Events:** Explicitly log `pause_start` and `pause_end` rather than inferring from `complete` - `start`.
8.  **Timestamp Precision Metadata:** Store `precision` in metadata, but also store `milliseconds` if available, to allow post-hoc rounding analysis.

# 7. Final adjudication

*   **High Confidence Interpretations:**
    *   **G1:** Genuine simultaneous batch (Machine cycle).
    *   **G4:** Sequential batching (Scanner serial).
    *   **G7:** Timestamp coarsening (Quarter-hour rounding).
    *   **G6:** End batching / Bulk submission (Manual form artifact).
*   **Exclude / Interval-Censored in Queue Analysis:**
    *   **G5:** Shared-account artifact. Do not attribute waiting time to specific analysts. Treat `resource` as a pool.
    *   **G2:** Start batching. Waiting time includes batch formation delay.
*   **Require Operational Validation:**

    *   **G8:** Queue accumulation. Need to verify if `start` delay is due to safety check or resource downtime.

*Recommendation:* For queue analysis, treat G1, G4, G8 as valid service times. Treat G6 service time as 0 (exclude from throughput) or use `recorded_at` to estimate batch duration. Treat G7 as rounded intervals. Treat G5 as a pool resource.
