## 1. Equivalence design space

Three equivalence relations are defined, from coarsest to finest. A fourth relation (businesscapability) is sketched to illustrate aggregation.

### 1.1 Activitysequence equivalence
**Definition**  
Two executions are equivalent iff the ordered list of activity labels (event types) is identical. All object identifiers, object types, O2O qualifiers, and crossobject references are ignored.

**Invariants preserved**  
Sequence of activity names.

**Information discarded**  
Everything except the ordered activityname trace.

**Properties**  
Reflexive, symmetric, transitive over the set of executions.  
Concurrent or sametimestamp events are treated as totally ordered by the given timestamp (no partialorder handling).

### 1.2 Typed structural equivalence under identifier renaming
**Definition**  
Construct a directed bipartite graph G = (E  O, R) where E is the set of event nodes, O the set of object nodes. Each object node has a type (Order, Item, Package, Delivery, Invoice, Payment) and a flag is_external iff the original ID begins with `EXT`. Each event node has its activity label. An edge (e, o) exists when event e references object o.  
Two executions are equivalent iff there exists a bijection  between their graphs that  
- preserves event order (the sequence of events maps liketolike),  
- preserves event labels, object types, and the external flag,  
- respects incidence (e references o  (e) references (o)),  
- treats eventparameter lists as **unordered** sets (so X1 and X2 can be matched by swapping the internal Item identities).  

Local object identifiers are replaced by placeholders; only types, external flags, and structural relations matter.

**Invariants preserved**  
Object types, multiplicities per event type, externalobject flags, event order, the existence of relations.

**Information discarded**  
Original local identifiers, ordering of object parameters inside an event, O2O qualifiers.

**Properties**  
Reflexive, symmetric, transitive. Concurrency is handled identically to Activitysequence equivalence; a total order is assumed.

### 1.3 Businesssemantic equivalence (preferred)
**Definition**  
Extends Typed structural equivalence by also matching O2O qualifiers (e.g., `removed_before_dispatch`, `partially_settles`) as edge attributes. Two executions are equivalent iff the typed structural graphs are isomorphic and, for every corresponding edge, the set of O2O qualifiers is identical.  
This captures lifecycle motifs: item replacement, returnrepack, partial payments, and crossorder sharing. Object multiplicities, external references, and qualifierlabelled edges are all mandatory.

**Invariants preserved**  
Everything preserved by Typed structural equivalence, plus O2O qualifiers.

**Information discarded**  
Only raw local identifiers.

**Properties**  
Reflexive, symmetric, transitive. Same handling of concurrency.

### 1.4 Businesscapability equivalence (fourth, optional)
Groups executions by highlevel business capability (e.g., “singleshipment fulfilment”, “splitshipment”, “return handling”). This is coarser than Businesssemantic equivalence and intentionally merges X3 and X4 into one “splitshipment” cluster. It is not used as the primary semantic clustering but is referenced in recommendations.

## 2. Canonical signatures

The following schem creates a signature that is invariant under localidentifier renaming but preserves all information required by the preferred Businesssemantic equivalence. It treats eventparameter sets as unordered, includes external flags, and encodes O2O qualifiers.

```python
def canonical_signature(execution):
    # execution: list of events, each with
    #   event.activity : str
    #   event.objects  : dict {object_type : [object_id]}
    # execution.o2o_qualifiers : dict {(event_idx, object_id) -> qualifier_str}

    # 1. Map every object to a canonical name.
    obj_map = {}
    type_counter = {}
    for i, ev in enumerate(execution.events):
        for otype, oids in ev.objects.items():
            for oid in oids:
                if oid not in obj_map:
                    if oid.startswith("EXT"):
                        obj_map[oid] = f"{otype}_EXT_{oid}"  # preserve external identity
                    else:
                        type_counter[otype] = type_counter.get(otype, 0) + 1
                        obj_map[oid] = f"{otype}_{type_counter[otype]}"

    # 2. Build eventlevel signature fragments.
    sig_fragments = []
    for i, ev in enumerate(execution.events):
        params = {}
        for otype in sorted(ev.objects.keys()):  # sort types for determinism
            can_ids = sorted([obj_map[oid] for oid in ev.objects[otype]])
            quals = []
            for oid in ev.objects[otype]:
                q = execution.o2o_qualifiers.get((i, oid))
                if q:
                    quals.append(f"{obj_map[oid]}:{q}")
            if quals:
                params[otype] = {"ids": can_ids, "quals": sorted(quals)}
            else:
                params[otype] = {"ids": can_ids}
        sig_fragments.append(f"{ev.activity}({params})")
    return "|".join(sig_fragments)
```

## 4. Cluster interpretations (preferred semantic)

### SEM1 – Standard singleshipment fulfilment
**Signature** `CreateAdd×2Pack(1 Package,2 Items)DispatchInvoicePayment`  
**Business behaviour** The entire order is packed into one package, dispatched in one delivery, invoiced once, and fully paid.  
**Operational risks/opportunities** Lowest complexity; underutilisation of consolidation opportunities.  
**Traditional flattening** A single case per order represents this perfectly.  
**Stability** Stable: identifier renaming does not change cluster.

### SEM2 – Split packages, consolidated delivery
**Signature** `… Pack, Pack, Dispatch(2 Packages) …`  
**Business behaviour** Items are packed in separate packages but shipped together.  
**Risks/opportunities** Reduced shipping cost vs. multiple deliveries; risk of one delayed item blocking the whole consignment.  
**Flattening** A single case loses the twopackage object count; attribute “number_of_packages” is needed but hides the objectcentric Pack relations.  
**Stability** Stable.

### SEM3 – Split packages, split deliveries, partial payments
**Signature** `PackDispatchPackDispatchInvoicePayment×2 (partial and completion)`  
**Business behaviour** Progressive fulfilment: items are packed and shipped as soon as ready; invoicing is single but payment is split (e.g., 50 % deposit, 50 % on completion).  
**Risks/opportunities** Improves cashflow control; introduction of paymentmatching complexity.  
**Flattening** Requires multiple case fragments (one per delivery) and loses the wholeorder invoicetopayment topology.  
**Stability** Stable.

### SEM4 – Crossorder logistics sharing
**Signature** `Pack on [Order,EXT-Order]; Items include EXT-Item`  
**Business behaviour** The package consolidates items from the current order and an external order, sharing physical shipment.  
**Risks/opportunities** Consolidation savings; incorrect blame attribution if damage occurs.  
**Flattening** Flattening to a single order loses the external order dependency; traditional caseperorder would split the Pack event.  
**Stability** Stable provided EXTreferences are preserved.

### SEM5 – Crossorder invoice sharing
**Signature** `Invoice on [Order,EXT-Order]`  
**Business behaviour** Two orders are billed together; payment is recorded without orderlevel allocation.  
**Risks/opportunities** Administrative convenience but risk of payment misapplication.  
**Flattening** Inflates a single case with two orders or requires an artificial “header” case.  
**Stability** Stable.

### SEM6 – Item replacement in fulfilment
**Signature** `Dispatch includes an Item (the replacement); Packoriginal_item has qualifier ‘removed_before_dispatch’`  
**Business behaviour** An item is replaced after packing; the original item is removed before dispatch, the new item is added.  
**Risks/opportunities** Inventory inaccuracy, orderchange management; opportunity to track changes precisely.  
**Flattening** The extra Item parameter on Dispatch is invisible in standard activity labels; O2O qualifiers are lost.  
**Stability** Stable.

### SEM7 – Return and repack
**Signature** `Return ItemInspect ReturnPack (new package)Dispatch (new delivery)`  
**Business behaviour** An item is returned after initial dispatch, inspected, repacked, and redelivered. The original package is replaced for that item.  
**Risks/opportunities** Reverse logistics cost; opportunity to learn defect patterns.  
**Flattening** Flattening would require a “return subprocess” case and cannot easily link the new package to the original order.  
**Stability** Stable.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### Information preserved by the PM4Py key structure
`pm4py.cluster_equivalent_ocel` operates on the objectcentric event log graph. It canonically labels event nodes (activity name, timestamp) and object nodes (object type, possibly object ID after hashing) and computes a graphisomorphism hash (e.g., Weisfeiler–Lehman). The resulting equivalence classes group executions with identical graph structure **after canonical labelling**. If raw object IDs are used as node labels, every execution becomes a singleton cluster because local IDs differ.

### Why raw object identifiers make clusters too fine
Object IDs are locally scoped; without canonical renaming, X1 and X2 would be placed in different clusters even though they are structurally identical. The function’s default behaviour risks overseparating variants.

### Canonicalisation and postprocessing
To obtain meaningful clusters, one must canonicalise local object IDs before/after `cluster_equivalent_ocel`:
- Preprocess: replace local IDs with typeordered indices (e.g., `Order_0`, `Item_0`) and mark external objects with a distinguishable prefix.
- Postprocess: merge clusters whose custom businesssemantic signature (shown in §2) matches.

### When exact equivalence is preferable
Exact equivalence (including raw IDs) is useful for duplicate detection, data cleaning, or when the log is guaranteed to have globally unique, meaningful identifiers.

### Impact of `max_objs` and large connected executions
Large fullorder graphs can lead to high computational cost. Pruning by object type, limiting object cardinality, or windowbased subgraph extraction is often necessary.

def canonicalise_ocel_subgraph(sub_ocel):
    local_ctr = {}
    for ev in sub_ocel.events:
        for obj in ev.objects:

## 8. Limitations and recommendation

No single equivalence notion is optimal for all purposes.

| Use case                  | Recommended equivalence level          | Why                                                                                       |
|---------------------------|-----------------------------------------|-------------------------------------------------------------------------------------------|
| **Compliance monitoring** | Businesssemantic (or even exact structural) | Must detect all deviations, including crossorder sharing and item replacement. Coarser levels would miss noncompliant patterns (e.g., X5, X7). |
| **Operational segmentation** | Businesscapability (coarser than semantic) | Grouping X3 and X4 as “split shipment” highlights the fulfilment strategy choice; finer splits may fragment the analysis. |
| **Rootcause analysis**   | Typedstructural or businesssemantic  | Distinguishes exact event–object configurations to correlate with defects. Collapsing variants hides causal factors (e.g., partial payment may correlate with delays). |
| **Descriptive reporting** | Activitysequence or businesscapability | Stakeholders need a highlevel, readable summary; 7 semantic clusters may be too many. Activitysequence clusters give a firstglance process picture. |

**Conclusion**  
The three explicit relations form a hierarchy from coarse (AS) to fine (semantic). Businesssemantic equivalence provides the richest objectcentric view while remaining robust to identifier changes. It is recommended as the primary analytical lens, but users should adapt the granularity (by ignoring qualifiers, external flags, or collapsing events) according to the question they seek to answer.
