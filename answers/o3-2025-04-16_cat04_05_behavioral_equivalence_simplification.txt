# 1. Equivalence Notions  
We use process-tree semantics as implemented in PM4Py.  
All notions are defined over **complete** executions (the final marking is reached).  
Occurrences of the same visible label are distinguished **positionally**; i.e.  
Open, Analyze, Analyze, Close  Open, Analyze, Close, Analyze.

• Visible-trace equivalence (VT) – Two models are VT–equivalent iff, after deleting every `tau` leaf, they generate exactly the same set of complete visible traces of unbounded length.

• Bounded visible-language equivalence under P3 (BV-12/3) –  
Restrict each trace to at most 12 visible events and to at most three occurrences of `Analyze Revision`.  
Two models are BV-12/3–equivalent iff the resulting finite trace sets coincide.

• Operational-compliance equivalence under P1 (OC) –  
A trace is OC-legal iff it satisfies  
  1. for every occurrence of `Analyze Revision` there is a *later* `Check Revision` and no `Rework Case` or `Close Case` intervenes;  
  2. `Open Case` is first and `Close Case` last;  
  3. every `Rework Case` is followed by another `Analyze Revision`;  
  4. all other visible behaviour may occur arbitrarily often, silent behaviour is invisible.  
Two models are OC-equivalent iff they generate the same OC-legal traces.

• Dashboard equivalence under P2 (DB) –  
Transform every complete visible trace T into the tuple  
  (#Analyze, hasRework  {0,1}, hasCheck  {0,1})  
after hiding `Approve Revision` and `tau`.  
Two models are DB-equivalent iff the obtained multisets of tuples coincide.

# 2. Structural Comparison  

| Feature | Model A | Model B | Semantic consequence |
|---------|---------|---------|----------------------|
| Position of `Check Revision` | Inside the loop body, executed once per loop iteration | Parallel branch outside the loop, executed exactly once | A guarantees 1-to-1 relation with each analysis attempt; B does not |
| Minimum #Checks | 1 | 1 | Equal |
| Maximum #Checks | = #Analyze attempts | 1 | A can have many checks, B cannot |
| Earliest moment of Check | During first iteration, before or after the first `Analyze` | Immediately after `Open Case` because branch is concurrent | Both allow very early check |
| `Approve Revision` | Optional (XOR with `tau`) | Same | Equal |
| Rework separation | Always *after* an analyse+check pair | May appear between two analyses without an intervening check | B violates OC rule 1 |
| Loop join | Sequential join before `Close Case` | AND-join after the parallel branch | Differences are invisible to dashboard but decisive for OC |

# 3. Verdicts  

| View | Verdict | Confidence | Decisive reason | Caveat |
|------|---------|------------|-----------------|--------|
| P1 – Operational compliance (OC) | not equivalent | high | B allows two analyses separated by Rework before the single check | — |
| P2 – Executive dashboard (DB) | equivalent only under stated abstraction | medium | Tuple abstraction collapses any number of checks >0 into `hasCheck = 1` | Assumes management really does not care about check-per-analysis ratio |
| P3 – Bounded testing (BV-12/3) | not equivalent | high | Two-check traces of A versus one-check limit of B appear within the bound | Bounded evidence, not a proof |

# 5. Bounded Comparison Code  

```python
# ---------------- bounded_exploration.py ----------------
import pm4py
from pm4py.objects.process_tree import replay
from pm4py.objects.conversion.process_tree import converter as pt_converter
from collections import deque, defaultdict
import itertools

PT_A = "->('Open Case',*(->(+('Analyze Revision','Check Revision'),X('Approve Revision',tau)),'Rework Case'),'Close Case')"
PT_B = "->('Open Case',+('Check Revision',*(->('Analyze Revision',X('Approve Revision',tau)),'Rework Case')),'Close Case')"

def load(tree_str):
    tree = pm4py.parse_process_tree(tree_str)
    net, im, fm = pm4py.convert_to_petri_net(tree)
    pm4py.check_soundness(net, im, fm)
    return tree, net, im, fm

def enum_visible_traces(net, im, fm, max_vis=12, max_an=3):
    Trace = tuple
    res = set()
    visited = set()
    queue = deque()
    queue.append((im, tuple(), 0))          # marking, visible trace, #Analyze so far
    while queue:
        mark, vis, n_an = queue.popleft()
        state_id = (frozenset(mark.items()), vis, n_an)
        if state_id in visited:
            continue
        visited.add(state_id)

        if mark == fm:
            res.add(vis)
            continue

        for t in pm4py.get_enabled_transitions(net, mark):
            new_mark = mark.copy()
            pm4py.execute_transition(net, new_mark, t)
            label = t.label
            new_vis = vis
            new_n_an = n_an
            if label is None:                           # tau
                pass
            else:
                if label == "Analyze Revision":
                    new_n_an += 1
                new_vis = vis + (label,)
                if len(new_vis) > max_vis or new_n_an > max_an:
                    continue
            queue.append((new_mark, new_vis, new_n_an))
    return res

treeA, netA, imA, fmA = load(PT_A)
treeB, netB, imB, fmB = load(PT_B)

tracesA = enum_visible_traces(netA, imA, fmA)
tracesB = enum_visible_traces(netB, imB, fmB)

onlyA = tracesA - tracesB
onlyB = tracesB - tracesA

print(f"#Traces A (bound) : {len(tracesA)}")
print(f"#Traces B (bound) : {len(tracesB)}")
print(f"Unique to A      : {len(onlyA)}")
print(f"Unique to B      : {len(onlyB)}\n")

for t in sorted(itertools.islice(onlyA, 5)):
    print("A-only:", t)
for t in sorted(itertools.islice(onlyB, 5)):
    print("B-only:", t)
```

The breadth-first search is **exhaustive** under the stated bounds because:
1. each queue state stores the full marking, visible-trace prefix and Analyse-count;
2. the queue is finite (12-event, 3-analysis cap);
3. silent transitions are included without consuming the budget.

# 6. Stochastic and Footprint Comparison  

PM4Py’s `discover_footprints` reveals that both models have the same directly-follows relations between most labels.  
However, the footprint abstraction forgets *counts* (“one per iteration” vs “once globally”), therefore an equal footprint would be inconclusive.

`get_stochastic_language` could sample probability distributions if transition probabilities were available, but none are defined; inventing them would bias the result. Even with arbitrary probabilities, a low Earth-Mover’s Distance (`compute_emd`) only says the two distributions are close, not identical; rare but OC-critical traces might be suppressed.

Accordingly, these quantitative techniques provide **supporting evidence** but cannot prove visible-trace equivalence.

# 8. Simplified Model  

Target semantics: **Dashboard view P2**.  
Goal: preserve (#Analyze, hasRework, hasCheck) and the mandatory opening/closing activities, nothing else.

Compact process tree (`simplified_pt`):  

```
->(
  'Open Case',
  *(
      'Analyze Revision',
      X('Rework Case', tau)      // optional rework after each analysis
  ),
  'Check Revision',
  'Close Case'
)
```

PM4Py code:

```python
simplified_pt = "->('Open Case',*( 'Analyze Revision', X('Rework Case',tau) ),'Check Revision','Close Case')"
simplified_model = pm4py.parse_process_tree(simplified_pt)
```

Preservation table  

| Property | Original A | Original B | Simplified | Remark |
|----------|------------|------------|------------|--------|
| #Analyze exact |  |  |  | loop keeps counter |
| hasRework exact |  |  |  | optional per iteration |
| hasCheck boolean | 1 | 1 | 1 | good for DB |
| Check per analysis |  |  |  | deliberately abstracted |
| Soundness |  |  |  | verified |

Regression traces (should be accepted)  
1. Open, Analyze, Check, Close  
2. Open, Analyze, Rework, Analyze, Check, Close  
3. Open, Analyze, Rework, Analyze, Rework, Analyze, Check, Close  

Negative traces (should be rejected)  
a. Open, Check, Analyze, Close – check occurs too early.  
b. Open, Analyze, Close – missing check.

The simplified model has only 9 nodes and depth 3 – substantially smaller than both originals.

# 9. Final Recommendation  

• For the **operational-compliance view (P1)**, keep **Model A**; Model B and the simplified model violate the one-check-per-analysis rule.  

• For the **executive dashboard (P2)** it is safe – and simpler – to replace either original by the **simplified model**. Stakeholders explicitly declared that check multiplicity is irrelevant.  

• For **bounded testing (P3)** neither original is equivalent to the other; choose the model that matches the real system. Bounded evidence must not be promoted to a proof.

Always document which abstraction a given model is meant to serve; mixing them will re-introduce the hidden compliance defect exemplified by Model B.
