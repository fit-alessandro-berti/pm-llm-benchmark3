## 1. Temporal Data Semantics

**Ordering and state reconstruction.** Every event is ordered by the lexicographic key `(time:timestamp, event_index)`. `event_index` is only a tie-breaker within equal timestamps, never a substitute for timestamp across different timestamps. The state of a case at event `e`, `State(c,e,attr)`, is the fold of all non-blank attribute values on events `f` with `f` at or before `e` in that order. Attribute updates take effect at their own event timestamp unless evidence explicitly establishes another effective time. This forward-fold is computed event by event, never by copying the last value in a case backwards.

**Blank cells.** A blank attribute cell means *no update at this event*: carry forward the previous value. If no value has ever been set, the state is `UNKNOWN` (), not zero, not `LOW`, not `null-as-low-risk`. A blank on a `Create_Transaction` therefore means the initial value is unknown (TX-305), whereas a blank on a later `Release_Funds` means the release does not update the value.

**What counts as an update.** `Update_Amount`, `Update_Jurisdiction`, `Update_Customer_Type` and `Risk_Reclassify` carry the new value. A Sanctions_List_Update jurisdiction field names the listed jurisdiction, not a case-jurisdiction update. A `Record_Exemption` exemption_id is linkage evidence, not a state change. A review carries no new attribute; it snapshots the state at its own position.

**Material changes.** Two kinds must be distinguished. (a) *Material amount change* (R4): an amount increase to more than 120% of the amount at the latest Standard_Review or Enhanced_Review. A decrease never by itself invalidates a review. An increase from UNKNOWN is unclassifiable. (b) *Trigger-relevant change*: a change in jurisdiction, risk or customer type that alters whether a rule's condition holds at release. Such a change is material for the rule it affects even when the R4 20% test is not met. A review covers the state it actually reviewed; a review document with no amount (TX-305) does not prove coverage of any amount.

**Final attributes and future events.** The final value in a case is valid only for events at or after its update. Settlement amount on 2026-04-07 does not fix the release amount on 2026-04-06 (TX-305); a reclassification at 10:15 governs a 10:30 release, not the 10:00 creation (TX-303); a jurisdiction update at event_index 4 governs the release, not the review at event_index 3 (TX-311). Future events are excluded from `State(c, release)`, though they may later serve as *evidence about* an earlier event, subject to provenance.

**Four distinct times.** *Event time* is when the activity occurred. *Effective time* is when a value, approval or exemption takes legal effect (`effective_from`, an attribute update's own timestamp by default). *Record time* is when a system recorded it (database insert at 11:00). *Evidence time* is when the supporting artefact was created (qualified signature timestamp, certificate creation, witness statement, settlement). A record time after release can be evidence of an earlier effective time only if the provenance chain (documented outage plus a trustworthy pre-release signature, TX-302) supports it. A displayed backdated field is a claim, not proof (TX-310). Conflating these times is the central error this assessment avoids.

## 4. Ambiguities and Alternative Readings

**TX-305 (INDETERMINATE).** A signed immutable release payload showing the amount at 11:30 would resolve it: if <100,000, R1 not triggered; if 100,000, the 11:15 Enhanced_Review would need to be shown to have reviewed that amount and to postdate any material change. Proof that the settlement amount equals the release amount (same payload hash, bank confirmation of the release instruction) would also resolve it; the current "may equal" does not. Copying the settlement value backwards would violate R7 and is not a valid resolution.

**TX-310 (INDETERMINATE).** What would change the result: an independent, contemporaneous record of Head_Compliance approval at or before 10:00 (qualified signature with certificate valid before release, system audit log, or a disinterested witness) would make the exemption valid and the case a justified exception to R1 despite the missing Enhanced_Review. Conversely, proof that 10:30 certificate creation was the first approval (no oral approval occurred) would make it NONCOMPLIANT. The present evidence proves neither: the certificate date undermines the displayed signature time but does not logically exclude a genuine oral approval at 08:45, and the witness's interest undermines but does not falsify the claim. Under a burden-of-proof reading of R5 ("effective only if evidence supports approval"), the exemption is not established and the case is NONCOMPLIANT; under a factual-existence reading it is INDETERMINATE. This assessment reports the latter and flags the former.

**TX-302 (other case, COMPLIANT).** The late 11:00 database insert does not defeat the exemption because the qualified signature at 09:05 and documented outage supply the provenance R5 requires; had the signature been post-release as in TX-310, the exemption would fail, but the case would still be COMPLIANT because the 09:20 Enhanced_Review independently satisfies R1. A taxonomy that labels any release protected by a valid exemption as JUSTIFIED_EXCEPTION would report this case under that label; the substantive conclusion (no breach, exemption valid, defence redundant) is identical. What would make it a breach: proof the Enhanced_Review did not cover the 180,000 state *and* invalidation of the signature evidence.

**TX-311 (other case, COMPLIANT).** The result turns on R1's release snapshot plus R7 ordering. Because event_index 4 (DE) follows event_index 3 (Enhanced_Review) at the same timestamp, the review was performed while the jurisdiction was still US and the amount was 115,000; it therefore satisfies the amount aspect. At release the jurisdiction is DE, so R1 is not triggered. Alternative reading: if the obligation crystallised during the 16:10–16:20 window when US + 115,000 held, and required an Enhanced_Review after the *latest* trigger-relevant change, the review preceding the DE change would fail and the case would be NONCOMPLIANT (or, if event_index were unreliable, INDETERMINATE). Evidence that would change the result: a rule version showing crystallisation at creation, or proof event_index does not reflect source-system order.

**TX-307 (additional other case, NONCOMPLIANT).** If Compliance_Approve were read as substantive approval regardless of packet type, the case would still fail because the Enhanced_Review itself is absent; only if Standard_Review were (contrary to the stated semantic fact) treated as equivalent to Enhanced_Review would it become COMPLIANT.

```python
            r1_status = "UNKNOWN"

                                         or enh > last_material_amt_change)

        # R2 (3-valued).
        if risk == "HIGH" or cust == "PEP":
            r2_status = "TRIGGERED"
        elif pd.notna(risk) and pd.notna(cust):
            r2_status = "NOT_TRIGGERED"
        else:
            r2_status = "UNKNOWN"
        r2_ok = enh is not None and comp is not None and enh < comp < ts

        # R3.
        r3_trigger = (list_upd is not None and pd.notna(jur)
                      and last_list_jur == jur
                      and (screen is None or list_upd > screen))
        r3_ok = screen is not None and list_upd is not None and screen > list_upd

        # Exemption join with scope + evidence-quality evaluation (R5, coarse).
        ex_status, ex_valid = "none", False
        if pd.notna(case_exemption) and case_exemption in exemptions.index:
            ex = exemptions.loc[case_exemption]
            scope_ok = (jur == ex["scope_jurisdiction"]
                        and cust == ex["scope_customer_type"]
                        and pd.notna(amt) and amt <= ex["scope_max_amount"])
            time_ok = ex["effective_from"] <= ts <= ex["expires"]
            if scope_ok and time_ok and ex["evidence_support"] == "strong":
                ex_status, ex_valid = "VALID_ON_STRONG_EVIDENCE", True
            else:
                ex_status = "REVIEW_REQUIRED_EVIDENCE_CONFLICT"

        r1_flag = r1_status == "TRIGGERED" and not enh_valid and not ex_valid
        r2_flag = r2_status == "TRIGGERED" and not r2_ok
        r3_flag = bool(r3_trigger and not r3_ok)
        unknown = "UNKNOWN" in (r1_status, r2_status) or pd.isna(jur)

        if r1_flag or r2_flag or r3_flag:
            verdict = "REVIEW_REQUIRED_COARSE_FLAG"
        elif unknown or ex_status.startswith("REVIEW"):
            verdict = "REVIEW_REQUIRED_UNKNOWN_OR_EVIDENCE"
        else:
            verdict = "NO_COARSE_FLAG"

        diagnostics.append({
            "case": case_id, "release_time": ts,
            "amount_at_release": amt, "risk_at_release": risk,
            "jurisdiction_at_release": jur, "customer_at_release": cust,
            "amount_unknown": pd.isna(amt), "risk_unknown": pd.isna(risk),
            "jurisdiction_unknown": pd.isna(jur), "customer_unknown": pd.isna(cust),
            "last_standard_review": last_time.get("Standard_Review"),
            "last_enhanced_review": enh, "last_compliance_approve": comp,
            "last_sanctions_screen": screen, "last_list_update": list_upd,
            "last_material_amount_change": last_material_amt_change,
            "last_trigger_change": last_trigger_change,
            "r1_status": r1_status, "r1_coarse_flag": r1_flag,
            "r2_status": r2_status, "r2_coarse_flag": r2_flag,
            "r3_coarse_flag": r3_flag,
            "exemption_id": case_exemption,
            "exemption_record_time": record_time,
            "exemption_coarse_status": ex_status, "coarse_verdict": verdict})

diagnostics_df = pd.DataFrame(diagnostics)

# --- 8. Coarse activity-only precedence (DECLARE-like Response check) ---
# Compares activity ORDER only. It will report Enhanced before Release for
# TX-309 even though R4 invalidates that review, and cannot see amounts,
# exemptions, UNKNOWNs, or why a screen is stale.
def precedence_ok(trace, first, second):
    return first in trace and second in trace and trace.index(first) < trace.index(second)

trace_check = pd.DataFrame([
    {"case": cid,
     "trace_enhanced_before_release": precedence_ok(
         list(g["concept:name"]), "Enhanced_Review", "Release_Funds")}
    for cid, g in df.groupby("case:concept:name", sort=False)])

diagnostics_df = diagnostics_df.merge(trace_check, on="case")
print(diagnostics_df.to_string(index=False))
```

Note on one deliberate correction risk in reproducing the log: the TX-309 Enhanced_Review timestamp above is transcribed as 2026-04-06T15:25:00Z; any transcription must preserve `(timestamp, event_index)` order, since the diagnostics depend on it.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** Conformance over a case's attribute table typically uses the last observed value. That would read TX-303's creation LOW as if it governed release, TX-311's final DE as if it governed the review, and TX-305's settlement 150,000 as the release amount. Each reverses the correct finding.
2. **Post-hoc exemptions and record time.** Activity traces see `Record_Exemption` at 11:00 for both TX-302 and TX-310 and would treat them identically. Only evidence time (signature 09:05 vs certificate 10:30) and provenance (documented outage vs interested witness) separate a valid exemption from a disputed one.
3. **Material changes after review.** A precedence check ("Enhanced before Release") passes TX-309 and TX-301, yet a >20% increase after the review invalidates it under R4. Control flow has no notion of invalidation by intervening data change, nor of direction (decrease in TX-308 is harmless).
4. **Conditional activation.** Whether any review is required at all depends on data: DE vs non-DE, the 100,000 threshold, HIGH/PEP status. The same activity sequence is compliant in one data context and a breach in another; language-based conformance over activities alone cannot express "required *if* amount  100,000".
5. **Missing data.** A trace either contains an activity or it does not. It cannot distinguish "amount known to be 90,000" from "amount never known" (TX-305), and silently defaults the latter to a benign reading, defeating R6.
6. **Same-timestamp ordering.** Timestamp-only traces treat TX-311's review and jurisdiction change as simultaneous and unordered. The consequence (review under US, release under DE) is visible only through `event_index`.
7. **Review content and linkage.** Activity names hide what was reviewed. TX-307's Compliance_Approve approved a *standard* packet; a trace sees "Compliance_Approve present" and passes R2's surface form while the substantive linkage to an Enhanced_Review is absent.
8. **External and latest-event semantics.** R3 depends on a sanctions-list change external to the case and on the *latest* screen, not on any screen existing. R2 depends on chains (Enhanced  Compliance  release) with the *relevant* pair. Simple precedence templates over the whole trace cannot express "latest" or "relevant" without data-aware temporal logic.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload.** At `Release_Funds`, write a signed, immutable snapshot: amount, risk, jurisdiction, customer type, rule version, evaluation outcome, and hashes of the reviews relied on. Settlement data reconciles against it; it never overwrites it. This alone resolves TX-305-type indeterminacy.
- **Bitemporal timestamps with stable ordering.** Every event carries `event_time`, `recorded_time`, and a per-case monotonic `sequence_no` assigned by the source system, so equal timestamps have a trustworthy, non-reassignable order. Never reuse wall-clock seconds as the only ordering key.
- **Effective-time discipline.** Attribute updates are explicit events with `old_value`, `new_value`, `effective_from`, source system, reason code, and actor (change provenance). Exemptions carry `effective_from`, `expires`, approver identity, qualified signature timestamp, and certificate validity window as separate fields; displayed dates are never the sole evidence.
- **Review payload binding.** A review event stores a hash/snapshot of the exact state it reviewed and the rule version applied. Compliance_Approve must reference a specific Enhanced_Review ID and packet hash, so "approved a standard packet" is structurally impossible to confuse with R2 approval.
- **Structured exemption scope.** Machine-readable scope (jurisdictions, customer types, max amount, rules waived) joined at release time, with automated checks for approver role, window, and scope match, escalating to a human only when evidence quality (signature vs witness) is genuinely contestable.
- **Sanctions list versioning.** Each Sanctions_Screen records the list version ID; each list update emits an event with scope and version. R3 then becomes a join on version, not a judgement call.
- **Explicit unknown handling.** Replace ambiguous blanks with reason-coded missingness (`amount_unknown_reason=FEED_UNAVAILABLE`) and fail closed: a release cannot proceed while a decisive trigger attribute is UNKNOWN, forcing resolution before release rather than INDETERMINATE after it.
- **System-computed materiality.** Emit the R4 materiality determination (review amount, new amount, percentage, invalidated review ID) as part of the update event, so downstream checks consume an auditable computation instead of re-deriving arithmetic from prose notes.
- **Rule and policy versioning.** Every evaluation records the policy version in force at release, making crystallisation-time vs release-time trigger questions (TX-311) answerable from the log.
