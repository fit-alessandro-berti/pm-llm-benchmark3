## 2. Process-model consistency checks
A concrete validation suite must ensure every feature and explanation is consistent with the process semantics at prediction time t0 (immediately after the first Coverage Check Completed). The suite comprises:

- **Prefixtime availability check** – For each feature, verify that its value is computed from data whose timestamps are  t0. This directly catches features such as `total_case_duration_hours`, `appeal_seen_anywhere`, and `full_trace_variant_id`.
- **Activityorder feasibility check** – Using a normative process model (e.g., a Petri net or declarative DECLARE constraints) determine whether a given pair of events can occur in that order. The pattern *Claim Closed  Damage Assessment Completed* is impossible under the normative flow; the check must flag it. The model must encode that *Claim Closed* can only occur after a final *Settlement Decision Recorded* (or withdrawal) and after *Damage Assessment Completed*.
- **Sametimestamp ambiguity resolution** – For events with identical timestamps, query the source system’s reliable sequence index. If absent, treat any order as undefined and do not use the specific ordering in features. This prevents artefact patterns like the *Claim Closed  Damage Assessment* pattern.
- **Completetrace signal detection** – Scan feature calculation code to identify aggregation over the entire case trace. Tracebased statistics, variant IDs, and “anywhere” flags are immediate red flags.
- **Enabled/futurepossible/impossible activity check at t0** – Given the known prefix (Case Registered, Coverage Check Completed), compute the set of immediately enabled activities (Damage Assessment, Documents Requested, Fraud Investigation if conditions met). An explanation that refers to an *Appeal* or *Settlement Decision Recorded* as a realised event is a futureinformation violation. However, an explanation may legitimately note that an *Appeal* is *futurepossible* (e.g., after a partial/deny decision), but it must not treat its occurrence as known.
- **Repeated Settlement Decision semantics** – The process allows a second *Settlement Decision Recorded* after an appeal. Any feature that counts these events must distinguish between the first and second occurrence, and should not leak the second occurrence at t0. A prefixaware feature can only count the instances that have already occurred.

**Role and limitations of common analysis techniques:**
- **Alignmentbased conformance** (e.g., optimal alignments) can measure how well a full trace fits the model, but at t0 we have only a prefix; therefore prefixalignment (or incremental alignment) is needed. A low conformance score on the full trace is not available at t0.
- **Footprint/DFG** – A frequent directlyfollows edge in a log does not make it a normative rule. For example, `Claim Closed  Payment` may appear frequently, but is still invalid. DFGs can surface suspicious edges, but must be checked against the process specification.
- **Declarative constraints** (e.g., “damage assessment must precede settlement decision”) can be used as checkers: a pattern that violates a hard constraint is a dataquality or ordering problem, not a legitimate predictor.
- **Prefixvariant analysis** – Instead of fulltrace variant IDs, prefix variants up to t0 should be used. These can be checked for conformance with the model’s state space.

This suite must be executed on every feature and on all local explanations before a prediction is released.

## 5. Recommendations for explanation validation

**Priority 1 – Feature-store design and historical timestamps**  
Build an offline feature store where every feature value is stored with its validasof timestamp. Mutable scores (risk_score, queue snapshots, document counts) must be versioned so that the model always queries the exact value at t0. Without this, model inputs are silently contaminated.

**Priority 2 – Prefixonly recomputation and lineage audit**  
Rewrite all featureengineering pipelines to produce “prefixtime” features. For example, `num_document_requests` becomes `num_doc_requests_issued_before_t0`. Audit every SQL transformation for the use of extraction date vs. event time. Fix the `prior_claim_count` filter. Remove all features that aggregate over the complete trace.

**Priority 3 – Processconformance tests as a gate**  
Implement processmodel checks (described in Section2) as an automated CI/CD gate. Any feature that relies on an impossible event ordering or that uses an event not yet enabled at the prediction prefix must be blocked. The test suite must run on every model release and on every explanation artefact.

**Priority 4 – Calibration and performance after feature removal**  
After dropping leaked features, recalibrate the model. Measure both discrimination and calibration on a temporallysplit test set that respects the predictiontime constraint. A model that relied heavily on future information may appear to lose accuracy; document the “true” online performance.

**Priority 5 – Explanation stability and counterfactual sanity checks**  
Evaluate SHAP (or other explanation) stability under small perturbations of admissible features. Verify that local explanations do not contradict process logic (e.g., that a lower queue length never *increases* risk beyond a plausible bandwidth). Implement counterfactual probes: “What would the prediction be if the queue length were one standard deviation lower?”

**Priority 6 – Proxy and fairness analysis**  
For region, channel, and initial reserve features, perform a bias audit: compute subgroup falsepositive and falsenegative rates, test for disparate impact, and consult domain experts on whether the features encode legally protected characteristics. If a feature is a strong proxy for a protected attribute, consider excluding it or using constrained optimisation during training.

**Priority 7 – Monitoring for schema and process drift**  
Deploy runtime monitors that compare live feature distributions against training distributions. Add a specific detector for new calendarweek effects (policy changes, unmodelled holidays) and for unexpected activityorder artefacts (which may indicate a sourcesystem change). Alert when sametimestamp events without sequence index become frequent, as they invalidate the ordering assumptions.
