# 1. Assumptions and Interpretation

1. **Low-risk/high-risk representation.**  
   The risk decision is represented as a control-flow **XOR** after `Analyze Root Cause`:
   - low-risk branch: `Supervisor Review`;
   - high-risk branch: `Quality Review` and `Regulatory Review` in a parallel/unordered block.  
   No explicit data attribute such as `risk_level` is modeled.

2. **Optional supplier consultation representation.**  
   `Consult Supplier` is represented as an optional singleton submodel: `XOR(tau, Consult Supplier)`, where `tau` is a silent skip. If the supplier branch is chosen, `Consult Supplier` occurs exactly once; if not, it is silently skipped.

3. **Passing inspection abstraction.**  
   Because inspection pass/fail is not an event label, the trial repeat behavior is abstracted by a loop:
   - body: `Execute Trial -> Inspect Trial`;
   - redo: `Adjust Parameters`.  
   A trace exits the loop after an `Inspect Trial` without a following `Adjust Parameters`; that final inspection is interpreted as the passing inspection.

4. **Duplicate visible labels.**  
   Duplicate visible labels as distinct model nodes are **not permitted/used** in the constructed models. Each visible activity has one visible transition/leaf, except that `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` may repeat behaviorally through the loop.

5. **Process-tree approximation policy.**  
   The process tree uses a **conservative under-approximation**. It preserves safety-critical synchronization—trial after `Plan Verification` and `Design Corrective Action`, release after trial/approvals/supplier—but excludes some intended early overlaps, especially approvals or supplier consultation overlapping `Plan Verification`/`Design Corrective Action`.

6. **Interpretation of “may overlap.”**  
   “May overlap” is interpreted as **absence of a required order constraint**. In PM4Py execution, this may still be realized as interleaving; the models do not require true simultaneous execution.

7. **Completion-time traces.**  
   Activities are treated as recorded at completion. Visible traces are projections that omit silent `tau` steps.

8. **Loop semantics assumption.**  
   I assume PM4Py `LOOP(body, redo)` has the usual process-tree semantics `body (redo body)*`, i.e. the body occurs at least once and the redo part occurs only between repeated bodies.

**Python construction**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def pt_node(operator=None, label=None, children=None):
    """
    Create a ProcessTree node and explicitly maintain parent/child links.
    """
    node = ProcessTree(operator=operator, label=label)
    node.children = []
    node.parent = None

    if children is not None:
        for child in children:
            node.children.append(child)
            child.parent = node

    return node


# Visible activities
R = pt_node(label="Register Deviation")
C = pt_node(label="Contain Material")
A = pt_node(label="Analyze Root Cause")
P = pt_node(label="Plan Verification")
D = pt_node(label="Design Corrective Action")
S = pt_node(label="Supervisor Review")
Q = pt_node(label="Quality Review")
G = pt_node(label="Regulatory Review")
U = pt_node(label="Consult Supplier")
E = pt_node(label="Execute Trial")
I = pt_node(label="Inspect Trial")
J = pt_node(label="Adjust Parameters")
M = pt_node(label="Release Material")
X = pt_node(label="Archive Case")

# Silent skip for optional supplier consultation
tau_supplier = pt_node(label=None)

# Trial loop: (Execute Trial -> Inspect Trial) (Adjust Parameters (Execute Trial -> Inspect Trial))*
trial_body = pt_node(operator=Operator.SEQUENCE, children=[E, I])
trial_loop = pt_node(operator=Operator.LOOP, children=[trial_body, J])

# Risk route: low-risk Supervisor Review XOR high-risk parallel Quality/Regulatory
high_risk = pt_node(operator=Operator.PARALLEL, children=[Q, G])
risk_route = pt_node(operator=Operator.XOR, children=[S, high_risk])

# Optional supplier consultation: silent skip XOR Consult Supplier
supplier_option = pt_node(operator=Operator.XOR, children=[tau_supplier, U])

# Pre-work parallel block:
# Contain Material -> Plan Verification
# Analyze Root Cause -> Design Corrective Action
pre_work = pt_node(
    operator=Operator.PARALLEL,
    children=[
        pt_node(operator=Operator.SEQUENCE, children=[C, P]),
        pt_node(operator=Operator.SEQUENCE, children=[A, D]),
    ],
)

# Post-work parallel block:
# trial loop, selected approval route, optional supplier consultation
post_work = pt_node(
    operator=Operator.PARALLEL,
    children=[trial_loop, risk_route, supplier_option],
)

# Full tree
tree = pt_node(
    operator=Operator.SEQUENCE,
    children=[R, pre_work, post_work, M, X],
)
```

**Approximation and representational loss**

The process tree cannot represent the intended non-block-structured dependency pattern exactly without duplication or unsafe relaxation. The main approximations are:

- **Requirement 2 is partially exact but then over-synchronized.** `Contain Material` and `Analyze Root Cause` are concurrent, but the parallel block joins both derived branches—`C -> P` and `A -> D`—before the approval route and supplier consultation can start.
- **Requirement 5 is delayed.** The risk route should be enabled after `Analyze Root Cause`. In this tree, it is enabled only after the whole pre-work parallel block completes, i.e. after both `Plan Verification` and `Design Corrective Action` are complete.
- **Requirement 6 is partially lost.** `Consult Supplier` is optional, singleton, and completed before release, but the tree prevents it from overlapping `Design Corrective Action` or `Plan Verification`. It can overlap only the trial and approval work in the post-work parallel block.
- **Requirement 7 is partially preserved.** The tree correctly requires `Plan Verification` and `Design Corrective Action` before trial and allows approvals to overlap the trial cycle. However, it cannot allow approvals to overlap the earlier design/planning work.
- **Requirement 8 is represented only structurally.** The loop encodes repeated `Execute Trial`/`Inspect Trial` cycles with `Adjust Parameters` between cycles, but it does not encode an explicit inspection-failure event.
- **Requirement 11 is represented by nondeterministic control-flow alternatives.** Low/high risk and supplier involvement are not data-conditioned; they are structural XOR choices.
- **No duplicate visible labels are used.** This avoids artificial multiple occurrences of the same activity, but it also means some unstructured overlaps cannot be represented exactly.

```text
  A  < SupplierOption
  P  < TrialLoop
  D  < TrialLoop
  TrialLoop      < M
  RiskRoute      < M
  SupplierOption < M
  M  < X

Submodels:
  RiskRoute = XOR(
    S,
    StrictPartialOrder(Q, G)   // Q and G unordered
  )

  SupplierOption = XOR(
    tau,
    U
  )

  TrialLoop = LOOP(
    StrictPartialOrder(E < I),
    J
  )
```

**Python construction**

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Visible transitions
R = Transition(label="Register Deviation")
C = Transition(label="Contain Material")
A = Transition(label="Analyze Root Cause")
P = Transition(label="Plan Verification")
D = Transition(label="Design Corrective Action")
S = Transition(label="Supervisor Review")
Q = Transition(label="Quality Review")
G = Transition(label="Regulatory Review")
U = Transition(label="Consult Supplier")
E = Transition(label="Execute Trial")
I = Transition(label="Inspect Trial")
J = Transition(label="Adjust Parameters")
M = Transition(label="Release Material")
X = Transition(label="Archive Case")

# Trial cycle partial order: Execute Trial < Inspect Trial
trial_cycle = StrictPartialOrder(nodes=[E, I])
trial_cycle.order.add_edge(E, I)

# Trial loop: repeat trial cycle with Adjust Parameters between cycles
trial_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[trial_cycle, J],
)

# High-risk route: Quality Review and Regulatory Review unordered
high_risk = StrictPartialOrder(nodes=[Q, G])
# Intentionally no order edge between Q and G.

# Risk route: low-risk XOR high-risk
risk_route = OperatorPOWL(
    operator=Operator.XOR,
    children=[S, high_risk],
)

# Optional supplier consultation: silent skip XOR Consult Supplier
tau_supplier = SilentTransition()
supplier_option = OperatorPOWL(
    operator=Operator.XOR,
    children=[tau_supplier, U],
)

# Top-level POWL model
powl = StrictPartialOrder(
    nodes=[
        R,
        C,
        A,
        P,
        D,
        risk_route,
        supplier_option,
        trial_loop,
        M,
        X,
    ]
)

# Start and initial work-stream dependencies
powl.order.add_edge(R, C)
powl.order.add_edge(R, A)

# Split dependencies into planning and design
powl.order.add_edge(C, P)
powl.order.add_edge(A, D)

# Risk route and optional supplier become available after root cause analysis
powl.order.add_edge(A, risk_route)
powl.order.add_edge(A, supplier_option)

# Trial may start only after both planning and design are complete
powl.order.add_edge(P, trial_loop)
powl.order.add_edge(D, trial_loop)

# Release synchronization
powl.order.add_edge(trial_loop, M)
powl.order.add_edge(risk_route, M)
powl.order.add_edge(supplier_option, M)

# Archive after release
powl.order.add_edge(M, X)
```

**Why intentionally unconnected nodes may remain concurrent**

The top-level order contains only the edges listed above. Any pair of top-level nodes without a direct or transitive order path is intentionally concurrent, unless an operator imposes choice or internal structure.

Examples:

- `C` and `A` are unconnected after `R`; they may overlap.
- `P` and `D` are unconnected; planning and design may overlap.
- `risk_route` and `trial_loop` are unconnected; approvals may overlap the trial cycle.
- `supplier_option` and `trial_loop` are unconnected; supplier consultation may overlap trial work.
- `supplier_option`, `D`, and `P` are unconnected except for common precedence from `A`/`C` and common synchronization at `M`; supplier consultation may overlap design and planning.
- Inside `high_risk`, `Q` and `G` are unconnected; they may complete in either order.
- Inside `risk_route`, the XOR means `S` and the high-risk branch are alternatives, not concurrent.
- Inside `trial_loop`, the loop operator controls repetition; `J` occurs only between trial cycles, not after the final `I`.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | After `R`, `C` and `A` may proceed independently and overlap. | `R` followed by parallel branches containing `C -> P` and `A -> D`. | `R < C`, `R < A`, no `C`/`A` order. | Neither model overconstraints the initial concurrency itself. | Containment and root-cause analysis can be performed in parallel, reducing cycle time. |
| Split dependencies into planning/design | `P` after `C`; `D` after `A`. | Encoded inside the pre-work parallel block. | Edges `C < P` and `A < D`. | POWL exact; process tree adds an extra join before approvals/supplier. | The tree may delay approvals or supplier consultation until design/planning are both finished. |
| Risk route | Selected after `A`; low-risk `S`; high-risk `Q` and `G` concurrent/unordered. | XOR of `S` and parallel `Q,G`, but placed after pre-work block. | XOR after `A`; high-risk branch unordered. | Process tree overconstrains start time of risk route; POWL exact under the assumed operator semantics. | Process tree may serialize risk reviews later than necessary. |
| Overlap of approval and trial | Approval route need not complete before trial; may overlap trial cycle. | Post-work parallel allows approval/trial overlap, but only after pre-work completes. | No order between `risk_route` and `trial_loop`; both synchronize only at `M`. | Process tree partially overconstrained; POWL exact. | POWL permits approvals to run alongside trial as soon as root cause is complete; tree may reduce scheduling flexibility. |
| Optional supplier consultation | Optional, at most once, after `A`, may overlap design/planning/approvals/trial, complete before `M`. | `XOR(tau, U)` in post-work parallel; overlaps trial/approvals but not design/planning. | `XOR(tau, U)` after `A`, before `M`, unordered with design/planning/trial/approvals. | Process tree overconstrains supplier start/overlap; POWL exact. | Tree may force supplier consultation later than business rules allow. |
| Repeat-until behavior | `E,I` cycles; if fail then `J` and repeat; no `J` after passing inspection. | `LOOP(E -> I, J)` abstracts pass by loop exit. | `LOOP(E < I, J)` abstracts pass by loop exit. | Both under-represent inspection outcome; neither encodes explicit fail/pass event. | Event logs cannot distinguish why a loop repeated unless additional data is captured. |
| Release synchronization | `M` requires passing trial, selected approvals, and supplier if selected. | Sequence after post-work parallel; all represented obligations complete before `M`. | Edges from `trial_loop`, `risk_route`, and `supplier_option` to `M`. | Exact for represented obligations. | Prevents premature release of deviated material. |
| Duplicate-label risk | Activities should not be artificially duplicated except loop repetitions. | One visible leaf per activity; no duplicate visible labels. | One visible transition per activity; no duplicate visible labels. | Avoiding duplication preserves label cleanliness but contributes to process-tree under-approximation. | Conformance checking and analytics see clean activity names without artificial repeated analysis/design events. |

# 7. Preferred Representation and Validation Plan

**Preferred representation**

The **POWL model** is the preferred canonical representation. It directly expresses the non-block-structured dependencies:

- `P` and `D` synchronize before trial;
- approvals and supplier consultation are not forced to wait for `P`/`D`;
- release synchronizes trial, approvals, and optional supplier;
- no duplicate visible labels are required.

The process tree is useful for tools that require structured trees, but its conservative under-approximation intentionally excludes valid behavior, such as early supervisor review or early supplier consultation.

**Validation plan**

1. **Conversion to accepting Petri nets where supported.**

   ```python
   import pm4py

   net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)

   try:
       net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)
   except Exception as exc:
       net_powl = im_powl = fm_powl = None
       print("POWL-to-Petri-net conversion not supported or failed:", exc)
   ```

2. **Soundness checking of converted nets.**

   ```python
   pm4py.check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)

   if net_powl is not None:
       pm4py.check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)
   ```

   Expected result: proper completion is possible, no deadlocks block mandatory completion, and no improper tokens remain at final marking.

3. **Bounded or sampled playout.**

   Use PM4Py’s playout utility, for example:

   ```python
   # The exact keyword arguments may vary by PM4Py version.
   sampled_tree_traces = pm4py.play_out(net_tree, im_tree, fm_tree)
   if net_powl is not None:
       sampled_powl_traces = pm4py.play_out(net_powl, im_powl, fm_powl)
   ```

   Then project away silent transitions and check invariants:
   - first visible event is `Register Deviation`;
   - last visible event is `Archive Case`;
   - `Contain Material` precedes `Plan Verification`;
   - `Analyze Root Cause` precedes `Design Corrective Action`;
   - first `Execute Trial` occurs after `Plan Verification` and `Design Corrective Action`;
   - `Release Material` occurs after the selected approval route and after `Consult Supplier` if present;
   - `Adjust Parameters` occurs only between `Inspect Trial` and a later `Execute Trial`.

4. **Explicit positive and negative trace tests.**

   Use the eight witnesses from Section 5.

   Positive expectations:
   - A1 accepted by both models;
   - A2 accepted by both models;
   - A3 accepted by POWL but rejected by the process tree, confirming the documented approximation;
   - A4 accepted by both models;
   - A5 accepted by both models.

   Negative expectations:
   - F1 rejected by both models because of invalid start;
   - F2 rejected by both models because trial starts before `Plan Verification`;
   - F3 rejected by both models because release occurs before supplier completion.

5. **Silent-behavior and duplicate-label check.**

   ```python
   from collections import Counter

   single_occurrence_activities = {
       "Register Deviation",
       "Contain Material",
       "Analyze Root Cause",
       "Plan Verification",
       "Design Corrective Action",
       "Supervisor Review",
       "Quality Review",
       "Regulatory Review",
       "Consult Supplier",
       "Release Material",
       "Archive Case",
   }

   def visible(trace):
       return [e for e in trace if e is not None]

   for trace in sampled_tree_traces:
       vtrace = visible(trace)
       counts = Counter(vtrace)

       assert vtrace[0] == "Register Deviation"
       assert vtrace[-1] == "Archive Case"
       assert counts["Consult Supplier"] <= 1

       for act in single_occurrence_activities:
           assert counts[act] <= 1
   ```

   For the POWL model, perform the same projection and counting if playout is supported. The silent transition should correspond only to skipping `Consult Supplier`, or to silent control-flow machinery introduced by conversion.

6. **Limitations of the validation plan.**

   - Sampled playout is not a proof of full language equivalence.
   - Soundness checks structural net properties but does not prove that the net language exactly matches the intended narrative.
   - PM4Py’s POWL-to-Petri-net conversion may be incomplete or version-dependent.
   - Silent transitions can hide optional behavior, making conformance checking more permissive unless silent moves are explicitly audited.
   - Because risk, supplier selection, and inspection outcome are not data-conditioned, validation can check control-flow consistency but cannot verify that the correct branch would be chosen for a real case.

# 8. Final Self-Critique

1. **Semantic uncertainty about composite POWL operators.**  
   The POWL model assumes that ordering edges to composite operator nodes such as `trial_loop`, `risk_route`, and `supplier_option` interact correctly with their internal events and that external concurrent nodes may interleave with internal events. If a PM4Py version treats such composite nodes more atomically, the POWL model may overconstrain overlap inside the trial cycle or approval route.

2. **Process-tree under-approximation may cause false rejections.**  
   The process tree intentionally excludes valid behavior where approvals or supplier consultation begin before `Plan Verification` and `Design Corrective Action` are both complete. If used for conformance checking, it would incorrectly reject traces such as A3.

3. **Control-flow alternatives do not enforce business data conditions.**  
   The models represent low/high risk, supplier involvement, and inspection failure purely as structural choices or loop repetitions. Therefore, they cannot guarantee that a high-risk route is chosen only for high-risk cases or that `Adjust Parameters` occurs only after an actual failed inspection. This is a semantic limitation, not merely a syntactic one.
