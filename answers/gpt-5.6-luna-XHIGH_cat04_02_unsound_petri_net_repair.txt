# 1. Executive Verdict

The net is structurally a workflow net: it has one source, one sink, and every node lies on a directed source-to-sink path. It should not be expected to be sound. The principal defect is that `t_join_waived` consumes only the waiver token and does not synchronize with the mandatory analysis branch. Consequently, authorization can occur before `t_analyze`, or after analysis while leaving `p_analysis_done` stranded. A sink token may therefore be produced without reaching the exact final marking, and the case may be authorized without completed analysis. The defect is behavioral, not a cosmetic or syntactic issue.

# 2. Structural Diagnosis

| Element or subnet | Intended role | Actual structural effect | Potential symptom |
|---|---|---|---|
| `source`, `t_register`, `p_ready` | Register the case and make it ready for the work | A single token moves from `source` to `p_ready` | No defect by itself |
| `t_split` | Start analysis and review in parallel | One input token produces one token in each of `p_analysis` and `p_review` | Both branches must be accounted for later |
| `p_analysis`, `t_analyze`, `p_analysis_done` | Mandatory analysis | `t_analyze` consumes the analysis token and produces `p_analysis_done` | The analysis token can be ignored by the waiver join |
| `p_review`, `t_standard_review`, `p_review_done` | Standard review alternative | `t_standard_review` consumes the sole review token and produces `p_review_done` | Correctly feeds the two-input normal join |
| `p_review`, `t_waive_review`, `p_waived` | Formally record a waiver as the review outcome | `t_waive_review` consumes the same review token and produces `p_waived` | Waiver is mutually exclusive with standard review, but its completion token is handled incorrectly |
| `join_normal` | Synchronize completed analysis and standard review | Requires both `p_analysis_done` and `p_review_done`, then produces `p_decision` | Normal path has the intended AND synchronization |
| `join_waived` | Synchronize completed analysis and waiver | Requires only `p_waived`, then produces `p_decision` | It is an OR-like bypass of mandatory analysis |
| `t_authorize`, `sink` | Authorize and finish the case | Consumes `p_decision` and deposits a token in `sink` | It can fire while a branch token remains elsewhere |
| `im` and `fm` | Start with one source token and finish with exactly one sink token | `im = {source: 1}` and `fm = {sink: 1}` are the selected markings | A token in `sink` alone does not mean `fm` has been reached if other tokens remain |
| Whole graph | Be a workflow net | `source` is the unique input place, `sink` the unique output place, and all places/transitions, including the waiver subnet, have a directed path from source to sink | Structural workflow-net status can be true even though behavioral soundness fails |

# 3. Marking-Based Counterexample

Write a marking as a set of its nonzero place counts. From `im`, the following is a legal waiver-first sequence:

`t_register, t_split, t_waive_review, t_join_waived, t_authorize, t_analyze`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — (`im`) | `{source: 1}` | `t_register` | Initial marking |
| 1 | `t_register` | `{p_ready: 1}` | `t_split` | Registration is complete |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | The split creates one token in each parallel branch |
| 3 | `t_waive_review` | `{p_analysis: 1, p_waived: 1}` | `t_analyze` | The review token is committed to the waiver alternative; analysis is still pending |
| 4 | `t_join_waived` | `{p_analysis: 1, p_decision: 1}` | `t_analyze`, `t_authorize` | The waiver join is enabled without `p_analysis_done` |
| 5 | `t_authorize` | `{p_analysis: 1, sink: 1}` | `t_analyze` | Authorization occurs before `t_analyze`; a sink token exists, but the marking is not `fm` |
| 6 | `t_analyze` | `{p_analysis_done: 1, sink: 1}` | none | Analysis can occur after authorization, but the exact final marking still has not been reached |

At step 4, `t_join_waived` ignores the token in `p_analysis`. After step 6, `p_analysis_done` cannot be consumed: `join_normal` also requires `p_review_done`, which the waiver route never creates, while `join_waived` requires `p_waived`, which was already consumed. Thus the extra token cannot be cleaned up.

The opposite ordering is also legal and demonstrates that merely performing analysis does not repair the problem:

`t_register, t_split, t_analyze, t_waive_review, t_join_waived, t_authorize`

| Step | Fired transition | Resulting nonzero marking | Enabled transitions | Observation |
|---:|---|---|---|---|
| 0 | — (`im`) | `{source: 1}` | `t_register` | Initial marking |
| 1 | `t_register` | `{p_ready: 1}` | `t_split` | Registration is complete |
| 2 | `t_split` | `{p_analysis: 1, p_review: 1}` | `t_analyze`, `t_standard_review`, `t_waive_review` | Both branches exist |
| 3 | `t_analyze` | `{p_analysis_done: 1, p_review: 1}` | `t_standard_review`, `t_waive_review` | Analysis completes first |
| 4 | `t_waive_review` | `{p_analysis_done: 1, p_waived: 1}` | `t_join_waived` | Waiver is selected |
| 5 | `t_join_waived` | `{p_analysis_done: 1, p_decision: 1}` | `t_authorize` | The join consumes only the waiver token |
| 6 | `t_authorize` | `{p_analysis_done: 1, sink: 1}` | none | `t_authorize` occurs after `t_analyze`, but `fm = {sink: 1}` is still not reached |

The normal-review sequence can reach `fm`, but soundness requires every reachable choice to have a proper completion, not merely that one successful path exists.

# 4. Minimal-Repair Alternatives

Use this edit-cost model: one unit for each added or removed arc, place, or transition. Deleting a node does not silently delete its incident arcs. Labels and markings have zero cost when unchanged.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---:|---|---|---|
| Repair A: make the waiver join a true synchronization | Add the arc `p_analysis_done -> join_waived`; remove nothing | 1 | Analysis remains mandatory; standard review and waiver remain alternatives; the two branches still start in parallel; authorization follows both required outcomes | A waiver may be recorded before analysis finishes, but `join_waived` waits for analysis | Two silent join transitions make the model slightly more complex to explain or align if silent moves are hidden |
| Repair B: guard waiver recording with analysis completion | Add the arc `p_analysis_done -> t_waive_review`; remove nothing | 1 | Analysis is mandatory, the review choice remains exclusive, and both routes can finish at the sink | The waiver cannot be recorded while analysis is pending; the analysis token is consumed by `t_waive_review`, so this imposes an additional ordering policy | An operational process that needs to record a waiver early may be blocked or appear deadlocked until analysis completes |

Both repairs are behaviorally and structurally distinct. Repair A preserves the intended parallel timing and fixes the missing synchronization input. Repair B fixes the same token leak by making the waiver transition itself wait for, and consume, completed analysis. With zero edits the original counterexample remains, so every repair has cost at least one. Each proposed repair has cost one, hence both are globally minimal under this model and tie.

# 6. Diagnostic and Reachability Code

```python
import pm4py
from pm4py.objects.petri_net.obj import Marking


def pretty_marking(marking):
    return {
        place.name: count
        for place, count in marking.items()
        if count
    }


def fire_named(candidate_net, marking, transition_name):
    matches = [
        transition for transition in candidate_net.transitions
        if transition.name == transition_name
    ]
    if len(matches) != 1:
        raise ValueError(
            f"Expected exactly one transition named {transition_name!r}"
        )

    transition = matches[0]
    enabled = pm4py.get_enabled_transitions(candidate_net, marking)
    if transition not in enabled:
        enabled_names = sorted(item.name for item in enabled)
        raise RuntimeError(
            f"{transition_name!r} is not enabled; enabled={enabled_names}"
        )

    next_marking = Marking(marking)
    for arc in transition.in_arcs:
        remaining = next_marking.get(arc.source, 0) - arc.weight
        if remaining < 0:
            raise RuntimeError("Enabledness and input-arc consumption disagree")
        if remaining:
            next_marking[arc.source] = remaining
        else:
            next_marking.pop(arc.source, None)

    for arc in transition.out_arcs:
        next_marking[arc.target] = (
            next_marking.get(arc.target, 0) + arc.weight
        )

    print(f"fired {transition_name}: {pretty_marking(next_marking)}")
    return next_marking


def run_trace(label, candidate_net, initial_marking, transition_names):
    marking = Marking(initial_marking)
    print(f"{label}: start {pretty_marking(marking)}")
    for transition_name in transition_names:
        marking = fire_named(candidate_net, marking, transition_name)
    print(f"{label}: end {pretty_marking(marking)}")
    return marking


for label, candidate_net, candidate_im, candidate_fm in (
    ("original", net, im, fm),
    ("repaired", repaired_net, repaired_im, repaired_fm),
):
    print(f"--- {label} ---")
    print("workflow net:", pm4py.check_is_workflow_net(candidate_net))
    print(
        "soundness:",
        pm4py.check_soundness(
            candidate_net,
            candidate_im,
            candidate_fm,
            print_diagnostics=True,
        ),
    )
    print(
        "enabled at initial:",
        sorted(
            transition.name
            for transition in pm4py.get_enabled_transitions(
                candidate_net, candidate_im
            )
        ),
    )
    reachability_graph = pm4py.convert_to_reachability_graph(
        candidate_net, candidate_im, candidate_fm
    )
    print("reachability graph object:", type(reachability_graph).__name__)


run_trace(
    "original waiver-before-analysis",
    net,
    im,
    [
        "t_register",
        "t_split",
        "t_waive_review",
        "t_join_waived",
        "t_authorize",
        "t_analyze",
    ],
)

try:
    run_trace(
        "repaired attempted bypass",
        repaired_net,
        repaired_im,
        [
            "t_register",
            "t_split",
            "t_waive_review",
            "t_join_waived",
        ],
    )
except RuntimeError as error:
    print("expected repaired rejection:", error)

run_trace(
    "repaired waiver path",
    repaired_net,
    repaired_im,
    [
        "t_register",
        "t_split",
        "t_waive_review",
        "t_analyze",
        "t_join_waived",
        "t_authorize",
    ],
)
```

Qualitatively, the workflow-net check should succeed for both nets. The original soundness check should fail because the waiver-first and analysis-first waiver traces can terminate with tokens outside `fm`; its diagnostics should identify improper completion or the corresponding unsound behavior without relying on any particular diagnostic key. The repaired soundness check should succeed: `t_join_waived` is not enabled until both `p_waived` and `p_analysis_done` are present. The reachability graph for the repaired model should therefore have no analogous reachable proper-completion failure, and the helper should reject the attempted waiver bypass at `t_join_waived`.

# 7. Repair Trade-Offs and Residual Risks

With Repair A, standard review and waiver remain distinguishable through `t_standard_review` / “Perform Standard Review” versus `t_waive_review` / “Record Review Waiver”. They converge only after their distinct outcome places. The two silent joins can look like duplicate behavior to an alignment or conformance tool that hides silent transitions, but they are not simultaneously enabled: the single token in `p_review` can produce either `p_review_done` or `p_waived`, never both.

Soundness is necessary but not sufficient for the business rule. It does not prove that visible labels have the intended meaning, that waiver evidence is adequately recorded outside the net, or that data-dependent authorization rules are modeled. It also does not by itself prove correct event-log alignment.

Regression tests should include positive standard and waiver traces, with analysis before and after the waiver decision where the latter is permitted by the process. They should assert that each reaches exactly `{sink: 1}`. Negative tests should attempt authorization before analysis on the waiver route, fire `t_join_waived` before analysis, and attempt both review alternatives from one split token. The first two must be rejected; the third must be impossible after either review transition has consumed `p_review`.

To detect an accidental analysis bypass, replay every authorization prefix and require a prior `t_analyze` event, and structurally assert that every transition producing `p_decision` has `p_analysis_done` as an input. The reachability graph should also be searched for any marking enabling `t_authorize` that has no analysis provenance.

# 8. Final Recommendation

Deploy Repair A. It is a one-arc, globally minimal change that directly expresses the business rule: the waiver join must consume both the waiver outcome and completed analysis. It also preserves the useful parallelism in the original design, allowing the waiver to be recorded while analysis is still in progress while still preventing authorization until both are complete.

Use Repair B as the fallback when the operational policy explicitly requires analysis to finish before a waiver can be recorded. It is equally minimal and sound, but it imposes that additional ordering constraint and may block legitimate early waiver recording. In either deployment, run the standard and waiver positive traces plus the waiver-before-analysis negative test and verify exact final marking, not merely the presence of a token in `sink`.
