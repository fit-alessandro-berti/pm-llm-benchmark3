## 1. Temporal Data Semantics

State reconstruction proceeds case-by-case in ascending `(time:timestamp, event_index)` order. Blank cells in `amount`, `risk_level`, `jurisdiction`, `customer_type`, or `exemption_id` mean “no update at this event”; the prior value within the case is retained by forward-fill. Only explicit update events change state.

- **Event time**: the `time:timestamp` of the event row.
- **State at an event**: the cumulative result of applying all updates with `(timestamp, event_index)`  that event.
- **Equal timestamps**: `event_index` is the tie-breaker; event 3 is fully applied before event 4 when both share `16:20`.
- **Effective time (exemptions)**: `effective_from` in the exemption register.
- **Record time (exemptions)**: `Record_Exemption` timestamp (e.g., 11:00 for EX-77/EX-88).
- **Evidence time**: digital signature timestamp, witness statement time, or system audit timestamp.

Final case attributes are **not** copied backward. For example, in TX-311 the jurisdiction is `US` during `Enhanced_Review` (index 3 at 16:20) and becomes `DE` only at index 4 (same timestamp); at `Release_Funds` (16:30) it is `DE`, so R1 is evaluated with `jurisdiction = DE`.

Material amount change (R4) is defined as an increase of more than 20% relative to the value present at the latest `Standard_Review` or `Enhanced_Review`. A decrease does not invalidate a review. An increase from an unknown base amount is not safely classifiable.

Missing `amount`, `risk_level`, `jurisdiction`, or `customer_type` is never defaulted to a low-risk value. If a decisive trigger cannot be established or excluded, the result is `INDETERMINATE` unless other evidence resolves it.

| R1 | `Release_Funds`: `jurisdiction  DE` AND `amount  100000` (known) | `Enhanced_Review` completed | `last_material_change` < `Enhanced_Review` < `Release_Funds` | Values at `Release_Funds` | Matching valid exemption (R5) waives R1 only | If `amount` or `jurisdiction` unknown: `INDETERMINATE` | Event log for review; exemption register + approval/signature evidence |
| R2 | `Release_Funds`: `risk_level = HIGH` OR `customer_type = PEP` (known) | Both `Enhanced_Review` and `Compliance_Approve` | `Enhanced_Review` < `Compliance_Approve` < `Release_Funds` | Values at `Release_Funds` | None defined in register | If `risk` or `customer_type` unknown: `INDETERMINATE` | Event log for both events; approval packet scope |
| R3 | `Release_Funds` with `jurisdiction = J` added to sanctions list after latest `Sanctions_Screen` but before release | New `Sanctions_Screen` | `Sanctions_List_Update` < `Sanctions_Screen` < `Release_Funds` | `jurisdiction` at update and at release | None | If jurisdiction unknown at update/release: `INDETERMINATE` | List-update event; screen event timestamps |
| R4 | Any `Update_Amount` after latest review (`Standard_Review` or `Enhanced_Review`) | N/A (invalidates prior review for amount-dependent obligations) | Update occurs after review | Amount at review and at update | Decrease does not invalidate; unknown base = not classifiable | Unknown prior amount: not safely classifiable | Update event with old/new values; review timestamp |
| R5 | Exemption claimed at obligation trigger time | N/A (validity check) | `effective_from`  trigger time; approval evidence time  trigger time | Scope fields (`jurisdiction`, `customer_type`, `amount`) at trigger | Late DB record may support earlier approval; backdated display alone is not conclusive | Unknown scope values break match | Digital signature / certificate timestamp; system record; witness independence |
| R6 | Any evaluation where decisive value missing | N/A | N/A | N/A | Resolved only if other evidence determines value | Do not default missing values | Explicit update or reliable external record |
| R7 | Every evaluation | Use cumulative state up to event | For ties: `event_index` ascending | Latest known value at the relevant event | N/A | Unknown values carried forward | Full ordered event sequence |

### Formal pseudo-logic (R1–R7)

```
State(c, e) = apply_updates(events(c) with (ts, idx)  (ts(e), idx(e)))

R1(Release_Funds r in c):
  J = State(c, r).jurisdiction
  A = State(c, r).amount
  Trigger: J  'DE'  A  100000  known(A)  known(J)
  Required: rev: name(rev)='Enhanced_Review'  ts(rev)<ts(r)  ts(rev)>ts(last_material_change(r))
  Exception: ex: exemption_at(r)=id(ex)  valid_R5(ex, r, J, customer, A)  scope(ex) includes R1

last_material_change(r):
  max { ts(u) | u updates jurisdiction, risk, customer, or (updates amount  increase>20%)  ts(u)<ts(r) }

R2(Release_Funds r in c):
  Rk = State(c, r).risk_level
  Ct = State(c, r).customer_type
  Trigger: (Rk='HIGH'  Ct='PEP')  known(Rk)  known(Ct)
  Required:
    rev: Enhanced_Review  ts(rev)<ts(r)  ts(rev)>ts(last_material_change(r))
    app: Compliance_Approve  ts(rev)<ts(app)<ts(r)

R3(Release_Funds r in c):
  J = State(c, r).jurisdiction
  Let S = latest Sanctions_Screen < ts(r)
  Let U = latest Sanctions_List_Update with J added, ts(U) < ts(r)
  Trigger: S exists  U exists  ts(S) < ts(U) < ts(r)
  Required: scr: Sanctions_Screen  ts(U)<ts(scr)<ts(r)

R4(Update_Amount u in c):
  rev = latest (Standard_Review  Enhanced_Review) with ts(rev)<ts(u)
  A_rev = State(c, rev).amount
  A_u = State(c, u).amount
  If known(A_rev)  known(A_u)  A_u > 1.2 * A_rev:
       review_invalidated(rev, u) = true
  If known(A_rev)  known(A_u)  A_u < A_rev:
       review_invalidated = false
  If A_rev unknown:
       classifiable = false

R5(exemption ex at trigger time T):
  approved_by(ex) = 'Head_Compliance'
   effective_from(ex)  T
   jurisdiction(ex) = State(jurisdiction, T)
   customer_type(ex) = State(customer_type, T)
   amount  max_scope(ex) (and  min if defined)
   expires(ex) > T
   approval_evidence_exists_at_or_before(T)  [signature/hash or reliable witness; not display-only backdating]

R6(c, evaluation_event e):
  For each v in {amount, risk_level, jurisdiction, customer_type}:
    if v required for trigger and State(c,e).v unknown:
       result = INDETERMINATE (unless other evidence resolves v)

R7(c):
  For all events e in c:
    apply updates in (ts, event_index) order
  State at e uses only updates with (ts, idx)  (ts(e), idx(e))
```

## 4. Ambiguities and Alternative Readings

**TX-302 (exemption evidence standard)**  
If one rejects the documented outage explanation and demands a system record present at release time (`09:40`), EX-77 could be deemed unproven, turning the case to `NONCOMPLIANT`. The qualified digital signature at `09:05` supports timely approval, but a strict “record-at-release” interpretation removes the justification.

**TX-305 (missing amount)**  
If the settlement amount (`150000` at 07:00) is treated as the de facto release amount despite the absence of an immutable release payload, then `amount` is known to be ` 100000`, R1 applies, and the existing `Enhanced_Review` (`11:15`) satisfies it (no material change after). This would yield `COMPLIANT`. Conversely, if the blank amounts are interpreted as “amount feed failure requiring halt,” the deviation is more severe. Without an immutable payload, the result remains `INDETERMINATE`.

**TX-310 (post-hoc exemption and witness credibility)**  
If the transaction requester’s oral testimony (`08:45`) is accepted as credible, EX-88 was approved before release and the case is `JUSTIFIED_EXCEPTION`. If the qualified signing certificate (`10:30`) dominates—showing the PDF was backdated—then the exemption is invalid and the case is `NONCOMPLIANT` (missing `Enhanced_Review`). Because the evidence is genuinely contradictory and the witness has a conflict of interest, `INDETERMINATE` is the defensible classification.

**TX-311 (same-timestamp ordering and material-change interpretation)**  
If same-timestamp events are collapsed (ignoring `event_index`), the jurisdiction might be considered `DE` during the `Enhanced_Review` at `16:20`, removing any R1 concern but also removing the `US`-state context. More importantly, an alternative reading could treat *any* jurisdiction change as “material,” requiring the review to occur after index 4. Even under that stricter reading, R1 is not triggered at release (`DE`), so the classification remains `COMPLIANT`. The result is robust, but the reasoning depends explicitly on `event_index` ordering.

**TX-306 (materiality threshold)**  
If one interprets “material data change” for R1 as *any* amount update (including `+4.55%`), then the `Enhanced_Review` (`12:15`) precedes the update (`12:30`) and R1 is violated. The problem’s R4 limits invalidation to `>20%`, which supports the `COMPLIANT` reading used here.

**TX-308 (boundary at exactly 100,000)**  
If `amount  100,000` is interpreted strictly as `> 100,000`, then `amount = 100,000` does not trigger R1, making the `Enhanced_Review` unnecessary but not creating a deviation; the case remains `COMPLIANT`. The rule text says “at least,” so inclusion is correct.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage**: A control-flow checker that copies the final case state backward (e.g., applying `jurisdiction = DE` in TX-311 to all prior events) would miss that `Enhanced_Review` occurred under `US` rules and would misjudge R1 applicability.
2. **Post-hoc exemptions**: EX-77 and EX-88 are recorded (`Record_Exemption`) after `Release_Funds`. A pure activity-order check cannot validate whether approval evidence existed *before* release (`09:05` vs. `11:00`; `08:50` display vs. `10:30` certificate).
3. **Material changes after review**: R4 requires comparing *values* (`95000`  `118000`  `145000` in TX-309) to invalidate a review. DECLARE can check “update after review,” but not whether the increase exceeded `20%`.
4. **Conditional activation**: R1 activates only if `jurisdiction  DE` and `amount  100000`; R2 activates only for `HIGH`/`PEP`. Control-flow has no data guards; it treats all cases as requiring the same path.
5. **Missing data**: Blank `amount` cells in TX-305 are not null defaults; they represent unknown values. A checker that imputes `0` or `LOW` would incorrectly suppress R1 and misclassify the case.
6. **Same-timestamp ordering**: In TX-311, `Enhanced_Review` (index 3) and `Update_Jurisdiction` (index 4) share `16:20`. A timestamp-only model collapses them, losing the fact that the review preceded the jurisdiction change.
7. **Evidence quality and temporal semantics**: R5 distinguishes `effective_from`, `approval` time, `record` time, and `evidence` time (signature vs. witness). Activity logs contain none of these distinctions without explicit attribute semantics.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload**: At `Release_Funds`, write an immutable record (`release_amount`, `release_jurisdiction`, `release_customer_type`, `release_risk`) that cannot be overwritten by later updates. This resolves TX-305-style ambiguity.
- **Effective / record / signature timestamps for exemptions**: Store `exemption_approved_at` (system), `exemption_effective_from`, `digital_signature_timestamp`, and `database_record_time` separately. This distinguishes EX-77 (signature `09:05`) from EX-88 (certificate `10:30`).
- **Old/new value logging for updates**: Every `Update_Amount`, `Update_Jurisdiction`, etc., should log `previous_value` and `new_value` with provenance (`org:resource`, reason code). This makes R4 calculations auditable.
- **Rule version tagging**: Include `rule_version` and `rule_trigger_snapshot` at each review/approval event so that evaluations are reproducible.
- **Stable event ordering**: Use a monotonic sequence number (`event_index` extended globally or case-level with no ties) rather than relying solely on database insertion order, eliminating ambiguity in same-timestamp cases like TX-311.
- **Exemption scope and match evidence at claim time**: When an exemption is referenced (`exemption_id`), log the matched scope fields (`jurisdiction`, `customer_type`, `amount`) at that exact event time, plus a pointer to approval evidence.
- **Sanctions list provenance**: For `Sanctions_List_Update`, log the `jurisdiction_added` and `update_source` explicitly, linking directly to the screening obligation (R3).
- **Unknown-value flags**: If a required attribute is missing at `Release_Funds`, generate an explicit `DATA_MISSING` event or flag rather than leaving a blank, forcing deterministic `INDETERMINATE` handling.
