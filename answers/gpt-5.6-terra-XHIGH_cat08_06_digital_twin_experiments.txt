# 1. Model scope and state variables

The twin should be a **calendar-aware, discrete-event simulation with case agents and shared operational state**, not an independent-case replay. PM4Py is used to prepare, discover, and validate process behavior; a separate simulation engine executes queues, calendars, dependencies, and policies.

The operational boundary is:

- **Start:** portal submission or, for the pre-submission policy, applicant intent/pre-check completion.
- **End:** permit issued, application rejected with no appeal, or appeal/rework reaches a terminal outcome.
- **Inside the twin:** municipal work queues, staff calendars, reviews, inspections, public notice, applicant document response, objections, batching, rework, and policy rules.
- **Outside but represented stochastically:** applicant behavior, consultant reports, architect workload, neighborhood objections, travel uncertainty, and appeal behavior.
- **Out of scope unless separate data are added:** safety outcomes after a skipped inspection, legal validity of a policy, applicant satisfaction, and whether a permit decision was substantively correct. These are decision guardrails, not outputs that the event log can establish.

The nominal process tree provides structural constraints, but the executable model should be a richer state machine/DAG because the tree does not encode attribute-dependent routing, calendars, appeal behavior, or cross-case dependencies.

### Entities and state

| Entity | Important state variables |
|---|---|
| Permit case | Case ID, case type, district, architect, value, submission time, flags for fire/environment/public notice, latent eligibility attributes, current stage, completed stages, rework counts, deadlines, age, priority, terminal outcome |
| Work item | Activity, required skill pool, ready time, required predecessors, service requirement, queue entry time, assigned resource, service start/end, interruption state, retry/rework reason |
| Applicant/architect | Architect ID, weekly submission cohort, document-quality propensity, response-time random effect, appointment adherence, associated cases |
| Neighborhood/public-notice group | District or neighborhood proxy, objection latent state, shared objection shock, notice extension duration, related cases |
| Inspection batch | District, candidate cases, batching window, route/order, travel-time realization, inspector assignment, applicant-readiness/no-show state |
| Resource pool | Capacity, skill eligibility, individual/pooled availability, calendar, queue discipline, current assignments, utilization, overtime policy |
| System state | Simulation time, event calendar, queues, available capacity, backlog by stage, open public notices, council-meeting periods, holiday schedule, work-in-progress inventory |

### Case flow and dependencies

The simulation should implement the following logic.

1. **Arrival and intake**
   - Cases arrive according to a non-stationary marked arrival process.
   - Each arrival receives case attributes, including observed flags and latent values for missing fire/environment/violation/sensitivity information.
   - The case enters the completeness queue.

2. **Completeness and applicant loops**
   - Completeness check consumes clerk capacity.
   - A missing-document outcome creates a municipal request task followed by an applicant-driven response delay.
   - The case returns for a completeness re-check. Rework count and document quality affect the probability of further loops.

3. **Parallel technical work**
   - Planning review is required for all cases.
   - Fire, environmental, and public-notice branches are activated only when routing conditions apply.
   - The simulation represents these as parallel work items with an explicit join: decision drafting cannot start until all applicable technical reviews, notice requirements, and inspection requirements have completed.

4. **Inspection and geographic interaction**
   - Inspection scheduling consumes scheduler capacity.
   - Site inspections consume inspector capacity, field calendars, appointment slots, travel time, and applicant readiness.
   - Related cases may be grouped by district and scheduling window. Batching reduces route travel but may delay the first case until a viable batch forms.
   - D3 and D5 should have district-specific travel distributions because D3 and D5 historically have longer travel times.

5. **Decision, legal check, and appeal/rework**
   - Decision drafting may start only after required technical branches join.
   - Legal check is sequential in the baseline unless D5 activates a limited pre-check.
   - Rework can return a case to an earlier stage after Planning review, Site inspection, Legal check, or an appeal.
   - An appeal is represented as a post-rejection event that may create a new review/rework path. If appeals are poorly observed, it should be modeled as a scenario rather than treated as fully identified.

6. **Public notice and objections**
   - The statutory minimum notice period is modeled as a calendar-time delay, not municipal service time.
   - Objections are a latent event because they are not fully observed. Public-notice duration is modeled with a hurdle/mixture distribution: minimum notice period with no objection versus an extended tail conditional on a latent objection.
   - Related cases may receive a shared neighborhood-objection shock, creating correlated long public-notice durations.

### Resources, queues, and calendars

| Pool | Capacity and calendar representation | Main queues |
|---|---|---|
| Clerks | 5 FTE, Monday-Friday 08:00-16:00; one clerk unavailable for normal work on Mondays due to portal support | Completeness, missing-document requests |
| Planners | 8 FTE, Monday-Friday 09:00-17:00; two restricted to Simple renovation work | Planning review, decision drafting, aging-case reserve under D6 |
| Fire reviewers | 2 FTE equivalent, Tuesday-Thursday only | Fire-safety review |
| Environmental reviewers | 3 FTE, Monday-Friday, with 40% blocked for non-permit duties | Environmental review |
| Schedulers | Derived from scheduler resource data or modeled as a small shared administrative pool | Inspection scheduling |
| Inspectors | 4 FTE, field work Tuesday-Friday; route and travel constraints | Inspection scheduling/field visit appointments |
| Legal officers | 2 FTE; no ordinary legal work during council-meeting weeks | Legal check and D5 pre-check |
| System | Unlimited practical capacity | Portal receipts, issue permit automation, clocks/notifications |

Calendar behavior should be explicit:

- Municipal work is accumulated in **working time**, not raw elapsed clock time.
- Human tasks can pause outside working hours; non-preemptive field inspections are scheduled only in feasible field-visit slots.
- Holidays, public closures, council meetings, and restricted specialist days block capacity.
- Applicant responses and public-notice periods run in calendar time and are not constrained by municipal work calendars.
- Urgent legal work should either be modeled as a separate reserved capacity stream or excluded consistently, because emergency cases were removed from the log.

### Cross-case dependencies

The twin should include the following explicitly rather than assuming cases are independent:

- **Architect clusters:** top architects create correlated weekly bursts and may have correlated document quality and response times.
- **Inspection batching:** cases in the same district can share route travel, with an explicit batching window and maximum route capacity.
- **Neighborhood objection shocks:** cases sharing district/neighborhood/time window can have correlated public-notice extensions.
- **Shared resource congestion:** all municipal queues create indirect dependencies across otherwise unrelated cases.
- **Calendar shocks:** council-meeting weeks and holidays affect every eligible legal/public-notice case simultaneously.
- **Policy-induced interactions:** for example, D2 can reduce inspection demand, which changes waiting times for remaining high-risk inspections; D4 may only be valuable when demand peaks or batching is active.

# 2. Parameter-estimation plan

### Log preparation and PM4Py use

Use pandas for file ingestion and PM4Py for event-log formatting, discovery, conformance, and process-model handling.

1. Read the raw CSV with `pandas.read_csv`; do not use a nonexistent `pm4py.read_csv`.
2. Normalize timestamps, time zones, resource identifiers, duplicate events, case attributes, and lifecycle information.
3. Use:

   ```python
   pm4py.format_dataframe(
       df,
       case_id="case:concept:name",
       activity_key="concept:name",
       timestamp_key="time:timestamp"
   )
   ```

4. Use PM4Py to obtain:
   - variants, stratified by case type and district;
   - DFG and performance DFG;
   - start/end activities;
   - inductive-discovery models as diagnostic comparisons;
   - token replay or alignment diagnostics against the nominal process tree where the tree can be parsed.

The PM4Py process model should be treated as a **behavioral and conformance reference**, not as the simulation engine. A process tree alone does not model resource capacity, non-stationary arrivals, batching, or cross-case effects.

### Arrival estimation

Estimate a marked, non-homogeneous arrival process rather than sampling independent historical inter-arrival times.

- Fit arrival intensity by:
  - month/season;
  - weekday;
  - hour of day;
  - case type;
  - district;
  - architect class: top-20 architects versus other architects.
- Preserve the observed March-May and September-November peak structure.
- Estimate weekday effects, including the observed Monday/Wednesday imbalance.
- Generate architect submissions using either:
  - a hierarchical weekly batch model, or
  - an empirical block bootstrap of architect-week submission bundles.
- Model case mix as conditional on calendar period, district, and architect class, rather than fixed overall percentages.
- Validate the model against daily counts, weekly autocorrelation, architect-week counts, and the distribution of simultaneous submissions.

A practical formulation is:

\[
\lambda_{t,k,a} =
\lambda_0(t)
\cdot s_{\text{month}}(t)
\cdot s_{\text{weekday}}(t)
\cdot s_{\text{hour}}(t)
\cdot s_{\text{case type}}(k \mid t)
\cdot s_{\text{architect}}(a \mid t)
\]

with an additional burst process for large architects.

### Service-time and waiting-time estimation

The crucial distinction is:

- **Municipal service time:** active work by a municipal resource.
- **Municipal waiting time:** time in a queue or blocked by a dependency/calendar.
- **Applicant/third-party delay:** external calendar time after a request or during notice.
- **Completion-to-completion elapsed time:** not automatically service time.

Because many human activities have only completion timestamps:

1. Where lifecycle start and completion timestamps exist, pair them by case, activity, occurrence number, and resource to estimate observed active service duration.
2. Convert service times into working-time units using the relevant calendar.
3. Fit conditional distributions by activity, case type, district, and where supported, resource pool. Lognormal, gamma, empirical bootstrap, or mixture models are preferable to using medians alone.
4. Fit heavy tails separately for:
   - applicant missing-document response;
   - environmental review;
   - public-notice extensions;
   - complex rework;
   - appeals.
5. Do **not** use the full timestamp gap between activities as a sampled service time. It contains prior service, queueing, dependency delays, closures, and applicant delays.
6. Let the simulation produce municipal waiting times through queues and calendars. Calibrate resource capacity and dispatching rules until simulated waiting distributions match observed waiting targets.
7. If a residual administrative delay remains after queueing and service are modeled, represent it as a named release/hand-off delay, not as hidden service time.

The supplied service-time summaries can serve as priors or calibration targets, particularly for activities with incomplete lifecycle data.

### Routing, branching, and rework estimation

Estimate routing as conditional probabilities or classifiers, not only global branch shares.

- Stratify by case type, district, value, architect class, observed flags, and season.
- Fire requirement:
  - use `requires_fire=yes` where present;
  - estimate probability of fire review for cases with missing area threshold information.
- Environmental requirement:
  - use `requires_environment=yes`;
  - estimate district-sensitivity probabilities where sensitivity data are incomplete.
- Public notice:
  - enforce Complex variance;
  - estimate the conditional probability for New residential cases.
- Rework:
  - estimate transition probabilities after Planning, Inspection, Legal, and appeal stages;
  - use attempt number and case type as predictors;
  - represent unreliable rework-reason text as a latent cause category or a sensitivity range.
- Terminal routing:
  - estimate issue/reject/appeal behavior by case type and review outcomes where available.

Right-censored cases still open at extraction should be handled with survival methods or excluded from naive duration fitting; they should not be treated as short completed cases.

### Resource and calendar estimation

- Reconcile resource labels in the log with HR-derived calendars and FTE counts.
- Estimate skill eligibility from observed resource-activity assignments.
- Use calendar-aware observed work time to estimate service demand.
- Represent environmental non-permit duties as blocked capacity, initially 40%, then calibrate against observed queue patterns.
- Compare legal throughput before, during, and after council-meeting periods.
- Derive inspector route/travel parameters from district, observed inspection timing, and any available appointment/route data.
- If individual resource assignments are too sparse, use pooled capacity while retaining skill restrictions.

### Dependency estimation

The flattened event log is insufficient to prove all dependencies, so estimate them conservatively.

- Architect dependency:
  - estimate distribution of cases per architect-week;
  - estimate correlation between architect class and missing-document loops;
  - include an architect-level response-time random effect.
- Inspection dependency:
  - estimate empirical district-week inspection volume;
  - infer batch-size and travel reduction only where routing or appointment data support it;
  - otherwise use a sensitivity range.
- Objection dependency:
  - use public-notice duration as a proxy only;
  - fit a latent objection mixture and test shared district/neighborhood shocks in sensitivity analysis;
  - do not claim that long notice duration proves an objection occurred.
- Calendar dependency:
  - treat council-week interruptions as observed common shocks.

### Calibration

Calibrate the twin against several simultaneous targets, not only mean cycle time:

- case-type and variant shares;
- median, p90, and p95 elapsed duration;
- queue waiting distributions;
- backlog age distribution;
- monthly completions;
- resource utilization by pool;
- inspection travel/throughput;
- public-notice tail behavior;
- rework rates;
- district and architect-group disparities.

Use simulation-based calibration, approximate Bayesian computation, indirect inference, or optimization against a weighted loss function. Preserve parameter uncertainty rather than selecting a single “best” parameter set.

Historical observational data do not identify the causal effect of D1-D10. Intervention effect parameters should therefore come from pilots, policy experts, external evidence, or explicit low/base/high scenarios.

# 3. Assumptions

### Arrivals

- Arrivals are non-stationary by month, weekday, hour, district, case type, and architect class.
- The 1.7x historical peak pattern is treated as a baseline seasonal pattern, not a permanent law.
- Large architects create correlated bursts; ordinary cases are not modeled as completely independent Poisson arrivals.
- D1 and D7 may shift the timing of submission. They do not automatically reduce underlying permit demand.

### Service times

- Service-time distributions are conditional on activity, case type, district, and resource pool where data support such segmentation.
- Service consumes working-time capacity and pauses outside resource calendars unless the task is non-preemptive.
- Completion-only timestamps do not identify service time exactly. The supplied service summaries and the subset with lifecycle information anchor the service-time model.
- Inspection service time is decomposed into on-site work, travel, scheduling delay, and no-show/revisit effects where possible.
- D5 does not make legal work disappear; it moves some legal analysis earlier and may reduce later rework or final legal effort.

### Routing

- Observed fire/environment/public-notice flags are used when available.
- Missing area threshold, environmental sensitivity, prior violations, and objection indicators are modeled probabilistically.
- Decision drafting waits for every applicable required predecessor.
- D2 only applies when Simple renovation, value below EUR 50,000, and no prior violations are **verified**. Cases with unknown violations remain inspected in the conservative scenario.
- Legal pre-check under D5 is a preliminary task; final legal sign-off remains required where legally mandated.

### Resources/calendars

- HR-derived capacity calendars are initially treated as accurate enough for a baseline but are calibrated and stress-tested.
- Environmental reviewers supply only 60% nominal permit capacity because 40% is reserved for non-permit work.
- One clerk’s Monday portal-support duty removes that capacity from ordinary clerical work.
- No ordinary legal work is scheduled during council-meeting weeks. Any urgent-case capacity is modeled separately.
- Overtime is not assumed unless explicitly introduced as a scenario.

### Rework

- Rework probability depends on case type, document quality, inspection outcome, attempt count, and latent complexity.
- Unstructured rework reasons are not treated as reliable labels.
- The simplified process tree does not fully specify appeal behavior; appeals are represented with a calibrated or scenario-based post-decision re-entry path.
- Rework loops are capped only where law or operational policy imposes a real cap; otherwise unusually long cases remain possible.

### Applicant/third-party response

- Missing-document response time is applicant-driven, heavy-tailed, and may differ by architect class and case type.
- Applicant response time does not consume municipal service capacity.
- D1 may reduce document loops but adds pre-submission effort and can delay submission or cause abandonment/deferral; these effects are scenario parameters.
- Public notice runs for at least 14 calendar days. Extensions are generated from a latent objection process, not from falsely observed objection events.

### Cross-case dependencies

- Same-architect cases may share burst timing and response behavior.
- Same-district inspection cases can be batched, subject to a configurable waiting window and route capacity.
- Neighborhood objection shocks can affect multiple related notices, but their degree of correlation is uncertain.
- Shared queues and calendars create system-wide dependence even when cases have no direct relationship.

### Non-stationary demand

- Seasonal, weekly, and council-calendar effects are retained through the simulation horizon.
- The model is evaluated over complete peak and non-peak cycles rather than assuming steady state.
- Demand shocks, changes in case mix, and staffing disruptions are represented as explicit stress scenarios.

### Missing data

- Missing lifecycle starts lead to interval-censored or latent service/wait decompositions; they are not silently replaced by completion-to-completion duration.
- Missing objections are represented as latent mixture components.
- Flattened case logs underrepresent relationship structure; cross-case effects are sensitivity-tested.
- Removed emergency decisions mean the model cannot be expected to reproduce total operational workload without an explicit emergency-capacity adjustment.
- Uncertainty in missing area, sensitivity, and violation attributes propagates into routing and policy eligibility.

# 4. Experiment matrix

All intervention runs should use identical baseline policy settings, calibrated arrival streams, and common random numbers where possible. Low/base/high effect levels represent uncertainty in policy adoption and causal efficacy, not historical facts.

| ID | Factor(s) changed | Levels to test | Expected trade-offs and guardrails |
|---|---|---|---|
| B0 | Calibrated baseline | Historical staffing, routing, calendars, and arrival pattern | Reference case; must reproduce observed variants, duration tails, backlog, and utilization |
| D1 | Pre-submission document checker | Adoption: 50%, 80%, 95%; missing-loop reduction: low/base/high; added pre-submit effort | Fewer completeness loops and clerk load, but later submission, applicant burden, digital-access risk, and possible deferred applications |
| D2 | Low-risk Simple renovation skip-inspection rule | Conservative verified eligibility; optimistic proxy eligibility with false-classification sensitivity | Frees inspectors and shortens simple cases; requires legal/safety review outside simulation; no unverified prior-violation case should be skipped in the conservative run |
| D3 | District-batched inspection scheduling | No batching; 2-day, 5-day, and 8-day batching windows; route-capacity limits | Less travel and more inspections/day, but longer waiting for early cases and potential district inequity |
| D4 | Temporary inspector in peak months | No addition; +1 inspector in March-May and September-November; 70%, 85%, 100% productive onboarding | Reduces peak inspection backlog; cost, onboarding delay, and underutilization outside peaks |
| D5 | Parallel legal pre-check for Commercial and Complex cases | No pre-check; pre-check after planning package; pre-check after initial technical package | May reduce late legal rework and final legal queue; can consume legal capacity earlier and delay other cases |
| D6 | Reserve one planner daily for aging cases | Aging thresholds of 30, 45, 60 calendar days; work-conserving fallback if no aged work | Reduces long-tail aging cases; may delay new/short cases and reduce apparent average throughput |
| D7 | Architect-facing appointment slots | Voluntary uptake 30%, 60%, 80%; priority/incentive variants | Smooths Monday peaks; may disadvantage small applicants, urgent cases, or users unable to use slots |
| D8 | Environmental-review triage | Priority-only triage; rapid low-risk screening; low/base/high classification accuracy | Reduces delay for straightforward cases; false triage can delay high-risk cases or create rework; review is not waived |
| D9 | Public-notice objection early warning | Detection sensitivity low/base/high; no effect, modest outreach effect, strong outreach effect | Earlier preparation may reduce extension risk, but statutory minimum notice remains; objection effects are highly uncertain |
| D10 | Combined policy: D1 + D2 + D3 + D4 | Conservative, base, and optimistic uptake/effect bundles | Interaction effects are simulated directly; gains must not be added arithmetically because D2 and D4 both reduce inspection congestion |
| C1 | Capacity-and-flow combination: D3 + D4 + D6 | Fractional factorial of batching, temporary inspector, and aging threshold | Tests whether capacity and priority policies complement or undermine each other |
| C2 | Upstream-risk combination: D1 + D8 + D9 | Low/base/high adoption and effectiveness | Tests whether upstream document/risk interventions reduce downstream rework and notice tails |
| S1 | Peak demand shock | Peak arrivals +30% and +50%; preserve architect clustering | Tests queue stability during high demand; D4 should be assessed primarily here |
| S2 | Operational disruption | One inspector absent for four weeks; two additional council-meeting weeks | Tests resilience to staffing and legal-calendar shocks |
| S3 | Objection surge | Objection probability doubled; extension tail increased by 25% and 50% | Tests public-notice and legal bottlenecks without claiming observed objection data |
| S4 | Adverse case-mix/service drift | Commercial/Complex share increased; environmental p90 service time +25% | Tests robustness to a more difficult future portfolio |

A practical design is:

1. Run B0 and D1-D10 with central assumptions and 50 paired replications.
2. Remove clearly dominated options.
3. Run finalists, D10, C1, and C2 with 200 paired replications.
4. Apply S1-S4 to B0, D10, and selected finalists.
5. Use low/base/high intervention-effect assumptions and parameter-bootstrap draws for finalists.

# 5. Warm-up, replications, and uncertainty treatment

### Warm-up and run length

A conventional steady-state warm-up is inappropriate because demand and calendars are seasonal.

Use a **calendar-conditioned initialization**:

- Preferred approach: initialize the simulation from an observed work-in-progress snapshot at the policy start date, including open cases, current stage, age, and estimated residual work.
- If such a snapshot is unavailable, run a one-year baseline pre-period using the prior seasonal calendar pattern and discard its output.
- For policy rollout experiments:
  - run the pre-period under baseline policy;
  - activate the intervention at the evaluation start date;
  - simulate at least 12 evaluation months so that both peak and non-peak periods are represented;
  - continue arrivals for another 12 months for follow-up, while reporting outcomes for cases submitted in the evaluation cohort.
- Cases not completed after follow-up should be reported as right-censored rather than discarded. The model should also be run with an extended drain period as a sensitivity check.

### Replications and seeds

Use separate reproducible random-number streams for:

- arrivals and case attributes;
- architect bursts;
- service times;
- applicant response;
- rework;
- objection shocks;
- inspection travel/no-shows;
- policy adoption/compliance.

For each policy comparison, use **common random numbers**: the same submitted cases, latent attributes, and stochastic shocks should be mapped to baseline and intervention runs where policy logic permits. This improves precision for paired differences.

Recommended replication plan:

- Initial screening: 50 paired replications per policy.
- Finalists and combined policies: 200 paired replications.
- Add replications until the 95% confidence interval half-width is below approximately:
  - 2 calendar days for p90 duration change;
  - 1 percentage point for SLA compliance change;
  - or a municipality-defined precision threshold.

Record seed lists and model version for every experiment.

### Input and parameter uncertainty

Separate two uncertainty layers:

1. **Stochastic simulation uncertainty**
   - Repeated arrivals, service realizations, rework, objections, and travel.
   - Estimate paired confidence intervals for policy differences.

2. **Input/model uncertainty**
   - Service-time fitting uncertainty.
   - Missing start-time decomposition.
   - Objection mixture parameters.
   - Routing probabilities for missing fire/environment/sensitivity data.
   - Batching travel savings.
   - Intervention adoption and efficacy.

For finalists, use blocked bootstrap or Bayesian posterior draws:

- Resample historical data by week and architect cluster, not individual events.
- Draw 20-30 parameter sets.
- For each parameter set, run approximately 30 paired stochastic replications.
- Aggregate the draws into a predictive uncertainty interval.

Use percentile bootstrap intervals or paired t/BCa intervals for well-behaved mean differences. For p90/p95 metrics, use replication-level quantile estimates and bootstrap the policy difference. If Bayesian input models are used, report posterior predictive credible intervals distinctly from frequentist confidence intervals.

### Heavy-tailed durations

Heavy-tailed applicant response, public notice, environmental review, and complex rework should not be replaced by normal distributions.

- Use empirical sampling, lognormal/log-logistic mixtures, or peaks-over-threshold tail models.
- Include a hurdle model for public notice: minimum statutory duration plus latent extension.
- Avoid arbitrary truncation. If operational policy imposes a maximum legal duration, encode it explicitly; otherwise report extreme-tail behavior and right-censoring.
- Report median, p90, p95, p99 where sample size allows, and conditional tail mean for long cases.
- Apply sensitivity analysis to the tail shape because 18 months may not identify very rare extreme events reliably.

# 6. Validation strategy

Validation should be iterative and should not be confused with proving that a policy will work.

### Face validation

Conduct structured walkthroughs with:

- clerks;
- planners;
- fire/environment reviewers;
- inspectors and schedulers;
- legal officers;
- public-notice/council staff;
- policy owners and applicant representatives.

Validate:

- routing rules;
- real calendar restrictions;
- whether work pauses overnight;
- inspection batching feasibility;
- priority rules;
- legal constraints on D2 and D5;
- plausibility of applicant and objection behavior;
- whether the model incorrectly omits informal queues or hand-offs.

### Event-log replay validation

Replay historical arrivals and case attributes through the calibrated twin under historical policies.

Compare:

- monthly completions;
- case-type and variant frequencies;
- activity ordering;
- rework-loop counts;
- terminal issue/reject proportions;
- stage-entry and completion profiles.

Use PM4Py alignments or token replay to quantify how much of the historical log conforms to the nominal process tree. Deviations should be classified as:

- expected exceptions;
- data-quality problems;
- omitted operational behavior;
- model errors.

Because starts are missing for many activities, replay should not claim exact task-level service reconstruction.

### Distributional validation

Compare simulated and observed distributions by case type, district, and season:

- total elapsed duration;
- municipal-controlled duration;
- applicant response duration;
- public-notice duration;
- queue waiting proxies;
- p50, p90, p95, and survival curves;
- case aging distribution;
- backlog size by stage.

Use visual QQ plots, empirical CDFs, Wasserstein/KS diagnostics, and calibration plots. Validate separately for peak and non-peak periods; a model that matches annual averages but fails in March-May is not adequate for D4.

### Resource-utilization validation

Compare simulated workload and utilization with:

- observed resource assignments;
- HR attendance/calendars;
- activity counts per pool;
- known field-visit capacity;
- legal throughput around council meetings.

Where start timestamps are missing, validate resource demand through service-time priors, completion volume, and queue patterns rather than falsely interpreting timestamp gaps as busy time.

### Bottleneck validation

Check whether the twin identifies operational bottlenecks consistent with staff experience:

- Monday completeness backlog;
- fire-review limited days;
- environmental queue variability;
- inspection field capacity and D3/D5 travel;
- legal congestion around council weeks;
- long public-notice tails;
- planning workload for complex cases.

Perform directional tests:

- temporarily add one inspector and confirm that inspection waits decline rather than unrelated stages;
- close legal capacity during council weeks and verify legal queues rise;
- increase Monday arrivals and verify clerk queues rise.

### Cross-case dependency validation

Validate simulated dependency structure against available summaries:

- cases per architect-week;
- autocorrelation in daily arrivals;
- district-week inspection batch sizes;
- travel-time differences by district;
- clustering of long public-notice durations where neighborhood proxies exist.

If neighborhood linkage cannot be validated, retain the shared-objection model as a sensitivity scenario rather than a calibrated fact.

### Out-of-sample and intervention validation

Use rolling-origin validation:

- calibrate on an earlier period;
- validate on later months, including at least one peak period;
- repeat with alternative splits if data allow.

If a historical policy change, pilot, or natural experiment exists, compare directional predictions with observed before/after changes while controlling for demand and case-mix shifts. The strongest validation for D1-D10 is a controlled pilot or phased rollout. Simulation alone should not be presented as evidence of exact causal impact.

# 7. Decision criteria

Use a multi-criteria decision rule. No single intervention should be selected solely because it reduces average duration.

The municipality should agree legal definitions of statutory clocks before final selection. Until then, report both:

- **total calendar duration** from submission to terminal decision;
- **municipal-controlled duration**, excluding applicant response and mandated notice minimums where legally appropriate.

| Criterion | Measure | Proposed decision threshold or range |
|---|---|---|
| Median duration | Median total and municipal-controlled duration by case type | No case type worsens materially; preferred options reduce median duration or improve another required objective |
| Tail duration | p90 and p95 duration by case type and district | Prefer at least 10% p90 reduction or 5-day reduction where feasible; 95% paired interval should not indicate meaningful tail deterioration |
| Illustrative SLA compliance | Share completed within configurable clock thresholds | Pending legal confirmation, test targets such as Simple <=30d, New residential <=60d, Commercial <=90d, Complex variance <=180d; report both total and municipal clocks |
| Fairness by district | Risk-adjusted median, p90, and SLA gap across districts | No district’s adjusted SLA compliance should worsen by more than 5 percentage points; D3/D5 must not deepen D3/D5 disadvantage |
| Fairness by architect group | Compare top-20 versus other architects after standardizing for case type/district/value | No more than 5 percentage-point worsening for smaller architects; appointment slots must preserve a non-slot access path |
| Resource utilization | Busy municipal working time / available working time; peak weekly utilization | Aim for sustainable annual utilization around 70%-90%; investigate pools above 95% for sustained peak weeks |
| Backlog | Mean/peak WIP, queue length, aged-case count, oldest-case age | No material increase in peak backlog or cases above SLA; preferred policies reduce aged backlog |
| Rework | Rework probability and expected number of loops | No more than 1-2 percentage-point increase unless legally justified; compare inspection rework among still-inspected cases under D2 |
| Inspection performance | Travel time, visits per field day, no-show/revisit rate | D3 must reduce travel or increase useful visits without excessive batch waiting |
| Public-notice performance | Notice extension tail, cases delayed beyond statutory minimum | D9 cannot shorten mandated notice; benefits must arise from validated operational mechanisms |
| Cost and staffing | Temporary staffing cost, implementation effort, applicant burden | Compare cost per additional SLA-compliant case and cost per tail-day avoided; use municipality budget thresholds |
| Safety/legal guardrails | D2 eligibility compliance, legal sign-off, quality audit outcomes | Hard constraint: no skipped inspection without verified eligibility and legal approval; simulation does not substitute for safety evaluation |
| Robustness | Performance under S1-S4 and parameter uncertainty | Preferred policy is non-inferior in at least 80% of plausible parameter draws and has no unacceptable stress-scenario failure |

A recommended selection rule is:

1. Eliminate options violating legal, safety, or fairness guardrails.
2. Eliminate options whose 95% uncertainty interval indicates material deterioration in p90 duration, SLA compliance, or backlog.
3. Identify the remaining Pareto-efficient policies across tail duration, equity, cost, utilization, and robustness.
4. Pilot the leading option or small set of options before city-wide deployment.

The result should be framed as: “under stated assumptions, these policies are robustly preferable,” not “the simulation proves the optimal policy.”

def add_observed_timing_columns(
    event_df: pd.DataFrame,
    start_col: str = "start:timestamp",
    end_col: str = TIMESTAMP,
) -> pd.DataFrame:
    """
    If genuine task start timestamps are available, estimate observed service:
        completion - start

    A generic previous-event completion is only a readiness proxy. It is not
    reliable for parallel branches, rework, or missing predecessors. A production
    estimator should infer activity readiness from the executable process DAG.
    """
    out = event_df.sort_values([CASE, end_col, ACTIVITY]).copy()
    out["previous_case_completion"] = out.groupby(CASE)[end_col].shift(1)
    out["observed_service_s"] = np.nan
    out["observed_wait_s_proxy"] = np.nan
    out["completion_to_completion_s"] = (
        out[end_col] - out["previous_case_completion"]
    ).dt.total_seconds()

    if start_col in out.columns:
        out[start_col] = pd.to_datetime(out[start_col], utc=True, errors="coerce")
        out["observed_service_s"] = (
            out[end_col] - out[start_col]
        ).dt.total_seconds()

        # Provisional only: replace with dependency-aware ready timestamps.
        out["observed_wait_s_proxy"] = (
            out[start_col] - out["previous_case_completion"]
        ).dt.total_seconds()

    return out

class Router:

    Produces an executable task DAG for each case, not merely a trace.

    It must preserve joins: decision drafting is released only after all applicable

    def __init__(self, routing_parameters: Mapping[str, Any], policy: Mapping[str, Any]):
        self.routing_parameters = routing_parameters
        self.policy = policy

    def needs_fire(self, case: PermitCase, rng: np.random.Generator) -> bool:

        raise NotImplementedError

The skeleton deliberately leaves the simulator implementation separate from PM4Py. PM4Py discovers and validates observed process behavior; the digital twin adds the operational mechanisms that traditional case-centric event-log replay does not contain: non-stationary arrivals, calendars, queues, inspection batches, latent objections, applicant delays, and inter-case dependencies.
