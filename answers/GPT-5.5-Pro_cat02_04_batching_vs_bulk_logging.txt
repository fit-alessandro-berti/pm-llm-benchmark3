# 3. Consequences for performance analysis

| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1      | Waiting from queue arrival to 09:00 is plausible as time until fixture admission. Bias arises if the queue model assumes one-at-a-time service rather than four-position capacity.                               | Per-item service is 3 minutes, but summing item service gives 12 item-minutes for a machine busy only 3 clock minutes.            | Naive event-duration summation can produce apparent 400% machine utilization. Throughput after recovery is serial and stable; conformance order between safety and repair systems requires clock validation.                                                                                            |

G6 deserves special caution because it contaminates both sides of a standard performance decomposition. With `waiting = start - queue_arrival`, all cases inherit the elapsed time until the 17:00 bulk entry, so waiting looks large. With `service = complete - start`, all cases have zero duration, so service capacity looks infinite. The same row can therefore make the queue look severely delayed while making the resource look unused or impossibly productive.

def parse_ts(clock_text):
    if pd.isna(clock_text) or str(clock_text).strip() == "":
        return pd.NaT
    return pd.to_datetime(f"{DATE} {str(clock_text).strip()}", errors="coerce")

for col in ["queue_arrival", "start", "complete", "recorded_at"]:
    df[col + "_ts"] = df[col].map(parse_ts)

df["service_min"] = (df["complete_ts"] - df["start_ts"]).dt.total_seconds() / 60
df["wait_min"] = (df["start_ts"] - df["queue_arrival_ts"]).dt.total_seconds() / 60
df["recording_lag_min"] = (df["recorded_at_ts"] - df["complete_ts"]).dt.total_seconds() / 60

def max_group_size(g, cols):
    return int(g.groupby(cols, dropna=False).size().max()) if len(g) else 0

def overlap_stats(g):
    h = g.dropna(subset=["start_ts", "complete_ts"]).sort_values(["start_ts", "complete_ts", "sequence_no"])
    pairs = 0
    overlap_pairs = 0
    events_with_overlap = set()
    for (_, a), (_, b) in combinations(h.iterrows(), 2):
        pairs += 1
        if max(a["start_ts"], b["start_ts"]) < min(a["complete_ts"], b["complete_ts"]):
            overlap_pairs += 1
            events_with_overlap.update([a["case"], b["case"]])
    return {
        "overlap_pair_rate": overlap_pairs / pairs if pairs else 0.0,
        "events_with_overlap": len(events_with_overlap),
    }

def adjacency_rate(g):
    h = g.dropna(subset=["start_ts", "complete_ts"]).sort_values(["start_ts", "sequence_no"])
    if len(h) < 2:
        return 0.0
    prev_complete = h["complete_ts"].iloc[:-1].reset_index(drop=True)
    next_start = h["start_ts"].iloc[1:].reset_index(drop=True)
    return float((next_start == prev_complete).mean())

def grid_rate(series, seconds):
    h = series.dropna()
    if h.empty:
        return np.nan
    midnight = h.dt.normalize()
    seconds_since_midnight = (h - midnight).dt.total_seconds()
    return float((seconds_since_midnight % seconds == 0).mean())

def independent_pattern(g):
    n = len(g)
    same_start = max_group_size(g, ["start_ts"]) == n
    same_end = max_group_size(g, ["complete_ts"]) == n
    adj = adjacency_rate(g)
    all_arrived_before_first_start = (g["queue_arrival_ts"] <= g["start_ts"].min()).all()
    median_wait = g["wait_min"].median()
    source = g["source"].iloc[0]
    resource = g["resource"].iloc[0]

    if source == "manual_bulk_form" and same_start and same_end and g["service_min"].eq(0).all():
        return "bulk_form_zero_duration"
    if source == "legacy_MES" or g["precision"].iloc[0] == "15 min":
        return "timestamp_coarsening_interval_censoring"
    if resource == "analyst_pool":
        return "shared_account_or_parallel_analysts"
    if same_start and same_end:
        return "simultaneous_or_physical_batch_candidate"
    if same_start and not same_end:
        return "common_start_or_setup_batch"
    if same_end and not same_start:
        return "common_completion_or_folder_submit"
    if adj == 1.0 and all_arrived_before_first_start and median_wait >= 30:
        return "queue_recovery_after_capacity_loss"
    if adj == 1.0:
        return "ordinary_serial_or_sequential_batch"
    return "mixed_or_uncertain"

def summarise_pm4py_result(result, merge_distance, min_batch_size):
    out = []
    entries = result if isinstance(result, list) else []
    for entry in entries:
        if not isinstance(entry, (tuple, list)) or len(entry) < 3:
            continue

        key, n_batches, typed_batches = entry[0], entry[1], entry[2]
        if isinstance(key, (tuple, list)) and len(key) >= 2:
            activity, resource = key[0], key[1]
        else:
            activity, resource = str(key), None

        category_counts = {}
        total_batched_events = 0
        if isinstance(typed_batches, (tuple, list)):
            for item in typed_batches:
                if isinstance(item, (tuple, list)) and len(item) >= 2:
                    category_counts[str(item[0])] = item[1]
                if isinstance(item, (tuple, list)) and len(item) >= 3:
                    try:
                        total_batched_events += sum(len(batch) for batch in item[2])
                    except TypeError:
                        pass

        cats_from_repr = sorted(set(re.findall(r"simultaneous|sequential|concurrent", str(entry), flags=re.I)))
        out.append({
            "merge_distance_s": merge_distance,
            "min_batch_size": min_batch_size,
            "activity": activity,
            "resource": resource,
            "cluster": pair_to_cluster.get((activity, resource), "unknown"),
            "pm4py_n_batches": n_batches,
            "pm4py_categories": category_counts or ",".join(cats_from_repr) or "unparsed",
            "pm4py_batched_events_seen": total_batched_events,
        })

    if not out:
        out.append({
            "merge_distance_s": merge_distance,

| robustness assumption                                    | effect on interpretation                                                                                                                                                                                                                                                                       |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Resource IDs are trusted as individual workers           | G2, G3, and G5 become problematic because their intervals overlap under one resource. G5 would imply extreme multitasking by one analyst, which conflicts with the shared-login context. G4 and G8 remain serial. G1 remains plausible because RBT-7 is an automated cell, not a human worker. |
| Resource IDs may be shared or represent stations/pools   | G5 changes from “one impossible multitasker” to “several analysts hidden behind one account.” G2’s T-B could be a station or screen rather than a person. Utilization and fairness analyses become unreliable wherever resource identity is pooled.                                            |
| Timestamps are exact execution times                     | G1 is strong evidence of physical fixture batching; G4 and G8 are strong evidence of serial service; G6 becomes an impossible zero-duration batch, suggesting logging artifact.                                                                                                                |
| Timestamps are interval-censored by documented precision | G7 cannot be ordered internally and should not produce exact waits or overlaps. G2 and G3, with 1-minute precision, may have short differences hidden inside a minute. Identical minute timestamps should be treated as equality within a bucket, not necessarily equality in reality.         |

# 6. Data-collection redesign

1. **Separate execution timestamps from recording timestamps.** Store actual work start, actual work completion, form-open time, form-submit time, and database insertion time as different fields. G3 and G6 show why one timestamp cannot safely play all roles.

2. **Capture source-clock metadata and synchronization status.** Store source system, clock offset, synchronization method, and last clock-sync time. This is essential for G8, where safety and repair systems have different clocks.

3. **Retain reliable resource identity.** Replace shared accounts with badge-level or session-level identities. If shared logins cannot be eliminated, store both pool ID and individual authenticated actor. This is critical for G5 and for any resource-utilization, fairness, handover, or segregation-of-duties analysis.

4. **Record explicit batch/group identifiers.** Add fixture ID, group-start ID, folder ID, bulk-submit ID, and batch cardinality. This distinguishes G1 physical batching, G2 common setup, G3 folder submission, and G6 manual bulk close.

5. **Represent workstation and machine capacity.** For RBT-7, record fixture capacity and occupancy. For human or tablet stations, record whether the resource is a person, station, screen, pool, or machine.

6. **Capture availability, downtime, pause, and resume events.** Add safety-check intervals, maintenance intervals, breaks, blocked states, and unavailable states to the same time base as the queue. This prevents G8-like queues from being misread as idle-time inefficiency.

7. **Store timestamp precision and rounding rules at field level.** Precision should be metadata per timestamp field, not only per source. For legacy MES, store whether starts are rounded down, completions rounded up, or both rounded to nearest quarter-hour.

8. **Preserve sequence numbers but do not use them as execution order without validation.** Sequence numbers are useful for insertion order, as in G1 and G7, but they do not by themselves prove physical order.

9. **Add lifecycle-state semantics.** Each timestamp should declare whether it means “eligible,” “assigned,” “setup started,” “active work started,” “work paused,” “work resumed,” “work completed,” “quality accepted,” or “record submitted.”

10. **Validate with short observational audits.** For each source type, observe a few real batches and compare physical work, local UI timestamps, recorded-at timestamps, and PM4Py-detected batch labels.

# 7. Final adjudication

| adjudication category                                          | clusters                 | conclusion                                                                                                                                                                                                    |
| -------------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| High-confidence interpretation                                 | G1, G4, G6, G7           | G1 is a likely physical automated fixture batch; G4 is reliable serial work; G6 is a bulk logging artifact unsuitable for lifecycle performance; G7 is interval-censored by coarse legacy timestamps.         |
| High-confidence data-quality problem                           | G5, G6, G7               | G5 has unreliable resource identity; G6 has artificial lifecycle timestamps; G7 has coarse rounded timestamps that can create false simultaneity and negative waits.                                          |
| Usable with correction or modeling adjustment                  | G1, G4, G8               | G1 is usable with capacity-aware batching; G4 is usable as serial processing; G8 is usable if downtime and clock alignment are modeled.                                                                       |
| Exclude or interval-censor in queue analysis                   | G6, G7, partly G3 and G5 | Exclude G6 from queue/service calculations unless true handling times are recovered. Interval-censor G7. Treat G3 completion as possibly submission-censored. Do not use G5 for individual-resource queueing. |
| Requires operational validation before performance conclusions | G2, G3, G5, G8           | G2 needs separation of setup/group start from item work. G3 needs actual completion versus folder submission. G5 needs badge identity. G8 needs clock synchronization and downtime validation.                |

The safest final reading is: G1 and G4 can support performance conclusions after respecting capacity and seriality; G6 and G7 should not be used as exact queue/service evidence; G2, G3, G5, and G8 require operational validation because their temporal signatures are compatible with more than one physical mechanism. PM4Py batch discovery is useful here as a detector of temporal regularities, but its labels should not be treated as proof of physical batching, concurrency, or worker behavior.
