# 3. Consequences for performance analysis

General bias mechanisms:

- **Waiting time** `W = start  queue_arrival`. If `start` is group-start (G2) or bulk-log time (G6/G3/G8-blocked) then `W` is inflated (or deflated if end-coarsened shifts start late). Variance inflated.
- **Service time** `S = complete  start`. Common-start inflates `S` for later items (G2 longest 27 min vs true 7), common-end inflates early items (G3 28 min vs true 6), zero-duration collapses `S0` (G6), coarse rounding fixes `S` to bin width (G7 15 min regardless of truth).
- **Utilization** `U = busy_time / observation_window` and **concurrent occupancy**. Overlapping interpretation double-counts single resource  `U>100%` or spurious multitasking violations; batch-machine correct accounting is `U_batch = batch_duration/window` not sum of overlapped durations.
- **Throughput & bottleneck detection** Spurious throughput spike at batch completion time, or starvation gap misread as resource idleness, misplaces bottleneck.

Per cluster:

**G1 – genuine batch.** *Waiting*: modest fixture-fill wait (2–6 min). If expanded naively to 4 parallel services, average `W` unchanged. *Service*: observed 3 min is **batch service**, not per-item sum; summing 4×3=12 min overestimates load by factor 4. *Utilization*: RBT-7 utilized 3 min per 9 min window 33% batch-util; counting 4 concurrent occupancies yields 133% phantom overload. *Throughput*: 4 completions at same second  instantaneous throughput 240/hr vs true batch throughput 80 batches/hr. Process mining without batch resource type flags false high workload. Correction: introduce workstation capacity=4 and throughput in items per batch cycle.

**G2 – start batching.** *Waiting*: using recorded `start=10:00`, W = 18/14/11/6 min respectively. True waiting for S04 is larger (had to queue behind S01–S03), but grouped start hides queuing order and compresses variation. *Service*: measured `S` 8/14/21/27 min monotonically increasing – classic start-batching artefact; true service 6.5 ±0.8 min (inter-completion times). Overestimation inflates average S by ~2× and variance by ~3×. *Utilization*: overlap 8–27 min suggests 2.5 avg concurrency  violates single-inspector constraint, false conformance violation (parallel gate). *Bottleneck*: downstream appears starved after 10:00 then bursty. Fix requires splitting group-start into estimated individual starts (`complete_prev` or `completeavg_service`).

**G3 – end batching.** *Waiting*: `start` relatively faithful (staggered), so `W` = 22/18/19/19 min reasonable. *Service*: `complete=11:30` forces S =28/20/13/6 min – inverse pattern, early items penalized; average 16.8 min vs ground truth 7 min reported in context (“half hour folder”  7.5 min/item). Variance hugely inflated. *Utilization*: if taken literally, 4 concurrent at 11:20–11:30 implies overload. *Throughput*: 4 completions logged instantaneously at 11:30  phantom capacity spike; Little’s Law `L = ·W` breaks because departure times batched. Correct via submission lag separation: use `start` plus inferred service chain, discard synchronous `complete`.

**G4 – sequential batching (reference).** *Waiting*: accurate FIFO: W1=7, W210, W3=13, etc. growing with queue length – true queue dynamics. *Service*: 4 min steady provides reliable capability `µ=15/hr`. *Utilization*: continuous busy 12:05–12:25 U=100% during busy period, correctly signals saturated resource if arrival rate exceeds. *Bottleneck detection*: valid; this is benchmark against which other clusters bias judged. Larger `merge_distance` >4 min would falsely merge chain into a G1-like batch – example of PM4Py parameter bias.

**G5 – shared-account artifact.** *Waiting/service/unavailable*: all computed per pooled ID meaninglessly mix 2–3 workers. Example: A02 waiting 15 min but executed by different analyst who may have been idle; apparent service overlaps yield sum-busy 70 min wall-time over 30 min elapsed  naïve U=233%. False “multitasking inefficiency” flagged; performance by analyst inverted. *Throughput*: aggregated throughput ~8/hr appears as single super-worker vs true 2–3×5/hr individuals. Must disaggregate or analyse at pool level (`throughput_pool` valid, `util_per_person` invalid).

**G6-like bulk logging – inflated waiting + near-zero service paradox.** This canonical “operational vs logging” divergence explains why one dataset simultaneously inflates one metric and deflates the other. Mechanism: execution timestamps are **replaced** by logging timestamps. `start_log = complete_log = submission_time` (17:00). Hence:

```
W_observed = submission  queue_arrival = W_true + (processing_delay + batching_delay)
             hours (99–176 min in data vs true maybe <60 min)
S_observed = complete_log  start_log 0
```

Waiting absorbs entire residence time including unrecorded work and holding before submit; service captures none. Effects: SLA breach false positives (waiting SLA fails massively); service-level agreements pass trivially (S0); utilization histogram: 0% for hours then impulse 700% at submission instant; discovery yields 7-way parallel zero-duration activity  conformance engine reports batch violation or skips timing. Any KPI averaging across G6 items without flagging corrupts enterprise averages: `average_W` over-all cases biased +~120 min proportionally to G6 share, `average_S` diluted toward zero. Remedy: censor `W` to `[ , submission]` as upper bound only, nullify `S`, route bottleneck analysis to upstream queues using `queue_arrival` vs `recorded_at` curve, not `start`.

**G7 – timestamp coarsening.** *Waiting & service*: both determined by bin, not truth. Observed W: if arrival 13:58 inside [14:00,14:15) then negative waiting if start floored to 14:00 – nonsensical; observed S=15 min for all hides true variance (true measure likely 2–4 min serial). *Utilization*: 5×100% overlap for 15 min suggests need for 5 parallel stations; corrected expectation 5 serial measures would occupy ~15 min with U=100% if pipelined, not 500%. *Throughput*: quantized departure  throughput granule 15 min. All time-prediction models degenerate unless interval-censored likelihood used (e.g., EM for rounded data). Bottleneck detection flips based on rounding rule (down-round vs nearest).

**G8 – queue accumulation after capacity loss.** *Waiting*: true W = blocked_wait + queueing_drain. Observed Q01 W=38 min dominated by block 35 min; decomposing `W_block  35 min` vs `W_queue 3 min`. Without external event tag, naïve analysis attributes large W to insufficient repair capacity (false bottleneck at T-H) rather than upstream safety stoppage. *Service*: accurate 7 min per item post-resume. *Utilization*: long idle 15:00–15:38 U=0% then sustained 100% drain; period-normalized U over full 73 min 47% masks post-resume overload. Requires conditional analysis: `U_given_available` vs `U_including_downtime`. Throughput during unavailable =0 inflates apparent arrival rate vs departure imbalance. Clock skew  between safety log and scanner adds ±uncertainty to gap length; sensitivity ±2 min translates directly to W_bias.

# 5. Robustness and alternative explanations

## Resource ID trust vs shared accounts

- **If resource IDs trusted as single workers:** G5 must be classified as severe violation of human capacity (impossible concurrent root-cause analyses). Conclusion becomes “massive multitasking/overload” and utilization metrics trigger staffing intervention. That conclusion is **fragile** because context explicitly states `analyst_pool` up to three analysts share login without badge retention. Trusting it assigns all delays to one overloaded analyst rather than distributing across team, biasing bottleneck detection toward “analyst_pool is bottleneck” instead of “team slightly loaded.”

- **If treated as shared account:** G5 switches to `shared-account artifact + concurrent work` – observed concurrency (up to 3) matches documented capacity, and waiting/service per analyst must be reported as bounds, not point estimates. Average service 17.5 min pooled could decompose to, e.g., Analyst A 25 & 10 min, Analyst B 15 min, Analyst C 20 min – indistinguishable from log. Sensitivity: any throughput/utilization ranking that includes G5 collapses uncertainty if resource identity uncertain; exclude G5 from individual leaderboard unless disambiguated.

Analogous but weaker effect for G1: if `RBT-7` assumed one-piece robot, simultaneous starts look like data error; knowing fixture capacity 4 reconciles pattern. For other clusters resource identity less ambiguous (personal tablets) but shift-handover or coverage could mimic G5 micro-effects.

## Exact timestamps vs interval-censored by precision

Treating timestamps as instants:

- G7 labelled `genuine simultaneous batch` (5× identical 14:00–14:15) with 100% confidence.
- G2 start equality seen as intentional batch policy.
- G3 end equality seen as synchronized release.

Treating timestamps as intervals `[t, t+precision)` (A1):

- G7 equality dissolves entirely: 15-min bin forces any measurement in quarter-hour into same reported time. Five recorded_at values 14:16–14:20 spanning 4 min prove underlying order hidden by rounding. Diagnosis flips to `timestamp coarsening` and requires interval algebra; point-estimate service 15 min replaced by interval `[<15, >0]` unknown. Bias correction: replace equality tests with overlap-of-intervals test.
- G2/G3 1-min precision: equality of 4 starts/ends within 0 min could be accidental truncation of starts 10:00:12, 10:00:48 etc. Under interval view confidence drops 10–15 points and categories become “start/end batching **within 1-min resolution**” rather than proven simultaneity. For G4/G8 1-sec precision, interval impact negligible – categories robust.
- G6 1-min precision irrelevant to zero-duration diagnosis because `start==complete==17:00` exact to minute still implies <1 min duration, inconsistent with plausible close-ticket work >1 min.

Implication: inference hierarchy must condition on `precision`. Fine-precision clusters (G1, G4, G8 scanner) support stronger physical claims; coarse clusters demand censored analysis.

## Three patterns supporting multiple physical explanations (treatment of uncertainty)

**1. Identical start + identical end (full coincidence) – G1 vs G6 vs G7**

- *Same signature*: `uniq_start=1, uniq_end=1, overlap=full`.
- *Three defensible physics*:
  - (a) G1-type genuine parallel machine batch (fixture, oven, robot).
  - (b) G6-type logging batch where work done at unknown earlier times and bulk-recorded with `start==complete==submit` (database insertion artefact).
  - (c) G7-type discretization where coarse rounding collapses distinct times into one bin.
- *Discriminators*: `recorded_at` jitter (G1 1-sec vs G6/G7 minute-separated), `source` (PLC sensor vs manual_bulk_form vs legacy_MES), documented capacity, precision metadata, and `queue_arrival` spread relative to precision. **Bounds** approach: without those metadata, interval could be any of (a)–(c); do not default to (a).

**2. Common start, staggered ends – G2 vs G5 subset**

- *Signature*: `max_start_eq = n`, `max_end_eq =1`, overlap converging-diverging.
- *Explanations*:
  - (a) Operational start batching: operator presses “begin group”, then works items serially (G2 narrative).
  - (b) True concurrent multitasking: one worker interleaves tasks with shared start effort (plausible for cognitive tasks).
  - (c) Shared-account superposition: two analysts started independent tasks coinciding to same minute by chance/rounding, appearing as common start (subset of G5).
- *Discriminators*: source UI design (single begin button present/absent), resource capacity documentation, inter-completion regularity (G2 ~6–7 min suggests serial cadence; random multitask would vary more). Uncertainty remains: even confirming (a), remaining staggered ends still encode true sequential batching – hypothesis not mutually exclusive.

**3. Contiguous adjacency chain – G4 vs G8 drain phase**

- *Signature*: `adjacent_chain = (n-1)/(n-1)`, `overlap0`, uniform durations.
- *Explanations*:
  - (a) Steady-state sequential batching under FIFO discipline with adequate capacity (G4 ideal).
  - (b) Backlog drain after capacity loss/downtime – arrival accumulation during idle gap followed by catch-up at max rate (G8). Same chain shape but preceded by `gap_arrival_to_first_start  service_time` and `queue_span` building during gap.
  - (c) Paced takt line where adjacency enforced by conveyor, not queue discipline.
- *Discriminators*: pre-chain idle interval correlation with external event (G8 safety-check 15:00–35), arrival curve `L(t)`, and change in waiting vs baseline. Conflation risks misclassifying G8 drain efficiency as normal load versus recovery surge; bottleneck responsibility assigned to repair station instead of safety blockage.

All three demonstrate why PM4Py’s `merge_distance`-defined batch must be crossed with arrival-process, recording-lag, precision, and resource-capacity evidence before asserting physical concurrency.

Bounds summary: Where hypotheses overlap, report **interval estimates** (e.g., service  [inter-completion time, reported S]) and **hypothesis-weighted confidence** rather than forced choice. Document assumptions A1–A4 alongside each inference.

# 6. Data-collection redesign

Prioritized, incremental (P0 immediate fix  P3 structural improvement). Addresses all required topics.

**P0 – Separate execution vs recording timestamps and synchronize clocks**
- Retain mandatory per-event fields: `event_time_utc` (when activity state actually changes) vs `recorded_at_utc` (DB insert) with millisecond ISO-8601 UTC and NTP-synced sources. Currently `recorded_at` mixes seconds and minutes and downstream uses `start` erroneously. For G6 this alone prevents inflated waiting/zero service conflation.
- Deploy central NTP, log `clock_skew_ms` per source (critical for G8 cross-clock comparison). Reject manual corrections without `modified_by` trace.

**P0 – Unique worker identity (fix shared-account artefact)**
- Replace `analyst_pool` shared VDI login with SSO badge tap  `resource_id` (badge) + `session_id` + pooled `team_id`. Enforce 1:1 credential:task assignment; retain fallback `proxy_for` field if delegation occurs. Enables G5 disaggregation and valid utilization/bottleneck detection.
- Add workstation capacity field `station_capacity_parallel_items` (e.g., RBT-7=4) and `fixture_id` to distinguish legal parallelism from overload.

**P1 – Explicit batch/group identifiers and parent-child linkage**
- Introduce `batch_id`, `batch_type  {physical_parallel, setup_shared, submission_folder, transport}`, `batch_size`, `parent_case_id` (fixture/pallet/folder) + child item cases. PLC emits batch_start/batch_end + per-slot events; tablet “begin group” creates parent record linked to children (G2); desktop form “release folder” records per-review completions then folder submission event separately (G3). Eliminates inference from coincident timestamps.
- Scanner/pack stations emit `sequence_position_in_batch` and `preceding_case_id` to make G4/G8 adjacency explicit rather than temporally guessed.

**P1 – Pause / resume / block events**
- Log `resource_state_change` events: `AVAILABLE/BLOCKED/DOWN/PAUSE` with reason codes (safety_check, break, maintenance) from authoritative source, with synchronized timestamps. G8 idle correctly attributed to blocking event stream, not station inefficiency. Supports Little’s Law conditioning `waiting | available`.

**P1 – Timestamp precision metadata as structured interval**
- Replace free-text `precision` with machine-readable: `timestamp_resolution_reported` (1 s, 1 min, 15 min), `truncation_rule` (floor/round/ceil/unknown), `accuracy_sigma` and `censored_interval [earliest, latest)` per event. Consumers forced to use interval-censored arithmetic for G7 coarse MES; legacy MES configured to emit raw sensor time + rounded display time dual fields until decommissioned.

**P2 – Capture execution lifecycle faithfully**
- Enforce lifecycle validation: `start  complete`, `complete  recorded_at`, duration >0 except instantaneous milestones flagged `is_milestone=true`. Tablet/desktop UI: separate “start individual item” tap (or auto-start on scan) and “complete” to avoid common-start/end artefacts; disable bulk edit of `start` in bulk forms (G6). Provide offline buffering with later `event_time` preserved vs `sync_time`.

**P2 – Enriched workstation/queue telemetry**
- Emit periodic `queue_depth_snapshot` from upstream feeder, not just `queue_arrival` per case, to monitor build-up during downtime independently of later processing events. Validates G8 backlog magnitude without relying on case timestamps alone.

**P3 – Validation and observability**
- Automated data-quality monitors: alert on `max_start_eq 3` with 1-min precision, `duration==0` batches >2, `overlap >1` per human resource, `recording_lag > precision+5 min`, clock drift >2 s. Dashboards contrast PM4Py-detected batches vs interval-censored diagnostics (Section 4 code promoted to pipeline) to catch emerging start/end batching practices (e.g., new folder workflow in G3).

Implementation sequence yields immediate protection against worst biases (G5 identity, G6 logging-batch masquerade, G7 rounding) while building toward operational-batch transparency.

# 7. Final adjudication

**Interpretable with high confidence without further fieldwork (use with documented correction):**

- **G1 – genuine simultaneous batch.** Confident operational parallel batch; performance analysis must treat as batch capacity 4 × 3 min cycle. Low residual risk (<7%) of PLC end-signal aggregation; confirm via PLC program spec that all slots released together.
- **G4 – sequential batching reference.** Gold standard for queue/service metrics; can serve as calibration for throughput/utilization models and PM4Py parameter tuning. No exclusion needed.
- **G6 – logging batch (instantaneous submission).** Very high confidence NOT execution data. Must be excluded from service-time, active-utilization, and conformance timing. Allowed only as `submission_event` bounding waiting from above.

**Usable for performance analysis only with interval censoring / corrected logic:**

- **G2 – start batching.** Usable if `start` recast: per-item service  inter-completion interval (6–7 min) not 8–27 min. Report waiting conditioned on interval-censored start. Recommend re-instrumentation of individual start taps; till then publish bounds.
- **G3 – end batching.** Usable analogously with `complete` interval-censored to submission burst. Early items’ service overstated 3–4× if naive; correct via serial reconstruction.
- **G7 – timestamp coarsened.** Unsuitable for point-estimate waiting/service/overlap. Publish only 15-min censored intervals and sequence order from `recorded_at`; queue-length-at-bin inference limited. Requires legacy MES fix before inclusion in SLA analysis.
- **G8 – queue accumulation + drain.** Overall pattern usable, but waiting must be partitioned into `blocked` (safety-check attribution) vs `queuing_drain`. Throughput/bottleneck conclusions require clock synchronization validation (~±2 min uncertainty). Include only `available-period` utilization in capacity planning.

**Require operational validation before any performance conclusion:**

- **G5 – shared-account pooling.** Cannot be interpreted as single-resource performance; individual productivity, compliance, or load-balancing conclusions invalid until badge-level reassignment or supervised sampling confirms per-analyst ownership. Pool-level throughput may be reported with “unallocated labor pool” disclaimer.
- **G2/G3 operational intent** (confirm group-button vs end-folder practice via shadowing) and **G8 clock alignment / safety-stop duration** need confirmation from maintenance logs to certify that 35-min gap indeed caused queue, not coincidental break. For G2/G3, 1-day time-motion study with stopwatch vs tablet stamps quantifies start/end bias magnitude for retrospective correction factors.
- **G1 fixture verification** optional high-value check: observe one full load-unload cycle to rule out staggered loading masked inside 09:00 reported start (unlikely given PLC resolution).

**Summary action rule:**  
Include G1 & G4 directly; include G2, G3, G8 after deterministic censoring/partitioning described; exclude G5 individuated metrics and G6 timing; treat G7 as ordinal-only. Any report mixing these tiers must display tier flags and assumption log A1–A4 to prevent PM4Py temporal batches being misread as physical efficiency or failure.
