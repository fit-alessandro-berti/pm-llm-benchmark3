> **Why bidirectional DFG  concurrency proof:** DFG counts direct succession in completion order. Both `AB` and `BA` occur if (i) truly concurrent tasks race, (ii) process is `XOR(SEQ(A,B), SEQ(B,A))` - two sequential variants, (iii) activities overlap and duration varies, (iv) identical timestamps ordered arbitrarily (S7). No information about start times, resources or enabling. Inductive miners that threshold bidirectional edges into `AND` over-generalize when sample is small.

# 2. Shared Assumptions

1.  **Event-completion semantics:** Log records `complete` lifecycle transition only (S7). No `start` timestamps. Therefore `directly-follows` means *completed before next completed*, not *enabled after*. All models are interpreted under completion semantics; partial orders are *completion-before* constraints.
2.  **Missing Supplier Confirmation:** Following S5, 5–10% of SC events may be absent due to integration failure. The latent attribute `component_type  {external, stocked}` was not exported, so we cannot separate `stocked  legitimately no SC` (S4) from `external + lost SC`. All three models represent this with **control-flow optionality** `XOR(SC, )` - an explicit abstraction. It *conflates* true optionality and missingness; disclosed as limitation. No model attempts data-aware condition.
3.  **Absent attribute:** No data condition on SC decision; we do not synthesize a fake guard. Validation cannot distinguish precision loss due to `stocked` vs noise.
4.  **Optionality representation:** Optional activities modelled as `XOR(activity, silent)` (ProcessTree) or `OperatorPOWL( XOR, [activity, SilentTransition])` (POWL). Silent transitions have zero business meaning.
5.  **At-most-once:** D6: Expedite occurs 1. All models use optional single occurrence, not a loop. No model allows multiple Expedite Reviews.
6.  **Mandatory checks:** CC and ER occur exactly once per case (D3). No skips, no loops, no duplication within a case (except XOR-enumeration duplicates across branches - see §3).
7.  **Fixed endpoints:** Register Order is first, Archive Case last, ApproveReleaseArchive is invariant (D1,D2).
8.  **Soundness:** All candidates designed to be sound workflow nets (no deadlocks, proper completion).
9.  **Infinite language handling:** Where language is infinite (loops would be), enumeration is bounded. Sampling does not prove inclusion.

# 3. Conservative Candidate

**Inductive bias:** *Enumerate what was seen, forbid what was not.* Maximizes precision / minimizes false positives at cost of recall. Assumes log is essentially complete for allowed behavior, SC skips are taken at face value only in observed CC/ER orders, and CCER bidirectionality reflects two distinct sequential variants (XOR), not concurrency. Admits no unseen interleavings; any unobserved permutation is treated as suspicious until more evidence. Overfits by design.

**Formal expression:**
```
SEQ( Register,
  XOR(
    SEQ(CC, ER, SC, Approve, Release, Archive)          // V1 12×
    SEQ(ER, CC, SC, Approve, Release, Archive)          // V2 7×
    SEQ(CC, ER, Approve, Release, Archive)              // V3 4×
    SEQ(ER, CC, Approve, Release, Archive)              // V4 3×
    SEQ(CC, SC, ER, Approve, Release, Archive)          // V5 2×
    SEQ(CC, ER, SC, Expedite, Approve, Release, Archive) // V6 1×
    SEQ(ER, CC, Expedite, SC, Approve, Release, Archive) // V7 1×
  )
)
```
Duplicate labels introduced intentionally; each branch has its own `CC`, `ER` leaf. POWL equivalent would need duplication.

**PM4Py code:**
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def seq(*children):
    pt = ProcessTree(operator=Operator.SEQUENCE)
    pt.children = list(children)
    for c in pt.children:
        c.parent = pt
    return pt

def xor(*children):
    pt = ProcessTree(operator=Operator.XOR)
    pt.children = list(children)
    for c in pt.children:
        c.parent = pt
    return pt

# 7 observed variants enumerated exactly
v1 = seq(leaf("Credit Check"), leaf("Engineering Review"), leaf("Supplier Confirmation"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v2 = seq(leaf("Engineering Review"), leaf("Credit Check"), leaf("Supplier Confirmation"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v3 = seq(leaf("Credit Check"), leaf("Engineering Review"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v4 = seq(leaf("Engineering Review"), leaf("Credit Check"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v5 = seq(leaf("Credit Check"), leaf("Supplier Confirmation"), leaf("Engineering Review"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v6 = seq(leaf("Credit Check"), leaf("Engineering Review"), leaf("Supplier Confirmation"), leaf("Expedite Review"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v7 = seq(leaf("Engineering Review"), leaf("Credit Check"), leaf("Expedite Review"), leaf("Supplier Confirmation"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))

model_conservative = seq(leaf("Register Order"), xor(v1, v2, v3, v4, v5, v6, v7))
```

*Duplicate labels & scalability note:* This tree duplicates `Credit Check` 7 times etc. Precision is maximal but (a) prevents mining of common causal structure, (b) size `O(variants * activities)` grows linearly - untenable beyond ~20 variants, (c) precision metrics overestimate due to label duplication - alignments distinguish leaves by position but real logs cannot, (d) generalization to any new interleaving requires tree surgery. It is the appropriate extreme for compliance auditing, not discovery.

**Behavior deliberately excluded:**
- Any SC interleaving not seen, e.g., `ER, SC, CC` or `CC, ER, Expedite, CC` impossible by duplication
- `CC, ER, SC, SC...` (multiple SC)
- `Expedite` after both checks but in position `CC, SC, Expedite, ER` 
- Simultaneous/conclusive `CC || ER` - only two sequential orders allowed
- `Expedite` without both checks, or `Expedite` after Approve
- `SC` optional outside observed orders (e.g., `ER, CC, SC` with Expedite without SC is not in this branch set beyond those enumerated)
- Any repetition, loop, or skipping of mandatory `CC/ER/Approve/Release/Archive`

**Known underfitting risks (actually overfitting risks):**
- **Overfitting / low generalization:** Future legitimate `CCER` concurrent execution or `ERSCCC` that satisfies D5 will be rejected as non-conforming.
- **False non-compliance:** 5-10% missing SC cases will be flagged as `SC skipped` violation when they may be logging loss; model has no robustness to missing SC.
- **Brittle to new Expedite position:** Valid `CC, ER, Expedite, Approve` (Expedite without SC - plausible per S6) is rejected despite being permitted by D6 if SC is skipped for stocked items.
- **No concurrency benefit:** Performance analysis will double-count sequential waiting.

# 4. Balanced Candidate

**Inductive bias:** *Most plausible generalization balancing evidence, domain rules, and uncertainty.* Interprets CCER bidirectionality (S2, D7) as true concurrency (`AND`/`partial order`) rather than XOR, adopts D5 literally (SC needs only one predecessor), treats SC optionality as legitimate (S4) but acknowledged conflated with missingness, and makes Expedite optional and unordered vs SC while strictly after both checks (D6,S6). Central tradeoff: allow all and only interleavings that respect D1-D6 and observed V5/V7 partial-order fragments.

**Formal expression (POWL):**
```
SEQ( Register,
  StrictPartialOrder {
    nodes = { CC, ER, SC_XOR, EXP_XOR }
    SC_XOR  = XOR(SC, )
    EXP_XOR = XOR(Expedite, )
    edges = {
      CC   SC_XOR,      // SC cannot be before CC (need at least one predecessor)
      CC   EXP_XOR,     // Expedite after CC
      ER   EXP_XOR      // Expedite after ER (= after both)
      // NO edge ERSC_XOR   SC concurrent with ER (allows CCSCER)
      // NO edge SC_XOREXP_XOR  SC and Expedite unordered (both V6 and V7)
    }
  },
  SEQ(Approve, Release, Archive)
)
```
Outer SEQ enforces D1,D2,D3,D4 (SCApprove implicitly via PO placed before Approve). Inner PO encodes concurrency decisions explicitly.

**PM4Py code:**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# Transitions
t_register = Transition(label="Register Order")
t_cc = Transition(label="Credit Check")
t_er = Transition(label="Engineering Review")
t_sc = Transition(label="Supplier Confirmation")
t_exp = Transition(label="Expedite Review")
t_app = Transition(label="Approve Configuration")
t_rel = Transition(label="Release Production")
t_arc = Transition(label="Archive Case")

# Optional wrappers: XOR(activity, tau)
sc_opt = OperatorPOWL(operator=Operator.XOR, children=[t_sc, SilentTransition()])
exp_opt = OperatorPOWL(operator=Operator.XOR, children=[t_exp, SilentTransition()])

# Inner partial order: checks + optional SC + optional Expedite
po_inner = StrictPartialOrder(nodes=[t_cc, t_er, sc_opt, exp_opt])
# D5: SC after CC, concurrent with ER
po_inner.order.add_edge(t_cc, sc_opt)
# D6/S6: Expedite after BOTH CC and ER
po_inner.order.add_edge(t_cc, exp_opt)
po_inner.order.add_edge(t_er, exp_opt)
# No edge ER->SC (allows CC SC ER) ; No edge SC<->Exp (allows both orders)

# Outer order: Register -> po_inner -> Approve -> Release -> Archive
model_balanced = StrictPartialOrder(nodes=[t_register, po_inner, t_app, t_rel, t_arc])
model_balanced.order.add_edge(t_register, po_inner)
model_balanced.order.add_edge(po_inner, t_app)
model_balanced.order.add_edge(t_app, t_rel)
model_balanced.order.add_edge(t_rel, t_arc)
```

**How sequence/concurrent/partial-order decisions made:**

- **CC vs ER:** Chose **concurrency (partial order, no edge)**. Evidence: `17 vs 11` bidirectional with near-even split and stakeholder claim of parallelism (S2). Domain D7 says order does not prove causality. XOR would require assuming two intentional sequential models; concurrency is simpler and more plausible given S2 and equal frequency. Sequence `CCER` (S1) rejected because V2,V4,V7 contradict.
- **SC vs CC/ER:** Chose **asymmetric partial order: SC after CC, concurrent with ER**. Rationale: V5 (`CC, SC, ER`) proves SC need not wait for both, supporting D5. D5 says after *either* - so SC must wait for at least one. Minimal edge `CCSC` achieves this while allowing SC before/after ER. Alternative `AND(CC,ER)SC` would forbid observed V5; `no edge` would allow `SC before CC` (violates D5 intuition and never observed). We explicitly document that `ERSCCC` is still forbidden; if future data shows it, model would need `OR` dependency (not expressible directly in POWL - would need XOR of two POs).
- **SC vs Expedite:** Chose **unordered (no edge)**. Direct evidence V6 `SCExp` and V7 `ExpSC`. D6/S6 state Expedite may be before or after SC. Therefore partial order.
- **Expedite vs CC/ER:** Chose **strict sequence after both** (`CCExp`, `ERExp`). D6 medium confidence + both observed Expedite traces respect it; no counter-example. This is sequence, not concurrency.
- **Approve/Release/Archive:** Strict sequence per D1/D2.

**Behavior deliberately excluded:**
- Missing CC or ER, multiple CC/ER/Expedite
- SC before CC (and before both checks)
- Expedite before either CC or ER, or after Approve
- Release without Approve
- Concurrent Approve with checks

**Known underfitting / overfitting risks:**
- **Under-constraining SC:** Allows `ER, CC, SC` and `CC, ER, SC` and `CC, SC, ER` but also allows `ER` concurrent with `SC` completing after `Approve`? No, because PO before Approve prevents. Still allows `CC, ER` concurrent with `SC` completing *after* `CC` but *overlapping* `ER` - considered plausible, low risk.
- **Still forbids `ERSCCC`** - if D5's "either" is symmetric, this is overfitting. Could be seen as asymmetric bias toward CC.
- **Precision risk:** Admits unobserved but plausible `CC, ER, Expedite, Approve` (SC skipped + Expedite present) - never observed; may be plausible for stocked expedited orders but unverified.
- **Silent-option abstraction:** Cannot distinguish stocked skip vs missing SC; fitness may be inflated.

# 5. Permissive Candidate

**Inductive bias:** *Admit any reasonable behavior consistent with high/medium domain rules, even if unobserved.* Prioritizes recall/generalization over precision. Interprets SC optionality as fully legitimate and robust to missingness, interprets CC/ER as fully concurrent, interprets SC(CC,ER) as maximally concurrent (SC may occur any time after start, before Approve), and Expedite as optional unordered vs SC. Used for exploration, what-if analysis, not compliance.

**Formal expression (ProcessTree - permissive):**
```
SEQ( Register,
  AND( Credit Check, Engineering Review, XOR(Supplier Confirmation, ) ),
  XOR(Expedite Review, ),
  Approve Configuration, Release Production, Archive Case
)
```
*Alternative reading:* `AND` = true concurrency. SC concurrent with both checks inside AND; Expedite optional after the AND but still before Approve. This admits any interleaving of CC,ER,SC (when SC present). Expedite fixed after checks+SC for simplicity; more permissive variant would put Expedite inside AND with dependency edges, but tree cannot encode `Exp after both` while also `SC concurrent`.

A strictly more permissive POWL variant would be:
```
SEQ( Register, PO{ CC, ER, SC_XOR, EXP_XOR ; edges = CCEXP, EREXP }, Approve, Release, Archive )
with NO edge to SC  SC fully concurrent.
```
We implement the tree version as primary (simpler) and document the POWL alternative as boundary.

**PM4Py code:**
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def seq(*children):
    pt = ProcessTree(operator=Operator.SEQUENCE)
    pt.children = list(children)
    for c in pt.children: c.parent = pt
    return pt

def xor(*children):
    pt = ProcessTree(operator=Operator.XOR)
    pt.children = list(children)
    for c in pt.children: c.parent = pt
    return pt

def and_node(*children):
    pt = ProcessTree(operator=Operator.PARALLEL)
    pt.children = list(children)
    for c in pt.children: c.parent = pt
    return pt

tau = ProcessTree(label=None)  # silent
sc_opt = xor(leaf("Supplier Confirmation"), tau)
# SC concurrent with checks inside AND; Expedite optional after
model_permissive = seq(
    leaf("Register Order"),
    and_node(leaf("Credit Check"), leaf("Engineering Review"), sc_opt),
    xor(leaf("Expedite Review"), ProcessTree(label=None)),
    leaf("Approve Configuration"),
    leaf("Release Production"),
    leaf("Archive Case")
)
# Note: this tree still enforces Expedite after checks (via SEQ after AND)
# SC has no predecessor edge  allows SC before CC/ER (more permissive than D5)
```

**Boundary between reasonable generalization and forbidden:**

*Admitted (reasonable):*
- Any permutation of CC,ER,SC before Approve
- SC skipped (stocked or missing)
- Expedite skipped or occurring after checks, before/after SC (depending on implementation)
- Concurrent execution

*Still forbidden (clearly undesirable) even in permissive:*
- Skipping CC, ER, Approve, Release, Archive (violates D2,D3)
- Register not first or Archive not last (D1)
- SC after Approve or Expedite after Approve
- Expedite without both CC and ER (D6)
- Multiple occurrences of any activity
- Release before Approve

**Behavior deliberately excluded (vs infinite):**
- No loops/rework
- No cancellation

**Known underfitting risks (low precision):**
- **Allows `SC before CC and ER`** (e.g., `Register, SC, CC, ER, Approve...`) - never observed, violates D5 intuition, but admitted for maximal permissiveness; disclosed as over-generalization tradeoff.
- **Allows `CC, ER` interleaved with `SC` in any order** including rare `ER, SC, CC` which balanced forbid.
- **Allows `Expedite` without `SC` + `SC` concurrency** - may be unrealistic for external components where SC mandatory (S3).
- **Low precision:** Will accept many unobserved traces, poor for compliance; high generalization deliberately.

# 7. Comparative Model Matrix

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|
| **Expected fitness on 30 observed cases** | **1.0** (perfect, exact enumeration) | **1.0** (all 30 fit; SC optional + CCER covers all) | **1.0** (all 30 fit; super-set) |
| **Expected precision risk** | **Very High precision (0.95-1.0 interval)** - admits almost nothing beyond log | **Medium-High precision (~0.6-0.8)** - admits plausible unseen interleavings, moderate over-approximation | **Low precision (~0.3-0.5)** - admits many unseen permutations (e.g., SC before checks) |
| **Generalization potential** | **Very Low** - no generalization beyond 7 variants; fails on new valid interleavings | **Medium-High** - best tradeoff; generalizes to concurrency and optional SC/Exp patterns supported by D5/D6 | **High** - maximal generalization; will fit future external/stocked and expedite combos |
| **Structural simplicity** | **Low simplicity** - 7 branches, 35+ nodes, duplicate labels; `size  variants` | **Medium** - 1 POWL with 5 nodes + 2 XORs + 3 edges; compact | **High simplicity** - 1 SEQ+AND+XOR, ~9 nodes; most readable |
| **Explainability** | **Low** - "because we saw it" not causal; duplicates confuse stakeholders | **High** - explicit partial order maps to domain rules D5/D6 | **Medium-High** - easy to explain but must justify why SC before checks allowed |
| **Robustness to missing SC events (S5)** | **Brittle** - treats missing SC as intentional skip only in observed orders; S5 noise causes false non-conformance | **Robust** - optional SC absorbs both legitimate skip and 5-10% missing; but conflates | **Very Robust** - same, even more tolerant |
| **Handling of unseen interleavings** | **Rejects all unseen** - e.g., `ER SC CC` flagged non-conforming | **Accepts plausible unseen that respect partial order** - e.g., `CC SC ER + Exp` | **Accepts all permutations respecting mandatory before Approve** |
| **Suitability for compliance vs exploration** | **Best for compliance / audit**: minimal false positives, proves deviations | **Best for operational use / monitoring**: balanced false positive/negative | **Best for exploration / what-if / simulation**: discovers possibilities, worst for enforcement |

*Qualitative intervals used deliberately; exact numbers depend on alignment implementation and silent-transition costing. Do not invent 0.873 precision without log-based calculation (see §8).*

# Self-contained validation for all three candidates
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

# ------------------------------------------------------------
# 1. Reconstruct 30-case log
# ------------------------------------------------------------
trace_variants = [
    ("Register Order, Credit Check, Engineering Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case", 12),
    ("Register Order, Engineering Review, Credit Check, Supplier Confirmation, Approve Configuration, Release Production, Archive Case", 7),
    ("Register Order, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case", 4),
    ("Register Order, Engineering Review, Credit Check, Approve Configuration, Release Production, Archive Case", 3),
    ("Register Order, Credit Check, Supplier Confirmation, Engineering Review, Approve Configuration, Release Production, Archive Case", 2),
    ("Register Order, Credit Check, Engineering Review, Supplier Confirmation, Expedite Review, Approve Configuration, Release Production, Archive Case", 1),
    ("Register Order, Engineering Review, Credit Check, Expedite Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case", 1),
]

log_strings = []
for trace_str, cnt in trace_variants:
    log_strings.extend([trace_str] * cnt)

# pm4py API: list of comma-separated trace strings
log = pm4py.parse_event_log_string(log_strings)
print(f"Log: {len(log)} traces, {sum(len(t) for t in log)} events")

# 2. Build models (re-define for self-containment)
# ------------------------------------------------------------
def leaf(label):
    return ProcessTree(label=label)
def seq_pt(*children):
    pt = ProcessTree(operator=Operator.SEQUENCE)
    pt.children = list(children)
    for c in pt.children: c.parent = pt
    return pt
def xor_pt(*children):
    pt = ProcessTree(operator=Operator.XOR)
    pt.children = list(children)
    for c in pt.children: c.parent = pt
    return pt
def and_pt(*children):
    pt = ProcessTree(operator=Operator.PARALLEL)
    pt.children = list(children)
    for c in pt.children: c.parent = pt
    return pt

# Conservative: XOR enumeration
v1 = seq_pt(leaf("Credit Check"), leaf("Engineering Review"), leaf("Supplier Confirmation"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v2 = seq_pt(leaf("Engineering Review"), leaf("Credit Check"), leaf("Supplier Confirmation"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v3 = seq_pt(leaf("Credit Check"), leaf("Engineering Review"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v4 = seq_pt(leaf("Engineering Review"), leaf("Credit Check"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v5 = seq_pt(leaf("Credit Check"), leaf("Supplier Confirmation"), leaf("Engineering Review"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v6 = seq_pt(leaf("Credit Check"), leaf("Engineering Review"), leaf("Supplier Confirmation"), leaf("Expedite Review"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
v7 = seq_pt(leaf("Engineering Review"), leaf("Credit Check"), leaf("Expedite Review"), leaf("Supplier Confirmation"), leaf("Approve Configuration"), leaf("Release Production"), leaf("Archive Case"))
model_conservative = seq_pt(leaf("Register Order"), xor_pt(v1,v2,v3,v4,v5,v6,v7))

# Balanced: POWL
t_register = Transition(label="Register Order")
t_cc = Transition(label="Credit Check")
t_er = Transition(label="Engineering Review")

po_inner = StrictPartialOrder(nodes=[t_cc, t_er, sc_opt, exp_opt])
po_inner.order.add_edge(t_cc, sc_opt)
po_inner.order.add_edge(t_cc, exp_opt)
po_inner.order.add_edge(t_er, exp_opt)
model_balanced = StrictPartialOrder(nodes=[t_register, po_inner, t_app, t_rel, t_arc])
model_balanced.order.add_edge(t_register, po_inner)
model_balanced.order.add_edge(po_inner, t_app)
model_balanced.order.add_edge(t_app, t_rel)
model_balanced.order.add_edge(t_rel, t_arc)

tau1 = ProcessTree(label=None)
tau2 = ProcessTree(label=None)
sc_opt_pt = xor_pt(leaf("Supplier Confirmation"), tau1)
model_permissive = seq_pt(
    leaf("Register Order"),
    and_pt(leaf("Credit Check"), leaf("Engineering Review"), sc_opt_pt),

    leaf("Release Production"),

for name, model in [("conservative", model_conservative), ("balanced", model_balanced), ("permissive", model_permissive)]:

        simp = pm4py.simplicity_petri_net(net, im, fm)
        print(f"[{name}] fitness={fit} precision={prec} generalization={gen} simplicity={simp}")
    except Exception as e:

# 5. Bounded / sampled playout (does NOT prove language inclusion)

for name, model in [("conservative", model_conservative), ("balanced", model_balanced), ("permissive", model_permissive)]:
    try:

        net, im, fm = pm4py.convert_to_petri_net(model)

        playout_log = pm4py.play_out(net, im, fm, parameters={"num_traces": 20})

# ------------------------------------------------------------
positive_traces = [
    "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case",
    "Register Order, Credit Check, Supplier Confirmation, Engineering Review, Approve Configuration, Release Production, Archive Case",
    "Register Order, Credit Check, Engineering Review, Expedite Review, Approve Configuration, Release Production, Archive Case",  # plausible but unobserved
]
negative_traces = [
    "Register Order, Supplier Confirmation, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case", # SC before checks
    "Register Order, Credit Check, Engineering Review, Approve Configuration, Expedite Review, Release Production, Archive Case", # Exp after Approve
    "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Release Production, Archive Case", # missing Approve
]

def check_trace(trace_str, model, name):
    from pm4py.objects.log.obj import EventLog, Trace, Event
    # Build single-trace log
    tlog = EventLog()
    tr = Trace()
    for act in trace_str.split(", "):
        ev = Event()
        ev["concept:name"] = act
        tr.append(ev)
    tlog.append(tr)
    try:
        net, im, fm = pm4py.convert_to_petri_net(model)
        # Use alignments fitness 1.0 as proxy for acceptance; or pm4py.conformance_diagnostics_alignments
        from pm4py.algo.conformance.alignments.petri_net import algorithm as align_algo
        aligned = pm4py.fitness_alignments(tlog, net, im, fm)
        # fitness dict contains log_fitness
        fit = aligned.get("log_fitness", aligned.get("averageFitness", 0))
        conforms = fit >= 0.999
        print(f"  {name} {'ACCEPTS' if conforms else 'REJECTS'}: {trace_str} (fit {fit:.3f})")
        return conforms
    except Exception as e:
        print(f"  {name} check error {trace_str}: {e}")
        return None

for name, model in [("conservative", model_conservative), ("balanced", model_balanced), ("permissive", model_permissive)]:
    print(f"\n--- {name} positive suite ---")
    for tr in positive_traces:
        check_trace(tr, model, name)
    print(f"--- {name} negative suite ---")
    for tr in negative_traces:
        check_trace(tr, model, name)

print("\nLIMITATION: Fitness/precision via alignments are estimates; exhaustive language comparison is undecidable for infinite languages; sampling does not prove inclusion.")

# 9. Recommendation and Data-Collection Plan

**Recommendation:**

- **Immediate operational use (monitoring, production planning): `model_balanced` (POWL).** It best reflects domain rules D1-D6, respects observed interleavings V5/V7, treats concurrency correctly, absorbs S5 missingness without over-generalizing to `SC before checks`. It offers best precision-recall tradeoff, remains interpretable for stakeholders, and will not flood compliance alerts like permissive nor reject valid future expedited-stocked cases like conservative.

- **Sensitivity analysis / what-if exploration: `model_permissive` (ProcessTree).** Use alongside balanced to quantify upper bound of allowed behavior. Any trace accepted by permissive but rejected by balanced is exactly the set of `risky generalizations` (e.g., `ERSCCC`, `SC before both`). Monitoring gap between their conformance rates estimates impact of D5 uncertainty.

- **`model_conservative` retained for compliance audit** where false positives are more costly than false negatives (e.g., external audit proving deviation). Do not use for discovery.

**Data-Collection Plan to resolve ambiguities:**

1.  **Lifecycle timestamps:** Collect `enable, start, complete` for each activity (especially CC, ER, SC, Expedite). Currently only `complete`. This directly distinguishes `XOR(SEQ)` vs `AND` (concurrent enable) and measures overlap. Add `resource` and `workstation` attributes.

2.  **Restore missing attribute:** Export `component_type` (external/stocked) and `supplier_id` / `stocked_flag`. This separates S3 vs S4 (mandatory vs optional SC) and lets us learn a data-aware decision: `if external then SC else `. Without it, any control-flow optional is confounded.

3.  **Fix integration gap:** Log SC with idempotency key; add audit table for SC events that failed to ingest (S5). Measure true missing rate. Cross-validate 5-10% estimate.

4.  **Expedite trigger:** Record `expedite_reason, requester, timestamp of request`. Validates D6 1 and whether Expedite is truly after both checks or can be requested earlier.

5.  **Maximally informative future traces to collect:**
    - `Register, CC, ER, Expedite, Approve, Release, Archive` (SC skipped + Expedite present) - distinguishes whether balanced's allowance of this is correct.
    - `Register, ER, SC, CC, Approve, Release, Archive` (mirror of V5) - symmetric test of D5. If observed, balanced's asymmetric `CCSC` is wrong; need symmetric OR.
    - `Register, SC, CC, ER, Approve...` - if ever observed, permissive's extra permissiveness is validated.
    - `Register, CC, SC, Expedite, ER, Approve...` - interleaved SC+Exp between checks; tests PO concurrency.
    - A case with two SC events (rework) - tests at-most-once assumption.
    - Cases with identical completion timestamps - to quantify S7 tie-break impact.

6.  **Experimental design:** For 4 weeks, enforce logging of start times for 100% of cases; A/B: route 50% of stocked components explicitly without SC and tag, to measure baseline. Monitor precision drift between conservative vs balanced on new log; if balanced precision drops <0.6, tighten.

7.  **Validation loop:** Re-run `pm4py.discover_dfg` with `start`/`complete` separation; compute `partial order` via `pm4py.discover_powl` or `inductive with lifecycle`. Compare discovered PO to hypothesized PO.

# 10. Uncertainty Statement

**Calibrated confidence:**

- **Register...Archive mandatory endpoints & ApproveRelease:** **95%** - high confidence (D1,D2, 30/30).
- **Both CC and ER mandatory before Approve:** **85%** - medium-high (D3) but could be challenged if future log shows skipping under delegation.
- **Expedite after both CC/ER, before Approve, 1, optional, unordered vs SC:** **75%** - medium (D6,S6) - n=2 is weak but domain consistent. Alternative where Expedite could be triggered after only one check is plausible **25%**.
- **CC and ER are concurrent (not XOR sequential):** **70%** - best interpretation of `11 vs 17` + S2 + D7, but **30%** chance true model is `XOR(SEQ(CC,ER), SEQ(ER,CC))` with no overlap, especially if resources are single-threaded.
- **SC optional (stocked) vs missingness:** **65%** that optionality is real (S4 explains >5-10% gap). **35%** that 23% skips are mostly missing logs and SC is near-mandatory (S3). Shared abstraction `XOR(SC,)` is correct under both, but precision interpretation changes materially.
- **SC dependency "after either CC or ER":** **60%** for balanced asymmetric `CCSC` as adequate approximation; **40%** that true dependency is symmetric OR (`CCSC  ERSC`) or even fully concurrent (permissive). Observation V5 alone insufficient to decide.
- **SCExpedite unordered:** **80%** - V6+V7 + S6 strongly support.

**Plausible alternative that would materially change recommendation:**

*Alternative hypothesis:* **SC is actually mandatory for all external cases, and 7/30 skips are entirely due to 23% missing SC (S5 underestimated) plus SC always requires both CC and ER (D5 misinterpreted). Under this, CC and ER are strictly sequential `CCER` per S1 (finance) and `SCER` 2 cases are logging errors where ER completion was delayed in system.**

If this alternative is true, then **conservative** (or a sequential `SEQ(CC,ER,SC)` variant) would be correct, **balanced and permissive would be over-generalizing dangerously**, allowing stocked-type cases that are actually non-compliant external orders with lost SC. Recommendation would flip to **conservative for immediate compliance, and data-collection priority would be fixing SC integration before any generalization**. A single new attribute (`component_type`) would invalidate balanced's `SCER` edge and halve its language.

A second alternative: **CCER is false concurrency due to S7 ingestion ordering** - true process is always `CCER` but 11 traces had ER logged first due to batch ingestion - would also invalidate balanced's concurrency, making conservative's XOR (with noise) more accurate.

These alternatives motivate the proposed collection of start timestamps and component_type before committing to balanced for audit use.
