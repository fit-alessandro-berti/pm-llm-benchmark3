## 1. Control-Objective Decomposition

## 2. Equivalence and Sufficiency Test

A compensating package is not judged by mere presence of events. Judgment requires seven dimensions.

**Dimensions:**

1.  **Timing:** Before Release vs ReleaseSettlement window vs Post-Settlement. Preventive > interceptive > detective. Settlement is normally irrevocable for internal control purposes. A late audit after the 24h recall window cannot correct.
2.  **Independence:** Is second reviewer distinct human, L3+, no hierarchical pressure (e.g., rater), no credential sharing, no social/familial conflict, not operating same workstation, and actually independent in fact not just in log?
3.  **Coverage:** Which O1-O6 threats are addressed? AV-2 narrow; MG-4 breadth depends on artifacts reviewed (invoice, independent bank-confirmation, PO, receipt, contract, ownership proof).
4.  **Overrideability:** Was control configured as block vs warning? Was warning overridden? Who owned override credential? Shared credential destroys independence even if log shows another name.
5.  **Recoverability:** Can defect still be stopped, recalled, or recovered? Determined by settlement status + audit speed. Within 24h usually possible, after uncertain.
6.  **Evidence Quality:** Did reviewer inspect primary sources or just approve screen? Is there signed checklist, ticket, callback log, service report? Quality distinguishes substantive review from rubber stamp.
7.  **Collusion Resistance:** Does design tolerate single-pair dominance? Rotation, anomaly detection on repeated pairs, workstation separation, rate limits.

**Four-tier verdict scale:**

| Tier | Definition | Required pattern |
|---|---|---|
| **Fully Equivalent** | Package achieves control objective to same practical effect as canonical distinct preparer/releaser before release, with no material residual window. Approvable as conforming, even with nominal violation. | All ED-1 gates satisfied *or* equivalent bundle demonstrated: AV-2 operational and passed without override, independent MG-4 before *both* Release and Settlement with documented review of relevant evidence, amount/tenure/bank-change gates respected given risk, 100% RA-7 within 1 business day within recall window, no independence or collusion indicators. Residual timing risk negligible. |
| **Partially Equivalent** | Substantively mitigated; deviation is technical/tolerable but leaves identifiable gap requiring acknowledgment, remediation, and monitoring. Not fully conforming but not a failure demanding loss recognition or disciplinary escalation on its own. | Strong mitigators present (e.g., independent MG-4 before Settlement, AV-2 pass) but one non-critical gate imperfect: e.g., manager after Release but before Settlement creating short race window, audit 25h vs 24h, token logging delay of minutes but emergency substantiated otherwise, non-critical evidence missing. Coverage mostly complete, independence intact, recoverability preserved enough to have stopped loss had defect existed. Low-medium residual risk. |
| **Merely Mitigating** | Control occurred but insufficient. Reduces expected loss versus nothing, but objective not achieved. Treat as nonconforming; requires corrective action, cannot be waived as equivalent. | Detective-only reliance after settlement, conflicted or rubber-stamp manager, AV-2 warning overridden or unavailable with no alternative, high-value / new-vendor / bank-change-within-7-days combination, audit well beyond recall window, or nominal compliance masking collusion indicators with no independent verification. Significant residual exposure remains. |
| **Ineffective** | No material reduction, or control actively subverted. | Block ignored via shared credential, collusive pair, fabricated evidence accepted, late ratification after settlement presented as control. |

**Why “same expected loss” is not the sole standard:**

Same expected-value-of-loss averaging ignores essentials that four-eyes is designed for: (a) tail-risk distribution — stakeholders are not indifferent between €900k recoverable in 99% of cases and €900k irrecoverable in 1% if the 1% wipes a business unit; amount caps reflect loss-tolerance not expectation; (b) Knightian uncertainty — novel fraud modes not in historical loss statistics, e.g., credential sharing not yet observed; (c) proof and assurance — auditors and regulators require demonstrable segregation, not probabilistic arguments that a single actor is statistically unlikely to cheat; (d) irreversibility and option value — a pre-release second pair preserves ability to investigate without time pressure; post-settlement detective control forfeits that option even if historic recovery rate looks high; (e) incentive effects — allowing convenience single-operator on low amounts normalizes circumvention, eroding culture. Hence equivalence requires timing, independence, coverage, evidence quality, and collusion resistance in addition to modeled loss.

**Chosen semantics for after-Release-but-before-Settlement manager action:** Classified as *interceptive* and scored intermediate: counted toward preventive credit only if (a) bank hold technically enforced between Release and Settlement for that payment rail, (b) manager demonstrated review of necessary artifacts, (c) amount/vendor risk commensurate with short window, and (d) independence uncompromised. AP-207 meets all four; AP-201 meets three of four but emergency justification absent and audit tardiness weaken overall package to Partially, not Fully, equivalent. This nuance avoids equating a control occurrence with sufficiency.

## 5. Counterfactual and Residual-Risk Analysis

Analysis uses qualitative likelihood/impact bands: Negligible/Low/Moderate/High/Critical. Numeric estimates noted explicitly as illustrative only.

**AP-201 — Low-value office-supply, same-user for convenience**
*   Most plausible loss mechanism:* Insider or compromised u17 account redirects low-value payment via subtle bank-master change outside 7-day window or miscoded invoice. AV-2 ownership check would still compare to poisoned register and pass; amount under limit so no flag. Erroneous transfer of €1.8k, or repeated low-value skimming across many convenience bypasses accumulating.
*   Which control breaks chain:* Manager m04 before settlement is the sole breaker. Had m04 inspected bank-detail change history and ownership proof, redirection would be caught before 10:00 settlement queue flush.
*   What remains exposed:* 24-minute unaudited window between Release and Ratify; if settlement rail were instant, loss would be irreversible before m04 viewed queue. Future scaling of convenience behavior normalizes bypass habit, eroding culture. Recall window technically preserved but audit started after recall window, so had m04 missed, second chance degraded.
*   Under truly independent second releaser:* Release at 08:06 would have remained pending until second distinct human actively released after own review, eliminating race window entirely and enforcing discipline. System would queue payment pending second release, providing guaranteed hold. Residual timing risk drops from Moderate to Negligible. Expected improvement is not lower average loss (already low) but elimination of tail timing fragility.
*   Qualitative risk before mitigator: Moderate likelihood of small error, Low impact. After m04: Low likelihood, Low impact, but timing fragility remains Medium at design level.

**AP-202 — 480k new vendor, bank change 2h prior, warning overridden**
*   Most plausible loss mechanism:* Insider-assisted vendor impersonation. Employee relative opens account, attacker changes vendor bank record 2h before payment, insider u23 prepares payment to new account, overrides AV warning using supervisor’s credential. Classic authorized-push-payment fraud enabled by insider.
*   Which control breaks chain:* AV-2 warning correctly fired and would have blocked/held pending escalation. Chain broken **if** warning not overrideable without independent second credential and mandatory bank-callback. Override destroyed this.
*   What remains exposed:* Every subsequent defense collapsed: conflicted manager, late ratification, late audit. Even without collusion, process allowed single point to authorize payee change and pay. Remaining exposed is total amount plus follow-on repetition risk until credential reset.
*   Under independent second releaser:* Second distinct releaser would face fresh AV-2 warning screen stating bank-change recency and limit breach, psychologically and procedurally harder to override than initiator justifying own work. Independent releaser has no incentive to use supervisor credential, likely escalates to procurement to verify change ticket via callback, exposing relative link before funds move. Likelihood of blocking rises from Negligible (actual overridden) to High. Even if colluding pair, distinct credential requirement forces conspiracy breadth larger.
*   Illustrative estimate: Ex ante probability of irreversible loss with overridden warning and conflicted later review approaches High. With enforced independent second release and dual-custody override, probability would fall to Low. Impact Critical in both due to size.

**AP-203 — Critical machine repair, token-before-prepare, manager-before-release**
*   Most plausible loss mechanism:* Overpayment due to pricing error or payment to correct vendor but for unperformed work (service not actually rendered). Fraud less plausible given tenure.
*   Which control breaks chain:* Manager m02 before release reviewing invoice + bank account + service report directly validates O4 receipt. AV-2 pass ensures no duplicate or sanction issue.

*   Under independent second releaser:* Canonical process would add little marginal gain: already have independent human gate before release plus automation plus timely audit. Second releaser would replicate m02 function, perhaps with slightly broader independence as releaser not approver-role conflation, incremental assurance gain from Negligible to essentially same. Demonstrates full equivalence achievable. Counterfactual change outcome unlikely.

**AP-204 — 220k consulting, distinct pair but fabricated receipt**
*   Most plausible loss mechanism:* Substantive fraud: either colluding dyad (u12 fabricates receipt, u13 knowingly releases) or opportunistic unilateral fabrication where releaser performs cursory check due to over-trust built via 37 repeated pairings and shared workstation environment degrading scrutiny. Funds to legitimate-looking vendor but for no-value services.
*   Which control breaks chain:* Neither AV-2 nor distinct releaser broke chain; both blind to receipt authenticity. Only substantive manager review of deliverables, contract outcomes, and independent receipt confirmation, or rigorous rotation/re-performance audit within recall window, could have broken chain. Actual detective audit 4 days later identified fabrication but outside recall window.
*   What remains exposed:* Recurring payment relationship now compromised; 37 payments population may contain duplicates. Recoverability after settlement dependent on civil claim not bank recall. Organizational blindness to pairing analytics perpetuates exposure.
*   Under independent second releaser:* Merely requiring distinct resource is already satisfied and proved insufficient. Meaningful change demands *different* second releaser each time via rotation, workstation separation, and forced deliverable evidence upload. Truly independent, rotated second releaser unfamiliar with u12’s pattern would apply fresh skepticism, increase likelihood of questioning unsupported receipt from Low to Moderate-High. Combined with mandatory pre-release receipt validation checkpoint, likelihood of blocking fabricated payment improves substantially.

**AP-207 — 35k safety repair, token before prepare, manager-after-release-before-settlement**
*   Most plausible loss mechanism:* Similar to AP-203 but timing variant: erroneous bank account on invoice due to clerical error, or duplicate submission during urgent outage. *   Under independent second releaser:* Ideal pre-release gate eliminates race dependency: payment waits in queue regardless of settlement rail technology. ## 6. Evidence and Monitoring Recommendations

**Evidence to retain per payment for assurance:**

*   Immutable event log: Prepare token ID reference validated server-side at Prepare ingestion, full AV-2 decision trace inputs/outputs (duplicate flag, ownership register version, 7-day change query result, limit table, PO match ID), Release gating decision, Manager action with evidence packet hash (invoice image, bank proof, receipt, callback log), workstation/session ID, IP, badge tap, Bank settlement confirmation with recall deadline timestamp, Audit review completeness checklist.
*   Token lifecycle: issuance requestor, approver, validity window, NTP-synchronized timestamps, revocation list. Resolve AP-206 ambiguity by mandating monotonic clock and server-side rejection if token creation timestamp > Prepare.
*   Override vault: who requested override credential, second-factor, peer approval, business justification ticket, duration.
*   Vendor master: every bank change with old/new values, change-request ticket, maker/checker IDs, independent verification callback recording.
*   Collaboration evidence: manager review evidence quality — not just “Approved” click but annotated fields reviewed, time spent on page, attachment downloads.

**Monitoring rules — alerts vs proof:**

An alert is a statistical or rule-based risk indicator triggering review; it is not proof of misconduct and must not alone trigger sanction. Each alert needs defined disposition workflow, SLA, and documentation standard. Base rates matter: low-frequency alerts with high severity need human triage, not auto-block; high-frequency alerts need thresholds tuned to avoid fatigue.

| Monitor | Signal computed | Suggested threshold / logic | Triage action | Distinction alert vs proof |
|---|---|---|---|---|
| **Same-user rate** | % completed payments where Prepare and Release same human per week/month/business unit | Alert if >2% overall or >10% in single unit; block/queue if >20% or any repeat >100k without token | Review emergency token presence, amount/vendor eligibility. Trend drift signals culture erosion not isolated error. | Elevated rate indicates design drift, not fraud. Proof requires case sample review showing lack of emergency justification. |
| **Override rate** | Warnings emitted vs overridden; blocks attempted to bypass | Alert if override rate >5% of warnings; immediate investigation if >0 override on bank-change or limit warnings for >100k | Vault log correlation, independent re-performance, credential ownership audit | Override is sometimes legitimate (false positive) but must be paired with extra review. Not proof unless justification absent and reviewer conflicted. |
| **Late manager approval** | Manager action after Release or after Settlement; delay minutes to Settlement | Alert every occurrence manager after Release; separate queue if after Settlement = ineffective. Report median ReleaseManager lag | Determine if settlement hold existed and was used. Flag rails with instant settlement where hybrid collapses | Timing taxonomy discussed above explains why post-Release pre-Settlement can be tolerable in emergencies but still inferior to pre-Release. Latency alone not proof of rubber stamp; evidence packet depth needed. |
| **Audit before recall window** | Audit completion vs settlement + 24h | Require 100% emergency single-operator audits within 1 business day; alert if <95% compliance or any >100k audit >24h | Escalate to head of control, extend recall attempt even if window labeled closed, document reason for delay | Missed SLA is process failure, not proof payment defective. Link to actual bank recall success data only through investigation. |
| **Repeated resource pairs** | Count of Prepare/Release pair co-occurrence per unordered pair per 30-day rolling window | Alert if same ordered pair >10 in 30 days or >50% of unit volume; shared workstation >2 joint sessions triggers review | Rotation enforcement, surprise re-performance of receipt population, workstation separation audit | High pairing may reflect efficient dedicated cell design, not collusion. Proof requires substantive testing of receipts/contract deliverables plus workstation forensics, not frequency alone. AP-204/AP-209 distinction exemplifies this. |
| **Shared workstation / session clustering** | Workstation ID, IP subnet, badge events for distinct OS users overlapping in time/place | Alert on concurrent/shared-terminal use or same Workstation ID for distinct resources within 1 hour; physical security log cross-check | Review session multiplexing policy, VDI isolation, require distinct device attestation | Shared terminal may be hot-desking, not fraud. Need to differentiate policy violation vs malicious use through observation and log retention. |
| **Bank-change proximity** | Payment where vendor bank changed 7 days before Release, especially with new vendor + high amount | Flag 100%; auto-hold for dual callback verification for any payment >threshold with 7-day change. AP-208 3-day change + 900k should have auto-deferred. | Mandatory independent ownership verification via archived callback number, not supplier-supplied number on altered invoice | Proximity is risk factor, not proof of hijack. Verification success can clear; absence/weakness sustains suspicion. |
| **Control outages** | AV-2 availability % uptime, manual checklist completion rate | Alert if availability <99.5% monthly or any high-value payment released during outage without dual CFO sign-off; zero tolerance for unsigned fallback | Deferral queue, incident post-mortem, retroactive enhanced audit of all transactions during outage window | Outage itself not misconduct, but releasing high-value payments during outage violates prudent pause principle. Need to monitor deferral compliance not just outage duration. |

**Governance enhancements:**

*   Enforce server-side eligibility gating: Prepare API rejects if amount 100k + no pre-approved token, or bank change 7d, or vendor tenure <180d, or AV-2 not PASS, unless escalated hard exception requiring two L4 approvals and board log. Remove warning-override path for bank-change velocity events; make it hard hold.
*   Dual-custody override vault: override credential cannot be assigned to subordinate hierarchy; temporary issuance logged with expiry, monitored separately. Resolve AP-202 credential-sharing ambiguity via technical binding of credential to biometric/second factor.
*   Rotation policy: No fixed preparer-releaser pair may exceed X cycles; monthly rotation, random assignment for >50k intangibles where O4 risk highest.
*   Training: emphasize that AV-2 pass does not equal receipt proof; fabricate-receipt scenario testing.
*   Reporting: dashboard combining above metrics with drill-down to case evidence packet, not just aggregate scores. Quarterly control-effectiveness opinion referencing timing, independence, coverage, recoverability, not just violation count.

pair_counts = df_raw[df_raw['concept:name'].isin(['Prepare_Payment','Release_Payment'])].copy()
# Build per-case pair tuple
case_pairs = {}
for case,g in pair_counts.groupby('case:concept:name'):
    prep = g[g['concept:name']=='Prepare_Payment']['org:resource'].values
    rel = g[g['concept:name']=='Release_Payment']['org:resource'].values
    if len(prep) and len(rel):
        case_pairs[case]=(prep[0], rel[0])
# count unordered pair frequency
from collections import Counter
pair_counter = Counter(case_pairs.values())
print("\n[Repeated pairs] case -> (prepare,releaser) frequencies:")
for pair, cnt in pair_counter.items():
    print(f"  Pair {pair}: {cnt} case(s) – involved cases {[c for c,p in case_pairs.items() if p==pair]}")
# flag cases involving high-frequency pair (threshold >2 in this tiny sample, real prod threshold ~10/30d)
repeated_flag = {c: pair_counter[p]>1 for c,p in case_pairs.items()}
facts_df["flag_repeated_pair"] = facts_df["case:concept:name"].map(repeated_flag).fillna(False)

print("\n=== PRELIMINARY EVIDENCE FLAGS (NOT FINAL VERDICT) ===")
print("Flags indicate risk indicators only; missing evidence (e.g., workstation logs, manager review depth)")
print("and timing vs settlement irrevocability must be adjudicated by human judgment.")
print(facts_df[["case:concept:name","flag_emergency_gates_basic","flag_AV_full_pass","flag_manager_before_release","flag_manager_before_settlement","flag_audit_within_24h_recall","flag_high_amount","flag_bank_change_7d","flag_repeated_pair"]].to_string(index=False))

print("\n--- PM4Py BEHAVIOR NOTES ---")
print("- pm4py.format_dataframe renames keys to internal columns; original col names retained for merge here.")
print("- filter_four_eyes_principle signature and return type differ across pm4py 2.7.x vs 2.8.x: some return (violating, satisfying) tuple, others return filtered log only. This code handles both via isinstance branching.")
print("- Function considers only completed Release_Payment events; Attempt_Release/Cancel_Payment cases like AP-205 are deliberately excluded from violating set and must be tracked separately (as done above).")
print("- Resource comparison is literal string equality; shared service accounts, delegation, or SYSTEM entries are not resolved as human actors by library logic and need business-rule augmentation.")
print("- Timestamp timezone handling may vary: explicit utc=True parsing ensures deterministic ordering; without it, naive sorting can misclassify manager before/after release by milliseconds across DST logs.")

**Explanatory note on PM4Py behavior you cannot guarantee across versions:**

*   In PM4Py 2.7 the function is `pm4py.algo.filtering...four_eyes_principle.apply`; in later distributions it is aliased as `pm4py.filter_four_eyes_principle`. Return conventions vary: documented as returning a filtered log of violating cases in some builds, whereas community examples show a tuple `(violating, compliant)`. Column expectations also change: older versions require renamed `case:concept:name` to be present after `format_dataframe`; newer tolerate arbitrary case-id names but still read `org:resource`. Handling of cases with no `Release_Payment` differs — some versions silently drop incomplete cases from both sets rather than marking them non-violating. Credential inheritance or SYSTEM resources are not interpreted. Consequently the script implements defensive try/except and manual fallback counting, labels the output strictly as *evidence* requiring human adjudication on timing, independence, coverage, overrideability, recoverability, evidence quality, and collusion resistance, and declares that no external file or service was consulted.
