# 1. Objectives and constraints

**Objectives (in priority order for this queue, not a single weighted sum):**

1. **Protect SLA for urgent and high-priority cases** (C001, C002, C005, C007, C008, C011, C016). Urgent work is never routed to a under-skilled or overloaded resource just to clear the queue.
2. **Reduce error and rework risk** by matching skill to the case, especially on high-complexity and reassigned cases.
3. **Preserve continuity of ownership** where handover cost is high (the historical evidence shows waiting, rework, and appeal penalties).
4. **Keep workload and overtime exposure fair and sustainable**, especially for resources flagged high overtime risk (R2, R4, R9).
5. **Build skills deliberately** through documented training priorities, but only on normal/low-priority work with acceptable SLA risk.
6. **Maintain resilience** so that absence of one person does not stop a skill queue (Approval and Security are thin).

**Hard constraints (safety and compliance; the policy must never violate these):**

| ID | Constraint | Enforcement |
|---|---|---|
| H1 | Skill 0 = never assign | Eligibility filter |
| H2 | Security Review: skill 3, or skill 1–2 only under explicit supervision by R7 or R8 (Rule 6) | Eligibility filter; supervisor must be named in log |
| H3 | Final Approval: finalizer must be skill 2–3; skill 1 may only prepare (Rule 7) | Eligibility filter |
| H4 | Urgent/high case: skill 2, or skill 1 with active supervision (Rule 2) | Eligibility filter |
| H5 | Quality Check batching only for normal/low priority with SLA >24h (Rule 8) | Batch gate |
| H6 | 4 new assignments per resource per batch (Rule 1) | Capacity gate |
| H7 | Projected hours must fit hours remaining today (no hidden overtime) | Capacity gate |

**Soft preferences (traded off explicitly through scoring):**

- S1: Avoid assigning new work to high overtime-risk resources unless urgent and no safer alternative exists (Rule 4). Treated as near-hard in this batch.
- S2: For high-complexity, high-handover-cost cases, keep the owner unless the owner is skill 0/1 with no feasible supervision (Rule 5).
- S3: At least 20% of normal/low assignments support documented training priorities, when SLA risk is acceptable (Rule 3).
- S4: Balanced open-case counts and hours used; no single resource as a persistent queue.
- S5: Named backups for each thin skill (Approval, Security, Quality batching).
- S6: Minimize handovers in general, weighted by handover cost band.

The separation matters for explainability: H-constraints are non-negotiable and can be audited as pass/fail. S-preferences are scored and can be overridden only with a logged reason code.

# 2. Assignment policy

### 2.1 Design principles

- **Filter first, then score.** Nobody is chosen by score if they are ineligible.
- **Explicit weights** that workers and supervisors can read and debate, reviewed monthly.
- **Owner-aware but not owner-locked.** Continuity is a strong default for high-cost cases, not an absolute rule.
- **Every decision carries a reason code** so the audit trail explains itself.

### 2.2 Pseudocode

```text
INPUT:  queue Q (cases), resources R (skills, open_cases, hours_left, OT_risk, team,
        training_priority), current owners, handover_cost, sla_remaining, complexity,
        supervisors_on_shift (subset of {R7, R8}), batch_assigned_count[r] = 0
OUTPUT: assignment A (case -> resource or supervised pair), reason codes, escalations

# Step 0: Freeze context
  compute for each resource r:
      projected_open[r] = open_cases[r]
      hours_avail[r]    = hours_left[r]
  compute bottleneck flags: skill s is "thin" if fewer than 2 resources with skill>=2
      (currently: Approval and Security-3 are thin)

# Step 1: Urgency score and processing order
  for each case c:
      U[c] = priority_weight[c] + max(0, 1 - sla_remaining[c]/24)*0.5 + 0.2*complexity[c]
      where priority_weight: urgent=1.0, high=0.7, normal=0.3, low=0.1
  sort Q by U descending; ties -> earlier SLA deadline first

# Step 2: Hard eligibility filter (H1-H7)
  for each case c in order:
      E[c] = []
      for each resource r:
          s = skill[r][required_skill[c]]
          if s == 0: continue                                              # H1
          if required_skill[c] == Security and s == 1 or 2:
              if no supervisor in supervisors_on_shift: continue            # H2
          if required_skill[c] == Approval and s == 1:
              mark as PREPARE_ONLY; only eligible as preparer, not finalizer # H3
          if priority[c] in {urgent, high} and s == 1 and no supervisor:
              continue                                                      # H4
          if batch_assigned_count[r] >= 4: continue                         # H6
          if est_hours[c] > hours_avail[r]: continue                        # H7
          E[c].append(r)
      if E[c] is empty -> go to Step 8 (exception handling)

# Step 3: Skill-fit score (0..1)
  SkillFit(c,r) = {1: 0.35, 2: 0.75, 3: 1.00}[skill[r][req[c]]]
  (skill 1 may be scored only if supervisor attached, see H2/H4)

# Step 4: Continuity / handover-cost score (0..1)
  is_owner = (r == current_owner[c])
  if complexity[c] >= 0.75 and handover_cost[c] == high:          # Rule 5 zone
      if is_owner and (skill[r] >= 2 or supervision_feasible):   Cont = 1.0
      elif is_owner:                                             Cont = 0.4
      else:                                                      Cont = 0.0
  else:
      Cont = 0.3 if is_owner else 0.0
  HandoverPenalty(c,r) = 0 if is_owner
                         else {low: 0.05, medium: 0.20, high: 0.40}[handover_cost[c]]

# Step 5: Load and overtime score (penalties)
  LoadPenalty(r) = projected_open[r] / max(projected_open over eligible) * 0.6
  OTPenalty(r,c) = {low: 0.0, medium: 0.25, high: 0.80}[OT_risk[r]]
  if OT_risk[r] == high:
      if U[c] >= urgency_threshold and no other eligible resource with OT != high:
          OTPenalty *= 0.5          # documented override path, logged
      else:
          OTPenalty stays; resource is excluded if other options exist

# Step 6: Development score (bonus; only for normal/low work)
  Dev(c,r) = 0
  if priority[c] in {normal, low}
     and skill[r][req[c]] == 1
     and req[c] in training_priority_of[r]
     and sla_remaining[c] >= 12h
     and OT_risk[r] != high:
        Dev = 0.30 ; supervision_required = true (log supervisor)

# Step 7: Resilience score (bonus/penalty)
  Resil(c,r) = +0.15 if at least one other eligible skill>=2 backup exists for this skill
  Resil(c,r) -= 0.30 if r is the only skill>=2 resource for this skill AND
                         r already holds >=2 urgent/high cases
  (prevents single-person bottlenecks e.g., R6 as only approval-3 with urgent load)

# Step 8: Composite score and selection
  Score(c,r) = 0.40*SkillFit + 0.25*Cont - 0.15*HandoverPenalty
             - 0.20*LoadPenalty - OTPenalty + Dev + Resil
  for each case c:
      best = argmax_{r in E[c]} Score(c,r)
      tie-break order:
         1. lower projected_open[r]
         2. lower OT_risk (low < medium < high)
         3. higher skill level
         4. is_owner = true
         5. lexicographic resource ID   (deterministic and reproducible)
      assign c -> best (or supervised pair if skill 1 or Security 1-2)
      projected_open[best] += 1; batch_assigned_count[best] += 1
      hours_avail[best] -= est_hours[c]
      log reason_code (see Section 6 deviation codes)

# Step 9: Batching (Quality Check only)
  group normal/low Quality cases with SLA > 24h assigned to the same resource
  -> one batch session per resource per batch window

# Step 10: Exception handling
  if E[c] empty OR best score < 0 for urgent/high case:
      escalate to shift lead within 15 minutes with:
         - list of constraints that failed
         - next-best option and the rule it violates
      fallback order:
         a) named backup for skill (from backup table)
         b) supervised pair with R7/R8 for Security, or with a skill-3 approver for Approval prep
         c) hold case in "awaiting specialist" with SLA clock visible to team
      any override is logged with reason_code = OVERRIDE_<rule>, approver ID
```

### 2.3 Weights and their rationale

| Term | Weight | Why |
|---|---|---|
| SkillFit | 0.40 | Errors and rework dominate cost; skill fit is the largest single driver |
| Continuity | 0.25 | Historical evidence shows handover penalties on complex cases |
| HandoverPenalty | 0.15 | Keeps handovers rare without making them impossible |
| LoadPenalty | 0.20 | Prevents recurring use of the same person as the fastest option |
| OTPenalty | 0.25 to 0.80 | Overtime is a sustainability and safety issue, not just a preference |
| Dev | +0.30 | Enough to break ties toward learning, not enough to override skill or SLA |
| Resil | ±0.15 / 0.30 | Protects thin skills (Approval, Security-3) from single points of failure |

These are starting values. They should be calibrated against historical rework, SLA miss, and handover data (Section 7), and the team should run a sensitivity check (for example, ±0.10 on each weight) before adopting them.

### 2.4 Tie-breaking and exceptions summary

- **Deterministic tie-breaks**: fewer projected open cases, then lower overtime risk, then higher skill, then owner, then ID. Workers can predict the outcome.
- **Exception paths**: named backups, supervised pairs, and escalation to a shift lead with a logged reason code. No silent overrides.
- **Absence handling**: each thin skill has a primary and a backup. If a primary is absent, the backup is used and the policy re-runs.

# 4. Comparison with baseline policies

### 4.1 How the baselines behave on this queue

**First-available (lowest open cases, skill 0 excluded):**
- Urgent C002 (Approval) goes to R10 (lowest open count) at skill 1. This violates H3 (skill 1 may not finalize) and H4 (urgent at skill 1 without supervision).
- Urgent C011 (VIP Negotiation) goes to R10 at skill 1 for the same reason.
- R10 is repeatedly the lowest-count resource, so it absorbs most urgent work at trainee level, while skill-3 specialists are underused.
- Continuity is ignored: C001, C007, and C016 leave high-cost owners.

**Specialist-only (highest skill, tie-break on open cases):**
- R6 receives all negotiation work (C005, C011) and approvals (C002, C010), reaching 4 new assignments. That is at the cap, and the cap was not enforced by the baseline itself.
- R3 receives C003, C007, C009, C014, and C016: five assignments. This breaks Rule 1 (4) and overloads one person with a skill-1 trainee case (C009) that would have been better for R1.
- R5 receives nothing, while C016 (its own case, skill 2) is moved to R3. This breaks continuity on a high-cost case.
- R1 is the only eligibility specialist option, so C013 goes to R1 at 9 open cases.
- Training and overtime are not considered. R4 and R2 are relieved only incidentally.

### 4.3 Where the proposed policy is weaker

- **Speed on the simplest items.** First-available can clear low-complexity cases faster by sending them to whoever is free.
- **Specialist quality on C003 and C014.** Using R8 and R7 instead of R3 and R4 lowers expected diagnosis and rework quality.
- **Dependence on supervisors.** C001 and any Security trainee work rely on R8 or R7 being available. If they are absent, the policy falls back to escalation, which adds delay.
- **Complexity of the rules.** Workers must learn the weights and rules. This is a real adoption cost (Section 5 addresses it).

**Conclusion (no single optimum).** Specialist-only is the best option when the only goal is first-pass quality on specialist work, but it breaks the cap and overloads individuals. First-available is the best option when speed on simple work is the only goal, but it violates skill and urgency rules. The proposed policy accepts a modest speed cost and a few residual skill-level risks in exchange for safer urgent handling, lower handover cost on complex cases, relief for overloaded staff, and resilience. Those trade-offs should be confirmed by a simulation on historical data before the policy is fully deployed.

# 5. Explanation to workers

**Why this approach?** The team has more work than people can handle at the same time, and some cases are time-critical, some are complex, and some are a chance to learn. This approach makes the reasons visible so that everyone can see why a case went where it did.

**What the system looks at, in plain terms:**

1. **Is the person allowed to do this kind of work?** Some cases, especially security reviews and final approvals, have rules about who can finalize them. Trainees can prepare, and supervised work is recorded.
2. **How urgent is it?** Urgent and high-priority cases get the most careful matching.
3. **Who already knows the case?** If a case is complex and expensive to hand over, we keep it with the person who has been working on it, as long as that person has the right skill or a supervisor is available. Switching people mid-case costs time and has been linked to more rework.
4. **How busy and how tired is each person?** We look at open cases and overtime risk. If someone is already at the limit, we give them less, not more.
5. **Is this a good chance to learn?** For normal or low-priority work with enough time, we deliberately choose a trainee, with a review checkpoint. This is never done for urgent work.

**What this is not:**

- It is **not a performance score**. Assignments are not based on how fast or how many cases you have completed.
- It is **not a ranking**. Getting a trainee case does not mean you are considered less capable. Getting an urgent case does not mean you are favored.
- It is **not hidden**. Every assignment has a short reason on the case record. If you think a reason is wrong, you can say so.

**Your part:**

- If you are told you are the supervisor on a case, your sign-off is what makes the case valid. Please review it at the checkpoint time shown.
- If you are blocked, say so early. The system escalates to the shift lead rather than silently reassigning.
- If the assignment does not match what you know about a case (for example, you have seen this customer before, or the documents are missing), flag it. This is useful information, and the policy will learn from it at the monthly review.
- If you believe a rule is causing a problem (for example, a training quota that cannot be met because of overtime limits), raise it at the team review. Changes are made openly and recorded.

**Example.** "C003 moved from R4 to R8. Reason: R4 is at high overtime risk with 14 open cases. R8 has the capacity and the diagnosis skill for a normal-priority case. R3 stays free for urgent and complex work. You may see a second look from R3 if the diagnosis loops again."

# 6. Process-mining audit indicators

All indicators are computed from the event log (`case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`, plus `assignment_reason`, `reassignment_count`, `workload_snapshot`, `handover_cost_band`, `required_skill`, `case_priority`, `sla_deadline`, `case_complexity`, `current_owner`, `team`). A skill-level lookup table is maintained alongside the log.

| Indicator | Definition | Target / alert | Why it matters |
|---|---|---|---|
| **Handover frequency** | Number of owner changes per case / total cases; also handovers per high-complexity case | Target: low; alert if high-complexity handover rate rises above baseline | Handovers on complex cases carry waiting and rework cost |
| **Reassignment count** | Distribution of `reassignment_count`; share of cases with >2 reassignments | Alert if any case reaches 3 without review | Historical rework rate is 1.8x for >2 reassignments |
| **Skill mismatch** | Share of assignments where skill < 2 for normal work or < 2 for urgent/high work (unsupervised); share of Security assignments at skill 1–2 without a named supervisor | Target: 0 for urgent/high unsupervised; 0 for Security without supervisor | Direct measure of Rules 2, 6, 7 compliance |
| **Workload distribution** | Open cases and hours used per resource; Gini coefficient and max/min ratio of new assignments per batch | Alert if max new assignments >4 (Rule 1) or Gini rises above threshold | Fairness and sustainability |
| **Overtime risk exposure** | Share of new assignments and hours going to high-OT resources; share of cases with high-OT owners at assignment time | Target: near zero unless urgent override is logged | Rule 4; protects people and quality |
| **SLA misses** | Share of cases where event time > `sla_deadline`, by priority, and by assignment policy version | Alert on urgent/high misses; compare to baseline | Primary service outcome |
| **Rework and appeal after assignment** | Rework events (Rework Correction activity) and appeal indicators within N days of assignment, by owner, skill level, and handover status | Compare between supervised and non-supervised; alert on rise | Tests whether skill-based assignments reduce errors |
| **Training assignment share** | Share of normal/low assignments that support a documented training priority (performed, not shadowed), with SLA risk acceptable | Target: 20% (Rule 3); reported with reason if below | Skill development and fairness |
| **Specialist bottleneck indicators** | Waiting time before Approval-3 and Security-3 activities; queue length per specialist; share of cases waiting >X hours for a thin skill; utilization of R6, R7, R8 | Alert if specialist queue wait exceeds SLA buffer | Shows whether specialist-only effects are emerging |
| **Deviations from policy** | Assignments that differ from the policy's top-scored option; each deviation must carry a reason code (for example, `OVERRIDE_RULE4_URGENT`, `OVERRIDE_CONTINUITY_OWNER_LOW_SKILL`, `ESCALATION_NO_FEASIBLE`, `BACKUP_USED_ABSENCE`) | Target: deviations are logged 100%; review monthly for patterns | Auditability and learning |

**Additional recommended indicators:** service time by resource-skill pair (to test the 3.3-hour "keeping weak owner" effect), waiting time added by handover on high-complexity cases (to test the 2.7-hour effect), and shadowing hours as a separate training category.

# 7. PM4Py implementation sketch

The code below assumes the event log has been exported with one row per event and the columns listed in the prompt. Some PM4Py function signatures differ slightly across versions; verify parameter names against your installed version. The pandas section does not depend on PM4Py internals and is the most reliable path for the audit indicators.

```python
import pandas as pd
import pm4py

# ---------- 0. Load and format ----------
df = pd.read_csv("assignment_events.csv", parse_dates=["time:timestamp", "sla_deadline"])
df = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
)
log = pm4py.convert_to_event_log(df)

# ---------- 1. Resource networks (who hands work to whom, who works together) ----------
handover_net = pm4py.discover_handover_of_work_network(log)
together_net = pm4py.discover_working_together_network(log)
```

**How to use this to learn or calibrate the policy (not just audit it):**

- **Calibrate weights.** Use historical logs to estimate the effect of continuity on rework and waiting, split by complexity and handover band. Use those effects to set the weights for Continuity and HandoverPenalty in Section 2. Replay the policy on past queues and compare SLA misses, rework, and overtime exposure with actual outcomes.
- **Validate the skill matrix.** Compare `discover_activity_based_resource_similarity` and `discover_organizational_roles` against the stated skill scores. If an person performs an activity they have a score of 1 for, and it succeeds at the same rate as a score 2 performer, the matrix may be too conservative.
- **Find bottlenecks.** Use `discover_performance_dfg` and `filter_case_performance` to find edges into Approval and Security with long waiting times. If waiting is concentrated in one resource, activate the backup rule.
- **Check handover effects.** Use `discover_handover_of_work_network` to identify which handovers occur most often and whether they are associated with rework. Target the most frequent high-cost handovers for policy change.
- **Monthly review.** Review deviations with reason codes, shadowing and training hours, and any urgent overrides. Propose weight or rule changes openly, with team input, and version the policy so that before-and-after comparisons remain valid.
