# 1. Delay-decomposition definitions

Let `c` index cases and `i  {A, B, C}` index parallel branches. All times are parsed as datetime on 20260519.

For each case `c`:

- **upstream_elapsed(c)** = `fork_release(c)  arrival(c)`
- For each branch `i`:
  - **branch_queue(i, c)** = `i_start(c)  fork_release(c)`
  - **branch_service(i, c)** = `i_end(c)  i_start(c)`
  - **branch_sync(i, c)** = `join_ready(c)  i_end(c)`
- **join_ready(c)** = `max{ A_end(c), B_end(c), C_end(c) }` (the synchronized completion under the stated rule; not directly logged)
- **elapsed_fork_join(c)** = `join_ready(c)  fork_release(c)`
- **downstream_queue(c)** = `final_start(c)  join_ready(c)`
- **final_service(c)** = `final_end(c)  final_start(c)`
- **total_flow_time(c)** = `final_end(c)  arrival(c)`

**Consistency (non-double-counting temporal decomposition).**

`total_flow_time(c)` can be written exactly as

```
upstream_elapsed(c)
+ elapsed_fork_join(c)
+ downstream_queue(c)
+ final_service(c)
```

because the intermediate quantities telescope:

```
(fork_release  arrival)
+ (join_ready  fork_release)
+ (final_start  join_ready)
+ (final_end  final_start)
= final_end  arrival
```

**Why summing all branch `queue + service + sync` would double count.**

Each non-critical branch `i` satisfies, by construction,

```
branch_queue(i,c) + branch_service(i,c) + branch_sync(i,c)
   = (i_end  fork_release) + (join_ready  i_end)
   = join_ready  fork_release
   = elapsed_fork_join(c)
```

The critical branch `i*` also satisfies the same identity with `sync = 0`. Therefore the sum across all three branches equals

```
_i [branch_queue + branch_service + branch_sync]
 = 3 · elapsed_fork_join(c)
```

So summing the per-branch `queue + service + sync` triple-counts `elapsed_fork_join` by a factor of three. Equivalently, summing only the per-branch `sync` terms over-counts the *idle* component of fork-join by `n  1` times `elapsed_fork_join` minus the already-counted active work, and so cannot be added to the temporal decomposition without explicit reconciliation. The chosen decomposition above attributes the elapsed stage to a single instance (`elapsed_fork_join`) and uses `branch_sync(i,c)` purely as an *informational* attribute of each branch, not a summable component.

**Critical branch.** `i* = argmax_i i_end(c)`. With one-minute timestamps there are no exact ties in this dataset; in general we apply deterministic tie-breaking by column order (A before B before C), implemented by `DataFrame.idxmax` which preserves that order.

# 5. Recommended redesigns and risks

**Redesign 1 — Reduce B queue delay by 50% (target the critical path).**

- *Throughput.* Expected improvement: ~7.7 min average case time, plus the longest cases (F07, F12) shrink by 15 min, materially shortening the flow-time tail.
- *Flow-time tail.* Tail cases all have B as critical with the largest B queues; halving B queue removes exactly the long-tail contribution.
- *Resource utilization.* B-resource utilization falls; a freed B resource could be repurposed or removed if cost-relevant.
- *New bottleneck risk.* As shown by the counterfactual, when B becomes faster, several cases (F02, F05, F06, F09, F10) flip criticality from B to A. A is a fixed 50-minute assay with zero queue; speeding B does nothing to help those cases. A secondary, smaller risk is that B queue is in fact a function of upstream variability (cases arrive at B from a shared technical pool); cutting B queue may require adding capacity rather than just smoothing, since the mean B service alone is 37.5 min.
- *Synchronization effects.* Reducing B queue shrinks `elapsed_fork_join` but does not change `join_ready` *relative ordering* in non-B-critical cases; C_sync actually rises in those cases because C was already finishing well before join_ready.
- *Pilot metric.* Measure `B_queue` directly (startfork_release) before and after, and watch whether cases that flip criticality (F02, F05, F06, F09, F10) still see total-flow gains or whether A becomes the limiter. Pilot on a single shift; required sample  30 cases for an effect size of 7.7 min at   11.

**Redesign 2 — Add final-station capacity or smooth final scheduling (target downstream queue).**

- *Throughput.* Expected improvement: ~7–15 min per case depending on how aggressively queue is reduced. Halving downstream queue already yields 7.3 min/case on average and 10 min in F10/F11.
- *Flow-time tail.* Long cases are disproportionately helped because their absolute downstream wait is large (e.g., F04 18 min, F10 20 min, F11 20 min). The downstream stage is a *floor*, not just a tail contributor.
- *Resource utilization.* F1/F2 utilization rises with the new arrival pattern (cases no longer dwell in queue); if a third resource is added, each F1/F2 utilization may *fall* if cases shift earlier.
- *New bottleneck risk.* None inside the fork-join: this is the *only* counterfactual that does not shift branch criticality. The risk is operational — if the third resource is underused, capacity is wasted; if F1/F2 are simply rebalanced, monitor arrival pattern.
- *Synchronization effects.* `downstream_queue` is not part of the fork-join, so synchronization waiting is unchanged.
- *Pilot metric.* Measure `final_start  join_ready` and final-resource idle time; pilot by adding a third resource for half of one week. Required sample ~25 cases for an effect size of 7.3 min at   4.4.

**Honest note on overlap.** CF1 was included for completeness but is the weakest lever (1.7 min/case, only F01/F11 benefit). A small A-side improvement (e.g., shaving A service to 45 min, ~10%) costs little and would shave ~5 min from F01 and F11 with no other case affected; it is worth doing *only* if the assay is cheap to accelerate, not as a primary redesign.

```python
# -----------------------------------------------------------------------------
def decompose(frame):
    out = frame.copy()
    out["upstream_elapsed"] = (out["fork_release"] - out["arrival"]).dt.total_seconds() / 60
    for br in ["A", "B", "C"]:
        out[f"{br}_queue"]    = (out[f"{br}_start"] - out["fork_release"]).dt.total_seconds() / 60
        out[f"{br}_service"]  = (out[f"{br}_end"]   - out[f"{br}_start"]).dt.total_seconds() / 60
    # join_ready is the synchronization point of the fork-join
    out["join_ready"]        = out[["A_end", "B_end", "C_end"]].max(axis=1)
    for br in ["A", "B", "C"]:
        out[f"{br}_sync"]    = (out["join_ready"]   - out[f"{br}_end"]).dt.total_seconds() / 60
    out["elapsed_fork_join"] = (out["join_ready"]   - out["fork_release"]).dt.total_seconds() / 60
    out["downstream_queue"]  = (out["final_start"]  - out["join_ready"]).dt.total_seconds() / 60
    out["final_service"]     = (out["final_end"]    - out["final_start"]).dt.total_seconds() / 60
    out["total_flow_time"]   = (out["final_end"]    - out["arrival"]).dt.total_seconds() / 60
    # critical branch: argmax of branch end times, deterministic tie-break A<B<C
    out["critical_branch"]   = out[["A_end", "B_end", "C_end"]].idxmax(axis=1).str[0]
    return out

base = decompose(df)

# Compact case-level table (matches Section 2)
case_table = base[[
    "case", "upstream_elapsed",
    "A_queue", "A_service",
    "B_queue", "B_service",
    "C_queue", "C_service",
    "join_ready", "critical_branch",
    "downstream_queue", "final_service", "total_flow_time",
]].copy()
case_table["join_ready"] = case_table["join_ready"].dt.strftime("%H:%M")
print("=== Case-level decomposition ===")
print(case_table.to_string(index=False))

# -----------------------------------------------------------------------------
# 3. Counterfactuals (all in minutes)
# -----------------------------------------------------------------------------
# CF1: reduce A service by 20%
cf1 = base.copy()
a_service = cf1["A_end"] - cf1["A_start"]
cf1["A_end"] = cf1["A_start"] + a_service * 0.8
cf1 = decompose(cf1.assign(A_end=cf1["A_end"]))
cf1_savings = base["total_flow_time"] - cf1["total_flow_time"]

# CF2: reduce B queue delay by 50%
cf2 = base.copy()
b_queue = cf2["B_start"] - cf2["fork_release"]
cf2["B_start"] = cf2["fork_release"] + b_queue * 0.5
cf2["B_end"] = cf2["B_start"] + (cf2["B_end"] - cf2["B_start"])  # service unchanged
cf2 = decompose(cf2.assign(B_start=cf2["B_start"], B_end=cf2["B_end"]))
cf2_savings = base["total_flow_time"] - cf2["total_flow_time"]

# CF3: halve downstream queue
cf3 = base.copy()
cf3["final_start"] = cf3["join_ready"] + (cf3["final_start"] - cf3["join_ready"]) * 0.5
cf3 = decompose(cf3.assign(final_start=cf3["final_start"]))
cf3_savings = base["total_flow_time"] - cf3["total_flow_time"]

cf_summary = pd.DataFrame({
    "counterfactual": ["CF1 A_service*0.8", "CF2 B_queue*0.5", "CF3 downstream_queue*0.5"],
    "total_saved_min": [cf1_savings.sum(), cf2_savings.sum(), cf3_savings.sum()],
    "mean_saved_min":  [cf1_savings.mean(), cf2_savings.mean(), cf3_savings.mean()],
    "cases_with_zero_benefit": [
        int((cf1_savings == 0).sum()),
        int((cf2_savings == 0).sum()),
        int((cf3_savings == 0).sum()),
    ],
})
print("\n=== Counterfactual savings ===")
print(cf_summary.to_string(index=False))

# -----------------------------------------------------------------------------
# 4. PM4Py interval-event log for the fork-join branches and final activity
#    (one row per (case, activity)); start_timestamp + time:timestamp
# -----------------------------------------------------------------------------
interval_rows = []
for _, r in base.iterrows():
    for br in ["A", "B", "C"]:
        interval_rows.append({
            "case:concept:name": r["case"],
            "concept:name": br,
            "start_timestamp": r[f"{br}_start"],
            "time:timestamp":  r[f"{br}_end"],
        })
    interval_rows.append({
        "case:concept:name": r["case"],
        "concept:name": "F",
        "start_timestamp": r["final_start"],
        "time:timestamp":  r["final_end"],
    })
interval_df = pd.DataFrame(interval_rows)

# pm4py.format_dataframe ensures case/activity/timestamp columns and sorts
log = pm4py.format_dataframe(
    interval_df,
    case_id="case:concept:name",
    activity_key="concept:name",
    start_timestamp_key="start_timestamp",
    timestamp_key="time:timestamp",
)

# -----------------------------------------------------------------------------
# 5. PM4Py analyses relevant to a fork-join interpretation
# -----------------------------------------------------------------------------
# Service time per activity: standard PM4Py analysis; this recovers active
# service but cannot separate queue from sync, hence the custom work above.
service_time = pm4py.get_service_time(log)

# Performance DFG: gives throughput-time between consecutive activities in a
# case, but in a fork-join the branches are not consecutive in a single
# trace; DFG metrics therefore do not capture join_ready or branch_sync.
perf_dfg = pm4py.discover_performance_dfg(log)

# Time-interval view of the interval event log
time_intervals = pm4py.convert_log_to_time_intervals(log)

print("\n=== PM4Py service time (minutes) per activity ===")
print(service_time)
print("\n=== PM4Py performance DFG (mean seconds between directly-follows pairs) ===")
print(perf_dfg[0])
print("\n=== PM4Py time intervals (head) ===")
print(time_intervals.head())

# -----------------------------------------------------------------------------
# 6. Aggregate critical-path summary (matches Section 3)
# -----------------------------------------------------------------------------
summary_rows = []
for br in ["A", "B", "C"]:
    crit = base[base["critical_branch"] == br]
    summary_rows.append({
        "branch": br,
        "critical_count":  len(crit),
        "critical_share":  round(len(crit) / len(base), 2),
        "mean_service":    round(base[f"{br}_service"].mean(), 2),
        "max_service":     round(base[f"{br}_service"].max(), 2),
        "mean_queue":      round(base[f"{br}_queue"].mean(), 2),
        "max_queue":       round(base[f"{br}_queue"].max(), 2),
        "mean_sync":       round(base[f"{br}_sync"].mean(), 2),
        "max_sync":        round(base[f"{br}_sync"].max(), 2),
        "mean_qs_when_crit": round((crit[f"{br}_queue"] + crit[f"{br}_service"]).mean(), 2),
    })
summary = pd.DataFrame(summary_rows)
print("\n=== Aggregate branch summary ===")
print(summary.to_string(index=False))
```

Notes on what the Python does and why custom pandas is needed:

- `decompose` is the fork-join-aware engine. `join_ready` is computed as `max(A_end, B_end, C_end)` because the join point is not logged. `branch_sync(i)` is `join_ready  i_end`. These are not recoverable from a directly-follows graph.
- `idxmax(axis=1).str[0]` implements the deterministic A-before-B-before-C tie-break for the critical branch.
- The PM4Py calls (`format_dataframe`, `get_service_time`, `discover_performance_dfg`, `convert_log_to_time_intervals`) are run on the interval-event log so that branch and final intervals are explicit; nevertheless the synchronization waiting and `elapsed_fork_join` come only from the custom pandas block above.
- Counterfactuals are computed by mutating the relevant component (A service, B queue, downstream queue) and rerunning `decompose`, so each scenario uses the same definitions and tie-breaking as the baseline.

# 7. Limits of inference

- **Causality is not identified.** We observe timestamps, not the policy that scheduled branches or routed them to resources. Whether `B_queue` is true resource contention, an artifact of a single shared machine, or a deliberate priority rule cannot be decided from these data alone. A before/after comparison with a controlled intervention would be needed.
- **Branch resource capacity is not observable.** The log does not record which physical resource ran each branch, how many resources exist per branch pool, or whether branches share machines. We therefore cannot distinguish "queue delay" from "single-server serialization".
- **Preemption, rework, and concurrency within a branch are invisible.** Each branch has a single start and end per case, so any internal subdivision of work is hidden. A long A_service in F08 (30 min) versus a short C_service (18 min) might reflect very different internal dynamics that we cannot disentangle.
- **`final_start  join_ready` is not necessarily a queue.** The model assumes that F can start immediately after `join_ready`; if F1/F2 are the only two final resources and arrivals are spaced closer than the service time, queueing is the natural explanation. However, the same pattern could arise from a release policy (e.g., F only runs at fixed times, or a manager must physically sign off and is unavailable). Distinguishing these requires process-owner input or a finer-grained event log around F.
- **`fork_release  arrival` is model-derived, not policy-measured.** Upstream elapsed is computed from two logged events whose semantic link (a `fork_release` after upstream preparation) is given by the prompt but not validated here. If `fork_release` is itself the result of an upstream decision, then upstream elapsed is partly downstream of an unobserved policy.
- **One-minute timestamps mask sub-minute dynamics.** All durations are quantized to whole minutes. The longest `downstream_queue` (20 min) could be 19:31–20:29 in reality; this affects mean estimates but not the ranking.
- **Counterfactuals assume independence.** CF2 assumes B queue can be halved without changing B service or other branches’ behavior. If B’s queue is driven by a shared resource with A or C, halving it might shift queue elsewhere. CF3 assumes adding capacity reduces downstream queue without inflating upstream; in reality it might surface branch congestion that is currently hidden by the final-station buffer.
- **Critical-branch criticality depends on tie-breaking.** With one-minute data we have no exact ties, but with finer timestamps tie-breaking would matter and the deterministic lexicographic rule is a modelling choice, not a measured fact.
- **Influence ranking is descriptive, not causal.** Branch B is most influential because it is critical most often and has the largest control over `elapsed_fork_join`; this is consistent with but does not prove that reducing B queue will improve outcomes if the queue itself is a symptom of an upstream constraint not visible in this log.
