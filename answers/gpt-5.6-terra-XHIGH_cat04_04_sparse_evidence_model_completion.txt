The two directions in the DFG, `Credit Check  Engineering Review` and `Engineering Review  Credit Check`, do **not** establish concurrency by themselves. They are also compatible with:

- different sequential routing policies for different order types;
- delayed completion of an activity that started first;
- overlapping but not fully concurrent work;
- timestamp granularity or tie-breaking by ingestion index;
- unobserved case attributes, such as component type or risk class.

A DFG loses interval information and most case-level context. It can support “both recorded completion orders are observed,” but not “the activities are concurrent” or “neither activity is a prerequisite at start time.”

# 2. Shared Assumptions

Let the following abbreviations denote visible activities:

- `r` = Register Order
- `c` = Credit Check
- `e` = Engineering Review
- `s` = Supplier Confirmation
- `x` = Expedite Review
- `a` = Approve Configuration
- `p` = Release Production
- `z` = Archive Case

Notation:

- `u ; v` means sequence.
- `XOR(u, v)` means exclusive control-flow choice.
- `` is a silent transition.
- `?q = XOR(, q)` is an optional visible event.
- `PO(N, E)` is a strict partial order over nodes `N` with precedence edges `E`.
- In a partial order, absence of an edge means “no visible completion-order constraint is asserted.” It does **not** mean physical simultaneity has been proven.

Common assumptions across the three candidates:

1. **Completion-event semantics.** Every visible label represents an observed completion event, not an activity start, state transition, or interval. Therefore, the models are log-level completion models rather than direct models of work-start causality.

2. **One occurrence per activity.** The supplied traces contain no repetition. All candidates allow each visible activity at most once. This is an abstraction; rework, repeated supplier contacts, and re-approval are not modeled.

3. **Fixed start and end.** Register Order is the first visible event and Archive Case is the last visible event, following D1.

4. **Approval and release constraints.** All candidates enforce:
   - `c` before `a`;
   - `e` before `a`;
   - `a` before `p`;
   - `p` before `z`.

5. **Supplier Confirmation missingness versus true optionality.** A missing visible `s` event is modeled as a control-flow alternative, but that alternative is an **observational abstraction**. It combines:
   - legitimate non-occurrence for stocked components, per S4;
   - unobserved external/stocked routing, per S5;
   - missing Supplier Confirmation integration events, per S5.

   Thus, `?s` does not mean “Supplier Confirmation is always optional in the real business process.”

6. **Absent external/stocked attribute.** None of the candidates can express the desired conditional rule “Supplier Confirmation is mandatory if and only if the component is external.” They instead use an unobserved choice. A production deployment should add the missing attribute and replace this abstraction with a guarded rule.

7. **Expedite Review optionality.** `?x` means no Expedite Review completion event is recorded in that case. When `x` occurs, every candidate enforces D6: it occurs once, after both principal checks, and before approval.

8. **No probability claim.** Variant counts inform plausibility but are not converted into stochastic transition probabilities. The three models are language hypotheses, not predictive probability models.

# 3. Conservative Candidate

## Inductive bias

`model_conservative` is an exact observed-language model. It prioritizes precision with respect to the seven observed completion sequences and deliberately avoids generalizing from DFG patterns, stakeholder claims, or latent explanations. It treats every observed variant as a separate XOR branch. This is suitable when the immediate goal is strict replay, audit of known variants, or establishing a lower-bound language. It is not a claim that the process truly has seven business routes; the duplicated labels are an encoding device for finite trace enumeration.

## Compact formal expression

\[
\begin{aligned}
L_C = XOR(&r;c;e;s;a;p;z,\\
          &r;e;c;s;a;p;z,\\
          &r;c;e;a;p;z,\\
          &r;e;c;a;p;z,\\
          &r;c;s;e;a;p;z,\\
          &r;c;e;s;x;a;p;z,\\
          &r;e;c;x;s;a;p;z)
\end{aligned}
\]

This finite language contains exactly the seven distinct observed variants.

## PM4Py ProcessTree code

```python
import pm4py

conservative_tree_string = """
X(
    ->('Register Order','Credit Check','Engineering Review',
       'Supplier Confirmation','Approve Configuration',
       'Release Production','Archive Case'),
    ->('Register Order','Engineering Review','Credit Check',
       'Supplier Confirmation','Approve Configuration',
       'Release Production','Archive Case'),
    ->('Register Order','Credit Check','Engineering Review',
       'Approve Configuration','Release Production','Archive Case'),
    ->('Register Order','Engineering Review','Credit Check',
       'Approve Configuration','Release Production','Archive Case'),
    ->('Register Order','Credit Check','Supplier Confirmation',
       'Engineering Review','Approve Configuration',
       'Release Production','Archive Case'),
    ->('Register Order','Credit Check','Engineering Review',
       'Supplier Confirmation','Expedite Review',
       'Approve Configuration','Release Production','Archive Case'),
    ->('Register Order','Engineering Review','Credit Check',
       'Expedite Review','Supplier Confirmation',
       'Approve Configuration','Release Production','Archive Case')
)
"""

model_conservative = pm4py.parse_process_tree(conservative_tree_string)
```

The ProcessTree intentionally duplicates labels across XOR branches. Duplicate labels are valid, but they reduce structural compactness and obscure that the same business activity appears in multiple paths. This approach scales poorly: adding one new ordering can require a new full branch, and allowing all interleavings of several activities grows factorially.

## Behavior deliberately excluded

- Any complete trace not identical to one of the seven observed variants.
- A case with Expedite Review and no visible Supplier Confirmation.
- `Credit Check, Engineering Review, Expedite Review, Supplier Confirmation` ordering.
- `Engineering Review, Supplier Confirmation, Credit Check` ordering.
- Supplier Confirmation before both principal check completions.
- Any future interleaving not already observed.
- Rework, repetition, cancellation, exception outcomes, or repeated supplier contacts.

## Known underfitting risks

- S5 says approximately 5–10% of Supplier Confirmation events may be missing; exact trace enumeration cannot tolerate new missingness patterns.
- The model rejects plausible unseen Supplier/Expedite combinations supported by D6 and S6.
- It cannot accommodate new stocked/external mixes because the latent condition is not modeled.
- It may reject valid completion interleavings that arise from overlapping work or timestamp tie-breaking.
- It treats low-frequency behavior as invalid merely because it has not yet appeared.

# 4. Balanced Candidate

## Inductive bias

`model_balanced` preserves high-confidence ordering constraints while generalizing only where the evidence provides a defensible explanation. It does not claim that Credit Check and Engineering Review are physically concurrent; it records no completion-order edge between them because both completion orders are observed and D7/S7 prevent a start-order conclusion. It represents Supplier Confirmation as observationally optional and encodes D5’s “after either check provides enough information” as two latent explanatory alternatives: Supplier Confirmation follows Credit Check in one branch, or follows Engineering Review in the other. Expedite Review is optional, follows both principal checks, and is unordered relative to Supplier Confirmation.

## Compact formal expression

Define:

\[
B_q =
PO\left(
\{c,e,?s,?x\},
\{q \prec ?s,\ c \prec ?x,\ e \prec ?x\}
\right)
\]

where \(q \in \{c,e\}\). Then:

\[
L_B = r ; XOR(B_c, B_e) ; a ; p ; z
\]

Interpretation:

- `c` and `e` have no relative completion-order edge.
- `s`, if visible, follows either `c` or `e`, represented by the latent XOR of explanatory branches.
- `x`, if visible, follows both `c` and `e`.
- `s` and `x` have no relation, so either recorded order is possible.
- Approval occurs only after all selected core activities are complete.

## PM4Py POWL code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def optional_activity(label):
    return OperatorPOWL(
        Operator.XOR,
        [SilentTransition(), Transition(label)]
    )


def make_balanced_core(supplier_predecessor):
    credit = Transition("Credit Check")
    engineering = Transition("Engineering Review")
    supplier = optional_activity("Supplier Confirmation")
    expedite = optional_activity("Expedite Review")

    core = StrictPartialOrder([
        credit,
        engineering,
        supplier,
        expedite,
    ])

    if supplier_predecessor == "credit":
        core.order.add_edge(credit, supplier)
    elif supplier_predecessor == "engineering":
        core.order.add_edge(engineering, supplier)
    else:
        raise ValueError("supplier_predecessor must be credit or engineering")

    # D6: Expedite Review follows both principal checks.
    core.order.add_edge(credit, expedite)
    core.order.add_edge(engineering, expedite)

    return core


core_supplier_after_credit = make_balanced_core("credit")
core_supplier_after_engineering = make_balanced_core("engineering")

supplier-information-source_choice = OperatorPOWL(
    Operator.XOR,
    [
        core_supplier_after_credit,
        core_supplier_after_engineering,
    ],
)

register = Transition("Register Order")
approve = Transition("Approve Configuration")
release = Transition("Release Production")
archive = Transition("Archive Case")

model_balanced = StrictPartialOrder([
    register,
    supplier-information-source_choice,
    approve,
    release,
    archive,
])

model_balanced.order.add_edge(register, supplier-information-source_choice)
model_balanced.order.add_edge(supplier-information-source_choice, approve)
model_balanced.order.add_edge(approve, release)
model_balanced.order.add_edge(release, archive)
```

## How sequence, concurrency, and partial order are decided

| Activities | Decision | Reason |
|---|---|---|
| Register Order and core work | Sequence | D1 identifies Register Order as the intended start. |
| Credit Check and Engineering Review | No partial-order edge | V1/V3/V5 show `c` before `e`; V2/V4/V7 show `e` before `c`; D7 and S7 say completion order cannot prove concurrency or start order. |
| Credit Check and Engineering Review actual concurrency | Not asserted | The POWL partial order permits either completion order; it does not state that the work was actually simultaneous. |
| Supplier Confirmation | Optional visible occurrence; follows `c` in one branch or `e` in another | S3/S4/S5 make true occurrence conditional and partially missing. D5 supports an “either information source” interpretation. V5 directly supports `c  s  e`. |
| Expedite Review | Optional; after both `c` and `e` | D6 and S6; both observed Expedite cases satisfy this. |
| Supplier Confirmation and Expedite Review | No edge | V6 has `s  x`; V7 has `x  s`; S6 explicitly permits either. |
| Approval, Release, Archive | Sequence after core | D1, D2, D3, D4, D6, and all observed traces. |

The balanced model does impose a completion-order approximation for D5: if `s` is visible, it must be after the visible completion of either `c` or `e`. This is a modeling choice, not a directly observed fact about starts. It is therefore more conservative than the permissive candidate.

## Behavior deliberately excluded

- Supplier Confirmation completing before both Credit Check and Engineering Review completions.
- Expedite Review before either principal check completes.
- Approval before Credit Check or Engineering Review.
- Approval before a visible Supplier Confirmation or Expedite Review.
- Supplier Confirmation or Expedite Review more than once.
- Supplier Confirmation after approval.
- Release Production before approval or Archive Case before release.

## Known underfitting risks

- If Supplier Confirmation can complete before both principal checks complete because it started after partial information became available, the model rejects valid behavior.
- The hidden XOR branch is an abstraction of an OR-predecessor rule; it does not identify which information source actually triggered supplier work.
- If D3 has legitimate emergency exceptions, the model is too strict.
- The model does not express the actual external/stocked condition, so it cannot distinguish true skips from missing events.
- No rework, cancellation, repeated approval, or multiple supplier contacts are modeled.

# 5. Permissive Candidate

## Inductive bias

`model_permissive` accepts a broader set of completion orders while preserving the strongest domain boundaries. It treats Supplier Confirmation’s relationship to the principal checks as uncertain because D5 concerns the availability of information and activity start, whereas S7 says only completion timestamps are logged. Therefore, Supplier Confirmation may be recorded before either principal check completes, as long as it occurs after registration and before approval. This is deliberately permissive and should be used for exploration, sensitivity analysis, and discovering whether apparent deviations are data-quality artifacts or valid process behavior.

## Compact formal expression

\[
\begin{aligned}
L_P = PO(&\{r,c,e,?s,?x,a,p,z\},\\
         &\{r \prec c,e,?s,?x;\ 
            c \prec ?x;\ 
            e \prec ?x;\\
         &\qquad c,e,?s,?x \prec a;\ 
            a \prec p;\ 
            p \prec z\})
\end{aligned}
\]

The important relaxation is that there is no direct precedence relation between `s` and either `c` or `e`.

## PM4Py POWL code

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def optional_activity(label):
    return OperatorPOWL(
        Operator.XOR,
        [SilentTransition(), Transition(label)]
    )


register = Transition("Register Order")
credit = Transition("Credit Check")
engineering = Transition("Engineering Review")
supplier = optional_activity("Supplier Confirmation")
expedite = optional_activity("Expedite Review")
approve = Transition("Approve Configuration")
release = Transition("Release Production")
archive = Transition("Archive Case")

model_permissive = StrictPartialOrder([
    register,
    credit,
    engineering,
    supplier,
    expedite,
    approve,
    release,
    archive,
])

# Register Order remains the intended visible start.
model_permissive.order.add_edge(register, credit)
model_permissive.order.add_edge(register, engineering)
model_permissive.order.add_edge(register, supplier)
model_permissive.order.add_edge(register, expedite)

# D6: Expedite Review only after both principal checks.
model_permissive.order.add_edge(credit, expedite)
model_permissive.order.add_edge(engineering, expedite)

# D3, D4, and D6: approval waits for both checks and for any selected optional work.
model_permissive.order.add_edge(credit, approve)
model_permissive.order.add_edge(engineering, approve)
model_permissive.order.add_edge(supplier, approve)
model_permissive.order.add_edge(expedite, approve)

# D2 and D1.
model_permissive.order.add_edge(approve, release)
model_permissive.order.add_edge(release, archive)
```

## Boundary between reasonable generalization and forbidden behavior

Reasonable generalization in this candidate includes:

- either recorded completion order of Credit Check and Engineering Review;
- Supplier Confirmation recorded before, between, or after the principal check completions;
- optional visible Supplier Confirmation, because no-Supplier traces may be stocked cases or missing integration events;
- optional Expedite Review after both principal checks;
- either ordering of Supplier Confirmation and Expedite Review.

Behavior remains forbidden when it violates the stronger shared constraints:

- Register Order cannot be preceded by another visible activity.
- Approval cannot occur before both Credit Check and Engineering Review.
- A visible Supplier Confirmation cannot occur after approval.
- Expedite Review cannot occur before either principal check.
- Release Production cannot occur before approval.
- Archive Case cannot occur before release.
- Repeated Supplier Confirmation or Expedite Review is not allowed.

The permissive allowance of `Supplier Confirmation` before the visible completion of both checks is not a claim that procurement starts without information. It is a log-level relaxation motivated by D5’s start-oriented wording and S7’s completion-only data.

## Behavior deliberately excluded

- `Expedite Review` before both principal checks.
- Approval without Credit Check or Engineering Review.
- Supplier Confirmation after approval.
- Release Production before approval.
- Archive Case before release.
- Multiple occurrences of any modeled activity.
- Rework loops, cancellation branches, and multiple supplier-confirmation cycles.

## Known underfitting risks

- Rework, repeated supplier interaction, re-approval, cancellation, and exception handling remain excluded.
- The model cannot enforce “Supplier Confirmation is mandatory for external components” because the external/stocked attribute is absent.
- It may still be too strict if approval exceptions exist despite D3.
- It assumes the visible Supplier Confirmation event, when present, must precede approval.
- It assumes Expedite Review occurs at most once and must follow both checks; this follows D6 but remains unverified by more than two observed cases.

| Conservative | `r, c, e, x, a, p, z` | `x` after `r, c, e` | No exact observed branch permits Expedite Review immediately after that prefix without Supplier Confirmation. |
| Conservative | `r, e, c, s, x, a, p, z` | `x` after `r, e, c, s` | The exact branch with `r, e, c, s` requires approval next; the exact expedited branch has `x` before `s`. |
| Balanced | `r, s, c, e, a, p, z` | `s` immediately after `r` | The balanced source-choice abstraction requires visible `s` after either visible `c` or visible `e`. |
| Balanced | `r, c, x, e, a, p, z` | `x` after `r, c` | D6 is encoded as `c  x` and `e  x`; Engineering Review has not yet completed. |
| Permissive | `r, c, x, e, a, p, z` | `x` after `r, c` | D6 remains enforced: Expedite Review must follow both principal checks. |
| Permissive | `r, c, e, a, s, p, z` | `a` before visible `s` | If Supplier Confirmation occurs visibly, D4 requires it before approval. |

# 7. Comparative Model Matrix

| Criterion | Conservative | Balanced | Permissive |
|---|---|---|---|
| Expected fitness on the 30 observed cases | Very high: every listed trace is explicitly represented. | Very high: all seven observed variants are structurally admitted. | Very high: all seven observed variants are structurally admitted. |
| Expected precision risk | Low risk of over-permission; high risk of rejecting valid unseen cases. | Moderate: generalizes constrained interleavings and optionality. | High: especially around Supplier Confirmation completion order. |
| Generalization potential | Very low. | Moderate and evidence-guided. | High, but some admitted behavior is speculative. |
| Structural simplicity | Low-to-moderate: seven full branches duplicate labels heavily. | Moderate: partial orders plus a latent source-choice XOR. | Moderate-to-high: one partial order with two optional nodes. |
| Explainability | High for literal trace audit, low for explaining actual business rules. | High for business discussion, provided the latent Supplier source-choice is explained. | Moderate: simple structure but broad semantics require careful caveats. |
| Robustness to missing Supplier Confirmation events | Low. Only already observed no-Supplier patterns are accepted. | Moderate-to-high. Visible absence is accommodated as a latent skip/missingness alternative. | High for log replay, but may overstate true business optionality. |
| Handling of unseen interleavings | Rejects all unseen interleavings. | Accepts only interleavings compatible with the selected partial-order assumptions. | Accepts most completion interleavings consistent with approval and expedite constraints. |
| Treatment of C/E concurrency uncertainty | Encodes observed sequences only. | Allows either completion order without claiming actual concurrency. | Allows either completion order without claiming actual concurrency. |
| Treatment of Supplier/Expedite order | Only the two observed combinations. | Both orders allowed after the necessary prerequisites. | Both orders allowed after the necessary prerequisites. |
| Suitability for compliance | Useful as a strict replay baseline, but not a complete policy model. | Best candidate for monitored decision support after policy validation. | Not suitable as an enforcement model without additional controls. |
| Suitability for exploration | Poor. | Good. | Best for exploratory anomaly analysis and sensitivity analysis. |

# 9. Recommendation and Data-Collection Plan

## Recommendation

Use `model_balanced` for immediate monitored use as a **log-level decision-support and conformance model**, not as an unqualified enforcement workflow.

It is the best current compromise because it:

- fits every observed variant;
- enforces D1, D2, D3, D4, D6, and S6;
- accommodates no-Supplier traces without falsely asserting they are all valid business skips;
- accommodates both observed Supplier/Expedite orders;
- avoids falsely declaring that the two principal checks are concurrent;
- does not admit Supplier Confirmation before both visible check completions.

Use `model_conservative` as the formal sensitivity baseline. It answers: “What changes if we refuse every generalization not already observed?” The gap between conservative and balanced conformance will quantify how much operational behavior depends on the proposed generalization.

Use `model_permissive` as an exploratory upper-bound model, especially for data-quality investigation. It should not be used to approve or enforce operational cases until the lifecycle and external/stocked ambiguities are resolved.

## Data-collection plan

| Ambiguity | Data to collect | Why it matters | Most informative future evidence |
|---|---|---|---|
| S1 sequence versus S2 parallel/overlapping checks | Start timestamp, completion timestamp, lifecycle state, worker/system identifier for Credit Check and Engineering Review | Completion order alone cannot identify start precedence or overlap. | Cases showing `Credit Check` starts before Engineering Review starts but Engineering Review completes first; true overlap intervals; or a verified Engineering start before Credit completion. |
| Actual concurrency versus merely varying sequence | Interval timestamps with sufficient precision, not ingestion order | Distinguishes concurrency, overlap, queueing, and independent sequential routing. | A case where the two activity intervals overlap materially; a case where they never overlap but completion order varies by route. |
| Supplier Confirmation mandatory for external components | `component_source` or `external_stocked`, component identifier, supplier-required flag, configuration type | Enables the desired conditional rule instead of an unobserved XOR abstraction. | Verified external orders with and without Supplier Confirmation; verified stocked orders with and without Supplier Confirmation. |
| Missing Supplier Confirmation events | Supplier-system event ID, integration delivery status, message retry status, reconciliation table, source-system audit log | Separates true non-occurrence from missing exported events. | Cases where the source system shows a Supplier Confirmation but the process-mining log does not. |
| D5 “after either check provides enough information” | Information-ready timestamp or state for each check, not only completion | D5 concerns availability of sufficient information, which may precede completion. | Supplier Confirmation starts after Engineering’s information-ready state but before Engineering completion; analogous Credit-driven cases. |
| Supplier/Expedite ordering | Start/end timestamps for Supplier Confirmation and Expedite Review plus expedite reason code | Confirms whether the two activities can overlap or have unobserved ordering rules. | Repeated cases of both `s  x` and `x  s` under known component types and expedite reasons. |
| Expedite eligibility and frequency | Expedite reason, risk tier, policy authorization, and lifecycle timestamps | Tests D6 and determines whether Expedite Review is conditioned on case attributes. | A suspected expedited case where either check is incomplete, which would challenge D6; repeated cases with no Supplier Confirmation. |
| Approval exceptions | Approval override reason, approver role, exception code | Tests whether D3 is truly hard or “normally required.” | Any approved case with an explicitly authorized missing Credit Check or Engineering Review. |

The most discriminating future traces are not merely new permutations. They are traces with the missing attributes and lifecycle timestamps attached. For example:

1. **To distinguish sequence from overlap:**  
   Collect a case where Credit Check starts before Engineering Review starts, but Engineering Review completes first. This supports S1 at the start level while explaining V2/V4/V7 at the completion level.

2. **To distinguish Supplier’s OR-predecessor hypotheses:**  
   Collect Supplier start/completion plus “information ready” timestamps. A case where Supplier starts after Engineering information is ready but before Credit completion supports the Engineering-source branch.

3. **To distinguish optionality from missingness:**  
   Examine known external cases with no visible Supplier Confirmation. Source-system evidence of an unexported event supports missingness; a verified absence supports a policy breach or a revised rule.

4. **To distinguish balanced from permissive Supplier behavior:**  
   A verified case where Supplier Confirmation completes before both principal checks complete, while supplier work began only after a documented information-ready state, supports the permissive completion abstraction.

5. **To distinguish Supplier/Expedite ordering assumptions:**  
   Collect multiple cases with both activities, grouped by component type and expedite reason. If one order systematically occurs only for certain classes, a guarded conditional model is preferable to an unconstrained partial order.

# 10. Uncertainty Statement

| Modeling decision | Calibrated confidence | Basis and caveat |
|---|---|---|
| Register Order first and Archive Case last | High, approximately 0.9+ | D1 and all 30 cases agree. Exceptions such as cancellation or reopened cases remain unobserved. |
| Approve Configuration before Release Production | High, approximately 0.9+ | D2 and all traces agree. This is the strongest internal precedence rule. |
| Both Credit Check and Engineering Review before approval | Medium-to-high, approximately 0.7–0.85 | D3 and all observed traces support it. The wording “should” leaves room for undocumented exception handling. |
| No fixed completion order between Credit Check and Engineering Review | High, approximately 0.9 | Both completion orders are observed repeatedly. This is a statement about recorded completions, not starts. |
| Actual physical concurrency of the two checks | Low, approximately 0.2–0.4 | S2 supports it, but S1 conflicts and S7 prevents direct inference from the data. |
| Supplier Confirmation visible-event optionality | High for log replay, approximately 0.8; medium for true business optionality, approximately 0.45–0.65 | Seven traces lack visible Supplier Confirmation, but S3/S4/S5 show that absence conflates stocked routing and missing events. |
| Balanced rule that visible Supplier Confirmation follows visible completion of either check | Medium-low, approximately 0.45–0.6 | V5 and D5 support a one-check information source, but D5 concerns start/information readiness rather than recorded completion. |
| Expedite Review after both principal checks and before approval | Medium-to-high, approximately 0.7–0.85 | D6, S6, V6, and V7 agree; only two expedited traces exist. |
| No fixed Supplier/Expedite order | Medium-to-high, approximately 0.75 | V6 and V7 demonstrate both visible orders, and S6 explicitly permits both. |
| Permissive allowance of Supplier Confirmation before both visible check completions | Low, approximately 0.2–0.4 | It is a plausible completion-timestamp interpretation, not an observed pattern. It should remain an exploratory assumption. |
| Absence of loops, rework, cancellation, and repeated activities | Low, approximately 0.2–0.4 | No such behavior appears in 30 cases, but absence from a small sample is weak evidence. |

A materially different recommendation would follow if either of these alternatives were verified:

1. **S1 is a hard lifecycle rule and Credit Check must finish before Engineering Review starts.**  
   The completion sequences with `Engineering Review` before `Credit Check` could still occur if Credit Check starts first but takes longer. However, a compliance model would then need start timestamps and likely a lifecycle-aware state model. The current completion-only POWL models would be insufficient for enforcement.

2. **Supplier Confirmation is truly mandatory for all external components and most no-Supplier cases are integration failures rather than stocked cases.**  
   The current optional `s` abstraction would be too permissive. The recommended model should become conditional on a repaired external/stocked attribute, with mandatory Supplier Confirmation for external orders and explicit data-quality handling for missing events.
