## 1. Duplicate-handling decision tree

For each candidate group, first compare stable source keys, complete event attributes, timestamp, and typed E2O relations. A matching activity and timestamp alone never establishes identity.

1. **Exact technical duplicate**: same source system and source event key, same timestamp and complete payload, and the same typed object relations; only transport/event-row identity differs. Keep a deterministic canonical row, record the retired ID, and **drop** only the redundant row. If any attribute or relation differs, continue down the tree.
2. **Same physical event observed by multiple systems**: corroborating reconciliation/business evidence identifies one occurrence, even if enrichment differs. **Merge attributes and relations** under explicit field authority rules, retain every source record and relation origin, and assign a canonical event ID. If relations conflict materially, quarantine rather than union blindly.
3. **Summary event derived from a detailed event**: if it denotes a distinct reporting/status transition, **retain both with refined labels or qualifiers**. Merge only when evidence says one business occurrence is the intended unit of analysis, the summary relations add no incompatible object links, and the lost abstraction boundary is recorded.
4. **Harmonization collision between semantically distinct source activities**: restore/refine source semantics and **retain both with refined labels or qualifiers**. Shared time and objects do not undo distinct meanings.
5. **Concurrent same-label events involving different objects**: **retain both unchanged** when the same activity is a valid repeated event, such as distinct item picks or payment captures. Preserve concurrency unless a causal rule orders them.
6. **Unresolved candidate**: **quarantine for review** (or retain both unchanged in a production log with a review flag). Do not silently drop or merge it.

## 3. Timestamp-tie ordering rules

Keep the UTC business timestamp immutable as `original_timestamp`. Build a precedence graph for events at a timestamp, then topologically sort it. Use the following precedence sources in order:

- **Domain constraints (semantic):** known causality such as authorization before capture, release before carrier acceptance, acceptance before handover, and a payment-balance summary after the messages that generated it. Treat invoice issuance before payment authorization as a business invariant only if confirmed by the process owner; otherwise leave those events unordered.
- **Within-source sequence (semantic when the source contract says it is meaningful):** compare `source_seq` only for events from the same source. Never compare ERP 40 with PSP 400 as if they shared a clock.
- **Shared-object lifecycle constraints (semantic when valid for that object):** picks precede packing for the picked items; do not infer order between independent item or payment objects solely because they share O1.
- **Source-specific semantics (semantic):** the source meaning distinguishes release, acceptance, handover, detail transaction, and summary update even when the harmonized label does not.
- **Ingestion time (not business order):** use only to diagnose latency or as a last-resort operational display hint, never as the primary event order.
- **Stable fallback (deterministic only):** among incomparable events use a fixed key such as source name, source event key, then eid. This creates reproducible output, not evidence of physical order.

Adding microseconds before resolving semantic constraints can turn an arbitrary tie-break into a fake causal sequence, create positive durations for simultaneous events, change performance statistics, and make a downstream analyst believe that order was observed. Synthetic timestamps therefore come last and original timestamps remain available for analysis.

At 10:00, after e03/e04 merge, the supported order is e03 (I1 pick), e05 (I2 pick), e06 (detailed pack), then e07 (ERP summary), given scanner sequence and pick-before-pack lifecycle plus WMS-to-ERP derivation. If the summary is merged, the sequence ends at the unified e06. The two item picks are distinct; their relative order is also supported by scanner sequence e04 then e05, with e04 representing the e03 physical scan.

At 10:15, order e08 release → e09 carrier acceptance → e10 handover. The first relation follows the meanings of release and acceptance and should be checked against domain rules; acceptance before handover is explicitly known.

At 12:00, merge e11/e16 into invoice issuance e11. With invoice-before-payment confirmed, the intended order is e11 → e12 authorization M1 → e13 capture M1 → e14 capture M2 → e15 ERP balance summary. PSP sequence 400–402 supports e12/e13/e14, and e15 is known to follow payment messages. Without the invoice invariant, e11 is unordered relative to e12–e14; stable fallback may display it first, but must mark that placement as deterministic only. e15 remains after its triggering messages.

## 4. Conservative cleaning pipeline

Start with a deep copy and a strict duplicate pre-check. Remove only exact technical row repeats if the complete source key, payload, timestamp, and typed relations match. In this fixture, no pair is an exact technical duplicate by that strict test. Then custom-merge e03/e04 using the reconciliation report and e11/e16 using invoice V1 and field-level authority. Keep relation origins and avoid unioning relations when object semantics conflict. Retain e06/e07 as distinct detail and summary observations. Refine e07, e08, e09, and optionally e15 to expose their source meanings while preserving the original harmonized activity. Preserve original IDs, source keys, source labels, and timestamps. Apply the partial-order rules; use a stable fallback only for unresolved ties. PM4Py’s tie sorting and index-based timedelta can create a reproducible display order after those decisions, but keep the untampered time column for durations and audit.

The retained count is **15 events**: 17 raw rows minus one e03/e04 observation and one e11/e16 observation. Label refinement and tie ordering do not change count. Raw E2O incidence is 44 links; the two merges remove three redundant links in total (three links for e04, two for e16, with the e11 pair’s two links represented once), leaving **39**. More precisely, e03/e04 remove three and e11/e16 remove two, so 44 − 5 = **39**.

## 5. Aggressive alternatives

**Evidence-based semantic merge (14 events).** Apply the conservative merges and, for an analysis whose unit is the business transition rather than system observations, also merge e06/e07 into e06. Evidence that e07 was generated from the WMS message supports this choice, but preserve the ERP summary snapshot and mark the abstraction boundary. Its O1/P1 relations are already within e06’s O1/I1/I2/P1 set, so this scenario need not add relations. Expected E2O count: **37** (39 minus e07’s two repeated links). This can erase the useful distinction between a detailed packing transaction and an ERP status transition.

**Mechanically aggressive PM4Py merge (expected 11 events).** Run `ocel_merge_duplicates` over the raw OCEL with the common-object predicate enabled, without semantic candidate review. Under a same-activity, same-timestamp, any-common-object interpretation, it collapses e03/e04/e05 to one, e06/e07 to one, e08/e09 to one, e11/e16 to one, and e13/e14 to one: 17 − 2 − 1 − 1 − 1 − 1 = **11**. Assuming the merge unions relations, E2O falls from 44 to about **30**: reductions of 5 pick links, 2 pack links, 3 dispatch links, 2 invoice links, and 2 capture links. Confirm actual grouping and counts against the installed PM4Py version; the function’s matching/union behavior is not a semantic guarantee.

`have_common_object=True` cannot protect e13 and e14: both share O1 and V1, although one captures M1 and the other M2. Under a common-object test they can collapse, and relation union can create one event linked to both Payments. Shared objects indicate context, not identity. The same weakness is even clearer for e03/e05 and e08/e09.

## 6. PM4Py-oriented Python implementation

This assumes the standard PM4Py OCEL columns (`ocel:eid`, `ocel:activity`, `ocel:timestamp`, and `ocel:eid`/`ocel:oid` in `relations`). Map the constants if the loaded OCEL uses different names. The exact-dedup pass temporarily gives nonmatching events unique activities, so PM4Py’s duplicate helper can only act on groups already verified as byte-for-byte/source-key exact. This fixture has no such group. Pair merges require matching relations, except the optional detailed/summary merge, where the summary relation set must be a subset.

```python
from copy import deepcopy
from collections import defaultdict
import json
import pandas as pd
import pm4py

EID, ACT, TS = "ocel:eid", "ocel:activity", "ocel:timestamp"
OID, REL_EID, REL_OID = "ocel:oid", "ocel:eid", "ocel:oid"
SOURCE, SOURCE_KEY = "source", "source_event_key"

def relset(o, eid):
    r = o.relations[o.relations[REL_EID] == eid]
    cols = [c for c in (REL_OID, "ocel:type") if c in r.columns]
    return frozenset(tuple(row) for row in r[cols].itertuples(index=False, name=None))

def validate(o):
    assert not o.events[EID].duplicated().any()
    assert set(o.relations[REL_EID]) <= set(o.events[EID])
    assert set(o.relations[REL_OID]) <= set(o.objects[OID])

def prepare(src):
    o = deepcopy(src)
    o.events["original_timestamp"] = o.events[TS].copy()
    o.events["original_activity"] = o.events[ACT].copy()
    # source and source_event_key remain unchanged in their original columns.
    return o

def strict_exact_groups(o):
    # Includes all event attributes except event-row identity and derived audit fields,
    # plus the complete typed relation set. repr() makes nested values hashable.
    ignored = {EID, "_source_records_json", "_merge_rule"}
    groups = defaultdict(list)
    for _, row in o.events.iterrows():
        attrs = tuple((c, repr(row[c])) for c in sorted(o.events.columns) if c not in ignored)
        sig = (attrs, tuple(sorted(map(repr, relset(o, row[EID])))))
        groups[sig].append(row[EID])
    return [ids for ids in groups.values() if len(ids) > 1]

def strict_exact_dedup(o):
    groups = strict_exact_groups(o)
    x = deepcopy(o)
    # Ensure the library cannot match any unverified pair on activity/time/object.
    x.events["_pre_dedup_activity"] = x.events[ACT]
    temp = {eid: f"__unique__{eid}" for eid in x.events[EID]}
    for i, ids in enumerate(groups):
        for eid in ids:
            temp[eid] = f"__verified_exact_{i}__"
    x.events[ACT] = x.events[EID].map(temp)
    x = pm4py.ocel_drop_duplicates(x)
    # Restore each surviving row’s original harmonized activity.
    originals = o.events.set_index(EID)[ACT].to_dict()
    x.events[ACT] = x.events[EID].map(originals)
    x.events.drop(columns=["_pre_dedup_activity"], inplace=True, errors="ignore")
    return x

def merge_pair(o, canonical, duplicate, rule, allow_subset=False, authority=None):
    authority = authority or {}  # attribute column -> preferred source name
    x = deepcopy(o)
    a = x.events.loc[x.events[EID] == canonical].iloc[0].copy()
    b = x.events.loc[x.events[EID] == duplicate].iloc[0].copy()
    ra, rb = relset(x, canonical), relset(x, duplicate)
    if allow_subset:
        if not (ra <= rb or rb <= ra):
            raise ValueError("quarantine: incompatible relation sets")
    elif ra != rb:
        raise ValueError("quarantine: verified merge has conflicting relations")

    prior = []
    for row in (a, b):
        old = row.get("_source_records_json")
        prior.extend(json.loads(old) if isinstance(old, str) else [row.to_dict()])
    # Resolve only fields with declared authority. Unlisted conflicts stay in snapshots.
    for col, preferred_source in authority.items():
        if col in x.events.columns:
            candidates = [row for row in (a, b) if row.get(SOURCE) == preferred_source]
            if candidates and pd.notna(candidates[0].get(col)):
                a[col] = candidates[0][col]
    a["_source_records_json"] = json.dumps(prior, default=str)
    a["_source_event_ids_json"] = json.dumps([canonical, duplicate])
    a["_merge_rule"] = rule
    x.events.loc[x.events[EID] == canonical, a.index] = a.values
    x.events = x.events[x.events[EID] != duplicate].copy()
    x.relations.loc[x.relations[REL_EID] == duplicate, REL_EID] = canonical
    x.relations.drop_duplicates(inplace=True)
    return x

def refine(o):
    x = deepcopy(o)
    labels = {
        "e07": "Pack Package (ERP summary)",
        "e08": "Release Package from Warehouse",
        "e09": "Carrier Accepts Package",
        "e15": "ERP Payment Summary",
    }
    for eid, label in labels.items():
        x.events.loc[x.events[EID] == eid, ACT] = label
    return x

raw = prepare(ocel_raw)
conservative = strict_exact_dedup(raw)
conservative = merge_pair(conservative, "e03", "e04", "reconciled_same_scan",
                          authority={"location": "WMS"})
conservative = merge_pair(conservative, "e11", "e16", "invoice_V1_field_authority")
conservative = refine(conservative)
validate(conservative)

evidence = deepcopy(conservative)
# Explicit sensitivity scenario: one business transition; summary O1/P1 links
# are a subset of detailed WMS links. Preserve both source rows in the audit field.
evidence = merge_pair(evidence, "e06", "e07", "derived_summary_same_transition",
                      allow_subset=True)
validate(evidence)

# Separate mechanically aggressive scenario; never use this as the canonical clean log.
aggressive = prepare(ocel_raw)
aggressive = pm4py.ocel_merge_duplicates(
    aggressive, have_common_object=True,
    activity_key=ACT, timestamp_key=TS
)
validate(aggressive)

def establish_order_then_adjust(o):
    x = deepcopy(o)
    # Rank is only a tie-break after semantic precedence has been reviewed.
    rank = {"e03": 100, "e05": 110, "e06": 120, "e07": 130,
            "e08": 200, "e09": 210, "e10": 220,
            "e11": 300, "e12": 310, "e13": 320, "e14": 330, "e15": 340}
    x.events["_stable_tie_key"] = x.events.apply(
        lambda r: f"{rank.get(r[EID], 900):04d}|{r[EID]}", axis=1)
    x = pm4py.ocel_sort_by_additional_column(x, "_stable_tie_key")
    # Called only after the partial order and stable tie key are established.
    x = pm4py.ocel_add_index_based_timedelta(x, timestamp_key=TS)
    validate(x)
    return x

conservative_ordered = establish_order_then_adjust(conservative)
evidence_ordered = establish_order_then_adjust(evidence)
aggressive_ordered = establish_order_then_adjust(aggressive)
```

For production use, persist the precedence edges and verify the installed PM4Py function signatures. Do not use adjusted timestamps as business times.

## 7. Sensitivity analysis

Counts below assume typed relations are unioned only as described: raw **17 events/44 E2O links**; conservative **15/39**; evidence-based **14/37**; aggressive common-object merge **11/30**. Counts for the aggressive case depend on the installed function’s matching and relation-union behavior, so record observed counts and group membership.

- **Order-flattened DFG:** raw may show repeated `Pick Item → Pick Item` from e03/e04/e05, repeated `Pack Package → Pack Package` from e06/e07, `Dispatch Package → Dispatch Package` from e08/e09, and `Issue Invoice → Issue Invoice` from e11/e16. Conservative removes the duplicate scan/invoice contribution while preserving a real second pick and the pack detail/summary distinction. Refined release and acceptance become separate nodes. Aggressive can erase both the second pick and the two distinct logistics meanings. All tied-edge frequencies remain sensitive to the chosen display order.
- **Item-flattened DFG:** e03/e04 can inflate an I1 pick count or create an I1 `Pick Item → Pick Item` self-loop; e05 is a genuine I2 pick and must remain. e06 links both items to packing. Merging e07 into e06 has no new Item relations in this fixture, but an indiscriminate relation union in other data could falsely attach a summary to item lifecycles.
- **Payment-flattened DFG:** M1 has `Authorize Payment → Capture Payment`; M2 has a distinct capture. The PSP sequence also supports `Capture Payment → Capture Payment` at invoice/order level as two partial captures. Collapsing e13/e14 removes that pattern and may attach one synthetic capture to both M1 and M2. e15 is an invoice-level balance update, not a capture linked to either payment.
- **OC-DFG edges and frequency metrics:** duplicate event removal lowers frequencies on affected event/object paths. The meaningful second pick and second partial capture should still contribute. Merge of e13/e14 can create a cross-payment event incidence that did not occur. Ties can change directly-follows edges even when event counts do not change.
- **ET–OT weights:** conservative cleaning reduces Pick Item-to-Item and Issue Invoice-to-Invoice relation counts while retaining distinct Pick Item and Capture Payment occurrences. Evidence-based pack merging removes redundant Pack-to-Order and Pack-to-Package incidences. Aggressive merging also lowers Dispatch-to-Delivery and Capture-to-Payment counts; these weights then understate logistics and payment activity.
- **OTG relations:** e13/e14 union may create a false M1–M2 co-occurrence edge because distinct Payment objects become related to one event. Likewise a merged pick may make I1 and I2 look co-involved in one scan. Preserve separate relation provenance to detect such artifacts.
- **ET–OT weights and lifecycle/performance:** synthetic microseconds can give zero-time ties apparent positive durations, alter waiting-time distributions, and fabricate ordering-based lifecycle counts. Calculate durations from original timestamps; report tied or interval-valued order where the source cannot establish sequence. Retaining e06/e07 may look like rework unless labels distinguish detailed packing from ERP summary.

Concrete interpretations that change include `Pick Item → Pick Item`, `Pick Item → Pack Package`, `Pack Package → Pack Package`, `Dispatch Package → Dispatch Package`, `Carrier Accepts Package → Handover to Carrier`, `Issue Invoice → Authorize Payment`, `Authorize Payment → Capture Payment`, `Capture Payment → Capture Payment`, and `Capture Payment → ERP Payment Summary`. The first, third, fourth, sixth, and eighth can be frequency artifacts or valid transitions depending on the chosen dataset and relation scope; the distinctions above determine which interpretation is defensible.

## 8. Audit trail and reversibility

Store an append-only merge record with: canonical event ID; every source event ID; source and source event key; merge rule and rule version; reviewer or automated rule identity; confidence and rationale; original and refined activity; original and adjusted timestamp; per-source attribute snapshots; chosen value and authority for each merged field; discarded/conflicting values; original and resulting typed E2O relations with relation origins; and any quarantine decision. A merged event’s canonical columns support analysis while a sidecar provenance table preserves source-grain values. To reconstruct the raw view, expand each canonical event into its stored source rows, restore each original ID/activity/timestamp/attribute set, restore relation-origin rows, and discard synthetic ordering timestamps. Do not attempt reconstruction from the flattened canonical OCEL alone.

## 9. Failure modes and safeguards

1. Collapsing M1 and M2 captures because they share O1/V1; key identity on the Payment object and source evidence.
2. Converting an ERP summary into a second physical pack or capture; retain abstraction labels and derivation links.
3. Ordering by ingestion time; keep it as latency metadata and use business constraints/source-local sequence.
4. Treating shared objects as proof of duplication; require identity evidence and compare typed relations.
5. Unioning incompatible E2O relations; validate relation equivalence or a declared subset rule before merging.
6. Changing durations through synthetic microseconds; preserve original timestamps and exclude adjusted times from performance calculations.
7. Losing source-authoritative attributes through last-write-wins; use per-field authority and preserve all conflicts.
8. Applying duplicate functions to the whole OCEL without inspecting candidate groups; pre-check exact keys and review groups before any broad merge.
9. Treating equal activity and timestamp as a duplicate key; protect valid repeated picks and partial payments.
10. Comparing `source_seq` across systems; sequence is local to its own source only.
11. Letting deterministic eid/source sorting be reported as observed physical order; label fallback edges as unresolved ties.
12. Deleting original labels, IDs, or relation provenance after refinement; make each transformation reversible from the audit record.
