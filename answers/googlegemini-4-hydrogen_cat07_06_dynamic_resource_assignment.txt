# 1. Objectives and constraints

Dynamic resource assignment in a knowledge-intensive service process is a multi-criteria socio-technical problem rather than a pure mathematical optimization with a single global optimum. Improving short-term throughput can starve skill development; maximizing immediate quality via specialist-only routing creates severe bottlenecks and burnout; and enforcing strict continuity can trap complex cases with under-skilled owners. The proposed policy (**Balanced Risk- & Continuity-Aware Assignment, BRCA**) makes these trade-offs explicit and configurable.

## Optimization objectives
The policy seeks a defensible balance across six competing objectives:
1. **SLA risk minimization (Short-term timeliness):** Prioritize urgent/high-priority cases and tight SLA deadlines, avoiding queueing delays on critical paths.
2. **Quality & rework minimization:** Match task complexity and risk to appropriate skill levels, avoiding the 3.3h service-time penalty and rework risk of weak-skill execution.
3. **Continuity of ownership:** Preserve current ownership when handover costs are high (avoiding the 2.7h median waiting penalty on high-complexity cases and the 1.8x rework / 1.4x appeal escalation observed after $>2$ reassignments).
4. **Workload fairness & overtime protection:** Smooth open-case counts and remaining daily capacity, protecting high-overtime-risk workers from burnout.
5. **Skill development (Long-term capacity):** Allocate structured, low-risk training and supervised opportunities aligned with each worker's documented training priority.
6. **Operational resilience & bottleneck avoidance:** Prevent single-point-of-failure queues in scarce competencies (especially `Security` and `Approval`) through cross-skilling, preparation/finalization splits, and safe batching.

## Hard constraints (Safety, compliance, and capacity boundaries)
Hard constraints filter out infeasible candidates before any scoring occurs; they cannot be overridden by throughput preferences:
- **H1 — Skill prohibition:** A resource with skill score `0` (`not allowed`) for the required activity cannot execute that activity (even under supervision; they may only observe/shadow in a non-executing capacity).
- **H2 — Batch intake cap:** No resource may receive more than **4** new assignments in the current decision batch.
- **H3 — High-priority skill floor:** No `urgent` or `high` priority case may be assigned to a resource with skill `< 2` unless paired with an explicit supervisor (`skill >= 2`, or `3` for Security).
- **H4 — Security Review compliance:** `Security Review` must be executed by a `skill = 3` specialist (`R7_Gita` or `R8_Hugo`), or by `skill = 1–2` *only* under explicit supervision by `R7_Gita` or `R8_Hugo`.
- **H5 — Final Approval authority:** `Final Approval` sign-off must be performed by `skill = 2–3`. `skill = 1` resources may act as preparers in a supervised pair, but may not finalize.
- **H6 — Daily hour feasibility:** Do not assign urgent work expected to exceed a resource's `hours_remaining_today` unless co-assigned or explicitly escalated.

## Soft constraints & preference trade-offs
Soft constraints govern tie-breaking and weighted scoring; deviations are permitted when documented in `assignment_reason`:
- **S1 — Overtime protection:** Avoid assigning new work to `overtime_risk = high` resources (`R2_Bruno`, `R4_David`, `R9_Iris`) unless SLA is `urgent` and no safer eligible resource/pair exists.
- **S2 — Continuity on high-risk handovers:** For high-complexity (`>= 0.70`) cases with `handover_cost = high`, retain the current owner unless they have `skill <= 1` and no supervision is feasible.
- **S3 — Training quota:** At least **20%** of `normal`/`low`-priority assignments should support documented `training_priority` goals, provided SLA buffers remain safe.
- **S4 — Safe Quality batching:** `Quality Check` cases may be batched only when priority is `normal`/`low` and `sla_time_remaining > 24h`.

# 2. Assignment policy

The BRCA policy runs in two stages: **(A) Case Triage Order** (preventing low-priority tasks from consuming scarce specialist capacity before urgent cases are placed) and **(B) Candidate Filtering, Scoring, and Exception Handling**.

## Algorithm / Pseudocode

```python
def assign_queue(cases, resources, batch_limit=4, training_target_share=0.20):
    # Stage 1: Order cases so urgent/high-SLA and high-continuity constraints are solved first
    # Sort by: priority_rank (urgent=3, high=2, normal=1, low=0) DESC,
    #          sla_time_remaining ASC,
    #          case_complexity DESC
    ordered_cases = sort_cases(cases)
    assignments = {}
    new_count = {r.id: 0 for r in resources}
    normal_low_cases = [c for c in ordered_cases if c.priority in ("normal", "low")]
    training_assigned = 0

    for case in ordered_cases:
        # 1. ELIGIBILITY FILTERING (Hard constraints H1-H6)
        candidates = []  # each candidate is either ("solo", r) or ("pair", worker, supervisor)
        for r in resources:
            if new_count[r.id] >= batch_limit:
                continue
            skill = r.skills[case.required_skill]
            if skill == 0:
                continue  # H1: skill 0 strictly prohibited from execution

            # H4: Security Review rules
            if case.activity == "Security Review":
                if skill == 3:
                    candidates.append(("solo", r, None))
                elif skill in (1, 2):
                    for sup in get_security_supervisors(resources, new_count, batch_limit):
                        if sup.id != r.id:
                            candidates.append(("pair", r, sup))
                continue

            # H5: Final Approval rules
            if case.activity == "Final Approval":
                if skill >= 2:
                    candidates.append(("solo", r, None))
                elif skill == 1:
                    for sup in get_approval_finalizers(resources, new_count, batch_limit):
                        if sup.id != r.id:
                            candidates.append(("pair", r, sup))
                continue

            # H3: High/Urgent priority skill floor
            if case.priority in ("urgent", "high") and skill < 2:
                for sup in get_domain_supervisors(resources, case.required_skill, new_count, batch_limit):
                    if sup.id != r.id:
                        candidates.append(("pair", r, sup))
                continue

            # Normal/Low cases with skill == 1 can run solo (if low complexity) or supervised
            candidates.append(("solo", r, None))
            if skill == 1:
                for sup in get_domain_supervisors(resources, case.required_skill, new_count, batch_limit):
                    if sup.id != r.id:
                        candidates.append(("pair", r, sup))

        # 2. MULTI-OBJECTIVE SCORING
        scored = []
        for mode, worker, sup in candidates:
            # (a) SLA Urgency & Capacity Fit Score [0..1]
            # Penalize low remaining hours on urgent/high cases
            est_hours = estimate_service_hours(case, worker.skills[case.required_skill])
            sla_slack = case.sla_time_remaining - est_hours
            if case.priority in ("urgent", "high") and worker.hours_remaining < est_hours:
                sla_score = -0.5  # capacity shortfall penalty
            else:
                sla_score = min(1.0, max(0.0, sla_slack / max(case.sla_time_remaining, 1.0)))

            # (b) Skill-Match Score [0..1]
            eff_skill = worker.skills[case.required_skill] if mode == "solo" else max(worker.skills[case.required_skill], sup.skills[case.required_skill])
            # Match high complexity to skill 3; avoid wasting skill 3 on trivial low-complexity work if alternatives exist
            if case.case_complexity >= 0.70:
                skill_score = eff_skill / 3.0
            else:
                skill_score = 1.0 - 0.15 * abs(eff_skill - 2.2)

            # (c) Continuity / Handover-Cost Score [0..1]
            is_owner = (worker.id == case.current_owner) or (sup and sup.id == case.current_owner)
            handover_weight = {"high": 1.0, "medium": 0.6, "low": 0.25, "none": 0.0}[case.handover_cost]
            reassignment_penalty = 0.25 * max(0, case.reassignment_count - 1)  # escalates sharply at >=2
            if is_owner:
                continuity_score = min(1.0, 0.5 + handover_weight + reassignment_penalty)
            else:
                continuity_score = max(0.0, 0.5 - handover_weight - reassignment_penalty)

            # (d) Workload & Overtime Fairness Score [0..1]
            effective_open = worker.open_cases + new_count[worker.id]
            load_norm = max(0.0, 1.0 - (effective_open / 16.0))
            ot_penalty = {"low": 0.0, "medium": 0.15, "high": 0.75}[worker.overtime_risk]
            if sup and sup.overtime_risk == "high":
                ot_penalty += 0.40
            # Soft constraint S1: strong gate against overtime_risk == "high" unless urgent & no alternative
            if (worker.overtime_risk == "high" or (sup and sup.overtime_risk == "high")) and case.priority != "urgent":
                fairness_score = load_norm - 1.0  # effectively disqualifies while non-high-OT options exist
            else:
                fairness_score = load_norm - ot_penalty

            # (e) Training / Development Score [0..1]
            matches_training = (worker.training_priority == case.required_skill.lower())
            training_quota_open = (training_assigned / max(1, len(normal_low_cases))) < training_target_share
            if case.priority in ("normal", "low") and matches_training:
                training_score = 1.0 if training_quota_open else 0.5
            elif mode == "pair" and case.priority in ("normal", "low"):
                training_score = 0.4
            else:
                training_score = 0.0

            # (f) Resilience / Bottleneck Avoidance & Batching [0..1]
            # Protect scarce Security (R7, R8) and Approval (R5, R6) specialists from routine non-specialist tasks
            scarcity_penalty = 0.25 if (worker.id in ("R6_Farid", "R7_Gita", "R8_Hugo")
                                        and case.required_skill not in ("Security", "Approval", "Negotiation")) else 0.0
            batch_bonus = 0.25 if (case.activity == "Quality Check"
                                   and case.priority in ("normal", "low")
                                   and case.sla_time_remaining > 24
                                   and already_assigned_quality(worker.id, assignments)) else 0.0
            resilience_score = 0.5 + batch_bonus - scarcity_penalty

            # Dynamic weights shift by priority & complexity
            w_sla   = 0.30 if case.priority in ("urgent", "high") else 0.15
            w_skill = 0.25 if case.case_complexity >= 0.65 else 0.15
            w_cont  = 0.25 if case.handover_cost == "high" or case.reassignment_count >= 2 else 0.15
            w_fair  = 0.25
            w_train = 0.20 if case.priority in ("normal", "low") else 0.0
            w_resil = 0.10

            total_score = (w_sla * sla_score + w_skill * skill_score + w_cont * continuity_score
                           + w_fair * fairness_score + w_train * training_score + w_resil * resilience_score)

            scored.append((total_score, mode, worker, sup, build_reason(...)))

        # 3. TIE-BREAKING & EXCEPTION HANDLING
        # Tie-break: (1) lower open_cases + new_count, (2) higher hours_remaining, (3) current_owner
        if not scored:
            # Exception path: relax S1 (high-OT gate) or escalate for manager split/shadowing
            assignments[case.id] = escalate_or_shadow(case, resources, new_count)
        else:
            best = select_best_with_tiebreak(scored)
            assignments[case.id] = best
            update_counts(new_count, best)
            if best.supports_documented_training:
                training_assigned += 1

    return assignments
```

## Shadowing rule for `skill = 0` training priorities
Notice an important edge case in the workforce matrix: `R5_Eva` and `R10_Jonas` have `training_priority = security` (`skill = 0`), and `R8_Hugo` has `training_priority = approval` (`skill = 0`). Because `skill = 0` prohibits execution (H1/H4/H5), the policy handles these through **non-executing shadowing**: an eligible specialist executes and signs off while the `skill = 0` trainee observes/prepares non-authoritative checklists to build prerequisite readiness toward `skill = 1`.

# 6. Process-mining audit indicators

Using the event log schema (`case:concept:name`, `concept:name`, `time:timestamp`, `org:resource`, `required_skill`, `case_priority`, `sla_deadline`, `case_complexity`, `current_owner`, `team`, `assignment_reason`, `reassignment_count`, `workload_snapshot`, `handover_cost_band`), auditors can compute the following indicators:

1. **Handover frequency:** Count and rate of resource transitions between consecutive events within a case ($\text{resource}_{i} \neq \text{resource}_{i-1}$), segmented by `handover_cost_band` and `case_complexity`. *Target:* declining handovers on `high` complexity/handover-cost cases.
2. **Reassignment count:** Distribution of `reassignment_count` at case completion and share of cases exceeding $>2$ reassignments. *Target:* $<5\%$ of cases reaching $\ge 3$ reassignments.
3. **Skill mismatch rate:** Share of events where the executing `org:resource` had `skill < 2` on `urgent`/`high` cases without a logged supervisory event, or `skill = 0` on any event. *Target:* $0\%$ unauthorized mismatches.
4. **Workload distribution (Gini / coefficient of variation):** Spread of active assignments and service hours across `org:resource` and `team` using `workload_snapshot`, compared against `hours_remaining_today`.
5. **Overtime risk exposure:** Percentage of new assignments routed to `overtime_risk = high` resources during non-urgent priorities (`normal`/`low`), plus late-day timestamp clustering. *Target:* $0\%$ non-urgent routing to `high` OT when safe alternatives exist.
6. **SLA misses:** Share of cases where completion `time:timestamp > sla_deadline`, stratified by `case_priority` and `assignment_reason`.
7. **Rework / appeal rate after assignment:** Frequency of loop-back transitions (e.g., `Technical Diagnosis` $\rightarrow$ `Rework Correction` $\rightarrow$ `Technical Diagnosis`) and post-approval appeals conditioned on whether the prior step involved a handover or skill mismatch.
8. **Training assignment share:** Share of `normal`/`low` events tagged with `assignment_reason = training_pair` or `training_shadow` matching the worker's `training_priority`. *Target:* $\ge 20\%$.
9. **Specialist bottleneck indicators:** Waiting time (`time_between_events`) and queue depth ahead of `Security Review` and `Final Approval`, plus share of scarce specialists' time spent on routine low-skill activities.
10. **Policy deviation rate:** Share of events where actual `org:resource` diverges from policy recommendation (or lacks a valid `assignment_reason`), tracked to detect informal workarounds, alert fatigue, or stale skill-matrix data.

# 7. PM4Py implementation sketch

The sketch below illustrates how to load the service event log in PM4Py, discover organizational/handover structures, measure service and waiting times, isolate bottleneck segments, and audit policy compliance.

```python
import pandas as pd
import pm4py

# 1. Load and format the event log
raw_df = pd.read_csv("service_process_log.csv")
raw_df["time:timestamp"] = pd.to_datetime(raw_df["time:timestamp"])

log_df = pm4py.format_dataframe(
    raw_df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
)

# 2. Organizational & social-network discovery (Audit handovers, pairs, roles, similarity)
# Handover-of-work network: reveals excessive bouncing between resources/teams
hw_network = pm4py.discover_handover_of_work_network(log_df)
pm4py.save_vis_sna(hw_network, "audit_handover_network.html")

# Working-together network: verifies whether supervised training pairs (e.g., R1+R3, R10+R6) collaborate
wt_network = pm4py.discover_working_together_network(log_df)
pm4py.view_sna(wt_network)

# Organizational roles & activity-based resource similarity: detects rigid silos vs cross-skilling
org_roles = pm4py.discover_organizational_roles(log_df)
resource_sim = pm4py.discover_activity_based_resource_similarity(log_df)

# Batching discovery: audits whether Quality Check batching complies with policy
discovered_batches = pm4py.discover_batches(log_df)

# 3. Performance DFG, service times, and waiting times
# Service and waiting times per case (used to calibrate est_hours & handover delay priors)
avg_service_time = pm4py.get_service_time(log_df)
log_with_times = pm4py.insert_case_service_waiting_time(log_df)

# Performance DFG highlights waiting-time bottlenecks before Security Review / Final Approval
perf_dfg, start_acts, end_acts = pm4py.discover_performance_dfg(log_df)

# 4. Filtering by case attributes & performance to audit rework and urgent SLAs
# Isolate urgent/high-priority cases to check SLA adherence and skill compliance
urgent_log = pm4py.filter_event_attribute_values(
    log_df,
    attribute_key="case_priority",
    values=["urgent", "high"],
    level="case",
    retain=True,
)

# Isolate slow/outlier cases (e.g., > 24 hours total duration) to inspect root causes
slow_cases_log = pm4py.filter_case_performance(
    log_df,
    min_performance=24 * 3600,
    max_performance=float("inf"),
)

# Check rework variants in slow cases (e.g., repeated Technical Diagnosis -> Rework Correction loops)
slow_variants = pm4py.get_variants(slow_cases_log)

# 5. Policy-audit indicator calculation directly from log columns
def compute_audit_kpis(df: pd.DataFrame, skill_matrix: dict, ot_risk_map: dict) -> dict:
    df_sorted = df.sort_values(["case:concept:name", "time:timestamp"]).copy()
    df_sorted["prev_resource"] = df_sorted.groupby("case:concept:name")["org:resource"].shift(1)
    df_sorted["is_handover"] = (
        df_sorted["prev_resource"].notna()
        & (df_sorted["org:resource"] != df_sorted["prev_resource"])
    )

    high_cost_df = df_sorted[df_sorted["handover_cost_band"] == "high"]
    normal_low_df = df_sorted[df_sorted["case_priority"].isin(["normal", "low"])]

    # Check high-priority skill mismatches without documented supervision
    def is_unsupervised_mismatch(row):
        skill = skill_matrix.get((row["org:resource"], row["required_skill"]), 0)
        supervised = "supervis" in str(row["assignment_reason"]).lower()
        return (row["case_priority"] in ("urgent", "high")) and (skill < 2) and (not supervised)

    df_sorted["skill_mismatch"] = df_sorted.apply(is_unsupervised_mismatch, axis=1)
    df_sorted["ot_exposure"] = df_sorted["org:resource"].map(ot_risk_map).eq("high") & df_sorted["case_priority"].isin(["normal", "low"])
    df_sorted["sla_missed"] = pd.to_datetime(df_sorted["time:timestamp"]) > pd.to_datetime(df_sorted["sla_deadline"])

    return {
        "overall_handover_rate": float(df_sorted["is_handover"].mean()),
        "high_cost_handover_rate": float(high_cost_df["is_handover"].mean()) if len(high_cost_df) else 0.0,
        "cases_gt2_reassignments_share": float((df_sorted.groupby("case:concept:name")["reassignment_count"].max() > 2).mean()),
        "urgent_high_skill_mismatch_rate": float(df_sorted["skill_mismatch"].mean()),
        "non_urgent_high_ot_exposure": float(df_sorted["ot_exposure"].mean()),
        "training_share_normal_low": float(normal_low_df["assignment_reason"].str.contains("train", case=False, na=False).mean()),
        "sla_miss_rate": float(df_sorted.groupby("case:concept:name")["sla_missed"].any().mean()),
        "policy_deviation_rate": float(df_sorted["assignment_reason"].str.contains("override|manual_deviation", case=False, na=False).mean()),
    }
```

### Continuous learning loop
By periodically re-running `discover_performance_dfg`, `get_service_time`, and `discover_handover_of_work_network` on completed cases, process owners can update the empirical `estimate_service_hours` and handover-delay priors in Section 2, verify whether cross-training actually flattens `Security` and `Approval` queues, and recalibrate weights transparently with worker input.
