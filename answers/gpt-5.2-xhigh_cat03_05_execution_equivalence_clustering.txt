## 1. Equivalence design space

Let an execution \(X(o)\) be the induced object-centric subgraph around a lead object \(o\) of type `Order`: all events that reference \(o\), all objects referenced by those events (including `EXT-*` objects), and the object–object (O2O) relations among those objects (with qualifiers when available). Events are totally ordered by timestamp; ties are handled as described per relation.

### R1 — Activity-sequence equivalence (\(\equiv_A\))
- **Definition (operational)**: Extract the activity trace \(\mathrm{seq}(X)=[a_1,\dots,a_n]\) where \(a_i\) is the event’s activity label, in timestamp order (for ties see below). Two executions \(X,Y\) are equivalent iff \(\mathrm{seq}(X)=\mathrm{seq}(Y)\).
- **Invariants preserved**:
  - event count \(n\);
  - exact activity labels and their repetition counts;
  - total order of activities (up to tie-handling).
- **Information discarded**:
  - all object identifiers and object types involved per event;
  - object multiplicities, shared objects across orders, and any O2O qualifiers;
  - topology (e.g., whether one or two packages) and allocation (e.g., which payment settles which invoice).
- **Equivalence properties**: Reflexive, symmetric, transitive (equality on sequences).
- **Concurrency / same-time events**: If timestamps tie, replace the tied block by a deterministically ordered list using a stable rule such as sorting by \((\text{activity label}, \text{multiset of object-type counts})\). Alternatively, treat each tie block as an unordered multiset and compare sequences of multisets; that variant remains an equivalence relation but is coarser.

### R2 — Typed structural equivalence under identifier renaming (\(\equiv_S\))
- **Definition (structural, rename-invariant)**:
  1. Represent \(X\) as a typed, ordered bipartite incidence structure \((E,O,\lambda_E,\tau_O,\mathrm{inc},\mathrm{o2o})\) where:
     - \(E\) are event nodes, \(\lambda_E(e)\) is the activity label;
     - \(O\) are object nodes, \(\tau_O(o)\) is the object type;
     - \(\mathrm{inc}(e,o)\) iff object \(o\) participates in event \(e\) (E2O incidence);
     - \(\mathrm{o2o}\) is the set of object–object relations; for “typed structural” I keep relations but can either (a) ignore qualifiers, or (b) keep a qualifier label as part of the edge label (I’ll call the qualifier-aware variant \(\equiv_{S+q}\)).
     - each object also has a Boolean flag \(\mathrm{ext}(o)\) indicating whether its identifier starts with `EXT` (external lifecycle).
  2. Define a **canonical renaming** \(\rho\) that maps each local object id to a canonical token based on type and first appearance in the event order:
     - traverse events in timestamp order; when an object id is first seen, assign it the next token of its type (`Item#1`, `Item#2`, `Package#1`, …);
     - for multiple first-seen objects in the same event and same type, break ties by sorting by their incident activity multiset within the execution (then by original id only as a last resort for determinism, not semantics).
     - external objects keep an `EXT` marker: `EXT-Order#1`, `EXT-Item#1`, … (so “externality” is preserved, but concrete external ids are not).
  3. Apply \(\rho\) to all event–object incidences and O2O relations and serialize the resulting structure into a canonical string (events as an ordered list of \(\lambda_E(e)\) plus, per event, the sorted multiset of canonical object tokens by type; plus serialized O2O edges).
  4. Two executions are equivalent iff their canonical serializations are identical.
- **Invariants preserved**:
  - object type counts and event count;
  - exact per-event incidence patterns (which typed objects co-occur in which activity);
  - external-vs-local distinction;
  - (optionally) O2O qualifier pattern under \(\equiv_{S+q}\).
- **Information discarded**:
  - raw object identifiers (local and external) beyond the `EXT` flag;
  - higher-level business meaning (e.g., “partial payment” as a concept) unless it manifests structurally (e.g., two payment events).
- **Equivalence properties**: Reflexive, symmetric, transitive (equality of a deterministic canonical form).
- **Concurrency / same-time events**: Canonicalization treats tied timestamps as a block: serialize the block as a multiset of event “atoms” \((\text{activity}, \text{typed object multiset})\) sorted lexicographically. This avoids spurious differences from arbitrary tie-breaking.

### R3 — Business-semantic motif equivalence (\(\equiv_B\)) (preferred)
- **Definition (feature-based, reproducible)**:
  Map each execution \(X\) to a **motif signature** \(\phi(X)\) capturing business-relevant invariants:
  - **Multiplicities**: counts of `Item`, `Package`, `Delivery`, `Invoice`, `Payment` objects involved in the execution neighborhood.
  - **Logistics structure**: multiset of package sizes (items per package), multiset of delivery sizes (packages per delivery), number of dispatches, whether a delivery carries multiple packages.
  - **Finance structure**: number of orders billed per invoice (detect co-billing via `EXT-Order`), payments per invoice.
  - **Cross-order coupling**: whether any `EXT-*` object appears in logistics events (`Pack Package`, `Dispatch`) vs finance events (`Issue Invoice`, `Record Payment`).
  - **Lifecycle motifs / qualifiers**: presence of replacement/substitution qualifiers (e.g., `replaces`, `removed_before_dispatch`), and reverse-logistics motifs (`Return Item` + `Inspect Return` + repack/reship).
  Two executions are equivalent iff \(\phi(X)=\phi(Y)\) exactly (no thresholds).
- **Invariants preserved** (by construction):
  - the business pattern of fulfillment, billing, and exception handling at a granularity useful for segmentation.
- **Information discarded**:
  - micro-ordering that does not affect the motif (e.g., whether the two `Add Item` events were swapped);
  - concrete identifiers; fine-grained graph isomorphism details (e.g., which specific local item id was returned), unless they change a motif flag.
- **Equivalence properties**: Reflexive, symmetric, transitive (equality of a deterministic feature vector).
- **Concurrency / same-time events**: Motifs are defined over counts and precedence constraints (“pack precedes dispatch for the same package”), so total order is not required; ties do not affect \(\phi\).

### Optional R4 — Outcome-phase equivalence (\(\equiv_P\)) (useful for reporting)
- **Definition**: Two executions are equivalent if they reach the same coarse phases: created, fulfilled (at least one dispatch), invoiced, paid; plus a coarse “exception present?” flag. This is intentionally too coarse for segmentation but useful for high-level dashboards.


## 2. Canonical signatures

I use \(\equiv_B\) as the preferred semantic relation. Below is a reproducible, rename-invariant signature scheme that could be applied to an induced per-order sub-OCEL (or to the compact representation in this question).

### Signature fields (semantic_key_v1)
The signature is a tuple/dict with deterministically ordered components:
- `n_items_local`, `n_items_ext`
- `n_packages`, `pkg_item_sizes_local`, `pkg_item_sizes_total`
- `n_deliveries`, `deliv_pkg_sizes`
- `n_invoices`, `invoice_order_counts` (per invoice, including external orders)
- `payments_per_invoice`
- `ext_in_logistics`, `ext_in_finance`
- `motifs` (sorted set): e.g., `split_packages`, `split_deliveries`, `partial_payment`, `shared_package`, `shared_invoice`, `replacement`, `return_repack_reship`

### Python-like canonicalization code

```python
from collections import defaultdict, Counter

def is_ext(obj_id: str) -> bool:
    return obj_id.startswith("EXT")

def semantic_key_v1(events, o2o_edges=()):
    """
    events: list of dicts like:
      {"act": "Pack Package",
       "e2o": {"Order": {"O1"}, "Item": {"I11","I12"}, "Package": {"P11"}}}
    o2o_edges: iterable of dicts like:
      {"src_t":"Item","src":"I72","rel":"replaces","tgt_t":"Item","tgt":"I71","qual":"replaces"}
      or {"src_t":"Package","src":"P71","rel":"links","tgt_t":"Item","tgt":"I71","qual":"removed_before_dispatch"}
    Returns a deterministic tuple that is invariant to local identifier renaming.
    """
    # --- collect object sets (by type) from E2O incidence
    objs_by_type = defaultdict(set)
    for ev in events:
        for t, ids in ev.get("e2o", {}).items():
            objs_by_type[t].update(ids)

    def count_type(t):
        return len(objs_by_type.get(t, set()))

    items = objs_by_type.get("Item", set())
    n_items_local = sum(1 for i in items if not is_ext(i))
    n_items_ext   = sum(1 for i in items if is_ext(i))

    # --- logistics maps from events (union if repeated references occur)
    pkg_to_items = defaultdict(set)
    deliv_to_pkgs = defaultdict(set)
    ext_in_logistics = False
    ext_in_finance = False

    inv_to_orders = defaultdict(set)
    inv_to_payments = defaultdict(set)

    for ev in events:
        act = ev["act"]
        e2o = ev.get("e2o", {})
        if act == "Pack Package":
            pkgs = next(iter(e2o.get("Package", ())), None)
            if pkgs is not None:
                for it in e2o.get("Item", set()):
                    pkg_to_items[pkgs].add(it)
            if any(is_ext(x) for xs in e2o.values() for x in xs):
                # external object presence in pack is logistics coupling
                if any(is_ext(x) for x in e2o.get("Order", set()) | e2o.get("Item", set())):
                    ext_in_logistics = True

        if act == "Dispatch":
            deliv = next(iter(e2o.get("Delivery", ())), None)
            if deliv is not None:
                for p in e2o.get("Package", set()):
                    deliv_to_pkgs[deliv].add(p)
            if any(is_ext(x) for xs in e2o.values() for x in xs):
                if any(is_ext(x) for x in e2o.get("Order", set()) | e2o.get("Package", set())):
                    ext_in_logistics = True

        if act == "Issue Invoice":
            inv = next(iter(e2o.get("Invoice", ())), None)
            if inv is not None:
                inv_to_orders[inv].update(e2o.get("Order", set()))
            if any(is_ext(x) for x in e2o.get("Order", set())):
                ext_in_finance = True

        if act == "Record Payment":
            inv = next(iter(e2o.get("Invoice", ())), None)
            pay = next(iter(e2o.get("Payment", ())), None)
            if inv is not None and pay is not None:
                inv_to_payments[inv].add(pay)
            if any(is_ext(x) for x in e2o.get("Order", set())):
                ext_in_finance = True

    pkg_item_sizes_local = sorted(
        [sum(1 for it in its if not is_ext(it)) for its in pkg_to_items.values()]
    )
    pkg_item_sizes_total = sorted([len(its) for its in pkg_to_items.values()])
    deliv_pkg_sizes = sorted([len(ps) for ps in deliv_to_pkgs.values()])
    invoice_order_counts = sorted([len(os) for os in inv_to_orders.values()])
    payments_per_invoice = sorted([len(ps) for ps in inv_to_payments.values()])

    # --- motif detection (simple, structural)
    motifs = set()
    if len(pkg_to_items) >= 2: motifs.add("split_packages")
    if len(deliv_to_pkgs) >= 2: motifs.add("split_deliveries")
    if any(k >= 2 for k in payments_per_invoice): motifs.add("partial_payment")
    if ext_in_logistics: motifs.add("shared_package")
    if any(k >= 2 for k in invoice_order_counts) or ext_in_finance: motifs.add("shared_invoice")

    # qualifier-based motifs
    quals = {e.get("qual") or e.get("rel") for e in o2o_edges}
    if "replaces" in quals or "removed_before_dispatch" in quals:
        motifs.add("replacement")
    acts = [ev["act"] for ev in events]
    if "Return Item" in acts and "Inspect Return" in acts and acts.count("Dispatch") >= 2:
        motifs.add("return_repack_reship")

    key = (
        ("n_items_local", n_items_local),
        ("n_items_ext", n_items_ext),
        ("n_packages", len(pkg_to_items)),
        ("pkg_item_sizes_local", tuple(pkg_item_sizes_local)),
        ("pkg_item_sizes_total", tuple(pkg_item_sizes_total)),
        ("n_deliveries", len(deliv_to_pkgs)),
        ("deliv_pkg_sizes", tuple(deliv_pkg_sizes)),
        ("n_invoices", len(inv_to_orders)),
        ("invoice_order_counts", tuple(invoice_order_counts)),
        ("payments_per_invoice", tuple(payments_per_invoice)),
        ("ext_in_logistics", bool(ext_in_logistics)),
        ("ext_in_finance", bool(ext_in_finance)),
        ("motifs", tuple(sorted(motifs))),
    )
    return key
```

This canonical key is invariant to renaming (it never uses concrete ids except for detecting the `EXT` prefix), but it preserves multiplicities, sharing, and exception motifs.


## 3. Cluster assignments

Cluster labels:
- Activity sequence clusters: `A0` baseline labels; `A1` split-pack; `A2` split-ship/partial-pay; `A3` return/reship.
- Typed-structural clusters: `S0` baseline isomorphic; others `S3`–`S8` are distinct.
- Preferred semantic clusters: `B0`–`B6`.

| Execution | Activity-sequence cluster | Typed-structural cluster | Preferred semantic cluster | Defining signature | Main reason |
|---|---|---|---|---|---|
| X1 | A0 | S0 | B0 | `itemsL2;pkg1(2);del1(1);inv1(orders1);pay/inv[1];extL0 extF0;motifs{}` | Isolated “happy path” single shipment & single settlement |
| X2 | A0 | S0 | B0 | `itemsL2;pkg1(2);del1(1);inv1(orders1);pay/inv[1];extL0 extF0;motifs{}` | Same structure as X1 under renaming (Add Item order irrelevant) |
| X3 | A1 | S3 | B1 | `itemsL2;pkg2(1,1);del1(2);inv1(orders1);pay/inv[1];extL0 extF0;motifs{split_packages}` | Two packages, one consolidated delivery |
| X4 | A2 | S4 | B2 | `itemsL2;pkg2(1,1);del2(1,1);inv1(orders1);pay/inv[2];extL0 extF0;motifs{split_packages,split_deliveries,partial_payment}` | Split deliveries + staged/partial payment |
| X5 | A0 | S5 | B3 | `itemsL2+ext1;pkg1(3);del1(1);inv1(orders1);pay/inv[1];extL1 extF0;motifs{shared_package}` | Logistics execution shared with another order (external item/order in pack/dispatch) |
| X6 | A0 | S6 | B4 | `itemsL2;pkg1(2);del1(1);inv1(orders2);pay/inv[1];extL0 extF1;motifs{shared_invoice}` | Financial execution shared (co-billed invoice and unallocated payment) |
| X7 | A0 | S7 | B5 | `itemsL2;pkg1(2);del1(1);inv1(orders1);pay/inv[1];extL0 extF0;motifs{replacement}` | Replacement/removal semantics captured by qualified relations (and item on dispatch) |
| X8 | A3 | S8 | B6 | `itemsL2;pkg2(2,1);del2(1,1);return+inspect;inv1(orders1);pay/inv[1];motifs{return_repack_reship}` | Reverse logistics: return → inspect → repack → re-dispatch |

Notes on the compact “Defining signature” strings: `pkg1(2)` means 1 package with 2 items; `del1(2)` means 1 delivery carrying 2 packages; `inv1(orders2)` means 1 invoice billed to 2 orders (one is external); `extL/extF` indicate external coupling in logistics/finance.


## 4. Cluster interpretations

### B0 — Standard isolated fulfillment (X1, X2)
- **Concise signature**: `2 items → 1 package → 1 delivery; 1 invoice → 1 payment; no EXT; no qualifiers`.
- **Business behavior**: Normal single-shipment order with consolidated packing and immediate settlement.
- **Operational risks/opportunities**:
  - risks: minimal; baseline for SLA, cost-to-serve, and conformance checks;
  - opportunity: serves as “control group” for detecting drift or exceptions.
- **Poorly represented by flattening**:
  - classic `Order`-flattening is mostly fine, but it still loses package/item allocation details (e.g., which items were in the package if that matters later).
- **Stability under data repair**: High; robust to id renaming, to swapping identical `Add Item` events, and to minor timestamp tie-break changes.

### B1 — Split packages, consolidated delivery (X3)
- **Concise signature**: `2 items → 2 packages (1 each) → 1 delivery (2 pkgs); finance normal`.
- **Business behavior**: Items require separate packaging (fragility/size) but are shipped together in one delivery run.
- **Operational risks/opportunities**:
  - risks: extra packing labor and packaging material; higher chance of one package missing at dispatch;
  - opportunities: optimize picking/packing stations, consolidate packing where possible, bundle tracking information.
- **Poorly represented by flattening**:
  - `Order`-flattening shows two `Pack Package` events but does not preserve which package contained which item unless package ids are kept; item-centric flattening may blur that both packages went out in the same delivery.
- **Stability under data repair**: Medium-high; stable unless package ids are incorrectly merged/split or if one pack event is missing (then it collapses toward B0).

### B2 — Split deliveries with partial payment (X4)
- **Concise signature**: `2 packages (1 each) → 2 deliveries (1 pkg each); 1 invoice → 2 payments`.
- **Business behavior**: Order is fulfilled in multiple shipments (backorder/warehouse split), and payment is captured in installments (or recorded as partial settlement events).
- **Operational risks/opportunities**:
  - risks: customer communication complexity; reconciliation (two payments to one invoice); risk of non-payment after partial fulfillment;
  - opportunities: identify backorder drivers, enable proactive dunning/credit control, choose invoice timing policy.
- **Poorly represented by flattening**:
  - case-level (`Order`) flattening lists two dispatches and two payments but cannot attribute which payment covers which shipment without additional allocation objects/attributes; invoice-centric flattening obscures that both shipments belong to one order.
- **Stability under data repair**: Medium; if payments are de-duplicated or aggregated to one event, the “partial_payment” motif may disappear; if deliveries are merged, it shifts toward B1.

### B3 — Shared logistics (X5)
- **Concise signature**: `shipping events include EXT order/item; invoice/payment remain single-order`.
- **Business behavior**: A package (and thus a delivery) is shared across multiple orders—e.g., consolidation across customers, family order bundling, or cross-order picking.
- **Operational risks/opportunities**:
  - risks: misallocation of shipping cost, liability and tracking ambiguity, privacy/compliance issues if different customers’ items share packages;
  - opportunities: consolidation savings, route optimization, reduced delivery trips.
- **Poorly represented by flattening**:
  - `Order`-flattening either duplicates the shared dispatch into multiple order traces (double-counting work) or assigns it to one order only (losing the coupling). Any analysis assuming order independence breaks.
- **Stability under data repair**: Low–medium; if external links are dropped (or EXT ids are treated as noise), X5 collapses into B0. If EXT objects are misclassified as local, it can create spurious sharing.

### B4 — Shared finance (X6)
- **Concise signature**: `invoice billed to multiple orders (includes EXT-Order); payment not allocated at order level`.
- **Business behavior**: Consolidated invoicing (e.g., monthly billing, umbrella customer account) and a payment that settles the invoice globally.
- **Operational risks/opportunities**:
  - risks: revenue recognition and settlement allocation per order; disputes affect multiple orders; harder aging analysis at order granularity;
  - opportunities: lower invoicing overhead, improved customer experience for bulk billing.
- **Poorly represented by flattening**:
  - order-based flattening creates apparent “single-order invoice/payment” duplicates unless the shared invoice object is preserved; invoice-based flattening hides per-order fulfillment linkage.
- **Stability under data repair**: Medium; robust if co-billing is captured reliably, but fragile if the EXT order reference is missing (then it resembles B0).

### B5 — Replacement/removal before dispatch (X7)
- **Concise signature**: `replacement qualifiers present; item removed before dispatch; dispatch references only remaining item`.
- **Business behavior**: One item is substituted/removed late (stockout, upgrade, correction), while the order still ships and is billed normally.
- **Operational risks/opportunities**:
  - risks: customer satisfaction, inventory accuracy, potential compliance issues if invoice does not reflect substitution correctly;
  - opportunities: detect frequent substitutions, improve availability forecasting, enforce “no dispatch of removed item” controls.
- **Poorly represented by flattening**:
  - activity-only views (R1) and many order-flattenings will miss the replacement (it looks like baseline). Qualifiers and item-level participation are essential.
- **Stability under data repair**: Low if qualifiers are not preserved; medium if item-on-dispatch is preserved (still a structural signal even without explicit qualifiers).

### B6 — Return and reship with repack (X8)
- **Concise signature**: `dispatch → return+inspect → repack → second dispatch; 2 packages, 2 deliveries; finance normal`.
- **Business behavior**: Reverse logistics loop for one item: return, inspection, repack, and re-dispatch (replacement shipment or repaired item).
- **Operational risks/opportunities**:
  - risks: extra cost, longer cycle time, fraud potential, quality issues driving returns;
  - opportunities: learn return drivers, optimize inspection capacity, automate return authorization and reshipment.
- **Poorly represented by flattening**:
  - order-only flattening shows additional events but does not preserve that the second package specifically contains the returned item; item-only flattening can separate the returned item’s lifecycle from the original order’s fulfillment story.
- **Stability under data repair**: Medium-high if return and inspection events exist; sensitive if returns are recorded as attributes (negative quantity) rather than explicit events, in which case motif detection changes.


## 5. Borderline cases

### X1 versus X2
- **Definition A (too strict)**: “Exact textual equality of event–object listings” (activity + concrete object ids per event) separates them because ids differ.
- **Definition B (rename-invariant)**: \(\equiv_S\) (canonical renaming) or \(\equiv_B\) groups them: after renaming, both are `2 items → 1 package → 1 delivery → 1 invoice → 1 payment`. This is the intended notion when identifiers are arbitrary.
- **Why disagreement is defensible**: In some auditing contexts, ids are meaningful (e.g., linking to external systems); in behavior clustering they are not.

### X1 versus X5
- **Definition A (order-local)**: Ignore external objects or collapse all `EXT-*` to “unknown other” and then compare; X5 becomes equivalent to X1 under \(\equiv_A\) and often under a simplified \(\equiv_B\).
- **Definition B (coupling-aware)**: Preserve cross-order coupling (external order/item in logistics); then X5 is distinct (B3) because the package/delivery is not an isolated execution.
- **Why disagreement is defensible**: If the goal is “how does O5 behave internally?”, externality may be treated as nuisance; if the goal is “can we treat orders as independent units?”, externality is crucial.

### X1 versus X6
- **Definition A (fulfillment-only semantics)**: A business key that focuses only on logistics multiplicities (`items, packages, deliveries`) clusters X6 with X1 (both are single shipment).
- **Definition B (finance-aware semantics)**: A key that preserves invoice cardinality across orders separates X6 (shared invoice/payment context) from X1.
- **Why disagreement is defensible**: Operations teams may segment by shipping patterns; finance/compliance teams must segment by billing coupling.

### X1 versus X7
- **Definition A (qualifier-agnostic)**: If you ignore O2O qualifiers and also ignore “extra” item references on `Dispatch` as logging noise, X7 collapses to baseline.
- **Definition B (qualifier-aware / item-aware)**: Under \(\equiv_{S+q}\) or \(\equiv_B\) with a replacement motif, X7 is distinct: substitution/removal is an exception pattern.
- **Why disagreement is defensible**: Some datasets systematically omit qualifiers; a robust clustering might downweight them. Conversely, if qualifiers are reliable, they carry the real semantics.

### X3 versus X4
- **Definition A (packaging equivalence)**: Cluster by package motif only: “two packages, one item each” → X3 and X4 become equivalent.
- **Definition B (end-to-end fulfillment/finance)**: Preserve delivery multiplicity and payment multiplicity; then X3 (one delivery, one payment) differs from X4 (two deliveries, two payments).
- **Why disagreement is defensible**: Warehouse optimization might care mainly about packaging; customer experience and cashflow depend on split shipments and staged payments.

### X4 versus X8
- **Definition A (counts-only shipment key)**: If you cluster by counts (`2 packages`, `2 deliveries`) and ignore intermediate activities, X8 can be grouped with X4 as “two-dispatch orders”.
- **Definition B (exception-motif key)**: Preserve return/inspect and the “return loop” motif; then X8 is its own exception cluster (B6), while X4 is planned/operational splitting (B2).
- **Why disagreement is defensible**: In some reporting, “two deliveries” is the main cost driver; in quality/reverse-logistics analysis, the return loop is the salient difference.


## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` is best viewed as providing an **exact-equivalence baseline**: it groups executions for a chosen lead object type (`Order`) by an internal key that preserves the *exact observed execution structure* used by the function.

### What exact information the PM4Py key structure preserves
At a high level, the exact key used for equivalence must preserve (otherwise clustering would be meaningless):
- the activity labels of the events in the extracted execution (often in timestamp order);
- the exact E2O incidence per event (which concrete object identifiers are referenced, typically grouped by object type);
- therefore, the observed object graph connectivity induced by those identifiers (shared objects create coupling in the key).
If qualifiers/attributes are included depends on parameters and implementation; in many “exact” utilities, the key is intentionally close to “(activity, involved object ids)” to avoid subjective abstraction.

### Why raw object identifiers can make exact clusters too fine
If raw ids are part of the key, two executions that are structurally isomorphic after renaming (X1 vs X2) will not match, because `O1/I11/...` differs from `O2/I21/...`. This yields clusters that reflect *identifier surface forms* rather than behavioral patterns.

### How to canonicalize or post-process returned clusters
Two practical strategies:
- **Pre-canonicalize (rewrite ids)**: For each order execution, rewrite local ids to canonical tokens (`Item#1`, `Package#1`, …) before calling the exact clusterer. This makes exact keys closer to \(\equiv_S\).
- **Post-process (re-key and merge)**: Run the exact clusterer, then compute a rename-invariant semantic key (e.g., `semantic_key_v1`) for each execution and merge exact clusters that share the same canonical key. This yields business clusters \(\equiv_B\) while retaining traceability to the exact partitions.

### When exact equivalence is preferable to a coarser business clustering
Exact equivalence is preferable for:
- ingestion/ETL validation (detect duplicated/changed executions caused by pipeline changes);
- forensic replay and audit trails where the concrete referenced objects matter;
- deduplication and integrity checks in connected OCELs (shared object ids are evidence, not noise).
Business clustering is preferable for operational segmentation, capacity planning, and explanatory analytics where identifier-level variance is irrelevant.

### How `max_objs` or large connected executions affect practical use
Object-centric logs often contain **large connected components** (e.g., a shared invoice or delivery that links many orders). In such cases:
- extracting “the execution of one order” can pull in many objects and events, making exact-key construction expensive and making most orders appear unique;
- a `max_objs` safeguard (or any size cap you impose) may cause large executions to be skipped, truncated, or treated separately, reducing comparability. Either way, cross-order sharing can dominate clustering behavior.
Practical mitigations: restrict neighborhood depth (e.g., include only 1-hop objects from the lead order), project away external orders for certain analyses, or canonicalize external objects to coarse placeholders.

### Executable-looking Python outline (exact then canonical merge)

```python
import pm4py

LEAD_OT = "Order"

raw = pm4py.cluster_equivalent_ocel(ocel, LEAD_OT, max_objs=5000)

# Normalize PM4Py output to iterable of (cluster_id, sub_ocel_or_members)
if isinstance(raw, dict):
    raw_items = list(raw.items())
else:
    raw_items = list(enumerate(raw))

def orders_in_subocel(sub):
    # "Executable-looking" placeholder: adapt to your OCEL object.
    # Many PM4Py OCEL wrappers expose an objects table or a helper to list object ids by type.
    if hasattr(sub, "objects") and isinstance(sub.objects, dict):
        return list(sub.objects.get(LEAD_OT, []))
    if hasattr(sub, "get_objects"):
        return list(sub.get_objects(LEAD_OT))
    raise NotImplementedError("Adapt orders_in_subocel to your OCEL representation")

def induced_execution_events(sub, order_id):
    # Placeholder: extract events that reference this order.

    df = sub.get_extended_table()  # typical OCEL helper; adapt if needed
```

## 7. Robustness analysis

How the preferred semantic clustering (B0–B6) changes under perturbations:

1) **Ignore all O2O qualifiers**
- Main effect: X7 loses its distinguishing “replacement” signal if the only indicator is qualified relations. If dispatch-item participation is also ignored, X7 merges into B0.
- X8 remains separate because it has explicit `Return Item`/`Inspect Return` events (motif still detectable without qualifiers).

2) **Ignore external objects**
- X5 and X6 collapse toward the baseline:
  - X5 becomes indistinguishable from X1/X2 if `EXT-OA` and `EXT-IA` are removed from pack/dispatch incidence.
  - X6 becomes indistinguishable if the external co-billed order is removed from invoice/payment incidence.
- This perturbation is reasonable if external links are known to be noisy, but it destroys the ability to detect cross-order coupling.

3) **Collapse repeated same-label events**
- If repeated `Pack Package` events are collapsed to a single conceptual “packed” marker, X3 moves closer to B0 (the split-pack motif disappears).
- If repeated `Record Payment` events are collapsed (or aggregated as an amount attribute), X4 may lose the `partial_payment` motif and could be reinterpreted as “split delivery, single settlement,” potentially forming a new cluster between B1 and B2.
- This shows why repetition counts are a fragile but informative structural signal.

4) **Treat Pack and Dispatch order as a partial order**
- For \(\equiv_S\)-style comparisons, X4’s interleaving (`Pack`→`Dispatch`→`Pack`→`Dispatch`) becomes equivalent to other linearizations that respect constraints (“a package must be packed before it is dispatched”). That increases stability to timestamp noise.
- For \(\equiv_B\), which already ignores micro-order, clusters are unchanged; the benefit is primarily to typed-structural clustering.

5) **(Optional) Treat payment multiplicity as amount attribute rather than structure**
- If two payments are interpreted as one settlement with an “installments=2” attribute, and that attribute is ignored, X4 can merge with otherwise similar patterns (especially if deliveries are also aggregated). This is defensible when payment events reflect accounting granularity rather than business behavior.

Overall: B-clusters are most sensitive to (i) dropping external objects (destroys B3/B4), (ii) dropping qualifiers (destroys B5), and (iii) collapsing repetition (weakens B1/B2).


## 8. Limitations and recommendation

### Recommended equivalence level by purpose
- **Compliance monitoring**: Prefer \(\equiv_{S+q}\) (typed structural with qualifier awareness) with rename-invariant canonicalization.
  - Rationale: compliance questions often hinge on exact incidence (“was a removed item dispatched?”, “was an invoice shared across orders?”). Qualifiers and cross-order links are signals, not noise.
- **Operational segmentation**: Prefer \(\equiv_B\) (motif-based semantic clustering).
  - Rationale: operations wants actionable segments (split shipments, returns, shared logistics/finance) rather than id-level uniqueness.
- **Root-cause analysis**: Start with \(\equiv_B\) to find the relevant segment, then drill down using \(\equiv_{S+q}\) within the segment.
  - Rationale: coarse clusters localize hypotheses; fine structure identifies the precise mechanism (e.g., which object link caused coupling).
- **Descriptive reporting**: Prefer \(\equiv_P\) or a lightweight \(\equiv_A\) augmented with multiplicities.
  - Rationale: dashboards need stable, comprehensible categories and are harmed by over-fragmentation.

### Why no single equivalence is best for all four purposes
Each purpose trades off **sensitivity** (detecting meaningful differences) against **stability and interpretability** (robustness to id noise, missing qualifiers, accounting granularity). Exact structural equivalence overfits identifiers; activity-only equivalence underfits object-centric meaning; motif equivalence is actionable but can hide compliance-relevant details. Therefore, a layered approach—exact (\(\equiv_S\)) for traceability and auditing, semantic (\(\equiv_B\)) for business clustering—is usually the most effective.
