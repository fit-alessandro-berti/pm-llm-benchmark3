# 1. Objectives and constraints

Designing a dynamic resource-assignment policy requires balancing immediate operational needs with long-term organizational health. Rather than optimizing a single metric (such as local processing speed), the policy uses a multi-objective scoring function governed by hard safety/compliance bounds and soft preference trade-offs.

```
       +-------------------------------------------------------+
       |               Multi-Objective System                  |
       +--------------------------+----------------------------+
                                  |
         +------------------------+------------------------+
         |                                                 |
         v                                                 v
+----------------------------------+   +----------------------------------+
|      Hard Constraints            |   |     Soft Preference Trade-Offs   |
|  (Non-Negotiable Bounds)         |   |     (Multi-Objective Scoring)    |
+----------------------------------+   +----------------------------------+
| * Max 4 assignments/batch        |   | * SLA urgency vs. Load balance   |
| * Priority skill floor (>=2)     |   | * Continuity vs. Specialist skill |
| * Security/Approval guardrails   |   | * Short-term speed vs. Training  |
| * High overtime risk shielding   |   | * Individual focus vs. Batching  |
| * Batching restrictions          |   |                                  |
+----------------------------------+   +----------------------------------+
```

## Optimization objectives

1. **Short-term throughput & SLA protection**: Minimize total queue latency and prevent SLA breaches, prioritizing cases with tight deadlines and high priority.
2. **Workload fairness & burnout prevention**: Balance open case counts and remaining daily capacity across workers, avoiding additional assignments to resources with high overtime risk.
3. **Quality & error reduction**: Minimize rework loops and appeals by avoiding skill mismatches and unnecessary transfers of case ownership.
4. **Continuity of case ownership**: Protect domain context in complex cases to avoid handover penalties (median 2.7h delay).
5. **Skill development & resilience**: Allocate routine, non-urgent work to support documented training priorities, building multi-skilled redundancy across teams.

---

## Hard safety and compliance constraints

* **Batch assignment cap**: No single resource may receive more than **4 new assignments** in the current decision batch.
* **Skill floor for high-priority cases**: Urgent and high-priority cases must be assigned to resources with a skill level $\ge 2$, unless an explicit mentor/supervisor is paired with the resource.
* **Security review compliance**: Security Review must be assigned to skill level 3, or to skill level 1–2 **only under explicit co-assignment/supervision** by R7_Gita or R8_Hugo.
* **Final approval compliance**: Final Approval requires skill level 2–3 for final sign-off. Skill level 1 may perform preparation work but cannot issue final approval alone.
* **Overtime protection**: Resources marked with Overtime Risk = `high` (R2_Bruno, R4_David, R9_Iris) must not receive new assignments unless the case is `urgent` and no qualified resource with lower overtime risk is available.
* **Batching guardrails**: Activity batching (e.g., Quality Check) is permitted **only** when case priority is `normal` or `low` and SLA time remaining $> 24\text{ hours}$.

---

## Soft preference trade-offs

* **Handover vs. skill upgrade**: For cases with high complexity ($\ge 0.65$) and high handover cost, preserve the current owner if their skill level is $\ge 2$. If the current owner is skill level 1, prefer supervised retention over transfer unless service time inflation ($>3.3\text{ hours}$) exceeds the handover delay ($2.7\text{ hours}$).
* **Immediate speed vs. capability building**: Dedicate at least **20% of normal/low-priority cases** to documented training goals, provided the case SLA remaining is $> 12\text{ hours}$.
* **Cross-team load sharing**: Allow cross-team assignments when local team queue depth exceeds 1.5x the organizational average, provided handover cost is `low` or `none`.

# 2. Assignment policy

The policy uses a two-stage process: an **Eligibility Filter** to enforce hard bounds, followed by a **Multi-Factor Utility Score ($U_{c,r}$)** to rank valid candidate resources $r$ for case $c$.

```
 Incoming Case Candidate
            |
            v
+-----------------------+
|  Stage 1: Eligibility | ---> [Fails Hard Bounds] ---> Exclude Resource
|      Filtering        |
+-----------------------+
            | Passes
            v
+-----------------------+
|   Stage 2: Composite  | ---> Calculate Scores: SLA, Skill, Continuity,
|    Utility Scoring    |      Fairness, Training, Resilience
+-----------------------+
            |
            v
  Select Highest Score
 (Apply Tie-Breakers)
```

## Stage 1: Eligibility filter algorithm

For case $c$ requiring activity $a$, skill $s$, priority $p$, complexity $k$, and current owner $o$, resource $r$ is **eligible** if and only if:

$$\text{Eligible}(c, r) = \text{SkillValid}(c,r) \land \text{OTValid}(c,r) \land \text{CapacityValid}(r) \land \text{BatchValid}(c,r)$$

Where:
* $\text{CapacityValid}(r) = (\text{NewAssignments}(r) < 4) \land (\text{HoursRemaining}(r) > 0.5)$.
* $\text{OTValid}(c,r) = (\text{OT\_Risk}(r) \neq \text{'high'}) \lor (p = \text{'urgent'} \land \forall r', \text{OT\_Risk}(r') = \text{'high'})$.
* $\text{SkillValid}(c,r)$:
  * If $a = \text{'Security Review'}$: $\text{Skill}(r,s) = 3 \lor (\text{Skill}(r,s) \in \{1,2\} \land \text{Supervisor}(r) \in \{\text{R7\_Gita}, \text{R8\_Hugo}\})$.
  * If $a = \text{'Final Approval'}$: $\text{Skill}(r,s) \ge 2 \lor (\text{Skill}(r,s) = 1 \land \text{CoSigner}(r) \in \{\text{Skill}(s) \ge 2\})$.
  * If $p \in \{\text{'urgent'}, \text{'high'}\}$: $\text{Skill}(r,s) \ge 2 \lor \text{HasSupervisor}(r)$.
  * Else: $\text{Skill}(r,s) \ge 1$.
* $\text{BatchValid}(c,r)$: If $c$ is batched, $a = \text{'Quality Check'} \land p \in \{\text{'normal'}, \text{'low'}\} \land \text{SLA}(c) > 24\text{h}$.

---

## Stage 2: Utility scoring model

For each eligible pair $(c, r)$, compute the total score:

$$U(c, r) = w_1 \cdot S_{\text{SLA}}(c,r) + w_2 \cdot S_{\text{Skill}}(c,r) + w_3 \cdot S_{\text{Cont}}(c,r) + w_4 \cdot S_{\text{Fair}}(r) + w_5 \cdot S_{\text{Train}}(c,r) + w_6 \cdot S_{\text{Resil}}(r)$$

Default weights: $w_1 = 0.25, w_2 = 0.20, w_3 = 0.20, w_4 = 0.15, w_5 = 0.10, w_6 = 0.10$.

### Component scoring formulas

#### 1. SLA Urgency Score ($S_{\text{SLA}}$)
$$S_{\text{SLA}}(c,r) = \left(1 - \frac{\text{SLA\_Hours\_Remaining}(c)}{72}\right) \times \text{PriorityWeight}(p)$$
*Where $\text{PriorityWeight}(\text{urgent}) = 1.0, \text{high} = 0.75, \text{normal} = 0.40, \text{low} = 0.20$.*

#### 2. Skill Match Score ($S_{\text{Skill}}$)
$$S_{\text{Skill}}(c,r) = \frac{\text{Skill}(r, s_c)}{3.0}$$

#### 3. Continuity Score ($S_{\text{Cont}}$)
$$S_{\text{Cont}}(c,r) = \begin{cases} 
1.0 & \text{if } r = \text{current\_owner}(c) \\
0.5 & \text{if } \text{current\_owner}(c) = \text{'none'} \lor \text{HandoverCost}(c) = \text{'low'} \\
0.2 & \text{if } \text{HandoverCost}(c) = \text{'medium'} \land r \neq \text{current\_owner}(c) \\
0.0 & \text{if } \text{HandoverCost}(c) = \text{'high'} \land r \neq \text{current\_owner}(c)
\end{cases}$$
*Multiply $S_{\text{Cont}}$ by $(1 + \text{Complexity}(c))$ to penalize transfers on complex cases.*

#### 4. Workload & Fairness Score ($S_{\text{Fair}}$)
$$S_{\text{Fair}}(r) = \left(1 - \frac{\text{OpenCases}(r)}{15}\right) \times \left(\frac{\text{HoursRemaining}(r)}{8.0}\right) \times \text{OT\_Penalty}(r)$$
*Where $\text{OT\_Penalty}(\text{low}) = 1.0, \text{medium} = 0.8, \text{high} = 0.3$.*

#### 5. Skill Development Score ($S_{\text{Train}}$)
$$S_{\text{Train}}(c,r) = \begin{cases} 
1.0 & \text{if } \text{TrainingPriority}(r) = s_c \land \text{Skill}(r, s_c) < 3 \land p \in \{\text{'normal'}, \text{'low'}\} \\
0.5 & \text{if } \text{TrainingPriority}(r) = s_c \land p = \text{'high'} \land \text{HasSupervisor}(r) \\
0.0 & \text{otherwise}
\end{cases}$$

#### 6. Resilience & Bottleneck Avoidance ($S_{\text{Resil}}$)
$$S_{\text{Resil}}(r) = 1.0 - \text{SpecialistLoadRatio}(r)$$
*Where $\text{SpecialistLoadRatio}(r)$ measures the proportion of critical single-point skills held by $r$ that are currently queued.*

---

## Tie-breaking and exception handling

1. **Tie-Breaker 1**: Choose the resource with lower open case count.
2. **Tie-Breaker 2**: Choose the resource with higher remaining daily work hours.
3. **Tie-Breaker 3**: Choose the resource from the same organizational team to preserve localized context.
4. **Unassigned Queue Exception**: If no resource passes Stage 1 for a high/urgent priority case, initiate a **Supervised Override Escalation**: assign to the highest-skilled available resource, auto-attaching the designated team lead (R7_Gita for Risk/Security, R9_Iris for Quality, R3_Celine for Team A, R4_David for Team B) as supervisor.

# 4. Comparison with baseline policies

```
                   Performance Profile Comparison
                   
  Metric                      First-Available   Specialist-Only   Proposed Policy
  -------------------------------------------------------------------------------
  Expected Throughput         [ High      ]    [ Low       ]     [ Moderate-High ]
  SLA Breach Protection       [ Weak      ]    [ Moderate  ]     [ Strong        ]
  Quality / Rework Mitigation [ Low       ]    [ High      ]     [ High          ]
  Workload Fairness           [ High      ]    [ Poor      ]     [ High          ]
  Skill Development           [ Zero      ]    [ Zero      ]     [ High          ]
  Context Continuity          [ Poor      ]    [ Moderate  ]     [ High          ]
  Systemic Resilience         [ Fragile   ]    [ Bottleneck]     [ Robust        ]
```

## Detailed trade-off evaluation

### 1. Expected throughput
* **First-available**: High initial task execution rate due to immediate dispatch without queueing. However, total system throughput drops over time because unskilled workers take longer and generate higher rework volumes.
* **Specialist-only**: Low total throughput. Creates severe structural bottlenecks at specialist nodes (e.g., Security and Approval), leaving other workers idle while work queues build up.
* **Proposed policy**: Moderate-to-high sustained throughput. Minimizes overall case duration by combining batching, bottleneck offloading, and controlled continuity.

### 2. SLA risk
* **First-available**: High breach rate for complex and high-priority cases. Tasks are assigned without regard for remaining SLA windows or worker skill.
* **Specialist-only**: Extreme breach rate for specialized tasks due to single-point queue accumulation, even when SLA deadlines are imminent.
* **Proposed policy**: Lowest SLA breach risk. SLA urgency dynamically overrides standard preference weights, routing critical cases to available qualified resources or supervised pairs.

### 3. Error / rework risk
* **First-available**: Very high error rate. Routinely assigns complex tasks to skill level 1 workers without supervision, leading to downstream appeals and repeat work loops.
* **Specialist-only**: Lowest initial error rate. Only level 3 specialists process tasks, but fatigue from concentrated workloads can increase secondary errors.
* **Proposed policy**: Low error rate. Enforces strict skill floors (level $\ge 2$) for urgent/high-priority work and requires explicit supervision for trainees on complex tasks.

### 4. Fairness of workload
* **First-available**: High superficial fairness based purely on case counts, but fails to account for task complexity, leading to uneven cognitive burden.
* **Specialist-only**: Highly unfair. Specialists (e.g., R4, R9, R2) are overwhelmed with high open case loads and high overtime risk, while generalists remain underutilized.
* **Proposed policy**: High true fairness. Incorporates current open cases, remaining work hours, task complexity, and overtime risk penalties into every assignment decision.

### 5. Skill development
* **First-available**: Zero systematic development. Assignments are opportunistic and unguided, missing opportunities to build team capabilities.
* **Specialist-only**: Zero cross-skilling. Reinforces skill silos and increases organizational dependency on key individuals.
* **Proposed policy**: High skill growth. Deliberately channels at least 20% of eligible normal/low-priority tasks into documented training paths with structured mentorship.

### 6. Continuity of case ownership
* **First-available**: Poor. Frequently shifts case ownership between steps, triggering average waiting delays of 2.7 hours per transfer on complex cases.
* **Specialist-only**: Moderate. Retains ownership only if the same specialist dominates consecutive steps; otherwise forces handovers to domain specialists.
* **Proposed policy**: High context retention. Explicitly weights current ownership and high handover costs, avoiding reassignments unless skill gaps or severe workload imbalances require it.

### 7. Resilience to absence or bottlenecks
* **First-available**: Fragile. Vulnerable to quality failures when experts are absent, as trainees lack backstop supervision structures.
* **Specialist-only**: Highly vulnerable. If a key specialist (e.g., R7_Gita for Security) is absent or overwhelmed, the entire process stalls.
* **Proposed policy**: High resilience. Continuously expands organizational capability through supervised cross-training while utilizing multi-resource routing paths.

### Dear Team,

We have updated our daily task assignment system to better balance customer priorities, fairness across the team, and individual career growth. Our goal is to make sure no one gets overwhelmed while ensuring every case receives the right level of expertise.

Here is how your daily assignments are calculated:

1. **Protecting your workload and time**:
   * If your current open case count is high or you are near your daily hour limits, the system automatically pauses new incoming cases to prevent burnout.

   * If you are already working on a complex case, the system prioritizes keeping that case with you. We know that passing complex work back and forth wastes time and creates frustration.

   * Priority cases (Urgent/High) are routed to experienced team members or supported pairs to guarantee quality and protect SLAs.

*This system is designed to support you—balancing fair workloads, reducing unnecessary handovers, and investing in your professional development.*

# 6. Process-mining audit indicators

To audit the policy using process event logs, monitor the following indicators using standard log attributes:

```
+-----------------------------------------------------------------------------------+
|                            EVENT LOG AUDIT METRICS                                |
+-----------------------------------------------------------------------------------+
| [1. Handover Frequency]    --> % transfers with Handover_Cost = 'high'            |
| [2. Reassignment Count]    --> Average reassignments per case (Target: < 1.5)    |
| [3. Skill Mismatch Rate]   --> Events where Skill Level < Required Skill Floor    |
| [4. Workload Variance]     --> Gini coefficient of open cases per resource        |
| [5. Overtime Risk Share]   --> % new tasks assigned to High OT Risk resources     |
| [6. SLA Near-Miss Rate]    --> % cases completed within < 10% SLA margin          |
| [7. Post-Assign Rework]    --> % cases triggering Rework Correction post-transfer |
| [8. Training Task Share]   --> % normal/low tasks mapped to Training Priority     |
| [9. Specialist Bottlenecks] --> Queue dwell time at single-specialist activities   |
| [10. Policy Override Rate] --> Events where assignment reason = 'Manual_Override' |
+-----------------------------------------------------------------------------------+
```

1. **Handover frequency**:
   $$\text{HF} = \frac{\sum \text{events where } \text{org:resource}_i \neq \text{org:resource}_{i-1}}{\text{Total Events}}$$
   *Audits whether handovers decrease over time, especially on high complexity cases.*

2. **Reassignment count**:
   $$\text{RC} = \text{mean}(\text{reassignment\_count} \text{ per case})$$
   *Monitors compliance with the rule to keep reassignments $\le 2$ per case.*

3. **Skill mismatch rate**:
   $$\text{SMR} = \frac{\sum \text{events where } \text{resource\_skill} < \text{required\_skill\_floor}}{\text{Total Events}}$$
   *Measures hard constraint compliance (Target = $0\%$).*

4. **Workload distribution (Gini coefficient)**:
   $$G = \frac{\sum_{i=1}^n \sum_{j=1}^n |w_i - w_j|}{2n^2 \bar{w}}$$
   *Evaluates workload equity across resources based on `workload_snapshot`.*

5. **Overtime risk exposure**:
   $$\text{ORE} = \frac{\sum \text{assignments to resources with } \text{overtime\_risk} = \text{'high'}}{\text{Total Assignments}}$$
   *Tracks whether high overtime risk resources are properly shielded (Target $< 5\%$, urgent only).*

6. **SLA miss / near-miss rate**:
   $$\text{SLAMR} = \frac{\sum \text{cases where } \text{time:timestamp} > \text{sla\_deadline}}{\text{Total Cases}}$$
   *Monitors total SLA breach rates and near-misses ($< 10\%$ remaining buffer).*

7. **Rework / appeal rate post-assignment**:
   $$\text{RAR} = \frac{\sum \text{cases containing activity } \text{'Rework Correction'} \text{ after ownership change}}{\text{Total Reassigned Cases}}$$
   *Verifies if handovers lead to downstream quality failures.*

8. **Training assignment share**:
   $$\text{TAS} = \frac{\sum \text{normal/low priority assignments matching } \text{training\_priority}}{\text{Total Normal/Low Priority Assignments}}$$
   *Audits compliance with the $20\%$ minimum training allocation rule.*

9. **Specialist bottleneck indicators**:
   $$\text{SBI} = \text{mean}(\text{insert\_case\_service\_waiting\_time}) \text{ for } \text{Security Review} \land \text{Final Approval}$$
   *Identifies structural delays caused by scarce specialist availability.*

10. **Policy deviation rate**:
    $$\text{PDR} = \frac{\sum \text{assignments violating utility model ranking}}{\text{Total Assignments}}$$
    *Tracks manual manager overrides or out-of-policy assignments for governance audits.*

# 7. PM4Py implementation sketch

The following Python code uses **PM4Py** to process event logs, analyze resource networks, measure service/waiting times, and audit compliance with the dynamic resource-assignment policy.

```python
import pm4py
import pandas as pd
import numpy as np

def audit_resource_policy(csv_log_path: str):
    # 1. Load and format event log
    df = pd.read_csv(csv_log_path)
    df = pm4py.format_dataframe(
        df,
        case_id_column='case:concept:name',
        activity_column='concept:name',
        timestamp_column='time:timestamp',
        resource_column='org:resource'
    )
    event_log = pm4py.convert_to_event_log(df)

    print("=== 1. ORGANIZATIONAL & RESOURCE NETWORK ANALYSIS ===")
    # Discover Handover of Work Network
    hw_network = pm4py.discover_handover_of_work_network(event_log)
    pm4py.save_vis_sna(hw_network, "handover_network.png")
    
    # Discover Working Together Network
    wt_network = pm4py.discover_working_together_network(event_log)
    
    # Activity-Based Resource Similarity & Organizational Roles
    resource_similarity = pm4py.discover_activity_based_resource_similarity(event_log)
    roles = pm4py.discover_organizational_roles(event_log)
    print(f"Discovered Organizational Roles: {roles}")

    print("\n=== 2. PERFORMANCE & BATCHING ANALYSIS ===")
    # Enrich log with service and waiting times
    enriched_df = pm4py.insert_case_service_waiting_time(df)
    
    # Discover Activity Batches (e.g., Quality Check batching)
    batches = pm4py.discover_batches(event_log)
    print(f"Detected Batching Patterns: {len(batches)} batches found.")
    
    # Discover Performance DFG
    perf_dfg, start_act, end_act = pm4py.discover_performance_dfg(event_log)

    print("\n=== 3. POLICY AUDIT INDICATORS ===")
    
    # Indicator A: Reassignment Count Audit (> 2 reassignments risk check)
    reass_filter = pm4py.filter_case_performance(
        event_log, 
        comparison_operator=">", 
        threshold=0
    )
    
    # Indicator B: Skill Mismatch Audit for High Priority Cases
    high_prio_log = pm4py.filter_event_attribute_values(
        event_log, 
        'case_priority', 
        ['urgent', 'high'], 
        level='case'
    )
    
    high_prio_df = pm4py.convert_to_dataframe(high_prio_log)
    # Check for skill level compliance (< 2 without supervision)
    mismatches = high_prio_df[
        (high_prio_df['required_skill_level'] < 2) & 
        (high_prio_df['assignment_reason'] != 'Supervised_Training')
    ]
    print(f"High Priority Skill Mismatches: {len(mismatches)} events")

    # Indicator C: Overtime Exposure Audit
    high_ot_assignments = df[
        (df['workload_snapshot'] == 'high_overtime_risk') & 
        (df['case_priority'] != 'urgent')
    ]
    print(f"Non-Urgent Assignments to High-OT Resources: {len(high_ot_assignments)}")

    # Indicator D: Training Allocation Share
    normal_low_df = df[df['case_priority'].isin(['normal', 'low'])]
    training_shares = normal_low_df['assignment_reason'].value_counts(normalize=True)
    training_pct = training_shares.get('Skill_Development', 0.0) * 100
    print(f"Training Allocation Share: {training_pct:.2f}% (Target: >= 20%)")

    # Indicator E: SLA Breach Analysis
    df['sla_deadline'] = pd.to_datetime(df['sla_deadline'])
    df['time:timestamp'] = pd.to_datetime(df['time:timestamp'])
    sla_breaches = df[df['time:timestamp'] > df['sla_deadline']]
    print(f"Total SLA Breach Events: {len(sla_breaches)} / {len(df)}")

    return {
        "roles": roles,
        "batch_count": len(batches),
        "skill_mismatches": len(mismatches),
        "overtime_violations": len(high_ot_assignments),
        "training_share_pct": training_pct,
        "sla_breach_count": len(sla_breaches)
    }
```
