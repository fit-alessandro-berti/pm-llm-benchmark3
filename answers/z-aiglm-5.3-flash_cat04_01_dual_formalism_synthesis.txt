from pm4py.objects.process_tree.obj import ProcessTree, Operator


def _leaf(label):
    return ProcessTree(label=label)


def _silent():
    return ProcessTree(label=None)


def _node(operator, children):
    n = ProcessTree(operator=operator)
    for c in children:
        c.parent = n          # explicit parent pointer
        n.children.append(c)  # explicit child registration
    return n


tau = _silent()

LOOP_TRIO = ('Execute Trial', 'Inspect Trial', 'Adjust Parameters')
ROUTE = ('Supervisor Review', 'Quality Review', 'Regulatory Review')
ONCE = ('Register Deviation', 'Contain Material', 'Analyze Root Cause',
        'Plan Verification', 'Design Corrective Action', 'Release Material',
        'Archive Case')

def invariants_ok(acts):
    # start / end, uniqueness of non-loop labels
    if acts[0] != 'Register Deviation' or acts[-1] != 'Archive Case':
        return False
    if any(acts.count(a) != 1 for a in ONCE):
        return False
    # exactly one complete approval route
    counts = tuple(acts.count(r) for r in ROUTE)
    if counts not in ((1, 0, 0), (0, 1, 1)):
        return False
    # optional supplier consultation, at most once
    if acts.count('Consult Supplier') > 1:
        return False
    idx = {a: acts.index(a) for a in set(acts)}
    # precedences
    if idx['Contain Material'] > idx['Plan Verification']:        return False
    if idx['Analyze Root Cause'] > idx['Design Corrective Action']: return False
    route_first = min(i for i, a in enumerate(acts) if a in ROUTE)
    if idx['Analyze Root Cause'] > route_first:                    return False
    if 'Consult Supplier' in idx and idx['Analyze Root Cause'] > idx['Consult Supplier']:
        return False
    if max(idx['Plan Verification'], idx['Design Corrective Action']) > idx['Execute Trial']:
        return False
    # trial loop: (ET IT) (AP ET IT)* ; AP never after the final IT
    trio = [a for a in acts if a in LOOP_TRIO]
    if not trio or trio[0] != 'Execute Trial' or trio[-1] != 'Inspect Trial':
        return False
    for k, a in enumerate(trio):
        if a == 'Adjust Parameters' and not (trio[k-1] == 'Inspect Trial' and trio[k+1] == 'Execute Trial'):
            return False
    if idx['Inspect Trial'] > idx['Release Material']:             return False
    last_route = max(i for i, a in enumerate(acts) if a in ROUTE)

    if 'Consult Supplier' in idx and idx['Consult Supplier'] > idx['Release Material']:
        return False
    return True

# 1. Assumptions and Interpretation

1. **Trace semantics.** Activities are recorded at completion time; a case is a finite sequence of visible labels. Concurrency manifests as *both* relative orders being possible across cases; any single case records one linearization. Both models define languages of visible traces; the silent label `` produces no event.
2. **Low-risk / high-risk choice.** Represented as an exclusive choice (XOR) between two *route blocks*: low risk = exactly `Supervisor Review`; high risk = exactly `Quality Review` **and** `Regulatory Review`, unordered with respect to each other. Exactly one route executes per case. Which branch is taken is decided by case data outside the model; **neither model can verify that the branch matches the true risk class** (documented blind spot, shared by both models).
3. **Optional supplier consultation.** Represented as `XOR('Consult Supplier', )`: 0 or 1 occurrences; if present, it must start after `Analyze Root Cause` and complete before `Release Material`; otherwise it is concurrent with everything it may overlap. The selection decision is data-driven and outside the model.
4. **Passing inspection.** The outcome is not an event label. The loop's *exit* choice stands for "the last `Inspect Trial` passed"; the *redo* choice stands for "it failed  `Adjust Parameters`  new cycle". Both models therefore guarantee  1 `Inspect Trial` before `Release Material` and forbid `Adjust Parameters` after the final `Inspect Trial`, but **cannot check the actual outcome** — the accepted abstraction per requirement 11.
5. **Duplicate visible labels.** Permitted in principle as an approximation technique, but **rejected** in the final models: every label outside `{Execute Trial, Inspect Trial, Adjust Parameters}` occurs at most once, so the eventlabel mapping stays unique. Loop-driven repetition is intended repetition, not duplication.
6. **Process-tree approximation policy.** *Conservative under-approximation*: the tree generates only intended-valid traces and deliberately excludes a small, precisely enumerated set of interleavings (§3). Rationale: requirements 8–10 (no trailing Adjust, full release synchronization) are safety-critical; the excluded behavior is efficiency-relevant, not compliance-relevant.
7. **"May overlap" = true concurrency**, i.e., the *absence* of an order constraint: the two activities may be recorded in either order, arbitrarily interleaved. It never means "must overlap". In POWL this is literally a missing edge; in the tree it is a `PARALLEL` operator.
8. Every mandatory activity occurs exactly once per case (outside the loop); `Register Deviation` exactly once and first; `Archive Case` exactly once and last; at least one trial cycle per case (release requires a passing inspection).
9. **Reference semantics.** The intended language is the set of all linearizations of the dependency DAG in §2, expanded through the choice/loop/optionality blocks. "Intended verdict" in §5 is judged against this reference.
10. PM4Py semantics used: tree `LOOP(A, B)` = `A (B A)*` (do/redo); POWL `OperatorPOWL(LOOP)` identically; POWL `StrictPartialOrder` = all nodes execute exactly once, edges give (transitively closed) precedence; `OperatorPOWL(XOR)` = exclusive choice of one child.

# 3. PM4Py Process-Tree Model

Compact expression (PM4Py tree syntax: `->` sequence, `+` parallel, `X` xor, `*` loop(do, redo), `` silent):

```text
-> ( 'Register Deviation' ,
     + ( 'Contain Material' , 'Analyze Root Cause' ) ,
     + ( -> ( + ( 'Plan Verification' , 'Design Corrective Action' ) ,
              * ( -> ( 'Execute Trial' , 'Inspect Trial' ) ,
                 'Adjust Parameters' ) ) ,
          X ( 'Supervisor Review' ,
              + ( 'Quality Review' , 'Regulatory Review' ) ) ,
          X ( 'Consult Supplier' ,  ) ) ,
     'Release Material' ,
     'Archive Case' )
```

Mapping to the narrative: the outer sequence realizes start/end (Req 1, 10). Phase 1 `+('Contain Material','Analyze Root Cause')` is Req 2. Phase 2 is a parallel composition of (a) the *work product* — `Plan Verification  Design Corrective Action` (Reqs 3/4 concurrency) followed by the do/redo trial loop `(Execute Trial  Inspect Trial)(Adjust …)*` (Reqs 7/8) — (b) the risk route `X(Supervisor, Quality  Regulatory)` (Req 5), and (c) the optional consultation `X(Consult Supplier, )` (Req 6). The phase-2 join in front of `Release Material` is the synchronization of Req 9. `pm4py.parse_process_tree(<the string above>)` yields the same object as the constructor code below; the string is given for readability, the code is authoritative.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def _leaf(label):
    return ProcessTree(label=label)


def _node(operator, children):
    n = ProcessTree(operator=operator)
    for c in children:
        c.parent = n           # explicit parent pointer
        n.children.append(c)   # explicit child registration
    return n


tau = ProcessTree(label=None)  # silent leaf

consult_opt = _node(Operator.XOR, [_leaf('Consult Supplier'), tau])

route = _node(Operator.XOR, [
    _leaf('Supervisor Review'),
    _node(Operator.PARALLEL, [_leaf('Quality Review'),
                              _leaf('Regulatory Review')]),
])

trial_loop = _node(Operator.LOOP, [
    _node(Operator.SEQUENCE, [_leaf('Execute Trial'), _leaf('Inspect Trial')]),
    _leaf('Adjust Parameters'),
])

work = _node(Operator.SEQUENCE, [
    _node(Operator.PARALLEL, [_leaf('Plan Verification'),
                              _leaf('Design Corrective Action')]),
    trial_loop,
])

phase2 = _node(Operator.PARALLEL, [work, route, consult_opt])

phase1 = _node(Operator.PARALLEL, [_leaf('Contain Material'),
                                   _leaf('Analyze Root Cause')])

tree = _node(Operator.SEQUENCE, [
    _leaf('Register Deviation'),
    phase1,
    phase2,
    _leaf('Release Material'),
    _leaf('Archive Case'),
])

assert tree.parent is None  # root bookkeeping
```

**What the tree cannot represent exactly.** An exact tree is impossible: fix the XOR choices (low route), drop the optional consult (take ), and take one loop iteration; the remaining mandatory core is the linear-extension language of a poset containing the induced **N-pattern** {w=`Plan Verification`, x=`Trial`, y=`Analyze Root Cause`, z=`Supervisor Review`} with w<x, y<x, y<z and wy, wz, xz. Block-structured (series-parallel) languages are N-free, so no process tree generates this core exactly — and specializing choices/loops inside any hypothetical exact tree would yield a tree for the core, a contradiction. I therefore chose a **conservative under-approximation** whose *only* fidelity losses are four over-synchronization families caused by the full phase-1 join: the tree additionally forbids (i) `Plan Verification` before `Analyze Root Cause`, (ii) `Design Corrective Action` before `Contain Material`, (iii) any approval before `Contain Material`, (iv) `Consult Supplier` before `Contain Material` — all intended-legal, none safety-relevant. Everything else is exact: ContainAnalyze, PlanDesign, both work products gating the trial, the do/redo loop (Adjust never trailing), route and consult fully concurrent with the trial and with each other, and the three-way release synchronization. Rejected alternatives: *full serialization* (sound but destroys requirement 7's approval–trial overlap); *duplication-based* route/consult copies in both phases (preserves overlap candidates but admits traces with **zero or two** approval records — unsafe); a *flat parallel* of {Plan, Design, route, consult, loop} (admits `Execute Trial` before `Plan Verification` — unsafe).

# 4. PM4Py POWL Model

```text
root = StrictPartialOrder over the nodes:
  R  = "Register Deviation"
  C  = "Contain Material"
  A  = "Analyze Root Cause"
  P  = "Plan Verification"
  D  = "Design Corrective Action"
  RT = XOR( "Supervisor Review" , SPO{ "Quality Review" , "Regulatory Review" } )  # empty SPO = concurrent
  CS = XOR( "Consult Supplier" ,  )
  TL = LOOP( SPO{ "Execute Trial" -> "Inspect Trial" } , "Adjust Parameters" )     # do / redo
  RE = "Release Material"
  AR = "Archive Case"

order edges (covering relation; transitive closure is maintained internally):
  R -> C        R -> A
  C -> P
  A -> D        A -> RT       A -> CS
  P -> TL       D -> TL
  TL -> RE      RT -> RE      CS -> RE
  RE -> AR
All remaining node pairs: unordered  =>  concurrent.
```

```python

    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)

# leaves

contain    = Transition(label='Contain Material')
analyze    = Transition(label='Analyze Root Cause')
plan       = Transition(label='Plan Verification')
design     = Transition(label='Design Corrective Action')
supervisor = Transition(label='Supervisor Review')
quality    = Transition(label='Quality Review')
regulatory = Transition(label='Regulatory Review')
consult    = Transition(label='Consult Supplier')

inspect    = Transition(label='Inspect Trial')
adjust     = Transition(label='Adjust Parameters')

# hierarchical blocks
high_route  = StrictPartialOrder(nodes=[quality, regulatory])   # no edge => concurrent
route       = OperatorPOWL(operator=Operator.XOR, children=[supervisor, high_route])
consult_opt = OperatorPOWL(operator=Operator.XOR,
                           children=[consult, SilentTransition()])
trial_cycle = StrictPartialOrder(nodes=[execute, inspect])
trial_cycle.order.add_edge(execute, inspect)                    # cycle = execute then inspect
trial_loop  = OperatorPOWL(operator=Operator.LOOP,
                           children=[trial_cycle, adjust])      # do / redo

# root partial order
powl = StrictPartialOrder(nodes=[reg, contain, analyze, plan, design, route,
                                 consult_opt, trial_loop, release, archive])

po = powl.order
po.add_edge(reg, contain)
po.add_edge(reg, analyze)
po.add_edge(contain, plan)
po.add_edge(analyze, design)
po.add_edge(analyze, route)
po.add_edge(analyze, consult_opt)
po.add_edge(plan, trial_loop)
po.add_edge(design, trial_loop)
po.add_edge(trial_loop, release)
po.add_edge(route, release)
po.add_edge(consult_opt, release)
po.add_edge(release, archive)
```

Given the §1 abstractions, this POWL is **exact**: its language is precisely the set of linearizations of the §2 DAG (every precedence is an edge; every concurrency is a missing edge; `routerelease`, `trial_looprelease`, `consult_optrelease` realize the three-way join).

**Why every intentionally unconnected pair may remain concurrent** (no directed path in either direction): `Contain  Analyze` (Req 2); `Analyze  Plan` (Plan is gated by Contain only, Req 3); `Contain  Design` (Design is gated by Analyze only, Req 4); `Plan  Design` (independent work products, Req 7); `route  {Contain, Plan, Design}` (route is gated by Analyze only, Req 5); `Consult  {Contain, Plan, Design, route, trial loop}` (Req 6: consult may overlap design, planning, approvals and trial work, and is gated only by Analyze and Release); `trial loop  route` and `trial loop  Consult` (Req 7/6: approvals and consultation need not complete before the trial). Pairs such as `Contain` and the trial loop are not *directly* connected but are ordered transitively (`Contain  Plan  trial loop`) — that transitive precedence is intended.

# 8. Final Self-Critique

1. **(Semantics) Data-blind safety core.** The most safety-critical clauses — "the loop exits only after a *passing* inspection", "the route matches the true risk class" — are encoded as unobservable choices in *both* models. They accept a case that releases after a failed inspection and a high-risk case that runs only a Supervisor Review. I documented this as the permitted requirement-11 abstraction, but it means requirement 9 is enforced only structurally; a deployment without an external data-aware gate has a real compliance hole that my models cannot close.
2. **(Semantics) Interpretation-relative exactness.** The POWL's claimed exactness holds only under my reading of "may overlap" as interleaving-concurrency of completion records and of StrictPartialOrder nodes as exactly-once blocks. If the business means stronger simultaneity (shared execution windows) or weaker ("typically overlapping"), even the POWL is unfaithful. Likewise, my claim that the tree excludes *exactly* the four enumerated interleaving families is argued analytically and checked by sampling (§7.5c), not proven by an exhaustive language-inclusion procedure; a subtle loop×parallel corner case could have been mis-reasoned.
3. **(Maintenance) Fragile phase encoding.** The tree's over-synchronization is an emergent property of *where I cut the phases*, not a visible modeling decision. A future edit — e.g., adding a third approval activity to the route — can silently change which interleavings are excluded, and since validation samples rather than proves, such a regression could pass CI unnoticed. The POWL avoids this failure mode, but pm4py's POWL tooling (miners, enhancers) is younger, so a team may drift back to the lossier tree representation.
