## 4. Expected flattened behavior

- **Order:**
  - **Trace Shape:** Two distinct traces (O100, O200).
  - **Copied Shared Events:** `e6` (Reserve), `e7` (Pack P1) will appear in both traces if relations are propagated, or split based on `ocel:objects`.
  - **Omitted Aspects:** Payment events (M1, M2) are linked to V1, not O100/O200 directly in E2O. They will likely be omitted from pure Order traces unless O2O is joined.
  - **Likely DFG Edges:** `Create -> Add Item -> Reserve -> Pack -> Dispatch -> Confirm -> Close`.
  - **Misleading Interpretation:** If `e7` (Pack P1) is duplicated in both traces, it implies P1 belongs to both orders exclusively, obscuring the fact that P1 is a single physical object.

- **Package:**
  - **Trace Shape:** Two traces (P1, P2).
  - **Copied Shared Events:** `e7` (Pack) is the start. `e9`/`e10` (Dispatch) are specific.
  - **Omitted Aspects:** Order creation details (e1-e5) are not in Package scope.
  - **Likely DFG Edges:** `Pack -> Dispatch -> Confirm`.
  - **Misleading Interpretation:** P1's trace might not show I1/I3 unless joined via O2O.

- **Delivery:**
  - **Trace Shape:** Two traces (D1, D2).
  - **Copied Shared Events:** `e9`/`e10` (Dispatch).
  - **Omitted Aspects:** Order creation, Payment.
  - **Likely DFG Edges:** `Dispatch -> Confirm`.

- **Invoice:**
  - **Trace Shape:** Single trace (V1).
  - **Copied Shared Events:** `e11` (Issue), `e12` (Payment M1), `e15` (Payment M2).
  - **Omitted Aspects:** Which Order generated the payment? (Requires O2O join).
  - **Likely DFG Edges:** `Issue -> Partial Payment -> Complete Payment`.
  - **Misleading Interpretation:** The single trace hides the fact that V1 was split across two Orders (O100/O200).

- **Payment Weakness:**
  - Flattening on Payment yields a single trace for M1 and M2 because they both link to V1. It fails to distinguish the *source* of the payment (Order O100 vs O200) without traversing O2O. The granularity is too high (Invoice) relative to the business need (Order fulfillment).

## 5. Expected object-centric structures

- **OC-DFG:**
  - Will show a central node for V1 connected to M1/M2.
  - O100 and O200 will branch off V1 via `bills`.
  - P1 will connect I1 and I3, showing the cross-order package.
  - **Insight:** Reveals that O100 and O200 are not independent; they converge at P1 and V1.

- **OTG (Object Type Graph):**
  - Will show transitions between types: `Order` -> `Item` -> `Package` -> `Delivery` -> `Invoice` -> `Payment`.
  - **Insight:** Confirms the standard E2E flow.

- **ET–OT (Event-Object Type):**
  - Will show which object types are active at each event.
  - **Insight:** Highlights that `Reserve Stock` involves both Orders and Items simultaneously.

- **Object-Centric Petri Net:**
  - Will model P1 as a token passing through states (Created -> Packed -> Dispatched -> Confirmed).
  - **Insight:** The net will likely have a merged place for O100 and O200 at the `V1` stage due to the unified Invoice.

- **Object-Interactions Summary:**
  - Will count co-occurrences.
  - **Insight:** P1 and I1/I3 will have high interaction counts. O100 and O200 will share interaction counts with V1.

## 6. Modeling alternatives

1.  **Source-Minimal Relations:**
    - **Policy:** Only link events to the *primary* object of the operation (e.g., `Create Order` -> `Order`, `Pack Package` -> `Package`).
    - **Impact:** Reduces noise in `relations`. Discovery will rely heavily on O2O. Flattening might miss "involved" items if not explicitly linked in E2O.
2.  **Full Operational Involvement:**
    - **Policy:** Link every event to every object involved (e.g., `Pack P1` -> `O100`, `O200`, `I1`, `I3`, `P1`).
    - **Impact:** `relations` becomes dense. Flattening on Order will show all logistics steps. Risk of "relation inflation" (Section 7).
3.  **O2O-Propagated Relations:**
    - **Policy:** Store `relations` only for direct actions, but populate `relations` with O2O links (e.g., Payment -> Order) derived from O2O.
    - **Impact:** Discovery methods might treat O2O as observation. Flattening on Payment would show Order links directly. Violates the separation of "Log" vs "Model".

## 7. Failure modes

1.  **Relation Inflation:** Adding too many qualifiers (e.g., linking `Create Order` to `Payment` indirectly via O2O in `relations`).
2.  **Missing Direct E2O Links:** Failing to link `Pack P1` to `O100` and `O200`, breaking the trace continuity for orders.
3.  **Treating O2O Propagation as Observation:** Storing derived links (Payment -> Order) in `relations` instead of `o2o`.
4.  **Duplicate Shared Events After Flattening:** `e7` appearing twice in O100 trace and twice in O200 trace, implying two packages.
5.  **Ambiguous Payment Allocation:** M1 and M2 not linked to V1 in `relations`, making it impossible to settle V1 in the log.
6.  **Overly Short Payment Traces:** Payment events only linked to Invoice, losing the connection to the Order they paid for.
7.  **Constructor/API Version Mismatch:** Using `OCEL` with a version that expects `objects` table to contain `ocel:timestamp` (not standard).
8.  **False Total Order:** Assuming events with the same timestamp (`e16` vs `e17`) have a strict temporal order without explicit ordering in the log.
