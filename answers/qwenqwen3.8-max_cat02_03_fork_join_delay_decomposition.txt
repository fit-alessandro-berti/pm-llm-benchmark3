def simulate_final_fcfs(join_min, service=20.0, n_resources=2):
    order = join_min.sort_values(kind='mergesort').index
    avail = [0.0]*n_resources
    starts = pd.Series(index=join_min.index, dtype=float)
    for idx in order:
        ready = float(join_min.loc[idx])
        r = int(np.argmin(avail))
        start = max(ready, avail[r])
        starts.loc[idx] = start
        avail[r] = start + service
    return starts

def total_from_join(join_min, arrival_min, service=20.0, n_resources=2):
    st = simulate_final_fcfs(join_min, service, n_resources)
    return st + service - arrival_min

# 1. Delay-decomposition definitions

Let case index be \(c\) and branch index be \(i \in \{A,B,C\}\). All durations below are in minutes.

Timestamps:

- \(t^{arr}_c\): arrival
- \(t^{fork}_c\): fork release
- \(s_{c,i}\): branch start time
- \(e_{c,i}\): branch completion time
- \(t^{Fstart}_c\): final activity start
- \(t^{Fend}_c\): final activity end

Assumptions used in the decomposition:

- **A1. No branch starts before fork release.** Therefore branch queue waiting is measured from `fork_release` to branch start. This is supported by the data: all branch starts are at or after `fork_release`.
- **A2. `join_ready` is the latest branch completion.** The prompt states this rule explicitly, so \(J_c = \max_i e_{c,i}\).
- **A3. Downstream waiting before F is `final_start - join_ready`.** This is valid if the final station can start only after the join is complete.
- **A4. Timestamp granularity is one minute.** Fractional counterfactual minutes are treated as estimates, not observed facts.

Decomposition components:

\[
U_c = t^{fork}_c - t^{arr}_c
\]

Upstream elapsed time before fork release.

For each branch \(i\):

\[
Q_{c,i} = s_{c,i} - t^{fork}_c
\]

Branch-specific queue waiting after fork release.

\[
P_{c,i} = e_{c,i} - s_{c,i}
\]

Branch active service time.

\[
J_c = \max_i e_{c,i}
\]

`join_ready`, inferred as the latest branch completion.

\[
E_c = J_c - t^{fork}_c
\]

Elapsed fork-join stage time. Equivalently:

\[
E_c = \max_i \left(Q_{c,i} + P_{c,i}\right)
\]

This max formulation is the key fork-join identity. The elapsed parallel stage is determined by the slowest branch, not by the sum of branch times.

Branch-specific synchronization waiting after completion:

\[
W^{sync}_{c,i} = J_c - e_{c,i}
\]

For the last-completing branch, synchronization wait is zero. For earlier branches, it is the time the completed branch waits for the other branches.

Downstream queueing before final activity F:

\[
D_c = t^{Fstart}_c - J_c
\]

Final service time:

\[
S^F_c = t^{Fend}_c - t^{Fstart}_c
\]

Total case flow time:

\[
T_c = t^{Fend}_c - t^{arr}_c
\]

The non-double-counting elapsed-time identity is:

\[
T_c = U_c + E_c + D_c + S^F_c
\]

or:

\[
T_c = U_c + \max_i(Q_{c,i}+P_{c,i}) + D_c + S^F_c
\]

Why summing all branch synchronization waits double counts elapsed time:

For every branch:

\[
Q_{c,i} + P_{c,i} + W^{sync}_{c,i} = E_c
\]

Therefore, if we summed all three branches:

\[
\sum_i (Q_{c,i} + P_{c,i} + W^{sync}_{c,i}) = 3E_c
\]

That is three times the elapsed fork-join stage time, not the elapsed time itself. The synchronization component alone is:

\[
\sum_i W^{sync}_{c,i}
= \sum_i (J_c - e_{c,i})
= 3J_c - \sum_i e_{c,i}
\]

This can be useful as a diagnostic of how much completed-branch waiting exists, but it is not elapsed case time. If two branches finish 10 minutes before the third branch, the same 10 minutes of clock time appears as 20 minutes of branch synchronization waiting. In this dataset, case F07 has fork-join elapsed time 75 minutes but synchronization waits of 25, 0, and 52 minutes, summing to 77 minutes. The sum exceeds the elapsed stage time because it counts overlapping waiting states across parallel branches.

Thus, branch queue, service, and synchronization times are useful for diagnosing branch behavior, but the case-level elapsed fork-join time must be computed using the maximum completion, not by summing branch components.

# 3. Aggregate critical-path analysis

Branch comparison:

| branch | mean_service | service_range | mean_queue | queue_range | mean_stage_queue_plus_service | max_stage | critical_count | critical_pct | mean_sync_wait | mean_fork_join_when_critical |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|

| C | 20.2 | 18–30 | 10.4 | 5–35 | 30.6 | 57 | 2/12 | 16.7% | 30.4 | 56.0 |

Interpretation:

- Branch A has the largest mean service time, 50 minutes, but zero queue and no observed variability. It is critical only in F01 and F11.
- Branch B has a lower mean service time than A, but its mean queue delay is 19.2 minutes. Its mean queue-plus-service stage time is 56.7 minutes, the highest of the three branches. It is the last-completing branch in 8 of 12 cases.
- Branch C has the lowest mean stage time, but it has queue spikes. It is critical in F04 and F08, where C queue is 35 and 25 minutes respectively.
- Mean synchronization wait is highest for C, 30.4 minutes, because C usually finishes early and waits for A/B. This does not mean C controls completion; it usually means C is not on the critical path.
- B’s mean fork-join elapsed time when critical is 65 minutes, higher than A’s 50 and C’s 56. The longest fork-join stages, F07 and F12 at 75 minutes, are both B-critical.

Influence ranking:

1. **B is clearly the most influential branch.** It is critical most often, has the highest mean queue-plus-service stage, has the highest maximum stage, and controls the longest fork-join tails.
2. **A and C are near-tied for second, but in different ways.**
   - A is critical only twice, but its deterministic 50-minute stage acts as a cap. When B is accelerated in counterfactuals, A becomes the limiting branch in several cases.
   - C is also critical twice, but its influence is concentrated in tail cases caused by administrative queue spikes. It is a tail-risk controller rather than a steady-state controller.
3. If forced to rank strictly: **B > A  C**, with A slightly more important for average counterfactual control and C more important for exceptional administrative delays.

The main caution is that A has the largest mean service time but is not the most influential branch. Influence comes from queue delay plus service and from being the max completion at the join.

# 4. Counterfactual redesign analysis

Counterfactual assumptions:

- **CF1. Other branches are unchanged.** Only the targeted branch changes.
- **CF2. Final service time remains 20 minutes.**
- **CF3. Fractional minutes are allowed in estimates.** The observed log is one-minute granular, but counterfactual queue reductions can produce half-minute estimates.
- **CF4. Direct branch benefit is measured as reduction in `join_ready`.** This is the maximum possible reduction in fork-join elapsed time.
- **CF5. End-to-end total-flow benefit depends on final-station behavior.**
  - Lower bound: if `final_start` is fixed by schedule or policy, branch acceleration may produce zero total-flow saving.
  - Upper bound: if final start moves earlier one-for-one with `join_ready`, total saving equals the `join_ready` saving.
  - Resource-constrained estimate: if final station is modeled as a pooled two-resource FCFS station, some branch benefits may be masked by final-resource conflicts.

Compact per-case counterfactual savings:

| case | CF1: A service -20%, join saving | CF2: B queue -50%, join saving | CF3: observed downstream queue |
|---|---:|---:|---:|
| F01 | 5.0 | 0.0 | 8 |
| F02 | 0.0 | 10.0 | 15 |
| F03 | 0.0 | 10.0 | 15 |
| F04 | 0.0 | 0.0 | 18 |
| F05 | 0.0 | 10.0 | 10 |
| F06 | 0.0 | 15.0 | 15 |
| F07 | 0.0 | 15.0 | 15 |
| F08 | 0.0 | 0.0 | 15 |
| F09 | 0.0 | 12.5 | 15 |
| F10 | 0.0 | 5.0 | 20 |
| F11 | 10.0 | 0.0 | 20 |
| F12 | 0.0 | 15.0 | 10 |
| **Total** | **15.0** | **92.5** | **176** |

## Counterfactual 1: Reduce A service time by 20%

A service falls from 50 to 40 minutes.

Direct join effect:

- A becomes earlier by 10 minutes in every case.
- But `join_ready` improves only when A is the last branch or close enough to the last branch.
- Positive join savings occur only in:
  - F01: 5 minutes, because B remains critical at 08:55 after A moves to 08:50.
  - F11: 10 minutes, because A moves from 11:30 to 11:20 and ties B.
- All other cases have zero join saving because B or C remains critical.

Aggregate direct join saving: **15 minutes**.

Total-flow implications:

- Upper bound, if final start follows `join_ready`: **15 minutes** total saving.
- Lower bound, if final start is fixed by schedule or release policy: **0 minutes** total saving.
- In a pooled two-resource FCFS final-station simulation, only about **5 minutes** of the benefit is realized relative to an already-pooled final station. The F11 benefit is masked because the final station remains busy.

Cases with zero benefit:

- F02, F03, F05, F06, F07, F09, F10, F12: B remains critical.
- F04, F08: C remains critical.

Secondary effects:

- A resource capacity would be freed by 10 minutes per case, but this does not translate into case flow-time reduction unless A is critical.
- Accelerating A mostly increases A synchronization slack.
- The intervention does little to reduce the dominant B-driven tail.

## Counterfactual 2: Reduce B queue delay by 50%

B queue delay is halved. B service time is unchanged.

Direct join effect:

- B’s completion time moves earlier by half of its queue delay.
- Positive join savings occur in 8 cases: F02, F03, F05, F06, F07, F09, F10, F12.
- Zero join saving occurs in:
  - F01: A is already critical.
  - F04 and F08: C is critical.
  - F11: A is critical.

Aggregate direct join saving: **92.5 minutes**, mean **7.71 minutes per case**.

Important limiting effects:

- In F02, B reduction creates a tie with A.
- In F05 and F10, A becomes critical.
- In F06, A and B tie.
- Therefore, further B acceleration would eventually be capped by A’s deterministic 50-minute stage unless A is also improved.

Total-flow implications:

- Upper bound, if final start follows `join_ready`: **92.5 minutes** total saving.
- Lower bound, if final start is fixed: **0 minutes**.
- In the pooled two-resource FCFS final-station simulation, the branch effect relative to the pooled baseline is about **97.5 minutes**. This is slightly larger than the direct join saving because earlier cases also reduce final-station congestion for F11.

Secondary effects:

- Earlier B completion shifts criticality partly toward A.
- Final-station demand arrives earlier. If final-station capacity or release policy is unchanged, some benefit may become additional downstream queue.
- B queue reduction is much more valuable than A service reduction, but it is not unlimited because A and C can become binding in specific cases.

## Counterfactual 3: Add final-station capacity or reduce downstream queueing

Observed downstream queueing is:

\[
\sum_c D_c = 176 \text{ minutes}
\]

Mean downstream queue:

\[
176 / 12 = 14.67 \text{ minutes per case}
\]

Direct effect if downstream queue is eliminated:

- Total saving upper bound: **176 minutes**.
- Every observed case has positive downstream queue, so no observed case has zero direct benefit under this assumption.

More nuanced final-station estimates:

- If the final station is modeled as pooled two-resource FCFS with no artificial release delay, the simulated saving versus observed is about **171 minutes**. Only 5 minutes remains unavoidable in this model, associated with F11 waiting for a final resource.
- If a third final resource is added, or if the remaining conflict is removed by flexible assignment, the full **176 minutes** becomes achievable in the model.

Cases with zero benefit:

- Under the observed data, none, because every case has positive downstream queue.
- Under a mandatory release-policy interpretation, the true benefit could be zero for the policy portion of the wait.

Secondary effects:

- Final-station utilization would increase.
- If upstream branches are not improved, the final station may simply expose more branch variability.
- If B is also accelerated, final-station arrivals become earlier and potentially denser, so final capacity or dispatch policy may need to be piloted together with branch improvements.

# 5. Recommended redesigns and risks

## Redesign 1: Reduce B queue delay

Recommended action: reduce queueing before Machine Stress Test B. Possible mechanisms include additional B capacity, better scheduling, setup reduction, priority rules for near-critical cases, or smoothing release of B work.

Why this is recommended:

- B is the last-completing branch in 8 of 12 cases.
- B has the highest mean queue-plus-service stage time, 56.7 minutes.
- B drives the longest fork-join stages, especially F07 and F12.
- Halving B queue delay gives an estimated 92.5 minutes of join-ready reduction across the 12 cases.

Expected effects:

- **Throughput:** Potentially higher if the final station can absorb earlier join completions. If final release remains delayed, throughput may not increase immediately.
- **Flow-time tail:** Strong reduction in B-critical tail cases. F07 and F12 each gain 15 minutes of join-ready reduction under the 50% queue reduction counterfactual.
- **Resource utilization:** B resources may need additional capacity or better scheduling. A utilization may become more uneven because A will sometimes become the limiting branch.
- **Possible new bottlenecks:** A becomes a cap in several cases after B improvement, especially F02, F05, F06, and F10. C remains a tail-risk bottleneck in F04 and F08. Final station congestion may also absorb some benefit.
- **Synchronization effects:** B synchronization wait falls when B is critical. A and C may experience different synchronization patterns as criticality shifts.
- **Pilot and measurement first:** Pilot a temporary B capacity increase or queue-reduction policy. Measure B queue, `join_ready`, critical-branch frequency, downstream queue, and total flow time. If downstream queue grows as B improves, final-station release should be addressed simultaneously.

## Redesign 2: Redesign final-station release and dispatch

Recommended action: treat the final station as a pooled two-resource or flexible-resource station and start F as soon as `join_ready` occurs, unless there is a mandatory policy reason to wait. If pooling still leaves resource conflicts, consider a third final resource or better assignment logic.

Why this is recommended:

- Observed downstream queue averages 14.67 minutes per case.
- The final service time is constant at 20 minutes, so the downstream queue is a pure waiting component.
- A pooled FCFS simulation suggests most of the observed downstream queue is avoidable under the stated model assumptions.

Expected effects:

- **Throughput:** Could increase if current final starts are delayed by batching, policy, or poor dispatch rather than by true resource scarcity.
- **Flow-time tail:** Reduces every observed case by its downstream queue. The largest observed downstream queues are 20 minutes in F10 and F11.
- **Resource utilization:** Final resources F1 and F2 would likely be busier and have fewer idle gaps. Utilization may rise, which is good for flow time but may reduce slack.
- **Possible new bottlenecks:** Upstream branch delays become more visible. If B queue remains high, final-station improvement will not eliminate fork-join delay. If final resources have hidden constraints, such as required reviewer availability, adding capacity may be necessary.
- **Synchronization effects:** Branch synchronization waiting before `join_ready` is unchanged, but post-join waiting is reduced. The process becomes more sensitive to the true critical branch.
- **Pilot and measurement first:** Pilot pooled dispatch or a release-as-soon-as-ready policy. Measure final-station queue, final resource utilization, total flow time, and whether downstream queue simply moves upstream as increased branch synchronization waiting.

A secondary recommendation, not one of the two primary redesigns: monitor C administrative review queue. C is not the dominant average bottleneck, but its queue spikes cause criticality in F04 and F08. A control chart for C queue would be a low-cost diagnostic.

def simulate_final_fcfs(join_ready_min, service_min, n_resources=2):
    """
    Simulate final station starts under FCFS dispatch to pooled resources.

    Assumptions:
    - Case priority is by join_ready, then original case order.
    - Service times remain as observed.
    - No mandatory release delay is imposed.
    """
    order = join_ready_min.sort_values(kind="mergesort").index
    available = [0.0] * n_resources
    starts = pd.Series(index=join_ready_min.index, dtype=float)

    for idx in order:
        ready = float(join_ready_min.loc[idx])
        resource = int(np.argmin(available))
        start = max(ready, available[resource])
        starts.loc[idx] = start
        available[resource] = start + float(service_min.loc[idx])

    return starts

    return final_start + service_min - arrival_min

            "time:timestamp": row[end_col],
            "resource": row["final_resource"] if activity == "F" else ""
        })

interval_df = pd.DataFrame(interval_records)

def manual_service_minutes(df_intervals):
    return (
        df_intervals.groupby("concept:name")
        .apply(
            lambda g: (
                (g["time:timestamp"] - g["start_timestamp"])
                .dt.total_seconds()
                .mean() / 60.0
            )
        )
        .round(2)
    )

if PM4PY_AVAILABLE:
    try:
        formatted_interval_df = pm4py.format_dataframe(
            interval_df,
            case_id="case:concept:name",
            activity_key="concept:name",
            timestamp_key="time:timestamp",
            start_timestamp_key="start_timestamp"
        )

        if formatted_interval_df is None:
            formatted_interval_df = interval_df

        try:
            service_times = pm4py.get_service_time(
                formatted_interval_df,
                start_timestamp_key="start_timestamp",
                timestamp_key="time:timestamp",
                activity_key="concept:name",
                case_id_key="case:concept:name"
            )

            service_times = pd.Series(service_times)

            # Some PM4Py versions return seconds; normalize to minutes if needed.
            try:
                if service_times.abs().max() > 500:
                    service_times = service_times / 60.0
            except Exception:
                pass

            service_times = service_times.round(2)

        except Exception:
            service_times = manual_service_minutes(formatted_interval_df)

        print("\nPM4Py interval-based service time, minutes")
        print(service_times.to_string())

    except Exception as exc:
        print("\nPM4Py formatting failed; using manual interval service times.")
        print(manual_service_minutes(interval_df).to_string())
else:
    print("\nPM4Py not available; manual interval-based service time, minutes")
    print(manual_service_minutes(interval_df).to_string())

# 7. Limits of inference

Several important things cannot be identified from these timestamps alone.

1. **Causality cannot be proven.**  
   The decomposition describes observed timing, but it does not prove that a particular queue delay was caused by resource scarcity, priority rules, batching, or policy.

2. **Branch resource capacity is unobserved.**  
   The data show branch start and end times, but not the number of resources assigned to A, B, or C, their calendars, setups, interruptions, or capacity constraints.

3. **Work preemption and rework are invisible.**  
   A branch duration may include active work, waiting inside the activity, interruptions, or rework. The timestamps do not distinguish these.

4. **Queue entry times are not logged.**  
   Branch queue waiting is inferred as `branch_start - fork_release`. If a case becomes ready for a branch later than `fork_release`, this inferred queue could overstate true resource queueing.

5. **Final-station waiting may not be a pure queue.**  
   `final_start - join_ready` could be caused by resource unavailability, but it could also be caused by batching, scheduled review windows, policy release times, or administrative delays. The counterfactual savings from reducing downstream queue are therefore bounds, not guaranteed savings.

6. **Final-resource assignment rules are unclear.**  
   The log records F1 or F2, but it does not reveal whether those resources are strictly dedicated, pooled, cross-trained, or assigned by case type. The pooled FCFS simulation is an assumption, not an observed dispatch rule.

7. **One-minute granularity hides sub-minute behavior.**  
   Small margins, ties, and short queues could be sensitive to sub-minute timing.

8. **Counterfactuals require assumptions.**  
   The estimated savings assume other parts of the process do not change behavior. In reality, faster branches can change arrival patterns to the final station, alter prioritization, or induce new batching behavior.

9. **`join_ready` is inferred, not logged.**  
   The analysis assumes the stated rule that the final activity may start only after all three branches complete. If there are hidden exceptions, partial releases, or manual overrides, the inferred `join_ready` would be wrong.

10. **No demand or arrival-rate context is provided.**  
   The 12 cases may be a representative sample, but they are too few to estimate stable capacity, utilization, or tail-risk metrics without uncertainty.
