## 1. Equivalence Design Space

### 1.1 Activity-sequence equivalence
**Definition:** Two executions are equivalent if their activity labels appear in the same order, irrespective of object identifiers, object multiplicities, or structural differences in their O2O mappings. Events that occur at the same timestamp are treated as concurrent.

- **Invariants preserved:** 
  - Full sequence of activity labels with repetitions.
  - Events appear in the same order (or in the same relative order for concurrent events).
- **Information discarded:** 
  - Object identifiers.
  - O2O relations, object types, and object multiplicities.
  - External-object flags or lifecycle boundaries.
- **Properties:** Reflexive, symmetric, transitive.
- **Handling concurrency:** Concurrent events (same timestamp) are grouped into sets, and these sets are ordered sequentially. This effectively treats concurrency as a partial order.

### 1.2 Typed structural equivalence under identifier renaming
**Definition:** Two executions are equivalent if their event flows can be aligned such that:
  - Activity labels are identical between matched events.
  - Their O2O topologies (typed structural relationships between objects) are identical modulo identifier renaming.

- **Invariants preserved:**
  - Typed object relations (e.g., Order contains Items; Packages hold Items).
  - Object multiplicities within each type.
  - Sequence of activities with respect to each affected object.
- **Information discarded:**
  - Object identifiers (recognizing equivalence modulo renaming).
  - External vs. local qualifier flags, as long as these do not affect object multiplicities or relations.
- **Properties:** Reflexive, symmetric, transitive.
- **Handling concurrency:** Same as 1.1; events may be grouped into concurrent sets, and identifiers must align across concurrent events.

### 1.3 Business-semantic equivalence
**Definition:** Two executions are equivalent if their business intent (e.g., associated logistics, invoicing, or payment structure) matches. This preserves semantics such as:
  - The lifecycle state of the order (e.g., complete vs. incomplete invoicing or payment).
  - Shared lifecycle/events across external orders or objects.
  - Distribution of items into packages and deliveries.

- **Invariants preserved:**
  - Business semantics such as package split/consolidation, shared external dependencies, and payment/invoicing resolution.
  - O2O qualifiers (e.g., `removed_before_dispatch`, `partial_payment`).
  - Multiplicities and grouping of events per lifecycle motif.
- **Information discarded:**
  - Activity-sequence granularity that does not affect semantics.
  - Minor reordering of events that preserves lifecycle semantics.
- **Properties:** Reflexive, symmetric, transitive.
- **Handling concurrency:** Not affected as long as business multiplicities and semantics are preserved.

### 1.4 Additional equivalence: External-sharing tolerance
**Definition:** Extends business-semantic equivalence by ignoring shared external objects and focusing solely on local order behavior. Equivalent if the logistics and financial execution of the local order remain unaffected by any shared objects.

- **Invariants preserved:**
  - Local lifecycle representations as in 1.3.
- **Information discarded:**
  - Use of shared external objects.
- **Properties:** Reflexive, symmetric, transitive.
- **Handling concurrency:** Follows 1.1’s partial-order semantics.

## 2. Canonical Signatures

**Preferred equivalence relation:** Business-semantic equivalence.

### Canonical Signature Scheme

```python
def canonical_signature(execution):
    """
    Compute the business-semantic canonical signature for an execution.
    """
    from collections import defaultdict

    # Initialize canonical signature.
    signature = {
        "multiplicities": defaultdict(int),
        "cross_order_sharing": [],
        "distinct_lifecycles": set(),
        "semantics": []
    }

    # Extract objects and multiplicities
    for event in execution:
        for obj_type, obj_ids in event.objects.items():
            for obj_id in obj_ids:
                if obj_id.startswith("EXT"):  # External references
                    signature['cross_order_sharing'].append((event.activity, obj_id))
                else:  # Local references
                    signature["multiplicities"][(obj_type, event.activity)] += 1

    # Add lifecycle motifs
    for obj_type, relations in execution.o2o_mapping.items():
        for obj_id, relation in relations:
            lifecycle = f"{obj_type}:{relation}"
            signature["distinct_lifecycles"].add(lifecycle)

    # Add semantics
    for qualifier, details in execution.qualifiers.items():
        signature['semantics'].append((qualifier, details))

    # Return tupled signature ensuring immutability
    return tuple(sorted((k, tuple(sorted(v)) if isinstance(v, list) else v) for k, v in signature.items()))
```
