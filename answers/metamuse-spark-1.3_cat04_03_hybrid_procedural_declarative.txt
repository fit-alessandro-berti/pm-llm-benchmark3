# 1. Policy Interpretation and Conflict Resolution

## Material assumptions
- **A1. Activity labels are normative.** No hidden labels, no silent transitions in the log. `Close Onboarding` is terminal; nothing is required after it.
- **A2. Case notion = vendor onboarding case.** All timestamps are relative hours from case start. Resource in `[...]` is `org:resource`.
- **A3. Control-flow vs obligation separation.** Concurrency, order and choice belong in the procedural backbone. Co-occurrence, eventuality, separation and post-activation repair belong in DECLARE / Log Skeleton / external checks. Time expectations in R12 are probabilistic, not hard constraints.
- **A4. Log incompleteness.** There is no `emergency=true`, `joint_authorization`, `risk_level`, or `approval_applicable` attribute. Any rule conditioned on them cannot be checked from activity sequence + timestamp + resource alone.
- **A5. Clarification scope.** `Request Clarification` / `Receive Clarification` can occur after receipt and before any final outcome (`Activate Vendor` or `Reject Vendor`). Several cycles are allowed. Unanswered clarification blocks compliant closure.
- **A6. Post-activation scope.** `Change Bank Details`, `Suspend Vendor`, second `Verify Bank Account` and `Release First Payment` are post-activation repair, not part of the stable block-structured backbone.
- **A7. Escalation scope.** `Sanctions Escalation` and `Obtain Legal Opinion` are optional. If escalation occurs, opinion is obligatory. Escalation requires prior screening.
- **A8. Approvals are exclusive and acceptance-conditional.** Accepted = activated. Rejected = no approval should have occurred. Low-risk = `Manager Approval` only. High-risk = `Enhanced Due Diligence` + `Compliance Approval` only.

## R5 / R6 conflict
- **R5 - Legal:** `Sanctions Escalation -> Obtain Legal Opinion` must precede `Activate Vendor` in all cases.
- **R6 - Operations:** activation may precede opinion in a jointly-authorized emergency; opinion must then follow within 24h. The joint authorization is outside the log.

These are incompatible on activity + timestamp alone because the log cannot distinguish `emergency + authorized` from `non-emergency / unauthorized early activation`.

### Resolution A - Strict legal precedence (implemented)
Treat R5 as authoritative. Any `Activate` with prior `Sanctions Escalation` and no prior `Obtain Legal Opinion` is a violation, even if opinion arrives within 24h. R6 is not implemented as a log-checkable permission; emergencies must be modeled as a separate appeal / override workflow with its own case attribute and evidence.

Compliance risk: rejects legitimate emergencies if the override is not logged, creates false positives for Operations, but creates no false negatives for Legal. Safe for audit, costly for availability.

### Resolution B - Emergency-tolerant with 24h SLA
Treat R6 as authoritative. Control-flow allows `Activate` before `Obtain Legal Opinion` when escalation occurred, provided opinion follows within 24h. R5 becomes the normal path, not a universal invariant.

Compliance risk: every early activation is accepted as `policy-dependent` because the log lacks the authorization attribute. An unauthorized early activation followed by a fast opinion would falsely pass. Creates false negatives for Legal, requires new attributes (`emergency_flag`, `authorizers`) to be safe.

**Implemented choice: Resolution A.** Reason: activity-only formalisms cannot verify R6's condition. Implementing B without the missing attribute would silently legalize violations. T6 therefore fails under the implemented model but passes control-flow under Resolution B if the 24h SLA holds.

# 3. Procedural Backbone

## 1. Compact formal description
```
SEQ(
  Receive Onboarding Request,
  AND(Capture Master Data, Run Sanctions Screening, Verify Bank Account),
  Classify Risk,
  XOR(
    SEQ(Reject Vendor, Close Onboarding),
    SEQ(
      XOR(Manager Approval, SEQ(Enhanced Due Diligence, Compliance Approval)),
      Activate Vendor,
      Release First Payment,
      Close Onboarding
    )
  )
)
```
Included: receipt-start, 3-way concurrency, classify join, reject vs accept choice, low vs high choice, activate->pay->close tail.

Deliberately excluded: `Request/Receive Clarification` loops, `Sanctions Escalation` / `Obtain Legal Opinion`, `Change Bank Details` / `Suspend Vendor` / second `Verify`. They are optional, non-block-structured repair/clarification behavior handled in DECLARE + external checks. Forcing them into a ProcessTree would either over-constrain (require them always) or misrepresent post-activation loops as block-structured choices.

## 2. Self-contained PM4Py code
```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

procedural_model = ProcessTree(operator=Operator.SEQUENCE)
r_receive = leaf("Receive Onboarding Request")
r_parallel = ProcessTree(operator=Operator.PARALLEL)
r_parallel.children = [
    leaf("Capture Master Data"),
    leaf("Run Sanctions Screening"),
    leaf("Verify Bank Account")
]
r_classify = leaf("Classify Risk")

r_choice = ProcessTree(operator=Operator.XOR)

# rejected branch
r_reject_branch = ProcessTree(operator=Operator.SEQUENCE)
r_reject_branch.children = [leaf("Reject Vendor"), leaf("Close Onboarding")]

# accepted branch
r_accept_branch = ProcessTree(operator=Operator.SEQUENCE)
r_route = ProcessTree(operator=Operator.XOR)
r_low = leaf("Manager Approval")
r_high = ProcessTree(operator=Operator.SEQUENCE)
r_high.children = [leaf("Enhanced Due Diligence"), leaf("Compliance Approval")]
r_route.children = [r_low, r_high]
r_accept_branch.children = [
    r_route,
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding")
]

r_choice.children = [r_reject_branch, r_accept_branch]

procedural_model.children = [r_receive, r_parallel, r_classify, r_choice]
```

## 3. Explanation
- **Concurrency:** `AND` allows any interleaving of Capture, Screening, Verify after receipt. Matches T1-T8 where order varies.
- **Choices:** Outer `XOR` enforces R1 structurally for backbone activities: cannot reach both Reject and Activate via tree replay. Inner `XOR` enforces low vs high route, approximating R2/R8 structurally.
- **Clarification loops:** Excluded. A loop `LOOP(Request, Receive)` before Classify would force clarification to occur before Classify only, contradicting possible late clarification, and would complicate replay with vacuous skips. Handled as DECLARE alternation.
- **Terminal outcomes:** Reject leads directly to Close; accept leads to Activate->Pay->Close. `Close Onboarding` appears in both branches but each execution takes exactly one branch, so at-most-once still holds per trace.
- **Post-activation:** Excluded. `Change Bank Details -> Suspend -> Re-Verify -> Pay` is a non-block-structured optional loop after Activate that a ProcessTree can only approximate as `LOOP` around Activate/Pay, which would incorrectly allow repeated Activate/Pay. Left to DECLARE response + external timestamp check.

| Rule | Direction / semantics |
|---|---|
| `noncoexistence(Activate, Reject)` | Symmetric exclusion. Violated iff both occur at least once, in any order. Covers R1. Stronger than `nonsuccession` which would only forbid order in one direction. |
| `noncoexistence(EDD, Manager)` and `noncoexistence(Manager, Compliance)` | Symmetric exclusion. Covers R8 and approximates R2. Does not require presence; vacuous pass if neither occurs. |
| `response(Escalation, Opinion)` | Forward eventuality: if source occurs, target must occur after (not necessarily immediately). Does not require source. Covers R4. Satisfied by T6/T7 because opinion eventually occurs. Distinct from `precedence` which is backward. |
| `response(Change, Suspend)` | Conservative approximation of R11 first half. True R11 is conditional on Change after Activate; DECLARE version unconditionally requires Suspend after any Change. Confidence <1.0 signals approximation. |
| `precedence(Screening, Escalation)` | Backward: if target (Escalation) occurs, source (Screening) must have occurred before. Does not force escalation. Covers R7. Distinct from `response` which would force escalation after every screening. |
| `precedence(Verify, Release)` | Approximation of R11 second half. True rule requires a Verify *between* Change and later Pay; DECLARE can only require *some* Verify before Pay. Weak, confidence 0.8. |
| `altresponse(Request, Receive)` | Strengthened response: each Request must be followed by Receive before the next Request. Forbids `Request, Request` without intervening Receive. Needed for R3 multi-cycle requirement. Stronger than plain `response`, weaker than `chainresponse` which would require immediate next event. |
| `altprecedence(Request, Receive)` | Each Receive must be preceded by Request with no other Receive in between. Together with `altresponse` enforces strict alternation, approximating `altsuccession` without forcing existence. |
| `init(Receive)` | Unary: every trace starts with receipt. Encodes backbone item 1 declaratively. |

R2 full logic, R5 order, R10 cardinalities, R11 conditional timestamps are intentionally not normatively encoded here; see mapping table.

```python
        ("Manager Approval", "Compliance Approval"),

    },
    "activ_freq": {
        "Receive Onboarding Request": {1},
        "Classify Risk": {1},
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1},
        "Manager Approval": {0, 1},
        "Compliance Approval": {0, 1},
        "Enhanced Due Diligence": {0, 1},
    },
    "directly_follows": set(),
}
```

Explanation:
- `always_before (A,B)` means in every trace where B occurs, A occurs before B. Orientation is `Receive before Classify/Activate/Reject/Close` and `checks before Classify`. Defensible from backbone sequence + join. No claim about clarification/escalation order.
- `always_after (A,B)` is converse: e.g. `Classify after Receive` means whenever Receive occurs, Classify occurs after. Only included where backbone guarantees it.
- Overlap: `never_together` duplicates DECLARE `noncoexistence` and procedural XOR for R1/R8. This is intentional redundancy; Skeleton fails fast on counts without replay, DECLARE gives violation explanation, procedural gives alignment.
- Disagreement risk: Skeleton `activ_freq Classify:{1}` would fail traces with zero or two classifies, while DECLARE has no such rule. If loops re-classify after bank change, Skeleton becomes inconsistent; that behavior was excluded from procedural for the same reason. `directly_follows` left empty because concurrency makes any DF claim overfitting; procedural AND already allows all interleavings.
- `equivalence` left empty: no pair always co-occurs (e.g. Activate does not always co-occur with Manager because high-risk uses Compliance).

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800.0, 86400.0),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200.0, 21600.0),
    ("Activate Vendor", "Release First Payment"): (259200.0, 129600.0),
}
zeta = 2.0
```

48h=172800s ±24h=86400s; 12h=43200s ±6h=21600s; 72h=259200s ±36h=129600s.

With `zeta=2.0`, allowed intervals are mean ±2: Request->Receive 0-96h, Escalation->Opinion 0-24h, Activate->Pay 0-144h. `pm4py.conformance_temporal_profile(..., zeta=2.0)` flags deviations as warnings.

Why warnings, not control-flow failures: R12 explicitly says normative enough to flag but not automatically reject. Durations are stochastic, affected by workload, vendor responsiveness, weekends; timestamp-only data cannot distinguish justifiable delay from non-compliance. Treating them as hard DECLARE/precedence constraints would conflate performance with correctness and create false rejections (e.g. T7 is legally ordered but slow; T1/T2 are compliant despite 70-80h pay delays). Therefore temporal layer never decides accept/reject alone.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement:** R1 in procedural XOR + DECLARE noncoexistence + Skeleton never_together; R8 in procedural inner XOR + DECLARE/Skeleton. Redundancy is deliberate: procedural gives alignments, DECLARE gives readable violations, Skeleton gives fast count checks. Risk: inconsistent updates if one layer is changed without others.
- **Inconsistency under loops / post-activation:** Skeleton `Classify:{1}` and `Activate:{0,1}`, `Release:{0,1}` assume single pass. A compliant R11 repair with re-Verify + second Release would violate Skeleton and procedural tail while satisfying DECLARE response. Procedural deliberately excludes repair to avoid unsound `LOOP` around Activate/Pay that would permit repeated activation.
- **Vacuity:** `response(Escalation,Opinion)` and `precedence(Screening,Escalation)` vacuously pass when escalation never occurs (T1-T5,T8). `noncoexistence` vacuously passes when neither occurs. Support=1.0 / confidence=1.0 metadata describes log fit in discovery, not normative force; treating them as truth would mistake vacuous satisfaction for positive compliance and would over-trust low-confidence approximations (`response(Change,Suspend)` 0.9, `precedence(Verify,Release)` 0.8).
- **Missing case attributes:** Risk level (low/high), emergency flag, joint authorizers absent. Hence R2 applicability, R5 vs R6 distinction, and R9 applicability (which approval is applicable) cannot be recovered from activity sequences alone. Resolution B without new attributes collapses to `policy-dependent` for every early activation.
- **Timestamp-only limitations:** Temporal profile uses only pairwise mean/. Cannot account for business hours, vendor delay, batching, or causality (e.g. fast 2h Activate->Pay in T7 may indicate rushing, but is within statistical bounds). With zeta=2.0, ~5% of normal cases will still flag; must remain warning.
- **Support/confidence risk:** Values in `declare_model` are placeholders for discovery statistics, not policy strength. A rule with confidence 1.0 may still be an approximation (e.g. `precedence(Verify,Release)`), and a rule with confidence 0.8 must not be deprioritized if its authoritative external counterpart fails. Normativity comes from policy decision (Section 1), not metadata.

# 10. Deployment Recommendation

- **Canonical procedural representation:** ProcessTree in Section 3. It is the only layer expressing concurrency (AND) and block-structured choice understandably. Use it for discovery visualization, alignment-based fitness, and operator training. Do not extend it with clarification or post-activation loops.
- **Authoritative policy layer:** No single layer is authoritative for all rules. Authority is per-requirement: procedural for backbone order, DECLARE for R1/R3-alternation/R4/R7/R8, Skeleton for R10 cardinalities, temporal profile for R12 warnings only, external resource/data checks for R2/R3-deadline/R5/R6/R9/R11. Where DECLARE over-approximates (R2 full, R5 conditional, R11 conditional), the external check overrides.
- **Run order:** 1) Procedural alignment (fail fast on backbone break, e.g. T8). 2) DECLARE (`conformance_declare`) + Log Skeleton (`conformance_log_skeleton`) for declarative/count violations (e.g. T5). 3) Resource/data checks (`filter_four_eyes_principle` + timestamp-ordered R2/R3/R5/R11 logic); missing resource  `not evaluated`, missing emergency attributes  `policy-dependent`. 4) Temporal profile (`conformance_temporal_profile`, zeta=2.0) last, warnings only, never promoting warning to fail (e.g. T7).
- **Surfacing contradictions:** Show layered verdicts side-by-side as in Section 8, never a single aggregated fitness score. Mark strict-R5 failures as `fail` with annotation `would satisfy R6 24h SLA but authorization unevidenced; route to Legal override workflow`. Mark temporal deviations as `warning` with interval and zeta. Mark attribute gaps as `not evaluated` / `policy-dependent` with required-attribute hint. Require Legal sign-off to reclassify a strict failure as emergency-authorized, and log that decision with authorizers to close the R6 blind spot.
