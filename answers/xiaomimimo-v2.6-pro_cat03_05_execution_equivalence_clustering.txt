```python
def perms_within(meta):

    for oid, key in meta.items():
```

```python
    evs, o2o, meta = X["events"], X["o2o"], _types(X)
    T  = lambda objs, t: [o for tt, o, x in objs if tt == t]
    XF = lambda objs: {o for tt, o, x in objs if x}
    items, pack, carry, deliv, inv, C, unalloc = set(), {}, {}, [], {}, set(), False
    acts = [a for a, _ in evs]
    for a, objs in evs:
        if a == "Add Item":     items |= {o for tt, o, x in objs if tt == "Item" and not x}
        if a == "Pack Package": pack[T(objs, "Package")[0]] = set(T(objs, "Item"))
        if a == "Dispatch":
            for p in T(objs, "Package"): carry.setdefault(p, set()).update(T(objs, "Delivery"))
            deliv += T(objs, "Delivery")
        if a == "Issue Invoice": inv[T(objs, "Invoice")[0]] = [len(T(objs, "Order")), 0]
        if a == "Record Payment":
            for v in T(objs, "Invoice"): inv[v][1] += 1
            if len(T(objs, "Order")) > 1: unalloc, _ = True, C.add("FIN.UNALLOCATED_SETTLEMENT")
        for o in XF(objs):
            layer = "LOG" if a in LOG_A else ("FIN" if a in FIN_A else None)
            if layer == "LOG":  C.add("LOG.CO_PACK" if meta[o][0] == "Item" else "LOG.SHARED_CONSIGNMENT")
            if layer == "FIN" and a == "Issue Invoice": C.add("FIN.SHARED_INVOICE")
    removed  = {(s, t) for s, r, t in o2o if r == "removed_before_dispatch"}
    replaced = {(s, t) for s, r, t in o2o if r == "replaces"}

    def shipped(d):                      # delivered local lines of a consignment
        got = {i for p, ds in carry.items() if d in ds for i in pack.get(p, set())}
        got -= {i for (p, i) in removed if d in carry.get(p, set())}
        return got & items
    per_d  = tuple(len(shipped(d)) for d in deliv)
    union  = set().union(*map(shipped, deliv)) if deliv else set()
    cov    = "full" if union == items else "partial"
    cnt    = Counter(i for d in deliv for i in shipped(d))
    redel  = int(any(v > 1 for v in cnt.values()) or "Return Item" in acts)

    D = set()
    if removed: D.add("REMOVED_BEFORE_DISPATCH")
    for s, t in replaced: D.add("ITEM_REPLACED" if meta[s][0] == "Item" else "PACKAGE_REPLACED")
    if "Return Item" in acts: D.add("ITEM_RETURNED")
    if "Inspect Return" in acts: D.add("RETURN_INSPECTED")

    M = "".join(c for i, c in enumerate("".join(STAGE[a] for a in acts))
                if i == 0 or c != "".join(STAGE[b] for b in acts)[i-1])
    F = (len(items), per_d, cov, redel)
    S = (len(inv), tuple(v[0] for v in inv.values()), tuple(v[1] for v in inv.values()),
         "U" if unalloc else "A")
    kappa = (len([p for p in pack if meta[p][0] == "Package"]),
             tuple(sorted(len(v & items) for v in pack.values())))
    return (M, F, S, tuple(sorted(C)), tuple(sorted(D)))          # cluster key
    # refinement: return (key, kappa)

def clusters(Xs):                                   # preferred equivalence
    out = {}
    for name, X in Xs.items(): out.setdefault(business_signature(X), []).append(name)
    return out
```

## 4. Cluster interpretations

**S1 — single consignment, settled in full (X1,X2,X3).** *Signature:* `CIPDBS2:(2):full:01:(1):(1):A——`, refinement `=1:(2)` or `2:(1,1)`. *Behaviour:* two lines ordered, packed in one or two packages, one consolidated dispatch, one invoice, one full payment. *Risk/opportunity:* lowest risk class; =2 signals split packing (size/hazmat) — a packagingcost optimisation candidate. *Poor flattening:* a **Packagecentric** flattening splits X3 into two shipments and manufactures a false "split shipment" KPI. *Stability:* high; only a repacking data repair changes , never the cluster.

**S2 — split consignments with instalment settlement (X4).** *Signature:* `CIPDPDBS2:(1,1):full:01:(1):(2):A`. *Behaviour:* each line packed and shipped separately (an adhoc second shipment after the first dispatch), one invoice settled by two payments (`partially_settles`  `completes_settlement`). *Risk:* secondshipment cost/SLA breach, credit and cashapplication risk, mislinked instalments. *Opportunity:* promisetopay and partialpayment analytics. *Poor flattening:* count/DFG flattening merges it with S6 (both 2 packages, 2 dispatches); removing duplicate activities turns `P·D·P·D` into `PD`. *Stability:* medium — survives paymentasamount repairs only through perconsignment counts.

**S3 — crossorder logistics coupling (X5).** *Behaviour:* this order's lines are copacked and coshipped with a foreign line/order; billing stays local. *Risk:* disputed delivery completeness, SLA attribution, one lost shipment damages two orders, customs documentation. *Opportunity:* consolidation savings. *Poor flattening:* any **singleOrder flattening** (e.g. `ocel_flattening` on `Order`) erases `EXT-OA/EXT-IA` and makes the execution label and shapeidentical to S1. *Stability:* depends entirely on the reliability of the externality flag; an ownership repair can move X5 into S1.

**S4 — crossorder financial coupling (X6).** *Behaviour:* one invoice bills two orders; one payment is applied without orderlevel allocation. *Risk:* perorder revenue double counting, unallocated cash, dunning/credit exposure attributed to the wrong order. *Opportunity:* accountlevel consolidated invoicing. *Poor flattening:* Orderflattening duplicates or drops the shared invoice; Invoiceflattening credits the payment to both orders. *Stability:* low — an allocation repair that splits `M61` moves X6 into S1.

**S5 — line substitution / removal before dispatch (X7).** *Behaviour:* two lines ordered, one delivered; the removed line stays in the package record and an explicit item role appears on `Dispatch`. *Risk:* silent underdelivery, refund/claim exposure, quality signal buried in a qualifier. *Poor flattening:* the **Orderflattened label log is identical to S1**, and every converter that drops O2O qualifiers merges the two. *Stability:* fragile; it survives only if either the qualifier or the item role on `Dispatch` is retained (both derivations agree here — see §7).

**S6 — return, inspect, repack, redispatch (X8).** *Behaviour:* one line returned after the first delivery, inspected, repacked in a replacement package and reshipped. *Risk:* reverselogistics cost, warranty/quality escalation, secondshipment SLA. *Opportunity:* recovery and resale of returned goods. *Poor flattening:* countbased or firstoccurrence flattening merges it with S2; a handoff DFG with duplicateactivity removal hides the loop entirely. *Stability:* high (explicit activities), unless the return is booked in a separate repair object type outside the Order neighbourhood.

## 5. Borderline cases

**X1 vs X2.** A key that serialises raw object identifiers (PM4Py's default event key) or that reads the log's withinevent listing order says *different*; renaminginvariant typed isomorphism (or firstappearance canonical renaming: `O2o1, I22i1, I21i2`) says *identical*. The reversal of the item listing is pure text. It would become observable only if the two `Add Item` events carried distinguishing attributes (price, priority): a positional definition would then split X1/X2 while a setbased one would not.

**X1 vs X5.** Activitysequence (and perline fulfilmentpath) equivalence merges them: identical word, each line has the path `AddPackDispatch`. Typedstructural and businesssemantic equivalence split them, because `Pack`/`Dispatch` touch `EXT-OA` and `EXT-IA`. The disagreement is whether "with whom" belongs to behaviour: itemlocal semantics says no, sharedresource semantics says yes.

**X1 vs X6.** Same word; a definition that counts only local objects per event sees one Order in both and merges them; `_T`/`_S` split them because the invoice and payment carry a second Order and the payment is unallocated. Even `_B` splits them (exclusivity), so the merge has to come from an explicitly localonly projection.

**X1 vs X7.** `_A` merges them (identical words). `_T` splits them (`Dispatch` in X7 has an extra item role). `_S` splits them (coverage `partial`, deviation tags). Two defensible derivations *inside* `_S` also disagree: delivered lines computed from `Dispatch` item roles or from package membership minus `removed_before_dispatch` both give 1 line here, but a "package membership" rule without the qualifier would report 2 and merge X7 into S1.

**X3 vs X4.** `_B` merges them: complete delivery, fully settled, exclusive. `_A`, `_T`, `_S` split them: `Pack²Dispatch` (a join) versus two `PackDispatch` chains, and one payment versus an instalment pair. The disagreement is whether consignment granularity and settlement granularity are part of behaviour or merely of execution efficiency.

**X4 vs X8.** `_B` merges them (both complete, settled, exclusive) and so does any countbased motif profile (2 packages, 2 dispatches, 2 deliveries). `_S` and `_T` split them: X8 contains a postdelivery reverse loop and a redelivered line. The disagreement is whether reverse logistics is part of the sales execution under observation.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the key preserves.** `cluster_equivalent_ocel` partitions **events**; the key of each class is built from (i) the activity label of the event and (ii) the sorted collection of the objects the event is related to — concretely their `(object type, object identifier)` pairs, truncated to the first `max_objs` objects. So it preserves the activity and the exact object *identity* multiset incident to the event (hence types as a side effect); it **discards** timestamps and event order, the O2O relations and every qualifier, the leadobject role, and — under truncation — all incidence beyond `max_objs`. (Verify against your release with `inspect.getsource(pm4py.cluster_equivalent_ocel)`; some builds key on object *types* only, in which case the clusters are far coarser and step 2 below becomes a noop.)

**Why raw identifiers oversplit.** In X1–X8 every event touches a disjoint identifier set, so the default key yields ~55 singleton classes: the partition degenerates to the identity and cannot answer "which orders behaved alike?". Identifiers carry exactly one piece of meaning here — the `EXT` externality flag — which is destroyed or, worse, accidentally encoded as "different".

**Canonicalisation / postprocessing.** (1) Strip identifiers from the key, keeping `(activity, sorted multiset of (type, ext_flag))`; (2) split connected components that contain more than one `Order` lead (X5 and X6 link two executions) and restrict each to the lead's own event neighbourhood; (3) aggregate event keys to one execution signature (my `business_signature`, or the multiset of canonical event keys for a purely structural cluster); (4) group executions by that signature. Retain the raw PM4Py classes as an *evidence map* (which events witnessed each signature component).

**When exact equivalence is preferable.** Conformance checking against a normative variant, audit evidence and segregationofduties checks, duplicate/eventquality detection, and compression of large logs — there the identity partition is meaningful and coarsening destroys evidence.

**`max_objs` and large components.** The maximum event degree here is 6 (X5's `Pack Package`); `max_objs < 6` truncates the key and can *falsely merge* unrelated events. Large `max_objs` on components with thousands of objects produces huge, uninterpretable keys and useless singleton classes. Practical recipe: set `max_objs` to the observed maximum degree (or one more), and presplit large connected executions by lead object before aggregating.

```python
import pm4py, inspect
from collections import defaultdict

LEAD, MAX_OBJS = "Order", 6          # max event degree in this data set is 6
assert "object" in inspect.getsource(pm4py.cluster_equivalent_ocel).lower()  # know your key

# 1) PM4Py's exact event-level equivalence (key = activity + related objects)
raw = pm4py.cluster_equivalent_ocel(ocel, max_objs=MAX_OBJS)        # {key: [event ids]}

# 2) custom canonicalisation: drop raw ids, keep (type, ext-flag) + repeated labels
def canon_event_key(key):
    objs = sorted({(otype(o), o.startswith("EXT")) for o in key_objects(key)})   # key_objects = helper
    return (key_activity(key), tuple(objs))
event_key = {e: canon_event_key(k) for k, evts in raw.items() for e in evts}

# 3) custom aggregation: one signature per lead object = one execution
execs = {oid: lead_execution(ocel, oid)          # helper: events + O2O in the lead's neighbourhood
         for oid in ocel.objects[ocel.objects[ocel.object_type_column] == LEAD][ocel.object_id_column]}
preferred, structural = defaultdict(list), defaultdict(list)
for oid, X in execs.items():
    preferred[business_signature(X)].append(oid)              # =_S  (business profile)
    structural[(business_signature(X),
                structural_signature(X))].append(oid)         # =_S refined by =_T
    X["evidence"] = sorted(event_key[e] for e in X["event_ids"])   # PM4Py classes kept as evidence
print(dict(preferred), dict(structural))
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** `_A`, `_T` unchanged (`_T` already drops them). In `_S` the `D` component vanishes; X7 remains separate **only** if coverage is derived from the `Dispatch` item role. Under the packagemembership rule without `removed_before_dispatch`, X7 reports 2 delivered lines and merges into S1  5 clusters. X8 and X4 survive (explicit activities and payment multiplicity).

**Ignore external objects.** S3 and S4 lose their only distinguishing tags and merge into S1 (X5 becomes structurally identical to X1; X6's payment becomes "allocated")  4 semantic clusters. `_T` drops from 7 to 5 classes. `_A` is unaffected (it was already blind). This is the single most damaging perturbation: sharedresource behaviour is invisible to every local projection.

**Collapse repeated samelabel events.** All of X1–X7 collapse to `C·I·P·D·B·S`, so `_A` goes from 4 to 2 classes. In `_S`, X4's `M` becomes S1's; the cluster survives **only** if multiplicities live at object level (payments per invoice = 2, perconsignment counts `(1,1)`). With eventlevel counting X4 merges into S1  5 clusters. X8 stays separate via `ITEM_RETURNED/RETURN_INSPECTED` and `redeliver=1`.

**Pack/Dispatch as a partial order.** No cluster changes: every class is separable without the interleaving cue (join vs. two chains still distinguishes X3 from X4). What is lost is the evidence `D41 < P42`, the only signal that the second shipment was *adhoc* rather than *planned*; combined with a perline projection it is exactly what makes X3  X4 defensible. X2's `Add Item` order becomes explicitly irrelevant.

**Payment multiplicity as an amount attribute.** X4's `S` component becomes `(1,(1,),(1,),A)` = S1's; X4 then survives only through `F=(2,(1,1))` and `M`. Its identity shifts from "instalments" to "split consignments", and a hypothetical singleshipment/twopayment execution would be indistinguishable from S1. Combined with perturbation 3, X4 merges into S1.

*Fixed points:* X8 is stable under all five; X7 under 2–5; X5/X6 under 1, 3, 4, 5; S1's membership is stable except under the coveragederivation repair.

## 8. Limitations and recommendation

* **Compliance monitoring  `_S` with the deviation vocabulary kept** (and `_T` where the norm is written in event/object shape, e.g. "an invoice must bill exactly one order"). Auditors need qualifiers and sharedresource exposure, not identifiers; `_A` cannot see either and `_B` cannot see the deviations.
* **Operational segmentation  `_T`**, or `_S` with the  refinement switched on. Warehouse, transport and cashcollection planning hinge on package fragmentation, consignment counts and instalments, which `_S` deliberately abstracts away.
* **Rootcause analysis  `_T`** (finest renaminginvariant level that keeps qualifiers). Cause attribution requires distinguishing shape; coarsening would merge X4 with X8 and X1 with X5, hiding exactly the causes under investigation. The cost is small classes, which is acceptable for caselevel investigation.
* **Descriptive reporting  `_B`**, with `_S` as drilldown. Dashboards need stable, few, comparable segments; `_T` produces seven classes for eight cases and fragments every KPI.

No single notion serves all four because they require different invariances: compliance needs deviation sensitivity but not identity; segmentation needs structural detail but tolerates semantic blind spots; rootcause work needs maximum discrimination; reporting needs stability and low cardinality. Moreover the relations are provably incomparable (`_A` merges X5 with X1 yet splits X1/X3; `_S` does the reverse), so any single choice must discard either sharedresource evidence or packaging noise. The layered signature of §2 makes the choice explicit and reversible: cluster on `sig_S`, refine by `` or by `structural_signature` on demand.
