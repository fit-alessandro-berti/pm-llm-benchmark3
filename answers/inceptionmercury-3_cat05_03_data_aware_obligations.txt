## 1. Temporal Data Semantics

- **State reconstruction.** For each case, I start from `Create_Transaction` and apply only non-blank updates in event order. Blank cells mean “no update at this event,” not “set to null.”
- **Only semantic updates change transaction state.** `Update_Amount` changes amount; `Risk_Reclassify` changes risk; `Update_Customer_Type` changes customer type; `Update_Jurisdiction` changes jurisdiction. Other events may carry attributes that are event context, not transaction state — for example, `Sanctions_List_Update.jurisdiction` identifies the list entry, not the transaction’s jurisdiction.
- **Event ordering.** Each event has key `K(e) = (time:timestamp, event_index)`. `K(e)  K(f)` means `e` occurs before `f`. For equal timestamps, `event_index` is the tie-breaker. Example: TX-311 has `Enhanced_Review` at event_index 3 and `Update_Jurisdiction` at event_index 4 at the same timestamp, so the jurisdiction update occurs after the review.
- **No backward copying.** A final attribute value is not assumed to have governed earlier events. For example, a late `Update_Jurisdiction` does not change what was known at an earlier `Enhanced_Review`.
- **Time concepts.**  
  - *Event time*: timestamp in the log.  
  - *Effective time*: normally the event timestamp, unless evidence establishes another effective time.  
  - *Record time*: when a row was inserted, e.g., `Record_Exemption` at 11:00.  
  - *Evidence time*: when proof was created, e.g., a signing certificate timestamp.  
  Late records can be evidence of earlier events, but a backdated displayed field alone is not conclusive.
- **Material changes.** For review validity, a material change is an update to risk, jurisdiction, or customer type, or an amount increase of more than 20% from a known previous amount. Decreases and 20% increases do not invalidate a review. An increase from an unknown prior amount is not safely classifiable.
- **Missing data.** Unknown amount, risk, jurisdiction, or customer type is never defaulted to a low-risk value. If a rule cannot be triggered or excluded because of missing data, the result is INDETERMINATE unless other evidence resolves the issue.

## 2. Normalized Rule Table

### Formal pseudo-logic

```text
Let K(e) = (time(e), event_index(e)).
K(e)  K(f) iff time(e) < time(f)
               or (time(e) = time(f) and event_index(e) < event_index(f)).

Let State(r) = latest known transaction attributes at Release_Funds event r,
              using only events e with K(e)  K(r).

R1:
  trigger1(r) = known(State(r).amount) and known(State(r).jurisdiction)
                and State(r).jurisdiction != "DE"
                and State(r).amount >= 100000

  material_change(m) = update of risk_level, jurisdiction, or customer_type
                       OR amount increase >20% from a known prior amount

  ok1(r) = trigger1(r) ->
            ( exists e:
                Enhanced_Review(e)
                and K(e)  K(r)
                and not exists m:
                    material_change(m)
                    and K(e)  K(m)  K(r)
            )
            or ValidExemption(r)

  Standard_Review is not an Enhanced_Review.

R2:
  trigger2(r) = State(r).risk_level = "HIGH"
                or State(r).customer_type = "PEP"

  ok2(r) = trigger2(r) ->
            ( exists e, c:
                Enhanced_Review(e)
                and Compliance_Approve(c)
                and K(e)  K(c)  K(r)
            )

R3:
  list_add(x, r) = Sanctions_List_Update(x)
                   and x.jurisdiction = State(r).jurisdiction
                   and K(x)  K(r)

  latest_screen(r) = max { K(s) : Sanctions_Screen(s) and K(s)  K(r) }

  req3(r) = exists x:
              list_add(x, r)
              and (latest_screen(r) is absent
                   or K(latest_screen(r))  K(x))

  ok3(r) = req3(r) ->
            ( exists s:
                Sanctions_Screen(s)
                and K(x)  K(s)  K(r)
            )

R4:
  large_inc(e) = amount update at e,
                 old amount a is known,
                 new amount a' is known,
                 and (a' - a) / a > 0.20

  invalidates(q) = exists e:
                     large_inc(e)
                     and K(q)  K(e)  K(release)

  A decrease or a 20% increase does not invalidate q.
  If the old amount is unknown, the increase is not safely classifiable.

R5:
  ValidExemption(x, r) =
      x.approved_by = Head_Compliance
      and x.effective_from <= time(r)
      and x.expiry >= time(r)
      and x.jurisdiction = State(r).jurisdiction
      and x.customer_type = State(r).customer_type
      and State(r).amount <= x.max_amount
      and EvidenceSupportsApprovalBefore(x, K(r))

  EvidenceSupportsApprovalBefore(x, r):
      timely signed approval or equivalent corroboration at/before K(r).
      A late database record may corroborate earlier approval;
      a displayed backdated field alone is not conclusive.

R6:
  If a decisive attribute is missing, do not assume a low-risk value.
  If neither trigger nor exclusion can be established, classify INDETERMINATE.

R7:
  Evaluate every obligation using State(r).
  Do not copy final case state backward in time.
  For equal timestamps, use event_index as the tie-breaker and state the consequence.
```

## 4. Ambiguities and Alternative Readings

- **TX-305.** The release amount is unknown. The later settlement amount of EUR 150,000 is reliable as a settlement record, but there is no immutable release payload proving it was the release amount.  
  - If an authoritative release payload shows EUR 150,000 and no material change occurred after the 11:15 Enhanced_Review, R1 would trigger and be satisfied; the case would be COMPLIANT.  
  - If the release payload shows an amount below EUR 100,000, R1 would not trigger, and the case would also be COMPLIANT.  
  - Without an authoritative release amount, the case remains INDETERMINATE.

- **TX-302.** The result is robust. Even if EX-77’s late database record were rejected as proof of timely approval, the Enhanced_Review at 09:20 still satisfies R1 because no material change occurred after it and before release at 09:40. The exemption is additional support, not the sole reason the case is compliant.

- **TX-310.** The outcome depends on whether the oral approval claim is accepted.  
  - If independent, credible evidence showed Head_Compliance approved EX-88 before release, R1 would be waived and the case would become JUSTIFIED_EXCEPTION.  
  - If a signed approval predating release were found, the case would also be JUSTIFIED_EXCEPTION.  
  - As logged, the qualified signing certificate was created after release, and the only witness is the interested transaction requester, so the exemption is not sufficiently supported. That makes the case NONCOMPLIANT.

- **TX-311.** The same-timestamp order matters for understanding the sequence, even though it does not change the final classification. `Update_Jurisdiction` at event_index 4 occurs after `Enhanced_Review` at event_index 3. At release, the jurisdiction is DE, so R1 is not triggered. If the event_index order were reversed, R1 would still not be triggered at release because the final jurisdiction is still DE. If the DE update were considered effective only after release, R1 would trigger, but the Enhanced_Review at 16:20 was after the amount update and before release, so the case would still be COMPLIANT.

- **TX-308.** If one interpreted R1’s “latest material data change” to include every amount change, the decrease at 14:25 would make the 14:20 Enhanced_Review occur before the latest material change. I reject that reading because R4 explicitly says a decrease does not by itself invalidate a review. Under the stated policy, TX-308 is COMPLIANT.

- **TX-309.** If the second amount increase had been exactly 20% or less, the Enhanced_Review at 15:25 would remain valid and the case would be COMPLIANT. The actual increase is 145,000  118,000 = 27,000, which is approximately 22.9%, so the Enhanced_Review is invalidated.

def event_state_value(row, col):
    """Return the value that should update transaction state for this event."""
    act = row["concept:name"]
    if act == "Create_Transaction" and pd.notna(row[col]):
        return row[col]
    if col == "amount" and act == "Update_Amount" and pd.notna(row["amount"]):
        return row["amount"]
    if col == "risk_level" and act == "Risk_Reclassify" and pd.notna(row["risk_level"]):
        return row["risk_level"]
    if col == "jurisdiction" and act == "Update_Jurisdiction" and pd.notna(row["jurisdiction"]):
        return row["jurisdiction"]
    if col == "customer_type" and act == "Update_Customer_Type" and pd.notna(row["customer_type"]):
        return row["customer_type"]
    return np.nan

    df["state_" + col] = df.apply(lambda r: event_state_value(r, col), axis=1)
    df["state_" + col] = df.groupby("case:concept:name")["state_" + col].ffill()


def evaluate_case(case_df):
    events = case_df.sort_values(["time:timestamp", "event_index"]).to_dict("records")

    current_state = {}
    reviews = []
    compliances = []
    screens = []
    list_updates = []
    material_changes = []
    amount_changes = []
    release = None
    release_key = None
    release_state = {}

    for ev in events:
        act = ev["concept:name"]
        key = (ev["time:timestamp"], int(ev["event_index"]))

        if act == "Release_Funds":
            release = ev
            release_key = key
            release_state = current_state.copy()
            continue

        if release is not None:
            # Post-release events do not change the release-time state.
            continue

        if act == "Create_Transaction":
            for col in ["amount", "risk_level", "jurisdiction", "customer_type"]:
                if pd.notna(ev[col]):
                    current_state[col] = ev[col]

        elif act == "Update_Amount":
            new = ev["amount"]
            old = current_state.get("amount")
            if pd.notna(new):
                if old is None or pd.isna(old):
                    pct = np.nan
                elif old == 0:
                    pct = np.inf if new > 0 else np.nan
                else:
                    pct = (new - old) / abs(old)
                amount_changes.append((key, old, new, pct))
                if pd.notna(pct) and pct > 0.20:
                    material_changes.append((key, "amount_increase", pct))
                current_state["amount"] = new

        elif act == "Risk_Reclassify":
            current_state["risk_level"] = ev["risk_level"]
            material_changes.append((key, "risk_level", ev["risk_level"]))

        elif act == "Update_Customer_Type":
            current_state["customer_type"] = ev["customer_type"]
            material_changes.append((key, "customer_type", ev["customer_type"]))

        elif act == "Update_Jurisdiction":
            current_state["jurisdiction"] = ev["jurisdiction"]
            material_changes.append((key, "jurisdiction", ev["jurisdiction"]))

        elif act == "Standard_Review":
            reviews.append(("standard", key))

        elif act == "Enhanced_Review":
            reviews.append(("enhanced", key))

        elif act == "Compliance_Approve":
            compliances.append(key)

        elif act == "Sanctions_Screen":
            screens.append(key)

        elif act == "Sanctions_List_Update":
            list_updates.append((key, ev["jurisdiction"]))

## 6. Why Control-Flow-Only Conformance Is Insufficient

- **Final-state leakage.** A control-flow checker that uses the final case attributes would incorrectly treat a late risk or jurisdiction change as if it had been present earlier. For example, a risk reclassification after a review might falsely appear to have been covered by that review.
- **Post-hoc exemptions.** Activity-only conformance sees that an exemption was referenced or recorded, but cannot validate whether approval existed before release. TX-310 appears to have an exemption reference, but the qualified signing certificate was created after release and the witness is interested.
- **Material changes after review.** Control-flow conformance sees only that an `Enhanced_Review` occurred before `Release_Funds`. It cannot detect that a later >20% amount increase invalidated that review. TX-309 looks compliant under a pure trace-order check.
- **Conditional activation.** Rules activate only when data conditions are true. Control-flow conformance cannot decide whether an `Enhanced_Review` or `Compliance_Approve` was required at all. TX-301 requires Enhanced review because of amount and jurisdiction; TX-307 requires Enhanced because of PEP; a control-flow-only model cannot distinguish these.
- **Missing data.** If amount, risk, jurisdiction, or customer type is missing, a control-flow conformance checker has no way to represent R6. It may treat the missing value as low-risk or as “not triggered,” producing a false compliant result.
- **Same-timestamp ordering.** Control-flow conformance often collapses equal timestamps. TX-311’s `Enhanced_Review` and `Update_Jurisdiction` share a timestamp, and `event_index` determines which happened first. Without that tie-breaker, the sequence is ambiguous and downstream material-change reasoning can be wrong.

## 7. Recommended Logging and Control Improvements

- **Immutable release payload.** At `Release_Funds`, record the authoritative amount, risk, jurisdiction, customer type, and any exemption relied on, with a hash. This removes reliance on later settlement data or forward-filled state.
- **Separate effective, record, and signature timestamps.** Log `effective_time`, `record_time`, and `signature_time` for every update and exemption. A displayed backdated field should never be treated as proof of timely approval.
- **Rule versioning.** Log which version of R1–R7 was applied at each event and at release. This makes retroactive evaluation possible when policy changes.
- **Exemption scope and evidence structure.** Store exemption jurisdiction, customer-type, amount bounds, waivable rule IDs, approval authority, signer certificate timestamp, and independent corroboration. Require structured evidence rather than free-text notes.
- **Change provenance.** For every attribute update, log old value, new value, reason, actor, system, and a monotonic sequence number. Include a machine-readable material-change classification at event time.
- **Stable event ordering.** Use a globally unique, monotonic event ID. If two events share a timestamp, make the `event_index` sequence explicit and meaningful, not arbitrary.
- **Complete initial data.** Require amount, risk, jurisdiction, and customer type at `Create_Transaction`. If a value is unavailable, mark it unknown and route to manual review instead of allowing a release with an ambiguous state.
- **Pre-release control gates.** The system should evaluate R1–R4 immediately before `Release_Funds` and block release if a required review, approval, or screen is outstanding. Log the gate evaluation result as an event.
- **Sanctions list updates.** Log the effective time of each jurisdiction added to the sanctions list, and link it to affected cases. Require a re-screen before release if the list changed after the latest screen.
- **Automatic review invalidation.** When a material amount change occurs after a review, automatically invalidate that review and create a pending review task before release is possible.
