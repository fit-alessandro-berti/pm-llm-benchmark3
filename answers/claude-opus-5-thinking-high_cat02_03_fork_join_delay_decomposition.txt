# 1. Delay-decomposition definitions

## Notation

For case `c` and branch `i ∈ {A, B, C}`:

| Symbol | Meaning | Source |
|---|---|---|
| `arr_c` | arrival (entry to the overall process) | logged |
| `fr_c` | fork_release (earliest permitted branch start) | logged |
| `s_ci`, `e_ci` | branch start / branch completion | logged |
| `fs_c`, `fe_c` | final_start / final_end | logged |
| `r_c` | final resource (F1 or F2) | logged |
| `J_c` | join_ready | **derived, not logged** |

## Component formulas

1. Upstream elapsed: `U_c = fr_c − arr_c`
2. Branch queue waiting: `Q_ci = s_ci − fr_c` (≥ 0 in all 12 cases, so no case starts a branch before release)
3. Branch active service: `S_ci = e_ci − s_ci`
4. Branch cycle time: `K_ci = Q_ci + S_ci = e_ci − fr_c`
5. Join readiness under the stated AND-join rule: `J_c = max_i e_ci = fr_c + max_i K_ci`
6. Branch synchronization waiting: `W_ci = J_c − e_ci ≥ 0`, with `min_i W_ci = 0`
7. Critical branch: `crit_c = argmax_i e_ci` (ties broken deterministically, see below)
8. Fork-join stage elapsed: `G_c = J_c − fr_c = max_i K_ci`
9. Downstream queueing before F: `D_c = fs_c − J_c`
10. Final service: `V_c = fe_c − fs_c`
11. Total flow time: `T_c = fe_c − arr_c`

## The only additive identity

```
T_c = U_c + G_c + D_c + V_c
```

This holds exactly for all 12 cases (verified in §6: `identity_ok` is True everywhere). It is additive because the four intervals `[arr,fr]`, `[fr,J]`, `[J,fs]`, `[fs,fe]` tile the case timeline end-to-end with no overlap and no gap.

Two refinements used later, both still non-overlapping:

12. Attributable-vs-joint split of the stage. Let `K_c(2)` be the **second largest** branch cycle time in case `c`. Then

```
G_c = K_c(2)  +  X_c,crit      where  X_ci = max(0, K_ci − max_{j≠i} K_cj)
```

`X_ci` is the *uniquely attributable* stage time of branch `i`: the number of minutes by which branch `i` alone extends the stage, and therefore the maximum saving obtainable by improving branch `i` and nothing else. `X_ci = 0` for every non-critical branch, so `Σ_i X_ci = X_c,crit` — no double counting. `K_c(2)` is a **joint** floor that cannot be attributed to any single branch: removing it requires improving at least two branches simultaneously. I also call `X_c,crit` the *criticality margin*.

13. Split of the downstream wait, using the per-resource predecessor `prev(c)` = case previously served by `r_c`:

```
Blk_c = max(0, fe_prev(c) − J_c)       (server still busy at join_ready)
Lag_c = D_c − Blk_c                     (residual: handover, release policy, or unlogged work)
D_c   = Blk_c + Lag_c
```

## Why summing branch synchronization waits double counts

For every branch in every case,

```
Q_ci + S_ci + W_ci = (s_ci − fr_c) + (e_ci − s_ci) + (J_c − e_ci) = J_c − fr_c = G_c
```

Each branch's own (queue + service + synchronization) triple already spans the **entire** fork-join stage, because synchronization waiting is defined as exactly the residual needed to reach the common join instant. Therefore

```
Σ_i (Q_ci + S_ci + W_ci) = 3 · G_c        (verified True for all 12 cases in §6)
```

With three branches, naive summation inflates the stage by a factor of 3 — here 2196 minutes instead of 732. Equivalently, `Σ_i W_ci = 3·J_c − Σ_i e_ci` is a measure of *branch imbalance*, not a duration any case actually spends anywhere. The structural reason is that the join is a **maximum**, not a sum: concurrent branches consume the same wall-clock minutes. So:

- Use `G_c = max_i K_ci` in the flow-time identity — never a sum over branches.
- Report `W_ci` per branch as a *slack/imbalance diagnostic* only (how much idle tolerance branch `i` had), and aggregate it by branch (mean `W_ci` across cases), never across branches within a case.
- Attribute stage minutes to branches with `X_ci`, which sums correctly.

Assumption D1 (needed, and it is the assumption most worth doubting): `J_c` is unobserved and is *defined* as `max_i e_ci`. If the real join has any extra condition (a supervisor sign-off, a batch window, a shift boundary), then part of what I book as `D_c` is actually join logic, and `D_c` is an upper bound on true downstream queueing rather than a measurement of it. §7 shows the data are consistent with exactly that possibility.

Assumption D2: timestamps are complete-event data at 1-minute resolution, so every derived duration carries roughly ±1 min per endpoint (±2 min on a difference of two logged times). Differences of 5 minutes or less — e.g. the F08 criticality margin of 5 min — are within measurement noise and I treat them as near-ties.

Assumption D3: branch start times are treated as genuine work starts, so `Q_ci` is "not yet working" and `S_ci` is "working". If a branch pre-books its slot or logs a start at handover rather than at first touch, the queue/service boundary shifts. Nothing in the data can test this.

## Worked calculations

### F02 — B critical, generous slack everywhere else

- `U = 08:25 − 08:05 = 20`
- A: `Q = 08:25 − 08:25 = 0`, `S = 09:15 − 08:25 = 50`, `K_A = 50`
- B: `Q = 08:45 − 08:25 = 20`, `S = 09:25 − 08:45 = 40`, `K_B = 60`
- C: `Q = 08:30 − 08:25 = 5`, `S = 08:50 − 08:30 = 20`, `K_C = 25`
- `J = max(09:15, 09:25, 08:50) = 09:25` → critical = B, `G = 60 = K_B` ✓
- Synchronization: `W_A = 09:25 − 09:15 = 10`, `W_B = 0`, `W_C = 09:25 − 08:50 = 35`
- Double-counting check: A gives 0+50+10 = 60, B gives 20+40+0 = 60, C gives 5+20+35 = 60; sum = 180 = 3 × 60. The stage is 60, not 180.
- Margin: runner-up is A at 50, so `X_B = 60 − 50 = 10`. Speeding B by more than 10 min buys nothing without also touching A.
- `D = 09:40 − 09:25 = 15`. F2 had no prior case, so `Blk = 0` and the whole 15 min is residual lag — an idle server and still a 15-minute gap.
- `V = 20`, `T = 10:00 − 08:05 = 115`. Identity: 20 + 60 + 15 + 20 = 115 ✓
- Interpretation: B's 20-minute queue is the entire controllable content here; C finished 35 minutes early and A 10 minutes early, so both had pure slack.

### F04 — C critical, and the only case where C's queue explodes

- `U = 08:55 − 08:35 = 20`
- A: `Q = 0`, `S = 50`, `K_A = 50`
- B: `Q = 09:05 − 08:55 = 10`, `S = 09:35 − 09:05 = 30`, `K_B = 40` (B's *best* case in the log)
- C: `Q = 09:30 − 08:55 = 35`, `S = 09:52 − 09:30 = 22`, `K_C = 57` (C's worst queue, 7× its modal 5 min)
- `J = max(09:45, 09:35, 09:52) = 09:52` → critical = C, `G = 57`
- `W_A = 7`, `W_B = 17`, `W_C = 0`
- Margin: runner-up A at 50, `X_C = 7`. Even eliminating C's entire 35-minute queue only pulls the join in 7 minutes, because A's 50-minute wall is right behind it.
- `D = 10:10 − 09:52 = 18`, of which `Blk = 10:00 − 09:52 = 8` (F2 was finishing F02) and `Lag = 10`.
- `V = 20`, `T = 10:30 − 08:35 = 115`. Identity: 20 + 57 + 18 + 20 = 115 ✓
- Interpretation: this is a textbook case for not confusing service with influence. C has the smallest mean service of the three branches (20.2 min) yet is critical here purely through queueing. And fixing it is worth only 7 minutes — which the simulation in §4 shows is then fully absorbed by the final station, giving **zero** case-level benefit.

### F07 — worst total flow time in the log, B critical with a wide margin

- `U = 09:40 − 09:20 = 20`
- A: `Q = 0`, `S = 50`, `K_A = 50`
- B: `Q = 10:10 − 09:40 = 30`, `S = 10:55 − 10:10 = 45`, `K_B = 75` — worst queue **and** worst service simultaneously
- C: `Q = 5`, `S = 18`, `K_C = 23`
- `J = 10:55` → critical = B, `G = 75` (equal-worst stage with F12)
- `W_A = 25`, `W_B = 0`, `W_C = 52`. C sat finished for 52 minutes; A for 25.
- Margin: `X_B = 75 − 50 = 25`, the largest in the log. This is the one case where a large B improvement converts almost fully into join improvement.
- `D = 11:10 − 10:55 = 15`; F1 had been free since 10:40 (end of F05), so `Blk = 0` and all 15 min is residual lag.
- `V = 20`, `T = 11:30 − 09:20 = 130`. Identity: 20 + 75 + 15 + 20 = 130 ✓
- Interpretation: F07 = 130 min versus a case-mix mean of 115.25. The whole 15-minute excess over the mean is stage time (75 vs 61), and all of it is B. B queue and B service co-move (F07 and F12 are the two 30-min-queue / 45-min-service cases), which is why B drives the tail rather than just the mean.

### F11 — A critical, downstream fully masked

- `U = 10:40 − 10:20 = 20`
- A: `Q = 0`, `S = 50`, `K_A = 50`
- B: `Q = 10:50 − 10:40 = 10`, `S = 11:20 − 10:50 = 30`, `K_B = 40`
- C: `Q = 5`, `S = 18`, `K_C = 23`
- `J = max(11:30, 11:20, 11:03) = 11:30` → critical = A, `G = 50`. This is the stage **floor**: both other branches beat A, so the case is limited by A's deterministic 50 minutes.
- `W_A = 0`, `W_B = 10`, `W_C = 27`
- Margin: `X_A = 50 − 40 = 10`.
- `D = 11:50 − 11:30 = 20`, and F1 was busy with F09 until 11:50, so `Blk = 20` and `Lag = 0`. Meanwhile F2 was idle from 11:25 to 11:40 — under the observed strict F1/F2 alternation, F11 waited 20 minutes while a qualified server sat free.
- `V = 20`, `T = 12:10 − 10:20 = 110`. Identity: 20 + 50 + 20 + 20 = 110 ✓
- Interpretation: F11 is the clearest demonstration of downstream masking. Cutting A's service by 20% (−10 min) moves `J` from 11:30 to 11:20 — a full 10-minute join gain, exactly the margin — yet `fs` stays at 11:50 because F1 is still busy until then. **Realized flow-time saving: 0 minutes.**

## What each metric says, and where they disagree

**Service time alone is actively misleading.** A has the largest mean service (50 min, every single case) but is critical only twice. C has the smallest mean service but is also critical twice. Ranking by mean service gives A > B > C; ranking by influence gives B > A > C. The reason is that A's service is offset by A's zero queue while B carries 19.2 min of mean queue on top of 37.5 min of service.

**Queue plus service (cycle time) is the right branch-level quantity**, because that is what enters `max_i K_ci`. On cycle time B leads on both mean (56.7 vs 50.0 vs 30.6) and maximum (75 vs 50 vs 57).

**Frequency of being last: B 8/12 (67%), A 2/12, C 2/12.** With n = 12 the Wilson 95% interval for B's share is roughly 39–86%, so "B is usually critical" is supported but "B is critical two-thirds of the time" is not precise. The A-versus-C comparison is a genuine tie on this metric (2 each) and should be reported as such — but it is a tie between two completely different mechanisms, discussed below.

**Synchronization wait is the inverse-influence signal.** B has the lowest mean slack (4.33 min) and is at zero slack in 8 cases; C has 30.4 min of mean slack and finishes early by 22–52 min in the 10 cases where it is not critical. C is, on average, structurally irrelevant to the join.

**Tail contribution.** The five longest cases (F07 130, F12 125, F03/F06/F09 120) are all B-critical, and their stage times (75, 75, 65, 65, 65) are precisely the five largest `K_B` values. The three shortest cases (F01 93, F05/F08/F11 110) include both A-critical cases. B is the tail driver; correlation of `K_B` with total flow time is +0.72 (n = 12, so the interval around this is wide, roughly +0.25 to +0.91).

**Correlation cannot see A at all.** `K_A` is exactly 50 in every case, so it has zero variance and cannot explain any variance in flow time. This is the sharpest illustration of the level-versus-variance distinction: a perfectly deterministic branch can be the dominant contributor to the *level* of flow time while contributing nothing to its *variation*, and every variance-based bottleneck detector will miss it.

**Attribution without double counting.** Using `X_ci`: B owns 120 of the 147 uniquely attributable stage minutes (82%), A owns 15, C owns 12. But the joint floor is 585 minutes, and A sets that floor in 10 of 12 cases at exactly 50 min. Making B *instantaneous* saves only 120 min of join time (10 min/case) before A takes over; making B and C both instantaneous saves 132 min (11 min/case) and then A is the sole determinant, with the stage pinned at 50 min for every case.

## Influence ranking

1. **B — Machine Stress Test — the controlling branch.** Critical in 8/12, largest mean and max cycle time, lowest slack, owns 82% of attributable stage time, drives the whole upper tail, and is the only branch whose cycle time correlates meaningfully with total flow time. It is critical because of a queue-plus-service compound: its queue (mean 19.2, max 30) and its service (mean 37.5, max 45) both peak in the same cases (F07, F12).
2. **A — Laboratory Assay — the binding backstop / floor.** Critical in only 2/12, but the runner-up in 10/12 at exactly 50 minutes, with margins of only 5–25 min between B and A. A is not the current constraint; it is the constraint that appears the moment B is improved. §4 confirms this: after halving B's queue, A becomes critical in 6 of 12 cases. Any B roadmap must be planned jointly with A.
3. **C — Documentation Review — near-irrelevant on average, a pure tail risk.** Critical in 2/12, tied with A on frequency, but for a different reason: C's mean cycle time is 26 minutes below A's, and it becomes critical only through two anomalies (F04's 35-min queue, F08's 25-min queue plus a 30-min service). Its correlation with flow time is slightly *negative* (−0.18, indistinguishable from zero at n = 12). C deserves an outlier-suppression control, not a capacity or speed programme. And even when C is critical, its margins are tiny (7 and 5 min).

Honest caveats on this ranking: (i) the A-versus-C frequency tie is real and I have broken it on mechanism, not on the count; (ii) F01, F08 and F10 have criticality margins of 5 minutes, which is within the ±2 min measurement noise plus ordinary variation, so their critical-branch labels are fragile; (iii) all 12 cases come from one morning with an almost perfectly regular 15-minute arrival cadence, so none of these rankings can be assumed stable under different load.

# 4. Counterfactual redesign analysis

## Method

Counterfactuals must be evaluated through the final station, otherwise join improvements are mistaken for flow-time improvements. I therefore re-simulate F as

```
fs_c = max(J_c, server_free(r_c)) + Lag_c ,   service 20 min
```

with `Lag_c` calibrated per case from the baseline (`release_lag` in §2). Calibrated this way the simulator reproduces the observed log **exactly** (verified in §6), so every reported difference is attributable to the intervention rather than to model error.

Assumption C1: only the named quantity changes; branch dispatch order, arrivals, and the F1/F2 alternation are held fixed unless the counterfactual explicitly changes them. Assumption C2: `Lag_c` is a property of the case, not of the wait it experienced. This is the weak point — four cases (F05, F08, F09, F11) were fully blocked and have `Lag_c = 0` by construction, so any counterfactual that removes their blocking implicitly assumes zero handover for them. I therefore bound rather than point-estimate the capacity counterfactual.

## CF1 — reduce A service time by 20% (50 → 40 min)

**Direct effect.** A never queues, so every `A_end` moves in by exactly 10 minutes; 120 minutes of service capacity is freed. Yet the join moves in only **15 minutes in total, in 2 of 12 cases** (F01 −5, F11 −10), and total realized flow time falls by **5 minutes across the whole log** (0.42 min/case, 0.36%).

**Zero-benefit cases and why.** Ten cases get nothing at the join because another branch is critical: B in 8 (F02, F03, F05, F06, F07, F09, F10, F12) and C in 2 (F04, F08). In those cases A merely converts 10 minutes of service into 10 more minutes of synchronization waiting — `W_A` rises from a mean of 11.0 to 21.0. F11 is worse than useless: it gains a full 10-minute join improvement and **still finishes at 12:10**, because F1 is occupied with F09 until 11:50. So only F01's 5 minutes survives to the case level. This is the single most important quantitative finding in the whole analysis: a 20% cut in the branch with the largest mean service time yields a 0.36% flow-time improvement.

**Secondary effects.** A's station frees 120 minutes of capacity (a fall from roughly 2.8 to 2.2 busy server-equivalents), which is a real cost saving but not a flow-time saving. Critical-branch mix shifts only from (A 2, B 8, C 2) to (A 1, B 9, C 2) — and the A entry is now a tie in F11 where A and B both end at 11:20, resolved only by the tie-break rule. Risk: if the 50-minute duration reflects a fixed assay protocol (incubation, cure time), a 20% cut may be a quality change rather than an efficiency change, and this log cannot distinguish those.

## CF2 — reduce B queue delay by 50%

**Direct effect.** `B_start` moves to `fr_c + Q_B/2`, service unchanged, so `B_end` moves in by 2.5–15 min. Join gain: **92.5 minutes across 8 cases**. Realized flow saving: **122 minutes** (10.17 min/case, 8.8%); mean flow 115.25 → 105.08; worst case 130 → 115.

**Why realized saving (122) exceeds join gain (92.5).** Positive downstream spillover: earlier finishes release F1/F2 earlier, which unblocks *later* cases whose own join did not improve at all. F04 (join unchanged, C critical) still saves 8 minutes because F2 becomes free at 09:50 instead of 10:00; F08 (C critical) saves 8 minutes the same way. Queueing systems amplify upstream improvements, and a per-case delta-join calculation would have understated the benefit by 24%.

**Where the benefit is capped, and by what.** The join gain is `min(Q_B/2, X_B)`, i.e. the improvement is truncated by A's 50-minute wall. F05 (12.5 available, margin 10 → 10 realized), F10 (10 available, margin 5 → 5), F11 and F01 and F04 and F08 (margin held by another branch → 0). Only F01 ends with zero realized flow benefit; the other 11 gain something, but 3 of them gain purely through spillover rather than through their own join.

**Zero-benefit cases.** F01 (A critical, and halving a 5-minute queue cannot change that), plus F04/F08 at the join (C critical). Nothing in CF2 addresses C's queue outliers, so the two C-critical cases remain C-critical.

**Secondary effects.** Critical-branch mix flips from (A 2, B 8, C 2) to (**A 6**, B 4, C 2), with F02 and F06 becoming exact A/B ties — deterministic tie-breaking now materially affects the reported bottleneck, which is precisely why §6 makes it explicit. This is the bottleneck migrating to A, and it is the reason CF2 alone recovers 122 of a theoretical 120-minute join headroom and then stalls. Operationally, pulling B starts forward compresses B arrivals toward `fork_release`, raising instantaneous demand at the B station: observed peak B concurrency is 4 today, and under CF2 the B station would need to sustain that peak more often. Cutting a *queue* by fiat is not free — it presumes the queue is a policy or dispatch artefact, not capacity (see §7, where the evidence actually favours the policy interpretation).

## CF3 — final-station capacity and downstream queueing

The 176 minutes of downstream wait split into 73 min of same-resource blocking and 103 min of residual lag. **Capacity can only address the 73.** That framing changes the conclusion completely.

**CF3a — pool F1/F2 (drop strict alternation; first-free server, FIFO on `J_c`), lags as observed.** Net saving only **20 minutes**, 9 cases unaffected, and **two cases get worse** (F07 and F10 each lose 10 min) because FIFO-on-`J_c` reorders the queue relative to the observed alternation. Worst-case flow rises from 130 to **140** minutes. A pure pooling change redistributes waiting more than it removes it, and it degrades the tail — the opposite of what a pooling argument usually promises.

**CF3b — add a third final resource, lags as observed.** Saving exactly **73 minutes** (6.08/case, 5.3%), i.e. all blocking eliminated, in 6 cases; 6 cases gain nothing because they were never blocked. But this is the *optimistic* end of a range: it credits the four fully-blocked cases with zero handover lag, which is an artefact of Assumption C2. If those four cases actually carry the median idle-server lag of 15 minutes, the saving collapses to about **18 minutes** (1.5/case). Honest interval: **18–73 minutes**, likely near the middle, around 40 minutes. Against that, F1/F2 utilization is already only ~67% (120 busy minutes each over a ~180-minute serving window; offered load is 20/15 = 1.33 servers), and a third server drops it to ~44%. Buying a third of the final station's capacity for 1.5–6 min/case is poor value.

**CF3c — cut the residual lag to 5 minutes, keeping 2 dedicated resources.** Saving **91 minutes** (7.58/case, 6.6%), 11 of 12 cases benefit, worst case 130 → 120. Only F11 gains nothing (it is blocking-limited, not lag-limited). This dominates adding a server, at plausibly lower cost — *if* the lag is compressible, which depends entirely on what it actually is (§7).

**CF3d — pool and cut the lag to 5 minutes.** Saving **106 minutes** (8.83/case, 7.7%), every case benefits, worst case 120. Pooling and lag reduction are complements: pooling alone is nearly worthless and hurts the tail, but once the lag is small the reordering penalty disappears and pooling adds 15 minutes on top of CF3c.

**Does downstream congestion mask branch improvements?** Yes, demonstrably, and asymmetrically:

- It masked CF1 **completely** in F11 (10-min join gain → 0-min flow gain).
- A separate counterfactual capping C's queue at its modal 5 minutes yields a 12-minute join gain in F04 and F08 and **exactly 0 minutes of flow-time benefit**, because F04 is then lag-limited and F08 is blocking-limited. A fix that looks worthwhile at the join is entirely invisible to the customer.
- It did **not** mask CF2 — there the effect ran the other way, with spillover *amplifying* the benefit from 92.5 to 122 minutes. Masking is not a uniform discount factor; whether it bites depends on whether the specific case is join-limited, lag-limited or blocking-limited. That has to be decided case by case, which is what the simulator is for.

**Interaction / sequencing.** CF1 + CF2 together give a 117.5-minute join gain versus 107.5 if the two were additive — super-additive, because removing the A backstop unlocks B gains that were previously truncated (F05 12.5 instead of 10, F10 10 instead of 5, F11 10 instead of 0). In realized flow time the combination gives 129.5 min versus 127 for the sum of the parts. The order matters enormously: A-first buys 5 minutes, B-first buys 122, and A-after-B buys another 7.5. The full stack (CF2 + pooling + lag 5) reaches **204 minutes saved, 17 min/case, 14.8%**, with mean flow 98.25 and worst case 105 — a 25-minute reduction in the tail.

# 5. Recommended redesigns and risks

## Redesign 1 — Dispatch B at fork_release (attack B's queue, not its service)

**What.** Make `B_start = fork_release` the default: reserve the stress-test rig at fork time rather than dispatching B after A and C, and treat any `B_queue > 5 min` as an exception requiring a reason code. CF2 halved the queue; full elimination is the ceiling.

**Throughput.** Flow time is not throughput here. Arrivals are one per 15 minutes and no station is saturated (F1/F2 at ~67%, A at ~70% of an assumed 4 servers, B at ~48%, C at ~45%), so throughput is arrival-limited and this change adds none. Sell it as flow time and predictability, not capacity.

**Flow-time tail.** Strongest single lever on the tail: worst case 130 → 115 min at 50% queue reduction, and the five worst cases are all B-critical. Standard deviation of flow time falls because B is the only branch whose cycle time correlates with flow time.

**Resource utilization.** B station utilization is unchanged in total (same work, earlier), but demand becomes more bursty: B starts would cluster at `fork_release`, and peak concurrency would need to sustain the currently occasional value of 4. Because arrivals are 15 minutes apart and B's service is 30–45 minutes, steady-state concurrency needs ceil(45/15) = 3 rigs with headroom for 4 — which the log already shows exists, but only intermittently.

**New bottlenecks.** Certain and predictable: **A becomes critical in 6 of 12 cases** (up from 2), with F02 and F06 exact ties. The stage floor is A's deterministic 50 minutes, so after this change the fork-join stage cannot fall below 50 min/case (600 min total against 732 today) no matter what happens to B and C. The second-order bottleneck is the downstream station, which is why Redesign 2 is a complement rather than an alternative.

**Synchronization effects.** Mean `W_B` rises from 4.3 toward 15+ minutes and mean `W_A` falls toward 0 — synchronization waiting migrates from C and A onto B. This is progress (imbalance shifting onto the branch with slack) but it means B staff will observe more idle finished work and may misread the change as making things worse. Instrument `W_ci` and publish it so the imbalance shift is expected rather than alarming.

**Pilot / measure first.** (1) The decisive unknown: *why* does B wait? F02 waited 20 minutes while only one B job was in progress, against an observed peak concurrency of 4 — so the wait is not explained by contention among the observed jobs. Add a reason code (rig unavailable / calibration / setup / awaiting sample / dispatcher batching / staff shift) for 3–4 weeks before spending anything. If the answer is "capacity", CF2 is not implementable as modelled and the cost is rigs, not policy. (2) Confirm true B rig count and any case-to-rig eligibility constraints. (3) Then run dispatch-at-fork on a random half of cases and measure `Q_B`, `W_B`, `X_B` and total flow time; the expected effect (≈10 min/case) is large relative to the ±2 min measurement noise but needs on the order of 30–50 cases per arm to separate from day-to-day variation.

## Redesign 2 — Diagnose and compress the join → F handover, then pool F1/F2

**What.** Two coupled changes: (a) reduce the residual lag from a median of 15 minutes to ~5 by logging a `join_confirmed` event and removing whatever sits in that gap; (b) abandon the strict F1/F2 alternation in favour of first-free assignment. Do (a) first.

**Throughput.** Again none directly; the final station is at ~67% utilization. But pooling raises *effective* capacity at the same headcount, which matters if arrival rates ever rise — under a burst, two pooled servers behave much better than two dedicated ones.

**Flow-time tail.** CF3d gives 8.83 min/case and cuts the worst case from 130 to 120. Critically, **pooling alone (CF3a) makes the tail worse (140 min)** while saving a net 20 minutes. Do not ship pooling on its own; ship it after the lag is compressed, and with a queue discipline chosen deliberately (FIFO on `J_c` costs F07 and F10 10 minutes each; longest-waiting-first or an EDD rule would protect the tail better).

**Resource utilization.** F1/F2 utilization stays at ~67% under pooling and drops to ~44% if a third resource is added — which is why I recommend pooling plus lag reduction (106 min saved, no new headcount) over a third resource (18–73 min saved for 50% more headcount).

**New bottlenecks.** If the lag compresses and B is also fixed, the constraint becomes A's 50-minute assay plus the 20 minutes of final service — a floor of about 90 minutes of flow time against the current mean of 115. Also watch for a masking inversion: with a small lag, cases arrive at F closer together and blocking (currently 73 min) can rise even as total wait falls.

**Synchronization effects.** None directly on the branches — this change is entirely downstream of the join. Its real synchronization role is *unmasking*: it is what makes branch improvements visible to the customer. Without it, the C-queue fix delivers 12 minutes of join gain and 0 minutes of flow gain, and CF1 delivers 15 minutes of join gain and 5 minutes of flow gain.

**Pilot / measure first.** (1) Add the `join_confirmed` event. This is the highest-value single instrumentation change in the whole system, because the current 103 minutes of residual lag is completely unattributed — it could be handover paperwork, a batch/release policy, a supervisor check, or genuine unlogged work, and the redesign differs in each case. (2) Test whether F1 and F2 are truly interchangeable (qualifications, case-type restrictions) before pooling; the perfectly alternating assignment suggests a deliberate rule, and rules usually exist for a reason. (3) Note that the data already contains evidence the alternation is costly: F11 waited 20 minutes for F1 while F2 was idle from 11:25 to 11:40, and F10 waited for F2 while F1 was free from 10:40. Quantify how often that happens over a longer window before changing the rule.

**Explicitly not recommended.** Cutting A's service time as a first move (5 minutes of realized benefit across 12 cases), and adding a third final resource (18–73 minutes for 50% more capacity at a station already at 67%). A speed-up becomes worthwhile *after* Redesign 1, once A is the constraint in half the cases — sequence it second, not first.

# 6. Reproducible Python

```python
"""
Fork-join delay decomposition for the 3-branch (A/B/C) + join + F process.

Design note (expanded in the comment block at the end):
everything involving the JOIN is computed in pandas, not in PM4Py, because a
directly-follows / performance-DFG view aggregates *pairwise* waiting times and
therefore cannot recover (a) join_ready = max_i end_i, (b) per-branch
synchronization waiting join_ready - end_i, or (c) the split of the wait before F
into "resource blocking" and "release lag". PM4Py is used only where its
semantics genuinely fit: interval-log service times and a performance DFG.
"""

import io
import numpy as np
import pandas as pd

# ----------------------------------------------------------------------------
# 1. Data (embedded exactly as supplied; all events on 2026-05-19)
# ----------------------------------------------------------------------------
RAW = """case,arrival,fork_release,A_start,A_end,B_start,B_end,C_start,C_end,final_start,final_end,final_resource
F01,07:55,08:10,08:10,09:00,08:15,08:55,08:20,08:38,09:08,09:28,F1
F02,08:05,08:25,08:25,09:15,08:45,09:25,08:30,08:50,09:40,10:00,F2
F03,08:20,08:40,08:40,09:30,09:00,09:45,08:45,09:03,10:00,10:20,F1
F04,08:35,08:55,08:55,09:45,09:05,09:35,09:30,09:52,10:10,10:30,F2
F05,08:50,09:10,09:10,10:00,09:35,10:10,09:15,09:35,10:20,10:40,F1
F06,09:05,09:25,09:25,10:15,09:55,10:30,09:40,10:00,10:45,11:05,F2
F07,09:20,09:40,09:40,10:30,10:10,10:55,09:45,10:03,11:10,11:30,F1
F08,09:35,09:55,09:55,10:45,10:00,10:30,10:20,10:50,11:05,11:25,F2
F09,09:50,10:10,10:10,11:00,10:35,11:15,10:15,10:35,11:30,11:50,F1
F10,10:05,10:25,10:25,11:15,10:45,11:20,10:30,10:50,11:40,12:00,F2
F11,10:20,10:40,10:40,11:30,10:50,11:20,10:45,11:03,11:50,12:10,F1
F12,10:35,10:55,10:55,11:45,11:25,12:10,11:00,11:18,12:20,12:40,F2
"""
DAY = "2026-05-19 "
BRANCHES = ["A", "B", "C"]
FINAL_SERVICE_MIN = 20.0                   # constant in the data; used by the simulator
TIE_PRIORITY = {"A": 0, "B": 1, "C": 2}    # deterministic tie-break order

df = pd.read_csv(io.StringIO(RAW))
time_cols = [c for c in df.columns if c not in ("case", "final_resource")]
for c in time_cols:
    df[c] = pd.to_datetime(DAY + df[c])

mins = lambda a, b: (a - b).dt.total_seconds() / 60.0

# ----------------------------------------------------------------------------
# 2. Decomposition components (all custom pandas; none of this is DFG-derivable)
# ----------------------------------------------------------------------------
df["upstream_elapsed"] = mins(df.fork_release, df.arrival)          # U_c
for i in BRANCHES:
    df[f"{i}_queue"] = mins(df[f"{i}_start"], df.fork_release)      # Q_ci
    df[f"{i}_service"] = mins(df[f"{i}_end"], df[f"{i}_start"])     # S_ci
    df[f"{i}_cycle"] = df[f"{i}_queue"] + df[f"{i}_service"]        # K_ci = Q + S

end_cols = [f"{i}_end" for i in BRANCHES]
df["join_ready"] = df[end_cols].max(axis=1)                         # J_c = max_i e_ci
for i in BRANCHES:
    df[f"{i}_sync"] = mins(df.join_ready, df[f"{i}_end"])           # W_ci (NOT summable)

# Critical branch with deterministic tie handling: among branches whose end equals
# join_ready (at the logged 1-minute resolution) take the lowest TIE_PRIORITY.
# Ties do not occur in the baseline but DO occur under counterfactual 2.
def critical(row):
    tied = [i for i in BRANCHES if row[f"{i}_end"] == row["join_ready"]]
    tied.sort(key=lambda i: TIE_PRIORITY[i])
    return pd.Series({"critical_branch": tied[0],
                      "critical_tied": "|".join(sorted(tied)),
                      "n_tied": len(tied)})

df = pd.concat([df, df.apply(critical, axis=1)], axis=1)

df["fork_join_stage"] = mins(df.join_ready, df.fork_release)        # G_c = max_i K_ci
df["downstream_queue"] = mins(df.final_start, df.join_ready)        # D_c
df["final_service"] = mins(df.final_end, df.final_start)            # V_c
df["total_flow_time"] = mins(df.final_end, df.arrival)              # T_c
df["identity_ok"] = np.isclose(
    df.total_flow_time,
    df.upstream_elapsed + df.fork_join_stage + df.downstream_queue + df.final_service)

# Criticality margin X_c,crit: how far the critical branch must be pulled in before
# the runner-up branch takes over. This is the ONLY non-double-counting way to
# attribute stage minutes to a single branch.
df["runner_up_cycle"] = df[[f"{i}_cycle" for i in BRANCHES]].apply(
    lambda r: sorted(r.values)[-2], axis=1)
df["critical_margin"] = df.fork_join_stage - df.runner_up_cycle

# Split the pre-F wait into (a) same-resource blocking and (b) residual lag.
# Needs the resource-level sequence (a per-resource "previous case"), which is
# again a custom pandas computation, not a DFG statistic.
prev_end, rows = {}, []
for _, r in df.sort_values("final_start").iterrows():
    pe = prev_end.get(r.final_resource)
    blocking = 0.0 if pe is None else max(0.0, (pe - r.join_ready).total_seconds() / 60.0)
    rows.append((r["case"], blocking, r.downstream_queue - blocking))
    prev_end[r.final_resource] = r.final_end
df = df.merge(pd.DataFrame(rows, columns=["case", "final_blocking", "release_lag"]), on="case")

pd.set_option("display.width", 220)
CASE_COLS = ["case", "upstream_elapsed", "A_queue", "A_service", "B_queue", "B_service",
             "C_queue", "C_service", "join_ready", "critical_branch", "downstream_queue",
             "final_service", "total_flow_time"]
print("=== Case-level decomposition (minutes) ===")
out = df[CASE_COLS].copy()
out["join_ready"] = out["join_ready"].dt.strftime("%H:%M")
print(out.to_string(index=False))

print("\n=== Supplementary: synchronization waiting, stage, margin, wait split ===")
print(df[["case", "A_sync", "B_sync", "C_sync", "fork_join_stage", "critical_margin",
          "final_blocking", "release_lag", "n_tied", "identity_ok"]].to_string(index=False))
print("sum of per-branch (Q+S+W) equals 3 x stage for every case:",
      bool(np.all(np.isclose(
          sum(df[f"{i}_queue"] + df[f"{i}_service"] + df[f"{i}_sync"] for i in BRANCHES),
          3 * df.fork_join_stage))))
print("stage total %.0f = joint floor %.0f + uniquely attributable %.0f"
      % (df.fork_join_stage.sum(), df.runner_up_cycle.sum(), df.critical_margin.sum()))

# ----------------------------------------------------------------------------
# 3. Aggregate branch comparison
# ----------------------------------------------------------------------------
agg = pd.DataFrame({
    "service_mean": [df[f"{i}_service"].mean() for i in BRANCHES],
    "service_sd":   [df[f"{i}_service"].std(ddof=1) for i in BRANCHES],
    "service_max":  [df[f"{i}_service"].max() for i in BRANCHES],
    "queue_mean":   [df[f"{i}_queue"].mean() for i in BRANCHES],
    "queue_max":    [df[f"{i}_queue"].max() for i in BRANCHES],
    "cycle_mean":   [df[f"{i}_cycle"].mean() for i in BRANCHES],
    "cycle_max":    [df[f"{i}_cycle"].max() for i in BRANCHES],
    "critical_n":   [(df.critical_branch == i).sum() for i in BRANCHES],
    "runner_up_n":  [int((df[[f"{j}_cycle" for j in BRANCHES]].apply(
                         lambda r: sorted(r.items(), key=lambda kv: -kv[1])[1][0], axis=1)
                         == f"{i}_cycle").sum()) for i in BRANCHES],
    "sync_mean":    [df[f"{i}_sync"].mean() for i in BRANCHES],
    "attributable_min": [df.loc[df.critical_branch == i, "critical_margin"].sum()
                         for i in BRANCHES],
    # A's cycle time has zero variance, so no correlation with flow time exists:
    # a perfectly deterministic branch can dominate the LEVEL of flow time while
    # explaining none of its VARIANCE. Variance-based bottleneck hunting misses A.
    "corr_cycle_flow": [np.nan if df[f"{i}_cycle"].std(ddof=1) == 0
                        else df[f"{i}_cycle"].corr(df.total_flow_time) for i in BRANCHES],
}, index=BRANCHES).round(2)
print("\n=== Aggregate branch comparison ===")
print(agg.to_string())

print("\n=== Stage-level means (minutes) ===")
print(df[["upstream_elapsed", "fork_join_stage", "downstream_queue", "final_service",
          "total_flow_time"]].mean().round(2).to_string())
print("downstream wait split: blocking %.0f min + release lag %.0f min = %.0f min"
      % (df.final_blocking.sum(), df.release_lag.sum(), df.downstream_queue.sum()))

zero_B = sum(max(0.0, (r.join_ready - max(r.A_end, r.C_end)).total_seconds() / 60.0)
             for _, r in df.iterrows())
zero_BC = sum((r.join_ready - r.A_end).total_seconds() / 60.0 for _, r in df.iterrows())
print("max join gain if B instantaneous   : %.1f min (%.2f/case)" % (zero_B, zero_B / len(df)))
print("max join gain if B and C instant.  : %.1f min (%.2f/case) -> then A alone binds"
      % (zero_BC, zero_BC / len(df)))

# ----------------------------------------------------------------------------
# 4. Counterfactuals, re-simulating the final station so that downstream
#    masking is visible:  start = max(join_ready, server_free) + lag,  20 min svc.
#    lag is calibrated per case from the baseline release_lag, so the simulator
#    reproduces the observed log exactly before any intervention is applied.
# ----------------------------------------------------------------------------
LAG = dict(zip(df["case"], df.release_lag))
BASE_ENDS = {r["case"]: {i: r[f"{i}_end"] for i in BRANCHES} for _, r in df.iterrows()}
ARRIVAL = dict(zip(df["case"], df.arrival))
RESOURCE = dict(zip(df["case"], df.final_resource))
BASE_FLOW = dict(zip(df["case"], df.total_flow_time))

def simulate(ends, pooled=False, n_servers=2, lag=None):
    """pooled=False keeps the observed strict F1/F2 alternation;
       pooled=True is a shared FIFO queue on join_ready over n_servers."""
    order = sorted(ends, key=lambda c: (max(ends[c].values()), c))   # deterministic
    free = ({f"S{k}": pd.Timestamp.min for k in range(n_servers)} if pooled
            else {"F1": pd.Timestamp.min, "F2": pd.Timestamp.min})
    res = {}
    for c in order:
        j = max(ends[c].values())
        key = min(free, key=lambda s: free[s]) if pooled else RESOURCE[c]
        L = LAG[c] if lag is None else lag
        start = max(j, free[key]) + pd.Timedelta(minutes=L)
        end = start + pd.Timedelta(minutes=FINAL_SERVICE_MIN)
        free[key] = end
        tied = sorted([i for i in BRANCHES if ends[c][i] == j], key=lambda i: TIE_PRIORITY[i])
        res[c] = dict(join_ready=j, critical=tied[0], n_tied=len(tied),
                      final_start=start, final_end=end,
                      flow=(end - ARRIVAL[c]).total_seconds() / 60.0)
    return res

def evaluate(name, ends, **kw):
    sim = simulate(ends, **kw)
    rec = []
    for c in df["case"]:
        d_join = (max(BASE_ENDS[c].values()) - max(ends[c].values())).total_seconds() / 60.0
        rec.append(dict(scenario=name, case=c, d_join=d_join,
                        d_flow=BASE_FLOW[c] - sim[c]["flow"],
                        new_critical=sim[c]["critical"], new_flow=sim[c]["flow"]))
    return pd.DataFrame(rec)

assert all(abs(simulate(BASE_ENDS)[c]["flow"] - BASE_FLOW[c]) < 1e-9 for c in BASE_FLOW), \
    "simulator must reproduce the observed baseline exactly"

# CF1: A service -20% (A never queues, so A_end moves in by 0.2 * S_A).
cf1 = {r["case"]: {"A": r.A_start + pd.Timedelta(minutes=0.8 * r.A_service),
                   "B": r.B_end, "C": r.C_end} for _, r in df.iterrows()}
# CF2: B queue -50% (service unchanged, so B_end moves in by 0.5 * Q_B).
cf2 = {}
for _, r in df.iterrows():
    b_start = r.fork_release + pd.Timedelta(minutes=r.B_queue / 2.0)
    cf2[r["case"]] = {"A": r.A_end, "B": b_start + pd.Timedelta(minutes=r.B_service),
                      "C": r.C_end}
# CF-C: cap C's queue at its modal 5 min (tests the two C-critical outliers).
cfc = {}
for _, r in df.iterrows():
    c_start = r.fork_release + pd.Timedelta(minutes=min(r.C_queue, 5))
    cfc[r["case"]] = {"A": r.A_end, "B": r.B_end,
                      "C": c_start + pd.Timedelta(minutes=r.C_service)}

scen = pd.concat([
    evaluate("CF1 A service -20%", cf1),
    evaluate("CF2 B queue -50%", cf2),
    evaluate("CF3a pool F1/F2, observed lags", BASE_ENDS, pooled=True),
    evaluate("CF3b 3rd final resource", BASE_ENDS, pooled=True, n_servers=3),
    evaluate("CF3c release lag -> 5 min", BASE_ENDS, lag=5.0),
    evaluate("CF3d pooled + lag 5 min", BASE_ENDS, pooled=True, lag=5.0),
    evaluate("CF1+CF2 combined", {c: {"A": cf1[c]["A"], "B": cf2[c]["B"], "C": cf2[c]["C"]}
                                  for c in cf1}),
    evaluate("CF2 + pooled + lag 5", cf2, pooled=True, lag=5.0),
    evaluate("CF-C cap C queue at 5", cfc),
], ignore_index=True)

print("\n=== Counterfactuals: per-case realized flow-time saving (minutes) ===")
print(scen.pivot(index="case", columns="scenario", values="d_flow").to_string())

print("\n=== Counterfactuals: aggregate ===")
summ = scen.groupby("scenario").agg(
    join_gain_total=("d_join", "sum"),
    flow_saving_total=("d_flow", "sum"),
    flow_saving_mean=("d_flow", "mean"),
    cases_no_benefit=("d_flow", lambda s: int((s <= 0).sum())),
    worst_case_flow=("new_flow", "max"),
    mean_flow=("new_flow", "mean")).round(2)
summ.loc["BASELINE"] = [0.0, 0.0, 0.0, len(df), df.total_flow_time.max(),
                        df.total_flow_time.mean()]
print(summ.to_string())
print("NB: join gain > flow saving means downstream masking (CF1, CF-C);")
print("    flow saving > join gain means downstream spillover amplification (CF2).")

print("\n=== Critical-branch mix per scenario (ties resolved by TIE_PRIORITY) ===")
print(pd.crosstab(scen.scenario, scen.new_critical).to_string())

# ----------------------------------------------------------------------------
# 5. PM4Py interval event log: one row per branch and per final activity
# ----------------------------------------------------------------------------
records = []
for _, r in df.iterrows():
    for act, s, e, resource in [
        ("Laboratory Assay", r.A_start, r.A_end, "A_station"),
        ("Machine Stress Test", r.B_start, r.B_end, "B_station"),
        ("Documentation Review", r.C_start, r.C_end, "C_station"),
        ("Release Decision", r.final_start, r.final_end, r.final_resource),
    ]:
        records.append(dict(case_id=r["case"], activity=act, start_timestamp=s,
                            end_timestamp=e, resource=resource))
ev = pd.DataFrame(records).sort_values(["case_id", "start_timestamp", "activity"])

import pm4py
log = pm4py.format_dataframe(ev, case_id="case_id", activity_key="activity",
                             timestamp_key="end_timestamp",
                             start_timestamp_key="start_timestamp")

print("\n=== PM4Py get_service_time: mean active work per activity (interval semantics) ===")
svc = pm4py.get_service_time(log, aggregation_measure="mean",
                             start_timestamp_key="start_timestamp",
                             timestamp_key="time:timestamp")
print((pd.Series(svc) / 60.0).round(2).rename("mean_service_min").to_string())

print("\n=== PM4Py discover_performance_dfg: mean time per directly-follows pair ===")
perf_dfg, sa, ea = pm4py.discover_performance_dfg(log)
for (a, b), v in sorted(perf_dfg.items(), key=lambda kv: -kv[1]["mean"]):
    print(f"  {a:22s} -> {b:22s} mean {v['mean'] / 60.0:7.1f} min")

# ---------------------------------------------------------------------------
# WHICH QUANTITIES ARE CUSTOM PANDAS, AND WHY THE DFG CANNOT SUPPLY THEM
#
# PM4Py supplies correctly:
#   * S_ci and V_c  -- get_service_time on an interval log reproduces the branch
#     and final service means exactly (50.0 / 37.5 / 20.17 / 20.0 min), because
#     "duration of one activity instance" is exactly what its semantics express.
#
# PM4Py cannot supply, and these are therefore pandas computations above:
#   * J_c = max_i e_ci. A DFG has no notion of "all incoming branches complete";
#     it only relates consecutive events within a trace.
#   * W_ci = J_c - e_ci. Synchronization waiting is defined by a MAXIMUM over
#     concurrent branches. No directly-follows relation ranges over a set of
#     concurrent activities, so no directly-follows performance statistic can
#     express it. This is a semantic limitation, not a tooling gap.
```

# 7. Limits of inference

**Causality cannot be established.** Everything above is a timestamp decomposition, i.e. accounting, not inference. "B is critical in 8 of 12 cases" is an observation; "reducing B's queue reduces flow time by 10 min/case" is a *model-based projection* under Assumption C1 (nothing else changes), and the counterfactuals are arithmetic on a re-simulation, not estimated treatment effects. The single strongest reason for caution: the log is suspiciously deterministic — arrivals exactly 15 min apart (except F01→F02 at 10), upstream exactly 20 min (except F01 at 15), A service exactly 50 min in all 12 cases, final service exactly 20 min in all 12 cases, and C's queue equal to exactly 5 min in 8 of 12 cases. This is the signature of a schedule or a plan, not of a free-running stochastic queue. Queueing-theoretic extrapolation to other load levels is therefore unsupported.

**Branch resource capacity is only bounded below, and the bounds contradict a pure-contention story.** Observed maximum concurrency is 4 for A, 4 for B, 3 for C, 2 for F. Those are lower bounds on server counts; the true counts, any case-to-server eligibility rules, shift patterns, and breaks are all invisible. More damaging: F02 waited 20 minutes for B while only one B job (F01) was in progress, and F04 waited 35 minutes for C while only one C job (F03) was running. Under any FIFO multi-server model with the capacity we can see, neither case should have waited at all. So `Q_B` and `Q_C` are **not** explained by contention among the observed jobs. They could be dispatch batching, rig calibration or setup, sample transport, staff scheduling, an unlogged prerequisite, or capacity that varies over the morning. Counterfactual 2 assumes the queue is compressible policy; if it is capacity or a physical setup, the projected 122-minute saving does not exist. This is the largest single threat to the recommendations, and it is why Redesign 1's first pilot step is reason-coding rather than any operational change.

**Work preemption, interruption, and multitasking are invisible.** We have one start and one end per branch instance, so any interruption inside `[s_ci, e_ci]` is silently booked as service. "Active service" is really "elapsed time between the logged start and the logged end". A branch that is touched for 10 minutes, abandoned for 30, and finished in 10 is indistinguishable from 50 minutes of continuous work. This matters for CF1 specifically: if A's 50 minutes is largely unattended incubation, a 20% cut is a protocol change and possibly a quality change, not a productivity gain — and the log cannot tell us which.

**Whether the wait before F is a queue at all is genuinely undecidable here, and two models fit differently.** The 176 minutes split into 73 min of demonstrable same-resource blocking and 103 min of residual lag that occurs *even when the assigned resource is idle*: F01 waited 8 min, F02/F03/F06/F07 waited 15 min, F12 waited 10 min, all with their server free at `join_ready`. There is a nonzero floor, so this is not pure queueing. Two candidate models:

- *Sequential handover* (`fs = max(J, prev_end) + L`, prep only once the server is free) fits all 12 cases with per-case `L ∈ {0, 8, 10, 15}` — but requires `L = 0` for exactly the four fully blocked cases (F05, F08, F09, F11), which is suspicious.
- *Parallel handover* (`fs = max(J + L, prev_end)`, prep overlapping the wait) is consistent with those four cases but fails for F04 (would need L = 18) and F10 (would need L = 20), which contradicts F05's requirement that L ≤ 10.

Neither model is consistent across all 12 cases, so the mechanism is not identified: the 103 minutes could be an unlogged handover or verification step, a release policy (start-times cluster on 5-minute boundaries), a batch window, or a supervisor sign-off. This directly bounds CF3b, which is why I reported 18–73 minutes rather than 73. It also means my `D_c` should be read as "elapsed time between derived join readiness and final start", not as "queueing". Resolving it requires one new event (`join_confirmed`), not more analysis of the existing log.

**The F1/F2 assignment is a policy, not an observation of contention.** Cases alternate F1, F2, F1, F2 in strict arrival order across all 12 cases. That is a rule, and the log gives no clue why: qualification, case type, workload balancing, or coincidence over a small sample. Its cost is visible (F11 waited 20 min for F1 while F2 was idle 11:25–11:40; F10 waited for F2 while F1 was free from 10:40), but whether pooling is *permissible* is a question about the resources, not the timestamps.

**Also not identifiable.** (i) Whether the AND-join rule is exactly "all three complete" — a fourth hidden precondition would reallocate time from `D_c` to the join. (ii) Resolution: 1-minute rounding puts ±2 min on every derived difference, so the 5-minute margins in F01, F08 and F10 are not safely distinguishable from zero, and the 8-vs-2-vs-2 criticality split has a Wilson interval of roughly 39–86% for B. (iii) Sample and horizon: 12 cases from a single morning (07:55–12:40), one arrival cadence, no overnight or shift-change effects, no weekday variation, no seasonality; F12's downstream is right-censored in the sense that no successor is observed for it. (iv) No rework, failure, re-test or rejection is visible; if a stress test can fail and repeat, `S_B` is a mixture and its mean is not a design parameter. (v) No cost, capability, or quality data, so "reduce A by 20%" and "add a resource" cannot be compared on anything but time. (vi) Nothing distinguishes `arrival → fork_release` as work from waiting: it is 20 min in 11 of 12 cases, which looks like a fixed preparation protocol rather than a queue, but with A never queuing behind it and no start event for the preparation step, that is an inference from constancy, not a measurement.
