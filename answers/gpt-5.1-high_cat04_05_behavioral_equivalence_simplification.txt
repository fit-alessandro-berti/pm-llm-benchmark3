## 1. Equivalence Notions

**Visible trace equivalence after hiding `tau`.**  
Each process tree induces a set of complete runs. After hiding `tau`, every run is represented as a finite sequence of visible labels
\( \langle e_1, e_2, \dots, e_n \rangle \) where each \(e_i \in \{\text{'Open Case'},\text{'Analyze Revision'},\text{'Check Revision'},\text{'Approve Revision'},\text{'Rework Case'},\text{'Close Case'}\}\).
Two models are **visibly trace equivalent** iff their sets of such sequences are identical.  
Duplicate visible labels are distinguished **by position in the sequence**: the second `'Analyze Revision'` in a trace is different from the first, even though they share the same label.

**Bounded visible-language equivalence under P3.**  
Let \(L(M)\) be the visible trace language of model \(M\) after hiding `tau`. Define the **P3-bounded language**
\[
L_{\leq}(M) = \{\sigma \in L(M)\mid \text{len}(\sigma) \le 12 \text{ and }\#_{\text{Analyze Revision}}(\sigma) \le 3\}.
\]
Two models are **P3-bounded equivalent** iff \(L_{\leq}(A) = L_{\leq}(B)\).  
This is an **exhaustive bounded** comparison over the stated bounds, but it is **not** a proof of unbounded equivalence beyond the bound.

**Business-relevant equivalence under P1 (operational compliance view).**  
For a visible trace \(\sigma\) of the form:
\[
\sigma = \langle \text{'Open Case'}, \dots, \text{'Close Case'} \rangle,
\]
partition the sub-sequence between `'Open Case'` and `'Close Case'` into **revision segments** by splitting on `'Rework Case'`.  
For each segment \(i\), define:
- \(a_i\): number of `'Analyze Revision'` events in segment \(i\);
- \(c_i\): number of `'Check Revision'` events in segment \(i\);
- \(p_i\): the ordered list of `'Approve Revision'` events in segment \(i\) (their positions within the segment remain visible);
- the total number and order of segments is also observed.

The **P1 observation** of a trace is:
\[
\pi_{P1}(\sigma) = \big\langle (a_1, c_1, p_1), \dots, (a_k, c_k, p_k) \big\rangle.
\]
P1’s compliance requirement is:
- for every segment \(i\), if \(a_i \ge 1\) (a revision attempt was made), then \(c_i \ge 1\) (there is at least one `'Check Revision'` in that segment);
- `'Rework Case'` separates revisions, so checks cannot “belong” to a later revision.

Two models are **P1-equivalent** if, after hiding `tau`, the sets of P1 observations they admit are identical and **all** admitted traces satisfy the above compliance constraint. Under P1, duplicate visible labels are distinguished both **by segment** and **by position within the segment**; the number and placement of `'Approve Revision'` occurrences inside a segment are part of the observation.

**Abstracted dashboard equivalence under P2 (executive view).**  
From a visible trace \(\sigma\), define the P2 abstraction:
- `open_first`: whether the first visible event is `'Open Case'`;
- `close_last`: whether the last visible event is `'Close Case'`;
- `num_analyze`: total number of `'Analyze Revision'` events in the whole trace;
- `any_check`: Boolean, true iff at least one `'Check Revision'` occurs anywhere;
- `any_rework`: Boolean, true iff at least one `'Rework Case'` occurs anywhere.

`'Approve Revision'` and all `tau` events are **hidden** in this view, and the exact interleaving of `'Analyze Revision'` with `'Check Revision'` is not recorded.  
The **P2 observation** of a trace is:
\[
\pi_{P2}(\sigma) =
(\text{open\_first}, \text{close\_last}, \text{num\_analyze}, \text{any\_check}, \text{any\_rework}).
\]
Two models are **P2-equivalent** if their sets of P2 observations coincide.  
Under P2:
- duplicate `'Check Revision'` events are **collapsed** to the Boolean `any_check`;
- duplicate `'Rework Case'` events are collapsed to `any_rework`;
- duplicate `'Analyze Revision'` events are distinguished **by count but not by exact position**.

## 2. Structural Comparison

| Feature | Model A | Model B | Semantic consequence |
| --- | --- | --- | --- |
| Loop scope | `*( ->( +('Analyze Revision','Check Revision'), X('Approve Revision', tau)), 'Rework Case')` — `'Check Revision'` is **inside** the loop body | `+('Check Revision', *( ->('Analyze Revision', X('Approve Revision', tau)), 'Rework Case'))` — `'Check Revision'` is **outside** the loop, in parallel with it | In A, each loop iteration necessarily contains (at least) one `'Check Revision'`; in B, there is exactly one `'Check Revision'` for the **entire case** irrespective of the number of iterations. |
| Minimum number of `'Check Revision'` per complete case | At least 1, and in fact **exactly one per loop iteration**; the loop must execute the body once, so at least one check always occurs. | **Exactly 1** per complete case, because the parallel branch contains a single `'Check Revision'` leaf. | With multiple analysis iterations, A yields multiple checks, B yields one. |
| Maximum number of `'Check Revision'` per case | Unbounded: as many iterations of the loop as desired, each with one check. | Exactly 1, regardless of the number of analysis/rework iterations. | A can express “many checks over time”; B can never have more than one, which is fatal for P1. |
| Placement of `'Check Revision'` relative to `'Analyze Revision'` and `'Rework Case'` | For each iteration, `'Analyze Revision'` and `'Check Revision'` are executed in parallel within the same `+(...)` block, then (optionally) `'Approve Revision'`, then possibly `'Rework Case'` before the next iteration. A check can appear **before or after** the analyze of its own revision, but it **cannot cross revision boundaries**: no `'Rework Case'` can occur between an analyze and its associated check. | The single `'Check Revision'` runs in parallel with the **entire loop**: it may occur before any `'Analyze Revision'`, between two analyses, after all analyses (but before `'Close Case'`), and independent of `'Rework Case'` boundaries. A revision segment may contain **no** check at all. | A enforces “one check per revision segment”; B allows some revisions to be un-checked and others to share a single global check. |
| Optional `'Approve Revision'` occurrences | `X('Approve Revision', tau)` appears once **per loop iteration** after the analyze/check block; each revision may or may not be explicitly approved. | The same `X('Approve Revision', tau)` appears once per loop iteration inside the analysis loop. | Both admit the same patterns of optional approvals (0 or 1 per revision), but they attach to different check structures. |
| Concurrency structure | Concurrency is **local**: only `'Analyze Revision'` and `'Check Revision'` for a given revision are in parallel; the surrounding loop and `'Open Case'`/`'Close Case'` are purely sequential. | Concurrency is **global**: `'Check Revision'` is parallel to the entire analysis/rework loop. | Footprints and partial orders differ: in A, concurrency links only analyze/check of the same revision; in B, `'Check Revision'` is concurrent with all analyses and reworks. |
| Join before `'Close Case'` | The root is a pure sequence `->('Open Case', loop, 'Close Case')`; there is **no top-level parallel join** before `'Close Case'`. Joins only occur locally inside the analyze/check parallel block. | The root sequence contains `+('Check Revision', loop)` as its middle element; `'Close Case'` is only enabled when **both** the global check and the loop have completed. | In B, closing the case synchronizes the completion of both the global check and the revision loop; in A, loop completion alone suffices (because checks are scoped to the loop body). |

## 3. Verdicts

| View | Verdict | Confidence | Decisive reason | Caveat |
| --- | --- | --- | --- | --- |
| Unbounded visible trace equivalence (after hiding `tau`) | not equivalent | High | Model A produces one `'Check Revision'` per loop iteration, so any run with \(k \ge 2\) analysis iterations has \(k\) check events; Model B always has exactly one `'Check Revision'` per case. Thus there are visible traces with multiple checks (A-only) and traces with multiple analyses but a single check (B-only). | None for the unbounded language: the difference already appears for two iterations. |
| P1 — operational compliance view | not equivalent | High | Under P1, every revision segment that contains an `'Analyze Revision'` must also contain at least one `'Check Revision'` before the next `'Rework Case'` or `'Close Case'`. In Model A this is structurally enforced; in Model B, a single global check can be scheduled so that some segments with analyses contain no check. | P1 abstracts away the internal ordering of `'Analyze Revision'` vs `'Check Revision'` within a segment; it focuses on counts per segment. Even under this abstraction, B violates the “check per revision” requirement. |
| P2 — abstracted executive dashboard view | equivalent only under stated abstraction | Medium–High | After mapping each complete run to `(open_first, close_last, num_analyze, any_check, any_rework)`, both models generate the same combinations: `'Open Case'` first and `'Close Case'` last, at least one analyze and one check, and `any_rework` true iff there are at least two analyses. The difference in how checks are distributed over revisions is **intentionally hidden** by this abstraction. | P2’s abstraction collapses all per-revision compliance information; two models can be dashboard-equivalent while being very different from an audit/compliance viewpoint. |
| P3 — bounded visible-language equivalence (≤12 visible events, ≤3 analyses) | not equivalent | High | Even with at most three `'Analyze Revision'` occurrences, we can construct traces with two analyses and two checks (Model A only) and traces with two analyses and a single check (Model B only). An exhaustive bounded search up to this limit therefore finds genuine language differences. | Bounded equivalence cannot prove unbounded equivalence; it can only disprove it by finding counterexamples within the bound. Here it already finds such counterexamples. |

## 4. Counterexample Traces

All traces below list only **visible** events (i.e., after hiding `tau`). Each trace starts with `'Open Case'` and ends with `'Close Case'`.

| Trace ID | Trace (visible sequence) | Model A | Model B | First decisive semantic difference | Relevant view |
| --- | --- | --- | --- | --- | --- |
| A1 | `['Open Case', 'Analyze Revision', 'Check Revision', 'Rework Case', 'Analyze Revision', 'Check Revision', 'Close Case']` | yes | no | Contains **two** `'Check Revision'` events (one per revision). In Model B there is only one check leaf, so no complete run can have two checks. | Unbounded visible traces; P1; P3 (2 analyses, 2 checks within the bound). |
| A2 | `['Open Case', 'Check Revision', 'Analyze Revision', 'Approve Revision', 'Rework Case', 'Analyze Revision', 'Check Revision', 'Close Case']` | yes | no | Again two checks for two analyses, but the first revision executes `'Check Revision'` before `'Analyze Revision'` due to local parallelism, followed by `'Approve Revision'`. Model B cannot realize **any** trace with two checks. | Unbounded visible traces; P1; P3. |
| B1 | `['Open Case', 'Analyze Revision', 'Approve Revision', 'Rework Case', 'Analyze Revision', 'Approve Revision', 'Check Revision', 'Close Case']` | no | yes | There are **two** analyses but only **one** check, placed after the second analysis and after the rework. In Model A, each revision segment with an analysis must contain its own check before `'Rework Case'` or `'Close Case'`, so a first revision without a check is impossible. | Unbounded visible traces; P1 (violates “check per revision”); P3. |
| B2 | `['Open Case', 'Check Revision', 'Analyze Revision', 'Approve Revision', 'Rework Case', 'Analyze Revision', 'Approve Revision', 'Close Case']` | no | yes | Again two analyses but a single check, now scheduled at the very beginning (before any analyze). Model A would require a second check for the second revision; thus it cannot produce a run with two analyses and only one check. | Unbounded visible traces; P1; P3. |

All four counterexamples use two analysis attempts, satisfying the requirement for at least one trace with two analyses.  
The presence or absence of `'Approve Revision'` does **not** repair the mismatch:
- Both models allow an optional approval after each analysis; adding or removing approvals in these examples never changes the number or placement of checks per revision.
- Hiding `tau` only removes internal silent choices of the `X('Approve Revision', tau)` operator when the `tau` branch is taken; it does not affect any of the visible patterns above. Thus these counterexamples remain valid whether or not some iterations take the silent branch.

## 5. Bounded Comparison Code

```python
import pm4py
from collections import deque


MODEL_A_STR = """->(
  'Open Case',
  *(
    ->(
      +('Analyze Revision', 'Check Revision'),
      X('Approve Revision', tau)
    ),
    'Rework Case'
  ),
  'Close Case'
)"""

MODEL_B_STR = """->(
  'Open Case',
  +(
    'Check Revision',
    *(
      ->(
        'Analyze Revision',
        X('Approve Revision', tau)
      ),
      'Rework Case'
    )
  ),
  'Close Case'
)"""


def parse_and_convert(tree_str):
  """Parse a process tree string and convert it to a Petri net."""
  tree = pm4py.parse_process_tree(tree_str)
  net, im, fm = pm4py.convert_to_petri_net(tree)
  # Optional: wrap into an accepting Petri net if desired
  return tree, net, im, fm


tree_a, net_a, im_a, fm_a = parse_and_convert(MODEL_A_STR)
tree_b, net_b, im_b, fm_b = parse_and_convert(MODEL_B_STR)

# 3. Check soundness (workflow net soundness diagnostics printed by pm4py)
print("Model A soundness:")
pm4py.check_soundness(net_a, im_a, fm_a, print_diagnostics=True)
print("Model B soundness:")
pm4py.check_soundness(net_b, im_b, fm_b, print_diagnostics=True)


def marking_key(marking):
  """
  Canonical hashable representation of a marking.
  This collapses structurally equal markings so we can detect revisits.
  """
  return tuple(sorted((p.name, marking[p]) for p in marking))


def bounded_visible_language(net, im, fm,
                             max_visible_len=12,
                             max_analyze=3,
                             analyze_label="Analyze Revision",
                             tau_label="tau"):
  """
  Exhaustively enumerate all complete visible traces within the P3 bounds.

  - Uses an explicit breadth-first search over markings.
  - Hides transitions whose label is None or equals tau_label.
  - Avoids infinite exploration by remembering (marking, visible_len, analyze_count).
  """
  # State: (marking, visible_trace (tuple of labels), analyze_count)
  queue = deque()
  start_state = (im, tuple(), 0)
  queue.append(start_state)

  seen = set()
  seen.add((marking_key(im), 0, 0))

  traces = set()

  while queue:
    marking, trace, analyze_count = queue.popleft()
    visible_len = len(trace)

    # If we reached a final marking, record the trace (even if it uses fewer than the max bounds)
    if marking == fm:
      traces.add(trace)

    # 4. Get enabled transitions for this marking.
    # Prefer the convenience wrapper mentioned in the problem statement.
    try:
      enabled = pm4py.get_enabled_transitions(net, marking)
    except AttributeError:
      # Fallback to the lower-level Petri net semantics API, if needed.
      from pm4py.objects.petri import semantics as petri_semantics
      enabled = petri_semantics.enabled_transitions(net, marking)

    for t in enabled:
      label = getattr(t, "label", None)

      # Decide whether this transition is visible or silent.
      is_tau = (label is None) or (label == tau_label)

      # Fire the transition to obtain the successor marking.
      try:
        new_marking = pm4py.execute_transition(net, marking, t)
      except AttributeError:
        from pm4py.objects.petri import semantics as petri_semantics
        new_marking = petri_semantics.execute(t, net, marking)

      new_trace = trace
      new_analyze_count = analyze_count
      new_visible_len = visible_len

      if not is_tau:
        # Enforce the P3 bounds on visible length and number of analyses.
        if visible_len + 1 > max_visible_len:
          continue
        if label == analyze_label and analyze_count + 1 > max_analyze:
          continue
        new_visible_len = visible_len + 1
        new_trace = trace + (label,)
        if label == analyze_label:
          new_analyze_count = analyze_count + 1

      key = (marking_key(new_marking), new_visible_len, new_analyze_count)
      if key not in seen:
        seen.add(key)
        queue.append((new_marking, new_trace, new_analyze_count))

  return traces


# 5. Compute bounded visible trace sets for both models under P3.
bounded_a = bounded_visible_language(net_a, im_a, fm_a)
bounded_b = bounded_visible_language(net_b, im_b, fm_b)

# 6. Compare and print traces unique to each model.
only_a = bounded_a - bounded_b
only_b = bounded_b - bounded_a

print("=== Traces unique to Model A (within P3 bounds) ===")
for t in sorted(only_a):
  print(list(t))

print("=== Traces unique to Model B (within P3 bounds) ===")
for t in sorted(only_b):
  print(list(t))

print(f"Total bounded traces A: {len(bounded_a)}")
print(f"Total bounded traces B: {len(bounded_b)}")
print(f"Unique in A: {len(only_a)}, unique in B: {len(only_b)}")
```

This breadth-first exploration is **exhaustive within the P3 bounds**: every reachable marking/visible-length/analysis-count triple is explored at most once.  
By contrast, a call such as:

```python
log_a = pm4py.play_out(tree_a, no_traces=1000, max_trace_length=12)
log_b = pm4py.play_out(tree_b, no_traces=1000, max_trace_length=12)
```

would only produce a **random sample** of traces; equal sampled languages or a small symmetric difference in such logs would provide **heuristic evidence** but never a proof of bounded equivalence.

## 6. Stochastic and Footprint Comparison

**Footprint comparison.**  
`pm4py.discover_footprints(...)` can be applied directly to the trees (or their accepting Petri nets) to obtain relations such as “directly-follows” and “in parallel”:

```python
fp_a = pm4py.discover_footprints(tree_a)
fp_b = pm4py.discover_footprints(tree_b)
print("Footprints Model A:", fp_a)
print("Footprints Model B:", fp_b)
```

We expect both footprints to show concurrency between `'Analyze Revision'` and `'Check Revision'`, but with **different scopes**:
- In Model A, concurrency is local to each revision (analyze/check within one loop iteration).
- In Model B, `'Check Revision'` is concurrent with the entire analysis/rework loop, so footprints will reflect additional parallel relations between `'Check Revision'` and `'Rework Case'`.

Similar footprints (or even equal ones, if computed coarsely) are **not sufficient** to guarantee trace equivalence: footprints abstract from counts, loop unfoldings, and long-range dependencies such as “each revision gets its own check”.

**Stochastic language and Earth Mover’s Distance (EMD).**  
If we equip the process trees with stochastic semantics (for example, assuming **uniform probabilities** over XOR branches and loop continuation decisions up to a finite length), we can approximate stochastic languages and compare them with EMD:

```python
# Example: approximate stochastic languages under the P3 bounds
stoch_lang_a = pm4py.get_stochastic_language(
  tree_a,
  max_trace_length=12,
  max_iteration=100000  # or similar bound on generated runs
)
stoch_lang_b = pm4py.get_stochastic_language(
  tree_b,
  max_trace_length=12,
  max_iteration=100000
)

emd_value = pm4py.compute_emd(stoch_lang_a, stoch_lang_b)
print("EMD between stochastic languages (bounded):", emd_value)
```

This yields a **distance between probability distributions** over (bounded) traces:
- A **small EMD** suggests that, under the assumed probabilities and within the given bounds, the two models behave similarly for most runs.
- An EMD of **zero** would mean that the induced probability distributions over the **bounded** language coincide for the chosen probability model.

However:
- The probabilities themselves are **assumptions** (e.g., uniform loop continuation, uniform XOR choices); changing them can change the distributions and the EMD.
- Even an EMD of zero over the bounded language does **not** establish unbounded trace equivalence; loops beyond the bound may still diverge.
- Stochastic comparison cannot detect purely **qualitative** differences such as “every revision must have its own check” unless those differences are given non-zero probability mass under the chosen distribution.

Thus, footprints, stochastic language, and EMD provide **supporting evidence** about similarity or dissimilarity but cannot replace explicit trace and property reasoning.

## 7. Complexity Comparison

**Process-tree structure (manual analysis).**

For both models we can count nodes directly from the given trees:

- Model A:  
  - Operators: root `->`, inner `*`, inner `->`, `+`, and `X` — **5 operator nodes**.  
  - Leaves: `'Open Case'`, `'Close Case'`, `'Rework Case'`, `'Analyze Revision'`, `'Check Revision'`, `'Approve Revision'`, `tau` — **7 leaves** (6 visible, 1 silent).  
  - Total nodes: **12**.
- Model B:  
  - Operators: root `->`, `+`, inner `*`, inner `->`, and `X` — **5 operator nodes**.  
  - Leaves: `'Open Case'`, `'Close Case'`, `'Check Revision'`, `'Analyze Revision'`, `'Approve Revision'`, `tau`, `'Rework Case'` — **7 leaves** (6 visible, 1 silent).  
  - Total nodes: **12**.

In both models:
- Maximum operator nesting depth is the same: a path to `'Approve Revision'` or `tau` goes through **four operator layers** (root `->`, then either `*` or `+`, then the inner `*`/`->`, then `X`).
- Visible-leaf count = 6, silent-leaf count = 1.
- Duplicate-label count (structural) = 0: every visible label appears in exactly one leaf, even though loops generate multiple **runtime** occurrences.

**Code for structural counting.**

```python
from collections import Counter


def collect_tree_stats(tree_root):
  """
  Recursively collect structural statistics for a process tree.
  Returns a dict with:
    - nodes
    - operators
    - visible_leaves
    - silent_leaves
    - max_depth (operator depth)
    - label_counts (Counter over visible labels)
  """
  def visit(node, depth):
    if getattr(node, "operator", None) is None:
      # Leaf
      label = getattr(node, "label", None)
      is_silent = (label is None) or (label == "tau")
      return {
        "nodes": 1,
        "operators": 0,
        "visible_leaves": 0 if is_silent else 1,
        "silent_leaves": 1 if is_silent else 0,
        "max_depth": depth,
        "label_counts": Counter({label: 1}) if (label is not None and not is_silent) else Counter(),
      }
    else:
      # Operator
      stats = {
        "nodes": 1,
        "operators": 1,
        "visible_leaves": 0,
        "silent_leaves": 0,
        "max_depth": depth,
        "label_counts": Counter(),
      }
      for child in node.children:
        child_stats = visit(child, depth + 1)
        stats["nodes"] += child_stats["nodes"]
        stats["operators"] += child_stats["operators"]
        stats["visible_leaves"] += child_stats["visible_leaves"]
        stats["silent_leaves"] += child_stats["silent_leaves"]
        stats["max_depth"] = max(stats["max_depth"], child_stats["max_depth"])
        stats["label_counts"].update(child_stats["label_counts"])
      return stats

  return visit(tree_root, depth=0)


stats_a = collect_tree_stats(tree_a)
stats_b = collect_tree_stats(tree_b)

def duplicate_label_count(label_counts):
  """
  Number of duplicate **occurrences**:
  sum over labels of max(0, count - 1).
  """
  return sum(max(0, c - 1) for c in label_counts.values())


print("Model A stats:", stats_a)
print("Model B stats:", stats_b)
print("Model A duplicate labels:", duplicate_label_count(stats_a["label_counts"]))
print("Model B duplicate labels:", duplicate_label_count(stats_b["label_counts"]))
```

We can use PM4Py’s simplicity metric on the nets:

```python
simplicity_a = pm4py.simplicity_petri_net(net_a, im_a, fm_a)
```

## 8. Simplified Model

**Target semantics.**  
We choose **P1 (operational compliance view)** as the primary business purpose: every analysis revision should have its own check before the next rework or case closure, and approvals remain visible. We are willing to **abstract away** the precise internal interleaving between `'Analyze Revision'` and `'Check Revision'` within a revision, treating them as a logically ordered pair instead of a parallel block.

### 8.1 Simplified process-tree expression

A compact, P1-preserving simplification of Model A is:

```text
->(
  'Open Case',
  *(
    ->(
      'Analyze Revision',
      'Check Revision',
      X('Approve Revision', tau)
    ),
    'Rework Case'
  ),
  'Close Case'
)
```

Compared to Model A, this model:
- removes the inner `+('Analyze Revision', 'Check Revision')` parallelism, enforcing a simple sequence `'Analyze Revision'` → `'Check Revision'`;
- keeps the loop structure: one `(analyze, check, optional approve)` per revision, separated by `'Rework Case'`;
- keeps `'Open Case'` and `'Close Case'` as outer delimiters.

Structurally, it reduces the operator count from 5 to 4 (no `+`), while preserving all P1-relevant invariants.

### 8.2 PM4Py code for the simplified model

```python
import pm4py

SIMPLIFIED_STR = """->(
  'Open Case',
  *(
    ->(
      'Analyze Revision',
      'Check Revision',
      X('Approve Revision', tau)
    ),
    'Rework Case'
  ),
  'Close Case'
)"""

simplified_model = pm4py.parse_process_tree(SIMPLIFIED_STR)
net_s, im_s, fm_s = pm4py.convert_to_petri_net(simplified_model)

print("Simplified model soundness:")
pm4py.check_soundness(net_s, im_s, fm_s, print_diagnostics=True)

simplicity_s = pm4py.simplicity_petri_net(net_s, im_s, fm_s)
print("Simplified model Petri net simplicity:", simplicity_s)
```

### 8.3 Preservation table

We compare key properties across the two originals and the simplified model (`S`).

| Property | Model A | Model B | Simplified S | Comment |
| --- | --- | --- | --- | --- |
| P1 compliance: every revision segment with an analyze has at least one check before next rework/close | exact | lost | exact | In A and S, the loop body guarantees an analyze–check pair per revision; B allows multiple analyses to share a single global check. |
| Per-revision approvals visible and attached to the correct revision | exact | exact | exact | Each model has one `X('Approve Revision', tau)` per iteration; S preserves this structure. |
| Dashboard outcomes `(num_analyze, any_check, any_rework)` under P2 | exact | exact | exact | All three models realize the same combinations: at least one analyze and one check; `any_rework` true iff there are ≥2 analyses. |

Here “exact” means the property is preserved without change; “lost” means the property is no longer expressible; and “abstracted” (where applicable) means that multiple concrete behaviors in the original collapse to a single behavior in the simplified model without changing P1-relevant observations.

### 8.4 Regression and negative traces for the simplified model

**Regression traces (must remain allowed, and are P1-compliant):**

1. `R1 = ['Open Case', 'Analyze Revision', 'Check Revision', 'Close Case']`  
   - Single revision, no approval, no rework.
2. `R2 = ['Open Case', 'Analyze Revision', 'Check Revision', 'Approve Revision', 'Close Case']`  
   - Single revision, explicit approval after the check.
3. `R3 = ['Open Case', 'Analyze Revision', 'Check Revision', 'Approve Revision', 'Rework Case', 'Analyze Revision', 'Check Revision', 'Close Case']`  
   - Two revisions, first approved, second only checked; both revisions have their own checks.

All three traces are:
- admitted by Model A and by the simplified model S;
- admitted by Model B as well, but in B the same aggregated behavior can also be realized with the single global check in different positions.

**Negative traces (should be rejected by the simplified model and are P1-noncompliant):**

1. `N1 = ['Open Case', 'Analyze Revision', 'Rework Case', 'Analyze Revision', 'Check Revision', 'Close Case']`  
   - The first revision has an analyze but no check before the rework; S (and A) cannot produce this trace, while B can schedule its single check after the second analyze.
2. `N2 = ['Open Case', 'Analyze Revision', 'Approve Revision', 'Rework Case', 'Analyze Revision', 'Approve Revision', 'Check Revision', 'Close Case']`  
   - Two analyses but only one check in the final segment; S (and A) require one check in each revision segment, so they reject this trace; B accepts it.

These regression and negative traces show that the simplified model:
- preserves the intended P1-compliant behaviors of Model A; and
- deliberately excludes P1-violating behaviors that Model B admits.

## 9. Final Recommendation

- **For P1 (operational compliance)**: Model A and the simplified model S both enforce “one check per revision”; Model B does not. The simplified model S is preferable because it is structurally simpler and easier to explain while still encoding the compliance rule exactly at the trace level relevant for P1.
- **For P2 (executive dashboard)**: Models A, B, and S are equivalent under the given abstraction; however, using the P1-sound simplified model S avoids the risk that the dashboard is later misinterpreted as evidence for per-revision checking when the underlying model (B) does not guarantee it.
- **For P3 (bounded testing)**: Exhaustive bounded exploration (as in the provided code) quickly finds counterexamples showing that A, B, and S differ; bounded agreement alone should never be taken as proof of full equivalence.
- Overall, the **simplified model S** is a good replacement for Model A in both P1 and P2 contexts and should be preferred over Model B, which fails the key P1 compliance requirement despite looking similar at the dashboard level; bounded and stochastic comparisons are useful sanity checks but must be combined with explicit property reasoning before drawing equivalence conclusions.
