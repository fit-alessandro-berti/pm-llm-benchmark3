## 1. Duplicate-handling decision tree

Apply the tree **per candidate group**, never to the whole log by activity and timestamp alone. Equality of `activity + timestamp` is only a screening signal, not evidence.

```
Is (activity, timestamp, object set, payload_hash, source_event_key)
exactly repeated within the same source?
 Yes -> Exact technical duplicate.
         DROP the copy, after recording all source row IDs.
         [No such pair is proven in the candidates.]
 No
   Does external/domain evidence say the rows are observations of
   the same physical/business occurrence?
    Yes, and systems contribute complementary evidence
     -> SAME PHYSICAL EVENT, MULTIPLE OBSERVATIONS.
        MERGE attributes and relations into one canonical event;
        retain every source ID/key. Example: e03/e04, e11/e16.
    Yes, but one row is generated from / summarises the other(s)
     -> SUMMARY DERIVED FROM DETAILED EVENT(S).
        Conservative: RETAIN BOTH, rename the summary and link it
        by derivation provenance. Merge/drop only under an explicit
        abstraction policy.
    No / not established
      Were different source activities mapped to one label?
       Yes, with different source meanings
        -> HARMONIZATION COLLISION.
           RETAIN BOTH WITH REFINED LABELS/qualifiers.
           Example: e08 “released” vs e09 “accepted”.
       No
         Same label/time but disjoint distinguishing objects?
          Yes -> CONCURRENT DISTINCT EVENTS.
                  RETAIN BOTH UNCHANGED (order is a tie-break only).
                  Examples: I1 vs I2 picks; M1 vs M2 captures.
          No -> UNRESOLVED CANDIDATE.
                  QUARANTINE FOR REVIEW: retain both in the working
                  log, flag the pair, exclude neither from counts,
                  and run sensitivity analysis with/without merging.
```

Key safeguards: (i) `source_seq` is comparable only inside ERP, WMS, SCANNER, CARRIER or PSP respectively; (ii) `ingested_at` is technical arrival, never primary business evidence; (iii) a shared object such as O1 or V1 is necessary for many candidate screens but is not proof of identity — identity normally needs a distinguishing object (I, M), a source key, a document number, or reconciliation evidence; (iv) never union relations blindly if qualifiers/object roles conflict.

## 3. Timestamp-tie ordering rules

Apply rules in this priority order. A total order is produced only at the end, for tools that require one; the partial order is the semantic artefact and must be stored alongside it.

| Priority | Rule | Type | Application here |
|---|---|---|---|
| 1 | **Domain constraints** from known facts/process semantics | Semantic | e09 before e10; e12 before e13 (same Payment M1); detailed event before a summary generated from it (e06e07, capturese15) |
| 2 | **Lifecycle constraints on a shared distinguishing object** | Semantic | On V1: Issue Invoice  Authorize  Capture; on P1: Pick  Pack  Dispatch. Valid only when the same object and a genuine lifecycle exist — not merely because O1 is shared by everything |
| 3 | **Within-source sequence** (`source_seq` within one source only) | Semantic (weak–moderate) | CARRIER: e09 (1) < e10 (2); PSP: e12 (400) < e13 (401) < e14 (402) — but PSP sequence orders *recording*, so e13<e14 is not evidence that M1 was captured physically before M2 |
| 4 | **Source-specific semantics** (restored original labels) | Semantic | Warehouse release precedes carrier acceptance precedes handover; ERP summaries follow their triggering messages |
| 5 | **Ingestion time** | Merely deterministic, diagnostic only | Never primary (Fact 9). It may be inspected (e.g. e07 ingested 10:01 hints it is a later summary) but must not define business order; at most a last-resort tie-break, explicitly flagged |
| 6 | **Stable fallback**: canonical eid, then distinguishing object ID (I1<I2, M1<M2) | Merely deterministic | Guarantees reproducibility for genuinely concurrent events; encodes **no** precedence claim |

**Why microseconds must come last.** If `ocel_add_index_based_timedelta` (or any +1µs nudging) is applied *before* the semantic order is decided, whatever arbitrary order the sort happened to produce — file order, ingestion order, hash order — is frozen into timestamps. Downstream tools then read it as fact: a handover “1 µs before” acceptance, a summary “before” its own detail, false directly-follows edges, and invented performance durations. Synthetic timestamps are a *rendering* of an already-justified order, stored in a separate column; `original_timestamp` is never overwritten (Fact 10). A deterministic total order is a presentational device, **not** proof of true physical order; concurrent events (the two picks, the two captures) remain concurrent in the partial order even when listed sequentially.

**Intended orders (admissible alternatives noted):**

- **10:00, e03–e07:** `e03/e04-canonical (Pick, I1)` and `e05 (Pick, I2)` — mutually unordered, listed I1-then-I2 by fallback — then `e06 (Pack, detailed)`, then `e07 (Pack, ERP summary)`. Admissible alternative: e05 listed first. Inadmissible: Pack before either Pick on P1/I1/I2 lifecycle grounds.
- **10:15, e08–e10:** `e08 (warehouse release) < e09 (carrier acceptance) < e10 (handover)`. This is semantically forced by Facts 4–5 and CARRIER sequence, not by timestamps.
- **12:00, e11–e16 after conservative merges:** `e11/e16-canonical (Issue Invoice) < e12 (Authorize, M1) < e13 (Capture, M1)`; `e14 (Capture, M2)` unordered w.r.t. e12/e13 except after invoice issuance, listed after e13 by M1<M2 fallback; `e15 (ERP summary)` last, after both captures it summarises. Admissible alternative: e14 anywhere after the invoice and before e15.

## 4. Conservative cleaning pipeline

Minimum-change scenario:

1. **Freeze** `ocel_raw`; work only on deep copies. Add `original_timestamp`, `original_activity`, `source`, `source_event_key`, `source_seq`, `payload_hash` preservation columns before any transformation.
2. **Screen** candidate groups by (activity, timestamp) and by shared distinguishing objects; present groups for the decision tree — no global deduplication call.
3. **Merge only verified pairs**: e03/e04 and e11/e16, using field-level authority and full provenance (§6, §8). This is the only event-removing step.
4. **Refine, don’t remove, abstraction/harmonization cases**: e07  summary label, e15  summary label with `summarises` links, e08/e09  source-qualified Dispatch labels (original labels preserved).
5. **Retain all concurrency**: e05, e13, e14 untouched.
6. **Order** by §3: store `order_rank` and the partial-order constraints; only then render a synthetic strictly-increasing timestamp column for tools that need one.
7. **Validate** referential integrity and re-check counts against expectations.

**Expected retained count: 15 events** (17  2 verified merges), E2O relations 44  39 (merged pairs had identical object sets, so each merge removes only the duplicated relations). Nothing is silently deleted: both removed rows survive in the provenance map.

## 5. Aggressive alternatives

**Scenario B — Evidence-based semantic merging (14 events).** As conservative, plus merge e06/e07 into e06 (Scenario B in §2), on the argument that the ERP row adds no business transition. E2O: 37. *Most likely damage:* the ERP’s independent state observation disappears; analysts can no longer distinguish “WMS packed” from “ERP knew about packing”, message latency (10:0010:01 ingestion) is unauditable, and if the assumption is wrong for other orders, genuine two-step packing is systematically erased. e15 is still retained — merging a one-to-many summary into one capture would be arbitrary.

**Scenario C — Mechanically aggressive PM4Py merging (10 events).** Apply `ocel_merge_duplicates` over the whole log keyed on activity + timestamp (with object-overlap condition). It collapses: {e03,e04,e05}1, {e06,e07}1, {e08,e09}1, {e11,e16}1, {e13,e14,e15}1: **17  10 events**, E2O 44  28. *Damage:* the I2 pick vanishes as a distinct event (Item I2 appears packed without being picked); both partial payments and their summary fuse into one capture, so M1 and M2 lose separate lifecycles and amounts risk double-counting or loss; warehouse release and carrier acceptance fuse, deleting the handover boundary; all intra-timestamp concurrency is misread as duplication.

**Why `have_common_object=True` does not protect e13/e14.** The flag only requires *some* shared object. e13 and e14 share O1 and V1 — objects that sit on nearly every event in this log — while differing on the *distinguishing* object, Payment (M1 vs M2). A common-object test is an intersection test; duplicate identity requires agreement on the object that individuates the event type. For payment events that is M; for picks it is I. Any merge key must therefore include the discriminating object type, or exclude groups whose object sets differ on a discriminating type.

## 6. PM4Py-oriented Python implementation

```python
import copy
import pandas as pd
import pm4py

# ocel_raw: pm4py OCEL; events table carries eid, timestamp, activity,
# source, source_event_key, source_seq, ingested_at, payload_hash.
EV, REL, OBJ = "ocel:eid", "ocel:oid", "ocel:qualifier"  # adapt to version

def validate_ocel(ocel, label):
    ev, rel, obj = ocel.events, ocel.relations, ocel.objects
    assert ev[EV].is_unique, f"{label}: duplicate eids"
    assert set(rel[EV]) <= set(ev[EV]), f"{label}: orphan event refs"
    assert set(rel[REL]) <= set(obj[REL]), f"{label}: orphan object refs"
    assert ev["original_timestamp"].notna().all()
    print(f"{label}: {len(ev)} events, {len(rel)} E2O relations OK")

def preserve(ocel):
    ocel.events["original_timestamp"] = ocel.events["ocel:timestamp"]
    ocel.events["original_activity"]  = ocel.events["ocel:activity"]
    # source, source_event_key already present; never overwrite them.
    return ocel

def candidate_groups(ocel):
    """Pre-check ONLY: groups sharing activity+timestamp, for human/tree review."""
    ev = ocel.events
    rel = ocel.relations.groupby(EV)[REL].agg(lambda s: tuple(sorted(s)))
    ev = ev.assign(objects=ev[EV].map(rel))
    return {k: g for k, g in ev.groupby(["ocel:activity", "ocel:timestamp"])
            if len(g) > 1}

def merge_verified_pair(ocel, keep_eid, drop_eid, rule_id, field_authority):
    """
    Merge drop_eid into keep_eid for a VERIFIED same-event pair (§1).
    field_authority: {column: 'keep'|'drop'} per source-authority policy;
    default keeps canonical value and logs the discarded one.
    Relations are unioned; provenance row is appended to ocel._provenance
    (a side table carried alongside the OCEL, exported with it).
    """
    ev, rel = ocel.events, ocel.relations
    keep = ev.loc[ev[EV] == keep_eid].iloc[0]
    drop = ev.loc[ev[EV] == drop_eid].iloc[0]
    conflicts = {}
    for col, who in (field_authority or {}).items():
        if who == "drop":
            ev.loc[ev[EV] == keep_eid, col] = drop[col]
        elif pd.notna(drop.get(col)) and drop.get(col) != keep.get(col):
            conflicts[col] = drop[col]          # discarded, but recorded
    rel.loc[rel[EV] == drop_eid, EV] = keep_eid
    ocel.relations = rel.drop_duplicates(subset=[EV, REL, "ocel:qualifier"])
    ocel.events = ev[ev[EV] != drop_eid]
    ocel._provenance.append({
        "canonical_eid": keep_eid, "merged_source_eids": [keep_eid, drop_eid],
        "source_event_keys": [keep["source_event_key"], drop["source_event_key"]],
        "rule": rule_id, "fields_from_dropped": list((field_authority or {})),
        "discarded_conflicts": conflicts})
    return ocel

# ---------- Scenario A: conservative (deep copy; ocel_raw untouched) ----------
ocel_cons = preserve(copy.deepcopy(ocel_raw))
ocel_cons._provenance = []
for k, g in candidate_groups(ocel_cons).items():
    print("REVIEW GROUP", k, list(g[EV]))          # decision tree applied here

merge_verified_pair(ocel_cons, "e03", "e04", "VERIFIED-SAME-SCAN-v1",
                    field_authority={"location": "keep"})       # WMS enriched
merge_verified_pair(ocel_cons, "e11", "e16", "VERIFIED-SAME-INVOICE-V1-v1",
                    field_authority={"billing_ref": "drop"})    # BILLING authoritative
# Refined labels only; originals preserved in original_activity.
rename = {"e07": "Pack Package (ERP summary)",
          "e15": "Capture Payment (ERP summary)",
          "e08": "Dispatch Package [warehouse release]",
          "e09": "Dispatch Package [carrier acceptance]"}
m = ocel_cons.events[EV].isin(rename)
ocel_cons.events.loc[m, "ocel:activity"] = ocel_cons.events.loc[m, EV].map(rename)

# Deterministic order from the semantic rules of Section 3 (NOT ingestion).
rank = {"e01":1,"e02":2,"e03":3,"e05":4,"e06":5,"e07":6,"e08":7,"e09":8,
        "e10":9,"e11":10,"e12":11,"e13":12,"e14":13,"e15":14,"e17":15}
ocel_cons.events["order_rank"] = ocel_cons.events[EV].map(rank)
ocel_cons = pm4py.ocel_sort_by_additional_column(ocel_cons, "order_rank")
# Only AFTER the order above is fixed, render strictly increasing timestamps
# into a NEW column family; original_timestamp stays untouched.
ocel_cons = pm4py.ocel_add_index_based_timedelta(ocel_cons)
validate_ocel(ocel_cons, "conservative")

# ---------- Scenario A': exact-duplicate drop, justified narrow use ----------
# Justified ONLY on a copy pre-filtered to one candidate group already proven
# to be exact technical duplicates (same source key/hash/objects). No group
# in the current candidates qualifies, so this is shown but not executed on
# unverified data:
# ocel_exact = pm4py.ocel_drop_duplicates(copy.deepcopy(ocel_cons))

# ---------- Scenario B: evidence-based (adds e06/e07 merge) ----------
ocel_evid = copy.deepcopy(ocel_cons)
ocel_evid._provenance = list(ocel_cons._provenance)
merge_verified_pair(ocel_evid, "e06", "e07", "SUMMARY-DERIVED-v1",
                    field_authority={"erp_status": "drop"})
validate_ocel(ocel_evid, "evidence-based")

# ---------- Scenario C: aggressive library merge -- WARNING ----------
# WARNING: merges on activity+timestamp(+object overlap) across the WHOLE log.
# It WILL collapse e05 into the I1 pick and e13/e14/e15 into one capture
# (shared O1/V1 defeats have_common_object=True). Shown only to quantify
# semantic damage in the sensitivity analysis; never use as production output.
ocel_aggr = copy.deepcopy(ocel_raw)
ocel_aggr = pm4py.ocel_merge_duplicates(ocel_aggr)  # check kwargs per version
validate_ocel(ocel_aggr, "aggressive")

assert "e05" in set(ocel_cons.events[EV]) and "e14" in set(ocel_cons.events[EV])
```

Note: exact PM4Py signatures vary by version; inspect `help(pm4py.ocel_merge_duplicates)` before running Scenario C, and assert the candidate groups printed by `candidate_groups` match expectations before any library dedup call.

## 7. Sensitivity analysis

| Dataset | Events / E2O | Flattening & metric consequences |
|---|---|---|
| **Raw** | 17 / 44 | All duplicates counted. Order-flattened DFG shows inflated frequencies and self-loops (§ below). Payment flattening shows e13e14 as a sequence although they are concurrent partial captures. ET–OT weights double-count Pick–Item, Issue–Invoice, Dispatch–Delivery. |
| **Conservative** | 15 / 39 | Duplicate frequencies removed; concurrency and abstraction levels retained and labelled. Costs: summary events still appear as extra steps unless analysts filter `abstraction_level`; deterministic order still forces concurrent events into a sequence in flattened views. |
| **Evidence-based merge** | 14 / 37 | Additionally removes the Pack summary step; cleaner end-to-end DFG. Costs: ERP visibility/latency unmeasurable; risk generalises badly if some ERP pack rows are genuine second packs. |
| **Aggressive library merge** | 10 / 28 | Frequencies collapse; several real transitions disappear entirely. Item and Payment lifecycles are factually wrong (below). Useful only as a lower-bound stress test. |

Concrete edges/patterns whose interpretation changes:

1. **Pick Item  Pick Item (Order/P1 flattening):** raw and conservative show a self-loop — but in raw it is triply caused (e03,e04 duplicate + e05 distinct), while conservatively it correctly represents two distinct picks (I1, I2). Aggressive deletes the loop *and* the I2 pick.
2. **Pick Item  Pack Package:** raw frequency inflated by duplicate picks; conservative gives the true 2-picks1-pack pattern; aggressive suggests 1 pick  pack, so **Item-flattened DFG for I2 loses PickPack entirely** (I2 is packed, never picked).
3. **Pack Package  Pack Package:** raw = false rework loop; conservative with refined labels = detailsummary (filterable, not rework); evidence-based = gone; aggressive = gone but by the same mechanism that destroys real events.
4. **Dispatch Package  Dispatch Package / Dispatch  Handover:** raw collided labels create a loop and bury e10; refined labels yield ReleaseAcceptanceHandover, the true carrier chain; aggressive merges release+acceptance, shortening measured warehouse-to-carrier performance to zero.
5. **Issue Invoice  Issue Invoice (Invoice flattening):** raw shows rework on V1; conservative/merged shows a single issuance; this also corrects the **ET–OT weight Issue Invoice–Invoice from 2 to 1** and removes a spurious edge in the **OTG** (V1 no longer appears issued twice).
6. **Capture Payment  Capture Payment (Payment flattening):** raw/conservative show e13e14 sequence — must be read as concurrency of M1/M2, not rework; a per-Payment-object flattening (M1, M2 separately) shows no loop at all. Aggressive shows a single capture: total captured amount and the M2 lifecycle are wrong, and AuthorizeCapture for M1 may inherit M2’s merged relations.
7. **Authorize Payment  Capture Payment:** retained in all sane scenarios for M1; in the aggressive merge, unioned relations can attach M2 to authorization artefacts, fabricating an AuthorizeCapture path for M2 that no source recorded.
8. **Performance/lifecycle effects:** duplicate removal changes event frequencies in the **OC-DFG** (e.g. Pick Item node weight 32, Capture Payment 32 conservative) and every frequency-weighted edge; synthetic microseconds, if misapplied early, create near-zero durations between distinct events and negative-looking handovers; summary retention (e07, e15) lengthens Order case duration if treated as business steps, so lifecycle/performance reports must state whether summaries are included.

## 8. Audit trail and reversibility

One provenance record per canonical event (and per retained-but-refined event):

| Field | Content |
|---|---|
| `canonical_eid` | Surviving event ID (e.g. e03) |
| `source_eids[]`, `source_event_keys[]`, `sources[]` | All contributing rows (e03: W-77/ERP… i.e. WMS W-77 + SCANNER S-901) |
| `merge_rule` | Rule ID + version, e.g. `VERIFIED-SAME-SCAN-v1`, `SUMMARY-DERIVED-v1`, `LABEL-REFINE-v1`, `NO-MERGE` |
| `reviewer_or_rule_version` | Human reviewer or pipeline release |
| `original_activity` / `refined_activity` | Pre- and post-harmonization labels |
| `original_timestamp` / `adjusted_timestamp` | Source timestamp (immutable) and any synthetic tie-break timestamp, clearly flagged `synthetic=true` |
| `partial_order_constraints` | e.g. `e09<e10 (domain)`, `e13e14 (concurrent)` |
| `attributes_retained{field: source_eid}` | Field-level authority decisions (e11/e16) |
| `relations_retained{oid: source_eid}` | Which source contributed each E2O link; relations *not* unioned are listed too |
| `discarded_conflicts` | Values lost in merging (e.g. scanner payload variant) |
| `confidence`, `reason` | High/Medium/Low plus the fact(s) relied on (Known Facts 1–10, reconciliation report ID) |

**Reconstruction:** the raw view is the inverse map — expand each canonical event into its `source_eids`, restore `original_activity`/`original_timestamp`, drop synthetic columns, and re-attach relations per `relations_retained`. Because merges only union relations and overwrite fields listed in `attributes_retained` (with losers kept in `discarded_conflicts`), and because `ocel_raw` itself is never mutated, the raw OCEL is fully recoverable and every scenario is reproducible from `ocel_raw + provenance table + rule version`.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments** (e13/e14 via shared O1/V1). *Safeguard:* discriminating-object check per event type (PaymentM, PickI); forbid merges when candidate sets differ on a discriminating type.
2. **Converting abstraction-level updates into false rework** (e06e07, capturese15 read as loops). *Safeguard:* refined summary labels + `abstraction_level`/`derived_from` attributes; report DFGs with and without summaries.
3. **Ordering by ingestion time.** e07/e15 were ingested a minute later for technical reasons; ingestion order across systems reflects pipelines, not business time. *Safeguard:* ingestion used only diagnostically; order from §3 rules.
4. **Treating shared objects as proof of duplication.** O1 is on all 17 events. *Safeguard:* shared-object overlap is a screening criterion only; require key/document/reconciliation evidence.
5. **Unioning incompatible E2O relations.** Copying M1 onto e15, or items onto the ERP pack summary, fabricates relations. *Safeguard:* union only for verified same-event merges; summaries keep their native object sets; validate qualifier compatibility.
6. **Changing durations through synthetic microseconds.** Early timedelta injection invents precedence and near-zero/negative durations. *Safeguard:* synthetic timestamps only after semantic ordering, in separate columns, flagged synthetic.
7. **Losing source-authoritative attributes.** Picking ERP wholesale for e11/e16 discards BILLING-authoritative fields (and vice versa). *Safeguard:* field-level authority map; all losers logged in `discarded_conflicts`.
8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups.** Library calls have log-wide blast radius (Scenario C: 1710). *Safeguard:* mandatory `candidate_groups` pre-check, per-group decision-tree sign-off, deep copies, post-hoc validation, and count assertions (e05, e14 must survive conservative cleaning).
9. **Cross-source `source_seq` comparison.** PSP seq 400 vs ERP seq 40 says nothing cross-system. *Safeguard:* sequence used only within its source, and even then as recording order, not proof of physical precedence (e13 vs e14).
10. **Mistaking the rendered total order for truth.** Flattened DFGs will show e13e14 as a sequence. *Safeguard:* publish the partial order with the log; annotate deterministic-only adjacencies; never claim the total order proves physical order.
