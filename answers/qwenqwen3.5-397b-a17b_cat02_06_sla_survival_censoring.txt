# 1. SLA estimands and time definitions

**Time Origin:** The `Submit` event marks $t=0$ for all cases.
**Time Scale:** Elapsed hours (`duration_or_age_h`).
**Horizon:** 72 hours (SLA threshold).
**Event of Interest:** `Resolve` (Operational Success).

**Censoring and Competing Risks:**
- **Right Censoring:** Cases with `observed_status` = `open` are censored at `duration_or_age_h` (the observation cutoff age). We know they survived at least this long without resolving.
- **Competing Events:** `Withdraw` and `Reject` are terminal states that preclude `Resolve`. They remove the case from the risk set for resolution.
- **Ambiguous Event:** `Transfer` removes the case from the internal system. Its treatment defines the sensitivity scenarios (see Section 2).

**Proposed Estimands:**

1.  **Cumulative Incidence of Resolution (CIF) at 72h:**
    -   *Definition:* The probability that a case is resolved within 72 hours, acknowledging that withdrawal/rejection/transfer may occur first.
    -   *Formula:* $CIF_{resolve}(72) = \int_0^{72} S(t^-) h_{resolve}(t) dt$.
    -   *Operational Decision:* **SLA Compliance Reporting.** This tells management the actual percentage of cases successfully closed within SLA, accounting for cases that "disappeared" via other outcomes.

2.  **Survival Probability of Non-Resolution at 72h:**
    -   *Definition:* The probability that a case has *not* reached a terminal resolved state by 72 hours (includes open, withdrawn, rejected, transferred).
    -   *Formula:* $S(72) = P(T_{terminal} > 72 \cup \text{Terminal} \neq \text{Resolve})$.
    -   *Operational Decision:* **Workload Forecasting.** This estimates the volume of cases potentially requiring attention or escalation review at the 72h mark, regardless of final outcome.

**Case Contributions:**
-   **S03 (Resolved, 76h):** Contributes to the risk set until 76h. Counts as a **breach** for CIF (event > 72).
-   **S09 (Open, 92h):** Contributes to the risk set until 92h (censored). Counts as **not resolved** at 72h.
-   **S06 (Withdrawn, 27h):** Contributes to risk set until 27h. Removed as a **competing event**. Does not count as resolved.
-   **S08 (Transferred, 68h):** Contribution depends on the Transfer Assumption (see Section 2). If treated as competing, it removes risk at 68h. If treated as censoring, it removes risk at 68h. If treated as breach, it counts as failure.

# 3. Why naive completed-case analysis is biased

A naive analysis considers only cases with `observed_status` = `resolved`. This introduces severe bias:

1.  **Survivor Bias (Denominator Error):**
    -   *Example:* If we calculate average resolution time using only S01-S04, S07, S13, S16-S20, S27-S28, we ignore S09 (Open, 92h) and S11 (Open, 81h).
    -   *Impact:* We underestimate the tail risk. S09 and S11 are likely breaches, but excluding them makes the process look faster.
2.  **Informative Censoring (Open Cases):**
    -   *Example:* S26 (Open, 104h, `last_event_gap_h`=72). This case has been stagnant for 72 hours. It is highly unlikely to resolve soon. Treating it as standard right-censoring (assuming it behaves like a resolved case eventually) overestimates the resolution probability.
3.  **Competing Risks Ignored:**
    -   *Example:* S05 (Rejected, 9h) and S12 (Withdrawn, 15h). These cases left the system quickly. A naive "time-to-event" analysis might exclude them, inflating the average duration of the remaining cases (length-biased sampling).
4.  **Cohort Imbalance:**
    -   *Observation:* Cohort B (S16+) has `AutoCheck` earlier in the prefix than Cohort A.
    -   *Bias:* If Cohort B resolves faster, mixing them without stratification hides the policy effect. S18 (B, P1, 12h) resolved much faster than S04 (A, P1, 29h).

# 7. Operational interpretation

**From Survival Outputs to Actions:**
-   **Alerting:** Do not alert on *all* open cases. Alert on cases where the **conditional hazard** exceeds a threshold (e.g., "Probability of breach in next 24h > 50%"). Use the Landmark model (Section 4) to score open cases daily.
-   **Workload:** Use the CIF curve to predict how many cases will resolve naturally vs. how many will hit 72h open. This informs staffing for the "SLA Breach Review" queue.
-   **Governance:** Report SLA Compliance as $CIF_{resolve}(72)$, not "Average Resolution Time".

**Fairness and Calibration:**
-   **Priority Check:** Compare $CIF_{resolve}(72)$ for P1 vs. P3. If P1 breach rate > P3, the escalation policy is failing.
-   **Cohort Check:** If Cohort B has significantly better SLA, investigate if `AutoCheck` is the cause or if case complexity differs.
-   **Calibration:** Plot predicted breach probability vs. actual breach outcome (for resolved/open cases) to ensure the model isn't overconfident.

# --- 2. Encode Estimands & Transfer Scenarios ---
SLA_LIMIT = 72

def encode_status(row, transfer_scenario='competing'):
    """
    Returns (event_indicator, competing_code, time)
    event_indicator: 1 if Resolved, 0 otherwise
    competing_code: 0=None, 1=Withdraw, 2=Reject, 3=Transfer, 4=Open(Censor)
    """
    t = row['duration_or_age_h']
    status = row['observed_status']
    
    if status == 'resolved':
        return 1, 0, t
    elif status == 'open':
        return 0, 4, t # Censored
    elif status == 'withdrawn':
        return 0, 1, t
    elif status == 'rejected':
        return 0, 2, t
    elif status == 'transferred':
        if transfer_scenario == 'censored':
            return 0, 4, t
        elif transfer_scenario == 'competing':
            return 0, 3, t
        elif transfer_scenario == 'breach':
            # Treat as failure if not resolved
            return 0, 3, t 
    return 0, 0, t

    df[f'compete_{scen}'] = df.apply(lambda r: encode_status(r, scen)[1], axis=1)

# 9. Limitations and additional data

**Critical Data Gaps:**
1.  **Exact Event Timestamps:** We only have `duration_or_age_h` (total elapsed time). We cannot reconstruct the exact time of `Escalate` or `Rework`. This prevents precise time-dependent covariate modeling (e.g., Cox model with time-varying coefficients).
2.  **Transfer Outcomes:** We do not know if `transferred` cases were eventually resolved externally. This makes the "Competing Risk" assumption necessary but unverified.
3.  **Cutoff Date:** We know the age at cutoff, but not the calendar date. We cannot control for seasonal workload spikes or policy rollout dates (Cohort B start time).
4.  **Assignment Mechanism:** Cohort assignment was "not randomized." Differences between A and B may be due to case complexity rather than the policy change.
5.  **Workload Data:** No data on queue size or agent availability. High `last_event_gap_h` might be due to workload, not case difficulty.

**Recommendations for Data Collection:**
-   Log exact timestamps for every activity event.
-   Track external resolution status for transferred cases (feedback loop).
-   Record reason codes for `Withdraw` and `Reject` to distinguish customer-initiated vs. system-initiated termination.
-   Capture agent ID to control for performer variance in survival models.
