## 1. Model scope and state variables

### Purpose and boundary

The digital twin should be a **discrete-event simulation (DES)** with a process-mining-informed routing layer. Its purpose is to estimate the operational and distributional consequences of interventions D1-D10 under realistic demand variation, staffing calendars, applicant delays, rework, and dependencies among cases.

The twin should not be a pure historical replay. Historical event data calibrates its parameters and validates its baseline behavior, but the simulation generates new arrivals and allows counterfactual policies.

The modeled boundary begins at:

- Applicant submission through the portal, including optional pre-submission activity for D1,

and ends at:

- Permit issued,
- Application rejected, or
- Application closed/withdrawn if that outcome is observed or added as a censored outcome.

The model should include municipal work, applicant-driven delays, third-party/public-notice delays, and operational resource constraints. It should exclude detailed construction execution after permit issuance.

### Modeling level of detail

Use a **hybrid case-centric and network-centric design**:

1. **Case level:** each permit application follows a conditional process path derived from the process tree and observed variants.
2. **Resource level:** municipal activities compete for finite staff pools subject to calendars, skills, vacations/holidays, reserved capacity, and policy-specific priorities.
3. **Cross-case level:** cases can be linked by architect, district, time window, objection cluster, and inspection route group.
4. **Calendar level:** activities advance in working time where appropriate; applicant and public-notice delays progress in elapsed calendar time, subject to policy and statutory rules.

### Entities

| Entity | Key attributes | Main role |
|---|---|---|
| Permit case | case ID, type, district, architect, value, requirements, risk features, process state | Primary simulation entity |
| Applicant/architect | architect ID, submission behavior, document quality propensity, response-time profile, appointment use | Drives correlated arrivals and missing-document response |
| Municipal resource | resource ID/pool, skill, calendar, availability, capacity, utilization | Executes municipal activities |
| Resource pool | clerks, planners, fire, environmental, inspectors, legal, system | Queueing and assignment unit |
| Inspection bundle | district, geographic zone, candidate cases, ready times, route size | Supports batching and travel-time reduction |
| Public-notice cluster | district/neighborhood, notice start dates, objection intensity latent variable | Represents correlated objections despite missing events |
| Calendar event | holidays, council meeting weeks, peak-month staffing change | Alters service availability and statutory timing |
| Policy configuration | D1-D10 switches and parameter values | Defines counterfactual scenarios |

### Process state and routing logic

The simulation should implement the nominal model as a constrained routing model, rather than treating every mined variant as a fixed script:

1. Submit application.
2. Completeness check.
3. Optional missing-document loop:
   - Request missing documents.
   - Applicant response delay.
   - Receive missing documents.
   - Return to completeness check.
4. Planning review.
5. Optional and potentially parallel:
   - Fire-safety review.
   - Environmental review.
6. Optional public-notice period.
7. Inspection scheduling and site inspection, with possible rework.
8. Decision drafting after all applicable predecessor work is complete.
9. Optional legal check or policy-specific legal pre-check.
10. Issue permit or reject application.
11. Optional appeal/rework loop where observed and within scope.

The process tree should guide allowed behavior, while empirical routing probabilities should determine choices and loops conditional on case attributes and scenario conditions.

### Resources, queues, and calendars

Queues should be modeled separately by activity and skill:

| Queue/activity | Capacity and skill rule | Calendar and special behavior |
|---|---|---|
| Completeness check | Clerk pool; one Monday clerk reserved for portal support | Monday-Friday, 08:00-16:00 |
| Planning review | Planner pool; two planners restricted to Simple renovation | Monday-Friday, 09:00-17:00 |
| Fire-safety review | Fire reviewer pool | Tuesday-Thursday only |
| Environmental review | Environmental pool with 60% effective permit capacity | Monday-Friday; non-permit allocation |
| Inspection scheduling | Scheduler resource/pool | Working-day calendar |
| Site inspection | Inspector pool and route/bundle assignment | Tuesday-Friday field visits |
| Decision drafting | Planner pool or designated drafting subset | Working-day calendar |
| Legal check | Legal officer pool | No ordinary work during council-meeting weeks |
| System activities | Unlimited | Always available |
| Applicant response | External actor | Calendar-time heavy-tailed delay |
| Public notice | External/statutory process | Fixed minimum plus objection extension |

The model should support:

- FIFO as baseline discipline,
- priority disciplines for D6,
- batch-release rules for D3,
- appointment-controlled arrivals for D7,
- service eligibility by resource skill and case type,
- preemption only where operationally credible,
- explicit holiday and council-meeting interruption calendars.

### Cross-case dependencies

The twin must explicitly model the following dependencies.

#### Architect-related submission bursts

Top architects generate correlated arrivals. Rather than independent Poisson arrivals only, model architect-specific arrival processes:

- Background arrivals by case type and district.
- Additional cluster arrivals for high-volume architects.
- Within-cluster correlation in document quality, case type, and submission day.
- Optional appointment-slot behavior under D7.

A practical structure is a **non-homogeneous Poisson process plus cluster process**, such as a Hawkes-like or compound-Poisson burst component for major architects.

#### Inspection bundling by district/geography

Inspection-ready cases in the same district or geographic zone can be bundled. Bundling reduces per-case travel time but may hold early-ready cases until enough compatible work exists.

State variables include:

```text
district
geographic_zone
inspection_ready_time
bundle_open_time
bundle_size
bundle_release_rule
route_travel_time
maximum_waiting_before_forced_release
```

#### Neighborhood/public-notice correlation

Objection events are missing and must not be simulated as directly observed historical events. Instead, introduce a latent neighborhood-period factor:

```text
neighborhood_objection_pressure[district, month]
```

This factor can raise the probability and duration of public-notice extensions for related cases. It may be estimated from unusually long notice durations after controlling for case type and notice requirement.

#### Shared resource queues

All cases affect one another through resource pools and calendar capacity. In particular:

- Commercial and Complex variance cases compete for legal capacity.
- Environmental and legal workloads may interact indirectly through decision drafting prerequisites.
- Monday submission bursts create clerk and planner queue spikes.
- Peak demand affects all downstream queues with lagged effects.

## 2. Parameter-estimation plan

### Data preparation and PM4Py role

PM4Py should be used for:

- Event-log formatting and validation.
- Variant discovery.
- Directly-follows graph (DFG) discovery.
- Performance DFG analysis.
- Process-tree parsing where syntax is supported.
- Conformance checking between the observed log and the reference process model.
- Identifying deviations, loops, missing-document behavior, and rare variants.
- Producing process-mining features for simulation calibration.

PM4Py is not the simulation engine. The simulation should be built separately, for example with SimPy, salabim, custom DES infrastructure, or an event-scheduling framework. PM4Py supplies empirical structure and calibration evidence.

### Event-log reconstruction

Before estimating parameters:

1. Standardize timestamps and time zones.
2. Deduplicate repeated technical events where appropriate.
3. Sort by case ID and timestamp.
4. distinguish:
   - system events,
   - human municipal activities,
   - applicant events,
   - public/third-party events.
5. identify incomplete/censored cases at the start and end of the observation window.
6. retain case-level attributes through all events.
7. create derived fields:
   - day of week,
   - week/month/season,
   - holiday proximity,
   - council-week indicator,
   - district,
   - architect group,
   - type/value bands,
   - observed route,
   - rework count.

### Arrival-process estimation

Estimate arrivals from `Submit application` timestamps, not all event timestamps.

#### Baseline arrival model

Fit a non-stationary arrival model by:

- hour of day,
- weekday,
- month/season,
- case type,
- district,
- architect segment,
- public holiday proximity.

A suitable model is a negative-binomial or Poisson regression for daily arrivals:

\[
N_{d,t} \sim \text{NegativeBinomial}(\lambda_{d,t}, \phi)
\]

with:

\[
\log(\lambda_{d,t}) =
\beta_0 +
\beta_{\text{weekday}} +
\beta_{\text{month}} +
\beta_{\text{district}} +
\beta_{\text{case type}} +
\beta_{\text{peak}} +
\beta_{\text{holiday}}.
\]

The 1.7x March-May and September-November effect and 2.2x Monday-to-Wednesday effect should be estimated from the full log and treated as starting evidence, not fixed universal constants.

#### Architect bursts

Estimate high-volume architect behavior separately:

- Identify the top 20 architects.
- Measure weekly submission counts, autocorrelation, and same-week multi-case cluster size.
- Estimate:
  - probability of an architect-driven burst,
  - burst size distribution,
  - within-burst time dispersion,
  - correlation of district/type/value among cases in a burst.

Use a compound-Poisson cluster process or an empirical weekly bootstrap of architect-specific submission bundles.

### Service-time estimation

Service times should not be inferred from inter-event elapsed time when start timestamps are missing. The elapsed interval between two events usually contains both waiting and service.

Use three evidence tiers:

1. **Directly observed start-complete pairs:** estimate service times directly for activities with reliable lifecycle timestamps.
2. **Resource-contiguous inference:** where a resource’s consecutive events plausibly imply work intervals, infer bounded service-time samples with caution.
3. **External/elicited calibration:** use staffing records, time studies, and expert estimates for activities with completion-only timestamps.

For each activity, fit service time conditional on relevant covariates:

- case type,
- district,
- value band,
- required reviews,
- resource pool,
- calendar day,
- bundle size for inspections,
- rework iteration,
- environmental/public-notice risk category.

Candidate distributions:

- lognormal,
- gamma,
- Weibull,
- log-skew-normal,
- empirical bootstrap distributions,
- mixture distributions for heterogeneous tasks.

Use distribution selection based on out-of-sample likelihood, quantile fit, and operational plausibility rather than only AIC/BIC.

Examples:

- Completeness check: lognormal or gamma, with Monday-dependent queue rather than Monday-dependent service unless evidence supports service variation.
- Planning review: mixture by case type and district.
- Site inspection: service component plus district/bundle travel component.
- Legal check: mixture or calendar-conditioned service/availability model due to meeting-week interruptions.

### Waiting-time estimation

Waiting time should be modeled through resource queues in the simulation, not independently sampled for every municipal task. Otherwise the model double-counts congestion and cannot respond credibly to staffing interventions.

For activities with start timestamps:

\[
\text{waiting time} = \text{start timestamp} - \text{preceding prerequisite completion}.
\]

For activities with completion-only timestamps:

- derive an interval-censored waiting/service decomposition;
- use service-time distributions from direct observations or expert data;
- estimate likely queue-entry time from predecessor completion;
- calibrate simulated total activity lead time, queue length, utilization, and case duration jointly.

For applicant response and public notice, elapsed duration is a process delay and may legitimately be sampled directly because it is not produced by municipal resource queues.

### Branching-probability estimation

Estimate conditional routing probabilities with logistic regression, Bayesian hierarchical models, or empirical stratification.

Examples:

| Routing decision | Candidate predictors |
|---|---|
| Missing documents required | case type, architect, value, district, submission channel, D1 policy |
| Fire review needed | `requires_fire`, case type, inferred area/risk proxy |
| Environmental review needed | `requires_environment`, district sensitivity proxy, type/value |
| Public notice needed | Complex variance, New residential, district, value |
| Legal check needed | case type, planning outcome/risk, policy configuration |
| Inspection needed | type, district, application value, low-risk flags, D2 |
| Reject versus issue | case type, review outcomes/proxies, rework count |
| Rework | stage, case type, document quality, inspector no-show, objection pressure |

Use partially pooled estimates so sparse groups, particularly Complex variance, borrow strength while retaining group-level differences.

### Rework estimation

Rework should be stage-specific, not represented by one global loop probability.

Estimate:

- probability of a missing-document loop after completeness check;
- number of completeness loops;
- probability of inspection rework;
- probability of legal/planning rework;
- appeal/rework probability for applicable decisions;
- conditional rework probability after prior rework.

Potential model:

\[
P(\text{rework at stage } s) =
\operatorname{logit}^{-1}(X\beta_s + u_{\text{district}} + v_{\text{architect}})
\]

where random effects capture recurring document-quality or district-specific conditions.

Unstructured rework text should support exploratory clustering only. It should not be treated as perfectly coded ground truth.

### Public-notice and objection proxy estimation

Because objections are not explicitly captured:

1. Identify cases requiring public notice.
2. Separate the statutory minimum duration from excess duration.
3. Define an excess-notice indicator, for example:

\[
I(\text{notice duration} > 14 \text{ days} + \epsilon)
\]

4. Model excess probability and excess duration conditional on:
   - case type,
   - district,
   - month,
   - project value,
   - neighborhood latent factor,
   - historical related notices in a local time window.

This creates an inferred objection-extension model, not a claim that long durations perfectly identify objections.

### Resource-calendar estimation

Start from HR-derived calendars, then calibrate effective capacity using log evidence:

- estimate observed event completions by resource/day/hour;
- compare with nominal working windows;
- estimate effective productive fraction by pool;
- represent non-permit duties as scheduled capacity reductions;
- include public holidays and council meeting weeks explicitly.

Examples:

- Environmental reviewers: 3 FTE nominal, 60% permit availability.
- Fire reviewers: 2 FTE equivalent only Tuesday-Thursday.
- Legal officers: unavailable in council-meeting weeks except a configurable urgent-case fraction.

### Dependency estimation

Estimate the effect of dependencies using grouped historical patterns.

#### Architect dependency

Measure correlations among same-architect cases submitted within 7 days:

- same district probability,
- same case type probability,
- missing-document rate correlation,
- shared queue and completion-time correlation.

#### Inspection dependency

Estimate:

- travel-time differences by district,
- route/day throughput,
- time between inspection scheduling and inspection,
- same-district same-day inspection counts,
- whether high same-day district density corresponds to lower average travel time.

The D3 policy should use these estimates to specify bundle travel savings and maximum waiting cost.

#### Neighborhood dependency

Use district-month or neighborhood-month random effects on public-notice excess duration. If neighborhood identifiers are unavailable, treat district-month effects as a coarse proxy and report the limitation.

## 3. Assumptions

### Arrivals

- Applications arrive through a non-stationary process with weekday, seasonal, case-type, district, and architect effects.
- Monday submissions remain substantially higher than midweek submissions unless D7 is active.
- High-volume architects produce correlated bursts rather than independent individual submissions.
- The simulation generates arrivals, rather than reusing the exact historical cases, except in a separate replay-validation mode.
- Extreme external events, such as a sudden legislative change or major disaster, are not assumed unless represented in stress scenarios.

### Service times

- Municipal service time is distinct from queue waiting time.
- Service-time distributions are estimated separately by activity and relevant case attributes where data support it.
- When only completion timestamps exist, service time is partially inferred and carries uncertainty.
- Site inspection duration includes an on-site component and a travel component.
- Public notice and applicant response are not municipal service times.
- System tasks have near-zero service time but can still have business-rule delays if applicable.

### Routing

- The process tree defines permissible paths, but empirical routing models determine which optional branches occur.
- Fire, environmental, and public-notice requirements depend on observed flags plus estimated latent eligibility where required information is missing.
- Decision drafting waits for all applicable reviews and inspections.
- D2 changes inspection routing only for Simple renovation cases that meet the specified value and low-risk eligibility criteria.
- Legal pre-check under D5 is modeled as an earlier legal activity that may identify issues before decision drafting; it must not create duplicate legal workload without an explicit redesign rule.
- Rare emergency decisions remain outside the principal calibrated process unless separately modeled as a sensitivity scenario.

### Resources/calendars

- Resources are finite, skill-constrained, and unavailable outside their calendars.
- Calendar time and working time are distinct.
- Council-meeting weeks remove ordinary legal capacity but allow a small urgent-case pathway if stakeholders confirm it exists.
- Staff absenteeism is either represented through average effective capacity or included in stress scenarios.
- Temporary inspector capacity under D4 applies only during defined peak months and follows field-visit calendars.
- Two planners remain dedicated to Simple renovation unless a staffing policy explicitly changes that rule.

### Rework

- Rework is stage-specific and probabilistic.
- Rework probability can depend on case type, document quality, architect, district, prior rework, and inspection outcomes.
- Rework reasons extracted from unstructured text are uncertain and should not be overinterpreted.
- Appeals are modeled only where the historical log and policy scope support them; otherwise they are represented as a calibrated post-decision rework probability for relevant case types.

### Applicant/third-party response

- Applicant document-response time is a separate heavy-tailed external delay.
- Applicant response may vary by architect segment and case type.
- D1 reduces missing-document incidence and/or the number of loops, but may shift effort before formal submission.
- The pre-submission effort cost is tracked separately and should not be hidden by measuring only post-submission permit duration.
- Public-notice extension is driven by a latent objection process inferred from duration patterns, not by observed objection events.
- Statutory public-notice minimum duration is enforced regardless of municipal staffing.

### Cross-case dependencies

- Architect-associated cases can arrive in bursts and share latent document-quality or coordination effects.
- Inspection bundles are formed among geographically compatible, inspection-ready cases.
- Bundling may reduce route travel time but delay early-ready cases; a maximum hold time prevents indefinite waiting.
- District/neighborhood-period latent factors induce correlated public-notice extensions.
- Shared resource queues create endogenous interactions across all cases.

### Non-stationary demand

- Seasonal and weekday demand patterns continue approximately as observed in the calibration window.
- Peak demand increases both arrivals and downstream congestion with lag.
- Peak-month inspector staffing under D4 is evaluated against explicitly modeled peak-month demand, not annual-average demand.
- Stress scenarios test plausible deviations from historical seasonality.

### Missing data

- Missing start timestamps imply uncertainty in service/wait splits.
- Missing objection events are represented as latent uncertainty, not observed labels.
- Incomplete building area and environmental sensitivity data require probabilistic eligibility models.
- HR calendars are treated as imperfect priors and calibrated to observed activity patterns.
- Flattened case logs understate some cross-case relationships; architect and district grouping are minimum viable proxies.
- Removed emergency decisions create selection bias in observed tail behavior; this is disclosed and optionally tested through a rare-urgent-case sensitivity scenario.

## 4. Experiment matrix

All experiments should use the same calibrated baseline arrival model, process logic, case-mix distribution, calendar horizon, random-number streams, and outcome metrics unless a scenario explicitly changes them.

| ID | Experiment | Factors / levels | Expected trade-offs and hypotheses |
|---|---|---|---|
| B0 | Calibrated baseline | Current routing, staffing, calendars, no intervention | Reference for all comparisons; should reproduce observed variants, lead times, queue behavior, and utilization within validation tolerances |
| D1 | Pre-submission document checker | Reduction in missing-doc probability: low/central/high calibrated effect; applicant pre-submission effort added | Fewer completeness loops and lower clerk/planner congestion; possible longer pre-submission elapsed time and unequal benefit for digitally less capable applicants |
| D2 | Low-risk Simple renovation no-inspection rule | Eligibility: value < EUR 50k and no prior violations; strict versus uncertain eligibility treatment | Reduces inspection queue and Simple duration; requires monitoring of risk/compliance proxy and equity if prior-violation data are incomplete |
| D3 | District-batched inspection scheduling | Bundle target size 2/3/4; maximum hold 1/3/5 business days | Lower travel and inspector utilization pressure; may worsen waiting for first-ready cases, especially low-volume districts |
| D4 | Temporary peak-month inspector | Add 1 inspector during Mar-May and Sep-Nov only; full versus partial availability | Reduces peak inspection backlog and tail delay; may yield low off-peak benefit and require scheduler/vehicle capacity |
| D5 | Parallel legal pre-check | Commercial and Complex only; start after Planning or after all technical reviews; legal capacity unchanged | Earlier defect detection and less late rework; may increase legal WIP, create queue displacement, or duplicate work if redesign is poor |
| D6 | Aging-case planner reservation | Reserve 0.5, 1.0, or 1.5 planner FTE-equivalent daily; aging thresholds 30/45/60 days | Reduces long-tail delay and backlog aging; may increase median duration for newer or Simple cases |
| D7 | Architect appointment slots | Voluntary/mandatory for top 20 architects; slot quotas and incentives | Smooths Monday arrival spikes and clerk queues; may shift burden to applicants and create strategic resubmission behavior |
| D8 | Environmental-review triage | Low/medium/high risk classes; fast-track fraction; false-negative/false-positive sensitivity | Improves low-risk flow and environmental queue performance; risk of inappropriate fast tracking and extra rework for misclassified cases |
| D9 | Public-notice objection early warning | Detection sensitivity 40/60/80%; earlier outreach lead time; extension reduction conditional on true objection | Can reduce long notice extensions and late rework; may add staff work and cannot eliminate statutory minimum periods |
| D10 | Combined operational policy | D1 + D2 + D3 + D4 | Potentially large system benefit through lower inflow rework and inspection load; interaction effects may shift bottleneck to planning/legal |
| C1 | D1 + D4 | Document quality improvement plus peak inspection capacity | Tests whether upstream rework reduction reduces need for temporary field capacity |
| C2 | D2 + D3 + D4 | Inspection-focused package | Tests route efficiency, inspection avoidance, and peak capacity interaction |
| C3 | D5 + D6 + D8 | Review/legal flow package | Tests whether faster technical triage simply shifts congestion to legal/planning |
| C4 | D1 + D5 + D9 | Upstream quality plus long-tail reduction package | Tests impact on Complex variance and objection-sensitive cases |
| S1 | Peak-demand stress | Peak arrival multiplier: 2.0x and 2.3x instead of observed 1.7x | Tests resilience under stronger seasonal surge; likely exposes inspection, planning, and legal backlog |
| S2 | Staff-absence stress | 10%, 20%, 30% effective capacity loss in planners/inspectors/legal; random or clustered absences | Tests whether interventions remain beneficial under operational disruption |
| S3 | Objection shock | Public-notice extension probability and extension duration increased, correlated by district | Tests D9 and system resilience to neighborhood opposition |
| S4 | Large-architect burst stress | Top-20 architect burst frequency/size increased by 25% and 50% | Tests D7, D1, and queue robustness under correlated arrivals |
| S5 | Council-calendar disruption | Additional council meeting week or extended legal shutdown | Tests D5/D6 and legal backlog recovery |
| S6 | Data/eligibility uncertainty | Higher uncertainty in low-risk eligibility, environmental sensitivity, and service-time split | Tests policy robustness to incomplete information rather than only point estimates |

For each intervention, report both:

1. **absolute outcomes** under the intervention, and  
2. **incremental outcomes** relative to B0 using paired random-number streams.

## 5. Warm-up, replications, and uncertainty treatment

### Simulation horizon

Use a sufficiently long horizon to capture seasonal cycles and delayed downstream effects.

Recommended primary design:

- **Warm-up:** 6 months.
- **Measurement period:** 24 months.
- **Total simulated run:** 30 months.
- **Calendar replication:** preserve weekday, holiday, council-week, and seasonal patterns across the horizon.

A two-year measurement period ensures both peak seasons are represented twice. For final policy comparisons, also run a 36-month measurement sensitivity analysis if computationally feasible.

### Warm-up approach

The permit system may begin with a non-empty backlog. Use two complementary approaches:

1. **Historical initialization:** initialize queues and active cases from a real historical cut date, including age and process stage where reconstructable.
2. **Warm-up simulation:** run the model before the measurement window and discard warm-up outcomes.

Because demand is seasonal, a simple “empty system then warm up” can bias results. Prefer initialization at the same month across replications or use a cyclic warm-up spanning a full seasonal year.

Assess warm-up adequacy using:

- total WIP,
- queue lengths by pool,
- age of open cases,
- resource utilization,
- monthly completion counts.

### Replications

Use at least:

- **100 replications per baseline/intervention comparison** for primary reporting.
- **200+ replications** for close decisions, tail-SLA metrics, or rare Complex variance outcomes.
- More replications for heavy-tail outcomes or stress scenarios where variance is high.

Use **common random numbers** for paired policy comparisons:

- same arrival streams,
- same case attributes,
- same latent objection draws,
- same applicant-response draws where policy does not logically alter them,
- same service-time latent draws where applicable.

This improves precision of estimated differences.

### Random seeds

Use a documented seed scheme, for example:

```text
base_seed = 20260101
replication_seed = base_seed + replication_number
scenario_seed = hash((scenario_id, replication_number))
```

Separate random-number streams by mechanism:

- arrivals,
- architect bursts,
- routing,
- service times,
- applicant delays,
- public-notice extensions,
- rework,
- resource absences,
- inspection travel/bundling.

This makes experiments reproducible and helps isolate policy effects.

### Uncertainty representation

Represent uncertainty at two levels.

#### Stochastic uncertainty

This is natural simulation variability from:

- arrivals,
- queue interactions,
- service durations,
- applicant response,
- objections,
- rework,
- staff availability.

Estimate with replication distributions.

#### Parameter uncertainty

Many fitted parameters are uncertain, especially where event starts or objection labels are missing. Use one of:

- bootstrap parameter sets from historical cases,
- Bayesian posterior draws,
- probabilistic sensitivity distributions around fitted values.

For each policy, run an outer loop over parameter draws and an inner loop over DES replications. This yields uncertainty that reflects both historical estimation and operational randomness.

### Confidence and credible intervals

Report:

- mean difference with 95% confidence interval for approximately symmetric metrics;
- bootstrap confidence interval for medians and percentiles;
- paired confidence intervals for intervention-minus-baseline differences;
- probability of meeting a target, such as:

\[
P(\text{SLA compliance} \geq 90\%)
\]

under parameter and simulation uncertainty.

For Bayesian calibration components, report credible intervals and posterior probabilities rather than relabeling them as frequentist confidence intervals.

### Heavy-tailed duration treatment

Heavy tails are central for applicant response, public notice, Complex variance, rework, and some legal/environmental delays.

Use:

- lognormal, Weibull, log-logistic, Pareto-tail, or mixture distributions where justified;
- capped tail models only if there is a real operational cap;
- empirical or semi-parametric bootstrap for sparse rare variants;
- survival-analysis treatment for right-censored historical cases;
- robust summaries in addition to means:
  - median,
  - p75,
  - p90,
  - p95,
  - p99 where sample size supports it,
  - conditional tail expectation.

Do not use only average duration; it is unstable and hides the policy impact on long-delay cases.

### Sensitivity analysis

Conduct one-way and global sensitivity analyses on at least:

- D1 document-checker effectiveness;
- D2 low-risk eligibility misclassification;
- D3 bundle size and maximum waiting;
- D4 temporary inspector effective availability;
- D5 legal pre-check workload duplication;
- D6 aging threshold and reserved capacity;
- D7 appointment adoption rate;
- D8 triage accuracy;
- D9 objection-warning sensitivity;
- service-time distribution tail parameters;
- applicant response tail parameters;
- public-notice extension parameters;
- peak-demand multiplier;
- legal calendar shutdown duration.

Use tornado plots for local sensitivity and Latin hypercube or Sobol-style sampling for global sensitivity where feasible.

## 6. Validation strategy

Validation should proceed in stages. A good fit on total average lead time alone is insufficient.

### Face validation

Conduct structured workshops with:

- clerks,
- planners,
- fire and environmental reviewers,
- inspectors and schedulers,
- legal officers,
- policy owners,
- IT/process-mining analysts,
- applicant-facing staff.

Validate:

- process logic and prerequisites,
- routing rules,
- resource pools and skills,
- calendar rules,
- plausibility of batching,
- rework triggers,
- policy implementation details,
- whether queues behave as practitioners recognize.

Use animated case traces and queue dashboards to expose implausible assumptions.

### Event-log replay validation

Run a replay mode using historical submission timestamps and observed/static case attributes where possible.

Compare simulated and observed:

- activity sequences,
- transition frequencies,
- rework-loop counts,
- case completion timing,
- backlog trajectory,
- completion counts by week/month.

Replay validation does not require the simulator to reproduce each individual case exactly. It should reproduce aggregate and segment-level behavior conditional on the historical arrival stream.

### Distributional validation

Compare baseline simulation against held-out historical data for:

- total case duration,
- waiting time by activity where estimable,
- activity lead times,
- duration by case type,
- duration by district,
- duration by variant group,
- p50/p75/p90/p95 durations,
- applicant missing-document response time,
- public-notice duration,
- number of rework cycles.

Use:

- quantile comparison plots,
- empirical CDFs,
- QQ plots,
- Wasserstein distance or similar distributional distance,
- calibration plots for routing probabilities.

Validation should focus especially on:

- Complex variance long tails,
- inspection rework variants,
- Commercial legal/environmental interactions,
- Monday-driven clerk queues,
- D3/D5-related bottlenecks.

### Resource-utilization validation

Compare simulated and observed or HR-derived utilization proxies:

- completions per resource/day,
- task mix by resource pool,
- active hours by weekday,
- field inspections per inspector/day,
- legal throughput around council meeting periods,
- environmental permit capacity relative to nominal FTE.

Avoid falsely validating utilization from completion timestamps alone. Treat it as a triangulation exercise using HR schedules, workload records, and log patterns.

### Bottleneck validation

Check whether the baseline identifies historically credible bottlenecks:

- clerk queues after Monday peaks,
- planning-review queues by district/type,
- fire-review limitations due to Tuesday-Thursday schedule,
- environmental queue volatility,
- inspector travel and readiness delays,
- legal delays during council-meeting weeks,
- public notice as a non-capacity statutory/external bottleneck.

Validate not only average utilization but queue aging and bottleneck migration over time.

### Out-of-sample validation

Use temporal holdout:

- Calibrate on the first 12-15 months.
- Validate on the remaining 3-6 months.
- Preserve observed seasonal demand differences.

If a policy change or staffing change occurred historically, use it as a quasi-experimental external check where appropriate, while recognizing confounding.

Also perform subgroup holdout validation:

- hold out selected districts,
- hold out selected architect groups,
- test transferability to rare but important case types.

### Acceptance criteria

Illustrative baseline acceptance ranges, to be refined with stakeholders:

- monthly arrivals/completions within roughly ±10%;
- median duration by major case type within ±10%;
- p90 duration by major case type within ±15-20%;
- major variant shares within ±3 percentage points for common variants;
- resource throughput/utilization within plausible operational ranges;
- correct identification of the top two or three operational bottlenecks.

Failure to meet a target should trigger model revision or wider uncertainty bounds, not forced calibration.

---

## 7. Decision criteria

No intervention should be declared “optimal” solely because it wins one simulation metric. Selection should use a multi-criteria decision framework with uncertainty and equity constraints.

### Primary outcome metrics

| Dimension | Metric | Decision use |
|---|---|---|
| Overall timeliness | Median end-to-end duration | Measures typical applicant experience |
| Tail performance | p90 and p95 duration | Measures long-delay risk, especially Complex variance and rework |
| SLA performance | Share completed within statutory/municipal SLA by case type | Core service-quality measure |
| Throughput | Completed cases per month/quarter | Detects backlog-clearing and capacity effects |
| Backlog | WIP, queue length, aged backlog, oldest-case age | Detects congestion and instability |
| Rework | Missing-document loop rate, inspection rework rate, post-legal rework rate | Measures quality and avoidable workload |
| Resource performance | Utilization, overtime proxy, queue pressure by resource pool | Tests feasibility and bottleneck shifts |
| Fairness | Median/p90/SLA gap by district, case type, architect segment | Avoids improvements concentrated in already advantaged groups |
| Applicant burden | Pre-submission time, extra steps, appointment waiting, document effort proxy | Essential for D1 and D7 |
| Policy risk | Misclassification rate, skipped-inspection exposure, triage error proxy | Essential for D2 and D8 |
| Robustness | Performance under S1-S6 | Ensures policies work beyond average conditions |

### Illustrative decision thresholds

Thresholds should be finalized with municipal leadership and statutory requirements, but the simulation can support rules such as:

1. **Timeliness improvement**
   - At least 10% reduction in p90 total duration for targeted case types, or
   - At least 5 percentage-point increase in SLA compliance,
   - with no material worsening in non-targeted types.

2. **No unacceptable tail harm**
   - No more than 5% increase in p90 duration for any protected/priority group.
   - No increase in the p95 duration of Complex variance cases beyond uncertainty bounds unless explicitly accepted for a compensating statutory benefit.

3. **Fairness**
   - District-level SLA gap should not worsen by more than 3 percentage points.
   - Architect concentration should not cause small or infrequent applicants to receive systematically worse waiting times.
   - D3 must be evaluated for low-volume districts that may be disadvantaged by batching.

4. **Operational feasibility**
   - Sustained utilization should generally remain below approximately 85-90% for constrained human pools, recognizing that short peak periods can exceed this.
   - Backlog should return to pre-peak levels within an agreed recovery period, for example 6-10 weeks after peak demand subsides.
   - Legal and environmental queues should not become newly unstable after D2/D4 relieve inspections.

5. **Rework and quality**
   - D1 should reduce missing-document loops enough to justify added applicant effort.
   - D5 should reduce late legal rework, not merely move it earlier while increasing total legal workload.
   - D8 and D2 should satisfy agreed risk-control limits under eligibility/triage uncertainty.

6. **Robustness**
   - Preferred interventions should retain a positive or neutral net benefit in at least 80-90% of parameter/scenario draws.
   - A policy that improves average results but fails under peak-demand stress should be treated as fragile.

### Multi-criteria selection rule

A transparent rule could be:

1. Eliminate policies that violate statutory, safety, or fairness constraints.
2. Among feasible policies, identify the Pareto frontier for:
   - p90 duration,
   - SLA compliance,
   - backlog,
   - applicant burden,
   - resource cost,
   - risk proxy.
3. Select a policy or package only if:
   - its expected benefit is material,
   - its uncertainty interval is acceptable,
   - it does not shift disproportionate harm to a district, applicant group, or case type,
   - it remains acceptable under stress scenarios.

The final recommendation should be phrased as evidence such as: “D1 + D2 + D4 appears robustly preferable under calibrated assumptions,” not as an exact proof of optimality.

def inspect_process_with_pm4py(log_df: pd.DataFrame) -> Dict[str, Any]:
    """
    Discover process-mining artifacts from a PM4Py-formatted dataframe.

    Exact return structures can differ slightly between PM4Py versions,
    so production code should pin a PM4Py version and add version-specific tests.
    """
    results: Dict[str, Any] = {}

    # Variant discovery: dictionary-like mapping from variants to cases/counts
    results["variants"] = pm4py.get_variants_as_tuples(log_df)

    # Frequency DFG
    results["dfg"] = pm4py.discover_dfg(log_df)

    # Performance DFG: commonly gives elapsed time on directly-following arcs.
    # This elapsed time is not automatically a pure service-time estimate.
    results["performance_dfg"] = pm4py.discover_performance_dfg(log_df)

    # Average inter-case arrival time. PM4Py computes it from case starts.
    # Guard for small logs where only a few cases are present.
    try:
        results["case_arrival_average_seconds"] = (
            pm4py.get_case_arrival_average(log_df)
        )
    except Exception:
        results["case_arrival_average_seconds"] = np.nan

    return results

def add_elapsed_and_proxy_columns(log_df: pd.DataFrame) -> pd.DataFrame:
    """
    Add elapsed-time columns without falsely claiming that inter-event time is service.

    With only completion timestamps, the time since the previous event is generally:
        predecessor completion -> queue waiting -> service -> current completion

    It is useful as a total lead-time proxy for calibration, but it should not be
    used directly as municipal service time.

    If lifecycle start timestamps become available, compute:
        service_time = complete - start
        waiting_time = start - predecessor completion
    """
    df = log_df.copy()
    df = df.sort_values(["case:concept:name", "time:timestamp"])

    group = df.groupby("case:concept:name", sort=False)
    df["previous_event_time"] = group["time:timestamp"].shift(1)
    df["previous_activity"] = group["concept:name"].shift(1)

    df["elapsed_since_previous_event_seconds"] = (
        df["time:timestamp"] - df["previous_event_time"]
    ).dt.total_seconds()

    # Completion-only logs cannot identify service vs waiting separately.
    df["lead_time_proxy_seconds"] = df["elapsed_since_previous_event_seconds"]

    # Placeholder fields; populate only if true start timestamps are available.
    df["service_time_seconds"] = np.nan
    df["waiting_time_seconds"] = np.nan
    df["service_waiting_identified"] = False

    # Example of handling a lifecycle-enriched log:
    # if {"start:timestamp", "time:timestamp"}.issubset(df.columns):
    #     df["start:timestamp"] = pd.to_datetime(df["start:timestamp"])
    #     df["service_time_seconds"] = (
    #         df["time:timestamp"] - df["start:timestamp"]
    #     ).dt.total_seconds()
    #     df["waiting_time_seconds"] = (
    #         df["start:timestamp"] - df["previous_event_time"]
    #     ).dt.total_seconds()
    #     df["service_waiting_identified"] = True

    # External delays should be tagged, not treated as staff service.
    df["is_applicant_external_activity"] = df["concept:name"].isin(
        {"Receive missing documents"}
    )
    df["is_public_notice_activity"] = df["concept:name"].eq("Public-notice period")
    df["is_human_municipal_activity"] = df["concept:name"].isin(HUMAN_ACTIVITIES)

    return df


def estimate_case_arrivals(log_df: pd.DataFrame) -> pd.DataFrame:
    """
    Build a case-arrival table from first Submit application events.
    """
    submissions = log_df.loc[
        log_df["concept:name"].eq("Submit application")
    ].copy()

    submissions = submissions.sort_values("time:timestamp")
    submissions["interarrival_seconds"] = (
        submissions["time:timestamp"].diff().dt.total_seconds()
    )
    submissions["weekday"] = submissions["time:timestamp"].dt.day_name()
    submissions["month"] = submissions["time:timestamp"].dt.month
    submissions["hour"] = submissions["time:timestamp"].dt.hour

    return submissions

@dataclass
class CalendarRule:
    """
    Represents availability logic. Production code should include:
    - holidays,
    - council meeting weeks,
    - individual leave/absence,
    - daily time windows,
    - special urgent legal work rules.
    """
    name: str
    weekdays_allowed: set
    start_hour: int
    end_hour: int
    blocked_dates: set = field(default_factory=set)
    blocked_weeks: set = field(default_factory=set)

    def is_working_time(self, dt: datetime) -> bool:
        iso_week = dt.isocalendar().week
        if dt.date() in self.blocked_dates:
            return False
        if iso_week in self.blocked_weeks:
            return False
        if dt.weekday() not in self.weekdays_allowed:
            return False
        return self.start_hour <= dt.hour < self.end_hour

            and policy.temporary_peak_inspector
            and now.month in policy.temporary_inspector_peak_months

            capacity += 1.0

        return capacity

class ArrivalGenerator:
    """
    Placeholder for a non-homogeneous arrival process plus architect bursts.

    Production calibration:
    - daily/weekly negative-binomial or Poisson model,
    - weekday/month effects,
    - type/district mix,
    - top-architect cluster process,
    - D7 appointment-slot smoothing.
    """

    def __init__(
        self,
        rng: np.random.Generator,
        policy: PolicyConfig,
        base_daily_rate: float = 60.0,
    ):
        self.rng = rng
        self.policy = policy
        self.base_daily_rate = base_daily_rate

    def seasonal_multiplier(self, dt: datetime) -> float:
        if dt.month in {3, 4, 5, 9, 10, 11}:
            return 1.7
        return 1.0

    def weekday_multiplier(self, dt: datetime) -> float:
        # Illustration only. In production fit all weekday effects.
        if dt.weekday() == 0:  # Monday
            return 2.2
        if dt.weekday() == 2:  # Wednesday
            return 1.0
        return 1.2

    def expected_daily_arrivals(self, dt: datetime) -> float:
        lam = (
            self.base_daily_rate
            * self.seasonal_multiplier(dt)
            * self.weekday_multiplier(dt)
        )

        # D7: slots smooth Monday spikes, but should conserve or explicitly
        # model displaced demand rather than simply deleting cases.
        if self.policy.architect_appointment_slots and dt.weekday() == 0:
            lam *= 0.80

        return lam

    def generate_day(self, day_start: datetime) -> List[PermitCase]:
        """
        Generate background arrivals plus optional correlated architect bursts.
        """
        expected = self.expected_daily_arrivals(day_start)
        n_background = self.rng.poisson(expected)

        cases: List[PermitCase] = []
        for i in range(n_background):
            cases.append(self._sample_case(day_start, suffix=f"B{i:04d}"))

        # Architect burst placeholder:
        # production model should estimate burst probability and burst-size
        # distribution from top-20 architect weekly submission patterns.
        burst_probability = 0.20
        if self.rng.random() < burst_probability:
            burst_size = int(self.rng.integers(2, 7))
            architect = f"A{int(self.rng.integers(1, 21)):02d}"
            district = self.rng.choice(["D1", "D2", "D3", "D4", "D5"])
            for j in range(burst_size):
                case = self._sample_case(
                    day_start,
                    suffix=f"A{j:03d}",
                    forced_architect=architect,
                    forced_district=district,
                )
                cases.append(case)

        return cases

    def _sample_case(
        self,
        day_start: datetime,
        suffix: str,
        forced_architect: Optional[str] = None,
        forced_district: Optional[str] = None,
    ) -> PermitCase:
        case_type = self.rng.choice(
            ["Simple renovation", "New residential", "Commercial", "Complex variance"],
            p=[0.45, 0.28, 0.17, 0.10],
        )

        district = forced_district or self.rng.choice(
            ["D1", "D2", "D3", "D4", "D5"]
        )
        architect = forced_architect or f"A{int(self.rng.integers(1, 300)):03d}"

        submit_hour = int(self.rng.integers(8, 19))
        submit_minute = int(self.rng.integers(0, 60))
        submit_time = day_start.replace(
            hour=submit_hour, minute=submit_minute, second=0, microsecond=0
        )

        value = float(np.exp(self.rng.normal(math.log(80_000), 1.0)))
        requires_fire = bool(
            case_type in {"New residential", "Commercial", "Complex variance"}
            and self.rng.random() < 0.65
        )
        requires_environment = bool(
            case_type in {"Commercial", "Complex variance"}
            and self.rng.random() < 0.55
        )
        requires_public_notice = bool(
            case_type == "Complex variance"
            or (case_type == "New residential" and self.rng.random() < 0.55)
        )

        low_risk = (
            case_type == "Simple renovation"
            and value < 50_000
            and self.rng.random() < 0.85
        )

        case_id = f"SIM-{day_start:%Y%m%d}-{suffix}"
        return PermitCase(
            case_id=case_id,
            case_type=case_type,
            district=district,
            architect_id=architect,
            application_value=value,
            submit_time=submit_time,
            requires_fire=requires_fire,
            requires_environment=requires_environment,
            requires_public_notice=requires_public_notice,
            requires_legal=case_type in {"Commercial", "Complex variance"},
            low_risk=low_risk,
            prior_violations=None,  # Often incomplete; use uncertainty model.
            document_quality_score=float(self.rng.beta(3, 2)),
            objection_risk_score=float(self.rng.beta(2, 5)),
            environmental_risk_score=float(self.rng.beta(2, 3)),
        )

# 6. Routing and external-delay logic

class Router:
    """
    Routes cases according to process constraints and calibrated probabilities.
    """

    def __init__(self, rng: np.random.Generator, policy: PolicyConfig):
        self.rng = rng
        self.policy = policy

    def missing_documents_probability(self, case: PermitCase) -> float:
        base = {
            "Simple renovation": 0.15,
            "New residential": 0.30,
            "Commercial": 0.35,
            "Complex variance": 0.45,
        }[case.case_type]

        # Lower document quality increases missing-document probability.
        p = base * (1.4 - case.document_quality_score)

        if self.policy.pre_submission_checker:
            p *= (1.0 - self.policy.precheck_missing_doc_reduction)

        return float(np.clip(p, 0.01, 0.95))

    def should_skip_inspection(self, case: PermitCase) -> bool:
        if not self.policy.no_inspection_low_risk_simple:
            return False

        if case.case_type != "Simple renovation":
            return False

        # In production, prior-violation uncertainty should be explicitly
        # represented with imputation/sensitivity analysis.
        no_known_violations = case.prior_violations is not True

        return (
            case.application_value < 50_000
            and case.low_risk
            and no_known_violations
        )

    def public_notice_duration_days(
        self,
        case: PermitCase,
        district_month_objection_pressure: float,
    ) -> float:
        """
        Missing objection events are not treated as observed. A latent pressure
        factor affects the probability and magnitude of extension beyond the
        statutory 14-day minimum.
        """
        minimum = 14.0
        if not case.requires_public_notice:
            return 0.0

        extension_probability = min(
            0.95,
            0.10
            + 0.50 * case.objection_risk_score
            + 0.30 * district_month_objection_pressure,
        )

        if self.policy.objection_early_warning:
            # This is a policy assumption to estimate/sensitivity-test, not fact.
            extension_probability *= 0.75

        if self.rng.random() < extension_probability:
            # Heavy-tailed extension; calibrate from excess public-notice duration.
            extension = float(np.exp(self.rng.normal(math.log(20), 0.8)))
            return minimum + extension

        return minimum

    def next_activities_after_completeness(
        self, case: PermitCase
    ) -> List[str]:
        if self.rng.random() < self.missing_documents_probability(case):
            return ["Request missing documents", "Receive missing documents", "Completeness check"]

        parallel = ["Planning review"]
        if case.requires_fire:
            parallel.append("Fire-safety review")
        if case.requires_environment:
            parallel.append("Environmental review")
        if case.requires_public_notice:
            parallel.append("Public-notice period")
        return parallel

    def downstream_after_reviews(self, case: PermitCase) -> List[str]:
        case.requires_inspection = not self.should_skip_inspection(case)

        if case.requires_inspection:
            return ["Inspection scheduling", "Site inspection"]

        return ["Decision drafting"]

class InspectionBundler:
    """
    Holds inspection-ready cases by district/zone. D3 reduces travel time but
    can delay early-ready cases. A maximum hold time prevents indefinite delay.
    """

    def __init__(self, policy: PolicyConfig):
        self.policy = policy
        self.pending_by_district: Dict[str, List[PermitCase]] = {}

    def add_ready_case(self, case: PermitCase, now: datetime) -> None:
        case.inspection_ready_time = now
        self.pending_by_district.setdefault(case.district, []).append(case)

    def release_bundles(self, now: datetime) -> List[List[PermitCase]]:
        released: List[List[PermitCase]] = []

        for district, pending in list(self.pending_by_district.items()):
            if not pending:
                continue

            if not self.policy.district_batching:
                released.extend([[case] for case in pending])
                self.pending_by_district[district] = []
                continue

            pending.sort(key=lambda c: c.inspection_ready_time or now)
            target = self.policy.batch_target_size
            max_hold = timedelta(days=self.policy.batch_max_hold_days)

            while len(pending) >= target:
                released.append(pending[:target])
                del pending[:target]

            # Force release of aged first-ready case.
            if pending:
                first_ready = pending[0].inspection_ready_time or now
                if now - first_ready >= max_hold:
                    released.append(list(pending))
                    pending.clear()

        return released

    @staticmethod
    def travel_time_hours(bundle: List[PermitCase]) -> float:
        """
        Illustration: D3 should estimate this empirically from district, route,
        and same-day geographic density. D3/D5 have longer travel patterns.
        """
        if not bundle:
            return 0.0

        district = bundle[0].district
        base = 1.0 if district in {"D3", "D5"} else 0.5
        savings = 0.15 * max(0, len(bundle) - 1)
        return max(0.2, base - savings)

class PermitSimulation:
    """
    Framework-neutral skeleton.

    A production implementation may use SimPy:
        - Environment
        - Resource / PriorityResource
        - Store for inspection bundle queues
        - custom calendar-aware service acquisition

    Important design principle:
    Do not sample historical waiting times independently if finite-capacity
    queues are explicitly simulated. Waiting should emerge from arrivals,
    priorities, resource calendars, and service durations.
    """

    def __init__(
        self,
        start_time: datetime,
        end_time: datetime,
        policy: PolicyConfig,
        seed: int,
        resource_pools: Dict[str, ResourcePool],
    ):
        self.start_time = start_time
        self.end_time = end_time
        self.policy = policy
        self.seed = seed

        self.rng = np.random.default_rng(seed)
        self.py_rng = random.Random(seed)

        self.arrivals = ArrivalGenerator(self.rng, policy)
        self.router = Router(self.rng, policy)
        self.bundler = InspectionBundler(policy)
        self.resource_pools = resource_pools

        self.completed_cases: List[PermitCase] = []
        self.open_cases: Dict[str, PermitCase] = {}
        self.metrics: Dict[str, List[float]] = {
            "total_duration_days": [],
            "queue_wait_days": [],
            "service_hours": [],
            "public_notice_days": [],
            "rework_count": [],
        }

    def run(self) -> pd.DataFrame:
        """
        Placeholder event loop.

        In a real DES:
        1. Iterate through simulation time / event queue.
        2. Generate non-stationary arrivals.
        3. Route cases and schedule prerequisites.
        4. Place municipal work in finite queues.
        5. Advance calendar-aware resource availability.
        6. Model applicant/public delays separately.
        7. Form inspection bundles under D3.
        8. Record event-level simulated log and case-level metrics.
        """
        current_day = self.start_time.replace(
            hour=0, minute=0, second=0, microsecond=0
        )

        while current_day < self.end_time:
            daily_cases = self.arrivals.generate_day(current_day)

            for case in daily_cases:
                self.open_cases[case.case_id] = case
                # Placeholder: actual engine would schedule Submit and then
                # the complete process lifecycle with resources/calendars.
                self._simulate_case_placeholder(case)

            current_day += timedelta(days=1)

        return self.collect_case_metrics()

    def _simulate_case_placeholder(self, case: PermitCase) -> None:
        """
        Deliberately simplified placeholder showing separation of delays.

        This is NOT the final operational simulation. It does not replace
        calendar-aware shared resource contention. Its purpose is to make
        the interfaces and metric structure explicit.
        """
        now = case.submit_time

        # Example external applicant delay if documents are missing.
        if self.rng.random() < self.router.missing_documents_probability(case):
            applicant_delay_days = float(np.exp(self.rng.normal(math.log(5), 0.8)))
            now += timedelta(days=applicant_delay_days)
            case.rework_counts["completeness"] = 1

        # Public notice is separate from municipal staff service.
        objection_pressure = 0.25  # Replace with district-month latent process.
        notice_days = self.router.public_notice_duration_days(
            case, objection_pressure
        )
        if notice_days > 0:
            now += timedelta(days=notice_days)

        # Inspection policy decision.
        if not self.router.should_skip_inspection(case):
            self.bundler.add_ready_case(case, now)

        # Placeholder completion. A real engine waits on queues/resources.
        completion_days = float(np.exp(self.rng.normal(math.log(20), 0.6)))
        now += timedelta(days=completion_days)

        case.status = "completed"
        case.outcome = "Issue permit"
        case.activity_end_times["Issue permit"] = now

        self.completed_cases.append(case)
        self.open_cases.pop(case.case_id, None)

    def collect_case_metrics(self) -> pd.DataFrame:
        rows = []
        for case in self.completed_cases:
            completion = case.activity_end_times.get("Issue permit")
            if completion is None:
                continue

            duration_days = (completion - case.submit_time).total_seconds() / 86400.0
            rows.append(
                {
                    "case_id": case.case_id,
                    "case_type": case.case_type,
                    "district": case.district,
                    "architect_id": case.architect_id,
                    "application_value": case.application_value,
                    "submit_time": case.submit_time,
                    "completion_time": completion,
                    "total_duration_days": duration_days,
                    "rework_count": sum(case.rework_counts.values()),
                    "policy": self.policy.name,
                    "outcome": case.outcome,
                }
            )

        return pd.DataFrame(rows)

    weekday_office = {0, 1, 2, 3, 4}

def run_experiment(
    policy: PolicyConfig,
    replications: int,
    start_time: datetime,
    end_time: datetime,
    base_seed: int = 20260101,
) -> pd.DataFrame:
    """
    Run replications. For paired comparisons, call baseline and intervention
    with the same replication seed sequence and aligned random streams.
    """
    all_results = []

    pools = build_resource_pools(
        holidays=set(),
        council_meeting_weeks={8, 20, 44},  # illustrative only
    )

    for rep in range(replications):
        seed = base_seed + rep

        sim = PermitSimulation(
            start_time=start_time,
            end_time=end_time,
            policy=policy,
            seed=seed,
            resource_pools=pools,
        )

        result = sim.run()
        result["replication"] = rep
        result["seed"] = seed
        all_results.append(result)

    if not all_results:
        return pd.DataFrame()

    return pd.concat(all_results, ignore_index=True)


def summarize_results(case_results: pd.DataFrame) -> pd.DataFrame:
    """
    Example outcome summary. Production reporting should add:
    - p90/p95 by case type and district,
    - SLA rates,
    - queue and utilization metrics,
    - backlog aging,
    - applicant burden,
    - fairness gaps,
    - stress-scenario robustness.
    """
    if case_results.empty:
        return pd.DataFrame()

    return (
        case_results.groupby(["policy", "case_type"], dropna=False)
        .agg(
            n_cases=("case_id", "size"),
            median_duration_days=("total_duration_days", "median"),
            p90_duration_days=(
                "total_duration_days",
                lambda x: np.quantile(x, 0.90),
            ),
            mean_rework=("rework_count", "mean"),
        )
        .reset_index()
    )
