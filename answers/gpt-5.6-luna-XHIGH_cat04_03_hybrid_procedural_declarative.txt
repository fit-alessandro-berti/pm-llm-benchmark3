# 1. Policy Interpretation and Conflict Resolution

The model treats a trace as a complete case, with events ordered by timestamp and a stable secondary event order for ties. “Eventually” means later in the same case. The visible activity labels are the event identity; risk class, emergency status, authorization, and responsibility are not inferred from labels.

The material assumptions are:

- `Receive Onboarding Request` is the unique case start, and a complete case has one `Close Onboarding`.
- The three checks are concurrent after receipt. Their interleaving in the event log is not itself a violation.
- The approval actually performed identifies the route: `Manager Approval` identifies the low-risk route and `Compliance Approval` identifies the high-risk route. A risk attribute, if available, is a useful independent cross-check, not a substitute for the approval rule.
- In the canonical process tree, clarification cycles occur before `Classify Risk`. Requirement R3 is also checked independently so that a later clarification, or a clarification in a non-block-structured trace, cannot evade the obligation.
- The process tree models one optional sanctions/legal detour. Multiple escalation/legal pairs are checked by the external validator; the validator does not rely on the tree approximation.
- The canonical control-flow model is the strict legal policy in R5. Change-of-bank-details activity is a post-activation extension checked outside the tree, because it can be interleaved with the payment lifecycle.
- A temporal profile checks elapsed time only when both events in a configured pair occur. A deviation beyond `mean +/− zeta * standard_deviation` is a warning, not a hard conformance failure.
- Missing timestamps, activity names, or case identifiers make the event schema invalid. Missing resource identity fails closed for a segregation-of-duties check. Missing emergency authorization evidence does not prove that an emergency occurred; it leaves the R6 exception unverified and is failed closed for strict compliance deployment.

R5 and R6 cannot both be unconditional rules. If an escalation occurs, activation before the legal opinion violates R5, while it can be permitted by R6 only under an independently verified exception.

Two coherent resolutions are possible:

1. **Strict precedence (chosen).** R5 is authoritative: after an escalation, a legal opinion must be present before activation. R6 is retained as a possible future exception procedure, but an event log without an emergency flag and external joint-authorization record cannot select that branch. This is the policy implemented by `procedural_model`.
2. **Controlled emergency exception.** R6 overrides R5 only for a case with a valid external joint authorization recorded before activation and a legal opinion no later than 24 hours after activation. Otherwise R5 applies. The activity-only model can contain an exceptional path, but only the external layer can decide whether that path is authorized.

The strict choice risks delaying a legitimate emergency activation and therefore creates an operational false positive. The exception choice risks permitting an unauthorized activation if external evidence is incomplete or incorrectly associated with the case. The implementation chooses strict precedence because it is auditable from the supplied trace and fails closed when the required exception evidence is unavailable. Under the alternative resolution, T6 can pass only with valid external authorization; the supplied event log alone cannot establish that fact.

# 2. Requirement-to-Formalism Mapping

| Requirement | Primary formalism | Exact encoding | Why this formalism | Redundancy or limitation |
|---|---|---|---|---|
| R1 | DECLARE, with procedural authority | `noncoexistence(Reject Vendor, Activate Vendor)`; the process-tree XOR has the same effect | It is a simple case-level exclusion | DECLARE and the log skeleton duplicate it; neither layer explains why a contradictory trace occurred |
| R2 | Separate policy validation, backed by the tree | If rejected, approval count is 0; if accepted, `count(Manager Approval) + count(Compliance Approval) == 1` | The accepted/rejected condition is data-dependent and disjunctive | DECLARE can express noncoexistence but not “exactly one iff accepted” without also rejecting valid rejected cases |
| R3 | Separate ordered-event validation, backed by DECLARE | Pending requests must be closed by a response before another request and before a terminal event; DECLARE has `altresponse(Request Clarification, Receive Clarification)` and `response(...)` | The validator can maintain a pending-request state and enforce the boundary before the final outcome | `response` alone allows a response after the outcome; `altresponse` does not name arbitrary terminal activities, so the external check is authoritative |
| R4 | DECLARE | `response(Sanctions Escalation, Obtain Legal Opinion)` | An eventual response is exactly the useful activity-only obligation | It is vacuous when no escalation occurs and does not by itself enforce a deadline or pair multiple escalations precisely |
| R5 | ProcessTree under the chosen policy, plus external audit | Every modeled escalation is in `Escalation -> Legal Opinion` detour joined before approval/activation | The tree can enforce the strict ordering on its canonical branch | A conditional “only if escalation” ordering cannot be expressed by one unconditional precedence rule without rejecting traces that have no escalation |
| R6 | Resource/data-aware validation | For activation before opinion, require external joint authorization valid before activation and opinion within 86,400 seconds | Authorization and the emergency condition are not event labels | The supplied event log lacks the required attributes, so an activity-only conformance result cannot certify R6 |
| R7 | DECLARE | `precedence(Run Sanctions Screening, Sanctions Escalation)` | Every escalation must have a preceding screening event | The tree also places escalation after classification, which is a conservative placement beyond the stated minimum |
| R8 | DECLARE | `noncoexistence(Enhanced Due Diligence, Manager Approval)` and `noncoexistence(Compliance Approval, Manager Approval)` | Non-co-occurrence is directly expressible and symmetric in meaning | The procedural route choice duplicates it; DECLARE does not explain which route was intended |
| R9 | Resource/data-aware validation | Compare every `Verify Bank Account` resource with the applicable approval resource; compare `Capture Master Data` with `Activate Vendor` | The condition is on event attributes, not activity order | A sequence model can never recover resource identity from labels; absent resources fail closed |
| R10 | Log Skeleton, with procedural support | `activ_freq` allows `{0,1}` for `Activate Vendor`, `Reject Vendor`, and `Release First Payment`; the tree has one occurrence of each leaf | Frequency sets express “at most once” directly | A skeleton frequency rule does not explain route semantics; incomplete cases may be rejected before their lifecycle is complete |
| R11 | Separate ordered-event validation | For every post-activation bank-detail change, require a later suspension and, for every later payment, a verification after that change | It needs timestamps, repeated events, and a “later payment” condition | DECLARE can add `response(Change Bank Details, Suspend Vendor)`, but cannot require the *new* verification before a later payment |
| R12 | Temporal profile | The three configured pairs use the supplied mean and standard deviation, with `zeta = 2.0` | This is a statistical timing expectation rather than control flow | A timing warning neither repairs a missing event nor proves a causal relationship |

# 3. Procedural Backbone

Let `D = Sanctions Escalation -> Obtain Legal Opinion` and `C = Request Clarification -> Receive Clarification`. The strict canonical process is:

```text
Receive Onboarding Request
  -> (Capture Master Data || Run Sanctions Screening || Verify Bank Account)
  -> C*
  -> Classify Risk
  -> XOR(
       RejectPath,
       (Manager Approval || (tau XOR D)) -> Activate Vendor -> Release First Payment -> Close Onboarding,
       (Enhanced Due Diligence || (tau XOR D)) -> Compliance Approval -> Activate Vendor -> Release First Payment -> Close Onboarding
     )
```

`RejectPath` is either `Reject Vendor`, `D -> Reject Vendor`, or `Reject Vendor -> D`, followed by `Close Onboarding`. The parallel gates in the two accepted routes allow the sanctions/legal detour to interleave with the route-specific approval work, but the join must complete before activation. Thus, in the chosen strict policy, legal opinion precedes activation whenever escalation occurs. The tree intentionally permits only one modeled detour; the external validator handles repeated escalations.

The clarification loop is zero-or-more repetitions of `C`. A process-tree loop is used as a compact representation of the repetition, with a silent redo/exit structure. This is a block-structured approximation: arbitrary clarification activity after classification is not represented by the tree, although the ordered validator still checks R3.

Change-of-bank-details, suspension, and re-verification are deliberately excluded from the onboarding tree. They are post-activation lifecycle behavior with potentially multiple interleavings. R11 is therefore authoritative in the data-aware layer. The tree does enforce the single accepted route, one approval path, activation before first payment, and closure after rejection or payment.

The following is self-contained PM4Py-style construction code. A `ProcessTree()` with no label and no operator is a silent transition.

```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree


def leaf(label):
    return ProcessTree(label=label)


def tau():
    return ProcessTree()


def make(operator, *children):
    tree = ProcessTree(operator=operator)
    tree.children = list(children)
    return tree


def seq(*children):
    return make(Operator.SEQUENCE, *children)


def xor(*children):
    return make(Operator.XOR, *children)


def par(*children):
    return make(Operator.PARALLEL, *children)


def zero_or_more(body):
    # LOOP children are: do, redo, exit. A silent redo permits repetition;
    # the outer XOR supplies the zero-iteration case.
    return xor(
        tau(),
        make(Operator.LOOP, body, tau(), tau()),
    )


receive = leaf("Receive Onboarding Request")
capture = leaf("Capture Master Data")
screen = leaf("Run Sanctions Screening")
verify = leaf("Verify Bank Account")
classify = leaf("Classify Risk")
request_clarification = leaf("Request Clarification")
receive_clarification = leaf("Receive Clarification")
escalation = leaf("Sanctions Escalation")
legal = leaf("Obtain Legal Opinion")
edd = leaf("Enhanced Due Diligence")
manager = leaf("Manager Approval")
compliance = leaf("Compliance Approval")
reject = leaf("Reject Vendor")
activate = leaf("Activate Vendor")
release = leaf("Release First Payment")
close = leaf("Close Onboarding")

clarification_cycle = seq(request_clarification, receive_clarification)
clarifications = zero_or_more(clarification_cycle)
checks = par(capture, screen, verify)

def optional_sanctions_detour():
    # A fresh subtree is needed each time; process-tree nodes have one parent.
    return xor(tau(), seq(leaf("Sanctions Escalation"),
                           leaf("Obtain Legal Opinion")))


reject_path = seq(
    xor(
        leaf("Reject Vendor"),
        seq(leaf("Sanctions Escalation"), leaf("Obtain Legal Opinion"),
            leaf("Reject Vendor")),
        seq(leaf("Reject Vendor"), leaf("Sanctions Escalation"),
            leaf("Obtain Legal Opinion")),
    ),
    leaf("Close Onboarding"),
)

low_path = seq(
    par(leaf("Manager Approval"), optional_sanctions_detour()),
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding"),
)

high_path = seq(
    par(leaf("Enhanced Due Diligence"), optional_sanctions_detour()),
    leaf("Compliance Approval"),
    leaf("Activate Vendor"),
    leaf("Release First Payment"),
    leaf("Close Onboarding"),
)

procedural_model = seq(
    receive,
    checks,
    clarifications,
    classify,
    xor(reject_path, low_path, high_path),
)
```

# 4. DECLARE Model

The following uses only standard templates listed in the question. Every rule has explicit support and confidence metadata. The values are policy declarations for this model, not claims that the eight test traces statistically establish the rules.

```python
declare_model = {
    "init": {

    },
    "exactly_one": {
        "Receive Onboarding Request": {"support": 1.0, "confidence": 1.0},
    },
    "response": {
        ("Request Clarification", "Receive Clarification"):
            {"support": 1.0, "confidence": 1.0},
        ("Sanctions Escalation", "Obtain Legal Opinion"):
            {"support": 1.0, "confidence": 1.0},
        ("Change Bank Details", "Suspend Vendor"):
            {"support": 1.0, "confidence": 1.0},

            {"support": 1.0, "confidence": 1.0},
        ("Release First Payment", "Close Onboarding"):
            {"support": 1.0, "confidence": 1.0},
    },
    "altresponse": {
        ("Request Clarification", "Receive Clarification"):
            {"support": 1.0, "confidence": 1.0},
    },
    "precedence": {
        ("Request Clarification", "Receive Clarification"):
            {"support": 1.0, "confidence": 1.0},
        ("Run Sanctions Screening", "Sanctions Escalation"):
            {"support": 1.0, "confidence": 1.0},
    },
    "succession": {
        ("Activate Vendor", "Release First Payment"):
            {"support": 1.0, "confidence": 1.0},
    },
    "noncoexistence": {
        ("Reject Vendor", "Activate Vendor"):
            {"support": 1.0, "confidence": 1.0},
        ("Enhanced Due Diligence", "Manager Approval"):
            {"support": 1.0, "confidence": 1.0},
        ("Compliance Approval", "Manager Approval"):
            {"support": 1.0, "confidence": 1.0},
    },
}
```

| Encoded rule | Direction and semantics |
|---|---|
| `init(Receive Onboarding Request)` | The first event is `Receive Onboarding Request`. |
| `exactly_one(Receive Onboarding Request)` | The request occurs exactly once; this complements, but is stronger than, the start rule. |
| `response(Request Clarification, Receive Clarification)` | For every request, some response occurs later. It does not require the response to be before a final outcome. |
| `altresponse(Request Clarification, Receive Clarification)` | Every request is eventually answered and a new request cannot intervene before that answer. This is stronger than ordinary response, but still does not name the final-outcome boundary. |
| `precedence(Request Clarification, Receive Clarification)` | Every response has a request earlier in the trace. The direction is request before response; it is not a response obligation by itself. |
| `response(Sanctions Escalation, Obtain Legal Opinion)` | Every escalation is eventually followed by legal opinion. It is intentionally vacuous if there is no escalation. |
| `precedence(Run Sanctions Screening, Sanctions Escalation)` | Every escalation has a screening event earlier in the trace. It does not require screening to be immediately before escalation. |
| `response(Change Bank Details, Suspend Vendor)` | Every bank-detail change is eventually followed by suspension. It does not impose the additional re-verification-before-payment condition. |
| `succession(Activate Vendor, Release First Payment)` | This combines response and precedence: activation is followed by release, and every release has an earlier activation. It is not a chain-succession rule, so intervening events are permitted. |
| `response(Reject Vendor, Close Onboarding)` and `response(Release First Payment, Close Onboarding)` | The applicable terminal event is eventually followed by closure. The conditional “either reject or release, but not both” remains procedural. |
| `noncoexistence(A, B)` | The two activities cannot both occur in a case. It is not the same as `nonsuccession`: nonsuccession is a negative ordering relation, whereas noncoexistence forbids co-occurrence regardless of order. |

R2 is not encoded as `exactly_one` over the two approvals: that would incorrectly reject T3, where neither approval is required. R5 is also not encoded as unconditional `precedence(Obtain Legal Opinion, Activate Vendor)`, because that would incorrectly reject every accepted case with no sanctions escalation. The strict conditional ordering is enforced by the procedural detour and the external validator.

# 5. Log-Skeleton Model

For pair-valued entries below, the orientation is `(A, B)`: for `always_before`, A must occur before B whenever B occurs; for `equivalence`, A and B have equal occurrence counts; for `never_together`, both cannot occur in one trace; and for `directly_follows`, A must be immediately followed by B. `always_after` is left empty because its useful conditional consequences are already covered without imposing an incorrect unconditional relationship.

```python
log_skeleton = {

    "always_before": {

        ("Receive Onboarding Request", "Run Sanctions Screening"),
        ("Receive Onboarding Request", "Verify Bank Account"),
        ("Receive Onboarding Request", "Classify Risk"),
        ("Receive Onboarding Request", "Close Onboarding"),

        ("Request Clarification", "Receive Clarification"),
        ("Capture Master Data", "Classify Risk"),
        ("Run Sanctions Screening", "Classify Risk"),
        ("Verify Bank Account", "Classify Risk"),
        ("Classify Risk", "Reject Vendor"),
        ("Classify Risk", "Manager Approval"),
        ("Classify Risk", "Enhanced Due Diligence"),
        ("Classify Risk", "Sanctions Escalation"),
        ("Classify Risk", "Activate Vendor"),
        ("Classify Risk", "Close Onboarding"),
        ("Run Sanctions Screening", "Sanctions Escalation"),
        ("Sanctions Escalation", "Obtain Legal Opinion"),
        ("Activate Vendor", "Release First Payment"),
    },
    "always_after": set(),
    "never_together": {
        ("Reject Vendor", "Activate Vendor"),
        ("Enhanced Due Diligence", "Manager Approval"),
        ("Compliance Approval", "Manager Approval"),
    },
    "activ_freq": {
        "Receive Onboarding Request": {1},
        "Close Onboarding": {1},
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1},
    },
    "directly_follows": set(),
}
```

The clarification equivalence captures one response per request, while DECLARE `altresponse` supplies the order-sensitive part. The activation/release equivalence and frequency sets duplicate the tree’s single-payment route. `never_together` duplicates the DECLARE exclusions. `always_before` contains only unconditional precedences: it does not say that `Manager Approval` precedes every activation, because a high-risk activation has no manager approval, and it does not say that `Reject Vendor` precedes every closure, because an accepted case closes without rejection. `directly_follows` is empty because the three checks are concurrent and because optional detours, clarifications, and future post-activation events make adjacency too strong.

The skeleton cannot encode the conditional R5/R6 exception, resource identity, or the requirement that a new verification occur after a particular bank-detail change. Its `equivalence` constraints also assume complete traces; an in-progress case with a pending clarification is expected to fail or be marked incomplete rather than treated as a valid prefix.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"):
        (48 * 60 * 60, 24 * 60 * 60),
    ("Sanctions Escalation", "Obtain Legal Opinion"):
        (12 * 60 * 60, 6 * 60 * 60),
    ("Activate Vendor", "Release First Payment"):
        (72 * 60 * 60, 36 * 60 * 60),
}

zeta = 2.0
```

The three pairs are respectively `(172800, 86400)`, `(43200, 21600)`, and `(259200, 129600)` seconds. A pair is warned when its observed elapsed time is more than two standard deviations from its mean. Thus the nominal bands are 0–96 hours for clarification, 0–24 hours for escalation-to-opinion, and 0–144 hours for activation-to-first-payment; elapsed times are non-negative, so the lower bounds are truncated at zero.

The profile is advisory because these are normative service expectations rather than causal control-flow constraints. A delayed opinion can be a compliance concern even when all activities are correctly ordered, while a fast payment does not make a missing approval valid. Missing one endpoint is handled by DECLARE/procedural validation, not by inventing a timing value.

# 7. Resource- and Data-Aware Checks

The event dataframe below is assumed to contain `case_id`, `concept:name`, `time:timestamp`, and `org:resource`. Timestamps must be timezone-normalized. An external authorization table is keyed by `case_id` and is not part of the event log.

```python
import pandas as pd

ACT = "concept:name"
TS = "time:timestamp"
RES = "org:resource"
CASE = "case_id"

ACCEPTED_APPROVALS = {"Manager Approval", "Compliance Approval"}
FINAL_ACTIVITIES = {
    "Reject Vendor", "Activate Vendor", "Release First Payment", "Close Onboarding"
}


def ordered(case_df):
    # The original row order is the deterministic tie-breaker for equal timestamps.
    x = case_df.copy()
    x["_event_order"] = range(len(x))
    return x.sort_values([TS, "_event_order"])


def require_schema(df):
    required = {CASE, ACT, TS}
    missing = required - set(df.columns)
    if missing:
        raise ValueError("invalid event schema; missing " + repr(sorted(missing)))
    if df[[CASE, ACT, TS]].isna().any().any():
        raise ValueError("case, activity, and timestamp cannot be missing")


def check_clarifications(case_df):
    """Return pass/fail for R3, including the final-outcome boundary."""
    pending = 0
    final_seen = False
    for _, row in ordered(case_df).iterrows():
        activity = row[ACT]
        if final_seen and activity in {
            "Request Clarification", "Receive Clarification"
        }:
            return "fail"
        if activity == "Request Clarification":
            if pending > 0:       # no second request before the first response
                return "fail"
            pending += 1
        elif activity == "Receive Clarification":
            if pending == 0:      # unsolicited response
                return "fail"
            pending -= 1
        if activity in FINAL_ACTIVITIES:
            if pending > 0:
                return "fail"
            final_seen = True
    return "pass" if pending == 0 else "fail"


def check_outcomes_and_approvals(case_df):
    """Check R1, R2, and the activity-count part of R10."""
    names = case_df[ACT]
    n_reject = int((names == "Reject Vendor").sum())
    n_activate = int((names == "Activate Vendor").sum())
    n_release = int((names == "Release First Payment").sum())
    n_manager = int((names == "Manager Approval").sum())
    n_compliance = int((names == "Compliance Approval").sum())

    if max(n_reject, n_activate, n_release) > 1:
        return "fail"
    if n_reject and n_activate:
        return "fail"
    if n_reject and (n_manager or n_compliance):
        return "fail"
    if n_activate and (n_manager + n_compliance != 1):
        return "fail"
    return "pass"


def check_sod(case_df):
    """Check R9. Missing org:resource fails closed, not pass."""
    x = ordered(case_df)
    approvals = x[x[ACT].isin(ACCEPTED_APPROVALS)]
    verifications = x[x[ACT] == "Verify Bank Account"]
    captures = x[x[ACT] == "Capture Master Data"]
    activations = x[x[ACT] == "Activate Vendor"]

    if RES not in x.columns or x[RES].isna().any():
        return "fail"

    # If there is one applicable approval, all performed bank verifications
    # must be by someone other than that approver. Rejected cases have no
    # applicable approval, so this particular comparison is vacuous.
    if len(approvals) == 1:
        approval_resource = approvals.iloc[0][RES]
        if any(row[RES] == approval_resource for _, row in verifications.iterrows()):
            return "fail"
    elif len(approvals) > 1:
        return "fail"

    if len(captures) and len(activations):
        capture_resources = set(captures[RES])
        activation_resources = set(activations[RES])
        if capture_resources & activation_resources:
            return "fail"
    return "pass"


def check_sanctions_policy(case_df, external_authorization=None, mode="strict"):
    """Check R4, R5, R6, and R7.

    external_authorization[case_id] is expected to contain:
      joint_authorization_valid: bool
      authorization_id: non-empty identifier
      authorized_at: timestamp no later than activation
      authorizers: at least two independently recorded authorizers
    """
    x = ordered(case_df)
    screening = x[x[ACT] == "Run Sanctions Screening"]
    escalations = x[x[ACT] == "Sanctions Escalation"]
    opinions = x[x[ACT] == "Obtain Legal Opinion"]
    activations = x[x[ACT] == "Activate Vendor"]

    for _, e in escalations.iterrows():
        later_opinions = opinions[opinions[TS] > e[TS]]
        if later_opinions.empty:
            return "fail"                    # R4
        if screening.empty or not (screening[TS] < e[TS]).any():
            return "fail"                    # R7

    if escalations.empty or activations.empty:
        return "pass"

    activation_time = activations.iloc[0][TS]
    all_opinions_before_activation = True
    for _, e in escalations.iterrows():
        qualifying = opinions[(opinions[TS] > e[TS]) &
                              (opinions[TS] < activation_time)]
        if qualifying.empty:
            all_opinions_before_activation = False
            break

    if all_opinions_before_activation:
        return "pass"
    if mode == "strict":
        return "fail"                    # R5

    # R6 exception path. The event log has no emergency or joint-authorization
    # attribute, so absence of the external record is indeterminate here.
    case_id = case_df[CASE].iloc[0]
    auth = (external_authorization or {}).get(case_id)
    if not auth:
        return "policy-dependent"
    if not auth.get("joint_authorization_valid"):
        return "fail"
    if not auth.get("authorization_id") or not auth.get("authorized_at"):
        return "policy-dependent"
    if auth["authorized_at"] > activation_time:
        return "fail"
    authorizers = auth.get("authorizers", [])
    if len(set(authorizers)) < 2:
        return "fail"

    later_opinions = opinions[opinions[TS] > activation_time]
    if later_opinions.empty:
        return "fail"
    opinion_time = later_opinions.iloc[0][TS]
    if (opinion_time - activation_time).total_seconds() > 24 * 60 * 60:
        return "fail"
    return "pass"


def check_bank_change(case_df):
    """Check R11 using timestamp order and repeated verification events."""
    x = ordered(case_df)
    activations = x[x[ACT] == "Activate Vendor"]
    changes = x[x[ACT] == "Change Bank Details"]
    suspensions = x[x[ACT] == "Suspend Vendor"]
    verifications = x[x[ACT] == "Verify Bank Account"]
    releases = x[x[ACT] == "Release First Payment"]

    if changes.empty:
        return "pass"
    if activations.empty:
        return "fail"  # the model has no pre-activation change extension
    activation_time = activations.iloc[0][TS]

    for _, change in changes.iterrows():
        if change[TS] <= activation_time:
            return "fail"  # outside the modeled post-activation lifecycle
        if not (suspensions[TS] > change[TS]).any():
            return "fail"
        later_releases = releases[releases[TS] > change[TS]]
        for _, payment in later_releases.iterrows():
            new_verification = verifications[
                (verifications[TS] > change[TS]) &
                (verifications[TS] < payment[TS])
            ]
            if new_verification.empty:
                return "fail"
    return "pass"
```

For an accepted case, `check_sod` requires a single applicable approval before comparing resources. For a rejected case, the approval comparison is vacuous, but R2 separately fails if an approval is present. If `org:resource` is absent from the dataframe, the segregation check returns `fail`; silently treating a missing resource as different would defeat R9. If there are multiple approvals or ambiguous event times, the validator should fail the case or route it to manual review rather than choose an approver arbitrarily.

The emergency condition cannot be reconstructed from the eight visible fields. A valid external record must bind the authorization to the same case, be created no later than activation, identify at least two authorizers, and attest that the exception was valid. Without it, an R6 result is `policy-dependent`; the production compliance gate converts that status to a hard hold. A system that adds event attributes should still retain the external authorization check because “emergency” alone does not prove joint authorization.

# 8. Test-Case Verdict Matrix

The main matrix uses the chosen strict-R5 policy. `pass` in the temporal column means every observed configured pair is within its profile band; `not evaluated` means no configured pair was present. It does not mean that missing control-flow events are acceptable.

| Test | Procedural | DECLARE | Log Skeleton | Temporal | Resource/data layer | Overall verdict | Explanation |
|---|---|---|---|---|---|---|---|
| T1 | pass | pass | pass | pass | pass | pass | The three checks can be interleaved, the low-risk route has one manager approval, and all segregation checks pass. The 71-hour activation-to-payment interval is within the 0–144 hour band. |

# 9. Contradictions, Redundancies, and Blind Spots

- R1, R8, parts of R3, and the activation/payment order are duplicated across the tree, DECLARE, and the log skeleton. The duplication is useful as a diagnostic cross-check, but a user interface should identify the same policy violation once and list the confirming layers rather than display three unrelated failures.
- The tree, `altresponse`, and the clarification-count equivalence can disagree on prefixes and non-block-structured traces. A case with an unanswered request is expected to fail R3; a running case may instead need an “incomplete prefix” status so that operational monitoring does not confuse unfinished work with a completed nonconforming case.
- `response` and `precedence` are often vacuous. A response rule does nothing in a trace with no activation of its source; a precedence rule does nothing when its target is absent. Neither absence nor vacuity proves that the route was semantically appropriate.
- Conditional route rules cannot be represented faithfully by unconditional activity pairs. In particular, requiring legal opinion before every activation would reject ordinary cases with no escalation, while requiring both approval activities would reject both valid route alternatives. The same limitation prevents a pure DECLARE or skeleton model from expressing “another verification after this particular change and before a later payment.”
- The `Activate Vendor`/`Release First Payment` equivalence is consistent with the complete-case backbone and R10, but it rejects a trace that ends after activation. That is correct for a complete-case conformance report and potentially too strong for live prefix monitoring. R11 is also sensitive to R10: if payment is truly at most once and a bank change occurs after that payment, the “later payment” clause is vacuous, although suspension is still required.
- The log has no emergency flag, authorization identifier, authorizer identities, risk attribute, or case-level policy version. It is therefore impossible to tell whether T6 was a legitimate emergency from activity names and timestamps. Missing attributes must be surfaced as unverified evidence, not filled with defaults.
- Timestamp order cannot establish causality when timestamps tie, clocks are skewed, events are asynchronously ingested, or resource changes occur between event creation and recording. The implementation needs a documented tie-breaker and normalized timezone; high-risk decisions should retain source-system event IDs and authorization timestamps.
- Temporal profiles can flag unusual elapsed times but cannot enforce a deadline unless a separate hard-deadline rule is added. A profile also cannot distinguish a delayed event from a missing event.
- Support and confidence values in a DECLARE dictionary are metadata consumed by the conformance implementation; setting both to `1.0` makes the rules active model declarations here. They are not proof that the policy was empirically observed, and they must not override a formal policy version or external authorization record.
- Resource identity needs normalization. “Cora”, a user ID, a service account, and a group alias must not be compared as raw display strings without a controlled identity mapping. Otherwise R9 can produce both false passes and false failures.

# 10. Deployment Recommendation

Use the ProcessTree-derived procedural model as the canonical onboarding representation, or convert it to an accepting Petri net for execution and monitoring where repeated escalation/legal detours and post-activation lifecycle behavior need richer synchronization. Keep the strict R5 variant as the default policy version. Treat the R6 exception as a separately versioned, externally gated policy rather than silently broadening the canonical tree.

Run conformance checks in this order:

1. Validate event schema, case completeness, timestamp normalization, resource identity, and external authorization joins.
2. Run procedural conformance for the backbone, route choice, concurrency, clarification-loop approximation, terminal behavior, and strict legal ordering.
3. Run DECLARE for eventual, precedence, and non-coexistence diagnostics.
4. Run the log skeleton for occurrence counts and unconditional before/after structure.
5. Run resource/data checks for approvals, segregation of duties, R3 boundary handling, R6 evidence, and R11.
6. Run the temporal profile and attach warnings without changing a hard control-flow verdict.

The result should distinguish hard violations, unverified policy conditions, and timing warnings. A case such as T6 should be displayed as “R5 ordering violation; possible R6 exception requires external evidence,” not merely as a generic process failure. When layers disagree, retain the earliest event and rule that caused the decisive result, list redundant confirmations underneath it, and expose the policy version used. An R6 authorization record can change the policy verdict only through the explicit exception workflow; it must never be inferred from an activity sequence or from DECLARE support/confidence metadata.

The emergency condition cannot be reconstructed from the eight visible fields. A valid external record must bind the authorization to the same case, be created no later than activation, identify at least two authorizers, and attest that the exception was valid. Without it, an R6 result is `policy-dependent`; the production compliance gate converts that status to a hard hold. A system that adds event attributes should still retain the external authorization check because “emergency” alone does not prove joint authorization.
