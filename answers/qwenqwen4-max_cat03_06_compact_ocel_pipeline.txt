## 1. Modeling assumptions

**Object types (capitalization).** Six singular, capitalized types: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. IDs are exactly as narrated (`O100, O200, I1, I2, I3, P1, P2, D1, D2, V1, M1, M2`) — 12 objects, 17 events, no invented objects. Payment amounts (100 / 150) are **event attributes** (`amount` on `Record Payment`), never objects.

**E2O qualifier vocabulary (role of the object in the event).** Nine qualifiers, split into two families:

| family | qualifiers | meaning |
|---|---|---|
| bare role (source fact) | `order`, `item`, `package`, `delivery`, `invoice`, `payment` | the object is a stated participant/subject of the event |
| `context_*` (operational involvement) | `context_order`, `context_item`, `context_package` | the object is operationally involved because it is contained in / carries a directly participating object, and that containment already holds at event time |

The prefix is the contract: **`context_*`  derived operational involvement**, bare role  source-system fact.

**O2O direction convention.** `ocel:oid` = the *referencing / containing / later* object, `ocel:oid_2` = the *referenced / contained* object. So `Order --contains--> Item`, `Package --packs--> Item`, `Delivery --carries--> Package`, `Invoice --bills--> Order`, `Payment --partially_settles|completes_settlement--> Invoice`. M1 is `partially_settles`, M2 is `completes_settlement` (100 + 150 = 250 closes V1).

**Do logistics/financial events touch Orders and Items?** Logistics: **yes, explicitly** (policy “full operational involvement”). `Reserve Stock`, `Pack Package`, `Dispatch Package`, `Confirm Delivery` carry the Items and Orders they operationally involve, tagged `context_*`. Financial: `Issue Invoice` relates V1 **and both Orders** (a stated fact, bare `order`). `Record Payment` relates **only** its Payment and V1 — I deliberately do **not** propagate payments to Orders/Items, because the narrative gives no allocation of M1/M2 to O100/O200. That gap is a real analytical finding, not a bug.

**Preventing propagation from masquerading as observation.** Three mechanisms: (a) the `context_` qualifier prefix; (b) an extra, non-mandatory provenance column `ocel:relation_origin  {source, operational}` on `relations`, mechanically derived from the prefix and validated; (c) all containment facts used for propagation are *also* stored as first-class `o2o` rows, so any consumer can recompute or strip the operational layer (`relations[relations["ocel:relation_origin"] == "source"]`) and re-run discovery. No propagated row is ever silently indistinguishable from a source row.

**Version-dependent PM4Py assumptions.** `OCEL` is the dataclass `pm4py.objects.ocel.obj.OCEL` accepting the four denormalized DataFrames (pm4py’s in-memory OCEL repeats activity/timestamp in `relations`, unlike the normalized OCEL 2.0 SQLite/JSON encoding — the `events` table stays authoritative and consistency is asserted). `discover_etot` and `ocel_objects_interactions_summary` are recent APIs ( pm4py  2.7.13); they are called through a small availability guard that reports the version gap instead of silently changing semantics. The `OCEL(...)` construction is a single isolated line.

def validate(events: pd.DataFrame, objects: pd.DataFrame,
             relations: pd.DataFrame, o2o: pd.DataFrame) -> None:

    assert objects[OID].is_unique, "duplicate object IDs"
    assert events[TS].map(lambda t: t.tzinfo is not None).all(), "naive timestamps"

    eids, oids = set(events[EID]), set(objects[OID])
    assert set(relations[EID]) <= eids, "orphan event ID in relations"
    assert set(relations[OID]) <= oids, "orphan object ID in relations"
    assert set(o2o[OID]) <= oids and set(o2o[OID2]) <= oids, "orphan object ID in o2o"

    # activity / timestamp consistency between events and relations
    joined = relations.merge(events[[EID, ACT, TS]], on=EID,
                             suffixes=("_rel", "_evt"), validate="many_to_one")
    assert (joined[f"{ACT}_rel"] == joined[f"{ACT}_evt"]).all(), "activity mismatch"
    assert (joined[f"{TS}_rel"] == joined[f"{TS}_evt"]).all(), "timestamp mismatch"

    # object-type consistency between objects and relations
    typed = relations.merge(objects, on=OID, suffixes=("_rel", "_obj"),
                            validate="many_to_one")
    assert (typed[f"{OTYPE}_rel"] == typed[f"{OTYPE}_obj"]).all(), "object type mismatch"

    assert not relations.duplicated([EID, OID, QUAL]).any(), "duplicate E2O rows"
    assert not o2o.duplicated([OID, OID2, QUAL]).any(), "duplicate O2O rows"
    assert (o2o[OID] != o2o[OID2]).all(), "self-referencing O2O row"

    # coverage: no isolated event, no isolated object
    assert set(relations[EID]) == eids, "event without any object relation"
    assert set(relations[OID]) == oids, "object never touched by an event"

    # provenance contract
    assert ((relations[QUAL].str.startswith("context_")) ==
            (relations[ORIGIN] == "operational")).all(), "qualifier/provenance drift"

    # narrative spot checks
    assert len(events) == 17 and len(objects) == 12
    assert set(relations.loc[relations[EID] == "e06", OID]) == {"I1", "I3", "O100", "O200"}
    assert set(relations.loc[relations[EID] == "e07", OID]) == {"P1", "I1", "I3", "O100", "O200"}
    assert set(relations.loc[relations[EID] == "e11", OID]) == {"V1", "O100", "O200"}
    assert set(relations.loc[relations[EID].isin(["e12", "e15"]), OID]) == {"M1", "M2", "V1"}
    assert events["amount"].sum() == 250.0
    assert not relations.loc[relations[ACT] == "Record Payment", QUAL] \
                        .str.startswith("context_").any(), "fabricated payment allocation"
    print("[validation] all integrity and semantic checks passed "
          f"({len(events)} events, {len(objects)} objects, "
          f"{len(relations)} E2O, {len(o2o)} O2O)")


validate(events, objects, relations, o2o)

# ----------------------------------------------------------------------------------
# G. OCEL construction (VERSION-DEPENDENT LINE — isolated on purpose)
#    If your pm4py build exposes a different constructor, adapt ONLY this line,
#    e.g. OCEL(events=..., objects=..., relations=...) for pre-O2O versions,

- **Omitted:** which Orders are billed (O100, O200), deliveries, and the fact that the two payments are *different objects* M1/M2 with amounts 100/150.
- **DFG:** Issue InvoiceRecord Payment (1), Record PaymentRecord Payment (1).
- **Misleading:** a single case gives no variability and 100 %-confidence skeleton constraints; the self-loop reads as “payment repeated/retried” rather than two partial settlements; total 250 is only recoverable by summing the `amount` attribute, not from the DFG.

**Why Payment flattening is particularly weak.** Each Payment participates in exactly **one** event (`Record Payment`), so flattening yields two **singleton traces**: the DFG has *no edges*, start = end = `Record Payment`, and the log skeleton is degenerate. The payment lifecycle (invoice issued  partial  complete) lives on **V1** and on the `o2o` edges M1V1, M2V1, which flattening does not traverse. Payment is a *transactional* object, not a process carrier — a textbook case where object-centric analysis is mandatory.

## 5. Expected object-centric structures

**OC-DFG.** Six typed sub-graphs plus cross-type start/end annotations: `Order`: Create Order  Add Item  Reserve Stock  Pack Package  Dispatch Package  Issue Invoice  Confirm Delivery  Close Order; `Item`: Add Item  Reserve Stock  Pack Package  Dispatch Package  Confirm Delivery; `Package`: Pack  Dispatch  Confirm; `Delivery`: Dispatch  Confirm; `Invoice`: Issue Invoice  Record Payment (with a Record Payment self-edge); `Payment`: isolated node. The interesting signal is **edge counts per type diverging for the same activity pair**: `Pack Package` occurs 2× for Package but 3× for Order (e07 contributes O100 *and* O200) — the signature of **P1 combining two Orders**. `Reserve Stock` is a single event with 2 Order and 2 Item participations (convergence of I1 and I3). `Issue Invoice` shows 2 Order participations against 1 Invoice (**O100 + O200  V1**), and `Record Payment` shows 2 Payment participations against 1 Invoice (**M1 + M2  V1**), i.e. convergence in the financial branch that no single flattening reveals. `Close Order` appears twice with O200 preceding O100 — visible as independent per-object endings, not as a loop.

**OTG.** One connected component with two clusters joined by a bridge: logistics cluster {Order, Item, Package, Delivery} densely connected (Order–Item, Order–Package, Order–Delivery, Item–Package, Item–Delivery, Package–Delivery), financial pair Invoice–Payment, and the bridge edges **Order–Invoice** (from `Issue Invoice`). Notably **no Order–Payment edge**: under the chosen policy the interaction summary/OTG makes the *payment-allocation blind spot* structurally visible. V1 is the articulation point between logistics and settlement.

**ET–OT.** Bipartite event-type  object-type graph: Create Order/Close Order  {Order}; Add Item, Reserve Stock  {Order, Item}; Pack Package  {Order, Item, Package}; Dispatch Package, Confirm Delivery  {Order, Item, Package, Delivery}; Issue Invoice  {Order, Invoice}; Record Payment  {Invoice, Payment}. Reading degree: `Dispatch Package`/`Confirm Delivery` are the widest (4 types, true multi-object synchronization), `Record Payment` the narrowest (2). `Issue Invoice` is the only event type touching both an Order and a financial type — the hand-off point.

**Object-centric Petri net (not uniquely determined).** Expect places per type and transitions per activity, with **variable arcs** where cardinality > 1: `Reserve Stock` consuming two Item tokens (I1, I3); `Pack Package` consuming two Items and producing one Package for P1 versus one Item  one Package for P2; `Issue Invoice` consuming/reading two Order tokens (O100, O200) and producing one Invoice token V1; `Record Payment` producing a Payment token (M1, then M2) while touching V1. Genuine ambiguity remains and should be reported as such: whether V1’s token is *consumed* by each payment or *read/looped* (only M2 completes settlement — a data condition the net cannot express without the `amount` attribute); whether `Confirm Delivery` consumes the Package token or only the Delivery token; whether `Close Order` requires a payment-derived precondition (absent here by policy); and whether silent transitions are inserted to reconcile the 1-vs-2 cardinalities. Different discovery settings yield different but equally defensible nets; the *business story* (P1 merges O100/O200; V1 bills both; M1+M2 = 250 settle V1; O200 closes before O100) is invariant.

**Object-interactions summary.** Expected non-zero pairs: **O100–O200 share 5 events** (e06, e07, e09, e11, e13) — quantified cross-order coupling; I1–I3 share 4 (Reserve, Pack P1, Dispatch P1, Confirm D1); O100–I1/I2 rich; O200–I3 rich; P1–D1 = 2, P2–D2 = 2; V1–O100 = V1–O200 = 1 (Issue Invoice only); **M1–V1 = 1, M2–V1 = 1, but M1–M2 = 0** — the two payments never co-occur in one event, so their convergence is *only* observable through V1. Likewise **I2–I3 = 0** and **P1–P2 = 0**: the two logistics branches never touch directly; they meet only at V1 (and, for O100, inside its own trace).

## 6. Modeling alternatives

1. **Source-minimal E2O** (drop all 19 `context_*` rows; keep only stated subjects). `Reserve Stock` touches only I1/I3; `Pack Package` only Package+Item; `Dispatch`/`Confirm` only Package+Delivery. Order traces shrink to Create Order  Add Item(×k)  Issue Invoice  Close Order (5 events for O100, 4 for O200); OTG loses Order–Package and Order–Delivery, leaving Order–Item, Order–Invoice, Invoice–Payment plus a separate Item–Package–Delivery chain; the OC-DFG’s Order path no longer contains logistics, and cross-order convergence is visible **only** at `Issue Invoice`. Same business story, but logistics performance can no longer be attributed to Orders without joining `o2o` at query time.
2. **Full operational involvement (chosen).** Logistics events carry Items and Orders explicitly with `context_*` + provenance. Order flattening becomes an end-to-end order-fulfillment view; OTG becomes densely connected; the OC-DFG exposes P1’s cross-order merge as a frequency asymmetry. Cost: 19 derived rows and duplicated shared events after flattening — mitigated by the provenance flag.
3. **O2O-propagated analytical closure** (transitively propagate everything, including payments: M1/M2  V1  O100/O200  I1…I3). `Record Payment` would then touch Payment, Invoice, Order, Item; Order traces gain both payments (14 / 10 events), an Order–Payment OTG edge appears, and the OC-DFG shows settlement inside the order path. But it **fabricates** an allocation: it asserts that M1’s 100 and M2’s 150 each settle *both* orders, which the narrative never states, and it inflates relations far beyond observed participation. Defensible only as an explicitly labelled *analytical view* (`relation_origin="analytical"`), never as the source log.
4. **Logistics-only propagation** (keep `context_item`/`context_package`, drop `context_order`). Item and Package views stay end-to-end, Order traces stop after `Add Item` and resume at `Issue Invoice`; the OTG keeps Item–Package–Delivery but loses Order–Package/Delivery. Useful when order-level logistics KPIs are considered unreliable because of shared packages — again the same story, a different analytical lens.

## 7. Failure modes

1. **Relation inflation.** Blanket propagation (alternative 3) multiplies E2O rows, makes every event “touch everything”, and turns the OC-DFG/OTG into a near-complete graph with no discriminating power. Mitigation: cap propagation at containment known at event time, count `source` vs `operational` rows (30/19 here).
2. **Missing direct E2O links.** Source-minimal logs make `ocel_flattening(ocel, "Order")` skip packing/dispatch entirely; an analyst concludes “orders are never shipped”. Mitigation: `ocel_object_type_activities` audit + `o2o`-aware queries.
3. **Treating O2O propagation as observation.** Derived rows without provenance get quoted as “the WMS recorded O200 at pack time”. Mitigation: `context_*` prefix + `ocel:relation_origin`, validated for drift, plus a documented strip-and-rediscover recipe.
4. **Duplicate shared events after flattening.** e06/e07/e09/e11/e13 appear in both Order traces: 15 distinct events become 20 rows; frequencies, throughput times and conformance counts are inflated, and divergence-induced self-loops (`Add Item`, `Pack Package`, `Dispatch Package`, `Confirm Delivery`) get misread as rework. Mitigation: report distinct-event counts alongside flattened counts; use the OC-DFG for cardinality.
5. **Ambiguous payment allocation.** 100 + 150 = 250 settles V1, but no split between O100 and O200 is given. Propagating payments to Orders silently invents an allocation and can “prove” that O200 was fully paid before it closed. Mitigation: keep payments on {Payment, Invoice}; expose the missing Order–Payment OTG edge as a data-quality finding.
6. **Overly short Payment traces.** Payment flattening gives two singleton traces, an edgeless DFG and a degenerate skeleton; any “payment process model” built from it is meaningless. Mitigation: analyze settlement on Invoice or via M1V1/M2V1 O2O plus the `amount` attribute.
7. **Constructor / API version mismatch.** Older pm4py `OCEL` has no `o2o`; `discover_etot` / `ocel_objects_interactions_summary` may not exist; some builds expect `pm4py.objects.ocel.obj.OCEL` vs a re-export. Mitigation: the single isolated `OCEL(...)` line, the `optional_api` guard, and no semantic edits to the tables.
8. **False total order for same-time events.** This log has no ties, but a naive pipeline that sorts by timestamp alone (or assigns integer indices) can fabricate a strict sequence between simultaneous events, or between events sharing an object only via propagation. Mitigation: stable sort on `(timestamp, eid)` (as in the code), never infer causality from order alone; the net/OC-DFG should treat co-timed events as potentially concurrent.
9. **Naive timestamps / mixed timezones.** `pd.Timestamp` without `tz` breaks cross-day comparisons (D2 confirmation, M2) and pm4py performance annotations. Mitigation: `utc()` helper + tz assertion.
10. **Denormalization drift.** `relations` activity/timestamp copied by hand diverge from `events` after an edit, producing phantom activities in flattening. Mitigation: relations generated from the event spec and re-validated by merge.
11. **Amount modeled as an object.** A “Money 100” object would create fake shared objects between M1 and other events and pollute the OTG. Mitigation: `amount` stays an event attribute.
12. **Skeleton overfitting.** Invoice has 1 trace, Delivery/Package 2; log-skeleton constraints hold with trivial support and look like strong business rules. Mitigation: always print trace counts next to skeleton output.

## 8. Final semantic checks

A reviewer can verify the narrative directly in the four tables:

1. **Sizes:** `events` = 17 unique eids (e01–e17), `objects` = 12 unique oids across 6 types, `relations` = 49 rows (30 `source` + 19 `operational`), `o2o` = 12 rows.
2. **Shared reservation:** e06 `Reserve Stock` relates exactly {I1, I3, O100, O200}, with I1/I3 as `item` and both Orders as `context_order` — one event, two Orders.
3. **Cross-order package:** e07 relates P1 with I1 **and** I3; joining `o2o` `contains` shows I1O100 and I3O200, i.e. P1 genuinely mixes two Orders; e08 relates P2 with I2 only (O100 only).
4. **Delivery chain:** e09/e13 pair D1 with P1; e10/e14 pair D2 with P2; `o2o` has D1P1 and D2P2 (`carries`), and no D1–P2 or D2–P1 relation anywhere.
5. **Invoice convergence:** e11 relates exactly {V1, O100, O200} with bare `order` qualifiers, and `o2o` contains V1O100 and V1O200 (`bills`); e11 touches no Item/Package/Delivery.
6. **Payments as attributes, not objects:** e12 `amount` = 100.0 with {M1, V1}; e15 `amount` = 150.0 with {M2, V1}; sum = 250; no Order/Item rows on either payment event; `o2o` has M1 `partially_settles` V1 and M2 `completes_settlement` V1.
7. **Closure order and timing:** e16 `Close Order` on O200 at 2026-04-07 10:30 UTC precedes e17 on O100 at 10:35 UTC; e14 (D2) and e15 (M2) fall on 2026-04-07 while all others are on 2026-04-06; all timestamps are UTC-aware.
8. **Denormalization integrity:** for every relation row, (`ocel:activity`, `ocel:timestamp`) equals the row of the same eid in `events`, and `ocel:type` equals the object’s type in `objects`; no duplicate (eid, oid, qualifier) triples; every event has 1 relation and every object is touched 1 time.
9. **Provenance contract:** `ocel:qualifier.startswith("context_")` is true exactly where `ocel:relation_origin == "operational"`, so the derived layer can be removed with one filter without touching a single source fact.
