## 1. Consistency rules and evidence model

We treat the domain semantics as defeasible, weighted evidence rather than axioms. Repairs are abductive: we infer missing relations that best explain the observations without creating stronger commitments than warranted.

**Hard invariant** - violations reject a repair outright:
- Referential integrity: every `ocel:eid` / `ocel:oid` must exist.
- Type compatibility: no cross-type nonsense (e.g., `Record Payment` cannot relate to `Package` as its primary payment object).
- Directionality of O2O: `DEL-X carries PK-7` is not interchangeable with `PK-7 carries DEL-X`. We must not invent reverse edges.
- Temporal monotonicity: an object's lifecycle cannot go backward. `Pack Item` cannot occur before `Add Item` for the same `Item`; `Dispatch Package` cannot precede `Pack Item` for the same `Package`. Timestamps are taken as observed truth; we do not rewrite them.
- No invention: no new events or objects to complete lifecycles.

**Strong default** - expected cardinality, override only with a specific alternative mechanism documented in the semantics:
- `Create Order`: exactly one `Order`.
- `Add Item`: one `Order` + one `Item`.
- `Pack Item`: one `Item` + one `Package`. Exception allowed: scanner outage  item-only `Pack Item` row reconciled later (ev08 is candidate).
- `Dispatch Package`: one `Package` + one `Delivery`. Exception: bulk dispatch covering multiple packages.
- `Issue Invoice`: one `Invoice` + one or more `Orders`.
- `Record Payment`: exactly one `Payment` + normally one `Invoice`. Exception: unapplied cash (no invoice).
- `Confirm Delivery`: variable 1..n `Delivery` or 0 (customer/order only) if portal loses carrier identifier.

A deviation without an explicit mechanism is evidence *against* that repair.

**Weak heuristic** - corroborating but not decisive alone:
- Identifier similarity: `scanner_ref=PK8-2`  `PK-8`; `external_ref=N-421?`  `DEL-Y` (`carrier_ref=N-421`); `N-42*` prefix overlap; `bank_ref` match.
- Time proximity: ev07 (09:04) / ev08 (09:05) cluster; ev09/ev10 both 10:00  parallel dispatch intended.
- Amount/customer/route: `declared_value` 130+100 =230 corresponding to `INV-44 total=230`; `customer=C17` shared; `route_hint=NORTH` shared by PK-7/PK-8 and `route=NORTH` for DEL-X/DEL-Y; `gross_weight` plausibility; `order_hint` attribute.
- These are treated as Bayesian cues. Crucially, arithmetic equality of `130+100=230` and `PAY-1=100, PAY-2=130` is *evidence, not proof*: fees, discounts, taxes or coincidence can produce the same sum, and a customer can have multiple open invoices.

**Evidence against a repair**:
- Scanner-outage rule legitimizes ev08 as item-only, against inferring PK-8.
- Bulk-dispatch rule legitimizes ev10 as multi-package event, against 1:1 split.
- Portal-loss rule legitimizes ev11 as order-only, against forcing a delivery link.
- Unapplied-cash and multi-order invoicing alternatives undermine financial linkage.
- Weight ambiguity: `PK-8 gross_weight=2.9` vs `PK-7=3.1` for one item does not distinguish one vs. two light cables without a bill of materials.
- Singleton anomalies: creating a 2:1 `Package` containing items from two orders (`IT-A2` from ORD-A + `IT-B1` from ORD-B) is operationally possible (zone pooling) but creates a many-to-one crossing that changes order lifecycles substantially; needs independent confirmation.

**Combination strategy**:
Corroboration requires *independent* E2O and O2O support and lifecycle order. We combine cues conjunctively but penalize *circularity*: inferring `O2O PK-8 packs IT-B1` solely because we assumed `E2O ev08  PK-8` and then treating that O2O as independent confirmation is circular. True independent O2O evidence would be a separate system assertion, weight scan, or repeated co-occurrence, none of which exists here. Identifier and time cues are down-weighted if they share a single source field (e.g., `scanner_ref` used for both E2O and O2O). Cardinality and lifecycle order act as gatekeepers: a proposal passing weak heuristics but violating a strong default without invoking its licensed exception is rejected. Confidence is calibrated to the weakest needed independent piece, preserving `unresolved` rather than forcing completeness.

## 8. Over-repair warnings

1. **Inventing a mixed-order package without weight confirmation**: Asserting `PK-8 packs IT-B1` definitively creates a 2-item, 2-order package. If `gross_weight 2.9` actually reflects one cable not two, the Package flattening will show false co-location, leading to incorrect cubing, shipping-cost allocation and false OC-DFG edge `Add Item (ORD-A)`  `Dispatch (ORD-B)` via the same package.

2. **Forcing exclusive Confirm Delivery assignment**: Linking `ev11` solely to `DEL-X` (or `DEL-Y`) because `N-42*` superficially matches `N-420` ignores portal-loss semantics. This would fabricate a clean `Dispatch  Confirm` lifecycle for one delivery while leaving the other permanently unconfirmed, biasing delivery-performance metrics and masking a potential failed or pending delivery of the second NORTH shipment.

3. **Treating amount equality as invoice proof**: Adding `INV-44 bills ORD-B` because `130+100=230` assumes no fees, discounts or taxes and that `declared_value` equals invoice line amount. This duplicates `Issue Invoice` across flattened Order logs, inflates billed-order throughput, and creates a false OTG Invoice-Order many-to-many that downstream order-to-cash mining will interpret as intentional order consolidation.

4. **Closing the payment cycle with complementary amounts**: Adding `PAY-2 settles INV-44` because `100+130=230` eliminates the legitimate unapplied-cash scenario. In the flattened Payment/Invoice view this falsely marks INV-44 as fully settled, hides outstanding receivables risk, and adds a spurious `Issue Invoice  Record Payment` edge counted twice, distorting collection cycle-time and payment-behavior clustering.

5. **Bulk-dispatch merging of distinct deliveries**: Repairing `ev10DEL-X` and `DEL-X carries PK-8` as a bulk dispatch would merge two carrier references (`N-420` vs `N-421?`) into one Delivery. This destroys the parallel-shipment variant visible in the 10:00 dual dispatch, collapses the OTG Delivery-Package 1:1 pattern into a false many-to-one, and causes delivery flattening to undercount northbound shipments.

6. **Using derived O2O as independent validation**: Treating an O2O edge inferred from an assumed E2O (e.g., proposing `PK-8 packs IT-B1` then citing that O2O as confirmation that `ev08PK-8` is correct) is circular.
