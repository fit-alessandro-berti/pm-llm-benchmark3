

## 1. Analytical assumptions

In this context, a "case notion" refers to the specific object type selected to define unique case identifiers during the flattening process. "Convergence" occurs when multiple distinct objects (e.g., O2 and O3) map to the same case ID (e.g., V2) based on shared relations, potentially merging independent business streams into one trace. "Divergence" happens when a single object (e.g., O1) relates to multiple instances of the chosen case type (e.g., P1 and P2), fragmenting one logical process into parallel traces.

I treat copied shared events as evidence duplication. While copying ensures every relevant object sees the activity, it inflates frequency metrics and distorts process models by making events appear multiple times across different traces. I permit analytical transformations such as relation propagation through O2O links (e.g., inferring that O1 relates to D1 via P1) to complete lifecycles, but I require these to be explicitly noted as derived data to distinguish them from direct Event-Object evidence.

## 3. Concrete distortion analysis

1.  **Cross-order package P3:** Flattening on Package merges O2 and O3. Event `Pack Package` (e13) links both orders. In a Package-based view, O2's creation (e02) and O3's creation (e03) appear in the same trace. This distorts the process by implying a joint business decision for unrelated orders, inflating perceived process complexity. This is context-dependent (informative for logistics, harmful for customer service analytics).
2.  **Cross-order package P4:** Similar to P3, P4 packs items from O3 and O4. Event e14 relates to both. Flattening on Package creates a trace that spans two separate contractual agreements. This creates a "merged case" where closing events (e30, e31) occur in the same lifecycle. This is informative for warehouse throughput but distorts order-level KPIs.
3.  **Consolidated delivery D2:** D2 carries P2 and P3, involving O1, O2, and O3. Event `Dispatch` (e16) references all three orders. Flattening on Delivery creates a single massive trace combining three distinct business cases. This risks performance bias by inflating delivery duration metrics; the start time depends on the earliest order (O1) and end on the latest confirm. This is harmful for accurate order lead time calculation.
4.  **Consolidated invoicing V2:** V2 bills O2 and O3. Event `Issue Invoice` (e19) relates to both. Flattening on Invoice merges the financial lifecycle of two orders. This hides the specific payment triggers for each order if the Invoice is viewed in isolation. This is informative for revenue recognition but distorts individual order payment cycle times.
5.  **Partial payments M2/M3:** Invoice V2 is settled by M2 (partial) and M3 (complete). Flattening on Payment splits this into two distinct cases. The `Record Payment` events (e22, e25) appear in separate traces. This creates a "short lifecycle" for each payment object, losing the view that they collectively settle one invoice. This is informative for cash flow but distorts the invoice settlement timeline.
6.  **Near-singleton lifecycle I11:** Item I11 relates directly only to Add Item, Pack, Dispatch, and Confirm events. If O2O propagation is not applied, I11's trace starts at 09:15 (e05) rather than 09:00 (e01, Create Order). This artificially truncates the lifecycle by 15 minutes, biasing "time in system" metrics. This is informative for item-level tracking but harmful for end-to-end order analysis.
7.  **Event duplication e16:** `Dispatch` event e16 involves O1, O2, O3. In an Order-based flattened log, this activity appears three times. This creates a false frequency spike in the process model. It suggests `Dispatch` happens more often than it physically does, confusing the DFG edge counts. This is harmful for operational efficiency analysis.
8.  **Lifecycle fragmentation O1:** O1 items are packed separately (P1, P2). In a Package-based view, O1 appears in two cases (P1 trace, P2 trace). O1's `Close Order` event (e28) only attaches to one or is lost if not propagated. This risks truncating the lifecycle for one of the package traces. This is informative for logistics but distorts the completion status of the original business case.

## 4. Traditional versus object-centric analysis portfolio

For robust analysis, we should create at least two traditional flattened logs: Order and Invoice. The Order log answers questions about end-to-end customer experience, such as "What is the total time from Create Order to Close Order?" It safely supports frequency analysis on creation and closure activities. The Invoice log answers financial questions, such as "How long does it take to settle an invoice after issuance?" It safely supports payment split analysis without the noise of physical packing.

Questions requiring Object-Centric (OC) graphs include multi-party coordination and resource utilization. For instance, analyzing how P3 serves both O2 and O3 requires an Object Interaction Graph (OTG) or Object-Centric DFG (OC-DFG) to visualize the split and merge. Questions about delivery consolidation (D2) require an Event-Object-Object graph (ET-OT) to trace how one activity impacts three business cases. These require object interaction summaries rather than linear traces.

To reconcile contradictory findings, we prioritize the Order view for KPI dashboards and the OC view for process discovery. If the Order view shows long cycle times due to waiting for packing, we switch to the OC view to isolate whether the bottleneck is at P1, P2, or P3. We use frequency metrics from the OC-DFG to adjust counts in the flattened view, reducing the impact of copied events. For example, we count e16 once in the total process, despite appearing thrice in the Order log. This ensures high-level metrics reflect reality, even if individual traces are technically fragmented.

## 5. Lead-object decision

**Position B: Use a primary lead object plus explicitly secondary lifecycles.**

**Decision criteria:** The lead object must maximize trace coverage while minimizing artificial fragmentation or merging of distinct business contracts. It must reflect the central entity driving the process.

**Strongest supporting evidence:** Orders (O1-O4) drive all other activities. Every event relates to at least one Order (directly or indirectly). Flattening on Order preserves the creation (e01-e04) and closing (e28-e31) events essential for lifecycle closure. While splits occur (e.g., O1 to P1/P2), they represent logical parallelism rather than merged business cases.

**Strongest counterargument:** Consolidated objects like V2 and D2 create significant divergence. Flattening on Order hides the merged financial view of O2 and O3 (V2) and the merged delivery view (D2). An Order-only view cannot answer "How often do we consolidate shipments?" or "How often do we combine invoices?"

**Residual risk:** If secondary views are not modeled, financial or logistics analysts may draw incorrect conclusions from the Order log, such as assuming every order has a unique invoice.

**Conditions for change:** If the business goal shifts entirely to warehouse optimization (ignoring customer contracts), Delivery would become the lead. If the goal shifts to accounting compliance, Invoice would dominate. Currently, the order-fulfilment context prioritizes the customer contract (Order) as the primary anchor.

## 7. Sensitivity and validation plan

First, perform a **copied event removal test**. We will remove all events that relate to more than one object (e.g., e16, e19) and re-calculate the frequency of "Dispatch" and "Issue Invoice" activities. If the DFG shows a significant drop in frequency, the original model is heavily distorted by duplication. We will document the difference in edge weights.

Second, we will conduct a **relation propagation test**. We will generate two OC-DFG variants: one using only direct E2O relations and one propagating relations through O2O links (e.g., connecting O1 to D1 via P1). We will compare the start and end activities of the O1 lifecycle in both graphs. If the start activity changes from "Create Order" to "Add Item" in the direct variant, we quantify the lifecycle truncation error.

Third, we will execute a **lead object swap test**. We will flatten on Package and compare the trace lengths against the Order-flattened log. Specifically, we will check the number of "Close Order" events visible in the Package log versus the Order log. If the Package log misses closing events (e.g., e28, e30), we will flag it as incomplete for business process analysis.

Finally, we will perform a **frequency metric reconciliation**. We will calculate "events per case" using the total events in the flattened log versus unique events in the OC-DFG. If the flattened log shows 30 events and the unique count is 28 (due to e16 and e19 copying), we will note the inflation factor. This allows us to normalize performance metrics (like cost per case) when reporting to stakeholders.
