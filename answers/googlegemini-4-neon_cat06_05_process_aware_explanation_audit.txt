## 2. Process-model consistency checks

To prevent leaked, impossible, or semantically misread features and explanations from reaching production, deploy a six-part automated validation suite across both training/scoring pipelines and explanation outputs.

### 1. Prefix-time availability checks (strict `t0` cut-off)
- **Check:** For every case, anchor `t0` at the timestamp (and deterministic sequence index) of the first `Coverage Check Completed` event. Assert that every event, attribute, join key, and feature snapshot satisfies `feature_available_at <= t0` (with zero forward tolerance; replace `±5 min` with `[t0 - 5 min, t0]`).
- **Mechanism:** Enforce schema-level lineage metadata (`event_timestamp`, `ingestion_timestamp`, `as_of_timestamp`, `is_immutable`) in the feature store and run an automated **prefix-replay invariance test**: execute feature extraction on an event stream truncated at `t0` and compare bit-for-bit against features extracted from the closed warehouse record. Any non-zero diff automatically flags complete-trace or mutable-field leakage (catching `prior_claim_count_before_t0`, `same_day_document_count_snapshot`, `risk_score_current`, `final_handler_team`, and `employee_experience`).

### 2. Activity-order feasibility checks
- **Check:** Validate both full historical logs (for training integrity) and any sequence patterns emitted by explainers against the normative process specification.
- **Mechanism:**
  - **Data-aware alignment checking (Petri net / BPMN with guards):** Computes optimal alignments between each trace and the normative model. Flags violations such as any activity occurring after `Claim Closed`, `Appeal` occurring without a prior `Settlement Decision Recorded`, or `Damage Assessment Completed` occurring before `Coverage Check Completed`.
  - **Declarative rules (Declare / LTL with data):** Encode targeted invariants cleanly without over-constraining parallel branches (such as `Fraud Investigation`):
    - `Not-Succession(Claim Closed, AnyActivity)` — terminal closure constraint.
    - `Precedence(Coverage Check Completed, Damage Assessment Completed)` — minimum prerequisite.
    - `Precedence(Documents Requested, Documents Received)` and `Precedence(Documents Received, Documents Validated)` — evidence-cycle integrity.
- **Role & limitations of methods:**
  - *DFG (Directly-Follows Graph)* checks are fast for exploratory triage, **but a frequent DFG edge is not a normative rule**. Systematic logging bugs or tied timestamps can generate high-frequency spurious DFG edges (like `Claim Closed -> Damage Assessment Completed`), and DFGs collapse concurrency and long-range dependencies.
  - *Footprint matrices* (`->`, `#`, `||`) quickly flag impossible direct orderings but fail when coarse activity labels repeat (e.g., two `Settlement Decision Recorded` events) or when legality depends on payload data (`Partial`/`Deny`).
  - *Alignments* accurately handle loops and parallelism (`Fraud Investigation`) but are computationally heavier and require explicit data guards to validate decision outcomes.

### 3. Same-timestamp ambiguity detection
- **Check:** Scan all traces for adjacent events where `timestamp(e_i) == timestamp(e_{i+1})`.
- **Mechanism:**
  - Verify whether a monotonic, source-generated `sequence_index` exists to break ties deterministically.
  - Where `sequence_index` is missing (as in Case Z’s `Claim Closed` and `Damage Assessment Completed`), **do not** serialize ties using arbitrary ingestion or alphabetical order. Instead: (a) treat tied events as a partial order / simultaneous set, (b) check whether exactly one permutation conforms to the normative model (e.g., `Damage Assessment Completed -> ... -> Claim Closed`), and (c) quarantine unresolved ambiguities from sequence-pattern mining and flag affected records for data-engineering remediation.
  - Crucially, if a tie occurs *at* `t0` (e.g., `Coverage Check Completed` and a downstream activity share the same timestamp), exclude the ambiguously simultaneous downstream event from the `t0` prefix to prevent silent look-ahead leakage.

### 4. Complete-trace feature contamination tests
- **Check:** Detect features or explainers that inspect anything beyond the prefix ending at `t0`.
- **Mechanism:**
  - **Static lineage gate:** Reject features aggregated across `case_id` without a `WHERE event_time <= t0` predicate or derived from closure-only warehouse tables (`final_*`, `last_*`, `total_*`, `*_anywhere`, `full_trace_*`).
  - **Counterfactual future-perturbation test:** Take valid closed cases, synthetically alter their *post-`t0`* suffix (e.g., add an `Appeal`, change `final_decision`, extend closure by 10 days, reassign to SIU), and recompute all model inputs and SHAP values at `t0`. Any feature whose value changes—or whose attribution shifts—fails the test with immediate build failure.

### 5. Explanation-activity reachability classifier at `t0`
- **Check:** Every activity, edge, or sequence pattern referenced in a global or local explanation must be classified against the normative process state immediately after `t0`:
  1. **Observed in prefix (`<= t0`):** Admissible in `t0` explanations (e.g., `Claim Registered -> Coverage Check Completed`).
  2. **Enabled next at `t0`:** Normatively reachable immediately after `t0` (e.g., `Documents Requested`, `Damage Assessment Completed`, or `Fraud Investigation Opened` if triggered), **inadmissible** as an observed input feature or past-event explanation at `t0` (may only be mentioned qualitatively as a *hypothetical future risk pathway*).
  3. **Future-possible (not yet enabled at `t0`):** Reachable only after intervening steps (e.g., `Appeal -> Settlement Decision Recorded`, `Damage Assessment Completed -> Settlement Decision Recorded`). **Strictly inadmissible** as a feature or explanation at `t0`.
  4. **Normatively impossible:** Violates process constraints regardless of time (e.g., `Claim Closed -> Damage Assessment Completed`). **Strictly inadmissible**; triggers an upstream event-log defect alert.

### 6. Semantic validation of repeated `Settlement Decision Recorded` events
- **Check:** Distinguish legitimate appeal-driven reconsiderations from duplicate logging or unauthorized rework.
- **Mechanism:** Use a **data-aware declarative rule** rather than a naive activity-count or footprint rule:
  - Let $D_1, D_2, \dots, D_k$ be occurrences of `Settlement Decision Recorded`.
  - For every $j \ge 2$, verify that there exists an `Appeal` event strictly between $D_{j-1}$ and $D_j$, AND that the outcome attribute of $D_{j-1}$ is in `{"Partial", "Deny"}`.
  - If $D_{j-1}$ was `"Approve"` or `"Withdrawn"`, or no intervening `Appeal` exists, flag the trace as a conformance anomaly (or duplicate event record) rather than a valid appeal loop.
  - Note that this check applies to historical log hygiene and downstream-checkpoint models; at `t0`, *no* `Settlement Decision Recorded` event should appear in the feature set at all.

## 3. Alternative feature interpretations

Auditing predictive process models requires separating four distinct evidentiary standards:
- **Predictive validity:** Is the signal genuinely available at `<= t0` and stably associated with future 10-day breach out-of-time?
- **Causal interpretation:** Would intervening on this variable change breach probability (requires causal identification/confounding control, not SHAP importance)?
- **Operational actionability:** Can a claims team legitimately act on the signal to reduce breach risk (e.g., load balancing, proactive triage)?
- **Fairness review:** Does using the signal proxy protected or socioeconomic traits in ways that create unjustified disparities in service speed or scrutiny?

Below is the classification of all surviving or repairable signals (excluding permanently banned complete-trace/target leaks such as `total_case_duration_hours`, `appeal_seen_anywhere`, `num_document_requests_total`, `full_trace_variant_id`, `final_decision`, and all five post-`t0` sequence patterns).

### 1. Defensible predictive signal
- **Features:** `initial_damage_complexity` (currently valid); plus, *only after lineage repair/verification* (see Class 5), `prior_claim_count_before_t0`, `same_day_document_count_at_t0`, `initial_reserve_at_t0`, `handler_team_at_t0`, `resource_role_at_t0`, and `employee_experience_at_t0`.
- **What may be claimed:** At `t0`, higher recorded damage complexity (and, once verified, higher initial financial severity or prior claim history) is statistically associated with higher 10-day breach probability—useful for early risk stratification and triage routing.
- **What may not be claimed:** Do not claim that the label itself *causes* the delay (e.g., downgrading a complexity tag will not make the claim settle faster), nor treat predictive attribution as proof of claimant fault or fraud.

### 2. Process-state or congestion signal
- **Features:** `queue_length_at_t0` (after clamping join tolerance to `[t0 - 5 min, t0]`), `elapsed_since_registration_at_t0`.
- **What may be claimed:** Both capture legitimate operational state at `t0`. Higher `queue_length_at_t0` reflects real-time workload congestion associated with longer waiting times for downstream evidence handling or assessment. Higher `elapsed_since_registration_at_t0` arithmetically reduces remaining slack under the 10-day SLA clock and may also reflect early intake bottlenecks. These are strong candidates for **operational actionability** (e.g., capacity reallocation or SLA-at-risk prioritization).
- **What may not be claimed:** Do not claim a guaranteed unit causal effect (e.g., “reducing queue length by 5 guarantees a X% drop in breach probability”) without controlling for shared drivers such as catastrophe surges or seasonal claim-mix shifts that simultaneously raise queue length and claim complexity.

### 3. Proxy requiring fairness/robustness review
- **Features:** `claimant_region`, `claimant_channel` *(subject to confirming `claimant_channel` is immutable at registration)*.
- **What may be claimed:** These attributes correlate with observed turnaround differences—potentially capturing real operational asymmetries such as local repair-network capacity, intermediary documentation workflows, or language-support friction. Retaining them during auditing can help surface regional service deficits rather than hiding them.
- **What may not be claimed:** Never present region or channel as a direct causal “delay driver” or blame claimants/brokers for breaches. Do not use these proxies to justify adverse actions (such as deprioritizing high-risk regions or triggering extra scrutiny) without formal disparate-impact testing and replacing coarse geographic proxies with direct operational capacity measures wherever possible.

### 4. Drift/calendar proxy
- **Features:** `calendar_week`.
- **What may be claimed:** Calendar timing captures non-stationary contextual factors—specifically holiday staffing reductions and the timing of an operating-policy change—that shifted historical breach rates during specific weeks.
- **What may not be claimed:** Do not claim that a given week number is intrinsically “operationally worse” or expect last year’s policy-change weeks to repeat with the same effect next year. Calendar proxies fail under regime change and should be replaced by explicit business-day/holiday capacity features and policy-version indicators rather than surfaced as root-cause explanations.

### 5. Unusable until lineage is repaired
- **Features:**
  - `prior_claim_count_before_t0` (SQL bug uses `<= extraction_date` instead of `< t0`).

- **What may be claimed:** Nothing in production today. These features must be excluded from scoring and explanations until point-in-time lineage is engineered, backfilled, and verified via prefix-replay tests.
- **What may not be claimed:** Do not treat partial overlap with `t0` values (such as `final_handler_team` matching ~65% of the time) as “good enough,” because the mismatched subset is systematically concentrated in escalated and breaching claims, severely inflating apparent predictive power.

## 5. Recommendations for explanation validation

Execute the following prioritized remediation plan before redeploying the predictive process monitoring model or surfacing explanations to claims handlers.

### Priority 0 — Immediate Containment (Stop-Ship)
1. **Halt production use of current scores and explanations:** Withdraw the current model and sequence explainer from operational dashboards; its performance is artificially inflated by target leakage (`total_case_duration_hours`) and complete-trace leakage (`appeal_seen_anywhere`, `full_trace_variant_id`).
2. **Enforce strict prefix-only recomputation tests:** Build an automated CI/CD gate that truncates historical traces at `t0` (`Coverage Check Completed`), recomputes all features and explanations from the truncated event stream, and fails the build if any value differs from the offline training table or changes under synthetic post-`t0` suffix perturbations.

### Priority 1 — Data Lineage, Feature Store, and Conformance Engineering
3. **Redesign the feature store for point-in-time correctness:**
   - Separate immutable event-sourced attributes (e.g., `initial_damage_complexity`) from time-varying entities (reserves, risk scores, handler teams, roles, employee tenure) stored as append-only slowly changing tables with explicit `effective_from` / `available_at` timestamps.
   - Standardize offline/online point-in-time joins (`ASOF JOIN` with `feature.available_at <= case.t0`), eliminating extraction-date joins (`prior_claim_count_before_t0`, `employee_experience`), nightly overwrite snapshots (`same_day_document_count_snapshot`), and forward-looking tolerances (`±5 min` tightened to `[t0 - 5 min, t0]`).
4. **Mandate historical feature timestamps and event sequence indices:**
   - Require every feature table to carry an auditable `feature_timestamp` and every event-log source to emit a monotonic `sequence_index`.
   - Quarantine same-timestamp ties lacking a sequence index so they cannot fabricate impossible transitions (`Claim Closed -> Damage Assessment Completed`).
5. **Embed automated process-conformance tests into the explanation pipeline:**
   - Run alignment and data-aware declarative checks (`Not-Succession(Claim Closed, Any)`, `Appeal` legality conditioned on `Partial`/`Deny`, valid repeated `Settlement Decision Recorded` semantics) on event logs before training.
   - Add an **explanation reachability filter** that blocks any explanation citing activities that are future-possible, merely enabled, or normatively impossible at `t0`.

### Priority 2 — Model Retraining, Calibration, and Explanation Rigor
6. **Retrain and recalibrate after removing leaked features:**
   - Expect a substantial drop in apparent ROC-AUC/PR-AUC once leakage is removed—treat this as uncovering true early-stage predictability rather than a regression.
   - Evaluate strictly on **out-of-time splits** (spanning before and after policy changes and holiday periods) to expose `calendar_week` overfitting.
   - Recalibrate probabilities (e.g., isotonic or Platt scaling on an out-of-time calibration fold), verify calibration across key subgroups (`claimant_region`, `claimant_channel`, complexity tiers), and re-optimize operational alert thresholds against realistic SLA intervention costs.
7. **Validate explanation stability and correlation behavior:**
   - Measure global and local explanation stability across bootstrap resamples and rolling time windows (e.g., rank correlation of top drivers and variance of local SHAP attributions).
   - Because features such as `claimant_region`, `claimant_channel`, `initial_damage_complexity`, and `initial_reserve` are correlated, compare observational vs. conditional/grouped attribution methods so correlated proxies do not arbitrarily swap importance across retrains.
   - Enforce an explanation style guide separating **predictive cues** from **causal claims**; require causal inference or controlled operational pilots before presenting any feature as an actionable lever.

### Priority 3 — Fairness Governance and Continuous Monitoring
8. **Conduct proxy and fairness analysis before operationalizing triage:**
   - Audit error rates (false-positive/false-negative rates), calibration, and downstream intervention allocation across `claimant_region` and `claimant_channel` (and linked socioeconomic/language proxies).
   - Where `claimant_region` proxies legitimate operational constraints (e.g., repair-network bottlenecks), prioritize replacing it with direct, actionable operational capacity metrics rather than relying on coarse geographic labels.
   - Define governance rules restricting how breach predictions may be used (e.g., permissible for proactive resource allocation and SLA support; impermissible for punitive claim handling or coverage decisions).
9. **Monitor continuously for schema, lineage, and process drift:**
   - Track input feature distributions, missingness, `available_at` lag, timestamp-tie rates, missing `sequence_index` rates, and prefix-conformance violation rates in production.
   - Monitor rolling Brier score/calibration drift, process-variant drift (e.g., changes in fast-track vs. evidence-cycle rates or policy-regime shifts), and explanation-attribution drift to detect silent warehouse schema changes or operational regime breaks early.
