## 2. Process-model consistency checks

A validation suite should combine static lineage analysis with formal conformance techniques:

**a. Prefix-time availability (lineage tagging).**
Every feature definition must carry metadata: `defining_event_time_bound` (max timestamp of any event referenced) vs. `extraction_time`. Automated CI should reject any feature whose SQL/ETL references an event timestamp, aggregation window, or join condition that is not provably `<= t0`. Naming conventions ("_total", "final_", "full_trace_") should trigger mandatory manual review, since they are common leakage smells.

**b. Activity-order feasibility (footprint + alignment checks).**
Encode the normative process (registration  coverage check  {fast track | evidence cycles}  damage assessment  [fraud investigation]  decision  [appeal  decision]  closed) as a Petri net or BPMN model. Use:
- **Footprint matrix** (directly-follows / never-follows / parallel relations) to quickly flag impossible pairs such as `Closed -> Damage Assessment Completed` (never a valid precedence).
- **Alignment-based conformance** (e.g., PM4Py alignments) to compute the cheapest explanation of any deviation between an observed sequence and the model — this distinguishes genuine rare-but-legal paths from actual logging errors, which a raw DFG cannot do.

*Limitation:* a frequent DFG edge only reflects statistical co-occurrence, not permissibility — it will happily "learn" `Closed -> Damage Assessment` as a real edge if the log contains ordering noise. Only the model-based check (footprint/alignment) can label it impossible.

**c. Same-timestamp ambiguity.**
Maintain an ingestion sequence index for all events with identical timestamps. Where absent (as in Case Z), the correct rule is: treat order as **unknown**, not as a directional edge. Any explanation citing a directional pattern over tied timestamps without a sequence index must be suppressed or replaced with an "order ambiguous" flag, and the affected log slice should trigger a data-quality ticket.

**d. Complete-trace usage detection.**
Static analysis should distinguish "prefix-only" features (computed via a bounded replay of the log up to t0) from "full-trace" features (computed over the closed case). Every full-trace feature used in an explanation at t0 is leakage by construction and should be auto-flagged, regardless of its predictive power.

**e. Enabled / impossible / future-possible classification.**
For any activity referenced by a feature, classify it against the prefix's current marking in the process model:
- *Observed*: already occurred in the prefix (legitimate to reference).
- *Enabled*: reachable in one step from the current state (e.g., Documents Requested, Damage Assessment Completed, Fraud Investigation Opened are all enabled immediately after Coverage Check) — legitimate to reference *branch-possibility*, illegitimate to reference as having *occurred*.
- *Impossible*: not reachable without intervening activities (e.g., Settlement Decision before Damage Assessment) — if such an activity appears as "occurred," it indicates a data or log-parsing error, not a genuine rare path.

**f. Legitimacy of repeated `Settlement Decision Recorded`.**
Use a declarative (Declare-style) constraint: a second Decision event is legitimate **iff** it is preceded by an Appeal, which itself is preceded by a first Decision in {Partial, Deny}. Alignments against this constraint should be run on any trace with two Decision events; violations indicate either genuine data errors or a business-rule breach, and should be excluded from "normal pattern" statistics rather than treated as a valid Sequence-explainer signal.

*Overall limitation caveat:* DFG/frequency-based explainers are good for descriptive discovery but cannot certify feasibility or temporal availability; alignments and declarative checks are heavier but necessary before any pattern is allowed into an explanation surfaced at t0.

## 3. Alternative feature interpretations

**Defensible predictive signal** (prefix-derived, temporally clean, plausible mechanism):
`initial_damage_complexity`, `elapsed_since_registration_at_t0`, `claimant_channel`, `initial_reserve` (once lineage confirmed). *May claim*: these are valid statistical predictors of breach risk observable at t0, consistent with a plausible mechanism (harder/larger claims genuinely take longer). *May not claim*: strong individual causal effect size without a controlled/quasi-experimental design — association only.

**Process-state or congestion signal**:
`queue_length_at_t0`. *May claim*: this reflects current operational load and is a legitimate, actionable operational lever (e.g., staffing, triage). *May not claim*: that it reflects anything about the claim's inherent nature — it is a shared-resource property, not a claim property, and its effect is likely to shift the moment staffing changes (non-stationary).

**Proxy requiring fairness/robustness review**:
`claimant_region`, and (once repaired) `final_handler_team`/`assigned_team_at_t0` if team assignment correlates with region or claim type. *May claim*: statistically useful in-sample; predictive of the outcome. *May not claim*: causal delay driver, or a legitimate basis for differential treatment. Requires disparate-impact/equalized-odds analysis before any operational use; if used for prediction only (not action), must be documented as a proxy with governance sign-off.

**Drift/calendar proxy**:
`calendar_week`. *May claim*: a real, time-bounded predictive association tied to a specific policy/holiday period in the training window. *May not claim*: a generalizable causal "week effect" — the signal is likely to disappear or invert once the policy/holiday period passes, and should not be described as an inherent property of certain weeks.

**Unusable until lineage repaired**:
`final_handler_team` (needs as-of-t0 capture), `prior_claim_count_before_t0` (SQL bug), `same_day_document_count_snapshot` (nightly refresh bug), `risk_score_current` (no point-in-time versioning). These are not yet classifiable as predictive or not — they must be re-engineered with correct point-in-time semantics before any interpretation is attempted.

## 5. Recommendations for explanation validation

**Priority 1 — Feature-store redesign (foundational).**
Enforce as-of-t0 (point-in-time) joins as a platform-level guarantee, not a per-feature convention. Require every feature to declare `event_time_bound` and `prefix_only: true/false` metadata; block registration of full-trace features for any t0-scoped model.

**Priority 2 — Historical feature timestamps for mutable fields.**
Version `risk_score_current`, `final_handler_team`/assigned-team, and similar recalculable fields with effective-from/effective-to intervals so any point-in-time value can be reconstructed exactly, not approximated.

**Priority 3 — Prefix-only recomputation of the full training set.**
Rebuild every feature (`prior_claim_count`, `same_day_document_count`, `num_document_requests`, `full_trace_variant_id -> prefix_variant_id`) via strict event-log replay up to each case's t0, not via warehouse snapshots taken at extraction time.

**Priority 4 — Process-conformance tests as CI gates.**
Integrate footprint/alignment checks into the feature-engineering pipeline: reject any feature referencing an activity not reachable/observed by t0; add unit tests using synthetic traces for each canonical path (fast-track, single evidence cycle, multi-cycle, appeal) verifying computed values match expected prefix-only results.

**Priority 5 — Recalibration after feature removal.**
Expect substantial AUC/Brier degradation once leaked features are stripped; retrain and recalibrate (Platt/isotonic) against this new, honest baseline, and communicate the revised performance envelope to stakeholders rather than retaining the inflated original metrics.

**Priority 6 — Explanation stability testing.**
Check SHAP/local-explanation stability across bootstrap retrainings and small prefix perturbations (e.g., ±5 min timestamp jitter on snapshot joins like `queue_length_at_t0`) to catch fragile or noise-driven attributions before they are shown to users.

**Priority 7 — Proxy and fairness analysis.**
Run disparate-impact/equalized-odds analysis on `claimant_region`, `claimant_channel`, and repaired `assigned_team_at_t0`; document a governance decision (keep with disclosure, transform, or drop) before any operational use, distinct from pure predictive-validity sign-off.

**Priority 8 — Ongoing drift and data-quality monitoring.**
Monitor: (a) trace-variant novelty (structural/process drift), (b) rate of same-timestamp/ordering anomalies as a log-quality KPI, (c) calendar/policy-period confounds re-emerging, and (d) silent schema or lineage-tag changes in the feature store (including previously unaudited fields like employee experience, joined at extraction rather than event date).
