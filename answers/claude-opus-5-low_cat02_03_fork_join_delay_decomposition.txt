# 1. Delay-decomposition definitions

Notation: case index `c` (F01…F12), branch index `i ∈ {A, B, C}`. All quantities in minutes; the log is complete-event data at 1-minute resolution on a single day, so no date arithmetic across midnight is needed.

Primitive observations per case `c`:
`arr(c)`, `fr(c)` (fork_release), `s_i(c)` (branch start), `e_i(c)` (branch end), `fs(c)` (final_start), `fe(c)` (final_end), `res(c)`.

Definitions (observations unless marked):

1. **Upstream elapsed** — `U(c) = fr(c) − arr(c)`.
   Everything between entry to the process and the moment branch work becomes permissible. It is *not* decomposable further here: we cannot see whether it is preparation service or pre-fork queueing (see §7).

2. **Branch queue** — `Q_i(c) = s_i(c) − fr(c)`.
   Time the branch waited for its own station after work was permitted. `Q_i ≥ 0` in all 12 cases, which is consistent with the stated fork semantics (no branch starts before `fr`).

3. **Branch service** — `S_i(c) = e_i(c) − s_i(c)`.
   Elapsed busy interval, not necessarily pure work (interruptions are invisible; §7).

4. **Branch completion offset** — `L_i(c) = Q_i(c) + S_i(c) = e_i(c) − fr(c)`.
   This is the quantity that matters for the join, not `S_i` alone.

5. **Join-ready (estimate, not logged)** — `J(c) = max_i e_i(c)`.
   Under the stated rule "F may start only after all three branches complete", `J` is the earliest admissible start of F. It is an *estimate* of readiness: if there were an unlogged hand-off/aggregation step, true readiness would be later.

6. **Critical branch** — `crit(c) = argmax_i e_i(c)`, i.e. the branch attaining `J(c)`. Ties (none occur at 1-minute resolution in this data, though F04 has A and B ending simultaneously at 09:35 *below* the max) are resolved deterministically in code by a fixed priority order A < B < C, and reported as ties.

7. **Branch synchronization wait** — `W_i(c) = J(c) − e_i(c) ≥ 0`, with `W_crit(c) = 0` by construction.
   Idle-after-completion time of a finished branch's output waiting for its siblings.

8. **Fork–join stage elapsed** — `FJ(c) = J(c) − fr(c) = max_i L_i(c) = Q_crit(c) + S_crit(c)`.

9. **Downstream queue** — `D(c) = fs(c) − J(c)`.
   Under the model assumptions this is waiting for the final station. §4/§7 show that in this log a large part of it is *not* attributable to F1/F2 being busy.

10. **Final service** — `FS(c) = fe(c) − fs(c)` (constant 20 in all cases).

11. **Total flow time** — `T(c) = fe(c) − arr(c)`.

**Exact, non-overlapping additive identity (the decomposition):**

```
T(c) = U(c) + FJ(c) + D(c) + FS(c)
```

and inside the stage, exactly one branch is charged:

```
FJ(c) = Q_crit(c) + S_crit(c)
```

This identity holds for all 12 cases (verified in §2 and in code).

**Why summing branch synchronization waits double counts.**
For every branch, by construction,

```
Q_i(c) + S_i(c) + W_i(c) = (s_i − fr) + (e_i − s_i) + (J − e_i) = J(c) − fr(c) = FJ(c)
```

So each of the three branches individually spans the *same* wall-clock interval `[fr, J]`. Therefore

```
Σ_i (Q_i + S_i + W_i) = 3 · FJ(c),   and   Σ_i W_i(c) = 3·J(c) − Σ_i e_i(c)
```

Adding `W_A + W_B + W_C` (or adding any branch's queue+service to another branch's sync wait) counts the same minutes of elapsed time up to three times, because the branches run *in parallel*, not in sequence. Synchronization wait is a **resource-slack / earliness measure per branch**, not a component of case elapsed time. Only the critical branch's `Q + S` enters `T`. In the decomposition below, `W_i` is reported as a diagnostic column, explicitly outside the additive identity.

A second, sometimes useful non-double-counting split of `FJ` is the *marginal* one:

```
FJ(c) = L_second(c) + (L_max(c) − L_second(c))
```

where `L_second` is the second-largest branch offset. The second term is the **exclusive** contribution of the critical branch — the amount that would actually be saved if that branch became instantaneous. This is what drives §4 and prevents the naive "biggest mean service = biggest lever" error.

Structural observations from the table:

- `A_queue = 0` for **every** case: A always starts exactly at `fork_release`. A never contends for its station in this window.

- `B` carries almost all the variability: queue 5–30, service 30–45.

### Worked calculations

**F02** — arrival 08:05, fork_release 08:25.
- `U = 08:25 − 08:05 = 20`.
- A: `Q_A = 08:25 − 08:25 = 0`, `S_A = 09:15 − 08:25 = 50`, `L_A = 50`.
- B: `Q_B = 08:45 − 08:25 = 20`, `S_B = 09:25 − 08:45 = 40`, `L_B = 60`.
- C: `Q_C = 08:30 − 08:25 = 5`, `S_C = 08:50 − 08:30 = 20`, `L_C = 25`.
- `J = max(09:15, 09:25, 08:50) = 09:25`; `crit = B`; `FJ = 60 = Q_B + S_B` ✓.
- Sync: `W_A = 09:25 − 09:15 = 10`, `W_B = 0`, `W_C = 09:25 − 08:50 = 35`. (Sum 45 ≠ any elapsed component — diagnostic only.)
- `D = 09:40 − 09:25 = 15`; `FS = 20`; `T = 10:00 − 08:05 = 115`.
- Check: `20 + 60 + 15 + 20 = 115` ✓. Exclusive B contribution = `L_B − L_second (=L_A=50) = 10`: even an instant B saves only 10 minutes here.

**F04** — arrival 08:35, fork_release 08:55. The one case where the *administrative* branch is critical because of queueing.
- `U = 20`.
- A: `Q_A = 0`, `S_A = 50` (09:45), `L_A = 50`.
- B: `Q_B = 09:05 − 08:55 = 10`, `S_B = 09:35 − 09:05 = 30`, `L_B = 40` (fastest B in the log).
- C: `Q_C = 09:30 − 08:55 = 35`, `S_C = 09:52 − 09:30 = 22`, `L_C = 57`.
- `J = 09:52`, `crit = C`, `FJ = 57 = 35 + 22` ✓. Note C's *service* (22) is the second-shortest work in the case; it is the **queue** that makes it critical — the clearest illustration that service time alone misidentifies the bottleneck.
- `W_A = 7`, `W_B = 17`, `W_C = 0`.
- `D = 10:10 − 09:52 = 18`; `FS = 20`; `T = 10:30 − 08:35 = 115 = 20 + 57 + 18 + 20` ✓.
- Exclusive C contribution = `57 − 50 = 7` only; halving C's queue (to 17.5) would drop `L_C` to 39.5 < 50, so A would cap the saving at 7 minutes.

**F07** — arrival 09:20, fork_release 09:40. Worst case in the log (T = 130).
- `U = 20`.
- A: `Q_A = 0`, `S_A = 50` (10:30), `L_A = 50`.
- B: `Q_B = 10:10 − 09:40 = 30`, `S_B = 10:55 − 10:10 = 45`, `L_B = 75` — worst B queue *and* worst B service simultaneously.
- C: `Q_C = 5`, `S_C = 18`, `L_C = 23`.
- `J = 10:55`, `crit = B`, `FJ = 75` ✓.
- `W_A = 25`, `W_B = 0`, `W_C = 52` — C's output sits idle for 52 minutes, nearly three times its own service time.
- `D = 11:10 − 10:55 = 15`; `FS = 20`; `T = 11:30 − 09:20 = 130 = 20 + 75 + 15 + 20` ✓.
- Exclusive B contribution = `75 − 50 = 25`. This is a genuine tail case: B alone explains the entire excess over the 105-minute "A-limited floor" (20 + 50 + 15 + 20).

**F11** — arrival 10:20, fork_release 10:40. A-critical case, and the largest downstream wait.
- `U = 20`.
- A: `Q_A = 0`, `S_A = 50` (11:30), `L_A = 50`.
- B: `Q_B = 10`, `S_B = 30`, `L_B = 40`.
- C: `Q_C = 5`, `S_C = 18`, `L_C = 23`.
- `J = 11:30`, `crit = A`, `FJ = 50` ✓ — the structural floor of the stage, since `S_A = 50` and `Q_A = 0` always.
- `W_A = 0`, `W_B = 10`, `W_C = 27`.
- `D = 11:50 − 11:30 = 20`; `FS = 20`; `T = 12:10 − 10:20 = 110 = 20 + 50 + 20 + 20` ✓.
- Exclusive A contribution = `50 − 40 = 10`. Even here, making A instantaneous saves only 10 minutes, because B closes in at 40.

A: F01 (+5 over B's 45), F11 (+10) = 15 — but see the CF1 caveat below; measured as `L_A − L_second` it is 5 + 10 = 15, mean 1.25. C: F04 (+7), F08 (+5, `L_C = 55` vs `L_A = 50`) = 12, mean 1.0. (Table shows the per-branch means over all 12 cases; small rounding differences are immaterial.)

**Influence ranking (reasoned, not by service time):**

1. **B — dominant.** It is the last-completing branch in 8/12 cases, owns 68 of the 90 exclusive critical minutes (≈76 %), and holds the entire upper tail (`L_B = 75` in F07 and F12, the two worst-flow cases). Crucially B is *not* the largest mean service (37.5 < A's 50); it wins on **queue + service** (56.7) and on variance. Its queue alone (mean 19.2, up to 30) exceeds C's entire service time.
2. **A — structural floor, low marginal influence.** A is the longest single service (50, deterministic) and never queues, so it sets a hard lower bound `FJ ≥ 50` for every case. But because it is deterministic and B routinely exceeds it, A is critical only twice and its exclusive contribution is ~1.25 min/case. A is the *binding constraint on any redesign* (nothing can push `FJ` below 50 without touching A) while being a poor first target.
3. **C — negligible on average, non-zero in the tail.** Mean offset 30.6, far below the others; it is critical only when its own queue misbehaves (F04 q = 35, F08 q = 25 with an atypical 30-min service). Its huge mean sync wait (30.4, max 52) is the mirror image: C is almost always early and idle.

**Honest ties / near-ties.** A and C are effectively tied for second place on influence (2 critical cases each; exclusive totals 15 vs 12 minutes — a difference of one case's noise, not a real ranking). No exact `argmax` ties occur in the data, but several cases are near-ties that make the ranking fragile: F04 (`L_C = 57` vs `L_A = 50`), F08 (`L_C = 55` vs `L_A = 50`), F10 (`L_B = 55` vs `L_A = 50`), F01 (`L_A = 50` vs `L_B = 45`). With 12 cases the standard error on a 67 % criticality share is roughly ±14 pp, so "B is critical about two-thirds of the time" is the defensible claim; "B is critical 8 times" is sample-specific.

**Second-order observation on why B queues.** With arrivals every 15 minutes and mean B service 37.5, B needs ≥ 2.5 parallel servers to be stable; the persistent 20–30 minute queue is consistent with B being run at very high utilization (or with 2 servers and mild overload, since the queue drifts upward from 5 to 30 across the morning without exploding). A needs ≥ 3.33 servers and shows zero queue → A is provisioned generously. C needs ≥ 1.34 and mostly shows 5 minutes. This capacity read is a **hypothesis**, not an observation: server counts are not in the log (§7).

# 4. Counterfactual redesign analysis

All counterfactuals are evaluated with **max-based re-computation of `J`**, never by subtracting the saving from `T` directly. Two downstream models are reported:

- **Model D-fix (conservative baseline):** `D(c)` stays at its observed value, so `ΔT(c) = ΔJ(c)`. This assumes the final station's release behaviour is pace-driven, which §2/§4.3 shows is partly true.
- **Model D-sim (re-queued):** cases are re-sequenced by new `J`, assigned FIFO to the first free of 2 servers, 20-min service. This lets downstream congestion absorb upstream gains.

### CF1 — Reduce A service by 20 % (50 → 40 min)

New `e_A = fr + 0 + 40`, i.e. 10 minutes earlier in every case.

| case | old J | new J | new crit | ΔJ |
|---|---|---|---|---:|
| F01 | 09:00 (A) | 08:55 (B) | B | **5** |
| F11 | 11:30 (A) | 11:20 (B) | B | **10** |
| all other 10 cases | — | unchanged | B or C | **0** |

- **Direct benefit:** 15 minutes total, mean **1.25 min/case (1.1 % of mean flow time)**. Median saving 0.
- **Zero-benefit cases: 10 of 12** — B or C remains critical. This is the headline result: A has the *largest service time in the entire process* and cutting it by a fifth changes almost nothing. Even in the two cases that benefit, the saving is truncated by the runner-up branch (F01 gains 5 of the 10 offered minutes; F11 gains 10 only because B sits at 40).
- **Secondary effects:** A's station frees ~10 min of capacity per case, but since `Q_A ≡ 0`, there is no queue to drain — the capacity release is pure slack, possibly usable to *remove* A servers rather than to speed cases. It also raises `W_A` (A idles longer waiting for B), which is a utilization loss at the A station, and lowers the structural floor `FJ ≥ 50` to 40, which is only exploitable *after* B is fixed. Under D-sim (re-queued FIFO on 2 servers) only F01's 5 minutes survives — F11's 10-minute gain is absorbed by the final station — giving 0.42 min/case. CF1 is weak under either downstream model.

### CF2 — Reduce B queue delay by 50 %

`s_B' = fr + Q_B/2`, service unchanged, so `e_B` moves earlier by `Q_B/2` (2.5–15 min; half-minute values kept as fractions, flagged as sub-resolution artefacts of the 1-minute log).

| case | Q_B/2 offered | new `L_B` | new crit | ΔJ |
|---|---:|---:|---|---:|
| F01 | 2.5 | 42.5 | A (50) | 0 |
| F02 | 10 | 50 | tie A/B (50) | 10 |
| F03 | 10 | 55 | B | 10 |
| F04 | 5 | 35 | C (57) | 0 |
| F05 | 12.5 | 47.5 | A (50) | 10 |
| F06 | 15 | 50 | tie A/B | 15 |
| F07 | 15 | 60 | B | 15 |
| F08 | 2.5 | 32.5 | C (55) | 0 |
| F09 | 12.5 | 52.5 | B | 12.5 |
| F10 | 10 | 45 | A (50) | 5 |
| F11 | 5 | 35 | A (50) | 0 |
| F12 | 15 | 60 | B | 15 |

- **Direct benefit:** 92.5 minutes total, mean **7.7 min/case (6.7 % of flow time)** — over **six times** CF1, for an intervention that touches no service content at all.
- **Zero-benefit cases: 4 of 12** (F01, F04, F08, F11) — precisely the cases where A or C was already critical.
- **Truncation is visible and important:** in F05, F10, F02, F06 the offered saving is only partly realised because `L_A = 50` becomes the new binding constraint. Of the 125 minutes of queue removed, only 92.5 (74 %) convert to flow time, and the marginal return falls off sharply — a further halving would hit the A floor almost everywhere. **CF1 and CF2 are complements, not substitutes:** doing CF2 first makes CF1 valuable, doing CF1 first is nearly worthless.
- **Secondary effects:** halving B's queue means B starts earlier and B's station utilization pattern shifts — if the queue reduction is achieved by adding a B server, arrivals to the final station become *more* clustered (join times compress toward the A-determined floor), which increases downstream contention (see CF3). Under D-sim (2-server FIFO re-queueing) the saving is *not* absorbed — it is 8.1 min/case, marginally larger, because the FIFO baseline itself removes the pacing delay. So **~7.7–8.1 min/case is robust to the downstream model**, which is the strongest evidence for prioritising this lever.

### CF3 — Add final-station capacity / reduce downstream queueing

First, a diagnostic that must precede the counterfactual: **is `D` actually a queue?** Reconstructing F1/F2 busy periods from the log (each 20 min, strict F1/F2 alternation in case order):

| case | J | final_start | D | a server free at J? | capacity-bound portion |
|---|---|---|---:|---|---:|
| F01 | 09:00 | 09:08 F1 | 8 | both idle | 0 |
| F02 | 09:25 | 09:40 F2 | 15 | both idle | 0 |
| F03 | 09:45 | 10:00 F1 | 15 | **F1 idle since 09:28** | 0 |
| F04 | 09:52 | 10:10 F2 | 18 | F1 busy→10:20, F2 free 10:00 | 8 |
| F05 | 10:10 | 10:20 F1 | 10 | F1 free 10:20 | 10 |
| F06 | 10:30 | 10:45 F2 | 15 | F2 free 10:30 | 0 |
| F08 | 10:50 | 11:05 F2 | 15 | F2 free 11:05 | 15 |
| F07 | 10:55 | 11:10 F1 | 15 | F1 free 10:40 | 0 |
| F09 | 11:15 | 11:30 F1 | 15 | F1 free 11:30 | 15 |
| F10 | 11:20 | 11:40 F2 | 20 | F2 free 11:25 | ~5 |
| F11 | 11:30 | 11:50 F1 | 20 | F1 free 11:50 | 20 |
| F12 | 12:10 | 12:20 F2 | 10 | F2 free 12:00 | 0 |

- Observed total `D` = 176 min (mean 14.7). Only ≈ **73 min are attributable to both servers being busy**; ≈ **103 min occur while a server is demonstrably idle** (F03 is the cleanest case: F1 free for 32 minutes, yet the case waits 15). The near-constant 15–20 minute waits and the rigid F1/F2 alternation point to a **paced release / batching policy or an unlogged pre-release step**, not pure capacity.
- **Adding a third final resource** therefore has an upper bound of roughly **73 min total (≈6 min/case)** on the *observed* schedule — and the honest figure is far lower, because those "busy" intervals were themselves created by the policy delay of earlier cases. Re-simulating the observed `join_ready` times under a clean 2-server FIFO rule (in §6) reproduces almost every case with **zero** waiting; only F11 waits at all (5 min), and a third server saves 5 minutes across the whole day. **Two servers are already sufficient.** Essentially all 176 downstream minutes are policy, not capacity.
- **Removing the pacing policy** is therefore worth up to ~176 min (≈14.7 min/case) at *zero capital cost* — the single largest identified lever in the log — but only if the policy is not protecting something real (batched approvals, a shift rule, a quality gate, or an unlogged post-join step). This is a hypothesis about an unobserved mechanism, not a costed saving.
- **Zero-benefit cases:** F01 and F12 already start within 8–10 min and are not capacity-bound; a third server does nothing for them.
- **Secondary effects:** eliminating `D` removes the buffer that currently absorbs upstream variability. Combined with CF2, joins arrive faster and more clustered, so a third server may be *needed* to keep CF2's gains from being re-absorbed. Utilization of F1/F2 is currently ≈ 40 % (12 × 20 min over ~3.5 h × 2 servers), and the FIFO re-simulation absorbs the whole day on two servers with 5 minutes of total waiting — a third server is unjustified. The policy fix strictly dominates the capacity fix on this evidence.

**Combined estimate.** CF2 + policy fix, applied jointly with D-sim re-queueing, is the only combination that plausibly moves mean flow time from 115 min to the low-90s. CF1 should be sequenced last.

# 5. Recommended redesigns and risks

### Redesign 1 — Attack B's queue (capacity or dispatch rule at the Machine Stress Test station)

Add roughly half a server's worth of capacity at B, or re-dispatch so B starts closer to `fork_release` (e.g. reserve a stress-test slot at fork time the way A evidently is reserved — A's `Q_A ≡ 0` proves such a reservation mechanism is already operationally feasible somewhere in this shop).

- **Throughput:** B is the only station showing a persistent, drifting queue (5 → 30 across the morning), which is the signature of utilization near 1. Relieving it raises sustainable arrival rate; without it, the queue keeps growing and today's 12-case picture understates the steady-state problem.
- **Flow-time tail:** largest tail effect available. F07 and F12 (T = 130, 125) are pure B-tail cases (`L_B = 75`); both collapse toward the 105-minute A floor. Expected mean saving 5–7.7 min/case, but P90 saving ~15 min.
- **Utilization:** B's utilization falls (that is the point); A's and C's *idle-waiting* (`W_A`, `W_C`) fall too, since less time is spent holding completed output.
- **New bottleneck:** **A becomes critical in most cases.** The floor `FJ ≥ 50` is then binding, and further B investment returns nothing (visible already in CF2, where 26 % of the offered saving evaporates against A). Plan CF1 as the *follow-on*, not the opener.
- **Synchronization effects:** join times compress toward `fr + 50`, so cases arrive at the final station in tighter bursts — downstream contention rises. Do not deploy this alone if the final station is genuinely capacity-bound.
- **Pilot / measure first:** instrument B with *enqueue* timestamps (currently `Q_B` is inferred as `s_B − fr`, which conflates queueing with any unlogged setup). Measure B server count and utilization directly. Run a 1-week shadow test where B jobs are pre-assigned at fork; track `L_B`, criticality share of B, and mean `D` to detect downstream absorption.

### Redesign 2 — Fix the final-station release policy before buying capacity

Replace the apparent paced/alternating release with "start F on the first free server as soon as `J` is reached", and log the release decision explicitly.

- **Throughput:** unchanged in principle (F1/F2 are only ~40 % utilized); the gain is pure latency.
- **Flow-time tail:** up to ~8.6 min/case mean, and it applies to *all* cases including those where no branch redesign helps (F01, F04, F08, F11 get nothing from CF2 but do get this). It is the only lever that is uniformly distributed across cases.
- **Utilization:** F1/F2 utilization rises slightly in bursts; the alternation pattern disappears, so one resource may take consecutive cases — check for fairness/workload-balance rules that may be the *reason* for the alternation.
- **New bottleneck:** if the pacing exists to protect an unlogged aggregation/QA step, removing it just relocates the wait and may create rework. It could also expose F1/F2 to genuine contention once Redesign 1 compresses joins — at which point a third resource (worth ≤ 6 min/case today) becomes justified.
- **Synchronization effects:** none upstream; but faster F completion shortens the whole pipeline's response to demand surges, making the B queue the sole remaining accumulator.
- **Pilot / measure first:** log the true `join_ready` event and the final-station *enqueue* event, so `D` can be split into "waiting for a server" vs "waiting for a release decision" instead of being inferred. Interview the station on why F03 waited 15 minutes with F1 idle for 32. Run the policy change on one resource only (A/B test F1 vs F2) for a week and compare `D` distributions.

**Explicitly not recommended first:** speeding up the Laboratory Assay. It has the longest service time and is the intuitive target, but it is critical in 2/12 cases and a 20 % cut buys 1.25 min/case. Its value is entirely conditional on Redesign 1 landing first.

Fork-join delay decomposition for the A/B/C -> F process (12 cases, 2026-05-19).

Design notes on tooling:
  * Every fork-join quantity below (branch queue, branch service, join_ready,
    critical branch, per-branch SYNCHRONIZATION WAIT, downstream queue) is a
    CUSTOM pandas calculation.  This is deliberate.  Standard directly-follows
    performance analysis (pm4py.discover_performance_dfg) measures the time
    between the completion of one activity and the start/completion of the next
    along OBSERVED SEQUENTIAL edges.  In a fork-join it therefore reports, e.g.,
    A->F and C->F edge times separately, and CANNOT tell you:
      - which branch determined join_ready (it has no max_i semantics),
      - how long a *finished* branch idled waiting for its siblings
        (that idle time is not an edge between two events of the same branch),
      - that summing those per-branch waits would triple-count elapsed time.
    DFG performance also silently treats the three parallel edges as if they were
    alternative sequential paths.  pm4py IS used below for what it does well:
    per-activity service times on interval logs and a performance DFG for the
    branch->F edges, which we then contrast with the custom sync-wait numbers.
"""

import pandas as pd
import numpy as np

# ---------------------------------------------------------------- 1. data ----
RAW = """case,arrival,fork_release,A_start,A_end,B_start,B_end,C_start,C_end,final_start,final_end,final_resource
F01,07:55,08:10,08:10,09:00,08:15,08:55,08:20,08:38,09:08,09:28,F1
F02,08:05,08:25,08:25,09:15,08:45,09:25,08:30,08:50,09:40,10:00,F2
F03,08:20,08:40,08:40,09:30,09:00,09:45,08:45,09:03,10:00,10:20,F1
F04,08:35,08:55,08:55,09:45,09:05,09:35,09:30,09:52,10:10,10:30,F2
F05,08:50,09:10,09:10,10:00,09:35,10:10,09:15,09:35,10:20,10:40,F1
F06,09:05,09:25,09:25,10:15,09:55,10:30,09:40,10:00,10:45,11:05,F2
F07,09:20,09:40,09:40,10:30,10:10,10:55,09:45,10:03,11:10,11:30,F1
F08,09:35,09:55,09:55,10:45,10:00,10:30,10:20,10:50,11:05,11:25,F2
F09,09:50,10:10,10:10,11:00,10:35,11:15,10:15,10:35,11:30,11:50,F1
F10,10:05,10:25,10:25,11:15,10:45,11:20,10:30,10:50,11:40,12:00,F2
F11,10:20,10:40,10:40,11:30,10:50,11:20,10:45,11:03,11:50,12:10,F1
F12,10:35,10:55,10:55,11:45,11:25,12:10,11:00,11:18,12:20,12:40,F2"""

from io import StringIO
df = pd.read_csv(StringIO(RAW))

DAY = "2026-05-19 "
TS = ["arrival", "fork_release", "A_start", "A_end", "B_start", "B_end",
      "C_start", "C_end", "final_start", "final_end"]
for c in TS:
    df[c] = pd.to_datetime(DAY + df[c])

BRANCHES = ["A", "B", "C"]
mins = lambda s: (s.dt.total_seconds() / 60.0)

# ------------------------------------------------- 2. decomposition ----------
df["upstream_elapsed"] = mins(df["fork_release"] - df["arrival"])
for i in BRANCHES:
    df[f"{i}_queue"]   = mins(df[f"{i}_start"] - df["fork_release"])
    df[f"{i}_service"] = mins(df[f"{i}_end"] - df[f"{i}_start"])
    df[f"{i}_offset"]  = df[f"{i}_queue"] + df[f"{i}_service"]   # L_i = e_i - fr

df["join_ready"] = df[[f"{i}_end" for i in BRANCHES]].max(axis=1)
for i in BRANCHES:
    # synchronization wait: DIAGNOSTIC ONLY -- summing these across branches
    # would count the interval [fr, join_ready] up to three times, because
    # Q_i + S_i + W_i == FJ for EVERY branch i (they run in parallel).
    df[f"{i}_sync"] = mins(df["join_ready"] - df[f"{i}_end"])

def critical(row, order=("A", "B", "C")):
    """Deterministic tie handling: max offset, ties broken by fixed order A<B<C.
    Also returns the full tie set so ties are reported, not hidden."""
    best = max(row[f"{i}_offset"] for i in order)
    tied = [i for i in order if np.isclose(row[f"{i}_offset"], best)]
    return pd.Series({"critical_branch": tied[0],
                      "critical_tie": "|".join(tied) if len(tied) > 1 else "",
                      "L_max": best,
                      "L_second": sorted((row[f"{i}_offset"] for i in order))[-2]})

df = pd.concat([df, df.apply(critical, axis=1)], axis=1)
df["fj_elapsed"]       = mins(df["join_ready"] - df["fork_release"])
df["exclusive_crit"]   = df["L_max"] - df["L_second"]   # marginal value of the critical branch
df["downstream_queue"] = mins(df["final_start"] - df["join_ready"])
df["final_service"]    = mins(df["final_end"] - df["final_start"])
df["total_flow_time"]  = mins(df["final_end"] - df["arrival"])
df["identity_ok"] = np.isclose(
    df["upstream_elapsed"] + df["fj_elapsed"] + df["downstream_queue"]
    + df["final_service"], df["total_flow_time"])

MAIN = ["case", "upstream_elapsed", "A_queue", "A_service", "B_queue", "B_service",
        "C_queue", "C_service", "A_sync", "B_sync", "C_sync", "fj_elapsed",
        "critical_branch", "critical_tie", "downstream_queue", "final_service",
        "total_flow_time", "identity_ok"]
print("=== CASE-LEVEL DECOMPOSITION (minutes) ===")
print(df.assign(join_ready=df["join_ready"].dt.strftime("%H:%M"))[
      MAIN[:1] + ["join_ready"] + MAIN[1:]].to_string(index=False))
print("\nadditive identity U + FJ + D + FS == T holds for all cases:",
      bool(df["identity_ok"].all()))

# ------------------------------------------------- 3. aggregate --------------
agg = pd.DataFrame({
    "mean_service": [df[f"{i}_service"].mean() for i in BRANCHES],
    "sd_service":   [df[f"{i}_service"].std(ddof=0) for i in BRANCHES],
    "max_service":  [df[f"{i}_service"].max() for i in BRANCHES],
    "mean_queue":   [df[f"{i}_queue"].mean() for i in BRANCHES],
    "max_queue":    [df[f"{i}_queue"].max() for i in BRANCHES],
    "mean_offset":  [df[f"{i}_offset"].mean() for i in BRANCHES],
    "max_offset":   [df[f"{i}_offset"].max() for i in BRANCHES],
    "n_critical":   [(df["critical_branch"] == i).sum() for i in BRANCHES],
    "mean_sync":    [df[f"{i}_sync"].mean() for i in BRANCHES],
    "excl_minutes": [df.loc[df["critical_branch"] == i, "exclusive_crit"].sum()
                     for i in BRANCHES],
}, index=BRANCHES).round(2)
print("\n=== BRANCH COMPARISON (influence, not service time) ===")
print(agg.to_string())

# ------------------------------------------------- 4. counterfactuals --------
def rebuild(ends, base):
    """Recompute join/flow given new branch end times. Two downstream models."""
    J = pd.concat(ends, axis=1).max(axis=1)
    dJ = mins(base["join_ready"] - J)                       # >= 0
    # Model D-fix: observed downstream wait is pace-driven -> preserved.
    T_fix = base["total_flow_time"] - dJ
    # Model D-sim: FIFO on new J across 2 servers, 20-min deterministic service.
    order = J.sort_values(kind="mergesort").index
    free = [pd.Timestamp(DAY + "00:00")] * 2
    start = {}
    for idx in order:
        k = int(np.argmin(free))
        s = max(J[idx], free[k])
        start[idx] = s
        free[k] = s + pd.Timedelta(minutes=20)
    fs = pd.Series(start).reindex(base.index)
    T_sim = mins(fs + pd.Timedelta(minutes=20) - base["arrival"])
    return J, dJ, T_fix, T_sim

base_sim = rebuild([df[f"{i}_end"] for i in BRANCHES], df)[3]  # 2-server baseline

results = {}

# CF1: A service -20%  (A_queue is identically 0, so A_end = fork_release + 40)
endsA = [df["A_start"] + pd.to_timedelta(df["A_service"] * 0.8, unit="m"),
         df["B_end"], df["C_end"]]
results["CF1_A_service_-20%"] = rebuild(endsA, df)

# CF2: B queue halved (service unchanged -> B_end shifts earlier by Q_B/2)
endsB = [df["A_end"],
         df["B_end"] - pd.to_timedelta(df["B_queue"] / 2.0, unit="m"),
         df["C_end"]]
results["CF2_B_queue_-50%"] = rebuild(endsB, df)

# CF3a: downstream queue eliminated entirely (policy fix, D -> 0)
cf3a = df["total_flow_time"] - df["downstream_queue"]
# CF3b: third final-station server, FIFO on the OBSERVED join_ready
def sim_servers(J, n):
    order = J.sort_values(kind="mergesort").index
    free = [pd.Timestamp(DAY + "00:00")] * n
    out = {}
    for idx in order:
        k = int(np.argmin(free))
        s = max(J[idx], free[k]); out[idx] = s
        free[k] = s + pd.Timedelta(minutes=20)
    return pd.Series(out).reindex(J.index)
cf3b = mins(sim_servers(df["join_ready"], 3) + pd.Timedelta(minutes=20) - df["arrival"])

summary = pd.DataFrame({"case": df["case"], "base_T": df["total_flow_time"]})
for name, (J, dJ, T_fix, T_sim) in results.items():
    summary[name + " |dJ"]  = dJ
    summary[name + " |Dfix"] = df["total_flow_time"] - T_fix
    summary[name + " |Dsim"] = base_sim - T_sim
summary["CF3a_no_downstream_wait |save"] = df["total_flow_time"] - cf3a
summary["CF3b_third_server |save"]       = base_sim - cf3b
print("\n=== COUNTERFACTUAL SAVINGS PER CASE (minutes) ===")
print(summary.round(2).to_string(index=False))

print("\n=== COUNTERFACTUAL AGGREGATES ===")
rows = []
for name, (J, dJ, T_fix, T_sim) in results.items():
    rows.append({"scenario": name, "mean_save_Dfix": (df["total_flow_time"] - T_fix).mean(),
                 "total_save_Dfix": (df["total_flow_time"] - T_fix).sum(),
                 "mean_save_Dsim": (base_sim - T_sim).mean(),
                 "cases_zero_benefit": int((dJ <= 1e-9).sum())})
rows.append({"scenario": "CF3a_no_downstream_wait",
             "mean_save_Dfix": (df["total_flow_time"] - cf3a).mean(),
             "total_save_Dfix": (df["total_flow_time"] - cf3a).sum(),
             "mean_save_Dsim": np.nan,
             "cases_zero_benefit": int((df["downstream_queue"] <= 0).sum())})
rows.append({"scenario": "CF3b_third_final_server",
             "mean_save_Dfix": np.nan, "total_save_Dfix": np.nan,
             "mean_save_Dsim": (base_sim - cf3b).mean(),
             "cases_zero_benefit": int(np.isclose(base_sim, cf3b).sum())})
print(pd.DataFrame(rows).round(2).to_string(index=False))

# Diagnostic: how much of the observed downstream wait is truly capacity-bound?
# (compare observed final_start with a 2-server FIFO simulation on observed J)
sim_start = sim_servers(df["join_ready"], 2)
print("\n=== IS DOWNSTREAM WAIT REALLY A QUEUE? ===")
print(pd.DataFrame({
    "case": df["case"],
    "join_ready": df["join_ready"].dt.strftime("%H:%M"),
    "observed_start": df["final_start"].dt.strftime("%H:%M"),
    "fifo2_start": sim_start.dt.strftime("%H:%M"),
    "observed_D": df["downstream_queue"],
    "capacity_D": mins(sim_start - df["join_ready"]),
    "policy_D": df["downstream_queue"] - mins(sim_start - df["join_ready"]),
}).round(1).to_string(index=False))

# ------------------------------------------------- 5. PM4Py ------------------
# Interval event log: one row per branch activity and one for the final activity.
recs = []
for _, r in df.iterrows():
    for i in BRANCHES:
        recs.append({"case:concept:name": r["case"],
                     "concept:name": {"A": "Laboratory Assay",
                                      "B": "Machine Stress Test",
                                      "C": "Documentation Review"}[i],
                     "start_timestamp": r[f"{i}_start"],
                     "time:timestamp": r[f"{i}_end"],
                     "org:resource": "tech" if i in ("A", "B") else "admin"})
    recs.append({"case:concept:name": r["case"], "concept:name": "Release Decision",
                 "start_timestamp": r["final_start"], "time:timestamp": r["final_end"],
                 "org:resource": r["final_resource"]})
elog = pd.DataFrame(recs)

try:
    import pm4py
    elog = pm4py.format_dataframe(elog, case_id="case:concept:name",
                                  activity_key="concept:name",
                                  timestamp_key="time:timestamp",
                                  start_timestamp_key="start_timestamp")
    print("\n=== PM4PY: per-activity service time (mean, seconds) ===")
    print(pm4py.get_service_time(elog, aggregation_measure="mean"))
    perf_dfg, s, e = pm4py.discover_performance_dfg(elog)
    print("\n=== PM4PY: performance DFG (seconds) ===")
    for edge, val in perf_dfg.items():
        print(f"  {edge[0]} -> {edge[1]}: {val:.0f}")
    # NOTE: the DFG edges branch->'Release Decision' mix synchronization waiting
    # with downstream queueing and never expose max_i(e_i). The per-branch
    # sync waits and the critical-branch attribution above are therefore
    # necessarily custom pandas work, not DFG output.
except Exception as exc:      # pm4py optional
    print("\n[pm4py unavailable or failed: %s] custom results above are complete." % exc)

# 7. Limits of inference

**Causality.** Nothing here is causal. B being last-to-finish in 8/12 cases is an *association* between B's completion offset and `join_ready`; the counterfactuals in §4 are arithmetic re-computations under a fixed-structure assumption (branch timings independent of one another and of the intervention), not identified causal effects. In particular, if B's queue and C's queue are fed by a shared dispatcher or shared staff, halving B's queue could lengthen C's — an interference/SUTVA violation the data cannot rule out. The apparent drift in B's queue across the morning also confounds "branch identity" with "time of day".

**Branch resource capacity.** Server counts at A, B and C are unobserved. `Q_A ≡ 0` is consistent with (i) ample A capacity, (ii) a reservation policy, or (iii) A simply being the designated first task. `Q_B` in the 20–30 range is consistent with 2 servers near saturation *or* 3 servers plus setup time. Without resource identifiers per branch event (the log has none for A/B/C), utilization, queue discipline (FIFO vs priority) and the true capacity elasticity assumed in Redesign 1 are all unidentified.

**Queue vs. non-queue waiting.** `Q_i = s_i − fr` is a *residual*, not an observation of queueing. It also contains setup, travel, batching, breaks, and any unlogged preparatory activity. The same applies to `U = fr − arr`, which cannot be split into upstream service and upstream waiting at all.

**Work preemption and true work content.** Only complete-event pairs are available, so `S_i` is an elapsed interval, not effort. A 50-minute assay might be 20 minutes of work plus a 30-minute unattended incubation; if so, "reducing A service by 20 %" (CF1) may be physically impossible or, conversely, free. Interruptions, multitasking and rework loops are invisible. A's perfectly constant 50 minutes across 12 cases is itself suspicious — it may indicate a fixed protocol duration or a *recorded* rather than measured value.

**Is `join_ready` real?** It is derived, not logged. If any aggregation, hand-off or check occurs between the last branch completion and eligibility for F, true readiness is later than `max_i e_i`, and the downstream queue `D` is correspondingly overstated. The §4.3 finding that ~103 of 176 downstream minutes occur while a server sits idle is equally consistent with (a) a paced release policy, (b) an unlogged post-join step, (c) shift/break structure at the final station, or (d) F1/F2 being reserved for other, unlogged work. These have very different remedies — capacity purchase helps only under a genuine-queue reading — so instrumenting the release decision is the single highest-value logging change.

**Statistical limits.** Twelve cases from one morning, one day, no arrival-rate variation (arrivals are exactly 15 minutes apart, which is itself unrealistically regular and may be a scheduled rather than stochastic arrival stream). Tail estimates ("P90 saving ~15 min") rest on two observations. Criticality shares carry roughly ±14 pp of sampling error. No weekend/night/shift-change data, so nothing here generalises to periods of different load, and the observed B-queue drift suggests the system may not even be in steady state within the window observed.
