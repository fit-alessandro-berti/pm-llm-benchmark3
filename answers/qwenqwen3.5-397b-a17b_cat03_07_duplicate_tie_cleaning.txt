## 1. Duplicate-handling decision tree

To minimize semantic damage, we employ a hierarchical decision tree that prioritizes business semantics over technical convenience. This tree classifies candidate pairs before any modification occurs.

1.  **Are Event IDs identical?**
    *   **Yes:** **Exact Technical Duplicate.** Action: **Drop** the later ingested copy. Preserve the earliest `ingested_at` provenance.
    *   **No:** Proceed to 2.

2.  **Do events share Activity, Timestamp, and All Related Objects?**
    *   **Yes:** Proceed to 3.
    *   **No:** Proceed to 4.

3.  **Is there external reconciliation evidence (e.g., payload hash match, reconciliation report)?**
    *   **Yes:** **Same Physical Event (Cross-System).** Action: **Merge Attributes and Relations.** Create a canonical event retaining the most granular attributes (e.g., WMS location) and unioning objects.
    *   **No:** **Unresolved Candidate.** Action: **Quarantine for Review.** Do not alter log structure.

4.  **Do events share Activity and Timestamp but differ in Objects?**
    *   **Yes:** **Concurrent Same-Label Events.** Action: **Retain Both Unchanged.** (e.g., picking two different items).
    *   **No:** Proceed to 5.

5.  **Do events share Objects but differ in Activity Granularity (Detail vs. Summary)?**
    *   **Yes:** **Summary Event Derived from Detail.** Action: **Retain Both with Refined Labels.** Qualify the summary (e.g., `Pack Package (Summary)`).
    *   **No:** Proceed to 6.

6.  **Do events share Objects and Activity but have known lifecycle ordering (e.g., Acceptance vs. Handover)?**
    *   **Yes:** **Harmonization Collision.** Action: **Retain Both with Deterministic Ordering.** Use domain rules to order, do not merge.
    *   **No:** **Unresolved Candidate.** Action: **Quarantine for Review.**

## 3. Timestamp-tie ordering rules

To convert the partial order into a total order for analysis without fabricating history, we apply a deterministic tie-breaking policy. This policy acknowledges that equal timestamps often represent a business transaction window rather than an instantaneous point.

**Ordering Hierarchy:**
1.  **Domain Constraints (Semantic):** Known lifecycle rules (e.g., Authorization before Capture). This is semantic truth.
2.  **Within-Source Sequence (Semantic):** `source_seq` provides the true order within a single system.
3.  **Lifecycle Constraints on Shared Objects (Semantic):** If Event A creates an object used by Event B, A precedes B.
4.  **Ingestion Time (Deterministic Fallback):** Only used if business semantics are identical. This is technical, not semantic.
5.  **Stable Fallback Order (Deterministic):** Lexicographical sort on `source_event_key`.

**Warning on Microseconds:**
Adding synthetic microseconds to break ties (e.g., forcing e09 before e10 because `ingested_at` differs) encodes a false story. It implies physical precision that does not exist. If two events share a second-level timestamp and domain knowledge says they are sequential, we must order them sequentially but flag the timestamp as "tied" in metadata. We do not alter the `timestamp` column; we alter the sort index.

**Intended Orders:**

*   **10:00 Group (e03–e07):**
    1.  e03/e04 (Merged Pick I1)
    2.  e05 (Pick I2) – *Distinct object allows concurrency, but sorted after I1 for determinism.*
    3.  e06 (Pack Detail) – *Requires picks.*
    4.  e07 (Pack Summary) – *Derived from e06.*
*   **10:15 Group (e08–e10):**
    1.  e08/e09 (Merged Dispatch) – *Release/Acceptance.*
    2.  e10 (Handover) – *Fact 5 states Handover follows Acceptance.*
*   **12:00 Group (e11–e16):**
    1.  e11/e16 (Merged Invoice)
    2.  e12 (Authorize) – *Precondition for capture.*
    3.  e13 (Capture M1)
    4.  e14 (Capture M2) – *Sorted by Payment ID M1 < M2.*
    5.  e15 (ERP Summary) – *Fact 8 states generated after messages.*

    *   *Failure:* Adding 1s to e09 to force it before e10, then calculating latency.
    *   *Safeguard:* Use `sort_index` for ordering, but calculate duration using `original_timestamp`. Flag tied durations as ranges.
7.  **Losing Source-Authoritative Attributes:**
    *   *Failure:* Overwriting WMS location data with ERP summary data during merge.
    *   *Safeguard:* Priority rules for attribute merging (Detail > Summary; System-of-Record > Downstream).
8.  **Applying Duplicate Functions to the Whole OCEL Without Inspection:**
    *   *Failure:* Running `drop_duplicates` on activity/timestamp globally.
    *   *Safeguard:* Pre-filter candidate groups using the Decision Tree (Section 1). Only apply mechanical deduplication to groups marked "Exact Technical Duplicate."

By adhering to these safeguards and the conservative pipeline, we ensure the OCEL remains a faithful representation of the multi-system reality, suitable for both operational auditing and process mining.
