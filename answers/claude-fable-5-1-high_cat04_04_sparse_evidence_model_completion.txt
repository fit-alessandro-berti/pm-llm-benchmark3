Why both DFG directions do not prove concurrency: a DFG records adjacency of completions. For two activities a and b, observing both a→b and b→a means only that both completion orders occur in the log. That is the footprint of parallelism, but also of an exclusive choice between two sequential branches (e.g., a case attribute decides which check goes first), of a rework loop, and of timestamp ties resolved arbitrarily by ingestion index (S7). Distinguishing these requires either lifecycle start events (overlap of intervals proves concurrency), a case attribute that predicts the order (proves a hidden XOR), or repeated activities (proves a loop). Because none is available here, all three candidates express CC/ER as an admissibility statement about completion order, not as a claim about how work was actually done.

# 2. Shared Assumptions

1. **Event semantics.** Every event is a completion event (S7). An order edge x→y in any model means "the completion of x is recorded before the completion of y". No model claims anything about start times or overlaps (D7).
2. **Ties.** Same-timestamp events were ordered by ingestion index; we treat the resulting order as data but do not build sequence constraints on the CC/ER pair because part of the 19:11 split may be tie-breaking.
3. **Missing SC events.** The 7 traces without SC are modeled through a silent alternative ×(SC, τ). This τ deliberately conflates (a) legitimate skips for stocked components (S4) and (b) events lost by the integration problem (S5, ≈1–3 of the 7). The models therefore describe the *log-generating* process, not the *business* process; a conformance verdict "SC skipped" is not a compliance finding until the external/stocked attribute exists.
4. **Absent external/stocked attribute.** Because the attribute was not exported, the S3/S4 data rule cannot be expressed as a guard. We represent it as an unguarded control-flow choice and disclose that the models are therefore more permissive than the real rule (they admit an external-component order without SC).
5. **Optionality representation.** Optional activities (SC, XR) are ×(activity, τ) in process trees and `OperatorPOWL(XOR, [Transition, SilentTransition])` in POWL. No activity may repeat: nothing in the log or in D1–D7 shows a loop, and D6 states "at most once" for XR. All models are therefore acyclic and have finite languages.
6. **Mandatory activities.** RO, CC, ER, AC, RP, ArC occur exactly once in every trace (30/30; D1, D2, D3).
7. **Fixed skeleton.** RO is first; AC→RP→ArC is a fixed tail; all checks (CC, ER, SC if present, XR if present) complete before AC (D3, D4, D6, 30/30). The three candidates differ only in the block between RO and AC.
8. **Noise.** We assume no mislabeled events and no case merges; all 30 traces are taken as genuine behavior. If S5-type loss also affects other activities we have no evidence of it.
9. **Language vs. structure.** Two models with the same trace language are indistinguishable by any completion-only conformance technique; when we choose partial order over an XOR of sequences we do so for simplicity and explainability, not because the log proves it.

# 3. Conservative Candidate

**Inductive-bias statement.** The conservative model assumes that the 30 observed traces are the complete legitimate behavior and that any unobserved interleaving is unsupported until proven otherwise. It only factors out what is deterministic in 30/30 cases (RO first, AC→RP→ArC last) and enumerates the seven observed middle segments in an exclusive choice. Its bias is maximal precision and zero generalization: it is a trace model with a shared prefix and suffix. It relies only on the high-confidence rules D1 and D2 (and D3/D4/D6 hold trivially because every enumerated branch satisfies them). It does not encode S2, D5 or S6 as generalizable rules; it merely admits the instances of them that happened to be observed.

**Compact formal expression.**

→( RO, ×( →(CC,ER,SC), →(ER,CC,SC), →(CC,ER), →(ER,CC), →(CC,SC,ER), →(CC,ER,SC,XR), →(ER,CC,XR,SC) ), AC, RP, ArC )

Language size: exactly 7 traces (the observed variants).

**PM4Py code.**

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

RO, CC, ER, SC, XR, AC, RP, AR = (
    "Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
    "Expedite Review", "Approve Configuration", "Release Production", "Archive Case")

def leaf(label):
    return ProcessTree(label=label)

def node(op, children):
    t = ProcessTree(operator=op)
    for c in children:
        c.parent = t
        t.children.append(c)
    return t

def seq(*labels):
    return node(Operator.SEQUENCE, [leaf(l) for l in labels])

# the seven observed segments between Register Order and Approve Configuration
MIDDLES = [(CC, ER, SC), (ER, CC, SC), (CC, ER), (ER, CC), (CC, SC, ER),
           (CC, ER, SC, XR), (ER, CC, XR, SC)]

model_conservative = node(Operator.SEQUENCE, [
    leaf(RO),
    node(Operator.XOR, [seq(*m) for m in MIDDLES]),
    leaf(AC), leaf(RP), leaf(AR),
])

# equivalent string form (labels with spaces must be quoted):
model_conservative_str = pm4py.parse_process_tree(
    "->( 'Register Order', X( "
    "->('Credit Check','Engineering Review','Supplier Confirmation'), "
    "->('Engineering Review','Credit Check','Supplier Confirmation'), "
    "->('Credit Check','Engineering Review'), "
    "->('Engineering Review','Credit Check'), "
    "->('Credit Check','Supplier Confirmation','Engineering Review'), "
    "->('Credit Check','Engineering Review','Supplier Confirmation','Expedite Review'), "
    "->('Engineering Review','Credit Check','Expedite Review','Supplier Confirmation') ), "
    "'Approve Configuration', 'Release Production', 'Archive Case' )")
```

**Duplicate labels and scalability.** CC and ER each appear seven times, SC five times and XR twice in the tree. After conversion the Petri net has 25 transitions for 8 activity labels (20 places, 50 arcs in pm4py 2.7). Consequences: (i) alignment-based fitness and precision still work because they match on labels, but the search space contains duplicate-label transitions and the alignment cost function may pick any of them, so diagnostics point to "a" CC transition, not "the" CC step; (ii) token-based replay and footprint/causal-net techniques that assume unique labels behave poorly or lose meaning; (iii) the model reads as a lookup table, not as a process description, so stakeholders cannot see that "CC/ER order" and "SC present" are independent decisions; (iv) size grows linearly with the number of variants: with a realistic log of a few hundred variants the XOR would have hundreds of branches, which is exactly the "trace model" end of the precision/generalization trade-off. A slightly compressed exact-language form is possible, e.g. ×( →(×(→(CC,ER),→(ER,CC)), ×(SC,τ)), →(CC,SC,ER), →(CC,ER,SC,XR), →(ER,CC,XR,SC) ), but it still needs duplicate labels because the XR-containing segments do not compose with the others without admitting unobserved traces.

**Behavior deliberately excluded.**
- XR without SC (e.g., RO,CC,ER,XR,AC,RP,ArC).
- XR before SC when CC completed first (RO,CC,ER,XR,SC,AC,RP,ArC); XR after SC when ER completed first (RO,ER,CC,SC,XR,AC,RP,ArC).
- XR following the observed CC,SC,ER order (RO,CC,SC,ER,XR,AC,RP,ArC).
- SC completing before CC in any form (RO,ER,SC,CC,... or RO,SC,...).
- Any repetition of any activity; any trace not starting with RO or not ending with AC,RP,ArC.

**Known underfitting risks.**
- XR occurred in only 2 of 30 cases. The model has effectively "learned" XR's behavior from two samples; the next XR case has a substantial chance of being flagged as non-conformant even though S6 explicitly permits it (3 of the 5 traces the balanced model adds are XR interleavings that S6 allows).
- V5 (CC,SC,ER) appears twice; if D5 is symmetric the mirror ER,SC,CC will eventually appear and be rejected.
- The tau-free enumeration hard-codes the *observed* mix of legitimate SC skips and lost SC events; it therefore fails on a legitimate stocked-component order that happens to combine with an unobserved order of the other checks.
- Zero generalization by construction: replay-based generalization in a pm4py run was ≈0.3 versus ≈0.75 for the other two candidates.
- Each new variant requires a model change, which makes the model a moving target for conformance checking.

# 4. Balanced Candidate

**Inductive-bias statement.** The balanced model assumes that the variability in the log is generated by a small number of independent mechanisms rather than by a list of scripts: the two principal checks are unordered relative to each other; SC is optional and depends on CC but not on ER; XR is optional, depends on both checks and is unordered relative to SC; AC synchronises everything. Where the log is silent, it follows the medium-confidence rules (D6, S6) and follows the data over the weakest rule (D5) by keeping the CC→SC dependency that holds in 23/23 SC occurrences. Its bias is "independence unless contradicted", and it prefers a partial order (POWL) because a process tree cannot express "XR after CC and ER, but unordered with SC, while SC depends only on CC" without duplicating labels.

**How the sequence/concurrency/partial-order decisions were made.**
- *CC vs ER — unordered (concurrent completion).* Both orders occur (19 vs 11), S2 says parallel, D7 says the log cannot distinguish, and S1 is contradicted by 11 completion orders. A hidden-attribute XOR of two sequences has the same completion language, so choosing the unordered pair costs nothing in log-level precision and is simpler. The 19:11 asymmetry is not a reason for sequencing: parallel activities with different durations naturally produce skewed completion orders.
- *SC vs CC — ordered CC→SC.* SC never completes before CC in the data (0 of 9 ER-first traces with SC), although D5 would allow it. There is also a plausible business reason (do not commit to suppliers before credit is cleared). The evidence is weak (a 0/9 result has roughly a 25% chance under the base rate seen on the ER side), which is precisely why the permissive model drops this edge and why Section 9 asks for the ER,SC,CC trace as a discriminating observation.
- *SC vs ER — unordered.* V5 shows SC before ER twice, V1/V2 show SC after ER 19 times. A sequence in either direction would misfit observed behavior; ∧-style freedom is the only option.
- *SC presence — optional via τ.* Required by V3/V4; abstraction disclosed in Section 2.
- *XR — optional, after CC and ER, unordered with SC.* D6 and S6 are the most specific statements available, both observations agree with them, and the observed XR cases show both XR-before-SC and XR-after-SC. Forcing an order between XR and SC would contradict one of the two XR traces.
- *Partial order instead of process tree.* The nearest process trees are →(RO, ∧(CC,ER), ∧(×(SC,τ),×(XR,τ)), AC,RP,ArC) (forbids the observed CC,SC,ER) or →(RO, ∧(CC,ER,×(SC,τ)), ×(XR,τ), AC,RP,ArC) (admits SC before CC and forbids the observed XR-before-SC). Neither fits; the POWL does.

**Compact formal expression.**

PO( nodes = {RO, CC, ER, SC° = ×(SC,τ), XR° = ×(XR,τ), AC, RP, ArC};
    order = RO→CC, RO→ER, CC→SC°, CC→XR°, ER→XR°, CC→AC, ER→AC, SC°→AC, XR°→AC, AC→RP, RP→ArC )

Language size: 12 traces (7 observed + 5 unobserved; all 5 contain XR).

**PM4Py code.**

```python
import pm4py
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

RO, CC, ER, SC, XR, AC, RP, AR = (
    "Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
    "Expedite Review", "Approve Configuration", "Release Production", "Archive Case")

def optional(label):
    return OperatorPOWL(Operator.XOR, [Transition(label), SilentTransition()])

ro, cc, er, ac, rp, ar = (Transition(RO), Transition(CC), Transition(ER),
                           Transition(AC), Transition(RP), Transition(AR))
sc_opt, xr_opt = optional(SC), optional(XR)

model_balanced = StrictPartialOrder([ro, cc, er, sc_opt, xr_opt, ac, rp, ar])
for a, b in [(ro, cc), (ro, er),            # both checks start after registration
             (cc, sc_opt),                  # SC waits for CC only (0/9 counter-examples)
             (cc, xr_opt), (er, xr_opt),    # D6/S6: XR after both principal checks
             (cc, ac), (er, ac), (sc_opt, ac), (xr_opt, ac),   # D3/D4/D6: everything before AC
             (ac, rp), (rp, ar)]:           # D2/D1 tail
    model_balanced.order.add_edge(a, b)
```

**Behavior deliberately excluded.**
- SC completing before CC (RO,ER,SC,CC,… and RO,SC,…): not observed, only supported by the weakest rule D5.
- XR before either check completes; XR after AC; XR more than once (D6).
- SC after AC (D4); RP before AC (D2); any missing CC, ER, AC, RP, ArC.
- Any repetition, any loop, any trace not bracketed by RO and ArC.

**Known underfitting risks.**
- If D5 is symmetric, ER,SC,CC traces will be rejected (permissive fixes this).
- If S5 is worse than estimated and some traces also lose other events (e.g., ER), the model rejects them; there is no noise tolerance by design.
- If XR can legitimately precede one of the checks in genuinely urgent cases (a plausible real-world deviation from D6), it is rejected.
- The model forbids repetition of CC or ER after a failed check (rework); no rework is observed, but 30 cases is a small sample for a rare loop.

Overfitting risks are the mirror image: the model admits 5 XR interleavings on the strength of 2 observations plus S6; if XR must in reality follow SC, three of those are false positives.

# 5. Permissive Candidate

**Inductive-bias statement.** The permissive model assumes that everything not forbidden by a rule of at least medium confidence is allowed, and that the *absence* of a completion order in a 30-case sample is not evidence of a prohibition. It keeps the skeleton (D1, D2), the mandatory checks before approval (D3), SC before approval (D4) and the XR constraints (D6, S6), but it removes every ordering among CC, ER and SC. Its bias is "constraints must be justified by a rule, not by a missing observation". It is intended for exploration and sensitivity analysis, not for compliance checking.

**Boundary between reasonable generalization and forbidden behavior.**
- *Generalized (admitted although unobserved):* any completion order among CC, ER and SC, including SC before both checks. Justification: D5 is low-to-medium confidence and refers to *starting* SC after a check has "produced enough information", which under completion-only logging can happen before that check's completion event. Also, "SC after at least one of CC/ER" is a disjunctive constraint that a partial order cannot express without duplicating CC/ER/SC in an XOR of two orders, which would reintroduce the duplicate-label problems of Section 3; dropping the constraint is the honest permissive reading. All XR interleavings allowed by D6/S6 are admitted, as in the balanced model.
- *Still forbidden:* RP before AC (D2); any check, SC or XR after AC (D3, D4, D6); XR before either principal check (D6, S6); XR twice (D6); skipping CC, ER, AC, RP or ArC; a start other than RO or an end other than ArC (D1); any repetition or loop (no evidence, and loops would make the language infinite and unauditable).

**Compact formal expression.**

PO( nodes = {RO, CC, ER, SC° = ×(SC,τ), XR° = ×(XR,τ), AC, RP, ArC};
    order = RO→CC, RO→ER, RO→SC°, CC→XR°, ER→XR°, CC→AC, ER→AC, SC°→AC, XR°→AC, AC→RP, RP→ArC )

Language size: 18 traces (7 observed + 11 unobserved). The only difference from the balanced model is that the edge CC→SC° is replaced by RO→SC°.

**PM4Py code.**

```python
import pm4py
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

RO, CC, ER, SC, XR, AC, RP, AR = (
    "Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
    "Expedite Review", "Approve Configuration", "Release Production", "Archive Case")

def optional(label):
    return OperatorPOWL(Operator.XOR, [Transition(label), SilentTransition()])

ro, cc, er, ac, rp, ar = (Transition(RO), Transition(CC), Transition(ER),
                           Transition(AC), Transition(RP), Transition(AR))
sc_opt, xr_opt = optional(SC), optional(XR)

model_permissive = StrictPartialOrder([ro, cc, er, sc_opt, xr_opt, ac, rp, ar])
for a, b in [(ro, cc), (ro, er), (ro, sc_opt),   # CC, ER, SC mutually unordered (D5 relaxed)
             (cc, xr_opt), (er, xr_opt),         # D6/S6 kept
             (cc, ac), (er, ac), (sc_opt, ac), (xr_opt, ac),
             (ac, rp), (rp, ar)]:
    model_permissive.order.add_edge(a, b)
```

**Behavior deliberately excluded.**
- Everything after AC except RP,ArC; RP before AC.
- XR before CC or before ER; XR repeated; XR after AC.
- Missing CC/ER/AC/RP/ArC; repeated SC; loops of any kind.
- Traces not starting with RO or not ending with ArC.

**Known underfitting risks (and the dominant overfitting risk).**
- Underfitting: rework loops (repeat CC after a credit hold, repeat ER after design change) remain forbidden; if the real process has them the model still fails on those traces.
- Underfitting: a genuinely urgent order that runs XR before ER completes is rejected (D6 is only medium confidence).
- Overfitting/over-permissiveness: 6 of the 11 added traces put SC before CC or before both checks, contradicting the finance-side intuition behind D5 and the 0/9 observation; if a compliance team uses this model, SC-before-credit-clearance will silently pass.

# 8. Validation Code

The script below was executed against pm4py 2.7.x; API names follow that version (`parse_event_log_string` returns a DataFrame there, which all used functions accept). `pm4py.check_soundness` is deprecated, so WOFLAN is called directly; replace with `pm4py.check_soundness(net, im, fm)` if preferred.

```python
"""Validation harness for the three candidate models (pm4py >= 2.7)."""
import warnings
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.algo.simulation.playout.petri_net import algorithm as pn_playout
from pm4py.algo.analysis.woflan import algorithm as woflan

warnings.filterwarnings("ignore")

RO, CC, ER, SC, XR, AC, RP, AR = (
    "Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation",
    "Expedite Review", "Approve Configuration", "Release Production", "Archive Case")

# ------------------------------------------------------------------ 1. log
VARIANTS = [
    (12, [RO, CC, ER, SC, AC, RP, AR]),
    (7,  [RO, ER, CC, SC, AC, RP, AR]),
    (4,  [RO, CC, ER, AC, RP, AR]),
    (3,  [RO, ER, CC, AC, RP, AR]),
    (2,  [RO, CC, SC, ER, AC, RP, AR]),
    (1,  [RO, CC, ER, SC, XR, AC, RP, AR]),
    (1,  [RO, ER, CC, XR, SC, AC, RP, AR]),
]
trace_strings = [",".join(t) for n, t in VARIANTS for _ in range(n)]
assert len(trace_strings) == 30
log = pm4py.parse_event_log_string(trace_strings)
observed = {tuple(t) for _, t in VARIANTS}

# ------------------------------------------------------------------ 2. models
def leaf(label):
    return ProcessTree(label=label)

def node(op, children):
    t = ProcessTree(operator=op)
    for c in children:
        c.parent = t
        t.children.append(c)
    return t

def seq(*labels):
    return node(Operator.SEQUENCE, [leaf(l) for l in labels])

MIDDLES = [(CC, ER, SC), (ER, CC, SC), (CC, ER), (ER, CC), (CC, SC, ER),
           (CC, ER, SC, XR), (ER, CC, XR, SC)]
model_conservative = node(Operator.SEQUENCE, [
    leaf(RO), node(Operator.XOR, [seq(*m) for m in MIDDLES]), leaf(AC), leaf(RP), leaf(AR)])

def optional(label):
    return OperatorPOWL(Operator.XOR, [Transition(label), SilentTransition()])

def build_powl(sc_predecessors):
    ro, cc, er, ac, rp, ar = (Transition(RO), Transition(CC), Transition(ER),
                               Transition(AC), Transition(RP), Transition(AR))
    sc_opt, xr_opt = optional(SC), optional(XR)
    by_name = {RO: ro, CC: cc, ER: er}
    po = StrictPartialOrder([ro, cc, er, sc_opt, xr_opt, ac, rp, ar])
    edges = [(ro, cc), (ro, er), (cc, xr_opt), (er, xr_opt), (cc, ac), (er, ac),
             (sc_opt, ac), (xr_opt, ac), (ac, rp), (rp, ar)]
    edges += [(by_name[p], sc_opt) for p in sc_predecessors]
    for a, b in edges:
        po.order.add_edge(a, b)
    return po

model_balanced = build_powl(sc_predecessors=[CC])     # SC needs CC; free w.r.t. ER and XR
model_permissive = build_powl(sc_predecessors=[RO])   # SC only needs the case to exist

models = {"conservative": model_conservative, "balanced": model_balanced, "permissive": model_permissive}

# ------------------------------------------------------------------ 3-4. nets, soundness, metrics
nets, results = {}, {}
for name, m in models.items():
    net, im, fm = pm4py.convert_to_petri_net(m)
    nets[name] = (net, im, fm)
    sound = woflan.apply(net, im, fm, parameters={
        woflan.Parameters.RETURN_ASAP_WHEN_NOT_SOUND: True,
        woflan.Parameters.PRINT_DIAGNOSTICS: False})
    fit = pm4py.fitness_alignments(log, net, im, fm)
    prec = pm4py.precision_alignments(log, net, im, fm)
    gen = pm4py.generalization_tbr(log, net, im, fm)
    simp = pm4py.simplicity_petri_net(net, im, fm)
    results[name] = dict(sound=sound, places=len(net.places), transitions=len(net.transitions),
                         log_fitness=round(fit["log_fitness"], 4),
                         perc_fit=fit["percentage_of_fitting_traces"],
                         precision=round(prec, 4), generalization=round(gen, 4), simplicity=round(simp, 4))
    print(name, results[name])

# ------------------------------------------------------------------ 5. playout
# All three models are acyclic, so their languages are finite and extensive playout with a
# bound >= the longest possible trace (8 events) enumerates the language exactly.  For cyclic
# models this would only be a bounded approximation, and sampled playout never proves inclusion.
languages = {}
for name, (net, im, fm) in nets.items():
    lang = pn_playout.apply(net, im, fm, variant=pn_playout.Variants.EXTENSIVE,
                            parameters={pn_playout.Variants.EXTENSIVE.value.Parameters.MAX_TRACE_LENGTH: 10})
    languages[name] = {tuple(e["concept:name"] for e in tr) for tr in lang}
    unobserved = languages[name] - observed
    print(f"{name}: |L|={len(languages[name])}, observed covered={observed <= languages[name]}, "
          f"unobserved admitted={len(unobserved)}")
    for t in sorted(unobserved):
        print("   ", " > ".join(t))

# sampled playout (illustrative only; NOT a proof of language inclusion)
sample = pm4py.play_out(*nets["balanced"], parameters={"noTraces": 100})
sample_traces = {tuple(e["concept:name"] for e in tr) for tr in sample}
print("sampled balanced traces all inside enumerated language:", sample_traces <= languages["balanced"])

# ------------------------------------------------------------------ 6. positive / negative suite
POSITIVE = {  # expected acceptance by (conservative, balanced, permissive)
    (RO, CC, ER, SC, AC, RP, AR):        (True, True, True),
    (RO, ER, CC, XR, SC, AC, RP, AR):    (True, True, True),
    (RO, CC, ER, XR, AC, RP, AR):        (False, True, True),   # XR without SC
    (RO, CC, ER, XR, SC, AC, RP, AR):    (False, True, True),   # XR before SC, CC-first
    (RO, ER, SC, CC, AC, RP, AR):        (False, False, True),  # SC before CC (D5 symmetric)
    (RO, SC, CC, ER, AC, RP, AR):        (False, False, True),  # SC first (completion semantics)
}
NEGATIVE = {  # expected rejected by all three; the string names the earliest violated rule
    (RO, CC, ER, SC, RP, AC, AR): "D2: Release Production before Approve Configuration",
    (RO, CC, SC, AC, RP, AR): "D3: Engineering Review missing",
    (RO, ER, SC, AC, RP, AR): "D3: Credit Check missing",
    (RO, CC, ER, AC, SC, RP, AR): "D4: Supplier Confirmation after Approve Configuration",
    (RO, CC, XR, ER, SC, AC, RP, AR): "D6: Expedite Review before Engineering Review",
    (RO, CC, ER, XR, XR, SC, AC, RP, AR): "D6: Expedite Review twice",
    (CC, RO, ER, SC, AC, RP, AR): "D1: Register Order not first",
    (RO, CC, ER, SC, AC, RP): "D1: Archive Case missing",
}

def accepted(name, trace):
    """Exact membership (finite language) cross-checked with alignment fitness == 1."""
    in_lang = tuple(trace) in languages[name]
    net, im, fm = nets[name]
    tl = pm4py.parse_event_log_string([",".join(trace)])
    diag = pm4py.conformance_diagnostics_alignments(tl, net, im, fm)
    by_alignment = abs(diag[0]["fitness"] - 1.0) < 1e-9
    assert in_lang == by_alignment, (name, trace)
    return in_lang

order = ["conservative", "balanced", "permissive"]
ok = True
for trace, expected in POSITIVE.items():
    got = tuple(accepted(n, trace) for n in order)
    ok &= got == expected
    print("POS", got == expected, got, " > ".join(trace))
for trace, reason in NEGATIVE.items():
    got = tuple(accepted(n, trace) for n in order)
    ok &= got == (False, False, False)
    print("NEG", got == (False, False, False), reason)
print("SUITE PASSED" if ok else "SUITE FAILED")
```

Results of an actual run (pm4py 2.7.x): all three nets are sound workflow nets; fitness 1.0 / 100% fitting traces for all three; alignment precision 1.0 / ≈0.92 / ≈0.82; replay generalization ≈0.3 / ≈0.75 / ≈0.75; language sizes 7 / 12 / 18 with the observed 7 covered in every case; every positive/negative expectation above held and the exact-membership check agreed with the alignment check on every test trace ("SUITE PASSED"). Limitations: (i) alignment-based precision is a log-relative escaping-edges measure, not a language ratio; (ii) the replay generalization metric only reflects how often transitions were visited and does not distinguish balanced from permissive; (iii) the exhaustive comparison is possible only because the models are acyclic — if a loop were added the extensive playout would have to be bounded and the membership test would become "within bound", and sampled playout would prove nothing about inclusion.

# 9. Recommendation and Data-Collection Plan

**Recommendation.** Use `model_balanced` for immediate conformance monitoring and communication: it fits all 30 cases, every edge is traceable to a rule or to a 100%-consistent observation, and the only behavior it adds beyond the log is the XR interleavings explicitly permitted by the compliance officer (S6). Use `model_permissive` for sensitivity analysis: any case that fits permissive but not balanced is, by construction, an SC-before-CC case and therefore a direct test of D5 and of the finance intuition; the count of such cases over the next months is the statistic that decides whether the CC→SC edge stays. Keep `model_conservative` only as a regression baseline ("a variant never seen before has appeared"), not as a normative model.

**Plan to resolve the ambiguities.**

1. *Export the external/stocked attribute (S3/S4/S5).* Then split the log: for external components SC becomes mandatory and every absence is an integration failure (data-quality KPI, not process deviation); for stocked components SC absence is legitimate and any SC presence is a process question. This replaces the τ abstraction with a guard and separates missingness from optionality.
2. *Repair or backfill the SC integration and log a `data_completeness` flag per case* so that conformance on SC can be computed only on complete cases in the meantime.
3. *Collect lifecycle `start` timestamps (or assign/start events) for CC, ER, SC and XR.* This directly settles D7 and the S1/S2 dispute: interval overlap between CC and ER in a meaningful share of cases proves concurrency; CC.complete ≤ ER.start in all cases proves S1 (and would show that the 11 ER-first completion orders are a logging artefact, e.g., late posting of CC). It also tells whether SC starts before or after CC completes, which is what D5 is actually about.
4. *Record the original event timestamp with millisecond resolution and the ingestion index separately (S7)* to quantify how many CC/ER orderings are tie-breaks.
5. *Record who/what triggers XR and the order priority attribute* to learn the XR guard and to test whether D6's "after both checks" ever bends for urgent orders.
6. *Record a rework reason code* so that any repeated CC/ER (currently forbidden in all models) can be recognised as a legitimate loop rather than noise.

**Maximally informative future traces.**
- RO,ER,SC,CC,… : a single genuine occurrence refutes the balanced CC→SC edge (distinguishes balanced from permissive; tests D5 symmetry).
- RO,SC,CC,ER,… or RO,SC,ER,CC,… : tests whether SC can precede both checks (D5 lower bound).
- RO,CC,ER,XR,AC,… (XR without SC) and RO,CC,ER,XR,SC,… : confirm that XR's relation to SC is a free interleaving rather than a fixed order (conservative vs balanced).
- A stocked-component order *with* SC, or an external-component order *without* SC and no integration error: tests whether S3/S4 are rules or tendencies (XOR vs optionality hypothesis).
- Cases where CC and ER have overlapping [start, complete] intervals: decide concurrency (S2) vs sequence (S1) vs hidden-attribute XOR; if orders with a particular attribute value always show CC first and others always ER first, the pair is an XOR of sequences, not parallelism.
- Any case with a repeated CC or ER: decides whether a rework loop must be added to all three models.
- A trace with XR before ER completes: would show D6 is a tendency rather than a rule.

# 10. Uncertainty Statement

| Decision | Confidence | Basis and what would change it |
|---|---|---|
| RO first; AC→RP→ArC fixed tail; CC, ER, AC mandatory | ≈0.95 | 30/30 and high-confidence rules D1–D3. Only a new variant would change it. |
| CC and ER modeled as unordered (interleaving) rather than sequence | ≈0.85 that interleaving is the right *log-level* admissibility; ≈0.55 that the checks are truly concurrent in execution | Both orders occur; S1 is contradicted at the completion level. The alternative "hidden-attribute XOR of two sequences" has the same language, so the modeling choice is robust even if the interpretation is wrong. Lifecycle data would settle it. |
| SC optional via τ (rather than mandatory with data loss) | ≈0.75 that most of the 7 skips are legitimate | S4 plus the arithmetic on S5 (5–10% loss ≈ 1–3 traces). If the attribute export shows all 7 were external components, SC must become mandatory and the τ branch removed. |
| CC→SC edge kept in balanced | ≈0.60 | 0/9 counter-examples against a 2/14 base rate on the ER side is suggestive, not conclusive; D5 (low-medium) points the other way. One genuine ER,SC,CC trace flips this. |
| SC unordered w.r.t. ER | ≈0.85 | Directly observed both ways (V5 vs V1/V2). |
| XR optional, after both checks, unordered w.r.t. SC, before AC | ≈0.75 for the structure; ≈0.35 that the two observed XR traces are representative of XR frequency and placement | Two observations plus D6/S6. Structure is rule-based; frequency is unknown. |
| No loops / no repetition | ≈0.70 | No repetition in 30 cases; a rare rework loop with per-case probability of a few percent could easily be unobserved. |
| Recommending balanced over permissive | ≈0.65 | Hinges on the CC→SC decision above and on the intended use (compliance). |

**Alternative interpretations that would materially change the recommendation.**

1. *S1 is true and the 11 ER-first completion orders are a logging artefact* (e.g., CC completions are posted in a nightly batch while ER is logged in real time). Then the real process is →(CC, ER), the 11 "ER-first" traces are data-quality problems, and the balanced model hides a genuine control weakness by admitting both orders. The recommendation would become: fix the timestamp source, model CC→ER as a sequence, and treat ER-before-CC as a deviation to investigate. Lifecycle timestamps or a comparison with the source system's own audit trail would confirm or refute this.
2. *All SC-less traces are lost events* (no stocked components in this sample). Then SC is mandatory, the τ branch is masking an integration failure rate of ≈23% (far above the engineer's 5–10% estimate), and the immediate action is a data-pipeline fix rather than process modeling; the conservative and balanced models would both be wrong in the same way.
3. *D5 is symmetric and the CC→SC pattern is coincidental.* Then the permissive model is the correct normative model and the balanced model will start flagging legitimate ER,SC,CC cases; the fraction of such cases in the next few hundred orders decides this, and Section 9's plan captures it directly.
4. *The CC/ER order is decided by a hidden attribute* (a customer segment or order value threshold). The trace language of all three models is unaffected, but the process description, the resource planning implications and the conformance semantics for lifecycle-aware checking would change; this can only be detected once attributes or start timestamps are exported.
