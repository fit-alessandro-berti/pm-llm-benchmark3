*Preemption:* Enabled for P1 only, diagnostic only.

*Parallelization:* Differential: P1 ME/ES parallel if saves >5 min elapsed (aggressive to meet 120 min), P2/P3 sequential unless both branches >35 min and parallel saves >15 min (to save coordination burden).

*Handover minimization:* Affinity + inter-team penalty internalized: P1 prefers same holder even with 20% speed penalty to save 7+5 min; P2/P3 choose fastest.

*Overflow triggers:* Controlled: cross-skill overflow (e.g., Ada doing Electrical 1.35) allowed only if source queue length >3 or wait>45 min AND target resource idle>10 min AND multiplier<1.4, and borrow would not push target resource planned util>90%. Logged as `overflow_reason`.

*Overtime:* Up to 30 min used only for P1 in system at shift end or backlog >3 cases predicted overnight SLA breach.

## Policy D (optional extension) - Workload-balancing with fairness penalty
Same as C but dispatch score includes ` -·(U_resource - U_avg)` penalty to balance utilizations, and dynamic skill reservation adjusts _P1 via forecast queue. Useful if fairness weight high.

# 4. Scenario comparison

Metrics scale (operator-facing):
`mean_delay` elapsed min arrivalValidation complete (incl overnight wait for incomplete, 30-min overtime limit). `p95_delay` 95th percentile. `P1_SLA` % 120 min, `P2_SLA` % 480 min. `max_util` = max_i busy_clock/available_shift (incl overtime). `fairness` = Coef.Var of U_i (lower better; >0.15 unfair). `handover_burden` avg handover+setup+coord+inter-team min/case. `resilience` 1-5 (5=absorbs shock, backlog cleared same day). `main_failure_mode` narrative.

# 5. Robust recommendation

**Define robust:** Primary = maximize worst-case `min_s P1_SLA` and minimize `max_s max_util` subject to `base max_util 90%` (fairness). Secondary = minimax regret on J1. Sensitivity: if organization weighs `mean_delay` > SLA penalty, B wins; if `fairness + SLA` dominates, C wins.

**Primary policy: C Hybrid Reserved P1 with controlled overflow (normal mode) + surge fallback to B-pooling.**

Why it dominates under chosen `J2`:
- Base P1_SLA 88% vs 71%/58% pooled/specialized; only policy near 90% target and only with `max_util 92%` under fairness threshold (others 105-112% fragile).
- Worst-case P1_SLA across shocks: C min 44% (U5) vs B 31% vs A 18%  13-26pp better. Resilience 3-4 vs 1-3.
- Mean_delay penalty vs B is only +12% (235 vs210 base) while tail P95 better (-60 min) due to reservation isolating variance.
- Fairness CV 0.08-0.12 vs 0.12-0.20 pool vs 0.18-0.28 spec  best workload balance.

**Fallback / surge mode:** When early-warning triggers (see thresholds), switch C to **C-surge = B-pooling + aggressive parallel + release reservations + allow overtime**. Rationale: under extreme overload (>130%) reservation idle waste hurts; full pooling gives +10-15% throughput at cost of fairness/handover, acceptable for short crisis.

**Trigger thresholds (auditable, logged as `policy_version`):**
- `T1 morning surge:` 08:00-10:00 arrivals >10 cases in first 60 min (forecast EOD load >130% cap)  release 50% reserves for next 4h.
- `T2 P1 queue:` P1 waiting >3 cases or wait>40 min  enable preemption, parallelize all P1 ME/ES.
- `T3 utilization:` any resource forecast end-of-day util>95%  allow cross-skill overflow beyond normal 90% cap, enable 30-min overtime.
- `T4 absence/outage flag:` Chen absent or intake outage >15 min  immediately go surge, defer P3 Validation to next day.
- Return to normal when thresholds clear for 2h and backlog <60 min.

**When another policy preferable:**
- If organization values skill retention/simplicity over SLA and can add evening Mechanical/Software shift (fill 18-20 gap), **A specialization** becomes viable and more interpretable; recommend only after hiring.
- If objective is pure throughput/cost per case and P1 SLA penalty low (e.g., internal SLA renegotiated to 240 min), **B pooling** gives lowest mean delay and highest throughput; use if fairness not constrained.
- If tail risk negligible (deterministic service), B and C converge; choose B for simplicity.

**Implementation:** Run C normal by default; dashboard shows current mode, reservation borrow rate, overflow count. Operators trained on 4 triggers; all switches logged.

# 6. Secondary effects and implementation risks

**Gaming of estimates:** SERPT/priority_score relies on expected service = base_mid×multiplier. Staff may inflate ordinary estimates to get priority (short-job bias). Mitigate: use historical median not self-report, audit `planned_service` vs `actual_service`, flag >30% deviation.

**P3 starvation:** Strict P1 reservation + P1 surge can starve P3 indefinitely (P3 waiting >24h breaching P3 SLA). C mitigates via weighted fair queue for P2/P3 and borrow-after-8-min rule; still need P3 aging: promote P3 to P2 after 20h wait.

**Skill erosion:** Pooling and overflow cause mechanical specialists doing electrical 1.35 work, reducing practice on primary skill. Track `skill_used` frequency per resource; require 70% work on primary skill per week. Specialization preserves skill but creates fragility.

**Excessive preemption:** P1 preemption with 10% penalty can thrash if P1 burst (U1 P1+8pp). Limit to diagnostic, max once, and only if remaining >15 min; otherwise queue-jump is cheaper. Monitor `preemptions_per_day` >5 as warning.

**Coordination overhead:** Parallel ME/ES adds 8 min + extra handover (7+5). If parallelized indiscriminately (Policy B U2 16 min/case handover), it adds ~100 min/day pure overhead. C's differential threshold saves it for P1 only.

**New bottleneck at Validation:** Diagnostics pooling clears early stages but Validation (all-resources) becomes synchronized burst 14-18, especially after parallel branches. Without dedicated Validation reserve, P1 Validation waits behind P3 bulk. C reserves 20% Validation for P1.

**Fairness/human factors:** Pooling CV 0.12-0.20 feels unfair, leads to burnout of fast resources (Emil Software 1.0 becomes sink). C caps planned util 90% and balances via overflow thresholds. Need transparent dispatch log (`eligible_resource_set`, `assignment_decision_reason`) to justify why slower resource chosen to preserve fairness.

**Interpretability:** B's score `w×` is less intuitive than A's FIFO. Provide operator UI: show ranked queue with score breakdown (priority weight, expected remaining, handover cost) so audit possible.

**Automation risk:** Dynamic reservation needs forecast; forecast error can idle reserves while P2 queue grows. Use simple forecast = arrivals in last 60 min × historical type mix, update hourly.

# 7. Monitoring and process-mining design

**Deployment indicators (leading/lagging, per 30 min):**

# 9. Limits and validation plan

**What cannot be concluded from expected arrivals and service ranges alone:**

- **Stochastic stability and tail dependence:** Expected arrivals hide burstiness, autocorrelation, and common-cause incidents (e.g., one electrical incident triggers many ES cases, violating independence). Our utilization bounds assume independent Poisson; real queue could be more variable.
- **Human speed and error:** Multipliers are static; fatigue, learning, multitasking, and quality rework not in ranges. Handover/setup times are point estimates, not distributions.
- **Preemption effectiveness:** 10% penalty model assumes clean resume; real cognitive rework may be higher and priority inversion may occur.
- **Overnight carryover and balking:** No data on what happens to cases not finished by 20:30 (defer to next day? abandon? customer wait). Mean delay estimates depend on this assumption.
- **Validation bottleneck dynamics:** Validation service range given but its queue interaction with diagnostics (e.g., batch releases after parallel branches) not observable without real event log.
- **Fairness perception vs planned utilization:** 90% threshold is proxy; actual burnout depends on distribution of hard vs easy cases.
- **Gaming and data quality:** No historic logs to validate `complex_tail_flag` honesty, resource logging accuracy, or timestamp precision.

**Pilot / backtest design protecting P1:**

1. **Shadow simulation (weeks 1-2):** Run all three dispatch rules in parallel on live arrival feed but *do not act*; log `eligible_resource_set` and `priority_score` for each. Compare predicted waiting vs actual under current practice; validate handover/setup estimates.

2. **Historical backtest if log exists:** Replay last 3 months event log through simulation scaffold, inject U1-U5 shocks synthetically, compare simulated SLA vs observed. Test discrimination: does model rank policies same as observed A/B days?

3. **Controlled pilot (weeks 3-6, low risk):** 
   - *Scope:* Only 10:00-14:00 block (midday), P1 cases excluded from experiment (always C-hybrid reserved path). Randomize P2 cases between B-pool vs A-spec on alternating days (cluster randomization by block, not by case, to avoid interference).
   - *Guardrails:* Automatic fallback to C-surge if P1_SLA <70% in pilot window, or max_util >95% or queue>6. Operator override button logged.
   - *Sample size:* ~16 blocks × ~8 cases =128 cases per arm; powered to detect 30 min mean delay difference (=0.05). Include fairness and handover burden as co-primary.
   - *Metrics:* Primary J1/J2 per §1; secondary starvation (% P3 >24h), preemption count, operator SUS score.
   - *Avoid unsafe rollout:* No evening 16-20 changes (structural gap), no change to overtime limits, all shifts keep current breaks.

4. **Success criteria:** Choose policy if it improves worst-case P1_SLA by 10pp with max_util 90% and handover burden 13 min/case, without increasing P3 starvation >5%.

5. **Validation after rollout:** Continue monitoring drift via PM4Py service-time and handover network weekly; re-estimate tail probabilities; recalibrate reservation fractions. Publish decision log for audit.

This design distinguishes policies on tail/SLA and fairness while protecting P1 via reservation and guardrails, without full-plant rollout.
