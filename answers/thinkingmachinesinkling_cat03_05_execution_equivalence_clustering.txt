## 1. Equivalence design space

We center every execution on its lead `Order` object. All local identifiers (those not prefixed with `EXT`) are considered arbitrary labels; only the `EXT` flag carries semantic weight, because it signals that an object’s lifecycle is anchored elsewhere.

### 1.1 Activity-sequence equivalence (ASE)

**Definition.** Two executions are ASE-equivalent iff their timestamp-ordered lists of activity labels are identical as sequences. If two or more events share the same timestamp, they form an antichain; ASE requires that the multiset of activities at that timestamp be equal and that the induced partial order be isomorphic.

**Invariants preserved.** The temporal ordering of activities; the multiset of activities performed.

**Information discarded.** All object types, object identifiers (local and external), event-object incidence (E2O), object-object relations (O2O), multiplicities, qualifiers, and cross-order links.

**Formal properties.** Reflexive, symmetric, and transitive (equality of canonical string lists).

**Concurrency handling.** Same-timestamp events are compared as antichains; internal ordering within the antichain is ignored.

**Role in clustering.** ASE produces the coarsest partition. Here it yields four clusters: `BL` (baseline linear: X1, X2, X5, X6, X7), `SPCD` (split-pack, consolidated-delivery: X3), `SPSDP` (split-pack, split-delivery, partial-pay: X4), and `RET` (return-repack: X8).

### 1.2 Typed structural isomorphism (TSI)

**Definition.** For each execution, rename local object identifiers within each object type by first-appearance order (`Order`  `Order_L1`, `Item`  `Item_L1`, `Item_L2`, etc.). Rename external objects canonically (`EXT-OA`  `Order_EXT1`, `EXT-IA`  `Item_EXT1`, etc.). Compare the resulting canonical structures for equality of:
- the ordered sequence of events (activity label + multiset of `(type, canonical_id, ext_flag)` pairs);
- the O2O adjacency graph (subject type, canonical subject id, predicate, object type, canonical object id), **ignoring qualifier annotations** (e.g., `partial_settles` vs `completes_settlement` are both mapped to `settles`).

**Invariants preserved.** Object-type multiplicities; which types participate in each event; presence/absence of O2O edges; `EXT` vs local distinction; temporal event order.

**Information discarded.** Literal local identifier strings; qualifier values on O2O relations; the semantic reason for an absence (e.g., whether an item is missing from a dispatch because it was never added or because it was replaced).

**Formal properties.** Reflexive, symmetric, and transitive on the space of canonical representations; isomorphism of finite labeled graphs with a linear extension (event order) is an equivalence relation.

**Concurrency handling.** Events with identical timestamps are treated as incomparable nodes in a partial order; the canonical form stores the reachability relation rather than a strict linear index.

**Role in clustering.** TSI distinguishes X1/X2 (isomorphic), X3 (two `Package` nodes, one `Delivery` carrying both), X4 (two `Delivery` nodes, two `Payment` nodes), X5 (`EXT` objects in `Pack` and `Dispatch`), X6 (`EXT` object in `Issue` and `Record`), X7 (`Item` present in `Dispatch` but absent from `Pack` adjacency without qualifier context—structurally anomalous), and X8 (extra `Return` and `Inspect` events, second `Package` and `Delivery`).

### 1.3 Business-semantic equivalence (BSE) — preferred

**Definition.** Two executions are BSE-equivalent iff their **canonical semantic signatures** (Section 2) are identical. The signature encodes:
- logistics motif: counts and internal structures of `Pack`, `Dispatch`, `Delivery`, `Return`, `Inspect`;
- financial motif: `Invoice` sharing patterns and `Payment` settlement types (`full`, `partial`, `complete`, `unspecified`);
- lifecycle qualifiers: `removed_before_dispatch`, `replaces`, etc.;
- cross-order flags: presence of `EXT` objects inside specific activities or O2O relations.

**Invariants preserved.** Everything in TSI **plus** qualifier annotations, the precise role of external objects (logistics vs financial), and lifecycle motifs (replacement, return-inspection-repack).

**Information discarded.** Only meaningless local identifier strings.

**Formal properties.** Reflexive, symmetric, transitive (equality of serialized canonical signatures).

**Concurrency handling.** Same as TSI: event precedence is preserved, but simultaneous events are represented as sets with an explicit antichain flag.

**Role in clustering.** This is the finest meaningful clustering used for interpretation. It separates X5 (cross-order logistics) from X6 (cross-order finance) despite both having ASE cluster `BL`, and it isolates X7 (hidden replacement) and X8 (return lifecycle).

---

### 1.4 Compressed multiplicity equivalence (CME) — optional

**Definition.** Collapse the event sequence to a multiset of activity counts (e.g., `Add Item`: 2). Summarize object multiplicities globally (`Item`: 2, `Package`: 2, etc.). Represent cross-order links as boolean presence flags per link type. Ignore event order, specific object associations, and qualifiers.

**Invariants preserved.** Activity multiset; global object-type counts; presence/absence of any `EXT` link; presence of lifecycle keywords (`Return`, `Inspect`).

**Information discarded.** Event ordering; which specific objects are linked in which event; O2O qualifiers; identity of external partners.

**Formal properties.** Reflexive, symmetric, transitive (multiset equality).

**Role.** Useful for high-level dashboards but dangerous for diagnostics, as it merges X3 and X4 if not careful with counts, and collapses X7 into `BL`.

## 2. Canonical signatures

We define the canonical signature for BSE. The algorithm is reproducible: it always produces the same string for isomorphic executions regardless of local naming.

```python
def canonical_bse_signature(execution, lead_type="Order"):
    # execution: ordered list of events; each event = (activity, {type:id_set})
    # o2o: list of (subj_type, subj_id, pred, qualifier_or_None,
    #                  obj_type, obj_id)
    # Step 1: Identify lead and rename locals by first appearance
    first_idx = {t: {} for t in all_local_types}
    rename_local = {}
    for ev in execution.events:
        for (t, ids) in ev.objects.items():
            if not any(i.startswith("EXT") for i in ids):
                for i in ids:
                    if i not in first_idx[t]:
                        first_idx[t][i] = len(first_idx[t])
    # Assign canonical IDs L1, L2, ...
    for t in first_idx:
        sorted_ids = sorted(first_idx[t], key=first_idx[t].get)
        for rank, i in enumerate(sorted_ids, 1):
            rename_local[i] = f"{t}_L{rank}"

    # Rename EXT objects canonically by type and appearance order
    ext_counter = {}
    rename_ext = {}
    for ev in execution.events:
        for (t, ids) in ev.objects.items():
            for i in ids:
                if i.startswith("EXT"):
                    base = i.split("-")[1] if "-" in i else "UNK"
                    ext_counter.setdefault(t, 0)
                    ext_counter[t] += 1
                    rename_ext[i] = f"{t}_EXT{ext_counter[t]}"

    # Step 2: Canonical events (ordered)
    canon_events = []
    for ev in execution.events:
        act = ev.activity
        refs = {}
        for (t, ids) in ev.objects.items():
            canon_ids = set()
            for i in ids:
                canon_ids.add(rename_local.get(i, rename_ext.get(i, i)))
            refs[t] = tuple(sorted(canon_ids))
        # Preserve event as (activity, tuple of sorted (type, tuple(ids)))
        obj_key = tuple(sorted((t, refs[t]) for t in refs))
        canon_events.append((act, obj_key))

    # Step 3: Canonical O2O with qualifiers
    canon_o2o = []
    for (st, sid, pred, q, ot, oid) in execution.o2o:
        sid_c = rename_local.get(sid, rename_ext.get(sid, sid))
        oid_c = rename_local.get(oid, rename_ext.get(oid, oid))
        q_c = q if q is not None else "default"
        canon_o2o.append((st, sid_c, pred, q_c, ot, oid_c))
    canon_o2o.sort()

    # Step 4: Signature assembly (hashable representation)
    sig = {
        "version": "BSE-v1",
        "events": canon_events,
        "o2o": canon_o2o,
    }
    return json.dumps(sig, sort_keys=True)
```

The signature is invariant to local renaming, preserves `EXT` flags, keeps event order, retains all E2O and O2O qualifiers, and records repeated activities explicitly.

## 4. Cluster interpretations

### `IF` (X1, X2)
**Concise signature.** One `Pack` with exactly two local items, one `Dispatch` carrying that package, one `Invoice` billed to the lead order, one `Payment` with `settles` qualifier (full). Zero external objects, zero lifecycle qualifiers.

**Business behavior.** Standard end-to-end fulfillment: all items are packed together, shipped in a single delivery, invoiced once, and paid in full. The customer receives exactly what was added.

**Operational risks / opportunities.** Low complexity; ideal for SLA measurement (time from `Create` to `Record Payment`). Opportunity: use as baseline for throughput metrics.

**Traditional flattening failure.** Case-based process mining (e.g., one trace per `Order`) represents this perfectly; however, it provides no protection against hidden deviations (see `HS`).

**Stability under repair.** Highly stable. The only repair risk is misclassifying a hidden replacement (`HS`) as `IF` if the qualifier is lost during extraction.

---

### `SLIF` (X3)
**Concise signature.** Two `Package` nodes (`P1`: item 1; `P2`: item 2); one `Delivery` carrying both; single invoice/payment; no external objects.

**Business behavior.** Items are separated into distinct packages (e.g., due to size, fragility, or warehouse zones) but consolidated into one delivery (e.g., same truck). Billing remains unified.

**Operational risks / opportunities.** Risk: delivery-level tracking must aggregate multiple package IDs; if one package is damaged, the delivery record may not immediately reveal which item is affected. Opportunity: optimize consolidation ratios without splitting invoices.

**Traditional flattening failure.** A case-based model that treats `Package` as a separate case fragments the execution; the unified `Delivery` event is either duplicated or lost, breaking the one-to-many logistics view.

**Stability under repair.** Stable as long as the `carries` relation lists both packages. If repair splits the delivery record into two, `SLIF` degrades to `SFPS`.

---

### `SFPS` (X4)
**Concise signature.** Two `Package` nodes; two `Delivery` nodes (each carrying one); one `Invoice`; two `Payment` events with distinct settlement qualifiers (`partial_settles`, `completes_settlement`).

**Business behavior.** The order is fulfilled in waves (e.g., partial stock availability). A single invoice is issued, but settlement occurs in installments tied to separate deliveries or contractual terms.

**Operational risks / opportunities.** Risk: reconciliation of payments to deliveries is ambiguous—does `M41` settle `D41` specifically, or the whole invoice? Opportunity: design milestone-based billing tied to delivery waves.

**Traditional flattening failure.** Flattening by `Order` forces two deliveries and two payments into a single trace with loops or parallel branches that violate standard sequential process models. Flattening by `Package` splits the invoice and loses the unified billing context.

**Stability under repair.** Moderately stable. If payment qualifiers are stripped or payments are merged into an aggregate amount, `SFPS` collapses toward `SLIF` or `IF`, hiding the installment structure.

---

### `COLI` (X5)
**Concise signature.** `Pack` and `Dispatch` events include an external `Order` (`EXT-OA`) and an external `Item` (`EXT-IA`). The `Package` (`P51`) packs the local items plus `EXT-IA`. The `Invoice` and `Payment` involve only the lead order.

**Business behavior.** A shared logistics execution: the lead order is packed together with an item belonging to another order (`EXT-OA`), possibly for consolidated shipping. The financial obligation, however, remains isolated to the lead order (`V51` bills only `O5`).

**Operational risks / opportunities.** Risk: misallocation of `EXT-IA` to the wrong invoice; delivery responsibility ambiguity if damage occurs. Opportunity: reduce shipping costs through cross-order consolidation, but requires explicit item-to-order reconciliation.

**Traditional flattening failure.** Any flattening centered solely on `O5` loses `EXT-OA` and `EXT-IA`, making the package contents appear anomalous (three items for a two-item order). Centering on `EXT-OA` creates an orphan execution.

**Stability under repair.** Unstable if `EXT` references are stripped (collapses to `IF`). Stable only when external links are preserved in extraction.

---

### `COFI` (X6)
**Concise signature.** Logistics structure identical to `IF` (one pack, one delivery, local items only). `Issue Invoice` and `Record Payment` include `EXT-OB`. The invoice (`V61`) is shared; payment (`M61`) settles it without order-level allocation.

**Business behavior.** Joint financial settlement: multiple orders are invoiced together (e.g., monthly billing). The logistics execution is isolated—each order is packed and delivered separately—but the financial lifecycle is coupled.

**Operational risks / opportunities.** Risk: payment disputes require disaggregating `V61` across orders; if `EXT-OB` is unknown, `O6` appears to have an unreconciled invoice. Opportunity: streamline accounts-receivable for regular customers.

**Traditional flattening failure.** Case-based mining on `Order` either duplicates `V61` across both orders or assigns it to `O6` alone, destroying the shared-invoice semantics.

**Stability under repair.** Unstable if external references are removed; then `COFI` collapses to `IF`.

---

### `HS` (X7)
**Concise signature.** Activity sequence identical to `IF`. `Pack` (`P71`) includes `I71` and `I72`. `Dispatch` (`D71`) includes `I72`, `P71`, and `D71`, but **not** `I71`. O2O qualifier: `removed_before_dispatch` links `P71` to `I71`.

**Business behavior.** A hidden substitution: both items are added and packed, but one (`I71`) is removed or replaced (`I72` takes its place) before dispatch. The customer receives `I72`. The invoice is still issued for `O7`, presumably reflecting the corrected contents, but the event log reveals the discrepancy only through the qualifier and the missing item in `Dispatch`.

**Operational risks / opportunities.** Risk: inventory discrepancy; customer receives goods different from the original pack list; quality-control failure if replacement was due to damage. Critical risk: **activity-label-only monitoring misses this entirely**.

**Traditional flattening failure.** Any flattening that ignores O2O qualifiers and E2O absence (e.g., standard case-based mining or ASE clustering) represents `HS` identically to `IF`, rendering the substitution invisible.

**Stability under repair.** Highly unstable. If the qualifier `removed_before_dispatch` is lost during data cleaning, or if the `Dispatch` event is “repaired” to include `I71` (incorrectly), the cluster assignment shifts to `IF`.

---

### `RRR` (X8)
**Concise signature.** `P81` (`I81`, `I82`) dispatched via `D81`. Then `Return Item` (`I82` via `D81`), `Inspect Return` (`I82`), second `Pack` (`P82`: `I82`), second `Dispatch` (`D82`: `P82`), then `Issue Invoice` and `Record Payment`. Qualifier indicates `P82` replaces `P81` for `I82`.

**Business behavior.** Post-delivery return: the customer returns `I82`, it is inspected, repacked (`P82`), and redelivered (`D82`). The invoice (`V81`) and payment (`M81`) occur after the resolution cycle.

**Operational risks / opportunities.** Risk: long cycle time; quality-control failure if `Inspect` reveals damage; inventory in limbo during return-inspection. Opportunity: capture return-rate metrics by linking `Inspect` outcomes to original deliveries.

**Traditional flattening failure.** Sequential process models reject loops (`Dispatch`  `Return`  `Pack`). Case-based flattening either breaks the trace into two cases (`P81` and `P82`) or creates an invalid loop that violates model constraints.

**Stability under repair.** Stable if `Return` and `Inspect` activities are preserved. If they are filtered as “noise,” `RRR` collapses to a multi-delivery cluster (`SFPS`-like).

## 5. Borderline cases

### X1 versus X2
Under ASE, TSI, and BSE, these are equivalent. The only defensible disagreement arises if one adopts a **strict intra-event tuple ordering** structural definition that preserves the literal sequence of object IDs within an event record (e.g., `Item:I11,I12` vs `Item:I22,I21`). Under such a definition—before canonical renaming—X1 and X2 differ. Once canonical renaming is applied (sorting within the multiset), they merge. This illustrates that **identifier-independent canonicalization is a design choice**, not a given.

### X1 versus X5
ASE clusters them together (`BL`). TSI separates them (`ISO` vs `COL`): X5 contains `EXT-OA` and `EXT-IA` in `Pack` and `Dispatch`. BSE also separates them (`IF` vs `COLI`). The disagreement is between **surface-level activity equivalence** and **structural/semantic equivalence**. A flat log analyst would see identical steps; an object-centric analyst sees shared logistics resources that change delivery accountability and package contents.

### X1 versus X6
Again, ASE groups them (`BL`). TSI separates them (`COF`) because `EXT-OB` participates in `Issue Invoice` and `Record Payment`. BSE separates them (`COFI`). The disagreement highlights that **financial sharing is invisible in the logistics activity stream**. A process-mining tool that flattens by `Order` and ignores `EXT` objects will treat X6 as a standard fulfillment, missing the joint-billing risk.

### X1 versus X7
ASE groups them (`BL`). TSI distinguishes them (`SUB` vs `ISO`) because the `Dispatch` event in X7 includes `Item:I72` (absent in X1’s `Dispatch`) and excludes `Item:I71` (present in X1’s `Pack`). BSE distinguishes them sharply (`HS` vs `IF`) via the `removed_before_dispatch` qualifier. The disagreement demonstrates that **activity-label equivalence is insufficient for quality control**: X7 represents a substitution that only O2O qualifiers and E2O absence reveal.

### X3 versus X4
Both involve split packages (`SPCD` vs `SPSDP` under ASE). TSI distinguishes them (`SLC` vs `SLSF`) due to delivery multiplicity (one vs two) and payment multiplicity. BSE distinguishes them (`SLIF` vs `SFPS`). A defensible disagreement can occur if one adopts a **logistics-only semantic view** that ignores financial events: both have split packages and are therefore “split logistics.” Another defensible view (full BSE) separates them because settlement structure (single vs installment) is a business-critical distinction. Thus, **domain scope determines cluster boundaries**.

### X4 versus X8
Under ASE they differ (`SPSDP` vs `RET`). However, a **structural equivalence that ignores post-delivery lifecycle activities** (`Return`, `Inspect`) and ignores replacement qualifiers might observe that both have two `Package` nodes, two `Delivery` nodes, and one `Invoice`. Under such a reduced TSI variant, X4 and X8 could be merged as “multi-delivery fulfillment.” BSE refuses this merger (`SFPS` vs `RRR`) because the return-inspection-repack motif is a distinct business lifecycle involving quality failure and inventory recovery. This shows that **ignoring lifecycle qualifiers and return activities creates false structural similarity**.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### What PM4Py preserves
`pm4py.cluster_equivalent_ocel(ocel, obj_type="Order", max_objs=...)` computes, for each execution centered on the specified object type, an equivalence key. The key typically encodes:
- the sequence (or multiset) of activities within the execution;
- the specific object identifiers (raw strings) involved in each event;
- the object-object relationships present in the execution’s local subgraph.

Because raw local IDs are included literally, X1 (`O1`, `I11`, `P11`) and X2 (`O2`, `I21`, `P21`) receive different keys despite being isomorphic.

### Why raw identifiers make clusters too fine
In a large log with thousands of orders, every execution gets a unique key unless it is an exact duplicate. This produces a **degenerate clustering** (mostly singletons), defeating the purpose of equivalence analysis. External objects (`EXT-OA`) are also included literally, so two executions with the same cross-order partner type but different partner IDs are separated, even when the business pattern (`COLI`) is identical.

### Canonicalization and post-processing
The remedy is to canonicalize **before** or **after** calling the function:
1. **Pre-process:** Rename all local objects in the OCEL to canonical IDs (`Order_L1`, `Item_L1`, ...) and normalize `EXT` references to canonical external roles (`Order_EXT1`). Then call `cluster_equivalent_ocel`.
2. **Post-process:** Compute BSE canonical signatures (Section 2) for all executions in each returned cluster; merge clusters that share the same signature.

```python
import pm4py
import json

# Assume `ocel` is loaded, with executions accessible
# Step 1: Raw exact clustering (too fine)
raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    obj_type="Order",
    max_objs=15   # truncate very large connected subgraphs
)

# Step 2: Custom canonicalization function (Section 2)
def build_sig(exec_data):
    return canonical_bse_signature(exec_data)

# Step 3: Post-process merge by BSE canonical key
merged = {}
for cluster_key, exec_ids in raw_clusters.items():
    # Use first execution to represent cluster semantics
    rep = ocel.get_execution(exec_ids[0])
    canon_key = build_sig(rep)
    merged.setdefault(canon_key, set()).update(exec_ids)

# Step 4: Aggregate for reporting
final_clusters = {
    k: sorted(v) for k, v in merged.items()
}

# Optional: label clusters by dominant pattern
labels = {}
for k, v in final_clusters.items():
    # Heuristic: check presence of Return -> RRR; check EXT in Invoice -> COFI; etc.
    labels[k] = classify_by_signature(k)
```

### When exact equivalence is preferable
Exact (raw-ID) clustering is preferable for **forensic traceability** and **audit replay**, where every instance must be individually identifiable. It is also useful when object identifiers encode hidden semantics (e.g., `Order_URGENT` vs `Order_STND`) that are not captured by type alone.

### Effects of `max_objs` and large executions
`max_objs` limits the number of objects included in an execution’s subgraph. In X5 and X6, if `max_objs` is set too low (e.g., 5), the external object (`EXT-OA`, `EXT-OB`) may be truncated. This causes `COLI` and `COFI` to be misclassified as `IF`. Conversely, in very large connected logs (e.g., a marketplace where one delivery contains hundreds of items from hundreds of orders), `max_objs` may force truncation that splits a true cluster or merges disparate fragments. The practical recommendation is to set `max_objs` generously (based on the 99th percentile of execution size) and rely on canonical post-processing rather than truncation to control cluster granularity.

## 7. Robustness analysis

We examine how cluster assignments shift under five perturbations applied to the BSE framework.

### 7.1 Ignore all O2O qualifiers
Removing `removed_before_dispatch`, `partial_settles`, `completes_settlement`, and `replaces`:
- `SFPS` (X4) retains two payments but loses settlement semantics; it remains distinct from `IF` by payment multiplicity but its “installment” interpretation is weakened.
- `HS` (X7) loses its replacement explanation; without the qualifier, the absence of `I71` from `Dispatch` becomes unexplained, but the structural anomaly (`Item` in `Dispatch`) remains, so X7 stays in `SUB`/`HS` rather than `IF` (assuming E2O is preserved).
- `RRR` (X8) loses the replacement qualifier for `P82`; however, the `Return`/`Inspect` sequence still distinguishes it.

### 7.2 Ignore external objects (`EXT`)
Stripping all `EXT` references:
- X5 (`COLI`) collapses to `IF`: `Pack` contains only two items, `Dispatch` only the package.
- X6 (`COFI`) collapses to `IF`: `Invoice` and `Payment` involve only the lead order.
- This demonstrates that **cross-order clusters are artifacts of the `EXT` flag**; without it, shared-resource patterns disappear entirely.

### 7.3 Collapse repeated same-label events
Replacing consecutive or global repetitions with a count (`Add Item × 2`):
- Sequence order is lost; partial-order constraints must be reconstructed.
- X4 (`SPSDP`) and X8 (`RET`) both have `Pack` and `Dispatch` twice, but X8 includes `Return`/`Inspect`. The collapse still distinguishes them by activity multiset.
- However, interleaved structures (e.g., `Pack`–`Dispatch`–`Pack`–`Dispatch` in X4) become indistinguishable from `Pack`–`Pack`–`Dispatch`–`Dispatch`, so **delivery-package pairing is lost**.

### 7.4 Treat `Pack` and `Dispatch` as partial order
If `Pack`  `Dispatch` is required but cross-pair ordering is free:
- X3 (`SPCD`) has both `Pack` events preceding the single `Dispatch`; its partial order is `{P1<D1, P2<D1}`.
- X4 (`SPSDP`) has `{P1<D1, P2<D2}` with `P1||P2` and `D1||D2`.
These partial orders are non-isomorphic, so X3 and X4 remain separated. This perturbation mainly affects variant executions where independent packages are packed in different orders but delivered together; they now merge, which is often **business-correct** for consolidation analysis.

### 7.5 Treat payment multiplicity as amount attribute
If two payments (`M41`, `M42`) are collapsed into one `Record Payment` with an `amount` attribute:
- X4 (`SFPS`) loses its second payment event; its sequence becomes closer to X3 (`SPCD`): both have one `Record` event.
- The cluster `SFPS` disappears unless the cluster definition explicitly checks for an amount-aggregation attribute.
- This highlights that **structural representations of financial multiplicity are sensitive to data-model choices**: event-based vs. attribute-based modeling changes cluster topology.

## 8. Limitations and recommendation

### Recommended equivalence levels by purpose

| Purpose | Recommended level | Justification |
|---|---|---|
| **Compliance monitoring** | **BSE (full)** | Must detect hidden substitutions (`HS`), shared invoices (`COFI`), cross-order logistics (`COLI`), and partial settlements (`SFPS`). Qualifiers and `EXT` links are audit-critical. |
| **Operational segmentation** | **BSE with logistics/financial sub-clusters** | Group executions by fulfillment pattern (`IF`, `SLIF`, `SFPS`, `RRR`) and separately by financial coupling (`COFI`, `COLI`). This supports targeted operational improvement (e.g., reduce return rates in `RRR`, improve consolidation in `SLIF`). |
| **Root-cause analysis** | **TSI + BSE deviation flags** | Start with TSI to detect structural anomalies (wrong object counts, missing events), then apply BSE within clusters to find qualifier-level deviations (e.g., `HS` hidden inside an `IF` cluster). |
| **Descriptive reporting** | **ASE or CME** | Stakeholders require high-level counts (how many returns? how many split deliveries?) without object-ID noise. CME summarizes safely; ASE preserves temporal intuition. |

### Why no single equivalence is best
The four purposes optimize different points on the **detail-abstraction spectrum**. Compliance demands maximal preservation (BSE) to avoid missing hidden replacements or shared obligations. Reporting demands minimal preservation (CME/ASE) for readability. Root-cause analysis needs a **two-layer** approach: a coarse cluster for baseline comparison and a fine-grained signature for deviation detection. Operational segmentation sits in the middle: it needs business-meaningful groups (`IF`, `COLI`, etc.) but must not be so fine that every renamed execution is its own segment. Therefore, **equivalence should be treated as a configurable lens**, not a universal taxonomy.

### Final note
The eight executions illustrate that object-centric process mining derives its value not from counting activities, but from **preserving object relationships and qualifiers** across events. Clustering that discards these—whether through raw-ID equivalence, activity-label flattening, or qualifier stripping—destroys the very semantics that distinguish `X1` from `X7`, or `X5` from `X6`. The canonical BSE signature offers a reproducible middle ground: fine enough for compliance, structured enough for segmentation, and invariant enough to support large-scale comparison.
