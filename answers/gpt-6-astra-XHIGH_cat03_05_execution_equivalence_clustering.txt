## 1. Equivalence design space

Treat each execution as a rooted object–event structure. The distinguished root is its local Order; objects carry types and a local/external flag. Events have activity labels, E2O incidence, and the supplied chronological order. O2O notes provide additional directed, qualified relations. Missing notes mean “not stated,” not “false”; I do not infer O2O relations from co-occurrence alone. Identifier spelling has no significance beyond the supplied EXT convention.

**Activity-sequence equivalence, A.** Let \(w(X)\) be the ordered word of activity labels, retaining repetitions. Define \(X\sim_A Y\iff w(X)=w(Y)\). This preserves activities, their counts, and their order, but discards all objects, incidence, qualifiers, attributes, and elapsed times.

**Typed structural equivalence, T.** Two executions are equivalent when bijections between their objects and between their events preserve the root, object types, external flags, event labels, event order, and every E2O incidence. This preserves object multiplicities and repeated event instances. It discards identifier spelling, absolute times, attributes, and, deliberately, O2O relations. Thus T tests the typed event–object structure; it does not claim to capture all supplied semantics.

**Preferred semantic equivalence, S.** Use the signature
\[
s(X)=((n_I,n_P,n_D,n_V,n_M),L,F,U,R).
\]
The counts are distinct **local** Items, Packages, Deliveries, Invoices, and Payments. L denotes observed external sharing in logistics; F denotes observed external sharing in invoicing/payment. U denotes an explicit item-to-item replacement or a package–item removed_before_dispatch relation. R denotes a return–inspection–repack–redispatch chain for the same item, using a different package after return. Define equivalence by signature equality.

S preserves these multiplicities, sharing categories, and lifecycle motifs. It discards names, external-object counts beyond presence, unrelated ordering, redundant event repetitions, and other incidence/qualifier details. A zero flag means “no matching evidence in this execution.” In particular, payment count does not prove an amount or settlement status. S and T are not generally refinements of each other: S uses selected qualifiers that T excludes, while T preserves incidence that S summarizes.

For compliance, a useful fourth relation, **Q**, extends T by preserving every supplied O2O relation, direction, qualifier, and item-specific context. It still ignores names and numerical timestamp distances. Q preserves the supplied evidence, without treating unstated edges as known absences.

All four relations are reflexive, symmetric, and transitive: A and S are equality of deterministic signatures; T and Q are structure isomorphisms.

For equal timestamps, A uses ordered timestamp blocks containing multisets of labels. T and Q use event partial orders, with equal-time events incomparable unless explicit causal constraints resolve them. S requires its lifecycle witness to follow that partial order. Never break ties using object identifiers. More general concurrency uses the same policy with an explicitly chosen causal partial order; this policy must be fixed across the dataset.

## 2. Canonical signatures

The following Python-like implementation defines S reproducibly. Objects and events are dictionaries keyed by arbitrary identifiers. Each object has type and external fields; each event has activity and objects fields. before is the transitive strict precedence relation. O2O contains normalized directed triples. Item-specific context on other relations is retained in the input but is not consumed by S.

Logistics sharing is evidenced by an external participant in Pack Package/Dispatch, or a package packing an external item. Financial sharing requires an external Order in Issue Invoice/Record Payment, or an invoice billing an external Order.

```python
from itertools import product

def semantic_signature(X):
    O, E, Q = X["objects"], X["events"], X["o2o"]

    def typ(o):
        return O[o]["type"]

    def ext(o):
        return O[o]["external"]

    def local(o):
        return not ext(o)

    def ids(e, t):
        return {o for o in E[e]["objects"] if typ(o) == t}

    counts = tuple(
        sum(local(o) and typ(o) == t for o in O)
        for t in ("Item", "Package", "Delivery", "Invoice", "Payment")
    )

    logistics = {"Pack Package", "Dispatch"}
    finance = {"Issue Invoice", "Record Payment"}

    L = any(
        e["activity"] in logistics and any(ext(o) for o in e["objects"])
        for e in E.values()
    ) or any(
        typ(a) == "Package" and local(a)
        and q in {"packs", "repacks"} and typ(b) == "Item" and ext(b)
        for a, q, b in Q
    )

    F = any(
        e["activity"] in finance
        and any(typ(o) == "Order" and ext(o) for o in e["objects"])
        for e in E.values()
    ) or any(
        typ(a) == "Invoice" and q == "bills"
        and typ(b) == "Order" and ext(b)
        for a, q, b in Q
    )

    U = any(
        (q == "replaces" and typ(a) == typ(b) == "Item"
         and local(a) and local(b))
        or
        (q == "removed_before_dispatch" and typ(a) == "Package"
         and typ(b) == "Item" and local(b))
        for a, q, b in Q
    )

    labels = ("Pack Package", "Dispatch", "Return Item",
              "Inspect Return", "Pack Package", "Dispatch")
    candidates = [
        [eid for eid, e in E.items() if e["activity"] == label]
        for label in labels
    ]

    R = False
    for chain in product(*candidates):
        if not all((a, b) in X["before"]
                   for a, b in zip(chain, chain[1:])):
            continue
        a, b, c, d, e, f = chain
        items = ids(a, "Item") & ids(c, "Item")                 & ids(d, "Item") & ids(e, "Item")
        old_packages = ids(a, "Package") & ids(b, "Package")
        new_packages = ids(e, "Package") & ids(f, "Package")
        returned_delivery = ids(b, "Delivery") & ids(c, "Delivery")
        if (any(local(i) for i in items)
            and returned_delivery
            and any(p != q for p in old_packages for q in new_packages)):
            R = True
            break

    return ("semantic-v1", counts, bool(L), bool(F), bool(U), bool(R))
```

Renaming identifiers consistently cannot change any count, type test, incidence intersection, qualifier test, or precedence witness. Therefore this is a canonical semantic signature, rather than merely a hash heuristic.

For T, an exact, expensive alternative enumerates object numberings consistent with type/root/external colors and event numberings consistent with the event structure, serializes all colors, precedence pairs, and E2O pairs, and takes the lexicographically smallest serialization. Q adds qualified O2O records. No original identifier participates in that serialization.

## 4. Cluster interpretations

**S1 — Baseline: 2/1/1/1/1; 0000.** Two items enter one package and one delivery, followed by an invoice and a payment record. This provides a useful reference for routine throughput. An Order activity trace captures the broad route but obscures packaging both items together; item flattening duplicates shared events. Identifier repair is harmless. Cardinality-changing deduplication requires evidence that objects were duplicates.

**S2 — Consolidated split packing: 2/2/1/1/1; 0000.** Two separately packed items share one delivery. Consolidation offers transport opportunities while creating a coordination point between packages. Package-based flattening represents the common Dispatch repeatedly and can overcount deliveries. The cluster survives identifier and harmless timestamp repairs; merging the two packages changes its defining fact.

**S3 — Split fulfillment and multiple payments: 2/2/2/1/2; 0000.** Separate deliveries accompany two payment objects. The notes identify partial settlement followed by completion. Operational concerns include delivery synchronization and reconciliation of installments. Order activity flattening cannot express which package belongs to which delivery; invoice flattening obscures logistics. Qualifier repair may change the settlement interpretation without changing this signature. Deduplicating payments or deliveries would change membership.

**S4 — Cross-order logistics: 2/1/1/1/1; 1000.** Local items share a package and delivery with another order’s item, while the invoice bills only the lead Order. Consolidation may save handling costs but creates cross-order dependencies in routing, claims, and attribution. Order flattening loses the shared package boundary or duplicates its events across orders. Membership is stable only if external participation survives extraction and repair.

**S5 — Cross-order finance: 2/1/1/1/1; 0100.** Ordinary local logistics feeds an invoice shared with another Order. Settlement of that invoice supplies no order-level allocation. Reconciliation or reporting must avoid assigning the entire payment to both orders. Per-order flattening obscures that allocation ambiguity. Renaming is harmless; deleting external links or inventing an allocation changes the evidence materially.

**S6 — Substitution/removal: 2/1/1/1/1; 0010.** I72 replaces I71, and I71 is removed before dispatch. Initial package membership is therefore not its dispatched contents. Opportunities include substitution analysis and inventory reconciliation; the notes alone establish neither a billing error nor its cause. Unqualified static object graphs and activity traces both represent this poorly. Membership is sensitive to loss or misclassification of replacement/removal qualifiers.

**S7 — Return and repack: 2/2/2/1/1; 0001.** I82 returns through D81, is inspected, then moves through a second package and dispatch. The package replacement is specific to I82, not evidence that I81 also returned. This enables analysis of rehandling and reverse-logistics costs. Package traces fragment the item’s lifecycle; Order traces hide its identity across iterations. Membership survives renaming and noncausal timestamp repair, but not deletion of return/inspection evidence.

## 5. Borderline cases

- **X1 versus X2:** Raw identifier equality separates them, while A, T, Q, and S merge them. Map I11 to I22 and I12 to I21, following their first Add Item occurrences. The apparent reversal is identifier spelling, not different behavior.
- **X1 versus X5:** A merges them. T and S separate them because of external logistics participation. A lead-order projection that deletes external objects also merges them, defensibly for local workload reporting but poorly for coordination analysis.
- **X1 versus X6:** A merges them, as does a local-only projection. S separates them because shared invoicing and missing allocation have business significance even though local object counts match.
- **X1 versus X7:** A merges them. Q and S distinguish substitution/removal; T independently distinguishes Dispatch incidence. A counts-only definition would merge them. Ignoring qualifiers alone therefore does not necessarily make their structures equivalent.
- **X3 versus X4:** T and S distinguish delivery and payment multiplicities. A coarser “multiple-package fulfillment without observed return” equivalence can merge them, ignoring consolidation and installments. That is useful for portfolio segmentation but insufficient for transport or cash-flow analysis.
- **X4 versus X8:** A logistics-count equivalence using only packages and deliveries merges them: both have two of each. S distinguishes an observed return/repack loop from split fulfillment, and also preserves payment multiplicity. Equal resource counts do not establish equal lifecycle behavior.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The API returns a mapping from an implementation-generated key to a collection of extracted OCELs. Library-key equality must be distinguished from A, T, Q, and S.

An exact field inventory requires the installed PM4Py version and its key construction; neither is supplied here. It would be unjustified to claim, from the function name alone, that its key preserves chronological order, externality, or all qualified OCEL 2.0 O2O information. In particular, event/object endpoint tuples preserve E2O incidence; object/type records preserve their encoded types and identifiers; an O2O endpoint pair preserves adjacency and direction but preserves its qualifier only when that qualifier is included. An ordered event sequence preserves order; an unordered collection does not. These distinctions should be verified against the concrete returned key, not assumed from “equivalent.”

If raw object identifiers participate in a key, X1 and X2 can be separated despite isomorphism. If the installed implementation already renames objects, do not attribute this problem to it automatically; also check that tie-breaking is invariant under renaming.

The outline below preserves external flags before any internal renaming and recomputes S for **every** returned member. This can both merge library clusters and split a cluster that ignored semantic evidence. The adapter uses standard OCEL column names and requires retained annotations and an unambiguous local root.

```python
import copy
from collections import defaultdict
import pm4py

FLAG = "benchmark:external"
work = copy.deepcopy(ocel)
work.objects[FLAG] = (
    work.objects["ocel:oid"].astype(str).str.startswith("EXT")
)

def normalize(sub):
    if FLAG not in sub.objects.columns:
        raise ValueError("External annotations were lost during extraction")
    objects = {
        r["ocel:oid"]: {
            "type": r["ocel:type"], "external": bool(r[FLAG])
        }
        for r in sub.objects.to_dict("records")
    }
    roots = [
        o for o, v in objects.items()
        if v["type"] == "Order" and not v["external"]
    ]
    if len(roots) != 1:
        raise ValueError("Supply explicit extraction-root/boundary metadata")

    incidence = defaultdict(set)
    for r in sub.relations.to_dict("records"):
        incidence[r["ocel:eid"]].add(r["ocel:oid"])

    rows = sub.events.to_dict("records")
    events = {
        r["ocel:eid"]: {
            "activity": r["ocel:activity"],
            "objects": incidence[r["ocel:eid"]]
        }
        for r in rows
    }
    before = {
        (a["ocel:eid"], b["ocel:eid"])
        for a in rows for b in rows
        if a["ocel:timestamp"] < b["ocel:timestamp"]
    }
    qualified = set()
    table = getattr(sub, "o2o", None)
    if table is not None:
        for r in table.to_dict("records"):
            qualified.add((
                r["ocel:oid"], r.get("ocel:qualifier", ""),
                r["ocel:oid_2"]
            ))
    return dict(root=roots[0], objects=objects, events=events,
                before=before, o2o=qualified)

raw = pm4py.cluster_equivalent_ocel(
    work, object_type="Order", max_objs=100
)
semantic_clusters = defaultdict(list)
for library_key, members in raw.items():
    print("Library key:", repr(library_key))  # Keep for version-specific audit.
    for sub in members:
        sig = semantic_signature(normalize(sub))
        semantic_clusters[sig].append(sub)
```

This assumes the input encodes the supplied qualifiers. The benchmark’s EXT convention is execution-relative; a general production OCEL needs boundary annotations relative to each root, not a global identifier-prefix rule.

Use exact equivalence for reproducibility, detailed regression checks, and audits where small distinctions matter; use semantic aggregation for operational categories. max_objs is an extraction/size control, not a semantic threshold. Depending on implementation, oversized executions can be excluded or bounded. Check coverage, oversize cases, root identity, and retained O2O data explicitly. Cross-order links can generate large, overlapping executions; summing cluster members then need not count independent orders or unique events. General graph canonicalization also becomes expensive as structures grow.

## 7. Robustness analysis

**Ignore all O2O qualifiers.** Keep endpoints but erase relation labels. S6 merges into S1 because U has no remaining witness. T still distinguishes X7’s Dispatch incidence. S7 retains its event-based return/repack witness. S3 remains separate by counts, but partial-versus-complete settlement is no longer established. A is unchanged.

**Ignore external objects.** Delete flagged objects and their incidence and O2O links, retaining the remaining events. X5 and X6 merge into S1 and T1. A is unchanged. This is a deliberate loss of business boundaries, not harmless identifier normalization.

**Collapse repeated same-label events.** Define this precisely as replacing each maximal consecutive run by one event with the union of its incidences. All S assignments remain: objects and the relevant motifs survive. Under A, X3 joins A1 after its adjacent Pack events collapse; X4 and X8 remain distinct. Object counts still distinguish T’s split-package cases. Keeping only the first event’s objects would instead discard evidence. Global label-set projection is even coarser: it merges X1–X7.

**Use a causal partial order for packing/dispatch.** Retain precedence along non-Order object lifecycles and explicit prerequisites, while permitting independent package work to commute. Sharing the root Order alone must not force serialization. No T or S clusters here merge: counts, incidence, and exception evidence still distinguish them. Future executions differing only in independent scheduling can merge. X8’s return chain remains ordered through its package, delivery, and item links.

**Represent payment multiplicity as an amount attribute.** Removing n_M from S still leaves X4 distinct through delivery count or the return flag when compared with X3 and X8. Amount equivalence cannot actually be evaluated here: no amounts are supplied.

## 8. Limitations and recommendation

For **compliance monitoring**, use Q with explicit temporal and financial checks; structural equivalence itself is not proof of compliance. For **operational segmentation**, use S, optionally combining S2/S3 when only multi-package workload matters. For **root-cause analysis**, retain the full qualified structure, event identities, and available timestamps, then compare narrow variants; a cluster suggests hypotheses, not causation. For **descriptive reporting**, use A for route frequencies alongside S for object counts and sharing categories.

The examples provide neither durations nor quantities, payment amounts, or complete object histories. Several zero flags reflect absent evidence. No single partition is best: reporting benefits from compression, segmentation needs business distinctions, and investigation and compliance require traceable detail.
