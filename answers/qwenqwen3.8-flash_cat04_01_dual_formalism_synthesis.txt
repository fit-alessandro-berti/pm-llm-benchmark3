# 1. Assumptions and Interpretation

1. **Completion-event semantics.**  
   The narrative says activities are recorded at completion. Therefore every precedence edge is interpreted as a **completion-to-completion** constraint: if `A -> B`, then the completion event of `A` must occur before the completion event of `B`. Start-time constraints such as “may start only after” are approximated by completion-order constraints because start events are not represented.

2. **Low-risk / high-risk choice.**  
   Risk data is not encoded as a guard. The choice is represented purely as a control-flow alternative:
   - low risk: `Supervisor Review`;
   - high risk: both `Quality Review` and `Regulatory Review`, with no order between them.  
   In the POWL model this choice is placed directly after `Analyze Root Cause`. In the process tree it is placed later because of block-structured limitations.

3. **Optional supplier consultation.**  
   `Consult Supplier` is represented as an XOR branch:
   - selected: visible `Consult Supplier`;
   - not selected: silent transition.  
   This enforces “at most once” without encoding case data. The POWL model places the optional branch after `Analyze Root Cause`; the process tree places it later as an approximation.

4. **Passing inspection abstraction.**  
   Inspection outcome is not an event label. It is represented by silent transitions and structural position:
   - a failing cycle is `Execute Trial -> Inspect Trial -> silent_fail -> Adjust Parameters`;
   - a passing cycle is `Execute Trial -> Inspect Trial -> silent_pass`.  
   Thus, an `Inspect Trial` followed by `Adjust Parameters` is treated as failing; the final `Inspect Trial` before `Release Material` is treated as passing.

5. **Duplicate visible labels.**  
   Duplicate visible labels are permitted for repeated trial activities. The models intentionally contain two distinct nodes labeled `Execute Trial` and two distinct nodes labeled `Inspect Trial`: one pair for the failing loop body and one pair for the passing exit. No non-repeating activity is duplicated.

6. **Process-tree approximation policy.**  
   The process tree uses a **conservative under-approximation**: it excludes some intended behavior rather than admitting unsafe behavior. Specifically, it delays the approval route and optional supplier consultation until after both `Plan Verification` and `Design Corrective Action` have completed. This preserves the safety requirements that trial starts only after planning/design and release waits for approvals/supplier/passing inspection, but it loses intended early overlap of approvals/supplier with planning/design.

7. **PM4Py LOOP semantics assumption.**  
   Both models assume the common PM4Py unfolding:
   ```text
   LOOP(body, exit) = body* exit
   ```
   For the trial loop:
   - `body` = failing cycle `Execute -> Inspect -> silent_fail -> Adjust`;
   - `exit` = passing cycle `Execute -> Inspect -> silent_pass`.  
   If a particular PM4Py version uses `body+ exit`, the trial loop should be rewritten as:
   ```text
   XOR(pass_cycle, ->(fail_cycle, LOOP(fail_cycle, pass_cycle)))
   ```
   The intended semantics is unchanged.

8. **“May overlap” interpretation.**  
   “May overlap” is interpreted as **absence of a mandatory completion precedence**, not as a requirement that actual temporal overlap must occur. In partial-order/Petri-net semantics this admits interleaving and, where enabled, true concurrency. In completion-only event logs, it is represented by no edge between the activities.

9. **Data conditions are not modeled.**  
   Conditions such as “low risk”, “high risk”, “supplier involved”, and “inspection failed/passed” are not represented as data guards. They are represented by control-flow alternatives, silent transitions, and loop structure.

10. **Start and end behavior.**  
   Every trace must start with `Register Deviation` and end with `Archive Case`. Both models enforce this by placing `Register Deviation` as the first obligation and `Archive Case` after `Release Material`.

11. **High-risk approvals.**  
   `Quality Review` and `Regulatory Review` are modeled as concurrent alternatives with no completion order. Therefore either completion order is allowed.

12. **Supplier completion before release.**  
   If `Consult Supplier` is visible, it must complete before `Release Material`. If it is not selected, the silent alternative completes before `Release Material`.

# 3. PM4Py Process-Tree Model

Compact process-tree expression, using `silent` as a placeholder for an empty transition:

```text
->(
  Register Deviation,
  ||(
    ->(Contain Material, Plan Verification),
    ->(Analyze Root Cause, Design Corrective Action)
  ),
  ||(
    loop(
      ->(Execute Trial, Inspect Trial, silent_fail, Adjust Parameters),
      ->(Execute Trial, Inspect Trial, silent_pass)
    ),
    xor(Supervisor Review, ||(Quality Review, Regulatory Review)),
    xor(Consult Supplier, silent_no_supplier)
  ),
  Release Material,
  Archive Case
)
```

Self-contained PM4Py construction:

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def _children(parent, children):
    parent.children = children
    for child in children:
        child.parent = parent
    return parent


# Visible leaves
register = ProcessTree(label="Register Deviation")
contain = ProcessTree(label="Contain Material")
analyze = ProcessTree(label="Analyze Root Cause")
plan = ProcessTree(label="Plan Verification")
design = ProcessTree(label("Design Corrective Action"))
supervisor = ProcessTree(label="Supervisor Review")
quality = ProcessTree(label="Quality Review")
regulatory = ProcessTree(label="Regulatory Review")
consult = ProcessTree(label="Consult Supplier")
adjust = ProcessTree(label="Adjust Parameters")
release = ProcessTree(label="Release Material")
archive = ProcessTree(label="Archive Case")

# Trial leaves, duplicated for failing and passing cycles
execute_fail = ProcessTree(label="Execute Trial")
inspect_fail = ProcessTree(label="Inspect Trial")
silent_fail = ProcessTree(label=None)

execute_pass = ProcessTree(label="Execute Trial")
inspect_pass = ProcessTree(label="Inspect Trial")
silent_pass = ProcessTree(label=None)

# Optional supplier silent alternative
silent_no_supplier = ProcessTree(label=None)

# Initial independent work streams:
# Contain -> Plan and Analyze -> Design may overlap.
contain_plan = _children(
    ProcessTree(operator=Operator.SEQUENCE),
    [contain, plan]
)

analyze_design = _children(
    ProcessTree(operator=Operator.SEQUENCE),
    [analyze, design]
)

initial_streams = _children(
    ProcessTree(operator=Operator.PARALLEL),
    [contain_plan, analyze_design]
)

# Trial loop:
# zero or more failing cycles, then one passing cycle.
fail_cycle = _children(
    ProcessTree(operator=Operator.SEQUENCE),
    [execute_fail, inspect_fail, silent_fail, adjust]
)

pass_cycle = _children(
    ProcessTree(operator=Operator.SEQUENCE),
    [execute_pass, inspect_pass, silent_pass]
)

trial_loop = _children(
    ProcessTree(operator=Operator.LOOP),
    [fail_cycle, pass_cycle]
)

# Risk route:
# low risk: Supervisor Review
# high risk: Quality Review and Regulatory Review concurrently, either order
high_risk = _children(
    ProcessTree(operator=Operator.PARALLEL),
    [quality, regulatory]
)

risk_route = _children(
    ProcessTree(operator=Operator.XOR),
    [supervisor, high_risk]
)

# Optional supplier:
# either visible Consult Supplier or silent no-consultation
supplier_optional = _children(
    ProcessTree(operator=Operator.XOR),
    [consult, silent_no_supplier]
)

# Post-synchronization obligations:
# trial, approvals, and optional supplier may overlap each other,
# but all must complete before release.
post_trial = _children(
    ProcessTree(operator=Operator.PARALLEL),
    [trial_loop, risk_route, supplier_optional]
)

# Full case flow
tree = _children(
    ProcessTree(operator=Operator.SEQUENCE),
    [register, initial_streams, post_trial, release, archive]
)
```

**Requirements not represented exactly by the process tree.**  
The process tree captures the start/end rules, the overlap of `Contain Material` and `Analyze Root Cause`, the split dependencies `Contain -> Plan` and `Analyze -> Design`, the synchronization of trial on `Plan` and `Design`, the risk-choice XOR, the optional supplier XOR, and the repeat-until trial loop through silent pass/fail transitions. However, it cannot represent the intended non-block-structured relation that the approval route and optional supplier consultation depend only on `Analyze Root Cause` while `Execute Trial` depends on `Plan Verification` and `Design Corrective Action`. In the tree, `risk_route` and `supplier_optional` are placed in `post_trial`, which is executed only after both `contain_plan` and `analyze_design` have completed. Therefore the tree excludes intended traces where `Supervisor Review`, `Quality Review`, `Regulatory Review`, or `Consult Supplier` starts before `Plan Verification` or `Design Corrective Action` completes. It also excludes intended overlap of supplier consultation with corrective-action design and verification planning. This is a conservative under-approximation: it removes flexibility but does not admit unsafe behavior such as trial before planning/design or release before required approvals/supplier/passing inspection.

# 4. PM4Py POWL Model

Compact POWL description:

```text
Root = StrictPartialOrder(
  nodes = {
    Register, Contain, Analyze, Plan, Design,
    RiskXOR, SupplierXOR, TrialLoop, Release, Archive
  }
)

Root edges:
  Register -> Contain
  Register -> Analyze
  Contain  -> Plan
  Analyze  -> Design
  Analyze  -> RiskXOR
  Analyze  -> SupplierXOR
  Plan     -> TrialLoop
  Design   -> TrialLoop
  TrialLoop -> Release
  RiskXOR   -> Release
  SupplierXOR -> Release
  Release   -> Archive

RiskXOR = XOR(
  SupervisorReview,
  HighRiskRoute
)

HighRiskRoute = StrictPartialOrder({QualityReview, RegulatoryReview})
  # no edges: concurrent, either completion order

SupplierXOR = XOR(
  ConsultSupplier,
  silent_no_supplier
)

TrialLoop = LOOP(
  body = ExecuteTrial -> InspectTrial -> silent_fail -> AdjustParameters,
  exit = ExecuteTrial -> InspectTrial -> silent_pass
)
```

Self-contained PM4Py POWL construction:

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator


def _silent():
    # Compatibility for versions where SilentTransition takes no label.
    try:
        return SilentTransition("")
    except TypeError:
        return SilentTransition()


# Visible root-level activities
register = Transition("Register Deviation")
contain = Transition("Contain Material")
analyze = Transition("Analyze Root Cause")
plan = Transition("Plan Verification")
design = Transition("Design Corrective Action")
supervisor = Transition("Supervisor Review")
quality = Transition("Quality Review")
regulatory = Transition("Regulatory Review")
consult = Transition("Consult Supplier")
release = Transition("Release Material")
archive = Transition("Archive Case")

# Trial nodes, duplicated for failing and passing cycles
execute_fail = Transition("Execute Trial")
inspect_fail = Transition("Inspect Trial")
silent_fail = _silent()
adjust = Transition("Adjust Parameters")

execute_pass = Transition("Execute Trial")
inspect_pass = Transition("Inspect Trial")
silent_pass = _silent()

# Optional supplier silent alternative
silent_no_supplier = _silent()

# High-risk approvals: Quality and Regulatory may occur concurrently,
# in either completion order.
high_route = StrictPartialOrder([quality, regulatory])

# Risk route: low-risk supervisor review OR high-risk quality+regulatory.
risk_xor = OperatorPOWL(Operator.XOR, [supervisor, high_route])

# Optional supplier: visible consultation OR silent no-consultation.
supplier_xor = OperatorPOWL(Operator.XOR, [consult, silent_no_supplier])

# Failing trial cycle:
# Execute -> Inspect -> silent_fail -> Adjust
fail_cycle = StrictPartialOrder([execute_fail, inspect_fail, silent_fail, adjust])
fail_cycle.order.add_edge(execute_fail, inspect_fail)
fail_cycle.order.add_edge(inspect_fail, silent_fail)
fail_cycle.order.add_edge(silent_fail, adjust)

# Passing trial cycle:
# Execute -> Inspect -> silent_pass
pass_cycle = StrictPartialOrder([execute_pass, inspect_pass, silent_pass])
pass_cycle.order.add_edge(execute_pass, inspect_pass)
pass_cycle.order.add_edge(inspect_pass, silent_pass)

# Repeat-until trial loop:
# zero or more failing cycles, then one passing cycle.
# Assumes PM4Py LOOP(body, exit) = body* exit.
trial_loop = OperatorPOWL(Operator.LOOP, [fail_cycle, pass_cycle])

# Root partial order.
powl = StrictPartialOrder([
    register,
    contain,
    analyze,
    plan,
    design,
    risk_xor,
    supplier_xor,
    trial_loop,
    release,
    archive,
])

# Required precedence edges.
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, risk_xor)
powl.order.add_edge(analyze, supplier_xor)
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)
powl.order.add_edge(trial_loop, release)
powl.order.add_edge(risk_xor, release)
powl.order.add_edge(supplier_xor, release)
powl.order.add_edge(release, archive)
```

**Why intentionally unconnected POWL nodes may remain concurrent.**  
The root partial order deliberately omits edges between:

- `Contain Material` and `Analyze Root Cause`: the narrative says they may proceed independently and overlap.
- `Plan Verification` and `Design Corrective Action`: each has a different prerequisite, and they may overlap.
- `risk_xor` and `trial_loop`: the approval route does not have to complete before trial starts and may overlap the trial cycle.
- `supplier_xor` and `trial_loop`: supplier consultation may overlap trial work.
- `supplier_xor` and `risk_xor`: supplier consultation may overlap approvals.
- `supplier_xor` and `plan` / `design`: supplier consultation may overlap verification planning and corrective-action design.
- `quality` and `regulatory` inside `high_route`: high-risk approvals may occur concurrently and in either completion order.

All other pairs are ordered directly or transitively: `Register Deviation` precedes all work; `Release Material` follows trial pass, selected approvals, and supplier completion if selected; `Archive Case` follows release.

# 7. Preferred Representation and Validation Plan

**Preferred representation: POWL.**  
The POWL model is preferred because the intended behavior is fundamentally non-block-structured: several obligations share the same predecessor `Analyze Root Cause`, while `Execute Trial` synchronizes on `Plan Verification` and `Design Corrective Action`, and approvals/supplier must not block trial. POWL expresses these cross-branch dependencies directly with partial-order edges. The process tree is useful as a fallback for tools that require block-structured trees, but it requires conservative approximation and loses early approval/supplier overlap.

Concrete validation plan:

1. **Convert both models to accepting Petri nets where supported.**
   ```python
   import pm4py

   net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)
   net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)
   ```

2. **Check soundness of converted nets.**
   ```python
   pm4py.check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)
   pm4py.check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)
   ```
   Expected result: both nets are sound, with no deadlocks, livelocks, or unreachable final markings, assuming the conversion supports the loop and silent transitions.

3. **Bounded or sampled playout.**
   Use bounded playout to inspect representative traces:
   ```python
   pm4py.play_out(net_powl, im_powl, fm_powl, max_steps=50)
   pm4py.play_out(net_tree, im_tree, fm_tree, max_steps=50)
   ```
   Inspect that:
   - every trace starts with `Register Deviation` and ends with `Archive Case`;
   - `Execute Trial` never occurs before both `Plan Verification` and `Design Corrective Action`;
   - `Release Material` never occurs before a final passing trial cycle, selected approvals, and supplier completion if visible;
   - `Adjust Parameters` is never followed directly by `Release Material`.

4. **Explicit positive and negative trace tests.**
   Replay the witness traces:
   - T1–T4 should be allowed by both models.
   - T5 should be allowed by POWL but forbidden by the process tree, exposing the approximation.
   - F1–F3 should be forbidden by both models.
   Use token-based replay or alignment:
   ```python
   # Conceptual; exact API may depend on PM4Py version.
   pm4py.conformance_diagnostics_token_based(net_powl, im_powl, fm_powl, traces)
   ```
   The expected diagnostics should show that F1 violates release-before-approval, F2 violates release-before-supplier, and F3 violates the repeat-until trial loop.

5. **Silent behavior and duplicated-label check.**
   Generate visible projections of playout traces by removing silent transitions. Then check:
   - no visible labels are introduced for `silent_fail`, `silent_pass`, or `silent_no_supplier`;
   - all non-repeating labels occur at most once in a trace;
   - only `Execute Trial` and `Inspect Trial` may occur multiple times;
   - `Adjust Parameters`, when present, occurs only after an `Inspect Trial` and before another `Execute Trial`.

6. **Limitations of the validation plan.**
   - Petri-net conversion may not preserve all POWL loop semantics exactly in every PM4Py version.
   - Finite playout cannot prove unbounded repeat-until behavior exhaustively.
   - Silent pass/fail transitions are not observable in completion-only logs; their correctness is structural, not data-based.
   - Duplicate visible labels can make conformance checking ambiguous if event IDs or timestamps are unavailable.
   - The process tree is intentionally approximate; validation will confirm the approximation, not exact equivalence to the narrative.

# 8. Final Self-Critique

1. **Process-tree fidelity is intentionally incomplete.**  
   The conservative tree excludes intended early overlap of approvals and supplier consultation with planning/design. This is defensible for safety, but it means the tree is not a faithful representation of the full intended behavior.

2. **The inspection-outcome abstraction is semantic rather than observable.**  
   Passing and failing inspections are represented by silent transitions and structural position. In a completion-only event log, a human analyst cannot directly see which `Inspect Trial` was passing; the model infers it from whether `Adjust Parameters` follows. This may be fragile if logs contain timestamps, overlapping activities, or incomplete records.

3. **The answer depends on a specific PM4Py loop convention.**  
   The models assume `LOOP(body, exit) = body* exit`. If a PM4Py version uses a different loop unfolding, the trial-loop code must be adjusted. The intended semantics can be preserved, but the exact executable model is version-sensitive.
