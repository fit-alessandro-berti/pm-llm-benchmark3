## 1. Equivalence design space

**1. Activity-sequence equivalence (`_seq`)**
- **Definition:** Two executions are equivalent iff their sequences of activity labels are identical after stripping all object identifiers, timestamps, and qualifiers. Formally, ` = a, a, …, a _seq  = b, b, …, b` iff `k, a = b`.
- **Invariants preserved:** Total temporal ordering of activities, repetition counts of each label.
- **Information discarded:** All E2O incidence, object types, multiplicities, external flags, O2O qualifiers, and any structural topology.
- **Algebraic properties:** Reflexive, symmetric, transitive. Forms a strict partition based on label strings.
- **Concurrency handling:** Assumes a total order. If concurrent events exist, they are ordered by arrival timestamp or left as an unordered multiset; equivalence requires matching multisets.

**2. Typed structural equivalence under identifier renaming (`_str`)**
- **Definition:** Two executions are equivalent iff their event-to-object incidence structures are isomorphic under a bijection that preserves event labels, object types, external-object flags (`EXT`), and the global event order. Formally, a pair of mappings `(_E, _O)` exists such that `_E(event_e) = e'`, `_O(obj_o) = o'`, preserving `label(e)=label(e')`, `type(o)=type(o')`, `is_ext(o)is_ext(o')`, and incidence relations.
- **Invariants preserved:** Labeled hypergraph topology of E2O relations, object type multiplicities per event, external-context flags, temporal sequence.
- **Information discarded:** Exact local identifiers, numerical values (e.g., payment amounts), semantic qualifiers unless encoded as incidence edges.
- **Algebraic properties:** Reflexive, symmetric, transitive. Equivalent to labeled graph isomorphism with a fixed vertex ordering constraint.
- **Concurrency handling:** Preserves the provided total order. If partial order is intended, the equivalence relation relaxes to topological isomorphism.

**3. Business-semantic equivalence (`_bus`)**
- **Definition:** Executions are equivalent iff they satisfy the same set of high-level operational invariants extracted from O2O topology, sharing patterns, and lifecycle motifs. We define four binary invariants:
  1. `Isolation`: No `EXT` objects in any event.
  2. `LogisticsGranularity`: Ratio of unique Packages to unique Deliveries (1:1, >1:1, or 1:>1).
  3. `SettlementPattern`: Number of Payment events per Invoice (1, >1, or 0).
  4. `LifecycleModifier`: Presence of qualifiers indicating substitution/removal (`removed_before_dispatch`) or explicit return/inspect/repack cycles.
  Two executions are `_bus` iff their invariant tuples match.
- **Invariants preserved:** Business intent, fulfillment strategy, financial consolidation level, exception handling motif.
- **Information discarded:** Exact event ordering within logical phases, precise object counts beyond ratio categories, non-semantic identifier differences.
- **Algebraic properties:** Reflexive, symmetric, transitive by construction (equivalence classes over a finite invariant space).
- **Concurrency handling:** Invariants are aggregation-based; concurrency does not affect tuple equality unless it alters phase boundaries (handled via causal precedence rules).

## 2. Canonical signatures

```python
from collections import defaultdict, Counter
import hashlib

def canonical_signature(events, lead_type="Order"):
    # 1. Normalize object IDs: strip suffixes, mark EXT
    obj_map = {}
    def norm_id(raw, idx):
        if raw.startswith("EXT"):
            return f"EXT:{raw.split(':')[0]}"
        return f"{lead_type}:{idx}"
    
    # 2. Extract topology & counters
    ext_in_logistics = False
    ext_in_finance = False
    pack_events = []
    dispatch_events = []
    invoice_count = 0
    payment_count = 0
    has_return_cycle = False
    has_replacement_qualifier = False
    
    for evt in events:
        act = evt["activity"]
        objs = evt.get("objects", [])
        
        if act == "Pack":
            pack_events.append(objs)
            if any(o.startswith("EXT") for o in objs): ext_in_logistics = True
        elif act == "Dispatch":
            dispatch_events.append(objs)
            if any(o.startswith("EXT") for o in objs): ext_in_logistics = True
        elif act == "Issue Invoice":
            invoice_count += 1
            if any(o.startswith("EXT") for o in evt.get("objects", [])): ext_in_finance = True
        elif act == "Record Payment":
            payment_count += 1
            if any(o.startswith("EXT") for o in evt.get("objects", [])): ext_in_finance = True
        elif act == "Return Item":
            has_return_cycle = True
        elif "removed_before_dispatch" in evt.get("qualifiers", []):
            has_replacement_qualifier = True
            
    # 3. Compute invariants
    is_isolated = not (ext_in_logistics or ext_in_finance)
    
    pkg_set = set()
    del_set = set()
    for p in pack_events:
        for o in p:
            if o.startswith("Package:"): pkg_set.add(o)
    for d in dispatch_events:
        for o in d:
            if o.startswith("Delivery:"): del_set.add(o)
            
    n_pkgs = len(pkg_set)
    n_del = len(del_set)
    if n_pkgs == 0: log_gran = "N/A"
    elif n_pkgs == 1 and n_del == 1: log_gran = "1P-1D"
    elif n_pkgs > 1 and n_del == 1: log_gran = ">1P-1D"
    elif n_pkgs > 1 and n_del > 1: log_gran = ">1P->1D"
    else: log_gran = "1P->1D"
    
    settlement = "Single" if payment_count <= 1 else "Multi"
    
    modifier = "None"
    if has_replacement_qualifier: modifier = "Replacement"
    elif has_return_cycle: modifier = "ReturnRework"
    
    # 4. Build frozen signature
    sig = {
        "act_pattern": tuple(e["activity"] for e in events),
        "isolated": is_isolated,
        "logistics": log_gran,
        "settlement": settlement,
        "modifier": modifier
    }
    return frozenset(sig.items())
```

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py’s `cluster_equivalent_ocel` clusters object-centric event logs by comparing object-centric traces. The key structure typically preserves:
- Exact event indices and timestamps
- Precise object identifiers (including `EXT` prefixes)
- Full E2O incidence per object
- Strict temporal ordering within each object’s trace

**Why raw identifiers make exact clusters too fine:** Local renaming (X1 vs X2) or incremental ID generation fragments clusters unnecessarily. Exact equivalence becomes overly granular for business analysis, treating cosmetic differences as structural divergence.

**Canonicalization/post-processing:** After obtaining PM4Py clusters, one should:
1. Map all local IDs to type-indexed placeholders (`Item:1`, `Item:2`).
2. Normalize `EXT:` prefixes to boolean sharing flags.
3. Replace exact timestamps with causal order or phase buckets.
4. Aggregate repeated activities into multiplicity counts where order within a phase is irrelevant.
5. Re-cluster using the canonical signatures from Section 2.

**When exact equivalence is preferable:** Audit logging, regulatory compliance, digital twin synchronization, and debugging production incidents require exact trace matching to pinpoint failures.

**Impact of `max_objs`:** PM4Py limits connected component size to control memory usage. Large executions with many shared objects may be truncated or split, producing artificial boundaries. Setting `max_objs` too low hides cross-order dependencies (like X5/X6); too high risks combinatorial blowup.

**Python outline:**
```python

        sigs = []
        for ex in exec_list:
            sig = canonical_signature(ex.events, lead_type)
            sigs.append(sig)
        # Representative signature for the cluster
        representative = min(sigs)  # deterministic tie-break
        canonical_groups[representative] = canonical_groups.get(representative, [])
        canonical_groups[representative].extend(exec_list)
        
    # 3. Merge equivalent canonical signatures
    merged_clusters = list(canonical_groups.values())
    return merged_clusters
```

## 8. Limitations and recommendation

**Recommended equivalence levels by use case:**
- **Compliance monitoring:** `_str` (Typed structural). Audits require exact incidence matching, including `EXT` flags and qualifiers, to verify regulatory boundaries (tax, data residency, chain of custody).
- **Operational segmentation:** `_bus` (Business-semantic). Groups executions by fulfillment strategy (baseline, split logistics, shared context, rework), enabling targeted KPI dashboards and resource allocation.
- **Root-cause analysis:** `_str` + qualifier-aware extension. Pinpoints exact failure nodes (e.g., which package failed, whether payment was shared, whether a replacement occurred) without collapsing exception workflows into baselines.
- **Descriptive reporting:** Coarse `_seq` or aggregated `_bus` metrics. High-level trend analysis benefits from smoothing identifier noise and focusing on phase completion rates.

**Why no single notion is best:** Compliance demands precision and traceability, favoring fine-grained structural equivalence. Operations need actionable grouping, favoring semantic motifs. Root-cause analysis requires surgical granularity to isolate fault propagation. Reporting prioritizes signal-over-noise, favoring abstraction. Each purpose optimizes a different trade-off between fidelity, interpretability, and computational tractability. Forcing one equivalence onto all use cases either obscures critical exceptions (too coarse) or overwhelms analysts with noise (too fine). A layered approach—canonicalizing once, then projecting to purpose-specific equivalence relations—delivers both accuracy and usability.
