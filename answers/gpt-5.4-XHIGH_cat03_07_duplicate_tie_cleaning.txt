## 1. Duplicate-handling decision tree
1. First test for exact technical duplication inside one source: same `source`, same `source_event_key` or another immutable business key, same original activity, same original timestamp, and same object links. Terminal decision: drop the duplicate row or duplicate E2O relation, keep one canonical event, and record the dropped identifier in provenance.
2. If not exact, test whether independent evidence proves two records are the same physical event observed by multiple systems. Accept only hard evidence such as reconciliation reports, shared immutable business keys, or explicit source lineage. Terminal decision: merge attributes and relations into one canonical event, preserve both original IDs, both labels, both payload hashes, and conflict metadata.
3. If not the same physical event, test whether one event is a summary, status echo, or abstraction-level derivative of another detailed event. Terminal decision in the conservative pipeline: retain both with refined labels or qualifiers such as `[detail]`, `[ERP summary]`, or `[billing echo]`. Terminal decision in an aggressive semantic-transition view: merge only if governance explicitly models one business transition rather than two observations.
4. If the same harmonized label hides different source semantics, treat it as a harmonization collision. Terminal decision: retain both with refined labels or qualifiers; do not merge. This applies to `Dispatch Package` for warehouse release versus carrier acceptance.
5. If the events have the same label and timestamp but differ on discriminating objects, such as different `Item` or different `Payment`, treat them as concurrent same-label events. Terminal decision: retain both unchanged, or retain both with analysis-only qualifiers if needed for flattening. Do not drop or merge.
6. If the evidence is mixed and none of the above is conclusive, classify as unresolved candidate. Terminal decision: quarantine for review, meaning keep both raw events in the production OCEL but attach a review flag and candidate-duplicate case ID so analysts can decide later.

## 3. Timestamp-tie ordering rules
The ordering policy should be partial-order first, total-order second.

Semantic rules:
- Domain constraints: `Authorize Payment` must precede `Capture Payment` for `M1`; carrier acceptance precedes handover; picks needed for `P1` must precede packing `P1`.
- Lifecycle constraints on shared objects: when two events act on the same `Package` or same `Payment`, use the object lifecycle if it is explicit. Example: `e06` before `e07` if the ERP event is known to be a summary emitted from WMS.
- Source-specific semantics: refine harmonized labels before ordering. `e08` is warehouse release, `e09` is carrier acceptance; otherwise a total order over two identically named events tells the wrong story.
- Within-source sequence: use `source_seq` only after semantic rules and only inside one source system.

Merely deterministic rules:
- `ingested_at` is a late fallback for unresolved ties, never primary business order.
- Stable fallback order is lexical canonical `eid` after all semantic and source-local signals are exhausted.

Adding microseconds before deciding semantic order is dangerous because the synthetic order can be mistaken for fact. If I first assign `e08 < e09 < e10` by row index and then run performance or conformance analysis, the OCEL now encodes a fake sub-second narrative rather than an uncertainty-aware same-second tie. Synthetic deltas are acceptable only after the admissible order is chosen and only as a technical aid.

Intended orders:
- `e03-e07` at 10:00 after merging `e03/e04`: admissible total orders are `e03, e05, e06, e07` or `e05, e03, e06, e07`. The semantic part is only `{e03,e05} < e06 < e07`.
- `e08-e10` at 10:15 after relabeling: `e08 (warehouse release) < e09 (carrier acceptance) < e10 (handover)`.
- `e11-e16` at 12:00 after merging `e11/e16`: the safe semantic order is `e12 < e13`, `e15` after the payment messages, and `e14` distinct from `e13`. `Issue Invoice` can be before the payment events if finance governance says so; otherwise `Issue Invoice`, `Authorize Payment`, and `Capture Payment M2` remain partly unordered, with only deterministic tie-breakers between them.

## 4. Conservative cleaning pipeline
The minimum-change scenario should merge only strongly verified same-event pairs: `e03/e04` from the reconciliation report and `e11/e16` from shared invoice `V1`. It should retain `e06/e07` as different abstraction levels, retain `e08/e09` after label refinement, retain `e13`, `e14`, and `e15` as distinct, and never deduplicate on timestamp plus activity alone.

Process:
- Deep-copy the raw OCEL.
- Preserve `original_timestamp`, `original_activity`, `source`, `source_event_key`, original `eid`, and original payload hashes.
- Refine labels where semantics differ: `e07 -> Pack Package [ERP summary]`, `e08 -> Dispatch Package [Warehouse release]`, `e09 -> Dispatch Package [Carrier acceptance]`, `e15 -> Capture Payment [ERP summary]`.
- Apply verified-pair merges only for `e03/e04` and `e11/e16`.
- Use `pm4py.ocel_drop_duplicates` only afterward, to remove duplicate E2O rows introduced by the verified merges, not as a semantic event-merging method.
- Compute an ordering key from semantic rank, refined label, within-source `source_seq`, late-fallback `ingested_at`, and stable `eid`.
- Sort by that key, then add index-based timedelta only for deterministic processing tools.

Expected retained event count: 15 events, down from 17. Expected E2O relation count falls from 44 to about 39 because the merged pairs have overlapping object links.

## 5. Aggressive alternatives
Evidence-based semantic merging:
- Start from the conservative dataset.
- Additionally merge `e06/e07` into one canonical pack transition if the modeling goal is one business transition per package state change rather than one observation per source.
- Keep `e08/e09` separate because they are semantically distinct milestones, and keep `e13`, `e14`, `e15` separate because payment-object granularity matters.
- Expected retained event count: 14. Most likely damage: removal of a useful abstraction-level checkpoint that may matter for ERP conformance and message-latency analysis.

Mechanically aggressive PM4Py merging:
- Run `pm4py.ocel_merge_duplicates(..., have_common_object=True)` on a copy for sensitivity analysis only, with explicit warning.
- If applied naively to the raw log, it will likely collapse `e03/e04/e05`, `e06/e07`, `e08/e09`, `e11/e16`, and `e13/e14/e15`, producing roughly 10 events and about 28 E2O relations.
- Most likely semantic damage: it erases distinct item picks, distinct partial payments, and milestone separation, and can create unioned super-events linked to incompatible object combinations.

`have_common_object=True` is not sufficient to protect `e13` and `e14` because they share `O1` and `V1` while differing on the discriminating `Payment` objects `M1` and `M2`. The same issue appears for `e03` and `e05`, which share `O1` and `P1` but involve different `Item` objects.

## 6. PM4Py-oriented Python implementation
```python
import copy
import json
import pandas as pd
import pm4py

EID = ocel_raw.event_id_column
ACT = ocel_raw.event_activity
TS = ocel_raw.event_timestamp
OID = ocel_raw.object_id_column
OTYPE = ocel_raw.object_type_column


def preserve_originals(ocel):
    if "original_timestamp" not in ocel.events.columns:
        ocel.events["original_timestamp"] = ocel.events[TS]
    if "original_activity" not in ocel.events.columns:
        ocel.events["original_activity"] = ocel.events[ACT]
    if "canonical_eid" not in ocel.events.columns:
        ocel.events["canonical_eid"] = ocel.events[EID]
    for col in ["source", "source_event_key"]:
        if col not in ocel.events.columns:
            raise KeyError(f"missing required metadata column: {col}")
    if "source_eids" not in ocel.events.columns:
        ocel.events["source_eids"] = ocel.events[EID].map(lambda x: json.dumps([x]))
    if "merge_rule" not in ocel.events.columns:
        ocel.events["merge_rule"] = None
    if "discarded_conflicts" not in ocel.events.columns:
        ocel.events["discarded_conflicts"] = None
    if "reviewer_rule_version" not in ocel.events.columns:
        ocel.events["reviewer_rule_version"] = "duplicate_tie_cleaning_v1"
    return ocel


def sync_event_columns_to_relations(ocel):
    sync_cols = [ACT, TS]
    for optional in ["source", "source_event_key", "original_activity", "original_timestamp"]:
        if optional in ocel.events.columns:
            sync_cols.append(optional)
    lookup = ocel.events.set_index(EID)[sync_cols]
    ocel.relations = ocel.relations.drop(columns=[c for c in sync_cols if c in ocel.relations.columns], errors="ignore")
    ocel.relations = ocel.relations.merge(lookup, left_on=EID, right_index=True, how="left")
    return ocel


def candidate_duplicate_groups(ocel):
    rel = ocel.relations[[EID, OID]].drop_duplicates()
    obj_sets = rel.groupby(EID)[OID].agg(lambda s: tuple(sorted(map(str, s))))
    base = ocel.events[[EID, TS, ACT, "source", "source_event_key", "payload_hash"]].copy()
    base["object_set"] = base[EID].map(obj_sets)
    grouped = (
        base.groupby([TS, ACT], dropna=False)
        .agg(
            event_count=(EID, "count"),
            eids=(EID, lambda s: list(s)),
            sources=("source", lambda s: list(s)),
            object_sets=("object_set", lambda s: list(s)),
        )
        .reset_index()
    )
    return grouped[grouped["event_count"] > 1]


def merge_verified_pair(
    ocel,
    keep_eid,
    drop_eid,
    rule_name,
    refined_activity=None,
    authoritative_by_column=None,
):
    authoritative_by_column = authoritative_by_column or {}
    events = ocel.events.copy()
    relations = ocel.relations.copy()

    keep_mask = events[EID] == keep_eid
    drop_mask = events[EID] == drop_eid
    keep_row = events.loc[keep_mask].iloc[0].copy()
    drop_row = events.loc[drop_mask].iloc[0].copy()

    conflicts = {}
    protected = {EID, "canonical_eid", "source_eids"}
    for col in events.columns:
        if col in protected:
            continue
        kv = keep_row.get(col)
        dv = drop_row.get(col)
        if pd.isna(kv) and not pd.isna(dv):
            keep_row[col] = dv
        elif pd.isna(dv) or kv == dv:
            pass
        else:
            preferred_source = authoritative_by_column.get(col)
            if preferred_source == drop_row["source"]:
                keep_row[col] = dv
            conflicts[col] = {
                "kept_value": None if pd.isna(keep_row[col]) else str(keep_row[col]),
                "dropped_value": None if pd.isna(dv) else str(dv),
                "drop_source": str(drop_row["source"]),
            }

    source_eids = sorted(set(json.loads(keep_row["source_eids"])) | set(json.loads(drop_row["source_eids"])))
    keep_row["source_eids"] = json.dumps(source_eids)
    keep_row["merge_rule"] = rule_name
    keep_row["discarded_conflicts"] = json.dumps(conflicts, sort_keys=True)
    if refined_activity is not None:
        keep_row[ACT] = refined_activity

    events.loc[keep_mask, keep_row.index] = keep_row.values
    relations.loc[relations[EID] == drop_eid, EID] = keep_eid

    events = events.loc[~drop_mask].drop_duplicates(subset=[EID]).reset_index(drop=True)
    relations = relations.drop_duplicates(subset=[EID, OID]).reset_index(drop=True)

    ocel.events = events
    ocel.relations = relations
    return sync_event_columns_to_relations(ocel)


def refine_labels(ocel):
    ocel.events.loc[ocel.events[EID] == "e07", ACT] = "Pack Package [ERP summary]"
    ocel.events.loc[ocel.events[EID] == "e08", ACT] = "Dispatch Package [Warehouse release]"
    ocel.events.loc[ocel.events[EID] == "e09", ACT] = "Dispatch Package [Carrier acceptance]"
    ocel.events.loc[ocel.events[EID] == "e15", ACT] = "Capture Payment [ERP summary]"
    return sync_event_columns_to_relations(ocel)


def add_ordering_key(ocel):
    # Semantic rank first; ingestion time is only a late deterministic fallback.
    rank = {
        "Create Order": 10,
        "Validate Order": 20,
        "Pick Item": 30,
        "Pack Package": 40,
        "Pack Package [ERP summary]": 41,
        "Dispatch Package [Warehouse release]": 50,
        "Dispatch Package [Carrier acceptance]": 60,
        "Handover to Carrier": 70,
        "Issue Invoice": 80,
        "Authorize Payment": 80,
        "Capture Payment": 90,
        "Capture Payment [ERP summary]": 95,
        "Confirm Delivery": 100,
    }
    source_seq = pd.to_numeric(ocel.events["source_seq"], errors="coerce").fillna(10**9).astype("int64")
    ingested = pd.to_datetime(ocel.events["ingested_at"], utc=True, errors="coerce")
    ingested_key = ingested.fillna(pd.Timestamp.max.tz_localize("UTC")).dt.strftime("%Y%m%d%H%M%S%f")
    ocel.events["ordering_key"] = (
        ocel.events[ACT].map(rank).fillna(999).astype(int).astype(str).str.zfill(3)
        + "|"
        + ocel.events["source"].astype(str)
        + "|"
        + source_seq.astype(str).str.zfill(12)
        + "|"
        + ingested_key
        + "|"
        + ocel.events[EID].astype(str)
    )
    return ocel


def validate_referential_integrity(ocel):
    event_ids = set(ocel.events[EID])
    object_ids = set(ocel.objects[OID])
    assert ocel.events[EID].is_unique, "duplicate event IDs remain"
    assert ocel.objects[OID].is_unique, "duplicate object IDs remain"
    assert set(ocel.relations[EID]).issubset(event_ids), "relations reference missing events"
    assert set(ocel.relations[OID]).issubset(object_ids), "relations reference missing objects"
    if ocel.o2o is not None and not ocel.o2o.empty:
        assert set(ocel.o2o[OID]).issubset(object_ids)
    if ocel.e2e is not None and not ocel.e2e.empty:
        assert set(ocel.e2e[EID]).issubset(event_ids)
    return True


raw = copy.deepcopy(ocel_raw)
raw = preserve_originals(raw)
raw = sync_event_columns_to_relations(raw)
duplicate_candidates = candidate_duplicate_groups(raw)
print(duplicate_candidates)

# Conservative scenario
conservative = copy.deepcopy(raw)
conservative = refine_labels(conservative)
conservative = merge_verified_pair(
    conservative,
    keep_eid="e03",
    drop_eid="e04",
    rule_name="verified_same_physical_event_cross_system",
    refined_activity="Pick Item",
    authoritative_by_column={"payload_hash": "WMS"},
)
conservative = merge_verified_pair(
    conservative,
    keep_eid="e11",
    drop_eid="e16",
    rule_name="verified_same_invoice_issue_cross_system",
    refined_activity="Issue Invoice",
    authoritative_by_column={"payload_hash": "ERP"},
)
conservative = pm4py.ocel_drop_duplicates(conservative)  # only to remove duplicate E2O rows after verified merges
conservative = add_ordering_key(conservative)
conservative = pm4py.ocel_sort_by_additional_column(conservative, "ordering_key")
conservative = pm4py.ocel_add_index_based_timedelta(conservative)  # technical tie-break only after semantic order exists
validate_referential_integrity(conservative)

# Evidence-based semantic merge scenario
semantic_merge = copy.deepcopy(conservative)
semantic_merge = merge_verified_pair(
    semantic_merge,
    keep_eid="e06",
    drop_eid="e07",
    rule_name="optional_transition_level_merge_pack",
    refined_activity="Pack Package",
    authoritative_by_column={"payload_hash": "WMS", "source_seq": "WMS"},
)
semantic_merge = pm4py.ocel_drop_duplicates(semantic_merge)
semantic_merge = add_ordering_key(semantic_merge)
semantic_merge = pm4py.ocel_sort_by_additional_column(semantic_merge, "ordering_key")
semantic_merge = pm4py.ocel_add_index_based_timedelta(semantic_merge)
validate_referential_integrity(semantic_merge)

# Aggressive library scenario for sensitivity analysis only.
# WARNING: even with have_common_object=True, this may wrongly collapse e03/e05 or e13/e14
# because they share Order/Invoice objects while differing on Item/Payment objects.
aggressive_library = copy.deepcopy(raw)
aggressive_library = refine_labels(aggressive_library)
aggressive_library = pm4py.ocel_merge_duplicates(aggressive_library, have_common_object=True)
aggressive_library = sync_event_columns_to_relations(aggressive_library)
aggressive_library = add_ordering_key(aggressive_library)
aggressive_library = pm4py.ocel_sort_by_additional_column(aggressive_library, "ordering_key")
aggressive_library = pm4py.ocel_add_index_based_timedelta(aggressive_library)
validate_referential_integrity(aggressive_library)
```

## 7. Sensitivity analysis
Raw dataset: 17 events and 44 E2O relations. It maximizes observability but contains false rework impressions. Order-flattened DFG likely shows `Pick Item -> Pick Item`, `Pack Package -> Pack Package`, `Dispatch Package -> Dispatch Package`, `Issue Invoice -> Issue Invoice`, and `Capture Payment -> Capture Payment`. Some of those are true multiplicity, some are cross-system duplication, and some are summary/detail overlap.

Conservative dataset: about 15 events and 39 E2O relations. Order-flattened DFG loses the false `Issue Invoice -> Issue Invoice` loop and the false `Pick Item` duplicate for `I1`, but still may show `Pick Item -> Pick Item` because `I1` and `I2` are genuinely separate picks on the same order. Item-flattened DFG becomes cleaner: `I1` has one pick, `I2` has one pick, and package packing can follow both. Payment-flattened DFG remains informative: `M1` shows `Authorize Payment -> Capture Payment`; `M2` shows its own capture without being mistaken for rework. OC-DFG edges involving `Order-Item`, `Order-Package`, `Invoice-Payment`, and `Package-Delivery` lose some duplicate frequency but keep topology. ET-OT weights fall slightly for `Pick Item` to `Item/Order/Package` and for `Issue Invoice` to `Order/Invoice`. OTG relations stay faithful because no event is given a fake union of incompatible payments.

Evidence-based merge dataset: about 14 events and 37 E2O relations. The main new change is the disappearance of `Pack Package -> Pack Package` on order or package flattenings. That can improve business-transition views but hides ERP message latency and any mismatch between WMS detail and ERP status propagation. OC-DFG frequency on pack-related edges decreases. Lifecycle measurements for `Package` become shorter because the summary checkpoint disappears.

Aggressive library merge dataset: roughly 10 events and 28 E2O relations if run naively. Order-flattened DFG becomes deceptively simple: the repeated `Pick Item`, `Dispatch Package`, and `Capture Payment` patterns largely disappear. Item-flattened DFG becomes wrong because `I2` may lose its own pick event. Payment-flattened DFG becomes wrong because `M1` and `M2` may be collapsed into one capture super-event. OC-DFG edges and ET-OT weights become distorted by event union: one merged capture can carry `Order`, `Invoice`, `M1`, and `M2` together, overstating cross-object coupling. Apparent rework falls, but only because legitimate multiplicity was destroyed.

Concrete edges or patterns whose interpretation changes:
- `Dispatch Package -> Dispatch Package` changes from false rework in raw to `Warehouse release -> Carrier acceptance` after label refinement.
- `Pack Package -> Pack Package` changes from possible summary/detail overlap to no loop in the evidence-based merge.
- `Issue Invoice -> Issue Invoice` disappears after verified `e11/e16` merge.
- `Authorize Payment -> Capture Payment` for `M1` is preserved in conservative and evidence-based datasets but can be obscured in aggressive library merge.
- `Capture Payment -> Capture Payment` changes from distinct partial payments plus ERP summary in raw to either protected multiplicity or false collapse, depending on scenario.
- `Pick Item -> Pick Item` on the order view changes from mixed duplicate-plus-multiplicity in raw to pure multi-item concurrency in conservative, then to false disappearance in aggressive library merge.
- `Warehouse release -> Handover to Carrier` may be incorrectly shortened if `e09` is merged away.
- Payment-to-invoice ET-OT weights shrink appropriately after `e11/e16` merge but are severely misestimated if `e13/e14/e15` are collapsed.

Performance metrics are especially sensitive. Conservative ordering adds technical microseconds only after choosing an admissible order, so same-second durations remain analytically flagged as tie-broken. Aggressive merge changes both path frequencies and durations by removing checkpoints, not just by ordering them.

## 8. Audit trail and reversibility
Use a provenance table keyed by `canonical_event_id` with these fields: `source_event_ids`, `merge_rule`, `reviewer_or_rule_version`, `confidence`, `reason`, `original_activities`, `refined_activity`, `original_timestamps`, `adjusted_timestamp`, `source_systems`, `source_event_keys`, `attributes_kept_by_source`, `discarded_conflicts`, `relation_union_from_sources`, and `scenario_name`.

Store source-authoritative attribute decisions explicitly, for example `{"invoice_total":"ERP","invoice_number":"BILLING"}` or `{"location":"WMS","scan_device":"SCANNER"}`. Also store whether the event was dropped, merged, relabeled, tie-broken only, or quarantined.

An analyst reconstructs the raw view by exploding each canonical event back into its `source_event_ids`, restoring `original_activity` and `original_timestamp`, replaying the source-specific attributes from `attributes_kept_by_source`, and undoing refined labels or synthetic timedeltas. Because the raw identifiers and original timestamps are never erased, reversibility is mechanical rather than interpretive.

## 9. Failure modes and safeguards
- Collapsing distinct partial payments. Safeguard: require matching discriminating `Payment` objects before any payment-event merge.
- Converting abstraction-level updates into false rework. Safeguard: refine summary labels before DFG analysis and keep abstraction level in provenance.
- Ordering by ingestion time. Safeguard: use `ingested_at` only after semantic and source-local rules fail.
- Treating shared objects as proof of duplication. Safeguard: demand stronger evidence than `have_common_object=True`, especially for shared `Order` or `Invoice`.
- Unioning incompatible E2O relations. Safeguard: on merges, review whether the union creates a business-impossible event linked to multiple discriminating objects.
- Changing durations through synthetic microseconds. Safeguard: preserve `original_timestamp` and mark adjusted timestamps as technical ordering artifacts.
- Losing source-authoritative attributes. Safeguard: use per-column authority rules and keep discarded conflicts.
- Applying duplicate functions to the whole OCEL without inspecting candidate groups. Safeguard: run a candidate-group report first and approve merges group by group.
- Hiding legitimate concurrency by forcing one total order into business semantics. Safeguard: document the partial order separately from the deterministic total order.
- Letting harmonization collisions survive under one label. Safeguard: refine labels before both deduplication and ordering so `e08` and `e09` are not mistaken for duplicates.
