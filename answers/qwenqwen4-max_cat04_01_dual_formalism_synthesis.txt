# 1. Assumptions and Interpretation

1. **Event granularity.** Every activity is atomic and logged at *completion*. A trace is therefore a total order of completion events. "X must be complete before Y starts" is rendered as the precedence constraint `completion(X)  completion(Y)`. Duration, start events, resources, and cancellation are out of scope.
2. **Cardinality.** `Register Deviation`, `Contain Material`, `Analyze Root Cause`, `Plan Verification`, `Design Corrective Action`, `Release Material`, `Archive Case` occur exactly once per case. `Consult Supplier` occurs 0 or 1 times. `Execute Trial`/`Inspect Trial` occur *k  1* times, `Adjust Parameters` exactly *k  1* times. The approval route executes exactly one alternative.
3. **Risk route = free exclusive choice.** "low risk"/"high risk" is data, so it is abstracted to `XOR(Supervisor Review, PARALLEL(Quality Review, Regulatory Review))`. The choice is *nondeterministic*, not data-guarded: neither model can detect that a high-risk case wrongly took the supervisor-only route. The high-risk branch is an unordered conjunction (either completion order, overlap allowed).
4. **Supplier option = XOR with a silent skip.** `XOR(, Consult Supplier)` (process tree) / `OperatorPOWL(XOR, [SilentTransition(), CS])` (POWL). This gives "at most once" for free, because the operator is executed once. Selection is a free choice; no data predicate is encoded.
5. **Inspection outcome = free loop exit.** The trial cycle is `LOOP(SEQ(Execute Trial, Inspect Trial), Adjust Parameters)` with the standard semantics `body (redo body)*`. "Fail"  take the redo branch, "pass"  exit. This structurally guarantees that `Adjust Parameters` is *always* followed by a new `Execute Trial`–`Inspect Trial` cycle and can never follow the final (passing) inspection. No `Inspect Trial (pass)` / `Inspect Trial (fail)` label split is introduced.
6. **No duplicate visible labels.** Both models contain exactly one node per activity label. Duplication is *discussed* as an alternative policy (§3, §6) but not used, because it corrupts activity frequencies, alignment costs, and precision/fitness interpretation.
7. **Approximation policy for the process tree: permissive over-approximation, duplicate-free, concurrency-preserving.** The tree keeps *every* intended ordering constraint except two: `Analyze Root Cause  approval route` and `Analyze Root Cause  Consult Supplier`. Consequently `L(intended)  L(tree)`, and the tree additionally admits approvals/supplier consultation that complete before root-cause analysis. I chose this over a conservative under-approximation because the narrative's core intent (req. 6–9: independently progressing obligations that overlap the trial and are joined only at release) is exactly what a block-structured tree cannot keep while also keeping the two analysis gates. §3 documents the rejected alternatives and their costs.
8. **POWL is exact modulo the mandated data abstraction.** The root `StrictPartialOrder` *is* the intended precedence relation; choice, optionality and looping are local operators. No extra order edges are added, so no intended interleaving is lost and no unintended one is gained (beyond the free choices required by assumption 3–5).
9. **"May overlap" = true concurrency, observed as absence of order.** Semantically I read it as genuine concurrency (partial-order/true-concurrency reading, which POWL supports natively). Operationally, on completion-only logs, true concurrency is *indistinguishable* from "no ordering constraint", so both models are validated on interleavings of completion events. This is a real expressiveness limit of the log, not only of the models (see §8).
10. **No hidden obligations.** No timeouts, no rework outside the trial loop, no re-opening of containment, no partial releases, no case cancellation. `Archive Case` is the unique sink.

# 3. PM4Py Process-Tree Model

**Compact expression** (pm4py textual syntax; the code below builds the same object graph explicitly and does not depend on the parser):

```text
->(
  'Register Deviation',
  *(
     ->(                                  # work pipeline
        *( ->('Contain Material','Plan Verification'),          # containment stream
           ->('Analyze Root Cause','Design Corrective Action')  # analysis stream
         ),                                                     # AND-join of the two work products
        loop( ->('Execute Trial','Inspect Trial'), 'Adjust Parameters' )
     ),
     X( 'Supervisor Review', *('Quality Review','Regulatory Review') ),   # risk route
     X( tau, 'Consult Supplier' )                                        # optional supplier
  ),                                     # join = release synchronization (D17)
  'Release Material',
  'Archive Case'
)
```

Mapping to the narrative: the outer `->` fixes D1/D18; the inner `*(CMPV, ARCDCA)` gives D2–D5 and D3 (branch independence); sequencing the loop *after* that parallel block gives the AND-join D10 and the loop shape D12–D15; the three top-level parallel branches give D11 and D16 (approvals and supplier may overlap the whole pipeline) and D17 (the parallel join is the release gate); `X(SR, *(QR,RR))` gives D7/D8; `X(tau, CS)` gives D9's optionality.

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def op_node(operator, children):
    """Build an operator node and wire parent/child links explicitly."""
    node = ProcessTree(operator=operator)
    for c in children:
        node.children.append(c)
        c.parent = node
    return node

def act(label):
    return ProcessTree(label=label)          # visible leaf

def tau():
    return ProcessTree()                     # label=None, operator=None  => silent leaf

# --- containment stream: CM -> PV -------------------------------------------
containment = op_node(Operator.SEQUENCE, [act("Contain Material"),
                                          act("Plan Verification")])

# --- analysis stream: ARC -> DCA --------------------------------------------
analysis = op_node(Operator.SEQUENCE, [act("Analyze Root Cause"),
                                       act("Design Corrective Action")])

# --- the two work products are produced concurrently, then joined -----------
work_products = op_node(Operator.PARALLEL, [containment, analysis])

# --- trial cycle: (ET -> IT) (AP -> (ET -> IT))* ----------------------------
cycle = op_node(Operator.SEQUENCE, [act("Execute Trial"), act("Inspect Trial")])
trial = op_node(Operator.LOOP, [cycle, act("Adjust Parameters")])

work_pipeline = op_node(Operator.SEQUENCE, [work_products, trial])

# --- risk route: XOR(SR, parallel(QR, RR)) ----------------------------------
high_risk = op_node(Operator.PARALLEL, [act("Quality Review"),
                                        act("Regulatory Review")])
approval_route = op_node(Operator.XOR, [act("Supervisor Review"), high_risk])

# --- optional supplier consultation: XOR(tau, CS) ---------------------------
supplier = op_node(Operator.XOR, [tau(), act("Consult Supplier")])

# --- three independently progressing obligations, joined before release -----
obligations = op_node(Operator.PARALLEL, [work_pipeline, approval_route, supplier])

tree = op_node(Operator.SEQUENCE, [act("Register Deviation"),
                                   obligations,
                                   act("Release Material"),
                                   act("Archive Case")])

# sanity: unique visible labels, exactly one silent leaf
def leaves(t):
    if not t.children:
        return [t]
    out = []
    for c in t.children:
        out.extend(leaves(c))
    return out

lv = leaves(tree)
visible = [n.label for n in lv if n.label is not None]
assert len(visible) == len(set(visible)) == 14
assert sum(1 for n in lv if n.label is None and n.operator is None) == 1
```

**What the tree cannot represent exactly.** Two intended constraints are *dropped*, not approximated by extra structure: **D6** (`Analyze Root Cause  approval route`) and the precedence half of **D9** (`Analyze Root Cause  Consult Supplier`). Because the approval branch and the supplier branch must be parallel with the *entire* work pipeline in order to preserve D11/D16 (overlap with the trial), they cannot be placed inside a block that is sequenced after `Analyze Root Cause` — that activity lives inside the pipeline. The tree therefore admits compliance-critical deviations such as `QR` completing before `ARC` (witness F2). Everything else is exact: D1–D5, D7, D8, D10, D12–D15, D17, D18, and the "at most once" cardinality of `CS`. D19 (data conditions) is abstracted in both models by mandate. A short argument that this loss is unavoidable *given my policy*: to keep `CS` concurrent with the trial, `CS` must sit in a different parallel branch than the trial; the trial's gates `PV`/`DCA` and their gates `CM`/`ARC` must then all be in the trial's branch or in a common prefix; putting `ARC` in the prefix destroys D3 (`CM  ARC`), and putting it in the trial's branch leaves the supplier/approval branch ungated. Hence at least the two analysis gates must go. Two rejected alternatives: (i) *conservative under-approximation* `->(RD, *(->(CM,PV), ->(ARC, *(DCA, X(SR,*(QR,RR)), X(tau,CS)))), loop(->(ET,IT),AP), RM, AC)` — no unsafe admissions, but it forces approvals and supplier consultation to finish **before** the trial, contradicting req. 6/7 and producing false deviations on legitimate flexible cases; (ii) *duplication* — copy `Analyze Root Cause` into the approval and supplier branches; this restores local gating but admits two or three `ARC` completions per case, breaks activity-frequency and cost analysis, makes alignments pick arbitrary copies, and inflates apparent rework. I preferred a single, clearly localized over-approximation over either.

# 4. PM4Py POWL Model

```text
root = StrictPartialOrder{ RD, CM, ARC, PV, DCA, APPR, SUP, TRIAL, RM, AC }
order edges:
  RD -> CM        RD -> ARC
  CM -> PV
  ARC -> DCA      ARC -> APPR      ARC -> SUP
  PV -> TRIAL     DCA -> TRIAL
  TRIAL -> RM     APPR -> RM       SUP -> RM
  RM -> AC

APPR  = OperatorPOWL(XOR,  [ SR , StrictPartialOrder{QR, RR} (no edges) ])
SUP   = OperatorPOWL(XOR,  [ SilentTransition , CS ])
TRIAL = OperatorPOWL(LOOP, [ StrictPartialOrder{ET, IT} with ET->IT , AP ])
```

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

RD  = Transition(label="Register Deviation")
CM  = Transition(label="Contain Material")
ARC = Transition(label="Analyze Root Cause")
PV  = Transition(label="Plan Verification")
DCA = Transition(label="Design Corrective Action")
SR  = Transition(label="Supervisor Review")
QR  = Transition(label="Quality Review")
RR  = Transition(label="Regulatory Review")
CS  = Transition(label="Consult Supplier")
ET  = Transition(label="Execute Trial")
IT  = Transition(label="Inspect Trial")
AP  = Transition(label="Adjust Parameters")
RM  = Transition(label="Release Material")
AC  = Transition(label="Archive Case")

# high-risk sub-route: QR and RR unordered (either completion order, may overlap)
high_risk = StrictPartialOrder(nodes=[QR, RR])          # deliberately no edges

# D7: exclusive risk route
approval_route = OperatorPOWL(operator=Operator.XOR, children=[SR, high_risk])

# D9: optional supplier consultation, at most once
supplier_option = OperatorPOWL(operator=Operator.XOR,
                               children=[SilentTransition(), CS])

# D12-D15: trial cycle, redo = Adjust Parameters
cycle = StrictPartialOrder(nodes=[ET, IT])
cycle.order.add_edge(ET, IT)
trial = OperatorPOWL(operator=Operator.LOOP, children=[cycle, AP])

# root partial order: the intended dependency relation, nothing more
powl = StrictPartialOrder(nodes=[RD, CM, ARC, PV, DCA,
                                 approval_route, supplier_option, trial, RM, AC])

powl.order.add_edge(RD, CM)                    # D2
powl.order.add_edge(RD, ARC)                   # D2
powl.order.add_edge(CM, PV)                    # D4
powl.order.add_edge(ARC, DCA)                  # D5
powl.order.add_edge(ARC, approval_route)       # D6  (missing in the tree)
powl.order.add_edge(ARC, supplier_option)      # D9  (missing in the tree)
powl.order.add_edge(PV, trial)                 # D10 (cross-branch gate)
powl.order.add_edge(DCA, trial)                # D10 (cross-branch gate)
powl.order.add_edge(trial, RM)                 # D17
powl.order.add_edge(approval_route, RM)        # D17
powl.order.add_edge(supplier_option, RM)       # D17
powl.order.add_edge(RM, AC)                    # D18
```

**Why unconnected pairs stay concurrent.** In a `StrictPartialOrder`, only the (transitive closure of the) added edges constrain execution; every other pair is incomparable and may overlap or complete in either order. The intentionally unconnected pairs are exactly the intended independences: `CM  ARC` (D3, two independent work streams); `PV  ARC`, `PV  DCA`, `PV  approval_route`, `PV  supplier_option` (planning depends only on containment); `DCA  approval_route`, `DCA  supplier_option` (both gated by `ARC`, mutually independent); `approval_route  trial` (D11, approvals may overlap the trial cycle); `supplier_option  {PV, DCA, approval_route, trial}` (D16); `QR  RR` inside `high_risk` (D8). No transitive edges (e.g. `RD  PV`, `ARC  trial`) are added — they are implied and would add no constraint. Crucially, `PV  trial` and `DCA  trial` are *cross-branch* edges into a single node, which is precisely the non-block-structured AND-join a process tree cannot express without also joining the approval branch.

# 7. Preferred Representation and Validation Plan

**Canonical representation: the POWL model.** It is exact modulo the abstraction that req. 11 forces on *both* formalisms: every intended precedence, choice, option, loop and independence appears once, and the non-block-structured AND-join (`PV, DCA  trial`) plus the deferred release join are expressed directly as partial-order edges. The tree is retained only as a *permissive envelope* (useful as a cheap upper bound and for tools that require trees), never as the compliance oracle, because it cannot see approvals/supplier work that precedes root-cause analysis.

Validation plan (each step is evidence to inspect, not proof):

Additional targeted checks:

- **Silent-behaviour / skip abuse:** the trace RD, CM, ARC, PV, DCA, ET, IT, RM, AC (no approval at all) must be **unfit in both** models — this proves the `` is confined to the supplier option and cannot silently discharge the approval obligation. Also assert structurally that the tree has exactly one silent leaf and the POWL exactly one `SilentTransition`, and that neither is a child of the approval `XOR`.
- **Duplicate-label / cardinality:** assert unique visible labels in both models (code in §3); test …, CS, …, CS, … (two consultations) and …, RM, CS, AC (consultation after release) are unfit in both; test that `ARC` never appears twice in any playout trace.
- **Loop-shape check:** in every sampled trace, verify `#AP == #ET  1`, `#ET == #IT`, and that the last trial-family event is `Inspect Trial`.
- **Precision probe:** compute `pm4py.precision_token_based_replay(log_p, net_t, im_t, fm_t)`; a value < 1 localizes the escaping edges introduced by the dropped gates.

**Limitations.** (i) Successful conversion and a "sound" verdict say nothing about fidelity — a sound net can still admit W7. (ii) Sampling cannot prove `L(POWL)  L(tree)`; it can only fail to refute it, and the loop makes the languages infinite (I cap at 3 iterations, so deep-loop interactions are untested). (iii) Token-based replay with silent transitions can silently "repair" orderings; alignments with default costs may prefer -moves and mask deviations, so both diagnostics must be compared. (iv) Completion-only traces cannot distinguish true overlap from sequential execution, so D3/D11/D16 are only validated as *absence of order*, never as genuine concurrency. (v) Data guards (risk, supplier flag, inspection result) are untestable here by construction. (vi) POWLPetri conversion and `play_out`/`check_soundness` signatures vary across pm4py versions; the `try/except` fallback means the POWL side may end up validated only structurally plus by witness replay on a hand-built net.

# 8. Final Self-Critique

1. **Semantic, not syntactic: the tree's dropped analysis gates are compliance-relevant.** My over-approximation cannot flag a Quality/Regulatory Review or a supplier consultation that completes before root-cause analysis (W7). I argued that *some* gate must be dropped under a duplicate-free, concurrency-preserving policy, but that argument is informal and restricted to the structural family I considered — I have not proved a general impossibility theorem, and a cleverer tree (e.g. one that sacrifices a *different*, less critical independence such as `PV  approvals`) might dominate mine on business risk. The choice of *which* constraint to lose is a judgment call I made explicit but did not optimize against a stated cost model.
2. **Semantic: point-based abstraction of durational activities.** Because events are completions, "X complete before Y starts" and "X completes before Y completes" collapse into the same constraint, and "may overlap" is unverifiable. A real case where `Execute Trial` *started* before `Plan Verification` finished but *completed* after it is indistinguishable from a compliant case in both models; likewise the free loop exit permits arbitrarily many implausible iterations. Neither model can express the minimum-duration or resource constraints that make the intended overlap meaningful.
3. **Validation is empirical and version-fragile.** The inclusion claim rests on sampled playout plus replay, and the POWL side may fall back to structural checks if `convert_to_petri_net` does not support POWL in the installed version. I also did not exhibit a formal witness set that *separates* the two languages exhaustively (only one exposing witness, W7), nor did I check the tree net for boundedness properties beyond what `check_soundness` reports, so an unexpected unbounded place in the loop/parallel encoding could go unnoticed.
