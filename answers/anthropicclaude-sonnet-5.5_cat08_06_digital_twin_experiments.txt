## 1. Model scope and state variables

### 1.1 Boundary and purpose
The twin covers the municipal permit process from portal submission to a permit or rejection, including the post-decision appeal loop. It is a **hybrid discrete-event simulation with agent-like entities**: cases are processed by calendar-constrained resource pools, and architects, inspection bundles, and objection clusters are explicit entities that couple cases.

The process model is used as a skeleton, not as the simulator. The simplified tree has only two explicit rework loops (completeness, inspection). It does not represent rework after Planning, Legal or appeal, it does not encode "Decision drafting waits for all applicable results", and it places Planning, Fire and Environmental in parallel even though P001 shows Fire after Planning. The simulator therefore uses a **routing state machine with token/AND-join semantics**, discovered and checked with PM4Py and extended with business rules.

| Layer | Content |
|---|---|
| L0 Data/model (PM4Py) | Log formatting, variants, DFG and performance DFG, process tree, conformance, case-arrival statistics |
| L1 Calibration | Distributions, branching probabilities, calendars, latent-variable models, parameter uncertainty |
| L2 Simulation engine | Arrival generation, routing, resource pools and calendars, inspection planner, external-delay models, policy hooks |
| L3 Experiment manager | Scenarios, common random numbers, replications, output analysis, sensitivity analysis |

**Out of scope:** the quality of permit decisions (for example, the safety effect of skipping inspections) and staff behavior beyond aggregate productivity factors. These are tracked as proxy/guardrail metrics and are not optimized.

### 1.2 Level of detail
- Time resolution is minutes, with calendars at hourly granularity. Service is measured in **work-hours** and elapsed time is computed through calendars.
- Activity-level granularity matches the log. Each activity is assigned to a resource pool, not an individual, except inspectors, who need location and route state. Individual identity for clerks and planners matters only for the two Simple-only planners.
- System tasks (portal, Issue permit, Public-notice timer) have effectively infinite capacity.

### 1.3 Entities

| Entity | Key attributes |
|---|---|
| Application (case) | case_type, district, architect_id, application_value, flags requires_fire / requires_environment / requires_public_notice, latent true flags (area-threshold fire need, environmental sensitivity), latent `prior_violation`, latent `objection` flag and severity, missing-doc count, rework counters per loop, priority/age, bundle_id |
| Architect | id, size class (top-20 or other), baseline weekly rate, burst state, districts served |
| Bundle | (district, architect_id or neighbour group), member cases, opening time, release rule, planned visit day |
| Objection cluster | Latent shared state over (district, time window, optionally architect or project group) that raises objection probability for related cases |
| Resource pool | Pool name, headcount or FTE, productivity factor, calendar, priority rule, reserved capacity |
| Inspector | Location/district, day plan, travel state, weekly availability |
| Calendar | Weekly pattern, public holidays, council-meeting weeks, seasonal multipliers, temporary staff windows |
| Applicant / third-party | Response-time models (missing documents, consultant reports, inspection readiness, appeal filing), kept separate from municipal service |

### 1.4 State variables
**Case-level**
- Stage tokens: `completeness`, `planning_done`, `fire_done/NA`, `env_done/NA`, `notice_done/NA`, `inspection_done/NA`, `legal_done/NA`.
- Timestamps per activity (ready, start, complete) and cumulative municipal, applicant and external time.
- Rework counters and reasons (latent class).

**System-level**
- Simulation clock, queue contents per pool with ages, resources busy/free, on/off duty.
- WIP and backlog by stage and case type.
- Open bundles per (district, architect).
- Council-meeting and holiday calendar, current policy configuration, current seasonal regime.

### 1.5 Queues and disciplines
- Completeness: FIFO, with a Monday portal-support adjustment.
- Planning: priority by case type pool (two Simple-only planners), FIFO within pool, optionally aging-based (D6).
- Fire, Environmental, Legal: FIFO or priority by age/SLA risk.
- Inspection scheduling  bundle buffer  inspector day plans.
- Decision drafting: a join queue. A case enters only when all applicable tokens are complete, and it then competes for planners.
- Emergency decisions (removed from the log): a small high-priority stream (for example 1–2%, scenario-dependent) that pre-empts planner and legal capacity.

### 1.6 Cross-case dependencies
1. **Architect bursts:** a cluster arrival process for top-20 architects creates correlated arrivals within a week.
2. **Shared queues:** all queueing is emergent and never sampled from a "waiting" distribution.
3. **Inspection bundling:** cases from the same architect and district, or the same district, are bundled. This cuts per-case travel and delays the first case (a holding window).
4. **Objection clusters:** a latent neighborhood/project factor correlates objections, which lengthen public notice for related cases.
5. **Council calendar:** Legal and Public-notice closure weeks affect all cases simultaneously.
6. **Applicant behavior within architects:** architect-level random effects for missing-doc probability and response speed.

### 2.2 Arrivals
- Aggregate submissions to hourly, daily and weekly counts. Fit an NHPP intensity
  (t) =  · s(month) · d(weekday) · h(hour) · holiday(t).
  - s: Jan–Feb = 1.0, Mar–May and Sep–Nov = 1.7. Jun–Aug and Dec must be estimated. With 18 months, Jul–Dec is seen only once, so give wide intervals.
  - d: Monday = 2.2 × Wednesday. Estimate Tue, Thu, Fri, Sat and Sun; the portal is open 24/7.
  - Sanity check: 31,200 cases in 18 months is about 1,730 per month, or 80 per working day on average.
- **Architect clusters:** for each top-20 architect, fit a cluster (Neyman–Scott or Hawkes-like) process with a parent rate and a negative-binomial batch size within a week. The remaining architects form a Poisson background. Top-20 share = 31% is a calibration target.
- Fit a joint model of attributes given architect and type: case_type | architect, district | architect, value | type (lognormal), flags | type and district.
- Overdispersion check: compare variance-to-mean of weekly counts with the Poisson value. Use a negative binomial or random-intensity model if needed.

### 2.3 Service times
- Start timestamps are largely missing, so **the log gives elapsed intervals, not service times**.
- Where start times exist (`lifecycle:transition` or a start column), compute service directly.
- Elsewhere, use the empirical median and p90 as priors. For a lognormal,  = ln(median) and  = ln(p90/median)/1.2816. For example, Completeness check has   1.0 and Planning review (3.5h and 14h)   1.08.
- **Do not treat "median waiting before activity" as an input.** It is an output to validate against. Sampling it would freeze queue behavior and make interventions meaningless.
- Calibrate service scale and effective capacity by **simulation-based inference** (ABC or simulated method of moments). Choose parameters so that simulated inter-event elapsed time distributions, per activity and case type, match observed ones. This is the principled way to separate waiting from service when only completion timestamps exist.
- Fit by activity × case type (and district for Site inspection): lognormal, Weibull, log-logistic and mixtures. Model tails above p90 with a generalized Pareto if warranted. Inspection = on-site time + district-specific travel time + no-show probability.
- **Limitation to state in reports:** any waiting/service split is inferred. The elapsed gap = waiting + service (+ non-permit work, + calendar closure). Reports must say which part is observed and which is modelled.

### 2.4 Waiting times
- Waiting is emergent from queue, calendar, priority and join logic.
- Empirical elapsed time is used for validation, and for bounds: for example, Fire waiting must include closed days (Mon, Fri, weekends).
- Purely external waits (applicant response, consultant report, public-notice minimum, council calendar) are modelled as **exogenous delays**, not queues.

### 2.5 Branching probabilities
- Estimate from variants and attributes: P(missing docs | type, architect, value), P(Fire), P(Env), P(Public notice), P(Legal check), P(Reject).
- Use logistic or hierarchical (architect random effect) models, with case-type-stratified frequencies as the baseline.
- Known gaps: the fire area threshold and environmental sensitivity are not in the log. Treat the "true" requirement as a latent variable, where observed flag = yes implies required. Estimate the hidden remainder from cases where a review occurred despite flag = no. If that is not possible, use scenario ranges.

### 2.6 Rework
- Identify loops from repeated activities (completeness, inspection) and from variants such as Planning  re-Planning or Legal  Decision drafting. Extend the model beyond the tree with explicit loops: after Planning, after Inspection, after Legal, and after appeal.
- For each loop estimate P(rework | type, stage), the distribution of rework count (geometric with decaying probability), and shorter service for repeat passes.
- Rework reasons are unstructured text. Optionally use a topic model or weak labelling to create latent classes. These are auxiliary, and the twin must not depend on them being correct.
- Appeals: applicant-initiated, modelled as post-decision events for Complex variance (and optionally others), with filing delay and a council-calendar-dependent path.

### 2.7 Resource calendars
- Start from the HR calendars, then validate against event-log weekday and hour activity profiles.
- Calendar model = weekly pattern × FTE × productivity factor × exceptions (holidays, council weeks, leave).
  - Clerks: 5 FTE, Mon–Fri 08–16, one on Monday portal support, so effective 4 clerks on Monday for checks (a test factor).
  - Planners: 8 FTE, including 2 Simple-only (6 general-pool capacity).
  - Fire: 2 FTE-equivalent over Tue–Thu, about 26.7 h/day of capacity.
  - Environmental: 3 FTE × 0.6 = 1.8 effective.
  - Inspectors: 4 FTE, Tue–Fri field days.
  - Legal: 2 FTE, blocked in council-meeting weeks except urgent cases.
- Calibrate a productive-time factor (for example 0.6–0.9) per pool so that simulated completions per pool-week match the log.
- Because HR calendars were reconstructed, treat FTE and productivity as uncertain parameters in sensitivity analysis.

### 2.8 Dependencies
- **Architect effects:** architect random effects in missing-doc probability and applicant response times. Estimate cross-case correlation via intra-architect correlation and within-week co-occurrence.
- **Bundling:** estimate the current share of same-architect/same-district co-visits from inspection dates, if any. If not observable, the baseline assumes no formal bundling (only incidental co-scheduling).
- **Objections (latent):** there is no objection event. Use public-notice duration as a proxy: fit a two-component mixture (a component near the fixed 14-day minimum, plus a long-tail component) per case type and district. Interpret the tail component as "probable objection", not as an observed fact. Add a shared cluster random effect over (district, time) to capture correlated objections. Validate only against the duration distribution and report as latent.
- **Council calendar:** reconstruct from dates of Legal slowdowns and external calendars.

## 3. Assumptions

**Arrivals**
- Non-homogeneous arrivals with multipliers by season, weekday and hour, plus an architect cluster process. Arrival rates are exogenous except under D1 (pre-submission effort may defer submissions) and D7 (slots shift timing).
- Summer/December multipliers are estimated with wide uncertainty.
- Unobserved demand (abandoned or withdrawn applications before the first logged event) is ignored and flagged.

**Service times**
- Service times are lognormal/Weibull with heavy-tail correction, conditional on activity × type (× district for inspection). Service is sampled in work-hours and consumed only during calendar-open hours.
- Independence of service times across activities within a case is the default, with an optional case-complexity random effect, since complexity likely correlates across steps.
- Reworked passes are shorter by an estimated factor (for example 0.5–0.8).

**Routing**
- Flags are as observed, plus latent hidden requirements (fire area threshold, environmental sensitivity) by probability. True and "known to the municipality" requirements can differ, and delayed discovery triggers rework.
- Public notice is required for Complex variance and for some New residential cases, with the New residential share estimated from data.
- Decision drafting starts only after all applicable tokens are complete.
- Legal check and Reject probabilities are conditional on type and on rework history.

**Resources and calendars**
- Pools are homogeneous except Simple-only planners. Productivity factors are constant within a scenario, with seasonal variants as a stress test.
- Holidays and council weeks are known in advance and sampled from the real calendar for the run.
- Non-permit work for environmental staff is a fixed 40% reduction.
- No pre-emption except for emergency cases. No overtime unless a scenario sets it.
- Inspector travel depends on district, and D3/D5 have longer travel.

**Rework**
- Rework probabilities are stage- and type-specific, with no memory beyond a counter. Repeated rework has decaying probability.
- Rework reasons are not used causally.

**Applicant and third-party response**
- Applicant response times (missing docs, inspection readiness, appeal filing) and consultant reports are separate distributions, heavy-tailed, with an architect random effect. They are estimated with survival methods (Kaplan–Meier or parametric survival) to handle cases that never responded (withdrawal).
- They are **not** affected by municipal capacity unless a scenario changes them (D1, D9).
- Applicant effort outside the municipal clock (pre-submission for D1) is tracked separately.

**Cross-case dependencies**
- Architect bursts, shared queues and calendars, inspection bundles and objection clusters are modelled as described. Bundles have a holding window and a maximum size, and the first case waits for the window to close.
- Objection clusters are a latent modelling construct with assumed scale and correlation.

**Non-stationary demand**
- Seasonal and weekday multipliers are deterministic, with stochastic variation around them. Capacity changes (for example D4) are scheduled by calendar, so capacity is also time-varying.
- The same seasonal pattern is assumed to repeat over the horizon, with no long-term trend unless a stress scenario adds one.

**Missing data**
- Missing start timestamps: the waiting/service split is inferred through simulation-based calibration, and the uncertainty is carried forward.
- Objection events are missing and are **not** treated as observed. The objection is a latent variable, with prevalence and effect as uncertain parameters.
- Rework reasons are not coded and are treated as latent classes, not as features to rely on.
- Removed emergency decisions: a small assumed stream is injected and examined in sensitivity analysis.
- Calendars come from HR data and not from the log. They are validated and treated as uncertain.
- The flattened log underrepresents dependencies. Cross-case coupling parameters (bundle opportunity, objection cluster size) are weakly identified, so they are carried as scenario ranges with priors.

| D8 | Environmental-review triage | Triage sensitivity 80 / 90 / 95%; specificity 60 / 80%; review skipped for low-risk; late-discovery rework probability and delay | Shorter Environmental queue and fewer hours. False negatives cause late rework and tail increase. Depends on incomplete sensitivity data. |
| D9 | Objection early-warning | Detection recall 40 / 60 / 80%; precision 50 / 70%; effect: objection duration reduction 10 / 25%; extra planner/clerk hours per flagged case | Shorter public-notice tail for Complex and New residential. Extra work and false alarms. Effect is unverifiable with current data, so report as a sensitivity band. |
| D10 | D1 + D2 + D3 + D4 | As D1–D4 at central levels, plus a 2 factorial (16 cells) over on/off of each | Interactions: D2 and D4 both relieve inspectors (diminishing returns). D3 may counteract D4 benefits for Simple cases. D1 reduces clerk load. The factorial decomposes main effects and interactions. |

### 4.2 Combination and follow-up experiments
- **C1:** D3 + D4 (inspection package). **C2:** D5 + D6 + D9 (long-case package). **C3:** D1 + D7 (front-end package).
- Best single interventions per bottleneck are combined after one-factor screening, using fractional factorial design to limit runs.

### 4.3 Stress scenarios (applied to B0 and to the leading interventions, including D10)

| ID | Stress | Levels | What it tests |
|---|---|---|---|
| S1 | Demand surge | Peak multiplier 1.7  2.0–2.2; top-20 burst intensity ×1.5; all-year +15% | Robustness of capacity-related interventions (D4, D6, D7) |

## 5. Warm-up, replications, and uncertainty treatment

### 5.1 Warm-up and run length
- The system is **non-stationary and terminating-like**, so a single steady-state warm-up is not appropriate.
- **Initial conditions:** seed the model with the WIP snapshot at a chosen log date (cases in stage with ages, bundle states, queue contents), so the system does not start empty. As a robustness check, also run from empty with a long warm-up.
- **Warm-up length:** the long tail (Complex variance p90  260 days) means queues and WIP need about 9–12 months to equilibrate to the seasonal cycle. Use Welch's procedure on WIP and mean cycle time to confirm. Discard the first 12 months.
- **Measurement window:** 24 months (two full seasonal cycles) after warm-up, with cases assigned to cohorts by **arrival date**.
- **Drain period:** continue 12 months after the last arrival so long cases complete. Otherwise tail metrics are right-censored and biased downward. Report the number of censored cases if any.

### 5.2 Replications and seeds
- Pilot: 30 replications to estimate variance. Then sequentially add replications until the 95% CI half-width is  5% of the mean for median cycle time and  10% for p90/p95 of each case type. Expect  100 replications for tail metrics, and more if the paired-difference CI still straddles zero.
- **Seeds:** use `numpy.random.SeedSequence` spawned into independent streams per source (arrivals, architects, attributes, each activity's service, applicant responses, objections, rework routing, inspection no-shows). Replication *r* uses the same root seed across scenarios (**common random numbers**), so scenario differences are paired and less noisy. Record all seeds.
- If a policy changes the number of random draws on a stream (for example D2 skipping inspections), keep stream alignment by drawing and discarding.

### 5.3 Intervals
- For each metric and scenario, report the mean across replications with a t-based 95% CI, and for paired differences (scenario  baseline) the CI of the paired difference.
- For quantiles, compute the quantile within each replication, then summarize across replications (mean and percentile interval). Alternatively use a bootstrap of replications. Quantile CIs are wider, which is expected.
- Report the **probability of improvement** P( < 0) over replications and parameter draws.

### 5.4 Parameter uncertainty (two layers)
1. **Input uncertainty:** bootstrap the log by blocks (architect-week or case clusters) to preserve dependence, refit parameters, and draw a parameter set per replication (single-loop), or do an outer loop of 50–100 parameter sets × 5–10 inner replications (nested). Latent parameters (objection prevalence, hidden requirement share, calendar productivity) get explicit priors or ranges.
2. **Stochastic uncertainty:** replication noise given parameters.
- Use a variance-component decomposition (input vs. stochastic) to show which dominates. If input uncertainty dominates, more replications won't help and calibration data should be improved instead.

### 5.5 Sensitivity analysis
- Screening with Morris or fractional factorial across about 20 uncertain parameters: seasonal multipliers, productivity factors, FTE, objection prevalence and duration, hidden-requirement share, rework probabilities, applicant response tails, intervention effect sizes, bundling parameters.
- Variance-based (Sobol) indices or random-forest importance for the top 6–8 parameters.
- Report **break-even thresholds**, for example "D1 needs  X% reduction in missing docs to beat D3".

### 5.6 Heavy-tailed durations
- Avoid means alone. Report median, p75, p90, p95, and the share above SLA thresholds.
- Fit tails explicitly (lognormal/Weibull body with generalized Pareto tail above p90). Test the tail fit with QQ plots on log scale and mean-excess plots.
- Do not truncate or winsorize for the decision metrics. Use trimming only for diagnostics.
- Use survival methods (Kaplan–Meier) for applicant and consultant delays so withdrawn or censored cases are not dropped.
- For tail metrics use more replications and report quantile CIs. With heavy tails, sample means converge slowly, so means get "tail-sensitive" warnings.
- Consider a withdrawal/abandonment cap (for example applications lapsing after a legal maximum) if supported by policy.

## 6. Validation strategy

| Type | Procedure | Acceptance guide |
|---|---|---|
| **Face validation** | Walk-throughs with clerks, planners, fire, environmental, legal, inspectors, scheduling staff. Review the routing state machine, calendars, bundling rules, join logic, and the plausibility of queue behavior. Check the weekend-timestamp discrepancy with staff. | Domain experts sign off the model structure and the list of known simplifications |
| **Event-log replay** | (a) Control-flow: replay the log on the Petri net from the process tree to check that the skeleton fits. Expect imperfect fit, because the tree omits several rework loops, and document the deviations. (b) Trace-driven simulation: use observed arrival times, attributes and routing, but simulate service, queues and calendars. Compare per-case completion times. | Per-case error distribution is centered near zero, and the main deviations are explained |
| **Distributional validation** | Compare simulated and observed cycle-time distributions by case type and variant group: medians, p90, QQ plots, KS/Anderson–Darling or Wasserstein distance, and the fit of the tail. Also compare inter-event elapsed time per activity and the variant shares. | Median within ±10% and p90 within ±15–20% per case type and variant group. Variant shares within a few percentage points. |
| **Resource-utilization validation** | Compare simulated busy hours per pool-week with workload inferred from event counts × service estimates, and with staff-reported workload. Include the 40% non-permit time for environmental staff. | Within ±10 percentage points, with differences explained by unobserved work |
| **Bottleneck validation** | Compare queue lengths and waiting-time rankings by activity and season. Does the twin reproduce known pain points (Planning queue, Inspection wait, Legal in council weeks, Monday Completeness spikes)? Check that bottleneck shifts under capacity changes are consistent with staff experience. | Same top bottlenecks and plausible seasonal movement |
| **Dependency validation** | Compare simulated and observed architect-week clustering (bundle sizes, top-20 share 31%), Monday/Wednesday ratio 2.2, seasonal 1.7×, correlation of public-notice durations within district-time windows. | Targets reproduced within CI |
| **Out-of-sample validation** | Calibrate on the first ~12 months and predict the final ~6 months (ideally including one peak season, Sep–Nov). Also do rolling-origin tests and hold out a season. Use natural experiments (staff absences, holiday clusters) as mini intervention tests. | Prediction errors comparable to in-sample, and no systematic bias at peak |

**Scope of validation claims:** validation supports comparing interventions *relative to baseline under the stated assumptions*. It does not validate effects of interventions without historical analogues (D1, D2, D5, D8, D9). For these, the effect-size assumptions remain unvalidated and should be tested in pilots. Until calibration and validation pass, rankings are hypotheses, not optimal decisions.

## 7. Decision criteria

Thresholds below are **proposals to be agreed with the municipality**, expressed mostly relative to the validated baseline.

| Metric | Definition | Suggested threshold/range |
|---|---|---|
| Median cycle time | Per case type, submission  decision | Improve  5–10% vs. baseline, or at least no worsening, with the paired CI excluding zero for "improved" |
| Tail (p90/p95) | Per case type | p90 improvement  10% for target groups, and no case type's p90 worsens > 5% |
| SLA compliance by type | Share finishing within SLA (to be set; illustrative: Simple 30 days, New residential 120, Commercial 150, Complex variance 280, near the baseline p90 values) | Target  90% per type, or +5 pp over baseline; no type falls by > 2 pp |
| Municipal vs. applicant time | Processing time separated from applicant/third-party time (also pre-submission effort under D1) | Report both. Do not credit a gain that only moves effort to applicants. |
| Fairness across districts | Ratio of p90 (or median) worst district / best district, especially D3/D5 | Not worse than baseline, and  1.25–1.3 (to be confirmed) |
| Fairness across architects | Gap between top-20 architects and others, and between bundled and non-bundled cases | Gap does not grow > 10%; bundling must not systematically delay small applicants |
| Resource utilization | By pool and week | Mean 70–85%; weekly peak  90%; no pool > 95% for more than 2 consecutive weeks; no pool's utilization driven to very low levels without reason |
| Rework | Rework rate by loop and type, mean rework loops per case | Not higher than baseline + 2 pp, unless offset by large speed gains |
| Backlog | WIP by stage and cases older than 90/180 days, WIP at end of peak seasons | Peak WIP and the aged count no higher than baseline, and recovery time after peak shorter |
| Robustness | Performance across stress scenarios S1–S8 | Improvement holds in  80% of stress scenarios, or minimize maximum regret. Report the worst case. |
| Quality/risk guardrails | For D2: number of cases skipping inspection, and estimated share with prior violations. For D8: missed requirements and late-discovery rework. | Must be within agreed risk limits. These are not simulated as outcome quality. |
| Probability of improvement | P( < 0 or > 0 as relevant) across replications and parameter draws |  0.9 for recommending, 0.7–0.9 for "promising, pilot" |

**Selection procedure**
1. Drop any intervention that violates a guardrail or worsens a protected group beyond limits.
2. Rank the rest on a Pareto front (median/tail by case type, backlog, utilization, fairness). Weighted scoring is optional but must be transparent, with weights set by stakeholders.
3. Check robustness across S1–S8 and parameter uncertainty.
4. Recommend pilots for interventions whose effects depend on unverified assumptions. Do not claim optimality: the output is a ranked shortlist with uncertainty, conditional on calibrated and validated behaviour.

def load_and_format_log(csv_text: Optional[str] = None, path: Optional[str] = None) -> pd.DataFrame:
    """Load with pandas (there is no pm4py.read_csv) and format with PM4Py conventions."""

def add_elapsed_and_calendar_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Only ONE timestamp per event is available (assumed completion time), so the gap
    between consecutive events = waiting + service of the later event (+ closed calendar
    time + any non-permit work). True service/waiting cannot be separated without start
    timestamps. If a 'start_timestamp' column exists, service is computed exactly.
    """
    df = df.sort_values(["case:concept:name", "time:timestamp"]).copy()
    g = df.groupby("case:concept:name")["time:timestamp"]
    df["prev_ts"] = g.shift(1)
    df["elapsed_since_prev_h"] = (df["time:timestamp"] - df["prev_ts"]).dt.total_seconds() / 3600
    df["case_start"] = g.transform("min")
    df["age_days"] = (df["time:timestamp"] - df["case_start"]).dt.total_seconds() / 86400
    df["weekday"] = df["time:timestamp"].dt.day_name()
    df["hour"] = df["time:timestamp"].dt.hour

    if "start_timestamp" in df.columns:  # observed start -> exact split where available
        df["service_h_obs"] = (df["time:timestamp"] - pd.to_datetime(df["start_timestamp"])
                               ).dt.total_seconds() / 3600
        df["wait_h_obs"] = (pd.to_datetime(df["start_timestamp"]) - df["prev_ts"]
                            ).dt.total_seconds() / 3600

    # INFERRED split (prior-based, for diagnostics ONLY; label as inferred, never as observed):
    prior = df["concept:name"].map(SERVICE_PRIOR_H)
    df["service_h_inferred"] = np.minimum(df["elapsed_since_prev_h"], prior)
    df["wait_h_inferred"] = (df["elapsed_since_prev_h"] - df["service_h_inferred"]).clip(lower=0)
    ext = df["concept:name"].isin(EXTERNAL_ACTIVITIES)
    df.loc[ext, ["service_h_inferred", "wait_h_inferred"]] = np.nan  # external delay, not municipal
    return df


def calendar_consistency_check(df: pd.DataFrame) -> pd.DataFrame:
    """Weekday x pool completion counts, to compare with the reconstructed HR calendars.
    (The excerpt has weekend timestamps, e.g. 2026-01-03, -17 and 2026-02-07, that conflict
    with Mon-Fri / Tue-Thu calendars.)"""
    d = df.copy()
    d["pool"] = d["org:resource"].str.replace(r"_\d+$", "", regex=True)
    return d.pivot_table(index="pool", columns="weekday", values="case:concept:name",
                         aggfunc="count", fill_value=0)

def load_reference_tree():
    """
    Limitations of the simplified string:
    - the redo labels 'Completeness rework' / 'Inspection rework' never occur in the log;
      they represent repeated activities, so they are replaced by tau for conformance;
    - no rework after Planning, Legal or appeal; no Reject path from earlier stages;

      and Fire after Planning (as in P001) is not implied; the simulator's routing layer

        return tree
    except Exception as exc:                                    # parser is strict about syntax
        print(f"Tree parsing failed ({exc}); fall back to a hand-built ProcessTree.")
        return None

def lognormal_from_median_p90(median: float, p90: float):
    """mu, sigma for a lognormal with the given median and p90 (z_0.9 = 1.2816)."""
    return np.log(median), np.log(p90 / median) / 1.2816

class Simulator:
    def __init__(self, params: dict, policy: PolicyConfig, streams: Dict[str, np.random.Generator],
                 horizon_h: float, warmup_h: float, initial_wip: Optional[pd.DataFrame] = None):
        self.params, self.policy, self.streams = params, policy, streams
        self.horizon_h, self.warmup_h = horizon_h, warmup_h
        self.clock, self.events, self._seq = 0.0, [], 0
        self.arrivals = ArrivalGenerator(params["arrivals"], streams["arrivals"])
        self.router = Router(params["routing"], policy, streams["routing"])
        self.insp = InspectionPlanner(params["inspection"], policy)
        self.external = ExternalDelayModel(params["external"], streams["external"])
        self.pools: Dict[str, ResourcePool] = {}     # built from params["calendars"]
        self.completed: List[Case] = []
        self.initial_wip = initial_wip               # seed WIP from log snapshot

    def schedule(self, t: float, handler: Callable, *args):
        self._seq += 1
        heapq.heappush(self.events, (t, self._seq, handler, args))

def make_streams(root_seed: int, names: List[str]) -> Dict[str, np.random.Generator]:
    """Independent streams per source -> common random numbers across scenarios."""
    children = np.random.SeedSequence(root_seed).spawn(len(names))
    return {n: np.random.default_rng(c) for n, c in zip(names, children)}


STREAM_NAMES = ["arrivals", "attributes", "service", "external", "routing", "rework", "inspection"]


def summarize(case_table: pd.DataFrame, sla_days: Dict[str, float]) -> dict:
    """Metrics per case type: median/p90/p95 cycle time, SLA compliance, rework, district gaps ..."""
    out = {}
    for ct, grp in case_table.groupby("case_type"):
        d = grp["cycle_days"]
        out[ct] = dict(median=d.median(), p90=d.quantile(0.9), p95=d.quantile(0.95),
                       sla=(d <= sla_days.get(ct, np.inf)).mean())
    return out


class ExperimentRunner:
    def __init__(self, base_params: dict, sla_days: Dict[str, float],
                 n_reps: int = 100, root_seed: int = 20260101):
        self.base_params, self.sla_days = base_params, sla_days
        self.n_reps, self.root_seed = n_reps, root_seed

    def sample_params(self, rep: int) -> dict:
        """Draw a parameter set from bootstrap / posterior (input uncertainty)."""
        return self.base_params  # placeholder

    def run_scenario(self, policy: PolicyConfig, overrides: Optional[dict] = None) -> List[dict]:
        results = []
        for r in range(self.n_reps):
            params = {**self.sample_params(r), **(overrides or {})}
            streams = make_streams(self.root_seed + r, STREAM_NAMES)   # same r -> same randomness
            sim = Simulator(params, policy, streams, horizon_h=24 * 30 * 24, warmup_h=12 * 30 * 24)
            log = sim.run()
            # case_table = build_case_table(log)   # cohort by arrival date, drain period included
            # results.append(summarize(case_table, self.sla_days))
        return results

    def compare(self, baseline: List[dict], scenario: List[dict], metric: Callable) -> dict:
        """Paired differences per replication -> mean, CI, P(improvement)."""
        diffs = np.array([metric(s) - metric(b) for b, s in zip(baseline, scenario)])
        half = 1.96 * diffs.std(ddof=1) / np.sqrt(len(diffs))
        return dict(mean=diffs.mean(), ci=(diffs.mean() - half, diffs.mean() + half),
                    p_improve=(diffs < 0).mean())

**Notes on the skeleton.** PM4Py is used only for loading/formatting, variants, DFGs, arrival statistics, tree parsing and conformance. The simulation engine takes calibrated parameters and never depends on PM4Py objects. Service/waiting columns labelled `_inferred` are diagnostics derived from priors, not observed values, and `elapsed_since_prev_h` is the only quantity that is directly supported by the timestamps. The latent `objection`, `prior_violation`, and hidden fire/environmental requirements are modelled as latent variables with uncertain parameters, never as observed data.
