## 1. Consistency rules and evidence model

I use the following evidence hierarchy.

| Rule or signal | Classification | Use |
|---|---|---|
| Every E2O endpoint must reference an existing event and object; every O2O endpoint must reference existing objects | hard invariant | Reject dangling relations. |
| Duplicate relations with the same endpoints and qualifier should not be inserted | hard invariant | Prevent technical duplication. |
| Qualifier direction must follow the domain vocabulary, e.g. `Delivery carries Package`, `Package packs Item` | hard invariant | Do not insert inverse-looking records under the same qualifier. |
| `Create Order` has one Order; `Add Item` has one Order and one Item; `Record Payment` has one Payment | strong default | Existing records satisfy these cardinalities; additions should not violate them without evidence. |
| `Pack Item` ordinarily has one Item and one Package | strong default | Supports linking ev08 to PK-8, but scanner-outage semantics mean this is not mandatory. |
| `Dispatch Package` ordinarily has one Package and one Delivery | strong default | Supports a delivery relation for ev10, while bulk dispatch remains possible. |
| `Issue Invoice` has one Invoice and one or more Orders | strong default | Allows ORD-B to be added to ev12 and billed by INV-44. |
| An item is normally packed by only one package in the observed operational stage | strong default | Favors PK-8 for IT-B1 without also assigning it to PK-7. |
| Carrier reference `N-421` resembles ev10’s `N-421?` | strong default | Strongly supports DEL-Y at ev10 despite the uncertainty marker. |
| Payment bank reference and amount agree with the Payment object | strong default | Confirms the event-to-Payment records, but does not by itself identify an Invoice. |
| Temporal order create/add  pack  dispatch  confirm  invoice/payment | strong default | Repairs should preserve lifecycle order. Same timestamps permit bulk handling but do not prove it. |
| Shared customer C17 | weak heuristic | Useful for candidate generation, poor for distinguishing ORD-A from ORD-B because both share it. |
| Invoice total 230 equals 130 + 100; PAY-1 + PAY-2 also equals 230 | weak heuristic | Supports, but does not prove, consolidated billing and settlement. Fees, tax, discounts, split payments, and unapplied cash remain possible. |
| Shared NORTH route | weak heuristic | Makes either delivery superficially compatible with PK-8 and ev11; identifiers are more discriminating. |
| Existing O2O structure | mixed evidence | Existing edges are strong contextual evidence, but missing edges cannot be treated as negative facts. |
| Adding DEL-X to ev10 despite `N-421?` and DEL-X’s `N-420` | evidence against a repair | Possible only as a bulk dispatch interpretation; identifier mismatch lowers confidence. |
| Adding only DEL-X to ev10 while leaving DEL-Y unused | evidence against a repair | Wastes the strongest identifier match and creates a less coherent DEL-Y lifecycle. |
| Assigning ev11 uniquely from `N-42*` | evidence against a repair | The wildcard fits both `N-420` and `N-421`; portal semantics explicitly permit aggregate or order-only confirmation. |
| Treating amount equality as proof of invoice/payment linkage | evidence against a repair | Amounts are supportive but non-unique and defeasible. |
| Completing every object’s lifecycle merely because it is present | evidence against a repair | This would optimize completeness rather than evidential plausibility. |

I combine signals qualitatively rather than multiplying pseudo-independent probabilities. Exact or near-exact identifiers receive greatest weight, followed by activity cardinality and lifecycle order. Existing O2O edges constrain likely interpretations, but they are not complete. Customer, route, time, and arithmetic are corroborative signals. Correlated evidence is discounted: for example, `INV-44 total=230` and event amount 230 are likely copied from the same source and are not two independent observations.

## 3. Alternative repair bundles

### Bundle A: conservative/minimum-change repair

**ev08 and PK-8.** Add `ev08  PK-8` and `PK-8 packs IT-B1`. The scanner reference is unusually specific, and it restores the normal one-Item/one-Package event cardinality without inventing entities. PK-8 consequently contains items from ORD-A and ORD-B. That is unusual but operationally possible; it should not be “corrected” by moving IT-A2 or IT-B1 elsewhere.

**ev10 and deliveries.** Add `ev10  DEL-Y` and `DEL-Y carries PK-8`. This is the clearest missing dispatch relation because `N-421?` nearly matches DEL-Y’s carrier reference. Do not add DEL-X to ev10: ev09 already provides a complete DEL-X/PK-7 dispatch at the same time.

**ev11.** Leave the observed `ev11  ORD-A` unchanged and add no Delivery. The wildcard cannot distinguish DEL-X and DEL-Y, and the portal may have lost the carrier identifier. This preserves an order-level confirmation rather than manufacturing a unique Delivery case. DEL-Y can still have dispatch but no observed confirmation.

**Invoice.** Add neither `ev12  ORD-B` nor `INV-44 bills ORD-B`. Consolidation is plausible, but customer and arithmetic alone are insufficient for the minimum-change bundle. INV-44 remains explicitly tied only to ORD-A despite the suspicious total.

**PAY-2.** Leave PAY-2 unapplied: retain `ev14  PAY-2`, but add neither `ev14  INV-44` nor `PAY-2 settles INV-44`. This is allowed by the domain and avoids treating the split total as proof.

This bundle produces coherent physical lifecycles while retaining ambiguity in finance and confirmation. It leaves no event orphaned, but DEL-Y lacks confirmation and PAY-2 lacks an Invoice association by design.

### Bundle B: consolidated fulfillment and finance

Bundle B keeps Bundle A’s PK-8 and DEL-Y repairs, then adopts a broader interpretation.

**ev08 and PK-8.** Add the same two packing relations. PK-8 is a consolidated package containing IT-A2 and IT-B1 from two orders.

**ev10 and DEL-X/DEL-Y.** Add `ev10  DEL-Y` and `DEL-Y carries PK-8`, but not DEL-X. Concurrent ev09 and ev10 are interpreted as separate dispatch records for N-420 and N-421, rather than one bulk event.

**ev11.** Interpret `N-42*` as an aggregate portal acknowledgement and add both DEL-X and DEL-Y to ev11. This is permitted by the stated semantics and explains the wildcard. However, it is only provisional: the retained ORD-A relation does not establish that ORD-B was confirmed, and DEL-Y carries a mixed-order package under this bundle.

**Invoice.** Add `ev12  ORD-B` and `INV-44 bills ORD-B`. The shared customer and `130 + 100 = 230` make a consolidated invoice plausible, although fees and adjustments prevent certainty.

**PAY-2.** Add `ev14  INV-44` and `PAY-2 settles INV-44`, interpreting PAY-1 and PAY-2 as split settlement of INV-44. Again, amount equality supports but does not prove application.

The full bundle forms a coherent consolidated story: separate orders feed a shared package, two deliveries are acknowledged together, one invoice bills both orders, and two payments settle it. Its very narrative coherence is also a risk: several edges are correlated consequences of one consolidation hypothesis rather than independent confirmations.

### Bundle C: bulk dispatch but unresolved confirmation/finance

A further plausible alternative would treat ev10 as a bulk dispatch of PK-8 under both DEL-X and DEL-Y, while leaving ev11 order-only and finance unresolved. This is weaker than A because DEL-X’s carrier reference conflicts with ev10 and ev09 already dispatches DEL-X. It illustrates that same-time events and the bulk-dispatch rule permit, but do not compel, shared Delivery participation.

## 5. Lifecycle and cardinality audit

### Order

ORD-A has Create, two Add Item events, an order-level Confirm Delivery, and Issue Invoice. ORD-B has Create and Add Item only in Bundle A. Its item later packs and dispatches through object links, but those events do not directly relate to ORD-B; this is incomplete rather than impossible. Bundle B adds invoice participation to ORD-B but still does not add it to ev11.

No Order is orphaned. The shared PK-8 creates a many-orders-through-one-package pattern through Item/O2O paths. That is suspicious but permitted.

### Item

All Items have Add Item and Pack Item participation after Bundle A. Each has one `contains` parent and one `packs` parent. IT-B1’s PK-8 membership is supported by ev08’s scanner and reconstructed E2O/O2O pair, but those are not independent confirmations: P02 is inferred from the same scan interpretation as P01.

### Package

PK-7 has Pack and Dispatch; PK-8 has two Pack events and a Dispatch after repair. PK-8’s two Items belong to different Orders, creating consolidation rather than a cardinality violation. Both packages are non-orphaned.

For PK-7, E2O ev06/ev09 and O2O packing/carrying structure independently existed in the input. For PK-8’s IT-B1 and DEL-Y edges, the repaired E2O and O2O records encode the same abductive decisions and must not be double-counted as independent evidence.

### Delivery

DEL-X has dispatch participation and carries PK-7. DEL-Y becomes non-orphaned through ev10 and carries PK-8. Under Bundle A, neither Delivery is explicitly related to a confirmation event: ev11 remains Order-only. That lifecycle truncation is allowed by the portal-loss semantics.

Bundle B creates one Confirm Delivery event related to two Deliveries. This is an allowed one-to-many event relation, but Delivery flattening will duplicate ev11 into both cases.

### Invoice

INV-44 participates in Issue Invoice and PAY-1’s payment event and bills ORD-A. Bundle A leaves its total unexplained by explicit billed objects, which is suspicious but not inconsistent because adjustments or missing scope are possible. Bundle B adds ORD-B and forms a one-Invoice/two-Order relation.

PAY-1’s Invoice relation is independently present as both E2O and O2O. By contrast, any Bundle-B Invoice–ORD-B E2O/O2O agreement is circular if counted as confirmation: both additions arise from the same customer-and-arithmetic hypothesis.

### Payment

PAY-1 has a complete observed payment-to-invoice pattern. PAY-2 has a Record Payment event but no Invoice in Bundle A, representing possible unapplied cash. It is not an orphan object because it participates in ev14. Bundle B gives INV-44 two Payments, a normal split-payment cardinality.

Adding both P12 and P13 does not provide two independent proofs. The event relation and settlement edge are paired expressions of one inferred application.

### Events and global cardinality

No event is orphaned before or after repair. ev08 and ev10 move from deficient default cardinality to the normal one Item/Package and Package/Delivery pattern. Bundle A introduces no event-level many-to-many relation. Bundle B introduces ev11-to-two-Deliveries and ev12-to-two-Orders, both domain-permitted but analytically consequential.

## 6. Downstream process-mining effects

### OC-DFG

In the unrepaired log, Package PK-8 appears at ev07 and ev10, but not ev08. Its Package lifecycle is therefore `Pack Item  Dispatch Package`, while IT-B1 ends at Pack Item without a Package bridge. DEL-Y has no events.

Bundle A makes PK-8’s sequence `Pack Item(ev07)  Pack Item(ev08)  Dispatch Package(ev10)`. This can add or increase a Package-type self-loop `Pack Item  Pack Item`. DEL-Y obtains a singleton `Dispatch Package` trace. Through object-centric participation, ev08 and ev10 become connected by PK-8.

Bundle B additionally gives DEL-X and DEL-Y `Dispatch Package  Confirm Delivery`, potentially counting that edge twice across Delivery objects. It also adds `Issue Invoice  Record Payment` for INV-44 at ev14 after ev13, yielding an Invoice sequence `Issue Invoice  Record Payment  Record Payment` and potentially a `Record Payment  Record Payment` edge. For ORD-B, `Add Item  Issue Invoice` may appear, skipping explicit fulfillment activities in its direct Order trace.

### OTG

The unrepaired OTG includes Order–Item, Package–Item, Delivery–Package, Invoice–Order, and Payment–Invoice type connections, but individual structures are incomplete. Bundle A strengthens existing Package–Item and Delivery–Package topology without adding new object-type pairs: PK-8–IT-B1 and DEL-Y–PK-8.

Bundle B increases multiplicities: one Package links to Items from two Orders, INV-44 links to two Orders, and two Payments link to one Invoice. These patterns can make consolidation appear standard if a small log is summarized without confidence labels.

### ET–OT graph

Bundle A raises `Pack Item–Package` participation from two to three Pack events and `Dispatch Package–Delivery` from one to two Dispatch events. Bundle B further adds `Confirm Delivery–Delivery`, `Issue Invoice–Order` participation for ORD-B, and `Record Payment–Invoice` participation for ev14.

Counts must distinguish event-object relations from unique events. One ev11 related to two Deliveries means one event frequency but two total Delivery participations.

### Flattenings

- **Order:** Unrepaired and Bundle A leave ORD-B’s direct trace at Create/Add Item, while ORD-A contains Confirm Delivery and Issue Invoice. Bundle B appends Issue Invoice to ORD-B. It should not automatically propagate Pack or Dispatch events from Items unless enrichment is explicitly applied.
- **Package:** Bundle A inserts ev08 into PK-8 and creates the two-Pack sequence. Unrepaired PK-8 omits IT-B1’s packing event.
- **Delivery:** Unrepaired DEL-Y has no case. Bundle A gives it Dispatch only. Bundle B gives both deliveries Confirm Delivery; ev11 is duplicated across two flattened cases.
- **Invoice:** Bundle A has ev12 and ev13 for INV-44. Bundle B adds ev14, creating two payment occurrences in its case.
- **Payment:** Bundle A leaves PAY-2’s trace as ev14 only. Bundle B’s direct Payment flattening still has one event per Payment; the settlement O2O changes topology but does not automatically copy Invoice events into Payment cases.

### Frequency semantics

Event frequency remains 14 in every bundle because no events are invented. Unique objects per activity change when relations are added: ev11 still has frequency one, but Bundle B associates two unique Delivery objects with it. Total object participations change more sharply: a multi-object event contributes multiple relations. Reporting “Confirm Delivery frequency = 2” from Delivery-flattened occurrences would differ from event-based frequency = 1.

Likewise, Issue Invoice remains one event, but Bundle B has two Order participations. Record Payment remains two events globally, while INV-44’s flattened case contains both.

### Equivalent-execution clustering around Order

In the unrepaired log and Bundle A, ORD-A and ORD-B have visibly different direct executions: ORD-A reaches confirmation/invoice, while ORD-B stops after Add Item. Bundle B moves them closer by sharing Issue Invoice, and O2O-aware enrichment could make both appear connected to PK-8 and its dispatch. This may cluster the orders as a consolidated execution.

That clustering can be misleading: ORD-A has a direct ev11 relation, ORD-B does not. If transitive enrichment propagates ev11 through DEL-Y  PK-8  IT-B1  ORD-B, it may erase precisely the ambiguity the repair preserved.

## 8. Over-repair warnings

1. **Forcing ev11 onto DEL-X alone** would create an apparently certain `Dispatch Package  Confirm Delivery` lifecycle despite the wildcard fitting both deliveries and the portal-loss rule.

2. **Assigning ev11 to both deliveries without qualification** would duplicate one physical event in Delivery flattening and could double the apparent confirmation count.

3. **Adding ORD-B to ev11 through PK-8’s mixed contents** would turn transitive connectivity into direct event participation and falsely imply that the portal explicitly confirmed ORD-B.

4. **Treating 230 = 130 + 100 as proof** would create a consolidated Invoice–Order structure that may actually reflect fees, discounts, tax, or an unobserved billing scope.

5. **Treating PAY-1 + PAY-2 = 230 as proof of settlement** would eliminate the legitimate unapplied-cash interpretation and manufacture an Invoice lifecycle ending in two payments.

6. **Adding DEL-X to ev10 because ev09 has the same timestamp** could duplicate DEL-X’s Dispatch activity and produce a false bulk-dispatch pattern. Timestamp equality is not event identity.

7. **Linking PK-8 to IT-B1 and then counting the resulting O2O edge as independent support for ev08  PK-8** would be circular. Both relations arise from the same scanner interpretation.

8. **Propagating all package and delivery events to Orders through O2O enrichment** could make ORD-A and ORD-B appear to share identical fulfillment traces, hiding the fact that only ORD-A is directly related to ev11.

9. **Repairing DEL-Y or PAY-2 solely to avoid orphan or partial lifecycles** would substitute a completeness objective for evidence. Partial lifecycles are explicitly plausible here.

10. **Adding inverse O2O records with unchanged qualifiers**, such as `PK-8 carries DEL-Y`, would corrupt directional semantics and alter the OTG with a relation that has the wrong business meaning.
