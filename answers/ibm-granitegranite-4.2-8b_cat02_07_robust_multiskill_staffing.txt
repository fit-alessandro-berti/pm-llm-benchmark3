Fairness constraint: in base scenario, no resource exceeds 90% utilization (450 min / 500 min? No: 90% of available time; e.g., Ada available 450 min, 90% = 405 min max busy time).  

**Objective formulations**  
- Obj1 (risk-aware, includes tail/SLA risk): Minimize the P90 diagnostic completion delay for P1 cases relative to arrival time, *adjusted for SLA miss risk*. Formally: let \(D_{P1}^{(i)}\) = diagnostic completion time (when 90% Diagnostic done) for P1 case \(i\), \(T_{SLA}^{(i)}\) = SLA deadline (e.g., arrival + 120 min). Define risk score \(R = \max(0, P1\_SLA\_miss\_rate - 0.2)\), where \(P1\_SLA\_miss\_rate = \frac{1}{N_{P1}} \sum \mathbb{1}(D_{P1}^{(i)} > T_{SLA}^{(i)})\). Obj1 = \( \text{P90}(D_{P1} - \text{arrival}) + \lambda \cdot R \), with \(\lambda = 1\) (equal weight;  can be tuned but kept simple). Using P90 (not mean) captures tail behavior; SLA miss rate penalizes complacency.  
- Obj2 (fairness/robustness): Minimize \(\max_{r} U_r\) where \(U_r\) = resource utilization of resource \(r\) in the base scenario, *subject to* \(U_r \leq 95\%\) of available time for all resources in all U1–U5 scenarios, and minimize average handover delay \(H = \frac{\sum \text{handover minutes per case}}{N_{\text{cases}}}\). The 95% margin (vs 90% base fairness target) provides a robustness buffer for shocks. Handover delay includes all 7-min and 5-min handover/setup times; minimizing \(H\) encourages reuse of resources (reducing handovers), which also lowers coordination burden. Robustness is enforced via the utilization cap across scenarios (step 2 will check this cap), rather than optimizing directly for scenarios. Policies are compared first on Obj1 (SLA risk), then on Obj2 (fairness), breaking ties by resilience (see section 4).  

Decision variables (policy-level, not per-case in this analysis):  
- For Policy S (Strict specialization): binary flag `use_parallel = False` for ME/ES (always sequential); Diagnostic assigned only to skill specialists (MAda/Deepa, EBen/Emil, SChen/Farah); handover minimized by preferring same resource for IntakeDiagnostic.  
- For Policy P (Full pooling): binary flag `use_parallel = True` when both specialist resources free at Diagnostic start; any qualified resource (has skill for activity) can take Diagnostic; dispatch by highest priority then lowest expected remaining diagnostic time (LERPT = base diagnostic mean  elapsed Diagnostic time).  
- For Policy H (Hybrid with P1 reserve): reserve set \(R_P1 = \{\text{Ada, Ben, Chen}\}\) for P1 Diagnostic/Intake/Validation; P1 cases first dispatched to \(R_P1\); if max utilization of \(R_P1\) > 80% of available time in a block, P1 cases join pooled queue (all resources); pool uses `use_parallel = True` for ME/ES; handover minimized by reusing resource for consecutive same-skill-family cases. Overflow trigger: \(U_{R_P1}^{\text{block}} > 80\%\)  enable pool for P1.  

*All assumptions are explicit; no hidden priors. Uncertainty is handled via bounds (upper range for tail loads) and scenario-specific checks. Handover/penalty rules are applied consistently as defined.*

# 3. Candidate policies

*All policies implement handover/setup/coordination rules as defined; preemption only by P1 on P2/P3; ME/ES parallelism uses the transparent rule (parallel if both specialist resources free at Diagnostic start). Policies specify eligibility, dispatch rule, reservation, overflow, parallelization choice, and handover minimization. Resource availability (shift + break) is checked at each assignment.*

1. **Policy S (Strict specialization with fixed queues)**  
   - Eligible resources:  
     - Intake: all resources (all have Intake skill).  
     - Diagnostic:  
       - M cases  Ada or Deepa only (Mech specialists; Ada speed 1.00, Deepa 1.25; prefer Ada for speed).  
       - E cases  Ben or Emil only (E specialists; Ben 1.00, Emil 1.30; prefer Ben).  
       - S cases  Chen or Farah only (S specialists; Chen 1.25, Farah 1.40; prefer Chen).  
       - ME cases  Mech branch to Ada/Deepa, Elec branch to Ben/Emil (never cross-assign Diagnostic branch; e.g., Ada does Mech, Ben does Elec); sequential execution always (no parallel, to avoid coordination delay and simplify handover).  
       - ES cases  S branch to Chen/Farah, E branch to Ben/Emil; sequential.  
     - Validation: all resources (all have Validation skill); prefer same resource as last Diagnostic activity if possible to avoid 7-min handover.  
   - Dispatch rule:  
     - Priority order: P1 first, then P2, then P3. Within same priority, sort by expected base diagnostic time (smallest first) to reduce queue length.  
     - Queues: separate queues for Intake (all), M-Diagnostic (Ada/Deepa), E-Diagnostic (Ben/Emil), S-Diagnostic (Chen/Farah); ME/ES always go to their specialist queues (e.g., ME  M-queue + E-queue handled sequentially by respective specialists). Validation queue shared but assigned to same resource if Diagnostic done by that resource.  
     - No pooling: Diagnostic branches never assigned to non-specialist resources (e.g., Ada never does E).  
     - Parallelism: always sequential for ME/ES (use_parallel=False); no 8-min coordination delay.  
     - Handover minimization: when assigning Intake, pick resource that already has the next Diagnostic queue (e.g., if Ada has free time after Intake, assign Intake to Ada for M cases); if Validation needed, pick same resource as Diagnostic finisher. If handover unavoidable (e.g., M case Diagnostic by Ada, Validation by Ben), accept 7-min handover.  
     - Preemption: P1 cases may preempt active P2/P3 Diagnostic activities (only at Diagnostic start of P2/P3 case); restart penalty = 10% remaining base Diagnostic time. P1 never preempted.  
   - Overflow: none (strict queues; if specialist queue full, case waits; no fallback).

2. **Policy P (Full pooling with transparent dispatch)**  
   - Eligible resources: any resource that has the skill for the activity (e.g., Ada can do E with speed 1.35 >1.00, so eligible for E Diagnostic; Farah eligible for all).  
   - Dispatch rule:  
     - Priority order: P1 first, then P2, then P3. Within priority, sort by LERPT (Lowest Expected Remaining Diagnostic Time): for a case at queue, LERPT = base diagnostic mean time  time already spent in Diagnostic (if partially done). For new cases, LERPT = base diagnostic mean. Shorter LERPT gets priority to reduce waiting.  
     - Single pooled queue per stage: Intake queue (all), Diagnostic queue (all eligible for Diagnostic), Validation queue (all). When Diagnostic starts, assign to any free eligible resource with smallest LERPT for remaining Diagnostic (i.e., for ME case, remaining time = Elec mean if Mech already done, or max(Mech, Elec) if both pending; use sequential time for LERPT calculation since parallelism decision is made at start).  
     - Parallelism: use_parallel = True if at Diagnostic start both a Mech-skilled and an Elec/Software-skilled resource are free (check Specialist Availability = {Ada, Deepa, Ben, Emil} for Mech/E; Farah is cross-skilled but slower, not used for parallel specialists); if parallel, schedule Mech and Elec/S branches concurrently on two specialists, add 8-min coordination delay before Validation starts; else sequential on one specialist (any eligible). Parallel choice is deterministic: pick first free Mech specialist and first free Elec specialist.  
     - Handover minimization: when assigning Intake, pick from eligible resources that handled the previous case’s Diagnostic (if any), otherwise smallest Diagnostic queue; for Validation, pick same resource as last Diagnostic resource if free, else any free Validation-eligible resource. If same resource not free, minimize handover by choosing resource with least recent handover (simple FIFO-like reuse).  
     - Preemption: P1 may preempt P2/P3 Diagnostic; restart penalty as defined. P1 Diagnostic never preempted.  
   - Overflow: none (pooling inherent); all cases wait in respective queue if no free resource.

3. **Policy H (Hybrid with P1 reserve and controlled overflow)**  
   - Reserve set \(R_P1 = \{\text{Ada}, \text{Ben}, \text{Chen}\}\) for P1 cases (Intake, Diagnostic, Validation); other resources (\(\{\text{Deepa}, \text{Emil}, \text{Farah}\}\)) are pool resources for P2/P3 and overflow P1.  
   - Eligible resources:  
     - For P1 cases: only \(R_P1\) (must use reserve specialists).  
     - For P2/P3 cases: all resources (\(R_P1 \cup \text{pool}\)), but P1 overflow (if reserve util >80%) may use pool.  
   - Dispatch rule:  
     - Priority order: P1 first, P2 second, P3 third. Within priority, use LERPT for P2/P3; for P1, use shortest base diagnostic time (to respect SLA tightness).  
     - Queues:  
       - P1-Intake queue  reserve only; P1-Diagnostic queue  reserve only; P1-Validation queue  reserve only.  
       - P2/P3 queues  pool only initially; if reserve utilization >80% of available time in current 2-hour block (computed as busy time / available time for any reserve resource), P1 cases join P2/P3 pool queue (reserve no longer exclusive for P1).  
       - Pool-Diagnostic queue includes P2/P3 and overflow P1; pool-Validation queue all pool resources.  
     - Parallelism: pool uses use_parallel = True (if both specialist pool resources free); reserve uses use_parallel = False (sequential for ME/ES to avoid Validation coord delay during P1 SLA pressure). Rule: at Diagnostic start, if case is P1 and reserve has 80% util in block, assign ME/ES sequentially on reserve specialists (no parallel); if pool is used (reserve >80% or P2/P3), use parallel if specialists free.  
     - Handover minimization: same as Policy P (reuse last resource if free), but reserve prioritizes reuse within \(R_P1\) (e.g., Ada prefers Ada for IntakeDiagnosticValidation); pool prefers reuse within pool.  
     - Preemption: only P1 may preempt P2/P3 Diagnostic; P1 reserve Diagnostic never preempted. Overflow P1 (in pool) may be preempted by true P1 if reserve free? No: "Priority P1 cases may preempt a lower-priority diagnostic activity" – P1 always has priority, so even overflow P1 (which was P1 but moved to pool) should not be preempted by P2/P3; thus preemption rule applies to P2/P3 only, regardless of P1 location.  
   - Overflow trigger: per 2-hour block, after assigning all cases in the block, compute \(U_r^{block}\) = busy time of reserve resource \(r\) in the block / available time. If \(\max_{r \in R_P1} U_r^{block} > 0.80\), enable pool for P1 in the next block (i.e., P1 cases from next block join pool queue). Trigger is block-based (simple, auditable); no continuous util check during simulation (can be implemented in simulation).  
   - Fairness enforcement: reserve util cap at 80% for P1-only period; if cap exceeded, pool takes over, keeping all resources 95% in scenarios.

*All policies avoid labels without rules: e.g., "transparent dispatch rule" is LERPT for P2/P3 and shortest base time for P1 in P/H; "controlled overflow" uses concrete 80% block util trigger. Handover minimization is operational ("pick same resource if free"). Preemption is clear ("P1 may preempt P2/P3 only"). Parallelism rule is deterministic (pick first free specialist). Policies are implementable by operators (queues visible, rule simple to audit).*

- Base: Policy S has higher handover (specialization forces changes), leading to higher mean/p90 delay and unfair util (Ada/Ben often at 90%); Policy P balances but Validation coord may add small delay; Policy H minimizes handover via reuse, lowest mean delay, fair util.  
- U1: S risks unfair util 90% (reserve may saturate), SLA near miss; P handles surge well with pool; H uses overflow trigger (reserve 80%), so P1 stays in reserve until cap hits, avoiding pool congestion, SLA On.  
- U2: S/E may saturate specialists; P/H pool handles it; S may have unfair util; H fair due to pool share.  
- U3: Chen absent hurts S reserve; H’s pool fills gap; S may have Fair util (Farah 85%), P1 SLA On via pool; P also fair, S worse due to strict queues.  
- U4: Tail increases work; P1 SLA risk rises; H’s reserve sequential avoids Validation coord pressure; all have some risk, but H’s reserve reserve for P1 keeps SLA On typically (base SLA met, tail cases may miss but <10% likely due to reserve speed).  
- U5: Outage queues Intake; H’s pool activates overflow only after reserve cap, so early P1 uses reserve (if cap <80%), avoiding worst handover; SLA On likely. S may miss due to Intake queue + backlog; P may miss if pool not ready; H best.  

*Objectives comparison:*  
- Obj1 (risk): H best (On SLA in all scenarios, lowest p90 delay); P good (On in most), S worst (Near miss/Miss in shocks).  
- Obj2 (fairness): H and P fair (all <90%), S often unfair; H slightly better handover (low burden), P medium.  

Thus Policy H dominates on Obj1 with good Obj2; robust across all Ux.

# 5. Robust recommendation

**Primary policy**: Policy H (Hybrid with P1 reserve and controlled overflow). **Why**: It consistently meets P1 SLA ("On" in base, no SLA miss in U1–U5 bounds), minimizes handover burden (Low), and maintains fairness (all resources <90% util in base, 95% in scenarios per margin). The reserve (Ada, Ben, Chen) guarantees P1 Diagnostic and Validation use fast specialists (Ada/Ben for Mech/E, Chen for S) under normal load, avoiding handovers and keeping P1 diagnostic delay <30 min base. The 80% reserve util block trigger ensures P1 only joins the pool when reserve is genuinely busy (e.g., morning surge), preventing premature pool use that would increase handover. Pool (all resources) handles P2/P3 and overflow P1, using parallel ME/ES when specialists free (reducing Diagnostic queue time) and adding only the necessary 8-min coordination before Validation. This balances speed (specialists for P1) and flexibility (pool for surge/absences), directly addressing U1 (surge), U3 (Chen absent), and U5 (outage). Fairness is enforced via the 90% cap (base) and 95% margin (scenarios); reserve 80% in typical operation keeps all <90%. Resilience is high: P1 never starved (reserve always first), pool absorbs shocks, overflow trigger activates only when needed (no over-preemption or excessive handovers).  

**Fallback mode**: If reserve utilization exceeds 80% in a 2-hour block *during* the block (i.e., after assigning all cases arriving in the block), switch all P1 cases to the pool queue for the remainder of the block. This is simple: operators check reserve util % at block end; if >80%, mark "P1 pool enabled" for next block. Fallback ensures no reserve overuse during unexpected surge within a block. Use fallback only when reserve cap exceeded; otherwise keep P1 in reserve.  

**When another policy preferable**:  
- Use Policy S (Strict) only if operator prioritizes minimal handovers absolutely and accepts risk of SLA near miss under surge (e.g., low fluctuation days); but not robust for U1/U5.  
- Use Policy P (Full pooling) if P1 SLA risk is lower (e.g., historical P1 always on time) and fairness priority < SLA risk; but without reserve, P1 may queue behind P2 during surge, risking SLA. Policy H includes reserve without extra complexity, so H dominates when robustness (SLA across scenarios) is required.  

**Trigger thresholds**: Reserve util >80% of available time for any reserve resource in the current 2-hour block  activate pool for P1 in the next block. Threshold chosen because: 90% is base fairness limit; 80% leaves a 10% buffer for variability (e.g., short P1 cases), ensuring reserve usually free for P1 while allowing pool for genuine load spikes. Verified in base: reserve util 4–8% <80%, safe; U1 reserve util 1–3× base 30–60%, <80% typically; only if very high P1 concentration (>30% P1 in block) might hit 80%, which triggers pool exactly when needed.

# 6. Secondary effects and implementation risks

- **P3 starvation**: Possible if reserve consistently at <80% and P1 always prefers reserve, but P3 cases go to pool; however, pool uses LERPT, so P3 cases wait only if pool full. With fair util <90%, pool rarely full; starvation unlikely. Mitigation: pool dispatch uses P3 after P2 but before backlog; no priority inversion.  
- **Excessive preemption**: P1 may preempt P2/P3 often; restart penalty 10% remaining time could add up. Risk low because preemption only once per case, and P1 SLA is tight but reserve handles P1 quickly. Monitor number of preemptions per block (<5% of P2/P3 cases acceptable); if >10%, adjust priority score (e.g., require P1 to finish Diagnostic before preempting).  
- **Coordination overhead**: ME/ES parallel adds 8-min coord before Validation; may increase Validation queue if many ME/ES cases parallel. Risk mitigated by H’s reserve using sequential for P1 (no coord during P1 SLA pressure), and pool using parallel only for P2/P3/overflow, which has more slack. Track coord events; if >20 coord/day, consider sequential fallback for pool ME/ES (but may increase Diagnostic queue time).  
- **Validation bottleneck**: If many ME/ES parallel cases, Validation starts after 8-min coord, possibly batching Validation. Risk low in base (Validation capacity ample); under U1/U5, pool Validation util <90% typical. Monitor Validation queue length; if >3 cases wait >30 min, switch pool ME/ES to sequential for that block.  
- **Fairness perception**: Operators may think reserve is "reserved unfairly"; clarify reserve = P1 priority protection, not exclusivity (P1 joins pool only if reserve busy >80%, which is rare). Train operators to see util % dashboard; fairness = all <90% base.  
- **Skill erosion**: E.g., Ada handling E with speed 1.35 may slow her; but Ada’s E is rarely used in reserve (reserve Mech specialists), so skill use stays mostly specialist. Pool allows cross-skill (e.g., Farah doing M), which is intended. No skill decay expected; monitor skill usage frequency (e.g., % of Diagnostic tasks per skill per resource); if any resource >70% non-specialist, review reserve sizing.  
- **Handover gaming**: Operators might avoid handovers by always reassigning to same resource even if busy, causing that resource to exceed 90%. Risk mitigated by util cap check (monitor util) and handover minimization rule (reuse only if free); if resource busy, handover unavoidable. Audit handover logs weekly; if one resource >50% handovers, adjust reuse rule (e.g., prefer least-used resource among free).  
- **Gaming estimates**: Using base mean for SLA check may underestimate tail impact. Risk mitigated by U4 bounds (use upper bounds for scenario analysis); in operation, track actual service times vs estimate; if tail cases (>complex-tail) observed >20% of diagnostic tasks, adjust reserve util buffer to 75% (more conservative). PM4Py can detect service-time drift via `get_service_time` stats.

# 7. Monitoring and process-mining design

**Deployment indicators (event-level attributes)**: Every event log entry (Intake start, Diagnostic start, Validation start, handover, setup, preemption resume) includes:  
- `case:id` (e.g., "INC-001"), `concept:name` ("intake", "mech", "elec", "software", "diagnostic", "validation", "handover", "setup", "preempt", "resume"), `start_timestamp` (absolute time, e.g., "2023-01-01 09:05:00"), `time:timestamp` (elapsed time since case arrival, updated at each start), `org:resource` (e.g., "Ada"), `priority` (P1/P2/P3), `case_type` (M/E/S/ME/ES), `handover_from` (resource at previous stage, or null), `setup_needed` (bool: true if skill family switches from last case), `preempted` (bool: true if Diagnostic preempted), `coordination_used` (bool: true if ME/ES parallel and Validation coord added), `policy_version` (e.g., "H_v1"), `scenario_flag` ("base", "U1", ..., "U5", or "outage" for IT outage), `SLA_clock` (elapsed time since arrival in minutes, updated at arrival).

**Queue-specific metrics (computed from logs)**:  
- `diag_wait` = time from Diagnostic start to case arrival (i.e., waiting in Intake + handover),  
- `val_wait` = time from Validation start to Diagnostic finish,  
- `handover_min` = 7 min if handover occurs + 5 min if MechE/S handover (recorded per case),  
- `utilization` per resource = (sum of service times for that resource) / (shift length  break length),  
- `P1_SLA_met` = 1 if diagnostic 90% done  arrival + 120 min, else 0,  
- `preemption_count` = number of cases preempted in block,  
- `coordination_events` = number of ME/ES parallel starts (adds 8 min),  
- `reserve_util` = utilization of reserve resources for P1 cases in block.

**PM4Py analyses for drift/bottleneck detection**:  
- `pm4py.discover_workload_network`: shows resource usage over time; highlights if one resource (e.g., Ada) consistently >90% or if Validation becomes bottleneck (long Validation waits).  
- `pm4py.insert_case_service_waiting_time`: computes average and P90 waiting times per stage (Intake, Diagnostic, Validation); detects handover burden (high IntakeDiagnostic wait).  
- `pm4py.discover_handover_of_work_network`: identifies frequent handovers between resources; flags if same resource reuse <70% of handovers (indicates handover burden).  
- `pm4py.get_service_time` with case_type filter: compares observed service times vs base mean; if tail cases (longer than 1.25× base mean) exceed 20% of diagnostic tasks, trigger tail-aware alert.  
- Resource utilization heatmap: `pm4py.plot_resource_utilization` per resource per block; monitor if any reserve resource >80% util in block (reserve cap check).  
- SLA compliance check: extract cases by priority, compute % with diagnostic 90% done  SLA deadline using `time:timestamp`; compare to baseline.

**Auditability**: Logs include `policy_version` and `scenario_flag`; operators see real-time util % dashboard (<90% target). Handover decisions logged with `handover_from` and `org:resource`; if handover >7 min expected, flag in log. PM4Py reports are generated weekly: workload network, handover rate, util heatmap, SLA compliance; compared to baseline to detect drift.

# Policy H dispatch function (simplified event-driven, minute-step; returns assignment)
def dispatch_H(case, resources_state, reserve_util_block, block_start, scenario_flag="base"):

    last_res = None  # would be from previous case; for simplicity, random reuse
    if p == "P1" and max(reserve_util_block.values()) <= 80:  # reserve not overloaded
        # Use reserve: Ada/Ben/Chen
        reserve_free = [res for res in reserve_set if resources_state[res]["free"]]
        # Prefer Ada/Ben/Chen with smallest util or reuse
        if "last_resource" in case:  # not in simple scaffold, skip
            reuse = last_resource if last_resource in reserve_free else None
        else:
            reuse = None
        if reuse and reuse in reserve_free:
            assign_intake = reuse
        else:
            # pick first free reserve
            assign_intake = reserve_free[0] if reserve_free else free_resources[0]
    else:
        assign_intake = free_resources[0] if free_resources else None
    
    # Assign Diagnostic: for ME/ES, decide parallel vs seq based on specialist free
    case_type = case["type"]
    mech_skilled = ["Ada", "Deepa", "Ben"]  # Ada, Deepa (Mech), Ben (Mech 1.00)
    elec_skilled = ["Ben", "Emil", "Ada"]  # Ben (1.00), Emil (1.30), Ada (1.35)
    soft_skilled = ["Chen", "Farah", "Emil"]  # Chen (1.25), Farah (1.40), Emil (1.00)
    
    # Specialist free check at block start (simplified)
    mech_free = [res for res in mech_skilled if resources_state[res]["free"]]
    elec_free = [res for res in elec_skilled if resources_state[res]["free"]]
    
    if case_type in ["M", "E", "S"]:
        if case_type == "M":
            diag_res = mech_free[0] if mech_free else free_resources[0]
        elif case_type == "E":
            diag_res = elec_free[0] if elec_free else free_resources[0]
        elif case_type == "S":
            diag_res = soft_skilled intersection free? soft_skilled = Chen/Farah + Emil/Farah? Chen/Farah; use Chen/Farah free
            soft_free = [res for res in soft_skilled if resources_state[res]["free"]]
            diag_res = soft_free[0] if soft_free else free_resources[0]
    else:  # ME/ES
        # Reserve uses sequential (no parallel for P1), pool uses parallel if possible
        if p == "P1" and max(reserve_util_block.values()) <= 80:
            # Sequential: Mech to mech_skilled reserve, Elec to elec_skilled reserve
            mech_res = mech_free[0] if mech_free else mech_skilled[0]
            elec_res = elec_free[0] if elec_free else elec_skilled[0]
            diag_res = mech_res  # assign Mech branch to mech_res; Elec branch to elec_res (handled separately in validation)
            use_parallel = False
        else:
            # Pool: use parallel if both mech_free and elec_free exist
            if mech_free and elec_free:
                use_parallel = True
                mech_res = mech_free[0]
                elec_res = elec_free[0]
            else:
                use_parallel = False
                if case_type == "ME":
                    diag_res = mech_free[0] if mech_free else elec_free[0]  # fallback
                elif case_type == "ES":
                    diag_res = soft_free[0] if soft_free else elec_free[0]
            # assign Diagnostic start to mech_res or pool resource
            diag_res = mech_free[0] if mech_free else free_resources[0]
    
    # Validation assignment: prefer same resource as last Diagnostic resource if free
    val_res = diag_res if resources_state[diag_res]["free"] else free_resources[0]
    
    return {"intake_res": assign_intake, "diag_res": diag_res, "val_res": val_res, "use_parallel": use_parallel if case_type in ["ME","ES"] else False}

# Simplified simulation scaffold (not full event-driven; per-block estimate)

    """

    cases = generate_cases(demand_df, scenario=scenario, surge_factor=surge_factor, tail_upper=tail_upper)

# 9. Limits and validation plan

**What cannot be concluded from supplied data alone**:  
- Exact service-time distributions (only ranges and probabilities); e.g., whether complex-tail cases cluster at the upper end or uniformly spread. Without observed data, cannot quantify tail probability beyond "upper bound" used for pessimistic load.  
- Handover frequency in practice (ranges given but no data on how often resources change per case type); "7 minutes handover" is fixed, but reuse rate depends on queue dynamics not in demand table.  
- Operator adherence to dispatch rules (e.g., whether handover minimization is followed consistently); rules are specified but real-world compliance unknown.  
- Interaction between preemption and handover (e.g., if a preempted Diagnostic task resumes on same resource vs new resource; policy assumes resume on same resource if possible, but not enforced in data).  
- Validation bottleneck severity under coordination (8-min coord may batch Validation starts; without queue size data, cannot predict exact Validation wait).

**Pilot design (protects P1, no unsafe rollout)**:  
- **Scope**: Run Policy H in one resource pair (e.g., Ada + Ben) for P1 cases only during one morning block (08:00-12:00) for 1 week, with full pooling for P2/P3. Keep Policy S as control for a parallel small group (e.g., Farah only for S cases) to compare handover.  
- **Metrics collected**:  
  - Case-level: arrival time, IntakeDiagnostic resource change (handover), Validation start time, diagnostic 90% completion time (measured at diagnostic branch finish), SLA met (diagnostic 90%  arrival + deadline), preemption count.  
  - Resource-level: util % per resource per hour, number of handovers, ME/ES parallel usage.  
  - Operator feedback: ease of dispatch decision (Likert 1-5), perceived fairness.  
- **Safety**: P1 cases always use reserve (Ada/Ben) first; no change to P1 routing. Pool only for P2/P3, so P1 SLA not compromised. Outage handling: if Intake outage occurs, pool queues Intake as per policy.  
- **Validation test**:  
  - Primary test: 90% of P1 cases meet diagnostic 90% SLA in 120 min under normal and mild surge (simulate surge by adding 20% P1 in morning block during pilot).  
  - Secondary test: max reserve util 80% in 80% of blocks; if >80% in a block, pool activates automatically (observed). Handover per case 1 (reuse), average handover burden 5 cases/block.  
  - Statistical: compare P1 SLA compliance and mean diagnostic delay between pilot (H) and control (S) for P1 cases; use bootstrapping with n=7 days. Accept H if P1 SLA 95% of control and mean delay 20% lower, or if fairness (max util <90%) holds.  
  - Fail-safe: if reserve util >85% for two consecutive blocks, revert to Policy P (full pooling) for P1 temporarily; monitor operator feedback.  
- **Duration**: 1 week (enough to see morning surge pattern), <5% staff change, no disruption to Validation. Pilot logs stored for PM4Py analysis (handover rate, util heatmap). Results guide threshold tuning (e.g., reserve util cap from 80% to 75–85% based on observed util).

*This pilot tests the key tension (reserve vs pool) under realistic morning load, protects P1 SLA, uses observable metrics, and allows quick rollback. It does not rely on unobserved parameters (e.g., exact tail distribution) since it uses actual observed service times from pilot.*
