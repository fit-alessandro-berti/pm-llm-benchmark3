The shared mechanism is an AND-join mechanism: when both identity and document verification are required before Assessment, completing independent work in overlap can reduce the elapsed time to the join and therefore reduce waiting before Assessment. That mechanism is plausibly transportable for Site B cases where documents are digitally available and the two checks can genuinely start independently.

Several mechanisms are site-specific. Site A had mostly digital documents, cross-trained reviewers, simultaneous task ownership, added document capacity, an API upgrade, daily huddles, and a simpler post-period mix. Site B has statutory originals requirements, specialist pools, a case lock, a legal branch, supplement loops, and a thinner assessment/legal capacity buffer. These alter both treatment fidelity and the downstream response to earlier releases.

Important effect modifiers include originals-required status, digital availability, complexity, legal-review eligibility, role specialization, IT locking, pool utilization, and rework propensity. They affect either whether overlap can occur or whether earlier verification completion merely moves delay downstream.

Thus the apparent parallel pattern at A does not identify a single causal effect, and even a valid A effect would be conditional on a different operational regime.

## 6. Candidate Site B intervention

Implement a **receipt-aware, segment-specific parallel-verification workflow**, not Site A’s unconditional task creation.

**Eligibility rules**
- Initial treatment population: digitally complete claims with no statutory originals requirement, low-to-moderate complexity, and no immediate legal-review flag.
- Expansion population: originals-required cases only after testing the blocked-document design.
- Exclude cases with an active supplement loop from initial treatment; they remain on a controlled rework path.
- Public-sector/high-value cases may receive parallel verification only when legal queue utilization is below a predefined threshold.

**Concurrent tasks**
- After `Register`, create `Identity Check` and either:
  - `Document Check` concurrently for digitally complete, no-original cases; or
  - `Originals Receipt` concurrently with `Identity Check` for originals-required cases.
- For originals-required cases, create a visible but non-executable `Document Check` task only after receipt; it cannot be claimed, started, or completed before `Originals Receipt`.

**Mandatory prerequisites**
- `Document Check` requires `Originals Receipt` where legally required.
- `Assessment` requires completed Identity and Document checks.
- Legal review remains mandatory for statutorily designated cases.
- A `Request Supplement` reopens Document Check and then Assessment; prior completion does not satisfy the new iteration.

**Queue and WIP controls**
- Separate WIP caps by identity, document, assessment, and legal pools.
- Start with caps of 4 active identity, 7 active document, 3 Assessment-ready releases, and 2 active legal reviews, adjusted after observed utilization.
- Pause treatment intake when Assessment queue age or legal queue age exceeds pre-specified guardrails.

**Resource responsibilities**
- Identity, document, assessment, and legal roles retain ownership boundaries.
- A workflow coordinator resolves blocked receipt/document tasks and exception routing; no informal simultaneous ownership workarounds.

**Logging requirements**
- Log task creation, eligibility decision, statutory-originals flag, receipt timestamp, assignment, work start, completion, owner, lock status, rework reason, legal decision, supplement request, and event-entry timestamp.
- Distinguish true work intervals from retrospective data entry.

**POWL-style partial-order relation set**

```text
Register
  ->
  +(
    Identity Check,
    XOR(
      Document Check                                    [digital/no-original],
      Originals Receipt -> Document Check               [originals-required]
    )
  )
  ->
  Assessment
  ->
  XOR(
    Approve,
    Reject,
    Legal Review -> XOR(
      Approve,
      Reject,
      Request Supplement -> Document Check -> Assessment -> Legal Review
    )
  )
  ->
  Notify
```

The legal branch is data-dependent: only legally designated cases enter `Legal Review`; the supplement branch repeats the document/assessment path before the legal decision is finalized.

The pilot distinguishes mechanism failure from implementation failure by measuring the causal chain, not only final cycle time. A case assigned to treatment but showing no true concurrent work because of a lock, unavailable documents, or unclaimed tasks is an implementation-fidelity failure. A case with verified true overlap but no reduction in time-to-both-checks-complete, or with gains erased by Assessment or Legal queues, is mechanism limitation or bottleneck displacement.

Randomized concurrent controls address the confounding that affected Site A’s before/after comparison. Treatment versions separate immediate document parallelism from the legally feasible identity-plus-receipt design. Stratification identifies whether digital availability, originals, legal routing, complexity, and utilization modify effects. Queue-level exposure measures detect interference: a control case can be affected if treatment cases consume shared specialist capacity. Finally, immutable task timestamps and sampled operational audits distinguish genuine overlap from retrospective event entry.

## 8. PM4Py model-construction code

```python
# Self-contained illustrative PM4Py construction code.
#
# Version note:
# PM4Py's POWL API has evolved across releases. The imports and constructors below
# follow the current-style POWL object model used in recent PM4Py versions. If a
# local release uses a different operator/loop signature, inspect:
# pm4py.objects.powl.obj and adapt only the constructor names/signatures.
#
# This model encodes control-flow precedence only. It cannot encode data-dependent
# statutory routing, resource capacity, legacy case locks, task ownership, durations,
# external-originals delay distributions, API latency, or retrospective timestamp entry.

import pm4py

from pm4py.objects.powl.obj import (
    POWL,
    Transition,
    SilentTransition,
    StrictPartialOrder,
    OperatorPOWL,
    Operator,
)

# ---------------------------------------------------------------------
# 1. Site A before/after process trees
# ---------------------------------------------------------------------
site_a_before_tree = pm4py.parse_process_tree(
    "->( 'Register', 'Identity Check', 'Document Check', "
    "'Assessment', X( 'Approve', 'Reject' ), 'Notify' )"
)

site_a_after_tree = pm4py.parse_process_tree(
    "->( 'Register', +( 'Identity Check', 'Document Check' ), "
    "'Assessment', X( 'Approve', 'Reject' ), 'Notify' )"
)

# ---------------------------------------------------------------------
# 2. Convert both process trees to accepting Petri nets
# ---------------------------------------------------------------------
a_before_net, a_before_im, a_before_fm = pm4py.convert_to_petri_net(site_a_before_tree)
a_after_net, a_after_im, a_after_fm = pm4py.convert_to_petri_net(site_a_after_tree)

print("Site A before workflow net:",
      pm4py.check_is_workflow_net(a_before_net))
print("Site A after workflow net:",
      pm4py.check_is_workflow_net(a_after_net))

try:
    print("Site A before sound:", pm4py.check_soundness(a_before_net, a_before_im, a_before_fm))
    print("Site A after sound:", pm4py.check_soundness(a_after_net, a_after_im, a_after_fm))
except Exception as exc:
    print("Soundness API differs in this PM4Py version or check unavailable:", exc)

# ---------------------------------------------------------------------
# 3. Site B candidate POWL model
#
# Intended control-flow:
# Register
#   -> parallel(Identity Check, document-route)
#   -> Assessment
#   -> decision route
#   -> Notify
#
# document-route is an XOR abstraction:
# - digital/no-original case: Document Check
# - originals-required case: Originals Receipt -> Document Check
#
# This is an abstraction of a data-dependent route. A POWL net alone cannot enforce
# "62% require originals" without an external data guard/routing rule.
# ---------------------------------------------------------------------

register = Transition(label="Register")
identity = Transition(label="Identity Check")
originals = Transition(label="Originals Receipt")
document_digital = Transition(label="Document Check")
document_original = Transition(label="Document Check")
assessment = Transition(label="Assessment")
approve = Transition(label="Approve")
reject = Transition(label="Reject")
legal_review = Transition(label="Legal Review")
request_supplement = Transition(label="Request Supplement")
notify = Transition(label="Notify")

# Sequential originals-required document path:
# Originals Receipt -> Document Check
originals_then_document = StrictPartialOrder([originals, document_original])
originals_then_document.order.add_edge(originals, document_original)

# XOR between direct digital document verification and originals-gated verification.
# The precise Operator name may be XOR or EXCLUSIVE_CHOICE depending on version.
document_route = OperatorPOWL(
    Operator.XOR,
    [document_digital, originals_then_document]
)

# Verification partial order:
# Identity Check and document_route may execute concurrently.
# Assessment must wait for BOTH branches.  The explicit edges into Assessment
# represent the mandatory AND-join.
verification_join = StrictPartialOrder([identity, document_route, assessment])
verification_join.order.add_edge(identity, assessment)
verification_join.order.add_edge(document_route, assessment)

# Legal supplement loop:
# Legal Review either finishes with approve/reject, or requests supplement and loops
# through Document Check -> Assessment -> Legal Review.
#
# The supplement path is represented as a loop body. The exact loop constructor
# varies across PM4Py versions; Operator.LOOP conventionally uses [do, redo].
supplement_document = Transition(label="Document Check")
supplement_assessment = Transition(label="Assessment")
supplement_path = StrictPartialOrder(
    [request_supplement, supplement_document, supplement_assessment]
)
supplement_path.order.add_edge(request_supplement, supplement_document)
supplement_path.order.add_edge(supplement_document, supplement_assessment)

legal_then_decision = OperatorPOWL(
    Operator.XOR,
    [approve, reject, supplement_path]
)

# A loop with Legal Review as "do" and Request Supplement -> Document -> Assessment
# as "redo". In operational deployment, the loop is enabled only if legal issues
# a Request Supplement; this data condition is outside pure control flow.
legal_supplement_loop = OperatorPOWL(
    Operator.LOOP,
    [legal_review, supplement_path]
)

# After legal loop, a final legal decision occurs.
legal_route = StrictPartialOrder([legal_supplement_loop, legal_then_decision])
legal_route.order.add_edge(legal_supplement_loop, legal_then_decision)

# Non-legal decision route.
direct_decision = OperatorPOWL(
    Operator.XOR,
    [Transition(label="Approve"), Transition(label="Reject")]
)

# Optional legal-review branch represented as XOR:
# non-legal cases take direct decision; legally required cases take legal route.
decision_route = OperatorPOWL(
    Operator.XOR,
    [direct_decision, legal_route]
)

# Overall strict partial order. Register precedes verification; Assessment is already
# constrained to wait for identity + document route; decision follows assessment;
# Notify follows final decision.
site_b_powl = StrictPartialOrder(
    [register, verification_join, decision_route, notify]
)
site_b_powl.order.add_edge(register, verification_join)
site_b_powl.order.add_edge(verification_join, decision_route)
site_b_powl.order.add_edge(decision_route, notify)

# Some PM4Py releases wrap POWL roots in POWL(...), while others accept a POWL node
# directly. This conditional keeps the example readable.
try:
    site_b_model = POWL(site_b_powl)
except Exception:
    site_b_model = site_b_powl

# ---------------------------------------------------------------------
# 4. Convert Site B POWL to an accepting Petri net
# ---------------------------------------------------------------------
b_net, b_im, b_fm = pm4py.convert_to_petri_net(site_b_model)

print("Site B candidate workflow net:",
```

## 9. Recommendation

`conditional go`

Transfer the **mechanism**, not Site A’s literal workflow. Site B should test whether reducing elapsed time to the identity-and-document completion join improves cycle time for cases where both tasks are legally and technically capable of running concurrently. The first subgroup should be digitally complete, no-original-required, low-to-moderate complexity cases without an immediate legal-review requirement. These cases most closely resemble Site A’s favorable conditions: document availability at registration, fewer statutory dependencies, and less exposure to legal and supplement loops.

Do not copy the proposed “create both tasks immediately for every case” design. For the 62% requiring originals, Document Check must remain legally blocked until receipt. The transferable design is instead Identity Check plus Originals Receipt in parallel, followed by Document Check after receipt. Creating an executable document task before receipt would be both non-compliant and analytically misleading.

Expected benefit for the initial subgroup is a modest reduction in median cycle time, plausibly around four to seven hours if true simultaneous ownership is technically supported and Assessment has capacity. The all-case benefit will be smaller because originals delays, legal review, rework, and heavy-tail complexity remain. The major risk is bottleneck displacement: faster verification may increase Assessment and Legal queues, causing p90 performance to worsen even if median performance improves. A second risk is that the legacy case lock produces nominal parallelization but only retrospective timestamps and informal ownership workarounds.

Expand only if randomized or phased pilot evidence shows: high verified overlap fidelity; lower time-to-both-checks-complete; at least a practically meaningful median improvement; no material increase in p90, rework, supplement requests, audit defects, or appeals; and stable Assessment/Legal queue age. Modify the intervention if benefits are confined to digital claims or if assessment congestion appears; add admission control or capacity balancing rather than broadening blindly. Abandon the concurrent-execution version if the system cannot support genuine dual ownership, legal prerequisites are breached, rework rises materially, or the p90/legal tail deteriorates persistently.

## 10. Assumption register

1. **Identity and document checks are substantively independent for initially eligible digital cases — why needed:** parallel execution must not create avoidable rework or quality loss — **how to test:** audit sampled treated and control cases for cross-check dependencies and error rates — **consequence if false:** restrict eligibility or preserve sequential review for dependent case types.

2. **The case system can support auditable simultaneous task ownership for the pilot population — why needed:** true overlap, rather than timestamp back-entry, is the treatment — **how to test:** technical sandbox test plus production audit of ownership/start events — **consequence if false:** use a controlled handoff alternative or abandon concurrent execution.

3. **Originals Receipt can be reliably identified at Register — why needed:** statutory gating depends on correct routing — **how to test:** compare intake classification with later legal/document audit — **consequence if false:** high compliance risk and unreliable subgroup estimates.

4. **Assessment capacity has enough short-run headroom for earlier releases — why needed:** verification gains otherwise shift into the Assessment queue — **how to test:** measure utilization, queue age, and wait by treatment assignment — **consequence if false:** impose release throttles or add assessor capacity.

5. **Legal capacity can absorb treated legal-eligible cases without worsening tails — why needed:** two legal reviewers may be the dominant bottleneck — **how to test:** monitor legal queue age, p90 turnaround, and supplement frequency — **consequence if false:** exclude legal cases or cap their treatment share.

6. **Treatment and control cases can coexist without overwhelming interference — why needed:** shared specialist queues can contaminate case-level comparisons — **how to test:** model outcomes against team/day treatment saturation and utilization — **consequence if false:** randomize by team/week or reduce treatment share.

7. **Event timestamps can distinguish work start from later data entry — why needed:** overlap and waiting mechanisms require valid measurement — **how to test:** compare immutable system logs, audit trails, and observed work samples — **consequence if false:** do not use measured overlap as fidelity evidence.

8. **No major concurrent staffing, API, policy, or intake-mix change occurs differentially by arm — why needed:** causal interpretation requires comparable operating conditions — **how to test:** change log, staffing records, API telemetry, and covariate balance checks — **consequence if false:** suspend inference, adjust design, or restart with concurrent controls.
