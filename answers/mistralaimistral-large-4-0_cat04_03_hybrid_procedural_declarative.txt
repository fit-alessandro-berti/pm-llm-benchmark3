# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

1. **Clarification placement.** `Request Clarification` may occur before or after `Classify Risk`, but every request must be answered by a `Receive Clarification` before the next request and before any final outcome (`Reject Vendor`, `Activate Vendor`, or `Close Onboarding`). In the procedural model I place optional clarification loops both before and after `Classify Risk`; this is stricter than R3 for pre-classification requests, because it forces the answer to arrive before `Classify Risk`.
2. **Sanctions escalation placement.** R7 only requires `Sanctions Escalation` to occur after `Run Sanctions Screening`. For procedural modeling I place it after `Classify Risk`, because it is an escalation of the risk classification. This is a design choice, not a stated requirement.
3. **Legal opinion before terminal outcome.** R4 says `Obtain Legal Opinion` must eventually occur after `Sanctions Escalation`. In the procedural model I require it before the terminal outcome (`Reject Vendor` or `Activate Vendor`) when escalation occurs. This is stricter than R4 but simplifies the control-flow model.
4. **Post-activation changes.** `Change Bank Details` and `Suspend Vendor` are deliberately excluded from the procedural backbone. They are handled by DECLARE and the external resource/data-aware layer.
5. **Resource attribute.** The event log is assumed to have a `resource` column (or `org:resource`). If it is missing, segregation-of-duties checks fail closed.
6. **Temporal deviations.** R12 temporal expectations are treated as warnings, not automatic control-flow rejections.
7. **Emergency attributes.** The log does not contain `emergency_authorized` or `joint_authorizers`. Therefore R6 cannot be verified from the log alone.
8. **Frequency of `Verify Bank Account`.** Because R11 allows another `Verify Bank Account` after a post-activation bank change, I do not constrain `Verify Bank Account` to exactly one occurrence in the log skeleton.
9. **Exactly-once activities.** `Receive Onboarding Request`, `Capture Master Data`, `Run Sanctions Screening`, `Classify Risk`, and `Close Onboarding` are assumed to occur exactly once per case.
10. **Applicable approval for R9.** In a low-risk case the applicable approval is `Manager Approval`; in a high-risk case it is `Compliance Approval`. In a rejected case there is no applicable approval, so R9 is vacuous.

## R5/R6 conflict resolutions

The conflict is:

- **R5 (Legal):** after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` under all circumstances.
- **R6 (Operations):** emergency activation may occur before `Obtain Legal Opinion`, but only with joint authorization outside the log, and the opinion must arrive within 24 hours. The log has no emergency attribute.

### Resolution A — strict legal precedence (chosen)

R5 is authoritative. After `Sanctions Escalation`, any `Activate Vendor` before `Obtain Legal Opinion` is a violation. R6 is treated as a possible external exception that requires an explicit `emergency_authorized` attribute and joint-authorization evidence. Because the log lacks those attributes, the implemented model does not allow the exception.

**Compliance risk:** legitimate emergency activations such as T6 will be flagged as violations. This creates false positives and possible alert fatigue, but it is conservative and prevents unauthorized activations from passing silently.

### Resolution B — emergency-tolerant

R6 is authoritative when an external authorization attribute is present. The model allows `Activate Vendor` before `Obtain Legal Opinion` if `emergency_authorized=True` and joint authorization is present, and the opinion arrives within 24 hours.

**Compliance risk:** this relies on external data quality. If the attribute is missing, forged, or incomplete, violations may be missed. It also contradicts R5’s “under all circumstances” unless the policy is formally amended.

### Resolution C — dual-track

Model both constraints separately: strict R5 as a hard check, and R6 as a separate exception check that can override only when external evidence is present. This is what the external layer supports, but the implemented default is strict R5.

## Chosen resolution

I choose **Resolution A (strict R5)** for the implemented model. The log lacks the emergency attributes, and R5 is stated as an absolute legal requirement. The external layer can be extended to Resolution B/C if the organization enriches the log with `emergency_authorized` and `joint_authorizers`.

# 3. Procedural Backbone

## Compact formal description

```
Receive Onboarding Request
 (Capture Master Data  Run Sanctions Screening  Verify Bank Account)
 (Request Clarification  Receive Clarification)*        [optional, pre-classification]
 Classify Risk
 (Request Clarification  Receive Clarification)*        [optional, post-classification]
 [Sanctions Escalation 
      (Obtain Legal Opinion  Outcome
       | EDD  Obtain Legal Opinion  Compliance Approval  Activate Vendor  Release First Payment  Close Onboarding
       | EDD  Compliance Approval  Obtain Legal Opinion  Activate Vendor  Release First Payment  Close Onboarding
       | Manager Approval  Obtain Legal Opinion  Activate Vendor  Release First Payment  Close Onboarding
       | Obtain Legal Opinion  Reject Vendor  Close Onboarding)]
 Outcome

Outcome =
  Reject Vendor  Close Onboarding
  | Manager Approval  Activate Vendor  Release First Payment  Close Onboarding
  | Enhanced Due Diligence  Compliance Approval  Activate Vendor  Release First Payment  Close Onboarding
```

## PM4Py ProcessTree code

```python
from pm4py.objects.process_tree.process_tree import ProcessTree

def leaf(label):
    return ProcessTree(label=label)

def seq(*children):
    return ProcessTree(operator=ProcessTree.Operator.SEQUENCE, children=list(children))

def par(*children):
    return ProcessTree(operator=ProcessTree.Operator.PARALLEL, children=list(children))

def xor(*children):
    return ProcessTree(operator=ProcessTree.Operator.XOR, children=list(children))

def loop(do, redo):
    return ProcessTree(operator=ProcessTree.Operator.LOOP, children=[do, redo])

TAU = ProcessTree(label=None)  # silent transition

RECEIVE = "Receive Onboarding Request"
CAPTURE = "Capture Master Data"
RUN = "Run Sanctions Screening"
VERIFY = "Verify Bank Account"
CLASSIFY = "Classify Risk"
REQUEST = "Request Clarification"
RECEIVE_CLAR = "Receive Clarification"
SANCTIONS = "Sanctions Escalation"
LEGAL = "Obtain Legal Opinion"
EDD = "Enhanced Due Diligence"
MANAGER = "Manager Approval"
COMPLIANCE = "Compliance Approval"
REJECT = "Reject Vendor"
ACTIVATE = "Activate Vendor"
RELEASE = "Release First Payment"
CLOSE = "Close Onboarding"

def make_clar_loop():
    # zero or more Request -> Receive cycles
    return xor(
        TAU,
        loop(
            seq(leaf(REQUEST), leaf(RECEIVE_CLAR)),
            seq(leaf(REQUEST), leaf(RECEIVE_CLAR))
        )
    )

def make_outcome_choice():
    return xor(
        seq(leaf(REJECT), leaf(CLOSE)),
        seq(leaf(MANAGER), leaf(ACTIVATE), leaf(RELEASE), leaf(CLOSE)),
        seq(leaf(EDD), leaf(COMPLIANCE), leaf(ACTIVATE), leaf(RELEASE), leaf(CLOSE))
    )

def make_escalation():
    # Optional sanctions escalation branch.
    # Strict R5: if Sanctions Escalation occurs, Obtain Legal Opinion must precede Activate Vendor.
    return xor(
        TAU,
        seq(
            leaf(SANCTIONS),
            xor(
                seq(leaf(LEGAL), make_outcome_choice()),
                seq(leaf(EDD), leaf(LEGAL), leaf(COMPLIANCE), leaf(ACTIVATE), leaf(RELEASE), leaf(CLOSE)),
                seq(leaf(EDD), leaf(COMPLIANCE), leaf(LEGAL), leaf(ACTIVATE), leaf(RELEASE), leaf(CLOSE)),
                seq(leaf(MANAGER), leaf(LEGAL), leaf(ACTIVATE), leaf(RELEASE), leaf(CLOSE)),
                seq(leaf(LEGAL), leaf(REJECT), leaf(CLOSE))
            )
        )
    )

procedural_model = seq(
    leaf(RECEIVE),
    par(leaf(CAPTURE), leaf(RUN), leaf(VERIFY)),
    make_clar_loop(),
    leaf(CLASSIFY),
    make_clar_loop(),
    make_escalation()
)
```

## Explanation

- **Concurrency:** `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` run in parallel after `Receive Onboarding Request`.
- **Choices:** XOR is used for the optional clarification loops, the optional escalation branch, and the three terminal outcomes.
- **Clarification loops:** Two optional loops are included: one before `Classify Risk` and one after it. Each loop is `Request Clarification  Receive Clarification` and can repeat. This enforces R3 in the procedural model, but it is stricter than R3 for pre-classification requests because it forces the answer before `Classify Risk`.
- **Terminal outcomes:** Either `Reject Vendor  Close Onboarding`, or `Manager Approval  Activate Vendor  Release First Payment  Close Onboarding`, or `Enhanced Due Diligence  Compliance Approval  Activate Vendor  Release First Payment  Close Onboarding`.
- **Post-activation behavior:** `Change Bank Details` and `Suspend Vendor` are deliberately excluded from the procedural backbone. They are handled by DECLARE and the external layer.
- **Approximation disclosed:** The escalation branch is a conservative approximation. It forces `Obtain Legal Opinion` before `Activate Vendor` when `Sanctions Escalation` occurs (strict R5), and it places `Sanctions Escalation` after `Classify Risk`. It does not allow `Obtain Legal Opinion` after `Reject Vendor`, which is stricter than R4.

## Rule semantics

| Template | Rule(s) | Direction and semantics |
|---|---|---|
| `init` | `Receive Onboarding Request` | Every trace must start with `Receive Onboarding Request`. |
| `exactly_one` | `Receive Onboarding Request`, `Capture Master Data`, `Run Sanctions Screening`, `Classify Risk`, `Close Onboarding` | Each of these activities occurs exactly once per case. |
| `altresponse` | `(Request Clarification, Receive Clarification)` | Every `Request Clarification` is eventually followed by a `Receive Clarification` before the next `Request Clarification`; every `Receive Clarification` is preceded by a `Request Clarification`. This is stronger than `response` and captures R3’s alternation. |
| `response` | `(Sanctions Escalation, Obtain Legal Opinion)` | If `Sanctions Escalation` occurs, `Obtain Legal Opinion` must eventually occur after it. Captures R4. |
| `response` | `(Change Bank Details, Suspend Vendor)` | If `Change Bank Details` occurs, `Suspend Vendor` must eventually occur after it. Partial R11. |
| `precedence` | `(A, B)` for all listed pairs | If `B` occurs, `A` must have occurred before `B`. Used for backbone order. |
| `noncoexistence` | `(A, B)` for all listed pairs | `A` and `B` never occur in the same trace. Used for R1, R8, and partial R2. |

**Response vs precedence:** `response(A, B)` is activation-triggered: if `A` occurs, `B` must eventually occur. `precedence(A, B)` is target-triggered: if `B` occurs, `A` must have occurred before it.

**Alternate response vs chain response:** I use `altresponse` for clarification because R3 requires alternation: no two `Request Clarification` events without a `Receive Clarification` in between. I do not use `chainresponse` because it would require immediate succession, which is not required.

**Noncoexistence vs nonsuccession:** I use `noncoexistence` because R1, R8, and R2 require the activities never to co-occur in the same case. `nonsuccession` would only forbid one order, which is weaker.

## Orientation and overlap

- `always_before` pair `(A, B)` means **A always occurs before B**. I use this orientation for all precedence-like constraints.
- `always_after` is left empty to avoid redundant inverses.
- `never_together` pair `(A, B)` means **A and B never occur in the same trace**.
- `activ_freq` maps an activity to its allowed occurrence-count set.

**Overlap with other layers:**

- `always_before` overlaps with DECLARE `precedence` and procedural sequence edges. It is weaker than DECLARE `response` because it only constrains order when both activities occur; it does not require the second activity to occur.
- `never_together` overlaps with DECLARE `noncoexistence` and procedural XOR choices.
- `activ_freq` overlaps with R10 and procedural cardinality.
- The log skeleton cannot express conditional R5 or R2’s “exactly one in accepted” requirement. Those are handled by the procedural model and external layer.
- `always_before(("Sanctions Escalation", "Obtain Legal Opinion"))` is only a necessary condition for R4; it does not enforce that `Obtain Legal Opinion` occurs. DECLARE `response` is stronger.
- `always_before(("Request Clarification", "Receive Clarification"))` is only a necessary condition for R3; DECLARE `altresponse` is stronger.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800, 86400),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200, 21600),
    ("Activate Vendor", "Release First Payment"): (259200, 129600)
}

zeta = 2.0
```

Conversions:

- 48 hours = 172,800 seconds; 24 hours = 86,400 seconds.
- 12 hours = 43,200 seconds; 6 hours = 21,600 seconds.
- 72 hours = 259,200 seconds; 36 hours = 129,600 seconds.

**Why temporal deviations are warnings, not automatic control-flow violations:** R12 explicitly says these temporal expectations are “normative enough to flag but not automatically reject a case.” Therefore a deviation outside `[mean - zeta*sd, mean + zeta*sd]` (clipped at 0) is surfaced as a warning. It does not change the control-flow verdict.

# 7. Resource- and Data-Aware Checks

Required event attributes:

- `case_id` — case identifier.
- `activity` — activity label.
- `timestamp` — event timestamp.
- `resource` — person or role performing the activity.
- Optional for emergency exception: `emergency_authorized` (boolean), `joint_authorizers` (list).

Missing attribute handling:

- Missing `resource`  fail closed for segregation-of-duties checks.
- Missing `timestamp`  temporal checks are `not evaluated`.
- Missing `emergency_authorized`  treated as `False`; strict R5 applies.

## R9 — segregation of duties

```python
def check_r9_sod(df):
    violations = []
    for case_id, g in df.groupby("case_id"):
        # Verify Bank Account vs applicable approval
        verify_rows = g[g["activity"] == "Verify Bank Account"]
        if verify_rows["resource"].isna().any():
            violations.append((case_id, "R9: missing resource on Verify Bank Account"))
            continue
        verify_res = set(verify_rows["resource"].dropna())

        for approval in ["Manager Approval", "Compliance Approval"]:
            appr_rows = g[g["activity"] == approval]
            if len(appr_rows) == 0:
                continue
            if appr_rows["resource"].isna().any():
                violations.append((case_id, f"R9: missing resource on {approval}"))
                continue
            appr_res = set(appr_rows["resource"].dropna())
            if verify_res & appr_res:
                violations.append((case_id, f"R9: Verify Bank Account and {approval} share resource {verify_res & appr_res}"))

        # Capture Master Data vs Activate Vendor
        capture_rows = g[g["activity"] == "Capture Master Data"]
        activate_rows = g[g["activity"] == "Activate Vendor"]
        if len(capture_rows) and len(activate_rows):
            if capture_rows["resource"].isna().any() or activate_rows["resource"].isna().any():
                violations.append((case_id, "R9: missing resource on Capture Master Data or Activate Vendor"))
            else:
                cap_res = set(capture_rows["resource"].dropna())
                act_res = set(activate_rows["resource"].dropna())
                if cap_res & act_res:
                    violations.append((case_id, f"R9: Capture Master Data and Activate Vendor share resource {cap_res & act_res}"))

    return violations
```

`pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")` can be used to filter compliant cases, but the dataframe check above is used to detect violations.

## R5 strict — legal opinion before activation

```python
def check_r5_strict(df):
    violations = []
    for case_id, g in df.groupby("case_id"):
        g = g.sort_values("timestamp")
        if (g["activity"] == "Sanctions Escalation").any() and (g["activity"] == "Activate Vendor").any():
            first_activate = g.loc[g["activity"] == "Activate Vendor", "timestamp"].min()
            legal_before = g.loc[(g["activity"] == "Obtain Legal Opinion") & (g["timestamp"] < first_activate)]
            if legal_before.empty:
                violations.append((case_id, "R5 strict: Activate Vendor before Obtain Legal Opinion after Sanctions Escalation"))
    return violations
```

## R5/R6 emergency-tolerant variant

```python
def check_r5_r6_emergency(df):
    violations = []
    for case_id, g in df.groupby("case_id"):
        g = g.sort_values("timestamp")
        if (g["activity"] == "Sanctions Escalation").any() and (g["activity"] == "Activate Vendor").any():
            first_activate = g.loc[g["activity"] == "Activate Vendor", "timestamp"].min()
            legal_before = g.loc[(g["activity"] == "Obtain Legal Opinion") & (g["timestamp"] < first_activate)]
            if not legal_before.empty:
                continue

            act_row = g.loc[g["activity"] == "Activate Vendor"].iloc[0]
            emergency = act_row.get("emergency_authorized", False)
            joint_auth = act_row.get("joint_authorizers", None)

            if emergency and joint_auth and len(joint_auth) >= 2:
                legal_after = g.loc[(g["activity"] == "Obtain Legal Opinion") & (g["timestamp"] > first_activate)]
                if not legal_after.empty and (legal_after["timestamp"].min() - first_activate).total_seconds() <= 86400:
                    continue
                else:
                    violations.append((case_id, "R6: emergency activation without legal opinion within 24h"))
            else:
                violations.append((case_id, "R5/R6: Activate before Obtain without verifiable emergency authorization"))

    return violations
```

## R11 — post-activation bank change

```python
def check_r11(df):
    violations = []
    for case_id, g in df.groupby("case_id"):
        g = g.sort_values("timestamp")
        if not (g["activity"] == "Activate Vendor").any():
            continue

        activate_time = g.loc[g["activity"] == "Activate Vendor", "timestamp"].min()
        changes = g.loc[(g["activity"] == "Change Bank Details") & (g["timestamp"] > activate_time)]

        for _, change in changes.iterrows():
            suspends = g.loc[(g["activity"] == "Suspend Vendor") & (g["timestamp"] > change["timestamp"])]
            if suspends.empty:
                violations.append((case_id, "R11: Change Bank Details after activation without subsequent Suspend Vendor"))

            later_releases = g.loc[(g["activity"] == "Release First Payment") & (g["timestamp"] > change["timestamp"])]
            if not later_releases.empty:
                first_later_release = later_releases["timestamp"].min()
                verify_after_change = g.loc[
                    (g["activity"] == "Verify Bank Account") &
                    (g["timestamp"] > change["timestamp"]) &
                    (g["timestamp"] < first_later_release)
                ]
                if verify_after_change.empty:
                    violations.append((case_id, "R11: Release First Payment after Change Bank Details without another Verify Bank Account"))

    return violations
```

def check_r2(df):

    for case_id, g in df.groupby("case_id"):
        manager_count = (g["activity"] == "Manager Approval").sum()
        compliance_count = (g["activity"] == "Compliance Approval").sum()
        reject_count = (g["activity"] == "Reject Vendor").sum()
        activate_count = (g["activity"] == "Activate Vendor").sum()

        if reject_count > 0:
            if manager_count > 0 or compliance_count > 0:

        elif activate_count > 0:

    return violations

## R3 — clarification response

```python
def check_r3(df):
    violations = []
    final_outcomes = {"Reject Vendor", "Activate Vendor", "Close Onboarding"}

    for case_id, g in df.groupby("case_id"):
        g = g.sort_values("timestamp")
        requests = g[g["activity"] == "Request Clarification"].index.tolist()
        receives = g[g["activity"] == "Receive Clarification"].index.tolist()
        finals = g[g["activity"].isin(final_outcomes)].index.tolist()

        for req_idx in requests:
            next_req = min([r for r in requests if r > req_idx], default=None)
            valid_receive = [
                r for r in receives
                if r > req_idx
                and (next_req is None or r < next_req)
                and (not finals or r < finals[0])
            ]
            if not valid_receive:
                violations.append((case_id, "R3: Request Clarification without Receive Clarification before next request or final outcome"))

    return violations
```

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement across layers

R1, R8, R10, and the backbone precedence constraints are enforced in the procedural model, DECLARE, and the log skeleton. This is intentional defense-in-depth, but it can produce conflicting verdicts if the layers are not aligned. The authoritative layer must be explicit: the procedural model is authoritative for control-flow structure; DECLARE is authoritative for activity-only response/precedence/noncoexistence; the external layer is authoritative for resource, data, and conditional temporal obligations.
