## 1. Duplicate-handling decision tree

For each candidate pair or group, first compare source keys, payloads, business timestamps, object identities, and source semantics. Do not use equal activity and timestamp as a duplicate key by themselves.

1. If the same source event key is repeated and the business timestamp, activity, payload, and object references are identical, classify it as an exact technical duplicate. Keep the first canonical event, drop the repeated row and duplicate relations, and retain the dropped event ID in provenance.
2. If different systems report the same physical event, and reconciliation or a stable business identifier confirms that identity, classify it as a cross-system observation. Merge attributes and the union of relations into one canonical event. Keep every source ID and record conflicts rather than silently choosing one.
3. If one event is a detailed transaction and the other is a derived summary/status update, do not merge merely because one follows the other. The default terminal decision is retain both with refined labels or qualifiers, such as Pack Package [detail] and Pack Package [ERP summary]. A separately governed business-level view may merge them only when the organization defines them as one transition and accepts the loss of abstraction level.
4. If harmonization has mapped different source activities to one common label, classify this as a harmonization collision. Retain both with refined labels or source-semantic qualifiers, for example Released from Warehouse and Accepted by Carrier.
5. If same-label events at the same time concern different objects or business instances, classify them as concurrent same-label events. Retain both unchanged; an object-instance qualifier may be added for trace construction, but no event is deleted.
6. If evidence does not decide between these cases, quarantine the candidate for review. It remains in the analytical raw view and is excluded only from a separately named merged view.

The resulting order of preference is therefore: drop only exact technical duplicates; merge only verified physical observations; retain abstraction and semantic distinctions; quarantine uncertainty.

## 3. Timestamp-tie ordering rules

Construct a directed acyclic graph before assigning any artificial timestamp. Add edges from explicit domain constraints first: create before validate; picks before packing; warehouse release before carrier acceptance; carrier acceptance before handover; invoice issuance before authorization; authorization before capture; and payment messages before the ERP balance summary. Add e12 -> e13 and e13 -> e14 from PSP source_seq; that sequence is comparable only within PSP. Use shared-object lifecycle constraints only when the event semantics support them, not as proof of identity.

Within a source, source_seq can break otherwise unresolved ties. Across sources it is not comparable. Source-specific semantics, such as a carrier acceptance preceding carrier handover, are semantic edges. Ingestion time is technical metadata: it is useful for audit and detecting late arrival, but is not a business-order edge. A stable fallback such as source rank, source event key, and original eid is merely deterministic. It must never be described as recovered physical order.

Perform a stable topological sort. At each step choose an available event by (business timestamp, source rank, source_seq where applicable, source_event_key, eid). If a semantic edge conflicts with that fallback, the semantic edge wins. Store the resulting ordinal as an explicit order column. Only after this order is established may an analysis copy receive index-based microsecond offsets. Keep the original timestamp unchanged. Adding microseconds first would make an arbitrary ingestion or row order look like a factual causal sequence and can create artificial durations and directly-follows edges.

For the 10:00 group, e03/e04 are one event in the conservative view; e03 and e05 are concurrent distinct picks, and both precede e06 by the pick-before-pack constraint. e07 is actually timestamped 10:01, not 10:00, and follows the detailed pack transition in a WMS-to-ERP summary interpretation. A valid totalization is e03, e05, e06, e07, with the order between e03 and e05 explicitly marked as fallback-only. In the evidence-based merge, e06/e07 become one qualified pack transition.

For 10:15, the intended lifecycle order is e08 (Released from Warehouse) -> e09 (Accepted by Carrier) -> e10 (Handover to Carrier). The first edge is semantic warehouse/carrier lifecycle reasoning; the second is explicitly known. If the first edge is not guaranteed by a particular source contract, leave it as a partial order and use the stable fallback only for reproducible serialization.

After merging e11/e16, the 12:00 order is e11 (Invoice Issued) -> e12 (Authorize M1) -> e13 (Capture M1) -> e14 (Capture M2) -> e15 (ERP balance summary). The first and last relationships use domain/source-message semantics, while e12-to-e14 use PSP sequence plus the stated authorization rule. The e13/e14 order is deterministic evidence from one PSP, not proof that the two payments were causally dependent.

## 4. Conservative cleaning pipeline

The minimum-change pipeline copies the OCEL, snapshots original_timestamp, original_activity, source, and source_event_key, and creates a candidate report before changing anything. It merges only e03/e04 and e11/e16. It retains e05 and e14, keeps e06/e07 as separate abstraction-level observations, and splits the dispatch collision into refined labels. It also keeps e15 as an invoice-level summary without manufacturing a Payment relation.

For each verified merge, retain the chosen canonical eid and union relations after removing duplicate event-object pairs. Attribute precedence is field-specific: source authority is declared for each field; a non-null value may fill a null value, but conflicting non-null values are both retained in the audit record. The raw label, source, source key, payload hash, and business timestamp remain available even when the analytical activity is refined.

The semantic graph is then topologically sorted and written to an order column. PM4Py's index-based timedelta helper can be applied only to a derived performance view after that step. The synthetic value is never used to overwrite the original business time in the audit view and should not be interpreted as causal evidence.

There are 17 raw events. Two verified pairs reduce this to 15 retained canonical events. The e03/e04 and e11/e16 relation sets are already identical, so 44 raw E2O rows reduce to 39 after relation deduplication.

## 5. Aggressive alternatives

The evidence-based semantic-merge scenario starts from raw, merges e03/e04 and e11/e16 as above, and additionally treats e06/e07 as one business transition because the ERP row is explicitly generated from the WMS message. It preserves a detail/summary lineage field, but the analytical event is one qualified Pack Package. It retains e08/e09, e09/e10, e03/e05, e13/e14, and e13/e15 separately. Expected count: 14 events and 37 E2O rows. The likely damage is loss of the distinction between operational packing work and an ERP status observation, which can distort latency and conformance analyses.

The mechanically aggressive PM4Py scenario calls pm4py.ocel_merge_duplicates with have_common_object=True after grouping by harmonized activity and timestamp. On this data, the expected mechanical groups are e03/e04/e05, e08/e09, e11/e16, and e13/e14, giving 12 events and approximately 32 E2O rows after relation union. The exact result should be measured against the installed PM4Py version because candidate-key details can vary. This scenario is for sensitivity analysis, not the canonical audit dataset.

have_common_object=True is not a semantic safeguard. e13 and e14 share O1 and V1, but their payment objects are M1 and M2. A common order or invoice merely says the events belong to the same case; it does not say they are observations of one event. The same problem occurs for e03/e05 through shared O1 and P1, and for e08/e09 through shared O1/P1/D1.

## 6. PM4Py-oriented Python implementation

~~~python
from copy import deepcopy
import json
import heapq
import pandas as pd
import pm4py

# PM4Py's standard names are used below. If the input uses bare names such as
# "eid", map them once to the standard names before calling this block.
EID, ACT, TS = "ocel:eid", "ocel:activity", "ocel:timestamp"
OID = "ocel:oid"


def ensure_metadata(ocel):
    """Snapshot raw values before any scenario-specific operation."""
    ev = ocel.events.copy()
    ev["original_timestamp"] = ev[TS]
    ev["original_activity"] = ev[ACT]
    # Keep source and source_event_key themselves; do not repurpose them.
    for c in ("source", "source_event_key"):
        if c not in ev.columns:
            raise KeyError(c)
    ev["business_timestamp"] = ev[TS]
    ocel.events = ev
    return ocel


def candidate_groups(ocel):
    ev = ocel.events
    # This is only a review index, never an automatic merge key.
    out = {}
    for key, g in ev.groupby([ACT, TS], dropna=False, sort=True):
        ids = list(g[EID])
        if len(ids) > 1:
            out[key] = ids
    return out


def exact_technical_groups(ocel):
    cols = [ACT, TS, "source", "source_event_key", "payload_hash"]
    ev = ocel.events
    groups = []
    for _, g in ev.groupby(cols, dropna=False, sort=True):
        if len(g) > 1:
            groups.append(list(g[EID]))
    return groups


def _missing(x):
    return x is None or (not isinstance(x, (list, dict, tuple))
                         and bool(pd.isna(x)))


def merge_verified_pair(ocel, keep_id, drop_id, rule, confidence="high"):
    """Merge one reviewed pair, preserving source and conflict evidence."""
    ev = ocel.events.copy()
    ki = ev.index[ev[EID].eq(keep_id)].tolist()
    di = ev.index[ev[EID].eq(drop_id)].tolist()
    if len(ki) != 1 or len(di) != 1:
        raise ValueError((keep_id, drop_id))
    ki, di = ki[0], di[0]
    conflicts, retained = {}, {}

    for col in ev.columns:
        if col == EID:
            continue
        a, b = ev.at[ki, col], ev.at[di, col]
        if _missing(a) and not _missing(b):
            ev.at[ki, col] = b
            retained[col] = "from " + str(drop_id)
        elif not _missing(a) and not _missing(b) and str(a) != str(b):
            conflicts[col] = {str(keep_id): a, str(drop_id): b}
            retained[col] = "canonical " + str(keep_id)

    members = [keep_id, drop_id]
    ev.at[ki, "source_event_ids"] = json.dumps(members)
    ev.at[ki, "merged_sources"] = json.dumps(
        sorted({str(ev.at[ki, "source"]), str(ev.at[di, "source"])}))
    ev.at[ki, "merged_source_event_keys"] = json.dumps(
        [str(ev.at[ki, "source_event_key"]),
         str(ev.at[di, "source_event_key"])])
    ev = ev.drop(index=di).reset_index(drop=True)
    ocel.events = ev

    rel = ocel.relations.copy()
    rel.loc[rel[EID].eq(drop_id), EID] = keep_id
    relation_key = [EID, OID]
    if "ocel:type" in rel.columns:
        relation_key.append("ocel:type")
    rel = rel.drop_duplicates(subset=relation_key, keep="first").reset_index(drop=True)
    ocel.relations = rel

    audit_row = {
        "canonical_eid": keep_id,
        "source_event_ids": json.dumps(members),
        "merge_rule": rule,
        "rule_version": "duplicate-tie-cleaning-v1",
        "reviewer": "rule-based",
        "original_activity": "stored on source rows before merge",
        "original_timestamps": "stored on source rows before merge",
        "attributes_retained": json.dumps(retained, default=str),
        "discarded_conflicts": json.dumps(conflicts, default=str),
        "confidence": confidence,
        "reason": rule,
    }
    prior = list(getattr(ocel, "audit_trail", []))
    prior.append(audit_row)
    ocel.audit_trail = prior
    return ocel


def validate_referential_integrity(ocel):
    event_ids = set(ocel.events[EID])
    object_ids = set(ocel.objects[OID])
    rel = ocel.relations
    assert set(rel[EID]).issubset(event_ids)
    assert set(rel[OID]).issubset(object_ids)
    keys = [EID, OID] + (["ocel:type"] if "ocel:type" in rel.columns else [])
    assert not rel.duplicated(keys).any()


def order_and_make_analysis_view(ocel, semantic_edges):
    ev = ocel.events.copy()
    ids = list(ev[EID])
    present = set(ids)
    edges = [(a, b) for a, b in semantic_edges
             if a in present and b in present and a != b]
    out = {i: set() for i in ids}
    indegree = {i: 0 for i in ids}
    for a, b in edges:
        if b not in out[a]:
            out[a].add(b)
            indegree[b] += 1

    source_rank = {"ERP": 0, "WMS": 1, "SCANNER": 2,
                   "CARRIER": 3, "BILLING": 4, "PSP": 5}
    rows = ev.set_index(EID)

    def tie(i):
        r = rows.loc[i]
        seq = r.get("source_seq")
        seq = int(seq) if not pd.isna(seq) else 10**18
        return (pd.Timestamp(r[TS]), source_rank.get(str(r.get("source", "")), 99),
                seq, str(r.get("source_event_key", "")), str(i))

    ready = [(tie(i), i) for i in ids if indegree[i] == 0]
    heapq.heapify(ready)
    ordered = []
    while ready:
        _, i = heapq.heappop(ready)
        ordered.append(i)
        for j in sorted(out[i], key=tie):
            indegree[j] -= 1
            if indegree[j] == 0:
                heapq.heappush(ready, (tie(j), j))
    if len(ordered) != len(ids):
        raise ValueError("semantic ordering graph contains a cycle")

    rank = {i: n for n, i in enumerate(ordered)}
    ev["__total_order"] = ev[EID].map(rank).astype("int64")
    ocel.events = ev
    ocel = pm4py.ocel_sort_by_additional_column(ocel, "__total_order")
    # This call is deliberately after the graph/topological order exists.
    ocel.events["business_timestamp"] = ocel.events[TS]
    ocel = pm4py.ocel_add_index_based_timedelta(ocel)
    ocel.events["adjusted_timestamp"] = ocel.events[TS]
    return ocel


raw = ensure_metadata(deepcopy(ocel_raw))
review_index = candidate_groups(raw)
exact_groups = exact_technical_groups(raw)
validate_referential_integrity(raw)

# Conservative branch: use the library only for reviewed exact technical
# duplicates. The supplied candidates have no such group, so this is a no-op
# here. In a release exposing subset/keep parameters, pass the exact signature;
# never apply a broad default to all equal-time events.
conservative = deepcopy(raw)
if exact_groups:
    conservative = pm4py.ocel_drop_duplicates(
        conservative,
        parameters={"subset": [ACT, TS, "source", "source_event_key", "payload_hash"],
                    "keep": "first"})
conservative = merge_verified_pair(conservative, "e03", "e04",
                                   "reconciled physical scan")
conservative = merge_verified_pair(conservative, "e11", "e16",
                                   "same invoice V1 issuance")
validate_referential_integrity(conservative)

semantic_edges = [
    ("e01", "e02"), ("e02", "e03"), ("e02", "e05"),
    ("e03", "e06"), ("e05", "e06"), ("e06", "e07"),
    ("e08", "e09"), ("e09", "e10"),
    ("e11", "e12"), ("e12", "e13"), ("e13", "e14"),
    ("e14", "e15"),
]
conservative = order_and_make_analysis_view(conservative, semantic_edges)
validate_referential_integrity(conservative)

# Evidence-based scenario: independent copy and an explicit, reviewable
# detail/summary merge. This is not applied to the conservative dataset.
evidence_based = ensure_metadata(deepcopy(ocel_raw))
evidence_based = merge_verified_pair(evidence_based, "e03", "e04",
                                     "reconciled physical scan")
evidence_based = merge_verified_pair(evidence_based, "e11", "e16",
                                     "same invoice V1 issuance")
evidence_based = merge_verified_pair(evidence_based, "e06", "e07",
                                     "approved detail-to-summary business view",
                                     confidence="medium")
validate_referential_integrity(evidence_based)
evidence_based = order_and_make_analysis_view(evidence_based, semantic_edges)

# Mechanical sensitivity scenario. This function may merge semantically
# distinct events; inspect its candidate key and output before using it.
aggressive_library = pm4py.ocel_merge_duplicates(
    ensure_metadata(deepcopy(ocel_raw)),
    parameters={"have_common_object": True})
required = {"original_timestamp", "original_activity", "source", "source_event_key"}
assert required.issubset(set(aggressive_library.events.columns))
validate_referential_integrity(aggressive_library)
aggressive_library = order_and_make_analysis_view(aggressive_library, semantic_edges)
validate_referential_integrity(aggressive_library)

The aggressive view collapses the three pick rows e03/e04/e05, so it loses the distinct I2 pick and undercounts Pick Item -> Pack Package; it also erases the warehouse-release-to-acceptance edge and invoice duplicate.

The concrete Pick(I1) -> Pack(I1) and Pick(I2) -> Pack(I2) frequencies therefore change differently from the raw view.

In the Payment-flattened DFG, Authorize(M1) -> Capture(M1) remains in the conservative and evidence-based views, and the distinct Capture(M2) remains visible. OC-DFG edge frequencies and performance metrics are sensitive to both deduplication and tie serialization. Removing e03/e04 lowers the apparent frequency of the pick observation without changing the I1 business event. Merging e11/e16 lowers invoice frequency. Merging e06/e07 removes a one-minute detail-to-summary interval. Collapsing e08/e09 removes a same-time dispatch-to-dispatch edge. Conversely, retaining both same-time events but serializing them can create edges such as Capture(M1) -> Capture(M2) that are deterministic rather than observed causal transitions.

ET-OT weights decrease when duplicate event observations are merged, while aggressive unioning can make one event touch both M1 and M2 and thus change the apparent Capture-Payment-type weight. OTG weights can acquire a false M1-M2 relation only in the aggressive view. All four datasets should therefore be reported with the order policy and timestamp status attached.

## 8. Audit trail and reversibility

Each canonical event should have an audit record with canonical_eid, a list of source_event_ids, source keys, source systems, merge rule, rule version, reviewer or automated reviewer identity, confidence, and reason. Store original and refined activities, original business timestamp, adjusted analysis timestamp, and the deterministic order ordinal. For every attribute, record its source event, authority class, retained value, and any discarded conflict. Store relation-level provenance too: original event-object rows, unioned canonical rows, and the rule that removed a duplicate relation.

A merge record should be append-only and immutable. The event table can retain source_event_ids as a compact convenience, while a normalized alias table maps every source eid to its canonical eid. A separate conflict table stores both non-null values, so discarded means not selected as canonical, not destroyed.

To reconstruct raw, expand each canonical event through the alias table, restore the source row's original activity, timestamp, source key, and attributes, and replay the original relation snapshot. The conservative pipeline should thus be reversible exactly for e03/e04 and e11/e16. A refined-label view is reversible by using the original activity fields. Synthetic timestamps are never needed for reconstruction.

## 9. Failure modes and safeguards

1. Collapsing e13 and e14 because they share activity, time, O1, and V1 loses two partial payments. Require payment-object identity and source evidence.
2. Dropping e05 because it looks like e03/e04 loses the I2 pick. Compare item objects before any same-label merge.
3. Converting e07 into a second pack transaction creates false rework. Preserve detail-versus-summary lineage or isolate the semantic merge in a separate dataset.
4. Ordering by ingestion time mistakes transport latency for business sequence. Treat ingested_at as audit metadata only.
5. Treating shared objects as proof of duplication merges events from the same order, package, invoice, or delivery that are expected to be distinct.
6. Unioning incompatible E2O relations can make a canonical event touch objects that never participated in one physical event. Union only after verified identity and audit every added relation.
7. Adding synthetic microseconds before resolving semantics changes durations and creates false directly-follows edges. Apply index-based offsets only to a named analysis copy after ordering.
8. Losing source-authoritative attributes during a merge damages billing, WMS, ERP, or PSP semantics. Use field-level authority and retain both conflicting values.
9. Applying a duplicate function to the whole OCEL without inspecting candidate groups can merge e03/e05, e08/e09, or e13/e14. Precompute candidate groups and review each terminal decision.
10. Assuming cross-source sequence numbers are comparable imposes an invented global order. Use source_seq only within its source and a documented fallback elsewhere.
11. Replacing the original timestamp with the adjusted timestamp prevents later performance audits and makes the synthetic order look factual. Store both permanently.
12. Ignoring late-arriving or replayed messages can create duplicate aliases or orphaned relations. Enforce unique canonical IDs, validate all E2O references, and quarantine unresolved replay candidates.
