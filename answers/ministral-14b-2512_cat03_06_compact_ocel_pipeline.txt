# OCEL 2.0 Retail Order Processing Analysis

## 1. Modeling Assumptions

**Object Types and Capitalization:**
- `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment` (PascalCase for consistency with PM4Py conventions)

**E2O Qualifier Vocabulary:**
- `creates` (Order creation)
- `adds` (Item addition to Order)
- `reserves` (Stock reservation)
- `packs` (Item packaging)
- `dispatches` (Package dispatch)
- `issues` (Invoice creation)
- `records` (Payment recording)
- `confirms` (Delivery confirmation)
- `closes` (Order closure)

**O2O Direction Conventions:**
- Always `oid`  `oid_2` (source  target)
- Qualifiers indicate directionality (e.g., `contains` means Order  Item)

**Relation Scope:**
- Logistics events (packing, dispatching) relate directly to both Orders and Items when operationally shared
- Financial events relate directly to Invoices and indirectly to Orders via O2O relations
- Payment events contain amount information in event attributes

**Preventing Analytical Propagation Confusion:**
- Use distinct qualifiers for source vs. analytical relations
- Maintain direct E2O relations for all operationally significant connections
- Avoid creating O2O relations that would be obvious from E2O relations

**PM4Py Version Assumption:**
- Using PM4Py 2.2.x with OCEL support
- Constructor assumes `pm4py.objects.ocel.OCEL` class

- **e12/e15 (Record Payment)**: Create relations to M1/M2 and V1, with amounts

## 4. Expected Flattened Behavior

**Order Flattening:**
- **Trace Shape**: ~10 events per order (O100: 8, O200: 7)
- **Shared Events**: Reserve Stock (e6), Pack Package (e7), Issue Invoice (e11)
- **Omitted**: Package/Item-specific events not directly tied to Order
- **DFG Edges**: CreateAddReservePackDispatchIssueClose
- **Misleading**: May show parallel packing/dispatching that's actually shared

**Package Flattening:**
- **Trace Shape**: ~4 events per package (P1: 4, P2: 3)
- **Shared Events**: Pack Package (e7/e8), Dispatch Package (e9/e10)
- **Omitted**: Order-specific events, Item details
- **DFG Edges**: PackDispatchConfirm
- **Misleading**: May obscure that P1 serves two Orders

**Delivery Flattening:**
- **Trace Shape**: ~2 events per delivery (D1: 2, D2: 2)
- **Shared Events**: Dispatch Package (e9/e10), Confirm Delivery (e13/e14)
- **Omitted**: Package/Item/Order context
- **DFG Edges**: DispatchConfirm
- **Misleading**: No visibility of which Orders are served

**Invoice Flattening:**
- **Trace Shape**: ~4 events (Issue, 2 Payments, 1 Order closure)
- **Shared Events**: Issue Invoice (e11), Record Payment (e12/e15)
- **Omitted**: Order-specific events before invoicing
- **DFG Edges**: IssuePaymentPaymentClose
- **Misleading**: Shows payments as sequential when they're parallel

**Payment Flattening Would Be Weak Because:**
- Payments are invoice-centric, not order-centric
- Amount information would be lost in flattened traces
- No visibility of which Orders are being settled
- Would show only partial process without context

## 5. Expected Object-Centric Structures

**OC-DFG:**
- Shows parallel Order creation paths converging at Invoice creation
- Reserve Stock and Pack Package events appear as shared activities
- Payment events branch from Invoice
- Delivery confirmation happens after dispatch but before order closure

**OTG:**
- Order lifecycle: CreateAddReservePackDispatchIssueClose
- Package lifecycle: PackDispatchConfirm
- Invoice lifecycle: IssuePaymentPaymentClose
- Delivery lifecycle: DispatchConfirm
- Shows that Packaging can involve multiple Orders

**ET-OT Graph:**
- Reserve Stock connects to both Orders and Items
- Pack Package connects to Packages, Items, and Orders
- Issue Invoice connects to Invoice, Orders, and Payments
- Will show that P1 is involved in both O100 and O200 processes

**Object-Centric Petri Net:**
- Multiple places for Order states (created, item-added, reserved, etc.)
- Shared transitions for Reserve Stock and Pack Package
- Invoice place with multiple incoming arcs from Orders
- Payment transitions that can occur in any order
- Will model the parallel nature of O100 and O200 processing

**Object-Interactions Summary:**
- O100 and O200 interact through shared Reserve Stock and Pack Package events
- V1 interacts with both O100 and O200 via billing relations
- P1 interacts with both O100 and O200 via packing relations
- M1 and M2 both interact with V1 via payment relations
- Will show that P1 is the only Package involved in cross-Order interactions

## 6. Modeling Alternatives

**1. Source-Minimal Relations:**
- Only create E2O relations for events that directly create objects
- Remove relations for events that modify existing objects (e.g., Add Item)
- *Impact*: Would lose visibility into item addition timing relative to orders
- *Discovery*: Would show orders appearing fully formed without item addition events

**2. Full Operational Involvement:**
- Create E2O relations for every operational involvement
- Include relations for events that affect but don't directly create objects
- *Impact*: More relations but clearer operational picture
- *Discovery*: Would show complete operational involvement but risk relation inflation

**3. O2O-Propagated Analytical Relations:**
- Derive some relations from O2O structure rather than direct E2O
- Example: Infer that P1 is related to O200 from O200P2D2P1 chain
- *Impact*: More complete analytical view but risk of false positives
- *Discovery*: Would show more connections but some may be analytical artifacts

## 7. Failure Modes

1. **Relation Inflation**: Creating too many relations makes discovery noisy
   - *Symptom*: OC-DFG becomes overly complex with many spurious connections
   - *Fix*: Use qualifier vocabulary carefully to distinguish operational vs. analytical relations

2. **Missing Direct E2O Links**: Omitting critical relations breaks process understanding
   - *Symptom*: Flattened logs show incomplete order lifecycles
   - *Fix*: Ensure all operationally significant events have E2O relations

3. **Treating O2O Propagation as Observation**: Confusing analytical with source relations
   - *Symptom*: OC-DFG shows connections that don't exist in source data
   - *Fix*: Clearly distinguish source E2O from analytical O2O relations

4. **Duplicate Shared Events After Flattening**: Same event appears multiple times
   - *Symptom*: Flattened logs show parallel paths where there should be shared events
   - *Fix*: Use proper OCEL flattening that handles shared events correctly

5. **Ambiguous Payment Allocation**: Payments not clearly linked to specific orders
   - *Symptom*: OC-DFG shows payments without clear order context
   - *Fix*: Maintain clear O2O relations between payments and invoices, and invoices to orders

6. **Overly Short Payment Traces**: Payments appear as isolated events
   - *Symptom*: Flattened payment logs show only Record Payment without context
   - *Fix*: Include invoice creation and order billing in payment traces

7. **Constructor/API Version Mismatch**: Using wrong OCEL constructor
   - *Symptom*: Import errors or data structure validation failures
   - *Fix*: Verify PM4Py version and OCEL class signature

8. **False Total Order for Same-Time Events**: Assuming strict ordering where none exists
   - *Symptom*: OC-DFG shows spurious dependencies between concurrent events
   - *Fix*: Use proper timestamp handling and accept that some events are concurrent
