# 3. Consequences for performance analysis

G1 – Treating a 4-piece parallel batch as four serial jobs would  
• inflate resource utilisation (robot appears 4× busy)  
• understate service time per item if divided by 4, or overstate if kept whole  
• waiting time unaffected because queue_arrival is upstream and genuine.  
Throughput analysis correct if fixture size known.

G2 – Equal start creates exaggerated waiting-time reduction and understates service time for the later-finished items. Resource utilisation is inflated during the common setup minute and understated afterwards.

G3 – Common completion sets all service times to long values for early-started items and almost zero for the last. Waiting time is inflated for items finished early but only logged later. Bottleneck detection will falsely blame the review step for long processing.

G4 – Regular cadence with no overlaps is benign; however, analysts might infer a four-minute activity time whereas true time could vary. No strong bias.

G5 – Shared account pools hide concurrency. Utilisation is underestimated (three analysts look like one). Waiting and service times are blurred; conformance wrong-fully flags parallelism violations.

G6 – Flat 17:00 start and end give zero service and extreme queue waits. Process-mining tools could mis-diagnose an impossible instantaneous service and mark all earlier time as waiting, overstating back-log and understating capacity.

G7 – Quarter-hour rounding compresses variability. Waiting-time bias depends on unknown rounding rule (floor for start, ceiling for end gives long service). Utilisation smoothed, throughput appears stair-stepped.

G8 – Post-downtime burst shortens measured waiting (because downtime not modelled) and may indicate a false bottleneck earlier. Resource appears under-utilised before 15:38 then overloaded.

# 5. Robustness and alternative explanations

1. If resource IDs are *trusted*, G5 must be concurrent multitasking by one analyst; utilisation is low but acceptable.  
   If resource IDs are *unreliable*, the same timestamps are harmless overlap of different people; utilisation is underestimated and concurrency higher.

2. If timestamps are treated as *exact*, G7 shows a true 15-minute simultaneous batch.  
   If they are *interval-censored* to ±7.5 min, the equality disappears and the event order becomes ambiguous.

3. G2’s equal start supports both “operator pressed begin group” and “tablet clock rounds to minute”. A higher-resolution clock or keystroke log would distinguish.

# 6. Data-collection redesign

Priority 1 – Capture separate badge/resource identity even behind shared accounts (badge swipe, SSO).  
Priority 2 – Store system clock, time-zone and precision per source; synchronise clocks (NTP).  
Priority 3 – Log both `setup_start` and per-item `work_start`/`work_complete` where fixtures allow.  
Priority 4 – Add explicit batch/group ID and fixture capacity to each event.  
Priority 5 – Record pause/resume/downtime markers and reason codes to explain queue bursts.  
Priority 6 – Preserve raw millisecond timestamps; apply rounding only in the BI layer.

# 7. Final adjudication

• High-confidence physical interpretation: G1, G3, G6, G7  
• Exclude or interval-censor in queue analysis: G6 (service=0), G7 (rounded), G3 completes, G2 starts  
• Require shop-floor validation before performance conclusions: G2 (is inspection serial?), G5 (who did what?), G8 (true downtime length).

Hence only G1, G4 can safely feed into automated bottleneck or simulation studies without further cleansing.
