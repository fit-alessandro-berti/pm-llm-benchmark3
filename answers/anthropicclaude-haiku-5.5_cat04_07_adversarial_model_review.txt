# 1. Review Scope and Assumptions

**Use cases.** The two submissions were built for different purposes, and the metrics do not separate those purposes. I distinguish five uses:

1. **Exploration.** Analysts look for variants, bottlenecks, and deviations. False alarms are cheap and missed behavior is tolerable if the model is labeled as incomplete. Model S is defensible here, provided it is labeled as permissive.
2. **Conformance enforcement.** A system or reviewer blocks or escalates traces that violate policy. False acceptance of a forbidden trace is the costliest error. Fitness on unseen but policy-valid behavior matters less than zero acceptance of forbidden behavior. Neither model is acceptable for this use.
3. **Simulation.** Play-out should produce realistic, policy-valid cases. Over-permissive models produce impossible cases (for example, a dossier approved without checks). Under-permissive models omit valid cases. Both distort simulation.
4. **Stakeholder communication.** The model must be read correctly by process owners, compliance staff, and operations. A simple diagram that hides a mandatory check is worse than a longer diagram that states it.
5. **Maintenance and impact analysis.** IT and operations need to see where a change lands. Duplicate labels and branch explosion hurt this use directly.

**How use changes the trade-off.** For exploration, a high-fitness and low-precision model is acceptable if its permissiveness is disclosed (F7). For enforcement, the acceptable trade-off is nearly opposite: precision against a curated negative suite and zero acceptance of mandatory-skip traces matter more than fitness on the holdout. Unseen but valid behavior should go to a review queue, not be silently accepted or rejected (this addresses the tension between F7 and F8). For communication, the requirement is that readers answer policy questions correctly, which is not measured by the informal 1–5 score.

**Assumptions.**

- A1. Metric values are as reported. I have not re-run them and do not treat them as ground truth.
- A2. The external/internal attribute and the affected-check attribute are unavailable (stated by the team). Any rule depending on them is unverifiable, not satisfied or violated.
- A3. Probe traces B1–B8 are illustrative policy test cases. Eight probes do not characterize the full policy.
- A4. The string notation parses `+` as concurrency, `X` as exclusive choice, `->` as sequence, `*` as loop, and unquoted `tau` as a silent transition. I verified the semantics by reasoning from the expressions. Before relying on the results, confirm them with `pm4py.play_out` on each tree (see Section 9).
- A5. I could not determine whether the reported fitness is log-level (cost-weighted) or average trace fitness. This matters for interpretation (Section 2).
- A6. Alignment cost settings are unknown. Where I discuss costs, I assume unit costs, which is the PM4Py default but not confirmed.

# 3. Adversarial Review of Model S

**Strongest case for S.** S is compact and easy to explain. It has the highest training and holdout fitness and the highest token-based generalization. It has no duplicate labels. For exploration of incomplete logs (F4 notes missing Supplier Review events), its tolerance is useful: it avoids flagging every trace with a missing event as a deviation. On the probe set, S accepts all four probes that are policy-valid without qualification (B1, B2, B5, B7). It also correctly rejects B8, the repeated credit check without correction. Its errors are concentrated in the forbidden category (B3, B4).

**Strongest case against S.** S accepts two of the three forbidden probes (B3 and B4). It accepts a dossier with no mandatory check at all, and one in which expedite review happens before any check. That is exactly the failure described in F1. Its high fitness is produced by the same permissiveness, so the headline metric rewards the defect. The model also cannot represent Correct Dossier at all, so B6 and every legitimate correction trace are rejected for a reason unrelated to policy.

**Concrete admitted behaviors.** Each trace below is accepted by S, as I read the expression. Each is checked against P1–P7.

- **S-a:** `Register Dossier, Manager Approval, Release Order`. No credit or technical check at all. Violates P2. This is probe B3.
- **S-b:** `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order`. Expedite Review precedes the mandatory checks. Violates P4. This is probe B4.
- **S-c:** `Register Dossier, Expedite Review, Auto Approval, Release Order`. Expedite Review and approval with neither mandatory check. Violates P2 and P4. Under the parallel block, this is accepted because both mandatory options are silent.
- **S-d:** `Register Dossier, Technical Review, Manager Approval, Release Order`. Credit Check is skipped while the order is still released. Violates P2 and is the most direct compliance failure (F1).
- **S-e:** `Register Dossier, Supplier Review, Auto Approval, Release Order`. Supplier Review without any mandatory check. Violates P2. Because external status is unknown, the model cannot tell whether this is an external order that should have been reviewed, so P3 is also unenforceable here.
- **S-f:** `Register Dossier, Credit Check, Technical Review, Expedite Review, Supplier Review, Auto Approval, Release Order`. Acceptable under P4. Shows that the model's permissiveness is not uniformly wrong; the problem is specific to the mandatory-check and ordering constraints.

**Intentional noise tolerance vs. accidental semantic flaws.**

Intentional or defensible:

- Free order of Credit Check and Technical Review. P2 says either order is acceptable. S's interleaving is correct.
- Optional Supplier Review. Defensible while the external attribute is missing, but only if the model explicitly records that Supplier Review is conditional rather than optional. S does not record this, so the tolerance is implicit.
- Tolerance of missing events in the log. This is a stance, and it is acceptable in exploration. In compliance it is wrong, because a log without a credit-check event is indistinguishable from a skipped check.

Accidental or unjustified:

- Credit Check and Technical Review are optional. This contradicts P2 and is most likely a modeling mistake (the designer used optional choice where a mandatory block was needed).
- Expedite Review is inside the same parallel block as the checks. This allows expedite review before the checks, violating P4.
- Correction and repetition are absent. This is a structural omission, not tolerance. P6 and P7 cannot be represented.
- Approval and expedite interact without restriction (S-c), which P4 does not permit.

The governance problem is that "robust to missing events" is the same mechanism as "skip any mandatory check." The discovery team presents one as a benefit and the other as a defect, but they are the same property of the model.

# 4. Adversarial Review of Model C

**Strongest case for C.** C gets several things right. Every branch contains both Credit Check and Technical Review, so C never accepts a dossier without the mandatory checks (P2 holds across the whole expression). Repetition appears only after Correct Dossier, which satisfies P7 directly. Manager and Auto Approval each appear once per branch (P5). On the probe set, C correctly rejects B3, B4, and B8, and accepts B1 and B7. Each branch is a human-readable path that a process owner can verify. Because C mirrors observed variants, its training precision is high and its paths correspond to behavior the organization actually has. If the board values auditability at the path level, C is the more transparent artifact.

**Strongest case against C.** C is a list of observed or assumed variants, not a model of policy. It rejects two policy-valid probes: B2 (Technical Review before Credit Check, ending in Auto Approval) and B5 (external and urgent case with Auto Approval). It also rejects a correction on an external order, and any correction beyond one. The correction branch forces both checks to repeat (F6), so it encodes a decision the process owner has not made. Its holdout fitness shows it cannot generalize to valid combinations, and the rejection of unseen behavior is a false-positive generator for an enforcement system.

**Branch enumeration.** C has eight branches. Each new optional activity roughly doubles the branch count, and each order variant doubles it again. Supplier Review and Expedite Review together with two approval options and two check orders already produce combinations that are absent. Enumeration makes the model precise about the training log and blind to combinations it has not seen. The number of branches needed to represent the policy grows much faster than the policy itself.

**Duplicate labels.** Register Dossier, Credit Check, Technical Review, Manager Approval, and Release Order each appear in multiple branches. Credit Check appears in nine places and Technical Review in nine, including twice in branch 7. Duplicates make impact analysis hard: a change to "Credit Check" must be traced through every branch, and the model does not tell reviewers which occurrence is which.

**Unseen combinations.** C does not include: Expedite Review before Supplier Review; Expedite Review with Auto Approval; Supplier Review with Auto Approval; Technical Review before Credit Check with Expedite Review; any correction with Supplier Review; two corrections. Several of these are policy-valid (B2, B5, and the examples below). F4 identifies these combinations as present in holdout data.

**Correction handling.** C accepts one correction, always followed by Credit Check then Technical Review, and then Manager Approval. It cannot represent: a correction that affects only one check (B6); two corrections; a correction on an external order; a correction followed by Auto Approval. Each of these is either rejected or forced into a repeat of both checks, which is an assumption the policy does not make.

**Holdout degradation.** The drop from 0.973 training fitness to 0.744 holdout fitness shows the model is tied to observed variants. The holdout cases combine Supplier Review, Auto Approval, and alternate check order (F4). Those combinations are the ones C does not enumerate. This is evidence about coverage, not about whether those combinations are compliant.

**Maintainability.** A new policy-valid variant requires a new branch and a re-run of the enumeration. There is no way to express "either check may repeat after correction" except by listing the options. Operations (F2) reports exactly this difficulty.

**Is high precision a memorization artifact?** Largely yes. A model that is the list of training variants has precision close to 1.0 on the training log by construction. The reported 0.941 is not evidence that C generalizes or that its behavior is policy-valid; it is evidence that C copies the log. The 2.7% training fitness gap and the 0.941 precision together suggest some training behavior (possibly including valid combinations) is absent from C. That is the more informative reading, and it should be checked against the training log directly.

**Maintainability of "audit-ready."** The discovery team's claim, "closely mirrors frequent variants," means C encodes frequency, not permission. Frequent behavior is not necessarily policy-compliant, and infrequent but valid behavior is excluded. C is therefore audit-ready only for the variants it contains, and it cannot tell an auditor whether the excluded behavior is allowed.

# 6. Likely Metric Pathologies

Ranked by likely impact on governance decisions, highest first.

**1. Fitness rewarded by optionalizing mandatory behavior (S).** This is the most serious pathology in the submission, because it is the headline metric. A model that makes Credit Check optional gains fitness for every trace that lacks it. The discovery team reads 0.992 as quality. In fact, the number is partly produced by the very permissiveness that F1 rejects. Mitigation: fitness must be computed against a policy-weighted cost, in which missing mandatory events cost much more than missing optional ones, and against a negative suite (Section 9).

**2. Missing-event bias.** A missing event in the log is treated as a skipped activity when the model has a silent alternative (for S) or as a log move when it does not (for C). Missing Supplier Review events (F4) therefore make external orders look internal, and missing Credit Check events make compliant traces look like skipped checks. Missing-event bias affects which variants C learns, because a missing Supplier Review event creates a spurious internal variant. It also rewards S. Mitigation: missing-event perturbation tests and a data-quality audit of the event attributes.

**3. Generalization rewarded by permissiveness.** Token-based generalization is high for S because S shares transitions across many traces. A permissive model reuses its transitions heavily and therefore scores well. Mitigation: report generalization only alongside negative-suite acceptance; do not use TBR as evidence of policy-valid generalization.

**4. Positive-log-only precision.** C's precision is high because C is a variant list, and S's precision is low because S is permissive. Neither number tells us about policy-valid unseen behavior or about forbidden behavior that the log never contained. The auditor's objection (F5) is correct. Mitigation: a curated negative suite and holdout precision on labeled cases.

**5. Train/holdout leakage and split sensitivity.** Both teams claim the same 80/20 split and PM4Py installation, but they have not published seeds, preprocessing, or held-out cases. Holdout fitness for C is therefore not reproducible, and the training fitness gap for C (0.973) may reflect a different split. Holdout precision is not reported for either model. If C's variant list was selected after viewing the holdout, the holdout is contaminated. Mitigation: publish the split, seeds, and the case identifiers, and rerun both models on the same cases.

**6. Alignment-cost sensitivity.** Under unit costs, a missing mandatory activity costs the same as a missing optional one. Fitness is therefore length-weighted and insensitive to policy. A dossier missing Credit Check and Technical Review with 10 other events loses only about 0.2 of fitness, which hides a compliance failure. Also, since S's optional branches have zero cost, skipping is free. Mitigation: policy-weighted cost functions (Section 9).

**7. Silent-transition effects.** S uses four silent options. These change the simplicity score, the net's token flow (and hence TBR), and the alignment search. A different encoding of the same optionality would change these numbers without changing the language. Mitigation: report the language size and the number of silent transitions along with the metrics.

**8. Duplicate-label effects.** C's duplicates make the reported precision and the duplicate count harder to interpret, and they blur which transition corresponds to which event. Alignments may choose between identical labels, which affects costs and the diagnostics. The reported count of 33 cannot be reproduced. Mitigation: define the count, report the net-level duplicates, and document the mapping.

**9. Stakeholder-score methodology.** The comprehension score is informal and has no protocol. It may reward simplicity of appearance over understanding. A diagram that hides optional checks will score highly with readers who do not check which activities are required. Mitigation: a keyed comprehension test (Section 9).

**10. Runtime confounding by model size.** Alignment runtime is dominated by the fit of the trace to the model, not by model size. S's trace fit is near-perfect, so its runtime is low; C's holdout misfit is high, so its runtime is high. The 25-fold difference therefore says more about fit than about size. Mitigation: report runtime per fit class and under a fixed harness.

# 7. Third Alternative

**Design choice.** I use a block-structured procedural backbone with explicit recheck-scope handling and a declarative layer for rules that a process tree cannot express or that depend on missing attributes. This follows the second option in the prompt.

The principles are:

- Mandatory activities are structural, not optional. Credit Check and Technical Review each occur at least once, in any order, before any other review activity.
- Repetition is structural and only after Correct Dossier (P7).
- Expedite Review is structurally placed after both mandatory checks and before approval, and in any order relative to Supplier Review (P4).
- Supplier Review is conditional on external status, which is unknown. It is therefore optional in the tree and flagged, rather than silently optional (see the explicit semantics below).
- Correction scope is unknown. The tree admits any non-empty subset of checks after each correction, and the flag makes the admission visible rather than silent.
- Exactly one approval is structural (P5).

Duplicate labels are limited to Credit Check and Technical Review, each occurring twice (once initially, once on recheck). This is the minimum needed for a procedural tree to repeat a check after correction without using a loop over the full review. The duplicates are documented in the code and counted in the validation program.

## 7.1 Compact formal description

Activities: RD (Register Dossier), CC (Credit Check), TR (Technical Review), CD (Correct Dossier), SR (Supplier Review), ER (Expedite Review), MA (Manager Approval), AA (Auto Approval), RO (Release Order). Let `X?` denote optional (silent alternative).

```
M3 = RD · (CC  TR) · ( CD · (CC?  TR?) )* · (SR?  ER?) · (MA  AA) · RO
```

The language L(M3) consists of traces of the form

```
RD · p · (CD · r_1)(CD · r_2)...(CD · r_k) · s · a · RO
```

where:

- p is CC and TR in either order (both exactly once);
- k  0 corrections;
- each r_i is a subset of {CC, TR}, including the empty subset in the tree (see the post-hoc rule);
- s is a subset of {SR, ER} in either order or concurrently, with ER appearing after p and every r_i;
- a is exactly one of MA or AA.

## 7.2 Explicit semantics

**Mandatory checks.** `+(CC, TR)` requires both to occur exactly once in the initial round. They may occur in either order or concurrently (P2). No trace in L(M3) lacks either check, so B3 and A5 (below) are rejected structurally. This is the central difference from S.

**Optional Supplier Review.** SR is optional in the tree because the external/internal attribute is absent. This is not a silent treatment of SR as optional for every order. Rule R6 is a conditional-existence rule that becomes enforced when the attribute is available. Until then, traces without SR are accepted with the flag `R6 external attribute missing`. The flag is emitted in the audit trail, so the decision is visible and reviewable. If the attribute is later unavailable for an order that would need SR, the flag is raised, not suppressed.

**Expedite Review ordering.** ER appears only in the final block, which begins after the initial checks and after any corrections. This enforces P4: ER after both mandatory checks, before approval, and in either order relative to SR. An ER before CC or TR is structurally impossible (B4 is rejected). The declarative rule R2 repeats this check as an assertion, which costs nothing and documents the intent.

**Exactly-one approval.** `X(MA, AA)` occurs once, and no loop encloses it (P5). Neither approval type is restricted by the model; restricting Auto Approval to certain order types would be a separate policy decision (noted as a gap in Section 10).

**Correction and recheck behavior.** Correct Dossier may occur zero or more times (P6). Each correction is followed by a recheck block `(CC?  TR?)`. The tree admits any subset, including the empty set. Three cases follow.

- Empty recheck (CD followed directly by the next block or approval). The tree accepts this, but the post-hoc rule R5 rejects it as "correction without recheck." The tree alone is therefore too permissive here, and the post-hoc layer is required.
- Non-empty recheck with unknown scope. Accepted, with rule R7 emitting "recheck scope unverified." This is the honest state until the affected-check attribute exists (F6).
- Recheck of a check that occurred earlier. Repetition of CC or TR is possible only after a CD, which implements P7 structurally (rule R4 verifies this).

Corrections occurring after SR or ER are not representable in M3, because the correction loop sits before the final block. Such traces are rejected by the tree. This is a deliberate conservative choice and a known gap. The process owner must decide whether corrections after SR or ER are allowed (Section 10).

**Limitations caused by missing attributes.**

- Without the external attribute, P3 (SR required for external orders) cannot be enforced. M3 accepts external orders without SR and internal orders with SR. Both are flagged in the audit trail but not rejected.
- Without the affected-check attribute, P6's scope rule cannot be enforced. M3 accepts any non-empty recheck subset, so B6 is accepted with a scope flag. This is not a silent acceptance; it is a documented weaker guarantee.
- Corrections after SR or ER are a structural gap.
- The model cannot tell whether an approval type is appropriate for the order type, because no such attribute exists.

## 7.3 PM4Py code: `model_third`

```python
import pm4py
from pm4py.objects.log.obj import EventLog, Trace, Event

# ---------------------------------------------------------------------------
# 1. Procedural backbone (block-structured process tree)
#    - CC and TR: mandatory, either order, exactly once in the initial round
#    - Correct Dossier: repeatable; each correction is followed by a recheck
#      block that may contain CC and/or TR (scope unknown -> any subset,
#      non-empty enforced post hoc)
#    - SR and ER: optional, placed after the initial checks and after any
#      corrections; either order or concurrent
#    - Exactly one of Manager Approval / Auto Approval
#    Duplicate labels: 'Credit Check' and 'Technical Review' occur twice each
#    (initial round and recheck round). No other duplicates.
# ---------------------------------------------------------------------------
MODEL_THIRD_TREE = """
->(
  'Register Dossier',
  +('Credit Check', 'Technical Review'),
  *(
    tau,
    ->(
      'Correct Dossier',
      +(X('Credit Check', tau), X('Technical Review', tau))
    )
  ),
  X(tau, +(X('Supplier Review', tau), X('Expedite Review', tau))),
  X('Manager Approval', 'Auto Approval'),
  'Release Order'
)
"""

model_third = pm4py.parse_process_tree(MODEL_THIRD_TREE)
net_third, im_third, fm_third = pm4py.convert_to_petri_net(model_third)
# Confirm soundness; in recent PM4Py versions this returns a boolean
# (verify with the installed version).
is_sound_third = pm4py.check_soundness(net_third, im_third, fm_third)

# ---------------------------------------------------------------------------
# 2. Declarative layer. The tree enforces most rules structurally; the
#    entries below document which layer enforces each rule and what is
#    unverifiable.
# ---------------------------------------------------------------------------
MANDATORY = ("Credit Check", "Technical Review")
APPROVALS = ("Manager Approval", "Auto Approval")
REVIEW_BOUNDARY = {"Correct Dossier", "Supplier Review", "Expedite Review",
                   "Manager Approval", "Auto Approval", "Release Order"}

DECLARE_THIRD = {
    "R1_mandatory_existence": {
        "kind": "existence", "activities": MANDATORY,
        "layer": "tree (structural); re-checked post hoc"},
    "R2_expedite_after_checks": {
        "kind": "precedence",
        "pairs": [(a, "Expedite Review") for a in MANDATORY],
        "layer": "tree (structural); re-checked post hoc"},
    "R3_exactly_one_approval": {
        "kind": "exactly-one", "activities": APPROVALS,
        "layer": "tree (structural)"},
    "R4_repeat_requires_correction": {
        "kind": "repeat-guard", "activities": MANDATORY,
        "trigger": "Correct Dossier", "layer": "tree; re-checked post hoc"},
    "R5_recheck_nonempty": {
        "kind": "response-window", "trigger": "Correct Dossier",
        "requires_one_of": MANDATORY,
        "layer": "post hoc only (tree permits empty recheck)"},
    "R6_supplier_if_external": {
        "kind": "conditional-existence", "activity": "Supplier Review",
        "condition": "external == True",
        "layer": "post hoc; attribute missing -> flagged, not enforced"},
    "R7_recheck_scope": {
        "kind": "unverifiable",
        "layer": "none; emitted as flag (affected-check attribute missing)"},
}


def check_trace(trace, external=None):
    """Post-hoc policy checks. trace: list of activity labels.
    external: True / False / None (None = attribute missing).
    Returns (violations, flags)."""
    violations, flags = [], []

    # R1
    for a in MANDATORY:
        if a not in trace:
            violations.append(f"R1 missing mandatory {a}")

    # R2
    if "Expedite Review" in trace:
        i = trace.index("Expedite Review")
        for a in MANDATORY:
            if a not in trace[:i]:
                violations.append(f"R2 Expedite Review before {a}")

    # R3
    n_app = sum(1 for a in trace if a in APPROVALS)
    if n_app != 1:
        violations.append(f"R3 approvals={n_app}, expected 1")

    # R4: each repeated mandatory check needs a Correct Dossier between
    for a in MANDATORY:
        idxs = [i for i, x in enumerate(trace) if x == a]
        for prev, cur in zip(idxs, idxs[1:]):
            if "Correct Dossier" not in trace[prev + 1:cur]:
                violations.append(f"R4 repeated {a} without correction")

    # R5 and R7: each correction needs a non-empty recheck window
    for i, x in enumerate(trace):
        if x == "Correct Dossier":
            window = []
            for y in trace[i + 1:]:
                if y in REVIEW_BOUNDARY:
                    break
                if y in MANDATORY:
                    window.append(y)
            if not window:
                violations.append(f"R5 correction at position {i} has no recheck")
            else:
                flags.append(
                    f"R7 recheck scope unverified at position {i}: {sorted(set(window))}")

    # R6
    if external is True and "Supplier Review" not in trace:
        violations.append("R6 external order without Supplier Review")
    if external is None:
        flags.append("R6 external attribute missing: Supplier Review presence not enforced")

    return violations, flags


def tree_accepts(trace_labels, net=net_third, im=im_third, fm=fm_third):
    """Structural acceptance by alignment: zero-cost fit against the net."""
    log = make_log([trace_labels])
    diag = pm4py.conformance_diagnostics_alignments(log, net, im, fm)
    # 'fitness' key assumed; verify against the installed PM4Py version
    return diag[0].get("fitness", 0.0) >= 1.0 - 1e-9


def make_log(traces):
    log = EventLog()
    for t in traces:
        tr = Trace()
        for a in t:
            tr.append(Event({"concept:name": a}))
        log.append(tr)
    return log


def decide(trace_labels, external=None):
    """Full decision: tree acceptance AND post-hoc policy layer."""
    if not tree_accepts(trace_labels):
        return "reject", ["tree: not in language (structural)"], []
    violations, flags = check_trace(trace_labels, external=external)
    if violations:
        return "reject", violations, flags
    if flags:
        return "accept_with_flags", [], flags
    return "accept", [], []
```

## 9.1 Reproducible case splits and published preprocessing

- Publish the raw log hash, the preprocessing script, the PM4Py version, and the Python environment.
- Split by case identifier, not by event. Stratify by variant frequency bucket and by the presence of Correct Dossier, Supplier Review, and Expedite Review. Stratification by external status is impossible until the attribute is available.
- Fix seeds (for example, 0, 1, 2, 3, 4) and report results across seeds with variance.
- Publish the exact case identifiers for each split.
- Use one split for model construction and a separate, sealed split for evaluation. Do not reuse the holdout for variant selection.

```python
import random
import pm4py

def case_ids_by_variant(log):
    variants = {}
    for trace in log:
        key = tuple(e["concept:name"] for e in trace)
        variants.setdefault(key, []).append(trace.attributes["concept:name"])
    return variants

def stratified_case_split(log, seed, test_frac=0.2):
    rng = random.Random(seed)
    variants = case_ids_by_variant(log)
    train_ids, test_ids = [], []
    for variant, cases in sorted(variants.items()):
        rng.shuffle(cases)
        k = max(1, round(len(cases) * test_frac)) if len(cases) > 1 else 0
        test_ids += cases[:k]
        train_ids += cases[k:]
    return set(train_ids), set(test_ids)

# Verify in the installed PM4Py version and in the source log.
```

## 9.4 Missing-event and duplicate-event perturbation tests

Generate perturbed copies of the holdout and positive suite:

- drop one event (from non-first, non-last positions);
- duplicate one event in place;
- swap adjacent events;
- drop only Supplier Review events (simulating F4's missing SR data).

Measure how often a perturbed valid trace is rejected (sensitivity) and how often a perturbed forbidden trace is accepted (robustness). A good model rejects a trace with a dropped mandatory event unless the trace can be explained as a logging error that is itself flagged.

```python
import random

def perturb(trace, kind, rng):
    t = list(trace)
    if kind == "drop" and len(t) > 2:
        del t[rng.randrange(1, len(t) - 1)]
    elif kind == "dup":
        i = rng.randrange(len(t))
        t.insert(i, t[i])
    elif kind == "swap" and len(t) > 3:
        i = rng.randrange(1, len(t) - 2)
        t[i], t[i + 1] = t[i + 1], t[i]
    return t

def perturbation_suite(traces, kinds=("drop", "dup", "swap"), n=10, seed=0):
    rng = random.Random(seed)
    out = []
    for t in traces:
        for kind in kinds:
            for _ in range(n):
                out.append((kind, perturb(t, kind, rng)))
    return out
```

Compute, for each model and each split:

```python
def evaluate_model(tree, train_log, test_log, neg_log=None):
    net, im, fm = pm4py.convert_to_petri_net(tree)
    out = {}
    out["fitness_train"] = pm4py.fitness_alignments(train_log, net, im, fm)
    out["fitness_test"] = pm4py.fitness_alignments(test_log, net, im, fm)
    out["precision_test"] = pm4py.precision_alignments(test_log, net, im, fm)
    out["generalization_train"] = pm4py.generalization_tbr(train_log, net, im, fm)
    out["simplicity"] = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")
    if neg_log is not None:

        diag = pm4py.conformance_diagnostics_alignments(neg_log, net, im, fm)
        out["negative_acceptance"] = sum(
            1 for d in diag if d.get("fitness", 0) >= 1.0 - 1e-9) / max(1, len(diag))
    return out
```

Do not average these values. Report each separately with the per-stratum breakdown. The negative-suite acceptance rate is the primary enforcement metric and should not be traded against fitness.

## 9.9 Stakeholder comprehension: documented protocol

- Participants: process owner, compliance analyst, operations lead, and data analyst (at least three each, counterbalanced).
- Materials: each model shown in the same format (the diagram and the tree string, or the third model's tree with its declarative rules).
- Task: 20 yes/no questions keyed to policy. Examples: "Can a dossier be released without a credit check?" "Can Expedite Review occur before Technical Review?" "Can a correction be followed by no recheck?"
- Measures: accuracy against the key, time to answer, confidence rating, and the proportion of questions the participant could not answer.
- Analysis: accuracy per model, with confidence intervals, and error type (false belief that a forbidden behavior is allowed, or vice versa).
- Pre-register the key before data collection.

## 9.10 Decision rule: when a model is rejected despite good aggregate metrics

Reject a candidate model if any of the following holds, regardless of its fitness or precision:

1. Any trace in negative class N1 (mandatory check absent) or N2 (expedite before checks) is accepted.
2. Acceptance of a deletion-mutated valid trace, where the deleted event is a mandatory check, exceeds the threshold agreed by the governance board (proposed: zero acceptance).
3. False rejection on the labeled positive suite exceeds the threshold agreed by the board (proposed: 5%).
4. Results vary across seeds by more than a pre-registered tolerance.
5. The model fails soundness.
6. Stakeholder comprehension accuracy falls below the pre-registered threshold for process owners and compliance staff.

Good aggregate fitness and precision do not override any of these conditions.
