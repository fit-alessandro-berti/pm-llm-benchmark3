# 1. Delay-decomposition definitions

For case \(c\) and branch \(i \in \{\text{A, B, C}\}\):

- **Upstream elapsed**  
  `upstream_elapsed(c) = fork_release(c)  arrival(c)`  
  Time from case entry until all branches are allowed to start. Includes the upstream preparation step and any prior queuing.

- **Branch queue waiting**  
  `Q_i(c) = start_i(c)  fork_release(c)`   (nonnegative by construction)  
  Time branch \(i\) waits for a resource after being released by the fork.

- **Branch active service**  
  `S_i(c) = end_i(c)  start_i(c)`

- **Synchronisation waiting after completion**  
  `join_ready(c) = max_i( end_i(c) )`  
  `sync_i(c) = join_ready(c)  end_i(c)`  
  Time branch \(i\) spends idle after finishing, waiting for the slowest branch.  
  The lastcompleting branch has `sync_i(c) = 0`.

- **Forkjoin stage time**  
  `stage(c) = join_ready(c)  fork_release(c)`  
  For **any** branch \(i\): `stage(c) = Q_i(c) + S_i(c) + sync_i(c)`.  

- **Downstream queue**  
  `DQ(c) = final_start(c)  join_ready(c)`  
  Waiting for an available resource at the final station (F1 or F2).

- **Final service**  
  `FS(c) = final_end(c)  final_start(c)`

- **Total case flow time**  
  `total(c) = final_end(c)  arrival(c)`  
  `total(c) = upstream_elapsed(c) + stage(c) + DQ(c) + FS(c)`

**Why summing all branch synchronisation waits would double count elapsed time**  
`_i sync_i(c) = 3·join_ready(c)  _i end_i(c)`.  
This sum contains the same gap `join_ready(c)  end_i(c)` for each noncritical branch, thereby counting the same waiting period multiple times. In the totalflow decomposition we use only the **stage** time, which appears once. Perbranch sync waits are meaningful for quantifying idle resource capacity, but they must not be added when building the overall case timeline.

- **Cases with zero direct benefit** are those where B was not critical (F01, F04, F08, F11). In these, B’s reduced duration still does not surpass the actual critical branch, so `join_ready` stays unchanged.  
- **Secondary effects**: If B’s queue is genuinely halved, B’s resource utilisation will drop; the freed capacity could attract more work or change arrival patterns, but with the given isolated data we see no knockon degradation. In several cases the new bottleneck shifts to A (F05, F10) or creates a tie (F02, F11), meaning **further improvements would require also addressing A**. Thus CF2 is highly effective but points to the need for a balanced approach.

## CF3 – Eliminate downstream queuing (final station with infinite capacity)

Set `downstream_queue = 0` for all cases, i.e., `final_start_new = join_ready`.

- **Direct benefit**: every case’s total flow time reduces by its original downstream queue.
  - Original DQ values (min): 8, 15, 15, 18, 10, 15, 15, 15, 15, 20, 20, 10.  
  - Sum = 176 min, mean reduction **14.7 min per case** (12.7% of overall average flow time).  
- **Zerobenefit cases**: none; all 12 cases enjoy a direct reduction.
- **Secondary effects**: Eliminating downstream queuing effectively removes the final station as a bottleneck. However, if finalstation capacity becomes infinite but demand remains the same, the system simply shifts the bottleneck to the forkjoin stage. **The critical path will then be entirely determined by the branches**, making branch improvements (especially on B) even more valuable. If only a partial capacity increase is implemented, the queue will shrink but not disappear; the benefits would be proportional.  
- **Caveat**: In reality, downstream queuing could reemerge if the final station is still busy with later cases; this counterfactual isolates the static impact under the assumption that the same sequence of finalstart times can be compressed.

# 5. Recommended redesigns and risks

## Redesign 1 – Reduce B’s queue delay (e.g., add a resource or improve scheduling at B)

- **Rationale**: B is the most frequent critical branch and its average queue (19.2 min) is the largest component of its total delay. Halving B’s queue (as in CF2) would save ~7.7 min per case on average and would shift the bottleneck toward A in several cases, balancing the system.  
- **Expected impact on throughput & flowtime tail**: Throughput would increase because joinready times move earlier, reducing downstream start times if finalstation capacity remains constant. Cases that currently suffer long B waits (e.g., F12 with 30 min queue) would see marked reduction, improving the tail.  
- **Resource utilisation**: Adding a resource at B would lower utilisation, possibly making B less costefficient. If instead scheduling rules (e.g., priority to B when a batch arrives) are changed without extra resources, utilisation may stay high but variability could change.  
- **Possible new bottlenecks**: As B’s duration drops, A becomes the critical branch in 4–5 cases. Thus A may need attention soon after. Downstream queuing might also increase slightly if overall cycle time shrinks (more cases arriving at final station per time unit), but with only 12 cases we cannot quantify that.  
- **Synchronisation effects**: Reducing B’s duration cuts the slack that A and C currently enjoy. That could increase downstream pressure if the final station cannot absorb earlier releases.  
- **What to pilot / measure first**: Pilot by adding an additional resource at B for a set of cases, or by giving B higher priority during certain shifts. Measure B queue length, `join_ready`, finalstation queue, and overall flow time. Validate that A does not become an immediate new bottleneck.

## Redesign 2 – Increase finalstation capacity (e.g., add a third resource F3, or shift some work to a parallel station)

- **Rationale**: Downstream queuing averages 14.7 min, which is a substantial fraction of total flow time (mean 115 min). Eliminating or reducing this queue directly shortens every case and removes a mask that could hide the benefit of branch improvements.  
- **Expected impact**: Immediate reduction in total flow time for all cases. Even a 50 % reduction would yield ~7.4 min saving. If combined with branch improvements, the full effect of earlier joinready would be realised without being diluted by finalstation waiting.  
- **Resource utilisation**: With a third resource, utilisation per resource would drop (from perhaps high levels if two resources are currently saturated). Demand forecasting is needed to avoid overinvestment.  
- **Possible new bottlenecks**: The final station might no longer be the choke point; the forkjoin stage (especially B) would become the dominant bottleneck. This would increase the return on investing in B later.  
- **Synchronisation effects**: No direct synchronisation change, but earlier final completion could affect downstream processes not included in the dataset.  
- **What to pilot / measure first**: Temporarily assign an extra resource to the final station during peak periods. Measure finalstation queue, wait times, and whether branch completion times start to dictate overall flow time. Monitor for any new backlog at branch B or A.

# 7. Limits of inference

- **Causality and resource contention**: The observed queue delays are only the realised waits given the resource assignments. Without data on resource availability, scheduling policies, or work interruption (preemption), we cannot distinguish true capacity shortage from poor prioritisation. It is possible that B’s queue would shrink if a different dispatching rule were used, even without adding resources.
- **Branch resource capacity**: We see start times but not the number of resources at each branch, nor their work calendars. Therefore we cannot tell whether A’s zero queue is due to ample capacity or because A work is less variable; similarly, B’s queue might be inflated by a single busy resource.
- **Work preemption and interleaving**: Timestamps are completeevent data; we assume nonpreemptive, nonoverlapping execution. If resources can be taken away midactivity, the “service” time would contain waiting, inflating our estimate.
- **Finalstation waiting**: We interpret `final_start  join_ready` as downstream queuing for F1/F2. However, it could also reflect a “release policy” where the decision maker deliberately delays starting even though a resource is free (e.g., batch processing, approval windows). Without additional logs of resource states, we cannot distinguish pure queueing from discretionary postponement.
- **Singleday data**: The 12 cases are all from one day; patterns may differ across days, shifts, or workload mixes. Extrapolating to steadystate throughput requires longer observation.
- **Forkjoin semantics**: We assumed that all three branches must be complete before F can start, and that `join_ready` is exactly `max(end)`. If partial completion can trigger preliminary work or if there is an ORjoin, the real synchronisation constraint would differ.
- **Independence of branches**: We treated queue and service per branch as independent, but resource contention could create dependencies (e.g., a resource serving both A and B causing blocking). Our data lack resource identifiers beyond the final station, so such interactions remain hidden.
