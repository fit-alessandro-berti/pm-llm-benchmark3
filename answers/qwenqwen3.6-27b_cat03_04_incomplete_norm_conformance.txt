## 1. Conformance semantics

To interpret deviations against a deliberately incomplete norm, we must separate structural expectations from empirical observations using a tiered semantic framework:

- **Forbidden behavior:** Explicitly disallowed by the norm (closed-world). Any observed instance constitutes a violation unless proven to be a data artifact. The norm’s closed-world assumption applies strictly here: absence of a prohibition means permission, but presence of a prohibition means zero tolerance.
- **Missing mandatory behavior:** Expected whenever the stated scope applies (closed-world within scope, open-world outside). Gaps require scope verification and abstraction analysis before classification. A missing edge is only a violation if the scope condition is met and the abstraction level aligns with the rule’s intent.
- **Unexpected but unregulated behavior:** Relations or patterns not covered by the norm (open-world). Their presence does not imply noncompliance; they reflect process reality outside the normative boundary. Classification requires explicit norm references (e.g., `unspecified`) or absence thereof.
- **Typical-pattern absence:** Common and desirable but explicitly allows legitimate exceptions. Absence or low frequency is not a violation. The norm’s open-world stance applies; deviations are evaluated against stated exception conditions.
- **Likely data-quality error:** Structural artifacts from logging, joining, or schema mapping that mimic behavioral deviations. These require cross-validation with event attributes, system logs, or domain knowledge before escalation.
- **Abstraction mismatch:** Discrepancy between the norm’s logical expectation (e.g., “eventually,” object lifecycle) and the observed summary’s granularity (e.g., directly-follows, event-level binding). Misalignment produces false positives/negatives if not reconciled.
- **Insufficient evidence:** Cases where counts, context, or norm scope leave multiple plausible interpretations. Classification must remain provisional until raw logs or domain clarification is obtained.

**Open-world vs. closed-world impact:** The norm is closed-world only for `forbidden` relations and `mandatory` columns within their explicit scope. Everything else operates under an open-world assumption: absence of a normative edge does not imply prohibition, and presence of an unlisted edge does not imply violation. This prevents over-penalizing rare but legitimate process variants or modeling gaps.

## 3. Detailed reasoning by model family

### OC-DFG
The object-centric directly-follows graph establishes lifecycle progression for individual object types. It can establish whether a stated transition occurs and at what frequency, but it cannot establish parallel object interactions, exact temporal gaps, or causal dependencies across object types. Counts provide empirical grounding, but scope conditions (e.g., N4’s “externally shipped”) must be applied externally; raw counts alone cannot filter scope. A critical danger lies in interpreting “eventually expected” rules (like N1) as directly-follows constraints. The summary’s 98/100 count for `Create Order -> Validate Order` appears as a 2% violation, but the context explicitly notes unrecorded review events. Directly-follows abstraction collapses intermediate steps into missing edges, generating false mandatory violations. Proper interpretation requires either an “eventually” operator or explicit allowance for intermediate event types.

### OTG
The object type graph captures structural relationships at creation, interaction, or termination. It can establish co-occurrence and relationship typology (interaction, cobirth, codeath), but it cannot establish temporal ordering of interactions or distinguish primary from secondary object roles. Counts reflect relationship frequency, not compliance timing. For example, T2 mandates `(Package, object_interaction, Delivery)` for dispatch, but the observed 200 weight matches the count while E6 shows 198. This discrepancy highlights an abstraction mismatch: the OTG records the relationship existence, while ET-OT records event-level binding. If a Delivery object is created but not linked at the event level, OTG appears compliant while ET-OT flags a gap. Open-world assumptions protect unspecified relations (T4, T5), but forbidden relations (T6) require strict boundary alignment. A single cobirth edge violates T6, but may stem from a composite business event rather than true simultaneous creation.

### ET–OT
The event type–object type graph binds event occurrences to object instances. It can establish whether events correctly instantiate or interact with expected object types, but it cannot distinguish between intentional exceptions and logging failures without explicit event attributes. E8’s mandatory status includes an exception for unapplied cash, yet the observed log lacks this label, creating a false mandatory violation. Similarly, E10’s forbidden `Sensor Heartbeat -> Invoice` edge is almost certainly a data-quality artifact from a reused identifier join, not a behavioral breach. ET-OT is highly sensitive to schema mapping: if event attributes (e.g., carrier reference) are not elevated to object relations, mandatory bindings appear missing. The model family excels at detecting structural mismatches but requires domain rules to separate DQ errors from process deviations.
