# 1. Assumptions and Interpretation

1. The low-risk/high-risk choice is represented as an exclusive choice (XOR) after Analyze Root Cause completes. The low-risk branch consists solely of Supervisor Review. The high-risk branch is a concurrent pair (no ordering constraint) of Quality Review and Regulatory Review. The choice itself is data-driven and non-deterministic in the model; both routes are admitted as alternatives.

2. The optional supplier consultation is represented as an exclusive choice (XOR) between the visible activity Consult Supplier and a silent transition (tau). The choice occurs after Analyze Root Cause. When the visible branch is selected the activity occurs at most once. The chosen branch (visible or silent) must complete before Release Material; otherwise the sub-model is concurrent with Plan Verification, Design Corrective Action, the risk-route activities and the trial loop.

3. A passing inspection is abstracted purely by the structure of a LOOP operator whose do-part is the sequence Execute Trial → Inspect Trial and whose redo-part is Adjust Parameters. After every Inspect Trial the process may exit the loop (modelling “pass”) or take the redo. Consequently Adjust Parameters appears only on failure paths and can never follow the final (passing) Inspect Trial. No explicit pass/fail labels exist.

4. Duplicate visible activity labels are not permitted in either model. Silent transitions are used only for optionality (the supplier skip) and are never given a visible label.

5. The process-tree approximation policy is a conservative under-approximation. All hard precedence constraints (Register Deviation first, Contain Material before Plan Verification, Analyze Root Cause before Design Corrective Action and before the risk/supplier choices, both planning products before the trial loop, loop-exit + selected approval route + supplier-or-skip before Release Material, Release Material before Archive Case, and the internal loop discipline) are enforced exactly. The only intentional loss is that the risk-route and the supplier choice are forced to begin only after both Plan Verification and Design Corrective Action have finished, rather than as soon as Analyze Root Cause finishes. This excludes some intended early interleavings of reviews/consultation with the still-running planning stream, but never admits a forbidden behaviour.

6. “May overlap” / “proceed independently” is interpreted as the absence of an ordering constraint, i.e. true concurrency is possible. In a process tree this is expressed by the PARALLEL operator; in a POWL model it is expressed by the lack of a partial-order edge. Completions may therefore interleave arbitrarily (or, in the semantic model, occur concurrently).

# 3. PM4Py Process-Tree Model

Compact expression:

```text
->( 'Register Deviation',
    +( ->( 'Contain Material', 'Plan Verification' ),
       ->( 'Analyze Root Cause', 'Design Corrective Action' ) ),
    +( *( ->( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' ),
       X( 'Supervisor Review', +( 'Quality Review', 'Regulatory Review' ) ),
       X( 'Consult Supplier', tau ) ),
    'Release Material',
    'Archive Case' )
```

Self-contained construction code:

```python
import pm4py
from pm4py.objects.process_tree.obj import ProcessTree, Operator

tree_string = (
    "->( 'Register Deviation', "
    "+( ->( 'Contain Material', 'Plan Verification' ), "
    "   ->( 'Analyze Root Cause', 'Design Corrective Action' ) ), "
    "+( *( ->( 'Execute Trial', 'Inspect Trial' ), 'Adjust Parameters' ), "
    "   X( 'Supervisor Review', +( 'Quality Review', 'Regulatory Review' ) ), "
    "   X( 'Consult Supplier', tau ) ), "
    "'Release Material', "
    "'Archive Case' )"
)
tree = pm4py.parse_process_tree(tree_string)
```

(The same tree can be built by successive `ProcessTree(operator=..., children=..., parent=...)` calls; the parse form is used only for compactness and is semantically identical.)

The process tree realises every hard precedence and the loop discipline exactly. Because a process tree is block-structured it cannot express “start the risk-route / supplier choice as soon as Analyze Root Cause finishes, yet keep them concurrent with a later trial that itself waits for Plan Verification and Design Corrective Action.” The chosen under-approximation therefore forces the risk-route XOR and the supplier XOR to begin only after the PARALLEL of the two planning streams has completed. Consequently any trace in which Supervisor Review (or Quality/Regulatory Review or Consult Supplier) occurs while Plan Verification is still outstanding is rejected by the tree, even though the narrative permits it. All other intended concurrent interleavings that do not violate a hard precedence are retained, and no forbidden behaviour is admitted.

# 4. PM4Py POWL Model

Compact description:

```text
StrictPartialOrder(
  nodes = {
    Register Deviation,
    Contain Material,
    Analyze Root Cause,
    Plan Verification,
    Design Corrective Action,
    risk_op = XOR( Supervisor Review , StrictPartialOrder(Quality Review, Regulatory Review) ),
    cs_op   = XOR( Consult Supplier , τ ),
    trial_op = LOOP( StrictPartialOrder(Execute Trial → Inspect Trial) , Adjust Parameters ),
    Release Material,
    Archive Case
  },
  order = {
    Register Deviation → Contain Material,
    Register Deviation → Analyze Root Cause,
    Contain Material → Plan Verification,
    Analyze Root Cause → Design Corrective Action,
    Analyze Root Cause → risk_op,
    Analyze Root Cause → cs_op,
    Plan Verification → trial_op,
    Design Corrective Action → trial_op,
    risk_op → Release Material,
    cs_op → Release Material,
    trial_op → Release Material,
    Release Material → Archive Case
  }
)
```

Self-contained construction code:

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

rd  = Transition(label="Register Deviation")
cm  = Transition(label="Contain Material")
arc = Transition(label="Analyze Root Cause")
pv  = Transition(label="Plan Verification")
dca = Transition(label="Design Corrective Action")
sr  = Transition(label="Supervisor Review")
qr  = Transition(label="Quality Review")
rr  = Transition(label="Regulatory Review")
cs  = Transition(label="Consult Supplier")
et  = Transition(label="Execute Trial")
it  = Transition(label="Inspect Trial")
ap  = Transition(label="Adjust Parameters")
rm  = Transition(label="Release Material")
ac  = Transition(label="Archive Case")
tau = SilentTransition()

high = StrictPartialOrder(nodes=[qr, rr])          # concurrent, no edges
risk_op = OperatorPOWL(operator=Operator.XOR, children=[sr, high])
cs_op   = OperatorPOWL(operator=Operator.XOR, children=[cs, tau])

trial_do = StrictPartialOrder(nodes=[et, it])
trial_do.order.add_edge(et, it)
trial_op = OperatorPOWL(operator=Operator.LOOP, children=[trial_do, ap])

powl = StrictPartialOrder(nodes=[rd, cm, arc, pv, dca, risk_op, cs_op, trial_op, rm, ac])
powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)
powl.order.add_edge(cm, pv)
powl.order.add_edge(arc, dca)
powl.order.add_edge(arc, risk_op)
powl.order.add_edge(arc, cs_op)
powl.order.add_edge(pv, trial_op)
powl.order.add_edge(dca, trial_op)
powl.order.add_edge(risk_op, rm)
powl.order.add_edge(cs_op, rm)
powl.order.add_edge(trial_op, rm)
powl.order.add_edge(rm, ac)
```

Every pair of nodes that is intentionally unordered (Contain Material with Analyze Root Cause, Plan Verification with Design Corrective Action, the whole risk_op with the trial_op, the whole cs_op with the trial_op, risk_op with Plan Verification after their respective starts, etc.) has no partial-order edge. Consequently those sub-models remain concurrent and any interleaving of their visible activities is admitted, exactly as required by the narrative.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|-------------|--------------------|--------------|------|-----------------------------------|----------------------|
| Two initial work streams | Contain Material ∥ Analyze Root Cause after Register Deviation | exact (PARALLEL of the two sequences) | exact (no edge) | none | Independent containment and root-cause work can proceed simultaneously |
| Split dependencies into planning/design | Plan Verification after Contain Material only; Design Corrective Action after Analyze Root Cause only | exact | exact | none | Verification planning is not artificially delayed by root-cause analysis (and vice versa) |
| Risk route | XOR after Analyze Root Cause; low = Supervisor Review; high = Quality Review ∥ Regulatory Review | under (route may start only after both planning products) | exact | under-constraint of start time in tree | Reviews cannot begin while verification planning is still running; possible loss of lead-time in high-urgency cases |
| Overlap of approval and trial | Approval activities may interleave freely with the trial loop | exact (PARALLEL of LOOP and risk XOR) | exact (no edge) | none | Trial execution need not wait for final regulatory sign-off |
| Optional supplier consultation | XOR after Analyze Root Cause, concurrent with almost everything, before Release Material | under (same delayed start as risk route) | exact | under-constraint of start time in tree | Supplier dialogue cannot start until planning is finished; may lengthen cycle time |
| Repeat-until behaviour | LOOP(Execute Trial → Inspect Trial, Adjust Parameters); exit only after a successful Inspect Trial | exact | exact | none | Failed trials are correctly reworked; a passing inspection never followed by Adjust Parameters |
| Release synchronisation | Release Material after (loop exit ∧ selected approvals ∧ supplier-or-skip) | exact | exact | none | Material cannot be released until every required obligation is discharged |
| Duplicate-label risk | No visible activity appears more than once in the model | none used | none used | none | Frequency and performance analyses remain unbiased |

# 7. Preferred Representation and Validation Plan

The POWL model is the canonical representation. It encodes every intended partial-order dependency by an explicit edge and every intentional concurrency by the absence of an edge, while the XOR and LOOP operators capture the data-driven choices and the repeat-until trial cycle without approximation. The process tree is retained only as a hierarchical projection that is guaranteed never to accept unsafe behaviour.

Validation plan:

- Convert both models with `pm4py.convert_to_petri_net` (supported for ProcessTree and for POWL).
- Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on the resulting workflow nets; both should be sound (the LOOP and XOR operators produce free-choice constructs that the conversion preserves).
- Perform bounded playout (`pm4py.play_out`) with a modest maximum trace length and a modest number of traces to obtain a sample of the language; inspect that every generated trace respects the hard precedences and the loop discipline.
- Explicit positive tests: feed the five allowed witnesses (A1–A5) to a token-based or alignment-based conformance checker; A1–A4 must be perfectly fitting for both models, A5 must be fitting only for the POWL net.
- Explicit negative tests: the three forbidden witnesses (F1–F3) must produce non-zero fitness cost (or be rejected) on both nets.
- Silent-behaviour / duplicate-label check: confirm that the only silent transition is the supplier-skip tau, that it appears in exactly the expected optional position, and that no visible label occurs more than once in any generated trace or in the model structure.
- Limitations: infinite trial loops cannot be exhaustively enumerated; soundness algorithms may time-out on very large unfoldings; the conversion of POWL to a Petri net introduces additional silent transitions whose exact placement must be inspected manually; data conditions that originally selected the risk route or the supplier are invisible, so the models over-approximate the real decision logic.

# 8. Final Self-Critique

1. The process-tree under-approximation, while safe, still excludes a non-negligible set of intended early-review traces; a more elaborate duplication of the risk-route subtree (one copy nested early, one concurrent with the trial) could recover those traces at the cost of duplicate labels and more complex fitness calculations.
2. The POWL model treats the whole risk_op and the whole cs_op as atomic nodes in the partial order; an analyst who expands them sees the internal concurrency, but any tool that only examines the top-level edges may under-estimate the true interleaving freedom inside the high-risk branch.
3. Because outcomes of inspection and the risk/supplier decisions are purely structural, the models cannot be used for decision-mining or for predicting which route will be taken; any subsequent stochastic or data-aware extension would have to re-introduce the missing guards.
