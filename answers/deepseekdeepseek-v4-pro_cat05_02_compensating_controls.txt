## 1. Control-Objective Decomposition

FEP-1’s core objective is to prevent erroneous or fraudulent payments by ensuring no single individual can both initiate and authorize a payment. I decompose this into six specific threat scenarios:

**Objective O1: Unintentional Error by Single Operator**
One person making both preparation and release without independent review may propagate data-entry errors (wrong amount, wrong vendor, duplicate payment).
- AV-2: PREVENTS for checks covered (duplicate, amount limits); FAILS for transposition errors within limits or wrong vendor selection from dropdown
- MG-4: PREVENTS if performed before release with substantive review; DETECTS if after release but before settlement; FAILS if rubber-stamped
- RA-7: DETECTS after settlement; PARTIALLY CORRECTS if within recall window
- ED-1: Does not address this risk; conditions require AV-2 pass but do not add error detection

**Objective O2: Deliberate Fraud by Single Rogue Employee**
One person intentionally creates payment to controlled account, falsifies supporting documents, and releases.
- AV-2: DETECTS bank-account changes within 7 days; PARTIALLY DETECTS new vendors via sanctions screening; FAILS against established-vendor substitution with unchanged bank details
- MG-4: PREVENTS if independent manager verifies beneficiary ownership and business purpose before settlement; FAILS if manager is complicit or performs perfunctory review
- RA-7: DETECTS post-settlement; CORRECTS only within bank recall window
- ED-1: Does not address; conditions provide false comfort if underlying evidence is fabricated

**Objective O3: Collusion Between Two Operators**
Two individuals acting together can defeat simple segregation (distinct preparer and releaser) while achieving fraudulent outcome.
- AV-2: FAILS against collusion; automated checks do not evaluate social relationships or shared workstation access
- MG-4: PREVENTS if manager is truly independent and outside collusion circle; FAILS if manager is supervisor of colluding pair or participates
- RA-7: DETECTS retrospectively but only if audit examines behavioral patterns, not just transaction validity
- ED-1: Not applicable; collusion scenario typically involves distinct-user setup

**Objective O4: Credential Misuse or Shared Accounts**
One person uses another’s credentials (with or without permission) to create appearance of segregation.
- AV-2: FAILS; cannot detect credential sharing
- MG-4: PARTIALLY DETECTS if manager notices pattern inconsistency; FAILS if manager’s own credentials are compromised
- RA-7: DETECTS through access log analysis and behavioral pattern review; audit must examine login timestamps, IP addresses, workstation identifiers
- ED-1: Not applicable in standard form; emergency tokens could themselves be shared

**Objective O5: Circumvention During Control Outages**
When preventive controls (AV-2) are unavailable, segregation becomes the sole preventive barrier.
- AV-2: FAILS when unavailable; absence creates control gap
- MG-4: PREVENTS if performed before release with enhanced scrutiny compensating for missing AV-2; FAILS if performed after settlement
- RA-7: DETECTS but cannot correct after settlement; timing criticality increases
- ED-1: Condition 5 explicitly requires AV-2 operational; ED-1 is invalid during AV-2 outage

**Objective O6: Urgent Operational Necessity Override**
Legitimate emergencies require single-operator action where strict segregation would cause unacceptable operational harm.
- AV-2: PREVENTS for covered checks even during emergency
- MG-4: PREVENTS when performed before settlement with substantive review under time pressure
- RA-7: DETECTS and CORRECTS when performed within one business day with recall capability
- ED-1: ADDRESSES by providing structured permission framework with compensating conditions rather than ad-hoc violation

## 2. Equivalence and Sufficiency Test

A compensating control package is assessed against FEP-1’s objective using seven dimensions. The package must be evaluated holistically, not as a checklist of control presence.

### Structured Test Framework

**Dimension 1: Timing of Compensating Control Relative to Irrevocability**
- Before Release: Strongest preventive position; can stop erroneous payment entirely
- After Release, Before Settlement: Preventive for settlement risk; payment initiated but recoverable
- After Settlement, Within Recall Window (24 hours): Detective with corrective potential
- After Recall Window: Detective only; loss crystallization likely complete
- Scoring: Full equivalence requires preventive control before settlement; post-settlement controls are inherently detective/detective-corrective

**Dimension 2: Independence of Compensating Actor**
- Truly Independent: No reporting relationship, no shared incentives, no social proximity that impairs objectivity
- Organizationally Independent: Different reporting chain, but may have collegial relationship
- Supervisory Relationship: Direct or indirect reporting line creates conflict; objectivity compromised
- Self-Review: Same individual; no independence
- Scoring: Full equivalence requires truly independent actor; supervisory relationship provides at most partial equivalence

**Dimension 3: Coverage of Threat Scenarios**
- Error Detection: What types of errors does the control catch?
- Fraud Detection: What fraud mechanisms does the control disrupt?
- Collusion Resistance: Can the control be defeated by two or more actors?
- Scope Completeness: Does the control address amount, vendor identity, bank details, commercial substance, receipt of goods?
- Scoring: Full equivalence requires coverage of all material threat scenarios; gaps reduce to partial

**Dimension 4: Overrideability and Strength**
- Mandatory and Non-overridable: Control operates automatically and cannot be bypassed by affected parties
- Overridable with Independent Authorization: Bypass requires action by person not implicated in transaction
- Self-Overridable: The same person who would benefit from bypass can execute bypass
- Scoring: Self-overridable controls provide minimal assurance; mandatory controls are strongest

**Dimension 5: Recoverability**
- Full Recovery Certain: Funds can be recalled with high confidence within window
- Partial Recovery Possible: Some probability of recovery depending on recipient bank cooperation
- Recovery Unlikely: After recall window or with uncooperative recipient institution
- No Recovery Possible: Funds dissipated or legal recovery impractical
- Scoring: Equivalence requires high-confidence recoverability for any post-settlement control package

**Dimension 6: Evidence Quality and Verifiability**
- Objective and Tamper-Proof: System-generated logs, cryptographic signatures, immutable records
- Documented but Alterable: Signed documents, manual checklists subject to post-hoc modification
- Undocumented or Reconstructable Only: Verbal approvals, missing records
- Scoring: Full equivalence requires objective, verifiable evidence of control operation

**Dimension 7: Collusion Resistance**
- Collusion-Proof: Control requires actor outside any plausible conspiracy
- Collusion-Resistant: Collusion would require improbable combination of actors
- Collusion-Vulnerable: Two people with existing relationship can defeat
- Scoring: Objective equivalence requires collusion-resistance at organizational level

### Classification Standards

**Fully Equivalent**: All seven dimensions score at highest level; residual risk indistinguishable from proper FEP-1 execution with independent actors.

**Partially Equivalent**: Most dimensions strong but one or two material gaps; residual risk elevated but within tolerance for transaction risk level.

**Merely Mitigating**: Multiple dimensions weak; control package reduces but does not adequately address risk; likely unacceptable except for immaterial amounts.

**Ineffective**: Control package provides no meaningful risk reduction beyond having no controls; nominal presence without substance.

### Why “Same Expected Loss” Is Not the Only Standard

Expected loss calculation (probability × impact) is inadequate because:
1. Probability estimates for low-frequency, high-impact fraud events are inherently unreliable and subject to over-optimism
2. Control objectives include deterrence value not captured in loss distributions
3. Some control failures (e.g., collusion enabling systematic fraud) have unlimited upside exposure not bounded by transaction amount
4. Regulatory and stakeholder expectations may require segregation irrespective of calculated loss expectancy
5. Organizational culture and control environment effects extend beyond actuarial calculations

### Classification of Manager Action After Release but Before Settlement

This is best classified as a **detective-corrective hybrid**, not purely preventive.

**Rationale**: 
- The payment has already been released (funds committed from entity's perspective)
- However, settlement (irrevocable transfer) has not occurred
- Manager review creates a gate between release and irrevocability
- If issue found: settlement can be stopped  corrective function
- If no issue found: settlement proceeds  detective confirmation

I classify this as **"last-chance detection with corrective capability"** because:
1. The release decision was already made without segregation  preventive opportunity was missed
2. The manager is detecting whether the release was proper  detective function
3. The manager can correct by stopping settlement  corrective capability
4. The sequence matters: prevention would have stopped release; this stops settlement

This is not preventive for the release action itself, but is preventive for the irrevocable loss. In control taxonomy, I place it as a detective control with operational corrective capacity, distinct from pure detective controls (post-settlement review) and pure preventive controls (pre-release approval).

### AP-202: EUR 480,000 Fraud Loss
**Most Plausible Loss Mechanism**: u23 created payment to vendor with bank account changed two hours earlier, linked to employee's relative. u23 used m09's override credential to bypass AV-2 warning for bank change and limit exceedance. u23 then released same-user without independent review. Manager m09 (u23's supervisor) ratified two days later without substantive scrutiny.

**Which Control Breaks the Causal Chain**:

- If AV-2 override required *independent* authorization (not self-override): u23 could not have bypassed warning
- If FEP-1 segregation existed: second person would have seen bank change warning on release

**What Remains Exposed**:
- Collusion between supervisor and subordinate is unaddressed by any control
- Override credential management is weak (assigned to supervisor, potentially shared)
- New vendor + bank change combination has no mandatory independent verification
- Manager ratification timing (two days) provides no protection

**Likely Change Under Truly Independent Second Releaser**:
- Independent releaser would see AV-2 warning for bank change and limit
- If independent releaser was not complicit, payment would be blocked or escalated
- Probability of catching fraud: illustrative estimate ~85-95% (range reflects whether releaser would rubber-stamp warning or investigate)
- Residual risk with independent releaser: still exposed to collusion if u23 and releaser conspire, or if releaser is negligent

## 6. Evidence and Monitoring Recommendations

### Continuous Monitoring Rules

**Rule 1: Same-User Preparation and Release Rate**
- **Metric**: Percentage of completed payments where Prepare_Payment and Release_Payment share org:resource
- **Alert Threshold**: >5% of payments per month (amber); >10% (red)
- **Evidence Collected**: All same-user cases with case IDs, amounts, emergency token status
- **Not Proof Of**: Misconduct; may reflect legitimate ED-1 use or low-risk convenience
- **Is Proof Of**: Process conformance deviation requiring explanation
- **Action**: Verify ED-1 conditions met for each case; identify non-emergency same-user patterns

**Rule 2: AV-2 Override Rate and Self-Override Pattern**
- **Metric**: Override_Warning events as percentage of Automated_Validate_Warning events
- **Alert Threshold**: >2% override rate (amber); any self-override where override org:resource equals Prepare_Payment org:resource (red, immediate)
- **Evidence Collected**: Override events with warning type, override resource, preparer resource, subsequent release resource
- **Not Proof Of**: Fraud (may be legitimate exception); IS Proof Of control weakness when self-override permitted
- **Action**: Investigate all self-overrides; verify override credential authorization; consider system-enforced independent override

**Rule 3: Late Manager Approval (Post-Settlement)**
- **Metric**: Manager_Approve or Manager_Ratify events where timestamp > Bank_Settlement timestamp
- **Alert Threshold**: Any instance (amber); >1 per quarter (red)
- **Evidence Collected**: Case details, amount, manager identity, timing gap
- **Not Proof Of**: Fraud; IS Proof Of detective-only control posture for those cases
- **Action**: Require pre-settlement manager review; escalate cases where amount > EUR 100,000

**Rule 4: Audit Timing Relative to Recall Window**
- **Metric**: Audit_Review timestamp minus Bank_Settlement timestamp (or Release_Payment if no settlement event)
- **Alert Threshold**: >24 hours for same-user cases (red); >5 business days for any case (amber)
- **Evidence Collected**: Audit timing, case risk factors, audit findings
- **Not Proof Of**: Loss (audit may find no issue); IS Proof Of reduced corrective capacity
- **Action**: Prioritize same-day audit for ED-1 cases; investigate systematic audit delays

**Rule 5: Repeated Resource Pairs**
- **Metric**: Count of distinct cases where the same (Prepare_Payment resource, Release_Payment resource) pair appears within 30 days
- **Alert Threshold**: >10 paired cases in 30 days (amber); >30 paired cases (red)
- **Evidence Collected**: Pair identities, case amounts, workstation identifiers, approval patterns
- **Not Proof Of**: Collusion (may be legitimate team structure); IS Proof Of concentration risk requiring organizational review
- **Action**: Review organizational design; verify pair members are not in reporting relationship; check workstation sharing

**Rule 6: Shared Workstation Indicators**
- **Metric**: Cases where Prepare_Payment and Release_Payment originate from same IP address, hostname, or physical workstation
- **Alert Threshold**: Any instance where preparer  releaser but same workstation (amber); repeated instances (red)
- **Evidence Collected**: Workstation identifiers, timestamps, user access logs
- **Not Proof Of**: Credential sharing; IS Proof Of physical segregation failure requiring investigation
- **Action**: Correlate with Rule 5 findings; interview users; implement workstation-level controls

**Rule 7: Bank-Account Change Proximity**
- **Metric**: Payments where vendor bank account changed within 7 days before payment
- **Alert Threshold**: Any instance (amber); combined with same-user or high amount (red)
- **Evidence Collected**: Bank change timestamp, payment amount, AV-2 result, override events
- **Not Proof Of**: Fraud (legitimate changes occur); IS Proof Of elevated risk requiring enhanced verification
- **Action**: Require independent verification of bank-change authenticity; call-back verification to vendor

**Rule 8: Control Outage Events**
- **Metric**: Validation_Service_Unavailable events
- **Alert Threshold**: Any instance (red); duration > 15 minutes (critical)
- **Evidence Collected**: Outage duration, payments processed during outage, compensating controls applied
- **Not Proof Of**: Loss; IS Proof Of control gap period requiring retrospective review
- **Action**: Immediately halt high-value payments during outage; require manual compensating checklist; 100% audit of all payments during outage

**Rule 9: Emergency Token Timing Integrity**
- **Metric**: Cases where emergency token creation timestamp > Prepare_Payment timestamp
- **Alert Threshold**: Any instance (red)
- **Evidence Collected**: Token creation time, preparation time, case context, manager approval timing
- **Not Proof Of**: Intentional circumvention (may be logging delay); IS Proof Of ED-1 condition violation requiring investigation
- **Action**: Verify system clock synchronization; if genuine post-preparation token, treat as FEP-1 violation without ED-1 protection

**Rule 10: Manager Independence Verification**
- **Metric**: Cases where approving manager has supervisory relationship with preparer or releaser (from HR hierarchy data)
- **Alert Threshold**: Any instance (red)
- **Evidence Collected**: Organizational hierarchy, performance rating responsibility, approval patterns
- **Not Proof Of**: Improper approval; IS Proof Of independence compromise
- **Action**: Reassign approvals to independent managers; review past approvals by non-independent managers

### Evidence Collection Requirements

1. **Immutability**: All timestamps must be system-generated and stored in append-only logs
2. **Completeness**: All control events (Automated_Validate, Manager_Approve, Manager_Ratify, Override_Warning, Audit_Review) must be logged with resource, timestamp, and result
3. **Correlation**: Case identifiers must link all events; payment amount, vendor details, and bank details must be retrievable
4. **Workstation Attribution**: Network logs must capture source IP/hostname for all human actions
5. **Hierarchy Data**: Organizational structure must be maintained in analyzable format for independence checks

### Distinguishing Alerts from Proof of Misconduct

- **Alert**: Statistical deviation, pattern anomaly, or control-rule violation indicating elevated risk requiring investigation
- **Proof of Misconduct**: Investigative conclusion supported by evidence showing intentional circumvention, fraud, or gross negligence
- Alerts trigger investigation; investigations may find legitimate explanation, control weakness, or misconduct
- No single monitoring rule should trigger automatic misconduct determination
- Combinations of alerts (e.g., same-user + bank change + self-override + late audit) increase probability of misconduct but still require investigation

**PM4Py Behavior Notes:**

1. **`pm4py.filter_four_eyes_principle()`**: In PM4Py 2.7.x, this function expects a DataFrame with standard column names and returns either a filtered DataFrame containing violating traces or a list of case IDs. The behavior for cases where one of the activities is missing is version-dependent—some versions exclude incomplete traces, others include them. Our manual check handles edge cases explicitly.

2. **`dataframe_utils.convert_timestamp_columns_in_df()`**: This function standardizes timestamp formats. In some PM4Py versions, it modifies the DataFrame in place; in others, it returns a new DataFrame. We use the returned value for safety.

3. **Version differences**: PM4Py 2.5.x, 2.6.x, and 2.7.x may have different filter implementations. The manual four-eyes check provides a reliable baseline independent of PM4Py version quirks.
