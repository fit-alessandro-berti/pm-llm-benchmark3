# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

- **A1 — Single case notion.** Each test string is one case identified by a case id; `Activity@hour[resource]` maps to `concept:name`, `time:timestamp` (hours after case start, converted to seconds), and `org:resource`.
- **A2 — Visible labels only.** The 18 labels are the only observable activities. Silent routing (τ) is allowed inside the procedural model but never appears in the log.
- **A3 — Backbone is authoritative for control flow.** Ordering/branching in the "stable procedural backbone" (steps 1–5) is enforced by the procedural model; DECLARE/Log-Skeleton mainly encode cross-cutting and negative constraints that a block-structured model expresses poorly.
- **A4 — "Accepted" vs "rejected".** A case is *accepted* if it contains `Activate Vendor`, *rejected* if it contains `Reject Vendor`. R1/R10 make these mutually exclusive and at-most-once.
- **A5 — Post-activation loop (Change Bank Details / Suspend / re-Verify / re-Release) is real but rare.** It is included declaratively (R11) and, in the procedural model, only as an optional post-activation block; I disclose this as a block-structure approximation.
- **A6 — Resources and time are event attributes, not control-flow tokens.** Segregation-of-duties (R9) and temporal expectations (R12) are therefore delegated to the temporal-profile and resource/data layers, not to the procedural/declarative control-flow models.
- **A7 — Missing attributes.** The log has **no** `emergency` flag and **no** `joint_authorization` attribute (stated in R6). Any check requiring them is *undecidable from the log* and must degrade to a conservative default (see §7).
- **A8 — Clarification is a loop that must "close" (R3).** Every `Request Clarification` must be matched by a later `Receive Clarification` before the next request and before any terminal outcome (`Reject Vendor` / `Activate Vendor` / `Close Onboarding`).
- **A9 — Timestamps are exact and ordered.** Deviations under R12 are computed on elapsed time between the paired activities.
- **A10 — `support = 1.0`, explicit `confidence`.** As required, every DECLARE rule carries `support = 1.0`; `confidence < 1.0` marks rules I expect to be occasionally violated by legitimate but rare behavior (they warn rather than hard-fail).

## The R5/R6 conflict

- **R5 (Legal):** After `Sanctions Escalation`, `Obtain Legal Opinion` must **precede** `Activate Vendor` *under all circumstances*. This is a strict precedence: `precedence(Obtain Legal Opinion, Activate Vendor)` conditioned on escalation.
- **R6 (Operations):** Emergency activation *may* occur **before** `Obtain Legal Opinion`, provided joint authorization exists (not in the log) and the opinion arrives within 24h. This explicitly *permits* the ordering R5 forbids.

These are logically incompatible on the observable log alone, because the discriminating attributes (emergency flag, joint authorization) are absent (A7). I must not silently merge them.

**Resolution option 1 — Legal-strict (chosen for the implemented model).**
Encode R5 as a hard precedence in DECLARE/Log-Skeleton: if `Sanctions Escalation` occurs, `Obtain Legal Opinion` must appear *before* `Activate Vendor`. Any activation-before-opinion trace **fails** control-flow conformance. R6 becomes an *exception that lives entirely outside the log*: it can only be honored by an out-of-band waiver record, never by the event data. Compliance risk: **false positives** — genuine, properly authorized emergency activations are flagged as violations and require manual waiver reconciliation; operational friction, but no compliance gap.

**Resolution option 2 — Operations-permissive.**
Drop the strict precedence; allow `Activate Vendor` before `Obtain Legal Opinion` as long as (a) `Obtain Legal Opinion` eventually occurs (R4 `responded_existence`) and (b) the escalation→opinion elapsed time is within the temporal profile (12h mean; and the 24h hard cap of R6). Compliance risk: **false negatives** — without the joint-authorization attribute, we cannot distinguish an authorized emergency from an unauthorized premature activation, so illegitimate early activations pass silently. This is the more dangerous failure mode.

**Chosen: Option 1 (Legal-strict).** Rationale: with the discriminating attributes missing (A7), a conservative model must default to the stricter legal control and surface the operations exception as an explicit, auditable manual override. In §8 I show T6's verdict under **both** resolutions.

# 3. Procedural Backbone

## 1. Compact formal description

Using process-tree operators →(sequence), ∧(parallel/AND), ×(exclusive choice), ⟲(loop), and τ (silent):

```
Onboarding =
  → ( Receive Onboarding Request,
      Intake,                                  // optional clarification loop, then the 3 checks
      Classify Risk,
      × ( → (Reject Vendor, Close Onboarding),
          → ( Route,                           // low- or high-risk approval route
              Activate Vendor,
              PostActivation,                  // optional bank-change / re-verify loop
              Release First Payment,
              Close Onboarding ) ) )

Intake     = → ( ⟲ ( ∧ (Capture Master Data, Run Sanctions Screening, Verify Bank Account),
                       → (Request Clarification, Receive Clarification) ),  // redo-branch = clarification cycle
                  τ )
Route      = × ( Manager Approval,                                  // low-risk
                 → (Enhanced Due Diligence, Compliance Approval) )  // high-risk
PostActivation = ⟲ ( τ, → (Change Bank Details, Suspend Vendor, Verify Bank Account) )
```

**Disclosed approximations (block-structure limits):**
- `Sanctions Escalation` / `Obtain Legal Opinion` are *not* placed in the backbone tree. They are non-block-structured cross-cuts (escalation can occur after screening but before classification, and the opinion is tied to activation ordering by R4/R5). Forcing them into the tree would over-constrain; they are handled declaratively + resource layer. This is a deliberate exclusion.
- The clarification loop is modeled as a loop whose redo-body is the request/response pair; the tree cannot forbid "two requests without a response" — R3 is delegated to DECLARE `altsuccession`.
- `PostActivation` places `Release First Payment` after an optional loop; the "re-Verify before a *later* Release" refinement (R11) is a data-aware check (§7), not the tree.

## 2. PM4Py code (`procedural_model`)

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(label=label)

def node(op, children):
    n = ProcessTree(operator=op)
    for c in children:
        c.parent = n
        n.children.append(c)
    return n

# --- Intake: loop over (parallel checks) redo (request -> receive) ---
checks = node(Operator.PARALLEL, [
    leaf("Capture Master Data"),
    leaf("Run Sanctions Screening"),
    leaf("Verify Bank Account"),
])
clar = node(Operator.SEQUENCE, [leaf("Request Clarification"), leaf("Receive Clarification")])
intake_loop = node(Operator.LOOP, [checks, clar])          # do=checks, redo=clarification
intake = node(Operator.SEQUENCE, [intake_loop, ProcessTree()])  # trailing tau exit

# --- Approval route: low-risk XOR high-risk ---
low_risk = leaf("Manager Approval")
high_risk = node(Operator.SEQUENCE, [leaf("Enhanced Due Diligence"), leaf("Compliance Approval")])
route = node(Operator.XOR, [low_risk, high_risk])

# --- Post-activation optional loop: tau XOR (change -> suspend -> re-verify) ---
post_body = node(Operator.SEQUENCE, [
    leaf("Change Bank Details"), leaf("Suspend Vendor"), leaf("Verify Bank Account"),
])
post_activation = node(Operator.LOOP, [ProcessTree(), post_body])  # do=tau, redo=post body

accept_branch = node(Operator.SEQUENCE, [
    route,
    leaf("Activate Vendor"),
    post_activation,
    leaf("Release First Payment"),
    leaf("Close Onboarding"),
])
reject_branch = node(Operator.SEQUENCE, [leaf("Reject Vendor"), leaf("Close Onboarding")])
outcome = node(Operator.XOR, [reject_branch, accept_branch])

procedural_model = node(Operator.SEQUENCE, [
    leaf("Receive Onboarding Request"),
    intake,
    leaf("Classify Risk"),
    outcome,
])

# Optional: obtain an accepting Petri net for token-based conformance
# import pm4py
# net, im, fm = pm4py.convert_to_petri_net(procedural_model)
```

## 3. Explanation

- **Concurrency:** the three checks run under `∧`, so any interleaving (T1: Capture→Screening→Verify; T2: Screening→Verify→Capture) is accepted before `Classify Risk`.
- **Choices:** the top-level `×` splits reject vs accept; inside accept, `Route` is the low-/high-risk `×`. R8's route-exclusivity is *structurally* implied here and *reinforced* declaratively.
- **Clarification loops:** the `⟲` around the checks lets any number of request/response cycles occur (R3's "several cycles possible"); the tree cannot forbid an unanswered request, so R3's closure is declarative.
- **Terminal outcomes:** both branches end in `Close Onboarding` (backbone step 5). Reject and accept are mutually exclusive by construction; R1/R10 also guard against branch leakage produced by real logs (T8).
- **Post-activation behavior:** included as an *optional* loop (`Change Bank Details → Suspend Vendor → Verify Bank Account`) so normal cases (empty redo) are unaffected. The "re-Verify before a *later* Release" ordering (R11) is intentionally **excluded** from the tree and delegated to §7, because a block-structured tree cannot bind a specific second `Verify` to a specific later `Release`.

## Rule direction/semantics table

| Template | Key | Direction / meaning | Distinguished from |
|---|---|---|---|
| `init` | Receive Onboarding Request | Case must start with this activity | — |
| `existence` | Receive/Classify/Close | Activity must occur ≥1 in every case | vs `absence` (upper cap) |
| `absence` (max 1) | Activate / Reject / Release First Payment | At most one occurrence (a 2nd is forbidden) | Caps count, unlike `existence` which only lower-bounds |
| `responded_existence` | (Sanctions Escalation → Obtain Legal Opinion) | If source occurs, target must occur *somewhere* (no order) — **R4** | vs `response`: no ordering requirement |
| `responded_existence` | (Activate Vendor → Release First Payment) | If activated, a payment must exist (conf 0.9: suspended cases may not pay) | vs `response`: order-agnostic |
| `response` | (Change Bank Details → Suspend Vendor) | If source occurs, target must occur *later* — **R11** | vs `responded_existence`: adds "after" |
| `precedence` | (Run Sanctions Screening → Sanctions Escalation) | Target may occur only if source occurred *before* it — **R7** | vs `response`: guards the *target*, not the source |
| `precedence` | (Obtain Legal Opinion → Activate Vendor) | `Activate Vendor` only if `Obtain Legal Opinion` earlier — **R5**, conf 0.85 (emergency exception is rare/out-of-band) | vs `response`: precedence looks backward from target |
| `altresponse` | (Request Clarification → Receive Clarification) | After a request, a response must come *before any next request* — **R3** | vs `response` (allows two requests then one response); vs `chainresponse` (would force immediate adjacency) |
| `altprecedence` | (Request Clarification → Receive Clarification) | Each response is preceded by a request with no intervening second request | Pairs with altresponse to give alternating semantics |
| `noncoexistence` | (Reject, Activate); (Manager, Compliance); (EDD, Manager); (Compliance, Manager) | The two activities never appear in the same case (symmetric) — **R1, R2, R8** | vs `nonsuccession`: unordered mutual exclusion |
| `nonsuccession` | (Activate Vendor → Reject Vendor) | `Reject Vendor` must never occur *after* `Activate Vendor` — ordered guard for **R1** (catches T8) | vs `noncoexistence`: ordered, not symmetric |

I deliberately use **altresponse+altprecedence** (not `chainresponse`) for clarification because R3 requires "before the next request," not immediate adjacency; another activity may legitimately sit between request and response.

## Overlap / disagreement with other layers

- **`never_together`** duplicates DECLARE `noncoexistence` (R1, R2, R8). LS is authoritative for these because it is the cheapest global mutual-exclusion check; DECLARE mirrors them for a second opinion.
- **`always_before`** orientation: the pair `(X, Y)` in LS means "whenever X occurs, Y always occurred earlier." So `(Sanctions Escalation, Run Sanctions Screening)` = escalation always has screening before it (R7); `(Release First Payment, Activate Vendor)` = payment always has activation before it. These *reinforce* backbone ordering but scoped only to activities that actually appear (so they stay vacuously true in cases lacking them).
- **`directly_follows`** is kept minimal and only for adjacencies the log truly guarantees (`Reject/Release → Close`). I avoid asserting `Classify Risk` directly-follows any single check because the three checks are concurrent (any of them may be last) — asserting a DF here would contradict the parallel semantics of the procedural model.
- **`activ_freq`** carries R10 (authoritative here) and allows `{1,2}` for `Verify Bank Account`/`Capture Master Data` to accommodate the R11 re-verify loop without forcing it.
- **Disagreement to note:** LS `equivalence(Manager Approval, Activate Vendor)` holds only in the low-risk accepted subset; on the *whole* log it would be violated by rejected/high-risk cases. I keep it because pm4py's equivalence is evaluated per-trace on activities present; it is vacuous when `Manager Approval` is absent. This is a scoping subtlety flagged in §9.

# 6. Temporal Profile

```python
zeta = 2.0

temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),   # 172800s, 86400s
    ("Sanctions Escalation",  "Obtain Legal Opinion"):  (12 * 3600,  6 * 3600),   #  43200s, 21600s
    ("Activate Vendor",       "Release First Payment"): (72 * 3600, 36 * 3600),   # 259200s, 129600s
}
# Deviation flagged when |elapsed - mean| > zeta * std.
```

Bands (`mean ± zeta·std`):
- Clarification: 48h ± 48h → **[0h, 96h]**.
- Escalation→Opinion: 12h ± 12h → **[0h, 24h]** (this band also happens to coincide with R6's 24h cap; see §7).
- Activation→Payment: 72h ± 72h → **[0h, 144h]**.

**Why warnings, not violations.** R12 explicitly says these expectations are "normative enough to flag but not automatically reject." Elapsed time reflects workload, holidays, vendor responsiveness — legitimate variance that should not void an otherwise compliant control-flow. Temporal outliers therefore raise a **warning** and route to human review, never a hard `fail`. They are computed independently of the procedural/declarative verdicts and reported alongside them.

# 7. Resource- and Data-Aware Checks

These express what activity-only models cannot: resource inequality (R9), cardinality-with-attributes, the R11 re-verify ordering, and the R6 emergency policy.

```python
import pandas as pd
import pm4py

# Expected columns: case:concept:name, concept:name, time:timestamp, org:resource
# Optional (may be MISSING): emergency (bool), joint_authorization (bool)

# ---------- R9: segregation of duties ----------
def check_r9_sod(case_df):
    """case_df: events of ONE case, sorted by timestamp."""
    findings = []
    acts = case_df.set_index("concept:name")["org:resource"].to_dict()  # last-wins; fine (each once here)

    verify_res = case_df[case_df["concept:name"] == "Verify Bank Account"]["org:resource"].tolist()
    # applicable approval = whichever approval is present
    approval = None
    for a in ("Manager Approval", "Compliance Approval"):
        if a in acts:
            approval = acts[a]
    if verify_res and approval is not None and approval in verify_res:
        findings.append("R9: Verify Bank Account resource == approval resource")

    if "Capture Master Data" in acts and "Activate Vendor" in acts:
        if acts["Capture Master Data"] == acts["Activate Vendor"]:
            findings.append("R9: Capture Master Data resource == Activate Vendor resource")
    return findings

# pm4py helper for the four-eyes principle on a full log:
#   viol = pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")
#   viol = pm4py.filter_four_eyes_principle(log, "Capture Master Data", "Activate Vendor")
# (returns cases where the SAME resource did both -> violations)

# ---------- R11: re-verify before a later Release First Payment ----------
def check_r11(case_df):
    findings = []
    ev = list(case_df["concept:name"])
    if "Change Bank Details" in ev:
        # must be followed by Suspend Vendor
        i = ev.index("Change Bank Details")
        if "Suspend Vendor" not in ev[i+1:]:
            findings.append("R11: Change Bank Details not followed by Suspend Vendor")
        # any Release First Payment after the change needs a Verify Bank Account between them
        for j, a in enumerate(ev):
            if a == "Release First Payment" and j > i:
                if "Verify Bank Account" not in ev[i+1:j]:
                    findings.append("R11: later Release First Payment without intervening Verify Bank Account")
    return findings

# ---------- R6 / R5 emergency policy ----------
def check_r5_r6(case_df, resolution="legal_strict"):
    """
    resolution: 'legal_strict' (Option 1) or 'ops_permissive' (Option 2).
    Requires: emergency (bool), joint_authorization (bool) per event/case.
    """
    ev = list(case_df["concept:name"])
    if "Sanctions Escalation" not in ev:
        return []
    if "Obtain Legal Opinion" not in ev:
        return ["R4: escalation without eventual Obtain Legal Opinion"]
    if "Activate Vendor" not in ev:
        return []
    i_op = ev.index("Obtain Legal Opinion")
    i_ac = ev.index("Activate Vendor")
    opinion_before_activation = i_op < i_ac

    if opinion_before_activation:
        return []  # satisfies both R5 and R6

    # activation BEFORE opinion:
    if resolution == "legal_strict":
        return ["R5: Activate Vendor before Obtain Legal Opinion (Option 1: FAIL, "
                "emergency waiver must be reconciled out-of-band)"]

    # ops_permissive: need attributes to authorize the exception
    cols = case_df.columns
    if "emergency" not in cols or "joint_authorization" not in cols:
        # CONSERVATIVE DEFAULT when attributes are missing (A7):
        return ["R6: emergency attributes MISSING -> cannot confirm authorization; "
                "conservative FAIL (treat as R5 violation)"]
    emergency = bool(case_df["emergency"].max())
    authorized = bool(case_df["joint_authorization"].max())
    if not (emergency and authorized):
        return ["R6: early activation without emergency+joint_authorization -> FAIL"]
    # authorized emergency: opinion must arrive within 24h of escalation
    esc_t = case_df[case_df["concept:name"] == "Sanctions Escalation"]["time:timestamp"].iloc[0]
    op_t  = case_df[case_df["concept:name"] == "Obtain Legal Opinion"]["time:timestamp"].iloc[0]
    if (op_t - esc_t).total_seconds() > 24 * 3600:
        return ["R6: authorized emergency but opinion arrived >24h after escalation -> FAIL"]
    return ["R6: authorized emergency activation within 24h -> PASS (waiver on file)"]
```

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement:** R1 (Reject⊥Activate) is enforced in the procedural XOR, DECLARE `noncoexistence` + `nonsuccession`, *and* LS `never_together`. R7/R8/R10 likewise appear in ≥2 layers. This is intentional defense-in-depth, but the authoritative layer must be named (done in §2) to avoid conflicting messages; redundant layers should report as *corroborating*, not as separate failures.
- **Inconsistency under loops / post-activation:** LS `activ_freq` for `Verify Bank Account`/`Capture Master Data` was widened to `{1,2}` to admit R11's re-verify loop; had it stayed `{1}`, a legitimate post-activation re-verification would falsely fail. The `equivalence(Manager Approval, Activate Vendor)` pair is only valid in the low-risk subset and would break if evaluated globally — a scoping hazard. R11's "re-Verify before a *later* Release" cannot be expressed by any activity-only cardinality and must live in the data layer.
- **Vacuity in declarative rules:** `responded_existence(Sanctions Escalation, Obtain Legal Opinion)` and `precedence(Obtain Legal Opinion, Activate Vendor)` are **vacuously satisfied** in the (majority) cases with no escalation. Vacuous satisfaction can mask the fact that the rule was never actually exercised; conformance reports should distinguish *vacuously true* from *actively satisfied*.
- **Missing case attributes:** the log has no `emergency` and no `joint_authorization` (A7), so R6 is fundamentally undecidable from data; SoD (R9) collapses if `org:resource` is absent. These are hard blind spots, not modeling failures.
- **Timestamp-only limitations:** the temporal profile sees elapsed time but not *why* (holiday, vendor delay). It cannot separate a benign slow response (T7) from a genuine process problem, hence warnings only.
- **Support/confidence as "truth":** `support=1.0`/`confidence` are *mined statistics*, not laws. Treating a `confidence=0.9` rule as a hard control would wrongly reject rare-but-legal behavior; conversely `support=1.0` does not prove a rule is a policy — it only reflects the sample. These numbers must annotate, never adjudicate.

# 10. Deployment Recommendation

- **Canonical procedural representation:** the `ProcessTree` of §3, converted to an **accepting Petri net** (`pm4py.convert_to_petri_net`) for token-based replay. The tree is the human-readable source of truth for the control-flow backbone; the Petri net is the executable conformance artifact. Escalation/legal-opinion and post-activation refinements are *not* baked into the net (disclosed approximation) and are enforced declaratively/externally.
- **Authoritative policy layer:** the **resource/data-aware validation layer** is authoritative for R6/R9/R11-ordering; **DECLARE + Log Skeleton** are authoritative for the global negative/ordering constraints (R1–R5, R7, R8, R10); the **temporal profile** is authoritative only for R12 warnings. Where layers overlap, the mapping table (§2) names the single authoritative owner.
- **Check execution order:**
  1. **Procedural replay** (fitness / does the case follow the backbone?).
  2. **Log Skeleton** (cheap global cardinality + mutual-exclusion guards).
  3. **DECLARE** (ordering, precedence, alternate-response loop closure).
  4. **Resource/data layer** (R9 four-eyes, R11 ordering, R5/R6 policy with chosen resolution).
  5. **Temporal profile** (R12 warnings), always last and never blocking.
  Stop-and-report the **earliest decisive** hard violation, but continue evaluating all layers so the audit record is complete.
- **Surfacing contradictions:** present a per-case matrix (like §8) that keeps each layer's verdict separate, marks the earliest decisive violation, and shows *both* R5/R6 resolutions for escalated cases as `policy-dependent` until a human selects the applicable policy (and attaches any out-of-band emergency waiver). Warnings (temporal, missing-attribute) are shown distinctly from hard fails, and redundant corroborating findings are grouped under their authoritative owner so users see one reason, not four echoes.
