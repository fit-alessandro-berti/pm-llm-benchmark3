# 1. Policy Interpretation and Conflict Resolution

## Material Assumptions

1. **Parallel activities are unordered**: The three checks (CMD, RSS, VBA) can execute in any order and overlap in time. In the process tree, they are modeled as a parallel (interleaving) block.

2. **Clarification is optional and repeatable**: The clarification loop can execute zero or more times. Each iteration consists of exactly one Request Clarification followed by one Receive Clarification.

3. **Sanctions Escalation and Obtain Legal Opinion are cross-cutting**: They are not part of the main backbone. SE can occur any time after RSS. OLO must eventually follow SE.

4. **Post-activation activities (Change Bank Details, Suspend Vendor) are exceptional**: They are not part of the main backbone. They are handled by DECLARE and resource/data checks.

5. **Close Onboarding is always the terminal activity**: It occurs exactly once, at the end of every case.

6. **Resource attributes are required for R9**: The event log must contain `org:resource` for each event.

7. **Temporal attributes are required for R12**: The event log must contain `time:timestamp` for each event.

## R5/R6 Conflict

R5 states that Obtain Legal Opinion must precede Activate Vendor after Sanctions Escalation "under all circumstances." R6 permits an emergency exception where activation precedes the opinion, provided joint authorization exists outside the event log and the opinion arrives within 24 hours. The event log contains no `emergency` attribute or joint authorization marker.

### Resolution 1: Strict R5 (No Exceptions)
- Enforce precedence(OLO, AV) whenever SE occurred.
- Any violation is a hard failure.
- **Compliance risk**: Legitimate emergency activations are rejected, causing operational delays. But no unauthorized activation can slip through.

### Resolution 2: R5 Default with R6 Exception (Requires External Evidence)
- R5 is the default policy. If AV occurs before OLO after SE, the case is flagged as "policy-dependent."
- The system checks whether OLO arrived within 24 hours of AV (R6 deadline). If not, it's a hard failure.
- External joint authorization must be verified manually.
- **Compliance risk**: If manual review is weak, unauthorized activations could pass. The 24-hour deadline provides a safety net.

### Chosen Resolution
I implement **Resolution 2** for the resource/data layer: R5 is the default, R6 is a documented exception requiring manual verification. The automated system flags violations as "policy-dependent" when OLO arrives within 24 hours, and as "fail" when it arrives later. The compliance risk is that emergency activations without proper authorization could go undetected, but the combination of flagging and the 24-hour deadline mitigates this.

```python
    return n

def _tau(parent):
    n = ProcessTree(parent=parent)
    parent.children.append(n)
    return n

root = ProcessTree(operator=Operator.SEQUENCE)

# 1. Start
_leaf("Receive Onboarding Request", root)

# 2. Three concurrent checks
par = _op(Operator.PARALLEL, root)
_leaf("Capture Master Data", par)
_leaf("Run Sanctions Screening", par)
_leaf("Verify Bank Account", par)

# 3. Optional clarification loop
loop = _op(Operator.LOOP, root)
_tau(loop)  # skip (exit)
body = _op(Operator.SEQUENCE, loop)
_leaf("Request Clarification", body)
_leaf("Receive Clarification", body)

# 4. Risk classification
_leaf("Classify Risk", root)

# 5. Three mutually exclusive outcome routes
xor = _op(Operator.XOR, root)

rej = _op(Operator.SEQUENCE, xor)
_leaf("Reject Vendor", rej)
_leaf("Close Onboarding", rej)

low = _op(Operator.SEQUENCE, xor)
_leaf("Manager Approval", low)
_leaf("Activate Vendor", low)
_leaf("Release First Payment", low)
_leaf("Close Onboarding", low)

high = _op(Operator.SEQUENCE, xor)
_leaf("Enhanced Due Diligence", high)
_leaf("Compliance Approval", high)
_leaf("Activate Vendor", high)
_leaf("Release First Payment", high)
_leaf("Close Onboarding", high)

procedural_model = root
```

## 3.3 Explanation

**Concurrency**: The parallel operator `(CMD, RSS, VBA)` allows the three checks to execute in any interleaved order. All three must complete before the loop and Classify Risk.

**Clarification loop**: `*(, (RC_req, RC_resp))` models zero or more clarification cycles. The loop body is a strict sequence: each Request Clarification is immediately followed by its Receive Clarification. The tau (skip) allows exiting without any clarification.

**Choices**: The XOR after Classify Risk selects exactly one route:
- Reject: RV  CO
- Low-risk: MA  AV  RFP  CO
- High-risk: EDD  CA  AV  RFP  CO

**Terminal outcomes**: Close Onboarding is the last activity in every route, ensuring it always terminates the case.

**Excluded activities**: The following are deliberately excluded from the backbone and handled elsewhere:
- Sanctions Escalation, Obtain Legal Opinion: cross-cutting, handled by DECLARE (R4, R7) and resource layer (R5/R6)
- Change Bank Details, Suspend Vendor: post-activation exceptions, handled by resource layer (R11)
- R5/R6 conditional precedence: handled by resource/data layer

**Approximation disclosure**: The clarification loop is positioned strictly between the parallel block and Classify Risk. If clarification were to occur between individual parallel activities (e.g., after CMD but before RSS), this would not be captured by the process tree. The test cases are consistent with this approximation.

**Key distinctions**:
- **response vs precedence**: `response(A, B)` means "if A occurs, B must eventually follow." `precedence(A, B)` means "B can only occur if A has already occurred." Response looks forward from A; precedence looks backward from B.
- **altresponse vs chainresponse**: `altresponse(A, B)` means "every A is followed by B before the next A (not necessarily immediately)." `chainresponse(A, B)` would require B immediately after A. We use altresponse for clarification because other activities may intervene between RC_req and RC_resp.
- **noncoexistence vs nonsuccession**: `noncoexistence(A, B)` means neither can occur if the other does (symmetric). `nonsuccession(A, B)` means A can never be followed by B, but B could precede A. We use noncoexistence because the mutual exclusion is symmetric (R1, R2, R8).

**Deliberate omissions**: R5 (conditional precedence of OLO before AV) is NOT encoded because DECLARE lacks conditional constraints. An unconditional `precedence(OLO, AV)` would incorrectly reject valid cases without Sanctions Escalation.
