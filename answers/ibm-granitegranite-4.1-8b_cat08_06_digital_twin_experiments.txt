**1. Model scope and state variables**  

**Boundary** – The digital twin models the *buildingpermit issuance* process for the municipality, covering all case types (Simple renovation, New residential, Commercial, Complex variance). It does **not** model upstream applicant initiative or downstream usage of the permit after issuance.  

**Level of detail** –  
- *Entity*: a *permit case* identified by `case_id`.  
- *State variables per case*:  
  - `stage` (e.g., *Submit application*, *Completeness check*, …).  
  - `needs_docs`, `missing_docs_requested`, `has_docs`.  
  - `fire_required`, `env_required`, `public_notice_required`.  
  - `architect_id`, `district`, `area`, `application_value`.  
  - `rework_type` (if any).  
- *Time stamps*: arrival time (`submit_ts`), start and end timestamps for each activity (derived from log where present; otherwise modeled).  
- *Crosscase dependencies*:  
  - Same `architect_id` cases bundled for *Inspection scheduling*  reduces travel time.  
  - Districtlevel *Publicnotice* can affect multiple cases simultaneously via a common `objection_event` flag.  
- *Resources*: queues for clerks, planners, fire reviewers, env reviewers, inspectors, legal officers, and system tasks. Each queue holds resourcespecific calendars (working hours, peakmonth inspectors, special holidays).  
- *External calendars*: public holidays, council meeting weeks, and the nonstationary seasonal demand pattern.  

**Entities & Queues**  
| Entity | Queue | Calendar Influence |

**2. Parameterestimation plan**  

**Step1 – Load and format log** (using `pandas` and `pm4py.formulate_dataframe`):  

```python
import pandas as pd

log_df = pd.read_csv('permit_log.csv', parse_dates=['time:timestamp'])
formatted_log = pm4py.format_dataframe(log_df,
                                      event_attribute='concept:name',
                                      timestamp_attribute='time:timestamp',
                                      case_attribute='case:concept:name')
```

**Step2 – Build process model & variants**  
- Use `pm4py.discover.dfg` to obtain the DirectlyFollows Graph (DFG) from the formatted log.  
- Use `pm4py.discover.process_tree` on the DFG to automatically generate the highlevel tree matching the supplied string (note: the simplified string omitting explicit decision decisions will be reconciled by mapping observed branches).  

```python
dfg = pm4py.discover.dfg(formatted_log)
process_tree = pm4py.discover.process_tree(dfg, activity_generalization=True)
```

**Step3 – Servicetime & waitingtime estimation**  
- For each activity in the process tree, compute **median** and **p90** service times from the log (using `pm4py.statistical_analysis.service_time`).  
- For missing start timestamps (e.g., many human activities), infer waiting time as *arrival_to_completion minus logged service time* and capture the heavytailed behaviour with a Pareto or shiftedlognormal distribution (see `pm4py.distributions.estimate_parameters`).  

```python
service_stats = pm4py.statistical_analysis.service_time(formatted_log,
                                                        activities=[*process_tree.nodes])
```

**Step4 – Arrival pattern**  
- Aggregate daily case counts per month.  
- Fit a **nonstationary Poissontype** process: baseline  (JanFeb) × 1.7 for MarMay & SepNov (derived from log summary).  
- Model weekday intensity (Mon = 2.2× Wed) by scaling _weekday.  

```python
arrival_data = pm4py.summarize_arrivals(formatted_log, resolution='day')
seasonal_factor = pd.Series({1:1,2:1,3:1.7,4:1.7,5:1.7,6:1,7:1,8:1,9:1.7,10:1.7,11:1.7,12:1})
# combine weekday factor similarly ...
```

**Step5 – Branching probabilities & rework**  
- Rework occurrences are coded as activity names (`Completeness rework`, `Planning review rework …`).  
- Count frequency of each rework after its parent activity in the log to get **rework rates** (µ_r).  

```python
rework_rates = pm4py.analyze_rework(formatted_log, parent_activity_pattern='Planning review')
```

**Step6 – Resource calendars & dependencies**  
- **Load** the supplied calendar tables into the simulation engine (e.g., `ResourceCalendar` objects).  
- **Architect bundling**: a rule engine checks queued cases with same `architect_id`  group into a *bundle* and apply reduced traveltime factor (`travel_factor = 0.7`).  
- **Publicnotice length**: use `public_notice_duration = base 14d + objection_extension` where `objection_extension` follows the empirical distribution from the log (estimated via `pm4py.statistical_analysis.variable_distribution`).  

**Step7 – Missingdata handling**  
- For **objection events**, treat the *publicnotice* duration’s p90 as a proxy; apply a **confidence interval** (±30%) in the simulation to capture uncertainty.  
- For **missing start timestamps**, adopt the inferred waitingtime distribution and run a **MonteCarlo propagation** of its variance (see Section5).  

3. **Assumptions**  

| Category | Assumption | Rationale |
|----------|------------|-----------|
| **Arrivals** | Nonstationary Poisson with seasonality factors (×1.7 MarMay, SepNov) and weekday multiplier (Mon2.2× Wed). | Directly supported by the log summary. |
| **Service times** | Use median & p90 from the log; heavytailed behavior modeled with Pareto or shifted lognormal when start times are missing. | Captures observed variability (e.g., Inspection scheduling longtails). |
| **Routing** | Binary decisions (`requires_fire`, `requires_environment`, `public_notice_required`) are deterministic per case attributes; policy D2 overrides `requires_fire` for lowvalue Simple renovations. | Aligns with known business rules. |
| **Resources / Calendars** | Clerks work MondayFriday 0816, extra clerk on Mondays; planners 0917 with Simpleonly pair; fire reviewers TueThu; env reviewers 3FTE with 40% offshift; inspectors TueFri, districtbatching; legal officers off during council weeks; system unlimited. | Mirrors the supplied resource calendars. |
| **Rework** | Rework events follow the observed frequencies; probability of rework after each activity is constant over time (estimated from log). | Provides a firstorder approximation; future stochastic variation can be added. |
| **Applicant/Thirdparty response** | Applicantdriven `Receive missing documents` time drawn from empirical distribution (mean  5days delay). | Captures external delay that is not captured by municipal staff. |
| **Crosscase dependencies** | Architectlevel bundling reduces inspection travel time by 30%; districtwide objections extend publicnotice uniformly for all pending cases in that district. | Reasonable proxy given partial log data. |
| **Nonstationary demand** | Seasonal factors applied multiplicatively to the baseline arrival rate each simulated month. | Enforces the known demand spikes. |
| **Missing data** | Objevent proxy used with ±30% uncertainty; starttime missingness treated with inferred waitingtime distributions. | Acknowledges gaps and quantifies their impact. |

5. **Warmup, replications, and uncertainty treatment**  

- **Warmup**: Run the simulation for **1000 simulated days** (3×baseline median cycle length) to allow transient effects to dissipate.  
- **Replication**: For each experimental setting, perform **N=200 independent replications** with distinct random seeds (`seed = i*13`).  
- **Confidence intervals**: Use **90% bootstrap percentile intervals** on aggregated performance metrics (median, p90, 95th percentile).  
- **Heavytailed durations**: Replace pure exponential servicetime draws with a **shiftedlognormal** fitted to the p90/p95 observations; propagate variance via MonteCarlo redrawing per replication.  
- **Sensitivity analysis**: Vary the key seasonal factor (+/10%) and the legaloffweek length (0–3weeks) across an additional **10replication grid** to assess robustness of ranking decisions.  

6. **Validation strategy**  

| Validation type | Method | Data source | Pass criteria |
|-----------------|--------|-------------|---------------|
| **Face validation** | Domain expert review of process diagram, resource calendars, and policy interventions. | Interviews with municipal staff. | All major process steps and policies correctly represented. |
| **Eventlog replay** | Regenerate a synthetic log from the calibrated model and compare with original log distributions. | `pm4py.replay.simulate_log`. | KStest pvalue>0.05 for arrival rates, activity durations, and rework frequencies. |
| **Distributional validation** | Compare empirical CDFs of median and p90 service times, waiting times, and overall casecompletion times. | Postsimulation statistics vs. logderived statistics. | RMSE<5% for all key metrics. |
| **Resourceutilization validation** | Check average queue lengths and utilization percentages against observed logs (where available). | Queue metrics from simulation vs. logimplied queues. | Utilization within ±10% of observed. |
| **Bottleneck validation** | Identify topranked bottlenecks (e.g., Planning review, Publicnotice) and verify they match bottleneck analysis from log (e.g., highest average waiting). | Bottleneck analysis via `pm4py.analyze_bottlenecks`. | Same activities appear in top3 for both. |
| **Outofsample validation** | Run the model on a holdout subset of the log (e.g., last 10% of cases) and compare predictions. | Separate test set. | Correlation between simulated and observed completion times 0.85. |

class Queue:
    def __init__(self, capacity=float('inf')):
        self.items = []          # list of (case_id, start_time, end_time)
