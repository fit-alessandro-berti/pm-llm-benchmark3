## Why G6-Like Data Creates Both Inflated Waiting and Near-Zero Service

Cluster G6 illustrates a classic dual-distortion pathology caused by **deferred bulk-form submission** (`manual_bulk_form`) stamping a single submission timestamp $t_{\text{sub}} = 17{:}00$ into both `start` and `complete`.

Let a ticket arrive at $t_{\text{arr}}$, truly wait for $W_{\text{true}} \ge 0$, undergo actual processing of duration $S_{\text{true}} > 0$ (ending at $t_{\text{work\_end}} = t_{\text{arr}} + W_{\text{true}} + S_{\text{true}}$), and then sit unlogged until end-of-shift bulk submission at $t_{\text{sub}}$ with administrative deferral $D_{\text{defer}} = t_{\text{sub}} - t_{\text{work\_end}} \ge 0$. Because the bulk form records $t_{\text{start}}^{\text{obs}} = t_{\text{complete}}^{\text{obs}} = t_{\text{sub}}$:

1. **Observed waiting time absorbs everything prior to submission:**
   $$W_{\text{obs}} = t_{\text{start}}^{\text{obs}} - t_{\text{arr}} = t_{\text{sub}} - t_{\text{arr}} = W_{\text{true}} + S_{\text{true}} + D_{\text{defer}}$$
   For C01–C07, $W_{\text{obs}}$ ranges from `35 min` (C07) up to `175 min` (C01), averaging `103.4 min`—decreasing mechanically as arrivals get closer to `17:00`. Even if `Close ticket` were genuinely performed as a quick bulk click at `17:00` ($D_{\text{defer}}$ replaced by policy deferral), $W_{\text{obs}}$ reflects shift-end scheduling rather than congestion.
2. **Observed service time collapses to zero:**
   $$S_{\text{obs}} = t_{\text{complete}}^{\text{obs}} - t_{\text{start}}^{\text{obs}} = t_{\text{sub}} - t_{\text{sub}} = 0$$
   All actual work effort $S_{\text{true}}$ disappears from `service_time` and is silently transferred into $W_{\text{obs}}$ (or hidden inside `<1 min` resolution if the form click itself took seconds).
3. **Downstream analytical breakdown:**
   - **Utilization paradox:** $\rho_{\text{obs}} = \sum S_{\text{obs}} / T = 0\%$, yet mean queue wait is `103.4 min`. Standard queueing formulas ($W_q \propto \frac{\rho}{1-\rho} E[S]$) become completely inconsistent with the observed data.
   - **Misguided intervention:** Performance dashboards flag `Close ticket` / `T-F` as the facility's worst delay bottleneck while simultaneously showing zero productive workload—risking punitive management action or misplaced automation investments when the root problem is bulk-form logging.

def parse_ts(series: pd.Series, base_date: str = "2026-05-26") -> pd.Series:
    """Parse HH:MM or HH:MM:SS strings without silently dropping blanks."""
    def _norm(val):
        if pd.isna(val) or str(val).strip() == "":
            return pd.NaT
        s = str(val).strip()
        if len(s) == 5:
            s = f"{s}:00"
        return pd.Timestamp(f"{base_date} {s}")
    return series.map(_norm)

def compute_overlap_and_concurrency(g: pd.DataFrame) -> dict:
    valid = g.dropna(subset=["start", "complete"]).sort_values(["start", "complete", "sequence_no"])
    n = len(valid)
    if n < 2:
        return {
            "pair_overlap_strict": 0.0,
            "event_overlap_strict": 0.0,
            "pair_overlap_closed": 0.0,
            "adj_rate": 0.0,
            "peak_conc_strict": int((valid["complete"] > valid["start"]).any()) if n == 1 else 0,
            "point_ties": 0,
        }
    starts = valid["start"].to_numpy()
    ends = valid["complete"].to_numpy()

    total_pairs = n * (n - 1) // 2
    strict_pairs = 0
    closed_pairs = 0
    event_has_strict_ov = np.zeros(n, dtype=bool)
    for i in range(n):
        for j in range(i + 1, n):
            # Strict open-interval overlap: start_i < end_j and start_j < end_i (requires positive duration)
            if (starts[i] < ends[i]) and (starts[j] < ends[j]) and (starts[i] < ends[j]) and (starts[j] < ends[i]):
                strict_pairs += 1
                event_has_strict_ov[i] = True
                event_has_strict_ov[j] = True
            # Closed-interval touch/overlap (includes zero-duration ties & exact adjacency)
            if (starts[i] <= ends[j]) and (starts[j] <= ends[i]):
                closed_pairs += 1

    # Consecutive exact adjacency (end[i] == start[i+1] on positive-duration intervals)
    adj_count = sum(
        1 for i in range(n - 1)
        if (ends[i] > starts[i]) and (ends[i + 1] > starts[i + 1]) and (ends[i] == starts[i + 1])
    )

    # Sweep-line peak concurrency for strict intervals (end processed before start on ties)
    events = []
    for s, e in zip(starts, ends):
        if e > s:
            events.append((s, 1))
            events.append((e, -1))
    events.sort(key=lambda x: (x[0], x[1]))
    cur = peak = 0
    for _, delta in events:
        cur += delta
        peak = max(peak, cur)

    zero_pts = valid.loc[valid["start"] == valid["complete"], "start"]
    point_ties = int(zero_pts.value_counts().max()) if len(zero_pts) else 0

    return {
        "pair_overlap_strict": round(strict_pairs / total_pairs, 2),
        "event_overlap_strict": round(event_has_strict_ov.mean(), 2),
        "pair_overlap_closed": round(closed_pairs / total_pairs, 2),
        "adj_rate": round(adj_count / (n - 1), 2),
        "peak_conc_strict": peak,
        "point_ties": point_ties,
    }

# 5. Robustness and alternative explanations

## Sensitivity to Resource-Identity Trust vs Shared-Account Assumption

*Assumption A1 (Trusted individual IDs)*: Each distinct `resource` string maps 1-to-1 to a single worker or machine slot (except `RBT-7`, known to hold 4 items).  
*Assumption A2 (Shared accounts possible everywhere)*: Any resource string may represent $m \ge 1$ concurrent workers.

| Cluster | Under A1 (Trusted individual ID) | Under A2 (Possible shared account) | Robustness of Diagnosis |
|---|---|---|---|
| **G1 (`RBT-7`)** | Automated 4-slot fixture; simultaneous cycle is physically valid. | Unchanged—physical fixture capacity drives parallelism, not user login. | **High** (invariant to account sharing). |
| **G2 (`T-B`)** | Single inspector cannot plausibly inspect 4 items simultaneously; strongly favors UI "begin group" + serial execution. | Multiple inspectors sharing `T-B` *could* start together at 10:00 and finish at 10:08–10:27, making true parallel work more plausible—yet identical `10:00` starts + exact 6–7 min completion spacing still favor UI group start. | **Moderate–High** (still favors start-batching, but confidence drops from ~85 to ~65). |
| **G3 (`T-C`)** | Single reviewer strongly favors serial review (7–8 min cadence) + bulk folder submit at 11:30. | Multiple reviewers sharing `T-C` could work concurrently and submit a shared folder at 11:30, raising plausibility of concurrent review + end-gate. | **Moderate** (end-submission at 11:30 holds, but serial-vs-parallel work becomes less certain). |
| **G4 (`T-D`) & G8 (`T-H`)** | Single serial worker executing back-to-back. | Intervals remain strictly disjoint (`peak_conc=1`); shared scanner could mean shift/worker handoffs between items, weakening intentional single-worker batching claims. | **High for serial execution; Moderate for batch-policy attribution.** |
| **G5 (`analyst_pool`)** | Forces extreme conclusion: one super-analyst juggling 4 root-cause analyses simultaneously (`233%` utilization). | Known shared login (`m <= 3`) explains most overlap as multi-worker parallelism—**yet peak concurrency = 4 during `13:12–13:20` still proves at least one analyst is multitasking (or a 4th person uses the login)**. | **Critical shift**: A1 produces completely invalid utilization; A2 resolves pool capacity but still exposes residual multitasking. |
| **G6 (`T-F`)** | Single worker doing shift-end bulk close (`0 min` service). | Even with multiple users, `start==complete==17:00` on `manual_bulk_form` remains a bulk-submission artifact. | **High** (invariant). |
| **G7 (`T-G`)** | Negative waiting times + 15-min grid prove timestamp coarsening. | Shared accounts cannot make an item start before `queue_arrival` (`-1` to `-11 min`); coarsening remains proven. | **High** (invariant). |

## Sensitivity to Exact Timestamps vs Interval-Censored Timestamps

*Assumption B1 (Exact timestamps)*: Observed values represent true instants (with `:00` seconds where omitted).  
*Assumption B2 (Interval-censored by stated precision and rounding/truncation)*: True timestamps lie inside uncertainty intervals governed by documented precision and observed formatting.

- **G7 (`15 min` precision, undocumented down/up rounding)**:
  - Under B1, M02–M05 violate causality (`start < queue_arrival`) and every item takes `15 min` simultaneously.
  - Under B2, imposing physical constraints $t_{\text{start}}^{\text{true}} \ge t_{\text{arr}}$ and $t_{\text{complete}}^{\text{true}} \le t_{\text{rec}}$ (assuming monotonic clocks):
    - If `start` is floored to `14:00` (`[14:00, 14:15)`) and `complete` is ceiled to `14:15` (`(14:00, 14:15]`), then all 5 items executed inside `[13:58, 14:15]` (total window `<=15 min`, average serial duration `<=3 min`) and were logged/flushed 1 per minute at `14:16–14:20`.
    - Alternatively, if *both* `start` and `complete` are floored to 15-min boundaries, then `complete` fell in `[14:15, 14:20)`—matching `recorded_at = 14:16–14:20` as a constant `~1 min` lag!—and M05 (`arr=14:11`, `rec=14:20`) had true service time bounded in `[0, 9] min` (not `15 min`).
    - Under B2, **all negative waiting times vanish** and simultaneous execution is no longer supported.
- **G6 (`1 min` precision, `17:00–17:00`, `recorded_at=17:01`)**:
  - Under B1, service time is identically `0 s`.
  - Under B2, true execution of the bulk-close action lies in `[0, 60) s` (or up to `<120 s` before `17:01:59`), making a quick multi-select bulk click physically feasible—while still ruling out full manual ticket resolution during `17:00–17:01`.
- **G2, G3, G5 (`1 min` precision)**:
  - Under B2, each duration has `±1 min` (up to `±2 min` worst-case) censoring uncertainty. None of the structural diagnoses change (e.g., G5's 4-way overlap during `13:12–13:20` spans `8 min`, surviving worst-case `±1 min` censoring as a `>=6 min` 4-way overlap!).
- **G1, G4, G8 (`1 sec` stated precision, `HH:MM` displayed format, `HH:MM:SS` recording)**:
  - Under B1 (`:00` exact), G1 is simultaneous to the second and G4/G8 have exact `0 s` changeover gaps and exact `240 s`/`420 s` durations.
  - Under B2 (assuming silent minute-truncation of `start`/`complete` with no negative recording lag, so $t_{\text{complete}}^{\text{true}} \le t_{\text{rec}}$):
    - In G1, `complete` is pinned tightly to `[09:03:00, 09:03:03]` (within `3 s`), confirming near-simultaneous completion, while `start` could vary across `[09:00:00, 09:00:59]`.
    - In G4 and G8, because `recorded_at` is `:02–:06` seconds past the minute, true completions are tightly pinned to `[HH:MM:00, HH:MM:06]` (assuming no clock skew), whereas if starts were truncated downward, real inter-item changeover gaps of up to `~54–58 s` could exist—which would break `Sequential batching` at tight `merge_distance < 60 s`!

## Four Cases Where the Same Temporal Pattern Supports Multiple Physical Explanations

1. **Identical `[start, complete]` (`Simultaneous` pattern) — G1 vs G7 vs G6 (and within G1):**
   - *Explanation A (Physical parallelism):* Four-head automated fixture labeling four parts concurrently (G1).
   - *Explanation B (Cycle-level logging of internal serial work):* Single-head cell inside a 4-item fixture logging only fixture-close/fixture-open times (G1 alternative).
   - *Explanation C (Timestamp coarsening):* Serial manual measurements snapped to 15-min quarter-hour buckets (G7).
   - *Explanation D (Zero-duration bulk logging):* End-of-shift bulk submission stamping `start = complete = 17:00` (G6).
2. **Zero-gap back-to-back serial intervals (`Sequential batching` pattern) — G4 vs G8:**
   - *Explanation A (Intentional sequential batching):* Waiting to accumulate a batch of 5 items before starting a continuous run to amortize setup/changeover (G4 top hypothesis).
   - *Explanation B (Post-downtime queue drainage):* Unplanned or scheduled capacity loss (safety check 15:00–15:35) builds a backlog that is then drained continuously FIFO upon return (G8 top hypothesis).
   - *Explanation C (Auto-chained busy-period logging):* Ordinary busy-period serial service where scanner UI sets `start[i+1] = complete[i]` automatically.
3. **Common start, staggered completions (`Batching at start` pattern) — G2:**
   - *Explanation A (UI-induced start logging over serial work):* Single "begin group" click at 10:00 followed by strictly serial 6–8 min inspections.
   - *Explanation B (Physical shared setup + serial inspection):* Operator genuinely stages/calibrates all 4 items together at 10:00 before inspecting each.
   - *Explanation C (Parallel multitasking or team execution):* All 4 items genuinely worked concurrently with item-dependent durations (8, 14, 21, 27 min).
4. **Staggered starts, common completion (`Batching at end` pattern) — G3 (and `Concurrent batching` — G5):**
   - In **G3**, identical `complete=11:30` supports both *deferred logging* (reviews finished around 11:10, 11:17, 11:24, 11:30 and submitted together) and *operational end-batching* (reviews kept open/held until the whole release folder is approved together at 11:30).
   - In **G5**, staggered overlapping intervals support *multi-worker shared-account parallelism*, *single-worker cognitive multitasking*, and *open-ticket wait states* (waiting for external data while working another case).

# 6. Data-collection redesign

Recommendations are prioritized by impact on analytical validity and directly target the failure modes observed in G1–G8.

| Priority | Redesign Area | Concrete Specification | Target Clusters & Failure Mode Resolved |
|---|---|---|---|
| **P0 (Critical)** | **Execution timestamps (`start`, `complete`)** | Capture true item-level `start` and `complete` at native machine/UI event time in ISO-8601 UTC with millisecond/second precision (`YYYY-MM-DDTHH:MM:SS.sssZ`). Disable `legacy_MES` 15-min rounding; forbid bulk forms from copying submission time into `start`; decouple "begin group" UI clicks from per-item inspection start; forbid auto-chaining `start[i+1]=complete[i]`. | **G1, G2, G3, G4, G6, G7, G8** (eliminates negative waits, zero-duration artifacts, hidden changeover, and false start/end batching). |

Prohibit shared generic logins (`analyst_pool`) for transactional event logging. | **G5** (eliminates shared-account concurrency illusion and restores per-analyst utilization and handover mining). |
| **P0 (Critical)** | **Source clocks** | Enforce NTP/PTP clock synchronization across upstream queue systems, PLCs, scanners, tablets, desktop/VDI hosts, MES, and safety/EHS systems (target skew `<100 ms`). Log periodic `clock_offset_ms` and `clock_sync_status` telemetry per source. | **G7, G8** (eliminates cross-system negative waits and verifies alignment between downtime events and queue stalls). |
