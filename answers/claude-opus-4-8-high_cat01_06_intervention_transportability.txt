## 2. Transportability graph

```text
# Selection nodes encode site differences (S_* -> variable)
S_originals_required   -> originals_required
S_case_complexity      -> case_complexity
S_role_specialization  -> role_specialization
S_IT_case_lock         -> IT_case_lock
S_document_capacity    -> document_capacity
S_legal_capacity       -> legal_capacity
S_digital_documents    -> digital_documents

# Treatment and its enabling/blocking conditions
treatment_parallelization -> true_overlap
IT_case_lock              -> true_overlap        # lock blocks real concurrency
originals_required        -> true_overlap        # blocks Document Check start
digital_documents         -> true_overlap        # enables early Document Check
role_specialization       -> true_overlap        # distinct owners enable concurrency
document_capacity         -> true_overlap

# Overlap and capacities drive waiting
true_overlap              -> waiting_before_assessment
identity_capacity         -> waiting_before_assessment
document_capacity         -> waiting_before_assessment
assessment_capacity       -> waiting_before_assessment
API_latency               -> waiting_before_assessment
queue_huddles             -> waiting_before_assessment

# Cycle time and tail
waiting_before_assessment -> cycle_time
assessment_capacity       -> cycle_time
legal_capacity            -> cycle_time
originals_required        -> cycle_time          # variable-delay tail
case_complexity           -> cycle_time
rework                    -> cycle_time

# Rework, legal, appeal
originals_required        -> rework              # premature checks -> re-check
case_complexity           -> rework
legal_capacity            -> rework              # supplement loops
true_overlap              -> rework              # if checks start on invalid docs
rework                    -> cycle_time
case_complexity           -> appeal
legal_capacity            -> appeal
rework                    -> appeal
```

Shared mechanisms: the core causal edge `true_overlap -> waiting_before_assessment -> cycle_time` is structurally the same at both sites — running Identity and Document verification simultaneously removes a serial segment and shortens the pre-Assessment wait. Capacity-to-waiting edges (`identity/document/assessment_capacity -> waiting`) are also shared queueing physics.

Site-specific mechanisms: `originals_required` and `IT_case_lock` gate whether `treatment_parallelization` ever produces `true_overlap`. At A these are effectively off (90% digital, simultaneous ownership); at B they are dominant. Legal review and its supplement loop (`legal_capacity -> rework`) exist only at B, creating a downstream serial stage A never had.

Effect modifiers: `originals_required`, `digital_documents`, `IT_case_lock`, `role_specialization`, `case_complexity`, `legal_capacity`, and `assessment_capacity` all modify the treatment→outcome path. They do not merely add noise; they change the sign and magnitude of the effect for subgroups.

Why identical control-flow does not guarantee transportability: the two sites can share the same before/after process-tree edges yet differ on the *selection variables* that sit between the treatment and `true_overlap`. Transportability requires that the treatment-to-outcome mechanism be invariant *after conditioning on the effect modifiers*. Because B's selection nodes (`S_originals_required`, `S_IT_case_lock`, `S_legal_capacity`) activate blocking paths that are silent at A, the same diagram carries a different interventional distribution. A do-operator on the concurrency edge yields overlap at A but is intercepted by prerequisites and the case lock at B, so the estimand is not identified by A's data alone.

## 6. Candidate Site B intervention

Modified, segmented, staged intervention (reject blanket copy).

Eligibility rules:
- Stratum E1 (full parallel): no originals legally required (≈38%) AND not flagged public-sector/high-value. Create Identity Check and Document Check concurrently at Register.
- Stratum E2 (partial parallel): originals required. Create Identity Check ∥ Originals Receipt at Register; Document Check is created only after a *valid* Originals Receipt event.
- Stratum E3 (legal-gated): public-sector/high-value cases follow E1/E2 for verification but always route through Legal Review before decision.

Concurrent tasks: {Identity Check, Document Check} in E1; {Identity Check, Originals Receipt} in E2. Never start Document Check before valid originals when required.

Statutory prerequisites (mandatory, non-removable): Document Check ⟸ valid Originals Receipt (when required); Assessment ⟸ (Identity complete ∧ Document complete); Legal Review mandatory for public-sector/high-value; Notify after Approve/Reject.

Queue and WIP controls: per-pool WIP caps (e.g., ID ≤ 4×k, Doc ≤ 7×k active tasks); global cap on simultaneously opened verification pairs to avoid thrashing; a dedicated legal-WIP cap so verification speed does not overrun 2 legal reviewers; daily queue huddle retained as an explicit, separately measured practice.

Resource responsibilities: 4 identity reviewers own Identity Check; 7 document reviewers own Document Check + Originals validation; 3 assessors own the Assessment join; 2 legal reviewers own Legal Review and Request Supplement decisions. Enable dual active task ownership (or sanctioned lock workaround) so ID and Doc owners can hold the case simultaneously.

Legal-review and supplement loops: Legal Review may emit Request Supplement → repeat Document Check → re-Assessment; cap loop iterations and prioritize supplement follow-ups to bound the tail.

Logging: emit server-side task-open and task-close events (start/complete) for every task; forbid crediting overlap from manually back-entered timestamps; log an "originals valid at Doc start" flag; log stratum, legal flag, supplement-loop count.

POWL-style partial-order relation set (dependencies preserved; not unique):
```text
nodes = {Register, IdentityCheck, OriginalsReceipt, DocumentCheck,
         LegalOpt, Assessment, Decision(=XOR(Approve,Reject)), Notify}
LegalOpt = XOR( LOOP( LegalReview, PO{RequestSupplement -> DocumentCheck} ), tau )

order (strict partial order, transitive):
  Register        -> IdentityCheck
  Register        -> OriginalsReceipt
  OriginalsReceipt-> DocumentCheck        # statutory gate (E2/E3)
  IdentityCheck   -> Assessment           # join
  DocumentCheck   -> Assessment           # join
  Assessment      -> LegalOpt
  LegalOpt        -> Decision
  Decision        -> Notify
# IdentityCheck and DocumentCheck are UNORDERED w.r.t. each other -> concurrency
# In E1, Register -> DocumentCheck directly (no OriginalsReceipt gate)
```

## 7. Pilot for transport learning

| design element | specification | causal purpose | operational safeguard | process-mining measurement |
|---|---|---|---|---|
| Unit of assignment | The case (with team-week blocks to limit spillover) | Isolate per-case treatment effect | Block by team/week to control shared-resource contamination | Trace-level variant + cycle-time per case |
| Randomization / phased | Stratified randomization within strata; stepped-wedge across teams as fallback | Break confounding with secular trends/mix | Pre-register allocation; conceal upcoming assignment | Compare treated vs control variant frequencies (DFG) |
| Eligible strata | E1 no-originals digital; E2 originals-required; E3 legal-gated | Estimate effect *by* effect modifier | Minimum support per stratum before analysis | Per-stratum support counts, filtered logs |
| Treatment versions | V0 control (sequential); V1 ID∥Doc (E1); V2 ID∥Originals, gated Doc (E2); V3 = V1/V2 + WIP caps + huddles | Separate parallelization from co-interventions | Keep V1/V2 pure; add co-interventions only in V3 | Variant comparison V0→V1/V2→V3 |
| Primary outcomes | Median and p90 cycle time; wait-before-Assessment | The mechanism-linked outcomes | Mix-adjust; report by stratum | Waiting-time between task-close→next task-open |
| Secondary outcomes | Rework %, 90-day appeal %, Assessment/Legal queue length, true-overlap % (server events) | Detect quality/bottleneck side effects | Alert thresholds on rework/appeal | Overlap = intersecting task-open/close intervals |
| Interference controls | Shared pools (ID/Doc/Assess/Legal) create cross-case interference; use team-week blocks + WIP caps | Prevent treated cases from starving control cases | Monitor utilization parity across arms | Resource-utilization and queue telemetry per arm |

| Duration | ≥ 3–4 months to cover originals-delay tail and legal loops | Capture tail, not just first pass | Interim looks with alpha spending | Time-window filtered event log |
| Stop rules | Stop V-arm if rework/appeal exceeds baseline + δ, or legal queue diverges | Protect quality and legal SLA | Automatic guardrail dashboards | Trend monitoring on rework/appeal/queue |
| Transportability analysis | Re-estimate effect conditioning on originals/legal/lock modifiers; recompute selection nodes from graph in §2 | Test whether A→B transport holds after conditioning | Compare observed B effect to A-implied bound | Stratified effect estimates from mined logs |

How the pilot separates mechanism failure from implementation failure (≤220 words): The pilot instruments *true overlap* from server-side task-open/close events, independent of self-reported timestamps. If assigned-treated cases show no genuine overlap (because the IT case lock or the originals gate blocked concurrency), we have an **implementation/fidelity failure**: the treatment was never actually delivered, so a null result says nothing about the mechanism. We diagnose this by checking overlap-% and "originals-valid-at-Doc-start" flags in the treated arm before interpreting outcomes. If, instead, cases show high measured overlap yet cycle time does not improve, we have a **mechanism failure**: parallel verification genuinely happened but the binding constraint lies elsewhere (e.g., the Assessment join, legal capacity, or originals-arrival variance). The stratified design pinpoints where: E1 (no-originals) isolates the pure mechanism; E2 tests whether the statutory gate neutralizes it; V1/V2 vs V3 separates parallelization from co-interventions (WIP caps, huddles). Bottleneck-shift is detected by watching queue length migrate from verification to Assessment or Legal. Thus fidelity metrics (delivered overlap) gate the causal read of outcome metrics, and per-stratum, per-version contrasts attribute any null to a specific blocked prerequisite, saturated pool, or absent overlap — rather than conflating "we didn't do it" with "it doesn't work."

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)
from pm4py.objects.process_tree.obj import Operator

# ---------------------------------------------------------------------------
# 1. Site A BEFORE and AFTER process trees
# ---------------------------------------------------------------------------
site_a_before_str = (
    "-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', "
    "X ( 'Approve', 'Reject' ), 'Notify' )"
)
site_a_after_str = (
    "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', "
    "X ( 'Approve', 'Reject' ), 'Notify' )"
)

pt_a_before = pm4py.parse_process_tree(site_a_before_str)
pt_a_after = pm4py.parse_process_tree(site_a_after_str)

# ---------------------------------------------------------------------------
# 2. Convert both Site A trees to accepting Petri nets
# ---------------------------------------------------------------------------
net_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(pt_a_before)
net_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(pt_a_after)

# ---------------------------------------------------------------------------
# 3./4. Site B candidate as a STRICT PARTIAL ORDER (POWL)
#     - Register precedes Identity Check and Originals Receipt
#     - Document Check waits for Originals Receipt (statutory gate)
#     - Assessment waits for BOTH Identity Check and Document Check
#     - Optional Legal Review branch with a Request-Supplement -> Doc loop
# ---------------------------------------------------------------------------
register = Transition(label="Register")
identity_check = Transition(label="Identity Check")
originals_receipt = Transition(label="Originals Receipt")
document_check = Transition(label="Document Check")
assessment = Transition(label="Assessment")

# Supplement loop body: after Request Supplement, Document Check is repeated.
request_supplement = Transition(label="Request Supplement")
document_recheck = Transition(label="Document Check")
supplement_body = StrictPartialOrder(nodes=[request_supplement, document_recheck])
supplement_body.order.add_edge(request_supplement, document_recheck)

legal_review = Transition(label="Legal Review")
# LOOP( do=Legal Review, redo=(Request Supplement -> Document Check) )
legal_loop = OperatorPOWL(operator=Operator.LOOP,
                          children=[legal_review, supplement_body])

# Optional legal review: XOR( legal_loop, tau )  -> only ~40% of cases need it,
# but the *data-dependent* choice cannot be encoded, so we model it as a choice.
skip_legal = SilentTransition()
legal_optional = OperatorPOWL(operator=Operator.XOR,
                              children=[legal_loop, skip_legal])

decision = OperatorPOWL(operator=Operator.XOR,
                        children=[Transition(label="Approve"),
                                  Transition(label="Reject")])
notify = Transition(label="Notify")

site_b = StrictPartialOrder(
    nodes=[register, identity_check, originals_receipt, document_check,
           legal_optional, assessment, decision, notify]
)
o = site_b.order
o.add_edge(register, identity_check)        # Identity may start after Register
o.add_edge(register, originals_receipt)     # Originals may start after Register
o.add_edge(originals_receipt, document_check)  # statutory gate
o.add_edge(identity_check, assessment)      # 4. Assessment waits for Identity
o.add_edge(document_check, assessment)      # 4. Assessment waits for Document
o.add_edge(assessment, legal_optional)
o.add_edge(legal_optional, decision)
o.add_edge(decision, notify)
# NOTE: Identity Check and Document Check are left UNORDERED w.r.t. each other,
# which is exactly the parallelization the intervention introduces.

# ---------------------------------------------------------------------------
# 5. Convert the Site B POWL model to an accepting Petri net
# ---------------------------------------------------------------------------
net_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b)

# ---------------------------------------------------------------------------
# 6. Workflow-net / soundness checks
# ---------------------------------------------------------------------------
for name, (net, im, fm) in {
    "A_before": (net_a_before, im_a_before, fm_a_before),
    "A_after": (net_a_after, im_a_after, fm_a_after),
    "B_candidate": (net_b, im_b, fm_b),
}.items():
    is_wf = pm4py.check_is_workflow_net(net)
    sound = pm4py.check_soundness(net, im, fm)
    sound_flag = sound[0] if isinstance(sound, tuple) else sound
    print(f"{name}: workflow_net={is_wf}, sound={sound_flag}")

# ---------------------------------------------------------------------------
# 7. Optional playout: print a few sample traces from the Site B candidate
# ---------------------------------------------------------------------------
sample_log = pm4py.play_out(net_b, im_b, fm_b)
for i, trace in enumerate(sample_log[:5]):
    activities = [e["concept:name"] for e in trace]
    print(f"trace {i}: {activities}")

# ---------------------------------------------------------------------------
# 8. What this model CANNOT encode
# ---------------------------------------------------------------------------
# - Data-dependent legal requirement: Legal Review is truly required only for
#   the 40% public-sector/high-value cases and originals only for 62% of cases.
#   Control-flow XOR/optional branches cannot express these data guards; the
#   choice looks free even though it is determined by case attributes.
# - Resource capacity: 4 identity / 7 document / 3 assessment / 2 legal
#   reviewers and per-reviewer WIP caps are not representable in a plain
#   accepting Petri net; queueing and contention are outside this formalism.
# - Case locks: the legacy single-active-owner lock (which blocks REAL
#   concurrency) cannot be encoded; the net permits overlap the IT system may
#   forbid.
# - Durations / delays: highly variable originals-arrival delay, service times,
#   and the resulting tail behavior are not modeled; the net is untimed.
# - The loop bound on supplements and the true frequency of rework are not
#   captured; the model shows structural possibility, not likelihood.
```

## 9. Recommendation

**`conditional go`.**

What should be transferred: the *mechanism* — decoupling identity and document verification so they no longer sit in a forced sequence, thereby shortening the wait before the Assessment join. Also transfer the cheap, robust co-practices that A bundled in: a per-reviewer WIP cap and daily queue huddles, but as separately measured levers rather than as part of "parallelization."

What should not be copied: the literal proposal to "create Identity Check and Document Check simultaneously for *every* case." That is legally impossible for the 62% of cases needing originals (Document Check cannot start before a valid Originals Receipt) and physically impossible under the single-owner case lock. Copying it wholesale would manufacture *reported* overlap via back-entered timestamps while delivering little real speedup (scenario S4), and would risk premature document checks that inflate the already-high 17% rework (S6). Do not import A's headline 9h median gain as an expectation; it is confounded by an easier case mix (48→40%), two added reviewers, a registry-API upgrade, and huddles.

Which subgroup enters first: the no-originals, non-legal digital stratum (E1, ≈38% of volume). Here full ID∥Doc concurrency is both legal and realizable, so the mechanism can be observed cleanly. In parallel, apply the partial pattern (Identity ∥ Originals Receipt, gated Document Check) to the originals stratum.

Expected benefits and risks: benefits are a stratum-level reduction in wait-before-Assessment and median cycle, largest for E1 (S1/S2). Risks: the bottleneck shifts to 3 assessors or 2 legal reviewers (S3, S5), producing the "mean improves but p90 worsens" pattern; the IT lock nullifies real overlap (S4); premature checks raise rework (S6).

Evidence that triggers expansion: E1 shows genuine server-measured overlap plus a mix-adjusted wait/median reduction, with rework, appeals, and legal-queue length stable. Evidence that triggers modification: overlap realized but no cycle gain (bottleneck elsewhere) → rebalance assessor/legal capacity or WIP caps. Evidence that triggers abandonment: no true overlap achievable (lock cannot be lifted), or rework/appeals rise past guardrails despite gating.

## 10. Assumption register

1. Overlap is the causal driver of A's wait reduction — why needed: it is the only metric plausibly tied to the treatment rather than confounders — how to test: pilot arm with server-side overlap measurement vs control — consequence if false: transferring the mechanism yields no cycle-time benefit at B.
2. Site B's IT case lock can be lifted or a sanctioned dual-ownership workaround exists — why needed: without it no real concurrency occurs — how to test: attempt configuration change; audit whether treated cases show true concurrent task intervals — consequence if false: only implementation failure (S4); intervention delivers nothing real.
3. The ~38% no-originals stratum is stable and identifiable at registration — why needed: it is the first-wave eligible group — how to test: mine registration attributes / DFG for cases lacking Originals Receipt — consequence if false: eligibility shrinks, expected aggregate gain falls.
4. Assessment (3) and Legal (2) pools have slack to absorb faster verification — why needed: otherwise the wait merely relocates — how to test: monitor queue length at Assessment/Legal during pilot — consequence if false: bottleneck shift, p90 worsens (S3/S5).
5. Document Check can be reliably gated on *valid* originals — why needed: to avoid premature checks and rework — how to test: log "originals-valid-at-Doc-start" flag and rework correlation — consequence if false: rework rises 2–4pt (S6), eroding gains.
6. Case mix at B stays roughly constant during the pilot — why needed: to avoid A's mix-shift confound — how to test: track high-complexity % across arms/weeks — consequence if false: effect estimates become confounded and non-comparable.
7. Timestamps used for analysis are server-generated, not back-entered — why needed: to distinguish real overlap from artifact — how to test: compare system events vs manual entries; audit sample — consequence if false: illusory improvement, wrong go/no-go decision.
8. Cross-case interference through shared pools is controllable via blocking + WIP caps — why needed: SUTVA-style independence for the pilot — how to test: check utilization parity and starvation across arms — consequence if false: biased effect estimates; treated cases starve controls.
