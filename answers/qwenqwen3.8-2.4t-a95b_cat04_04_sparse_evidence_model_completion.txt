# 2. Shared Assumptions

The following assumptions are common to all three candidates.

1. **Event semantics are completion timestamps.**  
   Each event represents completion of an activity. The observed order is completion order, not start order or causal enablement order.

2. **Same-timestamp ordering is artificial.**  
   When timestamps are equal, ingestion index imposes a total order. This order is not interpreted as evidence of causality or true sequence.

3. **Activities are not repeated within a case.**  
   There is no observed rework. Expedite Review is explicitly at most once by D6. We extend the at-most-once assumption to the other activities in all three models.

4. **Supplier Confirmation absence is ambiguous.**  
   A trace without Supplier Confirmation may represent:
   - a stocked component that legitimately does not require Supplier Confirmation;
   - a missing Supplier Confirmation event caused by integration failure;
   - an unobserved case type where Supplier Confirmation is not applicable.  
   The models represent this ambiguity through a no-Supplier control-flow alternative, not through a separate data-quality attribute.

5. **The external/stocked attribute is unavailable.**  
   Because the attribute was not exported, Supplier Confirmation cannot be conditionally required by case type. Optionality is represented structurally.

6. **High-confidence rules are enforced in all candidates.**  
   All models enforce:
   - `Register Order` first;
   - `Archive Case` last;
   - `Approve Configuration` before `Release Production`;
   - `Credit Check` and `Engineering Review` before `Approve Configuration`.

7. **Partial order is used as uncertainty, not proof of concurrency.**  
   When a model leaves two activities unordered, this means the available evidence does not justify imposing a fixed order. It does not assert that the activities were truly concurrent.

8. **Optional behavior is represented by explicit alternatives.**  
   Optionality is modeled using XOR-style branches or alternative partial orders. The models are not probabilistic; they do not assign likelihoods to branches.

9. **The candidates are acyclic.**  
   No loops or rework are modeled. This is consistent with the observed 30 traces but may underfit future behavior if rework exists.

# 4. Balanced Candidate

**Inductive bias.**  
The balanced candidate generalizes the strongest evidence while explicitly representing uncertainty. It treats Credit Check and Engineering Review as unordered prerequisites for Approve Configuration, because both orders are observed and the engineering lead describes parallel work. It treats Supplier Confirmation as optional and, when present, requires it after Credit Check and before Approve Configuration. This choice is evidence-driven: every observed Supplier Confirmation completes after Credit Check. Engineering Review is left unordered with Supplier Confirmation, allowing Supplier Confirmation before or after Engineering completion. Expedite Review is optional, at most once, after both principal checks, before Approve Configuration, and unordered with Supplier Confirmation. The model uses partial orders not as proof of concurrency but as a compact way to avoid imposing unsupported sequential constraints.

**Decision between sequence, concurrency, and partial order.**

- **Credit Check and Engineering Review:**  
  The log contains both completion orders. D7 says completion timestamps cannot prove true concurrency. The balanced model therefore uses a partial order: neither activity is forced before the other, but both must precede Approve Configuration.

- **Supplier Confirmation:**  
  All observed Supplier Confirmations complete after Credit Check. Therefore the balanced model imposes `Credit Check -> Supplier Confirmation`. It does not impose `Engineering Review -> Supplier Confirmation`, because V5 shows Supplier Confirmation can complete before Engineering Review. This is a conservative interpretation of D5: it allows overlap with Engineering Review but does not admit the unobserved Engineering-only trigger.

- **Expedite Review:**  
  D6 and S6 require both Credit Check and Engineering Review before Expedite Review and Expedite Review before Approve Configuration. The observed Expedite cases show Expedite both after Supplier Confirmation and before Supplier Confirmation. Therefore the balanced model imposes `Credit Check -> Expedite Review`, `Engineering Review -> Expedite Review`, and `Expedite Review -> Approve Configuration`, while leaving Expedite Review unordered with Supplier Confirmation.

- **Approve, Release, Archive:**  
  These are modeled as a strict sequence because D1 and D2 are high confidence and all observed variants agree.

```python
                ("Credit Check", "Expedite Review"),
                ("Engineering Review", "Expedite Review"),
                ("Expedite Review", "Approve Configuration"),
            ]
        )

    return strict_po(labels, edges)


balanced_branches = [
    balanced_po(has_supplier=False, has_expedite=False),
    balanced_po(has_supplier=False, has_expedite=True),
    balanced_po(has_supplier=True, has_expedite=False),
    balanced_po(has_supplier=True, has_expedite=True),
]

model_balanced = make_xor(balanced_branches)
```

**Behavior deliberately excluded.**

- Supplier Confirmation before Credit Check.
- Supplier Confirmation after Approve Configuration.
- Expedite Review before both Credit Check and Engineering Review are complete.
- Expedite Review after Approve Configuration.
- Release Production before Approve Configuration.
- Missing Register Order or Archive Case.
- Repeated Supplier Confirmation or repeated Expedite Review.
- Supplier Confirmation triggered only by Engineering Review while Credit Check is still incomplete.

**Known underfitting and uncertainty risks.**

- If D5 is true in the stronger sense and Supplier Confirmation can be triggered by Engineering Review alone, the balanced model will reject valid cases where Supplier Confirmation completes before Credit Check.
- If the finance manager’s rule S1 is a hard policy, the unordered Credit/Engineering partial order may be too permissive.
- The no-Supplier branch conflates legitimate stocked-component skips with missing Supplier Confirmation events.
- The XOR over partial orders can create hidden choice: a case where Supplier Confirmation occurs after both checks may be explainable by more than one branch.
- The model admits Expedite Review without Supplier Confirmation, which is consistent with D6 and S4 but not directly observed.

# 5. Permissive Candidate

**Inductive bias.**  
The permissive candidate admits all reasonable combinations consistent with the broad domain rules, while still forbidding clear compliance violations. Its bias is toward recall and exploration. It allows Credit Check and Engineering Review to appear in either completion order or to be interpreted as overlapping. It allows Supplier Confirmation to be absent, or to occur after Credit Check, or after Engineering Review. It allows Expedite Review with or without Supplier Confirmation, before or after Supplier Confirmation, provided Expedite occurs after both principal checks and before Approve Configuration. The boundary of the model is defined by the hard constraints, not by the exact observed variants.

**Boundary between reasonable generalization and forbidden behavior.**

Reasonable generalization includes any trace satisfying:

1. `Register Order` is first.
2. `Archive Case` is last.
3. `Credit Check` and `Engineering Review` both occur before `Approve Configuration`.
4. If `Supplier Confirmation` occurs, it occurs before `Approve Configuration` and after at least one of `Credit Check` or `Engineering Review`.
5. If `Expedite Review` occurs, it occurs at most once, after both `Credit Check` and `Engineering Review`, and before `Approve Configuration`.
6. `Release Production` occurs after `Approve Configuration`.

Forbidden behavior includes:

- Supplier Confirmation before both principal checks.
- Expedite Review before both principal checks.
- Approve Configuration before Credit Check or Engineering Review.
- Release Production before Approve Configuration.
- Supplier Confirmation or Expedite Review after Approve Configuration.
- Repeated Supplier Confirmation or Expedite Review.
- Missing Register Order or Archive Case.

**Compact formal expression.**

Base constraints:

```text
R -> C
R -> E
C -> A
E -> A
A -> P -> Z
```

Supplier alternatives:

```text
no S
C -> S -> A
E -> S -> A
```

Expedite alternative:

```text
no X
C -> X
E -> X
X -> A
```

No fixed order is imposed between `S` and `X` when both are present, except their individual prerequisites and the requirement that both precede `A`.

The permissive model is:

```text
XOR over:
  Supplier mode in {none, after Credit, after Engineering}
  Expedite mode in {absent, present}
```

**PM4Py code.**

```python
import networkx as nx

from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,  # imported for possible extensions; not used directly here
)
from pm4py.objects.process_tree.obj import Operator


def T(label: str) -> Transition:
    try:
        return Transition(label)
    except TypeError:
        return Transition(label=label)


def strict_po(node_labels: list[str], edges: list[tuple[str, str]]) -> StrictPartialOrder:
    graph = nx.DiGraph()
    trans = {}

    for label in node_labels:
        t = T(label)
        trans[label] = t
        graph.add_node(t)

    for source, target in edges:
        graph.add_edge(trans[source], trans[target])

    try:
        return StrictPartialOrder(order=graph)
    except TypeError:
        try:
            return StrictPartialOrder(graph)
        except TypeError:
            po = StrictPartialOrder()
            po.order = graph
            return po


def make_xor(children: list) -> OperatorPOWL:
    try:
        return OperatorPOWL(Operator.XOR, children)
    except TypeError:
        try:
            return OperatorPOWL(operator=Operator.XOR, children=children)
        except TypeError:
            op = OperatorPOWL(Operator.XOR, [])
            op.children = children
            return op


BASE_LABELS = [
    "Register Order",
    "Credit Check",
    "Engineering Review",
    "Approve Configuration",
    "Release Production",
    "Archive Case",
]

BASE_EDGES = [
    ("Register Order", "Credit Check"),
    ("Register Order", "Engineering Review"),
    ("Credit Check", "Approve Configuration"),
    ("Engineering Review", "Approve Configuration"),
    ("Approve Configuration", "Release Production"),
    ("Release Production", "Archive Case"),
]


def permissive_po(supplier_mode: str | None, has_expedite: bool) -> StrictPartialOrder:
    labels = BASE_LABELS.copy()
    edges = BASE_EDGES.copy()

    if supplier_mode == "after_credit":
        labels.append("Supplier Confirmation")
        edges.extend(
            [
                ("Credit Check", "Supplier Confirmation"),
                ("Supplier Confirmation", "Approve Configuration"),
            ]
        )
    elif supplier_mode == "after_engineering":
        labels.append("Supplier Confirmation")
        edges.extend(
            [
                ("Engineering Review", "Supplier Confirmation"),
                ("Supplier Confirmation", "Approve Configuration"),
            ]
        )
    elif supplier_mode is None:
        pass
    else:
        raise ValueError("supplier_mode must be None, 'after_credit', or 'after_engineering'")

    if has_expedite:
        labels.append("Expedite Review")
        edges.extend(
            [
                ("Credit Check", "Expedite Review"),
                ("Engineering Review", "Expedite Review"),
                ("Expedite Review", "Approve Configuration"),
            ]
        )

    return strict_po(labels, edges)


permissive_branches = []

for supplier_mode in [None, "after_credit", "after_engineering"]:
    for has_expedite in [False, True]:
        permissive_branches.append(
            permissive_po(
                supplier_mode=supplier_mode,
                has_expedite=has_expedite,
            )
        )

model_permissive = make_xor(permissive_branches)
```

**Behavior deliberately excluded.**

- `Supplier Confirmation` immediately after `Register Order`, before either principal check.
- `Expedite Review` before both principal checks.
- `Expedite Review` after `Approve Configuration`.
- `Supplier Confirmation` after `Approve Configuration`.
- `Release Production` before `Approve Configuration`.
- Multiple occurrences of `Expedite Review` or `Supplier Confirmation`.
- Cases missing `Register Order` or `Archive Case`.

**Known underfitting and overgeneralization risks.**

- The model may admit traces that are operationally possible but organizationally rare, reducing precision.
- It may hide compliance problems by treating missing Supplier Confirmation events as legitimate optional behavior.
- It does not distinguish stocked components from external components; the same no-Supplier branch covers both.
- It may admit Supplier Confirmation after Engineering Review but before Credit Check, which is consistent with D5 but unsupported by the observed log.
- The broad language can make root-cause explanation harder because many branch choices may be consistent with the same visible trace.

# 9. Recommendation and Data-Collection Plan

**Immediate-use recommendation: `model_balanced`.**

The balanced candidate is the best immediate operational model because it:

- fits all 30 observed traces;
- enforces the high-confidence and medium-to-high-confidence rules D1, D2, D3, D4, and D6;
- represents Credit Check and Engineering Review as unordered without falsely claiming proven concurrency;
- allows Supplier Confirmation to be absent because of stocked components or missing events;
- allows Supplier Confirmation to overlap Engineering Review, as observed in V5;
- allows Expedite Review before or after Supplier Confirmation, as observed in V6 and V7;
- avoids the most unsupported generalization in the data: Supplier Confirmation before Credit Check.

**Sensitivity-analysis recommendation: `model_permissive`.**

The permissive candidate should be used as a sensitivity model to test how much conclusions change if D5 is interpreted broadly, allowing Supplier Confirmation after Engineering Review but before Credit Check. Comparing balanced and permissive results can show how much precision and compliance risk is introduced by that assumption.

The conservative candidate should be retained as an audit baseline, not as the main discovery model.

**Data-collection plan to resolve major ambiguities.**

1. **Collect lifecycle timestamps, not only completion timestamps.**  
   For each activity, capture:
   - scheduled start, if available;
   - actual start;
   - last update;
   - completion;
   - event ingestion time.  
   This is essential for distinguishing true concurrency from different sequential orders.

2. **Add the external/stocked component attribute.**  
   This directly resolves whether Supplier Confirmation is legitimately skipped or missing. A case-level field such as `component_type = external | stocked` would allow conditional modeling.

3. **Add a Supplier Confirmation requirement flag.**  
   A field such as `supplier_required = true | false` would separate true optionality from data absence.

4. **Add missing-event indicators or integration health metadata.**  
   If Supplier Confirmation events are known to be lost 5–10% of the time, include:
   - source system;
   - interface status;
   - retry count;
   - event confidence flag.

5. **Capture activity instance identifiers.**  
   This would allow detection of repeated activities, rework, and multiple Expedite Reviews.

6. **Capture trigger information for Supplier Confirmation.**  
   Record whether Supplier Confirmation was requested after Credit Check, after Engineering Review, after both, or by manual intervention.

7. **Capture Expedite Review reason.**  
   Expedite is rare. A reason code would help determine whether it is independent of Supplier Confirmation and whether it should be modeled as an exception.

**Future traces that would be maximally informative.**

- `R, E, S, C, A, P, Z`  
  This would distinguish the balanced model from the permissive model. It would support Supplier Confirmation after Engineering Review but before Credit Check.

- `R, C, E, X, A, P, Z`  
  This would confirm whether Expedite Review can occur without Supplier Confirmation.

- Cases where Credit Check and Engineering Review have overlapping start and completion times.  
  These would help decide whether an AND/concurrency structure is preferable to an XOR of sequential orders.

- External-component cases without Supplier Confirmation.  
  These would confirm missing-event behavior rather than legitimate skipping.

- Stocked-component cases with Supplier Confirmation.  
  These would indicate whether Supplier Confirmation can occur even when not strictly required.

# 10. Uncertainty Statement

|---|---:|---|---|

| `Approve Configuration -> Release Production`. | High, about 0.95 | D2 and all traces agree. | If emergency production release can occur before formal approval, the model would need an exception branch. |

| Credit Check and Engineering Review should be unordered in balanced/permissive models. | Medium, about 0.60 | Both completion orders are observed; S2 suggests parallelism; D7 warns that concurrency is unproven. | If S1 is a hard policy and Engineering-before-Credit traces are logging errors, a sequential `Credit Check -> Engineering Review` model would be preferable. |
