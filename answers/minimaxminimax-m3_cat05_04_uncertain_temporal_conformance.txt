## 1. Normalization Assumptions

**Interval construction (general).** For each recorded timestamp `R`:
1. Convert `R` from the recorded time zone to a UTC clock-time interval by applying the time-zone conversion over the full resolution window, not just at the displayed instant.
2. Add the source-clock offset interval `O` (which is on UTC for HUB/SENSOR, or on local clock time for the others). True UTC = (UTC of R)  offset, where offset  O. Operationally, this widens the interval symmetrically: subtract O[1] (later) and add O[0] (earlier) magnitude after sign correction.
3. Add display/rounding uncertainty before offset correction (since rounding is applied first by the source).

**Clock-offset direction.** Per task definition, `offset = recorded  true`. So `true = recorded  offset`. A +1 s offset means the clock runs fast by 1 s; to recover true time, subtract 1 s. Applied as symmetric expansion of the UTC-clock interval using |O|.

**Rounding semantics.**
- HUB: ±0.5 s.
- OPS-BER, VENDOR-NY, LEGACY-BER: floor-to-minute  displayed `M:SS` represents the minute interval `[M:00, M:59.999]`.
- SENSOR: round to nearest 10 s  displayed `M:SS` represents ±5 s; but the recorded value `08:51:10` is already a multiple of 10 so the true display window is `[08:51:05, 08:51:15)` (boundary rule: half-open at the upper end).
- MOBILE-LON: round to nearest minute  ±30 s.

**Time-zone conversion.**
- HUB, SENSOR already UTC.
- OPS-BER: Europe/Berlin. On 2026-06-01, CEST = UTC+2.
- VENDOR-NY: America/New_York. On 2026-06-01, EDT = UTC4.
- LEGACY-BER: 2025-10-26 02:00–02:59 fall-back fold (CEST  CET). 02:00–02:59 local time can correspond to either UTC 00:00–00:59 (CEST) or UTC 01:00–01:59 (CET). Ingestion order eliminates impossible combos.
- MOBILE-LON: Europe/London. On 2026-06-01, BST = UTC+1.

**DST folds (T-405).** Each LEGACY-BER event produces two possible UTC intervals. Ingestion sequence (Alert < Investigation < Containment) rules out some fold combinations, but residual ambiguity remains. I keep a disjoint union where it cannot be collapsed.

**Inferred starts.**
- T-404: `Investigation_Start` is missing. A signed work record states investigation duration  [18, 25] min, measured from `Investigation_Complete = 10:35:00 UTC` backwards. So feasible start  `[10:10, 10:17] UTC`. Forward direction is not used because containment occurs 20 min after completion (well within duration), so start must precede completion.
- T-407: `Alert_Received` is missing. Only `Alert_Sent = 14:00 UTC`. Network delivery latency  [0, 20] min gives a feasible Alert_Received window of `[14:00, 14:20] UTC`. Receipt-before-investigation-start is a plausible (not logged) causal constraint; I evaluate both with and without it.

**Mobile entry delay (T-406).** "User may have entered the displayed time up to five minutes late." Two interpretations:
- (A) Late *recording*: the actual occurrence happened earlier, and the user back-dated (or the device stamped later than the event). The displayed time already is recorded; the event itself occurred up to 5 min earlier. This shifts occurrence-time earlier.
- (B) Late *entry*: occurrence was correct, only the log is late; in that case no occurrence-time shift is needed.
Because the instruction says "state whether it shifts the record time or your estimate of occurrence time," I treat it as shifting the *occurrence-time estimate earlier by up to 5 min*, in addition to the clock-offset uncertainty. This is the more conservative (S1-protective) reading.

**Activity semantics.** SENSOR events are completion events, so no processing-time adjustment. LEGACY-BER ingestion order rules out cross-fold swaps where, e.g., an event labeled "02:50" in CEST cannot follow one labeled "02:05" in CET after folding that would put the first earlier in absolute time.

def parse_local(s):
    if len(s) == 16:        # floor-to-minute "YYYY-MM-DD HH:MM"
        return datetime.strptime(s, "%Y-%m-%d %H:%M")
    return datetime.strptime(s, "%Y-%m-%d %H:%M:%S")

def resolution_window(local_dt, system):
    """Return (lo, hi) UTC-aware datetimes representing the resolution window
       of the displayed time (without offset). DST fold on LEGACY-BER returns
       two windows."""
    res = RES[system]
    tz  = TZ[system]
    if system == "LEGACY-BER":
        # Local naive dt; test both folds via fixed offset conversions
        lo = local_dt.replace(tzinfo=zoneinfo.ZoneInfo("Europe/Berlin"))
        # Two possible UTC offsets during the fold: +02:00 (CEST) and +01:00 (CET)
        windows = []
        for off in (2, 1):
            utc_lo = lo - timedelta(hours=off) - timedelta(seconds=res)
            utc_hi = lo - timedelta(hours=off) + timedelta(seconds=res)
            windows.append((utc_lo.replace(tzinfo=timezone.utc),
                            utc_hi.replace(tzinfo=timezone.utc)))
        return windows
    utc = local_dt.replace(tzinfo=tz).astimezone(timezone.utc)
    return [(utc - timedelta(seconds=res), utc + timedelta(seconds=res))]

def apply_offset(windows, system):
    """Apply clock offset band: true = recorded - offset; offset in OFFSET[system]."""
    lo_off, hi_off = OFFSET[system]
    out = []
    for a, b in windows:
        # true in [a - hi_off, b - lo_off]
        out.append((a - timedelta(seconds=hi_off),
                    b - timedelta(seconds=lo_off)))
    return out

## 7. Governance Recommendation

1. **UTC-only storage with raw retention.** Store every event timestamp as (a) raw local clock time, (b) source-system clock-offset estimate at event time, (c) UTC equivalent, and (d) resolution/rounding metadata. Never collapse to a single UTC value at ingest.

2. **Per-source clock telemetry.** Each emitting system must publish a continuous offset bound (e.g., NTP offset p95, GPS disciplining status, last calibration). Reject events whose offset band exceeds the source's SLA budget.

3. **Time-zone and resolution metadata as first-class fields.** Carry `tz`, `rounding`, `resolution_seconds`, `dst_fold_status` (values: `none`, `before_fold`, `after_fold`, `ambiguous`). Refuse to ingest `ambiguous` events without an explicit fold choice.

4. **Lifecycle semantics.** Capture activity verbs (`start` vs `complete`) and require paired start/complete events. For SENSOR-style "completion" sources, do not subtract processing time. Provide a separate completion-event flag so consumers can apply appropriate semantics.

5. **DST-fold policy.** Where the local clock does not log which side of a fold a timestamp belongs to, the platform must either (a) refuse to ingest, (b) ingest as a disjoint interval and propagate both branches through SLA evaluation, or (c) require a follow-up corroborating event within a short window to disambiguate. Option (b) is recommended for legal traceability.

6. **Causal identifiers.** Each `Investigation_Start` must carry a `trigger_event_id` referencing the `Alert_Received` it responded to. Without this, S1 cannot be deterministically evaluated (T-407 case).

7. **Mobile entry-delay policy.** Capture both the device-recorded timestamp and an explicit user-asserted "happened-at" timestamp when available. Treat them as a union interval and document the policy choice (does the platform consider the entry-delay as occurrence-time shift, recording-time shift, or both?). The recommended default is occurrence-time shift, because SLAs govern behavior, not logs.

8. **Interval overlap as enforcement.** A SLA **violation** should be enforceable only when the feasible duration interval lies wholly above the cap (CERTAIN_VIOLATION). POSSIBLE_VIOLATION cases should be queued for evidence strengthening rather than auto-escalated, to avoid penalizing legitimate activity on noisy clocks. This avoids penalizing responders for vendor clock errors.

9. **Profile re-estimation cadence.** Recompute the temporal-profile average and standard deviation quarterly. The  choice should be a documented risk policy: =1 for strict process control, =2 for normal monitoring, =3 for exploratory diagnostics. Material profile changes must trigger SLA cap review.

10. **Audit trail.** Every SLA decision (pass / possible / certain / indeterminate) should be retained with its interval evidence, , tolerance additions, and the policy version, so that downstream legal review can re-run the analysis.

11. **Vendor governance.** Sources like VENDOR-NY with no event-level synchronization should not be used for SLA gating without an explicit, separately attested clock-offset envelope; otherwise treat them as informational only.

12. **Ingestion-order vs wall-clock order.** Where ingestion sequence contradicts wall-clock order (T-405), ingest both but flag the discrepancy. The platform should not silently trust either; it must produce a POSSIBLE_VIOLATION or INDETERMINATE classification and demand reconciliation.
