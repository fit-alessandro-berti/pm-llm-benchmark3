## 1. Analytical assumptions

- **Case notion:** a rule assigning directly related events to each object of a selected type. Thus, order flattening creates four cases, item flattening six, package four, delivery three, invoice three, and payment four. I do not infer event membership through O2O relations unless explicitly stated.
- **Convergence:** one real event is copied into multiple flattened cases because it directly relates to multiple objects of the chosen type. Examples are `e13` in both O2 and O3 order cases and `e16` in P2 and P3 package cases.
- **Divergence:** one business object or process instance is represented across several cases, fragmenting its lifecycle. O1, for example, is split over item cases I11/I12 and package cases P1/P2.
- **Copied shared events:** both valid evidence and duplication. Within a case, a copy correctly records that the object participated. Across cases, naïvely summing copies inflates event and DFG frequencies. I would retain event IDs so unique-event and case-occurrence counts remain distinguishable.
- **Permitted transformations:** the baseline uses only direct E2O relations. I would additionally permit a separately labelled propagated variant, such as event  package  item  order or event  payment  invoice  order, but never silently mix it with the baseline. Propagation needs direction, qualifier, path-length, and deduplication rules.
- **Ordering:** timestamps establish order; ties such as `e29` and `e30` are not treated as causal relations across cases. Same-event co-participation is interaction, not precedence.
- **Performance:** elapsed time in a flattened trace measures participation of that case object, not necessarily end-to-end order fulfilment.

## 3. Concrete distortion analysis

1. **Order flattening—cross-order P3 convergence.**  
   `e13` is copied into O2 and O3, creating a `Add Item  Pack Package` transition in both cases. Counting flattened occurrences reports two pack events although one package P3 was packed once. This is harmful for workload counts but informative for measuring two-order exposure to a shared package.

2. **Order flattening—cross-order P4 convergence.**  
   `e14`, `e17`, and `e27` appear in both O3 and O4. The apparent `Pack Package  Dispatch  Confirm Delivery` path is counted twice, even though P4 and D3 each have one lifecycle. This inflates package/delivery frequencies; it is informative only when the metric is “orders affected.”

3. **Package flattening—P3 and P4 hide cross-order composition.**  
   P3 and P4 both yield the same activity variant as ordinary P1/P2: `Pack Package  Dispatch  Confirm Delivery`. An activity-only variant analysis cannot see that P3 packs I21/I31 from O2/O3 and P4 packs I32/I41 from O3/O4. This is harmful for detecting mixed-order handling unless object composition is retained.

4. **Package flattening—split orders look independent.**  
   P1 and P2 become separate cases, concealing that both serve O1. Likewise P3/P4 conceal O3’s split. Package lead-time distributions are valid, but using four package cases as four fulfilment cases overstates independent demand and suppresses split-shipment complexity. The effect is context-dependent.

5. **Package flattening—consolidated D2 is duplicated.**  
   `e16` and `e24` are directly related to both P2 and P3 and therefore copied into both package traces. The edge `Dispatch  Confirm Delivery` is counted twice for one D2 trip, while P2 and P3 appear independent. This is harmful for trip volume and capacity analysis, though useful for package exposure.

6. **Order flattening—D2 creates three-order frequency inflation.**  
   `e16` and `e24` occur in O1, O2, and O3, producing three copies of the D2 dispatch and confirmation. A DFG may count three `Dispatch  Confirm Delivery` relations attributable to one consolidated delivery. It also hides that O1’s D2 portion is P2 while O2/O3 share P3. Harmful for operational event counts; informative for affected-order counts.

7. **Order flattening—consolidated invoicing appears order-specific.**  
   V2’s `e19`, `e22`, and `e25` are copied into both O2 and O3. Each order trace appears to possess an issue-plus-two-payments lifecycle, although there was one joint invoice. Order-level payment frequency becomes four flattened payment occurrences for two actual V2 payments. This is harmful if interpreted as transaction count, but valid for financial exposure.

8. **Invoice flattening—partial payments become apparent repetition.**  
   V2 has `Issue Invoice  Record Payment  Record Payment` via `e19`, `e22`, and `e25`. Without using M2’s `partially_settles` and M3’s `completes_settlement` qualifiers, the self-loop-like `Record Payment  Record Payment` pattern can be labelled duplicate work or rework. It is actually informative instalment behaviour, but only with qualifier-aware interpretation.

9. **Payment flattening—near-singleton lifecycle.**  
   M1–M4 each relate directly to only one `Record Payment` event (`e21`, `e22`, `e25`, `e26`). Every trace is a singleton, so no DFG edge exists and duration is zero or undefined. M2 and M3 no longer appear sequentially connected even though both settle V2. This is strongly harmful for lifecycle analysis but accurate as an event-to-payment registry.

10. **Delivery flattening—artificially short lifecycle.**  
    D1, D2, and D3 each contain only `Dispatch  Confirm Delivery`: for example, D2 runs from `e16` at 11:05 to `e24` at 16:00. The 4h55m value is a transport interval, not the duration from order creation or packing. Calling it fulfilment lead time creates severe downward bias; for carrier SLA analysis it is exactly the intended measure.

11. **Item flattening—commercial lifecycle truncation.**  
    I21’s trace ends at `e24`, while O2 continues through payment `e25` and close `e29`. I32 ends at `e27`, while O3 closes at `e30`. The common item variant suggests completion at delivery and omits invoice/payment/closure entirely. Harmful for end-to-end claims, but useful for physical throughput.

12. **Order flattening—O1’s split shipment becomes repeated operational stages.**  
    O1 contains two packs (`e11/e12`), two dispatches (`e15/e16`), and two confirmations (`e23/e24`). A variant detector may classify this as rework or loops rather than planned split fulfilment. The repetition is genuine order experience, but its cause requires package identities P1/P2.

13. **Order flattening—ordering can imply misleading cross-stream causality.**  
    In O1, `e16` dispatches P2 before `e18` issues V1, while `e23` confirms P1 after payment `e21`; chronological adjacency may produce edges such as `Record Payment  Confirm Delivery`. This does not establish that payment caused delivery confirmation. The edge is useful descriptively but harmful when read as a control-flow dependency.

## 4. Traditional versus object-centric analysis portfolio

I would create five operational flattened logs and one diagnostic log:

- **Order:** commercial elapsed time, order-facing variants, split fulfilment incidence, and time from `Create Order` to `Close Order`. Frequencies must be reported both as flattened occurrences and unique event IDs.
- **Item:** item throughput from `Add Item` to `Confirm Delivery`, comparison of I11/I12 or I31/I32, and item waiting times between packing and dispatch.
- **Package:** pack-to-dispatch and dispatch-to-delivery performance; package-level variants. Cross-order composition must be joined from O2O relations.
- **Delivery:** transport SLA only, especially D1 versus D2 versus D3.
- **Invoice:** issue-to-first-payment and issue-to-complete-payment, with explicit settlement qualifiers.
- **Payment:** retain as a diagnostic singleton log for data-quality and payment-object coverage, not for DFG-based lifecycle discovery.

Questions about **synchronisation and multiplicity** require object-centric structures:

- An **OC-DFG** should distinguish event, unique-object, and total-object frequencies and reveal that one D2 event affects several orders/packages.
- An **OTG** should expose order–item, item–package, package–delivery, order–invoice, and invoice–payment topology.
- An **ET–OT graph** should show that payment objects participate only in `Record Payment`, whereas orders span many event types.
- An **object interaction summary** should identify P3 linking O2/O3, P4 linking O3/O4, D2 linking P2/P3 and O1/O2/O3, and V2 linking O2/O3/M2/M3.
- **Equivalent-execution clustering**, if used, should group objects or sub-OCELs by comparable execution without erasing object identities. For example, P1–P4 have similar activity executions but materially different interaction structures.

Contradictions are expected, not automatically errors. “Six delivery confirmations” in an order-flattened count may mean six order exposures, while the event table contains three unique confirmation events (`e23`, `e24`, `e27`). I would reconcile findings by stating the denominator and unit:

1. unique events;
2. flattened case occurrences;
3. unique participating objects by type;
4. interaction structures such as consolidated deliveries;
5. elapsed time endpoints.

No metric is accepted until its counting unit matches the business question.

## 5. Lead-object decision

**B. Use a primary lead object plus explicitly secondary lifecycles.**

### Decision criteria

1. Coverage of commercial start and completion.
2. Ability to represent customer-facing commitments.
3. Degree of convergence and divergence.
4. Interpretability of performance intervals.
5. Need for secondary objects to explain repeated or shared stages.
6. Risk that a lifecycle is artificially short.

### Primary lead

I select **Order** as the primary lead, with **Item, Package, Delivery, Invoice, and Payment** retained as explicit secondary lifecycles.

### Strongest supporting evidence

Orders are the only listed objects directly connected to the broad sequence from creation through closure. O1 has `e01` through `e28`, and the other orders similarly contain creation, physical handling, invoicing/payment, delivery, and close events. An order view captures customer-relevant split fulfilment: O1 spans P1/P2 and O3 spans P3/P4. Delivery, invoice, and payment flattenings are too narrow to represent end-to-end fulfilment.

### Strongest counterargument

Order flattening has severe convergence. D2’s `e16/e24` is copied across three order cases; V2’s `e19/e22/e25` across O2/O3; P3 and P4 operations across their constituent orders. It can turn one shared execution into multiple apparent executions and conceal the operational object responsible. Therefore “order is primary” must not become “order is the true process.”

### Residual risk

Analysts may still treat order-case DFG frequencies as event workload or interpret chronological adjacency as causality. Order closure also occurs after different secondary milestones without showing whether closure semantics depend on delivery or settlement. The small snapshot amplifies the influence of each shared event.

### Conditions for changing the decision

I would choose **Package** as primary for warehouse/carrier optimisation, **Invoice** for receivables, or reject any primary lead if the programme’s main goal were shared-resource coordination rather than customer-order outcomes. I would also abandon order primacy if larger data showed incomplete order E2O coverage, pervasive cross-order bundling, or no stable order-level start/end semantics.

## 6. PM4Py analysis outline

```python
import pm4py
from collections import Counter

print(ocel)

# API representations can vary slightly by PM4Py version.
events_df = ocel.events
objects_df = ocel.objects
relations_df = ocel.relations

activity_col = "ocel:activity"
object_type_col = "ocel:type"

activity_frequencies = events_df[activity_col].value_counts(dropna=False)
object_type_frequencies = objects_df[object_type_col].value_counts(dropna=False)

print("\nActivity frequencies (unique OCEL events):")
print(activity_frequencies)
print("\nObject-type frequencies:")
print(object_type_frequencies)

object_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

flattened_logs = {}
flattened_dfgs = {}
flattened_skeletons = {}
flattened_activity_occurrences = {}

for object_type in object_types:
    log = pm4py.ocel_flattening(ocel, object_type)
    flattened_logs[object_type] = log

    dfg, start_activities, end_activities = pm4py.discover_dfg(log)
    flattened_dfgs[object_type] = {
        "dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
    }

    flattened_skeletons[object_type] = pm4py.discover_log_skeleton(log)

    # These are flattened case occurrences, not necessarily unique OCEL events.
    flattened_activity_occurrences[object_type] = Counter(
        event["concept:name"]
        for trace in log
        for event in trace
    )

    print(f"\n{object_type} flattened occurrences:")
    print(flattened_activity_occurrences[object_type])
    print(f"{object_type} DFG:")
    print(flattened_dfgs[object_type])

# Object-centric structures retain co-participation and multiplicity.
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
object_interactions = pm4py.ocel_objects_interactions_summary(ocel)

print("\nObject interaction summary:")
print(object_interactions)

# Decision B justifies testing equivalent executions, but clusters must be
# interpreted together with object interactions rather than as semantic cases.
equivalent_execution_clusters = pm4py.cluster_equivalent_ocel(ocel)

analysis_results = {
```

## 7. Sensitivity and validation plan

1. **Copied-event weighting.**  
   Run flattened DFGs with ordinary case-occurrence counts, unique-event counts, and fractional weights `1/k`, where `k` is the number of selected-type objects directly related to an event. Thus `e16` receives weight 1 per unique event, 3 as order exposure, or 1/3 in each of O1/O2/O3. Check whether dominant edges change.

2. **Direct versus propagated E2O.**  
   Compare the supplied direct baseline with a separately constructed variant propagating along selected O2O paths. For example, invoice/payment events could be propagated to items via V2  O2/O3  items, and delivery events to orders via D2  P2/P3  items  orders. Report newly introduced relations and path rules; do not treat them as recorded facts.

3. **Change the lead object.**  
   Recompute variants and durations under Order, Item, Package, Delivery, Invoice, and Payment. In particular, compare O1’s create-to-close duration with I11/I12 physical durations, P1/P2 logistics durations, and D1/D2 transport durations. Differences should be explained by endpoints rather than ranked as correctness.

4. **OC-DFG frequency semantics.**  
   Compare event frequency, unique-object frequency, and total-object participation. For `e16`, one event, one delivery D2, two packages P2/P3, three orders O1/O2/O3, and three listed items answer different questions. Validate every reported frequency against the intended unit.

5. **Qualifier-aware payment analysis.**  
   Analyse V2 once using only activity labels and once using `partially_settles` versus `completes_settlement`. Confirm that `Record Payment  Record Payment` is interpreted as staged settlement, not automatically as rework.

6. **Interaction-stratified performance.**  
   Compare ordinary packages P1/P2 with cross-order P3/P4 and compare single-package deliveries D1/D3 with consolidated D2. With this tiny sample, findings are descriptive, but the test checks whether consolidation systematically changes dispatch or confirmation intervals.

7. **Unique-event reconciliation.**  
   For every flattened activity count, map copies back to original event IDs. Specifically verify `e13`, `e14`, `e16`, `e17`, `e19`, `e22`, `e24`, `e25`, and `e27`. Any discrepancy must be labelled as exposure inflation, propagation, or implementation error.

8. **Lifecycle endpoint robustness.**  
   Compare order completion at last delivery, complete settlement, and `Close Order`. O2/O3 share settlement completion `e25` but close separately at the same timestamp through `e29/e30`; O4 pays before D3 confirmation. This tests whether performance conclusions depend on an unstated definition of completion.
