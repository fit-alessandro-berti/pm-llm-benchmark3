*   **Semantics:** Deviations beyond `mean + 2*SD` trigger a warning, not a hard failure. This aligns with R12's "normative enough to flag but not automatically reject" statement.
*   **Design Choice:** Temporal checks run after control-flow checks. A case can be structurally valid but temporally suspicious.

# 9. Contradictions, Redundancies, and Blind Spots

**Contradictions:**
*   **R5 vs R6:** The core conflict. Enforcing R5 as the control flow makes any case violating R5 (like T6) a hard failure, even if R6 permits it. The Resource layer cannot resolve this without the `emergency` attribute.
*   **R3 vs ProcessTree:** ProcessTrees generally do not support loops. The backbone model approximates the loop as a linear sequence, which fails to capture the "non-blocking" nature of R3. DECLARE handles this correctly.

**Redundancies:**
*   **R1/R8:** Both `never_together` in Log Skeleton and `noncoexistence` in DECLARE enforce similar exclusions.
*   **R4/R5:** Both use `precedence`. The Log Skeleton `always_before` duplicates the ProcessTree `edges`.

**Blind Spots:**
*   **Missing Attributes:** R6 requires an "emergency" flag. Without it, the model cannot distinguish between a policy breach and an authorized exception.
*   **Timestamp Limitations:** R12 relies on timestamps. If timestamps are missing or inaccurate, temporal checks fail or become vacuous.
*   **Vacuity in Declarative Rules:** `support` and `confidence` in DECLARE are metadata. If a rule has `support=0` (not observed in training), it might still be enforced as `confidence=1.0` if manually set, leading to false positives.

# 10. Deployment Recommendation

**Canonical Representation:**
*   **Procedural Backbone:** Use the **ProcessTree** defined in Section 3 as the primary executable model. It provides the best visualization of the "Happy Path" and decision points.
*   **Authoritative Policy Layer:** The **DECLARE Model** (Section 4) serves as the authoritative constraint layer. It captures the non-blocking loops (R3) and mutual exclusions (R1, R8) that ProcessTrees struggle with.

**Conformance Check Order:**
1.  **Resource/Data Layer:** Run R9 checks first. If resource segregation fails, stop immediately (critical security risk).
2.  **Procedural/DECLARE/Log Skeleton:** Run control-flow checks (R1, R2, R4, R5, R7, R10). These are hard constraints.
3.  **Temporal Profile:** Run R12 checks last. These are recommendations/warnings.

**Surface Contradictions:**
*   If a case fails the Resource Layer but passes Control Flow (e.g., T4), flag as **"Segregation of Duties Breach"**.
*   If a case fails Control Flow (R5) but Resource Layer flags "Emergency" (if attribute existed), flag as **"Policy Exception: Emergency Activation"**.
*   If a case fails Temporal Profile, flag as **"Warning: Delayed Compliance"**.
*   **T6 Specific:** Since the log lacks the emergency flag, the system must return a **"Hard Fail: Legal Opinion Missing"** with a note that "Emergency status unverified". This prioritizes compliance safety over operational flexibility.
