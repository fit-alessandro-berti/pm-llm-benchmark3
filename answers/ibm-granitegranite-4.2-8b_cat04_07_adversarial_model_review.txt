# 7. Third Alternative

**Goal:** A lightweight, procedurallystructured backbone that enforces mandatory checks, optional Supplier Review (conditioned on an external flag), optional Expedite Review (must follow mandatory checks), exactlyone approval, and a correction mechanism that repeats *only* the checks that could be affected. Because the controlflow log lacks an “affectedcheck” attribute, we introduce a minimal, explicit correction field (`affected_checks`) that the user (or process operator) supplies when issuing a `Correct Dossier`. This keeps the model simple and transparent while remaining compliant.

### 1. Compact formal description (procedural backbone + constraints)

```
Phase0: Register Dossier (event carries attribute `is_external`  {true, false})
Phase1 (mandatory): perform BOTH Credit Check AND Technical Review in any order.
        - If a Correct Dossier occurs before Phase1 completes, repeat only the checks listed in `affected_checks` (subset of {Credit Check, Technical Review}).
Phase2_opt (optional): Supplier Review – allowed ONLY if `is_external == true` and occurs after Phase1 finishes.
Phase3_opt (optional): Expedite Review – allowed ONLY after Phase1 finishes (regardless of external flag) and before approval.
Phase4 (approval): exactly ONE of Manager Approval or Auto Approval, chosen by policy rule (e.g., Manager for highvalue orders, Auto otherwise). Must occur after Phase1 and after any optional Phase2/Phase3.
Phase5: Release Order (final).

Correction semantics:
    - `Correct Dossier` may appear at most once before approval.
    - It introduces a field `affected_checks` (string list, e.g., "Technical Review" or "Credit Check, Technical Review").
    - Upon seeing `Correct Dossier`, the process returns to the state *immediately after Register Dossier* and resumes Phase1, but only repeats the checks in `affected_checks`. All alreadycompleted checks not in `affected_checks` are assumed valid and do not need reexecution.
    - After repeating the affected checks, the process proceeds normally (Phase2_opt, Phase3_opt, approval, release). No check may be repeated without a preceding `Correct Dossier` (enforced by the backbone).

Policy constraints encoded directly:
    - Credit Check  Technical Review must appear (in either order) before any approval transition.
    - Supplier Review  (is_external == true)  after Phase1.
    - Expedite Review  after Phase1 (optional) and before approval.
    - Exactly one of Manager Approval or Auto Approval occurs before Release Order.
    - No approval transition may appear before Phase1 completes.
```

```python
    """
    trace: list of events (pm4py.event objects with .attributes dict)
    event_attributes: dict mapping event label -> attribute dict (e.g., {"Register Dossier": {"is_external": True}})
    Returns True if trace conforms to policy including correction.
    """
    # Locate Register Dossier (first event) and Correct Dossier
    reg_idx = next(i for i, e in enumerate(trace) if e.label == "Register Dossier")
    corr_idx = None
    for i, e in enumerate(trace):
        if e.label == "Correct Dossier":
            corr_idx = i
            break
    
    if corr_idx is None:
        # No correction  enforce mandatory checks before approval
        # Find first approval (Manager or Auto)
        for i, e in enumerate(trace):
            if e.label in ("Manager Approval", "Auto Approval"):
                # Ensure both Credit Check and Technical Review appear before i
                cc_seen = any(ee.label == "Credit Check" for ee in trace[:i])
                tr_seen = any(ee.label == "Technical Review" for ee in trace[:i])
                if not (cc_seen and tr_seen):
                    return False
                # Supplier Review only if external
                if corr_idx is None and any(ee.label == "Supplier Review" for ee in trace[:i]):
                    ext = get_external(trace[reg_idx])
                    if not ext:
                        return False
                # Expedite Review only if after mandatory checks (already enforced by net)
                break
        return True
    
    # Correction present before approval
    # Extract affected_checks list from Correct Dossier attributes
    affected = event_attributes[trace[corr_idx].label]["affected_checks"]  # e.g., ["Technical Review"] or ["Credit Check", "Technical Review"]
    affected_set = set(affected)
    
    # Find the index of the first approval after correction
    for i, e in enumerate(trace):
        if e.label in ("Manager Approval", "Auto Approval"):
            approval_idx = i
            break
    
    # Reevaluate mandatory checks that appear after correction but before approval:
    # We require that every check in {Credit Check, Technical Review} that occurs
    # after the correction and before approval must belong to affected_set.
    # If a check not in affected_set appears after correction, reject.
    for i, e in enumerate(trace):
        if corr_idx < i < approval_idx and e.label in ("Credit Check", "Technical Review"):
            if e.label not in affected_set:
                return False
    
    # Supplier Review and Expedite Review must obey same conditional rules as normal flow
    ext = get_external(trace[reg_idx])
    for i, e in enumerate(trace):
        if e.label == "Supplier Review":
            if not ext:
                return False
        if e.label == "Expedite Review":
            # must appear after mandatory checks (i.e., after both Credit and Tech have been seen at least once before correction or after correction if they are affected)
            # simple check: ensure no Expedite Review occurs before the first completion of mandatory checks (both seen)
            # we compute first index where both CC and TR have appeared (ignoring correction)
            seen_cc = any(ee.label == "Credit Check" for ee in trace[:i])
            seen_tr = any(ee.label == "Technical Review" for ee in trace[:i])
            if not (seen_cc and seen_tr):
                return False
    
    # Exactly one approval before release
    approvals = [e.label for e in trace if e.label in ("Manager Approval", "Auto Approval")]
    if len(approvals) != 1:
        return False
    
    return True
```

### 5. Limitations caused by missing attributes

1. **External/internal flag** – The log does not record whether an order is externally sourced. We rely on the operator to attach `is_external` to the Register Dossier event (or to annotate the trace). If the flag is missing, the validator defaults to internal (`false`) and will reject any Supplier Review that appears, which is conservative but safe. In practice, a simple rule (“if Supplier Review is present, mark order as external”) could be used, but that would sometimes incorrectly flag internal orders that legitimately require Supplier Review (if external definition expands). Therefore we keep the flag explicit.

2. **Affectedcheck attribute** – The log lacks a field indicating which checks are impacted by a correction. We introduce `affected_checks` as part of the `Correct Dossier` event (a short list supplied by the operator). If operators cannot determine this list (e.g., due to time pressure), the safest default is to repeat both Credit Check and Technical Review. The validator accepts the default automatically when `affected_checks` is empty or unspecified. Thus the model remains usable even with incomplete information, while still satisfying P7 (no repeat without correction).

3. **Silent repetition** – The net uses explicit transitions; there are no silent transitions for checks, which avoids hidden repeats. The validator explicitly checks for duplicate mandatorycheck events without a preceding `Correct Dossier`, mitigating silentrepeat pathology.

4. **No enumeration of branches** – By using a single backbone net plus a small validator, we avoid enumerating all variants (unlike ModelC). This reduces maintenance and duplicatelabel issues while still allowing optional Supplier Review and Expedite Review in any order after mandatory checks.

# 11. Dissenting View

> *A concise rebuttal (180words):*  
> While the third alternative addresses most policy violations, it introduces an extra runtime validator and requires operators to record `is_external` and `affected_checks`. In environments where trace metadata is frequently incomplete or collected manually, this extra burden could lead to underreporting (e.g., operators omit `is_external` for external orders, causing Supplier Review to be rejected even when legitimate). Moreover, the validator’s “duplicatecheck without correction” rule may flag a legitimate rerun of a check after a minor amendment that does not truly affect the original assessment, resulting in falsenegative rejections during rapid correction cycles. The validation plan’s reliance on a curated negative suite assumes that negative traces can be authored without exhaustive enumeration; in practice, eliciting all subtle violations (e.g., partial correction affecting only one check) may be difficult. Therefore, for teams that prioritize speed of iteration over perfect conformance, ModelS’s permissiveness might still be preferable, provided a lightweight manual audit step (a onepage checklist) is added to catch the few critical violations (Expedite before checks, missing mandatory checks). The third alternative should be adopted cautiously, with a fallback to manual review for borderline correction cases.

> *What additional evidence would change the decision:*  
> 1. Empirical measurement showing that operators consistently fill `is_external` and `affected_checks` with 90% accuracy in daytoday use. 2. Validation results from the actual operational logs demonstrating negative precision 0.95 and stakeholder comprehension 4.0 after minimal training. 3. A controlled A/B test where `model_third` + validator versus ModelS (with a simple checklist) is used for compliance review; if the validator rejects fewer legitimate urgent external orders than the checklist misses violations, then `model_third` gains acceptance. If the validator causes unnecessary corrections (i.e., >20% of valid corrections are rejected), then ModelS with a lightweight checklist remains preferable for rapid exploration.
