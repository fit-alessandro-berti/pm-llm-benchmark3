Consequences derived from the marking: (i) from the reachable marking `{p_analysis:1, sink:1}` there is no sequence reaching the exact final marking, so the "option to complete properly" property fails on that branch; (ii) `{p_analysis_done:1, sink:1}` is a reachable dead marking; (iii) the reachable marking `{p_analysis:1, sink:1}` is an improper completion (final token plus an extra token). The net is therefore **not sound**, although it *is* a workflow net.

**Second counterexample (analysis completed first — shows the defect is not an ordering artefact).**

- after `t_join_waived`: `{p_analysis_done:1, p_decision:1}` — the waiver join consumed only `p_waived`, leaving the completed-analysis token behind;

# 4. Minimal-Repair Alternatives

**Edit-cost model (explicit).** One unit = one added arc, one removed arc, one added place, one removed place, one added transition, one removed transition. Label/identifier edits cost 0 units but are listed explicitly (they do not change reachability or firing). Modifications are counted on the net's structure, not on lines of code. Cost is compared under this unit model; "minimal" means *no cheaper edit sequence exists that satisfies the repair's stated constraint family*.

| Repair | Exact edits | Edit cost | Preserved intent | Changed behavior | New risk |
|---|---|---|---|---|---|
| **A. Proper two-input waiver join** (selected) | Add arc `p_analysis_done  t_join_waived`. No removals, no new places/transitions, no label changes | **1** (1 added arc) | Mandatory analysis on **both** routes; standard vs. waiver remain distinguishable via `p_review_done` vs. `p_waived` and via two separate joins | `t_join_waived` becomes enabled only after `t_analyze`; `t_authorize` can no longer fire before analysis; both routes reach `fm` exactly | Two unlabelled joins still converge on `p_decision`; the structure itself would not prevent both joins from becoming enabled under a future edit (duplicated `p_decision`/`sink` tokens). Needs an invariant/regression test, not only structural checks |
| **B. Collapse the waiver into the normal synchronization** | Remove arc `t_waive_review  p_waived`; add arc `t_waive_review  p_review_done`; remove arcs `p_waived  t_join_waived` and `t_join_waived  p_decision`; remove transition `t_join_waived`; remove place `p_waived` | **5** (1 added arc, 2 removed arcs, 1 removed transition, 1 removed place) | Mandatory analysis retained (still enforced by `t_join_normal`); standard/waiver choice remains visible in the transition `t_waive_review` vs. `t_standard_review` | Both outcomes synchronize at `t_join_normal`; the waiver-specific place and join disappear, so the waiver is no longer observable in the marking (only in the event log) | Largest structural churn of the three; loss of a persistent waiver marker (audit/analytics relying on `p_waived` break); higher regression risk |
| **C. Make analysis optional under waiver — explicit policy change** | Add arc `p_analysis  t_join_waived` and relabel `t_join_waived` as "Waiver Without Analysis (analysis skipped)"; add transition `t_join_waived_done` labelled "Waiver With Completed Analysis"; add arcs `p_waived  t_join_waived_done`, `p_analysis_done  t_join_waived_done`, `t_join_waived_done  p_decision` | **5** (4 added arcs, 1 added transition) | Standard route still requires analysis (`t_join_normal` unchanged) | **Policy change:** on the waiver route `t_authorize` may occur without `t_analyze`; the pending `p_analysis` token is consumed by a "skip" join | A transition silently discards the pending analysis token — exactly the kind of hidden bypass the business wants to prevent; two waiver joins create confusion; only defensible if governance explicitly approves optional analysis under waiver |

**Minimality justification.**

- **A is globally minimal.** With zero edits the counterexample in §3 shows a reachable marking from which `fm` cannot be reached and a reachable dead marking, so no zero-cost repair exists. Adding the single missing input arc `p_analysis_done  t_join_waived` makes `t_join_waived` a proper AND-join; both branches then converge on `p_decision` only after analysis completion, each branch consumes `p_analysis_done` exactly once, and every reachable marking can reach `{sink:1}` exactly. No removal is needed, so cost 1 is minimal.
- **B is minimal within its family** ("reuse the existing normal AND-join, keep the net a workflow net"). Re-targeting the waiver output costs one removal plus one addition; the old waiver join then has no live input, so its two arcs must be removed, and both `t_join_waived` and the now-unreachable place `p_waived` must be deleted — otherwise the place/transition would no longer lie on a source-to-sink path and the workflow-net check would fail. Any variant that keeps `p_waived`/`t_join_waived` alive needs an extra transition or extra arcs and is therefore not cheaper under this cost model.
- **C is minimal within its family** ("analysis genuinely optional under waiver"). A single join cannot consume *either* the pending token (`p_analysis`) or the completed token (`p_analysis_done`): adding both as inputs makes it an AND of both and deadlocks the "analysis already done" case, while adding only `p_analysis` orphans `p_analysis_done` (the defect pattern of §3). Hence two mutually exclusive waiver exits are needed: one extra input arc on the existing join plus one new transition with three arcs = 5 units.
- **Tie:** B and C both cost 5. The tie is an artefact of the chosen unit weights (B removes structures, C adds them); they are not equivalent — B preserves the policy, C changes it. A is strictly cheaper (1) and is the only global optimum.

from pm4py.objects.petri_net.utils import petri_utils

def marking_text(marking):
    """Human-readable, non-zero marking."""
    items = sorted(((p.name, c) for p, c in marking.items() if c > 0),
                   key=lambda kv: kv[0])
    return "{" + ", ".join(f"{name}:{c}" for name, c in items) + "}"


def marking_key(marking):
    """Hashable representation used for visited-set bookkeeping."""
    return tuple(sorted((p.name, c) for p, c in marking.items() if c > 0))


def _apply(net, trans, marking):
    """Fire `trans` on a COPY of `marking` (PM4Py helper, with manual fallback)."""
    try:
        return petri_utils.apply_transition(trans, net, Marking(marking))
    except TypeError:  # pragma: no cover - alternative PM4Py signature
        out = Marking()
        for p, c in marking.items():
            out[p] = c
        for p in trans.in_arcs:
            out[p] = out.get(p, 0) - 1
        for p in trans.out_arcs:
            out[p] = out.get(p, 0) + 1
        return out


def fire_named(net, marking, transition_name):
    """Fire a transition BY NAME, refusing to fire a disabled transition."""
    enabled = pm4py.get_enabled_transitions(net, marking)
    enabled_names = sorted(t.name for t in enabled)
    if transition_name not in enabled_names:
        raise ValueError(
            f"transition '{transition_name}' is not enabled; "
            f"enabled transitions: {enabled_names}; marking={marking_text(marking)}"
        )
    trans = next(t for t in enabled if t.name == transition_name)
    result = _apply(net, trans, marking)
    cleaned = Marking()  # drop zero-token entries so equality with fm is exact
    for p, c in result.items():
        if c > 0:
            cleaned[p] = c
    return cleaned


def run_sequence(net, marking, sequence, title):
    """Fire a sequence, printing the marking and enabled set after each step."""
    current = marking
    print(f"--- {title} ---")
    print(f"step 0 (initial): {marking_text(current)}")
    for name in sequence:
        current = fire_named(net, current, name)
        enabled = sorted(t.name for t in pm4py.get_enabled_transitions(net, current))
        print(f"after {name}: {marking_text(current)} | enabled={enabled}")
    return current


def reachable_from(net, marking):
    """All markings reachable from `marking` (BFS over enabled transitions)."""
    seen = {marking_key(marking): marking}
    frontier = [marking]
    while frontier:
        current = frontier.pop(0)
        for trans in pm4py.get_enabled_transitions(net, current):
            nxt = fire_named(net, current, trans.name)
            key = marking_key(nxt)
            if key not in seen:
                seen[key] = nxt
                frontier.append(nxt)
    return seen


def audit(net, initial_marking, final_marking):
    """Model-based checks complementing PM4Py's soundness routine."""
    states = reachable_from(net, initial_marking)
    final_key = marking_key(final_marking)
    dead = [m for m in states.values()
            if marking_key(m) != final_key
            and not pm4py.get_enabled_transitions(net, m)]
    final_plus_extra = [m for m in states.values()
                        if marking_key(m) != final_key
                        and all(m.get(p, 0) >= c
                                for p, c in final_marking.items() if c > 0)]
    cannot_complete = [m for m in states.values()
                       if final_key not in reachable_from(net, m)]
    return {
        "reachable_markings": len(states),
        "dead_markings": len(dead),
        "final_plus_extra": len(final_plus_extra),
        "cannot_reach_exact_fm": len(cannot_complete),
    }

# 7. Repair Trade-Offs and Residual Risks

**Distinguishability of the two review outcomes.** In Repair A (selected) the outcomes remain distinguishable both in the log (`t_standard_review` vs. `t_waive_review`) and in the model state (`p_review_done` vs. `p_waived`), and each has its own join. In Repair B only the transition distinguishes them; the waiver-specific place disappears, so any downstream analytics, conformance checks or case files that read `p_waived` would need to be migrated to the event log. In Repair C there are two waiver exits, which weakens the distinction further.

**Silent transitions, duplication and confusion.** `t_split`, `t_join_normal` and `t_join_waived` carry no visible label. In the original, the single token in `p_review` makes the two review alternatives mutually exclusive, so only one join can fire and only one `p_decision`/`sink` token is produced. The repaired model preserves that property, but the property is *emergent*, not enforced: nothing forbids a future edit that would make both `p_review_done` and `p_waived` reachable, in which case both joins could fire and two `p_decision` tokens (and two `sink` tokens) would result. Mitigations: give the joins meaningful labels, or use separate decision places per branch and join them (a further, non-minimal change). Repair C is the most exposed, because its "skip analysis" transition consumes the pending analysis token without performing the analysis — an explicit, but easily overlooked, bypass.

**Soundness is not business conformance.** A repaired net that allowed waiver without analysis (Repair C) would also be *sound* while violating the stated policy. Conversely, soundness only asserts: a proper completion exists, no reachable dead markings, and no improper final markings. The mandatory-analysis rule is a semantic property that must be verified by trace-level conformance tests and by an explicit invariant, not by the soundness flag.

**Regression tests (positive).** (1) Standard route: `t_register  t_split  t_analyze  t_standard_review  t_join_normal  t_authorize`, ending exactly in `{sink:1}`. (2) Waiver route: `t_register  t_split  t_waive_review  t_analyze  t_join_waived  t_authorize`, ending exactly in `{sink:1}`. (3) Both orderings of `t_analyze` and the review transition on each route. (4) Each complete trace contains exactly one `t_authorize`, exactly one `t_analyze`, and exactly one decision-producing join.

**Regression tests (negative).** (1) On the waiver route, `t_authorize` and `t_join_waived` must be *disabled* while `p_analysis_done` is absent — assert an exception from the enabledness-checking helper rather than a silent token move. (2) `t_join_normal` must be disabled on the waiver route (no `p_review_done`). (3) No reachable marking may equal `{sink:1}` plus extra tokens, and no reachable marking may be a dead end other than `{sink:1}`. (4) No trace may contain `t_authorize` before an `t_analyze` occurrence.

**Detecting an accidental bypass of mandatory analysis.** Monitor the event stream with the invariant: every occurrence of `t_authorize` must be preceded by exactly one `t_analyze` in the same case and the completed-analysis token must have been consumed by an AND-join. Structurally, check that no transition other than the (labelled, policy-approved) skip transition consumes `p_analysis` without producing `p_analysis_done`, and that `p_analysis_done` is consumed only by a join that also requires a review-outcome token. A lightweight model-based check — for every reachable marking, `t_authorize` enabled  analysis completed — should be part of the CI pipeline alongside `check_soundness`.

# 8. Final Recommendation

**Deploy Repair A** (add the single arc `p_analysis_done  t_join_waived`). It is the globally minimal edit (cost 1), preserves the business policy exactly — analysis remains mandatory on both the standard-review and waiver routes — and keeps the two review outcomes distinguishable in both the log and the model state (`p_review_done` vs. `p_waived`, two separate joins). It removes both symptoms at once: `t_authorize` can no longer fire before `t_analyze`, and the analysis token can no longer be stranded on the waiver route, so both routes terminate in exactly `{sink:1}`.

**Fallback: Repair B** (re-target `t_waive_review` to `p_review_done` and delete the waiver-specific join and place; cost 5) if the organisation prefers a single synchronization point and is willing to rely on the event log for waiver auditing. It is equally sound and equally policy-preserving, but it is a larger structural change, removes a marker that downstream tooling may consume, and therefore carries more regression risk; it should only be taken with an explicit migration of waiver-related checks.

**Not recommended without governance approval: Repair C**, because it deliberately makes analysis optional under waiver and hides that decision in a transition that discards the pending analysis token.

Before deployment, add the trace-level regression suite and the "authorization implies analysis completed" invariant from §7; a green `check_soundness` result alone does not demonstrate business-rule alignment.
