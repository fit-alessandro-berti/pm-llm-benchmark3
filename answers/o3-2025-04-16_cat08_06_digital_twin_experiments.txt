1. Model scope and state variables
• System boundary  
  – Starts when an application is uploaded to the portal and ends when a permit is issued / rejected or the applicant withdraws.  
  – External actors (applicant, neighborhood, council) are included only through the delays they impose; their internal work is not modelled.  

• Main entities  
  – Case (permit application) with attributes: case_id, case_type, architect_id, district, application_value, requires_fire, requires_environment, requires_public_notice, submission_week, objection_flag, appeal_flag, rework_counter.  
  – Activity instance with: activity_name, planned_start, planned_end, actual_start, actual_end, assigned_resource.  
  – Resource pools: clerks, planners, fire_reviewers, env_reviewers, inspectors, legal_officers, system.  
  – Calendars: per-resource weekly calendars + holiday calendar + council-meeting calendar.  
  – Spatial cells: districts (D1–D5) hold inspection-travel times and batching queues.  

• Global state variables (observable during simulation step)  
  – Clock (simulation time, datetime).  
  – Arrival intensity (t) (piece-wise non-stationary Poisson modified by Monday multiplier and architect burst process).  
  – Resource diaries: for each human resource, the next free time slot.  
  – Queues per activity, e.g. Q_Planning, Q_Fire, … (FIFO except when batching or ageing rules apply).  
  – Batch buffer for inspections keyed by (district, architect_id, calendar week).  
  – Public-notice register with expiration date, objection probability, and residual days.  
  – KPI collectors (sojourn time per case, activity utilisation, rework counts, backlog, fairness indexes).  

• Cross-case dependencies  
  – Architect bursts: when one application from architect_id a arrives, a correlated compound Poisson draws the number of additional applications in the same week.  
  – Inspection batching: cases in the same district and with the same architect can be grouped; grouped inspections share travel time and start together.  
  – Shared resource queues couple all concurrent cases.  
  – Policy D2 dynamically changes the routing of qualified Simple renovation cases; that choice influences the inspection queue length of the remaining cases.  

2. Parameter-estimation plan
Arrivals  
 1. Import log with pandas, format with pm4py.format_dataframe.  
 2. Aggregate submissions by day; use STL or Prophet to separate trend, seasonality (monthly, week-day) and residuals.  
 3. Fit a non-homogeneous Poisson process (t); Monday multiplier is exp(_Monday).  
 4. Fit a hurdle model for architect bursts: P(burst | architectTop20) and Negative-Binomial size.  

Routing / branching  
 1. Extract directly-follows graph (DFG) with pm4py.algo.discovery.dfg.  
 2. Estimate branching probabilities conditional on attributes with gradient-boosted trees; fall back to unconditional frequency if support < 50 cases.  
 3. For optional activities with missing data (Fire, Env, Public notice) use logistic regression on requires_* flags and district.  

Service times  
 1. Where start & end available: service = end-start.  
 2. Else: infer service time from activities with similar resource and activity_name that do have both stamps; estimate log-normal (,).  
 3. Keep empirical distribution via kernel density and sample by inverse CDF to preserve heavy tails.  

Waiting / inter-start time  
 1. Waiting = start(activity i) – end(activity i-1 in same case).  
 2. Regress waiting on queue length proxy (#events/day) and resource utilisation at that date; use this to validate that calendar constraints reproduce the same queuing times.  

Rework  
 1. Detect loops in each case trace.  
 2. Estimate probability of re-entry at Planning, Inspection, Legal using event positions; fit geometric distribution for number of loops.  

Calendars and resources  
 1. HR roster table (given)  pm4py.resources.calendar objects.  
 2. Public-holiday list from national calendar library.  
 3. Council-meeting weeks flagged in a Pandas Series; Legal capacity set to 15 % during those weeks.  

Cross-case dependencies  
 1. Architect-based clustering: mine temporal proximity (same architect_id within 5 days) and fit copula to arrival times.  
 2. Inspection batching probability derived from historical ratio (#batched visits)/(#eligible sets).  

Tools  
 – pm4py for log parsing, DFG, process-tree handling, conformance checks.  
 – pandas, statsmodels/Prophet for time-series.  
 – SciPy for distribution fitting.  
 – Simulation engine can be SimPy, salabim, or bespoke; PM4Py remains the process-mining layer.  

3. Assumptions
Arrivals  
 • After de-seasonalisation residuals are Poisson; architect bursts captured via compound Poisson.  
Service times  
 • Log-normal tails; pre-emptions ignored (rare).  
Routing  
 • Branching depends only on case attributes available at start; applicant choices after submission (e.g. adding fire sprinklers) not modelled.  
Resources / calendars  
 • No sick-leave; holidays and council weeks already reduce capacity.  
Rework  
 • Each loop is independent conditioned on case type.  
Applicant / third-party response  
 • Response delays are exogenous; municipality cannot accelerate them (except D1 & D9).  
Cross-case dependencies  
 • Only architect batching and inspection batching are modelled; other forms (e.g. shared neighbourhood objections) aggregated into longer Public-notice durations.  
Non-stationary demand  
 • Trend over 18 months assumed flat; only seasonal patterns and bursts included.  
Missing data  
 • Start time gaps filled by sampling from peer activities; bias assumed negligible after calibration.

5. Warm-up, replications, and uncertainty treatment
• Horizon: 3 simulation years so that two full seasonal cycles are captured.  
• Warm-up: first 90 simulated days discarded using moving-average of WIP until steady.  
• Replications: 30 independent runs per scenario, common random numbers across scenarios (same seeds) to reduce variance.  
• Random streams: NumPy PCG64 with seed set (base_seed + run_id).  
• Output analysis: 95 % confidence intervals from batch means; for heavy-tailed KPIs also report 90-th percentile with BCa bootstrap.  
• Sensitivity: Morris screening on key uncertain inputs (rework prob, objection extension, env-review capacity).  
• Heavy tails: if p-value <0.05 for fitted log-normal vs empirical Kolmogorov–Smirnov, sample from empirical directly (bootstrap).  

6. Validation strategy
1. Face validation with domain experts (walk through token animation of selected cases).  
2. Replay validation: feed historical arrivals for 6 months and compare activity start/end distributions (PM4Py alignments).  
3. Distribution fit: K-S tests on per-activity service and waiting times between simulated and real data.  
4. Resource utilisation: compare simulated %busy per resource type with HR timesheets.  
5. Bottleneck validation: cross-check queue lengths on Mondays and peak months.  
6. Out-of-sample: hold-out last 3 months of log; simulate with learned parameters and compare KPIs.  

7. Decision criteria
Primary  
 • Median total throughput time per case type (goal < 30 d Simple, < 60 d New residential, < 90 d Commercial, < 150 d Complex).  
 • 90-th percentile throughput time (tail control).  
 • SLA compliance: %cases decided within statutory limit.  

Secondary  
 • Resource utilisation range 60-85 % (avoid chronic overload/idleness).  
 • Rework loops per 100 cases.  
 • Backlog at month-end.  
 • Fairness: median duration spread across districts < 10 d.  
 • Robustness: KPI deterioration < 15 % between nominal and stress S1/S2.  
Intervention chosen if it meets primary goals and improves at least two secondary metrics without violating fairness/robustness.
