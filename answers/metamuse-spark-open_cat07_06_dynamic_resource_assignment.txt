# 1. Objectives and constraints
This is a multi-objective assignment problem. There is no single optimum that maximizes throughput without unacceptable side-effects. The policy must make explicit trade-offs.

**Optimization objectives (to balance, not maximize individually):**
- **Throughput and flow:** minimize waiting + service time per case, enable batching where safe.
- **Quality / error reduction:** minimize rework and appeal after assignment.
- **Workload fairness and sustainability:** distribute load, protect people with high overtime risk, avoid burnout.
- **Skill development:** create safe stretch opportunities aligned to documented training priorities.
- **Resilience and continuity:** preserve case ownership where valuable, avoid creating single points of failure in scarce skills (Security, Approval).

**Hard / Safety-Compliance constraints (never violated, logged as deviations if forced):**
- S1 Skill allowlist: `required_skill -> minimum skill`. Security Review: skill 3, or skill 1-2 ONLY with explicit supervision by R7_Gita or R8_Hugo. Skill 0 in Security is never executor, even supervised. Final Approval: skill 2-3 to finalize; skill 1 may *prepare* but not finalize. `0 = not allowed` for any activity.
- S2 High-priority protection: No `priority = high/urgent` assigned to skill <2 unless supervised pair is logged and supervisor is skill 3. SLA `urgent` cases require supervisor co-sign if trainee involved.
- S3 SLA risk gate: Cannot deliberately increase waiting for `SLA remaining < 8h` via handover unless safety requires it (e.g., skill 0 owner).
- S4 Auditability: Every assignment writes `assignment_reason, reassignment_count, workload_snapshot, handover_cost_band` to log. Reassignment >2 must trigger review.

**Soft / Preference constraints (trade-offs to explain and monitor):**
- P1 Workload fairness: No resource >4 new assignments per batch. Avoid `overtime risk = high` (R2_Bruno, R4_David, R9_Iris) unless urgent SLA and no safer alternative with hours_remaining covering expected service time.
- P2 Continuity: For `case_complexity >0.70` AND `handover_cost = high`, prefer current_owner if skill >=2 or supervised feasible. Changing owner adds median 2.7h wait; keeping weak skill (0-1) adds median 3.3h service and rework — neither is free.
- P3 Training: At least 20% of `priority = normal/low` assignments should support documented `training priority = required_skill` if SLA >15h and complexity <0.60 or supervision is feasible. Documented priorities: R1/R6diagnosis, R2quality, R3/R9negotiation, R4/R8approval, R5/R10security.
- P4 Resilience / bottleneck avoidance: Specialist-only routing reduces immediate errors but creates queues in Security and Approval (historical evidence). First-available reduces waiting but increases reassignments (1.8x rework after >2 handovers) and skill mismatch. Preference: penalize assigning to specialist team if its queue > p75 waiting time for that skill.
- P5 Batching: Quality Check may be batched only if `priority normal/low` AND `SLA remaining >24h` (C006, C012). Batching saves service time but delays feedback — explain to workers.

Socio-technical principle: The policy is an *advisor with reasons*, not an optimizer that dictates. Workers can see scores, contest them, and request exception handling.

# 2. Assignment policy
Explainable scoring: transparent points, not black box. All eligible resources are filtered first, then scored 0-10 per dimension.

**Pseudocode:**
```
FOR each case in queue sorted by SLA urgency (urgent high > high > normal > low, tie by SLA remaining):
  1. ELIGIBILITY FILTER
     eligible = { r | r.skill[required_skill] != 0 AND
                     NOT (required_skill==Security AND r.skill<3 AND supervisor not in {Gita,Hugo}) AND
                     NOT (required_skill==Approval AND r.skill==1 AND unsupervised_finalize) AND
                     NOT (Quality batch violation) AND
                     r.hours_remaining_today >= estimated_service_time * 0.5 OR SLA>24h (allow next-day) }
     IF eligible empty -> exception: escalate to team lead, log deviation, allow overtime with consent

  2. SCORES (0-10, weights sum to 100, shown to worker)
     SLA_urgency = 10 * priority_weight(urgent=1.0, high=0.7, normal=0.3, low=0.1) * urgency_factor(1/SLA_remaining) * (1+complexity)
       // e.g., C002: 10, C013: 1

     skill_match = skill_level * 3 + specialist_bonus if needed (enterprise customer)
       // 3=10, 2=7, 1=3 supervised, 0=0 filtered

     continuity = 
       if r == current_owner: 10 - reassignment_penalty(reassignment_count*2) - skill_mismatch_penalty
       else: 10 - handover_cost_band(high=7, medium=4, low=1) - 2.7h_wait_equivalent if complexity>0.7
       // Rule 5: high complexity+high cost -> keep unless skill 0/1 unsupervised

     workload_fairness = 10 - (current_open_cases / max_open) *5 - overtime_risk(high=5, medium=2, low=0) - hours_remaining_shortage

     training = 
       if r.training_priority == required_skill AND r.skill in [1,2] AND SLA>15h AND complexity<0.65 AND supervised_feasible: 8
       else if r.training_priority == required_skill AND skill0 shadow feasible (Security): 4 (observation, executor stays specialist)
       else 0
       // capped to avoid sacrificing SLA

     resilience = -bottleneck_penalty if assigning would overload scarce skill queue (Security/Approval queue > p75 waiting)
       // Encourages competent generalist over specialist when specialist queue long and SLA safe

  3. AGGREGATE (explainable weighted sum, default weights tunable with workers)
     total = 0.25*SLA_urgency + 0.20*skill_match + 0.20*continuity + 0.15*workload_fairness + 0.10*training + 0.10*resilience
     // High SLA forces SLA_urgency to dominate; otherwise balance

  4. TIE-BREAKING and EXCEPTION HANDLING
     - If top 2 within 0.5 points: prefer current_owner -> lower overtime risk -> lower open cases -> random
     - If high-priority would go to trainee unsupervised: force supervised pair or next best specialist, log reason
     - If high overtime-risk resource is top but alternative within 1 point and SLA not urgent: choose alternative, log fairness reason
     - If >2 reassignments: require continuity or explicit lead approval for handover, log handover_cost_band

  5. LOG and EXPLAIN
     assignment_reason = "SLA_urgency X, skill Y, continuity Z, fairness W, training T, bottleneck B"
     Store scores for audit. Show worker: 2-3 sentence reason + trade-off.

Weights are not mathematical truth — they are negotiated defaults reviewed monthly via process mining indicators (Sec 6).
```

# 6. Process-mining audit indicators
All indicators are computed from the enriched event log (`case:concept:name, concept:name, time:timestamp, org:resource, required_skill, case_priority, sla_deadline, case_complexity, current_owner, team, assignment_reason, reassignment_count, workload_snapshot, handover_cost_band` plus derived waiting/service times). Targets are reviewed monthly with workers.

- **Handover frequency:** `handover = case where org:resource != previous org:resource`. Rate = handovers / activity transitions. Slice by `handover_cost_band`. Alert if >0.30 overall or high-cost handovers >0.15.
- **Reassignment count:** Distribution of `reassignment_count` per case; % cases with >2 (must be <5%). Cases with reassignment jump correlate with rework (check via `get_variants`).
- **Skill mismatch:** % assignments where `resource skill <2` for `priority high/urgent` without supervisor in log (must be 0). Also % with skill 1 supervised (expected 5-15% for learning). Detect via join skill matrix.
- **Workload distribution:** Gini of `current_open_cases` + new assignments per resource per day/week; max assignments per batch >4 flagged. Variance of `hours remaining today` utilization.
- **Overtime risk exposure:** % assignments in last 2h of shift to `overtime risk=high` resources; overtime hours logged vs `hours remaining`. Target: 0 high-risk urgent unless SLA<4h.
- **SLA misses:** % cases where `time:timestamp > sla_deadline`; avg/median waiting vs deadline by priority. Correlate with handover vs specialist queue (via `filter_case_performance`).
- **Rework / appeal after assignment:** % cases with rework activities (`Rework Correction` loop) or appeal within 7d after assignment. Compare `skill 1 unsupervised` vs `skill3` cohorts; validate 1.8x/1.4x signals.
- **Training assignment share:** % normal/low assignments where `resource.training_priority == required_skill` and `assignment_reason` contains training/supervision. Target 20% rolling 4 weeks, SLA-safe. Includes shadow logged as `training_shadow` but distinguished from executor.
- **Specialist bottleneck indicators:** For Security and Approval, 95th percentile waiting time per `required_skill` via `insert_case_service_waiting_time`; queue length per specialist team (Risk/Quality). Alert if waiting > SLA_remaining *0.5.
- **Deviations from assignment policy:** Cases where top-scoring eligible per logged scores was not chosen without exception note; unsupervised high-priority trainee assignments; batching violations (`Quality Check` batched with priority high or SLA<24h). Track via `assignment_reason` keyword audit + `discover_performance_dfg` for waiting anomalies.
- **Socio-technical health:** `discover_working_together_network` / `discover_handover_of_work_network` to see isolation; `discover_organizational_roles` drift vs skill matrix; `pm4py.get_service_time` for supervision overhead not ballooning.
