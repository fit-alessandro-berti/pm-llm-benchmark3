# 1. Assumptions and Interpretation

1. **Risk route.** Low-risk vs. high-risk is represented as a control-flow XOR after Analyze Root Cause. Low-risk selects Supervisor Review. High-risk selects a concurrent Quality Review and Regulatory Review submodel; the two high-risk reviews have no order between them and may complete in either order. The choice is made once per case.
2. **Optional supplier consultation.** Consult Supplier is represented as an XOR between a silent skip branch and one Consult Supplier transition, so it occurs zero or one time. It may start only after Analyze Root Cause and must finish before Release Material. In the POWL model this is represented directly with a `SilentTransition`. In the process-tree approximation it is delayed until after Plan Verification and Design Corrective Action complete, which is conservative and discussed below.
3. **Passing inspection abstraction.** Inspection outcomes are not event labels. A trial cycle is modeled as Execute Trial followed by Inspect Trial. A pass is represented by exiting the loop after an Inspect Trial; a failure is represented by taking the loop redo Adjust Parameters and then repeating Execute Trial–Inspect Trial. Consequently, the models cannot distinguish a semantically passing inspection from a failing one except via the visible choice to exit or redo. Adjust Parameters is never allowed after the final exit from the loop, because the loop redo path must be followed by another Execute Trial.
4. **Duplicate visible labels.** No structural duplication of labels is used. Loop repetition necessarily causes repeated visible labels for Execute Trial, Inspect Trial, and Adjust Parameters in traces. Release Material and Archive Case are unique. Validation must therefore treat repeated trial labels as legitimate loop occurrences rather than as duplicated model activities.
5. **Process-tree approximation policy.** The process tree uses a **conservative under-approximation** for the non-block-structured release synchronization. It does not admit unsafe behavior such as release before approval, before supplier completion, or before a passed trial. It does exclude some intended timing flexibility: in the tree, the approval route and optional supplier consultation begin only after both Plan Verification and Design Corrective Action complete, whereas intentionally they may begin after Analyze Root Cause and overlap planning/design.
6. **Meaning of “may overlap.”** In the POWL model, “may overlap” is interpreted as true partial-order concurrency: unconnected nodes can execute in any interleaving allowed by the remaining order edges. In the process tree, `PARALLEL` represents true interleaving concurrency among its children. The process-tree under-approximation delays some activities, but once those activities are enabled they are genuinely concurrent with their siblings.
7. **Recording semantics.** Activities are recorded at completion time. The models encode only control-flow ordering and do not encode data conditions such as actual risk, supplier involvement, or inspection result.

# 3. PM4Py Process-Tree Model

**Compact process-tree expression**  
This is a schematic PM4Py-style expression. The executable construction below is the code of record because it explicitly sets parent/child links.

```text
->(
  Register Deviation,
  +(
    ->(Contain Material, Plan Verification),
    ->(Analyze Root Cause, Design Corrective Action)
  ),
  +(
    X(Supervisor Review, +(Quality Review, Regulatory Review)),
    X(tau, Consult Supplier),
    *(->(Execute Trial, Inspect Trial), Adjust Parameters)
  ),
  Release Material,
  Archive Case
)
```

**Self-contained Python code**

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    return ProcessTree(operator=None, parent=None, children=[], label=label)

def silent():
    return ProcessTree(operator=None, parent=None, children=[], label=None)

def op(operator, *children):
    node = ProcessTree(operator=operator, parent=None, children=[], label=None)
    for child in children:
        child.parent = node
        node.children.append(child)
    return node

# Activities
register = leaf("Register Deviation")
contain = leaf("Contain Material")
analyze = leaf("Analyze Root Cause")
plan = leaf("Plan Verification")
design = leaf("Design Corrective Action")
supervisor = leaf("Supervisor Review")
quality = leaf("Quality Review")
regulatory = leaf("Regulatory Review")
supplier = leaf("Consult Supplier")
execute = leaf("Execute Trial")
inspect = leaf("Inspect Trial")
adjust = leaf("Adjust Parameters")
release = leaf("Release Material")
archive = leaf("Archive Case")

# Initial parallel work streams
contain_then_plan = op(Operator.SEQUENCE, contain, plan)
analyze_then_design = op(Operator.SEQUENCE, analyze, design)
initial_parallel = op(Operator.PARALLEL, contain_then_plan, analyze_then_design)

# Risk route
high_risk_reviews = op(Operator.PARALLEL, quality, regulatory)
risk_route = op(Operator.XOR, supervisor, high_risk_reviews)

# Optional supplier consultation
supplier_choice = op(Operator.XOR, silent(), supplier)

# Trial loop
trial_body = op(Operator.SEQUENCE, execute, inspect)
trial_loop = op(Operator.LOOP, trial_body, adjust)

# Post-planning/design parallel synchronization:
# approvals, optional supplier, and trial loop may overlap here.
post_parallel = op(Operator.PARALLEL, risk_route, supplier_choice, trial_loop)

tree = op(Operator.SEQUENCE, register, initial_parallel, post_parallel, release, archive)
```

**Parent/child handling.** The helper `op(...)` explicitly sets `child.parent = node` and appends each child to `node.children`. Leaves are created with `operator=None`; silent skip is represented by a leaf with `label=None`.

**Approximation paragraph.** The process tree exactly represents the initial concurrency of Contain Material and Analyze Root Cause, the precedence constraints Contain Material  Plan Verification and Analyze Root Cause  Design Corrective Action, the risk XOR, concurrency of Quality Review and Regulatory Review, optional supplier consultation, the trial loop with Adjust Parameters as redo, and release synchronization after the post-parallel block. However, it is a conservative under-approximation for the intended non-block-structured timing: the approval route and supplier consultation are placed after both Plan Verification and Design Corrective Action complete. Thus, the tree excludes intended traces where Supervisor Review, Quality Review, Regulatory Review, or Consult Supplier start or complete after Analyze Root Cause but before Plan Verification or Design Corrective Action completes. It also cannot encode inspection failure vs. pass as data; it treats loop exit after Inspect Trial as the passing outcome.

# 4. PM4Py POWL Model

**Compact POWL description**

```text
Top-level StrictPartialOrder nodes:
  Register Deviation
  Contain Material
  Plan Verification
  Analyze Root Cause
  Design Corrective Action
  ApprovalChoice = XOR(Supervisor Review,
                       StrictPartialOrder(Quality Review, Regulatory Review with no edge))
  SupplierChoice = XOR(SilentTransition, Consult Supplier)
  TrialLoop = LOOP(StrictPartialOrder(Execute Trial -> Inspect Trial), Adjust Parameters)
  Release Material
  Archive Case

Edges:
  Register Deviation -> Contain Material
  Register Deviation -> Analyze Root Cause
  Contain Material -> Plan Verification
  Analyze Root Cause -> Design Corrective Action
  Analyze Root Cause -> ApprovalChoice
  Analyze Root Cause -> SupplierChoice
  Plan Verification -> TrialLoop
  Design Corrective Action -> TrialLoop
  ApprovalChoice -> Release Material
  SupplierChoice -> Release Material
  TrialLoop -> Release Material
  Release Material -> Archive Case

Internal edges:
  High-risk branch: no edge between Quality Review and Regulatory Review.
  Trial body: Execute Trial -> Inspect Trial.
```

**Self-contained Python code**

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

register = Transition("Register Deviation")
contain = Transition("Contain Material")
plan = Transition("Plan Verification")
analyze = Transition("Analyze Root Cause")
design = Transition("Design Corrective Action")
supervisor = Transition("Supervisor Review")
quality = Transition("Quality Review")
regulatory = Transition("Regulatory Review")
consult_supplier = Transition("Consult Supplier")
execute_trial = Transition("Execute Trial")
inspect_trial = Transition("Inspect Trial")
adjust_parameters = Transition("Adjust Parameters")
release = Transition("Release Material")
archive = Transition("Archive Case")

# High-risk approval branch: both reviews required, no order between them.
high_risk_inner = StrictPartialOrder([quality, regulatory])
# No edge is added between quality and regulatory, so they may occur concurrently
# and in either completion order.

# Risk choice after Analyze Root Cause.
approval_choice = OperatorPOWL(
    Operator.XOR,
    [supervisor, high_risk_inner]
)

# Optional supplier consultation.
skip_supplier = SilentTransition()
supplier_choice = OperatorPOWL(
    Operator.XOR,
    [skip_supplier, consult_supplier]
)

# Trial loop: body is Execute Trial -> Inspect Trial; redo is Adjust Parameters.
trial_body = StrictPartialOrder([execute_trial, inspect_trial])
trial_body.order.add_edge(execute_trial, inspect_trial)
trial_loop = OperatorPOWL(
    Operator.LOOP,
    [trial_body, adjust_parameters]
)

# Top-level partial order.
nodes = [
    register,
    contain,
    plan,
    analyze,
    design,
    approval_choice,
    supplier_choice,
    trial_loop,
    release,
    archive,
]

powl = StrictPartialOrder(nodes)

# Start: Register Deviation precedes both initial work streams.
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)

# Split dependencies into planning and design.
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)

# Risk route and optional supplier may start after Analyze Root Cause.
powl.order.add_edge(analyze, approval_choice)
powl.order.add_edge(analyze, supplier_choice)

# Execute Trial may start only after both Design Corrective Action and Plan Verification.
powl.order.add_edge(plan, trial_loop)
powl.order.add_edge(design, trial_loop)

# Release synchronization.
powl.order.add_edge(approval_choice, release)
powl.order.add_edge(supplier_choice, release)
powl.order.add_edge(trial_loop, release)

# End.
powl.order.add_edge(release, archive)
```

**Partial-order dependencies.** The top-level dependencies are added explicitly with `.order.add_edge(...)`: RegisterContain, RegisterAnalyze, ContainPlan, AnalyzeDesign, AnalyzeApprovalChoice, AnalyzeSupplierChoice, PlanTrialLoop, DesignTrialLoop, ApprovalChoiceRelease, SupplierChoiceRelease, TrialLoopRelease, and ReleaseArchive. Internally, Execute TrialInspect Trial is added to the trial body.

**Intentionally unconnected pairs.** Contain Material and Analyze Root Cause are unconnected because the initial work streams may overlap. Plan Verification and Design Corrective Action are unconnected because planning and design may overlap; they are synchronized only by both being required before TrialLoop. ApprovalChoice and TrialLoop are unconnected because approvals may overlap the trial cycle. SupplierChoice and Plan Verification, Design Corrective Action, ApprovalChoice, and TrialLoop are unconnected except through Analyze Root Cause and Release Material, so supplier consultation may overlap those activities and must merely finish before release. Quality Review and Regulatory Review are intentionally unconnected inside the high-risk submodel so they may complete in either order.

|---|---|---|---|---|---|

# 7. Preferred Representation and Validation Plan

The **POWL model is preferred as the canonical representation** because the intended process is fundamentally a partial order with independent obligations: planning, design, approvals, optional supplier work, and the trial loop progress independently and synchronize at Release. POWL expresses these cross-branch dependencies directly with partial-order edges and does not require the delay introduced by the block-structured process tree.

Validation plan:

1. **Conversion to accepting Petri nets where supported.** Convert both models with `pm4py.convert_to_petri_net(model)`:
   ```python
   net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)
   net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)
   ```
   If a PM4Py version does not support direct POWL conversion, convert the process tree and use the POWL model for structural inspection and playout; record that limitation.
2. **Soundness checking.** Run soundness diagnostics on the converted nets:
   ```python
   pm4py.check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)
   pm4py.check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)
   ```
   A sound result is evidence to inspect, not proof of semantic fidelity.
3. **Bounded or sampled playout.** Use bounded playout to inspect generated traces:
   ```python
   sampled = pm4py.play_out(powl, num_traces=1000, max_trace_length=80)
   ```
   Check for impossible traces such as Release before any approval, Release before trial completion, Consult Supplier more than once, or Adjust Parameters after Release.
4. **Explicit positive and negative trace tests.** Convert the eight witnesses in Section 5 into an event log and replay them against the converted nets using token-based replay or alignments. T1–T5 must be fit for the POWL net; T1–T4 must be fit for the process tree; T5 must be non-fit for the process tree. F1–F3 must be non-fit for both models.
5. **Silent-behavior and duplicate-label checks.** Inspect played-out traces specifically for: `Consult Supplier` count in `{0,1}`; no `Adjust Parameters` after `Release Material`; every `Adjust Parameters` followed by `Execute Trial` before `Release Material`; exactly one `Release Material`; exactly one `Archive Case`; and no visible leakage from `SilentTransition`. Also verify that repeated `Execute Trial`, `Inspect Trial`, and `Adjust Parameters` are only interpreted as loop iterations.
6. **Limitations.** Playout is bounded and sampled, so it cannot prove absence of all bad traces. The models intentionally abstract away inspection outcome, risk data, and supplier-selection data, so semantic correctness of those data-dependent choices cannot be validated from control flow alone. Conversion to Petri nets may be lossy or unsupported for some PM4Py versions, and silent transitions can complicate alignment diagnostics.

# 8. Final Self-Critique

1. **Semantic approximation in the process tree.** The process tree is deliberately conservative, but it excludes intended behavior where approvals or supplier consultation overlap Plan Verification and Design Corrective Action. It is safe with respect to release, but it is not behaviorally complete.
2. **Inspection pass/fail remains an abstraction.** Because inspection result is not an event label, the loop allows an exit after any Inspect Trial and allows retries without evidence that the inspection actually failed. It cannot enforce that no redo occurs after a semantically passing inspection.
3. **Dependence on PM4Py loop and conversion semantics.** The code assumes PM4Py interprets `Operator.LOOP` as first child do/body and second child redo, and that the installed PM4Py supports the stated POWL-to-Petri-net conversion. If those API semantics differ, the loop or validation results could change.
