# 1. Assumptions and Interpretation

1. **Low-risk/high-risk choice** is represented as a control-flow XOR after `Analyze Root Cause`. The low-risk branch is `Supervisor Review`. The high-risk branch is a parallel submodel containing `Quality Review` and `Regulatory Review` with no order between them. In the process tree this is `x('Supervisor Review', +('Quality Review','Regulatory Review'))`; in POWL it is `XOR(S, StrictPartialOrder(Q, G))`. The data condition “low risk” or “high risk” is not encoded.
2. **Optional supplier consultation** is represented as `XOR(tau, 'Consult Supplier')` after `Analyze Root Cause`, with a precedence edge to `Release Material`. It occurs at most once. In the process tree it is `x(tau, 'Consult Supplier')` inside the `Analyze Root Cause` branch; in POWL it is `XOR(SilentTransition(), U)` with edges `A -> supplier_xor` and `supplier_xor -> L`.
3. **Passing inspection abstraction**: because inspection results are not event labels, a completed `Inspect Trial` in the final loop iteration is treated as the passing inspection. The trial loop is structured as `LOOP(SEQUENCE(Execute Trial, Inspect Trial), Adjust Parameters)`, so the loop exits after `Inspect Trial`; `Adjust Parameters` only appears before another `Execute Trial`. Thus “fail” is abstracted as taking the loop’s redo branch, and “pass” as loop exit.
4. **Duplicate visible labels** are not permitted in the intended model. The POWL model uses each visible activity exactly once. The process-tree model also uses each visible activity exactly once; no duplication-based approximation is used.
5. **Approximation policy for the process tree**: conservative under-approximation. Process trees are block-structured and cannot express the partial join at `Execute Trial` — which requires `Design Corrective Action` and `Plan Verification` — while allowing the approval route and supplier consultation to continue until `Release Material`. The tree therefore forces the approval route and supplier consultation to complete before the trial loop. This excludes intended traces where approvals or supplier consultation overlap the trial or occur after it. It does not admit unsafe behavior such as trial before `D`/`P`, release before approvals/supplier, or `Adjust Parameters` after a passing inspection.
6. **“May overlap” interpretation**: interpreted as true concurrency, i.e., absence of an order constraint, in POWL. In the process tree, the parallel operator gives true concurrency where used, but the under-approximation removes some intended overlaps.
7. **Activity completion**: activities are recorded at completion time; a precedence edge means the target starts only after the source completes.
8. **Risk route selection** is placed after `Analyze Root Cause`; the choice itself is a control-flow alternative, not a data condition.
9. **Supplier selection** depends on case data not represented in the control-flow model; it is represented as an XOR skip/consult choice.
10. **Loop semantics**: the loop body is `Execute Trial -> Inspect Trial`; the redo branch is `Adjust Parameters`; the loop exits after the body, i.e., after a passing `Inspect Trial`.

# 3. PM4Py Process-Tree Model

Compact process-tree expression:

```text
->(
  'Register Deviation',
  +(
    ->('Contain Material', 'Plan Verification'),
    ->(
      'Analyze Root Cause',
      +(
        'Design Corrective Action',
        x(
          'Supervisor Review',
          +('Quality Review', 'Regulatory Review')
        ),
        x(tau, 'Consult Supplier')
      )
    )
  ),
  *(
    ->('Execute Trial', 'Inspect Trial'),
    'Adjust Parameters'
  ),
  'Release Material',
  'Archive Case'
)
```

Self-contained Python code:

```python
import pm4py

tree = pm4py.parse_process_tree(
    "->("
    "  'Register Deviation',"
    "  +("
    "    ->('Contain Material', 'Plan Verification'),"
    "    ->("
    "      'Analyze Root Cause',"
    "      +("
    "        'Design Corrective Action',"
    "        x("
    "          'Supervisor Review',"
    "          +('Quality Review', 'Regulatory Review')"
    "        ),"
    "        x(tau, 'Consult Supplier')"
    "      )"
    "    )"
    "  ),"
    "  *("
    "    ->('Execute Trial', 'Inspect Trial'),"
    "    'Adjust Parameters'"
    "  ),"
    "  'Release Material',"
    "  'Archive Case'"
    ")"
)
```

No manual parent/child handling is required because `pm4py.parse_process_tree` constructs the tree from the expression. The expression maps to the narrative as follows: `->` is sequence, `+` is parallel, `x` is XOR, `*` is loop, and `tau` is silent. The outer sequence is `Register Deviation`, then the two parallel workstreams, then the trial loop, then `Release Material`, then `Archive Case`. The first parallel branch is `Contain Material -> Plan Verification`. The second parallel branch is `Analyze Root Cause -> parallel(Design Corrective Action, risk XOR, supplier XOR)`. The trial loop is `*( ->('Execute Trial','Inspect Trial'), 'Adjust Parameters' )`, i.e., `(Execute Trial Inspect Trial) (Adjust Parameters Execute Trial Inspect Trial)*`.

This tree is a **conservative under-approximation**. It cannot represent the intended partial join at `Execute Trial`: the trial requires `Design Corrective Action` and `Plan Verification`, but the approval route and supplier consultation must be allowed to continue until `Release Material`. Because process trees are block-structured, this tree forces the approval route and supplier consultation to complete before the trial loop. Consequently, it excludes intended traces where `Supervisor Review`, `Quality Review`, `Regulatory Review`, or `Consult Supplier` overlap the trial cycle or occur after it. It also forces the trial to wait for approvals and supplier consultation, not only for `D` and `P`. The tree does represent exactly: start/end, `C || A`, `P` after `C`, `D` after `A`, the risk XOR, optional supplier consultation, the trial loop with no `Adjust Parameters` after a passing inspection, release after the trial loop, and archive after release. It does not duplicate visible labels.

# 4. PM4Py POWL Model

Abbreviations: `R` = Register Deviation, `C` = Contain Material, `A` = Analyze Root Cause, `P` = Plan Verification, `D` = Design Corrective Action, `S` = Supervisor Review, `Q` = Quality Review, `G` = Regulatory Review, `U` = Consult Supplier, `E` = Execute Trial, `I` = Inspect Trial, `J` = Adjust Parameters, `L` = Release Material, `Z` = Archive Case, `tau` = silent.

Compact POWL description:

```text
StrictPartialOrder(
  nodes = [
    R, C, A, P, D,
    XOR(S, StrictPartialOrder(Q, G)),
    XOR(tau, U),
    LOOP(StrictPartialOrder(E -> I), J),
    L, Z
  ],
  edges = [
    R->C, R->A,
    C->P,
    A->D, A->risk_xor, A->supplier_xor,
    D->trial_loop, P->trial_loop,
    trial_loop->L, risk_xor->L, supplier_xor->L,
    L->Z
  ]
)
```

Self-contained Python code:

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

R = Transition('Register Deviation')
C = Transition('Contain Material')
A = Transition('Analyze Root Cause')
P = Transition('Plan Verification')
D = Transition('Design Corrective Action')
S = Transition('Supervisor Review')
Q = Transition('Quality Review')
G = Transition('Regulatory Review')
U = Transition('Consult Supplier')
E = Transition('Execute Trial')
I = Transition('Inspect Trial')
J = Transition('Adjust Parameters')
L = Transition('Release Material')
Z = Transition('Archive Case')
tau = SilentTransition()

# High-risk route: Q and G are concurrent.
high_risk = StrictPartialOrder([Q, G])

# Risk route: low-risk S or high-risk Q || G.
risk_xor = OperatorPOWL(Operator.XOR, [S, high_risk])

# Optional supplier consultation: skip or U.
supplier_xor = OperatorPOWL(Operator.XOR, [tau, U])

# Trial cycle body: E then I.
trial_body = StrictPartialOrder([E, I])
trial_body.order.add_edge(E, I)

# Trial loop: (E I) (J E I)*, exit after E I.
trial_loop = OperatorPOWL(Operator.LOOP, [trial_body, J])

# Root partial order.
powl = StrictPartialOrder([
    R, C, A, P, D,
    risk_xor,
    supplier_xor,
    trial_loop,
    L, Z,
])

powl.order.add_edge(R, C)
powl.order.add_edge(R, A)
powl.order.add_edge(C, P)
powl.order.add_edge(A, D)
powl.order.add_edge(A, risk_xor)
powl.order.add_edge(A, supplier_xor)
powl.order.add_edge(D, trial_loop)
powl.order.add_edge(P, trial_loop)
powl.order.add_edge(trial_loop, L)
powl.order.add_edge(risk_xor, L)
powl.order.add_edge(supplier_xor, L)
powl.order.add_edge(L, Z)
```

Intentionally unconnected node pairs may remain concurrent because no order edge exists between them. In particular: `C` and `A` are concurrent after `R`; `P` and `D` may overlap because they depend on different parallel branches; `D`, `risk_xor`, and `supplier_xor` may overlap after `A`; `risk_xor` and `supplier_xor` may overlap; `risk_xor` and `trial_loop` may overlap; `supplier_xor` and `trial_loop` may overlap; and inside `high_risk`, `Q` and `G` are concurrent.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | `R` then `C` and `A` may overlap | `R -> +(C->P, A->...)` | `R->C`, `R->A`, no `C-A` edge | Neither | Both preserve parallel containment and root-cause analysis. |
| Split dependencies into planning/design | `P` after `C`; `D` after `A` | `C->P` in branch1; `A->D` in branch2 | `C->P`, `A->D` | Neither | Both preserve independent workstream dependencies. |
| Risk route | After `A`, XOR low `S` vs high `Q || G` | `x(S, +(Q,G))` after `A` | `XOR(S, StrictPartialOrder(Q,G))` after `A` | Neither | Both preserve risk-based approval choice and high-risk concurrency. |
| Overlap of approval and trial | Approval route may overlap trial; not required before trial | Forces risk route before trial loop | No edge `risk_xor <-> trial_loop` | Process tree overconstrains; POWL exact | Process tree excludes valid cases where review occurs during/after trial; POWL preserves them. |
| Optional supplier consultation | Optional, at most once, after `A`, before `L`, may overlap `D`/`P`/approvals/trial | `x(tau,U)` after `A` but before trial loop | `XOR(tau,U)` with `A->supplier_xor`, `supplier_xor->L`, no edges to `D`/`P`/risk/trial | Process tree overconstrains (forces `U` before trial); POWL exact | Process tree excludes supplier consultation during/after trial; POWL preserves. |
| Repeat-until behavior | `E->I`, if fail `J` then `E->I` repeat until pass; no `J` after pass | `LOOP(->(E,I), J)` | `LOOP(StrictPartialOrder(E->I), J)` | Neither | Both preserve trial iteration and prevent `J` after final pass. |
| Release synchronization | `L` requires passing `I`, approval route complete, `U` complete if selected | `L` after trial loop; risk and `U` before trial loop, so also before `L` | edges `trial_loop->L`, `risk_xor->L`, `supplier_xor->L` | Process tree overconstrains upstream but release sync exact; POWL exact | Both prevent release before approvals/`U`/trial; process tree may delay release unnecessarily. |
| Duplicate-label risk | Each visible activity occurs at most once, except trial loop `E`/`I`/`J` may repeat | No duplicate visible labels | No duplicate visible labels | Neither | Both avoid duplicate-label artifacts; no duplication-based approximation needed. |
| Trial start synchronization | `E` requires `D` and `P` | Trial after parallel join of `C->P` and `A->(D,risk,U)`, so `E` after `D` and `P` (and risk/`U`) | `D->trial_loop`, `P->trial_loop` | Process tree overconstrains (also waits risk/`U`); POWL exact | Both prevent trial before `D`/`P`; process tree also prevents trial before approvals/`U`. |

# 7. Preferred Representation and Validation Plan

The **POWL model is the canonical representation**. It directly expresses the non-block-structured partial-order dependencies: `D` and `P` both precede the trial loop, while `risk_xor` and `supplier_xor` precede only `Release Material` and may overlap the trial loop. The process tree requires a conservative under-approximation that excludes intended overlap behavior.

Validation plan:

- **Conversion to accepting Petri net**: convert the POWL model with `pm4py.convert_to_petri_net(powl)` to obtain `(net, im, fm)`. Also convert the process tree for comparison.
- **Soundness checking**: run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on both converted nets. Check for deadlocks, proper completion, and option to complete.
- **Bounded/sampled playout**: use `pm4py.play_out(powl, ...)` and `pm4py.play_out(net, ...)` to generate a bounded sample of traces, e.g., 1000 cases, and collect visible traces.
- **Explicit positive and negative trace tests**: replay the eight witnesses from Section 5 on the converted Petri net. For POWL, assert A1–A5 are accepted and F1–F3 are rejected. For the process tree, assert A1–A4 are accepted, A5 is rejected, and F1–F3 are rejected.
- **Silent behavior and duplicated-label check**: inspect generated traces to ensure `tau` never appears as a visible label; verify that the supplier XOR skip branch produces no `Consult Supplier`; and check that no trace contains duplicate visible labels except `E`/`I`/`J` inside the trial loop. This specifically targets silent behavior and duplicate-label risk.
- **Limitations**: playout is bounded/sampled, not exhaustive; soundness checking depends on the correctness of the POWL/process-tree-to-Petri-net conversion; conformance tests cover only the selected witnesses; data conditions such as risk level, supplier involvement, and inspection result are not encoded; and the process tree under-approximation means its converted net will reject some intended traces.

# 8. Final Self-Critique

1. **Semantic weakness**: the process-tree model under-approximates by forcing approvals and supplier consultation to complete before the trial loop, thereby excluding intended overlap between approvals/supplier work and the trial cycle. This is a significant semantic loss even though it is explicitly documented.
2. **Semantic weakness**: the abstraction of inspection pass/fail as loop exit/redo is a control-flow approximation. It cannot distinguish a failed inspection from a passing one in event data, so it may not align with actual event logs where inspection results are recorded as attributes.
3. **API/Python weakness**: the code assumes current PM4Py interfaces for `OperatorPOWL`, `StrictPartialOrder.order.add_edge`, and `pm4py.parse_process_tree`; version differences may require adjustments.
