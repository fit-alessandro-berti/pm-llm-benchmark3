## 1. Temporal Data Semantics

State reconstruction relies on a **forward-fill (last observation carried forward)** strategy within each case, constrained by event ordering.
*   **Blanks:** A blank attribute cell in an event row signifies "no update at this event." The value persists from the previous event. It does not mean `null` or reset.
*   **Ordering:** Events are ordered by `time:timestamp` ascending. If timestamps match, `event_index` (source-system order) determines precedence. This is critical for cases like TX-311 where jurisdiction changes at the same time as a review.
*   **Material Changes:** Attribute updates (amount, risk, jurisdiction, customer_type) are treated as effective immediately at the event timestamp unless an explicit `effective_from` is provided in exemption data.
*   **Final State vs. Event State:** The final case state (e.g., at the last log entry) is **not** copied backward. Compliance is evaluated using the state *at the moment of the triggering event* (typically `Release_Funds`), derived from the history up to that point.
*   **Time Distinctions:**
    *   **Event Time:** When the log entry was generated (`time:timestamp`).
    *   **Effective Time:** When the attribute change legally took effect (usually Event Time).
    *   **Record Time:** When a record was inserted into a database (e.g., `Record_Exemption` at 11:00 for TX-302).
    *   **Evidence Time:** When supporting proof (e.g., digital signature) was generated. Record Time != Evidence Time.

**Formal Pseudo-Logic:**

```text
// R1: Foreign High-Value
IF Release_Funds(t) AND Jurisdiction(t) != 'DE' AND Amount(t) >= 100000 THEN
    EXISTS e: Enhanced_Review(e) WHERE e.time < t.time AND e.time > Latest_Material_Change(t)
    OR EXISTS x: Exemption(x) WHERE x.valid_at(t) AND x.scope_matches(t)
    ELSE VIOLATION(R1)

// R2: High-Risk/PEP
IF Release_Funds(t) AND (Risk(t) == 'HIGH' OR CustType(t) == 'PEP') THEN
    EXISTS e: Enhanced_Review(e) WHERE e.time < t.time
    AND EXISTS c: Compliance_Approve(c) WHERE c.time > e.time AND c.time < t.time
    ELSE VIOLATION(R2)

// R3: Sanctions
IF Release_Funds(t) AND Jurisdiction(t) IN Sanctions_List
    AND EXISTS u: Sanctions_List_Update(u) WHERE u.time < t.time AND u.time > Last_Screen(t)
    THEN EXISTS s: Sanctions_Screen(s) WHERE s.time > u.time AND s.time < t.time
    ELSE VIOLATION(R3)

// R4: Material Change
IF Release_Funds(t) AND EXISTS r: Review(r) WHERE r.type IN (Standard, Enhanced)
    AND Amount(t) > Amount(r) * 1.20
    THEN Review_Valid(r, Amount) = FALSE

// R5: Exemption Validity
Exemption_Valid(x, t) =
    Approved_By(x, 'Head_Compliance') AND
    Effective_From(x) <= Trigger_Time(t) AND
    Scope_Match(x, Jurisdiction(t), CustType(t), Amount(t)) AND
    Not_Expired(x, t) AND
    Evidence_Supports_Approval_Time(x, t)

// R6: Missing Data
IF Trigger_Condition(t) Depends_on(Amount) AND Amount(t) == NULL THEN
    Classification = INDETERMINATE

// R7: Event Semantics
State(t) = Get_Latest_Attribute(t, Event_List)
Order(a, b) = IF a.time == b.time THEN a.event_index < b.event_index ELSE a.time < b.time
```

*   *Alternative Reading:* If `Update_Jurisdiction` occurred before `Enhanced_Review`, the review was done on DE jurisdiction (R1 off). If after, review was on US (R1 on, but Release is DE).

## 6. Why Control-Flow-Only Conformance Is Insufficient

1.  **Final-State Leakage:** Control-flow models often assume the final state of the case applies to all prior events. R1 and R3 depend on the state *at Release*, which may differ from the state at Review (e.g., TX-311 Jurisdiction change).
2.  **Post-Hoc Exemptions:** A control-flow check sees `Record_Exemption` and `Release_Funds`. It cannot validate if the exemption was *effective* at Release time (TX-310 vs TX-302). This requires evidence timestamps, not event order.
3.  **Material Changes After Review:** R4 requires comparing `Amount` at Review vs `Amount` at Release. Pure event logs record the change event but do not inherently enforce the 20% calculation logic without attribute inspection.
4.  **Conditional Activation:** R1 only triggers if `Jurisdiction != DE`. A control-flow model expecting `Enhanced_Review` before `Release_Funds` would flag TX-311 as a deviation (missing ER) even though the rule is not active due to jurisdiction.
5.  **Missing Data Handling:** R6 mandates `INDETERMINATE` for missing triggers. Control-flow conformance typically assumes missing attributes are null or defaults, leading to false negatives (assuming compliant) or false positives (assuming violation).
6.  **Same-Timestamp Ordering:** Control-flow often treats simultaneous events as unordered. R7 requires `event_index` to determine if `Update_Jurisdiction` happened before or after `Enhanced_Review` (TX-311), which changes the governing jurisdiction for the review validity.

## 7. Recommended Logging and Control Improvements

1.  **Immutable Release Payloads:** Log the exact `amount`, `risk`, and `jurisdiction` values in the `Release_Funds` event attributes, rather than relying on forward-fill from previous events. This eliminates ambiguity for R1/R2 triggers.
2.  **Effective/Record/Signature Timestamps:** For exemptions, log `approval_effective_time`, `database_record_time`, and `signature_timestamp` separately. This allows automated validation of R5 without manual witness assessment.
3.  **Rule Versioning:** Include a `rule_version` attribute in events to handle policy changes over time (e.g., if R1 threshold changes mid-year).
4.  **Change Provenance:** Log `previous_value` in update events (e.g., `Update_Amount` logs `old_amount=80000, new_amount=125000`). This simplifies R4 calculation.
5.  **Stable Event Ordering:** Enforce a system-wide monotonic sequence ID in addition to `event_index` to resolve race conditions across distributed systems.
6.  **Exemption Scope Attributes:** Log `exemption_scope_jurisdiction`, `exemption_scope_max_amount` directly in the `Record_Exemption` event to enable automated scope matching (R5) without external lookups.
