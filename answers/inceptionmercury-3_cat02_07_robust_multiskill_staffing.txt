# 1. Assumptions, objectives, and decision variables

## Assumptions

- A1. Arrival process: arrivals in each two-hour block follow a Poisson process with the expected number in the base table. Within a block, arrivals are uniformly distributed. Case type and priority are drawn from the supplied multinomial percentages.
- A2. Service-time distributions: within a normal range, service time is uniform between the stated bounds. For a complex-tail case, service time is uniform between the complex-tail bounds. Complex-tail status is independent of case type, priority, and resource. In U4, the complex-tail probability for Mechanical, Electrical, and Software doubles.
- A3. Resource multipliers are multiplicative. If a resource has multiplier 1.25, the active service time is `1.25 × standard_draw`.
- A4. Breaks are unavailable. A task is not split across a break or shift; if it cannot fit in the remaining window, it starts in the next available window. Overtime is limited to 30 minutes per resource per day.
- A5. Preemption: a P1 case may preempt a lower-priority diagnostic activity. The interrupted case is preempted at most once. On resumption, it incurs a penalty equal to 10% of the remaining active service time at the moment of preemption.
- A6. Handover/setup rules are applied exactly as given:
  - 7 minutes when the resource changes between Intake, a diagnostic activity, or Validation.
  - Additional 5 minutes when moving between mechanical and electrical/software teams, unless the same cross-skilled resource keeps the case.
  - 5 minutes when a resource switches diagnostic skill family between consecutive cases.
  - 8 minutes coordination before Validation if ME/ES branches were executed in parallel.
- A7. ME/ES parallelization is a policy decision. We model it as follows: parallel if the policy allows it and two distinct eligible resources are available at branch release; otherwise sequential. Sequential execution avoids the 8-minute coordination delay but may lengthen the critical path.
- A8. SLA clocks start at arrival. P1 target: 90% complete within 120 elapsed minutes. P2: 90% within 480 minutes. P3: 90% within 1440 minutes.
- A9. The simulation horizon is 72 hours. Unfinished cases after the horizon are treated as SLA failures; in practice this means they spill into the next operating day.
- A10. The base load is already close to one-shift capacity. Overnight completion of P3 work is normal and acceptable; the comparison is about prioritization, not about completing every case on the same calendar day.

## Objectives

Two objective functions are used to compare policies.

### Objective 1: tail/SLA risk

\[
Z_1 = E[\text{delay}] + 100(1-\text{P1\_SLA}) + 40(1-\text{P2\_SLA}) + 10(1-\text{P3\_SLA}) + 0.05 \cdot Q90
\]

This objective penalizes mean delay, the 90th-percentile delay, and missed SLA targets. The weights are deliberately biased toward P1 because P1 is a safety-critical target.

### Objective 2: fairness and robustness across scenarios

\[
Z_2 = \max_{s \in \{BASE,U1,\dots,U5\}} \left[ 100(1-\text{P1\_SLA}_s) + 40(1-\text{P2\_SLA}_s) \right] + 25 \cdot \max_r u_r + 15 \cdot CV(u) + 0.1 \cdot B
\]

where \(u_r\) is resource utilization, \(CV(u)\) is the coefficient of variation of utilization across resources, and \(B\) is handover/setup burden. This objective prefers policies that protect the worst scenario, avoid overloading any single resource, and do not create excessive coordination overhead.

## Decision variables

- Dispatch rule: strict lane, full pool, or hybrid.
- Lane/home assignments for specialized resources.
- Overflow thresholds for P2/P3 work in the hybrid policy.
- Parallelization decision for ME/ES cases.
- Whether and when P1 preemption is allowed.
- Overtime use.

# 3. Candidate policies

## Policy SPEC: strict specialization with fixed lanes

- Resources are assigned to fixed half-day diagnostic lanes.
- Example lane rota:
  - Ada: Electrical 08:00-12:00, Mechanical 12:00-16:00
  - Ben: Mechanical 08:00-16:00
  - Chen: Software 08:00-12:00, Electrical 12:00-16:00
  - Deepa: Mechanical 10:00-14:00, Electrical 14:00-18:00
  - Emil: Software 12:00-16:00, Electrical 16:00-20:00
  - Farah: Electrical 08:00-10:00, Software 10:00-12:00
- Each diagnostic skill has a fixed queue. A resource only pulls from its assigned lane.
- Intake and Validation are common activities; any free resource can work on them.
- Within a lane, the queue is ordered by SLA deadline, then arrival time.
- P1 preemption is allowed only within a lane.
- ME/ES branches are parallel only when both lanes have a free resource at branch release; otherwise they run sequentially.
- No cross-skill overflow is allowed.

## Policy POOL: full pooling with transparent dispatch

- There is a single global diagnostic queue and a single waiting queue for Intake/Validation.
- Any resource can take any waiting task for which it is qualified.
- Dispatch rule: lowest SLA deadline first, then earliest arrival, then task ID. This is transparent and easy to audit.
- P1 preemption is allowed across all eligible resources.
- ME/ES branches are parallel by default if two distinct eligible resources are free; otherwise sequential.
- Setup and handover penalties are charged whenever they occur. The dispatch rule does not avoid them; it optimizes SLA priority first.

## Policy HYB: hybrid with reserved P1 capacity and controlled overflow

- Resources have home lanes for stability:
  - Ada: Electrical
  - Ben: Mechanical
  - Chen: Software
  - Deepa: Mechanical
  - Emil: Software
  - Farah: Electrical
- Reserved P1 capacity:
  - Ada is the reserved P1 resource from 08:00 to 16:00.
  - Emil is the reserved P1 resource from 16:00 to 20:00.
  - If a P1 task is waiting, the reserved resource takes it first.
- Controlled overflow:
  - A resource may leave its home lane only when the target P2/P3 task has waited longer than a threshold.
  - Thresholds: P2 = 30 minutes, P3 = 60 minutes.
  - The resource first checks its home lane; if its home lane has work, it stays there.
- Parallelization:
  - ME/ES branches run parallel if two distinct eligible resources are available and both branch queues are not overloaded.
  - Otherwise, they run sequentially.
- Preemption:
  - P1 may preempt a lower-priority task only if no free eligible resource is available and the P1 has waited at least 15 minutes.
  - Preemption is limited to once per interrupted case.

# 5. Robust recommendation

The recommended primary policy is **HYB: hybrid with reserved P1 capacity and controlled overflow**.

Why:

- HYB protects P1 better than strict specialization because it reserves a resource for P1 and permits preemption.
- HYB avoids the worst setup churn of full pooling by keeping resources in home lanes unless overflow is justified.
- HYB is the most robust across U1-U5. Its failure modes are milder than SPEC’s stranded work and POOL’s over-utilization.
- It keeps the maximum individual utilization below or near 90% in most scenarios, satisfying the fairness/robustness constraint better than POOL.

### Fallback mode

Use **POOL full-pool emergency mode** when:

- Rolling P1 SLA falls below 90% over any 8-hour window.
- A P1 waits more than 15 minutes while lower-priority work is running.
- U5-like combined stress occurs: morning surge plus absence plus outage.

In emergency mode, all home-lane restrictions are suspended. The global earliest-deadline dispatch rule takes over. This should be temporary because it increases setup burden and utilization.

### Switch-back triggers

Return to HYB when:

- P1 backlog is clear.
- P1 mean waiting time has been below 10 minutes for two consecutive hours.
- Maximum resource utilization has been below 88% for two consecutive hours.

### When another policy is preferable

- If the business values skill preservation and low coordination overhead more than tail SLA, and demand is stable, SPEC is defensible.
- If the objective is solely average SLA and the organization accepts high coordination overhead, POOL may yield slightly better P2/P3 delays in some scenarios, but at the cost of fairness and resource over-utilization.

# 6. Secondary effects and implementation risks

- Gaming of estimates: operators may classify work as complex-tail to reduce assigned load. The process-mining system should monitor actual complex-tail rates and service-time bounds by resource and case type.
- Starvation of P3: HYB overflow thresholds may starve P3 work if P1/P2 continuously consume capacity. Track the oldest P3 case and the P3 completion ratio.
- Skill erosion: full pooling can make specialists less efficient over time. Track service-time drift per resource and skill. Use targeted training when a resource’s speed multiplier worsens.
- Excessive preemption: preemption adds a 10% penalty to interrupted work. If P1 volume is high, preemption can reduce overall throughput. Track preemption count per resource and per case.
- Coordination overhead: handover and setup delays can become a hidden bottleneck. The process-mining log should record each handover and setup instance explicitly.
- New bottleneck at Validation: parallel ME/ES branches increase the number of Validation arrivals and add 8 minutes of coordination. The Validation stage may become the bottleneck even if diagnostics are balanced.
- Fairness: if one resource is repeatedly used as the “reserved” P1 resource, its utilization may become unfair. Rotate reservation among qualified resources by shift.
- Human interpretability: dispatch rules must be understandable. HYB has simple thresholds: home lane, P1 reservation, 30/60-minute overflow triggers. More complex rules would be harder to audit.

| `setup:delay_min` | Setup delay applied |
| `policy:version` | Policy version |

PM4Py analysis plan:

1. Use `pm4py.format_dataframe(...)` to build the event log.
2. Use `pm4py.insert_case_service_waiting_time(log)` to add case-level service and waiting times. PM4Py stores these as `@@case_service_time` and `@@case_waiting_time`.
3. Use `pm4py.get_service_time(log, timestamp_key="time:timestamp", start_timestamp_key="start_timestamp")` to obtain per-event service times.
4. Use `pm4py.discover_handover_of_work_network(log)` to identify handover-heavy resource pairs and potential coordination bottlenecks.
5. Use stage-specific grouping: separate Intake, diagnostics, and Validation. Monitor waiting time at Validation.
6. Use control charts on service-time means by activity/resource to detect drift and complex-tail gaming.
7. Compare event logs across scenarios to see bottleneck migration: which activity’s waiting time increases first under U1-U5.

def scenario_blocks(scenario):
    blocks = [dict(b) for b in BLOCKS]

    if scenario in ("U1", "U5"):
        for b in blocks[:2]:
            b["expected"] *= 1.7
            b["p1"] = min(0.9, b["p1"] + 0.08)
            total = b["p1"] + b["p2"] + b["p3"]
            b["p1"] /= total
            b["p2"] /= total
            b["p3"] /= total

    if scenario == "U2":
        for b in blocks[2:4]:
            weights = {
                "M": b["M"],
                "E": 2.0 * b["E"],
                "S": b["S"],
                "ME": b["ME"],
                "ES": 2.0 * b["ES"],
            }
            total = sum(weights.values())
            for key in weights:
                b[key] = weights[key] / total

    return blocks


def draw_service(activity, rng, tail_mult=1):
    normal, tail, p = SERVICE[activity]
    if activity in DIAG_FAMILIES:
        p *= tail_mult
    lo, hi = tail if rng.random() < p else normal
    return rng.uniform(lo, hi)


def generate_cases(rng, scenario):
    blocks = scenario_blocks(scenario)
    cases = []
    case_counter = 0
    tail_mult = 2 if scenario == "U4" else 1

    for block in blocks:
        n = int(rng.poisson(block["expected"]))
        for _ in range(n):
            arrival = rng.uniform(block["start"], block["end"])
            case_type = rng.choice(TYPES, p=[block[t] for t in TYPES])
            priority = rng.choice(
                PRIORITIES,
                p=[block["p1"], block["p2"], block["p3"]],
            )

            intake_release = arrival
            if scenario == "U5" and 570 <= arrival < 600:
                intake_release = 600

            services = {"Intake": draw_service("Intake", rng)}
            plan = DIAG_PLAN[case_type]
            for activity in plan:
                services[activity] = draw_service(activity, rng, tail_mult=tail_mult)
            services["Validation"] = draw_service("Validation", rng)

            sla_target = {"P1": 120, "P2": 480, "P3": 1440}[priority]

            cases.append({
                "case_id": f"C{case_counter}",
                "arrival": arrival,
                "intake_release": intake_release,
                "priority": priority,
                "type": case_type,
                "services": services,
                "diag_plan": list(plan),
                "diag_pending": list(plan),
                "parallel": False,
                "deadline": arrival + sla_target,
                "last_activity": None,
                "last_resource": None,
                "preempt_count": 0,
                "completion_time": None,
            })
            case_counter += 1

    return cases


def split_windows(resource, day):
    start, end = SHIFTS[resource]
    ws = start + day * 1440
    we = end + day * 1440 + OVERTIME_MAX
    segments = [(ws, we)]

    for bs, be in BREAKS[resource]:
        bstart = bs + day * 1440
        bend = be + day * 1440
        new_segments = []
        for a, b in segments:
            if b <= bstart or a >= bend:
                new_segments.append((a, b))
            else:
                if a < bstart:
                    new_segments.append((a, bstart))
                if bend < b:
                    new_segments.append((bend, b))
        segments = new_segments

    return segments

            if not (scenario in ("U3", "U5") and r == "Chen")
        ]

        self.resources = {}
        for r in self.active_resources:
            self.resources[r] = {
                "free_at": 0.0,
                "last_diag_family": None,
                "busy_time": 0.0,
            }

        self.waiting = []
        self.events = []
        self.cancelled = set()
        self.running = {}
        self.log = []
        self.now = 0.0
        self.max_completion = 0.0
        self.counter = 0

        for case in self.cases:

                case["services"]["Intake"],

            self._add_promote(task)

    # ------------------------------------------------------------------
    # Event management
    # ------------------------------------------------------------------

    def _add_promote(self, task):
        self.counter += 1
        heapq.heappush(self.events, (task.release, self.counter, "promote", task))

    def _make_task(self, case, activity, release, std_dur, family):
        self.counter += 1
        return Task(
            task_id=f"{case['case_id']}_{activity}_{self.counter}",
            case_id=case["case_id"],
            activity=activity,
            family=family,
            release=release,
            std_dur=std_dur,
            priority=case["priority"],
            deadline=case["deadline"],
        )

    def run(self, max_time=4320):
        while self.events:
            time, seq, typ, payload = heapq.heappop(self.events)
            if time > max_time:
                break
            self.now = time

            if typ == "promote":
                task = payload
                task.wait_since = self.now
                if task.status == "waiting":
                    self.waiting.append(task)

            elif typ == "finish":
                if seq in self.cancelled:
                    continue
                self._complete(payload)

            self._dispatch()
            self._preempt_if_needed()

    # ------------------------------------------------------------------
    # Dispatch
    # ------------------------------------------------------------------

    def _dispatch(self):
        progress = True
        while progress:
            progress = False
            for res in self.active_resources:
                if res in self.running:
                    continue
                task = self._select_task(res)
                if task is not None:
                    self._start_task(res, task)
                    progress = True

    def _select_task(self, res):
        now = self.now
        eligible = [
            t for t in self.waiting
            if t.release <= now + 1e-9 and SPEED[res].get(t.activity) is not None
        ]
        if not eligible:
            return None

        if self.policy == "SPEC":
            lane = self._strict_lane(res, now)
            if lane is None:
                eligible = [t for t in eligible if t.activity in ("Intake", "Validation")]
            else:
                eligible = [
                    t for t in eligible
                    if t.activity in ("Intake", "Validation") or t.family == lane
                ]

        elif self.policy == "HYBRID":
            if self._is_reserved(res, now):
                p1 = [t for t in eligible if t.priority == "P1"]
                if p1:
                    eligible = p1
                else:
                    eligible = [t for t in eligible if self._home_or_overflow(res, t)]
            else:
                eligible = [t for t in eligible if self._home_or_overflow(res, t)]

        candidates = []
        for task in eligible:
            alloc = self._attempt_allocation(res, task)
            if alloc is not None:
                candidates.append((self._priority_key(task), task, alloc))

        if not candidates:
            return None

        candidates.sort(key=lambda x: (x[0], x[1].task_id))
        return candidates[0][1]
