# 1. Objectives and constraints

**Optimization objectives**

1. Meet SLA deadlines, with urgent/high-priority cases protected first.
2. Minimize total throughput time without creating specialist bottlenecks.
3. Minimize error and rework risk by matching skill to task, while allowing safe learning.
4. Preserve case continuity where handover cost is high, especially on complex cases.
5. Balance workload across resources and avoid assigning too much to high-overtime-risk workers.
6. Develop skills intentionally: at least 20% of normal/low-priority assignments should support documented training priorities, when SLA risk allows.
7. Keep the policy explainable, auditable, and resilient to absence of key specialists.

**Hard / compliance constraints**

- A resource with skill score 0 for a required skill is not eligible.
- Security Review must be performed by skill level 3, or by skill level 1–2 only under explicit supervision by R7_Gita or R8_Hugo.
- Final Approval must be finalized by skill level 2–3; skill level 1 may prepare but not finalize.
- High-priority/urgent work cannot go to skill level < 2 unless a suitable supervisor is explicitly assigned.
- No resource receives more than 4 new assignments in this decision batch.
- Quality Check may be batched only when priority is normal/low and SLA time remaining > 24h.

**Soft / preference trade-offs**

- Avoid high-overtime-risk resources unless there is no safe alternative and SLA risk is urgent.
- Preserve continuity on high-complexity/high-handover cases unless the current owner is unsafe.
- Prefer training assignments when service risk is acceptable.
- Avoid overloading the few Security/Approval specialists with non-specialist work while those queues still have demand.

There is no single “obvious optimum”: **specialist routing** minimizes immediate skill error but creates bottlenecks; **first-available routing** balances workload but damages continuity and skill fit; the proposed policy trades these off explicitly.

# 2. Assignment policy

The policy is a scored assignment procedure, not a rigid rule.

## Pseudocode

```
for each case in queue, sorted by:
    priority (urgent/ high > normal > low)
    SLA time remaining ascending

for each candidate resource r for case c:
    # 1. Eligibility filtering
    if skill[r][required_skill(c)] == 0: reject
    if task == Security Review and not (
        skill[r] >= 3 or (skill[r] >= 1 and supervisor in {R7_Gita, R8_Hugo})
    ): reject
    if task == Final Approval and skill[r] < 2 and no approved finalizer: reject
    if priority in {urgent, high} and skill[r] < 2 and no supervisor: reject
    if r.overtime_risk == high and SLA_remaining(c) > 8 and safe alternative exists:
        reject unless urgent escalation
    if new_assignments[r] + existing_open_cases[r] > capacity threshold: reject
    if new_assignments[r] >= 4: reject

    # 2. SLA urgency score
    if SLA_remaining < 4h: urgency = 10
    elif SLA_remaining < 8h: urgency = 8
    elif SLA_remaining < 24h: urgency = 4
    else: urgency = 1

    # 3. Skill match score
    if skill[r] == 3: skill_score = 3
    elif skill[r] == 2: skill_score = 2
    elif skill[r] == 1: skill_score = 1

    # 4. Continuity / handover-cost score
    if r == current_owner(c):
        continuity_score = 3
        if c.handover_cost_band == high: continuity_score += 2
        if c.case_complexity > 0.7: continuity_score += 1
    else:
        continuity_score = 0
        if c.handover_cost_band == high and c.case_complexity > 0.7:
            continuity_score -= 3

    # 5. Workload / overtime fairness score
    workload_score = - (r.current_open_cases + new_assignments[r]) * 0.3
    if r.overtime_risk == high: workload_score -= 2
    if r.overtime_risk == medium: workload_score -= 0.5

    # 6. Training / development score
    training_score = 0
    if required_skill(c) == r.training_priority and priority in {normal, low}:
        training_score = 2.5
        if SLA_remaining > 20:
            training_score += 0.5

    # 7. Resilience / bottleneck avoidance
    bottleneck_penalty = 0
    if r in {R7_Gita, R8_Hugo} and task != Security Review:
        if any waiting Security Review or future security workload is high:
            bottleneck_penalty -= 1.5
    if r in {R6_Farid} and current open cases high:
        bottleneck_penalty -= 1

    total_score = (
        0.30 * urgency
        + 0.25 * skill_score
        + 0.30 * continuity_score
        + 0.20 * workload_score
        + 0.15 * training_score
        + bottleneck_penalty
    )

    # 8. Tie-breaking
    lower SLA remaining
    higher skill
    lower overtime risk
    lower current open cases
    current owner preferred
```

**Exception handling**

- If no eligible candidate exists, violate workload cap only for urgent cases, with manager approval.
- For security, if R7 and R8 are unavailable, assign R4_David under remote supervision by one of them; never assign score-0 resources.
- If a training assignment degrades SLA, cancel the training intent and reassign to a specialist.

# 4. Comparison with baseline policies

### First-available routing

- **Expected throughput:** likely lowest average waiting time initially because work is spread to least-loaded resources, but throughput degrades due to rework, specialist rework, and reassignments.
- **SLA risk:** good for short-term urgent cases, but dangerous for Security and Approval because it may assign weak-skilled or unqualified resources unless only score-0 filtering is used.
- **Error/rework risk:** high: ignores skill depth, supervision rules, and handover costs.
- **Fairness of workload:** good initially by design, but unfair to low-workload/trainee resources who receive complex cases they cannot handle.
- **Skill development:** accidental rather than planned; may overexpose trainees to high-risk cases.
- **Continuity of ownership:** poor; current owner ignored.
- **Resilience:** modest; can overload low-workload generalists but does not protect specialists.

### Specialist-only routing

- **Expected throughput:** good on first-pass quality for each task, but poor end-to-end because all Security/Approval/Quality work concentrates on a few specialists.
- **SLA risk:** high for urgent cases when specialists are unavailable or overloaded; e.g. Security work waits for R7/R8.
- **Error/rework risk:** lowest immediate error rate, but problems appear when specialists are overused and make fatigue-driven mistakes.
- **Fairness of workload:** poor; R7/R8/R6/R9 carry disproportionate load; high-overtime-risk specialists get even more.
- **Skill development:** almost none; trainees never get opportunities.
- **Continuity of ownership:** not considered; high-handover cases may change owners repeatedly.
- **Resilience:** poor; absence of R7/R8/R6 stops the process.

### Proposed explainable dynamic policy

- **Expected throughput:** slightly slower than first-available initially, but avoided rework and handover delays improve stable throughput.
- **SLA risk:** protects urgent cases by strong urgency weighting, while giving normal cases to available competent resources.
- **Error/rework risk:** balances skill and supervision; security/approval hard rules prevent critical failures.
- **Fairness of workload:** better than specialist-only and more disciplined than first-available; high-overtime-risk workers are shielded when not needed.
- **Skill development:** deliberately includes C003 and C009 as training assignments with supervisors/review.
- **Continuity of ownership:** strong on high-handover/high-complexity cases such as C001, C007, C016.
- **Resilience:** protects security specialists by not loading them with non-security work unless necessary; R8 and R7 can back each other up.

Trade-off accepted: the proposed policy occasionally chooses a less-specialist resource for a normal-priority case to preserve capacity, continuity, or training. This is a conscious choice; we do **not** claim it is optimal for every metric.

# 5. Explanation to workers

We want you to understand why cases are assigned as they are.

The assignment is not based on individual performance or preference. It is based on a shared list of constraints:

- Some tasks legally or operationally require a particular skill level or supervision.
- Urgent cases have to be protected.
- We want to avoid switching cases too often, especially when a case is complex and the current worker already understands it.
- We try not to give one person too many new cases in a single batch.
- We also need to develop skills, so some normal-priority cases are intentionally used as training opportunities with supervision.
- We try not to overload people who already have high overtime risk, unless the case is urgent and no one else can do it.

For example:

- R3_Celine keeps C007 because moving it again would create even more rework, but R7_Gita supervises C001 so security rules are followed.
- R1_Amal gets C009 as a diagnosis training case, because the SLA allows learning time and R1 already owns the case.
- R10_Jonas gets C006 and C012 together because both are normal/low priority quality checks with enough SLA to batch, avoiding extra workload for R9.

This policy will be audited. If you believe an assignment is unsafe or unfair, please raise it. The policy is meant to be reviewed, not to be a black box.

# 6. Process-mining audit indicators

Use the event log and the assignment log to monitor:

| Indicator | Definition / idea |
|---|---|
| **Handover frequency** | Number of times `current_owner` changes per case; should be higher for routine cases, lower for high-complexity/high-handover cases. |
| **Reassignment count** | Average `reassignment_count` after assignment; compare against historical baseline. |
| **Skill mismatch** | Percentage of assignments where `org:resource` has skill < 2 for `required_skill`, after excluding supervised/training cases. |
| **Workload distribution** | Gini coefficient / variance of open cases or assignments per resource after the batch. |
| **Overtime risk exposure** | Share of assignments given to resources with `overtime_risk = high`. |
| **SLA misses** | Percentage of cases completed after `sla_deadline`, segmented by priority and queue activity. |
| **Rework/appeal after assignment** | Whether a later `Rework Correction` or appeal event appears in the same case after the assigned activity. |
| **Training assignment share** | Share of normal/low-priority assignments where `required_skill == resource.training_priority`; target 20%. |
| **Specialist bottleneck indicators** | Waiting time, queue size, and utilization for Security Review and Final Approval activities; especially R7/R8 and R6. |
| **Deviations from assignment policy** | Cases where the actual assignment reason differs from the recommended policy reason; count as exceptions needing review. |

# Audit function sketch
def audit_assignments(log, skill_matrix):
    audit = []
    for event in log:
        resource = event["org:resource"]
        activity = event["concept:name"]
        case = event["case:concept:name"]
        required_skill = event["required_skill"]

        skill = skill_matrix.get((resource, required_skill), 0)

        audit.append({
            "case": case,
            "activity": activity,
            "resource": resource,
            "skill_mismatch": int(skill < 2),
            "handover": event.get("handover_cost_band"),
            "reassignment_count": event.get("reassignment_count"),
            "overtime_risk": event.get("overtime_risk"),
            "assignment_reason": event.get("assignment_reason"),
        })

    audit_df = pd.DataFrame(audit)
    # compute indicators: SLA misses, rework, training share, etc.
    return audit_df

In practice, the PM4Py outputs are not used to replace the assignment policy, but to **learn** resource behavior, **validate** bottlenecks, and **audit** whether the policy produces the intended trade-offs.
