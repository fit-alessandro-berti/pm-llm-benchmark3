## 1. Temporal Data Semantics

For each case, I reconstruct a time-indexed state rather than using a final case snapshot.

- The ordering key is `(time:timestamp, event_index)`. An event with a lower `event_index` occurs first when timestamps are equal.
- A nonblank amount, risk level, jurisdiction, or customer type cell updates that attribute at that event’s ordering key. A blank cell means **no update**, not a nulling of the prior value.
- State at an event is the state after applying that event’s explicit updates. Thus, a `Release_Funds` event is evaluated using values known at release, not values populated later.
- Forward filling is allowed only from earlier events to later events within the same case. Backfilling from a later final value into an earlier review or release is prohibited.
- An amount increase is measured against the amount known at the latest relevant `Standard_Review` or `Enhanced_Review`. An increase of more than 20% invalidates that review for amount-dependent obligations. A decrease alone does not.
- A change from an unknown prior amount is not safely classifiable as an increase under R4.
- A transaction’s final attributes have no retrospective force. For example, TX-305’s settlement amount at 2026-04-07 does not establish the amount at its 2026-04-06 release.
- A `Record_Exemption` event is normally a record-time fact, not automatically an approval-time fact. It may nevertheless be evidence of earlier approval if supported by reliable evidence.

The relevant temporal concepts are distinct:

| Concept | Meaning here |
|---|---|
| Event time | Timestamp of the logged event. Default time at which an attribute update becomes effective. |
| Effective time | Time at which an underlying fact legally/operationally applies. Defaults to event time unless reliable evidence establishes another time. Exemption `effective_from` is an explicit effective-time claim. |
| Record time | Time at which a database or workflow system recorded a fact. TX-302 and TX-310 have late exemption record times. |
| Evidence time | Time supported by evidence such as a qualified signature, immutable workflow entry, or trusted timestamp. A displayed backdate is weaker than a trusted evidence timestamp. |

For TX-311, the ordering is decisive: `Enhanced_Review` at `(16:20, 3)` occurs before `Update_Jurisdiction` at `(16:20, 4)`. The review therefore saw US, while the release saw DE. The later DE value cannot be copied backward into the review.

## 2. Normalized Rule Table

| Rule | Trigger event and condition | Required prior/subsequent event | Ordering constraint | State snapshot used | Exception | Missing-data treatment | Evidence needed |
|---|---|---|---|---|---|---|---|
| R1 | `Release_Funds`; jurisdiction is not DE and amount is at least EUR 100,000 | A valid `Enhanced_Review` | Review before release and after the latest relevant material change | Release state; review-time state; changes between review and release | Matching valid exemption that waives R1 | If foreign status or amount threshold cannot be established/excluded, INDETERMINATE | Review completion, review coverage/state, amount history, jurisdiction history, exemption evidence |
| R2 | `Release_Funds`; risk is HIGH or customer type is PEP | `Enhanced_Review` and `Compliance_Approve` | Relevant Enhanced Review before Compliance Approve before release | Release state and state at Enhanced Review | No stated exemption | Unknown risk/customer type yields INDETERMINATE unless the other trigger limb resolves the condition | Risk/KYC provenance, Enhanced Review evidence, approval scope and timestamp |
| R3 | A sanctions-list update adds the case’s current jurisdiction after the latest screen and before release | New `Sanctions_Screen` | List update before new screen before release | Jurisdiction at list update/release; latest prior screen | None stated | Unknown jurisdiction or list applicability may make the trigger indeterminate | List version/update timestamp, jurisdiction applicability, screening timestamp/result |
| R4 | Amount update after latest `Standard_Review` or `Enhanced_Review` | Invalidates that earlier review for amount-dependent duties if increase exceeds 20%; a new required review may then be needed | Review before amount increase before release | Amount at review and at each later amount update | Decrease alone does not invalidate | Unknown baseline or increase from unknown amount is not safely classifiable | Old/new amount values, update provenance, review-time amount |
| R5 | An exemption is asserted for an obligation | Head_Compliance approval supported at the relevant time | Effective from no later than trigger; unexpired at trigger; approval must already exist at relevant time | Obligation-trigger state and exemption scope | It is itself the exception-validation rule | Unknown scope, expiry, approval timing, or proof means exemption cannot safely be treated as valid | Approval identity, signature/workflow timestamps, effective/expiry dates, jurisdiction/customer/amount scope |
| R6 | Any rule depends on unknown amount, risk, jurisdiction, or customer type | No synthetic low-risk default permitted | N/A | State at the relevant trigger event | Other reliable evidence may resolve the issue | INDETERMINATE where the decisive trigger cannot be established or excluded | Immutable source payloads, authoritative KYC/risk/amount evidence |
| R7 | All obligations and evidence comparisons | Total event order by timestamp and `event_index` | `(timestamp, event_index)` is strictly increasing | State after each event’s own update | Explicitly established alternative effective time can override default event-time effect | Ambiguous ordering is avoided when `event_index` exists | Stable event index, source-system sequence, event IDs |

Let:

- `e  f` mean `e` occurs strictly before `f` under lexicographic ordering `(timestamp, event_index)`.
- `S_c(e)` be case `c`’s reconstructed state immediately after event `e`.
- `A(e), R(e), J(e), C(e)` be amount, risk, jurisdiction, and customer type in `S_c(e)`.
- `K()` be a three-valued evaluation of condition ``: `T`, `F`, or `U` for unknown.
- `r` be a `Release_Funds` event.
- `ER(e)` mean `e` is an `Enhanced_Review`; `CA(a)` means `Compliance_Approve`; `SS(s)` means `Sanctions_Screen`; `LU(u)` means `Sanctions_List_Update`.

A material R1 change includes a jurisdiction change relevant to foreign/high-value status or exemption scope, an amount change that activates the R1 threshold, or an amount increase that invalidates the candidate review under R4. A decrease does not become material merely because it occurred after a review.

**R1 — Foreign high-value enhanced review**

```text
T1(r) := K(J(r) != "DE" AND A(r) >= 100000)

R1_satisfied(r) iff
    T1(r) = F
    OR ValidExemption("R1", r)
    OR exists e:
         ER(e) AND e  r AND FreshR1Review(e, r)

FreshR1Review(e, r) iff
    no known post-e material R1 change invalidates e before r
    AND no unresolved post-e change makes freshness unknowable.
```

**R2 — High-risk or PEP approval**

```text
T2(r) := K(R(r) = "HIGH" OR C(r) = "PEP")

R2_satisfied(r) iff
    T2(r) = F
    OR exists e, a:
         ER(e) AND CA(a)
         AND e  a  r
         AND FreshR2Review(e, r)
         AND ApprovalAddressesEnhancedReview(a, e)
```

`FreshR2Review` requires the Enhanced Review to remain relevant after the latest risk/customer-type change that establishes or materially affects HIGH-risk or PEP status. A compliance approval of only a standard packet is not treated as approval of an Enhanced Review.

**R3 — Sanctions-list update**

```text
For each list update u before release:
    if SS(s) is the latest relevant screen before u
       AND s  u  r
       AND AddedJurisdiction(u) matches the case jurisdiction to which the update applies,
    then there must exist s2 such that:
       SS(s2) AND u  s2  r.
```

If the jurisdiction/list applicability cannot be established, the R3 result is indeterminate rather than assumed clear.

**R4 — Material amount change**

```text
For q = latest Standard_Review or Enhanced_Review before an amount update x:

InvalidatesAmountDependentReview(q, x) iff
    q  x
    AND A(q) and A(x) are known
    AND A(x) > 1.20 * A(q).

If A(q) is unknown and a later amount appears, the increase is U, not T.
If A(x) <= A(q), the decrease alone does not invalidate q.
```

**R5 — Exemption validity**

```text
ValidExemption(rule, r) iff
    exemption waives rule
    AND approved_by = Head_Compliance
    AND effective_from <= time(r)
    AND time(r) < expires
    AND scope matches J(r), C(r), and A(r)
    AND ReliableEvidenceSupportsApprovalExistedBy(exemption, r).
```

A database insertion after release can support earlier approval only when other evidence establishes that earlier approval. A displayed date alone is not sufficient proof of timely approval.

**R6 — Missing data**

```text
If a decisive trigger predicate evaluates to U,
and no other evidence makes it T or F,
then the case outcome for that obligation is INDETERMINATE.
```

For example, `J != DE AND A >= 100000` is false if `J=DE` even when amount is unknown, but it is unknown if jurisdiction is known non-DE and amount is unknown.

**R7 — Event-time ordering**

```text
e  f iff
    time(e) < time(f)
    OR (time(e) = time(f) AND event_index(e) < event_index(f)).

An update at e is reflected in S(e), but never in S(g) for g  e,
unless reliable evidence establishes an earlier effective time.
```

## 4. Ambiguities and Alternative Readings

**TX-302 — late exemption record, but strong evidence.**  
The 11:00 database insertion should not be treated as the exemption’s approval time. The 09:05 qualified signature is strong evidence that Head_Compliance approval existed before the 09:40 release. In any event, the 09:20 Enhanced Review independently satisfies R1.

The substantive result would change only if both of the following were undermined: the Enhanced Review were shown not to have completed, not to cover the transaction, or to have been followed by a material change; and EX-77’s qualified signature evidence were shown invalid, unrelated, or not authorized by Head_Compliance. A purely stylistic taxonomy could instead call the case `JUSTIFIED_EXCEPTION` because EX-77 was valid, but the policy result remains compliant.

**TX-305 — unknown release amount.**  
The next-day settlement amount of EUR 150,000 is reliable only for settlement. It may be the release amount, but there is no immutable release payload proving that it was. The review document also lacks an amount, so it does not resolve whether the Enhanced Review assessed the release amount.

Evidence that would change the result:

- An immutable release message showing amount below EUR 100,000 would make R1 not triggered and support `COMPLIANT`.
- A release payload showing EUR 100,000 or more, plus evidence that the 11:15 Enhanced Review covered that amount and that no later material amount change occurred, could support `COMPLIANT`.
- A release payload showing EUR 100,000 or more, plus evidence that the amount changed after the Enhanced Review or that the review did not cover the amount, would support `NONCOMPLIANT`.

The current evidence requires `INDETERMINATE` under R6 rather than assuming either a low amount or a high amount.

**TX-310 — claimed backdated exemption with conflicting proof.**  
EX-88 has matching stated scope and displayed dates, but its strongest technical timestamp is a signing certificate created at 10:30, after the 10:00 release. The only asserted earlier approval is an 08:45 statement by the transaction requester. That is not conclusive proof of timely Head_Compliance approval.

Evidence that would change the result:

- A trusted workflow log, Head_Compliance attestation, contemporaneous signed approval, or trusted timestamp proving approval before 10:00 would make EX-88 valid and support `JUSTIFIED_EXCEPTION`.
- Evidence that Head_Compliance approved only after release, or that the document was created retrospectively, would make the exemption invalid and support `NONCOMPLIANT`.
- A documented policy interpretation that oral approval by Head_Compliance is valid, together with independent corroboration of the oral approval, could also support the exception. The requester’s unsupported statement alone is insufficiently reliable.

**TX-311 — same-timestamp ordering.**  
The specified source order means the Enhanced Review at event index 3 saw US, and the jurisdiction became DE only at event index 4. At release, the jurisdiction is DE, so R1 is not triggered. This is not an example of a final DE state being copied backward; the review actually occurred while the known jurisdiction was US.

Reversing the two events would not change the release result here because release would still be DE. It would, however, change what state the Enhanced Review is documented as having reviewed. The substantive result would change if reliable evidence showed that the DE update was ineffective until after release, or that the post-review jurisdiction changed to another non-DE jurisdiction rather than DE and no refreshed review occurred.

**TX-306 — whether any amount change invalidates approval.**  
Under the stated policy, R4 invalidates only for increases of more than 20%, and only for amount-dependent obligations. The increase from EUR 220,000 to EUR 230,000 is below that threshold. A stricter internal policy stating that any post-approval amount change requires reapproval would change TX-306, but that is not the supplied policy.

**TX-308 — decrease after review.**  
A literal reading that treats every later data update as “material” would make the review stale after the amount decrease. That conflicts with R4’s explicit statement that a decrease does not by itself invalidate a review. The better harmonized interpretation is that the explicit R4 rule controls; TX-308 remains compliant. A later jurisdiction change, a material increase, or evidence that the amount decrease represented a different transaction would change that outcome.

# 4. Three-valued trigger helpers and event-history helpers.

def is_missing(value):
    return pd.isna(value)

def tri_r1(jurisdiction, amount):
    """True / False / None for (jurisdiction != DE and amount >= 100000)."""
    j_known = not is_missing(jurisdiction)
    a_known = not is_missing(amount)

    if j_known and jurisdiction == "DE":
        return False
    if a_known and float(amount) < 100000:
        return False
    if j_known and a_known:
        return bool(jurisdiction != "DE" and float(amount) >= 100000)
    return None

def tri_r2(risk_level, customer_type):
    """True / False / None for (HIGH risk or PEP)."""
    risk_known = not is_missing(risk_level)
    customer_known = not is_missing(customer_type)

    if risk_known and risk_level == "HIGH":
        return True
    if customer_known and customer_type == "PEP":
        return True
    if risk_known and customer_known:
        return False
    return None

def tri_text(value):
    return "TRUE" if value is True else "FALSE" if value is False else "UNKNOWN"

def last_of(g, activity, upto_seq):
    prior = g.iloc[:upto_seq]
    hits = prior[prior[ACT] == activity]
    return None if hits.empty else hits.iloc[-1]

    if is_missing(raw_update):
        return False
    if is_missing(prior_value):
        return True
    return raw_update != prior_value

def changed_after(g, start_seq, end_seq, attrs):
    """
    Returns (known_change, unknown_transition).
    An update from an unknown previous state is not assumed harmless.
    """
    if start_seq is None:
        return False, False

    rows = g[(g["case_seq"] > start_seq) & (g["case_seq"] < end_seq)]
    known_change = False
    unknown_transition = False

    for _, row in rows.iterrows():
        for attr in attrs:
            raw_update = row[f"{attr}_update"]
            prior = row[f"prior_state_{attr}"]
            if is_missing(raw_update):
                continue
            if is_missing(prior):
                unknown_transition = True
            elif raw_update != prior:
                known_change = True

    return known_change, unknown_transition

def r4_after_review(g, review, release_seq):
    """
    R4 status for all amount updates after a candidate review and before release.
    The review-time amount is the baseline. Any >20% increase invalidates the review.
    """
    if review is None:
        return "NO_REVIEW"

    post = g[
        (g["case_seq"] > review["case_seq"])
        & (g["case_seq"] < release_seq)
        & (g["amount_update"].notna())
    ]

    if post.empty:
        return "NOT_INVALIDATED"

    baseline = review["state_amount"]
    if is_missing(baseline):
        return "UNKNOWN_BASELINE"

    for _, row in post.iterrows():
        new_amount = row["state_amount"]
        if is_missing(new_amount):
            return "UNKNOWN_AMOUNT_UPDATE"
        if float(new_amount) > 1.20 * float(baseline):
            return "INVALIDATED"

    return "NOT_INVALIDATED"

def material_history(g, upto_seq):
    """
    Coarse material-change tracker for diagnostics.
    It does not replace legal/evidential judgment, but records:
      * risk/customer/jurisdiction changes;
      * threshold activation;
      * >20% increases measured from latest Standard/Enhanced Review;
      * unclassifiable increases from unknown values.
    """
    latest_review = None
    latest_material = None
    unknown_amount_change_seen = False

    for _, row in g.iloc[:upto_seq].iterrows():
        activity = row[ACT]

        if activity != "Create_Transaction":
            for attr, label in [
                ("jurisdiction", "jurisdiction_change"),
                ("risk_level", "risk_change"),
                ("customer_type", "customer_type_change"),
            ]:
                if changed(row[f"{attr}_update"], row[f"prior_state_{attr}"]):
                    latest_material = (row[TS], int(row["event_index"]), label)

            if not is_missing(row["amount_update"]):
                old_amount = row["prior_state_amount"]
                new_amount = row["state_amount"]

                if latest_review is not None:
                    baseline = latest_review["state_amount"]
                    if is_missing(baseline) or is_missing(new_amount):
                        unknown_amount_change_seen = True
                        latest_material = (
                            row[TS],
                            int(row["event_index"]),
                            "amount_change_from_unknown_since_review",
                        )
                    elif float(new_amount) > 1.20 * float(baseline):
                        latest_material = (
                            row[TS],
                            int(row["event_index"]),
                            "amount_increase_gt20_since_review",
                        )
                    elif (
                        not is_missing(old_amount)
                        and float(old_amount) < 100000 <= float(new_amount)
                    ):
                        latest_material = (
                            row[TS],
                            int(row["event_index"]),
                            "amount_crossed_r1_threshold",
                        )
                else:
                    if is_missing(old_amount):
                        unknown_amount_change_seen = True
                        latest_material = (
                            row[TS],
                            int(row["event_index"]),
                            "amount_change_from_unknown",
                        )
                    elif float(old_amount) < 100000 <= float(new_amount):
                        latest_material = (
                            row[TS],
                            int(row["event_index"]),
                            "amount_crossed_r1_threshold",
                        )

        if activity in {"Standard_Review", "Enhanced_Review"}:
            latest_review = row

    return latest_material, unknown_amount_change_seen

def r3_status(g, release_seq, release_jurisdiction):
    """
    Coarse R3 check: each matching list update after an earlier screen must
    have a later screen before release. It assumes Sanctions_List_Update's
    jurisdiction field identifies the jurisdiction added to the list.
    """
    prior = g.iloc[:release_seq]
    screens = prior[prior[ACT] == "Sanctions_Screen"]
    updates = prior[prior[ACT] == "Sanctions_List_Update"]

    if updates.empty:
        return "NOT_TRIGGERED"

    if is_missing(release_jurisdiction):
        return "UNKNOWN_TRIGGER"

    if screens.empty:
        # R3 itself is framed around a list update after a latest screen.
        # A missing baseline-screen obligation would need another policy rule.
        return "NO_PRIOR_SCREEN_R3_NOT_APPLICABLE"

    trigger_updates = []
    for _, update in updates.iterrows():
        added_jurisdiction = update["jurisdiction_update"]
        if is_missing(added_jurisdiction):
            added_jurisdiction = update["state_jurisdiction"]

        had_screen_before_update = not screens[
            screens["case_seq"] < update["case_seq"]
        ].empty

        if (
            not is_missing(added_jurisdiction)
            and added_jurisdiction == release_jurisdiction
            and had_screen_before_update
        ):
            trigger_updates.append(update)

    if not trigger_updates:
        return "NOT_TRIGGERED"

    for update in trigger_updates:
        rescreens = screens[
            (screens["case_seq"] > update["case_seq"])
            & (screens["case_seq"] < release_seq)
        ]
        if rescreens.empty:
            return "FAIL_NO_POST_UPDATE_SCREEN"

    return "SATISFIED_POST_UPDATE_SCREEN"

def exemption_facts(release, exemption):
    """
    Returns:
      asserted_scope_and_time_match,
      strongly_timely_supported,
      needs_human_evidence_review.
    """
    if exemption is None:
        return False, False, False

    amount = release["state_amount"]
    jurisdiction = release["state_jurisdiction"]
    customer_type = release["state_customer_type"]
    release_time = release[TS]

    scope_match = (
        exemption["waives"] == "R1"
        and exemption["approved_by"] == "Head_Compliance"
        and not is_missing(amount)
        and not is_missing(jurisdiction)
        and not is_missing(customer_type)
        and jurisdiction == exemption["jurisdiction_scope"]
        and customer_type == exemption["customer_type_scope"]
        and float(amount) <= float(exemption["amount_max"])
    )

    stated_time_match = (
        exemption["effective_from"] <= release_time
        and release_time < exemption["expires"]
        and exemption["displayed_approval"] <= release_time
    )

    asserted = bool(scope_match and stated_time_match)

    strong = bool(
        asserted
        and exemption["evidence_assessment"] == "STRONG_TIMELY"
        and exemption["signature_timestamp"] <= release_time
    )

    human_review = bool(asserted and not strong)
    return asserted, strong, human_review

def add_event_stamp(out, label, event):
    out[f"last_{label}_timestamp"] = pd.NaT if event is None else event[TS]
    out[f"last_{label}_event_index"] = (
        pd.NA if event is None else int(event["event_index"])
    )

The code intentionally emits `REVIEW_REQUIRED` rather than resolving EX-88 from its displayed date or resolving TX-305 from its later settlement amount. That is appropriate because R5 and R6 require evidential judgment that is not safely reducible to event order.

The final trace-order check is only a coarse control-flow indicator. A chain such as `Enhanced_Review  Compliance_Approve  Release_Funds` does not prove that R2 applied, that the review covered the current risk/KYC state, or that the approval addressed the Enhanced Review rather than a standard packet.

## 6. Why Control-Flow-Only Conformance Is Insufficient

A control-flow model alone cannot faithfully assess these cases for at least the following reasons:

1. **Final-state leakage.**  
   A process model may see a final amount or jurisdiction but cannot tell whether it was known at an earlier review or release. Using TX-305’s settlement amount at release would be retrospective leakage.

2. **Post-hoc exemption records.**  
   `Record_Exemption` after release is not equivalent to timely approval. TX-302 is supportable because of a qualified 09:05 signature; TX-310 is not conclusively supportable from the late record and displayed date alone.

3. **Material changes after review.**  
   Sequence alone can show that a review preceded release, but cannot calculate whether EUR 118,000 to EUR 145,000 is a more-than-20% increase that invalidates the review under R4.

4. **Conditional activation.**  
   R1 applies only if both non-DE jurisdiction and amount threshold are met. R2 applies only if HIGH risk or PEP status is current. A trace containing `Release_Funds` without `Enhanced_Review` is not necessarily noncompliant.

5. **Missing-data semantics.**  
   Absence of an amount is not evidence of an amount below EUR 100,000. A conventional process model typically treats missing event attributes as irrelevant or absent rather than as an indeterminate compliance condition.

6. **Same-timestamp ordering.**  
   Standard timestamp-only sorting cannot determine whether the TX-311 review preceded the DE update. `event_index` is needed to reconstruct the review-time state.

7. **Approval scope and semantic linkage.**  
   A `Compliance_Approve` event after an `Enhanced_Review` is not enough if the approval actually approved only a standard review packet, as in TX-307.

8. **External dynamic facts.**  
   R3 depends on sanctions-list state changing after an earlier screen. A sequence model cannot determine whether a list update applies to the transaction’s jurisdiction without data and list-version semantics.

9. **Exemption scope matching.**  
   Jurisdiction, customer type, amount cap, rule waiver, effective period, expiry, and approval provenance must all match. “An exemption exists somewhere in the trace” is not sufficient.

10. **Different review invalidation scopes.**  
    R4 invalidates reviews for amount-dependent obligations. It should not automatically invalidate every approval or every non-amount-dependent control merely because an amount changed.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payloads.**  
   Store and hash the amount, currency, jurisdiction, risk level, customer type, sanctions-list version, rule version, and decision result used at `Release_Funds`. This would resolve TX-305-like disputes.

2. **Separate event, effective, record, and signature timestamps.**  
   Log `event_time`, `effective_from`, `recorded_at`, `approved_at`, and trusted `signature_time` as separate immutable fields. Do not overload a displayed approval date.

3. **Stable total event ordering.**  
   Require an immutable per-case monotonic sequence number, event UUID, source-system sequence, and causal parent ID. Preserve ordering across data exports and PM4Py transformations.

4. **Old and new attribute values with provenance.**  
   Every update should record previous value, new value, source, reason, confidence, source document ID, and whether the update is a correction, enrichment, or actual business change.

5. **Explicit unknown versus no-update representation.**  
   Use separate fields such as `amount_status = KNOWN | UNKNOWN | NOT_APPLICABLE` and `attribute_update_flag`. Do not rely on blank strings to encode multiple meanings.

6. **Review coverage snapshots.**  
   A review event should store the values reviewed, review type, review scope, review version, evidence document hash, reviewer identity, and whether it covers amount-dependent requirements.

7. **Approval linkage.**  
   `Compliance_Approve` should include the reviewed packet ID, linked Enhanced Review event ID, decision scope, approver role, delegation authority, and approval signature timestamp. This prevents standard-packet approvals from appearing to cure Enhanced Review requirements.

8. **Structured exemption register events.**  
   Log exemption ID, waived rule IDs, jurisdiction/customer/amount scope, currency handling, effective-from and expiry timestamps, Head_Compliance approval event ID, signature hash, revocation status, and evidence quality.

9. **Sanctions-list versioning.**  
   Store screening list provider, list version, list update timestamp, jurisdiction applicability, screen result, and re-screen trigger ID. This makes R3 measurable without inference from free text.

10. **Rule-version and decision-audit fields.**  
    At release, record the policy/rule version, evaluated trigger values, exemption evaluation result, review freshness result, automated/manual decision source, override reason, and operator identity.

These changes would convert several currently defeasible findings—especially TX-305 and TX-310—into determinate, auditable compliance decisions.
