# 3. Consequences for performance analysis

- **G1:** Service time (3 min) applies to the batch. If treated as individual, resource utilization is overestimated by 4x. Throughput per item appears identical to actual throughput.
- **G2:** Waiting time for items 2–4 is overestimated (they arrive before start). If "begin group" logic is unmodeled, service time for the group is fragmented (e.g. completion 1 = 10:08, but arrival was 09:42).
- **G3:** End batching compresses actual duration. If actual work took 30 minutes but was logged as 15 (11:15 to 11:30), service time metrics are biased low for late items.
- **G5:** Shared resource identity inflates utilization. If three analysts worked sequentially on `analyst_pool`, it looks like a single resource working continuously (utilization > 100% is common here).
- **G6:** This creates the classic "zero service, high wait" artifact. Queue time = (17:00 – `queue_arrival`). Service time = 0. Throughput looks instantaneous.
- **G7:** Coarse precision (15 min) hides variance. If real durations are 20–25 min, the recorded 15 min is systematic underreporting.
- **G8:** Safety checks create apparent waiting; if clocks are unsynchronized, queue analysis may incorrectly attribute 35 mins to waiting time instead of a process step.

# 5. Robustness and alternative explanations

- **Resource ID Trust:** If `analyst_pool` (G5) is trusted as a single resource, utilization exceeds 100%, flagging process violations. If treated as shared account (as suggested by "badge-level identity not retained"), utilization is normalized but process conformance (resource consistency) is lost.
- **Timestamp Precision:** If G7 timestamps are exact (ignoring 15-min precision), service time variance is hidden. If interval-censored (real start within 15 min of recorded), service time is uncertain by ±15 min.
- **Multiple Physical Explanations:** 
    1. **G1/G6:** Identical timestamps could be simultaneous execution (G1) or end-of-shift bulk logging (G6). Without context on fixtures, they are ambiguous.
    2. **G2/G8:** Both show staggered starts/ends. G2 is grouped by "begin" button; G8 is natural sequential triage.
    3. **G3/G5:** Both have shared resources (folder vs analyst pool). G3 is end-batching; G5 is concurrent work on shared login.

# 6. Data-collection redesign

**Prioritized recommendations:**

1.  **Unique Execution Events:** Add explicit `start` and `complete` timestamps at case level, not folder/batch level (fixes G3/G6).
2.  **Group Identifiers:** Add optional `batch_id` to separate logical work batches from physical case instances.
3.  **Identity Tracking:** Require badge/ID on shared resource logs (fixes G5); otherwise use session IDs.
4.  **Clock Synchronization:** Ensure queue_arrival system (upstream) and local source (downstream) share a common clock; otherwise log time offsets.
5.  **Precision Metadata:** Store and validate precision field to allow interval-censoring in analysis.
