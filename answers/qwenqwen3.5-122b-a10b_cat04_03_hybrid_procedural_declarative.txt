# 1. Policy Interpretation and Conflict Resolution

## Material Assumptions

1. **Event log completeness**: All activities listed in the trace are captured; no silent activities exist between logged events.
2. **Case uniqueness**: Each case has exactly one `Receive Onboarding Request` as start event.
3. **Terminal exclusivity**: Once `Reject Vendor` or `Activate Vendor` occurs, no other terminal activity follows in the same case.
4. **Clarification cycles**: Multiple `Request Clarification`/`Receive Clarification` pairs are possible before classification.
5. **Post-activation changes**: `Change Bank Details` can occur after activation, triggering suspension and re-verification.
6. **Emergency authorization**: R6's "jointly authorized outside the event log" condition cannot be verified from the event log alone.

## R5/R6 Conflict Resolutions

### Resolution A (Strict Safety): R5 Dominates
- **Rule**: After `Sanctions Escalation`, `Obtain Legal Opinion` MUST precede `Activate Vendor`.
- **Implication**: T6 fails conformance (emergency activation occurred at hour 13, opinion at hour 23).
- **Risk**: May block legitimate emergency activations; requires manual override mechanism.
- **Compliance Risk**: Low operational risk, higher business friction.

### Resolution B (Operational Flexibility): R6 Dominates
- **Rule**: Emergency activation allowed if `Obtain Legal Opinion` arrives within 24 hours of activation.
- **Implication**: T6 passes if time difference  24 hours (1323 = 10 hours, passes).
- **Risk**: Potential legal exposure if emergency justification is insufficient.
- **Compliance Risk**: Higher legal risk, lower operational friction.

### Chosen Resolution: Resolution B with Warning Flag
We adopt Resolution B but treat it as a **temporal warning** rather than a hard control-flow violation. This acknowledges that:
1. The event log lacks an "emergency" attribute to distinguish legitimate vs. illegitimate early activations.
2. Hard blocking would require data not available in the log.
3. A warning allows post-hoc audit review while maintaining flexibility.

**Compliance Risk**: Cases flagged under this resolution require manual compliance review within 48 hours to validate emergency justification. Unvalidated cases should trigger automatic suspension.


## 3. Explanation

**Concurrency**: Initial three checks (`Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account`) modeled as AND-node allowing parallel execution.

**Choices**: Two XOR-nodes: (1) rejection vs. acceptance, (2) low-risk vs. high-risk approval path.

**Clarification Loops**: Approximated using LOOP node. True non-block-structured behavior (clarifications can occur at multiple points) requires POWL edges or Petri net places.

**Terminal Outcomes**: `Reject Vendor` and `Activate Vendor` are mutually exclusive endpoints in the tree structure.

**Post-Activation Behavior**: Deliberately excluded from core tree. `Change Bank Details`  `Suspend Vendor`  re-verification is modeled as separate subprocess invoked after activation (see Resource/Data layer for full logic).

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),  # 48h mean, 24h std
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),     # 12h mean, 6h std
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600),        # 72h mean, 36h std
}

zeta = 2.0
```

## Why Warnings, Not Violations

1. **Business Reality**: Some delays are legitimate (vendor unresponsive, legal complexity).
2. **No Hard Blocking**: Temporal deviations don't indicate control-flow errors, just performance issues.
3. **Audit Trail**: Warnings allow retrospective investigation without halting processes.
4. **Statistical Nature**: With zeta=2.0, ~95% of cases fall within bounds; outliers require human judgment.

**Violation Calculation**: For pair (A, B), compute elapsed time. Flag if:
```
|elapsed_time - mean| > zeta × standard_deviation
```

Example: `Sanctions Escalation`@hour 6  `Obtain Legal Opinion`@hour 23 = 17 hours.
Threshold: 12 ± (2.0 × 6) = [0, 24] hours. Result: 17  [0, 24], so PASS.

```python
def check_resource_segregation(log_df):
    """
    R9: Resource segregation rules
    Returns list of violations with details
    """
    violations = []
    
    # Group by case_id
    for case_id, case_df in log_df.groupby('case_id'):
        
        # Get resources per activity
        activity_resources = {}
        for _, row in case_df.iterrows():
            act = row['activity']
            res = row['resource']
            if act not in activity_resources:
                activity_resources[act] = []
            activity_resources[act].append(res)
        
        # R9a: Verify Bank Account  Approval resource
        verify_resources = set(activity_resources.get('Verify Bank Account', []))
        approval_resources = set()
        for approval_act in ['Manager Approval', 'Compliance Approval']:
            approval_resources.update(activity_resources.get(approval_act, []))
        
        if verify_resources & approval_resources:
            violations.append({
                'case_id': case_id,
                'rule': 'R9a',
                'description': 'Same resource performed Verify Bank Account and Approval',
                'resources': list(verify_resources & approval_resources)
            })
        
        # R9b: Capture Master Data  Activate Vendor resource
        capture_resources = set(activity_resources.get('Capture Master Data', []))
        activate_resources = set(activity_resources.get('Activate Vendor', []))
        
        if capture_resources & activate_resources:
            violations.append({
                'case_id': case_id,
                'rule': 'R9b',
                'description': 'Same resource performed Capture Master Data and Activate Vendor',
                'resources': list(capture_resources & activate_resources)
            })
    
    return violations


def check_emergency_policy(log_df):
    """
    R5/R6: Legal Opinion timing relative to Activation after Sanctions Escalation
    Returns warnings and violations based on chosen policy
    """
    results = {'warnings': [], 'violations': []}
    
    for case_id, case_df in log_df.groupby('case_id'):
        # Check if Sanctions Escalation occurred
        escalation_events = case_df[case_df['activity'] == 'Sanctions Escalation']
        if escalation_events.empty:
            continue
        
        escalation_time = escalation_events.iloc[0]['timestamp']
        
        # Check for Obtain Legal Opinion
        opinion_events = case_df[case_df['activity'] == 'Obtain Legal Opinion']
        
        # Check for Activate Vendor
        activate_events = case_df[case_df['activity'] == 'Activate Vendor']
        if activate_events.empty:
            continue
        
        activate_time = activate_events.iloc[0]['timestamp']
        
        if not opinion_events.empty:
            opinion_time = opinion_events.iloc[0]['timestamp']
            
            # R5: Opinion must precede activation
            if opinion_time < activate_time:
                # Check R6: Within 24 hours?
                time_diff_hours = (opinion_time - activate_time).total_seconds() / 3600
                
                if abs(time_diff_hours) <= 24:
                    results['warnings'].append({
                        'case_id': case_id,
                        'rule': 'R6',
                        'description': f'Emergency activation: Opinion {abs(time_diff_hours):.1f}h after activation',
                        'severity': 'warning'
                    })
                else:
                    results['violations'].append({
                        'case_id': case_id,
                        'rule': 'R5/R6',
                        'description': f'Legal Opinion more than 24h after activation ({time_diff_hours:.1f}h)',
                        'severity': 'violation'
                    })
            else:
                # Opinion before activation - compliant with R5
                pass
        else:
            # No legal opinion at all - violation
            results['violations'].append({
                'case_id': case_id,
                'rule': 'R4',
                'description': 'Sanctions Escalation occurred but no Obtain Legal Opinion',
                'severity': 'violation'
            })
    
    return results


def check_four_eyes_principle(log_df, activity1, activity2):

    Returns cases violating segregation
    """

        result = pm4py.filter_four_eyes_principle(log_df, activity1, activity2)

def check_post_activation_changes(log_df):
    """
    R11: Change Bank Details after activation triggers suspension and re-verification
    """
    violations = []
    
    for case_id, case_df in log_df.groupby('case_id'):
        activate_idx = case_df[case_df['activity'] == 'Activate Vendor'].index
        if activate_idx.empty:
            continue
        
        activate_time = case_df.loc[activate_idx[0], 'timestamp']
        
        # Find bank changes after activation
        bank_changes = case_df[(case_df['activity'] == 'Change Bank Details') & 
                               (case_df['timestamp'] > activate_time)]
        
        for _, change_row in bank_changes.iterrows():
            change_time = change_row['timestamp']
            
            # Check for subsequent suspend
            suspends = case_df[(case_df['activity'] == 'Suspend Vendor') & 
                              (case_df['timestamp'] > change_time)]
            
            if suspends.empty:
                violations.append({
                    'case_id': case_id,
                    'rule': 'R11',
                    'description': f'Change Bank Details at {change_time} without subsequent Suspend Vendor',
                    'severity': 'violation'
                })
            else:
                # Check for re-verification before next payment
                next_payment = case_df[(case_df['activity'] == 'Release First Payment') & 
                                      (case_df['timestamp'] > change_time)]
                
                if not next_payment.empty:
                    re_verify = case_df[(case_df['activity'] == 'Verify Bank Account') & 
                                       (change_time < case_df['timestamp'] < next_payment.iloc[0]['timestamp'])]
                    
                    if re_verify.empty:
                        violations.append({
                            'case_id': case_id,
                            'rule': 'R11',
                            'description': 'Payment released without re-verification after bank change',
                            'severity': 'violation'
                        })
    
    return violations
```

| R1 (Reject/Activate) | ProcessTree, DECLARE, Log Skeleton | Triple-check overhead; false sense of security |
| R7 (Screening before Escalation) | ProcessTree, DECLARE, Log Skeleton | Redundant but provides defense-in-depth |
| R9 (Resource segregation) | DECLARE (indirect), Resource Layer | DECLARE cannot truly enforce; only Resource Layer matters |

**Recommendation**: Keep structural enforcement in ProcessTree (fastest), use DECLARE for exception detection, rely on Resource Layer for authoritative checks.

## Inconsistencies Under Loops

1. **Clarification Loops**: DECLARE `responded_existence` satisfied vacuously if no clarification requested. ProcessTree loop requires at least one iteration if entered. **Resolution**: Use ProcessTree for mandatory loops, DECLARE for optional patterns.

2. **Post-Activation Changes**: R11 creates new control-flow after terminal `Activate Vendor`. Traditional process trees assume single termination. **Resolution**: Treat post-activation as separate subprocess triggered by state change.

## Vacuity in Declarative Rules

- `responded_existence(A, B)` is satisfied if A never occurs (no obligation triggered).
- `noncoexistence(A, B)` is satisfied if neither occurs.

**Mitigation**: Combine with `existence` templates for activities that should occur in accepted cases.

## Missing Case Attributes

| Missing Attribute | Impact | Mitigation |
|-------------------|--------|------------|
| `emergency_flag` | Cannot validate R6 exceptions | Conservative default; manual audit |
| `risk_score` | Cannot verify Classification accuracy | Assume `Classify Risk` output is authoritative |
| `justification_text` | Cannot assess quality of clarifications | Flag for human review |
| `authorization_code` | Cannot prove joint authorization for emergencies | Require external system integration |

## Timestamp-Only Limitations

1. **Duration vs. Elapsed Time**: Event logs record timestamps, not durations. Cannot detect activity duration violations without additional data.
2. **Concurrent Execution**: Cannot determine true concurrency from sequential timestamps alone.
3. **Timezone Issues**: Global operations may have timezone mismatches affecting temporal profiles.

## Support/Confidence Metadata Risk

Treating `support: 1.0` as normative truth assumes:
1. Training data represents all valid scenarios.
2. No policy changes since model creation.
3. Complete event logging.

**Reality**: These are statistical estimates, not legal guarantees. Always combine with deterministic rule checks.

# 10. Deployment Recommendation

## Canonical Procedural Representation

**Primary Model**: Accepting Petri Net (not shown in code above, but recommended over ProcessTree for production).
- **Reason**: Handles non-block-structured behavior (clarification loops at arbitrary points) better than ProcessTree.
- **Tool**: PM4Py `process_tree_to_petri_net()` conversion or direct discovery.

## Authoritative Policy Layer

**Order of Authority** (highest to lowest):
1. **Resource/Data Layer** (R9, R11, R5/R6 exceptions) - Contains business-critical constraints requiring external context.
2. **ProcessTree/Petri Net** (Core control flow) - Fast structural validation.
3. **DECLARE** (Exception patterns) - Detects deviations from expected patterns.
4. **Log Skeleton** (Simple constraints) - Quick pre-filtering.
5. **Temporal Profile** (Performance monitoring) - Warnings only.

## Conformance Check Execution Order

```python
def run_conformance_suite(log_df):
    results = {}
    
    # 1. Quick pre-filters (Log Skeleton)
    results['skeleton'] = pm4py.conformance_log_skeleton(log_df, log_skeleton)
    if any_violations(results['skeleton']):
        return results  # Early exit for structural failures
    
    # 2. Structural validation (ProcessTree/Petri Net)
    results['procedural'] = pm4py.conformance_alignement(log_df, procedural_model)
    
    # 3. Declarative pattern checking
    results['declare'] = pm4py.conformance_declare(log_df, declare_model)
    
    # 4. Resource/data-aware checks (authoritative)
    results['segregation'] = check_resource_segregation(log_df)
    results['emergency'] = check_emergency_policy(log_df)
    results['post_activation'] = check_post_activation_changes(log_df)
    
    # 5. Temporal profiling (warnings only)
    results['temporal'] = pm4py.conformance_temporal_profile(log_df, temporal_profile, zeta=2.0)
    
    return results
```

## Surfacing Contradictory Findings

**Priority Matrix**:

| Finding Type | Action | User Notification |
|--------------|--------|-------------------|
| Structural violation (ProcessTree) | Block case progression | Critical alert |
| Resource segregation failure | Block case progression | Critical alert + assigned reviewer |
| Declarative pattern deviation | Flag for review | Warning with explanation |
| Temporal deviation | Log only | Dashboard notification |
| Policy conflict (R5/R6) | Route to compliance team | Escalation ticket |

**Contradiction Resolution Protocol**:
1. If Resource Layer says PASS but ProcessTree says FAIL  Investigate logging gap.
2. If DECLARE says PASS but ProcessTree says FAIL  Trust ProcessTree (structural > pattern).
3. If Temporal says WARNING but all others PASS  Monitor, do not block.
4. If R5/R6 conflict detected  Apply chosen resolution consistently; document exception.

**Dashboard Display**:

This layered approach ensures:
- **Speed**: Quick filters catch obvious violations.
- **Accuracy**: Authoritative checks handle complex conditions.
- **Flexibility**: Exceptions documented and auditable.
- **Transparency**: Users understand why decisions were made.
