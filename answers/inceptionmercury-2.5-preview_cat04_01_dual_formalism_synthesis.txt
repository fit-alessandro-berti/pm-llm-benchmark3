

# 1. Assumptions and Interpretation

1.  **Risk Route Representation:** The choice between `Supervisor Review` (low) and (`Quality Review` + `Regulatory Review`) (high) is represented by an XOR split. Since we lack data events, we treat these as mutually exclusive control-flow paths within the model.
2.  **Supplier Consultation:** The optional nature of `Consult Supplier` is represented by an XOR split where one branch contains `Consult Supplier` and the other is silent.
3.  **Passing Inspection:** The outcome of inspection is not an event label. A passing inspection is abstracted by a Loop operator. When `Inspect Trial` is followed immediately by `Release Material`, a passing outcome is implied.
4.  **Duplicate Labels:** Visible labels are not duplicated. While some models (like WF-nets) require silent transitions or duplicated labels to enforce synchronization, this representation relies on partial-order relations to avoid structural inflation.
5.  **Approximation Policy:** For the Process Tree, a **Permissive Over-Approximation** is used. Because standard tree operators are block-structured, we cannot strictly enforce that `Release Material` waits for three independent, non-branching inputs without duplicating subtrees. The tree allows valid interleavings but may also admit unintended orders.
6.  **Overlap Interpretation:** "May overlap" is interpreted as **true concurrency**. In the Partial Order (POWL), this is modeled by the absence of a constraint; in the Process Tree, by the `PARALLEL` operator.

# 3. PM4Py Process-Tree Model

```text
Sequence(
  Register Deviation,
  Parallel(
    Sequence(Contain Material, Plan Verification),
    Sequence(
      Analyze Root Cause,
      Parallel(
        Design Corrective Action,
        Sequence(
           XOR(Sequence(Quality Review, Regulatory Review), Supervisor Review),
           XOR(Consult Supplier, Silent)
        )
      )
    )
  ),
  Parallel(
    Sequence(Execute Trial, Inspect Trial, Adjust Parameters),
    Silent
  ),
  Release Material,
  Archive Case
)
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# Helper to create nodes
def node(op, children):
    t = ProcessTree()
    t.operator = op
    t.children = children
    for c in children:
        c.parent = t
    return t

def leaf(label):
    t = ProcessTree()
    t.operator = Operator.LEAF
    t.label = label
    return t

# Construct tree structure
# Approximation: The model flattens the Trial synchronization to be permissive.
# It assumes Trial is independent enough to sit in a parallel block before Release.
root = node(Operator.SEQUENCE, [
    leaf("Register Deviation"),
    node(Operator.PARALLEL, [
        node(Operator.SEQUENCE, [leaf("Contain Material"), leaf("Plan Verification")]),
        node(Operator.SEQUENCE, [
            leaf("Analyze Root Cause"),
            node(Operator.PARALLEL, [
                leaf("Design Corrective Action"),
                node(Operator.SEQUENCE, [
                    node(Operator.XOR, [
                        node(Operator.SEQUENCE, [leaf("Quality Review"), leaf("Regulatory Review")]),
                        leaf("Supervisor Review")
                    ]),
                    node(Operator.XOR, [leaf("Consult Supplier"), ProcessTree()])
                ])
            ])
        ])
    ]),
    # Loop approximation: Execute-Inspect-Adjust as a sequence block
    node(Operator.PARALLEL, [
        node(Operator.LOOP, [
            node(Operator.SEQUENCE, [leaf("Execute Trial"), leaf("Inspect Trial")]),
            node(Operator.SEQUENCE, [leaf("Adjust Parameters"), leaf("Execute Trial")])
        ]),
        ProcessTree() # Silent placeholder to keep parallelism
    ]),
    leaf("Release Material"),
    leaf("Archive Case")
])

tree = root
```

**Approximation Limitations:**
The Process Tree cannot strictly enforce the "Release Material requires all paths" synchronization. In the tree above, `Release Material` follows a `SEQUENCE`, effectively forcing a specific order where the parallel block finishes before Release starts. While this matches the flow, the tree cannot express that `Execute Trial` strictly depends on *both* branches of the parallel block unless we duplicate activities. Additionally, the Loop operator in the tree is simplistic and may not correctly model the conditional repeat-until behavior without extra guards.

# 4. PM4Py POWL Model

```text
Transition(Register)
Transition(Contain)
Transition(Plan)
Transition(Analyze)
Transition(Design)
Transition(Supervisor)
Transition(Quality)
Transition(Regulatory)
Transition(Supplier)
Transition(Execute)
Transition(Inspect)
Transition(Adjust)
Transition(Release)
Transition(Archive)

Order(
  Register -> Contain
  Register -> Analyze
  Contain -> Plan
  Analyze -> Design
  Analyze -> Supervisor
  Analyze -> Quality
  Analyze -> Regulatory
  Analyze -> Supplier
  Plan -> Execute
  Design -> Execute
  Execute -> Inspect
  Inspect -> Adjust
  Adjust -> Execute
  Inspect -> Release
  Supplier -> Release
  Supervisor -> Release
  Quality -> Release
  Regulatory -> Release
  Release -> Archive
)
```

```python
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Create nodes
nodes = [Transition(a) for a in [
    "Register Deviation", "Contain Material", "Plan Verification",
    "Analyze Root Cause", "Design Corrective Action", "Supervisor Review",
    "Quality Review", "Regulatory Review", "Consult Supplier",
    "Execute Trial", "Inspect Trial", "Adjust Parameters",
    "Release Material", "Archive Case"
]]

# Create order
powl = StrictPartialOrder(nodes)

# Add edges for dependencies
edges = [
    ("Register Deviation", "Contain Material"),
    ("Register Deviation", "Analyze Root Cause"),
    ("Contain Material", "Plan Verification"),
    ("Analyze Root Cause", "Design Corrective Action"),
    ("Analyze Root Cause", "Supervisor Review"),
    ("Analyze Root Cause", "Quality Review"),
    ("Analyze Root Cause", "Regulatory Review"),
    ("Analyze Root Cause", "Consult Supplier"),
    ("Plan Verification", "Execute Trial"),
    ("Design Corrective Action", "Execute Trial"),
    ("Execute Trial", "Inspect Trial"),
    ("Inspect Trial", "Adjust Parameters"),
    ("Adjust Parameters", "Execute Trial"),
    ("Inspect Trial", "Release Material"),
    ("Consult Supplier", "Release Material"),
    ("Supervisor Review", "Release Material"),
    ("Quality Review", "Release Material"),
    ("Regulatory Review", "Release Material"),
    ("Release Material", "Archive Case")
]

for source, target in edges:
    s = next(n for n in nodes if n.name == source)
    t = next(n for n in nodes if n.name == target)
    powl.order.add_edge(s, t)

# Explicitly define optional path (XOR) using OperatorPOWL (conceptual)
# In practice, the absence of edges in POWL implies flexibility.
```

**Concurrency Explanation:**
Pairs such as `Plan Verification` and `Quality Review` remain unconnected by edges because they are independent paths. Similarly, `Consult Supplier` and `Execute Trial` are unconstrained to allow true overlap, matching the narrative's allowance for concurrency.

| :--- | :--- | :--- | :--- | :--- | :--- |

| Duplicate labels | Avoided | N/A | None | None | None |

# 7. Preferred Representation and Validation Plan

**Preferred Representation:** The **POWL** model is preferred. It directly encodes the non-block-structured dependencies (e.g., Trial waits for both Plan and Design) without structural approximation. Process Trees impose a hierarchy that conflicts with the cross-dependencies in the narrative.

**Validation Plan:**
1.  **Conversion:** Convert both models to Petri Nets using `pm4py.convert_to_petri_net`.
2.  **Soundness:** Run `pm4py.check_soundness` on the resulting nets to check for deadlocks or lack of progress.
3.  **Playout:** Perform bounded play-out (`pm4py.play_out`) to verify traces match intended behavior.
4.  **Tests:** Use positive test traces (T1-T4) and negative test traces (T6-T8) against simulation traces.
5.  **Silent Behavior Check:** Ensure `SilentTransition` counts in the tree do not exceed expectations.
6.  **Limitations:** Petri Net conversion may lose the specific "at most once" constraint on `Consult Supplier`, as standard nets do not easily encode counting constraints without extensions.

# 8. Final Self-Critique

1.  **Loop Constraint:** The Process Tree loop approximation (`LOOP` operator) is structural and does not enforce that `Adjust Parameters` only occurs on *failures*. It simply cycles activities regardless of data conditions.
2.  **Validation Scope:** The validation plan does not explicitly check the "at most once" constraint on `Consult Supplier` because standard Petri nets do not enforce this without specific place invariants.
3.  **Trace Interpretation:** In the behavioral witnesses, T5 ("Bad Sync") assumes approval routes are implicitly skipped. In strict event logs, skipping is often impossible (no event means "done"), so this witness is logically ambiguous in a real system.
