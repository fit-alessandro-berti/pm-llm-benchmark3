# 1. Delay-decomposition definitions

**Notation.** Case index c, branch index i  {A, B, C}. Timestamps are in minutes after the case's own clock; all durations are in minutes.

| Symbol | Meaning |
|---|---|
| a_c | arrival (entry to the overall process) |
| f_c | fork_release (earliest permitted start of all branch work) |
| s_ci, e_ci | start and end of branch i in case c |
| s_Fc, e_Fc | start and end of the final activity F (Release Decision) |
| s_ci - f_c | branch queue start offset (assumed  0) |

**Decomposition components**

1. **Upstream elapsed:** U_c = f_c  a_c
2. **Branch queue:** Q_ci = s_ci  f_c
3. **Branch active service:** V_ci = e_ci  s_ci
4. **Join-ready (derived, not logged):** J_c = max_i e_ci. The critical branch K_c = argmax_i e_ci, with ties broken deterministically in the order A < B < C. A tie flag is recorded so that ties are never hidden.
5. **Branch synchronization wait:** W_ci = J_c  e_ci  0. By construction W_cK = 0 for the critical branch.
6. **Elapsed fork-join stage:** S_c = J_c  f_c. Because e_ci  f_c = Q_ci + V_ci, the max-based identity is S_c = max_i (Q_ci + V_ci). The stage is therefore the critical branch's own queue plus service, measured from the fork.
7. **Downstream queue before F:** D_c = s_Fc  J_c
8. **Final service:** V_Fc = e_Fc  s_Fc
9. **Total flow time:** T_c = e_Fc  a_c

**Identity (no double counting along the critical path):**

T_c = U_c + S_c + D_c + V_Fc

Checking this on the data: (fa) + (Jf) + (s_FJ) + (e_Fs_F) = e_F  a holds for each telescoping step. Each minute of wall-clock time between arrival and final end is assigned to exactly one of the four terms.

**Why summing all branch synchronization waits double-counts elapsed time.**

Summing W_ci over i gives _i W_ci = _i (S_c  (Q_ci + V_ci)). This is not a wall-clock quantity. When two branches are both finished and waiting, the same minute is counted once for each waiting branch. The non-overlapping (union) waiting time is the window from the first branch completion to the join:

- Union of waiting windows = J_c  min_i e_ci = max_i W_ci
- Naive sum = _i W_ci  max_i W_ci

Example, F07: W = (A 25, B 0, C 52). The naive sum is 77 min, but the real waiting window is 10:03  10:55 = 52 min. The 25 min of A's wait lies inside C's wait and is counted twice. The same overlap affects the naive sum of branch elapsed times (_i (e_i  f) = 50 + 75 + 23 = 148 min for F07 versus a true fork-join stage of 75 min).

The additive, non-overlapping components are therefore U, S (the critical path), D, and V_F. The W_ci values are reported only as diagnostics of each branch's slack. Across the 12 cases, the naive sum of W is 549 min. The union-based total (_c max_i W_ci) is 402 min, so the naive sum overstates waiting by 147 min.

**Assumptions (labelled):**

- **A1.** fork_release is the earliest time a branch may start; a branch's queue is measured from that time.
- **A2.** J_c = max_i e_ci is the join rule given by the scenario. No join event is logged, so this is an inferred quantity.
- **A3.** The logged final_resource is the actual server used. Resource occupancy is inferred from the other cases' logged final intervals.
- **A4.** Timestamps are accurate to ±1 min. Differences of 0–1 min are treated as unresolved.
- **A5.** Branch service is non-preemptive and is measured from start to end.

**Trap check.** A has the largest mean service time (50 min), but it is last in only 2 of 12 cases. B has the smaller service time but controls the join most often.

**Frequency of being last.** No exact ties occur at the join in the observed data. The smallest margin between the last and second-last branch is 5 min (F01, F08, F10). Under ±1 min measurement error, the critical identity is robust, since a 5-min margin cannot be reversed by 1-min errors on each timestamp.

**Tail contribution to join_ready.** B is last in the high-tail cases: S = 75 min in F07 and F12, and 65 min in F03, F06, and F09. Seven of the eight cases with total flow  115 min have B as the critical branch. The only exception is F04, which is C-critical.

**Influence ranking**

1. **B: primary controller.** It is last in 8 of 12 cases. Its queue is the largest and most variable (5–30 min), and its queue plus service has the largest mean and tail. Its queue-reduction counterfactual is worth 82.5 min, about five times the A-service counterfactual.
2. **A and C: near-tie for the secondary position.** Both are last in 2 of 12 cases. A's counterfactual gain (15 min) slightly exceeds C's (12 min). A's contribution is deterministic: its 50-min service sets a floor on the join in every case, and it is last only when its service plus queue is ahead of B. C is volatile. Its queue ranges from 5 to 35 min and its synchronization waits are large, but it is last only in F04 (queue 35) and F08 (queue 25). A and C should be treated as co-secondary, with A ahead on the measured counterfactual. This is a judgment call, not a clear separation.

The branch with the largest mean service (A) is not the most influential. B controls the join most often, and its variance and queueing drive the tail.

# 4. Counterfactual redesign analysis

Each counterfactual is evaluated under two bounds that bracket the unknown final-station behaviour:

- **Fixed-start bound:** the final start time is unchanged. Any earlier join produces zero saving. This represents a release gate or a fixed daily slot.
- **Rigid-queue bound:** downstream queue D stays at its observed duration, so the saving equals the join reduction J. This is an optimistic but common modelling choice.

Immediate dispatch (CF3b) is a separate upper bound.

**Counterfactual 1: A service reduced by 20% (50  40 min)**

- Direct benefit: only where A is critical. F01 saves 5 min (new join 08:55, set by B). F11 saves 10 min (new join 11:20, a tie with B).
- Zero-benefit cases: 10 of 12. In the other ten cases, A's end is already earlier than the critical branch.
- Total saving (rigid): 15 min, mean 1.25 min per case.
- Fixed-start bound: 0.
- Secondary effects: F11 creates a new A/B tie, so further A reduction gives no benefit. A's share of criticality would only be relevant after B is also reduced. The tail (max 130 min, F07) is unchanged.

**Counterfactual 2: B queue delay reduced by 50%**

Per-case join reductions:

| case | new B_end | new join | J (min) |
|---|---|---|---|
| F02 | 09:15 | 09:15 (tie A) | 10 |
| F03 | 09:35 | 09:35 | 10 |
| F05 | 09:57.5 | 10:00 (A) | 10 |
| F06 | 10:15 | 10:15 (tie A) | 15 |
| F07 | 10:40 | 10:40 | 15 |
| F09 | 11:02.5 | 11:02.5 | 12.5 |
| F10 | 11:10 | 11:15 (A) | 5 |
| F12 | 11:55 | 11:55 | 15 |

- Direct benefit: 8 cases, total J 82.5 min, mean 6.9 min per case. Realised benefit is 72% of the 115 min of B queue that is removed, because A takes over the join in several cases.
- Zero-benefit cases: 4 (F01, F04, F08, F11). In each, B is not last. A is last in F01 and F11, and C is last in F04 and F08.
- Migration: after the change, A is last in six cases, B in four, and C in two. Two cases (F02, F06) have exact A/B ties, so the deterministic tie-break matters.
- Rigid-queue total: mean flow falls from 115.3 to 108.4 min. P90 falls from 124.5 to about 114.5 min. The maximum falls from 130 to 115 min.
- Fixed-start bound: 0.
- Secondary effects: B utilisation rises. The observed B queue occurs while two or more B jobs are in service, so the implied B capacity is not a single machine (see Section 7).

**Counterfactual 3: Final-station capacity or downstream queue reduction**

This counterfactual has two variants.

- **3a. Add final-station capacity (remove only server-blocked minutes):** Saving is 35 min (any-server view). F05, F09, F10, and F11 gain 10, 10, 5, and 10 min. Eight cases gain nothing. Using the logged-server view instead gives 73 min. The range of 35–73 min reflects the uncertainty about server pooling.
- **3b. Immediate dispatch (remove all downstream queue):** Saving is 176 min, mean 14.7 min per case, with a gain in all 12 cases. Mean flow falls to 100.6 min and the maximum to 115 min. This is an upper bound. Realistic dispatch would not recover the whole queue, and the rigid-queue assumption does not apply.

Direct and secondary effects:

- Neither variant changes J. Critical-branch counts stay at A = 2, B = 8, C = 2.
- Neither variant reduces the branch queues or the tail of the branch completion distribution.
- 3a has a large relative effect only where the server was actually blocked. 3b shows the value of the 141 min of unexplained wait, and that value depends on what is causing it.

**Does final-station congestion mask branch improvements?**

- Under the fixed-start bound, all branch improvements are fully masked: CF1 and CF2 give zero.
- Under the rigid-queue bound, branch improvements pass through in full.
- Under a resource-constrained model, masking is partial. Example, F09 with B queue 50%: the join moves to 11:02.5, but F2 is not free until 11:25 (F08 finishes) and F1 is occupied until 11:30 by F07. The earliest feasible start is about 11:25, so only 5 of the 12.5 min join gain reaches the case.

A full resource-constrained re-simulation is needed to quantify this masking precisely.

**Additional counterfactual (for comparison): C queue reduced by 50%**

- Gains are in F04 (J = 7 min, new join 09:45, set by A) and F08 (J = 5 min, new join 10:45, set by A).
- Total 12 min, zero gain in 10 cases.

# 5. Recommended redesigns and risks

**Redesign 1: Event-driven dispatch at the final station (release on join, with a reserved server)**

- **Target:** the 141 min of downstream wait during which a final server was not occupied by another logged case (80% of queue minutes). Under the any-server view, the logged minutes that are server-blocked are only 35 min, so capacity is not the main constraint.
- **Throughput:** Arrivals are about every 15 minutes, so throughput is arrival-limited. Throughput is not expected to change much. The benefit is in flow time and WIP, with a potential reduction of 176 min in total (upper bound).
- **Flow-time tail:** Max flow falls from 130 to 115 min and P90 from about 124.5 to about 114 min under the upper bound. Realistic gains would be smaller.
- **Resource utilisation:** The final station is at about 57% utilisation over its active window (240 min of service across two servers in 212 min). F1 is at about 66% and F2 at about 67%. There is headroom, so this change is low-cost. It increases utilisation only slightly, but it adds some idle time between cases.
- **New bottlenecks:** The dispatch rule may create contention on a reserved server, and a reserved server may idle when no case is ready. If the wait is actually a documentation or sign-off gate, a dispatch rule changes nothing.
- **Synchronization effects:** None on the branches, since J is unchanged.
- **Pilot and measurement first:** Log a join-ready event (the time the last branch completes), a final-server availability signal, and the reason code for any wait between J and s_F. Pilot the reserved-server rule on one resource for a week. Track D (downstream queue) and the unexplained share.

**Redesign 2: B-branch capacity and sequencing (reduce B queue)**

- **Target:** B queue, which is the largest controllable driver of the join. Mean queue is 19.2 min, total 230 min, and the highest queue (30 min) occurs in F06, F07, and F12.
- **Throughput:** Again arrival-limited, so no change expected. The benefit is in flow time and WIP.
- **Flow-time tail:** Under the rigid-queue bound, P90 falls from about 124.5 to about 114.5 min and the maximum from 130 to 115 min. Realistic gains depend on how much B's queue is capacity-driven.
- **Resource utilisation:** B's total service is 450 min. Its span is 235 min (08:15 to 12:10), so B cannot be a single server. Its implied concurrency is at least 2 and possibly 4. Adding one unit of B capacity would reduce queue but increase idle time, and the right size is unknown.
- **New bottlenecks:** Once B's queue is reduced, A becomes the critical branch in six cases, with exact ties in two. A's 50-min fixed service then determines the join, and a further B reduction yields little. Reducing B's queue also brings the next bottleneck, A, into view.
- **Synchronization effects:** Non-critical branches (C especially) wait longer as the join moves earlier relative to their completion, so the synchronization waits of A and C become the next lever.
- **Pilot and measurement first:** Record B machine or pool identifiers, B concurrency, B queue length by time, and whether B queues occur at times of full concurrency. Pilot a B-first admission rule or an extra pool unit for two hours in the morning peak before committing capacity.

**Priority.** Redesign 1 is cheap and low-risk, and it is a measurement exercise first. Redesign 2 has the larger potential effect on the critical path but needs capacity knowledge that the data does not provide.

# 6. Reproducible Python

```python
"""
Fork-join delay decomposition for the Release Decision scenario (2026-05-19).

Run:  python fork_join_decomposition.py
Requires: pandas, numpy. PM4Py is optional; its step is wrapped in try/except.
All quantities are minutes unless stated. Timestamps are parsed from HH:MM on 2026-05-19.
"""
import numpy as np
import pandas as pd
from io import StringIO

pd.set_option("display.width", 220)
pd.set_option("display.max_columns", 40)

# ---------------------------------------------------------------- data
RAW = """case,arrival,fork_release,A_start,A_end,B_start,B_end,C_start,C_end,final_start,final_end,final_resource
F01,07:55,08:10,08:10,09:00,08:15,08:55,08:20,08:38,09:08,09:28,F1
F02,08:05,08:25,08:25,09:15,08:45,09:25,08:30,08:50,09:40,10:00,F2
F03,08:20,08:40,08:40,09:30,09:00,09:45,08:45,09:03,10:00,10:20,F1
F04,08:35,08:55,08:55,09:45,09:05,09:35,09:30,09:52,10:10,10:30,F2
F05,08:50,09:10,09:10,10:00,09:35,10:10,09:15,09:35,10:20,10:40,F1
F06,09:05,09:25,09:25,10:15,09:55,10:30,09:40,10:00,10:45,11:05,F2
F07,09:20,09:40,09:40,10:30,10:10,10:55,09:45,10:03,11:10,11:30,F1
F08,09:35,09:55,09:55,10:45,10:00,10:30,10:20,10:50,11:05,11:25,F2
F09,09:50,10:10,10:10,11:00,10:35,11:15,10:15,10:35,11:30,11:50,F1
F10,10:05,10:25,10:25,11:15,10:45,11:20,10:30,10:50,11:40,12:00,F2
F11,10:20,10:40,10:40,11:30,10:50,11:20,10:45,11:03,11:50,12:10,F1
F12,10:35,10:55,10:55,11:45,11:25,12:10,11:00,11:18,12:20,12:40,F2
"""
DAY = "2026-05-19"
MIN = pd.Timedelta(minutes=1)
BR = ["A", "B", "C"]   # fixed order = deterministic tie-break priority (first max wins)
ACT = {"A": "A_Laboratory_Assay", "B": "B_Machine_Stress_Test",
       "C": "C_Documentation_Review", "F": "F_Release_Decision"}

raw = pd.read_csv(StringIO(RAW))
df = raw.copy()
for col in raw.columns:
    if col not in ("case", "final_resource"):
        df[col] = pd.to_datetime(DAY + " " + raw[col], format="%Y-%m-%d %H:%M")

# ---------------------------------------------------------------- helpers
def mins(start, end):
    """Duration in minutes between two timestamp Series."""
    return (end - start) / MIN

def join_ready(d):
    # CUSTOM: join_ready is not logged; it is derived as max over branch completions (A2).
    return pd.DataFrame({b: d[f"{b}_end"].values for b in BR}, index=d.index).max(axis=1)

def decompose(d):
    """Full case-level decomposition using max-based fork-join logic."""
    E = pd.DataFrame({b: d[f"{b}_end"].values for b in BR}, index=d.index)
    J = E.max(axis=1)                                   # CUSTOM join_ready
    o = pd.DataFrame({"case": d["case"].values}, index=d.index)
    o["upstream_elapsed"] = mins(d.arrival, d.fork_release)
    for b in BR:
        o[f"{b}_queue"] = mins(d.fork_release, d[f"{b}_start"])     # CUSTOM queue from fork
        o[f"{b}_service"] = mins(d[f"{b}_start"], d[f"{b}_end"])
    o["join_ready"] = J.dt.strftime("%H:%M")
    # Deterministic tie-break: first branch in BR order among the maxima
    o["critical_branch"] = np.array(BR)[E.values.argmax(axis=1)]
    o["tie_at_join"] = (E.values == J.values[:, None]).sum(axis=1) > 1
    for b in BR:
        o[f"{b}_sync"] = mins(E[b], J)                      # CUSTOM sync wait (not in DFG)
    o["fork_join_stage"] = mins(d.fork_release, J)          # CUSTOM = J - f = max(Q+V)
    o["downstream_queue"] = mins(J, d.final_start)          # CUSTOM downstream queue
    o["final_service"] = mins(d.final_start, d.final_end)
    o["total_flow_time"] = mins(d.arrival, d.final_end)
    # Identity check: no double counting along the critical path
    assert np.allclose(o.upstream
