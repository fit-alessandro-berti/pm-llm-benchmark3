# 1. Assumptions and Interpretation

1. **Low-risk / high-risk choice:** Represented as control-flow exclusive choice `XOR` between `Supervisor Review` and concurrent `Quality Review + Regulatory Review`. The data condition “low vs high risk” is not modeled; non-deterministic choice abstracts the decision. The choice is positioned after `Analyze Root Cause` to enforce rule 5 that route is selected after analysis.
2. **Optional supplier consultation:** Represented as `XOR(Consult Supplier, silent/skip)`. Case data “supplier involved” is not modeled; the choice is non-deterministic. At-most-once is enforced by placing a single `Consult Supplier` transition in the model. Ordering `Analyze Root Cause -> choice` and `choice -> Release Material` enforces “may start only after analysis” and “must be complete before release”.
3. **Passing inspection abstraction:** `Inspect Trial` is a single visible label. Pass vs fail is not an event label or data attribute. Fail is abstracted as loop-redo via `Adjust Parameters` followed by a new `Execute Trial–Inspect Trial` cycle; pass is abstracted as loop-exit with no following `Adjust Parameters`. Therefore `Adjust Parameters` occurring implies failure, absence after last `Inspect Trial` implies pass.
4. **Duplicate visible labels:** Not permitted in either model submitted here. Duplication would allow more interleavings but creates label-duplication risk for conformance, frequency, and provenance analysis. Consequences are discussed in §6.
5. **Approximation policy for the process tree:** Conservative under-approximation without duplication. The tree admits only a subset of intended behavior and admits no unsafe release or trial ordering. Specifically it adds precedence `Plan Verification + Design Corrective Action before approvals/supplier-trial phase` to obtain block structure, thereby excluding some intended overlaps rather than admitting forbidden orderings.
6. **“May overlap / may proceed independently”:** Interpreted as absence of order constraint, i.e. true concurrency in the partial-order semantics. After conversion to Petri net / interleaved trace semantics this appears as all interleavings preserving required precedences. Completion-time logging means concurrency is observed as either completion order.
7. **Recording semantics:** Traces are sequences of activity completions. “A starts only after B is complete” is modeled as `B -> A` completion precedence. No separate start events are modeled.
8. **Trial cycle:** Exactly `Execute Trial -> Inspect Trial` per iteration, with `Adjust Parameters` strictly between a failed `Inspect Trial` and the next `Execute Trial`. Zero or more failures followed by one pass. Infinite looping is theoretically allowed; bounded playout is used for validation.

# 2. Intended Dependency Specification

Abbreviations: RD=Register Deviation, CM=Contain Material, ARC=Analyze Root Cause, PV=Plan Verification, DCA=Design Corrective Action, SR=Supervisor Review, QR=Quality Review, RR=Regulatory Review, CS=Consult Supplier, ET=Execute Trial, IT=Inspect Trial, AP=Adjust Parameters, RM=Release Material, AC=Archive Case.

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|----|------------------------------|------------------------------|----------|-----------|
| D01 | RD | CM, ARC | precedence + concurrency | Every case starts with RD; CM and ARC may proceed independently after RD |
| D02 | CM | PV | precedence | PV may start only after CM complete |
| D03 | ARC | DCA | precedence | DCA may start only after ARC complete |
| D04 | ARC | risk-route choice {SR xor (QR par RR)} | precedence | Risk route selected after ARC; low needs SR, high needs QR+RR concurrent |
| D05 | SR vs QR+RR | — | XOR choice; QR concurrent RR | Data-driven risk decision abstracted as control-flow alternative |
| D06 | ARC | CS if selected | precedence | CS may start only after ARC |
| D07 | CS | RM | precedence if selected | If selected, must be complete before RM; otherwise skipped |
| D08 | CS | PV, DCA, approvals, trial loop | concurrency | CS may overlap design, planning, approvals, trial work |
| D09 | DCA, PV | ET (trial loop entry) | joint precedence / synchronization | ET may start as soon as both DCA and PV complete |
| D10 | Approval route | trial loop | concurrency (no order) | Approval does not have to complete before trial, may overlap trial cycle |
| D11 | ET | IT | precedence, repeated | Trial cycle is ET followed by IT |
| D12 | IT-fail | AP -> next ET-IT | LOOP redo | If inspection fails, AP then new ET-IT; repeats until pass |
| D13 | AP | final passing IT | exclusion | AP must never occur after passing inspection |
| D14 | Trial-pass (loop exit), approval completion, (CS if selected) | RM | multi-way synchronization (AND-join) | RM requires passing IT + selected approvals + CS if present |
| D15 | RM | AC | precedence | Archive after Release; AC ends case |
| D16 | PV vs DCA; CM vs ARC; CM vs DCA/approvals; PV vs approvals | — | concurrency | Independent work streams: containment branch vs analysis branch; planning vs design vs approvals except stated precedences |

# 3. PM4Py Process-Tree Model

## Compact expression

```text
->( RD, +( ->(CM, PV), ->(ARC, DCA) ), +( *( ->(ET, IT), AP ), X( SR, +(QR, RR) ), X( CS, tau ) ), RM, AC )
with RD='Register Deviation', CM='Contain Material', PV='Plan Verification',
ARC='Analyze Root Cause', DCA='Design Corrective Action',
ET='Execute Trial', IT='Inspect Trial', AP='Adjust Parameters',
SR='Supervisor Review', QR='Quality Review', RR='Regulatory Review',
CS='Consult Supplier', RM='Release Material', AC='Archive Case'
```

Mapping to narrative: outer `->` enforces start RD and end RM->AC. First `+` preserves the two initial streams `CM->PV` concurrent with `ARC->DCA`. Second `+` makes trial-loop, approval-choice, and optional-CS concurrent, preserving approval-trial overlap. `*(->(ET,IT),AP)` is repeat-until; `X(SR,+(QR,RR))` is risk choice; `X(CS,tau)` is optionality. The expression adds one non-intended sequencing: the whole first `+` must complete before the second `+` starts.

## Self-contained construction code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

# leaves
RD = ProcessTree(label="Register Deviation")
CM = ProcessTree(label="Contain Material")
PV = ProcessTree(label="Plan Verification")
ARC = ProcessTree(label="Analyze Root Cause")
DCA = ProcessTree(label="Design Corrective Action")
SR = ProcessTree(label="Supervisor Review")
QR = ProcessTree(label="Quality Review")
RR = ProcessTree(label="Regulatory Review")
CS = ProcessTree(label="Consult Supplier")
ET = ProcessTree(label="Execute Trial")
IT = ProcessTree(label="Inspect Trial")
AP = ProcessTree(label="Adjust Parameters")
RM = ProcessTree(label="Release Material")
AC = ProcessTree(label="Archive Case")
tau = ProcessTree()  # silent skip for optional CS

# SEQ(CM,PV)
seq_cmpv = ProcessTree(operator=Operator.SEQUENCE)
seq_cmpv.children = [CM, PV]
CM.parent = seq_cmpv
PV.parent = seq_cmpv

# SEQ(ARC,DCA)
seq_arcdca = ProcessTree(operator=Operator.SEQUENCE)
seq_arcdca.children = [ARC, DCA]
ARC.parent = seq_arcdca
DCA.parent = seq_arcdca

# PAR( SEQ(CM,PV), SEQ(ARC,DCA) )
par_phase2 = ProcessTree(operator=Operator.PARALLEL)
par_phase2.children = [seq_cmpv, seq_arcdca]
seq_cmpv.parent = par_phase2
seq_arcdca.parent = par_phase2

# SEQ(ET,IT)
seq_et_it = ProcessTree(operator=Operator.SEQUENCE)
seq_et_it.children = [ET, IT]
ET.parent = seq_et_it
IT.parent = seq_et_it

# LOOP( SEQ(ET,IT), AP )  -- redo = fail + adjust
trial_loop = ProcessTree(operator=Operator.LOOP)
trial_loop.children = [seq_et_it, AP]
seq_et_it.parent = trial_loop
AP.parent = trial_loop

# PAR(QR,RR) for high-risk
par_high = ProcessTree(operator=Operator.PARALLEL)
par_high.children = [QR, RR]
QR.parent = par_high
RR.parent = par_high

# XOR(SR, PAR(QR,RR))
approval = ProcessTree(operator=Operator.XOR)
approval.children = [SR, par_high]
SR.parent = approval
par_high.parent = approval

# XOR(CS, tau)
opt_cs = ProcessTree(operator=Operator.XOR)
opt_cs.children = [CS, tau]
CS.parent = opt_cs
tau.parent = opt_cs

# PAR( trial_loop, approval, opt_cs )
par_phase3 = ProcessTree(operator=Operator.PARALLEL)
par_phase3.children = [trial_loop, approval, opt_cs]
trial_loop.parent = par_phase3
approval.parent = par_phase3
opt_cs.parent = par_phase3

# SEQ( RD, PAR_phase2, PAR_phase3, RM, AC )
tree = ProcessTree(operator=Operator.SEQUENCE)
tree.children = [RD, par_phase2, par_phase3, RM, AC]
RD.parent = tree
par_phase2.parent = tree
par_phase3.parent = tree
RM.parent = tree
AC.parent = tree
```

## Approximation and inexactness

The tree cannot represent the non-block-structured DAG exactly without duplication. It enforces a phase barrier: `CM->PV` and `ARC->DCA` must both complete before any of trial, approvals, or supplier work can start/complete. Intended behavior allows: (a) approval route `SR / QR+RR` to start as soon as `ARC` completes, overlapping `CM, PV, DCA` — tree forbids approval before `PV+DCA`; (b) `CS` to start after `ARC` and overlap `PV, DCA, approvals, trial` — tree forbids `CS` before `PV+DCA` and forbids `CS` overlapping `PV/DCA` design/planning; (c) `DCA` overlapping approvals and `PV` overlapping approvals — tree sequentializes them. The trial dependency `DCA+PV -> ET` is preserved, release synchronization `trial+approvals+(CS)->RM` is preserved, and `RD` start / `RM->AC` end are exact. Loop, XOR risk choice, and XOR optionality are exact modulo data abstraction. The policy is strict under-approximation: every tree trace is intended-allowed, but intended-allowed traces with early approvals or early/overlapping `CS` are excluded. No duplicate labels were introduced, so no label-ambiguity cost is incurred.

# 4. PM4Py POWL Model

## Compact description

```text
POWL-ROOT = StrictPartialOrder{
  nodes = [RD, CM, ARC, PV, DCA, ApprovalXOR, OptCS_XOR, TrialLOOP, RM, AC]
  edges = [RD->CM, RD->ARC, CM->PV, ARC->DCA, ARC->ApprovalXOR, ARC->OptCS_XOR,
           PV->TrialLOOP, DCA->TrialLOOP,
           TrialLOOP->RM, ApprovalXOR->RM, OptCS_XOR->RM, RM->AC]
}
ApprovalXOR = XOR( SR, StrictPartialOrder{[QR,RR] no edge} )
OptCS_XOR = XOR( CS, silent )
TrialLOOP = LOOP( StrictPartialOrder{[ET,IT] edge ET->IT}, AP )
```

## Self-contained construction code

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

RD = Transition(label="Register Deviation")
CM = Transition(label="Contain Material")
ARC = Transition(label="Analyze Root Cause")
PV = Transition(label="Plan Verification")
DCA = Transition(label="Design Corrective Action")
SR = Transition(label="Supervisor Review")
QR = Transition(label="Quality Review")
RR = Transition(label="Regulatory Review")
CS = Transition(label="Consult Supplier")
ET = Transition(label="Execute Trial")
IT = Transition(label="Inspect Trial")
AP = Transition(label="Adjust Parameters")
RM = Transition(label="Release Material")
AC = Transition(label="Archive Case")

# trial body ET->IT
trial_body = StrictPartialOrder(nodes=[ET, IT])
trial_body.order.add_edge(ET, IT)
trial_loop = OperatorPOWL(operator=Operator.LOOP, children=[trial_body, AP])

# high-risk concurrent approvals
high = StrictPartialOrder(nodes=[QR, RR])
# no edge between QR and RR -> concurrent, either order
approval = OperatorPOWL(operator=Operator.XOR, children=[SR, high])

# optional supplier
skip = SilentTransition()
opt_cs = OperatorPOWL(operator=Operator.XOR, children=[CS, skip])

# root partial order
powl = StrictPartialOrder(nodes=[RD, CM, ARC, PV, DCA, approval, opt_cs, trial_loop, RM, AC])
powl.order.add_edge(RD, CM)
powl.order.add_edge(RD, ARC)
powl.order.add_edge(CM, PV)
powl.order.add_edge(ARC, DCA)
powl.order.add_edge(ARC, approval)
powl.order.add_edge(ARC, opt_cs)
powl.order.add_edge(PV, trial_loop)
powl.order.add_edge(DCA, trial_loop)
powl.order.add_edge(trial_loop, RM)
powl.order.add_edge(approval, RM)
powl.order.add_edge(opt_cs, RM)
powl.order.add_edge(RM, AC)
```

## Why unconnected pairs may remain concurrent

No edge was added unless required by §2. Remaining concurrency is intended: `CM vs ARC` (independent containment/analysis); `CM vs DCA/approval` and `ARC vs PV` cross-branch independence; `PV vs DCA` (planning vs design); `PV vs approval` and `DCA vs approval` (work products vs reviews, both only depend on different parents); `approval vs trial_loop` (explicit rule 7 overlap); `opt_cs vs PV/DCA/approval/trial_loop` (explicit rule 6 overlap); `QR vs RR` (explicit concurrent high-risk reviews); `CM vs opt_cs/trial` transitive only via stated paths, so early containment may overlap later obligations except where `PV->trial_loop->RM` transitively orders them before release. All such interleavings preserve start-after and synchronization requirements and correspond to “may overlap” as absence of constraint.

# 7. Preferred Representation and Validation Plan

## Canonical choice

**POWL is canonical.** It expresses the cross-branch DAG directly with partial-order edges `PV->trial, DCA->trial, approval->RM, trial->RM, CS->RM` while leaving `approval vs trial` and `CS vs work` unconnected. The process tree requires a phase barrier and therefore systematically excludes compliant early-review and early-supplier behavior (T04). POWL is exact modulo the necessary data-to-choice and pass-to-loop-exit abstractions, has no duplicate labels, and converts to a sound workflow net preserving concurrency. The tree is retained only as a conservative, tool-compatible approximation where block structure is required.

## Validation plan

- **Conversion to accepting Petri net where supported:** `net, im, fm = pm4py.convert_to_petri_net(powl)` and same for `tree`. Inspect that conversion succeeds; compare place/transition counts and that all 14 visible labels appear exactly once (plus one silent for optionality). Failure or label multiplication signals representational blow-up.
- **Soundness checking:** `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` on both nets. Require workflow soundness (option to complete, proper completion, no dead transitions). Unsoundness would indicate modeling error in LOOP/XOR wiring.
- **Bounded/sampled playout:** `pm4py.play_out(powl, ...)` / `play_out(net,...)` with limits (e.g., max loop iterations 2, sample 500 traces). Confirm presence of low-risk, high-risk, supplier, and two-iteration variants and absence of traces violating `CM->PV` or `DCA->trial` in the sample. Bound loops to avoid infinite playout.
- **Explicit positive/negative trace tests:** Replay T01–T05 as positive (expect fit for POWL; expect T04 to misfit tree) and T06–T08 as negative (expect misfit for both) using conformance/alignment or language-membership checks. Record earliest violation per trace to confirm cross-branch enforcement, not just start/end.
- **Silent/duplicated-label check:** Enumerate transitions by label; assert exactly one `Consult Supplier`, one silent skip in `opt_cs`, no duplicate visible labels; test trace `RD,CM,ARC,PV,DCA,ET,IT,RM,AC` with silent correctly skipped vs trace requiring silent to fire twice; verify skip does not create a bypass of `ARC->RM` ordering (e.g., `CS` cannot be skipped and also executed).
- **Limitations:** Playout is bounded and samples interleavings, not proof of language equality; Petri-net conversion may introduce silent bridging that obscures partial-order concurrency; completion-only traces cannot distinguish true simultaneity from interleaving; data conditions and inspection outcomes are abstracted so validation cannot detect incorrect risk routing or false pass/fail mapping; soundness does not imply fidelity to intended DAG.

# 8. Final Self-Critique

1. **Semantics – silent ordering in POWL:** Adding `ARC->opt_cs` where `opt_cs = XOR(CS, silent)` forces the silent skip to be ordered after `ARC`. This is harmless for completion traces but arguably over-constrains the decision point formalism; a purist partial-order semantics might order only the `CS` branch, not the skip. The answer treats skip-ordering as vacuous, which should be made explicit to the engine.
2. **Semantics – trial-approval interleaving granularity:** Both models claim `QR/RR` may complete between `ET` and `IT` (T02). Whether POWL/process-tree PAR truly allows splitting `SEQ(ET,IT)` depends on interleaving semantics vs atomic-block execution in a given engine. If an engine treats loop-body as atomic, T02 would be rejected despite the claim; validation must confirm engine behavior.
3. **Python/syntax fragility:** Manual `ProcessTree`/`StrictPartialOrder` construction relies on remembered constructor signatures (`label=`, `operator=`, `nodes=`, `children=`) and `order.add_edge` API. Minor version differences (e.g., `Operator.LOOP` needing three children, `SilentTransition` labeling, `OperatorPOWL` argument names) could break execution. The compact string expressions mitigate this but `parse_process_tree` quoting for multi-word labels was avoided rather than tested, leaving executability to be verified in situ.
