# 1. Review Scope and Assumptions

I distinguish five uses, because they have different acceptable fitness/precision trade-offs:

- **Exploration/visualization:** permissive models can be useful if clearly labeled. Low precision is tolerable, but it must not be exported as policy.
- **Conformance enforcement:** mandatory checks, optional/conditional activities, approval exclusivity, and correction semantics must be explicit. False acceptance is usually more dangerous than false rejection.
- **Audit:** the model must be traceable to policy and able to explain why a trace is rejected. High training precision is not enough if negative behavior is unmeasured.
- **Simulation:** the model needs stochastic and attribute-conditioned choices. Neither supplied model is sufficient because external/internal and affected-check attributes are missing.
- **Stakeholder communication:** simplicity helps, but a simple wrong model is worse than a slightly more complex correct one.

Assumptions used below:

- In PM4Py process-tree notation, `+` is parallel, `X` is exclusive choice, `*` is loop, `->` is sequence, and `tau` is silent.
- Model S therefore allows each of Credit Check, Technical Review, Supplier Review, and Expedite Review to occur or be skipped, in any parallel order, before one approval.
- Model C is an exclusive choice among the eight enumerated traces, with no silent skips and no free combinations.
- The missing external/internal and affected-check attributes are not minor logging details; they are central to P3 and P6.
- Reported metrics are evidence, not ground truth. The lack of seeds, preprocessing code, alignment costs, and held-out cases makes cross-model comparison weak.

# 3. Adversarial Review of Model S

**Strongest case for Model S:** It is simple, fast, and robust to missing events. Its high holdout fitness and generalization suggest it can accommodate new combinations without being rebuilt. For exploratory process mining or stakeholder workshops, it gives a readable “anything around the checks may happen” picture. Its low precision is less harmful if it is never used to generate compliance alerts.

**Strongest case against Model S:** It is not merely permissive; it is semantically wrong for the agreed policy. It makes mandatory checks optional, allows Expedite Review before the mandatory checks, and has no Correct Dossier at all. Its low precision is not just noise tolerance; it is false acceptance of forbidden traces.

Concrete undesirable or ambiguous behaviors:

1. `Register Dossier, Manager Approval, Release Order`  
   Model S accepts this. Policy P2 forbids it because Credit Check and Technical Review are mandatory before approval.

2. `Register Dossier, Credit Check, Manager Approval, Release Order`  
   Model S accepts this. Technical Review is missing.

3. `Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order`  
   Model S accepts this. P4 requires Expedite Review to follow both mandatory checks, not precede them.

4. `Register Dossier, Supplier Review, Credit Check, Technical Review, Auto Approval, Release Order`  
   Model S accepts this even if the order is internal. P3 says Supplier Review is required only for externally sourced orders; the model has no external/internal condition.

5. `Register Dossier, Auto Approval, Release Order`  
   Model S accepts this because all four review actions can be silent. This is a direct violation of P2.

6. `Register Dossier, Credit Check, Technical Review, Correct Dossier, Technical Review, Manager Approval, Release Order`  
   Model S rejects this because `Correct Dossier` is not in its alphabet. This is a valid correction case if the correction affected Technical Review alone.

7. `Register Dossier, Credit Check, Technical Review, Credit Check, Manager Approval, Release Order`  
   Model S rejects this because it has no loop or repetition. That is good for P7, but it also means the model cannot represent legitimate post-correction repetition.

**Intentional vs accidental permissiveness:** Making all four reviews optional may be intentional noise tolerance for missing events. But optionalizing Credit Check and Technical Review contradicts P2. Allowing Expedite Review before the mandatory checks is an accidental semantic flaw caused by putting all optional branches in one parallel block. Omitting Correct Dossier is a modeling omission, not a principled tolerance.

# 4. Adversarial Review of Model C

**Strongest case for Model C:** It is precise on the training log and mirrors frequent observed variants. It explicitly includes some correction behavior and avoids the obviously forbidden skip patterns accepted by Model S. For a narrow historical audit of exactly the observed variants, it is more conservative and easier to defend as “this is what happened.”

**Strongest case against Model C:** It is a brittle trace catalogue, not a process model. It enumerates eight complete traces under an exclusive choice. It cannot express new combinations of already known behavior. It rejects valid traces such as `Register Dossier, Technical Review, Credit Check, Auto Approval, Release Order`. It handles correction only through one branch that repeats both Credit Check and Technical Review after Correct Dossier. It has no external/internal condition and no affected-check semantics.

Key issues:

- **Branch enumeration:** Every new allowed combination requires a new branch. With optional Supplier, optional Expedite, two check orders, two approval types, and correction variants, the combinatorial space explodes.
- **Duplicate labels:** The reported 33 duplicate labels likely reflect repeated activity labels across branches and within the correction branch. Even if the exact count is undocumented, the structure is hard for impact analysis and ownership.
- **Unseen combinations:** F4 says holdout cases combine Supplier Review, Auto Approval, and alternate check order. Model C rejects these because they are absent from training.
- **Correction handling:** Model C only allows one correction pattern: initial Credit Check then Technical Review, Correct Dossier, then Credit Check and Technical Review again, then Manager Approval, then Release. It cannot repeat only Credit Check, only Technical Review, or a corrected subset after a different initial order.
- **Holdout degradation:** Holdout fitness 0.744 is a serious warning. For enforcement, this means many legitimate new combinations will be blocked.
- **Maintainability:** Adding Supplier+Auto, Expedite-before-Supplier, or single-check correction would require more branches and more duplicated labels. This is not sustainable under policy change.
- **Precision artifact:** Training precision 0.941 may come from memorizing training traces. Because the model has no optionality except branch choice, it can be very precise on the positive training log while failing on negative or unseen behavior. The absence of a curated negative suite means precision is not policy precision.

Model C is safer than Model S only for the exact traces it already knows. It is not a generalizable or maintainable policy model.

| B7: Register, Credit, Technical, Supplier, Manager, Release | Yes | Yes, branch 3 | Valid external case | Both pass, but Model S does not require Supplier for external and Model C cannot condition it. |
| B8: Register, Credit, Technical, Credit, Manager, Release | No. No loop/repetition. | No. No repeated Credit without correction in any branch. | Suspicious/forbidden without correction | Both reject, which is correct for this probe. |

Uncertainty note: Model S’s acceptance is driven by `+` parallel optional branches and `X(activity, tau)` skips. Model C’s acceptance is exact sequence membership under `X`. There is no loop or silent uncertainty in these probes beyond those semantics.

# 6. Likely Metric Pathologies

Ranked by likely decision impact:

1. **Positive-log-only precision and no negative suite.** The reported precision cannot establish policy compliance. Model C can be precise on observed positives while accepting no negative cases. Model S can have low precision but the negative cases are not even measured. This is the highest decision risk because it makes both precision numbers misleading.

2. **Missing external/internal and affected-check attributes.** P3 and P6 cannot be enforced without them. Any model that treats Supplier Review as optional or correction as a generic loop is making an unvalidated assumption. For compliance, missing attributes may be more important than any reported metric.

3. **Fitness rewarded by optionalizing mandatory behavior.** Model S’s high training and holdout fitness are partly purchased by allowing Credit Check and Technical Review to be skipped. High fitness here is not evidence of correctness.

4. **Unseen-combination overfitting in Model C.** Holdout fitness 0.744 and generalization 0.412 show that Model C rejects legitimate new combinations. Branch enumeration turns every new combination into a nonconforming trace.

5. **Train/holdout leakage or split sensitivity.** Both teams claim the same 80/20 split but provide no seed, preprocessing, or held-out cases. With small logs, a different split could reverse the holdout story. The metrics are not reproducible.

6. **Silent-transition effects.** Model S uses many `tau` branches. Silent transitions can inflate fitness, affect token-based generalization, and make precision harder to interpret. A trace may fit because the model silently skips mandatory work.

7. **Duplicated-label effects.** Model C’s 33 duplicate labels complicate alignment, impact analysis, and ownership. Duplicate labels can also make precision and generalization harder to compare because multiple transitions share a label.

8. **Generalization rewarded by excessive permissiveness.** Token-based generalization favors S, but S generalizes by allowing forbidden behavior. The metric does not separate correct generalization from uncontrolled permissiveness.

9. **Runtime confounding by model size.** Model C’s 0.440 s median runtime is slower than Model S’s 0.018 s, but this is confounded by C’s larger branch structure and duplicate labels. Runtime alone should not choose a model.

10. **Stakeholder-score methodology.** The 4.4 vs 1.9 comprehension score is informal. It may measure preference for simplicity rather than understanding of policy. A simple model that silently allows missing checks can be popular but dangerous.

# 7. Third Alternative

I propose a **block-structured procedural backbone plus declarative/data constraints**. The backbone enforces the mandatory control-flow skeleton. Declarative checks enforce context-dependent rules that the log cannot currently express. This avoids Model S’s “everything optional” semantics and Model C’s trace enumeration.

**Compact formal description**

Let activities be:

- `R` = Register Dossier
- `C` = Credit Check
- `T` = Technical Review
- `S` = Supplier Review
- `E` = Expedite Review
- `CD` = Correct Dossier
- `AM` = Manager Approval
- `AA` = Auto Approval
- `Rel` = Release Order

Main backbone:

```text
R ;
(C || T) ;
( tau ; ( CD ; nonempty_subset(C,T) ) )* ;
( S? || E? ) ;
( AM xor AA ) ;
Rel
```

Where:

- `||` means parallel/any order.
- `?` means optional.
- `*` means zero or more loop iterations.
- `nonempty_subset(C,T)` means Credit only, Technical only, or both in any order.
- `AM xor AA` means exactly one approval.

Semantics:

- **Mandatory checks:** `(C || T)` forces both Credit Check and Technical Review, in either order, before approval.
- **Optional Supplier Review:** `S?` allows it, but the backbone cannot know whether the order is external. An external check must require `S` for external cases and, if policy says so, forbid `S` for internal cases.
- **Expedite Review:** `E?` occurs after the mandatory/correction block and before approval. It is parallel with `S?`, so it may occur before or after Supplier Review. This satisfies P4.
- **Exactly-one approval:** `AM xor AA` enforces exactly one approval before release.
- **Correction/recheck:** The loop allows `CD` followed by a non-empty subset of `C` and `T`. It does not allow repeated `C` or `T` without a preceding `CD`. An external check enforces that the repeated checks match the affected checks when the attribute exists.

**Self-contained PM4Py code assigning the main model to `model_third`**

**Declarative dictionaries and external checks**

```python
POLICY = {
    "mandatory_checks": {"Credit Check", "Technical Review"},
    "approvals": {"Manager Approval", "Auto Approval"},
    "supplier": "Supplier Review",
    "expedite": "Expedite Review",
    "correction": "Correct Dossier",
}

def policy_check(trace, case_attrs=None, event_attrs=None):
    """
    trace: list of event dicts, each with at least 'concept:name'
    case_attrs: dict with optional 'external': True/False/None
    event_attrs: list aligned with trace, may contain 'affected_checks' on Correct Dossier events
    Returns: dict(violations=[...], uncertain=[...])
    """
    case_attrs = case_attrs or {}
    event_attrs = event_attrs or []
    acts = [e["concept:name"] for e in trace]
    violations = []
    uncertain = []

    approvals = [i for i, a in enumerate(acts) if a in POLICY["approvals"]]
    if len(approvals) != 1:
        violations.append(f"expected exactly one approval, got {len(approvals)}")

    approval_pos = approvals[0] if approvals else len(acts)

    for m in POLICY["mandatory_checks"]:
        if m not in acts:
            violations.append(f"missing mandatory check: {m}")
        elif acts.index(m) > approval_pos:
            violations.append(f"{m} occurs after approval")

    for i, a in enumerate(acts):
        if a == POLICY["expedite"]:
            if not any(x == "Credit Check" for x in acts[:i]) or not any(x == "Technical Review" for x in acts[:i]):
                violations.append("Expedite Review before both mandatory checks")
            if i > approval_pos:
                violations.append("Expedite Review after approval")

    if POLICY["supplier"] in acts and acts.index(POLICY["supplier"]) > approval_pos:
        violations.append("Supplier Review after approval")

    ext = case_attrs.get("external")
    if ext is True and POLICY["supplier"] not in acts:
        violations.append("external order missing Supplier Review")
    if ext is False and POLICY["supplier"] in acts:
        violations.append("internal order has Supplier Review (policy-dependent)")
    if ext is None:
        uncertain.append("missing external/internal attribute: Supplier Review requirement cannot be enforced")

    # Repeated mandatory checks must follow a Correct Dossier.
    positions = {"Credit Check": [], "Technical Review": []}
    for i, a in enumerate(acts):
        if a in positions:
            positions[a].append(i)

    for a, pos_list in positions.items():
        for prev, cur in zip(pos_list, pos_list[1:]):
            if not any(acts[k] == POLICY["correction"] for k in range(prev + 1, cur)):
                violations.append(f"{a} repeated between {prev} and {cur} without Correct Dossier")

    # Correction affected-check check.
    for i, a in enumerate(acts):
        if a == POLICY["correction"]:
            affected = None
            if i < len(event_attrs):
                affected = event_attrs[i].get("affected_checks")

            repeated = []
            for j in range(i + 1, len(acts)):
                if acts[j] in {POLICY["correction"], "Manager Approval", "Auto Approval"}:
                    break
                if acts[j] in POLICY["mandatory_checks"]:
                    repeated.append(acts[j])

            if not repeated:
                violations.append("Correct Dossier without repeated check")

            if affected is None:
                uncertain.append("missing affected_checks attribute for Correct Dossier")
            else:
                aff = set(affected if isinstance(affected, (list, set, tuple)) else [affected])
                rep = set(repeated)
                if not rep.issubset(aff):
                    violations.append(f"repeated checks {rep} not subset of affected {aff}")
                if not aff.issubset(rep):
                    violations.append(f"affected checks {aff} not all repeated")

    return {"violations": violations, "uncertain": uncertain}
```

**Limitations caused by missing attributes**

- Without external/internal, the backbone cannot require Supplier Review for external orders or forbid it for internal orders. The main model treats Supplier Review as optional; the external check only works if the attribute exists.
- Without affected-check data, the backbone allows any non-empty subset of Credit Check and Technical Review after Correct Dossier. This is intentionally more permissive than P6, but it is not silently treated as fully compliant. Missing affected-check data produces `uncertain` and should trigger manual review or conservative rejection.
- The backbone places correction before optional Supplier/Expedite. If policy allows correction after Expedite or after Supplier, the model will falsely reject such traces. That is a conservative limitation, not a hidden permissiveness.

# 9. Validation Experiments

Concrete evaluation program:

1. **Reproducible case splits with seeds and published preprocessing.** Use at least seeds `42`, `43`, `44`. Publish the exact XES preprocessing: attribute renaming, timestamp parsing, case-ID selection, label cleaning, and removal of incomplete cases. Use the same PM4Py version and alignment cost map for all models.

2. **Attribute-stratified holdout tests.** Stratify by:
   - external/internal if known,
   - presence/absence of Supplier Review,
   - presence/absence of Expedite Review,
   - Manager vs Auto Approval,
   - correction vs no correction,
   - check order.
   Report fitness/precision separately per stratum.

3. **Curated negative trace suite.** Include B3, B4, B8, and synthetic forbidden traces:
   - missing Credit before approval,
   - missing Technical before approval,
   - Expedite before both checks,
   - Supplier Review for internal order if policy forbids,
   - approval without any mandatory check,
   - repeated check without correction,
   - correction followed by unaffected check.
   A model must reject or flag all negative traces.

4. **Missing-event and duplicate-event perturbation tests.** Randomly remove 5%, 10%, and 20% of non-registration/release events. Randomly duplicate checks, approvals, and Supplier/Expedite events. Measure false acceptance and false rejection.

5. **Unseen-combination tests.** Hold out entire combinations, e.g. Supplier+Auto, Expedite+Supplier+Auto, single-check correction, correction after alternate initial order. Evaluate whether the model rejects all unseen behavior or accepts valid unseen combinations.

6. **Alignment-cost sensitivity.** Re-run alignments with standard costs, unit costs, and activity-specific costs for mandatory checks vs optional reviews. Report how fitness/precision rankings change.

7. **Soundness and reachability checks.** For every model:
   ```python
   pm4py.check_soundness(net, im, fm, print_diagnostics=True)
   pm4py.play_out(model_or_net, num_traces=1000)
   ```
   Verify that play-out does not produce traces that violate P1–P7 without being flagged by external checks.

8. **Fitness, precision, generalization, and simplicity reported separately.** Do not aggregate them into a single score. Use:
   ```python
   fit = pm4py.fitness_alignments(log, net, im, fm)
   prec = pm4py.precision_alignments(log, net, im, fm)
   gen = pm4py.generalization_tbr(log, net, im, fm)
   simp = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")
   diags = pm4py.conformance_diagnostics_alignments(log, net, im, fm)
   ```

9. **Stakeholder comprehension measured with a documented protocol.** Give stakeholders a set of allowed/forbidden traces and ask them to classify them using the model. Record inter-rater agreement and not just preference. A model fails communication if stakeholders cannot explain why B3/B4 are forbidden.

10. **Decision rule for rejection despite good aggregate metrics.** Reject a model for compliance if any of these hold:
    - It accepts any forbidden trace in the negative suite with no flag.
    - It rejects a valid trace in the attribute-stratified holdout more than an agreed threshold, e.g. >5% of valid external/urgent cases.
    - Precision on the negative suite is below an agreed threshold, e.g. <0.95.
    - Soundness or reachability checks fail.
    - Stakeholder comprehension is below 4/5 with the documented quiz.
    - Runtime per case exceeds the operational budget for the intended audit size.
    - The model requires undocumented attributes to appear correct.

**PM4Py metric skeleton**

```python
def evaluate_model(log, model):
    net, im, fm = pm4py.convert_to_petri_net(model)
    pm4py.check_soundness(net, im, fm, print_diagnostics=True)

    fitness = pm4py.fitness_alignments(log, net, im, fm)
    precision = pm4py.precision_alignments(log, net, im, fm)
    generalization = pm4py.generalization_tbr(log, net, im, fm)
    simplicity = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")
    diagnostics = pm4py.conformance_diagnostics_alignments(log, net, im, fm)

    return {
        "fitness": fitness,
        "precision": precision,
        "generalization": generalization,
        "simplicity": simplicity,
        "diagnostics": diagnostics,
        "net": net,
        "im": im,
        "fm": fm,
    }
```

from pm4py.objects.log.obj import EventLog, Trace, Event

def accepts_trace(net, im, fm, activities):

# 10. Governance Recommendation

**Exploration:** Model S may be used only for exploration, visualization, and stakeholder workshops. It must carry a prominent “not compliance” label. It must not be used to generate enforcement alerts or automated rejections.

**Historical audit of observed variants:** Model C may be used as an archived historical variant catalogue. It should not be used to judge new cases or to enforce policy, because its holdout degradation and branch enumeration cause false rejection of legitimate new combinations.

**Compliance enforcement:** Neither original model is acceptable. Model S falsely accepts forbidden traces. Model C rejects valid unseen combinations and cannot represent attribute-conditioned behavior.

**Third alternative:** The hybrid backbone plus declarative checks may be used for compliance only after all of these conditions are met:

- External/internal and affected-check attributes are captured, or every ambiguous case is routed to manual review.
- The negative trace suite passes with no unflogged forbidden acceptance.
- Attribute-stratified holdout tests show acceptable false rejection for valid external/urgent and correction cases.
- Soundness and reachability checks pass.
- Fitness, precision, generalization, simplicity, and runtime are reported separately and meet thresholds for the intended use.
- Stakeholder comprehension reaches at least 4/5 using a documented, trace-based quiz.
- Governance signs off on the exact declarative rules and on the manual-review escalation path.

**Retirement:** Retire Model C from operational compliance use. Keep Model S only as an exploratory model. If Model C is retained, label it as a historical variant catalogue, not a policy model.

# 11. Dissenting View

The strongest rebuttal to my recommendation is that the hybrid still cannot enforce the distinctions that matter most. Missing external/internal and affected-check attributes are not minor logging gaps; they define P3 and P6. A hybrid that treats Supplier Review as optional and allows a non-empty subset of checks after correction may create false assurance. Model C, by rejecting every trace not in its enumerated set, is conservative: in a regulated setting, false rejection may be safer than false acceptance. Its low holdout fitness may simply mean it catches novel cases for human review. Model S is at least honestly permissive when labeled exploratory. The third alternative’s post-hoc checks depend on extra event attributes and disciplined execution; if those checks are bypassed, it becomes Model S with extra complexity. It may also disallow legitimate corrections after Expedite or Supplier, creating new false negatives. Therefore, I would not deploy the third model until the attributes exist and negative-suite testing proves it rejects all forbidden traces. Until then, keep Model C as a conservative gate and Model S as visualization only. Additional evidence that would change my decision: if external/internal and affected-check attributes are reliably logged, if stratified holdout shows the third model accepts valid unseen combinations while rejecting all negative cases, and if stakeholder comprehension exceeds 4/5 with a documented protocol, then deploy the third model. If attributes remain unavailable, prefer conservative rejection and manual review over automated compliance.
