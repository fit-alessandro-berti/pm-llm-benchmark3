## 6. Candidate Site B intervention

Recommended intervention: **segmented verification concurrency with statutory prerequisites and WIP controls**, not a copy of Site A's all-case immediate Document Check.

### Process specification

- **Eligibility rules:**
  - At Register, classify each case as:
    - `DIGITAL`: no original documents legally required and digital documents are sufficient;
    - `ORIGINAL`: original documents legally required;
    - `LEGAL`: public-sector or high-value, likely to require Legal Review.
  - Wave 1 covers `DIGITAL` cases. Wave 2, after interim analysis, may cover `ORIGINAL` cases with Document Check created only after Originals Receipt.

- **Concurrent tasks:**
  - For `DIGITAL`: after Register, create Identity Check and Document Check tasks concurrently.
  - For `ORIGINAL`: after Register, create Identity Check and Originals Receipt tasks concurrently. Document Check is not created until Originals Receipt completes.
  - For `ORIGINAL`, after Originals Receipt, Document Check may run concurrently with Identity Check if Identity Check is still open.
  - Assessment always requires both Identity Check and Document Check to be complete.

- **Statutory prerequisites that remain mandatory:**
  - Register before all other tasks.
  - Originals Receipt before Document Check when original documents are legally required.
  - Identity Check and Document Check before Assessment.
  - Legal Review before final decision when required.
  - Final decision before Notify.
  - Request Supplement may send the case back to Document Check, Assessment, or Identity Check depending on supplement type.

- **Queue and WIP controls:**
  - At most two verification tasks active per case.
  - Role-level WIP caps:
    - Identity reviewer: 4 open cases.
    - Document reviewer: 3 open cases because document service is long.
    - Assessor: 4 open cases.
    - Legal reviewer: 4 open cases.
  - Managers rebalance daily using queue-huddle data.
  - Document Check tasks for `DIGITAL` cases are released in priority order, not all at once.

- **Resource responsibilities:**
  - Identity reviewers perform only Identity Check.
  - Document reviewers perform only Document Check.
  - Assessors perform only Assessment.
  - Legal reviewers perform only Legal Review and supplement decisions.
  - There is no cross-assignment; concurrency is achieved through separate queues, not shared ownership.

- **Handling legal-review and supplement loops:**
  - After Assessment, if `LEGAL` is true, route to Legal Review.
  - Legal Review may decide Approve, Reject, or Request Supplement.
  - `Request Supplement` routes to Document Check, Assessment, and, if identity information is deficient, Identity Check.
  - After repeated Assessment, route again to Legal Review before final decision.

- **Logging requirements:**
  - Log task creation, start, completion, assignment, wait, and release times.
  - Log whether Document Check was created after Register or after Originals Receipt.
  - Log supplement type and which task had to be repeated.
  - Record timestamps automatically at the moment a task is opened or closed; no retrospective data entry without audit flag.

### POWL-style partial-order specification

```text
Register < IdentityCheck

if DIGITAL:
    Register < DocumentCheck
elif ORIGINAL:
    Register < OriginalsReceipt
    OriginalsReceipt < DocumentCheck

IdentityCheck < Assessment
DocumentCheck < Assessment

if LEGAL:
    Assessment < LegalReview
    LegalReview < Decision
    RequestSupplement < DocumentCheck
    RequestSupplement < Assessment
    if identity_supplement:
        RequestSupplement < IdentityCheck
else:
    Assessment < Decision

Decision = Approve | Reject
LegalReview = Approve | Reject | RequestSupplement
Decision < Notify
```

This preserves the rule that Document Check for original-required cases cannot start before Originals Receipt, while still allowing Identity Check and Document Check to overlap when the legal prerequisite is satisfied.

## 7. Pilot for transport learning

| design element | specification | causal purpose | operational safeguard | process-mining measurement |
|---|---:|---|---:|---|
| Unit of assignment | Case, blocked by registration day and stratified by originals requirement and legal requirement | Avoids site-level confounding; estimates case-level effect | Case-level randomization within narrow time blocks | Trace ID and case attributes linked to task event log |
| Randomization or phased assignment | 1:1 randomized allocation within four strata: `DIGITAL/LEGAL`, `DIGITAL/NON-LEGAL`, `ORIGINAL/LEGAL`, `ORIGINAL/NON-LEGAL`; phased: Wave 1 only `DIGITAL` | Tests treatment effect without violating legal prerequisites | Pre-specified allocation sequence; no manual ad hoc overrides | Compare actual assignment with randomization list |
| Eligible strata | Wave 1: `DIGITAL` cases; Wave 2: `ORIGINAL` cases with post-originals concurrency | Tests mechanism in the most transportable subgroup before scaling | Excludes cases without enough digital document stability | Stratified trace frequency and overlap |
| Treatment versions | T1: immediate Identity + Document tasks for `DIGITAL`; T2: Identity + Originals then Document for `ORIGINAL`; control: current process | Distinguishes digital concurrency from originals-segmented concurrency | Version recorded in case log | Conformance checking for treatment-version path |
| Primary outcome | Median waiting time before Assessment | Directly captures the intended upstream mechanism | Pre-specified analysis in subgroups | Waiting before Assessment from event log |
| Secondary outcomes | Median and p90 cycle time; true overlap; rework; supplement rate; appeal rate; queue length by role | Captures downstream and quality effects | Multiple outcome monitoring with stop rules | Overlap %, rework loop counts, role queue waiting |
| Interference controls | Limit number of treatment cases released per day per role; monitor queue spillover; include queue occupancy covariates | Reduces case-to-case and queue-to-queue spillover | Pilot coordinator can pause release if queue thresholds exceed pre-registered limits | Queue length and utilization by assigned arm |
| Power / minimum-support logic | Target ~600 completed cases per arm overall; at least 120 per legal/original stratum; 80% power for a 6 h median waiting reduction at alpha 0.05 under log-normal assumptions | Ensures subgroup estimates are not noise | Continuously monitor recruitment; do not expand before minimum support | Stratified precision of estimated effects |
| Duration | 12 weeks for Wave 1, or until 300 per arm; then interim analysis; Wave 2 only if stop rules not triggered | Balances learning with operational risk | Fixed calendar and sample thresholds | Process drift checks via weekly trace statistics |
| Stop rules | Stop if p90 cycle time exceeds control by >10 h; rework increases >3 percentage points; appeal increases >1 percentage point; true overlap <25% in treated `DIGITAL` cases | Prevents tail and quality harm | Independent data-safety check at interim | Visual process-mining dashboards showing p90 and loop frequencies |
| Transportability analysis | Compare Site B effect estimates with Site A's confounded before/after effect; use negative-control process and sensitivity analysis | Tests whether Site A evidence predicts Site B behavior | Pre-register transport model before unblinding | `waiting_before_assessment`, `true_overlap`, and downstream queue metrics as causal intermediates |

The pilot separates mechanism failure from implementation failure by measuring both treatment fidelity and intermediate outcomes. If the treated arm does not achieve true overlap, or if task-creation logs show blocked Document Check tasks for original-required cases, that is implementation failure: the intervention was not executed as specified. If true overlap is high but waiting before Assessment, cycle time, or p90 do not improve, that is mechanism failure: the structural theory that verification overlap reduces delay does not hold in Site B's operating context. The pilot also records downstream queue outcomes, so it can distinguish whether an average improvement masks a harmful tail shift.

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.powl.obj import (
    POWL,
    StrictPartialOrder,
    Sequence,
    XOR,
    Loop,
    Transition,
    SilentTransition,
)

# ----------------------------------------------------------------------
# 1. Site A process trees, before and after the intervention
# ----------------------------------------------------------------------
site_a_before_tree = pm4py.parse_process_tree(
    "->('Register','Identity Check','Document Check','Assessment',X('Approve','Reject'),'Notify')"
)
site_a_after_tree = pm4py.parse_process_tree(
    "->('Register',+('Identity Check','Document Check'),'Assessment',X('Approve','Reject'),'Notify')"
)

net_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(site_a_before_tree)
net_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(site_a_after_tree)

print("Site A before workflow net:", pm4py.check_is_workflow_net(net_a_before))
print("Site A after workflow net:", pm4py.check_is_workflow_net(net_a_after))
print("Site A before soundness:", pm4py.check_soundness(net_a_before, im_a_before, fm_a_before))
print("Site A after soundness:", pm4py.check_soundness(net_a_after, im_a_after, fm_a_after))

# ----------------------------------------------------------------------
# 2. Site B candidate POWL model
# ----------------------------------------------------------------------
# Activities
register = Transition("Register")
identity = Transition("Identity Check")
originals = Transition("Originals Receipt")
document = Transition("Document Check")
assessment = Transition("Assessment")
legal = Transition("Legal Review")
approve = Transition("Approve")
reject = Transition("Reject")
request_supp = Transition("Request Supplement")
notify = Transition("Notify")

# Verification options:
# DIGITAL: Identity and Document may execute concurrently.
digital_spo = StrictPartialOrder(
    children=[identity, document],
    order=[]  # no order edge between identity and document
)

# ORIGINAL: Identity may start after Register, Originals Receipt may also start
# after Register, but Document Check must wait for Originals Receipt.
originals_spo = StrictPartialOrder(
    children=[identity, originals, document],
    order=[(originals, document)]
)

# This XOR approximates the data-dependent legal/original classification.
verification = XOR(children=[digital_spo, originals_spo])

# Direct decision path for non-legal cases.
direct_decision = XOR(children=[approve, reject])

# Legal decision path with supplement loop.
# The loop approximation allows legal review to exit with approve/reject,
# or issue Request Supplement, after which document checking and assessment
# may be repeated before legal review is reached again.
legal_exit = XOR(children=[approve, reject])
legal_review_exit = Sequence(children=[legal, legal_exit])
supplement_redo = Sequence(children=[request_supp, document, assessment])
legal_loop = Loop(do=legal_review_exit, redo=supplement_redo)

post_assessment = XOR(children=[direct_decision, legal_loop])

# Final POWL model:
# Register -> verification -> Assessment -> decision/legal -> Notify.
# The Sequence after verification ensures Assessment waits for all verification
# children in the chosen StrictPartialOrder.
site_b_powl = Sequence(
    children=[
        register,
        verification,
        assessment,
        post_assessment,
        notify,
    ]
)

net_b, im_b, fm_b = pm4py.convert_to_petri_net(site_b_powl)

print("Site B candidate workflow net:", pm4py.check_is_workflow_net(net_b))
print("Site B candidate soundness:", pm4py.check_soundness(net_b, im_b, fm_b))

# ----------------------------------------------------------------------
# 3. Optional playout
# ----------------------------------------------------------------------
try:
    traces = pm4py.play_out(net_b, im_b, fm_b, no_traces=5)
    for i, trace in enumerate(traces, 1):
        labels = [
            event.get("concept:name", event)
            for event in trace
        ]
        print(f"Site B playout {i}: {labels}")
except Exception as e:
    print("Playout skipped:", e)

# ----------------------------------------------------------------------
# What this model cannot encode:
# - data-dependent legal requirements: the XOR between digital and original
#   paths is a modeling approximation, not a legal rule evaluator.
# - resource capacity: staff pools, WIP caps, queue lengths, and durations
#   are not represented in a workflow net.
# - case locks: the fact that Site B's legacy system may prevent true
#   concurrent task ownership is not encoded structurally.
# - durations and timing: median service times and originals receipt delay
#   cannot be inferred from the control-flow model.
# ----------------------------------------------------------------------
```

## 9. Recommendation

**Conditional go**

Transfer only the mechanism that is structurally plausible and legally feasible at Site B: true overlap of Identity Check and Document Check for cases where documents are digitally available at registration. Do not copy Site A's all-case immediate Document Check. Site B's 62% originals-required share, 40% legal-review share, specialized roles, legacy case locking, heavier complexity, and higher baseline rework mean that a direct copy would likely fail or worsen the tail.

The first subgroup should be `DIGITAL` cases: no originals legally required and digital documents sufficient. Within that subgroup, legal and non-legal cases should be stratified but not excluded. The intervention should use separate role queues, WIP caps, and strict logging. For original-required cases, the only lawful concurrency is Identity Check plus Originals Receipt after Register, then Document Check after originals receipt. That is a later expansion only if the digital pilot succeeds.

Expected benefits are modest: for digital cases, median waiting before Assessment may fall, producing perhaps a 2-4 h overall median improvement rather than Site A's 9 h confounded reduction. The main risks are document queue saturation, assessment or legal bottleneck shift, rework from supplement loops, and p90 deterioration from IT workarounds.

Expansion should require: true overlap above 60% in treated digital cases, median waiting before Assessment at least 6 h below control in that subgroup, no p90 increase above control of more than 10 h, rework increase no more than 3 percentage points, appeal increase no more than 1 percentage point, and acceptable role queue lengths. Modify the intervention if document capacity or assessment capacity saturates. Abandon if the stop rules trigger despite adequate implementation fidelity, especially if p90 worsens or if legacy IT lock prevents true overlap.

## 10. Assumption register

1. **True overlap can be implemented in Site B for digital/no-originals cases despite legacy IT lock** — needed because overlap is the core mechanism — test by measuring true concurrent task ownership and overlap percentages during pilot — if false, the intervention becomes implementation failure and should be paused until IT is fixed.

2. **Digital/no-originals cases have sufficient document availability to begin Document Check immediately after Register** — needed to justify early Document Check task creation — test by tracking the proportion of eligible digital cases where Document Check starts without waiting for missing documents — if false, narrow eligibility to a document-ready subpopulation.

3. **Site B's specialized roles can support concurrency through separate queues without materially increasing handoff delays** — needed because parallelization may increase role-to-role transitions — test by measuring handoff wait between verification, assessment, and legal tasks — if false, add queue coordination or modify task routing.

4. **Document capacity of 7 reviewers can absorb earlier document starts without creating a document bottleneck** — needed because document service is long and Site A added document reviewers — test by monitoring document queue length and utilization during pilot — if false, reduce release rate or add WIP caps.

5. **Assessment capacity of 3 assessors can absorb faster verification without downstream p90 worsening** — needed because the main risk is shifting waiting from verification to assessment — test by monitoring assessment queue length and p90 cycle time by arm — if false, restrict release-to-assessment rate or expand assessor capacity before broader rollout.

6. **Legal review and supplement-loop rates remain stable under earlier verification** — needed because Site B rework is already high and legal loops can amplify delay — test by comparing Request Supplement, repeated Document Check, and rework rates between arms — if false, pause or exclude legally heavy cases from concurrency.

7. **Site A's 9-hour median reduction is not an identified treatment effect; it is confounded by API, capacity, case mix, and queue huddles** — needed to avoid overestimating expected benefit — test by comparing Site B pilot effect estimates with Site A bounds and sensitivity analyses — if false, then a larger effect may be possible, but current evidence does not justify that assumption.

8. **Timestamp reliability can be made sufficient to measure true overlap and waiting intervals** — needed because Site B has legacy locking and retrospective entry — test by auditing event timestamps against system access records and by tracking back-entry flags — if false, the pilot cannot produce transportable evidence even if operational effect exists.
