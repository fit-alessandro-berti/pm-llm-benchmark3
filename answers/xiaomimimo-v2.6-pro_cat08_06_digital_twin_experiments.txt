# 1. Model scope and state variables

## 1.1 Boundary and purpose

**In scope.** The twin spans the municipal permit value stream from *presubmission* (only when D1 is switched on) through portal submission, clerical completeness handling, technical reviews, public notice, inspection, decision drafting, legal check, and issuance/rejection, **plus the appeal window** that can reinject a case into Planning/Legal. Applicant actions (`Receive missing documents`, appeal statements, noshow rescheduling) and thirdparty actions (consultant reports, neighbourhood objections, council calendars) are *in scope as exogenous agent models*, because their latencies are the dominant driver of p90/p95 cycle time.

**Out of scope.** Preapplication design work by architects (modelled only as an *arrival driver*, e.g. architectburst generation), construction and postpermit enforcement, and fee/billing systems.

**Purpose.** Not a replay: a **counterfactual comparison engine** for D1–D10 under nonstationary demand, real resource calendars, rework loops, crosscase coupling, and policy change. The twin must therefore represent *interventionsensitive mechanisms* (queues, calendars, batching, rework loops, bundling) rather than a fitted regression on cycle time.

**Level of detail.** Tasklevel discreteevent simulation (DES) with resourceconstrained queues and join semantics, augmented with **cluster agents** (architect bursts, inspection bundles, neighbourhood objection clusters). Time resolution: seconds internally; analysis windows: day/week. Not agentbased at the individualcitizen level (no behavioral learning), but not a purely flowlevel or systemdynamics model either — queueing delay must emerge from calendars and contention.

**Horizon.** 36 simulated months, of which the first 12 are warmup (see §5) and 24 are measured.

## 1.2 Entities

| Entity | Meaning | Cardinality / notes |
|---|---|---|
| **Case** | One permit application (`case:concept:name`) | ~31,200 / 18 months |
| **Task (work item)** | One execution of an activity on a case | Up to ~12–16 per case with rework |
| **Architect cluster** | Cases sharing `architect_id`, arriving within a 0–14 day burst window | Top20 architects = 31% of cases |
| **Inspection bundle** | Cases of the same `district` (and optionally same street/parcel) scheduled in the same routing day | Implicit entity created by D3 |
| **Neighbourhood cluster (latent)** | Spatially/temporally correlated objection events | Unobserved; inferred from `Public-notice period` durations |
| **Resource** | Individual clerk, planner, fire, environmental, inspector, legal officer | 24 FTE nominal + temps |
| **Resource pool / skill** | Clerk, plannersimple, plannercomplex, fire, environmental, inspection, legal, system | Fire: Tue–Thu only |
| **Document request cycle** | A requestresponse subloop attached to a case | Heavytailed response |
| **Policy state** | Version of routing rules active at simulated time *t* | Enables midhorizon policy changes |

## 1.3 State variables

**Caselevel (observed).** `case_type`, `district`, `architect_id`, `application_value`, `requires_fire`, `requires_environment`, `requires_public_notice`, arrival timestamp, case age, current activity, review results (planning/fire/environmental/inspection/legal  {clear, conflict, needsrework}), outcome (permit/reject/withdrawn/appealed), rework counters per loop, cumulative applicant waiting, cumulative municipal working time.

**Caselevel (latent — must be modelled, never treated as observed).** `building_area` (drives the firesafety threshold), `prior_violations` (drives D2 eligibility), `env_sensitivity` (district×project, incompletely observed), `objection_occurred` and `objection_count` (latent; **only** the *duration* of `Public-notice period` is an observed proxy), `no_show_flag`, `consultant_report_needed`, `emergency_flag` (cases removed from the log).

**Tasklevel.** activity name, required skill, ready time, priority class, join dependency set (for `Decision drafting`: the ANDjoin of Planning  Fire?  Environmental?  Publicnotice?  Site inspection), `batch_id`, `travel_district`, `is_rework`, `is_completion_only_log`.

**Resourcelevel.** id, skill set, FTE fraction, weekly shift windows, holiday/blackout sets (councilmeeting weeks for Legal), dedication constraints (1 clerk reserved for portal support Mondays; 2 planners restricted to `Simple renovation`; 40% of environmental capacity reserved for nonpermit duties), current assignment, remaining shift time, accumulated overtime, leave.

**Clusterlevel.** architect burst index and residual burst size, district load indicator, inspectionroute length for the current bundle, neighbourhood objection intensity (a slowly varying latent field), backlog/aging distribution per skill.

## 1.4 Resources, queues, calendars

- **Queues.** One logical queue per (activity × skill pool); scheduling policy = *SLAslack priority* (cases with the least slack first) with FIFO tiebreak, because the observed log shows aging effects and D6 explicitly targets aging. Baseline policy must be estimated from the log (see §2) — if observed dispatching is closer to FIFO, use FIFO as the calibrated baseline and treat priority as an intervention lever.
- **Calendars (hard constraints).**
 - Clerks 5 FTE, Mon–Fri 08:00–16:00; one clerk is *not* in the general pool on Mondays (portal support) — this reproduces the observed "queue spikes after Monday submissions".
 - Planners 8 FTE, Mon–Fri 09:00–17:00; two planners `simple_only=True`.
 - Fire reviewers 2 FTE, **Tuesday–Thursday only** (creates a hard 3day service window and a calendarinduced wait of up to 3.5 days).
 - Environmental 3 FTE, Mon–Fri but `capacity_fraction=0.6` for permits.
 - Inspectors 4 FTE, field work Tue–Fri; `travel_time(district)` added to service (D3/D5 longer); bundling can amortize travel across cases in a bundle but makes the first case wait for bundle formation (a batching window, e.g. 3 working days).
 - Legal 2 FTE, **zero service during councilmeeting weeks** except `urgent=True` (raises the p90 of `Legal check` dramatically).
 - System tasks (`Submit application`, `Issue permit`, `Reject application` routing) unlimited capacity, still obeying businesshour posting rules where observed.
 - **Applicant / thirdparty calendars are separate** from municipal calendars: `Receive missing documents` and objections run on the applicant's/neighborhood's clock (24/7 with weekend and holiday effects), never on municipal shifts.

## 1.5 Crosscase dependencies (explicit, not optional)

1. **Architect bursts.** Arrival generation is a *cluster* process: a "mother" arrival from a top20 architect with probability `p_burst` spawns `K ~ 1+NegBinom` additional cases in a 0–14 day window with the same `architect_id` and usually the same `district`.
2. **Inspection bundling.** The scheduler holds an open bundle per district for `W_batch` working days; travel cost `T_travel(bundle) = T_fixed +  legs` is shared, so marginal service time per case falls with bundle size while the first case's waiting rises. Also emits a constraint: no inspector serves two bundles at once.
3. **Neighbourhood objection clusters.** A latent neighbourhood field `_obj(block, week)` makes objections correlated across related applications (same block / same architect / overlapping publicnotice windows). Because objections are *unobserved*, this field is calibrated through the `Public-notice period` duration distribution only.
4. **Shared caseofficer effects.** A planner who picks up one Complex variance case may hold related cases (context switching), modeled as a small perswitch setup time on the planner.
5. **Policychange dependency.** Routing rules are functions of simulated time `t` (e.g., "from month 13, `Simple renovation` with `application_value<50k` and `prior_violations=False` skips Site inspection"), which makes the twin a *policy* model, not a static flow model.

# 2. Parameter-estimation plan

Everything is estimated **from the event log first**, then reconciled with the process team's domain rules and HR calendars. All estimation code lives in the PM4Py layer (§8) and emits a **fittedparameter file** consumed by the simulator.

## 2.1 Log ingestion and PM4Py usage

- Load with **pandas** (`pd.read_csv` / `pm4py.read_xes` for XES) — *there is no `pm4py.read_csv`*; conversion to an `EventLog` is done with `pm4py.format_dataframe(df, case_id_key='case:concept:name', activity_key='concept:name', timestamp_key='time:timestamp', resource_key='org:resource')`.
- Structural discovery as **crosschecks, not as the model of record**: `pm4py.discover_process_tree(log)` (Inductive Miner) and `pm4py.convert_to_petri_net(tree)` compared against the handgiven simplified tree; `pm4py.discover_dfg`, `pm4py.discover_performance_dfg`, `pm4py.discover_variants`, `pm4py.discover_variants_by_coverage`, `pm4py.extract_start_activities`/`extract_end_activities`, `pm4py.get_event_attribute_values`.
- Segmentation: `pm4py.filter_event_attribute_values(log, 'case_type', [...], level='case')`, `pm4py.filter_time_range` for seasonality windows, `pm4py.filter_end_activities` to isolate appeals.
- Conformance: `pm4py.conformance_diagnostics_alignments(log, net, im, fm)` and `pm4py.conformance_diagnostics_token_based_replay` to (a) quantify how much of the log the simplified tree explains and (b) later validate the *simulated* log (§6).
- **Limitation to state explicitly:** PM4Py's discovered tree is a *controlflow* abstraction with silent `tau` transitions and no durations, calendars or case attributes; the simulator's routing model is therefore a *separate, attributeconditioned* decision model derived from the log, and the tree is used for structural validation only.

## 2.2 Arrivals (nonstationary)

- Case arrival = timestamp of the **first** `Submit application` per case. Compute arrivals/day, dayofweek factors (Monday 2.2× vs Wednesday must be recovered), month factors (Mar–May and Sep–Nov 1.7× vs Jan–Feb), and a trend term.
- Fit a **nonhomogeneous Poisson process with piecewiseconstant intensity** `(t) = 0 · s_month(m) · s_dow(d) · s_tod(h) · (1 + ·trend)`, with `s_*` estimated as smoothed empirical rates (additiveLaplace smoothing to avoid zero cells) and renormalized so the annual total matches 31,200/18 months.
- Validate the Poisson assumption with an **index of dispersion** (variance/mean of interarrival times per stratum). Where ID > 1 (expected: Monday bursts, architect clusters), switch to a **cluster/Hawkestype** arrival model: base NHPP + architecttriggered offspring process (`p_burst`, `K` distribution, burst window from empirical coarrival times of the same `architect_id`).
- Case mix and case attributes are drawn conditionally on (month, dow, architect class) since case mix is not independent of season/architect.

## 2.3 Service vs. waiting times

**This is the hardest parameter and must not be collapsed silently.** For many human activities only *completion* timestamps exist.

1. Where `time:start_timestamp` exists: service = end  start (workingtime aware); waiting = start  predecessor end.
2. Where it does not: only `elapsed_to_prev` is observed, which equals `waiting + service + calendar outages`.
3. Resolution strategies, in order of preference:
 - **Workingtime masking:** convert `elapsed_to_prev` into *working elapsed* using the resource's calendar. For a 25minmedian task this bounds service  waiting and lets us attribute almost all working elapsed to waiting.
 - **Latentsplit model:** Bayesian/EM model with prior `service_share ~ Beta` per activity, informed by (a) activities with observed starts in the same skill pool, (b) the reported median service times (25 min, 3.5 h, …), and (c) a twoweek time study recommended in §6. Posterior on the split is propagated to the simulator as a distribution, not a point value.
4. Distribution fitting per (activity, case type, district class): candidate families lognormal, gamma, Weibull, loglogistic, and **mixtures** (routine vs. stalled). Selection by AIC/QQ + Anderson–Darling; report median and p90 and check them against the provided empirical table (a direct calibration target).
5. Special cases:
 - `Request missing documents`  `Receive missing documents` is **applicant time**, fitted separately (lognormal or loglogistic; heavy tail, median 5 d) and is *not* municipal service.
 - `Public-notice period`: fixed minimum 14 d + latentobjection extension fitted as a **mixture** `P(no objection)·14 + P(objection)·(14 + Lognormal(,))`, with `P(objection)` inferred from the bimodality of the observed `Public-notice period` durations **as a proxy**, and the objection count/identity treated as latent (never as observed events).
 - `Site inspection`: base service + `travel(district)` + `bundle_amortization` + `no_show  rescheduling delay` (a mixture component).
 - `Legal check`: service fitted on working time only; calendar blackouts (council weeks, holidays) applied as *separate* delay draws so the model can respond to D5/D6.

## 2.4 Branching / routing probabilities

- Estimate conditional branching probabilities per decision node, **stratified by `case_type` and, where the split differs, by district and value quartile**. Use **Dirichlet/Beta smoothing** with a weak prior (e.g.,  = 1) because rare cells are frequent and `Other rare variants` is 7%.
- Routing rules driven by **unobserved attributes** (buildingarea threshold for fire safety; environmental sensitivity) are handled with an **imputation model**: a logistic regression / latent class model `P(requires_fire_observed | case_type, application_value, district, …)` plus a latent flag drawn for every simulated case, so that the aggregate fire/env review incidence matches the log while remaining policysensitive (a threshold change can be simulated).
- Outcome (permit vs. reject) is a statedependent function of review results, not a constant coin: fit `P(reject | planning_conflict, legal_conflict, rework_count, case_type)`.
- Reworkbranch probabilities (`after Planning`, `after Inspection`, `after Legal`, `appeal`) estimated as conditional rates per visit; loopiteration counts per loop node fitted as geometric / negativebinomial. Since rework *reasons* are unstructured text and not coded, rework **causes are latent** (mixture of applicant error, inspector finding, legal conflict) — parameterized by the three outcomeproxies and carried as structural uncertainty in §5.

## 2.5 Resource calendars and utilization

- Calendars come from HR (authoritative for shifts/holidays) and are crosschecked against the log: e.g., the fact that one clerk is on portal duty Mondays, and that fire reviews cluster Tue–Thu. Where HR and log disagree (HR may not record councilmeeting weeks), the log wins for *effective* availability and the discrepancy is recorded as a calibration residual.
- **Utilization is not directly observed** (no start timestamps), so utilization is calibrated indirectly: simulated completions per resource per week and perskill queuelength trajectories are matched to the observed arrivaltoactivity waiting profile (the "Median waiting before activity" column is an explicit calibration target). A short time study (2 weeks, sampled start/end stamps) is the recommended data collection to convert this proxy into direct evidence.

## 2.6 Crosscase dependencies

- **Architect clusters:** from `architect_id`, fit cluster size (Poisson/NegBinom), burst window (empirical distribution of withinarchitect interarrival times), and the probability a top20 architect submits 2 cases in one week (31% of volume is the calibration constraint).
- **Inspection bundling:** estimate coscheduling potential by counting samedistrict cases whose `Inspection scheduling` falls within a 3day window (an *upper bound* on bundleable volume under current practice). Fit `travel(district)` from the observed `Site inspection` durations by district (D3/D5 longer is the given signal) using quantile regression of service on district + bundle size.
- **Objection clustering:** estimate the spatial/temporal autocorrelation of the *residual* `Public-notice period` extension (after removing the fixed 14 d minimum), i.e., do long notices cooccur in the same district/week? This calibrates the latent neighbourhood field without ever logging an objection event.

## 2.7 Known data gaps  explicit treatment

| Gap | Treatment |
|---|---|
| Missing start timestamps | Latent split model + workingtime masking; service/waiting posteriors carried into simulation as distributions; uncertainty widened in §5 |
| Objection events missing | Latent Bernoulli/cluster model calibrated on `Public-notice period` residuals only; **never** labelled as observed |
| Rework reasons uncoded | Latent cause mixture; sensitivity analysis over cause shares |
| Emergency decisions removed | Add an explicit lowrate "removed tail" mixture component (righttail is censored in the log) and widen tail intervals |
| Calendars from HR, not log | Crossvalidation with log availability patterns; residual as a sensitivity parameter |
| Flattened log, crosscase links underrepresented | Dependencies rebuilt from `architect_id`, `district`, timestamps and domain rules; treat dependency strength as a top3 sensitivity parameter |

# 3. Assumptions

### Arrivals
1. Arrivals follow a piecewiseconstant **NHPP** modulated by month, dayofweek and hourofday, fitted to `Submit application` timestamps; deviations from Poisson (ID > 1) are absorbed by an architectburst cluster process.
2. Case mix, `application_value` and the fire/env/notice flags are conditionally dependent on month, district and architect class, not i.i.d.
3. No exogenous seasonality in *applicant* behaviour beyond that captured in the arrival stream (a weaker assumption than assuming stationary arrivals).
4. Withdrawn/abandoned cases are modelled explicitly (they free capacity) but are assumed rare and constant across interventions.

### Service times
5. Service times are independent across tasks **conditional on** activity × case type × district class × resource pool (the dependence through shared resources appears as queueing, not as correlated service draws).
6. Service time is stationary within a policy regime; the interventions change *routing and capacity*, not intrinsic task difficulty (except D1, which is assumed to shift effort to presubmission and *not* to change `Completeness check` service time — a sensitivity factor).
7. Where only completion timestamps exist, service/waiting are **not** assumed to be observed; they are inferred and their uncertainty is propagated. Service and waiting are **never collapsed** into a single figure without reporting the residual unattributed share.
8. Service times are rightskewed and heavytailed for `Receive missing documents`, `Environmental review`, `Legal check`, `Site inspection`; capped draws are *flagged*, not silently winsorized.

### Routing
9. Fire/env/publicnotice requirements follow the stated rules, with the unobserved triggers (building area, environmental sensitivity) modelled as latent attributes so that aggregate incidence matches the log and policy thresholds remain manipulable.
10. `Decision drafting` is an **ANDjoin** over exactly those upstream tasks that apply to the case.
11. Rework loops at Planning, Inspection, Legal and appeal are present even though the simplified tree omits them; the *simplified tree is not the simulation's controlflow model of record* (see §8 limitations).
12. `Issue permit` / `Reject application` probabilities depend on accumulated review results and rework counts.

### Resources / calendars
13. HR calendars are correct for shifts and public holidays; councilmeeting weeks are modelled as recurring blackouts for Legal with an annual frequency (parameter, not observed).
14. Resources work on one task at a time; no multitasking within a shift except negligible context switching (a setup time per task switch of 5–15 min is included as a sensitivity).
15. System tasks have unlimited capacity and no queueing beyond a 0.5 d posting lag.
16. Overtime is not used in the baseline (adding temporary staff is D4).

### Rework
17. Loop iteration counts are geometric-like with a covariate shift by case type (Complex variance heavier); rework causes are latent mixtures.
18. `Completeness rework` is triggered only after `Receive missing documents`, matching the observed `check  request  receive  check` pattern.

### Applicant / thirdparty response
19. Applicant response times are modelled on a 24/7 clock with a mild weekend effect, and are **separate** from municipal service time; they are the main driver of the `Simple with missing docs` variant's 22 d median.
20. No strategic applicant behaviour (no gaming of the presubmission checker) beyond a modest increase in presubmission effort (D1).
21. Consultant reports for `Environmental review` are thirdparty draws that lengthen environmental service/turnaround; modelled as a mixture component.

### Crosscase dependencies
22. Architectlevel cosubmission is a cluster process; cases in a cluster share `architect_id` and usually `district`.
23. Inspection bundling is feasible only within a district and a 3workingday window; travel cost is subadditive in bundle size; the first case in a bundle pays a formation delay.
24. Neighbourhood objections are correlated in space and time (a latent field), not independent Bernoulli events.

### Nonstationary demand
25. Seasonal amplitude (1.7× Mar–May and Sep–Nov vs Jan–Feb) and the Monday factor (2.2×) are assumed stable across the horizon in the baseline; stress scenarios perturb them.
26. Policy changes take effect on a known simulated date and are *deterministic regime switches* in the routing rules.

### Missing data
27. Objection events are **never** reconstructed as if observed; the twin only models a latent variable calibrated through the `Public-notice period` proxy, and all results that depend on it carry a wide uncertainty band and a "datacollection value" note.
28. Removed emergency cases are treated as a censored right tail; tail metrics (p95/p99/CVaR95) therefore carry extra uncertainty and are reported as lower bounds on the true tail.

# 5. Warm-up, replications, and uncertainty treatment

## 5.1 Initialization and warm-up

- **Initialization:** empty system at `t=0` is the default (cold start). Because a cold start biases the early months, a second initialization is simulated: **warm start**, where the initial WIP is sampled from the empirical distribution of "cases in flight on a random day" (reconstructed from the log by lefttruncation) and placed in its observed activity's queue with a residual service/response draw. Results must be stable to this choice.
- **Warm-up length:** because demand is seasonal with a full annual cycle, a warm-up shorter than one year *cannot* warm up the queue regime of the Sep–Nov peak. Recommended: **12 simulated months warm-up** with 24 measured months. Confirm with **Welch's graphical procedure** applied to moving averages (window 30 days) of (i) cycle time, (ii) WIP, (iii) `Planning review` waiting — crosschecked with an initializationbias test (first 10% vs. last 10% of the warm-up window, twosample test on batch means). If the moving averages still drift at month 12, extend to 18 months warm-up / 36 measured.
- Warm-up must also cover at least one councilmeeting cycle and one full set of holiday blackouts.

## 5.2 Run length and replications

- Run length 36 months (12 warm-up + 24 measured). Measured window must contain 2 repetitions of every seasonal peak so peakquarter KPIs are not singlesample estimates.
- **Replications:** start at **30** per cell and increase **sequentially** to a maximum of 100 for taildominated cells (E5, E9, E15, S2, S6), stopping when the 95% CI halfwidth for the *primary* response of that cell is below the practical threshold:  2 days for median cycle time,  5 days for p90,  2 percentage points for SLA compliance,  5% of the mean for cost/case.
- Tail metrics (p95, p99, CVaR95) require  50 replications or pooled batchwithinreplication estimation; state explicitly that p99 on a 24month window with ~40,000 cases has ~400 exceedances and is correspondingly noisy.

## 5.3 Random seeds and common random numbers

- **Deterministic seeding:** `numpy.random.SeedSequence(MASTER_SEED, spawn_key=(experiment_id, replication_id))`  one child generator per *stream* (arrivals, attributes, objections, service draws per activity, travel, calendar noise). This gives bitwise reproducibility and lets different streams be reused across cells.
- **Common random numbers (CRN):** every intervention cell uses the *same* exogenous streams as its paired E0 replication (identical arrival times and case attributes, identical preindexed service draws per `(case, activity)`, identical latent objection realizations). This yields paired differences with much tighter CIs. Caveat: CRN correlation degrades when the interventions change the *number* of tasks executed (e.g., D2 removes inspections); use **indexed draws** (one draw per `(case, activity, attempt)`) rather than a sequential stream so that divergence does not destroy pairing.
- Report both the paireddifference CI **and** the marginal CIs; judge on the paired difference.

## 5.4 Intervals and inference

- Primary estimand per cell: the mean across replications of each KPI; **95% tintervals on replicationlevel statistics** (the standard for terminating steadystatefree DES with independent replications).
- Within long replications, use **batch means** (e.g., 12 batches of 60 days) to obtain a second, independent estimate of the interval and check agreement.
- **Heavy tails:** for p50/p90/p95/p99 and CVaR95 use **BCa bootstrap** over replications (2,000 resamples) rather than normal approximations; report CVaR95 ("expected shortfall on the worst 5%") as the headline tail metric because it is more stable than p99.
- **Multiple comparisons:** 17 cells × ~10 KPIs would inflate false positives; use **paired Wilcoxon / paired ttest with Holm–Bonferroni** on the E0paired differences, report effect sizes (days, percentage points) and require *practical* significance (see §7), not just p < 0.05. Claim **no optimality** — only "best supported under the stated assumptions, with the reported intervals".

## 5.5 Uncertainty treatment (three layers, reported separately)

1. **Stochastic (aleatory) uncertainty** — process randomness; handled by replications/CRN as above.
2. **Parameter (epistemic) uncertainty** — estimation error in fitted distributions, routing probabilities, calendar availability, dependency strengths. Propagate by drawing parameter vectors from their posterior/sampling distributions at the *start of each replication* (a hierarchical draw), giving intervals that cover both layers. For heavily underdetermined parameters (objection rate, service/waiting split, architect burst size) use plausible ranges, not point estimates.
3. **Structural uncertainty** — e.g., objection model as independent Bernoulli vs. clustered latent field; service/waiting split as fixed share vs. latent mixture; routing as deterministic rule vs. noisy rule. Simulate **both structural variants** as scenario blocks and report the union of intervals; do not average over them.

**Sensitivity analysis program:**
- **Stage 1 – Morris screening** on 20–25 uncertain inputs (seasonal amplitude, Monday factor, `P(objection)` and its tail , `P(missing-doc loop)`, applicant response /, planning/fire/env/legal service shapes, rework probabilities per loop, travel times D3/D5, bundle window, councilweek frequency, service/waiting split shares, burst parameters, eligibility share for D2, misrouting rate for D8). Output: \* and  ranking  identify the 3–5 dominant inputs.
- **Stage 2 – Response surface / GP emulator** (LatinHypercube, 200–400 design points) over the dominant inputs  variance decomposition (Sobol indices) and prediction intervals at candidate operating points.
- **Stage 3 – Value of information:** for each dominant input, estimate how much narrowing its uncertainty would change the *decision* (§7). Expected top3: objection rate/cluster strength, service/waiting split for `Planning review` and `Legal check`, and `prior_violations` completeness for D2. These become the datacollection recommendations.
- **Heavytail handling:** fit candidate families per heavytailed activity; if no single family fits both median and p90 (common for `Receive missing documents`), use a **twocomponent mixture** (routine lognormal + stalled/pareto component) and report both the mixture's moments and its quantiles. Draws beyond p99.5 of the fitted body are drawn from the fitted tail and **flagged** in output so results can be recomputed with a declared cap (e.g., 2× p99.5) to test taildriven conclusions. Censored (removed) emergency cases add a lowrate extra tail component; tail KPIs are reported as **lower bounds** with an explicit note.

# 6. Validation strategy

| Type | Method | Passing criterion |
|---|---|---|
| **Face validation** | Structured workshops with clerks, planners, fire/env reviewers, inspectors, legal officers, and 2–3 architects. Walk through 8 historical cases (covering each variant group) and 3 synthetic stress cases (Monday surge, objection cluster, councilweek legal delay) inside the running model with an animation/trace view. Ask "would this have happened here, and why?" | No mechanism is judged wrong by the domain experts; every unexplained timing gap is either modelled or recorded as a known gap; agreement on the queue/priority/batching policies |
| **Eventlog replay validation** | (a) Drive the simulator with the **historical arrivals and historical case attributes**, freeze exogenous draws to their historical values where recoverable, and compare predicted vs actual timestamps per activity (MAE/MAPE per activity on waiting and on service). (b) Convert the simulation output to an `EventLog` and run `pm4py.conformance_diagnostics_alignments(sim_log, net, im, fm)` against the reference Petri net derived from the given tree (`pm4py.convert_to_petri_net`) — the simulated log must be *structurally* conformant (no impossible sequences) and its fitness must not be worse than the real log's | Mean absolute timing error per activity  1 working day for short activities,  3 days for long ones;  95% of simulated traces alignmentfit the reference model |
| **Distributional validation** | Twosample KS/Anderson–Darling + QQ plots per (activity) on service and waiting; ² on branch frequencies stratified by `case_type`; compare the simulated **variantgroup shares, median and p90 durations** against the supplied variant table (26/19/18/13/8/9/7%, 12/22/48/68/140/80/90 d medians etc.) — these are hard calibration targets | Variantgroup shares within ±3 pp; median durations within ±15%; p90 within ±25% (p90 is expected to be looser because of the censored tail) |
| **Resourceutilization validation** | Simulated completions per resource per week and perskill queuelength trajectories compared with the observed "median waiting before activity" profile and with resourcelevel completion counts in the log. Check the named artefacts: Monday clerk bottleneck, fire Tue–Thu clustering, legal councilweek gaps, D3/D5 longer inspection service | Simulated median waiting per activity within ±25% of the reported table; observed qualitative artefacts reproduced (Monday spike, Tue–Thu fire, D3/D5 inspection gap). **Caveat:** utilization itself is *not observed* (no start stamps) — validate on the proxy and flag it; recommend a 2week time study to close this |
| **Bottleneck validation** | Rank activities by simulated total waiting and by queuelength × time; compare with the ranking implied by the reported "median waiting before activity" and by the variant notes (e.g., "Legal and environmental queues interact", "Applicantresponse delay dominates") | Bottleneck ordering matches for the top3; the model reproduces the *mode of failure* per variant group, not just the averages |
| **Outofsample (hindcast) validation** | (i) **Temporal split:** fit on months 1–12, test on 13–18 (arrival rates, waiting distributions, SLA compliance). (ii) **Stratified split:** hold out district D5 (long travel) and the `Complex variance` type and test. (iii) **Policy relevance:** the interventions rely on mechanisms (bundling, aging, objections) that the historical data only weakly identifies  run *reality checks* with deliberately perturbed mechanisms (stress S5) and require the ranking of E0 vs. the "known" historical reality to be stable | Predictive coverage:  85% of heldout case cycle times inside the model's 90% predictive interval (calibration check via PIT histogram); KPI point errors within the interval widths of §5; no sign reversals in the top2 ranking |

Additional checks: loopiteration distributions (rework) must reproduce the observed `Completeness check` repetition rate; crosscase validation must reproduce the cosubmission correlation of top20 architects and the sameweek/samedistrict bundleable share. **Every validation failure is recorded as a known limitation with an uncertaintywidening note, not silently tuned away.**

# 7. Decision criteria

Metrics are computed per **case type**, per **district**, per **architect group** (top20 vs. rest), and per **value quintile**, overall and in peak quarters. Thresholds below are illustrative and must be ratified with the municipality.

## 7.1 Primary metrics and thresholds

| Metric | Definition | Target / threshold |
|---|---|---|
| Median cycle time | p50 of submission  `Issue permit`/`Reject` | Improve  5% vs E0 (practical significance) with 95% CI of the paired difference excluding 0 |
| Tail duration | p90, p95 and **CVaR95** | p90 improve  10% vs E0; CVaR95 must not increase |
| SLA compliance by type | Illustrative SLAs: Simple renovation 90%  20 d; New residential 90%  60 d; Commercial 85%  90 d; Complex variance 80%  180 d | Each type must meet its band, and no type's compliance may fall by > 2 pp vs E0 |
| Throughput & backlog | Completed cases/month; endofmonth WIP; max queue age | Backlog at the 24month horizon  backlog at month 12 (no secular growth); max age  2× the type SLA |
| Rework | % of cases with  1 rework loop; reworkdays share of total cycle time | Rework share must not increase by > 2 pp (guardrail for D1/D5/D8) |
| Resource utilization | Per pool, workingtime utilization | Target band 70–85%; > 90% flagged as queueexplosion risk (heavy tails amplify there); < 50% flagged as overcapacity |
| Applicant burden | Applicantborne days + number of portal interactions | D1 must be reported alongside municipal gains (burden shifts to applicants) |

## 7.2 Equity / fairness

- **District fairness:** `p90(D3 or D5) / p90(other districts)`  1.3 **and** absolute gap  10 days; SLAcompliance gap across districts  5 pp.
- **Architect fairness:** p90 for top20 architects vs. the rest: ratio  1.3 (guards against D7/D3 benefiting only large filers).
- **Casetype fairness:** no case type may be used as a buffer: its SLA compliance must not drop while another's rises.
- **Value fairness:** the lowest value quintile must not see a compliance drop > 2 pp (guards against D2 benefiting only lowvalue cases at the expense of others via capacity reshuffling).
- Fairness metrics are reported as **disparities with confidence intervals**, not as a single score.

## 7.3 Robustness and decision rule

An intervention (or combination) is **recommended** only if **all** of:
1. **Dominance on primary metrics:** improves p50 **and** p90 **and** CVaR95 vs E0, with the paired 95% CI for each difference excluding zero and meeting the practical thresholds above;
2. **No guardrail violation:** fairness, rework, utilization band and applicantburden limits all respected;
3. **Robustness:** the sign of the improvement on the primary metrics holds in ** 5 of the 6 stress scenarios** (S1–S6) and under **both structural variants** of the objection and service/waiting models;
4. **Rank stability:** the option stays in the Pareto set (cycle time, tail, cost/case, fairness) in  90% of the parameter draws from the sensitivity emulator;
5. **Feasibility:** cost within the approved envelope (report days saved per € and cases accelerated per FTEmonth).

If several options pass, choose the **minimaxregret** option over the stress set (smallest worstcase regret in CVaR95 and SLA compliance), and report the runnerup plus the **value of information**: which additional data (objection events, start timestamps, `building_area`, `prior_violations`, council calendar) would most change the decision. If no option passes, the recommendation is **"no intervention is evidencesupported yet — collect data on X"**, explicitly not "option Y is optimal". Conclusions are worded as "best supported under the stated assumptions and intervals"; no claim of optimality is made from an unvalidated/un­calibrated model.

def load_log_frame(path: Optional[str] = None) -> pd.DataFrame:
    """Load the event log as a plain pandas DataFrame.

    Uses `pandas.read_csv` (there is no `pm4py.read_csv`). For the production log
    (18 months, 31k cases) this would be `pd.read_csv(...)` for CSV or
    `pm4py.read_xes(path)` (returns an EventLog) for XES.
    """
    if path is None:
        from io import StringIO
        frame = pd.read_csv(StringIO(EXCERPT_CSV), sep=",")
    else:
        frame = pd.read_csv(path, sep=",")

    # Raw strings -> datetime (kept explicit so we can pass a tstamp_format if needed)
    frame["time:timestamp"] = pd.to_datetime(frame["time:timestamp"], format="%Y-%m-%d %H:%M:%S")

    for col in ("requires_fire", "requires_environment", "requires_public_notice"):
        if col in frame.columns:
            frame[col] = frame[col].map({"yes": True, "no": False})

    frame["application_value"] = pd.to_numeric(frame["application_value"])
    return frame


def pm4py_to_event_log(frame: pd.DataFrame):
    """Layer A: pandas DataFrame -> pm4py EventLog.

    `pm4py.format_dataframe` is the canonical converter; the three canonical
    keys are the XES standard mappings used everywhere in PM4Py.
    """
    kwargs: Dict[str, Any] = {}
    if frame["time:timestamp"].dtype == object:              # still strings
        kwargs["tstamp_format"] = "%Y-%m-%d %H:%M:%S"

    return pm4py.format_dataframe(
        frame.copy(),
        case_id_key="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
        resource_key="org:resource",
        **kwargs,
    )


# ---------------------------------------------------------------------------
# A1. Process tree: parse the given simplified string (or explain & fall back)
# ---------------------------------------------------------------------------

PT_STRING = """->(
  'Submit application',
  *(
    ->(
      'Completeness check',
      X(
        tau,
        ->('Request missing documents','Receive missing documents')
      )
    ),
    'Completeness rework'
  ),
  +(
    'Planning review',
    X(tau,'Fire-safety review'),
    X(tau,'Environmental review')
  ),
  X(tau,'Public-notice period'),
  *(
    ->('Inspection scheduling','Site inspection'),
    'Inspection rework'
  ),
  'Decision drafting',
  X(tau,'Legal check'),
  X('Issue permit','Reject application')
)"""

PT_LIMITATIONS = """
LIMITATIONS OF THE SIMPLIFIED PROCESS-TREE STRING (documented, not ignored):
 1. Notation/format: the string is PM4Py's *infix* tree notation, NOT the PTML
    XML read by `pm4py.read_ptml`. Not every PM4Py release exposes a textual
    parser (`pm4py.parse_process_tree`), so we try it and fall back to building
    the `ProcessTree` programmatically with `pm4py.objects.process_tree.obj`.
 2. `tau` is the PM4Py silent-activity label used for the "optional" idiom
    `X(tau, A)`; it must never appear in the event log.
 3. Operator semantics in PM4Py: `->` SEQUENCE, `X` XOR, `+` PARALLEL (AND),
    `*` LOOPEXEC (do-part first, then optional redo-parts). So `+('Planning
    review', ...)` really means "reviews may run in parallel", which matches
    "reviews partly parallel".
 4. Control-flow only: the tree encodes no resources, calendars, durations,
    case attributes or routing probabilities. It is used for STRUCTURE and for
    conformance checks, never as the simulation's timing/routing model.
 5. Rework mismatch: the log shows  check -> Request -> Receive -> check , i.e.
    'Completeness check' is executed twice and the loop body is
    ->('Completeness check', X(tau, ->('Request','Receive'))), with the REWORK
    happening as a repeat of the body. The given loop
    *('Completeness check','Completeness rework') instead executes a separate
    'Completeness rework' activity that is NOT in the log excerpt. These two
    representations must be reconciled before simulation.
 6. Missing loops: rework after 'Planning review', 'Site inspection', 'Legal
    check' and the applicant 'appeal' loop are in the nominal process but NOT
    in the string. The simulator adds them explicitly (see RoutingModel).
 7. Duplicated activity semantics ('Completeness check' appearing twice) is not
    expressible in a single tree node; the simulator tracks loop counters.
 8. X('Issue permit','Reject application') looks like a free XOR but is a
    STATE-DEPENDENT decision (review results, rework counts). Fitting it as an
    unconditional XOR probability would be wrong.
 9. Real-time loops (public notice with objections, appeals) cannot carry their
    durations in a tree; they are modelled as explicit timed sub-processes.
"""


def _leaf(label: Optional[str] = None) -> ProcessTree:
    """Leaf node; label=None -> silent (tau) transition in PM4Py."""
    return ProcessTree(label=label)


def _build_tree_programmatically() -> ProcessTree:
    """Fallback builder mirroring PT_STRING using pm4py.objects.process_tree.obj."""
    tau = ProcessTree(operator=Operator.TAU)                      # silent node

    completeness_loop = ProcessTree(
        operator=Operator.LOOPEXEC,
        children=[
            ProcessTree(
                operator=Operator.SEQUENCE,
                children=[
                    _leaf("Completeness check"),
                    ProcessTree(
                        operator=Operator.XOR,
                        children=[
                            tau,
                            ProcessTree(
                                operator=Operator.SEQUENCE,
                                children=[_leaf("Request missing documents"),
                                          _leaf("Receive missing documents")],
                            ),
                        ],
                    ),
                ],
            ),
            _leaf("Completeness rework"),
        ],
    )

    reviews = ProcessTree(
        operator=Operator.PARALLEL,                                # '+' = AND
        children=[
            _leaf("Planning review"),
            ProcessTree(operator=Operator.XOR, children=[tau, _leaf("Fire-safety review")]),
            ProcessTree(operator=Operator.XOR, children=[tau, _leaf("Environmental review")]),
        ],
    )

    inspection_loop = ProcessTree(
        operator=Operator.LOOPEXEC,
        children=[
            ProcessTree(operator=Operator.SEQUENCE,
                        children=[_leaf("Inspection scheduling"), _leaf("Site inspection")]),
            _leaf("Inspection rework"),
        ],
    )

    return ProcessTree(
        operator=Operator.SEQUENCE,
        children=[
            _leaf("Submit application"),
            completeness_loop,
            reviews,
            ProcessTree(operator=Operator.XOR, children=[tau, _leaf("Public-notice period")]),
            inspection_loop,
            _leaf("Decision drafting"),
            ProcessTree(operator=Operator.XOR, children=[tau, _leaf("Legal check")]),
            ProcessTree(operator=Operator.XOR,
                        children=[_leaf("Issue permit"), _leaf("Reject application")]),
        ],
    )


def load_or_build_process_tree(pt_string: str = PT_STRING) -> ProcessTree:
    print(PT_LIMITATIONS)
    parser = getattr(pm4py, "parse_process_tree", None)           # not in every release
    if parser is not None:
        try:
            return parser(pt_string)
        except Exception as exc:                                   # noqa: BLE001
            print(f"[warn] pm4py.parse_process_tree failed ({exc}); using programmatic builder.")
    return _build_tree_programmatically()

def _perf_value(obj: Any) -> float:
    """pm4py performance DFG values may be a dict of aggregates or a raw list."""
    if isinstance(obj, dict):
        for key in ("median", "mean", "raw"):
            if key in obj:
                return _perf_value(obj[key])
        return float("nan")
    if isinstance(obj, (list, tuple, np.ndarray)):
        return float(np.median(obj)) if len(obj) else float("nan")
    return float(obj)


def pm4py_summaries(log) -> Dict[str, Any]:
    """Layer A: structural + performance discovery over the (P)M4Py EventLog."""
    variants: Dict[Tuple[str, ...], List[str]] = pm4py.discover_variants(log)
    # shares / duration per variant (median & p90 of case duration)
    frame = pm4py_convert_log_to_frame(log)
    dur = (frame.groupby("case:concept:name")["time:timestamp"]
                .agg(lambda s: (s.max() - s.min()).total_seconds() / 86400.0)
                .rename("case_duration_days"))
    case_variant = {cid: v for v, cids in variants.items() for cid in cids}
    rows = []
    total = len(dur)
    for variant, cids in variants.items():
        d = dur.loc[[c for c in cids if c in dur.index]]
        rows.append({
            "variant": " -> ".join(variant),
            "n_cases": len(cids),
            "share": len(cids) / total,
            "median_days": float(d.median()) if len(d) else np.nan,
            "p90_days": float(d.quantile(0.9)) if len(d) else np.nan,
        })
    variant_table = pd.DataFrame(rows).sort_values("share", ascending=False)

    dfg, start_acts, end_acts = pm4py.discover_dfg(log)             # counts
    try:
        perf_dfg, _, _ = pm4py.discover_performance_dfg(log)        # seconds (or dict)
    except AttributeError:                                          # older releases
        from pm4py.algo.discovery.dfg import algorithm as dfg_alg
        perf_dfg, _, _ = dfg_alg.apply(log, variant=dfg_alg.Variants.PERFORMANCE)

    perf_table = pd.DataFrame([
        {"edge": f"{a} -> {b}", "count": dfg.get((a, b), 0),
         "median_perf": _perf_value(v)}
        for (a, b), v in perf_dfg.items()
    ]).sort_values("count", ascending=False)

    # Structural cross-check against the hand-given tree (PM4Py, not simulation)
    discovered_tree = pm4py.discover_process_tree(log)
    net, im, fm = pm4py.convert_to_petri_net(discovered_tree)

    return {
        "variants": variants,
        "variant_table": variant_table,
        "dfg": dfg, "start_activities": start_acts, "end_activities": end_acts,
        "performance_dfg": perf_dfg, "performance_table": perf_table,
        "discovered_tree": discovered_tree, "net": net, "im": im, "fm": fm,
    }


def pm4py_convert_log_to_frame(log) -> pd.DataFrame:

    try:

def case_arrival_stats(frame: pd.DataFrame) -> Dict[str, Any]:
    """Layer A: non-stationary arrival profile (feeds ArrivalModel in Layer B)."""
    f = frame.sort_values("time:timestamp")
    firsts = f.groupby("case:concept:name")["time:timestamp"].min().sort_values()
    iat = firsts.diff().dt.total_seconds().dropna() / 86400.0        # days
    per_day = firsts.dt.date.value_counts()
    dow = firsts.dt.dayofweek
    month = firsts.dt.month
    dow_factor = dow.value_counts(normalize=True) / (1 / 7.0)         # vs. uniform
    month_factor = month.value_counts(normalize=True) / (1 / 12.0)

    return {
        "mean_interarrival_days": float(iat.mean()) if len(iat) else np.nan,
        "cv_interarrival": float(iat.std() / iat.mean()) if len(iat) and iat.mean() else np.nan,
        "index_of_dispersion": (float(iat.var() / iat.mean())
                                if len(iat) > 1 and iat.mean() else np.nan),   # >1 -> clustered
        "arrivals_per_day_mean": float(per_day.mean()) if len(per_day) else np.nan,
        "dow_factor": dow_factor.to_dict(),      # Monday factor must come out ~2.2x vs Wednesday
        "month_factor": month_factor.to_dict(),  # Mar-May / Sep-Nov must come out ~1.7x vs Jan-Feb
        "first_arrival": firsts.iloc[0] if len(firsts) else None,
        "last_arrival": firsts.iloc[-1] if len(firsts) else None,
    }


def add_service_waiting_columns(frame: pd.DataFrame,
                                service_share_prior: Optional[Dict[str, float]] = None,
                                working_time_fn=None) -> pd.DataFrame:
    """Layer A: service / waiting decomposition.

    CRITICAL LIMITATION (must never be ignored):
      Many human activities carry only a COMPLETION timestamp. For those events
      `elapsed_to_prev` = waiting + service + calendar outages and the split is
      NOT identified from data. Therefore:
        * `service_time` is computed only where `time:start_timestamp` exists;
        * `inferred_service` / `inferred_waiting` are computed ONLY if a
          `service_share_prior` (fitted externally, e.g. by the latent-split
          model or a time study) is supplied; otherwise they stay NaN and the
          column `attribution` is 'unattributed';
        * `working_elapsed_to_prev` removes non-working calendar time when a
          `working_time_fn` (from the Calendar class) is provided, which is the
          least-assumption way to bound the service share for short tasks.
      Service and waiting are NEVER silently collapsed into one number.
    """
    f = frame.sort_values(["case:concept:name", "time:timestamp"]).copy()

    g = f.groupby("case:concept:name")["time:timestamp"]
    f["elapsed_to_prev_days"] = (f["time:timestamp"] - g.shift(1)).dt.total_seconds() / 86400.0

    if working_time_fn is not None:
        prev = g.shift(1)
        f["working_elapsed_to_prev_days"] = [
            (working_time_fn(p, t) if pd.notna(p) else np.nan)
            for p, t in zip(prev, f["time:timestamp"])
        ]
    else:
        f["working_elapsed_to_prev_days"] = np.nan

    start_col = "time:start_timestamp"
    if start_col in f.columns:
        f["service_time_days"] = (
            (f["time:timestamp"] - pd.to_datetime(f[start_col])).dt.total_seconds() / 86400.0
        )
    else:
        f["service_time_days"] = np.nan          # NOT observed -> left missing

    if service_share_prior:
        share = f["concept:name"].map(service_share_prior)          # in [0,1]
        base = f["working_elapsed_to_prev_days"].where(
            f["working_elapsed_to_prev_days"].notna(), f["elapsed_to_prev_days"])
        f["inferred_service_days"] = base * share
        f["inferred_waiting_days"] = base * (1 - share)
        f["attribution"] = np.where(share.notna(), "prior-apportioned", "unattributed")
    else:
        f["inferred_service_days"] = np.nan
        f["inferred_waiting_days"] = np.nan
        f["attribution"] = np.where(f["service_time_days"].notna(),
                                    "observed-start", "unattributed")

    f["is_completion_only_log"] = f["service_time_days"].isna()
    return f

class Calendar:
    """Shifts + holidays + blackouts (council weeks, out-of-season fields)."""

    def __init__(self, weekly_windows: Dict[int, List[Tuple[str, str]]],
                 holidays: Sequence[pd.Timestamp] = (),
                 blackout_weeks: Sequence[int] = (),
                 capacity_fraction: float = 1.0):
        self.weekly_windows = weekly_windows   # {0..6: [("08:00","16:00")]}
        self.holidays = set(pd.to_datetime(list(holidays)))
        self.blackout_weeks = set(blackout_weeks)      # ISO weeks, e.g. council weeks
        self.capacity_fraction = capacity_fraction    # e.g. env: 0.6 for permit work

    def is_working(self, t: pd.Timestamp) -> bool: ...
    def next_working_start(self, t: pd.Timestamp) -> pd.Timestamp: ...
    def add_working_time(self, t_start: pd.Timestamp, hours: float) -> pd.Timestamp: ...
    def working_hours_between(self, t0: pd.Timestamp, t1: pd.Timestamp) -> float: ...

class Simulator:
    """Discrete-event simulation: priority queues, AND-joins for 'Decision
    drafting', loop counters for rework, calendars, cross-case bundling."""

    def __init__(self, spec: ExperimentSpec,
                 arrivals: ArrivalModel,
                 routing: RoutingModel,
                 service: ServiceTimeModel,
                 resources: ResourcePool,
                 objections: ObjectionModel,
                 coordinator: CrossCaseCoordinator):
        self.spec, self.arrivals, self.routing = spec, arrivals, routing
        self.service, self.resources = service, resources
        self.objections, self.coordinator = objections, coordinator
        self.events: List[Tuple[pd.Timestamp, str, Any]] = []   # time-ordered FEL

    def schedule(self, t: pd.Timestamp, kind: str, payload: Any) -> None: ...
    def run(self, seed: int) -> List[EventRecord]:
        """Main loop: arrivals -> task ready -> resource request -> service
        completion -> routing (incl. rework loops and appeal) -> terminal.
        'Decision drafting' is released only when its AND-join is complete."""
        ...
    def kpis(self, records: List[EventRecord]) -> Dict[str, Any]:
        """p50/p90/p95/CVaR95 cycle time per case type, SLA compliance,
        district/architect disparities, utilization, rework share, backlog."""
        ...


class ExperimentRunner:
    """Matrix execution, CRN pairing, replications, CIs, sensitivity hooks."""

    MASTER_SEED = 20260101

    def __init__(self, matrix: List[ExperimentSpec], fitted_params: Dict[str, Any]): ...

    @staticmethod
    def _streams(exp_id: str, rep: int) -> Dict[str, np.random.Generator]:
        """One independent child generator per exogenous stream; the same
        (exp_id=paired baseline, rep) key pair is used for the intervention cell
        so common random numbers survive."""
        ss = np.random.SeedSequence(ExperimentRunner.MASTER_SEED, spawn_key=(hash(exp_id) % 2**32, rep))
        names = ["arrivals", "attributes", "objections", "service", "travel", "calendar"]
        children = ss.spawn(len(names))

    def run_one(self, spec: ExperimentSpec) -> pd.DataFrame:
        rows = []
        for rep in range(spec.n_reps):
            streams = self._streams(spec.paired_to or spec.exp_id, rep)   # CRN
            sim = self._build(spec, streams)
            recs = sim.run(seed=rep)
            rows.append({"exp_id": spec.exp_id, "rep": rep, **sim.kpis(recs)})
        return pd.DataFrame(rows)

    @staticmethod
    def paired_difference(base: pd.DataFrame, treat: pd.DataFrame,
                          metric: str) -> Dict[str, float]:
        """95% t-CI on paired (CRN) differences; add BCa bootstrap for tails."""
        d = treat.set_index("rep")[metric] - base.set_index("rep")[metric]
        n, m, s = len(d), d.mean(), d.std(ddof=1)
        half = 1.96 * s / np.sqrt(n) if n > 1 else np.nan
        return {"mean_diff": float(m), "ci95_lo": float(m - half), "ci95_hi": float(m + half)}

    @staticmethod
    def bootstrap_quantile_ci(values: np.ndarray, q: float = 0.95, n_boot: int = 2000,
                              seed: int = 0) -> Tuple[float, float]:
        """BCa/percentile bootstrap for p90/p95/p99 and CVaR95 (heavy tails)."""
        rng = np.random.default_rng(seed)
        stats = [np.quantile(rng.choice(values, size=len(values), replace=True), q)
                 for _ in range(n_boot)]
        return float(np.quantile(stats, 0.025)), float(np.quantile(stats, 0.975))
