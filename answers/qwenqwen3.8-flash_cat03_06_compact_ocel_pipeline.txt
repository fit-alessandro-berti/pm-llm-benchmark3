## 1. Modeling assumptions

- **Object types and capitalization**: I use singular, title-case object types: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`. Object identifiers are uppercase: `O100`, `O200`, `I1`, `I2`, `I3`, `P1`, `P2`, `D1`, `D2`, `V1`, `M1`, `M2`.

- **E2O qualifier vocabulary**:
  - Direct source qualifiers:
    - `creates`: an event creates an object.
    - `adds`: an event adds an item to an order context.
    - `involves_order`: the event explicitly involves an order, as stated by the narrative.
    - `reserves`: stock reservation for an item.
    - `packs_package`: an event creates/packs a package.
    - `packs_item`: an event packs a specific item.
    - `dispatches_package`: an event dispatches a package.
    - `dispatches_delivery`: an event dispatches a delivery.
    - `issues`: an event issues an invoice.
    - `records_payment`: an event records a payment object.
    - `settles`: a payment event settles against an invoice.
    - `confirms_delivery`: an event confirms a delivery.
    - `closes`: an event closes an order.
  - Analytical propagated qualifiers:
    - `propagated_involves_order`: derived order involvement from composition/settlement context.
    - `propagated_involves_item`: derived item involvement from package/delivery context.
    - `propagated_involves_package`: derived package involvement from delivery confirmation context.

- **O2O direction conventions**: I use the direction “subject object  related object”:
  - `Order --contains--> Item`
  - `Package --packs--> Item`
  - `Delivery --carries--> Package`
  - `Invoice --bills--> Order`
  - `Payment --partially_settles--> Invoice`
  - `Payment --completes_settlement--> Invoice`

  Direction expresses semantic dependency or composition, not necessarily temporal causality.

- **Logistics and financial events vs Orders/Items**:
  - Logistics and financial events are directly related to the objects explicitly acted upon: packages, deliveries, invoices, and payments.
  - Orders are directly related only where the narrative explicitly says the event relates to both orders: reserve stock for `I1` and `I3`, pack `P1`, and issue invoice `V1`.
  - Other downstream order/item/package links are modeled as **analytical propagated E2O relations** using `propagated_*` qualifiers. This keeps flattening on `Order`, `Package`, and `Item` operationally meaningful while preserving provenance.

- **Preventing propagated relations from being confused with source facts**:
  - Propagated links are isolated by qualifier prefix `propagated_`.
  - Static composition is kept in `o2o`, not silently copied into `relations`.
  - A source-only analysis can filter `relations` to exclude qualifiers beginning with `propagated_`.
  - The validation step checks that all E2O qualifiers belong to the declared vocabulary.

- **Version-dependent PM4Py assumption**:
  - I assume `OCEL(events=events, objects=objects, relations=relations, o2o=o2o)` is available.
  - If a PM4Py version uses positional arguments, a different factory method, or different keyword names, only the constructor line should be adjusted. The four DataFrames and their semantics should remain unchanged.

## 3. Data-model audit

### Object types and objects

| Object type | Objects |
|---|---|
| `Order` | `O100`, `O200` |
| `Item` | `I1`, `I2`, `I3` |
| `Package` | `P1`, `P2` |
| `Delivery` | `D1`, `D2` |
| `Invoice` | `V1` |
| `Payment` | `M1`, `M2` |

### O2O qualifiers and cardinality

| O2O qualifier | Direction convention | Cardinality | Examples / pairs |
|---|---:|---:|---|
| `contains` | `Order -> Item` | 3 | `O100 -> I1`, `O100 -> I2`, `O200 -> I3` |
| `packs` | `Package -> Item` | 3 | `P1 -> I1`, `P1 -> I3`, `P2 -> I2` |
| `carries` | `Delivery -> Package` | 2 | `D1 -> P1`, `D2 -> P2` |
| `bills` | `Invoice -> Order` | 2 | `V1 -> O100`, `V1 -> O200` |
| `partially_settles` | `Payment -> Invoice` | 1 | `M1 -> V1` |
| `completes_settlement` | `Payment -> Invoice` | 1 | `M2 -> V1` |

### Activities and touched object types

The table distinguishes direct source involvement from analytical propagated involvement.

| Activity | Events | Direct E2O object types | Propagated E2O object types |
|---|---|---|---|
| `Create Order` | `E01`, `E04` | `Order` | — |
| `Add Item` | `E02`, `E03`, `E05` | `Item`, `Order` | — |
| `Reserve Stock` | `E06` | `Item`, `Order` | — |
| `Pack Package` | `E07`, `E08` | `Package`, `Item`, `Order` | `Order` |
| `Dispatch Package` | `E09`, `E10` | `Package`, `Delivery` | `Item`, `Order` |
| `Issue Invoice` | `E11` | `Invoice`, `Order` | — |
| `Record Payment` | `E12`, `E15` | `Payment`, `Invoice` | `Order` |
| `Confirm Delivery` | `E13`, `E14` | `Delivery` | `Package`, `Item`, `Order` |
| `Close Order` | `E16`, `E17` | `Order` | — |

### Especially consequential events for convergence or divergence

- `E06` — `Reserve Stock`: one event links `I1`, `I3`, `O100`, and `O200`. It is the first clear convergence point between the two orders.
- `E07` — `Pack Package` for `P1`: one event links `P1`, `I1`, `I3`, `O100`, and `O200`. It is the strongest cross-order convergence event because a single package combines items from two orders.
- `E09` — `Dispatch Package` for `D1`: direct `P1`/`D1` involvement plus propagated item/order involvement creates a divergence from a combined package to a single delivery while still touching both orders analytically.
- `E11` — `Issue Invoice`: one invoice event links `V1`, `O100`, and `O200`, creating financial convergence.
- `E13` — `Confirm Delivery` for `D1`: one delivery confirmation is analytically propagated to `P1`, `I1`, `I3`, `O100`, and `O200`, making logistics and order lifecycles converge in a single event.
- `E12` and `E15` — `Record Payment`: two payment events converge on one invoice `V1`, and through propagated order links they also touch both orders. `E15` is especially important because it completes settlement.

## 4. Expected flattened behavior

The expected behavior below assumes the hybrid policy in the pipeline: direct source links plus explicitly qualified propagated analytical links. If propagated links are filtered out, the `Order`, `Package`, and `Item` flattened views become much sparser.

### Flattening on `Order`

- **Approximate trace shape**:
  - Two traces: one for `O100`, one for `O200`.
  - `O100` is longer because it includes both `P1`-related and `P2`-related logistics events.
  - `O200` is shorter but still includes cross-order events involving `P1` because `P1` packs `I3` from `O200`.
  - A plausible `O100` activity sequence is:
    `Create Order`  `Add Item`  `Add Item`  `Reserve Stock`  `Pack Package`  `Pack Package`  `Dispatch Package`  `Dispatch Package`  `Issue Invoice`  `Record Payment`  `Confirm Delivery`  `Confirm Delivery`  `Record Payment`  `Close Order`.
  - A plausible `O200` activity sequence is:
    `Create Order`  `Add Item`  `Reserve Stock`  `Pack Package`  `Dispatch Package`  `Issue Invoice`  `Record Payment`  `Confirm Delivery`  `Record Payment`  `Close Order`.

- **Copied shared events**:
  - `E06` reserve stock appears in both order traces.
  - `E07` pack `P1` appears in both order traces.
  - `E09` dispatch `P1`/`D1` appears in both order traces through propagated links.
  - `E11` issue `V1` appears in both order traces.
  - `E12` payment `M1` appears in both order traces through propagated links.
  - `E13` confirm `D1` appears in both order traces through propagated links.
  - `E15` payment `M2` appears in both order traces through propagated links.

- **Omitted lifecycle aspects**:
  - Traditional traces usually do not expose which object instance caused each copied event.
  - `O100` and `O200` traces may not distinguish `P1` from `P2`, `D1` from `D2`, `M1` from `M2`, or amounts unless event attributes are retained.
  - The difference between direct source involvement and propagated analytical involvement is lost in ordinary flattening.
  - `O200` does not include `E08`, `E10`, or `E14`, which is correct because those events involve only `P2`, `D2`, and `I2`.

- **Likely DFG edges**:
  - `Create Order`  `Add Item`
  - `Add Item`  `Add Item`
  - `Add Item`  `Reserve Stock`
  - `Reserve Stock`  `Pack Package`
  - `Pack Package`  `Pack Package`
  - `Pack Package`  `Dispatch Package`
  - `Dispatch Package`  `Issue Invoice`
  - `Issue Invoice`  `Record Payment`
  - `Record Payment`  `Confirm Delivery`
  - `Confirm Delivery`  `Confirm Delivery`
  - `Confirm Delivery`  `Record Payment`
  - `Record Payment`  `Close Order`

- **Misleading interpretations**:
  - The trace may suggest that payments are order-specific, when they are actually invoice-specific.
  - The trace may suggest that `O200` is directly involved in `D1`, when the source event is a delivery of `P1`, and the order link is propagated through `I3`.
  - Repeated `Record Payment` and `Confirm Delivery` edges may look like rework or loops, when they are simply interleaving across shared orders.
  - The flattened order view may overstate the importance of propagated links if the analyst assumes all relations are source observations.

### Flattening on `Package`

- **Approximate trace shape**:
  - Two short traces: `P1` and `P2`.
  - `P1`: `Pack Package`  `Dispatch Package`  `Confirm Delivery`.
  - `P2`: `Pack Package`  `Dispatch Package`  `Confirm Delivery`.

- **Copied shared events**:
  - No event is copied across both package traces in this model.
  - The same activity names appear in both traces, but the event instances are distinct.

- **Omitted lifecycle aspects**:
  - The package traces omit items inside the package.
  - They omit source orders.
  - They omit invoice and payment settlement.
  - `Confirm Delivery` appears in package traces only because of propagated links; the raw event was a delivery confirmation.

- **Likely DFG edges**:
  - `Pack Package`  `Dispatch Package`
  - `Dispatch Package`  `Confirm Delivery`

- **Misleading interpretations**:
  - `P1` and `P2` look structurally identical, hiding that `P1` combines items from two orders while `P2` contains only one item from one order.
  - `Confirm Delivery` may be misread as a package-specific confirmation rather than a delivery confirmation analytically propagated to the package.
  - The absence of item and order context may lead to overly optimistic claims that package lifecycle is independent.

### Flattening on `Delivery`

- **Approximate trace shape**:
  - Two very short traces: `D1` and `D2`.
  - `D1`: `Dispatch Package`  `Confirm Delivery`.
  - `D2`: `Dispatch Package`  `Confirm Delivery`.

- **Copied shared events**:
  - No event is copied across both delivery traces.

- **Omitted lifecycle aspects**:
  - The delivery traces omit carried packages.
  - They omit items and orders.
  - They omit invoice and payment context.
  - The delivery creation event is not separately modeled; dispatch is the first visible delivery event.

- **Likely DFG edges**:
  - `Dispatch Package`  `Confirm Delivery`

- **Misleading interpretations**:
  - `D1` and `D2` look identical, hiding that `D1` carries the cross-order package `P1`.
  - The delivery view may suggest logistics is a simple two-step process, while the object-centric model shows complex package and order coupling.
  - The activity name `Dispatch Package` in a delivery trace can be misleading because the event is also a delivery dispatch.

### Flattening on `Invoice`

- **Approximate trace shape**:
  - One trace for `V1`.
  - Sequence: `Issue Invoice`  `Record Payment`  `Record Payment`.

- **Copied shared events**:
  - No event is copied across multiple invoice traces because there is only one invoice.
  - The same invoice event is propagated to both order traces, but not the other way around.

- **Omitted lifecycle aspects**:
  - The invoice trace omits billed orders unless event attributes or object IDs are retained.
  - It may not distinguish `M1` from `M2` if only activity names are kept.
  - It may omit payment amounts if flattening does not preserve event attributes.
  - It omits logistics completion.

- **Likely DFG edges**:
  - `Issue Invoice`  `Record Payment`
  - `Record Payment`  `Record Payment`

- **Misleading interpretations**:
  - Two `Record Payment` activities may look like repeated payments without indicating that the first is partial and the second completes settlement.
  - The trace may suggest payments are sequential and independent, when they are jointly settling one invoice.
  - The order-level billing relationship is hidden.

### Why flattening on `Payment` would be particularly weak

Flattening on `Payment` would produce one-event traces for `M1` and `M2`:

- `M1`: `Record Payment`
- `M2`: `Record Payment`

This is weak because payment lifecycle is not meaningful in isolation. The important facts are:

- `M1` partially settles `V1`.
- `M2` completes settlement of `V1`.
- `V1` bills `O100` and `O200`.
- The amounts `100` and `150` are event attributes.

A `Payment`-centric traditional trace loses invoice context, order context, settlement status, and amount unless additional attributes are explicitly retained. The object-centric or invoice-centric views are far more informative.

## 5. Expected object-centric structures

### OC-DFG

The OC-DFG should reveal activity sequences and interactions mediated by object instances rather than by artificial traces.

Expected insights:

- `P1` should create a package-centric chain:
  - `Pack Package`  `Dispatch Package`  `Confirm Delivery`.
- `V1` should create an invoice-centric chain:
  - `Issue Invoice`  `Record Payment`  `Record Payment`.
- `M1` and `M2` should appear as payment objects interacting with `V1` through `Record Payment` and settlement semantics.
- `O100` and `O200` should show strong shared interaction through:
  - `E06` reserve stock,
  - `E07` pack `P1`,
  - `E09` dispatch `D1`,
  - `E11` issue `V1`,
  - `E12` payment `M1`,
  - `E13` confirm `D1`,
  - `E15` payment `M2`.
- `O100` should additionally show `P2`-specific behavior through `E08`, `E10`, and `E14`.
- `O200` should close earlier than `O100`, but both order objects should be connected to the same invoice and payment settlement events through propagated analytical links.

The OC-DFG should therefore show convergence at `P1`, `V1`, and the payments, and divergence after packing into `P1`/`D1` versus `P2`/`D2`.

### OTG

The OTG should show object-type relationships derived from O2O and possibly event co-touching.

Expected type-level edges:

- `Order -> Item` through `contains`.
- `Package -> Item` through `packs`.
- `Delivery -> Package` through `carries`.
- `Invoice -> Order` through `bills`.
- `Payment -> Invoice` through `partially_settles` and `completes_settlement`.

Instance-level interpretation:

- `P1` is the package type instance that bridges `Item` and `Delivery`.
- `V1` is the invoice type instance that bridges `Order` and `Payment`.
- `M1` and `M2` are payment type instances connected to `V1`.
- `O100` and `O200` are order type instances connected to `V1` and, through item/package composition, to `P1`.

The OTG should make clear that the process is not a single order-centric lifecycle but a heterogeneous network where orders, items, packages, deliveries, invoices, and payments interact.

### ET–OT graph

The ET–OT graph should show which activities touch which object types.

Expected patterns:

- `Create Order`, `Add Item`, `Reserve Stock`, `Pack Package`, `Issue Invoice`, `Record Payment`, `Confirm Delivery`, and `Close Order` touch `Order` because of direct or propagated links.
- `Add Item`, `Reserve Stock`, `Pack Package`, `Dispatch Package`, and `Confirm Delivery` touch `Item`.
- `Pack Package`, `Dispatch Package`, and `Confirm Delivery` touch `Package`.
- `Dispatch Package` and `Confirm Delivery` touch `Delivery`.
- `Issue Invoice` and `Record Payment` touch `Invoice`.
- `Record Payment` touches `Payment`.

Specific instance relevance:

- `P1` is touched by `Pack Package`, `Dispatch Package`, and `Confirm Delivery`.
- `V1` is touched by `Issue Invoice` and both `Record Payment` events.
- `M1` and `M2` are touched by their respective `Record Payment` events.
- `O100` and `O200` are touched by many activities, especially the shared cross-order events.

The ET–OT graph should highlight that `Record Payment`, `Confirm Delivery`, `Pack Package`, and `Issue Invoice` are high-connectivity activities because they bridge multiple object types.

### Object-centric Petri net

A plausible object-centric Petri net interpretation would include:

- Places or token types for `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`, possibly instance-specific depending on the PM4Py implementation.
- Transitions for the 17 activities.
- Token creation for `O100`, `O200`, `P1`, `P2`, `D1`, `D2`, `V1`, `M1`, and `M2`.
- Synchronization where one event consumes or produces multiple object tokens:
  - `E06` may require or touch tokens for `I1`, `I3`, `O100`, and `O200`.
  - `E07` may create or update `P1` while touching `I1`, `I3`, `O100`, and `O200`.
  - `E11` may create `V1` and connect it to `O100` and `O200`.
  - `E13` may update `D1` and propagate effects to `P1`, `I1`, `I3`, `O100`, and `O200`.
- `P1` should appear as a package token or place involved in packing, dispatching, and confirmation.
- `V1` should appear as an invoice token or place involved in issuance and settlement.
- `M1` and `M2` should appear as payment tokens or places created by payment recording and connected to `V1`.
- `O100` and `O200` should appear as order tokens or places that are created, synchronized through shared events, and eventually closed.

Important caveat: the object-centric Petri net does not have one uniquely determined interpretation. Different PM4Py versions or modeling conventions may represent shared events as transitions with multiple input/output arcs, as replicated transitions, or as token-flow patterns over object types. The qualitative insight is the cross-object synchronization, not a single canonical net.

### Object-interactions summary

The object-interactions summary should highlight pairs of objects that co-occur in events or are connected through O2O semantics.

Expected insights:

- `P1` should interact with `I1`, `I3`, `O100`, `O200`, and `D1`.
- `P2` should interact with `I2`, `O100`, and `D2`.
- `V1` should interact with `O100`, `O200`, `M1`, and `M2`.
- `M1` and `M2` should interact with `V1`, and through propagated links with `O100` and `O200`.

  - stock reservation,
  - packing of `P1`,
  - dispatch of `D1`,

  - and confirmation of `D1`.

The summary should make clear that the strongest convergence is not between two complete orders in isolation, but through shared intermediate objects: `P1`, `V1`, `M1`, and `M2`.

## 6. Modeling alternatives

### Alternative 1: Source-minimal E2O relations

Policy:

- Include only direct source facts.
- Remove all `propagated_*` E2O links.
- Keep O2O composition as the only mechanism for understanding how packages, items, deliveries, invoices, and payments relate to orders.

Effect on discovery:

- `Order` flattening becomes sparse: dispatch, delivery confirmation, and payments may disappear from order traces.
- `Package` flattening may omit `Confirm Delivery` if package confirmation is not a direct source event.
- OC-DFG and OTG may still show composition through O2O, but traditional flattened views will understate lifecycle coupling.
- Object-centric Petri net may show more disconnected object lifecycles.
- The business story remains the same, but the analysis becomes more conservative and may miss operational consequences.

Trade-off:

- Pro: minimal inflation and clean source provenance.
- Con: flattened views can be misleadingly incomplete.

### Alternative 2: Full operational involvement as direct source relations

Policy:

- Treat every event that affects an item, package, delivery, invoice, or payment as directly involving all related orders and items.
- Replace `propagated_involves_order` with direct qualifiers such as `involves_order`.
- Similarly promote propagated item and package links to direct links.

Effect on discovery:

- `Order` traces become rich and include dispatch, confirmation, invoice, and payment events.
- DFGs become denser and may show more loops and apparent concurrency.
- Flattening becomes more useful for business users but less faithful to raw event logs.
- Object-centric discovery may overstate the number of direct order-item interactions.
- The same business story is preserved, but the model asserts that the source system already recorded all downstream order context.

Trade-off:

- Pro: strong analytical convenience and fewer missing lifecycle events in flattened views.
- Con: relation inflation and loss of provenance between observed and derived links.

### Alternative 3: O2O-propagated analytical relations computed only at query time

Policy:

- Keep `relations` strictly source-minimal.
- Do not materialize propagated E2O links in the OCEL.
- When analyzing, use O2O to expand order, item, package, or invoice context in derived views.

Effect on discovery:

- Standard PM4Py flattening based only on E2O relations will produce sparse traces.
- Object-centric structures that use O2O may still reveal composition.
- Derived order-centric views can be created separately without contaminating source tables.
- DFGs and log skeletons from raw flattening may miss cross-object lifecycle events.
- The business story is unchanged, but the pipeline must explicitly distinguish raw discovery from derived propagation.

Trade-off:

- Pro: cleanest separation of source facts and analytical inference.
- Con: more complex analysis pipeline and potentially weak default flattening.

### Alternative 4: Hybrid with qualifier filtering

Policy:

- Use the hybrid model from the pipeline.
- Always run discovery twice:
  - once on all relations,
  - once on direct-only relations by filtering out qualifiers beginning with `propagated_`.

Effect on discovery:

- The direct-only view shows what the source system explicitly observed.
- The all-relations view shows analytically enriched lifecycle behavior.
- Differences between the two views reveal the impact of propagation.
- This makes convergence and divergence visible without hiding their provenance.

Trade-off:

- Pro: best balance between interpretability and analytical richness.
- Con: requires analysts to understand and respect qualifier semantics.

## 7. Failure modes

1. **Relation inflation**
   - Adding too many propagated E2O links can make every event appear to involve every order and item.
   - DFGs and OC-DFGs become dense, and discovery may suggest false concurrency or rework.
   - Mitigation: use explicit `propagated_*` qualifiers and keep propagation minimal.

2. **Missing direct E2O links**
   - If an event creates or affects an object but is not linked to it, the object may have an empty or misleading lifecycle.
   - For example, omitting `E07 -> P1` would make `P1` invisible in package-centric discovery.
   - Mitigation: validate that every event and object appears in at least one relation.

3. **Treating O2O propagation as observation**
   - O2O links such as `Order contains Item` or `Invoice bills Order` are static relationships.
   - They should not be mistaken for event occurrences.
   - If propagated E2O links are not marked, analysts may believe the source system directly recorded order context for every logistics or payment event.
   - Mitigation: separate O2O from E2O and mark derived E2O links.

4. **Duplicate shared events after flattening**
   - A shared event such as `E07` may appear in both `O100` and `O200` traces.
   - Aggregating flattened traces can double-count the same event and inflate frequencies.
   - Mitigation: annotate traces with event IDs, aggregate by unique event when needed, or use object-centric discovery.

5. **Ambiguous payment allocation**
   - `M1` and `M2` settle `V1`, but the narrative does not allocate amounts to `O100` and `O200`.
   - Propagating payments to both orders may imply that each payment is split across orders, which is not stated.
   - Mitigation: keep payment-to-invoice links direct, order links propagated, and add allocation attributes only if they exist in the source.

6. **Overly short Payment traces**
   - Flattening on `Payment` yields one-event traces and hides settlement context.
   - This can lead to the false conclusion that payments have no lifecycle.
   - Mitigation: flatten on `Invoice` or use object-centric structures.

7. **Constructor/API version mismatch**
   - PM4Py versions may differ in how `OCEL` is constructed or how OCEL functions are exposed.
   - If the constructor fails, changing the data model to satisfy the API is the wrong fix.
   - Mitigation: isolate the constructor line and adjust only the API call, not the DataFrame semantics.

8. **False total order for same-time events**
   - This example has no timestamp ties, but in general equal timestamps can produce arbitrary ordering after flattening.
   - A DFG may imply a strict sequence where only concurrency is known.
   - Mitigation: use stable secondary sorting by event ID or add sequence attributes when source ordering is meaningful.

9. **Naive timestamps**
   - Losing timezone information can break ordering across regions or daylight saving transitions.
   - Mitigation: use timezone-aware UTC timestamps and validate dtype.

10. **Qualifier inconsistency**
   - Synonyms such as `contains`, `has_item`, and `includes` fragment the semantic model.
   - Discovery may treat them as unrelated qualifiers if they are used in filters or summaries.
   - Mitigation: define and validate a closed qualifier vocabulary.

11. **Duplicate relation rows**
   - Duplicate E2O rows inflate activity frequencies and object interactions.
   - Mitigation: validate duplicates on all columns and on the semantic key `(eid, oid, qualifier)`.

12. **Modeling amount as an object**
   - Payment amount is an event attribute, not a separate object.
   - Creating amount objects would distort object-centric discovery and imply amount lifecycle.
   - Mitigation: keep `ocel:amount` in the `events` table.

A reviewer should be able to inspect the generated tables and confirm at least the following assertions:

1. **Event completeness and uniqueness**:
   - `events` contains exactly 17 rows with unique IDs `E01` through `E17`.
   - The timestamps match the narrative and are timezone-aware UTC.

2. **Object completeness and typing**:
   - `objects` contains exactly the stated 11 objects:
     `O100`, `O200`, `I1`, `I2`, `I3`, `P1`, `P2`, `D1`, `D2`, `V1`, `M1`, `M2`.
   - Each object has the correct type: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, or `Payment`.

3. **Payment amounts are event attributes**:
   - `E12` has `ocel:amount = 100`.
   - `E15` has `ocel:amount = 150`.
   - No amount is represented as a separate object.

4. **O2O composition matches the business relationships**:
   - `O100` contains `I1` and `I2`.
   - `O200` contains `I3`.
   - `P1` packs `I1` and `I3`.
   - `P2` packs `I2`.
   - `D1` carries `P1`.
   - `D2` carries `P2`.
   - `V1` bills `O100` and `O200`.
   - `M1` partially settles `V1`.
   - `M2` completes settlement of `V1`.

5. **Explicit shared events are directly related to both orders**:
   - `E06` relates to `O100` and `O200` with direct `involves_order`.
   - `E07` relates to `O100` and `O200` with direct `involves_order`.
   - `E11` relates to `O100` and `O200` with direct `involves_order`.

   - Every row in `relations` has the same `ocel:activity` and `ocel:timestamp` as the corresponding row in `events` for that `ocel:eid`.
   - Every `relations.ocel:type` matches the type of the corresponding object in `objects`.

8. **No orphan or duplicate structural facts**:
   - Every event ID in `relations` exists in `events`.
   - Every object ID in `relations` and `o2o` exists in `objects`.
   - There are no duplicate relation rows and no duplicate O2O rows.
