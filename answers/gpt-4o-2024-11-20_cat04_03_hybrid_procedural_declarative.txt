# 1. Policy Interpretation and Conflict Resolution

### Material Assumptions
1. Reject Vendor and Activate Vendor are mutually exclusive end states, per R1.
2. The R5 and R6 statements create a normative conflict concerning the sequence of Sanctions Escalation, Obtain Legal Opinion, and Activate Vendor. 
3. Emergency activation (R6) operates as an exceptional policy outside regular compliance rules and is jointly authorized without direct traceability in logs.
4. All identified constraints are enforceable either within traceable activity flows or via additional attributes such as resource ID and timestamps.

### R5/R6 Conflict and Possible Resolutions
- **Resolution 1 (Strict Compliance Priority):** Sanctions Escalation must always be followed by Obtain Legal Opinion before Activate Vendor, even under emergency scenarios. Emergency activations are disallowed unless additional documentation exists.
  - **Compliance risk:** Strictly forbids emergency activation, which could delay critical vendor onboarding under operational needs.
  
- **Resolution 2 (Emergency Exception):** Emergency activation is allowed before Obtain Legal Opinion but requires a post-facto check for the legal opinion to occur within 24 hours. The process should flag these cases for manual review due to the lack of an explicit "emergency" log attribute.
  - **Compliance risk:** Introduces exceptions to normal policies, increasing manual workload and creating edge cases for regulatory audits.

The implemented model adopts **Resolution 2** to cater to operational flexibility while introducing a flagging mechanism to monitor and enforce post-activation obligations under emergency conditions.

# 3. Procedural Backbone

### Formal Description
- Start with `Receive Onboarding Request`.
- Afterward, execute `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` concurrently.
- Once all three are complete, proceed to `Classify Risk`.
- Based on risk classification:
  - Reject Vendor;
  - For low risk, perform `Manager Approval` followed by `Activate Vendor`;
  - For high risk, perform `Enhanced Due Diligence`, followed by `Compliance Approval`, then `Activate Vendor`.
- Release First Payment post-activation.
- Close Onboarding marks terminal completion.

### Python Code
```python
from pm4py.objects.process_tree import process_tree as pt
from pm4py.objects.process_tree.utils import generic
import pm4py

# Process Tree Definition
tree = pt.ProcessTree(operator=pt.ProcessTreeOperator.SEQ)
child1 = pt.ProcessTree(operator=pt.ProcessTreeOperator.PAR)
child1.children.extend([
    pt.ProcessTree(identifier="Capture Master Data"),
    pt.ProcessTree(identifier="Run Sanctions Screening"),
    pt.ProcessTree(identifier="Verify Bank Account"),
])
child2 = pt.ProcessTree(identifier="Classify Risk")
child3 = pt.ProcessTree(operator=pt.ProcessTreeOperator.XOR)
child3.children.extend([
    pt.ProcessTree(identifier="Reject Vendor"),
    pt.ProcessTree(operator=pt.ProcessTreeOperator.SEQ, children=[
        pt.ProcessTree(identifier="Manager Approval"),
        pt.ProcessTree(identifier="Activate Vendor")
    ]),
    pt.ProcessTree(operator=pt.ProcessTreeOperator.SEQ, children=[
        pt.ProcessTree(identifier="Enhanced Due Diligence"),
        pt.ProcessTree(identifier="Compliance Approval"),
        pt.ProcessTree(identifier="Activate Vendor")
    ])
])
tree.children.extend([child1, child2, child3])

# Assign procedural model
procedural_model = tree
```

### Explanation of Key Features
1. **Concurrency:** `Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` execute in parallel after the onboarding request.
2. **Choices:** XOR branch after `Classify Risk` cleanly models exclusive outcomes.
3. **Clarification Loops:** Explicitly omitted from the procedural backbone; handled separately in DECLARE as they are not block-structured.
4. **Post-Activation Behavior:** `Release First Payment` and `Close Onboarding` are linear post-activation activities.
5. **Approximations:** Parallelism assumes no interaction delays.

### Emergency Activation
```python
def check_emergency_activation(events):
    emergency_flags = []
    for case in events:
        if "Activate Vendor" in case and "Obtain Legal Opinion" in case:
            activate_time = case["Activate Vendor"]
            opinion_time = case["Obtain Legal Opinion"]
            if activate_time < opinion_time and (opinion_time - activate_time).total_seconds() > 86400:
                emergency_flags.append(case["case_id"])
    return emergency_flags
```

### Key Points
1. **Redundancies:** R1 appears in both procedural and declarative layers.
2. **Inconsistencies:** Emergency policy creates potential contradictions with strict sequencing.

# 10. Deployment Recommendation

### Canonical Representation
The procedural backbone serves as the core model, with declarative rules extending to enforce non-sequential constraints.

### Authoritative Policy Layer
The separation of duties and temporal profiles are independently authoritative layers, providing flexible guardrails around the procedural model.

### Conformance Check Order
1. Procedural backbone for main flow.
2. DECLARE for non-sequential constraints.
3. Resource overlap and temporal deviations.
4. Emergency checks and exception flagging.

### Contradictory Findings
Surface conflicts as warnings with appropriate metadata to allow human intervention in policy-sensitive cases.
