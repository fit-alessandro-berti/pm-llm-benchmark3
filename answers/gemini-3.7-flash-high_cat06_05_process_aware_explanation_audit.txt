## 2. Process-model consistency checks

To guarantee that predictive explanations reflect valid, actionable, and temporally uncorrupted process reality, an automated validation suite must execute across five formal layers:

```
+-----------------------------------------------------------------------------+
|                          EXPLANATION VALIDATION SUITE                       |
+-----------------------------------------------------------------------------+
| Layer 1: Temporal & Point-in-Time Availability Assertion (t_event <= t0)    |
| Layer 2: Sequence Integrity & Same-Timestamp Resolution (sequence_index)    |
| Layer 3: Process Conformance & Declarative Rules (Declare / Footprint)      |
| Layer 4: State-Based Activity Enabling & Explanation Validity               |
| Layer 5: Semantic Distinction of Re-executions (e.g., Appeals) vs Anomalies |
+-----------------------------------------------------------------------------+
```

### 1. Prefix-Time Availability and Lineage Verification
- **Assertion:** For any feature $f$ or event $e$ included in the training vector or explanation at checkpoint $t_0$, enforce:
  $$\tau(e) \le t_0 \quad \text{and} \quad \tau_{\text{asserted}}(f) \le t_0$$
- **Implementation:** Bi-temporal feature store audit. Compare the event timestamp $\tau(e)$ and ingestion/assertion timestamp $\tau_{\text{asserted}}(f)$ against $t_0$. Any feature lacking a point-in-time timestamp or derived from aggregate case-level tables (e.g., `total_case_duration`, `final_decision`) fails the gate immediately.

### 2. Activity-Order Feasibility and Same-Timestamp Ambiguity Resolution
- **Problem:** Source systems often log events with identical timestamps ($\Delta t = 0$, e.g., batch commits or second-level granularity). Ingestion without an explicit sequence key leads to random or alphabetical ordering, generating impossible artifacts like `Claim Closed -> Damage Assessment Completed`.
- **Validation Rule:**
  - For any pair of events $e_1, e_2$ in case $\sigma$ where $\tau(e_1) = \tau(e_2)$, require an immutable, monotonically increasing integer `sequence_index` (or database log sequence number LSN).
  - If `sequence_index` is missing or null, flag the trace as *Ambiguous Ordering* and quarantine it from pattern explainers.
  - Assert that the causal footprint matrix satisfies reachability: the transition `Claim Closed -> Damage Assessment Completed` is marked strictly forbidden ($M_{\text{footprint}}(\text{Claim Closed}, \text{Damage Assessment}) = \#$).

### 3. Complete-Trace vs. Prefix-Trace Discrimination
- **Check:** Compare the feature extraction scope against the prefix sub-log $\mathcal{L}_{prefix(t_0)}$.
- **Implementation:**
  - `trace_variant_id` must be computed solely over the prefix trace $\langle e_1, e_2, \dots, e_k \rangle$ where $\tau(e_k) = t_0$.
  - Trace entropy and sequence patterns are evaluated on prefix windows $\sigma_{\le t_0}$. Any explainer token referencing activities outside $\Sigma_{prefix(t_0)}$ is rejected.

### 4. Activity-Enabling and Explanation State Classification
At $t_0$ (`Coverage Check Completed`), an explanation engine must categorize all process activities into four distinct modal states:
1. **Executed in Prefix (Admissible as Historical Fact):** `Claim Registered`, `Coverage Check Completed`. Can be cited as observed facts (e.g., "Registration to coverage check took 1.2h").
2. **Currently Enabled / Immediately Pending (Admissible as Next-Step Risk):** `Damage Assessment Completed` (fast track) or `Documents Requested` (evidence track). Can be cited as immediate operational choices.
3. **Future-Possible Downstream (Inadmissible as Realized Events):** `Settlement Decision Recorded`, `Appeal`, `Claim Closed`. Cannot be cited as executed events or pattern drivers at $t_0$.
4. **Normatively Impossible from Current State (Anomalous / Bug):** `Claim Closed` before `Damage Assessment`, or `Appeal` before `Settlement Decision`. Citing these indicates structural model error or pipeline failure.

### 5. Semantic Validation of Re-executions vs. Process Cycles
- **Normative Looping Rule:** The activity `Settlement Decision Recorded` can legitimately execute twice if and only if an `Appeal` intervenes following an adverse decision:
  $$\text{Response}(\text{Settlement Decision Recorded}[\text{result} \in \{\text{Partial}, \text{Deny}\}], \text{Appeal})$$
  $$\text{Precedence}(\text{Appeal}, \text{Settlement Decision Recorded}_{\text{second}})$$
- **Role & Limitations of Mining Formalisms:**
  - **Directly-Follows Graphs (DFG):** A DFG collapses multi-instance executions into single nodes and edges. An edge `Settlement Decision -> Appeal` and `Appeal -> Settlement Decision` creates a cycle in the DFG. However, a DFG is purely descriptive (reflecting historical transitions) and cannot enforce that the first decision must be `Partial` or `Deny`, nor does it prevent an infinite loop. A frequent DFG edge is not a normative rule.
  - **Declare / Linear Temporal Logic (LTL):** Formally enforces multi-event dependencies (e.g., `AlternateResponse`, `ChainPrecedence`) across non-adjacent events.
  - **Prefix Alignments:** Computes the cost-optimal alignment between the observed prefix $\sigma_{\le t_0}$ and the normative Petri net. Guarantees that the explanation state corresponds to a reachable marking.
  - *Limitation:* Alignments assume the normative model is complete; legitimate emergency bypasses or ad-hoc operational fast-tracks may be penalized as non-conforming unless the process model accommodates planned exceptions.

## 3. Alternative feature interpretations

To prevent misleading stakeholder narratives, surviving and repaired features are categorized by their epistemic and operational status:

```
+-----------------------------------------------------------------------------------+
|                            FEATURE TAXONOMY & USAGE                               |
+-----------------------------------------------------------------------------------+
| 1. Defensible Predictive Signals        | 2. Process-State / Congestion Signals   |
|    - initial_damage_complexity          |    - queue_length_at_t0                 |
|    - initial_reserve                    |    - elapsed_since_registration_at_t0   |
|    - claimant_channel                   |                                         |
+-----------------------------------------+-----------------------------------------+
| 3. Fairness / Robustness Proxies        | 4. Drift / Calendar Proxies             |
|    - claimant_region                    |    - calendar_week                      |
+-----------------------------------------+-----------------------------------------+
| 5. Unusable Until Lineage Repaired                                                |
|    - prior_claim_count_before_t0, same_day_document_count_snapshot,               |
|      final_handler_team, risk_score_current, last_resource_role, employee_exp     |
+-----------------------------------------------------------------------------------+
```

### 1. Defensible Predictive Signal
*Features:* `initial_damage_complexity`, `initial_reserve`, `claimant_channel`.
- **Permissible Claims:** "Claims with high initial complexity and substantial initial reserves statistically require more extensive evidence gathering, multi-party inspections, and higher approval thresholds, increasing the probability of exceeding the 10-day settlement window."
- **Impermissible Claims:** Causal intervention claims must not be made. Adjusting or artificially lowering the initial reserve will not accelerate the case; initial reserve is an indicator of case magnitude, not an operational lever.

### 2. Process-State or Congestion Signal
*Features:* `queue_length_at_t0`, `elapsed_since_registration_at_t0`.
- **Permissible Claims:** "High queue length at $t_0$ reflects operational intake congestion, leading to waiting-time delays before downstream assessment begins. Time consumed between registration and coverage check directly depletes the fixed 10-day SLA buffer."
- **Impermissible Claims:** Do not claim handler-level incompetence from general queue depth. Do not claim that skipping coverage checks is a viable solution to save elapsed time.

### 3. Proxy Requiring Fairness and Robustness Review
*Features:* `claimant_region`.
- **Permissible Claims:** "Geographic region correlates with local repair-network capacity, inspection facility availability, and travel logistics."
- **Impermissible Claims:** Must not be presented as claimant-driven fault or used to justify deprioritization, discriminatory routing, or delayed settlement. Region must undergo rigorous disparate impact testing to ensure it does not serve as a proxy for protected socioeconomic or demographic characteristics. Where possible, replace with direct operational capacity metrics (`regional_adjuster_availability`).

### 4. Drift and Calendar Proxy
*Features:* `calendar_week`.
- **Permissible Claims:** "Calendar week 52 exhibits seasonal throughput reductions due to holiday operating hours, reduced adjuster staffing, and partner business closures."
- **Impermissible Claims:** Cannot be claimed as a permanent or structural causal mechanism. Cannot be assumed stable across years if operating policies, staffing shifts, or holiday coverage rules change.

### 5. Unusable Until Lineage is Repaired
*Features:* `prior_claim_count_before_t0`, `same_day_document_count_snapshot`, `final_handler_team`, `risk_score_current`, `last_resource_role`, `employee_experience`.
- **Audit Requirement:**
  - `prior_claim_count_before_t0`: SQL must be corrected to filter strictly by `claim_created_at < t0`.
  - `same_day_document_count_snapshot`: Replace daily 23:00 batch snapshot with real-time stream filtered to `event_time <= t0`.
  - `final_handler_team` & `last_resource_role`: Replace with `handler_team_at_t0` and `coverage_check_resource_role`.
  - `risk_score_current`: Implement immutable scoring logs to extract `risk_score_as_of_t0`.
  - `employee_experience`: Recompute tenure dynamically as of $t_0$.
- **Permissible/Impermissible Claims:** *Zero* predictive or explanatory reliance is permitted until lineage repair is verified. Once repaired, they become valid prefix-state or resource signals.

## 5. Recommendations for explanation validation

To establish robust, audit-compliant, and process-consistent predictive monitoring, the organization should execute the following prioritized roadmap:

```
+-----------------------------------------------------------------------------------+
|                        EXPLANATION VALIDATION ROADMAP                             |
+-----------------------------------------------------------------------------------+
| 1. Architecture: Bi-Temporal Feature Store & Point-in-Time Joins (Immediate)     |
| 2. Ingestion Integrity: Monotonic Sequence Indexing for Coincident Events        |
| 3. Conformance Gate: Prefix Truncation & State-Based Activity Verification        |
| 4. Model Calibration: Retraining on Prefix Features & OOTV Recalibration         |
| 5. Explanation Governance: Prefix SHAP, Stability Testing & Causal Boundaries     |
| 6. Fairness & Ethics: Disparate Impact Auditing of Regional/Channel Proxies       |
| 7. Monitoring: Continuous Tracking of PSI, Process Drift & Policy Changes        |
+-----------------------------------------------------------------------------------+
```

### 1. Bi-Temporal Feature Store Design (Immediate Priority)
- **Point-in-Time Joins:** Implement an enterprise feature store (e.g., Feast, Hopsworks) that enforces strict `as-of` temporal joins based on the prediction timestamp $t_0$:
  $$\text{FeatureValue}(f, t_0) = \arg\max_{\tau \le t_0} \text{Record}(f, \tau)$$
- **Immutability & Slowly Changing Dimensions:** Eliminate in-place overwrites for mutable fields (`risk_score`, `handler_team`, `reserves`). Store all attribute updates as append-only event streams or SCD Type 2 tables with explicit `valid_from` and `valid_to` microsecond timestamps.
- **Deprecate Daily Snapshots:** Replace end-of-day batch snapshots (`same_day_document_count_snapshot`) with real-time sliding-window aggregations bounded strictly by $t \le t_0$.

### 2. Event-Log Conformance and Sequence Integrity Gate
- **Monotonic Sequence Indexing:** Ensure source data extractors assign a monotonic integer `sequence_index` or transaction ID to disambiguate same-timestamp events ($\Delta t = 0$).
- **Prefix Conformance Filtering:** Prior to feature extraction, validate prefix traces $\sigma_{\le t_0}$ against the normative process model (Petri net / BPMN). Traces exhibiting impossible sequences (e.g., `Claim Closed` before `Damage Assessment`) must trigger pipeline alerts and be quarantined.

### 3. Prefix-Only Retraining and Calibration
- **Feature Purging:** Permanently remove all full-trace aggregations (`total_case_duration`, `appeal_seen_anywhere`, `full_trace_variant_id`, `final_*`, `last_*`).
- **Model Retraining:** Re-estimate baseline predictive models exclusively on valid prefix attributes and prefix process metrics (e.g., prefix elapsed time, intake queue length, initial complexity, prefix variant).
- **Probability Recalibration:** Recalibrate model output probabilities using Platt scaling or Isotonic Regression on out-of-time validation (OOTV) splits to ensure predicted breach probabilities reflect genuine post-leakage risk distributions.

### 4. Explanation Governance and Causal Claim Fencing
- **Prefix-Constrained Explanations:** Evaluate TreeSHAP / KernelSHAP strictly within the prefix-admissible feature space. Suppress any local explanation feature referencing downstream states.
- **Explanation Stability:** Test explanation robustness against minor data perturbations (e.g., queue length ±1) to prevent unstable local attributions.
- **Causal Claim Boundaries:** Formally annotate model explanation cards:
  - *Statistical Association:* High reserve, complexity, channel.
  - *Operational State:* Queue length, elapsed time.
  - *Strict Prohibition:* Explanations must never present correlational proxies as prescriptive causal levers (e.g., claiming that altering reserve amounts will accelerate settlement).

### 5. Fairness, Proxy, and Disparate Impact Auditing
- **Protected Attribute Review:** Conduct rigorous fairness audits (Equalized Odds, Demographic Parity) on geographic and channel features (`claimant_region`, `claimant_channel`) to prevent systemic bias against specific claimant demographics.
- **Operational Decomposition:** Replace sensitive geographic proxies with explicit operational factors (e.g., local assessor capacity, distance to certified repair network) to enhance actionability and mitigate bias.

### 6. Continuous Process Drift and Schema Monitoring
- **Data & Concept Drift:** Deploy Population Stability Index (PSI) and Wasserstein distance monitors on all prefix features.
- **Process Drift Tracking:** Monitor transition probability matrices and prefix variant distributions. Trigger automated alerts when operating policy revisions or holiday schedules alter baseline cycle times.
- **Continuous Explanation Audit:** Periodically sample production local explanations and run automated assertion checks to verify zero leakage of newly created warehouse fields.
