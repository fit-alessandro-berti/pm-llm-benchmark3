# 4. Network and conformance analyses

Use the analyses below as screening and validation tools, not as proof of a relationship or intent. Before analysis, preserve the original source extract, retain an event identifier if available, normalize time zones, and determine whether `lifecycle:transition` records represent separate start/complete events or separate business occurrences.

**Prepare a PM4Py-ready event table and preserve actor uncertainty**

```python
import pandas as pd
import pm4py

CASE = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"
RES = "org:resource"

raw = raw.copy()
raw[TS] = pd.to_datetime(raw[TS], utc=True, errors="coerce")
raw["_source_order"] = range(len(raw))
raw = raw.sort_values([CASE, TS, "_source_order"], kind="stable")

evt = pm4py.format_dataframe(
    raw,
    case_id=CASE,
    activity_key=ACT,
    timestamp_key=TS
)
```

Create a separately governed `verified_actor` field only after reconciliation to identity-provider, workflow, bot-service-account, and detailed audit-trail data. Do not silently replace an unknown identity with `org:resource`, `entered_by`, or `approved_by`; classify such events as unresolved.

**Reproduce and then validate four-eyes findings**

```python
def four_eyes_violations(log, activity_1, activity_2, actor_key):
    return pm4py.filter_four_eyes_principle(
        log,
        activity_1,
        activity_2,
        resource_key=actor_key,
        keep_violations=True
    )

reported_po = four_eyes_violations(
    evt,
    "Create Purchase Order",
    "Approve Purchase Order",
    RES
)

reported_bank_payment = four_eyes_violations(
    evt,
    "Change Vendor Bank Details",
    "Payment Approval",
    RES
)

verified_human_evt = evt.loc[
    evt["verified_actor"].notna()
    & evt["actor_type"].eq("human")
].copy()

confirmed_po = four_eyes_violations(
    verified_human_evt,
    "Create Purchase Order",
    "Approve Purchase Order",
    "verified_actor"
)

confirmed_bank_payment = four_eyes_violations(
    verified_human_evt,
    "Change Vendor Bank Details",
    "Payment Approval",
    "verified_actor"
)
```

The precise keyword names can vary slightly by PM4Py release; the key methodological point is to run the test twice: first on the recorded resource field, then on validated, non-shared human identities. Exclude confirmed bot actions from a rule defined for the “same human resource,” but retain them for separate data-quality reconciliation.

`get_service_time` is meaningful only where the lifecycle data reliably records paired start/complete events. For manual uploads and quarter-close migrations, compare original event time, upload time, and ingestion time.

**Check the emergency exception with declarative and custom controls**

A Declare response rule can test the basic existence condition: every `Emergency Override` should be followed by `Retrospective Justification`. A discovered Declare model is descriptive; the policy rule should be imposed separately.

```python
verified_compliant_emergency = emergency_log.loc[
    emergency_log["verified_emergency_compliance"].eq(True)
].copy()

baseline_declare = pm4py.discover_declare(verified_compliant_emergency)
baseline_diagnostics = pm4py.conformance_declare(
    emergency_log,
    baseline_declare
)

policy_declare = {
    "response": {
        ("Emergency Override", "Retrospective Justification"): {
            "support": 1.0,
            "confidence": 1.0
        }
    }
}

response_diagnostics = pm4py.conformance_declare(
    emergency_log,
    policy_declare
)

skeleton = pm4py.discover_log_skeleton(verified_compliant_emergency)
skeleton_diagnostics = pm4py.conformance_log_skeleton(
    emergency_log,
    skeleton
)
```

The exact Declare-model dictionary format should be checked against the installed PM4Py version. Neither a Declare response constraint nor a log skeleton can fully express “within three working days by a different human.” That policy should be tested with adjacent Python logic using the organization’s working-day calendar and validated actor identities:

```python
from pandas.tseries.offsets import CustomBusinessDay

COMPANY_BDAY = CustomBusinessDay(holidays=company_holidays)

def check_emergency_exception(case_events):
    g = case_events.sort_values(TS)
    overrides = g[g[ACT].eq("Emergency Override")]
    results = []

    for _, override in overrides.iterrows():
        deadline = override[TS] + 3 * COMPANY_BDAY
        justifications = g[
            g[ACT].eq("Retrospective Justification")
            & g[TS].ge(override[TS])
            & g[TS].le(deadline)
        ]

        if pd.isna(override["verified_actor"]):
            results.append("identity_unresolved")
        elif justifications["verified_actor"].isna().any():
            results.append("identity_unresolved")
        elif (justifications["verified_actor"] != override["verified_actor"]).any():
            results.append("pass")
        else:
            results.append("same_actor_or_missing_independent_review")

    return results
```

Confirm whether policy requires the retrospective reviewer to differ from the override actor only, or also from the emergency approver.

# 5. Evidence that would materially change the assessment

**Evidence that would increase concern**

- Immutable source audit records showing that the same authenticated individual performed both sides of a four-eyes control, rather than merely sharing a role-labelled account.
- A confirmed `entered_by`/`approved_by` identity sequence showing bank-detail change and payment approval by the same person without an approved exception.
- Absence of a V-77x migration ticket, maintenance file, or case linkage for a manual bank-detail change.
- Vendor bank-confirmation records that do not match the bank account used in the payment run.
- Payment files showing that a changed bank account received payment shortly after the update, especially for high amount bands and without independent validation.
- Missing or invalid emergency tickets, expired delegations, absent on-call authorization, or retrospective justifications outside the three-working-day deadline.
- Raw detailed logs showing that same-person retrospective justifications were not merely imported from a spreadsheet and were not independently reviewed.
- Evidence that a shared account was used contrary to policy without a compensating, attributable audit trail.
- Legacy_erp source data showing that a purported bot action was actually initiated by a human credential, or that the mapping table was changed selectively.
- Repeated unexplained exceptions across unrelated vendors, regions, purchase categories, or emergency/non-emergency routes after controlling for workload and policy.

**Evidence that would reduce concern**

- An approved V-77x banking-platform migration plan containing the affected vendors, dates, bank-account changes, responsible teams, and manual-upload batch identifiers.
- Vendor confirmations, callback records, or secure portal confirmations matching the revised bank details and payment destination.
- Field-level vendor-master logs showing a genuine maker-checker approval by separate authenticated users.
- Approved RACI, delegation matrix, and emergency/on-call roster supporting the Carla–Gita and Dan–Hugo routes.
- Emergency incident reports, facilities work orders, clinical supply urgency records, and evidence that the relevant goods or repairs were received.
- Retrospective Justification records created or independently approved by a different verified human within three working days.
- Original spreadsheet and import logs demonstrating that the 12 quarter-close records retained their original preparer/reviewer identities and were merely timestamped at migration.
- A corrected legacy_erp mapping table and bot job logs demonstrating that apparent bot/human same-resource findings were artifacts.
- Consistent event semantics showing that `entered_by` identifies data entry, `approved_by` identifies approver, and `org:resource` is only a role account; this would allow accurate re-performance of controls.

# 6. Cautious audit-report wording

Analysis of the procurement-to-payment event log identified control exceptions and process patterns that warrant targeted follow-up; it does not establish fraud, collusion, or other misconduct. The most concerning subgroup is the VendorMaster_Lena–AP_Kim cluster involving vendor family V-77x: it combines nine reported bank-detail-change/payment-approval four-eyes exceptions, a 17-minute median in 16 rapid cases, high manual_upload use, high-value concentration, and a repeated correction loop. The combination is more risk-relevant than any one indicator, but it may also be explained in part by the documented V-77x banking-platform migration and missing ticket linkage.

Emergency medical and facilities routes show very short approvals and recurring handovers. Their high emergency rates, known urgency channels, and weekend pattern make emergency handling and informal specialization plausible explanations. They should nevertheless be tested for an authorized override and a timely retrospective justification by an independent human. The same-person retrospective-justification findings are control exceptions, but twelve appear to be quarter-close spreadsheet migrations and require source-record reconciliation before reliance.

Interpretation is limited by a shared Approver_Gita account, legacy_erp bot-to-human mapping errors, and ambiguity between org:resource, entered_by, and approved_by. Accordingly, the reported four-eyes counts should be re-performed using authenticated individual identities. Internal Audit should first obtain vendor-master tickets, vendor bank confirmations, payment-run approvals, emergency tickets, retrospective approvals, and immutable access/import logs for the prioritized cases. Any conclusion regarding misconduct should await that corroboration.
