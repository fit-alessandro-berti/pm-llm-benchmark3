## 1. Equivalence design space

An execution is a timestamp-ordered list of events, each with an activity label and E2O links to objects typed by Order, Item, Package, Delivery, Invoice, Payment, etc., plus O2O triples with qualifiers. Identifiers beginning `EXT` are external. The relations form, in general, a refinement chain: exact refines typed-structural refines business-semantic refines activity-sequence.

**1. Activity-sequence equivalence, $\sim_A$.** Two executions are equivalent iff their projections onto activity labels, in timestamp order, are identical sequences. Preserved: activity order and repetition count. Discarded: all objects, multiplicities, sharing, qualifiers, identifiers. It is equality of sequences, hence reflexive, symmetric and transitive. Same-timestamp events are treated as one unordered multiset per timestamp, canonically sorted by label, avoiding arbitrary recorded order.

**2. Typed structural equivalence, $\sim_T$.** Equivalent iff there is a bijection between local object identifiers preserving object type, `EXT` flag, ordered activity sequence, per-event E2O type-multisets, reuse of an object across events, and O2O triples including qualifier strings. Preserved: object-type counts, per-event cardinalities, topology, sharing, repeated events. Discarded: concrete local identifiers, timestamps beyond order, unrecorded attributes. Existence of a type-preserving isomorphism is reflexive, symmetric (inverse isomorphism) and transitive (composition). Same-timestamp events are unordered: an isomorphism must respect timestamp precedence only.

**3. Business-semantic equivalence, $\sim_S$ (preferred).** Equivalent iff equality holds for the semantic signature $\phi$ defined in §2: activity sequence, local/external counts per type, per-event type counts, external-sharing dimensions for logistics vs finance, categorized O2O qualifiers, and lifecycle motifs such as substitution, split shipment, partial settlement, return-repack. Preserved: business-relevant multiplicities, sharing, qualifiers, repetition, motif structure. Discarded: local names, exact O2O wording beyond category, order among independent same-time events, symmetric identity of packages/items. As equality of $\phi$, it is reflexive, symmetric and transitive. It is coarser than $\sim_T$ in general, yet finer than $\sim_A$.

**4. Exact OCEL equivalence, $\sim_E$.** Equivalent iff raw identifiers, activity sequence, timestamps, E2O and O2O links with qualifiers, and recorded event order are identical. Preserved: everything recorded. Discarded: nothing. It is equality, hence an equivalence relation; same-timestamp recorded order is preserved, which is precisely why it is brittle.

## 2. Canonical signatures

The preferred signature is $\phi$ applied after canonical renaming. Canonicalisation first colours objects by type and externality, refines colours by neighbouring events and O2O links, then renames objects in refined-colour/first-occurrence order. This makes X1 and X2 identical despite swapped item identifiers, while X7 items remain distinguishable via replacement, removal and Dispatch incidence. The semantic projection then retains counts, sharing flags, qualifier categories and motifs, not canonical names themselves.

```python
QUAL = {"replaces": "REPLACES", "removed_before_dispatch": "REMOVED",
        "partially_settles": "PARTIAL", "completes_settlement": "COMPLETE",
        "repacks": "REPACK", "replaces_package": "REPACK"}

def canonical_signature(events, o2o):
    # events: [{'activity': str, 'objects': {type: [ids]}}] in order
    # o2o: [(src_id, dst_id, qualifier)]
    objs, first = {}, {}
    for i, ev in enumerate(events):
        for typ, ids in ev["objects"].items():
            for oid in ids:
                objs[oid] = (typ, oid.startswith("EXT"))
                first.setdefault(oid, i)
    color = {oid: objs[oid] for oid in objs}
    for _ in range(max(1, len(objs))):  # colour refinement
        new = {}
        for oid in objs:
            neigh = []
            for i, ev in enumerate(events):
                if any(oid in ids for ids in ev["objects"].values()):
                    neigh.append((i, ev["activity"],
                                  tuple(sorted(color[x] for ids in ev["objects"].values()
                                               for x in ids))))
            neigh += [("O2O", color[s], color[d], q) for s, d, q in o2o if oid in (s, d)]
            new[oid] = (color[oid], tuple(sorted(map(str, neigh))))
        if new == color: break
        color = new
    order = sorted(objs, key=lambda o: (str(color[o]), first[o], objs[o][0]))
    canon, per_type = {}, {}
    for oid in order:  # invariant to local renaming
        t = objs[oid][0]; per_type[t] = per_type.get(t, 0) + 1
        canon[oid] = f"{t}#{per_type[t]}"
    activities = tuple(ev["activity"] for ev in events)
    counts = tuple(sorted((t,
        sum(1 for o in objs if objs[o][0] == t and not objs[o][1]),
        sum(1 for o in objs if objs[o][0] == t and objs[o][1])) for t in per_type))
    per_event = tuple((ev["activity"],
        tuple(sorted((t, len(ids), sum(x.startswith("EXT") for x in ids))
                     for t, ids in ev["objects"].items()))) for ev in events)
    quals = tuple(sorted(QUAL.get(q, q.upper()) for _, _, q in o2o))
    ext_log = any(ev["activity"] in ("Pack Package", "Dispatch") and
                  any(x.startswith("EXT") for ids in ev["objects"].values() for x in ids)
                  for ev in events)
    ext_fin = any(ev["activity"] in ("Issue Invoice", "Record Payment") and
                  any(x.startswith("EXT") for ids in ev["objects"].values() for x in ids)
                  for ev in events)
    motifs = (("SUBST" if {"REPLACES", "REMOVED"} & set(quals) else "-"),
              ("RETURN_REPACK" if {"Return Item", "Inspect Return"} & set(activities) else "-"))
    return (activities, counts, per_event, quals, ext_log, ext_fin, motifs)
```

Grouping executions by this tuple is reproducible and implements $\sim_S$.

## 4. Cluster interpretations

**S1 Baseline isolated fulfilment (X1,X2).** Signature: one package, delivery, invoice and payment for two items. Behaviour: standard end-to-end order. Risk/opportunity: low structural risk; ideal benchmark for automation and cycle-time analysis. Flattening on Item fragments invoice/payment and duplicates them; flattening on Order is adequate here but not generally. Stable under renaming, reordering of the two Add Item events, and identifier repair.

**S2 Split packages, consolidated delivery (X3).** Signature: two one-item packages, one delivery. Behaviour: warehouse splits shipment but transport consolidates. Risk/opportunity: package-level loss, mis-pick and tracing complexity, but lower transport cost. Flattening on Order hides which package holds which item; on Package loses the shared delivery. Stable unless packing links are missing, which would falsely collapse it to S1.

**S3 Split packages, split deliveries, split settlement (X4).** Signature: two package-delivery cycles and two payments, partial then completing. Behaviour: staggered fulfilment and staged cash collection. Risk/opportunity: backorder communication, extra delivery cost, under-settlement; opportunity for partial fulfilment revenue. Flattening on Order merges two deliveries into one case and hides the second cycle; on Delivery splits the single invoice. Stable in counts, but payment semantics depend on retaining partial/complete qualifiers or amounts.

**S4 Externally shared logistics (X5).** Signature: baseline locally, but package/delivery shared with an external order and item. Behaviour: cross-order consolidation. Risk/opportunity: cost allocation, delay contagion, confidentiality and liability; opportunity for shared transport savings. Flattening on Order duplicates the shared package and delivery, overstates cost and hides dependency. Stable only while `EXT` flags are retained; filtering external objects collapses it to S1.

**S5 Externally shared finance (X6).** Signature: baseline logistics, jointly billed invoice and payment with external order. Behaviour: combined billing without order-level allocation. Risk/opportunity: revenue recognition, collection, reconciliation and dispute risk. Flattening on Order double-counts the full invoice; on Invoice loses order attribution. Stable if external links on Issue Invoice and Record Payment are kept; vulnerable if finance links are recorded only as O2O relations.

**S6 Substitution / removal before dispatch (X7).** Signature: baseline activities, Dispatch includes the replacement item, O2O records replacement and removal. Behaviour: item I71 was packed then removed, I72 substituted. Risk/opportunity: consent, picking-error, warranty and inventory risk; opportunity to learn substitution causes. Flattening on Order shows a normal completed case and loses the removal; on Item disconnects invoice. Fragile: depends on qualifiers and Dispatch E2O incidence; dropping qualifiers alone leaves the weaker Dispatch-incidence signal.

**S7 Return and repack (X8).** Signature: initial shipment plus Return Item, Inspect Return, second Pack and Dispatch of the same item. Behaviour: post-delivery return loop ending in redelivery. Risk/opportunity: reverse-logistics cost, quality failure, non-terminating loops; opportunity for inspection learning. Flattening on Order may truncate or merge the two dispatches, creating apparent loops or duplicate shipments. Fairly stable due to distinct activities, but fragile if return events are filtered as exceptions.

## 5. Borderline cases

**X1 versus X2.** $\sim_A$, $\sim_T$ and $\sim_S$ merge them; $\sim_E$ separates them because every identifier differs. Both answers are defensible: renaming invariance is correct for process behaviour, exact identity matters for audit traceability. The opposite Add Item identifier order is irrelevant under all renamed relations.

**X1 versus X5.** $\sim_A$ merges them; $\sim_T$ and $\sim_S$ separate them. Activity labels around O5 are identical, but Pack/Dispatch involve an external order and item, and the package packs three objects. Ignoring external objects would wrongly merge a shared-logistics execution with an isolated one.

**X1 versus X6.** Again $\sim_A$ merges, $\sim_T/\sim_S$ split, but on the finance dimension: invoice and payment are shared and unallocated. Local multiplicities near O6 look baseline-like only if `EXT` objects are dropped. The disagreement shows why activity projection cannot be called object-centric.

**X1 versus X7.** $\sim_A$ merges; $\sim_T/\sim_S$ split. The difference is invisible in labels but present in qualified O2O relations and in Dispatch's extra Item link. Conversely, a purely qualifier-based semantic view is fragile: if qualifiers are unreliable, one might defensibly merge, accepting that substitution is then unobservable.

**X3 versus X4.** A coarse “split-package” semantic grouping that ignores delivery and payment multiplicity would merge them; $\sim_A$, $\sim_T$ and the present $\sim_S$ split them. X3 consolidates delivery and settles once, X4 staggers deliveries and settles in two steps. The disagreement is about whether customer-visible delivery and cashflow differences are business-semantic or mere attributes.

**X4 versus X8.** Both contain two Pack and two Dispatch events, so a coarse repeated-shipment motif could merge them. $\sim_A/\sim_T/\sim_S$ split them: X4's second cycle fulfils a different item for the first time and is paid partially then completed, whereas X8's second cycle repacks a returned item after explicit return and inspection. Collapsing repeated labels or ignoring qualifiers would erase this distinction.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py's `cluster_equivalent_ocel` implements an exact-equivalence style key for a chosen lead object type: recursively, it encodes the ordered events of an object's execution, their activities and timestamps, the linked objects by type and raw identifier, and their executions, subject to a size limit. It therefore preserves identity, exact order, exact multiplicity and shared-object structure. That is valuable for auditing, but raw identifiers make clusters too fine in practice: X1 and X2, and almost any two real orders, fall into singleton clusters because O1O2, I11I22, and so on, even when behaviour is identical. Timestamps and incidental identifier choices fragment further.

Post-processing is straightforward: take the exact clusters as a fine partition, extract each lead Order's execution, apply the canonical signature from §2, and merge exact clusters sharing a semantic signature. This retains exact clusters for drill-down while reporting business clusters. Exact equivalence is preferable when identity itself is the question—duplicate shipment, fraud, shared-object contamination, or legal evidence—and when data volume is small. `max_objs` bounds expansion of linked executions; with shared packages or invoices such as X5/X6 at scale, executions become large connected components, so truncation, exclusion or very slow hashing can occur, and clusters become unstable or uninformative. Large shared networks should therefore be segmented, sampled, or clustered semantically before exact expansion.

```python
import pm4py
from collections import defaultdict

lead_type = "Order"
exact = pm4py.cluster_equivalent_ocel(ocel, object_type=lead_type, max_objs=1000)
# Assumed format: dict exact_key -> [lead object ids]; adapt if version differs.

def extract_execution(ocel, lead_id, lead_type="Order", max_objs=1000):
    events_df = pm4py.ocel.ocel_events(ocel)  # adapt to installed OCEL version
    seen_objs, seen_events, frontier = {(lead_type, lead_id)}, [], [(lead_type, lead_id)]
    while frontier and len(seen_objs) + len(seen_events) <= max_objs:
        new_frontier = []
        for _, row in events_df.iterrows():  # outline: BFS over E2O links
            linked = [(t, o) for t, o in row.get("ocel:objects", [])]
            if any(x in seen_objs for x in linked) and row.name not in seen_events:
                seen_events.append(row); new_frontier += linked
        seen_objs |= set(new_frontier); frontier = new_frontier
    # convert seen_events to [{'activity':..., 'objects':{type:[ids]}}] and O2O triples
    return normalize_events(seen_events), normalize_o2o(ocel, seen_objs)

semantic = defaultdict(list)
for order_ids in exact.values():
    for oid in order_ids:
        ev, o2o = extract_execution(ocel, oid, lead_type)
        semantic[canonical_signature(ev, o2o)].append(oid)  # canonicalisation step
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** S6 loses its REPLACES/REMOVED evidence and moves toward S1, though Dispatch's extra Item link still separates it under $\sim_T$. S3 loses partial/complete settlement meaning but keeps two payments; S7 loses repack semantics but keeps return activities. Qualifier removal therefore mainly endangers substitution detection.

**Ignore external objects.** S4 and S5 both collapse to S1. This is the most damaging perturbation: shared logistics cost and shared finance risk disappear, and shared packages/invoices are silently treated as local. Any filtering of `EXT` objects must be reported as a change of question, not a neutral cleaning step.

**Collapse repeated same-label events.** If consecutive duplicates are merged with summed objects, X3's two Pack events become one two-item Pack and it collapses toward S1; X4's consecutive Record Payment events collapse to one, losing split settlement, while its non-consecutive Pack/Dispatch cycles survive. If all repetitions globally collapse, X8's second shipment also disappears. Repetition is therefore structural information, not noise.

**Treat Pack and Dispatch as a partial order.** Independent Pack events and independent package-delivery branches become order-invariant, which is desirable for concurrency. It does not merge X3 and X4: X3 requires both packs before the single dispatch, X4 requires each pack before its own dispatch. It would merge executions differing only by swapping independent branches. X1/X2 Add Item order is already invariant under renaming.

**Treat payment multiplicity as an amount attribute.** X4's two payments become one payment event with summed amount if amounts are recorded; S3 then differs from S2 only by two deliveries, and partial-settlement timing is lost if only the total is kept. If partial/complete flags or timestamps are retained as attributes, the distinction can be recovered analytically but no longer structurally.

## 8. Limitations and recommendation

The eight executions are handcrafted and small; real OCELs contain missing links, timestamp granularity problems, many-to-many sharing, and qualifier vocabularies that may not match the categories assumed here. Canonical colour refinement is reproducible for these finite executions but exact graph canonicalisation can be expensive on large shared components, and semantic categories embed analyst judgement—for example, treating delivery consolidation as business-semantic while treating item identity as not.

No single relation is best for all purposes because the purposes trade off sensitivity against generalisation. **Compliance monitoring:** use $\sim_T$ for clustering, retaining qualifiers, externality and per-event incidence, with exact identifiers kept for traceability; rules about substitution and sharing must not be abstracted away. **Operational segmentation:** use $\sim_S$, because teams need actionable groups such as split shipment, shared finance or return-repack. **Root-cause analysis:** start from $\sim_S$ segments but drill down to $\sim_T$, and $\sim_E$ within a segment, to isolate the single structural difference between otherwise similar executions. **Descriptive reporting:** use $\sim_A$ or aggregated $\sim_S$ counts, because readable activity-level summaries are stable and comparable; object multiplicities should be reported as KPIs rather than exploding the cluster count. Exact equivalence is thus a diagnostic instrument, semantic equivalence a management instrument, and activity equivalence a communication instrument; choosing one for all four would either hide risk or fragment insight.
