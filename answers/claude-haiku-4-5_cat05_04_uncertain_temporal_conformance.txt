# Incident-Response Timing Evaluation

## 1. Normalization Assumptions

### Clock-Offset Convention
For a source with `clock_offset  [a, b]` seconds:
- **Definition:** `clock_offset = recorded_clock  true_clock`
- **True-time computation:** `true_time = recorded_time  offset`, where `offset  [a, b]`
- **Direction:** A positive offset means the source clock *runs fast* (recorded time is ahead of true time). Subtracting it yields the earlier true time.

### Rounding and Timestamp Resolution

| System | Resolution | Interval construction |
|--------|-----------|----------------------|
| **HUB** | ±0.5 s exact | Recorded second ± 0.5 s |
| **OPS-BER** | Floor to minute | Displayed HH:MM means [HH:MM:00, HH:MM:59.999] |
| **SENSOR** | Round to ±10 s | Recorded value ± 10 s symmetric interval |
| **VENDOR-NY** | Floor to minute | Displayed HH:MM means [HH:MM:00, HH:MM:59.999] |
| **LEGACY-BER** | Floor to minute | Displayed HH:MM means [HH:MM:00, HH:MM:59.999]; DST fold adds second interpretation |
| **MOBILE-LON** | Round to ±1 min | Displayed HH:MM means ±30 s; user entry delay treated separately |

### Time-Zone Conversions (2026-06-01 is standard summer period; 2025-10-26 is DST transition)

- **Europe/Berlin (CEST = UTC+2):** Summer offsets apply on 2026-06-01; on 2025-10-26 03:00 CEST  02:00 CEST (fold).
- **America/New_York (EDT = UTC4):** 2026-06-01 uses EDT.
- **Europe/London (BST = UTC+1):** 2026-06-01 uses BST.
- **UTC:** No conversion needed.

### DST Fold (T-405: 2025-10-26)

At 2025-10-26 03:00 CEST, the clock reverts to 02:00 CET. Local times 02:00–02:59 occur twice:
- **First occurrence (02:00 CEST = 00:00 UTC):** before transition.
- **Second occurrence (02:00 CET = 01:00 UTC):** after transition.

Ingestion sequence constrains interpretation: if `Investigation_Start` is recorded after `Alert_Received` in the ingestion log, we rule out the combination where start is in the *first* fold and alert is in the *second* fold. However, we cannot eliminate ambiguity entirely without additional synchronization.

**Assumption:** For T-405, we retain both feasible UTC intervals (one for each fold occurrence) unless ingestion order fully constrains it. Since ingestion_sequence places Investigation_Start *after* Alert_Received and Containment_Complete *after* Investigation_Start, we exclude interpretations where a later event has an earlier local time requiring the opposite fold choice. This reduces but does not eliminate ambiguity.

### Inferred Investigation_Start (T-404)

- **Given:** `Investigation_Complete = 10:35:00 UTC`, `Alert_Received = 10:00:00 UTC`.
- **Given duration:** 18–25 minutes.
- **Inference:** `Investigation_Start = Investigation_Complete  duration  [10:35:00  25 min, 10:35:00  18 min] = [10:10:00, 10:17:00]`.
- **Treatment:** Retain as an interval; do not collapse to a point midpoint.

### Mobile User-Entry Delay (T-406)

- **Recorded:** 2026-06-01 13:14 (MOBILE-LON, rounded to ±1 min).
- **Source clock bound:** ±300 s.
- **User entry delay:** "up to five minutes late." This is semantic and distinct from clock error.
  - **Assumption:** Entry delay shifts the *recording time*, not our estimate of true occurrence. If user entered the timestamp up to 5 minutes after the event, the true event time is *before* the recorded time.
  - **Interpretation:** True occurrence  [recorded  5 min  300 s, recorded + 300 s].
  - **Rationale:** Late entry makes the recorded timestamp a strict upper bound on true time. Combined with clock uncertainty, true time is (recorded  5 min  300 s, recorded + 300 s], but the lower bound is more restrictive.

### Causal Constraints (T-407)

- **Alert_Sent**  **Alert_Received** by definition.
- **Evidence:** Network delivery latency  [0, 20] min; no receipt ack.
- **Assumption:** We cannot invert the causal direction (start cannot precede receipt). Assume receipt  [Alert_Sent, Alert_Sent + 20 min] and receipt  Investigation_Start (investigation cannot start before the alert arrives).
- **Feasible Alert_Received:** [2026-06-01 14:00:00, 2026-06-01 14:20:00] UTC.

### Summary of Materiality

**Material assumptions that affect classifications:**
- **Clock-offset direction** (subtractive correction) applies uniformly.
- **DST-fold ambiguity** in T-405 yields *two* feasible UTC intervals per event; ingestion order eliminates one per event but leaves residual uncertainty.
- **User-entry delay** in T-406 is treated as a tightening lower bound on true occurrence, not as clock error.
- **Inferred start in T-404** retains duration-interval uncertainty; no point midpoint substitution.
- **Causal network latency** in T-407 bounds alert receipt but does not pinpoint it.

- Rounding uncertainty: ±30 s  [12:13:30, 12:14:30] UTC.

Actually, more carefully:
- If the true event occurred at time $t_{\text{true}}$, the user recorded it at time $t_{\text{recorded}} \in [t_{\text{true}}, t_{\text{true}} + 300\text{s}]$ (clock) and up to 5 min later $t_{\text{recorded}} \in [t_{\text{true}}, t_{\text{true}} + 300\text{s}]$ (user delay is additional).

Let me reframe: the recorded timestamp is $t_{\text{rec}} = 12:14$ BST = 12:14 UTC. This is what was entered/logged. The *true occurrence time* $t$ satisfies:
1. Clock error: $|t_{\text{rec}} - t| \leq 300\text{s}$ (since source clock has offset [300, +300] s, true time = recorded  offset, so $t \in [t_{\text{rec}} - 300, t_{\text{rec}} + 300]$).
2. User entry delay: user may have entered the timestamp up to 5 min after the event, so $t \leq t_{\text{rec}}$ (and $t \geq t_{\text{rec}} - 300\text{s}$).

Combining: $t \in [t_{\text{rec}} - 300\text{s}, t_{\text{rec}}]$ = [12:13:30, 12:14:00] UTC under just entry delay, but rounding adds another ±30 s to the recorded time.

**With rounding:** recorded  [12:13:30, 12:14:30] UTC (round to nearest min ±30 s).
- If recorded = 12:13:30, then true $\in$ [12:13:00, 12:13:30] (entry delay) = [12:13:00, 12:13:30].
- If recorded = 12:14:30, then true $\in$ [12:14:00, 12:14:30] (entry delay).
- **Union:** [12:13:00, 12:14:30] UTC.

Adding clock offset [300, +300] s: true = recorded  offset, so if recorded  [12:13:30, 12:14:30] and offset  [300, +300], then true  [12:13:30  300, 12:14:30 + 300] = [12:08:30, 12:19:30].

But entry delay constrains further: true  recorded. Over the range [12:13:30, 12:14:30], the true time must be  recorded. Entry delay is subtractive; clock offset is also subtractive (we subtract a positive or negative offset).

**Conservative interval:** Assuming both sources of lower-bound uncertainty (entry delay + clock offset are independent):
- Entry delay alone: [recorded  5 min, recorded].
- Clock offset alone: [recorded  300, recorded + 300].
- Intersection: [recorded  300, recorded] (since entry delay is stricter for lower bound).
- Rounding: [12:13:30, 12:14:30].
- **Combined:** [12:13:30  300, 12:14:30] = [12:08:30, 12:14:30] UTC.

I'll use **[12:08:30, 12:14:30] UTC** for T-406 Investigation_Start, reflecting that entry delay tightens the lower bound relative to clock offset alone.

# System metadata: (resolution_seconds, clock_offset_min_s, clock_offset_max_s)
system_metadata = {
    'HUB': (0.5, -1, 1),
    'OPS-BER': (60, -90, 120),  # minute floor
    'SENSOR': (10, -5, 5),
    'VENDOR-NY': (60, -180, 180),  # minute floor
    'LEGACY-BER': (60, -60, 60),  # minute floor
    'MOBILE-LON': (60, -300, 300),  # round to minute
}

def parse_and_convert_to_utc(record):
    """
    Parse recorded time, apply time-zone conversion, then compute UTC interval bounds.
    """
    recorded_str = record['recorded_time']
    system = record['system']
    tz_name = record['tz']
    
    # Parse recorded time as naive datetime
    naive_dt = datetime.strptime(recorded_str, '%Y-%m-%d %H:%M:%S')
    
    # Localize to the specified time zone
    tz = pytz.timezone(tz_name)
    
    # Handle DST fold for LEGACY-BER on 2025-10-26
    if system == 'LEGACY-BER' and naive_dt.date() == datetime(2025, 10, 26).date():
        # Ambiguous hour: use 'fold' parameter if provided
        fold = record.get('dst_fold', 'first')  # 'first' or 'second'
        if fold == 'first':
            # Before transition (CEST = UTC+2)
            localized_dt = tz.localize(naive_dt, is_dst=True)
        else:
            # After transition (CET = UTC+1)
            localized_dt = tz.localize(naive_dt, is_dst=False)
    else:
        localized_dt = tz.localize(naive_dt)
    
    # Convert to UTC
    utc_dt = localized_dt.astimezone(pytz.UTC)
    
    # Apply resolution uncertainty (±)
    resolution_sec, offset_min_s, offset_max_s = system_metadata[system]
    
    # For minute floor, the recorded time is the floor: true time  [recorded, recorded + 60 s)
    if system in ['OPS-BER', 'VENDOR-NY', 'LEGACY-BER']:
        # Minute floor: uncertainty is [0, 60) seconds
        resolution_lower = timedelta(seconds=0)
        resolution_upper = timedelta(seconds=60)
    elif system == 'MOBILE-LON':
        # Round to nearest minute: ±30 seconds
        resolution_lower = timedelta(seconds=-30)
        resolution_upper = timedelta(seconds=30)
    elif system == 'SENSOR':
        # Round to nearest 10 s: ±10 seconds
        resolution_lower = timedelta(seconds=-10)
        resolution_upper = timedelta(seconds=10)
    elif system == 'HUB':
        # Exact to second ±0.5 s
        resolution_lower = timedelta(seconds=-0.5)
        resolution_upper = timedelta(seconds=0.5)
    else:
        resolution_lower = timedelta(seconds=0)
        resolution_upper = timedelta(seconds=0)
    
    # Apply clock offset (true_time = recorded_time - offset, so offset  [min, max])
    # When offset is positive, true time is earlier
    lower_bound = utc_dt + resolution_lower + timedelta(seconds=-offset_max_s)
    upper_bound = utc_dt + resolution_upper + timedelta(seconds=-offset_min_s)
    
    return lower_bound, upper_bound

def classify_duration_interval(duration_lower, duration_upper, profile_mean, profile_std, zeta=1):
    """
    Classify a feasible duration interval against a temporal-profile band.
    """
    band_lower = profile_mean - zeta * profile_std
    band_upper = profile_mean + zeta * profile_std
    
    # Clamp band to non-negative
    band_lower = max(0, band_lower)
    
    # Check for overlap
    if duration_upper < band_lower:
        return "CERTAIN_VIOLATION"  # entirely below
    elif duration_lower > band_upper:
        return "CERTAIN_VIOLATION"  # entirely above
    elif duration_lower >= band_lower and duration_upper <= band_upper:
        return "CERTAIN_PASS"  # entirely within
    else:
        return "POSSIBLE_VIOLATION"  # partial overlap
