## 1. Model scope and state variables

### Purpose and boundary

Build an **open, resource-constrained, non-stationary process simulation**, not just a historical replay engine. It should answer counterfactual questions such as:

- How would a pre-submission checker change missing-document loops, total applicant effort, and municipal workload?
- Does exempting low-risk Simple renovations from inspection reduce bottlenecks without transferring delays or risks to other cases?
- When does district batching improve total inspection time despite delaying the first case in a bundle?
- Are benefits of a temporary inspector robust to demand peaks, missing-data assumptions, and objection-driven delays?

The normal process boundary begins at application submission and ends at **issued permit, final rejection, or resolved appeal**. For alternative policies, include applicant effort before submission, such as a pre-submission checker, as an explicit extension of the case lifecycle.

Construction, enforcement, and post-permit inspections are outside the initial boundary. Their interfaces can be modeled later.

### Modeling level

Use activity-level simulation with:

- Explicit service durations, queueing, calendars, and resource contention.
- Parallel specialist reviews where the routing rules permit them.
- A decision-drafting synchronization point over all applicable prerequisites.
- Explicit loops and rework triggers rather than a single fixed case-duration distribution.
- Correlated case arrivals and cross-case inspection bundles.
- An open population: applications continue to arrive even when municipal queues grow.

The municipal clock should distinguish:

1. Active municipal service.
2. Waiting for municipal capacity.
3. Waiting outside municipal working hours.
4. Applicant or third-party response time.
5. Legally imposed waiting, such as public notice.
6. Waiting for another case or a bundle.

### Entities and state

| Entity | Important state |
|---|---|
| `Case` | Case ID, type, district, architect, application value, submission time, required activities, current status, completed activities, review outcomes, rework counts, appeal status, terminal outcome, and policy-eligibility evidence |
| `Applicant` | Response deadlines, document requests, document submission times, abandonment or retry status, and pre-submission effort |
| `CaseRelationship` | Related-case IDs, architect, district, geographic cluster, relationship strength, and whether bundling is permitted |
| `WorkItem` | Activity, priority, release time, actual start, completion, processing time, queue-wait time, and waiting reason |
| `ResourcePool` | Role, qualifications, capacity, utilization, reserved capacity, and assigned cases |
| `Resource` | Working intervals, leave, non-permit commitments, council closures, temporary appointments, and resource-specific skills |
| `Calendar` | Working-day rules, start/end times, holidays, interruptions, and effective date |
| `Bundle` | Inspection cases, geographic area, opening time, expected travel, and cases that arrive after bundle formation |
| `PublicNotice` | Start time, statutory minimum, objection proxy status, extensions, and source/quality of the objection information |
| `ExperimentPolicy` | Enabled interventions, eligibility rules, policy effective date, model version, and random-number stream identifiers |

A case should not have a single `status = "waiting"` field. For example, an inspection-scheduling case waiting for a geographic batch is different from an applicant waiting five days to submit documents.

### Resources, queues, and routing

Represent resources as **capacity pools with qualifications and schedules**, rather than assuming that every event labeled with one `org` value is a distinct server. The event log’s organizational labels do not establish:

- Whether people interchange roles.
- Whether a specialist can process several case types.
- Whether recorded resources correspond to full-time equivalents.
- How much capacity is reserved for non-permit work.

Minimum separate pools include:

- Completeness clerks, including Monday portal support.
- Planners, including the two dedicated to Simple renovation.
- Fire reviewers.
- Environmental reviewers, with their 60% available capacity.
- Inspection schedulers and field inspectors.
- Legal officers, with council-meeting closures.
- System tasks, which should not create artificial municipal queues.

Separate queues are needed for completeness, each specialist review, inspection scheduling, decision drafting, legal review, and rework. Applicant response is an **external hold**, not a municipal service queue.

The `required_reviews` set should be determined per case. Decision drafting waits for all tasks in that set, including inspection only when inspection remains required. Public-notice duration is a waiting/legally imposed activity, not evidence that a municipal employee worked for fourteen days.

### Cross-case dependencies

Model at least three dependencies:

1. **Correlated arrivals:** Multiple applications from the same architect, especially in the same week.
2. **Geographic inspection bundles:** Several sites in one district or travel area can share a scheduling session or inspector trip.
3. **Explicit related-case links:** If reliable relationships become available, coordinate notices or reviews only where policy actually permits it.

A shared architect should not automatically create a process dependency. For example, the second application should not wait merely because an architect has another case under review. Geographic batching, by contrast, deliberately creates a waiting-versus-travel tradeoff.

## 2. Parameter-estimation plan

### General estimation approach

Estimate parameters at the level needed by the simulation mechanism. Aggregate case-duration distributions alone will not reproduce resource queues, calendar effects, or review dependencies.

Use the full 18-month event log for estimation, retaining:

- Actual case-type, district, architect, and application-value distributions.
- Observation-window boundaries.
- Multiple occurrences of the same activity within a case.
- Incomplete cases and their last observed events.
- Data-quality flags for missing starts, missing attributes, and inferred route information.

Maintain separate uncertainty for:

- Measurement uncertainty.
- Sampling uncertainty.
- Future demand uncertainty.
- Structural uncertainty, such as whether an unlogged objection mechanism explains long public-notice periods.

### Parameter-specific plan

| Quantity | Estimation plan | Important qualifications |
|---|---|---|
| Arrival intensity | Fit time-of-day/day-of-week and monthly intensities over the complete observation window. Start with a non-homogeneous Poisson or marked point-process model; add a Hawkes or equivalent short-lived clustering component if architect bursts remain after calendar effects. | The 1.7 seasonal and 2.2 Monday-to-Wednesday ratios are summary evidence, not automatically independent multiplicative factors. Estimate their joint effect from the full log. |
| Case composition | Estimate case type jointly with district and architect; model the top-20 architect contribution explicitly. | The 31% contribution is not equivalent to 20 equally sized architect strata. Preserve correlated same-week submissions. |
| Service times | Where start and completion are observed, fit service time conditional on resource role, case type, district, workload period, and rework status. Use positive-duration distributions such as lognormal, Gamma, Weibull, or empirical residual distributions. | A completion-to-completion gap is not a service time. A plausible service distribution is not evidence that the observed interval is pure service. |
| Waiting times | Prefer queue-wait estimates from observed starts or an interval-censored queue model. Treat aggregate waiting as a validation target, not an independently assigned delay preceding each activity. | Queue emergence should arise from arrivals, service, and capacity. Fitting waiting times and then independently sampling additional waiting would double-count congestion. |
| Applicant response | Fit a separate response-time distribution from request events to receipt events, conditional on request count, case type, applicant/architect, and policy history where available. | Zero-minute `Receive missing documents` is a milestone duration, not applicant service effort. Account for unresolved requests as right-censored observations. |
| Route probabilities | Estimate case-level probabilities of missing documents, review requirements, rework, and terminal outcomes. Use event sequences and case attributes together. | Absence of an activity is not automatically its routing probability. Administrative deletions, exception handling, and incomplete traces can bias absence-based estimates. |
| Rework | Manually code a stratified sample of rework text, using two reviewers where feasible. Separate rework reason, triggering activity, returned-to activity, and subsequent repeated review requirements. | The simplified process tree does not contain the intended planning, legal, or appeal loops. Rework rates must not be inferred from that tree. |
| Resource calendars | Reconcile observed start/end intervals with HR schedules, leave, reserved duties, and known closures. Calibrate effective capacity against workload and throughput. | Completion-only events and reconstructed calendars cannot uniquely identify service and idle time. |
| Cross-case dependence | Estimate same-architect same-week clustering and, if relationships are identified, geographic bundling behavior. | The flattened log may underrepresent dependency networks. Report assumed dependence separately from directly observed relationships. |
| Public notice | Use the presence and duration of extended notice as a proxy for possible objections. If supplementary objection records are obtained, fit an explicit latent objection mechanism. | Do not interpret unobserved objection events as zero objections. |
| Future demand | Use the 18-month history to establish a baseline forecast, supplemented by planning scenarios for economic, seasonal, and policy-induced changes. | Eighteen months is limited evidence for annual seasonality. Uncertainty about repeating the pattern should be explicit. |

### Handling missing starts and administrative bias

Where starts are missing, use one of three treatments:

1. Recover starts from detailed audit records or applicant/HR records.
2. Fit an interval-censored model in which each activity’s service interval falls within the surrounding observed gap and plausible calendar constraints.
3. Use multiple imputation, retaining the distribution of imputed starts.

Do not simply subtract the preceding completion from the current completion and label the result service. Doing so incorrectly turns congestion, overnight time, and external response into worker productivity.

Also distinguish:

- **Right censoring:** a case has not yet reached the activity or outcome.
- **Administrative truncation:** cases were removed from the exported log.
- **Competing termination:** issue, reject, withdrawal, or appeal resolution.

### PM4Py use

Use PM4Py for descriptive process mining and model handling:

- Load tabular data with `pandas.read_csv`.
- Convert the DataFrame with `pm4py.format_dataframe`.
- Discover variants with `pm4py.discover_variants`.
- Discover direct-follows graphs with `pm4py.discover_dfg`.
- Discover performance direct-follows graphs with `pm4py.discover_perf_dfg`.
- Retain case and event attributes for separate statistical analysis.
- Import the actual BPMN process, if available, and reconcile it with the observed variants rather than silently repairing discrepancies.
- Use model conformance checks to identify where the intended process and the observed process differ.

The supplied process-tree string can be parsed, but it is **not a faithful executable specification** of the intended process:

- Its completeness structure does not represent the observed return from `Receive missing documents` to another `Completeness check`.
- `tau` has no estimated probability.
- Optional Fire, Environmental, Public-notice, and Legal activities are not tied to case-level routing rules.
- The tree does not implement the required review join.
- `Inspection rework` is sequential, not a loop back to inspection.
- Planning rework, legal rework, and appeal loops are absent.
- The small excerpt has repeated completeness checking but no `Completeness rework` event.

Use the tree as a documented starting abstraction, not as ground truth. The simulation engine should use explicit routing, synchronization, and loop semantics.

## 3. Assumptions

All numeric values not supplied by the municipality are **initialization or sensitivity assumptions**, not estimated facts.

### Arrivals

- The 18-month arrival process supplies the baseline workload.
- Case mix initially uses 45% Simple renovation, 28% New residential, 17% Commercial, and 10% Complex variance, with uncertainty checked against the full data.
- Arrivals are marked point processes: case type, district, and architect are not sampled independently of time.
- Same-week architect bursts are explicitly represented.
- Portal submissions are not artificially restricted to municipal office hours. A submission arriving outside working hours waits until service can begin.
- Under policy comparisons, demand is held common unless the experiment explicitly studies adoption or population changes.

### Service times

- Summary medians and p90s initialize duration models; they do not uniquely identify a distribution.
- Human service time is modeled separately from waiting and outside-hours time.
- `Public-notice period` is not treated as municipal service.
- `Receive missing documents` is not treated as a zero-duration applicant service distribution.
- Heavy tails and case-mix differences are preserved rather than represented by one average duration per case.

### Routing

- Planning review is always required unless the municipality supplies a contrary rule.
- Fire, Environmental, Public-notice, and Legal requirements come from case-level rules, not case type alone.
- Missing building-area and environmental-sensitivity data are represented as unknown or sampled latent attributes, not as “not required.”
- Decision drafting waits for every applicable prerequisite.
- Approval and rejection are mutually exclusive terminal routes, with appeal modeled as a subsequent state transition.
- A no-inspection exemption requires affirmative evidence that there were no prior violations; missing violation history does not qualify a case.

### Resources and calendars

- HR calendars are treated as plausible operational constraints, not independently validated truth.
- Fire review occurs only Tuesday–Thursday.
- Environmental reviewers have approximately 60% of nominal capacity available for permits.
- Legal work stops during council meeting weeks except for explicitly modeled urgent cases.
- Holidays, leave, reserved capacity, and meetings produce legitimate waiting.
- Resource qualification and case eligibility matter; pool assignment is not arbitrary.
- D4’s temporary inspector is active during the observed peak periods—March–May and September–November—unless the municipality specifies a different definition.

### Rework

- Rework occurs only after a failed or materially changed check.
- Planning rework can trigger re-review depending on what changed.
- Inspection rework requires correction/rescheduling and another applicable inspection.
- Legal rework returns the appropriate draft or decision package.
- Appeal can reopen a previously terminal case.
- Missing rework reasons and unstructured text require coding and uncertainty treatment.

### Applicant and third-party response

- Applicant response is external to municipal staffing and has a separate heavy-tailed duration distribution.
- Requesting and receiving documents have distinct timestamps.
- Applicant pre-submission effort under D1 is added to the lifecycle and reported separately from municipal service.
- Document resubmission, withdrawal, and repeated requests are possible.
- Applicant inactivity is not interpreted as municipal queueing.

### Cross-case dependencies

- Same-architect submissions are correlated in time, but not automatically dependent in routing.
- Inspection bundling may reduce travel while delaying the first waiting case.
- Newly arriving cases may miss a bundle already formed.
- Public-notice dependencies are introduced only when a related-case mechanism is explicitly specified.
- The model should not assume that a shared inspection inspector creates unmodeled review dependencies.

### Non-stationary demand

- The two observed peak periods and Monday effect are retained.
- Forecast demand may be scaled or shifted in stress tests.
- Repeated annual seasonality is a planning assumption because 18 months is limited for estimating annual cycles.
- Resource decisions use time-varying demand, not an average daily workload.
- Interventions that alter application behavior are evaluated separately from capacity interventions under otherwise identical demand.

### Missing data

- Missing service starts do not become observed service times.
- Missing objection events do not imply no objections.
- Missing rare emergency cases remain a scope-coverage risk.
- Uncertain routing attributes and eligibility are sampled or bounded in sensitivity analysis.
- Results that depend strongly on these assumptions are labeled provisional.

## 4. Experiment matrix

### Experimental factors and levels

| Factor | Levels |
|---|---|
| Policy configuration | Baseline; each of D1–D10; selected combinations |
| Demand path | Empirical forecast; higher/lower forecast realization; shifted seasonal peak |
| Case mix | Empirical mix; New-residential/Commercial-heavy mix; Complex-variance-heavy mix |
| Arrival clustering | Fitted architect clustering; stronger/weaker clustering |
| Missing-document behavior | Estimated response distribution; longer response distribution; pre-check eligibility/compliance scenarios |
| Review requirements | Observed routing; plausible ranges for unobserved area, environmental sensitivity, and Legal requirements |
| Low-risk eligibility | No exemption; exemption for qualifying cases only; additional audit/screening conditions |
| District batching | Disabled; enabled with plausible bundle-size and formation rules |
| Temporary inspection capacity | Zero; one additional peak-month FTE; higher-capacity sensitivity |
| Legal pre-check | Disabled; enabled for eligible Commercial and Complex variance cases |
| Applicant scheduling | Unrestricted portal; limited appointment availability; broader appointment availability |
| Calendar disruption | Normal calendars; holidays/council closure; temporary staffing outage |
| Objection mechanism | Fitted latent mechanism; higher incidence/duration, with feasible probability bounds |

Maintain a common demand stream across policies for a given replication. A process intervention should not improve measured performance merely because it attracts easier cases.

### Main policy experiments

| Experiment | Intervention and factor settings | Expected trade-offs and questions |
|---|---|---|
| B0 | Baseline; all intervention flags off | Reference for duration, SLA, queues, effort, and utilization |
| D1 | Pre-submission checker on/off | Fewer municipal completeness loops versus applicant effort and possible increased complete submission volume |
| D2 | Simple renovation inspection exemption: value **< EUR 50,000**, no prior violations, and all other conditions met | Less inspection demand versus incomplete violation-history risk and possible shift toward drafting/legal queues |
| D3 | District batching off/on | Lower travel and inspector idle time versus bundle formation delay and unequal district effects |
| D4 | One temporary inspector only during observed peak months | Higher peak inspection capacity versus limited benefit if scheduling, readiness, or other reviews dominate |
| D5 | Legal pre-check off/on for eligible Commercial and Complex variance cases | Earlier detection of legal defects versus duplicated legal effort if a final legal check remains necessary |
| D6 | Zero or one daily planner reserve for cases aging beyond a predeclared threshold | Shorter aging tail versus reduced flexible capacity for new complex work |
| D7 | Unrestricted submissions versus limited and broad architect-facing appointment availability | smoother arrivals versus reduced access, rescheduling effort, and possible displacement to other submission days |
| D8 | No triage versus district/attribute-based environmental triage | Shorter routine reviews versus misclassification or inequitable treatment where attributes are incomplete |
| D9 | No early warning versus conservative objection early-warning process | Potentially faster resolution versus extra notice work and false positives |
| D10 | D1 + D2 + D3 + D4 | Tests complementarity: fewer applications needing correction, fewer inspections, better batching, and added peak capacity |
| C1 | D1 + D7 | Tests whether reducing document problems complements smoother submission demand |
| C2 | D5 + D6 | Tests whether upstream legal detection complements planner capacity reserved for aging cases |
| C3 | D1 + D2 + D3 + D7 | Tests demand smoothing plus inspection-demand reduction; likely leaves fewer cases for D4 to assist |
| C4 | D5 + D6 + D8 | Tests a planning-and-review bottleneck package; requires careful guardrails against premature decisions |

For D5, “pre-check” should start only after sufficient review inputs exist. A final legal decision should remain necessary; otherwise the intervention could improve duration by omitting legally required work.

A one-factor-at-a-time screen is useful for D1–D10, but follow it with selected interaction experiments such as:

- D1 × D2: pre-check quality and inspection eligibility.
- D3 × D4: batching versus added inspector capacity.
- D5 × D6: upstream legal resolution versus aging-case prioritization.
- D1 × D7: document preparation and submission timing.

### Stress scenarios

Run at least the shortlisted interventions and D10 under these scenarios.

| Stress | Factor levels | Purpose |
|---|---|---|
| S1: Demand surge | Peak arrival rate at least 1.7 times the reference period; additional overall multiplier up to 1.5; higher New residential/Commercial share | Test whether gains disappear when queues become capacity-saturated |
| S2: Objection and notice shock | Fitted underlying objection mechanism versus approximately doubled feasible objection incidence and longer notice durations | Test tail risk without pretending objection events were observed |
| S3: Calendar and staffing disruption | Normal calendars plus extended public holidays, council meeting weeks, and a temporary planner or inspector outage | Test robustness to disruptions beyond the reconstructed average calendar |
| S4: Correlated-arrival and bundling stress | Stronger architect bursts, more same-week district arrivals, and larger geographic bundles | Test fairness and the waiting-versus-travel tradeoff |
| S5: Data/eligibility stress | Plausible ranges for missing violation history, review requirements, and service/wait imputation | Test whether a policy works only under optimistic assumptions |
| S6: Forecast error | Demand shifted by a month, unusual weekday composition, or higher amplitude peaks | Test sensitivity to extrapolation from only 18 months |

For S2, a stress assumption is not a fitted estimate. If the estimated objection probability is \(p\), doubling it means using \(\min(2p,1)\), while durations and false-negative/positive rates are varied separately.

## 5. Warm-up, replications, and uncertainty treatment

### Warm-up and run length

Use a target planning year, for example 365 days, with a common calendar and policy effective date across experiments.

A practical warm-up procedure is:

1. Reconstruct the most recent observed workload and backlog as an initial snapshot, marking uncertain resource occupancy explicitly.
2. Run an additional warm-up period covering at least one seasonal peak and one lower-demand period.
3. Check that backlog, utilization, and age distributions do not change materially over successive warm-up windows.
4. Use a six-month post-warm-up measurement period as an initial design, with twelve months as a sensitivity check.
5. If historical state cannot be reconstructed, report startup-from-empty results separately; do not treat them as equivalent to a populated municipality.

Continue arrivals for the full target year and then drain the remaining population. Report both:

- Fixed-arrival-cohort outcomes for applications arriving during the target year.
- Calendar-period throughput and backlog for the target year.

If draining takes longer than a practical reporting limit, report unresolved backlog rather than silently excluding difficult cases or treating them as completed.

### Replications and random numbers

An initial design is:

- **200 independent replications** per screening experiment.
- **At least 500 replications** for finalists and stress tests.
- Increase the count until the Monte Carlo standard error is acceptable—for example, below 2% of the baseline mean metric and below 0.5 percentage points for an SLA proportion.

Use and publish deterministic seed lists or reproducible seed-generating rules, such as `numpy.random.SeedSequence`.

For policy comparisons, use common random numbers where possible:

- One arrival/process stream.
- One stable case-attribute stream.
- One workflow-distribution stream.

Counterbased random-number allocation by case and decision is preferable to consuming a single stream in different orders under different policies. Common random numbers reduce noise but do not eliminate sensitivity to policy-induced state changes.

### Confidence and credible intervals

Report:

- 95% confidence intervals for simulation performance metrics.
- Paired differences versus baseline using the same replication seeds.
- Simultaneous confidence bands or paired bootstrap adjustment when comparing many interventions.
- Posterior credible intervals only if a Bayesian estimation model is actually used; do not relabel ordinary simulation intervals as Bayesian credibility.

For duration metrics, stratify intervals by case type. For example, a policy that improves Simple renovation duration but substantially worsens Complex variance outcomes should not be summarized only by an overall favorable mean.

### Parameter and structural uncertainty

Propagate uncertainty in:

- Arrival intensity and seasonal amplitude.
- Case mix and architect clustering.
- Service and applicant-response distributions.
- Eligibility and review requirements.
- Rework and rejection behavior.
- Resource availability.
- Cross-case bundling and public-notice extensions.

Use a combination of:

- Day-level or architect/district block resampling.
- Parameter draws from the fitted statistical model.
- Alternative plausible structural assumptions.
- One-at-a-time sensitivity analysis for important quantities.
- Morris or Sobol screening for global sensitivity.

### Heavy tails

Do not force lognormal service times solely because they are convenient. Compare empirical and fitted tails, inspect p95/p99 where support permits, and consider mixtures or generalized Pareto tails.

Use applicant-response survival models for unresolved requests. Retain right-censored cases rather than dropping them. Public-notice and total cycle-time distributions should not be truncated at an arbitrary “completed cases only” cutoff.

## 6. Validation strategy

### Face validation

Hold structured walkthroughs with clerks, planners, inspectors, legal officers, applicant representatives, and policy owners.

Validate:

- The meaning of each activity and token.
- Routing and decision-drafting prerequisites.
- Whether a rework loop reopens other reviews.
- Public-notice and appeal rules.
- Resource eligibility and reserved capacity.
- Whether an application is considered submitted before or after a pre-submission check.
- The intended treatment of applicant holds and SLA clocks.

Record every rule change in a model decision log.

### Event-log replay validation

Inject historical arrivals, known attributes, and historical routing where available. Compare:

- Observed and generated case activity orders.
- Repeated checks and rework.
- Terminal outcomes and incomplete cases.
- Review completion order and drafting synchronization.
- Impossible or overly long negative/calendar-inconsistent intervals.

Start with observed history, but do not invent historical intervention effects. Replay agreement validates transition and sequencing behavior, not automatically the service/wait decomposition or counterfactual policy effects.

### Distributional validation

Compare model and historical results for:

- Interarrival intensity by day and month.
- Case type, district, and architect composition.
- Case duration by type and observed variant.
- Activity start/end intervals where observed.
- Applicant response distributions.
- Rework and outcome rates.
- Kaplan–Meier survival curves and quantile confidence intervals.

Use chronological train/test splits or rolling-origin validation. Do not use only a random event split, because that leaks future process regimes into training.

### Resource-utilization validation

Compare:

- Municipal work minutes divided by available work minutes.
- Daily and weekly utilization by role.
- Queue lengths and waiting times.
- Fire-review activity against Tuesday–Thursday availability.
- Environmental capacity against its reserved-duty allowance.
- Legal activity against council closures.
- Inspector utilization and geographic travel patterns.

Because starts are missing, utilization is a secondary validation target with acknowledged uncertainty.

### Bottleneck validation

Check whether the model reproduces relevant observed pressure points:

- Completeness queue spikes after Monday submissions.
- Planning queue differences by district and case type.
- Environmental variability and long waits.
- Legal/council effects.
- Inspection scheduling and district travel differences.
- Decision-drafting waits for incomplete review sets.

Also challenge these beliefs: a bottleneck identified from average durations may actually be driven by applicant response, missing documents, notice extensions, or decision synchronization.

### Out-of-sample and ongoing validation

- Reserve later months for out-of-sample testing.
- Track forecast error and queue growth after deployment.
- Compare predicted and observed distributions after each policy change.
- Validate eligibility and routing attributes with an audit sample.
- Obtain prospective evidence—ideally randomized, stepped-wedge, or phased implementation—for interventions whose effects cannot be inferred from the historical log.
- Recalibrate on a scheduled basis and after material policy, staffing, or calendar changes.

Validation should produce calibrated uncertainty bands, not a claim of a single exact historical reconstruction.

## 7. Decision criteria

The thresholds below are **illustrative governance targets to ratify**, not observed statutory SLAs or discovered optimal cutoffs.

### Core metrics

| Dimension | Metric and reporting requirement |
|---|---|
| Central performance | Median elapsed cycle time, from submission to terminal outcome, by case type; report separately for applicants requesting missing documents |
| Tail performance | p90, p95, and p99 cycle time by case type and district; applicant-held time should also be reported separately |
| Throughput | Permits, rejections, and other terminal outcomes per 30 days under the offered case mix |
| SLA compliance | Percentage completed within case-type-specific elapsed-time limits |
| Backlog | Open cases, overdue cases, and age-weighted workload at the end of the year; growth rate and recovery time after a peak |
| Rework | Initial-check failure rate, proportion entering each loop, loops per case, and additional municipal/applicant effort |
| Applicant impact | Pre-submission effort, document-response time, repeated submissions, abandonment, and total elapsed time |
| Quality/safety | Approval/rejection consistency, rework, legal reversals, and error indicators for exempted or triaged cases |
| Cost | Municipal labor, temporary staffing, applicant effort, and administrative burden, valued using municipal assumptions |

An illustrative initial SLA table is:

| Case type | Illustrative elapsed-time target |
|---|---:|
| Simple renovation | 80% within 30 days |
| New residential | 90% within 60 days |
| Commercial | 95% within 90 days |
| Complex variance | 90% within 150 days |

Review these against the municipality’s actual obligations before use. Missing-document cases can also have a separate applicant-response target.

### Resource and operational guardrails

- Mean busy-period utilization should generally remain below approximately 90%, leaving flexibility for demand variability.
- Sustained p95 utilization near or above 95% is a capacity warning, even if average utilization looks acceptable.
- Monitor queue age, not just queue length.
- Do not accept a policy that creates substantial new bottleneck load without a corresponding capacity or routing adjustment.
- Do not use D2, D8, or D9 if the required audit and routing data cannot support their eligibility and quality controls.

### Fairness

Report unadjusted and case-mix-adjusted results for:

- Districts, including longer-travel D3 and D5.
- Small architects versus the top-20 architect group.
- Simple renovation, New residential, Commercial, and Complex variance.
- Qualified and unqualified applicants under D2.
- Missing-attribute populations under D8 and D9.

A practical review threshold is a p90 duration disparity ratio of at most 1.5 for comparable case mixes, subject to statistical uncertainty. Geographic disparity is not automatically evidence of discrimination, but it should trigger investigation rather than be hidden by an overall average.

### Robustness and selection

Adopt an intervention only if:

1. It produces a practically meaningful improvement against baseline, with uncertainty reported.
2. It does not violate quality, safety, fairness, or capacity guardrails.
3. Its benefits persist across plausible demand, calendar, objection, and missing-data scenarios.
4. Applicant effort and municipal cost are acceptable.
5. The result is not driven primarily by one favorable random seed or subgroup.

For example, require the probability of satisfying all critical constraints to remain above a governance threshold such as 0.80 across the specified stress set. This is a decision robustness criterion, not a 80% probability that the real-world policy is correct.

Use constrained multi-objective or Pareto analysis. A policy with the highest average throughput is not automatically preferable if it increases Complex variance delays, shifts risk to small applicants, or requires an unbounded backlog.

def add_time_columns(frame: pd.DataFrame) -> pd.DataFrame:
    """
    Completion-only logs yield net interevent gaps, not identified service
    and waiting times. If start:timestamp exists, use it where available.
    """
    out = frame.copy()
    out[TIMESTAMP] = pd.to_datetime(
        out[TIMESTAMP], format=TIME_FORMAT, errors="raise"
    )
    out = out.sort_values([CASE, TIMESTAMP], kind="stable").reset_index(drop=True)

    by_case = out.groupby(CASE, sort=False)
    out["interevent_gap_days"] = (
        by_case[TIMESTAMP].diff().dt.total_seconds() / DAY_SECONDS
    )

    if "start:timestamp" in out.columns:
        out["start:timestamp"] = pd.to_datetime(
            out["start:timestamp"], format=TIME_FORMAT, errors="coerce"
        )
        by_case = out.groupby(CASE, sort=False)
        previous_completion = by_case[TIMESTAMP].shift()

        out["service_time_days"] = (
            (out[TIMESTAMP] - out["start:timestamp"])
            .dt.total_seconds() / DAY_SECONDS
        )
        out["waiting_time_days"] = (
            (out["start:timestamp"] - previous_completion)
            .dt.total_seconds() / DAY_SECONDS
        )
        out["time_quality"] = np.where(
            out["start:timestamp"].notna(),
            "observed_start_and_completion",
            "missing_start",
        )
    else:
        out["service_time_days"] = np.nan
        out["waiting_time_days"] = out["interevent_gap_days"]
        out["time_quality"] = "net_gap_only_not_service_wait_split"

    # Do not use these columns indiscriminately for applicant milestones,
    # system tasks, or public-notice waiting without role-specific checks.
    return out

def analyze_with_pm4py(frame: pd.DataFrame) -> dict:
    # This sorting also makes direct-follows calculations deterministic.
    frame = add_time_columns(frame)

    formatted = pm4py.format_dataframe(
        frame,
        case_id=CASE,
        activity_key=ACTIVITY,
        timestamp_key=TIMESTAMP,
        timestamp_format=TIME_FORMAT,
    )
    event_log = formatted.to_event_log()

    variants = pm4py.discover_variants(event_log)
    dfg = pm4py.discover_dfg(event_log)
    performance_dfg = pm4py.discover_perf_dfg(event_log)
    traces = pm4py.discover_traces(event_log)

    arrivals = (
        frame.groupby(CASE, sort=True)[TIMESTAMP].min().sort_values()
    )
    span_days = (
        (arrivals.max() - arrivals.min()).total_seconds() / DAY_SECONDS
    )
    mean_gap = arrivals.diff().dt.total_seconds().dropna().mean()
    arrival_statistics = {
        "cases": len(arrivals),
        "observed_first_arrival": arrivals.min(),
        "observed_last_arrival": arrivals.max(),
        "observed_span_days": span_days,
        # Descriptive estimate only; use the known administrative observation
        # window and boundary model for the production rate estimate.
        "mean_case_interarrival_days": mean_gap / DAY_SECONDS,
    }

    return {
        "event_log": event_log,
        "variants": variants,
        "dfg": dfg,
        "performance_dfg": performance_dfg,
        "traces": traces,
        "arrival_statistics": arrival_statistics,
        "time_columns": frame,
    }

@dataclass(frozen=True)
class Policy:
    enabled: frozenset[str] = frozenset()

    def __post_init__(self):
        valid = {f"D{i}" for i in range(1, 11)}
        unknown = self.enabled - valid
        if unknown:
            raise ValueError(f"Unknown policies: {sorted(unknown)}")


def required_stages(case: CaseState, policy: Policy) -> set[str]:
    required = {
        "Completeness check",
        "Planning review",
        "Inspection scheduling",
        "Site inspection",
        "Decision drafting",
    }

    # None must not silently become False. The case factory should supply
    # an observed value or a sampled latent value from sensitivity analysis.
    optional_rules = [
        (case.requires_fire, "Fire-safety review"),
        (case.requires_environment, "Environmental review"),
        (case.requires_public_notice, "Public-notice period"),
        (case.requires_legal, "Legal check"),
    ]
    for observed_or_sampled, activity in optional_rules:
        if observed_or_sampled is None:
            raise ValueError(
                f"{case.case_id}: unresolved routing for {activity}"
            )
        if observed_or_sampled:
            required.add(activity)

    qualifies_for_d2 = (
        case.case_type == "Simple renovation"
        and case.application_value < 50_000  # strictly less than EUR 50,000
    )
    if qualifies_for_d2 and "D2" in policy.enabled:
        if case.prior_violations is None:
            raise ValueError("D2 requires affirmative prior-violation evidence")
        if case.prior_violations is False:
            required.discard("Site inspection")
            required.discard("Inspection scheduling")

    return required


@dataclass(frozen=True)
class ServiceLaw:
    """Illustrative lognormal initialization, not a calibrated fit."""
    median: float
    p90: float

    def sample_minutes(self, rng: np.random.Generator) -> float:
        if not (0 < self.median < self.p90):
            raise ValueError("Require 0 < median < p90")
        z90 = 1.2815515655446004
        sigma = (np.log(self.p90) - np.log(self.median)) / z90
        mu = np.log(self.median)
        return float(rng.lognormal(mu, sigma))


# Calendar times below are seconds since the experiment's local epoch.
# weekly[Monday] = [(8.0, 16.0)] means 08:00-16:00.
class WeeklyCalendar:
    def __init__(self, weekly: dict[int, list[tuple[float, float]]],
                 closures: list[tuple[float, float]] | None = None):
        self.weekly = weekly
        self.closures = closures or []

    def is_working(self, now: float) -> bool:
        dt = datetime.fromtimestamp(now)
        minute_of_day = (
            dt.hour * 60 + dt.minute + dt.second / 60 + dt.microsecond / 6e7
        )
        tod = minute_of_day / 60
        return (
            any(start <= tod < end
                for start, end in self.weekly.get(dt.weekday(), []))
            and not any(start <= now < end for start, end in self.closures)
        )

    def next_boundary(self, now: float) -> float:
        # Readable adapter assuming day-local shifts. A production calendar
        # should use an efficient event calendar, fractional availability,
        # timezone/DST rules, and explicit meeting/holiday intervals.
        dt = datetime.fromtimestamp(now)
        midnight = dt.replace(hour=0, minute=0, second=0, microsecond=0)

        for offset in range(8):
            weekday = (dt + timedelta(days=offset)).weekday()
            day_start = midnight + timedelta(days=offset)
            for start_hour, end_hour in sorted(
                self.weekly.get(weekday, [])
            ):
                opening = (day_start + timedelta(hours=start_hour)).timestamp()
                closing = (day_start + timedelta(hours=end_hour)).timestamp()
                if now < opening:
                    return opening
                if opening <= now < closing:
                    return closing

        raise RuntimeError("Calendar has no future working interval")


class CalendarResource:
    """Minimal SimPy adapter; production pools need skills and commitments."""

    def __init__(self, env: simpy.Environment, capacity: int,
                 calendar: WeeklyCalendar, name: str):
        self.pool = simpy.PriorityResource(env, capacity=capacity)
        self.calendar = calendar
        self.name = name

    def run(self, env: simpy.Environment, case: CaseState,
            activity: str, service_minutes: float):
        remaining = max(0.0, float(service_minutes))

        while remaining > 1e-9:
            if not self.calendar.is_working(env.now):
                case.phase = "calendar_wait"
                yield env.timeout(
                    max(1.0, self.calendar.next_boundary(env.now) - env.now)
                )
                continue

            # Older cases have higher priority under SimPy's ordering.
            # D6 and other policies may require a special reserved pool
            # rather than simply a global aging priority.
            with self.pool.request(priority=case.submitted) as ticket:
                yield ticket

                # State may have changed while waiting for capacity.
                if not self.calendar.is_working(env.now):
                    continue

                interval = self.calendar.next_boundary(env.now) - env.now
                if interval <= 0:
                    continue

                used_minutes = min(remaining, interval / 60.0)
                started = env.now
                case.phase = "in_service"
                yield env.timeout(used_minutes * 60.0)

                case.work_log.append((activity, started, env.now))
                remaining -= used_minutes

        case.phase = "resource_wait_or_dependency"

@dataclass(frozen=True)
class DemandConfig:
    mean_daily_arrivals: float
    peak_multiplier: float
    dow_multipliers: dict[int, float]  # estimated for all seven weekdays
    peak_months: frozenset[int] = frozenset({3, 4, 5, 9, 10, 11})
    hawkes_alpha: float = 0.0          # extra arrivals per day near prior event
    hawkes_beta: float = 1.0           # inverse-day decay rate


class HawkesArrivalSource:
    def __init__(self, config: DemandConfig, seed: int):
        self.config = config
        self.rng = np.random.default_rng(np.random.SeedSequence([seed, 1]))
        self.last_arrival = 0.0

        weights = np.array(
            [config.dow_multipliers[d] for d in range(7)], dtype=float
        )
        if np.any(weights < 0) or weights.mean() <= 0:
            raise ValueError("Invalid weekday multipliers")
        self.base_daily = config.mean_daily_arrivals / weights.mean()

    def intensity(self, now: float) -> float:
        dt = datetime.fromtimestamp(now)
        month_factor = (
            self.config.peak_multiplier
            if dt.month in self.config.peak_months else 1.0
        )
        deterministic = (
            self.base_daily
            * self.config.dow_multipliers[dt.weekday()]
            * month_factor
        )
        cluster = self.config.hawkes_alpha * np.exp(
            -self.config.hawkes_beta * max(0.0, now - self.last_arrival)
        )
        return max(0.0, deterministic + cluster)

    def next_arrival(self, current_time: float) -> float:
        while True:
            value = self.rng.exponential(
                scale=1.0 / self.intensity(current_time)
            ) * DAY_SECONDS
            self.last_arrival = current_time + value
            if self.intensity(self.last_arrival) > 0:
                return self.last_arrival

@dataclass(frozen=True)
class ExperimentSpec:
    name: str
    policy: Policy
    demand: DemandConfig
    seed: int
    start_datetime: str = "2027-01-01T00:00:00"
    horizon_days: int = 365


CaseFactory = Callable[[str, float, np.random.Generator], CaseState]
TwinBuilder = Callable[[simpy.Environment, Policy, np.random.Generator], object]


class TwinAdapter:
    """
    Deliberate integration boundary.

    Implement calibrated completeness/review routing, applicant holds,
    parallel review tokens, drafting join, bundles, rework, appeals,
    outcomes, and measurement here. Do not silently ignore enabled policies.
    """

    def run_case(self, case: CaseState, required: set[str]):
        raise NotImplementedError(
            "Connect the calibrated process model and resource pools here"
        )


def execute_experiment(
    spec: ExperimentSpec,
    twin_builder: TwinBuilder,
    case_factory: CaseFactory,
) -> tuple[simpy.Environment, list[CaseState], object]:
    start = datetime.fromisoformat(spec.start_datetime).timestamp()
    env = simpy.Environment(initial_time=start)
    deadline = start + spec.horizon_days * DAY_SECONDS

    # Separate stream for case attributes/joint architect-district draws.
    attribute_rng = np.random.default_rng(
        np.random.SeedSequence([spec.seed, 2])
    )
    twin = twin_builder(env, spec.policy, attribute_rng)
    arrivals = HawkesArrivalSource(spec.demand, spec.seed)

    emitted: list[CaseState] = []
    next_time = arrivals.next_arrival(env.now)

    while next_time < deadline:
        case_id = f"{spec.name}-{spec.seed}-{len(emitted):08d}"
        case = case_factory(case_id, next_time, attribute_rng)
        required = required_stages(case, spec.policy)
        case.pending.update(required)
        emitted.append(case)

        # The adapter should emit the actual start/completion events used
        # for queue, service, calendar, and end-to-end measurements.
        env.process(twin.run_case(case, required))
        next_time = arrivals.next_arrival(env.now)

    # Include a warm-start backlog source here if using historical state.
    # Drain and collect outcome/backlog metrics after the target horizon.
    env.run(until=deadline)
    return env, emitted, twin
