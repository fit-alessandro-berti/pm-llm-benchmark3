## 1. Normalization Assumptions

**Interval Construction:**
- **Clock Offset:** Defined as `offset = recorded_clock - true_clock`. Thus, `true_time = recorded_time - offset`. If `offset  [a, b]`, `true_time  [recorded_time - b, recorded_time - a]`.
- **Rounding:**
  - **HUB:** Uncertainty `±0.5s`. Interval `[T - 0.5s, T + 0.5s]`.
  - **OPS-BER / VENDOR-NY:** Floor to minute. Displayed `10:14` means `[10:14:00, 10:14:59.999]`.
  - **SENSOR:** Round to nearest 10s. Displayed `T` means `[T - 5s, T + 5s]`.
  - **MOBILE-LON:** Round to nearest minute + Entry Delay.
- **Time Zone Conversion:**
  - **HUB:** UTC (Offset 0).
  - **OPS-BER:** Europe/Berlin. On 2026-06-01, CEST applies (UTC+2).
  - **SENSOR:** UTC.
  - **VENDOR-NY:** America/New_York. On 2026-06-01, EDT applies (UTC-4).
  - **LEGACY-BER:** Europe/Berlin. On 2025-10-26, DST fold occurs at 02:00.
  - **MOBILE-LON:** Europe/London. On 2026-06-01, BST applies (UTC+1).
- **DST Folds (T-405):**
  - 2025-10-26 02:00 local time falls back from 02:00:00 (CEST) to 01:00:00 (CET).
  - The local time 02:xx occurs twice: UTC 00:xx (CEST) and UTC 03:xx (CET).
  - Ingestion sequence constraint (`Alert`  `Inv`  `Containment`) forces selection of UTC instances that preserve chronological order.
- **Inferred Starts (T-404):**
  - `Investigation_Start` is missing. It is inferred as `Containment_Complete - Duration`.
  - Duration interval `[18 min, 25 min]` is applied to the `Containment_Complete` UTC interval.
- **Causal Constraints (T-407):**
  - `Alert_Received` is missing. `Alert_Sent` (14:00) + Latency `[0, 20] min` defines `Alert_Received  [13:40, 14:00]`.
  - Assumption: `Alert_Received  Investigation_Start` (receipt must not be after start).
- **Mobile Entry Delay (T-406):**
  - User entered time "up to five minutes late".
  - This implies `True_Event_Time  Recorded_Time`.
  - Combined with clock offset, `True_Time  [Recorded - MaxDelay - MaxOffset, Recorded - MinDelay - MinOffset]`.
  - Entry delay is treated as a shift to the *estimate of occurrence time*, not just the record time.
- **SLA vs Profile:**
  - SLA (S1-S3) is a hard maximum.
  - Temporal Profile is a statistical expectation (Mean ± Zeta * StdDev).

## 7. Governance Recommendation

1.  **UTC Storage:** All event timestamps must be stored in UTC ISO 8601 format (e.g., `2026-06-01T08:00:00Z`). Local time should never be stored as the canonical value.
2.  **Raw Timestamp Retention:** Systems must retain raw log entries including the `clock_source`, `timezone`, and `offset` metadata.
3.  **Source Offset Telemetry:** Implement automated NTP diagnostics logging (e.g., daily reports) to bound clock offset for each system. This enables the interval calculation required for T-401, T-409.
4.  **Resolution Metadata:** Explicitly log timestamp resolution (e.g., `resolution_seconds=1`, `rounding_floor=60`). This enables the interval construction for T-401, T-402.
5.  **Start/Complete Semantics:** Define strict semantics for `Investigation_Start` vs `Investigation_Complete`. Use a dedicated `Investigation_Start` event rather than inferring from duration records (T-404).
6.  **DST Fold Handling:** Systems operating in regions with DST transitions must log the UTC offset at the moment of event ingestion. For legacy systems, enforce UTC-only logging to avoid T-405 ambiguity.
7.  **Causal Identifiers:** Use unique `Incident_ID` or `Trace_ID` to link `Alert_Received` to `Alert_Sent` and `Investigation_Start` across systems (T-407).
8.  **Enforcement Policy:** Adopt an "Interval-Overlap" policy for SLA enforcement. If the feasible interval of `Investigation_Start` overlaps the SLA boundary, flag it as "At-Risk" rather than "Violated". Only if the interval is wholly above the SLA boundary should it be "Violated". This prevents false positives from clock drift.
