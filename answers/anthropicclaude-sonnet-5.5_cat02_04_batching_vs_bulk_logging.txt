**Assumptions** (each labelled, each needed for calculations below):
- **A1.** Displayed HH:MM values for 1-s sources hide unseen seconds. Lags computed from displayed `complete` are therefore approximate (±<60 s).
- **A2.** `recorded_at`  true completion, i.e. no back-dating. This gives an upper bound on completion.
- **A3.** `queue_arrival` is correct and comparable to local clocks, except in G8 where the clock mismatch is explicit.
- **A4.** `precision` bounds timestamp error symmetrically (±p). The G7 rounding rule is undocumented, so symmetric is the conservative choice.
- **A5.** PM4Py category semantics are as I understand them (Simultaneous, Batching at start, Batching at end, Sequential batching, Concurrent batching). They should be verified against the installed version.
- **A6.** "Serial-implied" service is the difference between adjacent completions (G2) or between a start and the next start (G3). It is a hypothesis, not an observation.

**Why G6-like data inflate waiting and show near-zero service.** The pipeline measures `wait = start  arrival` and `service = complete  start`.
1. When `start = complete = entry time`, service is zero by construction.
2. Everything that happened between arrival and entry is assigned to "waiting". This includes true idle time, true work time (hidden), and the delay until someone entered the record.
3. The first ticket (arrived 14:05) gets 175 min of "wait" although real work may have been complete at 14:30.
4. The waits fall almost linearly with arrival order, because all tickets share one release time. This is a signature of common release, not of a priority or FIFO effect.
5. Correct treatment: treat start as unknown, `complete  17:00`, `wait  [0, 17:00  arrival]`, `service  [0, same]`.

**Cross-interpretation effects on throughput and conformance:**
- **Throughput:** end batching and bulk entry (G3, G6) create spikes and gaps in completion counts. Simultaneous batches (G1) make true bursts. Coarsening (G7) produces grid-quantized throughput.
- **Conformance:**
  - Zero-duration or grid-aligned stamps produce ties, so event order must rely on `sequence_no`. Insertion order is not event order, especially for end batching.
  - Downstream events may precede a batched completion, giving spurious deviations.
  - Shared accounts (G5) distort resource-based conformance such as segregation-of-duties and handover.
  - For G4 and G8, conformance is straightforward if hand-offs are real.

def to_ts(x):
    x = str(x).strip()
    if x == "" or x.lower() in {"nan", "none", "nat"}:
        return pd.NaT                      # blank = unavailable (kept, never dropped)
    fmt = "%H:%M:%S" if x.count(":") == 2 else "%H:%M"
    return pd.to_datetime(f"{DAY} {x}", format="%Y-%m-%d " + fmt)

def _case_ids(obj, known):
    if isinstance(obj, str):
        return [obj] if obj in known else []
    if isinstance(obj, (list, tuple, set)):
        out = []
        for o in obj:
            out += _case_ids(o, known)
        return out
    return []

def run_pm4py(pm_in, merge_distances=(1, 60, 900), min_sizes=(2, 5)):
    try:
        import pm4py
    except Exception as exc:
        return pd.DataFrame(), [f"pm4py unavailable: {exc}"]
    errors, recs, known = [], [], set(pm_in["case"])
    try:
        fmt = pm4py.format_dataframe(pm_in, case_id="case", activity_key="activity",
                                     timestamp_key="complete_ts", start_timestamp_key="start_ts")
    except Exception as exc:
        return pd.DataFrame(), [f"format_dataframe failed: {exc}"]
    for md in merge_distances:
        for mb in min_sizes:
            try:
                res = pm4py.discover_batches(fmt, merge_distance=md, min_batch_size=mb)
            except Exception as exc:
                errors.append(f"discover_batches(md={md}, mb={mb}) failed: {str(exc)[:100]}")
                continue
            for item in res:
                try:
                    act, rsc = item[0]
                    types = item[-1]
                    if not isinstance(types, dict):
                        continue
                    for cat, batches in types.items():
                        for b in batches:
                            ids = sorted(set(_case_ids(b, known)))
                            recs.append(dict(merge_distance=md, min_batch_size=mb,
                                             cluster=AR2CL.get((act, rsc)), category=cat,
                                             batch_size=len(ids) or len(b), cases=",".join(ids)))
                except Exception as exc:
                    errors.append(f"parse issue: {str(exc)[:100]}")
    return pd.DataFrame(recs), errors

pm_long, pm_errors = run_pm4py(pm_in)

def pm_wide(pm_long, clusters):
    out = pd.DataFrame(index=clusters)
    if pm_long.empty:
        out["pm4py"] = "n/a"
        return out
    for (md, mb), sub in pm_long.groupby(["merge_distance", "min_batch_size"]):
        col, vals = f"md{md}_mb{mb}", {}
        for cl, s2 in sub.groupby("cluster"):
            vals[cl] = ", ".join(f"{k}x{v}" for k, v in s2.groupby("category").size().items())
        out[col] = pd.Series(vals)
    return out.fillna("-")

# ------------------------------------------------------------------ 5. independent diagnostics
def sweep_max(starts, ends):
    ev = [(t, 1) for t in starts] + [(t, -1) for t in ends]
    ev.sort(key=lambda x: (x[0], x[1]))            # ends before starts at ties
    cur = best = 0
    for _, d in ev:
        cur += d
        best = max(best, cur)
    return best

def overlap_rate(g):
    s, e, n = g["start_eff"].tolist(), g["e_eff"].tolist(), len(g)
    if n < 2:
        return 0.0
    hit = [any(s[i] < e[j] and s[j] < e[i] for j in range(n) if j != i) for i in range(n)]
    return float(np.mean(hit))

                                         "max_conc": sweep_max(g["start_eff"], g["e_eff"])}))
             .reset_index())

def on_q15(s):
    return float(((s.dt.minute % 15 == 0) & (s.dt.second == 0)).mean())

def serial_svc(g):
    """Serial-implied service in minutes (hypothesis, not observation)."""
    s, c = g["start_eff"], g["complete"]
    if s.nunique() == 1 and c.nunique() > 1:          # start-batched: serial from common start
        gg = g.sort_values(["complete", "sequence_no"])
        prev = gg["complete"].shift(1)
        imp_start = pd.concat([gg["start_eff"], prev], axis=1).max(axis=1)
        return float(((gg["complete"] - imp_start).dt.total_seconds() / 60).mean())
    if c.nunique() == 1 and s.nunique() > 1:          # end-batched: completion <= next start
        gg = g.sort_values(["start_eff", "sequence_no"])
        nxt = gg["start_eff"].shift(-1)
        imp_end = pd.concat([gg["complete"], nxt], axis=1).min(axis=1)
        return float(((imp_end - gg["start_eff"]).dt.total_seconds() / 60).mean())
    return np.nan

def bounds(g):
    """Interval-censored bounds: +/-precision, start >= arrival, completion <= recorded_at."""
    p = pd.to_timedelta(g["precision_s"], unit="s")
    comp_lb = g["complete"] - p
    comp_ub = pd.concat([g["complete"] + p, g["recorded_at"]], axis=1).min(axis=1)
    st_lb = pd.concat([g["start_eff"] - p, g["queue_arrival"]], axis=1).max(axis=1)
    st_ub = g["start_eff"] + p
    st_lb = st_lb.where(~g["start_suspect"], g["queue_arrival"])      # suspect start = unknown
    st_ub = st_ub.where(~g["start_suspect"], comp_ub)
    st_ub = pd.concat([st_ub, comp_ub], axis=1).min(axis=1)
    f = lambda x: x.dt.total_seconds() / 60
    w_lo, w_hi = f(st_lb - g["queue_arrival"]), f(st_ub - g["queue_arrival"])
    s_lo, s_hi = f(comp_lb - st_ub).clip(lower=0), f(comp_ub - st_lb)
    return (f"{w_lo.mean():.1f}-{w_hi.mean():.1f}", f"{s_lo.mean():.1f}-{s_hi.mean():.1f}")

# 5. Robustness and alternative explanations

**Resource IDs trusted versus treated as shared accounts**

| cluster | IDs trusted (one worker / device) | IDs treated as shared accounts |
|---|---|---|
| G1 | RBT-7 is an automated cell, so ID trust is natural. Capacity 4 makes the batch physical. | Little change. Shared-account risk is low for a PLC cell. |
| G2 | One inspector: parallel inspection of 4 surfaces is doubtful, so serial work under a group stamp rises in likelihood. | If T-B is shared by up to 4 inspectors, concurrent inspection becomes plausible and rises to second or even first place. Utilization 259 % then falls to  65 % for 4 workers. |
| G3 | One reviewer: serial work with deferred submission (end batching) is best. | Multiple reviewers working in parallel and submitting together is possible. End batching stays on top, but the serial-implied service of 7 min is no longer justified. |
| G4 | Strict hand-offs mean one busy worker. Sequential is supported. | Four exact hand-offs among several workers would be a coincidence, so the conclusion barely changes. Start-derivation remains the main alternative. |
| G5 | One person would have 233 % utilization and 4-fold overlap, which is impossible. The "trusted" reading is rejected. | Pool model (c = 3 or 4) is workable. It gives 78 % or 58 % pooled utilization. This is the preferred interpretation. |
| G6 | Immaterial. Zero duration is a semantic fault either way. | Shared entry would fit bulk entry even better (one person enters for the team). |
| G7 | Same worker means serial manual measures are plausible. | Several measurers in parallel are plausible. Coarsening stays on top. |
| G8 | Single T-H: downtime plus serial drain. | Multiple workers sharing the ID would make the strictly serial pattern odd, so ID trust is supported. |

**Timestamps exact versus interval-censored**

| cluster | exact reading | interval-censored reading |
|---|---|---|
| G1 | Equality at 1 s is strong evidence. | The ±1 s interval is negligible relative to the 3-min duration. The conclusion is unchanged. |
| G2 | Starts identical, ends spread. | ±1 min cannot bridge the 6–8 min spacing of completions. Start-batching and its serial reading remain. Group-start equality is an artefact of the button, not of precision. |
| G3 | Starts staggered by 7–8 min, ends identical. | ±1 min cannot merge the starts. End equality holds. Conclusion robust. |
| G4 | Exact hand-offs. | Adjacency within ±1 s remains plausible. The start-derived alternative cannot be ruled out by censoring. |
| G5 | Overlap 13:12–13:20. | A02 ends 13:20 (±1) and A04 starts 13:12 (±1), a gap of 8 min that ±2 min cannot close. 4-way overlap is robust. |
| G6 | Zero duration. | ±1 min is irrelevant: the true completion may be hours earlier, so the censoring is one-sided and enormous. |
| G7 | Equality and 15-min service. | ±15 min dominates. Bounds are wide (service  0 to 18 min), and negative waits disappear (truncated at  0). Start and end equality carry almost no information. |
| G8 | 3-min gap after the safety window. | Clock mismatch makes the gap indeterminate. Downtime attribution is plausible but not proven. |

**Cases where the same temporal pattern supports multiple physical explanations**

1. **G2 (common start, distinct ends):**
   - Start batching of a serial sequence (true starts at 10:00, 10:08, 10:14, 10:21).
   - Genuinely concurrent inspection.
   - A real common setup (for example, all surfaces prepared at 10:00).
   
   Only a per-item start event, an audit of the work, or an observation of the workstation can distinguish them.
2. **G3 (distinct starts, common end):**
   - Serial reviews with bulk submission.
   - Multitasking across reviews that really finish together.
   - Start stamps meaning "form opened" rather than "work begun".
3. **G7 (all equal, 15-min grid):**
   - Timestamp coarsening.
   - A simultaneous physical measurement.
   - Serial measurements squeezed into one window (supported by the 1-min `recorded_at` staggering).
4. **G1 (all equal, 1-s precision):**
   - A physical joint operation on a fixture.
   - Four independent parallel positions.
   - A cell that logs batch events at the level of the fixture. The temporal pattern cannot distinguish them, but they differ little for capacity modelling.
5. **G6 (zero duration):**
   - Retrospective bulk entry.
   - A genuine instantaneous system action, such as a scheduled auto-close policy.
   
   The queue wait is an artefact in one reading and a real policy delay in the other.
6. **G4 and G8 (strict back-to-back):**
   - A genuine busy single server.
   - Start derived from the previous scan.
   - For G8, a restart after downtime.

# 6. Data-collection redesign

Priority order, highest first:

1. **Execution timestamps (P0).**
   - Record per-item start and complete events from the physical activity (scan or button).
   - Include pause and resume.
   - Never overwrite start with a group or entry time.
   - This fixes G2, G3, G6, G7 and partly G4.
2. **Recording versus execution timestamps (P0).**
   - Keep `event_time` and `recorded_at` separate and labelled.
   - Mark whether `event_time` was user-entered, system-captured, or derived.
   - Require an explicit flag for retrospective or bulk entry (G3, G6).
3. **Group / batch identifiers (P0).**
   - Emit a `batch_id`, `batch_size`, and the role of each item.
   - Distinguish a physical batch (G1) from a logging batch (G6) and a shared-screen group (G2).
4. **Resource / badge identity (P1).**
   - Retain individual identity for shared logins (G5).
   - Record the number of people logged in simultaneously.
5. **Workstation capacity (P1).**
   - Store nominal capacity per resource (RBT-7 = 4, T-B, T-C, analyst pool) and its changes over time.
   - Needed for correct utilization (G1, G5).
6. **Pause/resume and availability events (P1).**
   - Log downtime, safety checks and unavailability as resource states, not as a separate system with its own clock (G8).
7. **Source clocks (P1).**
   - Synchronise all sources (NTP or equivalent).
   - Log the clock offset and uncertainty.
   - Reconcile safety and repair clocks (G8).
8. **Timestamp precision metadata (P2).**
   - Store the precision, the rounding rule (floor / ceil / nearest), and the expected accuracy, not just the nominal granularity.
   - Stop the legacy MES rounding of start and complete, or document the rule exactly (G7).
   - Store seconds wherever the source provides them.

# 7. Final adjudication

| confidence class | clusters | reasoning |
|---|---|---|
| **Interpretable with high confidence** | **G1** (physical simultaneous batch, capacity 4), **G4** (sequential, non-overlapping; subject to the start-semantics check) | Equality or adjacency at 1-s precision, consistent lag, coherent context. G4 magnitude of service is conditional on start being measured. |
| **Exclude from service-time analysis and interval-censor in queue analysis** | **G6** (start unknown, complete an upper bound, service unobservable), **G7** (15-min rounding, negative waits) | Stamped intervals are not observations. Use only bounds: G6 wait  [0, 17:00  arrival], G7 from arrival/recorded_at limits. |
| **Usable only with interval or serial-implied bounds** | **G2**, **G3** | Start (G2) or end (G3) stamp is a group stamp. Report nominal, serial-implied, and concurrent readings side by side (G2 service 17.5 vs 6.75 min, G3 16.75 vs 7 min). |
| **Require operational validation before any performance conclusion** | **G5** (analyst count, capacity 3 vs 4, nature of the ~15-min lag), **G8** (clock offset and whether the safety check blocked T-H), **G2** and **G3** (serial or concurrent work), **G4** (start measured or derived), **G6** (administrative bulk close versus retrospective entry) | The same temporal pattern supports materially different physical explanations and opposite bias directions. |

**Bottom line:**
- Identical timestamps are not simultaneous work. They come from at least four mechanisms here: real batching (G1), group-start stamping (G2), bulk submission or entry (G3, G6), and quantization (G7).
- PM4Py labels identify temporal patterns only. G1, G6 and G7 all appear as "Simultaneous" but have very different data-quality implications.
- The safest policy is to carry explicit bounds and validity flags rather than a single-point waiting or service time for G2, G3, G5, G6, G7 and G8.
