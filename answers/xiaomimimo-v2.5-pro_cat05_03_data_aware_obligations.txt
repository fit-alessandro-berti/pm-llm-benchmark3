## 1. Temporal Data Semantics

State reconstruction:
- Forward-fill: blank cells mean "no update" and inherit the most recent prior non-blank value within the same case.
- No backward propagation: future values are never copied to earlier events.
- Tie-breaking: when two events share a timestamp, `event_index` determines order (lower index first).
- State snapshot: at any event, the state is the forward-filled value from the most recent event (by timestamp, then event_index) that set or inherited that attribute.

Event time vs. effective time vs. record time vs. evidence time:
- Event time: the `time:timestamp` in the log (when the event was recorded in the source system).
- Effective time: when the change actually takes effect (may differ from event time; e.g., a jurisdiction change might be effective immediately or at a future date).
- Record time: when the event was recorded in the database (may be later than event time due to outages; e.g., TX-302's Record_Exemption at 11:00 for an approval at 09:05).
- Evidence time: when the evidence was created or signed (e.g., signing certificate timestamp for EX-88 at 10:30, contradicting displayed approval at 08:50).

Material data changes:
- An amount change is material if it increases by >20% (per R4) or changes the trigger condition (e.g., crossing the 100,000 threshold).
- A jurisdiction change is material if it affects rule triggers (e.g., changing to/from DE for R1).
- A risk level or customer type change is material if it affects R2 triggers.

def check_exemption(exemption_id, jurisdiction, customer_type, amount, release_time):

        return False, f"Exemption expired at {exm['expires']}"

        if exm['signing_cert_time'] > release_time:
            return False, f"Signing cert {exm['signing_cert_time']} after release; backdated field alone not conclusive (R5)"

def check_exemption(exm_id, jur, cust, amt, release_ts):
    """Evaluate exemption validity per R5. Returns (valid, reason)."""
    if pd.isna(exm_id):
        return False, "no exemption referenced"
    row = EXEMPTIONS.loc[EXEMPTIONS["exemption_id"] == exm_id]
    if row.empty:
        return False, f"{exm_id} not in register"
    e = row.iloc[0]
    if e["scope_jur"] != jur:
        return False, "jurisdiction mismatch"
    if e["scope_cust"] != cust:
        return False, "customer-type mismatch"
    if pd.notna(amt) and amt > e["scope_max_amt"]:
        return False, "amount exceeds scope"
    if e["eff_from"] > release_ts:
        return False, "effective_from after release"
    if e["expires"] <= release_ts:
        return False, "expired at release"
    # R5 evidence gate
    if e["signing_cert_ts"] > release_ts:
        return False, "signing cert after release; backdated field not conclusive (R5)"
    return True, "valid"

def _prev_amount(case_df, evt):
    """Forward-filled amount at the event immediately before evt."""
    before = case_df[
        (case_df["time:timestamp"] < evt["time:timestamp"])
        | (
            (case_df["time:timestamp"] == evt["time:timestamp"])
            & (case_df["event_index"] < evt["event_index"])
        )
    ]
    if before.empty:
        return np.nan
    return before.iloc[-1]["amount"]

## 6. Why Control-Flow-Only Conformance Is Insufficient

| # | Failure mode | Example | Explanation |
|---|---|---|---|
| **1. Final-state leakage** | TX-303 | A control-flow model that checks "High_Risk  Enhanced_Review  Release" would need to know risk=HIGH. But risk was LOW at creation and only became HIGH at 10:15. A purely structural model either applies the constraint unconditionally (false positives on LOW-risk cases) or misses it entirely. |
| **2. Post-hoc / backdated exemptions** | TX-310 | EX-88's displayed approval (08:50) precedes release (10:00), so a record-time check would accept it. Only comparing the signing certificate timestamp (10:30) to release time reveals the exemption was not approved in time. Control-flow has no notion of evidence time vs. display time. |
| **3. Material changes after review** | TX-309 | The trace `Create  StdReview  Update  EnhReview  Update  Release` has an Enhanced_Review before Release—control-flow says "compliant." But R4 invalidates the review because the second amount increase (22.9 %) exceeds 20 %. No control-flow constraint can encode a percentage threshold on a changing numeric attribute. |
| **4. Conditional activation** | TX-311 | The trace has Enhanced_Review before Release—control-flow says a precedence constraint is satisfied. But R1 is *not triggered* because jurisdiction = DE at release. Conversely, TX-307 has Compliance_Approve before Release (satisfying a naïve precedence constraint), but R2 requires Enhanced_Review—not Standard_Review—which is a data-attribute distinction invisible to control flow. |
| **5. Missing / unknown data** | TX-305 | The amount is never recorded before release. A control-flow model would evaluate the trace normally and likely declare compliance. But R6 requires INDETERMINATE classification when a decisive trigger cannot be established. Control-flow conformance has no mechanism for "we don't know if this rule applies." |
| **6. Same-timestamp ordering** | TX-311 | Enhanced_Review (index 3) and Update_Jurisdiction (index 4) share timestamp 16:20. Whether the review saw US or DE depends entirely on event_index. Most process-mining tools collapse same-timestamp events or order them arbitrarily, making the outcome non-deterministic. |
| **7. Temporal gap between screen and release** | TX-304 | The trace contains Sanctions_Screen  Sanctions_List_Update  Release. Control-flow sees "a screen occurred before release" and declares compliance. But R3 requires a *new* screen *after* the list update, because the jurisdiction's sanctions status changed. A static precedence constraint cannot express "re-screen if the list changed." |
| **8. Review type distinction** | TX-307 | The trace contains Standard_Review and Compliance_Approve before Release. A naïve model might check "Review  Approve  Release." But R2 requires *Enhanced_Review*, not Standard_Review. Process-mining DECLARE templates treat activity labels as atomic; they cannot distinguish review quality levels without data-attribute inspection. |

## 7. Recommended Logging and Control Improvements

| Improvement | What to log | Why it helps |
|---|---|---|
| **Immutable release payload** | Record the exact amount, jurisdiction, risk, and customer_type *as sent* in the release message, with a cryptographic hash. | TX-305's indeterminacy would be resolved immediately; no post-hoc settlement inference needed. |
| **Separate effective / record / signature timestamps** | Every event should carry `effective_ts`, `record_ts`, and (where applicable) `signature_ts`. | EX-88's conflict (displayed 08:50 vs. signing cert 10:30) would be unambiguous. EX-77's outage delay would be clearly distinguished from the approval time. |
| **Rule version and rule-set identifier** | Tag each compliance decision with the rule-set version that governed it. | Future rule changes won't create ambiguity about which obligations applied to historical cases. |
| **Exemption scope as structured data** | Record scope as structured fields (jurisdiction list, customer-type list, max amount, rules waived) rather than free-text. | Automated scope matching becomes deterministic; no need to parse PDF documents. |
| **Change provenance chain** | For every attribute update, record: (a) previous value, (b) new value, (c) reason code, (d) actor, (e) whether it is a material change under the current rule-set. | R4's 20 % calculation and R1's "latest material data change" become directly queryable without re-deriving from the event sequence. |
| **Stable event ordering** | Assign a globally monotonic `event_sequence` number (not just per-timestamp `event_index`). | Same-timestamp ambiguity (TX-311) is eliminated. Process-mining tools can reconstruct the exact order without tie-breaking rules. |
| **Decision-point logging** | At every point where a rule *could* apply, log: (a) which rules were evaluated, (b) the state snapshot used, (c) the outcome (triggered/satisfied/violated/not-applicable). | Post-hoc auditing becomes a comparison of logged decisions against the rule-set, rather than a reconstruction from raw events. |
| **Review scope annotation** | Tag each Enhanced_Review / Standard_Review with the attributes it covered (amount range, jurisdiction, risk at time of review). | R4 invalidation and R1's "after latest material data change" can be checked directly against the review's declared scope, rather than inferred from timestamps. |
