## 1. Equivalence design space

Conventions. An execution consists of labelled events in timestamp order, typed objects, an externality flag, E2O incidence and qualified O2O relations. Local identifiers carry no meaning; the `EXT` prefix does. No events are added. Where O2O notes are abbreviated (X3, X4, X6, X8), only baseline relations implied by the E2O incidence are assumed, and no assignment depends on them.

**R1 — Activity-sequence equivalence (≡act)**
- Definition: X ≡act Y iff the label sequences of the events containing the lead Order, in timestamp order, are identical.
- Preserved: activity vocabulary, repetition counts, total order.
- Discarded: all non-lead objects, object types, multiplicities, externality, E2O, O2O.
- Properties: reflexive, symmetric, transitive (kernel of a function).
- Concurrency: same-timestamp events form a block whose labels are sorted, so tie order cannot create variants.
- Role: baseline only; it is the order-flattened variant notion, not object-centric.

**R2 — Typed structural equivalence under renaming (≡typ)**
- Definition: X ≡typ Y iff there is a bijection f on objects preserving object type and EXT flag, and an order-preserving bijection g on events preserving labels, such that o ∈ E2O(e) ⇔ f(o) ∈ E2O(g(e)). The variant R2+ additionally requires (o, q, o') ∈ O2O ⇔ (f(o), q, f(o')) ∈ O2O.
- Preserved: labels, event order, object types, exact multiplicities, externality, complete incidence; R2+ also qualified relations.
- Discarded: identifiers, timestamps and durations, attribute values; plain R2 discards O2O.
- Properties: equivalence relation (identity, inverse and composition of isomorphisms).
- Concurrency: timestamp-tie blocks are antichains; g must preserve the block index. A behavioral variant R2po replaces the total order by the object-induced partial order (e precedes e' iff they share a non-lead object and e is earlier; transitive closure) and requires labelled-DAG isomorphism; it remains an equivalence.

**R3 — Business-semantic equivalence (≡sem), preferred**
- Definition: X ≡sem Y iff σ(X) = σ(Y), with σ = (isolation, fulfilment plan, exception motif):
  - isolation ∈ {ISOLATED, SHARED-LOGISTICS, SHARED-FINANCE, SHARED-BOTH}: does an EXT object take part in an event touching Package/Delivery, respectively Invoice/Payment;
  - fulfilment plan ∈ {SINGLE, SPLIT}: the number of planned packages (all packages minus re-shipment packages) is 1 or more than 1;
  - exception ⊆ {SUBSTITUTION, RETURN-RESHIP}. SUBSTITUTION: an Item–Item `replaces` or a `removed_before_dispatch` qualifier exists, or a Dispatch lists a strict subset of the items packed in its packages. RETURN-RESHIP: a reverse-logistics activity occurs, an already packed item is packed again, or a Package–Package `replaces` exists.
- Refinement R3+ appends modifiers: capped counts (1/N) of items, packages, deliveries and payments per invoice, delivery consolidation, and the partial-settlement qualifier.
- Preserved: cross-order sharing, split versus single plan, exception motifs, supplied qualifiers.
- Discarded: identifiers, exact counts above 1, item count, the position of invoicing relative to logistics, and (in the primary key only) delivery consolidation and instalments.
- Properties: equivalence relation (kernel of σ). A threshold variant ("signature distance ≤ k") would be reflexive and symmetric but not transitive, so I avoid it.
- Concurrency: σ uses only object-induced precedence (an item packed before it is packed again), so permuting concurrent or same-time events does not change it.

**R4 — Order-local projection equivalence (≡loc)**
- Definition: delete all EXT objects, then apply R2. A per-order extraction computes this implicitly.
- Preserved: local typed structure. Discarded: every coupling to other orders. Properties and concurrency: as R2.

Lattice. R2+ refines R2, R2 refines R4, R4 refines R1, and R2+ refines R3. R1 and R3 are incomparable: R1 merges X1/X5/X6/X7, which R3 separates, and R3 merges X3/X4, which R1 separates.

## 2. Canonical signatures

`structural_key` is a canonical form for R2/R2+/R4. `semantic_signature` is σ for the preferred relation R3; it returns the primary key (the cluster) and the modifiers (the drill-down).

Why `structural_key` is canonical: each object gets a profile (type, EXT flag, indices of its events, qualified O2O neighbourhood), and objects are numbered per type in profile order. With E2O only, objects with equal profiles occur in exactly the same events, so swapping them is an automorphism. With O2O, the minimum over permutations inside tie groups is taken: exact, but exponential in tie-group size.

The cluster columns in section 3 were produced by running this code on X1–X8 encoded exactly as listed.

```python
from itertools import permutations, product
from collections import defaultdict

PACK, DISPATCH, PAY = "Pack Package", "Dispatch", "Record Payment"
REVERSE_ACTS = {"Return Item", "Inspect Return"}        # configurable motif vocabulary
LOGISTICS, FINANCE = {"Package", "Delivery"}, {"Invoice", "Payment"}
is_ext = lambda oid: oid.startswith("EXT")
cap = lambda n: "0" if n == 0 else "1" if n == 1 else "N"

# execution = {"events": [(activity, {otype: [oid, ...]}), ...],   # timestamp order
#              "o2o":    [(source_oid, qualifier, target_oid), ...]}

def activity_key(ex):                                     # R1
    return tuple(a for a, _ in ex["events"])

def structural_key(ex, drop_ext=False, use_o2o=False):    # R2, R2+ (use_o2o), R4 (drop_ext)
    keep = lambda o: not (drop_ext and is_ext(o))
    events = [(a, {t: [o for o in os if keep(o)] for t, os in objs.items()})
              for a, objs in ex["events"]]
    typ, occ = {}, defaultdict(list)
    for i, (a, objs) in enumerate(events):
        for t, os in objs.items():
            for o in os:
                typ[o] = t
                occ[o].append(i)
    o2o = [(s, q, d) for s, q, d in ex["o2o"] if s in typ and d in typ] if use_o2o else []

    def profile(o):
        rel = sorted([("out", q, typ[d]) for s, q, d in o2o if s == o] +
                     [("in", q, typ[s]) for s, q, d in o2o if d == o])
        return (typ[o], is_ext(o), tuple(occ[o]), tuple(rel))

    groups = defaultdict(list)
    for o in typ:
        groups[profile(o)].append(o)
    ordered = [groups[p] for p in sorted(groups)]
    best = None
    for combo in product(*[permutations(g) for g in ordered]):
        name, counter = {}, defaultdict(int)
        for g in combo:
            for o in g:
                k = (typ[o], is_ext(o))
                counter[k] += 1
                name[o] = f"{'ext:' if is_ext(o) else ''}{typ[o]}#{counter[k]}"
        ev = tuple((a, tuple(sorted(name[o] for os in objs.values() for o in os)))
                   for a, objs in events)
        rel = tuple(sorted((name[s], q, name[d]) for s, q, d in o2o))
        if best is None or (ev, rel) < best:
            best = (ev, rel)
        if not use_o2o:          # equal profiles are automorphic: one labelling suffices
            break
    return best

def semantic_signature(ex, use_qualifiers=True, use_ext=True):   # R3 (primary) / R3+ (both)
    ev = ex["events"]
    o2o = ex["o2o"] if use_qualifiers else []
    typ = {o: t for _, objs in ev for t, os in objs.items() for o in os}
    local = lambda t: {o for o, ty in typ.items() if ty == t and not is_ext(o)}

    # 1. isolation: does a foreign object take part in logistics / finance events?
    def shared(domain):
        return use_ext and any(is_ext(o) for _, objs in ev if domain & objs.keys()
                               for os in objs.values() for o in os)
    isolation = {(False, False): "ISOLATED", (True, False): "SHARED-LOGISTICS",
                 (False, True): "SHARED-FINANCE", (True, True): "SHARED-BOTH"}[
                 (shared(LOGISTICS), shared(FINANCE))]

    # 2. package contents and re-shipment packages (E2O evidence, then qualifier evidence)
    content, seen, reship = defaultdict(set), set(), set()
    for a, objs in ev:
        if a == PACK:
            items = [i for i in objs.get("Item", []) if not is_ext(i)]
            for p in objs["Package"]:
                content[p] |= set(items)
                if items and all(i in seen for i in items):
                    reship.add(p)
            seen |= set(items)
    reship |= {s for s, q, d in o2o
               if q == "replaces" and typ.get(s) == typ.get(d) == "Package"}

    # 3. exception motifs
    returned = any(a in REVERSE_ACTS for a, _ in ev) or bool(reship)
    subst_q = any(q == "removed_before_dispatch" or
                  (q == "replaces" and typ.get(s) == typ.get(d) == "Item")
                  for s, q, d in o2o)
    subst_e = any(a == DISPATCH and "Item" in objs and
                  set(objs["Item"]) < set().union(*[content[p] for p in objs["Package"]])
                  for a, objs in ev)
    exception = tuple(f for f, on in (("RETURN-RESHIP", returned),
                                      ("SUBSTITUTION", subst_q or subst_e)) if on) or ("NONE",)

    # 4. fulfilment plan: packages that are not re-shipments
    n_pkg, n_del = len(local("Package")), len(local("Delivery"))
    fulfilment = "SINGLE" if n_pkg - len(reship) <= 1 else "SPLIT"

    # 5. modifiers (R3+ only)
    pays = defaultdict(set)
    for a, objs in ev:
        if a == PAY:
            for v in objs["Invoice"]:
                pays[v] |= set(objs["Payment"])
    max_pay = max((len(p) for p in pays.values()), default=0)
    partial = any(q.startswith("partially_settles") for _, q, _ in o2o)

    primary = (isolation, fulfilment, "+".join(exception))
    modifiers = (f"items={cap(len(local('Item')))}", f"pkg={cap(n_pkg)}", f"del={cap(n_del)}",
                 "consolidated" if n_del < n_pkg else "one-delivery-per-package",
                 f"pay/inv={cap(max_pay)}" + ("(partial)" if partial else ""))
    return primary, modifiers

def cluster(executions, key):                 # executions: {"X1": ex, ...}
    out = defaultdict(list)
    for name, ex in executions.items():
        out[key(ex)].append(name)
    return dict(out)
```

## 3. Cluster assignments

Activity abbreviations: CO Create Order, AI Add Item, PP Pack Package, D Dispatch, RI Return Item, IR Inspect Return, II Issue Invoice, RP Record Payment.

- A1 = ⟨CO, AI, AI, PP, D, II, RP⟩; A2 = ⟨CO, AI, AI, PP, PP, D, II, RP⟩; A3 = ⟨CO, AI, AI, PP, D, PP, D, II, RP, RP⟩; A4 = ⟨CO, AI, AI, PP, D, RI, IR, PP, D, II, RP⟩.
- T1–T7 are R2 classes. R2+ yields the same partition on these eight executions.
- S1–S6 are R3 classes (primary key). Modifiers are shown in brackets.

## 4. Cluster interpretations

**S1 — Clean isolated order-to-cash (X1, X2)**
- Signature: ISOLATED / SINGLE / NONE.
- Behavior: every item ships once in one package and one delivery; one invoice, one payment.
- Risks and opportunities: reference population for throughput benchmarks and automation targets.
- Poor flattening: on Item, which copies the single Pack event into each item case (convergence).
- Stability: stable. The danger is false membership: X5, X6 and X7 fall into S1 once foreign objects or qualifiers are lost.

**S2 — Planned split fulfilment (X3, X4)**
- Signature: ISOLATED / SPLIT / NONE; S2a consolidated delivery with single payment, S2b staggered deliveries with instalments.
- Behavior: the order is deliberately fulfilled in several packages; no item ships twice and nothing is corrected.
- Risks and opportunities: extra handling and freight cost; partial-delivery complaints in S2b; X4-like cases are consolidation candidates.
- Poor flattening: on Order, repeated Pack/Dispatch looks like rework; on Package, order and finance events are duplicated per package and X3's single Dispatch is counted twice.
- Stability: membership depends only on planned-package multiplicity, so it survives payment repairs; it is sensitive to duplicate package identifiers for one parcel.

**S3 — Shared logistics (X5)**
- Signature: SHARED-LOGISTICS / SINGLE / NONE.
- Behavior: O5's items are co-packed and co-dispatched with an item of another order; billing remains per order.
- Risks and opportunities: freight saving; coupled delay, damage and returns; ambiguous freight-cost allocation.
- Poor flattening: on Order, the shared Pack and Dispatch appear in both order cases, so packages are double-counted and X5 looks like X1.
- Stability: depends entirely on retaining foreign objects; a per-order extraction erases the cluster.

**S4 — Shared finance (X6)**
- Signature: SHARED-FINANCE / SINGLE / NONE.
- Behavior: a collective invoice bills two orders; one payment settles it without order-level allocation.
- Risks and opportunities: fewer invoices; the settlement status of O6 alone is not determinable; a dispute on one order can block cash for both.
- Poor flattening: on Order, the payment is counted in both order cases; on Invoice, two orders' logistics interleave in one case and look like loops.
- Stability: survives a pro-rata payment allocation (the invoice is still shared); disappears if foreign objects are dropped.

**S5 — Pre-dispatch substitution (X7)**
- Signature: ISOLATED / SINGLE / SUBSTITUTION.
- Behavior: I71 was packed, then removed before dispatch; I72 replaces it and is the only item dispatched.
- Risks and opportunities: the invoice bills the order without item-level evidence, so billing of the removed item must be checked; stock accuracy; no explicit removal event exists, a logging gap.
- Poor flattening: on Order, because the label sequence equals X1.
- Stability: the least stable cluster. It rests on two qualifiers and one E2O detail; a repair that treats the Dispatch item list as noise merges X7 into S1.

**S6 — Return and re-shipment (X8)**
- Signature: ISOLATED / SINGLE / RETURN-RESHIP.
- Behavior: I82 is dispatched, returned, inspected, repacked and dispatched again; invoicing follows the second dispatch.
- Risks and opportunities: reverse-logistics cost, a likely quality or picking issue, delayed cash.
- Poor flattening: on Order it resembles a split delivery; on Package, P82 loses its return context.
- Stability: robust, with three independent evidence sources (activity labels, the item in two packages, the `replaces` qualifier).

## 5. Borderline cases

**X1 versus X2.** R1, R2, R3 and R4 all merge them. They are split only by a naive canonicalization that numbers objects by sorted raw identifier: X2 then reads "add item 2, add item 1". That is defensible only if identifiers encode something (line position, SKU), which the task excludes.

**X1 versus X5.** R1 and R4 merge them, since the order-local view is identical. R2 separates them because Pack carries two Orders and three Items and Dispatch carries two Orders, and R3 separates them on isolation. The local view suits questions about O5's own objects; it fails for cost and risk coupling.

**X1 versus X6.** R1, R4 and even a local object-count vector merge them, because the multiplicities are identical. R2 and R3 separate them, since Issue Invoice and Record Payment include EXT-OB. The disagreement is about whether "paid" is a property of the invoice (merge) or of the order (separate, since no allocation exists).

**X1 versus X7.** R1 and any type-count signature merge them. R2 separates them only because Dispatch lists Item I72; R2+ and R3 also use the qualifiers. If Dispatch were logged as in X1, plain R2 would merge them and only qualifier-aware relations would not.

**X3 versus X4.** R1, R2 and R3+ separate them (one Dispatch against two, one payment against two). R3's primary key merges them as planned split fulfilment. Separation suits carrier-cost and cash-collection analysis; merging suits the question "was the order split, and was anything corrected". I merge at the primary level and keep S2a/S2b visible.

**X4 versus X8.** A logistics-multiplicity signature (two packages, two deliveries, repeated Pack then Dispatch) merges them as multi-shipment orders. R1, R2 and R3 separate them. The decisive invariant is item-to-package multiplicity: in X4 every item ships once, in X8 I82 ships twice and P82 replaces P81. Counting deliveries per order treats a failure loop as a plan.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

**What the key preserves.** As I know the implementation (verify against the installed version), the function splits the OCEL into one sub-OCEL per object of the chosen type, containing the objects connected to it through the ancestor/descendant closure of the object interaction graph. It renames the objects of each sub-OCEL deterministically by type and order of first appearance, with a lexicographic tie-break. It then builds a textual description without timestamps and uses that string as the dictionary key; the values are lists of sub-OCELs. The key therefore preserves event order, activity labels and typed E2O incidence under canonical names: close to R2, without a lead-versus-foreign distinction. I would not rely on O2O qualifiers or attribute values being part of the key.

**Why raw identifiers make clusters too fine.** Any identifier that leaks into the key turns isomorphic executions into singletons. Leaks come from an identifier-based tie-break among objects first seen in the same event or at the same timestamp, from attributes that embed identifiers, or from foreign objects that are named rather than flagged.

**Canonicalization and post-processing.** Per returned sub-OCEL: identify the lead Order, flag foreign objects, compute `structural_key` to re-merge clusters split by naming artefacts, then aggregate by `semantic_signature`. The signature is computed per member, not per representative, because exact clusters may be heterogeneous in qualifiers.

**When exact equivalence is preferable.** For audit evidence, regression testing of extraction pipelines, deduplication, and whenever a single incidence difference such as a shared invoice is the finding.

**`max_objs` and large executions.** Shared packages, collective invoices or carrier-level deliveries connect many orders. The closure then yields very large, almost always unique executions, so clusters fragment and keys become expensive. `max_objs` bounds this by discarding oversized executions, which biases the result towards isolated orders: the discarded ones are exactly S3- and S4-like. Report the dropped share and handle those executions with a signature that flags foreign objects without expanding them.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"
exact = pm4py.cluster_equivalent_ocel(ocel, LEAD_TYPE, max_objs=40)   # {key: [sub_ocel, ...]}

def to_execution(sub):
    rel = sub.relations.sort_values(["ocel:timestamp", "ocel:eid"])
    orders = rel[rel["ocel:type"] == LEAD_TYPE]
    # lead Order: the Order taking part in most events; ties go to the earliest (heuristic)
    stats = orders.groupby("ocel:oid").agg(n=("ocel:eid", "nunique"), t=("ocel:timestamp", "min"))
    lead = stats.sort_values(["n", "t"], ascending=[False, True]).index[0]

    o2o = [tuple(r) for r in sub.o2o[["ocel:oid", "ocel:qualifier", "ocel:oid_2"]].itertuples(index=False)]
    foreign = set(orders["ocel:oid"]) - {lead}
    foreign |= {d for s, q, d in o2o if s in foreign and q == "contains"}   # children of foreign orders
    tag = lambda o: f"EXT-{o}" if o in foreign else o

    events = []
    for _, grp in rel.groupby("ocel:eid", sort=False):
        objs = defaultdict(list)
        for oid, ot in zip(grp["ocel:oid"], grp["ocel:type"]):
            objs[ot].append(tag(oid))
        events.append((grp["ocel:activity"].iloc[0], dict(objs)))
    return {"events": events, "o2o": [(tag(s), q, tag(d)) for s, q, d in o2o]}

structural, semantic, mixed = defaultdict(list), defaultdict(list), []
for key, members in exact.items():
    sigs = set()
    for sub in members:
        ex = to_execution(sub)
        structural[structural_key(ex, use_o2o=True)].append(sub)   # custom canonicalization
        primary, modifiers = semantic_signature(ex)                # custom aggregation
        semantic[primary].append((modifiers, sub))
        sigs.add(primary)
    if len(sigs) > 1:
        mixed.append(key)          # exact cluster that is not semantically homogeneous

total = sum(len(m) for m in exact.values())
print(f"{len(exact)} exact -> {len(structural)} structural -> {len(semantic)} semantic clusters")
for primary, members in sorted(semantic.items(), key=lambda kv: -len(kv[1])):
    variants = len({m for m, _ in members})
    print(primary, f"{len(members) / total:.1%}", f"{variants} modifier variants")
print("exact clusters split by the semantic signature:", len(mixed))
```

## 7. Robustness analysis

| Perturbation | R1 | R2 | R3 |
|---|---|---|---|
| Ignore all O2O qualifiers | unchanged | unchanged; R2+ degrades to R2 | unchanged only because of the E2O fallbacks |
| Ignore external objects | unchanged | T1 absorbs X5 and X6 (equals R4) | S1 absorbs X5 and X6; S3 and S4 vanish |
| Collapse repeated labels | A1 absorbs X3, and also X4 under set-style collapse | unchanged if object sets are united | unchanged |
| Pack/Dispatch as partial order | unchanged | unchanged on these eight | unchanged |
| Payment count as amount | A3 loses its last event, stays distinct | T3 changes shape, stays distinct | unchanged; S2b loses only the instalment modifier |

**Ignoring qualifiers.** X7 remains S5 solely because Dispatch lists I72 against a package containing I71 and I72; without that E2O detail it merges into S1. X8 keeps S6 through its Return and Inspect labels and I82 being packed twice. X4 loses the "partial" flag, so instalments cannot be told apart from a duplicate payment.

**Collapsing repeated labels.** Consecutive collapse merges X3's two Pack events, so X3 joins A1. A first-occurrence collapse leaves only X8 distinct from X1–X7. R2 and R3 are unaffected as long as collapsing merges events but keeps objects, because multiplicities live in the objects.

**Partial order.** No assignment changes: X3 and X4 differ in the number of Dispatch events and Delivery objects, not merely in interleaving. The interpretation sharpens: X4's two Pack-then-Dispatch chains become concurrent, X3 becomes a join, and X8's chains stay causally linked through I82 and D81. Caveat: under a purely object-induced order, invoicing is concurrent with logistics, so an invoice-before-dispatch violation would be invisible.

**Payment as attribute.** The X3/X4 distinction then rests on delivery consolidation alone, which supports keeping instalments out of the primary key. Overall, ignoring external objects is the most damaging perturbation: two of six semantic clusters vanish.

## 8. Limitations and recommendation

| Purpose | Recommended level | Why |
|---|---|---|
| Compliance monitoring | R2+ (exact, qualifier-aware) | A false merge is the costly error: one extra Order on an invoice or one removed item is the finding. Fragmentation is acceptable. |
| Operational segmentation | R3 primary key (S1–S6) | Classes map to different handling and stay populated as item counts vary. |
| Root-cause analysis | R3+ as the outcome label, contrasted with R4 and R2po | Executions that are R4-equal but R3-different isolate the effect of sharing; the partial order exposes causal chains such as X8's. |
| Descriptive reporting | R1 with the R3 breakdown overlaid | Label variants are what audiences recognize, but A1 alone would report five of eight executions as the standard path when only two are clean. |

No single notion serves all four purposes, because they price errors differently: compliance cannot tolerate false merges, segmentation cannot tolerate hundreds of singleton classes, root-cause analysis needs contrasts between levels, and reporting needs recognizability. The relations are also not totally ordered by refinement (R1 and R3 are incomparable), so no level dominates.

Limitations:
- σ uses a configured vocabulary (reverse-logistics labels, qualifier names); a new exception type is invisible until added.
- Merging X3 and X4 is a design choice; moving the delivery or payment modifier into the primary key is a one-line change.
- In real logs externality must be derived from a chosen lead object, and that derivation can be wrong.
- Eight executions show no class frequencies; on real data, check that coarse classes are homogeneous in outcome measures.
