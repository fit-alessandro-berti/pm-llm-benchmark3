# 1. Objectives and constraints  

Safety / compliance (hard)  
1. Security Review  Skill 3, or Skill 1–2 only under supervision by R7_Gita or R8_Hugo.  
2. Final Approval  Skill 2–3 (Skill 1 may only prepare drafts).  
3. No high-priority or urgent case is executed by Skill 0–1 without supervision.  
4. Max. 4 new assignments per resource in one decision batch.  
5. Do not add work to resources with overtime-risk = “high”, unless the case is urgent and no safer option exists.  
6. For high-complexity & high handover-cost cases, keep the current owner unless his/her skill < 2 and no supervision possible.  
7. Quality Check can be batched only if priority  normal and SLA > 24 h.  

Optimisation (soft, to be balanced)  
a. Minimise expected SLA violations (urgency).  
b. Minimise expected rework / appeals (skill match & continuity).  
c. Balance workload (open-case count and remaining hours).  
d. Reserve specialist capacity where it is the bottleneck (resilience).  
e. Deliver at least 20 % of normal/low-priority cases to the holder’s documented training priority.  
f. Minimise handovers, but not at the expense of rule 1–3.  

# 2. Assignment policy  

Pseudocode (single decision batch)

```
Input: queue, resource_table, parameters
Output: assignment_list   # list of (case, worker, [supervisor])

1. Pre-processing
   For each resource r:
       capacity_score  = hours_remaining_today(r) / avg_handling_time
       overload_flag   = (overtime_risk(r) == 'high')
   For each case c:
       c.sla_score     = max(0, 1 - (sla_time_remaining(c)/sla_threshold(c.priority)))
       c.complexity    = case_complexity(c)
       c.handover_pen  = handover_cost_band(c)

2. Eligible resource set  
   For each (case c):
       R_eligible = { r | skill_level(r, c.required_skill)  required_min(c)
                      AND new_assignments(r) < 4
                      AND (NOT overload_flag(r) OR c.priority in {urgent,high}) }
       If R_eligible is empty and supervision_rule exists:
           Add pairs (trainee,supervisor) that satisfy the rule.

3. Scoring  
   For every candidate k = (r) or (r,supervisor) in R_eligible:
       skill_score   = f1(skill_level(r, c.skill))        # 0…1
       continuity    = 1 if current_owner(c)==r else 0
       handover_cost = (1-continuity) * handover_pen(c)
       workload_pen  = g1(open_cases(r), capacity_score(r))
       training_boost= 0.15 if (c.prioritynormal AND
                                 training_priority(r)==c.required_skill) else 0
       resilience_boost = 0.1 if (bottleneck_skill(c.skill) AND
                                  skill_level(r,c.skill)<3) else 0
       total_score =  0.35*sla_score(c) \
                    + 0.25*skill_score \
                    + 0.15*continuity \
                    + 0.10*training_boost \
                    + 0.05*resilience_boost \
                    - 0.10*workload_pen \
                    - 0.10*handover_cost
   Select candidate with highest total_score.
   If tie: pick lower open-cases, then more remaining hours, then random.

4. Post-checks  
   • Verify rules 1–7 again; if violated back-track to next best candidate.  
   • Ensure 20 % of normal/low cases went to training assignments; if not, swap lowest-risk cases to meet quota.  

5. Output assignment_list.
```

Important exception handling  
• If no eligible worker exists: route to team lead with flag “manual escalation”.  
• If supervisor is assigned, the supervisor only receives a “review” sub-activity (does not count towards the 4-limit).

# 5. Explanation to workers  

“Every two hours the system allocates the waiting cases.  
1. Urgent work is assigned first, so we do not miss SLAs.  
2. If you already own the case and have the right skill level, you keep it – this avoids unnecessary hand-offs.  
3. Security Reviews and Final Approvals always stay with qualified staff; trainees can help only when a named supervisor is available.  
4. Nobody receives more than four new cases per round, and we try not to add work to colleagues who are already at overtime risk.  
5. At least one in five normal cases is used for the training plans you agreed with your leads; a senior colleague is scheduled as reviewer.  
6. When a tie occurs, the system chooses the colleague with fewer open cases and more time left in the day.  

You will always see who your reviewer is (if any) in the “Supervisor” column. If the assignment looks wrong, call the team lead – the rule-set is transparent and can be overridden when justified.”

# 6. Process-mining audit indicators  

1. Handover frequency = events where org:resource changes / total activities  
2. Reassignment count per case (mean, stdev)  
3. Skill mismatch rate = activities executed by skill 0–1 without supervision  
4. Workload distribution Gini index on open cases per resource (daily)  
5. Overtime risk exposure =  activities executed by “high” overtime workers  
6. SLA misses before/after assignment (pm4py.insert_case_service_waiting_time)  
7. Rework & appeal rate after assignment (flag loops / extra “Appeal” activities)  
8. Training assignment share = training-labelled cases / normal+low priority cases  
9. Specialist bottleneck indicator = queue length for skills level 3 resources  
10. Policy deviation log = #cases where discovered assignment  rule-based expected (can be mined via pm4py.get_variants on “assignment_reason”)
