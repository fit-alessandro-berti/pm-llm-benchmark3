**Assumption A1:** “Physical concurrency plausible” means more than one case can be in active service on the named resource at the same wall-clock time under that top explanation.  
**Assumption A2:** Confidence is epistemic (pattern + context fit), not statistical sample-size confidence.

# 3. Consequences for performance analysis

**G1 (simultaneous batch on fixture)**  
- **Waiting:** If queue_arrivalstart is used, waiting is roughly correct (items wait until fixture cycle). If discovery treats four starts as four independent busy intervals, waiting of “others” can be mis-ordered.  
- **Service:** True batch service  3 min wall-clock for the group; per-case attribution of 3 min each is OK for sojourn if parallel, but **summing** four 3-min services double-counts capacity.  
- **Utilization:** Robot busy ~3 min once, not 12 min. Uncorrected logs **inflate utilization × batch size**.  
- **Bottleneck:** Overstates RBT-7 load; understates need for fixture-level capacity metrics.

**G2 (common begin, separate completes)**  
- **Waiting:** queue10:00 includes setup synchronization; early arrivals look longer-waiting than late ones even if inspection order is fair.  
- **Service:** Measured service = 8…27 min from common start; **inflates** early cases’ service (includes others’ work after shared begin) if work is actually serial after the button.  
- **Utilization:** One inspector; overlapping open intervals from common start **overstate multitasking**.  
- **Bottleneck:** Surface inspection looks slower/more loaded than true touch time.

**G3 (work then folder submit)**  
- **Waiting:** If waiting = arrivalstart, starts may be usable; if arrivalcomplete, waiting **inflates** by deferred submit.  
- **Service:** completestart **mixes true review + idle until folder submit**; late-started cases show tiny service (11:24–11:30), early ones huge — **distorts** service distribution.  
- **Utilization:** Resource appears busy until 11:30 for all; may be OK as “folder open” but not as effort.  
- **Bottleneck:** Release review completion spike at 11:30 looks like a capacity cliff; false synchronization.

**G4 (serial chain)**  
- Little bias if intervals trusted: waiting  arrivalown start; service  4 min; utilization  busy fraction of T-D; bottleneck detection healthy.  
- Mild risk: calling the chain a “batch” in PM4Py may tempt batch-capacity corrections that are unnecessary.

**G5 (overlaps + pool)**  
- **Waiting:** Unclear who worked which case; pool start times may be OK for case sojourn if starts real.  
- **Service:** Overlapping intervals on one resource ID make **per-resource service sum &gt; wall clock**  impossible utilization unless multiplicity allowed.  
- **Utilization:** Either **&gt;100%** (if one identity) or under-specified (if up to 3).  
- **Bottleneck:** analyst_pool looks overloaded or chaotic; cannot rank true headcount need without badge data.

**G6 (bulk close at 17:00, zero duration) — dual bias**  
- **Waiting inflated:** Using complete (or start) at 17:00 as the service instant makes waiting = arrival17:00, i.e. up to ~3 hours, even if tickets were actually closed earlier in the afternoon.  
- **Service near-zero:** start=complete  service time 0 (or 1 min precision noise). Throughput events clump at shift end.  
- **Utilization:** T-F appears idle all day then instantaneous burst; or 0 busy time if zero-length events ignored.  
- **Bottleneck:** False afternoon queue explosion; hides real close workload; conformance “late close” mass violation.  
- **Mechanism:** Logging time substitutes for execution time  **sojourn absorbed entirely into waiting**, service stripped to zero. This is the canonical “inflated waiting + near-zero service” pattern.

**G7 (15-minute coarsening)**  
- **Waiting:** Starts snapped to 14:00 can **understate** wait for post-14:00 arrivals (14:01–14:11 stamped start 14:00  negative or zero wait) and distort pre-boundary cases.  
- **Service:** All get exactly 15 min; true short/long jobs censored  variance collapse, mean biased to bin width.  
- **Utilization:** Block of full overlap on T-G for 15 min ×5 looks like 5× capacity or one batch; both wrong under pure rounding.  
- **Bottleneck:** Spurious batch bottleneck at quarter-hours; MES grid artifacts dominate.

**G8 (sequential drain after safety window)**  
- **Waiting:** Large wait from 15:00-arrivals until 15:38+ is **real queueing if safety blocked work**, but clock skew caveat means absolute waits uncertain.  
- **Service:** ~7 min chain appears reliable (scanner).  
- **Utilization:** T-H busy after 15:38; idle/blocked before — if safety not modeled, idle looks like low demand.  
- **Bottleneck:** Repair triage may be blamed for long waits that are **upstream safety/downtime**; sequential pattern after release is healthy capacity drain.

```python
def intervals_overlap(s1, e1, s2, e2):
    return (s1 < e2) and (s2 < e1)

def pairwise_overlap_rate(g):
    """Fraction of unordered pairs with strict time overlap (same resource group)."""
    recs = list(g[["case", "start", "complete"]].itertuples(index=False, name=None))
    n = len(recs)
    if n < 2:
        return 0.0
    ov = 0
    tot = 0
    for i in range(n):
        for j in range(i + 1, n):
            tot += 1
            _, s1, e1 = recs[i]
            _, s2, e2 = recs[j]
            if intervals_overlap(s1, e1, s2, e2):
                ov += 1
    return ov / tot if tot else 0.0

def adjacency_rate(g, tol_sec=1.0):
    """Among consecutive by start time, fraction where next.start  prev.complete."""
    gg = g.sort_values("start")
    if len(gg) < 2:
        return 0.0
    ends = gg["complete"].values
    starts = gg["start"].values
    adj = 0
    for i in range(len(gg) - 1):
        delta = abs((starts[i + 1] - ends[i]) / np.timedelta64(1, "s"))
        if delta <= tol_sec:
            adj += 1
    return adj / (len(gg) - 1)

def equality_groups(series):
    return int(series.value_counts().max()) if len(series) else 0

print("\n=== Overlap rate by resource id ===")
for res, g in raw.groupby("resource"):
    print(f"  {res}: pair_overlap={pairwise_overlap_rate(g):.2f}, n={len(g)}, "
          f"sum_svc/wall={g['service_sec'].clip(lower=0).sum() / max((g['complete'].max()-g['start'].min()).total_seconds(),1):.2f}")
```

**Interpretation note (expected runtime behavior):** With fine `merge_distance` (0–60s), G1 tends toward simultaneous batches; G2 start batches; G3/G6 end batches; G4/G8 sequential; G5 concurrent/simultaneous-overlap styles; G7 may look simultaneous only because of 900s bins—large `merge_distance` (900) merges aggressively and can create false mega-batches. Pandas heuristics above are the control against over-trusting PM4Py category names.

# 5. Robustness and alternative explanations

**Resource IDs trusted vs shared**
- **Trusted:** G5 overlaps  true concurrency/multitasking and utilization may exceed 1.0  need multi-server model. G1–G4, G6–G8 keep single-server semantics.
- **Treated as shared accounts:** G5 becomes primarily a **logging identity collapse**; cannot estimate headcount utilization; overlaps are not proof of one person multitasking. `analyst_pool` context already forces this reading as co-primary. No other cluster has explicit pool semantics; forcing “shared account” on T-B/T-C/T-D would **undermine** strong UI/device explanations without evidence.

**Timestamps exact vs interval-censored by stated precision**
- **Exact:** G1 identical 09:00–09:03 is strong simultaneous batch; G4/G8 chains are crisp; G2/G3 minute equality is still informative.
- **Censored:** Each stamp is an interval of width `precision`.  
  - G7 (15 min): start  [13:45,14:15] style ambiguity (rule undocumented)  **identical stamps are almost non-identifying**; simultaneous batch vs serial jobs inside the bin are not separable from data alone. Negative waits for arrivals after 14:00 are censoring artifacts.  
  - G2/G3/G6 (1 min): common ends/starts could differ by &lt;60s physically.  
  - G1/G4/G8 (1 s): conclusions stable under censoring.

**At least three patterns with multiple physical explanations**

1. **Identical start and end (G1 vs G7):**  
   - G1 + fine PLC + fixture capacity  genuine simultaneous batch.  
   - G7 + 15 min MES  pure coarsening (or coarsening on top of unknown truth).  
   Same temporal equality pattern; **precision and source context decide**.

2. **Common start, staggered ends (G2):**  
   - UI “begin group”  start batching / common setup.  
   - Alternatively: true parallel inspection with synchronized clock-in only.  
   - Or coarse minute stamp hiding staggered true starts.  
   Completes every ~6–7 min lean serial-after-common-start, but parallel multi-person is not fully ruled out without staffing data.

3. **Common end, staggered starts (G3 vs G6):**  
   - G3: real work then bulk form submit (end batching).  
   - G6: no recorded real service at all (EOD bulk entry, zero duration).  
   Same “end equality” discovery class; **service duration and source type** separate operational bulk completion from pure logging batch.

4. **Adjacent non-overlapping chain (G4 vs G8):**  
   - Both sequential execution.  
   - G8 additionally admits **queue accumulation after capacity loss** (safety window) as the waiting-time story; G4 does not need downtime.  
   Sequential batch discovery alone does not encode the outage.

5. **Overlaps on one resource id (G5):**  
   - Multiple analysts on shared_VDI.  
   - Single analyst multitasking.  
   - Stale session / delayed recorded starts.  
   Identity reliability dominates.

# 6. Data-collection redesign

Prioritized (highest impact first):

1. **Separate execution vs recording times (mandatory)**  
   - Capture true `started_at` / `completed_at` at the workstation.  
   - Keep `recorded_at` as DB insert only (as now).  
   - Ban silent backfill that copies submit time into start/complete (fixes G6-class bias).

2. **Group / batch / fixture identifiers**  
   - RBT-7 fixture cycle id; T-B “begin group” id; folder id for T-C reviews.  
   - Enables physical batch vs logging batch distinction without guesswork.

3. **Resource / badge identity**  
   - Replace or augment `analyst_pool` with badge-level actor while allowing role=pool.  
   - Flag shared accounts explicitly in a `resource_reliability` field.

4. **Source clock discipline**  
   - NTP sync across PLC, tablet, scanner, safety system, MES.  
   - Store `clock_id` and estimated skew; G8 safety vs repair ambiguity needs this.

5. **Workstation capacity & concurrency metadata**  
   - Max simultaneous items (fixture=4), number of active sessions, multi-server multiplicity.  
   - Prevents utilization inflation on batches and pools.

6. **Pause / resume / blocked events**  
   - Safety-check, downtime, setup, “folder open” as first-class lifecycle.  
   - Separates G8 queue-after-loss from slow service; separates G3 think time from submit lag.

7. **Timestamp precision & rounding metadata**  
   - Publish precision **and** rounding rule (floor/ceil/nearest) per source.  
   - Legacy MES must not silently snap without provenance; prefer raw epoch before binning.

8. **Queue_arrival already good — extend with upstream buffer state**  
   - Keep upstream stamp; add buffer occupancy so batch load vs arrival stagger is visible (G1).

9. **Reject zero-duration completes in operational paths**  
   - Validation rule: if `complete == start` on bulk forms, mark `lifecycle_quality=logging_only` and exclude from default service KPIs.

# 7. Final adjudication

**High confidence (usable for careful performance analysis with stated semantics)**  
- **G4:** Serial single-piece flow; intervals trustworthy; minimal correction.  
- **G1:** Genuine simultaneous batch on RBT-7; analyze at **fixture/cycle** level for utilization; per-case service  cycle time is OK for sojourn, not for summing capacity.  
- **G6:** High confidence it is **logging bulk entry**, not execution; pattern interpretation is clear.

**Exclude or interval-censor in queue / service analysis**  
- **G6:** Exclude from service-time and utilization; waiting to 17:00 is not operational wait unless independently validated. Treat as compliance/logging process only.  
- **G7:** Interval-censor all MES times to 15-minute uncertainty; do **not** interpret identical stamps as simultaneous work; avoid fine-grained bottleneck ranking on T-G.  
- **G3:** Do not use shared `complete` as true per-case end for service or waiting-to-completion KPIs without correction; starts may be partially usable.  
- **G2:** Do not treat common `start` as independent per-case start for multi-resource busy-time sums; service from common start biases early cases.

**Require operational validation before performance conclusions**  
- **G5:** Need badge-level identity and headcount before utilization or multitasking claims.  
- **G8:** Validate safety-system vs scanner clock alignment and whether triage is blocked during 15:00–15:35; until then, long waits are **hypotheses** (downtime queue vs late start preference).  
- **G2:** Confirm whether work after “begin group” is serial one-person or multi-item parallel.  
- **G3:** Sample actual review touch time vs folder-submit delay (observation or richer UI events).

**Summary stance:** Identical timestamps are not proof of simultaneous physical work. PM4Py batch categories should be read as **temporal signatures** to be matched against source precision, lifecycle integrity, capacity, and identity reliability. Strongest actionable split: **trust G4 (and G1 at batch grain); rewrite G6/G7 before KPI use; field-check G2/G3/G5/G8.**
