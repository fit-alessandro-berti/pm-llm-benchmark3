## 1. Conformance semantics  

The following mutually-exclusive labels are used in the sequel.

1. forbidden behaviour  
   A relation that the norm explicitly marks “forbidden”. Any occurrence is a prima-facie violation because the norm is closed-world for such relations.

2. missing mandatory behaviour  
   A relation that is “mandatory” in the norm but is absent where its scope applies. Because the norm is closed-world for its mandatory columns, absence is non-conformant unless we can show that the scope did not in fact apply.

3. unexpected but unregulated behaviour  
   A relation that is not mentioned in the norm or that the norm labels “unspecified”. Open-world assumption applies; no non-conformance is inferred, but it may still be business-relevant.

4. typical-pattern absence  
   A relation labelled “typical” appears less often than expected. This is not a violation but may indicate inefficiency or risk exposure.

5. likely data-quality error  
   The relation conflicts with domain knowledge outside the norm or is supported by an explicit data-quality comment in the brief.

6. abstraction mismatch  
   The analytic abstraction (e.g., directly-follows) is stricter than the business rule (“eventually”). Missing arcs may therefore be benign.

7. insufficient evidence  
   Counts are too small, or we lack event detail, to decide between (2), (5) and (6).

Closed-world assumption: only “forbidden” edges and the mandatory columns are closed; everything else is open. Therefore, absence of an edge that is merely unspecified does NOT imply non-compliance.  

Open-world assumption: unspecified and typical relations may occur without limit unless they collide with a forbidden rule.

## 3. Detailed reasoning by model family  

### OC-DFG  
• Establishes which activities directly follow each other for the same object.  
• Cannot see events that intervene, so “eventually” rules are approximated.  
• Counts (“98 of 100”) suggest high but not full coverage; absence may stem from skipped scans or abstraction mismatch.  
• Example danger: N1 requires that every created order is validated eventually. Interpreting this as “directly-follows” flags the 2 Orders although a Review event in between would be perfectly compliant.

### OTG  
• Captures structural relationships between object types, regardless of time.  
• Enables “born together” / “interact” obligations.  
• Cannot verify sequencing or multiplicity within individual cases.  
• Weight 1 for `(Order, object_cobirth, Payment)` violates the forbidden T6 rule unequivocally; no abstraction escape is possible because co-birth is a single fact.

### ET–OT  
• Binds event types to the objects they must reference.  
• Checks completeness inside single events.  
• Sensitive to missing foreign keys and incorrect event tagging.  
• Dual obligations (E7 & E8) show how a relation can be fine under one object (Payment present) yet incomplete under another (Invoice missing).  
• The gap in Dispatch  Delivery exposes the difference between event attribute (carrier ref) and object relation: conforming at raw data field, non-conforming in graph.

Forbidden (must not exist)

Typical (desirable)  
• Validate  Close Order (N2) – 83/100 (17% deviation).  
• Issue Invoice  Record Payment (N5) – 92/110 (open credit & write-off explain shortfall).  
• (Invoice, interaction, Payment) (T3) – 92 edges (expected).  

Unregulated / unspecified  
• Reopen  Close Order (N6).  
• (Order, interaction, Customer) (T4).  
• (Order, interaction, RiskCase) (T5).  
• (Package, codeath, Delivery).  
• Manual Compliance Review links.

Condition-dependent buckets  
• Create  Validate gaps move from “missing mandatory” to “conforming” if any intervening event belonging to validation path is found.  
• Record Payment w/o Invoice moves from “missing mandatory” to “conforming” if finance classifies the event as unapplied cash.

## 5. PM4Py conformance code sketch
```python
import pm4py

# --- Discover observed models ---
ocdfg_obs = pm4py.discover_ocdfg(ocel)
otg_obs   = pm4py.discover_otg(ocel)
etot_obs  = pm4py.discover_etot(ocel)

# --- Normative models are pre-built and carry extra metadata -------------
# Each edge carries .status in {"mandatory","forbidden","typical","unspecified"}
# Those metadata are stored outside the bare graph objects.

# --- Run PM4Py built-in conformance (raw diagnostics) --------------------
ocdfg_raw_diag = pm4py.conformance_ocdfg(ocel, ocdfg_obs, norm_ocdfg)
otg_raw_diag   = pm4py.conformance_otg(ocel, otg_obs, norm_otg)
etot_raw_diag  = pm4py.conformance_etot(ocel, etot_obs, norm_etot)

# --- Semantic post-processing layer --------------------------------------
def classify_edge(edge, norm_dict, raw_violation_set):
    """
    edge : tuple identifying the relation
    norm_dict : mapping edge -> status
    raw_violation_set : result from PM4Py indicating presence/absence
    """
    status = norm_dict.get(edge, "unspecified")
    present = edge in raw_violation_set.get("present", set())
    missing = edge in raw_violation_set.get("missing", set())
    
    if status == "forbidden" and present:
        return "forbidden_behaviour"
    if status == "mandatory" and missing:
        return "missing_mandatory"
    if status == "typical" and missing:
        return "typical_pattern_absence"
    # open-world fall-back
    return "unregulated"

semantic_diag = {
    "ocdfg": {e: classify_edge(e, norm_ocdfg, ocdfg_raw_diag) for e in ocdfg_raw_diag["checked_edges"]},
    "otg":   {e: classify_edge(e, norm_otg,   otg_raw_diag)   for e in otg_raw_diag["checked_edges"]},
    "etot":  {e: classify_edge(e, norm_etot,  etot_raw_diag)  for e in etot_raw_diag["checked_edges"]},
}

# Diagnostics are now available in `semantic_diag` without overwriting
# the lower-level PM4Py details.
```

## 6. Norm-completeness assessment  

1. Re-closure after Reopen Order  
   • Risk: inconsistent stock if closure logic differs.  
   • Clarify: add “typical” `Reopen  Close` path with counting guard.  

2. Missing tolerance for eventual vs directly-follows in N1, N4  
   • Risk: false positives; audit fatigue.  
   • Clarify: define “within five business events” not “directly”. Status: mandatory.  

3. Unapplied cash handling in E8 and T3  
   • Risk: legal misstatement of revenue.  
   • Clarify: add event subtype “Unapplied Cash” and mark Invoice link “unspecified” for that subtype.  

4. Sensor data linkage  
   • Risk: privacy and segregation breaches.  
   • Clarify: explicitly forbid any telemetry-finance join across all object types (forbidden).  

5. Package codeath with Delivery  
   • Risk: potential miscounting of shipped items.  
   • Clarify: declare it “typical” if the business event is “Delivery Confirmation”.  

6. RiskCase interaction with Order  
   • Risk: KYC gaps if forgotten.  
   • Clarify: add “typical” interaction edge `(Order, object_interaction, RiskCase)` for high-value orders.

## 8. Uncertainty statement  

Robust conclusions  
• `Cancel Order  Dispatch Package` and Order-Payment cobirth violate explicit forbidden rules.  
• Sensor Heartbeat–Invoice link is almost certainly a join error.

Dependent on norm incompleteness  
• Missing Create  Validate and Pack  Dispatch arcs may be compliant if the rule is “eventually” rather than “directly”.  
• Record Payment without Invoice hinges on whether the event is unapplied cash.

Dependent on suspected data issues  
• Missing Delivery relations; Add Item without Order; scanner omissions.

Undecidable from summaries alone  
• Whether the forbidden edges share the same real-world Order instance (key collision).  
• Whether open invoices will still be paid within agreed terms.  
• Whether codeath edges hide any shipment anomalies.

Complete event logs, timestamps, and domain metadata are required for final judgement.
