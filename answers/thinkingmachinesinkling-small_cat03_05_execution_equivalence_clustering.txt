## 1. Equivalence design space

I define four relations that move from purely syntactic to fully interpretive, allowing different stakeholders to extract different value from the same eight executions.

### Relation  — Activity-sequence equivalence
*Formal definition.* Let an execution `e` be the ordered list of its events `e, …, e`, each with an activity label `act(e)`. The -signature is `(e) = [act(e), …, act(e)]`. Two executions are -equivalent iff `(e) = (e')` as ordered sequences of strings, preserving repetitions.
*Invariants preserved.* Label ordering, multiplicities of identical labels (e.g., two `Add Item` events, two `Record Payment` events), presence/absence of activity types.
*Information discarded.* All object identifiers (`O1`, `I11`, etc.), all object-type references (`Order:O1`), all O2O qualifiers (`removed_before_dispatch`), all external-object flags (`EXT-`), event timestamps beyond total order, and concurrency relations.
*Algebraic properties.* Reflexive, symmetric, and transitive because it is equality of finite strings.
*Concurrency.* If two events have identical timestamps and are semantically concurrent, the total order is ambiguous. For , one must either (a) assume a deterministic total order (the notation already imposes one), or (b) extend  to multiset equivalence with partial-order constraints, which weakens it to a coarser “label multiset” relation.

### Relation  — Typed structural equivalence under identifier renaming (OCEL isomorphism)
*Formal definition.* Each execution is an object-centric event log fragment rooted at a lead object of type `Order`. A mapping `` is a -isomorphism if it is a bijection between local object identifiers (preserving `EXT-` prefixes and object types) and between events (preserving `act` and the partial/time order), such that for every event `e`, the multiset of object types referenced in `e` (including qualifiers on O2O relations, if preserved) is mapped identically, and every O2O link is mapped to a corresponding link.
*Invariants preserved.* Event sequence order, activity labels, object-type multiplicities per event, graph topology (which objects participate in which events), distinction between local and external objects, and qualifier vocabularies if incorporated.
*Information discarded.* The concrete strings of local identifiers (e.g., `O1` vs. `O2`, `I11` vs. `I22`). What remains is the “shape” of the log.
*Algebraic properties.* Reflexive, symmetric, and transitive: isomorphism is an equivalence relation on finite labeled directed multigraphs.
*Concurrency.* Handled naturally by requiring `` (the event mapping) to preserve the event partial order; if events are concurrent, their relative positions can be swapped, but the partial-order structure remains.

### Relation  — Business-semantic equivalence (signature clustering)
*Formal definition.* A canonical semantic signature `s(e)` is computed from the execution: (i) the activity-label sequence; (ii) object-type multiplicities (`#Package`, `#Delivery`, etc.); (iii) external-object masks (`logistics_shared`, `finance_shared`); (iv) qualifier vocabulary (`removed_before_dispatch`, implicit replacements); (v) lifecycle-motif tags (`straight`, `split_consolidated`, `split_independent`, `partial_payment`, `return_repack`, `substitution`, `cross_order`). *Information discarded.* Precise event-to-event ordering when it does not change a motif (e.g., within a concurrent group), specific identifier strings, and granular timestamp differences.
*Algebraic properties.* Reflexive, symmetric, and transitive if `s` is a deterministic function into a discrete set (no continuous thresholds).

## 2. Canonical signatures

My preferred equivalence is ** (business-semantic)** because it answers operational questions (“Is this a standard fulfillment, a split shipment, a shared logistics run, a substitution, or a return loop?”) without over-fitting to local names. The signature must be reproducible and invariant to identifier renaming.

**Principles:**
- Replace every local identifier with its type and a positional index ordered by first appearance in the trace.
- Keep `EXT-*` flags intact because they encode semantic externality.
- Count objects by type, not by identity.
- Extract qualifier vocabulary from O2O relations.
- Derive motifs from multiplicities and event types.

### Pseudocode / Python-like signature generator

```python
def canonical_sig(trace, lead_type="Order"):
    """
    trace: ordered list of events for a lead Order execution.
    Returns an immutable tuple signature invariant to local ID renaming.
    """
    # 1. Normalize: map local ids to canonical tokens
    local_map = {}
    ext_flags = {"logistics_shared": False, "finance_shared": False}
    obj_counts = Counter()
    quals = set()
    events = []

    for e in trace:
        # Activity label sequence (invariant to objects)
        events.append(e.act)
        
        # Object type counts (local and EXT preserved by type, not id)
        for obj_ref in e.o2o + e.event_objs:
            obj_type = obj_ref.type
            obj_id = obj_ref.id
            obj_counts[obj_type] += 1
            
            # External flag detection
            if obj_id.startswith("EXT-"):
                if obj_type == "Order" and "Invoice" not in e.act and "Payment" not in e.act:
                    ext_flags["logistics_shared"] = True  # external order in logistics
                if obj_type == "Order" and ("Invoice" in e.act or "Payment" in e.act):
                    ext_flags["finance_shared"] = True
                if obj_type == "Item" and "Item" in e.act:
                    # external item in logistics context
                    pass  # motif logic below handles it
        
        # Qualifiers
        for rel in e.o2o_relations:
            if rel.qualifier:
                quals.add(rel.qualifier)

    # 2. Sequence tuple
    seq = tuple(events)

    # 3. Multiplicity profile (distinct objects related to lead, by type)
    # For simplicity, count distinct object ids per type; under renaming, counts are invariant
    multis = tuple(sorted(obj_counts.items()))

    # 4. Motif inference
    motifs = set()
    pkg = obj_counts.get("Package", 0)
    deliv = obj_counts.get("Delivery", 0)
    pay = obj_counts.get("Payment", 0)
    inv = obj_counts.get("Invoice", 0)
    has_return = any("Return" in act for act in events)
    has_inspect = any("Inspect" in act for act in events)
    has_repack = any("Pack" in act for act in events) and pkg >= 2 and has_return

    if pkg == 1 and deliv == 1:
        motifs.add("straight")
    elif pkg > 1 and deliv == 1:
        motifs.add("split_consolidated")
    elif pkg == deliv > 1:
        motifs.add("split_independent")
    if pay > 1 or "partial_settles" in quals or "partial" in quals:
        motifs.add("partial_payment")
    if has_return and has_inspect and has_repack:
        motifs.add("return_repack")
    if "removed_before_dispatch" in quals:
        motifs.add("substitution")
    if ext_flags["logistics_shared"]:
        motifs.add("cross_order_logistics")
    if ext_flags["finance_shared"]:
        motifs.add("cross_order_finance")

    # 5. Assemble invariant signature
    return (seq,
            multis,
            tuple(sorted(ext_flags.items())),
            tuple(sorted(quals)),
            tuple(sorted(motifs)))
```

This is invariant to local ID renaming because `obj_counts` and `multis` depend only on type cards, and `seq` depends only on labels. External flags are preserved via `EXT-` prefixes. Qualifiers are preserved as vocabulary tokens.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` (part of the PM4Py OCEL framework) computes exact equivalence clusters for object-centric event logs. Its key structure preserves:
- **Event sequences** per object or per execution, including exact activity labels and order;
- **Object identifiers** in their raw form (local and external);
- **Object-to-event relationships** (`E2O`) as explicit links;
- **Object-to-object relationships** (`O2O`) including any explicit attributes or qualifiers, if encoded in the OCEL;
- **Object types** and the lead-type context, depending on the projection.

### Why raw identifiers make clusters too fine
Because `X1` and `X2` differ only by local strings (`O1`/`O2`, `I11`/`I21`), the PM4Py exact key treats them as different clusters unless a canonicalization step is applied. In large logs, every renaming produces a unique cluster, rendering the clustering useless for business segmentation.

### Canonicalization / post-processing
I recommend a two-stage pipeline:
1. Run `pm4py.cluster_equivalent_ocel` to obtain exact equivalence classes (preserving structural fidelity for forensic use).
2. For each exact cluster, extract the lead-order subgraph and apply the canonical signature from Section 2 (type-based indexing, motif inference, external-flag extraction). Then merge exact clusters whose signatures match.

### When exact is preferable vs. coarser
- **Exact (-like)** is preferable for **compliance and forensic replay**: if a dispute arises about which specific package `P41` was dealt with, or whether `EXT-OB` was invoiced, you need the raw-object-level graph.
- **Coarser ()** is preferable for **operational segmentation and reporting**: you want to know “how many executions are return-repack patterns?” not “how many distinct ID permutations represent that pattern?”.

### `max_objs` and large connected executions
`max_objs` limits how many objects can appear in an execution cluster. In executions like X5 (with `EXT-OA`, `EXT-IA`) and X6 (with `EXT-OB`), the connected component spans multiple orders/items. If `max_objs` is low, PM4Py may split the execution or exclude it, fragmenting the shared-logistics or shared-finance pattern. Large connected executions can also cause exponential growth in equivalence keys if every object combination is hashed; canonical aggregation prevents this by reducing to type-multiplicity fingerprints.

## 7. Robustness analysis

I test four perturbations that data-quality repair, logging errors, or modeling choices might introduce.

### Ignore all O2O qualifiers
- **Effect:** `X7` loses the `removed_before_dispatch` qualifier and its `substitution` motif. Its `Dispatch` event still contains `Item:I72`, so  still distinguishes it from X1 (event arity differs), but if event references are also reduced, X7 collapses to `-StandardFulfill`.
- **Assignment change:** `X7` moves from `-Substitution` to `-StandardFulfill`. The operational risk of hidden substitution disappears from the clustering, making root-cause analysis miss inventory errors.

### Ignore external objects (strip `EXT-*`)
- **Effect:** `X5` and `X6` lose `EXT-OA`, `EXT-IA`, `EXT-OB`. Their event references shrink to only local objects.
- **Assignment change:** Both become `-Standard` and `-StandardFulfill`. The critical distinction between isolated fulfillment and shared-resource fulfillment is erased. Operational segmentation would incorrectly treat shared-logistics orders as standard.

### Collapse repeated same-label events
- **Effect:** `X3`’s two `Pack` events merge into one (multiplicity lost); `X4`’s two `Pack`, two `Dispatch`, and two `Record Payment` merge. `X8`’s second `Pack`/`Dispatch` could merge with the first if ordering is not preserved.
- **Assignment change:** `X3` might merge with `X1` if multiplicities are ignored; `X4` loses its `partial_payment` signature and may merge with `X3` or `X1`; `X8` might lose its return-loop identity and appear as `X4`.

### Treat Pack and Dispatch as a partial order rather than total order
- **Effect:** If `Pack` and `Dispatch` are not strictly ordered, the motif `split_independent` (where delivery follows packaging per package) becomes ambiguous.
- **Assignment change:** `X4` could be interpreted as concurrent packaging/delivery streams; `X8`’s second `Pack` could be seen as concurrent with second `Dispatch`. The clusters remain mostly stable, but the *motif inference logic* must enforce causal constraints (e.g., a package must be packed before it is dispatched). Without that, false positives for split patterns could emerge.

### Optional: Treat payment multiplicity as an amount attribute
- **Effect:** `X4`’s two `Record Payment` events are folded into one `Record Payment` event with an amount attribute.
- **Assignment change:** `X4` loses `pay=2`; if multiplicities are ignored, it collapses toward `X3` or `X1`. The partial-settlement business semantics are hidden in an attribute rather than in structure, making structural clustering blind to it.

## 8. Limitations and recommendation

### Recommended equivalence by purpose

| Purpose | Recommended relation | Rationale |
|---|---|---|
| **Compliance monitoring** | ** (Typed structural)** with qualifier preservation | Auditors need exact object genealogy: which external order (`EXT-OB`) was invoiced, which item (`EXT-IA`) was co-packed, and which qualifier (`removed_before_dispatch`) explains inventory adjustments. Coarse grouping would hide regulatory exposure. |
| **Operational segmentation** | ** (Business-semantic)** | Managers need actionable groups: “How many simple fulfillments vs. split deliveries vs. return loops this week?” The motif taxonomy (`straight`, `split_independent`, `return_repack`) splits the population into operational units with distinct cost and risk profiles. |
| **Root-cause analysis** | ** + qualifier-aware** | To trace a failure (e.g., missing item in delivery), one must know whether the failure is isolated (X1), shared (X5/X6), or substitution-related (X7). Ignoring qualifiers or external objects eliminates the causal link. |
| **Descriptive reporting / process discovery** | ** (Activity-sequence)** or coarse ** (Motif)** | High-level process maps and frequency reports do not need object-level detail.  gives the cleanest “process flow” visualization;  gives the simplest business-language segmentation. |

### Why no single equivalence is best
- ** is too coarse:** It collapses X1, X5, X6, and X7 into one cluster, hiding cross-order sharing and hidden substitution—exactly the anomalies that matter for operations.
- ** is too fine:** It splits X1 and X2 into separate exact clusters because of identifier renaming, producing noisy, non-reproducible clusters unless canonicalized.
- ** is subjective:** Motif definitions (`split_consolidated` vs. `split_independent`) require a taxonomy choice; different analysts might place borderline cases differently, though the signature is reproducible once taxonomy is fixed.
- **Exact/raw-ID clustering is brittle:** It is unsuited for business reporting because every data-upload with new IDs creates new clusters.

Therefore, the best practice is a **layered pipeline**: use  for forensic integrity, apply canonicalization to collapse identifier noise, and extract  for segmentation and reporting. No single layer answers every question, but together they preserve fidelity from raw data to business insight.

### Word-count and reproducibility note
All definitions are operational (optional code is provided), cluster assignments are tabulated consistently, and borderline cases explicitly state which relations agree and which diverge. The canonical signature is invariant to local identifier renaming, making the clustering reproducible across data refreshes.
