# 2. Process-model consistency checks

A concrete suite, run in CI on every feature release and every explanation batch. Each test names its pass criterion and its limitation.

### A. Prefix-time availability
- **A1 — Truncation-invariance test (decisive, cheap).** Recompute every feature from the log with all events after `t0` deleted, and again after randomly permuting/perturbing those events. *Pass:* value unchanged. Any feature that moves is leaky by construction, regardless of what its name or lineage document claims. This catches `*_total`, `*_anywhere`, `full_trace_variant_id`, `last_resource_role` automatically.
- **A2 — Bitemporal availability assertion.** For each feature, assert `max(event_time, commit_time, valid_from)  t0`. Event time alone is insufficient: a coverage-check payload written 40 minutes later is not available at `t0`.
- **A3 — Snapshot tolerance test.** For `queue_length_at_t0`, assert `snapshot_ts  t0` and `t0  snapshot_ts  max_staleness`. Unit-test the boundary at `t0 ± 5min`; the current ±5 min rule must be one-sided.
- **A4 — Predicate lint + adversarial fixtures.** Static lint of SQL for `<= extraction_date`, `CURRENT_DATE`, `MAX(...) OVER (whole case)`, and non-excluded self-joins. Fixture: insert a prior claim created at `t0 + 1h` and a document uploaded at `t0 + 3h`; `prior_claim_count_before_t0` and the document count must not change.
- **A5 — Degenerate-variance test.** Per horizon, drop zero-variance features. At `t0`, `appeal_so_far`, `document_requests_so_far`, `prefix_variant_id` must be constant; if they are not, raise a leakage alarm rather than shipping the feature.
- **A6 — Label-proximity alarm.** Flag any feature whose single-feature AUC against the label exceeds a threshold, or which is a monotone function of case duration.

### B. Activity-order feasibility
- **B1 — Declarative precedence constraints** (checked per trace, cheap, interpretable): `Appeal` requires a preceding decision in {Partial, Deny}; `Claim Closed` requires a preceding final decision or withdrawal; `Documents Received` requires a preceding `Documents Requested`; `Documents Validated` requires a preceding `Documents Received`; a decision requires a preceding `Damage Assessment Completed`. Report violation counts by constraint and by activity pair.
- **B2 — Alignments against a normative Petri net/BPMN** with an explicit **parallel branch** for fraud investigation. Cost-based alignments give fitness and localize the deviating move (log-move vs model-move). *Limitation:* alignments need a trustworthy total order and complete traces; a deviation is a **triage item**, not a verdict — it may be a data error, a legitimate unmodeled variant (reopen, administrative closure of a duplicate), or a gap in the normative model. Case Z's missing decision before closure must be triaged, not silently "repaired".
- **B3 — Footprint/DFG comparison, with concurrency awareness.** Compare the empirical footprint (causal / parallel / choice / unrelated) to the normative one. *Limitations:* a frequent DFG edge is not a rule — `Claim Closed -> Damage Assessment Completed` could be frequent purely because of timestamp ties; interleaved parallel fraud events manufacture directly-follows edges that are perfectly legal; coarse labels collapse `Documents Requested/Received/Validated` into `DOC`, so `DOC->DOC` self-loops are legitimate cycles, not rework violations. Use frequency only to prioritize investigation.

### C. Same-timestamp ambiguity
- **C1 — Tie census.** Report the rate of identical-timestamp pairs by activity pair and by source system; alert on spikes.
- **C2 — Deterministic ordering policy, in priority order:** (1) reliable ingestion/sequence index; (2) source transaction counter; (3) topological sort constrained by the normative precedence partial order; (4) if still unresolved, mark the trace **order-uncertain**. Never break ties by insertion order, alphabetical label, or row id without documenting it.
- **C3 — Order-robust features.** For order-uncertain traces, compute order-dependent features over the *set of feasible linearizations* and carry an interval (min/max) or abstain. Explanations for such cases must show the ambiguity rather than a single confident attribution — this is exactly Case Z.

### D. Complete-trace detection
- **D1 — Feature manifest contract.** Each feature declares: source table/event, cut semantics (`prefix` / `as-of` / `closure`), mutability class (immutable-at-registration, append-only event-derived, mutable SCD, periodic snapshot), aggregation window, and owner. Any feature declaring `closure` is rejected for all pre-closure horizons.
- **D2 — Lineage graph scan.** Walk the transformation DAG to the raw log; any aggregate without a ` cut` filter, or any join to a current-state warehouse view, fails.

### E. Enabled / impossible / future-possible at `t0`
Replay the prefix to obtain the net marking, then classify every activity referenced anywhere in an explanation. Explanations may assert only **observed** facts; enabled/future-possible activities may appear only as explicitly modal forecasts.

# 5. Recommendations for explanation validation

**P0 — Stop the bleeding (days).**
1. Disable handler-facing explanations and any automated routing driven by this model at the `t0` horizon. Publish a blocked-feature list (duration, appeal flag, document totals, variant id, final team, final decision, last role, current risk score, nightly document snapshot) enforced by a hard admissibility gate in the serving path — fail closed, not warn.
2. Run the truncation-invariance test (A1) across the whole feature catalogue, not just the top-12; the ranking hides leaky features below rank 12 (e.g. employee experience).
3. Review decisions already taken with these scores. If high-risk claims were deprioritized, the model may have caused the breaches it "predicted"; quantify and remediate, and log the incident.

**P0/P1 — Feature-store redesign with bitemporal semantics.**
4. Store `event_time`, `availability_time` (commit/ingest), and `valid_from/valid_to` for every attribute; serve features only through deterministic as-of joins against the cut key `(event_ts, sequence_index)`. Ban current-state warehouse views from training and serving paths.
5. Prefer immutable event payloads over mutable case-header fields; make aggregates event-sourced and append-only; make mutable attributes SCD2 (team, reserve, risk score, employee experience, channel).
6. Publish a feature manifest (cut semantics, mutability class, window, staleness bound, owner) and make it machine-readable so the admissibility gate and the CI tests read the same contract. Fix `prior_claim_count` SQL with an adversarial fixture in the test suite.

**P1 — Prefix-only recomputation and horizon design.**
7. Build a replay harness that reconstructs every feature from the truncated log for each cut and asserts equality with the stored value; block release on any mismatch for immutable features and on any non-zero variance for structurally constant features.
8. Replace the single model with horizon-specific models (`t0`, after documents validated, after damage assessment, after first decision). This is where document cycles, appeals and repeated decisions become legitimate signals, each with its own admissible feature set, its own explainer and its own calibration.

**P1 — Conformance and data quality in CI.**
9. Ship the Section-2 suite as automated checks: declarative precedence constraints, alignments against a normative model with an explicit parallel fraud branch, tie census with alerting, dedupe rules that preserve legitimate reconsideration, and cut-integrity assertions (first coverage check, case not already closed).
10. Negotiate a data contract with the source system for a monotonic sequence index; until then, propagate order uncertainty into features and explanations rather than resolving ties silently.

**P1 — Honest retraining and recalibration.**
11. Retrain prefix-only; expect and report a large drop in discrimination. Benchmark against a transparent baseline (regularized logistic regression on queue state, complexity, elapsed slack, repaired prior-claim count, verified reserve/channel). Prefer the simpler model unless the complex one wins out-of-time.
12. Recalibrate per horizon and per period (isotonic/Platt), re-derive decision thresholds from an explicit cost matrix, and report calibration curves with confidence intervals overall and by subgroup. Verify the explainer's additivity space (margin vs probability) before quoting any contribution.

**P2 — Explanation stability and uncertainty.**
13. Bootstrap/re-seed/re-train and measure top-k rank overlap and sign stability; unstable drivers are demoted or grouped. Use grouped attributions for correlated blocks (region/channel/complexity; the leaky future block, once removed, no longer splits credit).
14. Add counterfactual sanity checks (monotone direction for queue length and elapsed slack within feasible prefix ranges) and an explicit uncertainty/abstention path for order-ambiguous or lineage-unverified cases, as in Case Z.
15. Standardize explanation language: observed facts in the indicative, future activities only in explicit forecast modality, no causal verbs without an identification strategy, and an actionability tag (static attribute / system state / candidate lever) with an owner for each driver.

**P2 — Proxy, fairness and performativity.**
16. Mediation and incremental-lift analysis for region, channel and prior-claim count; substitute measurable operational mediators where they carry the signal. Subgroup calibration and error-rate audit, legal review of proxy use, documented justification for retention or removal. Monitor for feedback loops if scores influence routing; keep a randomized or shadow holdout to preserve an uncontaminated evaluation stream.

**P2 — Drift monitoring and governance.**
17. Monitor schema drift (new/renamed activities, coarse-label collapses), process drift (new DFG edges, tie-rate spikes, constraint-violation rates), feature drift (PSI), calendar/policy regime flags, and label-definition changes. Alert on any single feature whose label separation suddenly jumps — the classic signature of a new leak.
18. Scheduled out-of-time backtests, shadow deployment before promotion, versioned explanation artifacts with lineage snapshots for audit, and a sign-off checklist that requires: A1 pass, manifest completeness, conformance report, calibration report, stability report, and fairness review.
