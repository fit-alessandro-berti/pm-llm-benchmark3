# 2. Benign alternative explanations

### Pattern 1: VendorMaster_Lena & AP_Kim (Fast bank detail changes, high amount share, vendor family V-77x, manual upload)

* **Benign Explanation 1: Bulk Bank Migration Project.**
  Vendor family V-77x transitioned to a new banking platform. To handle high volumes efficiently, AP_Kim and VendorMaster_Lena were assigned as a dedicated processing pair, uploading standardized banking update spreadsheets (`manual_upload`) and prioritizing pending invoice releases.
  * *Evidence to support:* Valid banking change request forms from V-77x signed by authorized vendor officers; a corporate IT/procurement project ticket establishing the V-77x banking migration project; cross-system timestamps showing bank updates matching official banking network notification dates.
  * *Evidence to refute:* No corresponding ticket in IT service management (ITSM); banking details pointing to personal accounts or unverified offshore entities; mismatched signatures on vendor change request letters.
* **Benign Explanation 2: Data Quality & System Migration Artifact.**
  The `manual_upload` tag reflects retroactive logging of approved platform updates. Lena updated the master data based on central ERP records, while Kim processed payments in an external banking interface, leading to compressed event-log timestamps during batch ingestion.
  * *Evidence to support:* DB logs showing the underlying updates were executed days prior; system logs demonstrating batch import scripts running at fixed intervals.
  * *Evidence to refute:* Log timestamps matching exact real-time database write times without automated batch import scripts involved; missing audit trails in the underlying ERP.

### Pattern 2: Buyer_Carla & Approver_Gita / Buyer_Dan & Manager_Hugo (Rapid emergency PO approvals and subcontracting loops)

* **Benign Explanation 1: Established Operational Emergency Protocol.**
  Carla (medical supplies) and Dan (facilities repairs) handle time-critical domain emergencies. Approver_Gita and Manager_Hugo maintain active communication via phone/chat to perform real-time verification before approving transactions instantly in the system.
  * *Evidence to support:* Instant messaging or call logs between buyer and approver at case creation time; independent delivery receipts for emergency goods; formal policy documenting authorized verbal approval followed by immediate system sign-off.
  * *Evidence to refute:* Goods receipt timestamps occurring long after approval or not at all; absence of communication records; orders placed outside operational emergency guidelines for non-urgent items.
* **Benign Explanation 2: Process Redesign / System Assignment Rules.**
  System workflows automatically route urgent cases directly to designated on-call managers (Gita and Hugo). The subcontracting loop ($A \rightarrow B \rightarrow A$) reflects automated re-routing when additional documentation is requested and resubmitted within the purchase request UI.
  * *Evidence to support:* Active ERP routing rule definitions showing explicit auto-assignment logic for `emergency_flag=True`; system edit logs showing document re-attachments.
  * *Evidence to refute:* Workflows manually routed by buyers; cases where emergency flags were added retroactively to bypass approval queues.

### Pattern 3: Retrospective Justifications (Same-person approvals with short cycle times)

* **Benign Explanation 1: Quarter-End Data Entry Reconciliation.**
  Operational emergency approvals granted offline (e.g., verbal or radio approval during weekend incidents) were captured in offline spreadsheets and entered into the audit system in bulk by administrative staff during quarter-close reconciliation.
  * *Evidence to support:* Signed paper exception forms or email approvals predating the quarter-close upload; administrative delegation logs for Temp_Nina or administrative staff performing data entry.
  * *Evidence to refute:* Complete absence of paper or digital authorization pre-dating the upload date; missing physical goods receipts or service completion sign-offs.
* **Benign Explanation 2: Legacy ERP Mapping Error.**
  The legacy system recorded the user completing the administrative "close case" step as the performer of all historical steps in the transaction summary table during data migration into the process mining log.
  * *Evidence to support:* Database schema showing `entered_by` preserving original distinct user IDs while `org:resource` displays the migration user; vendor log export scripts demonstrating user ID fallback rules.
  * *Evidence to refute:* Raw transaction tables in the legacy database showing identical user IDs across all lifecycle steps.

import pm4py
import pandas as pd

# Load and format dataframe
df = pd.read_csv("procurement_event_log.csv")
df['time:timestamp'] = pd.to_datetime(df['time:timestamp'])
df = pm4py.format_dataframe(
    df, 
    case_id='case:concept:name', 
    activity_key='concept:name', 
    timestamp_key='time:timestamp'

# -------------------------------------------------------------------------
# 1. Filtering Four-Eyes Principle Violations

    df, 
    "Change Vendor Bank Details", 
    "Payment Approval"
)

    df, 
    "Emergency Override", 
    "Retrospective Justification"
)

handover_net = pm4py.discover_handover_of_work_network(df)

# Working Together Network

# Subcontracting Network (Identifies A -> B -> A loops)

# 6. Cautious audit-report wording

**MEMORANDUM**

**TO:** Audit Committee / Management  
**FROM:** Internal Audit Team  
**DATE:** October 24, 2023  
**SUBJECT:** Process Mining Analysis & Internal Control Review of Procurement-to-Payment (P2P) Event Logs  

Internal Audit has completed a process mining analysis of the procurement-to-payment event log for the preceding quarter. The objective was to evaluate operational efficiency, process conformance, and the effectiveness of key internal financial controls.

The analysis identified key control exceptions and procedural deviations from normative segregation of duties (SoD) policies. Specifically, 42 cases exhibited dual involvement in purchase order creation and approval, 17 cases lacked independent retrospective justification following emergency overrides, and 9 cases involved administrative bank detail changes followed by payment approvals within the same operational pair (`VendorMaster_Lena` and `AP_Kim`).

It is critical to distinguish formal control exceptions from willful misconduct or fraud. A significant portion of the observed rapid approvals and approval loops is strongly correlated with operational emergency responses in specialized departments (e.g., emergency medical supplies and urgent facilities repairs). Furthermore, data-quality limitations—including mapping table anomalies in legacy ERP extracts and batch spreadsheet ingestion during quarter-close reconciliation—contribute to non-conforming process patterns in the event log.

The most concerning pattern involves the interaction between `VendorMaster_Lena` and `AP_Kim` in vendor family `V-77x`, characterized by high manual file uploads, high dollar amounts, and non-segregated banking updates. While this may reflect an authorized bulk maintenance activity, the absence of system cross-references requires targeted audit verification.

**Recommendations:**
1. Execute immediate substantiation testing on all banking changes and payment releases associated with vendor family `V-77x`.
2. Update legacy ERP logging integration scripts to resolve resource-mapping artifacts.
3. Standardize and enforce formal call-back and dual-authorization procedures for manual bank data updates across all operating regions.
