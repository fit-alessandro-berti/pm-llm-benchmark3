## 1. Modeling assumptions

The object types are `Order`, `Item`, `Package`, `Delivery`, `Invoice`, and `Payment`, with exactly that capitalization. The E2O qualifier vocabulary is `affected_order`, `involved_item`, `package`, `delivery`, `invoice`, and `payment`: the qualifier states the object's role at an event and is used consistently across activities.

O2O edges are directed from `Order` to `Item` (`contains`), `Package` to `Item` (`packs`), `Delivery` to `Package` (`carries`), `Invoice` to `Order` (`bills`), and `Payment` to `Invoice` (`partially_settles` or `completes_settlement`). The narrative says the two payments settle V1; given their chronological order, M2 is modeled as completing settlement after M1. No payment is assigned to an individual order.

For logistics, the model directly relates the described objects to each event, and adds relevant orders and items as analytical context where they can be obtained through the stated O2O links. For financial events, the invoice and payment are directly related, while the two orders are added as context to each payment event; items are not related to financial events. The `relation_origin` E2O column distinguishes `described` links from `derived_context` links. These labels describe the narrative and the analytical construction, not provenance verified against an actual source system. PM4Py's standard discovery routines generally treat both categories as relations: filter the derived rows before constructing a separate OCEL when a source-minimal analysis is desired. O2O links are not implicitly traversed by the pipeline to create E2O links.

The constructor is isolated below and assumes the stated `OCEL` signature. The API calls use PM4Py 2.7-style top-level functions, including `view_ocpn`. If a version differs, adapt the constructor or function names/signatures to that version while preserving the tables and relation semantics. Flattening and discovery consume E2O relations; the O2O table retains explicit business links rather than automatically guaranteeing that every discovery routine uses them.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

# Every amount is an event attribute, not an object.
event_rows = [
    ("E01", "Create Order",     "2026-04-06 08:00", None),
    ("E02", "Add Item",         "2026-04-06 08:05", None),
    ("E03", "Add Item",         "2026-04-06 08:06", None),
    ("E04", "Create Order",     "2026-04-06 08:10", None),
    ("E05", "Add Item",         "2026-04-06 08:12", None),
    ("E06", "Reserve Stock",    "2026-04-06 08:30", None),
    ("E07", "Pack Package",     "2026-04-06 09:00", None),
    ("E08", "Pack Package",     "2026-04-06 09:05", None),
    ("E09", "Dispatch Package", "2026-04-06 10:00", None),
    ("E10", "Dispatch Package", "2026-04-06 10:15", None),
    ("E11", "Issue Invoice",    "2026-04-06 11:00", None),
    ("E12", "Record Payment",   "2026-04-06 11:30", 100),
    ("E13", "Confirm Delivery", "2026-04-06 13:00", None),
    ("E14", "Confirm Delivery", "2026-04-07 09:00", None),
    ("E15", "Record Payment",   "2026-04-07 10:00", 150),
    ("E16", "Close Order",      "2026-04-07 10:30", None),
    ("E17", "Close Order",      "2026-04-07 10:35", None),
]
events = pd.DataFrame(event_rows, columns=[
    "ocel:eid", "ocel:activity", "ocel:timestamp", "amount"
])
events["ocel:timestamp"] = pd.to_datetime(events["ocel:timestamp"], utc=True)
events["amount"] = events["amount"].astype("Float64")

object_rows = [
    ("O100", "Order"), ("O200", "Order"),
    ("I1", "Item"), ("I2", "Item"), ("I3", "Item"),
    ("P1", "Package"), ("P2", "Package"),
    ("D1", "Delivery"), ("D2", "Delivery"),
    ("V1", "Invoice"), ("M1", "Payment"), ("M2", "Payment"),
]
objects = pd.DataFrame(object_rows, columns=["ocel:oid", "ocel:type"])

o2o = pd.DataFrame([
    ("O100", "I1", "contains"), ("O100", "I2", "contains"),
    ("O200", "I3", "contains"),
    ("P1", "I1", "packs"), ("P1", "I3", "packs"),
    ("P2", "I2", "packs"),
    ("D1", "P1", "carries"), ("D2", "P2", "carries"),
    ("V1", "O100", "bills"), ("V1", "O200", "bills"),
    ("M1", "V1", "partially_settles"),
    ("M2", "V1", "completes_settlement"),
], columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"])

# IDs in "described" are stated as participants in that event. IDs in
# "derived" are additional context inferred from the business relationships.
event_objects = {
    "E01": {"described": ["O100"]},
    "E02": {"described": ["O100", "I1"]},
    "E03": {"described": ["O100", "I2"]},
    "E04": {"described": ["O200"]},
    "E05": {"described": ["O200", "I3"]},
    "E06": {"described": ["I1", "I3", "O100", "O200"]},
    "E07": {"described": ["P1", "I1", "I3", "O100", "O200"]},
    "E08": {"described": ["P2", "I2"], "derived": ["O100"]},
    "E09": {"described": ["P1", "D1"],
            "derived": ["I1", "I3", "O100", "O200"]},
    "E10": {"described": ["P2", "D2"],
            "derived": ["I2", "O100"]},
    "E11": {"described": ["V1", "O100", "O200"]},
    "E12": {"described": ["M1", "V1"], "derived": ["O100", "O200"]},
    "E13": {"described": ["D1"],
            "derived": ["P1", "I1", "I3", "O100", "O200"]},
    "E14": {"described": ["D2"], "derived": ["P2", "I2", "O100"]},
    "E15": {"described": ["M2", "V1"], "derived": ["O100", "O200"]},
    "E16": {"described": ["O200"]},
    "E17": {"described": ["O100"]},
}
qualifier_by_type = {
    "Order": "affected_order", "Item": "involved_item",
    "Package": "package", "Delivery": "delivery",
    "Invoice": "invoice", "Payment": "payment",
}
relation_rows = []
for eid, groups in event_objects.items():
    for group, origin in [("described", "described"),
                          ("derived", "derived_context")]:
        for oid in groups.get(group, []):
            relation_rows.append((eid, oid, origin))

relations = pd.DataFrame(relation_rows, columns=[
    "ocel:eid", "ocel:oid", "relation_origin"
])
# Populate activity, timestamp, and object type from their authoritative tables.
relations = relations.merge(
    events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
    on="ocel:eid", how="left", validate="many_to_one"
).merge(
    objects[["ocel:oid", "ocel:type"]],
    on="ocel:oid", how="left", validate="many_to_one"
)
relations["ocel:qualifier"] = relations["ocel:type"].map(qualifier_by_type)
relations = relations[[
    "ocel:eid", "ocel:activity", "ocel:timestamp", "ocel:oid",
    "ocel:type", "ocel:qualifier", "relation_origin"
]]

# Integrity checks; the pair uniqueness rule is deliberately stricter than
# allowing several differently qualified relations to the same object/event.
assert events["ocel:eid"].is_unique
assert objects["ocel:oid"].is_unique
assert relations["ocel:eid"].isin(events["ocel:eid"]).all()
assert relations["ocel:oid"].isin(objects["ocel:oid"]).all()
assert o2o["ocel:oid"].isin(objects["ocel:oid"]).all()
assert o2o["ocel:oid_2"].isin(objects["ocel:oid"]).all()
assert not relations.duplicated().any()
assert not relations.duplicated(["ocel:eid", "ocel:oid"]).any()
assert not o2o.duplicated().any()
assert relations["ocel:qualifier"].notna().all()
assert set(relations["ocel:eid"]) == set(events["ocel:eid"])
assert events["ocel:timestamp"].dt.tz is not None
check = relations.merge(
    events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
    on="ocel:eid", suffixes=("_rel", "_event"), validate="many_to_one"
)
assert check["ocel:activity_rel"].eq(check["ocel:activity_event"]).all()
assert check["ocel:timestamp_rel"].eq(check["ocel:timestamp_event"]).all()
type_check = relations.merge(objects, on="ocel:oid", suffixes=("_rel", "_object"),
                             validate="many_to_one")
assert type_check["ocel:type_rel"].eq(type_check["ocel:type_object"]).all()

# Isolated version-dependent constructor.
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)
print("Activity frequencies:\n", events["ocel:activity"].value_counts())
print("Object-type frequencies:\n", objects["ocel:type"].value_counts())
print("PM4Py object types:", pm4py.ocel_get_object_types(ocel))
print("Activities per object type:", pm4py.ocel_object_type_activities(ocel))

flat_logs, dfgs, skeletons = {}, {}, {}
for object_type in ("Order", "Package", "Delivery", "Invoice"):
    flat_logs[object_type] = pm4py.ocel_flattening(ocel, object_type)
    # PM4Py returns (DFG, start-activity counts, end-activity counts).
    dfgs[object_type] = pm4py.discover_dfg(flat_logs[object_type])
    skeletons[object_type] = pm4py.discover_log_skeleton(flat_logs[object_type])

ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
oc_petri_net = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Optional, requires a working visualization backend such as Graphviz:
# pm4py.view_ocdfg(ocdfg)
# pm4py.view_ocpn(oc_petri_net)
```

## 5. Expected object-centric structures

- **OC-DFG:** Activity edges are distinguished by object type, so the Order, Package, Delivery and Invoice directly-follows patterns coexist. Shared events such as P1's packing and V1's issuance are represented once as events while being associated with multiple objects. Counts can be based on events, objects, or event pairs, depending on the displayed metric; derived context contributes to these counts. Shared activities and per-type edges suggest convergence and divergence, although aggregated edges alone do not reconstruct the entire instance-level story.
- **OTG:** The object-type graph summarizes relations such as interaction and lifecycle-derived relationships between types. P1 co-occurs with O100 and O200 in packing and, through derived context, later logistics events; V1 co-occurs with both orders, M1 and M2. Lifecycle-based edges depend on the event associations and on the selected algorithm; they are not simply the directed `packs`, `bills`, or settlement O2O rows.
- **ET–OT:** The event-type/object-type graph shows which activity types touch which object types and their frequencies, including Pack Package–Package, Issue Invoice–Invoice, and Record Payment–Payment, Invoice and Order. An edge is an aggregate association; it does not by itself identify P1, V1, M1, M2, O100, or O200 or establish an allocation. Exact weight interpretation follows the PM4Py implementation.
- **Object-centric Petri net:** The discovered model combines type-specific lifecycle behavior around shared activity transitions. P1 can involve multiple Item and Order objects at packing, while V1 connects two orders to invoicing and later M1/M2 payments. Variable-multiplicity indications and discovered control flow depend on the miner and input relations. Two orders and a few traces provide little evidence, so this is one discovered abstraction, not a uniquely determined process model or proof of the business rules.
- **Object-interactions summary:** Event-level co-occurrence rows expose pairs such as P1 with O100 and O200 at E07, and V1 with each order at E11 and the payment events. M1 and M2 each co-occur with V1 at their own payment event; they do not co-occur with each other in this dataset. Pair rows may be directional and repeated across events; they are not necessarily unique business links, causal dependencies, or O2O edges. Derived relations also create interaction rows.

## 6. Modeling alternatives

1. **Source-minimal:** Retain only event–object links explicitly recorded or described for each event. For this narrative, retaining only `described` rows provides one approximation. Order traces then omit inferred dispatches, confirmations, the P2 pack and payments; Package traces omit inferred confirmations. DFGs and interactions become sparser, even though the O2O relationships and business story remain available separately.
2. **Full operational involvement:** Record all objects known by an operational system to participate in each event, including affected orders and items for logistics and the invoice's orders for payment. This can yield E2O sets like the richer view above, but the additional links are direct observations only if the system actually recorded them. Discovery exposes more cross-type connections and longer lifecycles.
3. **O2O-propagated analytical context:** Start from observed event links and deliberately derive additional links using explicit rules, as in this pipeline. Propagation extends traces and co-occurrence graphs while provenance distinguishes the new links. Different traversal depths or cutoffs change the result: indiscriminately propagating an invoice payment to every item, for example, would add financial activities to item lifecycles without establishing item-level payment.

These policies answer different questions about the same events. Their discoveries are not interchangeable, even if the O2O business facts remain unchanged.

## 7. Failure modes

- **Relation inflation:** Propagating every reachable object can create large cliques, longer lifecycles and spurious interaction or DFG counts.
- **Missing direct E2O links:** An O2O connection alone need not cause PM4Py flattening or discovery to attach an event to an order or item; relevant behavior can disappear from that view.
- **Mistaking inference for observation:** Treating `derived_context` as a source-system event participant invents evidence. Standard mining calls do not automatically enforce the provenance distinction.
- **Duplicate shared events after flattening:** Summing rows over order cases double-counts shared events such as E07 and E11. Preserve event IDs and count distinct events when that is the desired measure.
- **Ambiguous payment allocation:** M1 and M2 settle V1 collectively; linking each to both orders does not say how much either order paid. Counting 100 and 150 against each order would double-count money.
- **Overly short Payment traces:** A one-event case for each payment provides no payment-to-payment edge and little evidence for a lifecycle model.
- **Constructor or API mismatch:** PM4Py releases may change constructor arguments, function names, return structures, flattening conventions or visualization requirements. Adapt the isolated call and interfaces, and verify output semantics.
- **False total order at timestamp ties:** This example has no ties, but sorting equal timestamps arbitrarily can invent directly-follows relations and causality. Use a justified secondary order or retain the uncertainty when ties arise.
- **Confusing aggregation levels:** Interaction rows, object counts, event counts and edge-occurrence counts answer different questions; graph frequencies must be interpreted using the selected metric.
- **Overfitting discovery:** Two order cases and one invoice do not establish mandatory sequences or a unique Petri net; correlations in this sample may not generalize.
