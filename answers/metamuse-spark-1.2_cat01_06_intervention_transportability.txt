Shared mechanisms: The core chain `treatment_parallelization -> true_overlap -> waiting_before_assessment -> cycle_time` is structurally shared, provided Document has no prerequisite. Capacity -> waiting is also shared physics (queueing). Appeal and rework generation from cycle time/complexity is shared.

Site-specific mechanisms: `originals_required -> true_overlap` and `originals_required -> waiting` is essentially absent at A (90% digital) but dominant at B (62% legal bar). `legal_capacity -> waiting` and the supplement loop `rework -> cycle_time` is null at A, active at B. `IT_case_lock -> true_overlap` blocks translation of intent to execution at B only. `API_latency` reduction and `queue_huddles` at A are co-interventions not present at B, spuriously boosting A effect. `role_specialization` changes whether parallel creation translates to parallel execution.

Effect modifiers: `digital_documents`/`originals_required` (positivity: 62% cannot receive A treatment), `case_complexity` (longer Document service 8.1h vs 6.5h, heavier tail), `role_specialization` and `IT_case_lock` (implementation fidelity), `assessment_capacity`/`legal_capacity` (bottleneck shift), `rework` risk via supplementation.

Similar control-flow diagrams do not guarantee transportability because transportability depends on the partial order of prerequisites and resource/IT constraints, not the drawn sequence. A diagram `->(Register, +(Identity,Document), Assessment)` abstracts away data dependencies (originals), role pools, locking, and exogenous delays that determine whether `+( )` is legally or operationally realizable and whether waiting saved in verification simply reappears before Assessment. Selection diagrams formalize this: when `S` points to a parent of overlap, the effect is not S-admissible without conditioning/stratifying.

## 6. Candidate Site B intervention

**Eligibility rules**
- Eligible for full A-like parallel: `originals_required = False` AND `legal_requirement = Low` (digital, non-public, low-value, low complexity). ~25-30% of volume.
- Eligible for partial parallel (Identity // Originals wait): `originals_required = True`. Document stays blocked. ~62%.
- Conditional/excluded: High supplement-risk legal cases (public/high-value with history of supplement >20%) require Legal pre-triage before full Document; initially excluded from pilot treatment.

**Tasks that may be created/executed concurrently**
- After `Register`, system creates `Identity Check` immediately.
- If digital-no-originals: also creates `Document Check` immediately; both may be owned concurrently (requires IT lock fix or explicit dual-owner workaround flag).
- If originals-required: creates `Originals Receipt` wait task immediately, in parallel with `Identity Check`. `Document Check` is NOT created until `Originals Receipt` completes and statutory receipt logged.
- `Assessment` is pull-based, only when both required prerequisites complete.

**Statutory prerequisites that remain mandatory**
- `Originals Receipt -> Document Check` when originals_required.
- `Identity Check + Document Check -> Assessment` (both complete).
- `Assessment -> Legal Review` for public/high-value; `Legal Review -> Request Supplement -> Document Check -> Assessment` loop preserved. Supplement decision always requires re-document and re-assessment.

**Queue and WIP controls**
- Per-reviewer WIP 6 (as at A) enforced per pool: ID 4*6=24, Doc 7*6=42, Assessors 3*5=15 stricter, Legal 2*6=12.
- Global Assessment throttle: if Assessment queue >12, pause pulling new verifications from Document pool (upstream WIP control).
- Daily 15-min cross-pool huddle (separate intervention, measured).

**Resource responsibilities**
- Retain specialization but allow joint huddle; no cross-training required. Identity reviewers only Identity, Document only Document, Assessors only Assessment, Legal only Legal. Parallel means different persons, not same person.

**Handling of legal-review and supplement loops**
- Legal review is XOR branch after Assessment. If `Request Supplement`, case returns to Document Check (with originals already satisfied, re-check) then Assessment again, then Legal re-review. Loop is bounded; second iteration not parallelized.
- Supplement risk score gates early parallel: score High  defer Document start until Legal pre-screen.

**Logging requirements**
- Log intent timestamps: `task_created`, `task_claimed`, `task_started`, `task_completed`, plus `entry_mode` (system vs workaround), `owner_id`, `WIP_at_claim`. Originals arrival logged via scan event, not manual entry. All concurrent claims allowed and timestamped by system creation.

**Compact POWL-style description / partial-order**

```
POWL model: SiteB_Candidate

Transitions: {Register, IdentityCheck, OriginalsReceipt, DocumentCheck, Assessment, LegalReview, RequestSupplement, Approve, Reject, Notify}

PartialOrder PO_main =
  Register < {IdentityCheck, OriginalsReceipt_or_Document}
  OriginalsReceipt < DocumentCheck   // when branchB
  {IdentityCheck, DocumentCheck} < Assessment

Choice branches after Register:
  BranchDigital = DocumentCheck (no OriginalsReceipt)
  BranchOriginals = OriginalsReceipt -> DocumentCheck

POWL = ->( Register,
          StrictPartialOrder( nodes={IdentityCheck, OriginalsReceipt, DocumentCheck},
                              edges={IdentityCheck concurrent OriginalsReceipt,
                                     OriginalsReceipt -> DocumentCheck,
                                     IdentityCheck -> Assessment,
                                     DocumentCheck -> Assessment}),
          Assessment,
          X( ->(LegalReview,
                X( ->(RequestSupplement, DocumentCheck, Assessment, LegalReview),
                   tau )),
             tau ),
          X(Approve, Reject),
          Notify
        )

Loop: Supplement Loop = *( LegalReview -> RequestSupplement -> DocumentCheck -> Assessment ) with exit to Approve/Reject.
Constraint: LegalReview node only if legal_required attribute = True; otherwise tau bypass.
```

Equivalently, order edges: `Register < IdentityCheck, Register < OriginalsReceipt, OriginalsReceipt < DocumentCheck, IdentityCheck < Assessment, DocumentCheck < Assessment, Assessment < LegalReview, LegalReview < RequestSupplement, RequestSupplement < DocumentCheck, RequestSupplement < Assessment (via Document), LegalReview < Approve/Reject, Assessment < Approve/Reject (if no legal), Approve/Reject < Notify`.

Separating mechanism from implementation failure: The pilot measures both assignment (`treatment_parallelization` intent) and `true_overlap` execution via creation/claim timestamps. Intent-to-treat estimates capture policy effect including IT lock and role constraints; per-protocol and instrumental-variable estimates using assignment as instrument for true overlap isolate the mechanism of concurrency itself. If ITT shows null but `true_overlap` also shows null (<30%) with many cases flagged `IT_case_lock` or `entry_mode=workaround`, failure is implementation—repair IT and re-test. If `true_overlap` reaches 60%+ yet waiting before Assessment and cycle time do not improve, especially with Assessment queue length rising, mechanism fails due to bottleneck shift or statutory dominance—requires WIP/legal fixes, not more parallelism. Negative-control metric (Legal Review service time, which parallel should not affect) and stratification by digital/originals further diagnose confounding vs genuine transport failure.

## 8. PM4Py model-construction code

```python
import pm4py

# ---- 1. Site A before / after as process trees (manual: pm4py.parse_process_tree) ----
# Operators: -> sequence, + parallel, X exclusive choice
tree_A_before_str = "-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"
tree_A_after_str  = "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', X ( 'Approve', 'Reject' ), 'Notify' )"

tree_A_before = pm4py.parse_process_tree(tree_A_before_str)
tree_A_after  = pm4py.parse_process_tree(tree_A_after_str)

# ---- 2. Convert to accepting Petri nets ----
net_A_before, im_A_before, fm_A_before = pm4py.convert_to_petri_net(tree_A_before)
net_A_after, im_A_after, fm_A_after   = pm4py.convert_to_petri_net(tree_A_after)

print("A_before sound:", pm4py.check_soundness(net_A_before, im_A_before, fm_A_before))
print("A_before is workflow net:", pm4py.check_is_workflow_net(net_A_before, im_A_before, fm_A_after))

# ---- 3. Site B candidate POWL with strict partial order + legal loop ----
# Manual: pm4py.objects.powl.obj.{POWL, StrictPartialOrder, OperatorPOWL, Transition}
from pm4py.objects.powl.obj import POWL, StrictPartialOrder, OperatorPOWL, Transition

# Transitions
t_register = Transition(label="Register")
t_identity = Transition(label="Identity Check")
t_originals = Transition(label="Originals Receipt")
t_document = Transition(label="Document Check")
t_assessment = Transition(label="Assessment")
t_legal = Transition(label="Legal Review")
t_supplement = Transition(label="Request Supplement")
t_approve = Transition(label="Approve")
t_reject = Transition(label="Reject")
t_notify = Transition(label="Notify")

# Sub-order that encodes statutory constraints:
# Register -> {Identity, Originals}; Originals -> Document; {Identity, Document} -> Assessment
# POWL StrictPartialOrder captures concurrent prerequisites
po = StrictPartialOrder(nodes=[t_identity, t_originals, t_document, t_assessment])
# Explicit edges so Assessment waits for BOTH identity and document
po.order.add_edge(t_originals, t_document)   # statutory: originals required -> document
po.order.add_edge(t_identity, t_assessment)  # identity -> assessment
po.order.add_edge(t_document, t_assessment)  # document -> assessment
# Note: Identity and Originals are concurrent (no edge), modelling partial parallel

# Choice for document channel: digital vs originals - modeled as XOR over POWL branches
# For simplicity we embed po above; digital cases simply have zero-duration Originals (skipped) in simulation
# OperatorPOWL for exclusive choice Approve/Reject
choice_decision = OperatorPOWL(operator=OperatorPOWL.XOR, children=[t_approve, t_reject])

# Legal branch with optional supplement loop
# LegalReview -> ( RequestSupplement -> DocumentCheck -> Assessment -> LegalReview )*
# Use OperatorPOWL LOOP: LOOP(body, redo)
```

## 9. Recommendation

**`conditional go`**

What should be transferred: The principle of removing unnecessary sequencing where tasks are truly independent. For Site B this means: create `Identity Check` immediately after `Register` in all cases, and hide its execution under the waiting time for `Originals Receipt`. This `Identity // Originals Wait` partial parallel is the transportable kernel of Site A’s intervention and directly addresses the 62% originals-required cases without violating statute.

What should not be copied: The naive rule “create Identity and Document together for every case.” At At 62% of B cases Document cannot legally start before originals; copying full `+(Identity, Document)` would breach compliance, waste document reviewer effort, and inflate rework when supplements occur. Do not import Site A’s 9-hour median gain as an expected effect, nor its supporting co-interventions (API upgrade, +2 FTE, marketing mix shift, huddles) as part of the treatment—they are confounders that inflated A’s before/after. Do not assume cross-trained pools or case-lock-free IT; B’s specialization and single-owner lock would turn intent into logged but not real concurrency.

Which subgroup should enter first: Digital-only, non-public/low-value, low-to-medium complexity cases (25-30% of volume) where Document has no prerequisite and Legal loop risk is low. This subgroup is structurally S-admissible to Site A and isolates the mechanism from statutory and bottleneck interference. Second wave only if first shows waiting drop without rework: originals-required group testing only Identity concurrency, keeping Document blocked.

Expected benefits and risks: For the eligible digital subgroup, expect subgroup median -4 to -6h (waiting before Assessment -5h) and population median -1.5 to -2.5h; p90 may not improve at population level because tail is dominated by postal variance and legal loops. Risk: assessment/legal bottleneck shift could worsen p90 by 5-10h and raise rework 2-3 points if bursts are not throttled; IT-lock failure would yield zero benefit despite logged overlap. Both harms are preventable with WIP caps and a lock fix.

Evidence to trigger expansion/modification/abandonment: Expand only if 12-week stratified RCT shows in Stratum D: true_overlap >60%, waiting before Assessment  -3h+ (p<0.05), rework  +1.5pp, and Assessment queue not +4h vs control, with per-protocol confirming mechanism. Modify to throttle or add assessor/legal capacity if p90 degrades while median improves. Abandon full Document parallel if true_overlap remains <30% after IT fix (fidelity failure) or if supplement rework rises >3pp or appeal ticks up, indicating harmful early document work.

## 10. Assumption register

1. **assumption**: At Site A, Identity and Document checks are truly independent (no data/control dependency) — **why needed**: justifies parallelization as causal mechanism for waiting reduction — **how to test**: trace attribute analysis: Document start not conditional on Identity result; no shared data artefact; interview + DFG — **consequence if false**: A effect overestimated; copying to B would risk rework due to hidden dependency

2. **assumption**: Originals Receipt is exogenous delay (median 18h highly variable) unaffected by treatment — **why needed**: to bound expected cycle gain for 62% originals-required to near zero — **how to test**: measure Originals delay by arm; should be identical in pilot — **consequence if false**: if pilot pressures applicants to send faster, spillover inflates benefit unsustainably

3. **assumption**: IT case lock change (or logged workaround) can achieve true_overlap >60% among eligible — **why needed**: transport requires intentexecution fidelity — **how to test**: compare `task_created` vs `task_claimed` timestamps, `entry_mode` flag, overlap intervals by arm — **consequence if false**: ITT null despite sound mechanism; need IT redesign not process redesign

4. **assumption**: Assessment capacity (3 assessors, 2 legal) has slack to absorb verification speed-up — **why needed**: prevents bottleneck shift that cancels upstream gain — **how to test**: monitor Assessment queue length hourly by arm; queueing model with current utilization — **consequence if false**: median gain small but p90 +5-10h; require WIP throttle or capacity addition

5. **assumption**: Legal supplement risk is independent of verification parallelism conditional on complexity — **why needed**: ensures early Document not invalidated more often under parallel — **how to test**: supplement rate 26% of legal cases by arm, stratified by complexity — **consequence if false**: rework 17%20%+, doubling Document work and degrading tail

6. **assumption**: No secular trend / mix shift during B pilot (unlike A’s 48%40% high-complexity shift) — **why needed**: to identify treatment vs confounded before/after — **how to test**: track weekly case mix, arrivals, negative-control (e.g., Legal service time) by arm — **consequence if false**: apparent gain is mix effect; requires adjustment and longer pilot

7. **assumption**: Role specialization pools are correctly sized (4 ID/7 doc) to avoid starvation when parallel — **why needed**: parallel creation assumes both pools can take task promptly — **how to test**: pool utilization, time-to-claim by task type by arm — **consequence if false**: one pool queue builds, waiting merely moves, overlap not realized

8. **assumption**: Timestamp logging after fix reflects true work intervals, not back-entry — **why needed**: fidelity and outcome measurement validity — **how to test**: audit creation vs completion entry lag, workaround flag rate, conformance checks — **consequence if false**: mining shows false overlap and underestimates waiting; decisions based on artefactual improvement
