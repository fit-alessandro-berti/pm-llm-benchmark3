## 1. Model scope and state variables

The twin should be a calendar-aware, discrete-event simulation with object-centric extensions for architects, objection episodes, and inspection tours. It should not sample an independent total duration for each permit.

### Boundary and clocks

The modeled boundary should cover:

1. Pre-submission checker or appointment interaction, when applicable.
2. Formal `Submit application`.
3. Municipal reviews, applicant responses, notice periods, inspections, rework, and appeals.
4. `Issue permit` or final `Reject application`.

Two clocks should be reported:

- **Applicant journey time:** starts when an applicant enters a checker or appointment queue. This prevents D1 and D7 from appearing beneficial merely by shifting delay upstream.
- **Formal permit time:** starts at `Submit application`.
- A third, **municipal-controllable time**, should exclude legally paused applicant-response periods where local rules permit that exclusion.

Post-permit violations, safety incidents, and construction outcomes are outside the current event-log boundary, but D2 cannot be recommended without linking or prospectively collecting those outcomes.

### Simulation entities

| Entity | Important state |
|---|---|
| Permit case | Case ID, type, district, architect, value, submission time, age, current process state, enabled activities, completed prerequisites, priority, accumulated work/wait, result |
| Latent case attributes | Building area, prior violations, environmental sensitivity, document quality, objection propensity, applicant readiness, appeal propensity |
| Architect | Submission intensity, burst state, active cases, appointment compliance, applicant-response capacity/random effect |
| Related-case group | Architect, district, submission window or external project identifier, shared objection episode, inspection-bundle eligibility |
| Objection episode | Neighborhood/district, affected cases, latent occurrence, objection arrival time, extension duration, outreach status |
| Inspection tour/bundle | District, cases, first-case hold time, route, inspector, travel time, no-shows |
| Resource | Pool, individual or skill class, calendar state, assigned case, remaining work, overtime |
| Activity instance | Enablement, queue entry, start, pause/resume, completion, assigned resource, work content, reason for delay |
| Policy state | Eligibility, checker uptake, triage classification, aging threshold, peak staffing, audit selection |

Simulated output should contain lifecycle events—enable, queue, start, pause/resume, and complete—even though the historical log does not. This supports later diagnosis of service and waiting separately.

### Process logic

- Submission is available continuously through the portal.
- Completeness checking may lead to one or more missing-document loops.
- Planning is mandatory. Fire and environmental reviews are conditional and may proceed in parallel.
- Public notice is conditional and has a statutory minimum plus a latent objection-related extension.
- Inspection scheduling creates either an individual visit or a district bundle.
- Inspection rework re-enters scheduling/inspection as appropriate.
- Decision drafting is an **AND-join**: it waits for every applicable planning, fire, environmental, notice, and inspection result.
- Legal check is conditional. D5 adds an earlier pre-check, not an unconditional removal of final legal authorization.
- Appeals should be represented as an exception subprocess returning to planning, inspection, drafting, or legal review depending on the appeal reason.
- Rejections and permits are terminal only after any applicable appeal window or appeal resolution included in the chosen boundary.

The supplied process tree is a useful normative starting point, but it does not fully represent the observed repeated `Completeness check`, appeal behavior, objection episodes, or rare exceptions.

### Queues and resource pools

| Pool/process | Baseline representation |
|---|---|
| Permit clerks | Five FTE, but four available for permit work on Mondays because one handles portal support; weekday 08:00–16:00 |
| General planners | Six FTE, weekday 09:00–17:00; planning and decision drafting |
| Simple-only planners | Two FTE, weekday 09:00–17:00; only Simple renovation work |
| Fire reviewers | Two FTE equivalent, Tuesday–Thursday only |
| Environmental reviewers | Three nominal FTE, with only about 60% capacity available to permits; model reserved blocks rather than merely multiplying service time |
| Schedulers | Separate pool because scheduling has observed resource contention; capacity/calendar must be estimated or obtained |
| Inspectors | Four FTE, field work Tuesday–Friday; on-site work and travel represented separately |
| Legal officers | Two FTE; calendar blackouts during council-meeting weeks except modeled urgent work |
| System | Effectively unlimited capacity |
| Applicants/consultants | External delay processes, not municipal FTE pools |
| Public notice | Legal elapsed-time process plus any staff work and latent objection episode |

Municipal queues should generally be work-conserving and skill-constrained. Baseline priority rules—FIFO, case-type specialization, informal aging, or district preference—must be inferred rather than assumed to be pure FIFO.

Work effort is consumed only when a resource calendar is open. Most desk activities can be preempted at shift boundaries and resumed. Site visits are non-preemptive appointments and must fit within a field-day route. Public-notice and applicant-response delays run in elapsed or legally defined calendar time rather than staff work time.

### Cross-case dependencies

The following dependencies are explicit state, not independent random noise:

- A non-homogeneous, clustered arrival process produces architect-level submission bursts.
- Shared municipal queues couple all active cases.
- Architect random effects may correlate document quality and response delays across the architect’s cases.
- Related cases can share a neighborhood objection episode, creating correlated notice extensions.
- Inspection bundles trade a hold for the first case against lower travel time for the group.
- Council weeks, holidays, illness, and specialist availability create common calendar shocks.
- Policy capacity consumed by one type can increase waiting for another type.
- Where a true related-project identifier is unavailable, probable groups should be generated from architect, district, time window, and other attributes, with structural sensitivity analysis.

## 2. Parameter-estimation plan

### Log preparation and process mining

Use the complete 18-month log, not the two-case excerpt, for calibration.

1. Load data with pandas and normalize it using `pm4py.format_dataframe`.
2. Verify that case-level attributes are internally consistent within each case.
3. Resolve timestamp semantics and timezone/DST handling from the source systems.
4. Compute variants, frequency and performance DFGs, case arrivals, repetitions, and conditional path frequencies.
5. Parse the normative process tree and convert it to a Petri net where useful.
6. Use token replay or alignments to identify:
   - repeated completeness checks not represented exactly by the tree;
   - unexpected orderings;
   - skipped reviews;
   - rework and appeal-like traces;
   - incomplete or censored cases.
7. Compare the normative model with a discovered model, but retain the normative model as the policy-valid control-flow backbone. Rare observed behavior should be represented as exception paths rather than forcing a highly permissive model.

PM4Py should support log formatting, model handling, conformance analysis, variants, and DFG diagnostics. The calendar-aware simulation itself should be implemented separately, for example with SimPy or a purpose-built event scheduler.

### Arrivals and case attributes

Estimate a marked, non-homogeneous arrival process:

\[
\lambda(t \mid \text{month, weekday, hour, trend})
\]

using Poisson or negative-binomial regression with:

- month or seasonal spline;
- weekday and month-by-weekday interaction;
- hour of day;
- holidays;
- trend terms, if supported;
- overdispersion.

The 1.7 peak multiplier and 2.2 Monday/Wednesday ratio are calibration targets, not sufficient by themselves.

Architect bursts should be estimated with a hierarchical component, such as:

- architect random effects plus negative-binomial weekly counts;
- a background arrival process plus burst/cluster offspring;
- or a Cox/Hawkes-style process if excitation is supported by the data.

Preserve correlations among case type, district, value, architect, and routing flags. Estimate the conditional case-mix distribution rather than independently drawing each field.

Use block bootstrap units such as week and architect-week when quantifying arrival uncertainty. Eighteen months contains only one and a half annual cycles, so seasonal parameters need wider uncertainty or external multi-year portal counts.

### Service effort and waiting

For records with both start and completion timestamps:

- Calculate service effort in resource-working time, not merely wall-clock time.
- Model activity-specific distributions, conditional on type, district, rework status, assigned resource class, and other relevant attributes.
- Use hierarchical lognormal, gamma, Weibull, or empirical/mixture models rather than exponential distributions by default.
- Retain resource-level random effects where enough observations exist.

For completion-only records:

- The preceding inter-event duration is not service time.
- In parallel branches it is not necessarily waiting time either.
- Use activities with valid lifecycle data, time studies, staffing information, and the supplied median/p90 summaries as evidence about latent work content.
- Treat service effort and resource availability as jointly uncertain; avoid calibrating both freely because they are weakly identifiable.
- Use interval-censored or latent-variable estimation where possible.

Municipal queue waiting should normally emerge from arrivals, queue discipline, skills, service effort, and calendars. Historical waiting-time distributions are validation and calibration targets, not additional sampled delays. Sampling historical municipal waiting on top of simulated queues would double count congestion.

Separate non-resource holds, including:

- applicant response;
- consultant report preparation;
- statutory notice minimum;
- objections;
- appointment readiness;
- legal/council holds;
- data-entry or handoff delays not represented by a resource queue.

### Routing and branching

Estimate routing jointly, conditional on case attributes, rather than multiplying marginal branch probabilities.

Examples include:

- missing-document probability and number of loops;
- fire review conditional on `requires_fire`, type, value, and latent building area;
- environmental review conditional on the recorded flag, district, and latent sensitivity;
- public notice conditional on type, district, value, and available project features;
- legal review and rejection conditional on review results and rework;
- inspection and legal rework;
- appeal probability and return point.

Logistic or multinomial hierarchical models can provide conditional probabilities and uncertainty. The observed variant shares should be reproduced as joint calibration targets.

Building area, environmental sensitivity, and prior violations should be linked from authoritative registries before operational use. Until then, generate them as latent variables with scenario ranges. Do not infer that every observed review was caused by the recorded flag.

### Rework

Use event repetitions and conformance alignments to identify rework episodes. Estimate:

- probability of rework after each eligible activity;
- number of loops;
- work effort on repeated attempts;
- routing destination;
- correlation with document quality, type, district, resource, and applicant readiness.

Because reasons are unreliable text, use a small latent mixture such as applicant deficiency, technical failure, inspection no-show, substantive violation, and legal conflict. Vary mixture weights in sensitivity analysis.

Each loop should create new service and queue demand. Do not simply add a fixed duration to the original activity or impose an arbitrary low loop cap. A high technical safety cap may prevent nontermination, but capped runs must be flagged.

### Applicant, objection, and other external durations

Model applicant response separately from municipal work. Candidate distributions include lognormal or log-logistic bodies with a heavy-tail component and architect/case random effects. Account for right-censoring when documents never return.

Public notice should be modeled as:

\[
D_{\text{notice}} =
D_{\min} + I_{\text{objection}}D_{\text{extension}} +
D_{\text{calendar hold}}
\]

where the objection indicator is latent. Long notice durations are evidence about objections, not direct observations of them. Fit a mixture constrained by the 14-day minimum, supplemented with planning staff estimates or external objection records. D9 effects require pilot or expert priors because they are not identifiable from the current log.

### Resource calendars and assignments

Reconcile HR calendars, leave records, event resource IDs, and observed completion patterns.

- Build explicit weekly shifts, holiday exceptions, council-week blackouts, and part-time schedules.
- Estimate skill matrices from resource/activity relationships, then validate with managers.
- Treat the environmental 40% reservation as scheduled or stochastic unavailability, not automatically as 40% longer service.
- Infer scheduler capacity rather than treating it as unlimited.
- Separate inspection on-site effort, route/travel time, and no-show loss.
- Validate reconstructed available hours against HR totals.

### Cross-case dependency estimation

- Fit architect-week count distributions, burst sizes, and within-burst interarrival times.
- Estimate architect random effects for document quality and response duration.
- Identify probable related cases using architect, district, submission proximity, address/project identifiers where available, and common attributes.
- Identify existing informal inspection batching from same-inspector, same-day, same-district sequences.
- Estimate district travel matrices from schedules/GPS if available; otherwise use elicited ranges.
- Estimate objection clustering by district and submission/notice windows using a latent shared-shock model.
- Compare weekly count variance, autocorrelation, bundle-size distribution, and correlated notice extensions between observed and generated data.

### Calibration

Use simulated method of moments, approximate Bayesian calibration, or Bayesian optimization against a weighted set of targets:

- arrivals by month, weekday, type, district, and architect group;
- common variant shares;
- activity service and waiting quantiles;
- case median, p90, and p95 by type;
- queue lengths and aging where available;
- resource utilization and assignments;
- rework counts;
- district inspection differences;
- architect burst and inspection-bundle statistics.

Reserve holdout data before calibration. Parameters should not be tuned solely to match overall mean duration.

## 3. Assumptions

### Arrivals

- Portal submissions can occur outside municipal working hours.
- The arrival process is clustered and overdispersed; it is not homogeneous Poisson.
- Case attributes are drawn jointly so type, value, district, architect, and review requirements remain correlated.
- Appointment policies can move formal submission time and may cause abandonment or noncompliance. Both are reported rather than ignored.
- Historical emergency cases are outside the primary regular-process population unless separately modeled.

### Service times

- Human service time means active work effort, while calendar interruption and queueing are modeled separately.
- Desk work is preempt-resume across shifts unless operational interviews indicate otherwise.
- Site visits are non-preemptive.
- Activity distributions are conditional and generally right-skewed; exponential service is not assumed.
- The supplied medians and p90s are priors or calibration targets where start data are absent, not exact known parameters.
- Inspection travel is separate from the one-hour on-site median.

### Routing

- Applicable planning, fire, environmental, notice, and inspection branches synchronize before decision drafting.
- Recorded flags are informative but incomplete.
- The supplied process tree is normative and incomplete, particularly for repeated completeness checks, objections, appeals, and rare exceptions.
- D2 eligibility requires both value below EUR 50,000 and no prior violations. Missing prior-violation status is never silently treated as “none.”
- D5 performs useful work early but retains any legally required final authorization.
- D8 false negatives and false positives are explicitly represented.

### Resources/calendars

- A Monday portal-support clerk is unavailable for permit processing unless measured otherwise.
- The two Simple-only planners cannot serve other types; the six general planners may serve all modeled planning work.
- Fire reviewers work only Tuesday–Thursday.
- Environmental non-permit work blocks capacity rather than merely slowing every permit.
- Inspectors conduct field visits Tuesday–Friday.
- Legal work pauses during council weeks except for separately modeled urgent work.
- Public holidays and daylight-saving changes use the municipality’s actual local calendar.
- Unknown pools, such as schedulers or outreach staff, are calibrated or scenario-tested rather than assumed unlimited.

### Rework

- Rework propensity is correlated with latent case quality, applicant readiness, and case complexity.
- Repeated work has its own service draw and queue entry.
- Rework reasons are treated as latent categories because text coding is unreliable.
- Appeal behavior is represented as an exception subprocess even though the simplified tree omits it.
- Any simulation loop guard is a technical safeguard and is disclosed in outputs.

### Applicant/third-party response

- Applicant and consultant delays are external elapsed-time processes and do not consume municipal FTE continuously.
- Architect-level random effects can correlate response times across cases.
- Non-response and very late response are represented through censoring or a heavy-tail component.
- Public notice has a fixed legal minimum, but objection occurrence is latent.
- Council and holiday rules may affect legal notice completion separately from municipal staff service.

### Cross-case dependencies

- Shared queues, architect bursts, objection episodes, and inspection bundles create dependencies between cases.
- Same architect, district, and week is evidence of relatedness, not proof; grouping uncertainty is propagated.
- Bundling reduces expected travel but may increase waiting for the first case.
- Cases in a common objection episode can have correlated extensions.
- No additional cross-case precedence is invented without an address, project, neighborhood, or policy basis.

### Non-stationary demand

- Seasonal and weekday effects persist over the evaluation horizon unless a stress scenario changes them.
- Annual demand level, seasonal amplitude, and Monday concentration are separate uncertain parameters.
- A trend is included only if supported by longer external counts; otherwise it is varied in stress tests.
- Policy effects are compared using the same underlying stochastic arrival realization where possible.

### Missing data

- Completion-to-completion time is labeled as an inter-event duration, not service time.
- Objections are latent; long public-notice duration is only a proxy.
- Missing building area, environmental sensitivity, and prior violations are imputed probabilistically or linked from other systems.
- Missingness may be non-random, so optimistic and adverse missing-data scenarios are required.
- Flattened logs are augmented with object links where possible; otherwise cross-case structure is calibrated with explicit uncertainty.
- Removed emergency decisions limit validation to the regular process.
- HR calendars are treated as uncertain reconstructed inputs and checked against operational interviews.

## 4. Experiment matrix

The levels below are experimental design points, not already-established causal effects. D1, D5, D8, and D9 especially need pilot evidence or elicited priors.

| Experiment | Factors and levels | Main expected benefit | Main trade-off or risk |
|---|---|---|---|
| B0: calibrated baseline | Existing routing, four inspectors, current queues/calendars, inferred informal batching | Reference distribution and backlog | Must reproduce current system before comparison |
| D1: document checker | Uptake 50%/80%; missing-document odds multiplier 0.7/0.4; pre-submit effort 0.25/1 day; abandonment 0%/2% | Fewer completeness loops and downstream starts with incomplete files | Applicant burden; delay shifted before formal submission; selective abandonment |
| D2: low-risk no-inspection | Skip 90%/100% of eligible Simple cases; optional 10% random audit; eligibility classification error varied | Removes inspection demand and shortens eligible cases | Compliance/safety risk; missing prior-violation data; planner demand may become the next bottleneck |
| D3: district batching | Maximum hold 0/1/2 business days; minimum batch 2/4; district route optimization on/off | Lower travel and more visits per field day | Longer wait for first case; possible district inequity |
| D4: peak inspector | Add 0.8/1.0 FTE in March–May and September–November | Peak backlog and inspection-tail reduction | Cost, recruitment feasibility, possible off-peak underuse |
| D5: legal pre-check | Commercial/Complex eligibility; 30%/60% of legal effort moved early; duplicate-work rate 0%/10% | Detects conflicts earlier and overlaps legal work with other reviews | Earlier legal load; duplicate work; can congest legal officers and delay other cases |
| D6: aging planner reserve | One planner reserved daily above 30/45 elapsed days; work-conserving fallback when no aged case exists | Reduces long tail and aged backlog | Some young/simple cases wait longer; throughput may fall if poorly implemented |
| D7: architect appointments | Uptake 50%/80%; Monday accepted-volume cap; slots redistributed Tuesday–Friday; missed-slot rate varied | Smooths clerical and planning arrivals | Applicant waiting moves upstream; access advantage for large architects; noncompliance |
| D8: environmental triage | 10/20-minute triage; two classifier operating points; low-risk fast queue and specialist assignment | Shorter environmental queues and better skill matching | False negatives, false positives, added triage work, environmental compliance risk |
| D9: objection early warning | Classifier sensitivity 0.65/0.85 and specificity 0.75/0.90; outreach capacity 0.5/1 FTE; extension odds multiplier 0.8/0.6 for contacted cases | Fewer or shorter severe objection extensions | Added workload; uncertain causal effect; may reveal objections previously not logged |
| D10: combined policy | D1 80% uptake, D2 with 10% audit, D3 one-day hold/minimum two, D4 +1 peak FTE | Broad reduction in document, inspection, and peak congestion | Interaction and implementation cost; D2 safety constraint; bottleneck can move to planning/legal |
| C1: inspection capacity package | D3 × D4 full factorial at listed levels | Tests whether batching and extra capacity substitute or complement each other | Added inspector may reduce the benefit of holding for batches |
| C2: tail-management package | D5 × D6 | Earlier conflict detection plus aged-case protection | Legal/planning congestion and priority spillovers |
| C3: front-door package | D1 × D7 | Better documents and smoother submissions | Greatest risk of shifting delay and effort to applicants |
| C4: review-risk package | D8 × D9 | Targeted environmental and objection handling | Compound classification and compliance risk |
| S1: demand surge | Cross B0, D1–D10, and shortlisted combinations with total demand +30%, peak/base ratio 2.1, architect burst sizes +50% | Tests capacity resilience | Queue instability and growing backlog |
| S2: specialist absence/calendar shock | One inspector unavailable for eight peak weeks; one legal officer unavailable for four weeks overlapping a council blackout; fire capacity 20% | Tests single-point specialist fragility | Severe tail and join delays |
| S3: objection/complexity shock | Complex share rises from 10% to 15%; objection odds ×2; objection-extension scale +25% | Tests notice, legal, and aging policies | Long-lived WIP and council-calendar congestion |
| S4: travel and no-show shock | D3/D5 travel +25%; inspection no-show odds ×1.5 | Tests D2–D4 and district fairness | More field capacity loss, especially in D3/D5 |
| S5: adverse policy behavior | Lower checker/appointment uptake; D8/D9 use lower operating point; D2 eligibility error at upper plausible bound | Tests implementation and data-quality risk | Benefits may disappear while safety or fairness risks remain |

A staged design is preferable:

1. Screen D1–D10 individually under the reference scenario.
2. Test all individual policies under at least S1–S3.
3. Estimate selected interactions through C1–C4 and D10.
4. Refine promising policies using response-surface levels, implementation costs, and pilot-derived effect distributions.

## 5. Warm-up, replications, and uncertainty treatment

### Initialization and run horizon

Two estimands should be maintained:

- **Implementation forecast:** initialize every policy with the same observed WIP snapshot, including case age, completed prerequisites, queued work, and any scheduled inspections.
- **Periodic long-run performance:** run a policy-specific warm-up to its seasonally periodic operating regime.

If a reliable WIP snapshot is available:

- Start on the actual implementation date.
- Evaluate at least 24 months so each policy experiences two peak cycles.
- Continue simulation long enough to observe completion of evaluation-entry cohorts, while reporting calendar-horizon backlog separately.

If WIP is unavailable:

- Use at least a 12-month seasonal warm-up, starting with generated arrivals and architect processes.
- Check monthly queue and age profiles over repeated years. Extend warm-up to 24 months if long Complex cases or backlog have not reached a stable annual pattern.
- Do not use a generic mean-based warm-up test that ignores annual seasonality.

Completed-case durations can be biased by truncating slow cases. Report both:

- cohort outcomes with sufficient follow-up or survival adjustment;
- operational backlog and age at fixed horizon dates.

### Replications and random numbers

- Begin with 30 pilot replications.
- Use approximately 100–200 paired replications for final comparisons; p95 and rare backlog outcomes may require more.
- Continue until the 95% interval half-width is, for example:
  - below 2% of the estimated median;
  - below 5% of the estimated p90;
  - below 1–2 percentage points for SLA compliance.
- Use common random numbers across baseline and interventions.
- Maintain separate random streams for background arrivals, architect bursts, attributes, service effort, routing, responses, objections, no-shows, travel, and absences.
- Prefer entity-keyed random draws so policy-induced event-order changes do not destroy all pairing.
- Store a master seed, scenario seed, replication seed, parameter-draw ID, and model version.

### Intervals

For aleatory simulation uncertainty:

- Use paired differences between each intervention and baseline.
- Report 95% bootstrap or t-based intervals for means where appropriate.
- Use replication-level bootstrap intervals for medians, p90/p95, SLA proportions, and fairness gaps.
- Report tail risk such as p95 and conditional tail mean, not just averages.

For parameter uncertainty:

- Bootstrap data by week and architect-week, or fit a hierarchical posterior.
- Draw an outer set of parameter vectors and an inner set of stochastic replications.
- A practical initial design is 100 parameter draws × 20 inner replications, refined around decision boundaries.
- Report aleatory and epistemic intervals separately as well as their combined predictive interval.

Intervention-effect uncertainty should also be sampled. For example, checker effectiveness, classifier accuracy, objection-outreach effect, and appointment uptake should not be fixed at favorable point values.

### Heavy-tailed durations

- Fit the body and tail separately where justified, using lognormal/log-logistic mixtures, generalized Pareto tails, or empirical bootstrap.
- Account for right-censoring and non-returned applicant requests.
- Do not truncate durations at p90.
- Any operational maximum or case-closure rule should be modeled as an explicit policy and sensitivity-tested.
- Use robust diagnostics, quantile intervals, survival curves, and conditional tail means.
- Conduct sensitivity tests for tail index, objection prevalence, no-response probability, and appeal/rework recurrence.

## 6. Validation strategy

### Face validation

Conduct structured walkthroughs with clerks, planners, fire and environmental reviewers, inspectors, legal staff, portal staff, applicants, and policy owners.

Validate:

- control flow and synchronization;
- actual queue disciplines;
- calendar behavior and handoffs;
- meaning of timestamps;
- rework and appeal return points;
- informal batching;
- council-week behavior;
- missing objection and emergency processes;
- intervention implementation assumptions.

Use animated case and resource traces and explain a small number of simulated cases end to end.

### Event-log replay validation

Run two replay modes:

1. **Control-flow replay:** use PM4Py token replay or alignments against the normative model, reporting fitness and deviations by type.
2. **Trace-conditioned simulation:** feed historical arrivals and observed case attributes into the simulation, while simulating service, resources, and routing where not fixed.

Compare simulated and observed:

- activity sequences and common variant shares;
- repeated activities;
- branch combinations;
- completion counts;
- monthly backlog;
- case duration distributions.

The performance DFG is a completion-to-completion diagnostic, not proof that service times are correct.

### Distributional validation

Validate by case type, district, value band, architect group, and month:

- arrival counts and overdispersion;
- weekday/hour profiles;
- architect burst-size and interarrival distributions;
- service effort where starts are observed;
- inter-event and inferred waiting distributions;
- median, p75, p90, p95, and survival curves;
- applicant-response and notice-duration tails;
- rework counts and outcomes;
- inspection bundle sizes, travel, and no-shows.

Reasonable initial tolerances are:

- common variant shares within about 2 percentage points;
- monthly/type counts within 5–10%;
- medians within 10%;
- p90s within 10–15%;
- wider tolerances for rare variants, accompanied by uncertainty intervals.

### Resource-utilization validation

Compare simulated utilization, assignments, overtime, and idle blocks with:

- HR available hours;
- known non-permit reservations;
- event-log resource counts;
- inspector schedules or GPS;
- manager estimates.

Validate both average utilization and peak-week saturation. A model can match duration for the wrong reason if service effort and calendar capacity are jointly miscalibrated.

### Bottleneck validation

The baseline should reproduce known qualitative bottlenecks:

- completeness spikes after Monday submissions;
- fire delay from the Tuesday–Thursday calendar;
- environmental variability and reserved capacity;
- D3/D5 travel effects;
- planning/type interactions;
- legal queues around holidays and council weeks;
- long tails for objections, applicant response, rework, and appeals.

Perform perturbation checks such as adding or removing one resource. The direction and rough magnitude of response should be operationally plausible. Implausible effects often reveal an incorrect join, calendar, or queue discipline.

### Out-of-sample validation

Use temporal and group holdouts, for example:

- first 12 months for fitting and final 6 months for testing;
- rolling-origin monthly tests;
- held-out districts or selected architect groups for hierarchical generalization.

No holdout month should be used to tune service distributions, seasonality, or queue priorities. Validate common-shock and dependency statistics in addition to case-level durations.

Direct validation of new interventions requires pilots where feasible:

- checker A/B or phased rollout;
- shadow D8/D9 classifications;
- inspection-batching pilot;
- temporary staffing period;
- random D2 safety audit.

## 7. Decision criteria

Use a constrained, Pareto-based decision rather than claiming an exact optimum. The following are proposed governance thresholds and should be replaced by statutory or council-approved targets.

| Dimension | Metric and proposed decision range |
|---|---|
| Median duration | Targeted type should improve by at least 5%; no non-targeted type should worsen by more than 5% |
| Tail duration | Target at least 10% reduction in p90 or p95 for the affected type; paired 95% interval should preferably exclude deterioration |
| SLA compliance | Measure both gross and legally paused clocks. Provisional calendar targets could be Simple 30d, New residential 90d, Commercial 120d, Complex 240d. Seek at least +3 percentage points for targeted types and no type worse by more than 2 points |
| Backlog stability | Completion/arrival ratio at least 0.99 over annual periods; no positive year-over-year backlog slope; total backlog not more than 2% above baseline |
| Aged WIP | Cases above the type-specific SLA or aging threshold should fall by at least 10–15%; maximum/99th-percentile age must not worsen materially |
| District fairness | Risk-standardized p90 ratio between highest and lowest district no greater than about 1.25; no district gap worsens by more than 3 calendar days without explicit justification |
| Architect fairness | Compare top-20 architects with smaller architects after standardizing for case mix. SLA gap should not worsen by more than 5 percentage points; appointment access and upstream waiting must be reported |
| Rework | Target at least 10% reduction in the rework type addressed by the intervention; no material increase in downstream legal or inspection rework |
| Resource utilization | Average critical-pool utilization generally 70–85%; avoid utilization above 90% for more than four consecutive weeks; report overtime and unavailable-calendar hours |
| Applicant burden | Report pre-submit effort, appointment delay, number of contacts, abandonment, and formal-case time. A shorter formal clock is insufficient if total journey time worsens |
| Inspection/environmental safety | D2 and D8 require non-inferiority on audit failures, later violations, complaints, and severe false negatives. Without these data, recommendation is conditional rather than final |
| Cost | Report incremental staff, IT, outreach, training, and applicant cost per permit and per SLA-compliant case |
| Robustness | A preferred policy should remain beneficial in at least 80–90% of parameter draws, avoid material harm under S1–S3, and have no unresolved safety/fairness gate |
| Statistical relevance | Use paired effect intervals and probabilities of meeting thresholds, not p-values alone |
| Practicality | Include implementation time, legal authority, union/HR constraints, data availability, and reversibility |

An intervention should be shortlisted only if it:

1. Keeps the system stable.
2. Passes safety and legal constraints.
3. Improves at least one primary duration/SLA outcome.
4. Does not create unacceptable district, architect, or applicant inequity.
5. Remains useful under plausible parameter and stress uncertainty.
6. Is non-dominated in cost, service, fairness, and risk.

## 8. Python skeleton

The skeleton below uses pandas for CSV loading and PM4Py for log/model diagnostics. It deliberately leaves the calendar-aware simulation engine separate.

The simplified process-tree string may parse in PM4Py versions supporting `->`, `X`, `+`, `*`, and `tau`. Parsing does not resolve its semantic gaps: the observed second `Completeness check`, appeals, objections, and rare exceptions require model revision after conformance analysis.

def load_and_format_log(
    csv_path: Optional[str | Path] = None,
    local_timezone: Optional[str] = None,
) -> pd.DataFrame:
    """
    Load with pandas, never pm4py.read_csv (which is not the relevant API).

    In production, local_timezone should be the municipality's IANA timezone.
    Source-system timestamp semantics must be confirmed before localization.
    """
    if csv_path is None:
        raw = pd.read_csv(StringIO(EXCERPT_CSV))
    else:
        raw = pd.read_csv(csv_path)

    raw[COMPLETE_TS] = pd.to_datetime(raw[COMPLETE_TS], errors="raise")

    if local_timezone is not None and raw[COMPLETE_TS].dt.tz is None:
        raw[COMPLETE_TS] = raw[COMPLETE_TS].dt.tz_localize(
            local_timezone,
            ambiguous="infer",
            nonexistent="shift_forward",
        )

    # PM4Py accepts pandas DataFrames. This also adds/normalizes PM4Py indices.
    formatted = pm4py.format_dataframe(
        raw,
        case_id=CASE_ID,
        activity_key=ACTIVITY,
        timestamp_key=COMPLETE_TS,
    )
    return formatted


def parse_nominal_process_tree():
    """
    Parse the supplied normative tree.

    Limitations:
      * the loop label 'Completeness rework' does not exactly explain the
        repeated Completeness check in P001;
      * appeals and objection episodes are omitted;
      * a successfully parsed tree is not evidence of conformance.
    """
    compact = " ".join(PROCESS_TREE_TEXT.split())
    try:
        tree = pm4py.parse_process_tree(compact)
        return tree
    except Exception as exc:
        warnings.warn(
            "The installed PM4Py parser could not parse the simplified tree. "
            "Check PM4Py version/operator grammar, or construct/import a "
            "reviewed BPMN/Petri-net model instead. Error: " + repr(exc)
        )
        return None


def add_observed_timing_columns(
    log_df: pd.DataFrame,
    start_col: str = "start_timestamp",
    enabled_col: str = "enabled_timestamp",
) -> pd.DataFrame:
    """
    Add timing columns without claiming that completion-to-completion gaps are
    service or queue waiting.

    service_seconds is available only with a valid activity start timestamp.
    waiting_seconds requires a valid enable/queue-entry timestamp as well.
    In a parallel process, previous case completion is not generally the
    activity's enablement timestamp.
    """
    out = log_df.copy()
    out = out.sort_values([CASE_ID, COMPLETE_TS], kind="stable")

    out["previous_completion_timestamp"] = (
        out.groupby(CASE_ID, sort=False)[COMPLETE_TS].shift(1)
    )
    out["inter_event_seconds"] = (
        out[COMPLETE_TS] - out["previous_completion_timestamp"]
    ).dt.total_seconds()

    out["service_seconds"] = np.nan
    out["waiting_seconds"] = np.nan
    out["candidate_previous_event_gap_seconds"] = np.nan

    if start_col in out.columns:
        out[start_col] = pd.to_datetime(out[start_col], errors="coerce")

        out["service_seconds"] = (
            out[COMPLETE_TS] - out[start_col]
        ).dt.total_seconds()

        # This is only a diagnostic and must not be labeled true waiting.
        out["candidate_previous_event_gap_seconds"] = (
            out[start_col] - out["previous_completion_timestamp"]
        ).dt.total_seconds()

        if enabled_col in out.columns:
            out[enabled_col] = pd.to_datetime(out[enabled_col], errors="coerce")
            out["waiting_seconds"] = (
                out[start_col] - out[enabled_col]
            ).dt.total_seconds()

    out["negative_service_flag"] = out["service_seconds"] < 0
    out["negative_wait_flag"] = out["waiting_seconds"] < 0
    return out


def compute_pm4py_diagnostics(log_df: pd.DataFrame) -> dict[str, Any]:
    """
    Standard PM4Py high-level diagnostics.

    A performance DFG computed from a completion-only log describes elapsed
    edge time. It does not isolate service time.
    """
    variants = pm4py.get_variants(log_df)

    dfg, start_activities, end_activities = pm4py.discover_dfg(log_df)

    performance_dfg, perf_starts, perf_ends = (
        pm4py.discover_performance_dfg(log_df)
    )

    # Typically returned in seconds. It is only an overall diagnostic;
    # the simulation must fit a non-stationary arrival model.
    case_arrival_average = pm4py.get_case_arrival_average(log_df)

    # Explicit counts are useful because PM4Py variant return representations
    # can differ across versions.
    ordered = log_df.sort_values([CASE_ID, COMPLETE_TS], kind="stable")
    variant_counts = (
        ordered.groupby(CASE_ID, sort=False)[ACTIVITY]
        .agg(tuple)
        .value_counts()
    )

    return {
        "pm4py_variants": variants,
        "variant_counts": variant_counts,
        "frequency_dfg": dfg,
        "start_activities": start_activities,
        "end_activities": end_activities,
        "performance_dfg": performance_dfg,
        "performance_start_activities": perf_starts,
        "performance_end_activities": perf_ends,
        "case_arrival_average_seconds": case_arrival_average,
    }


def convert_tree_for_conformance(tree):
    """Convert a parsed process tree to a Petri net for replay/alignment."""
    if tree is None:
        return None
    net, initial_marking, final_marking = pm4py.convert_to_petri_net(tree)
    return net, initial_marking, final_marking

@dataclass

    name: str
    weekly_intervals: WeeklyIntervals
    holidays: set[date] = field(default_factory=set)
    blackout_ranges: list[tuple[datetime, datetime]] = field(
        default_factory=list
    )
    available_fraction: float = 1.0

    def is_open(self, at: datetime) -> bool:
        """Placeholder; production code must handle timezone and exceptions."""
        if at.date() in self.holidays:
            return False

        for start, end in self.blackout_ranges:
            if start <= at < end:
                return False

        intervals = self.weekly_intervals.get(at.weekday(), ())
        return any(start <= at.time() < end for start, end in intervals)

class PermitSimulation:
    """
    Calendar-aware discrete-event engine interface.

    A SimPy implementation would:
      * create skill-constrained queues;
      * seize/release resources;
      * pause work while calendars are closed;
      * synchronize parallel reviews at an AND-join;
      * create applicant/consultant timeout events;
      * create objection episodes shared by related cases;
      * build district inspection tours;
      * record enable/start/pause/complete lifecycle events.
    """

    def __init__(
        self,
        parameters: SimulationParameters,
        intervention: InterventionConfig,
        arrival_generator: ArrivalGenerator,
        seed: int,

        self.parameters = parameters
        self.intervention = intervention
        self.arrival_generator = arrival_generator
        self.seed = seed

        self,
        start: datetime,

        raise NotImplementedError(

class SimulationFactory(Protocol):
    def __call__(
        self,
        intervention: InterventionConfig,
        seed: int,
    ) -> PermitSimulation:
        ...


def run_experiment(
    intervention: InterventionConfig,
    engine_factory: SimulationFactory,
    start: datetime,
    end: datetime,
    drain_until: Optional[datetime],
    replications: int = 100,
    master_seed: int = 20260301,
) -> pd.DataFrame:
    """
    Generic experiment runner.

    For paired comparisons, call baseline and intervention with the same
    master seed and implement stable, stream-specific/entity-keyed RNGs inside
    the engine.
    """
    seed_sequence = np.random.SeedSequence(master_seed)
    child_sequences = seed_sequence.spawn(replications)

    records: list[dict[str, Any]] = []

    for replication, child in enumerate(child_sequences):
        seed = int(child.generate_state(1, dtype=np.uint32)[0])
        engine = engine_factory(intervention, seed)
        metrics = dict(engine.run(start, end, drain_until=drain_until))

        records.append(
            {
                "experiment": intervention.name,
                "replication": replication,
                "seed": seed,
                **metrics,
            }
        )

    return pd.DataFrame.from_records(records)
