## 1. Duplicate-handling decision tree

The pipeline must navigate ambiguity without assuming physical truth. The decision tree begins by assessing data identity, then moves to semantic overlap, and finally checks for business causality.

1.  **Exact Technical Duplicate:** If `source_event_key`, `payload_hash`, and `timestamp` match across different ingestion paths, this is a technical redundancy.
    *   *Action:* Drop one instance; retain the other with `source_event_key` preserved.
2.  **Same Physical Event Observed by Multiple Systems:** If `related objects` are identical, `activity` is harmonized, but `source` differs (e.g., WMS vs. Scanner), check payload similarity.
    *   *Action:* Merge attributes (union), retain both events with a `multi-source` qualifier to preserve provenance.
3.  **Summary Event Derived from Detailed Event:** If one event aggregates attributes of another (e.g., ERP summary vs. WMS detail) and `timestamp` gaps exist, treat as hierarchy.
    *   *Action:* Retain both unchanged. Add a `derivation` relation. Do not merge.
4.  **Harmonization Collision:** If source systems use different labels for distinct business realities (e.g., WMS "Dispatch" vs. Carrier "Acceptance"), verify causal link.
    *   *Action:* Retain both unchanged. Do not force label harmonization unless business context confirms equivalence.
5.  **Concurrent Same-Label Events:** If `activity` and `timestamp` match but `related objects` differ (e.g., multiple picks), they are distinct.
    *   *Action:* Retain both unchanged.
6.  **Unresolved Candidate:** If ambiguity persists after fact-checking.
    *   *Action:* Quarantine for review. Do not drop or merge.

## 3. Timestamp-tie ordering rules

Determining order when `timestamp` is identical requires a layered approach that distinguishes between domain constraints and arbitrary determinism.

*   **Domain Constraints:** Lifecycle constraints on shared objects are semantic. For example, `Pick` must precede `Pack`. If `e03` (Pick) and `e06` (Pack) share a second-level timestamp, the domain model dictates `e03` < `e06`.
*   **Within-Source Sequence:** `source_seq` is meaningful only within one system. If `e08` (WMS) and `e09` (Carrier) share a timestamp, `source_seq` cannot be used to order them directly without external context.
*   **Lifecycle Constraints:** Object creation precedes object disposition. `O1` creation (`e01`) must precede `P1` creation (`e06`).
*   **Source-Specific Semantics:** If activities differ (e.g., WMS `Dispatch` vs. Carrier `Accept`), semantic precedence rules apply based on Fact 5.
*   **Ingestion Time:** `ingested_at` is a technical artifact and must not drive business order, as ingestion order is not guaranteed to match business order.
*   **Stable Fallback:** If no semantic rule applies, use `source_event_key` lexicographically.

**Why Microseconds are False Stories:**
Adding microseconds to force a total order (e.g., `10:00:00.000001`) encodes a false story. It implies the WMS scanner physically triggered the event a nanosecond before the ERP system, which is physically impossible or irrelevant. It introduces artificial precision that suggests a causality that does not exist in the business domain. The OCEL must reflect the uncertainty of the timestamp, not the certainty of the sort key.

**Intended Order:**
*   **10:00 Events:** e03 (Pick I1) < e04 (Pick I1 Alt) < e05 (Pick I2) < e06 (Pack).
*   **10:15 Events:** e08 (WMS Dispatch) < e09 (Carrier Accept) < e10 (Handover).
*   **12:00 Events:** e11 (ERP Invoice) < e16 (Billing Invoice) < e12 (Auth M1) < e13 (Capture M1) < e14 (Capture M2) < e15 (ERP Summary).

## 4. Conservative cleaning pipeline

The conservative pipeline prioritizes data fidelity over reduction. It assumes that every event in the raw log has a potential business justification unless proven otherwise.

1.  **Grouping:** Identify candidate duplicates using `payload_hash` and `related objects` similarity.
2.  **Filtering:** Apply the decision tree from Section 1. Only "Exact Technical Duplicate" candidates are dropped.
3.  **Refinement:** For "Same Physical Event" pairs (e.g., e03/e04), retain both but add a metadata tag `is_observed_by=[source1, source2]`.
4.  **Summary Handling:** For e06/e07 and e13/e15, do not merge. Instead, create a `derived_from` relation.
5.  **Ordering:** Apply the timestamp tie-breaking rules from Section 3.
6.  **Validation:** Check referential integrity on objects.

**Expected Retained Event Count:**
Starting with 17 events, conservative cleaning will drop only exact technical duplicates (none in this specific dataset based on `source_event_key` uniqueness). The count remains 17. However, the logical graph size increases due to the addition of `derived_from` relations. This ensures no business nuance is lost, such as the distinction between the WMS and ERP views of the packing process.

## 5. Aggressive alternatives

Two aggressive scenarios demonstrate the risks of over-optimization.

**Scenario A: Evidence-based Semantic Merging**
This approach attempts to merge e03/e04 and e11/e16 based on Fact 1 and Fact 6.
*   **Expected Count:** 15 events.
*   **Semantic Damage:** Merging e03/e04 loses the location enrichment provided by WMS, which might be critical for warehouse efficiency analysis. Merging e11/e16 assumes ERP and Billing systems agree on all attributes, potentially hiding discrepancies between systems that auditors need to see.

**Scenario B: Mechanically Aggressive PM4Py Merging**
This applies `ocel_merge_duplicates` to all events with equal `activity` and `timestamp`.
*   **Expected Count:** ~10 events.
*   **Semantic Damage:** This would likely merge e13 and e14. While they share `O1` and `V1`, they represent distinct Payment objects (M1 vs. M2). Merging them destroys the granularity of the payment ledger. It assumes that two "Capture Payment" events at the same time for the same Invoice are the same transaction, which is false.
*   **Why `have_common_object=True` Fails:** `have_common_object=True` checks if events share `O1` or `V1`. It does not check if they share the specific transaction object instance (e.g., Payment M1 vs. M2). Relying on shared Invoice objects conflates the order level with the payment execution level, leading to data loss in financial auditing.

## 8. Audit trail and reversibility

To ensure the pipeline is reversible and auditable, a provenance schema `event_provenance` must be maintained alongside the OCEL.

**Schema Fields:**
*   `canonical_event_id`: The new ID in the cleaned log.
*   `source_event_ids`: List of original IDs (e.g., `['e03', 'e04']`).
*   `merge_rule`: String identifier of the logic used (e.g., `conservative_union`).
*   `reviewer`: User ID or system version.
*   `original_activity`: Original label.
*   `refined_activity`: New label if changed.
*   `original_timestamp`: The UTC timestamp.
*   `adjusted_timestamp`: The timestamp after sorting.
*   `attributes_retained`: List of fields kept from each source.
*   `discarded_conflicts`: List of conflicting values (e.g., `payload.location`).
*   `confidence`: Score (0.0-1.0).

**Reconstruction:**
An analyst can reconstruct the raw view by joining `event_provenance` back to the original raw data source using `source_event_ids`. This allows the analyst to see exactly which raw events contributed to a cleaned event and why conflicts were resolved. This transparency prevents "black box" data loss.

## 9. Failure modes and safeguards

1.  **Collapsing distinct partial payments:** If the pipeline merges e13 and e14, the total payment amount becomes incorrect for financial reconciliation. *Safeguard:* Check `payload_hash` before merging.
2.  **Converting abstraction-level updates into false rework:** Merging e06 and e07 might hide the fact that WMS packed before ERP acknowledged it. *Safeguard:* Retain both with `derived_from` relation.
3.  **Ordering by ingestion time:** Using `ingested_at` might order e09 before e08 if WMS was slower. *Safeguard:* Use `timestamp` first, `source_seq` second.
4.  **Treating shared objects as proof of duplication:** e13 and e14 share `O1`. Merging them based on this is incorrect. *Safeguard:* Check `related objects` depth (Payment object vs. Order object).
5.  **Unioning incompatible E2O relations:** Merging e03 and e04 might lose the WMS location attribute. *Safeguard:* Union payloads only if compatible types.
6.  **Changing durations through synthetic microseconds:** Adding `0.001` seconds to force order implies a timeline that never existed. *Safeguard:* Do not modify `timestamp`.
7.  **Losing source-authoritative attributes:** If ERP is authoritative for Invoice Date, but Billing is authoritative for Tax, merging might average them. *Safeguard:* Retain distinct rows.
8.  **Applying duplicate functions to the whole OCEL without inspecting candidate groups:** Running `ocel_drop_duplicates` blindly might drop e05. *Safeguard:* Pre-check groups as per Section 6.

This pipeline ensures that the OCEL remains a faithful representation of the business reality, preserving the complexity of the multi-system environment rather than simplifying it at the cost of truth. By explicitly defining conservative and aggressive modes, stakeholders can choose the level of abstraction required for their specific analytical goals, whether that is operational efficiency or forensic auditing.
