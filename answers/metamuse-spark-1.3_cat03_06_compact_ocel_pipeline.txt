## 1. Modeling assumptions
**Object types and capitalization:** singular PascalCase consistently used in `objects.ocel:type`, `relations.ocel:type` and flattening keys: `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`.

- `Order`: O100, O200
- `Item`: I1, I2, I3
- `Package`: P1, P2
- `Delivery`: D1, D2
- `Invoice`: V1
- `Payment`: M1, M2

**E2O qualifier vocabulary — consistent per activity × object-type:**
- `Create Order`: Order=`creates`
- `Add Item`: Item=`adds`, Order=`in_order`
- `Reserve Stock`: Item=`reserves`, Order=`reserves_for`
- `Pack Package`: Package=`packs`, Item=`packed`, Order=`packs_for`
- `Dispatch Package`: Delivery=`dispatches`, Package=`dispatched`, Order=`fulfills`
- `Issue Invoice`: Invoice=`issues`, Order=`billed`
- `Record Payment`: Payment=`records`, Invoice=`settles`, Order=`settled_for`
- `Confirm Delivery`: Delivery=`confirms`, Package=`confirmed`, Order=`fulfills`
- `Close Order`: Order=`closes`

Verbs without suffix (`creates`, `packs`, `dispatches`, `issues`, `settles`, `confirms`) denote the operationally primary object. Suffixed qualifiers (`in_order`, `packs_for`, `fulfills`, `billed`, `settled_for`, `reserves_for`) explicitly mark contextual / analytically propagated involvement.

**O2O direction conventions — container/carrier  content:**
- `Order -contains-> Item`: `ocel:oid`=Order, `ocel:oid_2`=Item
- `Package -packs-> Item`: `ocel:oid`=Package, `ocel:oid_2`=Item
- `Delivery -carries-> Package`: `ocel:oid`=Delivery, `ocel:oid_2`=Package
- `Invoice -bills-> Order`: `ocel:oid`=Invoice, `ocel:oid_2`=Order
- `Payment -partially_settles-> Invoice` for M1, `Payment -completes_settlement-> Invoice` for M2: `ocel:oid`=Payment, `ocel:oid_2`=Invoice. M2 is `completes_settlement` because 100+150 settles V1.

**Direct vs propagated relations:** Logistics (`Dispatch`, `Confirm`) and financial (`Issue`, `Record Payment`) events are directly related to `Order` in `relations` to allow end-to-end `Order` flattening. They are generally not directly related to `Item` downstream of Pack/Reserve: Item reachability for Dispatch/Confirm/Invoice/Payment is via O2O (`Order-contains-Item`, `Package-packs-Item`). `Reserve Stock` and `Pack Package` relate directly to both `Item` and `Order` because joint reservation and cross-order packing are operational facts.

Trade-off: direct source-only relations preserve system truth but fragment `Order` traces and hide convergence. Rich analytical propagation enables `Order`-centric DFG/skeleton discovery but inflates event fan-out, duplicates shared events on flattening, and creates false precedence.

**Preventing confusion of propagation with source facts:** OCEL 2.0 `relations` does not carry a source/derived flag. Ground truth is kept in `o2o` plus primary qualifiers. Propagated Order links use distinct qualifiers (`packs_for`, `fulfills`, `billed`, `settled_for`, `reserves_for`, `in_order`) and are documented here as analytical convenience, not as claims that the WMS/TMS/billing system wrote those foreign keys. No O2O row is invented to justify an E2O propagation.

**Version-dependent assumption:** `from pm4py.objects.ocel.obj import OCEL` and function names `ocel_flattening`, `discover_ocdfg`, `discover_otg`, `discover_etot`, `discover_oc_petri_net`, `ocel_get_object_types`, `ocel_object_type_activities`, `ocel_objects_interactions_summary` follow the task specification. If installed PM4Py exposes `OCEL` elsewhere or renames flattening/discovery, only the import and constructor line and thin wrappers should change; `events`, `objects`, `relations`, `o2o` semantics stay unchanged.

## 4. Expected flattened behavior
Order flattening: O100 trace about 14 events: CreateAdd I1Add I2ReservePack P1Pack P2Dispatch P1Dispatch P2IssuePayment M1Confirm D1Confirm D2Payment M2Close. O200 trace about 10 events: CreateAdd I3ReservePack P1Dispatch P1IssuePayment M1Confirm D1Payment M2Close. Copied shared events: Reserve, Pack P1, Dispatch P1, Confirm D1, Issue, both payments. Omitted: nothing major — this is the end-to-end view by design. Likely DFG edges: CreateAddReservePackDispatchIssueRecordConfirm interleaved with Pack P2/Dispatch P2 branches for O100; Record Payment self-loop (M1M2 both map to Record Payment). Misleading: implies sequential causality between P1 and P2 logistics, implies O100 waited for D1 confirm before D2, double-counts invoice/payments, suggests O200 caused P1 alone.

Package flattening: P1: Pack P1Dispatch P1Confirm D1. P2: Pack P2Dispatch P2Confirm D2. Copied: none — packages are disjoint. Omitted: order creation, Add Item, Reserve Stock, all finance, Close Order. Likely DFG: single linear chain PackDispatchConfirm per package. Misleading: hides that P1 needed joint stock and two Orders; Reserve disappearance makes packing look unconstrained.

Delivery flattening: D1: Dispatch P1Confirm D1 (3-hour gap). D2: Dispatch P2Confirm D2 (23-hour gap). Omitted: all upstream packing and all finance. Likely DFG: one edge DispatchConfirm. Misleading: looks trivial and independent; hides P1 cross-order effect and that D1 confirmation preceded D2 dispatch by 20h without causal link.

Invoice flattening: V1: IssueRecord M1Record M2. Omitted: all logistics and order closures. Likely DFG: IssueRecord PaymentRecord Payment self-loop. Misleading: self-loop collapses M1 and M2 into repetition; without amount attribute the two payments look identical; Order split (O100/O200) invisible.

Why Payment flattening is weak: M1 occurs only in E12, M2 only in E15. Each trace is a singleton with no transitions, so DFG is empty, skeleton has no always/never relations, and no throughput can be inferred. Payment behavior only makes sense jointly with Invoice (V1) as the linking object.

## 5. Expected object-centric structures
OC-DFG: expected per-type edges preserve local lifecycles while shared activities connect types. Pack PackageDispatch PackageConfirm Delivery should appear for Package and Delivery with matching frequencies (P1/D1 and P2/D2). Order edges span creation to close but fork at Pack/Dispatch. Cross-order convergence visible at Reserve Stock, Pack P1, Dispatch D1, Confirm D1, Issue V1, and both Record Payments, each annotated with multiple object types. P1 is the bridge: its Pack edge carries Order+Item+Package, unlike P2 which carries only O100. V1 fans to both O100 and O200, and M1 then M2 both point to V1 with increasing amounts.

OTG: expected hub nodes O100 (high degree: I1,I2,P1,P2,D1,D2,V1,M1,M2 via E2O/O2O) and V1 (bills both Orders, settled by both Payments). O200 degree smaller but linked to P1/D1 through shared events, revealing that O200 depends on a package also containing O100 goods. P1 connects to two Items from different Orders, the only such Package. M1 and M2 both connect to V1 but not to each other except via V1.

ET–OT graph: expected dense columns for Reserve, Pack P1, Dispatch D1, Confirm D1, Issue, Record Payments touching Order+one or more other types. Close Order touches only Order; Create Order touches only Order; Add Item touches Item+Order. This immediately distinguishes lifecycle-private events from synchronizing events.

Object-centric Petri net: expected place per object type with transitions replicating the OC-DFG, with variable arcs for synchronizing transitions (e.g., Pack P1 consumes two Item tokens and two Order tokens but one Package token; Issue consumes/produces one Invoice and two Order tokens). V1 enables two payment transitions (M1 partial, M2 completing) on the Invoice/Payment places while Order places show both O100 and O200 waiting for settlement. No single total order is forced; concurrent Package/Delivery branches for O100 remain concurrent. Any single net visualization is one defensible replay, not uniquely determined.

Object-interactions summary: expected highest interaction counts Order–Item (adds/reserves/packs), Order–Package, Order–Delivery via propagated fulfills, and Invoice–Order (bills). Payment–Invoice appears twice (M1 partial, M2 complete). P1–I1/P1–I3 and O100–O200 co-occurrence via shared events should rank high despite no direct O100–O200 O2O row.

## 6. Modeling alternatives
Source-minimal relations: relate each event only to objects its source system would directly write — e.g., Dispatch only to Delivery+Package, Issue only to Invoice, Payment only to Payment+Invoice, Confirm only to Delivery, Pack only to Package+Item. Consequence without changing business story: Order traces fragment (CreateAddReserveClose only), Order DFG loses logistics/finance, Invoice DFG loses Order context, but convergence/divergence metrics are conservative and counts are not duplicated. Analysis must then traverse O2O to reconstruct end-to-end flow.

Full operational involvement: relate every downstream event to all operationally affected objects including Items — e.g., Dispatch/Confirm also to I1/I2/I3, Issue/Payment also to Items. Consequence: Item traces become end-to-end (AddReservePackDispatchConfirmIssuePayment) and Item DFG looks complete, but divergence explodes (E7/E9/E13 fan to 5+ objects), flattening duplicates events even more, and false Item-level precedence (e.g., I1payment causality) appears.

O2O-propagated analytical relations: keep E2O source-minimal and generate a second analytical view by joining through O2O at query time (e.g., infer Order link for Dispatch via Delivery-carries-Package-packs-Item + Order-contains-Item). Consequence: base tables stay truthful, Order flattening can be reproduced on demand, but discovery results depend on propagation rules (one-hop vs transitive, temporal bounds). Different propagation choices yield different OC-DFG frequencies from identical source facts, making reproducibility depend on documenting the rule.

## 7. Failure modes
Relation inflation: linking every event to Orders and Items maximizes Order trace completeness but multiplies E2O rows (here 47 vs ~25 minimal), inflates activity frequencies per object type, and makes every shared event look like Order synchronization.

Missing direct E2O links: omitting Order from Dispatch/Confirm/Issue/Payment to stay minimal breaks Order flattening; Order DFG then suggests orders close without shipment or payment, and skeleton misses IssuePayment ordering for Orders.

Treating O2O propagation as observation: counting inferred Order–Payment links as if the billing system recorded them conflates structural reachability with event observation; e.g., claiming M1 was allocated 50/50 to O100/O200 when narrative only says partial settlement of V1.

Duplicate shared events after flattening: Reserve, Pack P1, Issue, M1/M2 appear in both O100 and O200 traces, so naive counts double-report revenue, shipments, and confirmations; DFG frequencies sum to twice reality.

Ambiguous payment allocation: V1 bills two Orders but M1/M2 settle V1 as a whole; without allocation logic no per-Order outstanding balance can be derived; assigning full 100+150 to each Order overstates settlement.

Overly short Payment traces: flattening on Payment yields singletons (M1, M2 alone) with no edges; running DFG/skeleton on them returns degenerate models that invite over-interpretation of noise as structure.

Constructor/API version mismatch: different PM4Py versions expect different OCEL constructors (`OCEL(...)` vs `OCELProj` vs dict-based) or rename `ocel_flattening`/`discover_ocdfg`; blindly adapting by reshaping tables (e.g., dropping qualifiers) silently changes semantics — only import/constructor wrappers should change.

False total order for same-time events: this dataset has distinct timestamps, but generally sorting flattened traces by timestamp alone imposes a total order where source systems recorded concurrency (e.g., Pack P1 vs Pack P2 five minutes apart is ordered, but Reserve for I1/I3 jointly is truly simultaneous). Assuming timestamp order equals causality creates false DFG edges; ties would need tie-breakers or partial-order preservation.

## 8. Final semantic checks
A reviewer can manually verify narrative conformance by inspecting the tables:

- Events has 17 rows with unique E1–E17, timezone-aware timestamps from 2026-04-06 08:00 UTC to 2026-04-07 10:35 UTC, and amount only on E12=100 and E15=150, otherwise empty.
- Objects has 12 rows: O100/O200 are Order, I1/I2/I3 are Item, P1/P2 are Package, D1/D2 are Delivery, V1 is Invoice, M1/M2 are Payment.
- Relations repeats activity/timestamp from events for every row, has no duplicates, and every oid exists in objects; E6 has 4 rows (I1,I3,O100,O200) and E7 has 5 rows (P1,I1,I3,O100,O200).
- O2O contains P1I1, P1I3 proving cross-order package, O100I1/I2 and O200I3 proving order contents, D1P1/D2P2, V1O100/V1O200, M1V1 partially_settles and M2V1 completes_settlement.
