# 5. Robustness and alternative explanations

-   **Analysis Shift:** Treating as single person forces us to discard overlap (assume error). Treating as shared account allows us to calculate aggregate throughput but loses individual utilization metrics.

### Exact Timestamps vs. Interval-Censored
-   **Scenario:** Assume G7 timestamps are exact vs. rounded to nearest 15 mins.
-   **Impact:** If exact, G7 shows perfect batching (all start 14:00, end 14:15). If rounded (context states "rounds down/up"), actual start could range 13:45-14:00 and end 14:15-14:30.
-   **Analysis Shift:** If censored, we cannot compute service time variance. We must treat G7 service time as a distribution $[0, 30]$ mins rather than a point estimate of 15 mins. This widens confidence intervals for any downstream simulation.

### Three Cases Supporting Multiple Explanations
1.  **G1 (Identical Start/End):**

-   **Action:** Automate `start` and `complete` triggers. For G6 (Close ticket), disable manual bulk forms. Require individual case closure triggers.
-   **Reason:** Eliminates G6-style zero-service-time artifacts.

**Priority 2: Recording Timestamps & Clocks**
-   **Action:** Synchronize all source clocks (Scanner, PLC, Tablet, MES) to a central NTP server.
-   **Reason:** G8 notes safety system clock drift; un-synced clocks invalidate queue analysis across systems.

**Priority 3: Resource/Badge Identity**
-   **Action:** Replace shared logins (`analyst_pool`) with individual badge scans or biometrics.
-   **Reason:** Resolves G5 ambiguity between concurrency and shared accounts, enabling accurate utilization calculation.

**Priority 4: Group/Batch Identifiers**
-   **Action:** If batching is operational (G1, G2), add a `batch_id` field linking related cases.
-   **Reason:** Allows process miners to treat the batch as a single entity for performance analysis without distorting individual case metrics.

**Priority 5: Pause/Resume Events**
-   **Action:** Log interruptions (e.g., safety check in G8) as explicit events.
-   **Reason:** Distinguishes waiting (queue) from interruption (downtime), clarifying why G8 queue arrives at 15:00 but starts at 15:38.

**Priority 6: Timestamp Precision Metadata**
-   **Action:** Store precision metadata alongside every event (e.g., `is_rounded=True`).
-   **Reason:** Enables G7 analysis to account for interval censoring during statistical modeling.

# 7. Final adjudication

**High Confidence Interpretation:**
-   **G1 (Robot):** Operational batch confirmed by fixture constraints. Treat as single unit for cell utilization, or split with fixed offset for individual throughput.
-   **G4, G8 (Sequential):** Clear serial execution. Valid for standard conformance checking and bottleneck analysis.
-   **G6 (Bulk Close):** Confirmed logging artifact. **Exclude** from service time calculations. Use `recorded_at` as proxy for completion time if necessary, but acknowledge high uncertainty.

**Excluded / Interval-Censored:**
-   **G7 (MES):** Due to 15-min rounding and undocumented rules, exclude from precise service time analysis. Use for volume counts only. Mark queue analysis as unreliable due to start/end rounding.
-   **G6 (Queue Wait):** Waiting time is inflated by the 17:00 cap. Report as "Upper Bound Waiting Time".

**Requires Operational Validation:**
-   **G5 (Analyst Pool):** Cannot proceed with resource utilization analysis without confirming if `analyst_pool` maps to 1, 2, or 3 individuals. If >1, split the resource ID in the log.
-   **G2, G3 (Group Buttons):** Validate if "Start" is truly simultaneous or just logged simultaneously. If physical work starts sequentially but logs together, service time is underestimated. Recommend spot-checking video or sensor data.
