**Cause of the conformance drop vs. real operational concern.** The measured collapse from 93% to 32% is caused overwhelmingly by hypotheses 1, 2, and 3 — three *measurement* mechanisms that together account for 32%→89% in Jun-Jul without any behavioural assumption — plus hypothesis 4 for the Aug-Sep leg. ```

Measured fitness is not a property of the process; it is a property of the join between a normative model and a recorded log, and every arrow into `recorded_labels`, `recorded_order`, or `normative_model` moves it without anyone doing anything differently. Four independent mechanisms landed inside one hundred days. A rename detached `Classify` from its model transition, converting every case into a paired log-and-model move. A gateway inserted an unmodelled event into 85% of traces, adding a second log move each. An ETL switch to ingestion time inverted a causally forced pair in 70 cases. A policy added a real control the model never learned. These compose roughly additively in alignment cost, which is why the staged repairs recover fitness in clean increments — 32, 58, 81, 89 — each step neutralizing one mechanism and leaving the next exposed. The order of repair matters interpretively: what looks like "employees skipping checks" in the raw log is largely the shadow of the earlier layers.

Unchanged approval, appeal, and cycle-time series are consistent with measurement error but do not prove it: an aggregate of 620 cases can absorb 30 bypasses without a detectable shift, and appeals only surface harm that the customer notices and contests. Conversely, flat outcomes do not rule out noncompliance, because the compliance function itself says detection is incomplete — absence of confirmed incidents is a statement about detection, not about occurrence. The residue that survives all four repairs, the enhanced reviews without a compliance check, is precisely the part the outcome data is least able to adjudicate; it is exactly ambiguous between a missing event and a real bypass, and only provenance work can separate them.

def variants_to_log(variant_counts):
    """Build an EventLog from a {trace_string: count} mapping.

    pm4py.parse_event_log_string expects trace strings whose activities are
    separated by a separator character; we use "," and keep activity names
    with embedded spaces intact.
    """
    trace_strings = []
    for trace, count in variant_counts.items():
        trace_strings.extend([trace] * count)
    return pm4py.parse_event_log_string(trace_strings, sep=",")


log_apr_may = variants_to_log(APR_MAY)
log_jun_jul = variants_to_log(JUN_JUL)

# ---------------------------------------------------------------------------
# 3. Normalization pipeline (transparent, reversible, one step at a time)
# ---------------------------------------------------------------------------

LABEL_MAP = {"Risk Screen": "Classify"}
TECHNICAL_EVENTS = {"Queue Routed"}


def normalize(log, apply_label_map=False, drop_technical=False):
    """Return a new log with the requested normalization steps applied.

    We go through a DataFrame so the transformation is explicit and auditable,
    then convert back to an EventLog.
    """
    df = pm4py.convert_to_dataframe(log)

    if apply_label_map:
        df["concept:name"] = df["concept:name"].replace(LABEL_MAP)

    if drop_technical:
        df = df[~df["concept:name"].isin(TECHNICAL_EVENTS)]

    df = df.sort_values(["case:concept:name", "time:timestamp"])
    df = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp",
    )
    return pm4py.convert_to_event_log(df)

def show_dfg(log, title, edges_of_interest=None):
    dfg, start_acts, end_acts = pm4py.discover_dfg(log)
    print(f"\n--- DFG: {title} ---")
    print(f"start activities: {dict(start_acts)}")
    print(f"end activities:   {dict(end_acts)}")
    if edges_of_interest:
        for edge in edges_of_interest:
            print(f"  {edge[0]} -> {edge[1]}: {dfg.get(edge, 0)}")
    else:
        for edge, count in sorted(dfg.items(), key=lambda kv: -kv[1])[:10]:
            print(f"  {edge[0]} -> {edge[1]}: {count}")
    return dfg

def evaluate(log, pn, i_m, f_m, label):
    fitness = pm4py.fitness_alignments(log, pn, i_m, f_m)
    print(f"\n=== {label} ===")
    print(f"  trace fitness (avg)  : {fitness['average_trace_fitness']:.3f}")
    print(f"  perc. fitting traces : {fitness['percentage_of_fitting_traces']:.1f}%")
    print(f"  log fitness          : {fitness['log_fitness']:.3f}")
    return fitness


def deviation_profile(log, pn, i_m, f_m, label, top=8):
    """Aggregate the visible log moves and model moves across all alignments."""
    diagnostics = pm4py.conformance_diagnostics_alignments(log, pn, i_m, f_m)
    log_moves, model_moves = {}, {}
    for aligned in diagnostics:
        if aligned is None:
            continue
        for log_step, model_step in aligned["alignment"]:
            if log_step != ">>" and model_step == ">>":
                log_moves[log_step] = log_moves.get(log_step, 0) + 1
            elif log_step == ">>" and model_step not in (">>", None):
                # skip invisible (tau) transitions: they carry no label
                model_moves[model_step] = model_moves.get(model_step, 0) + 1
    print(f"\n--- deviation profile: {label} ---")
    print("  dominant moves on log:")
    for act, cnt in sorted(log_moves.items(), key=lambda kv: -kv[1])[:top]:
        print(f"    {act}: {cnt}")
    print("  dominant visible moves on model:")
    for act, cnt in sorted(model_moves.items(), key=lambda kv: -kv[1])[:top]:
        print(f"    {act}: {cnt}")
    return log_moves, model_moves

## 7. Provisional conclusion

**Primary explanation for the measured collapse (high confidence, ~90%).** The fall from 93% to 32% fitting traces is predominantly a measurement failure, not a process failure. Three dated, independently documented changes each inserted a systematic mismatch between the log and an unchanged normative model: the 2026-05-31 rename of `Classify` to `Risk Screen`, the 2026-06-03 introduction of the technical event `Queue Routed` across roughly 85% of cases, and the 2026-06-15 ETL switch to warehouse-ingestion time that inverted `Decision` and `Notify` in 70 traces. The staged repairs are the decisive evidence: relabelling alone recovers 32%→58%, technical-event removal 58%→81%, and source-sequence ordering 81%→89% — all without a single assumption about behaviour. The Aug-Sep leg has a fourth, different cause: a real policy change on 2026-08-01 introduced `Supervisor Sign-off` while the normative tree was never versioned. That is model obsolescence, and its signature is clean — 210 cases, both branches, always immediately before `Decision`.

**Whether a real compliance problem remains (moderate confidence that one may, ~40% that it is a genuine bypass).** Yes, potentially, and it is not the thing the headline number was measuring. Fifty-five enhanced-review cases across the two periods reach `Decision` with no recorded `Compliance Check`, and this residue survives every repair. It is genuinely undetermined between an extraction gap and a real bypass; no audit has been done. Flat approval, appeal, and cycle-time series do not exonerate it — 55 cases in ~1,270 would not move those aggregates, and compliance itself states its detection is incomplete. `Manual Override`, up from 20 to 35, is similarly unresolved, and the 2026-08-12 logging patch confounds a rise in occurrence with a rise in visibility. Separately, the un-versioned model means the EUR 50,000 control is currently unverifiable at all — a governance exposure independent of anyone's conduct.

**Immediate actions.** IT: publish the 4.2 event-name mapping, classify `Queue Routed` and `Manual Override` against the resource field, and repoint the conformance job at the source sequence number rather than ingestion time; explain the 30 cases still emitting `Classify` and the 90 without `Queue Routed`. Process owners: version the normative model to include `Supervisor Sign-off`, but prefer a value-stratified mandatory model over a blanket optional element, and report precision alongside fitness. Compliance: commission a stratified case-file audit of the 55 no-check cases and the 59 unverified reversed cases, and join the high-value attribute so the EUR 50,000 rule can actually be tested.

**What must not be claimed yet.** Do not claim reviewers became noncompliant — the raw increase in moves on log is almost entirely explained by measurement layers, and the residue is unadjudicated. Do not claim the process is now conformant because fitness recovered — the optional-sign-off model buys fitness with permissiveness and cannot enforce the amount condition. Do not claim `Manual Override` increased in reality until the logging patch is controlled for. Do not treat compliance's "no confirmed incidents" as clearance; by their own statement it is a fact about detection.

## 8. Model-governance recommendation

1. **Model versioning bound to policy.** Every normative model carries a version, an effective-date range, and a link to the policy text it encodes. No policy change may take effect without a corresponding model version released on or before the same date, and conformance results must always be reported as a (log-period, model-version) pair. A conformance drop whose onset coincides with a policy date is a governance defect, never a behavioural finding.

2. **Event-semantic contracts.** Activity names in the log are a versioned interface contract between the source system and analytics, not a UI cosmetic. Any release that renames, splits, merges, or retires an event must ship a machine-readable mapping from old to new identifiers, and stable non-display event IDs must underlie the human-readable labels so that a screen caption change cannot break conformance at all.

3. **Technical-event policy.** Every emitted event is classified at emission time as business or technical, with a mandatory actor/resource attribute for business events and an explicit system marker for technical ones. Technical events are excluded from conformance by default via a declared, auditable filter list; introducing a new event type requires a classification decision and an assessment of coverage, including why coverage is partial when it is.

4. **Timestamp provenance.** Every timestamp declares its semantics — source occurrence, source recording, or warehouse ingestion — and ordering for conformance uses source occurrence or a source sequence number, never ingestion time. Where a sequence number exists it must be carried end to end and used as the tiebreaker; ETL changes that alter timestamp semantics require a formal impact review and a regression check on directly-follows relations before release.

5. **Data-aware constraints.** Rules conditioned on case data (the EUR 50,000 sign-off trigger) must be expressed as data-aware or decision-aware constraints, or implemented as stratified control-flow models per attribute value, and never as blanket optional elements. Case attributes needed to evaluate a control are mandatory joins in the conformance job, and fitness must always be reported with precision so that permissiveness cannot masquerade as compliance.

6. **Post-release validation.** Every UI, gateway, ETL, or policy release triggers an automatic pre/post conformance regression on a fixed reference cohort, comparing variant sets, DFG edges, activity vocabularies, events-per-case, and missing-attribute rates. A vocabulary change or a fitness shift beyond a set threshold blocks promotion of the analytics pipeline until reconciled, and any conformance deterioration is investigated as a data-quality incident first and a behavioural finding only after nominal mechanisms are excluded.
