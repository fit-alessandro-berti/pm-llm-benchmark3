## 1. Equivalence design space

Let an execution be a typed temporal graph containing events, objects, event-to-object (E2O) incidences, O2O relations and qualifiers, and strict event precedence.

**Activity-sequence equivalence \(R_A\).** Executions are equivalent when their activity-label sequences are identical. This preserves activity order, repetition, and counts of activity occurrences, but discards object types, multiplicities, identity across events, E2O/O2O topology, externality, and qualifiers. It is reflexive, symmetric, and transitive because it is equality of sequences. With concurrent events, arbitrary timestamp tie-breaking must not determine the result: compare activity-labelled partial orders, treating simultaneous events as unordered.

**Typed structural equivalence \(R_T\).** Executions are equivalent when their graphs are isomorphic. An isomorphism must map the lead `Order` to the lead `Order`, preserve activity labels, strict precedence, object types, local/external status, E2O incidence, O2O relation labels and qualifiers, and map local identifiers bijectively. Thus `I11` may be renamed `I22`, but a local item cannot become an external item. This preserves exact wiring and multiplicities while discarding identifier spelling, absolute timestamps, durations, and unstated business interpretation. Graph isomorphism is an equivalence relation. For concurrency, only strict precedence edges are retained; same-time or genuinely independent events need not be ordered.

**Preferred business-semantic equivalence \(R_B\).** Define a feature vector \(\beta(x)\) and set \(x\sim_B y\) exactly when \(\beta(x)=\beta(y)\). The vector contains:

1. local multiplicities `(Item, Package, Delivery, Invoice, Payment)`;
2. external sharing by stage—`logistics` or `finance`—external object type, and multiplicity;
3. fulfilment motif: `single`, `split-consolidated`, `split-multi-delivery`, or `return-repack`;
4. settlement motif: single payment, multiple payments to one invoice, and whether cross-order payment lacks order allocation;
5. exception motif: clean, pre-dispatch content replacement/removal, or post-dispatch return/rework.

Consequently, \(R_B\) can merge executions with different detailed wiring or independent-event interleavings, but not when those differences change a listed business feature. It discards exact item-to-package assignments and timestamps unless they change a motif. It is an equivalence relation by feature-vector equality. Features involving before/after are derived only from strict partial-order constraints; unresolved ordering receives an `unknown` marker rather than an invented sequence.

## 2. Canonical signatures

For \(R_T\), use a canonical graph serialization \(\gamma\). For the preferred clustering, apply the deterministic projection \(\beta\) above. The following exhaustive renaming is practical for these small executions; production implementations can use a labelled-graph canonizer.

```python
from itertools import permutations, product

def graph_signature(x):
    # x.objects: oid -> (type, external_flag, lead_flag)
    # x.time_groups: timestamp-ordered groups; events within a group are tied
    # x.events[e].incidence: E2O rows for event e
    # x.o2o: (source, relation, qualifier, target)
    buckets = {}
    for oid, (typ, ext, lead) in x.objects.items():
        buckets.setdefault((typ, ext, lead), []).append(oid)

    keys = sorted(buckets)
    for k in keys:
        buckets[k] = sorted(buckets[k])  # only determines search order
    inventory = tuple(sorted((k, len(buckets[k])) for k in keys))
    best = None

    choices = product(*(permutations(buckets[k]) for k in keys))
    for choice in choices:
        rename = {}
        for k, permutation in zip(keys, choice):
            for j, oid in enumerate(permutation):
                rename[oid] = (k, j)

        groups = []
        for tied_events in x.time_groups:
            serialized_events = []
            for e in tied_events:
                incidence = tuple(sorted(
                    (rename[r.object_id], getattr(r, "role", ""))
                    for r in e.incidence
                ))
                serialized_events.append((e.activity, incidence))
            groups.append(tuple(sorted(serialized_events)))

        o2o = tuple(sorted(
            (rename[r.source], r.relation, r.qualifier, rename[r.target])
            for r in x.o2o
        ))
        candidate = repr((inventory, tuple(groups), o2o))
        best = candidate if best is None else min(best, candidate)

    return best
```

This preserves repeated activities, cross-event object identity, concurrency groups, external sharing patterns, and qualifiers, but no raw identifiers. The preferred signature is `preferred_signature(x) = beta(x)`. Its fulfilment rules are deterministic: return activity takes precedence and yields `return-repack`; otherwise multiple packages with multiple deliveries yield `split-multi-delivery`, multiple packages with one delivery yield `split-consolidated`, and otherwise fulfilment is `single`. Qualified item replacement changes the exception feature; package replacement in X8 does not get misclassified as X7 because the return motif takes precedence.

## 4. Cluster interpretations

Reasonable repair below means identifier normalization, reordering only genuinely simultaneous events, and removing exact technical duplicates—not deleting external links, qualifiers, or qualified payments.

**B0 — clean-isolated.** Signature: one local package, delivery, invoice, and payment, with no exception or sharing. This is the standard fulfilment-and-settlement path and a useful baseline for service-time and first-pass-yield measurement. Order flattening is adequate for a basic activity SLA, but is a poor equivalence key because X5–X7 produce the same activity trace. The cluster is highly stable under reasonable repair.

**B1 — split-consolidated.** Signature: two item-specific packages consolidated into one delivery. It represents packing fragmentation without transport fragmentation; opportunities include cartonization review while retaining consolidated shipping. Order flattening shows repeated `Pack Package` but not the package-item partition; package flattening can duplicate the shared dispatch and obscure consolidation. It is stable unless distinct packages are incorrectly merged.

**B2 — staged-multi-settlement.** Signature: two packages, two deliveries, and two payments against one invoice. This supports staged fulfilment and partial-then-complete settlement, with risks around delivery dependencies, outstanding-balance calculation, and mistaken payment deduplication. Order flattening preserves the long trace but not shipment/payment wiring; treating the two payments as duplicates would be especially harmful. Stability is medium-high because settlement semantics depend on retaining both payments and their qualifiers.

**B3 — shared-logistics.** Signature: baseline local financial counts, but P51 also contains an external item and Pack/Dispatch involve an external order. This is consolidation across order lifecycles, creating capacity, ownership, delay-propagation, and cost-allocation questions; billing only O5 is a fact to review, not automatically an error. Order flattening makes it look like B0, while package/delivery flattening can mix orders and omit order-only financial events. It is stable only while external participation is preserved.

**B4 — shared-finance.** Signature: isolated baseline logistics but one invoice bills O6 and EXT-OB, settled by one payment without order-level allocation. Consolidated billing may be desirable, but order-level receivables, dunning, revenue allocation, and payment confirmation are ambiguous. Order flattening incorrectly suggests B0; invoice-centric analysis is needed to expose the coupling. It is stable under identifier repair, but projecting away EXT-OB or inventing an allocation changes its meaning.

**B5 — pre-dispatch-content-change.** Signature: one package/delivery financially, with replacement and `removed_before_dispatch` evidence, plus item incidence on Dispatch. The business issue is substitution or content correction before shipment, with inventory, serial-number, customer-authorization, and billed-versus-shipped risks. Activity flattening hides it; package flattening without qualifiers can wrongly suggest both original items remained shipped. Stability is medium because the strongest temporal interpretation depends on qualified O2O information.

**B6 — return-repack.** Signature: dispatch, return, inspection, repack into P82, and redispatch through D82, followed by invoice/payment. This is a reverse-logistics and recovery loop, not merely a second forward shipment. Risks include rework cost, inventory/state consistency, and repeat-delivery customer impact; no refund or inspection outcome is inferred. Order flattening at least exposes return activities, but item/package flattening is needed for causality. It is highly stable while those activities remain.

## 5. Borderline cases

- **X1 versus X2:** Raw serialization separates them, and an item-identifier-sensitive definition could also interpret the Add-item order as different. Typed isomorphism swaps I11/I12 appropriately and equates them; \(R_A\) and \(R_B\) agree. There is no supplied semantic reason to preserve the identifier order.
- **X1 versus X5:** Activity-sequence and lead-order-local equivalence equate them. Typed and preferred semantic equivalence separate them because logistics is not isolated. Ignoring external objects deliberately reproduces the former answer.
- **X1 versus X6:** Logistics-only or activity equivalence equates them. Finance-aware equivalence separates them: X6 has shared settlement scope and no order allocation, despite baseline local multiplicities.
- **X1 versus X7:** Activity plus local-count equivalence can equate them if it also ignores E2O roles and O2O qualifiers. Qualified lifecycle semantics separates them. Typed structure is stricter still: the extra `Item:I72` incidence on Dispatch prevents structural equivalence even before using the removal qualifier.
- **X3 versus X4:** A coarse “multi-package fulfilment” segmentation puts them together. Delivery- and settlement-aware semantics separates consolidated transport/single payment from staged transport/two payments. Neither total- nor partial-order activity equivalence makes them identical.
- **X4 versus X8:** Logistics multiplicity alone sees `(2 items, 2 packages, 2 deliveries)` in both and may equate them. Behavioral equivalence does not: X4 has two forward fulfilment chains, whereas X8’s second packing is causally preceded by return and inspection. Payment multiplicity provides an additional distinction.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py’s helper should be understood as exact execution-key clustering, not typed graph isomorphism or business clustering. Its key serializes the extracted event/object execution information—activities and E2O relation tuples with concrete object identity/type information, together with the exact event/order fields used by that implementation. Thus exact incidence and repetitions survive; sorting rows does not rename identifiers. O2O qualifiers, `EXT` lifecycle semantics, invoice allocation, and my motifs are not automatically added. Key and return details should be checked against the pinned PM4Py version.

Consequently, X1 and X2 can receive different exact keys solely because their concrete identifiers differ. Canonicalize each returned execution with \(\gamma\), then optionally aggregate by \(\beta\); never simply delete IDs, since that would also erase sharing and incidence patterns.

Exact equivalence is preferable for ingestion regression tests, duplicate extraction detection, and forensic comparison. It is usually too fine for operational segmentation. `max_objs` is an engineering safeguard, not a semantic coarsening control. Shared packages or invoices can produce very large connected executions; size cut-offs can reduce memory/key-construction work but may leave oversized components outside useful output. Track coverage and retain an overflow bucket rather than silently truncating them, especially for compliance.

## 7. Robustness analysis

- **Ignore all O2O qualifiers:** X4 still has two payments, but their partial/completion interpretation weakens. X8 remains identifiable from return/inspection activities. X7 remains replacement-related if `replaces` survives, although its pre-dispatch timing may become uncertain; if replacement/removal information is discarded entirely and Dispatch item incidence is also projected away, it collapses toward B0.
- **Ignore external objects:** X5 and X6 both acquire the local baseline projection and join B0 semantically. This is useful for a deliberately local view, but unsuitable for coupling or financial-risk analysis.
- **Collapse repeated same-label events:** Consecutive collapse makes A0 and A1 activity-normalized forms identical; global collapse can also hide X4’s repeated Pack/Dispatch/Payment pattern. Preferred semantic clusters need not change if object and payment multiplicities remain. Collapsing those objects as well would destroy, rather than repair, evidence.
- **Use a Pack/Dispatch partial order:** X4 becomes two potentially independent package-delivery chains rather than one meaningful total interleaving. X3 still requires both packs before its consolidated dispatch, and X8 retains the return-before-repack chain. No additional pair among X1–X8 becomes equivalent solely from this change.
- **Represent payment multiplicity as an amount attribute:** X4 loses its two-settlement structural distinction, assuming a legitimate amount attribute exists, but remains separate from X3 through two deliveries and from X8 through the return loop. Compliance analysis should nevertheless retain the original payment events.

## 8. Limitations and recommendation

For **compliance monitoring**, use qualifier- and externality-aware **typed structural equivalence**, supplemented by rule-specific semantic tests; apparently minor wiring differences can be violations. For **operational segmentation**, use the preferred **business-semantic equivalence**, balancing actionable distinctions against identifier noise. For **root-cause analysis**, begin with **exact instance execution comparison**, retaining raw IDs, timestamps, and full topology for drill-down rather than prematurely clustering. For **descriptive reporting**, use coarser semantic families—standard, fragmented fulfilment, cross-order coupling, and return/content exceptions—with subtypes such as B1/B2 and B3/B4 retained in notes.

No single notion is optimal: compliance rewards sensitivity, operations rewards manageable segments, root-cause analysis rewards evidential detail, and reporting rewards stable aggregation. Activity-only reporting is especially inadequate here because it makes five materially different executions look identical.
