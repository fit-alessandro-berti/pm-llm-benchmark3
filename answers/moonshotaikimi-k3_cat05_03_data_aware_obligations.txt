## 1. Temporal Data Semantics

**State reconstruction (last-write-wins under event-time order).** For each case I sort events by `(time:timestamp, event_index)` and define a strict within-case order `` (lexicographic). The value of attribute `a` "as of" event `e` is the value written by the latest event `e0` in the same case with `e0  e` that writes `a`. Blank cells are *no-update* (they never overwrite), so a blank is ignored rather than read as null. This is a forward-only fill: information at `e` can only come from writes ` e`; nothing is ever propagated backward.

**Equal timestamps.** When two events share a timestamp, `event_index` is the tie-breaker (R7). Consequence (TX-311): at 16:20, `event_index=3` (Enhanced_Review) precedes `event_index=4` (Update_JurisdictionDE). **Material changes.** A *trigger-affecting* change is any post-creation write to `jurisdiction`, `customer_type`, or `risk_level` (these switch obligations on/off). An *amount* change is material for amount-dependent obligations only per R4: an increase `>20%` over the last known amount invalidates the latest Standard/Enhanced review; a decrease does not; an increase from an *unknown* baseline is not safely classifiable (R4/R6) and is flagged, not decided. **Four clocks.** I distinguish (i) *event time* = `time:timestamp` of the business event; (ii) *effective time* = `effective_from`/expiry of an exemption or list; (iii) *record time* = when a row was inserted (e.g., `Record_Exemption` at 11:00); (iv) *evidence time* = when trustworthy proof of approval came into existence (qualified-signature time). ## 4. Ambiguities and Alternative Readings

**TX-305 (INDETERMINATE).** Decisive unknown = release-time amount. Flips to **NONCOMPLIANT** if an immutable, signed release payload shows amount  100000 (R1 triggers; the 11:15 Enhanced_Review "has no amount," so it cannot have discharged an amount-dependent obligation, and there is no exemption). Flips to **COMPLIANT** if a trustworthy payload shows amount < 100000 (R1 off; no other rule triggered). The next-day settlement of 150000 is reliable at settlement time and "may equal" the release amount, but equating them would be final-state leakage (R7); it raises suspicion without resolving the trigger (R6).

**TX-310 (primary NONCOMPLIANT, Medium confidence).** The trigger is clear (AE, 200000) and there is no Enhanced_Review, so everything rests on EX-88. Under R5 the proponent must show approval existed at the relevant time; the only strong artifact (qualified certificate) was created at 10:30, after the 10:00 release, the displayed 08:50 is backdated and "alone is not conclusive," and the oral-approval witness is the requester (interested). It flips to **JUSTIFIED_EXCEPTION** if independent evidence corroborates approval at/before 10:00 (e.g., a qualified signature actually timestamped 10:00, an approver's contemporaneous log, or a disinterested witness). A stricter reading that wholly disregards oral approvals hardens NONCOMPLIANT; a lenient reading that credits the requester's testimony yields JUSTIFIED_EXCEPTION — the audit-burden reading (R5) is why I land on NONCOMPLIANT.

**TX-302 (COMPLIANT).** Even if one (incorrectly) doubted the Enhanced_Review's sufficiency, EX-77 independently justifies release: the 11:00 `Record_Exemption` is *record time*; the *evidence time* is the qualified signature at 09:05 (hash valid, outage documented), which precedes the 09:40 release. It would flip to NONCOMPLIANT only if the signature were shown to be created after 09:40 or the scope did not cover 180000 — neither holds. This is the clean contrast to TX-310: late *recording* is excused by timely *evidence*; backdated *display* contradicted by late *evidence* is not.

**TX-311 (COMPLIANT).** Everything hinges on the tie-breaker. With `event_index` 34 at 16:20, the Enhanced_Review ran while the case was still US/115000 (foreign high-value), and the jurisdiction became DE only afterward; at the 16:30 release the *current* jurisdiction is DE, so R1's condition is false and no obligation is owed. If one ignored `event_index` and treated the two 16:20 events as simultaneous, the review-time jurisdiction would be ambiguous (US or DE), and — worse — if one *also* required the review to post-date the latest material change, the ER (idx3) would precede the jurisdiction change (idx4). That counterfactual only matters if jurisdiction had stayed non-DE; because the change made the case domestic, it switches R1 off rather than resetting a review clock. It would flip to NONCOMPLIANT only if a later event re-set jurisdiction to non-DE before release, or if evidence showed the DE update was erroneous/backdated.

**TX-306 (COMPLIANT) — alternative reading.** A strict "any post-approval amount change reopens approval" reading would demand re-approval after 12:30. I reject it because R4 fixes amount materiality at >20% (the +4.5% note is deliberate) and R2 concerns risk/PEP, which did not change. It would flip if the 12:30 update were shown to be one of a structuring pattern (multiple sub-20% increases cumulatively >20%) or if risk/customer type also changed.

**TX-307 (NONCOMPLIANT) — alternative reading.** One could defend that hc03 substantively performed enhanced due diligence despite the "standard packet" label. Under the stated semantic fact (a CA over only a standard packet does not cure the absence of an Enhanced_Review) and the explicit "Standard_Review is not an Enhanced_Review," that defense fails absent evidence the CA actually applied enhanced procedures to the PEP relationship. It flips to COMPLIANT only with proof the 13:12 approval executed enhanced (not standard) controls for the newly matched PEP beneficial owner.

**TX-309 (NONCOMPLIANT) — measurement note.** The invalidating increase is measured from the amount the Enhanced_Review actually saw (118000) to 145000 = +22.9% (>20%), so the 15:25 ER is invalidated regardless of the earlier 95k118k step. It would flip only if a further Enhanced_Review between 15:28 and 15:35 existed (none does) or if the 15:28 update were documented as a correction restoring a previously reviewed amount (it is labeled an increase).

```python
    print(f"  {case}: control-flow R1={cf_r1} R2={cf_r2}   <-- compare to data-aware:",
          diag.loc[diag.case == case, "suggested_label"].iloc[0])
# NOTE: a precedence template only checks activity order. It cannot see that TX-309's ER precedes a >20%
# increase (R4), that TX-305's amount is unknown (R6), that TX-311's tie is broken by event_index (R7),
# or that EX-88's approval evidence post-dates release (R5). Hence conditional data obligations need the
# state reconstruction above; control-flow conformance alone is necessary-at-most, never sufficient.
```

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** A Declare/data-unaware check that reads the case's final attributes would import TX-305's next-day settlement (150000) into the release decision, or read TX-311's final jurisdiction (DE) back into the 16:20 review. R7 forbids this; only writes `` the event may govern it.
2. **Post-hoc / backdated exemptions.** Control flow sees a `Record_Exemption` activity and an `exemption_id` at release, but cannot separate *record time* (11:00 insert) from *evidence time* (qualified signature 09:05 for EX-77 vs certificate created 10:30 for EX-88). EX-77 is valid despite late recording; EX-88 is unproven despite a timely-looking displayed field. That distinction is evidential, not structural.
3. **Material change after review (moving reference).** A precedence template `Enhanced_Review  Release` **passes** TX-309 and TX-301 even though a >20% increase sits between the review and release (R4). The obligation is "review after the *latest* material change," a target that moves with the data; pure ordering cannot express it.
4. **Conditional activation.** Whether R1/R2/R3 fire at all depends on release-time data (jurisdictionDE, amount100000, HIGH/PEP, listed jurisdiction). TX-311 contains an Enhanced_Review yet owes nothing at release (jurisdiction became DE); a hypothetical trace could contain every "right" activity while the condition is off, or omit them while the condition is on. Control flow cannot see the condition.
5. **Missing / unknown data.** "Amount unknown" (TX-305) has no activity-graph signature; a conformance run would silently treat the case as if the threshold were not met (a low-risk default R6 prohibits). Data-aware checking must surface INDETERMINATE rather than pass/fail.
6. **Same-timestamp ordering.** TX-311's two 16:20 events are indistinguishable to a timestamp-only engine; `event_index` (34) decides that the review preceded the jurisdiction change. Conformance without a stable tie-breaker can invert cause and effect.
7. **Activity identity vs. granularity.** `Standard_Review` is not `Enhanced_Review`, and a `Compliance_Approve` over a *standard* packet does not discharge an enhanced obligation (TX-307, TX-310). A template that counts "a review" or "an approval" generically would falsely pass both.
8. **Scope matching is data, not flow.** Exemption validity requires jurisdiction/customer-type/amount-ceiling matching plus effective/expiry windows (R5). No control-flow template encodes "amount  250000" or "effective_from  trigger < expires."

## 7. Recommended Logging and Control Improvements

- **Immutable release payload.** At `Release_Funds`, write a signed hash of the exact decision snapshot `{amount, currency, risk_level, jurisdiction, customer_type, sanctions_list_version, rule_version}` so later events (e.g., settlement) can never be mistaken for the release state (fixes TX-305).
- **Separate the clocks.** Store `effective_from`, `expires_at`, `approval_time`, `record_time` (DB insert), and `signature_time` (qualified timestamp) as distinct fields, plus the signing-certificate creation time; never let a displayed `approval_time` be editable apart from the signature (fixes EX-88 backdating; preserves EX-77's outage excuse).
- **Rule versioning.** Stamp each obligation evaluation with `rule_version` and the evaluated inputs so decisions are replayable when thresholds (e.g., 100000, 20%) change.
- **Structured exemption scope.** Persist scope as machine-checkable fields (jurisdiction set, customer-type set, amount_min/max, rules waived) with Head_Compliance's qualified signature and expiry; require the scope check to be computed, not asserted.
- **Change provenance.** Every update event carries old_valuenew_value, source system, reason code, and actor; amount changes must state the baseline so the >20% test (R4) is computable and "increase from unknown" is explicitly flagged rather than silently passed.
- **Stable global ordering.** Make `event_index` mandatory and monotonic per case (or use a vector/sequence clock), and forbid two business events sharing a key; record clock-sync source (UTC/NTP).
- **Explicit unknowns and negatives.** Use a distinct `UNKNOWN` sentinel (not blank) for feed outages, and log negative facts (e.g., "no exemption," "PEP match rescinded") so absence-of-event is distinguishable from absence-of-evidence.
- **Review-to-snapshot binding.** Each Standard/Enhanced review embeds the hash of the data snapshot it reviewed, so a later material change is mechanically detectable and a review that "has no amount" (TX-305) is rejected at capture.
- **Sanctions lineage.** Reference the exact list version at each `Sanctions_Screen` and at release, and emit a rescreen task automatically when the current jurisdiction is listed between screen and release (R3).
- **Independence and tamper evidence.** Enforce segregation of duties (an approver/witness cannot be the requester), and keep the log append-only with hash chaining and idempotency keys so late inserts (outages) are provable and backdating is detectable.
