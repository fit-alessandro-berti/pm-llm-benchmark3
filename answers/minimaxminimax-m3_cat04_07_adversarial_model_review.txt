# Process-Mining Model Review: Custom-Order Dossier Workflow

**Reviewer:** Independent Process-Mining Expert
**Date:** 2026-Q1
**Subject:** Model S (Simple & Permissive) vs. Model C (Complex & Precise) — Critical Multi-Criteria Assessment and Third Alternative Design
**Distribution:** Model-Governance Board, Internal Audit, Process Owner, IT Architecture, Discovery Teams

---

## Executive Summary

This report reviews two process models discovered for a custom-order dossier workflow under conditions of substantial ambiguity: two data attributes required to ground the policy (`external/internal` flag, `affected check` after a correction) are missing from the event log, and the discovery teams used the same 80/20 split without publishing seeds, preprocessing code, or alignment-cost configurations. Neither submission, as presented, is safe to deploy. Model S **fails on compliance** (admits traces that bypass mandatory checks); Model C **fails on maintainability and generalizability** (enumerates training branches, produces duplicate labels, and rejects plausible unseen combinations with poor holdout behavior). A third alternative is proposed that uses a procedural backbone for mandatory sequencing and optional branching, supplemented with declarative guards for the two unknown attributes. The governance recommendation distinguishes exploration from enforcement, requires soundness verification and a curated negative suite before any deployment, and explicitly retires Model S from any compliance use.

---

## 1. Review Scope and Assumptions

**Three intended use cases are distinguished, because each implies a different acceptable trade-off between the reported metrics.**

| Use case | Primary need | Acceptable fitness | Acceptable precision | Acceptable complexity | When Model S / C could be acceptable |
|---|---|---|---|---|---|
| **Exploration** (data triage, hypothesis generation) | Recall of variants in log; cheap iteration | High ( 0.95) | Low is tolerable if honestly framed as exploration | Low to medium | Model S is acceptable for exploration, with caveats about under-fitting; Model C is over-restrictive |
| **Conformance enforcement** (audit, automated case handling) | Faithfulness to mandatory rules; clear rejections on known-forbidden patterns | High ( 0.95) | High (mandatory activities should not be skippable) | Medium | Neither as presented; Model S fails (silent skips), Model C fails (over-rejection, duplicate labels) |
| **Simulation / what-if** | Behavioral variety; ability to parameterize | Medium-high | Not the central concern | Medium-high | Model S simulates too much; Model C simulates too little |
| **Stakeholder communication** | Readable, defensible to non-analysts | N/A | N/A | Very low (process tree, not 200 edges) | Model S is preferable for communication; Model C is not |

**Key assumption about the unknown attributes:** Because `external/internal` and `affected check` are not in the log, **silently promoting activities to optional is not a valid modeling move** — it converts an evidence gap into policy. The third alternative should treat these as guard-conditions that gate optional behavior rather than swallowing it into a permissive OR.

## 3. Adversarial Review of Model S

### 3.1 Strongest case for Model S

Model S is a four-tier tree that captures the *scaffolding* of the process: a unique start, a parallel block of all four checks (with `tau`/silent skips), an exclusive choice between the two approvals, and a unique end. **For an exploration tool used by an analyst to triage deviations**, this is genuinely useful: it does not over-constrain the data, the parallel block makes it visible at a glance that the checks are not strictly ordered (only Credit Check and Technical Review are known to be order-flexible), and its simplicity gives it a 0.918 simplicity score and 0.018 s alignment runtime that no other model here can match. Its 0.907 token-based generalization and 0.981 holdout fitness suggest that it generalizes *to the data as observed*, even if not to the policy.

### 3.2 Strongest case against Model S

The same `+` block that gives S its elegance is its **policy-fatal flaw**: any combination of checks — including *none* — is admitted before approval. This is not noise tolerance; it is a silent transition that erases the *mandatory* status of Credit Check and Technical Review.

### 3.3 Concrete admitted behaviors (traces, not just prose)

The following traces are all accepted by Model S; each is policy-ambiguous or clearly policy-violating:

1. **`<Register Dossier, Manager Approval, Release Order>`** (B3) — accepted. Both mandatory checks are skipped. **Policy: forbidden.** S accepts because the parallel block is closed with all `tau` skips.
2. **`<Register Dossier, Expedite Review, Credit Check, Technical Review, Manager Approval, Release Order>`** (B4) — accepted. Expedite Review precedes both mandatory checks. **Policy: forbidden (P4).** S accepts because the parallel block allows Expedite Review to fire before the others; nothing in the model enforces "after both mandatory checks."
3. **`<Register Dossier, Credit Check, Technical Review, Manager Approval, Release Order>`** followed by another `<Credit Check, Manager Approval>` later in the same case — **accepted**, with no requirement for a preceding `Correct Dossier`. **Policy: suspicious (P7).**
4. **`<Register Dossier, Credit Check, Credit Check, Manager Approval, Release Order>`** — accepted. **Policy: forbidden** unless a correction preceded; S has no such notion.
5. **`<Register Dossier, Manager Approval, Auto Approval, Release Order>`** — accepted. **Policy: forbidden (P5: exactly one).** S uses `X(Manager Approval, Auto Approval)` but the *parallel* parent block is over-approximated; the exclusive choice is nested, not at the top, and trace semantics may admit both. **Uncertain** without `play_out`; should be verified.
6. **`<Register Dossier, Manager Approval, Manager Approval, Manager Approval, Release Order>`** — accepted in principle (loops in X are unconstrained). **Policy: ambiguous at best; likely forbidden.**
7. **`<Register Dossier, Credit Check, Technical Review, Correct Dossier, Credit Check, Technical Review, Manager Approval, Release Order>`** — accepted, *and equally* `<Correct Dossier, Credit Check>` without Technical Review repeat would also be accepted. **Policy: P6 is silent on which check is affected.** S does not distinguish.

### 3.4 Intentional vs. accidental permissiveness

Of the seven admissions, **(1), (2), and (5) are silent-transition artifacts of the `+` block — accidental semantic flaws, not noise tolerance.** (3), (4), (6), and (7) are consequences of using silent transitions to model mandatory repetition and exclusive choice that should have been expressed declaratively. The "exploration-not-enforcement" defense (F7) does not hold for the *policy-violating* admissions; the model does not merely tolerate noise, it launders mandatory constraints.

## 4. Adversarial Review of Model C

### 4.1 Strongest case for Model C

Model C is constructed as a flat XOR of eight hand-curated sequence variants. The intent is to make the model **directly auditable**: an auditor can read the model and recognize traces in the log. Its training precision of 0.941, training fitness of 0.973, and absence of silent transitions mean that *anything the model can do was a real trace in training* (modulo the branch enumeration). For a small process with a stable log, this can be acceptable.

### 4.2 Strongest case against Model C

The model has at least six structural problems:

1. **Branch enumeration.** Eight variants are enumerated; new combinations of existing activities are not admitted. B5 (`Technical Review, Credit Check, Supplier Review, Expedite Review, Auto Approval`) is not in the eight, so it is rejected despite being a plausible valid external/urgent case. **The auditor's evidence (F2) is decisive here.**
2. **Duplicate labels.** 33 duplicates. The two re-check variants in C (`..., Correct Dossier, Credit Check, Technical Review, ...`) introduce identical transition labels in the same trace path. In a Petri net, this means the *same label* appears on multiple transitions, which **breaks simple token-game replay**: a `Credit Check` event after a `Correct Dossier` could be matched to the *original* or the *post-correction* `Credit Check` transition, and the alignment cost is not necessarily 0 on the intended match. This is not a cosmetic issue — it is a **soundness-of-mapping** problem.
3. **Unseen combinations.** C's holdout fitness of 0.744 (a 22.9 pp drop) is consistent with the data analyst's observation (F4) that holdout cases mix Supplier Review, Auto Approval, and alternate orderings. C is over-fit.
4. **Correction handling.** C represents *only one* correction pattern (correct  both checks re-run). It does not represent `correct  only Credit Check re-runs` or `correct  only Technical Review re-runs` (F6). The eight variants do not cover the policy's stated branching.
5. **Maintainability.** Adding a new variant requires manual model surgery; there is no graceful way to express "any of these ordering/repetition patterns is allowed." (F3)
6. **High precision may be an artifact.** Precision is computed only against observed positive traces (F5). On a curated negative suite, precision would likely be substantially lower; in fact, on the negative suite, both models should fail differently.

### 4.3 Is high precision memorizing training variants?
