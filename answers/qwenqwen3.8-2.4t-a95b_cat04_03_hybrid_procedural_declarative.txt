# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

1. **Case completeness**  
   The supplied traces are complete onboarding cases. A complete accepted case ends with `Close Onboarding` after `Release First Payment`; a complete rejected case ends with `Close Onboarding` after `Reject Vendor`.

2. **“Final outcome” interpretation**  
   I treat `Activate Vendor` and `Reject Vendor` as decisive terminal outcomes. `Close Onboarding` is the administrative terminal event. Therefore, an unanswered `Request Clarification` blocks `Activate Vendor`, `Reject Vendor`, and ultimately `Close Onboarding`.

3. **Accepted versus rejected cases**  
   An accepted case is one containing `Activate Vendor`. A rejected case is one containing `Reject Vendor`. Because of R1, these should be mutually exclusive.

4. **Approvals are route-dependent**  
   `Manager Approval` is the low-risk approval. `Compliance Approval` is the high-risk approval, after `Enhanced Due Diligence`. The event log does not contain an explicit risk class; the route is inferred from the approval path.

5. **Resource semantics**  
   The resource in `Activity@hour[resource]` is assumed to map to `org:resource`. Where a required resource attribute is missing, the resource/data layer cannot certify compliance and should emit a warning or an inconclusive finding, unless a policy explicitly says missing data is a violation.

6. **Emergency data is outside the event log**  
   R6 depends on an emergency/joint authorization attribute that is not present in the event log. Therefore, R6 cannot be decided by activity-only conformance checking. It requires an external case attribute or manual evidence.

7. **Temporal rules are advisory**  
   R12 says temporal expectations are “normative enough to flag but not automatically reject.” Therefore, temporal-profile deviations are treated as warnings, not hard failures.

8. **Post-activation bank changes are modeled before first payment**  
   `Change Bank Details`, `Suspend Vendor`, and re-verification are included in the procedural model only between `Activate Vendor` and `Release First Payment`. Post-payment or post-close bank-change lifecycle behavior is deliberately excluded from the onboarding backbone.

9. **Strict legal baseline for the implemented model**  
   The implemented procedural model enforces R5 strictly: after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor`. R6 is handled as an external exception mechanism, not as an activity-only rule.

## R5/R6 conflict and possible resolutions

R5 and R6 are incompatible if both are encoded as unconditional activity-flow rules:

- **R5, legal/compliance view:** after `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` under all circumstances.
- **R6, operations view:** emergency activation may occur before `Obtain Legal Opinion`, but only with joint authorization outside the log and with the opinion arriving within 24 hours.

### Resolution A: Strict legal supremacy — chosen for the implemented model

Encode R5 as a hard control-flow rule. Any case with:

```text
Sanctions Escalation ... Activate Vendor ... Obtain Legal Opinion
```

fails control-flow conformance. The emergency exception is not encoded in the activity model. It can only be handled by an external exception workflow, and only if the external authorization attribute is available.

**Compliance risk:**  
This can produce false positives for operationally legitimate emergency activations. It may also create pressure to bypass the log or delay urgent activations. However, it is conservative and audit-friendly because it does not silently accept undocumented exceptions.

### Resolution B: Permissive emergency exception

Relax the activity-flow model so that `Activate Vendor` may precede `Obtain Legal Opinion` after `Sanctions Escalation`, but only if:

1. an external case attribute, for example `emergency_joint_authorization`, is true;
2. `Obtain Legal Opinion` occurs within 24 hours of `Activate Vendor`;
3. the exception is surfaced as a warning or policy-dependent finding.

**Compliance risk:**  
Because the event log lacks the emergency authorization attribute, this resolution can silently legalize noncompliant cases if the external attribute is missing, unreliable, or retrospectively edited. It is operationally flexible but weaker as an automated control.

### Chosen resolution

I choose **Resolution A** for the implemented procedural model. The emergency rule is handled in the separate resource/data-aware layer as an external exception check. This preserves a conservative control-flow baseline and makes the conflict explicit instead of hiding it.

# 3. Procedural Backbone

## Compact formal description

The implemented model is an accepting Petri net. Its main control-flow logic is:

```text
Receive Onboarding Request
  -> parallel:
       Capture Master Data
       Run Sanctions Screening
       Verify Bank Account
  -> Classify Risk after all three checks

Clarification obligation:
  Request Clarification consumes clarification_idle
  Receive Clarification restores clarification_idle
  Activate Vendor and Reject Vendor require clarification_idle

Legal obligation, strict R5:
  Run Sanctions Screening produces sanctions_screened_permission
  Sanctions Escalation consumes legal_clear and produces legal_open
  Obtain Legal Opinion restores legal_clear
  Activate Vendor requires legal_clear
  Close Onboarding requires legal_clear

After Classify Risk, choose one primary route:
  reject:
    Reject Vendor -> Close Onboarding
  low-risk:
    Manager Approval -> Activate Vendor -> optional bank-change loop -> Release First Payment -> Close Onboarding
  high-risk:
    Enhanced Due Diligence -> Compliance Approval -> Activate Vendor -> optional bank-change loop -> Release First Payment -> Close Onboarding

Post-activation bank-change loop:
  Activate Vendor produces activated
  either:
    Release First Payment
  or:
    Change Bank Details -> Suspend Vendor -> Verify Bank Account -> activated
```

The model deliberately excludes post-payment or post-close `Change Bank Details` behavior. If that lifecycle is in scope, a separate post-onboarding model is needed.

## Explanation

### Concurrency

After `Receive Onboarding Request`, the net enables:

- `Capture Master Data`
- `Run Sanctions Screening`
- `Verify Bank Account`

These three activities may occur in any interleaved order. `Classify Risk` consumes the three completion places, so it cannot occur until all three checks have completed.

### Choices

`Classify Risk` produces one `classified` token. That token can be consumed by exactly one of:

- `Reject Vendor`
- `Manager Approval`
- `Enhanced Due Diligence`

Thus the reject, low-risk, and high-risk routes are mutually exclusive. This enforces R1, R2, and R8 structurally.

### Clarification loops

The places `clarification_idle` and `clarification_open` implement a paired request/response obligation:

- `Request Clarification` consumes `clarification_idle`.
- `Receive Clarification` restores `clarification_idle`.
- `Activate Vendor` and `Reject Vendor` require `clarification_idle`.

Therefore, an unanswered clarification blocks final outcomes but does not block `Classify Risk` or preparatory approvals. This matches R3 more precisely than a simple sequential loop before classification.

### Terminal outcomes

`Activate Vendor` and `Reject Vendor` consume `clarification_idle` and `sanctions_screened_permission`. This prevents further clarification requests and further sanctions escalations after the decisive outcome.

`Close Onboarding` requires `legal_clear`. Therefore, if a `Sanctions Escalation` occurred, the case cannot close until `Obtain Legal Opinion` restored `legal_clear`.

### Post-activation behavior

The model includes a bank-change loop between `Activate Vendor` and `Release First Payment`:

```text
Activate Vendor
  -> Release First Payment
  or
  -> Change Bank Details -> Suspend Vendor -> Verify Bank Account -> ready for payment
```

This enforces R11 for changes before first payment. The loop can repeat.

### Deliberate exclusions

The model does not include:

- `Change Bank Details` after `Release First Payment`;
- `Change Bank Details` after `Close Onboarding`;
- suspension workflows that do not eventually return to payment;
- emergency authorization as an event-log attribute.

These are either out of scope for the stable onboarding backbone or require external data.

| Rule | Template | Direction / key | Meaning | Related requirement |
|---|---|---|---|---|
| `Receive Onboarding Request` must be first | `init` | unary activity | Every case must start with `Receive Onboarding Request`. | Stable backbone |
| `Close Onboarding` must occur | `existence` | unary activity | Every complete case contains `Close Onboarding`. | Stable backbone |
| No activation and rejection together | `noncoexistence` | `("Activate Vendor", "Reject Vendor")` | The two activities cannot co-occur in the same case. Order is irrelevant. | R1 |
| No EDD with Manager Approval | `noncoexistence` | `("Enhanced Due Diligence", "Manager Approval")` | These activities cannot co-occur. | R8 |
| No Compliance Approval with Manager Approval | `noncoexistence` | `("Compliance Approval", "Manager Approval")` | These activities cannot co-occur. | R8 |
| Clarification response alternation | `altresponse` | `("Request Clarification", "Receive Clarification")` | Every `Request Clarification` must be followed by `Receive Clarification` before the next `Request Clarification`. | R3, partial |
| Legal opinion after escalation | `altresponse` | `("Sanctions Escalation", "Obtain Legal Opinion")` | Every `Sanctions Escalation` must be followed by `Obtain Legal Opinion` before another escalation. | R4, partial |
| Suspension after bank change | `altresponse` | `("Change Bank Details", "Suspend Vendor")` | Every `Change Bank Details` must be followed by `Suspend Vendor` before another bank change. | R11, partial |
| Reverification after suspension | `altresponse` | `("Suspend Vendor", "Verify Bank Account")` | Every `Suspend Vendor` must be followed by `Verify Bank Account` before another suspension. | R11, partial |
| Escalation only after screening | `precedence` | `("Run Sanctions Screening", "Sanctions Escalation")` | If `Sanctions Escalation` occurs, it must be preceded by `Run Sanctions Screening`. | R7 |

## Template distinctions

### Response versus precedence

- `response(A, B)` means: if `A` occurs, `B` must occur later.
- `precedence(A, B)` means: if `B` occurs, `A` must have occurred before it.

I use `precedence` for `Run Sanctions Screening -> Sanctions Escalation` because the rule is triggered by the occurrence of `Sanctions Escalation`.

### Alternate response versus chain response

I use `altresponse`, not `chainresponse`.

- `altresponse(A, B)` allows other activities between `A` and `B`, but requires `B` before the next `A`.
- `chainresponse(A, B)` would require `B` to immediately follow `A`.

Immediate response is too strict for clarification and legal opinion. For example, in T2, several events occur between `Request Clarification` and `Receive Clarification`.

### Noncoexistence versus nonsuccession

I use `noncoexistence` for R1 and R8 because the prohibited fact is co-occurrence, regardless of order.

`nonsuccession(A, B)` would prohibit `B` after `A`, but would not necessarily capture the reverse order unless another rule were added. For R1, order does not matter: activation and rejection must not both occur. Therefore `noncoexistence` is the better template.

## DECLARE limitations in this design

The DECLARE model does **not** fully encode R5. A rule such as:

```python
"precedence": {("Obtain Legal Opinion", "Activate Vendor"): ...}
```

would require `Obtain Legal Opinion` before every activation, even in no-escalation accepted cases such as T1. That would be wrong. Therefore, conditional R5 is enforced by the procedural Petri net, while DECLARE only enforces the weaker R4 obligation.

# 5. Log-Skeleton Model

```python
log_skeleton = {
    "equivalence": {
        ("Request Clarification", "Receive Clarification")
    },
    "always_before": {
        ("Receive Onboarding Request", "Classify Risk"),
        ("Capture Master Data", "Classify Risk"),
        ("Run Sanctions Screening", "Classify Risk"),
        ("Run Sanctions Screening", "Sanctions Escalation"),
        ("Classify Risk", "Manager Approval"),
        ("Classify Risk", "Compliance Approval"),
        ("Classify Risk", "Reject Vendor"),
        ("Classify Risk", "Activate Vendor"),
        ("Enhanced Due Diligence", "Compliance Approval"),
        ("Activate Vendor", "Release First Payment")
    },
    "always_after": set(),
    "never_together": {
        ("Activate Vendor", "Reject Vendor"),
        ("Manager Approval", "Enhanced Due Diligence"),
        ("Manager Approval", "Compliance Approval")
    },
    "activ_freq": {
        "Receive Onboarding Request": {1},
        "Close Onboarding": {1},
        "Activate Vendor": {0, 1},
        "Reject Vendor": {0, 1},
        "Release First Payment": {0, 1}
    },
    "directly_follows": set()
}
```

## Explanation of constraints and orientation

### Equivalence

| Pair | Semantics |
|---|---|
| `("Request Clarification", "Receive Clarification")` | If either activity occurs in a case, the other must also occur. This is symmetric. It catches T5, where a request occurs without a response. |

This is weaker than the procedural model and weaker than DECLARE `altresponse`. It does not enforce order or pairing. It only enforces co-occurrence.

### Always before

The orientation is:

```text
(first_activity, second_activity)
```

meaning: whenever the second activity occurs, the first activity must have occurred earlier in the case.

| Pair | Reason |
|---|---|
| `("Receive Onboarding Request", "Classify Risk")` | Classification happens only after case receipt. |
| `("Capture Master Data", "Classify Risk")` | Master data capture must precede classification. |
| `("Run Sanctions Screening", "Classify Risk")` | Sanctions screening must precede classification. |
| `("Run Sanctions Screening", "Sanctions Escalation")` | Escalation only after screening. |
| `("Classify Risk", "Manager Approval")` | Manager approval occurs only after classification. |
| `("Classify Risk", "Compliance Approval")` | Compliance approval occurs only after classification. |
| `("Classify Risk", "Reject Vendor")` | Rejection occurs only after classification. |
| `("Classify Risk", "Activate Vendor")` | Activation occurs only after classification. |
| `("Enhanced Due Diligence", "Compliance Approval")` | High-risk approval follows EDD. |
| `("Activate Vendor", "Release First Payment")` | First payment follows activation. |

I deliberately omit `("Verify Bank Account", "Classify Risk")` from `always_before` because the procedural model allows a later re-verification `Verify Bank Account` after bank changes. A strict global always-before constraint on `Verify Bank Account` could become inconsistent with legitimate loops.

### Always after

I leave `always_after` empty to avoid redundant inverse constraints. The selected `always_before` orientation is sufficient for the defensible constraints.

### Never together

These pairs are symmetric:

| Pair | Reason |
|---|---|
| `("Activate Vendor", "Reject Vendor")` | R1. |
| `("Manager Approval", "Enhanced Due Diligence")` | R8. |
| `("Manager Approval", "Compliance Approval")` | R8 and R2. |

### Activity frequencies

| Activity | Allowed counts | Reason |
|---|---:|---|
| `Receive Onboarding Request` | `{1}` | Starts every case. |
| `Close Onboarding` | `{1}` | Every complete case closes once. |
| `Activate Vendor` | `{0, 1}` | Accepted cases activate once; rejected cases zero. |
| `Reject Vendor` | `{0, 1}` | Rejected cases reject once; accepted cases zero. |
| `Release First Payment` | `{0, 1}` | At most one first payment. |

I do not constrain `Verify Bank Account` to `{1}` because R11 may require re-verification.

### Directly follows

I leave `directly_follows` empty. Direct succession is brittle here because:

- the initial checks are concurrent;
- clarification cycles can interleave;
- legal opinion can occur at different points after escalation;
- bank-change loops can insert events between activation and payment.

## Overlap and disagreement with other layers

- `never_together` duplicates procedural exclusivity and DECLARE `noncoexistence`.
- `equivalence` for clarification is weaker than DECLARE `altresponse` and procedural token blocking.
- `always_before` captures part of the backbone but cannot express conditional obligations such as “legal opinion before activation only if escalation occurred.”
- `activ_freq` captures R10 better than DECLARE for at-most-once activities, but still does not capture route-dependent exactly-one approval.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (172800, 86400),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (43200, 21600),
    ("Activate Vendor", "Release First Payment"): (259200, 129600)
}

zeta = 2.0
```

The values are in seconds:

| Pair | Mean hours | Std-dev hours | Mean seconds | Std-dev seconds |
|---|---:|---:|---:|---:|
| `Request Clarification -> Receive Clarification` | 48 | 24 | 172800 | 86400 |
| `Sanctions Escalation -> Obtain Legal Opinion` | 12 | 6 | 43200 | 21600 |
| `Activate Vendor -> Release First Payment` | 72 | 36 | 259200 | 129600 |

## Why temporal deviations are warnings

R12 explicitly says these temporal expectations are normative enough to flag but not enough to automatically reject a case. Therefore:

- a duration outside `mean ± zeta * std` produces a warning;
- it does not by itself make the overall case fail;
- missing target events are not treated as temporal deviations; they are handled by control-flow or DECLARE layers if they represent missing obligations.

With `zeta = 2.0`, the acceptable deviation band is two standard deviations around the mean.

Examples:

- T7: `Sanctions Escalation@6` to `Obtain Legal Opinion@40` is 34 hours.  
  Deviation: `34 - 12 = 22` hours.  
  Threshold: `2 * 6 = 12` hours.  
  Therefore T7 receives a temporal warning.

- T6: `Sanctions Escalation@6` to `Obtain Legal Opinion@23` is 17 hours.  
  Deviation: `17 - 12 = 5` hours.  
  Threshold: 12 hours.  
  Therefore T6 does not receive a temporal warning for that pair, even though it violates strict R5 control flow.

# 7. Resource- and Data-Aware Checks

The following executable-style pseudocode uses a pandas DataFrame with these event attributes:

- `case:concept:name`
- `concept:name`
- `concept:timestamp`
- `org:resource`

It also assumes an optional external dictionary `case_attributes` containing:

```python
case_attributes = {
    "case_id": {
        "emergency_joint_authorization": True
    }
}
```

## Check implementation

```python
import pandas as pd
from datetime import timedelta

CASE = "case:concept:name"
ACT = "concept:name"
RES = "org:resource"
TS = "concept:timestamp"

def resource_data_checks(df, case_attributes=None, policy="strict"):
    """
    Returns a list of findings.

    policy:
      - "strict": R5 is enforced; emergency activation before legal opinion fails.
      - "emergency": R6 exception may be accepted if external authorization exists
        and Obtain Legal Opinion occurs within 24 hours after Activate Vendor.
    """
    findings = []
    case_attributes = case_attributes or {}

    for case_id, g in df.groupby(CASE):
        g = g.sort_values(TS)

        def events(activity):
            return g[g[ACT] == activity]

        ma = events("Manager Approval")
        ca = events("Compliance Approval")
        av = events("Activate Vendor")
        vba = events("Verify Bank Account")
        cmd = events("Capture Master Data")
        se = events("Sanctions Escalation")
        olo = events("Obtain Legal Opinion")

        # ---------------------------------------------------------------
        # R9: Four-eyes / segregation of duties
        # ---------------------------------------------------------------

        approval_event = None
        approval_label = None

        if not ma.empty:
            approval_event = ma.iloc[0]
            approval_label = "Manager Approval"
        elif not ca.empty:
            approval_event = ca.iloc[0]
            approval_label = "Compliance Approval"

        if approval_event is not None:
            approval_resource = approval_event.get(RES)

            if pd.isna(approval_resource):
                findings.append({
                    "case": case_id,
                    "severity": "warning",
                    "rule": "R9",
                    "message": f"Missing resource for {approval_label}; cannot verify four-eyes rule."
                })
            else:
                for _, vba_event in vba.iterrows():
                    vba_resource = vba_event.get(RES)

                    if pd.isna(vba_resource):
                        findings.append({
                            "case": case_id,
                            "severity": "warning",
                            "rule": "R9",
                            "message": "Missing resource for Verify Bank Account; cannot verify four-eyes rule."
                        })
                    elif vba_resource == approval_resource:
                        findings.append({
                            "case": case_id,
                            "severity": "fail",
                            "rule": "R9",
                            "message": f"Same resource performed Verify Bank Account and {approval_label}."
                        })

        if not av.empty:
            av_resource = av.iloc[0].get(RES)

            if pd.isna(av_resource):
                findings.append({
                    "case": case_id,
                    "severity": "warning",
                    "rule": "R9",
                    "message": "Missing resource for Activate Vendor; cannot verify four-eyes rule."
                })
            else:
                for _, cmd_event in cmd.iterrows():
                    cmd_resource = cmd_event.get(RES)

                    if pd.isna(cmd_resource):
                        findings.append({
                            "case": case_id,
                            "severity": "warning",
                            "rule": "R9",
                            "message": "Missing resource for Capture Master Data; cannot verify four-eyes rule."
                        })
                    elif cmd_resource == av_resource:
                        findings.append({
                            "case": case_id,
                            "severity": "fail",
                            "rule": "R9",
                            "message": "Same resource performed Capture Master Data and Activate Vendor."
                        })

        # Optional PM4Py helper for pairwise four-eyes checks.
        # These are useful but less precise because the applicable approval depends on route.
        #
        # pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")
        # pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Compliance Approval")
        # pm4py.filter_four_eyes_principle(log, "Capture Master Data", "Activate Vendor")

        # ---------------------------------------------------------------
        # R5/R6 emergency-policy condition
        # ---------------------------------------------------------------

        if not se.empty and not av.empty:
            av_time = av[TS].min()
            olo_time = olo[TS].min() if not olo.empty else None

            if pd.isna(av_time):
                findings.append({
                    "case": case_id,
                    "severity": "warning",
                    "rule": "R5/R6",
                    "message": "Missing timestamp for Activate Vendor; cannot evaluate legal-opinion timing."
                })
            elif olo_time is None or pd.isna(olo_time):
                if policy == "strict":
                    findings.append({
                        "case": case_id,
                        "severity": "fail",
                        "rule": "R4/R5",
                        "message": "Sanctions Escalation occurred but Obtain Legal Opinion is missing."
                    })
                else:
                    findings.append({
                        "case": case_id,
                        "severity": "fail",
                        "rule": "R6",
                        "message": "Emergency exception claimed but Obtain Legal Opinion is missing."
                    })
            elif av_time < olo_time:
                if policy == "strict":
                    findings.append({
                        "case": case_id,
                        "severity": "fail",
                        "rule": "R5",
                        "message": "Activate Vendor occurred before Obtain Legal Opinion after Sanctions Escalation."
                    })
                else:
                    attrs = case_attributes.get(case_id, {})
                    authorized = attrs.get("emergency_joint_authorization", None)

                    if authorized is None:
                        findings.append({
                            "case": case_id,
                            "severity": "policy-dependent",
                            "rule": "R6",
                            "message": "Emergency activation before legal opinion requires external joint authorization."
                        })
                    elif authorized is not True:
                        findings.append({
                            "case": case_id,
                            "severity": "fail",
                            "rule": "R6",
                            "message": "Emergency activation before legal opinion lacks valid joint authorization."
                        })
                    elif olo_time - av_time > timedelta(hours=24):
                        findings.append({
                            "case": case_id,
                            "severity": "fail",
                            "rule": "R6",
                            "message": "Obtain Legal Opinion did not occur within 24 hours after emergency activation."
                        })
                    else:
                        findings.append({
                            "case": case_id,
                            "severity": "warning",
                            "rule": "R6",
                            "message": "Emergency exception accepted; retain external authorization evidence."
                        })

    return findings
```

## Required attributes and missing-attribute policy

| Check | Required attribute | If missing |
|---|---|---|
| Four-eyes: `Verify Bank Account` vs approval | `org:resource` on both events | Emit warning; cannot certify compliance. In strict audit mode, this may be escalated to fail. |
| Four-eyes: `Capture Master Data` vs `Activate Vendor` | `org:resource` on both events | Emit warning; cannot certify compliance. |
| Emergency exception | external `emergency_joint_authorization` case attribute | Under strict policy: fail if activation precedes legal opinion. Under emergency policy: mark as `policy-dependent` until evidence is supplied. |
| Legal opinion within 24 hours | `concept:timestamp` for `Activate Vendor` and `Obtain Legal Opinion` | If timestamp missing, emit warning or fail depending on audit strictness; time-bound rule cannot be evaluated. |

## Note on R11 data awareness

The procedural model can enforce the sequence:

```text
Change Bank Details -> Suspend Vendor -> Verify Bank Account
```

but it cannot verify whether the bank details were actually changed, whether the re-verification checked the new account, or whether the suspended vendor was restored. Those checks require data payloads or external vendor-master-data records.

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement across layers

Several requirements are encoded in more than one layer:

- R1 appears in the procedural net, DECLARE `noncoexistence`, and Log Skeleton `never_together`.
- R7 appears in the procedural net and DECLARE `precedence`.
- R8 appears in the procedural net, DECLARE `noncoexistence`, and Log Skeleton `never_together`.
- R10 appears in the procedural net and Log Skeleton `activ_freq`.
- R3 appears in the procedural net, DECLARE `altresponse`, and Log Skeleton `equivalence`.

This redundancy can be useful because different layers catch violations at different levels of granularity. However, it creates a maintenance risk: if one model is updated and another is not, the layers may produce conflicting findings.

## Constraints that become inconsistent under loops or post-activation changes

Loops make some activity-only constraints dangerous.

For example, a naive Log Skeleton constraint:

```python
("Verify Bank Account", "Classify Risk")
```

could become problematic if a later re-verification `Verify Bank Account` occurs after `Classify Risk` because of R11. I therefore omitted that pair from `always_before` and relied on the procedural net to distinguish initial verification from re-verification through transition structure, even though both share the same visible label.

Similarly, DECLARE rules:

```python
("Suspend Vendor", "Verify Bank Account")
("Change Bank Details", "Suspend Vendor")
```

assume that suspension is always followed by re-verification. If a future process allows suspension without returning to payment, these rules may overconstrain the process.

## Vacuity in declarative rules

DECLARE rules can be vacuously satisfied when the triggering activity does not occur.

Examples:

- `altresponse("Sanctions Escalation", "Obtain Legal Opinion")` passes every case without escalation.
- `precedence("Run Sanctions Screening", "Sanctions Escalation")` passes every case without escalation.
- `altresponse("Request Clarification", "Receive Clarification")` passes every case without clarification requests.

This is appropriate for conditional rules, but it means DECLARE cannot replace the procedural model for route-dependent obligations.

## Missing case attributes

The event log lacks several attributes needed for full policy evaluation:

- risk class: low-risk versus high-risk;
- emergency joint authorization;
- bank account data before and after `Change Bank Details`;
- resource roles, not just resource identifiers;
- vendor identifier or master-data version;
- clarification request identifier, which would allow pairing requests and responses more robustly.

Without these attributes, some checks must remain approximate or external.

## Timestamp-only limitations

Temporal-profile checking uses only timestamps. It cannot distinguish:

- calendar hours versus business hours;
- working-day conventions;
- time-zone effects;
- events recorded late;
- retroactive timestamp correction;
- multiple events with identical timestamps.

Also, temporal checks assume that the relevant source and target events can be paired unambiguously. With multiple clarification cycles, pairing can become ambiguous unless request identifiers or event correlation attributes are available.

## Risk of treating support/confidence metadata as normative truth

The DECLARE dictionary uses:

```python
"support": 1.0,
"confidence": 1.0
```

These values represent modeling confidence, not observed log support. They should not be interpreted as proof that the rule was mined from data or that violations are acceptable if confidence is lower.

In deployment, support and confidence should be treated as metadata for model governance, not as automatic overrides of policy violations.

# 10. Deployment Recommendation

## Canonical procedural representation

Use the accepting Petri net as the canonical procedural representation. It is the most expressive layer for this scenario because it can represent:

- concurrency of initial checks;
- exclusive route choices;
- clarification obligations;
- legal-opinion obligations;
- at-most-once terminal events;
- post-activation bank-change loops.

A process tree would be simpler but would require approximations for conditional obligations and interleaved clarification loops. The Petri net is therefore preferred.

## Authoritative policy layer

The authoritative layer depends on the policy type:

| Policy type | Authoritative layer |
|---|---|
| Control-flow backbone and terminal exclusivity | Procedural accepting Petri net |
| Conditional legal precedence R5 | Procedural accepting Petri net, strict baseline |
| Emergency exception R6 | External resource/data-aware validation layer |
| Resource segregation R9 | Resource/data-aware validation layer |
| Temporal expectations R12 | Temporal profile, advisory only |
| Lightweight activity monitoring | DECLARE and Log Skeleton as secondary detectors |

DECLARE and Log Skeleton should not be the final authority for rules that depend on route, resources, external authorizations, or conditional obligations.

## Recommended conformance-check order

1. **Schema and attribute validation**  
   Check that required attributes exist:
   - case identifier;
   - activity name;
   - timestamp;
   - resource;
   - external emergency authorization where relevant.

2. **Procedural conformance checking**  
   Run alignment or replay against the accepting Petri net. This produces hard control-flow failures.

3. **DECLARE conformance checking**  
   Run DECLARE as a secondary declarative monitor. It is useful for detecting missing responses, forbidden co-occurrences, and precedence violations.

4. **Log Skeleton conformance checking**  
   Run Log Skeleton for lightweight frequency, equivalence, and never-together checks.

5. **Temporal-profile checking**  
   Run temporal profiling with `zeta = 2.0`. Treat deviations as warnings.

6. **Resource/data-aware checking**  
   Run four-eyes checks and emergency-policy checks using resource attributes and external case attributes.

7. **Aggregation and disposition**  
   Combine findings into a case verdict:
   - hard control-flow failure;
   - resource failure;
   - temporal warning;
   - policy-dependent exception pending evidence;
   - pass.

## Surfacing contradictory findings

Contradictory findings should not be silently merged. The UI or audit report should show:

- which layer produced the finding;
- which requirement or rule was triggered;
- the event or events involved;
- whether the finding is hard, advisory, or policy-dependent;
- whether an exception is possible.

For T6, the system should display something like:

```text
Strict R5 violation: Activate Vendor occurred before Obtain Legal Opinion after Sanctions Escalation.
Possible R6 emergency exception: external joint authorization required.
Current status: policy-dependent because authorization attribute is missing.
```

If valid emergency authorization is later supplied and the 24-hour condition is satisfied, the case can be reclassified from fail to warning or accepted exception, but the original strict violation should remain visible in the audit trail.
