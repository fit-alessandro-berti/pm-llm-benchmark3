## 1. Consistency rules and evidence model

**Hard invariants**

- No new events or objects may be invented.
- Every proposed E2O endpoint must reference an existing event and object.
- Every proposed O2O endpoint must reference existing objects.
- Observed relations are retained unless directly contradicted; here none are contradicted.
- O2O qualifiers are directional. `DEL-X carries PK-7` does not imply `PK-7 carries DEL-X`.
- Duplicate identical E2O or O2O tuples should not be added.

**Strong defaults**

- `Create Order` normally relates to exactly one Order.
- `Add Item` normally relates to one Order and one Item.
- `Pack Item` normally relates to one Item and one Package, but an item-only row may be a legitimate scanner outage.
- `Dispatch Package` normally relates to one Package and one Delivery, though bulk dispatch is possible.
- `Confirm Delivery` may relate to one Delivery, several Deliveries, or only a customer/Order if the carrier identifier is lost.
- `Issue Invoice` relates to one Invoice and one or more Orders.
- `Record Payment` relates to exactly one Payment and normally one Invoice, but unapplied cash is possible.
- Lifecycle order is normally: Create Order  Add Item  Pack Item  Dispatch Package  Confirm Delivery; Invoice and Payment usually follow order creation and are often after dispatch.
- Identifier matching is strong when it is exact or near-exact: `N-421?` versus `N-421`, `PK8-2` versus `PK-8`, `N-420` versus `N-420`.
- Existing O2O structure is strong evidence that an event involving both endpoints is coherent, but it is not independent proof if the O2O edge was inferred from the same event.

**Weak heuristics**

- Wildcard or masked identifiers, such as `N-42*`, are suggestive but not decisive.
- Same route (`NORTH`) is supportive but weak.
- Same customer (`C17`) is supportive but weak.
- Amount equality or complementarity is corroborating, not proof, because fees, discounts, taxes, partial payments, and unapplied cash are possible.
- Timestamp proximity is weak support for related operations but not decisive.
- Gross weight is not used here because item weights are absent.

**Evidence against a repair**

- `ev08` is item-only. The scanner reference `PK8-2` is suggestive, but a scanner outage can legitimately produce an unreconciled item-only pack row.
- `ev10` has `external_ref=N-421?`, so the match to `DEL-Y` is strong but not perfect.
- `ev11` uses `N-42*` and is observed only with `ORD-A`. Assigning it to `DEL-Y` may imply delivery of `ORD-B` content without direct evidence.
- `INV-44` is observed only with `ORD-A`. The total `230` equals `130 + 100`, but arithmetic matching does not prove that `ORD-B` is billed.
- `PAY-2` is observed only with itself. Its amount complements `PAY-1`, but unapplied cash is possible.

**Combination policy**

A candidate relation is accepted or provisionally added only if it passes all hard invariants and has at least one strong identifier, lifecycle, or cardinality signal. Candidates supported only by weak heuristics remain unresolved. Inferred O2O edges are not treated as independent confirmation of the E2O edge that motivated them.

## 8. Over-repair warnings

1. **Adding `ev08  PK-8` and `PK-8 packs IT-B1` can create a false cross-order package.** This would make `PK-8` contain items from both `ORD-A` and `ORD-B`, producing a `Pack Item  Pack Item` fragment on `PK-8` and implying consolidated shipping that is not directly observed.

2. **Assigning `ev11` uniquely to `DEL-X` or `DEL-Y` can create a false delivery confirmation.** A unique assignment would create `Dispatch Package  Confirm Delivery` on one delivery while suppressing a plausible multi-delivery confirmation. If `DEL-Y` is chosen, it may also imply delivery of `ORD-B` content without direct evidence.

3. **Adding `INV-44 bills ORD-B` based on amount matching can create a false invoice scope.** This would make `ORD-B` appear invoiced and could cause downstream payment, reconciliation, and Order flattening to show a billing lifecycle that is not directly evidenced.

4. **Adding `PAY-2 settles INV-44` can create a false settlement edge.** This would make the invoice appear fully paid by two payments and could mask a legitimate unapplied-cash state. The amount complement is supportive but not decisive.

5. **Adding `ev10  DEL-X` or `DEL-Y carries PK-7` can create duplicate or wrong dispatch behavior.** This would attach the wrong carrier to the package, duplicate Delivery–Package edges, and create false `Dispatch Package` behavior on the wrong delivery object.

6. **Adding `ev11  ORD-B` directly can create a false Confirm Delivery on Order.** This would alter the Order lifecycle and equivalent-execution clustering even when the safer route is to relate the confirmation to delivery objects and let O2O paths provide indirect order-level meaning.
