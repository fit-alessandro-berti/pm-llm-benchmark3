## 1. Target definition

**Primary target: 90-day default among activated accounts, scored at an activation landmark.**

For application \(i\), let:

- \(A_i\): Account Activated time;
- \(T_i\): time of the first qualifying default event after activation, or infinity if none occurs;
- \(\tau_i=A_i+24\text{ hours}\): prediction landmark;
- \(X_{i,\le \tau_i}\): information available by that landmark.

The target is

\[
Y_i^{90}=\mathbf{1}\{T_i\le A_i+90\text{ days}\}.
\]

The default clock starts at **activation**, not application start. The model produces

\[
\widehat R_i(90)
=
\widehat P(Y_i^{90}=1\mid
\text{activated and no default already known at }\tau_i,
X_{i,\le\tau_i}).
\]

Accounts with a known default by the landmark are handled as observed events rather than receiving a prospective early-warning score.

**Population and estimand.** The primary population is applications that have reached activation and the prediction landmark under the historical activation process. The estimand is the calibrated 90-day default risk conditional on activation, observed process history, and the current operating policy.

This deliberately **does not implement an initial-credit score for every application**. It is an activation/onboarding risk model. An activated-only prevalence, such as the export’s \(2700/21600=12.5\%\), is not the default probability for all 48,000 applications and is not even an unbiased activated-population rate if outcome feeds are selectively missing.

**Unit of analysis:** one canonical credit application, not one event, identifier, or platform account.

**Credible alternative: an all-application pathway model.** Predict, from an early application prefix:

1. activation within a specified application-level horizon;
2. rejection, withdrawal, or unresolved transfer as distinct pathways;
3. conditional default within 90 days after activation.

This answers “what pathway is this application likely to follow?” It is not a binary test for default among all applications. A joint model or sequential competing-state model is preferable to multiplying separately fitted activation and default models.

A stronger alternative would estimate **“default if every application were offered credit under policy \(g\)”**. That is a counterfactual target: rejected, withdrawn, and unobserved cases have no activation-observed default outcome. Identifying it requires a specified intervention—such as an approval rule or randomized offer—and assumptions or data supporting that counterfactual, not relabeling missing outcomes as zero.

## 2. Cohort construction

### As-of rules

Use two distinct timestamps:

- **Event-history endpoint:** 31 December 2025. No process event after that date enters the supplied event history.
- **Warehouse/feed availability cutoff:** 15 February 2026. Labels and technical records must have been available by this cutoff.

Other rules:

1. Select one observation per canonical application before counting or splitting.
2. Resolve known cross-platform identifiers through the linkage table before analysis.
3. Do not automatically merge unlinked transferred applications using fuzzy matching. Record unresolved identifier chains and investigate duplicates.
4. Normalize validated activity aliases globally, including a **historical, timestamped** migration crosswalk. Preserve duplicate-source flags.
5. Do not use a terminal disposition discovered after a case’s prediction point to construct its prefix.
6. A horizon is mature at activation plus 90 days. A negative label is adjudication-ready only when complete-feed requirements are also satisfied.
7. “Label available” is not proof that a blank is a verified negative. A mature negative requires a trustworthy complete outcome feed.

Under a **hard maximum** 35-day feed delay, activations on or before **13 October 2025** should be mature by 15 February 2026. The reported 3,600 immature accounts should therefore be checked against activation dates and actual feed-arrival times. A 35-day “common” delay is not necessarily a guaranteed maximum.

### Cohort flow

The following accounts for the **48,000 reported applications**. It describes the supplied export; the implementation must reconstruct these dispositions from the events rather than trust preselected ML rows.

| Initial disposition at the reporting cutoff | Count | Statistical meaning |
|---|---:|---|
| Rejected | 9,100 | Observed competing non-activation outcome; not a non-default |
| Withdrawn | 5,700 | Observed competing non-activation outcome; not a non-default |
| Transferred, with no observed subsequent activation in the supplied cohort | 2,900 | Competing pathway or missing follow-up, depending on linkage and return |
| Still open, not yet activated | 5,100 | Right-censored for time to activation; no primary target yet |
| Activated, 90-day label reported | 21,600 | Reported positives: 2,700; reported non-defaults: 18,900. Use only after label/feed audit |
| Activated, horizon or feed outcome pending | 3,600 | No assumed negative; pending 90-day endpoint or incomplete follow-up |
| **Total** | **48,000** | |

The activated rows total 25,200, not 27,300. The activated rows also contain the subset already known to be in default at the 24-hour landmark; that subset must be removed from prospective scoring.

If linkage establishes that a transferred application returned and activated before the cutoff, its disposition must be reconciled within the 48,000-canonical-application total. It must not be added as a second application or automatically retained in the 2,900 transfer count.

## 3. Censoring and missing-label strategy

The mechanisms require different treatment:

| Mechanism | Correct interpretation |
|---|---|
| **Ordinary right censoring** | An activated account has not had a recorded event through the available follow-up endpoint. For time-to-default analysis, the event observation endpoint is 31 December 2025, not 15 February 2026 merely because the warehouse was extracted then. |
| **Delayed labels** | The 90-day default window has ended, but the feed has not adjudicated the outcome. This is not evidence of non-default and should not automatically become an administrative “survived 90 days” observation. |
| **Selection through activation** | Default is defined only after activation. Non-activation is outside the primary target’s risk set, not an observed survival time for default after activation. |
| **Transfer** | Before activation, transfer can be a competing pathway. After activation, it can mean loss to follow-up or a competing observation event if the destination process terminates observation. It is not a default and not automatically a non-default. |
| **Permanently missing partner feeds** | Missingness is plausibly related to source, activation history, and collection process. Complete-case proportions can be selected and biased. Blank labels are neither censoring at day 90 nor verified survival. |

### Primary analysis

Use a **90-day landmark analysis with inverse-probability weighting and explicit complete-follow-up criteria**:

- Positive target: a reliably observed qualifying default by activation plus 90 days.
- Negative target: a verified complete outcome feed showing no default through that horizon.
- Pending cases: not assigned zero.
- Weight for verified outcome observation and applicable loss-to-follow-up mechanisms when their overlap and covariates are adequate.
- Report performance and calibration in the verified test cohort even if weighting cannot recover a fully representative population.

For a time-to-default implementation, use a discrete-time or conventional survival model, fitted outside PM4Py, with delayed entry at the chosen landmark. The default deadline remains activation plus 90 days. Early evidence arriving late must be handled explicitly rather than creating immortal follow-up.

### Sensitivity analyses

1. **Partial-follow-up survival analysis:** include activated cases with known event times and defensible last-known-alive times, using administrative censoring at the event-history endpoint. The 3,600 pending cases can contribute if reliable follow-up exists; they cannot contribute as presumed negatives.
2. **Selection comparison:** compare the export with the activation and feed-availability population, using source-specific availability propensities where possible. Examine overlap and weight instability.
3. **Complete-case versus weighted estimates:** report unweighted and weighted results, especially by partner source and activation month.
4. **All-application pathway analysis:** model activation, non-activation, and transfer separately, leaving unresolved pathways probabilistically or as an explicit unknown state.

### Testability

- **Testable or partially testable:** label-delay distributions; event-time completeness; censoring curves by month/source; migration-related missingness; activation-selection associations with observed covariates; propensity-weight overlap; conflicts between event-recorded and feed-reported outcomes.
- **Assumptions that cannot be verified from these data alone:** that missingness is independent of default after measured covariates; that linked and unlinked transfers have comparable follow-up; that historical event-time fields represent the values actually available at the prediction time; that post-policy relationships remain stable.
- **Fundamentally untestable here:** the default risk that rejected or withdrawn applications would have experienced under a specified alternative activation policy.

## 4. Prefix extraction

### Fixed event-count prefixes

For illustration, use \(k=3\), counting the first three canonical, source-deduplicated events, including Application Started.

For each case:

1. Establish its canonical identifier.
2. Apply a documented migration alias map.
3. Sort by event timestamp and a reliable source event/version identifier.
4. Retain only the first \(k\) events.
5. Calculate all sequence, control-flow, and as-of attributes from those events.
6. Attach activation-landmark and outcome metadata separately.

The fixed-prefix feature table is comparable only to cases with the same complete prefix length. A three-event prefix containing three Credit Review visits is not equivalent to three distinct process stages.

If the supplied schema cannot resolve event order within identical timestamps, do not silently use CSV row order as business chronology. Use source ordering where available, aggregate to timestamps, or quarantine ambiguous prefix boundaries.

### Elapsed-time prefixes

Use all events satisfying

\[
t_e\le \tau_i,
\qquad \tau_i=A_i+24\text{ hours}
\]

for the primary activation-landmark model. The number of events may vary.

For the alternative all-application model, a defensible landmark is, for example, application start plus seven days. That model must handle applications with no events in the first seven days using an explicit no-event/short-prefix state, not future events.

Both methods must enforce event-time and availability-time cutoffs. A snapshot value cannot be recovered merely because its associated event timestamp is early.

### Short cases and loops

- Short cases receive a prefix-availability flag and may be routed to a separately trained short-prefix model.
- Do not pad prefixes with invented events or treat no future event as a feature.
- A case known to have ended before the landmark may have a feature such as `terminal_observed`, but that status must be derived from information already available by the landmark.
- Retain raw event counts and revisit counts. This prevents a document loop from appearing to be equivalent to forward progress.
- Translate validated renamed activities into historical names while retaining a migration-era/source indicator.

## 5. Process-aware features

All features must have both an **event-time rule** and, where necessary, an **availability/ingestion-time rule**.

| Feature family | Examples and construction |
|---|---|
| **Static case attributes** | Region, channel, requested amount, original source, policy/migration period. Use the value available at prediction time; assume stability only after checking whether these fields are versioned. |
| **Prefix control flow** | Counts by canonical activity; presence and order of identity, review, document request, acceptance, and activation; observed transitions; terminal state already known; document-loop count; return-to-review count; last observed activity. |
| **Timing** | Time since application start; time since first review; time between the latest two events; events per observed day; within-observation processing rates; known queue/waiting durations. |
| **Resource and queue** | Resource category or pseudonym rather than unrestricted employee identity; distinct resources observed; historical workload before the landmark; prior completed applications; prior median handling time. Use only reference cases completed before the prediction time, or explicitly model incomplete service times. |
| **Dynamic case information** | Latest `risk_score` available by the landmark, previous risk values and changes, strictly as-of document-request counts. |
| **Cohort/calendar** | Application start month, activation month, policy era, migration era, weekday, working-day counts, source/channel/region. |
| **Historical reference features** | DFG transition frequencies fit on training prefixes only; historical resource experience; prior-month application composition. Unseen categories receive an explicit unknown indicator, not frequencies estimated from the test period. |

A global DFG fitted on complete logs is not a prefix feature. In the implementation below, DFG discovery is restricted to eligible training prefixes. Similarly, resource experience at extraction time must be replaced with a count or summary of experience accumulated strictly before each prediction point.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Final approved limit reflects the completed decision and possibly later revisions. Backfilling it into an early prefix changes the question. | Only a version explicitly available at the prediction point could be used. No such version is supplied here. | Drop from primary feature table; retain separately for audit | A terminal credit decision must not appear in an early application prefix. For the activation-landmark model it could theoretically be known, but a separately timed historical version is required. |
| `decision_reason` | Terminal reason may be backfilled and can encode approval selection or policy changes. | Retain only a historically versioned reason whose availability time precedes the feature time. | Drop here; repair/version only if such timestamps exist | Availability after a decision is not automatically leakage, but terminal-field backfilling is unsafe. |
| `collection_status` | Can directly encode arrears or default. | Only a genuinely past, narrowly defined status could be used in a separately specified postactivation model. | Drop from the primary model | Avoids a near-copy of the target and post-outcome collection processes. |
| Future events, including Contract Signed, Account Activated, Collections Contact, and Default Recorded | Reveals subsequent process and outcome; using a complete-case DFG or sequence creates look-ahead bias. | Every event must satisfy \(t_e\le\tau_i\) and be historically available. Use a prefix-only DFG fit on training cases. | Drop all post-prefix events; keep activation/outcome events in separate cohort logic only | Cohort construction may use activation to define the primary landmark; that does not make activation a permissible feature in an earlier application-only model. |
| `documents_total` | A daily snapshot can include uploads later on the prediction day. | Recompute from document events with \(t_e\le\tau_i\), and verify ingestion availability. Without reliable availability metadata, drop. | Repair, otherwise drop | Calendar-day membership is insufficient for an intraday prediction point. |
| Updated `risk_score` | Using the last or final value imports later decisions and revisions. | Select the latest nonmissing value with event and availability timestamps at or before the prefix boundary. | Repair | A prefix may use a risk score updated within that prefix, never the case’s final score. Resolve simultaneous-version ambiguity conservatively. |
| `org:resource` and resource experience | Extraction-time experience contains the employee’s future workload and experience. | Construct experience from reference cases completed before the prediction point. | Repair | A current extraction-time scalar cannot be used as a historical feature. |
| `default_90d` and `label_available_at` | Direct target and adjudication metadata. A missing label must not become zero. | Join only after feature extraction, requiring verified outcome and as-of availability. | Exclude from features; use for outcome construction | Keeps feature computation independent of target generation. |
| `data_extract_time` and ingestion metadata | Can reveal warehouse snapshot membership or later corrections. | Use for technical availability audits, never as a predictor. | Exclude from features | It is pipeline metadata, not application risk information. |
| Static case columns and `source_system` | May be populated or changed after the prefix. A final source can encode later migration/platform membership. | Use the first or versioned value known by the prediction point. | Repair/version | Migration and source are legitimate history only when observed prospectively. |
| Duplicate events and cross-platform identifiers | Duplicates inflate flow counts; unlinked identifiers can split one case across train and test or double-count an application. | Canonicalize through documented linkage and source event identifiers before splitting. | Repair; quarantine unresolved cases | Case-level temporal validation is invalid if canonical applications can cross partitions. |

A column-name audit is necessary but insufficient. The implementation also checks that every extracted prefix timestamp precedes its as-of landmark and that feature rows belong only to the designated training cohort.

## 7. Validation design

### Temporal design

Use canonical **application start time**, not extraction order, to assign partitions:

- **Training:** starts in 2024.
- **Validation and model selection:** starts from 1 January through 30 June 2025.
- **Locked prospective test:** starts from 1 July through 30 September 2025. Evaluate the primary target only where activation and follow-up satisfy the declared maturity rules.
- **Shadow period:** starts from October through December 2025. This includes the 15 October migration and is primarily a data-quality and partial-horizon evaluation until sufficient outcomes mature.

The final test spans the 1 July policy change, so report its pre-1-July and post-1-July strata separately. It is not evidence of performance on a stable post-migration regime.

For realistic rolling-origin backtesting:

1. At each historical origin, fit preprocessing, reference tables, imputation, and calibration using only information available at that origin.
2. Restrict evaluation to labels available by the origin.
3. Do not use outcomes from later test months to tune an earlier fold.
4. Use calendar-month or contiguous-time block bootstraps by canonical application for uncertainty intervals.

The final 2025 Q3 test has mature 90-day outcomes for sufficiently early activations; the October–December shadow period will not. A 35-day feed delay also requires a later data vintage than the nominal default deadline. Evaluate available 7-day and 35-day label vintages separately if historical vintage data permit it.

### Metrics

For the primary 90-day target:

- AUROC and area under the precision–recall curve, with the mature activated-export prevalence stated as a reference—not an all-application baseline;
- Brier score and log loss using calibrated predicted risks;
- calibration intercept, calibration slope, and calibration plots;
- decision-curve analysis only for an explicitly activation-restricted use case;
- confidence intervals clustered by canonical application and calendar-time block;
- partial-horizon discrimination and calibration while recent outcomes remain censored.

If follow-up supports survival analysis, use censoring-adjusted time-dependent AUC/C-index and calibration of the survival curve at 30, 60, and 90 days. Transfer-related observation loss requires a competing-risk or joint-observation treatment.

### Subgroups and drift

Report metrics and missingness by:

- pre- and post-policy period;
- pre- and post-migration period;
- region, channel, and source;
- partner versus internal accounts;
- activation month and available activation-latency bands.

Inspect feature distribution shift, DFG changes, label prevalence, and feed completeness. A policy-period indicator does not make an unstable policy relationship invariant.

A random case split is misleading because it:

- distributes applications from the same operational periods across folds;
- allows linked or repeated applications to cross partitions;
- evaluates post-migration activity using pre-migration patterns;
- obscures changed activation selection and outcome ascertainment;
- permits future-derived reference statistics to influence historical folds.

## 8. Limitations and decision-use boundary

The study can support **predictive association** for 90-day default after activation, conditional on observed activation and outcome-observation processes. It cannot establish:

- the causal effect of accepting or rejecting an application;
- the default counterfactual for an application that withdrew or was never activated;
- a representative all-application default rate;
- transportability to a materially different lending policy, partner mix, or source system.

The reported 12.5% is a mature-export proportion. It is not appropriate for automatic denial, limit setting, pricing, or portfolio-wide expected-loss calculations without an explicit population and policy estimand.

Deployment can change the data-generating process through at least three mechanisms:

1. **Intervention feedback:** using the score to request documents, change limits, intensify onboarding, or contact applicants changes subsequent behavior and activation.
2. **Operational learning:** experienced staff may handle flagged cases differently, changing review duration and activation selection.
3. **Policy and data-system changes:** future underwriting thresholds, partner referrals, collections practices, migrations, or feed changes alter both risk relationships and label ascertainment.

Accordingly, the primary model should be deployed only within a monitored activation/onboarding boundary, with prospective calibration, subgroup missingness monitoring, and drift alerts. A lender seeking an initial-credit policy model should commission the explicitly different all-application pathway or policy-counterfactual study.

## 9. PM4Py-oriented Python implementation skeleton

This skeleton targets PM4Py 2.7.x; pin and test an exact version in production. It deliberately requires a negative-feed audit: the supplied CSV cannot prove that blank and partner-origin feeds were complete. The model itself is not fitted, and no nonexistent PM4Py survival API is used.

```python
import numpy as np
import pandas as pd
import pm4py

CSV = "applications_events.csv"
CUT = pd.Timestamp("2026-02-15", tz="UTC")
END = pd.Timestamp("2025-12-31 23:59:59", tz="UTC")
K = 3
LD = pd.Timedelta("24h")
ACT, DEF = "Account Activated", "Default Recorded"
COMP = ["Rejected", "Withdrawn", "Transferred"]
ALIASES = {  # Replace only with a validated migration crosswalk.
    "KYC Check": "Identity/KYC Check",
    "Credit Review - New": "Credit Review",
}
# False until zero labels have passed an external complete-feed audit.
NEGATIVE_FEEDS_AUDITED = False

# Canonicalize identifiers using linkage BEFORE this point.
# Quarantine unresolved transfers; do not add linked returns as new cases.
df = pd.read_csv(CSV)
df["case"] = df["case:concept:name"].astype(str)
T, L, E = "time:timestamp", "label_available_at", "data_extract_time"
for col in (T, L, E):
    df[col] = pd.to_datetime(df[col], utc=True, errors="coerce")
df["risk_score"] = pd.to_numeric(df["risk_score"], errors="coerce")
assert df[T].notna().all()

# As-of event and warehouse availability rules.
df = df[
    df[T].between(pd.Timestamp("2024-01-01", tz="UTC"), END)
    & (df[T] <= CUT)
    & (df[E].isna() | df[E].le(CUT))
].sort_values(T, kind="stable").reset_index(drop=True)
df["activity"] = df["activity"] if False else df["concept:name"]
df["activity"] = df["activity"].replace(ALIASES)
assert len(df) == 48000  # After canonicalization, not by dropping duplicates.

# Labels are metadata, not prefix attributes.
known = df[df["default_90d"].notna() & df[L].le(CUT)].copy()
known["default_90d"] = pd.to_numeric(known["default_90d"])
conflicts = set(known.groupby("case")["default_90d"].nunique().loc[lambda x: x > 1].index)
labels = known.sort_values(L).groupby("case")["default_90d"].last()
suspects = set(df.loc[
    df.duplicated(["case", "activity", T, "org:resource"], keep=False), "case"
])
SAFE = ["case:channel", "case:region", "case:requested_amount", "source_system"]

def row_features(prefix, tau, case_events):
    # Both p and e are clipped to the prefix boundary before any access.
    p = prefix[prefix[T] <= tau].sort_values(T, kind="stable")
    if p.empty:
        return None
    e = case_events[case_events[T] <= p[T].max()].sort_values(T, kind="stable")
    r = e["risk_score"].dropna()
    f = {
        "case": p["case"].iloc[0], "as_of": tau, "start": p[T].min(),
        "n_events": len(p), "max_prefix_time": p[T].max(),
        "risk_latest": r.iloc[-1] if len(r) else np.nan,
        "risk_seen": int(len(r) > 0),
        "elapsed_hours": (tau - p[T].min()).total_seconds() / 3600,
        "distinct_resources": e["org:resource"].nunique(),
    }
    for col in SAFE:
        v = e[col].dropna()
        f[col] = v.iloc[0] if len(v) else None
    f["activity_counts"] = p["activity"].value_counts().to_dict()
    f["sequence_first8"] = "|".join(p["activity"].astype(str).head(8))
    f["review_returns"] = max(0, int((p["activity"] == "Credit Review").sum()) - 1)
    f["terminal_observed"] = int(p["activity"].isin(COMP).any())
    return f

# Case-level cohort accounting. Outcome events affect status, never features.
rows = []
for cid, g in df.groupby("case", sort=False):
    a = g.loc[g["activity"].eq(ACT), T].min()
    d = g.loc[g["activity"].eq(DEF), T].min()
    h = a + pd.Timedelta("90d") if pd.notna(a) else pd.NaT
    d = d if pd.notna(a) and pd.notna(d) and a <= d <= h else pd.NaT
    term = g.loc[g["activity"].isin(COMP), T].min()
    term_name = g.loc[g[T].eq(term), "activity"].iloc[0] if pd.notna(term) else None
    y = labels.get(cid, np.nan)
    if pd.isna(a):
        status = ("competing_" + term_name.lower()) if term_name else "open_pending_activation"
    elif a + LD > CUT:
        status = "not_at_landmark"
    elif pd.notna(d) and d <= a + LD:
        status = "default_known_by_landmark"
    elif pd.notna(d) or y == 1:
        status = "default_observed_by_90d"
    elif h > CUT:
        status = "90d_or_label_pending"
    elif y == 0 and NEGATIVE_FEEDS_AUDITED:
        status = "no_default_verified"
    elif y == 0:
        status = "zero_label_feed_unverified"
    else:
        status = "feed_unverified_or_missing"
    reason = {
        "open_pending_activation": "right_censor_time_to_activation",
        "90d_or_label_pending": "label_delay_or_90d_censoring",
        "zero_label_feed_unverified": "unknown_followup_not_assumed_censoring",
        "feed_unverified_or_missing": "unknown_followup_not_assumed_censoring",
    }.get(status, "complete_target_or_not_at_risk")
    rows.append({
        "case": cid, "start": g[T].min(), "activation": a,
        "terminal_event": term_name, "terminal_time": term,
        "default_time": d, "horizon_end": h, "label_due_if_35d_max": a + pd.Timedelta("125d"),
        "ninety_day_mature": bool(pd.notna(a) and h <= CUT),
        "default_by_landmark": bool(pd.notna(d) and d <= a + LD),
        "observation_end": min(END, h) if pd.notna(a) else min(END, CUT),
        "status": status, "censor_reason": reason, "label_reported": y,
    })

c = pd.DataFrame(rows)
assert len(c) == 48000 and c["case"].is_unique
assert not ((c["label_reported"] == 0) & ~c["ninety_day_mature"]).any()
c["y90"] = c["status"].map({
    "default_observed_by_90d": 1, "no_default_verified": 0
})
c["primary_eligible"] = (
    c["y90"].notna() & ~c["default_by_landmark"]
    & ~c["case"].isin(conflicts | suspects)
)
c["split"] = pd.cut(
    c["start"],
    [pd.Timestamp(x, tz="UTC") for x in
     ("2024-01-01", "2025-01-01", "2025-07-01", "2025-10-01", "2026-01-01")],
    labels=["train", "validation", "test", "shadow"], right=False,
)
print(c["status"].value_counts(dropna=False))
print(pd.crosstab(c["split"], c["status"], dropna=False))
print("Already known defaults at landmark:", int(c["default_by_landmark"].sum()))

def to_log(frame):
    out = pm4py.format_dataframe(
        frame[["case", "activity", T]], case_id="case",
        activity_key="activity", timestamp_key=T,
    )
    return pm4py.convert_to_event_log(out) if isinstance(out, pd.DataFrame) else out

train_ids = set(c.loc[c["primary_eligible"] & c["split"].eq("train"), "case"])
train = df[df["case"].isin(train_ids)].copy()
assert train_ids, "No eligible training cases: audit negatives/feed completeness."
log = to_log(train)
fixed, elapsed, prefixes = [], [], []

for cid, n in list(pm4py.get_prefixes_from_log(log, K)):
    g = train[train["case"].eq(cid)]
    p = pm4py.get_case_prefix(
        log, cid, n, activity_key="activity", timestamp_key=T, case_id_glue="case"
    )
    p[T] = pd.to_datetime(p[T], utc=True)
    p["case"], p["activity"] = cid, p["activity"].astype(str)
    p = p.sort_values(T, kind="stable").head(K)  # PM4Py may count implicit start.
    f = row_features(p, g["activation"].iloc[0] + LD, g)
    if f and f["n_events"] == K:
        f["prefix_regime"], _ = "fixed_k3", fixed.append(f)
        prefixes.append(p[["case", "activity", T]])
    e = g[g[T] <= g["activation"].iloc[0] + LD]
    f = row_features(e, g["activation"].iloc[0] + LD, g)
    if f:
        f["prefix_regime"], _ = "elapsed_landmark", elapsed.append(f)

# Fit these two views separately unless a justified comparison design is used.
tables = {"fixed_k3": pd.DataFrame(fixed), "elapsed": pd.DataFrame(elapsed)}
features = pd.concat(tables.values(), ignore_index=True)
dfg = pm4py.discover_dfg(to_log(pd.concat(prefixes, ignore_index=True)))
# Join separately constructed as-of historical resource/queue features here.
# Connect a verified 90-day weighted model or survival model OUTSIDE PM4Py.
# Do not infer survival calls from discover_dfg/get_variants.

forbidden = {
    "final_limit", "decision_reason", "collection_status", "risk_score_final",
    "default_90d", "label_available_at", "data_extract_time",
}
checks = {
    "forbidden_columns": len(set(features.columns) & forbidden),
    "non_training_cases": int((~features["case"].isin(train_ids)).sum()),
    "post_prefix_timestamps": int((features["max_prefix_time"] > features["as_of"]).sum()),
}
print(pd.DataFrame({"check": checks.keys(), "violations": checks.values()}))
assert all(v == 0 for v in checks.values())
```
