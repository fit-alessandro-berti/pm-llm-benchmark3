# 1. Objectives and constraints

There is no single “obvious optimum” here because the queue contains competing goals: urgent SLA protection, specialist quality, continuity, fairness, training, and resilience. The policy should therefore make trade-offs explicit, not pretend that one scalar objective solves everything.

**Optimization objectives**

1. **Short-term throughput / SLA protection**
   - Complete urgent and high-priority work before deadline.
   - Prefer assignments that reduce waiting and avoid unnecessary handovers for time-critical cases.

2. **Quality / rework avoidance**
   - Match required skill to adequate competence.
   - Avoid assigning high-risk work to unsupported trainees.
   - Avoid repeated reassignment loops, especially where historical evidence shows harm after more than two reassignments.

3. **Workload fairness and overtime protection**
   - Distribute new assignments reasonably across resources.
   - Protect resources marked as high overtime risk unless there is an urgent, unavoidable exception.

4. **Skill development**
   - Use normal/low-risk work for supervised training where SLA slack exists.
   - Respect documented training priorities where possible.

5. **Continuity of case ownership**
   - Keep current owners on high-complexity, high-handover-cost cases where their skill is adequate.
   - If ownership must change, reduce handover cost by involving the previous owner or a supervisor.

6. **Resilience and bottleneck avoidance**
   - Avoid creating queues around a few specialists, especially in Security Review and Final Approval.
   - Build secondary capability through supervised pairs and cross-team exposure.

**Hard safety / compliance constraints**

These should not be traded away silently.

- Skill level `0` means “not allowed”; such a resource cannot perform the activity.
- Security Review must be performed by skill level `3`, or by skill level `1–2` only under explicit supervision by `R7_Gita` or `R8_Hugo`.
- Final Approval must be finalized by skill level `2–3`. Skill level `1` may prepare but not finalize.
- High-priority cases, interpreted here as `urgent` or `high`, must not be assigned to skill level below `2` unless supervised.
- No resource receives more than `4` new assignments in the current decision batch.
- Quality Check may be batched only when priority is `normal` or `low` and SLA time remaining is greater than `24h`.
- Do not assign additional work to high-overtime-risk resources unless the SLA risk is urgent and there is no safer alternative.

**Preference / socio-technical trade-offs**

These are weighted, explainable preferences rather than absolute rules.

- Specialist routing reduces errors but may create bottlenecks.
- First-available routing reduces waiting but may increase mismatch, rework, and handovers.
- Continuity is valuable, but not if the current owner lacks adequate skill and no supervision is available.
- Training is valuable, but not on urgent, high-complexity, or high-risk work without strong supervision.
- Fairness should not mean equal assignment regardless of skill, urgency, or team capacity.

# 2. Assignment policy

The policy is a decision-support rule, not a black-box optimizer. Each recommended assignment should generate human-readable reason codes such as:

- `SLA_URGENT`
- `SECURITY_COMPLIANCE`
- `CONTINUITY_HIGH_HANDOVER`
- `OVERTIME_PROTECTION`
- `TRAINING_WITH_SUPERVISION`
- `WORKLOAD_BALANCE`
- `BOTTLENECK_AVOIDANCE`
- `EXCEPTION_NO_SAFE_ALTERNATIVE`

**High-level algorithm**

```text
For each decision batch:

1. Load queue, resource skills, current workload, overtime risk,
   training priorities, and estimated activity durations.

2. Compute SLA risk for each case:
   sla_risk(case) =
       priority_weight(case.priority)
       * deadline_pressure(case.sla_time_remaining)
       + complexity_pressure(case.case_complexity)

   Priority weights:
       urgent = 1.0
       high   = 0.8
       normal = 0.4
       low    = 0.2

   Deadline pressure increases as remaining time approaches expected processing time.

3. Sort cases by descending SLA risk, but keep batchable low-risk quality work
   eligible for batching where allowed.

4. For each case, generate candidate assignments:
   - Single resource assignments.
   - Supervised pairs where needed or useful.
   - Previous owner as primary, supervisor, or handover supporter where appropriate.

5. Apply hard eligibility filters to each candidate:
   - skill[resource][required_skill] > 0
   - Security Review:
       skill = 3, or skill 1–2 with explicit supervisor R7_Gita or R8_Hugo
   - Final Approval:
       finalizing resource must have skill >= 2
       skill 1 may only prepare under a skill >= 2 finalizer
   - urgent/high priority:
       effective skill >= 2 unless supervised
   - new_assignment_count[resource] <= 4
   - Quality batching only if priority normal/low and SLA remaining > 24h
   - high overtime risk resource blocked unless urgent and no safer alternative

6. Score each feasible candidate.

7. Select the best candidate, apply tie-breakers, and update assignment counts.

8. Check training quota:
   - At least 20% of normal/low-priority assignments should support training
     where SLA risk remains acceptable.
   - If quota is not met, increase training bonus for normal/low cases and re-rank,
     unless this would create unacceptable SLA or quality risk.

9. Emit explanation and reason codes for each assignment.

10. If no feasible candidate exists, trigger exception handling:
   - escalate to human coordinator,
   - allow only documented emergency exceptions,
   - defer low-priority work before compromising urgent work.
```

**Scoring components**

A candidate assignment can be scored as:

```text
score =
    w_urgency      * sla_urgency_score
  + w_skill        * skill_match_score
  + w_continuity   * continuity_score
  + w_fairness     * workload_fairness_score
  + w_training     * training_score
  + w_resilience   * resilience_score
  - hard_penalty
```

The weights should be context-dependent and governance-controlled. For urgent cases, SLA and compliance weights increase. For normal/low cases, training and fairness weights increase.

**SLA urgency scoring**

```text
sla_urgency_score =
    priority_weight
    * max(0, 1 - sla_time_remaining / planning_horizon[priority])
```

Example planning horizons:

- urgent: 8h
- high: 12h
- normal: 24h
- low: 72h

Cases with very low remaining SLA time and high complexity receive higher urgency scores.

**Skill-match scoring**

```text
effective_skill =
    performer skill, or
    maximum of performer and supervisor skill where supervision is used

skill_match_score =
    effective_skill / 3
    - overqualification_penalty
    - unsupported_trainee_penalty
```

Specialist use is rewarded when risk is high, but a small bottleneck penalty is applied when a non-urgent case could be handled safely by a competent non-specialist.

**Continuity / handover-cost scoring**

```text
if candidate includes current owner:
    continuity_score = owner_bonus
else:
    continuity_score =
        - handover_cost_penalty[handover_cost_band]
        * case_complexity

Extra penalty if:
    reassignment_count > 2
    handover_cost_band = high
    case_complexity high
```

Handover cost bands can be encoded as:

- low = 0.2
- medium = 0.5
- high = 1.0

**Workload and overtime fairness scoring**

```text
workload_fairness_score =
    0.4 * inverse_open_cases_score
  + 0.3 * hours_remaining_score
  + 0.3 * overtime_safety_score
```

High overtime risk receives a strong penalty unless the case is urgent and no safer alternative exists. Supervised pairs count both resources for workload capacity.

**Training / development scoring**

```text
training_score =
    1.0 if:
        case priority is normal or low
        SLA slack is acceptable
        trainee skill is 1 or 2 where allowed
        trainee's documented training priority matches required skill
        qualified supervisor is available
    0.0 otherwise
```

If the batch is below the 20% training target for normal/low work, an additional quota bonus is added to eligible training candidates.

**Resilience / bottleneck avoidance**

```text
resilience_score =
    + backup_bonus if assignment develops secondary capability
    + team_spread_bonus if work is moved away from saturated team
    - specialist_bottleneck_penalty if assignment concentrates work
      on a scarce specialist or highly central resource
```

Process-mining indicators, such as handover-network centrality and activity-based resource similarity, can be used to update these penalties over time.

**Tie-breaking**

If scores are close, use this order:

1. Preserve safety/compliance.
2. Reduce immediate SLA risk.
3. Prefer current owner for high-complexity, high-handover-cost cases.
4. Prefer lower overtime risk.
5. Prefer lower current open cases.
6. Prefer documented training value.
7. Prefer batching opportunities where allowed.
8. Escalate to human review if the choice remains ambiguous.

**Exception handling**

- If no eligible resource exists, escalate; do not silently violate skill rules.
- If only a high-overtime-risk resource is available for urgent work, allow assignment only with reason code `EXCEPTION_NO_SAFE_ALTERNATIVE`.
- If a training candidate has skill `0`, they may shadow but not perform.
- If estimated hours exceed remaining capacity, defer low-priority work first, not urgent/high work.
- If supervision capacity is exhausted, reduce training assignments before reducing compliance or SLA protection.

**Likely baseline behavior on this queue**

First-available routing would tend to select resources with low open-case counts, such as R10, R6, R3, and R8. This may look fair, but it can assign complex security or approval work to resources without sufficient specialization, or overload low-load resources with too many varied tasks.

Specialist-only routing would tend to push Security Review toward R7/R8, Final Approval toward R6, Negotiation toward R6/R5, and Diagnosis toward R3/R4. This reduces skill mismatch but creates hot spots. R6, R8, and R3 could become bottlenecks, and high-complexity owner continuity could be damaged.

The proposed policy intentionally accepts some local inefficiencies, such as supervised pairs and occasional owner changes for overtime protection, to improve overall service reliability, fairness, and skill development.

# 5. Explanation to workers

We are using a transparent assignment helper, not a hidden ranking system. The goal is not to push as much work as possible onto individuals, but to make assignments that are safe, fair, and explainable.

Assignments are based on several practical considerations:

- **Customer deadlines:** Urgent cases are assigned first, especially where SLA time remaining is very short.
- **Required skills and permissions:** Some activities, especially Security Review and Final Approval, have strict skill and supervision rules. These are not bypassed.
- **Case continuity:** Where a case is complex, sensitive, or already has many handovers, we try to keep the current owner if their skill level is adequate.
- **Workload and overtime protection:** We avoid adding non-urgent work to colleagues already at high overtime risk. If an urgent exception is necessary, it is documented.
- **Training and development:** Where the SLA allows, normal and low-priority cases are used for supervised training that matches documented development priorities.
- **Bottleneck avoidance:** We try not to overload a small number of specialists, because that creates delays for everyone and increases pressure.

If you receive a training case, the expectation is not that you handle it alone under pressure. There should be a named supervisor or reviewer. If you are asked to shadow a case, this is for learning and does not mean you are accountable for performing work above your current permission level.

If an assignment feels wrong, unsafe, or impossible within the remaining time, please raise it. The assignment logic is meant to support human judgment, not replace it. Exceptions should be visible, discussed, and logged so we can improve the policy.

# 6. Process-mining audit indicators

The deployed policy should be audited continuously using the event log. The log should contain case attributes, activity names, timestamps, resources, required skill, priority, SLA deadline, complexity, current owner, assignment reason, reassignment count, workload snapshot, and handover cost band.

| Indicator | Definition | Why it matters | Suggested target / interpretation |
|---|---|---|---|
| Handover frequency | Number of owner/resource changes per case, or per unit of time. Derived from changes in `org:resource` or `current_owner`. | Excessive handover increases waiting and context loss. | Median handovers should remain low; high-complexity cases should have fewer handovers. |
| Reassignment count | Mean, median, and share of cases with `reassignment_count > 2`. | Historical evidence links >2 reassignments to higher rework and appeal rates. | Share of cases >2 reassignments should decrease after policy deployment. |
| Skill mismatch | Assignments where effective skill is below required threshold, e.g. high-priority work below skill 2 without supervision, Security without skill 3 or approved supervision, or Final Approval below skill 2. | Direct compliance and quality risk. | Hard violations should be zero; near-misses should be investigated. |
| Workload distribution | Gini coefficient or coefficient of variation of new assignments per resource; also team-level workload distribution using `workload_snapshot`. | Detects hidden overload and unfairness. | Stable or decreasing inequality; no persistent outliers. |
| Overtime risk exposure | Share of new assignments given to resources with `overtime risk = high`; estimated assigned hours versus `Hours remaining today`. | Protects worker wellbeing and reduces burnout-driven errors. | High-overtime assignments should be rare and limited to documented urgent exceptions. |
| SLA misses | Cases completed after `sla_deadline`; also near-miss rate where completion occurs close to deadline. | Core service-level outcome. | Urgent/high SLA misses should be minimized; trend should improve. |
| Rework / appeal after assignment | Rate of `Rework Correction`, repeated diagnosis loops, or appeal-like variants after assignment. Can be measured using variants and activity sequences. | Shows whether assignments are causing downstream quality problems. | Lower rework after supervised training and continuity-preserving assignments. |
| Training assignment share | Share of normal/low-priority assignments that have `assignment_reason` indicating documented training, with appropriate supervision. | Ensures development objective is not crowded out by short-term pressure. | At least 20% of normal/low assignments where SLA risk is acceptable. |
| Specialist bottleneck indicators | Queue length, waiting time, and utilization for Security Review and Final Approval; centrality of specialists in handover/working-together networks. | Specialist-only routing can create hidden bottlenecks. | No sustained increase in specialist waiting time or centrality concentration. |
| Policy deviations | Assignments where actual assignment differs from recommended policy, missing `assignment_reason`, or exception code used. | Audits whether the policy is followed and whether exceptions are justified. | Low deviation rate; all deviations explained and categorized. |
| Continuity preservation rate | Share of high-complexity, high-handover-cost cases kept with current owner or handed over with previous owner involvement. | Measures respect for continuity constraint. | High for high-complexity/high-handover cases. |
| Supervised training safety | Rate of trainee assignments that have a qualified supervisor recorded; rework rate for supervised versus unsupervised trainee work. | Ensures training does not become unsafe offloading. | Supervised trainee rework should not exceed acceptable threshold. |

# 6.1 Handover frequency from resource changes
def count_owner_changes(case_frame):
    resources = case_frame[RESOURCE].tolist()
    changes = 0
    for i in range(1, len(resources)):
        if resources[i] != resources[i - 1]:
            changes += 1
    return changes

handover_frequency = (
    df.sort_values(TIMESTAMP)
      .groupby(CASE)
      .apply(count_owner_changes)
      .rename("handover_count")
)

# 6.2 Reassignment count audit
reassignment_audit = (
    df.groupby(CASE)["reassignment_count"]
      .max()
      .rename("max_reassignment_count")
)

high_reassignment_share = (
    (reassignment_audit > 2).mean()
)

# 6.3 Skill mismatch audit
# This requires an effective-dated skill matrix.
# Example structure:
# skill_matrix[resource][required_skill] = 0/1/2/3

skill_matrix = {
    "R1_Amal": {"Eligibility": 3, "Diagnosis": 1, "Negotiation": 2,
                "Security": 0, "Approval": 1, "Quality": 2, "Rework": 2},
    # add all resources
}

def skill_mismatch(row):
    resource = row[RESOURCE]
    required_skill = row.get("required_skill")
    activity = row[ACTIVITY]

    # Only evaluate assignment-relevant activities
    assignment_activities = {
        "Eligibility Review",
        "Technical Diagnosis",
        "Customer Negotiation",
        "Security Review",
        "Final Approval",
        "Quality Check",
        "Rework Correction"
    }

    if activity not in assignment_activities:
        return False

    if required_skill is None or resource not in skill_matrix:
        return False

    skill = skill_matrix[resource].get(required_skill, 0)

    # Hard rules
    if activity == "Security Review":
        # Skill 3 required unless supervised by R7_Gita or R8_Hugo.
        # In a real log, supervision should be recorded in assignment_reason
        # or a supervisor attribute.
        if skill < 3:
            return True

    if activity == "Final Approval":
        if skill < 2:
            return True

    if row.get("case_priority") in ["urgent", "high"]:
        if skill < 2:
            # In production, check whether supervised pair is recorded.
            return True

    return skill == 0

skill_mismatch_rate = df["skill_mismatch_flag"].mean()

# 6.4 Workload distribution audit

    df.groupby(RESOURCE)[CASE]
      .nunique()
      .rename("cases_touched")
)

def gini_coefficient(series):
    values = series.sort_values().values
    if len(values) == 0 or values.sum() == 0:
        return 0.0
    index = range(1, len(values) + 1)
    return (2 * sum(i * v for i, v in zip(index, values))
            / (len(values) * values.sum())) - (len(values) + 1) / len(values)

workload_gini = gini_coefficient(workload_by_resource)

    overtime_exposure = (
        df[df["overtime_risk"] == "high"]
          .groupby(RESOURCE)[CASE]

    )
else:

    deadline = case_frame["sla_deadline"].iloc[-1]
