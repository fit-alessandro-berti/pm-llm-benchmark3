## 1. Duplicate-handling decision tree

A rule-based tree that classifies every candidate pair before any action is applied. The tree flows from structural identity to semantic context.

1. **Exact technical duplicate**  
   *Condition*: Identical `source_event_key`, `payload_hash`, `timestamp`, `activity`, and `source`.  
   *Terminal action*: **Drop** one copy. Retain the record with the lowest `source_seq` or highest confidence flag, but delete the redundant row. No semantic loss.

2. **Same physical event observed by multiple systems**  
   *Condition*: Shared core objects (e.g., O1) and timestamp, but `payload_hash` differs because systems enriched or abstracted the same reality differently (e.g., WMS added location, ERP did not).  
   *Terminal action*: **Retain both with refined labels/qualifiers**. Add a `system_view` tag (e.g., `WMS_location`, `ERP_summary`) and preserve both `original_activity` and any system-specific attributes. Do not merge payloads.

3. **Summary event derived from a detailed event**  
   *Condition*: One event is temporally after another, shares most attributes, and Fact 3/8 indicates the later event is a system-generated aggregate or status update from the earlier one (e.g., e07 from e06, e15 from e12/e13/e14).  
   *Terminal action*: **Retain both, mark the later as `derived_from`**. Keep the detailed event as the source of truth; the summary retains its own eid but carries a `derivation_rule` provenance link. Do not delete the detailed event.

4. **Harmonization collision between semantically distinct source activities**  
   *Condition*: After activity harmonization, two events share the same label (e.g., `Dispatch Package`) but originated from activities with different business meanings (e.g., “released from warehouse” vs. “accepted by carrier”).  
   *Terminal action*: **Retain both, refine labels to distinguish original meaning**. Restore or tag `original_activity` (the pre-harmonization label) and keep the harmonized label as `canonical_activity`. Add a `harmonization_source` field indicating which system drove the merge.

5. **Concurrent same-label events involving different objects**  
   *Condition*: Same activity and timestamp, but the `related objects` set differs (e.g., Pick Item for I1 vs. I2).  
   *Terminal action*: **Retain both unchanged**. The shared label is superficial; the object distinction proves they are separate business instances. No merge or drop.

6. **Unresolved candidate**  
   *Condition*: Evidence is insufficient to classify into 1–5 (e.g., timestamp ties, shared objects, but no clear lifecycle or payload difference).  
   *Terminal action*: **Quarantine for review**. Flag in an audit table; no automatic drop or merge. An analyst resolves manually.

## 3. Timestamp-tie ordering rules

A deterministic partialordertototalorder policy that respects business semantics before imposing mechanical order.

### Rule definitions
- **Domain constraints**: Business rules that are nonnegotiable (e.g., “payment authorization must precede capture for the same payment ID”; “pick must precede pack for the same item”). These are encoded as hard constraints in the ordering function.
- **Withinsource sequence**: If two events share the same `source` and timestamp, use `source_seq` to order them. This preserves the internal logic of each system.
- **Lifecycle constraints on shared objects**: For any object X, the order must respect the canonical lifecycle XYZ (e.g., Order  Pick  Pack  Handover  Deliver). If two events touch the same object, the one earlier in the lifecycle comes first, regardless of timestamp ties.
- **Sourcespecific semantics**: Certain sources are authoritative for specific transitions (e.g., Carrier is authoritative for Handover/Dispatch; WMS for Pack/Release). When timestamps tie and objects differ, the authoritative source for that transition goes first.
- **Ingestion time**: Used only as a stable fallback *after* all semantic rules are applied. It must never override a domain or lifecycle constraint.
- **Stable fallback order**: If all above rules are equal (rare), order by `source` alphabetically, then `source_seq` ascending. This ensures determinism without claiming semantic truth.

### Why adding microseconds before deciding semantic order is dangerous
Timestamps in multisystem OCELs are often synchronized to the minute or second; subsecond precision is frequently an artifact of clock drift, logging resolution, or dataentry padding. Imposing a total order based on invented microseconds encodes a false physical story: it suggests a sequence of actions that was never measured or intended, potentially reordering truly concurrent events or hiding the real causal chain. Always decide the *semantic* order first; microseconds should only break ties among events that are already proven concurrent or independent.

  Semantic order: e03 (Pick I1, WMS) and e04 (Pick I1, Scanner) are concurrent samephysicalevent qualifiers  placed first (order between them arbitrary but deterministic, e.g., WMS before Scanner).  
  Next: e05 (Pick I2, Scanner) – distinct item, after the I1 picks in lifecycle.  
  Next: e06 (Pack Package, WMS detail) – must follow any pick of I1/I2 that includes P1; here it follows e03/e04/e05.  
  Final: e07 (Pack Package, ERP summary) – derived from e06, placed after e06.

- **e08–e10 at 10:15**:

```python
ocel_stats(ocel_cons, "Conservative scenario")
ocel_stats(ocel_agg, "Aggressive scenario (posthelper merges)")
```

*Notes on the implementation*:
- Deep copies (`copy.deepcopy`) ensure `ocel_raw` is never mutated.
- `pm4py.ocel_drop_duplicates` is used only where exact technical duplicates exist (a noop here, per the data).
- `pm4py.ocel_merge_duplicates` appears in the aggressive block with `have_common_object=True`; the surrounding code and the `verified_pair_merge` helper act as safeguards, especially for e13/e14.
- `pm4py.ocel_sort_by_additional_column` and `pm4py.ocel_add_index_based_timedelta` follow the semantic ordering established by the decision tree, ensuring timestamps are not the sole driver of order.
- The custom `verified_pair_merge` function defines explicit merge rules for e03/e04 and e11/e16, preserving `original_timestamp`, `original_activity` (via tags), `source`, and `source_event_key` in the new event’s metadata.
- Referential integrity is validated by collecting all `related_objects` values and confirming the presence of the eight OCEL objects.

## 7. Sensitivity analysis

Four datasets are compared: **raw**, **conservative**, **evidencebased merge**, and **aggressive library merge**. Below is a discussion of expected changes across key OCEL metrics, followed by six concrete edges/patterns whose interpretation shifts.

### Comparative metrics summary

| Metric | Raw (17 events) | Conservative (17 events, refined) | Evidencebased merge (15 events) | Aggressive library merge (~13 events) |
|---|---|---|---|---|
| **Event count** | 17 | 17 | 15 (e04, e16 retired via merge) | ~13 (additional merges e06/e07, e13/e14) |
| **E2O relation count** | 17 (one per event, multiobject) | 17 (same, with refined roles) | 15 (merged events union their `related_objects`; e.g., e03* has {O1,I1,P1}  scanner data) | 13 (object sets may collapse if events merged) |

Edge frequencies unchanged. | DFG simplifies: PickPack edge frequency drops from 2 (e03,e04) to 1 (e03*); InvoicePayment fanout reduces from two invoice events to one merged node, but edge weight to Payment stays similar. | DFG loses the Pick I1/I2 concurrency (merged into one node), payment split M1/M2 vanishes (single “Capture Payment” node), and DispatchHandover becomes a single edge, flattening the logistics branch. |
| **Itemflattened DFG** | Distinct I1andI2 paths from the two picks; e05 (I2) separate from e03/e04 (I1). | Same paths preserved; qualifiers added but topology identical. | I1 and I2 paths merge at the Pack node because e03*/e04* now represent the “same” pick, potentially erasing the I1/I2 distinction in the DFG. | I1 and I2 fully merged; the DFG shows a single “Pick Item” node with one outgoing “Pack” edge, losing the dualitem concurrency entirely. |

Edge weights unchanged. | e13 and e14 still separate (our evidencebased rules protect them), but the DFG may show a combined “Payment captured” node if downstream consumers ignore the M1/M2 tag; however, the pipeline explicitly retains both, so the payment split remains visible in a welltagged export. | **Critical change**: e13 and e14 merged into one “Capture Payment” node. The DFG now has a single paymentcapture edge from Authorization, erasing the partialpayment branch. This makes the process appear as one complete payment instead of two partials, distorting metrics like “time-to-payment” and “payment success rate.” |

### Six concrete edges/patterns whose interpretation changes

1. **PickPack edge frequency**  
   - *Raw*: Frequency 2, representing two distinct WMSScanner picks (e03, e04) that both feed into e06.  
   - *Evidencebased*: Frequency drops to 1 (merged e03*), suggesting a single pick event, which misleads capacityplanning analysis that relied on dualsensor redundancy.  
   - *Aggressive*: Same as evidencebased but with additional collapses; the DFG may show a single PickPack edge, erasing the parallelsensor insight.

2. **AuthorizationCapture M1/M2 edges**  
   - *Raw*: Two separate edges from e12 (Authorize Payment) to e13 (Capture M1) and e14 (Capture M2), enabling partialpayment tracking.  
   - *Conservative*: Edges preserved with `payment_id` tags (M1, M2).  
   - *Aggressive*: Merged into one AuthorizationCapture edge, making the process appear as a single payment completion. An analyst might incorrectly conclude that the order-to-cash cycle has a 100% payment success rate, when in fact two partial payments occurred.

3. **DispatchHandover edge directionality**  
   - *Raw*: e08 (Release)  e09 (Acceptance)  e10 (Handover) forms a threestep chain.  
   - *Aggressive*: If e08 and e09 merge via `have_common_object=True`, the chain collapses to a single DispatchHandover edge, losing the acceptance intermediate step and obscuring the fact that carrier acceptance is a distinct, inspectable milestone.

4. **InvoicetoPayment edge weight**  
   - *Raw*: Two invoice issuance events (e11, e16) each fan out to payment capture edges, giving a weight of 2 for “Invoice issued  Payment started.”  
   - *Evidencebased*: Merged invoice e11* still fans out to two payment captures, so weight remains 2, but the invoice node is labeled “merged ERP/Billing.”  
   - *Aggressive*: If the merged invoice is treated as one event, the weight might still be 2 (if payments remain separate) or 1 (if payments also merge). The interpretation shifts from “two sourcesystem invoices” to “one canonical invoice,” affecting financial reconciliation reports.

5. **Concurrent Pick events (e03 vs. e05) in the DFG**  
   - *Raw*: e03 (Pick I1) and e05 (Pick I2) are concurrent, both feeding the Pack node; the DFG shows a “diamond” pattern (two picks  one pack), indicating parallel item preparation.  
   - *Evidencebased*: e03 merged with e04, but e05 remains distinct; the diamond pattern is preserved for I2 but I1’s twosensor evidence is lost, subtly changing the perceived parallelism.  
   - *Aggressive*: Both picks merge into one, eliminating the diamond; the DFG looks like a linear PickPack flow, suggesting sequential item handling when actually two items were picked at the same time.

6. **ET–OT weight for “Pick Item”**  
   - *Raw*: Weight 2 (e03 and e04 both contribute to the “Pick Item” activity count).  
   - *Conservative*: Weight 2, with `system_view` annotations.  
   - *Aggressive*: Weight 1, because the library merge removes one of the two events. This changes cycletime calculations: average time per pick drops, potentially misinforming workforce productivity models that assume one pick per transaction.

## 8. Audit trail and reversibility

A structured provenance schema enables full reconstruction of the raw view and transparent traceability of every cleaning decision.

### Provenance schema (perevent record)
| Field | Description | Example |
|---|---|---|
| `canonical_eid` | The event ID in the cleaned OCEL (may be original or newly assigned). | `e03` |
| `source_eids` | List of original source event IDs that contributed to or were merged into `canonical_eid`. | `["e03", "e04"]` |
| `merge_rule` | The decisiontree category or custom rule applied (e.g., `"same_physical_event"`, `"derived_from"`). | `"same_physical_event"` |
| `reviewer_or_rule_version` | Identifier of the analyst or the software version that performed the merge/drop. | `"analyst_v1"` or `"pm4py0.14.1"` |
| `original_activity` | The activity label as it appeared in the source system, before any harmonization or refinement. | `"Pick Item"` |
| `original_timestamp` | The exact business timestamp from the source, preserved without adjustment. | `2026-05-18 10:00:00` |
| `adjusted_timestamp` | If a deterministic total order required a slight shift (never for business timestamps; only for sorting indices), the value added. `NULL` if unchanged. | `NULL` |
| `attributes_retained_from_each_source` | Dictionary mapping source name to the subset of its attributes kept in the canonical event. | `{"ERP": ["ER-100"], "SCANNER": ["S-901"]}` |
| `discarded_conflicts` | Summary of any conflicting attributes that were *not* merged, with reason (e.g., `"WMS location vs. Scanner reading — retained both in system_attributes"`). | `"Location detail from WMS kept separate; scanner reading kept as fallback"` |
| `confidence` | A numeric or categorical score (high/medium/low) indicating how strongly the rule was supported by evidence. | `High` |
| `reason` | Freetext explanation of why this action was taken, linking to the decisiontree path. | `"Same physical pick observed by WMS (location enrichment) and Scanner; payloads differ but objects identical."` |

### Reconstructing the raw view
An analyst can reverseengineer the cleaned OCEL back to the raw state by:
1. **Querying `source_eids`**: For any `canonical_eid`, retrieve the list of original event IDs.
2. **Looking up raw records**: Use the `original_activity` and `original_timestamp` (or the source system’s primary key, if stored elsewhere) to fetch the exact records from the ERP, WMS, scanner, etc., databases.
3. **Restoring dropped events**: If a `merge_rule` was `"drop"`, the `source_eids` list still contains the IDs of the dropped event(s); an analyst can request those records from the source systems using the preserved `source_event_key` or `source_seq`.
4. **Unapplying qualifiers**: Remove `system_view`, `derivation_rule`, or `harmonization_source` tags by stripping the appended strings from `original_activity` or `activity`, returning the label to its precleaning form.
5. **Retiming**: If `adjusted_timestamp` is nonNULL (only in edgecase ordering), subtract the delta to recover the original timestamp.
6. **Full provenance audit**: Export the entire provenance table as a CSV or integrate it into a datalineage tool (e.g., Apache Atlas) to visualize the cleaning pipeline as a directed acyclic graph, where nodes are events and edges are merge/drop rules.

This schema ensures that no decision is “blackboxed”; every change is attributable, reversible, and auditable.

## 9. Failure modes and safeguards

At least eight distinct ways the pipeline can go wrong, with builtin or recommended safeguards.

1. **Collapsing distinct partial payments**  
   - *Failure*: Merging e13 and e14 because they share O1 and V1, producing a single “Capture Payment” event and losing the M1/M2 split.  
   - *Safeguard*: The decisiontree explicitly classifies e13/e14 as “distinct partial payments same timestamp”  **retain both unchanged**. The `verified_pair_merge` helper includes a guard clause: `if "Payment" in related_objects and len(set(payload_hash for ...)) > 1: do_not_merge`. Provenance records `merge_rule: "unresolved"` if a merge is attempted, forcing manual review.

2. **Converting abstractionlevel updates into false rework**  
   - *Failure*: Treating e07 (ERP summary) as equivalent to e06 (WMS detail), then interpreting the OCEL as having two independent pack events, inflating throughput and creating false rework loops.  
   - *Safeguard*: Rule 3 in the decision tree (`Summary event derived from detailed event`) mandates marking the later event as `derived_from` and retaining the detailed event. The pipeline never drops the detailed event; `pm4py.ocel_merge_duplicates` is never called on this pair without first checking for a `derivation_rule` tag.

3. **Ordering by ingestion time**  
   - *Failure*: Using `ingested_at` as the primary sort key, which rearranges events contrary to business lifecycle (e.g., a lateringested event placed before an earlierbusinesstimestamp one).  
   - *Safeguard*: Ingestion time is relegated to the **stable fallback** rule, applied *only* after domain constraints, lifecycle constraints, withinsource sequence, and sourcespecific semantics are satisfied. The Python implementation explicitly sorts by `["timestamp", "source", "source_seq"]` before any ingestiontime consideration.

4. **Treating shared objects as proof of duplication**  
   - *Failure*: Assuming that two events sharing O1 are duplicates and merging them, ignoring that they may represent different business instances (e.g., e13 vs. e14).  
   - *Safeguard*: The decision tree’s Rule 5 (`Concurrent same-label events involving different objects`) requires objectset comparison, not just object presence. The `verified_pair_merge` function checks `set(related_objects_a) == set(related_objects_b)` *and* `payload_hash` equality before merging. The sensitivity analysis explicitly names this failure mode and shows how OTG relations collapse when it occurs.

5. **Unioning incompatible E2O relations**  
   - *Failure*: Merging events and blindly unioning their `related_objects` sets, even when the objects represent different aggregates (e.g., merging e11/e16 unions O1 and V1, but the invoice attributes conflict; a naive union loses which system is authoritative for tax vs. payment terms).  
   - *Safeguard*: The attribute merge policy in Section 2 and the `verified_pair_merge` helper enforce **sourcespecific tagging** (`erp_attr`, `billing_attr`) rather than a flat union. The `attributes_retained_from_each_source` provenance field records which attributes came from which source, preventing loss of authority information.

6. **Changing durations through synthetic microseconds**  
   - *Failure*: After deciding semantic order, adding microseconddelta timestamps (e.g., `e03` at `10:00:00.001`, `e04` at `10:00:00.002`) to force a total order, then using these synthetic deltas to compute cycle times that imply a physical sequence that never existed.  
   - *Safeguard*: The pipeline **never** introduces microseconds to business timestamps. The `pm4py.ocel_add_index_based_timedelta` function computes deltas based on the *index* (position in the sorted list), not on modifying the `original_timestamp` column. The `original_timestamp` field remains untouched; any `adjusted_timestamp` is documented as `NULL` in the provenance schema. The rule “Do not erase the original timestamp” is enforced by code assertions.

7. **Losing sourceauthoritative attributes**  
   - *Failure*: During a merge, keeping only the first event’s attributes and discarding latersource specifics (e.g., dropping Billing’s tax ID when merging e11/e16, because ERP’s event was processed first).  
   - *Safeguard*: The `attributes_retained_from_each_source` provenance field is populated by the merge helper, which iterates over both events’ payloads and stores a dict keyed by source. The `confidence` score for the merge is lowered if any source has a “mustpreserve” flag (e.g., tax identifiers, compliancecritical fields), triggering a quarantine instead of an automatic merge.

8. **Applying duplicate functions to the whole OCEL without inspecting candidate groups**  
   - *Failure*: Running `pm4py.ocel_drop_duplicates` or `pm4py.ocel_merge_duplicates` on the entire event table with default parameters, which may merge events that should remain separate (e.g., e13 and e14) or drop events that are not technical duplicates.  
   - *Safeguard*: The pipeline **always** begins with a precheck (Section 6 code: `groupby("source_event_key").filter(...)`) and a manual decisiontree pass *before* any library function is invoked. The aggressive scenario in Section 6 wraps the library call in a try/except and falls back to the custom `verified_pair_merge` for known pairs. The “Sensitivity analysis” section explicitly compares results of “wholetable merge” vs. “pairwiseinformed merge” to demonstrate the risk. Additionally, the audit trail records which `merge_rule` was applied to which group, providing a posthoc audit if something was missed.
