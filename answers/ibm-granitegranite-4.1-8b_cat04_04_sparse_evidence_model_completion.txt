# 2. Shared Assumptions

1. **Event Completion Semantics**: An activity is considered completed once its timestamp appears in the log; subsequent activities may start immediately or after a systemdefined delay, but we treat the observed order as the effective control flow.
2. **Missing Supplier Confirmation (S)**: Up to ~10% of Supplier Confirmation events may be absent due to integration errors (S5). Models must allow S to be **optional** when a stocked component is presumed.
3. **Absence of External/Stocked Attribute**: No attribute distinguishes external vs stocked components, so S may be conditionally omitted without explicit data.
4. **Optionality Representation**: Optional activities are modeled via **XOR** alternatives in ProcessTree or **conditional transitions** in POWL, with a Boolean guard representing the condition (e.g., `is_external`).
5. **Interleaving of Credit Check (CC) & Engineering Review (ER)**: Highconfidence evidence (S2, D3, D7) suggests **partial order**; models must permit both sequences CCER and ERCC, possibly enforcing concurrency if data supports it.
6. **Expedite Review (E)**: Implemented as an **optional** subbranch that requires a guard `both_checks_done`. If omitted, the path continues directly to Approve Configuration (AC).
7. **Finality of RArchive Case**: Both observed variants and D2 guarantee that Release Production (R) strictly precedes Archive Case (AC).

# 3. Conservative Candidate

## Inductivebias statement
The **conservative** model adopts a strict sequential ordering whenever the evidence is unambiguous, treats Supplier Confirmation as mandatory **unless** a stockedcomponent exception can be explicitly inferred (which we cannot, thus S is retained), and models Expedite Review only when explicitly observed. It heavily penalizes any concurrency that is not directly supported by multiple variants, aiming to **underfit** rather than overfit.

## Compact formal expression
Using PM4Py's ProcessTree syntax, the model is:

```text
( Register Order
   ( Credit Check
         ( Engineering Review
               ( Supplier Confirmation
                     ( Expedite Review?
                         Approve Configuration
                         Release Production
                         Archive Case )
                     Approve Configuration
                     Release Production
                     Archive Case )
               Approve Configuration
               Release Production
               Archive Case )
         Approve Configuration
         Release Production
         Archive Case )
   Approve Configuration
   Release Production
   Archive Case )
```

*Key points*:
- **XOR gates** (denoted by `??`) indicate strict alternatives (e.g., optional `Expedite Review` after both checks).
- **No explicit concurrency** between `Credit Check` and `Engineering Review`; the model assumes the order seen most often (CCER) is the canonical one, with the observed reverse variants treated as noise or measurement error.
- **Supplier Confirmation** is placed **immediately after the checks**, enforcing the highconfidence rule D4.

## Behavior deliberately excluded
1. **Concurrent Credit Check & Engineering Review** that are not sequential (i.e., allowing ERCC without a strict sequence node).
2. **Supplier Confirmation before either CC or ER** (i.e., S appearing earlier than both checks).  
   *Reason*: Only 2/30 traces show this (V5), insufficient highconfidence support.
3. **Expedite Review interleaving with Supplier Confirmation before both checks** (i.e., E appearing before S).  
   *Reason*: Observed only once (V7) and conflicts with D6’s requirement that E follows both checks.

## Known underfitting risks
- **Overrestricting concurrency**: By not modeling the observed parallelism between CC and ER, the model may inaccurately evaluate traces that truly run checks in parallel.
- **Optionality of Supplier Confirmation**: Treating S as mandatory ignores the stockedcomponent exception, potentially misclassifying valid traces that skip S due to internal state.
- **Handling missing S events**: Without a guard for possible omission, the model cannot explain the 4 traces missing S (V3/V4).

# 4. Balanced Candidate

## Inductivebias statement
The **balanced** model captures the most plausible generalization by accommodating observed sequence flexibility, explicit concurrency hints, optional Supplier Confirmation when stock components are presumed, and the conditional Expedite Review. It balances coverage (fitness) and precision by introducing **guards** for optionality and **partialorder constraints** for CCER.

## Compact formal expression (ProcessTree + POWL illustration)
ProcessTree core (central linearization):
```
Register Order  (CC / ER)  Supplier Confirmation?  Expedite Review?  Approve Configuration  Release Production  Archive Case
```
Where `(CC / ER)` denotes a **parallel choice** (XOR in ProcessTree), and `Supplier Confirmation?` is optional (`S?`). `Expedite Review?` is guarded by `both_checks_done`.

POWL illustration (partial order):

```python
po.add_edge(("Expedite Review", "Approve Configuration"))
po.add_edge(("Approve Configuration", "Release Production"))
po.add_edge(("Release Production", "Archive Case"))
```

## Decision between sequence, concurrency, and partial order
- **CC  ER**: Given D3 (both must precede AC) and S2 (parallel execution), the model introduces a **parallel choice** `(CC / ER)` to capture observed reversals while retaining precision.
- **Supplier Confirmation (S)**: Modeled as **optional** (`S?`) per D5 and S4; a guard `is_external` would be inferred from future data.
- **Expedite Review (E)**: Guarded by `both_checks_done` (derived from D6 and S6) and placed **after** the checks but **before** AC, allowing it to appear or not based on trace context.
- **Sequence Constraints**: All mandatory linear steps (AC  R  Archive Case) remain strictly sequential due to highconfidence D2 and universal observation.

## Known underfitting risks
- **Missing explicit concurrency semantics**: By using a parallel `/` operator, we assume both alternatives are equally likely; if one direction dominates in actual processes, fitness may suffer.
- **Guard for stocked components**: Without collected external vs stocked flag, the optional S may be misactivated or deactivated, affecting precision.

# 5. Permissive Candidate

## Inductivebias statement
The **permissive** model embraces a broad class of behaviors consistent with domain rules, allowing any interleaving of Credit Check and Engineering Review, optional Supplier Confirmation under any condition, and Expedite Review appearing anywhere before Approval provided both checks are complete. It prioritizes **generalization** over strict precision, thus suitable for exploratory analysis.

## Compact formal expression
ProcessTree (permissive):
```
Register Order  (Credit Check ? / Engineering Review ?)  (Supplier Confirmation ?)  (Expedite Review{both_checks_done}?)  Approve Configuration  Release Production  Archive Case
```
- `?` denotes optional activities.
- The OR `/` between CC and ER indicates **any ordering or concurrency** is permissible.
- `Expedite Review?` is optional and guarded by `both_checks_done`.

## Selfcontained PM4Py code
```python
import pm4py
from pm4py.objects.process_tree.obj import Operator, Transition, SilentTransition

pt_permissive_str = """
( Register Order
   ( Credit Check? / Engineering Review?
         ( Supplier Confirmation? 
               ( Expedite Review{both_checks_done}?
                     Approve Configuration
                     Release Production
                     Archive Case )
               Approve Configuration
               Release Production
               Archive Case )
         Approve Configuration
         Release Production
         Archive Case )
   Approve Configuration
   Release Production
   Archive Case )
"""

permissive_pt = pm4py.parse_process_tree(pt_permissive_str, ignore_invisible=True)
```

## Boundary between “reasonable generalization” and forbidden behavior
- **Allowed**: Any ordering of CC and ER, optional S, E appearing anywhere **before** AC **provided** `both_checks_done` holds (i.e., both CC and ER have completed).
- **Forbidden**: E appearing **after** AC (violates D6), S occurring **after** AC, or CC/ER not both completed before E (guards enforce this).  
  These constraints are preserved to stay compliant with highconfidence domain rules.

## Known underfitting risks
- **Precision loss**: By permitting virtually any interleaving, the model may incorrectly classify traces that truly follow stricter rules, leading to low precision.
- **Overgeneralization**: Optional S without a condition may admit traces that should be annotated with missing data rather than genuine skipping, inflating generalization but confusing data quality interpretation.

```python

from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition as PWLTransition, SilentTransition as PWSilent
from pm4py.algo.discovery.cfdfg import algorithms as cfdfg

# ------------------- 1. Reconstruct the 30case log -------------------
trace_strings = [
    "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Approve Configuration, Release Production, Archive Case",
    "Register Order, Engineering Review, Credit Check, Supplier Confirmation, Approve Configuration, Release Production, Archive Case",
    "Register Order, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case",
    "Register Order, Engineering Review, Credit Check, Approve Configuration, Release Production, Archive Case",

                     "Register Order, Engineering Review, Credit Check, Supplier Confirmation, Approve Configuration, Release Production, Archive Case": 7,
                     "Register Order, Credit Check, Engineering Review, Approve Configuration, Release Production, Archive Case": 4,
                     "Register Order, Engineering Review, Credit Check, Approve Configuration, Release Production, Archive Case": 3,
                     "Register Order, Credit Check, Supplier Confirmation, Engineering Review, Approve Configuration, Release Production, Archive Case": 2,
                     "Register Order, Credit Check, Engineering Review, Supplier Confirmation, Expedite Review, Approve Configuration, Release Production, Archive Case": 1,

        log_lines.append(activities)

    fitness      = pm4py.fitness_alignments(log, net)

conservative_metrics = eval_metrics(log, conservative_petri)
balanced_metrics     = eval_metrics(log, balanced_petri)
```

# 9. Recommendation and DataCollection Plan

**Immediate Use**: `model_balanced` – it strikes a pragmatic balance between compliance (respecting highconfidence rules D1–D6) and flexibility (allowing observed concurrency and optionality). It provides sufficient fitness while retaining reasonable precision and is ready for operational monitoring.

**Sensitivity Analysis**: `model_permissive` – use this to explore hidden interleavings, test robustness of optional Supplier Confirmation, and assess how many truly hidden traces might appear if external vs stocked flags become available.

**DataCollection Plan**:
1. **Attribute enrichment**: Capture `external_component_flag` for each order to distinguish when Supplier Confirmation is truly required vs optional (solves S3 vs S4 ambiguity).
2. **Timestamp granularity**: Record exact start and end timestamps for Credit Check, Engineering Review, and Expedite Review to resolve DFG ambiguity (D7) and confirm true concurrency vs sequential logging.
3. **Completion flags**: Add a binary flag indicating whether Supplier Confirmation was **intentionally skipped** (e.g., `stocked_component = True/False`) to explicitly model the missingevent uncertainty (S5).
4. **Expedite Review context**: Log the trigger reason for Expedite Review (e.g., `trigger = "deadline"`, `trigger = "material_issue"`) to finetune guard conditions and assess frequency.
5. **Additional traces**: Collect at least 50 new orders spanning diverse product mixes (external vs stocked) and varying urgency levels to better differentiate:
   - Pure concurrency of Credit Check  Engineering Review.
   - Sequencing patterns where Supplier Confirmation precedes one check.
   - Cases where Expedite Review appears either before or after Supplier Confirmation while satisfying the `both_checks_done` guard.
6. **Validation framework**: Implement automated checks (e.g., using the validation code above) after each data batch to monitor fitness, precision, and generalization drift, ensuring the chosen model remains appropriate.

# 10. Uncertainty Statement

| Decision | Calibrated Confidence | Plausible Alternative Interpretation | Impact on Recommendation |
|----------|-----------------------|-------------------------------------|--------------------------|
| **CC  ER ordering** (par  seq) | **Medium** (based on 7/30 traces showing ERCC) | Treat CC and ER as **strictly sequential** (CC must precede ER) per Finance manager’s highconfidence claim (S1). | If true, conservative model would overfit; balanced model’s parallel choice would become excessive, shifting recommendation toward conservative. |
| **Supplier Confirmation optionality** | **LowMedium** (due to 510% missing S events, S5; 4 traces missing S) | Assume **S mandatory for all orders** (S3) and treat missing S as data loss rather than genuine omission. | Would simplify the balanced/permissive models but harm precision for stockedcomponent cases; might reduce recommendation preference for balanced/permissive if missing data dominates. |
| **Expedite Review guard** (requires both checks) | **High** (supported by D6, S6, 2 observed traces) | Allow **E to appear after only one check** if urgency is high, expanding guard to `CC_done || ER_done`. | Would increase permissive model’s flexibility but risk noncompliance; balanced model would need guard relaxation, affecting fitness. |
| **Absence of external/stocked flag** | **Medium** (S4 vs S3) | Infer **stocked vs external** from order volume or supplier list automatically; treat missing S as external omission. | Directly influences optional S modeling; if inference is accurate, balanced/permissive become more precise, strengthening their case. |

**Overall Calibration**: The **balanced model** enjoys **moderate confidence** across the major uncertainties, while the **conservative** and **permissive** models lie at the extremes of underfitting and overfitting risk respectively. The primary uncertainty is the true nature of **CC  ER concurrency**, which could swing the optimal choice. If future data confirms **strict CCER**, the recommendation would shift to conservative; if true concurrency is frequent, balanced remains ideal; if highly flexible interleaving emerges, a more permissive or even hybrid model may be warranted. 

*Plausible Alternative Interpretation*: Assuming **Credit Check must strictly precede Engineering Review** (high confidence from Finance manager, S1) and **Supplier Confirmation is always required** (S3) would eliminate the need for optional guards and parallel choices. Under this strict interpretation, the **conservative** model becomes the clear winner, and the balanced/permissive models would suffer from unnecessary complexity. This alternative directly alters the recommendation from “balanced” to “conservative”.
