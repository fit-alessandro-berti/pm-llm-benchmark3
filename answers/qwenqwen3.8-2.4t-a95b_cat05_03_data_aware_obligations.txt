## 1. Temporal Data Semantics

I reconstruct each case as an event-ordered state history, not as a final-case snapshot.

- **State reconstruction:** For each case, events are ordered by `time:timestamp`, then by `event_index` within identical timestamps. The state applicable to an event is the latest non-blank value for each attribute immediately before that event, or at that event if the event itself is an attribute update.
- **Blank cells:** A blank attribute cell means **“no update at this event.”** It is not a nullification or reset of the attribute.
- **Same-timestamp ordering:** When two or more events share the same UTC timestamp, `event_index` is the tie-breaker. For example, in TX-311, `Enhanced_Review` at index 3 occurs before `Update_Jurisdiction` at index 4, even though both have timestamp `2026-04-06T16:20:00Z`.
- **Final attributes:** Final case values are not copied backward. A final settlement amount, final jurisdiction, final risk level, or later exemption record does not automatically establish the value or evidence state at an earlier `Release_Funds` event.
- **Material changes:** A material change is a change in a governed attribute — amount, risk level, jurisdiction, or customer type — where the policy treats that change as relevant to an obligation. For amount-dependent obligations, R4 specifically treats an increase of more than 20 percent after the latest relevant review as invalidating. A decrease does not by itself invalidate a review.
- **Unknown values:** Unknown amount, risk, jurisdiction, or customer type are not defaulted to low-risk values. If an unknown value is decisive for a trigger or exception, the case is treated as **INDETERMINATE** unless independent evidence resolves it.
- **Temporal layers:**
  - **Event time:** when the operational event occurred, per `time:timestamp` and `event_index`.
  - **Effective time:** when an attribute or exemption is treated as operative. Unless evidence establishes another effective time, this is the event time.
  - **Record time:** when a fact was written to a database or register. A late record may evidence an earlier fact, but is not conclusive by itself.
  - **Evidence time:** when approval, signature, hash, witness, or other evidentiary support existed or was created. Evidence created after the obligation trigger may be insufficient unless it reliably proves an earlier operative approval.

- If an immutable release payload or bank confirmation showed amount < EUR 100,000, R1 would not trigger and the case could become **COMPLIANT**, assuming no other rule triggered.
- If reliable evidence showed the release amount was EUR 150,000, R1 would trigger. The question would then become whether the `Enhanced_Review` covered the amount and current state. If the enhanced review documentation showed it reviewed a 150,000 amount or an amount range including 150,000, the case could become **COMPLIANT**.
- If the release amount was proven to be 150,000 but the enhanced review had no amount evidence, a stricter reading could classify the case **NONCOMPLIANT** because the enhanced review cannot be tied to the amount-dependent obligation.
- If the amount feed outage were treated as creating a presumption that the amount was high rather than unknown, the case could move toward **NONCOMPLIANT**, but R6 forbids silently defaulting missing data to a low-risk value; a conservative control could instead require release blocking or manual evidential review.

### TX-302 — valid exemption, but direct review also exists

TX-302 is classified as **JUSTIFIED_EXCEPTION** because R1 triggered and was waived by EX-77. The enhanced review also independently satisfies R1, so one could alternatively classify the case as **COMPLIANT**.

Evidence or interpretations that would change the result:

- If the qualified signature timestamp or hash evidence were invalid, EX-77 might not be accepted. However, because an `Enhanced_Review` occurred before release and no material change occurred afterward, the case would likely still be **COMPLIANT** on direct review grounds.
- If policy required the exemption database record to exist before release, rather than permitting reliable evidence of earlier approval, the late `Record_Exemption` at 11:00 could create a control deviation. The result might then be **REVIEW_REQUIRED** or a documented exception, depending on the evidentiary standard.
- If the enhanced review were deemed not to cover the current amount or jurisdiction, reliance on the exemption would become more central. If the exemption were then rejected, the case could become **NONCOMPLIANT**.

### TX-310 — weak exemption evidence

TX-310 is classified **NONCOMPLIANT** because R1 triggered, there was no `Enhanced_Review`, and EX-88 does not provide sufficient evidence that approval existed at or before release. The qualified signing certificate was created at 10:30, after the 10:00 release. The witness is the transaction requester, making the oral-approval claim weak without corroboration.

Alternative readings:

- If independent evidence showed Head_Compliance actually approved EX-88 before release — for example, an email, ticket, meeting record, or system audit trail from before 10:00 — the exemption could become valid and the case could become **JUSTIFIED_EXCEPTION**.
- If the organization accepts oral approval by Head_Compliance as sufficient even when the requester is the only witness, the case could be treated as **JUSTIFIED_EXCEPTION** or at least **INDETERMINATE** rather than noncompliant.
- If the qualified certificate creation at 10:30 is merely a late technical signing step for an approval that demonstrably existed before release, the result could change to **JUSTIFIED_EXCEPTION**.
- If `Standard_Review` were accepted as satisfying R1, the case would become compliant, but the policy explicitly states that a `Standard_Review` is not an `Enhanced_Review`.

### TX-311 — same-timestamp ordering and jurisdiction change

TX-311 is compliant under the stated event-index semantics. At release, jurisdiction is DE, so R1 does not trigger. The amount increase from 90,000 to 115,000 occurred before the `Enhanced_Review`, so R4 does not invalidate the enhanced review.

Alternative readings:

- If `event_index` were unavailable or unreliable, the same-timestamp sequence between `Enhanced_Review` and `Update_Jurisdiction` would be ambiguous. The case could become **INDETERMINATE** if the ordering were decisive.
- If the jurisdiction update to DE were treated as a material change requiring a refreshed review even though DE removes the R1 foreign-high-value trigger, the case could become **REVIEW_REQUIRED** or **NONCOMPLIANT** under a broader material-change policy.
- If the jurisdiction update were ineffective and the release jurisdiction remained US, R1 would trigger. However, the existing `Enhanced_Review` occurred after the amount increase and before release, so the case would likely still be **COMPLIANT** unless the review did not cover the current amount.
- If the jurisdiction had changed after the enhanced review from DE to a non-DE jurisdiction, R1 would likely require a new enhanced review, and the result could become **NONCOMPLIANT**.

### Additional possible ambiguity: TX-306

TX-306 is compliant because the amount increase after approval is below 20 percent and R4 does not invalidate it. However, if a stricter policy required any amount increase after `Compliance_Approve` to be re-approved, TX-306 could become **NONCOMPLIANT** or **REVIEW_REQUIRED**. The given note “increase below 20 percent” strongly supports the compliant reading.

def last_row(hist: pd.DataFrame, activities: list):
    sub = hist[hist[ACTIVITY].isin(activities)]
    if sub.empty:

    return sub.iloc[-1]


def row_order_of(row):
    return int(row["row_order"]) if row is not None else None


def time_of(row):
    return row[TIMESTAMP] if row is not None else pd.NaT


def amount_increase_gt20(case_df: pd.DataFrame, review_order, release_order):
    """
    Returns:
      True   if known amount increased by more than 20 percent after review
      False  if known amounts do not show >20 percent increase
      None   if unknown amount prevents classification
    """
    if review_order is None:
        return None

    review_amount = case_df.loc[review_order, "amount"]
    release_amount = case_df.loc[release_order, "amount"]

    if pd.isna(review_amount) or pd.isna(release_amount):
        return None

    after = case_df[
        (case_df["row_order"] > review_order)
        & (case_df["row_order"] < release_order)
    ]

    updates = after.loc[after[ACTIVITY] == "Update_Amount", "amount"].dropna()
    threshold = 1.2 * float(review_amount)

    if (updates > threshold).any():
        return True

    return bool(float(release_amount) > threshold)


def non_amount_material_after(case_df: pd.DataFrame, review_order, release_order):
    """
    Coarse flag for non-amount governed attribute changes after a review.
    Human judgment is needed to determine whether the change is material
    for the specific rule under review.
    """
    if review_order is None:
        return None

    after = case_df[
        (case_df["row_order"] > review_order)
        & (case_df["row_order"] < release_order)
    ]

    return bool(
        after[ACTIVITY]
        .isin(["Risk_Reclassify", "Update_Customer_Type", "Update_Jurisdiction"])
        .any()
    )


def latest_high_pep_trigger_row(hist: pd.DataFrame, release_state: pd.Series):
    """
    Find latest explicit event that established HIGH or PEP status.
    Creation can establish initial status.
    """
    candidates = []

    if release_state["risk_level"] == "HIGH":
        sub = hist[
            hist[ACTIVITY].isin(["Create_Transaction", "Risk_Reclassify"])
            & (hist["risk_level"] == "HIGH")
        ]
        if not sub.empty:
            candidates.append(sub.iloc[-1])

    if release_state["customer_type"] == "PEP":
        sub = hist[
            hist[ACTIVITY].isin(["Create_Transaction", "Update_Customer_Type"])
            & (hist["customer_type"] == "PEP")
        ]
        if not sub.empty:
            candidates.append(sub.iloc[-1])

    if not candidates:
        return None

    return max(candidates, key=lambda r: r["row_order"])


def evaluate_exemption(ex_id, release_time, jurisdiction, customer_type, amount):
    out = {
        "exemption_id": None if pd.isna(ex_id) else ex_id,
        "exemption_referenced": False,
        "exemption_scope_ok": None,
        "exemption_time_ok": None,
        "exemption_evidence_strong": None,
        "exemption_late_record": None,
        "exemption_waived": False,
        "exemption_review_required": False,
    }

    if pd.isna(ex_id):
        return out

    ex_id = str(ex_id)
    out["exemption_referenced"] = True

    if ex_id not in exemption_register.index:
        out.update(
            {
                "exemption_scope_ok": False,
                "exemption_time_ok": False,
                "exemption_evidence_strong": False,
                "exemption_review_required": True,
            }
        )
        return out

    ex = exemption_register.loc[ex_id]

    scope_unknown = pd.isna(jurisdiction) or pd.isna(customer_type) or pd.isna(amount)

    if scope_unknown:
        out["exemption_scope_ok"] = None
    else:
        out["exemption_scope_ok"] = bool(
            jurisdiction == ex["jurisdiction"]
            and customer_type == ex["customer_type"]
            and float(amount) <= float(ex["amount_max"])
        )

    if pd.notna(ex["effective_from"]) and pd.notna(ex["expires"]):
        out["exemption_time_ok"] = bool(ex["effective_from"] <= release_time <= ex["expires"])
    else:
        out["exemption_time_ok"] = None

    signature_before_release = bool(
        pd.notna(ex["qualified_signature_time"])
        and ex["qualified_signature_time"] <= release_time
    )

    certificate_after_release = bool(
        pd.notna(ex["certificate_created"])
        and ex["certificate_created"] > release_time
    )

    out["exemption_evidence_strong"] = bool(
        ex["evidence_strong"]
        and signature_before_release
        and not certificate_after_release
    )

    out["exemption_late_record"] = bool(
        pd.notna(ex["database_record_time"])
        and ex["database_record_time"] > release_time
    )

    out["exemption_waived"] = bool(
        out["exemption_scope_ok"]
        and out["exemption_time_ok"]
        and out["exemption_evidence_strong"]
        and ex["waives"] == "R1"
    )

    out["exemption_review_required"] = bool(
        out["exemption_time_ok"]
        and not out["exemption_evidence_strong"]
        and out["exemption_scope_ok"] is not False
    )

    return out

## 6. Why Control-Flow-Only Conformance Is Insufficient

Control-flow conformance checks whether expected activities occur in an expected order. That is useful, but insufficient for this policy because the obligations are data-conditional, time-sensitive, and evidence-sensitive.

1. **Final-state leakage**
   A control-flow checker that uses final case attributes may wrongly assume the final state governed earlier events. TX-311’s final jurisdiction is `DE`, but the enhanced review occurred before the jurisdiction changed to `DE`. Conversely, a later settlement amount in TX-305 cannot automatically be treated as the release-time amount.

2. **Post-hoc exemptions**
   Exemption records may be inserted after release. In TX-302, the late database insert is explained and supported by strong signature evidence. In TX-310, the late record and backdated display are contradicted by certificate creation after release. Pure control-flow conformance cannot distinguish these evidentiary differences.

3. **Material changes after review**
   A trace may contain `Enhanced_Review` followed by `Release_Funds`, which looks compliant. But in TX-301 and TX-309, later amount increases materially changed the risk profile and invalidated the prior review for amount-dependent obligations. Control-flow-only checks do not calculate amount deltas or review invalidation.

4. **Conditional activation**
   Rules activate only when data conditions are met. `Enhanced_Review` may be mandatory for a foreign high-value transaction but not for a low-value domestic one. `Compliance_Approve` may be mandatory only for HIGH risk or PEP cases. A control-flow model may either require activities unnecessarily or fail to require them when triggered.

5. **Missing data**
   TX-305 has an unknown release amount. A control-flow checker may see `Enhanced_Review` then `Release_Funds` and mark the trace compliant. But without the amount, R1 cannot be established or excluded. Missing data requires indeterminacy handling, not trace matching.

6. **Same-timestamp ordering**
   TX-311 depends on `event_index` at the same timestamp. Without stable ordering, one cannot know whether the jurisdiction update occurred before or after the enhanced review. Timestamp-only control-flow conformance can collapse distinct causal orders into ambiguity.

7. **Evidence quality and effective time**
   The policy requires judging whether approval existed at the relevant time. A displayed effective date, database record time, qualified signature time, certificate creation time, and witness evidence can point to different times. Control-flow conformance has no native way to weigh evidence quality.

8. **Threshold and percentage calculations**
   R1 and R4 require numeric comparisons: EUR 100,000 threshold and >20 percent amount increase. These are data computations, not activity-order constraints.

## 7. Recommended Logging and Control Improvements

To make future transaction-review decisions more determinate, the event log and control architecture should capture the following.

1. **Immutable release payloads**
   Each `Release_Funds` event should include a hash-signed payload containing:
   - amount;
   - currency;
   - jurisdiction;
   - risk level;
   - customer type;
   - referenced exemptions;
   - review identifiers;
   - rule version;
   - release approval identifiers.

2. **Separate event time, effective time, record time, and signature time**
   Every attribute update and exemption event should carry:
   - `event_time`: when the operational action occurred;
   - `effective_time`: when the value became operative;
   - `record_time`: when the database row was inserted or updated;
   - `signature_time`: when a qualified signature or cryptographic approval was created.

3. **Before-and-after values for changes**
   Update events should record both old and new values:
   - `old_amount`, `new_amount`;
   - `old_risk_level`, `new_risk_level`;
   - `old_jurisdiction`, `new_jurisdiction`;
   - `old_customer_type`, `new_customer_type`.

   This would make percentage-change and materiality calculations direct rather than inferential.

4. **Change provenance and reason codes**
   Each update should include:
   - source system;
   - actor or service identity;
   - reason code;
   - supporting document identifier;
   - whether the change is material for compliance rules.

5. **Review snapshot references**
   Each `Standard_Review`, `Enhanced_Review`, and `Compliance_Approve` should reference the exact state snapshot reviewed, ideally by snapshot hash. This would resolve cases like TX-305, where a review exists but the reviewed amount is unclear.

6. **Exemption lifecycle events**
   Exemptions should have explicit events:
   - `Exemption_Requested`;
   - `Exemption_Approved`;
   - `Exemption_Signed`;
   - `Exemption_Recorded`;
   - `Exemption_Revoked`;
   - `Exemption_Expired`.

   Each should include approver, scope, waived rules, effective time, expiry time, and evidence hash.

7. **Stable global event ordering**
   In addition to timestamps, logs should include a monotonic event sequence number or logical clock per case. This avoids reliance on timestamp equality and makes same-timestamp ordering auditable.

8. **Rule versioning**
   Each release or review decision should record which policy version and rule set were applied. This is essential when rules change while cases are in flight.

9. **Sanctions-screening versioning**
   `Sanctions_Screen` events should record:
   - sanctions-list version;
   - jurisdictions screened;
   - screening result;
   - expiry or validity window of the screening result.

   `Sanctions_List_Update` events should record list version and effective time.

10. **Blocking controls for missing decisive data**
   If amount, jurisdiction, risk level, or customer type is unknown at release, the system should either block release or create an explicit `Missing_Data_Escalation` event. This prevents ambiguous releases such as TX-305.
