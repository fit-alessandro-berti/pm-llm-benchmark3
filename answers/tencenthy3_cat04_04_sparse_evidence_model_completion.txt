**Why both DFG directions do not prove concurrency.**  
The DFG contains `Credit Check  Engineering Review` (17) and `Engineering Review  Credit Check` (11). A directly-follows edge only records that, in some trace, activity A’s *completion* was immediately followed by B’s *completion*. The reverse edge records the opposite completion order in other traces. # 2. Shared Assumptions

1. **Event-completion semantics:** Traces record only completion events. A total order in the log is a projection of the underlying partial order; same-timestamp activities are ordered arbitrarily by ingestion.
2. **Missing `Supplier Confirmation`:** Observed absence of `SC` is treated as a single abstraction covering both true optionality (S4) and possible missing events (S5). The model cannot distinguish them; therefore `SC` is represented as a control-flow optional skip.
3. **Absent external/stocked attribute:** Because the component type was not exported, we do not condition `SC` on data attributes. Optionality is modeled purely in control flow.
4. **Optionality representation:** Optional activities are encoded with an `XOR(activity, silent )` or, in the process tree, by omitting them in some branches. “At most once” is enforced because no loop operator is introduced.
5. **Single execution per activity:** No evidence of loops or rework; all candidates are acyclic.
6. **High-confidence backbone:** `RO` is the only start, `AR` the only end, and `AC  RP  AR` is common to all models.

# 3. Conservative Candidate

### Inductive-bias statement
The conservative model prefers specificity over generalization. It admits exactly the observed variants and nothing else, relying only on high-confidence rules D1–D2 plus the empirical trace set. This minimizes precision risk on the observed data but treats every unobserved ordering as impossible. Duplicate activity labels appear in every XOR branch; the tree grows linearly with the number of variants, which is comprehensible for 7 variants but does not scale to large logs and will underfit if the true process has unobserved but valid behavior.

### Compact formal expression
\[
M_{C} = \bigoplus_{v \in V_{obs}} \text{seq}(v), \quad V_{obs}=\{\text{the 7 observed variants}\}
\]

# 4. Balanced Candidate

### Inductive-bias statement
The balanced model generalizes the observed variants only where the evidence or medium-confidence rules support it. It treats `Credit Check` and `Engineering Review` as concurrent (both orders observed; S1/S2 conflict). It encodes D3, D4, and D6 as hard constraints, and encodes D5 (“after at least one check”) by choosing between two branches: `SC` ordered after `CC` or after `ER`. This admits the observed `CC–SC–ER` pattern and its symmetric `ER–SC–CC`, but stops short of allowing `SC` before both checks.

### Compact formal expression
\[
M_{B} = RO \to \text{XOR}(B_{CC}, B_{ER}) \to RP \to AR
\]
where each branch contains `CC` and `ER` concurrent, `AC` after both, optional `EX` after both, and optional `SC` after the branch-specific check (`CC` in \(B_{CC}\), `ER` in \(B_{ER}\)), all before `AC`.

### Self-contained PM4Py code (POWL)
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
import pm4py

def opt(t):
    return OperatorPOWL(OperatorPOWL.XOR, [t, SilentTransition()])

def balanced_branch(sc_after_cc):
    cc = Transition("Credit_Check")
    er = Transition("Engineering_Review")
    sc = opt(Transition("Supplier_Confirmation"))
    ex = opt(Transition("Expedite_Review"))
    ac = Transition("Approve_Configuration")
    po = StrictPartialOrder([cc, er, sc, ex, ac])
    po.order.add_edge(cc, ac)
    po.order.add_edge(er, ac)
    po.order.add_edge(cc, ex)
    po.order.add_edge(er, ex)
    po.order.add_edge(ex, ac)
    if sc_after_cc:
        po.order.add_edge(cc, sc)
    else:
        po.order.add_edge(er, sc)
    po.order.add_edge(sc, ac)
    return po

branch_a = balanced_branch(sc_after_cc=True)
branch_b = balanced_branch(sc_after_cc=False)
xor_checks_sc = OperatorPOWL(OperatorPOWL.XOR, [branch_a, branch_b])

ro = Transition("Register_Order")
rp = Transition("Release_Production")
ar = Transition("Archive_Case")
model_balanced = StrictPartialOrder([ro, xor_checks_sc, rp, ar])
model_balanced.order.add_edge(ro, xor_checks_sc)
model_balanced.order.add_edge(xor_checks_sc, rp)
model_balanced.order.add_edge(rp, ar)
```

### How sequence / concurrency / partial order were decided
- **Credit Check & Engineering Review:** Both orders observed and stakeholders conflict; modeled as concurrent (no edge between them) rather than enforcing S1’s sequence.
- **Supplier Confirmation:** Observed after both checks and between `CC` and `ER`. D5 says “after either.” Modeled by an `XOR` of two branches giving `SC` a prerequisite of `CC` or `ER`, but never both, so `SC` may still interleave with the other check.
- **Expedite Review:** D6 medium says after both checks; modeled with edges from both `CC` and `ER` to optional `EX`, and `EX  AC`. Its order with `SC` is left free (no edge), satisfying S6.

### Behavior deliberately excluded
- `SC` before any check (`RO, SC, CC, ER, ...`).
- `EX` before `CC` or `ER` completes.
- More than one `EX` or `SC` (optional `XOR` with silent skip enforces at most once).
- Any trace missing `CC` or `ER`.

### Known underfitting risks
- If `SC` occasionally legitimately starts before both checks (despite low–medium D5), the model will reject those cases.
- The branch choice is redundant for “after both” cases; this is a harmless abstraction but may slightly reduce precision.

# 5. Permissive Candidate

### Inductive-bias statement
The permissive model encodes only the medium/high-confidence constraints as loose partial-order constraints and admits any remaining ordering consistent with them. It keeps `CC` and `ER` mandatory before `AC`, keeps `EX` after both checks, but relaxes D5: `SC` is optional and only constrained to occur after `Register Order` and before `Approve Configuration`. This is the explicit boundary—behavior that remains forbidden is anything violating D1, D2, D3, D4, or D6.

### Compact formal expression

M_{P} = PO\big(\{RO, CC, ER, SC?, EX?, AC, RP, AR\}\big)

### Known underfitting risks

# 9. Recommendation and Data-Collection Plan

**Recommended for immediate use:** `model_balanced`.  
It fits all 30 observed variants, respects medium/high-confidence rules (D1–D4, D6), and avoids the most clearly undesirable behavior (e.g., `SC` before any check). It is robust enough for operational monitoring while remaining explainable.

**Recommended for sensitivity analysis:** `model_permissive` (optimistic bound) together with `model_conservative` (pessimistic bound). If only one is chosen, use `model_permissive` to test how much missing/unordered `Supplier Confirmation` data could distort conformance and performance metrics; the conservative model should additionally be used as a strict compliance baseline.

**Concrete data-collection plan to resolve ambiguities**
1. **Export the external/stocked component attribute** so true `SC` optionality can be separated from missing-event optionality (S3, S4, S5).
2. **Collect start and complete lifecycle timestamps** for every activity (not just completion). This directly tests S1 vs S2 and D7: we can then measure overlap of `CC` and `ER` and detect true concurrency.
3. **Instrument the integration that drops `SC`** (S5) and flag cases where `SC` was expected but absent, so missingness is a known Boolean rather than silent.
4. **Targeted future traces:** prioritize collecting cases that would distinguish the hypotheses:
   - `RO, ER, SC, CC, ...` (symmetric SC-between pattern);
   - `RO, SC, CC, ER, ...` (SC before both checks—should be rare if D5 holds);
   - `RO, CC, ER, EX, AC, RP, AR` without `SC` (tests whether `EX` depends on `SC`);
   - Cases with identical start timestamps for `CC` and `ER` (direct concurrency evidence).
5. **Increase sample size** to >200 cases, especially for the rare `Expedite Review` variant, to estimate its true frequency and ordering distribution with `SC`.

# 10. Uncertainty Statement

| Decision | Calibrated confidence | Plausible alternative that would change recommendation |
|---|---|---|
| `CC` and `ER` are both mandatory before `AC` | Medium–high (~0.8) | If a later attribute shows some emergency cases skip `ER`, a model with optional `ER` would be needed. |
| `CC` and `ER` are concurrent / unordered | ~0.6 (both orders observed, but stakeholder conflict) | If S1 (Finance) is enforced, a strict `CC  ER` sequence is correct and the balanced/permissive partial order overfits. |
| `SC` is optional because of stocked components | ~0.7 | If S5 missing-data rate is higher than thought, many no-`SC` traces actually required `SC`; then models should treat `SC` as mandatory and impute missing events. |
| `SC` must follow at least one check (D5) | Low–medium (~0.4) | If D5 is ignored as unreliable, `Permissive` becomes preferable; if D5 is stronger, `Balanced` should be tightened to forbid `SC` before both. |
| `EX` is optional, after both checks, before `AC` | Medium (~0.7) | If `EX` can occur before `ER` in a rush scenario, the `EX` ordering constraints in all three models are too strict. |
| Observed variants are representative | Low–medium (n=30, rare `EX`) | New variants with `EX` but no `SC`, or `ER, SC, CC`, may appear and shift fitness/precision rankings. |

**Key alternative interpretation:** If future lifecycle timestamps show that `Credit Check` always starts and ends before `Engineering Review`, then the balanced/permissive concurrency assumption is wrong and a sequential model (or the conservative enumeration with only `CCER` branches) would be materially better. Conversely, if the missing-`SC` rate is confirmed near 10% and external/stocked is not the only cause, the conservative model’s acceptance of no-`SC` traces is misleading, and a mandatory-`SC` model with missing-data imputation should replace all three candidates.
