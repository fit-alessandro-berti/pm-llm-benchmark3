## 1. Interaction-graph description

To understand how individual jobs become tightly coupled despite appearing independent in flattened event logs, we model the manufacturing execution system as a **Typed Object Interaction Graph (OIG)**. In this model, vertices represent distinct entity instances, and edges capture structural, transactional, or operational dependencies.

```
+---------------------------------------------------------------------------------------------------+
|                                 TYPED OBJECT INTERACTION GRAPH                                    |
+---------------------------------------------------------------------------------------------------+

[ ComponentLot: L7 ] --(contains)--> [ Component: C2 ] <--(requires)-- [ Job: J2 ] --(batches)--> [ Batch: B1 ]
        |                                                                 |                             |
    (contains)                                                      (consolidates)                 (executes_on)
        v                                                                 v                             v
[ Component: C5 ] <--(requires)-- [ Job: J5 ]                        [ Shipment: S2 ]               [ Machine: OVEN-1 ]
                                      |                                                                 ^
                                  (batches)                                                             |
                                      v                                                            (executes_on)
                                [ Batch: B2 ] ----------------------------------------------------------+
                                      |
                                 (uses_tool)
                                      v
                                [ Tool: RACK-7 ]

[ Job: J3 ] --(uses_tool: 09:00-11:40)--> [ Tool: FIX-A ] <-- (uses_tool: 11:45-...) -- [ Job: J4 ]
     |                                                                                       |
(processed_on)                                                                          (processed_on)
     v                                                                                       v
[ Machine: CNC-2 ] <-------------------------------------------------------------------------+

[ Job: J5 ] --(tested_on)--> [ Machine: TEST-1 ] <-- (tested_on) -- [ Job: J6 ]
     |                             ^                                   |
 (requires)                    (mounted_on)                        (requires)
     v                             |                                   v
 [ Tool: CAL-3 ] ------------------+-------------------------------> [ Tool: CAL-3 ]
```

### Node Types
- **Job ($J$)**: Dynamic entity tracking work-in-progress (J1–J6).
- **Component ($C$)**: Physical material inputs (C1–C6) required 1:1 by Jobs.
- **ComponentLot ($L$)**: Material batch origin (L7, L8) grouping multiple Components.
- **Machine ($M$)**: Processing equipment (CNC-2, OVEN-1, TEST-1).
- **Tool ($T$)**: Auxiliary resource required for setup, staging, or processing (FIX-A, RACK-7, CAL-3).
- **Batch ($B$)**: Transient grouping object (B1, B2) required for thermal processing.
- **Shipment ($S$)**: Logistic consolidation object (S1, S2, S3) grouping completed Jobs for dispatch.

### Edge Types and Qualifiers
- `requires` ($J \rightarrow C$, Direct): Structural dependence of a Job on a specific Component.
- `contains` ($L \rightarrow C$, Direct): Allocation of Components to a parent ComponentLot.
- `batches` ($B \rightarrow J$, Direct): Inclusion of a Job in a batch event.
- `consolidates` ($S \rightarrow J$, Direct): Association of a Job with an outbound shipment.
- `executes_on` ($B \rightarrow M$ / $J \rightarrow M$, Direct): Execution of an activity on a specific machine.
- `uses_tool` ($J \rightarrow T$ / $B \rightarrow T$, Direct & Inferred): Allocation of a tool to a job or batch.
- `blocks_tool` ($J_i \rightarrow J_k$, Inferred): Temporal allocation overlap where $J_i$ holds tool $T$ required by $J_k$.
- `awaits_lot_release` ($J \rightarrow L$, Inferred): Operational holding of a Job due to quarantine status of its parent Lot.

### Higher-Order Interaction Motifs

1. **Batch-Tool-Machine Synchronization Motif ($B - T - M - \{J_i\}$)**
   - *Structure*: Hyper-edge connecting Batch $B_1$, Machine $OVEN-1$, Tool $RACK-7$, and Jobs $\{J_1, J_2, J_3\}$.
   - *Dynamics*: All jobs in $\{J_i\}$ must reach readiness before $B_1$ can enter $OVEN-1$. Simultaneously, $RACK-7$ must be available and clean. Delay in any single job or in tool sanitization halts processing for all co-batched jobs.

2. **Lot-Quarantine Multi-Job Coupling Motif ($L - \{C_i\} - \{J_i\} - B$)**
   - *Structure*: ComponentLot $L_7$ contains $C_2$ (for $J_2$) and $C_5$ (for $J_5$).
   - *Dynamics*: A quality hold on $L_7$ propagates to both $J_2$ and $J_5$. When $J_2$ bypasses this hold via an informal administrative override while $J_5$ complies, the execution schedules of $B_1$ and $B_2$ decouple unevenly, introducing downstream variance in $S_1$, $S_2$, and $S_3$.

3. **Tool-Contention Cascade Motif ($J_i - T - J_k - M$)**
   - *Structure*: $J_3$ acquiring $FIX-A$ at 09:00 and releasing at 11:40; $J_4$ arriving at $CNC-2$ at 09:50; $FIX-A$ required for $J_4$'s process at $CNC-2$.
   - *Dynamics*: Machine $CNC-2$ is idle from 10:05 to 10:47, but $J_4$ cannot process because $FIX-A$ is held by $J_3$ elsewhere. The machine utilization metric reflects idleness, masking the tool-starvation state of $J_4$.

### Direct vs. Inferred Edges

- **Directly Observed Edges**:
  - `(J1, requires, C1)`, `(L7, contains, C2)`, `(B1, batches, J1..J3)`, `(S1, consolidates, J1, J4)`.
  - Machine process events explicitly listing $(J_k, M_m)$.
- **Inferred Edges**:
  - Tool retention intervals: $J_3$ holding $FIX-A$ from 09:00 to 11:40 is inferred by joining the `Acquire Tool` (09:00) and `Release Tool` (11:40) events.
  - Job-to-Lot dependencies: $J_2$ and $J_5$ dependency on $L_7$ is inferred by joining `(J2, requires, C2)` and `(L7, contains, C2)`.
  - Waiting dependency edges: Edge from $J_1$ to $J_3$ representing $J_1$'s forced idle time while waiting for $J_3$ to complete prior steps before $B_1$ can start.

L7  -> [C2 (contains), C5 (contains), J2 (affects), J5 (affects)]
L8  -> [C1 (contains), C3 (contains), J1 (affects), J3 (affects)]

## 2. Quantitative delay decomposition

Using timestamps provided in the object-centric logs, we decompose observed non-processing intervals into distinct, structured delay categories.

```
       Timeline of B1 / B2 / Tool / Shipment Waiting Mechanics
08:00          10:00          12:00          14:00          16:00          18:00          20:00
  |--------------|--------------|--------------|--------------|--------------|--------------|
  [J1 Ready: 08:10]============================>| (3h 55m Batch B1 Sync Wait)
  [J2 Ready: 08:25]===========================>| (3h 40m Batch B1 Sync Wait)
                 [J3 Ready: 11:55]------------->| [B1 Cure Starts: 12:05]
  [J3 Holds FIX-A: 09:00 - 11:40]==============>|
         [J4 at CNC-2: 09:50]=================>[J4 Process Starts: 11:45] (1h 50m FIX-A Wait)
                                [J4 Ready B2: 13:10]=========>| (1h 25m RACK-7 Cleaning Wait)
                                               [RACK-7 Ready: 14:35]
                                                       [J5 Ready: 14:40]->[B2 Starts: 14:50]
  [J1 Packed: 13:30]=======================================================>[S1 Dispatch: 19:25] 
                                                                              (5h 55m Consolidation Wait)
```

### Calculation 1: Batch B1 Synchronization Waiting for J1 and J2
* **Observed Data**:
  * J1 ready for batch at 08:10.
  * J2 ready for batch at 08:25.
  * J3 ready for batch at 11:55.
  * Batch B1 `Batch Cure` start time on OVEN-1: 12:05.
* **Formulas & Computations**:
  $$\text{Wait}_{J1} = t_{\text{start}}(B1) - t_{\text{ready}}(J1) = 12:05 - 08:10 = 3\text{ h } 55\text{ min } (235\text{ min})$$
  $$\text{Wait}_{J2} = t_{\text{start}}(B1) - t_{\text{ready}}(J2) = 12:05 - 08:25 = 3\text{ h } 40\text{ min } (220\text{ min})$$
  $$\text{Wait}_{J3} = t_{\text{start}}(B1) - t_{\text{ready}}(J3) = 12:05 - 11:55 = 10\text{ min}$$
* **Decomposition & Attribution**:
  * $J_1$ total wait = $235\text{ min}$. Pacing-job synchronization delay (waiting for $J_3$) = $11:55 - 08:10 = 225\text{ min}$. Batch setup/loading overhead = $12:05 - 11:55 = 10\text{ min}$.
  * $J_2$ total wait = $220\text{ min}$. Pacing-job synchronization delay (waiting for $J_3$) = $11:55 - 08:25 = 210\text{ min}$. Batch setup/loading overhead = $10\text{ min}$.
* **Counterfactual Assumption**: If $J_1$ and $J_2$ were processed in a single-unit or small-batch thermal apparatus immediately upon readiness (08:10 and 08:25 respectively), $J_1$ would save up to $235\text{ min}$ and $J_2$ up to $220\text{ min}$ of queue time, assuming thermal cycle time remains constant.

### Calculation 2: Fixture FIX-A Contention Delay for J4 at CNC-2
* **Observed Data**:
  * J3 acquires FIX-A at 09:00, releases FIX-A at 11:40.
  * J4 arrives at CNC-2 at 09:50.
  * CNC-2 is idle from 10:05 to 10:47.
  * J4 `Machine Process` starts at 11:45 using CNC-2 and FIX-A.
* **Formulas & Computations**:
  $$\text{Total Idle Time}_{J4\text{ at }CNC-2} = t_{\text{start}}(J4) - t_{\text{arrival}}(J4) = 11:45 - 09:50 = 1\text{ h } 55\text{ min } (115\text{ min})$$
  $$\text{Tool Unavailability Interval} = t_{\text{release}}(\text{FIX-A}) - t_{\text{arrival}}(J4) = 11:40 - 09:50 = 1\text{ h } 50\text{ min } (110\text{ min})$$
  $$\text{Post-Release Setup Overhead} = t_{\text{start}}(J4) - t_{\text{release}}(\text{FIX-A}) = 11:45 - 11:40 = 5\text{ min}$$
* **Counterfactual Assumption**: If a second fixture (FIX-B) were available at 09:50, $J_4$ could have mounted immediately. Machine CNC-2 was available at 10:05 (after finishing its previous task). Under tool availability, $J_4$ would have started at 10:05, saving $100\text{ min}$ ($11:45 - 10:05$) of delay.

### Calculation 3: Shipment S1 Consolidation Delay Imposed on J1
* **Observed Data**:
  * J1 packing completed at 13:30.
  * J4 packing completed at 19:10.
  * Shipment S1 dispatch time: 19:25.
* **Formulas & Computations**:
  $$\text{Total Dwell Time}_{J1\text{ in Shipping}} = t_{\text{dispatch}}(S1) - t_{\text{packed}}(J1) = 19:25 - 13:30 = 5\text{ h } 55\text{ min } (355\text{ min})$$
  $$\text{Consolidation Waiting (Waiting for J4)} = t_{\text{packed}}(J4) - t_{\text{packed}}(J1) = 19:10 - 13:30 = 5\text{ h } 40\text{ min } (340\text{ min})$$
  $$\text{Staging and Load Time} = t_{\text{dispatch}}(S1) - t_{\text{packed}}(J4) = 19:25 - 19:10 = 15\text{ min}$$
* **Counterfactual Assumption**: If S1 operated under a "dispatch upon packing + 30 min window" policy (similar to S2/S3 which dispatched 25 min and 35 min after final packing), $J_1$ would have dispatched at $14:00$, saving $325\text{ min}$ of warehouse dwell time.

### Calculation 4: Calibration Tool CAL-3 Delay Imposed on J6
* **Observed Data**:
  * J5 ready for final test at 16:00.
  * J6 ready for final test at 16:05.
  * J5 testing on TEST-1: 16:10 to 16:35.
  * CAL-3 recalibration interval: 16:35 to 17:20 ($45\text{ min}$).
  * J6 testing on TEST-1: 17:25 to 17:50.
* **Formulas & Computations**:
  $$\text{Total Waiting Time}_{J6} = t_{\text{start}}(J6) - t_{\text{ready}}(J6) = 17:25 - 16:05 = 1\text{ h } 20\text{ min } (80\text{ min})$$
  $$\text{Queue Wait behind J5} = t_{\text{end}}(J5) - t_{\text{ready}}(J6) = 16:35 - 16:05 = 30\text{ min}$$
  $$\text{Recalibration Wait (CAL-3)} = t_{\text{end}}(\text{Calib}) - t_{\text{end}}(J5) = 17:20 - 16:35 = 45\text{ min}$$
  $$\text{Handling / Mount Overhead} = t_{\text{start}}(J6) - t_{\text{end}}(\text{Calib}) = 17:25 - 17:20 = 5\text{ min}$$
* **Counterfactual Assumption**: If CAL-3 recalibration was performed prior to 16:00 or deferred until after J6 testing, J6 would have started testing immediately after J5 at 16:35, reducing J6's wait from $80\text{ min}$ to $30\text{ min}$ (saving $45\text{ min}$ associated with recalibration).

### Calculation 5: Tool Cleaning vs. Job Readiness Delay for Batch B2
* **Observed Data**:
  * J4 ready for batch B2 at 13:10.
  * J5 ready for batch B2 at 14:40 (delayed by L7 release at 13:50 + intermediate operations).
  * OVEN-1 idle from 12:55 to 14:50.
  * RACK-7 unavailable ("cleaning/quarantine") from 12:55 to 14:35.
  * B2 start time: 14:50.
* **Formulas & Computations**:
  $$\text{Total Wait}_{J4\text{ in B2}} = t_{\text{start}}(B2) - t_{\text{ready}}(J4) = 14:50 - 13:10 = 1\text{ h } 40\text{ min } (100\text{ min})$$
  $$\text{Tool-Blocked Wait (RACK-7 Cleaning)} = t_{\text{ready}}(\text{RACK-7}) - t_{\text{ready}}(J4) = 14:35 - 13:10 = 1\text{ h } 25\text{ min } (85\text{ min})$$
  $$\text{Job-Synchronization Wait (Awaiting J5)} = t_{\text{ready}}(J5) - t_{\text{ready}}(\text{RACK-7}) = 14:40 - 14:35 = 5\text{ min}$$
  $$\text{Batch Loading Overhead} = t_{\text{start}}(B2) - t_{\text{ready}}(J5) = 14:50 - 14:40 = 10\text{ min}$$
* **Counterfactual Assumption**: If a secondary batch rack (RACK-8) were available, RACK-7 cleaning would not have blocked B2. However, $J_4$ would still have waited until $J_5$ became ready at 14:40 (due to batch size requirements). Thus, tool availability alone saves $85\text{ min}$ only if single-job batching is permitted; under strict 2-job batch policy, tool availability saves $0\text{ min}$ net delay because $J_5$ was not ready until 14:40.

### Explaining the Paradox: Low Machine Utilization vs. Long Job Waiting

Traditional process mining assumes that long wait times correlate directly with high resource utilization (queuing theory / Kingman's formula). In this facility, machines exhibit **low to moderate utilization (44% to 58%)**, yet jobs experience severe idle delays.

```text
TRADITIONAL QUEUING MODEL (Single-Object Perspective):
High Arrival Rate / High Utilization ----> Queue Build-up ----> Long Job Waiting Time

OBJECT-CENTRIC MULTI-RESOURCE REALITY:
[ Job Ready ] --+--> Waiting for Co-Batch Jobs (J1, J2 waiting for J3) --------+
                +--> Waiting for Shared Tool (J4 waiting for FIX-A) ------------+--> [ Machine Idle ]
                +--> Waiting for Tool Cleaning (J4 waiting for RACK-7) --------+    (Utilization: 44-58%)
                +--> Waiting for Quality Release (J5 waiting for Lot L7) ------+
```

This paradox occurs due to **Multi-Resource Synchronization Constraints**:
1. **Tool Starvation**: Machine CNC-2 is idle (10:05–10:47), but $J_4$ cannot be processed because tool $FIX-A$ is locked by $J_3$ on another process. The machine is available, but the process cannot start.
2. **Batch Pacing Starvation**: Machine OVEN-1 is idle (12:55–14:50), but cannot run because $J_4$ is waiting for $RACK-7$ cleaning, while $J_5$ is held by Lot $L_7$ quarantine.
3. **Information Loss via Flattening**: Flattening projects multi-entity relationships onto a single entity axis. When flattening on `Job`, the context of co-dependent jobs is erased. When flattening on `Machine`, the wait time of jobs staged in the buffer is omitted, projecting an illusion of operational efficiency alongside random delay.

## 5. Object-lifecycle evidence

### Narrative 1: Thermal Batching & Tool Sanitization Barrier
*Affected Object Types: ComponentLot, Job, Tool, Batch, Machine, Shipment*

```
[ Lot L7 Quarantined (10:20) ] 
       |
       +---> [ J2 Override: Enters B1 Buffer ] 
       |            |
       |            +---> [ J1/J2 Wait in B1 Buffer for J3 (08:10-12:05) ]
       |                               |
       |                               +---> [ B1 Cures in OVEN-1 with RACK-7 (12:05-12:55) ]
       |                                              |
       |                                              +---> [ RACK-7 Cleaning Quarantine (12:55-14:35) ]
       |                                                           |
       +---> [ J5 Blocked until L7 Release (13:50) ]               |
                    |                                              |
                    +-------------------> [ B2 Delayed until J5 & RACK-7 Ready (14:50) ]
```

1. **Temporal Precedence**:
   - 10:20 - ComponentLot $L_7$ enters `Quarantine Lot` status (affecting $C_2$ for $J_2$ and $C_5$ for $J_5$).
   - 12:05 - $J_2$ enters Batch $B_1$ on $OVEN-1$ using $RACK-7$ despite $L_7$ quarantine.
   - 12:55 - Batch $B_1$ completes curing; $RACK-7$ enters `cleaning/quarantine` until 14:35.
   - 13:50 - $L_7$ is officially released via `Release Lot`.
   - 14:40 - $J_5$ becomes ready for Batch $B_2$.
   - 14:50 - Batch $B_2$ starts curing on $OVEN-1$ using $RACK-7$.
2. **Resource Feasibility**:
   - $OVEN-1$ was thermally available at 12:55, but $B_2$ could not execute because $RACK-7$ was locked in sanitization until 14:35.
3. **Policy Constraints**:
   - Minimum batch size policy requires 2 jobs for $B_2$ ($J_4$ and $J_5$). $J_4$ was ready at 13:10 but could not run alone.
4. **Causal Speculation**:
   - $J_2$'s unauthorized supervisor override allowed $B_1$ to run on schedule, but forced $J_5$ to bear the full duration of $L_7$'s quality hold, directly pushing $B_2$'s execution into the late afternoon.

### Narrative 2: Cross-Machine Fixture Contention & Downstream Delay
*Affected Object Types: Job, Tool, Machine, Shipment*

```
[ J3 Locks FIX-A (09:00-11:40) ] 
       |
       +---> [ J4 Arrives CNC-2 (09:50) ] 
                   |
                   +---> [ CNC-2 Idle (10:05-10:47) - FIX-A Unavailable ]
                               |
                               +---> [ J4 Process Starts (11:45) post FIX-A Release ]
                                           |
                                           +---> [ J4 Delayed to Packing (19:10) ]
                                                       |
                                                       +---> [ S1 Dispatch Held for J4 (13:30-19:25) ]
```

1. **Temporal Precedence**:
   - 09:00 - $J_3$ acquires tool $FIX-A$.
   - 09:50 - $J_4$ arrives at $CNC-2$ buffer.
   - 10:05 - $CNC-2$ finishes prior operation and becomes idle.
   - 11:40 - $J_3$ releases $FIX-A$.
   - 11:45 - $J_4$ acquires $FIX-A$ and begins `Machine Process` on $CNC-2$.
   - 13:30 - $J_1$ completes packing and enters Shipment $S_1$ staging.
   - 19:10 - $J_4$ completes packing.
   - 19:25 - Shipment $S_1$ dispatches.
2. **Resource Feasibility**:
   - $CNC-2$ had physical capacity to execute $J_4$ at 10:05, but lacked required fixture $FIX-A$.
3. **Policy Constraints**:
   - Consolidation policy for $S_1$ dictates that no partial shipments are dispatched; $J_1$ must wait for $J_4$.
4. **Causal Speculation**:
   - The $110\text{ min}$ tool contention delay experienced by $J_4$ at $CNC-2$ directly shifted $J_4$'s completion to 19:10, which in turn locked $J_1$ in warehouse staging for nearly 6 hours.

### Narrative 3: Sequential Testing & Calibration Contention
*Affected Object Types: Job, Machine, Tool, Shipment*

```
[ J5 & J6 Ready for Test (16:00 / 16:05) ]
       |
       +---> [ J5 Tests on TEST-1 with CAL-3 (16:10-16:35) ]
                   |
                   +---> [ CAL-3 Recalibration Cycle (16:35-17:20) ]
                               |
                               +---> [ J6 Tests on TEST-1 with CAL-3 (17:25-17:50) ]
                                           |
                                           +---> [ S3 Staging & Dispatch (18:25) ]
```

1. **Temporal Precedence**:
   - 16:00 - $J_5$ ready for final test.
   - 16:05 - $J_6$ ready for final test.
   - 16:10–16:35 - $J_5$ executes `Final Test` on $TEST-1$ using tool $CAL-3$.
   - 16:35–17:20 - Tool $CAL-3$ undergoes scheduled recalibration.

### Intervention Details

#### Intervention 1: Dynamic Thermal Batch Sizing (Addressing Synchronization)
* **Target Mechanism**: Batch synchronization waiting in $B_1$ and $B_2$.
* **Expected Benefit**: Eliminates pacing-job wait time. $J_1$ and $J_2$ save up to 235 minutes.
* **Jobs / Objects Helped**: $J_1, J_2, J_4$.
* **Jobs / Objects Potentially Harmed**: OVEN-1 thermal efficiency; overall energy cost per job increases.
* **New Cost or Risk**: Increased energy consumption; risk of uneven thermal distribution in half-empty ovens.
* **Perverse Incentive Metric**: "Oven Runs per Day" or "Batch Capacity Utilization %" (drivers will force sub-optimal holds to maximize batch size).
* **Object-Centric Evaluation Design**: Track $E_{B} = t_{\text{start}}(B) - \min_{j \in B}(t_{\text{ready}}(j))$ before and after policy change across all $Batch$ instances in OCEL.

#### Intervention 2: Duplicate Tooling & Off-Peak Calibration (Addressing Tools)
* **Target Mechanism**: Shared tool contention ($FIX-A$) and mid-shift calibration ($CAL-3$).
* **Expected Benefit**: Reduces $J_4$ waiting time by 110 minutes; reduces $J_6$ waiting time by 45 minutes.
* **Jobs / Objects Helped**: $J_4, J_6, CNC-2, TEST-1$.
* **Jobs / Objects Potentially Harmed**: Maintenance budget; tool storage footprint.
* **New Cost or Risk**: Tool acquisition costs ($FIX-B$ investment); risk of uncalibrated secondary tools if maintenance routines fail.
* **Perverse Incentive Metric**: "Tool Utilization %" (having redundant tools lowers average utilization per tool instance).
* **Object-Centric Evaluation Design**: Measure `Tool_Hold_Wait_Time` by computing the difference between `Machine_Buffer_Arrival` and `Tool_Acquire_Event` for all $(Job, Tool)$ tuples.

#### Intervention 3: Threshold-Based Partial Shipment Dispatch (Addressing Consolidation)
* **Target Mechanism**: Shipping consolidation delays ($S_1$).
* **Expected Benefit**: Prevents completed jobs from waiting for incomplete partner jobs. $J_1$ saves up to 325 minutes of warehouse staging wait.
* **Jobs / Objects Helped**: $J_1$, warehouse buffer space.
* **Jobs / Objects Potentially Harmed**: Logistics budget; partial freight costs; receiving logistics at customer site.
* **New Cost or Risk**: Exponentially higher Less-Than-Truckload (LTL) shipping costs; fragmented deliveries to customers.
* **Perverse Incentive Metric**: "On-Time Shipment %" calculated per shipment object rather than per job object.
* **Object-Centric Evaluation Design**: Evaluate $D_{\text{stage}} = t_{\text{dispatch}}(S) - t_{\text{packed}}(J)$ for all $Job \rightarrow Shipment$ relationships.

#### Intervention 4: Explicit Object-Centric Event Logging (Addressing Data Integration)
* **Target Mechanism**: Missing `Wait for Tool`, missing `Lot Quarantine` linkages, and implicit state transitions.
* **Expected Benefit**: Provides complete operational visibility; eliminates false diagnostic conclusions from standard flattenings.
* **Jobs / Objects Helped**: Production planners, process mining analysts, automated scheduling algorithms.
* **Jobs / Objects Potentially Harmed**: Data pipeline performance; database storage footprint.
* **New Cost or Risk**: Increased IoT instrumentation costs; potential latency in log ingestion pipelines.
* **Perverse Incentive Metric**: "Log Ingestion Rate" or "Database Storage Overhead."
* **Object-Centric Evaluation Design**: Calculate the percentage of operational wait intervals explained by explicit events in the OCEL graph ($Coverage \% \rightarrow 100\%$).

#### Intervention 5: Standardized Digital Exception Handling for Lot Quarantine
* **Target Mechanism**: Informal supervisor overrides bypassing quarantine ($L_7$).
* **Expected Benefit**: Prevents schedule skew between co-lot components ($J_2$ vs $J_5$).
* **Jobs / Objects Helped**: $J_5, B_2$, Quality Compliance.
* **Jobs / Objects Potentially Harmed**: Fast-track jobs that previously benefited from ad-hoc overrides ($J_2$).
* **New Cost or Risk**: Formal administrative friction slowing down emergency overrides; risk of quality escapes if overrides are normalized.
* **Perverse Incentive Metric**: "Audit Non-Compliance Incidents" (leads operators to bypass system logging entirely).
* **Object-Centric Evaluation Design**: Quantify the variance in throughput time between jobs linked to the same ComponentLot object ($Var(T_{J} | L_k)$).

## 7. PM4Py analysis outline

```python
import pm4py
import pandas as pd
import networkx as nx

def analyze_object_centric_coupling(ocel_path: str):
    """
    Executes object-centric process mining analysis on OCEL data to detect
    hidden coupling, tool contention, and multi-resource bottlenecks
    without relying on machine event gap inference.
    """
    # 1. Load Object-Centric Event Log (OCEL 2.0 format)
    ocel = pm4py.read_ocel(ocel_path)
    
    print("=== 1. OBJECT INTERACTION SUMMARY ===")
    # Extract object interaction summary
    interaction_summary = pm4py.ocel_objects_interactions_summary(ocel)
    print(interaction_summary)
    
    print("\n=== 2. DISCOVER OBJECTS GRAPH & TYPE TOPOLOGY ===")
    # Discover object graph and object type graph (OTG)
    obj_graph = pm4py.discover_objects_graph(ocel)
    otg = pm4py.discover_otg(ocel)
    print("Object Type Graph Edges:", otg)
    
    print("\n=== 3. EVENT-TYPE TO OBJECT-TYPE (ETOT) MATRIX ===")
    # Uncover how activities bind multiple object types simultaneously
    etot = pm4py.discover_etot(ocel)
    print(etot)
    
    print("\n=== 4. OBJECT-CENTRIC DIRECTLY-FOLLOWS GRAPH (OC-DFG) ===")
    # Compute OC-DFG across all object types
    ocdfg = pm4py.discover_ocdfg(ocel)
    
    print("\n=== 5. COMPARE FREQUENCY METRICS Across VIEWPOINTS ===")
    # Metrics comparison: Event Frequency vs Object Interaction Frequency
    # Metric A: Job Flattened Performance DFG
    job_flattened = pm4py.ocel_flattening(ocel, object_type="Job")
    job_perf_dfg, start_act, end_act = pm4py.discover_performance_dfg(job_flattened)
    
    # Metric B: Machine Flattened Performance DFG
    machine_flattened = pm4py.ocel_flattening(ocel, object_type="Machine")
    machine_perf_dfg, m_start, m_end = pm4py.discover_performance_dfg(machine_flattened)
    
    print(f"Job Viewpoint Edge Count: {len(job_perf_dfg)}")
    print(f"Machine Viewpoint Edge Count: {len(machine_perf_dfg)}")
    
    print("\n=== 6. EXTRACT OCEL FEATURES FOR WAITING TIME PREDICTION ===")
    # Feature extraction capturing multi-object relationships
    ocel_features = pm4py.extract_ocel_features(ocel)
    print("Extracted Feature Vectors Head:")
    print(ocel_features.head())
    
    print("\n=== 7. DETECT RESOURCE CONTENTION VIA NETWORKX CONVERSION ===")
    # Convert OCEL object graph to NetworkX for structural metric calculation
    nx_graph = pm4py.convert_ocel_to_networkx(ocel)
    
    # Measure node degree centrality to spot bottleneck resource objects
    centrality = nx.degree_centrality(nx_graph)
    sorted_centrality = sorted(centrality.items(), key=lambda x: x[1], reverse=True)
    
    print("Top Resource Objects by Coupling Centrality:")
    for obj_id, score in sorted_centrality[:10]:
        print(f"Object: {obj_id} | Centrality Score: {score:.4f}")

if __name__ == "__main__":
    # Assuming 'ocel' variable exists in environment
    try:
        analyze_object_centric_coupling("factory_process.jsonocel")
    except Exception as e:
        print(f"Execution outline ready. (Error during standalone execution: {e})")
    print(ocel)
```
