## 2. Process-model consistency checks

A concrete validation suite (as CI gates on the feature/explanation pipeline, not a one-off review). Each check is labelled, with its role and its limits.

**T0 — Label-clock definition test (precondition).** Pin down the target: is the 10day target in calendar or business days, and does it run to the *first* or the *final* `Settlement Decision Recorded`, and do `Withdrawn` cases count as breach or as censored? Until this is fixed, `calendar_week` (holidays), `appeal_seen_anywhere` (extra decision cycles) and `elapsed_since_registration_at_t0` (slack arithmetic) cannot be interpreted. *Limitation:* this is a business decision, not a statistical one; it must be versioned alongside the model.

**T1 — Prefix-time availability (point-in-time assertion).** Every feature carries contract metadata: `source_events[]`, `window = [start, t0]`, `as_of_semantics`, `mutable (bool)`, `valid_from/valid_to`. The build fails if a feature has no event or SCD row with `event_time  t0` that reproduces its value. Implement as an as-of (bitemporal) join in the feature store with `ingest_time` vs `event_time` kept distinct, and a **metamorphic "prefix-invariance" test**: evaluate every feature on the trace truncated at `t0` and on the full trace; `F(prefix) == F(full)` must hold. Any feature that changes is complete-trace leakage by construction (`total_case_duration_hours`, `appeal_seen_anywhere`, `full_trace_variant_id`, `num_document_requests_total`, `final_decision`, `last_resource_role` all fail this test immediately). *Limitation:* the test detects leakage but not *meaning*; a feature can pass and still be a proxy or a drift indicator.

**T2 — Activity-order feasibility (alignment-based conformance).** Align each trace to the normative process model (Petri net / BPMN with the data-aware extensions below) and record fitness plus deviation types; additionally run declarative `Declare`-style constraints, since the normative model is partly conditional and partly declarative:
- `Precedence(SettlementDecision{Partial|Deny}, Appeal)` — appeal only after Partial/Deny;
- `Precedence(DamageAssessment, SettlementDecision)` (with the fast-track exemption: `DamageAssessment` may occur without an evidence cycle, but never after `SettlementDecision`);
- `Precedence(DocumentsRequested, DocumentsReceived)` and `Precedence(DocumentsReceived, DocumentsValidated)`;
- terminality of `Claim Closed`: `NotChainSuccession(ClaimClosed, a)` for all `a` except an explicit `Claim Reopened`/amendment event;
- `CoExistence(Appeal, SettlementDecision{2})` — see T6.
Failures are reported as **process-infeasible feature/pattern**. *Limitations:* alignment cost grows with trace length and deviation count; alignments against an informal model can be misleading (one deviation can be aligned many ways); the model must be **semantically versioned** and the fast-track variant must be modelled as a legitimate alternative, not forced onto a single happy path; coarse labels under-discriminate (see T6).

**T3 — Same-timestamp ambiguity.** For every consecutive pair `(e_i, e_{i+1})` with identical `(case_id, timestamp)`: require a reliable sequence index (event id / append counter / process-tracker step number). If missing, mark the pair **order-unknown** and (i) forbid both linear orders from producing features or DFG/n-gram patterns, (ii) represent the pair as a partial order (pomset) and count an edge only if it holds in **all** linear extensions, (iii) run a **permutation-sensitivity test**: score the case under both orderings; any feature/explanation whose value or sign flips is order-fragile and must be quarantined. Case Z's `Claim Closed`/`Damage Assessment Completed` pair is the canonical failure and its +0.18/+0.21 contribution must be treated as an ordering artifact, not evidence. *Limitation:* missing indices cannot be recovered statistically; also distinguish "same instant" (true simultaneity) from "coarse timestamp resolution" (e.g. second-level truncation), which needs a different remedy (higher-resolution capture).

**T4 — Complete-trace usage audit.** Beyond T1, statically scan feature SQL/aggregation code for unbounded windows (`GROUP BY case_id` with no `WHERE event_time < :t0`), `MAX`/`LAST` over the case, and `whole-case` flags. Require a signed lineage attestation per feature. Include HR-type joins (employee experience) with as-of semantics at **event** date. This is what catches `final_handler_team`, `last_resource_role`, `risk_score_current`, `same_day_document_count_snapshot`.

**T5 — Enablement classification at `t0` (prefix-aware explanation linting).** Given the prefix and the constraint set, compute three sets:
- **ENABLED** at `t0` (immediately after `Coverage Check Completed`): `Damage Assessment Completed` (fast track), `Documents Requested`, `Fraud Investigation Opened`;
- **FUTURE-POSSIBLE**: `Documents Received`, `Documents Validated`, a further `Documents Requested`, `Damage Assessment Completed` after an evidence cycle, `Settlement Decision Recorded`, `Claim Closed`, and `Appeal` **conditionally** (only if the first decision is Partial/Deny), and hence a second `Settlement Decision Recorded`;
- **IMPOSSIBLE-as-observed at `t0`**: anything asserted to have *already* happened outside the prefix — `appeal_seen_anywhere = 1`, `final_decision = Partial`, `last_resource_role = SIU`, the full-trace variant value in Case Y, and the `Claim Closed -> Damage Assessment Completed` pattern.
An explanation linter rejects any driver that asserts an IMPOSSIBLE-as-observed activity. Distinguish carefully: referring to a FUTURE-POSSIBLE activity is only allowed as an explicitly labelled risk statement ("a fraud trigger recorded at `t0` is associated with longer handling"), never as a fact about the case. *Limitation:* enablement depends on the constraint model's fidelity; a permissive model will under-flag (e.g. `Documents Received` would look "enabled" if the `Documents Requested` precondition is not encoded).

**T6 — Repeated `Settlement Decision Recorded` semantics.** Because the activity label is coarse, encode a data-aware refinement `SettlementDecision{initial | reconsideration}` and validate: (i) at most 2 occurrences per case; (ii) if 2, exactly one `Appeal` strictly between them and the first decision's outcome  {Partial, Deny}; (iii) `NotSuccession(SettlementDecision, SettlementDecision)` **without** an intervening `Appeal` (catches duplicated ETL rows / double-booking); (iv) dedupe on `(case_id, activity, outcome, timestamp, sequence_index)`; (v) `Withdrawn` and `Deny`/`Partial` must be mutually exclusive outcomes on the same decision record. Applied to the sequence explainer: the edge `Appeal -> Settlement Decision Recorded` **passes** (target is decision #2, a legitimate reconsideration) and must be preserved as legal history — the exact opposite treatment from the `Claim Closed -> Damage Assessment Completed` edge, which fails T2 and T3. *Limitation:* a rare but legal pattern (e.g. a withdrawn-then-reopened claim) may be wrongly flagged; a frequent pattern is not thereby legal — see below.

**T7 — DFG/footprint usage policy.** DFG edges and directly-follows footprints are **descriptive statistics of the log, not normative rules**. A frequent edge can be a systematic data error (a late-arriving ETL batch producing `Claim Closed -> Damage Assessment Completed`) and a rare edge can be perfectly legal (`Appeal -> SettlementDecision{reconsideration}` in a small share of cases). Therefore: DFG/footprint may generate *hypotheses* and drift alarms; only T2/T3/T6 constraints may certify or reject a pattern. Conversely, conformance has its own limits: alignments are model-dependent, escaping-edge statistics are sensitive to label granularity, and legitimate operational variance (fast track, re-opened claims, withdrawal) must be modelled as permitted behaviour rather than punished as non-conformance.

## 3. Alternative feature interpretations

Standards used throughout (they are different bar heights and must not be conflated):
- **Predictive validity**: the feature is available at `t0` (point-in-time correct) and adds out-of-sample, out-of-time discrimination/calibration. This is a correlation standard. It licenses "is associated with / is an early indicator of", nothing more.
- **Causal interpretation**: requires an intervention, an identification strategy (exchangeability/no unmeasured confounding, positivity, consistency) and no post-treatment variables. Almost nothing here qualifies; "SHAP value  causal effect" is the default.
- **Operational actionability**: causal evidence **plus** a controllable lever plus feasibility/ethics of acting on it. A predictive feature with no lever (region) is not actionable; a lever with untested effect (staffing the queue) is not actionable either until a trial/quasi-experiment supports it.
- **Fairness review**: an orthogonal, non-negotiable gate. A feature can be perfectly predictive, temporally admissible and even causal and still be restricted or forbidden (directly or as a proxy for protected attributes), especially where it changes claimant-facing treatment.

**Class A — Defensible predictive signals (usable at `t0` as-is).**
`elapsed_since_registration_at_t0` (strongest; express as remaining SLA slack), `initial_damage_complexity` (admissible and frozen; caveat: judgement field).
*May claim:* "available at prediction time", "associated with breach risk", "adds out-of-time discrimination", and for elapsed/slack, "the remaining SLA budget is arithmetically smaller" (a definitional statement, not a discovery).
*May not claim:* "complexity causes delay" (no intervention tested), "slow-starting cases will settle slowly" (behavioural claim), or any conclusion about *why* complexity was recorded as High. Also: do not present the slack effect as an insight — it is a property of the SLA definition.

**Class B — Process-state / congestion signals (usable at `t0`, best operational content).**
`queue_length_at_t0` (±5 min tolerance), and — to be built as proper prefix features — handling-team WIP/throughput at `t0`, number of open evidence cycles at `t0` (0 in X, Y), days since last event, currently enabled-activity set, fast-track eligibility at `t0`, intake document completeness at registration.
*May claim:* "the operating state at `t0` is associated with breach risk" and "this is a workload/capacity marker"; these are the most legitimate candidates for capacity planning *indicators*.
*May not claim:* "congestion causes breach" (staffing, season, case mix and holiday regime confound it; queue length is also an outcome of prior arrivals), nor "adding handlers will prevent breach" without an experiment. Actionability requires a staffing/routing A/B test or a natural experiment (e.g. exogenous holiday closures) — then the causal and actionable standards can be met for the *queue*, not for the individual claim.

**Class C — Proxies requiring fairness/robustness review (temporally valid, restricted use).**
`claimant_region`, `claimant_channel`, `prior_claim_count_before_t0` (after repair — claimant repeat behaviour), `initial_reserve` (asset value/wealth correlate), `initial_damage_complexity` and `final_handler_team`/`employee experience` (after repair — human judgement and workforce composition).
*May claim:* predictive association, and — importantly — these features may be retained **specifically to audit for disparate impact**.
*May not claim:* anything that attributes delay to the claimant or to a group ("region is a delay driver", "brokers are slower"), any causal story about claimant characteristics, and no use in adverse claimant-facing decisions without legal basis and a documented fairness decision per feature (retain / monitoring-only / drop). Required analyses: proxy detection against protected attributes, group-wise calibration and error-rate parity, "swap-the-region" counterfactual stability, and re-testing after substituting the underlying service variables (repair-network coverage, language support, SLA tier). Deleting them wholesale is also wrong: it hides inequity and usually leaks through correlated features anyway.

**Class D — Drift/calendar proxies (admissible but regime-bound).**
`calendar_week`; variant-ID distributions (as a drift alarm, not a feature).
*May claim:* "cases opened in this period show higher breach rates" — a descriptive/monitoring statement.
*May not claim:* "week 52 is operationally worse" as a stable mechanism, and no extrapolation beyond the observed policy/holiday regime. Use for monitoring and as a regime covariate; require out-of-time replication (post-policy-change holdout) before it keeps model weight.

**Class E — Unusable (split by repairability).**
*E1 — Repairable after lineage work:* `final_handler_team` ( `team_at_t0`), `prior_claim_count_before_t0` (predicate fix + self-count test), `same_day_document_count_snapshot` ( point-in-time doc count, will collapse to ~0), `risk_score_current` ( `risk_score_as_of_t0` from version history), `initial_reserve` (attestation of "first reserve"), `employee experience` (as-of event date), and the order of the same-timestamp `Claim Closed`/`Damage Assessment Completed` pair (sequence index or partial order).
*May claim (after repair):* only "as-of-`t0` value is associated with breach", plus, for `risk_score_as_of_t0` and `team_at_t0`, "a trigger/assignment recorded before `t0` is associated with longer handling".
*May not claim (even after repair):* that any of these is a cause, and — for `risk_score`/`team_at_t0` — that acting on them (escalating, reassigning) improves timeliness, absent a trial.
*E2 — Irreparable at `t0` (must be dropped from `t0` models and moved to stage models):* `total_case_duration_hours`, `appeal_seen_anywhere`, `full_trace_variant_id`, `num_document_requests_total`, `final_decision`, `last_resource_role`, and the post-`t0` sequence patterns (`Documents Requested -> Documents Received`, `Coverage Check Completed -> Fraud Investigation Opened`, `Damage Assessment Completed -> Settlement Decision Recorded`, `Appeal -> Settlement Decision Recorded`, `Claim Closed -> Damage Assessment Completed`). ## 5. Recommendations for explanation validation

**P0 — Stop the bleeding (immediate, blocking).**
1. **Withdraw `t0` explanations built on the current feature set** and freeze claimant-facing use. Remove the six irreparable leaks (`total_case_duration_hours`, `appeal_seen_anywhere`, `full_trace_variant_id`, `num_document_requests_total`, `final_decision`, `last_resource_role`) and all five post-`t0` sequence patterns from `t0` models. Re-fit, re-calibrate, and **report the performance drop honestly** — quantify "how much of the reported 0.44/0.35/… importance was future information" as the headline finding of this audit.
2. **Prefix-only recomputation pipeline.** Materialize each case's feature vector *as of `t0`* from the raw log, and wire the **prefix-invariance metamorphic test** (§2 T1) into CI as a hard build failure: any feature whose value changes when the trace is truncated at `t0` is automatically disqualified.
3. **Label-clock definition freeze (T0)**: business vs. calendar days, clock end at first vs. final decision, treatment of `Withdrawn` — versioned alongside the model, because it determines the interpretation of slack, appeals and holiday weeks.

**P1 — Fix the data substrate (1–2 weeks).**
4. **Feature-store design with point-in-time correctness.** Bitemporal storage (`event_time` and `ingest_time` kept distinct); every feature carries a machine-readable contract: `source_events`, `window = [start, t0]`, `as_of_semantics`, `mutable`, `valid_from/valid_to`, `admissible_at_stage`, `fairness_class`, `owner`, `attested_on`. Ban unbounded per-case aggregates in the transformation layer (enforced by linting of the SQL/aggregation DSL), require `as_of_ts` on every read, and version every definition with semantic versioning so that a change in meaning is a new feature, not a silent overwrite.
5. **Historical feature timestamps (SCD Type 2) and as-of joins** for every mutable/derived field: `team_at_t0` (assignment history), `risk_score_as_of_t0` (score version history), `initial_reserve` (first reserve with `set_at`), `experience_as_of_t0` (as-of **event** date, not extraction date), `documents_received_upto_t0` (intraday snapshots instead of a 23:00 nightly refresh, or event-level counting), plus corrected `prior_claim_count` (`claim_created_at < t0 AND claim_id <> current`) with self-count, boundary and monotonicity regression tests. Where history does not exist, the feature is dropped — never approximated from today's value.
6. **Process-conformance test suite as a permanent gate**: the `Declare`-style constraints and data-aware `SettlementDecision{initial|reconsideration}` refinement of §2 (T2, T3, T6) run nightly against the log; per-case fitness and deviation types stored so any feature/pattern can be certified against the normative model. DFG/footprint statistics are retained **only** as descriptive drift alarms (T7). Add the ambiguity handling explicitly: same-timestamp pairs without a sequence index enter a quarantine bucket and are excluded from order-derived features, and a permutation-sensitivity test flags order-fragile explanations (this is exactly what would have caught Case Z).

**P2 — Restore trust in the model and its explanations (2–6 weeks).**
7. **Calibration and utility after feature removal.** Re-measure discrimination (PR-AUC/ROC-AUC), Brier score, calibration curves and ECE overall **and per segment** (region, channel, complexity, week, reserve band), against honest baselines (elapsed/slack-only model; a survival/time-to-event model is a good reference for a deadline target). Publish the "leakage budget": the delta in each metric between the contaminated and the clean model, and residual calibration drift per segment — removal of `claimant_region`-class features is not automatic and can hurt minority-group calibration, which is a reason to review, not a reason to ignore.
8. **Explanation stability testing.** Re-run local explanations across bootstrap resamples, random seeds, and both permitted orderings of ambiguous same-timestamp events; report per-driver sign stability and rank stability, and suppress drivers whose sign flips (Case Z's top driver would be suppressed). Impose **explanation completeness**: attributions must reconcile to `f(x)  E[f(x)]` with an unattributed `other` bucket  5% and a downloadable full list; the base value is disclosed separately. Run the §2 T5 enablement linter over every generated narrative before release.
9. **Proxy and fairness analysis.** Correlation/association tests of `claimant_region`, `claimant_channel`, `prior_claim_count`, `initial_reserve`, `initial_damage_complexity`, `team_at_t0` and `experience` against protected attributes (including "4%-rule"-style removal tests); group-wise calibration and error-rate parity; counterfactual "swap region/channel" stability tests; re-test each proxy after substituting the underlying service variable (repair-network coverage, language support, SLA tier). Output is a **documented decision per feature** — retain / monitoring-only / excluded from decisions — plus a mandated fairness review board sign-off, since these models are high-risk in an insurance context (EU AI Act) and engage GDPR Art. 22 / non-discrimination obligations. Language policy for all user-facing explanations: associative verbs only ("associated with", "an early indicator of"); causal verbs ("causes", "drives", "determines") are blocked by template lint unless a documented identification study exists.
10. **Drift and schema monitoring.** (a) Schema drift: new/renamed event labels, changed coarse-label semantics (a second `Settlement Decision Recorded` must remain legal after appeal), timestamp resolution/precision changes, unit changes (hours vs days). (b) Process drift: variant-distribution shift, DFG-edge churn, **constraint-violation rate** as the primary conformance alarm, rate of same-timestamp/unindexed pairs, rate of post-closure activity. (c) Feature/label drift: PSI/KS per feature, calibration error per calendar week, regime flags for policy changes and holiday periods. (d) **Leakage sentinels**: deliberately retain one known-leaked feature in a shadow scoring job and alarm if its importance or any rebuilt feature's prefix-invariance test starts to fail again — lineage defects recur silently after upstream refactors.

**P3 — Standing governance (ongoing).**
11. **Lineage attestation and change control**: every feature carries a signed attestation ("reproducible from data with `event_time  t0`") refreshed on any upstream schema/SQL change (contract tests on the upstream queries would have caught `prior_claim_count`'s `<=` predicate); an explanation review board signs off new drivers before they appear in claimant- or handler-facing text; stage-appropriate models (`t0` model, mid-process model, post-decision appeal model) are registered separately so that legitimately later information (`Appeal -> Settlement Decision Recorded`, evidence-cycle turnaround) is used where it is legal instead of being smuggled into the early model.
