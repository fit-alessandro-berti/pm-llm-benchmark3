## 1. Analytical assumptions

**Case notion.** A "case" is not a discovered fact but a modeling commitment: the object whose identifier defines a trace when the OCEL is projected onto one object type. Under the stated convention, an event is copied into every case of the lead type it is *directly* related to in the E2O table (e.g., e16 lands in the O1-, O2-, and O3-cases when flattening on Order). I treat the flattened trace as a *viewpoint*, never as ground truth about the process.

**Convergence and divergence.** I use the standard object-centric definitions:
- **Convergence**: multiple objects of the same type are related to one event, so flattening either duplicates the event across their cases or blurs the objects together in aggregates. Here, for Order: e13, e14, e16, e17, e19, e22, e24, e25 (two or three orders each). For Item: e13, e14, e16, e17, e24, e27.
- **Divergence**: one object's lifecycle fragments across several cases when flattening on a *different* type. Example: O1's story splits across I11/I12 (Item view) and P1/P2 (Package view); Create Order (e01) and Close Order (e28) appear in neither.

**Copied shared events = both evidence and duplication.** A copy of e16 in the O2-case is genuine evidence that O2 participated in a consolidated dispatch, and simultaneously an inflation of "Dispatch" frequency if summed naively. I therefore never delete them; I discount them in aggregated metrics and elevate them in object-centric views.

**Permitted transformations.** (T1) Qualifier-aware relabeling: using the supplied O2O qualifiers, rename e22 to "Record Partial Payment" and e25 to "Record Completing Payment" — this uses given labels, invents nothing. (T2) Explicit propagation of E2O relations through O2O links (e.g., attaching e28 to I11 via O1 contains I11), only in a clearly flagged derivative log, never mixed with direct-E2O results. (T3) Weighting each copied event by 1/k (k = number of lead-type objects related) for sensitivity analysis. Prohibited: silent propagation, deletion of shared events, invention of tie-breaking timestamps.

## 3. Concrete distortion analysis

**D1 — Packing frequency inflation (Order flattening; cross-order package #1).** e13 (Pack Package, 10:12) relates O2, O3, I21, I31, P3 and is copied into both the O2- and O3-cases. Physical pack operations number 4 (e11–e14); case-level occurrences number 6 (O1: e11, e12; O2: e13; O3: e13, e14; O4: e14) — a +50% inflation. A warehouse-capacity analysis would overstate picking effort by half. **Harmful.**

**D2 — Pseudo-replication and false rework via P4/D3 (Order flattening; cross-order package #2).** e14, e17, e27 are shared by O3 and O4, so both cases show an identical 22h45m dispatch-to-confirm transit — two "independent" observations that are one physical shipment (statistical pseudo-replication). Worse, O3's flattened trace reads …Confirm Delivery (e24, 16:00)  Record Payment (e25)  Confirm Delivery (e27, next day)…, which a DFG renders as a Confirm DeliveryRecord PaymentConfirm Delivery loop: an apparent re-delivery that is actually D3 delivering I32 jointly for O3 and O4. **Context-dependent**: informative for detecting shared-fate objects, harmful for variant/conformance analysis.

**D3 — Package flattening's consolidation blind spot (Package flattening).** P3's case (e13, e16, e24) is a clean PackDispatchConfirm trace. Nothing in the flattened log reveals that P3's pack event bound two orders or that its dispatch (e16) also carried P2 belonging to O1. The single-variant package DFG invites the conclusion "one package = one order," falsified by P3 and P4. Detectable only via E2O multiplicity, not the log. **Harmful** if used for certification-style checks.

**D4 — Consolidated delivery D2 triple-counted; phantom double dispatch (Order flattening).** e16 and e24 each relate O1, O2, O3, so D2's 4h55m transit is charged to three order flow times. O1 additionally shows Dispatch at 11:00 (e15, via D1) *and* 11:05 (e16, via D2), producing a Dispatch self-loop that reads as rework or an unplanned re-shipment when it is a planned split shipment across P1/P2. **Harmful** for order-level SLA attribution; **informative** for carrier-load analysis.

**D5 — Delivery near-singleton lifecycle (Delivery flattening).** Each delivery case has exactly two events. The discovered DFG is one edge per case; "process discovery" degenerates to computing two timestamps. Anything upstream (why did D3 take 22h45m?) is unanswerable. **Harmful** as a standalone view; **informative** as a focused transit KPI table.

**D6 — Consolidated invoicing V2 double-counted (Order flattening).** e19, e22, e25 relate O2 and O3 and are copied into both cases. Case-level counts: Issue Invoice 3 physical  4 copies; Record Payment 4 physical  6 copies. Any "payments received per order" KPI double-counts V2's money movement, and the O2/O3 pair appears financially twice as active as O1/O4 without being so. **Harmful** for revenue-cycle metrics.

**D7 — Partial-payment semantics collapse (any flattening; especially Invoice).** e22 (M2, `partially_settles` V2) and e25 (M3, `completes_settlement` V2) share the label "Record Payment." The Invoice DFG shows a Record Payment self-loop on V2, and the 20h55m open-balance window (12:40 Feb 3  09:00 Feb 4) is indistinguishable from duplicate/rework behavior. In the Order flattening this combines with e22e24 (pay before delivery confirmation) and e24e25 (confirm before final payment) to produce **bidirectional** Record PaymentConfirm Delivery edges. Fixable only via transformation T1 (qualifier-aware relabeling). **Harmful**; the qualifier information exists only at object level.

**D8 — Payment singleton lifecycles (Payment flattening).** M1–M4 each participate in exactly one event (e21, e22, e25, e26). The flattening yields four 1-event cases and an edgeless DFG — the extreme form of the "artificially short lifecycle" trap. **Harmful** as discovery input; **informative** as evidence that payments are pure bookkeeping handles, not process anchors.

**D9 — Timestamp tie destabilizes the DFG (Order flattening).** e18 (Issue Invoice, O1) and e23 (Confirm Delivery, O1) both carry 2026-02-03 12:00. The flattened trace's ordering — hence the direction of the Issue InvoiceConfirm Delivery edge — depends on an arbitrary tie-break. An OC-DFG would display them as concurrent on O1. **Context-dependent**, but any conclusion built on that edge's direction is fragile.

**D10 — Lifecycle truncation and end-marker dominance (Item/Package flattenings; contrast Order).** Create Order, Issue Invoice, Record Payment, and Close Order never touch items or packages, so those cases have no natural start/end; throughput collapses to the physical segment (I11: 2h45m). Conversely, the Order flattening reports near-identical ~26h lead times for all four orders (closes e28–e31 cluster within 10 minutes on Feb 4) — an administrative batching artifact that masks the 1h-vs-22h45m delivery variance that the Delivery view exposes. **Harmful** in both directions: truncation understates, batched closes homogenize.

**D11 — Propagation trap (derivative Item/Package logs, transformation T2).** Propagating O1's twelve events onto I11 and I12 (via `contains`) makes both item cases inherit the full order lifecycle, inflating item-level duplication from 1.5× toward ~2.4× and fabricating per-item closures. Legitimate only as a flagged derivative view. **Context-dependent.**

## 4. Traditional versus object-centric analysis portfolio

**Flattenings worth creating:**
- **Order** (primary, convergence-flagged). Answers safely: per-order milestone sequencing among directly related events; CreateClose SLA; per-order activity repetition (e.g., O2/O3's two Record Payments); bottleneck timing between order milestones. Does *not* safely answer: physical operation volumes (D1), cross-order attribution (D2, D6), or conformance via variants (all four orders form distinct variants purely from consolidation structure).
- **Invoice** (zero duplication). Safely answers: billing-to-cash duration per invoice (V1: 30 min; V2: 20h55m; V3: 21h20m), instalment detection *after* T1 relabeling. Unsafe for per-order revenue attribution (V2 bills O2+O3).
- **Delivery** (zero duplication). Safely answers: transit time per shipment, carrier comparison (D1 vs D2 vs D3). Unsafe for anything upstream of Dispatch.
- **Package** (optional, 1.2×). Pack-to-dispatch dwell per parcel. Skip for discovery.
- **Item**: per-unit handling audit only. **Payment**: never flatten; retain as an object table joined to invoices.

**Questions requiring object-centric constructs:**
- *OC-DFG*: any mixed-type question — "what happens around Dispatch?" — because the Dispatch nodes of e15/e16/e17 aggregate 3 events but 17 unique objects (4 orders, 6 items, 4 packages, 3 deliveries); convergence becomes visible instead of hidden.
- *OTG*: quantifying object-type co-occurrence (Order–Package intensity via e11–e17; Order–Invoice via e18–e26).
- *ET–OT graph*: cardinality signatures of consolidation — Dispatch touches 3 Orders, 3 Items, 2 Packages, exactly 1 Delivery; Record Payment touches 2 Orders, 1 Invoice, 1 Payment.
- *Object interactions summary*: pairwise shared-event counts identify O3 as the hub (13 events; co-occurs with O2 in e13, e16, e19, e22, e24, e25 — six shared events; with O4 in e14, e17, e27; with O1 in e16, e24).
- *Equivalent-execution clustering*: validates that duplication stems from convergence, not duplicate object records — no two objects share identical full footprints (every Add Item/Close Order is object-specific), though I21I31 and I32I41 are near-equivalent after excluding creation events.

**Reconciliation protocol.** (1) Every cross-type claim must reproduce in the OC view; flattened-only findings are scoped to "directly related events of type X." (2) Frequency conflicts resolve in favor of unique-event counts (31), with case-level counts reported alongside. (3) Sequencing conflicts (ties like e18/e23; bidirectional payment/delivery edges) resolve by returning to raw E2O timestamps and O2O qualifiers. (4) All transformations (T1–T3) are logged with provenance.

## 5. Lead-object decision

**Position B: Order as primary lead object, with explicitly mandated secondary lifecycles (Invoice, Delivery) and OC-DFG as the integrating view.**

- **Decision criteria**: (i) lifecycle coverage across phases; (ii) identifiable start/end; (iii) duplication cost; (iv) alignment with dominant business questions (order SLA, variants, cash conversion); (v) complementarity rather than redundancy with other views.
- **Strongest supporting evidence**: Order is the only type touching all eight activity types (O3 alone appears in 13 of 31 events, e03–e30); it has clean boundaries (e01–e04, e28–e31); its duplication (1.35×) is the lowest among types with full coverage and is fully attributable to eight identified shared events.
- **Strongest counterargument**: the units of physical movement and value exchange are *not* orders — P3, P4, D2, and V2 each span multiple orders, so the Order flattening systematically fabricates autonomy (four orders  four "distinct" variants; 50% packing inflation; triple-counted D2 transit). A purist would adopt C and refuse a lead object altogether.
- **Residual risk**: analysts over-trust order-level variants and frequencies; instalment semantics (D7) and the e18/e23 tie (D9) leak into conclusions unless T1 and tie-handling are enforced; the ~26h uniform lead time (D10) can be mistaken for operational stability.
- **Conditions to change the decision**: upgrade to A if future data enforces single-order packages/shipments/invoices (convergence events vanish); downgrade to C if multi-order events exceed roughly half of all events, at which point only OC-DFG/OTG reporting is defensible and flattened logs are demoted to illustrative appendices.

## 6. PM4Py analysis outline

```python
import pm4py
import pandas as pd

# ---------- 0. Inventory ----------
print(ocel)  # object types, event/object counts; expect 31 events, 20 objects

# ---------- 1. Frequencies and convergence candidates ----------
activity_freq = ocel.events["ocel:activity"].value_counts()
otype_freq = ocel.objects["ocel:otype"].value_counts()
print("Activities:\n", activity_freq, "\nObject types:\n", otype_freq)

e2o = ocel.relations.copy()
events_per_eid = e2o.groupby("ocel:eid").size().rename("n_objects")
multi_object_events = events_per_eid[events_per_eid > 1]
# Expect e13, e14, e16, e17, e19, e22, e24, e25 -> the convergence set
print("Shared (multi-object) events:\n", multi_object_events)

# ---------- 2. Flatten on all six types; quantify duplication ----------
flattenings = {}
for otype in ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]:
    flat = pm4py.ocel_flattening(ocel, otype)
    flattenings[otype] = flat
    n_rows = len(flat)
    print(f"{otype}: {n_rows} case-event rows; "
          f"duplication factor vs 31 source events = {n_rows / 31:.2f}")
# Expected: Order 42 (1.35x), Item 24 (1.5x... vs 16 item-touching events),
# Package 12, Delivery 6, Invoice 7, Payment 4 (singletons, edgeless DFG)

order_log   = flattenings["Order"]
invoice_log = flattenings["Invoice"]
delivery_log = flattenings["Delivery"]

# ---------- 3. Classic discovery on the PRIMARY lead (Order) ----------
dfg_order, sa_order, ea_order = pm4py.discover_dfg(
    order_log,
    case_id_key="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp")
# Inspect for: Dispatch self-loop (O1: e15->e16), Record Payment<->Confirm
# Delivery both directions (e22->e24 vs e24->e25), 4/4 distinct variants.

log_skeleton_order = pm4py.discover_log_skeleton(order_log, noise_threshold=0.1)
# Check 'always_before' / 'never_together' assertions against known ties
# (e18/e23 at 12:00) and copied shared events before trusting violations.

# ---------- 4. Object-centric discoveries (authoritative views) ----------
ocdfg = pm4py.discover_ocdfg(ocel)   # per-type DFGs; annotate nodes by
                                     # events vs unique objects vs total objects
otg   = pm4py.discover_otg(ocel)     # object-type interaction intensities
etot  = pm4py.discover_etot(ocel)    # event-type -> object-type cardinalities
                                     # (Dispatch: <=3 orders, <=2 packages, 1 delivery)

# ---------- 5. Pairwise object interactions (hub detection) ----------
obj_interactions = pm4py.ocel_objects_interactions_summary(ocel)
# Expect O2-O3 strongest pair (shared: e13, e16, e19, e22, e24, e25);
# O3 is the hub with 13 of 31 events.

# ---------- 6. Equivalent-execution clustering (justified by decision B) ----------
# Purpose: prove duplication arises from CONVERGENCE (shared events), not from
# duplicated object records. Expect no identical full footprints; near-equivalent
# item pairs (I21~I31, I32~I41) only after excluding creation events.
equiv_clusters = pm4py.cluster_equivalent_ocel(ocel)
print("Equivalent execution clusters:", equiv_clusters)
```

## 7. Sensitivity and validation plan

**S1 — Down-weighting copied shared events.** Recompute the Order DFG assigning weight 1/k to each copy (k = related orders: ½ for e13, e14, e17, e19, e22, e25, e27;  for e16, e24). Order-private edges (CreateAdd Item, …Close Order) keep weight 1; consolidation-heavy edges (PackDispatch via e13/e16, ConfirmPay via e24/e25) deflate. If the ranking of top edges changes materially, report both weighted and unweighted figures and treat unweighted case-level frequencies as "participation counts," not occurrence counts.

**S2 — Direct E2O versus propagated-relation variant.** Build the T2 derivative in which Item and Package cases inherit their order's events via `contains`/`packs`. Verify that item duplication explodes (from 24 rows toward ~6×12) and that the "uniform 4-step item variant" dissolves. If any conclusion survives only under propagation, mark it as transformation-dependent and exclude it from primary reporting.

**S3 — Lead-object swap.** Re-extract the headline KPIs with Invoice and Delivery as lead (variables `invoice_log`, `delivery_log`). Cash-cycle and transit figures (V2: 20h55m; D3: 22h45m) must remain stable — they are duplication-free by construction. Then check whether order-level claims (e.g., "~26h uniform lead time," "4 distinct variants") still look plausible; any claim contradicted by the swap (D10's false uniformity) is reclassified as a flattening artifact.

**S4 — OC-DFG metric comparison.** Annotate every OC-DFG node/edge with (a) event count, (b) unique-object count, (c) total-object mentions. At Dispatch the three metrics read 3 events / 17 unique objects / 19 mentions — materially different stories about the same node. If a node's rank in the process changes across metrics, the finding is metric-sensitive and must be reported with all three values.

**S5 — Timestamp-tie robustness.** Permute the ordering of e18/e23 (both 12:00, O1) across runs and re-discover the Order DFG. Any edge whose direction or existence flips (Issue InvoiceConfirm Delivery) is declared unstable and excluded from causal claims.

**S6 — Leave-the-hub-out.** Filter out O3-involving copies and recompute duplication: O3 participates in 13 events, five of them multi-order (e13, e14, e16, e17, e27) plus the shared financial trio (e19, e22, e24, e25). If convergence metrics collapse without O3, the Order flattening's distortions are concentrated in one hub object — a targeted finding that should accompany any order-level report, and a warning that sample growth through more multi-order consolidations will scale distortion super-linearly.
