## 1. Target definition

**Primary target formulation:**
*Time-to-default after activation with right censoring*
- **Prediction target:** Time from Account Activated to first Default Recorded (or censoring)
- **Prediction time:** After the first few events of the application process (e.g., after Credit Review decision)
- **Horizon:** Up to 90 days post-activation (aligned with business definition)
- **Unit of analysis:** Individual credit application (case)
- **Population:** Applications that reach Account Activated (regardless of final outcome)
- **Estimand:** Conditional survival function P(T > t | X, activated), where T is time to default after activation, X are features observed at prediction time

This formulation directly answers the business question about early warning of default among activated accounts while accounting for censoring (e.g., cases still active after 90 days). It avoids labeling non-activated cases as non-default and respects the observed data structure.

**Alternative target formulation:**
*Competing risks target for all applications*
- **Prediction target:** Multinomial outcome: {Activated-within-90d-default, Activated-within-90d-no-default, Rejected, Withdrawn, Transferred, Still-open}
- **Estimand:** Probability of each outcome given prefix features
- **Why different question:** Answers "what happens to this application?" rather than "will this activated account default?" This better reflects the business reality where many applications never reach activation.

## 2. Cohort construction

| Cohort type | Count | Inclusion criteria | Label status | Notes |
|-------------|-------|--------------------|--------------|-------|
| **Primary analysis cohort** | 21,600 | Activated within event window (1 Jan 2024 - 31 Dec 2025) AND 90-day outcome mature by 15 Feb 2026 | Labeled: 18,900 non-default, 2,700 default | Includes all activated cases with mature labels |
| **Censored activated** | 3,600 | Activated within window but 90-day outcome not mature by extraction | Censored at 90 days | Outcome may arrive later (7-35 days after 90-day horizon) |
| **Rejected** | 9,100 | Rejected during Credit Review | Competing outcome | Never exposed to credit risk |
| **Withdrawn** | 5,700 | Withdrawn by applicant | Competing outcome | Voluntary exit from process |
| **Transferred** | 2,900 | Transferred to partner platform | Partially observed | 60% have linkage to new identifier; elevated missing outcome risk |
| **Still-open** | 5,100 | Not activated or terminal by extraction | Competing outcome | May activate later or remain open indefinitely |
| **Pre-policy change** | ~24,000 | Applications started before 1 Jul 2025 | - | Affected by old credit policy |
| **Post-policy change** | ~24,000 | Applications started on/after 1 Jul 2025 | - | Affected by new credit policy |

**As-of rules:**
- Prediction time is defined as the timestamp of the first event after Credit Review decision (e.g., "Accepted" or "Rejected")
- For activated cases, prediction time must be before Account Activated
- Cases are included in the cohort if their first event occurs within the event observation window
- Label maturity is determined by `data_extract_time` minus `label_available_at` (should be  90 days for mature labels)

## 3. Censoring and missing-label strategy

**Primary analysis strategy:**
- **Ordinary right censoring:** Cases still active after 90 days post-activation (3,600 cases)
- **Delayed labels:** Cases where outcome feed arrives 7-35 days after 90-day horizon (handled by censoring at extraction date)
- **Selection through activation:** Only activated cases are included in primary analysis (acknowledges selection bias)
- **Transfer as competing event:** Transferred cases are treated as competing outcomes (not censored, not defaults)
- **Permanently missing outcome feeds:** Partner-originated activated accounts with missing feeds are excluded from primary analysis (sensitivity analysis includes them as censored)

**Sensitivity analysis:**
1. **Intention-to-treat analysis:** Treat all applications (including rejected/withdrawn/transferred) as the population, with default defined as activation followed by default within 90 days. Cases that never activate are treated as "non-default" only if they would have activated under current policy (requires counterfactual assumptions).
2. **Worst-case imputation:** Assume all transferred cases with missing outcomes defaulted (upper bound on default rate).
3. **Best-case imputation:** Assume all transferred cases with missing outcomes survived (lower bound).

**Testable assumptions:**
- Label maturity can be verified by comparing `data_extract_time` and `label_available_at`
- Transfer linkage completeness can be audited (60% coverage is documented)

**Partially testable assumptions:**
- The assumption that rejected/withdrawn cases would not have defaulted if activated (cannot be verified)
- The assumption that transferred cases with missing outcomes have similar default risk to observed transferred cases

**Unverifiable assumptions:**
- The missing-at-random assumption for transferred cases with missing outcomes
- The assumption that the credit-policy change did not affect the relationship between prefix features and default risk (only selection probability)

## 4. Prefix extraction

**Prefix generation rules:**
- **Prediction time:** Timestamp of the first event after Credit Review decision (e.g., "Accepted" or "Rejected")
- **Prefix length options:**
  - Fixed event-count: First 3 events after prediction time (to capture early process behavior)
  - Elapsed-time: Events occurring within 7 days of prediction time (to capture early behavior without being too restrictive)
- **Handling short cases:** Cases with fewer than 3 events after prediction time are included with available events (no padding)
- **Repeated document loops:** Count total document requests and time spent in loops as features, but do not truncate the prefix
- **Activity renaming:** Use a mapping table to standardize activity names across the migration date (15 Oct 2025). Activities renamed in the migration are mapped back to pre-migration names for consistency.

**Implementation approach:**
- For each case, identify prediction time as the timestamp of the first event after Credit Review decision
- Extract all events with timestamp  prediction time and  prediction time + 7 days (or up to 3 events)
- Ensure no post-activation events (e.g., Account Activated, Default Recorded) are included in the prefix

## 5. Process-aware features

| Feature type | Examples | Availability |
|--------------|----------|--------------|
| **Static case attributes** | `case:requested_amount`, `case:region`, `case:channel`, pre-policy-change flag | Available at prediction time |
| **Prefix-derived features** | - Control-flow: variant, number of loops, time in Credit Review, document request frequency <br> - Timing: mean/median time between events, variance in inter-event times <br> - Resource/queue: resource experience (at event time, not extraction time), queue length at prediction time <br> - Rework: number of times returned to Credit Review <br> - Cohort/calendar: day of week, holiday flag, pre/post policy change | Available at prediction time |
| **Historical reference data** | - Historical default rate by region/channel <br> - Historical processing time percentiles by activity <br> - Historical resource performance | Available at prediction time (must be computed from historical data prior to prediction time) |

**Feature engineering notes:**
- `risk_score` should be used only if it was updated before the prediction time (check timestamp)
- `final_limit` and `decision_reason` are only available after Credit Review decision (may be at or after prediction time)
- `collection_status` is only available after activation (post-prediction) and should not be used

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|-------------------------|----------------------|--------------------------|------------------|-----------|
| `final_limit` | Leakage if used before activation | Only available after activation | Drop | Cannot be known at prediction time |
| `decision_reason` | May be available at prediction time (after Credit Review) | Available at prediction time if Credit Review decision has occurred | Keep (with timestamp check) | Part of the decision process |
| `collection_status` | Post-activation status | Only available after activation | Drop | Cannot be known at prediction time |
| Future events (e.g., Account Activated) | Future information | Must exclude events after prediction time | Drop | Violates as-of principle |
| `documents_total` | Snapshot may include later same-day uploads | Use only documents uploaded before prediction time | Repair: use timestamp to filter | Prevents leakage from same-day updates |
| Updated `risk_score` | Risk score updates may occur after prediction time | Only use risk scores with timestamp  prediction time | Repair: filter by timestamp | Prevents using future information |
| Resource experience | Stored as experience at extraction time, not event time | Use only if experience can be estimated at event time (e.g., from hire date) | Drop or repair: estimate experience at event time | Prevents leakage from future knowledge |
| `label_available_at` | Indicates when label is available, not when it was known | Do not use as feature | Drop | Leakage of label maturity |
| `data_extract_time` | Extraction time is after label maturity | Do not use as feature | Drop | Leakage of label maturity |
| `default_90d` | Outcome label | Only available for activated cases with mature labels | Keep only for primary analysis cohort | Part of the target definition |

## 7. Validation design

**Temporal validation scheme:**
- **Training period:** 1 Jan 2024 - 30 Jun 2025 (pre-policy change)
- **Validation period 1:** 1 Jul 2025 - 14 Oct 2025 (post-policy change, pre-migration)
- **Validation period 2:** 15 Oct 2025 - 31 Dec 2025 (post-migration)
- **Test period:** 1 Jan 2026 - 15 Feb 2026 (label maturity period)

**Why random split is misleading:**
- Policy change on 1 Jul 2025 affects feature-outcome relationships
- System migration on 15 Oct 2025 affects activity names and event structure
- Label maturity varies by cohort (e.g., cases starting later have less mature labels)
- Random split would mix pre- and post-change cohorts, obscuring distribution shift

**Evaluation metrics:**
- **Primary target (survival):** Concordance index (C-index) for time-to-event, calibration of survival curves
- **Discrimination:** AUC-ROC for 90-day default prediction (binary classification on activated cases)
- **Calibration:** Brier score for survival probabilities
- **Competing risks (alternative target):** AUC for each outcome class, calibration of multinomial probabilities
- **Subgroup performance:** By region, channel, pre/post policy change

**Calibration checks:**
- Compare predicted vs observed survival curves by deciles of risk score
- Stratify by pre/post policy change to detect shift

## 8. Limitations and decision-use boundary

**What the study can claim:**
1. **Predictive association:** The model can identify prefixes of activated accounts that are associated with higher risk of default within 90 days, conditional on the observed features.
2. **Selection effects:** The study acknowledges that only activated accounts are included, so the model's predictions apply to the activated subpopulation.
3. **Policy-aware predictions:** The model accounts for the policy change on 1 Jul 2025 in training and validation.

**What the study cannot claim:**
1. **Counterfactual default risk:** Cannot claim that rejected/withdrawn cases would have defaulted if activated (requires stronger assumptions).
2. **Causal effects:** Cannot claim that changing a prefix feature (e.g., reducing document requests) would reduce default risk.
3. **Generalizability to all applications:** Predictions do not apply to non-activated cases.

**Ways deployment could change the data-generating process:**
1. **Behavioral change:** Applicants may alter their behavior (e.g., withdraw earlier) if they know they are being monitored for early warning.
2. **Process change:** Lenders may adjust credit policies or processing steps in response to the model's predictions, changing the feature-outcome relationship.
3. **Data change:** The event data may become more or less granular depending on system updates, affecting feature quality.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import pm4py
from datetime import datetime, timedelta
import numpy as np
from sklearn.model_selection import train_test_split

# Configuration
EVENT_FILE = "applications_events.csv"
CUTOFF_DATE = datetime(2026, 2, 15)  # Data extraction date
POLICY_CHANGE_DATE = datetime(2025, 7, 1)
MIGRATION_DATE = datetime(2025, 10, 15)
PREDICTION_HORIZON_DAYS = 90
PREFIX_EVENT_COUNT = 3
PREFIX_TIME_WINDOW_DAYS = 7

def load_and_preprocess_events():
    """Load event data with basic preprocessing"""
    df = pd.read_csv(EVENT_FILE, parse_dates=['time:timestamp'])

    # Standardize activity names across migration
    activity_mapping = {
        'Credit Review (Old)': 'Credit Review',
        'Credit Review (New)': 'Credit Review',
        'Accepted (Old)': 'Accepted',
        'Accepted (New)': 'Accepted',
        # Add other mappings as needed
    }
    df['concept:name'] = df['concept:name'].map(activity_mapping).fillna(df['concept:name'])

    # Ensure timestamps are timezone-naive (PM4Py requirement)
    df['time:timestamp'] = df['time:timestamp'].dt.tz_localize(None)

    return df

def build_case_outcomes(df_events):
    """Build case-level outcome information as of CUTOFF_DATE"""
    # Identify terminal events
    terminal_events = ['Rejected', 'Withdrawn', 'Transferred', 'Account Activated', 'Default Recorded']
    case_outcomes = []

    for case_id, case_df in df_events.groupby('case:concept:name'):
        # Find activation and default events
        activated_event = case_df[case_df['concept:name'] == 'Account Activated']
        default_event = case_df[case_df['concept:name'] == 'Default Recorded']

        # Determine activation time and default time
        activation_time = activated_event['time:timestamp'].min() if not activated_event.empty else None
        default_time = default_event['time:timestamp'].min() if not default_event.empty else None

        # Determine case outcome
        if activation_time is not None:
            if default_time is not None and (default_time - activation_time) <= timedelta(days=90):
                outcome = 'default_90d'
                outcome_time = default_time
            else:
                # Check if outcome is mature (label available at least 90 days after activation)
                label_mature = (CUTOFF_DATE - activation_time) >= timedelta(days=90 + 35)  # Allow 35 days for feed delay
                outcome = 'non_default' if label_mature else 'censored_activated'
                outcome_time = activation_time + timedelta(days=90) if label_mature else CUTOFF_DATE
        else:
            # Non-activated cases
            terminal_event = case_df[case_df['concept:name'].isin(terminal_events)]
            if not terminal_event.empty:
                terminal_time = terminal_event['time:timestamp'].min()
                if terminal_event['concept:name'].iloc[0] == 'Rejected':
                    outcome = 'rejected'
                elif terminal_event['concept:name'].iloc[0] == 'Withdrawn':
                    outcome = 'withdrawn'
                elif terminal_event['concept:name'].iloc[0] == 'Transferred':
                    outcome = 'transferred'
                else:
                    outcome = 'still_open'
                outcome_time = terminal_time
            else:
                outcome = 'still_open'
                outcome_time = CUTOFF_DATE

        case_outcomes.append({
            'case:concept:name': case_id,
            'outcome': outcome,
            'outcome_time': outcome_time,
            'activation_time': activation_time,
            'start_time': case_df['time:timestamp'].min()
        })

    return pd.DataFrame(case_outcomes)

def identify_prediction_time(case_df):
    """Identify prediction time as first event after Credit Review decision"""
    # Find Credit Review decision events
    credit_review_events = case_df[case_df['concept:name'] == 'Credit Review']
    if credit_review_events.empty:
        return None

    # Find first event after Credit Review
    credit_review_time = credit_review_events['time:timestamp'].max()
    post_credit_events = case_df[case_df['time:timestamp'] > credit_review_time]

    if post_credit_events.empty:
        return None

    return post_credit_events['time:timestamp'].min()

def extract_prefixes(df_events, case_outcomes):
    """Extract prefixes without looking into the future"""
    prefix_data = []

    for case_id, case_df in df_events.groupby('case:concept:name'):
        # Get case outcome info
        case_outcome = case_outcomes[case_outcomes['case:concept:name'] == case_id].iloc[0]

        # Identify prediction time
        pred_time = identify_prediction_time(case_df)
        if pred_time is None:
            continue  # Skip cases without prediction time

        # Filter events at or after prediction time
        future_events = case_df[case_df['time:timestamp'] >= pred_time]

        # Apply prefix constraints
        if PREFIX_EVENT_COUNT > 0:
            # Fixed event-count prefix
            if len(future_events) > PREFIX_EVENT_COUNT:
                future_events = future_events.head(PREFIX_EVENT_COUNT)
        else:
            # Time-window prefix
            time_window_end = pred_time + timedelta(days=PREFIX_TIME_WINDOW_DAYS)
            future_events = future_events[future_events['time:timestamp'] <= time_window_end]

        # Ensure no post-activation events are included
        if case_outcome['activation_time'] is not None:
            future_events = future_events[future_events['time:timestamp'] < case_outcome['activation_time']]

        # Create prefix dataframe
        prefix_df = future_events.copy()
        prefix_df['case:concept:name'] = case_id
        prefix_df['prediction_time'] = pred_time

        prefix_data.append(prefix_df)

    return pd.concat(prefix_data) if prefix_data else pd.DataFrame()

def build_features_and_targets(df_prefixes, case_outcomes):
    """Build feature matrix and target vector"""
    # Merge prefix data with case outcomes
    df_features = df_prefixes.groupby('case:concept:name').agg({
        'concept:name': lambda x: list(x),
        'time:timestamp': lambda x: list(x),
        'org:resource': lambda x: list(x),
        'risk_score': lambda x: list(x),
        'case:requested_amount': 'first',
        'case:region': 'first',
        'case:channel': 'first',
        'source_system': 'first'
    }).reset_index()

    # Add case outcome
    df_features = df_features.merge(case_outcomes, on='case:concept:name')

    # Feature engineering (simplified examples)
    # 1. Static features
    df_features['requested_amount'] = df_features['case:requested_amount']
    df_features['region'] = df_features['case:region']
    df_features['channel'] = df_features['case:channel']

    # 2. Process features
    def extract_process_features(activity_list):
        return {
            'variant': '-'.join(activity_list),
            'num_events': len(activity_list),
            'has_document_request': any('Document Request' in act for act in activity_list),
            'num_loops': activity_list.count('Credit Review')
        }

    process_features = df_features['concept:name'].apply(extract_process_features)
    for k, v in process_features.iloc[0].items():
        df_features[f'proc_{k}'] = process_features.apply(lambda x: x[k])

    # 3. Timing features
    def extract_timing_features(timestamps):
        timestamps = pd.to_datetime(timestamps)
        diffs = timestamps.diff().dt.total_seconds() / 3600  # hours
        return {
            'mean_inter_event_hours': diffs.mean(),
            'max_inter_event_hours': diffs.max(),
            'num_events': len(timestamps)
        }

    timing_features = df_features['time:timestamp'].apply(extract_timing_features)
    for k, v in timing_features.iloc[0].items():
        df_features[f'timing_{k}'] = timing_features.apply(lambda x: x[k])

    # Target construction (for primary analysis)
    def get_target(row):
        if row['outcome'] == 'default_90d':
            return 1
        elif row['outcome'] in ['non_default', 'censored_activated']:
            return 0
        else:
            return np.nan  # Competing outcomes excluded from primary analysis

    df_features['target'] = df_features.apply(get_target, axis=1)

    # For survival analysis, we would also need:
    # - Time to event/censoring
    # - Event indicator

    return df_features

def temporal_split(df_features):
    """Temporal train/validation/test split"""
    # Split by case start time
    df_features = df_features.sort_values('start_time')

    # Define split points
    train_end = datetime(2025, 6, 30)
    val1_end = datetime(2025, 10, 14)

    train = df_features[df_features['start_time'] <= train_end]
    val1 = df_features[(df_features['start_time'] > train_end) & (df_features['start_time'] <= val1_end)]
    val2 = df_features[df_features['start_time'] > val1_end]

    return train, val1, val2

def leakage_audit(df_features):
    """Audit for leakage in feature construction"""
    audit_results = []

    # Check for post-prediction features
    if 'final_limit' in df_features.columns:
        audit_results.append({
            'Feature': 'final_limit',
            'Risk': 'Leakage if used before activation',
            'Valid_availability': 'Only after activation',
            'Action': 'Drop',
            'Rationale': 'Cannot be known at prediction time'
        })

    # Check for future events in prefixes
    # (This would be checked during prefix extraction)

    return pd.DataFrame(audit_results)

def main():
    # Load and preprocess events
    df_events = load_and_preprocess_events()

    # Build case outcomes as of CUTOFF_DATE
    case_outcomes = build_case_outcomes(df_events)

    # Print cohort counts
    print("Cohort counts:")
    print(case_outcomes['outcome'].value_counts())

    # Extract prefixes
    df_prefixes = extract_prefixes(df_events, case_outcomes)

    # Build features and targets
    df_features = build_features_and_targets(df_prefixes, case_outcomes)

    # Temporal split
    train, val1, val2 = temporal_split(df_features)

    print(f"\nTrain size: {len(train)}")
    print(f"Validation 1 size: {len(val1)}")
    print(f"Validation 2 size: {len(val2)}")

    # Leakage audit
    audit_df = leakage_audit(df_features)
    print("\nLeakage audit:")
    print(audit_df)

    # For survival analysis, we would add:
    # - Time to event/censoring
    # - Event indicator
    # - Use lifelines or scikit-survival for modeling

if __name__ == "__main__":
    main()
```
