## 5. Monitoring architecture

We'll design a monitoring system with the following components:

- **Predictive monitors**: Track AUROC, Brier, and ECE over time, with alerts for significant drops.
- **Calibration monitors**: Plot calibration curves (predicted vs observed) for each month and each segment.
- **Label-maturity monitors**: Track label maturity and alert when maturity drops below a threshold (e.g., 90%).
- **Data-quality monitors**: Monitor feature missingness, unknown activity share, and data pipeline errors.
- **Process-variant monitors**: Track the distribution of process variants and alert on significant shifts.
- **Performance-DFG monitors**: Track key process times (e.g., part delivery time) and alert on significant increases.
- **Population monitors**: Track the distribution of new segments (like Partner Z) and their characteristics.
- **Intervention/deployment monitors**: Log when the model or feature pipeline is updated.

**Alert dependencies**: A label-delay alarm should not automatically trigger retraining. Instead, it should trigger a hold on performance evaluation and a label-maturity investigation. Similarly, a data-quality alarm should trigger a pipeline investigation.

```python
import pandas as pd
import pm4py
from datetime import datetime

def process_monthly_evidence(event_log_path, month_start, month_end):
    # Read the event log
    df = pd.read_csv(event_log_path, parse_dates=['timestamp'])
    
    # Normalize activity labels: map new diagnosis label to old
    df['activity'] = df['activity'].replace('Diagnostic Assessment Completed', 'Initial Diagnosis Completed')
    
    # Handle duplicates: drop exact duplicates (same case_id, activity, timestamp)
    df = df.drop_duplicates(subset=['case_id', 'activity', 'timestamp'])
    
    # Format for pm4py
    df = pm4py.format_dataframe(df, case_id='case_id', activity_key='activity', timestamp_key='timestamp')
    
    # Create event-calendar cohort: events that occurred in the month
    event_cohort = pm4py.filter_time_range(df, month_start, month_end, mode='events')
    
    # Create case-start cohort: cases that started in the month
    case_start_cohort = pm4py.filter_time_range(df, month_start, month_end, mode='cases')
    
    # For each cohort, compute summaries
    summaries = {}
    
    for cohort_name, cohort in [('event_calendar', event_cohort), ('case_start', case_start_cohort)]:
        # Discover DFG
        dfg, start_activities, end_activities = pm4py.discover_dfg(cohort)
        
        # Discover performance DFG
        perf_dfg, _, _ = pm4py.discover_performance_dfg(cohort)
        
        # Get variants
        variants = pm4py.get_variants(cohort)
        
        # Extract temporal features (e.g., elapsed times)
        temporal_features = pm4py.extract_temporal_features_dataframe(cohort)
        
        # Compute summary statistics for key edges
        # Example: median elapsed time for 'Order Part' -> 'Part Received'
        key_edges = [('Order Part', 'Part Received')]
        median_times = {}
        for edge in key_edges:
            if edge in perf_dfg:
                times = [t for _, _, t in perf_dfg[edge]]
                if times:
                    median_times[edge] = pd.Series(times).median()
                else:
                    median_times[edge] = None
            else:
                median_times[edge] = None
        
        # Store summary
        summaries[cohort_name] = {
            'num_cases': len(cohort['case_id'].unique()),
            'num_events': len(cohort),
            'dfg': dfg,
            'perf_dfg_median': median_times,
            'variants': variants,
            'temporal_features_summary': temporal_features.describe()
        }
    
    return summaries
```

Note: The above code is a sketch and may need adjustments for actual pm4py API.

We call this function for each month and aggregate the results.

The model’s mean predicted risk (0.28) overshot the observed breach rate (0.19), and AUROC/Brier/ECE all worsened. This is primarily a pipeline incident, not a realworld shift.

- **May**: The pipeline was patched but not fully repaired (cached feature not recomputed). Data quality improved but residual missingness (3%) and early supplier delays (partdelivery time 38h vs. 35h in Mar) created a mix of **residual covariate drift** and early **concept drift** for V3. Model performance improved but did not return to baseline.

- **Jun**: A **process drift** occurred: a new remoterouting policy raised V2 share from 35% to 52%. This is a covariate shift in variant distribution. The model’s predicted risk (0.20) was higher than the observed breach rate (0.15), likely because it did not account for the lower risk of V2. Supplier delays were still moderate (42h), so concept drift was not yet dominant. This month’s deterioration is mainly due to processmix change.

- **Jul**: **Concept drift** emerges for V3: supplier delivery times jumped to 65h, and V3 breach rates rose to 0.46. The model’s AUROC fell to 0.76, and calibration error increased. V3 share also grew to 22%, adding covariate drift. This is a genuine change in the outcomefeature relationship for V3.

- **Aug**: Supplier delays became severe (130h), V3 breach rates soared to 0.64, and V3 share reached 35%. The model’s underprediction (mean risk 0.19 vs. observed 0.28) indicates strong **concept drift** for V3, amplified by covariate drift. Label maturity was still 93%, so label delay played a minor role.

- **Sep**: **Three forces converge**: (1) concept drift continues (V3 breach 0.61, partdelivery 148h), (2) a **population shift** arrives (PartnerZ, 24% of cases, with higher risk and missing features), and (3) label maturity drops to 82%. The model’s performance degrades further, but the observed breach rate (0.31) is now a mixture of true risk and censoring.

- **Oct**: **Label delay/censoring** dominates: maturity is only 55%, and the outcome API has a backlog. The observed breach rate (0.16) is artificially low because cases with long resolution paths (V3) have not yet matured. The model’s mean predicted risk (0.23) may be more accurate, but the observed metrics are unreliable. Supplier delays and population shift persist but are confounded by immaturity.

**Why not treat these as one failure?** April is a pipeline artifact, June is a processmix change, August–September are genuine performance/concept/population shifts, and October is a labelmaturity artifact. Conflating them would lead to wrong fixes (e.g., retraining on October’s immature labels or recalibrating around April’s pipeline bug).

## 3. Diagnostic tests

1. **Labelmaturity curves and fixedvintage backtesting**
   - *Test*: For each month, plot the observed breach rate as a function of days since case start until full maturity. Then, for a fixed vintage (e.g., August cases), track the breach rate over time.
   - *Expected under label delay*: Breach rate rises and then stabilizes at a higher level than initially observed.
   - *Expected under concept drift*: The stabilized breach rate will be higher than historical baselines for the same variant.

2. **Recomputation after activitylabel normalization and duplicate cleaning**
   - *Test*: Reprocess April–May data with the corrected activity mapping and duplicate removal; recompute all derived features, including the cached “number of events before diagnosis.”
   - *Expected under pipeline failure*: Model performance (AUROC, Brier) should return to Jan–Mar levels for those months.
   - *Expected under other drifts*: Performance will not fully recover, indicating additional drift sources.

3. **Calibration and discrimination stratified by variant, source, and month**
   - *Test*: Compute AUROC, Brier, and ECE separately for V1, V2, V3 and for PartnerZ vs. others, month by month.
   - *Expected under concept drift for V3*: Calibration and discrimination for V3 degrade in Jul–Sep, while V1/V2 remain stable.
   - *Expected under population shift*: PartnerZ shows worse calibration than nonPartnerZ after controlling for variant.

4. **Comparison of process variants and DFG/performanceDFG edges**
   - *Test*: For each month, extract median elapsed time for key edges (e.g., Order Part  Part Received) and correlate with variantspecific breach rates.
   - *Expected under supplierdriven concept drift*: As partdelivery time increases, V3 breach rate increases and model calibration worsens.

5. **Tests of whether the outcome relationship conditional on the same path changed**
   - *Test*: For cases that follow the exact same path (e.g., V3 with similar features), compare breach rates across months using statistical tests (e.g., logistic regression with month as a predictor).
   - *Expected under concept drift*: The coefficient for later months will be positive and significant, indicating higher breach probability given the same path.

6. **Population reweighting or transportstyle checks for PartnerZ**
   - *Test*: Reweight PartnerZ cases to match the feature distribution of nonPartnerZ cases (if features are available) and compare breach rates.
   - *Expected under population shift*: After reweighting, the breach rate gap narrows. If it remains wide, unobserved heterogeneity or concept drift exists.

7. **Feature missingness and lineage audits**
   - *Test*: For each month, compute missingness rates for each feature and trace feature lineage through the pipeline.
   - *Expected under pipeline failure*: April and May will show high missingness in specific features, correlated with prediction errors.
   - *Expected under natural drift*: Missingness rates remain low and stable.

## 4. Recalibrationversusretraining decision

**Immediate containment (next 1–2 weeks)**
- **October**: Stop reporting observed breach rates and model metrics until labels mature. Use only cohorts with 60 days of maturity for evaluation.
- **April–May**: Hotfix the pipeline: normalize activity labels, remove duplicates, and recompute all derived features. Backfill predictions for those months.
- **PartnerZ**: If possible, add missing features (rural travel distance, device age) to the feature pipeline.

**Shortterm recalibration (next 1–2 months)**
- Recalibrate the model using isotonic regression or Platt scaling on recent mature data (e.g., June–August) to correct calibration drift.
- If stratified analysis shows differential calibration, apply variantspecific or sourcespecific calibration.

**Feature repair (next 2–3 months)**
- Harden the feature pipeline against activitylabel changes (e.g., use mapping tables, handle unknowns gracefully).
- Incorporate PartnerZspecific features and consider interaction terms with variant.
- Add a realtime supplierperformance feature (e.g., recent average partdelivery time) to capture concept drift.

**Full retraining (next 3–6 months)**
- Retrain on data from September onward once labels are fully mature, but exclude April–May until their features are repaired.
- Use a model that can adapt to temporal changes (e.g., include month as a feature, or use online learning).
- **Safe months for training**: Jan–Mar (stable), Jun–Aug (once pipeline fixed and supplier drift is understood). April–May are unsafe until pipeline is fixed. Sep is safe once labels mature, but note population shift. Oct is unsafe until labels mature.

**Segmentspecific model justification**
Given the distinct dynamics for V3 (supplierdriven concept drift) and PartnerZ (population shift), a segmentspecific model (e.g., separate models for V3 and V1/V2, or for PartnerZ vs. others) is justified if interpretability and maintenance are manageable. Otherwise, a single model with interaction terms (variant×month, variant×supplier performance) may suffice.

## 5. Monitoring architecture

**Components**
- **Predictive monitors**: AUROC, Brier, ECE, and mean predicted risk, computed monthly on mature cohorts.
- **Calibration monitors**: Calibration curves (predicted vs. observed) for each variant and source.
- **Labelmaturity monitors**: Track label maturity and median label delay; alert when maturity <90%.
- **Dataquality monitors**: Feature missingness rates, unknownactivity share, pipeline error logs.
- **Processvariant monitors**: Distribution of V1, V2, V3, and unmapped variants; alert on significant shifts.
- **PerformanceDFG monitors**: Key process times (e.g., partdelivery, remotefix) and their trends.
- **Population monitors**: Share of new segments (e.g., PartnerZ) and their feature distributions.
- **Intervention/deployment monitors**: Log all pipeline fixes, model recalibrations, and feature changes.

**Alert dependencies**
- A **labelmaturity alarm** should not trigger retraining; instead, it should trigger a hold on performance evaluation and an investigation into the outcome API.
- A **dataquality alarm** should trigger a pipeline investigation, not necessarily model retraining.
- A **processvariant alarm** should trigger a review of variantspecific performance and possible recalibration.
- A **predictiveperformance alarm** (e.g., AUROC drop) should only trigger retraining after dataquality and labelmaturity alarms are resolved.

**Python code block: monthly processevidence extraction**

```python
import pandas as pd
import pm4py
from datetime import datetime

def extract_monthly_process_evidence(event_log_path: str,
                                     month_start: str,
                                     month_end: str) -> dict:
    """
    Extract auditable monthly process evidence from a field-service event log.
    Returns summaries for both event-calendar and case-start cohorts.
    """
    # 1. Read and prepare the event log
    df = pd.read_csv(event_log_path, parse_dates=['timestamp'])
    
    # 2. Normalize renamed diagnosis activity
    df['activity'] = df['activity'].replace({
        'Diagnostic Assessment Completed': 'Initial Diagnosis Completed'
    })
    
    # 3. Handle duplicates (exact duplicates on case_id, activity, timestamp)
    df = df.drop_duplicates(subset=['case_id', 'activity', 'timestamp'])
    
    # 4. Format for pm4py
    df = pm4py.format_dataframe(
        df,
        case_id='case_id',
        activity_key='activity',
        timestamp_key='timestamp'
    )
    
    # 5. Create two cohorts
    # Event-calendar cohort: all events occurring in the month
    event_cohort = pm4py.filter_time_range(
        df,
        month_start,
        month_end,
        mode='events'
    )
    
    # Case-start cohort: cases that started (first event) in the month
    case_start_cohort = pm4py.filter_time_range(
        df,
        month_start,
        month_end,
        mode='cases'
    )
    
    # 6. Compute summaries for each cohort
    summaries = {}
    for cohort_name, cohort in [('event_calendar', event_cohort),
                                ('case_start', case_start_cohort)]:
        if cohort.empty:
            summaries[cohort_name] = {'error': 'No data in period'}
            continue
        
        # Discover DFG and performance DFG
        dfg, start_act, end_act = pm4py.discover_dfg(cohort)
        perf_dfg, _, _ = pm4py.discover_performance_dfg(cohort)
        
        # Get variants
        variants = pm4py.get_variants(cohort)
        
        # Extract temporal features (e.g., elapsed times, event counts)
        temporal_features = pm4py.extract_temporal_features_dataframe(cohort)
        
        # Compute median elapsed time for key edges
        key_edges = [
            ('Order Part', 'Part Received'),
            ('Initial Diagnosis Completed', 'Remote Fix')
        ]
        median_times = {}
        for edge in key_edges:
            if edge in perf_dfg:
                times = [t for _, _, t in perf_dfg[edge]]
                median_times[edge] = pd.Series(times).median() if times else None
            else:
                median_times[edge] = None
        
        # Aggregate summary
        summaries[cohort_name] = {
            'num_cases': cohort['case:concept:name'].nunique(),
            'num_events': len(cohort),
            'num_variants': len(variants),
            'dfg_size': len(dfg),
            'median_elapsed_times': median_times,
            'temporal_features_summary': temporal_features.describe().to_dict()
        }
    
    return summaries

# Example usage:
```

## 6. Risks of acting on the wrong diagnosis

1. **Retraining on immature labels (October)**
   - *Risk*: The model learns from incomplete outcomes, leading to systematic underprediction of breach rates, especially for longresolution variants (V3).
   - *Mitigation*: Use only fully mature labels for training. Implement a maturitybased holdout: do not include a month in training until label maturity exceeds a threshold (e.g., 95%).

2. **Calibrating around a pipeline bug (April–May)**
   - *Risk*: Recalibrating the model on April–May data without fixing the pipeline corrects for artificial errors that will not recur, potentially overadjusting and harming future performance.
   - *Mitigation*: Always fix pipeline issues first, then recompute features and predictions before any recalibration. Use Jan–Mar as a clean baseline.

3. **Ignoring genuine supplierdriven concept drift (July–September)**
   - *Risk*: Assuming the deterioration is only due to pipeline or population shifts leads to a model that remains poorly calibrated for V3, resulting in high falsenegative rates and missed breaches.
   - *Mitigation*: Update the model with recent data that reflects the new supplier performance. Consider adding a timevarying feature (e.g., rolling average partdelivery time) to capture the drift explicitly.

4. **Attributing PartnerZ’s population shift to unfair model behavior without stratified evidence**
   - *Risk*: Assuming the model is biased against PartnerZ and applying fairness adjustments without understanding the true drivers (e.g., missing ruraltravel features) could introduce bias or reduce accuracy for other segments.
   - *Mitigation*: Conduct stratified analysis to determine if the performance gap persists after controlling for available features. If missing features explain the gap, prioritize adding them. If unexplained heterogeneity remains, consider a separate model or reweighting.
