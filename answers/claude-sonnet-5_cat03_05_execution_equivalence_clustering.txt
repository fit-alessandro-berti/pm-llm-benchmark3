## 1. Equivalence design space

**R1 — Activity-sequence equivalence**
*Definition:* Two executions are equivalent iff the projection of their event list onto activity labels only (dropping all object references, types, ids, qualifiers) yields the same sequence (or, if concurrency is allowed, the same linearizable label sequence class).
*Invariants preserved:* control-flow shape as seen by a classical (non-object-centric) process-mining tool: number and order of activity labels.
*Discarded:* object types, cardinalities, external-object flags, O2O relations, qualifiers — i.e. everything that makes the log "object-centric."
*Properties:* reflexive, symmetric, transitive — it is literal string/sequence equality, hence a genuine equivalence relation.
*Concurrency:* two events with no causal dependency (e.g. the two `Add Item` events) can be treated as an unordered pair; R1 should be defined on the *linearization class* of the partial order, not the observed total order, otherwise X1 and X2 would spuriously differ.

**R2 — Typed structural equivalence under identifier renaming**
*Definition:* Build a typed, attributed hypergraph per execution: nodes are (ObjectType, local/EXT-flag); hyperedges are events with an ordered/partial-order position, an activity label, and an incidence set of (ObjectType, node) pairs. Two executions are equivalent iff there exists a bijection between local object ids (respecting type, and mapping EXT-flagged objects only to EXT-flagged objects of the same type) and an order-preserving bijection between events (label-preserving, incidence-preserving) such that the hypergraphs are isomorphic. O2O relation *types* (edge existence, source/target type) are preserved; O2O *qualifiers* (e.g. `replaces`, `partially_settles`) are optional and, in this relation, **ignored** — only structural incidence counts.
*Invariants preserved:* object type multiplicities, per-event E2O incidence (which types/how many objects touch which event), externality flags, event order up to permitted concurrency swaps.
*Discarded:* concrete identifier values, O2O qualifier labels, business meaning of the shape.
*Properties:* reflexive (identity map), symmetric (inverse bijection), transitive (composition of bijections) — genuine equivalence relation as long as the concurrency-permutation group is fixed in advance.
*Concurrency:* isomorphism is also allowed to permute events that are mutually non-adjacent in the derived precedence order (e.g., swap the two `Add Item` events), so X1  X2 despite the reversed item order.

**R3 — Business-semantic equivalence (preferred)**
*Definition:* Extract a fixed-arity **motif tuple** per execution:
`(fulfillment_pattern, settlement_pattern, sharing_pattern, exception_pattern)`, where
- `fulfillment_pattern`  {simple(1pkg-1delivery), split-merge(pack-fan-out, delivery-fan-in), split-split(pack-fan-out, delivery-fan-out), return-repack}
- `settlement_pattern`  {single-payment, installment/partial, joint-invoice}
- `sharing_pattern`  {none, logistics-pooled(EXT in Pack/Dispatch), financial-pooled(EXT in Invoice/Payment)}
- `exception_pattern`  {none, substitution/removal, return}
Two executions are equivalent iff their motif tuples are equal.
*Invariants preserved:* everything that changes an operational/financial risk profile — package/delivery topology class, settlement complexity, cross-execution sharing, and exception type, including O2O qualifiers where they are the only witness of an exception (e.g. `replaces`, `removed_before_dispatch`).
*Discarded:* exact object counts beyond the class boundary (e.g. 2 vs 3 items), exact identifiers, non-discriminating event ordering.
*Properties:* reflexive/symmetric/transitive by construction (equality of tuples over a fixed feature space).
*Concurrency:* the feature extractor is defined on the object graph, not on the raw timestamp order, so interleavings such as X4's Pack/Dispatch/Pack/Dispatch vs. a hypothetical Pack/Pack/Dispatch/Dispatch produce the same tuple.

R1  R2-information  R3-information in terms of what is *retained*, but as sets of pairs, **R1 is coarser than R2 is coarser than R3 is not guaranteed** — R3 is a business projection, not a strict refinement, and can (by design) merge things R2 keeps separate or separate things R1 merges.

## 2. Canonical signatures

```python
def canon_ids(events):
    """Rename local ids to type-scoped counters in first-seen order;
       external ids become type-scoped EXT tokens."""
    counters, ext_counters, mapping = {}, {}, {}
    for e in events:
        for otype, ids in e.objects.items():           # {'Item': [...], ...}
            for oid in ids:
                if oid in mapping:
                    continue
                if oid.startswith("EXT"):
                    k = ext_counters.get(otype, 0); ext_counters[otype] = k + 1
                    mapping[oid] = f"EXT:{otype}#{k}"
                else:
                    k = counters.get(otype, 0); counters[otype] = k + 1
                    mapping[oid] = f"{otype}#{k}"
    return mapping

def concurrency_classes(events, precedes):
    """Group events with identical causal predecessors into unordered classes."""
    classes, seen = [], set()
    for e in events:
        if e in seen: continue
        peers = [f for f in events if precedes(f) == precedes(e)]
        classes.append(sorted(peers, key=lambda x: (x.activity, canon_repr(x))))
        seen.update(peers)
    return classes

def canon_repr(event, mapping):
    incidence = sorted((otype, mapping[oid])
                       for otype, ids in event.objects.items() for oid in ids)
    return (event.activity, tuple(incidence))

def full_signature(execution):
    mapping = canon_ids(execution.events)
    classes = concurrency_classes(execution.events, execution.precedes)
    event_seq = tuple(tuple(canon_repr(e, mapping) for e in cls) for cls in classes)
    o2o = tuple(sorted(
        (rel.qualifier, rel.source_type, mapping[rel.source],
         rel.target_type, mapping[rel.target])
        for rel in execution.o2o))
    return (event_seq, o2o)

def business_motif(execution):
    fulfillment = classify_pack_dispatch_topology(execution)
    settlement  = classify_payment_pattern(execution)
    sharing     = classify_external_incidence(execution)
    exception   = classify_qualifiers(execution)
    return (fulfillment, settlement, sharing, exception)

def signature_hash(sig):
    import json, hashlib
    return hashlib.sha256(json.dumps(sig, sort_keys=True).encode()).hexdigest()
```
`full_signature` implements R2 (add qualifiers back in to get a qualifier-aware refinement of R2); `business_motif` is the R3 projection used as the preferred clustering key.

## 4. Cluster interpretations

**SEM-A (X1, X2) — Clean single-shipment order.** Signature: one Pack, one Dispatch, one Invoice, one Payment, no external incidence. Business behavior: the textbook happy path. Risk: essentially none; opportunity: reference/benchmark variant for SLA timing. A flat "one row per order" table represents this cluster perfectly — no loss. Stable under data repair (id typos, reordering of concurrent Add Items don't change membership).

**SEM-B (X3) — Multi-package, consolidated delivery.** Signature: 2×Pack, 1×Dispatch(2 packages), 1×Payment. Business behavior: warehouse split items across packages but logistics still consolidates into one shipment — likely same address/carrier run. Risk: packing overhead, but delivery-side risk is low. A flattened "order  delivery" table would hide the two-package fan-in and could misreport package-level SLA breaches. Stable under repair unless a Dispatch event is later split (then it becomes X4-like).

**SEM-C (X4) — Multi-package, multi-shipment, installment settlement.** Signature: 2×(Pack,Dispatch) + 2×Payment with `partially_settles`/`completes_settlement`. Business behavior: partial fulfillment combined with partial payment — classic drop-ship or backorder scenario. Risk: revenue recognition timing, partial-delivery customer dissatisfaction, reconciliation complexity. Any flattening that reports "order total paid" without installments will misstate AR aging. Less stable: if the second payment never arrives, this execution mutates into an incomplete-settlement case that a repair process must not silently merge with SEM-A.

**SEM-D (X5) — Pooled logistics.** Signature: local topology of SEM-A but Pack/Dispatch incidence includes EXT-typed Order/Item. Business behavior: warehouse consolidates shipments across orders (e.g., same address, marketplace fulfillment). Risk: a failure in the shared package (damage, mis-pick) impacts multiple orders simultaneously — a case-flattened "per order" view cannot see this blast radius. Opportunity: shipping cost amortization. Stability: fragile — if the EXT link is a data-quality artifact rather than genuine pooling, repair (removing EXT) collapses it into SEM-A, materially changing risk assessment.

**SEM-E (X6) — Pooled financial settlement.** Signature: local logistics like SEM-A, but Invoice/Payment incidence includes EXT-Order, with no order-level allocation. Business behavior: joint billing/consolidated invoice across orders. Risk: unclear liability allocation, dunning/collections ambiguity, revenue split disputes. This is exactly the kind of case that a per-order financial ledger would corrupt if flattened without noting the joint invoice. Stability: same fragility as SEM-D — depends on whether the shared invoice is intentional (co-billing) or an integration bug.

**SEM-F (X7) — Silent substitution.** Signature: identical label sequence to SEM-A, but Dispatch incidence includes an Item edge and O2O carries `replaces`/`removed_before_dispatch`. Business behavior: item was swapped or dropped after packing but before shipment, without a visible cancel/return activity. Risk: the customer may receive different contents than ordered/invoiced — a serious compliance/audit exposure precisely because it is invisible at the activity-sequence level. Any label-only flattening is dangerously misleading here. Stability: low — this cluster's entire identity rests on a qualifier and one extra incidence edge; if the OCEL extraction drops qualifiers (a common simplification), SEM-F silently merges into SEM-A.

**SEM-G (X8) — Return and repack.** Signature: extra `Return Item`/`Inspect Return` activities, two Pack/Dispatch pairs linked by a `replaces` qualifier on packages. Business behavior: a genuine reverse-logistics loop — customer or carrier returns an item, it's inspected, repacked, and re-dispatched. Risk: increased lead time, cost of reverse logistics, potential double-dispatch billing errors. Opportunity: root-cause input for return-rate analytics. This is the most structurally distinctive cluster and is stable under essentially all reasonable perturbations, since it is the only execution with unique activity labels.

## 5. Borderline cases

**X1 vs X2:** Under R1 and R2 they are equivalent (label sequence identical; hypergraphs isomorphic once concurrent `Add Item` events are treated as a swappable pair). Under R3 they are trivially equivalent since the motif ignores identifiers entirely. No disagreement — this pair calibrates that identifier renaming and concurrent-event reordering must *not* create false distinctions.

**X1 vs X5:** R1 says equivalent (same seven labels). R2 says **not** equivalent — Pack and Dispatch in X5 carry extra EXT-typed incidence, breaking the isomorphism. R3 (as defined with `sharing_pattern`) also separates them. But a coarser R3 variant that drops the sharing dimension (arguably "business as usual from O5's point of view — same product delivered") would merge them. Both are defensible: an operations team focused on *this order's* customer experience may not care that packaging was pooled; a risk/compliance team must.

**X1 vs X6:** Same pattern as X5 but the sharing is financial rather than logistical. R2 separates them (Invoice/Payment incidence includes EXT-Order). R3 separates them via `sharing_pattern=financial-pooled`. A coarser reporting-oriented R3 that only tracks "was this order fully paid" would merge X1 and X6, hiding the joint-liability risk — defensible for a dashboard, indefensible for AR audit.

**X1 vs X7:** This is the sharpest illustration of hidden semantics. R1 declares them equivalent (identical activity labels). A *naive* R2 that only checks event-type/object-type multiplicities without recording the exact Dispatch incidence would also merge them, because both have "one Pack, one Dispatch" over two items. But an incidence-faithful R2 catches the extra Item edge at Dispatch, and R3 catches the `replaces`/`removed_before_dispatch` qualifier. The disagreement hinges entirely on *how carefully* the structural definition records per-event incidence — a good argument for always using incidence-level, not just cardinality-level, structural equivalence.

**X3 vs X4:** Both instantiate "split packaging." A coarse business view ("split-package fulfillment," ignoring delivery consolidation and settlement count) merges them. My chosen R3 separates them because `fulfillment_pattern` distinguishes merged-delivery (X3) from split-delivery (X4), and `settlement_pattern` distinguishes single from installment payment. Both views are legitimate: a warehousing team cares only about "did we pack into >1 box" (merge); a finance/logistics-risk team cares about delivery fragmentation and installment billing (separate).

**X4 vs X8:** Superficially both have two Pack events and two Dispatch events. A count-based structural relation could merge them. But the *causal* shape differs completely: X4's second Pack/Dispatch is proactive fan-out (no intervening exception activity), while X8's second Pack/Dispatch is reactive, gated by `Return Item`/`Inspect Return` and linked via a `replaces` qualifier on the *package* object. Any equivalence that is sensitive to intervening activity labels or O2O qualifiers separates them cleanly; one that only counts activity occurrences (a "bag of activities" relation) would wrongly conflate a normal multi-shipment order with a return/repack incident — a significant business-semantics failure mode worth flagging explicitly.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`cluster_equivalent_ocel` extracts, per lead object, a process execution (the connected sub-object-graph reachable from that object) and groups executions that are **isomorphic as typed E2O/O2O graphs**, effectively implementing something close to R2: it preserves object types, event labels, per-event incidence, and relation structure, but is invariant to the concrete object identifiers. Raw identifiers would make every execution unique trivially (X1  X2 by literal id), so the library must already anonymize by construction — but the resulting clusters can still be **too fine for business use**, because any incidental structural wrinkle (an extra object touching one event, as in X7, or a differently-shaped but business-equivalent installment pattern, as in X3 vs X4) yields a new singleton cluster, exactly as our TS1–TS7 table shows.

**Canonicalization/post-processing:** after obtaining exact clusters, compute a `business_motif` (Section 2) for one representative per cluster, and re-group clusters whose motifs coincide. This two-stage pipeline — exact structural clustering first, coarse motif aggregation second — keeps the exact result auditable while producing an operationally usable segmentation.

**When exact equivalence is preferable:** conformance checking against a reference model, deduplication of logically identical executions, and any audit context where "these two cases are provably the same shape" must be demonstrable, not inferred.

**Effect of `max_objs`/large connected components:** cross-order sharing (X5, X6) means a lead object's connected component can span many orders through shared packages or invoices; `max_objs` truncation may cut the graph before the shared object is fully explored, which can (a) make two differently-shared executions look identical because both were truncated identically, or (b) fail to detect sharing at all if the truncation boundary falls exactly at the shared node. This is a genuine risk for the pooled-logistics/pooled-financial clusters and should be checked by re-running with a larger `max_objs` or by explicitly flagging truncated executions.

```python
import pandas as pd
import pm4py

def business_key(exec_summary):
    return (exec_summary["fulfillment_pattern"],
            exec_summary["settlement_pattern"],
            exec_summary["sharing_pattern"],
            exec_summary["exception_pattern"])

exact_clusters = pmpy_clusters = pm4py.cluster_equivalent_ocel(
    ocel, lead_object_type="Order", max_objs=50
)

rows = []
for cluster_id, executions in exact_clusters.items():
    rep = executions[0]
    summary = derive_business_summary(ocel, rep)   # custom: fulfillment/settlement/sharing/exception
    rows.append({"exact_cluster": cluster_id, "orders": [e.order_id for e in executions],
                 **summary})

df = pd.DataFrame(rows)
df["business_cluster"] = df.apply(lambda r: business_key(r), axis=1)
business_grouped = df.groupby("business_cluster")["orders"].sum()
```

## 7. Robustness analysis

**Ignore O2O qualifiers:** X5/X6/X7's *incidence* (EXT objects, extra Item edge on Dispatch) is not solely qualifier-carried, so they stay separated at the structural level; what is lost is *why* — substitution vs. arbitrary anomaly become indistinguishable, and X4's "partial vs completes" payments collapse into an undifferentiated "multiple payments" bucket. Cluster membership is mostly preserved; interpretive precision is not.

**Ignore external objects:** This is the most disruptive perturbation. Dropping EXT-OA/EXT-IA from X5 and EXT-OB from X6 makes both structurally and semantically identical to X1/X2 — SEM-D and SEM-E collapse into SEM-A. This erases the joint-liability and shared-capacity risks entirely, which is dangerous if applied uncritically in a production pipeline.

**Collapse repeated same-label events:** Merging X3's two `Pack` events into one aggregated event (Package:{P31,P32}) makes its activity-sequence identical to X1's, merging AS2 into AS1. Applied to X4, collapsing both Pack/Dispatch pairs *and* both Payments removes the installment signal entirely, making X4's label multiset equal to X1's — a serious information loss that must be flagged as a real risk of using multiset/"bag of activities" abstractions in object-centric settings. X8 remains distinguishable because `Return Item`/`Inspect Return` are non-repeated, unique labels that survive any collapsing scheme.

**Treat Pack/Dispatch order as partial rather than total order:** No change to clustering among X1–X8 (no two executions currently differ only by Pack/Dispatch interleaving), but it improves reproducibility: a re-logged or re-ingested version of X4 with Pack(P41)-Pack(P42)-Dispatch(P41)-Dispatch(P42) instead of the interleaved order must still land in SEM-C, not spawn a spurious new cluster.

**Payment multiplicity as an amount attribute:** If the number of Payment events is replaced by a scalar "installments" attribute outside the graph, SEM-A and SEM-C could be re-merged into one structural cluster differing only by an attribute value, shifting the fulfillment/settlement distinction from cluster boundary to intra-cluster statistic — appropriate for financial reporting, inappropriate for process-variant analysis.

## 8. Limitations and recommendation

- **Compliance monitoring:** use qualifier-aware typed structural equivalence (R2 + qualifiers, i.e. `full_signature`). Compliance must catch X5/X6 (sharing) and X7 (substitution) even when they are label-identical to X1.
- **Operational segmentation:** use business-semantic equivalence (R3, the motif tuple). Operations teams need SEM-A…SEM-G granularity to route work and estimate SLAs, without drowning in per-identifier noise.
- **Root-cause analysis:** use a qualifier/causal-motif equivalence that emphasizes the `exception_pattern` dimension specifically (isolating X7 from X8 from "none"), even at the cost of ignoring fulfillment/settlement dimensions that are irrelevant to the exception under investigation.
- **Descriptive reporting:** use activity-sequence equivalence or a deliberately coarse business projection (e.g., simple vs multi-package vs exception), because dashboards need maximal abstraction and human-readability over structural fidelity.

No single relation serves all four: fidelity (needed for compliance/root-cause) and abstraction (needed for segmentation/reporting) are in direct tension, and which dimensions matter (sharing vs exception vs settlement) itself depends on the question being asked — a reminder that "the finest partition" and "one preferred partition" are both traps; the right move is to keep the canonical signature parametrized and choose the projection per use case.
