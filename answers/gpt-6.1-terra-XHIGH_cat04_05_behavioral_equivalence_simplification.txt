# 1. Equivalence Notions

Treat a complete execution as a run from the initial marking to the exact final marking. Its visible trace is the ordered sequence of visible transition labels, with every `tau` removed. Events with the same label are distinguished by their positions in the sequence, not by a persistent identity or by which transition produced them. Thus two `Check Revision` occurrences remain two events in visible-trace comparisons.

- **Visible trace equivalence:** the two sets of complete visible traces are equal, allowing any number of loop repetitions and hiding `tau`. This is a language property, not a claim about identical internal states, causality, or probabilities.
- **P3 bounded visible-language equivalence:** the two sets are equal after retaining only complete visible traces of length at most 12 with at most three `Analyze Revision` events. The bounds apply to visible events, after hiding `tau`.
- **P1 business-relevant equivalence:** compare complete traces with all the stated activity labels and their order and multiplicity visible, including approvals and checks. Each analysis attempt has a distinct associated check within the same attempt, before the next rework or close; the check and analysis may occur in either order because P1 does not explicitly require the check to follow the analysis. Rework separates attempts, and an approval is optional per attempt. Under this observation boundary equality of the P1-relevant trace sets is required. If a business rule instead requires every check to follow its analysis, both models would need closer scrutiny: A also allows a check first.
- **P2 abstracted dashboard equivalence:** map each complete trace to `(first, last, analysis_count, check_occurred, rework_occurred)`, ignoring approval and silent events, check multiplicity, and all internal ordering beyond the first and last events. Compare the sets of resulting tuples. The order of analysis and check, and the locations and count of reworks, are not recorded.

# 2. Structural Comparison

| Feature | Model A | Model B | Semantic consequence |
|---|---|---|---|
| Loop scope | The parallel analysis/check and optional approval form the repeated loop body. | Only analysis and optional approval are repeated; the check is outside the loop. | A associates a fresh check with every attempt; B does not. |
| Minimum and maximum checks | One per iteration; at least one, with no finite maximum. | Exactly one per complete case. | For `n` analyses, A has `n` checks and B has one. |
| Check placement | Each check can precede or follow its analysis, but must finish before that iteration's optional approval and before the next rework or close. | The single check can interleave anywhere with the entire loop, including across reworks and approvals. | B permits an attempt with no separate check; A constrains each check to its own iteration. |
| Optional approvals | Zero or one per iteration, after both its analysis and check. | Zero or one per iteration, after its analysis; the check may occur before or after it. | Up to `n` approvals for `n` analyses in either model, but their order relative to checks differs. |
| Concurrency | Analysis and check are parallel within each iteration. | The one check is parallel with the whole loop. | Both analysis/check orders are possible, but B allows a check to cross an attempt boundary. |
| Join before close | The loop must finish; every iteration's parallel branches have joined. | Both the check branch and the entire loop branch must finish. | Close is last in every complete trace, but the joins enforce different check counts and timing. |

# 3. Verdicts

| View | Verdict | Confidence | Decisive reason | Caveat |
|---|---|---|---|---|
| P1 | not equivalent | High | Two attempts in A require two checks; B permits and requires only one. Approval/check ordering can differ even with one attempt. | The interpretation of a check before analysis should be agreed with the business. |
| P2 | equivalent only under stated abstraction | High | Both produce exactly `(Open Case, Close Case, n, true, n > 1)` for every integer `n >= 1`. | This discards check counts, approval information, and internal ordering; it does not establish visible-trace equivalence. |
| P3 | not equivalent | High | Both have distinguishing complete traces with two analyses and fewer than 12 visible events. | The bound is a test scope, not a proof of general equivalence. |

The P2 characterization follows because each loop executes its body at least once, and exactly one rework separates consecutive analyses. Both models contain at least one check, and both put open first and close last. For every `n >= 1` each model admits a complete execution with `n` analyses, so their abstract sets are equal.

# 4. Counterexample Traces

Use `O` = Open Case, `A` = Analyze Revision, `C` = Check Revision, `P` = Approve Revision, `R` = Rework Case, and `Z` = Close Case. Spaces separate events.

| Trace ID | Trace | Model A | Model B | First decisive semantic difference | Relevant view |
|---|---|---|---|---|---|
| A1 | `O A C R A C Z` | yes | no | The second `C` is required by the second A iteration; B has only one check. | P1, P3 |
| A2 | `O C A P R C A Z` | yes | no | The second `C` again exceeds B's single check; the first approval follows the first iteration's join. | P1, P3 |
| B1 | `O A C R A Z` | no | yes | The second attempt ends without its own check, whereas A requires one. | P1, P3 |
| B2 | `O A P C Z` | no | yes | In A, the check must precede the approval; B's independent check may follow it. | P1, P3 |

There is no visible-language inclusion in either direction. `tau` represents the optional approval branch and disappears from the trace; it does not erase checks. An explicit approval remains visible, and its placement can distinguish the models even with only one analysis, as B2 shows. P2 hides approvals and collapses all checks to one Boolean fact, so each of these witnesses has a matching abstract outcome in the other model.

# 5. Bounded Comparison Code

The following is a self-contained exhaustive exploration of the converted nets for this finite bounded state space. It keeps both the marking and the entire visible prefix in the visited key: merging all visits to the same marking would incorrectly discard different traces. Silent steps remain explorable even after the visible bound is reached, and repeated silent cycles at the same marking and prefix are suppressed. Exact marking equality determines completion. The visible-event and analysis bounds prune prefixes, which is safe because neither count can decrease. The code relies on these converted nets being bounded; the given structured process trees satisfy that condition. On an arbitrary net with unbounded silent token generation, termination would not be guaranteed.

```python
from collections import deque
import pm4py
from pm4py.objects.petri_net import semantics

A = "->('Open Case', *(->(+('Analyze Revision', 'Check Revision'), X('Approve Revision', tau)), 'Rework Case'), 'Close Case')"
B = "->('Open Case', +('Check Revision', *(->('Analyze Revision', X('Approve Revision', tau)), 'Rework Case')), 'Close Case')"

tree_a = pm4py.parse_process_tree(A)
tree_b = pm4py.parse_process_tree(B)
net_a, im_a, fm_a = pm4py.convert_to_petri_net(tree_a)
net_b, im_b, fm_b = pm4py.convert_to_petri_net(tree_b)

for name, net, im, fm in [('A', net_a, im_a, fm_a),
                          ('B', net_b, im_b, fm_b)]:
    sound, diagnostics = pm4py.check_soundness(net, im, fm)
    print(name, 'sound:', sound)
    if not sound:
        print('diagnostics:', diagnostics)

def bounded_language(net, im, fm, max_events=12, max_analyses=3):
    def key(marking, trace):
        # Place objects preserve identity even if place names coincide.
        tokens = frozenset((place, count) for place, count in marking.items()
                           if count)
        return tokens, trace

    queue = deque([(im, ())])
    seen = {key(im, ())}
    complete = set()
    while queue:
        marking, trace = queue.popleft()
        if marking == fm:
            complete.add(trace)
        for transition in pm4py.get_enabled_transitions(net, marking):
            label = transition.label
            new_trace = trace if label is None else trace + (label,)
            if (len(new_trace) > max_events or
                    new_trace.count('Analyze Revision') > max_analyses):
                continue
            next_marking = semantics.execute(transition, net, marking)
            state = key(next_marking, new_trace)
            if state not in seen:
                seen.add(state)
                queue.append((next_marking, new_trace))
    return complete

lang_a = bounded_language(net_a, im_a, fm_a)
lang_b = bounded_language(net_b, im_b, fm_b)
print('A traces:', len(lang_a), 'B traces:', len(lang_b))
print('Bounded equivalent:', lang_a == lang_b)
for title, difference in [('A only', lang_a - lang_b),
                          ('B only', lang_b - lang_a)]:
    print(title, ':', len(difference))
    for trace in sorted(difference):
        print('  ' + ' -> '.join(trace))
```

With PM4Py 2.7.23.4 this exploration returns 76 A traces and 85 B traces: four common, 72 A-only, and 81 B-only. Both soundness checks return true in that installation. This is exhaustive **within P3**, not random playout and not an unbounded equivalence proof. Different PM4Py versions and dependencies can affect APIs and soundness diagnostics.

# 6. Stochastic and Footprint Comparison

`pm4py.discover_footprints(...)` summarizes relations such as sequence and parallelism. It can expose differences in the relation between check and approval, but footprints aggregate local relations and do not capture all trace multiplicities, ordering constraints, or long-range dependencies. Equal footprints would not prove equal languages.

`pm4py.get_stochastic_language(...)` can estimate trace frequencies from representative event logs, or obtain a language from a supported model using its implementation's assumptions and approximations. Real probabilities require observed frequencies or an explicitly specified stochastic model, including loop and scheduling choices. The original trees alone do not specify them. Given two normalized stochastic languages, `pm4py.compute_emd(...)` measures the cost of transporting probability mass between traces under its trace-distance definition. A low EMD is quantitative evidence of similarity under those distributions; rare but important violations can have low weight, and even zero distance for a particular distribution need not establish equality of all possible traces.

For example, with `tree_a` and `tree_b` from section 5 and representative logs `log_a` and `log_b` supplied by the analyst:

```python
import pm4py

footprints_a = pm4py.discover_footprints(tree_a)
footprints_b = pm4py.discover_footprints(tree_b)
print('Footprints equal:', footprints_a == footprints_b)

# These languages reflect the observed log frequencies, not probabilities
# implied by the process trees. Obtain the logs from the relevant population.
language_a = pm4py.get_stochastic_language(log_a)
language_b = pm4py.get_stochastic_language(log_b)
print('EMD:', pm4py.compute_emd(language_a, language_b))
```

Sampling error, log coverage, the selected ground distance, and any differences in populations affect interpretation. No transition probabilities are assumed here.

# 7. Complexity Comparison

Count every operator and leaf as one node, and define depth as the maximum number of edges from root to leaf. A duplicate-label count is the sum, over visible labels, of occurrences beyond the first. These are static syntax counts, not counts of runtime loop executions.

| Measure | A | B | Simplified model in section 8 |
|---|---:|---:|---:|
| Tree nodes | 12 | 12 | 8 |
| Depth in edges | 4 | 5 | 3 |
| Visible leaves | 6 | 6 | 5 |
| Silent leaves | 1 | 1 | 0 |
| Duplicate visible labels | 0 | 0 | 0 |
| Converted-net arc-degree simplicity, PM4Py 2.7.23.4 | 0.8182 | 0.7778 | 0.8462 |

These simplicity scores depend on the conversion and metric implementation, and do not measure behavioral fidelity. The following code computes the tree measures and the PM4Py default net score; provide `tree_a`, `tree_b`, and `simplified_model` as defined in sections 5 and 8.

```python
from collections import Counter
import pm4py

def tree_stats(tree):
    nodes = visible = silent = depth = 0
    labels = Counter()
    stack = [(tree, 0)]
    while stack:
        node, d = stack.pop()
        nodes += 1
        depth = max(depth, d)
        if node.children:
            stack.extend((child, d + 1) for child in node.children)
        elif node.label is None:
            silent += 1
        else:
            visible += 1
            labels[node.label] += 1
    duplicates = sum(count - 1 for count in labels.values())
    return {'nodes': nodes, 'depth_edges': depth, 'visible_leaves': visible,
            'silent_leaves': silent, 'duplicate_labels': duplicates}

for name, tree in [('A', tree_a), ('B', tree_b), ('simplified', simplified_model)]:
    net, im, fm = pm4py.convert_to_petri_net(tree)
    print(name, tree_stats(tree), 'net simplicity:',
          pm4py.simplicity_petri_net(net, im, fm))
```

# 8. Simplified Model

Target **P2**, using the abstraction defined in section 1. Remove the optional approval branch from B, retaining a single check concurrent with the analysis/rework loop:

```text
->(
  'Open Case',
  +('Check Revision', *('Analyze Revision', 'Rework Case')),
  'Close Case'
)
```

```python
import pm4py

simplified_model = pm4py.parse_process_tree(
    "->('Open Case', +('Check Revision', "
    "*('Analyze Revision', 'Rework Case')), 'Close Case')"
)
```

For any `n >= 1`, this model has exactly `n` analyses, `n - 1` reworks, one check, open first and close last. Therefore its set of P2 tuples is exactly the same as that of both original models. Its eight nodes and depth three are smaller than both original trees by the counts in section 7. The simplification changes visible behavior, so the preservation claim is for the dashboard abstraction, not raw trace equivalence.

| Property | Preservation | Explanation |
|---|---|---|
| P2 dashboard outcome set | exact | All and only the same tuples are possible. |
| Open first, close last, at least one analysis and check | exact | Sequence, loop minimum, and parallel join enforce them. |
| Analysis count and presence of rework | exact | Every `n >= 1` is possible, with rework present exactly when `n > 1`. |
| Check multiplicity and placement | abstracted for P2; weakened versus A | The simplified model has one case-wide check, so it does not require one per attempt. P2 records only existence and ignores placement. |
| Optional approval occurrences and ordering | lost | No approval is generated; P2 hides approvals. |
| P1 compliance and P3 visible language | lost | Two attempts can share one check, and approval/check multiplicities differ from the originals. |

Regression traces below are **complete raw traces of the simplified model**, using the abbreviations from section 4. Their P2 tuples also occur in both originals.

| Trace | Expected | Reason |
|---|---|---|
| `O A C Z` | accept | One analysis and one check in parallel. |
| `O C A Z` | accept | Either parallel branch can finish first. |
| `O A R A C Z` | accept | Two attempts separated by rework; check occurs after both. |
| `O C Z` | reject | The loop must execute its analysis body at least once. |
| `O A R C Z` | reject | Every rework must be followed by another analysis before the loop exits. |

The two negative traces are rejected as raw complete traces; P2 itself ignores internal order and cannot distinguish every malformed trace from a valid trace with the same tuple.

# 9. Final Recommendation

For **P1**, use Model A as the better starting point: it enforces one check per analysis attempt and preserves optional approval occurrences. Confirm whether the business requires the check to happen after analysis; if so, replace the per-attempt parallel block with an appropriate sequence. Model B does not enforce a check per attempt and is unsuitable for that requirement.

For **P2**, either original and the simplified model produce the same dashboard outcomes. Use the simplified model as a dashboard abstraction if the omitted approval and per-attempt check information is not needed downstream. It should not replace A as an operational compliance model or replace either original where their visible languages matter.

For **P3**, neither original is equivalent to the other or to the simplified model under the stated visible bounds; choose the model whose full operational requirements are intended and use the bounded comparison as a regression test. Passing a bounded comparison alone would not prove unbounded equivalence.
