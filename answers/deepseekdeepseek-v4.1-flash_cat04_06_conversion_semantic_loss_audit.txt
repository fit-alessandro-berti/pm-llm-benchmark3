def marking_key(marking):
    return tuple(sorted(
        (str(getattr(p, "name", None) or id(p)), int(c))
        for p, c in marking.items() if c > 0
    ))

def transition_label(t):
    lab = getattr(t, "label", None)
    if lab is None or lab == "":
        return None
    return str(lab)

def fire_transition(net, marking, transition):
    new = dict(marking)
    for arc in net.arcs:
        if arc.target == transition:
            w = getattr(arc, "weight", 1)
            w = 1 if w is None else int(w)
            src = arc.source
            new[src] = new.get(src, 0) - w
            if new[src] < 0:
                raise ValueError("not enabled")
    for arc in net.arcs:
        if arc.source == transition:
            w = getattr(arc, "weight", 1)
            w = 1 if w is None else int(w)
            tgt = arc.target
            new[tgt] = new.get(tgt, 0) + w
    return {p: c for p, c in new.items() if c > 0}

def bounded_visible_traces(net, im, fm,
                           max_visible_len=12,
                           max_silent_steps=10,
                           max_steps=3000,
                           max_label_count=4):
    fm_key = marking_key(fm)
    accepted = set()
    seen = set()
    stack = [(dict(im), (), 0, 0, {})]
    while stack:
        marking, vtrace, silent_steps, steps, label_counts = stack.pop()
        if steps > max_steps:
            continue
        key = (marking_key(marking), vtrace, silent_steps)
        if key in seen:
            continue
        seen.add(key)

        if marking_key(marking) == fm_key:
            accepted.add(vtrace)
            continue

        if len(vtrace) > max_visible_len:
            continue

        for t in pm4py.get_enabled_transitions(net, marking):
            lab = transition_label(t)
            new_vtrace = vtrace
            new_silent = silent_steps + 1
            new_counts = label_counts
            if lab is None:
                if silent_steps + 1 > max_silent_steps:
                    continue
            else:
                new_silent = 0
                if len(vtrace) + 1 > max_visible_len:
                    continue
                new_counts = dict(label_counts)
                new_counts[lab] = new_counts.get(lab, 0) + 1

                    continue
                new_vtrace = vtrace + (lab, )

                new_marking = fire_transition(net, marking, t)

                continue

# 4. Preservation and Loss Audit

Assessment terms are restricted to the requested vocabulary.

| Source invariant | POWLPetri | PetriBPMN | PetriTree | BPMN round trip | Evidence or uncertainty |
|---|---|---|---|---|---|
| I1 Register first | expected preserved | expected preserved | conversion failed | ambiguous | Validate visible traces begin with Register. |
| I2 Assess/Prepare unordered | expected preserved | ambiguous | conversion failed | ambiguous | BPMN layout may visually serialize the two branches; trace tests must include both orders. |
| I3 Legal optional | expected preserved | ambiguous | conversion failed | ambiguous | Silent skip may become an unlabeled default flow; check traces with and without Legal Review. |
| I4 Verification prerequisites | expected preserved | expected preserved | conversion failed | ambiguous | Negative traces starting verification before Assess/Prepare must be rejected. |
| I5 Legal/verification unordered overlap | expected preserved | ambiguous | conversion failed | ambiguous | True concurrency is not directly observable; require all interleavings, e.g. Configure before Legal Review. |
| I6 Loop body order | expected preserved | expected preserved | conversion failed | ambiguous | Check Configure before Inspect in every iteration. |
| I7 Minimum one iteration | expected preserved | expected preserved | conversion failed | ambiguous | Negative zero-iteration trace must be rejected. |
| I8 Sync before Release | expected preserved | expected preserved | conversion failed | ambiguous | Release before verification or before legal branch must be rejected. |
| I9 Archive after Release | expected preserved | expected preserved | conversion failed | ambiguous | Archive-before-Release trace must be rejected. |
| I10 Label uniqueness | expected preserved | ambiguous | conversion failed | ambiguous | Gateways/silent nodes may add unlabeled routing or duplicate visual labels. |

Discussion of required points:

- **True concurrency versus arbitrary interleaving:** POWL compiles the absence of ordering into Petri-net concurrency. BPMN may represent this with parallel gateways, but layout and gateway choice can reduce it to arbitrary interleaving or even forced ordering. Trace tests can detect lost interleavings but cannot prove true simultaneity.
- **Lack of edge between Optional Legal Review and verification:** The source explicitly does not order the optional-legal branch against the verification loop. A BPMN diagram may visually place one above/before the other, but that is layout, not semantics. The Petri-net/BPMN should still allow interleavings such as Configure before Legal Review.
- **Silent optional behavior:** The XOR with `skip_legal` is silent. BPMN may render it as a default flow or an unlabeled exclusive gateway. This can be behaviorally correct while visually opaque.
- **Binary-loop semantics:** `LOOP(trial_body, correct_defect)` has at least one `trial_body` and uses `Correct Defect` as redo, not as a required final step. BPMN loop notation can easily suggest `Correct Defect` occurs after every iteration, including the last.
- **Join before Release Change:** Release requires both the optional-legal branch and the verification loop. BPMN must use an AND-join/parallel merge conceptually; drawing it as an XOR merge would lose synchronization.
- **Activity-label uniqueness:** Source labels are unique per distinct visible activity. BPMN gateways, event labels, or duplicated activity names can introduce ambiguity.
- **Initial and final markings:** BPMNPetri round trips may return `None` markings or different final markings. Any accepted trace must reach exact final marking equality.
- **Gateway or routing-node ambiguity in BPMN visualization:** Diamonds with `+`, `X`, or unlabeled gateways can be misread. The visual artifact is not proof of semantic equivalence.

# 5. Round-Trip Validation Code

This is a continuation after Section 3. The bounded exploration hides transitions whose label is `None`, requires exact final-marking equality for completed traces, bounds silent steps to avoid silent cycles, and bounds visible length and repeated labels. It is exhaustive only under the stated bounds, not for unbounded loop iterations.

# ===== Round-trip validation =====

BASE_NET = (net_from_powl, im_from_powl, fm_from_powl)


def marking_key(marking):
    return tuple(
        sorted(
            (str(getattr(p, "name", None) or id(p)), int(c))
            for p, c in marking.items()
            if c > 0
        )
    )


def transition_label(t):
    lab = getattr(t, "label", None)
    if lab is None or lab == "":
        return None
    return str(lab)


def fire_transition(net, marking, transition):
    new = dict(marking)

    for arc in net.arcs:
        if arc.target == transition:
            w = getattr(arc, "weight", 1)
            w = 1 if w is None else int(w)
            src = arc.source
            new[src] = new.get(src, 0) - w
            if new[src] < 0:
                raise ValueError("transition not enabled")

    for arc in net.arcs:
        if arc.source == transition:
            w = getattr(arc, "weight", 1)
            w = 1 if w is None else int(w)
            tgt = arc.target
            new[tgt] = new.get(tgt, 0) + w

    return {p: c for p, c in new.items() if c > 0}


def bounded_visible_traces(
    net,
    im,
    fm,
    max_visible_len=16,
    max_silent_steps=10,
    max_steps=3000,
    max_label_count=4,
):
    fm_key = marking_key(fm)
    accepted = set()
    seen = set()

    # stack item: marking, visible trace, silent steps since last visible, total steps, label counts
    stack = [(dict(im), (), 0, 0, {})]

    while stack:
        marking, vtrace, silent_steps, steps, label_counts = stack.pop()

        if steps > max_steps:
            continue

        key = (marking_key(marking), vtrace, silent_steps)
        if key in seen:
            continue
        seen.add(key)

        if marking_key(marking) == fm_key:
            accepted.add(vtrace)
            continue

        if len(vtrace) > max_visible_len:
            continue

        for t in pm4py.get_enabled_transitions(net, marking):
            lab = transition_label(t)

            new_vtrace = vtrace
            new_silent = silent_steps + 1
            new_counts = label_counts

            if lab is None:
                if silent_steps + 1 > max_silent_steps:
                    continue
            else:
                new_silent = 0
                if len(vtrace) + 1 > max_visible_len:
                    continue
                new_counts = dict(label_counts)
                new_counts[lab] = new_counts.get(lab, 0) + 1
                if new_counts[lab] > max_label_count:
                    continue
                new_vtrace = vtrace + (lab,)

            try:
                new_marking = fire_transition(net, marking, t)
            except Exception:
                continue

            stack.append(
                (new_marking, new_vtrace, new_silent, steps + 1, new_counts)
            )

    return accepted

        g = getattr(rg, "graph", rg)
        nodes = len(getattr(g, "nodes", []))

        return {"type": str(type(rg)), "nodes": nodes, "edges": edges}

# 6. Visual-Semantics Review

A BPMN diagram can be behaviorally acceptable in the underlying converted net but still be misread visually.

- **Parallel gateways:** A `+` gateway should indicate true concurrency. If the layout places optional legal review and verification in a vertical sequence, viewers may wrongly infer an ordering that the model does not have.
- **Exclusive gateways:** The optional Legal Review branch may appear as an `X` gateway with one visible path and one unlabeled/default path. Without annotation, viewers may think Legal Review is mandatory or that the silent path is an error.
- **Loop visualization:** The verification loop may be drawn as a backward edge from Correct Defect to Configure Trial. This can imply Correct Defect is required after every iteration, including the last. The source semantics require at least one ConfigureInspect iteration and allow Correct Defect only as a redo step between iterations.
- **Silent routing nodes:** BPMN gateways and default flows are not activities. A correct conversion may introduce unlabeled routing nodes that do not correspond to visible work. These should not be interpreted as missing activities.
- **Apparent ordering from graph layout:** Left-to-right or top-to-bottom placement is not control flow. In particular, Optional Legal Review may be drawn before verification even though the model allows interleaving.
- **Join before Release Change:** The join before Release must synchronize the optional-legal branch and the verification loop. If rendered as an exclusive merge, Release may appear to wait for only one branch.
- **Activity-label uniqueness:** Visible activity labels should remain unique for distinct activities. If BPMN duplicates labels or adds gateway labels, documentation should map them back to the POWL source.

Recommended annotations/documentation:

- Add a BPMN text annotation: “Optional Legal Review and verification are unordered; both must complete before Release Change.”
- Label the default/silent legal path: “skip Legal Review.”
- Annotate the loop: “At least one Configure Trial  Inspect Trial. Correct Defect separates iterations and is not required after the final iteration.”
- Annotate the join before Release: “AND-join: optional-legal branch and verification loop must both complete.”
- Keep a separate semantic invariant appendix with the table from Section 1.
- Use BPMN documentation fields on gateways to state whether they are XOR, AND, or loop routing.

# 7. Rejection Criteria

A conversion result should be rejected or quarantined if any of the following holds:

1. BPMNPetri conversion returns `None` initial or final marking, so the net is not accepting.
2. `pm4py.check_is_workflow_net(net)` is false or `pm4py.check_soundness(net, im, fm)` fails/returns unsound.
3. A required positive witness is rejected, especially an interleaving where Configure Trial occurs before Legal Review.
4. A negative witness is accepted, especially Release Change before verification, Release before legal completion, Archive before Release, or Inspect before Configure.
5. Optional legal behavior collapses: no accepted trace without Legal Review, or Legal Review is forced before Assess Risk.
6. Loop semantics change: zero verification iterations are accepted, Correct Defect is required after the final iteration, or silent cycling is unbounded/uncontrolled.
7. Synchronization before Release is lost: Release can occur before both optional-legal completion and verification-loop completion.
8. Activity-label uniqueness is broken: two distinct source activities map to the same visible label, or a visible source activity becomes silent.
9. Exact-final-marking validation fails: a completed trace reaches a marking different from the specified final marking.
10. Round-trip drift appears: the BPMN round-tripped net has a different bounded visible-trace set or different soundness/footprint/reachability evidence from `net_from_powl`.

# 8. Canonical Representation Recommendation

- **Authoritative representation for storage:** The source POWL is authoritative. It preserves strict partial order, optional XOR with silent skip, loop scope, and synchronization before Release without relying on BPMN layout. If serialization stability is a concern, store the serialized POWL plus a content-addressed, validated accepting Petri net as an executable derivative.
- **Stakeholder visualization:** Use BPMN generated from the authoritative POWLPetri pipeline, with annotations. BPMN is derivative and should not be manually edited as the source of truth.
- **Derivative artifacts:** BPMN diagrams, process-tree intermediates, round-trip Petri nets, reachability graphs, footprint reports, and visualizations are all derivative.
- **Validation evidence for derivatives:** Each derivative should carry PM4Py version, conversion pipeline version, workflow-net result, soundness result, bounded trace comparison, positive/negative witness results, exact-final-marking checks, and the stated bounds.
- **Process-tree intermediate:** Allow it only as an optional visualization or diagnostic. If `pm4py.convert_to_process_tree(...)` fails, record that as a valid result. If it succeeds but loses interleavings, optionality, loop scope, or synchronization, quarantine it as an approximation, not as canonical.
- **Avoiding round-trip drift:** Future edits should be made in the authoritative POWL. Regenerate all Petri nets, BPMN models, process trees, and reports from that source. Do not round-trip BPMN back into the canonical model unless the result is revalidated against the full invariant suite.

# 9. Residual Uncertainty

Even if every proposed test passes, the following cannot be established:

1. **Unbounded loop equivalence:** Bounded exploration cannot prove equivalence for arbitrarily many verification iterations or silent-loop behavior beyond the chosen bound.
2. **True concurrency:** Trace-based validation can observe interleavings but cannot prove that the model truly permits simultaneous execution rather than merely accepting all interleavings.
3. **Stakeholder interpretation:** A BPMN diagram may be behaviorally equivalent but visually misread. Tests cannot guarantee that viewers interpret gateways, loops, and silent routing correctly.
4. **Converter correctness:** Successful PM4Py conversions do not prove that the converter has no hidden semantic assumptions or version-specific behavior.
5. **Unspecified business semantics:** The source POWL does not model data conditions, resource constraints, cancellation, error handling, or organizational responsibilities. No conversion can validate those unstated concerns.
6. **Exact final-marking completeness:** The bounded check verifies exact final marking only for explored traces. It is not an exhaustive proof over all reachable markings.
7. **Silent-trace identity:** Hiding `` merges traces that may be different internally. The tests may not distinguish a correct silent skip from an accidentally omitted optional branch if both yield the same visible trace set.
