## 1. Modeling assumptions

- **Object types and capitalization**  
  I use PascalCase object types, as this is readable and common in OCEL-style modeling:
  - `Order`
  - `Item`
  - `Package`
  - `Delivery`
  - `Invoice`
  - `Payment`

- **E2O qualifier vocabulary**  
  The event-to-object qualifiers describe the role of an object in an event. I intentionally keep them lower-snake-case and semantically narrow:

  | Qualifier | Meaning |
  |---|---|
  | `created` | object created by the event |
  | `item_added` | item being added |
  | `order_updated` | order changed by adding an item |
  | `item_reserved` | item whose stock is reserved |
  | `order_reserved_for` | order for which stock is reserved |
  | `package_packed` | package being packed |
  | `item_packed` | item placed into a package |
  | `order_packed_for` | order whose items are packed |
  | `package_dispatched` | package being dispatched |
  | `delivery_used` | delivery used for dispatch |
  | `invoice_issued` | invoice issued |
  | `order_billed` | order billed by invoice |
  | `payment_recorded` | payment recorded |
  | `invoice_settled` | invoice receiving payment |
  | `delivery_confirmed` | delivery confirmed |
  | `order_closed` | order closed |

- **O2O direction conventions**  
  O2O rows are written as **source  target** with a qualifier that reads naturally from source to target:
  - `Order` **contains** `Item`
  - `Package` **packs** `Item`
  - `Delivery` **carries** `Package`
  - `Invoice` **bills** `Order`
  - `Payment` **partially_settles** or **completes_settlement** of `Invoice`

- **Directness of logistics and financial relations**  
  I model direct E2O links only where the operational event plausibly records that object directly:
  - Order-management events directly touch `Order` and `Item`.
  - Reservation and packing directly touch affected `Order`, `Item`, and `Package` objects because these are fulfillment events.
  - Dispatch and delivery confirmation directly touch `Package` and/or `Delivery`, but not `Order` or `Item`. Those broader links can be analytically propagated through O2O if desired.
  - Invoice issuance directly touches `Invoice` and billed `Order` objects.
  - Payments directly touch `Payment` and `Invoice`, but not `Order`, because the narrative gives no direct order-level payment allocation.

- **Preventing analytical propagation from being confused with source facts**  
  The `relations` table contains only observed/source-style E2O facts. The `o2o` table contains structural/master-data links. I do **not** inflate `relations` by traversing `o2o` and writing inferred event involvement as if it were observed. If an analyst wants propagated relations, they should be created as a separate derived artifact with a distinct qualifier namespace, for example `derived:affected_order`, not mixed into the source E2O vocabulary.

- **Version-dependent PM4Py assumption**  
  I assume a recent PM4Py-style OCEL constructor of the form:

  ```python
  OCEL(events=events, objects=objects, relations=relations, o2o=o2o)
  ```

  Some PM4Py versions may require positional arguments instead. The pipeline isolates this constructor call and provides a small fallback without changing the data semantics.

**Order flattening**

Approximate trace shapes:

- `O100`:  
  `Create Order`  `Add Item`  `Add Item`  `Reserve Stock`  `Pack Package`  `Pack Package`  `Issue Invoice`  `Close Order`

- `O200`:  
  `Create Order`  `Add Item`  `Reserve Stock`  `Pack Package`  `Issue Invoice`  `Close Order`

Copied shared events:

- `E06 Reserve Stock` appears in both order traces.
- `E07 Pack Package` appears in both order traces.
- `E11 Issue Invoice` appears in both order traces.

Omitted lifecycle aspects:

- Dispatch events `E09` and `E10` are omitted because they are linked to packages and deliveries, not directly to orders.
- Delivery confirmation events `E13` and `E14` are omitted.
- Payment events `E12` and `E15` are omitted because payments are linked to invoice `V1`, not directly to orders.

Likely DFG edges:

- `Create Order`  `Add Item`
- `Add Item`  `Add Item`
- `Add Item`  `Reserve Stock`
- `Reserve Stock`  `Pack Package`
- `Pack Package`  `Pack Package`

Misleading interpretations:

- Payment amounts are event attributes, not control-flow information.
- There is no direct payment-to-order allocation in the model, so Payment flattening cannot answer order-level settlement questions.

## 6. Modeling alternatives

**Alternative 1: Source-minimal E2O relations**

Policy:

- Link each event only to objects explicitly mentioned in the event description.
- For example, `Pack Package P1 with I1 and I3` would link only to `P1`, `I1`, and `I3`, not to `O100` or `O200`, unless the source system explicitly recorded order identifiers.

Effect:

- Flattened Order traces would become shorter.
- Order traces might omit packing, dispatch, or even reservation depending on what is considered explicit.
- Object-centric graphs would still show structural links through O2O, but flattened traditional logs would be less end-to-end.
- This reduces relation inflation but can make operational monitoring by order less useful.

**Alternative 2: Full operational involvement**

Policy:

- Add direct E2O links from downstream events to all operationally affected objects.
- For example, dispatching `P1` would also relate directly to `I1`, `I3`, `O100`, and `O200`.
- Payments could be allocated to orders using a business rule, such as proportional allocation.

Effect:

- Flattened Order traces would become full end-to-end order logs, including logistics and payments.
- DFGs would show a more complete order lifecycle.
- However, the model would risk treating inferred or derived knowledge as observed source data.
- Payment allocation could become misleading if the source system does not actually allocate payments to orders.

**Alternative 3: O2O-propagated analytical relations with provenance**

Policy:

- Keep the source E2O table lean and faithful to observed events.
- Create a separate derived relation set for analytical propagation, using qualifiers such as `derived:affected_order` or `derived:affected_item`.
- Keep derived relations separate from source relations or store them in an analytical copy of the OCEL.

Effect:

- Analysts can choose between a source-faithful view and an enriched end-to-end view.
- Discovery results can be made richer without confusing inferred links with observed facts.
- This supports auditability and reproducibility.
- It also makes explicit that, for example, a delivery’s connection to an order is inferred through package-item-order relations rather than directly observed in the delivery confirmation event.

## 7. Failure modes

1. **Relation inflation**  
   Adding every possible ancestor object to every event can make traces dense and noisy. For example, linking every delivery confirmation to all orders and items would make flattened Order logs contain logistics events that were not directly observed at order granularity. Discovery may then overstate synchronization and hide object autonomy.

2. **Missing direct E2O links**  
   If a direct link is omitted where it should exist, flattening will omit important lifecycle steps. For example, if `Pack Package` were not linked to `O100`, the flattened Order view would miss a fulfillment step that the business user expects to see.

3. **Treating O2O propagation as observation**  
   O2O relations such as `Package packs Item` and `Order contains Item` are structural facts. If we traverse them and write inferred event involvement into `relations` without provenance, we confuse master data with event observations. This can produce misleading conformance and performance results.

4. **Duplicate shared events after flattening**  
   Shared events such as `Reserve Stock`, `Pack Package` for `P1`, and `Issue Invoice` appear in multiple flattened object traces. This is expected in OCEL flattening, but it can create artificial edge counts, apparent loops, or false synchronization if interpreted as a traditional event log.

5. **Ambiguous payment allocation**  
   `M1` and `M2` settle `V1`, but the model does not allocate them to `O100` or `O200`. Any order-level payment allocation would be an assumption. Flattened Order views therefore cannot answer questions about order-level payment completion without adding derived relations.

6. **Overly short Payment traces**  
   Flattening on `Payment` produces singleton traces for `M1` and `M2`. This gives almost no control-flow insight. The settlement process is better analyzed by flattening on `Invoice` or by using object-centric discovery.

7. **Constructor/API version mismatch**  
   PM4Py versions may differ in OCEL constructor signatures, flattening return types, or discovery function names. If the constructor or discovery calls are changed without preserving semantics, the dataset may no longer represent the same OCEL. The pipeline isolates the constructor fallback and keeps the DataFrames unchanged.

8. **False total order for same-time events**  
   If two events have identical timestamps, sorting may impose an arbitrary order. This example has no timestamp ties, but in general OCEL pipelines must be careful not to interpret tie-broken order as true precedence. Timestamp ties should be handled explicitly or annotated.

9. **Activity-name aggregation hiding object identity**  
   Activities such as `Add Item`, `Pack Package`, and `Record Payment` are reused for different objects. In flattened DFGs, this can hide the fact that different items, packages, or payments are involved. Object-centric views or event attributes are needed to avoid oversimplification.
