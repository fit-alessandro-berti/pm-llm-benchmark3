# 3. Conservative Candidate

**Inductive-Bias Statement:**
The conservative model prioritizes **precision over generalization**. It assumes that unobserved interleavings of the core activities (`Credit Check`, `Engineering Review`, `Supplier Confirmation`, `Expedite Review`) are risky or invalid. It explicitly enumerates the 7 observed variants to ensure 100% fitness on the training data while admitting zero unobserved behavior within the core block. This approach avoids assuming concurrency where variable sequence might exist.

**Formal Expression:**
`Start -> XOR(Variant_1, ..., Variant_7) -> Approve -> Release -> End`
Where each Variant is a strict sequence of the middle activities as observed.

**Behavior Deliberately Excluded:**
1.  `Expedite Review` occurring before `Credit Check`.
2.  `Supplier Confirmation` occurring before `Register Order` (impossible) or after `Approve Configuration`.
3.  Any interleaving of `Credit Check`, `Engineering Review`, and `Supplier Confirmation` not explicitly listed in the 7 variants (e.g., `SC, ER, CC`).

**Known Underfitting Risks:**
1.  **Scalability:** Adding an 8th variant requires modifying the model structure.
2.  **False Negatives:** Legitimate but unobserved parallel executions (e.g., `SC` starting while `CC` is running) are rejected.
3.  **Noise Sensitivity:** If a trace deviates slightly due to logging noise, fitness drops to 0 for that trace.

# 4. Balanced Candidate

**Inductive-Bias Statement:**
The balanced model seeks the **most plausible generalization** consistent with stakeholder input (S2, S6) and data patterns. It interprets the variable ordering of `Credit Check` and `Engineering Review` as true concurrency (Parallel). It treats `Supplier Confirmation` as loosely coupled (parallel to checks) but acknowledges the dependency on information (modeled as parallel due to POWL limitations with OR-joins). `Expedite Review` is constrained to follow both Checks (D6). This model manages uncertainty by allowing unobserved interleavings that are logically sound.

**Decision Logic:**
*   **CC vs ER:** Modeled as Parallel (`CC || ER`) due to DFG loops and S2.
*   **SC:** Modeled as Parallel to Checks (`SC || (CC || ER)`) because it appears before and after ER in data (V5 vs V1), and S5 says "after either".
*   **Expedite:** Modeled as dependent on `CC` and `ER` (edges `CC->Exp`, `ER->Exp`) per D6, but parallel to `SC`.
*   **Formalism:** POWL is used to express these partial order constraints precisely without forcing a tree structure.

**Formal Expression:**
`POWL Graph G = (V, E)`
`V = {R, CC, ER, SC, Exp, AC, RP, Arc}`
`E = { (R,CC), (R,ER), (R,SC), (CC,Exp), (ER,Exp), (CC,AC), (ER,AC), (SC,AC), (Exp,AC), (AC,RP), (RP,Arc) }`

**PM4Py Code:**
```python
from pm4py.objects.powl.obj import StrictPartialOrder, Transition

# Initialize POWL
model_balanced = StrictPartialOrder()

# Add Transitions
activities = ["Register Order", "Credit Check", "Engineering Review", 
              "Supplier Confirmation", "Expedite Review", "Approve Configuration", 
              "Release Production", "Archive Case"]

transitions = {name: Transition(name) for name in activities}
for t in transitions.values():
    model_balanced.order.add_node(t)

# Add Edges (Dependencies)
edges = [
    ("Register Order", "Credit Check"),
    ("Register Order", "Engineering Review"),
    ("Register Order", "Supplier Confirmation"), # Loosely coupled
    ("Credit Check", "Expedite Review"),         # D6: Exp after CC
    ("Engineering Review", "Expedite Review"),   # D6: Exp after ER
    ("Credit Check", "Approve Configuration"),
    ("Engineering Review", "Approve Configuration"),
    ("Supplier Confirmation", "Approve Configuration"),
    ("Expedite Review", "Approve Configuration"),
    ("Approve Configuration", "Release Production"),
    ("Release Production", "Archive Case")
]

for src, tgt in edges:
    model_balanced.order.add_edge(transitions[src], transitions[tgt])
```

**Behavior Deliberately Excluded:**
1.  `Expedite Review` before `Credit Check` or `Engineering Review` (Violates D6).
2.  `Approve Configuration` before `Supplier Confirmation` (Violates D4).
3.  `Release Production` before `Approve Configuration` (Violates D2).

**Known Underfitting Risks:**
1.  **SC Dependency:** Allows `SC` before `CC`/`ER` (via `R->SC`), which technically violates S5 ("after either"), but POWL lacks OR-join.
2.  **Expedite/SC Order:** Allows `Exp` and `SC` in any order (observed both ways), but doesn't enforce if specific conditions dictate one.

# 5. Permissive Candidate

**Inductive-Bias Statement:**
The permissive model maximizes **generalization** to support exploration and compliance checking against broad rules. It assumes that unless a constraint is High Confidence (D1, D2, D3), the order is flexible. It treats `Credit Check`, `Engineering Review`, `Supplier Confirmation`, and `Expedite Review` as a fully parallel block (`AND`), relaxing the D6 constraint on `Expedite Review` to test if it is truly enforced or just observed habit. This model is suitable for conformance checking to detect deviations from even the relaxed norms.

**Boundary Definition:**
*   **Reasonable Generalization:** Any interleaving of the "Review/Confirmation" cluster.
*   **Forbidden:** Skipping `Register Order`, `Approve Configuration`, or `Archive Case`. Reordering `Approve` -> `Release`.
*   **Relaxed:** `Expedite Review` position (allowed before Checks in this model to test D6 validity).

**Formal Expression:**
`->(Register Order, AND(Credit Check, Engineering Review, X(Supplier Confirmation, tau), X(Expedite Review, tau)), Approve Configuration, Release Production, Archive Case)`

**PM4Py Code:**
```python
import pm4py

# ProcessTree with AND split for maximum flexibility in the middle block
# X(Activity, tau) makes the activity optional
tree_string_permissive = """
->(
    'Register Order',
    &(
        'Credit Check',
        'Engineering Review',
        X('Supplier Confirmation', tau),
        X('Expedite Review', tau)
    ),
    'Approve Configuration',
    'Release Production',
    'Archive Case'
)
"""

model_permissive = pm4py.parse_process_tree(tree_string_permissive)
```

**Behavior Deliberately Excluded:**
1.  `Archive Case` before `Release Production`.
2.  Missing `Register Order`.
3.  Missing `Approve Configuration` (Required for `Release Production`).

**Known Underfitting Risks:**
1.  **Over-generalization:** Admits `Expedite Review` before `Credit Check`, which likely violates safety/compliance (D6).
2.  **SC Timing:** Admits `Supplier Confirmation` before `Register Order`? No, blocked by tree structure. But admits `SC` after `Approve`? No, blocked by tree.
3.  **Precision:** Low precision on the 30 traces because it admits many paths not seen (e.g., `Exp` first in block).

# 9. Recommendation and Data-Collection Plan

**Recommendation:**
*   **Immediate Use:** **`model_balanced` (POWL)**. It offers the best trade-off between precision and generalization. It respects the high-confidence rules (D1-D4) and the most plausible stakeholder explanation for the DFG loops (S2: Parallelism). It is robust to the missing `Supplier Confirmation` events.
*   **Sensitivity Analysis:** **`model_permissive`**. Use this to run conformance checking. If many cases deviate from the Balanced model but fit the Permissive one, it indicates process drift. If cases fit neither, it indicates data quality issues or violations of D2 (Release before Approve).

**Data-Collection Plan to Resolve Ambiguities:**
1.  **Lifecycle Timestamps:** Collect `start_timestamp` and `complete_timestamp` for all activities.
    *   *Why:* To distinguish true concurrency (overlapping intervals) from fast sequential execution (S7). This validates S2 vs S1.
2.  **Case Attribute: `Component_Type`:** Export `Stocked` vs `External`.
    *   *Why:* To distinguish logical optionality (S4) from technical missingness (S5). If `Stocked` cases align perfectly with missing `Supplier Confirmation`, S5 is disproven.
3.  **Resource/Role ID:** Capture who performed `Credit Check` and `Engineering Review`.
    *   *Why:* If different resources perform them simultaneously, it confirms parallelism. If the same resource does both, it implies sequence.
4.  **Expedite Trigger:** Log the *reason* for `Expedite Review`.
    *   *Why:* To understand if D6 is a hard rule or a rare exception pattern.

# 10. Uncertainty Statement

**Confidence Assessment:**
*   **Start/End Flow (D1, D2):** **High Confidence.** Data is consistent (30/30).
*   **Parallelism of Checks (S2):** **Medium-High Confidence.** Supported by DFG loops and stakeholder explanation, but cannot be proven without start timestamps.
*   **Supplier Confirmation Optionality:** **Medium Confidence.** Data shows 23% missing. S4/S5 offer conflicting explanations (Logic vs Error). We model as optional but flag for audit.
*   **Expedite Review Constraints (D6):** **Low-Medium Confidence.** Only 2 observed cases. Relying heavily on stakeholder statement S6.

**Alternative Interpretation:**
If **S1 (Finance)** is correct and `Credit Check` *must* precede `Engineering Review`, then the 11 traces showing `ER` before `CC` are either logging errors (S7 ingestion index) or policy violations.
*   *Material Change:* This would invalidate the parallelism assumption in `model_balanced`. The model would need to change to a strict sequence `CC -> ER`, classifying the 11 traces as deviations (noise). This would significantly increase the "deviation" rate in conformance checking and might require a data cleaning step before process analysis.
