# 1. Executive Verdict

This net is **structurally a workflow net** (unique source/sink, all nodes on a source-to-sink path), but it is **not sound** due to a critical behavioral defect. The principal defect is that the waiver path (`t_waive_review`) bypasses the mandatory analysis synchronization entirely, allowing `t_authorize` to fire prematurely if the waiver branch completes before the analysis branch. The business consequence is that cases may be authorized without completing the required analysis, violating the core policy that "Authorization may occur only after the analysis and whichever review outcome are both complete."

---

# 2. Structural Diagnosis

| Element or subnet               | Intended role                                                                 | Actual structural effect                                                                                     | Potential symptom                                                                                     |
|---------------------------------|------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| **Split (`t_split`)**           | Fork analysis and review branches in parallel.                               | Correctly splits into two branches (`p_analysis` and `p_review`).                                           | No structural issue.                                                                                 |
| **Analysis branch**             | Mandatory analysis path (`p_analysis`  `t_analyze`  `p_analysis_done`).    | Correctly enforces sequential analysis.                                                                   | No structural issue.                                                                                 |
| **Review branch**               | Optional review: standard (`t_standard_review`) or waiver (`t_waive_review`). | Both paths are structurally valid, but waiver path lacks synchronization with analysis.                     | Premature authorization possible if waiver completes before analysis.                                  |
| **Normal join (`t_join_normal`)**| Synchronizes analysis and standard review.                                    | Correctly joins `p_analysis_done` and `p_review_done`.                                                    | No structural issue.                                                                                 |
| **Waiver join (`t_join_waived`)**| Synchronizes analysis and waiver.                                            | **Defect**: Only synchronizes `p_waived` with `p_decision`; no explicit synchronization with `p_analysis_done`. | Waiver path can reach `p_decision` without analysis completion.                                       |
| **Initial/final markings**      | `im` has 1 token in `source`; `fm` has 1 token in `sink`.                   | Correct for workflow net.                                                                                   | No structural issue.                                                                                 |
| **Source-to-sink paths**        | All nodes must lie on a path from `source` to `sink`.                       | All nodes except `p_decision` lie on such paths. `p_decision` is reachable but not all paths lead to `sink`. | **Defect**: `p_decision` can accumulate tokens if analysis is pending, violating soundness.             |

# 3. Marking-Based Counterexample

### Firing Sequence (Waiver Path):
1. `t_register` (creates token in `p_ready`).
2. `t_split` (tokens in `p_analysis` and `p_review`).
3. `t_analyze` (token moves to `p_analysis_done`).
4. `t_waive_review` (token moves to `p_waived`).
5. `t_join_waived` (token moves to `p_decision`).
6. **`t_authorize` is now enabled** (token in `p_decision` and analysis token still in `p_analysis_done`).
   - Firing `t_authorize` moves the `p_decision` token to `sink`, but the `p_analysis_done` token remains.
   - **Result**: `sink` has 1 token, but `p_analysis_done` still has 1 token  **not `fm`**.

### Marking Table:

| Step               | Fired transition       | Resulting nonzero marking                     | Enabled transitions                          | Observation                                                                                     |
|--------------------|-------------------------|-----------------------------------------------|---------------------------------------------|-------------------------------------------------------------------------------------------------|
| 0                  | -                       | `{source: 1}`                                | `{t_register}`                              | Initial marking.                                                                                 |
| 1                  | `t_register`           | `{p_ready: 1}`                                | `{t_split}`                                 | Token moves from `source` to `p_ready`.                                                     |
| 2                  | `t_split`              | `{p_analysis: 1, p_review: 1}`                | `{t_analyze, t_standard_review, t_waive_review}` | Parallel branches created.                                                                   |
| 3                  | `t_analyze`            | `{p_review: 1, p_analysis_done: 1}`           | `{t_standard_review, t_waive_review, t_join_normal}` | Analysis completes; review branch still active.                                               |
| 4                  | `t_waive_review`       | `{p_analysis_done: 1, p_waived: 1}`           | `{t_join_waived, t_join_normal}`             | Waiver completes; `t_join_waived` is enabled but `t_join_normal` is not (analysis not joined). |
| 5                  | `t_join_waived`        | `{p_decision: 1, p_analysis_done: 1}`         | `{t_authorize}`                             | **Defect**: `t_authorize` is enabled despite pending analysis.                                  |
| 6                  | `t_authorize`          | `{sink: 1, p_analysis_done: 1}`               | `{}`                                        | **Defect**: Final marking `fm` not reached; leftover token in `p_analysis_done`.                 |

### Why Leftover Token Cannot Be Consumed:
- After `t_authorize`, the token in `p_analysis_done` has no outgoing arcs to consume it. The net lacks a mechanism to force synchronization of the waiver path with the analysis path.

# 4. Minimal-Repair Alternatives

| Repair                          | Exact edits                                                                                                                                                                                                 | Edit cost (arcs/places/transitions) | Preserved intent                                                                                     | Changed behavior                                                                                     | New risk                                                                                              |
|---------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------|------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| **Repair A: Waiver into Normal Join** | Add arc from `p_waived` to `t_join_normal`; remove `t_join_waived` and `p_decision` (merge into `p_decision` via `t_join_normal`).                                                                                     | -1 transition, -1 place, +1 arc   | Analysis remains mandatory; waiver and standard review are symmetric in synchronization.            | Waiver path now synchronizes with analysis via `t_join_normal`.                                       | None; all paths now enforce analysis completion.                                                     |
| **Repair B: Dedicated Waiver Join** | Add a new transition `t_join_waiver` with two input arcs: `p_analysis_done` and `p_waived`. Replace `t_join_waived` with `t_join_waiver`; update `p_decision` arcs.                                      | +1 transition, +1 arc             | Analysis remains mandatory; waiver path explicitly synchronizes with analysis.                       | Waiver path now requires analysis completion before joining.                                          | Slightly more complex net, but clearer intent.                                                       |
| **Repair C: Optional Analysis**  | Remove arc `p_ready  t_split`; add arc `p_ready  t_analyze` and `p_ready  t_review_split` (new transition). Modify waiver path to bypass analysis entirely. **Policy change**: Analysis is optional under waiver. | +1 transition, +2 arcs, -1 arc     | Waiver path no longer requires analysis.                                                             | Violates business intent; analysis is no longer mandatory.                                            | High risk of policy violation.                                                                     |

**Justification of Minimality**:
- **Edit-cost model**: Cost is defined as the sum of added/removed arcs, places, and transitions. Repair A and B are minimal (cost  2), while Repair C is more invasive (cost  3) and changes the policy.
- **Behavioral distinctness**: Repair A and B differ in how they synchronize the waiver path:
  - Repair A merges the waiver path into the normal join, making the net simpler but less explicit.
  - Repair B adds a dedicated join, making the synchronization explicit but slightly more complex.
- **Preservation of intent**: Both Repair A and B retain the mandatory analysis requirement, while Repair C does not.

# Places

p_ready = PetriNet.Place("p_ready")

p_analysis_done = PetriNet.Place("p_analysis_done")

for p in {source, p_ready, p_analysis, p_review, p_analysis_done,
          p_review_done, p_waived, p_decision, sink}:
    repaired_net.places.add(p)

register = PetriNet.Transition("t_register", "Register Case")

for t in {register, split, analyze, standard_review, waive_review, join_normal, authorize}:
    repaired_net.transitions.add(t)

petri_utils.add_arc_from_to(p_ready, split, repaired_net)
petri_utils.add_arc_from_to(split, p_analysis, repaired_net)
petri_utils.add_arc_from_to(split, p_review, repaired_net)

petri_utils.add_arc_from_to(p_review, waive_review, repaired_net)
petri_utils.add_arc_from_to(waive_review, p_waived, repaired_net)

petri_utils.add_arc_from_to(p_analysis_done, join_normal, repaired_net)

# 7. Repair Trade-Offs and Residual Risks

- **Distinguishability of Waiver/Standard Review**:
  - Repair A merges the waiver path into the normal join, so the two review types are no longer structurally distinguishable in the net. This may obscure auditability but enforces the policy.
  - Repair B keeps them distinct, making it easier to track which review type was used.

- **Silent Transitions or Duplicate Behavior**:
  - Neither repair introduces silent transitions. Repair A is slightly more compact but less explicit about the waiver path's synchronization.

- **Soundness  Business Alignment**:
  - Soundness ensures no tokens are left after reaching the sink, but it does not guarantee that all business rules are enforced. For example, a net could be sound but allow analysis to be skipped if the waiver path is taken (as in Repair C). Thus, **reachability analysis** (e.g., checking if `t_authorize` can fire before `t_analyze`) is critical.

- **Regression Testing**:
  - **Positive traces**: All paths where analysis and review complete before authorization.
  - **Negative traces**: Attempts to authorize without completing analysis (should fail).
  - **Edge cases**: Waiver after analysis completes, standard review after waiver (if allowed), and interleaved analysis/review steps.

- **Detecting Bypass of Mandatory Analysis**:
  - Use **PM4Py's reachability graph** to verify that `t_authorize` is never enabled until both `p_analysis_done` and the review path (standard or waiver) are satisfied.
  - **Runtime monitoring**: Log the order of transitions and flag cases where `t_authorize` fires before `t_analyze`.

# 8. Final Recommendation

**Primary Repair for Deployment: Repair A (Waiver into Normal Join)**
This repair is **minimal** (cost = 2), **preserves the business intent** (analysis is mandatory), and **simplifies the net** by eliminating the redundant `t_join_waived` and `p_decision` split. The trade-off is that the waiver path is no longer structurally distinct from the standard review path, but this is acceptable because the synchronization behavior is now correct. The net remains intuitive for modelers and auditors, as the join condition is explicit and uniform.

**Fallback Repair: Repair B (Dedicated Waiver Join)**
This repair is **more explicit** about the waiver path's synchronization with analysis, which may be preferable if auditability of waiver cases is a priority. The slightly higher cost (cost = 2) is justified by the clarity it provides. However, it is not chosen as the primary repair because the structural distinction adds complexity without a clear business benefit.

**Why Not Repair C?**
Repair C violates the core business rule that analysis is mandatory, even for waived cases. While it might reduce processing time in some scenarios, it introduces unacceptable risk and should never be deployed without explicit policy change.
