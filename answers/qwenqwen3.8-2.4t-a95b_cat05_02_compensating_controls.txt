## 1. Control-Objective Decomposition

FEP-1 should not be reduced to “two different user IDs appear in the log.” Its control objective is to prevent one human actor from causing an irrevocable, erroneous, or fraudulent payment without independent challenge. That objective decomposes into at least the following threat scenarios.

| # | Threat / control objective | AV-2 automated validation | MG-4 independent manager approval | RA-7 retrospective audit / recall | ED-1 emergency permission |
|---|---|---|---|---|---|
| 1 | **Single-operator fraud or error**: one person prepares and releases a payment without independent challenge. | Can prevent some known data anomalies, but cannot by itself establish independent human authorization. It does not detect collusion or compromised accounts. | Preventive if performed before release or before irrevocable settlement; detective if performed after release but still able to stop settlement. | Detective; corrective only if recall/recovery is still possible. | Permits single-operator only if all conditions are satisfied; otherwise it does not compensate. |
| 2 | **Duplicate or repeated erroneous payment**. | Strong preventive control for duplicate invoice detection, assuming service is available and not overridden. | Can detect duplicate support documents if manager actually reviews. | Can detect after release and support recall if timely. | Does not itself address duplicates; AV-2 pass remains required. |
| 3 | **Vendor bank-account substitution / account takeover / sanctions or bank-ownership risk**. | Preventive for covered checks: bank-account change, ownership, sanctions, operator limits. A warning is only useful if escalation is enforced. | Preventive/detective if manager independently validates bank details and supporting evidence before settlement. | Corrective only within recall window; after settlement recovery is uncertain. | Explicitly excludes recent bank-account changes; if this condition fails, ED-1 is not a valid compensating permission. |
| 4 | **Payment without goods/services received or without commercial reasonableness**. | Weak / fails: AV-2 does not establish receipt, performance, or commercial reasonableness. | Strong if manager reviews invoice, receipt/service evidence, and business rationale before release/settlement. | Detective; may identify missing receipt after payment. | Does not create receipt evidence. Emergency status does not substitute for proof of services. |
| 5 | **Collusion, repeated pairing, shared workstation, or rubber-stamp second actor**. | Fails: automated validation does not address human collusion or false attestation. | Only useful if manager/releaser is genuinely independent and performs real review. A conflicted or rubber-stamp approver fails. | Detective; can identify repeated pairing, shared workstation, or anomalous approval patterns later. | Fails if emergency token or single-operator path is abused by colluding actors. |
| 6 | **Override abuse / warning suppression**. | AV-2 warnings can be overridden; the control is only as strong as override governance. | Preventive if override requires an independent manager who reviews the warning. | Detective if overrides are audited timely. | ED-1 requires AV-2 pass without override; an overridden warning defeats ED-1 condition 5. |

## 2. Equivalence and Sufficiency Test

A compensating-control package should be evaluated against the causal chain:

**Prepare  Release  Bank Settlement / irrevocable loss  Recovery / audit.**

The relevant dimensions are:

1. **Timing**
   - Controls before release are stronger than controls after release.
   - Controls before bank settlement may still prevent irrevocable loss.
   - Controls after settlement are primarily detective and only weakly corrective.

2. **Independence**
   - The reviewer must not be the preparer/releaser.
   - Shared service accounts are not independent human actors.
   - Direct supervisory conflicts, shared credentials, repeated pairing, or shared workstations reduce independence.

3. **Coverage**
   - AV-2 covers duplicate, sanctions, bank-account ownership/change, limits, and basic PO match.
   - AV-2 does not cover receipt of goods/services, commercial reasonableness, collusion, or compromised-account control.

4. **Overrideability**
   - A warning that can be overridden by the same operator is weak.
   - Override by a preparer using another person’s credential is a severe independence and authentication failure.

5. **Recoverability**
   - Recall within approximately 24 hours may be corrective.
   - Audit after the recall window is detective, not corrective, unless exceptional recovery is still possible.

6. **Evidence quality**
   - Manager approval must be supported by evidence: invoice, bank details, receipt/service report, and rationale.
   - Unsigned checklists, missing token logs, missing settlement records, and missing workstation logs reduce assurance.

7. **Collusion resistance**
   - A nominal second user is insufficient if the pair is repeated, co-located, shared a workstation, or has a conflict of interest.
   - Monitoring patterns is necessary because individual cases may look formally compliant.

### Sufficiency categories

| Category | Meaning |
|---|---|
| **Fully equivalent / objective met** | The package prevents a single actor from causing irrevocable loss with assurance comparable to a genuine independent release. Typically requires independent approval before release or settlement, operational AV-2 without improper override, timely audit/recall capacity, and evidence resistant to collusion. |
| **Partially equivalent / technically nonconforming but tolerable** | The package materially reduces risk but has a gap: post-release but pre-settlement approval, uncertain emergency-token timing, low exposure, or detective controls that do not fully replace prevention. |
| **Merely mitigating** | Controls reduce impact or detect after the fact but cannot prevent the payment from being released or settled. Late audit, late manager ratification, or low amount may mitigate but do not establish equivalence. |
| **Ineffective / objective failed** | The control package fails on a material dimension: improper override, conflicted approval, AV-2 unavailable, no independent review before settlement, collusion evidence, or audit after recovery window. |
| **Indeterminate** | The evidence is insufficient to decide whether the control objective was met, even if nominal form appears satisfied. |

### Why “same expected loss” is not the only standard

Expected loss alone is insufficient because controls also provide:

- **Assurance**: prevention is more reliable than post-loss recovery.
- **Deterrence**: independent release increases perceived detection risk.
- **Timeliness**: recall after settlement is uncertain; prevention avoids dependency on recovery.
- **Accountability**: independent review creates evidence and responsibility.
- **Tail-risk protection**: low average loss does not justify exposure to rare high-impact fraud.
- **Control health**: repeated exceptions, overrides, or pairing patterns indicate decay even if no loss has yet occurred.

## 4. Preventive–Detective–Corrective Comparison

| Control | Primary timing | Preventive role | Detective role | Corrective role | Coverage strengths | Coverage limitations |
|---|---|---|---|---|---|---|
| **AV-2 automated validation** | Before release | Prevents or warns on covered data anomalies: duplicate invoice, sanctions, bank ownership, recent bank change, operator limit, basic PO match | Warning events reveal risk; block events reveal attempted defects | Does not recover funds; can stop completion if it blocks | Fast, scalable, consistent for structured checks | Does not prove receipt, commercial reasonableness, collusion resistance, or control of compromised accounts; can be overridden |
| **MG-4 independent manager approval** | Best before release; acceptable before irrevocable settlement under emergency logic | Preventive if manager can block release/settlement after real review | Detective if performed after release but before settlement, because it can identify a defect already initiated | Can be corrective if performed before settlement by stopping payment | Addresses invoice, bank details, receipt/service evidence, and business rationale if done properly | Depends on independence, competence, time, and evidence; rubber-stamping or conflicts defeat it |
| **RA-7 retrospective audit and recall** | After release, ideally within recall window | Not preventive unless audit occurs before settlement and can stop payment | Detective: identifies defects, fraud patterns, overrides, and control gaps | Partly corrective if recall/recovery is still possible, especially within 24 hours | Can identify systemic issues and support recovery | Late audit is weak; after settlement recovery is uncertain; audit quality depends on evidence |
| **ED-1 emergency single-operator permission** | Conditional permission surrounding prepare/release/settlement | Preventive only if all conditions constrain emergency use and preserve independent challenge | Can create audit trail for emergency exceptions | Does not itself correct; relies on RA-7 and recall | Allows business continuity under strict safeguards | If any condition fails, it becomes an unjustified exception rather than a compensating control |

### Manager action after Release_Payment but before Bank_Settlement

I treat this as a **hybrid control**:

- **Detective relative to Release_Payment**: the manager is reviewing an action that has already been performed by the preparer/releaser.
- **Preventive relative to irrevocable loss**: if the manager can still block bank settlement, the control can prevent the loss event.

For control-objective evaluation, the manager action should receive preventive credit only if there is credible evidence that the manager had stop authority, reviewed relevant evidence, and acted before settlement. If the manager merely ratifies after settlement, the control is detective only.

## 6. Evidence and Monitoring Recommendations

### Evidence collection

| Evidence area | Recommended evidence |
|---|---|
| Emergency tokens | Immutable token creation/activation timestamps, token owner, reason code, incident ticket linkage, and whether token was active before Prepare_Payment. |
| Manager approval | Review checklist, invoice ID, bank-detail validation, receipt/service evidence, approval timestamp, approval device, and explicit stop authority. |
| AV-2 validation | Full validation result, warning reason, override identity, override justification, credential used, and whether override was performed by the preparer. |
| Bank-account risk | Vendor bank-change history, bank-ownership validation, sanctions result, and evidence of confirmation with vendor through an independent channel. |
| Audit and recall | Audit start/end timestamps, auditor independence, recall request timestamp, bank response, and recovery result. |
| Workstation / identity | Workstation ID, concurrent session logs, credential issuance, shared-device indicators, and resource-pair history. |
| Organizational design | Documentation authorizing dedicated payment cells, rotation rules, segregation-of-duties matrix, and reporting lines. |

### Monitoring rules

| Metric / rule | Alert condition | Interpretation |
|---|---|---|
| **Same-user prepare/release rate** | Any completed payment with same preparer/releaser outside valid ED-1 conditions. | Strong exception signal; not proof of fraud by itself. |
| **Override rate** | AV-2 warning overridden, especially by preparer, using another user’s credential, or for bank-change/operator-limit warnings. | High-risk control degradation; credential misuse possible. |
| **Late manager approval** | Manager approval after release, after settlement, or beyond approved emergency window. | Reduces preventive value; may be detective only. |
| **Audit before recall window** | Audit not completed within approximately 24 hours of release for emergency same-user payments. | Loss of corrective recall capacity. |
| **Repeated resource pairs** | Same preparer/releaser pair above threshold over rolling 30 days, e.g. more than 5–10 payments, depending on volume. | Increased collusion or rubber-stamp risk; alert, not proof. |
| **Shared workstation / shared device** | Prepare and release events from same workstation or close temporal/device overlap. | Weakens independence; requires investigation. |
| **Bank-change proximity** | Payment to vendor with bank-account change in prior seven days, especially with AV-2 warning or override. | High account-takeover/fraud risk. |
| **Control outages** | AV-2 unavailable, unsigned manual checklist, or missing validation during release. | Preventive-control failure; should require compensating independent approval before settlement. |
| **Emergency token timing** | Token created or activated after Prepare_Payment. | Possible ED-1 precondition failure or logging defect. |
| **Amount threshold exceptions** | Emergency single-operator payment at or above EUR 100,000. | ED-1 condition failure; requires escalation. |

### Alert versus proof

An alert indicates increased risk or control weakness. It is not proof of misconduct. For example:

- Repeated u12/u13 pairing may be an approved dedicated cell or a collusion risk.
- A late emergency token may be a logging delay or a control bypass.
- An override may be legitimate escalation or credential misuse.

Investigation should seek independent evidence before concluding misconduct.

- The function may accept an event log, a dataframe, or both depending on version. The code converts the formatted dataframe to an event log but includes a fallback if the returned object is dataframe-like.
- Resource handling may vary, especially for `SYSTEM` or missing resources. The code explicitly fills missing resources with `SYSTEM` and treats identical resource intersections conservatively.
- The exact import path for filtering helpers may vary. The code first uses the requested top-level `pm4py.filter_four_eyes_principle`, then attempts a fallback import if needed.
- The 24-hour audit flag is a conservative proxy for “one business day” and does not encode a full business calendar.
