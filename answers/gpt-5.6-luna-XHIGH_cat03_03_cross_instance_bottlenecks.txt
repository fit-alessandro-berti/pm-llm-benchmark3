## 1. Interaction-graph description

The useful graph is a typed, time-aware object graph, not a graph of jobs alone. Its nodes are Jobs, Components, ComponentLots, Machines, Tools, Batches, Shipments, and event nodes. Event nodes are important because one event can connect many object types and can carry the timestamp needed to distinguish readiness, service, release, and policy effects.

The direct object-to-object edges include `Job -requires-> Component`, `ComponentLot -contains-> Component`, `Batch -batches-> Job`, and `Shipment -consolidates-> Job`. Direct event-to-object relations include the B1 `Batch Cure` relation to B1, OVEN-1, RACK-7, J1, J2, J3, C1, C2, and C3; the corresponding B2 event; the FIX-A acquisition/release relations; the L7 quarantine and release events; and the CAL-3 recalibration and test events. Qualifiers such as `requires`, `contains`, `batches`, `consolidates`, `uses`, `acquires`, `releases`, `quarantines`, and `releases-lot` should be retained rather than collapsed into an untyped “connected” edge.

A compact edge list is:

```text
J1-requires->C1, J2-requires->C2, J3-requires->C3,
J4-requires->C4, J5-requires->C5, J6-requires->C6
L7-contains->{C2,C5}; L8-contains->{C1,C3}
B1-batches->{J1,J2,J3}; B2-batches->{J4,J5}
S1-consolidates->{J1,J4}; S2-consolidates->{J2,J3};
S3-consolidates->{J5,J6}
E_B1_Cure(12:05)-relates->{B1,OVEN-1,RACK-7,J1,J2,J3,C1,C2,C3}
E_B2_Cure(14:50)-relates->{B2,OVEN-1,RACK-7,J4,J5}
E_FIX_A_release(11:40)-relates->{J3,FIX-A};
E_J4_process(11:45)-relates->{J4,C4,CNC-2,FIX-A}
E_L7_quarantine(10:20)-relates->{L7,C2,C5,J2,J5};
E_L7_release(13:50)-relates->{L7,C2,C5,J2,J5}
E_J5_test(16:10-16:35)-relates->{J5,TEST-1,CAL-3};
E_CAL_recal(16:35-17:20)-relates->{CAL-3,TEST-1?}
E_J6_test(17:25-17:50)-relates->{J6,TEST-1,CAL-3}
```

The last three lines should be read as event-object evidence; whether TEST-1 is explicitly related to the recalibration event is a data question, not an assumption. The first four groups are direct O2O or O2M observations. Edges such as `J1 waits-for J3`, `J4 waits-for J3/FIX-A`, `J5 waits-for L7 release`, `J6 waits-for CAL-3`, and `J1 waits-for J4/S1` are inferred dependency edges. They express a plausible enabling relationship, not a proven causal edge.

There are several higher-order motifs. First, the batch motif is `J1/J2/J3 -> C1/C2/C3 -> B1 -> OVEN-1 -> RACK-7`: three jobs become jointly exposed to one cure event, so a late member can create a synchronization barrier for early members. Second, the fixture motif is `J3 -> FIX-A <- J4`, embedded in `FIX-A -> CNC-2 -> Machine Process`: a tool held by one job can starve a machine that is otherwise idle. Third, the lot-release motif is `J2 -> C2 <- L7 -> C5 <- J5`, with L7 also connecting B1 and B2 indirectly; one quality state can affect jobs in different batches. Fourth, the shipment motif is `J1 -> S1 <- J4`, where the later packed job determines dispatch for the earlier packed job. Fifth, the testing motif is `J5/J6 -> CAL-3 -> TEST-1`, where recalibration of a shared tool leaves the machine idle. These motifs explain why each individual job can look ordinary while the object graph has long cross-instance paths.

## 2. Quantitative delay decomposition

These calculations are counterfactual decompositions, not causal estimates. Each requires the stated assumption about what would have happened if the implicated object or policy had been different.

1. For B1, J1’s readiness-to-cure interval is `12:05 - 08:10 = 3 h 55 min = 235 min`. If B1 could have started as soon as J1 was ready, with OVEN-1, RACK-7, and all other prerequisites available, 235 minutes is the maximum synchronization exposure for J1. The supplied table attributes this interval to batch synchronization, but it does not prove that no hidden prerequisite existed.

2. J2’s corresponding interval is `12:05 - 08:25 = 3 h 40 min = 220 min`. Under the same partial-batch counterfactual, J2 could have avoided up to 220 minutes. J1 and J2 together account for `235 + 220 = 455 minutes` of early-readiness waiting, while J3 waited only `12:05 - 11:55 = 10 minutes`. If the actual rule was “wait for all three,” the late readiness of J3 is a plausible trigger; if B1 had a fixed 12:05 start, that interpretation is weaker.

3. For B2, OVEN-1 is recorded idle from 12:55 to 14:50, or `115 minutes`. RACK-7 remains in cleaning/quarantine until 14:35, overlapping the first `14:35 - 12:55 = 100 minutes` of that idle interval. If RACK-7 had been available at 12:55 and the batch policy still required both jobs, the earliest plausible start would be when J5 became ready at 14:40, followed by the observed 10-minute start delay; this counterfactual removes up to 100 minutes of rack-related exposure, not necessarily all 115 minutes. A different scheduling or setup constraint could explain the residual 15 minutes.

4. J4 reaches CNC-2 at 09:50, while J3 holds FIX-A until 11:40 and J4’s process begins at 11:45. The interval from J4 arrival to process start is `115 minutes`; the direct overlap between the observed CNC idle interval and J3’s tool hold is `10:05-10:47 = 42 minutes`. The broader overlap from the start of the machine idle period to tool release is `10:05-11:40 = 95 minutes`, but the period 10:47-11:40 is not described as machine-idle, so it cannot be assigned to FIX-A with confidence. If FIX-A had been available and J4 were otherwise executable at 10:05, the process could have started then, implying a possible 100-minute reduction to the observed 11:45 start. The conservative evidence is at least 42 minutes of machine starvation plausibly coincident with the fixture hold.

5. L7 is quarantined at 10:20 and released at 13:50, an interval of `3 h 30 min = 210 minutes`. If J5 was otherwise ready at 10:20 and the lot gate was its only blocker, 210 minutes is the maximum plausible lot-induced exposure. No J5 readiness timestamp is provided, so the observed interval is a release-window duration, not a measured J5 wait. J2’s supervisor override further prevents treating L7 release as a necessary predecessor for J2.

6. J1 is packed at 13:30 and S1 dispatches at 19:25, so J1’s pack-to-dispatch wait is `5 h 55 min = 355 minutes`. S1’s last job, J4, is packed at 19:10 and dispatch occurs 25 minutes later. If J1 could ship alone with the same 25-minute handling interval as a counterfactual, it would dispatch at 13:55 and avoid `19:25-13:55 = 330 minutes`; with zero handling time, the upper bound is 355 minutes. This attributes the difference to consolidation only if J1 had no customer cutoff, documentation, or loading constraint of its own.

7. J6 is ready at 16:05 and tests at 17:25, a total of `80 minutes`. CAL-3 is occupied by J5 through 16:35 and recalibrated from 16:35 to 17:20, a direct unavailability interval of 45 minutes; the subsequent five minutes is a handoff or setup interval. If no recalibration were required between these tests and TEST-1 could begin J6 immediately after J5, J6 would plausibly start at 16:35, reducing its wait by 50 minutes. The remaining 30 minutes from J6 readiness to J5 completion reflects the other test already in progress, not the recalibration.

The ranking separates an operational dependency from a measurement dependency. The data artifact is highly credible as an explanation of why managers do not see the coupling, but it is not proof that the artifact created the waiting.

## 4. What flattening misses

The Job flattening makes each job’s activity sequence and aggregate duration visible. It hides cross-job readiness barriers, shared tool occupancy, lot state, and partner-dependent shipment dwell. Because lot events are not directly related to the Job in the extraction, it omits L7 quarantine and release altogether. It also duplicates a shared event once per related job or, depending on implementation, assigns it inconsistently. A misleading conclusion is that six ordinary-looking trajectories and no 1.8-standard-deviation outlier imply stable waiting performance.

The Machine flattening makes service events, utilization, and gaps for CNC-2, OVEN-1, and TEST-1 visible. It hides why a machine is starved: a fixture, rack, batch policy, lot release, or priority rule. A single batch cure can also look like ordinary machine service rather than a barrier for three jobs. The misleading DFG conclusion is that 44%-58% utilization rules out machine-related delay. It rules out sustained machine saturation, not tool-induced or policy-induced starvation.

The Batch flattening would make B1 and B2 membership, shared cure events, and batch-level duration visible. It hides each component’s lot status, job-specific readiness, tool contention outside the batch, and shipment consequences. If a batch event is copied to all member jobs, its frequency and apparent per-job duration can be inflated. A misleading conclusion is that the batch cure itself is short and therefore harmless; the barrier is the time before it starts.

The Tool flattening makes FIX-A, RACK-7, and CAL-3 acquisitions, releases, cleaning, and recalibration visible. It hides which waiting job was ready, which machine could have used the tool, and whether a hold was intentional. Inferred tool holds can also be duplicated for every related event. A misleading conclusion is either that the tool is lightly used because waits are unlogged, or that high tool occupancy alone proves every affected job was blocked.

The ComponentLot flattening makes L7’s contents, quarantine, release, and genealogy visible. It hides the operational consequence unless job-component and readiness links are joined. It can duplicate one lot event for C2 and C5, or make J2 appear released even though its supervisor override bypassed the ordinary gate. A misleading conclusion is that the lot had no job impact because the Job DFG contains no lot event.

The Shipment flattening makes three create-load-dispatch paths and their short load-to-dispatch medians visible. It hides already-packed jobs waiting for consolidation partners, shipment cutoff policy, and each job’s share of dispatch dwell. It may duplicate a shipment event for multiple jobs or collapse all partner waits into one shipment duration. A misleading conclusion is that shipping is fast because the measured path begins at shipment creation rather than at each job’s packing time.

Low machine utilization can coexist with long job waiting because a machine is only one conjunct in the enabling condition. A job may be ready but lack a fixture, rack, released lot, batch partner, calibrated tool, or shipment partner. The machine then remains idle or becomes idle while the job’s critical path continues. Utilization measures occupied machine time divided by calendar opportunity; it does not measure the time a job spends waiting for a different object or policy decision.

## 5. Object-lifecycle evidence

**B1 cure narrative.** Temporally, J1 and J2 are ready at 08:10 and 08:25, J3 at 11:55, and B1 starts at 12:05. Resource feasibility is a many-to-one relation: B1 uses OVEN-1 and RACK-7 and includes the three component/job branches. The policy constraint is the apparent requirement to launch a common batch rather than cure each ready job independently. It is causal speculation that J3 caused the 235- and 220-minute waits; a fixed start, rack state, or unrecorded readiness gate could have produced the same timestamps.

**Fixture and CNC narrative.** Temporally, J3 acquires FIX-A at 09:00, J4 reaches CNC-2 at 09:50, CNC-2 is idle from 10:05 to 10:47, J3 releases FIX-A at 11:40, and J4 starts at 11:45. Resource feasibility requires FIX-A for J4’s machine process even though CNC-2 itself is available for part of the interval. The policy/data constraint is that no explicit `Wait for Tool` activity records the queue, so the hold must be reconstructed from acquire/release and process relations. It is plausible, but not proven, that FIX-A caused all of J4’s 115-minute arrival-to-start interval; the 42-minute overlap is stronger evidence than the unobserved portion.

**Lot and batch narrative.** Temporally, L7 is quarantined at 10:20 and released at 13:50, while its C2 and C5 contents serve J2 and J5 in different batches. Resource feasibility is quality eligibility: J5 cannot proceed while its component lot is unavailable. The policy constraint is asymmetric: J2 enters B1 through a supervisor override, whereas J5 does not proceed until release. The causal claim that L7 delayed J5 is plausible and consistent with the record, but the missing J5 readiness timestamp prevents quantifying its actual wait; the shared event may also be a quality-control response to another issue.

**Calibration and shipment narrative.** Temporally, J5 tests from 16:10 to 16:35, CAL-3 is recalibrated until 17:20, J6 tests from 17:25 to 17:50, while J1 is packed at 13:30 and J4 at 19:10 before S1 dispatches at 19:25. Resource feasibility links J5/J6 to CAL-3 and TEST-1; shipment feasibility links J1/J4 to S1. Policy constraints are recalibration sequencing and shipment consolidation. It is speculative that calibration caused all J6 delay or consolidation caused all J1 delay, because explicit readiness, handoff, documentation, and cutoff events are incomplete.

## 7. PM4Py analysis outline

```python
import itertools
import pandas as pd
import pm4py

# ocel is supplied by the caller. Keep the native OCEL tables for joins and provenance.
interaction_summary = pm4py.ocel_objects_interactions_summary(ocel)
objects_graph = pm4py.discover_objects_graph(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
ocdfg = pm4py.discover_ocdfg(ocel)
features = pm4py.extract_ocel_features(ocel)

# A conventional comparison, retained only as a view of the object-centric data.
job_log = pm4py.ocel_flattening(ocel, object_type="Job")
job_performance_dfg = pm4py.discover_performance_dfg(job_log)

events = ocel.events.copy()
relations = ocel.relations.copy()
objects = ocel.objects.copy()
events["ocel:timestamp"] = pd.to_datetime(events["ocel:timestamp"])

# Metric 1: event-object link frequency by object type. This counts links, not waits.
link_frequency = (
    relations.drop_duplicates(["ocel:eid", "ocel:oid", "ocel:type"])
    .groupby("ocel:type").size().rename("event_object_links")
    .sort_values(ascending=False)
)

# Metric 2: distinct object-type co-presence frequency per event. This counts one
# type-pair once per event, avoiding inflation when an event has several same-type objects.
event_type_pairs = []
for eid, group in relations.groupby("ocel:eid"):
    types = sorted(group["ocel:type"].dropna().unique())
    event_type_pairs.extend((a, b) for a, b in itertools.combinations(types, 2))
coevent_frequency = (
    pd.DataFrame(event_type_pairs, columns=["source_type", "target_type"])
    .value_counts().rename("coevent_count").sort_values(ascending=False)
)
print("link metric:\n", link_frequency.head(20))
print("co-presence metric:\n", coevent_frequency.head(20))
print("library interaction summary:\n", interaction_summary)

# Object-pair frequency is a third useful check: repeated co-use of the same two objects.
oid_to_type = objects.set_index("ocel:oid")["ocel:type"].to_dict()
object_pair_rows = []
for eid, group in relations.groupby("ocel:eid"):
    oids = sorted(group["ocel:oid"].dropna().unique())
    for left, right in itertools.combinations(oids, 2):
        object_pair_rows.append((left, right, oid_to_type.get(left),
                                 oid_to_type.get(right), eid))
object_pair_frequency = (
    pd.DataFrame(object_pair_rows,
                 columns=["left_oid", "right_oid", "left_type", "right_type", "eid"])
    .groupby(["left_type", "right_type"]).size()
    .rename("distinct_event_object_pair_cooccurrences")
)

def linked_time(oid, activities):
    """Earliest timestamp of an activity linked to one object."""
    eids = relations.loc[relations["ocel:oid"].eq(oid), "ocel:eid"]
    rows = events[events["ocel:eid"].isin(eids) &
                  events["ocel:activity"].isin(activities)]
    if rows.empty:
        return pd.NaT
    return rows["ocel:timestamp"].min()

def minutes_between(left_oid, left_activity, right_oid, right_activity):
    left = linked_time(left_oid, {left_activity})
    right = linked_time(right_oid, {right_activity})
    return (right - left).total_seconds() / 60.0

# These waits use semantic predecessor/enabling events, not a machine-event gap.
# Activity names may be mapped to the site's vocabulary before running this block.
semantic_waits = pd.Series({
    "J1_ready_to_B1": minutes_between("J1", "Ready for batch", "B1", "Batch Cure"),
    "J2_ready_to_B1": minutes_between("J2", "Ready for batch", "B1", "Batch Cure"),
    "J6_ready_to_test": minutes_between("J6", "Ready for final test", "J6", "Final Test"),
    "J1_pack_to_S1_dispatch": minutes_between("J1", "Pack", "S1", "Dispatch"),
})
print("semantic waits:\n", semantic_waits)

# Machine gaps can be reported as context, but are not labeled as job waiting.
machine_activity_counts = relations.merge(
    events[["ocel:eid", "ocel:activity", "ocel:timestamp"]], on="ocel:eid"
).query("ocel:type == 'Machine'").groupby(
    ["ocel:oid", "ocel:activity"]
).size()
print("machine event counts (diagnostic only):\n", machine_activity_counts)
```

The interaction, object graph, OTG, ETOT, and OCDFG outputs should be inspected with event and object qualifiers retained. In particular, a machine gap should not be converted into a wait unless a job readiness event, a feasible resource state, and a later enabling or service event establish the interval.

## 8. Falsification and additional data

Observations that would weaken the batch-synchronization hypothesis include:

- B1’s documented policy permits immediate partial curing, and the 12:05 start was fixed independently of J3 readiness.
- RACK-7 and OVEN-1 were both unavailable before 12:05 for a documented reason unrelated to batch fill.
- J1 or J2 had an unfulfilled quality, release, or setup prerequisite at 08:10 or 08:25.
- Repeated B1-like cases show no early-ready job waiting when a later member becomes ready.
- A replay of the dispatch policy with all three jobs ready at 08:10 still schedules 12:05.
- Manual observations show that J1/J2 were not physically ready despite the recorded “ready” timestamps.
- J4 starts at the same time in comparable runs when FIX-A is free, but J6 is not delayed when CAL-3 is recalibrated elsewhere.
- J1’s customer cutoff or documentation requirement independently fixes S1’s 19:25 dispatch.

Additional fields and event types that would discriminate the mechanisms are:

- Explicit per-stage `request`, `ready`, `eligible`, `queue-enter`, `queue-exit`, `start`, and `complete` timestamps, with a reason code for every wait.
- Machine, rack, fixture, and calibration-tool reservation, acquire, release, cleaning, maintenance, and availability-calendar events; include the requesting job and denied requests.
- Batch policy fields for minimum and maximum fill, planned start, earliest start, setup time, late-member rule, and the eligible-member snapshot at scheduling time.
- Component-lot quarantine reason, per-component release status, quality disposition, genealogy, sample/test result, override identity, and override authorization time.
- Shipment cutoff, consolidation rule, partner readiness, load appointment, paperwork hold, partial-shipment authorization, and job-level pack-to-dispatch timestamps.
- Tool calibration validity intervals, recalibration trigger, calibration queue, and whether a calibrated tool can be shared during a test.
- A stable event-source ID, ingestion time, correction/version field, object-link provenance, and a late-arriving-event flag to reconcile the Job extraction with the lot pipeline.
- Machine state labels distinguishing busy, starved, blocked, reserved, setup, fault, and idle, plus the object causing each non-busy state.

With these data, the strongest test is not whether a machine gap is long. It is whether a ready job repeatedly has a feasible path blocked by a specific shared object or policy, whether the blocking object is temporally available in the counterfactual, and whether changing that object or policy changes downstream job, batch, lot, tool, and shipment outcomes without merely moving the delay elsewhere.
