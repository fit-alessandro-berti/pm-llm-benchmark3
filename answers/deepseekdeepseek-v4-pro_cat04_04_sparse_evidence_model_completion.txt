**DFG and Concurrency:** A DFG with both `(CC  ER)` and `(ER  CC)` does **not** prove concurrent execution. The same edge pairs can emerge from a sequential model that allows CCER in some cases and ERCC in others (e.g., an XORloop). In a completiononly log, concurrency would require forking two activities that can finish in any order, but the direct evidence is missing. Without start timestamps, commitment to concurrency is an inductive leap.

# 2. Shared Assumptions

All three models share the following assumptions:

- **Event semantics:** Every event records the completion timestamp of the activity. An activity is considered “executed” when its completion event appears in the trace. This implies that the order of events is the order of completions, not start times.
- **Missing Supplier Confirmation:** Observed traces without SC may represent either (a) genuinely skipped Supplier Confirmation for stocked components (S4) or (b) missing events due to an integration gap (S5). No model can distinguish the two cases; we treat the absence of SC as an explicit skippath but acknowledge the possibility of event loss.
- **Absent external/stocked attribute:** Since the attribute is not exported, we cannot condition the presence of SC on any data. Modelling must therefore use controlflow choices (e.g., a silent  to skip SC) rather than a databased decision.
- **Optionality representation:** All optional activities (SC, Expedite) are modelled through a choice between the activity and a silent transition. This is an abstraction that does not capture the underlying cause (stocked component or omitted event) but gives a clear overapproximation of behaviour.
- **Highconfidence rules D1 and D2:** Every model enforces Register Order at start, Archive Case at end, and a strict sequence Approve Configuration  Release Production.

# 3. Conservative Candidate

### Inductivebias statement
This model aims to admit **no** complete trace that has not been directly observed in the event log. It trusts the sample exhaustively and makes zero generalisation beyond the recorded variants, while still respecting the highconfidence rules (D1, D2) that are already satisfied by the observations.

### Formal expression
An XOR (choice) over the seven observed sequences, each expressed as a strict sequential chain of the corresponding activities. Activities are leaf nodes; duplicate labels across branches are allowed. This forms a finitelanguage process tree with 7 branches.

### Behaviour deliberately excluded
- **Any trace not identical to the seven observed variants.** Even a permutation that swaps two activities that never cooccurred (e.g., `RO  ER  SC  CC  AC  …`) is excluded.
- **Traces where Expedite appears in a position never seen** (e.g., immediately after RO).
- **Traces where SC is present but the check order differs from the few observed possibilities** (e.g., `RO  SC  CC  ER  …`).

### Known underfitting risks
- The model will reject any future valid execution that slightly reorders checks, SC, or Expedite. This makes it **brittle** and unusable for automated enforcement because a single new interleaving would break conformance.
- It assumes that the seven variants are exhaustive and that no other path can legitimately occur, which is almost certainly false given the small sample and the datamissingness issue.
- Scalability: enumerating all observed variants leads to a process tree with duplicate labels, inflating model size linearly with the number of distinct trace types; for large logs this becomes impractical. The model describes the training set, not the process.

# 4. Balanced Candidate

### Inductivebias statement
The balanced model encodes the most plausible structural generalisation guided by domain rules and stakeholder statements, while explicitly treating CC/ER as concurrent and SC as an activity that can start after **either** check has finished. It respects the high and mediumconfidence rules, uses parallel constructs to model true concurrency, and offers a skip path for SC to account for both legitimate absences and data loss.

### Decisions on order and concurrency
- **Credit Check  Engineering Review:** we reject S1 (strict sequence) in favour of S2 (parallel execution). Observed interleaving V1–V4 and V6/V7 is consistent with concurrency. D7 confirms that completion timestamps do not refute it. The partial order places CC and ER as independent activities that can run simultaneously; the model does not force the completion of one before the other can start.
- **Supplier Confirmation:** based on D5 (lowmedium), SC may start after the first of CC/ER finishes. To encode this without ORjoins we create two parallel branches inside an XOR:  
  (i) `CC  SC` running concurrently with `ER`,  
  (ii) `ER  SC` running concurrently with `CC`.  
  A third branch, containing only parallel `CC` and `ER` (no SC), represents the “skip SC” case.
- **Expedite Review:** required to be after both CC and ER (D6) and before AC. In this model it appears after the parallel block (i.e., after both checks and SC, if present) as an optional step. This means Expedite always follows SC when SC is executed, which is permitted by S6 (“may occur before or after SC”). The alternative ordering (Expedite before SC) is not covered; we accept this simplification because the evidence (V6, V7) shows both options, but modelling both would require additional branches and make the model less readable.

### Formal expression (POWL)
A sequence root:  
`RO`  XOR( `PO`, `PO`, `PO` )  XOR( , `EX` )  `AC`  `RP`  `Arc`  
where  
- `PO` is a strict partial order with nodes {CC, SC, ER} and edge CCSC (ER independent).  
- `PO` is a strict partial order with nodes {ER, SC, CC} and edge ERSC (CC independent).  
- `PO` is a strict partial order with nodes {CC, ER} and no edges (concurrent).  
- `` is a silent transition.

### PM4Py code
```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition

t_ro = Transition("Register Order")
t_cc = Transition("Credit Check")
t_er = Transition("Engineering Review")
t_sc = Transition("Supplier Confirmation")
t_exp = Transition("Expedite Review")
t_ac = Transition("Approve Configuration")
t_rp = Transition("Release Production")
t_arc = Transition("Archive Case")
tau = SilentTransition()

# Partial order 1: CC -> SC, ER independent
po1 = StrictPartialOrder(nodes={t_cc, t_sc, t_er})
po1.order.add_edge(t_cc, t_sc)

# Partial order 2: ER -> SC, CC independent
po2 = StrictPartialOrder(nodes={t_er, t_sc, t_cc})
po2.order.add_edge(t_er, t_sc)

# Partial order 3: both checks concurrent, no SC
po3 = StrictPartialOrder(nodes={t_cc, t_er})

# XOR of the three partial orders
xor_po = OperatorPOWL(operator=OperatorPOWL.XOR, children=[po1, po2, po3])

# Optional Expedite (xor with silent)
opt_exp = OperatorPOWL(operator=OperatorPOWL.XOR, children=[tau, t_exp])

# Final sequence
model_balanced = OperatorPOWL(
    operator=OperatorPOWL.SEQUENCE,
    children=[t_ro, xor_po, opt_exp, t_ac, t_rp, t_arc]
)
```

### Behaviour deliberately excluded
- Traces where SC runs before any check is complete (e.g., `RO  SC  CC  ER  …`).
- Traces where Expedite occurs after SC has started but before it finishes (Expedite must wait for the whole parallel block to end).
- Traces where AC appears before both CC and ER are finished (rule D3 is enforced).
- Traces where Credit Check and Engineering Review are forced into a fixed sequential order (S1 is ignored).

### Known underfitting risks
- The model is slightly stricter than D5 would allow, because the optional Expedite cannot interleave inside the SCcontaining blocks. In reality, an expedited review might start while SC is still in progress, but this is a rare combination unobserved in the data.
- It does not expose the distinction between missingbydesign and missingbydataloss for SC; any trace without SC is accepted via `PO`, potentially masking a true missing event if later data becomes available.
- The choice to ignore S1 could be contested by Finance; if the sequential constraint were later confirmed, the model would need revision.

# 5. Permissive Candidate

### Inductivebias statement
This model accepts all interleavings that are not explicitly forbidden by the highconfidence rules (D1, D2) and the mediumhigh rule (D3). It treats the checks as concurrent, SC as fully optional and parallel with the checks (no startafterfirstcheck constraint), and Expedite as optional but following the completion of both checks. The goal is to **explore** the space of plausible behaviour rather than to enforce strict compliance.

### Boundary between “reasonable generalization” and forbidden behaviour
**Admitted (reasonable):**  
- CC and ER may occur in any order, fully concurrently, or even overlapping in ways not observed.  
- SC may appear or be skipped; when present it may be placed anywhere between RO and AC, even before either check completes. This is a deliberate overgeneralisation of D5 (low confidence).  
- Expedite may be skipped; if executed it must come after both checks but may still run concurrently with SC. However, in the chosen ProcessTree structure Expedite must wait until the entire parallel block (CC, ER, optional SC) finishes, which is a modelling simplification; we accept that Expedite cannot occur during an ongoing SC.

**Forbidden:**  
- Any trace where RP appears without preceding AC, or where AC appears before both CC and ER (D3, highmedium).  
- Any trace where Expedite appears before both CC and ER are complete (D6).  
- Traces that omit CC or ER entirely.  
- Start and end activities are fixed.

### Formal expression (ProcessTree)
`RO`  AND( `CC`, `ER`, XOR(, `SC`) )  XOR(, `EX`)  `AC`  `RP`  `Arc`

### Behaviour deliberately excluded
- Any sequence that violates D3 (i.e., AC before both CC and ER complete), D6 (Expedite before both checks), D2 (RP without AC), or D1 (start/end).
- Interleavings where Expedite occurs while SC is still running; the model forces Expedite after the parallel block, effectively serialising Expedite after SC completion. This is a limitation of using ProcessTree ANDsequential constructs.

### Known underfitting risks
- By allowing SC to start before any check, the model admits traces that are physically nonsensical if SC truly requires “enough information” from a check. This could inflate precision metrics and mislead process discovery tools.
- The forced ordering of Expedite after SC may suppress the observed variant where Expedite appeared before SC (V7). This is an intentional tradeoff for simplicity but reduces fitness slightly.

# 9. Recommendation and DataCollection Plan

**Immediate recommendation:** Use the **Balanced** model. It respects the medium and highconfidence rules, explains the observed concurrency between Credit Check and Engineering Review, allows SC to start after a single check, and offers an SCskip path. It strikes the best tradeoff between fitness, precision, and explainability for compliancelight auditing and process improvement discussions.

**Sensitivity analysis:** Keep the **Conservative** model as a worstcase benchmark. Any violation flagged by the conservative model but accepted by the balanced model should be manually reviewed to decide whether the deviation is legitimate or a sign of model underfitting.

**Datacollection plan to resolve ambiguities:**
1. **Start timestamps:** Record activity start events in addition to completion events. This would directly reveal whether Credit Check and Engineering Review are truly parallel or strictly sequential (D7, S1 vs S2).
2. **External/stocked attribute:** Export the attribute that indicates whether an order contains at least one external component. This would distinguish genuinely skipped Supplier Confirmations from missing events (S3, S4, S5). It also makes the SCskip path datadependent rather than a blind choice.
3. **Integration gap audit:** Track the number of missing SC events over a known period and compare with procurement records to estimate the true missingness rate and identify affected orders.
4. **Expedite Review lifecycle:** Log start and completion timestamps for Expedite Review. This would allow a precise placement relative to SC and the checks, and reveal whether it can overlap with SC.
5. **Maximally informative future traces:**  
   - A trace where SC is started after the **second** check finishes but Expedite appears **before** SC completes.  
   - A trace where Credit Check and Engineering Review have identical start times (proving true concurrency).  
   - A trace where SC is executed but the external attribute is **absent** according to the billofmaterials (probing missingness).  
   These traces would help differentiate between the models and sharpen the concurrency/optionality assumptions.
