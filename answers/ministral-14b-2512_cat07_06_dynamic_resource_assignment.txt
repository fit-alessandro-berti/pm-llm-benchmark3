# 1. Objectives and Constraints

## **Optimization Objectives (Trade-offs)**
1. **Short-term throughput** – Minimize waiting times and maximize case completions per day.
2. **Skill development** – Allocate 20% of normal/low-priority cases to training needs where SLA risk is acceptable.
3. **Workload fairness** – Distribute assignments evenly, avoiding overload on high-overtime-risk resources.
4. **Continuity of case ownership** – Reduce reassignments, especially for high-complexity cases.
5. **SLA risk mitigation** – Prioritize urgent cases and avoid delays in high-priority workflows.
6. **Resilience** – Avoid bottlenecks in specialist roles (e.g., Security, Approval) and ensure coverage for absences.

## **Hard Constraints (Safety/Compliance)**
- **Skill requirements**:
  - Security Review: Skill 3 (or supervised by R7_Gita/R8_Hugo if skill 1–2).
  - Final Approval: Skill 2 (skill 1 may only prepare, not finalize).
- **Overtime risk**:
  - No high-priority assignments to resources with `overtime risk="high"` unless SLA is critical.
- **Reassignment limits**:
  - No case with `reassignment_count > 2` should be reassigned unless absolutely necessary.
- **Specialist-only activities**:
  - Security Review and Final Approval cannot be assigned to skill 0.

## **Soft Constraints (Preference Trade-offs)**
- **Training priority**: At least 20% of normal/low-priority cases should support documented training needs.
- **Continuity preference**: High-complexity cases with high handover cost should stay with current owner unless skill is insufficient.
- **Batching**: Quality Check may be batched only for normal/low-priority cases with >24h SLA remaining.
- **Supervision**: Trainees (skill 1) may assist on high-priority cases only under supervision.

# 2. Assignment Policy (Pseudocode)

```python
def assign_case(case, resources, constraints):
    # 1. Eligibility filtering (hard constraints)
    eligible_resources = []
    for resource in resources:
        if (case["required_skill"] == 0 and resource["required_skill"][case["concept:name"]] >= 1) or \
           (case["required_skill"] == 1 and resource["required_skill"][case["concept:name"]] >= 2) or \
           (case["required_skill"] == 2 and resource["required_skill"][case["concept:name"]] >= 3):
            # Check overtime risk for high-priority cases
            if (case["case_priority"] == "urgent" or case["case_priority"] == "high") and \
               resource["overtime_risk"] == "high":
                continue
            eligible_resources.append(resource)

    # 2. SLA urgency scoring (weight: 0.3)
    sla_score = 1 - (case["sla_time_remaining"] / max_sla_time_for_priority[case["case_priority"]])

    # 3. Skill-match scoring (weight: 0.25)
    skill_scores = []
    for resource in eligible_resources:
        skill = resource["required_skill"][case["concept:name"]]
        if skill == 0: continue  # already filtered
        skill_scores.append(skill)

    # 4. Continuity/handover-cost scoring (weight: 0.2)
    continuity_score = 0
    if case["current_owner"] is not None:
        current_owner = next(r for r in resources if r["name"] == case["current_owner"])
        if current_owner["required_skill"][case["concept:name"]] >= 2:
            continuity_score = 1 - (case["handover_cost_band"] / 3)  # high=3, medium=2, low=1

    # 5. Workload fairness (weight: 0.15)
    workload_scores = [1 - (r["current_open_cases"] / max_open_cases) for r in eligible_resources]

    # 6. Training/development scoring (weight: 0.05)
    training_scores = [1 if r["training_priority"] == case["required_skill"] and
                       case["case_priority"] in ["normal", "low"] else 0 for r in eligible_resources]

    # 7. Resilience/bottleneck avoidance (weight: 0.05)
    bottleneck_scores = [1 if r["team"] != "Risk" and r["team"] != "Quality" else 0.5 for r in eligible_resources]

    # Combine scores (weighted sum)
    combined_scores = []
    for i, resource in enumerate(eligible_resources):
        score = (
            sla_score * 0.3 +
            (skill_scores[i] / 3) * 0.25 +
            continuity_score * 0.2 +
            workload_scores[i] * 0.15 +
            training_scores[i] * 0.05 +
            bottleneck_scores[i] * 0.05
        )
        combined_scores.append((resource, score))

    # Sort by score (descending) and pick top candidate
    best_candidate = max(combined_scores, key=lambda x: x[1])[0]

    # Tie-breaking: prefer current owner if continuity is high
    if continuity_score > 0.7 and case["current_owner"] in [r["name"] for r in eligible_resources]:
        best_candidate = next(r for r in eligible_resources if r["name"] == case["current_owner"])

    return best_candidate
```

# 4. Comparison with Baseline Policies

| **Metric**               | **Proposed Policy**                          | **First-Available Routing**               | **Specialist-Only Routing**               |
|--------------------------|---------------------------------------------|--------------------------------------------|--------------------------------------------|
| **Expected Throughput**  | Balanced (avoids bottlenecks)               | High (fast assignments)                    | Low (specialists overloaded)              |
| **SLA Risk**             | Low (prioritizes urgency)                   | Medium (ignores skill)                    | High (specialists may be blocked)         |
| **Error/Rework Risk**    | Low (skill + continuity)                    | High (skill mismatches)                   | Low (but creates queues)                  |
| **Workload Fairness**    | High (explicit fairness constraints)        | Medium (first-available may overload)      | Low (specialists overloaded)              |
| **Skill Development**    | High (20% training cases)                   | Low (ignores training)                    | Low (no training focus)                   |
| **Continuity**           | High (prefers current owner)               | Low (ignores continuity)                  | Medium (specialists may not own cases)    |
| **Resilience**           | High (avoids bottlenecks)                   | Medium (no bottleneck awareness)          | Low (specialists are single points of failure) |

**Key Trade-offs:**
- **First-available** maximizes throughput but increases rework and SLA misses.
- **Specialist-only** minimizes errors but creates bottlenecks and ignores training.
- **Proposed policy** balances all factors but requires careful monitoring of trade-offs (e.g., training vs. SLA risk).

# 5. Explanation to Workers

**"How Your Work Is Assigned"**

Your assignments are made using a **fair, skill-aware, and SLA-conscious** system that balances:
 **Your strengths** – We prioritize tasks where you have the highest skill.
 **Case urgency** – High-priority cases get top attention.
 **Workload fairness** – No one gets overloaded; we monitor overtime risk.
 **Learning opportunities** – 20% of normal/low-priority cases are chosen to help you develop new skills.
 **Case continuity** – If you’re already working on a complex case, we try to keep it with you.

**Why might you get a case you’re not a specialist in?**
- **Training priority**: You’re being given a chance to learn (e.g., R6_Farid on Approval with supervision).
- **Urgency**: A high-priority case needs immediate attention, and no specialist is available.
- **Fairness**: Someone else has too much work, and this is the next best fit.

**What to watch for:**
 **High reassignment risk**: Cases with `>2` reassignments are flagged for careful handling.
 **Overtime risk**: If you’re marked as "high overtime risk," we’ll avoid assigning urgent cases unless absolutely necessary.
 **Specialist tasks**: Security Reviews and Approvals **must** be done by qualified staff (or supervised trainees).

**How to influence assignments:**
- If you see a case you’re **not qualified** for, **flag it immediately**—we’ll reassign it.
- If you’re **overloaded**, let your manager know so we can adjust.
- If you want **more training**, ask to be included in the 20% training cases.

**Our goal is to keep cases moving smoothly while helping everyone grow!**

# 7. PM4Py Implementation Sketch

```python
import pm4py
from pm4py.objects.log.util import dataframe_utils
from pm4py.algo.discovery.handover import algorithm as handover_discovery
from pm4py.algo.discovery.performance_dfg import algorithm as perf_dfg_discovery

# Load and preprocess event log
log = pm4py.read_xes("service_process.xes")
df = pm4py.format_dataframe(log)

# 1. Discover handover patterns
handover_net, _, _ = handover_discovery.apply(df)
pm4py.view_sna(handover_net, "handover_network.png")

# 2. Check skill mismatch and reassignment risk
skill_mismatch_cases = pm4py.filter_event_attribute_values(
    df, "required_skill", ["Security", "Approval"]
).groupby(["case:concept:name", "org:resource"]).filter(
    lambda x: x["required_skill"].iloc[0] > x["skill"].iloc[0]
)

# 3. Performance DFG to detect bottlenecks
perf_dfg = perf_dfg_discovery.apply(df)
pm4py.view_performance_dfg(perf_dfg, "performance_dfg.png")

# 4. Workload fairness analysis
workload_snapshot = df.groupby("org:resource").agg({
    "case:concept:name": "nunique",
    "time:timestamp": "count"
}).rename(columns={"case:concept:name": "open_cases", "time:timestamp": "total_events"})

# 5. Training opportunity detection
training_cases = df[df["case_priority"].isin(["normal", "low"])] \
    .groupby("required_skill") \
    .filter(lambda x: len(x) > 0.2 * len(df[df["case_priority"].isin(["normal", "low"])]))
```

**Key PM4Py Functions Used:**
- `discover_handover_of_work_network()`  Detect reassignment hotspots.
- `discover_activity_based_resource_similarity()`  Identify skill mismatches.
- `discover_organizational_roles()`  Monitor specialist bottlenecks.
- `filter_case_performance()`  Track SLA compliance.
- `get_service_time()`  Measure efficiency gains/losses.
- `view_sna()`/`save_vis_sna()`  Visualize resource collaboration.

**Audit Loop:**
1. **Discover** handover patterns, skill mismatches, and bottlenecks.
2. **Compare** against policy constraints (e.g., reassignment count >2).
3. **Alert** if deviations exceed thresholds.
4. **Adjust** policy weights or reassign cases.

This design ensures **explainability**, **auditability**, and **balance** across conflicting objectives while leveraging PM4Py for continuous improvement.
