## 1. Consistency rules and evidence model

**Hard invariants** (never relaxed)
- No new events or objects are created, and no timestamps are changed.
- Every E2O and O2O endpoint must exist, and there are no duplicate rows.
- O2O direction is fixed by type: `Package packs Item`, `Delivery carries Package`, `Invoice bills Order`, `Payment settles Invoice`.
- `Create Order` has one Order, and `Record Payment` has exactly one Payment. Both already hold.

**Strong defaults** (overridable with explicit reasons)
- `Pack Item` has one Item and one Package.
- `Dispatch Package` has one Package and one Delivery.
- `Record Payment` has one Invoice, unless the cash is unapplied.
- `Issue Invoice` has at least one Order.
- A package is dispatched once, so a second dispatch event on an already-dispatched package is suspicious.

**Weak heuristics**
- Identifier similarity: `PK8-2` with PK-8, and `N-421?` with `N-421`.
- Near-simultaneity: ev07 and ev08 are one minute apart.
- Amount equality: 130 + 100 = 230, PAY-1 = 100, PAY-2 = 130.
- Sequential `bank_ref` values (B-771, B-772).
- Same customer (C17) and same route (NORTH).

**Evidence against a repair**
- Mixed-order packaging, which is legal but creates many-to-many structure.
- The `?` on ev10's reference.
- The wildcard in ev11.
- ev12 and the existing `INV-44 bills` row naming only ORD-A.
- A repair that would turn a legitimate anomaly (unapplied cash, lost portal ID, scanner outage) into a "complete" lifecycle.

**How the evidence is combined**
- Route and customer are not discriminating here. Every object is NORTH and C17, so they count for almost nothing.
- Time order is checked only for consistency. The same timestamp on ev09 and ev10 gives no ordering information, but they touch different packages.
- Existing O2O structure constrains a repair but cannot prove an E2O edge that was inferred from it.
- Evidence counts once per source. One scanner reference or carrier reference supporting an E2O edge and its derived O2O edge is one piece of evidence, not two.
- Amount equality is a likelihood boost only. Fees, taxes, discounts, and partial payments can break or fake it.
- Decisions are correlated, especially the finance ones. I therefore give marginal confidences and state joint bundle plausibility separately.

**Status terms.** `accept` means included in every bundle. `provisional` means included in at least one bundle but not certain. `unresolved` means deliberately not repaired. `reject` means tempting but unsupported.

4. ev14INV-44 followed by `PAY-2 settles INV-44`.

## 6. Downstream process-mining effects

**Unrepaired log.**
- Order: ORD-A runs Create Order  Add Item  Add Item  Confirm Delivery  Issue Invoice. ORD-B runs Create Order  Add Item.
- Package: PK-8 runs Pack Item  Dispatch Package.
- Delivery: only DEL-X is seen (Dispatch Package). DEL-Y is absent from flattening.
- Payment: one-event traces.
- ET–OT: Pack Item is tied to Item and Package, Dispatch Package to Package and Delivery, Confirm Delivery to Order only, and Record Payment to Payment and Invoice (only PAY-1 connects to INV-44).
- Execution clustering: ev14 is a singleton. ORD-A's execution includes ev10 through PK-8. ORD-B's execution is {ev02, ev05, ev08}.

**Bundle A.**
- OC-DFG: a new Package self-loop `Pack Item  Pack Item` (ev07ev08), and a new Delivery trace for DEL-Y (Dispatch Package only).
- Activity counts: Pack Item stays at 3 events. Package total objects go from 2 to 3 with 2 unique objects. Dispatch Package delivery objects go from 1 to 2.
- ET–OT: no new type edges, only multiplicities.
- OTG: no new type pairs. At instance level, PK-8 now links items of two orders.
- Flattening on Order: unchanged. On Package: PK-8 becomes Pack, Pack, Dispatch (new variant). On Delivery: DEL-Y appears. On Invoice and Payment: unchanged.
- Execution clustering: PK-8 merges ORD-A's and ORD-B's components into one two-order cluster. This is the largest structural change A causes.

**Bundle B.**
- OC-DFG additions: Delivery `Dispatch Package  Confirm Delivery` for both DEL-X and DEL-Y (2 unique objects, 2 event pairs). Order ORD-B gains `Add Item  Issue Invoice`, which skips delivery. Invoice gains a `Record Payment  Record Payment` self-loop.
- Counts: Issue Invoice has 1 event but 2 unique Order objects (vs 1). Record Payment has 2 events, 2 total Invoice objects, but 1 unique invoice. Confirm Delivery gains 2 Delivery objects from 0.
- ET–OT: the new edge (Confirm Delivery, Delivery). Record Payment already touches Invoice, so ev14 adds no new type edge.
- OTG: type pairs unchanged. Instance-level Invoice–Order and Payment–Invoice counts rise.
- Flattening on Order: ORD-B becomes Create, Add, Issue Invoice. On Invoice: INV-44 becomes Issue, Pay, Pay. On Delivery: two Dispatch  Confirm traces. On Payment: still one-event traces.
- Execution clustering: INV-44 merges both orders even without P1, and ev14 joins the cluster.

**Bundle C.** This is A without the new Package self-loop. PK-8 stays Pack, Dispatch, and ORD-A and ORD-B remain separate clusters. ev08 still adds an item-only row for IT-B1.

**Activity frequency caution.** Event counts hide the effects of multi-object events. Unique-object counts hide repeated events on the same object (INV-44 in B). Total-object counts inflate activities that touch many objects (Confirm Delivery in B).

## 7. PM4Py-oriented validation outline

```python
import pandas as pd
import pm4py

# 0. Keep originals untouched
events0, objects0 = events.copy(), objects.copy()
relations0, o2o0 = relations.copy(), o2o.copy()

BUNDLES = {
    "A": dict(
        e2o=[("ev08", "PK-8", "package"), ("ev10", "DEL-Y", "delivery")],
        o2o=[("PK-8", "IT-B1", "packs"), ("DEL-Y", "PK-8", "carries")]),
    "B": dict(
        e2o=[("ev08", "PK-8", "package"), ("ev10", "DEL-Y", "delivery"),
             ("ev11", "DEL-X", "delivery"), ("ev11", "DEL-Y", "delivery"),
             ("ev12", "ORD-B", "order"), ("ev14", "INV-44", "invoice")],
        o2o=[("PK-8", "IT-B1", "packs"), ("DEL-Y", "PK-8", "carries"),
             ("INV-44", "ORD-B", "bills"), ("PAY-2", "INV-44", "settles")]),
}
selected = "A"

def apply_bundle(name):
    b = BUNDLES[name]
    ev_meta = events0.set_index("ocel:eid")[["ocel:activity", "ocel:timestamp"]]
    ob_meta = objects0.set_index("ocel:oid")["ocel:type"]
    add_rel = pd.DataFrame(b["e2o"], columns=["ocel:eid", "ocel:oid", "ocel:qualifier"])
    add_rel["ocel:activity"] = add_rel["ocel:eid"].map(ev_meta["ocel:activity"])
    add_rel["ocel:timestamp"] = add_rel["ocel:eid"].map(ev_meta["ocel:timestamp"])
    add_rel["ocel:type"] = add_rel["ocel:oid"].map(ob_meta)
    add_o2o = pd.DataFrame(b["o2o"], columns=["ocel:oid", "ocel:oid_2", "ocel:qualifier"])
    return (pd.concat([relations0, add_rel], ignore_index=True),
            pd.concat([o2o0, add_o2o], ignore_index=True))

rel_new, o2o_new = apply_bundle(selected)

# 1. Referential integrity
eids, oids = set(events0["ocel:eid"]), set(objects0["ocel:oid"])
assert rel_new["ocel:eid"].isin(eids).all() and rel_new["ocel:oid"].isin(oids).all()
assert o2o_new["ocel:oid"].isin(oids).all() and o2o_new["ocel:oid_2"].isin(oids).all()
assert rel_new.notna().all().all(), "type/activity/timestamp lookup failed"

# 2. Duplicates
assert not rel_new.duplicated(["ocel:eid", "ocel:oid", "ocel:qualifier"]).any()
assert not o2o_new.duplicated(["ocel:oid", "ocel:oid_2", "ocel:qualifier"]).any()

# 3. Direction and cardinality checks (warnings, not proofs of semantics)
otype = objects0.set_index("ocel:oid")["ocel:type"]
allowed = {"packs": ("Package", "Item"), "carries": ("Delivery", "Package"),
           "bills": ("Invoice", "Order"), "settles": ("Payment", "Invoice"),
           "contains": ("Order", "Item")}
for _, r in o2o_new.iterrows():
    assert allowed[r["ocel:qualifier"]] == (otype[r["ocel:oid"]], otype[r["ocel:oid_2"]]), r.to_dict()
per_event = rel_new.groupby(["ocel:eid", "ocel:type"]).size().unstack(fill_value=0)
print("Events with >1 Delivery:", per_event.index[per_event.get("Delivery", 0) > 1].tolist())
print("Events with >1 Package :", per_event.index[per_event.get("Package", 0) > 1].tolist())
print("Orphan objects:", sorted(oids - set(rel_new["ocel:oid"])))

# 4. Build OCEL (VERSION-DEPENDENT: constructor signature and required columns
#    differ across PM4Py releases; check your installed version's OCEL class)
from pm4py.objects.ocel.obj import OCEL
ocel = OCEL(events=events0, objects=objects0, relations=rel_new, o2o=o2o_new)

# 5. Discovery
ocdfg = pm4py.discover_ocdfg(ocel)
otg   = pm4py.discover_otg(ocel)
etot  = pm4py.discover_etot(ocel)

# 6. Flattenings
flat_order    = pm4py.ocel_flattening(ocel, "Order")
flat_delivery = pm4py.ocel_flattening(ocel, "Delivery")
print(flat_order.groupby("case:concept:name")["concept:name"].apply(list))
print(flat_delivery.groupby("case:concept:name")["concept:name"].apply(list))

# NOTE: pm4py.ocel_o2o_enrichment is deliberately not used here. It propagates
# relations structurally and would present inferred links as if they were
# business-validated facts.
```

## 8. Over-repair warnings

1. **Completing every lifecycle.** Forcing ev11 onto a single delivery (say DEL-X) would make ORD-A look delivered while part of its goods is on DEL-Y. It would also erase the legitimate "portal lost the carrier ID" case.
2. **Treating 230 = 130 + 100 as proof.** Linking INV-44 to ORD-B and PAY-2 to INV-44 on arithmetic alone could hide fees, tax, or unapplied cash. The payment amounts also match each order individually (100  ORD-B, 130  ORD-A), which supports a different story than installments.
3. **Merging DEL-Y into DEL-X.** Reading the same 10:00 timestamp as a bulk dispatch would orphan DEL-Y and remove the N-421 reference from any object.
4. **Adding OrderDelivery shortcuts.** Direct ORD-ADEL-X/DEL-Y O2O rows would duplicate information derivable through ItemPackageDelivery and create false many-to-many structure in the OTG and clustering.
5. **Adding PK-8  ORD-B and ev11  ORD-B automatically.** Combined with the mixed-order PK-8 link, this would make ORD-B look physically delivered and confirmed and would merge two execution clusters on a scanner-prefix inference.
6. **Reversing O2O direction or ignoring qualifiers.** `PK-8 carries DEL-Y` would corrupt flattening and ET–OT readings.
7. **Attaching ev10 to PK-7 as a bulk dispatch.** PK-7 already has a dispatch, so this would create a duplicate dispatch and a false second-dispatch variant.
8. **Using ev08's PK8-2 prefix as a fact rather than a hint.** The resulting `Pack Item  Pack Item` self-loop on Package and the two-order cluster would then look like a normal process pattern rather than one uncertain reconciliation.
