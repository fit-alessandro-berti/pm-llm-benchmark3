# Simulation-Based Digital Twin for the Building-Permit Process

## 1. Model scope and state variables

### 1.1 Purpose and twin boundary

The twin is a **prospective, intervention-comparison twin**, not a replay engine. Its job is to answer counterfactual questions ("what happens to p90 lead time for Complex variance if we add a peak-month inspector and batch inspections by district?") under demand that is non-stationary, resources that are calendar-constrained, and cases that are *not* independent.

**Inside the boundary**

| Element | In scope |
|---|---|
| Time span | From `Submit application` (portal timestamp) to `Issue permit` / `Reject application`, plus post-decision appeal that re-enters the process as rework |
| Work | All 13 nominal activities, all four rework loops (completeness, planning, inspection, legal/appeal) |
| Resources | Clerks, planners (incl. the two Simple-renovation-only planners), fire reviewers, environmental reviewers, inspectors, legal officers, scheduler, "system"/portal (infinite server) |
| Non-municipal actors | Applicants/architects (document response), external consultants (environmental reports), objecting neighbours, council (calendar), all modelled as **exogenous delay generators**, never as municipal capacity |
| Structures | Queues, priority/dispatching rules, inspection batching, council-week blackout, public-holiday calendar |

**Outside the boundary (explicitly excluded, with reason)**

- Post-permit construction supervision and enforcement (no events in the log).
- Fee collection and payment reconciliation (not on the critical path in the log excerpt; would only add a constant offset).
- Court appeals beyond the municipal appeal step (the log removes rare emergency decisions and does not contain judicial outcomes).
- Individual human learning curves and absenteeism at the person level (HR-reconstructed calendars only support pool-level FTE, see §3.4).

**Level of detail.** Discrete-event simulation at *activity granularity*, with **individual case entities** and **individually identified resource units** inside pools (an inspector is an individual, because travel time, batching and a temporary extra inspector are all individual-level phenomena). Sub-activity detail (e.g., steps inside Planning review) is deliberately not modelled: the log cannot identify it, and no candidate intervention operates below activity level. Time resolution: 1 minute; calendars resolved to 15-minute slots.

### 1.2 Entities

1. **Case** (permit application) — the primary transactional entity.
2. **Architect / applicant agent** — a persistent entity across cases; owns a submission-burst process and a response-speed profile. This is what makes the model non-independent on the *arrival* side.
3. **Document bundle** — a sub-entity of a case with a `completeness` state; drives the missing-document loop.
4. **Objection** — a *latent* entity (never directly observed, see §3.9) attached to a public-notice period; it is generated by a neighbourhood-level latent process and can attach to several cases in the same district-week.
5. **Inspection trip (bundle)** — an entity created by the scheduler that holds 1..k site inspections in one district on one day; it owns travel time and a no-show risk per stop.
6. **Review task** — a work item instance (activity, case, required pool, priority, due date). Queues hold review tasks, not cases, because a case in the parallel review block occupies several queues at once.
7. **Council calendar / holiday calendar** — a deterministic exogenous entity that gates Legal check and Public-notice period.

### 1.3 State variables

**Per case `c`**

- Static attributes: `case_type ∈ {Simple, NewRes, Commercial, ComplexVar}`, `district ∈ {D1..D5+}`, `architect_id`, `application_value`, latent `building_area`, latent `prior_violations`, latent `env_sensitivity(district)`.
- Routing flags: `requires_fire`, `requires_environment`, `requires_public_notice`, `requires_legal` — each is a *realised Bernoulli* from a routing model, not a copied log field (§2.4).
- Dynamic: `phase` (submitted / completeness / review-block / notice / inspection / decision / legal / closed), `t_submit`, `t_phase_entry`, `age = now - t_submit`, `n_completeness_loops`, `n_inspection_loops`, `n_legal_loops`, `n_appeals`, `pending_reviews ⊆ {planning, fire, env, notice, inspection}` (the join condition for Decision drafting), `waiting_on ∈ {municipality, applicant, third_party, calendar}` (critical for SLA clock-stopping), `sla_clock_active`, `bundle_id`, `objection_flag` (latent), `priority_score`.

**Per resource pool `p`**

- `capacity_schedule[t]` (from calendar, integer number of units available at time `t`), `busy_units`, `roster` (list of unit states: idle / busy-until / off-shift / travelling), `reserved_capacity` (e.g. environmental 40% non-permit reservation; D6 aging-case planner reservation), `queue_p` (a priority queue of review tasks), `queue_length`, `oldest_waiting_age`, `utilisation_window` (rolling).

**Global**

- Simulation clock, `arrival_intensity_multiplier(t)` (month × day-of-week × hour), active `architect_burst` clusters, `council_week_flag(t)`, `holiday_flag(t)`, WIP per phase, backlog per pool, `objection_rate(district, t)` (latent), scenario/policy configuration, RNG streams (one stream per stochastic source — see §5.4).

### 1.4 Queues, calendars, dispatching

- **Queues:** one per pool, plus a scheduler queue for inspections. Default discipline FIFO within case-type priority; the two Simple-only planners have a *restricted* queue view (they can only pull Simple renovation), which creates the classic partial-flexibility effect that a naive pooled M/M/c would miss. D6 changes discipline to "one planner pulls the oldest case above an age threshold each day".
- **Calendars:** modelled as *capacity functions of time*, not as post-hoc multipliers. A task started at 15:40 by a clerk whose shift ends at 16:00 is **suspended and resumed** the next working morning (preemptible-resume), because permit review work is interruptible. Site inspections are **non-preemptible within a trip** and can only start Tue–Fri in a window that leaves room for travel + inspection before shift end. Legal check is blocked during council weeks except for an `urgent` flag. Public-notice minimum duration is a *calendar* duration (14 days wall-clock) and must not be shortened by resource availability — it is a delay, not a service.
- **Time-zone / clock-stopping:** the SLA clock is stopped while `waiting_on = applicant`, and reported both ways (gross lead time and net municipal time), because interventions D1 and D7 move work outside the municipal boundary and would otherwise look artificially good.

### 1.5 Cross-case dependencies (the part a naive twin gets wrong)

Five distinct coupling mechanisms, each with its own model component:

1. **Resource coupling (implicit).** Shared pools already couple cases; this is automatic in DES and is the main reason waiting time must *emerge* rather than be sampled (§2.3).
2. **Architect burst coupling (arrival side).** The top-20 architects (31% of volume) submit correlated clusters: a cluster arrival triggers `K ~ 1 + NegBin(...)` applications in the same week, sharing `architect_id`, often the same district and similar case type. Modelled as a **Neyman–Scott / marked cluster process** superimposed on the background NHPP (§2.1). This raises queue variance far above Poisson even at identical mean load — ignoring it systematically *under*-estimates p90.
3. **Neighbourhood objection coupling.** A latent neighbourhood-level "contention" state per (district, month) drives objection probability for all public-notice cases in that district-window; objections are therefore positively correlated across cases, producing simultaneous long-notice clusters. Because objections are unobserved, this is a **latent-variable model calibrated to public-notice duration mixtures** (§2.6, §3.9).
4. **Inspection batching coupling.** The scheduler groups pending inspections by (district, week) into trips; the trip's travel time is sub-additive (one round trip + inter-stop legs), but the *first* case in a bundle waits for the bundle to fill or for a batching deadline. This is a direct queueing–delay trade-off and is the entire content of D3. Batch formation must be an explicit state machine (open bundle → close on size `B` or timeout `τ` → schedule → execute).
5. **Calendar coupling (common shock).** Council weeks and holidays hit *all* legal checks and notice periods at once, producing synchronised backlog waves. This is a deterministic exogenous driver shared by all cases.

A sixth, softer coupling — **planner continuity** (P001 shows `planner_3` doing both Planning review and Decision drafting) — is modelled as a soft "same-resource-if-available-within-X-days, else any" rule, since it affects both quality (rework) and waiting.

## 2. Parameter-estimation plan

### 2.1 Arrivals

**Decomposition.** Model the submission process as a superposition:

$$\lambda(t) = \underbrace{\lambda_0 \cdot m_{\text{month}}(t)\cdot m_{\text{dow}}(t)\cdot m_{\text{hour}}(t)}_{\text{background NHPP}} \;+\; \underbrace{\text{cluster process from architect agents}}_{\text{bursts}}$$

- Extract case-start timestamps with PM4Py (`pm4py.get_start_activities`, then the first event per case; `pm4py.get_case_arrival_average` gives the sanity-check mean inter-arrival time).
- Bin arrivals per (month, day-of-week, hour) and fit a **Poisson GLM with log link** and an exposure offset: `count ~ month_factor + dow_factor + hour_factor (+ interactions)`. The stated 1.7× spring/autumn multiplier and 2.2× Monday/Wednesday ratio become *fitted, not hard-coded* values, and the GLM gives standard errors that feed parameter uncertainty (§5.5).
- Overdispersion test (Pearson χ²/df, index of dispersion per week): if the residual variance exceeds Poisson, attribute the excess to clustering rather than inflating λ. Fit the cluster component to the top-20 architect subsets: cluster rate per architect, cluster size distribution (fit NegBin to "applications by the same architect within a 7-day window"), and within-cluster district/case-type concordance (empirical contingency tables).
- Case-type mix: multinomial logistic on month/district so that the mix can drift seasonally rather than being a fixed 45/28/17/10 split.
- Generation in the engine: **thinning** against `λ_max` for the background NHPP, plus independent cluster triggers per architect agent.

### 2.2 Service times

- **Where start timestamps exist**, service time = `complete − start`. Build an interval log (`pm4py.format_dataframe(..., start_timestamp_key=...)`, or `interval_lifecycle.to_interval` for lifecycle-typed logs) and compute per-activity service distributions directly.
- **Where they do not exist** (many human activities), do *not* silently use `complete[i] − complete[i−1]`; that is sojourn time = waiting + service. Three-step strategy:
  1. **Transfer estimation.** Fit service distributions on the resource pools/periods that *do* record starts, conditioned on activity × case type × district, then transfer to the same activity for pools without starts, adjusting only for observable covariates. Validate the transfer on any pool that has both regimes.
  2. **Bounded imputation.** For an event with only a completion time, bound the start by `max(previous case-event completion, previous completion of the same resource)`; this yields an *upper* bound on service time and a *lower* bound on waiting. Report an interval-censored likelihood rather than a point estimate, and fit the parametric family by maximum likelihood on interval-censored data.
  3. **Calibration closure.** Whatever residual ambiguity remains is resolved in the calibration step (§2.8): service means are tuned within their censoring interval so that simulated *utilisations* match the independently-known FTE and observed throughput.
- **Distribution families.** Lognormal or gamma as the body; test with QQ plots and AIC. For heavy-tailed activities (Environmental review, Receive missing documents, Public-notice with objections, appeal loops) use a **body + generalized-Pareto tail** above a threshold chosen by mean-excess plot, or a two-component mixture. Anchor each fit to the two published points (median, p90) as a moment/quantile-matching constraint: e.g., for Planning review, solve lognormal (μ, σ) from median 3.5 h and p90 14 h — but only as an *initialisation*, with the full empirical distribution used where available.
- **Travel time for inspections** is estimated separately as a function of district (D3, D5 longer) and of bundle composition; fit from the gap between consecutive inspections by the same inspector on the same day (a natural experiment already in the log).

### 2.3 Waiting times — estimated for validation, never sampled as input

This is the central modelling stance: **waiting time is an output of the twin, not a parameter.** The published "median waiting before activity" column (1.5 d before completeness check, 7 d before legal check, etc.) is used **only as a validation target** (§6.3). If waiting were sampled, every intervention that changes capacity or discipline (D3, D4, D6, D7) would be structurally incapable of changing the answer — the twin would be an expensive replay.

Two exceptions where a "waiting" is genuinely exogenous and *is* sampled: (i) **applicant/third-party response** (`Receive missing documents`, ~5 d median from request, heavy tail) and (ii) **fixed statutory delays** (14-day public-notice minimum). These are delays, not queues.

Because start timestamps are partly missing, the waiting/service split is partly inferred; the twin therefore reports the validation comparison on the quantity that is *identified without assumption* — the **sojourn time between consecutive completions** — and treats the decomposed waiting/service comparison as secondary evidence.

### 2.4 Branching probabilities and routing

- Estimate `P(requires_fire | case_type, application_value, district)` etc. with penalised logistic regression on the observed flags. `building_area` is unavailable; treat it as a **latent covariate** whose effect is absorbed into a case-type-specific random effect, and calibrate the fitted marginal to the observed fire-review rate. Report this as a structural uncertainty, and include the fire-trigger threshold in the sensitivity analysis.
- `env_sensitivity(district)` is incomplete: use a **partially-observed indicator** — districts with confirmed sensitivity are fixed, unknown districts get a Beta prior on their sensitivity rate calibrated so that the aggregate environmental-review share matches the log.
- Legal check, public notice, rejection: same approach, conditioned on case type and on realised review outcomes (rejection is over-represented after legal/planning conflict, per the routing notes — so make rejection probability conditional on `n_legal_loops`, not a flat rate).
- Cross-check the fitted routing against the **variant-group table**: simulated variant shares must reproduce 26/19/18/13/8/9/7% within a tolerance (§6.2). The variant table is the strongest available constraint on joint routing, since it constrains combinations, not just marginals.
- PM4Py support: `pm4py.get_variants` / `pm4py.get_variants_as_tuples` for variant shares, `pm4py.discover_dfg` for the branching structure, `pm4py.filter_event_attribute_values` to build per-case-type sub-logs before fitting.

### 2.5 Rework

- Detect loops by activity repetition within a case (`Completeness check` more than once; `Site inspection` more than once; `Legal check` repeats; post-decision appeal). Count distributions per loop.
- Fit a **discrete hazard model** `P(rework at attempt k | covariates, k)` rather than a memoryless geometric, because the data suggest attempt-dependence (a second completeness failure is less likely than the first once documents are cleaned). Covariates: case type, architect (top-20 vs long tail), district, whether reviews were parallel, reviewer identity/pool load.
- Rework *reasons* are unstructured free text and unreliable; do **not** build reason-specific routing. Instead model a single latent "case difficulty" factor per case that raises the hazard of *all* loops jointly — this reproduces the observed correlation (cases with completeness rework are also more likely to have inspection rework) without pretending the reasons are coded. Optionally, cluster the free text offline and use it only as an exploratory covariate, flagged as low-confidence.
- Note the process-tree semantics caveat: the tree's `*` operator permits unbounded repetition; empirical loop-count distributions (and a hard cap with a documented truncation) supply what the tree cannot.

### 2.6 Objections and public-notice duration (latent)

The log has **no objection events**. Model public-notice duration as a **two-component mixture**: `no objection → ~14–21 d` and `objection → long right tail up to ~60–90 d`. Fit the mixture by EM on observed notice durations; the mixing weight *is* the estimated objection rate, with a credible interval. Add a district/period random effect to capture the clustering in §1.5(3). Every result that depends on this parameter must be reported with the mixture uncertainty propagated (§5.5), and D9 (early-warning) must be evaluated over a *range* of objection rates, not a point estimate, since the intervention's value is exactly proportional to a quantity we infer rather than observe.

### 2.7 Resource calendars and capacity

- Calendars come from HR, not from events; they are therefore a **hypothesis to be tested**, not ground truth. Build an empirical *activity-execution heatmap* (events per resource per weekday × hour) from the log and compare it with the HR calendar. Where events appear outside HR hours (overtime) or where whole HR-available slots are empty (meetings, non-permit duties), correct the effective calendar.
- Estimate **effective FTE** as HR FTE × observed availability factor. Explicitly encode: one clerk on Monday portal duty (reduces Monday completeness capacity exactly when Monday submission bursts land — a key interaction for D7); fire reviewers Tue–Thu only; environmental reviewers at 60% effective permit capacity; inspectors field Tue–Fri; legal blackout in council weeks.
- Cross-validate with a **workload identity**: for each pool, `Σ estimated service time / available capacity-hours ≈ observed utilisation`. If this exceeds 1.0, the service-time estimates or the calendar are wrong — this is the single most valuable consistency check available and it directly disciplines the censored service-time estimates from §2.2.
- Council weeks and public holidays come from an external municipal calendar file (a legitimate non-log data source), aligned to observed Legal-check gaps.
- PM4Py support: `pm4py.get_event_attribute_values(log, "org:resource")` for pool composition, `pm4py.discover_organizational_roles` to check whether the HR pools match behaviourally-observed role clusters (e.g., whether the "two Simple-only planners" are visible in the data), `pm4py.discover_handover_of_work_network` for the planner-continuity effect.

### 2.8 Dependencies and batching

- **Batching:** `pm4py.discover_batches` on the inspection/scheduling activities to quantify existing informal batching (simultaneous, batching-on-start, sequential batching) per district. This gives the *baseline* batching level — important, because D3 must be measured against however much batching already happens informally, not against zero.
- **Architect coupling:** build a case-level table (architect, week, district, case type) and estimate cluster size, intra-cluster time spread, and attribute concordance. Test significance against a permutation null (shuffle architect labels across cases within month) to confirm the clustering is real and not an artefact of volume.
- **Neighbourhood coupling:** estimate the district-month random effect in the objection mixture (§2.6).
- **Flattening caveat:** the log is case-flattened, so dependencies are under-represented by construction. Where possible, enrich with the object-centric view (architect and district as objects); PM4Py's OCEL utilities can hold this enriched view, but the dependency parameters ultimately come from the case-level joins described above.

### 2.9 Calibration

Log-derived parameters are *priors*, not final values. Run a **simulation-based calibration** loop (approximate Bayesian computation / sequential Monte Carlo, or a simpler Nelder–Mead on a weighted discrepancy) over a small set of hard-to-identify parameters — service-time means inside their censoring intervals, objection rate, applicant-response tail index, batching deadline, latent difficulty variance — minimising a discrepancy on summary statistics that were **not** used for point estimation: variant shares, per-group median and p90 durations, pool utilisations, queue-length profiles. Retain the posterior sample, not just the best point, so that §5.5 can propagate parameter uncertainty.

### 2.10 Division of labour: PM4Py vs. simulation engine

PM4Py is used for **log ingestion, filtering, model handling, descriptive statistics, and validation metrics**. It is *not* used as the simulation engine: its playout and Monte-Carlo simulation facilities assume broadly independent cases and do not natively support resource calendars, non-stationary arrivals, cluster arrivals, batching, or latent cross-case state. The DES engine (SimPy or a custom event-list engine) is separate; it *emits an event log in PM4Py format*, which is then fed back through the same PM4Py pipeline for like-for-like validation. That round trip — real log and simulated log analysed by identical PM4Py code — is the backbone of §6.

## 3. Assumptions

Each assumption is stated with its justification, its risk if wrong, and how it is tested. Assumptions are ranked H/M/L by impact on intervention *ranking* (which matters more than impact on absolute numbers).

### 3.1 Arrivals

| # | Assumption | Justification | Risk | Test |
|---|---|---|---|---|
| A1 | Background submissions follow an NHPP with multiplicative month × day-of-week × hour intensity (H) | Standard for portal-driven arrivals; matches the 1.7× and 2.2× ratios given | Additive/interaction effects (e.g., Monday-in-March) would be missed | Fit GLM with interaction terms; likelihood-ratio test |
| A2 | Architect bursts are a cluster process independent across architects (M) | Top-20 architects independently manage their own pipelines | Correlated market-wide shocks (a regulation deadline) would synchronise all architects | Check weekly totals for excess dispersion beyond the sum of fitted clusters |
| A3 | Arrival intensity is exogenous — applicants do not observe backlog and defer (M) | No feedback data in the log | If real applicants defer during congestion, the twin over-states congestion, and capacity interventions look better than they are | Regression of arrivals on lagged backlog; if significant, add a feedback term |
| A4 | The 18-month history is representative of the coming 2–3 years apart from modelled seasonality (H) | Only evidence available | Structural demand shift (e.g., housing programme) invalidates all absolute numbers | Handled by stress scenario S1, not by an assumption |

### 3.2 Service times

- **A5 (H).** Service time is independent of queue length (no hurrying under load). Reviewers plausibly do speed up when swamped; if so, the twin over-states congestion. *Test:* regress observed service time on contemporaneous queue length for the pools with start timestamps.
- **A6 (H).** Service-time distributions are stationary over the 18 months, conditional on covariates. *Test:* split-sample KS test, first 9 vs last 9 months.
- **A7 (M).** Service times are conditionally independent across activities within a case, *given* the latent difficulty factor. Without the latent factor this would be clearly false (long planning reviews co-occur with long legal checks); the factor is exactly what carries that correlation.
- **A8 (M).** Human activities are preemptible-resume across shift boundaries; site inspections are not. Reasonable for desk review vs. field work.
- **A9 (L).** Portal/system activities have zero queueing and near-deterministic short service.

### 3.3 Routing

- **A10 (H).** Routing flags are drawn from a covariate model rather than replayed from the log. This is required — replaying `requires_fire` would make D8 (environmental triage) unevaluable, since triage *changes* the flag.
- **A11 (H).** The unobserved fire-area threshold and district environmental sensitivity are absorbed into latent terms calibrated to observed marginals *and* to variant shares. The joint distribution of flags is therefore only as good as the variant table constrains it. *Risk:* correlation between fire and environmental requirements could be mis-estimated; *test:* compare simulated two-way flag contingency table with the log's.
- **A12 (M).** Rejection probability depends on realised conflicts (legal/planning loops), not on case type alone.
- **A13 (M).** Decision drafting waits for *all applicable* review results — a strict join. The tree's parallel operator supports this; the log excerpt is consistent with it.

### 3.4 Resources and calendars

- **A14 (H).** Pools are homogeneous within role except for the documented restrictions (two Simple-only planners; the Monday portal clerk). Individual speed differences exist but the log's resource-level sample sizes are thin. *Test:* ANOVA of service time by individual resource; if variance is material, add a per-resource speed multiplier.
- **A15 (H).** HR-reconstructed calendars, corrected by the observed execution heatmap, are accurate to within ±10% of effective capacity. This is the weakest-evidence assumption with the highest leverage on every capacity intervention (D4, D6), because HR calendars were *not* derived from events. It is therefore a first-class sensitivity factor (§5.6).
- **A16 (M).** The environmental reviewers' 40% non-permit reservation is a smooth capacity reduction rather than block-scheduled days. *Test:* look for day-level bimodality in environmental throughput; if present, model as blocked days (which is materially worse for queueing than a smooth 60%).
- **A17 (M).** Legal officers do zero non-urgent work in council weeks, with an urgent-case escape hatch at a small fitted rate.
- **A18 (L).** No unplanned absence beyond what the effective-FTE correction already absorbs; unplanned absence is instead explored as stress scenario S2.

### 3.5 Rework

- **A19 (H).** Rework probability is attempt-dependent (decreasing hazard) and driven by a latent case-difficulty factor shared across loop types.
- **A20 (M).** Rework repeats the *same* activity with the same service distribution, possibly with a modest multiplier (re-review is often faster). *Test:* compare first vs. repeat service times where identifiable.
- **A21 (M).** Loop counts are capped (e.g., ≤4 completeness, ≤3 inspection, ≤3 legal) with the truncation documented; unbounded loops in the tree are not literally realistic.
- **A22 (M).** Appeals are modelled as re-entry into legal/planning, with an appeal probability conditional on rejection and case type. Because appeal-related events are partly entangled with "rare emergency decisions removed from the log", appeal frequency carries wide uncertainty.

### 3.6 Applicant and third-party response

- **A23 (H).** Applicant document-response time is exogenous, heavy-tailed (lognormal body + Pareto tail, median ≈5 d), and **independent of municipal load**. Modelled separately from municipal service time so that SLA clock-stopping is possible and so that D1/D7 (which shift effort to applicants) do not get spurious credit.
- **A24 (H).** Response speed varies by applicant class: top-20 professional architects respond faster and more predictably than one-off private applicants. This is fitted per class, since D1 and D7 are architect-facing and their benefit depends on it.
- **A25 (M).** Applicant response is not calendar-free — responses cluster on business days, with a weekend dip.
- **A26 (M).** External environmental consultant reports are a separate heavy-tailed third-party delay, not municipal service time; this explains "highly variable, affected by consultant reports".

### 3.7 Cross-case dependencies

- **A27 (H).** Cluster arrivals from top-20 architects reproduce the observed weekly overdispersion; ignoring them would understate p90 lead time.
- **A28 (H).** Inspection batching benefit is sub-additive travel: `travel(bundle) = base_trip(district) + Σ inter-stop legs`, calibrated from same-inspector same-day gaps. The batching *cost* is the waiting of the first case until bundle close.
- **A29 (M).** Objections are positively correlated within district-month via a latent contention state; the correlation strength is calibrated from the over-dispersion of long public-notice durations, and it is an explicit sensitivity factor.
- **A30 (M).** Planner continuity (same planner for review and drafting) is preferred but not mandatory, with a fitted fallback rate.
- **A31 (M).** Because the log is flattened by case, measured dependency strength is a **lower bound**; sensitivity runs therefore scale dependency strength upward as well as downward.

### 3.8 Non-stationary demand

- **A32 (H).** Seasonality is multiplicative and repeats annually (1.7× Mar–May and Sep–Nov relative to Jan–Feb). With only 18 months, one and a half seasonal cycles are observed — the second peak season is only partially covered, so seasonal amplitude has real uncertainty and enters the sensitivity analysis (amplitude ∈ [1.4, 2.0]).
- **A33 (H).** The system must be simulated in **non-steady-state**: seasonal backlog build-up and drain is a first-order effect. Therefore no "average load" steady-state approximation is acceptable, and the twin must be initialised with realistic WIP (§5.1).
- **A34 (M).** Day-of-week effects are stable across seasons (the 2.2× Monday factor does not itself vary seasonally). *Test:* interaction term in the arrival GLM.

### 3.9 Missing data

- **A35 (H).** Missing start timestamps make the waiting/service split **partially identified**, not identified. The twin reports sojourn-time validation as primary; decomposed metrics carry a caveat. Under-estimating service time would inflate apparent idle capacity and make capacity interventions look unnecessary — hence the utilisation identity check in §2.7.
- **A36 (H).** Objections are **unobserved**, inferred as a latent mixture component from public-notice duration. The twin never treats an objection as an observed event, never reports an "objection rate" without a credible interval, and never claims to validate D9 against observed objection data. D9 is instead evaluated as a *conditional* result: "if the objection rate is in [x, y] and early warning detects a fraction f, then…".
- **A37 (M).** Rework reasons are not codeable; the latent-difficulty construct is a deliberate substitute, and no reason-specific intervention is evaluated.
- **A38 (M).** Rare emergency decisions were removed. The log therefore under-represents both the extreme fast path and some priority pre-emption. The twin adds a small, explicitly-parameterised urgent-case stream (~1–2%) and shows results with and without it, rather than pretending the removal is harmless.
- **A39 (M).** Some `Receive missing documents` events have 0-minute service and portal resource — they are milestones, not work; the engine treats them as state transitions with no capacity consumption.
- **A40 (L).** Timestamp granularity (minutes) is adequate; same-timestamp ties are broken by a deterministic activity order.

## 4. Experiment matrix

### 4.1 Design logic

Three stages, to avoid a combinatorial explosion while still catching interactions:

1. **Screening.** A Morris elementary-effects or Plackett–Burman screen over D1–D9 (each on/off) plus the top uncertain parameters, ~2 replications each, to identify which levers and which uncertainties actually move the outcome.
2. **Focused comparison.** Full evaluation of the baseline, each surviving single intervention, and the pre-specified combinations, with full replication counts and **common random numbers** (§5.4).
3. **Robustness.** Re-run the shortlist (typically baseline, best 3 singles, D10) under every stress scenario, and score by regret (§7.5).

All scenarios use identical arrival streams, service-time streams, and routing streams via CRN, so that differences are attributable to the policy, not to sampling noise.

### 4.2 Main matrix

| ID | Scenario | Factors changed (levels) | Primary hypothesis | Expected trade-off / risk |
|---|---|---|---|---|
| **B0** | **Baseline (as-is)** | none | Reproduces observed variant shares, medians, p90s, utilisations | Reference for all comparisons; also the calibration target |
| **B0-alt** | Baseline, alternative structural assumptions | env. reservation = blocked days (vs smooth); objection rate at 10th/90th posterior percentile | Tests whether conclusions survive structural ambiguity | If rankings flip, no intervention can be recommended without more data |
| **D1** | Pre-submission document checker | adoption ∈ {40%, 70%, 95%}; missing-doc probability reduced by {30%, 55%, 75%}; applicant pre-effort +{1, 3} d before submission | Cuts the 19% "missing docs" variant and the 5-day applicant loop | Shifts delay *outside* the SLA clock — gross lead time may barely improve while net municipal time improves a lot; low-adoption case may waste effort; risk of pushing marginal applicants away entirely (arrival reduction is *not* a benefit) |
| **D2** | Simple-renovation no-inspection rule | value threshold ∈ {30k, 50k, 75k}; violation-history availability ∈ {full, partial} | Removes ~high share of Simple inspections, freeing inspector capacity for Commercial/Complex | Quality/compliance risk not observable in the log — must be reported as an un-modelled externality; benefit concentrated on cases that are already fast (12 d median), so system-level p90 may move little |
| **D3** | District-batched inspection scheduling | batch size ∈ {2, 3, 5}; batching deadline τ ∈ {3, 5, 10} d; districts ∈ {D3+D5 only, all} | Travel reduction raises effective inspector capacity | Classic batching trade-off: first-in-bundle waits longer; with small τ the batches rarely fill; benefit concentrated in D3/D5 → may *worsen* district fairness for D1/D2 if inspectors are reallocated |
| **D4** | Temporary peak-month inspector | +1 inspector for {3, 5} peak months; also a "+1 all year" reference arm | Directly attacks the 8-day inspection wait during 1.7× demand | Cost per case is high if the bottleneck is not actually inspection; timing sensitivity — starting the temp inspector 4 weeks late may erase most of the benefit (include start-lag as a level) |
| **D5** | Parallel legal pre-check (Commercial, Complex) | pre-check triggered at {planning start, planning completion}; rework-detection effectiveness ∈ {30%, 60%} | Overlaps the 7-day legal wait with review work; catches conflicts before drafting | Legal is only 2 FTE with council blackouts — parallelising *adds* legal demand and may saturate the pool, worsening legal waits for everyone; expect a non-monotonic response |
| **D6** | Reserve one planner/day for aging cases | age threshold ∈ {30, 60, 90} d; reservation ∈ {0.5, 1.0} planner-day | Cuts the tail (p90/p99) without adding capacity | Pure discipline change: mean is roughly conserved, so median may worsen slightly; strong candidate if the objective weights tails and fairness |
| **D7** | Architect appointment slots (smooth Monday bursts) | slot coverage ∈ {top-20 architects, all}; smoothing target ∈ {Mon/Wed ratio 1.5, 1.2} | Reduces arrival variance → reduces queueing at constant mean load | Does not reduce load, only variance; benefit depends entirely on A27 being right. Interacts with the Monday portal-support clerk (freeing that clerk becomes possible only under D7) |
| **D8** | Environmental-review triage | triage sensitivity/specificity ∈ {0.9/0.6, 0.8/0.8}; share of cases screened out ∈ {20%, 40%} | Removes low-value environmental reviews from an 8-day-wait, 60%-effective pool | False negatives create environmental risk and possible late rework/appeal — model a rework penalty for missed cases so the twin does not reward triage for free |
| **D9** | Objection early-warning | detection rate ∈ {0.3, 0.6}; lead time gained ∈ {5, 15} d; true objection rate at posterior {p10, p50, p90} | Enables parallel preparation during long notice periods | **Cannot be validated against data** — objections are latent. Report as a conditional/scenario result only; if the benefit is not robust across the objection-rate range, it must not be recommended |
| **D10** | Combined D1+D2+D3+D4 | all four at their mid levels | Compound effect on the inspection-and-documents chain | Sub-additivity expected: D2 and D4 both add inspector capacity, so together they deliver less than the sum; possible bottleneck migration to planning/legal — the twin should show *where* the bottleneck moves |
| **C1** | D6 + D7 (no-cost combination) | mid levels | Discipline + variance reduction with zero headcount | Best "free" option candidate; test for interaction (variance reduction may make aging-case reservation less necessary) |
| **C2** | D3 + D4 | mid levels | Inspection-focused combination | Tests whether batching makes the temporary inspector redundant |
| **C3** | D1 + D8 + D5 | mid levels | Front-loading + demand reduction on specialist pools | Tests whether the specialist pools (fire/env/legal) become the binding constraint once documents and inspections are fixed |
| **S1** | **Stress: demand surge** | sustained +40% arrivals for 12 months; peak multiplier 1.7 → 2.2 | Which policies degrade gracefully? | Capacity-adding policies (D4) should dominate; discipline-only policies (D6, D7) may collapse |
| **S2** | **Stress: capacity shock** | −1 inspector for 8 weeks in peak season; 1 of 2 legal officers absent 6 weeks; council weeks +50% | Resilience to staffing loss | Expect large backlog waves; tests whether any policy prevents an absorbing backlog (ρ→1) |
| **S3** | **Stress: objection/contention surge** | objection rate ×2, district correlation strength ×2, public-notice p90 → 90 d | Tests the latent-parameter regime that we know least about | If rankings are stable across S3, the objection uncertainty is not decision-relevant; if not, more data collection is required before deciding |
| **S4** | **Stress: applicant responsiveness degradation** | response median 5 d → 9 d, tail index heavier; D1 adoption drops to 25% | Tests the exogenous-delay dependency | D1's business case should be most vulnerable here |
| **S5** | **Stress: correlated architect mega-burst** | top-20 cluster size ×2, three simultaneous clusters in one week | Tests cross-case dependency handling explicitly | A model without cluster arrivals would show no effect at all — this scenario is also a diagnostic for the twin itself |

|---|---|---|

## 5. Warm-up, replications, and uncertainty treatment

### 5.1 Initialisation and warm-up

The system is **never in steady state** (§3.8-A33), so the usual "run until steady, then measure" logic must be adapted:

- **Preferred: realistic initialisation.** Initialise the twin with a WIP snapshot reconstructed from the log at a chosen calendar date — the set of cases in flight, their phase, their age, and each queue's contents. This is far better than empty-and-idle and dramatically shortens the transient. PM4Py filtering (`pm4py.filter_time_range` in "traces intersecting" mode) extracts exactly the cases open at that date.
- **Additional warm-up.** Even with WIP initialisation, run a **6-month** warm-up that is discarded, and start the warm-up in the same calendar month as the intended evaluation window so that seasonal phase is aligned. Determine the discard length empirically with **MSER-5** or Welch's moving-average procedure applied to a *deseasonalised* series (fit and remove the seasonal component first, then look for residual drift), since a raw seasonal series will never look "flat".
- **Diagnostic:** WIP and queue lengths should return to the same seasonal pattern year over year. If year 2 and year 3 differ systematically, the system is not stable (ρ ≥ 1 somewhere) — that is itself a finding and must be reported rather than warmed away.

### 5.2 Run length and reporting window

- Evaluation window: **3 full calendar years** after warm-up, so that each seasonal phase is observed three times and slow effects (backlog carry-over across seasons, appeal tails of 260 d) are captured.
- Report metrics **per year and per season** as well as pooled, because a policy that helps in Jan–Feb and fails in Mar–May is a different animal from one that helps uniformly.
- Cases still open at the end of the window are **right-censored**; do not silently drop them (that biases every duration metric downward, exactly in the congested scenarios where it matters most). Either report Kaplan–Meier-style estimates or use a 6-month cool-down during which arrivals stop but in-flight cases complete, and clearly label which convention is used.

### 5.3 Replications

- **Terminating-style replication analysis**, not batch means: independent replications of the full warm-up + 3-year window. Batch means would be badly biased here because the seasonal cycle induces long autocorrelation.
- **Minimum 30 replications** for mean/median comparisons; **100–200** for p90/p95 and for fairness metrics, since tail estimators converge slowly. Set the count *adaptively*: continue until the half-width of the CI on the primary metric is below a pre-declared precision target (e.g., ±1.5 days on p90 lead time), rather than fixing the number a priori.
- Sequential testing must use a pre-registered stopping rule, or the CIs lose their meaning.

### 5.4 Random numbers

- **Independent RNG streams per stochastic source**: arrivals-background, arrivals-clusters, case attributes, routing, service times per pool, applicant response, objections, no-shows, travel, rework. Use a counter-based or splittable generator (e.g., `numpy.random.SeedSequence.spawn`) so streams stay independent and reproducible.
- **Common random numbers across scenarios**: replication *r* uses the same seed spawn in every scenario. Variance reduction is often 2–5×, and CRN is what makes paired comparisons (§5.5) possible. CRN synchronisation must be *entity-indexed*, not draw-ordered: case *i* draws its service time from stream `service[pool][i]`, so a policy that removes an activity does not desynchronise every subsequent draw.
- Antithetic variates as an optional second variance-reduction layer for the arrival stream.
- Log every seed with every result; a result that cannot be reproduced exactly is not admissible evidence.

### 5.5 Uncertainty: two nested layers

**Layer 1 — stochastic (Monte Carlo) uncertainty.** From replications. Report **paired differences** vs. baseline under CRN: `Δ_r = metric(policy, r) − metric(B0, r)`, and a CI on the mean/median of `Δ`. Paired CIs are much tighter than unpaired ones and are the right basis for ranking. For multiple comparisons across 10+ policies, use **Bonferroni-corrected simultaneous CIs** or a multiple-comparisons-with-the-best (MCB) procedure, and pre-declare the primary metric to avoid selecting on noise.

**Layer 2 — parameter/input uncertainty.** Draw parameter vectors from the calibration posterior (§2.9) or from bootstrap resamples of the log (bootstrap *whole cases*, not events, to preserve within-case correlation). Run `m ≈ 40` outer parameter draws × `n ≈ 20` inner replications. Total variance decomposes as input variance + stochastic variance; report both, because when input variance dominates — which is likely for the objection rate and the calendar accuracy — the honest conclusion is "collect more data", not "run more replications". Present intervals as **credible intervals** when using the Bayesian calibration posterior and **confidence intervals** for pure frequentist replication analysis; do not mix the labels.

### 5.6 Sensitivity analysis

- **Global screening:** Morris elementary effects over ~20 parameters to rank influence cheaply.
- **Variance-based:** Sobol first-order and total indices on the 6–8 survivors, to detect interactions (e.g., between inspector FTE and batching deadline).
- **Structural sensitivity:** re-run under alternative structures — blocked vs. smooth environmental reservation, preemptible vs. non-preemptible desk work, feedback vs. exogenous arrivals, clustering on vs. off. Structural sensitivity usually dominates parametric sensitivity and is routinely under-reported.
- **Tornado plot per intervention** showing which uncertainty most threatens its business case; this is the single most useful artefact for the municipality's decision.

### 5.7 Heavy-tailed durations

Complex variance p90 is 260 d and applicant response is heavy-tailed, so tail handling needs explicit treatment:

- **Never summarise by the mean alone.** Report the median, p75, p90, p95, and the mean, and treat p90 as the headline (it aligns with the variant table and with statutory deadlines).
- **Quantile CIs by bootstrap** over replications (percentile or BCa), not by normal approximation.
- **Tail modelling.** Fit a generalized Pareto tail above a mean-excess-plot threshold for the heaviest inputs; sample the body empirically and the tail parametrically. Check the estimated tail index: if `ξ ≥ 0.5`, the variance of the input is effectively unstable and quantile estimates need far more replications.
- **Truncation, documented.** Cap extreme draws at a defensible maximum (e.g., applicant response at 365 d, after which the case is administratively closed — which is genuine municipal practice) rather than letting a single 10⁴-day draw dominate a replication. Report what fraction of draws hits the cap; if it exceeds ~1%, the cap is doing too much work.
- **Robust comparison statistics.** Compare distributions with the Wasserstein distance or with quantile-by-quantile differences rather than a mean difference; also report `P(duration > SLA)` which is bounded and therefore well-behaved.
- **More replications for tails**, as in §5.3, and a convergence plot of the p90 estimate vs. replication count to demonstrate stability.

## 6. Validation strategy

Validation runs the **real log** and the **simulated log** through the *same* PM4Py pipeline, so every comparison is like-for-like. No intervention result is reported before the baseline passes stages 6.1–6.5.

### 6.1 Face validation

- Structured walkthrough with clerks, planners, fire/environmental reviewers, inspectors, legal officers, and the scheduler. Show them animated single-case traces and a week of queue dynamics, and ask specifically: "when does this differ from your Monday?"
- Targeted questions where the log is weak: how objections actually arrive and are handled, what really happens during council weeks, how inspections are informally batched today, how the Monday portal clerk is really used.
- **Extreme-condition tests:** set inspector capacity to 1 (queues must explode monotonically); set all service times to 0 (lead time must reduce to statutory delays plus applicant response — a good check that the 14-day public notice is modelled as a calendar delay and not as work); set arrivals to 0 (system must drain and stay empty); remove all rework (durations must drop toward the "clean path" variant). Each of these has a known qualitative answer, so failures are unambiguous.
- **Degeneracy check:** turn off cluster arrivals and objection correlation; the twin should visibly *under*-predict p90. If it does not, the dependency machinery is not actually doing anything.

### 6.2 Event-log replay / structural validation

- Discover a model from the simulated log (`pm4py.discover_petri_net_inductive`) and compare it structurally with the model discovered from the real log and with the given process tree (converted via `pm4py.convert_to_petri_net`).
- **Conformance both ways:** replay the *real* log on the model derived from the simulation and the *simulated* log on the model derived from reality (`pm4py.conformance_diagnostics_alignments`, `pm4py.fitness_alignments`, `pm4py.precision_alignments`). Target: fitness ≥ 0.95 and precision within a few points of the real-log baseline. Low precision on the simulated side means the twin invents behaviour that never occurs; low fitness means it cannot produce behaviour that does.
- **Variant-share comparison:** the simulated shares of the seven variant groups must match 26/19/18/13/8/9/7% within roughly ±2–3 percentage points absolute. Compare the full variant-frequency vectors with a chi-square goodness-of-fit or a rank-correlation on the top-20 variants (`pm4py.get_variants_as_tuples`). This is the strongest single structural test available.
- **DFG comparison:** compare the frequency DFG edge-by-edge (relative frequencies, cosine similarity of edge vectors) and flag any edge present in one and absent in the other.

### 6.3 Distributional (performance) validation

- **Case duration:** per case type and per variant group, compare simulated vs. observed median and p90 against the table (Simple clean 12/24 d, Simple missing-docs 22/45 d, New residential 48/95 d, Commercial 68/130 d, Complex variance 140/260 d, inspection rework 80/160 d). Acceptance: median within ±10%, p90 within ±20% (tails deserve a looser band, and pretending otherwise invites over-fitting).
- **Distributional tests:** two-sample Kolmogorov–Smirnov and Wasserstein distance on log-durations per case type; QQ plots as the primary visual. KS on 31,200 cases will reject almost any model on trivial differences, so use the *effect size* (Wasserstein, or the KS statistic itself) as the decision quantity rather than the p-value.
- **Activity-level:** compare the performance DFG (`pm4py.discover_performance_dfg`) edge-by-edge — this jointly validates waiting-plus-service on every hand-off, which is precisely the quantity that is identified without the start-timestamp assumption (§2.3). Where start timestamps exist, additionally compare the waiting/service split, and label that comparison as assumption-dependent.
- **Inter-arrival validation:** compare simulated vs. observed arrival counts per (month, day-of-week), the Monday/Wednesday ratio, and the *weekly count variance* (the cluster-process check). Matching the mean but not the variance means the burst model is wrong.

### 6.4 Resource-utilisation validation

- Compare simulated utilisation per pool with utilisation implied by the workload identity in §2.7 and with management's own reported figures. Acceptance: within ±10 percentage points, and — more importantly — the *ranking* of pools by utilisation must match.
- Compare simulated events-per-resource-per-week and the weekday × hour execution heatmap with the real one. A twin with correct utilisation but wrong day-of-week pattern will mispredict every calendar-sensitive intervention (D3, D7, and anything touching legal).
- Verify the specific structural constraints: fire reviews occur only Tue–Thu; inspections only Tue–Fri; legal checks essentially absent in council weeks; Simple-only planners never appear on other case types.

### 6.5 Bottleneck validation

- Rank pools by mean waiting time contribution in the simulation and compare with the observed waiting column (legal 7 d, environmental 8 d, inspection 8 d, planning 6 d, decision drafting 5 d). The *ordering* must match; absolute values should be close.
- Compare queue-length dynamics: seasonal backlog build-up in Mar–May and Sep–Nov, the Monday spike at completeness check, the post-council-week legal surge. These signatures are what an intervention has to move.
- **Bottleneck-shift test:** artificially add capacity to the top bottleneck and confirm that the second bottleneck emerges where domain experts expect. A twin that cannot reproduce bottleneck migration will over-sell single-pool interventions such as D4.

### 6.6 Out-of-sample validation

- **Temporal holdout:** calibrate on months 1–12, validate on months 13–18. This tests seasonal extrapolation, which is exactly what the twin is being asked to do. Report holdout error separately from in-sample error, and expect it to be materially worse; if in-sample and out-of-sample errors are similar, that is reassuring, and if in-sample is far better, the model is over-fitted.
- **Cross-sectional holdout:** hold out one district (e.g., D5) and check that the twin predicts it from the district covariates alone; likewise hold out a subset of top-20 architects.
- **Prospective validation:** freeze the twin, then compare its predictions with the next 3 months of real events as they arrive. This is the only validation that is genuinely uncontaminated, and it should gate any high-cost intervention (D4's temporary hire).
- **Natural-experiment validation:** if any historical change exists in the 18 months (a staffing change, a holiday cluster, an unusually large architect burst), replay it as a mini-intervention and check that the twin reproduces the observed response. Predicting a *change* correctly is much stronger evidence than reproducing a level.
- **Explicit non-claim.** Objection-related behaviour (D9) cannot be out-of-sample validated, because the validation target does not exist in the data. It is reported as a scenario analysis with an explicit "unvalidated" label.

## 7. Decision criteria

### 7.1 Metric definitions

All metrics are computed per replication and reported as paired differences vs. baseline with CIs (§5.5), pooled and split by case type, district, and season.

| Metric | Definition | Role |
|---|---|---|
| `LT50`, `LT90`, `LT95` | Median / p90 / p95 gross lead time, submission → decision | Primary |
| `NET50`, `NET90` | Same, with the clock stopped while waiting on applicant/third party | Primary (fairness to the municipality's own performance) |
| `SLA_t` | Share of cases decided within the statutory/target time, per case type | Primary |
| `U_p` | Utilisation per pool, seasonal max and annual mean | Guardrail |
| `RW` | Mean rework loops per case, by loop type | Secondary |
| `BL_max`, `BL_end` | Peak and end-of-year open-case backlog | Guardrail |
| `F_district` | Fairness across districts (see §7.4) | Guardrail |
| `F_architect` | Fairness between top-20 architects and the long tail | Guardrail |
| `COST` | Incremental FTE-months + implementation effort | Constraint |
| `REGRET` | Max shortfall vs. best policy across stress scenarios | Robustness |

### 7.2 Thresholds and ranges

These are proposed defaults to be ratified with the municipality *before* results are inspected, so that the decision rule is not fitted to the answer:

- **Materiality floor.** An improvement counts only if the paired 95% CI on the difference excludes zero *and* the point estimate exceeds a practical threshold: **≥3 days on `LT90`**, or **≥3 percentage points on `SLA`**. Statistically significant but sub-day improvements are noise dressed as insight in a process with 12–140 day medians.
- **Primary target.** `SLA` compliance ≥ 85% for Simple renovation and New residential, ≥ 75% for Commercial, ≥ 65% for Complex variance — set per case type because a single threshold would simply mean "ignore Complex variance".
- **Tail target.** `LT90` reduction of ≥ 10% for the two worst-performing groups (Complex variance and inspection-rework variants). Tail improvement is weighted more heavily than median improvement, because the median cases are already acceptable and public complaints come from the tail.
- **Utilisation guardrail.** No pool's annual mean utilisation may exceed **85%**, and no pool's seasonal peak may exceed **95%**. Above that, waiting time becomes hypersensitive to small errors in the service-time estimates — precisely the parameters that are only partially identified (§3.9-A35) — so any recommendation that pushes a pool there is untrustworthy regardless of its point estimate.
- **Backlog guardrail.** End-of-year backlog must not trend upward across the three simulated years in any stress scenario; a policy that is fine on average but produces an absorbing backlog under S1 or S2 is rejected outright.
- **Rework guardrail.** No intervention may increase any rework rate by more than 10% relative (relevant for D2 and D8, where screening cases out can generate downstream problems).
- **Applicant-effort guardrail.** For D1 and D7, report gross *and* net lead time. If gross lead time does not improve, the policy has moved work to citizens rather than removing it, and it must be presented that way.

### 7.3 Composite scoring (transparent, not authoritative)

For a single ranked view, use an explicitly weighted score on standardised improvements — e.g., 0.35 on `LT90` improvement, 0.25 on `SLA` gain, 0.15 on fairness, 0.15 on robustness (negative regret), 0.10 on backlog stability — subject to all guardrails being satisfied. Publish the weights, show the ranking's sensitivity to them, and state plainly that the composite is a communication device: any policy whose rank changes under reasonable reweighting is not a clear winner. Alongside it, present a **cost-effectiveness frontier** (`LT90` improvement per incremental FTE-month) so that the zero-cost policies (D6, D7) are compared on their own terms against the paid ones (D4).

### 7.4 Fairness

Equity is a first-class criterion for a public authority, not an afterthought:

- **District fairness:** the ratio `max_d LT90(d) / min_d LT90(d)`, and the Gini coefficient of per-district `LT90`. D3 warrants specific attention: batching (D3) improves the districts with long travel while potentially starving the near ones, so report per-district deltas, never just the aggregate.
- **Architect fairness:** compare `LT90` for the top-20 architects' cases vs. everyone else's. D7 (appointment slots) and D3 (bundling by architect+district) both risk institutionalising an advantage for large firms; if the gap widens by more than a few percent, that is a governance finding regardless of the efficiency gain.
- **Case-type fairness:** no intervention may improve the aggregate by degrading Complex variance (already at 140 d median) by more than 5%. D2 in particular improves the fastest segment and must be checked for exactly this.

### 7.5 Robustness and the decision rule

Rank policies by **maximum regret across the stress scenarios** (S1–S5) rather than by expected performance in the base scenario alone. The recommendation logic:

1. Discard any policy violating a guardrail in *any* scenario.
2. Among survivors, prefer policies that are within the materiality floor of the best in **every** scenario (robust satisficing) over policies that win big in the base case and fail under stress.
3. Prefer reversible, low-cost, low-commitment options (D6, D7, D3) where robust performance is comparable to expensive ones, and prefer staged rollouts with monitoring over one-shot commitments.
4. Where the decision hinges on a parameter with wide input uncertainty (objection rate for D9; calendar accuracy for D4 and D6), compute the **expected value of additional information**: the recommendation may well be "instrument the objection process for six months, then decide", which is a legitimate and often correct output of a digital twin.

### 7.6 Statement of epistemic limits

Any report from this twin must state: the twin **compares** interventions under stated assumptions; it does **not** identify an optimum. No claim of optimality is warranted, because (i) service/waiting decomposition is only partially identified, (ii) objections are latent and inferred rather than observed, (iii) resource calendars are HR-derived rather than event-derived, (iv) rare emergency decisions are absent from the log, and (v) the case-flattened log under-represents cross-case dependencies, making the dependency parameters lower bounds. Until the baseline passes §6 and, ideally, a prospective validation window, results should be read as **directional and comparative**, with intervals, not as point forecasts.

```python
PROCESS_TREE_STRING = (
    "->( 'Submit application', "
    "*( ->( 'Completeness check', "
    "X( tau, ->( 'Request missing documents', 'Receive missing documents' ) ) ), "
    "'Completeness rework' ), "
    "+( 'Planning review', X( tau, 'Fire-safety review' ), "
    "X( tau, 'Environmental review' ) ), "
    "X( tau, 'Public-notice period' ), "
    "*( ->( 'Inspection scheduling', 'Site inspection' ), 'Inspection rework' ), "
    "'Decision drafting', X( tau, 'Legal check' ), "
    "X( 'Issue permit', 'Reject application' ) )"
)


def load_log_excerpt(csv_text: str = LOG_EXCERPT_CSV) -> pd.DataFrame:
    """Read the raw CSV into pandas (pm4py has no read_csv)."""
    df = pd.read_csv(io.StringIO(csv_text))
    df[TS_KEY] = pd.to_datetime(df[TS_KEY])
    return df


def format_log(df: pd.DataFrame,
               start_timestamp_key: Optional[str] = None) -> pd.DataFrame:
    """
    Attach XES semantics. `start_timestamp_key` is passed only for the subset of
    resources that record start timestamps; for the rest the interval is unknown
    and the waiting/service split stays partially identified (see Assumptions).
    """
    kwargs = dict(case_id=CASE_KEY, activity_key=ACT_KEY, timestamp_key=TS_KEY)
    if start_timestamp_key is not None:
        kwargs["start_timestamp_key"] = start_timestamp_key
    log = pm4py.format_dataframe(df, **kwargs)
    return log.sort_values([CASE_KEY, TS_KEY]).reset_index(drop=True)


def parse_reference_tree(tree_string: str = PROCESS_TREE_STRING):
    """
    Parse the simplified process tree.

    Limitations of this string, which the simulation model must supply itself:
      * `X(tau, 'Fire-safety review')` encodes optionality but not the *data*
        condition (requires_fire / building area) — routing is data-driven and
        must be a covariate model, not a free choice.
      * `*(body, redo)` permits unbounded repetition; empirical loop-count
        distributions and a documented cap replace that.
      * The tree carries no resources, calendars, durations, queues, batching or
        cross-case dependencies. It constrains control flow only.
      * Appeal-driven rework after the decision is not representable at all.
    """
    try:
        tree = pm4py.parse_process_tree(tree_string)
    except Exception as exc:  # malformed / unsupported operator arity
        raise ValueError(f"process tree string could not be parsed: {exc}") from exc
    return tree


def tree_to_petri_net(tree):
    """Convert to an accepting Petri net for conformance-based validation."""
    net, im, fm = pm4py.convert_to_petri_net(tree)
    return net, im, fm


def describe_log(log: pd.DataFrame) -> Dict[str, Any]:
    """Descriptive artefacts used both for estimation and for validation."""
    variants = pm4py.get_variants(log)
    dfg, dfg_start, dfg_end = pm4py.discover_dfg(log)
    perf_dfg, perf_start, perf_end = pm4py.discover_performance_dfg(log)
    return {
        "n_cases": log[CASE_KEY].nunique(),
        "variants": variants,
        "n_variants": len(variants),
        "dfg": dfg,
        "dfg_start": dfg_start,
        "dfg_end": dfg_end,
        "performance_dfg": perf_dfg,
        "start_activities": pm4py.get_start_activities(log),
        "end_activities": pm4py.get_end_activities(log),
        "case_arrival_avg_sec": pm4py.get_case_arrival_average(log),
        "case_durations_sec": pm4py.get_all_case_durations(log),
        "resources": pm4py.get_event_attribute_values(log, RES_KEY),
    }


def add_timing_columns(log: pd.DataFrame,
                       start_col: Optional[str] = None) -> pd.DataFrame:
    """
    Add sojourn / service / waiting columns.

    Without start timestamps only the *sojourn* time between consecutive
    completions is identified. It is therefore the primary validation quantity;
    service and waiting are filled in only where a start timestamp exists, and a
    boolean flag records which rows carry the assumption.
    """
    out = log.sort_values([CASE_KEY, TS_KEY]).copy()
    g = out.groupby(CASE_KEY, sort=False)
    out["prev_complete"] = g[TS_KEY].shift(1)
    out["sojourn_h"] = (out[TS_KEY] - out["prev_complete"]).dt.total_seconds() / 3600.0

    if start_col is not None and start_col in out.columns:
        out[start_col] = pd.to_datetime(out[start_col])
        out["service_h"] = (out[TS_KEY] - out[start_col]).dt.total_seconds() / 3600.0
        out["waiting_h"] = (out[start_col] - out["prev_complete"]).dt.total_seconds() / 3600.0
        out["timing_identified"] = out[start_col].notna()
    else:
        out["service_h"] = np.nan
        out["waiting_h"] = np.nan
        out["timing_identified"] = False

    # Applicant-driven gaps are exogenous delays, not municipal queueing.
    out["exogenous_gap"] = out[ACT_KEY].isin(
        {"Receive missing documents", "Public-notice period"}
    )
    return out


def arrival_profile(log: pd.DataFrame) -> pd.DataFrame:
    """Case-start timestamps binned by month / weekday / hour for the NHPP fit."""
    first = (log.sort_values(TS_KEY)
                .groupby(CASE_KEY, as_index=False)
                .first()[[CASE_KEY, TS_KEY]])
    first["month"] = first[TS_KEY].dt.month
    first["dow"] = first[TS_KEY].dt.dayofweek
    first["hour"] = first[TS_KEY].dt.hour
    return (first.groupby(["month", "dow", "hour"])
                 .size()
                 .rename("n_arrivals")
                 .reset_index())


def detect_batching(log: pd.DataFrame):
    """Baseline (informal) batching, so D3 is measured against reality not zero."""
    return pm4py.discover_batches(log)

class PermitTwin:
    """
    Discrete-event engine. Emits an event log in PM4Py column conventions so the
    Layer-A pipeline can be re-run on simulated output for like-for-like
    validation. Waiting time is an OUTPUT of the queues here, never an input.
    """

    def __init__(self,
                 arrivals: ArrivalGenerator,
                 routing: RoutingEngine,
                 services: ServiceParams,
                 pools: Dict[str, ResourcePool],
                 dependencies: DependencyManager,
                 exogenous: ExogenousDelayParams,
                 policy: Policy,
                 rng_streams: Dict[str, np.random.Generator]):
        self.arrivals = arrivals
        self.routing = routing
        self.services = services
        self.pools = pools
        self.dependencies = dependencies
        self.exogenous = exogenous
        self.policy = policy
        self.rng = rng_streams
        self.events: List[Dict[str, Any]] = []

    def initialise_wip(self, wip_snapshot: pd.DataFrame) -> None:
        """Seed in-flight cases from the real log instead of empty-and-idle."""
        raise NotImplementedError

    def run(self, start: pd.Timestamp, warmup_end: pd.Timestamp,
            end: pd.Timestamp, cooldown_days: int = 180) -> pd.DataFrame:
        raise NotImplementedError

    def _emit(self, case: Case, activity: str,
              start: pd.Timestamp, complete: pd.Timestamp, resource: str) -> None:
        self.events.append({
            CASE_KEY: case.case_id,
            ACT_KEY: activity,
            TS_KEY: complete,
            "start_timestamp": start,          # the twin knows both, unlike reality
            RES_KEY: resource,
            "case_type": case.case_type,
            "district": case.district,
            "architect_id": case.architect_id,
            "application_value": case.application_value,
        })

    def to_pm4py_log(self, mask_start_timestamps: bool = False) -> pd.DataFrame:
        """
        Export simulated events. `mask_start_timestamps=True` reproduces the real
        log's observability so validation compares like with like rather than
        crediting the twin with information the real log never had.
        """
        df = pd.DataFrame(self.events)
        if mask_start_timestamps:
            df = df.drop(columns=["start_timestamp"])
            return format_log(df)
        return format_log(df, start_timestamp_key="start_timestamp")

class ExperimentRunner:
    """
    Replication with common random numbers: replication r uses the same spawned
    seed sequence in every scenario, and streams are entity-indexed so that a
    policy which removes an activity does not desynchronise later draws.
    """

    STREAMS = ("arrivals_bg", "arrivals_burst", "attributes", "routing",
               "service", "applicant", "objection", "travel", "noshow", "rework")

    def __init__(self, config: ExperimentConfig, builder: Callable[[Scenario, Dict[str, np.random.Generator]], PermitTwin]):
        self.config = config
        self.builder = builder

    def _streams(self, replication: int) -> Dict[str, np.random.Generator]:
        seeds = np.random.SeedSequence(
            entropy=self.config.master_seed, spawn_key=(replication,)
        ).spawn(len(self.STREAMS))
        return {name: np.random.default_rng(s) for name, s in zip(self.STREAMS, seeds)}

    def run_scenario(self, scenario: Scenario) -> pd.DataFrame:
        rows = []
        for r in range(self.config.n_replications):
            twin = self.builder(scenario, self._streams(r))
            sim_log = twin.run(
                start=self.config.start,
                warmup_end=self.config.start + pd.DateOffset(months=self.config.warmup_months),
                end=self.config.start + pd.DateOffset(
                    months=self.config.warmup_months + 12 * self.config.horizon_years),
            )
            metrics = compute_metrics(sim_log)
            metrics.update({"scenario": scenario.scenario_id, "replication": r})
            rows.append(metrics)
        return pd.DataFrame(rows)

    def compare_to_baseline(self, results: pd.DataFrame, baseline_id: str = "B0",
                            metric: str = "lt_p90_days") -> pd.DataFrame:
        """Paired (CRN) differences with bootstrap CIs; see decision criteria."""
        raise NotImplementedError

def validate_against_reality(real_log: pd.DataFrame,
                             sim_log: pd.DataFrame,
                             reference_net) -> Dict[str, Any]:
    """
    Run identical PM4Py analyses on both logs and compare.
    Structural: variants, DFG, conformance. Performance: performance DFG,
    duration quantiles. Resource: utilisation and weekday x hour heatmaps.
    """
    real_desc = describe_log(real_log)
    sim_desc = describe_log(sim_log)
    net, im, fm = reference_net
    return {
        "variant_share_delta": compare_variant_shares(real_desc["variants"],
                                                      sim_desc["variants"]),
        "dfg_edge_similarity": compare_dfgs(real_desc["dfg"], sim_desc["dfg"]),
        "perf_dfg_delta": compare_performance_dfgs(real_desc["performance_dfg"],
                                                   sim_desc["performance_dfg"]),
        "sim_fitness_on_reference": pm4py.fitness_alignments(sim_log, net, im, fm),
        "sim_precision_on_reference": pm4py.precision_alignments(sim_log, net, im, fm),
        "duration_quantile_delta": compare_duration_quantiles(
            real_desc["case_durations_sec"], sim_desc["case_durations_sec"]),
        "arrival_profile_delta": compare_arrival_profiles(
            arrival_profile(real_log), arrival_profile(sim_log)),
    }

def build_scenarios() -> List[Scenario]:
    """Baseline, D1-D10, combinations, and the stress scenarios of section 4."""
    baseline = Scenario("B0", Policy())
    d1 = Scenario("D1", Policy(pre_submission_checker=True, checker_adoption=0.70))
    d2 = Scenario("D2", Policy(skip_inspection_simple=True))
    d3 = Scenario("D3", Policy(district_batching=True, batch_size=3,
                               batch_deadline_days=5.0))
    d4 = Scenario("D4", Policy(temp_inspector_months=(3, 4, 5, 9, 10, 11)))
    d6 = Scenario("D6", Policy(aging_planner_reservation=True, aging_threshold_days=60))
    d7 = Scenario("D7", Policy(appointment_slots=True, monday_smoothing_target=1.5))
    d10 = Scenario("D10", Policy(pre_submission_checker=True, checker_adoption=0.70,
                                 skip_inspection_simple=True, district_batching=True,
                                 temp_inspector_months=(3, 4, 5, 9, 10, 11)))
    s1 = Scenario("S1_demand_surge", Policy(), demand_multiplier=1.4,
                  seasonal_amplitude=2.2)
    s2 = Scenario("S2_capacity_shock", Policy(),
                  capacity_overrides={"inspectors": 3, "legal": 1})
    s3 = Scenario("S3_objection_surge", Policy(), objection_rate_override=0.44)
    s5 = Scenario("S5_mega_burst", Policy(), burst_intensity_multiplier=2.0)
    return [baseline, d1, d2, d3, d4, d6, d7, d10, s1, s2, s3, s5]

    # Layer B -> Layer C -> Layer D would follow; estimation and engine bodies
    # are intentionally left as placeholders in this skeleton.
```

**Reading of the results.** Nothing in this design licenses a claim that any intervention is optimal. The twin produces *calibrated comparisons with intervals*, conditional on assumptions that are individually stated, individually testable, and — for the objection process, the resource calendars, and the waiting/service split — individually known to rest on incomplete evidence. The correct output of the first iteration is therefore a shortlist of robustly-positive interventions, a ranked list of the data gaps that most affect the ranking, and a proposal to instrument the process (start timestamps, objection events, coded rework reasons) before the expensive commitments are made.
