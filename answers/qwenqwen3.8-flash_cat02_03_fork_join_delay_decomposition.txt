import pm4py

# 1. construct supplied table
rows = [ ... ]
cols = [...]
df = pd.DataFrame(rows, columns=cols)

# parse timestamps
base = pd.Timestamp('2026-05-19')
time_cols = ['arrival','fork_release','A_start','A_end','B_start','B_end','C_start','C_end','final_start','final_end']
for col in time_cols:
    df[col + '_dt'] = pd.to_datetime('2026-05-19 ' + df[col])
    df[col + '_m'] = (df[col + '_dt'] - base).dt.total_seconds() / 60.0

branches = ['A','B','C']
# decomposition
df['upstream_elapsed'] = df['fork_release_m'] - df['arrival_m']
for i in branches:
    df[f'{i}_queue'] = (df[f'{i}_start_m'] - df['fork_release_m']).clip(lower=0)
    df[f'{i}_service'] = df[f'{i}_end_m'] - df[f'{i}_start_m']
    df[f'{i}_path'] = df[f'{i}_queue'] + df[f'{i}_service']
    df[f'{i}_completion'] = df[f'{i}_end_m']
df['join_ready'] = df[[f'{i}_completion' for i in branches]].max(axis=1)
for i in branches:
    df[f'{i}_sync_wait'] = df['join_ready'] - df[f'{i}_completion']
df['sum_sync_wait'] = df[[f'{i}_sync_wait' for i in branches]].sum(axis=1)
df['fork_join_elapsed'] = df['join_ready'] - df['fork_release_m']
df['downstream_queue'] = df['final_start_m'] - df['join_ready']
df['final_service'] = df['final_end_m'] - df['final_start_m']
df['total_flow_time'] = df['final_end_m'] - df['arrival_m']
df['total_by_stages'] = df['upstream_elapsed'] + df['fork_join_elapsed'] + df['downstream_queue'] + df['final_service']

# critical branch with tie handling
priority = {'A':0,'B':1,'C':2}
def critical(row):
    ends = {i: row[f'{i}_completion'] for i in branches}
    mx = max(ends.values())
    tied = [i for i in branches if np.isclose(ends[i], mx)]
    single = min(tied, key=lambda b: priority[b])
    return pd.Series({'critical_branches': '/'.join(tied),
                      'critical_branch': single,
                      'critical_weight': 1.0/len(tied)})
df = pd.concat([df, df.apply(critical, axis=1)], axis=1)

# print checks
assert np.allclose(df['total_flow_time'], df['total_by_stages'], atol=1e-9)
print('Max abs decomposition error:', (df['total_flow_time']-df['total_by_stages']).abs().max())

# 1. Delay-decomposition definitions

Let \(c\) index cases \(c=1,\ldots,12\), and let \(i\in\{A,B,C\}\) index the three parallel branches. All times below are measured in minutes from the same origin, e.g. minutes since midnight on 2026-05-19.

## Core notation

| Symbol | Meaning |
|---|---|
| \(AR_c\) | arrival time of case \(c\) |
| \(FR_c\) | fork-release time of case \(c\) |
| \(S_{i,c}\) | start time of branch \(i\) in case \(c\) |
| \(E_{i,c}\) | completion/end time of branch \(i\) in case \(c\) |
| \(FS_c\) | start time of final activity \(F\) |
| \(FE_c\) | end time of final activity \(F\) |

## Component definitions

1. **Upstream elapsed time before fork release**

\[
U_c = FR_c - AR_c
\]

This is the elapsed wall-clock time from entry to the process until branch work is permitted to begin.

2. **Branch-specific queue waiting**

\[
Q_{i,c} = \max(0,\; S_{i,c} - FR_c)
\]

The max is a safety rule. Under the stated model, branch work cannot be permitted before \(FR_c\), so a negative value would indicate a data/model violation. In the supplied data, all branch starts are at or after fork release.

3. **Branch active service time**

\[
Serv_{i,c} = E_{i,c} - S_{i,c}
\]

This assumes the logged start-to-end interval is the branch’s active work interval. It does **not** prove that the work was uninterrupted.

4. **Branch completion time**

\[
E_{i,c}
\]

The branch completion time is the logged end timestamp.

5. **Join-ready time**

Because the final activity may start only after all three branches complete, the inferred join-ready time is

\[
J_c = \max(E_{A,c}, E_{B,c}, E_{C,c})
\]

This is not directly logged; it is inferred from the stated synchronization rule.

6. **Branch-specific synchronization waiting after completion**

\[
Sync_{i,c} = J_c - E_{i,c}
\]

This is the time branch \(i\) has completed but the case as a whole is still waiting for the last branch.

7. **Elapsed fork-join stage time**

\[
FJ_c = J_c - FR_c
\]

Equivalently,

\[
FJ_c = \max_i \left(Q_{i,c} + Serv_{i,c}\right)
\]

This is the wall-clock time from fork release until the case is join-ready.

8. **Downstream queueing before final activity**

\[
DQ_c = FS_c - J_c
\]

Under the stated model, this is the time between join-ready and final start. If \(DQ_c < 0\), the model assumptions or timestamps would be inconsistent. In the supplied data, all \(DQ_c \ge 0\).

9. **Final service time**

\[
FServ_c = FE_c - FS_c
\]

10. **Total case flow time**

\[
TFT_c = FE_c - AR_c
\]

Using the stage decomposition:

\[
TFT_c = U_c + FJ_c + DQ_c + FServ_c
\]

This is the only additive wall-clock decomposition across the four sequential stages: upstream, fork-join, downstream queue, final service.

## Why summing all branch synchronization waits double counts time

For each case,

\[
\sum_{i\in\{A,B,C\}} Sync_{i,c}
= 3J_c - (E_{A,c}+E_{B,c}+E_{C,c})
\]

These synchronization waits are **branch-specific diagnostics**, not additive elapsed time. They overlap in wall-clock time.

Example from case F07:

- A completes at 10:30 and waits 25 minutes until join at 10:55.
- B completes at 10:55 and waits 0 minutes.
- C completes at 10:03 and waits 52 minutes until join at 10:55.

The sum of synchronization waits is

\[
25 + 0 + 52 = 77 \text{ minutes}
\]

But the actual elapsed fork-join stage time is only

\[
FJ_{F07} = 10:55 - 09:40 = 75 \text{ minutes}
\]

Adding the 77 minutes of synchronization waiting to the case flow time would double-count overlapping waiting intervals. In fact, across all 12 cases, the total branch synchronization waiting is 549 minutes, while the total elapsed fork-join stage time is only 732 minutes. The synchronization waits are useful for diagnosing which branch finishes early, but they must not be summed as if they were sequential stages.

## Branch comparison

No exact ties in critical branch were observed. The deterministic tie rule used in the code is: if multiple branches end at the same join-ready time, all are reported as tied, and the single-label critical branch is chosen by priority A < B < C. For aggregate frequency, tied branches can receive fractional weight; here the weighted and single-label frequencies are identical because there are no ties.

## Reasoned influence ranking

### 1. Branch B is the dominant branch controlling total completion time

B is the critical branch in 8 of 12 cases, or 66.7%. Its mean queue-plus-service path is 56.67 minutes, larger than A’s constant 50-minute path and much larger than C’s 30.58-minute mean path. B also has the largest tail: its queue-plus-service path reaches 75 minutes in F07 and F12, and those are the two largest fork-join stage times.

The key point is that B’s influence is not due to service time alone. A has the largest mean service time, but A always starts immediately at fork release and therefore has zero queue. B has shorter service time on average but substantial queue delay, with mean 19.17 minutes and maximum 30 minutes. The combined B path is what makes B usually last.

### 2. Branch A is less influential than its service time suggests

A has the highest mean service time, 50 minutes, but it is critical only in F01 and F11. In F01, A’s original completion is 09:00, only five minutes after B completes at 08:55. In F11, A completes at 11:30, only ten minutes after B completes at 11:20. A’s service time is constant and its queue is zero, so A is predictable but not usually controlling.

### 3. Branch C has high synchronization waiting but low control

C has the largest mean synchronization wait, 30.42 minutes, and maximum 52 minutes. This means C often finishes early and waits for B or A. High synchronization waiting is evidence that C is usually not controlling completion. C is critical only in F04 and F08, and even then its criticality is driven by queue delay rather than service time.

### 4. A and C are near-ties among the non-B branches

A and C each are critical in 2 of 12 cases. A has a larger constant service path; C has a larger queue tail and larger synchronization waiting. Depending on the improvement lever, either could appear slightly more influential, but both are far behind B.

### 5. Downstream final-station queueing is larger than any single branch acceleration considered here

The downstream queue has mean 14.67 minutes and total 176 minutes. This is a system-level stage, not a branch, but it is important for redesign: branch acceleration may be masked if final-start time is constrained by final-station queueing or release policy.

# 4. Counterfactual redesign analysis

## Counterfactual assumptions

These counterfactuals are **estimates under explicit assumptions**, not causal predictions.

1. **A service reduction by 20%**  
   Assumption: A service time becomes \(0.8 \times Serv_A\). A queue and start time are unchanged.

2. **B queue delay reduction by 50%**  
   Assumption: B queue time becomes \(0.5 \times Q_B\). B service time and fork release are unchanged. Odd-minute queues are allowed to produce fractional-minute counterfactuals; if integer-minute timestamps are required, results can be rounded conservatively.

3. **Downstream queue elimination**  
   Assumption: final activity starts immediately at join-ready, i.e. \(DQ_c^{new}=0\). This is an optimistic capacity/release-policy scenario. A 50% downstream reduction is also reported as a sensitivity.

4. **Branch counterfactuals keep downstream queue fixed**  
   For A and B counterfactuals, the reported savings are reductions in join-ready time. Total flow-time realization assumes the downstream queue does not absorb the earlier join-ready time. If final-station congestion is real and fixed, the realized total savings may be smaller.

## Per-case counterfactual savings

All savings are in minutes.

## Counterfactual 1: Reduce A service time by 20%

A service time is constant at 50 minutes, so a 20% reduction makes it 40 minutes. This reduces A completion by 10 minutes in every case.

Direct benefits:

- F01: A was critical, but after reduction B becomes critical. Savings are only 5 minutes, not 10.
- F11: A was critical. After reduction, A and B tie at 11:20. Savings are 10 minutes.

Zero-benefit cases:

- F02, F03, F05, F06, F07, F09, F12: B remains critical.
- F04, F08: C remains critical.
- F10: B remains critical.

Interpretation:

A has the largest mean service time, but it is usually not the last branch. Accelerating A has weak total-flow impact because the critical path is often B or C. This is the clearest example that largest mean service time is not the same as largest completion-time influence.

Secondary effects:

- In F01, the critical branch shifts from A to B.
- If final-station queueing is dynamic, earlier join-ready times may simply increase downstream queue, reducing realized savings.
- If A resource becomes underutilized, the redesign may need to reallocate A capacity elsewhere.

## Counterfactual 2: Reduce B queue delay by 50%

B queue time is reduced from mean 19.17 to mean 9.58 minutes. B completion is therefore reduced by half of its original queue time.

Positive-benefit cases:

- F02: saves 10 minutes; critical shifts from B to A.
- F03: saves 10 minutes; B remains critical.
- F05: saves 10 minutes; critical shifts from B to A.
- F06: saves 15 minutes; A/B tie at join-ready.
- F07: saves 15 minutes; B remains critical.
- F09: saves 12.5 minutes; B remains critical.
- F10: saves 5 minutes; critical shifts from B to A.
- F12: saves 15 minutes; B remains critical.

Zero-benefit cases:

- F01: A remains critical.
- F04: C remains critical.
- F08: C remains critical.
- F11: A remains critical.

Interpretation:

This is the strongest branch-level counterfactual. It saves 92.5 total minutes across 12 cases, or 7.71 minutes per case under the fixed-downstream assumption. The effect is much larger than A service reduction because B is usually the last branch and has substantial queue delay.

Secondary effects:

- B acceleration shifts the critical branch to A in several cases: F02, F05, F06, F10.
- If A becomes the new bottleneck, further A acceleration may have value only after B queue is reduced.
- If final-station queueing is fixed or resource-limited, earlier B completion may be absorbed by downstream waiting.
- The maximum fork-join time falls from 75 minutes to about 60 minutes under this counterfactual, reducing the tail.

## Counterfactual 3: Add final-station capacity or reduce downstream queueing

The observed downstream queue is positive in every case: 8 to 20 minutes, mean 14.67 minutes, total 176 minutes.

If downstream queueing is truly a final-station queue and capacity is added so that final activity starts immediately at join-ready, the direct savings are:

- Total savings: 176 minutes.
- Mean savings: 14.67 minutes per case.
- All 12 cases benefit.

If downstream queue is reduced by 50%, the estimated savings are:

- Total savings: 88 minutes.
- Mean savings: 7.33 minutes per case.

Interpretation:

Under the optimistic queue-elimination assumption, downstream final-station reduction is larger than any single branch counterfactual evaluated here. This does not mean it is necessarily feasible; it means the logged downstream component is large.

Zero-benefit or low-benefit possibilities:

- If the observed \(final\_start - join\_ready\) is a release policy rather than a queue, adding final-station capacity may produce little or no benefit.
- If final resources are busy with unlogged work, the logged data cannot identify that.
- If final-start times are batched or administratively delayed, capacity may not matter as much as schedule visibility.

Secondary effects:

- Reducing downstream queueing makes branch improvements more visible in total flow time.
- It may expose B as the dominant branch more clearly.
- It may increase final-station utilization if volume remains constant, or reduce utilization if capacity is added.
- It may change the interaction between branch acceleration and total flow: earlier join-ready may no longer be absorbed by downstream waiting.

## Combined branch counterfactual as a diagnostic

If A service is reduced by 20% and B queue is reduced by 50%, the combined branch-level join-ready savings are 117.5 minutes, not simply 15.0 + 92.5 = 107.5 minutes. The extra 10 minutes arise because A acceleration becomes useful in some cases once B is accelerated. If downstream queue is also eliminated, the combined optimistic savings are 293.5 minutes across the 12 cases.

This combined result is an estimate under the stated assumptions and should not be treated as a causal prediction.

# 5. Recommended redesigns and risks

## Recommendation 1: Reduce B queue delay through scheduling or capacity changes

### Why this redesign

B is the critical branch in 8 of 12 cases. Its mean queue-plus-service path is 56.67 minutes, larger than A’s 50-minute path. A 50% reduction in B queue delay yields the largest branch-level counterfactual savings: 92.5 minutes total, 7.71 minutes per case, under the fixed-downstream assumption.

### Expected impact

- **Flow time:** mean total flow time could fall from 115.25 to about 107.5 minutes if downstream queue behavior is unchanged.
- **Tail:** F07 and F12, the two largest total flow times, each save 15 minutes. The maximum fork-join time falls from 75 to about 60 minutes.
- **Throughput:** if final station can absorb earlier join-ready times, throughput may improve. If final station is constrained, throughput may not improve much.
- **Resource utilization:** B branch resource utilization may fall if queue is reduced by adding capacity; if queue is reduced by scheduling, utilization may improve.

### Risks

- **New bottleneck:** A becomes critical in several cases after B acceleration. Further improvement may require A acceleration or A scheduling changes.
- **Synchronization shift:** B synchronization wait is already low; reducing B increases A and C synchronization waits.
- **Downstream masking:** earlier join-ready may simply increase downstream queue if final station capacity is fixed.
- **Cause uncertainty:** the data show B queue delay but not why it occurs. It could be machine availability, technician scheduling, batch release, or external setup.

### Pilot and measurement

Pilot one of:

- a dedicated B stress-test slot immediately after fork release;
- an additional B resource or parallel B capability;
- priority scheduling for B queue;
- earlier B preparation so that B can start closer to fork release.

Measure:

- \(B\_start - fork\_release\)
- \(B\_end - fork\_release\)
- critical branch frequency
- join-ready time
- final_start  join_ready
- total flow time
- B resource utilization or queue length, if resource data can be logged

Success criteria:

- B queue mean falls substantially.
- B critical frequency falls or B path mean falls.
- Total flow-time tail falls.
- Downstream queue does not increase enough to absorb the gain.

## Recommendation 2: Make final-station waiting visible and reduce true downstream queueing

### Why this redesign

Downstream queueing contributes 176 minutes across the 12 cases, mean 14.67 minutes per case. If this is true queueing, reducing or eliminating it has a larger direct effect than the A or B branch counterfactuals evaluated here. If it is a release policy, adding capacity may not help, so the first step is to make the mechanism observable.

### Expected impact

- **Flow time:** if downstream queue is eliminated, mean total flow time falls from 115.25 to about 100.58 minutes.
- **Tail:** cases with 20 minutes downstream queue, F10 and F11, save 20 minutes.
- **Throughput:** final-station throughput may improve if the bottleneck is final resource availability.
- **Resource utilization:** adding capacity may lower final-station utilization; changing release policy may raise effective utilization.

### Risks

- **Misdiagnosis:** the observed downstream queue may not be a queue. It may be a fixed release delay, administrative hold, or unlogged final-station work.
- **New bottleneck exposure:** reducing downstream waiting may make branch B or A control total flow more clearly.
- **Utilization risk:** adding final capacity may create idle resources if branch completions remain late.
- **Synchronization effects:** earlier final starts may change queue dynamics for later cases in ways not visible in this small sample.

### Pilot and measurement

Pilot one of:

- log final resource availability and all final-station work, not only these 12 cases;
- test a rule allowing final activity to start immediately at join-ready;
- add temporary final-station capacity for a controlled period;
- stagger final releases to reduce batching.

Measure:

- final_start  join_ready
- final resource idle/busy time
- final service time
- number of cases waiting for final start
- total flow time
- whether branch accelerations translate into total flow savings

Success criteria:

- downstream queue falls materially.
- total flow time falls by an amount close to the observed reduction in downstream queue.
- if branch accelerations are also piloted, realized savings are not fully absorbed by final-station waiting.

# 7. Limits of inference

Several important quantities cannot be identified from these timestamps alone.

## 1. Causality is not identifiable

The timestamps show sequence and duration, not cause. For example, B queue waiting is observed as \(B\_start - fork\_release\), but the data do not reveal whether it is caused by:

- machine stress-test resource contention,
- technician scheduling,
- batch release,
- setup time,
- priority rules,
- external dependencies,
- or hidden work not logged.

Therefore, counterfactual savings are scenario estimates, not causal predictions.

## 2. Branch resource capacity is not logged

The data state that the final station has two resources, F1 and F2, but they do not provide resources for A, B, or C. Therefore we cannot compute:

- branch resource utilization,
- branch server count,
- branch queue length,
- branch waiting time due to resource contention,
- whether A’s zero queue is due to dedicated capacity, priority, or policy.

A queue of zero is an observation, not proof that A has unlimited capacity.

## 3. Work preemption and interruptions are invisible

The calculation

\[
Serv_{i,c} = E_{i,c} - S_{i,c}
\]

assumes the start-to-end interval is active branch work. It cannot distinguish:

- continuous work,
- paused work,
- waiting for materials,
- waiting for a technician,
- machine downtime,
- rework within the same activity,
- or administrative interruptions.

Thus branch service time is an elapsed interval, not necessarily pure processing time.

## 4. Join-ready is inferred, not logged

The data do not contain a direct `join_ready` event. We infer

\[
J_c = \max(E_{A,c}, E_{B,c}, E_{C,c})
\]

from the stated rule that final activity may start only after all three branches complete. If there are hidden synchronization conditions, unlogged join activities, or data errors, the inferred join-ready time and synchronization waits may be misattributed.

## 5. Downstream waiting may not be a queue

The quantity

\[
DQ_c = FS_c - J_c
\]

is labeled downstream queueing only under the stated model assumptions. It could instead be:

- a fixed release policy,
- administrative delay,
- a batch window,
- unlogged final-station work,
- resource unavailability not captured in the log,
- or a decision rule requiring additional conditions.

The final station has two resources and observed final service is constant at 20 minutes. A simple two-server FCFS interpretation would not obviously produce the observed positive downstream queues for all cases. That does not prove a release policy, but it shows that the data are insufficient to identify the mechanism.

## 6. Final-station utilization cannot be fully estimated

Observed final service is 240 resource-minutes total. Over the logged final-start to final-end window, two resources have some idle time, but we do not know whether the resources were occupied by other work outside these 12 cases. Therefore, we cannot reliably estimate true final-station utilization or capacity constraints.

## 7. Counterfactual interactions are uncertain

The counterfactuals assume simple changes:

- A service multiplied by 0.8,
- B queue multiplied by 0.5,
- downstream queue reduced or eliminated.

Real systems may have nonlinear effects:

- earlier join-ready may increase downstream queue if final capacity is fixed;
- reducing B queue may increase A or C synchronization waiting;
- adding final capacity may expose branch bottlenecks;
- reducing one delay may change arrival patterns, priorities, or batching;
- behavior may change because operators or resources respond to the new policy.

Thus the counterfactual savings should be treated as bounds or planning estimates, not guaranteed outcomes.

## 8. Small sample and no case attributes

Twelve cases are enough for descriptive decomposition but not enough for robust statistical inference. There are no case attributes, no rework loops, no alternative paths, and no stochastic capacity model. The analysis is deterministic and descriptive under the stated fork-join model.
