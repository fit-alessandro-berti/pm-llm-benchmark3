```
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def act(label):
    return ProcessTree(name=label)

def tau():
    return ProcessTree(operator=Operator.TAU)

def seq(*children):
    return ProcessTree(operator=Operator.SEQUENCE, children=list(children))

def xor(*children):
    return ProcessTree(operator=Operator.XOR, children=list(children))

def par(*children):
    return ProcessTree(operator=Operator.PARALLEL, children=list(children))

def loop(body, redo):
    return ProcessTree(operator=Operator.LOOP, children=[body, redo])

def clarification_optional():
    body = seq(act("Request Clarification"), act("Receive Clarification"))
    return xor(tau(), loop(body, tau()))

def payment_block():
    change_cycle = loop(seq(act("Change Bank Details"), act("Suspend Vendor"), act("Verify Bank Account")), tau())
    direct_payment = seq(act("Release First Payment"), act("Close Onboarding"))
    change_then_payment = seq(change_cycle, act("Release First Payment"), act("Close Onboarding"))
    return xor(direct_payment, change_then_payment)

reject_branch = seq(act("Reject Vendor"), act("Close Onboarding"))
low_risk_branch = seq(act("Manager Approval"), act("Activate Vendor"), payment_block())

high_no_escalation = seq(act("Enhanced Due Diligence"), act("Compliance Approval"), act("Activate Vendor"), payment_block())
high_escalation_legal_first = seq(act("Sanctions Escalation"), act("Obtain Legal Opinion"), act("Enhanced Due Diligence"), act("Compliance Approval"), act("Activate Vendor"), payment_block())
high_escalation_legal_after_edd = seq(act("Sanctions Escalation"), act("Enhanced Due Diligence"), act("Obtain Legal Opinion"), act("Compliance Approval"), act("Activate Vendor"), payment_block())
high_risk_branch = xor(high_no_escalation, high_escalation_legal_first, high_escalation_legal_after_edd)

outcomes = xor(reject_branch, low_risk_branch, high_risk_branch)

    par(act("Capture Master Data"), act("Run Sanctions Screening"), act("Verify Bank Account")),
    clarification_optional(),
    act("Classify Risk"),
```

# 1. Policy Interpretation and Conflict Resolution

## Material assumptions

1. **Case identity and labels**  
   The visible activity labels are used exactly as written. A case is one vendor-onboarding instance. The event log contains at least `case:concept:name`, `concept:name`, `time:timestamp`, and `org:resource`.

2. **Start and terminal semantics**  
   `Receive Onboarding Request` is the mandatory start event. `Close Onboarding` is the terminal event. `Reject Vendor` and `Activate Vendor` are mutually exclusive outcome events.

3. **Accepted versus rejected cases**  
   An *accepted* case is inferred as a case containing `Activate Vendor`. A *rejected* case is inferred as a case containing `Reject Vendor`. Because the log does not contain an explicit `accepted` attribute, this inference is based on control flow.

4. **Applicable approval**  
   For low-risk acceptance, the applicable approval is `Manager Approval`. For high-risk acceptance, the applicable approval is `Compliance Approval`. The process backbone enforces that an accepted case uses exactly one approval route.

5. **Clarification semantics**  
   `Request Clarification` creates an obligation that must be answered by a later `Receive Clarification`. Several request/response cycles are allowed, but cycles may not overlap: a new request may not be issued before the previous request has been answered. The response must occur before a final outcome. I treat `Activate Vendor`, `Reject Vendor`, and `Close Onboarding` as final/outcome events for this purpose.

6. **Sanctions escalation and legal opinion**  
   `Sanctions Escalation` may occur only after `Run Sanctions Screening`. If escalation occurs, `Obtain Legal Opinion` must eventually occur. Legal’s rule R5 says that, after escalation, the legal opinion must precede activation under all circumstances.

7. **Emergency exception is not observable**  
   R6 allows an emergency activation before legal opinion only when jointly authorized outside the event log. The log does not contain an `emergency` attribute or the joint authorization. Therefore, the exception is not directly checkable from the log.

8. **Temporal rules are warning rules**  
   R12 explicitly says temporal expectations are normative enough to flag but not automatically reject. Therefore, temporal-profile deviations produce warnings, not hard failures.

9. **Resource checks require explicit resource attributes**  
   Segregation-of-duties checks require `org:resource`. If the resource is missing for a relevant event, I treat the case as non-provable and conservatively fail the resource/data layer, with a data-quality flag.

10. **Post-activation bank changes**  
   I model `Change Bank Details` only in the pre-first-payment post-activation stage. Changes after `Release First Payment` are excluded from the procedural onboarding model and should be handled by a separate vendor-lifecycle process or external data check.

## R5/R6 conflict

R5 and R6 are directly incompatible unless R6 is treated as a controlled, auditable exception to R5.

### Resolution A — Strict legal-first policy, chosen for the implemented model

R5 is authoritative. If `Sanctions Escalation` occurs, `Obtain Legal Opinion` must occur before `Activate Vendor`. R6 is not encoded as an automatic exception because the event log lacks the emergency-authorization attribute. Emergency cases, if they exist, must be handled through an out-of-log waiver, incident ticket, or case attribute added by the system of record.

**Compliance risk:**  
This can create operational false positives. Genuine emergency activations may be flagged as violations, potentially delaying urgent vendor payments. If operations need emergency paths, strict modeling may encourage shadow workarounds or under-logging of emergency activations.

### Resolution B — Auditable emergency exception

R6 is treated as a controlled exception. Activation before legal opinion is allowed only if:

1. an external `emergency_joint_authorization` attribute or record is true;
2. `Obtain Legal Opinion` occurs within 24 hours of the emergency activation; and
3. the exception is surfaced for compliance review.

Because the given log lacks the authorization attribute, conformance cannot fully verify this exception. Cases would be marked `policy-dependent`, `warning`, or routed to manual attestation.

**Compliance risk:**  
This weakens Legal’s “under all circumstances” requirement. If the external authorization is not reliably captured, the exception can be abused. Sanctions exposure increases because activation can precede legal clearance.

### Chosen resolution

I choose **Resolution A — strict legal-first** for the implemented model. The emergency exception is represented only as an external, non-default policy alternative and must not silently override R5.

## 3. Explanation of modeling choices

### Concurrency

`Capture Master Data`, `Run Sanctions Screening`, and `Verify Bank Account` are placed in a parallel block after `Receive Onboarding Request`. The parallel operator synchronizes before `Classify Risk`, enforcing that risk classification requires completion of all three checks.

### Choices

After `Classify Risk`, an exclusive choice selects one primary outcome:

1. rejection;
2. low-risk acceptance with `Manager Approval`;
3. high-risk acceptance with `Enhanced Due Diligence` and `Compliance Approval`.

This encodes R1, R2, and R8 structurally.

### Clarification loops

The optional clarification loop allows zero or more paired `Request Clarification` / `Receive Clarification` cycles. The loop is placed before `Classify Risk` and again after `Classify Risk` but before the outcome choice.

This is a conservative approximation. R3 strictly requires response before the next request and before final outcome, but it does not necessarily require response before classification. The process-tree model is stricter because block-structured loops cannot easily represent an outstanding clarification obligation that may remain open across classification but must close before activation. The external check in Section 7 provides the more exact R3 state check.

### Terminal outcomes

The rejection branch terminates with `Close Onboarding`. Accepted branches terminate with `Release First Payment` followed by `Close Onboarding`, optionally after a bank-details repair loop.

### Post-activation behavior

A limited post-activation repair path is included:

```text
Activate Vendor
  -> Change Bank Details
  -> Suspend Vendor
  -> Verify Bank Account
  -> Release First Payment
  -> Close Onboarding
```

This models R11 for changes that occur before the first payment. Changes after `Release First Payment` are deliberately excluded from the procedural onboarding model. They should be handled by a separate vendor-lifecycle model or external data-aware check.

### Sanctions escalation placement

The procedural model allows `Sanctions Escalation` only in high-risk accepted branches, before activation. This matches the supplied tests and the strict R5 interpretation. If the business allows sanctions escalation on low-risk or rejection paths, the process tree must be extended. This limitation is disclosed rather than hidden.

```python
        ("Reject Vendor", "Manager Approval"): hard(),
        ("Reject Vendor", "Compliance Approval"): hard(),
        ("Manager Approval", "Compliance Approval"): hard(),
        ("Enhanced Due Diligence", "Manager Approval"): hard()
    }
}
```

## DECLARE rule semantics

| Template | Rule | Direction and meaning | Requirement(s) |
|---|---|---|---|
| `init` | `"Receive Onboarding Request"` | The first event of every case must be `Receive Onboarding Request`. | Backbone rule 1 |
| `exactly_one` | `"Receive Onboarding Request"` | The start event occurs exactly once. | Backbone rule 1 |
| `exactly_one` | `"Classify Risk"` | Classification occurs exactly once. | Backbone rule 3 |
| `exactly_one` | `"Close Onboarding"` | The case closes exactly once. | Backbone rule 5 |
| `existence` | `"Close Onboarding"` | Every case must eventually close. Redundant with `exactly_one` but explicit. | Backbone rule 5 |
| `response` | `("Request Clarification", "Receive Clarification")` | Every request must eventually be followed by a response. | R3 |
| `altresponse` | `("Request Clarification", "Receive Clarification")` | Every request must be answered before the next request. This is stronger than plain response for overlapping cycles. | R3 |
| `response` | `("Sanctions Escalation", "Obtain Legal Opinion")` | If escalation occurs, legal opinion must eventually occur. | R4 |
| `response` | `("Change Bank Details", "Suspend Vendor")` | If bank details change, suspension must eventually follow. | R11 |
| `response` | `("Manager Approval", "Activate Vendor")` | If manager approval occurs, activation must later occur. | R2, backbone |
| `response` | `("Compliance Approval", "Activate Vendor")` | If compliance approval occurs, activation must later occur. | R2, backbone |
| `response` | `("Activate Vendor", "Release First Payment")` | Activation must eventually be followed by first payment. | Backbone rule 5 |
| `response` | `("Release First Payment", "Close Onboarding")` | First payment must eventually be followed by closure. | Backbone rule 5 |
| `response` | `("Reject Vendor", "Close Onboarding")` | Rejection must eventually be followed by closure. | Backbone rule 5 |
| `precedence` | `("Capture Master Data", "Classify Risk")` | Classification may occur only if master-data capture occurred before. | Backbone rule 3 |
| `precedence` | `("Run Sanctions Screening", "Classify Risk")` | Classification may occur only if sanctions screening occurred before. | Backbone rule 3 |
| `precedence` | `("Verify Bank Account", "Classify Risk")` | Classification may occur only if bank verification occurred before. | Backbone rule 3 |
| `precedence` | `("Run Sanctions Screening", "Sanctions Escalation")` | Escalation may occur only if sanctions screening occurred before. | R7 |
| `precedence` | `("Request Clarification", "Receive Clarification")` | A received clarification may occur only if a request occurred before. | R3 |
| `precedence` | `("Classify Risk", "Reject Vendor")` | Rejection may occur only after classification. | Backbone rule 4 |
| `precedence` | `("Classify Risk", "Activate Vendor")` | Activation may occur only after classification. | Backbone rule 4 |
| `precedence` | `("Classify Risk", "Manager Approval")` | Manager approval may occur only after classification. | Backbone rule 4 |
| `precedence` | `("Classify Risk", "Compliance Approval")` | Compliance approval may occur only after classification. | Backbone rule 4 |
| `precedence` | `("Classify Risk", "Enhanced Due Diligence")` | EDD may occur only after classification. | Backbone rule 4 |
| `precedence` | `("Enhanced Due Diligence", "Compliance Approval")` | Compliance approval may occur only after EDD. | Backbone high-risk route |
| `noncoexistence` | `("Reject Vendor", "Activate Vendor")` | Rejection and activation may not both occur, regardless of order. | R1 |
| `noncoexistence` | `("Reject Vendor", "Manager Approval")` | A rejected case may not contain manager approval. | R2 |
| `noncoexistence` | `("Reject Vendor", "Compliance Approval")` | A rejected case may not contain compliance approval. | R2 |
| `noncoexistence` | `("Manager Approval", "Compliance Approval")` | The two approvals may not co-occur. | R2, R8 |
| `noncoexistence` | `("Enhanced Due Diligence", "Manager Approval")` | EDD and manager approval may not co-occur. | R8 |

## Important DECLARE distinctions

- **Response vs precedence:**  
  `response(A, B)` is activation-driven: if A occurs, B must occur later.  
  `precedence(A, B)` is target-driven: B may occur only if A occurred before.

- **Alternate response vs chain response:**  
  `altresponse(Request Clarification, Receive Clarification)` requires a response before the next request, but other events may occur between request and response.  
  `chainresponse` would require the response to be the immediate next event, which is too strong for this process.

- **Noncoexistence vs nonsuccession:**  
  `noncoexistence(A, B)` forbids both activities in the same case, regardless of order.  
  `nonsuccession(A, B)` would only forbid A followed by B, but would still allow B followed by A. For R1 and R8, noncoexistence is the appropriate template.

- **Not encoded directly:**  
  R5’s conditional precedence “if escalation occurred, legal opinion before activation” is not encoded as a global DECLARE precedence rule because `precedence("Obtain Legal Opinion", "Activate Vendor")` would require legal opinion for every activation. The conditional check is placed in the external validation layer.

## Explanation and orientation

### `equivalence`

- `("Request Clarification", "Receive Clarification")`  
  If either activity occurs, the other must also occur. This supports R3’s paired request/response semantics. It does not by itself enforce ordering; ordering is supported by `always_before`.

### `always_before`

For every pair `(A, B)`, the intended meaning is: **whenever both A and B occur in a case, A occurs before B**.

| Pair | Meaning |
|---|---|
| `("Receive Onboarding Request", "Classify Risk")` | Classification occurs after case receipt. |
| `("Capture Master Data", "Classify Risk")` | Classification occurs after master-data capture. |
| `("Run Sanctions Screening", "Classify Risk")` | Classification occurs after sanctions screening. |
| `("Run Sanctions Screening", "Sanctions Escalation")` | Escalation occurs only after screening. |
| `("Request Clarification", "Receive Clarification")` | A clarification response occurs after the corresponding request. |
| `("Sanctions Escalation", "Obtain Legal Opinion")` | If both occur, legal opinion occurs after escalation. |
| `("Classify Risk", "Reject Vendor")` | Rejection occurs after classification. |
| `("Classify Risk", "Activate Vendor")` | Activation occurs after classification. |
| `("Classify Risk", "Manager Approval")` | Manager approval occurs after classification. |
| `("Classify Risk", "Compliance Approval")` | Compliance approval occurs after classification. |
| `("Classify Risk", "Enhanced Due Diligence")` | EDD occurs after classification. |
| `("Manager Approval", "Activate Vendor")` | If manager approval occurs, it precedes activation. |
| `("Enhanced Due Diligence", "Compliance Approval")` | Compliance approval follows EDD. |
| `("Compliance Approval", "Activate Vendor")` | If compliance approval occurs, it precedes activation. |
| `("Activate Vendor", "Release First Payment")` | First payment follows activation. |
| `("Release First Payment", "Close Onboarding")` | Closure follows first payment. |
| `("Reject Vendor", "Close Onboarding")` | Closure follows rejection. |

I deliberately omitted `("Verify Bank Account", "Classify Risk")` from `always_before` because R11 can introduce a later re-verification after classification. A global always-before constraint on every `Verify Bank Account` occurrence would conflict with the post-activation repair loop.

### `always_after`

This is left empty to avoid inverse duplication of the `always_before` constraints. All ordering constraints are intentionally represented in the `always_before` orientation.

### `never_together`

These pairs are treated symmetrically. They duplicate the DECLARE noncoexistence rules and provide a fast structural sanity check.

### `activ_freq`

The frequency constraints encode at-most-once behavior for terminal and approval activities. `Verify Bank Account`, `Change Bank Details`, and `Suspend Vendor` allow more than one occurrence because R11 can require re-verification after bank-detail changes. The finite sets are approximations; if more than three verifications or more than two bank changes are legitimate, the sets must be widened.

### `directly_follows`

This is intentionally empty. The policy says that certain activities must eventually follow others, but it does not require immediate succession. For example, `Obtain Legal Opinion`, clarification events, or bank-change events may intervene between activation and payment.

## Overlap and disagreement with other layers

- The Log Skeleton duplicates some procedural and DECLARE constraints, especially exclusions and ordering.
- It is less expressive than DECLARE. It cannot express conditional response obligations such as “if escalation occurs, legal opinion must eventually occur” except through coarse pairwise constraints.
- It intentionally avoids constraints that would conflict with loops, especially repeated `Verify Bank Account`.
- It does not encode R5’s conditional legal-before-activation rule. That remains in the procedural high-risk variants and the external validation layer.

# 6. Temporal Profile

```python
temporal_profile = {
    ("Request Clarification", "Receive Clarification"): (48 * 3600, 24 * 3600),
    ("Sanctions Escalation", "Obtain Legal Opinion"): (12 * 3600, 6 * 3600),
    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)
}

zeta = 2.0
```

With `zeta = 2.0`, the expected intervals are:

| Pair | Mean | Std | Interval in hours |
|---|---:|---:|---:|
| `Request Clarification -> Receive Clarification` | 48 | 24 | `[0, 96]` |
| `Sanctions Escalation -> Obtain Legal Opinion` | 12 | 6 | `[0, 24]` |
| `Activate Vendor -> Release First Payment` | 72 | 36 | `[0, 144]` |

The lower bounds truncate at zero because elapsed time cannot be negative.

## Why temporal deviations are warnings

R12 says these temporal expectations are “normative enough to flag but not automatically reject a case.” Therefore:

- temporal-profile violations are treated as **warnings**;
- they do not by themselves make the overall verdict `fail`;
- a case can have a temporal warning and still be procedurally and legally conformant;
- repeated or extreme temporal warnings may trigger operational review, but they are not hard policy violations.

This separation is important because temporal deviations can have legitimate explanations: vendor responsiveness, external legal review, payment batching, weekends, holidays, or missing calendar-time information in the log.

# 7. Resource- and Data-Aware Checks

The following executable-style Python checks cover requirements that activity-only models cannot fully express: segregation of duties, emergency-policy conditionality, exact clarification-state checking, and conditional R11 checks.

Assumptions:

- `df` is an event dataframe.
- `time:timestamp` has been normalized to numeric seconds since case start.
- `org:resource` identifies the performer.
- `case_attrs` may contain `emergency_joint_authorization`.
- Missing `org:resource` on relevant events causes a conservative failure.
- Missing emergency authorization under the permissive alternative causes a policy-dependent warning, not silent pass.

```python
import pandas as pd

HOUR = 3600

FINAL_OUTCOMES = {
    "Activate Vendor",
    "Reject Vendor",
    "Close Onboarding"
}


def first_ts(case, activity):
    ev = case[case["concept:name"] == activity].sort_values("time:timestamp")
    if ev.empty:
        return None
    return ev.iloc[0]["time:timestamp"]


def resources_of(case, activity):
    ev = case[case["concept:name"] == activity]
    missing = ev["org:resource"].isna().any()
    return set(ev["org:resource"].dropna().unique()), bool(missing)


def check_case(case, case_attrs=None, strict_R5=True):
    """
    Returns errors and warnings for one case.

    Required event attributes:
      - case:concept:name
      - concept:name
      - time:timestamp
      - org:resource

    Optional case attribute for permissive R6:
      - emergency_joint_authorization
    """
    case_attrs = case_attrs or {}
    errors = []
    warnings = []

    # ---------------------------------------------------------------
    # Basic data quality
    # ---------------------------------------------------------------
    if case["time:timestamp"].isna().any():
        errors.append("Data quality: missing timestamp(s).")

    # ---------------------------------------------------------------
    # R3 exact clarification-state check
    # ---------------------------------------------------------------
    clar_events = case[
        case["concept:name"].isin(
            ["Request Clarification", "Receive Clarification"] + list(FINAL_OUTCOMES)
        )
    ].sort_values("time:timestamp")

    open_request = False
    final_seen = False

    for _, row in clar_events.iterrows():
        name = row["concept:name"]

        if name == "Request Clarification":
            if final_seen:
                errors.append("R3: Request Clarification after final outcome.")
            if open_request:
                errors.append("R3: new Request Clarification before previous Receive Clarification.")
            open_request = True

        elif name == "Receive Clarification":
            if not open_request:
                errors.append("R3: Receive Clarification without open Request Clarification.")
            open_request = False

        elif name in FINAL_OUTCOMES:
            if open_request:
                errors.append(f"R3: final outcome {name} while clarification request is open.")
            final_seen = True

    # ---------------------------------------------------------------
    # R9 segregation of duties
    # ---------------------------------------------------------------
    verify_resources, verify_missing = resources_of(case, "Verify Bank Account")
    capture_resources, capture_missing = resources_of(case, "Capture Master Data")
    activate_resources, activate_missing = resources_of(case, "Activate Vendor")

    approval_events = case[
        case["concept:name"].isin(["Manager Approval", "Compliance Approval"])
    ]

    # Verify Bank Account vs applicable approval
    if not approval_events.empty:
        if verify_missing:
            errors.append("R9: missing org:resource for Verify Bank Account; cannot prove separation.")

        for _, app in approval_events.iterrows():
            app_resource = app.get("org:resource")
            app_name = app.get("concept:name")

            if pd.isna(app_resource):
                errors.append(f"R9: missing org:resource for {app_name}.")
            elif app_resource in verify_resources:
                errors.append(
                    f"R9: same resource performed Verify Bank Account and {app_name}: {app_resource}."
                )

    # Capture Master Data vs Activate Vendor
    if not activate_resources:
        # No activation; this part of R9 is not applicable.
        pass
    else:
        if capture_missing or activate_missing:
            errors.append("R9: missing org:resource for Capture Master Data or Activate Vendor.")
        elif capture_resources & activate_resources:
            errors.append(
                "R9: same resource performed Capture Master Data and Activate Vendor: "
                f"{sorted(capture_resources & activate_resources)}."
            )

    # Optional PM4Py approximation for fixed pairs:
    # pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Manager Approval")
    # pm4py.filter_four_eyes_principle(log, "Verify Bank Account", "Compliance Approval")
    # pm4py.filter_four_eyes_principle(log, "Capture Master Data", "Activate Vendor")
    #
    # The custom checks above are authoritative because they handle missing resources,
    # multiple approvals, and the applicable-approval semantics explicitly.

    # ---------------------------------------------------------------
    # R4 / R5 / R6 sanctions escalation and legal opinion
    # ---------------------------------------------------------------
    esc_ts = first_ts(case, "Sanctions Escalation")
    act_ts = first_ts(case, "Activate Vendor")

    legal_events = case[case["concept:name"] == "Obtain Legal Opinion"].sort_values("time:timestamp")

    if esc_ts is not None:
        legal_after_esc = legal_events[legal_events["time:timestamp"] > esc_ts]

        if legal_after_esc.empty:
            errors.append("R4: Sanctions Escalation occurred without later Obtain Legal Opinion.")

        if act_ts is not None:
            legal_after_esc_before_act = legal_after_esc[
                legal_after_esc["time:timestamp"] < act_ts
            ]

            if legal_after_esc_before_act.empty:
                if strict_R5:
                    errors.append(
                        "R5: Activate Vendor occurred before Obtain Legal Opinion after Sanctions Escalation."
                    )
                else:
                    auth = case_attrs.get("emergency_joint_authorization", None)
                    legal_after_act = legal_after_esc[
                        legal_after_esc["time:timestamp"] > act_ts
                    ]

                    if auth is True and not legal_after_act.empty:
                        first_legal_after_act = legal_after_act.iloc[0]["time:timestamp"]
                        if first_legal_after_act - act_ts <= 24 * HOUR:
                            warnings.append(
                                "R6: emergency activation before legal opinion; "
                                "authorization present and opinion within 24 hours."
                            )
                        else:
                            errors.append(
                                "R6: emergency activation used, but Obtain Legal Opinion "
                                "did not occur within 24 hours."
                            )
                    elif auth is True:
                        errors.append(
                            "R6: emergency authorization present, but no later Obtain Legal Opinion."
                        )
                    else:
                        warnings.append(
                            "R6: activation before legal opinion after escalation, "
                            "but emergency joint authorization is missing/unverified."
                        )

    # ---------------------------------------------------------------
    # R11 post-activation bank-detail change checks
    # ---------------------------------------------------------------
    release_ts = first_ts(case, "Release First Payment")
    change_events = case[case["concept:name"] == "Change Bank Details"].sort_values("time:timestamp")

    for _, change in change_events.iterrows():
        change_ts = change["time:timestamp"]

        if act_ts is not None and change_ts > act_ts:
            later_suspend = case[
                (case["concept:name"] == "Suspend Vendor") &
                (case["time:timestamp"] > change_ts)
            ]

            if later_suspend.empty:
                errors.append("R11: Change Bank Details after activation without later Suspend Vendor.")

            if release_ts is not None and release_ts > change_ts:
                later_verify_before_release = case[
                    (case["concept:name"] == "Verify Bank Account") &
                    (case["time:timestamp"] > change_ts) &
                    (case["time:timestamp"] < release_ts)
                ]

                if later_verify_before_release.empty:
                    errors.append(
                        "R11: Change Bank Details after activation without re-verification "
                        "before later Release First Payment."
                    )

    return {
        "errors": errors,
        "warnings": warnings
    }
```

## Missing-attribute policy

| Missing attribute | Affected check | Treatment |
|---|---|---|
| `org:resource` on `Verify Bank Account`, approval, `Capture Master Data`, or `Activate Vendor` | R9 SoD | Conservative failure: cannot prove segregation. |
| `time:timestamp` | All temporal/order checks | Failure or non-evaluation; ordering cannot be trusted. |
| `emergency_joint_authorization` | R6 permissive exception | Under strict R5, irrelevant; activation before legal opinion fails. Under permissive R6, mark policy-dependent/warning and route to manual attestation. |
| Risk classification attribute | Route correctness | Not directly checkable; route is inferred from activities. This is a blind spot. |
| Bank-details data object | R11 semantic change detection | We rely on the `Change Bank Details` activity. If the activity is missing but data changed, the model is blind. |

# 9. Contradictions, Redundancies, and Blind Spots

## Duplicated enforcement across layers

Several requirements are enforced in more than one layer:

- R1 appears in the procedural XOR, DECLARE `noncoexistence`, and Log Skeleton `never_together`.
- R7 appears in DECLARE `precedence`, Log Skeleton `always_before`, and procedural placement.
- R8 appears in procedural route exclusivity, DECLARE `noncoexistence`, and Log Skeleton `never_together`.
- R10 appears in procedural structure and Log Skeleton `activ_freq`.

This redundancy can be useful defense-in-depth, but it creates a maintenance risk. If the process model changes but the DECLARE or Log Skeleton models are not regenerated, the layers can produce contradictory diagnostics. A policy registry should map each requirement to its authoritative layer and derived checks.

## Constraints that become inconsistent under loops or post-activation changes

Loops expose weaknesses in simple pairwise constraints.

Example: `Verify Bank Account` occurs before `Classify Risk` in the normal flow, but R11 may require another `Verify Bank Account` after activation and after classification. Therefore, a global Log Skeleton constraint `("Verify Bank Account", "Classify Risk")` would be too strong if it quantifies over every occurrence. I omitted that constraint from the Log Skeleton for this reason.

Similarly, `Change Bank Details` after `Release First Payment` is not represented in the procedural model. If such changes occur in reality, the onboarding model will either reject them or remain blind to them. They belong to a vendor-lifecycle process.

## Vacuity in declarative rules

Many DECLARE rules are vacuous when their source or target activity does not occur.

Examples:

- `response("Sanctions Escalation", "Obtain Legal Opinion")` is vacuous if there is no escalation.
- `precedence("Run Sanctions Screening", "Sanctions Escalation")` is vacuous if there is no escalation.
- `noncoexistence` rules pass trivially when one of the activities is absent.
- Temporal-profile checks only evaluate pairs that are observed. Missing target events are not temporal violations; they must be caught by response, procedural, or external checks.

Vacuity is not inherently bad, but it means that a “pass” from a declarative checker may mean “not applicable” rather than “positively compliant.”

## Missing case attributes

The event log lacks several attributes that are needed for full policy evaluation:

- `emergency_joint_authorization` for R6;
- explicit risk classification, to verify that the chosen route matches the risk class;
- bank-account data object state, to verify whether `Change Bank Details` truly changed relevant data;
- role information, to interpret resource identities for segregation of duties;
- waiver or exception identifiers, to distinguish authorized deviations from violations.

Without these attributes, conformance checking must either fail conservatively or produce policy-dependent warnings.

## Timestamp-only limitations

Temporal profiles use only elapsed time between activity timestamps. They do not capture:

- working hours, weekends, or holidays;
- time zones;
- waiting for external parties;
- whether an activity was delayed because a prior obligation was unresolved;
- causal relationships beyond observed order.

Therefore, temporal warnings should be interpreted operationally, not as automatic compliance violations.

## Risk of treating support/confidence metadata as normative truth

The DECLARE model uses `support: 1.0` and `confidence: 1.0` as normative policy settings. In discovered DECLARE models, support and confidence describe historical frequency or rule strength. They are not moral or legal authority.

Risks include:

- treating a frequently violated rule as acceptable because confidence is low;
- treating a rare but critical sanctions violation as acceptable because support is low;
- allowing historical behavior to override current policy;
- confusing statistical fit with regulatory compliance.

For governance, policy rules should be versioned, owned, and explicitly marked as hard or advisory. Support and confidence should be diagnostic metadata, not silent policy switches.

# 10. Deployment Recommendation

## Canonical procedural representation

Use the ProcessTree as the human-readable canonical model, but convert it to an accepting Petri net for production alignment/replay if PM4Py token-based replay is desired. The procedural model should remain the canonical representation of the stable backbone:

- start;
- concurrent checks;
- classification;
- exclusive outcome routes;
- activation/payment/rejection closure;
- limited post-activation bank-change repair loop.

## Authoritative policy layer

No single formalism should be authoritative for all requirements.

Recommended authority assignment:

| Policy area | Authoritative layer |
|---|---|
| Stable control-flow backbone | Procedural model |
| Mutual exclusion of outcomes/approvals | Procedural model, backed by DECLARE/Log Skeleton |
| Eventual response obligations | DECLARE |
| Exact clarification-state obligations | External state check |
| Conditional legal-before-activation after escalation | External validation layer under strict R5 |
| Emergency exception | External policy/data layer with explicit authorization attribute |
| Segregation of duties | Resource/data-aware validation layer |
| Temporal expectations | Temporal profile as warning layer |

## Recommended conformance-check order

1. **Data-quality validation**  
   Check required attributes: case ID, activity label, timestamp, resource. Flag missing resources and missing timestamps before substantive conformance.

2. **Procedural alignment**  
   Replay the trace against the procedural model. Detect impossible control flow, missing mandatory activities, invalid terminal outcomes, and unsupported post-activation behavior.

3. **DECLARE conformance**  
   Check temporal-logic obligations such as response, precedence, and noncoexistence. Use this as a secondary hard layer, not the sole authority.

4. **Log Skeleton sanity check**  
   Run fast structural checks. Treat failures as strong indicators but investigate mismatches caused by loops or repeated activities.

5. **External conditional/resource/data checks**  
   Run SoD checks, clarification-state checks, R5 legal-before-activation checks, R6 emergency exception checks, and R11 conditional bank-change checks.

6. **Temporal profile check**  
   Produce warnings for elapsed-time deviations. Do not fail a case solely because of temporal-profile warnings.

## Surfacing contradictory findings

Contradictions should be surfaced explicitly, not silently reconciled.

Recommended UI/API behavior:

- Show each layer’s result separately.
- Show the requirement IDs involved.
- Show the earliest decisive event and timestamp.
- Distinguish `hard failure`, `warning`, `policy-dependent`, and `not evaluated`.
- If procedural and DECLARE disagree, show which layer is authoritative for that requirement.
- If R5 and R6 conflict, show a policy-conflict banner and require an explicit waiver if the permissive emergency policy is being invoked.
- If a resource is missing, show a data-quality blocker rather than pretending the SoD check passed.
- If temporal warnings coexist with hard failures, show the hard failure as the primary reason and list temporal warnings as secondary observations.

This layered, requirement-owned approach avoids forcing every rule into one formalism, preserves the R5/R6 conflict for governance review, and prevents activity-only models from silently claiming compliance for resource-, data-, and exception-sensitive obligations.
