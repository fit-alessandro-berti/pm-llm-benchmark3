**Key discussion points**

- **True concurrency vs interleaving** – POWL `StrictPartialOrder` expresses potential concurrency through absent edges. The Petri net translation reduces this to interleaving, which is behaviourally equivalent for tracebased verification but discards the ability to distinguish “must be concurrent” from “may be concurrent”. All subsequent BPMN artefacts therefore only guarantee interleaving semantics.  
- **Missing edge between Optional Legal and Verification** – No edge exists between `optional_legal` and `verification_loop`, signalling concurrency. The Petri net correctly does not force an ordering. BPMN visualisation may place the legal and verification blocks one above the other, suggesting a sequence; gateways are not visually ambiguous at the syntactic level, but the spatial layout is not a semantic commitment.  
- **Silent optional behaviour** – The `skip_legal` silent transition is represented as a transition in the Petri net. In BPMN it becomes an exclusive gateway branch with no activity; this is standard but can be misinterpreted as “no action required”. After tauhiding the effect is identical.  
- **Binaryloop semantics** – The POWL `LOOP` operator enforces “body at least once, redo optional”. The Petri net translation uses a `do` subnet and a redo transition that loops back. BPMN marks this with a loop marker on the subprocess, but the internal “redo” activity may be placed outside the visual loop boundary; explicit annotation is needed.  
- **Join before Release Change** – The ANDjoin is correctly transferred as a synchronising gateway, verified by soundness and trace exploration.  
- **Activitylabel uniqueness** – All visible labels are unique; no label clash occurs.  
- **Initial and final markings** – Preserved as exactly one source place and one sink place in the workflow net; BPMN uses start and end events.  
- **Gateway ambiguity** – In the direct PetritoBPMN conversion, routing nodes derived from silent transitions may appear as gateways with no label, which could be misread. The audit verifies that the gateway logic (xor, and) corresponds to the net structure.

def explore_visible_traces(net, im, fm, max_visible_len=10, max_loop_iter=3):
    """
    DFS that hides silent transitions (label None).
    A trace is complete when marking == fm exactly.
    Prevents infinite silent loops by bounding the number of consecutive silent steps
    and the total length of visible sequence.
    """
    visible_traces = set()
    # Stack: (marking, visible_trace, silent_steps, loop_counts) where loop_counts is a dict mapping loop-entry-place to times visited
    # We'll limit total path length to avoid explosion.
    # Use list of markings and a depth limit.
    stack = []
    initial_state = (im, tuple(), 0, {})  # marking, vis_trace (tuple), sil_steps, loop context placeholder
    stack.append(initial_state)
    # For termination, we also track max depth.
    while stack:
        mk, vis, sil_steps, loop_ctx = stack.pop()
        if len(vis) > max_visible_len:
            continue
        if mk == fm:
            # Exact final marking reached
            visible_traces.add(vis)
            continue
        if sil_steps > 5:   # avoid infinite silent loops
            continue
        enabled = pm4py.get_enabled_transitions(net, mk)
        for t in enabled:
            new_mk = pm4py.execute_transition(net, mk, t)
            if t.label is None:
                # silent transition
                stack.append((new_mk, vis, sil_steps + 1, loop_ctx))
            else:
                # visible transition
                # Enforce loop bound: if t label is Correct Defect, increment a counter to limit iterations
                new_loop_ctx = dict(loop_ctx)
                if t.label == "Correct Defect":
                    count = new_loop_ctx.get("loop", 0) + 1
                    if count > max_loop_iter:
                        continue
                    new_loop_ctx["loop"] = count
                stack.append((new_mk, vis + (t.label,), 0, new_loop_ctx))
    return visible_traces

The exploration hides silent transitions and requires exactly the final marking for a completed trace. # 6. Visual-Semantics Review

While the underlying converted BPMN model is behaviourally faithful to the Petri net, the **visual rendering** can be misread in several ways:

1. **Parallel gateways** – The ANDsplit after registration and before release are often drawn as two distinct gateways separated by vertical lanes. If the diagram places the “legal review” and “verification loop” blocks sequentially, a reader might erroneously infer that legal review must finish before verification can start. This is a layout artefact, not a semantic constraint.

2. **Exclusive gateways with silent branches** – The optional legal review is an XOR gateway with one branch containing the `Legal Review` task and the other branch empty (silent). A reviewer may not realise that the empty branch represents an immediate skip, potentially confusing the decision point with an “else” that does nothing.

3. **Loop visualisation** – The verification loop may be shown as a subprocess with a loop marker, while the redo activity (`Correct Defect`) might be placed inside that subprocess or outside. If placed outside, the loop semantics (go back after redo) may become unclear. A textual annotation should state: “After each `Inspect Trial`, either proceed to release or perform `Correct Defect` and repeat the trial.”

4. **Silent routing nodes** – The conversion introduces silent transitions that become gateway nodes without labels. A viewer might mistake them for decision points that require human input, whereas they are purely for routing.

5. **Apparent ordering from grid placement** – BPMN layout algorithms often arrange blocks in a topdown or leftright grid. The two concurrent branches (`optional_legal` and `verification_loop`) will likely be placed one above the other, creating a visual sequence. Without explicit annotations (“these two blocks may happen in any order, including overlapping”), a stakeholder could enforce the visual order in a workflow engine.

**Recommended annotations and documentation**  

- Add a note to the diagram: *“The legal review branch and the verification loop may overlap; no ordering is enforced between them.”*  
- Mark the XOR gateway with a label “Optional Legal Review” and note that the empty branch means “Skip”.  
- Use a callout on the loop subprocess: *“At least one trial (Configure  Inspect) is mandatory. After each trial, the defect may be corrected, triggering another trial.”*  
- For any silent routing node, add a small text annotation “” to indicate that it is not a user task.  
- Provide a tracebased explanation alongside the diagram, e.g., the positive witnesses from Section1.

# 7. Rejection Criteria

A conversion result (BPMN model, process tree, or roundtripped net) should be rejected or quarantined if any of the following conditions hold:

1. **Unsoundness** – The Petri net or BPMN model is not sound (liveness or boundedness violation, improper completion). Soundness check using `pm4py.check_soundness` fails.  
2. **Initial/Final Marking Mismatch** – The initial marking of the converted net does not correspond to the source start, or the final marking does not correspond to exactly one token in the sink place after termination.  
3. **Loss of Mandatory Synchronisation** – The model allows `Release Change` to fire before both the legal branch and the verification loop have completed. This is a direct violation of invariant I5.  
4. **Admission of a Forbidden Interleaving** – The model allows a trace where `Assess Risk` is completely missing, or where `Inspect Trial` occurs before `Configure Trial` inside a loop iteration.  
5. **Collapse of Optional Behaviour** – The optional legal review becomes mandatory (every path includes `Legal Review`), or the loop forces at least two iterations. This violates I4 and I3.  
6. **Failed ExactFinalMarking Test** – The bounded trace exploration reveals a trace that reaches the final marking in the source net but not in the converted net, or viceversa, indicating a behavioural difference even within the exploration bound.  
7. **Conversion Exception or `None` Result** – Any conversion call returns `None` or raises an exception (e.g., processtree conversion fails). The pipeline must document this and not silently fall back to an alternative without explicit warning.  
8. **Duplicate or Missing Activity Labels** – A visible activity label appears more often in the converted model than in the source (e.g., two transitions with the same label), or a required label disappears.

These criteria combine technical validation (soundness, marking equality) with semantic checks derived from the source invariants.

# 8. Canonical Representation Recommendation

- **Authoritative canonical model**: The original POWL (`source_powl`) serves as the single source of truth. Its textual definition is unambiguous, supports true concurrency (via partial order), and can be directly manipulated if needed.  
- **Derivative artefacts**:  
  - The **accepting Petri net** (produced by `convert_to_petri_net`) is the primary behavioural artefact for verification, simulation, and further conversion.  
  - **BPMN diagrams** are purely for stakeholder communication; they are generated on demand and must **never** be edited manually.  
  - **Any process tree** that might succeed from the Petri net is considered experimental; it is not required and should not be stored as a trusted representation unless it passes full equivalence checks.  
- **Validation evidence required for each derivative**:  
  - Soundness certificate.  
  - Footprint comparison (at least start/end activity sets match).  
  - Reachability graph isomorphism (or traceset equality up to a bounded depth).  
  - Positive/negative witness tests (as defined in Section5) to confirm source invariants.  
  - Documentation of visualsemantic caveats.  
- **Processtree intermediate**: It can be allowed **only if** the conversion succeeds **and** the resulting BPMN (after roundtrip) yields an accepting Petri net that is traceequivalent to the direct PetrifromPOWL under exhaustive bounded exploration. Because this model is not blockstructured, the processtree pipeline should be treated as “not supported” by default; if a future version of PM4Py succeeds, the equivalence proof must be reestablished.  
- **Avoiding roundtrip drift**:  
  - All edits must be applied to the POWL source.  
  - After each change, regenerate the Petri net and BPMN from scratch.  
  - Automatically run the full validation suite; reject any change that introduces a violation.  
  - Keep a changelog that records the POWL diff and validation results.

# 9. Residual Uncertainty

Even if all provided tests pass, the following claims cannot be fully established by this validation:

1. **Exact behavioural equivalence for unbounded repeating loops** – The bounded trace exploration (max two iterations of the verification loop) covers the typical scenarios. An unbounded property (e.g., whether an infinite repetition of `Correct Defect` followed by trial still eventually reaches `Archive Change` correctly) is not fully proven without a full statespace proof, though soundness provides a guarantee for the Petri net.  
2. **True concurrency preservation** – The Petri net and BPMN rely on interleaving semantics. The fact that two tasks *could* be truly concurrent (rather than merely interleaved) in a distributed execution is lost; we cannot validate from the model alone that a runtime engine would preserve partialorder behaviour identical to the POWL.  
3. **Semantic interpretation of the silent skip** – After hiding `skip_legal`, a trace that omitted `Legal Review` could be “the skip was taken” or “legal review was never initiated because the branch was completely ignored”. The source POWL does not distinguish these two, and the validation treats them as equivalent. Outside the traceset view, such a difference might matter for compliance or audit logs, but it is beyond the model’s specification.  
4. **BPMN gateway behaviour in external engines** – Even if the BPMN diagram is structurally correct, an executing engine may impose additional semantics (e.g., exclusive gateways require a condition expression). The validation cannot guarantee that the generated diagram’s default gateways will behave identically across all BPMN runtimes.  

These uncertainties should be documented when handing the converted models to implementation teams, and additional domainspecific validation (e.g., execution simulation on a target engine) is recommended where absolute fidelity is required.
