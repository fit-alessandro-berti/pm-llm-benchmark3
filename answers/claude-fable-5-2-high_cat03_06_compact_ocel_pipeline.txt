## 1. Modeling assumptions

**Object types (singular, capitalized exactly like this):** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. There are 12 objects. Amounts are not objects: the payment amount is an event attribute (`amount` column in `events`, NaN for every non-payment event).

**Event identifiers:** `e01` … `e17`, in narrative order. All timestamps are timezone-aware UTC (`datetime64[..., UTC]`).

**E2O qualifier vocabulary.** A qualifier names the role the object plays in the event. Each (activity, object type) pair has exactly one qualifier, and the code enforces this.

| Activity | Object type → qualifier |
|---|---|
| Create Order | Order → `created order` |
| Add Item | Item → `added item`; Order → `receiving order` |
| Reserve Stock | Item → `reserved item`; Order → `requesting order` |
| Pack Package | Package → `packed package`; Item → `packed item`; Order → `fulfilled order` |
| Dispatch Package | Package → `dispatched package`; Delivery → `dispatching delivery` |
| Issue Invoice | Invoice → `issued invoice`; Order → `billed order` |
| Record Payment | Payment → `recorded payment`; Invoice → `settled invoice` |
| Confirm Delivery | Delivery → `confirmed delivery` |
| Close Order | Order → `closed order` |

**O2O direction convention.** A row reads "`ocel:oid` *qualifier* `ocel:oid_2`", so the qualifier is a verb whose subject is the first column: Order `contains` Item, Package `packs` Item, Delivery `carries` Package, Invoice `bills` Order, Payment `partially_settles` / `completes_settlement` Invoice. No inverse rows are stored. M1 gets `partially_settles` and M2 gets `completes_settlement`, because the narrative says the two payments together settle V1 and M2 is the last one. An invoice total of 250 is therefore an inference, and it is not stored anywhere. The conservative variant is `partially_settles` for both.

**Do logistics and financial events relate directly to Orders and Items?** Only where the narrative says so.

- Direct (source level): Reserve Stock and Pack Package relate to the Items and Orders involved, and Issue Invoice relates to both Orders, because the text states this.
- Not direct: Dispatch Package relates only to its Package and Delivery, Confirm Delivery only to its Delivery, and Record Payment only to its Payment and V1. The narrative gives no allocation of M1 or M2 to O100 or O200, so linking payments to Orders would invent a fact.
- One schema inference: `e08 → O100`. The narrative states the Order link for `e07` but is silent for `e08`. I apply the same Pack Package relation schema to both events, so the activity has one consistent object-type signature. The row is listed in `INFERRED_SOURCE_E2O` so a reviewer can drop it.

**Trade-off.** Direct relations are trustworthy but leave Order and Item lifecycles incomplete: an Order never "sees" dispatch, delivery, or payment. Propagated relations complete those lifecycles but copy events to objects that did not observably take part, which inflates frequencies, creates convergence, and encodes assumptions such as "every payment on V1 belongs to every billed Order".

**Keeping propagation apart from source facts.** Three safeguards:

1. `relations` contains source-level rows only, and `ocel` is built from it. Validation fails if a `derived:` qualifier appears there.
2. Propagated rows are generated by declarative rules from source E2O plus O2O, carry a `derived:` qualifier prefix, live in `derived_relations` / `relations_propagated`, and feed a second object, `ocel_propagated`.
3. Both logs share the same `events`, `objects`, and `o2o`, so the business story is identical. Only the analytical E2O lens differs.

**Version-dependent PM4Py assumptions.** I ran the code block end to end on PM4Py 2.7.23 with pandas 3.0, and the numbers quoted in sections 4 and 5 come from that run.

- The constructor call is isolated in `build_ocel`. If a version lacks the `o2o` keyword, build with `OCEL(events=..., objects=..., relations=...)` and assign `ocel.o2o = o2o` inside that function. The DataFrames do not change.
- `pm4py.discover_otg` and `pm4py.discover_etot` exist only in recent 2.7.x releases. On older versions, upgrade or drop those two dictionary entries.
- `discover_oc_petri_net` returns a dict or a dict-like `OCPetriNet` object depending on the version. The code only uses `["petri_nets"]`, which works for both.
- Older releases normalise timestamps to naive datetimes. If a version rejects tz-aware values, convert once, right after `events` is built.

## 2. Complete Python pipeline

```python
import pandas as pd
import pm4py
from pm4py.objects.ocel.obj import OCEL

# ---------------------------------------------------------------------------
# 0. Column names and controlled vocabularies
# ---------------------------------------------------------------------------
EID, ACT, TS = "ocel:eid", "ocel:activity", "ocel:timestamp"
OID, OTYPE, QUAL, OID2 = "ocel:oid", "ocel:type", "ocel:qualifier", "ocel:oid_2"
RELATION_COLUMNS = [EID, ACT, TS, OID, OTYPE, QUAL]
DERIVED_PREFIX = "derived:"

# ---------------------------------------------------------------------------
# 1. objects
# ---------------------------------------------------------------------------
OBJECTS_BY_TYPE = {
    "Order": ["O100", "O200"],
    "Item": ["I1", "I2", "I3"],
    "Package": ["P1", "P2"],
    "Delivery": ["D1", "D2"],
    "Invoice": ["V1"],
    "Payment": ["M1", "M2"],
}
objects = pd.DataFrame(
    [(oid, otype) for otype, oids in OBJECTS_BY_TYPE.items() for oid in oids],
    columns=[OID, OTYPE],
)
type_of = dict(zip(objects[OID], objects[OTYPE]))

# ---------------------------------------------------------------------------
# 2. events + source-level E2O, declared together so they cannot drift apart
#    (eid, timestamp, activity, amount, [(object id, E2O qualifier), ...])
# ---------------------------------------------------------------------------
EVENT_SPECS = [
    ("e01", "2026-04-06 08:00", "Create Order", None,
     [("O100", "created order")]),
    ("e02", "2026-04-06 08:05", "Add Item", None,
     [("I1", "added item"), ("O100", "receiving order")]),
    ("e03", "2026-04-06 08:06", "Add Item", None,
     [("I2", "added item"), ("O100", "receiving order")]),
    ("e04", "2026-04-06 08:10", "Create Order", None,
     [("O200", "created order")]),
    ("e05", "2026-04-06 08:12", "Add Item", None,
     [("I3", "added item"), ("O200", "receiving order")]),
    ("e06", "2026-04-06 08:30", "Reserve Stock", None,
     [("I1", "reserved item"), ("I3", "reserved item"),
      ("O100", "requesting order"), ("O200", "requesting order")]),
    ("e07", "2026-04-06 09:00", "Pack Package", None,
     [("P1", "packed package"), ("I1", "packed item"), ("I3", "packed item"),
      ("O100", "fulfilled order"), ("O200", "fulfilled order")]),
    # e08 -> O100 is the only E2O row not spelled out in the narrative. It applies
    # the Pack Package relation schema shown by e07 (see INFERRED_SOURCE_E2O).
    ("e08", "2026-04-06 09:05", "Pack Package", None,
     [("P2", "packed package"), ("I2", "packed item"),
      ("O100", "fulfilled order")]),
    ("e09", "2026-04-06 10:00", "Dispatch Package", None,
     [("P1", "dispatched package"), ("D1", "dispatching delivery")]),
    ("e10", "2026-04-06 10:15", "Dispatch Package", None,
     [("P2", "dispatched package"), ("D2", "dispatching delivery")]),
    ("e11", "2026-04-06 11:00", "Issue Invoice", None,
     [("V1", "issued invoice"), ("O100", "billed order"), ("O200", "billed order")]),
    ("e12", "2026-04-06 11:30", "Record Payment", 100.0,
     [("M1", "recorded payment"), ("V1", "settled invoice")]),
    ("e13", "2026-04-06 13:00", "Confirm Delivery", None,
     [("D1", "confirmed delivery")]),
    ("e14", "2026-04-07 09:00", "Confirm Delivery", None,
     [("D2", "confirmed delivery")]),
    ("e15", "2026-04-07 10:00", "Record Payment", 150.0,
     [("M2", "recorded payment"), ("V1", "settled invoice")]),
    ("e16", "2026-04-07 10:30", "Close Order", None,
     [("O200", "closed order")]),
    ("e17", "2026-04-07 10:35", "Close Order", None,
     [("O100", "closed order")]),
]
INFERRED_SOURCE_E2O = {("e08", "O100")}

# Allowed (activity, object type) -> qualifier combinations: the E2O vocabulary.
E2O_VOCABULARY = {
    ("Create Order", "Order"): "created order",
    ("Add Item", "Item"): "added item",
    ("Add Item", "Order"): "receiving order",
    ("Reserve Stock", "Item"): "reserved item",
    ("Reserve Stock", "Order"): "requesting order",
    ("Pack Package", "Package"): "packed package",
    ("Pack Package", "Item"): "packed item",
    ("Pack Package", "Order"): "fulfilled order",
    ("Dispatch Package", "Package"): "dispatched package",
    ("Dispatch Package", "Delivery"): "dispatching delivery",
    ("Issue Invoice", "Invoice"): "issued invoice",
    ("Issue Invoice", "Order"): "billed order",
    ("Record Payment", "Payment"): "recorded payment",
    ("Record Payment", "Invoice"): "settled invoice",
    ("Confirm Delivery", "Delivery"): "confirmed delivery",
    ("Close Order", "Order"): "closed order",
}

events = pd.DataFrame(
    [(eid, act, ts, amount) for eid, ts, act, amount, _ in EVENT_SPECS],
    columns=[EID, ACT, TS, "amount"],
)
events[TS] = pd.to_datetime(events[TS], utc=True)  # timezone-aware (UTC)
events["amount"] = events["amount"].astype("float64")  # NaN unless Record Payment

# E2O rows carry only the keys; activity and timestamp are merged in from
# `events`, so the repeated values are consistent by construction.
e2o_keys = pd.DataFrame(
    [(eid, oid, qual) for eid, _, _, _, rels in EVENT_SPECS for oid, qual in rels],
    columns=[EID, OID, QUAL],
)


def build_relations(keys: pd.DataFrame) -> pd.DataFrame:
    """Expand (eid, oid, qualifier) keys into a full OCEL relations table."""
    rel = keys.merge(events[[EID, ACT, TS]], on=EID, how="left", validate="many_to_one")
    rel = rel.merge(objects, on=OID, how="left", validate="many_to_one")
    return rel[RELATION_COLUMNS].sort_values([TS, EID, OID]).reset_index(drop=True)


relations = build_relations(e2o_keys)  # source-level facts only

# ---------------------------------------------------------------------------
# 3. O2O: the row reads "<ocel:oid> <qualifier> <ocel:oid_2>"
# ---------------------------------------------------------------------------
o2o = pd.DataFrame(
    [
        ("O100", "I1", "contains"),
        ("O100", "I2", "contains"),
        ("O200", "I3", "contains"),
        ("P1", "I1", "packs"),
        ("P1", "I3", "packs"),
        ("P2", "I2", "packs"),
        ("D1", "P1", "carries"),
        ("D2", "P2", "carries"),
        ("V1", "O100", "bills"),
        ("V1", "O200", "bills"),
        ("M1", "V1", "partially_settles"),
        ("M2", "V1", "completes_settlement"),
    ],
    columns=[OID, OID2, QUAL],
)
O2O_SCHEMA = {  # qualifier -> (source type, target type)
    "contains": ("Order", "Item"),
    "packs": ("Package", "Item"),
    "carries": ("Delivery", "Package"),
    "bills": ("Invoice", "Order"),
    "partially_settles": ("Payment", "Invoice"),
    "completes_settlement": ("Payment", "Invoice"),
}

# ---------------------------------------------------------------------------
# 4. Analytical propagation, kept in a separate table and a separate OCEL.
#    (activity, start type, [(O2O qualifier, direction), ...], derived qualifier)
# ---------------------------------------------------------------------------
DERIVATION_RULES = [
    ("Dispatch Package", "Package", [("packs", "fwd")], "shipped item"),
    ("Dispatch Package", "Package", [("packs", "fwd"), ("contains", "rev")], "shipped order"),
    ("Confirm Delivery", "Delivery", [("carries", "fwd")], "delivered package"),
    ("Confirm Delivery", "Delivery", [("carries", "fwd"), ("packs", "fwd")], "delivered item"),
    ("Confirm Delivery", "Delivery",
     [("carries", "fwd"), ("packs", "fwd"), ("contains", "rev")], "delivered order"),
    # Payment allocation per Order is unknown, so every billed Order is linked.
    ("Record Payment", "Invoice", [("bills", "fwd")], "paid order"),
]


def follow_o2o(oids: set, hops: list) -> set:
    """Walk a set of object ids along a path of qualified O2O hops."""
    for qualifier, direction in hops:
        edges = o2o[o2o[QUAL] == qualifier]
        src, dst = (OID, OID2) if direction == "fwd" else (OID2, OID)
        oids = set(edges.loc[edges[src].isin(oids), dst])
    return oids


def derive_e2o_keys(source_relations: pd.DataFrame) -> pd.DataFrame:
    """Derive extra E2O keys from source E2O + O2O; qualifiers are prefixed."""
    rows = []
    for activity, start_type, hops, qualifier in DERIVATION_RULES:
        seeds = source_relations[
            (source_relations[ACT] == activity) & (source_relations[OTYPE] == start_type)
        ]
        for eid, group in seeds.groupby(EID):
            for oid in sorted(follow_o2o(set(group[OID]), hops)):
                rows.append((eid, oid, DERIVED_PREFIX + qualifier))
    return pd.DataFrame(rows, columns=[EID, OID, QUAL])


derived_relations = build_relations(derive_e2o_keys(relations))
relations_propagated = (
    pd.concat([relations, derived_relations], ignore_index=True)
    .sort_values([TS, EID, OID])
    .reset_index(drop=True)
)

# ---------------------------------------------------------------------------
# 5. Validation
# ---------------------------------------------------------------------------
def validate_tables(events, objects, relations, o2o, allow_derived=False):
    """Raise AssertionError on any structural or semantic inconsistency."""
    for name, frame, cols in [
        ("events", events, [EID, ACT, TS]),
        ("objects", objects, [OID, OTYPE]),
        ("relations", relations, RELATION_COLUMNS),
        ("o2o", o2o, [OID, OID2, QUAL]),
    ]:
        missing = set(cols) - set(frame.columns)
        assert not missing, f"{name}: missing columns {missing}"
        assert not frame[cols].isna().any().any(), f"{name}: null in mandatory column"

    # Identifier uniqueness
    assert events[EID].is_unique, "duplicate event ids"
    assert objects[OID].is_unique, "duplicate object ids"

    # Timezone-aware timestamps in both tables
    for name, frame in [("events", events), ("relations", relations)]:
        assert isinstance(frame[TS].dtype, pd.DatetimeTZDtype), f"{name}: naive timestamps"

    # Referential integrity
    known_eids, known_oids = set(events[EID]), set(objects[OID])
    assert set(relations[EID]) <= known_eids, "orphan event id in relations"
    assert set(relations[OID]) <= known_oids, "orphan object id in relations"
    assert set(o2o[OID]) | set(o2o[OID2]) <= known_oids, "orphan object id in o2o"
    assert known_eids <= set(relations[EID]), "event without any related object"
    assert known_oids <= set(relations[OID]), "object without any related event"

    # Repeated activity / timestamp / type must equal the master tables
    check = relations.merge(events[[EID, ACT, TS]], on=EID, suffixes=("", "_ev"))
    assert (check[ACT] == check[ACT + "_ev"]).all(), "activity mismatch events/relations"
    assert (check[TS] == check[TS + "_ev"]).all(), "timestamp mismatch events/relations"
    assert (relations[OTYPE] == relations[OID].map(type_of)).all(), "type mismatch in relations"

    # Duplicates: full rows, and (event, object) pairs with two qualifiers
    assert not relations.duplicated().any(), "duplicate relation rows"
    assert not relations.duplicated([EID, OID]).any(), "event-object pair related twice"
    assert not o2o.duplicated().any(), "duplicate o2o rows"
    assert not o2o.duplicated([OID, OID2]).any(), "object pair related twice in o2o"
    assert (o2o[OID] != o2o[OID2]).all(), "self-referencing o2o row"

    # Qualifier vocabularies and O2O direction conventions
    is_derived = relations[QUAL].str.startswith(DERIVED_PREFIX)
    assert allow_derived or not is_derived.any(), "derived relation in the source table"
    source_rows = relations[~is_derived]
    expected = [E2O_VOCABULARY.get(key) for key in zip(source_rows[ACT], source_rows[OTYPE])]
    assert (source_rows[QUAL] == expected).all(), "E2O qualifier outside the vocabulary"
    for qualifier, (src_type, dst_type) in O2O_SCHEMA.items():
        rows = o2o[o2o[QUAL] == qualifier]
        assert not rows.empty, f"no o2o rows for {qualifier}"
        assert (rows[OID].map(type_of) == src_type).all(), f"{qualifier}: wrong source type"
        assert (rows[OID2].map(type_of) == dst_type).all(), f"{qualifier}: wrong target type"
    assert set(o2o[QUAL]) <= set(O2O_SCHEMA), "unknown o2o qualifier"

    # Business facts from the narrative
    assert len(events) == 17 and len(objects) == 12, "unexpected table size"
    paid = events["amount"].notna()
    assert (events.loc[paid, ACT] == "Record Payment").all(), "amount on a non-payment event"
    assert events.loc[events[ACT] == "Record Payment", "amount"].notna().all(), "payment without amount"
    assert events["amount"].sum() == 250.0, "payment amounts do not add up to 250"


validate_tables(events, objects, relations, o2o)
validate_tables(events, objects, relations_propagated, o2o, allow_derived=True)
assert set(INFERRED_SOURCE_E2O) <= set(zip(relations[EID], relations[OID]))
print("Validation passed:", len(events), "events,", len(objects), "objects,",
      len(relations), "source E2O rows,", len(derived_relations), "derived E2O rows,",
      len(o2o), "O2O rows")

# ---------------------------------------------------------------------------
# 6. OCEL construction (the only version-sensitive lines)
# ---------------------------------------------------------------------------
def build_ocel(events, objects, relations, o2o):
    """Single place to adapt if the installed PM4Py constructor differs."""
    return OCEL(events=events, objects=objects, relations=relations, o2o=o2o)


ocel = build_ocel(events, objects, relations, o2o)  # source facts only
ocel_propagated = build_ocel(events, objects, relations_propagated, o2o)  # analytical view

print(ocel)
print("\nActivity frequencies:")
print(events[ACT].value_counts().to_string())
print("\nObject-type frequencies:")
print(objects[OTYPE].value_counts().to_string())
print("\nObject types:", pm4py.ocel_get_object_types(ocel))
print("\nActivities per object type:")
for object_type, activities in pm4py.ocel_object_type_activities(ocel).items():
    print(f"  {object_type}: {sorted(activities)}")

# ---------------------------------------------------------------------------
# 7. Flattened views (one case notion at a time)
# ---------------------------------------------------------------------------
def flattened_views(ocel_obj, object_types):
    """Flatten per object type; return (logs, DFGs, log skeletons) keyed by type."""
    logs, dfgs, skeletons = {}, {}, {}
    for object_type in object_types:
        log = pm4py.ocel_flattening(ocel_obj, object_type)
        dfg, start_activities, end_activities = pm4py.discover_dfg(log)
        logs[object_type] = log
        dfgs[object_type] = {"dfg": dfg, "start": start_activities, "end": end_activities}
        skeletons[object_type] = pm4py.discover_log_skeleton(log, noise_threshold=0.0)
    return logs, dfgs, skeletons


FLATTENING_TYPES = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
flat_logs, flat_dfgs, flat_skeletons = flattened_views(ocel, FLATTENING_TYPES)
prop_logs, prop_dfgs, prop_skeletons = flattened_views(ocel_propagated, ["Order", "Item", "Package"])

for label, logs, dfgs in [("source", flat_logs, flat_dfgs), ("propagated", prop_logs, prop_dfgs)]:
    for object_type, log in logs.items():
        print(f"\n[{label}] flattened on {object_type}: {len(log)} rows, "
              f"{log['case:concept:name'].nunique()} cases")
        for case_id, trace in log.groupby("case:concept:name", sort=True):
            print(f"  {case_id}: {' > '.join(trace['concept:name'])}")
        print("  DFG:", dict(sorted(dfgs[object_type]["dfg"].items())))

# ---------------------------------------------------------------------------
# 8. Object-centric discovery on the source-level OCEL
# ---------------------------------------------------------------------------
oc_models = {
    "ocdfg": pm4py.discover_ocdfg(ocel),
    "otg": pm4py.discover_otg(ocel),
    "etot": pm4py.discover_etot(ocel),
    "ocpn": pm4py.discover_oc_petri_net(ocel),
    "interactions": pm4py.ocel_objects_interactions_summary(ocel),
}
oc_models_propagated = {"ocdfg": pm4py.discover_ocdfg(ocel_propagated)}

print("\nOC-DFG edges per object type (number of event couples):")
for object_type, edges in oc_models["ocdfg"]["edges"]["event_couples"].items():
    print(f"  {object_type}: { {edge: len(couples) for edge, couples in edges.items()} }")
print("\nOTG:", oc_models["otg"])
print("\nET-OT:", oc_models["etot"])
print("\nOC Petri net object types:", sorted(oc_models["ocpn"]["petri_nets"]))
print("\nObject interactions summary:")
print(oc_models["interactions"].to_string(index=False))

# Why propagated relations must never feed aggregations: each payment is copied
# to both Orders, so the Order-flattened total is 500 instead of the real 250.
print("\nPayment amount, events table:", events["amount"].sum(),
      "| propagated Order flattening:", prop_logs["Order"]["amount"].sum())
```

## 3. Data-model audit

**Objects**

| Type | Objects | Count |
|---|---|---|
| Order | O100, O200 | 2 |
| Item | I1, I2, I3 | 3 |
| Package | P1, P2 | 2 |
| Delivery | D1, D2 | 2 |
| Invoice | V1 | 1 |
| Payment | M1, M2 | 2 |

**O2O relations (12 rows)**

| Qualifier | Direction | Rows | Cardinality in this data |
|---|---|---|---|
| `contains` | Order → Item | O100→I1, O100→I2, O200→I3 | 1:N; every Item has exactly one Order |
| `packs` | Package → Item | P1→I1, P1→I3, P2→I2 | 1:N; every Item has exactly one Package |
| `carries` | Delivery → Package | D1→P1, D2→P2 | 1:1 |
| `bills` | Invoice → Order | V1→O100, V1→O200 | 1:N; one Invoice, two Orders |
| `partially_settles` | Payment → Invoice | M1→V1 | N:1 together with the next row |
| `completes_settlement` | Payment → Invoice | M2→V1 | exactly one completing payment |

Order–Package is not stored. It is many-to-many when derived through `contains` and `packs`: O100 ↔ {P1, P2} and P1 ↔ {O100, O200}.

**Activities and source-level E2O (35 rows)**

| Activity | Events | Object types touched | Objects per event |
|---|---|---|---|
| Create Order | e01, e04 | Order | 1 Order |
| Add Item | e02, e03, e05 | Item, Order | 1 Item + 1 Order |
| Reserve Stock | e06 | Item, Order | 2 Items + 2 Orders |
| Pack Package | e07, e08 | Package, Item, Order | e07: P1 + I1, I3 + O100, O200; e08: P2 + I2 + O100 |
| Dispatch Package | e09, e10 | Package, Delivery | 1 Package + 1 Delivery |
| Issue Invoice | e11 | Invoice, Order | V1 + O100, O200 |
| Record Payment | e12, e15 | Payment, Invoice | 1 Payment + V1 |
| Confirm Delivery | e13, e14 | Delivery | 1 Delivery |
| Close Order | e16, e17 | Order | 1 Order |

The propagated layer adds 18 `derived:` rows: Items and Orders on e09, e10, e13, and e14; Packages on e13 and e14; both Orders on e12 and e15.

**Consequential events**

- **e06 Reserve Stock** has four objects of two types. It is the first event shared by O100 and O200, so it is copied into both Order traces and both Item traces (convergence).
- **e07 Pack Package** is where P1 merges items of two Orders. It is the largest relation set, with five objects, and it is the reason Order and Package are many-to-many.
- **e08 Pack Package** carries the one inferred row. Without it O100 would show only one packing event although it has two packages.
- **e11 Issue Invoice** is one event for two Orders (convergence under Order flattening).
- **e12 and e15 Record Payment** are two events of the same activity attached to one Invoice through two different Payments (divergence under Invoice flattening).
- **e09/e10 and e13/e14** are harmless at source level. Once propagated, O100 receives two Dispatch and two Confirm events from independent deliveries, which is divergence introduced by the analyst.

## 4. Expected flattened behavior

Flattening on type T produces one case per T object and copies every event related to k objects of T into k cases.

**Order** (2 cases, 14 rows from 11 distinct events)

- Trace shape:
  - O100: Create Order > Add Item > Add Item > Reserve Stock > Pack Package > Pack Package > Issue Invoice > Close Order
  - O200: Create Order > Add Item > Reserve Stock > Pack Package > Issue Invoice > Close Order
- Copied shared events: e06, e07, and e11 appear in both cases.
- Omitted: Dispatch Package, Confirm Delivery, and Record Payment, because they have no direct Order relation.
- DFG edges (count): Create Order→Add Item (2), Add Item→Add Item (1), Add Item→Reserve Stock (2), Reserve Stock→Pack Package (2), Pack Package→Pack Package (1), Pack Package→Issue Invoice (2), Issue Invoice→Close Order (2). Start is Create Order and end is Close Order.
- Misleading readings:
  - Reserve Stock and Issue Invoice each look like two occurrences, but each is one event.
  - The self-loops on Add Item and Pack Package are item and package multiplicity, not rework.
  - Issue Invoice→Close Order suggests about 23.5 hours of idle waiting, during which deliveries were confirmed and payments recorded.
  - The log skeleton reports Add Item and Pack Package as equivalent. That is a coincidence of one item per packing event per order.
- Propagated variant (`prop_logs["Order"]`): 24 rows covering all 17 events. O100 becomes … Pack Package > Pack Package > Dispatch Package > Dispatch Package > Issue Invoice > Record Payment > Confirm Delivery > Confirm Delivery > Record Payment > Close Order. This adds Record Payment→Confirm Delivery and Confirm Delivery→Record Payment edges, which are interleavings of independent logistics and finance objects. It also makes each Order appear to have paid 250, for a flattened total of 500.

**Package** (2 cases, 4 rows)

- Trace shape: P1 and P2 are both Pack Package > Dispatch Package.
- Copied shared events: none, because every event has exactly one Package.
- Omitted: Confirm Delivery (related to the Delivery only), reservation, and all order and billing context.
- DFG: Pack Package→Dispatch Package (2).
- Misleading readings: P1 and P2 look identical, although P1 is the cross-order consolidation and P2 is not. The lifecycle seems to end at dispatch, as if packages were never delivered. The propagated variant adds Dispatch Package→Confirm Delivery (2).

**Delivery** (2 cases, 4 rows)

- Trace shape: D1 and D2 are both Dispatch Package > Confirm Delivery.
- Copied shared events: none.
- Omitted: everything before dispatch and every link to Orders.
- DFG: Dispatch Package→Confirm Delivery (2).
- Misleading readings: the view shows 3 h for D1 against 22 h 45 min for D2, but not that D1 serves both Orders while D2 affects only O100. The first activity is named after the Package, so the trace start is really "delivery created".

**Invoice** (1 case, 3 rows)

- Trace shape: V1 is Issue Invoice > Record Payment > Record Payment.
- Copied shared events: none, since there is one Invoice.
- Omitted: the two billed Orders, logistics, and order closing.
- DFG: Issue Invoice→Record Payment (1), Record Payment→Record Payment (1). Start is Issue Invoice and end is Record Payment.
- Misleading readings: the self-loop looks like a repeated or corrected payment, but it is two distinct Payment objects (divergence). With a single case, the skeleton constraint "Record Payment occurs exactly twice" is an anecdote, not a rule. The activity label cannot distinguish the partial payment from the completing one; only the O2O qualifier and `amount` can.

**Why Payment flattening is particularly weak.** M1 and M2 each yield a one-event trace (Record Payment). The DFG has no edges, start equals end, there is no duration, and the log skeleton holds only "Record Payment exactly once". The interesting facts lie between objects: M1 precedes M2, both hit V1, and 100 + 150 completes settlement. Flattening on Payment cuts exactly those links. Lengthening the traces by propagating Issue Invoice to the Payments would copy e11 into both cases and still say nothing about allocation.

## 5. Expected object-centric structures

**OC-DFG.** One event node per activity, with typed edges per object type and no duplication of shared events.

- Edges by type (event couples):
  - Order: Create Order→Add Item (2), Add Item→Add Item (1), Add Item→Reserve Stock (2), Reserve Stock→Pack Package (1), Pack Package→Pack Package (1), Pack Package→Issue Invoice (2), Issue Invoice→Close Order (2).
  - Item: Add Item→Reserve Stock (2), Reserve Stock→Pack Package (1), Add Item→Pack Package (1, for I2, which was never reserved).
  - Package: Pack Package→Dispatch Package (2).
  - Delivery: Dispatch Package→Confirm Delivery (2).
  - Invoice: Issue Invoice→Record Payment (1), Record Payment→Record Payment (1).
  - Payment: no edges; Record Payment is both its start and end activity.
- Reserve Stock→Pack Package is 1 event couple (e06→e07) here, against 2 in the flattened Order DFG. That difference is the convergence that flattening hides. With the `total_objects` metric the edge shows 2.
- The activities where colours meet are the synchronisation points: Pack Package (Order, Item, Package), Dispatch Package (Package, Delivery), Issue Invoice (Order, Invoice), Record Payment (Invoice, Payment).
- O100 and O200 do not reach dispatch, confirmation, or payment in the Order colour. The path continues through P1 and P2, then D1 and D2, and through V1, then M1 and M2. `oc_models_propagated["ocdfg"]` draws those Order edges at the cost of the interleavings described in section 4.

**OTG.** In the tested version the OTG is computed from object graphs derived from E2O co-occurrence and lifecycle order. The O2O table is not used, so qualifiers such as `contains` do not appear in it.

- Interaction edges: Item–Order (5 object pairs, including the cross pairs I1–O200 and I3–O100 created by e06 and e07), Item–Package (3), Order–Package (3: O100–P1, O200–P1, O100–P2), Package–Delivery (2), Order–Invoice (2), Invoice–Payment (2: V1–M1, V1–M2), Order–Order (1: O100–O200), Item–Item (1: I1–I3).
- Descendant edges give the type-level flow: Order→Item, Order→Package, Order→Invoice, Item→Package, Package→Delivery, Invoice→Payment.
- Inheritance edges mark hand-overs where one object's last event is another's first: Item→Package (3), Package→Delivery (2), and Invoice→Payment (1, V1→M2 only).
- There are no Order–Delivery, Order–Payment, Item–Delivery, or Payment–Payment edges. M1 and M2 are related only through V1.

**ET–OT.** A bipartite graph with 9 activities, 6 object types, and 16 edges whose weights are E2O row counts.

- Weights: Create Order–Order 2; Add Item–Item 3 and –Order 3; Reserve Stock–Item 2 and –Order 2; Pack Package–Package 2, –Item 3, and –Order 3; Dispatch Package–Package 2 and –Delivery 2; Issue Invoice–Invoice 1 and –Order 2; Record Payment–Payment 2 and –Invoice 2; Confirm Delivery–Delivery 2; Close Order–Order 2. The sum is 35.
- Order is the hub, with 6 activities. Payment is a leaf, with 1. Pack Package is the only three-type activity.
- A weight above the event count (Issue Invoice–Order is 2 for 1 event; Pack Package–Item is 3 for 2 events) signals multi-object events of that type.

**Object-centric Petri net.** One net per object type, discovered from that type's flattened log and merged on shared activity transitions.

- Variable arcs are expected for Order at Reserve Stock, Pack Package, and Issue Invoice, and for Item at Reserve Stock and Pack Package. Those are the places where one event consumes several objects of a type (O100 and O200 together; I1 and I3 into P1). All Package, Delivery, Invoice, and Payment arcs are single-object.
- The Invoice net is Issue Invoice followed by a Record Payment loop for V1. The Payment net is source → Record Payment → sink, for M1 and M2. The Order net allows repeated Add Item and Pack Package.
- This model does not have one uniquely determined interpretation. Its shape depends on the per-type miner and its settings, silent transitions are discovery artefacts, and variable arcs state only that cardinality varies. The net does not say that P1 must combine exactly O100 and O200, that M1 must precede M2, or that 250 must be reached before Close Order. Different E2O policies (section 6) yield different, equally valid nets for the same story.

**Object-interactions summary.** One row per ordered pair of objects co-occurring in an event: 58 rows, i.e. 29 unordered pairs.

- Contributions: e07 gives 20, e06 gives 12, e08 and e11 give 6 each, and every two-object event gives 2. Single-object events (Create Order, Confirm Delivery, Close Order) give none.
- O100 and O200 interact three times: at e06, e07, and e11.
- P1 interacts with I1, I3, O100, O200 (e07) and D1 (e09). P2 never touches O200.
- V1 interacts with O100 and O200 (e11), M1 (e12), and M2 (e15).
- M1 and M2 never interact with each other or with any Order, and no Delivery interacts with an Order or Item. Those absences are the direct-relation policy made visible.

## 6. Modeling alternatives

The business story, `events`, `objects`, and `o2o` stay fixed in every alternative. Only E2O changes.

1. **Source-minimal (primary objects only).** Each event relates only to what it acts on: Reserve Stock to Items, Pack Package to Package and Items, Issue Invoice to V1, Record Payment to the Payment. Order context comes from O2O alone. This removes all Order-level convergence and gives the smallest tables. Order traces shrink to Create Order > Add Item > Close Order, the Order colour nearly vanishes from the OC-DFG and Petri net, and Order–Order and Order–Invoice interactions disappear from the OTG and the interactions summary.

2. **Narrative-direct (the chosen `ocel`).** Relations are those the text states, plus one flagged schema inference. Shared upstream events show convergence at Reserve Stock, Pack Package, and Issue Invoice. Downstream logistics and payments remain in their own object lifecycles.

3. **Full operational involvement.** Every downstream event also relates directly, unprefixed, to the affected Orders and Items. Order and Item flattenings become end to end. The OC-DFG gains Order edges through Dispatch Package, Confirm Delivery, and Record Payment, more arcs become variable, and the OTG gains Order–Delivery, Order–Payment, and Item–Delivery edges. The interactions summary grows from 58 to 158 rows; e09 alone goes from 2 to 30 ordered pairs. Assumptions become indistinguishable from observations.

4. **O2O-propagated analytical relations (`ocel_propagated`).** The discovery results match alternative 3, but provenance stays in the `derived:` prefix and in the rule list. Rules can be changed and rerun, for example dropping `paid order` or propagating only to Items.

5. **Item-granular logistics.** Dispatch and Confirm are propagated to Items but not to Orders. Each Item has one Package and one Delivery, so Item traces become a clean Add Item > (Reserve Stock) > Pack Package > Dispatch Package > Confirm Delivery with no convergence. Order-level questions are answered by joining through `contains`.

6. **Allocation-aware finance.** A Payment relates to an Order only when the source records an allocation. Here the result equals the chosen model. With allocation data, Order traces would gain Record Payment without the double counting of alternative 3.

## 7. Failure modes

1. **Relation inflation.** Attaching every reachable object to every event multiplies E2O rows and interaction pairs. Shared activities then dominate every flattened DFG, and their frequencies stop meaning "number of events".
2. **Missing direct E2O links.** Dropping Orders from Reserve Stock, Pack Package, or Issue Invoice, or dropping `e08 → O100`, makes Order lifecycles jump from Add Item to Close Order and hides the cross-order coupling.
3. **Treating O2O propagation as observation.** Unprefixed derived rows lead to statements like "O200 was paid at 11:30", which no source system recorded.
4. **Duplicate shared events after flattening.** e06, e07, and e11 are counted twice in the Order log. Any sum, count, or duration computed there is overstated, e.g. payment totals of 500 in the propagated view.
5. **Ambiguous payment allocation.** M1 (100) and M2 (150) settle V1 jointly. Nothing says how much belongs to O100 or O200, so any Order-level payment metric is an assumption.
6. **Overly short Payment traces.** Single-event cases give an empty DFG and no performance information. Reading that as "payment handling is trivial" is a case-notion artefact.
7. **Constructor/API version mismatch.** A missing `o2o` keyword, different default column names, missing `discover_otg` / `discover_etot`, or dict versus object return types can break the run. Fix it in `build_ocel` or the affected call, never by reshaping the data.
8. **False total order for same-time events.** There are no timestamp ties here. If e09 and e11 shared a timestamp, stable sorting by table order or event id would invent a directly-follows edge. Such events should be treated as concurrent or given an explicit, documented tie-breaker.
9. **Activity/timestamp drift.** If `relations` is typed by hand, its repeated activity and timestamp columns can diverge from `events`. PM4Py then mixes both sources silently. Here they are merged from `events` and re-validated.
10. **Inconsistent object-type spelling or qualifiers.** `order` versus `Order`, or two qualifiers for the same role, split one type into two and break type-level discovery. The vocabulary check prevents this.
11. **Wrong O2O direction.** Storing `I1 contains O100` or mixing directions makes propagation rules walk the wrong way and silently produce empty or wrong derived relations. The O2O type-pair check prevents this.
12. **Convergence or divergence read as control flow.** Self-loops such as Record Payment→Record Payment on V1, or Pack Package→Pack Package on O100, are multiplicity of related objects, not rework.
13. **Over-generalising from one instance.** V1 is the only Invoice, so "always two payments" or "invoice always bills two orders" are properties of this sample.

## 8. Final semantic checks

A reviewer can verify these directly in the printed tables.

1. `events` has 17 rows with unique ids `e01`–`e17`, 9 activities with frequencies Add Item 3, Reserve Stock 1, Issue Invoice 1, and all others 2, and UTC-aware timestamps from 2026-04-06 08:00 to 2026-04-07 10:35.
2. `objects` has 12 rows: 2 Orders, 3 Items, 2 Packages, 2 Deliveries, 1 Invoice, and 2 Payments. There is no "amount" object.
3. `amount` is non-null only for e12 (100) and e15 (150), and sums to 250.
4. `relations` has 35 rows, no `derived:` qualifier, every event appears at least once, and every activity and timestamp equals the corresponding `events` row.
5. e06 relates to exactly I1, I3, O100, and O200. I2 is never related to Reserve Stock.
6. e07 relates to P1, I1, I3, O100, and O200. e08 relates to P2, I2, and O100. O200 never co-occurs with P2 or I2.
7. e09 relates to P1 and D1, and e10 to P2 and D2. e13 relates only to D1, and e14 only to D2.
8. e11 relates to V1, O100, and O200. e12 relates to M1 and V1, and e15 to M2 and V1. No Payment row touches an Order in `relations`.
9. `o2o` has 12 rows with the stated directions: 3 `contains`, 3 `packs`, 2 `carries`, 2 `bills`, 1 `partially_settles` (M1→V1), and 1 `completes_settlement` (M2→V1). Every Item has exactly one Order and one Package.
10. Close Order (e16 for O200, e17 for O100) is later than Issue Invoice, both Confirm Delivery events, and both payments. O200 closes before O100.
11. `derived_relations` has 18 rows, all prefixed `derived:`, all on Dispatch Package, Confirm Delivery, or Record Payment, and each is reproducible from one source E2O row plus an O2O path.
12. Flattened row counts match the relation counts per type: Order 14, Item 8, Package 4, Delivery 4, Invoice 3, Payment 2, which sum to 35.
