```
def _as_list(x):
    if x is None: return []
    if isinstance(x, (list,tuple,set,frozenset)): return list(x)
    return [x]

def merge_verified_pair(oc, duplicate_eid, canonical_eid, rule, authoritative_source_for=None):
    oc=copy.deepcopy(oc)
    ev=oc.events
    can_idx=ev.index[ev[EVENT_ID]==canonical_eid]
    dup_idx=ev.index[ev[EVENT_ID]==duplicate_eid]
    if len(can_idx)!=1 or len(dup_idx)!=1: return oc
    can=ev.loc[can_idx[0]]; dup=ev.loc[dup_idx[0]]
    union_objects=sorted(set(_as_list(can[OBJECTS])) | set(_as_list(dup[OBJECTS])))
    provenance=sorted(set(_as_list(can.get('provenance_source_events', []))) | set(_as_list(dup.get('provenance_source_events', []))) | {duplicate_eid, canonical_eid})
    source_keys=sorted(set(_as_list(can.get('merged_source_event_keys', []))) | {can['source_event_key'], dup['source_event_key']})
    payload_hashes=sorted(set(_as_list(can.get('merged_payload_hashes', []))) | {can['payload_hash'], dup['payload_hash']})
    sources=sorted(set(_as_list(can.get('merged_sources', []))) | {can['source'], dup['source']})
    conflicts={}
    for col in ev.columns:
       if col in {EVENT_ID,TIMESTAMP,ACTIVITY,OBJECTS,'source','source_event_key','payload_hash','ingested_at','provenance_source_events','merged_source_event_keys','merged_payload_hashes','merged_sources','merge_rule','original_timestamp','original_activity'}:
          continue
       cv,dv=can.get(col), dup.get(col)
       if pd.notna(dv) and (pd.isna(cv) or cv != dv):
           conflicts[col]={'canonical':cv, 'duplicate_source':dup['source'], 'duplicate_value':dv}
           # attribute authority optional
           if authoritative_source_for and dup['source'] in authoritative_source_for.get(col, []):
               ev.loc[can_idx[0], col] = dv
    ev.loc[can_idx[0], OBJECTS] = [union_objects]
    ev.loc[can_idx[0], 'provenance_source_events'] = [provenance]
    ev.loc[can_idx[0], 'merged_source_event_keys'] = [source_keys]
    ev.loc[can_idx[0], 'merged_payload_hashes'] = [payload_hashes]
    ev.loc[can_idx[0], 'merged_sources'] = [sources]
    ev.loc[can_idx[0], 'merge_rule'] = rule
    ev.loc[can_idx[0], 'attribute_conflicts'] = [conflicts]
    oc.events = ev.drop(index=dup_idx[0]).reset_index(drop=True)
    return oc
```

## 1. Duplicate-handling decision tree

Use candidate groups, not global deduplication. A candidate group may be formed by equal timestamp + activity, equal business key, shared object set, payload similarity, or external reconciliation evidence. The tree below is intentionally conservative: when semantic identity is uncertain, preserve both observations and record the ambiguity.

1. **Exact technical duplicate?**  
   Criteria: same source, same `source_event_key`, same `payload_hash`, or repeated technical emission of the same event record.  
   **Decision:** drop the redundant technical record, but retain its identifiers in provenance.  
   Rationale: no business information is lost.

2. **Same physical/business event observed by multiple systems?**  
   Criteria: reconciliation report, shared business key, matching objects, matching time, and explanatory payload difference. Examples: e03/e04, e11/e16.  
   **Decision:** merge attributes and relations into one canonical event, preserving source-level attributes, original event keys, payload hashes, and source systems.  
   If evidence is weak, quarantine instead of merging.

3. **Summary event derived from a detailed event?**  
   Criteria: one event is generated from another system’s message, often at a different abstraction level. Examples: e06/e07, e13/e15, e14/e15.  
   Conservative decision: retain both with refined labels or qualifiers and record `derived_from` provenance.  
   Aggressive decision, only with strong evidence: merge into one business transition, but keep the summary attributes as namespaced provenance.  
   Do not silently drop the summary, because it may represent authoritative ERP/billing state.

4. **Harmonization collision between semantically distinct source activities?**  
   Criteria: different original activities were mapped to the same canonical label. Example: e08 “released from warehouse” and e09 “accepted by carrier” both became `Dispatch Package`.  
   **Decision:** retain both with refined labels or qualifiers. Do not merge solely because timestamp, activity, and objects match.  
   If original activity cannot be recovered, quarantine for review.

5. **Concurrent same-label events involving different discriminating objects?**  
   Criteria: same activity and timestamp, but different lifecycle objects, such as different items or payments. Examples: e03/e05, e13/e14.  
   **Decision:** retain both unchanged, or retain both with refined qualifiers such as item or payment identifiers.  
   Do not merge. Shared higher-level objects such as order or invoice are not sufficient duplication evidence.

6. **Unresolved candidate?**  
   Criteria: same label/time/object overlap but no authoritative evidence.  
   **Decision:** quarantine for review or retain both with a `duplicate_candidate` flag. Never drop.

## 3. Timestamp-tie ordering rules

The pipeline must preserve `original_timestamp`. Any adjusted timestamp is a deterministic sorting artifact, not evidence of physical time.

Ordering priority:

1. **Domain constraints** — semantic.  
   Examples: pick before pack for the same item/package; authorize before capture for the same payment; carrier acceptance before handover when stated by domain facts.

2. **Within-source sequence** — semantic if the source sequence is known to reflect business order; otherwise a strong deterministic cue.  
   Examples: PSP sequence e12  e13  e14; carrier sequence e09  e10; ERP sequence e11  e15.

3. **Lifecycle constraints on shared objects** — semantic.  
   Examples: Item must be picked before Package is packed; Package must be released before Delivery is confirmed; Invoice issuance normally precedes payment capture.

4. **Source-specific semantics** — semantic.  
   Examples: e08 means warehouse release; e09 means carrier acceptance. If custody-transfer rules require release before acceptance, order e08 before e09. If not proven, treat them as tied and use deterministic fallback.

5. **Ingestion time** — deterministic only.  
   `ingested_at` may be delayed, batched, or out of order. It may be used only as a low-priority tie-breaker after semantic and source-sequence rules, and never as the primary business order.

6. **Stable fallback order** — deterministic only.  
   Use canonical eid, source event key, or a maintained semantic order index. The purpose is reproducibility, not truth.

Adding microseconds before deciding the semantic order is dangerous because downstream process mining tools often treat timestamps as factual. Synthetic subsecond offsets can convert an admitted tie into an apparently observed causal order, creating false performance measurements, false rework, and false causality.

Intended or admissible orders:

- **10:00 group e03–e07**  
  After merging e03/e04, intended conservative order:  
  `e03`  `e05`  `e06`  `e07`.  
  `e03` and `e05` are semantically concurrent picks; `e05` before `e03` is also admissible. `e06` should follow picks because it packs I1 and I2. `e07` follows `e06` if treated as derived ERP summary.

- **10:15 group e08–e10**  
  Intended order: `e08`  `e09`  `e10`.  
  If warehouse release before carrier acceptance is not accepted as a domain constraint, then `e08` and `e09` may be tied, with deterministic fallback placing `e08` first. `e10` must follow `e09`.

- **12:00 group after duplicate decisions**  
  With e11/e16 merged into canonical `e11`, intended order:  
  `e11`  `e12`  `e13`  `e14`  `e15`.  
  `e12` must precede `e13` for M1. `e13` before `e14` is supported by PSP `source_seq`, but if source sequence is considered technical rather than business, swapping them is admissible. `e15` follows captures because it is a later ERP summary.

A deterministic total order produced by these rules is an analysis convention. It does not prove the true physical order.

- abstraction-level differences between WMS, ERP, carrier, and PSP are flattened;
- loops may disappear, but only by deleting evidence rather than explaining it.

A critical safeguard: `have_common_object=True` is not sufficient to protect e13 and e14. They share O1 and V1, so a naive common-object rule may consider them duplicates. However, they represent different Payment objects, M1 and M2. The payment object is the discriminating lifecycle object. Therefore, payment capture events should only be merged if the relevant Payment object matches, or if an explicit payment identifier proves identity. The same logic protects e03/e05 through Item objects.

## 6. PM4Py-oriented Python implementation

```python
import copy
import warnings
import pandas as pd
import pm4py

# Assumption:
# ocel_raw is a PM4Py OCEL object.
# ocel_raw.events is a DataFrame containing at least:
# eid, timestamp, activity, source, source_event_key,
# source_seq, ingested_at, payload_hash, related_objects.

EVENT_ID = "eid"
TIMESTAMP = "timestamp"
ACTIVITY = "activity"
OBJECTS = "related_objects"


def _as_list(value):
    """Return a scalar/list/set as a plain list, treating NaN as empty."""
    if value is None:
        return []
    try:
        if pd.isna(value):
            return []
    except (TypeError, ValueError):
        pass
    if isinstance(value, (list, tuple, set, frozenset)):
        return list(value)
    return [value]


def deepcopy_ocel(ocel):
    """Never modify ocel_raw in place."""
    return copy.deepcopy(ocel)


def ensure_original_columns(ocel):
    """Preserve raw identifiers, timestamps, activities, and sources."""
    ocel = deepcopy_ocel(ocel)
    ev = ocel.events

    required = [EVENT_ID, TIMESTAMP, ACTIVITY, "source", "source_event_key"]
    missing = [c for c in required if c not in ev.columns]
    if missing:
        raise KeyError(f"Missing required event columns: {missing}")

    if "original_timestamp" not in ev.columns:
        ev["original_timestamp"] = ev[TIMESTAMP]
    if "original_activity" not in ev.columns:
        ev["original_activity"] = ev[ACTIVITY]
    if "provenance_source_events" not in ev.columns:
        ev["provenance_source_events"] = ev[EVENT_ID].map(lambda x: [x])
    if "merge_rule" not in ev.columns:
        ev["merge_rule"] = "raw"

    ocel.events = ev
    return ocel


def candidate_precheck(ocel):
    """
    Inspect candidate duplicate groups before applying any deduplication.
    This avoids applying duplicate functions blindly to the whole OCEL.
    """
    ev = ocel.events
    rows = []

    grouped = ev.groupby([TIMESTAMP, ACTIVITY], dropna=False)

    for (ts, act), df in grouped:
        if len(df) < 2:
            continue

        eids = df[EVENT_ID].tolist()
        objects_by_eid = {
            row[EVENT_ID]: frozenset(_as_list(row[OBJECTS]))
            for _, row in df.iterrows()
        }
        payload_by_eid = {
            row[EVENT_ID]: row.get("payload_hash")
            for _, row in df.iterrows()
        }

        for i in range(len(eids)):
            for j in range(i + 1, len(eids)):
                left = eids[i]
                right = eids[j]
                left_objects = objects_by_eid[left]
                right_objects = objects_by_eid[right]
                common = left_objects.intersection(right_objects)

                rows.append(
                    {
                        "left": left,
                        "right": right,
                        "timestamp": ts,
                        "activity": act,
                        "same_payload_hash": (
                            payload_by_eid[left] is not None
                            and payload_by_eid[left] == payload_by_eid[right]
                        ),
                        "have_common_object": bool(common),
                        "common_objects": sorted(common),
                        "left_only_objects": sorted(left_objects - right_objects),
                        "right_only_objects": sorted(right_objects - left_objects),
                    }
                )

    return pd.DataFrame(rows)


def object_id_set(ocel):
    """Find the object identifier column in the OCEL objects table."""
    obj = ocel.objects
    for candidate in ["object_id", "ocel:id", "ocel:object_id", "oid", "id"]:
        if candidate in obj.columns:
            return set(obj[candidate])
    # Fallback: use index if object id is the index.
    return set(obj.index)


def validate_referential_integrity(ocel, scenario_name):
    """Check that all event-object references point to existing objects."""
    valid_objects = object_id_set(ocel)
    bad = []

    for _, row in ocel.events.iterrows():
        related = set(_as_list(row.get(OBJECTS, [])))
        missing = related - valid_objects
        if missing:
            bad.append((row[EVENT_ID], sorted(missing)))

    if bad:
        raise ValueError(f"{scenario_name}: dangling object references: {bad}")

    if ocel.events[EVENT_ID].duplicated().any():
        raise ValueError(f"{scenario_name}: duplicate canonical event ids remain")

    return True


def merge_verified_pair(
    ocel,
    duplicate_eid,
    canonical_eid,
    rule,
    authoritative_source_for=None,
):
    """
    Custom verified-pair merge.

    This is intentionally explicit: only reviewed pairs are merged.
    It preserves source provenance and does not infer missing relations.
    """
    ocel = deepcopy_ocel(ocel)
    ev = ocel.events

    can_idx = ev.index[ev[EVENT_ID] == canonical_eid]
    dup_idx = ev.index[ev[EVENT_ID] == duplicate_eid]

    if len(can_idx) != 1 or len(dup_idx) != 1:
        # Pair no longer exists; return unchanged copy.
        return ocel

    can = ev.loc[can_idx[0]]
    dup = ev.loc[dup_idx[0]]

    union_objects = sorted(
        set(_as_list(can[OBJECTS])).union(set(_as_list(dup[OBJECTS])))
    )

    provenance = sorted(
        set(_as_list(can.get("provenance_source_events", [])))
        | set(_as_list(dup.get("provenance_source_events", [])))
        | {canonical_eid, duplicate_eid}
    )

    merged_sources = sorted(
        set(_as_list(can.get("merged_sources", [])))
        | {can.get("source"), dup.get("source")}
    )

    merged_source_keys = sorted(
        set(_as_list(can.get("merged_source_event_keys", [])))
        | {can.get("source_event_key"), dup.get("source_event_key")}
    )

    merged_payload_hashes = sorted(
        set(_as_list(can.get("merged_payload_hashes", [])))
        | {can.get("payload_hash"), dup.get("payload_hash")}
    )

    conflicts = {}
    authoritative_source_for = authoritative_source_for or {}

    protected = {
        EVENT_ID,
        TIMESTAMP,
        ACTIVITY,
        OBJECTS,
        "source",
        "source_event_key",
        "payload_hash",
        "ingested_at",
        "source_seq",
        "original_timestamp",
        "original_activity",
        "provenance_source_events",
        "merged_sources",
        "merged_source_event_keys",
        "merged_payload_hashes",
        "merge_rule",
        "attribute_conflicts",
    }

    for col in ev.columns:
        if col in protected:
            continue

        canonical_value = can.get(col)
        duplicate_value = dup.get(col)

        if pd.notna(duplicate_value) and (
            pd.isna(canonical_value) or canonical_value != duplicate_value
        ):
            conflicts[col] = {
                "canonical_value": canonical_value,
                "duplicate_source": dup.get("source"),
                "duplicate_value": duplicate_value,
            }

            # Optional authority matrix.
            # Example: authoritative_source_for={"invoice_number": ["BILLING"]}
            if dup.get("source") in authoritative_source_for.get(col, []):
                ev.loc[can_idx[0], col] = duplicate_value

    ev.loc[can_idx[0], OBJECTS] = [union_objects]
    ev.loc[can_idx[0], "provenance_source_events"] = [provenance]
    ev.loc[can_idx[0], "merged_sources"] = [merged_sources]
    ev.loc[can_idx[0], "merged_source_event_keys"] = [merged_source_keys]
    ev.loc[can_idx[0], "merged_payload_hashes"] = [merged_payload_hashes]
    ev.loc[can_idx[0], "merge_rule"] = rule
    ev.loc[can_idx[0], "attribute_conflicts"] = [conflicts]

    ocel.events = ev.drop(index=dup_idx[0]).reset_index(drop=True)
    return ocel


def apply_semantic_order(ocel, ordered_eids):
    """
    Create a deterministic total order from a partial semantic order.
    The original timestamp is preserved.
    """
    ocel = deepcopy_ocel(ocel)

    order_map = {eid: idx for idx, eid in enumerate(ordered_eids)}
    ocel.events["semantic_order"] = ocel.events[EVENT_ID].map(order_map)

    # Events not explicitly listed receive a stable trailing order.
    max_order = len(ordered_eids)
    missing = ocel.events["semantic_order"].isna()
    ocel.events.loc[missing, "semantic_order"] = (
        max_order + ocel.events.index[missing]
    )
    ocel.events["semantic_order"] = ocel.events["semantic_order"].astype(int)

    # Local deterministic sort before using PM4Py sorting helper.
    ocel.events = ocel.events.sort_values(
        ["original_timestamp", "semantic_order", EVENT_ID]
    ).reset_index(drop=True)

    sorted_ocel = pm4py.ocel_sort_by_additional_column(ocel, "semantic_order")
    if sorted_ocel is not None:
        ocel = sorted_ocel

    # Synthetic tie-breaking timestamp. It must not replace original_timestamp.
    ocel.events["adjusted_timestamp"] = pd.to_datetime(
        ocel.events["original_timestamp"]
    )

    try:
        timed_ocel = pm4py.ocel_add_index_based_timedelta(
            ocel,
            column="adjusted_timestamp",
            index_column="semantic_order",
        )
        if timed_ocel is not None:
            ocel = timed_ocel
    except Exception:
        # API signatures can differ by PM4Py version.
        ocel.events["adjusted_timestamp"] = pd.to_datetime(
            ocel.events["adjusted_timestamp"]
        ) + pd.to_timedelta(ocel.events["semantic_order"], unit="ms")

    # Guarantee that the business timestamp column remains unchanged.
    ocel.events[TIMESTAMP] = ocel.events["original_timestamp"]

    return ocel


# ---------------------------------------------------------------------
# Scenario 1: conservative cleaning
# ---------------------------------------------------------------------

ocel_cons = ensure_original_columns(ocel_raw)

# Pre-check candidate duplicate groups before any library operation.
candidate_report = candidate_precheck(ocel_cons)

# Exact technical duplicate removal only.
# This is justified as a first pass because it should remove only repeated records.
dropped = pm4py.ocel_drop_duplicates(ocel_cons)
if dropped is not None:
    ocel_cons = dropped

# Verified pair merges.
ocel_cons = merge_verified_pair(

    duplicate_eid="e04",
    canonical_eid="e03",
    rule="reconciliation_same_physical_scan",

ocel_cons = merge_verified_pair(

    rule="same_invoice_issuance_V1",
    authoritative_source_for={
        # Example authority matrix:
        # "invoice_number": ["BILLING"],
        # "accounting_posting": ["ERP"],
    },
)

# Refine labels where harmonization hides semantics.
refined_activities = {
    "e06": "Pack Package (WMS detail)",
    "e07": "Pack Package (ERP summary)",

ocel_cons.events["refined_activity"] = (

conservative_order = [

# ---------------------------------------------------------------------

# ---------------------------------------------------------------------

ocel_evidence = deepcopy_ocel(ocel_cons)

# Merge ERP pack summary into WMS pack detail only if derivation is accepted.
ocel_evidence = merge_verified_pair(

evidence_order = [
    "e01",

ocel_evidence = apply_semantic_order(ocel_evidence, evidence_order)
validate_referential_integrity(ocel_evidence, "evidence_based")


# ---------------------------------------------------------------------
# Scenario 3: mechanically aggressive PM4Py merging
# ---------------------------------------------------------------------

warnings.warn(
    "Aggressive OCEL merging can collapse abstraction levels, "

ocel_aggr = ensure_original_columns(ocel_raw)

# Library merge step. In some PM4Py versions this merges exact duplicate events;

merged_aggr = pm4py.ocel_merge_duplicates(ocel_aggr)
if merged_aggr is not None:
    ocel_aggr = merged_aggr

# Emulate aggressive object-common merging, but still protect e05 and e14.
ocel_aggr = merge_verified_pair(
    ocel_aggr,
    duplicate_eid="e04",
    canonical_eid="e03",

)

ocel_aggr = merge_verified_pair(

ocel_aggr = merge_verified_pair(
```

## 7. Sensitivity analysis

### Raw dataset

Expected event count: **17**.  
Expected event-to-object relation count: **44**, based on the listed related objects.

The raw OCEL contains cross-system duplicates and abstraction-level duplicates. This inflates frequencies and can create apparent loops.

### Conservative dataset

Expected event count: **15**.  
Expected E2O relation count: **39**.  
The reduction comes from removing e04’s three object relations and e16’s two object relations after merging.

Effects:

- **Order-flattened DFG**: `Pick Item -> Pack Package` becomes cleaner. The duplicate scanner/WMS pick no longer inflates the pick frequency. However, `Pick Item -> Pick Item` may still appear because e03 and e05 are two legitimate item picks for O1.
- **Item-flattened DFG**: I1 shows one pick followed by pack. I2 shows one pick followed by pack. This is the desired lifecycle view.
- **Payment-flattened DFG**: M1 shows authorize then capture. M2 shows capture only, based on available data. e15 is not attached to M1 or M2, preventing false payment duplication.
- **OC-DFG edges**: frequencies for `Pick Item -> Pack Package` are lower than raw because e04 is merged. `Issue Invoice -> Authorize Payment` is not doubled by e16.
- **ET–OT weights**: `Pack Package` remains associated with both Item and Package because e06 and e07 are retained. `Capture Payment` remains associated with Payment for e13/e14, while e15 remains invoice-level.
- **OTG relations**: Order–Item–Package and Order–Invoice–Payment relations remain separated. Partial payments remain visible.
- **Apparent rework**: reduced, but not eliminated. Some loops may remain if refined labels are ignored and only original activity names are used.
- **Lifecycle/performance**: durations are not artificially distorted by merged abstraction events. ERP summary latency remains visible.

### Evidence-based merge dataset

Expected event count: **14**.  
Expected E2O relation count: **37**, assuming e07 is merged into e06 and object relations are unioned.

Effects:

- **Order-flattened DFG**: `Pack Package -> Pack Package` disappears if refined labels are not used.
- **Item-flattened DFG**: item lifecycles remain mostly intact because e06 carries item relations.
- **Payment-flattened DFG**: unchanged from conservative if e15 is kept separate.
- **OC-DFG edges**: pack-related edge frequency decreases. The ERP summary no longer appears as a separate pack event.
- **ET–OT weights**: `Pack Package` becomes more strongly associated with Package and Item from the WMS view, while ERP summary-specific weights disappear.
- **OTG relations**: ERP-to-package abstraction is weakened.
- **Apparent rework**: less apparent rework, but at the cost of hiding abstraction-level divergence.
- **Lifecycle/performance**: ERP posting delay may disappear, making WMS-to-ERP integration look faster than observed.

### Aggressive library merge dataset

Expected event count: **13** if e08/e09 are merged.  
Expected E2O relation count: **34**, assuming e08/e09 have identical object relations and unioning does not add objects.

Effects:

- **Order-flattened DFG**: `Dispatch Package -> Dispatch Package` disappears, but only because warehouse release and carrier acceptance were collapsed.
- **Item-flattened DFG**: unchanged if e05 is protected.
- **Payment-flattened DFG**: unchanged if e13/e14 are protected. If a naive `have_common_object=True` rule merges e13/e14, M2 disappears and payment analytics become wrong.
- **OC-DFG edges**: dispatch frequency is understated. Carrier acceptance is no longer separately measurable.
- **ET–OT weights**: carrier acceptance weight is absorbed into warehouse dispatch.
- **OTG relations**: Package–Delivery relation still exists, but the handover nuance is weakened.
- **Apparent rework**: loops are reduced aggressively, but some are removed by semantic flattening rather than evidence.
- **Lifecycle/performance**: carrier acceptance latency and custody-transfer duration can vanish.

Six concrete edges or patterns whose interpretation changes:

1. `Pick Item -> Pack Package`: frequency changes after merging e03/e04.
2. `Pick Item -> Pick Item`: may look like rework but is actually concurrent item picking.
3. `Pack Package -> Pack Package`: abstraction-level difference between WMS and ERP, not necessarily rework.
4. `Dispatch Package -> Dispatch Package`: harmonization collision between release and acceptance.
5. `Dispatch Package -> Handover to Carrier`: changes if e08/e09 are merged.
6. `Issue Invoice -> Authorize Payment`: frequency changes after merging e11/e16.
7. `Capture Payment -> Capture Payment`: may represent distinct partial payments or summary duplication, not rework.
8. `Capture Payment -> ERP payment summary`: disappears if e15 is merged incorrectly.

## 8. Audit trail and reversibility

Use a provenance schema with at least the following entities.

**Canonical event table**

- `canonical_eid`
- `scenario`
- `refined_activity`
- `original_activity`
- `original_timestamp`
- `adjusted_timestamp`
- `ordering_rule`
- `semantic_order`
- `confidence`
- `reason`

**Source event lineage table**

- `canonical_eid`
- `source_eid`
- `source`
- `source_event_key`
- `source_seq`
- `ingested_at`
- `payload_hash`
- `is_canonical`
- `was_dropped`
- `merge_rule`
- `rule_version`
- `reviewer`
- `decision_timestamp`

**Attribute lineage table**

- `canonical_eid`
- `attribute_name`
- `retained_value`
- `source_eid`
- `source`
- `authoritative_system`
- `conflicting_value`
- `conflict_resolution`
- `discarded_reason`

**Relation lineage table**

- `canonical_eid`
- `object_id`
- `relation_type`
- `source_eids`
- `relation_added_by_rule`
- `relation_removed_by_rule`

An analyst can reconstruct the raw view by:

1. selecting the desired scenario;
2. expanding each canonical event to its source events using the source lineage table;
3. restoring `original_timestamp` and `original_activity`;
4. ignoring `adjusted_timestamp` and `semantic_order`;
5. re-inserting dropped source events from the immutable raw store;
6. reversing attribute conflict resolution by selecting source-specific values.

The raw OCEL should never be overwritten. All cleaned datasets should be materialized as versioned scenario outputs.

## 9. Failure modes and safeguards

1. **Collapsing distinct partial payments**  
   Failure: merging e13 and e14 because they share O1 and V1.  
   Safeguard: require matching Payment object or explicit payment key before merging payment events.

2. **Converting abstraction-level updates into false rework**  
   Failure: e06/e07 or e13/e15 appear as repeated activities.  
   Safeguard: refine labels, retain derived-from provenance, and merge only with explicit evidence.

3. **Ordering by ingestion time**  
   Failure: treating `ingested_at` as business time.  
   Safeguard: use ingestion time only as a low-priority deterministic cue, never primary.

4. **Treating shared objects as proof of duplication**  
   Failure: assuming events sharing O1 or V1 are duplicates.  
   Safeguard: identify discriminating lifecycle objects such as Item or Payment.

5. **Unioning incompatible E2O relations**  
   Failure: adding M1 or M2 to e15 without evidence.  
   Safeguard: merge relations only for verified same events; otherwise record derivation links.

6. **Changing durations through synthetic microseconds**  
   Failure: adjusted timestamps become factual timestamps.  
   Safeguard: keep `original_timestamp`, store adjusted timestamp separately, and report sensitivity with and without tie-breaking.

7. **Losing source-authoritative attributes**  
   Failure: ERP overwrites Billing invoice attributes, or vice versa.  
   Safeguard: maintain attribute lineage and an authority matrix.

8. **Applying duplicate functions to the whole OCEL without inspection**  
   Failure: global deduplication removes semantically distinct events.  
   Safeguard: run candidate-group pre-checks, reviewed-pair merges, and post-merge validation.
