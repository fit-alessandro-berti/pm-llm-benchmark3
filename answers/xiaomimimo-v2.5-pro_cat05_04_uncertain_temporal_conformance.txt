## 1. Normalization Assumptions

- **Interval Construction & Clock Offset:** For a source clock offset bound $[a, b]$, the true time is `recorded_time - offset`. Since `offset` $\in [a, b]$, the true time falls in the interval `[recorded_time - b, recorded_time - a]`. 
- **Resolution/Rounding:** Applied *before* clock correction. 
  - Exact to second (HUB): Measurement uncertainty of $\pm 0.5$s is added to the clock-offset bounds.
  - Floor to minute: Adds $[0\text{s}, 59.999\text{s}]$ to the recorded minute.
  - Round to nearest 10s/minute: Adds $[-5\text{s}, +5\text{s}]$ or $[-30\text{s}, +30\text{s}]$ respectively.
- **Time-Zone Conversion:** CEST = UTC+2, CET = UTC+1, EDT = UTC-4, BST = UTC+1.
- **DST Folds (T-405):** The ingestion sequence strictly orders events: `Alert_Received` (02:50) $\to$ `Investigation_Start` (02:05) $\to$ `Containment_Complete` (02:42). Because CET (UTC+1) is chronologically *after* CEST (UTC+2) on the fall-back day, the only way `02:50` can precede `02:05` is if `02:50` is CEST and `02:05` is CET. Similarly, `02:42` must be CET to follow `02:05`. This resolves the ambiguity into a single, non-disjoint feasible sequence.
- **Inferred Starts (T-404):** `Investigation_Start` is derived by subtracting the duration $[18\text{m}, 25\text{m}]$ from `Investigation_Complete`. Interval arithmetic is preserved (earliest start = earliest complete - longest duration).
- **Causal Constraints:** 
  - For T-404 and T-409, if inferred `Start < Alert_Received`, the start is clamped to $\ge$ `Alert_Received`.
  - For T-407, `Alert_Received` must precede `Investigation_Start`. The network latency window $[0, 20\text{m}]$ is truncated at the latest possible `Investigation_Start`.
- **Mobile Entry Delay (T-406):** I assume the delay represents the time between event observation and data entry. If the user entered the *current* clock reading upon opening the app 5 minutes late, the recorded time overestimates the true occurrence time. Therefore, the feasible occurrence window is shifted *earlier* by $[0, 5\text{m}]$.
- **SLA vs. Profile:** SLA is a hard operational maximum. The temporal profile is a statistical expectation.

## 7. Governance Recommendation

1.  **UTC Storage & Resolution Metadata:** Systems must store raw timestamps in UTC (or with explicit, unambiguous offset IDs) and retain the original resolution (e.g., `floor_to_minute`, `exact_second`) in metadata. This eliminates TZ/DST guessing.
2.  **Clock Telemetry & NTP Enforcement:** All event-emitting systems (especially edge/mobile/legacy) must log their NTP sync offset at the moment of event generation. Weak estimates (like T-409) must trigger a "low-confidence" flag. 
3.  **Lifecycle & Semantic Controls:** Standardize `Start` vs `Complete` semantics. When `Start` is missing, log a "duration range" inference flag so downstream parsing doesn't treat it as a hard fact.
4.  **Causal Identifiers:** Link `Alert_Sent` to `Alert_Received` using a transaction ID. This allows strict latency calculation rather than relying on time-window correlation.
5.  **Interval Overlap Enforcement Policy:** Define that a SLA is only "Certain Pass" if the *worst-case* interval is within the limit. If the interval overlaps the limit (Possible Violation), it must be treated as a governance exception requiring manual review until telemetry is tightened. PM4Py point-estimates should only be used for high-level trend analysis, not for hard SLA enforcement.
