# 3. Adversarial Review of Model S

**Strongest case for Model S:** It is sound (block-structured, no deadlocks), extremely fast (0.018 s), highly comprehensible (4.4/5), and replay-robust to missing middle events (e.g., absent `Supplier Review` or `Expedite Review`). For pure exploration—visualizing that the process always starts with `Register Dossier`, always ends with `Release Order`, and includes a flexible middle zone—it provides a readable “picture” without overwhelming users with branches.

**Strongest case against Model S:** Its permissiveness is not intentional noise tolerance; it is an accidental semantic collapse of mandatory controls and ordering rules. The parallel block `+(X(Credit,tau), X(Technical,tau), X(Supplier,tau), X(Expedite,tau))` treats all four activities as simultaneously optional and interleavable. This violates P2 (mandatory before approval), P4 (Expedite must follow both checks), and P1/P5 implicitly by allowing arbitrary omissions.

Five concrete undesirable behaviors admitted by Model S (all are valid traces in its language):

1. **Skips both mandatory checks:**  
   `Register Dossier  Manager Approval  Release Order`  
   (All middle branches take `tau`; B3 analog without checks.)

2. **Expedite before mandatory checks (ordering violation):**  
   `Register Dossier  Expedite Review  Credit Check  Technical Review  Manager Approval  Release Order`  
   (Within the parallel block, interleaving allows Expedite first; B4.)

3. **Supplier Review placed before checks with no external gate:**  
   `Register Dossier  Supplier Review  Credit Check  Technical Review  Auto Approval  Release Order`  
   (Interleaving allows Supplier before checks; no `external/internal` attribute blocks it.)

4. **Skips Credit Check alone, retains Technical:**  
   `Register Dossier  Technical Review  Supplier Review  Manager Approval  Release Order`  
   (`Credit Check` takes `tau`; `Technical` executes. P2 violated.)

5. **Allows any subset/interleaving including none:**  
   `Register Dossier  Credit Check  Release Order`  
   (`Technical`, `Supplier`, and `Expedite` all silent; approval present but no technical validation.)

**Distinction:** Intentional noise tolerance would allow `Supplier Review` to be missing (correct, since it is external-only) or allow `Expedite Review` to be absent (correct, optional). Accidental flaws include: (i) making `Credit` and `Technical` silent, (ii) placing them in unconstrained parallel with `Expedite`, destroying the “must follow both checks” rule, and (iii) lacking any loop or correction mechanism, which means `Correct Dossier` is structurally invisible and B6/B8 cannot be evaluated correctly.

# 4. Adversarial Review of Model C

**Strongest case for Model C:** It captures exactly the eight observed training variants (including the correction loop with full recheck and the single `Auto Approval` variant). For an audit context that treats “anything not seen is non-compliant until approved” (F8), this is defensible: it provides an explicit allow-list. The 0.941 training precision reflects that its language is tightly bounded.

**Strongest case against Model C:** It is an explicit enumeration, not a generalizable model. The 33 duplicate labels (undocumented definition) and eight explicit XOR branches create a maintenance nightmare (F2, F3). Its holdout fitness collapses to 0.744 because legitimate unseen combinations—such as `Auto Approval` combined with both `Supplier Review` and `Expedite Review`, or reversed check order with `Auto Approval`—are structurally absent. The correction loop (trace 7) enforces that *both* checks repeat; P6 allows partial repetition, which C rejects (B6). High precision is likely an artifact: with only eight paths and precision computed solely against the positive log (F5), there is no penalty for false positives outside the log, and alignment ambiguity from duplicate nodes may inflate the score.

Key pathologies:
- **Branch enumeration:** Every new valid combination requires adding a new child to the root `X`, making updates manual and error-prone.
- **Duplicate labels (33):** The same activity names appear in separate branches; this harms arc-degree simplicity (0.281), increases alignment runtime (0.440 s), and makes ownership/impact analysis impossible.
- **Unseen combinations:** F4 describes cases with `Supplier Review` + `Auto Approval` + alternate check order—absent from the eight traces—so C rejects them.
- **Correction handling:** Only one loop variant exists (`Correct Dossier` followed by both `Credit Check` and `Technical Review`). Partial correction (only one affected check) is structurally impossible.
- **Holdout degradation:** 0.744 indicates the model does not predict; it memorizes.
- **Maintainability:** Changing the approval rule or adding an external-source gate requires editing every branch.
- **Precision artifact:** Without a negative trace suite, 0.941 proves only that observed traces fit; it says nothing about the model’s false-positive rate.

# 6. Likely Metric Pathologies

Ranked by likely decision impact:

1. **Fitness rewarded by optionalizing mandatory behavior (Critical):** Model S achieves 0.981 holdout fitness largely because `Credit Check` and `Technical Review` can be replaced by `tau`. In enforcement, this is catastrophic: a trace that skips a credit check is replayed “successfully.” This invalidates fitness as a compliance metric for S.
2. **Positive-log-only precision (Critical):** F5 states precision was computed only on observed positives. Without a curated negative suite (e.g., B3, B4, B8, adversarial traces), C’s 0.941 precision is unverified. A model that allows thousands of unobserved invalid traces but never sees them in the positive log can still score 0.941.
3. **Missing-event / missing-attribute bias (Critical):** The log lacks `external/internal` (making P3 structurally unenforceable) and `affected_check` (making P6 unenforceable). Both models approximate these conditions; any claim of “audit-ready” enforcement is overstated without these fields.
4. **Generalization rewarded by excessive permissiveness (High):** S’s 0.907 token-based generalization reflects that its language is large and unstructured, not that it predicts true process dynamics. This is a classic “permissiveness bias.”
5. **Duplicated-label effects and model-size confounding (High):** C’s 33 duplicates inflate state-space size, degrade simplicity (0.281), and drive alignment runtime (0.440 s). The duplicate-label definition is undocumented, so the metric is not reproducible.
6. **Silent-transition effects (Moderate):** S uses `tau` extensively. Silent transitions absorb missing events, artificially smoothing fitness and hiding omissions of mandatory steps.
7. **Train/holdout leakage and split sensitivity (Moderate):** The same 80/20 split is claimed but seeds, case-level grouping (to avoid splitting order variants), and preprocessing (filtering incomplete cases) are not published. Holdout fitness differences could be split artifacts.
8. **Alignment-cost sensitivity (Moderate):** Fitness and precision depend on move costs. If silent moves are cheaper than visible moves, S’s skips are penalized less severely. The exact cost matrix is not reported.
9. **Stakeholder-score methodology (Low-Moderate):** The 1–5 comprehension score has no documented protocol, sample size, or task design. It is likely presentation-biased (F7 vs. F8 advocacy effects).
10. **Runtime confounding by model size (Low):** C’s 0.440 s is largely explained by branch enumeration and duplicate nodes, not by an inferior algorithm.

# 7. Third Alternative

**Design philosophy:** A block-structured procedural backbone captures the ordering and exclusivity rules that are structurally knowable (P1, P2, P4, P5), while an explicit external constraint layer handles conditions that require missing data attributes (`external/internal` for P3; `affected_check` for P6/P7). This avoids C’s brittle enumeration and S’s accidental removal of mandatory controls.

### 1. Compact Formal Description

- **Root:** Sequence.
- **Phase 1 (Mandatory Checks):** Parallel (`+`) execution of `Credit Check` and `Technical Review`. Both required; order free.
- **Phase 2 (Optional Middle Zone):** XOR choice (`X`) among:
  - `Supplier Review  Expedite Review`
  - `Expedite Review  Supplier Review`
  - `Supplier Review` only
  - `Expedite Review` only
  - Silent (`tau`) — neither present
  All branches occur after Phase 1 and before Phase 3, enforcing P4.
- **Phase 3 (Approval):** XOR (`X`) of exactly `Manager Approval` or `Auto Approval` (P5).
- **Phase 4 (Release):** `Release Order` (P1).
- **External Correction Policy (post-hoc / data-layer):**
  - `Correct Dossier` is permitted as an observable insertion between Phase 2 and Phase 3, or within Phase 1 repetition.
  - After `Correct Dossier`, repetition of `Credit Check` and/or `Technical Review` is permitted (partial recheck per P6).
  - Any repetition of `Credit Check` or `Technical Review` without a preceding `Correct Dossier` is flagged as suspicious (P7).
  - `Supplier Review` presence is validated against an external `source_type` field (`external` required); the backbone allows it structurally, but the data gate enforces P3.
  - Negative traces (e.g., B3, B4, B8 without correction) are rejected by the policy layer, not solely by structural absence, ensuring explicit audit logging.

### 4. Explicit Semantics

- **Mandatory checks:** Enforced structurally by the parallel block (`+`). Both must complete before Phase 2 (and thus before approval).
- **Optional Supplier Review:** Structurally permitted in Phase 2. Enforced as “required only for external” by the `source_type` data gate; traces with `Supplier Review` but `internal` source are flagged by the policy layer.
- **Expedite Review ordering:** Structurally placed in Phase 2 (after Phase 1), so it always follows both checks. The XOR branches allow it before or after `Supplier Review` (sequences) or alone.
- **Exactly-one approval:** Enforced by `X('Manager Approval', 'Auto Approval')`.
- **Correction/recheck:** Not structurally looped (because `affected_check` is missing). Instead, the backbone allows `Correct Dossier` as an observable event (if inserted by the log) and the external policy permits subsequent repetitions of `Credit Check` and/or `Technical Review`. If `Correct Dossier` is absent and a mandatory check repeats (`B8`), the policy flags it.

### 5. Limitations Caused by Missing Attributes

- **`external/internal` missing:** The backbone cannot gate `Supplier Review` structurally. Without linking the model to an external `source_type` table, P3 is unenforceable by the net alone.
- **`affected_check` missing:** The backbone cannot model “only the affected check repeats.” It permits any subset of `{Credit Check, Technical Review}` after `Correct Dossier`. This is slightly more permissive than reality, but far less permissive than S (which allows skipping checks entirely) and more flexible than C (which forces both).
- **No structural loop:** Because the loop is not encoded in the tree, replay of traces with `Correct Dossier` followed by partial rechecks requires the alignment algorithm to treat the backbone as allowing those repetitions via the external layer. In strict structural replay, such traces may show moves unless the external layer is integrated as a “soft constraint.”

### Decision Rule for Rejection Despite Good Metrics

A model is **rejected for enforcement deployment** if any of the following hold, regardless of aggregate fitness:
- Soundness check fails.
- Negative-trace rejection rate < 0.95 (i.e., admits >5% of curated forbidden traces like B3, B4, B8 analogs).
- Holdout fitness < 0.85 on **stratified** splits (not just aggregate).
- Mandatory-check omission is structurally possible (e.g., `tau` branch for `Credit Check` in a parallel block without external validation).
- Stakeholder comprehension protocol shows mean score < 3.0 or update-error rate > 20%.

# 10. Governance Recommendation

- **Exploration only (retired with warning):** Model S may be used for **initial exploratory visualization** of the dossier lifecycle, but only with an explicit disclaimer that it violates P2, P4, and P7. It must not be used for conformance, monitoring, or audit. Its 0.981 holdout fitness is an artifact of optionalizing mandatory controls.
- **Audit documentation only (restricted):** Model C may be retained as an **explicit allow-list of observed training variants** for historical audit reference. It must not be used for predictive conformance or holdout evaluation (0.744 fitness is unacceptable). It should be retired from operational monitoring due to 33 duplicate labels, 0.281 simplicity, 0.440 s alignment time, and unverified precision (positive-log-only).
- **Third alternative (`model_third`):** Recommended for **pilot deployment in exploration and preliminary compliance** subject to conditions:
  1. The external data layer (`source_type` for P3; `affected_check` or correction-log for P6/P7) must be implemented and linked to the event stream.
  2. Soundness verified (`check_soundness`).
  3. Stratified holdout fitness  0.90 and negative-trace rejection rate  0.95.
  4. Stakeholder comprehension protocol (Section 9) completed with mean  3.5.
  5. All adversarial traces (ADV1–ADV3) evaluated and documented.
- If the missing attributes (`external/internal`, `affected_check`) cannot be added within the data pipeline, then **no procedural model should be used for enforcement**; only a purely declarative constraint engine (e.g., DECLARE over the raw log with data conditions) should be considered.

# 11. Dissenting View

The recommendation to prefer the third alternative and retire C for enforcement is wrong in a high-regulation context. The F8 advocate is correct: in compliance, “unseen behavior should be treated as non-compliant until approved.” Model C’s 0.744 holdout fitness is not a failure; it is the correct rejection of unvetted combinations—such as `Auto Approval` paired with both `Supplier Review` and `Expedite Review` (B5 analog)—that have not been through managerial or audit approval. The third alternative’s “flexible backbone” is precisely the risk: by allowing any Phase 2 ordering and any subset of optional activities, it structurally admits B5-type traces before they are validated by the missing `source_type` and `affected_check` fields. But those fields are missing; therefore, the external data layer is a speculative addition, not an implemented control. Without it, M3 is just a more readable version of S with the same core vulnerability: it allows `Supplier Review` to appear on internal orders and permits `Expedite Review` in combinations never audited. Model S should also be rejected, but not replaced by M3—rather, the organization should fix the data collection (`external/internal`, `affected_check`), then rebuild C with the corrected attributes rather than inventing a hybrid that hides missing-data risk behind “post-hoc policy checks.” If evidence showed that the missing attributes are available in the source ERP and can be merged with 99% coverage, then M3’s external layer becomes defensible; if holdout stratification reveals that C’s 0.744 drop was caused by a single malformed case cluster rather than true variant rejection, then C should be retained and expanded manually with approved variants. Until either condition is met, the safest governance choice is to reject both S and M3 for enforcement, use C as a negative-reference allow-list, and block all non-listed traces pending manual review. What would change my decision is: (a) documented negative-suite testing showing M3 rejects >99% of forbidden traces with the data layer active; (b) reproducible split seeds showing C’s holdout collapse was split-bias; or (c) proof that `external/internal` and `affected_check` fields exist but were excluded by a preprocessing error, allowing structural gates to replace speculative external checks.
