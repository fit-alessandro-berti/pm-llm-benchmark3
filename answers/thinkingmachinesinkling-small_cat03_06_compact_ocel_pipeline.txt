## 1. Modeling assumptions

- **Object types and capitalization.** The business entities are capitalized in natural language (Order, Item, Package, Delivery, Invoice, Payment). In the OCEL tables they are stored with those exact spellings in `ocel:type`; object IDs carry prefixes (`O` for orders, `I` for items, `P` for packages, `D` for deliveries, `V` for invoice, `M` for payments).
- **E2O qualifier vocabulary.** To keep consistency across all relation rows, the qualifier is the object-type role of the link: `order`, `item`, `package`, `delivery`, `invoice`, `payment`. Thus every event-to-object tie is self-describing and invariant regardless of event activity.
- **O2O direction conventions.** Direct relations are directed from container/source to contained/target: `Order  Item` (`contains`); `Package  Item` (`packs`); `Delivery  Package` (`carries`); `Invoice  Order` (`bills`); `Payment  Invoice` (`partially_settles` / `completes_settlement`).
- **Logistics and financial direct links.** Primary objects mentioned in an event are always directly tied (`Pack Package`  `P1`; `Dispatch Package`  `D1`). For explicitly joint operations—`Reserve Stock`, `Pack Package` (P1 combines I1/I3), `Dispatch Package` (D1 carries P1), `Confirm Delivery`, and `Issue Invoice`—direct E2O links to the involved Orders and Items are also included. **Financial settlement (`Record Payment`) links only to `Payment` and `Invoice`, not to Orders**, so that the mediation through `V1` is preserved structurally rather than flattened prematurely.
- **Preventing propagation confusion.** Analytical reachability (e.g., Payment  Invoice  Order, or Package  Item  Order) is obtained only through the `o2o` table, never by inventing direct E2O links. If an analyst wants Order-level settlement traces, they must traverse `o2o`; the E2O table remains a record of direct observations.
- **Trade-off (direct vs. propagated).** Direct source relations make convergence explicit (e.g., `e7` touches both `O100` and `O200` because `P1` crosses orders) and allow accurate per-object flattening without hidden inference. Propagated relations via `o2o` keep the E2O table compact but require PM4Py to apply propagation settings during flattening, which can introduce ambiguity about whether a copied event belongs to the primary object or is analytically inferred. I choose direct links for shared operational events to keep the dataset semantically transparent.
- **Version assumption.** The code assumes `from pm4py.objects.ocel.obj import OCEL` with a constructor `OCEL(events=..., objects=..., relations=..., o2o=...)` (PM4Py 2.7+ pattern). If a specific environment uses `pm4py.ocel.OCEL` or requires `parameters`, only the import/construction line needs substitution; the DataFrames themselves are unchanged.

## 5. Expected object-centric structures

- **OC-DFG:** The graph will show `Reserve Stock` feeding into `Pack Package`, which feeds `Dispatch Package`, then `Confirm Delivery`, parallel to an `Issue Invoice` branch feeding `Record Payment`. The critical structural feature is the **convergence at `Pack Package` and `Dispatch Package`** because `P1` bundles `I1` (from `O100`) and `I3` (from `O200`). Thus `O100` and `O200` merge into shared logistics nodes, then diverge again at `Close Order`. `P1` is the physical artifact causing cross-order edges.
- **OTG (Object Type Graph):** Nodes: Order, Item, Package, Delivery, Invoice, Payment. Edges driven by co-occurrence in events: OrderItem (Add/Reserve/Pack), ItemPackage (Pack), PackageDelivery (Dispatch/Confirm), OrderInvoice (Issue), InvoicePayment (Record). The graph is a pipeline with a “diamond” around `Pack Package` due to multi-type involvement.
- **ET–OT (Event Type–Object Type):** `Reserve Stock` touches both Order and Item; `Pack Package` touches all three of Order, Item, Package; `Dispatch Package` touches Order, Package, Delivery; `Record Payment` touches Invoice and Payment; `Close Order` touches only Order. This highlights that logistics is multi-object while financial close is order-specific.
- **Object-centric Petri net:** The net will have transitions synchronized by token presence in multiple object places. For `e7` (`P1`), a transition requires tokens for `P1`, `I1`, `I3`, `O100`, `O200` simultaneously—explicitly modeling that packing is a joint operation across orders. Because the same `O100` token must also enable `P2` packing (`e8`), the net reveals resource reuse (the order participates in two packages). It will **not** have a single unique interpretation because synchronization choices (e.g., whether to model `O100` as one token per event or per trace) are modeling decisions.
- **Object-interactions summary:** High interaction counts between Order–Item, Package–Item, and Package–Delivery. Cross-order interaction is explicitly visible because `O100` and `O200` both appear in relations for `e6`, `e7`, `e9`, `e11`, `e13`. `V1` interacts with both orders; `M1` and `M2` interact only with `V1`. `P1` is the bridge object linking `I1` (O100) and `I3` (O200).

Explicit references: `P1` merges `I1`/`I3` from `O100`/`O200`; `V1` is settled by `M1` and `M2`; `O200` closes at `e16` and `O100` at `e17`.

## 6. Modeling alternatives

1. **Source-minimal E2O:** Only link each event to the object explicitly named. `Pack Package` links only to `P1`; `Reserve Stock` links only to items; `Dispatch Package` only to `D1`/`P1`. **Effect:** E2O table shrinks; flattening on Order loses all shared logistics; OC-DFG shows isolated vertical slices; analyst must rely fully on `o2o` propagation to see cross-order effects. The business story is unchanged but hidden.
2. **Full operational involvement:** Every event that could possibly involve an object gets a direct link (e.g., `Add Item` also links to all items already in the order; `Dispatch` links to all orders ever mentioned). **Effect:** Relation inflation; traces become almost identical across objects; DFG gains spurious concurrency; discovery is harder; no new business insight.
3. **O2O-propagated analytical relations:** E2O only to primary objects (e.g., `Pack`  `P1` only). `relations` carries no Order/Item links for logistics. Flattening relies on PM4Py propagation through `contains`/`packs`/`carries`. **Effect:** Clean source table; but if propagation is disabled or misconfigured, flattened logs appear to miss critical shared steps; the analyst must know that `o2o` defines the business topology, not just static taxonomy.

---

## 7. Failure modes

1. **Relation inflation:** Adding all possible E2O links for `e7` and `e9` creates many rows; without deduplication, duplicates corrupt frequency analysis.
2. **Missing direct E2O links:** If `e9` does not link to `O100`/`O200`, the cross-order nature of `P1` is invisible in event-level relations; only `o2o` reveals it, which some analysts may overlook.
3. **Treating O2O as observation:** Confusing `contains` (structural) with `Add Item` (event); `O2O` has no timestamp, so using it as a temporal relation causes false sequencing.
4. **Duplicate shared events after flattening:** If flattening copies events per object without trace-level deduplication, `e6` and `e7` appear twice per flattened Order trace, making metrics like average trace length misleading unless normalized.
5. **Ambiguous payment allocation:** `M1` (100) and `M2` (150) partially settle `V1`, but without a total target amount or allocation rules in the data, discovery cannot tell whether settlement is complete.
6. **Overly short Payment traces:** Each payment object has one event; DFG has no edges; skeleton is a single node; no process dynamics are discoverable at the Payment layer alone.
7. **Constructor/API version mismatch:** If PM4Py expects `OCEL(events=..., objects=..., relations=..., o2o=..., parameters=...)` or uses a different import path, construction fails. The data semantics remain valid but the construction line requires adaptation.
8. **False total order for same-time events:** Although this dataset has no timestamp ties, if two events (e.g., `e16` and `e17`) were given the same timestamp, any ordering would be arbitrary; process discovery might invent false precedence.
