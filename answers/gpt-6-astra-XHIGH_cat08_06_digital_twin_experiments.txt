# 1. Model scope and state variables

The twin should be a **calendar-aware, discrete-event simulation with shared resources and interacting cases**. Its purpose is to estimate conditional differences between policies, including their costs and unintended effects. It should not reproduce historical traces by independently sampling each case's observed duration. The supplied summaries support an initial model and uncertainty ranges, but do not identify a calibrated, decision-ready twin.

**Boundary and clocks.** Represent application preparation and attempted submission, the municipal process, applicant and consultant responses, inspections and travel, objections, decisions, and appeals/reopening. Starting the boundary before official submission is essential for D1 and D7: moving delay outside the municipal clock must not count as eliminating it. Report both official submission-to-decision time and preparation-to-decision time. Record initial decision, decision outcome, reopening, and durable resolution separately. Define an appeal observation window with the municipality; cases still appeal-eligible at the observation boundary are not known to be permanently resolved. Withdrawals and abandonment are separate outcomes, not successful fast decisions.

Use individual cases, staff members or equivalent capacity units, and inspector trips. Represent applicants, architects, consultants, and objection groups as linked entities where their capacity or common behavior affects several applications. Avoid simulating unrelated municipal operations in detail; represent their observed capacity reservations and disruptions.

| Entity | Essential state |
|---|---|
| Application | Stable ID; type; district; architect; value; available area and violation history; review requirements and their provenance; submission/preparation times; policy version; document version; risk/complexity; age; deadline; outcome; appeal status |
| Activity instance | Activity, case, visit number, prerequisites, enabled/queued/start/resume/complete times, remaining work, assigned resources, result version, interruption and rework reason |
| Review results | Required, pending, valid, expired, or invalidated status for Planning, Fire, Environment, Public notice, Inspection, and Legal; explicit authorized inspection waiver |
| Resource | Qualifications, district restrictions, calendar, absences, non-permit reservations, current assignment, remaining shift, location where relevant |
| Queue | Ready tasks, priority, age, eligibility, continuity preferences, reserved appointment, maximum batch hold time |
| Architect/related group | Linked applications, common submission burst, response workload, shared-document changes, dependence strength |
| Neighborhood/project group | Shared objection event and resolution state; affected applications; geographic confidence when exact linkage is unavailable |
| Inspection trip | Ready cases, route, travel and visit durations, inspector, appointment commitments, departure time, cancellations/no-shows |
| Municipality | Time-varying arrivals, queue lengths and ages, work in progress, holiday/council schedule, costs, cumulative decisions and quality outcomes |

**Executable process semantics.** Use the process tree as a structural reference, then build an explicitly versioned extension:

- The tree permits Planning, Fire, and Environment to run concurrently; the textual nominal path could suggest a sequence. Confirm which reviews can actually start on the same document set. Pending confirmation, use the tree's parallel review block, with any known information dependencies added as gates, and test a more sequential alternative.
- A review-eligibility function determines mandatory branches from case attributes and policy, rather than sampling every XOR independently. Completion of an optional branch's skip path satisfies its join; an unfinished required review does not.
- Public notice follows the required reviews in the reference model, then inspection. Decision drafting requires all applicable valid results, including notice and inspection or an authorized waiver. If notice or scheduling can legitimately overlap other work, model that as a documented structural alternative.
- The tree's loops cover completeness and inspection, but do not fully express planning rework, legal rework, appeals, or shared objections. Add explicit transitions and dependency invalidation. For example, revised plans can invalidate Fire and Environment results; resubmit only affected work. Rework is not an unconditional restart of the entire case.
- D5 introduces an early legal screening task and a later confirmation gate. A pre-check based on an earlier document version cannot satisfy the final legal requirement without verification.

Do not add an observed "Completeness rework" event merely because the tree contains that label. The illustrative trace repeats Completeness check without recording that event. Treat this mismatch explicitly in conformance analysis and in the executable model.

**Resources and calendars.** Queues share the following capacity. Store timestamps in UTC, but calculate working windows and dates in the municipality's Europe/Berlin timezone, including daylight-saving changes.

| Pool | Calendar and allocation |
|---|---|
| Clerks | Five, Monday–Friday 08:00–16:00. On Monday only four are available for ordinary permit work while one handles portal support. Record support work separately. |
| Planners | Eight, Monday–Friday 09:00–17:00; two eligible only for Simple renovation, six generalists. Planning and drafting compete for this pool if that assignment is confirmed. D6 reserves a generalist, without adding capacity. |
| Fire | Tuesday–Thursday only. Resolve whether "2 FTE equivalent" denotes weekly effort or two concurrent reviewers: two people working three eight-hour days supply 48 hours/week, while two conventional 40-hour FTE supply 80. Do not silently equate them. |
| Environment | Three reviewers with 40% reserved for other duties. With eight-hour weekdays, nominal permit capacity is 72 hours/week. Use actual reservation blocks, since scattered availability and contiguous blocks have different effects. |
| Scheduling | The scheduler roster is unspecified. Provisionally model one dedicated scheduler on weekdays 08:00–16:00, and test 0.5–1 FTE or shared-clerk allocation until verified; the single resource ID in the excerpt does not establish total capacity. |
| Inspectors | Four, field work Tuesday–Friday. Visits, travel, and relevant administration consume capacity. Monday is not automatically a field day or free scheduling capacity. |
| Legal | Two; normal work pauses during council-meeting weeks and holidays. Urgent work uses an explicitly modeled exception and consumes real capacity, including hidden urgent demand omitted from the log. |
| System | Effectively unlimited concurrency; technical processing or dispatch delays can still be nonzero. Confirm who handles rejections rather than assigning them to an unlimited server. |

For pools without stated daily hours, provisionally use 09:00–17:00 on their eligible weekdays, then replace this assumption with the roster and test shorter availability. Map Completeness and Request missing documents to clerks, scheduling to its explicit pool, and review/drafting to the corresponding specialists. Allocate any human rejection preparation or permit sign-off to a confirmed finite pool; an automated issue event does not erase that effort.

Use FIFO among eligible ready tasks initially, with verified urgency and skill rules, and calibrate continuity preferences rather than assuming the resource named on a completion event worked exclusively on that case. Desk work may pause and resume across closed periods; record only active work against capacity. Inspections require an uninterrupted feasible appointment including travel. An applicant-response timer holds the case, not a municipal employee.

The 14-day notice minimum is a statutory elapsed-time constraint, provisionally in calendar days. Council meetings and holidays can delay objection resolution or the next decision gate; they should not automatically stop or extend the statutory clock. Verify the applicable clock and meeting rules locally.

**Dependencies across cases.** Generate correlated architect submissions and responses; allow shared documents to affect several applications; generate neighborhood objection shocks affecting linked cases; and build inspection trips from jointly ready cases. A batch can save travel while imposing deliberate waiting on its first case. Only legally or operationally linked cases share a completion gate: sharing an architect alone does not make all their decisions mutually dependent. All applications also interact through resource queues. Maintain an object relationship table alongside the flattened case log.

# 2. Parameter-estimation plan

**Data preparation and identifiability.** Obtain the full 18-month event history, extract boundaries, open-case snapshot, lifecycle/start records where available, resource roster, council/holiday calendars, policy effective dates, and permitted linkage attributes. The two-case excerpt is sufficient to demonstrate parsing, not estimation. Audit duplicate events, event-instance identifiers, timezone semantics, changes to case attributes, missing completions, and withdrawn/reopened cases. Keep missing, false, and not-applicable values distinct.

Human completions in the excerpt occur on weekends, including Completeness check on 3–4 January 2026, despite the stated weekday calendars. Determine whether these are illustrative timestamps, delayed logging, overtime, or calendar exceptions. Do not invent overtime to make the model fit. Public-notice timestamps also need a semantic definition: opening a notice is not completing its duration.

**Perform a capacity consistency check before fitting.** The volume is roughly 1,733 applications/month, or 400/week. If every application consumes the stated median 3.5 hours of Planning plus 2 hours of drafting, a rough screen gives 2,200 planner-hours/week against only 320 nominal hours/week. Multiplying medians is not an expected-workload estimator, but the discrepancy is large enough to question the units, scope, staff counts, and whether "service" measures elapsed spans rather than exclusive staff effort. True means of heavy-tailed effort may worsen it. Investigate omitted staff, batching, shared case work, and multi-tasking; do not arbitrarily shrink effort or arrivals to match durations. If the inputs genuinely imply sustained overload, the baseline must accumulate backlog and the listed interventions may be insufficient.

For each resource pool, calculate expected assigned work, including rework, against integrated available capacity. A skill-constrained assignment calculation is preferable to a single aggregate utilization number; the two Simple-only planners cannot absorb arbitrary complex-case work.

**Arrivals.** Estimate attempted submissions and official submissions separately when preparation data become available. Fit a marked non-homogeneous count model, such as an overdispersed hourly/daily regression or Cox/cluster process:

\[
\lambda_g(t)=\lambda_0\,s_{month(t)}\,w_{weekday(t)}\,h_{hour(t)}
\exp\{x_g(t)^\top\beta+u_{architect(g),week(t)}+v_{district(g),t}\}.
\]

Here marks include type, district, architect, value, and requirements; group effects induce correlated rates. Normalize factors to reproduce total exposure-adjusted volume. Constrain or check peak-month rates against the reported 1.7 ratio and Monday/Wednesday against 2.2. Other months and weekdays remain to be estimated, not assumed equal. Fit joint marks, since independently sampling case type, architect, district, and review flags can create unrealistic applications. Model top architects' cluster sizes and within-week offsets, preserving their approximately 31% aggregate share. Check overdispersion, autocorrelation, and burst-size distributions; Poisson counts are a starting null model, not an established fact. Eighteen months provide weak evidence for trends or repeatable annual seasonality, so represent those as uncertain.

**Municipal effort and queue waiting.** Use paired activity-instance start/complete events and, ideally, pause/resume or time-accounting records to estimate active work. A start-to-complete interval that spans lunch, overnight, or work on other cases is not exclusive service effort. Estimate effort conditionally on activity, type, district, complexity, visit number, reviewer, and document quality. Consider lognormal, gamma, or mixture distributions with hierarchical partial pooling for sparse groups. Retain within-case correlations through complexity and document-quality effects.

For an illustrative lognormal fitted only to a median \(m\) and 90th percentile \(q\), \(\mu=\log m\), \(\sigma=[\log q-\log m]/1.28155\). This identifies one assumed family, not the distribution: compare alternative families and tails with the same quantiles, and require \(q>m>0\). Use point masses for zero-service receipt events and deterministic notice minima rather than fitting them with lognormals.

Without starts, completion-to-completion gaps mix upstream work, resource waiting, parallel branches, off-hours, external delays, and recording lag. They cannot identify a service/wait split. Combine credible effort observations, calendar constraints, targeted time studies, and uncertainty ranges. Calibration may constrain these ranges against observed queues, but multiple service/capacity combinations can fit the same cycle times.

In the simulation, municipal queue waiting is an **output** of enabled tasks competing for resources. Do not sample the supplied median waiting time and then also impose a resource queue. Decompose elapsed time into active effort, resource waiting, off-calendar waiting, batch hold, applicant/consultant response, statutory timers, and other documented gates. Parallel branch durations overlap and must not be summed to obtain case duration. Use the waiting summaries as calibration targets only after confirming their definitions.

**Routing, decisions, and rework.** Use mandatory rules first, then estimate unknown conditional transitions from conformance-aligned traces and case attributes. Fire=yes is sufficient for fire review; Fire=no is not sufficient evidence for a waiver when area is missing. Likewise, incomplete sensitive-district data do not establish environmental exemption. Link the missing attributes where possible, otherwise use explicit latent-eligibility scenarios. For D2, unknown prior violations mean the case is not automatically eligible.

Estimate rework source, destination, repeat count, elapsed response, and effort conditional on previous findings, case type, and document version. Manually code a stratified sample of free-text reasons to establish a usable taxonomy and its error rate. Fit a recurrent-event or state-transition model, with shared case difficulty allowing persistent rework. Estimate rejection, withdrawal, and appeal as competing outcomes where observed. Right-censor unresolved cases and delayed appeals. Do not calibrate all future routes to fixed historical variant shares: policies deliberately change those shares. Clarify whether the supplied variant groups are mutually exclusive, particularly "Inspection rework" and "Other".

**Calendars and travel.** Reconcile HR availability with actual work evidence, distinguishing absence, non-permit work, and underutilization. Obtain actual council weeks and holiday exceptions. For inspections, separate visit effort, origin/destination travel, appointment constraints, failed visits, and preparation time. Districts D3 and D5 need distinct travel distributions. Use route/appointment records to estimate savings from feasible bundles; their waiting costs emerge from the scheduler. Without coordinates or route data, use uncertain district-pair travel matrices, not fabricated precise routes.

**External delays and dependence.** Model applicant and consultant response with survival or accelerated-failure-time models, retaining right-censored outstanding requests. Include weekends, architect workload, repeat requests, and common consultant disruptions where supported. Fit related-case links using available architect/project/geographic identifiers and audit a sample for false links.

Objections are **latent**, not observed labels. A candidate notice model is

\[
T_{notice}=14\text{ calendar days}+E_{admin}+I_{objection}E_{resolution},
\]

with separate council/holiday gates and correlated objection states for genuinely related projects. A long notice can also reflect administration or timestamp conventions. Duration alone generally cannot identify both objection probability and objection severity. Use targeted notice-file review and interviews to bound them, then compare alternative latent models. D9's effectiveness remains scenario-based until intervention or pilot evidence exists.

**Role of PM4Py.** Use pandas for CSV ingestion, then `pm4py.format_dataframe` with the stated keys. Use PM4Py for variants, frequency and performance DFGs, process-tree parsing, Petri-net conversion, alignments/token replay, and case-arrival diagnostics. Lifecycle pairing must preserve repeated activity instances. Performance DFG edges from a completion-only log are descriptive adjacent-event gaps, not resource service or causal dependencies; flattened parallel reviews can create misleading adjacency. PM4Py supplies process-mining evidence and reference model artifacts. A separate simulation engine supplies capacity, calendars, policy rules, queues, and linked-case behavior.

Maintain an assumption register containing the rationale, evidence, uncertainty range, affected interventions, and owner responsible for resolving it. The initial assumptions are:

| Service times | Effort is positive, heterogeneous, and potentially heavy-tailed; zero-effort external receipt is a separate event. Case complexity induces correlated work across activities. The supplied service figures remain provisional until the workload inconsistency is resolved. Test alternative distributions and learning/fatigue effects if supported. |
| Routing | Required reviews follow legal/business attributes. Missing attributes remain unknown. The parallel block follows the tree provisionally; genuine prerequisite restrictions override it. Policy applicability is tied to an explicit effective date and grandfathering rule. |
| Resources/calendars | Staff cannot exceed their simultaneous capacity or qualifications. Closed time supplies no normal work capacity. Environmental reservations, Monday support, and council weeks are explicit. Ordinary desk work can resume next opening; field appointments must fit. Test unresolved fire FTE interpretation and hidden urgent demand. |
| Rework | Rework can recur and invalidate specific results. Difficulty persists across visits. Appeals and withdrawals are modeled explicitly. No arbitrary loop cap is used to create short tails; a computational safety limit flags unresolved cases and a model defect rather than recording completion. |
| Applicant/third-party response | Responses are outside municipal service capacity, may depend on shared architect/consultant workload, and can remain outstanding at run end. D1 adds effort and possibly delay before submission. Reduced missing documents is an uncertain treatment effect, not known from baseline traces. |
| Cross-case dependencies | Shared resources always create dependence. Additional architect, objection, and inspection links are modeled only with evidence or stated scenarios. Same architect/district is a useful candidate linkage, not proof of one shared legal outcome. |

Use multiple imputations or latent scenarios appropriate to the missingness mechanism. Excluded emergencies can still consume capacity. Compare plausible non-random missingness mechanisms. |

Baseline practice, proposed policy logic, and unknown policy effects must be separate configuration objects. Prefer targeted measurement over increasingly elaborate calibration when two explanations remain observationally indistinguishable.

# 4. Experiment matrix

All effect sizes below are **experimental hypotheses**, not estimates from the supplied summaries. Freeze a reconciled baseline and a scenario generator before comparing policies. Every policy comparison uses matched exogenous demand, case identities, common disruptions, and initial backlog. Cost and staffing are recorded for every arm.

|---|---|---|

Stress scenarios are separate conditional futures, not automatically equally likely forecasts.

# 5. Warm-up, replications, and uncertainty treatment

**Initialization and horizon.** The primary experiment is a terminating policy-launch study initialized from a real work-in-progress snapshot: case ages, current queues, partially completed work, pending external responses, document versions, scheduled appointments, and linked cases. Condition residual work and response times on what has already elapsed; do not restart every open case with a fresh unconditional duration. Represent uncertainty in undocumented initial state. Report inherited backlog and newly arriving cohorts separately. Do not discard the first months as warm-up when implementation effects on the existing backlog are part of the decision.

Observe 24 months of new application attempts/submissions, spanning two peak cycles. Continue ordinary arrivals and resource competition for at least another 12 months to follow those cohorts; stopping arrivals at month 24 would artificially accelerate their remaining work. Measure operating costs, utilization, and backlog over explicitly stated windows. Extend follow-up when important tail metrics remain unidentified. Keep unresolved cases and decisions beyond the horizon as censored observations, rather than dropping them or assigning the run-end date as completion.

For a separate long-run seasonal-capacity study, initialize from a credible snapshot or historical pre-run. Compare one, two, and three years of pre-run, using monthly phase-aligned backlog and age distributions across replications. Discard the pre-run only if these stabilize across annual cycles. There is no valid steady-state warm-up for an overloaded queue or a continually changing demand trend; analyze transient growth instead. The 18-month historical log cannot establish long-run annual stability by itself.

**Replications and random numbers.** Start with 40 independent paired replications per fixed parameter/scenario setting. Use a pilot to choose the final replication count, then add batches of 20 where needed. Example precision targets are a 95% interval half-width below two percentage points for an SLA difference and below the larger of two days or 5% of the baseline p90 for a p90 difference. Use tighter targets if competing policies are close. If a prespecified computational cap is reached, report the unresolved comparison. Avoid declaring a winner after repeatedly checking significance without a planned stopping procedure.

Within a replication, all policies receive the same underlying applicant attempts, case attributes, weather/consultant/objection shocks, and comparable work requirements. Use separate, stable random streams keyed by replication, case or group ID, activity, rework visit, and uncertainty source. A single sequential RNG is insufficient: when D2 removes an inspection, it would shift every subsequent draw. Policies should transform shared underlying worlds, not independently redraw them. Share latent shocks and potential response draws, while activating case-specific events only in the relevant state: changing the notice window can change exposure to objections. Do not force an objection on the same date for a case that is no longer under notice. Randomness for newly introduced tasks needs its own keys. Hold out fresh seeds for final confirmation after screening many policies.

**Three layers of uncertainty.**

1. **Simulation variability:** stochastic arrivals, work, responses, and common shocks conditional on parameters. Estimate paired policy differences at the replication level. For a mean difference, use the sample standard deviation of replication differences divided by the square root of the replication count, with a t interval when appropriate. For medians, quantiles, and fairness comparisons, use paired replication bootstrap intervals or an appropriate hierarchical bootstrap.
2. **Parameter uncertainty:** draw fitted rates, routing probabilities, work distributions, latent objection parameters, missing attributes, and policy effects from a posterior or a block bootstrap of the calibration data. As an initial design, use about 100 outer draws with sufficient inner replications determined by the pilot. Pair policies within every draw. Report uncertainty from parameters separately from Monte Carlo precision, and combine them only with a clearly identified inferential interpretation.
3. **Structural and forecast uncertainty:** compare alternative service/wait decompositions, review-overlap rules, dependence models, trend assumptions, and objection explanations. Show results by model/scenario. Do not average stress scenarios into a single probability of success without defensible scenario weights.

Bootstrap time blocks and linked groups to preserve temporal and architect/neighborhood dependence, rather than treating 31,200 cases as independent observations. With only 18 months, seasonal block resampling is limited; use fitted-model uncertainty and additional measurement plans rather than claiming a large effective sample for all effects. Keep interventions' causal effects distinct from ordinary input-estimation uncertainty: baseline association does not establish how much a document checker or early-warning process will help.

**Sensitivity and tails.** Screen inputs using a space-filling design and rank/regression-based sensitivity measures; investigate important inputs and interactions with global sensitivity methods where assumptions permit. Include service means/tail shape, unknown fire eligibility, fire capacity interpretation, objection incidence versus severity, architect correlation, travel/no-shows, legal closures, initial backlog, uptake, and omitted urgent work. Prioritize further data collection for uncertainties that change policy rankings.

Fit heavy tails using censored observations and compare lognormal, mixture, and, only when supported by enough data, threshold-tail alternatives. Do not winsorize long cases merely to obtain stable results. If an operational timeout or withdrawal rule exists, model it as a separate outcome; otherwise, continue or censor the case. Inspect the largest cases and report p90/p95, tail-exceedance probabilities, and restricted mean duration over a fixed horizon. Use p99 only when sample size and follow-up support it. If a survival curve never reaches the requested quantile, report it as not estimable or a lower bound. For competing outcomes, use outcome-specific cumulative incidence alongside time to any decision, rather than treating withdrawals as ordinary independent censoring.

# 6. Validation strategy

Validation has two separate questions: whether the implemented engine obeys its design, and whether that design adequately represents the municipality for the intended comparisons.

**Face validation and implementation verification.** Walk representative Simple, Commercial, and appealed Complex cases through the model with clerks, planners, inspectors, legal staff, and applicant representatives. Review actual calendar closures, document invalidation, batch release, urgent exceptions, and policy effective dates. In small deterministic scenarios, check:

- No required review is bypassed and drafting never starts before all applicable valid prerequisites.
- The statutory notice minimum holds, including holidays and council boundaries under the agreed rule.
- Concurrent work never exceeds qualified open capacity; environmental reservations and Monday support are respected.
- Rework consumes capacity, stale results cannot satisfy joins, and a partially completed task resumes correctly.
- Related objections affect all and only linked cases; inspection batch hold and travel savings are accounted for once.
- D2 handles EUR 50,000 exactly as ineligible, and unknown violation history does not produce a waiver.
- Flow accounting reconciles new cases, initial backlog, withdrawals, decisions, reopenings, and final active work, without counting a rework event as a new application.

These are meaningful engine checks, not evidence that uncertain input distributions are correct.

**Event-log replay validation.** First assess the reference tree against held-out observed traces using alignments or token replay, inspecting deviations rather than hiding them in an aggregate fitness score. Repeated completeness checks, missing rework labels, appeal paths, and arbitrary orderings of concurrent completions need explicit interpretation. Second, run a historical reconstruction using actual arrival times, available case attributes, staffing calendars, and initial backlog while allowing the simulator to produce queues and completions. Do not force recorded completion times into the engine and then claim their reproduction validates timing. A separate timestamp-driven diagnostic can locate model/calendar inconsistencies, but is not predictive validation.

**Distributional validation.** Compare distributions by type, district, architect size, calendar month, and rework status: case duration, work-in-progress age, initial versus final resolution, external response time, review counts, outcomes, weekly completions, and waiting before scarce pools. Compare empirical CDFs, quantile plots, and tail-exceedance rates with uncertainty bands, not just global averages. Check observed variant frequencies and DFGs while recognizing that multiple interleavings can represent the same parallel behavior. Where timestamps only support adjacent-event gaps, compare those explicitly labeled quantities, not invented queue waits.

**Resource-utilization validation.** Compare assigned effort and calendar availability against timesheets, rosters, appointment records, and staff observations. Report occupied permit hours divided by eligible open permit hours, plus absolute hours and calendar availability. Exclude holidays/non-permit reservations from that denominator, but report them separately so apparent utilization is interpretable. Completion counts alone do not identify utilization. Audit the major planner-capacity inconsistency before claiming fit.

**Bottleneck validation.** Check whether the model reproduces Monday completeness spikes, legal closure backlogs, environmental congestion, travel disadvantages in districts D3 and D5, and seasonal inspection queues. Inspect queue age, resource blocking, and critical-path contribution together: the activity with the most work is not necessarily the source of the longest case delay. Small diagnostic capacity perturbations should have plausible effects, including shifting congestion downstream. Compare such responses with historical absences, staff additions, or operational changes where usable, while accounting for confounding demand changes.

**Out-of-sample validation.** Use a chronological split, initially 12 months for fitting and six for validation, with rolling-origin checks where data volume permits. Reconstruct the opening backlog at each cutoff; do not leak future case outcomes into routing or residual-time estimates. Score the forecast of unresolved older cases as well as new arrivals, with censoring-aware metrics. The short holdout may not identify the Complex p95; disclose that limit. Stratified architect or district holdouts can test generalization but do not replace the chronological test.

Agree tolerances before calibration. Illustrative targets are monthly arrivals/throughput within approximately 10%, type medians within 10%, type p90 within 15–20%, effective utilization within five percentage points where independently measured, and no persistent bias in backlog trend or disadvantaged districts. Compare with historical sampling uncertainty rather than treating these as universal constants. A good aggregate fit does not compensate for wrong mechanisms or large subgroup errors. If the capacity/service inputs cannot be reconciled, label policy results exploratory.

After validation, run the twin in shadow mode and compare prospective predictions with reality. Use a bounded pilot for interventions with weak treatment evidence, especially D1, D2, D8, and D9. Batch, architect, and resource interactions make ordinary independent-case randomization problematic: use suitable cluster randomization or time-block designs with queue carryover considered. Version all inputs, assumptions, code, policies, and validation reports; recalibrate after detected drift rather than silently overwriting the reference baseline.

# 7. Decision criteria

Select from a Pareto set of feasible policies using prespecified objectives, quality constraints, affordability, and robustness. The following are proposed discussion thresholds, not existing municipal law or demonstrated results.

| Metric | Definition and proposed selection rule |
|---|---|
| Median and tail duration | By type, report median, p90, p95, and censored tail exceedance for both official and preparation-inclusive clocks. Seek roughly 10% median and 15% p90 improvement in targeted groups, with a paired 95% interval excluding no benefit for the primary metric. Use a noninferiority margin of at most 5% worsening in other types' p95. Report approval and rejection outcomes separately so quicker rejection cannot masquerade as service improvement. |
| SLA compliance | Illustrative submission-to-initial-decision SLAs: Simple 30, New residential 90, Commercial 120, Complex variance 240 calendar days. Confirm actual targets and any lawful stop-clock rules. Seek at least 90% compliance by type, or a pre-agreed staged improvement if baseline is far below that level. Also report total elapsed compliance without stop-clock exclusions and time to final resolution. |
| District/architect fairness | Show raw and case-mix/risk-standardized duration and SLA metrics for each district, top-20 versus other architects, small-volume applicants, and nonparticipants in slots/checkers. Require adequate precision to exclude more than 10% p90 worsening or a three-percentage-point SLA loss in a material subgroup. Report uncertain small groups explicitly rather than declaring fairness from a nonsignificant test. |
| Resources | Track eligible-capacity utilization, weekly overload, overtime, travel, idle periods, and workload concentration. A 70–85% average planning range can leave useful resilience, but is pool-specific. Sustained utilization above 90% for four weeks, or growing queues during closures, triggers further capacity analysis. Low utilization alone is not a policy failure. |
| Rework and quality | Track missing-document loops, repeat inspections, legal returns, appeals, overturned decisions, missed serious defects, and applicant withdrawals. Initially allow no more than a one-percentage-point increase in rework, subject to severity. Require zero simulated violations of mandatory reviews/notice rules. For D2, use audited defect outcomes and a safety margin approved before adoption; efficiency alone cannot establish waiver safety. |
| Backlog and recovery | Report total and age-banded active cases, cases beyond SLA, expected remaining work, and backlog by type. Require no persistent year-on-year increase at comparable seasonal phases under forecast demand; seek at least 20% reduction in over-SLA backlog for a backlog-focused policy. Under stress, compare peak backlog and time to recover after the shock, even if absolute stability is impossible. |
| Cost and burden | Include salaries, temporary recruitment/onboarding, checker development/support, triage/alert effort, audit inspections, travel, applicant preparation and waiting, and consultant burden. Compare annual budget, cost per completed case, and incremental cost per SLA breach avoided. Do not monetize every calendar day as a full day of labor. Where prices are unknown, report break-even costs. |
| Robustness | A preferred policy should satisfy mandatory constraints in every tested credible configuration and retain worthwhile benefits across most plausible parameter draws. For example, seek at least 80% probability of positive net benefit under a justified posterior, while displaying results separately for unweighted stress scenarios. Prefer low worst-case regret when rankings are sensitive. |

Use uncertainty bounds in noninferiority and safety decisions; lack of statistical significance is not proof of no harm. Account for multiple comparisons during screening and confirm finalists with fresh replications. Also check that benefits remain after implementation delays and that applicants without large architects can access them.

A sensible decision sequence is to eliminate unlawful or unaffordable designs, reject policies with unacceptable quality/fairness risks, compare the remaining cost–timeliness–backlog trade-offs, and pilot the options whose ranking depends on uncertain treatment effects. D10 is a candidate, not a presumed winner. If mandatory workload exceeds feasible staffing in every plausible model, report the additional capacity or demand-side changes needed instead of claiming that queue reordering solves overload.

def to_utc(series: pd.Series) -> pd.Series:
    # For this excerpt, naive times are provisionally local municipal time.
    # Resolve source semantics and ambiguous DST timestamps before production.
    dt = pd.to_datetime(series, errors="raise")
    if dt.dt.tz is None:

            LOCAL_TZ, ambiguous="raise", nonexistent="raise"
        )
    return dt.dt.tz_convert("UTC")

def add_timing_columns(log: pd.DataFrame) -> pd.DataFrame:
    out = log.sort_values([CASE, TS], kind="stable").copy()
    out["adjacent_event_gap_s"] = (
        out.groupby(CASE, sort=False)[TS].diff().dt.total_seconds()
    )
    # Unknown values stay unknown. None of these is inferred from a DFG gap.
    out["service_elapsed_s"] = np.nan
    out["service_work_s"] = np.nan
    out["queue_wait_elapsed_s"] = np.nan

    # Optional columns must come from semantically verified interval data.
    # A generic point-event timestamp is NOT assumed to be a completion.
    if {"start_timestamp", "complete_timestamp"}.issubset(out.columns):
        start = to_utc(out["start_timestamp"])
        complete = to_utc(out["complete_timestamp"])
        out["service_elapsed_s"] = (complete - start).dt.total_seconds()
        # Includes pauses unless separate work intervals are available.
        if "enabled_timestamp" in out:
            enabled = to_utc(out["enabled_timestamp"])
            out["queue_wait_elapsed_s"] = (start - enabled).dt.total_seconds()
            # Enabled means ready for a municipal resource, after any
            # document/notice/prerequisite gates. Includes closed hours.
    if "active_work_seconds" in out:
        out["service_work_s"] = pd.to_numeric(
            out["active_work_seconds"], errors="raise"
        )
    for col in ("service_elapsed_s", "service_work_s", "queue_wait_elapsed_s"):
        if (out[col].dropna() < 0).any():
            raise ValueError(f"Invalid timestamp/work semantics in {col}")
    return out

@dataclass(frozen=True)
class Streams:
    master: int
    parameter_draw: int
    scenario: str
    replication: int

    def rng(self, source: str, *keys: Any) -> np.random.Generator:
        # Stable entity-specific streams; deliberately excludes policy name.
        # A fresh call with identical keys reproduces the same draw stream.
        payload = repr((self.master, self.parameter_draw, self.scenario,
                        self.replication, source, keys)).encode("utf-8")
        seed = int.from_bytes(
            hashlib.blake2b(payload, digest_size=16).digest(), "little"
        )
        return np.random.default_rng(seed)

class ArrivalGenerator:
    def __init__(self, theta: dict, scenario: dict):
        self.theta, self.scenario = theta, scenario

    def generate(self, start, end, streams: Streams) -> list[dict]:
        """One possible marked Cox arrival model for underlying attempts.

        arrival_cells is a calibrated provider of disjoint time/mark cells.
        Each cell supplies id, start, end, architect_id, district, week_id,
        and an integrated mean reflecting season, weekday, and hour.
        Means are normalized outside this function, including the top-20
        marginal share. Small time cells can represent narrow bursts;
        a compound-cluster generator is a structural alternative.
        """
        attempts = []
        cells = self.theta["arrival_cells"](start, end, self.scenario)
        for cell in cells:
            sigma = self.theta["architect_week_log_sd"]
            shock = streams.rng(
                "architect_week", cell["architect_id"], cell["week_id"]
            ).lognormal(-0.5 * sigma**2, sigma)
            count = streams.rng("arrival_count", cell["id"]).poisson(
                cell["mean"] * shock
            )
            for k in range(count):
                cid = f"{cell['id']}:{k}"
                u = streams.rng("arrival_time", cid).uniform()
                when = cell["start"] + u * (cell["end"] - cell["start"])
                # Conditional sampler preserves joint attributes and unknowns.
                # Verified Boolean fields are Python bool, not NaN values.
                marks = self.theta["sample_marks"](
                    cell, streams.rng("marks", cid)
                )
                attempts.append({
                    **marks, "id": cid, "attempt_time": when,
                    "architect_id": cell["architect_id"],
                    "district": cell["district"],
                })
        return sorted(attempts, key=lambda c: (c["attempt_time"], c["id"]))


class Routing:
    def requirements(self, case: dict, policy: Policy,
                     streams: Streams) -> dict[str, bool]:
        # Resolved fields below come from verified data or the explicitly
        # selected latent-eligibility scenario; they are not inferred from
        # absence of a review event. The fire threshold is a model input.
        fire = (case["requires_fire"] == "yes"
                or case["resolved_area_exceeds_fire_threshold"])
        environment = (case["requires_environment"] == "yes"
                       or case["resolved_sensitive_district"])
        notice = (case["case_type"] == "Complex variance"
                  or case["requires_public_notice"] == "yes"
                  or case["resolved_other_notice_requirement"])
        eligible = (
            case["case_type"] == "Simple renovation"
            and case["application_value"] < 50_000
            and case.get("known_no_prior_violations") is True
        )
        audited = (
            streams.rng("inspection_audit", case["id"]).uniform()
            < policy.audit_fraction
        )
        waived = policy.inspection_waiver and eligible and not audited
        return {
            "Planning review": True,
            "Fire-safety review": bool(fire),
            "Environmental review": bool(environment),
            "Public-notice period": bool(notice),
            "Site inspection": not waived,
            "Legal check": bool(case["resolved_legal_requirement"]),
        }

    def drafting_ready(self, required: dict, state: dict) -> bool:
        prerequisites = (
            "Planning review", "Fire-safety review", "Environmental review",
            "Public-notice period", "Site inspection",
        )
        # Event handlers invalidate only results affected by a revision.
        return all(state["result_valid"].get(a, False)
                   for a in prerequisites if required[a])

    def after_finding(self, case, activity, visit, finding, streams):
        """Return affected rework tasks, external requests, and invalidations.

        Include planning/legal/inspection findings and appeal reopening;
        condition on case difficulty and previous findings. This is a
        calibrated transition model, not an unconditional geometric loop.

class LinkedCaseDES:
    def __init__(self, theta, scenario, policy, streams, world):
        self.theta, self.scenario = theta, scenario
        self.policy, self.streams = policy, streams
        self.world = copy.deepcopy(world)  # no cross-policy state leakage
        self.state = copy.deepcopy(self.world["initial_state"])
        self.state.setdefault("cases", {})
        self.state.setdefault("groups", self.world["linked_groups"])
        self.state.setdefault("trips", {})
        self.resources = CalendarResources(theta["calendars"], policy, scenario)
        self.routing = Routing()
        self.events = []
        self.sequence = itertools.count()
        self.trace = []

    def schedule(self, when, kind, payload):
        # Priority rules belong in dispatch; counter breaks equal-time ties.
        heapq.heappush(self.events, (when, next(self.sequence), kind, payload))

    def initialize(self, start, end):
        for case in self.world["attempts"]:
            self.schedule(case["attempt_time"], "application_attempt", case)
        # initial_events include residual in-flight tasks, pending responses,
        # reservations, and initial queue dispatch; all are >= run start.
        for event in self.world["initial_events"]:
            self.schedule(*event)
        for event in self.world["shared_events"]:
            self.schedule(*event)  # linked objections, weather, closures, etc.
        self.schedule(start, "dispatch", None)

    def handle(self, now, kind, payload):
        """Implement attempt -> preparation -> official submission, task
        enabling, dispatch, work completion, external responses, group
        shocks, batch deadlines, findings, decisions, and appeals.

        D1/D7 transform attempt timing/effort; preserve the attempt ID and
        both clocks. D8/D9 create work in specified real pools. D5 schedules
        early screening and later confirmation. Shared shocks update all
        affected cases in an applicable state; notice exposure is dynamic. Resource releases/openings trigger dispatch.
        Effort draws use keys (case ID, activity, visit); common latent
        difficulty and group shocks are shared across affected tasks.

        Emit lifecycle timestamps, effort intervals, queue/batch reasons,
        resource IDs, links, document versions, waivers, and outcomes.
        """
        raise NotImplementedError("Implement business event handlers")

    def run(self, start, cohort_end, end):
        self.initialize(start, end)
        while self.events and self.events[0][0] <= end:
            now, _, kind, payload = heapq.heappop(self.events)
            self.handle(now, kind, payload)
        # summarize must retain right-censoring, distinguish cohorts from
        # inherited backlog, and include raw effort/cost/fairness measures.
        return self.theta["summarize"](
            self.trace, self.state, start, cohort_end, end
        )


def make_world(theta, scenario, streams, start, end):
    attempts = ArrivalGenerator(theta, scenario).generate(start, end, streams)
    initial_state, initial_events = theta["initial_snapshot"](start, streams)
    linked_groups = theta["link_cases"](attempts, initial_state, streams)
    shared_events = theta["external_paths"](
        start, end, linked_groups, scenario, streams
    )
    return dict(
        attempts=attempts, initial_state=initial_state,
        initial_events=initial_events, linked_groups=linked_groups,
        shared_events=shared_events,
    )


def run_experiments(parameter_draws, scenarios, policies, start, cohort_end,
                    followup_end, replications=40, master_seed=734921):
    """Nested uncertainty design; paired worlds within each setting.

    Generate arrivals through followup_end, not just cohort_end, so late
    cohort cases still compete with continuing demand during follow-up.
    No PM4Py playout is used as a resource-constrained simulation engine.
    """
    records = []
    for draw_id, theta in enumerate(parameter_draws):
        for scenario in scenarios:
            for rep in range(replications):
                streams = Streams(master_seed, draw_id, scenario["name"], rep)
                world = make_world(theta, scenario, streams, start, followup_end)
                for policy in policies:
                    engine = LinkedCaseDES(theta, scenario, policy, streams, world)
                    metrics = engine.run(start, cohort_end, followup_end)
                    records.append({
                        "draw": draw_id, "scenario": scenario["name"],
                        "replication": rep, "policy": policy.name, **metrics,
                    })
    return pd.DataFrame(records)
