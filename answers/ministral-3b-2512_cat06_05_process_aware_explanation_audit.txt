### **2. Process-model consistency checks**
**Validation Suite:**
1. **Prefix-Time Availability**
   - For each feature, verify it is computable *only* from events  `t0`. Example: `appeal_seen_anywhere`  check if `Settlement Decision Recorded` (with appeal) occurs before `t0`.
   - *Limitation*: Prefix-only checks cannot rule out *future-possible* events (e.g., `queue_length_at_t0` if `t0` is in queue).

2. **Activity-Order Feasibility**
   - Use a **declarative graph** (DFG) to enforce normative rules:
     - `Coverage Check Completed`  `Damage Assessment Completed` (only if no appeal/deny path).
     - `Appeal`  `Settlement Decision Recorded` (must occur *after* `t0`).
     - `Claim Closed`  `Damage Assessment Completed` (only if no appeal/partial).
   - *Limitation*: DFGs cannot enforce *all* temporal constraints (e.g., same-timestamp ambiguity).

3. **Same-Timestamp Ambiguity**
   - For events with identical timestamps, enforce a **sequence index** or **timezone alignment** to resolve ordering. Example: `Claim Closed` and `Damage Assessment Completed` must be ordered by ingestion sequence.

4. **Complete-Trace vs. Prefix Checks**
   - Audit features like `full_trace_variant_id` to confirm they use *only* prefix events (e.g., `Damage Assessment Completed` before `t0`).

5. **Impossible vs. Future-Possible Activities**
   - Classify events at `t0` as:
     - **Enabled**: Possible now (e.g., `Damage Assessment Completed` if no appeal).
     - **Future-Possible**: Possible later (e.g., `Appeal` if `Settlement Decision Recorded` is pending).
     - **Impossible**: Never possible (e.g., `Claim Closed` if `Settlement Decision Recorded` is pending).

6. **Repeated `Settlement Decision Recorded`**
   - Validate that appeals *only* trigger a second `Settlement Decision Recorded` (not arbitrary rework).

**Tools:**
- **Prefix Footprint Analysis**: Compare feature values at `t0` vs. full trace.
- **Temporal Graph Traversal**: Simulate paths to identify forbidden sequences.
