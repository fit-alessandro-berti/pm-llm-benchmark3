## 1. Control-Objective Decomposition
FEP-1's core objective is to **prevent a single actor from unilaterally initiating and authorizing a fraudulent or erroneous payment**. Decomposed sub-objectives and threat scenarios:

| **Objective/Threat**                     | **AV-2** | **MG-4** | **RA-7** | **ED-1** | **Gaps** |
|------------------------------------------|----------|----------|----------|----------|----------|
| **Prevent unauthorized initiation**      | No       | No       | No       | No       | Requires segregation of duties (SoD) at preparation. |
| **Prevent unilateral authorization**     | No       | Yes (if independent and pre-release) | No | Conditional (if ED-1 conditions met) | Post-release manager approval is detective, not preventive. |
| **Detect duplicate/fraudulent payments** | Yes (pre-release) | No | Yes (retrospective) | No | AV-2 does not validate receipt of goods/services. |
| **Prevent collusion**                    | No       | Partial (if manager is truly independent) | No | No | AV-2 and MG-4 cannot detect collusion between preparer and manager. |
| **Ensure recoverability**                | No       | No       | Yes (if within recall window) | No | RA-7 is only corrective if recall is possible. |
| **Validate bank-account legitimacy**    | Yes (ownership, recent changes) | No | No | No | AV-2 does not verify account control at release time. |
| **Emergency override safety**           | Yes (if operational) | Yes (if pre-settlement) | Yes (if timely) | Yes (if all ED-1 conditions met) | ED-1 is a controlled exception, not a replacement for SoD. |

**Key Insight**: No single control addresses all objectives. AV-2 is strong for technical validation but weak for commercial legitimacy. MG-4 is preventive only if pre-release and independent. RA-7 is purely detective/corrective. ED-1 is a **temporary suspension** of FEP-1 under strict conditions.

## 2. Equivalence and Sufficiency Test
A compensating control package is evaluated against **7 dimensions**:

1. **Timing**:
   - Preventive: Before `Release_Payment` (e.g., MG-4 pre-release).
   - Detective: After `Release_Payment` but before settlement (e.g., MG-4 post-release).
   - Corrective: After settlement but within recall window (RA-7).

2. **Independence**:
   - The compensating actor (e.g., manager) must not be the preparer/releaser and must lack conflicts of interest (e.g., m09 supervising u23).

3. **Coverage**:
   - Does the control address the specific risk? (e.g., AV-2 does not cover receipt validation).

4. **Overrideability**:
   - Can the control be bypassed? (e.g., AV-2 warnings can be overridden by u23 in AP-202).

5. **Recoverability**:
   - Can losses be reversed? (e.g., RA-7 is ineffective if recall window is missed).

6. **Evidence Quality**:
   - Is the control’s output auditable? (e.g., unsigned manual checklists in AP-208).

7. **Collusion Resistance**:
   - Are there checks for coordinated fraud? (e.g., u12/u13 shared workstation in AP-204/AP-209).

**Equivalence Standards**:
- **Fully Equivalent**: Meets all FEP-1 objectives (e.g., distinct users + MG-4 pre-release + AV-2 pass).
- **Partially Equivalent**: Addresses some objectives but leaves gaps (e.g., MG-4 post-release + RA-7 within recall window).
- **Merely Mitigating**: Reduces but does not eliminate risk (e.g., AV-2 pass alone).
- **Ineffective**: Fails to address the core objective (e.g., same-user release with no compensating controls).

**Why "Same Expected Loss" is Insufficient**:
- **Qualitative risks** (e.g., reputational damage, regulatory penalties) are not captured by loss amounts.
- **Collusion** may be undetectable even with low expected loss.
- **Control timing** matters: A post-settlement detection does not prevent loss.

## 4. Preventive–Detective–Corrective Comparison

| **Control**               | **Preventive** | **Detective** | **Corrective** | **Semantics** |
|---------------------------|----------------|---------------|----------------|---------------|
| AV-2 (Automated Validation) | Yes (blocks release) | No | No | Preventive if it stops the payment (e.g., AP-205). |
| MG-4 (Manager Approval)   | Yes (if pre-release) | Yes (if post-release pre-settlement) | No | **Hybrid**: Pre-release = preventive; post-release pre-settlement = detective (can still block settlement). |
| RA-7 (Retrospective Audit) | No | Yes | Yes (if within recall window) | Detective by default; corrective only if recall is possible. |
| ED-1 (Emergency Permission) | Conditional | No | No | Preventive *only if all conditions are met* (e.g., AP-203, AP-207). |

**Key Distinction**:
- A manager approval **after `Release_Payment` but before `Bank_Settlement`** is **detective** (can still prevent loss) but not preventive (the payment was already released).
- A manager approval **after `Bank_Settlement`** is purely detective (no corrective capacity).

## 6. Evidence and Monitoring Recommendations

### **Monitoring Rules (Alerts, Not Proof)**
| **Metric** | **Threshold** | **Alert Type** | **Rationale** |
|------------|---------------|----------------|---------------|
| Same-user rate (Prepare_Payment + Release_Payment) | >0% | High | Direct FEP-1 violation. |

| Control outages (AV-2 unavailable) | Any | Critical | No automated validation. |

### **Evidence Collection**
1. **Emergency Token Logs**: Verify token activation time relative to `Prepare_Payment`.
2. **Manager Approval Evidence**: Signed checklists, system logs of review actions.
3. **AV-2 Override Justifications**: Document reasons for overrides (e.g., AP-202).
4. **Bank Account Validation**: Proof of ownership at release time (missing in AP-208).
5. **Workstation Logs**: Track shared usage patterns (u12/u13 in AP-204/AP-209).

**Alert vs. Proof**:
- An alert (e.g., same-user rate >0) **flags a risk** but does not prove misconduct.
- Proof requires **corroborating evidence** (e.g., fabricated receipts in AP-204).
