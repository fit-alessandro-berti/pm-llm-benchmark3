# Object-Centric Execution Clustering: Eight Order Executions

## 1. Equivalence Design Space

### 1.1 Activity-Sequence Equivalence (ASE)

**Definition:** Two executions are ASE-equivalent if their event streams are identical in activity label (e.g., "Create Order", "Pack Package") and that all object roles (lead, referenced, created) preserve type cardinality structure. Local identifiers are immaterial. Event order is preserved as a total order.

**Invariants preserved:**
- Activity label sequence
- Object type cardinalities per event (e.g., "Pack Package" always involves exactly one Package)
- Count of events

**Information discarded:**
- Local identifier assignments (O1 vs. O2)
- Qualifier annotations (e.g., `removed_before_dispatch`)
- External-object flags (EXT-)
- Item-identifier order within a single event
- Semantic interpretation of object roles

**Properties:** Reflexive, symmetric, transitive. Equivalence is preserved under concurrent events if both orderings produce the same label stream.

---

### 1.2 Typed-Structural Equivalence (TSE)

**Definition:** Two executions are TSE-equivalent if there exists a renaming isomorphism between their object-centric event graphs such that:
- Event labels and object types match
- The bipartite incidence structure (events  objects) is identical
- Cardinalities of object creation and participation are preserved
- Object identifiers (including EXT- flags) are preserved modulo consistent renaming

**Invariants preserved:**
- Activity sequence
- Object multiplicities per order (e.g., 2 items in O1)
- External references (presence of EXT- objects)
- Structural references (which items go in which packages)

**Information discarded:**
- Qualifier annotations
- Order of Add Item events (symmetric under reordering)
- Physical identifier names
- Semantic weight of external references

**Properties:** Reflexive (every execution is isomorphic to itself), symmetric (if X  Y then Y  X), and transitive. Handles concurrent events by treating events within the same timestamp as an unordered multiset.

---

### 1.3 Business-Semantic Equivalence (BSE)

**Definition:** Two executions are BSE-equivalent if they exhibit the same **lifecycle motif** with respect to:
- Order-item consolidation (single or split packages)
- Delivery strategy (consolidated vs. split deliveries)
- Financial settlement pattern (single vs. partial/multi-payment)
- External object involvement (isolated vs. cross-order sharing)
- Item mutation (substitution, return, repack) indicated by O2O qualifiers

The canonical signature is a tuple:

```
(package_count, delivery_count, payment_count, external_indicator, mutation_present)
```

A motif defines a reusable operational pattern; two executions with identical motifs are BSE-equivalent even if their local object counts differ.

**Invariants preserved:**
- Structural topology (items  packages  deliveries)
- Payment settlement cardinality and sequencing
- Cross-order sharing flags
- Item mutation presence

**Information discarded:**
- Specific item identifiers (I11 vs. I21)
- Specific invoice numbers
- Absolute values (only cardinalities matter)

**Properties:** Reflexive and transitive. Symmetric iff external-object involvement is symmetric (X5 shares externally but EXT-OA does not reciprocate, so X5  its external peer under strict semantics; however, "shares an external object" is symmetric as a property).

---

### 1.4 Qualification-Aware Equivalence (QAE) — Optional Fourth Relation

**Definition:** Refinement of BSE that distinguishes executions by their O2O qualifiers. Two executions are QAE-equivalent iff their BSE motifs are identical AND their O2O qualifier patterns match.

Qualifier patterns include:
- `removed_before_dispatch` (substitution)
- `partially_settles` + `completes_settlement` (staged payment)
- `replaces` (return and repack)

This is the most conservative equivalence that respects the narrative recorded in the data.

---

## 2. Canonical Signatures

I adopt **Business-Semantic Equivalence** as the preferred relation because it:
- respects process variability (e.g., split deliveries are operationally distinct from consolidated ones)
- is actionable (e.g., split deliveries trigger different logistics workflows)
- tolerates benign identifier renaming
- compresses identical motifs across different local naming schemes

### Signature Scheme

```python
def canonical_signature(execution: List[Event], lead_type="Order") -> tuple:
    """
    Returns a motif signature invariant to identifier renaming.
    
    Signature: (
        package_count: int,          # distinct packs created
        delivery_count: int,         # distinct deliveries created
        payment_count: int,          # distinct payments recorded
        has_external_objects: bool,  # any EXT- prefixed object
        mutation_present: bool,      # qualifiers indicate item mutation
        is_split_delivery: bool,     # packages distributed across deliveries
        invoice_count: int,          # distinct invoices
    )
    """
    packages = set()
    deliveries = set()
    payments = set()
    invoices = set()
    has_ext = False
    mutation = False
    pkg_to_delivs = {}  # package -> set of delivery IDs
    
    for event in execution:
        if event.activity == "Pack Package":
            pkg_id = event.objects["Package"][0]
            packages.add(pkg_id)
            pkg_to_delivs[pkg_id] = set()
        
        elif event.activity == "Dispatch":
            deliv_id = event.objects["Delivery"][0]
            deliveries.add(deliv_id)
            for pkg_id in event.objects.get("Package", []):
                if pkg_id in pkg_to_delivs:
                    pkg_to_delivs[pkg_id].add(deliv_id)
        
        elif event.activity == "Record Payment":
            payments.add(event.objects["Payment"][0])
        
        elif event.activity == "Issue Invoice":
            invoices.add(event.objects["Invoice"][0])
        
        # Check for external objects
        for objs in event.objects.values():
            if any(str(o).startswith("EXT") for o in objs):
                has_ext = True
        
        # Check for mutation qualifiers in O2O metadata
        if hasattr(event, "o2o_qualifiers"):
            if any("removed_before_dispatch" in str(q) or 
                   "replaces" in str(q) 
                   for q in event.o2o_qualifiers):
                mutation = True
    
    # is_split_delivery:  package distributed across 2 deliveries
    is_split = any(len(delivs) > 1 for delivs in pkg_to_delivs.values())
    
    return (
        len(packages),
        len(deliveries),
        len(payments),
        has_ext,
        mutation,
        is_split,
        len(invoices),
    )
```

**Pseudocode validation:**
- X1: (1, 1, 1, False, False, False, 1)  "standard"
- X3: (2, 1, 1, False, False, False, 1)  "split-pack-consolidated-delivery"
- X4: (2, 2, 2, False, False, True, 1)  "split-pack-split-delivery"
- X5: (1, 1, 1, **True**, False, False, 1)  "cross-order-pack"
- X7: (1, 1, 1, False, **True**, False, 1)  "substitution"
- X8: (2, 2, 1, False, **True**, False, 1)  "return-repack"

## 4. Cluster Interpretations

### **S1: Standard (X1, X2)**
- **Signature:** (1,1,1,F,F,F,1)
- **Behavior:** Single item set packed into one package, dispatched as one delivery, invoiced and paid in full without external involvement.
- **Operational profile:** Simplest, lowest-friction path; suitable for homogeneous shipments.
- **Risks:** None distinctive. Opportunities: automation, bulk pricing.
- **Flattening failure:** Flattened to "Order  Items  Invoice  Payment" obscures that all items move together.
- **Stability:** Highly stable; no qualifiers or external references to reinterpret.

---

### **S2: Split-pack-consolidated (X3)**
- **Signature:** (2,1,1,F,F,F,1)
- **Behavior:** Multiple items packed separately but dispatched in one consolidated shipment. Invoicing and payment unified.
- **Operational profile:** Deferred consolidation; reduces handling before final dispatch; typical for multi-warehouse fulfillment or quality-check workflows.
- **Risks:** Partial shipment visible in packing stage but opaque at dispatch. Opportunity: analytics on pack-to-dispatch latency.
- **Flattening failure:** Would lose the intermediate packing step; looks identical to single-pack on flat logs.
- **Stability:** Stable unless delivery system interprets "multiple packages in one shipment" ambiguously.

---

### **S3: Split-pack-split-delivery (X4)**
- **Signature:** (2,2,2,F,F,T,1)
- **Behavior:** Each package is dispatched separately; each dispatch may have separate financial treatment. Partial payment recorded (two Payment objects).
- **Operational profile:** Asynchronous fulfillment; typical when items are sourced from different locations or subject to separate SLAs. Partial payment suggests staged invoicing or backorder reconciliation.
- **Risks:** Order completion ambiguity; financial reconciliation complexity. Opportunity: per-item SLA tracking.
- **Flattening failure:** Collapses the temporal and logistical separation of deliveries.
- **Stability:** Vulnerable to identifier collisions if payment amounts are not recorded; currently stable.

---

### **S4: Cross-order-pack (X5)**
- **Signature:** (1,1,1,T,F,F,1)
- **Behavior:** One package contains items from both the lead order (O5) and an external order (EXT-OA). External order is not invoiced in this trace.
- **Operational profile:** Consolidation across administrative order boundaries; typical in multi-tenant systems or order-pooling logistics.
- **Risks:** Billing ambiguity (who pays for the shared package?); lifecycle dependency on external order. Opportunity: detect shared-shipment opportunities.
- **Flattening failure:** Order-level isolation assumptions fail; package cannot be attributed to a single order.
- **Stability:** Brittle; assumes EXT-OA is defined and reachable. Repair: either allocate package cost or exclude EXT- objects.

---

### **S5: Cross-order-invoice (X6)**
- **Signature:** (1,1,1,T,F,F,1)
- **Behavior:** Logistics are isolated to the lead order; however, the invoice is issued jointly to lead and external order. Payment settles without explicit allocation.
- **Operational profile:** Consolidated billing (e.g., corporate account, group buy); typical in B2B or subscription contexts.
- **Risks:** Financial settlement ambiguity (which order paid which fraction?). Opportunity: consolidated receivables.
- **Flattening failure:** Cannot reconstruct order-level financials without cross-reference table.
- **Stability:** Moderately stable if EXT-OB is a valid order reference; requires external reconciliation metadata.

---

### **S6: Item-substitution (X7)**
- **Signature:** (1,1,1,F,T,F,1)
- **Behavior:** Initial packing includes two items; a qualifier (removed_before_dispatch) indicates one item was swapped before dispatch. Final shipment contains the replacement (I72).
- **Operational profile:** Quality or inventory correction; common in systems where pre-dispatch inspection allows late substitution.
- **Risks:** Invoice correctness (does V71 reflect original or final contents?); traceability of removed item. Opportunity: anomaly detection on substitution rate.
- **Flattening failure:** Removed item cannot be traced; appears as an inconsistency between Pack and Dispatch.
- **Stability:** Depends on O2O qualifier preservation; if qualifiers are lost, looks identical to S1.

---

### **S7: Return-and-repack (X8)**
- **Signature:** (2,2,1,F,T,F,1)
- **Behavior:** Initial dispatch is followed by return of one item, inspection, and re-packing into a new package dispatched separately. Single invoice and payment cover both packages.
- **Operational profile:** Post-dispatch correction (e.g., customer return, damage in transit, wrong item). Two distinct logistics legs; unified financial closure.
- **Risks:** Split order completion (invoice issued before second dispatch); return causality. Opportunity: return-rate root-cause analysis.
- **Flattening failure:** Sequential package/delivery structure is essential; flattened logs may not preserve return  repack causality.
- **Stability:** Depends on return and inspect activities; if those are missing, collapses to S3. Stable under current schema.

## 5. Borderline Cases

### X1 vs. X2
- **ASE:** Identical (both label sequences are identical).
- **TSE:** Isomorphic under renaming O1O2, I11I21, etc.; Add Item order differs locally but has no semantic consequence.
- **BSE:** Identical signatures  **same cluster (S1)**.
- **Why they differ under QAE:** They do not; no qualifiers differ.
- **Defensible split:** If identifier order (I11 before I12 vs. I22 before I21) were treated as a processing order (e.g., warehouse pick sequence), one could cluster them separately. This is **not** recommended unless pick sequence affects downstream behavior (e.g., inventory depletion order).

### X1 vs. X5
- **ASE:** Identical up to external-object renaming (EXT-  O1, EXT-IA  I11 is not a valid renaming).
- **TSE:** NOT isomorphic; X5 has one external object (EXT-OA) and one external item (EXT-IA) in the package; X1 has none.
- **BSE:** Different signatures: X1 = (1,1,1,**F**,F,F,1), X5 = (1,1,1,**T**,F,F,1).
- **Why they differ:** X5 introduces external-order logistics coupling. X1 is purely isolated.
- **Defensible equivalence:** If cross-order consolidation is considered an implementation detail (i.e., the order payload is the same), one could ignore the EXT- flag and treat them as S1-equivalent. **Not recommended** because the presence of an external object signals architectural shared state.

### X1 vs. X6
- **ASE:** Identical.
- **TSE:** NOT isomorphic; X6 has EXT-OB in the Invoice event; X1 does not.
- **BSE:** Different signatures: X1 = (1,1,1,**F**,F,F,1), X6 = (1,1,1,**T**,F,F,1).
- **Why they differ:** X6's external involvement is financial, not logistical. Operationally, the order fulfills in isolation.
- **Defensible equivalence:** If one argues that cross-order billing is purely financial bookkeeping and does not affect fulfillment operations, X1 and X6 could be clustered as operationally equivalent (but financially shared). A **supply-chain view** would cluster them together; an **accounts-receivable view** would separate them.

### X1 vs. X7
- **ASE:** Identical (Dispatch references Package, not Item; the qualifier is metadata).
- **TSE:** Isomorphic (both have 1 package, 1 delivery, etc.) **iff qualifiers are not part of the type structure**. If O2O qualifiers are part of the signature, NOT isomorphic.
- **BSE:** Different signatures: X1 = (1,1,1,F,**F**,F,1), X7 = (1,1,1,F,**T**,F,1).
- **Why they differ:** X7 has a mutation (item substitution); X1 does not.
- **Defensible disagreement:** Under a purely event-label equivalence (ignoring metadata), X1  X7. Under a metadata-aware equivalence, they are distinct. **X7 is the borderline case where activity labels hide a semantic difference.** This is a key argument for why structure alone is insufficient.

### X3 vs. X4
- **ASE:** Different; X3 has a single Dispatch with multiple packages; X4 has two Dispatch events.
- **TSE:** NOT isomorphic (one vs. two Dispatch events).
- **BSE:** Different signatures: X3 = (2,**1**,1,F,F,**F**,1), X4 = (2,**2**,**2**,F,F,**T**,1).
- **Why they differ:** X4 splits delivery and payment; X3 consolidates both. Operationally distinct SLAs and billing models.
- **Defensible equivalence:** If split vs. consolidated delivery is not operationally significant (e.g., logistics system sends both in one truck anyway), one could treat them as equivalent at a higher abstraction. **Not defensible** in most supply-chain contexts.

### X4 vs. X8
- **ASE:** Different; X8 has Return Item and Inspect Return; X4 does not.
- **TSE:** NOT isomorphic.
- **BSE:** Different signatures: X4 = (2,2,**2**,F,F,T,1), X8 = (2,2,**1**,F,T,F,1). X8 also has Return and Inspect events.
- **Why they differ:** X8 is triggered by a post-dispatch event (return); X4 is planned asynchronous fulfillment. X8 has 1 payment (unified); X4 has 2 payments (possibly pro-rated). X8 has mutation; X4 does not.
- **Defensible equivalence:** If returns are modeled as a scheduled second dispatch (not a reactive response), one could treat X4 and X8 as variants. **Not defensible** unless return activity is suppressed.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### Information Preserved by PM4Py Key Structure

PM4Py's `cluster_equivalent_ocel(ocel, max_objs)` function:
- Returns clusters of (event_id, object_id) pairs grouped by equivalence class
- Uses the **object-type–attribute event graph** as its foundation
- Preserves event labels, object types, and object–event incidence
- Does **not** preserve:
  - O2O qualifiers (metadata on edges)
  - External-object flags (treats EXT-OA as a regular object ID)
  - Semantic interpretation of roles
  - Activity ordering (only connectivity)

### Why Raw Identifiers Create Fine-Grained Clusters

Example:
```
X1: Pack Package{Order:O1; Package:P11}
X2: Pack Package{Order:O2; Package:P21}
```

PM4Py's key structure distinguishes these as separate classes because (Order, O1)  (Order, O2). **Raw identifier clustering is too fine.** Solutions:

1. **Post-process canonicalization:** Rename all identifiers to type-based indices (Order_1, Item_1, Package_1, etc.).
2. **Use aggregate signature:** Map each cluster key to a motif signature before returning.
3. **Custom equivalence predicate:** Override PM4Py's comparison to ignore identifier values.

### Canonicalization Outline

```python
from pm4py.objects.ocel.obj import OCEL
import pm4py

def cluster_and_canonicalize(ocel: OCEL):
    """
    1. Run PM4Py's clustering on raw OCEL.
    2. Rename identifiers within each cluster to canonical form.
    3. Return super-clusters (motif-level equivalence).
    """
    # Step 1: Raw clustering
    raw_clusters = pm4py.cluster_equivalent_ocel(ocel, max_objs=100)
    
    # Step 2: Compute canonical signature per execution
    # (requires re-parsing OCEL into executions by lead object)
    executions = parse_ocel_by_lead_object(ocel, lead_type="Order")
    signatures = {eid: canonical_signature(exec) for eid, exec in executions.items()}
    
    # Step 3: Group executions by signature
    motif_clusters = {}
    for eid, sig in signatures.items():
        if sig not in motif_clusters:
            motif_clusters[sig] = []
        motif_clusters[sig].append(eid)
    
    return motif_clusters, signatures
```

### Equivalence Levels and Use Cases

| Use Case | Optimal Equivalence | Reason |
|----------|-------------------|--------|
| Exact process mining (e.g., ISO 27001 audit) | **Typed-structural (TSE)** | Preserves all observable structure; external references are material. |
| Operational segmentation (e.g., routing) | **Business-semantic (BSE)** | Identifies reusable motifs; ignores benign ID differences. |
| Financial reconciliation | **Qualification-aware (QAE)** | Mutation qualifiers affect settlement correctness. |
| High-level descriptive reporting | **Activity-sequence (ASE)** | Summarizes event flows; suitable for dashboards. |

## 7. Robustness Analysis

### Perturbation 1: Ignore All O2O Qualifiers

**Affected executions:** X7, X8

- **X7 (Item-substitution):** Signature changes from (1,1,1,F,**T**,F,1) to (1,1,1,F,**F**,F,1).
  - **X7 merges into S1** (Standard).
  - **Risk:** Loss of traceability on item substitution; becomes indistinguishable from a normal execution.

- **X8 (Return-and-repack):** Signature changes from (2,2,1,F,**T**,F,1) to (2,2,1,F,**F**,F,1).
  - **X8 remains in S7** (distinct because of 2 packages and 2 deliveries) but loses the "mutation" flag.
  - **Risk:** Return semantics become invisible; looks like a planned split delivery.

**Cluster stability:** X1, X2, X3, X4, X5, X6 **unchanged**. X7 collapses to S1. X8 becomes indistinguishable from a variant of S3 without mutation context.

---

### Perturbation 2: Ignore External Objects

**Affected executions:** X5, X6

- **X5:** Signature changes from (1,1,1,**T**,F,F,1) to (1,1,1,**F**,F,F,1).
  - **X5 merges into S1** (Standard).
  - **Risk:** Cross-order consolidation becomes invisible; billing allocation is lost.

- **X6:** Signature changes from (1,1,1,**T**,F,F,1) to (1,1,1,**F**,F,F,1).
  - **X6 merges into S1**.
  - **Risk:** Joint invoicing becomes invisible.

**Cluster stability:** X1, X2, X3, X4, X7, X8 **unchanged**. X5 and X6 collapse to S1. This is **not recommended** as it obscures shared-object architecture.

---

### Perturbation 3: Collapse Repeated Same-Label Events

**Affected executions:** None use repeated same-label events; however, X4 has two Record Payment events.

- **X4:** Collapse the two Record Payment events into a single abstract event with a multiplicity attribute.
  - Signature remains (2,2,**2**,F,F,T,1) if we count distinct Payment objects.
  - **If we count distinct Payment event types:** changes to (2,2,**1**,F,F,T,1)  merges with S2.
  - **Risk:** Partial payment semantics lost; becomes indistinguishable from a single-payment split delivery.

**Cluster stability:** **Not robust.** X4's identity depends on multi-payment structure.

---

### Perturbation 4: Treat Pack/Dispatch Order as Partial Order

**Affected executions:** X3, X4, X8

- **X3:** Current order: Pack P31, Pack P32, Dispatch (P31, P32).
  - Under partial order: the two Pack events can occur in any order (or concurrently) before Dispatch.
  - **Signature unchanged** (still 2 packages, 1 delivery).
  - **Interpretation:** Parallel packing is allowed; the execution is still consolidated delivery.

- **X4:** Current order: Pack P41, Dispatch D41, Pack P42, Dispatch D42.
  - Under partial order: Dispatch D41 must follow Pack P41; Dispatch D42 must follow Pack P42; but the two chains can interleave.
  - **Signature unchanged** (still 2 packages, 2 deliveries).
  - **Interpretation:** Asynchronous fulfillment is permitted; still split delivery.

- **X8:** Current order: Pack P81, Dispatch D81, Return I82, Inspect, Pack P82, Dispatch D82.
  - Under partial order: Return and Inspect can overlap with the second Pack; however, Dispatch D82 must follow Pack P82.
  - **Signature unchanged** (still 2 packages, 2 deliveries, mutation).
  - **Interpretation:** Return is a causal prerequisite; repack flows from return.

**Cluster stability:** **Highly robust.** Partial order does not change cardinalities; signatures remain stable.

---

### Perturbation 5: Treat Payment Multiplicity as Attributes (Payment Amount)

**Affected executions:** X4

- **X4:** Current: two Payment objects (M41, M42) recorded separately.
  - **Variant:** single Payment with two amount attributes (e.g., M41={amount:50}, M42={amount:50}).
  - Signature changes from (2,2,**2**,F,F,T,1) to (2,2,**1**,F,F,T,1) if we count Payment objects, or (2,2,**1**,F,F,T,{M: 2 components}) if we track component count.
  - **Risk:** Loses the distinction between "multiple invoices" and "one invoice with installments."

**Cluster stability:** Depends on whether amount-based aggregation is allowed in the metric. If BSE requires payment object cardinality, X4 remains distinct. If amount is absorbed into attributes, X4 becomes ambiguous with S3.

## 8. Limitations and Recommendation

### Recommended Equivalence by Purpose

| Purpose | Equivalence | Rationale |
|---------|-------------|-----------|
| **Compliance monitoring** | **Qualification-aware (QAE)** | Must preserve mutation qualifiers and external references; audits require full traceability. |
| **Operational segmentation** | **Business-semantic (BSE)** | Motif-level clustering groups operations by fulfillment strategy; actionable for routing and SLA assignment. |
| **Root-cause analysis** | **Typed-structural (TSE)** | Preserves all observable event and object structure; essential for debugging and anomaly detection. |
| **Descriptive reporting** | **Activity-sequence (ASE)** | Summarizes event flows at the highest level; sufficient for dashboards and KPI reporting. |

### Why No Single Notion Suffices

1. **Compliance** requires qualification awareness (X7 and X1 are NOT equivalent for audit purposes; the mutation must be recorded).

2. **Operations** do not care about identifier renaming (X1 and X2 are operationally identical; no routing or SLA change between them).

3. **Root-cause** needs full structure (a logistics issue in X3 cannot be diagnosed if consolidation is collapsed; you must know whether two packages existed).

4. **Reporting** benefits from aggregation (an executive dashboard does not need to distinguish X1 from X2; showing "standard fulfillment" is sufficient).

---

### Additional Limitations

- **Scalability:** PM4Py's `cluster_equivalent_ocel` may timeout on large `max_objs` values. Post-processing canonicalization is O(|executions| × |signature_space|), which is tractable if signatures are cached.

- **Missing metadata:** If O2O qualifiers are not present in the OCEL, QAE and BSE collapse toward TSE. Repair: reconstruct qualifiers from event attributes (e.g., item removal inferred from Pack-vs-Dispatch item lists).

- **External object ambiguity:** X5 and X6 assume EXT- objects are resolvable. If external objects are not traced back to their originating orders, "cross-order" semantics cannot be validated. Repair: require external object definition in the OCEL schema.

- **Causality and ordering:** Partial-order treatment (Perturbation 4) assumes that concurrent events do not introduce race conditions. If pack order affects inventory consistency, partial-order equivalence is invalid. Recommendation: preserve total order unless explicit concurrency timestamps are provided.
