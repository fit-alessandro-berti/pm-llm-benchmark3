## 1. Equivalence design space

To analyze these executions meaningfully, we define three equivalence relations ranging from syntactic to semantic. These relations determine which differences constitute distinct process variants.

**1. Activity-Sequence Equivalence ($\equiv_{act}$)**
*   **Definition:** Two executions $E_1$ and $E_2$ are equivalent if their projected event traces contain identical sequences of activity labels, ignoring all object identifiers and attributes. Formally, $\text{trace}(E) = [a_1, a_2, ..., a_n]$. $E_1 \equiv_{act} E_2 \iff \text{trace}(E_1) = \text{trace}(E_2)$.
*   **Invariants Preserved:** Control-flow order, activity types, repetition counts of activities.
*   **Information Discarded:** All object data, relationships, multiplicities, timestamps, and external references.
*   **Properties:** Reflexive, symmetric, transitive.
*   **Concurrency:** Assumes a strict total order provided by the input list; simultaneous events are ordered by input index.

**2. Typed Structural Equivalence ($\equiv_{struc}$)**
*   **Definition:** Two executions are equivalent if their object graphs (restricted to objects linked to the lead Order) are isomorphic under identifier renaming. We map object types to nodes and event incidences to edges. Multiplicities of object types per event matter (e.g., 1 Package vs 2 Packages).
*   **Invariants Preserved:** Object types, event-object incidence structure, object cardinalities within events (e.g., `Pack{Item:I1,I2}` vs `Pack{Item:I1}`).
*   **Information Discarded:** Specific local identifiers (e.g., `I11` vs `I21`), O2O qualifiers (e.g., `removed_before_dispatch`), external object flags (`EXT`).
*   **Properties:** Reflexive, symmetric, transitive.
*   **Concurrency:** Handles concurrent events by treating them as sets incident to the same time-step; ordering between concurrent sets is ignored.

**3. Business-Semantic Equivalence ($\equiv_{biz}$)**
*   **Definition:** Executions are equivalent if they represent the same operational intent and risk profile. This extends $\equiv_{struc}$ by preserving external object flags (`EXT`), O2O qualifiers (substitutions, returns), and lifecycle motifs (loops vs linear flow).
*   **Invariants Preserved:** All structural invariants plus external dependencies, modification qualifiers, and feedback loops.
*   **Information Discarded:** None relevant to business logic; purely cosmetic variations (ID names, whitespace) are removed.
*   **Properties:** Reflexive, symmetric, transitive.
*   **Concurrency:** Treats causal dependencies derived from object lifecycles (e.g., Pack before Dispatch) as the primary order, allowing reordering of independent parallel branches.

## 2. Canonical signatures

We implement a canonicalization scheme for $\equiv_{biz}$. The signature is a tuple representing the normalized event stream enriched with object topology summaries. Local identifiers are hashed to generic placeholders (`L1`, `L2`) based on first appearance, while external identifiers are flagged.

```python
def canonical_signature(execution):
    """
    Returns a hashable signature for Business-Semantic Equivalence.
    Input: List of Event dicts {'activity': str, 'objects': dict}
    """
    sig_parts = []
    id_map = {} 
    next_local_id = 1
    
    for event in execution:
        act_label = event['activity']
        obj_summary = []
        
        # Normalize Object IDs
        for o_type, ids in event['objects'].items():
            for oid in sorted(ids): # Sort for determinism
                if oid.startswith('EXT'):
                    obj_summary.append(f"{o_type}:EXT")
                else:
                    if oid not in id_map:
                        id_map[oid] = f"L{next_local_id}"
                        next_local_id += 1
                    obj_summary.append(f"{o_type}:{id_map[oid]}")
        
        # Capture O2O Qualifiers if present (simulated via metadata)
        qual = event.get('qualifiers', [])
        
        # Construct normalized event token
        token = f"{act_label}[{','.join(obj_summary)}]{{{','.join(qual)}}"
        sig_parts.append(token)
    
    # Aggregate global metrics for quick filtering
    ext_count = sum(1 for s in sig_parts if 'EXT' in s)
    return (tuple(sig_parts), ext_count)

# Example Usage

# sig_x2 = canonical_signature(X2_events)
# assert sig_x1 == sig_x2  # True
```

This signature ensures that `I11` and `I21` both map to `L1` upon first encounter in their respective contexts, while `EXT-OA` remains distinct. Qualifiers attached to events are serialized into the token, ensuring replacements (X7) or returns (X8) alter the signature even if activity labels match X1.

Under $\equiv_{act}$ and $\equiv_{struc}$, these are identical. Under $\equiv_{biz}$, they remain identical because the business intent (adding two items) is invariant to insertion order. Differences are ignored as noise.

**X1 versus X5**
$\equiv_{struc}$ groups them (same local topology). $\equiv_{biz}$ separates them. X5 involves `EXT-OA`, implying dependency on another order's lifecycle. Ignoring this (as $\equiv_{struc}$ does) hides supply chain coupling risks.

**X1 versus X6**
Similar to X5, but financial coupling. $\equiv_{act}$ cannot distinguish them. $\equiv_{biz}$ distinguishes based on Invoice participants. Merging them would obscure revenue recognition complexities.

$\equiv_{act}$ and $\equiv_{struc}$ view these as identical. This is a critical distinction for inventory accuracy.

**X3 versus X4**

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The function `pm4py.cluster_equivalent_ocel` clusters OCEL logs based on exact structural isomorphism of the object graph relative to the case concept.

*   **Preserved Information:** It preserves exact event names, object types, and specific object IDs. It checks if the connectivity graph is isomorphic.
*   **Identifier Sensitivity:** By default, it treats `I11` and `I21` as distinct constants. Thus, X1 and X2 would fall into different clusters unless the log is pre-processed to anonymize IDs.
*   **Canonicalization Strategy:** To fix this, one must run a normalization pass before clustering. Replace all local UUIDs with sequential integers or hashes per execution instance.
*   **Preferability:** Exact equivalence is preferable for forensic auditing where every byte matters. Business clustering is preferable for performance monitoring where patterns matter more than instances.
*   **`max_objs`:** Large connected components can explode memory usage. Setting `max_objs` limits the neighborhood size, potentially cutting off external links (like EXT objects), forcing X5/X6 into C1 erroneously.

```python
import pm4py
from pm4py.objects.ocel.obj import Ocel

def cluster_business_semantic(log, lead_type="Order"):
    # 1. Pre-process to anonymize local IDs
    # (Assume custom function 'canonicalize_ids' defined in Sec 2)
    log = canonicalize_ids(log) 
    
    # 2. Run standard clustering
    clusters = pm4py.cluster_equivalent_ocel(log, 
                                             max_objs=50, 
                                             lead_object_type=lead_type)
    
    # 3. Post-process to merge based on external flags
    # (Custom aggregation step)
    semantic_clusters = {}
    for c_id, members in clusters.items():
        has_ext = any(m.has_external_objects for m in members)
        key = ("external" if has_ext else "internal", len(members))
        semantic_clusters.setdefault(key, []).extend(members)
        
    return semantic_clusters
```

## 7. Robustness analysis

Assignments change significantly under perturbations:

1.  **Ignore all O2O qualifiers:** X7 (Replacement) collapses into C1 (Standard). The distinction between "Perfect Order" and "Corrected Order" vanishes. This degrades Root Cause Analysis capabilities.
2.  **Ignore external objects:** X5 and X6 collapse into C1. Supply chain dependencies are masked, leading to false positives in capacity planning (assuming internal resources only).
3.  **Collapse repeated same-label events:** X3 and X4 lose their distinction. If `Pack` is collapsed to a boolean "Packed?", X3 and X4 become identical to X1. This destroys logistical granularity.
4.  **Treat Pack/Dispatch as partial order:** If we allow Pack after Dispatch (violating physics but possible in bad logs), X8 might merge with C1. Enforcing causal validity (Pack < Dispatch) maintains separation.
5.  **Payment multiplicity as amount:** If M41+M42 sums to V41 value, X4 could merge with X1 financially. Structurally they remain distinct. This depends on whether the cluster goal is operational efficiency (structure) or accounting closure (amount).

## 8. Limitations and recommendation

No single equivalence notion satisfies all analytical needs due to conflicting fidelity requirements.

*   **Compliance Monitoring:** Use **Typed Structural Equivalence**. Regulators require proof of specific steps (e.g., "Was an Invoice issued?"). Exact object linkage ensures audit trails are verifiable.
*   **Operational Segmentation:** Use **Business-Semantic Equivalence**. Managers need to know if an order was "Split Shipped" or "Returned" to allocate costs accurately. Identifier noise must be filtered.
*   **Root-Cause Analysis:** Use **Fine-Grained Semantic Equivalence**. Here, distinctions like X7 (Substitution) vs X1 (Standard) are vital. Aggregating them hides defect rates.
*   **Descriptive Reporting:** Use **Activity-Sequence Equivalence**. Executive dashboards care about "Order Cycle Time" aggregates, not whether Package 1 or Package 2 was created first.

**Recommendation:** Adopt a hierarchical approach. Store raw data for Compliance. Compute Semantic Signatures (Section 2) for Operations. Derive Activity Traces for Reporting. This allows switching granularity without losing the underlying evidence. Relying solely on activity labels fails to capture the complexity of modern object-centric processes where the "Case" is defined by the Order, but the "Process" spans multiple Orders and Objects.
