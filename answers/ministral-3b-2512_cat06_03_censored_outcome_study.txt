### **1. Target Definition**
**Primary Target:**
- **Definition:** *Probability of default within 90 days after account activation*, conditioned on the case being activated (i.e., a *conditional survival probability* for activated accounts).
- **Prediction Time:** The first event after the case starts that meets the prefix criteria (e.g., Identity/KYC Check or Credit Review).
- **Horizon:** 90 days post-activation.
- **Unit of Analysis:** Activated accounts only (explicitly excluding rejected/withdrawn/transferred cases).
- **Estimand:** The model estimates the *conditional risk* of default given the observed process up to the prediction time, under the assumption that activation is the relevant policy decision point.

**Alternative Target:**
- **Multi-state competing-risk model:** Treat rejected/withdrawn/transferred cases as competing outcomes (non-default) and activated cases as the primary risk event. This explicitly models the *causal pathway* from application to default, accounting for selection bias. The target would be the *cumulative incidence function* (CIF) of default among activated cases, with competing risks for rejection/transfer.

---

### **2. Cohort Construction**
**Inclusion/Exclusion Rules (as-of 15 Feb 2026):**
- **Included:** Cases with:
  - A start event before 1 Jan 2024.
  - At least one event in the prefix (e.g., Identity/KYC Check or Credit Review) before the prediction time.
  - Activated by the data-extraction date (i.e., `Contract Signed` or `Account Activated` event).
- **Excluded:** Cases with:
  - No prefix events (e.g., empty logs).
  - Rejected/withdrawn/transferred before activation (explicitly excluded from the target).
  - Still-open cases (no activation event by 15 Feb 2026).
  - Activated cases with missing or delayed `default_90d` labels (censored).

### **3. Censoring and Missing-Label Strategy**
**Censoring Types:**
1. **Ordinary Right Censoring:** Activated cases with missing `default_90d` (3,600 cases; labels arrive 7–35 days later).
2. **Delayed Labels:** Cases where `default_90d` is missing at prediction time but will arrive later.
3. **Selection Through Activation:** Rejected/withdrawn cases are *competing outcomes* (not non-default).
4. **Transfer as Competing Event:** Transferred cases are censored at transfer time (60% linkage; assume 40% missing follow-up).
5. **Permanently Missing Feeds:** Partner-originated activated cases (unknown proportion) have no default feed.

**Primary Analysis Strategy:**
- Use a **competing-risks model** (e.g., Fine-Gray) for activated cases, with:
  - Default as the primary event.
  - Rejection/transfer as competing risks.
  - Censoring for still-open cases.
- Sensitivity Analysis: Compare to a *survival analysis* (only default) and a *binary classification* (default vs. non-default, ignoring competing risks).

**Assumptions:**
- Testable: Linkage completeness for transfers.
- Partially Testable: Partner-originated missing feeds (cannot verify).
- Untestable: Whether transfer/partner cases would default if activated (requires counterfactual).

### **4. Prefix Extraction**
**Prefix Rules:**
- **Fixed Event Count:** Use the first 3 events (e.g., Start  KYC  Credit Review) if they exist.
- **Elapsed Time:** If event count is ambiguous (e.g., repeated document loops), use the first event after 24 hours (to avoid short cases).
- **Handling Short Cases:** Drop cases with <3 events or <24h since start.
- **Activity Renaming:** Use `pm4py.discover_dfg` to map renamed activities (e.g., "Credit Review"  "Credit Assessment") to a canonical set.

### **5. Process-Aware Features**
**Features:**
1. **Control Flow:**
   - Prefix variants (e.g., "KYC  Credit Review").
   - Rework loops (count of document requests).
2. **Timing:**
   - Time from start to prefix event.
   - Time between prefix events.
3. **Resource/Queue:**
   - `risk_score` at prefix time.
   - `documents_total` (if available at prefix time).
4. **Static Case Attributes:**
   - `requested_amount`, `region`, `channel`.
5. **Historical Reference:**
   - Aggregated `risk_score` over the prefix.

**Avoid:**
- `final_limit` (post-activation).
- `decision_reason` (future-dependent).
- Future events (e.g., `Collection Contact`).

---

### **6. Leakage Audit**
| Feature/Data Element       | Leakage Risk                          | Valid Availability Rule                          | Keep/Repair/Drop | Rationale                                  |
|---------------------------|---------------------------------------|------------------------------------------------|------------------|--------------------------------------------|
| `final_limit`             | Post-activation (future-dependent)    | Must be before activation                       | Drop             | Leaks into future horizon.                  |
| `decision_reason`         | Future-dependent (e.g., "Rejected")    | Must be before prefix events                    | Drop             | Leaks outcome.                             |
| `collection_status`       | Future-dependent                      | Must be before activation                       | Drop             | Leaks default info.                        |
| Future Events             | Post-prefix (e.g., Contract Signed)    | Exclude all events after prefix                 | Drop             | Future-dependent.                          |
| `documents_total`         | Aggregated over day (not prefix time) | Must be at prefix time                          | Repair           | Use `documents_total` at prefix timestamp.  |
| Updated `risk_score`      | Updated after prefix events            | Use the latest score before prefix             | Keep             | Valid if prefix is time-based.              |
| Resource Experience        | Stored at extraction time             | Use employee experience at event time          | Repair           | Extract from event data.                   |
| `label_available_at`      | Future-dependent                      | Must be before prediction time                 | Drop             | Leaks label maturity.                      |

### **7. Validation Design**
**Temporal Split:**
- **Train:** Cases started 1 Jan 2024–30 Jun 2024 (policy pre-migration).
- **Validation:** 1 Jul 2024–31 Dec 2024 (policy change).
- **Test:** 1 Jan 2025–14 Feb 2026 (system migration).

**Metrics:**
- **Survival Analysis:** AUC for cumulative incidence.
- **Competing-Risks:** C-index or log-rank test.
- **Binary Classification:** AUC (if ignoring competing risks).

**Subgroup Checks:**
- Partner-originated cases (elevated missing-feed risk).
- Short vs. long cases (prefix length impact).

**Distribution Shift:**
- Monitor `risk_score` thresholds (policy change).
- Check event renaming (system migration).

---

### **8. Limitations and Decision-Use Boundary**
**What the Study Cannot Claim:**
- **Predictive Association:** The model estimates *observed* default risk, not causal effects.
- **Selection Effects:** Transfers/partners may default differently if activated.
- **Counterfactual Default Risk:** Cannot infer "what if rejected cases had been activated?"

**Deployment Risks:**
1. New policy thresholds alter selection probabilities.
2. System migration introduces event-renaming noise.
3. Partner-originated cases may have missing labels.

### **9. PM4Py Implementation Skeleton**
```python
import pandas as pd
import pm4py
from pm4py.objects.log.importer.csv import importer as csv_importer
from pm4py.objects.conversion.log import converter as log_converter

# Load data
df = pd.read_csv("applications_events.csv")
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"])

# Preprocess: Extract prefixes and activation events
log = csv_importer.import_dataframe(df, case_id_col="case:concept:name")
prefixes = pm4py.get_prefixes_from_log(log, max_length=3, min_length=1)
prefixes = prefixes[prefixes["length"] == 3]  # Fixed-length prefixes

# Build cohort metadata
case_metadata = pd.DataFrame({
    "case_id": log["case:concept:name"].unique(),
    "start_time": log["time:timestamp"].min(),
    "activation_time": log["time:timestamp"].max(),
    "label_available": log["label_available_at"].max(),
    "is_activated": log["case:concept:name"].isin(["Contract Signed", "Account Activated"]).any()
}).rename(columns={"case_id": "case_id"})

# Merge with prefixes
prefixes = prefixes.merge(case_metadata, on="case:concept:name")

# Filter activated cases (as-of 15 Feb 2026)
activated = prefixes[prefixes["is_activated"] & (prefixes["activation_time"] <= "2026-02-15")]
labeled = activated[activated["label_available"] > "2024-01-01"]  # Delayed labels

# Audit leakage
leakage_check = pd.DataFrame({
    "Feature": ["final_limit", "decision_reason", "collection_status"],
    "Risk": ["Future-dependent", "Future-dependent", "Future-dependent"],
    "Validity": ["Before activation", "Before prefix", "Before activation"],
    "Action": ["Drop", "Drop", "Drop"]
})

print(f"Cohort counts: {len(activated)} activated, {len(labeled)} labeled")
```

**Key Notes:**
- Uses `pm4py.get_prefixes_from_log` for fixed-length prefixes.
- Explicitly drops future-dependent features.
- Validates temporal splits by case start time.
- Audits leakage risks systematically.
