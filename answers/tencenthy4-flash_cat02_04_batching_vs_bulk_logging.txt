Why G6-like data can create both inflated waiting and near-zero service: both lifecycle fields are populated at the administrative submission moment, 17:00. Waiting measured as `queue_arrival  start` therefore absorbs the entire real or apparent delay from afternoon arrival to end-of-shift entry. Service measured as `complete  start` is then mechanically zero or near-zero because the same timestamp is reused. The result is internally consistent arithmetic but externally invalid process performance: long queues, no work time, and a false completion burst.

            max_batch_size=("size", "max"),
            merge_distances=("merge_distance", lambda x: ",".join(map(str, sorted(set(x))))),
            min_batch_sizes=("min_batch_size", lambda x: ",".join(map(str, sorted(set(x))))),
        )
    )
else:
    pm_summary = pd.DataFrame(columns=[
        "clusters", "category", "runs_detected", "max_batch_size",
        "merge_distances", "min_batch_sizes"
    ])

def max_group_size(s):
    s = s.dropna()
    return int(s.value_counts().max()) if len(s) else 0

equality = df.groupby("cluster", as_index=False).agg(
    n=("case", "size"),
    start_eq_max=("start_dt", max_group_size),
    end_eq_max=("complete_dt", max_group_size),
)

def pair_diagnostics(g):
    intervals = list(zip(g["start_dt"], g["complete_dt"]))
    overlapping_pairs = 0
    total_pairs = 0
    for i in range(len(intervals)):
        for j in range(i + 1, len(intervals)):
            s1, e1 = intervals[i]
            s2, e2 = intervals[j]
            if pd.notna(s1) and pd.notna(e1) and pd.notna(s2) and pd.notna(e2):
                total_pairs += 1
                if s1 < e2 and s2 < e1:
                    overlapping_pairs += 1

    events = []
    for s, e in intervals:
        if pd.notna(s) and pd.notna(e) and e > s:
            events.append((s, 1))
            events.append((e, -1))
    events.sort(key=lambda x: (x[0], x[1]))  # at equal times, end before start
    cur = max_cur = 0
    for _, delta in events:
        cur += delta
        max_cur = max(max_cur, cur)

    return pd.Series({
        "overlap_rate": overlapping_pairs / total_pairs if total_pairs else 0.0,
        "max_concurrency": max_cur if events else 0,
    })

overlap_rows = []
for (cluster, resource), g in df.groupby(["cluster", "resource"], sort=False):
    stats = pair_diagnostics(g)
    overlap_rows.append({"cluster": cluster, "resource": resource, **stats})
overlap_cluster = (
    pd.DataFrame(overlap_rows)
    .groupby("cluster", as_index=False)
    .agg(overlap_rate=("overlap_rate", "max"), max_concurrency=("max_concurrency", "max"))
)

lag = df.groupby("cluster", as_index=False).agg(
    record_lag_mean_sec=("record_lag_sec", "mean"),
    record_lag_spread_sec=("record_lag_sec", lambda x: x.max() - x.min()),
    zero_duration_count=("zero_duration", "sum"),
    negative_wait_count=("negative_wait", "sum"),
)

granularity = df.groupby("cluster", as_index=False).agg(
    precision=("precision", "first"),
    start_on_grid_rate=("start_on_grid", "mean"),
    complete_on_grid_rate=("complete_on_grid", "mean"),
)

queue_rows = []
for cluster, g in df.groupby("cluster", sort=False):
    first_start = g["start_dt"].min()
    arrivals = g["queue_arrival_dt"]
    queue_rows.append({
        "cluster": cluster,
        "queue_span_min": (arrivals.max() - arrivals.min()).total_seconds() / 60,
        "arrivals_before_first_start": int((arrivals <= first_start).sum()),
        "arrivals_15m_to_first_start": int(((arrivals > first_start - pd.Timedelta(minutes=15)) & (arrivals <= first_start)).sum()),
        "max_wait_to_first_start_min": (first_start - arrivals).dt.total_seconds().max() / 60,
        "min_wait_to_own_start_min": g["wait_min"].min(),
    })
queue_df = pd.DataFrame(queue_rows)

lifecycle = df.groupby("cluster", as_index=False).agg(lifecycle_flag=("lifecycle_flag", "first"))

parts = [equality, overlap_cluster, lag, granularity, queue_df, lifecycle]
diag = parts[0]
for part in parts[1:]:
    diag = diag.merge(part, on="cluster", how="left")
diag = diag.sort_values("cluster").reset_index(drop=True)

print("Cluster-level diagnostics")
diagnostic_cols = [
    "cluster", "n", "precision", "start_eq_max", "end_eq_max",
    "overlap_rate", "max_concurrency", "record_lag_mean_sec", "record_lag_spread_sec",
    "zero_duration_count", "negative_wait_count", "queue_span_min",
    "arrivals_before_first_start", "arrivals_15m_to_first_start",
    "max_wait_to_first_start_min", "min_wait_to_own_start_min",
    "start_on_grid_rate", "complete_on_grid_rate", "lifecycle_flag"
]
print(diag[diagnostic_cols].round(2).to_string(index=False))

print("\nPM4Py detected batch categories compared with clusters")
pm_cmp = diag[["cluster"]].merge(pm_summary, left_on="cluster", right_on="clusters", how="left")
if "clusters" in pm_cmp.columns:
    pm_cmp = pm_cmp.drop(columns=["clusters"])
pm_cmp["category"] = pm_cmp["category"].fillna("NONE_DETECTED")
pm_cmp["runs_detected"] = pm_cmp["runs_detected"].fillna(0)
pm_cmp = pm_cmp[[
    "cluster", "category", "runs_detected", "max_batch_size",

]]
print(pm_cmp.fillna("none").to_string(index=False))

# 5. Robustness and alternative explanations

**Resource IDs trusted vs treated as shared accounts**

- If resource IDs are trusted literally, G5 becomes an implausible case of one analyst working on four overlapping analyses, with four-way overlap around 13:12–13:20. The best alternative would be extreme multitasking or incorrect lifecycle endpoints. G1 remains a plausible automated cell batch because RBT-7 is explicitly a cell with four-item capacity. G2, G3, G4, G6, G7, and G8 remain single-resource interpretations, but their lifecycle problems are mostly source-semantics issues rather than identity issues.
- If resource IDs are treated as potentially shared more broadly, confidence drops wherever physical concurrency is inferred from one ID. For example, G3’s overlapping review intervals could reflect several reviewers using one T-C form account; G7’s five intervals could reflect several users of a legacy MES terminal. However, this does not erase the stronger evidence for end batching in G3 or quarter-hour rounding in G7.
- For G5 specifically, the shared-account interpretation is not merely defensive: it is documented. The main unresolved issue is capacity: up to three analysts versus four overlapping intervals. These can be reconciled by one analyst multitasking, endpoint uncertainty at 1-min precision, or a fourth unrecorded worker; badge data are required.

**Timestamps exact vs interval-censored by stated precision**

- Under an exact-timestamp reading, G1 and G4/G8 adjacency/equality are strong evidence of fixture batching and serial flow because scanner/PLC precision is 1 sec. G7 would look like five simultaneous 15-min manual measures, which is much less believable.
- Under interval-censoring, G7 changes decisively: the stored 14:00/14:15 values are grid artifacts, and the five measures could be serial, overlapping, or otherwise distributed inside the quarter-hour window. The negative wait for M05 is a strong sign that exact reading is invalid.
- For 1-min sources, equal stored timestamps should be treated as “equal within up to roughly a minute,” not exact simultaneity. This weakens fine-grained overlap claims in G5, but it does not explain G6’s multi-hour arrival-to-17:00 gap or G3’s contextual folder-submission evidence.
- For G8, precision is not the main issue; clock alignment is. If the safety clock and repair clock differ, the apparent 15:38 post-safety start time may shift.

**Cases where the same temporal pattern supports multiple physical explanations**

1. **Equal start and end in G1/G6/G7**: G1 supports a genuine four-item fixture batch; G6 supports bulk data entry with no physical service; G7 supports 15-min rounding. The stored pattern is similar, but source context separates them.
2. **Common start in G2/G7**: G2 supports a real group-begin action; G7 supports quarter-hour coarsening; both could superficially appear as a start batch in PM4Py.
3. **Common end in G3/G6/G7**: G3 supports folder submission after distributed reviews; G6 supports end-of-shift backfill; G7 supports rounding to a quarter-hour boundary.
4. **Overlap in G5**: overlap can mean multiple analysts behind one shared login, one analyst multitasking, or endpoint imprecision; resource identity and precision evidence are both needed.
5. **Adjacent intervals in G4/G8**: adjacency can mean normal serial single-piece flow, a sequential batch label, or post-downtime catch-up after queued work; only G8 has explicit downtime-context evidence, and even that is clock-uncertain.

# 6. Data-collection redesign

1. **P0 — Separate execution and recording timestamps.** Emit source event time for queue arrival, actual execution start, actual execution complete, and DB insertion time as distinct fields. Never overwrite execution start/complete with form-submission time.
2. **P0 — Add group/batch identifiers.** Require fixture ID or batch ID for G1-like cells, group-begin ID for G2-like screens, folder/submission ID for G3, bulk-form ID for G6, and job/queue ID for serial workflows. This lets analysts distinguish physical batches from logging batches.
3. **P0 — Capture human identity at badge/session level.** For shared logins such as `analyst_pool`, record badge ID, named user where permitted, role, and shared-account session mapping. Keep the shared account only as a system attribute, not as the utilization resource.
4. **P1 — Synchronize and document source clocks.** Use a common time source or record clock offsets per system. For G8-like cases, store safety-system time, repair-system time, and an explicit offset/alignment event.
5. **P1 — Record workstation capacity and group semantics.** Store capacity per resource/workstation, e.g., RBT-7 fixture slots = 4, inspection screen group controls, VDI analyst-pool capacity, and whether a timestamp applies to an item, group, folder, or form.
6. **P1 — Add pause/resume and downtime events.** Capture safety checks, maintenance, breaks, queue disablement, and restart times in the same process log. This prevents downtime queues from being misread as low performance.
7. **P2 — Preserve raw high-resolution timestamps and rich precision metadata.** Store raw source values, transformation rule, rounding direction, timezone, clock source, declared granularity, and estimated accuracy. The legacy MES rule in G7 should never remain undocumented.
8. **P2 — Export lifecycle events individually.** Rather than one row with multiple timestamp fields, emit append-only events such as `queued`, `started`, `paused`, `resumed`, `completed`, `submitted`, and `recorded`, each with source event ID and `sequence_no`.

# 7. Final adjudication

**High-confidence diagnoses**

- **G1**: high confidence as a genuine four-item fixture batch; analyze at fixture/batch level.
- **G3**: high confidence as end batching/bulk folder submission; use arrival-to-start cautiously, but do not trust complete as actual review completion.
- **G4**: high confidence as serial one-piece flow; suitable for ordinary queueing/service analysis.
- **G6**: high confidence as bulk data-entry/backfill; physically uninterpretable as execution.
- **G7**: high confidence as timestamp coarsening; physically uninterpretable at exact timestamp resolution.
- **G2**: moderately high confidence as group-start semantics; treat 10:00 as group start/setup unless per-item starts are recovered.

**Exclude or interval-censor**

- **G6**: exclude from waiting, service, utilization, and throughput conclusions unless real execution timestamps are recovered. At minimum, treat lifecycle timestamps as data-entry events only.
- **G7**: interval-censor by the 15-min source precision or exclude exact service-time analysis. Negative waiting makes exact use indefensible.
- **G3**: exclude `complete` from service-time analysis; interval-censor actual completion between start and 11:30 if no raw data exist.
- **G8**: do not compute final waiting-time or downtime-attribution conclusions until clocks are aligned, though the serial service after 15:38 is usable.
- **G5**: do not compute individual resource utilization from `analyst_pool`; use pool-level capacity or obtain badge identity.

**Require operational validation before performance conclusions**

- **G5**: validate how many analysts were active and whether overlapping cases were truly assigned to different people or multitasked.
- **G8**: validate whether the safety-check event caused the queue delay or whether clock skew/scheduled release explains the 15:38 start.
- **G2**: validate whether “begin group” corresponds to actual work start, setup start, or UI grouping only.
- **G1**: validate fixture/batch membership and whether start/complete semantics are per item or per fixture, although the physical batch explanation is already strong.
