# 1. Objectives and constraints

## Objectives (optimize jointly; no single “best”)
- **SLA protection**: minimize risk of missing `sla_deadline`, prioritizing urgent/high cases and preventing “near-miss” accumulation.
- **Quality / rework reduction**: reduce errors, rework, and downstream appeals by matching case complexity to skill and by limiting harmful reassignments.
- **Continuity of ownership**: keep the current owner when handover costs are high and/or reassignment history is already risky, unless safety/compliance or extreme SLA risk forces a change.
- **Fair workload & wellbeing**: balance assignments (WIP and time left today), avoid pushing high-overtime-risk workers except when justified by urgent SLA risk.
- **Skill development (controlled)**: create safe, documented learning opportunities; target **≥20%** of normal/low assignments to align with training priorities when SLA risk is acceptable.
- **Resilience**: avoid brittle “single-specialist” bottlenecks; keep capacity available in scarce skills (Security, Approval) and reduce dependence on one person/team.
- **Explainability & auditability**: every assignment must have a human-readable reason and leave measurable footprints in the event log (`assignment_reason`, `workload_snapshot`, `reassignment_count`, handover outcomes).

## Hard safety/compliance constraints (must hold)
- **C0. Skill 0 is forbidden**: if the matrix score is 0 for the required skill, that resource is ineligible.
- **C1. Batch cap**: no resource receives **>4** new assignments in the decision batch (supervision counts as involvement).
- **C2. High/urgent skill floor**: no **high/urgent** case to skill **<2** unless explicitly supervised.
- **C3. Overtime protection (guardrail)**: avoid assigning additional work to `overtime risk="high"` unless SLA urgency is high and no safer option exists.
- **C4. Continuity guardrail for expensive handovers**: for **high-complexity + high handover cost** cases, prefer continuity; switch only if current owner has skill 0–1 and safe supervision/quality cannot be ensured in time.
- **C5. Security Review rule**: Security Review must be done by **skill 3**, or by **skill 1–2 only under explicit supervision by R7_Gita or R8_Hugo**.
- **C6. Final Approval rule**: Final Approval must be performed by **skill 2–3** (skill 1 may prepare but not finalize).
- **C7. Quality batching rule**: Quality Check may be batched only when **priority ∈ {normal, low}** and **SLA remaining >24h**.

## Soft preferences (trade-offs we make explicit)
- **Throughput vs. rework**: first-available can be fast but increases mismatch/reassignments; specialist-only reduces immediate errors but can create queues.
- **Continuity vs. skill**: continuity reduces waiting from handovers; but keeping a weak-skill owner can inflate service time and rework.
- **Fairness vs. SLA**: distributing work improves wellbeing/resilience; but urgent cases may justify uneven load temporarily.
- **Specialization vs. resilience**: routing everything to specialists improves precision short-term; cross-training and “competent” routing improves robustness.

# 2. Assignment policy

## Overview (two-stage, explainable)
1. **Safety filter (hard constraints)** → remove ineligible assignments.
2. **Transparent scoring (soft preferences)** → rank remaining options with a small, auditable set of factors.

## Pseudocode (human-auditable)

```text
INPUTS:
  Queue Q = pending cases with (required_skill, priority, sla_remaining, complexity,
                                current_owner, reassignment_count, handover_cost_band, team/notes)
  Resources R = workers with (skill_matrix, current_open_cases, hours_remaining_today,
                              team, training_priority, overtime_risk)
  SecuritySupervisors = {R7_Gita, R8_Hugo}

PARAMS (interpretable weights; adjust by governance):
  w_sla=5, w_skill=3, w_continuity=3, w_fair=2, w_train=1.5, w_resilience=1.5
  complexity_high = 0.75
  training_min_share = 0.20 of normal/low assignments

HELPERS:
  eligible(case c, resource r):
    if skill(r, c.required_skill) == 0: return False

    if c.required_skill == "Security":
      if skill(r, "Security") == 3: pass
      else:
        # skill 1–2 allowed only if a Security supervisor is assigned and available
        if skill(r, "Security") in {1,2} and exists supervisor s in SecuritySupervisors
           with assignments_in_batch(s) < 4:
            mark "needs_supervision_by_security_supervisor"
        else: return False

    if c.next_activity == "Final Approval":
      if skill(r, "Approval") < 2: return False

    if c.priority in {"high","urgent"}:
      if skill(r, c.required_skill) < 2:
        if supervision_possible(c, r): mark "needs_supervision"
        else: return False

    if assignments_in_batch(r) >= 4: return False

    # continuity guardrail for expensive handovers
    if c.handover_cost_band == "high" and c.complexity >= complexity_high:
      if r != c.current_owner:
        # allow switch only if current owner is too weak and SLA/quality demands it
        if skill(c.current_owner, c.required_skill) >= 2: return False
        if not supervision_possible(c, c.current_owner): return True  # forced handover
        # otherwise, handover is allowed only if SLA is extremely tight and specialist needed
        if c.priority == "urgent" and c.sla_remaining_hours <= 4: return True
        else: return False

    return True

  sla_urgency_score(c, r):
    # estimate slack using historical medians per activity/skill level (auditable)
    est_service = median_service_time(activity=c.next_activity, skill_level=skill(r, c.required_skill))
    est_handover_wait = handover_wait_penalty(c, r)  # 0/low/med/high mapped to minutes
    est_queue_wait = queue_wait_estimate(required_skill=c.required_skill)  # by current backlog of eligible workers
    slack = c.sla_remaining - (est_service + est_queue_wait + est_handover_wait)
    return -slack  # higher is more urgent

  skill_match_score(c, r):
    base = {1:0.4, 2:0.7, 3:1.0}[skill(r, c.required_skill)]
    return base * (1 + 0.8*c.complexity)  # complexity raises value of skill

  continuity_score(c, r):
    if r == c.current_owner: return +1.0
    handover_pen = {"none":0.0, "low":0.2, "medium":0.6, "high":1.0}[c.handover_cost_band]
    reassign_pen = 0.5 if c.reassignment_count >= 2 else 0.0
    return -(handover_pen*(0.6+0.7*c.complexity) + reassign_pen)

  workload_fairness_score(c, r):
    wip = normalize(r.current_open_cases)
    time_left = normalize(r.hours_remaining_today)
    overtime_pen = {"low":0.0, "medium":0.3, "high":0.8}[r.overtime_risk]
    return -(0.7*wip - 0.4*time_left + overtime_pen)

  training_score(c, r):
    if c.priority not in {"normal","low"}: return 0
    if r.training_priority != c.required_skill: return 0
    if predicted_sla_risk(c, r) is "high": return 0
    # prefer trainee/competent doing with supervision when needed
    return +1.0

  resilience_penalty(c, r):
    # discourage concentrating scarce skills on one person; keep specialists available for urgent work
    bottleneck = backlog(required_skill=c.required_skill) / max(1, count_available_workers(required_skill=c.required_skill, min_skill=2))
    centralization_pen = 0.2 * assignments_in_batch(r)
    return +(0.6*bottleneck + centralization_pen)  # penalty to subtract

ALGORITHM:
  batch_assignments = []

  # 1) Optional batching: group Quality Check (normal/low, SLA>24h) into batch windows
  quality_batch = {c in Q | c.next_activity=="Quality Check" and c.priority in {normal,low} and c.sla_remaining>24h}

  # 2) Main loop: serve urgent → high → normal → low by descending SLA urgency score
  for c in sort_by_priority_then_sla(Q):
    candidates = []
    for r in R:
      if eligible(c, r):
        score = w_sla*sla_urgency_score(c,r) \
              + w_skill*skill_match_score(c,r) \
              + w_continuity*continuity_score(c,r) \
              + w_fair*workload_fairness_score(c,r) \
              + w_train*training_score(c,r) \
              - w_resilience*resilience_penalty(c,r)
        candidates.append((r, score))

    if candidates empty:
      assign exception: highest-skill available + record "exception_no_eligible"; escalate
    else:
      pick r* with max score
      if supervision required:
        pick supervisor s* (least loaded, eligible, within batch cap) and assign (r*, s*)
      record assignment_reason = top_contributors({SLA, SKILL, CONTINUITY, FAIRNESS, TRAINING, RESILIENCE})
      snapshot workload_snapshot = (open_cases, hours_left, overtime_risk, backlog_by_skill)

  # 3) Training quota check: if training share < 20% for normal/low, re-optimize only among
  #    low-risk normal/low cases with large SLA slack by swapping to eligible trainees + supervision.

TIE-BREAKING (when scores close):
  prefer (a) no handover on high handover-cost or high reassignment cases,
          (b) lower overtime risk,
          (c) same team when skills similar,
          (d) fewer open cases / more hours remaining,
          (e) random among equals to avoid systematic bias.
```

### How this stays explainable
- Each assignment is justified by **2–3 dominant factors** (e.g., “urgent SLA + specialist skill”, “continuity + training-with-supervision”).
- The policy is **auditable** because every factor is computable from the log and the skill matrix at assignment time, and stored/derivable via `assignment_reason` and `workload_snapshot`.

# 4. Comparison with baseline policies

## Expected outcomes (qualitative, trade-off aware)

| Dimension | First-available routing | Specialist-only routing | Proposed explainable dynamic policy |
|---|---|---|---|
| **Expected throughput (short-term)** | Often high (low waiting) but can drop later due to rework and thrashing | Can be slower when specialists queue; high utilization hotspots | Balanced: urgent work to specialists, non-urgent work to competent/trainees with guardrails; batching where safe |
| **SLA risk** | Lower average waiting, but higher risk of SLA misses from errors/rework and non-compliant assignments | Lower error-driven delays, but higher queue-driven misses in Security/Approval | Directly targets SLA slack; protects urgent cases; uses batching only when SLA slack allows |
| **Error / rework risk** | Higher due to skill mismatch and more handovers; violates supervision rules unless augmented | Lower immediate error risk, but fatigue and queueing can still trigger rework; more handovers when specialists differ from owners | Lower than first-available via skill/complexity matching + supervised training; avoids “handover spiral” on high-cost cases |
| **Fairness of workload** | Can overload the “least-loaded” people repeatedly; ignores overtime risk | Typically unfair: concentrates work on a few specialists | Uses batch cap, overtime penalties, and load-aware scoring; spreads where safe |
| **Skill development** | Accidental/unguarded; may put trainees on risky work | Minimal (experts do everything) | Explicit quota on low-risk cases; supervision logged and auditable |
| **Continuity of ownership** | Often poor: frequent owner changes as “first available” changes | Mixed: may frequently reassign to top specialist, increasing handovers | Continuity is a scored factor with hard guardrails for high-cost handovers and high reassignment histories |
| **Resilience (absence/bottlenecks)** | More distributed but unsafe/compliance-risky without supervision structure | Fragile: single points of failure in Security/Approval/Diagnosis | Avoids single-specialist overload; preserves specialist capacity for urgent work; uses supervision to extend capacity safely |

## Concrete implications in this queue
- **First-available** would tend to route many items to low-WIP workers (e.g., R10_Jonas, R6_Farid, R3_Celine) and might route Security/Approval to under-qualified resources unless extra rules are bolted on, increasing compliance and rework risk.
- **Specialist-only** would likely over-concentrate Security on **R8_Hugo** and Diagnosis/Rework on **R3_Celine**, creating bottlenecks and reducing resilience; it also tends to increase handovers when specialists are not current owners.
- **Dynamic** intentionally breaks continuity only when **SLA + complexity + compliance** justify it (e.g., C001), while using supervision and batching to keep throughput and learning without violating safety constraints.

# 5. Explanation to workers

We assign work using a small set of transparent rules that are meant to support you and protect customers:

- **Safety and compliance come first**: some tasks (like Security Review and Final Approval) have strict skill requirements. When supervision is required, we say so explicitly and name the supervisor.
- **Deadlines matter**: urgent cases are assigned to the people most likely to finish them on time with good quality, not simply the next available person.
- **We try to keep you on your cases**: if changing ownership is costly—especially on complex cases—we prefer continuity to avoid avoidable waiting and rework.
- **We protect wellbeing and fairness**: we avoid piling extra work on people at high overtime risk unless there’s an urgent deadline and no safe alternative.
- **Learning is planned, not accidental**: some low-risk work is deliberately used for training. When that happens, the assignment shows the training reason and the supervisor so expectations are clear and support is available.
- **You can challenge or override**: if you see a mismatch (missing context, unexpected complexity, availability issues), flag it—exceptions are allowed, but we record the reason so we can improve the system rather than blame individuals.

# 6. Process-mining audit indicators

All indicators below can be computed from the event log columns plus the skill matrix and shift metadata; they are intended to audit **outcomes** and **policy adherence**, not to micromanage individuals.

## Ownership continuity and handovers
- **Handover frequency (per case)**: count changes in `org:resource` across consecutive events, and/or count events where `org:resource != current_owner`. Track by `case_complexity` and `handover_cost_band`.
- **Handover-of-work network concentration**: use the handover network to measure whether work is becoming centralized around a few people (bottleneck risk) versus distributed (resilience).
- **Reassignment pressure**: distribution of `reassignment_count` at assignment events; % of cases with `reassignment_count > 2` and trend over time (given evidence of higher rework/appeal).

## Skill fit and supervision compliance
- **Skill mismatch rate**: for each assignment, compare `required_skill` to the assigned worker’s skill level; report:
  - share of high/urgent assignments with skill <2 (should be ~0 unless supervised),
  - share of Security Review assignments not skill 3 and without recorded supervisor (should be 0).
- **Supervision traceability**: when supervision is required, verify `assignment_reason` encodes the supervisor and that the supervisor belongs to {R7_Gita, R8_Hugo} for Security Review.

## Workload fairness and wellbeing
- **Workload distribution**: per day/shift, compute assignments per `org:resource`, WIP from `workload_snapshot`, and inequality measures (e.g., Gini / percentile gaps).
- **Overtime risk exposure**: fraction of assignments to `overtime risk="high"`, weighted by case urgency and by estimated service time; monitor whether urgent-only justification holds.
- **Batch cap violations**: per decision batch (or per hour), ensure no resource exceeds 4 new assignments (including supervision involvement).

## SLA outcomes
- **SLA miss rate**: cases where completion occurs after `sla_deadline`, segmented by `case_priority`, required skill, and whether handover occurred during the last X hours before deadline.
- **Near-miss rate**: cases completed within a narrow window before deadline (e.g., <1h), as early warning of hidden capacity issues.

## Quality outcomes
- **Rework after assignment**: probability of `Rework Correction` following a given assignment decision (especially after handovers or skill mismatches).
- **Appeal proxy**: if an explicit appeal activity/attribute exists, track it; if not, use (a) repeated rework cycles, (b) abnormal variant patterns, and (c) post-approval rework as proxies.

## Training effectiveness and safety
- **Training assignment share**: percent of normal/low assignments where `assignment_reason` indicates training and the resource’s `training priority` matches `required_skill` (target ≥20% when SLA risk acceptable).
- **Training guardrail outcomes**: compare supervised-training assignments vs non-training assignments on service time, rework, and SLA misses to ensure training is safe and effective.

## Specialist bottlenecks and resilience
- **Specialist load ratio**: backlog of cases requiring Security/Approval divided by count of available skill≥2 (or skill3 for Security) resources; rising ratios signal bottleneck risk.
- **Waiting-time by required skill**: use inserted waiting times to detect whether Security/Approval queues are growing (specialist-only routing signature).
- **Single-point-of-failure indicator**: share of Security/Approval events performed by the top 1 resource; high concentration reduces resilience.

## Deviations from policy
- **Policy deviation rate**: recompute the policy recommendation from the snapshot and compare with actual `org:resource`; deviations must have `assignment_reason` starting with an explicit exception code (e.g., `EXC_NO_ELIGIBLE`, `EXC_WORKER_UNAVAILABLE`, `EXC_MANAGER_OVERRIDE`).

# 7. PM4Py implementation sketch

Below is a sketch showing how to (a) compute audit indicators and (b) validate assignments against the policy. It deliberately uses PM4Py organizational mining and performance utilities so results are reproducible.

```python
import pandas as pd
import pm4py

# df columns assumed:
# case:concept:name, concept:name, time:timestamp, org:resource, required_skill,
# case_priority, sla_deadline, case_complexity, current_owner, team,
# assignment_reason, reassignment_count, workload_snapshot, handover_cost_band

def load_and_format(df: pd.DataFrame) -> pd.DataFrame:
    df = pm4py.format_dataframe(
        df,
        case_id="case:concept:name",
        activity_key="concept:name",
        timestamp_key="time:timestamp"
    )
    return df

def add_time_metrics(df: pd.DataFrame) -> pd.DataFrame:
    # adds waiting/service time attributes per event/case (auditable SLA and bottleneck metrics)
    df = pm4py.insert_case_service_waiting_time(df)
    return df

def org_mining(df: pd.DataFrame):
    # handovers and collaboration networks
    how = pm4py.discover_handover_of_work_network(df)
    wtn = pm4py.discover_working_together_network(df)
    sim = pm4py.discover_activity_based_resource_similarity(df)
    roles = pm4py.discover_organizational_roles(df)
    return how, wtn, sim, roles

def batching_audit(df: pd.DataFrame):
    # detect batches (e.g., Quality Check batching) and verify eligibility rules
    batches = pm4py.discover_batches(df)  # then filter to concept:name == "Quality Check"
    return batches

def performance_views(df: pd.DataFrame):
    # performance DFG and variants for throughput/loop detection
    perf_dfg = pm4py.discover_performance_dfg(df)
    variants = pm4py.get_variants(df)
    return perf_dfg, variants

def filter_slices(df: pd.DataFrame):
    # examples: focus on urgent cases, or Security work, or recent SLA-misses
    urgent = pm4py.filter_event_attribute_values(df, "case_priority", ["urgent"])
    security = pm4py.filter_event_attribute_values(df, "required_skill", ["Security"])
    slow_cases = pm4py.filter_case_performance(df, min_performance=0, max_performance=7*24*3600)
    return urgent, security, slow_cases

def compute_handover_per_case(df: pd.DataFrame) -> pd.Series:
    # simple per-case handover count using org:resource changes
    df_sorted = df.sort_values(["case:concept:name", "time:timestamp"])
    def count_changes(g):
        return (g["org:resource"] != g["org:resource"].shift(1)).sum() - 1
    return df_sorted.groupby("case:concept:name").apply(count_changes)

def skill_mismatch_indicator(df: pd.DataFrame, skill_lookup) -> pd.DataFrame:
    # skill_lookup(resource, required_skill) -> 0..3
    df = df.copy()
    df["skill_level"] = df.apply(lambda r: skill_lookup(r["org:resource"], r["required_skill"]), axis=1)
    df["is_high_or_urgent"] = df["case_priority"].isin(["high", "urgent"])
    df["skill_mismatch"] = df["skill_level"] < 2
    # Security rule: if not skill 3, must have explicit supervisor in assignment_reason
    df["security_supervision_missing"] = (
        (df["required_skill"] == "Security")
        & (df["skill_level"] < 3)
        & (~df["assignment_reason"].fillna("").str.contains("SUPERVISED_BY=R7_Gita|SUPERVISED_BY=R8_Hugo"))
    )
    return df

def audit_pipeline(df: pd.DataFrame, skill_lookup):
    df = load_and_format(df)
    df = add_time_metrics(df)
    how, wtn, sim, roles = org_mining(df)
    batches = batching_audit(df)
    perf_dfg, variants = performance_views(df)

    # Example indicator outputs
    handovers = compute_handover_per_case(df)
    df_ind = skill_mismatch_indicator(df, skill_lookup)

    # Optional: visualize SNA
    # pm4py.view_sna(how)
    # pm4py.save_vis_sna(how, "handover_network.png")

    return {
        "handover_network": how,
        "working_together_network": wtn,
        "resource_similarity": sim,
        "roles": roles,
        "batches": batches,
        "performance_dfg": perf_dfg,
        "variants": variants,
        "handover_per_case": handovers,
        "indicators_df": df_ind,
    }
```

To **validate policy adherence**, compute the recommended assignee from the same snapshot fields (`required_skill`, `case_priority`, `sla_deadline`, `case_complexity`, `current_owner`, `reassignment_count`, `handover_cost_band`, `workload_snapshot`) and compare it to `org:resource`. Any deviation should be justified in `assignment_reason` with an exception code, making deviations visible and reviewable rather than hidden.
