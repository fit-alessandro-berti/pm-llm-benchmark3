## 1. Equivalence design space

**Observation boundary.** Each execution contains the supplied events associated with its lead Order, all objects participating in those events—including `EXT` objects—and the supplied O2O facts. I do not expand an external object’s entire lifecycle. Identifiers are opaque except for the externality distinction. Missing O2O notes are not treated as evidence that a relationship does not exist.

**Activity-sequence equivalence, \(\equiv_A\).** Define

$$
A(X)=\langle activity(e_1),\ldots,activity(e_n)\rangle.
$$

Two executions are equivalent exactly when these sequences match. This preserves activity labels, repetitions, and supplied event order; it discards objects, incidence, qualifiers, and elapsed times. It is reflexive, symmetric, and transitive because it is equality of signatures.

For unresolved timestamp ties, use a sequence of unordered **label multisets**, rather than sorting by identifiers. Multiplicity remains observable.

**Typed E2O-structural equivalence, \(\equiv_T\).** Two executions are equivalent when object and event bijections preserve the lead-object designation, object types, externality flags, activity labels, E2O incidence, and event order. Here I deliberately exclude **all O2O facts** from this structural relation; a richer structural definition could include them.

This preserves object multiplicities, repeated activities, shared participation, and whether the same object reappears. It discards identifier spelling, O2O meaning, attributes, and durations. Identity, inverse, and composition of isomorphisms establish reflexivity, symmetry, and transitivity. With unresolved ties, compare block-ordered incidence graphs without imposing an arbitrary within-block sequence.

**Business-profile equivalence, \(\equiv_S\), my preferred relation.** Compare an identifier-invariant profile of item, delivery, invoice, and payment multiplicities; logistics and financial sharing; selected settlement qualifiers; and replacement/return motifs. Section 2 defines it precisely.

This deliberately ignores package count and packing-event count: X1 and X3 can therefore share an operational family while retaining different packaging subtypes. It also discards incidental ordering outside the selected motifs and most detailed incidence.

Equality of these profiles is reflexive, symmetric, and transitive. With uncertain event ordering, motif evidence should be encoded deterministically as **certain**, **possible**, or **not evidenced**, according to the admissible linearizations—not resolved differently for each comparison.

Equal timestamps alone do not establish physical concurrency. These are equivalences of observed representations, not claims that the underlying processes admit identical future behavior.

## 2. Canonical signatures

Use the preferred signature

$$
S(X)=(i,d,v,m,L,F,Q,R),
$$

where \(i\) counts non-external Item objects; \(d,v,m\) count distinct Delivery, Invoice, and Payment objects in scope. \(L,F\) indicate external participation in logistics and finance. \(Q\) records the supplied `partially_settles` and `completes_settlement` qualifiers.

\(R\) records two identity-sensitive motifs:

* **`sub`:** an item replaces another, the old item has `removed_before_dispatch`, and their package is subsequently dispatched.
* **`ret`:** the same item follows initial packing, dispatch, return, inspection, repacking into a different package, and dispatch through a different delivery.

Empty \(Q\) or \(R\) means **no selected evidence recorded**, not proof of full settlement or exception-free execution.

The following reference implementation accepts trusted event order. It uses cardinalities and relational joins, not identifier-based numbering.

```python
from itertools import combinations, product

def semantic_key(
    events: list[tuple[str, set[str]]],
    types: dict[str, str],
    links: set[tuple[str, str, str]],  # (source, qualifier, target)
) -> tuple:
    """Reference implementation for compact, totally ordered executions."""
    known = set(types)
    if any(not objs <= known for _, objs in events):
        raise ValueError("An event references an object without a type.")
    if any(s not in known or t not in known for s, _, t in links):
        raise ValueError("An O2O endpoint is outside the declared scope.")

    external = {o for o in known if str(o).startswith("EXT")}
    n = len(events)

    def objects_at(k, object_type):
        return {o for o in events[k][1] if types[o] == object_type}

    logistics_shared = (
        any(objs & external for act, objs in events
            if act in {"Pack Package", "Dispatch"})
        or any(types[s] == "Package" and q in {"packs", "repacks"}
               and types[t] == "Item" and t in external
               for s, q, t in links)
    )
    finance_shared = (
        any(objs & external for act, objs in events
            if act in {"Issue Invoice", "Record Payment"})
        or any(types[s] == "Invoice" and q == "bills"
               and types[t] == "Order" and t in external
               for s, q, t in links)
    )
    settlement = tuple(sorted({
        q for s, q, t in links
        if types[s] == "Payment" and types[t] == "Invoice"
        and q in {"partially_settles", "completes_settlement"}
    }))

    motifs = set()
    for new, q, old in links:
        if q != "replaces" or types[new] != "Item" or types[old] != "Item":
            continue
        for package, q2, removed in links:
            if (q2 != "removed_before_dispatch" or removed != old
                    or types[package] != "Package"):
                continue
            if any(
                {package, new, old} <= events[a][1]
                and package in events[b][1]
                for a, b in combinations(range(n), 2)
                if events[a][0] == "Pack Package"
                and events[b][0] == "Dispatch"
            ):
                motifs.add("sub")

    target = (
        "Pack Package", "Dispatch", "Return Item",
        "Inspect Return", "Pack Package", "Dispatch"
    )
    for indices in combinations(range(n), 6):
        if tuple(events[k][0] for k in indices) != target:
            continue
        a, b, c, d, e, f = indices
        same_item = (
            objects_at(a, "Item") & objects_at(c, "Item")
            & objects_at(d, "Item") & objects_at(e, "Item")
        )
        old_packages = objects_at(a, "Package") & objects_at(b, "Package")
        new_packages = objects_at(e, "Package") & objects_at(f, "Package")
        old_deliveries = objects_at(b, "Delivery") & objects_at(c, "Delivery")
        new_deliveries = objects_at(f, "Delivery")
        if (
            same_item
            and any(p != q for p, q in product(old_packages, new_packages))
            and any(p != q for p, q in product(old_deliveries, new_deliveries))
        ):
            motifs.add("ret")

    count = lambda t: sum(value == t for value in types.values())
    return (
        sum(t == "Item" and o not in external for o, t in types.items()),
        count("Delivery"), count("Invoice"), count("Payment"),
        int(logistics_shared), int(finance_shared),
        settlement, tuple(sorted(motifs)),
    )
```

Any type- and externality-preserving renaming preserves these joins and counts. The six-event enumeration is suitable for these compact examples; larger implementations should use indexed joins.

## 3. Cluster assignments

Let \(b=(2,1,1,1,0,0,\varnothing,\varnothing)\). Brackets below indicate substitutions into this signature; `partial` and `complete` abbreviate the settlement qualifiers.

| Execution | Activity-sequence cluster | Typed-structural cluster | Preferred semantic cluster | Defining signature                    | Main reason                                      |
| --------- | ------------------------- | ------------------------ | -------------------------- | ------------------------------------- | ------------------------------------------------ |
| X1        | A1                        | T1                       | S1                         | \(b\)                                 | Local, consolidated dispatch; one payment record |
| X2        | A1                        | T1                       | S1                         | \(b\)                                 | Identifier-renamed X1                            |
| X3        | A2                        | T2                       | S1                         | \(b\)                                 | Package splitting ignored at this semantic level |
| X4        | A3                        | T3                       | S2                         | \(b[d=2,m=2,Q=\{partial,complete\}]\) | Split deliveries and staged settlement           |
| X5        | A1                        | T4                       | S3                         | \(b[L=1]\)                            | Cross-order logistics sharing                    |
| X6        | A1                        | T5                       | S4                         | \(b[F=1]\)                            | Cross-order financial sharing                    |
| X7        | A1                        | T6                       | S5                         | \(b[R=\{sub\}]\)                      | Qualified substitution/removal                   |
| X8        | A4                        | T7                       | S6                         | \(b[d=2,R=\{ret\}]\)                  | Item-specific return and redispatch              |

Thus there are **four activity clusters, seven typed-structural clusters, and six preferred semantic clusters**. Although the preferred partition is coarser here, it is not universally coarser than \(\equiv_T\): its qualifiers can distinguish executions with identical E2O structures.

## 4. Cluster interpretations

**S1 — Local consolidated-dispatch family: \(b\); X1–X3.**
Two local item records feed one delivery, invoice, and payment record, without selected exception evidence. X3 retains a two-package subtype. Consolidation offers a coordination opportunity, but package-level tracking remains relevant. Order/activity flattening conceals X3’s packaging split; item flattening can duplicate shared work. This family is stable under redundant O2O completion and renaming, but not newly established sharing or exception evidence.

**S2 — Split delivery with staged settlement: \(d=2,m=2,Q=\{partial,complete\}\); X4.**
Separate packages are dispatched through separate deliveries; the second payment completes the recorded invoice settlement. This may represent legitimate staged fulfillment and payment—not necessarily delinquency. Coordination and reconciliation are the operational concerns. Order flattening shows repetition but obscures package–delivery and payment–invoice correspondence. The cluster is stable under redundant-link repairs; removing settlement qualifiers weakens its interpretation without erasing its multiplicities.

**S3 — Shared logistics, local billing: \(L=1\); X5.**
One package combines this Order’s items with another Order’s item, while the invoice bills only O5. Consolidation may save handling effort but creates cross-order tracking and cost-attribution dependencies. Separate Order traces duplicate shared Pack/Dispatch work and conceal the common package. The cluster survives repairs that preserve external participation; a local-only extraction destroys its defining evidence.

**S4 — Shared finance, local logistics: \(F=1\); X6.**
The invoice covers two Orders and is settled without order-level allocation. Invoice settlement therefore does not establish how payment should be attributed to O6. Consolidated billing is an opportunity; reconciliation ambiguity is the concern. Order flattening can misleadingly attribute the same payment independently to both Orders. Adding allocation data improves interpretation without changing this deliberately broad shared-finance cluster.

**S5 — Pre-dispatch substitution/removal: \(R=\{sub\}\); X7.**
Two Item objects are not simply two independently shipped items: I72 replaces I71, and I71 was removed before dispatch. Inventory, billing, and substitution traceability warrant attention, without assuming misconduct. Activity-only Order flattening makes this look ordinary. The cluster is stable under redundant incidence repairs, but sensitive to losing the replacement/removal qualifiers.

**S6 — Return, inspection, and item-specific repacking: \(d=2,R=\{ret\}\); X8.**
I82 returns and is repacked and redispatched; this is not merely a second initial shipment. The replacement-package relationship is scoped to I82, not automatically I81. Investigating handling or return causes is appropriate, but no cause is supplied. Package flattening separates the initial and recovery legs. The event-based motif survives redundant O2O repairs, but not loss of return events or corruption of item identity.

## 5. Borderline cases

**X1 versus X2.** All three proposed relations agree. An explicit isomorphism maps I11→I22 and I12→I21, preserving event positions. Literal record equality disagrees, which can be useful for provenance or duplicate-record detection—but is not a defensible business distinction here. Sorting identifier suffixes would impose an unjustified correspondence.

**X1 versus X5.** Activity equivalence merges them; full-scope typed and semantic equivalence separate them because X5 shares logistics with external objects. A deliberately local-only projection could merge them, but would answer a narrower question.

**X1 versus X6.** Their activity sequences and local multiplicities agree. A local workload profile can therefore merge them. The preferred relation separates financial sharing, because invoice-level settlement and order-level allocation are different observations.

**X1 versus X7.** Activity and object-count-only definitions can merge them. Qualified semantics separates substitution. Importantly, the specified typed relation also separates them: X7’s Dispatch has a direct Item incidence absent in X1. Qualifiers are not their only structural difference.

**X3 versus X4.** An item/package workload signature—two items, two packages—merges them. Delivery- and finance-aware definitions separate consolidated delivery from two deliveries with two payment objects. Packaging similarity does not imply equivalent coordination requirements.

**X4 versus X8.** A logistics-count signature—two items, two packages, two deliveries—merges them. Lifecycle-sensitive equivalence separates two initial shipment legs from return/recovery of the same item. Payment multiplicity also differs. Comparable handling counts need not imply comparable causes or customer experiences.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The inspected PM4Py implementation creates a nested tuple key of this form:

```text
(
  ((activity, related_object_id, ...), ...),
  ((object_id, object_type), ...)
)
```

It preserves ordered event occurrences, activity repetitions, E2O participation, and object identities/types **within the generated representation**. Events are ordered using timestamp, activity, and event identifier. The clustering call excludes timestamp values from the resulting description. 

The key does **not explicitly encode** O2O relations or qualifiers, E2O qualifier values, externality flags, the distinguished root, or monetary attributes. Consequently, key equality is not qualified business-semantic equality. 

There is an important correction to a purely “raw-ID” interpretation: the inspected wrapper **renames objects before generating keys**. Literal unrenamed identifiers would fragment X1/X2, but default PM4Py behavior is not simply literal-ID matching. Its renamer uses object type, first/last relation timestamps, and original identifiers as tie-breakers; that is not a general graph-isomorphism canonicalizer. 

I would recompute signatures for **every returned execution**, permitting both merges across keys and semantic splits inside a key. Exact structural equivalence is preferable for detailed variant diagnostics or regression tests when multiplicity and incidence differences matter; identifier-sensitive equality belongs mainly to provenance checking.

Extraction also matters: the inspected wrapper uses an ancestors/descendants splitter based on an object-interaction graph, rather than the direct-Order boundary defined above. Its `max_objs` limits the first lead objects processed, not neighborhood size or membership per cluster. Reachability is constructed before that limit is applied, so large shared neighborhoods can remain expensive. 

This outline uses returned root metadata but reconstructs the chosen boundary from the original OCEL, retaining external identifiers and qualifiers. It targets the inspected implementation; pin the version and verify coverage. 

```python
from collections import defaultdict
import pandas as pd
import pm4py

def order_view(log, lead):
    eid, oid = log.event_id_column, log.object_id_column
    act, ts = log.event_activity, log.event_timestamp
    ot, qual = log.object_type_column, log.qualifier

    # Keep all incidences of events directly associated with this lead.
    event_ids = set(log.relations.loc[
        log.relations[oid].eq(lead), eid
    ])
    relations = log.relations[log.relations[eid].isin(event_ids)]
    events = log.events[log.events[eid].isin(event_ids)].copy()

    if events.empty or events[ts].isna().any():
        raise ValueError("Missing events or timestamps.")

    sort_columns = [ts]
    if events[ts].duplicated().any():
        # A trusted source-order attribute, not an arbitrary ID tie-break.
        if ("source_order" not in events
                or events["source_order"].isna().any()
                or events.duplicated([ts, "source_order"]).any()):
            raise ValueError("Resolve tied order or use a partial-order adapter.")
        sort_columns.append("source_order")
    events = events.sort_values(sort_columns, kind="stable")

    incidence = relations.groupby(eid)[oid].agg(set).to_dict()
    object_ids = set(relations[oid])
    types = log.objects.loc[
        log.objects[oid].isin(object_ids)
    ].set_index(oid)[ot].to_dict()

    links = set()
    if log.o2o is not None and not log.o2o.empty:
        other = oid + "_2"
        selected = log.o2o[
            log.o2o[oid].isin(object_ids)
            & log.o2o[other].isin(object_ids)
        ]
        for source, q, target in selected[
            [oid, qual, other]
        ].itertuples(index=False, name=None):
            if pd.notna(q):
                links.add((source, q, target))

    ordered = [
        (activity, incidence[event_id])
        for event_id, activity in events[
            [eid, act]
        ].itertuples(index=False, name=None)
    ]
    return ordered, types, links


# Preconditions: validated IDs/types and chronologically ordered relations.
orders = ocel.objects.loc[
    ocel.objects[ocel.object_type_column].eq("Order"),
    ocel.object_id_column
].tolist()

raw_clusters = pm4py.cluster_equivalent_ocel(
    ocel, object_type="Order", max_objs=len(orders)
)

semantic_clusters = defaultdict(list)
seen = set()
for library_key, members in raw_clusters.items():
    for execution in members:  # Never inspect only one representative.
        lead = execution.parameters.get("@@central_object")
        if lead is None:
            raise RuntimeError("This PM4Py version needs a root-metadata adapter.")
        if str(lead).startswith("EXT") or lead in seen:
            continue
        key = semantic_key(*order_view(ocel, lead))
        semantic_clusters[key].append({
            "lead_order": lead,
            "library_key": library_key,
        })
        seen.add(lead)

intended = {o for o in orders if not str(o).startswith("EXT")}
if seen != intended:
    raise RuntimeError("Lead-Order extraction coverage is incomplete.")
```

## 7. Robustness analysis

**Ignore all O2O qualifiers.** S5/X7 joins S1 because its selected substitution evidence disappears; T6 remains distinct because of Dispatch’s Item incidence. X4 loses its staged-settlement annotation but remains separate through delivery/payment counts. X8’s event-based return motif survives, as do X5/X6’s sharing flags.

**Ignore external objects.** Delete their incidences and associated facts while retaining shared events. X5 and X6 join S1; they also become typed-equivalent to X1/X2 under the specified E2O relation. This is intentional information loss, not evidence that sharing never occurred.

**Collapse repeated same-label events.** Under adjacent-run compression, X3 joins A1 after its repeated packing labels collapse. For object-centric compression, merge incidences by union and retain objects and qualifiers: the preferred assignments remain unchanged. Dropping all but one event’s incidences would instead corrupt multiplicities.

**Use partial order for Pack/Dispatch.** Preserve same-package pack-before-dispatch dependencies and item-specific return dependencies, while allowing independent package operations to commute. A common Order incidence alone should not force serialization. Schedule variants of X4 may merge structurally, but none of these eight preferred assignments changes.

**Represent payment multiplicity through amounts.** No amounts are supplied, so equivalent totals cannot be established. Removing payment count alone still leaves X4 distinct through settlement qualifiers and its non-return, two-delivery profile. An amount-only view would nevertheless conceal settlement staging.

## 8. Limitations and recommendation

**Compliance monitoring:** use qualified, state- and order-sensitive structural signatures plus explicit control rules. Preserve allocation uncertainty and removal/replacement scope; do not interpret a coarse cluster as compliant.

**Operational segmentation:** use the six preferred families, retaining package count as a secondary workload subtype. This groups X1–X3 without concealing their packaging differences.

**Root-cause analysis:** retain fine E2O structure, qualified O2O facts, and lifecycle motifs, then add timing and resource evidence when available. Similar structures alone do not establish causes.

**Descriptive reporting:** use readable business families with explicit sharing and exception indicators; activity variants can be a supplementary view.

These eight examples do not establish population prevalence, physical delivery completion, or unrecorded payment amounts. **No single partition serves all four purposes:** detailed distinctions support audit and diagnosis, whereas selective abstraction makes segmentation and reporting useful.
