## 1. Analytical assumptions

**Case notion.** I treat a case as the chronologically ordered multiset of events that are *directly* E2O-related to one chosen object instance after flattening. The case identifier is that object’s ID. I do not treat “case” as a hidden ground-truth execution; it is an analytical projection that answers questions about that object type’s lifecycle.

**Convergence.** Convergence occurs when a single event is directly related to several objects of the flattening type (or is copied into several cases because the event’s E2O set contains multiple objects of that type). In the flattened log the same real-world event becomes multiple case-events. Classic examples here: e13 (related to O2 and O3), e16 (O1, O2, O3), e19 (O2, O3), e14 (O3, O4).

**Divergence.** Divergence occurs when one object of the case type is involved in several events of the same activity (or in interleaved sub-lifecycles of *other* object types), so the flattened trace shows repeated activity labels or artificial interleaving that does not correspond to a single sequential business step for that object. Example: O1 participates in two Pack Package events (e11, e12) and two Dispatch / Confirm Delivery pairs because it is split across P1/P2 and D1/D2.

**Copied shared events.** I treat them as **both** evidence and duplication:
- *Evidence* of true multi-object coordination (consolidation, batching, split fulfilment).
- *Duplication* with respect to frequency, performance, and DFG edge counts, because one timestamped fact is counted once per case that inherits it.

I therefore never read raw flattened frequencies as “how often the activity occurred in the world” without an explicit de-duplication step.

**Analytical transformations permitted.**
1. Direct-E2O flattening only (default, matches the table as given).
2. Optional *explicit* O2O propagation (e.g., attach an invoice event to items via Order–contains–Item and Invoice–bills–Order) — only when labelled as a separate scenario, never silently.
3. Event-identity tracking (retain original event ID so duplicated rows can be collapsed for frequency metrics).
4. No invention of events; no deletion of E2O links except in stated sensitivity checks.

## 3. Concrete distortion analysis

**D1 – Cross-order package P3 (Order flattening).**  
Affected flattening: Order.  
Events/objects: e13 relates to O2, O3, I21, I31, P3.  
Effect: Flattened cases O2 and O3 each receive a Pack Package event at 10:12. DFG edge Add Item  Pack Package is counted twice for one warehouse action; frequency of Pack Package becomes 2 instead of 1 for this fact. Variant mining may invent parallel “O2 packed” and “O3 packed” stories.  
Harmful for activity frequency and resource utilisation; informative if the analyst wants “orders touched by a pack act.”

**D2 – Cross-order package P4 (Order flattening).**  
Affected flattening: Order.  
Events/objects: e14 (O3,O4,I32,I41,P4), e17, e27.  
Effect: O3’s trace contains two Pack and two Dispatch/Confirm chains (P3/D2 and P4/D3). Apparent variant: PackPackDispatchDispatch, which looks like rework or loop, not multi-parcel fulfilment. Sojourn between first Pack and final Confirm mixes two independent parcels.  
Harmful for loop diagnostics and end-to-end duration; context-dependent useful signal that O3 is a split/merge order.

**D3 – Consolidated delivery D2 (Order & Item flattening).**  
Affected flattening: Order (also Item).  
Events/objects: e16, e24 related to O1,O2,O3 and I12,I21,I31,P2,P3,D2.  
Effect: One truck departure is copied into three order cases. DFG edge PackDispatch frequency inflated; average “dispatch waiting time” averages O1’s P2 leg with O2/O3’s P3 leg as if independent. On Item flattening, e16 appears in I12,I21,I31 — triple-counting transit performance.  
Harmful for capacity and on-time metrics; informative for “orders affected by consolidated route D2.”

**D4 – Consolidated invoicing V2 (Order flattening).**  
Affected flattening: Order.  
Events/objects: e19 (O2,O3,V2), e22, e25.  
Effect: Issue Invoice at 12:05 is duplicated in O2 and O3. Financial DFG shows two invoice issuances for one document. Order-level “time to invoice” is well-defined per order, but “number of invoices” is wrong.  
Harmful for document-count KPIs; acceptable for per-order billing latency.

**D5 – Partial payments on V2 (Order & Invoice flattening).**  
Affected flattening: Order (and Invoice as control).  
Events/objects: M2/e22 partially_settles V2; M3/e25 completes_settlement V2; both E2O-linked to O2 and O3.  
Effect: Both O2 and O3 traces show Record Payment  Record Payment. Looks like every co-billed order paid twice in full if activity labels are not qualified. Performance: “payment settlement time” from e19 to e25 is duplicated. On Invoice flattening the two-step settlement is *correct and informative* for V2.  
Context-dependent: distortion on Order, signal on Invoice.

**D6 – Near-singleton payment lifecycle (Payment flattening).**  
Affected flattening: Payment.  
Events/objects: M1e21 only; M2e22; M3e25; M4e26 (each payment object appears in essentially one event).  
Effect: Traces of length 1; DFG empty or trivial; log skeleton / variants meaningless; any “throughput time” is zero.  
Harmful if used as process lead; informative only as an event inventory of cash applications.

**D7 – O1 split across P1 and P2 (Order flattening divergence).**  
Affected flattening: Order.  
Events/objects: e11/e15/e23 (P1,D1) vs e12/e16/e24 (P2,D2).  
Effect: O1 trace: PackPackDispatchDispatch…ConfirmConfirm. Discovers false self-loops and exaggerates concurrency. Delivery confirmation e23 (14:00) and e24 (16:00) may be read as delayed second delivery rather than second parcel.  
Harmful for sham-loop removal and SLA calculation unless package sub-identifiers are retained as attributes.

**D8 – Lifecycle truncation on Delivery/Package (Delivery & Package flattening).**  
Affected flattening: Delivery (also Package).  
Events/objects: D1 = {e15,e23}; D2={e16,e24}; D3={e17,e27}.  
Effect: No Create Order, no Invoice, no Close. Process map collapses to DispatchConfirm. Upstream starvation and downstream cash cycle invisible. Comparing “median case duration” across object types would spuriously declare deliveries “faster” than orders.  
Harmful for E2E claims; informative strictly for transit-time distribution.

**D9 (extra) – Item flattening hides finance and close.**  
I11’s case ends at e23 Confirm Delivery; never sees e18/e21/e28. A compliance check “every item flow ends with paid invoice” is impossible on Item flattening without propagation.  
Harmful for audit questions; not a defect of the item view itself.

**D10 (extra) – Shared close timestamps O2/O3.**  
e29 and e30 both at 11:05 on O2 and O3. Not duplication of one event (two events), but may be batch closure. Order flattening preserves this; Package/Delivery flattening never see Close Order — silent loss of a control activity.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs still worth creating**
1. **Order** — primary traditional log for order-to-cash control flow, SLA, and variant analysis *with* convergence flags.
2. **Item** — secondary logistics log for line-level path and split-ship analysis.
3. **Invoice** — secondary finance log for issue-to-cash and instalment patterns (V2).
4. Package / Delivery / Payment — optional diagnostic extracts, not portfolio defaults.

**Questions each flattened log can answer safely**
- Order: per-order lead time CreateClose; which orders experienced split pack/dispatch (O1, O3); presence of multi-payment (O2, O3); close compliance (e28–e31).
- Item: physical path completeness AddConfirm for each of I11–I41; identify items on consolidated parcels (I21/I31 on P3; I32/I41 on P4).
- Invoice: settlement steps per bill; V2 instalment gap e22e25; bills per day.
- Package/Delivery: transit duration DispatchConfirm only (D1: e15e23; D2: e16e24; D3: e17e27).
- Payment: list of settlement events and partial vs complete qualifiers — not process structure.

**Questions that require object-centric artefacts**
- “Which orders co-shipped on D2?”  OC-DFG + OTG + objects-interactions summary (O1,O2,O3  D2 via P2,P3).
- “Does packing batch across orders cause invoice consolidation?”  ET–OT graph and interaction summary linking P3/P4 to V2.
- “True frequency of Pack Package / Dispatch”  OC-DFG event-based counts (e11–e14, e15–e17 counted once).
- “Are partial payments correlated with multi-order invoices?”  cluster_equivalent_ocel or interaction summary on Invoice–Payment–Order, not a single flat DFG.
- “Performance without double-counting D2”  OC-DFG performance with event identity, or Delivery flattening only for transit.

**Reconciling contradictions**
1. Always compare *event-level* OC-DFG frequencies with *case-level* flattened frequencies; the ratio approximates average convergence degree (e.g., Dispatch flattened count / OC-DFG count  average orders per dispatch).
2. When Order DFG shows PackPack loops, open the OTG/interactions: if loops coincide with multi-package E2O sets (O1–P1/P2, O3–P3/P4), classify as divergence from split fulfilment, not rework.
3. When finance KPIs disagree with logistics KPIs, align on shared timestamps (e.g., last Confirm Delivery vs Issue Invoice) using OC event table, not on case averages from different flattenings.
4. Document every metric as “per Order-case (with copies)” vs “per distinct event ID” vs “per Package object.”

## 5. Lead-object decision

**Position: C. Reject a single lead object for this process.**

**Decision criteria**
- Coverage of the business questions that span logistics *and* finance.
- Severity of convergence/divergence relative to object inventory size.
- Whether one type’s lifecycle is systematically truncated (near-singleton test).
- Whether consolidations (P3, P4, D2, V2) are first-class business facts rather than noise.

**Strongest supporting evidence**
- No object type touches all activity classes: Items/Packages/Deliveries miss Issue Invoice, Record Payment, Close Order; Invoices/Payments miss Create/Add/Pack; Orders see all *activities* but only via heavy convergence (e16 in three orders, V2 dual payments copied, P3/P4 cross-order packs).
- Business facts explicitly celebrate multi-object batching (P3, P4, D2, V2, M2+M3). A single lead type would either duplicate those facts into pseudo-loops or delete the co-objects that make them meaningful.
- Payment and Delivery fail the near-singleton test; Package is only three events deep — none can lead E2E.
- Order is the least-bad traditional case notion, yet D2 and V2 show that the economically real “case” sometimes *is* the consolidation set, not O2 or O3 alone.

**Strongest counterargument**
- Practitioners still need a case table for SLA dashboards; Order is the commercial anchor (CreateClose exists only on O1–O4), and many ERP extracts already key on order ID. Refusing a lead object may block adoption.

**Residual risk**
- Without a declared lead, teams may silently pick Order anyway and over-trust inflated Dispatch/Payment frequencies.
- Object-centric tooling maturity and audience literacy vary; pure OC views can under-communicate simple per-order lead times.

**Conditions that would change the decision**
- If the analytical mandate were strictly “order SLA and closure compliance,” switch to **B** with Order primary and Invoice/Item secondary.
- If the mandate were “parcel network utilisation only,” Package or Delivery could become primary inside a logistics sub-scope.
- If O2O propagation plus event-identity de-duplication were productionalised so that Order flattening reports both case-level and distinct-event metrics by default, **B** (Order primary) becomes defensible for a wider E2E scope.
- If new event types bound payments/invoices directly and exclusively to a single commercial object with no consolidations, a single lead might reappear.

import pm4py
from pm4py.visualization.ocel.ocdfg import visualizer as ocdfg_vis
from pm4py.visualization.ocel.otg import visualizer as otg_vis

    "Order": flat_order,
    "Item": flat_item,

    "Delivery": flat_delivery,
    "Invoice": flat_invoice,
    "Payment": flat_payment,
}

# --- 3. Classical DFG + log skeleton per flattening (capture distortion, do not 'trust' visually) ---

## 7. Sensitivity and validation plan

**S1 – Remove or down-weight copied shared events.**  
Build a frequency table keyed by original event ID. For Order flattening, count e13, e14, e16, e17, e19, e22, e24, e25, e27 once when reporting activity frequencies and DFG edge weights, while retaining copies only for per-case enablement. Recompute the convergence_proxy from §6. Accept Order-level DFG only if qualitative topology (not weights) is stable after de-duplication. Flag edges whose weight drops by factor 2 (expected: Dispatch, Confirm Delivery, Issue Invoice, Record Payment).

**S2 – Direct E2O vs explicit O2O propagation.**  
Variant A: relations as given. Variant B: propagate, e.g., Invoice events to Items through billscontains; Payment events to Orders already present but extend Payments to Packages via settlesbills… only for a labelled experiment. Re-flatten on Item and Package under Variant B. Validate that new Item traces gain e18–e26–e28-type events only when the chain is real (I11O1V1M1), and that no false link assigns V2 to I11. Compare trace lengths and false-positive finance completions.

**S3 – Change the putative lead object.**  
Repeat the full DFG + skeleton + lead-time dashboard under Order, Item, and Invoice leads. Checklist:
- Does Item lead still “see” unpaid V2 instalments? (No under direct E2O — documents coverage failure.)
- Does Invoice lead show O1’s split ship? (No — documents logistics failure.)
- Do rank-orders of “slowest cases” agree on O3 (multi-parcel + dual payment + dual delivery confirm e24 and e27)? Disagreement is expected and must be reported as view-dependence, not data error.

**S4 – Frequency metrics: events vs unique objects vs total object participations (OC-DFG).**  
For each activity (especially Pack Package, Dispatch, Record Payment):
- *Event count*: |{e11,e12,e13,e14}| = 4 packs; |{e15,e16,e17}| = 3 dispatches; |{e21,e22,e25,e26}| = 4 payments.
- *Unique objects of type T touched*.
- *Total E2O participations* (sum of related objects per event).  
Require that any published KPI states which denominator was used. Validate that consolidated facts move metrics predictably: e16 contributes 1 event, 3 orders, 3 items, 2 packages, 1 delivery.

**S5 (additional) – Lifecycle-length stress test.**  
Exclude object types whose median flattened trace length is 2 (Payment, Delivery) from any E2E claim. For Package (length 3), allow only transit KPIs. Confirm with the inventory: M1–M4 singleton behaviour; D1–D3 two-event behaviour.

**S6 (additional) – Business-fact recovery test.**  
After each view, ask whether an analyst can recover the six stated business facts solely from that view’s DFG/variants. Order flattening recovers splits and dual payments but over-counts; Invoice recovers V2 instalments; only OC interaction summary cleanly recovers “D2 consolidates P2 and P3 thereby involving three orders” without pseudo-loops. A view that cannot state those facts without external knowledge fails the validation gate for E2E reporting.
