# 1. Policy Interpretation and Conflict Resolution

**Material Assumptions**
- Timestamps are relative to case start in hours; PM4Py expects seconds for temporal checks.
- Resource names are extracted from the `[resource]` bracket notation.
- Case boundaries are implicit per test case string; no explicit case ID is provided.
- The event log contains only activity name, timestamp, and resource. No case-level attributes (e.g., risk score, emergency flag) are available.
- `zeta = 2.0` defines the statistical threshold for temporal deviations (mean ± 2).

**R5 vs R6 Conflict**
- **R5 (Legal):** After `Sanctions Escalation`, `Obtain Legal Opinion` must precede `Activate Vendor` under all circumstances.
- **R6 (Operations):** Emergency activation may occur before `Obtain Legal Opinion`, but only when jointly authorized outside the log; the opinion must arrive within 24 hours. The log lacks an emergency attribute.

**Two Possible Resolutions**
1. **Strict Control-Flow (R5 Authoritative):** Enforce `Obtain Legal Opinion`  `Activate Vendor` precedence in the procedural/DECLARE layer. R6 is treated as an out-of-band exception requiring manual override and post-hoc audit. The model flags any activation before the opinion as a hard violation.
2. **Flexible/Exception-Aware (R6 Authoritative):** Relax the strict precedence in the control-flow layer. Replace it with a temporal bound (24h) and a resource/data check that flags activations preceding the opinion for compliance review. The model treats the sequence as valid if the 24h bound holds.

**Chosen Resolution & Compliance Risk**
I implement **Resolution 1 (Strict Control-Flow)** as the authoritative model. R5 is enforced in the procedural backbone and DECLARE layer. R6 is handled via an explicit resource/temporal validation layer that detects the pattern, checks the 24h bound, and surfaces a `policy-dependent` flag rather than a hard fail.
*Compliance Risk:* Blocking legitimate emergencies in the control-flow layer may delay critical operations. However, silently allowing precedence violations weakens auditability. The chosen approach preserves strict conformance by default while providing a structured exception path for auditors, minimizing regulatory exposure.

)

sanct_esc = apply_leaf("Sanctions Escalation")

recv_clar = apply_leaf("Receive Clarification")

comp_app = apply_leaf("Compliance Approval")
activate = apply_leaf("Activate Vendor")
release = apply_leaf("Release First Payment")
close = apply_leaf("Close Onboarding")

# Parallel block
par_block = apply_parallel(cap_master, ver_bank)
par_block = apply_sequence(par_block, run_sanct)
par_block = apply_optional(par_block, apply_leaf("Sanctions Escalation")) # Approximation

# Clarification loop (approximated as optional sequence)
clar_loop = apply_sequence(req_clar, recv_clar)
clar_loop = apply_optional(clar_loop, apply_leaf("Skip Clarification"))

# Low-risk route
low_route = apply_sequence(mgr_app, activate, release, close)

# High-risk route
high_route = apply_sequence(edd, comp_app, activate, release, close)

# Risk choice
risk_choice = apply_xor(reject, low_route, high_route)

# Full backbone
procedural_model = apply_sequence(recv_req, par_block, clar_loop, classify, risk_choice)
```

- **Choices:** `apply_xor` enforces mutual exclusivity between rejection, low-risk, and high-risk paths.
- **Clarification Loops:** Approximated as an optional `RequestReceive` sequence. True arbitrary cycles are better handled in DECLARE (R3).
- **Terminal Outcomes:** `Reject` and `Activate` are in separate XOR branches, guaranteeing R1 structurally.
- **Post-Activation:** Deliberately excluded. R11's conditional flow breaks block-structured assumptions; it is enforced via DECLARE response chains instead.

temporal_profile = {

    ("Activate Vendor", "Release First Payment"): (72 * 3600, 36 * 3600)
}
zeta = 2.0
```

**Why Warnings Rather Than Violations?**
Temporal expectations reflect operational norms, not hard control-flow constraints. Business processes naturally exhibit variance due to workload, holidays, or data quality. Using `zeta=2.0` flags statistically significant deviations (>95% confidence) for review without blocking valid cases. This separates *compliance* (must/should not) from *performance* (should take ~X), preventing false negatives on legitimate edge cases.

# 7. Resource- and Data-Aware Checks

```python
import pandas as pd
import pm4py

def check_resource_segregation(log_df):
    """R9: Segregation of duties. Verify Bank != Approval; Capture Master != Activate."""
    violations = []
    # Group by case (assumes 'concept:name' and 'time:timestamp', 'organizational:resource')
    for case_id, case_df in log_df.groupby("concept:case_id"):
        resources = case_df.set_index("concept:name")["organizational:resource"].to_dict()
        
        # R9a: Verify Bank Account resource != applicable approval resource
        if "Verify Bank Account" in resources:
            ver_res = resources["Verify Bank Account"]
            approvals = ["Manager Approval", "Compliance Approval"]
            for app in approvals:
                if app in resources and resources[app] == ver_res:
                    violations.append(f"Case {case_id}: R9a violated (Verify Bank == {app})")
                    
        # R9b: Capture Master Data resource != Activate Vendor resource
        if "Capture Master Data" in resources and "Activate Vendor" in resources:
            if resources["Capture Master Data"] == resources["Activate Vendor"]:
                violations.append(f"Case {case_id}: R9b violated (Capture Master == Activate)")
    return violations

def check_emergency_policy(log_df):
    """R6: Emergency activation before Legal Opinion within 24h."""
    flags = []
    for case_id, case_df in log_df.groupby("concept:case_id"):
        events = case_df.sort_values("time:timestamp")
        times = events.set_index("concept:name")["time:timestamp"].to_dict()
        
        if "Activate Vendor" in times and "Obtain Legal Opinion" in times:
            t_act = times["Activate Vendor"]
            t_leg = times["Obtain Legal Opinion"]
            if t_act < t_leg:
                diff_hours = (t_leg - t_act).total_seconds() / 3600
                if diff_hours <= 24:
                    flags.append(f"Case {case_id}: Emergency activation detected (diff={diff_hours:.1f}h). Policy-dependent.")
                else:
                    flags.append(f"Case {case_id}: Emergency activation EXCEEDED 24h bound (diff={diff_hours:.1f}h). FAIL.")
    return flags
```

**Required Attributes & Missing Data Handling**
- Required: `concept:name`, `time:timestamp` (datetime), `organizational:resource`, `concept:case_id`.
- If `organizational:resource` is missing, the SOD check skips the case and logs a `data_quality_warning`. If timestamps are missing, temporal checks are deferred. The model assumes a pre-processing step that imputes or flags incomplete traces.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated Enforcement:** R1 and R8 are enforced in Procedural (XOR), DECLARE (`noncoexistence`), and Log Skeleton (`never_together`). This redundancy improves robustness but increases maintenance burden. The procedural layer is authoritative; others act as fast-filters.
- **Loop/Post-Activation Inconsistencies:** R11's conditional flow (`Change Bank  Suspend  Verify  Release`) is modeled as unconditional `response` chains in DECLARE. If `Change Bank` never occurs, the rules are vacuously true. If it occurs pre-activation, the model may incorrectly flag valid traces. This is a known limitation of declarative approximations of conditional control flow.
- **Vacuity in Declarative Rules:** `existence` bounds for `Activate`/`Reject` are `[0,1]`. In rejected cases, `Activate` count is 0, which satisfies the rule. This is correct but masks the fact that the rule doesn't enforce *mutual exclusivity* by itself (requires `noncoexistence`).
- **Missing Case Attributes:** R6's emergency condition and R2's context-dependence rely on metadata absent from the log. Activity-only formalisms must approximate or defer to external checks, creating a gap between model and policy.
- **Timestamp-Only Limitations:** Temporal profiles assume monotonic, accurate clocks. Clock drift, timezone mismatches, or missing timestamps break `zeta` calculations. The model treats temporal deviations as soft warnings to mitigate this.
- **Support/Confidence Metadata Risk:** Setting `support=1.0` and `confidence=0.95` uniformly implies all rules are equally certain and universally observed. In reality, R11 and R6 have lower empirical support. Treating confidence as normative truth can lead to over-penalizing valid process variants. Confidence should reflect historical adherence, not policy strictness.

# 10. Deployment Recommendation

**Canonical Procedural Representation:** The ProcessTree (`procedural_model`) serves as the canonical control-flow specification. It is block-structured, executable, and aligns with the stable backbone.

**Authoritative Policy Layer:** The procedural model + resource/data validation layer are authoritative. DECLARE and Log Skeleton serve as complementary conformance filters and audit trails. Temporal profiles are advisory.

**Conformance Check Execution Order:**
1. **Procedural Conformance:** Fast structural validation. Rejects traces violating backbone or XOR branches.
2. **Log Skeleton & DECLARE:** Parallel declarative checks. Catches cardinality, mutual exclusion, and response obligations.
3. **Temporal Profile:** Statistical deviation scan. Flags outliers for review.
4. **Resource/Data Layer:** SOD and emergency policy checks. Requires full attribute enrichment.

**Handling Contradictory Findings:**
When layers disagree (e.g., T6 fails procedural but passes resource/temporal), the system surfaces a `policy-dependent` status in the compliance dashboard. It presents:
- The violated rule (R5 precedence)
- The exception condition met (R6 24h bound)
- Recommended action: Route to compliance officer for manual adjudication and case attribute tagging (`emergency_override=true`).
This ensures strict default conformance while providing a transparent, auditable exception workflow.
