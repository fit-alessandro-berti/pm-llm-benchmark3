## 1. Analytical assumptions
A case notion is the sequence of events directly linked to instances of one chosen object type, treated as a trace. Convergence occurs when one event is related to multiple objects of the chosen type, so flattening copies the event into each of those traces and inflates frequencies. Divergence occurs when one object participates in only a narrow subset of activities, truncating its apparent lifecycle. Copied shared events are treated as duplication that produces measurable frequency inflation and spurious DFG edges; they are retained for completeness but never interpreted as genuine parallelism without an accompanying object-interaction summary. No automatic propagation of E2O relations through O2O links is performed; any such propagation is applied only as an explicit analytical variant whose results are compared against the direct-E2O baseline.

## 3. Concrete distortion analysis
Flattening on Order copies e16 three times (O1,O2,O3), creating a spurious DFG edge Create OrderDispatch that never existed for O2 or O3 individually; the effect is harmful for frequency-based variant mining.  
Flattening on Order copies e13, producing an artificial PackageDispatch edge for O2 that actually belongs only to P3; this inflates the apparent speed of O2 and is harmful.  
Flattening on Delivery for D2 copies e16 and e24, attributing the same 5-minute dispatch-to-confirmation interval to O1,O2,O3 simultaneously; the resulting performance bias is context-dependent and informative only when an object-interaction summary is inspected.  
Flattening on Invoice for V2 copies e19, e22 and e25; the DFG shows two Record Payment activities after a single Issue Invoice, creating an apparent loop that is informative about partial settlement but harmful if counted as two separate invoices.  
Flattening on Payment yields a near-singleton lifecycle for M1 (only e21), truncating any preceding activities; the resulting empty DFG is harmful and signals that Payment is unsuitable as lead object.  
Flattening on Package for P3 copies e13 into both O2 and O3 traces, duplicating the Pack Package activity and distorting the measured packing duration for both orders; the effect is harmful.  
Flattening on Item for I21 produces a four-event trace (e07,e13,e16,e24) that omits all invoice events, truncating the lifecycle and hiding the V2 settlement; the distortion is harmful for financial KPIs.  
Flattening on Order for O3 copies e14, e17 and e27, making O3 appear in three separate deliveries; the resulting variant count inflation is harmful for process-discovery algorithms.

## 4. Traditional versus object-centric analysis portfolio
Flattened logs should be created only for Order and Invoice. The Order flattening safely answers “what is the median time from Create Order to Close Order per order?” because all order-specific events remain intact. The Invoice flattening safely answers “what fraction of invoices are paid in multiple instalments?” because the M2/M3 split is native to V2. All other questions—package consolidation, multi-order delivery timing, and cross-object synchronisation—require an OC-DFG (pm4py.discover_ocdfg), an OTG (pm4py.discover_otg), an ET–OT graph (pm4py.discover_etot), and an object-interaction summary. Contradictory findings are reconciled by comparing the object-interaction summary counts against the duplicated event counts in each flattening; any edge whose support exceeds the number of distinct objects involved is flagged as an artefact.

## 5. Lead-object decision
C. Reject a single lead object for this process.  
Decision criteria: presence of systematic cross-object events (e13, e16, e19) whose duplication would systematically distort frequencies and performance. Strongest supporting evidence is the set of events e13, e16, e19, e24 that each relate to three or more objects of different types, guaranteeing convergence on any chosen lead. Strongest counterargument is that Order still yields the longest traces and preserves the Close Order milestone. Residual risk is that analysts will nevertheless default to Order flattening and publish inflated frequencies. The decision is changed only if the OCEL is filtered to a single-order subset in which no event relates to more than one Order.
