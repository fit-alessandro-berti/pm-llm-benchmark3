## 2. Raw-versus-normalized interpretation

The raw/mapped fitness gap shows that the old normative model stopped recognizing post-migration labels and technical duplicates, not necessarily that work changed. In March-April raw fitness collapses from ~0.93 to ~0.51-0.55, while mapped fitness remains ~0.90-0.91 and normalized DFG rates are almost unchanged. Thus the gap identifies semantic/provenance drift: `Eligibility Screen` is a renamed `Validate Eligibility`, and duplicated `Open Case` events are technical noise. However, successful mapping recovers conformance only under the assumption that the mapping is valid and complete. It cannot prove the business process remained unchanged because mapping can hide altered decision logic, omitted substeps, or new workarounds that still align after normalization. Duplicated technical events distort DFG edges, variant discovery, and case counts if not removed, but have little direct business meaning. Missing resource identifiers undermine workload, handoff, and accountability analyses, while leaving control-flow conformance mostly intact if resources are not modelled. After May, the drift cannot be dismissed as logging alone: mapped fitness still declines modestly, normalized rework edges double, rework variants rise with Supplier Z share, and cycle-time/p90 deterioration is driven more by queue waiting than by label changes. These are behavioral and performance signals, not merely semantic noise.

The primary monitoring population should be **standard-complexity, non-Supplier Z cases after label normalization and technical duplicate removal**, monitored alongside separate high-risk segments. This segment is the most stable reference population because it is less exposed to the known supplier disruption and less affected by seasonal high-complexity mix. It therefore makes it easier to detect internal control-flow, queueing, priority, and logging changes. Supplier Z and high-complexity cases should not be ignored; they should be monitored as separate segments because they are likely to drift earlier and for different reasons.

Seasonality should be handled by using separate baselines for renewal and non-renewal periods, or by decomposing series into trend, seasonal, and residual components and alerting on residuals rather than raw levels. High-complexity and Supplier Z segments should have their own baselines because their normal behavior differs. Multiple testing should be controlled hierarchically: first alert on a primary monitor, then require a corroborating diagnostic metric or persistence over two consecutive periods before opening an operational incident. For exploratory monthly reviews, a false discovery rate control such as Benjamini-Hochberg can be applied across monitor statistics, but operational alerts should rely on severity, persistence, and segment-specific business impact rather than a single universal threshold.

    contrib = sorted(zip(relations, diff), key=lambda x: abs(x[1]), reverse=True)
    top = "; ".join(
        f"{name}:{delta:+.0f}"
        for name, delta in contrib[:3]
        if abs(delta) > 0
    )
    return pd.Series(
        {
            "euclidean_distance": euclidean,
            "manhattan_distance": manhattan,
            "top_edge_contributions": top or "none",
        }
    )

def compute_monthly_dfgs(log, variant: str = "performance", noise_threshold: float = 0.0):
    """
    Compute one DFG per calendar month from a PM4Py-compatible event log.
    """
    import pm4py

    df = pm4py.convert_to_dataframe(log).copy()
    df["_month"] = (
        pd.to_datetime(df[TIME_KEY], utc=True)
        .dt.tz_convert(None)
        .dt.to_period("M")
    )

    result = {}
    for month, group in df.groupby("_month"):
        group = group.drop(columns=["_month"])
        month_log = pm4py.format_dataframe(
            group,
            case_id=CASE_KEY,
            activity_key=ACT_KEY,
            timestamp_key=TIME_KEY,
        )
        dfg, start_activities, end_activities = pm4py.discover_dfg(
            month_log,
            variant=variant,
            noise_threshold=noise_threshold,
        )
        result[str(month)] = {
            "dfg": dfg,
            "start_activities": start_activities,
            "end_activities": end_activities,
        }

    return result

def normalize_labels_and_remove_technical_duplicates(
    log,
    label_mapping: dict,
    technical_activity: str | None = "Open Case",
):
    """
    Create a normalized copy of the log without overwriting the original input.

    - Maps raw activity labels to normalized labels.
    - Optionally removes duplicated technical events within the same case.
    - Returns raw dataframe, normalized dataframe, normalized log, and mapping summary.
    """
    import pm4py

    raw_df = pm4py.convert_to_dataframe(log).copy()
    normalized_df = raw_df.copy()

    normalized_df["activity_raw"] = normalized_df[ACT_KEY]
    normalized_df[ACT_KEY] = normalized_df["activity_raw"].map(
        lambda a: label_mapping.get(a, a)
    )

    if technical_activity:
        is_technical = normalized_df[ACT_KEY] == technical_activity
        duplicated_technical = is_technical & normalized_df.duplicated(
            subset=[CASE_KEY, ACT_KEY],
            keep="first",
        )
        normalized_df = normalized_df.loc[~duplicated_technical].copy()

    normalized_log = pm4py.format_dataframe(
        normalized_df,
        case_id=CASE_KEY,
        activity_key=ACT_KEY,
        timestamp_key=TIME_KEY,
    )

    mapping_summary = (
        normalized_df.groupby(["activity_raw", ACT_KEY])
        .size()
        .reset_index(name="events")
        .sort_values("events", ascending=False)
    )

    return {
        "raw_dataframe": raw_df,
        "normalized_dataframe": normalized_df,
        "normalized_log": normalized_log,
        "mapping_summary": mapping_summary,
    }


def compare_raw_and_normalized_dfg(
    log,
    label_mapping: dict,
    technical_activity: str | None = "Open Case",
):
    """
    Compare raw and normalized DFGs after label mapping and technical duplicate removal.
    """
    import pm4py

    raw_dfg, raw_start, raw_end = pm4py.discover_dfg(log, variant="performance")

    normalized = normalize_labels_and_remove_technical_duplicates(
        log,
        label_mapping=label_mapping,
        technical_activity=technical_activity,
    )

    norm_dfg, norm_start, norm_end = pm4py.discover_dfg(
        normalized["normalized_log"],
        variant="performance",
    )

    return {
        "raw_dfg": raw_dfg,
        "raw_start_activities": raw_start,
        "raw_end_activities": raw_end,
        "normalized_dfg": norm_dfg,
        "normalized_start_activities": norm_start,
        "normalized_end_activities": norm_end,
        "mapping_summary": normalized["mapping_summary"],
    }

## 9. Provisional attribution

Strongest conclusion: the March raw-fitness collapse is logging/semantic drift caused by migration. The gap between raw and mapped fitness, new labels, duplicated `Open Case`, missing resources, and stable mapped DFG/cycle times make this high confidence (>85%). It does not imply the underlying eligibility screen was unchanged, but the evidence favors renaming/technical duplication over behavioral change.

Second strongest: the May–September increase in rework is supplier-driven, with medium-high confidence (~70%). Supplier Z share jumps from ~15% to >40%, `Assess -> Request Info` and `Request Info -> Collect Documents` double, rework variants rise, and September recovery partially reverses the pattern. The main caveat is that Supplier Z cases were already more complex and regionally concentrated, so case mix mediates part of the effect.

Third: staffing cuts and queue capacity explain much of the June–August performance deterioration, but confidence is moderate (~60%). Median and p90 cycle times rise after 2026-06-15, reconstructed queue waiting increases far more than `Assess` service time, and capacity was not replaced. The attribution is confounded by ongoing supplier rework and the July priority rule.

The July priority rule likely redistributed waiting rather than creating all of it: high-complexity cases may have shorter queues while standard cases absorb delay. This is plausible but not directly proven because aggregate data hide priority-class waiting.

October–November deterioration is best attributed to seasonal population drift plus residual resource constraints, with medium confidence. High-complexity share and volume peak, `Senior Assessment` visibility increases, and p90 cycle times reach the highest levels. Some of the senior assessment increase may be real routing; some may be improved recording.

December improvement is weakly attributable to overtime/document-quality campaign and supplier recovery, but seasonal de-escalation is a competing explanation.

I would revise these accounts if supplier-stratified rework did not differ, if priority-class waiting did not diverge after July, if mapped fitness decline vanished after complexity adjustment, or if missing resource identifiers were found to alter case reconstruction.

## 10. Monitoring decision rules

1. IF raw fitness drops sharply while mapped fitness and normalized DFG remain stable, with new labels, duplicated technical events, or missing resources, THEN apply or extend label mapping and suppress raw-label conformance alerts, BECAUSE the signal is primarily logging/semantic drift rather than operational process change.

2. IF mapped fitness declines and `Assess -> Request Info` / `Request Info -> Collect Documents` rates rise, especially in Supplier Z cases, THEN audit Supplier Z bundle completeness, API payload quality, and document rejection reasons, BECAUSE incomplete supplier documents generate rework loops.

3. IF queue waiting before `Assess` increases while `Assess` service time remains stable, THEN review assessor capacity, WIP limits, and backfill needs, BECAUSE staffing loss creates queueing delay rather than slower individual assessment work.

4. IF high-complexity waiting falls or stays stable while standard-complexity waiting and p90 cycle time rise after the priority rule, THEN recalibrate priority thresholds and protect standard-queue capacity, BECAUSE priority rules can redistribute delay instead of reducing total delay.

5. IF high-complexity share and volume rise in renewal season beyond the seasonal forecast, THEN activate seasonal staffing, overtime, or pre-screening of complex renewals, BECAUSE seasonal population drift increases both demand and processing difficulty.

6. IF `Senior Assessment` rates increase without a corresponding increase in high-complexity share or without changed outcomes, THEN audit senior assessment recording and routing policy, BECAUSE the apparent behavioral change may be semantic/recording drift from historically inconsistent labeling.

7. IF cycle time and rework improve after December-style interventions while seasonal load also falls, THEN retain segment-specific monitors and avoid declaring a permanent fix until a post-season baseline is observed, BECAUSE seasonal de-escalation and interventions are confounded.
