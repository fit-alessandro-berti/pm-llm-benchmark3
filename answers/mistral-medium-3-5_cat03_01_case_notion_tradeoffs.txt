## 1. Analytical assumptions

- **Case notion**: A *case* is a sequence of events and objects that collectively represent a meaningful unit of analysis for a specific business question. In OCEL, a case is not pre-defined but emerges from the choice of *lead object type* (e.g., Order, Package) and the flattening strategy. A case notion is *convergent* when multiple object lifecycles are merged into one (e.g., flattening on Delivery merges Orders), and *divergent* when one lifecycle is split across multiple cases (e.g., flattening on Item splits Order O1 into I11 and I12).

- **Copied shared events**: When flattening on an object type, events related to *any* object of that type are copied into the flattened trace for *each* such object. We treat these as **both evidence and duplication**:
  - *Evidence*: They preserve the full event context for the chosen object type (e.g., flattening on Order retains all events for O1, including those involving I11, P1, D1).
  - *Duplication*: They inflate event counts and may create artificial dependencies (e.g., e16 appears in traces for O1, O2, and O3 when flattening on Order, even though it is a single dispatch event).

- **Analytical transformations**: We permit **explicit propagation of O2O relations** (e.g., inferring that P3 is related to O2 and O3 via `packs` and `contains` relations) but only when:
  - The propagation is declared as a transformation (not silent).
  - It is used to answer a specific question (e.g., "Which Orders are in P3?").
  - We do not propagate relations transitively beyond one step unless justified (e.g., we do not infer that D2 is related to O1 via P2  O1 unless explicitly modeling delivery-order links).

## 3. Concrete distortion analysis

1. **Flattening: Package**
   - **Affected objects/events**: P3 (e13, e16, e24), O2, O3, I21, I31
   - **Distortion**: DFG edge `Pack Package (e13)  Dispatch (e16)` appears in P3’s trace, but e16 involves P2/P3/D2. The edge suggests P3 is dispatched alone, but it is **co-dispatched with P2** (D2). This inflates the frequency of `Pack Package  Dispatch` and hides that P3’s dispatch depends on P2’s readiness.
   - **Effect**: **Harmful** for logistics analysis; masks cross-order dependencies.

2. **Flattening: Package**
   - **Affected objects/events**: P4 (e14, e17, e27), O3, O4, I32, I41
   - **Distortion**: P4’s trace includes `Pack Package (e14)  Confirm Delivery (e27)`, but e27 confirms delivery for **both O3 and O4**. The DFG implies P4’s delivery is independent, but it is **shared with P3** (D2) and P4 (D3). Performance metrics (e.g., delivery time) for P4 would include O3/O4’s delays.
   - **Effect**: **Context-dependent**; useful for P4’s lifecycle but misleading for order-specific SLAs.

3. **Flattening: Delivery**
   - **Affected objects/events**: D2 (e16, e24), O1, O2, O3, P2, P3, I12, I21, I31
   - **Distortion**: D2’s flattened trace includes all events for O1/O2/O3, creating a **monolithic DFG** where `Dispatch (e16)  Confirm Delivery (e24)` appears as a single path. This hides that:
     - O1’s items (I12) are in P2, O2/O3’s items (I21/I31) are in P3.
     - P2 and P3 may have different packing times (e12 vs. e13).
   - **Effect**: **Harmful** for order-level performance; averages out order-specific bottlenecks.

4. **Flattening: Invoice**

### Flattened logs to create:

## 5. Lead-object decision

**Position: B. Use a primary lead object plus explicitly secondary lifecycles.**

### Decision criteria:
1. **Business relevance**: The primary lead object should align with the most critical KPIs (e.g., order fulfillment time, revenue recognition).
2. **Minimal distortion**: The lead object should minimize convergence/divergence risks for the primary questions.
3. **Complementarity**: Secondary lifecycles should cover gaps in the primary view (e.g., packaging for logistics, invoicing for finance).

### Strongest supporting evidence:
- **Order as primary**:
  - Preserves the **end-to-end order lifecycle** (e01–e31), which is central to fulfillment.
  - Captures **invoice/payment links** (V1–M1, V2–M2/M3, V3–M4), critical for revenue tracking.
  - Avoids extreme convergence (unlike Delivery) or divergence (unlike Item).
- **Package and Invoice as secondary**:
  - **Package**: Explains cross-order batching (P3, P4) and its impact on delivery times.
  - **Invoice**: Clarifies partial payments (V2/M2/M3) and their effect on order closure.

### Strongest counterargument:
- **Order flattening duplicates shared events** (e16, e19, e22, e24), inflating DFG edge frequencies and performance metrics. For example, `Dispatch  Confirm Delivery` appears in O1, O2, and O3 traces, but only one physical dispatch (D2) occurred.

### Residual risk:
- **Performance metrics** (e.g., average order duration) may include time spent waiting for other Orders in shared events (e.g., O1’s closure (e28) is delayed by D2’s batching of O2/O3).
- **Mitigation**: Use **OC-DFG** to filter events by direct object participation (e.g., only events where O1 is the *primary* object).

### Conditions to change decision:
- If the focus shifts to **logistics optimization**, promote **Package** to primary and demote Order to secondary.
- If **cash flow** becomes the priority, promote **Invoice** to primary.
