## 1. Interaction-graph description

Typed interaction graph nodes: Job {J1…J6}, Component {C1…C6}, ComponentLot {L7,L8}, Machine {CNC-2,OVEN-1,TEST-1}, Tool {FIX-A,RACK-7,CAL-3}, Batch {B1,B2}, Shipment {S1,S2,S3}.

Important edge types/qualifiers (from O2O and timing):
- Job —requires Component (direct)
- ComponentLot —contains Component (direct)
- Batch —batches Job (direct)
- Shipment —consolidates Job (direct)
- Job —uses/acquires Tool (mixed: FIX-A acquire/release observed; RACK-7 and CAL-3 partly inferred from co-occurrence with batch/test events)
- Job/Batch —processed_on Machine (direct via events)
- ComponentLot —quarantines/releases (affects) Job (inferred linkage; events relate to lot+components+jobs but Job-flattening omitted them)
- Tool —constrains Machine usability (inferred: FIX-A for CNC-2 work on J4; RACK-7 for OVEN-1 batches; CAL-3 for every TEST-1 Final Test)

Higher-order motifs (3 object types):
1. Batch–Tool–Machine–Jobs: B1/B2 + RACK-7 + OVEN-1 + {J1,J2,J3}/{J4,J5} — synchronization barrier gated by shared rack state.
2. Job–Tool–Machine–Job: J3 + FIX-A + CNC-2 + J4 — exclusive tool hold creates cross-job blocking without a “Wait for Tool” event.
3. ComponentLot–Components–Jobs–Batch: L7 + {C2,C5} + {J2,J5} + B1 — lot quarantine couples otherwise separate jobs; supervisor override lets J2 enter B1 while J5 waits on release.
4. Jobs–Tool–Machine–Shipment: {J5,J6} + CAL-3 + TEST-1 and separately {J1,J4} + S1 — sequential tool use and consolidation both impose finish-to-start coupling on early-ready jobs.

Direct observations vs inferred:
- Direct: requires, contains, batches, consolidates; Batch Cure event relating B1,OVEN-1,RACK-7,J1–J3,C1–C3; Quarantine/Release Lot on L7; FIX-A acquire/release times; Final Test intervals; pack and dispatch times.
- Inferred: waiting-for-batch from readiness timestamps; FIX-A as cause of CNC-2 idle + J4 start lag; CAL-3 recalibration as cause of TEST-1 idle before J6; packed-job wait inside shipments (shipment DFG lacks it); lot-to-job causal delay for J5.

## 2. Quantitative delay decomposition

All figures are time differences under stated counterfactuals; they are not causal proofs.

**(1) B1 synchronization wait for J1**  
Ready 08:10, batch starts 12:05  wait = 3 h 55 min.  
Counterfactual: B1 could start when the first job is ready (or when a full feasible subset exists) and RACK-7/OVEN-1 are free; if start were ~08:25 (J2 ready) or at J3-ready 11:55, J1’s sync wait falls to ~0–10 min beyond its own readiness. Avoidable sync portion vs last-arriver: 3 h 55 min  10 min = 3 h 45 min attributable to waiting for J3 (and any earlier policy that held the batch).

**(2) B1 synchronization wait for J2**  
Ready 08:25, start 12:05  3 h 40 min.  
Same counterfactual: vs J3 arrival, avoidable sync  3 h 30 min. (Note: J2 also sits under L7 quarantine until 13:50 in the lot system, yet entered B1 via supervisor override—so lot and batch stories partially diverge.)

**(3) FIX-A delay plausibly associated with J4**  
J4 reaches CNC-2 at 09:50; CNC-2 idle 10:05–10:47; J3 holds FIX-A until 11:40; J4 Machine Process starts 11:45.  
Elapsed from J4 at machine to process start  11:4509:50 = 1 h 55 min.  
CNC-2 idle pocket during hold  42 min (10:05–10:47), but full tool-blocked window runs to 11:40.  
Counterfactual: if FIX-A were free at 09:50 (or duplicated), J4 could start near 09:50–10:05; delay associated with FIX-A contention  1 h 40 min–1 h 55 min. Machine-idle gap alone understates the block.

**(4) S1 consolidation delay on J1**  
J1 packed 13:30; S1 dispatches 19:25  J1 waits 5 h 55 min after pack.  
Counterfactual: ship-on-ready (or S1 without waiting for J4); delay imposed on J1 by consolidation  5 h 55 min minus nominal load/dispatch (~0.3–0.8 h from shipment DFG)  ~5 h 15 min–5 h 45 min pure partner-wait. J4 packed 19:10; dispatch 19:25 is only 15 min after the late partner.

**(5) CAL-3 delay for J6**  
J5/J6 ready ~16:00–16:05; J5 tests 16:10–16:35; CAL-3 recalibrated 16:35–17:20; J6 tests 17:25–17:50.  
J6 start lag from readiness  17:2516:05 = 1 h 20 min.  
Counterfactual: if CAL-3 needed no post-J5 recalibration (or second calibrator), J6 could follow J5 immediately (~16:35); delay associated with CAL-3  50 min recalibration + any setup  50–80 min. TEST-1 idle 16:35–17:25 is the machine shadow of the tool constraint.

**Additional (B2 / RACK-7):** J4 ready 13:10, J5 ready 14:40, B2 starts 14:50; OVEN-1 idle 12:55–14:50; RACK-7 cleaning/quarantine until 14:35.  
Counterfactual: rack available at 13:10 and batch policy allows start without J5  J4 might cure ~13:10; sync+rack delay for J4  1 h 40 min. Rack release at 14:35 gates the 14:50 start more tightly than oven capacity.

Multiple near-ties (batch vs tools vs shipment) are acceptable: they operate on different time-of-day windows and object sets.

## 4. What flattening misses

**Job flattening**  
Visible: ReleaseStageMachineInspect(Rework)PackDispatch; frequencies 6/6/6/4/2…; no job outlier >1.8.  
Hides: batch membership barriers, tool acquires, lot quarantine/release, shipment partner waits; duplicates rework loops without showing shared CAL-3/FIX-A.  
Misleading conclusion: “process is healthy, median times modest”—masks 3–6 h cross-instance waits.

**Machine flattening**  
Visible: utilization 44–58%, setup/process sequences, longest gaps 39–73 min.  
Hides: *why* gaps (rack clean, FIX-A hold, CAL-3 recalc, waiting for batch peers); multi-job batch events collapse to one machine timeline.  
Misleading: “no severe machine bottleneck / spare capacity” while jobs queue on non-machine constraints.

**Batch flattening**  
Visible: B1/B2 cure events, which jobs are batched.  
Hides: pre-batch ready-time dispersion, rack cleaning as separate tool lifecycle, lot override that let J2 in early; interaction with shipments downstream.  
Misleading: batch duration looks like pure process time rather than sync + tool gate.

**Tool flattening**  
Visible (if logged): FIX-A acquire/release, RACK-7 cleaning, CAL-3 recalibration.  
Hides: jobs that waited without an explicit wait event; machine idle attributed elsewhere; shipment side-effects.  
Misleading: tool “utilization” may look moderate while exclusive holds create long critical-path delays.

**ComponentLot flattening**  
Visible: Quarantine/Release on L7 at 10:20/13:50, contains C2/C5.  
Hides: inconsistent propagation to Job views; supervisor override path; which downstream batch/shipment absorbed the delay (J5 vs J2 asymmetry).  
Misleading: lot QA appears local; coupling to J5 readiness and B2 start is dropped in job extracts.

**Shipment flattening**  
Visible: CreateLoadDispatch, median 0.8h + 0.3h.  
Hides: how long packed J1 waited for J4 inside S1; consolidation policy; upstream batch/tool causes of J4 lateness.  
Misleading: “shipments are fast” while early-ready jobs incur multi-hour dwell.

**Why low machine utilization coexists with long job waiting**  
Jobs are gated by multi-object synchronization (batch fullness, exclusive tools, lot release, shipment partners). Machines sit idle because the *conjunction* of required objects is false even when the machine object is free. Flattened machine metrics count only machine-event density; they do not count missing tool/rack/peer-job/lot predicates. Hence 44–58% utilization with hours of job-level waiting and cascading dispatch delay.

## 5. Object-lifecycle evidence

**Narrative A — B1 / RACK-7 / OVEN-1 / early jobs / S2**  
Objects: J1,J2,J3,C1–C3,B1,RACK-7,OVEN-1,(L8 for C1/C3),S2.  
Temporal precedence: J1 ready 08:10, J2 08:25, J3 11:55  single Batch Cure 12:05 on OVEN-1+RACK-7  later pack/dispatch into S2 (J2,J3).  
Resource feasibility: OVEN-1 and RACK-7 must be jointly free; one rack serializes B1 then B2.  
Policy: batch-all-three before cure.  
Causal speculation (not proof): J1/J2 long waits are mostly sync policy + waiting for J3, not oven capacity; feeds downstream schedule variance into S2.

**Narrative B — FIX-A / CNC-2 / J3–J4 / B2 / S1**  
Objects: J3,J4,C4,FIX-A,CNC-2,B2,RACK-7,OVEN-1,S1.  
Temporal precedence: J3 holds FIX-A 09:00–11:40; J4 at CNC-2 09:50; process starts 11:45 with FIX-A; J4 ready for batch 13:10; RACK-7 clean until 14:35; B2 starts 14:50; J4 packed 19:10; S1 dispatch 19:25 (with J1 packed since 13:30).  
Resource feasibility: CNC-2 work on J4 requires FIX-A; B2 requires RACK-7; S1 requires both J1 and J4.  
Policy: exclusive fixture; batch with J5; consolidate J1+J4.  
Causal speculation: fixture hold delays J4 into afternoon batch window; rack then delays B2; late J4 imposes evening consolidation wait on J1—cascade across toolmachinebatchshipment.

**Narrative C — L7 / J5 / CAL-3 / TEST-1 / S3**  
Objects: L7,C5,J5,J6,C6,CAL-3,TEST-1,B2,S3.  
Temporal precedence: L7 quarantine 10:20  release 13:50  J5 batch-ready 14:40  B2 14:50  J5/J6 test-ready ~16:00  J5 test 16:10–16:35  CAL-3 recalc 16:35–17:20  J6 test 17:25–17:50  S3 consolidates J5+J6.  
Resource feasibility: J5 needs released lot; Final Test needs CAL-3; S3 needs both jobs.  
Policy: lot hold applies until release (J2 overridden; J5 not); calibrator shared; shipment pairs J5 with J6.  
Causal speculation: lot release sets J5’s late readiness into B2; CAL-3 serializes J6 after J5; S3 inherits joint completion—coupling from lot QA through test tool to shipment.

Separation note: timestamps give precedence only; feasibility comes from required co-presence (tool+machine+job); policy from batch/consolidation/override rules; “caused the delay” remains hypothesis pending interventions or richer logs.

## 6. Intervention portfolio and spillovers

**I1 — Reduce batch synchronization (smaller batches / start-on-minimum-set)**  
Target: B1/B2 full-membership barrier.  
Benefit: cut J1/J2-type waits (~3.5h+).  
Helped: J1,J2,J4 (earlier oven).  
Harmed: possibly J3/J5 if partial batches reduce oven efficiency or recipe quality.  
New cost: more oven cycles, energy, rack turns.  
Perverse metric: “batch size maximized” or “oven fills.”  
OC evaluation: compare ready-to-batch-start distributions per Job–Batch edges before/after; OCEL interaction counts Batch–Job.

**I2 — Duplicate or pre-stage critical tools (second fixture / parallel CAL or offline calib)**  
Target: FIX-A and CAL-3 contention.  
Benefit: remove ~1.5–2h J4 block and ~50–80 min J6 block; raise effective CNC/TEST productivity without more machines.  
Helped: J4,J6 and any future fixture/calib users.  
Harmed: capital budget; calibration labor if dual CAL.  
New cost: tool purchase, certification.  
Perverse metric: “tool utilization %” (may fall while flow improves).  
OC evaluation: Tool–Job acquire/release overlap matrix; idle gaps on CNC-2/TEST-1 conditional on tool free.

**I3 — Shipment policy: ship-on-ready or time-boxed consolidation**  
Target: S1-style partner wait.  
Benefit: free J1 ~5h+ dwell; smoother dock.  
Helped: early-ready jobs in S1 (J1); possibly S2/S3 early members.  
Harmed: transport cost if more partial shipments; J4 may lose shared freight subsidy.  
New cost: freight frequency, emissions.  
Perverse metric: “shipment fill rate” or “cost per shipment.”  
OC evaluation: pack-to-dispatch time per Job–Shipment edge; compare consolidation delay quantiles.

**I4 — Rack lifecycle management (second rack or faster clean/quarantine clearance)**  
Target: RACK-7 gate between B1 and B2.  
Benefit: allow B2 nearer 13:10 when J4 ready; cut oven idle 12:55–14:50.  
Helped: J4,J5,OVEN-1 utilization quality.  
Harmed: none major if quality preserved; space for second rack.  
New cost: rack asset, cleaning capacity.  
Perverse metric: “rack utilization” alone.  
OC evaluation: Batch–Tool–Machine motif timing; RACK state events vs batch start.

**I5 — Logging / integration fix (not ops)**  
Target: data-integration artifacts—link lot events to jobs; emit Wait-for-Tool; record readiness and override; shipment partner-wait attributes.  
Benefit: make delays observable in Job views; enable fair ranking of mechanisms.  
Helped: all analysts and future interventions; J2/J5 lot asymmetry becomes measurable.  
Harmed: none operationally; short-term IT effort.  
New cost: instrumentation, OCEL pipeline work.  
Perverse metric: “event volume” (don’t spam low-value events).  
OC evaluation: before/after presence of Lot–Job edges in `ocel_objects_interactions_summary`; reduction in unexplained ready-to-start residuals.

**I6 — (optional) Explicit WIP / decoupling buffers with policy**  
Target: cascade from fixturebatchshipment.  
Benefit: absorb local contention without multi-hour sync.  
Helped: downstream partners (e.g., J1 not waiting on J4 path).  
Harmed: inventory holding; possible quality lag.  
Perverse metric: “WIP minimization” fighting buffer intent.  
OC evaluation: multi-hop path delays in object graph (Job–Tool–Batch–Shipment).

Spillovers: cutting batch sync without rack capacity moves queue to RACK-7; shipping early without fixing J4’s fixture path still leaves J4 late (local improvement, global incomplete); dual CAL without lot-release discipline leaves J5 late to test.

## 8. Falsification and additional data

**Observations that would weaken the top-ranked (batch sync + rack) explanation**
1. Evidence that J1/J2 were not actually “ready” at 08:10/08:25 (bad readiness sensor or unfinished prior step).  
2. OVEN-1 or labor unavailable until 12:05 for reasons unrelated to J3/RACK-7 (maintenance order, shift break).  
3. Thermal/recipe constraint forbidding start before a fixed clock time independent of membership.  
4. Second rack existed and was free, yet batch still waited—points to pure policy or staffing.  
5. B2 start at 14:50 explained by J5 material shortage unrelated to RACK-7 cleaning end at 14:35.  
6. Jobs not in B1/B2 show equal or larger waits—batch motif not distinctive.  
7. (Bonus) After forcing partial batches historically, quality scrap spiked enough to justify full sync waits.

**Additional fields / event types to discriminate hypotheses**
1. Explicit `Wait_for_Batch` / `Wait_for_Tool` / `Wait_for_Lot` / `Wait_for_Shipment_Partner` activities with foreign-key object references.  
2. Tool state machine events: `Tool_Free`, `Tool_Reserved`, `Clean_Start/End`, `Calibrate_Start/End` with timestamps and operators.  
3. True job readiness signal (BOM complete, previous stage OK) as a first-class event.  
4. Supervisor override events linked to both Lot and Job (who, why, system of record).  
5. Machine disable/reason codes (no-tool, no-rack, no-operator, no-batch) during idle gaps.  
6. Shipment planning attributes: planned consolidation set, earliest ship time, transport capacity, customer window.  
7. Resource calendars (shifts, oven programs, calibration due dates).  
8. Quality hold reason codes on ComponentLot and whether hold is hard-gating in MES vs advisory.  
9. Multi-object event payloads listing *all* related objects consistently (fix Job extract gaps).  
10. Cost/energy per oven cycle and freight cost per partial shipment (to score intervention spillovers).

These data would allow counterfactual-ready decompositions (policy vs resource vs quality vs integration) without equating succession with causation, and would show whether machine capacity ever binds once tool, lot, batch, and shipment predicates are satisfied.
