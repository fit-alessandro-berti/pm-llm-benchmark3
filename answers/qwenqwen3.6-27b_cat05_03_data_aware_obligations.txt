## 1. Temporal Data Semantics

State reconstruction follows a strict event-time forward propagation model within each case partition:
- **Blank cells** indicate no attribute update at that event; the prior value persists.
- **Effective time** defaults to the event timestamp unless policy or evidence explicitly states otherwise (e.g., exemption `effective_from`).
- **Final case state is never copied backward**; each obligation is evaluated against the latest known attribute values at the trigger event's timestamp.
- **Same-timestamp ordering** uses `event_index` as a deterministic tie-breaker. Earlier indices are processed first, establishing state before later indices at the identical clock time.
- **Material data changes** include any update to `amount`, `risk_level`, `jurisdiction`, or `customer_type`, plus `Sanctions_List_Update`. For amount, increases >20% trigger R4 invalidation; decreases do not.
- **Evidence vs. Record time**: A database insertion timestamp (`Record_Exemption`) is distinct from signature/approval time. R5 requires independent corroboration (qualified signature, audit trail) that approval existed before the obligation trigger. Backdated display fields alone are insufficient.
- **Missing data**: Per R6, unknown `amount`, `risk_level`, `jurisdiction`, or `customer_type` at a trigger event forces `INDETERMINATE` classification for rules dependent on those attributes, unless cross-referenced evidence (e.g., settlement payload with immutable provenance) resolves it.

## 4. Ambiguities and Alternative Readings

- **TX-302**: Classified COMPLIANT due to strong digital signature evidence for EX-77. If the qualified signature timestamp were missing or post-dated release, the late DB insert would fail R5, flipping classification to NONCOMPLIANT. Alternative reading: If policy required real-time exemption registry sync, the outage-induced delay could be treated as a control failure, though R5 explicitly accommodates documented outages.
- **TX-305**: INDETERMINATE per R6. If the settlement payload carried an immutable cryptographic hash linking to the original release message, and policy accepted settlement amount as a proxy for release amount, R1 would trigger (150k  100k) and require an Enh_Rev after the unknown material change, likely yielding NONCOMPLIANT. Conversely, if CA jurisdiction had a statutory exemption for amounts <150k, it could become COMPLIANT.
- **TX-310**: INDETERMINATE due to EX-88 evidence conflict. If an independent compliance officer (not the requester) corroborated the 08:45 oral approval with a contemporaneous email or system audit log, R5 would be satisfied, yielding COMPLIANT. If the qualified signature timestamp is treated as the definitive approval time (ignoring witness testimony), the exemption is invalid, yielding NONCOMPLIANT.
- **TX-311**: COMPLIANT relies on `event_index` ordering. If the system processed events by internal UUID or network arrival order instead of `event_index`, the jurisdiction update to DE might be evaluated before the Enhanced_Review, potentially triggering R1 (if US state persisted) or altering review scope. Explicit logging of processing order would eliminate this ambiguity.
- **TX-306 & TX-308**: Both hinge on R4's treatment of sub-20% increases and decreases. An alternative reading of R1's "after the latest material data change" could demand a fresh review for *any* attribute update, regardless of R4. Under that strict reading, both would be NONCOMPLIANT. The current reading prioritizes R4's explicit preservation clause.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-State Leakage**: Conformance checkers often snapshot the final case state and apply it retroactively. This violates R7, masking cases where attributes changed after a review (e.g., TX-301, TX-309) and falsely labeling them compliant.
2. **Post-Hoc Exemptions**: Control-flow models treat `Record_Exemption` as a standard event in a sequence. They cannot distinguish between an exemption approved before release vs. one inserted after, failing R5's evidentiary and temporal validity checks (e.g., TX-310).
3. **Material Changes After Review**: Sequence patterns cannot evaluate magnitude thresholds (R4's 20% rule). A log showing `Update_Amount` after `Enhanced_Review` looks structurally identical regardless of whether the change is 1% or 50%, yet compliance implications differ drastically.
4. **Conditional Activation**: Rules like R1 and R2 are data-gated (`jurisdiction != DE`, `risk = HIGH`). Control-flow conformance assumes unconditional obligation activation, producing false positives (flagging DE cases) or false negatives (missing PEP triggers if customer type isn't modeled as a data attribute).
5. **Missing Data Blindness**: Conformance engines typically ignore nulls or treat them as "event not fired". R6 mandates explicit `INDETERMINATE` classification when triggers cannot be established. Control-flow models lack the semantic layer to propagate uncertainty through rule evaluation.
6. **Same-Timestamp Ordering**: Many conformance algorithms bucket events by timestamp or assume strict monotonicity. They cannot resolve `event_index` tie-breaks, leading to incorrect state snapshots when jurisdiction changes and reviews share a clock time (e.g., TX-311).

## 7. Recommended Logging and Control Improvements

- **Immutable Release Payloads**: Capture a cryptographic hash of the complete release message (amount, jurisdiction, customer type, timestamp) at the moment of `Release_Funds`. Prevents post-hoc reconciliation ambiguity (TX-305).
- **Effective/Record/Signature Timestamps**: Log three distinct timestamps for exemptions: `effective_from`, `recorded_at`, and `qualified_signature_at`. Enables automated R5 validation without manual evidence review.
- **Rule Version & Scope Metadata**: Attach `rule_version` and `policy_scope` to each review event. Allows historical evaluation when policies change, and clarifies whether a `Compliance_Approve` covered PEP/HIGH-risk requirements (TX-307).
- **Change Provenance & Delta Tracking**: Log `previous_value` and `new_value` for all attribute updates, plus a `change_reason` code. Simplifies R4 materiality calculations and audit trails.
- **Stable Event Ordering**: Enforce a monotonically increasing `event_index` or use vector clocks to guarantee deterministic tie-breaking. Eliminates ambiguity in same-timestamp processing (TX-311).
- **Structured Exemption Registry**: Replace ad-hoc `Record_Exemption` events with a dedicated `Exemption_Activated` event that includes scope validation flags (`jur_match`, `amt_match`, `cust_match`, `sig_valid`). Shifts R5 logic into the data layer, enabling automated conformance checks.
