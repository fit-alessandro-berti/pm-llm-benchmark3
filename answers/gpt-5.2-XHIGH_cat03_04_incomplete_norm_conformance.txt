## 1. Conformance semantics

I treat the norm as **open-world by default**: behavior or relations that are not stated (or are explicitly marked **unspecified**) are **not** automatically noncompliant. The norm becomes **closed-world only** in two places: (i) relations explicitly marked **forbidden** (their *presence* is a prima facie problem), and (ii) relations marked **mandatory** within their stated **scope** (their *absence* is a potential nonconformance, but only after checking scope and the abstraction used to measure it).

I distinguish the following deviation semantics:

- **Forbidden behavior**: an observed relation/edge that is marked **forbidden** within scope (e.g., N3, T6, E10). This is the strongest signal, but can still be caused by mis-linkage or mis-ordering; when so, the “violation” is best interpreted as a **data/control failure** (e.g., an integration join error) rather than a true operational breach.
- **Missing mandatory behavior**: a **mandatory** expectation does not hold in-scope. In object-centric summaries this can reflect (a) a genuinely missing event/object link, or (b) the fact that we are testing a *business* rule (“eventually” / “must happen before”) using a **directly-follows** abstraction. I therefore split “missing mandatory” into **likely instrumentation/logging gap** (high confidence when ET–OT links are absent) vs **possible abstraction mismatch** (lower confidence when only OC-DFG direct-follows is missing).
- **Unexpected but unregulated behavior**: an observed relation not covered by the norm, or covered as **unspecified**. Under open-world semantics, it is *allowed*; the right outcome is usually “document and decide whether to govern,” not “flag as noncompliance.”
- **Typical-pattern absence**: a **typical** relation is absent or weaker than expected. This is not a violation; it is an *interpretation cue* (e.g., exceptions, censoring by time window, or alternative settlements).
- **Likely data-quality error**: evidence points to mis-joins, reused identifiers, incomplete object linking, or extraction artifacts (e.g., E10 case). These are handled as **data repair** items and should not be escalated as process misconduct without corroboration.
- **Abstraction mismatch**: the norm describes **eventual** or **precedence** constraints, but evaluation uses **directly-follows** edges (OC-DFG). Missing directly-follows edges can be false positives when legitimate intermediate steps exist (explicitly noted for N1 and implied for N2/N4).
- **Insufficient evidence**: graph summaries cannot decide case-level timing, partial cancellations, concurrency, late-arriving events, or whether “no successor” is simply outside the observation window. Such items get lower confidence and require trace-level inspection.

## 3. Detailed reasoning by model family

### OC-DFG

**What it can establish.** An OC-DFG summarizes **directly-follows** relations along object-specific projections (e.g., per Order, per Package). It is good for spotting strong **local sequencing** signals (e.g., a dispatch directly after a cancel in the same Order projection) and for measuring how often a particular edge appears.

**What it cannot establish.** It cannot reliably encode **eventual** obligations (“eventually validate,” “eventually close”), **precedence** (“pack must occur before dispatch”), or multi-step paths when legitimate intermediate events exist. It also cannot resolve **concurrency**, ties, or timestamp ordering ambiguity. Therefore, a missing direct-follows edge is often **not** evidence that the business rule failed—only that it did not occur *as an immediate successor* in the projection.

**Counts and scopes.** For N1, the text explicitly says “eventually enter validation,” but the summary tests it with a directly-follows approximation: **98/100** show `Create -> Validate`. The provided context even warns that the missing 2 may have an unrecorded review step in between. This is a canonical **abstraction mismatch**: a compliant trace `Create -> (Hold/Review) -> Validate` will be counted as nonconformant under a direct-follows test.

Similarly, N2 is **typical** (`Validate -> Close`) and explicitly allows intermediate steps (“invoice, review, fulfilment events may occur and are incompletely modeled”). The observed `Validate -> Issue Invoice` (**72 Orders**) should therefore be read as **model incompleteness**, not deviance: it is exactly the sort of intermediate step that breaks `Validate -> Close` as a directly-follows edge. Interpreting “eventually close” as `Validate -> Close` would inflate false positives.

N4 (`Pack -> Dispatch`) is labeled mandatory for externally shipped packages, but the same caution applies: if there are intermediate warehouse scans, label prints, or quality checks, a correct precedence relation can appear as a missing directly-follows edge. Thus **198/200** is a risk signal, but not decisive without trace-level verification that packing occurred before dispatch for the remaining 2.

For N3, the forbidden `Cancel -> Dispatch` (**2 Orders**) is more alarming because it indicates that, within the same Order projection, dispatch follows cancellation. Still, even here the OC-DFG cannot tell whether cancellation was partial, backdated, or mis-linked; it only tells us that the event ordering *as represented* violates the rule.

### OTG

**What it can establish.** An OTG captures which **object types are structurally related** (interaction) and, depending on extraction, lifecycle co-birth / co-death patterns. It is useful to check that required object interactions exist at all (e.g., packages interact with deliveries, orders interact with items).

**What it cannot establish.** It does not constrain **which event type** created the relation, nor does it capture **ordering** or whether a relation is present for every relevant event instance. Therefore OTG is necessary but not sufficient for event-scoped norms.

**Counts and scopes.** The OTG shows **(Package, interaction, Delivery)=200**, consistent with T2 being mandatory for dispatch interactions. However ET–OT shows only **198** dispatch events linked to Delivery. This illustrates a key cross-abstraction point: the overall object graph can be conformant (packages do interact with deliveries somewhere), while the **event-scoped** requirement (every `Dispatch Package` must attach a Delivery) is still violated or inconsistently logged.

The OTG’s **(Order, interaction, Item)=1450** aligns with the intended Add Item relation (T1), yet ET–OT reveals **2** `Add Item` events without an Order link. Again: structurally the interaction exists, but event-level completeness is imperfect.

The OTG’s **(Order, object_cobirth, Payment)=1** is directly governed (T6 forbidden) and is high-risk, but also highly sensitive to how “birth” is inferred (first observed event). If the log window starts after one object already existed, cobirth can be an artifact. Hence: severe if real; lower confidence without raw extraction evidence.

The **(Package, object_codeath, Delivery)=7** is ungoverned; it is a reminder that not every lifecycle pattern belongs to the compliance norm.

### ET–OT

**What it can establish.** ET–OT edges check whether each **event type** is linked to the required **object types** (and whether forbidden links occur). This is the most direct way, in this summary, to detect **instrumentation/completeness** failures for mandatory ET–OT rules (E1–E8) and to spot prohibited attachments (E10).

**What it cannot establish.** ET–OT does not show control-flow ordering, nor does it prove that the correct object instance is linked (only the object type). It also cannot decide whether “no successor” reflects a business state or simply the observation window.

**Counts and scopes.** Several deviations are high-confidence because they are simple count mismatches against mandatory ET–OT rules:

- `Add Item -> Order` is **1448** while `Add Item -> Item` is **1450** (E2/E3): likely missing Order attachment in 2 events.
- `Dispatch Package -> Delivery` is **198** while `Dispatch Package -> Package` is **200** (E6/E5): likely missing Delivery attachment in 2 dispatch events, even though packages and deliveries interact elsewhere (OTG 200).
- `Record Payment -> Invoice` is **92** while `Record Payment -> Payment` is **93** (E8/E7): one payment event lacks an invoice link. This may be a legitimate business exception (unapplied cash) but the norm requires it to be explicitly typed; none are so typed in this snapshot.
- `Sensor Heartbeat -> Invoice` occurs **1** time (E10 forbidden): strongly suggests a data integration error, consistent with the provided join explanation.

**Conforming at one abstraction, suspicious at another.** The dispatch and add-item cases show how an OTG can look fine while ET–OT reveals missing event-scoped links. Conversely, OC-DFG can suggest missing mandatory behavior (e.g., N1/N4) even when ET–OT indicates the relevant event types exist; the problem may be that the rule is **eventually/precedence**, not **directly-follows**.

**Explicit danger: “eventually expected” vs directly-follows.** N1 explicitly describes an eventual obligation (“should eventually enter validation”) but is evaluated via a directly-follows edge. This will systematically misclassify any trace where one or more legitimate intermediate events occur between creation and validation (including unrecorded reviews). The same danger extends to N2 and N4: “close after validation” and “pack before dispatch” are business constraints that should be tested with **reachability/precedence** (or temporal constraints), not direct succession.

## 4. Mandatory, forbidden, typical, and unregulated behavior

- **Mandatory (in-scope)**
  - N1: `Create Order -> Validate Order` (observed as direct-follows **98/100**; classify the missing 2 as either abstraction mismatch or missing validation depending on trace evidence).
  - N4: `Pack Package -> Dispatch Package` for externally shipped packages (**198/200**; missing 2 need trace check for precedence vs missing pack).
  - T1 + E2/E3: Every `Add Item` must attach **Order+Item** (observed **1450** to Item, **1448** to Order → 2 event-level gaps).
  - T2 + E6: Every `Dispatch Package` must attach **Delivery** (observed **198/200** at event level; carrier-attribute workaround does not satisfy the object requirement unless formalized).
  - E8: Every `Record Payment` must attach **Invoice** unless explicitly “unapplied cash” (observed **92/93**; missing 1).

- **Forbidden**
  - N3: `Cancel Order -> Dispatch Package` (**2 Orders**), unless proven to be mis-linkage or a partial-cancel exception that the norm has not defined.
  - T6: `(Order, object_cobirth, Payment)` (**1**), unless cobirth is an extraction artifact from truncated history.
  - E10: `Sensor Heartbeat -> Invoice` (**1**), even if root cause is a data-quality join error (still a forbidden linkage that must be prevented).

- **Typical (not required, but informative)**
  - N2: `Validate Order -> Close Order` observed **83 Orders**; absence elsewhere should not be treated as noncompliance because intermediate steps are expected.
  - N5/T3: invoice–payment settlement typicality: `Issue Invoice -> Record Payment` **92/110** and `(Invoice, interaction, Payment)=92`; remaining invoices may be on credit terms, written off, or outside the observation window.

- **Unregulated / allowed under open-world**
  - `Validate Order -> Issue Invoice` (**72 Orders**) as an intermediate step consistent with N2’s incomplete modeling.
  - `Create Order -> Manual Compliance Review` (**3 Orders**) and the associated `Manual Compliance Review` links to **RiskCase (3)** and **Customer (3)** (E9/T5/T4 are unspecified).
  - `Reopen Order -> Close Order` (**1**) (N6 unspecified).
  - `(Package, object_codeath, Delivery)=7` (norm silent on codeath).
  - `Issue Invoice -> Write Off` (**4**) and `Issue Invoice` with no successor (**14**) are not violations per se; they become problematic only when they breach credit-term policy or lack required approvals (a norm gap).

## 5. PM4Py conformance code sketch

```python
import pm4py

# 1) Discover observed structures from the OCEL
obs_ocdfg = pm4py.discover_ocdfg(ocel)
obs_otg = pm4py.discover_otg(ocel)
obs_etot = pm4py.discover_etot(ocel)

# 2) Run conformance diagnostics against the normative structures
# (Keep PM4Py diagnostics as raw technical output)
diag_ocdfg = pm4py.conformance_ocdfg(ocel, norm_ocdfg)
diag_otg = pm4py.conformance_otg(ocel, norm_otg)
diag_etot = pm4py.conformance_etot(ocel, norm_etot)

raw_diagnostics = {
    "ocdfg": diag_ocdfg,
    "otg": diag_otg,
    "etot": diag_etot,
}

# IMPORTANT:
# PM4Py graphs/tuples typically do NOT carry normative metadata such as
# {mandatory, typical, forbidden, unspecified} or scope conditions.
# Maintain that metadata separately and join it to diagnostics.
norm_meta = {
    "ocdfg": {
        # key shape depends on how you encode normative OC-DFG relations
        ("Order", "Create Order", "Validate Order"): {"id": "N1", "status": "mandatory", "scope": "standard orders"},
        ("Order", "Cancel Order", "Dispatch Package"): {"id": "N3", "status": "forbidden", "scope": "same order"},
        ("Package", "Pack Package", "Dispatch Package"): {"id": "N4", "status": "mandatory", "scope": "external shipment"},
        ("Invoice", "Issue Invoice", "Record Payment"): {"id": "N5", "status": "typical"},
    },
    "otg": {
        ("Order", "object_interaction", "Item"): {"id": "T1", "status": "mandatory"},
        ("Package", "object_interaction", "Delivery"): {"id": "T2", "status": "mandatory"},
        ("Invoice", "object_interaction", "Payment"): {"id": "T3", "status": "typical"},
        ("Order", "object_cobirth", "Payment"): {"id": "T6", "status": "forbidden"},
    },
    "etot": {
        ("Create Order", "Order"): {"id": "E1", "status": "mandatory"},
        ("Add Item", "Order"): {"id": "E2", "status": "mandatory"},
        ("Add Item", "Item"): {"id": "E3", "status": "mandatory"},
        ("Dispatch Package", "Delivery"): {"id": "E6", "status": "mandatory"},
        ("Record Payment", "Invoice"): {"id": "E8", "status": "mandatory", "scope": "unless unapplied cash"},
        ("Sensor Heartbeat", "Invoice"): {"id": "E10", "status": "forbidden"},
    },
}

def semantic_layer(pm4py_diag: dict, meta: dict, open_world: bool = True) -> list[dict]:
    """
    Build a parallel semantic interpretation layer.
    Do NOT overwrite PM4Py outputs; return enriched findings separately.
    """
    findings = []
    for dev in pm4py_diag.get("deviations", []):  # structure depends on PM4Py version
        key = dev.get("key")
        rule = meta.get(key, {"status": "unspecified"})
        status = rule["status"]

        observed = dev.get("observed", None)
        expected = dev.get("expected", None)

        if status == "forbidden" and observed:
            sem = "forbidden behavior"
        elif status == "mandatory" and (observed is False or observed == 0):
            sem = "missing mandatory"
        elif status == "typical" and (observed is False or observed == 0):
            sem = "typical-pattern absence"
        else:
            sem = "unexpected but unregulated" if open_world else "unexpected"

        findings.append(
            {
                "norm_id": rule.get("id"),
                "norm_status": status,
                "scope": rule.get("scope"),
                "semantic_class": sem,
                **dev,
            }
        )
    return findings

semantic_findings = {
    "ocdfg": semantic_layer(diag_ocdfg, norm_meta["ocdfg"]),
    "otg": semantic_layer(diag_otg, norm_meta["otg"]),
    "etot": semantic_layer(diag_etot, norm_meta["etot"]),
}
```

## 6. Norm-completeness assessment

1) **N1 “eventually validate” vs directly-follows proxy**
   - **Risk**: false positives (compliant orders flagged) and missed late validations if only direct succession is checked.
   - **Clarification**: define an **eventual** constraint: every standard Order must have a `Validate Order` event within \(X\) time units after creation; allow explicitly listed intermediate events.
   - **Status**: **mandatory** (eventual), optionally **typical** for the direct-follows shortcut.

2) **N4 packing rule encoded as `Pack -> Dispatch` direct-follows**
   - **Risk**: either over-enforcement (intermediate scan steps create “violations”) or under-enforcement (dispatch without prior pack still possible).
   - **Clarification**: specify whether the rule is **precedence** (“Pack occurs before Dispatch at any distance”) and list exceptions (drop-ship, pre-packed returns, internal transfer).
   - **Status**: **mandatory** (precedence) within clearly defined “external shipment” scope.

3) **N3 cancellation semantics are underspecified**
   - **Risk**: unclear whether partial cancellations, cancellation after dispatch, or cancel of remaining items should be treated as breach.
   - **Clarification**: define cancellation **granularity** (order vs line vs package) and the temporal rule (“no new dispatch after full cancellation timestamp”).
   - **Status**: **forbidden** for dispatch after *full* cancellation; explicitly **unspecified** (or separate policy) for post-dispatch cancellations/returns.

4) **N2 closure expectation lacks an “eventually close” definition**
   - **Risk**: cannot distinguish legitimately open orders (backorder/credit hold) from stuck cases.
   - **Clarification**: define closure conditions (fulfilled + invoiced, cancelled, etc.) and time-based expectations.
   - **Status**: likely **typical** (eventual close), with explicit **unspecified** carve-outs (e.g., long-running subscriptions).

5) **Invoice settlement exceptions are named but not modeled**
   - **Risk**: `Write Off` and credit-note pathways remain ungoverned; inconsistent accounting workflows go undetected.
   - **Clarification**: enumerate acceptable invoice terminal states (paid, written off, credited) and required approvals/links.
   - **Status**: **typical** for `Issue -> Record Payment`; **mandatory** for “invoice reaches one terminal settlement state or remains open under terms.”

6) **Unapplied cash handling is operationally allowed but not representable**
   - **Risk**: conformance flags (E8) will confuse legitimate operations; reconciliation breaks if unpaid/unknown is not typed.
   - **Clarification**: add an explicit event type/attribute for “unapplied cash,” and define whether it must later be linked to an invoice.
   - **Status**: **mandatory** to type the exception; keep invoice linkage **mandatory** when not typed as unapplied.

7) **T6 cobirth depends on ambiguous lifecycle extraction rules**
   - **Risk**: false alarms if “birth” = first observed event in a truncated window; missed true simultaneous creations if event identity is unclear.
   - **Clarification**: define cobirth as “same business event ID creates both objects” (not merely same timestamp / first observation).
   - **Status**: **forbidden** (true cobirth), plus **mandatory** evidence standard for asserting it.

8) **E10 forbids sensor–finance links but lacks data integration guardrails**
   - **Risk**: recurring joins on reused numeric identifiers can reintroduce forbidden edges even after process fixes.
   - **Clarification**: require typed identifiers or namespaces across streams; validate joins by source/type.
   - **Status**: **forbidden** linkage + **mandatory** ID-namespace enforcement and monitoring.

- **Monitoring**
  - Always-on alerts for **forbidden** edges (N3, T6, E10), with trace-level drill-down.
  - Data-quality KPIs for mandatory ET–OT completeness (E2/E6/E8 coverage rates) and cross-checks between OTG and ET–OT (structural presence vs event-level attachment).
  - Aging dashboards for open invoices/orders to avoid treating “no successor” as noncompliance without time context.
