## 1. Analytical assumptions

**Case notion.** I treat a "case notion" as a choice of object type whose individual instances become the trace-defining identifiers when the OCEL is flattened into a classical event log. Flattening on type T means: for every event e that is directly related (E2O) to at least one object o of type T, emit one trace-row per such o, using o's identifier as the case id and e's activity/timestamp as the event. An object of type T with no directly related events produces no trace; a case's trace is the timestamp-ordered sequence of the events that name it. Crucially, the case notion is a *lens*, not a claim about the "true" unit of work. The same physical event e13 will appear under several lenses, and its meaning changes depending on which identifier we are reading it against.

**Convergence.** Convergence occurs when a single event is directly related to *several* objects of the chosen case type, so that flattening copies that one event into multiple traces. Example: e13 (Pack Package) is related to both O2 and O3. Flattening on Order duplicates e13 into O2's trace and O3's trace. The event happened once; it is now counted twice. Convergence inflates activity frequencies and creates the illusion that a shared step recurred per case.

**Divergence.** Divergence occurs when several events that are really about *different* finer-grained objects all attach to the *same* case object, so their relative order within that case becomes ambiguous or spuriously sequential. Example: flattening on Order O1, the two "Add Item" events e05 (I11) and e06 (I12) both land in O1's trace. The directly-follows edge Add Item → Add Item is an artifact of two parallel item sub-lifecycles being serialized under one order, not a genuine repetition of the same work on the same thing.

**Copied shared events: evidence or duplication?** Both, and the distinction is contextual. A copied shared event is *legitimate evidence* that the event genuinely touched each of the objects it was copied into (e13 really did involve O2 and O3; that relation is in the log, not inferred). It becomes *harmful duplication* the moment we aggregate across cases — count activity frequencies, compute DFG edge weights, or average performance — because the physical singularity of the event is lost. My rule: copied shared events are evidence at the *per-case qualitative* level and duplication at the *cross-case quantitative* level. I will therefore always report event counts both as raw event occurrences and as unique-event counts.

**Permitted analytical transformations.** I will (a) use only the *direct* E2O relations for baseline flattening, honoring the instruction not to silently propagate through the O2O graph; (b) permit, as an *explicitly labeled* variant, relation propagation through O2O links (e.g., attaching a Payment event to the Items of the Order it bills via V→O→I), and I will always contrast propagated results against the direct baseline rather than substituting them; (c) permit deduplication of copied events when computing frequency/performance, again as a labeled variant. No transformation is treated as the ground truth.

## 3. Concrete distortion analysis

**(1) Cross-order package P3 inflates Pack Package under Order flattening.** Affected: Order flattening. Event e13 (Pack Package; O2,O3,I21,I31,P3) is copied into O2's trace and O3's trace. The DFG for both orders gains an "Add Item → Pack Package" edge from a single physical packing act, and the Pack Package activity count rises from one occurrence to two. Effect: **harmful** for frequency/throughput analytics (double counting), but **informative** as evidence that O2 and O3 were physically co-packed.

**(2) Cross-order package P4 creates a phantom shared step across O3 and O4.** Affected: Order (and Package) flattening. Event e14 (O3,O4,I32,I41,P4) is duplicated into O3 and O4. On the Package lens, P4's single trace correctly shows one Pack event, but on the Order lens the same act appears in two order histories, and O3 now shows *two* distinct packing events (e13 for I31 via P3, e14 for I32 via P4) even though O3 is one order split across two parcels. Effect: **context-dependent** — genuine split-shipment evidence, but a trap if read as "O3 was packed twice as a whole."

**(3) Consolidated delivery D2 fuses three orders into one Delivery case.** Affected: Delivery flattening. e16 (Dispatch) and e24 (Confirm Delivery) both name D2 with O1,O2,O3,I12,I21,I31,P2,P3. On the Delivery lens, D2 is a single two-event case (Dispatch 11:05 → Confirm 16:00), collapsing three orders' fulfilment into one 4h55m delivery duration. This *hides* per-order divergence and makes D2 look like a clean short lifecycle. Effect: **harmful** if used to attribute delivery performance to individual orders; **informative** for measuring pure shipment latency.

**(4) Consolidated invoice V2 mixes two orders' order-to-cash timelines.** Affected: Invoice flattening. e19 (Issue Invoice; O2,O3,V2) is one event; V2's trace is Issue → Record(M2) → Record(M3). Under Invoice flattening this is a coherent instalment story, but if we instead flatten on Order, e19 duplicates into O2 and O3, so *both* orders appear to be individually invoiced when in fact they share one invoice. Effect: **harmful** for revenue-per-order counts (V2 would be counted twice), **informative** for the fact that consolidated billing occurred.

**(5) Partial payment of V2 fabricates a "Record Payment" repetition.** Affected: Order flattening (and Invoice flattening handles it correctly). M2 partially settles V2 (e22, 12:40 same day) and M3 completes it (e25, next day 09:00). Under Order flattening, both e22 and e25 name O2 and O3, so *each* order's trace shows two Record Payment events on different days — a spurious "reworked payment" variant that is really one instalment plan on one shared invoice. The DFG gains a Record Payment → Record Payment self-adjacent edge with a ~20h delay, biasing payment-cycle KPIs upward. Effect: **harmful** if interpreted as payment failure/retry; **informative** about instalment structure only when read on the Invoice lens.

**(6) Payment lens yields degenerate near-singleton lifecycles.** Affected: Payment flattening. Each of M1,M2,M3,M4 appears in exactly one event (e21,e22,e25,e26). Every Payment case is a one-activity trace "Record Payment." No directly-follows edges exist within a case; the DFG is a single node with self-loop-free structure. This is the brief's "artificially short lifecycle when the object participates in only one or two event types." Effect: **harmful** if mistaken for a real process; **context-dependent** as a pure transaction inventory.

**(7) Multi-item order divergence: spurious Add Item → Add Item edges.** Affected: Order flattening. For O1, e05 (I11) then e06 (I12); for O3, e08 (I31) then e09 (I32). These serialize two independent item additions under one order, producing an "Add Item → Add Item" DFG edge and a variant "Create, Add, Add, Pack, ..." that overstates sequential dependency. On the Item lens this divergence vanishes (each item has exactly one Add). Effect: **harmful** for control-flow conformance; **informative** only as a proxy for order size.

**(8) O1 split across P1 and P2 doubles Pack/Dispatch on the Order lens.** Affected: Order (and Package) flattening. O1's items are packed separately: e11 (I11,P1) and e12 (I12,P2), then dispatched separately e15 (P1,D1) and e16 (P2,D2). O1's order trace therefore contains two Pack Package and two Dispatch events, suggesting repetition, when it is really one order fanned out to two parcels/deliveries. On the Package lens each parcel has exactly one Pack and one Dispatch — no distortion. Effect: **context-dependent**: real fan-out evidence, misleading as "repeated packing."

**(9) Delivery-lens performance bias via D1 singleton speed.** Affected: Delivery flattening. D1 (e15 Dispatch 11:00 → e23 Confirm 14:00) is 3h; D2 is ~4h55m; D3 (e17 11:15 → e27 next-day 10:00) is ~22h45m. Because D2 and D3 aggregate multiple orders, the per-delivery mean masks that D3's long duration burdens O3 and O4 equally in reality but is invisible on the Order lens unless propagated. Effect: **informative** for shipment KPI, **harmful** for per-order SLA attribution.

**(10) Close Order as an Order-only activity truncates every other lens.** Affected: Item, Package, Delivery, Invoice, Payment flattening. Close Order (e28–e31) names only Orders. Any non-Order lens therefore *never* sees process completion, so those logs terminate at their last domain event (e.g., Item ends at Confirm Delivery, Package at Confirm Delivery, Invoice at Record Payment). Effect: **harmful** if "no Close" is read as incompleteness; it is simply outside those case notions' scope.

## 4. Traditional versus object-centric analysis portfolio

**Flattened logs worth creating.**
- **Order log** — the only lens whose activity vocabulary spans the whole vocabulary (Create → Close). Keep it as the *narrative spine*, but annotate every shared/duplicated event.
- **Invoice log** — the clean order-to-cash view; correctly represents V2's instalments (Issue → Record → Record) without the Order lens's duplication.
- **Package log** — the clean logistics view (Pack → Dispatch → Confirm Delivery) that dissolves the O1-split and cross-order divergences.

I would *not* routinely build the **Payment** log (degenerate singletons) or the **Delivery** log as a standalone (near-singleton, high consolidation bias) except for the single KPI each supports. The **Item** log is worth building only for physical-handling questions.

**Questions each flattened log can answer safely.**
- Order log: order-level cycle time *if and only if* duplicated events are deduplicated; sequence of milestones per order; rework detection *after* removing convergence artifacts (2),(5),(7),(8).
- Invoice log: settlement variants, instalment frequency (V2), invoice-to-payment latency.
- Package log: packing-to-delivery throughput per parcel; parcel consolidation counts.
- Item log: per-item handling completeness; lost/mis-scanned items.
- Delivery log: raw shipment latency (D1/D2/D3) only.
- Payment log: transaction inventory only.

**Questions that require object-centric tooling.**
- "How do orders, packages, invoices interact?" → **OC-DFG** (no single flattening shows Pack sharing P3 across O2,O3 without duplication).
- "Which object types co-occur in which activities?" → **ET–OT graph** (e.g., Pack Package touches Order+Item+Package; Record Payment touches Order+Invoice+Payment).
- "How do object types relate structurally over time?" → **OTG** (Order↔Item, Package↔Delivery).
- "How many distinct objects of each type flow together?" → **object interaction summary** (quantifies convergence at e13,e14,e16,e17).
- "Which orders share an identical multi-object execution pattern?" → **equivalent-execution clustering**, if justified.

**Reconciling contradictions.** When the Order log says "Pack Package occurred 6 times" but the OC-DFG shows 4 unique Pack events (e11–e14), I treat the OC-DFG unique-event count as authoritative for *frequency* and the flattened count as a *per-case multiplicity* metric. General rule: flattened logs answer "what did this object experience?"; object-centric views answer "what actually happened?". Any KPI that aggregates across cases must be validated against the unique-event / OC-DFG figure, and discrepancies are reported as convergence measurements, not errors to be hidden.

## 5. Lead-object decision

**Position chosen: B — a primary lead object (Order) plus explicitly secondary lifecycles (Package/Delivery for logistics, Invoice/Payment for finance).**

**Decision criteria.** (1) Vocabulary coverage: does the lens see the whole activity set? (2) Distortion cost: how much convergence/divergence does it introduce? (3) Stakeholder question fit: does it answer the natural end-to-end question? (4) Reparability: can its distortions be corrected with deduplication rather than being intrinsic?

**Strongest supporting evidence.** Only the Order lens touches every activity from Create Order (e01) to Close Order (e28–e31). Items, Packages, Deliveries, Invoices, and Payments each see a strict subset and are structurally truncated (no lens except Order sees Close Order). Thus Order is the only viable *spine* for an end-to-end story. Its distortions — spurious Add→Add (7), doubled Pack/Dispatch for O1 (8), duplicated shared payment (5) — are all *repairable* by deduplicating copied events and by cross-checking against the Package/Invoice lenses, rather than being irreducible. That is why Order is primary but not sole.

**Strongest counterargument.** The Order lens systematically *hides* the very business facts the brief highlights: cross-order packing (P3,P4), delivery consolidation (D2 spanning three orders), and consolidated invoicing (V2). These are convergence phenomena that the Order lens either double-counts or flattens away, and no amount of deduplication reconstructs the parcel- and invoice-level truth. This is exactly why a *single* lead object should not dominate (rejecting Position A), and why the secondary lifecycles are mandatory rather than optional.

**Residual risk.** Even with Order-as-spine plus secondaries, analysts may still read duplicated Order events as rework and compute inflated per-order throughput. There is also reconciliation overhead: contradictory counts between lenses require disciplined use of unique-event metrics.

**Conditions under which I would change the decision.** (a) If the analytical question were purely logistics (parcel throughput, consolidation efficiency), I would switch the lead to Package and demote Order — moving toward Position A on Package. (b) If it were purely order-to-cash, Invoice becomes lead. (c) If cross-order entanglement were so dense that even the Order spine's duplication overwhelmed interpretation, I would abandon a lead entirely (Position C) and work only from the OC-DFG/ET–OT views. As given, the entanglement is moderate and repairable, so B is defensible.

## 7. Sensitivity and validation plan

**(1) Remove / down-weight copied shared events.** Recompute Order-lens activity frequencies and DFG edge weights after deduplicating the 8 shared events (e13,e14,e16,e17,e19,e22,e24,e25) to unique occurrences. If Pack Package drops from 6 to 4 and Record Payment's spurious self-edge (from e22/e25 under O2,O3) disappears, distortions (1),(2),(5),(8) are confirmed as convergence artifacts and any KPI sensitive to them is flagged.

**(2) Direct vs. propagated relations.** Build `ocel_prop` by propagating V→O→I and re-flatten on Item so that Items inherit Issue Invoice / Record Payment / Close Order. Compare Item-lens trace lengths and activity sets against the direct baseline. Large gains in Item lifecycle completeness reveal how much the direct E2O truncation (distortion 10) was hiding — but I report both, never replacing the baseline.

**(3) Change the lead object.** Re-run the whole portfolio with Package as lead, then Invoice as lead. Check whether business facts that vanish under Order (P3/P4 cross-order composition; V2 consolidation) reappear, and whether new distortions emerge (Package's loss of Create/Close). This tests the robustness of the Position-B recommendation and identifies which questions force a lead switch.

**(4) Frequency-metric triangulation.** For each activity, compute three counts: (a) event occurrences in the flattened log (case-multiplicity), (b) unique events, (c) total distinct objects touched, using the OC-DFG. For Pack Package expect (a)=6, (b)=4, (c)=6 packages/… ; for Record Payment expect (a)=6 under Order but (b)=4 unique events (M1–M4). Divergence among the three metrics is the quantitative signature of convergence and is reported explicitly rather than collapsed to one number.

**(5) Near-singleton and truncation check.** Verify that Payment traces have length 1 (M1–M4) and that non-Order lenses never contain Close Order. Confirm these are scope effects, not data quality defects, so downstream conformance checking does not penalize "missing" completion on the Item/Package/Invoice/Payment logs.
