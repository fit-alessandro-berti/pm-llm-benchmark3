# Process Mining Model Review: Custom Order Dossier

---

# 1. Review Scope and Assumptions

## Intended Use Cases

Three distinct use cases interact with these models:

1. **Exploration & discovery** (business process analysts, early-stage design)
   - Goal: reveal actual behavior patterns without enforcing rules
   - Acceptable fitness/precision trade-off: fitness  0.90; precision may be 0.50–0.70
   - Risk if wrong: false negatives (missed business patterns); low cost to revise
   - Model preference: permissive, fast, comprehensible

2. **Compliance & enforcement** (audit, legal, system enforcement)
   - Goal: reject cases that violate policy; approve those that conform
   - Acceptable trade-off: precision  0.85; fitness  0.75 (accept some unseen legitimate variants)
   - Risk if wrong: false positives (blocking valid work) are expensive; false negatives (passing violations) are expensive but less obvious
   - Model preference: conservative, transparent, contestable

3. **Simulation & prediction** (capacity planning, staffing, throughput)
   - Goal: generate representative traces that match observed distribution
   - Acceptable trade-off: fitness  0.92; precision  0.75; generalization  0.80
   - Risk if wrong: unrealistic traces lead to miscalibrated resource allocation
   - Model preference: balanced, validated on unseen cases

**Current problem:** Both teams presented their models as general-purpose; neither explicitly declared their primary use case. Stakeholder feedback (F1, F2, F3, F6, F8) reveals that Model S is defended for exploration and Model C for compliance, but their reported metrics are cross-contaminated (alignment fitness is not a compliance metric; precision on training data is not a generalization metric).

**Key assumption:** We accept P1–P7 as binding policy constraints; the behavior probes B1–B8 are consistency checks, not ground truth. Missing attributes (external/internal sourcing, affected checks) are treated as a **data collection debt**, not a reason to ignore the constraints.

## Summary of Metric Pathologies (ranked by decision impact)

1. **Holdout fitness gap (0.981 vs. 0.744) is unexplained.** Without knowing which cases were held out, whether they contain missing events, and whether they represent violations or legitimate unseen combinations, this gap could support either model.

2. **Training precision without negative traces (0.941 vs. 0.584) reflects training-data memorization, not generalization.** Model C's high precision on training data paired with its collapse on holdout data is a textbook overfitting signature.

3. **Duplicate-label metric is undefined.** Its presence in the table with no definition casts doubt on the rigor of the entire comparison.

4. **Token-based generalization (0.907 vs. 0.412) is a permissiveness reward, not a compliance metric.** It penalizes conservative models and should not be used to defend exploratory looseness in a compliance context.

5. **No published random seed, preprocessing, or alignment-cost weights.** Results cannot be reproduced; differences may be artifacts of implementation choices rather than model semantics.

# 3. Adversarial Review of Model S

## Strongest Case FOR Model S

- **Practical robustness:** If the control-flow log contains noise (missing events, recording delays, or system-recorded approximations), Model S's permissiveness allows genuine behavior to be recognized rather than flagged as violations.
- **Exploration value:** Model S has captured a simple, communicable backbone (Register  mandatory checks in parallel  optional reviews  approval  Release) that business users understand and can extend.
- **Handling of P6 implicitly:** Model S's `+()` (unordered choice) loop allows Credit Check and Technical Review to repeat without explicit Correct Dossier. This is pragmatic if the log does not reliably record corrections.
- **Fast alignment (0.018 s):** Real-time applicability in high-volume scenarios.
- **Non-prescriptive:** By not enumerating paths, Model S resists the brittleness that F2 describes (rejecting legitimate new combinations).

## Strongest Case AGAINST Model S

Model S is **non-compliant with stated policy P1–P7** in multiple ways:

### Five Concrete Undesirable Behaviors

**Trace 1: Violates P2 (both mandatory checks required)**
```
Register Dossier
 Expedite Review
 Manager Approval
 Release Order
```
**Acceptance by Model S:** YES. The `+()` loop allows zero iterations of Credit Check and Technical Review.  
**Assessment:** Explicitly forbidden by F1 and P2. This is not noise tolerance; it is semantic erasure of a mandatory constraint.

**Trace 2: Violates P4 (Expedite Review must follow both mandatory checks)**
```
Register Dossier
 Expedite Review
 Credit Check
 Technical Review
 Manager Approval
 Release Order
```
**Acceptance by Model S:** YES. The `+()` loop does not enforce an order; Expedite Review can precede both checks.  
**Assessment:** Explicitly forbidden by P4. Model S's use of `+()` (interleaving choice) rather than a guarded optional creates an orderless bag, not a constrained flow.

**Trace 3: Violates P5 (exactly one approval, not zero)**
```
Register Dossier
 Credit Check
 Technical Review
 Release Order
```
**Acceptance by Model S:** YES. Both Manager Approval and Auto Approval are optional in the `+()` loop; the model can skip both.  
**Assessment:** Explicitly forbidden by P5 and violates the invariant "exactly one approval must occur."

**Trace 4: Violates P2 (Credit Check is mandatory)**
```
Register Dossier
 Technical Review
 Supplier Review
 Expedite Review
 Manager Approval
 Release Order
```
**Acceptance by Model S:** YES. The loop allows zero occurrences of Credit Check.  
**Assessment:** Violates P2 and the implicit assumption that both mandatory checks are present before approval.

**Trace 5: Violates P5 (exactly one approval, not two)**
```
Register Dossier
 Credit Check
 Technical Review
 Manager Approval
 Auto Approval
 Release Order
```
**Acceptance by Model S:** YES. The `+()` loop allows arbitrary repetitions. Both Manager Approval and Auto Approval can occur.  
**Assessment:** Violates P5 ("exactly one").

### Categorization

- **Traces 1, 3, 5** arise from `+()` allowing zero or multiple iterations of elements, including those marked as mandatory or exclusive.
- **Traces 2, 4** arise from no ordering constraint within the `+()` loop.

**Assessment:** These are not noise-tolerance misses; they are **semantic flaws**. The notation `+()` does not have a built-in "at least once per activity" or "mutual exclusion" constraint. The model's simplicity has eliminated guardrails, not relaxed them intelligently.

**Why this happened:** The team appears to have used `+()` to say "these can happen in any order and possibly repeat," but the intent was "these can interleave, but each must occur at least once, and some are mutually exclusive." The mismatch is critical for a compliance model.

# 4. Adversarial Review of Model C

## Strongest Case FOR Model C

- **Explicit policy enforcement:** Model C enumerates traces that respect P1–P5 (as far as variant logic allows). Each branch is auditable.
- **No false accepts:** Model C rejects Traces 1–5 from the adversarial review above, correctly identifying them as violations.
- **Correction-loop handling:** Model C includes one example of Credit Check and Technical Review repeated (after Correct Dossier), honoring P6 implicitly.
- **Audit trail:** The explicit branching allows stakeholders to see exactly which combinations are allowed, making it contestable.
- **Precision on training (0.941):** Few alternate alignments per trace suggest clear, deterministic paths—useful for reproducible audits.

## Strongest Case AGAINST Model C

Model C faces **five critical defects:**

### 1. **Branch Enumeration Explosion and Incompleteness**

Model C lists 8 explicit variants. But P3, P4, and P6 suggest additional valid combinations not in the list:

- **P3 (Supplier Review optional for external orders):** Model C includes it in 4 of 8 variants. But it does not know which orders are external. If an external order skips Supplier Review, or an internal order includes it, Model C cannot conditionally accept or reject.
- **P4 (Expedite Review optional, can follow both checks, may occur before or after Supplier Review):** Model C's enumeration includes Expedite Review in only 2 of 8 variants, always after Supplier Review. It does **not** include traces where Expedite Review comes before Supplier Review (e.g., after Technical Review). This violates P4's "may occur before or after Supplier Review."

**Example missing valid trace under P4:**
```
Register Dossier
 Credit Check
 Technical Review
 Expedite Review
 Manager Approval
 Release Order
```
(No Supplier Review for internal orders; Expedite Review placed before where Supplier Review would be.)

**Does Model C accept this?** NO. It is not in the enumeration.  
**Should it?** YES, under P4.

### 2. **Duplicate Labels and Ambiguous Repetition (P6)**

Model C's branches include:
```
->(...'Correct Dossier', 'Credit Check', 'Technical Review'...)
```

This enumerates one specific recheck scenario (both checks re-run). But P6 says:
> "After correction, only the checks affected by the correction should repeat."

Model C does not distinguish whether a repeated check is due to a correction affecting it or a false positive (P7, suspicious). It also does not show branches where only Credit Check repeats, or only Technical Review repeats. This is **incomplete enforcement of P6**.

Additionally, because duplicate activity labels appear in multiple branches, the "33 duplicate labels" reported suggests the model was parsed or generated in a way that created ambiguity about which occurrence is which. This hampers audit clarity (F3).

### 3. **Holdout Fitness Collapse (0.744)**

Model C aligns only 74.4% of unseen cases. Stakeholder feedback (F2, F4) suggests that some holdout cases represent:
- Legitimate unseen combinations (e.g., Auto Approval with Supplier Review and Expedite Review in a new order)
- Missing events in the log (Supplier Review may not be recorded consistently)

If holdout cases are legitimate, Model C is **incorrectly rejecting valid business behavior.** If they are violations, the team should have published a curated negative trace suite to show this (F5 criticism applies). Instead, the holdout fitness is unexplained, and the team's defense (F8: "unseen behavior should be treated as noncompliant") is a **circular argument:** "we reject unseen cases, so we fit unseen cases poorly, therefore unseen cases are violations."

### 4. **Maintainability and Extensibility (F2, F3)**

The model is brittle. Adding a new valid combination requires editing the enumeration and re-testing all branches. With 8 variants now, and three optional elements (Supplier Review, Expedite Review, Correct Dossier + recheck), the actual policy space could be ~50+ variants. Model C does not scale.

The duplicate labels (33) and enumeration structure also make impact analysis hard: if a policy change affects "Supplier Review," which branches must be reviewed? Manual inspection is required.

### 5. **Missing Auto Approval Variants**

The enumeration includes only ONE branch with Auto Approval:
```
->('Register Dossier', 'Credit Check', 'Technical Review', 'Auto Approval', 'Release Order')
```

But P5 says "exactly one of Manager Approval and Auto Approval." Auto Approval is not inherently more restrictive than Manager Approval. Why does the model not include:
```
->('Register Dossier', 'Credit Check', 'Technical Review', 'Expedite Review', 'Auto Approval', 'Release Order')
->('Register Dossier', 'Credit Check', 'Technical Review', 'Supplier Review', 'Auto Approval', 'Release Order')
->('Register Dossier', 'Credit Check', 'Technical Review', 'Supplier Review', 'Expedite Review', 'Auto Approval', 'Release Order')
```

The lack of these variants suggests the model was built from the training log by selecting frequent branches, not from a principled encoding of P1–P7. This is **discovery**, not **specification**, yet it is being defended as "audit-ready."

### Summary

Model C's enumeration is **incomplete relative to P1–P7** and **overfit to the training log's specific traces.** Its high training precision reflects that it memorizes these traces, not that it correctly enforces policy. Its low holdout fitness reflects that new legitimate combinations fall outside the enumeration, not that the holdout cases are violations.

# 6. Likely Metric Pathologies

Ranked by likely decision impact:

### 1. **Holdout Fitness Collapse Unexplained (Model C: 0.744)**
**Pathology:** The holdout fitness drop from training (0.973) to holdout (0.744) is ~23 percentage points—unusually large. Without knowing:
- Which 20% of cases were held out
- Whether they are stratified by process variant (external vs. internal)
- Whether unseen combinations reflect missing events or true novel behavior
- The alignment-cost weight matrix

…we cannot determine whether this reflects overfitting, missing-event bias, or rejection of legitimately unseen behavior (F4).

**Impact:** This single metric is the primary driver of Model C's rejection in F2, F4, F8 arguments. If the holdout set is biased toward complex variants or toward cases with recording gaps, the metric is misleading.

**Mitigation required:** Publish holdout stratification; audit a sample of holdout cases for missing events.

---

### 2. **Training Precision Without Negative Traces (Model C: 0.941)**
**Pathology:** Precision is computed only against observed positive traces (F5 criticism). A model that says "any variant of {Credit Check, Technical Review} followed by {Supplier Review, Expedite Review} is ok" will have high precision on the training log **if the training log only contains true positives**. Precision does not penalize false positives (incorrectly accepted violations).

**Example:** If the training log never contains "Credit Check, Supplier Review without Technical Review," and the model allows it, training precision will not detect this error.

**Impact:** Model C's high precision (0.941) may be an artifact of training-log composition, not model correctness. Combined with low holdout fitness, this is a strong sign of memorization.

**Mitigation required:** Build a curated negative trace suite (violations of P1–P7) and measure precision against it.

---

### 3. **Positive-Log-Only Precision and Overfitting Signature**
**Pathology:** The pair (training precision: 0.941, training fitness: 0.973, holdout fitness: 0.744) exhibits a classic overfitting pattern:
- High performance on training data (fitness and precision both strong)
- Dramatic drop on holdout data

This occurs because Model C enumerates frequent variants observed in training. When the holdout set contains a new combination (e.g., Expedite Review before Supplier Review, or Auto Approval with Supplier Review), alignment fails because the path is not enumerated.

**Impact:** Model C's reported metrics are **not valid evidence of generalization.** The model is a compressed version of the training log, not a learned policy.

---

### 4. **Missing-Event Bias Conflates Noise with Constraint**
**Pathology:** P6 and F4 suggest that Correct Dossier and Supplier Review may be under-recorded in the log. If so:
- Model S's tolerance for repeated checks without preceding Correct Dossier may be justified (P6, P7 noise).
- Model C's enumeration of "Credit Check  Correct Dossier  Technical Review" does not prove this is the only valid recheck path; it may just be the most frequently recorded.

**Impact:** Both models are built on incomplete event data. Model S handles this by being permissive (wrong for compliance). Model C handles this by memorizing observed variants (wrong for generalization). Neither is robust.

---

### 5. **Duplicate-Label Metric Is Undefined**
**Pathology:** "Reported duplicate-label count, definition undocumented" is a report-quality failure, not a metric failure. But it signals that the comparison was not carefully executed. Possible meanings:
- Same activity label appears multiple times in the syntax tree (expected for repeated steps, a feature not a bug).
- Duplicate nodes in the Petri net conversion (a bug in the conversion).
- Ambiguous alignment (a state-space issue).

**Impact:** Without definition, this metric cannot inform the decision. Its presence suggests neither team validated their tooling carefully.

---

### 6. **Silent-Transition Effects on Simplicity and Fitness**
**Pathology:** Model S's `+()` and `X()` operators are converted to Petri nets with implicit choice and concurrency operators. Some of these conversions use silent transitions (). Silent transitions do not consume events and can affect:
- Simplicity score (are  counted as arcs?)
- Fitness (can  allow false positives?)
- Precision (do  reduce the number of distinct alignments?)

**Impact:** Model S's simplicity (0.918) and precision (0.584) may be artifacts of the silent-transition count, not true model properties. Comparison to Model C (which may use fewer ) is confounded.

---

### 7. **Alignment-Cost Sensitivity**
**Pathology:** Fitness and precision depend on the alignment-cost function (insertion, deletion, model-move costs). Neither team published their cost matrix. If Model S uses lower insertion costs, it will align more permissively. If Model C uses high deletion costs, it will reject unseen variants more harshly.

**Impact:** The reported fitness/precision differences could be entirely due to alignment-cost choices, not model semantics. **Results are not reproducible without publishing weights.**

---

### 8. **Token-Based Generalization as a Permissiveness Reward**
**Pathology:** Token-based generalization (TBR) measures whether the activity set of unseen traces is a subset of the model's activity set. It does **not** measure whether the trace order is correct. A model that says "Credit Check and Technical Review in any order or repetition" will have high TBR but violate P2 and P7.

**Example:** B8 (Register, Credit Check, Technical Review, Credit Check, Manager Approval, Release) has TBR = 1.0 if all activities are in the model's alphabet. But it violates P7. TBR is not sensitive to the violation.

**Impact:** Model S's high TBR (0.907) is misleading. It suggests good generalization, but really measures that Model S uses a broad activity alphabet and few ordering constraints. This is **a defect for compliance**, not a feature.

---

### 9. **Runtime as a Confound of Model Size and Search Space**
**Pathology:** Model S aligns in 0.018 s; Model C in 0.440 s (24× slower). This is attributed to model complexity, but it could also reflect:
- Different Petri-net sizes (Model C's enumeration may have more nodes).
- Search-space size (Model C's explicit branches may require more backtracking).
- Alignment algorithm choice (A*, Dijkstra, etc. not specified).

**Impact:** Runtime is not a measure of model quality; it is an implementation detail. For compliance checking (typically offline, batch), 0.44 s per case is acceptable. This metric should not influence the decision unless real-time alignment is a requirement.

---

### 10. **Stakeholder Comprehension Measured Informally**
**Pathology:** "Informal 1–5 score" with no protocol, inter-rater agreement, or sample size. This is anecdotal feedback, not a metric. The score of 4.4 vs. 1.9 is large, but it reflects Model S's simplicity, not its correctness.

**Impact:** Comprehension is valuable for adoption, but it should not override correctness. A model should not be deployed because users like it if it violates policy. However, if two models are equally compliant, comprehension becomes a tie-breaker.

---

### 11. **No Reproducibility; No Published Seeds or Preprocessing**
**Pathology:** Neither team provided:
- Random seed for train/test split
- Preprocessing code (filtering, aggregation, event duplication handling)
- PM4Py version
- Alignment algorithm and cost matrix
- Petri-net conversion variant

**Impact:** Results cannot be reproduced. Differences between models could be due to random variation, preprocessing differences, or actual model semantics. **Any recommendation must be conditional on reproducibility validation.**

# 7. Third Alternative

## Design Rationale

The third alternative must:
1. **Enforce P1–P7 correctly** without enumerating all combinations (addressing Model C's brittleness).
2. **Tolerate noise in event recording** (missing Correct Dossier, under-recorded Supplier Review) without creating semantic gaps (addressing Model S's compliance failures).
3. **Support conditional logic** by documenting missing attributes and providing a post-hoc policy-check layer.
4. **Be maintainable and contestable** by separating the procedural backbone from the constraints (addressing F2, F3, F6).

## Strategy: **Procedural Backbone + Declarative Constraints + Post-Hoc Policy Checks**

We design:
- A **POWL (Partially Ordered Workflow Language) procedural backbone** that enforces the main flow and mandatory ordering.
- A **declarative constraints dictionary** that encodes P1–P7 as machine-readable rules.
- A **post-hoc policy-check layer** that runs after alignment and accepts/rejects based on policy rules, not just model structure.
- Explicit **documentation of missing attributes** and how they affect policy.

### Formal Description

```
model_third = POWL(
  Transition('Register Dossier')
  + [
      PartialOrder(
        {
          'credit_check': Transition('Credit Check'),
          'tech_review': Transition('Technical Review')
        },
        edges=[(credit_check, tech_review) is_optional]  # Can occur in either order
      )
      +
      OperatorPOWL(
        [
          SilentTransition('check_credit_tech_complete'),
          OperatorPOWL([
            Transition('Supplier Review'),
            Transition('Expedite Review')
          ], 'concurrent')  # Both optional, concurrent, can occur 0+ times
        ],
        'sequence'
      )
      +
      OperatorPOWL([
        Transition('Manager Approval'),
        Transition('Auto Approval')
      ], 'xor')  # Exactly one
    ],
    'sequence'
  )
  + Transition('Release Order')
)

# Plus post-hoc policy checks (see below)
```

## Declarative Constraints Dictionary

```python
POLICY_CONSTRAINTS = {
    "P1": {
        "rule": "Register Dossier is the first activity; Release Order is the last",
        "check": lambda trace: trace[0] == 'Register Dossier' and trace[-1] == 'Release Order'
    },
    
    "P2": {
        "rule": "Credit Check and Technical Review are mandatory; both must occur before approval",
        "check": lambda trace: (
            'Credit Check' in trace and
            'Technical Review' in trace and
            (max(trace.index('Credit Check'), trace.index('Technical Review')) <
             min([trace.index(a) for a in trace if a in ['Manager Approval', 'Auto Approval']]))
        )
    },
    
    "P3": {
        "rule": "Supplier Review is required only for externally sourced orders (missing attribute)",
        "check": lambda trace, external_attr=None: (
            True  # Deferred: cannot check without external_attr
            if external_attr is None else
            (external_attr and 'Supplier Review' in trace) or (not external_attr)
        ),
        "missing_attribute": "external_internal_sourcing"
    },
    
    "P4": {
        "rule": "Expedite Review is optional, must follow both Credit Check and Technical Review, may occur before or after Supplier Review",
        "check": lambda trace: (
            'Expedite Review' not in trace or  # Optional
            (
                all(x in trace for x in ['Credit Check', 'Technical Review']) and
                max(trace.index('Credit Check'), trace.index('Technical Review')) < trace.index('Expedite Review')
            )
        )
    },
    
    "P5": {
        "rule": "Exactly one of Manager Approval or Auto Approval occurs before Release Order",
        "check": lambda trace: (
            (trace.count('Manager Approval') + trace.count('Auto Approval')) == 1 and
            all(a in trace for a in ['Manager Approval', 'Auto Approval']) is False
        )
    },
    
    "P6": {
        "rule": "Correct Dossier may repeat. After correction, only affected checks should repeat (missing 'affected' attribute)",
        "check": lambda trace, affected_attrs=None: (
            True  # Deferred: cannot fully check without affected_attrs
            if affected_attrs is None else
            # Heuristic: after Correct Dossier, Credit Check or Technical Review repeat
            all(
                (trace[i-1] == 'Correct Dossier' and trace[i] in ['Credit Check', 'Technical Review'])
                for i in range(len(trace)) if i > 0 and trace[i] in ['Credit Check', 'Technical Review']
                and i > trace.index('Correct Dossier')
            ) if 'Correct Dossier' in trace else True
        ),
        "missing_attribute": "affected_check_types"
    },
    
    "P7": {
        "rule": "A repeated mandatory check without a preceding Correct Dossier is suspicious",
        "check": lambda trace: (
            True if 'Correct Dossier' not in trace else
            # If a mandatory check repeats after Correct Dossier, it is defensible.
            # If it repeats without Correct Dossier, flag it.
            not (
                ('Credit Check' in trace[trace.index('Correct Dossier')+1:] and
                 trace[:trace.index('Correct Dossier')].count('Credit Check') > 0) or
                ('Technical Review' in trace[trace.index('Correct Dossier')+1:] and
                 trace[:trace.index('Correct Dossier')].count('Technical Review') > 0)
            ) or
            (trace.count('Credit Check') == 1 and trace.count('Technical Review') == 1)
        ),
        "severity": "warning"  # Suspicious, not forbidden
    }
}

# Missing data attributes that block full enforcement

    "affected_check_types": "List of activity names (e.g., ['Credit Check']) that the correction affected"
}
```

## Post-Hoc Policy Check Function

```python
def check_policy_compliance(trace_list, policy_dict=POLICY_CONSTRAINTS, 
                             external_attrs=None, affected_attrs=None):
    """
    Given a list of activity names, evaluate against policy constraints.
    
    Args:
        trace_list: list of activity names, e.g., ['Register Dossier', 'Credit Check', ...]
        policy_dict: POLICY_CONSTRAINTS
        external_attrs: dict mapping case_id to external_internal sourcing boolean
        affected_attrs: dict mapping case_id to list of affected check types
        
    Returns:
        dict with keys:
          - 'compliant': bool
          - 'violations': list of policy rule names that failed
          - 'warnings': list of suspicious patterns
          - 'missing_data': list of policies that cannot be checked due to missing attributes
    """
    
    violations = []
    warnings = []
    missing_data = []
    
    for policy_name, constraint in policy_dict.items():
        rule_fn = constraint['check']
        
        # Invoke the check with available data
        if policy_name == 'P3':
            # P3 requires external_attr
            result = (external_attrs is not None and 
                      rule_fn(trace_list, external_attr=external_attrs))
            if external_attrs is None:
                missing_data.append(('P3', 'external_internal_sourcing'))
        elif policy_name == 'P6':
            # P6 requires affected_attrs
            result = (affected_attrs is not None and 
                      rule_fn(trace_list, affected_attrs=affected_attrs))
            if affected_attrs is None:
                missing_data.append(('P6', 'affected_check_types'))
        else:
            result = rule_fn(trace_list)
        
        if not result:
            if constraint.get('severity') == 'warning':
                warnings.append(policy_name)
            else:
                violations.append(policy_name)
    
    return {
        'compliant': len(violations) == 0,
        'violations': violations,
        'warnings': warnings,
        'missing_data': missing_data
    }

# Example usage:
trace_b1 = ['Register Dossier', 'Credit Check', 'Technical Review', 'Manager Approval', 'Release Order']
result = check_policy_compliance(trace_b1)
print(result)
# Expected: {'compliant': True, 'violations': [], 'warnings': [], 'missing_data': [('P3', ...), ('P6', ...)]}

trace_b3 = ['Register Dossier', 'Manager Approval', 'Release Order']
result = check_policy_compliance(trace_b3)
print(result)
# Expected: {'compliant': False, 'violations': ['P1', 'P2', ...], ...}
```

## Hybrid Acceptance Logic

```python
def accept_case(trace_list, alignment_fitness_score, policy_check_result, 
                 fitness_threshold=0.80, allow_missing_data=False):
    """
    Accept a case if:
    1. It aligns with the model (fitness >= threshold)
    2. It passes policy constraints (no violations)
    3. Missing-data policies are either deferred or not required
    
    Args:
        trace_list: list of activities
        alignment_fitness_score: fitness from pm4py alignment
        policy_check_result: output of check_policy_compliance
        fitness_threshold: minimum alignment fitness (default 0.80)
        allow_missing_data: if True, defer P3/P6 checks; if False, reject if missing data
        
    Returns:
        dict:
          - 'decision': 'accept' | 'reject' | 'defer'
          - 'reason': explanation
          - 'action': next step (e.g., 'manual review', 'approve', 'quarantine')
    """
    
    if alignment_fitness_score < fitness_threshold:
        return {
            'decision': 'defer',
            'reason': f'Low alignment fitness ({alignment_fitness_score:.2f} < {fitness_threshold})',
            'action': 'manual_review'
        }
    
    if policy_check_result['violations']:
        return {
            'decision': 'reject',
            'reason': f"Violations of policies: {policy_check_result['violations']}",
            'action': 'quarantine'
        }
    
    if policy_check_result['missing_data']:
        if allow_missing_data:
            return {
                'decision': 'accept',
                'reason': f"Policy check passed (with deferred checks: {policy_check_result['missing_data']})",
                'action': 'approve'
            }
        else:
            return {
                'decision': 'defer',
                'reason': f"Missing data for policies: {policy_check_result['missing_data']}",
                'action': 'manual_review'
            }
    
    if policy_check_result['warnings']:
        return {
            'decision': 'accept',
            'reason': f"Accepted with warnings: {policy_check_result['warnings']}",
            'action': 'approve_with_flag'
        }
    
    return {
        'decision': 'accept',
        'reason': 'Fully compliant',
        'action': 'approve'
    }
```

## Limitations Caused by Missing Attributes

The model **cannot fully enforce P3 and P6** without:

1. **external_internal_sourcing** attribute on each case:
   - Enables conditional acceptance of Supplier Review (required if external, optional if internal).
   - Without it, the model must assume all Supplier Review occurrences are optional, losing a compliance constraint.

2. **affected_check_types** attribute on each Correct Dossier event:
   - Enables validation that only affected checks are re-run.
   - Without it, the model cannot distinguish between "both checks re-ran because both were affected" (valid) and "both checks re-ran because of sloppy correction handling" (potentially wasteful).

**Mitigation:**
- Flag all cases with Correct Dossier as "deferred" or "review required" until the attribute is recorded.
- Collect this metadata prospectively in a data-quality initiative; backfill historical cases if possible.

## Model Third in Process Tree Syntax

A simpler version that balances enforcement and flexibility:

```
->(
  'Register Dossier',
  X(
    ->(
      'Credit Check',
      'Technical Review'
    ),
    ->(
      'Technical Review',
      'Credit Check'
    )
  ),
  *(
    X(
      'Supplier Review',
      'Expedite Review'
    )
  ),
  X(
    'Manager Approval',
    'Auto Approval'
  ),
  'Release Order'
)
```

**Interpretation:**
- `->` (sequence): Register, then checks, then optional reviews, then approval, then Release.
- `X(..., ...)`: Credit Check and Technical Review can occur in either order (first position), but the sequence is fixed.
- `*()`: Loop allows Supplier Review and Expedite Review to occur 0 or more times in any interleaving. (Not perfect; allows both to repeat unboundedly, but avoids enumeration.)

**Post-hoc policy layer** (check_policy_compliance) enforces:
- Exactly one approval.
- Correct Dossier + recheck semantics (heuristic, deferred if affected_attrs missing).
- Suspicious repetition warnings (P7).

```python
def load_and_preprocess_log(log_file_path):
    """
    Load event log, apply preprocessing, return cleaned log.
    Log file: CSV with columns [case_id, activity, timestamp, external_sourced (if available)]
    """
    log_df = pd.read_csv(log_file_path)
    
    # Step 1: Remove incomplete cases
    required_activities = {'Register Dossier', 'Release Order'}
    log_df['has_start_end'] = log_df.groupby('case_id')['activity'].transform(
        lambda x: all(act in set(x) for act in required_activities)
    )
    log_df = log_df[log_df['has_start_end']]
    
    # Step 2: Check timestamp consistency
    log_df['timestamp'] = pd.to_datetime(log_df['timestamp'])
    log_df['ts_ok'] = log_df.groupby('case_id')['timestamp'].transform(
        lambda x: (x.diff() >= pd.Timedelta(0)).fillna(True).all()
    )
    log_df = log_df[log_df['ts_ok']]
    
    # Step 3: Extract case variant (signature)
    case_variants = log_df.groupby('case_id')['activity'].apply(
        lambda x: ''.join(x)
    ).reset_index(name='variant')
    
    # Step 4: Convert to pm4py EventLog
    event_log = EventLog()
    for case_id, group in log_df.groupby('case_id'):
        trace = pm4py.objects.log.obj.Trace()
        for _, row in group.sort_values('timestamp').iterrows():
            event = Event()
            event['concept:name'] = row['activity']
            event['time:timestamp'] = row['timestamp']
            if 'external_sourced' in row.columns:
                event['ext:external_sourced'] = row['external_sourced']
            trace.append(event)
        trace.attributes['concept:name'] = case_id
        event_log.append(trace)
    
    return event_log, case_variants

def stratified_train_test_split(log, case_variants, train_ratio=0.80, seed=42):
    """
    Stratify split by case variant to ensure both sets have representative mixes.
    """
    random.seed(seed)
    
    # Group cases by variant
    variant_cases = case_variants.groupby('variant')['case_id'].apply(list).to_dict()
    
    train_log = pm4py.objects.log.obj.EventLog()
    test_log = pm4py.objects.log.obj.EventLog()
    
    for variant, cases in variant_cases.items():
        # Shuffle and split
        random.shuffle(cases)
        split_point = int(len(cases) * train_ratio)
        train_cases, test_cases = cases[:split_point], cases[split_point:]
        
        # Add to respective logs
        for trace in log:
            if trace.attributes['concept:name'] in train_cases:
                train_log.append(trace)
            elif trace.attributes['concept:name'] in test_cases:
                test_log.append(trace)
    
    return train_log, test_log
```

```python
def perturb_log_missing_events(log, drop_activity_set, drop_probability=0.3):

    Simulate missing events: randomly drop activities (e.g., Correct Dossier under-recorded).

    perturbed = pm4py.objects.log.obj.EventLog()
    
    for trace in log:
        perturbed_trace = pm4py.objects.log.obj.Trace()
        for event in trace:
            activity = event['concept:name']
            if activity in drop_activity_set and random.random() < drop_probability:
                # Skip this event
                continue
            perturbed_trace.append(event)
        perturbed_trace.attributes = trace.attributes
        perturbed.append(perturbed_trace)
    
    return perturbed

def perturb_log_duplicate_events(log, duplicate_activity_set, dup_probability=0.2):
    """
    Simulate duplicate events: randomly repeat activities (e.g., system double-records).
    """
    perturbed = pm4py.objects.log.obj.EventLog()
    
    for trace in log:

                perturbed_trace.append(event)
        perturbed_trace.attributes = trace.attributes
        perturbed.append(perturbed_trace)
    
    return perturbed
```

```python
    """
    Identify activity bigrams (consecutive pairs) in test_log not in train_log.
    """
    def extract_bigrams(log):
        bigrams = set()

                bigrams.add((activities[i], activities[i+1]))
        return bigrams
    
    train_bigrams = extract_bigrams(train_log)
    test_bigrams = extract_bigrams(test_log)
```

### 9.8 Fitness, Precision, Generalization, Simplicity – Disaggregated

```python
def evaluate_model_comprehensive(model, train_log, test_log, negative_traces=None):
    """
    Compute all metrics separately, reported disaggregated.
    """
    
    # Convert model to Petri net
    net, im, fm = pm4py.convert_to_petri_net(model)
    
    # Validate structure
    assert validate_model_structure(net, im, fm), "Model is not sound"
    
    # Fitness on training
    fit_train = pm4py.fitness_alignments(train_log, net, im, fm)
    fit_train_avg = sum(f['fitness'] for f in fit_train) / len(fit_train)
    
    # Fitness on holdout
    fit_test = pm4py.fitness_alignments(test_log, net, im, fm)
    fit_test_avg = sum(f['fitness'] for f in fit_test) / len(fit_test)
    
    # Precision on training (positive traces only)
    prec_train_pos = pm4py.precision_alignments(train_log, net, im, fm)
    
    # Precision on negative traces (if provided)
    prec_neg = None
    if negative_traces:
        # Convert negative_traces to EventLog
        neg_log = pm4py.objects.log.obj.EventLog()
        for neg_trace_dict in negative_traces:
            trace = pm4py.objects.log.obj.Trace()
            for activity in neg_trace_dict['trace']:
                event = Event()
                event['concept:name'] = activity
                trace.append(event)
            neg_log.append(trace)
        
        # Measure: how many negative traces are rejected (do not align)?
        neg_fit = pm4py.fitness_alignments(neg_log, net, im, fm)
        avg_neg_fitness = sum(f['fitness'] for f in neg_fit) / len(neg_fit)
        prec_neg = 1.0 - avg_neg_fitness  # Precision on negatives = rejection rate
    
    # Token-based generalization
    gen_tbr = pm4py.generalization_tbr(test_log, net, im, fm)
    
    # Simplicity (arc-degree variant)
    simp = pm4py.simplicity_petri_net(net, im, fm, variant="arc_degree")
    
    return {
        'fitness_train': fit_train_avg,
        'fitness_test': fit_test_avg,
        'precision_train_positive': prec_train_pos,
        'precision_negative': prec_neg,
        'generalization_tbr': gen_tbr,
        'simplicity_arc_degree': simp,
        'net_nodes': len(net.places) + len(net.transitions),
        'net_arcs': len(net.arcs)
    }
```

```python
def measure_stakeholder_comprehension(model_dict, stakeholder_group=None):
    """
    Protocol for measuring comprehension of a model by a stakeholder group.
    
    Stakeholder groups: ['business_analysts', 'compliance_officers', 'it_architects']
    
    Measure: ability to predict model behavior on test traces and to modify the model.
    """
    
    comprehension_questions = [
        {
            'trace': ['Register Dossier', 'Credit Check', 'Technical Review', 'Manager Approval', 'Release Order'],
            'question': 'Will the model accept this trace?',
            'expected_answer': 'yes'
        },
        {
            'trace': ['Register Dossier', 'Manager Approval', 'Release Order'],
            'question': 'Will the model accept this trace?',
            'expected_answer': 'no'
        },
        {
            'trace': ['Register Dossier', 'Technical Review', 'Credit Check', 'Supplier Review', 'Manager Approval', 'Release Order'],
            'question': 'Will the model accept this trace?',
            'expected_answer': 'yes'  # Assuming internal order; policy-dependent for Supplier Review
        },
        {
            'question_text': 'If we add a new approval type (Director Approval), how would you modify the model to allow exactly one of {Manager, Auto, Director}?',
            'task': 'model_modification',
            'expected_difficulty': 5.0  # 1=trivial, 5=complex
        }
    ]
    
    scores = {}
    for q in comprehension_questions:
        # Administer question to stakeholder group; record correctness and time
        # (In a real study, this would be a structured interview or survey)
        scores[q.get('question_text', q.get('question'))] = {
            'correctness': 0.0,  # Placeholder
            'time_seconds': 0.0,
            'confidence': 0.0
        }
    
    # Aggregate: comprehension score = (correctness + 1.0 - time_penalty) / 2
    # where time_penalty = min(1.0, elapsed_time / expected_time)
    
    overall_score = sum(s['correctness'] for s in scores.values()) / len(scores)
    
    return {
        'overall_comprehension': overall_score,  # 0–1
        'detail': scores
    }
```

```python
def decide_model_acceptability(metrics, model_name, use_case='compliance'):
    """
    Decision rule: accept a model if it meets these thresholds.
    
    use_case: 'exploration', 'compliance', 'simulation'
    """
    
    thresholds = {
        'exploration': {
            'fitness_train_min': 0.85,
            'fitness_test_min': 0.80,
            'precision_negative_min': 0.50,  # Lower threshold; exploratory
            'generalization_tbr_min': 0.70,
            'simplicity_min': 0.60
        },
        'compliance': {
            'fitness_train_min': 0.92,
            'fitness_test_min': 0.75,
            'precision_negative_min': 0.80,  # High threshold; must reject violations
            'generalization_tbr_min': 0.65,  # More conservative (OK to be restrictive)
            'simplicity_min': 0.50  # Explicitness is OK
        },
        'simulation': {
            'fitness_train_min': 0.90,
            'fitness_test_min': 0.85,
            'precision_negative_min': 0.70,
            'generalization_tbr_min': 0.75,
            'simplicity_min': 0.60
        }
    }
    
    thres = thresholds[use_case]
    
    failures = []
    
    if metrics['fitness_train'] < thres['fitness_train_min']:
        failures.append(f"Training fitness ({metrics['fitness_train']:.3f}) < {thres['fitness_train_min']}")
    
    if metrics['fitness_test'] < thres['fitness_test_min']:
        failures.append(f"Holdout fitness ({metrics['fitness_test']:.3f}) < {thres['fitness_test_min']}")
    
    if metrics.get('precision_negative') is not None and metrics['precision_negative'] < thres['precision_negative_min']:
        failures.append(f"Negative precision ({metrics['precision_negative']:.3f}) < {thres['precision_negative_min']}")
    
    if metrics['generalization_tbr'] < thres['generalization_tbr_min']:
        failures.append(f"Generalization TBR ({metrics['generalization_tbr']:.3f}) < {thres['generalization_tbr_min']}")
    
    if metrics['simplicity_arc_degree'] < thres['simplicity_min']:
        failures.append(f"Simplicity ({metrics['simplicity_arc_degree']:.3f}) < {thres['simplicity_min']}")
    
    # Additional gate: check if fitness is too high relative to negative precision
    # (overfitting signature)
    if metrics['fitness_train'] > 0.95 and metrics.get('precision_negative', 1.0) < 0.70:
        failures.append("Overfitting signature: high training fitness, low negative precision")
    
    decision = 'ACCEPT' if len(failures) == 0 else 'REJECT'
    
    return {
        'model': model_name,
        'use_case': use_case,
        'decision': decision,
        'failures': failures,
        'metrics_summary': {
            'fitness_train': metrics['fitness_train'],
            'fitness_test': metrics['fitness_test'],
            'precision_negative': metrics.get('precision_negative'),
            'generalization_tbr': metrics['generalization_tbr'],
            'simplicity': metrics['simplicity_arc_degree']
        }
    }
```

# 11. Dissenting View

## 150–250 Word Rebuttal

**Counter-argument: Model C should be deployed pending data collection.**

The analysis above is overly harsh to Model C. The criticism rests on three assumptions that may not hold:

1. **Holdout fitness collapse is not overfitting; it is correct rejection.** The 80/20 split was not published, but if the holdout set is enriched with genuine new combinations (which process data naturally exhibits), Model C's 0.744 fitness may reflect sound policy enforcement, not overfitting. F8 ("unseen behavior should be treated as noncompliant until approved") is a defensible governance position for compliance-critical systems.

2. **Enumeration is not a defect; it is transparency.** Model C's explicit branching is auditable: a stakeholder can see exactly which combinations are allowed and contest them. Model Third's procedural backbone with post-hoc policy checks adds complexity and runtime, and defers P3/P6 indefinitely. In high-stakes compliance, explicit enumeration may be preferable to a "more maintainable" black box.

3. **The missing external_internal and affected_check attributes are not a blocker.** Model C handles them by assuming all orders are external (i.e., Supplier Review is optional for all). This is conservative and safe. If a later data collection reveals that some orders are internal (Supplier Review mandatory), the enumeration can be updated. This is not ideal, but it is not a deployment blocker.

**Recommendation: Deploy Model C operationally, with quarterly review gates.** Require Model C to maintain precision  0.80 on a growing negative-trace suite (built retrospectively from rejections). If precision drops, revert to Model Third or a hybrid.

---

## What Would Change This Rebuttal?

Evidence that would overturn this dissenting view:

1. **Audit of 50+ holdout cases labeled "legitimate" by domain experts.** If >30% of holdout cases are legitimate unseen variants (not violations), Model C's rejection is indefensible.

2. **Curated negative trace suite showing Model C's precision < 0.75 on violations.** If Model C accepts >25% of obvious violations, it has failed its compliance function.

3. **Stakeholder comprehension study showing Model C scores < 2.0/5.** If business users cannot explain what Model C accepts, it fails the transparency criterion.

4. **Data availability on external_internal sourcing showing that >20% of orders are internal.** If many orders are internal and Model C wrongly requires (or wrongly permits) Supplier Review, the assumption of "all external" is broken.

Any one of these would strengthen the case for Model Third and weaken Model C's deployment candidacy.
