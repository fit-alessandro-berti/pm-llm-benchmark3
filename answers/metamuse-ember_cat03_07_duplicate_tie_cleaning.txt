## 1. Duplicate-handling decision tree

Start with a candidate group sharing harmonized activity and timestamp plus some shared objects. Sharing those fields is only a reason to inspect, never a reason to delete.

1. **Exact technical duplicate?** Check same source, `source_event_key`, `source_seq`, `payload_hash`, activity, timestamp, and object set.
   - Yes: **drop** all but one copy, log dropped key.
   - No: continue. In this dataset no pair is exact: e03/e04 already differ in payload hash.

2. **Does a discriminating object differ?** Discriminating types are identity-bearing objects such as Item `I1/I2`, Payment `M1/M2`, Package, Delivery, or Invoice. If yes, the events are concurrent same-label events.
   - **Retain both unchanged**, with a concurrency qualifier. This protects e05 and e14.

3. **Harmonization collision?** If original source meanings differ although harmonization assigned the same label, e.g. warehouse release versus carrier acceptance, **retain both with refined labels** restoring source semantics. Never merge merely because objects coincide.

4. **Summary derived from a detailed event?** If one event is an abstraction/summary of another, e.g. ERP updates from WMS messages, conservatively **retain both with refined labels and a `derived_from` link**. Merging is allowed only in an explicitly scoped evidence-based scenario.

5. **Same physical event observed by multiple systems?** Require independent evidence: reconciliation report, same invoice/business-object identity, payload differences explained by enrichment or field authority, and no discriminating difference.
   - Yes: **merge attributes and relations** into one canonical event, retaining each source’s attributes and provenance.
   - No: continue.

6. **Unresolved candidate.** If evidence conflicts or scope is unknown, **quarantine for review**: keep in staging/raw, exclude from the primary cleaned OCEL, and record the missing evidence. If evidence proves distinctness, **retain both unchanged**.

## 3. Timestamp-tie ordering rules

The pipeline builds a **partial order**, tests it for consistency, and only then chooses a deterministic display order.

- **R1 Domain/lifecycle constraints — semantic.** Picks of items contained in a package precede packing that package; an invoice precedes payments against it; authorize M1 precedes capture M1. These are business constraints, subject to modelling completeness.
- **R2 Within-source sequence — semantic-local.** `source_seq` orders events only inside the same source. Carrier seq 1 before 2 supports e09 before e10. Sequences are not comparable across ERP, WMS, PSP, etc.
- **R3 Shared-object lifecycle — semantic but defeasible.** A shared object can support a lifecycle constraint, e.g. delivery before confirmation, but shared objects alone do not prove duplication. e13/e14 share O1/V1 yet are different payment lifecycles.
- **R4 Source-specific semantics and derivation — semantic.** e08’s warehouse-release meaning precedes e09’s carrier acceptance; a stated ERP summary generated from payment messages follows those messages. This can justify e06 before its derived e07.
- **R5 Ingestion time — non-semantic.** `ingested_at` is technical arrival time, is explicitly not guaranteed to match business order, and must never override R1–R4. It is retained only for audit.
- **R6 Stable fallback — merely deterministic.** For incomparable events, sort by canonical eid after topological ordering. This gives reproducibility, not evidence of physical order.

Adding microseconds before semantic ordering is decided encodes a false story: parallel picks become a false sequence, simultaneous events acquire artificial 1µs service times, rework loops disappear, and performance metrics inherit the invented order. Instead, preserve `original_timestamp`, compute the partial order, and store a separate `deterministic_rank`.

**10:00, e03–e07 after conservative merging:** intended display order `e03 Pick I1, e05 Pick I2, e06 Pack detailed, e07 Pack summary`. Picks precede packing. `e03` versus `e05` is incomparable; `e05, e03, e06, e07` is also admissible.

**10:15, e08–e10:** `e08 Warehouse Release, e09 Carrier Acceptance, e10 Handover`. Domain order and carrier sequence agree. Other permutations are formally possible only if these constraints are ignored.

**12:00, e11–e16 after duplicate decisions:** `e11 merged Issue Invoice, e12 Authorize M1, e13 Capture M1, e14 Capture M2, e15 ERP Capture summary`. e15 follows both captures. `e13` and `e14` are incomparable, so `e12, e14, e13, e15` is also admissible; the chosen order is deterministic, not proof of physical sequence.

## 4. Conservative cleaning pipeline

1. Freeze and hash the raw OCEL; copy it before any modification.
2. Preserve `original_timestamp`, `original_activity`, `source`, `source_event_key`, `source_seq`, `ingested_at`, and `payload_hash`.
3. Generate candidate groups by activity, timestamp, and shared objects for inspection.
4. Apply the exact-duplicate screen; `ocel_drop_duplicates` is justified only for exact-key rows. No rows qualify here.
5. Apply custom verified-pair merging only to e03/e04 and e11/e16, unioning relations and retaining source-specific attributes.
6. Refine labels without erasing originals: e08 as warehouse release, e09 as carrier acceptance, e06/e07 as detailed/summary packing, and e15 as invoice-level payment summary. Add `derived_from` links where supported.
7. Topologically order by R1–R4, assign deterministic rank for incomparable events, sort by that rank, and only then add index-based timedeltas. Validate referential integrity.

**Expected retained event count: 15** — e01, e02, merged e03, e05, e06, e07, e08, e09, e10, merged e11, e12, e13, e14, e15, e17. Distinct partial payments, distinct items, abstraction-level events, and legitimate concurrency remain.

## 5. Aggressive alternatives

### Evidence-based semantic merging

Use inspected candidate groups plus reconciliation, derivation, business-object identity, and source-authority evidence. In addition to the two conservative merges, merge e06/e07 into detailed canonical e06 because e07 is stated to be generated from the WMS message. Keep e15 separate because its payment scope is not established. Refine e08/e09 as in the conservative pipeline.

**Expected retained count: 14.** Main damage: PackPack disappears and ERP’s abstraction-level status activity is hidden. If e06/e07 were intended as separate detailed and summary observations, this scenario falsely treats an abstraction difference as duplication.

### Mechanically aggressive PM4Py merging

Run duplicate functions over the whole OCEL by activity and timestamp, using `have_common_object=True`, and union relations. The groups collapse as Pick 31, Pack 21, Dispatch 21, Issue Invoice 21, and Capture Payment 31.

**Expected retained count: 10:** e01, e02, e03, e06, e08, e10, e11, e12, e13, e17. This falsely presents one pick, one pack, one dispatch stage, one invoice issue, and one capture. It deletes e05’s I2 pick and e14’s M2 payment as independent events and creates a merged capture linked to both M1 and M2.

`have_common_object=True` is not sufficient protection because it tests only for **some** common object. e13 and e14 share O1 and V1, so they pass despite having different Payment objects. The same weakness would merge e03/e05 through O1/P1. A safer predicate must also require equality of discriminating objects and absence of a differing discriminating object.

## 6. PM4Py-oriented Python implementation

```python
import copy
import warnings
import pandas as pd
import pm4py

PROVENANCE_LOG = []

def preserve_provenance(ocel):
    events = ocel.events
    if "original_timestamp" not in events.columns:
        events["original_timestamp"] = events["timestamp"]
    if "original_activity" not in events.columns:
        events["original_activity"] = events["activity"]
    for col in ("source", "source_event_key"):
        if col not in events.columns:
            raise KeyError(f"Required provenance column missing: {col}")
    if "provenance_source_ids" not in events.columns:
        events["provenance_source_ids"] = events["eid"].astype(str)
    ocel.events = events
    return ocel

def candidate_duplicate_groups(ocel):
    grouped = ocel.events.groupby(["activity", "timestamp"], dropna=False)["eid"].apply(list)
    return grouped[grouped.apply(len) > 1]

def validate_referential_integrity(ocel, name):
    event_ids = set(ocel.events["eid"])
    object_ids = set(ocel.objects["oid"])
    relation_event_ids = set(ocel.relations["eid"])
    relation_object_ids = set(ocel.relations["oid"])
    assert ocel.events["eid"].is_unique, f"{name}: duplicate eid"
    assert relation_event_ids <= event_ids, f"{name}: relation references missing event"
    assert relation_object_ids <= object_ids, f"{name}: relation references missing object"
    assert (ocel.events["original_timestamp"] == ocel.events["timestamp"]).all()
    print(name, "events:", len(ocel.events), "E2O relations:", len(ocel.relations))

def merge_verified_pair(ocel, canonical_eid, duplicate_eid, reason):
    events, relations = ocel.events, ocel.relations
    if canonical_eid not in set(events["eid"]) or duplicate_eid not in set(events["eid"]):
        raise ValueError("Verified pair is not present")
    can_idx = events.index[events["eid"] == canonical_eid][0]
    dup_idx = events.index[events["eid"] == duplicate_eid][0]
    canonical, duplicate = events.loc[can_idx], events.loc[dup_idx]
    merged = canonical.copy()

    for col in events.columns:
        if col in {"eid", "timestamp", "activity", "original_timestamp", "original_activity"}:
            continue
        cval, dval = canonical[col], duplicate[col]
        if pd.isna(cval) and not pd.isna(dval):
            merged[col] = dval
        elif (not pd.isna(cval) and not pd.isna(dval) and cval != dval):
            if col == "provenance_source_ids":
                merged[col] = f"{cval}|{dval}"
            elif col in {"payload_hash", "source_event_key"}:
                merged[col] = f"{cval}|{dval}"
            # Otherwise retain canonical value and record the conflict below.

    events.loc[can_idx] = merged
    duplicate_relations = relations[relations["eid"] == duplicate_eid].copy()
    duplicate_relations["eid"] = canonical_eid
    ocel.relations = pd.concat([relations, duplicate_relations], ignore_index=True) \
        .drop_duplicates(subset=["eid", "oid"])
    ocel.events = events[events["eid"] != duplicate_eid].copy()

    PROVENANCE_LOG.append({
        "canonical_event_id": canonical_eid,
        "source_event_ids": [canonical_eid, duplicate_eid],
        "reason": reason,
        "discarded_conflicts": "non-canonical differing descriptive attributes retained in raw snapshot",
    })
    return ocel

def assign_deterministic_rank(ocel, order):
    rank = {eid: i for i, eid in enumerate(order)}
    ocel.events["deterministic_rank"] = ocel.events["eid"].map(rank)
    if ocel.events["deterministic_rank"].isna().any():
        raise ValueError("Deterministic order is missing retained events")
    return ocel

# Conservative scenario: ocel_raw is never modified in place.
ocel_cons = copy.deepcopy(ocel_raw)
ocel_cons = preserve_provenance(ocel_cons)
print("Candidate duplicate groups:\n", candidate_duplicate_groups(ocel_cons))

exact_cols = ["activity", "timestamp", "source", "source_event_key", "payload_hash"]
exact_mask = ocel_cons.events.duplicated(subset=exact_cols, keep=False)
print("Exact technical duplicate rows:", int(exact_mask.sum()))
# Justified here only as an exact-duplicate operation after the exact-key screen.
ocel_cons = pm4py.ocel_drop_duplicates(ocel_cons)

# Custom merge restricted to independently verified pairs.
ocel_cons = merge_verified_pair(
    ocel_cons, "e03", "e04",
    "Reconciliation report: same physical scan; WMS enrichment retained")
ocel_cons = merge_verified_pair(
    ocel_cons, "e11", "e16",
    "Same invoice V1; ERP and Billing attributes are source-authoritative")

# Label refinement is stored separately from original_activity.
refined_activity = {
    "e08": "Dispatch Package [Warehouse Release]",
    "e09": "Dispatch Package [Carrier Acceptance]",
    "e06": "Pack Package [WMS detailed]",
    "e07": "Pack Package [ERP summary]",
    "e15": "Capture Payment [ERP invoice summary]",
}
ocel_cons.events["refined_activity"] = ocel_cons.events["activity"]
for eid, label in refined_activity.items():
    ocel_cons.events.loc[ocel_cons.events["eid"] == eid, "refined_activity"] = label

intended_order = ["e01", "e02", "e03", "e05", "e06", "e07", "e08", "e09",
                  "e10", "e11", "e12", "e13", "e14", "e15", "e17"]
ocel_cons = assign_deterministic_rank(ocel_cons, intended_order)
ocel_cons = pm4py.ocel_sort_by_additional_column(ocel_cons, "deterministic_rank")
# Timedelta is added only after the deterministic order exists.
ocel_cons = pm4py.ocel_add_index_based_timedelta(ocel_cons)
validate_referential_integrity(ocel_cons, "conservative")

# Separate aggressive scenario: illustrative only, not the primary analysis.
ocel_aggr = copy.deepcopy(ocel_raw)
ocel_aggr = preserve_provenance(ocel_aggr)
warnings.warn("ocel_merge_duplicates may collapse e13/e14 because they share O1/V1 "
              "despite different Payment objects; do not use for primary analysis.")
ocel_aggr = pm4py.ocel_merge_duplicates(ocel_aggr, have_common_object=True)
validate_referential_integrity(ocel_aggr, "aggressive")
```

## 8. Audit trail and reversibility

Store one provenance record per canonical event, outside the analytical OCEL if necessary:

- `canonical_event_id`
- `source_event_ids`
- `merge_rule` and rule/reviewer version
- `original_activity`, `refined_activity`
- `original_timestamp`, `adjusted_timestamp` or deterministic rank
- `attributes_retained_by_source`, keyed by source and source event key
- `discarded_conflicts`
- `confidence`, evidence, and reviewer decision

For merged events, record both timestamps and labels even if identical; for deterministically ordered events, record the rank separately and leave the business timestamp unchanged. Retain an immutable raw OCEL snapshot, its hash, the original event and relation tables, code/rule versions, and the canonical-to-source mapping.

To reconstruct the raw view, split each canonical event back into its `source_event_ids`, restore each original event row and relation from the snapshot, discard `refined_activity`, deterministic rank, and index timedelta, then validate the expected 17 events and 44 E2O relations.

## 9. Failure modes and safeguards

| Failure mode | Safeguard |
|---|---|
| Collapsing distinct partial payments e13/e14 | Require identical discriminating Payment identity before merging |
| Converting abstraction-level updates into false rework | Use refined labels, `derived_from`, and distinguish detail from summary |
| Ordering by `ingested_at` | Prohibit ingestion as primary order; use it only for audit |
| Treating shared objects as proof of duplication | Require semantic, payload, provenance, or independent report evidence |
| Unioning incompatible E2O relations | Union only for verified same-event merges; preserve per-source relations in provenance |
| Changing durations through synthetic microseconds | Keep original timestamps; store deterministic rank separately |
| Losing source-authoritative attributes | Merge per-field with authority rules and retain conflicting values in the audit log |
| Applying duplicate functions to the whole OCEL without inspection | Generate candidate groups first; scope library use and verified merges explicitly |
| Harmonization collisions such as e08/e09 | Restore source semantics through refined labels; never merge solely on harmonized activity |
| Comparing `source_seq` across systems | Apply sequence only within the same source |
| Treating tied timestamps as proven simultaneity | Represent incomparable events as a partial order, not a claimed physical order |
