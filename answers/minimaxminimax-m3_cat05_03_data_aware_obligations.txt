## 1. Temporal Data Semantics

**State reconstruction.** For each case, I treat the log as an event-time sequence ordered by `(time:timestamp ASC, event_index ASC)`. State is a function from attribute name to the most recent non-blank value *strictly preceding* (or equal to, with smaller/equal event_index) the event under analysis. A blank cell never erases a prior value; it only means "no update at this event" (per instructions). Thus forward-filling of previously set attributes is a display convenience — the causal state is "the latest non-blank value at or before this position."

**Effective time vs. event time vs. record time vs. evidence time.**
- *Event time* = the `time:timestamp` on the event row.
- *Effective time* = the moment a value semantically takes effect, normally the event time unless a note or exemption field specifies otherwise. A "backdated" displayed field is *not* sufficient evidence of an earlier effective time.
- *Record time* = the moment a row was persisted in the system (often invisible, but surfaced by the late `Record_Exemption` rows in TX-302 and TX-310).
- *Evidence time* = the moment external proof (e.g., qualified signature creation) was produced. This is the strongest anchor for the exemption analysis in R5.

**Same-timestamp ordering.** When two events share a timestamp, `event_index` is the deterministic tie-breaker. Smaller event_index executes first. This is decisive in TX-311 (event_index 3 < 4).

**Material changes.** A *material data change* is any update to `amount`, `risk_level`, `jurisdiction`, or `customer_type`. For R4, only `amount` *increases* > 20% above the value at the latest review invalidate that review; decreases do not, and increases from an unknown prior amount are not safely classifiable (R6).

**Final attributes.** The final case attribute is *not* automatically the value that governed earlier events. Each obligation is evaluated against the snapshot reconstructed at its own trigger event.

**Unknown / missing data.** Blanks at the trigger event with no prior non-blank value are *unknown*; per R6 I do not default to a low-risk value but classify INDETERMINATE unless other evidence (e.g., a signed exemption register entry) resolves it.

**Exemption evidence.** A late database record is *not* by itself evidence of timely approval (R5). I treat the qualified signing certificate timestamp as the decisive evidence anchor when present; otherwise I weight displayed approval, effective_from, and witness statements, and discount self-interested witnesses.

|---|---|---|---|---|---|---|---|
| R1 | At `Release_Funds`: jurisdiction  DE AND amount  100,000 | `Enhanced_Review` after latest material data change and before release | ER strictly between last material change and release | jurisdiction & amount at release time | Exemption valid at release time (R5) | If amount or jurisdiction unknown at release  INDETERMINATE | ER record, exemption register entry, any material-change timestamps |

| R3 | At `Release_Funds`: jurisdiction added to sanctions list after latest `Sanctions_Screen` and before release | New `Sanctions_Screen` after list update and before release | List update < new screen < release | jurisdiction at screen time & at release time | None | If no screen and unknown jurisdiction  INDETERMINATE | Sanctions_Screen, Sanctions_List_Update events |
| R4 | Any `Update_Amount` (or release-time amount change) | Re-review if amount  > 20% from value at latest SR/ER | Change > threshold  that prior SR/ER no longer count | amount at review time vs. updated amount | Decrease does not invalidate | Increase from unknown prior amount  INDETERMINATE | amount history per case |
| R5 | An exemption is invoked | Must be: approved by Head_Compliance; effective_from  trigger; scope matches; not expired; approval proven at trigger time | — | exemption register & evidence | None if any sub-condition fails | Missing scope/approval evidence  exemption invalid | qualified signature, Head_Compliance ID, scope fields |
| R6 | Any decisive trigger | Do not default unknowns to "compliant" | — | full snapshot at trigger | — | Unknown decisive field  INDETERMINATE | note field, signed payloads |
| R7 | All evaluations | Reconstruct snapshot at the trigger event using `event_index` as tie-breaker on equal timestamps | Strict ordering on `(time, event_index)` | per-event snapshot | — | Tied events follow event_index | event_index column |

**Pseudo-logic (defeasible / Datalog-like; all temporal relations are “strictly before/after unless stated”).**

```
R1:
  at(E=Release_Funds(c), t)  state(jurisdiction(c), t)  DE
     state(amount(c), t)  100000
     ¬exemption(c, e) where valid(e, t, {R1})
   require ER(c, e) with last_material_change(c, t) < t_e < t.

R2:
  at(E=Release_Funds(c), t)
     (state(risk(c), t) = HIGH  state(customer(c), t) = PEP)
   require ER(c, e) with t_e < t
     CA(c, a) with t_e < t_a < t
     reviewer(a) considered substantive for ER packet.

R3:
  at(E=Release_Funds(c), t)
     SLU(c, u) with last_screen(c, s) < t_u < t
     state(jurisdiction(c), t) = state(jurisdiction(c), t_u)   // jurisdiction actually in newly listed set
   require Screen(c, s2) with t_u < t_s2 < t.

R4:
  let a0 = amount(c) at latest SR or ER of c
  let a1 = amount(c) at trigger t
  if a0 known  a1/a0 > 1.20 then prior SR/ER at t0 < t1 does not satisfy amount-dependent obligations.
  if a0 unknown then INDETERMINATE on R4 impact.
  Decrease is benign (does not invalidate).

R5:
  valid(e, t, scope) 
    approver(e) = Head_Compliance
     effective_from(e)  t
     not_expired(e, t)
     scope(e)  {jurisdiction(c), customer(c), amount(c)} at t
     evidence_time(e)  t           // strongest available proof precedes the trigger
  Late DB row alone does not establish evidence_time  t.

R6:
   rule r: if any decisive field  {amount, risk, jurisdiction, customer_type} is unknown at trigger t
     no external evidence resolves it  classify r INDETERMINATE.

R7:
  For every rule evaluation, define snapshot S_c(t) using the greatest event in prefix
    {(e', t', idx') | t' < t  (t' = t  idx'  idx_of(t))} whose target attribute is non-blank.
  All temporal comparisons are over (time, event_index) ordering.
```

## 4. Ambiguities and Alternative Readings

**TX-302 (COMPLIANT, high confidence but worth pressure-testing).** The exemption is recorded late because of a documented outage, and the qualified signing certificate was created at 09:05 — before the release at 09:40. The decisive evidence here is the *qualified signature timestamp*, not the database row. If we only had the PDF and the late DB record (no signing-certificate evidence), R5 would fail and classification would tip toward NONCOMPLIANT. Conversely, if R1 were reinterpreted to evaluate the jurisdiction/amount at the *time of the latest material change* rather than at release, the result is unchanged here (no material change). An interpretation that treats `Release_Funds` as a single instantaneous event whose jurisdiction equals the *immediately preceding* value (i.e., event_index 3 only, ignoring event_index 4) would change TX-311 and is rejected under R7.

**TX-305 (INDETERMINATE).** What would change the result:
- An *immutable release payload* (e.g., a signed MT103 or hash-pinned event payload) showing amount  100,000  R1 fires and there is no ER  NONCOMPLIANT.
- The same payload showing amount < 100,000  R1 does not fire and the case becomes COMPLIANT (no other triggered rule).
- A retroactive signed attestation by `rev05` specifying the amount reviewed would likewise resolve it. Without it, R6 forces INDETERMINATE; the post-hoc settlement figure is not a substitute for the release-time payload per the additional semantic facts.

**TX-310 (NONCOMPLIANT, but the exemption is the load-bearing fact).** Alternative readings:
- If the witness (the *requester* of the transaction) is treated as credible corroboration of an oral 08:45 approval, and the PDF timestamp is trusted, then effective_from = 08:00  release = 10:00 and R1 would be waived by EX-88. But R5 explicitly disfavors backdated fields and a self-interested witness; the qualified signing certificate created at 10:30 anchors the objective evidence *after* release. A reasonable alternative is JUSTIFIED_EXCEPTION only if the organization retroactively ratifies with a Head_Compliance countersignature and a revised signing-certificate log.
- An alternative reading that treats *any* exemption record present in the system at audit time as valid regardless of evidence_time would flip this to COMPLIANT/JUSTIFIED_EXCEPTION; this reading is rejected under R5.

**TX-311 (COMPLIANT, but jurisdiction timing is subtle).** At the *exact* timestamp 16:20, event_index 3 (ER, jur=US) precedes event_index 4 (Update_Jurisdiction to DE). R1 looks at release-time jurisdiction (DE), so the rule does not fire. An alternative reading that applies R1 to the jurisdiction *at the time of the Enhanced_Review* (US, foreign) would still require a new ER after the material change at event_index 4 — and there is none before release at 16:30. That alternative classification would be NONCOMPLIANT. R7's instruction is decisive: evaluate at the trigger event (release), not the review event, so I retain COMPLIANT. What would *strengthen* this conclusion: an ER performed after event_index 4 (none exists) or an explicit "reviewed post-jurisdiction-change" note in the ER (absent). What would *weaken* it: a policy memo requiring re-screening of jurisdiction changes regardless of release-time value.

**Other cases worth flagging:**
- *TX-301*: alternative is COMPLIANT only if R4's 20% threshold is computed against a *baseline* different from 80,000 (e.g., against an aggregated daily exposure), or if a "reviewed current state" note on the Standard_Review is treated as binding the reviewer to the 125,000 amount. Neither reading is supported by the log; NONCOMPLIANT stands.
- *TX-307*: alternative is COMPLIANT if "approved standard review packet" on the CA is treated as equivalent to having approved an Enhanced_Review. The R2 note explicitly cautions against this. NONCOMPLIANT stands.

CHANGING = ['amount', 'risk_level', 'jurisdiction', 'customer_type']

# --- 3. Forward-fill within each case WITHOUT copying future values backward ---
# We will compute snapshots lazily at each release event.
def snapshot_at(case_df, idx):
    """Return state using only rows with position <= idx (event-time + event_index prefix)."""
    prefix = case_df.iloc[:idx + 1]
    snap = {}
    for col in CHANGING:
        vals = prefix[col].dropna()
        # Treat empty string as 'no update' (CSV blanks)
        vals = vals[vals.astype(str).str.len() > 0]
        snap[col] = vals.iloc[-1] if len(vals) else None
    return snap

# --- 4 & 5. Track key event timestamps and material changes per case ---
records = []
for case, g in df.groupby('case:concept:name', sort=False):
    g = g.reset_index(drop=True)
    rel_idx = g.index[g['concept:name'] == 'Release_Funds']
    if len(rel_idx) == 0:
        continue
    ri = rel_idx[0]
    release_time = g.loc[ri, 'time:timestamp']
    state = snapshot_at(g, ri)

    # Most recent SR/ER/CA/Screen/SLU up to release
    def latest(concept):
        sub = g[(g['concept:name'] == concept) & (g.index <= ri)]
        return None if sub.empty else sub.iloc[-1]

    sr = latest('Standard_Review')
    er = latest('Enhanced_Review')
    ca = latest('Compliance_Approve')
    sc = latest('Sanctions_Screen')
    slu = latest('Sanctions_List_Update')

    # Material change times = any row with non-blank in CHANGING before release, excluding the create
    mat = g[(g.index < ri) & (g[CHANGING].notna().any(axis=1)) &
            (g[['concept:name']].apply(lambda r: r['concept:name']
                in {'Update_Amount','Update_Risk','Update_Jurisdiction',
                    'Update_Customer_Type','Risk_Reclassify'}, axis=1))]

    # R4: amount increase > 20% since latest SR or ER
    baseline_amt = None
    baseline_src = None
    for src in [er, sr]:
        if src is not None:
            v = src.get('amount', None)
            if pd.notna(v):
                baseline_amt = float(v); baseline_src = src['concept:name']
                break
    increase_invalidates = False
    r4_indeterminate = False
    if baseline_amt is not None and state.get('amount') is not None:
        if float(state['amount']) / baseline_amt - 1.0 > 0.20:
            increase_invalidates = True
    elif state.get('amount') is not None and baseline_amt is None:
        r4_indeterminate = True  # increase from unknown prior amount

    # R1 trigger
    r1_trigger = (state.get('jurisdiction') not in (None, 'DE')
                  and state.get('amount') is not None and state['amount'] >= 100000)
    r1_unknown = (state.get('jurisdiction') is None or state.get('amount') is None)

    # R2 trigger
    r2_trigger = (state.get('risk_level') == 'HIGH' or state.get('customer_type') == 'PEP')
    r2_unknown = (state.get('risk_level') is None or state.get('customer_type') is None)

    # R3 trigger: jurisdiction appears in SLU and last screen predates that SLU
    r3_trigger = False
    if slu is not None and sc is not None and pd.notna(slu.get('jurisdiction')):
        r3_trigger = (slu['time:timestamp'] > sc['time:timestamp']
                      and state.get('jurisdiction') == slu.get('jurisdiction'))

    records.append({
        'case': case,
        'release_time': release_time,
        'state_at_release': state,
        'last_SR_time': None if sr is None else sr['time:timestamp'],
        'last_ER_time': None if er is None else er['time:timestamp'],
        'last_CA_time': None if ca is None else ca['time:timestamp'],
        'last_Screen_time': None if sc is None else sc['time:timestamp'],
        'last_SLU_time': None if slu is None else slu['time:timestamp'],
        'last_material_change': last_mat_change,
        'baseline_amount_for_R4': baseline_amt,
        'baseline_source': baseline_src,
        'R4_invalidates_review': increase_invalidates,
        'R4_indeterminate': r4_indeterminate,
        'R1_trigger': r1_trigger, 'R1_unknown': r1_unknown,
        'R2_trigger': r2_trigger, 'R2_unknown': r2_unknown,
        'R3_trigger': r3_trigger,
    })

     'evidentiary_quality': 'strong'},
    {'exemption_id': 'EX-88', 'evidence_time': pd.Timestamp('2026-04-06T10:30:00Z', tz='UTC'),
     'effective_from': pd.Timestamp('2026-04-06T08:00:00Z', tz='UTC'),
     'expires':        pd.Timestamp('2026-04-06T12:00:00Z', tz='UTC'),
     'approver': 'Head_Compliance', 'scope_jur': 'AE', 'scope_cust': 'CORPORATE',
     'scope_amt_max': 250000, 'waives': 'R1',
     'evidentiary_quality': 'weak_backdated'},

# Pull exemption referenced at release from the log
ref_exempt = (df[df['concept:name'] == 'Release_Funds']
              .groupby('case:concept:name')['exemption_id'].first())
diag = diag.merge(ref_exempt.rename('referenced_exemption'),
                  left_on='case', right_index=True, how='left')
diag = diag.merge(exemptions, left_on='referenced_exemption',
                  right_on='exemption_id', how='left')

    (diag['approver'] == 'Head_Compliance') &

    (diag['expires'] > diag['release_time']) &
    (diag['evidence_time'] <= diag['release_time']) &
    diag['referenced_exemption'].notna()
)

# --- 7. Coarse case label ---
def label(row):
    if row['R1_unknown'] or row['R2_unknown'] or row['R4_indeterminate']:
        return 'REVIEW_REQUIRED'
    if row['R1_trigger'] and not (row['last_ER_time'] is not None
                                  and (pd.isna(row['last_material_change'])
                                       or row['last_ER_time'] > row['last_material_change'])
                                  and row['last_ER_time'] < row['release_time']
                                  and not row['R4_invalidates_review']
                                  or row.get('exemption_valid_at_release', False)):
        return 'REVIEW_REQUIRED'
    if row['R2_trigger'] and not (row['last_ER_time'] is not None
                                  and row['last_CA_time'] is not None
                                  and row['last_ER_time'] < row['last_CA_time'] < row['release_time']):
        return 'REVIEW_REQUIRED'
    if row['R3_trigger']:
        return 'REVIEW_REQUIRED'
    return 'AUTO_CLEAR'

diag['coarse_label'] = diag.apply(label, axis=1)
print(diag[['case', 'state_at_release', 'R1_trigger', 'R2_trigger', 'R3_trigger',
            'R4_invalidates_review', 'referenced_exemption',
            'exemption_valid_at_release', 'coarse_label']].to_string(index=False))

# --- 8. Coarse DECLARE-style control-flow check (demonstrative only) ---
# A pure DECLARE model would assert: Release_Funds must be preceded by
# {Enhanced_Review, Compliance_Approve, Sanctions_Screen} depending on context.
# It CANNOT represent: (a) the value of attributes at the release, (b) the
# direction of material changes, (c) exemption evidence times, or (d) same-
# timestamp event_index ordering. We illustrate the control flow check.
def trace_order_ok(case_df):
    concepts = case_df['concept:name'].tolist()
    # Coarse: if ER present, it must precede release
    try:
        er_i = next(i for i, c in enumerate(concepts) if c == 'Enhanced_Review')
        rl_i = next(i for i, c in enumerate(concepts) if c == 'Release_Funds')
        return er_i < rl_i
    except StopIteration:
        return None  # no ER at all

declare_pass = {c: trace_order_ok(g) for c, g in df.groupby('case:concept:name')}
print("\nCoarse DECLARE-style control flow (ER before Release):")
for k, v in declare_pass.items():
    print(f"  {k}: {v}")

**What the code does and does not claim.** Steps 1–4 reconstruct per-event state without leaking forward values (the `snapshot_at` helper is explicit about the prefix). Step 5 records the timestamps of the latest relevant control events. Step 6 joins the in-line exemption register and applies the evidence-time test from R5. Step 7 produces a coarse flag (`AUTO_CLEAR` vs `REVIEW_REQUIRED`) — it is deliberately not a hard classification; cases like TX-305 land in `REVIEW_REQUIRED` and require human evidential judgment. Step 8 demonstrates that a pure control-flow (DECLARE/trace-order) check would mark TX-310's *order* as plausible (Standard_Review precedes Release) and miss the missing Enhanced_Review plus invalid exemption — exactly the failure mode described in §6.

## 6. Why Control-Flow-Only Conformance Is Insufficient

1. **Final-state leakage.** Control-flow miners see `Create_Transaction(US)  …  Release_Funds` and treat the jurisdiction as US because it was set at create-time. But the obligation under R1 is evaluated *at release*; TX-311 only switches to DE at event_index 4, *after* the Enhanced_Review at event_index 3. Pure sequence matching would misclassify TX-311 as R1-triggered and then fail to notice the post-ER jurisdiction change.
2. **Post-hoc exemptions.** TX-310 references EX-88 at release and is then "backfilled" by `Record_Exemption` two hours later. A flow check that requires the exemption row to precede the release is correct in principle but will misfire whenever systems are partitioned; the *evidence* of the approval (qualified signature at 10:30) is what matters. Conformance to "exemption row exists before release" is neither necessary (TX-302 is fine without it) nor sufficient (TX-310 has it but it is post-hoc).
3. **Material changes after review.** R4 invalidates a prior review only on a > 20% increase. TX-309's review at 118k is invalidated by the bump to 145k. A control-flow-only check sees "Enhanced_Review  Release_Funds" and approves. The amount's trajectory is invisible to it.
4. **Conditional activation.** R1 fires only when jurisdiction  DE *and* amount  100k *and* no valid exemption. R2 fires only for HIGH risk or PEP. R3 fires only when a sanctions list update landed after the last screen. A pure "Enhanced_Review precedes Release" check is over- and under-inclusive simultaneously: it approves TX-303's release even though no Compliance_Approve is present (R2 violation), and it would approve a 60k DE release that never needed ER in the first place.
5. **Missing data.** TX-305 has no amount at release. A control-flow checker that defaults missing values to "compliant" silently approves a release whose trigger conditions cannot be evaluated. R6 forbids this and the right answer is INDETERMINATE.
6. **Same-timestamp ordering.** TX-311's ER and `Update_Jurisdiction` share a timestamp. Without an event_index tie-breaker, the order is undefined; the policy rule is *defined* in terms of the prefix that includes event_index 3 strictly before event_index 4. Conformance checkers that only compare timestamps would be non-deterministic.
7. **(Bonus) Decrease vs. increase asymmetry.** R4 is asymmetric: a decrease never invalidates a review. TX-308 (140k  100k) is fine even though the reviewed amount no longer matches the released amount, because the obligation is conservative (it protects against *under*-review, not over-review). Pure flow checkers cannot encode that asymmetry.
8. **(Bonus) Reviewer-of-record vs. packet scope.** R2's note says a CA based on a standard packet does not cure the absence of an Enhanced_Review. TX-307 illustrates this. A flow checker that sees "CA  Release" is satisfied, missing the substantive defect.

## 7. Recommended Logging and Control Improvements

1. **Immutable release payloads.** Persist a signed, hash-pinned payload at `Release_Funds` containing the operative `(amount, currency, jurisdiction, customer_type, risk_level, exemption_id, rule_version)`. This eliminates TX-305-style INDETERMINATE cases and gives auditors a single source of truth.
2. **Three explicit timestamps per write.** Every attribute update should carry `event_time` (when the change was decided), `record_time` (when persisted), and where relevant `effective_time` (when it semantically applies). Late records can then be distinguished from late approvals.
3. **Signature/infrastructure timestamps for approvals.** Store the qualified signing certificate creation time separately from the displayed approval time. This is the decisive anchor for R5 and would have changed the EX-88 analysis from "witness + backdated PDF" to "objective proof."
4. **Rule version stamp.** Embed the policy version ID in the release payload. R4's 20% threshold, the DE carve-out, and the R1 floor are version-dependent; without a version, audits are ambiguous across policy revisions.
5. **Exemption scope and linkage.** Persist `scope_jurisdiction`, `scope_customer_type`, `scope_amount_max`, `waived_rules`, `approver_id`, and a `release_id` link at the moment of invocation. Late `Record_Exemption` rows should reference the release they belong to and carry an `evidence_time`  `release_time` flag.
6. **Change provenance.** For every `Update_*` event, record `previous_value`, `new_value`, `actor`, and `reason_code` (e.g., `customer_request`, `risk_reclass`, `sanctions_update`). This makes R4 and R3 mechanically evaluable.
7. **Stable event ordering.** Require a strictly monotonic `(time:timestamp, event_index, sequence_id)` and reject inserts that violate it. For same-timestamp events, force a logical-clock component so R7 is deterministic.
8. **Per-rule evidence pointers.** Each compliance rule check should reference the specific event IDs (or hash anchors) that satisfy it. This makes "satisfied obligations" and "deviations" machine-checkable rather than narrative.
9. **Reviewer-of-record and packet scope.** Tag `Compliance_Approve` with `reviewed_packet_type` (standard / enhanced / sanctions) so the R2 note ("CA on a standard packet does not cure missing ER") can be enforced by rule, not by interpretation.
10. **Alerting on precipitating conditions.** On any `Sanctions_List_Update` or `Risk_Reclassify`, automatically schedule the next required control (`Sanctions_Screen`, `Enhanced_Review`) and block `Release_Funds` until the dependent control completes. This pre-empts TX-303 (no CA), TX-304 (no rescreen), TX-307 (no ER), TX-309 (no re-ER), and TX-310 (no ER) at the source.
