- **Choices**: After the parallel region joins, a threeway ``×`` split enforces exactly one terminal path; R1, R2, R5 and R8 are guaranteed by block structure.
- **Clarification loop**: The loop branch must finish (i.e., all open clarifications answered) before the ```` join, which occurs after the checkplusclassification branch finishes. This enforces that all clarification cycles are completed before any final outcome, but classification may happen before the loop ends (allowed by the backbone).
- **Postactivation behaviour**: The ``change_loop`` allows zero or more iterations of the sequence `Change Bank Details  Suspend Vendor  Verify Bank Account` before the onetime `Release First Payment`. The loop is duplicated in the low and highrisk branches; this is a conscious redundancy to keep the tree blockstructured.
- **Sanctions escalation**: The optional ``×`` node (`Sanctions Escalation` or silent tau) lets the case trigger the highrisk path without making escalation mandatory.
- **Emergency activation**: The chosen resolution A makes the sequence Obtain Legal Opinion  Activate Vendor mandatory in the highrisk branch; emergency activation (R6) is not representable in this tree and must be caught by the dataaware layer.

**Why temporal deviations are warnings**  
The durations in R12 represent business expectations, not hard deadlines. A case may legitimately take longer due to complex negotiations or operational delays. Exceeding the threshold (zeta = 2.0) indicates a notable deviation that should be investigated (e.g., SLA monitoring) but does **not** automatically invalidate the transaction. Temporal profile conformance therefore yields a `warning` rather than a `fail`. This separation avoids rejecting otherwise compliant cases because of a single timing outlier.

# 7. Resource- and DataAware Checks

All checks assume an event log where each trace has a `resource` attribute for every event. When the attribute is missing, the check is skipped and a notification is emitted.

**7.1 Segregation of duties (R9)**

```python
def check_four_eyes(trace):
    violations = []
    # 1. Verify Bank Account vs. applicable approval
    vfy_res = trace[trace["concept:name"] == "Verify Bank Account"]
    # determine which approval occurred
    mgr = trace[trace["concept:name"] == "Manager Approval"]
    comp = trace[trace["concept:name"] == "Compliance Approval"]
    if not mgr.empty:
        approval_act = "Manager Approval"
        approval_res = mgr
    elif not comp.empty:
        approval_act = "Compliance Approval"
        approval_res = comp
    else:
        approval_res = None   # rejected case, no approval

    if not vfy_res.empty and approval_res is not None:
        if vfy_res.iloc[0]["resource"] == approval_res.iloc[0]["resource"]:
            violations.append(f"Segregation violation: Verify Bank Account and {approval_act} performed by same resource '{vfy_res.iloc[0]['resource']}'")
    else:
        # missing data  log warning
        pass

    # 2. Capture Master Data vs. Activate Vendor
    cmd = trace[trace["concept:name"] == "Capture Master Data"]
    act = trace[trace["concept:name"] == "Activate Vendor"]
    if not cmd.empty and not act.empty:
        if cmd.iloc[0]["resource"] == act.iloc[0]["resource"]:
            violations.append("Segregation violation: Capture Master Data and Activate Vendor performed by same resource")

    return violations
```

**7.2 Emergencypolicy check (R6) – both resolutions**

```python
def emergency_check(trace, resolution="A"):
    """
    resolution 'A': strict legal precedence  activation before opinion is always a policy violation.
    resolution 'B': emergency allowed  require opinion within 24h of activation.
    """
    esc = trace[trace["concept:name"] == "Sanctions Escalation"]
    if esc.empty:
        return []   # no sanctions escalation, rule not triggered

    act = trace[trace["concept:name"] == "Activate Vendor"]
    opi = trace[trace["concept:name"] == "Obtain Legal Opinion"]
    if act.empty or opi.empty:
        return []   # incomplete trace

    t_act = act.iloc[0]["time:timestamp"]
    t_opi = opi.iloc[0]["time:timestamp"]

    if resolution == "A":
        if t_opi > t_act:   # opinion after activation  violation of R5
            return ["Emergency violation (Strict): Obtain Legal Opinion must precede Activate Vendor, but activation occurred first."]
        else:
            return []
    else:   # resolution B
        if t_opi > t_act:
            delta_seconds = (t_opi - t_act).total_seconds()
            threshold = 24 * 3600   # 24 hours
            if delta_seconds <= threshold:
                # Emergency bypass allowed; note that joint authorisation cannot be verified
                return [f"Warning: Emergency activation used (joint auth missing from log). Opinion obtained {delta_seconds/3600:.1f}h after activation."]
            else:
                return [f"Emergency violation: Obtain Legal Opinion arrived {delta_seconds/3600:.1f}h after activation, exceeding 24h limit."]
        return []
```

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement**: The mutual exclusion of Reject and Activate (R1), Manager and Compliance Approval (R2/R8) is present in the procedural model, the DECLARE `noncoexistence` pairs, and the logskeleton `never_together` set. This triple redundancy is intentional: each formalism can be used independently for conformance checking, and the overlap provides defenceindepth.
- **Inconsistencies under loops**: The logskeleton `activ_freq` for `Request Clarification` and `Receive Clarification` accepts {0,1,2,3}. The procedural model allows any number of iterations, but the log skeleton artificially caps it at 3. If a case requires four clarification rounds, it would falsely fail log skeleton while passing the procedural and DECLARE layers. This is a conscious limitation to prevent infinite loops from being considered valid by log skeleton.
- **Vacuity in declarative rules**: The `response(Sanctions Escalation, Obtain Legal Opinion)` rule is vacuously true in all lowrisk and rejected traces because `Sanctions Escalation` never occurs. This is acceptable because the rule is only meant to fire when the trigger is present.
- **Missing case attributes**: The verification of the emergency “jointly authorised” condition (R6) is impossible without an explicit attribute (e.g., `emergency_authorised=True`). The resourcelayer check can only validate the 24hour window; the authorisation gap remains. Moreover, foureyes checks require a `resource` field; if logs lack it, the checks degrade gracefully but silently.
- **Timestamponly limitations**: Temporal profile checks depend entirely on the existence and correctness of `time:timestamp`. If timestamps are missing or out of order, the profile cannot be evaluated. Additionally, timestamps alone cannot distinguish between processing delays and human decisions; two events far apart in time might still reflect acceptable behaviour.
- **Support / confidence as normative metadata**: The DECLARE model sets `support` and `confidence` to 1.0, creating the illusion of absolute certainty. In reality, these values are derived from a (possibly incomplete) normative specification, not from a log. Treating them as unquestionable truth can hide modelling errors or policy mismatches. In production, one should instead parameterise violation severity and distinguish “must” from “should” rules.

# 10. Deployment Recommendation

**Canonical procedural representation**  
The ProcessTree (section 3) serves as the primary executable description of the process. It encodes the mandatory sequence, concurrency, exclusive choices, and loops. All other layers should be seen as constraints **relative** to this model.

**Authoritative policy layer**  
The DECLARE model holds the definitive crosscutting rules (R1, R3, R4, R7, R8, R10) because these rules are stable business regulations not derivable from the procedural flow alone. When a violation is detected by DECLARE, it must be treated as a **policy violation**, even if the procedural model was somehow satisfied.

**Conformance checking order**
1. **Procedural conformance** – The trace must be replayable on the ProcessTree. A procedural failure already invalidates the trace; further checks are optional but may provide additional diagnostic detail.
2. **DECLARE conformance** – Checks the declarative rules. A trace that passes the procedural model but fails a DECLARE rule indicates a gap in the procedural design (e.g., a missing loopexit condition).
3. **Logskeleton conformance** – Quick frequency/pairbased checks. A failure here is usually a sign of dataquality issues or an unexpected variant, not necessarily a policy breach; it should be logged as a **compliance warning**.
4. **Temporal profile conformance** – Identifies duration outliers. Failures are **warnings**; they should be routed to the operations team for SLA analysis, not to compliance.
5. **Resource and data checks** – Executed last because they require additional attributes. A resource violation (e.g., foureyes breach) is a hard **compliance violation**. Missing attributes cause the check to be skipped with an audit entry.

**Surfacing contradictory findings**  
When multiple layers disagree (e.g., procedural passes but DECLARE fails), the conflict must be clearly reported: the DECLARE rule is the authoritative policy, so the process model must be investigated. The overall verdict is the **most severe** outcome across layers, weighted as follows: `fail` (resource/data or DECLARE policy) > `fail` (procedural) > `warning` (temporal/log skeleton) > `pass`. An integrated dashboard should display a colourcoded matrix (like section 8) so that analysts can trace the root cause.
