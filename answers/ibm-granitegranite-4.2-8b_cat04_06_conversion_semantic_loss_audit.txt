# 6. VisualSemantics Review

BPMN visualisations generated by the primary pipeline can be misread in the following ways, even though the underlying Petri net (and thus the behavioural acceptance) is correct:

1. **Exclusive vs. Parallel Gateway for the optional legal branch** – The net allows `legal_review` and `skip_legal` to be concurrent with the verification loop. BPMN often renders an XOR choice as an *exclusive gateway*. If the optional legal branch is shown as an exclusive gateway pointing to `Release`, a stakeholder might infer that *either* legal review *must* happen **before** verification starts, whereas the POWL semantics permit overlap (verification loop may start while legal review is pending or skipped). An exclusive gateway without a clear “optional” annotation suggests mandatory choice.

2. **Loop visualisation** – A LOOP operator is translated to a BPMN sequence flow with a backedge to a gateway. Without an explicit “at least one iteration” annotation, viewers might think zero iterations are possible (e.g., skipping `Configure Trial`  `Inspect Trial`). The net prevents Release before any trial body via soundness, but the diagram alone does not make the minimaliteration constraint obvious.

3. **Silent transition omission** – `skip_legal` () cannot be drawn as a visible node in BPMN. Consequently, the diagram shows only `Legal Review` as an optional flow. Stakeholders unfamiliar with the model may read this as “legal review is optional but visible”; they might still assume that if they see no `Legal Review` activity in a run, the process automatically performed the skip, which is correct behaviourally but not visually indicated. Without a legend or annotation (“Legal Review – optional (invisible skip available)”), the optionality can be ambiguous.

4. **Layout suggestion of ordering** – Even if the net permits concurrency, the default BPMN layout may place the optional legal gateway above the verification loop or viceversa, implying a natural precedence that does not exist. Readers might think “first do legal review, then verification” or “first do verification, then legal review”, depending on visual hierarchy.

5. **Gateway join for Release** – The net’s edge from `verification_loop` and `optional_legal` to `Release` is correctly enforced by a join gateway in BPMN. However, if the join gateway is not labelled (e.g., “await both branches completed”), a reviewer might overlook the requirement that Release waits for the final verification inspection, potentially planning Release before the last trial inspection in a simulation.

**Mitigation annotations (to be included in all BPMN exports):**

- Add a **legend** entry: “Legal Review – optional. If not performed, the invisible transition `skip_legal` is taken automatically. The diagram shows only the visible `Legal Review` activity; absence of `Legal Review` in a concrete execution means `skip_legal` occurred.”
- For the LOOP, annotate the BPMN sequence gateway with a note: “At least one iteration of `Configure Trial  Inspect Trial` is required. `Correct Defect` must appear between successive iterations.”
- Use a **parallel gateway** (not exclusive) for the XOR choice when both branches (`Legal Review` and `skip`) are concurrent with the verification loop. Label the gateway “Optional Legal Review (parallel with verification)”.
- Include a **visual cue** (e.g., dashed line or lighter colour) for the edge from `verification_loop` to `Release` and annotate it: “Release waits for completion of the final verification inspection (last `Inspect Trial`) and for completion of the optionallegal branch.”
- Provide a **process description box** near the BPMN diagram summarising the invariant: “Both Assess Risk and Prepare Evidence must finish before any trial body can start; Release cannot start before the last verification inspection.”

These annotations do not alter the BPMN semantics; they clarify intended behaviour and reduce misinterpretation risk.

# 7. Rejection Criteria

A conversion result (Petri net, BPMN, or roundtripped artefact) should be **rejected or quarantined** if **any** of the following conditions hold:

1. **Soundness violation** – `pm4py.check_soundness` returns `False` (i.e., the net admits a trace that violates a source invariant such as Release before any trial body activity).
2. **Finalmarking mismatch** – The set of final markings reachable from the initial marking of the roundtripped net differs from the final marking(s) of the original net (checked via `convert_to_reachability_graph`).
3. **Footprint mismatch** – `discover_footprints` yields different footprints for at least one state reachable from the initial marking.
4. **Incorrect ordering enforced by BPMN visualisation** – The BPMN diagram (when interpreted by a stakeholder following visible gateways) suggests a mandatory precedence that contradicts INV6 (e.g., “Legal Review must precede first trial body”) or INV5 (e.g., allows `trial_body  trial_body` without `Correct Defect`). This is detected by a simple manual review of the diagram plus an automated check that no exclusive gateway forces an order between the optional legal branch and the first trial body.
5. **Loss of optionality visibility** – The BPMN artefact omits any annotation indicating that `Legal Review` is optional and that an invisible `skip` exists, **and** the diagram does not use a parallel gateway for the XOR choice. (Annotations can be added automatically; absence without rationale is considered a loss.)
6. **Workflownet failure** – `check_is_workflow_net` returns `False` for the Petri net (or roundtripped net). Workflownet property ensures that all transitions are enabled only from processmodel places and that deadends are avoided; deviation indicates structural issues.

If any criterion is met, the artefact is quarantined, the offending pipeline is flagged, and the conversion is not released for stakeholder consumption without explicit overrides and documentation of the deviation.

# 9. Residual Uncertainty

The following three claims **cannot be established definitively by the validation techniques provided** (even if all tests pass):

1. **Exact overapproximation degree of concurrency** – The Petri net conversion may allow arbitrary interleaving of the optional legal branch and the verification loop (INV6). Soundness guarantees that Release cannot start before verification completes, but it does not detect whether the net permits unrealistic interleavings (e.g., `legal_review` occurring *after* an `Inspect Trial` of the first iteration but *before* the second `Configure Trial`). A bounded visibletrace exploration with depth6 may miss longer interleavings that involve multiple loop iterations. Thus we cannot assert that every interleaving shown in the BPMN diagram is behaviourally faithful to the intended “may overlap” without additional operator constraints.

2. **Stakeholder perception of optionality** – Even if the BPMN diagram includes the recommended annotations, readers may still interpret the optional legal choice differently (e.g., think it is mandatory if they see only the visible `Legal Review` flow). Automated tests (soundness, footprints) verify behavioural correctness but cannot measure how a human perceives the diagram. Therefore we cannot guarantee that the visualisation will eliminate all ambiguity about optionality.

3. **Silenttransition rendering consistency** – PM4Py’s BPMN exporter does not have a standard way to indicate an invisible optional branch. Whether the generated BPMN (with annotations) consistently reflects the POWL semantics across different BPMN viewers (e.g., Camunda Modeler vs. Signavio) is uncertain. Validation based on net semantics passes, but visual consistency across tools cannot be assured without explicit viewerlevel annotations or custom extensions.

These uncertainties are acknowledged in the documentation and rejection criteria; they guide human review and annotation rather than relying solely on automated checks.
