# PORTFOLIO-LEVEL EARLY-WARNING INTERVENTION POLICY

---

## 1. Decision Rule

### Eligibility Criteria

**Stage eligibility (necessary condition):**
- Case must be in **Triage or Diagnosis Started** stage. Cases in Diagnosis Complete or later are ineligible; the 45-minute swarm has negligible effect post-diagnosis (0.00–0.03 risk reduction).

**Alert integrity (necessary condition):**
- **First alert or evidence-changed alert:** Intervene on third+ alerts *only if* a materially new event (data upload, log arrival, workflow change) has occurred since the preceding alert. This blocks repeated cycles on static cases (I-05) while permitting substantive re-engagement (I-07).
- No more than one swarm per case per calendar day unless a critical escalation (e.g., SLA deadline moved forward materially, or a swarm was explicitly invalidated by an event occurring during the swarm).

**Calibration adjustment (pre-prioritization filter):**

| Segment | Adjustment to p_now | Rationale |
|---------|-----|----------|
| SME | +0.06 (midpoint of –0.04 to –0.09 underpredict range) | Backtest shows model underpredicts; increase weight |
| Strategic Enterprise | –0.08 (midpoint of +0.05 to +0.12 overpredict range) | Recent workflow redesign; reduce weight on high alerts |
| Public Sector | p_now (no adjustment) | Calibration acceptable; maintain supplied value |
| Non-Native-Language Support | p_now ± 0.10 (wide interval) | High uncertainty; flag for manual review; do not rely on model alone |

**Prioritization score (combining risk, value, effect, and uncertainty):**

For each eligible case, compute:

$$\text{Priority Score} = \frac{(\text{adj\_p\_now}) \times (\text{Value} - \text{FalsAlarmBurden}) \times (\text{midpoint effect})}{(\text{Cost} + \text{Spillover proxy})} \times \text{Stage\_Discount} \times \text{Urgency}$$

Where:
- **adj_p_now**: probability after calibration adjustment.
- **Value – FalsAlarmBurden**: net benefit from breach avoidance.
- **midpoint effect**: midpoint of stated effect range.
- **Cost**: €450 + estimated false-alarm burden.
- **Spillover proxy**: 0.02 × Value (conservative; accounts for 0.01–0.03 spillover risk on six other cases).
- **Stage_Discount**: 1.0 if Triage, 1.2 if Diagnosis Started (higher urgency: less time before Diagnosis Complete).
- **Urgency**: (1 + time-to-deadline / 12 hours)^–0.5 (cases with short deadlines score higher).

**Manual review triggers:**
- Any case flagged "sparse calibration segment" or with imputed data quality flags.
- Cases with effect ranges spanning <0.10 absolute points (high uncertainty in intervention efficacy).
- Spillover analysis suggests >0.05 probability that untreated cases in lower-value segments will breach due to queue delay.

---

### Allocation Logic

**Slot budget:** 4 slots available; recommend **reserving 1 for regulatory incident** (management preference, justified by tail risk and reputational cost).

**Available capacity:** 3 slots for current portfolio.

**Ranking by priority score:**
1. Compute priority score for all eligible cases.
2. Rank descending.
3. Allocate slots to top 3 candidates, subject to:
   - Confirmation of stage eligibility and alert integrity.
   - Manual review of high-uncertainty cases.
   - Spillover check: if 3+ cases selected and 4+ untreated cases are in diagnosis stage, revisit allocation to avoid spillover exceeding 0.06 cumulative breach-risk increase.

## 4. Repeated Alerts and Temporal Policy

### **Alert Cycle and Cool-Down Rules**

**Cool-Down Period:**
- After a swarm is completed on a case, suppress all subsequent alerts on that case for **90 minutes** (three model-refresh cycles at 30-min intervals).
- After a case generates an alert and **no swarm is allocated**, suppress alerts for **60 minutes** if:
  - (a) No new evidence (data upload, workflow change, SLA deadline shift >30 min) has arrived, AND
  - (b) The case's breach probability has not increased by >0.08 absolute points since the previous alert.
- If new evidence arrives, reset the cool-down timer; re-enter the case into eligibility pool on next refresh.

**Escalation Logic for Persistent Alerts:**
- **Alert count = 1:** Full eligibility for swarm allocation.
- **Alert count = 2:** Eligible for swarm IF:
  - (i) No prior swarm has been completed on this case, AND
  - (ii) Time-to-deadline has shortened by >20% since alert 1, OR breach probability has increased by >0.08 absolute points.
- **Alert count = 3+:** Eligible ONLY IF materially new evidence (see definition below) has arrived since the last alert.

**Definition of Materially New Evidence:**
- New customer-reported data (log file, error stack, communication) uploaded and processed.
- Workflow change detected in case metadata (e.g., customer escalation, SLA revision).
- Senior specialist or case owner has explicitly flagged the case for re-assessment (e.g., "diagnosis path incorrect").
- Calendar-event change: e.g., customer availability window closing, regulatory deadline acceleration.
- **NOT** merely a p-increase from model refresh if no new data is available (this prevents alert churn).

### **Temporal Rollout Policy (Daily/Weekly)**

1. **09:00 initial triage:** Run model on all open cases. Identify first-alert cases. Allocate available swarm slots using priority-score rule (Section 1).

2. **09:45, 10:15, 10:45, ...** (every 30 min): Refresh model predictions. Apply cool-down suppression to recently-alerted or recently-swarmed cases. Identify new alerts (cases crossing decision thresholds) and evidence-changed repeats (cases with new data).

3. **Second-alert and third-alert handling:**
   - Check whether new evidence has arrived.
   - If **no new evidence**, check cool-down status:
     - If within cool-down, suppress alert; do not re-rank.
     - If past cool-down and p has increased >0.08 absolute points, re-enter as second-alert case (eligible, but lower priority than first alerts, unless deadline is very short).
   - If **new evidence present**, reset cool-down; re-enter as evidence-changed alert (may jump priority if evidence is high-impact).

4. **Swarm-outcome feedback loop:** After a swarm is completed, mark case with swarm-completion timestamp. Begin cool-down (90 min). Assign outcome-label task to case owner: {Swarm was valuable / Not valuable / Unclear / N.A. (case resolved)}. Use labels for monthly effect calibration (see Section 6).

5. **Escalation for untreated repeats:** If a case generates 4+ alerts without swarm, escalate to senior case manager (not model-based). Manager reviews manually: is the alert valid? Are we starving a case due to resource limits (fairness issue) or model error?

## 5. Fairness and Feedback-Loop Risks

### Risk 1: Value-Based Prioritization Starving Lower-Value Cases

**Issue:**
- Decision rule prioritizes by expected benefit = breach probability × value × effect size.
- Lower-value cases (e.g., I-10 at €11,000; SME segment at typical €7–15k) will rarely be selected, even if breach risk is high.
- Over time, untreated lower-value cases will underperform (systematically breach) due to lack of intervention.
- Organizational norm may shift toward "low-value cases don't matter," creating equity and fairness friction.

**Concrete safeguards:**
1. **Reservation rule:** Reserve 1 of every 4 swarm slots for cases in the **lowest-value quartile** (by Value of avoiding breach). Quarterly, audit whether this quartile is breaching at >15% higher rate than high-value quartile. If so, increase reservation to 1 of 3.

2. **Effect-heterogeneity stratification:** Do not assume intervention effect is proportional to case complexity or value. Run separate effect studies for high-value vs. low-value cases within SME and Strategic Enterprise segments. If low-value cases have *higher* effect (e.g., because swarm uncovers quick-win solutions), adjust priority scores to weight effect more heavily.

3. **Cool-down exemption for high-breach low-value:** If a low-value case reaches p > 0.70 (high breach risk) and has been untreated for 3+ cycles, override cool-down and allocate a slot if capacity exists. Rationale: fairness demands intervention regardless of value when risk is extreme.

4. **Transparent communication:** Publish monthly allocation report (anonymized): % of swarms by value quartile, avg breach rate by quartile. If disparity emerges, escalate to governance; adjust rule or resource budget.

---

### Risk 2: Sparse Calibration Segment (Non-Native-Language Support, I-09)

**Issue:**
- I-09 segment has small validation sample; both calibration and intervention-effect estimates are unreliable.
- Using model predictions directly (p = 0.69) may over- or under-state true risk.
- If we intervene on I-09 and it resolves due to swarm, we can't distinguish whether swarm was causal or whether the segment's breach risk was naturally lower.
- If we don't intervene and I-09 breaches, we have limited ability to learn whether swarm would have prevented it (sparse segment means fewer counterfactuals).

**Concrete safeguards:**
1. **Manual case review gate:** All Non-Native-Language Support cases with p > 0.60 are escalated to a case specialist who understands language barriers and support workflows. Specialist independently assesses whether:
   - Breach risk is real (diagnostic difficulty, customer clarity) or an artifact of language model drift.
   - Swarm is the right intervention (vs. escalating to language-support team, customer clarification call, etc.).
   - If specialist agrees breach risk is high and swarm is relevant, case joins priority pool. If specialist disagrees, case is marked "specialist override" and monitored without swarm.

2. **Expanded sampling:** Allocate 1 additional swarm slot per month (if capacity exists) specifically to Non-Native-Language Support cases to expand empirical effect sample. Log swarm rationale and outcome carefully to build calibration data.

3. **Segment-specific threshold:** For Non-Native-Language Support, raise the p-threshold for automatic swarm eligibility from the default (e.g., p > 0.55) to p > 0.65, to reduce false-alarm exposure until calibration improves.

4. **Post-hoc audit:** Monthly, compare breach outcomes for Non-Native-Language Support cases that received swarms vs. those that did not, stratified by specialist-reviewed risk level. Detect systematic over/under-prediction.

### Risk 3: Differential Calibration Across Segments

**Issue:**
- SME segment underpredicts breach risk by 0.04–0.09; we adjust p upward by +0.06 (midpoint).
- Strategic Enterprise overpredicts by 0.05–0.12; we adjust p downward by –0.08 (midpoint).
- Public Sector and Non-Native-Language Support have less robust calibration evidence.
- These adjustments are point-estimates; true offsets may vary case-by-case.
- If we systematically defer Strategic Enterprise cases due to downward adjustment, and the true breach risk in that segment is *not* lower, we will selectively under-serve high-value cases, compounding fairness and financial risk.

**Concrete safeguards:**
1. **Calibration review cadence:** Monthly, recompute segment-level calibration using recent outcomes (last 4 weeks). Update adjustment factors. If adjustment for Strategic Enterprise drifts (e.g., recent post-redesign cases actually breach at 0.40 when p_model says 0.35), revise downward adjustment or flag redesign as incomplete.

2. **Stratified monitoring:** For each segment, track:
   - **Breach rate by p-bin:** Cases with p  [0.4, 0.5), [0.5, 0.6), etc. Do they breach at predicted rates?
   - **Intervention effect by segment:** Does swarm effect differ between SME and Strategic Enterprise? If SME swarms have higher effect, boost SME priority weighting.

3. **Sensitivity analysis in allocation:** Before committing Slot 3 (e.g., I-04, Strategic Enterprise), run two scenarios: (a) assume adjustment is correct (p = 0.40), (b) assume adjustment is wrong and true p = 0.48. Compute priority score in both. If Slot 3 assignment is sensitive to calibration, flag as "calibration-dependent" and prepare to reallocate if Q1 data contradicts adjustment.

4. **Inverse-probability weighting for swarms on uncertain-calibration segments:** When allocating a swarm to a case in a poorly-calibrated segment (e.g., Strategic Enterprise with large prediction error), upweight the expected false-alarm burden in the cost function (e.g., multiply by 1.5). This penalizes allocation to high-uncertainty cases and reduces over-confidence.

### Risk 4: Selective Intervention Changing Future Training Labels (Causal Inference Hazard)

**Issue:**
- Cases selected for swarm are not a random sample; they are selected because p_model is high or because value is high.
- If swarm is effective and prevents a breach, the outcome label will be "no breach."
- If swarm is not allocated (e.g., I-10), and case naturally breaches, outcome is "breach."
- Future training data will conflate:
  - True underlying breach risk (what we want to learn).
  - Selection bias (high-risk or high-value cases got swarms).
  - Causal effect of swarm (preventing breaches in some cases).
- Over time, model will learn that "cases that receive swarms breach less," which is *partially causal* (swarm prevents breaches) but *partially spurious* (high-value cases are easier to resolve even without swarm).
- This feedback loop can distort future predictions, over-weighting value and segment effects.

**Concrete safeguards:**
1. **Randomized holdout for effect estimation:** Quarterly, randomly assign ~10% of eligible cases (p > threshold, all else equal) to a "holdout" group that does not receive swarms, even if Slots are available. Use randomized comparison to estimate causal effect of swarm (treated vs. randomized-control). This breaks the correlation between selection-into-treatment and outcome.

2. **Inverse-probability-weighted labels for training:** When training the next-generation model, use IPW to adjust training labels. Weight each case by the inverse of its probability of receiving a swarm:
   $$\text{weight}_i = \frac{1}{P(\text{swarm}_i | \text{eligible}, p, \text{value})}$$
   This down-weights high-value and high-risk cases (which are over-sampled into swarm group) and up-weights low-value and low-risk cases (which are under-sampled), reducing bias.

3. **Swarm-outcome logging:** For each swarm, log detailed outcome labels:
   - **Outcome:** breach / no breach / resolved before deadline.
   - **Swarm effectiveness assessment:** specialist's post-hoc judgment of whether swarm diagnosis insights were used, and whether they accelerated resolution.
   - **Confounding events:** e.g., "customer called with clarification during swarm" or "swarm revealed vendor is OOS, forcing workaround."
   - Use these to separate causal-swarm effects from background resolution drivers.

4. **Segment-level effect stratification:** Estimate swarm effect separately for SME, Strategic Enterprise, and Public Sector. If effect heterogeneity is large (e.g., swarm works in SME but not in Strategic Enterprise), retrain segment-specific models. This prevents over-generalizing a swarm effect learned in one segment to another.

### Risk 5: Spillover Harms Systematically Falling on Untreated Groups

**Issue:**
- Allocation rule prioritizes high-breach-probability cases and high-value cases.
- Non-intervened cases are left in diagnosis queue, facing spillover (15–30 min delays, 0.01–0.04 breach-probability increase).
- If untreated cases are disproportionately in lower-value segments (SME, Public Sector) or early-stage cohorts (Triage), the spillover harm is distributed inequitably.
- A case with p = 0.45, value = €8,000 may not meet the swarm threshold; it gets spillover burden; breach occurs; realized loss is €8,000. If this pattern repeats for all low-value cases, spillover has created a fairness issue.

**Concrete safeguards:**
1. **Spillover-adjusted priority re-ranking:** When allocating swarm Slots 2–3 (not the first, which should be high-priority regardless), explicitly estimate spillover impact on each untreated case:
   $$\text{spillover\_harm}_i = \sum_j \mathbb{1}[\text{case}_j \text{ untreated}] \times P(\text{swarm}_k \text{ causes } j \text{ to breach})$$
   Rank treated cases by priority; if spillover on case *j* (untreated, low-value or early-stage) is large, reduce the priority of the *treated* case causing that spillover. This internalizes externality.

2. **Queue-balance monitoring:** Daily, report:
   - Number of untreated Triage cases: target is <6 (to keep spillover effect low).
   - Average time-in-Triage for untreated cases: target is <2 hours (to avoid deadline jeopardy from delay).
   - If queue depth exceeds targets, cap swarm allocation for the day (use 1 fewer slot) to free specialist capacity and reduce spillover.

3. **Spillover equity audit:** Monthly, stratify untreated cases that breached by whether they experienced swarm-induced queue delay. Compare breach rate for delayed vs. non-delayed untreated cases, controlling for p_model. If delayed cases breach >10% more often, escalate to operations; consider reducing slot allocation or hiring additional diagnostic staff.

4. **Spillover-aware reservation:** Reserve 1 swarm slot monthly for cases that were not intervened in prior month but are now at high risk (p > 0.70), even if value is lower. Label this "spillover recovery slot." Rationale: fairness requires that we do not chronically starve low-value cases.

### **Causal-Effect Estimation Protocol**

**Objective:** Estimate true causal effect of swarm on breach probability (not observational association).

**Method 1: Randomized Holdout (Quarterly)**
1. Define eligibility pool: cases with p  [0.45, 0.75], in Triage or Diagnosis Started, value >€5,000, no recent swarm.
2. Randomly assign 90% to treatment pool (eligible for swarm allocation); 10% to control pool (flagged as holdout, no swarm even if slot available).
3. Allocate swarms from treatment pool using standard rule.
4. At outcome (breach / no breach), compare breach rates: P(breach | treated, allocated swarm) vs. P(breach | control, no swarm).
5. Difference = **intention-to-treat (ITT) effect**. Divide by swarm-completion rate to estimate **CATE (conditional average treatment effect)**.
6. Stratify by segment and repeat to estimate heterogeneous effects.

**Method 2: Inverse-Probability Weighting (Monthly)**
1. Fit a logistic model to predict P(swarm allocated | case features: p, value, stage, segment).
2. For all cases with outcome labels, compute weight = 1 / P(swarm | features) if allocated; = 1 / (1 – P(swarm | features)) if not allocated.
3. Run weighted logistic regression: outcome ~ swarm + p + value + stage + segment, with weights.
4. Coefficient on swarm = **IPW causal effect estimate** (assumes no unmeasured confounding and model is correct).
5. Compare with observed effect sizes in treated-vs-untreated cohorts to detect bias.

**Method 3: Case-Owner Judgment (Post-Swarm Label)**
1. After swarm, ask case owner: "Did swarm insights directly accelerate resolution? (Yes / No / Unclear / N.A.)"
2. Aggregate: if >60% say Yes, label case as "swarm-effective"; otherwise "swarm-ineffective."
3. Monthly, compare breach rates in swarm-effective vs. swarm-ineffective subsets. Expect swarm-effective to have lower breach rate (post-treatment).
4. Use as auxiliary calibration check, not primary causal estimator (subject to response bias and hindsight bias).

**Causal-Effect Update Schedule:**
- **Monthly:** IPW estimate + case-owner judgment. Update effect-range priors (adjust 25th, 50th, 75th percentiles).
- **Quarterly:** Randomized-holdout CATE by segment. Publish confidence intervals.
- **Bi-annually:** Reconcile IPW, randomized, and judgment-based estimates. If divergent, investigate confounding or measurement error.

### **Predictive-Recalibration Protocol**

**Objective:** Detect and correct model drift (changes in case distribution, process changes, or outcome changes that violate model assumptions).

**Method 1: Calibration Plots (Monthly)**
1. For each segment, group recent cases (last 4 weeks) into p-deciles: [0.0–0.1), [0.1–0.2), ..., [0.9–1.0).
2. Compute observed breach rate in each decile.
3. Plot observed vs. predicted (p-bin midpoint). Compute calibration error = mean absolute error.
4. If error >0.08 for any segment, investigate cause:
   - Did process change (new SLA, staffing change)?
   - Did case distribution shift (e.g., more complex customer segments)?
   - Did model overfit to prior data?

**Method 2: Segment-Level Drift Detection (Bi-weekly)**
1. For each segment, fit a logistic model: breach ~ features (p, value, stage, time-to-deadline, queue-depth-at-time-of-prediction).
2. Compare coefficient estimates this month vs. prior month. If any coefficient changes by >20% (relative), flag as drift.
3. Example: if p-coefficient in SME breaches from 2.1 to 1.6, this suggests p-effect on breach is weaker (maybe diagnostics have improved). Retrain model.

**Method 3: Out-of-Sample Performance (Bi-weekly)**
1. Holdout recent cases (last 1 week) as test set. Retrain model on cases from weeks 2–5 of the month.
2. Compute AUC and calibration error on week-1 test set.
3. Compare to prior month's AUC and error. If AUC drops >0.05, model is degrading; pause allocation until retrain.

**Recalibration Actions:**
- **Calibration error 0.05–0.08:** Minor miscalibration. Adjust segment-level bias term (e.g., shift Strategic Enterprise p by –0.03 if underpredicting). Retrain next iteration.
- **Calibration error >0.08 or AUC drop >0.05:** Severe drift. Pause automated allocation; escalate to senior case manager. Manually review cases until root cause identified. Likely causes: process change (SLA, staffing), data quality issue, or model overfitting. Retrain on broader date range or add new features.
- **Coefficient drift >20%:** Likely real change in process or case distribution. Investigate; may need segment-specific retraining or revised decision thresholds.
