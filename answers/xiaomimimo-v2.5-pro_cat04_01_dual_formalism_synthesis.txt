# 1. Assumptions and Interpretation

1. **Low-risk / high-risk choice.** Represented as an exclusive-choice (XOR) node whose two children are *Supervisor Review* (low risk) and a PARALLEL of *Quality Review* and *Regulatory Review* (high risk). The XOR sits after *Analyze Root Cause*; the model does not encode the data predicate that selects the branch.

2. **Optional supplier consultation.** Represented as XOR(, *Consult Supplier*). The silent branch models "supplier not needed." The XOR is placed after *Analyze Root Cause* so the optional activity can only start once the root cause is known.

3. **Passing inspection abstraction.** Because the model is activity-based and does not encode data conditions, the LOOP operator naturally captures repeat-until-pass: the loop body (*Execute Trial  Inspect Trial*) iterates, and the "redo" child (*Adjust Parameters*) fires only when inspection fails. The loop's implicit -exit represents a passing inspection. No separate "Pass/Fail" label is introduced.

4. **Duplicate visible labels.** **Not permitted.** Each activity label appears exactly once in the model structure. Loop iterations produce repeated occurrences at runtime but with the same single label node. This preserves a one-to-one mapping for conformance checking.

5. **Approximation policy for the process tree.** **Conservative under-approximation (over-constraint):** the process tree forces the approval route and optional supplier consultation to complete *before* the trial loop begins, because the tree's hierarchical structure cannot express "approvals concurrent with trial while both are synchronised at release." This excludes valid behaviour (approvals/CS overlapping trial) but admits no unsafe behaviour.

6. **"May overlap" interpretation.** Interpreted as **true concurrency**: "may overlap" means there is *no ordering constraint* between the two activities (or sub-models), so they can execute in any interleaving—including fully sequential, partial overlap, or full concurrency. In the POWL model this is expressed by *not* adding a partial-order edge; in the process tree it would require a PARALLEL node, but cross-branch dependencies in the tree force a sequential approximation.

# 3. PM4Py Process-Tree Model

## 3.1 Compact Expression

```
->(RD,
   +(->(CM, PV),
      ->(ARC, +(DCA,
                  X(, CS),
                  X(SR, +(QR, RR))))),
   *(->(ET, IT), AP),
   RM,
   AC)
```

**Legend:** `->` sequence, `+` parallel, `X` exclusive choice, `*` loop (first child = body, second = redo), `` = silent transition.

**Mapping to narrative:**
- The root `->` enforces: registration  middle work  trial loop  release  archive.
- The outer `+` (parallel) has two branches: *Contain Material  Plan Verification* and *Analyze Root Cause  {DCA, optional supplier, risk route}*.
- Inside the ARC branch, a second `+` runs DCA, the optional-CS XOR, and the risk-route XOR concurrently after ARC.
- `*(->(ET, IT), AP)` is the repeat-until-pass trial loop.
- RM and AC follow the loop.

## 3.2 Python Code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def leaf(label):
    n = ProcessTree()
    n.label = label
    return n

def tau():
    return ProcessTree()           # label=None, operator=None

def op(operator, *children):
    n = ProcessTree()
    n.operator = operator
    for c in children:
        n.children.append(c)
        c.parent = n
    return n

# --- leaf nodes ---
RD  = leaf("Register Deviation")
CM  = leaf("Contain Material")
ARC = leaf("Analyze Root Cause")
PV  = leaf("Plan Verification")
DCA = leaf("Design Corrective Action")
SR  = leaf("Supervisor Review")
QR  = leaf("Quality Review")
RR  = leaf("Regulatory Review")
CS  = leaf("Consult Supplier")
ET  = leaf("Execute Trial")
IT  = leaf("Inspect Trial")
AP  = leaf("Adjust Parameters")
RM  = leaf("Release Material")
AC  = leaf("Archive Case")
t1  = tau()

# --- subtrees ---
seq_cm_pv   = op(Operator.SEQUENCE, CM, PV)

par_qr_rr   = op(Operator.PARALLEL, QR, RR)
xor_risk    = op(Operator.XOR, SR, par_qr_rr)

xor_cs      = op(Operator.XOR, t1, CS)

par_mid     = op(Operator.PARALLEL, DCA, xor_cs, xor_risk)
seq_arc_mid = op(Operator.SEQUENCE, ARC, par_mid)

par_work    = op(Operator.PARALLEL, seq_cm_pv, seq_arc_mid)

seq_et_it   = op(Operator.SEQUENCE, ET, IT)
loop_trial  = op(Operator.LOOP, seq_et_it, AP)

# --- root ---
tree = op(Operator.SEQUENCE, RD, par_work, loop_trial, RM, AC)
```

## 3.3 Approximation Limitations

The process tree cannot faithfully represent the following intended requirements:

1. **Overlap of approval route and trial cycle (req 7).** The tree places the risk-route XOR (containing *Supervisor Review* or *Quality Review  Regulatory Review*) inside the PARALLEL that must fully complete before the LOOP begins. Consequently, the selected approval must finish before *Execute Trial* starts. The intended semantics allow approvals to overlap the entire trial cycle—they need only be done before *Release Material*. This is a **strict over-constraint**: some intended interleavings (e.g., `… PV DCA ET SR IT RM …` where SR overlaps the trial) are excluded.

2. **Overlap of supplier consultation and trial cycle (req 6).** For the same structural reason, the optional *Consult Supplier* (when selected) is forced to complete before the trial loop. The intended semantics allow it to overlap trial work. Another **over-constraint**.

3. **Data-driven branch selection.** The XOR nodes for risk route and optional supplier are non-deterministic in the process tree. The model cannot enforce that the selection depends on case data; playout may generate traces with both `SR` and `QR,RR`, or with `CS` even when a case does not require it.

4. **Loop exit semantics.** The LOOP's implicit -exit represents "inspection passes," but the model cannot prevent *Adjust Parameters* from appearing after a *passing* inspection within a single iteration—the structural guarantee holds only because AP is the redo child, not because data conditions are checked.

# 4. PM4Py POWL Model

## 4.1 Compact Description

```
StrictPartialOrder(
  nodes = [RD, CM, ARC, PV, DCA,
           risk_route,     # XOR(SR | {QR  RR})
           optional_cs,    # XOR( | CS)
           trial_loop,     # LOOP({ETIT} , AP)
           RM, AC],
  edges = {
    RDCM,  RDARC,
    CMPV,
    ARCDCA,  ARCrisk_route,  ARCoptional_cs,
    PVtrial_loop,  DCAtrial_loop,
    trial_loopRM,  risk_routeRM,  optional_csRM,
    RMAC
  }
)
```

Where:
- `risk_route = OperatorPOWL(XOR, [SR, StrictPartialOrder([QR, RR])])` — QR and RR concurrent inside a partial order with no edges.
- `optional_cs = OperatorPOWL(XOR, [SilentTransition(), CS])` — skip or consult.
- `trial_loop = OperatorPOWL(LOOP, [StrictPartialOrder([ET, IT]), AP])` — ETIT body, AP redo.

| 5 | Optional CS, may overlap trial | CS optional, after ARC, before RM, may overlap trial | XOR(,CS) exact; but forced before trial loop in tree | ARCoptional_csRM, no edge to trial_loop: exact | **Over** | Delays trial when supplier response is slow; reduces parallelism. |
| 6 | Trial repeat-until-pass loop | LOOP body=ETIT, redo=AP | LOOP(SEQ(ET,IT), AP): exact | OperatorPOWL(LOOP) with SPO(ETIT): exact | — | — |
| 7 | Release synchronisation | RM after passing IT + approvals + CS | RM after LOOP and PARALLEL: correct but entire approval+CS stream is forced before trial, making RM synchronisation trivial (no true concurrent streams converge) | Edges from trial_loop, risk_route, optional_cs to RM: exact join | **Over** (indirect, via 4 & 5) | Loses the "converge from concurrent streams" pattern; the tree's RM join is sequential, not a true synchronisation of concurrent obligations. |
| 8 | Duplicate-label risk | Each activity once per case | Single label per node; loop re-executes same nodes: exact | Single Transition per label: exact | — | — |

# 7. Preferred Representation and Validation Plan

## Preferred Representation: **POWL**

**Defence.** The POWL model is preferred because:

1. **Faithfulness.** It represents every intended dependency, concurrency, optionality, and loop without over-constraint. The 12 partial-order edges directly encode cross-branch dependencies (D7a, D7b, D8, D9, D10) that the process tree must approximate.

2. **Concurrency preservation.** The 13 intentionally unconnected pairs (Section 4.3) capture exactly the concurrency the narrative requires, including the critical overlap of approvals and trial.

3. **Structural clarity.** The three nested OperatorPOWL nodes (risk route XOR, optional CS XOR, trial LOOP) cleanly isolate conditional/looping behaviour from the partial-order skeleton.

4. **No approximation needed.** Unlike the process tree, no intended requirement is over- or under-constrained.

## Validation Plan

| Step | Action | Tool / Method | Purpose |
|------|--------|---------------|---------|
| V1 | Convert POWL to Petri net | `pm4py.convert_to_petri_net(powl)` | Obtain an accepting Petri net `(net, im, fm)` for structural analysis. |
| V2 | Convert process tree to Petri net | `pm4py.convert_to_petri_net(tree)` | Obtain a second net for comparison. |
| V3 | Soundness check on both nets | `pm4py.check_soundness(net, im, fm)` | Verify no dead transitions, no deadlocks, proper termination. |
| V4 | Bounded playout (POWL) | `pm4py.play_out(powl, num_traces=500)` | Sample traces from the POWL model; inspect for unexpected behaviour. |
| V5 | Bounded playout (tree) | `pm4py.play_out(tree, num_traces=500)` | Sample traces from the tree; confirm over-constraint (no traces with SR after ET). |
| V6 | Positive trace tests (W1–W5) | Align each visible trace against both nets/models | Verify allowed traces are accepted by both models (except W5 by tree). |
| V7 | Negative trace tests (W6–W8) | Align each visible trace against both nets/models | Verify forbidden traces are rejected by both models. |
| V8 | Silent-transition check | Extract all -labelled places/transitions from both Petri nets; verify count matches expected (loop exit + optional CS skip + any structural  from XOR/LOOP encoding) | Ensure silent transitions do not introduce spurious reachable states or hide required activities. |
| V9 | Duplicate-label check | Assert `len(set(n.label for n in leaves)) == len(list(n.label for n in leaves))` for both models | Confirm no label appears twice in model structure; prevents conformance-checking ambiguity. |
| V10 | Trace W5 differential test | Run W5 against tree and POWL nets | Confirm tree rejects (over-constraint) and POWL accepts; this validates the approximation gap. |

### Limitations

- **Petri-net conversion of POWL:** `pm4py.convert_to_petri_net` may not support all POWL structures (e.g., nested OperatorPOWL inside StrictPartialOrder). If conversion fails, validation falls back to playout-based testing only.
- **Soundness scope:** Soundness checking verifies structural properties (option to complete, proper completion, no dead parts) but does not verify semantic correctness against the narrative.
- **Playout coverage:** Bounded playout is sampling, not exhaustive. Rare interleavings or deep loop iterations may not be explored.
- **Data conditions:** Neither model encodes "low risk" vs. "high risk" as data predicates. The XOR nodes are non-deterministic. Validation cannot check that the *correct* branch is taken for a given case.
- **Loop depth:** Playout may generate only shallow loop iterations (1–3). Deep iterations with many Adjust Parameters cycles may not be sampled.

# 8. Final Self-Critique

1. **Process-tree approximation excludes valid concurrent behaviour.** The most significant semantic weakness: the process tree forces approvals and supplier consultation to complete before the trial loop, excluding the intended overlap (requirements 6 and 7). This means any analysis relying on the process tree (e.g., performance mining, bottleneck detection) will incorrectly portray the trial as starting only after all approvals finish, potentially overstating the critical path and misidentifying the approval step as a bottleneck when it is not on the actual critical path. The POWL model resolves this, but downstream tooling that accepts only process trees will inherit this distortion.

2. **XOR branch selection is non-deterministic in both models.** Neither the process tree nor the POWL model encodes the data predicates that determine risk classification or supplier involvement. This means playout may generate semantically impossible traces (e.g., both SR and QR+RR in the same case, or CS appearing when not needed), and conformance checking against real event logs cannot distinguish valid from invalid branch choices without external data annotations. A data-aware extension (e.g., DECLARE constraints or data Petri nets) would be needed for production use.

3. **Loop exit does not enforce "Adjust Parameters only after failure."** The LOOP(ETIT, AP) structure structurally guarantees that AP only occurs between iterations (never after the final passing IT), which is correct. However, the model cannot express the data condition "AP occurs only when IT detects failure." If the model were extended with additional activity variants (e.g., "Inspect Trial—Pass" and "Inspect Trial—Fail"), the loop structure would need revision. The current abstraction conflates all inspection outcomes into a single label, relying on the implicit loop semantics to encode the pass/fail distinction. This limits the model's ability to support root-cause analysis of inspection outcomes in mined event logs.
