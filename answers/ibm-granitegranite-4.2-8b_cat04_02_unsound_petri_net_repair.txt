| 4     | `t_waive_review` | `{p_analysis_done:1, p_waived:1}` | `{t_join_normal (needs p_review_done, no), t_join_waived}` | Waiver path proceeds; `p_review` consumed |
| 5     | `t_join_waived` | `{p_analysis_done:1, p_decision:1}` | `{t_authorize}` (needs `p_decision`) | **Defect exposed**: `t_join_waived` fires only from `p_waived`; no arc from `p_analysis_done`, so it does **not** consume `p_analysis_done`. Token at `p_analysis_done` remains. |
| 6     | `t_authorize` | `{p_analysis_done:1, sink:1}` | `{}` (all transitions consumed) | Final marking has `p_analysis_done=1` + `sink=1`, but `fm = {sink:1}`. Leftover `p_analysis_done` token  marking not equal to `fm`. Authorization occurs while analysis token persists (violating "analysis complete" prerequisite). |

**Observation details**:
- `t_join_normal` is not enabled at step 4 because `p_review_done` is empty (waiver chose `t_waive_review`  `p_waived`, not `p_review_done`).
- `t_join_waived` is enabled at step 4 because it has an incoming arc from `p_waived` (which has a token), but no incoming arc from `p_analysis_done`, so it fires independently of analysis completion.
- `t_authorize` requires only `p_decision`, which is produced by `t_join_waived`, so it fires immediately after step 5.
- The exact final marking `fm = {sink:1}` is **not reached**; instead `{p_analysis_done:1, sink:1}` remains. This directly violates soundness (final marking must be exactly reached with no leftovers).

**Second counterexample (standard path works correctly)**:
- Sequence: `t_register`  `t_split`  `t_analyze`  `t_standard_review`  `t_join_normal`  `t_authorize` correctly consumes both `p_analysis_done` and `p_review_done` via `t_join_normal`, resulting in `{p_decision:1}` after join and `{sink:1}` after authorize — no leftover. This shows the defect is path-specific to waiver.

# Helper to fire a named transition safely (checks enabledness first)
def fire_transition(pn, marking, t_name):
    enabled = pm4py.get_enabled_transitions(pn, marking)
    enabled_names = {t.name for t in enabled}
    if t_name not in enabled_names:
        print(f"Transition '{t_name}' not enabled in current marking: {marking}")
        return marking
    # Find the transition object by name (pm4py net stores transitions with .name)
    for t in pn.transitions:
        if t.name == t_name:
            if pm4py.petri_utils.can_fire(t, marking):  # safe check
                new_marking = marking.copy()
                new_marking -= t.inputs  # consume inputs
                new_marking += t.outputs  # produce outputs
                return new_marking
            else:
                print(f"Transition '{t_name}' appears enabled but cannot fire due to token counts; actual enablement check failed.")
                return marking
    print(f"Transition '{t_name}' not found in net")
    return marking

# 7. Repair Trade-Offs and Residual Risks

- **Waiver vs. standard distinguishability**: Both repairs preserve the distinction. Repair A keeps `p_waived` place and `t_join_waived`, so the waiver outcome is still recorded (token moves to `p_waived`), and the join only fires when both analysis and waiver are ready. Repair B merges waiver into `p_review_done`; while the Petri net cannot store "waiver flag", business logic (e.g., audit log, UI indication) must record that the review was waived. Thus, distinguishability is maintained at the workflow level in both repairs; Repair A is safer for traceability since `p_waived` explicitly models the waiver artifact.

- **Duplicate behavior or confusion**: Repair A adds only one arc; no new transitions or silent steps are introduced, so no duplicate behavior. The parallelism remains clear (analysis and review start together), and the join correctly waits for both. Repair B removes `t_join_waived`, so there is only one join (`t_join_normal`), which is simpler but requires ensuring `p_review_done` correctly represents both standard-done and waiver-done (handled by firing `t_standard_review` or `t_waive_review` to `p_review_done`). No confusion arises since the review choice is made at `p_review` (standard vs. waiver), and the join condition (`p_analysis_done`  `p_review_done`) naturally waits for both.

- **Soundness vs. business rule alignment**: Soundness (reaching `fm` with no leftovers) is necessary but not sufficient for all business rules. Soundness alone does **not** prove that "authorization occurs only after analysis and review outcome are complete" if the net allowed a join to fire prematurely—but Repair A fixes the synchronization defect, so soundness now guarantees the join waits for analysis. However, additional regression tests (see below) are needed to verify that `t_authorize` cannot fire before `t_join_*` (join) fires, which is enforced by the net structure (since `t_authorize` requires `p_decision`, which only comes from joins). Thus, soundness + reachability test for waiver path suffices for this net.

- **Regression testing**: Test positive traces:
  - Standard path: `register  split  analyze  standard_review  join_normal  authorize`  final `fm`.
  - Waiver path (Repair A): `register  split  analyze  waive_review  join_waived  authorize`  final `fm` (no leftover).
  Test negative traces (should not reach `sink` early):
  - Attempt to fire `t_authorize` before `t_join_*`: e.g., `register  split  analyze` then `t_authorize` — should be disabled (needs `p_decision`), correct.
  - Attempt waiver join before analysis done: `register  split  waive_review` then `t_join_waived` — should be disabled if Repair A is applied (needs `p_analysis_done`), correct; original net incorrectly enabled it.
  Test residual leftover: for waiver path, after `analyze` and `waive_review`, check that `t_join_waived` is **not** enabled if `p_analysis_done` is missing (impossible since `t_analyze` must fire first), but the key test is that `t_join_waived` fires only when both inputs exist, confirmed by counterexample simulation.

- **Detecting bypass of mandatory analysis**: Analysis is mandatory because `t_analyze` consumes `p_analysis` (only input), and `p_analysis` is produced by `split`. No transition can consume `p_analysis` without firing `t_analyze` (only `t_analyze` has `p_analysis` as input), so analysis cannot be skipped. After Repair A, `t_join_waived` requires `p_analysis_done`, which is only produced by `t_analyze`, so analysis must fire before the join can fire. Thus, the net enforces analysis completion; detection is implicit in net behavior (no path to `p_decision` without `t_analyze`).

# 8. Final Recommendation

**Selected repair for deployment**: Repair A (arc-add minimal; add `p_analysis_done`  `t_join_waived`). **Fallback repair**: Repair B (semantics-refactor; reuse `t_join_normal` for waiver).

**Choice rationale (250 words)**: Repair A is recommended for deployment because it requires only one arc addition (`p_analysis_done`  `t_join_waived`), preserves all existing places (`p_waived`), transitions (`t_join_waived`), and labels, thus minimizing disruption to current modeling artifacts and audit trails (the "formally recorded waiver" place remains explicitly present). This directly fixes the synchronization defect without changing business semantics—analysis stays mandatory, waiver remains distinct, and parallel start is unchanged. Soundness is restored (tested via counterexample simulation), and the fix is minimal under the clear edit-cost model (arc additions = 1). Repair B (fallback) is simpler structurally (no `t_join_waived`) but requires removing `p_waived` and merging waiver into `p_review_done`, which may affect downstream logging or compliance checks that rely on a dedicated waiver place. Since the business explicitly states "formally recorded waiver", keeping `p_waived` is safer for traceability. Deployment should use Repair A; if future modeling prefers fewer joins, Repair B can be adopted later with updated documentation for `p_review_done` semantics. Both repairs were validated via marking simulation and `pm4py` soundness diagnostics.
