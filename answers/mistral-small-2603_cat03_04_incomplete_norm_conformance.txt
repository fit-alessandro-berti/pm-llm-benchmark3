## 1. Conformance semantics

### Definitions of deviation classes
The classification framework distinguishes seven semantic buckets, each tied to how the norm’s open-world/closed-world assumptions apply:

1. **Forbidden behavior**
   - *Definition*: A relation explicitly marked **forbidden** in the norm (closed-world).
   - *Detection*: Any observed instance of the forbidden relation.
   - *Severity*: High; these are absolute prohibitions.
   - *Example*: `Order: Cancel Order -> Dispatch Package` (N3).

2. **Missing mandatory behavior**
   - *Definition*: A **mandatory** relation that should occur within the stated scope but is absent.
   - *Detection*: Count < expected within the scope (e.g., 98/100 for `Create Order -> Validate Order`).
   - *Severity*: Medium to high; depends on whether the absence is explainable (e.g., abstraction mismatch) or unexplained.
   - *Example*: 2/100 Orders missing `Create Order -> Validate Order`.

3. **Unexpected but unregulated behavior**
   - *Definition*: Relations **unspecified** in the norm (open-world) but observed.
   - *Detection*: Any edge/event pair not covered by mandatory/typical/forbidden rules.
   - *Severity*: Low to medium; benign unless it reveals hidden risks.
   - *Example*: `Order: Create Order -> Manual Compliance Review` (N6 is unspecified).

4. **Typical-pattern absence**
   - *Definition*: A **typical** relation that is absent or underrepresented, but exceptions are legitimate.
   - *Detection*: Count << typical expectation (e.g., 72/100 `Validate Order -> Issue Invoice` vs. 83/100 `Validate Order -> Close Order`).
   - *Severity*: Low; typical patterns are not strict.
   - *Example*: 14 Invoices with no successor (E8).

5. **Likely data-quality error**
   - *Definition*: Observed relations that violate domain constraints but are not explicitly forbidden by the norm.
   - *Detection*: Relations that are logically inconsistent (e.g., `Sensor Heartbeat -> Invoice`).
   - *Severity*: High; requires immediate containment.
   - *Example*: `Sensor Heartbeat` linked to Invoice (E10).

6. **Abstraction mismatch**
   - *Definition*: The observed graph uses a coarser/finer abstraction than the norm’s directly-follows assumption.
   - *Detection*: Missing relations where intermediate events are plausible (e.g., `Create Order -> Validate Order` missing due to unrecorded review).
   - *Severity*: Medium; indicates logging gaps rather than process violations.
   - *Example*: 2 Orders missing `Create Order -> Validate Order` due to unrecorded `Manual Compliance Review`.

7. **Insufficient evidence**
   - *Definition*: Relations where the norm’s scope is ambiguous or the observed data lacks context.
   - *Detection*: Relations with unclear semantics (e.g., `Package object_codeath Delivery`).
   - *Severity*: Low; requires further investigation.
   - *Example*: 7 `Package -> Delivery` codeath edges.

### Open-world vs. closed-world assumptions
- **Closed-world**: Only applies to **forbidden** relations (N3, T6, E10) and **mandatory** relations *within their stated scope*. Absence here is a violation unless explained.
- **Open-world**: All other relations are intentionally unregulated. Unspecified or typical relations may be absent or present without implying noncompliance.
- **Abstraction sensitivity**: The norm’s directly-follows expectations (e.g., N1) assume no intermediate events. If the observed log includes such events (e.g., `Manual Compliance Review`), the abstraction mismatch must be acknowledged.

## 3. Detailed reasoning by model family

### OC-DFG (Object-Centric Directly-Follows Graph)
**What the model establishes**:
- Directly-follows relations between objects (e.g., `Order: Create -> Validate`).
- Mandatory relations (e.g., N1) are expected to occur in >95% of cases unless explained.
- Forbidden relations (e.g., N3) must never occur.

**What it cannot establish**:
- Intermediate events not captured in the directly-follows abstraction (e.g., `Manual Compliance Review` between `Create Order` and `Validate Order`).
- Typical-pattern absences (e.g., N2) are not violations unless extreme.
- The norm’s "eventually expected" rules (e.g., N1) are not strictly enforced in the directly-follows graph.

**Counts and scopes**:
- **N1**: 98/100 `Create Order -> Validate Order` suggests a 2% gap. The additional context notes that 2 Orders may have unrecorded review events, making this an **abstraction mismatch** rather than a violation.
- **N3**: 2/100 `Cancel Order -> Dispatch Package` is a **forbidden behavior** violation.
- **N2**: 72/100 `Validate Order -> Issue Invoice` is a **typical-pattern absence**; the norm allows intermediate events (e.g., fulfillment), so this is not a violation.

**Abstraction danger**:
The norm’s "eventually expected" rules (e.g., N1) are approximated with directly-follows expectations. If the log includes intermediate events (e.g., `Manual Compliance Review`), the directly-follows graph will miss the relation, leading to false positives for missing mandatory behavior. The additional context mitigates this by noting plausible unrecorded events.

---

### OTG (Object-Type Graph)
**What the model establishes**:
- Mandatory interactions (e.g., T1: `Order -> Item`) must occur for every `Add Item` event.
- Forbidden relations (e.g., T6: `Order object_cobirth Payment`) must never occur.

**What it cannot establish**:
- Typical interactions (e.g., T3: `Invoice -> Payment`) may have legitimate exceptions.
- Unspecified relations (e.g., T4: `Order -> Customer`) are out of scope.

**Counts and scopes**:
- **T2**: 200 `Package -> Delivery` interactions match the 200 `Dispatch Package` events, but 2 `Dispatch Package` events lack the edge. This is a **missing mandatory behavior** due to a possible data join error.
- **T6**: 1 `Order object_cobirth Payment` is a **forbidden behavior** violation.
- **T3**: 92 `Invoice -> Payment` interactions are typical; 18 Invoices lack successors, which may indicate unapplied cash or write-offs.

**Abstraction danger**:
The OTG model does not capture event sequences, so missing edges may reflect data-quality issues (e.g., unlinked `Delivery` objects) rather than process violations.

---

### ET–OT (Event-Type–Object-Type)
**What the model establishes**:
- Mandatory event-object pairs (e.g., E1: `Create Order -> Order`) must occur for every event of that type.
- Forbidden event-object pairs (e.g., E10: `Sensor Heartbeat -> Invoice`) must never occur.

**What it cannot establish**:
- Typical event-object pairs (e.g., E8: `Record Payment -> Invoice`) may have exceptions.
- Unspecified pairs (e.g., E9: `Manual Compliance Review -> RiskCase`) are out of scope.

**Counts and scopes**:
- **E10**: 1 `Sensor Heartbeat -> Invoice` is a **data-quality error**; the norm explicitly forbids this.
- **E8**: 1 `Record Payment` event lacks an `Invoice` link, suggesting unapplied cash not labeled as such (**data-quality error**).
- **E7**: 93 `Record Payment` events vs. 92 `Record Payment -> Invoice` edges suggests 1 unlinked payment (**data-quality error**).

**Abstraction danger**:
The ET–OT model assumes strict event-object pairing. Missing links may reflect logging gaps (e.g., unapplied cash) rather than process violations.

## 5. PM4Py conformance code sketch

```python
import pm4py
from typing import Dict, Tuple, List

# Assume ocel is the observed log (PM4Py OCEL format)
# Assume norm_ocdfg, norm_otg, norm_etot are normative structures with:
#   - norm_ocdfg: Dict[str, Dict[str, str]] (e.g., {"Order": {"Create Order -> Validate Order": "mandatory"}})
#   - norm_otg: List[Tuple[str, str, str]] (e.g., [("Order", "object_interaction", "Item")])
#   - norm_etot: List[Tuple[str, str, str]] (e.g., [("Create Order", "Order", "mandatory")])

def classify_ocdfg_edge(relation: str, count: int, total: int, norm_status: str) -> str:
    """Classify OC-DFG edge based on norm status and observed counts."""
    if norm_status == "forbidden" and count > 0:
        return "forbidden_violation"
    elif norm_status == "mandatory":
        if count < total * 0.95:  # 95% threshold for mandatory
            return "missing_mandatory"
        else:
            return "conforming"
    elif norm_status == "typical":
        if count < total * 0.7:  # 70% threshold for typical
            return "typical_absence"
        else:
            return "conforming"
    else:  # unspecified
        return "unregulated"

def classify_otg_edge(edge: Tuple[str, str, str], weight: int, norm_status: str) -> str:
    """Classify OTG edge based on norm status."""
    if norm_status == "forbidden" and weight > 0:
        return "forbidden_violation"
    elif norm_status == "mandatory" and weight == 0:
        return "missing_mandatory"
    else:
        return "conforming"

def classify_etot_edge(event_type: str, obj_type: str, weight: int, norm_status: str) -> str:
    """Classify ET-OT edge based on norm status."""
    if norm_status == "forbidden" and weight > 0:
        return "forbidden_violation"
    elif norm_status == "mandatory" and weight == 0:
        return "missing_mandatory"
    else:
        return "conforming"

# Discover conformance
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)

# Raw PM4Py diagnostics (preserved)
raw_ocdfg_diagnostics = pm4py.conformance_ocdfg(ocel, ocdfg)
raw_otg_diagnostics = pm4py.conformance_otg(ocel, otg)
raw_etot_diagnostics = pm4py.conformance_etot(ocel, etot)

# Semantic classification layer (adds metadata)
classified_ocdfg = {}
for relation, count in ocdfg.items():
    obj_type, edge = relation.split(" -> ")
    norm_status = norm_ocdfg.get(obj_type, {}).get(edge, "unspecified")
    classified_ocdfg[relation] = {
        "raw_count": count,
        "classification": classify_ocdfg_edge(edge, count, ocel["Order"].shape[0], norm_status),
        "norm_status": norm_status,
        "semantic_bucket": "forbidden_violation" if classified_ocdfg[relation]["classification"] == "forbidden_violation"
                          else "missing_mandatory" if classified_ocdfg[relation]["classification"] == "missing_mandatory"
                          else "typical_absence" if classified_ocdfg[relation]["classification"] == "typical_absence"
                          else "unregulated"
    }

classified_otg = {}
for edge, weight in otg.items():
    type1, rel, type2 = edge
    norm_status = "forbidden" if (type1, rel, type2) in norm_otg.get("forbidden", [])
                     else "mandatory" if (type1, rel, type2) in norm_otg.get("mandatory", [])
                     else "typical" if (type1, rel, type2) in norm_otg.get("typical", [])
                     else "unspecified"
    classified_otg[edge] = {
        "raw_weight": weight,
        "classification": classify_otg_edge(edge, weight, norm_status),
        "norm_status": norm_status,
        "semantic_bucket": classified_otg[edge]["classification"]
    }

classified_etot = {}
for event_type, obj_type, weight in etot:
    norm_status = "forbidden" if (event_type, obj_type) in norm_etot.get("forbidden", [])
                     else "mandatory" if (event_type, obj_type) in norm_etot.get("mandatory", [])
                     else "typical" if (event_type, obj_type) in norm_etot.get("typical", [])
                     else "unspecified"
    classified_etot[(event_type, obj_type)] = {
        "raw_weight": weight,
        "classification": classify_etot_edge(event_type, obj_type, weight, norm_status),
        "norm_status": norm_status,
        "semantic_bucket": classified_etot[(event_type, obj_type)]["classification"]
    }

# Output raw diagnostics + semantic layer
print("Raw OC-DFG diagnostics:", raw_ocdfg_diagnostics)
print("Classified OC-DFG:", classified_ocdfg)
print("Raw OTG diagnostics:", raw_otg_diagnostics)
print("Classified OTG:", classified_otg)
print("Raw ET-OT diagnostics:", raw_etot_diagnostics)
print("Classified ET-OT:", classified_etot)
```
