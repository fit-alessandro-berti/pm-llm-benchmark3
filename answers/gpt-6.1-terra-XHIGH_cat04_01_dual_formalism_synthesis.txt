# 1. Assumptions and Interpretation

1. The models describe complete cases as sequences of activity **completions**. Every named activity except the trial-cycle activities occurs exactly once when its branch is selected. Registration is first; release is followed by archival and the case then terminates.
2. After root-cause analysis, an exclusive control-flow choice selects either one Supervisor Review, or both Quality Review and Regulatory Review. The two high-risk reviews are unordered. No model tests the actual risk value: matching the chosen route to case data is an external responsibility.
3. Supplier consultation is an exclusive choice between Consult Supplier and a silent skip. The choice is made once per case, after analysis. Release waits for the chosen branch, including its silent skip; the visible consultation, when chosen, occurs once. The models do not determine selection from case data.
4. Each trial executes and is inspected. A silent loop decision after inspection either exits, abstracting a pass, or takes Adjust Parameters and repeats, abstracting a failure. Thus the last inspection in a complete trace is the passing inspection; every earlier inspection is followed by an adjustment and another trial. Neither model records the outcome itself or can check an outcome field against the branch taken.
5. Duplicate visible labels are permitted in general, but these models deliberately use one node per activity label; loop repetition reuses the same nodes. Silent transitions are not visible labels. Some Petri-net conversions may nevertheless create multiple transitions with the same visible label, so that property must be checked after conversion.
6. The process tree is a **conservative under-approximation**: it delays the approval and supplier branches until both planning and design have completed. This excludes intended early approvals and consultations but preserves the stated prerequisites and release obligations. No claim is made that this is the only or maximal process-tree approximation.
7. “May overlap” means that the model imposes no order between the relevant branches and permits true concurrency in the underlying execution semantics. A completion trace shows only an interleaving and cannot prove actual temporal overlap. Similarly, an ordering between completion events is a projection of the narrative's start-after-completion rule: without start events or durations it cannot detect an activity that started too early but completed later.

# 2. Intended Dependency Specification

| ID | Source activity or submodel | Target activity or submodel | Relation | Rationale |
|---|---|---|---|---|
| D1 | Register Deviation | Contain Material; Analyze Root Cause | Precedence; the two targets are unordered | Both initial streams follow registration and can overlap. |
| D2 | Contain Material | Plan Verification | Precedence | Planning starts only after containment completes. |
| D3 | Analyze Root Cause | Design Corrective Action | Precedence | Design starts only after analysis completes. |
| D4 | Analyze Root Cause | Approval route | Precedence followed by exclusive choice | Choose Supervisor Review for low risk or both high-risk reviews. |
| D5 | Quality Review | Regulatory Review | No ordering in either direction | Both high-risk reviews are required and may overlap or finish in either order. |
| D6 | Analyze Root Cause | Optional supplier branch | Precedence and XOR between consultation and silent skip | Consultation is optional, at most once, and cannot start before analysis. |
| D7 | Plan Verification; Design Corrective Action | Trial cycle | AND synchronization | Both work products are needed before the first Execute Trial. |
| D8 | Execute Trial | Inspect Trial | Precedence in each iteration | Every execution is followed by its inspection. |
| D9 | Inspect Trial | Adjust Parameters then another trial cycle, or loop exit | Exclusive repeat-until choice | Failure causes adjustment and repetition; passing exits with no subsequent adjustment. |
| D10 | Approval route; optional supplier branch | Trial cycle | No ordering in either direction after their own prerequisites | Reviews and consultation can overlap the trial, including between iterations. |
| D11 | Completed trial cycle; completed approval route; completed optional supplier branch | Release Material | AND synchronization | Release requires a passing inspection, selected approvals, and consultation if selected. |
| D12 | Release Material | Archive Case | Precedence and termination | Archival follows release and ends the case. |

# 3. PM4Py Process-Tree Model

Notation: `seq` is sequence, `and` is parallel composition, `xor` is exclusive choice, `tau` is a silent skip, and `loop(do, redo)` executes `do` at least once and repeats it after each `redo`. Labels in quotes are visible.

```text
seq('Register Deviation',
    and(seq('Contain Material', 'Plan Verification'),
        seq('Analyze Root Cause', 'Design Corrective Action')),
    and(xor('Supervisor Review',
            and('Quality Review', 'Regulatory Review')),
        xor('Consult Supplier', tau),
        loop(seq('Execute Trial', 'Inspect Trial'), 'Adjust Parameters')),
    'Release Material', 'Archive Case')
```

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    return ProcessTree(label=label)


def node(operator, *children):
    parent = ProcessTree(operator=operator)
    for child in children:
        parent.children.append(child)
        child.parent = parent
    return parent


def seq(*children):
    return node(Operator.SEQUENCE, *children)


def parallel(*children):
    return node(Operator.PARALLEL, *children)


def xor(*children):
    return node(Operator.XOR, *children)


tree = seq(
    leaf("Register Deviation"),
    parallel(
        seq(leaf("Contain Material"), leaf("Plan Verification")),
        seq(leaf("Analyze Root Cause"), leaf("Design Corrective Action")),
    ),
    parallel(
        xor(
            leaf("Supervisor Review"),
            parallel(leaf("Quality Review"), leaf("Regulatory Review")),
        ),
        xor(leaf("Consult Supplier"), ProcessTree()),
        node(Operator.LOOP,
             seq(leaf("Execute Trial"), leaf("Inspect Trial")),
             leaf("Adjust Parameters")),
    ),
    leaf("Release Material"),
    leaf("Archive Case"),
)
```

The first parallel block completes both planning and design before the second block can start. Consequently the tree excludes any intended review or supplier consultation that completes before either work product, including their overlap with planning or design. It also delays the silent approval/supplier choices until that point. Once the second block starts, reviews, consultation, and trial iterations may interleave freely. The containment-to-planning and analysis-to-design dependencies, trial prerequisites, route choice, supplier cardinality, loop, and release join are otherwise represented at completion-trace level. As with the POWL model, actual start times, risk values, supplier data, and inspection outcomes are not represented.

# 4. PM4Py POWL Model

Here `PO{...; edges}` is a partial order of its immediate child submodels; unlisted edges are implied by transitivity or absent. The loop body is itself the ordered pair Execute Trial then Inspect Trial.

```text
R = 'Register Deviation'; C = 'Contain Material'; A = 'Analyze Root Cause'
P = 'Plan Verification'; D = 'Design Corrective Action'
route = xor('Supervisor Review', PO{'Quality Review', 'Regulatory Review'; no edges})
supplier = xor('Consult Supplier', tau)
cycle = loop(PO{'Execute Trial' -> 'Inspect Trial'}, 'Adjust Parameters')
L = 'Release Material'; H = 'Archive Case'
PO{R, C, A, P, D, route, supplier, cycle, L, H;
   R -> C, R -> A, C -> P, A -> D, A -> route, A -> supplier,
   P -> cycle, D -> cycle, route -> L, supplier -> L, cycle -> L, L -> H}
```

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder, OperatorPOWL, Transition, SilentTransition,
)

register = Transition("Register Deviation")
contain = Transition("Contain Material")
analyze = Transition("Analyze Root Cause")
plan = Transition("Plan Verification")
design = Transition("Design Corrective Action")

supervisor = Transition("Supervisor Review")
quality = Transition("Quality Review")
regulatory = Transition("Regulatory Review")
high_risk = StrictPartialOrder([quality, regulatory])
route = OperatorPOWL(Operator.XOR, [supervisor, high_risk])

supplier = OperatorPOWL(
    Operator.XOR, [Transition("Consult Supplier"), SilentTransition()]
)

execute = Transition("Execute Trial")
inspect = Transition("Inspect Trial")
trial_body = StrictPartialOrder([execute, inspect])
trial_body.order.add_edge(execute, inspect)
cycle = OperatorPOWL(
    Operator.LOOP, [trial_body, Transition("Adjust Parameters")]
)

release = Transition("Release Material")
archive = Transition("Archive Case")
powl = StrictPartialOrder([
    register, contain, analyze, plan, design,
    route, supplier, cycle, release, archive,
])
powl.order.add_edge(register, contain)
powl.order.add_edge(register, analyze)
powl.order.add_edge(contain, plan)
powl.order.add_edge(analyze, design)
powl.order.add_edge(analyze, route)
powl.order.add_edge(analyze, supplier)
powl.order.add_edge(plan, cycle)
powl.order.add_edge(design, cycle)
powl.order.add_edge(route, release)
powl.order.add_edge(supplier, release)
powl.order.add_edge(cycle, release)
powl.order.add_edge(release, archive)
# PM4Py's relation stores edges explicitly; materialize implied precedence.
powl.order.add_transitive_edges()
assert powl.order.is_strict_partial_order()
```

At the outer level, after transitive closure, each incomparable pair is intentionally unordered: containment and its planning stream can progress independently of analysis and its design, approval, and supplier branches, except that both planning and design precede the cycle. Design, approval, and supplier are mutually unordered after analysis; approval and supplier are also unordered with the cycle. Release joins all three obligations. Inside the high-risk submodel, the two reviews are unordered. Inside the trial body, execution precedes inspection. Choice alternatives are mutually exclusive, not concurrent; the body and redo are ordered by loop semantics. These facts account for all unordered pairs without adding a global phase barrier.

# 5. Behavioral Witnesses

A trace is a complete case, written using these abbreviations: R = Register Deviation, C = Contain Material, A = Analyze Root Cause, P = Plan Verification, D = Design Corrective Action, S = Supervisor Review, Q = Quality Review, G = Regulatory Review, U = Consult Supplier, E = Execute Trial, I = Inspect Trial, J = Adjust Parameters, L = Release Material, H = Archive Case. Verdicts are for complete visible traces, with silent steps hidden.

| Trace ID | Visible trace | Intended verdict | Process-tree verdict | POWL verdict | Reason |
|---|---|---|---|---|---|
| T1 | R C P A D S E I L H | Allowed | Allowed | Allowed | Low-risk route, no supplier, one passing trial. |
| T2 | R A C D P Q E G I L H | Allowed | Allowed | Allowed | Both high-risk reviews occur; the trial interleaves with them. |
| T3 | R C A P D E I U S L H | Allowed | Allowed | Allowed | Supplier consultation and low-risk approval finish after inspection but before release. |
| T4 | R A C D P E I J E I S L H | Allowed | Allowed | Allowed | The first inspection fails, adjustment occurs, and the second inspection passes. |
| T5 | R A S U C P D E I L H | Allowed | Forbidden | Allowed | Analysis enables review and consultation before containment and planning; the tree's phase barrier excludes this. |
| N1 | R A P C D S E I L H | Forbidden | Forbidden | Forbidden | At P, containment C has not completed; this violates a cross-branch prerequisite. |
| N2 | R C A P D E I J L S H | Forbidden | Forbidden | Forbidden | At L, adjustment after the first inspection committed the case to another execution and inspection, so no passing inspection has occurred. |
| N3 | R C A P D Q E I L H | Forbidden | Forbidden | Forbidden | At L, the high-risk route selected by Q has not completed G. |

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | Containment and analysis are independent after registration. | Parallel containment–planning and analysis–design sequences. | Separate unordered C and A nodes after R. | Neither constrains their completion order. | Either stream can progress first. |
| Split dependencies into planning/design | C enables P; A enables D; both P and D enable the trial. | These prerequisites hold, but the enclosing block also gates reviews and consultation on both P and D. | Edges C→P, A→D, P→cycle, D→cycle. | Tree overconstrains reviews and supplier work; POWL has no extra phase barrier. | Tree can reject valid early work. |
| Risk route | Exactly S, or both Q and G unordered, after A. | Correct route alternatives, delayed until P and D finish. | XOR after A; high-risk reviews in an unordered PO. | Tree is stricter in timing; neither checks risk data. | Early approvals may be rejected by the tree; external data validation is needed. |
| Approval and trial overlap | Neither must finish before the other. | Parallel after P and D. | Unordered route and cycle after their separate prerequisites. | Tree forbids approval completion before P or D, even though the trial can still overlap approval. | Valid early review records may fail tree conformance. |
| Optional supplier | Zero or one U after A, possibly during other work; join before release. | XOR with silent skip, delayed until P and D finish. | XOR with silent skip, enabled after A and joined at release. | Tree excludes early U; both abstract supplier-selection data. | A valid early consultation can be rejected by the tree. |
| Repeat-until | E then I; failure leads to J and another E–I; pass exits without J. | Two-child loop with E–I body and J redo. | Two-child loop with ordered E–I body and J redo. | Both abstract outcome decisions and project start times to completions. | A wrong outcome value cannot be detected without data-aware checking. |
| Release synchronization | Passing trial, selected route, and selected consultation all complete before L. | Parallel block joins before L. | Edges from cycle, route, and supplier to L. | Neither omits a control-flow obligation; data correctness remains external. | Release cannot occur early in either model's visible control flow. |
| Duplicate-label risk | Each named activity has one conceptual identity, with E, I, and J repeated by iteration. | One leaf per visible label; loop reuses leaves. | One transition node per visible label; loop reuses nodes. | No source-model duplication; conversion may introduce duplicate labels or silent paths. | Label-only alignment can hide which converted transition fired; inspect the net and replay semantics. |

# 7. Preferred Representation and Validation Plan

Use POWL as the canonical control-flow representation: its explicit partial order expresses the independent prerequisites and release join without delaying approvals or supplier consultation. Its fidelity claim is for complete visible completion traces under the stated abstractions, not for recorded start times or data-dependent decisions.

Validate using the target PM4Py version and its supported conversion and conformance APIs:

1. Construct both models and verify each partial order is irreflexive and transitively closed; inspect the direct dependencies and implied closure. Convert each with `pm4py.convert_to_petri_net(model)` to `(net, im, fm)` where the installed version supports that model. Inspect the resulting visible and silent transitions, initial and final markings, and loop wiring; a successful conversion alone does not establish equivalence.
2. Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)` for each converted net and inspect its result and diagnostics, including reachability of the final marking and dead transitions where reported. If a conversion or soundness check is unsupported or inconclusive, report that rather than treating it as a pass.
3. Use bounded or sampled playout of each accepting net, allowing at least two trial iterations, both route choices, both high-risk review orders, and supplier present and absent. Project away silent transitions and check the generated complete traces against the dependency rules. Sampling does not establish absence of bad traces.
4. Replay T1–T5 and N1–N3 as complete traces against each accepting net, requiring a firing sequence from the initial to the final marking with exactly the listed visible labels and any number of silent moves. Check the exact verdicts in the witness table, especially T5's POWL/tree difference and N1's cross-branch violation. Also test supplier twice, only one high-risk review, release before supplier completion, and J after a purported pass with no subsequent E–I.
5. Inspect any duplicated visible transition labels in the converted nets and explore silent-transition closure during trace acceptance, including the supplier skip and loop exit/redo. Ensure silent choices do not admit a release that bypasses a required visible obligation or create a silent livelock. Match transition identity as well as label when investigating ambiguous replays.

The loop makes the complete trace language infinite, so finite tests cannot prove equivalence. Soundness is a structural property, not a proof of the business rules; silent choices and duplicate labels require careful acceptance checking. Completion-only traces cannot validate start-time constraints, actual overlap, or the correspondence between branch choices and case data. Stronger assurance would compare the converted POWL net with an independently specified reference using an appropriate language-equivalence or reachability analysis, subject to its own assumptions and computational limits.

# 8. Final Self-Critique

1. Completion-only semantics cannot establish that an activity started after its prerequisites, even when its completion appears in the correct order.
2. The process-tree phase barrier excludes more behavior than necessary for safety; a larger duplication-based tree might preserve more valid traces at the cost of complexity and label ambiguity.
3. The validation plan is finite in practice and conversion and soundness interfaces can vary by PM4Py version; it does not by itself prove the implementation's full infinite language matches the specification.
