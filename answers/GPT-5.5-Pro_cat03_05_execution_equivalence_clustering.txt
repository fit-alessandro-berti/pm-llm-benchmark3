## 1. Equivalence design space

**1. Activity-sequence equivalence.**
Operational definition: for each execution, project every event to its activity label only, preserving repetitions and timestamp order. Two executions are equivalent iff these label sequences are equal. For same-time events, I would use ordered timestamp buckets, where each bucket contains an unordered multiset of labels; if the source system has a reliable event index, the index can be used as a secondary order instead.

This preserves activity names, repetition counts, and temporal order or bucket order. It discards object identifiers, object types, object multiplicities, external-object participation, E2O incidence, O2O relations, qualifiers, and all business meaning of shared logistics or finance. It is reflexive, symmetric, and transitive because it is equality of a canonical label representation.

**2. Typed structural equivalence under identifier renaming.**
Operational definition: construct a typed object-centric graph for the lead Order execution. Event nodes carry activity labels and order or timestamp-bucket position. Object nodes carry object type and an external/local flag. E2O edges connect events to involved objects. O2O edges carry relation labels and qualifiers where supplied, for example `packs`, `carries`, `bills`, `settles`, `partially_settles`, `completes_settlement`, `replaces`, and `removed_before_dispatch`. Two executions are equivalent iff there is a bijection between local object identifiers of the same type, and separately between external object identifiers of the same type, that makes the ordered event graph and O2O graph identical.

This preserves object types, local/external distinction, object multiplicities, repeated activities, event-object incidence, O2O topology, relation labels, and qualifiers. It discards raw local identifier spellings such as `O1` versus `O2`, and it ignores numeric suffix order unless it affects event order or relations. It is reflexive, symmetric, and transitive because graph isomorphism under a fixed typed vocabulary is an equivalence relation. Same-time events are handled as unordered event buckets; isomorphism may permute events inside a bucket if their activity and incident object patterns allow it.

**3. Business-semantic equivalence, my preferred relation.**
Operational definition: two executions are equivalent iff they have the same lead-order business signature: number of local items, packages, deliveries, invoices, and payments; whether logistics are isolated or shared with external orders/items; whether finance is isolated or shared with external orders; package-to-item cardinalities; delivery-to-package cardinalities; invoice-to-order and payment-to-invoice cardinalities; return/repack motifs; replacement/removal motifs; and payment-settlement motif. Unlike strict structural equivalence, it may ignore irrelevant symmetric identity distinctions and harmless ordering among independent same-type events.

This preserves the distinctions that change operational interpretation: single versus split package, consolidated versus split delivery, single versus partial payment, cross-order package sharing, cross-order invoice sharing, pre-dispatch replacement, and post-dispatch return/repack. It discards raw IDs, arbitrary order among symmetric items, and low-value topology details that do not change the business motif. It is reflexive, symmetric, and transitive as defined, because it is equality of a canonical semantic signature. Same-time events are represented as unordered buckets unless a causal motif requires an order, for example return before repack.

## 2. Canonical signatures

A reproducible canonical-signature scheme for the preferred semantic relation can be built as follows. It is invariant to local identifier renaming but preserves object type, externality, multiplicity, event order or timestamp buckets, repeated activities, E2O object-type incidence, O2O qualifiers, and lifecycle motifs.

```python
from collections import Counter, defaultdict

def ext_flag(oid: str) -> str:
    return "EXT" if str(oid).startswith("EXT") else "LOCAL"

def role(oid, object_type_by_id):
    return (object_type_by_id[oid], ext_flag(oid))

def multiset_signature(counter):
    return tuple(sorted(counter.items()))

def canonical_semantic_signature(events, o2o, object_type_by_id, lead_order_id):
    """
    events: list of records with fields:
        ts_bucket, activity, objects = {object_type: [object_ids]}
    o2o: list of records:
        source, target, relation, qualifier
    object_type_by_id: dict object_id -> object_type
    lead_order_id: the local Order around which execution is centered
    """

    # 1. Activity/E2O signature: preserve activity order, repeated labels,
    #    and object-type/externality multiplicities per event.
    buckets = defaultdict(list)
    for ev in events:
        c = Counter()
        for ids in ev.objects.values():
            for oid in ids:
                c[role(oid, object_type_by_id)] += 1
        buckets[ev.ts_bucket].append((ev.activity, multiset_signature(c)))

    event_sig = tuple(
        tuple(sorted(buckets[bucket])) for bucket in sorted(buckets)
    )

    # 2. Object multiplicities by type and externality.
    obj_count = Counter(role(oid, object_type_by_id) for oid in object_type_by_id)
    obj_sig = multiset_signature(obj_count)

    # 3. O2O motif summaries, avoiding raw local identifiers.
    rels_by_relation = Counter()
    package_item_cards = defaultdict(Counter)
    delivery_package_cards = defaultdict(Counter)
    invoice_order_cards = defaultdict(Counter)
    invoice_payment_cards = defaultdict(Counter)
    qualifier_counts = Counter()

    for r in o2o:
        s_role = role(r.source, object_type_by_id)
        t_role = role(r.target, object_type_by_id)
        rel = r.relation
        qual = r.qualifier or ""

        rels_by_relation[(s_role, rel, qual, t_role)] += 1
        if qual:
            qualifier_counts[qual] += 1

        if rel == "packs" and object_type_by_id[r.source] == "Package":
            package_item_cards[r.source][role(r.target, object_type_by_id)] += 1

        if rel == "carries" and object_type_by_id[r.source] == "Delivery":
            delivery_package_cards[r.source][role(r.target, object_type_by_id)] += 1

        if rel == "bills" and object_type_by_id[r.source] == "Invoice":
            invoice_order_cards[r.source][role(r.target, object_type_by_id)] += 1

        if rel in {"settles", "partially_settles", "completes_settlement"}:
            # payment -> invoice
            invoice_payment_cards[r.target][rel] += 1

    pack_sig = tuple(sorted(multiset_signature(c) for c in package_item_cards.values()))
    delivery_sig = tuple(sorted(multiset_signature(c) for c in delivery_package_cards.values()))
    invoice_sig = tuple(sorted(multiset_signature(c) for c in invoice_order_cards.values()))
    payment_sig = tuple(sorted(multiset_signature(c) for c in invoice_payment_cards.values()))

    # 4. Lifecycle motifs from activities and O2O qualifiers.
    act_counts = Counter(ev.activity for ev in events)
    motif_sig = (
        ("returns", act_counts["Return Item"]),
        ("inspect_returns", act_counts["Inspect Return"]),
        ("replacement_edges", sum(v for (s, rel, q, t), v in rels_by_relation.items()
                                  if rel == "replaces" or q == "removed_before_dispatch")),
        ("external_logistics",
            any(ev.activity in {"Pack Package", "Dispatch"} and
                any(ext_flag(oid) == "EXT" for ids in ev.objects.values() for oid in ids)
                for ev in events)),
        ("external_finance",
            any(ev.activity in {"Issue Invoice", "Record Payment"} and
                any(ext_flag(oid) == "EXT" for ids in ev.objects.values() for oid in ids)
                for ev in events)),
    )

    return {
        "event_sig": event_sig,
        "object_sig": obj_sig,
        "pack_sig": pack_sig,
        "delivery_sig": delivery_sig,
        "invoice_sig": invoice_sig,
        "payment_sig": payment_sig,
        "qualifiers": multiset_signature(qualifier_counts),
        "motifs": motif_sig,
    }
```

## 4. Cluster interpretations

**S1 — clean isolated single shipment.** Signature: `2 local items → 1 local package → 1 local delivery; 1 invoice; 1 payment; no external sharing; no special qualifiers`. This is the uncomplicated order-to-cash case. The main opportunity is to use it as a reference cohort for timing, cost, and automation. Order flattening represents it fairly well; item flattening may duplicate the shared pack/dispatch events. It is stable under ordinary repair unless hidden external sharing or missing replacement qualifiers are later added.

**S2 — split packaging, consolidated delivery.** Signature: `two local items, two packages, one delivery carrying both packages`. Business behavior: warehouse creates separate parcels, but transport remains consolidated. Risk is increased packing workload and package-level loss/damage complexity, while customer-facing shipment remains simple. Order flattening shows two Pack events but poorly represents that there is only one Delivery object carrying both packages. The cluster is stable if the Dispatch E2O relation reliably lists both packages; if a missing second Delivery were repaired, it would move toward S3.

**S3 — split fulfillment with partial payment.** Signature: `two package-delivery pairs; one invoice; two payments, partial then complete`. This means physical fulfillment and financial settlement are both fragmented. Risks include coordination failures, duplicate shipping cost, invoice reconciliation effort, and confusion over whether the first payment was incomplete or duplicated. Order flattening shows repetition but not the one-package-per-delivery mapping or payment qualifiers. Stability is high for split fulfillment; the exact partial-payment interpretation is less stable if payment qualifiers are missing or amounts are modeled only as attributes.

**S4 — cross-order logistics sharing.** Signature: `lead order’s package/dispatch events include external order/item; invoice bills only lead order`. Business behavior: logistics are batched across orders, while finance remains order-specific. This may be efficient consolidation, but it creates traceability and allocation risks: damage, delay, or recall of the shared package affects multiple orders. Order flattening around O5 would falsely look baseline; package or delivery flattening would show the sharing but lose the lead-order financial boundary. Stable only if `EXT` participation is intentional and not a data-import artifact.

**S5 — cross-order finance sharing.** Signature: `local package and delivery; invoice/payment include external order; no order-level allocation`. This is consolidated billing or shared payment. Operationally it may reduce invoicing cost, but it increases revenue-recognition, settlement-allocation, and dispute risk. Order flattening makes it look like a normal paid order; invoice flattening reveals the multi-order invoice but may obscure that logistics were independent. Stability depends on whether shared invoice/payment is a real business design or a missing allocation relation.

**S6 — pre-dispatch replacement/removal.** Signature: `single package and delivery at label level; replacement/removal qualifier before dispatch`. Business behavior: one item was substituted or removed after initial packing. The risk is high if billing and dispatch eligibility depend on the final item set, because the label sequence gives false reassurance. Order flattening and even simple object-count flattening represent it poorly; the O2O qualifier is essential. Stability is medium: if qualifiers are ignored, this may collapse toward S1 or become a vague Dispatch anomaly.

**S7 — return, repack, redelivery.** Signature: `initial dispatch; return item; inspect return; repack returned item; second dispatch; replacement package relation`. This is a post-dispatch exception and recovery path. Risks include customer delay, reverse-logistics cost, inventory quality issues, and possible double-shipment confusion. Order flattening captures the visible return activities but poorly represents which item and package are superseded. It is relatively stable because the return and repack events are explicit, even if the `P82 replaces P81` O2O note is repaired or refined.

## 5. Borderline cases

**X1 versus X2.** Activity-sequence equivalence and typed structural equivalence both group them. A raw-ID exact comparison would split them, but that would violate the intended renaming invariance unless the IDs encode meaningful source-system semantics.

**X1 versus X5.** Activity-sequence equivalence groups them because the label trace is identical. Typed structural and business-semantic equivalence split them because X5’s Package and Delivery include an external order and external item. A lead-order-only financial view could defensibly group them, since the invoice bills only O5.

**X1 versus X6.** Activity-sequence equivalence and a logistics-only equivalence group them. Finance-aware semantic equivalence splits them because X6 has an invoice and payment involving `EXT-OB` with no allocation. This is not a packing difference; it is a settlement-boundary difference.

**X1 versus X7.** Activity labels group them. A relation-qualified semantic view splits them because item replacement/removal changes the final fulfilled item set. If all O2O qualifiers and the Dispatch-to-Item incidence were ignored, X7 could be misclassified as baseline.

**X3 versus X4.** A coarse “split into two packages” equivalence groups them because both have two items packed separately. Fulfillment-aware and finance-aware definitions split them: X3 has one consolidated delivery and one payment; X4 has two deliveries and two settlement events.

**X4 versus X8.** A coarse “two dispatches/two deliveries” equivalence can group them. Lifecycle semantics split them sharply: X4 is planned or operationally split fulfillment with partial payment; X8 is exception handling after a return, inspection, repack, and redelivery.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

The relevant PM4Py method clusters process executions around a chosen object type. The documented key structure has two parts: first, a tuple representing the sequence of events, where each event tuple starts with the activity name followed by the related object identifiers; second, a tuple representing the objects, where each object tuple contains the object identifier and object type. PM4Py’s OCEL representation also has event-object relations and O2O relations that can be qualified, but the described clustering key itself is identifier- and event-sequence oriented, not a business-semantic motif key. ([GitHub][1])

Raw object identifiers can make exact clusters too fine because executions such as X1 and X2 are the same after local renaming but have different object names. I would post-process returned keys by replacing IDs with canonical roles such as `(Item, LOCAL, #1)` or, for coarser business clustering, with multiplicities such as “two local Items.” Exact equivalence is still preferable for audit replay, data-quality checks, suspected duplicate events, and debugging object extraction. For segmentation, it is usually too brittle. `max_objs` and very large connected executions matter because cross-order batches can create huge components; setting a cap too low may exclude the exact executions where sharing is most important, while setting it too high may be slow or produce very sparse exact clusters.

```python
import pm4py
import pandas as pd
from collections import Counter, defaultdict

LEAD_OBJECT_TYPE = "Order"

exact = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=LEAD_OBJECT_TYPE,
    max_objs=200
)

def is_ext(oid):
    return str(oid).startswith("EXT")

def normalize_pm4py_key(key):
    event_seq, object_seq = key
    oid_type = {oid: typ for oid, typ in object_seq}

    norm_events = []
    for ev in event_seq:
        activity, *oids = ev
        roles = Counter(
            (oid_type.get(oid, "?"), "EXT" if is_ext(oid) else "LOCAL")
            for oid in oids
        )
        norm_events.append((activity, tuple(sorted(roles.items()))))

    obj_roles = Counter(
        (typ, "EXT" if is_ext(oid) else "LOCAL")
        for oid, typ in object_seq
    )
    return (tuple(norm_events), tuple(sorted(obj_roles.items())))

def o2o_motif_summary(exec_ocel):
    o2o = getattr(exec_ocel, "o2o", pd.DataFrame())
    if o2o is None or o2o.empty:
        return ()

    cols = set(o2o.columns)
    src_col = next(c for c in ["ocel:source", "source", "ocel:oid"] if c in cols)
    tgt_col = next(c for c in ["ocel:target", "target", "ocel:oid_2"] if c in cols)
    qual_col = next((c for c in ["ocel:qualifier", "qualifier"] if c in cols), None)

    # In real code, build this from exec_ocel.objects.
    obj_type = dict(zip(exec_ocel.objects["ocel:oid"], exec_ocel.objects["ocel:type"]))

    motifs = Counter()
    for _, row in o2o.iterrows():
        s, t = row[src_col], row[tgt_col]
        q = row[qual_col] if qual_col else ""
        s_role = (obj_type.get(s, "?"), "EXT" if is_ext(s) else "LOCAL")
        t_role = (obj_type.get(t, "?"), "EXT" if is_ext(t) else "LOCAL")
        motifs[(s_role, str(q), t_role)] += 1

    return tuple(sorted(motifs.items()))

business_clusters = defaultdict(list)

for exact_key, exec_ocels in exact.items():
    base_key = normalize_pm4py_key(exact_key)
    for exec_ocel in exec_ocels:
        semantic_key = (base_key, o2o_motif_summary(exec_ocel))
        business_clusters[semantic_key].append(exec_ocel)

summary = {
    semantic_key: len(executions)
    for semantic_key, executions in business_clusters.items()
}
```

## 7. Robustness analysis

If **all O2O qualifiers are ignored**, X4 remains separate from X1 because it still has two payment events, but “partial then complete” becomes merely “two payments.” X8 remains separate because Return, Inspect, Pack, and Dispatch events are explicit. X7 is most affected: if `replaces` remains as a relation label, it is still distinct; if replacement/removal was encoded only as a qualifier, it may collapse toward S1.

If **external objects are ignored**, X5 and X6 collapse dangerously toward S1. X5 loses the fact that the package and delivery are shared with another order. X6 loses the consolidated billing/payment risk. This perturbation is acceptable only for a narrow lead-order activity report, not for compliance or reconciliation.

If **repeated same-label events are collapsed**, X3 may look closer to baseline unless package multiplicity is retained. X4 still has two deliveries and possibly two payments if object counts survive, but its workload pattern becomes less visible. X8 still has return-specific labels, so it remains separate, although the second Pack/Dispatch recovery cycle is weakened.

If **Pack and Dispatch order is treated as partial rather than total**, X4 can group with executions where both packages are packed before both dispatches, provided the same package-delivery mapping holds. This is reasonable when timestamps reflect batch entry rather than true sequence. It should not group X4 with X8 because return and repack impose a causal order.

If **payment multiplicity is modeled as an amount attribute rather than structure**, X4 may move from “partial-payment structure” to “single invoice with payment schedule.” That is useful for revenue reporting but loses back-office workload caused by multiple payment events.

## 8. Limitations and recommendation

For **compliance monitoring**, use typed structural or business-semantic equivalence that preserves external objects, O2O qualifiers, replacement motifs, and finance-sharing motifs. The key risk is not just whether the activity labels occurred, but whether the right objects were packed, dispatched, billed, and settled.

For **operational segmentation**, use the preferred business-semantic clusters S1–S7. They separate clean fulfillment, split packaging, split delivery, shared logistics, shared finance, replacement, and return/repack without overvaluing arbitrary local identifiers.

For **root-cause analysis**, start with business-semantic clusters and then drill down into typed structural variants and attributes such as time, resource, amount, carrier, or warehouse. Root causes often live below the semantic cluster but above raw-ID exactness.

For **descriptive reporting**, use coarser activity or semantic summaries, but explicitly flag object-centric exceptions such as cross-order package sharing and shared invoices. A pure activity-label report would overstate the normality of X5, X6, and X7.

No single equivalence notion is best for all purposes. Activity-sequence equivalence is readable but too lossy. Strict structural equivalence is reproducible but can overfragment. Business-semantic equivalence is interpretable but depends on chosen domain motifs. The right level is therefore a decision tied to the monitoring question, not a universal property of the log.
