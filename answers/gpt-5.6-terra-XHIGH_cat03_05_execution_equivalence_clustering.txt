## 1. Equivalence design space

Let an execution be \(X=(E,O,\mathit{E2O},\mathit{O2O},\prec)\), anchored at one lead `Order`. Local object identifiers are treated as arbitrary names. `EXT-*` is not an identity to preserve literally, but its external-object status is meaningful.

### 1. Activity-sequence equivalence

Define the layered activity trace

\[
A(X)=[\,\{\!\{a(e): e\in E_t\}\!\}\,]_{t=1}^{k},
\]

where \(E_t\) is the set of events at timestamp layer \(t\), and braces denote a multiset. Two executions are activity-sequence equivalent iff their layered traces are equal.

It preserves activity labels, repeated activities, and temporal layer order. It discards object identifiers and types, E2O incidence, O2O links, external sharing, qualifiers, and all object multiplicities except those indirectly reflected by repeated event labels.

This is reflexive, symmetric, and transitive because it is equality of a normalized trace.

For concurrent or same-time events, events in the same timestamp layer are unordered: `{Pack, Dispatch}` differs from two sequential layers `[Pack],[Dispatch]`, but not from `[Dispatch, Pack]` at the same timestamp. If timestamps are totally ordered, every layer has one event.

### 2. Typed structural equivalence under identifier renaming

Construct a typed graph with:

- object nodes labelled by `(object type, external flag, is_lead_order)`;
- event nodes labelled by activity and timestamp layer;
- E2O edges from events to objects;
- unqualified O2O edges such as `contains`, `packs`, `carries`, `bills`, and `settles`;
- temporal precedence between timestamp layers.

Two executions are typed-structurally equivalent iff there is a graph isomorphism mapping lead order to lead order, preserving node labels, E2O incidence, base O2O predicates, event multiplicity, and temporal layers. Object IDs may be renamed within type/externality classes.

This preserves typed object counts, which objects recur across events, package-to-delivery structure, invoice sharing topology, and temporal order. It discards raw local IDs, absolute timestamps, event attributes, and—in this definition—fine O2O qualifiers such as `partial`, `complete`, and `removed_before_dispatch`.

Graph isomorphism is reflexive, symmetric, and transitive. Events in a common timestamp layer may be permuted by the isomorphism; events in different layers may not.

### 3. Preferred business-semantic equivalence

My preferred relation compares a canonical business projection rather than either a pure trace or raw graph. It preserves:

- item/package/delivery cardinalities and item-to-package-to-delivery paths;
- whether logistics or finance touches external objects;
- invoice and payment multiplicity;
- semantic O2O qualifiers, including replacement, removal-before-dispatch, partial settlement, and completion;
- lifecycle motifs such as return, inspection, repack, and redispatch;
- causal order, but not arbitrary ordering of independent events.

For example, `Pack(P41) < Dispatch(D41)` is causal, while the ordering between independent `Add Item` events is not. The projection deliberately ignores raw IDs, absolute timestamps, incidental attributes, and total ordering induced merely because every event mentions the lead order.

Two executions are business-semantically equivalent iff their canonical business projections are equal. Thus this is also reflexive, symmetric, and transitive. It is not merely a similarity score with an arbitrary threshold.

For concurrency, the projection uses a partial order: event order is retained when implied by shared non-lead objects, an explicit lifecycle motif, or a domain dependency such as invoice-before-payment. Otherwise simultaneous or independent events can be permuted.

A possible fourth, stricter relation for audit use would be **qualified typed structural equivalence**: relation 2 plus all O2O qualifiers and full observed timestamp order.

## 2. Canonical signatures

The following scheme makes the preferred relation reproducible. It is intentionally invariant to local renaming, including renaming `I11` to `I22`. It preserves externality, but not the literal spelling of external IDs.

```python
def preferred_signature(execution):
    # 1. Build a semantic graph G.
    # Object color: (kind="object", object_type, is_external, is_lead)
    # Event color:  (kind="event", activity)
    G = ColoredDirectedMultigraph()

    for o in execution.objects:
        G.add_node(o.id, color=(
            "object", o.type, o.id.startswith("EXT"), o.is_lead_order
        ))

    for e in execution.events:
        G.add_node(e.id, color=("event", e.activity))
        for o in e.related_objects:
            G.add_edge(e.id, o.id, label=("E2O", o.type))

    # Retain semantically meaningful O2O predicates and qualifiers.
    for r in execution.o2o_relations:
        # Examples: packs, carries, bills, settles(partial),
        # replaces, removed_before_dispatch.
        G.add_edge(r.source, r.target,
                   label=("O2O", r.base_predicate, r.qualifier))

    # Add causal, not merely global timestamp, order.
    for e1, e2 in causal_pairs(execution):
        # Examples: Pack(package) -> Dispatch(package);
        # Dispatch(delivery,item) -> Return(item);
        # Issue Invoice(invoice) -> Record Payment(invoice).
        G.add_edge(e1.id, e2.id, label=("before",))

    # 2. Canonically relabel graph nodes.
    # Partition nodes by color. Enumerate permutations within each color
    # class, serialize colored nodes and labelled edges, and choose lexicographic
    # minimum. A nauty/bliss-style canonical-labeling implementation is preferred
    # for non-toy executions.
    serializations = []
    for relabeling in all_color_preserving_permutations(G):
        nodes = sorted((relabeling[n], G.color[n]) for n in G.nodes)
        edges = sorted(
            (relabeling[u], edge.label, relabeling[v])
            for u, edge in G.edges
        )
        serializations.append((tuple(nodes), tuple(edges)))

    return min(serializations)
```

Repeated `Pack`, `Dispatch`, or `Record Payment` events remain separate event nodes. The signature distinguishes two packages in one delivery from two packages in two deliveries, and distinguishes an external co-billed order from an isolated invoice. In production, exhaustive permutation should be replaced by canonical graph labeling or partition-refinement plus backtracking.

## 4. Cluster interpretations

- **S0 — isolated single-package baseline (X1, X2).**  
  Signature: `2 items, 1 package, 1 delivery, 1 invoice, 1 payment, no external touch`. This is conventional end-to-end fulfilment. It is useful as a benchmark for service time and straight-through processing. An order-flattened trace represents the broad sequence adequately, but loses the fact that one package contains both items. It is stable under reasonable identifier repair and reordering of independent adds.

- **S1 — split packages with consolidated transport (X3).**  
  Signature: `2 items  2 packages  1 delivery`. This may reflect warehouse-zone picking with downstream carrier consolidation. It creates handling and handoff risk, but also an opportunity to measure package consolidation efficiency. A standard Order flattening shows two pack events and one dispatch but does not show that both packages belong to the same delivery. Stable unless package-to-delivery links are missing or repaired incorrectly.

- **S2 — staged multi-shipment and multi-payment execution (X4).**  
  Signature: `2 items  2 packages  2 deliveries; 1 invoice; partial then complete payment`. This is a split fulfilment case with financial staging. Risks include customer communication, partial-payment reconciliation, and duplicate shipment cost. Flattening to one Order trace poorly represents which package went in which delivery and why two payments occurred. Stable regarding shipment multiplicity; the partial/completion interpretation depends on qualifier quality.

- **S3 — externally shared logistics (X5).**  
  Signature: local items share a package and delivery with `EXT-OA` and `EXT-IA`, while billing is local. It suggests combined shipping, batching, or cross-order fulfilment. It may improve freight utilization but creates allocation, traceability, and privacy risks. An Order flattening makes it look identical to X1. It is stable only if external relations are reliably retained; deleting external links collapses it into S0.

- **S4 — externally shared finance (X6).**  
  Signature: local logistics but invoice and payment are associated with a second external order, without order-level allocation. It indicates consolidated invoicing or payment across orders. Risks are revenue allocation, dispute handling, and inability to establish settlement status per order. Order flattening hides the shared invoice entirely. Stable as a shared-finance cluster only while the external invoice relation and lack of allocation are recorded.

- **S5 — replacement/substitution execution (X7).**  
  Signature: two items packed, but one is removed before dispatch and the other replaces it. This is a fulfilment exception, potentially caused by stock substitution, quality failure, or customer-approved replacement. Risks are incorrect invoicing, customer dissatisfaction, and inventory reconciliation. Activity flattening makes it appear baseline-like. It is sensitive to qualifier quality: losing `removed_before_dispatch` weakens the interpretation substantially.

- **S6 — return and repack loop (X8).**  
  Signature: initial dispatch, return and inspection of one item, repack, then second dispatch. This is reverse logistics followed by re-fulfilment. It supports return-quality analysis but raises cost, fraud, and duplicate-shipping risks. An Order trace shows return events but does not naturally connect the returned `I82` to `P82` replacing its earlier package path. Stable if return-to-item and repack links are retained.

## 5. Borderline cases

- **X1 versus X2.** Raw-identifier exact matching can separate them because `O1`, `I11`, and `P11` differ from `O2`, `I22`, and `P21`. Identifier-renamed typed isomorphism and the preferred semantic relation group them. The latter is appropriate when identifiers are locally generated.

- **X1 versus X5.** Activity-sequence equivalence groups them. A local-only projection that deliberately removes external objects also groups them. External-aware structural or semantic equivalence separates them because the package and delivery are not operationally isolated.

- **X1 versus X6.** Again, activity equivalence groups them. A logistics-only segmentation could also group them because package and delivery paths match. A finance-aware semantic definition separates them due to shared invoice/payment ownership and absent allocation.

- **X1 versus X7.** A coarse “two items, one package, one delivery, one payment” profile can group them. The preferred qualifier-aware relation separates them because the delivered item is a replacement and one packed item was removed. Even the stated typed structural relation separates them because X7’s `Dispatch` event explicitly involves `I72`.

- **X3 versus X4.** A warehouse segmentation based only on “split package” behavior could group both. Full structural and semantic relations separate them: X3 consolidates two packages into one delivery, whereas X4 has two deliveries and two payment events.

- **X4 versus X8.** A very coarse shipping-leg profile sees two packages and two dispatches in both cases. Lifecycle-aware semantics separates them: X4 is parallel/split fulfilment with partial payment, while X8 is a return, inspection, replacement-package, and redispatch loop.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` is useful for exact execution descriptions, but its key is much closer to an E2O-level fingerprint than to a business motif. The key structure is an ordered execution description: event activity occurrences are retained together with the related raw object identifiers for those events. Consequently it preserves repeated activities, event ordering, and exact object co-participation/reuse. The object type is supplied by the OCEL relation/object context and the chosen anchor type.

This is stricter than identifier-renamed equivalence: raw `I11` versus `I22` can make otherwise isomorphic executions land in separate exact keys. It also does not automatically turn O2O qualifiers or missing allocation semantics into business motifs unless those facts have been encoded in the execution representation used for clustering.

A practical approach is to retain PM4Py’s exact clusters for auditability, then aggregate their member orders using an ID-free canonical signature such as section 2. Exact equivalence is preferable for duplicate detection, regression testing, and investigations where the precise shared object matters. Coarser semantic clustering is preferable for operational segmentation.

`max_objs` is important because externally connected executions can become large. A shared external order can pull many objects into an execution; exact keys become expensive and canonical graph matching becomes harder. The limit should be documented as a scope restriction, not silently interpreted as absence of complexity.

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"

# Exact PM4Py grouping. Current PM4Py variants commonly return a mapping
# from an exact execution-description key to member anchor object IDs.
exact_clusters = pm4py.cluster_equivalent_ocel(
    ocel,
    object_type=LEAD_TYPE,
    max_objs=250
)

# Build an audit map from Order to its PM4Py-exact key.
exact_key_of = {}
for raw_key, order_ids in exact_clusters.items():
    for oid in order_ids:
        exact_key_of[oid] = raw_key

OID = ocel.object_id_column
OTYPE = ocel.object_type_column
order_ids = ocel.objects.loc[
    ocel.objects[OTYPE].eq(LEAD_TYPE), OID
].tolist()

def execution_for_order(ocel, order_id):
    # Select events directly involving the lead Order and all objects
    # incident to those events. Extend this extraction with the supplied
    # O2O qualifier table when available.
    return extract_order_centered_execution(
        ocel, lead_order_id=order_id, include_external_objects=True
    )

semantic_clusters = defaultdict(list)
for order_id in order_ids:
    execution = execution_for_order(ocel, order_id)
    id_free_key = preferred_signature(execution)  # section 2
    semantic_clusters[id_free_key].append(order_id)

for semantic_key, members in semantic_clusters.items():
    print("semantic cluster:", members)
    print("PM4Py exact subclusters:",
          {repr(exact_key_of.get(x)) for x in members})
```

## 7. Robustness analysis

- **Ignore all O2O qualifiers.** Under the preferred signature, no listed clusters necessarily merge: X7 still has `I72` in `Dispatch`, X4 still has two payments, and X8 still has explicit return/repack events. However, S5 loses its strongest replacement interpretation, and a further coarse projection could merge X7 into S0.

- **Ignore external objects.** X5 and X6 both collapse into S0: their remaining local activity and local logistics/invoice topology match the baseline. This is a major loss, not harmless simplification.

- **Collapse repeated same-label events.** Activity clustering becomes much coarser: X1–X7 can approach one trace after collapsing repeated `Add`, `Pack`, `Dispatch`, and `Record Payment`; X8 remains distinct because of return and inspection. The preferred signature remains more robust if object and delivery multiplicities are retained, but it loses the staged nature of X4’s payments and dispatches.

- **Use partial rather than total Pack/Dispatch order.** X4’s two fulfilment branches become concurrent rather than serially staged. It remains distinct from X3 because it still has two deliveries and two payments. X1/X2 are unaffected; independent adds are already treated as reorderable.

- **Treat payment multiplicity as an amount attribute.** No payment amounts are supplied, so one cannot infer that X4 is financially equivalent to a one-payment order. If payment count is deliberately discarded, X4 loses its partial-settlement distinction but remains operationally distinct because of two deliveries.

## 8. Limitations and recommendation

For **compliance monitoring**, use qualified typed structural equivalence or direct rule checking: preserve external sharing, all qualifiers, and observed order. Compliance exceptions are often precisely the details a coarser cluster removes.

For **operational segmentation**, use the preferred business-semantic relation. It groups identifier-renamed routine orders while separating meaningful logistics, finance, substitution, and return motifs.

For **root-cause analysis**, begin with semantic clusters, then inspect the full qualified object graph within a cluster. The semantic cluster provides a useful cohort; exact relations explain the cause.

For **descriptive reporting**, activity-sequence variants, supplemented with package/delivery counts, are often clearest to nontechnical users.

No single notion is best: raw exactness is audit-friendly but over-fragments, activity traces are understandable but object-blind, and business semantics is useful for operations but depends on domain modelling and reliable qualifiers.
