## 1. Target definition
**Primary Target Formulation**: A multi-state competing-outcome target for all applications. The target is the mutually exclusive terminal state of an application at a 90-day horizon post-decision. The states are: Activated-Default, Activated-NonDefault, Rejected, Withdrawn, and Transferred.
**Prediction Time**: At the completion of the $k$-th event (fixed event-count prefix) or at elapsed time $t$ since application start (elapsed-time prefix).
**Horizon**: 90 days after the final credit decision (or 90 days post-activation for the activated state).
**Unit of Analysis**: A single credit application (case).
**Population**: All credit applications started within the observation window.
**Estimand**: The cause-specific cumulative incidence (probability) of reaching each terminal state within the horizon, given the event prefix.

**Alternative Target**: Default within 90 days *conditional on activation*. This target predicts the probability of default assuming the application is accepted and activated. While it directly answers the narrow definition of default, it suffers from severe selection bias (reject inference problem). It answers "What is the risk if we approve this?" but trains only on cases the historical policy already deemed safe enough to approve, making it statistically biased when applied to the general population of all applications. The primary multi-state formulation is operationally and statistically defensible because it models the actual observable outcomes for every application without fabricating counterfactuals or conditioning on the future.

## 2. Cohort construction
**Inclusion Rules**: All applications started between 1 January 2024 and 31 December 2025.
**Exclusion Rules**: None at the population level, but cases are partitioned by maturity and censoring status.
**As-of Rule**: The data extraction date is 15 February 2026. Only information recorded prior to this timestamp is available. Cases requiring a 90-day horizon plus up to 35 days of delayed feed (125 days total) must have started their horizon before 13 October 2025 to be considered mature.

**Cohort-Flow Table (Total Applications: 48,000)**
| Category | Count | Status / Treatment |
| :--- | :--- | :--- |
| **Total Started** | **48,000** | **Base Population** |
| - Still-open applications | 5,100 | Right-censored (not yet mature) |
| - Activated (immature/delayed feed) | 3,600 | Right-censored (label not yet mature) |
| - Transferred applications | 2,900 | Competing outcome / missing follow-up |
| - Withdrawn applications | 5,700 | Competing outcome |
| - Rejected applications | 9,100 | Competing outcome (selectively unobserved default) |
| **Labeled Activated (Mature)** | **21,600** | **Fully Observed (18,900 Non-default, 2,700 Default)** |

## 3. Censoring and missing-label strategy
- **Ordinary right censoring**: Applies to the 5,100 still-open applications and cases that reached a decision too close to the extraction date.
- **Delayed labels**: The 7–35 day delay in the external outcome feed means accounts activated within 125 days of extraction (3,600 cases) are treated as right-censored to prevent artificially inflating the non-default class.
- **Selection through activation**: Rejected and withdrawn cases (14,800) are treated as competing terminal events rather than non-defaults. Default is undefined/unobservable for them under the current policy.
- **Transfer as a competing event or missing follow-up mechanism**: Transferred cases are treated as a competing risk. For the 60% with a linkage table, outcomes could theoretically be joined, but the 40% unlinked represent missing follow-up.
- **Permanently missing outcome feeds**: Partner-originated accounts with missing feeds are treated as right-censored, though this censoring may be informative (non-random).

**Primary Analysis Strategy**: A competing-risks survival model (e.g., cause-specific hazard models) predicting the time to each mutually exclusive terminal state. Right censoring is applied to open and immature cases.
**Sensitivity Analysis**: A semi-supervised reject inference model (e.g., Heckman selection model) to impute the counterfactual default risk of rejected cases.
**Assumptions**: The assumption that delayed labels are missing completely at random (MCAR) conditional on time is testable. The assumption that permanently missing feeds for partner accounts are missing at random (MAR) given covariates is partially testable. The counterfactual default outcome of rejected cases is missing not at random (MNAR) and fundamentally untestable from these data.

## 4. Prefix extraction
Prefixes will be generated strictly using data available at the prediction point to prevent future leakage.
- **Fixed event-count prefixes**: Extract the first $k$ events for each case.
- **Elapsed-time prefixes**: Extract all events occurring within $t$ hours of the application start.
- **Short cases**: Cases that reach a terminal state before length $k$ or time $t$ will be excluded from the training set for that specific prefix length, or padded with a dummy "Terminal" event if using sequence models.
- **Repeated document loops**: The control flow will be preserved, but to avoid state explosion, repeated "request documents" activities will be aggregated into a numerical rework count feature (`documents_requested_count`) for the prefix.
- **Activity renaming**: A mapping dictionary will be applied to the event log prior to prefix extraction to unify post-migration (15 October 2025) activity names with their pre-migration equivalents.

## 5. Process-aware features
Features available at prediction time will be extracted from the prefix:
- **Static case attributes**: `case:channel`, `case:region`, `case:requested_amount`.
- **Prefix-derived features**:
  - *Control-flow*: Last completed activity, one-hot encoded presence of specific activities in the prefix.
  - *Timing*: Elapsed time since application start, time since the previous event, day of the week.
  - *Rework*: Count of "request documents" loops within the prefix.
- **Historical reference data (Process Context)**:
  - *Resource/queue*: The current workload of the assigned resource (active cases) and the queue length at the current activity, computed by replaying the event log up to the prediction timestamp.
  - *Cohort/calendar*: The month of the application start to capture the 1 July 2025 policy change context.

## 6. Leakage audit
| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
| :--- | :--- | :--- | :--- | :--- |
| `final_limit` | Future leakage | Not available at early prefix | Drop | Populated only after the final credit decision; reveals the outcome. |
| `decision_reason` | Future leakage | Not available at early prefix | Drop | Populated at/after Accept/Reject; directly reveals the decision. |
| `collection_status` | Target leakage | Not available at early prefix | Drop | Updated after activation; directly reveals default status. |
| Future events | Future leakage | Must not exist in prefix | Drop/Filter | Events like Contract Signed or Default Recorded must be filtered out of early prefixes. |
| `documents_total` | Temporal leakage | Only documents up to prefix time | Repair | Nightly snapshot includes future documents from the same day. Must recompute running total from event timestamps. |
| Updated `risk_score` | Temporal leakage | Score at the time of the event | Repair | Forward-fill the score from previous events; do not use the final case-level score. |
| Resource experience | Temporal leakage | Experience at the event time | Repair/Drop | Stored as experience at extraction time. Must subtract the time difference, or drop if hire date is unavailable. |
| Label availability | Target leakage | Not available at early prefix | Drop | `label_available_at` indicates that an outcome occurred, perfectly predicting maturity. |

## 7. Validation design
A strict temporal validation scheme will be used to evaluate performance under distribution shift. A random split is misleading because it leaks future policy and system dynamics into the training set and ignores the temporal nature of right-censoring.
- **Training Set**: Cases starting 1 January 2024 – 30 June 2025 (Pre-policy change).
- **Validation Set**: Cases starting 1 July 2025 – 30 September 2025 (Post-policy change, pre-migration). Used for calibration and hyperparameter tuning.
- **Test Set**: Cases starting 1 October 2025 – 13 October 2025 (Post-migration, up to the maturity cutoff). Tests robustness to the system migration and evaluates true future performance.
- **Evaluation Metrics**: Brier score for competing risks, cause-specific time-dependent AUC, and cause-specific calibration plots.
- **Subgroup Performance**: Metrics will be disaggregated by `case:channel` and `case:region` to ensure fairness and robustness across partner platforms.

## 8. Limitations and decision-use boundary
**Claims**: The study can claim to identify the predictive association between early application behaviors and the eventual terminal state under the historical credit policy.
**Limitations**: It cannot claim to measure the counterfactual default risk of rejected applications. Selection effects dominate the labeled data; the model learns "who defaults among those we currently approve," not "who would default if we approved everyone."
**Deployment Impacts on Data-Generating Process**:
1. **Performativity**: If the model is used to automatically reject high-risk cases, those cases will never activate, censoring their default outcomes and degrading future model retraining.
2. **Strategic Behavior**: Applicants or agents may learn the model's features and game the system (e.g., delaying applications to a different day of the week or altering requested amounts) to lower their risk score.
3. **Policy Drift**: Future changes to partner platform integrations or credit thresholds will shift the underlying distribution, requiring continuous monitoring of the competing-risk baseline hazards.

## 9. PM4Py-oriented Python implementation skeleton
```python
import pandas as pd
import pm4py
from pm4py.objects.log.util import dataframe_utils

def prepare_pm_study(csv_path: str, extraction_date_str: str):
    # 1. Read CSV and parse timestamps
    df = pd.read_csv(csv_path, parse_dates=["time:timestamp", "data_extract_time"])
    df = dataframe_utils.convert_timestamp_columns_in_df(df)
    
    # 2. Format dataframe for PM4Py
    df = pm4py.format_dataframe(
        df, 
        case_id="case:concept:name", 
        activity_key="concept:name", 
        timestamp_key="time:timestamp"
    )
    
    # 3. Repair activity renaming from system migration (Oct 15, 2025)
    migration_map = {"Identity Check V2": "Identity/KYC Check", "Credit Review New": "Credit Review"}
    df["concept:name"] = df["concept:name"].replace(migration_map)
    
    # 4. Build case-level maturity and terminal state information
    case_starts = df.groupby("case:concept:name")["time:timestamp"].min().reset_index(name="case_start_time")
    case_ends = df.groupby("case:concept:name")["time:timestamp"].max().reset_index(name="case_end_time")
    
    # Extract terminal activity to define competing states
    terminal_events = df.sort_values(["case:concept:name", "time:timestamp"]).groupby("case:concept:name").tail(1)
    terminal_events = terminal_events[["case:concept:name", "concept:name", "default_90d"]].rename(
        columns={"concept:name": "terminal_activity"}
    )
    
    case_info = case_starts.merge(case_ends, on="case:concept:name").merge(terminal_events, on="case:concept:name")
    
    # Define maturity cutoff: 90 days horizon + 35 days max feed delay = 125 days
    extraction_date = pd.to_datetime(extraction_date_str, utc=True)
    maturity_cutoff = extraction_date - pd.Timedelta(days=125)
    case_info["is_mature"] = case_info["case_start_time"] <= maturity_cutoff
    
    # 5. Temporal Train/Val/Test Split based on case start time (Avoid random split)
    train_cases = case_info[case_info["case_start_time"] < "2025-07-01"]["case:concept:name"]
    val_cases = case_info[(case_info["case_start_time"] >= "2025-07-01") & (case_info["case_start_time"] < "2025-10-01")]["case:concept:name"]
    test_cases = case_info[(case_info["case_start_time"] >= "2025-10-01") & (case_info["is_mature"])]["case:concept:name"]
    
    print(f"Cohort Split -> Train: {len(train_cases)}, Val: {len(val_cases)}, Test: {len(test_cases)}")
    
    df_train = df[df["case:concept:name"].isin(train_cases)].copy()
    
    # 6. Prefix extraction: Fixed-length prefixes (e.g., first 3 events)
    prefix_length = 3
    df_train["event_rank"] = df_train.groupby("case:concept:name")["time:timestamp"].rank(method="first", ascending=True)
    prefixes_train = df_train[df_train["event_rank"] <= prefix_length].copy()
    
    # 7. Leakage audit & prevention
    leakage_cols = [
        "final_limit", "decision_reason", "collection_status", 
        "default_90d", "label_available_at", "documents_total"
    ]
    prefixes_train = prefixes_train.drop(columns=[c for c in leakage_cols if c in prefixes_train.columns], errors="ignore")
    
    # Drop future events that shouldn't exist in early prefixes
    future_activities = ["Contract Signed", "Account Activated", "Collections Contact", "Default Recorded"]
    prefixes_train = prefixes_train[~prefixes_train["concept:name"].isin(future_activities)]
    
    # Repair risk_score: forward fill to ensure we only use the score available at the event time
    prefixes_train["risk_score"] = prefixes_train.groupby("case:concept:name")["risk_score"].ffill()
    
    # 8. Process-aware features extraction
    # Convert to event log for temporal feature extraction
    log_train = pm4py.convert_to_event_log(prefixes_train)
    temporal_features = pm4py.extract_temporal_features_dataframe(log_train)
    
    # 9. Leakage audit check
    assert "final_limit" not in prefixes_train.columns, "Leakage: final_limit present"
    assert "decision_reason" not in prefixes_train.columns, "Leakage: decision_reason present"
    assert not prefixes_train["concept:name"].isin(future_activities).any(), "Leakage: future activities in prefix"
    
    # Note: `temporal_features` would now be joined with `case_info` to train a survival model.
    return prefixes_train, case_info
```
