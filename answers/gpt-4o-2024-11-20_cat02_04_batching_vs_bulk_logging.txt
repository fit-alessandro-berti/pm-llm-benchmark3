# 3. Consequences for performance analysis

### G1: Apply label
- **Waiting time**: Likely accurate given automation and simultaneous batching.
- **Service time**: Unbiased; aligned with fixture constraints.
- **Utilization**: High concurrency would not bias utilization metrics.
- **Bottleneck detection**: Accurate as real concurrency is represented.

### G2: Surface inspection
- **Waiting time**: May appear higher than reality due to shared start time.
- **Service time**: Staggered end times give unbiased durations.
- **Utilization**: Slightly understated as batch start masks individual processing.
- **Bottleneck detection**: Could miss early-stage constraints near start batch.

### G3: Release review
- **Waiting time**: Overstated due to bulk completion.
- **Service time**: Potentially understated as processing overlaps.
- **Utilization**: Likely biased downward from shared account artifact.
- **Bottleneck detection**: Overshadowed by batch end submissions.

### G4: Pack item
- **Waiting time**: Unbiased or slightly overestimated (queue buildup during sequential process).
- **Service time**: Accurate as timestamps are granular and sequential.
- **Utilization**: Likely accurate for T-D resource.
- **Bottleneck detection**: Clearer identification of sequential flow possible.

### G5: Root-cause analysis
- **Waiting time**: Overestimated due to multitasking/shared-account artifact.
- **Service time**: Hard to disambiguate due to timestamp resolution.
- **Utilization**: Biased downward from shared account masking high effective use.
- **Bottleneck detection**: Less reliable when analysts cannot be individually identified.

### G6: Close ticket
- **Waiting time**: Appears inflated from fixed group close time.
- **Service time**: Commissive error—overstates zero service duration.
- **Utilization**: May appear intermittent and artificially low.
- **Bottleneck detection**: Artificial bulk events distort queueing models.

### G7: Manual measure
- **Waiting time**: Inflated by coarsened time rounding.
- **Service time**: Masked or approximate due to rounding effects.
- **Utilization**: Masked palliation conflates process overlap.
- **Bottleneck detection**: Unclear due to quarter-hour rounding imprecision.

### G8: Repair triage
- **Waiting time**: Could be overestimated due to queue buildup.
- **Service time**: Accurate at granular levels.
- **Utilization**: Likely accurate as process follows an aligning flow.
- **Bottleneck detection**: Captures transitional dynamics effectively.

# 4. PM4Py and pandas analysis

```python
import pandas as pd
from pm4py.objects.log.importer.csv import factory as csv_importer
from pm4py.algo.organizational.batch.discovery import algorithm as batch_discovery

# Input data as provided
data = [
    ["G1", "L01", "Apply label", "RBT-7", "08:54", "09:00", "09:03", "09:03:02", "PLC", "1 sec", 501],
    ["G1", "L02", "Apply label", "RBT-7", "08:55", "09:00", "09:03", "09:03:02", "PLC", "1 sec", 502],
    # ... (remaining rows omitted for brevity)
]

# Create DataFrame
columns = ["cluster", "case", "activity", "resource", "queue_arrival", "start", "complete", "recorded_at", "source", "precision", "sequence_no"]
df = pd.DataFrame(data, columns=columns)

# Format PM4Py interval log
interval_log = df.rename(columns={
    "case": "case:concept:name",
    "activity": "concept:name",
    "start": "start_timestamp",
    "complete": "time:timestamp",
    "resource": "org:resource"
})

# Discover batches with multiple parameters (merge_distance, min_batch_size)
for merge_distance in [1, 2]:
    for min_batch_size in [2, 4]:
        batches = batch_discovery.apply(interval_log, parameters={"merge_distance": merge_distance, "min_batch_size": min_batch_size})
        print(f"merge_distance={merge_distance}, min_batch_size={min_batch_size}")
        print(batches)

# Diagnostic metrics using pandas
df['start_diff'] = pd.to_datetime(df['start']) - pd.to_datetime(df['queue_arrival'])
df['completion_diff'] = pd.to_datetime(df['complete']) - pd.to_datetime(df['start'])
diagnostics = df.groupby("cluster").agg({
    "start_diff": ["mean", "max"],
    "completion_diff": ["mean", "max"],
    "resource": "nunique",
    "recorded_at": "nunique"
})
print(diagnostics)
```

# 5. Robustness and alternative explanations

1. **Resource IDs trusted vs shared**: Shared accounts (e.g., G5) can create multitasking artifacts. Treating all IDs as distinct can fragment concurrency patterns, while grouping inflates service time estimates.
2. **Timestamps exact vs interval-censored**: Exact timestamps (e.g., G6) would avoid rounding artifacts while coarse granularity confounds batch detection and queue modeling.
3. **Multiple temporal interpretations**:
   - **G3**: Shared account vs bulk completion.
   - **G7**: Coarsened time vs actual concurrency.
   - **G2**: Start-batch vs concurrent multitasking.

---

# 6. Data-collection redesign

1. **Execution timestamps**: Ensure precise, unrounded logging.
2. **Recording timestamps**: Log exact submission time as separate from execution.
3. **Source clocks**: Synchronize time sources.
4. **Resource/badge identity**: Retain individualized user data.
5. **Group/batch identifiers**: Enforce system-level batch tagging.
6. **Workstation capacity**: Explicitly log concurrent processing limits.
7. **Pause/resume events**: Allow fine-grained task interruption logging.
8. **Timestamp precision metadata**: Pair with confidence indicators.
