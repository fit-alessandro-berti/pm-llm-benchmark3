Now **2. Rule Interpretation**:

- RR1 (Drafter  Approver): for same case, Draft_Change_Request and Approve_Change must be by different humans (after alias normalization). Service accounts not humans; if svc_qms mapped to human, check against human.

- RR2 (Implementer  Verifier): same for Implement_Change and Verify_Implementation.

- RR3 (High-risk QM approval): HIGH-risk cases must be approved by QM (Asha) or valid QM delegate. Valid delegate requires:
  - Effective interval covers event time (e.g., delegation effective at or before event time and ends at or after event time)
  - Scope covers the change (e.g., D-QM-01 scope production-equipment, so covers CHG-501/503/504/506; D-QM-02 scope training-doc, covers CHG-508/509)
  - Principal is absent or formally unavailable when required by delegation. "When required" means if the delegation is to be used for that change, the principal must be absent/unavailable. "Absent" as recorded (annual leave), "formally unavailable" if e.g., on vacation, in meeting with no delegation override. Absence evidence includes recorded leave; "absent" does not require no activity (e.g., Asha's VPN session during leave — may indicate urgency, but still absent per leave record; formal unavailability could be "not available to approve within time window")
  - No prohibited subdelegation occurred (e.g., D-IC-03 prohibits subdelegation, so D-IC-04 invalid)
  - A later database entry (e.g., QMS db record created during migration) cannot retroactively validate an earlier delegation if the effective interval does not cover the event time; delegations must be effective at the time of approval. Evidence of delegation (signed PDF) at creation time suffices for validity if effective interval starts before event.

- RR4 (Emergency substitution): HIGH-risk emergency change may be implemented after approval by IC (Diego) or valid IC delegate. Valid IC delegate requires similar validity: effective interval covers event, scope covers change (CI-44 for D-IC-03), principal absent/unavailable, no subdelegation. Retrospective_QM_Review must occur within two business days (Mon-Fri, no weekends; e.g., impl on Mon  review by Tue or Wed? "Within two business days" typically means by the end of the second business day after implementation. If impl at time T on day X (BD), review must be on day X+1 or X+2. E.g., impl Aug 11 Mon 13:10, review by Aug 12 Tue 17:00 (BD1) or Aug 13 Wed 17:00 (BD2); Aug 14 Thu would be BD3, too late. - RR5 (Identity evidence): service account (svc_qms) is not human; conformance requires reliable session evidence mapping to authorized human. Normalized identities used for SoD checks.

- RR6 (Suspicion): repeated pairs etc. are indicators; not proof without evidence (e.g., collusion requires more than reciprocal approvals; could be workflow pattern)

**Business days**: Mon-Fri, weekends (Sat/Sun) not business days. "Within two business days" means counting only Mon-Fri; e.g., impl on Mon impl time, review must be done by end of Wed (Mon impl day + Tue BD1 + Wed BD2). Impl on Fri impl time, review by Mon (next week BD1) or Tue (BD2); but typically "within two business days" excludes weekends, so impl Fri 10:00, review by Mon 17:00 is BD1, Tue 17:00 BD2.

A db record created during interval confirms delegation is active then, but does not retroactively validate past events outside interval. Only effective interval matters for event-time validity.

## 2. Rule Interpretation

- **RR1 (Drafter/approver separation):** The human who performs `Draft_Change_Request` for a case must not perform `Approve_Change` for the same case. Applies to all cases (LOW/HIGH/emergency), no exception. Service accounts (`SvcAccount`) are not humans; if `Approve_Change` is by `SvcAccount`, RR1 is not violated against a human drafter (only human vs human checks), but a `SvcAccount` Verify may conflict with human Implementer if mapped.

- **RR2 (Implementer/verifier separation):** The human who performs `Implement_Change` must not perform `Verify_Implementation` for the same case. Same strict rule as RR1. Service accounts not humans; mapping uncertainty leads to flagging, not automatic violation.

- **RR3 (High-risk QM approval):** For HIGH-risk cases, `Approve_Change` must be performed by the QM (Asha) or a **valid** QM delegate. A delegation is valid **only at the event timestamp** if:
  1. Effective interval covers the event time (delegation start  event  delegation end).
  2. Scope covers the change (e.g., D-QM-01 scope "production-equipment" covers prod changes; D-QM-02 scope "training-document" covers training docs).
  3. Principal is **absent or formally unavailable** at the event time. "Absent" uses recorded leave (e.g., Asha’s annual leave 2026-08-10 00:00–2026-08-14 23:59 UTC). "Formally unavailable" means the principal has no ability to approve within the operational window (e.g., on vacation with no delegation override). The condition is checked per event time; if the principal is recorded on leave during the delegation interval, the condition is met. If the principal is present (e.g., Asha present on 2026-08-15), the "principal must be absent" clause for D-QM-02 makes the delegation invalid for usage on that day.
  4. No prohibited subdelegation occurred (e.g., D-IC-03 prohibits subdelegation; D-IC-04 is therefore invalid regardless of email evidence).
  - A later database entry (e.g., QMS db record created during migration) cannot retroactively validate a delegation for events outside its effective interval. Delegation validity is determined solely by event-time check (intervals + principal absence). Evidence at delegation creation (signed PDF, controlled db record) confirms delegation existence but does not override interval/absence check.

- **RR4 (Emergency substitution):** A HIGH-risk emergency change may be implemented after approval by the IC (Diego) or a **valid** IC delegate. "Valid IC delegate" follows the same event-time validity as RR3 (effective interval covers event, scope matches CI-44 for D-IC-03, principal absent/unavailable, no subdelegation). `Retrospective_QM_Review` **must** be performed by a QM or valid QM delegate within **two business days** of implementation. "Two business days" means counting only Mon–Fri (weekends excluded); e.g., implementation on Monday 10:00 UTC  review must occur by end of Wednesday 17:00 UTC (BD1 = Tuesday, BD2 = Wednesday). Implementation time on the business day is not counted as "day 0"; the first full business day after implementation is BD1. For example:
  - Impl 2026-08-11 (Monday) 13:10  BD1 = 2026-08-12 (Tue), BD2 = 2026-08-13 (Wed); review on 2026-08-14 (Thu) is BD3  violates "within two business days".
  - Impl 2026-08-11 (Monday) 10:00, review 2026-08-12 (Tue) 15:00  satisfies RR4 (review on BD1).
  The emergency flag (`emergency=true`) and safety rationale (`cooling_system`) are credible if they describe a safety-critical incident (e.g., cooling failure), but **RR4 timing requirement (within 2 BD for QM review) is mandatory; the justified exception applies only to implementation (may use IC approval without QM approval), not to review timing**. Thus late QM review (e.g., CHG-505 review 2026-08-14 vs impl 2026-08-11) violates RR4 even if emergency rationale is credible.

- **RR5 (Identity evidence):** A service account (`svc_qms`) is not a human identity. It supports conformance only if reliable session evidence maps the action to an authorized human (e.g., badge + FIDO token at session time matching workstation logs). Alias normalization (e.g., `u_bk`  "Ben") must be applied before SoD checks. Aliases belonging to the same human must be normalized (e.g., `b.koch`  "Ben") at event reconstruction.

- **RR6 (Suspicion versus proof):** Repeated resource pairs, unusual reciprocal approvals, shared workstations, concentrated handovers are **indicators** of potential issues but **not proof of collusion**. Evidence must include specific proof (e.g., meeting minutes, shared credential logs, conflicting statements). Ben drafting LOW training changes that Clara approves is a normal reciprocal pattern (Ben may draft docs, Clara verifies), not collusion.

- **Principal on leave:** If a principal (e.g., Asha) is on recorded annual leave (e.g., 2026-08-10–14), they are considered "absent" for the entire leave interval, even if they make a VPN session for an urgent case. "Absent" for delegation purposes means the principal is not formally available to approve per schedule (leave recorded); a VPN session does not override the leave status. Delegate validity depends only on principal absence at event time, not delegate availability.

- **Business days:** Mon–Fri are business days; Sat/Sun are not. "Within two business days" strictly means review must occur by the end of the second business day after implementation time. E.g., impl Monday  review deadline Wednesday end. No inclusion of implementation day as "day 0".

- **Later database entries:** Cannot prove earlier delegation validity. Only effective interval coverage at event time matters. A QMS db record created during migration (e.g., D-QM-01 db record 2026-08-12) confirms delegation existed during the interval but does not retroactively validate events before the interval start.

## 4. Collusion and Alternative-Explanation Analysis

- **Repeated Clara-Ben approvals (18/23 HIGH prod in 60 days):**  
  - *Benign explanation:* Normal workflow where Clara frequently drafts production-equipment changes (her frequent drafter role) and Ben (Quality Engineer) routinely approves them. No formal pair-rotation policy exists, so repeated pairing is natural. Security logs show same cell assignment; approvals occur during working hours with reasonable time gaps.   - *Evidence to discriminate:* Check for variation (e.g., approval time after draft, use of delegation records), workstation logs (same vs different), email trails for discussion. Absence of "reciprocal" approvals for high-risk decisions (e.g., no Ben drafting HIGH prod for Clara to approve) reduces collusion likelihood. Low severity indicator only; not proof.

# 3. RR4 review timing check (within two business days)
def within_two_bd(impl_time, review_time):
    """Return True if review_time occurs by end of 2nd business day after impl_time."""
    if impl_time is None or review_time is None:
        return None
    # Business day: Monday (0) to Friday (4)
    impl_wd = impl_time.weekday()  # 0=Mon, 4=Fri
    # Count business days starting from next business day
    bd_count = 0
    current = impl_time
    while current < review_time:
        current += pd.Timedelta(days=1)
        if current.weekday() < 5:  # Mon-Fri
            bd_count += 1
            if bd_count == 2:
                # Review must be <= current (end of day)
                if review_time <= current:
                    return True
                else:
                    return False
    # If review before impl or within first BD, return appropriately
    if review_time <= impl_time:
        return False  # review before impl
    # If never reached 2 BD before review
    # Check if review is within first BD
    first_bd_end = impl_time + pd.Timedelta(days=1) if impl_time.weekday() < 4 else impl_time + pd.Timedelta(days=3)  # if impl Fri, BD1 = Mon
    # Simpler: check minimal days
    delta_days = (review_time - impl_time).days
    # Exclude weekends: e.g., impl Mon, review Tue  delta=1, BD1=Tue  OK; impl Mon, review Wed  delta=2, BD2=Wed  OK; impl Mon, review Thu  delta=3, BD3=Thu  not OK
    # Count business days between impl_time (exclusive) and review_time (inclusive)
    bd_days = 0
    cur = impl_time + pd.Timedelta(days=1)
    while cur <= review_time:
        if cur.weekday() < 5:
            bd_days += 1
            if bd_days == 2:
                if review_time <= cur:
                    return True
                else:
                    return False
        cur += pd.Timedelta(days=1)
    return review_time <= impl_time + pd.Timedelta(days=2)  # fallback rough check
