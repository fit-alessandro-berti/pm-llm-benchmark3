## 1. Duplicate-handling decision tree

Decision order matters: exact identity  verified physical identity  semantic relationship  object evidence  risk containment.

```
Step 1: Are source_event_key + source + payload_hash + timestamp + activity byte-identical
        AND related objects identical?
        YES  EXACT TECHNICAL DUPLICATE
               Decision: DROP later ingested duplicate, keep earliest ingested_at
               Confidence: Very High | Provenance: mark duplicate_of
               Applies to NONE in this dataset (no identical payload_hash)

        NO 
Step 2: Is there EXTERNAL RECONCILIATION EVIDENCE that two eids are one physical observation?
        Example: reconciliation report, shared sensor ID, same invoice number + business key
        YES  SAME PHYSICAL EVENT, MULTI-SYSTEM OBSERVATION
               2a: Do payloads complement each other (e.g., WMS adds location vs scanner raw)?
                  YES  MERGE ATTRIBUTES AND RELATIONS (union, source-authoritative field priority)
                  NO (identical payloads)  DROP one, MERGE provenance
               Retain canonical eid, store source_event_keys[] , source[]
               Confidence: High if verified (e03/e04, e11/e16 with caveat)

        NO 
Step 3: Is one event a DERIVED SUMMARY / STATUS UPDATE causally generated from the other?
        Test: different abstraction, source_seq after, message-based, coarser payload/objects
              (e06 detailed Pack P1 with Items vs e07 Pack summary O1,P1;
               e13 detailed Capture M1 vs e15 invoice-level balance)
        YES  SUMMARY DERIVED FROM DETAILED
               3a CONSERVATIVE: RETAIN BOTH WITH REFINED LABELS/QUALIFIERS
                     e.g., `Pack Package_WMS_Detailed` vs `Pack Package_ERP_Status`
                      Prevents false rework, preserves abstraction level
               3b EVIDENCE-BASED AGGRESSIVE: MERGE only if downstream analysis requires
                     single business transition AND provenance + discarded summary fields logged
                      Decision: MERGE ATTRIBUTES, quarantine discarded fields
               Never DROP silently

        NO 
Step 4: Did ACTIVITY HARMONIZATION map semantically distinct source activities to one label?
        Test: original_activity / source semantics differ; documentation says e08=Released,
              e09=Accepted but both now `Dispatch Package`; shared objects are not proof.
        YES  HARMONIZATION COLLISION
               Decision: RETAIN BOTH WITH REFINED LABELS (restore original_activity)
                     `Dispatch Package`  `Released from Warehouse` (e08), `Accepted by Carrier` (e09)
               Merge is FORBIDDEN; would erase logistics handover boundary

        NO 
Step 5: Same activity + same timestamp but DIFFERENT BUSINESS OBJECTS (distinguishing qualifier)?
        Test: e03/e05 both `Pick Item` @10:00 but I1 vs I2; e13/e14 both `Capture Payment` but M1 vs M2
        YES  CONCURRENT DISTINCT EVENTS
               Decision: RETAIN BOTH UNCHANGED (or with object-qualified display label only)
               Do NOT merge even with have_common_object=True (shared O1/V1 is not discriminative)
               Ordering: keep concurrent in partial order; only total-order tie-breaker for determinism

        NO 
Step 6: Same activity + timestamp + overlapping objects but NO verification and semantics unclear
        (e13/e15, e14/e15; e08/e09 without label fix would fall here)
         UNRESOLVED CANDIDATE
         Decision: QUARANTINE FOR REVIEW (flag candidate_group, do not drop/merge in conservative pipeline)
         Requires business rule or object-type authoritative check (Payment object present vs absent)
```

Principles: `have_common_object` is a necessary but insufficient filter. `ingested_at` and `source_seq` are never semantic proof alone. Every terminal action must write provenance.

## 3. Timestamp-tie ordering rules

**Semantic vs deterministic:** Semantic rules encode business causality that must be true in any world; deterministic rules only ensure reproducible total order for algorithms that require one, without claiming truth.

1.  **Domain / lifecycle constraints (SEMANTIC, highest priority)**
    *   `Pick Item`  `Pack Package` (cannot pack before picking). Applies to e03/e05 < e06.
    *   `Released from Warehouse (e08)`  `Accepted by Carrier (e09)` < `Handover to Carrier (e10)`.
    *   `Authorize Payment (e12)` < `Capture Payment (e13)` for same M1. M2 (e14) independent but `Issue Invoice (e11/e16)` < {Authorize, Capture} < `Payment Summary (e15)`.
    *   `Pack Detailed (e06)`  `Pack Status (e07)` if both retained (causal message).

2.  **Within-source sequence (SEMANTIC when source is authoritative for that object)**
    *   `source_seq` monotonic within a source system. WMS: e03(100) < e06(110) < e08(120). CARRIER: e09(1) < e10(2). PSP: e12(400) < e13(401) < e14(402) but e14 is different object so sequence does not imply dependence. ERP: e01(10) < e02(20) < e07(30) < e11(40) < e15(41).

3.  **Object-type lifecycle constraints (SEMANTIC)**
    *   Item I1/I2: `Pick  Pack`. Package P1: `Pick  Pack  Release  Accept  Handover  Confirm`. Invoice V1: `Issue  Payment events`. Use per-object partial order to prune impossible interleavings.

4.  **Source-specific semantics (SEMANTIC, after verified overlaps)**
    *   WMS enriched event canonical over scanner raw; carrier `seq` order is ground truth for carrier steps.

5.  **Ingestion time (NON-SEMANTIC, weak tie-breaker only)**
    *   Used only after all semantic constraints exhausted, and never as primary. Fact 9 explicitly says ingestion order not guaranteed.

6.  **Stable fallback (DETERMINISTIC, NOT SEMANTIC)**
    *   `canonical eid` lexical order or `source` alphabetical. Ensures reproducibility across runs.

**Why adding `pm4py.ocel_add_index_based_timedelta` BEFORE deciding semantic order encodes a false story:** The function adds `i * epsilon` microseconds according to the *current* row order. If that order is still arbitrary (e.g., ingestion order or CSV order), you freeze an arbitrary interleaving as if it had microsecond precision. Downstream DFGs, performance metrics, and variant analysis will then treat that arbitrary order as observed business precedence, hiding concurrency (e.g., e03 vs e05 will appear sequential with 1µs gap) and making causal inference circular: you measure the order you just invented. Correct pipeline: first establish semantic partial order  sort deterministically by semantic keys  *then* add epsilon only to make total order explicit for tools, while preserving `original_timestamp` untouched and documenting that epsilon is synthetic.

**Intended orders (after duplicate decisions):**

*   **e03–e07 @10:00:00**
    *   Partial order: {e03/e04 merged} and e05 concurrent picks  both < e06 (detailed pack) < e07 (ERP status).
    *   Conservative retained (16 events): tie-breaker: WMS/SCANNER picks first in deterministic order `e03_04 (Pick I1)` < `e05 (Pick I2)` < `e06 (Pack Detailed)` < `e07 (Pack Status)`. Alternative admissible total order swaps e03_04 and e05 (they are concurrent; both precede packing). Must NOT interleave e06 between picks unless evidence.
    *   Aggressive merged e06_07: `e03_04` < `e05` < `e06_07`.

*   **e08–e10 @10:15:00**
    *   Strict admissible order: `e08 (Released_WMS)` < `e09 (Accepted_CARRIER)` < `e10 (Handover_CARRIER)` in *all* scenarios. If harmonization not fixed, naive sort would leave e08/e09 as identical `Dispatch Package` and arbitrary order; after refinement order is semantic. No concurrency here despite timestamp equality.

*   **e11–e16 @12:00:00 after decisions**
    *   Conservative (retain both invoice events): partial order ` {e11, e16} (Invoice, concurrent observations) ` < `e12 (Authorize M1)` < ` {e13 (Capture M1), e14 (Capture M2) concurrent} ` < `e15 (Payment Summary ERP)`. Deterministic total order for tools: `e11` < `e16` < `e12` < `e13` < `e14` < `e15` (stable to source_seq / eid). If e11/e16 merged: `e11_16` < `e12` < `e13` < `e14` < `e15`. e13 and e14 must remain concurrent—no ordering between them; any total order is synthetic.

Determinism disclaimer: The chosen total order is *one linearization* of a partial order. It does not prove physical order within ties.

## 4. Conservative cleaning pipeline

**Goal:** Minimum-change, maximum semantic preservation. Expected retained count: **16 events** (17 raw 1 merged e03/e04). If e11/e16 merged under conservative-with-verified merge, **15 events**; we label ultra-conservative (16) as default and conservative-merged-invoice (15) as variant.

Steps:

1.  **Preserve originals:** Copy `timestamp  original_timestamp`, `activity  original_activity` + `harmonized_activity`, keep `source`, `source_event_key`, `payload_hash`, add `refined_activity` initially = `original_activity`.

2.  **Refine harmonized labels (no deletion):** Restore source semantics: `e09: Dispatch Package  Accepted by Carrier`; keep `e08: Released from Warehouse`; `e10` retains `Handover to Carrier`. This prevents Step 4 collisions without dropping.

3.  **Verified merge only:** Merge e03+e04 via custom verified-pair routine (attribute union, relation union, provenance array). No other automated duplicate removal.

4.  **Quarantine, not merge, ambiguous pairs:** Flag candidate groups `G_pack={e06,e07}`, `G_invoice={e11,e16}`, `G_pay_summary={e13,e14,e15}` with `candidate_duplicate_group` and `confidence`. Retain both e06/e07, both e11/e16 (or merge e11/e16 only with explicit log if policy chooses), retain e13,e14,e15 all separate.

5.  **Deterministic ordering without deleting concurrency:** Define semantic sort keys: `timestamp`  `semantic_rank` (derived from domain + source_seq partial order)  `source_seq`  `eid`. Use `pm4py.ocel_sort_by_additional_column(semantic_rank)` to sort, then `pm4py.ocel_add_index_based_timedelta( epsilon=1ms, preserve_original=True)` only after sort, storing `adjusted_timestamp` while `original_timestamp` unchanged. Document epsilon is synthetic.

6.  **Validate:** Referential integrity check: all `object_id` still present, no orphan E2O, object lifecycles not broken (e.g., Item I1 still has Pick).

**Result:** Event count 16, E2O edges: raw had e.g., 3 pick edges + etc.; after merge e03/e04 union unchanged count, no relation loss. DFGs remain truthful: Item-flattened shows two parallel Picks, Order-flattened shows pickpack (with pack status as separate step), Payment-flattened shows two captures.

## 5. Aggressive alternatives

**A. Evidence-based semantic merging (Scenario B, "informed aggressive")**
*   Logic: Merge only where business key or causal evidence justifies single business transition, but still manually vetted.
*   Actions: Merge e03/e04 (verified), merge e11/e16 (same invoice V1, merge attributes), optionally merge e06/e07 (Pack detailed+status as one business transition) with provenance and discarded fields, keep e08/e09 separate, keep e13/e14 separate, keep e15 separate but relabel as summary.
*   Expected count: **14 events** if e06/e07 merged (17111) or **15** if e06/e07 kept. E2O: e06_07 union creates 1 fewer relation duplication but adds Items to ERP summary implicitly. E2O count drops by 1–2.
*   Most likely semantic damage: **Converting abstraction-level updates into false rework or false single event.** Merging e06/e07 hides that ERP never saw Items, and unioning E2O relations {O1,P1}  {O1,I1,I2,P1} claims ERP event related to I1,I2. If merged, downstream object-centric analyses will think package packing involved Items in ERP context, biasing OTG weights toward Item. Keeping them separate but merging invoices loses traceability of which system is authoritative for which invoice attribute unless conflicts logged.

**B. Mechanically aggressive PM4Py merging (Scenario C, "library-default aggressive" – NOT RECOMMENDED)**
*   Logic: `pm4py.ocel_drop_duplicates` / `ocel_merge_duplicates` on whole OCEL grouped by `(activity, timestamp, have_common_object=True)` without inspecting candidate groups.
*   Actions with default `have_common_object=True, keep_common_only=False`:
    *   e03,e04,e05 all share `Pick Item`+`10:00`+common O1,P1  collapsed to 1 event (drops e05 – violates constraint).
    *   e06,e07 share `Pack Package`+`10:00`+O1,P1  collapsed.
    *   e08,e09 share `Dispatch Package`+`10:15`+O1,P1,D1  collapsed (destroys Released vs Accepted).
    *   e11,e16,e12,e13,e14,e15 all share `12:00` but different activities except e11/e16 and e13/e14/e15 subgroups  e11+e16 collapsed, e13+e14+e15 collapsed (destroys M1/M2 distinction).
*   Expected count: **~9–11 events** depending on `keep_common_only`. E2O heavily reduced (union collapses).
*   Semantic damage: **Catastrophic.** 1) Collapsing e13/e14 despite shared O1/V1 demonstrates `have_common_object=True` is insufficient: shared Order/Invoice does not imply same Payment; discriminator object is Payment (M1 vs M2). 2) Dropping e05 loses Item I2 lifecycle, making Item-flattened DFG show only one Pick. 3) False loops disappear or appear arbitrarily, performance durations become zero or inflated, OTG relations incorrectly weighted.

**Why `have_common_object=True` fails for e13/e14:** `have_common_object` checks if candidate duplicates share *any* object. e13 (M1) and e14 (M2) both relate to O1 and V1, so `True`, but they differ on the discriminating object type Payment. Without `object_type` filter `have_common_object` + activity+timestamp over-merges. Correct protection requires checking distinguishing object type (Payment) or business key (M1 vs M2), not mere overlap.

def add_provenance_columns(ocel):
    ev = ocel.events.copy()

    ev["original_activity"] = ev["activity"]
    ev["harmonized_activity"] = ev["activity"]
    ev["refined_activity"] = ev["activity"]

            # keep canonical value, log discard
            pass
        # union provenance

        merged["sources"] = list(set(rk["sources"] + rd["sources"]))
        merged["merge_rule"] = rule_name
        merged["confidence"] = "High"
        # example: enrich location from WMS if present in drop
        # (actual implementation would inspect ocel.events extra attribute columns)
        # union E2O: re-point drop's relations to keep
        relations.loc[relations["event_id"]==drop, "event_id"] = keep
        relations = relations.drop_duplicates()
        # log audit

Stored as: `ocel.events` extended columns + separate `audit_log` DataFrame (or `ocel.audit` table) with one row per merge. Original columns `original_timestamp`, `original_activity`, `harmonized_activity`, `refined_activity`, `source_event_keys`, `sources` remain queryable.

**Reconstruction of raw view:**

1.  `audit_log` lists `source_event_ids` for each canonical. Explode `canonical_eid  source_event_ids` to restore 17 rows.
2.  For each restored row, replace `refined_activity` with `original_activity`, `adjusted_timestamp` with `original_timestamp`, and split unioned attributes using `attributes_retained` / `discarded_conflicts`.
3.  E2O: use `objects_before` to split unioned relations back to per-source event relations.
4.  Filter `WHERE merge_rule IS NOT NULL` and re-create dropped eids as separate events with their original `source`, `source_event_key`, `payload_hash`.
5.  Drop `semantic_rank` / `adjusted_timestamp` epsilon and sort by `original_timestamp, eid` to recover raw order.

Because `ocel_raw` is never overwritten (deep copies), raw remains available, and audit trail is append-only and versioned. Analyst can toggle `view = raw | conservative | evidence` by joining audit log.

## 9. Failure modes and safeguards

1.  **Collapsing distinct partial payments (e13 M1 vs e14 M2).** Failure: `have_common_object=True` merges events sharing O1/V1 despite different Payment objects, losing M2 lifecycle. Safeguard: require discriminating object-type check (`Payment` equality) or business key (`M1 vs M2`) before merging same-activity ties; quarantine e13/e14 group for manual review, never drop e14.

2.  **Converting abstraction-level updates into false rework or false single transition.** Failure: treating e06 (detailed WMS) + e07 (ERP status) as rework loop or merging them without logging unioned Items. Safeguard: conservative retains both with `refined_activity` qualifiers; if merged, log `union_E2O` and note ERP never saw Items; track performance using `original_activity` for business-level vs system-level DFG.

3.  **Ordering by ingestion time as primary business order.** Failure: using `ingested_at` (10:00:01 vs 10:00:03) to sequence picks destroys concurrency and encodes technical ingestion lag as business precedence. Safeguard: ingestion time is last non-semantic tie-breaker only after domain, source_seq, and lifecycle constraints; document as deterministic, not semantic.

4.  **Treating shared objects as proof of duplication.** Failure: “e08 and e09 share O1,P1,D1 so must be duplicate” – ignores harmonization collision and Payment example. Safeguard: decision tree Step 4 requires `original_activity` / source semantics check; `have_common_object` alone never triggers merge; require activity semantics + verification.

5.  **Unioning incompatible E2O relations.** Failure: merging e06+e07 unions `{O1,P1}` with `{O1,I1,I2,P1}` and claims ERP event related to Items; merging e15 with e13 attaches M1 to summary. Safeguard: relation merge policy explicit (`union` vs `keep_separate`); for abstraction merges, store `objects_before` and flag unioned objects as `inferred` not `observed`; validate object-type constraints after merge.

6.  **Changing durations through synthetic microseconds.** Failure: adding `index_based_timedelta` before semantic ordering freezes arbitrary order and makes `PickPack` or `ReleasedAccepted` appear to have 1 ms duration, biasing performance analysis. Safeguard: add epsilon *only after* semantic sorting, preserve `original_timestamp` for all performance calculations, store synthetic delta in `adjusted_timestamp` and disclose epsilon in report (e.g., “durations computed on original_timestamp, epsilon=1 ms for determinism only”).

7.  **Losing source-authoritative attributes.** Failure: merging e03/e04 and keeping only WMS location, or merging e11/e16 and keeping only ERP fields, loses scanner raw evidence or billing detail. Safeguard: attribute merge with source-authoritative priority map and full `attributes_retained` + `discarded_conflicts` log; never overwrite, union fields under `provenance.attributes`.

8.  **Applying duplicate functions to the whole OCEL without inspecting candidate groups.** Failure: `pm4py.ocel_drop_duplicates(have_common_object=True)` on entire log merges unrelated groups (e03/e04/e05, e13/e14/e15) without review. Safeguard: mandatory pre-check `precheck_candidates()` grouping by `(activity,timestamp)` and inspecting object sets; apply drop/merge only to verified groups via `verified_pair_merge`; aggressive call isolated to deep copy demo with warning comment.

9.  **Erasing original timestamp / activity.** Failure: overwriting `timestamp` with epsilon-adjusted value loses UTC secondprecision business time and harmonization history. Safeguard: never mutate `original_timestamp`/`original_activity`; write refinements to `refined_activity`/`adjusted_timestamp`.

10. **Claiming deterministic total order proves true physical order.** Failure: reporting “e03 happened before e05” as fact when they are concurrent picks at same second. Safeguard: explicitly state total order is one admissible linearization of a partial order; keep concurrency flag (`concurrent_group`) and warn in documentation/visualizations (dashed edges for synthetic order, solid for semantic order).
