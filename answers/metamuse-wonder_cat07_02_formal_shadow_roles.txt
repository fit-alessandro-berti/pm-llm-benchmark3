# 5. PM4Py role-discovery and similarity code

Illustrative but coherent; the key design choices are (i) run discovery, (ii) *join back* complexity/substitution context, and (iii) validate with social-network directionality before naming roles.

```python
import pandas as pd
import pm4py

# --- Load and format -------------------------------------------------------
df = pd.read_csv("order_to_resolution.csv", parse_dates=["time:timestamp"])
df = df.rename(columns={
    "case_id": "case:concept:name",
    "activity": "concept:name",
    "resource": "org:resource",
})
log = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp",
    resource_key="org:resource",
)

# --- Built-in role discovery (activity-profile clustering) -----------------
# Returns roles as (originator_importance-like dict, [activities]) per cluster.
roles = pm4py.discover_organizational_roles(log)
for i, role in enumerate(roles):
    print(f"Cluster {i}: activities/resources -> {role}")

# Activity-based resource similarity: cosine-style similarity over
# activity participation profiles. High similarity != equal authority.
similarity = pm4py.discover_activity_based_resource_similarity(log)
sim_df = pd.DataFrame(similarity)  # inspect pairs, e.g. Chen-Dina ~0.94, Erik-Mateo low

# --- Social networks: direction and co-work --------------------------------
handover = pm4py.discover_handover_of_work_network(log)        # who passes work to whom
together = pm4py.discover_working_together_network(log)        # who co-occurs in cases
subcontract = pm4py.discover_subcontracting_network(log)       # repeated intermediate handovers

# Broker check: Mateo should show high betweenness-style in/out diversity in
# handover (many distinct predecessors AND successors on high-escalation cases),
# whereas Erik should show narrow in/out ties concentrated on A6 neighbours.

# --- Join discovery output with complexity & substitution context ----------
prof = (
    log.groupby("org:resource")
       .agg(events=("concept:name", "size"),
            median_complexity=("case_complexity", "median"),
            frac_high_critical=("case_complexity", lambda s: (s >= 0.7).mean()),
            subst_events=("temporary_substitution", "sum"),
            subst_share=("temporary_substitution", "mean"))
       .reset_index()
)

# Activity share OF THE ORGANISATION (not just within-resource share):
act_share = (
    log.groupby(["concept:name", "org:resource"]).size().reset_index(name="n")
)
act_share["share_of_activity"] = act_share.groupby("concept:name")["n"].transform(
    lambda s: s / s.sum()
)
# Erik: low total events but share_of_activity(A6) ~0.66 -> core specialist.
# Mateo: no high share anywhere, but present in all activities -> broker flag.
coverage = act_share.groupby("org:resource")["concept:name"].nunique().rename("n_activities")

# Substitution-conditional profile: does Giorgio's A7 persist outside
# temporary_substitution == True windows?
giorgio_pricing = pm4py.filter_event_attribute_values(
    log, "org:resource", ["R07_Giorgio"], level="event", retain=True)
giorgio_by_subst = giorgio_pricing.groupby(
    ["temporary_substitution", "concept:name"]).size().unstack(fill_value=0)

# Complexity-conditional similarity: re-compute profiles per complexity band
# so Chen vs Dina (0.94 overall) can diverge on high/critical cases.
for band, sub in log.groupby(pd.cut(log["case_complexity"],
                                    [-1, .33, .66, 1.0],
                                    labels=["low", "medium", "high_critical"])):
    print(band, pm4py.discover_activity_based_resource_similarity(sub))

# Outcome check for temp closures: variants / reopens following temp A12
variants = pm4py.get_variants(log)
reopen_after_temp = (
    log.sort_values("time:timestamp")
       .groupby("case:concept:name")
       .apply(lambda c: ("R11_Kai" in set(c["org:resource"]) or
                         "R12_Lina" in set(c["org:resource"])) and
                        ("Reopen Request" in set(c["concept:name"])))
)

# --- Interpretation guardrails (in code review / notebook text) ------------
# 1. Name a cluster only after checking: share_of_activity, median_complexity,
#    subst_share, certification/authority attributes, and handover direction.
# 2. Never promote a substitution-window profile (Giorgio A7, Mateo A9)
#    to a permanent role without out-of-window persistence.
# 3. Treat singleton/low-similarity resources (Erik, Mateo) as candidate
#    critical roles, not outliers to be discarded.
# 4. Validate mined roles against formal data (contract, home team,
#    certifications) and case outcomes (reopen, service time via
#    pm4py.get_service_time / insert_case_service_waiting_time).
```

# 6. Operational interpretation

**Staffing.** Staff to the *revealed* structure, not the org chart alone: protect single-person critical roles (Erik in Security, Fatima in Commercial, Hana in Approval) with explicit deputies, because the log shows cover currently depends on informal arrangements (Giorgio, Mateo) that are slower or non-accountable. **Training.** Use the complexity gradients as training pathways: DinaChen pattern defines a technical progression (supervised exposure to high/critical and security-adjacent cases); Amira is the natural mentor/checker for temp validation notes, targeting the incomplete-A2 failure mode; formalise Giorgio's pricing cover with refresher training and supervised exception quotas so substitution duration (74 vs 38 min) improves *before* the next absence, not during it.

**Risk control.** Make shadow authority explicit and bounded: define which A7/A8/A9 acts Giorgio and Mateo may perform, at what value/escalation limits, and require Hana recheck sampling rather than ad-hoc rechecking (13/21 suggests uncertainty about the boundary). Monitor Mateo's security filtering with a critical-case waiting-time alert — the two >2-day waits are the cost side of a filter whose benefit (fewer false escalations) is real. Track reopen-after-close by closing resource as a standing quality KPI, segmented by `case_complexity` and `temporary_substitution`.

**Resilience.** Cross-train a second security reviewer at least for triage-level A6; document Ivan/Julia's KB criteria so gatekeeping survives absence; treat Nora's routing rules as part of the role structure — audit her medium-complexity passes and disagreement with human validation by `product_line`/`customer_segment`, especially given the Enterprise Security load episode.

**Caution 1 — mined roles describe behaviour, not competence or authority.** Reassigning work purely because profiles cluster (e.g., giving Dina Chen's critical caseload because similarity is 0.94, or treating Mateo's approvals as equivalent to Hana's) confuses activity shape with certified capability and accountable authority. Giorgio's doubled pricing time during substitution is the empirical warning: observed performance under cover conditions is not proof of permanent competence.

**Caution 2 — optimising on frequency will destroy the rare and the connective roles.** Erik and Mateo look inefficient or anomalous in count-based views; removing, diluting, or "balancing" their load by similarity metrics would eliminate the highest-risk specialist and the escalation broker simultaneously. Any staffing change should be tested against critical-case outcomes (waiting time, reopen, escalation correctness), not just utilisation and cluster purity — and shadow roles should be recognised and governed, not eliminated, since the process demonstrably already depends on them.
