## 1. Target definition

### Primary target: default risk conditional on eventual activation under the observed lending process

**Unit of analysis:** one credit application/case.

**Prediction time:** an operationally defined early prefix time, primarily:

- immediately after the first occurrence of `Credit Review`, or
- after a fixed prefix such as the first 3, 5, or 7 events,

provided that the case has not yet reached `Accepted`, `Rejected`, `Withdrawn`, `Transferred`, `Contract Signed`, or `Account Activated`.

The study should report results separately by prefix definition because “first few events” is ambiguous and event-count prefixes can represent very different elapsed durations.

**Horizon:** default within 90 days after `Account Activated`.

**Population:** applications that are still in the underwriting process at the prediction time and that would eventually be activated under the observed historical policy. This is not all started applications.

**Outcome:**

\[
Y = 1\{\text{default occurs within 90 days after activation}\}
\]

for cases with observed activation and mature, observed 90-day outcome information.

**Estimand:** the conditional risk

\[
P(Y=1 \mid X_t,\ A=1,\ \text{outcome observed and mature})
\]

where:

- \(X_t\) is information available at prefix time \(t\);
- \(A=1\) means the application was eventually activated under the historical policy.

The model should be explicitly described as an **activated-account default model**, used before final decision but interpreted only as risk among cases that would be activated under the observed decision process. It estimates an association conditional on selection into activation; it is not automatically the default probability for every applicant.

This formulation is operationally defensible if the lender’s near-term use case is, for example:

- prioritizing additional review among applications likely to be accepted;
- setting monitoring intensity for accepted applicants;
- informing a decision-support workflow while retaining policy and human review.

It is statistically more honest than assigning rejected, withdrawn, transferred, or open applications a zero default label.

### Credible alternative: multi-state application outcome model

A second formulation would model the next process outcome for every application, for example:

\[
\{\text{Activated}, \text{Rejected}, \text{Withdrawn}, \text{Transferred}, \text{Still open at horizon}\}
\]

possibly followed by a second-stage activated-account default model. This is a multi-state or competing-risks view:

1. application/process state transition model;
2. default-after-activation model conditional on activation.

It answers a different business question: “What is likely to happen to this application under the current process?” rather than “What is the default risk if it becomes an activated account?”

A third, more ambitious alternative is a **policy-specific counterfactual default target**:

\[
P(Y^{\pi}=1 \mid X_t)
\]

where \(Y^{\pi}\) is default under an explicit activation policy \(\pi\). This would require stronger assumptions about unobserved potential outcomes among rejected or withdrawn applicants, overlap/positivity, measured confounding, and policy stability. The available export alone cannot identify this target reliably.

## 2. Cohort construction

### As-of principle

All cohort membership, feature availability, labels, and censoring must be determined relative to a configurable analysis cutoff \(C\), initially:

\[
C = \text{15 February 2026}
\]

No event, feature value, label, linkage, or outcome feed record created after the applicable prediction time or after \(C\) may be used.

For the primary activated-account target, a case is label-eligible only if:

1. it has an `Account Activated` event by cutoff;
2. activation occurred at least 90 days before cutoff;
3. the delayed external feed window has also passed;
4. the outcome feed is available and not permanently missing.

Because the external feed arrives 7–35 days after the 90-day horizon, a conservative maturity rule is:

\[
\text{activation time} + 90\text{ days} + 35\text{ days} \le C
\]

Thus, under the initial extraction date, a conservatively mature activated case must have activated by approximately **13 October 2025**.

If `label_available_at` is reliable, the preferred record-level rule is:

\[
\text{label\_available\_at} \le C
\]

in addition to requiring the 90-day outcome horizon to have elapsed.

### Inclusion criteria for the primary modeling cohort

Include a case if all are true:

1. Case started during the study event observation period, 1 January 2024 through 31 December 2025.
2. The designated prediction prefix exists before a final decision or activation.
3. The case eventually activated under the observed process.
4. It has a mature and observed 90-day default label under the as-of cutoff.
5. All prefix events and feature values used occurred on or before the prefix timestamp.
6. The case belongs to a source/channel for which the outcome interpretation is compatible with the target. Partner-originated cases with structurally missing outcome feeds should be retained only with an explicit missing-outcome strategy, not silently discarded.

### Exclusion criteria

Exclude from the primary supervised training outcome set, while retaining for process and selection analyses:

- rejected applications;
- withdrawn applications;
- transferred applications without a verified reappearance linkage and mature downstream outcome;
- still-open applications;
- activated applications not yet outcome-mature;
- activated applications with delayed but not yet received labels;
- activated accounts with permanently missing outcome feeds unless modeled under an explicit missing-data strategy;
- cases whose prediction prefix occurs after decision, signing, activation, collections, or default.

## 3. Censoring and missing-label strategy

### Distinct mechanisms

| Mechanism | Meaning here | Appropriate treatment |
|---|---|---|
| Ordinary right censoring | Activated case has not yet completed 90 days of post-activation follow-up by extraction | Exclude from fixed 90-day binary-label training at the cutoff; include in future survival analysis |
| Delayed labels | 90-day horizon elapsed but external feed has not arrived yet | Treat as unknown until `label_available_at`; do not infer non-default |
| Selection through activation | Only activated cases have a well-defined observed `default_90d` under current warehouse semantics | Explicitly define target conditional on activation; analyze activation selection separately |
| Transfer | Case may continue under another system/identifier or may be intentionally handed off | Competing process event; use linkage where available, otherwise treat as informative missing follow-up |
| Permanently missing feeds | Activated account has no recoverable default outcome, disproportionately partner-originated | Missing outcome, potentially MNAR; not ordinary censoring by default |

### Primary analysis strategy

The primary analysis is a **complete-case, mature-label activated-account model with transparent selection scope**, combined with descriptive diagnostics for outcome observability.

1. Restrict supervised outcome training to activated cases with:
   - mature follow-up;
   - `label_available_at <= cutoff`;
   - observed `default_90d`;
   - valid prefix before decision/activation.

2. Fit and evaluate:
   - a default risk model conditional on observed activation;
   - a separate activation/selection model or descriptive selection analysis over all applications.

3. Report outcome-observation rates by:
   - channel;
   - source system;
   - region;
   - policy period;
   - transfer status;
   - partner-originated indicator;
   - risk-score bands;
   - time to activation.

4. Do not claim that the resulting probability applies to rejected, withdrawn, transferred, or never-activated cases.

This is defensible for the primary conditional estimand but relies on an additional missingness assumption for the observed labeled activated subset:

\[
P(Y \mid X, A=1, R=1) \approx P(Y \mid X, A=1)
\]

where \(R=1\) denotes an observed mature outcome. This is a missing-at-random-like assumption conditional on recorded variables, and is especially doubtful for partner-originated accounts.

### Sensitivity analyses

#### A. Inverse probability of observation weighting

Estimate the probability that an activated case has a mature observed outcome:

\[
\hat p(R=1 \mid X_t,\ \text{channel},\ \text{source},\ \text{activation date},\ldots)
\]

Then weight complete labeled cases by:

\[
w_i = \frac{1}{\hat p(R_i=1 \mid Z_i)}
\]

Potential predictors include source system, partner status, channel, activation month, region, risk-score band, policy period, and elapsed time to activation.

This addresses observed differences in outcome availability, but cannot repair missingness driven by unobserved default status after conditioning on available predictors.

#### B. Best-case/worst-case or tipping-point bounds

For permanently missing outcomes, report bounded performance and prevalence under assumptions such as:

- all missing outcomes are non-default;
- all missing outcomes are default;
- missing-outcome default rate is 1.25x, 1.5x, or 2x the observed rate within channel/source strata.

This does not identify the truth but demonstrates how strongly conclusions depend on missing outcome assumptions.

#### C. Transfer linkage sensitivity analysis

For the approximately 60% of transferred cases with linkage:

- estimate downstream activation and observed default rates after transfer;
- compare linked versus unlinked transfers;
- model probability of linkage using observed pre-transfer attributes;
- report whether linked transfers appear systematically different.

For unlinked transfers, treat downstream default status as unresolved rather than zero.

#### D. Survival / competing-risk extension

A later analysis can use time from activation to default with right censoring, allowing cases activated near cutoff to contribute partial follow-up. This requires a valid event-time default feed and careful handling of delayed reporting. It does not solve the activation-selection problem, but it reduces loss of partially observed activated accounts.

### What is testable?

**Testable or partially testable:**

- whether label availability differs by channel, source system, partner status, policy period, region, and observed risk factors;
- whether migration-era duplicate events change prefix distributions;
- whether linked and unlinked transferred cases differ on observed covariates;
- whether performance and calibration drift across policy periods;
- whether missing outcome feeds are disproportionately associated with partner origin.

**Fundamentally untestable from these data alone:**

- the default probability rejected applicants would have had if activated;
- whether missing outcome feeds depend on unobserved default after conditioning on recorded covariates;
- whether transferred-but-unlinked cases defaulted downstream;
- the causal effect of changing acceptance policy on default without stronger causal design and data.

## 4. Prefix extraction

### Prediction-time discipline

For every case-prefix observation, define a prediction timestamp \(t\). Only events satisfying:

\[
\text{event timestamp} \le t
\]

and data values known by \(t\) may contribute features.

The model must not ingest later events merely because they appear in the case trace. In particular, `Contract Signed`, `Account Activated`, `Collections Contact`, and `Default Recorded` are post-prediction activities for early-warning use.

### Fixed event-count prefixes

For each eligible case, construct prefixes of length \(k\), for example:

- \(k=3\),
- \(k=5\),
- \(k=7\).

The prefix endpoint is the timestamp of the \(k\)-th eligible event. A case contributes only if it has at least \(k\) events before terminal/decision leakage begins.

Recommendations:

- Define an allowed pre-decision activity vocabulary.
- Stop prefix construction before any final decision, signing, activation, collections, or default event.
- Preserve repeated document request / document received / credit review loops as meaningful rework, not as duplicates.
- Deduplicate only demonstrably duplicated migration artifacts, for example same case, normalized activity, timestamp, resource, and source-system identifier within a defined narrow time tolerance.

Short cases should not be padded with future events. They can either:

1. be excluded for that fixed-\(k\) model;
2. be modeled with a separate “up to \(k\)” prefix approach that includes prefix length as a feature;
3. use elapsed-time prefixes instead.

The first option is simplest but changes the target population; this must be reported.

### Elapsed-time prefixes

Construct prefixes at operational times such as:

- 1 hour after application start;
- 1 day after application start;
- 3 days after application start;
- immediately after first `Credit Review`.

For a time-based prefix at \(t = \text{start}+\Delta\):

- include only events timestamped at or before \(t\);
- require the case to still be under consideration at \(t\), if the intended deployment population excludes already-resolved cases;
- exclude cases not observed long enough only if their absence is due to the extraction cutoff; otherwise distinguish process completion from lack of observation.

Elapsed-time prefixes better reflect a realistic decision cadence and make cross-case comparisons more interpretable than event count alone.

### Activity renaming and migration

The 15 October 2025 migration requires a version-controlled activity normalization map, for example:

- `KYC_CHECK_V2`  `Identity/KYC Check`
- `DOC_REQ_NEW`  `Request Documents`
- `CREDIT_REVIEW_NEW`  `Credit Review`

Keep both:

- `activity_raw`;
- `activity_normalized`.

Use normalized labels for process discovery and model features, while retaining raw labels and migration-period indicators for audit and drift analysis.

Do not silently collapse activities when their semantics changed rather than merely their names.

## 5. Process-aware features

All features must be computed as of the prefix endpoint.

### Static case attributes

Available if recorded at or before application start or prefix time:

- `case:channel`;
- `case:region`;
- initial requested amount;
- source system;
- application start calendar date;
- policy-era indicator: pre/post 1 July 2025;
- migration-era indicator: pre/post 15 October 2025;
- day of week, month, holiday/business-day indicators;
- initial risk score, if its timestamp confirms availability by prefix time.

Do not use a value merely because it appears on an early event row; verify that its business timestamp or event timestamp precedes the prefix endpoint.

### Prefix-derived control-flow features

- number of observed events;
- number of distinct normalized activities;
- current/latest activity;
- previous activity;
- directly-follows transition counts;
- whether `Credit Review` has occurred;
- number of `Credit Review` occurrences;
- number of document-request loops;
- number of rework cycles:
  \[
  \text{Credit Review} \rightarrow \text{Request Documents} \rightarrow \text{Credit Review}
  \]
- whether KYC was completed;
- number and sequence position of document-related activities;
- trace variant or top-variant membership, with rare variants grouped as “other”;
- prefix conformance/deviation features relative to a training-period process model, used cautiously because process drift may make them unstable;
- terminal-state indicators only if terminal status is known before the actual prediction time and is part of the deployment population. For early warning before decision, such cases generally should not be scored.

### Timing features

- elapsed time from application start to prefix;
- time from KYC to first credit review;
- time since last event;
- waiting time in credit review;
- time spent in document loop;
- number of events per elapsed hour/day;
- business-hours versus out-of-hours submission;
- queue-delay proxies;
- same-day versus multi-day rework.

These require proper timestamp ordering and treatment of duplicate migration events.

### Risk-score trajectory features

If score updates are timestamped and available at the prefix:

- latest observed score before prefix;
- initial score;
- score change since start;
- number of score updates;
- score volatility or maximum change;
- missing-score indicator.

Never use the final score if it was updated after decision or after prefix.

### Resource and queue features

Potentially useful but fairness- and leakage-sensitive:

- current resource/team identifier;
- resource workload at prediction time;
- count of cases assigned to resource/team in prior 7/30 days;
- historical team-level turnaround time estimated only from earlier cases;
- queue length proxy based on cases open at time \(t\);
- resource tenure/experience as-of event time, reconstructed from history.

Resource features require historical reference data and must be computed using only records preceding the case’s prefix time. They can encode staffing and operational inequity; evaluate carefully by region/channel and avoid using them for adverse automated decisions without governance review.

### Features requiring historical reference data

- resource experience at event time;
- workload and queue length;
- historical approval/default rates by channel/region/resource;
- process conformance against a DFG or model discovered on prior training data;
- rare-variant frequency;
- calibration priors by policy period.

These must be generated with rolling, training-only reference windows to avoid target leakage.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---|---|---|---|
| `final_limit` | Populated only after final credit decision; directly reflects later underwriting outcome | Must be known before prefix endpoint, which is generally impossible for early-review prefixes | Drop for early-warning model | It is post-decision information and would artificially improve performance |
| `decision_reason` | Populated at or after Accept/Reject; encodes the decision and often underlying risk judgment | Include only for models explicitly scored after decision; not for pre-decision early warning | Drop | A pre-decision model cannot use a field created by the decision it is intended to inform |
| `collection_status` | Updated after activation and may directly reveal delinquency/default | Must predate prefix; for early application prefixes this never holds | Drop | Direct post-activation target leakage |
| Future events | Later events include Contract Signed, Account Activated, Collections Contact, Default Recorded | Include only events with timestamp \(\le\) prefix timestamp and in allowed pre-decision vocabulary | Repair by prefix filtering | Full traces must never be converted to features before truncation |
| `documents_total` nightly snapshot | May include documents uploaded later the same calendar day than nominal prediction timestamp | Use only snapshots whose materialization timestamp is \(\le\) prefix time; otherwise reconstruct from event-level document actions | Repair or drop | Date-level snapshots violate intraday as-of ordering |
| Updated `risk_score` | Multiple updates may occur after review, decision, or other later information | Select last score with event/update timestamp \(\le\) prefix time; retain update count and missingness | Keep after as-of repair | Score trajectory may be valid if timestamped correctly |
| Resource experience | Stored as experience at extraction, causing future-information leakage | Reconstruct tenure/experience from historical assignment records available before each event/prefix | Repair; otherwise drop | Extraction-time experience overstates what was known at prediction time |
| `default_90d` | Outcome field repeated on events when known; may appear only after outcome maturity | Use only as label, never as a predictor; require `label_available_at <= cutoff` | Keep as label only | Label must not enter event features or preprocessing |
| `label_available_at` | Can leak future knowledge if used as feature; needed for label maturity | Use for cohort/label eligibility only, not prediction feature generation | Keep for cohort rules only | Identifies whether outcome was observable as of analysis cutoff |
| Account Activated event | Defines target time origin and selection into observed outcome | Never include in pre-activation feature prefixes | Use for cohort/target only | Including it would make the pre-decision target circular |
| Contract Signed event | Often immediately precedes activation and reveals acceptance pathway | Exclude from early warning prefixes unless the deployment time is after signing | Drop for primary setting | Post-decision/policy-selected information |
| Policy-period indicator | Can encode changing thresholds and selection, but is genuinely known from calendar time | Calendar date at prefix is known | Keep | Required to model and audit temporal nonstationarity |
| Source system / partner indicator | May predict permanently missing labels and different workflows; can introduce operational bias | Available at start/prefix | Keep with missingness audit | Important for observation-process modeling and subgroup evaluation, but not proof of causal risk |
| Raw migrated activity name | Renaming can create artificial variants and drift | Normalize using a version-controlled mapping available independently of outcomes | Repair | Needed for comparable process features across migration |

## 7. Validation design

### Why random splits are misleading

A random case split would mix:

- pre- and post-1 July 2025 credit policy regimes;
- pre- and post-15 October 2025 migrated activity vocabularies;
- cases with different label maturity conditions;
- potentially related transferred cases or duplicate records across splits;
- future workflow knowledge into apparent historical generalization.

It would estimate interpolation within a mixed historical dataset rather than realistic forward performance under process and policy drift.

### Primary temporal split

Split by **application start time**, while ensuring labels are mature relative to each evaluation cutoff.

A practical design:

| Role | Application start period | Purpose |
|---|---|---|
| Training | 1 Jan 2024 – 31 Dec 2024 | Baseline historical process and outcomes |
| Validation | 1 Jan 2025 – 30 Jun 2025 | Tune model and calibration before policy change |
| Test 1: policy-shift test | 1 Jul 2025 – 14 Oct 2025 | Evaluate threshold-policy drift |
| Test 2: migration-shift test | 15 Oct 2025 onward, only cases mature by evaluation cutoff | Evaluate policy plus system-migration drift |

Because labels mature only after activation plus 90 days plus feed delay, later 2025 starts may not yet be fully evaluable at the 15 February 2026 extraction. The study should not force a complete test for all late-2025 cases. Instead:

- conduct backtesting at historical as-of cutoffs;
- freeze each evaluation cohort only after its labels mature;
- report sample sizes and missing-label proportions by fold;
- defer final late-2025 test conclusions until adequate follow-up exists.

### Rolling-origin backtesting

Use several historical cutoff dates, for example every quarter:

1. train on all mature cases available before cutoff;
2. validate on the next time block whose labels later mature;
3. evaluate calibration and discrimination in the forward block;
4. repeat across policy and migration periods.

This more closely mimics deployment retraining and monitoring.

### Policy and migration handling

- Include policy-era and migration-era indicators as known calendar features.
- Evaluate models separately pre-policy, post-policy/pre-migration, and post-migration.
- Compare activity-normalized versus raw-activity feature versions.
- Re-estimate the DFG, variant frequencies, and historical reference features using training data only.
- Do not assume a model trained pre-July 2025 remains calibrated post-policy change.

### Calibration

For the primary binary target, report:

- calibration intercept and slope;
- reliability curves;
- Brier score;
- expected calibration error, with caution for small subgroups;
- observed versus predicted default rates by decile;
- recalibration performance by time period.

Calibration should be assessed separately for:

- channel;
- region;
- source system;
- partner versus non-partner origin;
- requested amount band;
- policy period;
- score-availability subgroup;
- outcome-observed versus outcome-missing propensity strata.

A model may retain AUC while becoming poorly calibrated after a policy change.

### Discrimination and decision metrics

For mature observed activated accounts:

- ROC-AUC;
- PR-AUC, given approximately 12.5% default prevalence in the current labeled export;
- Brier score;
- log loss;
- sensitivity, specificity, precision/PPV, NPV at operational thresholds;
- recall and precision among the highest-risk review capacity band;
- decision curve analysis or expected utility only after specifying costs of review, false positive intervention, and missed default.

Because labels are selectively observed, report metrics alongside:

- label-observation rate;
- activation rate;
- missing-feed rate;
- weighting/sensitivity analysis results.

For a survival extension, appropriate metrics include time-dependent AUC, integrated Brier score, and calibration at 90 days, using methods valid under censoring. PM4Py itself should not be presented as providing survival modeling.

### Transfer-aware validation

Transferred cases with linkage should be grouped so that an original case and its linked downstream reappearance do not cross temporal folds in ways that leak information. For linked transfers, evaluate linkage completeness and analyze downstream outcomes separately; do not include unlinked transfer cases as negatives.

## 8. Limitations and decision-use boundary

### What the study can claim

The primary model can estimate predictive association between early observed application/process features and 90-day default among applications that:

1. were activated under the historical policy;
2. had mature, observable outcomes;
3. resemble the populations represented in the temporal training data.

It can support decision assistance, triage, monitoring, and prioritization when accompanied by calibration monitoring and human/process controls.

### What it cannot claim

It cannot claim:

- that rejected applicants are non-default;
- that the model estimates default risk for every application;
- that the model estimates what would happen if a rejected applicant were activated;
- that changes in a feature causally change default;
- that predicted risk remains valid after policy, channel, operational, or economic changes;
- that transferred or partner-originated cases with missing outcomes have the same risk distribution as observed labeled accounts.

The observed default label is defined after activation. Activation is a policy-dependent selection mechanism. Therefore, a high predicted default probability among historically activated accounts is not necessarily a counterfactual risk estimate for a currently rejected applicant.

### Selection effects

Acceptance thresholds changed on 1 July 2025. This can alter:

- who reaches activation;
- the covariate distribution among activated accounts;
- the relationship between prefix features and default;
- the observed default prevalence;
- apparent model performance.

The model may learn prior decision policy rather than borrower repayment behavior if decision-related or post-decision artifacts remain in the data.

### Deployment can change the data-generating process

At least three important feedback mechanisms are likely:

1. **Acceptance-policy feedback.** If risk predictions influence approval, fewer predicted high-risk applicants may be activated, changing both the training population and observed default prevalence.

2. **Intervention feedback.** If high-risk cases receive extra document checks, lower limits, pricing changes, or collections outreach, their observed default rate may change because of intervention rather than model error.

3. **Operational-routing feedback.** Using the model to prioritize queues can change waiting times, resource assignments, documentation loops, and process paths, making process features endogenous to model deployment.

Additional mechanisms include:

- applicants adapting behavior to changed lending policy;
- channel mix shifts;
- partner feed changes;
- resource incentives or gaming;
- migration changes to event logging;
- changes in default definition or collections practices.

Deployment should therefore include versioned data contracts, label-maturity monitoring, drift detection, periodic recalibration, fairness/governance review, and holdout or champion-challenger monitoring where feasible.

## 9. PM4Py-oriented Python implementation skeleton

```python
import pandas as pd
import numpy as np
import pm4py

# Assumptions:
# - one CSV row per event;
# - timestamps are UTC or consistently normalized;
# - label_available_at is the time the external/default label became known;
# - activity aliases below are semantic renames, not changed business meanings.
# Survival and competing-risk modeling would be connected after this pipeline,
# using a survival library rather than inventing a PM4Py survival API.

CSV = "applications_events.csv"
AS_OF = pd.Timestamp("2026-02-15", tz="UTC")
FEED_MAX_DELAY_DAYS = 35
PREFIX_K = 5

CASE = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"

POST_PREFIX_ACTIVITIES = {
    "Accepted", "Rejected", "Withdrawn", "Transferred",
    "Contract Signed", "Account Activated",
    "Collections Contact", "Default Recorded"
}

ACTIVITY_MAP = {
    # Example migration aliases; maintain this externally and version it.
    "KYC Check v2": "Identity/KYC Check",
    "Credit Review v2": "Credit Review",
    "Request Documents v2": "Request Documents",
}

# ---------------------------------------------------------------------
# 1) Read, timestamp-normalize, and retain only records available as-of.
# ---------------------------------------------------------------------
date_cols = [TS, "label_available_at", "data_extract_time"]
raw = pd.read_csv(CSV, parse_dates=date_cols)

for c in date_cols:
    raw[c] = pd.to_datetime(raw[c], utc=True, errors="coerce")

# Events extracted after the as-of analysis cutoff cannot be used.
raw = raw.loc[raw["data_extract_time"].isna() | (raw["data_extract_time"] <= AS_OF)].copy()
raw = raw.loc[raw[TS].notna() & raw[CASE].notna() & raw[ACT].notna()].copy()

raw["activity_raw"] = raw[ACT].astype(str)
raw[ACT] = raw["activity_raw"].replace(ACTIVITY_MAP)
raw = raw.sort_values([CASE, TS, ACT], kind="mergesort")

# Conservative duplicate handling for migration artifacts only:
# do not collapse legitimate repeated document-review loops.
dup_key = [CASE, ACT, TS, "org:resource", "source_system"]
raw = raw.drop_duplicates(subset=[c for c in dup_key if c in raw.columns])

# PM4Py event-log formatting. Keep normalized activity labels.
log_df = pm4py.format_dataframe(
    raw.copy(),
    case_id=CASE,
    activity_key=ACT,
    timestamp_key=TS
)

# Optional process summaries are descriptive and must be recomputed
# from training data only when used as model reference features.
dfg, start_acts, end_acts = pm4py.discover_dfg(log_df)
variants = pm4py.get_variants(log_df)

# ---------------------------------------------------------------------
# 2) Case-level lifecycle table as of cutoff.
# ---------------------------------------------------------------------
def first_time(g, activity):
    x = g.loc[g[ACT] == activity, TS]
    return x.min() if not x.empty else pd.NaT

def last_observed_label(g):
    # Outcome is usable only when label itself is known as-of cutoff.
    known = g.loc[
        g["default_90d"].notna()
        & g["label_available_at"].notna()
        & (g["label_available_at"] <= AS_OF),
        "default_90d"
    ]
    return known.iloc[-1] if len(known) else np.nan

rows = []
for case_id, g in log_df.groupby(CASE, sort=False):
    start = g[TS].min()
    activation = first_time(g, "Account Activated")
    rejected = first_time(g, "Rejected")
    withdrawn = first_time(g, "Withdrawn")
    transferred = first_time(g, "Transferred")

    terminal_times = pd.Series(
        [rejected, withdrawn, transferred],
        dtype="datetime64[ns, UTC]"
    ).dropna()
    terminal = terminal_times.min() if not terminal_times.empty else pd.NaT

    label = last_observed_label(g)
    mature_by_time = (
        pd.notna(activation)
        and activation + pd.Timedelta(days=90 + FEED_MAX_DELAY_DAYS) <= AS_OF
    )
    label_available = pd.notna(label)

    # "Mature observed" is the fixed-horizon supervised-label condition.
    mature_observed = bool(mature_by_time and label_available)

    rows.append({
        CASE: case_id,
        "case_start": start,
        "activation_time": activation,
        "terminal_time": terminal,
        "rejected_time": rejected,
        "withdrawn_time": withdrawn,
        "transferred_time": transferred,
        "default_90d_label": label,
        "outcome_mature_by_time": mature_by_time,
        "label_available_asof": label_available,
        "mature_observed_label": mature_observed,
        "channel": g["case:channel"].iloc[0] if "case:channel" in g else np.nan,
        "region": g["case:region"].iloc[0] if "case:region" in g else np.nan,
        "source_system": g["source_system"].iloc[0] if "source_system" in g else np.nan,
    })

cases = pd.DataFrame(rows)

def cohort_status(r):
    if r["mature_observed_label"] and pd.notna(r["activation_time"]):
        return "activated_labeled_default" if int(r["default_90d_label"]) == 1 else "activated_labeled_nondefault"
    if pd.notna(r["activation_time"]):
        return "activated_not_mature_or_feed_missing"
    if pd.notna(r["rejected_time"]):
        return "rejected_competing_outcome"
    if pd.notna(r["withdrawn_time"]):
        return "withdrawn_competing_outcome"
    if pd.notna(r["transferred_time"]):
        return "transferred_competing_or_missing_followup"
    return "still_open_right_censored"

cases["cohort_status"] = cases.apply(cohort_status, axis=1)
print("\nCohort counts as of", AS_OF.date())
print(cases["cohort_status"].value_counts(dropna=False))

# ---------------------------------------------------------------------
# 3) Temporal split by CASE START, not a random case split.
# Exact boundaries should be revised once mature-label counts are checked.
# ---------------------------------------------------------------------
train_end = pd.Timestamp("2024-12-31 23:59:59", tz="UTC")
valid_end = pd.Timestamp("2025-06-30 23:59:59", tz="UTC")
migration_date = pd.Timestamp("2025-10-15", tz="UTC")

cases["split"] = np.select(
    [
        cases["case_start"] <= train_end,
        cases["case_start"] <= valid_end,
        cases["case_start"] < migration_date,
    ],
    ["train", "validation_pre_policy_change", "test_policy_shift"],
    default="test_migration_or_not_yet_mature"
)

# Primary fixed-horizon outcome cohort: activated + observed mature label.
primary_cases = cases.loc[
    cases["mature_observed_label"]
    & cases["activation_time"].notna()
].copy()

# ---------------------------------------------------------------------
# 4) Prefix generation. PM4Py fixed-length prefixes are demonstrated,
# but prefix feature extraction below explicitly removes post-prefix events.
# ---------------------------------------------------------------------
predecision = log_df.loc[~log_df[ACT].isin(POST_PREFIX_ACTIVITIES)].copy()
predecision = predecision.sort_values([CASE, TS], kind="mergesort")

# Demonstration requested by study design. API returns a prefix log.
# Depending on PM4Py version, inspect the resulting case IDs before joining.
fixed_prefix_log = pm4py.get_prefixes_from_log(predecision, length=PREFIX_K)

# Robust explicit event-level prefix endpoint for feature engineering.
predecision["event_nr"] = predecision.groupby(CASE).cumcount() + 1
prefix_end = (
    predecision.loc[predecision["event_nr"] == PREFIX_K, [CASE, TS]]
    .rename(columns={TS: "prefix_time"})
)

prefix_events = (
    predecision.merge(prefix_end, on=CASE, how="inner")
    .loc[lambda d: d[TS] <= d["prefix_time"]]
    .copy()
)

# Hard audit: no feature event may occur after its own prefix endpoint.
assert (prefix_events[TS] <= prefix_events["prefix_time"]).all()

# ---------------------------------------------------------------------
# 5) As-of-safe prefix features. Do NOT aggregate final_limit,
# decision_reason, collection_status, default_90d, or label_available_at.
# ---------------------------------------------------------------------
SAFE_EVENT_COLUMNS = [CASE, ACT, TS, "risk_score", "org:resource"]
safe = prefix_events[[c for c in SAFE_EVENT_COLUMNS if c in prefix_events.columns]].copy()

# Last risk score observed within prefix; updated future scores are excluded.
safe["risk_score"] = pd.to_numeric(safe.get("risk_score"), errors="coerce")
feat = safe.groupby(CASE).agg(
    prefix_events=(ACT, "size"),
    prefix_distinct_activities=(ACT, "nunique"),
    prefix_last_event_time=(TS, "max"),
    risk_score_last_prefix=("risk_score", "last"),
    risk_score_updates_prefix=("risk_score", lambda s: s.notna().sum()),
).reset_index()

# Control-flow and rework examples.
feat["credit_review_count"] = (
    prefix_events[ACT].eq("Credit Review").groupby(prefix_events[CASE]).sum().reindex(feat[CASE]).fillna(0).to_numpy()
)
feat["document_request_count"] = (
    prefix_events[ACT].eq("Request Documents").groupby(prefix_events[CASE]).sum().reindex(feat[CASE]).fillna(0).to_numpy()
)
feat["document_rework_proxy"] = (
    (feat["credit_review_count"] > 1) & (feat["document_request_count"] > 0)
).astype(int)

features = (
    primary_cases.merge(prefix_end, on=CASE, how="inner")
    .merge(feat, on=CASE, how="inner")
)
features["elapsed_hours_to_prefix"] = (
    (features["prefix_time"] - features["case_start"]).dt.total_seconds() / 3600.0
)
features["policy_post_2025_07_01"] = (
    features["prefix_time"] >= pd.Timestamp("2025-07-01", tz="UTC")
).astype(int)
features["migration_post_2025_10_15"] = (features["prefix_time"] >= migration_date).astype(int)

# ---------------------------------------------------------------------
# 6) Leakage audit checks before model fitting.
# ---------------------------------------------------------------------
FORBIDDEN_MODEL_COLUMNS = {
    "final_limit", "decision_reason", "collection_status",
    "default_90d", "label_available_at", "activation_time",
    "terminal_time", "rejected_time", "withdrawn_time", "transferred_time"
}
present_forbidden = FORBIDDEN_MODEL_COLUMNS.intersection(features.columns)
assert not present_forbidden, f"Leakage columns found in feature table: {present_forbidden}"

print("\nPrimary labeled prefix cohort by temporal split")
print(features.groupby("split")["default_90d_label"].agg(["count", "mean"]))

print("\nOutcome-observation diagnostics by source/channel")
print(cases.groupby(["source_system", "channel"], dropna=False)["mature_observed_label"].agg(["count", "mean"]))
```
