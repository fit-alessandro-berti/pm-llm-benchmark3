## 1. Equivalence design space

### 1. Activity-sequence equivalence
- **Operational definition:** Two executions are equivalent if their sequences of activity labels projected onto the lead object type (`Order`) are identical, ignoring local object identifiers, external object flags, multiplicities, and O2O structural relationships.
- **Invariants preserved:** Total order of activity labels associated with the `Order` object type.
- **Information discarded:** All object identifiers, object types, multiplicities (e.g., whether 1 or 2 items/packages/payments occur), external object flags (`EXT-...`), O2O qualifiers (`removed_before_dispatch`), and parallel/nested lifecycles.
- **Equivalence properties:** Reflexive ($\checkmark$), Symmetric ($\checkmark$), Transitive ($\checkmark$). Forms an equivalence relation.
- **Concurrency/same-time events:** Handled by imposing a canonical topological sort (e.g., lexicographical sorting of activity labels for events sharing the exact same timestamp).

### 2. Typed structural equivalence under identifier renaming
- **Operational definition:** Two executions are equivalent if there exists an isomorphism between their object-centric event logs (OCEL graph structure) that preserves event activity labels, object types, event-to-object (E2O) incidence, and object-to-object (O2O) structural topologies, up to a bijective renaming of local object identifiers. External flags (`EXT-...`) are treated as a special structural property/type tag.
- **Invariants preserved:** Exact multi-set of events, event-to-object incidence edges, object-to-object graph topology, object types, and external object markers.
- **Information discarded:** Specific local identifier strings (e.g., `O1` vs `O2`, `I11` vs `I22`).
- **Equivalence properties:** Reflexive ($\checkmark$), Symmetric ($\checkmark$), Transitive ($\checkmark$). Forms an equivalence relation.
- **Concurrency/same-time events:** Preserved as partial orders (DAGs) rather than forced total sequences, as long as E2O/O2O graph isomorphism holds.

### 3. Business-semantic equivalence using multiplicities, shared external objects, O2O qualifiers, or lifecycle motifs
- **Operational definition:** Two executions are equivalent if they share the same operational motifs and business constraints regarding resource isolation, fulfillment cardinality, financial settlement integrity, and item integrity (no substitutions, returns, or external mingling).
- **Invariants preserved:** 
  1. Fulfillment isolation (whether packages/invoices are strictly 1:1 with the order or shared with `EXT` objects).
  2. Item lifecycle integrity (whether all items added are dispatched in their original packages without returns or removals).
  3. Financial closure cardinality (single vs. split payments).
- **Information discarded:** Exact numbers of items (as long as >0 and fully fulfilled), specific local identifier strings, and exact timestamps.
- **Equivalence properties:** Reflexive ($\checkmark$), Symmetric ($\checkmark$), Transitive ($\checkmark$). Forms an equivalence relation over business process archetypes.
- **Concurrency/same-time events:** Treated as non-deterministic execution interleavings; only the net structural business motifs (e.g., "split delivery", "return-and-repack") matter.

## 2. Canonical signatures

Below is a Python-like canonicalization scheme that generates a structural hash for an execution centered on an `Order` object. It normalizes local object identifiers, preserves object types, counts multiplicities, captures external object flags, preserves E2O/O2O incidence, and encodes O2O qualifiers.

```python
import hashlib
import json

def generate_canonical_signature(execution_data):
    """
    Generates a canonical signature for an Order-centric execution.
    execution_data format:
    {
      "events": [
        {
          "activity": str,
          "e2o": { obj_id: obj_type, ... },
          "o2o": [ { "source": id, "target": id, "qualifier": str or None }, ... ]
        },
        ...
      ],
      "objects": { obj_id: { "type": str, "is_ext": bool }, ... }
    }
    """
    objects = execution_data["objects"]
    
    # Step 1: Compute isomorphism-free canonical naming for objects
    # Group objects by type and externality, then sort and rename canonically
    obj_type_counts = {}
    id_mapping = {}
    
    # Sort objects deterministically: external first, then by original ID for stability
    sorted_objs = sorted(
        objects.items(), 
        key=lambda item: (not item[1]["is_ext"], item[1]["type"], item[0])
    )
    
    type_counters = {}
    for old_id, obj_info in sorted_objs:
        obj_type = obj_info["type"]
        is_ext = obj_info["is_ext"]
        prefix = "EXT_" if is_ext else ""
        type_counters[obj_type] = type_counters.get(obj_type, 0) + 1
        new_id = f"{prefix}{obj_type}_{type_counters[obj_type]}"
        id_mapping[old_id] = new_id

    # Step 2: Normalize events using canonical object IDs
    canonical_events = []
    for ev in execution_data["events"]:
        norm_e2o = sorted([
            (id_mapping[oid], objects[oid]["type"]) 
            for oid in ev["e2o"]
        ])
        norm_o2o = sorted([
            {
                "source": id_mapping[rel["source"]],
                "target": id_mapping[rel["target"]],
                "qualifier": rel.get("qualifier")
            }
            for rel in ev.get("o2o", [])
        ], key=lambda x: (x["source"], x["target"], str(x["qualifier"])))
        
        canonical_events.append({
            "activity": ev["activity"],
            "e2o": norm_e2o,
            "o2o": norm_o2o
        })

    # Step 3: Serialize and hash
    signature_payload = {
        "events": canonical_events
    }
    canonical_string = json.dumps(signature_payload, sort_keys=True)
    return hashlib.sha256(canonical_string.encode("utf-8")).hexdigest()
```

## 4. Cluster interpretations

### 1. `Standard-Isolated-Fulfillment` (X1, X2)
- **Concise signature:** Create $\rightarrow$ Add(2) $\rightarrow$ Pack(1) $\rightarrow$ Dispatch(1) $\rightarrow$ Invoice(1) $\rightarrow$ Pay(1), strictly 1:1 object mappings with no external links or exceptions.
- **Business behavior:** Straight-through processing (STP). The order is placed, packed into a single carton, shipped in one delivery, billed on a single invoice, and paid in full.
- **Operational risks or opportunities:** Highly efficient. Opportunity for complete automation (RPA / touchless processing). Risk of over-reliance on STP masking rigid fulfillment logic when customer demands vary.
- **Traditional flattening failure:** Case-centric flattening on `Order` treats X1 and X2 as identical flat traces. While acceptable here, flattening hides the granular multi-object cardinality (e.g., how many items are inside the package) unless flattened on Item, which explodes trace counts.
- **Data-repair stability:** Extremely stable; minor logging jitter on item addition order does not affect this cluster.

### 2. `Consolidated-MultiPackage-Fulfillment` (X3)
- **Concise signature:** Create $\rightarrow$ Add(2) $\rightarrow$ Pack(2) $\rightarrow$ Dispatch(1, multi-package) $\rightarrow$ Invoice(1) $\rightarrow$ Pay(1).
- **Business behavior:** Multi-item orders requiring physical separation into multiple boxes due to size/weight constraints, but consolidated onto a single truck/delivery run.
- **Operational risks or opportunities:** Packing labor is higher, but delivery cost is optimized. Opportunity to analyze item-to-package allocation efficiency.
- **Traditional flattening failure:** Standard process mining flattens this into a simple linear trace, completely obscuring that two physical packages were handled and consolidated under one delivery event.
- **Data-repair stability:** Stable. Minor timestamp variations between packing events do not alter the semantic cluster.

### 3. `Fragmented-Milestone-Fulfillment` (X4)
- **Concise signature:** Create $\rightarrow$ Add(2) $\rightarrow$ [Pack $\rightarrow$ Dispatch] $\times 2$ $\rightarrow$ Invoice(1) $\rightarrow$ Pay(2).
- **Business behavior:** Staggered fulfillment where items are shipped as soon as ready (backorders or multi-warehouse dispatch), followed by split or milestone payments against a single consolidated invoice.
- **Operational risks or opportunities:** Higher shipping and handling costs (multiple dispatches). Cash flow is received in installments, increasing working capital strain.
- **Traditional flattening failure:** Flattening on Order misses the shipment fragmentation; flattening on Item duplicates the invoice and payment events, distorting financial metrics.
- **Data-repair stability:** Moderately stable; sensitive to whether partial payments are logged as distinct events or lump-sum adjustments.

### 4. `Resource-Contaminated-Logistics` (X5)
- **Concise signature:** Activity sequence matches Standard, but Pack/Dispatch events feature mixed E2O incidence with external objects (`EXT-OA`, `EXT-IA`).
- **Business behavior:** Batching or commingling fulfillment where items from multiple distinct customer orders are packed into a shared master container or shipped together in a shared transport unit.
- **Operational risks or opportunities:** High risk of mis-delivery, customer disputes over missing items, and inaccurate cost allocation. Opportunity to optimize warehouse consolidation, but governance controls are weak.
- **Traditional flattening failure:** Case-centric flattening completely hides the cross-order contamination, reporting the execution as a standard clean order.
- **Data-repair stability:** Unstable if external object tags (`EXT-`) are inconsistently logged by warehouse scanners.

### 5. `Consolidated-Financial-Settlement` (X6)
- **Concise signature:** Standard physical fulfillment leading into a shared Issue Invoice and Record Payment event linked to an external order (`EXT-OB`).
- **Business behavior:** Consolidated billing or parent-child account settlement where multiple orders are invoiced and paid together under a single financial document without explicit line-item allocation.
- **Operational risks or opportunities:** Simplifies accounts receivable administration for corporate clients, but creates reconciliation nightmares if an individual order must be refunded or audited.
- **Traditional flattening failure:** Flattening on Order either duplicates invoice amounts across flattened traces or fails to link the payment back to the correct revenue stream.
- **Data-repair stability:** Stable, provided financial ledger keys reliably capture multi-order invoice mappings.

### 6. `Exception-Item-Substitution` (X7)
- **Concise signature:** Standard activity sequence with an internal O2O qualifier `removed_before_dispatch` linking the initial package to an excluded item (`I71`).
- **Business behavior:** An item was added, packed, but subsequently discovered to be defective, out of stock, or swapped at the packing station prior to truck loading.
- **Operational risks or opportunities:** Internal warehouse quality catch (good), but indicates inventory record inaccuracy and potential packing rework that is invisible at the activity-label level.
- **Traditional flattening failure:** Traditional event logs show a standard STP trace, completely missing the internal item swap and inventory discrepancy.
- **Data-repair stability:** Highly dependent on whether warehouse workers explicitly log exception qualifiers (`removed_before_dispatch`) or simply overwrite database records silently.

### 7. `Exception-Return-And-Repack` (X8)
- **Concise signature:** Create $\rightarrow$ Pack $\rightarrow$ Dispatch $\rightarrow$ Return Item $\rightarrow$ Inspect $\rightarrow$ Repack $\rightarrow$ Dispatch $\rightarrow$ Invoice $\rightarrow$ Pay.
- **Business behavior:** Post-dispatch exception handling where a delivered item is returned, inspected, repacked into a new package, and re-dispatched before final invoicing.
- **Operational risks or opportunities:** Severe margin erosion due to reverse logistics and double handling. Major opportunity to investigate root causes of initial picking/shipping errors.
- **Traditional flattening failure:** Flattening on Order produces a convoluted loop that is hard to interpret; flattening on Item separates the lifecycle into disconnected fragments.
- **Data-repair stability:** Stable, as physical returns and re-packings generate hard operational milestones and new package IDs.

## 5. Borderline cases

- **X1 versus X2:** 
  - *Activity-sequence & Typed-structural:* Equivalent (isomorphic up to renaming).
  - *Semantic:* Equivalent.
  - *Disagreement:* None; these are structurally identical instances of standard fulfillment.

- **X1 versus X5:** 
  - *Activity-sequence:* Equivalent (both exhibit the exact same 7-step activity label sequence).
  - *Typed-structural & Semantic:* Distinct. X1 has strictly isolated E2O/O2O boundaries, whereas X5 involves shared external objects (`EXT-OA`, `EXT-IA`). An activity-level miner groups them together, missing the logistics commingling risk in X5.

- **X1 versus X6:** 
  - *Activity-sequence:* Equivalent.
  - *Typed-structural & Semantic:* Distinct. X1 has a 1:1 invoice-to-order relationship, while X6 shares invoice `V61` with `EXT-OB`. Activity-sequence equivalence conflates clean single-order billing with shared multi-order financial settlement.

- **X1 versus X7:** 
  - *Activity-sequence:* Equivalent.
  - *Typed-structural & Semantic:* Distinct. X1 features pure item containment, while X7 contains an O2O qualifier (`removed_before_dispatch`) indicating item substitution. Activity-sequence equivalence hides internal warehouse exceptions and inventory discrepancies.

- **X3 versus X4:** 
  - *Activity-sequence:* Distinct (X3 has single pack/dispatch sequence with multiplicity; X4 has interleaved pack/dispatch pairs).
  - *Typed-structural & Semantic:* Both represent multi-package fulfillment, but X3 consolidates delivery and billing, whereas X4 splits delivery and payment milestones. Structural equivalence separates them due to distinct event topologies, whereas a coarse business semantic definition might group them as "Non-Standard Packing".

- **X4 versus X8:** 
  - *Activity-sequence:* Distinct.
  - *Typed-structural & Semantic:* Both exhibit multiple packing/dispatch phases and multiple payments. However, X4 is a *forward* staged split-fulfillment, whereas X8 involves a *reverse* logistics loop (Return Item $\rightarrow$ Inspect Return $\rightarrow$ Repack). Structural equivalence separates them cleanly based on the presence of the `Return Item` event, whereas a crude volume-based metric might group them under "Complex Multi-Step Orders".

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### Analysis of PM4Py Object-Centric Clustering
- **Information preserved:** PM4Py's `cluster_equivalent_ocel` typically hashes or groups event logs based on object-centric behavioral projections—specifically, the multi-sets of event-object graphs and direct succession relations per object type.
- **Why raw object IDs fail:** Raw object identifiers (e.g., `O1` vs `O2`, `I11` vs `I21`) are instance-specific strings. Two executions with identical structural topology will be placed into separate clusters if local identifiers differ, leading to severe fragmentation.
- **Canonicalization / Post-processing:** To make PM4Py clusters useful, one must pre-process the OCEL by applying a graph-automorphism or canonical relabeling algorithm (similar to Section 2) that replaces instance identifiers with structural equivalence classes, or post-process the cluster labels by mapping instance-level equivalence hashes to abstract business motifs.
- **When exact equivalence is preferable:** Exact structural/isomorphic equivalence is vital for automated compliance auditing, strict security verification, and deterministic robotic process automation (RPA) replay.
- **Challenges with `max_objs`:** In large enterprise OCELs, highly connected component graphs (e.g., central master hubs like a master distributor order or shared warehouse pallet) cause the connected component size to explode, leading to performance bottlenecks or massive monolithic clusters in `cluster_equivalent_ocel`.

## 7. Robustness analysis

1. **Ignore all O2O qualifiers:**
   - *Impact:* X7 (`Exception-Item-Substitution`) loses its `removed_before_dispatch` qualifier, making it indistinguishable from X1 and X2 (`Standard-Isolated-Fulfillment`). The exception is hidden, turning a quality/inventory discrepancy into a standard STP execution.
2. **Ignore external objects (`EXT-...`):**
   - *Impact:* X5 (`Resource-Contaminated-Logistics`) loses its external object links (`EXT-OA`, `EXT-IA`), and X6 (`Consolidated-Financial-Settlement`) loses `EXT-OB`. Both collapse into the `Standard-Isolated-Fulfillment` cluster, completely masking cross-order supply chain mingling and shared billing risks.
3. **Collapse repeated same-label events:**
   - *Impact:* X4 (`Fragmented-Milestone-Fulfillment`) features sequential packing/dispatch and payment events. If collapsed, X4 loses its multiplicity and resembles a multi-item batch execution, blurring the distinction between staggered milestone fulfillment and single-batch processing.
4. **Treat Pack and Dispatch event order as partial order rather than total order:**
   - *Impact:* X3 and X4 show different interleavings. In concurrent multi-package execution, if timestamps jitter slightly, partial-order semantics ensure that structural equivalence remains robust against minor logging race conditions, preventing artificial cluster splitting.
5. **Treat payment multiplicity as an amount attribute rather than structure:**
   - *Impact:* X4 has two `Record Payment` events representing partial installments. If payment structure is reduced to a single numeric attribute on the invoice, X4's distinctive multi-payment settlement pattern is masked, grouping it structurally closer to single-payment executions like X1.

## 8. Limitations and recommendation

### Recommended Equivalence Level per Use Case
- **Compliance monitoring:** *Typed structural equivalence with O2O qualifiers.* Required to detect unauthorized cross-order resource sharing (X5, X6) and hidden item substitutions (X7) that violate regulatory or contractual isolation constraints.
- **Operational segmentation:** *Business-semantic equivalence.* Required for process mining dashboards, throughput time analysis, and resource capacity planning, where operational motifs (e.g., split packaging vs. returns processing) dictate labor requirements.
- **Root-cause analysis:** *Typed structural equivalence.* Required to trace exact defect propagation, such as identifying which specific returned item (`I82`) in X8 triggered the secondary repack and dispatch cycle (`P82`, `D82`).
- **Descriptive reporting:** *Activity-sequence equivalence.* Sufficient for high-level executive summaries and KPI tracking (e.g., percentage of orders reaching invoice and payment), where internal logistics complexity can be safely abstracted away.

### Why No Single Equivalence Notion Suffices
Process mining over object-centric systems serves multiple stakeholders with conflicting goals. Executives require coarse abstractions (activity-sequence equivalence) to track macro-level volume and revenue. Operations managers require medium-granularity motifs (business-semantic equivalence) to staff packing stations and manage warehouse bottlenecks. Compliance officers and auditors require hyper-granular proofs (typed structural equivalence with qualifiers and externality tags) to catch fraud, shrinkage, and unauthorized resource commingling. Forcing a single equivalence notion across all use cases invariably sacrifices either executive clarity or forensic rigor.
