## 1. Modeling assumptions

**Object types (capitalized, singular):** `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`. The 12 objects are O100, O200, I1, I2, I3, P1, P2, D1, D2, V1, M1, M2.

**E2O qualifier vocabulary:** qualifiers are role-based, and each (activity, object type) pair has exactly one qualifier.

| Activity | Object type  qualifier |
|---|---|
| Create Order | Order  `created_order` |
| Add Item | Order  `extended_order`, Item  `added_item` |
| Reserve Stock | Item  `reserved_item`, Order  `reserved_for_order` |
| Pack Package | Package  `packed_package`, Item  `packed_item`, Order  `packed_for_order` |
| Dispatch Package | Package  `dispatched_package`, Delivery  `dispatched_delivery` |
| Issue Invoice | Invoice  `issued_invoice`, Order  `billed_order` |
| Record Payment | Payment  `recorded_payment`, Invoice  `paid_invoice` |
| Confirm Delivery | Delivery  `confirmed_delivery` |
| Close Order | Order  `closed_order` |

Analytically derived links use a separate namespace, `derived_order` and `derived_item`. They never appear in the base `relations`.

**O2O direction:** the source (`ocel:oid`) is the aggregating or acting object, and the target (`ocel:oid_2`) is the aggregated or referenced object.
- Order `contains` Item.
- Package `packs` Item.
- Delivery `carries` Package.
- Invoice `bills` Order.
- Payment `partially_settles` Invoice (M1).
- Payment `completes_settlement` Invoice (M2).

The process text calls both payments "partial". I use `completes_settlement` for M2 because it is the last payment, and this is an interpretation. The invoice total (250 = 100 + 150) is inferred, not stated, so no invoice amount attribute is stored. Keeping both payments as `partially_settles` would be equally defensible.

**Direct relations for downstream events (the decision):**
- The base OCEL is source-direct. An event is linked to the objects it names or operationally involves, using one relation schema per activity, not per instance.
- Pack Package therefore links to its Package, Items and Orders. The text states the Orders for P1. I apply the same pattern to P2, so P2 also links to O100. This is a modeling choice and is flagged in the audit.
- Dispatch Package and Confirm Delivery link only to Package and Delivery, or to Delivery alone.
- Record Payment links to Payment and Invoice only.
- Issue Invoice links to Invoice and to both Orders, because the text says "for both Orders".
- Logistics and financial events do not link directly to Orders or Items, except where stated above.

**Trade-off between direct and propagated relations:**
- Direct relations are faithful to the source and avoid inventing observations. They keep payment amounts and delivery events from being counted several times.
- They leave Order and Item flattenings without delivery and payment steps.
- Propagated relations (Delivery  Package  Item  Order) give richer Order-centric traces.
- They inflate relation counts, copy events into many cases, and turn ambiguous allocation into apparent fact. For example, the 250 paid would appear as 500 when summed per Order.
- The pipeline therefore builds `ocel` (source-direct) for the main analysis and `ocel_propagated` only as a clearly labeled comparison.

**Keeping analytical propagation separate from source facts:**
- Derived rows live in their own DataFrame, `derived_relations`.
- They carry an `analytic:derivation` provenance column and `derived_*` qualifiers.
- They are added only to the separate `ocel_propagated`.
- The validator rejects `derived_*` qualifiers in the base tables.

**Version-dependent PM4Py assumptions:**
- `OCEL(events=, objects=, relations=, o2o=)` is isolated in `make_ocel`.
- If a version lacks the `o2o` argument (older 2.7.x), construct without it and assign `ocel.o2o = o2o`. Some versions also need `globals` or `parameters` arguments. The data semantics do not change.
- Return shapes of `discover_otg`, `discover_etot` and `ocel_objects_interactions_summary` have varied, so the code prints them generically.
- Flattened logs use the standard columns `case:concept:name`, `concept:name` and `time:timestamp`.
- Visualization needs Graphviz and is commented out.

    check({"ocel:oid", "ocel:oid_2", "ocel:qualifier"} <= set(o2o.columns), "o2o: missing mandatory columns")

    for name, df in (("events", events), ("relations", relations)):
        check(isinstance(df["ocel:timestamp"].dtype, pd.DatetimeTZDtype), f"{name}: timestamps must be tz-aware")
        check(df[[c for c in df.columns if c.startswith("ocel:")]].notna().all().all(), f"{name}: null in ocel: column")

    # uniqueness
    check(events["ocel:eid"].is_unique, "duplicate event IDs")
    check(objects["ocel:oid"].is_unique, "duplicate object IDs")

    # referential integrity
    event_ids, object_ids = set(events["ocel:eid"]), set(objects["ocel:oid"])
    check(set(relations["ocel:eid"]) <= event_ids, "orphan event IDs in relations")
    check(event_ids <= set(relations["ocel:eid"]), "events without any E2O relation")
    check(set(relations["ocel:oid"]) <= object_ids, "orphan object IDs in relations")
    check(set(o2o["ocel:oid"]) <= object_ids and set(o2o["ocel:oid_2"]) <= object_ids, "orphan object IDs in o2o")
    check(object_ids <= set(relations["ocel:oid"]), "object never related to any event")

    # object-type consistency
    mapped = relations["ocel:oid"].map(objects.set_index("ocel:oid")["ocel:type"])
    check((mapped == relations["ocel:type"]).all(), "relations: type differs from objects table")

    # activity/timestamp consistency
    merged = relations.merge(events[["ocel:eid", "ocel:activity", "ocel:timestamp"]],
                             on="ocel:eid", suffixes=("", "_ev"))
    check((merged["ocel:activity"] == merged["ocel:activity_ev"]).all(), "activity mismatch events vs relations")
    check((merged["ocel:timestamp"] == merged["ocel:timestamp_ev"]).all(), "timestamp mismatch events vs relations")

    # duplicates
    check(not relations.duplicated(["ocel:eid", "ocel:oid", "ocel:qualifier"]).any(), "duplicate relation rows")
    check(not relations.duplicated(["ocel:eid", "ocel:oid"]).any(), "one object related twice to one event")
    check(not o2o.duplicated().any(), "duplicate o2o rows")

    # qualifier vocabulary
    for row in relations.itertuples(index=False):
        q = row[relations.columns.get_loc("ocel:qualifier")]
        act = row[relations.columns.get_loc("ocel:activity")]
        typ = row[relations.columns.get_loc("ocel:type")]
        if allow_derived and q.startswith("derived_"):
            continue
        check(E2O_RULES.get((act, typ)) == q, f"unexpected qualifier {q!r} for ({act}, {typ})")

    # O2O vocabulary, direction and no self loops
    type_of = objects.set_index("ocel:oid")["ocel:type"]
    for s, t, q in o2o[["ocel:oid", "ocel:oid_2", "ocel:qualifier"]].itertuples(index=False):
        check(q in O2O_TYPE_RULES, f"unknown o2o qualifier {q}")
        check((type_of[s], type_of[t]) == O2O_TYPE_RULES[q], f"o2o direction/type violation: {s} {q} {t}")
        check(s != t, "o2o self loop")

    # event attribute placement: amounts only on payment events
    check(events.loc[events["amount"].notna(), "ocel:activity"].eq("Record Payment").all(),
          "amount present on non-payment event")

    # documented property of this dataset: chronological, no ties
    check(events["ocel:timestamp"].is_monotonic_increasing and events["ocel:timestamp"].is_unique,
          "events must be chronological without timestamp ties")
    return True


# ----------------------------------------------------------------------------
# Analytical propagation: kept apart from source-direct facts.
# ----------------------------------------------------------------------------
def _adjacency(o2o, qualifiers):
    sub = o2o[o2o["ocel:qualifier"].isin(qualifiers)]
    fwd, rev = defaultdict(set), defaultdict(set)
    for s, t in zip(sub["ocel:oid"], sub["ocel:oid_2"]):
        fwd[s].add(t)
        rev[t].add(s)
    return fwd, rev


def derive_propagated_relations(events, relations, o2o):
    """Derive Order/Item links for logistics and finance events via O2O.

    Dispatch Package : Package -packs-> Item <-contains- Order
    Confirm Delivery : Delivery -carries-> Package -packs-> Item <-contains- Order
    Record Payment   : Invoice -bills-> Order   (Items deliberately NOT derived:
                       payment allocation to Items is undefined)
    """
    contains_f, contains_r = _adjacency(o2o, {"contains"})
    packs_f, _ = _adjacency(o2o, {"packs"})
    carries_f, _ = _adjacency(o2o, {"carries"})
    bills_f, _ = _adjacency(o2o, {"bills"})
    direct = relations.groupby(["ocel:eid", "ocel:type"])["ocel:oid"].agg(set).to_dict()
    already = set(zip(relations["ocel:eid"], relations["ocel:oid"]))
    rows = []

    def add(eid, oids, qualifier, path):
        for oid in sorted(oids):
            if (eid, oid) not in already:
                rows.append((eid, oid, qualifier, path))

    for eid, act in zip(events["ocel:eid"], events["ocel:activity"]):
        if act in ("Dispatch Package", "Confirm Delivery"):
            if act == "Dispatch Package":
                packages = direct.get((eid, "Package"), set())
                prefix = "Package-packs->Item"
            else:
                packages = {p for d in direct.get((eid, "Delivery"), set()) for p in carries_f[d]}
                prefix = "Delivery-carries->Package-packs->Item"
            items = {i for p in packages for i in packs_f[p]}
            orders = {o for i in items for o in contains_r[i]}
            add(eid, items, "derived_item", prefix)
            add(eid, orders, "derived_order", prefix + "<-contains-Order")
        elif act == "Record Payment":
            orders = {o for v in direct.get((eid, "Invoice"), set()) for o in bills_f[v]}
            add(eid, orders, "derived_order", "Invoice-bills->Order")

    derived = pd.DataFrame(rows, columns=["ocel:eid", "ocel:oid", "ocel:qualifier", "analytic:derivation"])
    derived = derived.merge(events[["ocel:eid", "ocel:activity", "ocel:timestamp"]], on="ocel:eid", how="left")
    derived["ocel:type"] = derived["ocel:oid"].map(OID_TYPE)
    return derived[RELATION_COLUMNS + ["analytic:derivation"]]

**Consequential events**
- **e06 Reserve Stock:** two Orders and two Items in one event. Flattening on Order copies it to both cases.
- **e07 Pack Package P1:** combines O100 and O200. It is the pivotal convergence event and links Order, Item and Package. It is copied in Order flattening, and Order flattening shows nothing after it about P1's shipment.
- **e08 Pack Package P2:** relating it to O100 is a modeling choice (uniform schema). It gives O100 two Pack Package events, which is divergence under Order flattening.

- **e13 and e14 Confirm Delivery:** they sit between the two payments in time. Under direct relations they are invisible to Order, Item and Invoice views.

## 4. Expected flattened behavior

**Order**
- **Shape:** O100 has 8 events: Create Order, Add Item, Add Item, Reserve Stock, Pack Package, Pack Package, Issue Invoice, Close Order. O200 has 6 events: Create Order, Add Item, Reserve Stock, Pack Package, Issue Invoice, Close Order.
- **Copied shared events:** e06, e07 and e11 appear in both cases. That gives 14 rows from 11 distinct events.
- **Omitted:** dispatch, delivery confirmation and all payments. Six events reach no Order.
- **Likely DFG edges:** Create OrderAdd Item (2), Add ItemAdd Item (1), Add ItemReserve Stock (2), Reserve StockPack Package (2), Pack PackagePack Package (1), Pack PackageIssue Invoice (2), Issue InvoiceClose Order (2).
- **Misleading:** orders appear to close after invoicing, with no shipment or payment. The PackPack loop looks like rework but is P1 and P2. The copied events double-count Reserve Stock, Pack Package P1 and Issue Invoice in frequencies.

**Package**
- **Shape:** P1 and P2 each give Pack Package  Dispatch Package (one variant, frequency 2).
- **Copied shared events:** none. Each event has one Package, though e07 hides a two-Order mix.
- **Omitted:** Orders, Items, reservation, delivery confirmation, invoice and payments.
- **DFG edge:** Pack PackageDispatch Package (2).
- **Misleading:** packaging looks simple and homogeneous. The fact that P1 combines two Orders is invisible.

**Delivery**
- **Shape:** D1 and D2 each give Dispatch Package  Confirm Delivery.
- **Copied shared events:** none.
- **Omitted:** packing, content, Orders, billing and payment. D1's confirmation falls on day 1 and D2's on day 2, and flattening drops those timestamps from the structure.
- **DFG edge:** Dispatch PackageConfirm Delivery (2).
- **Misleading:** the two deliveries look identical, although D1 serves two Orders and D2 one.

**Invoice**
- **Shape:** V1 has one case: Issue Invoice  Record Payment  Record Payment.
- **Copied shared events:** none. Issue Invoice links to the two Orders, but only V1 is the case.
- **Omitted:** delivery confirmations (between the payments), Orders, Items, Close Order, and M1 vs M2 identity and amounts.
- **DFG edges:** Issue InvoiceRecord Payment (1), Record PaymentRecord Payment (1).
- **Misleading:** the self-loop looks like repeated or duplicate booking, but it is two distinct partial payments. A single case makes the log skeleton overconfident ("Record Payment always occurs exactly twice").

**Why Payment flattening is especially weak:**
- Each payment case (M1, M2) has exactly one event, Record Payment. The DFG has no edges.
- Start and end activity are both Record Payment, with frequency 2.
- The log skeleton is essentially empty, with no ordering constraints.
- The flattening keeps none of the business story: invoice, orders, deliveries, and the order between M1 and M2. The amounts are event attributes and are not structural.

## 5. Expected object-centric structures

**OC-DFG**
- It has one layer per object type.
- Order layer: Create OrderAdd ItemReserve StockPack PackageIssue InvoiceClose Order, with an Add ItemAdd Item loop and a Pack PackagePack Package edge. The Reserve StockPack Package and Pack PackageIssue Invoice edges carry two Orders.
- Item layer: Add ItemReserve StockPack Package for I1 and I3, and Add ItemPack Package for I2.
- Package layer: Pack PackageDispatch Package.
- Delivery layer: Dispatch PackageConfirm Delivery.
- Invoice layer: Issue InvoiceRecord PaymentRecord Payment (V1, M1, M2).
- Payment layer: isolated Record Payment start/end nodes.
- Shared activities (Pack Package, Dispatch Package, Issue Invoice, Record Payment) connect the layers.
- Edge statistics should show event-pair counts lower than object counts where an event pair is shared. For example, O100 and O200 both traverse e06e07 as one event couple.

**OTG**
- Edges appear between object types that co-occur in events: Order–Item, Item–Package, Package–Delivery, Order–Package, Order–Invoice, Invoice–Payment.
- The result is event-based, so there is no Delivery–Order or Payment–Order edge from E2O alone. O2O paths are ignored.
- Edge labels (lifecycle-style relations) depend on the PM4Py version. Read them with its documentation.

**ET–OT graph**
- It is a bipartite activity/object-type graph with about 16 edges.
- Create Order: Order. Add Item: Order, Item. Reserve Stock: Order, Item. Pack Package: Order, Item, Package. Dispatch Package: Package, Delivery. Issue Invoice: Order, Invoice. Record Payment: Invoice, Payment. Confirm Delivery: Delivery. Close Order: Order.
- Pack Package touching Order, Item and Package marks the convergence point.
- The absence of Dispatch–Order and Payment–Order edges is the signature of the source-direct policy.

**Object-centric Petri net**
- Expect one sub-net per object type, joined through shared visible transitions.
- Variable arcs are plausible for Order and Item at Reserve Stock and Pack Package (an event with several objects of one type). They are also plausible for Order at Issue Invoice.
- Item and Order nets probably show loops or concurrency around Add Item and Pack Package.
- The Invoice net shows Issue Invoice followed by a repeatable Record Payment. The Payment net is trivial.
- The Order net ends Pack Package  Issue Invoice  Close Order, so delivery and payment are not constrained by Orders.
- This is not a unique interpretation. The net depends on E2O policy, the miner and its parameters (for example noise filtering), and the tiny sample. Each case occurs once or twice, so rare loops can be over- or under-generalized.

**Object-interactions summary**
- O100 and O200 co-occur in e06, e07 and e11 (three events) although no O2O link connects them. This is the coupling signal.
- P1 interacts with I1, I3, O100 and O200 in e07, and with D1 in e09.
- V1 interacts with O100, O200, M1 and M2. M1 and M2 never share an event and are related only through V1.
- I1 and I3 co-occur in e06 and e07.
- e07 is the densest event, with 5 objects and 10 pairs. e06 has 4 objects and 6 pairs.
- Columns and shape vary by PM4Py version, so the pandas `pair_cooccurrence` cross-check in the pipeline gives a stable reading.

## 6. Modeling alternatives

| Policy | Definition | Effect on discovery |
|---|---|---|
| **Source-minimal** | Only the objects literally named: Pack Package P1 would link to P1, I1 and I3 (no Orders), Issue Invoice to V1 only, and so on. | Fewer rows (under 35). Order flattening loses its shared events. The Order–Package–Invoice coupling is reachable only via O2O. O100 and O200 look independent in OC-DFG and OTG. |
| **Source-direct with uniform schema (this answer)** | Pack, Reserve and Issue Invoice link to their Orders; dispatch, confirmation and payment stay local. | Convergence is visible for the upstream and invoicing steps. Downstream views stay uncluttered and Order traces end at Close Order. |
| **Full operational involvement** | Every downstream event also links to all related Orders and Items. | Order traces have 14 (O100) and 10 (O200) events. Delivery and payment appear, but events are copied widely and amount attribution duplicates. |
| **O2O-propagated analytical** | Derived links stored separately as `derived_*` (the `ocel_propagated` comparison, 16 extra rows, 51 total). | Order flattening gains Dispatch, Confirm and Record Payment. The OC-DFG and ET–OT gain Order–Delivery and Order–Payment edges. The Order layer mixes observed and inferred steps, so it should be labeled as analytical. |
| **Selective propagation** | For example, Orders only for logistics, never for payments. | It avoids payment double counting while showing shipment on Orders. O200 sees only D1, O100 sees D1 and D2. |

In every policy the business story is unchanged: two Orders, one mixed Package, two partial payments. Only the observable event–object links differ.

## 7. Failure modes

1. **Relation inflation:** full propagation grows relations from 35 to 51 in this tiny example. At scale it grows roughly with the product of the object fan-outs.
2. **Missing direct E2O links:** Dispatch, Confirm and Payment are invisible to Order and Item flattenings. They produce Order traces that end at Close Order without shipment or payment.
3. **Treating O2O propagation as observation:** a derived Order–Payment link is an inference. Reporting it as a source fact misstates what the system recorded.
4. **Duplicate shared events after flattening:** e06, e07 and e11 are counted twice in Order flattening. Frequencies, throughput and performance statistics are inflated.
5. **Ambiguous payment allocation:** 100 and 150 cannot be attributed to O100 or O200 from the data. Propagation to both gives 500 against the true 250.
6. **Overly short Payment traces:** Payment-flattened cases have one event. The DFG has no edges, and the skeleton is degenerate or fails.
7. **Loop misreading in Invoice:** Record PaymentRecord Payment looks like duplicate booking or rework, but it is two legitimate partial payments.
8. **Divergence under Order flattening:** O100 has two Add Item and two Pack Package events, so the flattened DFG cannot tell which Item or Package they concern.
9. **Constructor/API version mismatch:** `OCEL(..., o2o=...)` may not exist, and function return types change. The fix is isolated in `make_ocel` by assigning `ocel.o2o` afterwards, and the output printing is generic.
10. **False total order for same-time events:** this example has no timestamp ties. With ties (for example a pack and a dispatch at the same minute), flattened traces would get an arbitrary order that looks like causality. The validator asserts uniqueness here so the property is explicit.
11. **Inconsistent per-instance schemas:** linking P1's Pack to Orders but not P2's would make the Package and Order views depend on the instance. The uniform schema avoids this but includes one inferred link, e08 to O100.
12. **Qualifier drift:** mixing qualifier spellings breaks qualifier-sensitive analysis. The validator enforces the vocabulary.

## 8. Final semantic checks

A reviewer can verify these in the generated tables:

1. `events` has 17 unique `ocel:eid` values (e01–e17), timestamps are tz-aware UTC and strictly increasing, and `amount` is non-null only on the two Record Payment events (100.0 and 150.0, sum 250).
2. `objects` has 12 unique IDs: Order 2, Item 3, Package 2, Delivery 2, Invoice 1, Payment 2.
3. `relations` has 35 rows and no duplicate `(eid, oid, qualifier)`. The `ocel:activity` and `ocel:timestamp` of each row equal those of its event.
4. e06 relates exactly to I1, I3, O100 and O200. e07 relates to P1, I1, I3, O100 and O200. e11 relates to V1, O100 and O200.
5. e09 relates only to P1 and D1. e12 relates only to M1 and V1. e15 relates only to M2 and V1. No base relation links Dispatch, Confirm Delivery or Record Payment to an Order or Item.
6. `o2o` has 12 rows with the expected directions: O100 contains I1, I2; O200 contains I3; P1 packs I1, I3; P2 packs I2; D1 carries P1; D2 carries P2; V1 bills O100, O200; M1 partially_settles V1; M2 completes_settlement V1.
7. Order flattening gives 14 rows over 2 cases (O100 with 8 events, O200 with 6). Package flattening gives two identical PackDispatch traces. Delivery flattening gives two DispatchConfirm traces. Invoice flattening gives one 3-event case.
8. `derived_relations` has 16 rows, all with `derived_*` qualifiers and an `analytic:derivation` value, and none appears in `relations`. Only `ocel_propagated` contains them.
9. No event has a timestamp tie, and payment amounts appear only as event attributes, never as objects.
