# Object-Centric Execution Clustering Analysis

## 1. Equivalence Design Space

### 1.1 Activity-Sequence Equivalence (ASE)

**Definition**: Two executions are ASE-equivalent if their sequences of activity labels (ignoring all object information) are identical.

**Invariants preserved**:
- Activity label sequence
- Activity count per label

**Information discarded**:
- Object types and identifiers
- Object multiplicities
- External object references
- O2O qualifiers
- Event-to-object relationships

**Properties**:
- Reflexive: Yes
- Symmetric: Yes
- Transitive: Yes

**Concurrency handling**: Treats concurrent events as ordered by their timestamp (total order).

### 1.2 Typed Structural Equivalence under Identifier Renaming (TSE)

**Definition**: Two executions are TSE-equivalent if there exists a bijective renaming of local object identifiers that makes:
1. The sequence of activity labels identical
2. The object types and multiplicities per event identical
3. The O2O topology identical (ignoring qualifiers)

**Invariants preserved**:
- Activity label sequence
- Object types per event
- Object multiplicities per event
- O2O topology (which objects relate to which others)
- External object flags

**Information discarded**:
- Specific local identifiers
- O2O qualifiers
- Exact timing information
- Payment amounts (treated as structure)

**Properties**:
- Reflexive: Yes
- Symmetric: Yes
- Transitive: Yes

**Concurrency handling**: Maintains total order of events but ignores timing differences.

### 1.3 Business-Semantic Equivalence (BSE)

**Definition**: Two executions are BSE-equivalent if they represent the same business process variant considering:
1. Activity sequence
2. Object multiplicities
3. External object sharing patterns
4. Key O2O qualifiers (e.g., item replacement, returns)
5. Payment structure (single vs. multiple payments)

**Invariants preserved**:
- Core activity sequence
- Object multiplicities per activity
- External object sharing patterns
- Key business semantics (returns, replacements)
- Payment structure

**Information discarded**:
- Local identifiers
- Exact timing
- Minor ordering variations (e.g., Add Item order)
- Some O2O qualifiers not affecting business semantics

**Properties**:
- Reflexive: Yes
- Symmetric: Yes
- Transitive: Yes

**Concurrency handling**: Treats some ordering variations as equivalent (e.g., Add Item order).

### 1.4 Qualified Structural Equivalence (QSE) - Additional Relation

**Definition**: Two executions are QSE-equivalent if they are TSE-equivalent and additionally preserve all O2O qualifiers.

**Invariants preserved**:
- All TSE invariants
- O2O qualifiers (e.g., "removed_before_dispatch")

**Information discarded**:
- Local identifiers
- Exact timing

**Properties**:
- Reflexive: Yes
- Symmetric: Yes
- Transitive: Yes

## 2. Canonical Signatures

For BSE (preferred semantic equivalence), we define the following canonical signature:

```python
def get_bse_signature(execution):
    # Step 1: Extract activity sequence with object type counts
    activity_seq = []
    for event in execution.events:
        # Count objects by type, distinguishing external objects
        obj_counts = {}
        for obj_type, obj_ids in event.objects.items():
            # Count local and external objects separately
            local_count = sum(1 for oid in obj_ids if not oid.startswith('EXT'))
            ext_count = len(obj_ids) - local_count
            if local_count > 0:
                obj_counts[f"{obj_type}_local"] = local_count
            if ext_count > 0:
                obj_counts[f"{obj_type}_ext"] = ext_count

        # Create activity signature with sorted object counts
        sorted_counts = sorted(obj_counts.items())
        activity_sig = (event.activity, tuple(sorted_counts))
        activity_seq.append(activity_sig)

    # Step 2: Add key business semantics markers
    markers = []

    # Check for item replacement (X7 pattern)
    has_replacement = any(
        event.activity == "Dispatch" and
        "Item" in event.objects and
        any(qualifier == "removed_before_dispatch"
            for obj in event.objects["Item"]
            for qualifier in get_qualifiers(obj))
        for event in execution.events
    )
    markers.append(("has_replacement", has_replacement))

    # Check for returns (X8 pattern)
    has_return = any(event.activity == "Return Item" for event in execution.events)
    markers.append(("has_return", has_return))

    # Check for split deliveries (X4 pattern)
    delivery_events = [e for e in execution.events if e.activity == "Dispatch"]
    has_split_deliveries = len(delivery_events) > 1
    markers.append(("has_split_deliveries", has_split_deliveries))

    # Check for cross-order package sharing (X5 pattern)
    has_cross_order_package = any(
        "Package" in event.objects and
        any(oid.startswith("EXT") for oid in event.objects["Package"])
        for event in execution.events
    )
    markers.append(("has_cross_order_package", has_cross_order_package))

    # Check for cross-order invoice sharing (X6 pattern)
    has_cross_order_invoice = any(
        "Invoice" in event.objects and
        any(oid.startswith("EXT") for oid in event.objects["Order"])
        for event in execution.events if event.activity == "Issue Invoice"
    )
    markers.append(("has_cross_order_invoice", has_cross_order_invoice))

    # Check for multiple payments (X4 pattern)
    payment_events = [e for e in execution.events if e.activity == "Record Payment"]
    has_multiple_payments = len(payment_events) > 1
    markers.append(("has_multiple_payments", has_multiple_payments))

    # Step 3: Combine into final signature
    signature = {
        "activity_sequence": tuple(activity_seq),
        "markers": tuple(markers)
    }

    return signature
```

## 4. Cluster Interpretations

### Cluster A: Baseline Single-Package Execution
**Signature**: Single package, single delivery, single payment, no external sharing, no returns/replacements
**Business behavior**: Standard order fulfillment with all items packed together and delivered in one shipment.
**Risks/Opportunities**:
- Risk: Single point of failure in delivery
- Opportunity: Simplified logistics and tracking
**Poor representation**: Traditional process mining would flatten this to a simple sequence, losing the object relationships.
**Stability**: Highly stable - unlikely to change under data repair.

### Cluster B: Split Packages, Consolidated Delivery
**Signature**: Multiple packages, single delivery, single payment
**Business behavior**: Items packed separately (perhaps due to size/weight constraints) but delivered together.
**Risks/Opportunities**:
- Risk: Higher packaging costs
- Opportunity: Better inventory management for different item types
**Poor representation**: Flattened models would show multiple Pack events but lose the consolidated delivery aspect.
**Stability**: Stable - package splitting is a clear operational decision.

### Cluster C: Split Deliveries, Partial Payment
**Signature**: Multiple packages, multiple deliveries, multiple payments
**Business behavior**: Items delivered separately (perhaps due to availability or location constraints) with separate payment processing.
**Risks/Opportunities**:
- Risk: Higher delivery costs, complex payment reconciliation
- Opportunity: Faster delivery for available items
**Poor representation**: Traditional models would show separate cases, losing the order-level connection.
**Stability**: Moderately stable - payment splitting might be adjusted in data repair.

### Cluster D: Cross-Order Package Sharing
**Signature**: Single package containing items from multiple orders
**Business behavior**: Logistics optimization where items from different orders are packed together for efficiency.
**Risks/Opportunities**:
- Risk: Complex tracking, potential for mix-ups
- Opportunity: Reduced shipping costs
**Poor representation**: Flattened models would show only the local order's perspective.
**Stability**: Moderately stable - external object references might be removed in repair.

### Cluster E: Cross-Order Invoice Sharing
**Signature**: Single invoice covering multiple orders
**Business behavior**: Financial consolidation where multiple orders are billed together.
**Risks/Opportunities**:
- Risk: Complex payment allocation, potential accounting issues
- Opportunity: Simplified billing for related orders
**Poor representation**: Traditional models would show only the local order's financials.
**Stability**: Moderately stable - financial sharing might be adjusted in repair.

### Cluster F: Item Replacement
**Signature**: Item replacement hidden in structure
**Business behavior**: One item was replaced (perhaps due to stock issues) but the replacement was packed in the same package.
**Risks/Opportunities**:
- Risk: Customer dissatisfaction if not communicated
- Opportunity: Maintain order fulfillment despite stock issues
**Poor representation**: Flattened models would miss the replacement semantics.
**Stability**: Less stable - qualifiers might be lost in data repair.

### Cluster G: Return and Repack
**Signature**: Item return followed by repacking and redelivery
**Business behavior**: Standard return process where a returned item is inspected and reshipped.
**Risks/Opportunities**:
- Risk: Higher operational costs, potential for lost items
- Opportunity: Customer satisfaction through flexible return policies
**Poor representation**: Traditional models would show this as two separate cases.
**Stability**: Highly stable - return process is a clear operational pattern.

## 6. Relation to pm4py.cluster_equivalent_ocel

PM4Py's `cluster_equivalent_ocel` preserves:
1. Exact object identifiers (including external ones)
2. Complete O2O topology with all qualifiers
3. Event order and timing
4. All object types and their relationships

**Why raw identifiers make clusters too fine**:
- Local identifiers (O1, O2, etc.) are treated as distinct, creating separate clusters for what are essentially identical executions (like X1 and X2)
- External identifiers create artificial distinctions between executions that share the same business pattern

**Canonicalization approach**:

```python
import pm4py
from collections import defaultdict

def cluster_ocel_executions(ocel, lead_object_type="Order"):
    # Step 1: Get exact clusters from PM4Py
    exact_clusters = pm4py.cluster_equivalent_ocel(ocel)

    # Step 2: Canonicalize by removing local identifiers and preserving structure
    canonical_clusters = defaultdict(list)

    for cluster_id, executions in exact_clusters.items():
        for execution in executions:
            # Create canonical signature
            signature = get_bse_signature(execution)  # Using our BSE signature function

            # Use signature as new cluster key
            canonical_clusters[signature].append(execution)

    # Step 3: Post-process to merge similar clusters
    # (Optional step to handle near-equivalent cases)
    final_clusters = merge_similar_clusters(canonical_clusters)

    return final_clusters

def merge_similar_clusters(clusters):
    # Implement logic to merge clusters that differ only in minor ways
    # For example, clusters that differ only in Add Item order
    merged = {}
    for sig, execs in clusters.items():
        # Create a simplified signature that ignores Add Item order
        simplified_sig = simplify_signature(sig)
        if simplified_sig not in merged:
            merged[simplified_sig] = []
        merged[simplified_sig].extend(execs)
    return merged

def simplify_signature(signature):
    # Create a version that ignores Add Item order
    simplified_activities = []
    for activity, counts in signature["activity_sequence"]:
        if activity == "Add Item":
            # Sort the counts to make order irrelevant
            sorted_counts = tuple(sorted(counts))
            simplified_activities.append(("Add Item", sorted_counts))
        else:
            simplified_activities.append((activity, counts))

    return {
        "activity_sequence": tuple(simplified_activities),
        "markers": signature["markers"]
    }
```

**When exact equivalence is preferable**:
1. For compliance monitoring where exact object references matter
2. For debugging specific execution instances
3. When external object relationships are critical to the analysis

**When coarser clustering is better**:
1. For process discovery and variant analysis
2. For operational segmentation where business patterns matter more than exact identifiers
3. For performance analysis where we care about process variants rather than individual cases

**Impact of max_objs or large executions**:
- With many objects, exact clustering becomes computationally expensive
- Large connected executions may span multiple business processes, making exact clustering less meaningful
- The canonicalization step becomes more important to reduce the cluster space

## 7. Robustness Analysis

### Perturbation 1: Ignore all O2O qualifiers
**Impact**:
- X7 (item replacement) would move from cluster F to cluster A
- X8 (return process) would lose some of its distinctive return semantics
- Overall, clusters would become coarser, merging some business-semantic distinctions

### Perturbation 2: Ignore external objects
**Impact**:
- X5 (cross-order package) would move from cluster D to cluster A
- X6 (cross-order invoice) would move from cluster E to cluster A
- All clusters would become more focused on local order processing

### Perturbation 3: Collapse repeated same-label events
**Impact**:
- Minimal impact on these executions since there are no repeated same-label events
- In general, would merge cases where the same activity occurs multiple times in sequence

### Perturbation 4: Treat Pack and Dispatch as partial order
**Impact**:
- X3 and X4 might become more similar as the exact ordering of Pack events becomes less important
- Would generally make clusters coarser by ignoring some ordering constraints

### Perturbation 5: Treat payment multiplicity as amount attribute
**Impact**:
- X4 (multiple payments) would move from cluster C to cluster A
- Payment structure would become less important in clustering
- Financial aspects of the process would be less visible in the clustering

## 8. Limitations and Recommendation

**Recommendation by purpose**:

1. **Compliance monitoring**: Use Qualified Structural Equivalence (QSE)
   - *Why*: Compliance often requires exact adherence to process rules, including all qualifiers and object relationships. The strictness of QSE ensures no compliance-relevant details are lost.

2. **Operational segmentation**: Use Business-Semantic Equivalence (BSE)
   - *Why*: Operational decisions benefit from seeing business patterns rather than exact structures. BSE captures the meaningful variations in how orders are fulfilled while ignoring minor differences.

3. **Root-cause analysis**: Use Typed Structural Equivalence (TSE)
   - *Why*: Root-cause analysis often needs to examine structural patterns without getting lost in exact identifiers. TSE provides a good balance between structural detail and abstraction.

4. **Descriptive reporting**: Use Activity-Sequence Equivalence (ASE)
   - *Why*: For high-level reporting, the sequence of activities is often sufficient. ASE provides the simplest view that still captures the main process flow.

**Why no single equivalence is best**:
- **Compliance** requires strict adherence to rules, making coarser equivalences inappropriate
- **Operational segmentation** benefits from seeing business patterns rather than exact structures
- **Root-cause analysis** needs structural detail but not exact identifiers
- **Descriptive reporting** requires simplicity and abstraction

The fundamental tension is between:
1. **Precision** (needed for compliance and debugging)
2. **Abstraction** (needed for pattern recognition and reporting)
3. **Business semantics** (needed for operational decision making)

Different purposes require different levels of detail, making multiple equivalence notions necessary for a comprehensive object-centric process analysis.
