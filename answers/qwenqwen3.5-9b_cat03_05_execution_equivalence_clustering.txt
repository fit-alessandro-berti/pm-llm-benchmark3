## 1. Equivalence design space

To cluster object-centric executions meaningfully, we must define relations that distinguish between superficial variations (like identifier renaming) and substantive business differences (like split shipments). We define three primary equivalence relations.

**1. Activity-sequence equivalence (`~_act`)**
*   **Definition:** Two executions are equivalent if their event sequences are identical in terms of Activity Type and the multiset of Object Types participating in each event. Timestamps and local identifiers are ignored.
*   **Invariants:** Event order, object type participation counts.
*   **Discarded:** Local object IDs, specific object types beyond the broad category (e.g., distinguishing `Order` from `Order`), qualifiers.
*   **Properties:** Reflexive, Symmetric, Transitive (Equivalence Relation).
*   **Concurrency:** Events occurring at the same timestamp are treated as unordered; the sequence is a partial order on types.

**2. Typed structural equivalence (`~_struct`)**
*   **Definition:** Executions are equivalent if their event-object graphs are isomorphic under a type-preserving mapping of identifiers. This preserves the topology of participation (who is in what) and object counts but ignores specific IDs.
*   **Invariants:** Graph topology, object type, object multiplicity, event type.
*   **Discarded:** Local IDs, specific values of attributes.
*   **Properties:** Reflexive, Symmetric, Transitive (Equivalence Relation).
*   **Concurrency:** Preserved via the partial order of event timestamps mapped to the graph.

**3. Business-semantic equivalence (`~_bus`)**
*   **Definition:** Builds on `~_struct` but incorporates O2O qualifiers (e.g., `removed_before_dispatch`), external object flags (`EXT-*`), and lifecycle motifs (e.g., returns, splits). It treats executions as equivalent only if they share the same business pattern, even if the graph topology differs slightly (e.g., split delivery).
*   **Invariants:** Business motifs, external dependencies, qualifiers, lifecycle phases.
*   **Discarded:** Minor structural variations that do not impact business outcome (e.g., item add order).
*   **Properties:** Reflexive and Symmetric. Transitivity is approximate (e.g., A is a return, B is a return, A and B are equivalent).
*   **Concurrency:** Treated via causal chains implied by qualifiers.

## 2. Canonical signatures

To ensure reproducibility, we define a canonical signature generator. This function normalizes an execution log into a hashable tuple, invariant to local identifiers but sensitive to structural and semantic distinctions.

```python
def canonicalize_execution(events, lead_type='Order'):
    """
    events: List of dicts { 'type': str, 'objects': {obj_id: obj_type, ...}, 'qualifiers': {...} }
    lead_type: Type of the root object (e.g., 'Order')
    """
    # 1. Normalize identifiers: Map local IDs to 0, 1, 2... based on type and order of appearance
    id_map = {}
    next_id = {t: 0 for t in set() for t in ['Order', 'Item', 'Package', 'Invoice', 'Payment', 'Delivery', 'EXT']}
    
    # 2. Track object types and multiplicities
    obj_types = {}
    
    signature_parts = []
    
    for ev in events:
        ev_type = ev['type']
        objs = ev['objects']
        qualifiers = ev.get('qualifiers', {})
        
        # Normalize object IDs to type-based integers
        norm_objs = []
        for obj_id, obj_type in objs.items():
            type_key = f"{obj_type}:{obj_id}"
            if type_key not in id_map:
                id_map[type_key] = next_id[obj_type]
                next_id[obj_type] += 1
            norm_objs.append(id_map[type_key])
        
        # Detect externality
        is_external = any('EXT' in str(k) for k in objs.keys())
        
        # Capture qualifiers
        qual_str = '|'.join(f"{q}:{v}" for q, v in qualifiers.items()) if qualifiers else ""
        
        signature_parts.append(f"{ev_type}|{','.join(map(str, norm_objs))}|{is_external}|{qual_str}")
        
        # Update multiplicities for structural signature
        for obj_type in objs.values():
            obj_types[obj_type] = obj_types.get(obj_type, 0) + 1
            
    # Structural signature includes type counts
    struct_sig = frozenset(obj_types.items())
    
    # Return tuple of (event_sequence, structural_counts)
    return (tuple(signature_parts), struct_sig)
```

## 4. Cluster interpretations

**Cluster 1: Standard Fulfillment (X1, X2)**
*   **Signature:** `Create -> Add -> Pack -> Dispatch -> Invoice -> Pay`.
*   **Behavior:** Linear, closed-loop transaction.
*   **Risk:** Assumes completeness; does not capture partial fulfillment or returns.
*   **Flattening:** Traditional flattening handles this well.
*   **Stability:** High; robust to minor event ordering changes.

**Cluster 2: Split Logistics (X3, X4)**
*   **Signature:** `Pack` count > 1; `Delivery` count > 1 (in X4).
*   **Behavior:** Inventory is fragmented across shipments or deliveries.
*   **Risk:** Inventory tracking complexity; higher shipping costs.
*   **Flattening:** Often merged incorrectly into single shipment.
*   **Stability:** Moderate; depends on how delivery events are aggregated.

**Cluster 3: Cross-Boundary (X5, X6)**
*   **Signature:** Presence of `EXT-*` objects in `Pack` or `Invoice`.
*   **Behavior:** Order participates in a shared logistical or financial context.
*   **Risk:** Liability allocation ambiguity; unclear ownership of costs.
*   **Flattening:** Poorly represented if external objects are dropped.
*   **Stability:** High; external flags are stable indicators.

**Cluster 4: Lifecycle Modification (X7, X8)**
*   **Signature:** Presence of qualifiers (`removed_before_dispatch`) or new activities (`Return Item`).
*   **Behavior:** The order state is altered during or after the process.
*   **Risk:** Data integrity issues; hidden state changes.
*   **Flattening:** Often lost if only final state is stored.
*   **Stability:** Low; requires strict audit of qualifiers.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

PM4Py's `cluster_equivalent_ocel` uses object-centric equivalence based on the key structure (events, objects, relations). It preserves the exact object identifiers by default. This makes clusters too fine-grained for business analysis, as X1 and X2 would be separate.

To use this effectively:
1.  **Canonicalize:** Pre-process OCEL to normalize IDs (e.g., `Order_001` -> `Order_0`).
2.  **Post-process:** Aggregate clusters that differ only in ID mapping.
3.  **Lead Object:** Filter the OCEL to ensure the `Order` object is the root.

```python
import pm4py
from pm4py.objects.ocel import OcelLog

def cluster_semantic(ocel_log):
    # 1. Canonicalize OCEL to normalize IDs
    # (Custom step to map IDs to types)
    canonical_ocel = normalize_ids(ocel_log)
    
    # 2. Run PM4Py clustering
    clusters = pm4py.cluster_equivalent_ocel(canonical_ocel)
    
    # 3. Post-process: Group by semantic motifs
    # (e.g., check for EXT flags or Return activities)
    semantic_clusters = {}
    for c in clusters:
        motif = get_motif(c)
        semantic_clusters.setdefault(motif, []).append(c)
        
    return semantic_clusters
```

Exact equivalence is preferable for debugging data pipelines. Coarser business clustering is preferable for KPIs and compliance. Large connected executions (e.g., X5 with EXT objects) may cause `max_objs` limits in PM4Py, requiring splitting the log or increasing memory limits.

## 7. Robustness analysis

We evaluate how assignments change under perturbations:

1.  **Ignore O2O qualifiers:** X7 would merge into Cluster 1 (Standard). This is dangerous as it hides substitution.
2.  **Ignore external objects:** X5 and X6 would merge into Cluster 1. This hides cross-order dependencies, leading to incorrect cost allocation.
3.  **Collapse repeated same-label events:** X3 (2 Packs) and X4 (2 Disps) would look like X1. This destroys the Split Logistics distinction.
4.  **Partial order for Pack/Dispatch:** If Pack/Dispatch order is ignored, X8 might look like X1 (if Return is ignored). This loses the Return semantics.
5.  **Payment as amount:** If X4's multiple payments are treated as an attribute sum, it merges into Cluster 1. This loses the partial settlement logic.

These perturbations show that strict structural equivalence is fragile. Business semantics requires preserving attributes like qualifiers and external flags.

## 8. Limitations and recommendation

**Limitations:**
No single equivalence notion is best for all purposes. Activity-sequence is too coarse for compliance (misses qualifiers). Typed-structural is too fine for reporting (misses business motifs). Business-semantic requires manual definition of motifs, which may vary by domain.

**Recommendations:**
*   **Compliance Monitoring:** Use **Typed-Structural Equivalence**. It ensures all required steps (Invoice, Payment) occurred without missing IDs, suitable for audit logs.
*   **Operational Segmentation:** Use **Business-Semantic Equivalence**. It groups work by process type (e.g., "Returns" vs "New Orders"), enabling resource allocation.
*   **Root-Cause Analysis:** Use **Activity-Sequence Equivalence**. It preserves exact event order and counts, allowing traceback of specific failures.
*   **Descriptive Reporting:** Use **Business-Semantic Equivalence**. It provides high-level counts of process variants (e.g., "10% of orders are split"), which is actionable for stakeholders.

We recommend a hybrid approach: Use Typed-Structural for data integrity checks and Business-Semantic for KPI aggregation. This balances the need for precision with the need for business relevance.
