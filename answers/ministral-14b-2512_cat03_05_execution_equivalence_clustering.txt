# **Object-Centric Execution Clustering for Order Processing**

This analysis defines equivalence relations, clusters executions X1–X8, and interprets business semantics while addressing borderline cases and robustness.

---

## **1. Equivalence Design Space**

### **1. Activity-Sequence Equivalence**
**Definition:** Two executions are equivalent if their sequences of event labels (ignoring object IDs) are identical, including the order of events.

**Invariants Preserved:**
- Event label sequence (e.g., `Create Order  Add Item  ...`).
- Relative ordering of events (e.g., `Pack Package` must precede `Dispatch`).

**Information Discarded:**
- Object identifiers (e.g., `O1` vs. `O2`).
- Object multiplicities (e.g., one vs. two `Add Item` events).
- External references (`EXT-OA`).
- O2O qualifiers (e.g., `removed_before_dispatch`).

**Properties:**
- Reflexive, symmetric, transitive.
- Concurrency: If two events occur at the same timestamp, their order is undefined (treated as unordered).

**Example:**
- X1 and X2 are equivalent under this relation (same labels, same order).
- X1 and X7 are **not** equivalent (X7 has `Return Item` and `Inspect Return`).

---

### **2. Typed Structural Equivalence (Under Identifier Renaming)**
**Definition:** Two executions are equivalent if their event sequences can be aligned via a bijection on object IDs, preserving:
- Event labels.
- Object types (e.g., `Order`, `Item`).
- Incidence relations (e.g., `Order:O1`  `Item:I11`).
- Event order (total or partial).

**Invariants Preserved:**
- Event label sequence.
- Object type multiplicities (e.g., one `Order`, two `Item`s).
- Event-to-object incidence (e.g., `Pack Package` must involve the same number of `Item`s).
- Event order (if total).

**Information Discarded:**
- External references (`EXT-*`).
- O2O qualifiers (e.g., `removed_before_dispatch`).
- Payment multiplicity (e.g., one vs. two `Record Payment`).

**Properties:**
- Reflexive, symmetric, transitive.
- Concurrency: If two events are concurrent, their order is ignored (treated as unordered).

**Example:**
- X1 and X2 are equivalent (same structure, just renamed IDs).
- X1 and X3 are **not** equivalent (X3 has two `Pack Package` events).
- X1 and X5 are **not** equivalent (X5 involves `EXT-OA`).

---

### **3. Business-Semantic Equivalence**
**Definition:** Two executions are equivalent if they represent the same **business workflow** despite structural differences, considering:
- **Multiplicities:** Number of `Add Item`, `Pack Package`, `Record Payment`.
- **Shared External Objects:** Cross-order dependencies (`EXT-*`).
- **O2O Qualifiers:** Special relations (e.g., `removed_before_dispatch`).
- **Lifecycle Motifs:** Patterns like "split packages," "returns," or "replacements."

**Invariants Preserved:**
- **Core workflow:** `Create Order  Add Items  Pack  Dispatch  Invoice  Payment`.
- **Logistics structure:** Single package vs. split packages.
- **Financial structure:** Single invoice vs. shared invoice.
- **Item lifecycle:** Replacements, returns, or substitutions.

**Information Discarded:**
- Exact object IDs (unless external).
- Event timestamps (unless critical for ordering).
- Payment amounts (only multiplicity matters).

**Properties:**
- Reflexive, symmetric, transitive.
- Concurrency: If two events are concurrent, their order is ignored.

**Example:**
- X1 and X2 are equivalent (same workflow, no external objects).
- X3 and X4 are **not** equivalent (X4 has split deliveries and partial payments).
- X7 and X1 are **not** equivalent (X7 involves a replacement).

---

### **4. (Optional) Behavioral Equivalence (Partial Order + Qualifiers)**
**Definition:** Two executions are equivalent if their **partial order of events** (ignoring timestamps) and **O2O qualifiers** match, even if object IDs differ.

**Invariants Preserved:**
- Event label sequence (partial order).
- O2O qualifiers (e.g., `removed_before_dispatch`).
- External object flags (`EXT-*`).

**Information Discarded:**
- Exact event timestamps.
- Object IDs (unless external).

**Example:**
- X1 and X7 are **not** equivalent (X7 has a `removed_before_dispatch` qualifier).
- X5 and X6 are **not** equivalent (X5 shares logistics, X6 shares finance).

## **2. Canonical Signatures**
We use **business-semantic equivalence** for clustering. The signature is a tuple:

```python
def canonical_signature(execution):
    # Step 1: Extract event labels in order (ignoring IDs)
    labels = [event.label for event in execution.events]

    # Step 2: Count multiplicities of key events
    counts = {
        "Add Item": sum(1 for e in execution.events if e.label == "Add Item"),
        "Pack Package": sum(1 for e in execution.events if e.label == "Pack Package"),
        "Dispatch": sum(1 for e in execution.events if e.label == "Dispatch"),
        "Record Payment": sum(1 for e in execution.events if e.label == "Record Payment"),
    }

    # Step 3: Check for external objects or qualifiers
    has_external = any("EXT-" in obj_id for event in execution.events for obj_id in event.objects)
    has_qualifiers = any("removed_before_dispatch" in event.qualifiers for event in execution.events)

    # Step 4: Check logistics structure (single vs. split packages)
    pack_events = [e for e in execution.events if e.label == "Pack Package"]
    dispatch_events = [e for e in execution.events if e.label == "Dispatch"]

    if len(pack_events) == 1 and len(dispatch_events) == 1:
        logistics = "single_package"
    elif len(pack_events) > 1 and len(dispatch_events) == 1:
        logistics = "split_packages_consolidated"
    elif len(pack_events) > 1 and len(dispatch_events) > 1:
        logistics = "split_packages_split_deliveries"
    else:
        logistics = "other"

    # Step 5: Check financial structure (single vs. shared invoice)
    invoice_events = [e for e in execution.events if e.label == "Issue Invoice"]
    if len(invoice_events) == 1 and not has_external:
        financial = "single_invoice"
    elif len(invoice_events) == 1 and has_external:
        financial = "shared_invoice"
    else:
        financial = "other"

    # Step 6: Check for replacements/returns
    has_replacement = any("removed_before_dispatch" in e.qualifiers for e in execution.events)
    has_return = any(e.label == "Return Item" for e in execution.events)

    return (
        tuple(labels),
        counts,
        has_external,
        has_qualifiers,
        logistics,
        financial,
        has_replacement,
        has_return,
    )
```

**Example Outputs:**
- X1  `(..., {"Add Item": 2, "Pack Package": 1, ...}, False, False, "single_package", "single_invoice", False, False)`
- X7  `(..., {"Add Item": 2, "Pack Package": 1, ...}, False, True, "single_package", "single_invoice", True, False)`
- X5  `(..., {"Add Item": 2, "Pack Package": 1, ...}, True, False, "single_package", "single_invoice", False, False)`

## **4. Cluster Interpretations**

### **Baseline (X1, X2, X7)**
**Signature:** `(..., 2 Add Items, 1 Pack, 1 Dispatch, 1 Invoice, 1 Payment, no EXT, no qualifiers)`
**Behavior:**
- Standard order processing: items added, packed, dispatched, invoiced, paid.
- X7 is a borderline case where an item is replaced but the structure remains identical.

**Risks/Opportunities:**
- **Risk:** Hidden replacements (X7) may indicate quality issues.
- **Opportunity:** Can be used as a reference for compliance.

**Flattening Issues:**
- Flattening would lose the `removed_before_dispatch` qualifier in X7, making it indistinguishable from X1.

**Stability:**
- Stable under minor data repairs (e.g., renaming IDs).

---

### **Split Packages (X3)**
**Signature:** `(..., 2 Packs, 1 Dispatch, 1 Invoice, 1 Payment)`
**Behavior:**
- Order split into two packages, but delivered together.
- Logistics efficiency: fewer deliveries.

**Risks/Opportunities:**
- **Risk:** If packages are lost separately, partial fulfillment occurs.
- **Opportunity:** Can optimize warehouse space by splitting.

**Flattening Issues:**
- Flattening would merge packages, losing split-logistics semantics.

**Stability:**
- Stable unless dispatch events are misordered.

---

### **Split Deliveries (X4)**
**Signature:** `(..., 2 Packs, 2 Dispatches, 2 Payments)`
**Behavior:**
- Order split into two packages, each with its own delivery.
- Partial payments allowed (e.g., first package paid in full, second later).

**Risks/Opportunities:**
- **Risk:** Payment mismanagement (e.g., overpaying for one package).
- **Opportunity:** Flexible financing for large orders.

**Flattening Issues:**
- Flattening would obscure partial payment logic.

**Stability:**
- Stable unless payment events are misordered.

---

### **Cross-Order Logistics (X5)**
**Signature:** `(..., 1 Pack, EXT-OA)`
**Behavior:**
- Package shares items with another order (`EXT-OA`).
- Logistics execution is not isolated.

**Risks/Opportunities:**
- **Risk:** If `EXT-OA` fails, both orders are affected.
- **Opportunity:** Cost savings via shared shipments.

**Flattening Issues:**
- Flattening would lose cross-order dependencies.

**Stability:**
- Stable unless external references are dropped.

---

### **Cross-Order Finance (X6)**
**Signature:** `(..., 1 Invoice, EXT-OB)`
**Behavior:**
- Invoice shared with another order (`EXT-OB`).
- Payment settles both orders.

**Risks/Opportunities:**
- **Risk:** Financial auditing becomes complex.
- **Opportunity:** Bulk discounts for shared orders.

**Flattening Issues:**
- Flattening would merge financial records incorrectly.

**Stability:**
- Stable unless external references are ignored.

---

### **Return & Repack (X8)**
**Signature:** `(..., Return Item, Inspect Return, 2 Dispatches)`
**Behavior:**
- Item returned, inspected, and repacked.
- Two dispatch events (original + repackaged).

**Risks/Opportunities:**
- **Risk:** Returned items may be damaged.
- **Opportunity:** Can track repackaging efficiency.

**Flattening Issues:**
- Flattening would lose return/repack logic.

**Stability:**
- Stable unless return events are omitted.

## **5. Borderline Cases**

### **X1 vs. X2**
- **Activity-Sequence:** Equivalent (same labels, same order).
- **Structural:** Equivalent (renamed IDs).
- **Semantic:** Equivalent (no external objects or qualifiers).
**Defensible Disagreement:**
- If we consider **event timestamps** (not in X1/X2), they might differ, but since timestamps are ignored, they are equivalent.

### **X1 vs. X5**
- **Activity-Sequence:** Equivalent (same labels, same order).
- **Structural:** Not equivalent (X5 has `EXT-OA`).
- **Semantic:** Not equivalent (X5 involves cross-order logistics).
**Defensible Disagreement:**
- If we ignore external objects, they become equivalent, but this loses business meaning.

### **X1 vs. X6**
- **Activity-Sequence:** Equivalent (same labels, same order).
- **Structural:** Not equivalent (X6 has `EXT-OB`).
- **Semantic:** Not equivalent (X6 involves shared finance).
**Defensible Disagreement:**
- If we ignore financial sharing, they become equivalent, but this obscures billing risks.

### **X1 vs. X7**
- **Activity-Sequence:** Equivalent (same labels, same order).
- **Structural:** Equivalent (same multiplicities).
- **Semantic:** Not equivalent (X7 has `removed_before_dispatch`).
**Defensible Disagreement:**
- If we ignore O2O qualifiers, they become equivalent, but this hides item replacements.

### **X3 vs. X4**
- **Activity-Sequence:** Not equivalent (X4 has `Record Payment` twice).
- **Structural:** Not equivalent (X4 has two `Dispatch` events).
- **Semantic:** Different (X3: split packages, one delivery; X4: split deliveries, partial payments).
**Defensible Disagreement:**
- If we ignore payment multiplicity, they might be grouped, but this loses financial semantics.

### **X4 vs. X8**
- **Activity-Sequence:** Not equivalent (X8 has `Return Item` and `Inspect Return`).
- **Structural:** Not equivalent (X8 has two `Dispatch` events + return logic).
- **Semantic:** Different (X4: split deliveries; X8: return and repack).
**Defensible Disagreement:**
- If we ignore return events, they might be grouped, but this loses return semantics.

## **6. Relation to `pm4py.cluster_equivalent_ocel`**

### **PM4Py’s Approach**
- Uses **exact object-centric equivalence** (same event labels, same object IDs, same order).
- **Preserves:**
  - Event labels.
  - Object IDs (unless renamed).
  - Event order (total or partial).
- **Discards:**
  - Business semantics (e.g., `EXT-*` or qualifiers).
  - Multiplicities (unless explicitly counted).

### **Why Raw IDs Are Too Fine**
- **Problem:** Two executions with different IDs (e.g., `O1` vs. `O2`) are considered distinct, even if structurally identical.
- **Solution:** Canonicalize IDs (e.g., rename all `Order` IDs to `O`, `Item` IDs to `I1`, `I2`).

### **Post-Processing Steps**
```python
import pm4py

def cluster_and_canonicalize(ocel):
    # Step 1: Use PM4Py for exact clustering
    clusters = pm4py.cluster_equivalent_ocel(ocel, lead_object_type="Order")

    # Step 2: Canonicalize each cluster
    canonical_clusters = {}
    for cluster_id, executions in clusters.items():
        canonical_signatures = []
        for exec in executions:
            sig = canonical_signature(exec)  # From Section 2
            canonical_signatures.append(sig)
        canonical_clusters[cluster_id] = canonical_signatures

    # Step 3: Merge clusters with same canonical signature
    merged_clusters = {}
    for cluster_id, sigs in canonical_clusters.items():
        key = tuple(sorted(sigs))  # Group by signature
        if key not in merged_clusters:
            merged_clusters[key] = []
        merged_clusters[key].extend(sigs)

    return merged_clusters
```

### **When Exact Equivalence is Preferable**
- **Use Case:** Compliance monitoring where exact traces must match.
- **Example:** If a regulation requires exact event ordering, exact clustering is needed.

### **Impact of `max_objs`**
- If `max_objs` is too low, large executions (e.g., orders with 100 items) may be split incorrectly.
- **Solution:** Increase `max_objs` or use a sliding window.

## **7. Robustness Analysis**

| Perturbation | Effect on Clustering |
|--------------|----------------------|
| **Ignore O2O qualifiers** | X1 and X7 merge (lose replacement semantics). |
| **Ignore external objects** | X5 and X6 merge with Baseline (lose cross-order logic). |
| **Collapse repeated events** | X4’s two `Record Payment` events become one (lose partial payment). |
| **Treat Pack/Dispatch as partial order** | X3 and X4 may merge if dispatch order is ignored. |
| **Treat payment multiplicity as amount** | X4’s partial payments may be indistinguishable from full payment. |

**Recommendations:**
- **For compliance:** Use exact clustering (no perturbations).
- **For business analysis:** Use semantic clustering (preserve qualifiers, externals).

---

## **8. Limitations and Recommendation**

### **Recommendations by Use Case**
| Use Case | Recommended Equivalence | Reason |
|----------|-------------------------|--------|
| **Compliance Monitoring** | Exact structural equivalence | Must match regulations exactly. |
| **Operational Segmentation** | Business-semantic equivalence | Groups by workflow patterns. |
| **Root-Cause Analysis** | Behavioral equivalence (with qualifiers) | Captures hidden issues (e.g., replacements). |
| **Descriptive Reporting** | Activity-sequence equivalence | Simple, high-level overview. |

### **Why No Single Best Equivalence Exists**
- **Compliance** needs exact matches.
- **Business analysis** needs semantic grouping.
- **Root-cause analysis** needs qualifiers and externals.
- **Reporting** needs simplicity.

**Final Recommendation:**
- **Default:** Use **business-semantic equivalence** (Section 3) for most analyses.
- **Compliance:** Fall back to **exact structural equivalence**.
- **Advanced diagnostics:** Use **behavioral equivalence** (with qualifiers).

---
**Summary:**
This framework provides a structured way to cluster order executions while balancing technical precision and business meaning. The choice of equivalence depends on the analytical goal, with semantic clustering being the most versatile for operational use.
