**Shared mechanisms.** Where both checks can lawfully start at registration against independent data sources, parallel execution compresses the critical path by roughly min(identity, document) service time and turns serial handoffs into concurrent work; the chain treatment_parallelization  true_overlap  waiting_before_assessment  cycle_time is structurally identical at both sites. Upstream gains reach the end only if downstream capacity absorbs them.

**Site-specific mechanisms.** For 62% of Site B cases the dominant path segment is the external originals wait (median 18h), which already exceeds identity service time (3.4h); identity-under-originals-wait concurrency largely exists, so the marginal mechanism is pre-staged release, not simultaneous execution. Legal review (40%) and the supplement loop are absent at Site A and add a second queue plus a rework cycle. Specialized roles and the legacy case lock mechanically suppress true_overlap, and tolerated back-entry biases its measurement.

**Effect modifiers.** originals_required, digital_documents, case_complexity, role_specialization, IT_case_lock, and the four capacity nodes modify the size and even the sign of the transported effect; queue_huddles and API_latency were co-interventions at Site A, so its historical effect is not identified even internally.

**Why identical diagrams mislead.** Control-flow isomorphism fixes only the ordering alphabet. It says nothing about data guards (originals), resource contention, loop frequencies, or measurement validity. Transportability requires the mechanism arrows above to be invariant; here several are switched off or reversed by Site B's selection differences, so the same diagram supports very different effect sizes.

## 6. Candidate Site B intervention

**Specification**

- **Eligibility.** E1: originals not legally required AND identity data available at registration  full parallel pair (create + execute concurrently). E2: originals required  Identity Check created and started at Register; Document Check task created in `PENDING_ORIGINALS` state, auto-released on the Originals Receipt event. E3: public-sector/high-value  Legal Review unchanged; eligible for pre-staging but excluded from wave-1 concurrency. E4: supplement re-entries bypass re-creation and enter the document queue with priority class.
- **Concurrency.** Identity  originals-wait (all cases); Identity  Document execution only under E1. Never Document execution before Originals Receipt under E2 — enforced by a system guard, not convention.
- **Statutory prerequisites preserved.** Document execution gated on Originals Receipt when required; Assessment gated on completion of both checks; Legal Review before final decision for covered cases.
- **Queue/WIP controls.** Per-reviewer cap of 6 *released* tasks; pending-originals queue uncapped but unpickable; aging alert at 24h; release throttling (max N releases/hour) to protect assessors and legal.
- **Resources.** Identity 4, document 7 + 1 cross-trained floater, assessors 3, legal 2; floater absorbs registration-wave identity surges.
- **Legal/supplement handling.** On Request Supplement: suspend the pair, cache valid outputs, re-enter Document Check with priority, re-assess (same assessor where possible), then Legal Review again.
- **Logging.** Server-side timestamps for created / released / started / completed per task; actor IDs; lock-override and back-entry flags; originals-requested and originals-received events; overlap computed from execution start/end only, never creation.

**POWL-style relation set** ( = enforced precedence;  = unordered/concurrent):

```text
Register  IdentityCheck
Register  XOR(Skip, OriginalsReceipt)          // optional originals branch (Skip iff not required)
XOR(Skip, OriginalsReceipt)  DocumentCheck     // statutory guard
IdentityCheck  XOR(Skip, OriginalsReceipt)     // identity runs during the originals wait
IdentityCheck  Assessment                      // explicit: Assessment waits for identity
DocumentCheck  Assessment                      // explicit: Assessment waits for document
Assessment  Outcome
Outcome = XOR( Seq(XOR(Approve, Reject), Notify),
               Seq( LOOP( LegalReview,
                          Seq(RequestSupplement, DocumentCheckRe, AssessmentRe) ),
                    XOR(Approve, Reject), Notify ) )
```

**Separating mechanism from implementation failure (220 words).** The three arms separate three hypotheses. Arm C reproduces baseline; T2 changes only task creation and pre-staged release; T1 additionally whitelists concurrent ownership. If T1 shows no effect and fidelity metrics show lock overrides rare with achieved overlap near zero, the failure is implementation: the mechanism was never activated; the remedy is IT remediation, not abandonment. If T1 achieves high fidelity — overlap rises, back-entry falls — yet cycle time does not improve, the failure is mechanistic: either the compressed segment was not on the critical path (the originals wait dominates) or the gain was absorbed downstream. These are distinguished by decomposing cycle time into pre-assessment versus assessment/legal segments: absorption appears as reduced waiting before assessment with unchanged end-to-end time, indicting assessor/legal saturation rather than the parallelization mechanism itself. Stratifying by originals-required separates the lawful-concurrency mechanism (digital stratum) from the pre-staging mechanism (originals stratum); if only the digital stratum responds, the statutory gate is confirmed as the binding moderator and transport limits are mapped precisely. Harm signals (rework, appeals, p90) identify adverse mechanisms such as coordination errors or queue saturation. Finally, comparing the estimated moderator gradient against Site A's pattern tests qualitative transportability: matching direction and rough magnitude in the digital stratum supports limited transfer; divergence localizes which mechanism failed to generalize.

## 8. PM4Py model-construction code

```python
"""
Transportability modelling:
  - Site A before/after process trees  -> accepting Petri nets
  - Site B candidate model in POWL     -> accepting Petri net
Requires pm4py >= 2.7.
"""

import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator


def seq(*nodes):
    """Strict partial order enforcing a chain n1 -> n2 -> ... """
    s = StrictPartialOrder(nodes=list(nodes))
    for a, b in zip(nodes, nodes[1:]):
        s.order.add_edge(a, b)
    return s


# ----------------------------------------------------------------------
# 1) Site A before / after process trees
# ----------------------------------------------------------------------
tree_a_before = pm4py.parse_process_tree(
    "-> ( 'Register', 'Identity Check', 'Document Check', 'Assessment', "
    "X ( 'Approve', 'Reject' ), 'Notify' )"
)
tree_a_after = pm4py.parse_process_tree(
    "-> ( 'Register', + ( 'Identity Check', 'Document Check' ), 'Assessment', "
    "X ( 'Approve', 'Reject' ), 'Notify' )"
)

# ----------------------------------------------------------------------
# 2) Convert both to accepting Petri nets
# ----------------------------------------------------------------------
net_a_before, im_a_before, fm_a_before = pm4py.convert_to_petri_net(tree_a_before)
net_a_after, im_a_after, fm_a_after = pm4py.convert_to_petri_net(tree_a_after)
print("Site A before: workflow net =", pm4py.check_is_workflow_net(net_a_before))
print("Site A after : workflow net =", pm4py.check_is_workflow_net(net_a_after))

# ----------------------------------------------------------------------
# 3) Site B candidate model in POWL
# ----------------------------------------------------------------------
register   = Transition(label="Register")
identity   = Transition(label="Identity Check")
document   = Transition(label="Document Check")
originals  = Transition(label="Originals Receipt")
skip       = SilentTransition()                 # originals not legally required
assessment = Transition(label="Assessment")
legal      = Transition(label="Legal Review")
supplement = Transition(label="Request Supplement")
doc_re     = Transition(label="Document Check (re)")
assess_re  = Transition(label="Assessment (re)")
appr_std   = Transition(label="Approve")
rej_std    = Transition(label="Reject")
appr_leg   = Transition(label="Approve")        # separate instance: post-legal path
rej_leg    = Transition(label="Reject")
notif_std  = Transition(label="Notify")
notif_leg  = Transition(label="Notify")

# Optional originals branch: Skip (digital case) OR Originals Receipt.
# NOTE: in reality this choice is data-dependent (attribute guard), which
# plain control-flow POWL cannot express -- see limitations below.
originals_opt = OperatorPOWL(operator=Operator.XOR, children=[skip, originals])

# Legal-review branch with supplement loop:
#   do: Legal Review ; redo: Request Supplement -> Document Check -> Assessment
legal_loop = OperatorPOWL(
    operator=Operator.LOOP,
    children=[StrictPartialOrder(nodes=[legal]),
              seq(supplement, doc_re, assess_re)],
)

dec_std  = OperatorPOWL(operator=Operator.XOR, children=[appr_std, rej_std])
dec_post = OperatorPOWL(operator=Operator.XOR, children=[appr_leg, rej_leg])
outcome  = OperatorPOWL(
    operator=Operator.XOR,
    children=[seq(dec_std, notif_std),
              seq(legal_loop, dec_post, notif_leg)],
)

# Root strict partial order for Site B
root = StrictPartialOrder(
    nodes=[register, identity, originals_opt, document, assessment, outcome]
)
root.order.add_edge(register, identity)
root.order.add_edge(register, originals_opt)
root.order.add_edge(originals_opt, document)   # statutory gate (Skip passes through)
# NOTE: no edge between identity and originals_opt -> they are CONCURRENT,
# i.e., Identity Check proceeds during the originals wait.
# NOTE: no edge between identity and document -> potentially concurrent;
# combined with the originals gate this yields parallel checks exactly when
# originals are not required.

# ----------------------------------------------------------------------
# 4) Explicit edges: Assessment waits for BOTH verifications
# ----------------------------------------------------------------------
root.order.add_edge(identity, assessment)      # explicit dependency on identity
root.order.add_edge(document, assessment)      # explicit dependency on document

# ----------------------------------------------------------------------
# 5) Convert the POWL model to an accepting Petri net
# ----------------------------------------------------------------------
net_b, im_b, fm_b = pm4py.convert_to_petri_net(root)

# ----------------------------------------------------------------------
# 6) Workflow-net / soundness checks
# ----------------------------------------------------------------------
print("Site B candidate: workflow net =", pm4py.check_is_workflow_net(net_b))
res = pm4py.check_soundness(net_b, im_b, fm_b)
print("Site B candidate: soundness =", res)

# ----------------------------------------------------------------------
# 7) Optional playout: sample traces
# ----------------------------------------------------------------------
log_b = pm4py.play_out(net_b, im_b, fm_b)
for i, trace in enumerate(log_b[:5]):
    print(f"trace {i}:", [ev["concept:name"] for ev in trace])

# ----------------------------------------------------------------------
# 8) What this model CANNOT encode
# ----------------------------------------------------------------------
# - Data-dependent legal requirements: whether Originals Receipt and Legal
#   Review apply depends on case attributes (originals-required flag,
#   public-sector/high-value). POWL's XOR chooses freely; an attribute guard
#   (e.g., PM4Py data-aware extensions or a decision miner) is needed.
# - Resource capacity and queueing: the 4/7/3/2 specialist pools, WIP caps,
#   release throttling, and queue disciplines are absent; playout is purely
#   control-flow and assumes infinite servers and zero waiting.
# - Case locks and IT behavior: the one-active-owner lock, whitelisted
#   concurrent pairs, and back-entered timestamps are not representable.
# - Durations and external delays: identity/document service times, the
#   highly variable originals arrival delay, and legal processing times
#   require a stochastic simulation extension, not a Petri net alone.
# - Rework probabilities: the LOOP allows supplements but assigns them no
#   frequency; observed probabilities (360/3,400) must come from the log.
```

## 9. Recommendation

**`conditional go`**

Transfer the mechanism, not the headline. What should move to Site B is the principle of early task creation with event-triggered release, execution of Identity Check inside the originals wait, and genuinely simultaneous Identity/Document execution restricted to cases where no statutory barrier exists. Adopt Site A's WIP discipline and daily queue review as supporting practices.

Do not copy: (i) blanket creation of both tasks for every case — for 62% of Site B cases Document Check cannot lawfully execute until originals arrive, so the copied rule manufactures aged WIP and illusory concurrency; (ii) the expectation of a nine-hour median reduction, which at Site A is confounded by an API upgrade, added reviewers, a simpler case mix, and huddles; (iii) reliance on cross-trained staff, since Site B's four specialist pools cannot flex.

First subgroup: digital-complete, non-public-sector, non-high-value cases (roughly 35–38% of volume). They face no originals gate and no legal review, so the shared path-compression mechanism can act undistorted; the expected treated-stratum gain is three to six hours, worth one to two and a half hours at site level.

Benefits and risks. Realistic upside is a 2–4 hour median improvement under full implementation, concentrated in the digital stratum. Principal risks are bottleneck shift into assessment (three assessors) and legal review (two reviewers for 40% of cases), WIP inflation from pre-staged tasks, timestamp corruption from lock workarounds, and small rework increases.

Decision triggers. Expand when the digital stratum sustains a 3-hour median gain with 80% implementation fidelity (real overlap, <5% back-entry), no rework or appeal deterioration, and stable p90. Modify when T2 (pre-staging only) matches T1 — then the binding constraint is the case lock, and IT remediation should precede further rollout — or when gains appear as reduced pre-assessment waiting without end-to-end change, in which case add assessor/legal capacity or throttle releases. Abandon on any compliance breach (document check executed before originals), rework rising more than 2 percentage points, appeals rising more than 0.5 points, or p90 worsening more than 10% without compensating median gains.

## 10. Assumption register

1. **Task creation can be decoupled from executability in Site B's IT** — needed because pre-staging a pending Document Check is the core design element for originals cases — test by a sandbox configuration trial and vendor confirmation of a `PENDING` task state — if false, restrict the intervention to the digital stratum only.
2. **The statutory gate binds execution, not task creation** — needed to establish that pre-staging is lawful — test by obtaining a written compliance/legal opinion before go-live — if false, abandon pre-staging entirely; the digital-only variant survives.
3. **Identity Check has no hidden data dependency on documents or originals** — needed because concurrent execution assumes independent inputs, as at Site A — test via an input-dependency audit of ~100 traces plus reviewer interviews — if false, parallel identity will generate rework; serialize the dependent fields.
4. **Assessment and legal have absorbable slack or can be protected** — needed so upstream compression translates into end-to-end gains rather than queue displacement — test with a queueing/utilization analysis of the 20h pre-assessment wait and legal pool — if false, expect bottleneck shift; add capacity or throttle releases.
5. **Timestamp integrity is achievable during the pilot** — needed because overlap and cycle-time KPIs are the primary measurements — test by baselining the back-entry rate from event-versus-server-time deltas — if false, deploy server-side event capture first; otherwise pilot conclusions are void.
