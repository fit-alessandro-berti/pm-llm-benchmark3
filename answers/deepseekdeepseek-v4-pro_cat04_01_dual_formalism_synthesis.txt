# 1. Assumptions and Interpretation

1. **Low-risk / high-risk choice** is represented as an XOR-split immediately after *Analyze Root Cause*. The XOR contains a lowrisk branch (*Supervisor Review*) and a highrisk branch that executes *Quality Review* and *Regulatory Review* in true concurrency (POWL: unordered *StrictPartialOrder*; process tree: `PARALLEL` inside the XOR). Data conditions are not modelled; the XOR is chosen nondeterministically.
2. **Optional supplier consultation** is represented as an XOR-split, also after *Analyze Root Cause*, that either executes *Consult Supplier* once or takes a silent skip (). The decision depends on unmodelled case data; the XOR abstracts this choice.
3. **Passing vs. failing inspection** is encoded via the controlflow of a `LOOP` operator (process tree and POWL). The loop body is *Execute Trial* followed by *Inspect Trial*. After the body, a silent XOR choice leads to *Adjust Parameters* (redo) for a failure or to a silent exit transition for a pass. Because inspection outcomes are not event labels, the loop itself represents “repeat until pass” behaviour.
4. **Duplicate visible labels are permitted** in the process tree if required by the approximation, but they are **not used** in either model. All visible labels appear exactly once.
5. **Processtree approximation policy:** conservative underapproximation. The process tree forces all approval activities (and the optional *Consult Supplier*) to complete **before** *Execute Trial* can start. This sacrifices the permitted overlap between approvals / supplier consultation and the trial cycle, but ensures that no unsafe interleavings (e.g., releasing material before approvals finish) are introduced. The model is therefore a subset of the allowed behaviour.
6. **“May overlap”** is interpreted as **true concurrency** (absence of order constraints); activities that may overlap are modelled with no precedence edges between them. In the POWL model this is expressed by omitting edges. In the process tree the overlap is deliberately eliminated (underapproximation) so that no concurrency needs to be modelled.

|D9 | Analyze Root Cause | Consult Supplier XOR | precedence | CS may start only after ARC |
|D10| Consult Supplier XOR | (end of CS XOR) | optionality / silent skip | CS may be omitted () |
|D11| Design Corrective Action | Execute Trial | precedence (joint) | ET may start as soon as DCA **and** PV are complete |
|D12| Plan Verification | Execute Trial | precedence (joint) | ET needs both DCA and PV completed |
|D13| Execute Trial | Inspect Trial | strict sequence | first step of trial cycle |
|D14| Inspect Trial (fail) | Adjust Parameters | loop reentry | after a failing IT, AP must occur |
|D15| Adjust Parameters | Execute Trial | loop restart | after AP a new trial cycle is performed |
|D16| Inspect Trial (pass) | (end of trial loop) | loop exit | when inspection passes the loop ends (silent exit) |
|D17| trialloop exit (passing IT) | Release Material | precedence | RM requires a passing IT |
|D18| riskroute completion | Release Material | precedence | RM requires the selected approval route to be complete |
|D19| CS XOR completion | Release Material | precedence | if CS was selected it must be complete before RM |
|D20| Release Material | Archive Case | strict sequence | AC occurs after RM |
|D21| (no edge) approval submodel – trial submodel | — | concurrency (no order) | approval route may overlap the trial cycle |
|D22| (no edge) CS submodel – trial submodel / approvals | — | concurrency (no order) | CS may overlap corrective action, verification, approvals and trial work |

# 3. PM4Py ProcessTree Model

## 1. Compact ProcessTree Expression

```
->("Register Deviation",
   +("Contain Material","Analyze Root Cause"),
   +("Plan Verification",
     "Design Corrective Action",
     X("Supervisor Review", +("Quality Review","Regulatory Review")),
     X("Consult Supplier", )
    ),
   *(
      ->("Execute Trial","Inspect Trial"),
      "Adjust Parameters",
      
     ),
   "Release Material",
   "Archive Case"
  )
```

## 2. SelfContained Python Code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def build_tree():
    # leaves
    rd = ProcessTree(label="Register Deviation")
    cm = ProcessTree(label="Contain Material")
    arc = ProcessTree(label="Analyze Root Cause")
    pv = ProcessTree(label="Plan Verification")
    dca = ProcessTree(label="Design Corrective Action")
    sr = ProcessTree(label="Supervisor Review")
    qr = ProcessTree(label="Quality Review")
    rr = ProcessTree(label="Regulatory Review")
    cs = ProcessTree(label="Consult Supplier")
    et = ProcessTree(label="Execute Trial")
    it = ProcessTree(label="Inspect Trial")
    ap = ProcessTree(label="Adjust Parameters")
    rm = ProcessTree(label="Release Material")
    ac = ProcessTree(label="Archive Case")
    tau = ProcessTree(label=None)  # silent

    # highrisk parallel
    high_risk_par = ProcessTree(operator=Operator.PARALLEL, children=[qr, rr])
    # risk XOR
    risk_xor = ProcessTree(operator=Operator.XOR, children=[sr, high_risk_par])
    # CS XOR
    cs_xor = ProcessTree(operator=Operator.XOR, children=[cs, tau])

    # second parallel (after the first join)
    par2 = ProcessTree(operator=Operator.PARALLEL, children=[pv, dca, risk_xor, cs_xor])

    # first parallel
    par1 = ProcessTree(operator=Operator.PARALLEL, children=[cm, arc])

    # trial loop: do = SEQ(et,it), redo = ap, exit = tau
    do_seq = ProcessTree(operator=Operator.SEQUENCE, children=[et, it])
    trial_loop = ProcessTree(operator=Operator.LOOP, children=[do_seq, ap, tau])

    # root sequence
    root = ProcessTree(operator=Operator.SEQUENCE,
                       children=[rd, par1, par2, trial_loop, rm, ac])

    # helper to set parent references
    def set_parents(node, parent=None):
        node.parent = parent
        if node.children:
            for c in node.children:
                set_parents(c, node)

    set_parents(root, None)
    return root

tree = build_tree()
```

## 3. Parent / Child Handling
The `build_tree` function constructs all `ProcessTree` nodes, assembles them into the tree, and then sets parent references with the recursive `set_parents` helper.

## 4. Representation Limitations (Approximation)
The process tree **underapproximates** the narrative in the following ways:

- **Overlap of approvals with trial is lost.** In the tree, the `PARALLEL` block that contains `Plan Verification`, `Design Corrective Action`, the approval XOR and the CS XOR must finish **before** `Execute Trial` can start. Hence all approval and supplier work is forced to complete ahead of any trial cycle.
- **Overlap of supplier consultation with trial / approvals is forced to end before the trial.** The CS XOR runs inside the same parallel and therefore must complete before the trial, whereas the narrative explicitly allows CS to overlap the trial.
- The **optionality of CS** and the **risk choice** are modelled via `XOR`, which nondeterministically selects a branch at execution time; this matches the datadriven nature of the decisions under the stated visibility assumptions.
- The **repeatuntilpass** behaviour of the trial is faithfully captured by the `LOOP` operator with silent exit.

No other intended requirements are violated; the duplication of activities is **not** required because all activities appear once.

# 4. PM4Py POWL Model

## 1. Compact POWL Description
The model is a `StrictPartialOrder` whose nodes include all visible transitions, three composite submodels (approval XOR, CS XOR, trial loop), and a final archive transition. Precedence edges enforce all mandatory ordering constraints; the absence of edges between approval/CS and the trial submodel allows true concurrency.

## 2. SelfContained Python Code

```python
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

# ----- visible transitions -----
rd = Transition("Register Deviation")
cm = Transition("Contain Material")
arc = Transition("Analyze Root Cause")
pv = Transition("Plan Verification")
dca = Transition("Design Corrective Action")
et = Transition("Execute Trial")
it = Transition("Inspect Trial")
ap = Transition("Adjust Parameters")
rm = Transition("Release Material")
ac = Transition("Archive Case")
sr = Transition("Supervisor Review")
qr = Transition("Quality Review")
rr = Transition("Regulatory Review")
cs = Transition("Consult Supplier")

# ----- submodels -----
# highrisk parallel: QR, RR unordered
high_risk_par = StrictPartialOrder([qr, rr])

# approval XOR (low / high risk)
approval_xor = OperatorPOWL(Operator.XOR, [sr, high_risk_par])

# CS optionality XOR: CS or silent skip
cs_seq = StrictPartialOrder([cs])          # a sequential block with one activity
cs_skip = SilentTransition()
cs_xor = OperatorPOWL(Operator.XOR, [cs_seq, cs_skip])

# trial loop
do_order = StrictPartialOrder([et, it])
do_order.order.add_edge(et, it)           # ET before IT
trial_loop = OperatorPOWL(Operator.LOOP, [do_order, ap, SilentTransition()])

# ----- main partial order -----
root = StrictPartialOrder([rd, cm, arc, pv, dca, approval_xor, cs_xor, trial_loop, rm, ac])

# precedence edges
root.order.add_edge(rd, cm)
root.order.add_edge(rd, arc)
root.order.add_edge(cm, pv)
root.order.add_edge(arc, dca)
root.order.add_edge(arc, approval_xor)
root.order.add_edge(arc, cs_xor)
root.order.add_edge(pv, trial_loop)
root.order.add_edge(dca, trial_loop)
root.order.add_edge(approval_xor, rm)
root.order.add_edge(cs_xor, rm)
root.order.add_edge(trial_loop, rm)
root.order.add_edge(rm, ac)

powl = root
```

## 3. Use of `StrictPartialOrder`, `OperatorPOWL`, `Transition`, `SilentTransition`
- `StrictPartialOrder` collects nodes and enables direct precedence edges.
- `OperatorPOWL` with `Operator.XOR` models the risk choice and CS optionality.
- `OperatorPOWL(Operator.LOOP, [do, redo, exit])` models the repeatuntilpass trial cycle.
- `Transition` instances hold visible labels; `SilentTransition` represents internal  steps.

## 4. Added PartialOrder Edges
Edges are listed in the code block above. Every edge corresponds to an intended precedence relation (see dependency table). No edge is added between concurrent submodels.

## 5. Justification of Intentionally Unconnected Nodes
The following pairs of nodes are deliberately left without a precedence edge, allowing them to occur in any relative order:

- **approval_xor  trial_loop** – approvals may finish before, during, or after trial cycles.
- **cs_xor  trial_loop** – supplier consultation may overlap trial work.
- **cs_xor  approval_xor** – supplier consultation and approvals may proceed independently.
- **pv  dca** – Plan Verification and Design Corrective Action may run concurrently after their respective prerequisites are met.
- **approval_xor / cs_xor / trial_loop** have no edges among themselves, only incoming from prerequisites and outgoing to Release Material.

# 7. Preferred Representation and Validation Plan

**Canonical representation: POWL model.** It faithfully captures all concurrency, overlapping work, and synchronisation without approximation, and it is structurally close to a simple Petrinet with partialorder constraints.

## Validation Plan

1. **Conversion to accepting Petri net**  
   Use `pm4py.convert_to_petri_net(powl)` (or the analogous POWLtoPN converter). The resulting net should be a safe, 1bounded Petri net (no duplicate labels).

2. **Soundness checking**  
   Run `pm4py.check_soundness(net, im, fm, print_diagnostics=True)`. The net must be sound (no dead transitions, proper completion, etc.). Because POWL is sound by construction, this is a sanity check.

3. **Bounded / sampled playout**  
   Invoke `pm4py.play_out(net, ...)` or `pm4py.generate_traces(powl, ...)` to generate a set of traces. Manually inspect them to confirm that:
   - Every trace starts with RD and ends with AC.
   - No trace contains AP after a passing IT (i.e., after the loop exit).
   - Traces exist where approvals finish after the first ET.

4. **Explicit positive and negative trace tests**  
   Feed the eight witnesses from Section 5 into the POWL model (using a tokenreplay or alignment checker) and verify:
   - A1–A5 are accepted.
   - F1–F3 are rejected.

5. **Silentbehaviour / duplicatelabel check**  
   - Extract the set of all activity labels from the Net and assert that every visible label appears exactly once (no duplication).
   - Analyse the silent transitions: ensure that the loop exit is a silent transition and that no infinite loops exist without advancing.

6. **Limitations**
   - The POWL model uses XOR to resolve the risk level and supplier consultation; conformance checking may report multiple possible routings for a trace that originally carried specific data attributes (e.g., `risk="high"`). This is inherent to the controlflowonly abstraction.
   - The loop operator does not enforce a *datadriven* condition; both redo and exit paths are nondeterministically enabled. Validation must therefore accept traces where AP occurs after IT even though they represent an intended failure; the model cannot distinguish “pass” vs “fail” – it only prevents AP *after* the loop exit.
   - Soundness checking assumes a 1safe net; the conversion may produce unsafe nets for certain POWL constructs, requiring additional postprocessing.

# 8. Final SelfCritique

1. **Semantic weakness: loop condition abstraction** – Both models represent the trial loop as a nondeterministic LOOP that can either redo or exit after each `Inspect Trial`. The realworld distinction between a failing and a passing inspection is not modelled; this may lead to conformance checking accepting traces that are physically impossible (e.g., a single execution of ETIT that exits immediately, ignoring the possibility that the part consistently fails). The workaround (silent exit) is common but still an overapproximation.

2. **Semantic weakness: mandatory integration of risk and supplier choices** – The POWL model places the `approval_xor` and `cs_xor` immediately after `ARC` with no further constraint. In a real system the choice of risk level and the decision to involve the supplier are determined early in the case. Our model allows the XOR branches to be chosen arbitrarily, but the POWL semantics do not prevent a trace that, for example, takes the lowrisk SR branch but later still expects QR or RR to have occurred (they are not in that trace). The model is correct in a controlflow sense because the XOR selects exactly one path, but it cannot enforce that the same risk level must govern the remainder of the process – a databased decision would be more precise.

3. **Processtree underapproximation may hide deadlocks** – The tree forces all ancillary work (approvals, CS) to finish before the trial, effectively serialising the process. This “conservative” policy ensures no unsafe interleaving, but it may mask design errors: if the actual system permits approvals to run in parallel with the trial, a soundness check on the tree could give a false sense of correctness. Moreover, the tree may reject valid observations during process mining, making it a less useful representation for discovery.

(All three weaknesses relate to the expressiveness gap between the controlflow operators and the real business semantics; the POWL model resolves the concurrency issue but is still limited by the loop and choice abstractions.)
