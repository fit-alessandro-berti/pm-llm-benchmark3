### Why synthetic microseconds are forbidden

Adding `0.001 s` increments to `timestamp` to force a total order **encodes a false physical story**. The source systems recorded only second-level precision; inventing sub-second causality implies observed temporal resolution that does not exist. It corrupts duration calculations (`timedelta` between events becomes artificial), violates provenance (the timestamp is no longer the original business timestamp), and misleads process-mining algorithms into interpreting invented precedence as measured reality. We therefore keep `timestamp` intact and apply ordering via an auxiliary column (`det_order` or event index) used solely for sorting and delta computation.

## 7. Sensitivity analysis

We compare four datasets: **Raw** (17 events, unmerged, unqualified), **Conservative** (16 events, e03/e04 merged, labels refined, order deterministic), **Evidence-merge** (15 events, also e11/e16 merged), and **Aggressive library merge** (~10–12 events, broad mechanical merge).

### Event count and E2O relation count
- **Raw**: 17 events; E2O relations = sum of `len(related_objects)` per event  17 + object multiplicities.
- **Conservative**: 16 events; E2O reduced by 4 (e04 had 3 objects) but merged into e03, so net E2O relations decrease by the duplicate row count but union sets remain intact.
- **Evidence-merge**: 15 events; additional reduction from e16 (2 objects) merged into e11.
- **Aggressive**: ~11 events; massive E2O collapse because `e05`, `e09`, `e10`, `e14`, `e07`, `e15` may be eliminated or fused, destroying relation specificity.

### Order-flattened DFG (per Order O1)
- **Raw / Conservative / Evidence**: Path `Create  Validate  Pick (I1) / Pick (I2)  Pack [Detailed/Summary]  Dispatch [Release/Accept/Handover]  Confirm`. In aggressive, picks collapse (e05 lost), dispatch collapses to a single node, and the path becomes artificially short.
- **Concrete edge change**: `Pack Package [WMS Detailed]  Dispatch Package [WMS Release]` (e06e08) is preserved in conservative/evidence but may disappear in aggressive if e07 and e08 are fused.

### Item-flattened DFG (per Item I1 and I2)
- **Raw / Conservative**: I1 shows `Pick  Pack`; I2 shows `Pick  Pack`. In aggressive, I2’s `Pick` (e05) is merged with I1’s (e03), so **I2’s item-level lifecycle vanishes entirely**. The I1-flattened graph falsely includes both items in one pick event.
- **Edge affected**: `(I1, Pick Item)  (I1, Pack Package)` remains; `(I2, Pick Item)  (I2, Pack Package)` is **deleted** in aggressive.

### Payment-flattened DFG (per Payment M1 and M2)
- **Raw / Conservative / Evidence**: M1 path: `Authorize  Capture (M1)`; M2 path: `Capture (M2)`. In aggressive, `e13` and `e14` are merged, so **M2’s capture event is destroyed**. The OC-DFG for `M2` becomes empty or incorrectly linked to `M1`.
- **Concrete edge affected**: `(M1, Authorize Payment)  (M1, Capture Payment)` may survive, but `(M2, Capture Payment)` is **lost**, and `M2` may be incorrectly attached to `M1`’s event.

### OC-DFG edges and frequency metrics
The directly-follows graph across all objects changes frequencies drastically:
- **Conservative**: `Dispatch [WMS Release]  Dispatch [Carrier Accept]` (e08e09) appears with freq 1; `Dispatch [Carrier Accept]  Handover` (e09e10) freq 1. In aggressive, these become self-loops or are replaced by `Dispatch  Confirm` (e08e17) with inflated frequency.
- **Concrete patterns changed**:
  1. `Pick Item  Pack Package` frequency drops if e05 is removed.
  2. `Pack Package  Dispatch Package` splits correctly in conservative but collapses in aggressive.
  3. `Issue Invoice  Authorize Payment` (e11/e16e12) frequency is 2 in conservative (two invoice observations), 1 in evidence-merge, and 1 (with wrong source) in aggressive.
  4. `Authorize Payment  Capture Payment` (e12e13) remains in all except if e13/e14 merged.
  5. `Capture Payment  Confirm Delivery` does not exist directly, but `Dispatch  Confirm` (e10e17) is preserved only if e10 survives.
  6. `Create Order  Validate Order` (e01e02) is stable across all scenarios.

### ET–OT weights (Event-Type to Object-Type)
- **Raw**: `Pick Item` relates to `Item` with weight 2 (I1, I2) and `Order` with weight 2.
- **Aggressive**: `Pick Item` relates to `Item` with weight 1 (only I1 remains), severely biasing OTG centrality of `Item`.

### OTG relations (Object-Type Graph)
- In conservative, `Item` connects to `Order`, `Package`, and `Person` (`P1`) via pick and pack events. If `e05` is dropped, `I2` is disconnected from `Package` and `Order` in the OTG, creating a false isolated item.

### Apparent rework or loops
- **Conservative / Evidence**: No false loops; abstraction-level events (`e07`, `e15`) are kept but qualified, so analysts can distinguish updates from rework.
- **Aggressive**: If `e07` is merged into `e06` and then misordered relative to `e06` (or vice versa), an artificial loop `Pack  Pack` may appear. If `e15` is placed before `e14` by ingestion-time ordering, a false loop `Capture  Capture` (summary before transaction) emerges.

### Lifecycle and performance measurements
- **Time Pick-to-Pack**: In raw/conservative, measured from earliest pick (`e03`/`e05`) to pack (`e06`). In aggressive, `e05` loss makes I2’s time-to-pack undefined or zero.
- **Invoice-to-Payment duration**: In evidence-merge, single invoice event simplifies calculation; in conservative, analysts must decide whether to use `e11` or `e16`, requiring explicit rule documentation.

## 8. Audit trail and reversibility

### Provenance schema

| Field | Type | Description |
|---|---|---|
| `audit_id` | string | UUID for the audit record |
| `canonical_eid` | string | Surviving event identifier |
| `source_eids` | list[string] | All original event IDs (e.g., `[e03, e04]`) |
| `merge_rule` | string | Rule version and type (`v1-reconciliation_scan`; `v1-harmonization_qualify`; `v1-abstraction_preserve`) |
| `reviewer` | string | `rule_engine` or `analyst_id` |
| `original_activity` | dict | `{source_eid: original_activity_label}` |
| `refined_activity` | string | Qualified label applied in pipeline |
| `original_timestamp` | dict | `{source_eid: timestamp}` |
| `adjusted_timestamp` | string | Only if synthetic order column added (not `timestamp` mutation) |
| `attributes_retained` | dict | `{source_eid: {"payload_hash": ..., "source_key": ...}}` |
| `discarded_conflicts` | list | Attributes not selected (e.g., SCANNER payload if WMS authoritative) |
| `confidence` | float | 0.0–1.0 or enum (`high`, `medium`, `low`) |
| `reason` | text | Human-readable justification (`reconciliation_report_confirmed`; `invoice_V1_correlation`) |

### Reconstruction of the raw view

An analyst can reconstruct the raw OCEL by:
1. Selecting `audit_id` records where `canonical_eid` exists.
2. Retrieving the original source rows from `ocel_raw.events` using `source_eids`.
3. For merged events (`e03`), splitting the canonical row back into the original `e03` and `e04` using `attributes_retained` and `discarded_conflicts`; re-inserting both rows with original `timestamp`, `activity`, `source`, and `related_objects`.
4. For qualified events (`e08`, `e09`), reversing the `refined_activity` mapping to `original_activity`.
5. Removing any `det_order` or `ordered_index` columns added for sorting.
6. Rebuilding E2O relations from the reconstructed event table.

Because `ocel_raw` is never overwritten (all scenarios are `deepcopy` outputs), the reconstruction is always possible by discarding the derived copies and using the audit table as a mapping layer.

## 9. Failure modes and safeguards

| # | Failure mode | How it manifests | Safeguard |
|---|---|---|---|
| 1 | **Collapsing distinct partial payments** (`e13`/`e14`) | `have_common_object=True` merges M1 and M2; revenue split lost | Inspect object-level differences (`M1` vs `M2`) before any merge; never merge across different object-type instances |
| 2 | **Converting abstraction-level updates into false rework** (`e06`/`e07`, `e15`) | Merging or misordering creates `Pack  Pack` loops or `Payment  Payment` loops | Retain both with qualifiers (`Detailed` vs `Summary`); enforce `e06` before `e07` by derivation link, not ingestion |
| 3 | **Ordering by ingestion time** | `e07` ingested at 10:01:00 placed after `e09` (10:15:01) or `e10` (10:15:21) wrongly | Use `det_order` based on `source_seq` and domain rules; `ingested_at` is only fallback `D3` |
| 4 | **Treating shared objects as proof of duplication** | `O1` and `V1` shared by `e13`/`e14`; system assumes duplicate | Require identity of **all distinguishing objects** and reconciliation evidence; quarantine if ambiguous |
| 5 | **Unioning incompatible E2O relations** | Merging `e03` (I1) and `e05` (I2) creates event linking to both items | Only union `related_objects` when sets are identical; otherwise retain separate events |
| 6 | **Changing durations through synthetic microseconds** | Adding `0.001 s` to `timestamp` changes `timedelta` calculations in performance analysis | Keep `timestamp` intact; use separate `ordered_index` or `det_order` for sequencing |
| 7 | **Losing source-authoritative attributes** | Keeping SCANNER version of `e04` and dropping WMS location data | In verified merge, store authoritative (`WMS`) and alternative (`SCANNER`) payloads in provenance |
| 8 | **Applying duplicate functions to the whole OCEL** | `pm4py.ocel_merge_duplicates` executed on full `ocel_raw` without `precheck_duplicate_groups` | Always run `precheck_duplicate_groups`; apply library functions only to explicitly listed `canonical/drop` pairs within restricted copies |

**Concluding principle**: The pipeline prioritizes **semantic fidelity over event-count reduction**. Every transformation is documented in the audit trail, every deterministic ordering choice is separated from the original timestamp, and every duplicate decision is traceable to either a reconciliation report, a source sequence, or a domain lifecycle rule—not to algorithmic coincidence.
