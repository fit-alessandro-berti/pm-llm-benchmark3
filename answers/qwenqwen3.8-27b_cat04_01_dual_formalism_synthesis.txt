# 1. Assumptions and Interpretation

1. **Trace abbreviations.** For compactness, the behavioral witnesses use:  
   `R = Register Deviation`, `C = Contain Material`, `A = Analyze Root Cause`, `P = Plan Verification`, `D = Design Corrective Action`, `S = Supervisor Review`, `Q = Quality Review`, `G = Regulatory Review`, `K = Consult Supplier`, `E = Execute Trial`, `I = Inspect Trial`, `J = Adjust Parameters`, `L = Release Material`, `Z = Archive Case`.

2. **Low-risk / high-risk choice.** The risk decision is not represented by a data condition or risk label. It is represented as a structural control-flow alternative:
   - low-risk alternative: `Supervisor Review`;
   - high-risk alternative: `Quality Review` and `Regulatory Review` in parallel.
   
   The model therefore admits either route. It does not validate that the selected route matches hidden case data.

3. **Optional supplier consultation.** `Consult Supplier` is modeled as an optional activity that may occur at most once:
   - process tree: `choice(Consult Supplier, )`, where `` is an unlabeled epsilon leaf;
   - POWL: `XOR(Consult Supplier, SilentTransition("skip supplier"))`.
   
   The skip branch is silent and should not appear in visible traces.

4. **Passing inspection abstraction.** Inspection outcomes are not event labels. I abstract a passing inspection as the **final** `Inspect Trial` in the trial loop. The trial language is:
   ```text
   (Execute Trial ; Inspect Trial ; Adjust Parameters)* ; Execute Trial ; Inspect Trial
   ```
   Under this abstraction:
   - every `Adjust Parameters` belongs to a failed cycle;
   - every `Adjust Parameters` must be followed by another `Execute Trial ; Inspect Trial`;
   - the final `Inspect Trial` is treated as the passing inspection;
   - `Adjust Parameters` after that final inspection is structurally impossible.

5. **Duplicate visible labels.** Duplicate visible labels are permitted only where the business process legitimately allows multiple occurrences of the same activity, namely repeated `Execute Trial` and `Inspect Trial` activities. The chosen process tree does **not** duplicate `Analyze Root Cause`. The POWL model also uses a single `Analyze Root Cause` node. If a duplication-based process tree were used, duplicate `Analyze Root Cause` labels would be an explicit artifact; I avoid that by using a conservative approximation instead.

6. **Process-tree approximation policy.** The process tree uses a **conservative under-approximation**. It serializes the two initial work products by requiring `Plan Verification` to complete before `Design Corrective Action`, the risk route, and `Consult Supplier` may start. This excludes some intended interleavings, especially cases where `Design Corrective Action` or reviews start before `Plan Verification` completes. It does not admit release before required obligations. The policy avoids duplicating `Analyze Root Cause` and avoids unsafe release behavior.

7. **Meaning of “may overlap”.** “May overlap” is interpreted as **absence of an imposed order constraint**, not as a requirement for true simultaneous timestamps. In the process tree, parallel operators allow interleavings. In the POWL model, missing partial-order edges allow interleavings.

8. **Loop and epsilon assumptions.** I assume:
   - `Operator.LOOP` is interpreted as zero-or-more repetitions, i.e. Kleene star;
   - an unlabeled process-tree leaf can be treated as epsilon for optional activities;
   - a `SilentTransition` in POWL produces no visible event.

# 3. PM4Py Process-Tree Model

1. Compact process-tree expression:

```text
seq(
  R,
  par(
    seq(C, P),
    A
  ),
  par(
    seq(D, loop(seq(E, I, J)); seq(E, I)),
    choice(S, par(Q, G)),
    choice(K, )
  ),
  L,
  Z
)
```

2. Self-contained Python construction:

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator


def leaf(label):
    return ProcessTree(label=label)


def op(operator, children):
    node = ProcessTree(label=None, operator=operator)
    node.children = list(children)
    for child in node.children:
        child.parent = node
    return node


R = leaf("Register Deviation")
C = leaf("Contain Material")
A = leaf("Analyze Root Cause")
P = leaf("Plan Verification")
D = leaf("Design Corrective Action")
S = leaf("Supervisor Review")
Q = leaf("Quality Review")
G = leaf("Regulatory Review")
K = leaf("Consult Supplier")

E_fail = leaf("Execute Trial")
I_fail = leaf("Inspect Trial")
J = leaf("Adjust Parameters")
E_final = leaf("Execute Trial")
I_final = leaf("Inspect Trial")

L = leaf("Release Material")
Z = leaf("Archive Case")

eps = ProcessTree(label=None)

contain_plan = op(Operator.SEQUENCE, [C, P])
initial = op(Operator.PARALLEL, [contain_plan, A])

failed_cycle = op(Operator.SEQUENCE, [E_fail, I_fail, J])
failed_loop = op(Operator.LOOP, [failed_cycle])
final_cycle = op(Operator.SEQUENCE, [E_final, I_final])
trial = op(Operator.SEQUENCE, [failed_loop, final_cycle])

design_trial = op(Operator.SEQUENCE, [D, trial])

high_risk = op(Operator.PARALLEL, [Q, G])
risk_route = op(Operator.XOR, [S, high_risk])

optional_supplier = op(Operator.XOR, [K, eps])

post_analysis = op(Operator.PARALLEL, [design_trial, risk_route, optional_supplier])

tree = op(Operator.SEQUENCE, [R, initial, post_analysis, L, Z])
```

3. Parent/child handling. The helper `op` creates an operator node, assigns its children to `node.children`, and explicitly sets `child.parent = node` for every child. Leaf nodes are created with `ProcessTree(label=...)` and have no children.

4. Approximation and loss. This process tree is not exact. Its main representational losses are:

   - It forces `Plan Verification` to complete before `Design Corrective Action`, the risk route, and `Consult Supplier` can start. The intended process allows `Design Corrective Action` and the risk route to start as soon as `Analyze Root Cause` completes, even if `Plan Verification` is still running.
   - It cannot represent the intended non-block-structured sharing of `Analyze Root Cause` without either duplicating `Analyze Root Cause` or serializing branches. This model chooses serialization to avoid duplicate `Analyze Root Cause` labels.
   - It represents risk selection and supplier selection as structural alternatives, not as data-driven decisions. The model cannot check whether a low-risk case selected the low-risk route or whether supplier consultation was selected based on case data.
   - It abstracts the passing inspection as the final `Inspect Trial`. It cannot distinguish a failed inspection from a passing inspection by label; it only enforces the structural pattern `(E ; I ; J)* ; E ; I`.
   - It assumes `Operator.LOOP` means zero-or-more repetitions. If a PM4Py implementation interprets `LOOP` as one-or-more, the model would overconstrain first-try passing cases.
   - It assumes the unlabeled epsilon leaf represents a silent skip for optional supplier consultation.

```python
        node.operator = operator
        node.children = list(children)
        return node


R = Transition("Register Deviation")
C = Transition("Contain Material")
A = Transition("Analyze Root Cause")
P = Transition("Plan Verification")
D = Transition("Design Corrective Action")

S = Transition("Supervisor Review")
Q = Transition("Quality Review")
G = Transition("Regulatory Review")

K = Transition("Consult Supplier")
skip_supplier = SilentTransition("skip supplier")

E_fail = Transition("Execute Trial")
I_fail = Transition("Inspect Trial")
J = Transition("Adjust Parameters")

E_final = Transition("Execute Trial")
I_final = Transition("Inspect Trial")

L = Transition("Release Material")
Z = Transition("Archive Case")

high_risk = strict_po([Q, G])
risk_route = make_operator(Operator.XOR, [S, high_risk])

optional_supplier = make_operator(Operator.XOR, [K, skip_supplier])

failed_cycle = strict_po([E_fail, I_fail, J])
failed_cycle.order.add_edge(E_fail, I_fail)
failed_cycle.order.add_edge(I_fail, J)

failed_loop = make_operator(Operator.LOOP, [failed_cycle])

root = strict_po([
    R,
    C,
    A,
    P,
    D,
    risk_route,
    optional_supplier,
    failed_loop,
    E_final,
    I_final,
    L,
    Z
])

root.order.add_edge(R, C)
root.order.add_edge(R, A)

root.order.add_edge(C, P)
root.order.add_edge(A, D)

root.order.add_edge(A, risk_route)
root.order.add_edge(A, optional_supplier)

root.order.add_edge(P, failed_loop)
root.order.add_edge(D, failed_loop)

root.order.add_edge(P, E_final)
root.order.add_edge(D, E_final)

root.order.add_edge(failed_loop, E_final)
root.order.add_edge(E_final, I_final)

root.order.add_edge(I_final, L)
root.order.add_edge(risk_route, L)
root.order.add_edge(optional_supplier, L)

root.order.add_edge(L, Z)

powl = root
```

3. Explicit use of required types. The code uses:
   - `StrictPartialOrder` for the root partial order and for the high-risk submodel and failed-cycle submodel;
   - `OperatorPOWL` for the risk `XOR`, optional supplier `XOR`, and failed-cycle `LOOP`;
   - `Transition` for visible activities;
   - `SilentTransition` for the silent supplier-skip branch.

4. Required partial-order dependencies. Every required precedence is added with `.order.add_edge(source_node, target_node)`:
   - `R` before `C` and `A`;
   - `C` before `P`;
   - `A` before `D`, risk route, and optional supplier;
   - `P` and `D` before the trial loop and final trial execution;
   - failed loop before final trial execution;
   - final `E` before final `I`;
   - final `I`, risk route, and optional supplier before `L`;
   - `L` before `Z`.

5. Intentionally unconnected nodes. The following pairs remain unconnected because they are intended to be concurrently interleavable:
   - `C` and `A`: containment and root-cause analysis may overlap after registration;
   - `P` and `D`: verification planning and corrective-action design depend on different sources and may overlap;
   - risk route and trial loop / final trial: approvals may overlap the trial cycle;
   - optional supplier and risk route / trial loop / final trial: supplier consultation may overlap approvals and trial work;
   - `Q` and `G`: high-risk reviews may occur concurrently and in either completion order;
   - `failed_loop` and risk route / optional supplier: failed trial iterations may overlap approvals and supplier consultation.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | After `R`, `C` and `A` may overlap. | `par(seq(C, P), A)` allows `C` and `A` to overlap. | `R > C`, `R > A`, no `C`/`A` edge. | Exact. | No significant loss. |
| Split dependencies into planning/design | `P` after `C`; `D` after `A`; `P` and `D` may proceed independently. | `P` after `C`; `D` after `A`, but the first parallel join forces `P` to complete before `D` starts. | `C > P`, `A > D`, no `P`/`D` edge. | Process tree overconstrains `D`; POWL exact. | Tree may delay corrective-action design and hide intended parallelism. |
| Risk route | Low risk: `S`. High risk: `Q` and `G` concurrently. | `choice(S, par(Q, G))`. | `XOR(S, high)`, where `high` is a partial order of `Q` and `G`. | Exact under the no-data assumption. | Neither model validates that the route matches hidden risk data. |
| Overlap of approval and trial | Selected approval route may overlap trial cycle. | Risk route is parallel with `D ; trial`, so approval can overlap trial, but risk starts only after `P` completes. | No edge between risk route and trial loop / final trial. | Process tree overconstrains approval start; POWL exact. | Tree may underestimate overlap and overstate cycle time. |
| Optional supplier consultation | Optional, at most once, after `A`, before `L`; may overlap design, planning, approvals, trial. | `choice(K, )` in the post-analysis parallel block. It may overlap trial and design, but starts only after `P` completes. | `XOR(K, silent skip)` after `A` and before `L`; no edges to design, planning, approvals, or trial. | Process tree overconstrains start; POWL exact. | Tree may delay supplier engagement. |
| Repeat-until behavior | `(E ; I ; J)* ; E ; I`; final `I` is passing. | `loop(seq(E, I, J)); seq(E, I)`. | `LOOP(failed_cycle)` followed by final `E_final ; I_final`. | Exact under the passing-inspection abstraction and zero-or-more loop assumption. | Cannot distinguish pass/fail by labels; final inspection is assumed passing. |
| Release synchronization | `L` after passing `I`, selected approval route, and selected supplier. | `L` after the post-analysis parallel block containing trial, risk, and optional supplier. | Edges from final `I`, risk route, and optional supplier to `L`. | Exact given the approximations above. | Release is protected in both models. |
| Duplicate-label risk | One logical `Analyze Root Cause`; multiple `E`/`I` occurrences are legitimate. | One `A`; duplicate `E`/`I` leaves are used for loop abstraction. | One `A` node; duplicate `E`/`I` transitions are used for failed and final cycles. | Avoids duplicate `A`; duplicate `E`/`I` are intended. | A duplication-based tree that duplicated `A` would admit extra analysis events; this answer avoids that by under-approximating the process tree. |

# 7. Preferred Representation and Validation Plan

**Preferred canonical representation: POWL.**  
The POWL model is preferred because it can express the cross-branch dependencies directly with partial-order edges: a single `Analyze Root Cause` node can feed both `Design Corrective Action` and the risk route; `Plan Verification` and `Design Corrective Action` can be independent prerequisites for the trial; approvals and supplier consultation can overlap the trial; and release can synchronize the final inspection, approval route, and optional supplier. The process tree is useful for tree-based tooling, but it must approximate the non-block-structured dependency pattern.

Validation plan:

1. **Conversion to an accepting Petri net where supported.**  
   Use:
   ```python
   net = pm4py.convert_to_petri_net(powl)
   ```
   If POWL conversion is unsupported or lossy, also convert the process tree:
   ```python
   tree_net = pm4py.convert_to_petri_net(tree)
   ```
   Identify the initial and final places from the converted net.

2. **Soundness checking of converted nets.**  
   Run:
   ```python
   pm4py.check_soundness(net, im, fm, print_diagnostics=True)
   ```
   and similarly for `tree_net`. Check for deadlocks, unreachable states, and traps. Soundness is necessary but not sufficient for business fidelity.

3. **Bounded or sampled playout.**  
   Use:
   ```python
   pm4py.play_out(powl, ...)
   ```
   or play out the converted net. Generate bounded traces and random interleavings. For each generated visible trace, check invariants such as:
   - first event is `R`;
   - last event is `Z`;
   - `A` occurs exactly once;
   - `K` occurs at most once;
   - either `S` occurs, or both `Q` and `G` occur;
   - `#E = #I = #J + 1`;
   - no `J` occurs after the final `I` before `L`;
   - `L` occurs only after final `I`, the selected approval route, and `K` if present.

4. **Explicit positive and negative trace tests.**  
   Use the eight witnesses from Section 5:
   - assert `T1` through `T5` are accepted by the POWL model;
   - assert `F1` through `F3` are rejected by the POWL model;
   - assert `T1` through `T4` are accepted by the process tree;
   - assert `T5` is rejected by the process tree as the intended approximation witness;
   - assert `F1` through `F3` are rejected by the process tree.

5. **Silent behavior and duplicate-label checks.**  
   Project generated traces to visible labels and verify:
   - no `skip supplier` or `None` labels appear;
   - `Analyze Root Cause` occurs exactly once in both models;
   - repeated `Execute Trial` / `Inspect Trial` labels satisfy the loop invariant;
   - no trace contains `S` together with `Q` or `G`;
   - no trace contains `K` more than once;
   - no trace contains `J` after the final `I` before `L`.

6. **Limitations of the validation plan.**  
   - Bounded playout cannot prove correctness of unbounded loops.
   - Petri-net conversion may introduce implementation-specific silent places or transitions.
   - Soundness checks do not verify business meaning, such as whether the selected risk route matches hidden risk data.
   - The passing-inspection abstraction is semantic: the model cannot distinguish a failed inspection from a passing inspection by label.
   - PM4Py API semantics for `OperatorPOWL`, `StrictPartialOrder`, `LOOP`, and epsilon/silent leaves may vary between versions, so successful construction is evidence to inspect, not proof of fidelity.

# 8. Final Self-Critique

1. **Semantic weakness: data-driven choices are not validated.**  
   The models represent low-risk/high-risk and supplier selection as structural alternatives. They cannot determine whether a low-risk case should have used `Supervisor Review` or whether a high-risk case should have used both `Quality Review` and `Regulatory Review`. The model admits the control-flow alternatives but does not validate them against hidden case data.

2. **Process-tree approximation may distort performance and behavior.**  
   The conservative process tree forces `Plan Verification` to complete before `Design Corrective Action`, risk reviews, and supplier consultation. This is safe in the sense that it does not admit release before obligations, but it rejects valid intended traces such as `T5` and may overstate dependencies, cycle time, and bottlenecks.

3. **Loop abstraction and API assumptions remain fragile.**  
   The trial model relies on the abstraction `(E ; I ; J)* ; E ; I`, the assumption that `LOOP` allows zero repetitions, and the assumption that `OperatorPOWL` can contain `StrictPartialOrder` submodels. If PM4Py’s implementation treats loops, operator children, or silent/epsilon leaves differently, the constructed models may overconstrain or underconstrain the intended behavior.
