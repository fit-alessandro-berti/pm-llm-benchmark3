## 2. Process-Model Consistency Checks

### 2.1 Proposed Validation Suite

The following concrete checks should be implemented in a **prefix-conformance testing pipeline** that runs at model-deployment time and periodically in production:

#### A. Prefix-Time Availability Check

**Purpose:** Ensure every feature value used in an explanation could have been computed from data available at or before *t*.

**Method:**
- For each feature, store a `source_event_type` and `source_timestamp` in the feature-store metadata.
- At evaluation time, verify `source_timestamp  t` for every feature in the explanation.
- Flag any feature where `source_timestamp > t` or where `source_timestamp` is NULL (as with `risk_score_current`).

**Limitations:** This check fails silently if the feature-store does not record source timestamps. The current system lacks these for `risk_score_current` and `final_handler_team`, so this check must be paired with the lineage-repair recommendations in §5.

#### B. Activity-Order Feasibility Check

**Purpose:** Verify that any activity referenced in a sequence-pattern explanation is *possible* at *t* given the normative process model.

**Method:**
- Encode the normative process as a **Petri net** or a **declare/constraint model**:
  - After `Coverage Check Completed`, the *enabled* transitions are: `Documents Requested`, `Damage Assessment Completed` (fast track), and `Fraud Investigation Opened`.
  - `Settlement Decision Recorded` is *disabled* (requires prior Damage Assessment Completed).
  - `Appeal` is *disabled* (requires prior Partial or Deny decision).
  - `Claim Closed` is *disabled* (requires prior final Settlement Decision or Withdrawal).
- For each sequence pattern in an explanation, check whether the target activity is enabled, future-possible (not yet enabled but could become enabled), or impossible at *t*.
- **Impossible activities** (e.g., `Appeal` at *t*) are hard violations.
- **Future-possible activities** (e.g., `Fraud Investigation Opened`) are soft violations: the activity hasn't happened yet, but could. Its *actual occurrence* in the trace is leakage; the *possibility* of it is legitimate domain knowledge.

**Limitations:** The normative model may not capture all real-world exceptions (e.g., a claim reopened after closure). The check is only as good as the process model.

#### C. Same-Timestamp Ambiguity Check

**Purpose:** Detect cases where two events share a timestamp and their ordering may be unreliable.

**Method:**
- For each pair of events `(e, e)` in a trace where `timestamp(e) = timestamp(e)`, check whether a reliable `sequence_index` exists and is consistent.
- If `sequence_index` is missing or inconsistent, flag the pair as **ordering-ambiguous**.
- Any sequence pattern that depends on the ordering of same-timestamp events (e.g., `Claim Closed  Damage Assessment Completed` in Case Z) is flagged as **unreliable**.

**Role and limitations:** This catches data-quality issues but cannot resolve them. Resolution requires either (a) a more granular timestamp, or (b) a business rule that establishes canonical ordering (e.g., "Damage Assessment always precedes Claim Closure").

#### D. Complete-Trace Feature Check

**Purpose:** Identify features that are computed from the complete case trace rather than the prefix at *t*.

**Method:**
- Tag each feature in the feature store with a **computation scope**: `prefix_only`, `complete_trace`, `post_closure`.
- Any feature tagged `complete_trace` or `post_closure` used in a *t* explanation is a violation.
- Features in the global top-12 that violate this: `total_case_duration_hours` (post_closure), `appeal_seen_anywhere` (complete_trace), `num_document_requests_total` (complete_trace), `full_trace_variant_id` (complete_trace), `final_handler_team` (post_closure).

**Limitations:** Some features have ambiguous scope (e.g., `final_handler_team` is 65 % valid at *t*). The check should produce a confidence flag rather than a binary pass/fail.

#### E. Activity-Enabled/Impossible/Future-Possible Classification

**Purpose:** For each activity mentioned in an explanation, classify its status at *t*.

| Activity | Status at *t* | Explanation |
|---|---|---|
| `Claim Registered` | **Past** (already occurred) | Part of the prefix. |
| `Coverage Check Completed` | **Past** (just occurred) | This is *t*. |
| `Documents Requested` | **Future-possible** | May occur next if evidence cycles are needed. |
| `Documents Received` | **Future-possible** | Requires prior Documents Requested. |
| `Documents Validated` | **Future-possible** | Requires prior Documents Received. |
| `Damage Assessment Completed` | **Future-possible** | May occur via fast track or after evidence cycles. |
| `Fraud Investigation Opened` | **Future-possible** | May be triggered by a red flag. |
| `Settlement Decision Recorded` | **Impossible** (for now) | Requires prior Damage Assessment Completed. Will become future-possible after assessment. |
| `Appeal` | **Impossible** | Requires prior Partial or Deny decision. Multiple steps away. |
| `Claim Closed` | **Impossible** | Requires final decision or withdrawal. |

**Role:** This classification is essential for evaluating whether sequence-pattern explanations are valid. Any pattern whose target activity is "impossible" at *t* is a hard leakage violation.

**Limitations:** The classification depends on the normative process model being correct. Deviations (e.g., emergency fast-track settlements) may exist.

#### F. Repeated Settlement Decision Semantic Check

**Purpose:** Verify that when `Settlement Decision Recorded` appears twice in a trace, the repetition is semantically legitimate (i.e., caused by an appeal-induced reconsideration) rather than a data error.

**Method:**
- If `Settlement Decision Recorded` appears twice, check that an `Appeal` event occurs between them.
- If no `Appeal` intervenes, flag as a potential data-quality issue (duplicate recording).
- Also check that the second decision has a different outcome or timestamp to avoid double-counting.

**Role:** This is important for the feature `appeal_seen_anywhere` and for any explanation that references settlement decisions. The double-occurrence is legitimate *in the complete trace* but is never available at *t*.

**Limitations:** The process model permits a second Settlement Decision only after appeal. If the real process allows other paths to reconsideration (e.g., internal audit), the check would produce false positives.

## 3. Alternative Feature Interpretations

After identifying and remediating leakage, the surviving and repairable signals can be classified as follows:

### 3.1 Defensible Predictive Signals

These features are temporally available at *t*, process-consistent, and have a plausible operational mechanism:

| Feature | Why defensible | What may be claimed | What may NOT be claimed |
|---|---|---|---|
| `initial_damage_complexity` | Frozen at registration; directly relates to investigation effort needed. | "Claims assessed as high-complexity at registration historically breach the 10-day target more often." | "High complexity *causes* delays"—there may be confounders (e.g., high-complexity claims also tend to have SIU referrals, which add time). |
| `elapsed_since_registration_at_t0` | Purely derived from past timestamps; measures slack consumed. | "Claims that have already used part of their 10-day window at the coverage-check point have less remaining buffer." | "Delay at registration *causes* breach"—the elapsed time may reflect a slow intake process or a complex initial contact, each with different operational implications. |
| `queue_length_at_t0` | Measured at *t* from a timestamped snapshot. | "When handler queues are long at the time of coverage check completion, settlement is more likely to be delayed beyond 10 days." | "Reducing queue length will reduce breach rates"—this is an interventional claim that requires causal inference (e.g., an experiment or natural experiment). |

### 3.2 Process-State or Congestion Signals

These capture the operational state at *t* and are useful for resource planning, but their causal relationship to breach is mediated by unobserved factors:

| Feature | Interpretation | Operational use | Caution |
|---|---|---|---|
| `queue_length_at_t0` (repeated here for emphasis) | Measures current workload pressure. | Staffing adjustments, workload rebalancing. | Queue length may spike *because* of a holiday or system outage, confounding the signal. |
| Repaired `team_assigned_at_coverage_check` (replaces `final_handler_team`) | Some teams may have higher throughput, different expertise, or different case mixes. | Identify teams that may need support or training. | Team performance differences may reflect case assignment policies rather than team skill. Do not use for individual performance evaluation without controlling for case mix. |
| `prefix_variant_id` (replaces `full_trace_variant_id`) | At *t* this is always `REG  COV`, so it has zero variance and is uninformative. However, if the model were predicting at a later point (e.g., after the first evidence cycle), prefix variants would become informative. | At *t*, this feature is useless. At later prediction points, it captures process-state information. | Do not confuse prefix-variant informativeness at later checkpoints with the leaked full-variant at *t*. |

### 3.3 Proxies Requiring Fairness/Robustness Review

These features are temporally legitimate but may encode protected attributes or sensitive characteristics:

| Feature | What it may proxy | Fairness concern | Recommended review |
|---|---|---|---|
| `claimant_region` | Repair-network density, language spoken, socioeconomic status, digital access, channel preference. | If region correlates with ethnicity, income, or immigration status, the model may produce disparate impact. | Decompose into operational sub-features (repair-network coverage, preferred language, channel). Run disparate-impact analysis across protected groups. |
| `claimant_channel = Broker` | Broker-assisted claims may involve different claimant demographics, expectations, or documentation quality. | If broker use correlates with income or digital literacy, channel may be a proxy for socioeconomic status. | Test whether channel effect persists after controlling for claim complexity and region. |
| `initial_reserve = €25,000` | Claim value, expected complexity, policy limits. | If reserve correlates with claimant wealth or property value, it may interact with protected characteristics. | Include in fairness review. Test for interaction effects with region and channel. |

### 3.4 Drift/Calendar Proxies

| Feature | Concern | What may be claimed | What may NOT be claimed |
|---|---|---|---|
| `calendar_week` | The model team notes alignment with a policy change and a holiday period. The feature may be capturing staffing reductions, policy shifts, or seasonal claim-volume spikes rather than a stable weekly pattern. | "Claims processed during week 52 have historically had higher breach rates, possibly due to holiday staffing." | "Week 52 causes breaches." The effect is likely non-stationary and may disappear when the policy changes or staffing adjusts. |

**Recommendation:** Replace with more interpretable derived features: `is_holiday_period`, `policy_version_active`, `staffing_level_estimate`. These are more stable under drift and easier to monitor.

| Feature | Current defect | Repair path | Interim status |

| `prior_claim_count_before_t0` | SQL uses ` extraction_date` instead of `< t`. | Fix SQL; recompute for all historical cases; re-evaluate model importance. | **Drop from explanations** until repaired. May still be directionally correct (the bug likely inflates the count by 0–1 claims in most cases), but the exact magnitude is unreliable. |

## 5. Recommendations for Explanation Validation

The following plan is ordered by priority, with the most critical items first.

### Priority 1 — Critical (Immediate)

**1.1 Prefix-Only Feature Recomputation Pipeline**
- **Action:** Build a feature computation pipeline that strictly uses only data with timestamps  *t*. Every feature in the model must pass through this pipeline.
- **Scope:** All 12 global features, all local features, and all sequence patterns.
- **Deliverable:** A `prefix_feature_store` that is the single source of truth for all explanations.
- **Why first:** This is the root cause of the majority of findings in §1. Without this, all downstream explanations are suspect.

**1.2 Fix SQL Bugs for `prior_claim_count_before_t0` and `same_day_document_count_snapshot`**
- **Action:** Change the `prior_claim_count` SQL from `claim_created_at  extraction_date` to `claim_created_at < t0` (strict inequality, using the exact *t* timestamp). Change `same_day_document_count_snapshot` to filter by `upload_timestamp  t0`.
- **Scope:** These are code changes to the feature-store ETL.
- **Validation:** Run the corrected SQL on a historical sample and compare to the buggy version. Quantify the frequency and magnitude of differences.
- **Why high priority:** These are subtle bugs that affect features currently in production. The fix is straightforward and low-risk.

**1.3 Extract `team_assigned_at_coverage_check` to Replace `final_handler_team`**
- **Action:** Parse the Coverage Check Completed event payload (or the immediately preceding event) to extract the handler team at *t*. Store this as a new feature.
- **Validation:** Compare the new feature to `final_handler_team` to quantify the 65 % agreement rate and identify the 35 % of cases where they differ.
- **Why high priority:** `final_handler_team` is rank 3 in importance. Replacing it with a legitimate feature preserves predictive power while eliminating leakage.

### Priority 2 — High (Within 2 Weeks)

**2.1 Historical Feature Timestamp Audit**
- **Action:** For every mutable feature in the feature store, add a `computation_timestamp` field. For `risk_score_current`, backfill historical timestamps if available from audit logs; if not, mark all historical values as `timestamp_unknown` and exclude them from explanations until a snapshotting mechanism is implemented.
- **Scope:** All mutable features, including `risk_score_current`, `employee_experience` (noted in lineage but not in top-12), and any other dynamically updated fields.
- **Deliverable:** Feature-store schema update with timestamp columns and a data-quality report on backfill coverage.

**2.2 Recalibrate Model After Feature Removal**
- **Action:** Retrain or recalibrate the model using only prefix-available features. Compare the recalibrated model's discrimination (AUC-ROC), calibration (Brier score), and explanation stability (SHAP value correlation) to the original model.
- **Expectation:** Discrimination will likely decrease (the leaked features were highly predictive of the outcome by construction). Calibration may improve or degrade depending on how much the leaked features contributed to overfitting.
- **Deliverable:** A comparison report with performance metrics and SHAP value distributions before and after remediation.

**2.3 Process-Conformance Test Suite**
- **Action:** Implement the validation suite described in §2 as automated tests that run on every model explanation before it is presented to a user. The suite should check:
  - Prefix-time availability (feature timestamps  *t*)
  - Activity-order feasibility (activities in explanations are enabled or future-possible at *t*)
  - Same-timestamp ambiguity detection
  - Complete-trace feature flagging
  - Repeated Settlement Decision semantic consistency
- **Implementation:** Use a declarative process model (e.g., DECLARE constraints or a Petri net) encoded in the model-serving layer. Explanations that fail any hard check are suppressed and logged for review.

### Priority 3 — Medium (Within 1 Month)

**3.1 Proxy and Fairness Analysis**
- **Action:** Conduct a formal fairness audit of `claimant_region`, `claimant_channel`, `initial_reserve`, and any replacement features (e.g., `repair_network_coverage_score`).
- **Method:** Compute disparate impact ratios across protected groups (defined by region, language, channel). Test whether the model's breach predictions are calibrated within each group. Assess whether region effects persist after controlling for operational factors.
- **Deliverable:** A fairness report with recommendations for feature modification or model constraints.

**3.2 Explanation Stability Analysis**
- **Action:** For a held-out sample of cases, compare the model's explanations before and after leakage remediation. Quantify:
  - Rank correlation of top-10 features (Spearman)
  - Sign agreement (do the same features have the same direction?)
  - Magnitude change in SHAP values
- **Purpose:** Ensure that the remediated model produces stable, interpretable explanations that do not flip direction or rank unpredictably.
- **Deliverable:** An explanation-stability report with case-level visualizations.

**3.3 Drift Monitoring for Calendar and Policy Proxies**
- **Action:** Implement monitors for `calendar_week` distribution shifts, policy-change events, and holiday periods. When a policy change occurs, automatically flag all `calendar_week`-dependent explanations for review.
- **Implementation:** Use population stability index (PSI) or KL-divergence on the `calendar_week` distribution, with alerts when PSI exceeds a threshold (e.g., 0.1).
- **Deliverable:** A drift dashboard with automated alerting.

### Priority 4 — Ongoing

**4.1 Schema and Process Drift Monitoring**
- **Action:** Monitor for changes in event types, event ordering, and feature definitions. If the normative process model changes (e.g., a new activity is added), automatically update the process-conformance test suite.
- **Method:** Compare incoming trace event types and orderings against the reference process model. Alert on novel event types, novel transitions, or changes in transition frequencies.
- **Deliverable:** A process-drift detection pipeline integrated into the model-monitoring infrastructure.

**4.2 Causal Claim Governance**
- **Action:** Establish a governance policy that distinguishes four levels of claim in all model explanations:
  1. **Predictive association:** "Feature X is correlated with breach in historical data."
  2. **Process-state interpretation:** "Feature X captures the operational state at *t*."
  3. **Causal hypothesis:** "Feature X may contribute to delays, pending experimental evidence."
  4. **Causal evidence:** "An intervention on Feature X has been shown to reduce breach rates in an A/B test."
  - Current explanations should be capped at level 2 unless causal evidence exists. The model team's current interpretations (e.g., "Appeals cause breaches") incorrectly imply level 4.
- **Deliverable:** A labeling convention for explanation narratives and a review checklist.

**4.3 Ongoing Explanation Audits**
- **Action:** Schedule quarterly audits of model explanations using the process-conformance test suite, fairness checks, and drift monitors. Rotate audit responsibility between the model team and an independent reviewer.
- **Deliverable:** Quarterly audit reports with findings and remediation tracking.
