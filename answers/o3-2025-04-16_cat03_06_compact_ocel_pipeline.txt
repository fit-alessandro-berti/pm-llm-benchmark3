## 1. Modeling assumptions
• Object types (exact spelling):  
  Order, Item, Package, Delivery, Invoice, Payment  

• E2O qualifier vocabulary (oneword verbs, active voice):  
  created, added, reserved, packed, dispatched, invoiced, paid, confirmed, closed  

• O2O direction conventions:  
  – Order  Item …… ‘contains’  
  – Package  Item …… ‘packs’  
  – Delivery  Package …… ‘carries’  
  – Invoice  Order …… ‘bills’  
  – Payment  Invoice …… ‘partially_settles’ (no “completes” because V1 is still open after M1 but closed after M2; both rows keep the same qualifier to stay Boolean)

• Down-stream event relations:  
  All logistics events (pack, dispatch, confirm) are linked directly to the Orders in which the affected Items reside.  
  Financial events (invoice, payment) are likewise linked directly to the Orders they monetise.  
  Trade-off: this creates redundancy but supports order-level dashboards without needing O2O propagation.

• Avoiding confusion with analytical propagation:  
  We never manufacture E2O rows from O2O edges in code. Every relation comes from an explicit business event.

• PM4Py version assumption:  
  OCEL lives in `pm4py.objects.ocel.obj.OCEL` in 2.4.1 and in `pm4py.objects.ocel.OCEL` in 2.5.  
  We import the latter and isolate the constructor in one line so that adapting for historical versions is trivial.

## 2. Complete Python pipeline
```python
# A. imports ---------------------------------------------------------------
import pandas as pd
from pm4py.objects.ocel import OCEL           # adapt import path if needed
import pm4py

# helper for tz aware timestamps
def ts(x): 
    return pd.Timestamp(x).tz_localize("UTC")

# B. build objects ---------------------------------------------------------
objects = pd.DataFrame([
    # Orders
    {"ocel:oid":"O100", "ocel:type":"Order"},
    {"ocel:oid":"O200", "ocel:type":"Order"},
    # Items
    {"ocel:oid":"I1", "ocel:type":"Item"},
    {"ocel:oid":"I2", "ocel:type":"Item"},
    {"ocel:oid":"I3", "ocel:type":"Item"},
    # Packages
    {"ocel:oid":"P1", "ocel:type":"Package"},
    {"ocel:oid":"P2", "ocel:type":"Package"},
    # Deliveries
    {"ocel:oid":"D1", "ocel:type":"Delivery"},
    {"ocel:oid":"D2", "ocel:type":"Delivery"},
    # Invoice
    {"ocel:oid":"V1", "ocel:type":"Invoice"},
    # Payments
    {"ocel:oid":"M1", "ocel:type":"Payment"},
    {"ocel:oid":"M2", "ocel:type":"Payment"},
])

# C. build events ----------------------------------------------------------
events_raw = [
    ("E1",  "Create Order",                   ts("2026-04-06 08:00"), {}),
    ("E2",  "Add Item",                       ts("2026-04-06 08:05"), {}),
    ("E3",  "Add Item",                       ts("2026-04-06 08:06"), {}),
    ("E4",  "Create Order",                   ts("2026-04-06 08:10"), {}),
    ("E5",  "Add Item",                       ts("2026-04-06 08:12"), {}),
    ("E6",  "Reserve Stock",                  ts("2026-04-06 08:30"), {}),
    ("E7",  "Pack Package",                   ts("2026-04-06 09:00"), {}),
    ("E8",  "Pack Package",                   ts("2026-04-06 09:05"), {}),
    ("E9",  "Dispatch Package",               ts("2026-04-06 10:00"), {}),
    ("E10", "Dispatch Package",               ts("2026-04-06 10:15"), {}),
    ("E11", "Issue Invoice",                  ts("2026-04-06 11:00"), {}),
    ("E12", "Record Payment",                 ts("2026-04-06 11:30"), {"amount":100}),
    ("E13", "Confirm Delivery",               ts("2026-04-06 13:00"), {}),
    ("E14", "Confirm Delivery",               ts("2026-04-07 09:00"), {}),
    ("E15", "Record Payment",                 ts("2026-04-07 10:00"), {"amount":150}),
    ("E16", "Close Order",                    ts("2026-04-07 10:30"), {}),
    ("E17", "Close Order",                    ts("2026-04-07 10:35"), {}),
]

events = pd.DataFrame([
    dict({"ocel:eid":eid, "ocel:activity":act, "ocel:timestamp":time}, **attrs)
    for eid,act,time,attrs in events_raw
])

# D. build relations -------------------------------------------------------
rel = []

def add(eid, activity, ts_, oid, otype, qual):
    rel.append({"ocel:eid":eid,
                "ocel:activity":activity,
                "ocel:timestamp":ts_,
                "ocel:oid":oid,
                "ocel:type":otype,
                "ocel:qualifier":qual})

# --- manual mapping from narrative ---------------------------------------
# E1 create O100
add("E1","Create Order",ts("2026-04-06 08:00"),"O100","Order","created")
# E2 add I1 to O100
add("E2","Add Item",ts("2026-04-06 08:05"),"O100","Order","added")
add("E2","Add Item",ts("2026-04-06 08:05"),"I1","Item","added")
# E3 add I2 to O100
add("E3","Add Item",ts("2026-04-06 08:06"),"O100","Order","added")
add("E3","Add Item",ts("2026-04-06 08:06"),"I2","Item","added")
# E4 create O200
add("E4","Create Order",ts("2026-04-06 08:10"),"O200","Order","created")
# E5 add I3 to O200
add("E5","Add Item",ts("2026-04-06 08:12"),"O200","Order","added")
add("E5","Add Item",ts("2026-04-06 08:12"),"I3","Item","added")
# E6 reserve stock I1,I3 for both Orders
for oid in ["O100","O200"]:
    add("E6","Reserve Stock",ts("2026-04-06 08:30"),oid,"Order","reserved")
for iid in ["I1","I3"]:
    add("E6","Reserve Stock",ts("2026-04-06 08:30"),iid,"Item","reserved")
# E7 pack P1 with I1,I3 for both Orders
add("E7","Pack Package",ts("2026-04-06 09:00"),"P1","Package","packed")
for iid in ["I1","I3"]:
    add("E7","Pack Package",ts("2026-04-06 09:00"),iid,"Item","packed")
for oid in ["O100","O200"]:
    add("E7","Pack Package",ts("2026-04-06 09:00"),oid,"Order","packed")
# E8 pack P2 with I2 for O100
add("E8","Pack Package",ts("2026-04-06 09:05"),"P2","Package","packed")
add("E8","Pack Package",ts("2026-04-06 09:05"),"I2","Item","packed")
add("E8","Pack Package",ts("2026-04-06 09:05"),"O100","Order","packed")
# E9 dispatch P1 in D1 (affects both orders)
add("E9","Dispatch Package",ts("2026-04-06 10:00"),"P1","Package","dispatched")
add("E9","Dispatch Package",ts("2026-04-06 10:00"),"D1","Delivery","dispatched")
for oid in ["O100","O200"]:
    add("E9","Dispatch Package",ts("2026-04-06 10:00"),oid,"Order","dispatched")
# E10 dispatch P2 in D2
add("E10","Dispatch Package",ts("2026-04-06 10:15"),"P2","Package","dispatched")
add("E10","Dispatch Package",ts("2026-04-06 10:15"),"D2","Delivery","dispatched")
add("E10","Dispatch Package",ts("2026-04-06 10:15"),"O100","Order","dispatched")
# E11 issue invoice V1 for both Orders
add("E11","Issue Invoice",ts("2026-04-06 11:00"),"V1","Invoice","invoiced")
for oid in ["O100","O200"]:
    add("E11","Issue Invoice",ts("2026-04-06 11:00"),oid,"Order","invoiced")
# E12 payment M1 against V1
add("E12","Record Payment",ts("2026-04-06 11:30"),"M1","Payment","paid")
add("E12","Record Payment",ts("2026-04-06 11:30"),"V1","Invoice","paid")
# E13 confirm D1
add("E13","Confirm Delivery",ts("2026-04-06 13:00"),"D1","Delivery","confirmed")
add("E13","Confirm Delivery",ts("2026-04-06 13:00"),"P1","Package","confirmed")
for oid in ["O100","O200"]:
    add("E13","Confirm Delivery",ts("2026-04-06 13:00"),oid,"Order","confirmed")
# E14 confirm D2
add("E14","Confirm Delivery",ts("2026-04-07 09:00"),"D2","Delivery","confirmed")
add("E14","Confirm Delivery",ts("2026-04-07 09:00"),"P2","Package","confirmed")
add("E14","Confirm Delivery",ts("2026-04-07 09:00"),"O100","Order","confirmed")
# E15 payment M2 against V1
add("E15","Record Payment",ts("2026-04-07 10:00"),"M2","Payment","paid")
add("E15","Record Payment",ts("2026-04-07 10:00"),"V1","Invoice","paid")
# E16 close O200
add("E16","Close Order",ts("2026-04-07 10:30"),"O200","Order","closed")
# E17 close O100
add("E17","Close Order",ts("2026-04-07 10:35"),"O100","Order","closed")

relations = pd.DataFrame(rel)

# E. O2O relations ---------------------------------------------------------
o2o = pd.DataFrame([
    # Order contains Item
    {"ocel:oid":"O100","ocel:oid_2":"I1","ocel:qualifier":"contains"},
    {"ocel:oid":"O100","ocel:oid_2":"I2","ocel:qualifier":"contains"},
    {"ocel:oid":"O200","ocel:oid_2":"I3","ocel:qualifier":"contains"},
    # Package packs Item
    {"ocel:oid":"P1","ocel:oid_2":"I1","ocel:qualifier":"packs"},
    {"ocel:oid":"P1","ocel:oid_2":"I3","ocel:qualifier":"packs"},
    {"ocel:oid":"P2","ocel:oid_2":"I2","ocel:qualifier":"packs"},
    # Delivery carries Package
    {"ocel:oid":"D1","ocel:oid_2":"P1","ocel:qualifier":"carries"},
    {"ocel:oid":"D2","ocel:oid_2":"P2","ocel:qualifier":"carries"},
    # Invoice bills Order
    {"ocel:oid":"V1","ocel:oid_2":"O100","ocel:qualifier":"bills"},
    {"ocel:oid":"V1","ocel:oid_2":"O200","ocel:qualifier":"bills"},
    # Payment partially settles Invoice
    {"ocel:oid":"M1","ocel:oid_2":"V1","ocel:qualifier":"partially_settles"},
    {"ocel:oid":"M2","ocel:oid_2":"V1","ocel:qualifier":"partially_settles"},
])

# F. basic validations -----------------------------------------------------
assert events["ocel:eid"].is_unique
assert objects["ocel:oid"].is_unique
assert relations["ocel:eid"].isin(events["ocel:eid"]).all()
assert relations["ocel:oid"].isin(objects["ocel:oid"]).all()
assert o2o[["ocel:oid","ocel:oid_2"]].stack().isin(objects["ocel:oid"]).all()
# activity / timestamp match
rel_chk = relations.merge(events[["ocel:eid","ocel:activity","ocel:timestamp"]],
                          on="ocel:eid", suffixes=("","_evt"))
assert (rel_chk["ocel:activity"]==rel_chk["ocel:activity_evt"]).all()
assert (rel_chk["ocel:timestamp"]==rel_chk["ocel:timestamp_evt"]).all()
# avoid duplicate relation rows
assert not relations.duplicated().any()

# G. OCEL construction & some prints --------------------------------------
ocel = OCEL(events=events, objects=objects, relations=relations, o2o=o2o)

print(ocel)

print("\nActivity frequencies:")
print(pm4py.ocel_activity_frequencies(ocel))

print("\nObject-type frequencies:")
print(pm4py.ocel_object_type_frequencies(ocel))

print("\nDeclared object types:")
print(pm4py.ocel_get_object_types(ocel))

print("\nActivities per object type:")
print(pm4py.ocel_object_type_activities(ocel))

# H. Flattenings per requested object types -------------------------------
flatten_dfg   = {}
flatten_skel  = {}
for ot in ["Order","Package","Delivery","Invoice"]:
    flat = pm4py.ocel_flattening(ocel, object_type=ot)
    dfg  = pm4py.discover_dfg(flat)
    skel = pm4py.discover_log_skeleton(flat)
    flatten_dfg[ot]  = dfg
    flatten_skel[ot] = skel

# I. Object-centric discovery artefacts -----------------------------------
oc_dfg = pm4py.discover_ocdfg(ocel)
otg    = pm4py.discover_otg(ocel)
etot   = pm4py.discover_etot(ocel)
ocpn   = pm4py.discover_oc_petri_net(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# J. optional visualisations (commented) ----------------------------------
# pm4py.view_ocdfg(oc_dfg)
# pm4py.view_oc_petri_net(ocpn)
```

## 3. Data-model audit
Object list  
Order: O100, O200  
Item: I1, I2, I3  
Package: P1, P2  
Delivery: D1, D2  
Invoice: V1  
Payment: M1, M2  

O2O cardinalities  
contains (OrderItem): 3  
packs (PackageItem): 3  
carries (DeliveryPackage): 2  
bills (InvoiceOrder): 2  
partially_settles (PaymentInvoice): 2  

Activity  object types  
Create Order …… Order  
Add Item …… Order, Item  
Reserve Stock …… Order, Item  
Pack Package …… Order, Package, Item  
Dispatch Package …… Order, Package, Delivery  
Issue Invoice …… Order, Invoice  
Record Payment …… Invoice, Payment  
Confirm Delivery …… Order, Package, Delivery  
Close Order …… Order  

Most convergent event: E7 (Pack Package P1) – it touches six objects across four types, linking the two orders early.  
Most divergent event: E11 (Issue Invoice) – one Invoice radiates to both Orders.

## 4. Expected flattened behavior
• Order flattening  
  – Trace = all events that reference a given Order.  
  – Shared events (E6, E7, E9, E11) appear in both order traces.  
  – DFG edges: CreateAddReservePackDispatchConfirmClose plus Invoice/Payment branches.  
  – Concurrency between dispatches and invoicing is lost; duplicated payments make the control-flow look serial yet it stems from shared artefacts.

• Package flattening  
  – Two traces (P1, P2).  
  – P1 trace mixes data from two Orders; its DFG includes dispatch and confirmation but no payment.  
  – No lifecycle for package creation (none in narrative) – so model begins with Pack.

• Delivery flattening  
  – Two traces (D1, D2).  
  – Edges: DispatchConfirm.  
  – Order logic invisible; falsely looks like instant shipping.

• Invoice flattening  
  – One trace (V1).  
  – Edges: IssuePaymentPayment.  
  – Lacks fulfilment context; makes payments seem consecutive although they could be parallel.

Payment flattening would be almost meaningless: each trace would contain exactly one “Record Payment” event, so discovery collapses to a trivial model.

## 5. Expected object-centric structures
• OC-DFG: highlights the two major strands (physical vs. financial).  
  Pack Package is a junction where Items, Orders, and Package join; Issue Invoice is another hub where Orders and Invoice meet; both nodes have high weighted degrees due to multi-typing.

• OTG:  
  Order  Item (dense), Package  Order (via shared packing), Delivery  Order (via dispatch), Invoice  Order, Payment  Invoice.  
  Path O100  P1  O200 confirms the cross-order packaging.

• ET–OT graph:  
  Reserve Stock connects Item and Order layers; Pack connects three layers simultaneously; therefore ET–OT shows tri-partite hyper-edges.

• Object-centric Petri net:  
  – Places for stock reserved, packed, shipped, delivered, invoiced, paid, closed.  
  – Token flow of P1 progresses both O100 and O200 marking; V1 place merges the two order tokens for the financial branch.  
  – M1 and M2 transitions both consume from the same invoice place, emulating partial settlement.

• Object interaction summary:  
  P1 interacts with O100 and O200; V1 interacts with both orders; M1 and M2 interact only with V1 (and by transitivity the two orders).  
  The summary shows O200 finished (token in closed) slightly before O100 because D2 was later.

## 6. Modeling alternatives
1. Source-minimal relations  
   Link every event only to its primary business object (e.g., Dispatch only to Delivery).  
    OC-DFG becomes sparse; flattening on Order would miss logistics and finance unless analysts propagate through O2O.

2. Full operational involvement  
   Add every “upstream” object as relation – even Items on Financial events.  
    Larger relation table; OTG thick with edges; risk of analytic noise but easier trace-level KPIs.

3. O2O-propagated analytical relations  
   Keep relations minimal in storage, then expand at query time by traversing O2O.  
    Smaller persisted OCEL, but correctness now depends on tool support for dynamic expansion.

## 7. Failure modes
1. Relation inflation slows discovery and makes false causal loops.  
2. Missing direct E2O links forces analysts to guess through propagation.  
3. Treating O2O propagation as factual observation pollutes the ground truth.  
4. Flattening duplicated shared events yields over-counted performance stats.  
5. Ambiguous allocation of Payment amounts when one payment is meant for several orders.  
6. Payment trace length =1 destroys control-flow mining if Payments were the focus.  
7. Using the wrong OCEL constructor path breaks the pipeline silently.  
8. Inventing an ordering for same-timestamp events may invent artificial causality (not triggered here, but common).

## 8. Final semantic checks
1. Objects table lists exactly 12 OIDs, one per narrative artefact.  
2. relations where qualifier “packed” reference P1 and P2 only once each.  
3. E7 relation count is 6 (2 Orders, 2 Items, 1 Package, 1 activity row per link).  
4. O2O row with qualifier “packs” for (P1,I1) exists and direction is PackageItem.  
5. In events, “amount” attribute exists only for E12 and E15 and equals 100 and 150.  
6. There is precisely one Invoice (V1) and both Orders appear in an O2O edge where qualifier is “bills”.
