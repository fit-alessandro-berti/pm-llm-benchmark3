## 1. Normalization Assumptions

**Interval construction, in fixed order.** For a displayed time `D` on a source clock:
1. Resolution interval in source-clock time: exact-second HUB `[D-0.5s,D+0.5s]`; floor to minute `[D,D+59.999s]`; round to 10s `[D-5s,D+5s]`; round to minute `[D-30s,D+30s]`. This is applied *before* clock correction, as instructed.
2. Clock correction: `clock_offset = recorded_clock - true_clock`, offset in `[a,b]`, so true local time is `[clock_low-b, clock_high-a]`. E.g. OPS-BER offset in [-90s,+120s] gives true local `[D-120s, D+59.999s+90s]`.
3. Time-zone conversion of the corrected local interval to UTC: June CEST (Berlin) UTC+2, BST (London) UTC+1, EDT (New York) UTC-4; 2025-10-26 Berlin CET UTC+1 / CEST UTC+2 on the fold.

No midpoint is used for any primary conclusion. Midpoints appear only in §5 as a labelled lossy comparison. Endpoints are treated as inclusive; differences of 1-3 s at a boundary (e.g. T-402, T-404, T-408) are flagged as boundary-sensitive, not enforcement-grade.

**Primary decision rules.** SLA tolerance addition 0 min for §3; temporal-profile primary zeta = 1. §4 varies both. Definitions: CERTAIN_PASS = every feasible duration passes; CERTAIN_VIOLATION = every feasible duration violates; POSSIBLE_VIOLATION = feasible set contains both pass and violate; INDETERMINATE = not testable under stated semantics because evidence is missing, unbounded in practice, internally inconsistent, or a stated bound is only a weak estimate. For a two-sided profile band, wholly below/above = certain violation, wholly inside = certain pass, partial overlap = possible violation. Severity = size of actual (certain) or potential (possible) excess over the limit; Confidence = width/hardness of the underlying bounds.

**Material assumptions, by case.**
- *Independence:* event intervals are treated as independent (no shared clock error) except for the explicit joint constraints below. This can only widen durations.
- *T-404 inferred start:* Investigation_Start is inferred as Investigation_Complete minus the signed duration [18,25] min, retaining full uncertainty. It happens to lie after Alert_Received, so no extra causal truncation is needed. Investigation_Complete is not itself a start.
- *T-405 DST fold:* unpruned, each event is a union of two 3-min UTC intervals (CEST fold and CET fold). I impose the stated ingestion order Alert <= Investigation <= Containment as a true-time causal constraint. Only one fold combination survives (Alert CEST, Investigation CET, Containment CET); see §2. Without that assumption the case would be INDETERMINATE. I do *not* collapse the union blindly before pruning.
- *T-406 mobile entry delay (primary):* the timestamp is user-entered, so up to 5 min late entry is treated as late *recording*: occurrence estimate = corrected recorded time minus a delay in [0,300s], expanding the interval only downward (earlier). Sensitivity in §4 shows the alternative semantics (delay is only provenance lag after a system-captured occurrence, interval unchanged) and that it changes S2.
- *T-407:* Alert_Sent is not Alert_Received. Primary classification for Alert_Received-dependent pairs is INDETERMINATE: no receipt acknowledgement, delivery within [0,20] min is not proven, and "receipt <= investigation" is not logged. Conditional arithmetic *if* delivery and causality are assumed is shown for transparency, but not used for enforcement.
- *T-409:* NTP diagnostics are missing; [-12,+12] min is only a weak engineering estimate, not a validated hard bound. Primary classification for Investigation-dependent pairs is INDETERMINATE. Conditional arithmetic treating the estimate as a hard bound is shown, but not used as certain.
- *Semantics:* SENSOR events are completion events, matching Containment_Complete completion; no additional shift is applied. Close_Incident, Investigation_Start etc. are taken at face value as the named lifecycle points.
- *Missing S3:* where no Close_Incident exists (T-402 to T-407, T-409) S3 and Containment->Close profile are not testable and are omitted, not scored as pass.

## 5. PM4Py Temporal-Conformance Code

The code below reconstructs intervals with pandas + `zoneinfo`, represents the DST fold as alternative intervals and prunes by the stated ingestion order, derives interval classifications, and *separately* builds a midpoint-only log for PM4Py. PM4Py does not natively resolve timestamp uncertainty; the midpoint log is a lossy approximation. Diagnostic output shape varies by PM4Py version, so that call is isolated with a fallback message.

```python
import pandas as pd
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

# ---- source metadata: semantics, offset bound (s), tz ----
SRC = {
    "HUB":        ("exact_second", (-1, 1),      "UTC"),
    "OPS-BER":    ("floor_minute", (-90, 120),   "Europe/Berlin"),
    "SENSOR":     ("round_10s",    (-5, 5),      "UTC"),
    "VENDOR-NY":  ("floor_minute", (-180, 180),  "America/New_York"),
    "LEGACY-BER": ("floor_minute", (-60, 60),    "Europe/Berlin"),
    "MOBILE-LON": ("round_minute", (-300, 300),  "Europe/London"),
}
EPS = timedelta(milliseconds=999)  # 59.999s style endpoints, approx.

def clock_interval(rec, sem):
    if sem == "exact_second": return rec - timedelta(seconds=0.5), rec + timedelta(seconds=0.5)
    if sem == "floor_minute": return rec, rec + timedelta(seconds=59) + EPS
    if sem == "round_10s":    return rec - timedelta(seconds=5), rec + timedelta(seconds=5)
    if sem == "round_minute": return rec - timedelta(seconds=30), rec + timedelta(seconds=30)
    raise ValueError(sem)

def normalize(recorded, system, override_offset=None, entry_delay_s=0):
    """Return list of (low_utc, high_utc) alternatives (union for DST fold)."""
    sem, (a, b), tzname = SRC[system]
    if override_offset is not None: a, b = override_offset
    rec = datetime.fromisoformat(recorded)
    cl, ch = clock_interval(rec, sem)              # 1) resolution
```

## 6. Evidential Sufficiency

For every POSSIBLE_VIOLATION / INDETERMINATE in §3, the minimum evidence to make it certain (i.e. to shrink the interval wholly to one side of the limit, or to prove the missing bound/activity):

- **T-401 P Alert->Inv (PV):** stronger synchronisation / resolution evidence for OPS-BER (NTP offset telemetry at 10:14 narrowing the combined 270 s width to <~60 s, or second-precision capture) would decide whether the true duration is <=780 s. Semantic evidence is not the issue.
- **T-402 S2 + P Inv->Contain (PV):** OPS-BER offset telemetry narrowing the 270 s width so that Inv high/low no longer straddles 2700 s (need ~62 s of tightening at the relevant end). Duration evidence (a second independent OPS-BER reading) would also work.
- **T-403 S1, P Alert->Inv, P Alert->Contain (PV):** stronger synchronisation for VENDOR-NY (event-level sync, recorded offset at time of alert, second-precision rather than floor-minute). The 420 s width must shrink by >242 s to settle S1. Alternatively a VENDOR-NY receipt acknowledgement with HUB clock.
- **T-404 S1, S2, P Alert->Inv, P Inv->Contain (PV):** missing-activity evidence — the actual Investigation_Start event (system-logged). That alone collapses the 423 s inferred width to HUB width and settles all four. Narrowing the signed duration from [18,25] to a few minutes would also suffice for S1; S2 needs start evidence precise to ~3 s at the extreme, i.e. effectively the start event itself.
- **T-405 S1, P Alert->Inv (PV):** semantic evidence — a logged DST fold flag (fold=0/1) or UTC offset at capture — plus, to settle S1, second-precision / tighter LEGACY-BER offset (current pruned width 180 s straddles 900 by 180 s). Without the ingestion-order assumption, no amount of fold flagging alone helps unless ingestion is proven to reflect true order; a UTC-stamped ingestion with bounded ingestion delay would do both.
- **T-406 S1, S2, P Alert->Inv, P Inv->Contain (PV):** semantic evidence first — whether entry delay shifts occurrence or only provenance, and a system capture timestamp (device clock at event) separate from user entry time. That single fact moves S2 from PV to CP under base semantics. Synchronisation evidence (MOBILE-LON offset telemetry, second precision) is then needed to settle S1, whose 16-min width straddles every limit.
- **T-407 S1, P Alert->Inv, P Alert->Contain (IND):** missing-activity evidence — a Alert_Received acknowledgement (receiver log with HUB-quality clock). Network latency bounds and a causal assumption cannot substitute: even with them the conditional interval is PV, and delivery itself is unproven. A receipt ack collapses the pair to HUB precision.
- **T-409 S1, S2, P Alert->Inv, P Inv->Contain (IND):** stronger synchronisation evidence — restored NTP diagnostics for OPS-BER at 18:04 giving a validated hard bound (ideally the standard [-90,+120] s, or tighter). A weak estimate, however narrow it looks, cannot be upgraded to certain by arithmetic. With the standard bound, S1 interval would be ~[959,1222]-style and testable; with second-precision it would be certain.

In all PV cases, note the asymmetry: to prove a *violation* certain one must raise the interval minimum above the limit; to prove *pass* certain one must lower the maximum below it. Evidence that only narrows one end may settle one direction only.

## 7. Governance Recommendation

**Timestamp and clock controls.**
1. *Store UTC, retain raw.* Persist every event as UTC instant (with sub-second precision) plus the raw displayed string, source system, time zone, and resolution/flooring semantics. Never overwrite raw with a converted or rounded value. Re-derivation must be possible.
2. *Offset telemetry as evidence.* NTP/PTP diagnostics (measured offset, sync state, last-sync time) must be captured per event or per minute and stored alongside it, with alerting when a source exceeds its budgeted bound. A missing-diagnostics hour (T-409) must automatically mark dependent evidence INDETERMINATE in downstream reporting, not silently fall back to an engineering estimate.
3. *Resolution metadata.* Record whether a timestamp is exact, floored, or rounded, and to what granularity, at capture time. Floor-to-minute sources (OPS-BER, VENDOR-NY, LEGACY-BER) should be migrated to second-precision; until then their 60 s floor must be part of the stored uncertainty, not an afterthought.
4. *Time-zone and DST.* Store the UTC offset in effect and, for ambiguous local times, the fold indicator (fold=0/1) and IANA zone name. Prohibit naive local timestamps in any store that crosses a DST transition. Ingestion must record both source and ingestion UTC times so order-vs-true-time assumptions are auditable (T-405).
5. *Start/complete semantics.* Lifecycle events must declare whether they are start, complete, or point events, and systems must log both start and complete where both exist (T-404). Inferring a start from a complete minus a duration is a fallback for analysis only and must be flagged as inferred, never back-filled as if logged.
6. *Causal identifiers.* Every Alert needs a correlation ID carried through Sent -> Received -> Investigation -> Containment -> Close, with explicit receipt acknowledgements. Alert_Sent must never be used as Alert_Received in SLA computation (T-407). Mobile/user-entered times must carry a flag distinguishing system-captured event time from user entry time, and entry delay must be a separate field, not folded into occurrence time (T-406).
7. *Enforcement policy for intervals.* CERTAIN_VIOLATION may trigger formal SLA enforcement. POSSIBLE_VIOLATION triggers investigation and evidence-gathering (per §6), not sanction, because every feasible world includes a compliant one. INDETERMINATE triggers evidence repair, not penalty or pass. Tolerance additions and zeta choices must be set by policy *before* the fact, published, and applied uniformly — they must not be tuned per case to flip a finding (§4 shows how easily +2/+5 min or z=2 would). Boundary differences of a few seconds are never enforcement-grade.
8. *Provenance and audit.* Keep an immutable event-evidence log (raw, normalised interval, assumptions version, bound provenance — hard diagnostic vs estimate vs inference). Re-running conformance (including any PM4Py midpoint diagnostics) must reproduce the interval conclusions from that provenance, and midpoint/point-estimate tooling must be labelled lossy wherever it is used for exploration.
