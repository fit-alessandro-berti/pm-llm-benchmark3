# 1. Objectives and constraints

**Objectives (none of them is optimized alone)**

| Objective | What "good" means here | Typical conflict |
|---|---|---|
| SLA protection | Urgent/high cases finish inside their SLA window | Pulls work toward a few specialists |
| Short-term throughput | Low waiting plus service time across the batch | Favors first-available routing and skill mismatch |
| Quality | Low rework and appeal rates | Favors specialist-only routing and queues |
| Continuity of ownership | Few handovers; no case pushed above 2 reassignments | Keeps work with overloaded or weakly skilled owners |
| Workload fairness | Balanced new assignments; no extra load on high-overtime-risk people | Conflicts with continuity (David, Bruno and Iris own cases) |
| Skill development | At least 20% of normal/low assignments support documented training priorities | Slower service and supervisor time |
| Resilience | No single point of failure in Security and Approval; scarce capacity kept in reserve | Conflicts with "always use the best person" |

**Safety/compliance constraints (hard: filtered out, never traded against score)**

- H1. Skill level 0 never performs the activity.
- H2. Security Review is done by level 3, or by level 1–2 only with R7_Gita or R8_Hugo as named supervisor (rule 6).
- H3. Final Approval is finalized only by level 2–3; level 1 may prepare but not finalize (rule 7).
- H4. Urgent/high cases need a performer at level 2 or above, or a level 1 performer with a named supervisor (rule 2).
- H5. No resource gets more than 4 new assignments per batch (rule 1). I count supervision, briefing and shadowing roles too, which is the conservative reading.
- H6. Quality Checks are batched only if priority is normal/low and SLA remaining is above 24h (rule 8).
- H7. Estimated effort must fit the resource's remaining hours.

**Gated constraints (default is binding; an exception needs a logged justification)**

- G1. No additional work goes to overtime-risk "high" resources (Bruno, David, Iris) unless the case is urgent and no safer feasible alternative exists (rule 4).
- G2. For high-complexity cases (assumed threshold: complexity ≥ 0.70) with high handover cost, the owner keeps the case. The exception is an owner at level 0–1 with no feasible supervision (rule 5).
- G3. A case is not moved to a third reassignment unless the alternative is an SLA breach or a hard-rule violation. This comes from the evidence that more than 2 reassignments means 1.8x rework and 1.4x appeals.

**Preference trade-offs (soft: scored and weighted)**

- Skill match versus workload balance.
- Continuity versus overtime relief.
- Training share versus speed. Rule 3 is a batch-level target that yields when SLA risk is not acceptable.
- Using specialists now versus keeping scarce specialist capacity free.
- Team proximity, used only as a tie-breaker.

**Interpretation issue in the data**

The notes suggest C015 as security training for Eva/Jonas and C010 as a "trainee approval". But Eva and Jonas have Security = 0, and the documented approval trainees (David, Hugo) have Approval = 0. I resolve this conservatively:

- Level 0 people may only shadow (observe, no execution, no sign-off).
- Shadowing is reported separately from hands-on training.
- Promoting someone from level 0 to level 1 is a management decision, not something the routing policy does.

# 2. Assignment policy

**Principle:** rules first, scores second, people last. Hard rules decide who may do the work, a small transparent score ranks the remaining options, and team leads and workers can override with a reason code.

```
INPUT : queue Q, resources R, skill matrix, roster (hours, overtime risk),
        learned parameters (service time by activity x skill level x complexity,
        handover waiting penalty, rework rates)

STEP 0  URGENCY SCORING (order of treatment)
  prio_w   = {urgent 1.0, high 0.7, normal 0.4, low 0.2}
  pressure = clip(expected_remaining_effort(c) / sla_time_remaining(c), 0, 1)
  U(c)     = 0.5 * prio_w + 0.5 * pressure
  band(c)  = RED    if priority = urgent or SLA <= 4h or pressure >= 0.5
             AMBER  if priority = high   or SLA <= 12h
             GREEN  otherwise
  sort Q by band (RED, AMBER, GREEN), then U descending, then earliest deadline

STEP 1  ELIGIBILITY FILTER (hard rules H1-H7, gates G1-G3)
  for each case c, build the options:
     solo(r)                 r performs alone
     pair(r, s)              r performs, s supervises (trainee work; Security L1-2; Approval prepare/finalize)
     owner_plus(r, owner)    r performs the activity, current owner keeps ownership and briefs r
     shadow(r, t)            r performs, t observes only (t may be level 0)
  drop options violating H1-H7
  drop options on high-overtime resources unless band = RED and no other option is feasible (G1)
  if complexity >= 0.70 and handover = high: keep only options where the owner stays owner (G2)
  if reassignment_count >= 2: drop ownership-changing options unless nothing else is feasible (G3)

STEP 2  SCORE EACH REMAINING OPTION (every component in [0,1])
  SKILL       L3 = 1.0; L2 = 0.7 (0.5 if complexity >= 0.70); supervised L1 = 0.3
  CONTINUITY  1.0 if the owner keeps ownership
              else 1 - band_penalty{none 0, low 0.2, medium 0.5, high 0.9}
                   - 0.3 if the move would make reassignment_count > 2
                   + 0.1 if the new owner is in the same team
  WORKLOAD    1 - (0.5 * open_cases / max_open + 0.5 * planned_hours / hours_remaining),
              multiplied by {low 1.0, medium 0.8, high 0.4} for overtime risk
  TRAINING    1.0 hands-on match with a documented training priority
                  (GREEN band, complexity <= 0.5, supervisor has capacity)
              0.5 shadowing that matches a training priority; 0 otherwise
  RESILIENCE  - penalty if r is one of <= 2 specialists of a bottleneck skill (Security, Approval)
                and the case needs a different skill that others can cover
              - penalty if r would hold > 50% of this batch's work for one skill
              + credit if the option adds a second or third capable person for a thin skill

  weights by band (starting values, agreed with team leads and worker representatives,
  re-calibrated quarterly from the log):
              SKILL  CONTINUITY  WORKLOAD  TRAINING  RESILIENCE
     RED       0.35     0.25       0.20      0.00       0.20
     AMBER     0.30     0.30       0.20      0.05       0.15
     GREEN     0.20     0.20       0.25      0.20       0.15

STEP 3  ASSIGN GREEDILY in urgency order, updating provisional loads and hours.

STEP 4  BATCH-LEVEL REPAIR
  check: cap of 4 per resource; training share >= 20% of GREEN cases;
         no skill with one person carrying everything; supervisors not over-committed
  if a check fails: try the swap with the smallest score loss among GREEN cases only
  if the training target cannot be met without SLA risk or overtime: record "training debt"
     and carry it into the next batch (do not force it)

STEP 5  TIE-BREAKING (deterministic, in this order)
  current owner > same team > lower overtime risk > fewer open cases
  > longest time since this person last received this type of work (rotation) > resource id

STEP 6  EXCEPTIONS
  no feasible option          -> try supervised pair -> escalate to team lead (never auto-break H1-H4)
  SLA breach unavoidable      -> pick the option with least expected lateness, notify lead and customer owner
  overtime exception          -> named approver plus reason code; offset by removing another case
  case would exceed 2 moves   -> "ownership lock": only a team lead can move it again
  absence / new urgent case   -> re-run only for affected cases; do not reshuffle work already started
  worker or lead override     -> always allowed, logged with reason code, reviewed monthly as feedback

STEP 7  OUTPUT for every assignment
  assignment_reason code (e.g. OWNER_SPECIALIST, SPECIALIST_OWNER_RETAINED, OVERTIME_RELIEF,
  TRAINING_SUPERVISED, TRAINING_SHADOW, QC_BATCH, NEW_CASE_BALANCE, EXCEPTION_OVERTIME, MANUAL_OVERRIDE),
  the two factors that decided it, and the runner-up option with why it was not chosen.
```

**Socio-technical safeguards**

- The weights are negotiated policy choices, not facts, and they are published.
- The score ranks options for a case; it never ranks people. Component scores are not used in performance appraisal.
- Training assignments are opt-in and come with protected supervisor time.
- Supervisors' support work counts as workload.
- A person can flag "I am at capacity" and trigger a re-run without having to justify it.
- Overrides are treated as information about where the policy is wrong, not as non-compliance.

**Where the baselines are legitimately better**

- First-available suits homogeneous, low-complexity, low-risk work, where its simplicity and perceived neutrality are real advantages.
- Specialist-only suits low volumes where an error is very costly.

**Costs of the proposed policy**

- It is more complex to run and explain.
- It needs supervisor time.
- It relies on negotiated weights and on estimated parameters that can be wrong.
- It can hide load in support roles.

It is a compromise that needs monitoring, not an optimum.

# 5. Explanation to workers

**How work is assigned, and why**

Work is assigned by a small set of rules that everyone can read. The aim is to get customers served on time without wearing people out, and to give everyone a fair chance to grow.

1. **Safety rules come first.** Some tasks (for example Security Review and Final Approval) need a certain qualification, or a named colleague supporting you. Nobody is put in a position where they must sign off something they are not yet cleared for.
2. **Cases stay with the person who knows them.** If you own a case, you normally keep it, especially if it is complex. Handing cases around costs time and frustrates customers and colleagues.
3. **Urgent cases go to someone who can finish them in time.** If that is not the owner, the owner stays involved and briefs the colleague. This is support, not a judgement on the owner.
4. **Workload matters.** If you are already at risk of overtime, you should not receive additional work. Sometimes a case will be moved away from you for that reason. That is protection, not a sign of distrust.
5. **Learning is planned in.** If you have an agreed development goal, you will get suitable, non-urgent cases with a colleague's support, or a chance to observe. On busy days this may be postponed. We keep track so it is made up later.
6. **Scarce expertise is kept available.** Specialists are not automatically given everything, so they stay free when they are really needed.

**What you will see:** every assignment carries a short reason, for example "you already own this case and have the right skill" or "moved to balance workload". You can also ask which alternative was considered.

**What this is not:** it is not a ranking of people and it is not used for performance appraisal. Supervising and briefing colleagues counts as real work.

**Your voice:** if an assignment does not make sense, or if you are at capacity, tell your team lead. Assignments can be changed, and your feedback is used to improve the rules. The rules and their weights are reviewed regularly together with team representatives.

# 6. Process-mining audit indicators

All indicators are computed per week and segmented by team, activity, priority and complexity band. They are compared against a pre-deployment baseline period and used to audit the policy, not to rank individuals.

| Indicator | Definition from the event log | Signal to investigate |
|---|---|---|
| Handover frequency | Share of consecutive events in a case where `org:resource` changes; edge weights of the handover-of-work network; cross-team handover share via `team` | Rising handovers per case; new heavy edges; ping-pong (A to B to A) |
| Reassignment count | Maximum `reassignment_count` per case; share of cases above 2; changes of `current_owner` per case | Any growth in the above-2 share; reassignments on cases with `handover_cost_band` = high |
| Skill mismatch | Join `org:resource` and `required_skill` to the skill matrix. Count level 0 events; level 1 events without a supervision reason code; urgent/high events below level 2 unsupervised; Security or Approval rule breaches | Target is zero for hard-rule breaches; trend the share of level 2 work on high-complexity cases |
| Workload distribution | Assignments and service hours per resource per day; Gini coefficient or max/median ratio; `workload_snapshot` at assignment; count of support roles; resources above 4 assignments per batch | Gini rising; hidden load on supervisors; cap breaches |
| Overtime risk exposure | Share of assignments to resources flagged high at assignment time (roster join, or proxy: `workload_snapshot` above threshold or events outside shift hours); share with reason `EXCEPTION_OVERTIME`; after-hours events | Non-urgent assignments to high-risk resources; exceptions clustering on the same people |
| SLA misses | Case completion timestamp after `sla_deadline`; lateness distribution; near misses (under 10% slack); by priority and by owner-changed versus not | Misses on urgent/high; misses linked to handovers or batching |
| Rework/appeal after assignment | Share of cases with Rework Correction (or an appeal activity) after an assignment event, by skill level, owner change, trainee flag and reassignment count; repeated Technical Diagnosis loops (variants) | Rework for supervised trainee work clearly above the competent baseline; loops after handovers |
| Training assignment share | Among normal/low cases: share with `assignment_reason` TRAINING_SUPERVISED (hands-on) and TRAINING_SHADOW, reported separately; coverage per person with a documented priority; skill-level progressions over time | Below 20% for several weeks; training debt growing; training always going to the same people |
| Specialist bottleneck indicators | Waiting time before Security Review and Final Approval (performance DFG incoming edges; case waiting time); queue length over time; share of each activity done by its top resource; count of people at level 2 or above per skill | Median wait growing; one person above 50–60% of an activity; bench size of 1 or 2 |
| Deviations from assignment policy | Replay the policy on the logged state (queue, loads, skills) and compare the recommendation with the actual `org:resource`; share and reasons of `MANUAL_OVERRIDE`; missing reason codes; batches formed against rule 8 | High override rate for one rule means the rule is probably wrong; unexplained deviations; outcomes of overrides versus recommendations |
| Outcome fairness (extra) | Distribution of urgent, complex and training cases per person; overrides requested versus granted per team | Systematic differences between teams or individuals |

Deviations are read in both directions. If overridden assignments perform better than recommended ones, the policy should change, not the people.

# 7. PM4Py implementation sketch

Assumptions: the log has one row per event; a start timestamp (`start_timestamp`) is available or derived from lifecycle transitions, because service time cannot be computed from a single timestamp; the skill matrix and roster are maintained as separate tables.

```python
import pandas as pd
import networkx as nx
import pm4py

CASE, ACT, TS, RES = "case:concept:name", "concept:name", "time:timestamp", "org:resource"

df = pd.read_csv("service_log.csv")
df = pm4py.format_dataframe(df, case_id=CASE, activity_key=ACT, timestamp_key=TS)
df["sla_deadline"] = pd.to_datetime(df["sla_deadline"], utc=True)
df = df.sort_values([CASE, TS]).reset_index(drop=True)

skills = pd.read_csv("skill_matrix.csv", index_col="resource")      # columns = skills, values 0..3
roster = pd.read_csv("roster.csv", parse_dates=["date"])            # resource, date, overtime_risk
HIGH_PRIO = {"urgent", "high"}

def resource_structure(df):
    """Resource networks, roles and similarity: who hands over to whom, who can back up whom."""
    hw = pm4py.discover_handover_of_work_network(df)                 # SNA object (pm4py >= 2.7)
    wt = pm4py.discover_working_together_network(df)
    sim = pm4py.discover_activity_based_resource_similarity(df)
    roles = pm4py.discover_organizational_roles(df)
    pm4py.save_vis_sna(hw, "handover_network.html")                  # or pm4py.view_sna(hw)

    g = nx.DiGraph()
    for (a, b), w in hw.connections.items():
        g.add_edge(a, b, weight=w)
    brokers = nx.betweenness_centrality(g, weight="weight")          # single points of failure
    return hw, wt, sim, roles, brokers

def learn_parameters(df):
    """Estimate the parameters the policy uses; keep them simple and inspectable."""
    service = pm4py.get_service_time(df, start_timestamp_key="start_timestamp",
                                     aggregation_measure="median")
    df = pm4py.insert_case_service_waiting_time(df, start_timestamp_key="start_timestamp")

    perf_dfg, sa, ea = pm4py.discover_performance_dfg(df)
    bottleneck_wait = {edge: v["median"] for edge, v in perf_dfg.items()
                       if edge[1] in ("Security Review", "Final Approval")}

    df["skill_level"] = [skills.at[r, s] if r in skills.index and s in skills.columns else None
                         for r, s in zip(df[RES], df["required_skill"])]
    grp = df.groupby(CASE)
    df["prev_owner"] = grp["current_owner"].shift()
    df["owner_changed"] = df["prev_owner"].notna() & (df["prev_owner"] != df["current_owner"])
    df["wait_before"] = (df["start_timestamp"] - grp[TS].shift()).dt.total_seconds() / 3600
    df["high_complexity"] = df["case_complexity"] >= 0.70

    handover_penalty = (df.groupby(["high_complexity", "handover_cost_band", "owner_changed"])
                          ["wait_before"].median().unstack())
    df["service_h"] = (df[TS] - df["start_timestamp"]).dt.total_seconds() / 3600
    service_by_skill = df.groupby([ACT, "skill_level"])["service_h"].median().unstack()
    return df, service, bottleneck_wait, handover_penalty, service_by_skill

def audit_indicators(df):
    grp = df.groupby(CASE)
    out = {}

    prev_res = grp[RES].shift()
    df["handover"] = prev_res.notna() & (prev_res != df[RES])
    out["handovers_per_case"] = df.groupby(CASE)["handover"].sum().mean()
    max_reassign = grp["reassignment_count"].max()
    out["share_cases_gt2_reassign"] = (max_reassign > 2).mean()

    supervised = df["assignment_reason"].fillna("").str.contains("SUPERVISED|SHADOW")
    df["hard_mismatch"] = (
        (df["skill_level"] == 0)
        | ((df["skill_level"] == 1) & df["case_priority"].isin(HIGH_PRIO) & ~supervised)
        | ((df[ACT] == "Security Review") & (df["skill_level"] < 3) & ~supervised)
        | ((df[ACT] == "Final Approval") & (df["skill_level"] < 2))
    )
    out["hard_mismatch_events"] = int(df["hard_mismatch"].sum())

    df["date"] = df[TS].dt.floor("D").dt.tz_localize(None)
    load = df.groupby(["date", RES]).size().unstack(fill_value=0)
    out["max_to_median_load"] = (load.max(axis=1) / load.median(axis=1)).mean()
    d = df.merge(roster, left_on=[RES, "date"], right_on=["resource", "date"], how="left")
    hi = d["overtime_risk"] == "high"
    out["share_assignments_high_overtime"] = hi.mean()
    out["non_urgent_to_high_overtime"] = int((hi & (d["case_priority"] != "urgent")).sum())

    case_end, sla = grp[TS].max(), grp["sla_deadline"].last()
    out["sla_miss_rate"] = (case_end > sla).mean()
    slow = pm4py.filter_case_performance(df, 5 * 86400, 365 * 86400)      # long-running cases

    rework = pm4py.filter_event_attribute_values(df, ACT, ["Rework Correction"],
                                                 level="case", retain=True)
    rework_cases = set(rework[CASE].unique())
    case_tab = pd.DataFrame({"max_reassign": max_reassign,
                             "rework": max_reassign.index.isin(rework_cases)})
    out["rework_rate_by_reassign"] = case_tab.groupby(case_tab["max_reassign"] > 2)["rework"].mean()

    variants = pm4py.get_variants(df)
    out["diagnosis_loop_variants"] = sum(1 for v in variants if list(v).count("Technical Diagnosis") > 1)

    low = df[df["case_priority"].isin(["normal", "low"])]
    reason = low["assignment_reason"].fillna("")
    out["training_share_hands_on"] = reason.str.startswith("TRAINING_SUPERVISED").mean()
    out["training_share_shadow"] = reason.str.startswith("TRAINING_SHADOW").mean()

    for act in ("Security Review", "Final Approval"):
        sub = pm4py.filter_event_attribute_values(df, ACT, [act], level="event", retain=True)
        out[f"top_resource_share_{act}"] = sub[RES].value_counts(normalize=True).iloc[0]

    urgent = pm4py.filter_event_attribute_values(df, "case_priority", ["urgent"],
                                                 level="case", retain=True)
    out["urgent_perf_dfg"] = pm4py.discover_performance_dfg(urgent)[0]

    batches = pm4py.discover_batches(df)
    out["quality_check_batches"] = [b for b in batches if b[0][0] == "Quality Check"]
    return out, slow

def policy_deviation(df, recommend):
    """Replay the policy: recommend(event_row) returns the resource the policy would pick
    from the logged state (skills, workload_snapshot, owner, SLA, complexity)."""
    df["recommended"] = df.apply(recommend, axis=1)
    df["deviation"] = df["recommended"] != df[RES]
    by_reason = df[df["deviation"]].groupby("assignment_reason").size()
    outcome = df.groupby("deviation")["hard_mismatch"].mean()
    return df["deviation"].mean(), by_reason, outcome
```

**How this feeds the policy**

- `handover_penalty` and `service_by_skill` replace the default continuity and skill scores with values measured on this process. They should reproduce figures such as the +2.7h and +3.3h medians.
- Resource similarity and discovered roles suggest realistic backups and training candidates. Betweenness in the handover network and the top-resource share reveal specialist bottlenecks.
- The performance DFG and waiting times show whether queues before Security Review and Final Approval grow under the policy.
- Batch discovery checks that Quality Check batching respects rule 8 (cross-check against `case_priority` and SLA slack at batch time).
- The deviation replay shows where people systematically disagree with the policy. Combined with rework and SLA outcomes of overridden versus followed recommendations, it is the main input for the periodic, jointly reviewed re-tuning of weights.
