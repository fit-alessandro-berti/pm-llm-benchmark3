## 1. Analytical assumptions
**Case notion** – A *case* for an object type \(o\) consists of all events whose `Related objects` set contains \(o\) and that are directly related to \(o\) (i.e. the event mentions \(o\) in its description or in the list of related objects). No silent propagation of objecttoobject relations (contains, packs, carries, bills, settles, etc.) is performed unless the analyst explicitly invokes a relationpropagation step.

**Convergence** – Convergence refers to the tendency of several flattened cases (e.g. the three orders involved in D2) to agree on the same timestamps for shared events (dispatch, invoice issuance). Agreement on timestamps does **not** imply logical equivalence; it merely reflects physical simultaneity.

**Divergence** – Divergence refers to apparent differences that arise because the same physical event is copied into multiple cases (e.g. Dispatche16 appears in the cases of O1, O2 and O3) or because a lifecycle is truncated when an object participates in only one or two event types (e.g. a payment object sees only RecordPayment events and no invoice or delivery events). Divergence is acceptable when it reflects genuine business variability (e.g. partial vs. complete settlement); it becomes problematic when it hides coordination (e.g. consolidation of packages or invoices).

**Treatment of copied shared events** – Copied shared events are taken as *both* evidence (they correctly capture the realworld simultaneity) **and** duplication (they appear multiple times in different flattened logs). Analysts must acknowledge the duplication explicitly (e.g. by noting “dispatch e16 copied to O1, O2, O3”) rather than silently ignoring or merging them. No automatic merging or deduplication is performed; frequency counts in flattened logs should be reported per case (i.e. “O1 sees 1 dispatch”, “O2 sees 1 dispatch”, etc.).

**Permitted analytical transformations** – Only *explicit* relation propagation through the OO graph may be used when an analyst decides to infer, for example, “ItemI21 belongs to PackageP3” from the existing `packs` relation. Such propagation must be recorded (e.g. as a derived edge) and must not be used automatically by the mining routine. Silent inference (e.g. adding an edge from AddItem directly to Dispatch based solely on containment) is **not** permitted.

**Recommendation:** Create flattened logs for **Delivery**, **Order**, and **Package** (these cover the majority of business questions with minimal duplication confusion). **Invoice** and **Payment** logs can be generated on demand for financial audits; they should not be used alone for endtoend operational analysis because qualifiers are easy to overlook. Item logs are useful for inventory logistics but not required for processlevel analysis.

Questions that safely answered by a single flattened log:

- Deliverylog: precise dispatch/confirmation timestamps per delivery; list of packages carried.
- Orderlog: order creation, item addition, which packages were packed for that order (directly from PackPackage events that mention the order).
- Packagelog: pack time and which items/orders the package contains (direct from PackPackage events that mention the package).

Questions requiring objectcentric models:

- Crossorder coordination (e.g., “How long does it take for O2’s items to reach O3 when they share P3?”) – needs OCDFG or OTG to show edges across orders.
- Settlement timing relative to delivery (e.g., “Is payment always recorded before or after delivery confirmation for consolidated deliveries?”) – needs objectinteraction summary (O2O + event relations) to resolve qualifier semantics.
- Detecting hidden nearsingleton lifecycles (e.g., “Are any items or payments appearing only once in their flattened logs?”) – requires ET–OT graph or clustering to identify short traces that might be truncated.
- Reconciling duplicated events (e.g., Dispatche16 appearing in three order cases) – an equivalentexecution clustering (EC) step can merge identical simultaneous events across cases while preserving perobject timestamps.

**Reconciliation procedure (practical):**

1. Keep all flattened logs with annotations that include the original event ID and the set of participating objects (e.g., “e16 (Dispatch) involves O1,O2,O3,P2,P3,D2”).
2. Build the OCDFG from the raw OCEL (using `pm4py.discover_ocdfg`). This graph respects object identities and timestamps without duplication.
3. For each flattened log, map its events back to the OCDFG nodes (by object instance). If a flattened log shows a duplicate event (e.g., two “Dispatch” activities for the same physical event), mark it as “shared” and do not count it twice in performance metrics that aggregate percase durations (instead compute durations using the underlying OCDFG timestamps).
4. When reporting perorder or perpackage metrics, compute them from the OCDFG rather than from the raw flattened log whenever the metric concerns coordination (e.g., “time from pack to dispatch for items that share a package”). Use the flattened logs only for questions that are naturally objectcentric (e.g., “list all items packed in P3”).
5. Document any observed divergence (e.g., O1 confirms delivery at 12:00 while O2/O3 confirm at 16:00) and explain it with the consolidation (D2). This transparent annotation resolves most apparent contradictions.

## 5. Leadobject decision

**Position C – Reject a single lead object for this process.**

*Decision criteria used*

1. **Coverage completeness** – A single object type must capture, without duplication or omission, all relevant events for an endtoend view (creation  delivery  payment  closure). The process inherently involves consolidation (packages, deliveries, invoices) across multiple orders, so no single object type naturally encompasses all aspects.
2. **Duplication inevitability** – Flattening on any object type inevitably copies shared events (e.g., Dispatche16, IssueInvoicee19). A single lead object would still suffer from duplication for events that involve other object types, leading to either hidden duplication (if ignored) or overcounting (if summed).
3. **Lifecycle truncation risk** – Objects that participate in only one or two event types (e.g., Payment objects only see RecordPayment) will produce very short flattened traces when compared to the full order timeline, causing perceived truncation if the analyst assumes a single lead object represents the whole process.
4. **Qualitative suitability matrix** – From Section2, only Delivery achieves “high” suitability for deliverycentric questions; Order and Package are “medium”; Invoice and Payment are “lowmedium”. No object type scored “high” for all typical endtoend questions (creation  delivery  payment  closure). Hence no single object type can be uniformly recommended.
5. **Businesslogic fidelity** – Consolidation semantics (e.g., V2 billed to O2&O3, D2 carrying P2&P3) are best expressed by keeping object identities (Order, Package, Delivery, Invoice) together in the analysis model. A single lead object would either hide consolidation (if we pick Order only) or lose package/delivery detail (if we pick Package only).

*Strongest supporting evidence*

- Crossorder package P3 (e13) and P4 (e14) involve two orders each; flattening on Order duplicates Pack events for both orders but also misses the fact that the same package serves two orders simultaneously.
- Consolidated delivery D2 (e16, e24) delivers P2 (O1) and P3 (O2/O3) together; flattening on Order shows O1 confirming earlier (e23) while O2/O3 confirm later (e24), creating an apparent divergence that reflects real logistics but not a singleorder flow.
- Consolidated invoicing V2 (e19) with two payments (M2partial, M3complete) requires qualifier awareness; flattening on Order alone may treat M2 and M3 as separate without linking them, leading to truncated settlement perception.
- Nearsingleton lifecycles (Item I11’s trace ends at e23 while payment M1 occurs at e21/e28) illustrate that picking a single object (e.g., Item) would hide payment timing.

*Strongest counterargument*

- “Order” is the most intuitive lead object because it naturally groups the business transaction (create  add items  pack  dispatch  invoice  payment  close). Many processmining tutorials start with the order object.

*Residual risk if we adopt a single lead object (e.g., Order)*

- Hidden consolidation benefits (D2 delivering two packages together) may be interpreted as slower delivery for O2/O3; payment timing may appear later relative to delivery confirmation because payment events are not included in the orderonly trace when focusing on only one payment instalment.
- Duplication of shared events (dispatch, invoice) would still appear in the order log, leading to frequency inflation if counts are aggregated per order without noting “shared”.
- Nearsingleton lifecycles (item or payment) could be overlooked, giving an overly optimistic view of fulfilment speed.

*Conditions under which the decision would change*

- If the process evolves so that **no package ever contains items from more than one order** (i.e., P3 and P4 become orderspecific) **and** **no invoice ever consolidates multiple orders** (i.e., each order gets its own invoice), then Order would become a natural singlelead object with minimal duplication and no consolidation semantics. In that case, the matrix would shift to “high” suitability for Order and the decision could move to **A** (select Order as lead).
- If the organization decides to **ignore crossorder consolidation** for reporting purposes (e.g., treat D2 as two separate deliveries), then a single Orderlead flattening might be acceptable; however the analysis would then misrepresent logistics and should be explicitly flagged.

Thus, **given the current snapshot with explicit consolidation at package, delivery, and invoice levels, rejecting a single lead object (OptionC) is defensible and internally consistent.**

## 6. PM4Py analysis outline

```python
import pm4py
from pm4py.ocel import ocel
from pm4py.variants import influence_discovery

# ----------------------------------------------------------------------
# 1. Print the OCEL structure (for inspection)
print("OCEL representation:")
print(ocel)

# 2. Extract object types and frequencies of activities per object type
#    (simple inspection)
def inspect_ocel(ocel):
    # list of object instances per type
    obj_types = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]
    for ot in obj_types:
        objs = [inst for inst in ocel["objects"] if inst["type"] == ot]
        print(f"{ot}: {len(objs)} objects")
    # activity frequencies (raw event counts)
    activities = set()
    for ev in ocel["events"]:
        activities.add(ev["activity"])
    print("\nUnique activities:", sorted(activities))

inspect_ocel(ocel)

# ----------------------------------------------------------------------
# 3. Flattening per object type (explicitly requested by the analyst)
#    We will flatten on each type separately and keep the original event IDs
flattened_orders = pm4py.ocel_flattening(ocel, flatten_on="Order")
flattened_packages = pm4py.ocel_flattening(ocel, flatten_on="Package")
flattened_deliveries = pm4py.ocel_flattening(ocel, flatten_on="Delivery")
flattened_invoices = pm4py.ocel_flattening(ocel, flatten_on="Invoice")
flattened_payments = pm4py.ocel_flattening(ocel, flatten_on="Payment")
flattened_items = pm4py.ocel_flattening(ocel, flatten_on="Item")

# ----------------------------------------------------------------------
# 4. Discover DFGs from each flattened log (for illustration)
dfg_orders = pm4py.discover_dfg(flattened_orders)
dfg_packages = pm4py.discover_dfg(flattened_packages)
dfg_deliveries = pm4py.discover_dfg(flattened_deliveries)
dfg_invoices = pm4py.discover_dfg(flattened_invoices)
dfg_payments = pm4py.discover_dfg(flattened_payments)
dfg_items = pm4py.discover_dfg(flattened_items)

print("\nDFG edges for orders:", dfg_orders.edges())
print("DFG edges for packages:", dfg_packages.edges())
print("DFG edges for deliveries:", dfg_deliveries.edges())
print("DFG edges for invoices:", dfg_invoices.edges())
print("DFG edges for payments:", dfg_payments.edges())

print("\nOCDFG edges:", oc_dfg.edges())

# ----------------------------------------------------------------------

otg = pm4py.discover_otg(ocel)
print("OTG edges:", otg.edges())

# ----------------------------------------------------------------------
# 8. Discover ET–OT graph (if needed) – pm4py provides `discover_etot`
etot = pm4py.discover_etot(ocel)

# ----------------------------------------------------------------------

#    Since we reject a single lead object, we still compute a summary for illustration.
interaction_summary = pm4py.ocel_objects_interactions_summary(ocel)
print("\nObjectinteraction summary:")
print(interaction_summary)
```
