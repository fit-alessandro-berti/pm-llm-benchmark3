## 1. Target definition

**Primary target: observed-policy cumulative incidence of default after activation.**  
For a credit application, the event of interest is:

> the case reaches **Account Activated** and then has a **default within 90 days after activation**, before any competing terminal event.

This is formulated as a multi-state/competing-outcome target, not as a binary “default vs non-default” label on all applications.

- **Unit of analysis:** one credit application/case.
- **Population:** all applications started between **1 January 2024** and **31 December 2025**.
- **Prediction time:** a prefix landmark after the first few events. Primary landmark: **3-event prefix**; secondary landmarks: 1, 2, 5 events and 7/14 elapsed days.
- **Target event time origin:** application start, with administrative follow-up truncation \(F = 365\) days from application start. The default clock starts after activation, but default must occur within 90 days after activation.
- **Estimand:**  
  \[
  \text{CIF}_p(s, x) = P(\text{case activates, then defaults within 90 days after activation, before a competing terminal event} \mid \text{prefix } x \text{ at landmark } s, \text{policy period } p)
  \]
  under the observed credit policy.

Rejected, withdrawn, transferred, and still-open cases are **not** coded as non-default. Rejected, withdrawn, and transferred cases are competing terminal events. Open and label-immature cases are censored.

**Credible alternative target:**  
Conditional default risk among applications that are eventually activated:

\[
P(\text{default within 90 days after activation} \mid \text{eventual activation, prefix } x).
\]

This answers a narrower question: “If this case is activated, what is the default risk?” It is useful for portfolio/activation risk, but it conditions on a future event. It should not be presented as the default risk for all applications unless the activation policy is assumed fixed and selection is ignorable.

Another alternative is a **policy-specific counterfactual default risk**: what would happen if every application were activated under the current credit policy. That requires strong, largely untestable assumptions about rejected/withdrawn cases and is therefore not primary.

## 2. Cohort construction

### Inclusion rules

- Application started between **2024-01-01** and **2025-12-31**.
- At least one event present in `applications_events.csv`.
- Event timestamp not after data extraction cutoff: **2026-02-15**.

### Exclusion rules

- Duplicate events caused by system migration are collapsed using `(case, activity, timestamp, resource)`.
- Events after the extraction cutoff are removed.
- No case is excluded merely because its outcome label is missing, immature, or transferred.

### As-of rules

- For a case to be treated as having a final observed `default_90d = 0` or `default_90d = 1`, `label_available_at` must be present and \(\le\) extraction cutoff.
- If not, the case is censored or treated as delayed/missing label.
- Terminal states are assigned only when the corresponding terminal activity is observed:
  - `Rejected`
  - `Withdrawn`
  - `Transferred`

### Cohort-flow accounting

| Cohort group | Count | Role in primary multi-state target |
|---|---:|---|
| Activated, mature label, non-default within 90 days | 18,900 | At risk; no default event within 90 days after activation |
| Activated, mature label, default within 90 days | 2,700 | Primary event |
| Activated, outcome immature / delayed feed / missing label | 3,600 | Right-censored or delayed-label censoring |
| Rejected | 9,100 | Competing terminal event; not non-default |
| Withdrawn | 5,700 | Competing terminal event; not non-default |
| Transferred | 2,900 | Competing terminal event / missing follow-up; 60% linked for sensitivity |
| Still open at extraction | 5,100 | Right-censored before terminal event or activation |
| **Total** | **48,000** | All applications started in window |

The labeled export of 21,600 cases is therefore only a subset. It is the **mature activated** subset, not the full target population.

## 3. Censoring and missing-label strategy

### Ordinary right censoring

Cases still open at extraction, or activated but whose 90-day window has not closed, are right-censored. In the multi-state model, censoring time is the earliest of:

- data extraction time,
- end of study follow-up \(F = 365\) days from start,
- last observable event timestamp.

These cases contribute information until censoring time, but they are not classified as default-free after censoring.

### Delayed labels

Some activated cases may have passed the 90-day horizon but the external default feed has not arrived by extraction, or `label_available_at` is missing. These cases are not given `default_90d = 0`. They are treated as delayed-label cases:

- If `label_available_at <= cutoff`, the outcome is final.
- If `label_available_at > cutoff` or missing, censor at the last usable non-default follow-up time, or extraction time if no clean follow-up exists.

### Selection through activation

Default is only observable after activation. The primary multi-state formulation avoids treating non-activation as default-free by making activation an explicit transition. Rejected/withdrawn/transferred cases are competing events. This is not a causal estimate of what would happen under a different approval policy; it is the observed-policy cumulative incidence.

### Transfer as competing event / missing follow-up

For the primary analysis, **Transferred** is a competing terminal event because follow-up often disappears into another platform. Only about 60% of transfers can be linked. In sensitivity analysis, linked transfers with continuing observable events may be merged into a single follow-up record, and results compared with the primary competing-event treatment.

### Permanently missing outcome feeds

Partner-originated activated accounts may have permanently missing outcome feeds. They are not assumed to be non-default. Primary analysis uses censoring/competing-risk methods. Sensitivity analyses include:

- excluding partner-originated cases,
- treating all missing partner feeds as default,
- treating all missing partner feeds as non-default.

This bounds the impact of nonignorable missingness.

### Primary analysis strategy

Use a **multi-state/competing-risk** survival formulation:

- event of interest: default after activation,
- competing events: rejected, withdrawn, transferred,
- right-censoring: still open, immature follow-up, delayed label, extraction cutoff.

Estimate cumulative incidence via Aalen-Johansen or cause-specific hazard models. Do not train a plain classifier on 21,600 rows as if the other 26,400 cases did not exist.

### Sensitivity analyses

1. Conditional model on mature activated subset with inverse probability of censoring weights.
2. Transfer-linkage follow-up sensitivity.
3. Worst-case missing-feed bounds.
4. Pre/post policy-stratified cumulative incidence curves.
5. Time-to-default after activation with right censoring, excluding competing non-activation events, interpreted only as conditional on activation.

### Assumption testability

- **Testable:** activity renaming and duplicate rates, transfer-linkage rates, label availability timing, missingness by observed channel/region/partner flag, policy change effect on event frequencies.
- **Partially testable:** missing-at-random for delayed labels given observed prefix and static features. We can test missingness against observed covariates, but cannot test missingness against unobserved true default status.
- **Fundamentally untestable:** counterfactual default risk for rejected/withdrawn cases under a different approval policy; missing-not-at-random for permanently missing partner feeds; outcome of unlinked transfers.

## 4. Prefix extraction

Prefixes are generated strictly from events with timestamp \(\le\) prediction time.

### Fixed event-count prefixes

For \(k \in \{1,2,3,5\}\):

- sort a case’s events by timestamp;
- take the first \(k\) events;
- set prediction time to the timestamp of the \(k\)-th event.

Primary prefix: \(k = 3\).

If a case has fewer than \(k\) events because it terminated early, use all available events and mark the prefix as truncated. Do not impute future events.

### Elapsed-time prefixes

For elapsed prefixes at 7 and 14 days:

- prediction time = `start_time + 7 days` or `start_time + 14 days`;
- include all events with timestamp \(\le\) prediction time.

For cases that terminate before the elapsed-time cutoff, the prefix ends at the terminal event and the prediction time is the terminal event time.

### Short cases

Short cases are not discarded. They enter the analysis as:

- competing events if terminated,
- censored if open,
- or truncated prefixes for event-count landmarks.

### Repeated document loops

Repeated `Credit Review -> Request Documents -> Credit Review` loops are retained in the prefix. Features count loop repetitions, number of document requests, and current location in a loop. For fixed event-count prefixes, the prefix may end inside a loop; this is valid as-of information.

### Activity renaming and duplicates

Activity names are mapped to a canonical set before prefix extraction. This mapping is applied based on the event timestamp and the known migration date, not by looking at the outcome. Duplicate events from migration are removed using:

- `case:concept:name`
- `concept:name`
- `time:timestamp`
- `org:resource`

## 5. Process-aware features

### Static case attributes

Available at application start:

- `case:channel`
- `case:region`
- `case:requested_amount`

These are baseline features.

### Prefix-derived control-flow features

Computed only from events \(\le\) prediction time:

- current prefix variant string, e.g. `Application Started -> Identity/KYC Check -> Credit Review`
- last activity in prefix
- number of events
- counts of key activities: KYC, Credit Review, Request Documents
- indicator for KYC already completed
- whether current prefix ended in a document request loop
- whether the case has entered Credit Review

### Timing features

- elapsed time from application start to prediction time
- mean/median inter-event time
- time since last event
- calendar day-of-week and hour of prediction time

### Resource/queue features

- number of distinct resources seen in prefix
- current resource or resource group
- number of resource changes
- queue-like features: number of cases with same resource/activity in training data at the same calendar period

Resource experience stored at extraction time is **not** used unless historical HR data allow reconstruction.

### Rework features

- count of document request loops
- count of repeated Credit Review
- number of times the process returns to Credit Review after document upload

### Cohort/calendar features

- application month/year
- policy period: before/after **2025-07-01**
- migration period: before/after **2025-10-15**
- holiday/seasonality flags

### Historical reference features

These require time-aware aggregation from training cases only, using information available before the prediction point:

- historical default incidence by channel, region, requested amount bin, current risk score bin
- historical activation rate by channel/region/policy period
- average duration from first event to activation or rejection

These features must be computed with a delay to avoid using future outcomes of the same case or future period information.

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep/repair/drop | Rationale |
|---|---:|---|---|---|
| `final_limit` | Post-decision value; not known at early prefix | Only non-null on prefix events \(\le\) prediction time | Drop from early-prefix model; at most use availability flag | Leaks final credit decision and future approval |
| `decision_reason` | Populated at/after Accept/Reject | Only non-null on prefix events \(\le\) prediction time | Drop for early-warning features | Leaks terminal decision |
| `collection_status` | Post-activation collections/default status | Not available before activation | Drop from features; use only for outcome/censoring | Severe target leakage |
| Future events | Activation, contract signed, collections, default recorded after prediction time | Only events with timestamp \(\le\) prediction time | Keep prefix only; drop future | Core temporal leakage prevention |
| `documents_total` | Nightly snapshot may include documents uploaded later on same day | Require snapshot timestamp \(\le\) prediction time; otherwise use previous-day value | Repair/drop | Avoid same-day future information |
| Updated `risk_score` | Time-varying, but may be updated after prefix | Use last non-null `risk_score` on/before prediction time | Keep with as-of rule | Valid if timestamped at event time |
| Resource experience | Stored at extraction time, not event time | Would require historical HR data at each event | Drop/repair | Otherwise biases experience feature |
| Label availability | Outcome metadata; not available at prediction time | Use only post-prediction for censoring/outcome definition | Outcome only; never feature | Would be direct target leakage |

Additional checks:

- `default_90d` and `label_available_at` must never enter the feature table.
- `data_extract_time` is not an event timestamp and must not be used as prediction time.
- `source_system` may be used only if the migration period is consistent with the event timestamp; otherwise treat as risk factor rather than causal feature.

## 7. Validation design

### Temporal validation

Random case splitting is misleading because of:

- credit-policy change on **2025-07-01**,
- system migration on **2025-10-15**,
- label maturity drift,
- strong calendar-time dependence in credit decisions.

Primary validation is temporal by **case start time**:

| Split | Case start window | Purpose |
|---|---:|---|
| Train | 2024-01-01 to 2025-06-30 | Historical model development |
| Validation | 2025-07-01 to 2025-09-30 | Post-policy-change calibration |
| Test | 2025-10-01 to 2025-12-31 | Migration and delayed-label stress test |

In addition, use **rolling-origin backtesting**:

- For each month \(m\) from 2025-07 onward, train on all cases starting before \(m\) with outcomes available by a cutoff that mimics the reporting delay.
- Test on cases starting in month \(m\).
- Never train on future cases relative to the prediction month.

### Label maturity in backtesting

For each historical prediction month, respect a realistic label-freeze:

- A case is usable as a mature outcome only if `label_available_at` would have been available by the backtest cutoff.
- Otherwise, handle as censored/delayed using the survival/competing-risk framework.

### Migration and policy change

- Include policy-period indicator only when known at prediction time.
- Evaluate separate calibration and discrimination before/after **2025-07-01**.
- Evaluate whether activity renaming/dedup changes feature distributions around **2025-10-15**.
- Compare predicted risk distributions across policy and migration periods.

### Evaluation metrics

Given the multi-state/competing-risk target:

- **Cumulative incidence calibration:** predicted CIF vs Aalen-Johansen observed CIF at the chosen follow-up horizon.
- **Time-dependent Brier score** for cumulative incidence.
- **Time-dependent Uno C-index** for cumulative incidence.
- **Subgroup performance:** channel, region, requested amount bin, risk score band, policy period, transfer status, partner-originated status.
- **Distribution shift monitoring:** PSI, mean predicted risk, event rates, missingness rates by month.

Do not report plain accuracy on the 21,600 mature labeled cases as the primary evaluation.

## 8. Limitations and decision-use boundary

### What the study can and cannot claim

- **Can claim:** predictive association between early process prefixes and observed default incidence under the current credit policy.
- **Cannot claim:** causal effect of activation or credit approval on default.
- **Cannot claim:** rejected or withdrawn cases would have defaulted at a particular rate if activated.
- **Cannot claim:** missing partner feeds or unlinked transfers are ignorable without sensitivity analysis.

### Selection effects

The observed default risk is a function of the activation policy. If the credit policy changes, both activation density and the mix of activated cases change. Therefore the model estimates a policy-specific outcome, not a universal applicant risk.

### Deployment could change the data-generating process

At least three mechanisms:

1. **Approval policy feedback:** if the model is used to reject high-risk applications, the future activated population changes, and observed default rates may fall even if total applicant credit risk is unchanged.
2. **Process/review feedback:** if model scores cause longer document reviews or more requests, prefix features such as rework loops and event counts shift.
3. **Data capture and collections feedback:** model deployment may change collection strategies, transfer handling, or data completeness. The model may also alter which cases are transferred or linked, affecting the missingness mechanism.

### Decision-use boundary

Use the model as decision support for early review prioritization, not as the sole automatic approval/rejection rule. It is not a counterfactual underwriting model for rejected applicants. Recalibration is required after any material policy, process, or data-system change.

    "KYC Complete": "Identity/KYC Check",

    start_time=("time:timestamp", "min"),

    region=("case:region", "first"),
    requested_amount=("case:requested_amount", "first")

    "Transferred": "transferred"

)

    case["label_available_at"].notna()

)

case.loc[mature_mask, "label_window_mature"] = (
    case.loc[mature_mask, "activation_time"]

) <= EXTRACT_CUTOFF

def classify_row(r):

            return "activated_missing_label"
        return "activated_followup_not_mature"

def extract_prefix_features(case_ids, event_df, case_table, k=None, elapsed_days=None):

        if evs.empty:

            "activation_time": case_table.loc[cid, "activation_time"],

        }
        rows.append(row)
