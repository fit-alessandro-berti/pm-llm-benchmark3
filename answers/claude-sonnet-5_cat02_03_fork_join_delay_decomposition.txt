# 1. Delay-decomposition definitions

For case *c* let branches be indexed *i  {A, B, C}*, with:

- `arrival_c`, `fork_release_c` — logged.
- `branch_start_{c,i}`, `branch_end_{c,i}` — logged per branch.
- `final_start_c`, `final_end_c` — logged.

**Component formulas**

| Component | Formula |
|---|---|
| upstream_elapsed_c | `fork_release_c  arrival_c` |
| branch_queue_{c,i} | `branch_start_{c,i}  fork_release_c` |
| branch_service_{c,i} | `branch_end_{c,i}  branch_start_{c,i}` |
| join_ready_c | `max_i( branch_end_{c,i} )` (the stated max-based rule; not directly logged) |
| critical_branch_c | `argmax_i( branch_end_{c,i} )` (deterministic tie-break rule needed, see §2/§6) |
| branch_sync_{c,i} | `join_ready_c  branch_end_{c,i}` (= 0 for the critical branch by construction) |
| fork_join_stage_c | `join_ready_c  fork_release_c` — **one** elapsed wall-clock span |
| downstream_queue_c | `final_start_c  join_ready_c` (queueing interpretation — see §7 for the alternative "release policy" reading) |
| final_service_c | `final_end_c  final_start_c` |
| total_flow_time_c | `final_end_c  arrival_c` |

**Additivity check (no double counting):**

```
upstream_elapsed_c + fork_join_stage_c + downstream_queue_c + final_service_c
= (fork_releasearrival) + (join_readyfork_release) + (final_startjoin_ready) + (final_endfinal_start)
= final_end  arrival = total_flow_time_c
```

This telescoping sum is valid **only because `fork_join_stage_c` is a single elapsed interval**, not a sum over branches.

**Why summing branch synchronization waits would double count:**

Since `branch_end_{c,i} = fork_release_c + branch_queue_{c,i} + branch_service_{c,i}` and `branch_sync_{c,i} = join_ready_c  branch_end_{c,i}`, algebraic substitution gives, **for every branch i**:

```
branch_queue_{c,i} + branch_service_{c,i} + branch_sync_{c,i} = join_ready_c  fork_release_c = fork_join_stage_c
```

This is an exact identity — it can be verified on every row of §2 (e.g. F01: A gives 0+50+0=50, B gives 5+40+5=50, C gives 10+18+22=50, all equal `fork_join_stage=50`). Each branch's own "queue+service+sync" reconstructs the **same** elapsed span. Therefore adding the three branch totals (or the three sync waits) reproduces the elapsed fork-join interval **three times** instead of once — the branches' waits are concurrent (nested/overlapping in wall-clock time), not sequential, so they must never be added across *i* when computing total flow time. Only the correctly identified `fork_join_stage_c` (driven by the critical branch) may enter the total-flow-time sum.

# 3. Aggregate critical-path analysis

**Branch service and queue summary (minutes):**

| branch | queue: mean / min / max | service: mean / min / max | queue+service: mean / max | mean sync wait |
|---|---|---|---|---|
| A | 0.0 / 0 / 0 | 50.0 / 50 / 50 | 50.0 / 50 | 11.0 |
| B | 19.2 / 5 / 30 | 37.5 / 30 / 45 | 56.7 / 75 | 4.3 |
| C | 10.4 / 5 / 35 | 20.2 / 18 / 30 | 30.6 / 57 | 30.4 |

**Critical-branch frequency:** A = 2/12 (16.7%), B = 8/12 (66.7%), C = 2/12 (16.7%).

**Margins at criticality (near-ties flagged honestly):**
- F01 (A critical): beats B by only 5 min — a *near-tie*, fragile to small B-queue changes.
- F11 (A critical): beats B by 10 min — moderate margin.
- F04 (C critical): beats A by 7 min; F08 (C critical): beats A by 5 min — both near-ties.
- No exact ties exist in the *observed* data; a tie is only produced in a counterfactual (§4/§6).

**Reasoned influence ranking: B  A  C**

1. **B is the dominant controlling branch.** It is critical in two-thirds of cases, has both the highest mean queue+service (56.7 min) and the single worst observed outcomes (75 min in F07 and F12, which are also the two longest total_flow_time cases in the sample — 130 and 125 min). B also drives the tail: its queue alone ranges 5–30 min, a 6× spread, versus A's zero spread and C's 5–35 min range concentrated at low values except one outlier (F04).
2. **A has the largest *service* time on average is false as a controlling metric** — A's service (50 min, constant) is actually the largest single mean of any branch component, yet A is critical in only 2/12 cases. Because A has **zero queueing variance**, it behaves as a fixed floor; it becomes decisive only when B/C are unusually fast. This is the clearest illustration in the data of "largest mean service  most influential branch."
3. **C has the largest mean synchronization wait (30.4 min)** — i.e., C usually finishes earliest and idles the longest waiting for join — which paradoxically signals **low** influence on total flow time: a branch that is rarely on the critical path, however long it waits, does not by itself lengthen the case (its wait is absorbed within `fork_join_stage`, not added to it).
4. A and C are near-tied in critical-branch frequency (2 vs 2) but for structurally different reasons: A is a deterministic near-miss bottleneck; C is critical only when its own queue spikes (F04: C_queue = 35, the largest in the data set) — an occasional resource-contention event rather than a systematic driver.

# 4. Counterfactual redesign analysis

*Assumption:* downstream station behavior (final_start relative to join_ready) is held fixed unless directly targeted by the counterfactual — i.e., we do not re-simulate F1/F2 queueing dynamics under altered upstream timing. This is a simplifying, labeled assumption; real second-order effects on downstream queueing are discussed as "secondary effects" below and flagged again in §7.

### CF1 — Reduce A service by 20% (50  40 min for all cases)

New `A_end_c = fork_release_c + 40`. Recomputing `join_ready_c = max(A_end_c, B_end_c, C_end_c)`:

- **Direct benefit:** only **F01** (join_ready 540535, 5 min) and **F11** (690680, 10 min) improve, because these are the only two cases where A was critical.
- **Zero benefit (10/12 cases):** all cases where B or C was already critical are unaffected — A's new end time still lies below the existing max (e.g., F02: new A_end 545 < B_end 565).
- **Mean reduction in total_flow_time  1.25 min/case** (15 min total / 12 cases), concentrated in 16.7% of cases.
- **Secondary effect:** speeding an already-fast, non-bottleneck branch has essentially no system-level payoff and would not be a sound investment priority — a direct demonstration that largest service time (A, 50 min) does not imply largest leverage.

### CF2 — Reduce B queue delay by 50%

New `B_end_c = B_end_c  0.5·B_queue_c`; recompute `join_ready_c`.

- **Direct benefit in 8/12 cases** (F02, F03, F05, F06, F07, F09, F10, F12): reductions of 10, 10, 10, 15, 15, 12.5, 5, 15 min respectively.
- **Zero benefit (4/12):** F01 and F11 (A already critical, B irrelevant), F04 and F08 (C already critical, exceeds even the improved B).
- **Mean reduction  7.7 min/case** (92.5 min total / 12) — roughly **6× the benefit of CF1** for a similarly modest intervention, confirming B's dominant leverage.
- **Secondary effect / new near-tie:** F10's bottleneck shifts from B to A (A becomes new critical branch at 675, still 5 min improvement); F06 produces an exact tie between A and B (both 615) — illustrating that accelerating the dominant branch can expose the *next* bottleneck (A's deterministic floor) rather than eliminating delay entirely. This is a genuine structural limit: once B is fast enough, A's fixed 50-minute floor becomes the new ceiling.

### CF3 — Add final-station capacity / reduce downstream queueing

Downstream_queue currently: mean 14.7 min, range 8–20 min, and **every case has downstream_queue > 0** (100% incidence, unlike branch-level bottlenecks which only affect subsets of cases).

- **Full elimination** (downstream_queue  0, e.g., abundant F1/F2 capacity): mean reduction = 14.7 min/case, applied to **all 12 cases** — the single largest aggregate benefit of the three counterfactuals, entirely because it touches every case rather than a critical-branch subset.
- **50% reduction** (e.g., adding a third resource that halves average wait under a simplified linear model): mean reduction  7.3 min/case, comparable in magnitude to CF2's 7.7 min, but **for a different reason** — CF3 helps broadly and shallowly, CF2 helps narrowly but sometimes more deeply (up to 15 min in single cases).
- **Zero-benefit cases:** none — this is the only counterfactual with universal incidence.
- **Masking risk:** because CF3 improves every case's headline flow time, it can create the appearance of system-wide improvement while leaving the upstream imbalance (B's dominance) completely untouched. Management dashboards tracking only total_flow_time could misattribute the gain to "process improvement" rather than recognize that the fork-join stage — and hence the real capacity constraint — is unchanged. This is exactly the "downstream congestion masks branch improvement" risk the task calls out.

# 5. Recommended redesigns and risks

**Recommendation 1 — Prioritize reducing Branch B queueing (capacity/scheduling fix for Machine Stress Test).**
- *Throughput:* Directly shortens the fork-join stage in 8/12 observed cases; should raise sustainable case throughput most because it targets the branch that is critical two-thirds of the time.
- *Flow-time tail:* Targets the two worst-observed cases (F07, F12, both 75-min B outcomes) directly, so should compress the upper tail of total_flow_time, not just the mean.
- *Resource utilization:* If B's queueing stems from a single constrained resource/technician, adding capacity there raises utilization efficiency of the overall pipeline (A and C are already "cheap" relative to B).
- *New bottlenecks:* As CF2 shows, once B is fast, A's deterministic 50-min floor becomes binding (F06, F10 examples) — expect the critical-branch distribution to shift toward A after this fix; a second-round evaluation of A's queue/service (currently zero-variance, but only because A is rarely constrained) may be needed.
- *Synchronization effects:* Expect C's mean sync wait (currently 30.4 min) to fall as the join point moves earlier — but this is a symptom, not a cost, of the fix.
- *Pilot/measure first:* Instrument B's actual resource/queue (currently unlogged — only start/end times are available); pilot on a subset of cases with added B capacity or reprioritized scheduling and measure join_ready and critical-branch frequency shift before wider rollout.

**Recommendation 2 — Add modest final-station capacity or better F1/F2 dispatch (secondary, not primary).**
- *Throughput:* Improves all cases by ~15 min mean at saturation elimination; cheap to reason about since it doesn't require touching branch-level processes.
- *Flow-time tail:* Reduces the additive downstream component uniformly (8–20 min range) but does **not** address the branch-driven tail (F07/F12's 75-min B outcomes remain).
- *Resource utilization:* Risk of over-provisioning — with only two resources (F1, F2) and unknown arrival-rate intensity, adding a third resource could leave the final station under-utilized while the real constraint (B) persists; utilization of F1/F2 should be checked against arrival volume before investing.
- *New bottlenecks:* None expected downstream of F, but this fix could mask the need for Recommendation 1 in high-level KPIs (total_flow_time), so it should be evaluated with the fork-join stage reported *separately*, not folded into a single headline number.
- *Synchronization effects:* None — this counterfactual only affects `downstream_queue`, not `join_ready` or branch sync waits.
- *Pilot/measure first:* Track final-station queue length / resource occupancy (F1 vs F2 idle time) over a larger sample to confirm downstream contention is a true queueing phenomenon (see §7) before adding capacity; a low-cost first step is testing whether better F1/F2 dispatch rules (e.g., earliest-available-resource assignment) reduce downstream_queue without adding a resource at all.

**Risk common to both:** the sample is only 12 cases; frequency-based conclusions (e.g., "B critical 66.7% of the time") carry wide uncertainty at this size and should be treated as a preliminary estimate, not a stable rate, pending more data.

```python
import pandas as pd
import numpy as np
from io import StringIO

# ---------------------------------------------------------------------
# 1. Construct the supplied table in memory
# ---------------------------------------------------------------------
raw = """case,arrival,fork_release,A_start,A_end,B_start,B_end,C_start,C_end,final_start,final_end,final_resource
F01,07:55,08:10,08:10,09:00,08:15,08:55,08:20,08:38,09:08,09:28,F1

F09,09:50,10:10,10:10,11:00,10:35,11:15,10:15,10:35,11:30,11:50,F1
F10,10:05,10:25,10:25,11:15,10:45,11:20,10:30,10:50,11:40,12:00,F2
F11,10:20,10:40,10:40,11:30,10:50,11:20,10:45,11:03,11:50,12:10,F1
F12,10:35,10:55,10:55,11:45,11:25,12:10,11:00,11:18,12:20,12:40,F2
"""
df = pd.read_csv(StringIO(raw))
DATE = "2026-05-19"
time_cols = ["arrival","fork_release","A_start","A_end","B_start","B_end",
             "C_start","C_end","final_start","final_end"]
for c in time_cols:
    df[c] = pd.to_datetime(DATE + " " + df[c], format="%Y-%m-%d %H:%M")

def mins(td):
    return td.dt.total_seconds() / 60.0

# ---------------------------------------------------------------------
# 2. Decomposition components.
# NOTE: join_ready / sync-waits / downstream_queue are CUSTOM pandas
# calculations implementing the stated max-based fork/join rule.
# A standard directly-follows / performance-DFG view (pm4py) only sees
# consecutive events *within a single trace ordering*; it has no notion
# of "wait for the slowest of several parallel branches", so it cannot
# recover join_ready or synchronization waiting on its own. That is why
# these quantities must be derived directly from the raw timestamps.
# ---------------------------------------------------------------------
df["upstream_elapsed"] = mins(df.fork_release - df.arrival)
for b in ["A", "B", "C"]:
    df[f"{b}_queue"]   = mins(df[f"{b}_start"] - df.fork_release)
    df[f"{b}_service"] = mins(df[f"{b}_end"]   - df[f"{b}_start"])

df["join_ready"] = df[["A_end", "B_end", "C_end"]].max(axis=1)

# Deterministic tie-break: alphabetical priority A < B < C on exact ties.
def critical_branch(row):
    ends = {"A": row.A_end, "B": row.B_end, "C": row.C_end}
    m = max(ends.values())
    for b in ["A", "B", "C"]:
        if ends[b] == m:
            return b
    return None
df["critical_branch"] = df.apply(critical_branch, axis=1)

for b in ["A", "B", "C"]:
    df[f"sync_{b}"] = mins(df["join_ready"] - df[f"{b}_end"])
    df.loc[df.critical_branch == b, f"sync_{b}"] = 0.0

df["fork_join_stage"]  = mins(df.join_ready - df.fork_release)
df["downstream_queue"] = mins(df.final_start - df.join_ready)
df["final_service"]    = mins(df.final_end - df.final_start)
df["total_flow_time"]  = mins(df.final_end - df.arrival)

# sanity check: no double counting (identity from section 1)
resid = (df.upstream_elapsed + df.fork_join_stage + df.downstream_queue
         + df.final_service - df.total_flow_time).abs().max()
assert resid < 1e-6, "decomposition failed to reconstruct total_flow_time"
for b in ["A", "B", "C"]:
    identity = (df[f"{b}_queue"] + df[f"{b}_service"] + df[f"sync_{b}"]
                - df.fork_join_stage).abs().max()
    assert identity < 1e-6, f"branch {b} queue+service+sync != fork_join_stage"

cols = ["case","upstream_elapsed","A_queue","A_service","B_queue","B_service",
        "C_queue","C_service","join_ready","critical_branch",
        "downstream_queue","final_service","total_flow_time"]
print("=== Case-level decomposition ===")
print(df[cols].to_string(index=False))

# ---------------------------------------------------------------------
# 3. Aggregate branch comparison
# ---------------------------------------------------------------------
agg = pd.DataFrame({
    "branch": ["A", "B", "C"],
    "mean_queue":   [df.A_queue.mean(),   df.B_queue.mean(),   df.C_queue.mean()],
    "mean_service": [df.A_service.mean(), df.B_service.mean(), df.C_service.mean()],
    "max_queue_plus_service": [
        (df.A_queue+df.A_service).max(), (df.B_queue+df.B_service).max(),
        (df.C_queue+df.C_service).max()],
    "mean_sync_wait": [df.sync_A.mean(), df.sync_B.mean(), df.sync_C.mean()],
    "critical_freq": [(df.critical_branch == b).mean() for b in ["A","B","C"]],
})
print("\n=== Branch comparison ===")
print(agg.to_string(index=False))

# ---------------------------------------------------------------------
# 4. Counterfactuals
# ---------------------------------------------------------------------
def flow_delta(join_ready_cf):
    # holding downstream_queue and final_service fixed (labeled assumption)
    return df.join_ready - join_ready_cf   # minutes saved in total_flow_time

# CF1: A service -20%  (A always starts at fork_release => A_queue=0)
A_end_cf1 = df.fork_release + pd.to_timedelta(df.A_service * 0.8, unit="m")
join_cf1 = pd.concat([A_end_cf1, df.B_end, df.C_end], axis=1).max(axis=1)
df["cf1_saving_min"] = mins(pd.Series(df.join_ready - join_cf1))

# CF2: B queue -50%
B_end_cf2 = df.B_end - pd.to_timedelta(df.B_queue * 0.5, unit="m")
join_cf2 = pd.concat([df.A_end, B_end_cf2, df.C_end], axis=1).max(axis=1)
df["cf2_saving_min"] = mins(pd.Series(df.join_ready - join_cf2))

# CF3: downstream queue eliminated / halved
df["cf3_full_saving_min"] = df.downstream_queue
df["cf3_half_saving_min"] = df.downstream_queue * 0.5

cf_summary = pd.DataFrame({
    "counterfactual": ["A service -20%", "B queue -50%",
                        "Downstream queue -50%", "Downstream queue eliminated"],
    "mean_saving_min": [df.cf1_saving_min.mean(), df.cf2_saving_min.mean(),
                         df.cf3_half_saving_min.mean(), df.cf3_full_saving_min.mean()],
    "cases_benefiting": [ (df.cf1_saving_min>1e-6).sum(), (df.cf2_saving_min>1e-6).sum(),
                          (df.cf3_half_saving_min>1e-6).sum(), (df.cf3_full_saving_min>1e-6).sum()],
})
print("\n=== Counterfactual summary ===")
print(cf_summary.to_string(index=False))
print("\nPer-case CF1/CF2 savings:")
print(df[["case","cf1_saving_min","cf2_saving_min","downstream_queue"]].to_string(index=False))

# 5-6. PM4Py interval-event log: one row per branch/final activity
# with start_timestamp and time:timestamp (completion).

# branch label as a resource *proxy* (explicit assumption).
# ---------------------------------------------------------------------
try:
    import pm4py
    rows = []
    for _, r in df.iterrows():
        for act, s, e, res in [
            ("A_LabAssay",   r.A_start, r.A_end, "A_res"),
            ("B_StressTest", r.B_start, r.B_end, "B_res"),
            ("C_DocReview",  r.C_start, r.C_end, "C_res"),
            ("F_ReleaseDecision", r.final_start, r.final_end, r.final_resource),
        ]:
            rows.append({"case:concept:name": r.case, "concept:name": act,
                         "start_timestamp": s, "time:timestamp": e,
                         "org:resource": res})
    interval_df = pd.DataFrame(rows)
    interval_df = pm4py.format_dataframe(
        interval_df, case_id="case:concept:name", activity_key="concept:name",
        timestamp_key="time:timestamp", start_timestamp_key="start_timestamp")

    # Relevant method: performance DFG. IMPORTANT — this only reports mean/median
    # time on directly-follows *arcs* (e.g. A->F, B->F, C->F) in whatever trace
    # ordering pm4py infers; it CANNOT reconstruct join_ready or sync waits,
    # because those require the max() over concurrently running branches, a
    # concept the sequential DFG model does not represent. It is shown here
    # only as a cross-check / descriptive-stats complement to the custom
    # pandas fork-join logic above, not a replacement for it.
    dfg, start_act, end_act = pm4py.discover_performance_dfg(interval_df)
    print("\n=== PM4Py performance DFG (illustrative only; not fork-join aware) ===")
    for k, v in dfg.items():
```

# 7. Limits of inference

- **Causality:** The data show correlated timestamps, not causal mechanisms. We cannot confirm *why* B's queue varies (e.g., staffing pattern, equipment contention, batching policy) or *why* C's queue spikes in F04 — only that it does.
- **Branch resource capacity:** No resource identifiers are logged for A, B, or C (only the final station distinguishes F1/F2). We therefore cannot tell whether B's queueing reflects one saturated resource, several resources with variable load, or a scheduling/priority policy — the "B_res"/"A_res"/"C_res" labels used in the code are a labeling convenience, not evidence of actual resource pools.
- **Work preemption / interruption:** Complete-event timestamps at one-minute resolution cannot reveal whether any branch's execution was paused and resumed (e.g., a technician switching tasks mid-assay). Service-time values are therefore *elapsed*, not necessarily *effort*, durations.
- **Final-station queue vs. release policy:** `downstream_queue = final_start  join_ready` is consistent with genuine queueing (F1/F2 busy with other cases) but is equally consistent with a deliberate policy (e.g., a fixed administrative buffer, batch-release scheduling, or a rule requiring a minimum delay after join before release). With only 12 cases and no visibility into F1/F2's occupancy on *other* concurrent cases, we cannot distinguish "resource busy" from "policy-mandated wait" — this materially affects whether Recommendation 2 (add capacity) would help at all versus a scheduling/policy change being required instead.
- **Sample size:** With 12 cases, critical-branch frequencies (e.g., B = 66.7%) and counterfactual mean savings are point estimates with unquantified confidence; near-tie cases (F01, F04, F08, F11) show the classification is sensitive to small perturbations, and a larger sample could shift both the ranking margins and possibly the ranking itself between A and C.
- **A's zero observed variance:** A's queue is 0 and service is exactly 50 in all 12 cases. This could reflect a genuinely deterministic process, a resolution artifact (rounding), or simply an unlucky/lucky sample — we cannot rule out latent variability that this data set happens not to exhibit.
