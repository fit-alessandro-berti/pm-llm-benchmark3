## 1. Normalization Assumptions  

1. **Clockoffset direction** – For each system, `true_time = recorded_time - clock_offset`. The offset is a *subtraction* so that a positive offset means the recorded clock runs **fast** (it exceeds the true time).  
2. **Timestamp resolution** – Apply rounding/ flooring **before** clock correction. For example, an “10:14” entry from `OPS-BER` (CEST) means `recorded_time`  [10:14:00, 10:14:59.999] (CEST). Convert to UTC, then subtract the offset interval.  
3. **Timezone conversion** – Use Python’s `zoneinfo` (or `pytz`) with historical daylightsaving data (e.g., 20251026 in Europe/Berlin).  
4. **DST fold (LEGACYBER)** – The ambiguous interval 02:0002:59 on 20251026 maps to *two* possible UTC intervals: one with fold0 and one with fold1. For each event we produce **both** intervals, kept as separate disjoint possibilities.  
5. **Inferred Investigation_Start (T404)** – From the signed work record “duration 1825min”, the possible start times are `Containment_Complete`[18,25]min. The resulting intervals are then corrected for any systemspecific offset (`HUB` metadata).  
6. **MobileLondon entry delay** – `MOBILELON` timestamps are recorded after a possible **user delay** of up to5min. This delay is **added** to the recorded time before applying the clock offset, because the user may have input the displayed instant later than it actually occurred. The final UTC interval is thus `[recordeddelayb, recordeddelaya]` after conversion.  
7. **Causal constraints (T407)** – “Alert_Received must not be after Investigation_Start”. Since `Alert_Sent` is available, we infer an upper bound on `Alert_Received`: `Alert_Received`  `Alert_Sent`. No further timing (e.g., latency bound) is applied because the latency only bounds the **difference** to the *sent* time, not the absolute receive time.  
8. **Handling of rounding** – For systems that round to the nearest 10s (SENSOR) or nearest minute (MOBILELON), the recorded interval is constructed by expanding the rounding rule into a continuous range that includes the exact second/minute value and the permissible rounding error.  
9. **Treatment of missing events** – Whenever an event is missing (e.g., `Investigation_Start` for T404), we **do not** replace it with a midpoint; instead we keep the full uncertainty interval derived from the available constraints.  
10. **Temporalprofile interpretation** – For a given `z` (zeta), a duration `d` is *accepted* if `average ± z × ` contains `d`. Zones of partial overlap give **possible violation**; only when the interval is completely inside or completely outside does it become **certain**.  

These assumptions are stated transparently so that any shift in tolerance or zeta value can be reexamined without hidden changes.

    df.loc[df['case']=='T-405'].apply(lambda r: pd.Series(add_fold(r)), axis=1)

# Resolve possible multiple rows; we keep a list of event dictionaries

norm_df = pd.DataFrame()
for _, row in df.iterrows():

    concept = row['concept']
    # If the field is a Series (multiple possibilities), iterate

        }, ignore_index=True)

offset_map = {

    # true_time = recorded_time - offset, where offset  [lo, hi]
    # therefore true_interval = [recorded_time - hi, recorded_time - lo]

norm_df[['true_start','true_end']] = norm_df.apply(lambda r: pd.Series(correct(r)), axis=1)

**Explanation of the code block**

1. **Reconstruction** – The raw event list (all cases) is built from the evidence.  
2. **Zone conversion & DST handling** – `pytz/zoneinfo` is used; for T405 ambiguous DST fold, two rows per event are generated.  
3. **Clockoffset correction** – `true_interval = [recordedhi, recordedlo]` (since `true = recorded – offset`).  
4. **Midpointonly log** – The mean of the corrected interval (`midpoint`) is kept for the lossy approximation required by PM4Py.  
5. **PM4Py usage** – `pm4py.format_dataframe` normalises the log; `pm4py.conformance_token_based` (or the custom tokenbased approach) is shown (here we directly compute the duration using the same `events_df`). The result dictionary stores passrate for SLAS1 at three zeta values.  

*Note*: PM4Py does **not** automatically expand intervals or handle DST folds; the code therefore first expands to a union of rows and then creates a midpointonly log. The midpoint log is explicitly labelled as a lossy approximation; the intervalbased conclusions from Section3 (where all uncertainties are preserved) remain separate.

## 7. Governance Recommendation  

1. **UTC storage policy** – All event timestamps must be stored in UTC with subsecond precision and a flag indicating the original local offset and resolution rule.  
2. **Clockoffset telemetry** – Continuously record each system’s offset (`clock_offset = recorded  true`). Include both instantaneous measurements and historical bounding intervals (e.g., NTP diagnostics).  
3. **Resolution metadata** – Document rounding/floor rules per system (e.g., “roundtonearest10s” or “floortominute”). Encode this in the log header so that interval expansion can be reproducible.  
4. **DSTfold handling** – For timezones with ambiguous local times, retain **both** possible UTC interpretations as distinct event rows until downstream analysis resolves the fold using additional context (e.g., ingestion order). If ambiguous events are discovered later, flag them for manual review.  
5. **Inferred start/complete events** – When an event must be inferred (e.g., T404), record the full uncertainty interval derived from the constraint (e.g., “Investigation_Start  [10:3010:40]UTC”). Do **not** replace with a midpoint unless the downstream model explicitly requests a lossy approximation.  
6. **Entrydelay awareness** – Mobile or userentered timestamps must include a separate “delay” field (e.g., “5min late”). Apply this delay before clockoffset correction to reflect the actual occurrence time.  
7. **SLA enforcement** – Treat SLA rules as *hard* bounds: any feasible interval that exceeds the bound yields a CERTAIN_VIOLATION, irrespective of statistical acceptability. However, present both the hardbound analysis and the statistical profile sidebyside for accountability.  
8. **Temporalprofile conformance** – Allow configurable `zeta` values; document the chosen `zeta` with its effect on sensitivity (as shown in Section4). Store the chosen `zeta` in the log for auditability.  
9. **Provenance & audit trail** – Every transformation (zone conversion, offset application, rounding, DSTfold selection) must be logged with a unique identifier, timestamp, and the transformation rule applied. This enables reproducibility and future sensitivity analysis.  

**Key takeaway:** By storing the full uncertainty intervals and preserving DSTfold ambiguity, the organization can differentiate *certain* violations (e.g., T401, T408 S2) from *possible* violations (e.g., T402 S1) and from *passes* that rest on statistical expectations. Governance that mandates UTC storage, detailed resolution metadata, and explicit delay handling ensures that downstream interval reasoning remains both transparent and auditable, supporting both legal SLA compliance and robust incidentresponse analytics.
