## 1. Modeling Assumptions

**Object Types and Capitalization:**
- Orders (O100, O200)
- Items (I1, I2, I3)
- Packages (P1, P2)
- Deliveries (D1, D2)
- Invoice (V1)
- Payments (M1, M2)

**E2O Qualifier Vocabulary:**
- `created`: Order creation
- `added`: Item addition to Order
- `reserved`: Stock reservation
- `packed`: Item packing into Package
- `carried`: Package carried by Delivery
- `confirmed`: Delivery confirmation
- `issued`: Invoice creation
- `partially_settled`: Partial payment
- `completed_settlement`: Final payment
- `closed`: Order closure

**O2O Direction Conventions:**
- Unidirectional where natural (e.g., OrderItem)
- Bidirectional for symmetric relationships (e.g., InvoiceOrder)
- Direction preserved in qualifiers (e.g., `bills` vs `is_billed_by`)

**Logistics/Financial Event Relations:**
- Directly relate to Orders/Items where operationally meaningful
- Propagate financial relationships through O2O when direct relations would be ambiguous

**Preventing Analytical Propagation Confusion:**
- Use distinct qualifiers for source relations vs analytical derivations
- Document all O2O relations with clear business semantics
- Validate no circular dependencies in O2O graph

**PM4Py Version Assumption:**
- Using PM4Py 2.0.0+ with OCEL 2.0 support
- If version differs, isolate OCEL constructor line with explanation

## 6. Modeling Alternatives

**1. Source-Minimal Relations:**
- Only include direct E2O relations (e.g., no O2O for contains)
- Would require analytical propagation for all relationships
- Discovery would show weaker Order-Item connections
- Would lose direct visibility of package contents

**2. Full Operational Involvement:**
- Include all possible E2O relations (e.g., every event relates to every touched object)
- Would create relation inflation
- Discovery would show many spurious connections
- Would make analysis harder to interpret

**3. O2O-Propagated Analytical Relations:**
- Derive some relations from O2O (e.g., infer ItemPackage from OrderItem and OrderPackage)
- Would create artificial dependencies
- Discovery would show "analytical" paths as operational
- Would make causal analysis ambiguous

---

## 7. Failure Modes

1. **Relation Inflation:** Creating too many E2O relations obscures actual process flow
2. **Missing Direct Links:** Omitting critical E2O relations breaks discovery
3. **Analytical Propagation:** Treating derived relations as operational facts
4. **Duplicate Shared Events:** After flattening, shared events appear multiple times
5. **Ambiguous Payments:** Payments not clearly allocated to specific Orders/Items
6. **Short Payment Traces:** Payments appear as isolated events without context
7. **Version Mismatch:** OCEL constructor incompatible with PM4Py version
8. **False Ordering:** Same-time events treated as sequential in discovery
