```python
def extract_prefixes(df, case_ids, prefix_length=PREFIX_LENGTH):
    """

    Post-prefix fields are dropped.
```

### Section 1: Target Definition

**Primary prediction target**: Conditional probability of default within 90 days of activation, given the observed application prefix.

- **Prediction target**: Binary event indicator within a 90-day horizon- **Prediction time**: After observing the first K events of the application process (before the activation decision is made)
- **Horizon**: 90 days from the Account Activated timestamp
- **Unit of analysis**: Individual credit application (case)
- **Population**: Applications that are eventually activated under the historical policy
- **Estimand**: E[Y = 1{default  90d} | X_prefix, activated under historical policy]

In survival analysis terms, the estimand is the conditional survival function S(t | X) = P(T > t | X, activated) for t  [0, 90], or equivalently the cumulative hazard or subdistribution hazard.

**Why this formulation is defensible**:
1. It directly answers the business question for the relevant population—accounts that will be activated
2. The outcome is well-defined and observed (with right-censoring for not-yet-matured cases)
3. Standard survival analysis machinery applies
4. No counterfactual assumptions about what would happen to rejected applications

**Alternative 1: Multi-state competing risks model for all applications**

This models the complete process:
- State 0: Application Started
- State 1: Decision (Accept / Reject / Withdraw / Transfer)
- State 2: Activated (only from Accept)
- State 3: Default (only from Activated, within 90 days)
- State 4: No Default (terminal, from Activated)

Estimand: Transition probabilities through this Markov (or semi-Markov) multi-state process. This answers: "What is the probability that a new application will result in a default?" This requires modeling the selection into activation explicitly and treating rejection, withdrawal, and transfer as competing events. It's more complex but uses all 48,000 applications and makes the selection mechanism transparent.

**Alternative 2: Counterfactual default under alternative activation policy**

Estimand: E[Y_i(policy_new) | X_prefix], the expected default if application i were activated under a new policy. This requires strong ignorability (no unmeasured confounders), positivity (every application could be activated), and a model for the outcome that extrapolates to the never-activated population. This is clearly labeled as requiring the strongest assumptions.

### Section 3: Censoring and Missing-Label Strategy

**Five distinct mechanisms:**

1. **Ordinary right censoring (3,600 cases)**: Activated accounts whose 90-day horizon + 35-day label delay has not elapsed by extraction date (Feb 15, 2026). 2. **Delayed labels (systematic)**: The external outcome feed arrives 7–35 days after the 90-day horizon. Even after the horizon elapses, the label may not be immediately available. 3. **Selection through activation (22,800 cases excluded)**: Only activated accounts have a default outcome. This is a form of selection bias. ### Section 8: Limitations and Decision-Use Boundary

**What the study can claim**:
1. Among accounts activated under the historical policy, the model can rank-order default risk based on early application characteristics.
2. The selected features have predictive association with default outcomes in the activated population.
3. The model's discrimination and calibration are quantified with appropriate uncertainty bounds.

**What the study cannot claim**:
1. The model predicts default risk for rejected, withdrawn, or transferred applications—these populations are excluded from the primary analysis.
2. The model cannot evaluate counterfactual outcomes under alternative activation policies without additional assumptions.
3. The model does not establish causal relationships between features and default.

**Three ways deployment could change the data-generating process**:

1. **Model-induced selection change**: If the model is used to change activation decisions (e.g., rejecting more high-risk applications), the distribution of activated accounts shifts. This is a form of performative prediction—the model changes the population it predicts for. Over time, training data becomes less representative of the deployment population.

2. **Feedback loops**: If the model's risk scores influence resource assignment (e.g., assigning more experienced reviewers to high-risk applications), the relationship between resources and outcomes changes. This creates a feedback loop that can degrade model performance over time.

3. **Distribution shift from external factors**: Economic conditions, regulatory changes, or competitor actions can change the applicant pool and default rates in ways not captured by historical data. The model has no mechanism to adapt to such shifts without retraining.

Let me also think carefully about what "estimand" means in this context. The estimand is the quantity we're trying to estimate from the data. For our primary target:

# Uncertainty-Aware Predictive Process Monitoring: Early Warning for 90-Day Default

---

## 1. Target definition

### Primary formulation: Conditional default hazard among activated accounts

| Element | Definition |
|---|---|
| **Prediction target** | Binary event indicator: default within 90 days of Account Activated |
| **Prediction time** | After observing the first *K* events of the application process (before the activation decision) |
| **Horizon** | 90 calendar days from the Account Activated timestamp |
| **Unit of analysis** | Individual credit application (case) |
| **Population** | Applications that are eventually activated under the historical policy |
| **Estimand** | $S(t \mid X) = P(T > t \mid X,\, A{=}1)$ for $t \in [0, 90\text{d}]$, equivalently $F(90 \mid X) = 1 - S(90 \mid X)$, the cumulative incidence of default within 90 days conditional on activation and the observed prefix $X$ |

**Why this is operationally and statistically defensible:**

1. It directly answers the business question for the population that actually receives credit—the only population for which default is meaningful.
2. The outcome is well-defined and observed (with right-censoring for immature cases); standard survival-analysis machinery applies without counterfactual assumptions.
3. Activation is observable, so the model's domain of validity is explicit: predictions apply to accounts activated under the historical policy, not to all applications.
4. It avoids the semantic error of labeling rejected/withdrawn/open applications as "non-default" merely to populate a binary label.

**Limitation (acknowledged upfront):** The model cannot predict what would happen if a rejected application were activated. That is a counterfactual question requiring structural assumptions beyond the scope of this design.

### Alternative 1 — Multi-state competing-outcome model for all applications

This models the complete application lifecycle as a multi-state process:

> Application Started  Decision (Accept / Reject / Withdraw / Transfer)  Activated (only from Accept)  Default / No-Default (within 90d)

**Estimand:** Transition probabilities through this semi-Markov multi-state structure, answering *"What is the probability that a new application will result in a 90-day default?"*

This uses all 48,000 applications, makes the selection mechanism into activation explicit, and treats rejection/withdrawal/transfer as competing events. It requires modeling the decision process and the activation step, which increases complexity but reduces selection bias. Transfer linkage (~60%) introduces additional missingness.

### Alternative 2 — Counterfactual default under a new activation policy (labeled as requiring stronger assumptions)

**Estimand:** $E[Y_i(\pi_{\text{new}}) \mid X]$, the expected default if application $i$ were activated under a proposed new policy $\pi_{\text{new}}$.

This requires strong ignorability (no unmeasured confounders affecting both selection and outcome), positivity (every application has non-zero probability of activation), and a model that extrapolates credibly to the never-activated population. It is useful for policy simulation but is clearly labeled as depending on assumptions that are **untestable** from the available data alone.

### Five distinct mechanisms

| 5 | **Permanently missing outcome feeds** | Subset of activated + transferred | Partner-originated accounts have elevated risk of MNAR missingness | Excluded from primary; MNAR sensitivity analysis |

### Primary analysis strategy

**Survival analysis with right-censoring** for the 25,200 activated accounts.

- **Time origin:** Account Activated timestamp.
- **Event:** Default within 90 days (`default_90d = 1`).
- **Censoring:** Right-censor at min(90 days, extraction date  activation time  35 days). For observed non-default cases, censoring occurs at 90 days (the horizon boundary, at which point the event is known not to have occurred within the window).
- **Covariates:** Process-aware features derived from the application prefix.
- **Stratification:** By pre/post policy-change period (1 Jul 2025) to accommodate regime shift.

### Sensitivity analyses

1. **Transfer inclusion:** Re-run the primary analysis adding the ~1,740 linked transferred cases with their retrieved outcomes. Compare to the primary to assess sensitivity.
2. **MNAR assumption for permanently missing labels:** Assume the missing-label cases have a default rate that is  × the observed default rate, for   {1.5, 2.0, 3.0}. Report how conclusions change.
3. **Informative censoring for not-yet-mature cases:** If the 3,600 censored cases are systematically different (e.g., higher-risk applications submitted late), apply inverse probability of censoring weights (IPCW) to adjust.
4. **Selection model:** Model activation as a function of observed features using a propensity score. Assess overlap; apply IPW to the survival model to re-weight toward the full applicant population. This partially adjusts for selection but cannot account for unmeasured confounders.

### Assumption testability

| Assumption | Status |
|---|---|
| Prefix–outcome relationship is stable within policy regimes | **Partially testable:** compare model coefficients and discrimination across temporal folds within the same regime |
| Censoring is independent of outcome given features | **Partially testable:** compare feature distributions of censored vs. observed cases; test for imbalance |
| The model generalizes across time within the same regime | **Testable:** temporal validation within the pre-policy period |
| The model generalizes across the policy boundary | **Partially testable:** evaluate on post-policy data; structural break tests |
| Transfer cases are comparable to non-transfer cases | **Partially testable:** compare feature distributions of linked transfers vs. non-transfers |
| Rejected applications would have different default rates if activated | **Untestable:** requires counterfactual data or structural assumptions |
| Permanently missing outcomes are MNAR | **Untestable:** cannot distinguish MAR from MNAR without external data |

## 4. Prefix extraction

### Fixed event-count prefixes

After *K* events (primary choice: *K* = 3, capturing Application Started  Identity/KYC Check  Credit Review). The prefix is the ordered sequence of the first *K* events for each case. All events with `event_rank > K` are excluded. All columns that contain post-prefix information (`final_limit`, `decision_reason`, `collection_status`, `default_90d`, `label_available_at`, `documents_total`) are dropped.

Sensitivity variants: *K* = 5 and *K* = 7, to capture more of the document-request loop and later credit-review iterations.

### Elapsed-time prefixes

Alternatively, keep all events within the first *T* hours/days from the application start (e.g., *T* = 72 hours). This creates a uniform time window but variable event counts, which may better reflect real-time deployment constraints. Not all cases will have reached Credit Review within *T* hours.

### Handling edge cases

| Edge case | Treatment |
|---|---|
| **Short cases** (e.g., Rejected after 2 events) | Prefix is the entire case. Excluded from primary analysis (not activated), but retained in the competing-risks alternative. |
| **Document loops** (Credit Review  Request Documents  Credit Review  …) | A fixed-*K* prefix captures the first (K  2)/2 loop iterations. Choice of *K* determines loop visibility. Document-loop count is a feature. |
| **Activity renaming** (post-15 Oct 2025 migration) | All activity names are mapped to canonical forms before prefix extraction via a predefined rename dictionary. |
| **Duplicate events** (migration artifact) | Removed by deduplication on `(case_id, activity, timestamp)` before any analysis. |
| **Events arriving out of order** | After sorting by `(case_id, timestamp)`, event rank is assigned. If out-of-order timestamps persist, the earliest timestamp wins; flag cases with >1h anomalies for review. |

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep / repair / drop | Rationale |
|---|---|---|---|---|
| `final_limit` | **HIGH** — populated only after the final credit decision | Never available at prediction time (occurs after prefix) | **Drop** | Directly determined by the acceptance/rejection decision, which has not occurred at prefix time |
| `decision_reason` | **HIGH** — populated at or after Accept/Reject | Never available at prediction time | **Drop** | Reveals the decision outcome; using it would trivially predict the target |
| `collection_status` | **HIGH** — updated after activation, directly reveals default | Never available at prediction time | **Drop** | Perfect proxy for the target variable; textbook label leakage |
| Future events (Contract Signed, Account Activated, Collections Contact, Default Recorded) | **HIGH** — events occurring after the prediction point | Never available at prediction time | **Drop** via prefix truncation | Temporal ordering violation; these events occur in the future relative to the prefix |
| `documents_total` | **MEDIUM** — nightly snapshot may include documents uploaded later on the same calendar day as the prediction time | Only documents uploaded strictly before the prediction timestamp | **Repair** — compute document count from event timestamps  prefix end, not from snapshot | Same-day snapshot timing creates subtle leakage; the snapshot captures uploads that occurred after the prefix observation time |
| `risk_score` (updated values) | **MEDIUM** — `risk_score` may be updated at several events, including after the prefix | Only the last value observed within the prefix window | **Repair** — use `risk_score_last_prefix` only; do not use the final risk_score value | Later updates may incorporate information from post-prefix events or decisions |
| `resource_experience` | **MEDIUM** — stored at extraction time (15 Feb 2026), not at the event time | Experience as of the event timestamp | **Repair** if timestamped history available; otherwise **drop** or **flag** | Extraction-time experience conflates future promotions, departures, or role changes; introduces temporal bias |
| `label_available_at` | **MEDIUM** — reveals when the outcome became known; is itself label-adjacent | Not a feature; used only for censoring logic | **Drop** as feature | Knowing when the label arrived can indirectly reveal information about the outcome (e.g., delayed feeds may correlate with default) |
| `source_system` | **LOW** — may correlate with data quality or process path | Available from first event | **Keep** with monitoring | Not inherently leaky, but distribution may shift post-migration; include as a covariate and monitor |

## 7. Validation design

### Temporal train / validation / test split

| Split | Application start period | Motivation | Expected size (activated, mature labels) |
|---|---|---|---|
| **Train** | 1 Jan 2024 – 31 Dec 2024 | 12 months, entirely pre-policy change; stable regime; sufficient sample | ~13,000–14,000 |
| **Validation** | 1 Jan 2025 – 30 Jun 2025 | Pre-policy change but recent; used for hyperparameter tuning and early stopping | ~5,500–6,500 |
| **Test** | 1 Jul 2025 – 30 Sep 2025 | Post-policy change, partially post-migration; mimics deployment environment | ~3,500–4,500 (some right-censored) |

Test cases from late September 2025 may have activation dates in November 2025 with labels not yet mature by extraction. These are included as right-censored observations in the test set; evaluation metrics must accommodate censoring.

### Why a random case split is misleading

1. **Policy change (1 Jul 2025):** A random split would mix pre- and post-policy cases across train and test. The model would be trained on data from a regime different from the deployment environment, and test performance would be inflated by the inclusion of "easy" old-regime cases.
2. **System migration (15 Oct 2025):** Random mixing conflates pre- and post-migration activity names and data quality, masking potential issues.
3. **Label maturity:** Randomly assigning late-2025 cases to training would include many right-censored cases, wasting effective training signal and biasing the survival model.
4. **Temporal dependence:** Cases close in time share unobserved macroeconomic and operational context. Random splitting violates the independence assumption between train and test, producing overly optimistic confidence intervals.
5. **Simulated deployment fidelity:** A temporal split replicates the actual model deployment scenario: learn from the past, predict the future.

### Walk-forward backtesting scheme

1. **Phase 1:** Train on 2024 data  validate on Q1 2025  evaluate calibration and discrimination.
2. **Phase 2:** Retrain on 2024 + Q1 2025  validate on Q2 2025  check for distributional drift.
3. **Phase 3:** Retrain on 2024 + H1 2025  test on Q3 2025 (post-policy, post-migration)  final performance report.

This walk-forward approach tests robustness across the policy boundary and simulates periodic model refresh.

### Evaluation metrics (appropriate for survival target with censoring)

| Metric | Purpose | Handles censoring? |
|---|---|---|
| **Harrell's C-index** | Rank-ordering discrimination: concordance between predicted risk and observed default times | Yes |
| **Time-dependent AUC (IPCW)** | Discrimination at the 90-day horizon, adjusted for censoring via inverse probability of censoring weights | Yes |
| **Integrated Brier Score (IPCW)** | Overall calibration and discrimination across the time axis | Yes |
| **Calibration plot at 90 days** | Predicted default probability vs. Kaplan-Meier estimate within risk deciles | Yes (via KM) |
| **Subgroup analysis** | C-index and calibration by channel, region, amount band, and policy period | Yes |

**Calibration in subgroups** is critical: a model well-calibrated overall may be severely miscalibrated for a specific channel or region that has shifted under the new policy.

## 8. Limitations and decision-use boundary

### What the study can claim

1. Among accounts activated under the historical policy, the model can **rank-order** 90-day default risk based on early application characteristics, as measured by the concordance index.
2. Predicted default probabilities can be **calibrated** to approximate the observed default rate within risk strata of the activated population, as assessed by the Brier score and calibration plots.
3. Specific process-aware features (e.g., document-request count, elapsed time, risk-score trajectory) have **predictive association** with default outcomes in the activated population.

### What the study cannot claim

1. The model predicts default for **rejected, withdrawn, or transferred applications**. These populations are excluded from the primary analysis. Default is not defined for accounts that never received credit.
2. The model does not estimate **counterfactual default risk** under alternative activation policies. Evaluating "what would happen if we activated this rejected applicant" requires structural assumptions (strong ignorability, positivity) that are not testable from these data and are not assumed here.
3. The observed associations are **predictive, not causal**. A feature correlated with default (e.g., document-request count) may not cause default; it may proxy for unobserved risk factors.

### Three ways deployment could change the data-generating process

1. **Model-induced selection shift (performative prediction):** If the model's risk scores are used to tighten activation criteria, the distribution of activated accounts changes. Higher-risk applications are filtered out, reducing the default rate in the activated population. Over time, the model is predicting for a population that differs from its training distribution. Periodic recalibration on recent data is essential.

2. **Feedback loops through resource assignment:** If the model flags high-risk applications for review by more experienced staff, and those staff are more effective at catching defaults, the relationship between `risk_score` and actual default changes. The model's features become entangled with the intervention it triggers, degrading its own predictive validity.

3. **Exogenous distribution shift:** Economic downturns, regulatory changes (e.g., new affordability rules), or competitor actions can change the applicant pool composition and default base rate in ways not reflected in the training data. The model has no mechanism to detect or adapt to such shifts without retraining. Monitoring for distributional drift (e.g., PSI on feature distributions, calibration drift) is required.

### Decision-use boundary

The model should be used as a **risk-ranking and calibration tool** within the activated population. It should **not** be used to:
- Deny applications (the model was not trained on rejected applications and has no validity there)
- Set credit limits (the `final_limit` outcome is outside the model's scope)
- Replace human judgment on edge cases without a human-in-the-loop review

## 9. PM4Py-oriented Python implementation skeleton

```python
"""
Predictive process monitoring pipeline:
Conditional 90-day default hazard among activated credit accounts.
Survival analysis with right-censoring; temporal validation; leakage audit.
"""
import pandas as pd
import numpy as np
import pm4py
from datetime import timedelta

#  Configuration 
CID = "case:concept:name"
ACT = "concept:name"
TSC = "time:timestamp"
EXTRACT  = pd.Timestamp("2026-02-15", tz="UTC")
POLICY   = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATE  = pd.Timestamp("2025-10-15", tz="UTC")
HORIZON  = 90        # days from activation to default window end
BUFFER   = 35        # max days for external outcome feed delay
K        = 3         # prefix length in events
TERM_ACT = {"Accepted", "Rejected", "Withdrawn", "Transferred"}

# Columns that must NOT appear in the feature table (leakage set)
_LEAK = frozenset({"final_limit", "decision_reason", "collection_status",
                   "default_90d", "label_available_at", "documents_total"})

#  1. Load, normalise, deduplicate 
raw = pd.read_csv("applications_events.csv", parse_dates=[TSC])
raw[TSC] = pd.to_datetime(raw[TSC], utc=True)

# Normalise post-migration activity names (15 Oct 2025)
RENAME = {"KYC_Verification": "Identity/KYC Check",
          "Document_Request": "Request Documents"}   # extend as needed
raw[ACT] = raw[ACT].replace(RENAME)

# Remove migration-induced duplicate events
raw = (raw.sort_values([CID, TSC])
         .drop_duplicates([CID, ACT, TSC], keep="first"))

# PM4Py formatting
df = pm4py.format_dataframe(raw, case_id=CID,
                             activity_key=ACT, timestamp_key=TSC)

#  2. Build case-level metadata (as-of extraction date) 
def _first(s):
    v = s.dropna()
    return v.iloc[0] if len(v) else np.nan

rows = []
for cid, g in df.groupby(CID):
    g = g.sort_values(TSC)
    # Activation time
    am = g[ACT].eq("Account Activated")
    act_time = g.loc[am, TSC].min() if am.any() else pd.NaT
    # Terminal activity
    tm = g[ACT].isin(TERM_ACT)
    term_act = g.loc[tm, ACT].iloc[0] if tm.any() else "StillOpen"
    term_time = g.loc[tm, TSC].iloc[0] if tm.any() else pd.NaT
    # Label
    dv = g["default_90d"].dropna()
    lv = g["label_available_at"].dropna()
    rows.append(dict(case=cid, start=g[TSC].min(),
                     term_act=term_act, term_time=term_time,
                     act_time=act_time,
                     default_90d=dv.iloc[0] if len(dv) else np.nan,
                     label_at=(pd.to_datetime(lv.iloc[0], utc=True)
                               if len(lv) else pd.NaT),
                     channel=_first(g["case:channel"]),
                     region=_first(g["case:region"]),
                     amount=_first(g["case:requested_amount"])))
meta = pd.DataFrame(rows)
print(f"Total cases: {len(meta)}")

#  3. Cohort classification (accounts for all 48 000) 
def _cohort(r):
    if r.term_act == "Rejected":    return "Rejected"
    if r.term_act == "Withdrawn":   return "Withdrawn"
    if r.term_act == "Transferred": return "Transferred"
    if r.term_act == "StillOpen":   return "StillOpen"
    if pd.isna(r.act_time):         return "Acc_NoActivation"
    if pd.notna(r.default_90d):
        return "Default" if r.default_90d == 1 else "NonDefault"
    mature_by = r.act_time + timedelta(days=HORIZON + BUFFER)
    return "LabelMissing" if EXTRACT >= mature_by else "NotYetMature"

meta["cohort"] = meta.apply(_cohort, axis=1)
print("\n Cohort flow table ")
print(meta["cohort"].value_counts().sort_index())
assert meta["cohort"].value_counts().sum() == 48000, "Cohort mismatch!"

#  4. Primary analysis set & survival variables 
# Include only activated accounts; non-activated are excluded (not labelled non-default)
prim = meta[meta.cohort.isin(["Default", "NonDefault", "NotYetMature"])].copy()
prim["event"]    = (prim.cohort == "Default").astype(int)
prim["observed"] = prim.cohort.isin(["Default", "NonDefault"]).astype(int)
# Simplified event/censor time; in production use exact default timestamp
prim["t_end"] = np.where(
    prim["observed"] == 1,
    prim["act_time"] + pd.Timedelta(days=HORIZON),
    EXTRACT - pd.Timedelta(days=BUFFER))
prim["t_end"] = pd.to_datetime(prim["t_end"], utc=True)

print(f"\nPrimary set: {len(prim)} activated accounts")
print(f"  Events (default):   {prim['event'].sum()}")
print(f"  Observed (mature):  {prim['observed'].sum()}")
print(f"  Right-censored:     {(1 - prim['observed']).sum()}")

#  5. Temporal train / validation / test split 
def _split(t):
    if t.year == 2024:                return "train"
    if t.year == 2025 and t.month <= 6: return "valid"
    return "test"

prim["split"] = prim["start"].apply(_split)
print("\n Split × event ")
print(prim.pivot_table(index="split", columns="event",
                       values="case", aggfunc="count", fill_value=0))

# NOTE: pm4py.split_train_test(df, train_percentage=0.8) exists for a
# random baseline but is NOT used here: random splits conflate the
# pre-/post-policy regimes and violate temporal ordering.

#  6. Prefix extraction (prevents post-prefix leakage) 
def get_prefix(log_df, case_ids, k=K):
    """First k events per case; drop columns that leak future info."""
    s = log_df[log_df[CID].isin(case_ids)].copy()
    s["evt_rank"] = s.groupby(CID).cumcount() + 1
    s = s[s["evt_rank"] <= k]
    s = s.drop(columns=[c for c in _LEAK if c in s.columns],
               errors="ignore")
    return s

train_ids = prim.loc[prim.split == "train", "case"]
val_ids   = prim.loc[prim.split == "valid", "case"]
test_ids  = prim.loc[prim.split == "test",  "case"]

tr_pf = get_prefix(df, train_ids)
va_pf = get_prefix(df, val_ids)
te_pf = get_prefix(df, test_ids)

# Alternative: pm4py.get_prefixes_from_log returns dict[str, EventLog]
# keyed by prefix trace string; useful for variant-based analysis.

#  7. PM4Py process analysis on prefix window 
# DFG on training prefixes: shows early-process activity transitions
dfg, start_acts, end_acts = pm4py.discover_dfg(tr_pf)
print(f"\nDFG edges (k={K}): {len(dfg)}")

# Variant analysis: how many distinct prefix paths exist?
prefix_log = pm4py.convert_to_event_log(tr_pf)
variants = pm4py.get_variants(prefix_log)
print(f"Distinct prefix variants: {len(variants)}")

#  8. Process-aware feature engineering from prefix 
def build_features(pf_df, meta_df):
    feats = []
    for cid, g in pf_df.groupby(CID):
        g = g.sort_values(TSC)
        m = meta_df.loc[meta_df.case == cid].iloc[0]
        acts = g[ACT].tolist()
        ts   = g[TSC].tolist()
        risk = g["risk_score"].dropna()
        gaps = (np.diff(ts).astype("timedelta64[s]").astype(float) / 3600
                if len(ts) > 1 else [])
        feats.append(dict(
            case=cid,
            #  control-flow 
            n_events=len(acts),
            n_unique_acts=len(set(acts)),
            saw_kyc=int("Identity/KYC Check" in acts),
            n_doc_requests=acts.count("Request Documents"),
            has_loop=int(len(acts) != len(set(acts))),
            #  timing 
            elapsed_h=(ts[-1] - ts[0]).total_seconds() / 3600,
            mean_gap_h=np.mean(gaps) if gaps else np.nan,
            max_gap_h=np.max(gaps) if gaps else np.nan,
            #  risk score (prefix window only) 
            risk_first=risk.iloc[0] if len(risk) else np.nan,
            risk_last_prefix=risk.iloc[-1] if len(risk) else np.nan,
            n_risk_updates=max(len(risk) - 1, 0),
            #  static / calendar 
            channel=m.channel,
            region=m.region,
            requested_amount=m.amount,
            pre_policy=int(m.start < POLICY),
            pre_migration=int(m.start < MIGRATE),
        ))
    return pd.DataFrame(feats)

X_train = build_features(tr_pf, meta)
X_val   = build_features(va_pf, meta)
X_test  = build_features(te_pf, meta)
print(f"\nFeature shapes: train={X_train.shape}, val={X_val.shape}, test={X_test.shape}")

#  9. Leakage audit check 
assert not set(X_train.columns).intersection(_LEAK), \
    "LEAKAGE: forbidden columns found in feature table!"

leakage_audit = pd.DataFrame([
    ["final_limit",        "HIGH", "post-decision field",       "Drop"],
    ["decision_reason",    "HIGH", "reveals Accept/Reject",     "Drop"],
    ["collection_status",  "HIGH", "direct proxy for default",  "Drop"],
    ["future events",      "HIGH", "after prediction point",    "Drop via prefix"],
    ["documents_total",    "MED",  "same-day snapshot leak",    "Use event-time count"],
    ["risk_score updates", "MED",  "post-prefix values",       "Last in prefix only"],
    ["resource_experience","MED",  "extraction-time bias",     "Repair or drop"],
    ["label_available_at", "MED",  "label-adjacent info",      "Not a feature"],
], columns=["Feature", "Risk", "Issue", "Action"])
print("\n Leakage audit ")
print(leakage_audit.to_string(index=False))

#  10. Downstream modelling notes (not executed) 
# SURVIVAL MODEL (e.g., Cox PH via lifelines / scikit-survival):
#   - Time origin : act_time
#   - Event       : default_90d == 1
#   - Right-censor: at min(90 d, EXTRACT  act_time  BUFFER)
#   - Stratify    : pre / post POLICY cutoff
#   - Fit         : CoxPHFitter.fit(df, duration_col, event_col)
#
# COMPETING-RISK ALTERNATIVE (Fine-Gray via lifelines):
```

| Design element | Choice | Why |
|---|---|---|
| Primary target | Conditional default hazard, activated accounts | Outcome well-defined; no counterfactual assumptions needed |
| Rejected/withdrawn cases | Excluded, not labeled as non-default | Default is undefined for unexposed accounts |
| Censoring | Survival analysis with right-censoring | Standard, handles immature labels honestly |
| Validation | Temporal split (2024 / H1-2025 / Q3-2025) | Mimics deployment; respects policy-change boundary |
| Leakage prevention | Prefix truncation + column audit | Every post-prefix field dropped or repaired |
| Assumption transparency | Distinguish testable, partially testable, untestable | Prevents overclaiming |
