## 1. Target definition

**Primary formulation: policy-conditional multi-state early-warning target for all applications.**

The primary target is **not** “90-day default for every application” as a simple binary label, because rejected, withdrawn, transferred, and still-open applications were not exposed to the same credit outcome process. The defensible primary target is a **multi-state application-pathway outcome** from an early prefix:

[
Y \in {\text{activated + default}*{90d},\ \text{activated + non-default}*{90d},\ \text{rejected},\ \text{withdrawn},\ \text{transferred},\ \text{censored/open},\ \text{activated but label delayed/missing}}.
]

The key risk quantity for the lender is:

[
P(\text{Account Activated and default within 90 days after activation} \mid \text{prefix information at } t_p,\ \text{historical policy/process}).
]

This is a **joint observed-policy risk**, not a counterfactual “would default if approved” risk.

**Prediction time.** The model is evaluated at early prefixes, primarily after the first three observed events, typically around `Application Started -> Identity/KYC Check -> Credit Review`. Additional analyses should use first-event, second-event, fifth-event, and elapsed-time prefixes such as 24 hours or 7 days after application start.

**Horizon.** The default horizon remains **90 days after `Account Activated`**. A label is considered usable only if the 90-day window has passed and the delayed external feed has had time to arrive. Since the feed can arrive 7–35 days after the 90-day horizon, a conservative maturity rule is:

[
\text{Account Activated time} + 90\text{ days} + 35\text{ days} \leq \text{evaluation cutoff}.
]

If `label_available_at` is present, it must also be no later than the evaluation cutoff.

**Unit of analysis.** The unit is an **application-prefix**, not merely a case. One application can contribute to different pre-specified prefix analyses, but within any single primary analysis, only one prefix per application is used.

**Population.** All applications started between 1 January 2024 and 31 December 2025 that have reached the relevant prediction point while still live in the process. Rejected, withdrawn, transferred, and open cases remain in the cohort as competing outcomes or censored cases; they are not converted to non-defaults.

**Estimand.** The primary estimand is the vector of state probabilities under the historical lending, review, transfer, and activation policies. Operationally, this supports queue triage, monitoring, and risk-aware review prioritization. It does **not** directly estimate what would happen if a rejected application were forcibly approved.

A credible alternative is **default among accounts that are eventually activated**:

[
P(\text{default}*{90d}=1 \mid \text{eventually activated}, X*{t_p}).
]

That target is statistically cleaner for the warehouse label because `default_90d` is defined only for activated accounts. However, it answers a narrower question: “Among accounts selected into activation by the historical process, which ones defaulted?” It is not a model for every application, and conditioning on eventual activation uses a future selection event that can create selection bias if the model is interpreted as all-application risk.

A stronger but much more assumption-heavy alternative is a **policy-specific counterfactual target**:

[
P(\text{default}*{90d}^{\text{if activated}}=1 \mid X*{t_p}).
]

That would require causal assumptions about approvals, applicant behavior, credit exposure, transfer linkage, and missing outcome feeds. It is not identified from the current export alone.

## 2. Cohort construction

The cohort must begin from the **48,000 applications started**, not from the 21,600 labeled rows. The labeled ML export is a selected subset: activated accounts whose 90-day outcome has matured and arrived.

**Inclusion rules**

Applications are included if they:

1. started between 1 January 2024 and 31 December 2025;
2. have a valid case identifier and timestamped `Application Started` event, or a clearly auditable substitute start timestamp;
3. have events available no later than the analysis cutoff;
4. reached the chosen prediction point while still live, for prefix-specific model fitting.

**Exclusion or quarantine rules**

Rows or cases are excluded or quarantined only for data-quality reasons, not because labels are inconvenient:

1. corrupt or missing case IDs;
2. impossible timestamps, such as events before application start without a known migration explanation;
3. exact or near-exact duplicate events introduced by the 15 October 2025 migration, after deterministic de-duplication;
4. cases where the activity-renaming map cannot reconcile pre- and post-migration activity names;
5. feature columns whose values are populated after the prediction point.

**As-of rules**

For any prediction prefix at time (t_p), features may use only information with timestamps no later than (t_p). Target construction may use later events, but only after the feature table has been frozen. Labels are usable only when `label_available_at <= evaluation_cutoff`. If `label_available_at` is unreliable or missing, use the conservative rule `activation_time + 125 days <= evaluation_cutoff`.

**Cohort-flow table**

| Cohort category                                |      Count | Percent of 48,000 | Current binary ML export status | Primary-study role                                 | Default interpretation                                       |
| ---------------------------------------------- | ---------: | ----------------: | ------------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |

| Activated, mature, default                     |      2,700 |              5.6% | Included                        | Labeled activated default state                    | Observed 90-day default among activated accounts             |
| Rejected                                       |      9,100 |             19.0% | Omitted                         | Competing terminal outcome                         | Not exposed to credit; default is undefined, not non-default |

This table shows why training only on the 21,600 labeled rows would answer a selected activated-account question, not the stated all-application question.

## 3. Censoring and missing-label strategy

The study must separate several mechanisms that are often incorrectly collapsed.

**Ordinary right censoring.** The 5,100 still-open applications have not yet reached a terminal process state by 15 February 2026. Their rejection, withdrawal, transfer, activation, and default pathway outcomes remain unknown. They should be treated as administratively censored, not as non-defaults.

**Delayed labels.** The 3,600 activated accounts without mature `default_90d` labels are different from rejected or open cases. They were exposed to credit, but their 90-day outcome or delayed feed has not arrived. These are label-delay or post-activation censoring cases.

**Selection through activation.** Default is observed only after activation. Activation is not random: it is a process decision influenced by credit review, documents, risk score, policy thresholds, channel, region, and possibly resource behavior. A binary model trained only on activated accounts estimates default conditional on historical activation selection.

**Transfer.** The 2,900 transferred cases are not ordinary closed non-defaults. Transfer is a competing event from the original platform and also a missing follow-up mechanism because cases may reappear under a new identifier. The 60% linkage table should be used in a sensitivity analysis, not silently assumed complete.

**Permanently missing outcome feeds.** Partner-originated activated accounts have elevated permanent missingness. This is likely **missing not at random** if partner origin is related to applicant mix, platform routing, or servicing. Treating missing partner outcomes as non-default would bias risk downward.

**Primary analysis strategy**

Use a **multi-state or competing-risk framework** with censoring-aware estimation:

1. Model transitions from live application prefix to terminal application states: reject, withdraw, transfer, activate, or remain censored.
2. For activated accounts, model the post-activation 90-day default substate only when labels are mature and available.
3. Use inverse probability of censoring weights for administrative censoring and label delay, estimated from observed variables such as start month, channel, region, source system, requested amount, policy regime, migration regime, and activation month.
4. Keep transfer as a separate competing outcome in the primary analysis.
5. Report the full probability vector, not only a default score.

The primary reported default quantity should be labeled as:

> Probability that an application following the historical process is activated and then defaults within 90 days after activation.

That is not the same as:

> Probability that the applicant would default if approved.

**Sensitivity analyses**

A minimum set of sensitivity analyses should include:

1. **Activated-only analysis.** Fit a binary model only among activated mature accounts, then compare it with the primary multi-state model. Report it explicitly as conditional on historical activation.
2. **Transfer-linkage sensitivity.** Use the 60% linked transfers to estimate downstream activation/default where possible; for the unlinked 40%, report bounds or pattern-mixture scenarios.
3. **Partner missing-feed sensitivity.** Re-estimate default risk under assumptions that permanently missing partner outcomes have default rates equal to, 1.5×, 2×, or lower than comparable observed partner-originated accounts.
4. **Policy-regime sensitivity.** Fit or calibrate separate models before and after the 1 July 2025 credit-policy change.
5. **Migration sensitivity.** Evaluate pre- and post-15 October 2025 activity-normalization effects separately.

**Assumptions**

Testable or mostly testable:

* distribution of `label_available_at - activation_time`;
* differences in label delay by source system, region, channel, and activation month;
* duplicate-event rates around migration;
* covariate and variant shifts before and after policy/migration dates;
* whether observed linked transfers resemble unlinked transfers on pre-transfer features.

Partially testable:

* whether censoring is independent after conditioning on observed covariates;
* whether partner-originated missing outcomes are explainable by observed source-system variables;
* whether pre- and post-policy prefixes have enough overlap for stable estimation.

Fundamentally untestable from these data alone:

* whether rejected applicants would have defaulted if approved;
* whether withdrawn applicants would have completed and repaid under a different process;
* outcomes for permanently unlinked transferred cases;
* causal effects of analyst actions, document requests, or approval thresholds without stronger design assumptions.

## 4. Prefix extraction

Prefixes must be created before labels or terminal outcomes are joined to the feature table.

**Fixed event-count prefixes**

Use pre-specified prefix lengths, for example (k \in {1,2,3,5}). For a fixed (k), the prediction time is the timestamp of the (k)-th event, after activity normalization and de-duplication. Cases that have not reached the (k)-th event while live are not eligible for that fixed-(k) prediction. Cases that terminate before (k) should remain in earlier-prefix analyses rather than being forced into a later-prefix cohort.

PM4Py’s `get_prefixes_from_log` can cut longer traces to a requested length, while shorter traces are returned as-is, so the implementation must explicitly record `actual_prefix_length` and prevent shorter traces from being silently treated as full (k)-event prefixes. ([GitHub][1])

**Elapsed-time prefixes**

Use elapsed-time prefixes such as:

* after 1 hour from `Application Started`;
* after 24 hours;
* after 7 days.

For elapsed-time prefixes, the prediction time is `application_start + elapsed_time`. Include only events with `time:timestamp <= prediction_time`. If a case terminated before that elapsed time, it is not live for that elapsed-time prediction; it can be evaluated only at earlier prediction points.

**Short cases**

Short cases are informative. A withdrawal after one event, for example, is part of the process outcome distribution. The correct treatment is not to drop all short cases, but to evaluate them at prefixes they genuinely reached.

**Repeated document loops**

Document loops should be preserved as process signal. Useful prefix variables include number of document requests, number of document-return cycles, last document status, time since last request, total loop duration so far, and whether the case returned to `Credit Review` multiple times. Counts may be capped or winsorized for model stability, but the cycle should not be collapsed into a single binary flag.

**Activity renaming and duplicates**

The 15 October 2025 migration requires a versioned activity-normalization map. Keep both `activity_raw` and `activity_normalized` for audit, but train on normalized activity names. Duplicate events should be removed only using deterministic keys such as case ID, normalized activity, timestamp, resource, and source system, with migration-period duplicate rates reported separately.

## 5. Process-aware features

Feature construction should separate static attributes, prefix-derived behavior, and historical reference features.

**Static case attributes available at or near application start**

* `case:channel`;
* `case:region`;
* `case:requested_amount`;
* source system if known at application start;
* application start month, weekday, hour, quarter;
* policy regime indicator: before or after 1 July 2025;
* system regime indicator: before or after 15 October 2025.

**Prefix-derived control-flow features**

* prefix length;
* last observed activity;
* activity counts;
* normalized prefix variant;
* directly-follows pairs within the prefix;
* whether `Credit Review` has occurred;
* whether documents have been requested;
* number of returns to `Credit Review`;
* rework count;
* number of distinct activities;
* rare-prefix indicator learned from prior training data only.

**Prefix-derived timing features**

* elapsed time since application start;
* time between `Application Started` and `Identity/KYC Check`;
* time between `Identity/KYC Check` and `Credit Review`;
* time since last event;
* inter-event time statistics within the prefix;
* weekend or outside-business-hours indicators;
* age of current queue position if queue timestamps are available.

**Resource and queue features**

* current or last resource, if operationally available;
* number of resource handovers so far;
* whether the same resource performed repeated reviews;
* resource workload at prediction time, computed from cases already open at that time;
* queue length by region/channel at prediction time;
* resource historical behavior calculated only from prior cases, never from future outcomes.

**Risk-score features**

* first risk score observed before prediction time;
* latest risk score as of prediction time;
* risk-score delta within the prefix;
* number of risk-score updates before prediction;
* missing-risk-score indicator.

**Historical reference features**

These require careful lagging:

* historical acceptance rate by channel/region, using only cases started before the prediction case;
* historical default rate among mature activated accounts by segment, lagged enough for label maturity;
* prefix variant frequency learned on the training window only;
* resource experience at event time, if an event-time HR history table exists;
* partner/source-system missing-feed rate estimated only from historical mature cohorts.

## 7. Validation design

A random case split is misleading here because it mixes policy regimes, migration artifacts, resource histories, label-delay patterns, and potentially linked transferred applicants across train and test. It would allow the model to learn from future policy behavior while being evaluated on earlier cases.

Use **temporal validation by application start time**, with label maturity enforced separately.

A practical split is:

| Split                       | Case start period         | Purpose                                                             | Main caveat                                                                               |
| --------------------------- | ------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Train                       | 1 Jan 2024 – 31 Dec 2024  | Model development and feature engineering                           | Must use only labels available by the simulated training cutoff in rolling backtests      |
| Validation 1                | 1 Jan 2025 – 30 Jun 2025  | Pre-policy-change validation                                        | Checks stability before 1 July 2025 threshold change                                      |
| Test 1                      | 1 Jul 2025 – 14 Oct 2025  | Post-policy, pre-migration test                                     | Default labels are mature only for activations early enough before 15 Feb 2026            |
| Test 2 / monitoring holdout | 15 Oct 2025 – 31 Dec 2025 | Post-migration pipeline, prefix, process-path, and drift evaluation | Full 90-day default evaluation is heavily delayed/censored at the current extraction date |

Because the extraction date is 15 February 2026 and the conservative maturity lag is 125 days, activations after roughly 13 October 2025 are not guaranteed to have complete `default_90d` labels by extraction. Therefore, the post-migration window can be used for process-path validation and drift checks, but not as a naive complete default test set.

**Backtesting**

Use rolling-origin backtests:

1. choose a training cutoff date;
2. include only cases and labels that would have been available by that cutoff;
3. freeze feature mappings, activity-normalization maps, encoders, and calibration;
4. score applications started after the cutoff;
5. evaluate only outcomes mature by the evaluation cutoff, with censoring weights where appropriate.

**Policy change**

The 1 July 2025 threshold change should be handled explicitly. At minimum, include a policy-regime feature and report calibration separately pre- and post-change. Better designs fit separate calibration layers or transition hazards by regime if sample size supports it.

**System migration**

The 15 October 2025 activity renaming and duplicate events require a separate migration audit:

* activity frequency before/after mapping;
* duplicate rate by source system;
* prefix variant distribution before/after migration;
* performance with and without post-migration cases.

**Calibration**

For the primary multi-state target, evaluate:

* statewise calibration curves;
* calibration for `activated + default_90d`;
* calibration by channel, region, source system, requested-amount band, policy regime, and migration regime;
* calibration-in-the-large and calibration slope;
* reliability of top-risk deciles.

**Metrics**

For the multi-state/censoring-aware primary analysis, use:

* IPCW Brier score for the activated-default event;
* time-dependent or state-specific AUC/C-index where appropriate;
* multinomial log loss or Brier score on resolved, mature states with censoring adjustment;
* cause-specific recall/lift for `activated + default_90d`;
* top-decile default capture rate;
* calibration error;
* decision-curve or net-benefit analysis for operational triage thresholds.

For the activated-only secondary analysis, report AUROC, PR-AUC, log loss, Brier score, and calibration only on activated mature accounts, clearly labeled as conditional on activation.

**Subgroup performance**

Report performance and calibration by:

* channel;
* region;
* requested amount band;
* source system;
* partner-originated versus lender-originated;
* transfer-linked versus transfer-unlinked;
* pre-/post-policy change;
* pre-/post-migration;
* prefix length;
* document-loop presence.

## 8. Limitations and decision-use boundary

This study can claim:

1. early application prefixes are predictively associated with observed historical process pathways;
2. under the historical policy, some prefixes have higher probability of ending in `activated + default_90d`;
3. process-aware features can support triage, queue monitoring, and risk-based review prioritization;
4. the current labeled export is insufficient for an honest all-application binary default model.

This study cannot claim:

1. rejected applications are non-defaults;
2. a rejected applicant would or would not have defaulted if approved;
3. analyst document requests causally reduce or increase default risk;
4. a model trained under the old threshold policy is automatically calibrated after the 1 July 2025 change;
5. transferred or partner-originated missing-feed cases have the same outcome distribution as fully observed lender-originated activated accounts;
6. the model estimates a causal approval policy without additional identification assumptions.

Deployment could change the data-generating process in several ways:

1. **Selective-label feedback.** If high-scoring applications are rejected more often, their default outcomes become even less observable.
2. **Reviewer behavior changes.** Analysts may request more documents, escalate cases, or delay decisions based on the score, changing prefixes and outcomes.
3. **Applicant behavior changes.** Applicants may withdraw more often if asked for extra evidence or routed through longer checks.
4. **Portfolio mix changes.** A new score may alter the population that reaches activation, changing the observed default base rate.
5. **Partner routing changes.** More cases may be transferred to partners or specialist platforms, increasing missing follow-up.
6. **Collections and reporting changes.** Earlier intervention could change whether and when defaults are recorded.

Therefore, the model should be deployed only as an **early-warning and decision-support tool**, not as proof that an applicant would default under a hypothetical approval intervention.

## 9. PM4Py-oriented Python implementation skeleton

The skeleton below uses PM4Py in its pandas-dataframe style: PM4Py documentation describes pandas dataframes as the preferred traditional event-log structure, recommends reading CSVs with pandas before formatting, and documents functions such as `format_dataframe`, `discover_dfg`, `get_prefixes_from_log`, `get_variants`, and `extract_temporal_features_dataframe`. ([GitHub][1])

```python
import numpy as np
import pandas as pd
import pm4py

# -----------------------------
# Configuration
# -----------------------------
CASE = "case:concept:name"
ACT = "concept:name"
TS = "time:timestamp"
RES = "org:resource"

AS_OF = pd.Timestamp("2026-02-15", tz="UTC")
OBS_START = pd.Timestamp("2024-01-01", tz="UTC")
OBS_END = pd.Timestamp("2025-12-31 23:59:59", tz="UTC")
POLICY_CHANGE = pd.Timestamp("2025-07-01", tz="UTC")
MIGRATION_DATE = pd.Timestamp("2025-10-15", tz="UTC")

DEFAULT_HORIZON = pd.Timedelta(days=90)
MAX_FEED_LAG = pd.Timedelta(days=35)
MATURITY_LAG = DEFAULT_HORIZON + MAX_FEED_LAG

PREFIX_LEN = 3

TERMINAL_ACTS = ["Rejected", "Withdrawn", "Transferred", "Account Activated"]

LEAKY_COLUMNS = {
    "final_limit",
    "decision_reason",
    "collection_status",
    "default_90d",
    "label_available_at",
    "data_extract_time",
}

POST_PREFIX_OUTCOME_ACTS = {
    "Contract Signed",
    "Account Activated",
    "Collections Contact",
    "Default Recorded",
}

# Versioned migration map. In production, store this as a governed reference table.
ACTIVITY_MAP = {
    "KYC Check": "Identity/KYC Check",
    "Identity Check": "Identity/KYC Check",
    "ID Verification": "Identity/KYC Check",
    "Credit Assessment": "Credit Review",
    "Manual Credit Review": "Credit Review",
    "Docs Requested": "Documents Requested",
    "Document Request": "Documents Requested",
    "Docs Received": "Documents Received",
    "Account Activation": "Account Activated",
}


# -----------------------------
# Helpers
# -----------------------------
def to_utc(series: pd.Series) -> pd.Series:
    return pd.to_datetime(series, errors="coerce", utc=True)


def last_non_null(series: pd.Series):
    s = series.dropna()
    return s.iloc[-1] if len(s) else np.nan


def parse_binary(v):
    if pd.isna(v):
        return np.nan
    if isinstance(v, str):
        v = v.strip().lower()
        if v in {"1", "true", "yes", "y", "default"}:
            return 1
        if v in {"0", "false", "no", "n", "non-default", "nondefault"}:
            return 0
    if v in {0, 1, False, True}:
        return int(v)
    return np.nan


def first_activity_time(events: pd.DataFrame, activity: str) -> pd.Series:
    return (
        events.loc[events[ACT].eq(activity)]
        .groupby(CASE, observed=True)[TS]
        .min()
        .rename(activity)
    )


def resource_handoffs(resources: pd.Series) -> int:
    r = resources.fillna("<missing>")
    if len(r) <= 1:
        return 0
    return int((r != r.shift()).sum() - 1)


def count_activity(values: pd.Series, activity: str) -> int:
    return int(values.eq(activity).sum())


# -----------------------------
# Read and clean event data
# -----------------------------
df = pd.read_csv("applications_events.csv")

for col in [TS, "label_available_at", "data_extract_time"]:
    if col in df.columns:
        df[col] = to_utc(df[col])

df = df.loc[df[CASE].notna() & df[TS].notna()].copy()
df = df.loc[(df[TS] >= OBS_START) & (df[TS] <= OBS_END)].copy()

# Enforce the extraction as-of date. For earlier rolling backtests, replace AS_OF.
if "data_extract_time" in df.columns:
    df = df.loc[df["data_extract_time"].isna() | (df["data_extract_time"] <= AS_OF)].copy()

df["activity_raw"] = df[ACT]
df[ACT] = df[ACT].replace(ACTIVITY_MAP)
df["event_after_migration"] = df[TS] >= MIGRATION_DATE

# Deterministic migration duplicate repair.
dedupe_keys = [CASE, ACT, TS, RES, "source_system"]
dedupe_keys = [c for c in dedupe_keys if c in df.columns]
df = (
    df.sort_values([CASE, TS, ACT])
    .drop_duplicates(subset=dedupe_keys, keep="first")
    .copy()
)

# PM4Py formatting for process-mining functions.
df = pm4py.format_dataframe(
    df,
    case_id=CASE,
    activity_key=ACT,
    timestamp_key=TS,
)

# -----------------------------
# Build case-level outcome/maturity table
# -----------------------------
case_first_event = df.groupby(CASE, observed=True)[TS].min().rename("first_event_time")
case_start = first_activity_time(df, "Application Started").rename("case_start")

case_info = pd.DataFrame(index=case_first_event.index)
case_info["case_start"] = case_start.reindex(case_info.index).fillna(case_first_event)
case_info["last_event_time"] = df.groupby(CASE, observed=True)[TS].max()

# Static attributes: take first observed value, not future-filled values.
static_cols = [
    "case:channel",
    "case:region",
    "case:requested_amount",
    "source_system",
]
static_cols = [c for c in static_cols if c in df.columns]
case_static = df.sort_values([CASE, TS]).groupby(CASE, observed=True)[static_cols].first()
case_info = case_info.join(case_static, how="left")

# First terminal event among rejection, withdrawal, transfer, activation.
terminal_frames = []
for act in TERMINAL_ACTS:
    s = first_activity_time(df, act)
    terminal_frames.append(
        pd.DataFrame(
            {
                CASE: s.index,
                "terminal_activity": act,
                "terminal_time": s.values,
            }
        )
    )

terminal_long = pd.concat(terminal_frames, ignore_index=True)
terminal_long = terminal_long.dropna(subset=["terminal_time"])
terminal_first = (
    terminal_long.sort_values([CASE, "terminal_time"])
    .groupby(CASE, observed=True)
    .first()
)

case_info = case_info.join(terminal_first[["terminal_activity", "terminal_time"]], how="left")

activation_time = first_activity_time(df, "Account Activated").rename("activation_time")
case_info = case_info.join(activation_time, how="left")

# Latest known label and its availability timestamp.
label_cols = [c for c in ["default_90d", "label_available_at"] if c in df.columns]
labels = (
    df.sort_values([CASE, TS])
    .groupby(CASE, observed=True)[label_cols]
    .agg(last_non_null)
)
if "default_90d" in labels.columns:
    labels["default_90d"] = labels["default_90d"].apply(parse_binary)
else:
    labels["default_90d"] = np.nan

if "label_available_at" not in labels.columns:
    labels["label_available_at"] = pd.NaT

case_info = case_info.join(labels[["default_90d", "label_available_at"]], how="left")

case_info["maturity_deadline_conservative"] = case_info["activation_time"] + MATURITY_LAG
case_info["mature_by_conservative_rule"] = (
    case_info["activation_time"].notna()
    & (case_info["maturity_deadline_conservative"] <= AS_OF)
)

case_info["label_observed_asof"] = (
    case_info["default_90d"].notna()
    & case_info["label_available_at"].notna()
    & (case_info["label_available_at"] <= AS_OF)
)

# Primary multi-state status. Do not call rejected/withdrawn/open non-default.
case_info["primary_status"] = "open_censored"

case_info.loc[
    case_info["terminal_activity"].eq("Rejected"),
    "primary_status",
] = "rejected_competing"

case_info.loc[
    case_info["terminal_activity"].eq("Withdrawn"),
    "primary_status",
] = "withdrawn_competing"

case_info.loc[
    case_info["terminal_activity"].eq("Transferred"),
    "primary_status",
] = "transferred_competing_or_missing_followup"

activated = case_info["activation_time"].notna()
observed_default = case_info["label_observed_asof"] & case_info["default_90d"].eq(1)
observed_nondefault = case_info["label_observed_asof"] & case_info["default_90d"].eq(0)

case_info.loc[activated & observed_default, "primary_status"] = "activated_default90"
case_info.loc[activated & observed_nondefault, "primary_status"] = "activated_nondefault90"

case_info.loc[
    activated & ~case_info["label_observed_asof"] & ~case_info["mature_by_conservative_rule"],
    "primary_status",
] = "activated_label_delayed_or_right_censored"

case_info.loc[
    activated & ~case_info["label_observed_asof"] & case_info["mature_by_conservative_rule"],
    "primary_status",
] = "activated_feed_missing_candidate"

cohort_counts = (
    case_info["primary_status"]
    .value_counts(dropna=False)
    .rename_axis("primary_status")
    .reset_index(name="n")
)
cohort_counts["pct"] = cohort_counts["n"] / cohort_counts["n"].sum()

# -----------------------------
# Temporal split by case start time
# -----------------------------
def assign_temporal_split(start_time: pd.Timestamp) -> str:
    if pd.isna(start_time):
        return "unknown_start"
    if start_time < pd.Timestamp("2025-01-01", tz="UTC"):
        return "train_2024"
    if start_time < POLICY_CHANGE:
        return "validation_2025H1_pre_policy"
    if start_time < MIGRATION_DATE:
        return "test_post_policy_pre_migration"
    return "holdout_post_migration_label_delayed"

case_info["split"] = case_info["case_start"].apply(assign_temporal_split)
case_info["policy_regime_at_start"] = np.where(
    case_info["case_start"] < POLICY_CHANGE,
    "pre_policy_change",
    "post_policy_change",
)
case_info["system_regime_at_start"] = np.where(
    case_info["case_start"] < MIGRATION_DATE,
    "pre_migration",
    "post_migration",
)

# pm4py.split_train_test(log) can be useful as a quick baseline, but the
# primary validation design stays temporal and case-start based.

# -----------------------------
# Prefix extraction without future columns
# -----------------------------
safe_event_cols = [
    CASE,
    ACT,
    TS,
    RES,
    "risk_score",
    "case:channel",
    "case:region",
    "case:requested_amount",
    "source_system",
]
safe_event_cols = [c for c in safe_event_cols if c in df.columns]

# Explicitly remove label, decision, final, collection, and extraction fields.
safe_log = df[safe_event_cols].copy()
assert not (set(safe_log.columns) & LEAKY_COLUMNS)

prefix_log = pm4py.get_prefixes_from_log(
    safe_log,
    length=PREFIX_LEN,
    case_id_key=CASE,
)
prefix_log = prefix_log.sort_values([CASE, TS]).copy()

prefix_meta = (
    prefix_log.groupby(CASE, observed=True)
    .agg(
        actual_prefix_len=(ACT, "size"),
        prediction_time=(TS, "max"),
    )
    .join(case_info[["terminal_time", "terminal_activity", "split"]], how="left")
)

# For a fixed-k live prediction, require a full prefix and no terminal event
# at or before the prediction timestamp.
prefix_meta["has_full_k_prefix"] = prefix_meta["actual_prefix_len"] >= PREFIX_LEN
prefix_meta["terminal_before_or_at_prediction"] = (
    prefix_meta["terminal_time"].notna()
    & (prefix_meta["terminal_time"] <= prefix_meta["prediction_time"])
)

eligible_cases = prefix_meta.index[
    prefix_meta["has_full_k_prefix"]
    & ~prefix_meta["terminal_before_or_at_prediction"]
]

prefix_log = prefix_log.loc[prefix_log[CASE].isin(eligible_cases)].copy()
prefix_meta = prefix_meta.loc[eligible_cases].copy()

# Audit: no event can be after its own prefix prediction time.
tmp = prefix_log[[CASE, TS]].merge(
    prefix_meta[["prediction_time"]],
    left_on=CASE,
    right_index=True,
    how="left",
)
assert (tmp[TS] <= tmp["prediction_time"]).all()

# -----------------------------
# Prefix feature engineering
# -----------------------------
def make_prefix_features(events: pd.DataFrame, meta: pd.DataFrame) -> pd.DataFrame:
    events = events.sort_values([CASE, TS]).copy()
    grp = events.groupby(CASE, observed=True)

    feats = grp.agg(
        prefix_events=(ACT, "size"),
        unique_activities=(ACT, "nunique"),
        first_prefix_time=(TS, "min"),
        last_prefix_time=(TS, "max"),
        last_activity=(ACT, "last"),
        distinct_resources=(RES, "nunique") if RES in events.columns else (ACT, "size"),
    )

    feats["elapsed_hours"] = (
        feats["last_prefix_time"] - feats["first_prefix_time"]
    ).dt.total_seconds() / 3600.0

    feats["doc_requests_so_far"] = grp[ACT].apply(
        lambda s: count_activity(s, "Documents Requested")
    )
    feats["credit_reviews_so_far"] = grp[ACT].apply(
        lambda s: count_activity(s, "Credit Review")
    )
    feats["kyc_seen"] = grp[ACT].apply(
        lambda s: int(s.eq("Identity/KYC Check").any())
    )
    feats["document_loop_seen"] = (
        feats["doc_requests_so_far"].fillna(0).astype(int) > 0
    ).astype(int)

    if RES in events.columns:
        feats["resource_handoffs_so_far"] = grp[RES].apply(resource_handoffs)
    else:
        feats["resource_handoffs_so_far"] = np.nan

    if "risk_score" in events.columns:
        events["risk_score"] = pd.to_numeric(events["risk_score"], errors="coerce")
        risk_first = (
            events.dropna(subset=["risk_score"])
            .groupby(CASE, observed=True)["risk_score"]
            .first()
        )
        risk_last = (
            events.dropna(subset=["risk_score"])
            .groupby(CASE, observed=True)["risk_score"]
            .last()
        )
        feats["risk_score_first_asof"] = risk_first
        feats["risk_score_last_asof"] = risk_last
        feats["risk_score_delta_asof"] = risk_last - risk_first
        feats["risk_score_missing_asof"] = feats["risk_score_last_asof"].isna().astype(int)

    first_rows = events.groupby(CASE, observed=True).first()
    for col in ["case:channel", "case:region", "case:requested_amount", "source_system"]:
        if col in first_rows.columns:
            feats[col] = first_rows[col]

    feats = feats.join(meta[["prediction_time", "split"]], how="left")
    feats["prediction_month"] = feats["prediction_time"].dt.to_period("M").astype(str)
    feats["post_policy_change_at_prediction"] = (
        feats["prediction_time"] >= POLICY_CHANGE
    ).astype(int)
    feats["post_migration_at_prediction"] = (
        feats["prediction_time"] >= MIGRATION_DATE
    ).astype(int)

    return feats


prefix_features = make_prefix_features(prefix_log, prefix_meta)

# Labels/statuses are joined only after features are built.
model_frame = prefix_features.join(
    case_info[
        [
            "primary_status",
            "default_90d",
            "label_observed_asof",
            "mature_by_conservative_rule",
            "policy_regime_at_start",
            "system_regime_at_start",
        ]
    ],
    how="left",
)

# PM4Py descriptive process features on train prefixes only
# -----------------------------
train_cases = case_info.index[case_info["split"].eq("train_2024")]
train_prefix_log = prefix_log.loc[prefix_log[CASE].isin(train_cases)].copy()

if len(train_prefix_log) > 0:
    dfg, start_acts, end_acts = pm4py.discover_dfg(

    # Descriptive calendar/process load features, not direct labels.

        activity_key=ACT,
        timestamp_key=TS,
        resource_key=RES,
    )
else:
    dfg, start_acts, end_acts, variants, temporal_features = {}, {}, {}, {}, pd.DataFrame()

feature_cols = set(prefix_features.columns)

print(cohort_counts.sort_values("primary_status"))
```
