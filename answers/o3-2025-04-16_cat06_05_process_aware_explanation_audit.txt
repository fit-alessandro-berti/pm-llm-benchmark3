## 2. Process-model consistency checks

Proposed validation suite:

1. Prefix-time availability check  
   • For each feature, store the feature-timestamp. Assert feature_timestamp  `t0`.  
   • Fails for `total_case_duration_hours`, `appeal_seen_anywhere`, etc.

2. Activity-order feasibility test (alignment)  
   • Build a reference declarative model:  
     - `Coverage Check Completed` must precede any `Damage Assessment`, `Fraud Investigation`, or `Settlement Decision`.  
     - `Claim Closed` is terminal.  
   • Flag prefixes that violate order (e.g., Closed before Assessment).

3. Same-timestamp ambiguity resolver  
   • If two events share timestamp, use sequence index; if missing, mark “order unknown” and exclude pattern from sequential features.

4. Complete-trace usage detector  
   • Static code scan: any SQL that aggregates over entire case after closure raises an alert.  
   • SHAP explanation audit: if a feature appears whose lineage references “final”, “last”, “total”, or “anywhere”, require explicit feature_timestamp evidence.

5. Activity enablement states  
   • Using Petri-net replay, test whether an activity referenced in an explanation (e.g., “Appeal”) is enabled in the marking reached by the prefix. If not enabled yet, flag.

6. Duplicate Settlement Decision semantic check  
   • Allow at most two occurrences; second must be after an `Appeal`. Use rule-based conformance counters; flag more than two or a second without preceding appeal.

Limitations:  
• Declarative/DFG edges reflect frequency, not obligation, so occasional legitimate deviations need human review.  
• Replay costs grow with variants; batch nightly.

## 5. Recommendations for explanation validation

1. Feature-store redesign  
   a. Store `feature_timestamp` alongside every value; enforce that training and inference filters on `feature_timestamp  t0`.  
   b. Version mutable features (e.g., risk scores) with audit history.

2. Historical recomputation pipeline  
   • Generate training examples by truncating each trace at `t0`.  
   • Recompute all *prefix-only* aggregations (counts, durations, variants).

3. Process conformance layer  
   • Before model training and explanation, run the validation suite from Section 2 nightly.  
   • Block deployment if critical violations detected.

4. Calibration and retraining after feature removal  
   • Drop critical-leakage features, retrain, and check Brier score and calibration; adjust thresholds.

5. Explanation stability tests  
   • Use perturbation or bootstrap to verify that SHAP rankings remain stable after minor data drift; flag volatile explanations.

6. Fairness & proxy analysis  
   • Run disparate impact tests on claimant_region, channel, and calendar proxies; simulate removal to evaluate performance trade-offs.

7. Monitoring for schema / process drift  
   • Auto-detect new activities, policy changes, or holiday shifts affecting calendar_week; trigger drift retraining or feature re-weighting.

8. Documentation & governance  
   • Maintain lineage diagrams and human-readable explanations outlining predictive vs. causal limits; sign-off by process owner and compliance.
