## 1. Equivalence design space

I treat each execution \(X\) as an object-centric trace centered on a lead `Order` object, with:
- a totally ordered list of events \(e_1,\dots,e_n\);
- for each event, an activity label \(\alpha(e)\);
- an incidence relation from events to objects with (object type, object id, external-flag) and possibly O2O qualifiers (e.g., `replaces`, `partially_settles`, `removed_before_dispatch`, `replaces_package`).

### 1.1 Activity-sequence equivalence \(E^{act}\)

**Definition.**  
Two executions \(X\) and \(Y\) are activity-sequence equivalent, \(X \sim_{act} Y\), iff

1. We project each execution on the lead `Order`:
   - keep all events that reference the lead `Order` (regardless of other objects);
   - sort them by timestamp; if two events share the same timestamp, break ties by their index in the given list (stable total order).
2. The resulting sequences of activity labels are identical:
   \[
   \langle \alpha(e_1), \dots, \alpha(e_n) \rangle_X = \langle \alpha(f_1), \dots, \alpha(f_m) \rangle_Y
   \]
   and \(n = m\).

**Invariants preserved.**
- Exact ordered sequence of activity labels involving the lead `Order`.
- Length of the sequence, and the number and positions of repetitions of each label (e.g., two `Record Payment` events vs. one).

**Information discarded.**
- All object identifiers and their types, except insofar as they influence whether an event is kept in the `Order`-projection.
- Object multiplicities per event (e.g., how many `Item` or `Package` objects are attached).
- External vs. local objects (`EXT-*` vs local ids).
- O2O qualifiers (`replaces`, `partially_settles`, `removed_before_dispatch`, `replaces_package`).
- Detailed O2O topology (e.g., which package carries which item).

**Reflexive, symmetric, transitive?**
- Reflexive: yes (any sequence equals itself).
- Symmetric: yes (equality of sequences is symmetric).
- Transitive: yes (equality of sequences is transitive).
So \(E^{act}\) is an equivalence relation.

**Concurrency handling.**
- Executions here are linearly ordered, but if same-time events existed, we would:
  - define a deterministic tie-breaker (e.g., original log index, then activity name) to linearize them; or
  - alternatively, treat same-time events as a multiset per timestamp and define equivalence on timestamp-indexed multisets.
- For reproducibility, I assume the first option: concurrent events are stably sorted, so the projected sequence is deterministic and comparably defined for all executions.

### 1.2 Typed structural equivalence under identifier renaming \(E^{str}\)

**Intuition.**  
Two executions are equivalent if they have the same typed event–object graph, up to renaming of object identifiers within each type and externality flag, ignoring O2O qualifiers but respecting whether objects are external.

**Representation.**  
For each execution \(X\), build a graph:
- Object nodes: one node per object, labelled by \((\text{otype}, \text{is\_external})\), where `is_external` is true iff the identifier starts with `EXT-`.
- Event nodes: one node per event, labelled by:
  - activity \(\alpha(e)\),
  - position index \(i\) in the total order (to preserve global ordering).
- E2O edges: for each event–object participation, an edge labelled by the object type and its role (e.g., `Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`).
- O2O edges: unlabeled edges between object nodes ignoring qualifiers (we preserve that there is, e.g., an edge from `Package` to `Item`, but not whether it is `replaces` vs `contains`).

**Definition.**  
Two executions \(X\) and \(Y\) are typed-structurally equivalent, \(X \sim_{str} Y\), iff there exist bijections:
- \(\phi_E\) between event nodes of \(X\) and \(Y\),
- and, for each object type \(T\) and externality flag \(b \in \{\text{external},\text{local}\}\), a bijection \(\phi_{T,b}\) between object nodes of type \(T\) and flag \(b\) in \(X\) and \(Y\),
such that:
1. \(\alpha(e) = \alpha(\phi_E(e))\) and the position index of \(e\) equals that of \(\phi_E(e)\) (events are matched position-wise with same activity).
2. For each E2O edge \((e, T, role, o)\) in \(X\), there is a corresponding E2O edge \((\phi_E(e), T, role, \phi_{T,b}(o))\) in \(Y\), and vice versa.
3. For each O2O edge \((o_1, o_2)\) in \(X\), there is an O2O edge \((\phi_{T_1,b_1}(o_1), \phi_{T_2,b_2}(o_2))\) in \(Y\), and vice versa (edge labels/qualifiers ignored).

**Invariants preserved.**
- Number of events and their activity labels and global ordering.
- For each event, the multiplicity of attached objects of each type and externality flag (e.g., `Dispatch` with 1 `Package` vs 2).
- For each object type and externality flag, the number of objects.
- Shape of the O2O topology (who connects to whom) ignoring qualifiers.

**Information discarded.**
- Raw object identifiers (e.g., `O1` vs `O2` vs `EXT-OA` are only distinguished by externality flag).
- Identity of specific objects beyond type/externality and relative position in the O2O graph.
- O2O qualifiers such as `partially_settles`, `replaces`, `removed_before_dispatch`, `replaces_package`.

**Reflexive, symmetric, transitive?**
- Reflexive: yes (identity bijection).
- Symmetric: yes (inverse bijections).
- Transitive: yes (composition of bijections).
Thus \(E^{str}\) is an equivalence relation.

**Concurrency handling.**
- As above, events are treated as having a total order index.  
  If concurrency existed, we would either:
  - include timestamp and define \(\phi_E\) to respect timestamp equivalence classes and intra-class order up to permutation; or
  - maintain a partial order and require an isomorphism of partially ordered event structures.
- For this dataset, we keep the given total order as-is.

### 1.3 Business-semantic equivalence \(E^{sem}\)

**Intuition.**  
We abstract each execution into a coarse business motif describing:
- whether logistics and invoicing are isolated to a single order or shared,
- whether fulfillment is single- vs multi-shipment,
- whether payments are single vs staged/partial,
- whether there is replacement or return-and-repack behavior.

**Feature vector.**  
For an execution \(X\) centered on order \(O\), define:
- \(pk\): number of distinct `Package` objects that ever ship at least one `Item` belonging to \(O\).
- \(del\): number of distinct `Delivery` objects carrying those packages.
- `multi_pay` (0/1): 1 if there are \(\ge 2\) `Record Payment` events for the same invoice of \(O\).
- `log_share` (0/1): 1 if there exists a `Pack Package` or `Dispatch` event that simultaneously references `Order: O` and at least one *external* order or item (`EXT-*`).
- `inv_share` (0/1): 1 if there exists an `Issue Invoice` or `Record Payment` event that references both `Order: O` and any other external order (`EXT-*`) on the same invoice.
- `replacement` (0/1): 1 if O2O qualifiers indicate an item replacement before shipment (e.g., `I72 replaces I71` and/or `removed_before_dispatch` between items and a package).
- `return_repack` (0/1): 1 if there is a `Return Item` for an item of \(O\) followed by an `Inspect Return` and a subsequent `Pack Package` + `Dispatch` for (some of) the same item(s), with an O2O qualifier that the new package replaces the old one for that item.

**Definition.**  
Two executions \(X\) and \(Y\) are business-semantically equivalent, \(X \sim_{sem} Y\), iff their feature vectors are identical:
\[
(pk_X, del_X, multi\_pay_X, log\_share_X, inv\_share_X, replacement_X, return\_repack_X)
=
(pk_Y, del_Y, multi\_pay_Y, log\_share_Y, inv\_share_Y, replacement_Y, return\_repack_Y).
\]

**Invariants preserved.**
- Coarse logistics pattern: single vs multiple packages and deliveries.
- Whether logistics is shared across orders (`log_share`).
- Whether the invoice/payment are shared (`inv_share`).
- Whether the order exhibits staged/partial payment behavior.
- Presence of two important lifecycle motifs: *replacement before dispatch* and *return+repack*.

**Information discarded.**
- Exact number of items and their mapping to packages, beyond the presence of replacement/return motifs.
- Exact relative ordering of multiple `Pack Package` and `Dispatch` events, as long as counts are unchanged.
- Raw object identifiers and detailed O2O graph shapes.
- Distinction between, e.g., 3 vs 4 packages (only `pk` numeric is kept; in this dataset we only need 1 or 2).

**Reflexive, symmetric, transitive?**
- Reflexive: yes (each execution has the same feature vector as itself).
- Symmetric: yes (equality of feature vectors is symmetric).
- Transitive: yes (equality of feature vectors is transitive).
Thus \(E^{sem}\) is an equivalence relation.

**Concurrency handling.**
- Features depend only on counts, presence/absence of certain motifs, and whether certain events exist; they are insensitive to within-day ordering and concurrency in logistics events, as long as the existence of the motifs is preserved.

### 1.4 Optional fourth relation: logistics-motif equivalence \(E^{log}\)

**Idea.**  
Sometimes we care purely about the *shipping pattern* ignoring finance. Define \(E^{log}\) like \(E^{sem}\), but feature vector restricted to:
- \((pk, del, log\_share, return\_repack)\),
ignoring payments and invoice sharing.  
This is coarser than \(E^{sem}\) and will, for example, group X3 and X4 together, and possibly X4 and X8 if we ignored returns.


## 2. Canonical signatures

I take \(E^{sem}\) as the preferred business equivalence. A canonical signature for an execution is the feature vector encoded as a stable string, invariant under identifier renaming.

### 2.1 Signature format

For execution \(X\),

\[
sig_{sem}(X) =
\text{f"Pk\{pk\}\_D\{del\}\_multiPay\{multi\_pay\}\_logShare\{log\_share\}\_invShare\{inv\_share\}\_repl\{replacement\}\_ret\{return\_repack\}"}
\]

This preserves:
- object types;
- object multiplicities at the package/delivery/payment level;
- external-object usage through `log_share`/`inv_share`;
- event patterns needed for replacement and return motifs;
- repeated activities via `multi_pay` and the fact that multiple packages/deliveries exist.

Identifier renaming leaves the signature unchanged because all features depend only on counts, types, and qualifiers.

### 2.2 Python-like pseudocode

Assume we have an execution as a list of events, where each event is a dict:
- `activity`: string, e.g. `"Pack Package"`;
- `objects`: list of `(otype, oid)` pairs;
- `o2o_qualifiers`: list of `(source_oid, target_oid, qualifier)` triples;
- we can test externality via `oid.startswith("EXT-")`.

```python
from collections import defaultdict

def compute_semantic_signature(execution, lead_order_id):
    # Collect object-type partitions
    packages_for_order = set()
    deliveries_for_order = set()
    invoice_for_order = None
    payments_for_order = []

    has_log_share = False
    has_inv_share = False
    has_replacement = False
    has_return_repack = False

    # Helper: does event reference an external object of type ot?
    def has_external_of_type(event, otype):
        return any(
            t == otype and oid.startswith("EXT-")
            for (t, oid) in event["objects"]
        )

    # Index O2O qualifiers by qualifier type
    q_by_type = defaultdict(list)
    for (src, tgt, q) in execution.o2o_qualifiers:
        q_by_type[q].append((src, tgt))

    # First pass: identify packages, deliveries, invoices, payments
    for ev in execution.events:  # already in timestamp order
        objs = ev["objects"]
        act = ev["activity"]

        # Link detection helpers
        orders = [oid for (t, oid) in objs if t == "Order"]
        is_lead_in_ev = lead_order_id in orders
        has_other_order = any(
            t == "Order" and oid != lead_order_id for (t, oid) in objs
        )

        if act == "Pack Package" and is_lead_in_ev:
            for (t, oid) in objs:
                if t == "Package":
                    packages_for_order.add(oid)
            # logistics sharing if other orders or items from other orders present
            if has_other_order or has_external_of_type(ev, "Item"):
                has_log_share = True

        if act == "Dispatch" and is_lead_in_ev:
            for (t, oid) in objs:
                if t == "Package":
                    packages_for_order.add(oid)
                if t == "Delivery":
                    deliveries_for_order.add(oid)
            if has_other_order or has_external_of_type(ev, "Item"):
                has_log_share = True

        if act == "Issue Invoice" and is_lead_in_ev:
            invoice_ids = [oid for (t, oid) in objs if t == "Invoice"]
            invoice_for_order = invoice_ids[0] if invoice_ids else None
            if has_other_order:
                has_inv_share = True

        if act == "Record Payment" and is_lead_in_ev:
            pmts = [oid for (t, oid) in objs if t == "Payment"]
            payments_for_order.extend(pmts)
            if has_other_order:
                has_inv_share = True

        if act == "Return Item" and is_lead_in_ev:
            has_return_repack = True  # will refine via repack pattern later

    # Counts
    pk = len(packages_for_order)
    deliv = len(deliveries_for_order)
    multi_pay = 1 if len(payments_for_order) >= 2 else 0

    # Replacement: any qualifier that indicates replacement or removal pre-dispatch
    if q_by_type.get("replaces") or q_by_type.get("removed_before_dispatch"):
        has_replacement = True

    # More precise return+repack detection:
    # Return followed by Inspect Return and a later Pack+Dispatch for same item(s)
    if has_return_repack:
        # In this small example, presence of both "Return Item" and
        # a later Pack+Dispatch for the same item(s) plus a "replaces_package"
        # qualifier is enough to set has_return_repack.
        if q_by_type.get("replaces_package"):
            has_return_repack = True
        else:
            # fallback: pattern-based detection could be added here
            pass

    signature = (
        f"Pk{pk}_D{deliv}_multiPay{multi_pay}_"
        f"logShare{int(has_log_share)}_invShare{int(has_inv_share)}_"
        f"repl{int(has_replacement)}_ret{int(has_return_repack)}"
    )
    return signature
```

This scheme is:
- invariant under identifier renaming (only counts and boolean flags matter);
- sensitive to external objects (through `logShare` and `invShare`);
- able to distinguish the key motifs present in X1–X8.

## 4. Cluster interpretations

### 4.1 SEM-Base (X1, X2)

- **Signature**: `Pk1_D1_multiPay0_logShare0_invShare0_repl0_ret0`.
- **Business behavior**: Standard, isolated order: one package containing all items, one delivery, one invoice, one payment that settles the invoice. No cross-order sharing, no replacements, no returns.
- **Operational risks/opportunities**:
  - Low complexity, low risk; straightforward fulfillment and accounting.
  - Opportunities for optimization via batching at warehouse level exist but would not be visible at this order-centric level.
- **Poorly represented by which flattening?**
  - Most traditional flattenings (case = `Order`, `Package`, or `Invoice`) represent this well; however, case = `Delivery` may understate that all items belong to one order, if later compared with shared deliveries.
- **Stability under data repair**:
  - Very stable: minor timestamp corrections or non-semantic data cleaning (e.g., correcting item labels) do not change the signature unless extra packages/payments are introduced or external links are added.

### 4.2 SEM-SplitPack (X3)

- **Signature**: `Pk2_D1_multiPay0_logShare0_invShare0_repl0_ret0`.
- **Business behavior**: The order is fulfilled in two physical packages but shipped together in a single delivery and invoiced and paid once. Typical reasons: packaging constraints or stock from two bins, but coordinated shipping.
- **Operational risks/opportunities**:
  - Slightly higher warehouse complexity (two picking and packing tasks).
  - Potential cost optimization via consolidating small packages, or evaluating whether two packages are necessary.
- **Poorly represented by which flattening?**
  - Case = `Order` hides that there were two packages and the extra handling cost.
  - Case = `Package` overemphasizes logistics compared with financial simplicity.
- **Stability under data repair**:
  - Stable if we do not invent or drop packages. If a data repair mistakenly merges `Pack Package` events, the cluster could collapse into SEM-Base.

### 4.3 SEM-SplitShip-PartialPay (X4)

- **Signature**: `Pk2_D2_multiPay1_logShare0_invShare0_repl0_ret0`.
- **Business behavior**: The order is shipped in two separate deliveries (likely at different times), and payment is split (e.g., deposit vs final payment, or partial payments). This is a typical backorder or staged-fulfillment scenario.
- **Operational risks/opportunities**:
  - Higher risk of customer dissatisfaction if partial shipments are not communicated clearly.
  - Increased credit and collection complexity due to partial payments.
  - Opportunity to analyze lead time differences between first and second deliveries.
- **Poorly represented by which flattening?**
  - Case = `Order` with naive activity sequence flattening may not highlight the two deliveries and two payments if one collapses repeated labels.
  - Case = `Invoice` misses the split-shipment logistics structure.
- **Stability under data repair**:
  - Sensitive to how multiple payments and deliveries are interpreted. If a repair merges two `Record Payment` events into one (e.g., summing amounts), X4 might migrate to SEM-SplitPack or even SEM-Base depending on deliveries.

### 4.4 SEM-CrossLog (X5)

- **Signature**: `Pk1_D1_multiPay0_logShare1_invShare0_repl0_ret0`.
- **Business behavior**: The package and delivery are shared: items from the focal order and another order’s item(s) are packed into the same package and shipped in one delivery. Financially, the invoice and payment remain order-specific.
- **Operational risks/opportunities**:
  - Risk: errors in allocating shipping costs between orders; customer service issues if one order is delayed but both are shipped together.
  - Opportunity: reduced shipping cost per order due to consolidation.
- **Poorly represented by which flattening?**
  - Case = `Order` hides that the same physical package serves multiple orders.
  - Case = `Delivery` over-aggregates, showing just one delivery without clear order boundaries.
- **Stability under data repair**:
  - Very sensitive to whether external objects are recorded. If external orders or items are dropped from the log, this cluster collapses into SEM-Base.

### 4.5 SEM-CrossInv (X6)

- **Signature**: `Pk1_D1_multiPay0_logShare0_invShare1_repl0_ret0`.
- **Business behavior**: Logistics are isolated to the order, but the invoice and payment cover both this and another order. This is a consolidated billing scenario.
- **Operational risks/opportunities**:
  - Risk: difficult dispute resolution if one order is rejected but the combined invoice is partially paid.
  - Opportunity: reduced invoicing overhead and potential payment-terms negotiation for bulk customers.
- **Poorly represented by which flattening?**
  - Case = `Invoice` hides which subset of line items belongs to which order.
  - Case = `Order` may miss that payment and billing risk are shared across multiple orders.
- **Stability under data repair**:
  - Sensitive to external-order references on invoice/payment. If these are lost, the cluster degenerates into SEM-Base.

### 4.6 SEM-Replacement (X7)

- **Signature**: `Pk1_D1_multiPay0_logShare0_invShare0_repl1_ret0`.
- **Business behavior**: One item is replaced before dispatch; the `Dispatch` event references the replacement item, and qualifiers indicate `I72 replaces I71` and `removed_before_dispatch` for I71. Customer ultimately receives only the replacement item.
- **Operational risks/opportunities**:
  - Risk: inventory mismatches if the removed item is not properly returned to stock.
  - Opportunity: indicator for quality issues or last-minute changes; useful for root-cause analysis on product defects or customer change requests.
- **Poorly represented by which flattening?**
  - Case = `Order` with label-only sequences makes X7 look like X1, hiding the replacement semantics.
  - Case = `Item` emphasizes which item shipped, but may not show the replacement link cleanly if qualifiers are ignored.
- **Stability under data repair**:
  - Very sensitive to O2O qualifiers. If `replaces` and `removed_before_dispatch` are dropped, X7 tends to fall back into SEM-Base under any semantics that do not inspect the `Dispatch` E2O pattern in detail.

### 4.7 SEM-ReturnRepack (X8)

- **Signature**: `Pk2_D2_multiPay0_logShare0_invShare0_repl0_ret1`.
- **Business behavior**: Order is first shipped in a single package; one item is returned, inspected, repacked into a new package, and shipped again in a second delivery. Invoice and payment are still single, but logistics show a return-and-rework loop.
- **Operational risks/opportunities**:
  - Risk: increased handling cost, potential customer dissatisfaction, and warranty exposure.
  - Opportunity: strong signal for quality or fit issues; cluster can help identify products or flows with high return-and-repack rates.
- **Poorly represented by which flattening?**
  - Case = `Order` with naive sequence mining may only see additional `Dispatch` events and ignore that the second is a re-delivery after return.
  - Case = `Delivery` separates the two dispatches but does not link them to a return-and-repack lifecycle.
- **Stability under data repair**:
  - Sensitive to return events and `replaces_package` qualifier. If the return or repack is logged incompletely, X8 may be misclassified as SEM-SplitShip-PartialPay or SEM-SplitPack depending on which parts remain.


## 5. Borderline cases

### X1 versus X2

- Under \(E^{act}\) and \(E^{str}\), X1 and X2 are equivalent: same activity sequence and identical typed structure up to identifier renaming and order of item identifiers within `Add Item`.
- A stricter equivalence that considers the exact *order of item identifiers* within multi-valued event attributes (e.g., the order of `Item` IDs listed in `Add Item`) would distinguish them: X2’s `Add Item` events introduce items in a different identifier order.
- A naive PM4Py-style key that includes raw object identifiers without canonicalization would also split them, because all object IDs differ, even though from a business perspective they represent the same pattern.

### X1 versus X5

- Under activity-sequence equivalence, X1 and X5 are equivalent (both follow `Create, Add, Add, Pack, Dispatch, Issue, Record`).
- Under typed structural equivalence that **ignores externality**, they are close: same multiplicity of objects, but X5’s `Pack`/`Dispatch` events have more `Order` and `Item` objects attached. With externality preserved, \(E^{str}\) and \(E^{sem}\) clearly separate them.
- A business-semantic equivalence that ignores `log_share` (i.e., treats cross-order packaging as irrelevant to the focal order) would cluster X1 and X5 together; a semantics that explicitly cares about cross-order logistics (as in \(E^{sem}\)) distinguishes them.

### X1 versus X6

- Activity-sequence equivalence again groups them (same labels and order).
- Typed-structural equivalence that preserves the number of `Order` objects per invoice and payment event will separate them: X6’s `Issue Invoice` and `Record Payment` reference two orders, X1’s only one.
- A semantics focused purely on outbound logistics (ignoring invoicing structure) might cluster X1 and X6 together; a financial-risk-oriented semantics that pays attention to `inv_share` (multi-order invoices) will keep them apart.

### X1 versus X7

- Label-only views or case = `Order` flattenings that ignore qualifiers and E2O multiplicities for `Dispatch` will likely classify X1 and X7 together.
- Typed-structural equivalence that looks at the `Dispatch` E2O pattern (presence of an explicit `Item` link in X7) already has grounds to separate them, even without qualifiers.
- A business-semantic equivalence that inspects `replaces` and `removed_before_dispatch` flags (as \(E^{sem}\) does) clearly treats X7 as “replacement flow” distinct from the baseline fulfilled order X1.

### X3 versus X4

- Under pure logistics-motif equivalence \(E^{log}\) that only records that there are two packages and at least one delivery, one could argue to cluster X3 and X4 together as “multi-package shipping.”
- Under \(E^{sem}\), they differ: X4 has multiple deliveries and multiple payments; X3 has one delivery and one payment. That is a meaningful business distinction (backorder and staged billing vs simple consolidation).
- A purely financial equivalence relation that only inspects invoices and payments (ignoring detailed logistics) might classify X3 with X1/X2 and set X4 aside as “multi-payment,” ignoring the multi-package nuance.

### X4 versus X8

- Both have two packages and two deliveries, so a coarse equivalence that only counts packages and deliveries (ignoring returns and qualifiers) might cluster X4 and X8 as “two-shipment orders.”
- However, X4’s semantics are staged/cascaded initial fulfillment and subsequent fulfillment with partial payments, whereas X8’s second shipment is a re-delivery after a return and inspection.
- Any semantics that cares about `Return Item`, `Inspect Return`, and `replaces_package` motifs (as in \(E^{sem}\)) clearly differentiates them, while a flattened sequence that collapses labels or ignores qualifiers risks merging them.


## 6. Relation to `pm4py.cluster_equivalent_ocel`

### 6.1 Information preserved by the PM4Py key

`pm4py.cluster_equivalent_ocel` typically constructs an *exact-equivalence* key for each execution (for a given lead object type, here `Order`) that preserves:
- the full ordered sequence of events involving the lead object;
- for each event, its activity label and the exact set of connected objects (types and **raw identifiers**);
- the E2O incidence structure for all involved objects;
- possibly additional event attributes (e.g., lifecycle or timestamp bucketing) depending on configuration.

Thus, two executions fall into the same PM4Py cluster only if they are effectively identical at the level of event labels, ordering, and object incidence, including identifiers.

### 6.2 Why raw object identifiers over-refine clusters

- Raw identifiers distinguish `O1` from `O2` and `I11` from `I21`, even if the topology is isomorphic.
- Therefore, X1 and X2 would be placed in different clusters, despite being structurally and semantically the same after renaming.
- Similarly, every order in a real log with unique IDs would be its own cluster unless other executions literally reused the same identifiers (which rarely happens).

Hence, exact-equivalence clustering without canonicalization is too fine-grained for most business analyses: it encodes bookkeeping artifacts rather than behavioral patterns.

### 6.3 Canonicalization/post-processing strategy

To obtain business-meaningful clusters, we can:
1. Use `pm4py.cluster_equivalent_ocel(ocel, parameters={"lead_ot": "Order"})` to obtain fine-grained execution clusters.
2. For each resulting cluster and each contained execution, compute a **canonical signature** such as `sig_sem` from Section 2.
3. Aggreg
ate clusters by this signature to form semantic clusters.

Python outline:

```python
from pm4py.algo.ocel.equivalence import algorithm as ocel_equiv

lead_ot = "Order"

# Step 1: exact equivalence clustering
exact_clusters = ocel_equiv.apply(ocel, parameters={"lead_ot": lead_ot})
# exact_clusters: dict[cluster_id] -> set of lead-object ids (orders)

def extract_execution(ocel, order_id):
    # Return a lightweight execution object: events, o2o_qualifiers, etc.
    # Details depend on the OCEL data structure.
    ...

def canonical_semantic_signature_for_order(ocel, order_id):
    exec_x = extract_execution(ocel, order_id)
    return compute_semantic_signature(exec_x, lead_order_id=order_id)

# Step 2–3: semantic aggregation
semantic_clusters = {}  # signature -> list of order ids
for cluster_id, order_ids in exact_clusters.items():
    for oid in order_ids:
        sig = canonical_semantic_signature_for_order(ocel, oid)
        semantic_clusters.setdefault(sig, []).append(oid)

# semantic_clusters now groups orders by business-semantic equivalence
```

Additional canonicalization steps could:
- normalize or bucket timestamps (e.g., order-day granularity);
- ignore benign attribute differences (e.g., warehouse code);
- collapse minor variations such as re-logging an identical event.

### 6.4 When to prefer exact vs coarser clustering

- **Exact equivalence (PM4Py key)** is preferable:
  - for *test data validation* (checking that replays or simulations reproduce exact executions);
  - for *technical regression detection* (detecting small changes in system behavior);
  - for *low-volume, high-risk flows* where even small variations matter.
- **Coarser business clustering (e.g., \(E^{sem}\))** is preferable:
  - for *operational segmentation* (grouping orders into few interpretable patterns);
  - for *root-cause analysis* across many similar but not identical cases;
  - for *descriptive reporting* and *KPI drill-down*, where hundreds of micro-clusters are unmanageable.

### 6.5 Role of `max_objs` and large connected components

- `max_objs` in PM4Py limits the number of objects considered when forming an execution around a lead object. If the object-centric graph around an `Order` is very large (many items, returns, linked invoices), clustering can become expensive or degenerate into a single huge connected component.
- With large components:
  - exact-equivalence clustering may produce very few clusters, since many executions differ only in minor structural details;
  - or it may become computationally heavy.
- A reasonable strategy:
  - use `max_objs` to bound neighborhood size for exact equivalence;
  - then apply semantic canonicalization (like \(E^{sem}\)) to distill the relevant business patterns from what remains.


## 7. Robustness analysis

I discuss how semantic cluster assignments would change under the specified perturbations.

### 7.1 Ignore all O2O qualifiers

- Dropping qualifiers (`replaces`, `removed_before_dispatch`, `partially_settles`, `replaces_package`) removes the explicit semantic flags for replacement, partial settlement, and repack relationships.
- **X7 (replacement)**:
  - Without `replaces` and `removed_before_dispatch`, we lose the clear signal that I72 replaces I71; we only see that `Dispatch` references item I72 and not I71.
  - A semantics that depends solely on qualifiers would now classify X7 as SEM-Base instead of SEM-Replacement.
  - In my design, we also use the E2O pattern of `Dispatch`, so some information remains, but classification becomes more fragile.
- **X4 (partial payment)**:
  - If partial vs full settlement is encoded only in qualifiers, ignoring them means we only see two `Record Payment` events for the invoice. We might still treat this as staged payment (by multiplicity), but we lose the nuance of “partial vs correcting” payments.
- **X8 (repack)**:
  - Loss of `replaces_package` weakens our ability to say P82 replaces P81 for I82. We still see a return, inspection, and a second `Pack`+`Dispatch`, but might confuse this with generic split shipping.
- Overall, ignoring qualifiers pushes X7 and X8 closer to baseline logistics clusters under coarser semantics, and blurs the distinction between partial vs repeated payments in X4.

### 7.2 Ignore external objects

- If we drop all `EXT-*` objects and treat only local ones:
  - **X5** loses its cross-order package sharing: `Pack` and `Dispatch` now only involve the focal order’s items and package, so `log_share` becomes 0, moving X5 from SEM-CrossLog to SEM-Base.
  - **X6** loses cross-order invoice sharing: `Issue Invoice` and `Record Payment` appear to involve only the focal order, so `inv_share` becomes 0, moving X6 from SEM-CrossInv to SEM-Base.
- In terms of robustness, this shows that SEM-CrossLog and SEM-CrossInv strongly depend on maintaining explicit external-object references; data extraction that flattens away cross-order links can collapse meaningful business behaviors into the baseline cluster.

### 7.3 Collapse repeated same-label events

Suppose we treat repeated same-label events per case as at most one occurrence (e.g., we compress multiple `Record Payment` events into one, multiple `Pack Package` events into one).

- **X3 vs X4**:
  - Collapsing repeated `Pack Package` and `Dispatch` events would reduce both to a single `Pack` and `Dispatch`. If we also collapse `Record Payment`, X4 appears to have one payment too.
  - Under such a perturbation, X3 and X4 might both map to a SEM-Base-like signature, obliterating distinctions between split packaging, split shipping, and partial payments.
- **X8**:
  - Collapsing repeated `Dispatch` and `Pack Package` could cause X8 to look more like SEM-Base plus a return, or even like SEM-SplitPack if the return is ignored.
- This perturbation dramatically weakens the discriminative power of both \(E^{act}\) and \(E^{sem}\) for patterns where multiplicities are meaningful (multi-ship, multi-pay).

### 7.4 Treat Pack and Dispatch order as partial order

If we regard `Pack Package` and `Dispatch` events as partially ordered (e.g., allowing reordering of multiple `Pack` events, or interleaving `Dispatch` differently) and declare two executions equivalent whenever their partial orders are isomorphic:

- In the current data, this has limited effect because the pack/dispatch sequences are already consistent; however, in more complex logs:
  - X3 and a variant with `Dispatch` interleaved between `Pack` events would remain equivalent under a partial-order semantics but not under strict-sequence equivalence.
- For X4 and X8, both having multiple `Pack` and `Dispatch` events, partial-order semantics could make them appear more similar if we ignore the fact that X8’s second pack/dispatch is *after* a return.
- Thus, relaxing to partial orders improves robustness to benign reordering but risks merging patterns where the ordering itself (e.g., after a return) is semantically important.

### 7.5 Treat payment multiplicity as amount attribute

If we model payments as amounts and only care about the *total* amount per invoice, multiple partial payments that sum to the invoice amount become equivalent to a single payment:

- **X4** might then be considered SEM-SplitShip rather than SEM-SplitShip-PartialPay if we only track that the invoice was ultimately fully settled.
- In absence of explicit amounts in this toy example, we conceptually see how mapping “two partial payments summing to full” and “one full payment” into a single case can mask gradual-collection risk and liquidity patterns.
- For robustness, one might choose to keep a binary `multi_pay` flag even when totals match to preserve staged-payment behavior.


## 8. Limitations and recommendation

No single equivalence notion suits all analytical purposes; each emphasizes different aspects and discards others.

- **Compliance monitoring**:
  - Recommended equivalence: close to typed-structural equivalence \(E^{str}\), possibly refined with some qualifiers (e.g., distinguishing cross-order shipments and multi-order invoices).
  - Rationale: compliance checks often hinge on whether *specific object relationships* occurred (e.g., no invoice without dispatch, no cross-order packaging beyond allowed customers). Overly coarse clustering like \(E^{sem}\) may hide small but non-compliant variations.

- **Operational segmentation**:
  - Recommended equivalence: business-semantic equivalence \(E^{sem}\) or an even coarser variant that groups SEM-Base, SEM-SplitPack, and SEM-SplitShip-PartialPay into a few interpretable segments.
  - Rationale: segmentation aims to bucket orders into a handful of patterns for managing SLAs, capacity, and costs. Fine-grained structural differences are less important than motifs like “cross-order logistics,” “multi-shipment,” or “return-and-repack.”

- **Root-cause analysis**:
  - Recommended equivalence: a hybrid—start from \(E^{sem}\) to focus on specific problematic motifs (e.g., SEM-ReturnRepack, SEM-Replacement), then optionally refine within those clusters using more detailed structural views (partial orders, qualifiers, item-level details).
  - Rationale: you want enough homogeneity within a cluster to attribute issues to a common cause, but you may also need to drill into intra-cluster variations.

- **Descriptive reporting**:
  - Recommended equivalence: activity-sequence equivalence \(E^{act}\) or a light extension that also counts key multiplicities (packages, deliveries, payments) but still yields a small number of variants.
  - Rationale: business dashboards and summary reports need a manageable vocabulary of “flow types.” Overly fine structural distinctions or qualifier-heavy semantics quickly overwhelm stakeholders.

In summary, activity-sequence equivalence is simple and good for high-level reporting; typed-structural equivalence is precise and useful for compliance and technical analyses; business-semantic equivalence provides interpretable, motif-based clusters for operations and root-cause work. Careful canonicalization and post-processing (e.g., as in Section 6) are needed to balance precision with interpretability in real OCEL-based clustering.
