## 1. Conformance semantics

Seven interpretive categories are used, each requiring a different evidentiary bar:

- **Forbidden behavior**: an observed instance matches a relation explicitly marked `forbidden` (N3, T6, E10). Because forbidden relations are closed-world, *any single occurrence* is a nonconformance, independent of frequency — unless a data-quality alternative can be substantiated.
- **Missing mandatory behavior**: a relation marked `mandatory` (N1, N4, T1, T2, E1–E8) is absent for a member that is within the stated scope. Mandatory columns are closed-world *within scope*, so the key judgment is always: *is this instance actually in scope?* (e.g., N4 only applies to packages "intended for external shipment").
- **Unexpected but unregulated behavior**: an observed edge/path has no counterpart in the norm and is not forbidden. Under open-world semantics this is *allowed by default*, not a violation — it is simply outside adjudication.
- **Typical-pattern absence**: a `typical` relation (N2, N5, T3) fails to occur for some members. Absence is expected some of the time; it becomes noteworthy only if no plausible legitimate exception (write-off, credit term, intermediate step) can be identified.
- **Likely data-quality error**: an observation that *would* be a forbidden/mandatory violation but for which the extraction mechanism itself is independently suspect (reused identifiers, attribute-vs-relation mismatch).
- **Abstraction mismatch**: the underlying business rule is an "eventually" or "any-path" rule, while the summary model expresses it as directly-follows or per-event-type aggregation, so a gap in one model's representation can be closed by evidence in another.
- **Insufficient evidence**: the aggregate summary cannot, by itself, determine the correct bucket; case-level data is required.

**Open- vs closed-world effect**: Forbidden edges and in-scope mandatory columns are the *only* places where absence-of-alternative-explanation counts against conformance — a single forbidden edge or a scope-confirmed mandatory gap is meaningful even at low counts. Everything else (typical, unspecified) is open-world: the norm's silence is not evidence of wrongdoing, and low frequency alone never proves misconduct.

## 3. Detailed reasoning by model family

**OC-DFG.** This family establishes directly-follows frequencies per object type — useful for sequence-sensitive rules like N3 (forbidden) where adjacency itself is the violation signal. It cannot establish full case-level ordering beyond the immediate pair, cannot see intervening unmodeled steps, and aggregates across the whole population, so "98 of 100" is a coverage ratio, not case identification. The central danger flagged by the additional context is treating an *eventually* obligation (N1: "should eventually enter validation") as if it were a strict *directly-follows* obligation. The 2 missing Create Order  Validate Order pairs may simply contain an intermediate, unmodeled review event — the DF abstraction is too strict to distinguish "never validated" from "validated late." The same caution applies to N2, which explicitly tolerates intermediate invoice/review/fulfilment steps; low DF coverage there is expected, not alarming. By contrast, the Cancel  Dispatch pair is much stronger evidence precisely because N3 is stated as a forbidden *adjacency*, not an eventually-rule — DF matching here is close to conclusive, modulo convergence/divergence artifacts in the object graph.

**OTG.** This family establishes aggregate object-to-object coexistence/interaction, decoupled from any specific event or time. It is well suited to closed-world forbidden checks (T6) because presence of even one such edge is decisive, and to sanity-checking mandatory coverage in aggregate (T1: 1450 Order-Item edges matching 1450 Add Item events). Its central limitation is that it cannot say *which* event produced a relation, nor when. This is exactly why the Package–Delivery total of 200 can be fully populated at the OTG level while the Dispatch-specific ET–OT pairing shows only 198: the OTG may be aggregating relations established through more than one event or through an object-reference field, while ET–OT is anchored to a single triggering event type. A relation can therefore be **OTG-conforming but ET–OT-suspicious simultaneously** — the same underlying data satisfies one abstraction's obligation while failing the other's stricter anchoring, and only case-level tracing (carrier-reference attribute in this case) can resolve which reading the norm intended.

**ET–OT.** This family gives the finest-grained mandatory/forbidden check, tying specific event types to specific object types and counts (E1–E10). It caught two subtle gaps invisible to the coarser OC-DFG/OTG views: 1448 vs 1450 for Add Item–Order (E2), and 92 vs 93 for Record Payment–Invoice (E8). It cannot, however, identify which two Add Item events or which Record Payment event are implicated, cannot explain causation, and cannot adjudicate whether an absent relation reflects a legitimate exception (unapplied cash) versus a capture failure — attribute-level or source-system evidence is required either way. As with the other families, a mandatory ET–OT gap should never be read in isolation; it must be cross-checked against OTG totals before being escalated, since the two models can legitimately disagree due to differing anchoring assumptions.

## 5. PM4Py conformance code sketch

```python
import pm4py

# --- Discovery (raw, unmodified diagnostic layer) ---
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)

# --- Conformance against normative structures (raw PM4Py output, untouched) ---
ocdfg_conf = pm4py.conformance_ocdfg(ocdfg, norm_ocdfg)
otg_conf = pm4py.conformance_otg(otg, norm_otg)
etot_conf = pm4py.conformance_etot(etot, norm_etot)

# =========================================================================
# SEMANTIC CLASSIFICATION LAYER
# This layer is deliberately separate from PM4Py's raw diagnostics.
# Mandatory / typical / forbidden / unspecified status is NOT encoded
# in the bare graph structures above -- it must be maintained here,
# alongside scope conditions and known data-quality caveats.
# =========================================================================

NORM_STATUS = {
    ("Order", "Create Order", "Validate Order"): "mandatory",      # N1
    ("Order", "Validate Order", "Close Order"): "typical",         # N2
    ("Order", "Cancel Order", "Dispatch Package"): "forbidden",    # N3
    ("Package", "Pack Package", "Dispatch Package"): "mandatory",  # N4
    ("Invoice", "Issue Invoice", "Record Payment"): "typical",     # N5
    ("Order", "Reopen Order", "Close Order"): "unspecified",       # N6
}

OTG_STATUS = {
    ("Order", "object_interaction", "Item"): "mandatory",          # T1
    ("Package", "object_interaction", "Delivery"): "mandatory",    # T2
    ("Invoice", "object_interaction", "Payment"): "typical",       # T3
    ("Order", "object_interaction", "Customer"): "unspecified",    # T4
    ("Order", "object_interaction", "RiskCase"): "unspecified",    # T5
    ("Order", "object_cobirth", "Payment"): "forbidden",           # T6
}

ETOT_STATUS = {
    ("Create Order", "Order"): "mandatory",     # E1
    ("Add Item", "Order"): "mandatory",         # E2
    ("Add Item", "Item"): "mandatory",          # E3
    ("Pack Package", "Package"): "mandatory",   # E4
    ("Dispatch Package", "Package"): "mandatory",   # E5
    ("Dispatch Package", "Delivery"): "mandatory",  # E6
    ("Record Payment", "Payment"): "mandatory",     # E7
    ("Record Payment", "Invoice"): "mandatory_with_exception",  # E8
    ("Manual Compliance Review", "RiskCase"): "unspecified",     # E9
    ("Sensor Heartbeat", "Invoice"): "forbidden",                # E10
}

# Known data-quality caveats, kept separate from norm status so that
# a forbidden/mandatory-gap classification is never silently overwritten.
DQ_CAVEATS = {
    ("Sensor Heartbeat", "Invoice"): "suspected reused-identifier join artifact",
    ("Dispatch Package", "Delivery"): "carrier reference attribute present but not promoted to relation",
}

def classify_deviation(edge_key, observed_count, expected_scope_count, model_family):
    """
    Combines raw PM4Py conformance output with the semantic layer above.
    Never mutates ocdfg_conf / otg_conf / etot_conf -- returns a new record.
    """
    status_map = {"ocdfg": NORM_STATUS, "otg": OTG_STATUS, "etot": ETOT_STATUS}
    status = status_map[model_family].get(edge_key, "unregulated")
    caveat = DQ_CAVEATS.get(edge_key)
    gap = expected_scope_count - observed_count if expected_scope_count else 0
    return {
        "edge": edge_key,
        "norm_status": status,
        "gap": gap,
        "data_quality_caveat": caveat,
        "raw_conformance_ref": model_family,  # pointer back to ocdfg_conf/otg_conf/etot_conf
    }

# Example assembly (illustrative; real code would iterate discovered edges)
findings = [
    classify_deviation(("Order", "Cancel Order", "Dispatch Package"), 2, 0, "ocdfg"),
    classify_deviation(("Order", "object_cobirth", "Payment"), 1, 0, "otg"),
    classify_deviation(("Sensor Heartbeat", "Invoice"), 1, 0, "etot"),
]
```

## 6. Norm-completeness assessment

1. **N1 DF vs eventually ambiguity.** Risk: legitimate intermediate steps (e.g., review) get flagged as mandatory gaps. Clarification: state N1 as an *eventually* relation with a whitelist of tolerated intermediate events, demoting the DF check to an advisory heuristic. Status: mandatory (for the eventual relation), advisory for the DF proxy.
2. **N4 "external shipment" undefined.** Risk: internal-only packages inflate the apparent mandatory gap. Clarification: require an explicit `shipment_type` attribute on Package objects. Status: mandatory metadata requirement.
3. **E8 rigid closed-world exception clause.** Risk: real unapplied-cash cases are flagged as violations because no labeling mechanism exists. Clarification: introduce an explicit "unapplied cash" event flag and require its use going forward. Status: mandatory (labeling procedure); the underlying relation remains typical once labeled.
4. **T2/E6 anchoring ambiguity.** Risk: same data yields opposite verdicts depending on whether OTG-aggregate or ET–OT-anchored evidence is consulted. Clarification: state explicitly whether the Package–Delivery relation must originate from Dispatch Package specifically, or may be established by any event. Status: mandatory clarification of scope.
5. **Interaction between unspecified branches and mandatory outcomes.** Risk: an unspecified path (e.g., Manual Compliance Review) could be used to silently bypass tracking of whether a mandatory obligation (N1) is ever fulfilled. Clarification: require that all unspecified branches still resolve to (or explicitly waive) mandatory downstream obligations. Status: mandatory meta-rule.
6. **No tolerance/frequency bands.** Risk: inconsistent judgment on whether small gaps (2/100, 1/93) are material. Clarification: define minimal tolerance thresholds, or explicitly adopt zero-tolerance with mandatory case-level triage for any gap. Status: needs explicit decision (mandatory either way).
7. **Codeath semantics unaddressed.** Risk: cannot distinguish benign shared-confirmation events from data-quality collapse of two distinct lifecycles. Clarification: define codeath as typical when tied to a named shared confirmation event type. Status: typical.

## 8. Uncertainty statement

The forbidden-relation findings (CancelDispatch, Order–Payment cobirth) are the most robust conclusions, resting on explicit closed-world norm statements and direct structural matches. The mandatory-gap findings (N1, N4, E2, E6, E8) are moderately robust as *signals* but their final classification depends entirely on case-level evidence not present in the aggregate summaries — several are plausibly resolved by legitimate exceptions (unrecorded review, unapplied cash, alternate relation source) rather than true noncompliance. The Sensor Heartbeat–Invoice finding is nominally a forbidden-edge match but carries low confidence as a genuine violation given the explicitly flagged identifier-reuse hypothesis. Conclusions about the norm's own gaps (Section 6) are inherently interpretive, since the norm is deliberately incomplete by design. What cannot be decided from these graph summaries alone: case-level causality, intent behind exceptions, whether the two OC-DFG gaps and the two ET–OT/OTG gaps refer to the same underlying packages, and whether any of the "unregulated" patterns will remain benign as volumes grow — all of which require record-level or source-system evidence beyond the aggregate OC-DFG/OTG/ET–OT tables.
