# 1. Risk indicators

**Overall reading.** The evidence fits **a mixture of explanations, and the mixture differs from one cluster to the next**. It should not be read as one pattern.

- **Routine pairs (Aline/Elena, Boris/Felix).** These look like ordinary team structure. They are the baseline, not a risk.
- **Emergency pairs (Carla/Gita, Dan/Hugo).** These are mostly consistent with designed emergency handling plus informal specialization. They still show real *control exceptions*: segregation-of-duties breaks, late or self-made retrospective justifications, and a shared account. Their risk profile (low vendor concentration, low manual share) does not point to a single beneficiary.
- **Same-person retrospective justifications.** These are largely a data-quality artefact. A small residue remains unexplained.
- **The VendorMaster_Lena → AP_Kim / vendor family V-77x cluster.** This is the one cluster where several independent risk indicators overlap on the most fraud-sensitive control in procure-to-pay (bank-detail change followed by payment). The overlapping indicators are vendor concentration, manual upload, high value, speed, same-person breaks, a tight loop, and few emergency flags. A plausible benign explanation exists: a banking-platform migration with a missing ticket link. That explanation can be tested but has not been verified yet. This cluster deserves the first review. Selecting it for review is not a conclusion that anything improper happened.

A note on figures: the tables use different denominators. For example, Carla/Gita has 118 co-cases in one table and 126 subgroup cases in another. Lena/Kim has a 19-minute median over 44 co-cases, but only 16 cases are in the "fast subgroup". Counts must be reconciled on one case definition before anything is reported.

# 2. Benign alternative explanations

### A. VendorMaster_Lena → AP_Kim: bank-detail change quickly followed by payment approval (V-77x, manual_upload, 9 same-person breaks, 11 loops)

|---|---|---|
| **A1. Legitimate mass maintenance for the V-77x banking-platform migration** | A maintenance/change ticket covering V-77x with a list of affected vendor IDs. New account numbers that match the vendor's own bank confirmation letters or the new platform's migration file. Change dates inside the migration window. One change per vendor, not per case. | Changes outside the migration window. New IBANs not in the migration file. Accounts in a different country or bank from the vendor's legal entity. That "change–pay–revert" signature is a recognised red flag.

# 4. Network and conformance analyses

The approach has four steps:
1. Normalize the log and build alternative resource attributions.
2. Recompute the four-eyes checks under each attribution.
3. Compare networks against workload-based expectations and matched strata, not raw counts.
4. Check timing and the retrospective-justification rule, and isolate source-system effects.

```python
import numpy as np
import pandas as pd
import pm4py

CID, ACT, TS, RES = "case:concept:name", "concept:name", "time:timestamp", "org:resource"
BOTS = {"Bot_PO", "Bot_Match"}

raw = pd.read_csv("p2p_event_log.csv")
df = pm4py.format_dataframe(raw, case_id=CID, activity_key=ACT, timestamp_key=TS)
df["emergency_flag"] = df["emergency_flag"].astype(str).str.lower().isin(["true", "1", "yes"])

# Use completions for ordering, SoD and networks; keep starts for service-time work.
dfc = df[df["lifecycle:transition"].str.lower().eq("complete")].copy()

# --- Alternative resource attributions (robustness) ---
# res_log      : as logged (shared account and mapping errors included)
# res_human    : entered_by where available (resolves shared-account assistants)
# mapping flag : legacy_erp Create PO where bot and human collapse into one org:resource
dfc["res_log"] = dfc[RES]
dfc["res_human"] = dfc["entered_by"].fillna(dfc[RES])
dfc["mapping_suspect"] = (
    dfc["source_system"].eq("legacy_erp")
    & dfc[ACT].eq("Create Purchase Order")
    & (dfc["entered_by"].isin(BOTS) | dfc["entered_by"].isna())
    & dfc[RES].eq(dfc["approved_by"])
)
dfc["shared_account"] = dfc[RES].eq("Approver_Gita") & dfc["entered_by"].notna() & dfc["entered_by"].ne("Approver_Gita")
```

### 4.1 Four-eyes violations with `pm4py.filter_four_eyes_principle`

```python
PAIRS = [
    ("Create Purchase Order", "Approve Purchase Order"),
    ("Change Vendor Bank Details", "Payment Approval"),
    ("Emergency Override", "Retrospective Justification"),
    ("Vendor Check", "Change Vendor Bank Details"),   # role-design check, not a formal rule
]

def pandas_same_person(log, a1, a2, res):
    x = log[log[ACT].isin([a1, a2]) & ~log[res].isin(BOTS)]
    s = x.groupby([CID, res])[ACT].nunique()
    return set(s[s == 2].index.get_level_values(0))

def pm4py_violations(log, a1, a2, res):
    # The meaning of `retain` has been documented inconsistently across pm4py versions,
    # so compute both outputs and keep the one matching the explicit pandas check.
    out_t = pm4py.filter_four_eyes_principle(log, a1, a2, retain=True, activity_key=ACT,
                                             timestamp_key=TS, case_id_key=CID, resource_key=res)
    out_f = pm4py.filter_four_eyes_principle(log, a1, a2, retain=False, activity_key=ACT,
                                             timestamp_key=TS, case_id_key=CID, resource_key=res)
    ref = pandas_same_person(log, a1, a2, res)
    cand = [set(out_t[CID]), set(out_f[CID])]
    return max(cand, key=lambda s: len(s & ref) - len(s - ref))

rows = []
for a1, a2 in PAIRS:
    v_log   = pm4py_violations(dfc, a1, a2, "res_log")
    v_human = pm4py_violations(dfc, a1, a2, "res_human")
    clean = dfc[~dfc[CID].isin(dfc.loc[dfc["mapping_suspect"], CID])]
    v_clean = pm4py_violations(clean, a1, a2, "res_human")
    rows.append({"pair": f"{a1} + {a2}", "as_logged": len(v_log),
                 "entered_by": len(v_human), "entered_by_no_legacy_mapping": len(v_clean),
                 "robust": sorted(v_log & v_human & v_clean)})
sod = pd.DataFrame(rows)
# "robust" violations (present under every attribution) feed review clusters M1/H1/H2.

# Stratify the robust violations
case_attr = dfc.groupby(CID).agg(emergency=("emergency_flag", "max"),
                                 amount_band=("amount_band", "first"),
                                 vendor=("vendor_id", "first"),
                                 manual=("source_system", lambda s: (s == "manual_upload").any()),
                                 legacy=("source_system", lambda s: (s == "legacy_erp").any()))
case_attr["is_V77x"] = case_attr["vendor"].astype(str).str.startswith("V-77")  # adapt to real vendor coding
```

### 4.2 Handover, working-together, subcontracting and generic network analysis

```python
def sna_to_df(sna):
    return pd.DataFrame([(a, b, v) for (a, b), v in sna.connections.items()],
                        columns=["src", "tgt", "value"])

def networks(log, res="res_human"):
    how = pm4py.discover_handover_of_work_network(log, beta=0, resource_key=res,
                                                  timestamp_key=TS, case_id_key=CID)
    wt  = pm4py.discover_working_together_network(log, resource_key=res,
                                                  timestamp_key=TS, case_id_key=CID)
    sub = pm4py.discover_subcontracting_network(log, n=2, resource_key=res,
                                                timestamp_key=TS, case_id_key=CID)
    return sna_to_df(how), sna_to_df(wt), sna_to_df(sub)

how, wt, sub = networks(dfc)
pm4py.save_vis_sna(pm4py.discover_handover_of_work_network(dfc, resource_key="res_human"),
                   "handover_human.html")

# Frequency is not suspicion: compare observed handovers with a workload-based expectation.
out_deg = how.groupby("src")["value"].sum()
in_deg  = how.groupby("tgt")["value"].sum()
total   = how["value"].sum()
how["expected"] = how.apply(lambda r: out_deg[r.src] * in_deg[r.tgt] / total, axis=1)
how["lift"] = how["value"] / how["expected"]

# Stratified networks: emergency vs non-emergency, manual vs system, V-77x vs rest
for name, ids in {
    "emergency":     case_attr.index[case_attr.emergency],
    "non_emergency": case_attr.index[~case_attr.emergency],
    "manual":        case_attr.index[case_attr.manual],
    "V77x":          case_attr.index[case_attr.is_V77x],
}.items():
    h, w, s = networks(dfc[dfc[CID].isin(ids)])
    h.to_csv(f"handover_{name}.csv", index=False); s.to_csv(f"subcontract_{name}.csv", index=False)

# Cross-case links via the vendor object (reveals vendor-level bank changes copied into cases
# and bank change -> payment approval sequences spanning cases of the same vendor).
vendor_net = pm4py.discover_network_analysis(
    dfc, out_column="vendor_id", in_column="vendor_id",
    node_column_source="res_human", node_column_target="res_human",
    edge_column=ACT, edge_reference="_out", performance=True,
    sorting_column=TS, timestamp_column=TS)

# Convergence check: is the same bank-change event duplicated across cases?
bc = dfc[dfc[ACT].eq("Change Vendor Bank Details")]
dup = bc.groupby(["vendor_id", TS, "res_log"])[CID].nunique().rename("n_cases").reset_index()
dup_share = (dup["n_cases"] > 1).mean()

# Change-pay-change loops: fetch before/after values from the source system (not in the log).
loops = []
for cid, g in dfc[dfc[CID].isin(case_attr.index[case_attr.is_V77x])].sort_values(TS).groupby(CID):
    seq = g[ACT].tolist()
    for i in range(len(seq) - 2):
        if seq[i] == "Change Vendor Bank Details" and seq[i+1] == "Payment Approval" \
           and seq[i+2] == "Change Vendor Bank Details":
            loops.append(cid)
```


**Interpretation rules.**
- A pattern counts as a **robust control exception** only if it persists under every resource attribution and after excluding the artefact sources.
- It is **elevated** only if it also stands out against matched peers: same category, amount band and emergency status.
- Network lift is a way to **select cases for review**. It is never evidence of intent.

# 5. Evidence that would materially change the assessment

### Evidence that would increase concern

- **Bank data.**
  - Source-system change documents show the V-77x IBAN changed to an account that is not in the migration file.
  - The new account is in a different country or bank than the vendor's legal entity.
  - The new account matches an employee's bank account (employee master or payroll match) or is shared by several unrelated vendors.
  - The account was **reverted** after a payment was released (the 11 loops).
- **Missing verification.** No independent call-back record, or a call-back to a phone number that itself changed recently. No V-77x migration ticket covering the vendor IDs or dates involved.
- **Access logs.**
  - The same user ID or session performed both the bank change and the payment approval in the *source system*, not just in manual_upload rows.
  - Sessions from the same workstation or IP for different named users.
  - A buyer's session using the shared "Approver_Gita" account.
- **Payments.**
  - Invoices created or matched *after* the bank change and approved within minutes, with no prior payment block.
  - Amounts clustered just below approval thresholds, the same invoice number paid in several regions, or payments ahead of due date.
- **Emergency channels.**
  - Fast or self-approved POs **without** an emergency flag or clinical/incident ticket.
  - Emergency flags set *after* approval.
  - Recurring vendors or contractors in emergency cases, rising over time.
  - Prices above framework rates.
- **Justifications.**
  - The original quarter-close spreadsheet names the override maker as the justifier.
  - The file was created after an audit request.
  - Justification text is generic or duplicated across cases.
  - Justifications are missing entirely for overrides.
- **Overlaps.** Any overlap between the Create/Approve violations, the V-77x cluster and the Bot_Match exception cases. For example, a match exception, a bank change and a fast approval all in one case.

### Evidence that would reduce concern

- **Migration explains V-77x.**
  - The migration ticket lists all affected V-77x vendors.
  - Bank changes fall inside the migration window and match vendor-signed confirmation letters or the new platform's file.
  - One change event per vendor, duplicated across cases by log flattening (same vendor_id, timestamp and resource in several cases).
- **Pre-existing blocks.** Payment blocks for missing or invalid bank data existed before the change, so fast approval was the release of already-due payments.
- **Attribution artefacts.** manual_upload file metadata shows the uploader is not the approver, and the source-system change log shows different users for the change and the approval.
- **Routing by design.** AP_Kim's routing rule for higher-risk suppliers covers all V-77x payments, not only those with bank changes.
- **Legacy mapping.** Correcting the legacy_erp Bot_PO/human mapping, and using entered_by and approved_by, removes most of the 42 Create/Approve violations.
- **Shared account.** Access logs show assistants with separate sessions, none belonging to the PO creator.
- **Delegation and rosters.** Written delegation of authority for Gita's urgent approvals, and an on-call roster naming Hugo for weekend repairs.
- **Emergency documentation.**
  - Clinical or facilities incident tickets timestamped before the override.
  - Framework contract_type with contract rates.
- **Justification sign-off.** The quarter-close spreadsheet (and email trail) shows a different justifier or a second-person countersignature within 3 working days. Late justifications cluster around holidays and are substantive.

# 6. Cautious audit-report wording

During the review of the procure-to-pay event log, process analytics identified control exceptions concentrated in a small number of resource pairs and case clusters. These are control exceptions, not findings of misconduct; nothing reviewed to date establishes fraud or collusion by any individual.

The most concerning subgroup comprises 44 cases in which vendor bank details were changed shortly before payment approval (median 19 minutes, versus 7.8 hours overall). These cases are concentrated on vendor family V-77x (72%), are mostly high-value (68%), were largely entered by manual upload (83%), and include nine related cases where the log attributes both steps to the same user. A documented banking-platform migration for V-77x may explain much of this, but the link between maintenance tickets and procurement cases is missing, so that explanation is not yet verified.

Emergency channels for medical supplies and weekend facilities repairs show fast approvals and many of the 42 cases in which one user both created and approved a purchase order. This is broadly consistent with designed rush procedures; however, retrospective justifications were late in 18–21% of these cases, and 17 justifications were recorded by the person who performed the override.

Conclusions are constrained by data quality: a shared approver account, a legacy ERP user-mapping error and a batch spreadsheet upload distort resource attribution and timestamps, so some exceptions may be artefacts.

We recommend: (1) priority verification of the V-77x bank changes against bank confirmations, independent call-back records and migration tickets; (2) recomputing segregation-of-duties exceptions after correcting user mappings; (3) sample testing of emergency justifications for timeliness and independence; and (4) retiring shared accounts. This assessment will be updated once these steps are complete.
