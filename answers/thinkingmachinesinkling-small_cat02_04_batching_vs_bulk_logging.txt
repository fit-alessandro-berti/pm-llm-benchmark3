# 3. Consequences for performance analysis

*General principle:* If a temporal cluster is interpreted as physical concurrency when it is actually coarsening/submission, service time is overstated for concurrent models or understated for serial models; if interpreted as serial when it is a batch, waiting time is overstated because queue-arrival-to-start seems long for later items but they are actually handled with the first.

**G1 (fixture batch)**  
- *Waiting time:* If batch, each case waits from `queue_arrival` to 09:00 (6, 5, 4, 2 min). If forced serial, later cases would wait longer (up to ~12 min at 3-min service).  
- *Service time:* 3 min for the batch (fixture duration) vs 12 min total if serial. Using 3 min per case overestimates resource load; using 12 min total underestimates throughput (4 cases in 3 min).  
- *Utilization:* Batch  high utilization for 3 min; serial  100% for 12 min. Bottleneck is fixture count, not worker speed.  
- *Conformance:* Batch model fits; serial model creates artificial “wait” for L04 that is physically false.

**G2 (start batch)**  
- *Waiting:* All wait until 10:00; actual inspection durations vary (8–27 min). If treated as concurrent, resource usage >100% impossible for one T-B. Must split into group-start event + sequential service.  
- *Service:* Divergent ends imply individual durations; if averaged as 10:00–10:27 for all, service is overestimated for early finishers and underestimated for late.  
- *Bottleneck:* Inspection step; but group-start button hides whether setup is shared.

**G3 (end batch / submission)**  
- *Waiting:* Calculated as start – `queue_arrival`; true work likely started earlier than 11:02, but form submission is 11:30. If submission = completion, waiting for E01 is 50 min (10:4011:30) vs possibly ~20 min if finished at ~11:00.  
- *Service:* If 11:30 is true end, durations are 28, 20, 13, 6 min. If submission is delayed, true service is shorter and more uniform; using 11:30 overestimates service and understates throughput.  
- *Conformance:* Event log treats “complete” as process end; if it is form submission, process may have finished earlier.

**G4 (sequential pipeline)**  
- *Bias minimal if adjacency is correct.* If misread as batch, service could be aggregated incorrectly. Waiting for P05 = 12:0112:21 start = 20 min, but pipeline cycle means it waits for 4 prior cycles. Correct pipeline analysis uses cycle time (4 min) not absolute wait.

    # Overlap rate per resource (within cluster/resource pair)
    times = g[["start_dt","complete_dt"]].dropna()
    pairs = overlaps = 0
    if len(times) > 1:
        for i in range(len(times)):
            for j in range(i+1, len(times)):
                pairs += 1
                s1, e1 = times.iloc[i]["start_dt"], times.iloc[i]["complete_dt"]
                s2, e2 = times.iloc[j]["start_dt"], times.iloc[j]["complete_dt"]

# 6. Data-collection redesign

*Prioritized, by impact on queue/service/conformance validity.*

1. **Execution timestamps (start / complete)** — Require source-system event hooks (not form-submission time) to capture true work intervals. For G6, separate “work done” from “bulk form submission.”

8. **Timestamp precision metadata** — Store not only `precision` but also `uncertainty_lower` / `uncertainty_upper` or use interval-censored fields. For G7 (15 min), report [start_prec, end_prec].
