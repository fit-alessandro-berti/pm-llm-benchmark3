# 1. Model scope and state variables

## Boundary and purpose

The digital twin is a **discrete-event, case-level, resource-constrained simulation** of the municipal building-permit process from **application submission** to **issue permit / reject application**. Its purpose is not replay-only, but **counterfactual comparison of interventions** under:

- non-stationary demand,
- resource calendars and skill constraints,
- rework and appeals,
- applicant and third-party delays,
- cross-case dependencies,
- policy changes.

The twin should support questions such as:

- Which interventions reduce median and p90 cycle time?
- Which interventions improve SLA compliance without creating new bottlenecks?
- What are the trade-offs between throughput, fairness, cost, risk, and robustness?
- How do policies behave under peak demand, objection waves, or resource shortages?

## In scope

The model includes:

- municipal permit activities from submission to final decision;
- applicant document submission and missing-document response;
- public-notice periods, including latent objection effects;
- inspection scheduling, travel, batching, no-shows, and rework;
- resource pools with calendars, skills, and partial availability;
- queues before activities;
- case attributes: case type, district, architect, application value, fire/environment/public-notice flags;
- cross-case dependencies:
  - same architect submitting related applications;
  - district-level objection effects;
  - geographic inspection batching;
- policy levers D1–D10;
- non-stationary arrivals by month, weekday, hour, and architect burst behavior.

## Out of scope or represented only indirectly

The following are excluded or simplified:

- construction-phase activities after permit issuance;
- detailed legal appeals outside the modeled administrative rework loop;
- full GIS routing for inspectors, replaced by district-level travel times;
- detailed political decision-making, represented through calendar constraints;
- complete objection workflow, because objection events are missing; objections are modeled as latent processes inferred from public-notice duration;
- rare emergency decisions removed from the log, represented only as an uncertainty/scenario factor if needed.

## Resource model

| Resource pool | Capacity / calendar constraints |
|---|---|
| Clerks | 5 FTE, Mon–Fri 08:00–16:00; one clerk dedicated to portal support on Mondays. |
| Planners | 8 FTE, Mon–Fri 09:00–17:00; two planners only handle Simple renovation. |
| Fire reviewers | 2 FTE equivalent, Tuesday–Thursday only. |
| Environmental reviewers | 3 FTE, Mon–Fri, 40% reserved for non-permit duties. |
| Inspectors | 4 FTE, field visits Tue–Fri; travel time depends on district; batching possible. |
| Legal officers | 2 FTE; unavailable during council meeting weeks except urgent cases. |
| System | Effectively unlimited capacity. |
| Applicant / third parties | External response processes modeled separately from municipal service times. |

## Queueing and calendar logic

The simulation should distinguish:

1. **Municipal queue waiting**: case waits for an available qualified resource.
2. **Calendar waiting**: case waits because the resource pool is not available.
3. **Applicant/third-party waiting**: case waits for documents, inspection access, consultant reports, or objection-related events.
4. **Process synchronization waiting**: decision drafting waits for all required predecessor branches.
5. **Batch waiting**: inspection cases wait until a district batch is large enough or a departure time is reached.

This separation is essential because the event log often only contains completion timestamps. Collapsing all waiting into one “service time” would misrepresent policy effects.

## Cross-case dependencies

The model must not assume fully independent cases. Dependencies include:

### Architect-level dependence

Large architects submit bursts of related applications. The model should include:

- architect-specific arrival burst processes;
- potential bundling of related applications;
- correlated document quality;
- correlated inspection readiness.

### District-level objection dependence

Neighborhood objections are not fully observed. The model should treat objections as latent events that can affect multiple cases in the same district or notice window. Public-notice duration is used as a proxy, not as direct evidence of objection events.

### Inspection batching dependence

Inspectors can group site visits geographically. Batching can reduce travel time but can increase waiting for the first case in the batch. The state should therefore include:

- inspection batch formation rule;
- minimum batch size;
- maximum batching delay;
- district travel-time matrix;
- inspector route capacity.

### Resource contention dependence

Cases share resource pools. Peak demand, council weeks, holidays, and part-time calendars create dependencies across otherwise unrelated cases.

# 2. Parameter-estimation plan

## PM4Py-based log and model handling

PM4Py should be used for event-log preparation, process-model handling, discovery, filtering, and replay-based diagnostics. The simulation engine itself should remain separate from PM4Py so that PM4Py is used for **data and model grounding**, while the simulation engine handles stochastic execution, calendars, resources, and dependencies.

Recommended PM4Py usage:

1. Load the event log with pandas, not with a nonexistent `pm4py.read_csv`.
2. Format the dataframe using:

   ```python
   pm4py.format_dataframe(
       df,
       case_id="case:concept:name",
       activity_key="concept:name",
       timestamp_key="time:timestamp"
   )
   ```

3. Parse or load the provided process tree. If the simplified string cannot be parsed by the installed PM4Py version, encode the same routing logic manually in the simulation configuration.
4. Use PM4Py to compute:
   - case variants;
   - directly-follows graphs;
   - performance DFGs;
   - start and end activities;
   - case durations;
   - filtered logs by case type, district, month, or variant.
5. Use PM4Py replay or conformance checking, where possible, to validate whether simulated traces remain plausible relative to the observed process model.

## Arrival-process estimation

### Case arrivals

Use the first event of each case, usually `Submit application`, to estimate arrivals.

Estimate:

- daily arrival counts;
- weekly arrival counts;
- monthly seasonality;
- weekday effects;
- hour-of-day effects;
- architect-specific burst behavior;
- case-type mix over time.

Given the summary:

- March–May and September–November have approximately 1.7× the arrival rate of January–February.
- Monday submissions are approximately 2.2× Wednesday submissions.
- Top 20 architects submit 31% of cases and often submit multiple related applications in the same week.

A suitable arrival model is a **non-homogeneous Poisson process** or **Cox process** with multiplicative intensity:

\[
\lambda(t) = \lambda_0 \cdot s_{\text{month}}(t) \cdot s_{\text{weekday}}(t) \cdot s_{\text{hour}}(t) \cdot s_{\text{architect}}(t)
\]

For large architects, a simple Poisson process may underrepresent bursts. Consider:

- Poisson cluster process;
- negative binomial weekly architect arrivals;
- Hawkes process with self-excitation for top architects.

### Case mix

Estimate conditional case-type probabilities:

- overall mix: Simple 45%, New residential 28%, Commercial 17%, Complex variance 10%;
- mix by month;
- mix by architect;
- mix by district.

If the mix changes seasonally, model it as time-dependent.

## Service-time and waiting-time estimation

The log contains a known limitation: many human activities have only completion timestamps. Therefore, service time and waiting time cannot always be directly observed.

### When start and completion timestamps exist

If both are available:

\[
\text{service time} = \text{completion timestamp} - \text{start timestamp}
\]

\[
\text{waiting time} = \text{start timestamp} - \text{ready time}
\]

### When only completion timestamps exist

Use completion-to-completion sojourn times only as a proxy. Do not interpret them as pure service time.

For each activity, decompose duration into:

- municipal queue waiting;
- calendar waiting;
- active service;
- applicant/third-party waiting;
- synchronization waiting.

Use:

- resource calendars;
- observed completion hour distributions;
- activity duration summaries;
- expert judgment;
- Bayesian priors or scenario ranges where data are weak.

### Activity-specific estimation

| Activity | Estimation approach |
|---|---|
| Completeness check | Fit service distribution from observed durations where possible; model Monday queue spikes separately. |
| Request missing documents | Short municipal service time; model as administrative trigger. |
| Receive missing documents | Model applicant response time from request to receipt; heavy-tailed distribution. |
| Planning review | Fit active review time conditional on case type and district; queue depends on planner pool. |
| Fire-safety review | Fit service time for specialized pool; Tuesday–Thursday calendar. |
| Environmental review | Fit highly variable service time; include consultant-report delay and non-permit duty losses. |
| Public-notice period | Model as fixed minimum plus latent objection extension; not municipal service time. |
| Inspection scheduling | Short administrative task; batching queue before scheduling may matter. |
| Site inspection | Service time plus travel time by district; include no-show and reschedule probability. |
| Decision drafting | Service time plus synchronization waiting for required reviews. |
| Legal check | Service time plus council-week and holiday effects. |
| Issue permit / reject | Mostly automated or short administrative task. |

## Distribution choices

Use flexible, non-negative distributions:

- lognormal for many human tasks;
- gamma for service times with moderate skew;
- Weibull for heavy-tailed or duration-dependent processes;
- Pareto-like or mixture distributions for applicant response and objection-driven public-notice delays;
- empirical resampling where sample size is sufficient.

For heavy-tailed processes, estimate median, p90, p95, and p99, not only means.

## Branching probabilities

Routing probabilities should be estimated from the event log and case attributes.

### Missing documents

Estimate:

\[
P(\text{missing documents} \mid \text{case type, architect, district, value})
\]

Use logistic regression or gradient-boosted classification. The pre-submission checker intervention should modify this probability.

### Fire-safety review

Observed `requires_fire=yes` is one indicator, but the true rule includes a building-area threshold not fully available.

Use:

\[
P(\text{fire review} \mid \text{requires_fire}, \text{case type}, \text{application value}, \text{district})
\]

Treat the missing threshold as an uncertain parameter.

### Environmental review

Use:

\[
P(\text{environment review} \mid \text{requires_environment}, \text{district sensitivity}, \text{case type}, \text{value})
\]

Because environmental sensitivity data are incomplete, use district-level priors and sensitivity analysis.

### Public notice

Public notice is required for Complex variance and some New residential cases. Estimate:

\[
P(\text{public notice} \mid \text{case type}, \text{district}, \text{project attributes})
\]

Objection occurrence is latent. Estimate objection probability from unusually long public-notice durations.

### Legal check

The process tree allows legal check to be skipped. The variant summary shows a simple clean path without legal check. Estimate legal-check probability by case type and risk indicators.

### Rework probabilities

Estimate rework after:

- Planning review;
- Site inspection;
- Legal check;
- applicant appeal.

Use repeated activities, loop variants, and case outcomes. Model rework probability as conditional on:

- case type;
- district;
- architect history;
- missing-document history;
- inspection outcome;
- legal conflict indicators.

Because rework reasons are unstructured and unreliable, do not depend on coded reasons. Use them only as optional enrichment if text mining is available.

## Resource-calendar estimation

Use HR calendars as the primary source, but validate against event timestamps.

Estimate:

- shift start and end times;
- weekday availability;
- part-time patterns;
- holidays;
- council meeting weeks;
- non-permit duty loss;
- inspector travel time by district;
- inspector no-show and reschedule rates.

Where HR calendars and event timestamps conflict, treat the difference as uncertainty and test both assumptions.

## Dependency estimation

### Architect bursts

Estimate:

- number of submissions per architect-week;
- probability that a top architect submits multiple related cases;
- correlation of case types within architect bursts;
- probability that related cases share district.

Use this to drive architect appointment slots and inspection bundling.

### Inspection batching

Estimate from district and timestamps:

- how often inspections occur in the same district on the same day;
- travel-time differences by district;
- potential reduction in travel time when batching;
- additional waiting caused by batch formation.

Because the log is flattened, some dependencies may be invisible. Use scenario ranges.

### Objection shocks

Objection events are missing. Use public-notice duration as a proxy.

Fit a mixture model:

- no objection: public notice near fixed minimum;
- objection: extended public notice;
- severe objection: very long extension.

Allow objection risk to correlate across cases in the same district and time window.

## PM4Py artifacts to produce

The parameter-estimation pipeline should generate:

1. formatted event log;
2. parsed or fallback process-tree object;
3. variant frequencies and variant durations;
4. DFG frequency graph;
5. performance DFG;
6. start/end activity distributions;
7. case-type-specific duration distributions;
8. activity waiting and service summaries;
9. routing probability tables;
10. rework probability tables;
11. arrival intensity tables;
12. calendar and resource-capacity tables;
13. dependency parameter tables.

# 3. Assumptions

## Arrivals

1. Arrivals are driven by the submission event and are exogenous to the municipal process except where policy interventions explicitly change submission behavior.
2. Monthly seasonality and weekday effects observed in the 18-month log remain structurally similar in the simulation horizon.
3. Monday bursts are real and not solely an artifact of backlog recording.
4. Top architects generate correlated bursts; a mixture of base arrivals and architect-specific burst arrivals is more realistic than a homogeneous Poisson process.
5. Rare emergency cases removed from the log are negligible for baseline performance but may be included as a stress scenario.
6. Future demand is uncertain; therefore, demand multipliers are treated as scenario factors, not fixed constants.

## Service times

1. Where start timestamps are missing, active service time is partially inferred and therefore uncertain.
2. Completion-to-completion durations include waiting and should not be treated as pure service time.
3. Service-time distributions are non-negative and right-skewed.
4. Service times depend on case type, district, resource skill, and calendar interruptions.
5. System activities have negligible service time compared with human activities.
6. Municipal service time is separated from applicant/third-party response time.

## Routing

1. The provided process tree is a useful structural prior but not a perfect representation of all observed behavior.
2. `tau` branches represent optional activities, not observed events.
3. Fire-safety and environmental review requirements are partially latent because thresholds and sensitivity data are incomplete.
4. Public notice is required for all Complex variance cases and some New residential cases.
5. Decision drafting waits for all required predecessor branches.
6. Legal check may be skipped for some low-risk cases, consistent with the variant summary.
7. Rare variants are grouped into an “other” category and modeled through sampled exception paths.

## Resources and calendars

1. HR-reconstructed calendars are sufficiently accurate for capacity modeling but are validated against event timestamps.
2. Clerks, planners, fire reviewers, environmental reviewers, inspectors, and legal officers have distinct skill pools.
3. Two planners restricted to Simple renovation cannot freely absorb peaks in other case types.
4. Fire reviewers are available only Tuesday–Thursday.
5. Environmental reviewers lose 40% of capacity to non-permit duties.
6. Legal officers are largely unavailable during council meeting weeks except for urgent cases.
7. Inspectors have district-dependent travel times and can batch visits geographically.
8. Temporary inspectors require ramp-up time and are not immediately equivalent to permanent inspectors.

## Rework

1. Rework occurs after planning review, inspection, legal check, or appeal.
2. Rework probabilities are correlated with case complexity, missing documents, and inspection outcomes.
3. Rework reasons are not reliably coded, so the model uses probabilistic loops rather than reason-based deterministic rules.
4. Rework can cause a case to re-enter earlier queues and consume additional resource capacity.
5. Inspection rework may require both municipal reinspection and applicant remediation time.

## Applicant and third-party response

1. Missing-document response time is applicant-driven and heavy-tailed.
2. Applicant response time is not municipal service time.
3. Pre-submission document checking can reduce missing-document loops but may add effort before submission.
4. Inspection no-shows depend on applicant availability and can trigger rescheduling.
5. Consultant reports can delay environmental review.
6. Objections are not directly observed; public-notice duration is a proxy for objection impact.

## Cross-case dependencies

1. Related cases from the same architect and district can be bundled for inspection scheduling.
2. Batching reduces travel time but can increase waiting for early cases in the batch.
3. Neighborhood objections may affect multiple cases in the same district or notice window.
4. Resource contention creates indirect dependencies among all cases.
5. The flattened log underrepresents dependencies, so dependency parameters are tested through ranges and scenarios.

## Non-stationary demand

1. Demand varies by month, weekday, and architect behavior.
2. Peak months interact with resource calendars and can expose bottlenecks.
3. Policies should be evaluated under base and stressed demand conditions.
4. A stationary steady-state assumption is insufficient; the simulation must represent time-varying demand and seasonal effects.

## Missing data

1. Missing start timestamps prevent exact service/waiting decomposition.
2. Missing objection events require latent modeling.
3. Missing environmental sensitivity data require proxy variables and sensitivity analysis.
4. Missing building-area thresholds require probabilistic fire-review routing.
5. Rare emergency cases are absent and should not be treated as representative of normal work.
6. The log may underrepresent related-case dependencies because it is flattened by case.

The matrix below should be run under common random numbers where possible. Stress scenarios should be applied as overlays to the same policy configurations.

## Factorial overlay

Rather than treating each row as isolated, the experiment design should support a factorial or partially factorial overlay:

- demand scenario: base, S1, S4;
- objection/legal stress: base, S2;
- resource stress: base, S3;
- policy package: baseline, single intervention, combined intervention.

This allows estimation of:

- main effects;
- interaction effects;
- robustness across scenarios;
- policy regret under adverse conditions.

# 5. Warm-up, replications, and uncertainty treatment

## Warm-up

Because demand is non-stationary, a classic stationary warm-up is not sufficient. Use a **time-dependent burn-in** approach.

Recommended approach:

1. Initialize the simulation at a realistic date, for example January 1.
2. Initialize backlog and open cases either:
   - from a reconstructed log snapshot, or
   - from a burn-in run.
3. Run a burn-in period of at least 3 months, preferably 6 months, before measuring KPIs.
4. Monitor:
   - queue lengths by resource pool;
   - backlog by case type;
   - work-in-progress;
   - resource utilization;
   - aging-case counts.
5. Discard the burn-in period or use it only for state initialization.

If the simulation starts with an empty system, the early period will unrealistically underestimate waiting. If it starts with an empirically reconstructed backlog, warm-up can be shorter but still should include enough time to stabilize queue behavior.

## Run length

Recommended measurement horizon:

- 18 months for direct comparability with the observed log;
- 24–36 months if seasonal robustness is important;
- at least two full seasonal cycles if computational cost allows.

For policies with long-tail effects, such as complex variance and public notice, longer horizons are preferable because p90 and p95 cycle times may take many months to stabilize.

## Replications

Use independent stochastic replications with different random streams but common policy inputs.

Recommended:

- at least 30 replications for initial screening;
- 50–100 replications for final comparison of shortlisted policies;
- more replications if estimating extreme quantiles such as p95 or p99.

Use common random numbers across policies for:

- arrivals;
- applicant behavior;
- resource availability shocks;
- objection shocks;
- inspection no-shows.

This reduces variance in policy comparisons.

## Random seeds

Use a reproducible seed hierarchy:

```text
master_seed
 arrival_stream_seed
 service_time_seed
 applicant_response_seed
 objection_seed
 resource_absence_seed
 routing_seed
 replication_seed
```

For each replication:

- derive replication-specific seeds from the master seed;
- keep the same derived streams across policies where common random numbers are desired.

## Confidence intervals and credible intervals

For each KPI and policy:

- report point estimates;
- report 95% confidence intervals for means and proportions;
- report bootstrap confidence intervals for quantiles;
- report median, p90, p95, and p99 separately.

For heavy-tailed outputs, avoid relying only on means. Use:

- median;
- p90;
- p95;
- SLA compliance rates;
- backlog counts;
- expected cost or overtime.

If a Bayesian parameter model is used, report credible intervals for parameters and posterior predictive intervals for KPIs.

## Heavy-tailed durations

Several processes are heavy-tailed:

- missing-document response;
- public notice with objections;
- environmental review;
- complex variance durations;
- inspection rework.

Treatment:

1. Fit distributions with heavy tails, such as lognormal, Weibull, gamma mixtures, or Pareto-like mixtures.
2. Use empirical resampling where sample sizes are sufficient.
3. Use quantile-based validation rather than mean-only validation.
4. Use robust statistics.
5. Test sensitivity of decisions to tail assumptions.
6. Do not truncate extreme values without justification.

## Sensitivity analysis

Perform global sensitivity analysis on uncertain parameters, especially:

- missing-document reduction from D1;
- inspection no-show probability;
- travel-time reduction from batching;
- objection probability;
- public-notice extension distribution;
- fire-review threshold;
- environmental sensitivity;
- legal council-week availability;
- temporary inspector productivity;
- applicant response slowdown.

Recommended methods:

- Morris screening for many parameters;
- Sobol indices for important parameters;
- scenario analysis for structural uncertainties;
- tornado charts for communication.

## Uncertainty categories

Distinguish:

1. **Aleatory uncertainty**: inherent randomness in arrivals, service, applicant response.
2. **Parameter uncertainty**: limited data for probabilities and distributions.
3. **Structural uncertainty**: simplified process tree, missing dependencies, missing objection events.
4. **Scenario uncertainty**: future demand, policy adoption, resource availability.

The digital twin should not present a single deterministic answer. It should present policy performance distributions and robustness across scenarios.

# 6. Validation strategy

## Face validation

Present the model logic to process owners, clerks, planners, inspectors, legal officers, and permit managers.

Check:

- whether the nominal flow is recognizable;
- whether rework loops are plausible;
- whether calendars and skill restrictions are correct;
- whether batching and objection assumptions are credible;
- whether bottleneck locations match operational experience;
- whether intervention mechanisms are represented realistically.

Face validation is especially important where the log is incomplete, such as objections and rework reasons.

## Event-log replay validation

Use PM4Py replay techniques to compare simulated behavior against observed event logs.

Steps:

1. Feed historical arrivals and case attributes into the simulation.
2. Generate simulated traces.
3. Compare simulated traces with observed traces using:
   - variant frequencies;
   - activity sequence fitness;
   - token-based replay diagnostics where applicable;
   - directly-follows graph similarity.
4. Check whether the simulation reproduces:
   - common variants;
   - missing-document loops;
   - inspection rework loops;
   - legal-check occurrence rates;
   - issue/reject rates.

Replay validation should not require exact timestamp matching. The goal is behavioral fidelity.

## Distributional validation

Compare simulated and observed distributions for:

- case cycle time by case type;
- activity sojourn times;
- waiting times where inferable;
- applicant response times;
- public-notice durations;
- inspection scheduling delays;
- rework counts;
- number of missing-document requests per case.

Use:

- QQ plots;
- empirical CDF plots;
- Kolmogorov–Smirnov or Cramér–von Mises tests, interpreted cautiously;
- quantile error metrics;
- CRPS where appropriate.

Pay special attention to p90 and p95, not only median.

## Resource-utilization validation

Compare simulated resource behavior against observed activity completions and calendar assumptions.

Validate:

- activity counts per resource pool by weekday;
- completion hour distributions;
- Monday clerk load;
- Tuesday–Thursday fire-review activity;
- inspector field-day utilization;
- legal activity reductions during council weeks;
- environmental review throughput given 40% non-permit duty.

Since start timestamps are often missing, utilization cannot be validated perfectly. Use completion patterns and capacity plausibility.

## Bottleneck validation

The model should reproduce known or suspected bottlenecks:

- completeness-check queue after Monday submissions;
- planning-review queue for complex cases;
- fire-review scarcity due to Tue–Thu availability;
- environmental-review variability;
- inspection backlog in peak months;
- travel burden in districts D3 and D5;
- legal delays around council meeting weeks;
- public-notice delays when objections are likely.

Compare simulated bottleneck rankings with empirical waiting summaries and stakeholder knowledge.

## Out-of-sample validation

Use temporal holdout:

- calibrate on the first 12–15 months;
- validate on the final 3–6 months.

Alternatively:

- calibrate on most districts;
- validate on one district;
- calibrate on most architects;
- validate on top architects.

Evaluate whether the model predicts:

- case durations;
- variant shares;
- SLA compliance;
- queue buildup during peak months;
- inspection delays;
- public-notice extensions.

## Intervention sanity checks

Before trusting policy results, test known directional effects:

- reducing missing documents should reduce completeness loops;
- adding peak inspector should reduce inspection waiting, unless blocked by scheduling or applicant availability;
- batching should reduce travel but may increase early-case waiting;
- legal council-week unavailability should increase legal tail;
- Monday smoothing should reduce clerk queue spikes.

If the model violates these sanity checks, revisit structure or parameters.

# 7. Decision criteria

## Primary decision metrics

| Metric | Definition | Why it matters |
|---|---|---|
| Median cycle time | 50th percentile from submission to final decision. | Typical applicant experience. |
| p90 cycle time | 90th percentile from submission to final decision. | Tail experience and political risk. |
| p95 / p99 cycle time | Extreme tail. | Important for complex cases and complaint risk. |
| SLA compliance | Share of cases completed within target duration by case type. | Operational accountability. |
| Backlog | Open cases by stage and age. | Capacity pressure and staffing need. |
| Rework rate | Share of cases with one or more rework loops. | Quality and waste. |
| Resource utilization | Active utilization by pool and calendar-adjusted capacity. | Feasibility and overtime risk. |
| Fairness | Variation in duration across districts, architects, and case types. | Equity and perceived fairness. |
| Robustness | Performance stability across demand and stress scenarios. | Policy resilience. |
| Cost / staffing impact | Temporary staff, overtime, tooling, triage effort. | Budget feasibility. |
| Risk exposure | False-negative inspections, under-reviewed environmental cases, objection escalation. | Regulatory and public risk. |

## Illustrative SLA targets

These should be calibrated with the municipality, but reasonable starting targets are:

| Case type | Median target | p90 target |
|---|---:|---:|
| Simple renovation | 15 calendar days | 30 calendar days |
| New residential | 35 calendar days | 70 calendar days |
| Commercial | 50 calendar days | 100 calendar days |
| Complex variance | 90 calendar days | 200 calendar days |

The simulation should report SLA compliance by case type and overall.

## Selection thresholds

A policy should be considered attractive if, relative to baseline:

1. It improves median cycle time by at least 5–10% for affected case types, or improves p90 cycle time by at least 10–15%.
2. It improves SLA compliance by at least 3–5 percentage points for at least one important case type without worsening another case type by more than 2 percentage points.
3. It does not increase p90 duration for any major case type by more than 5% unless compensated by large gains elsewhere and approved by decision-makers.
4. It keeps sustained resource utilization below a risk threshold, for example 85–90% of calendar-adjusted capacity, unless overtime is explicitly budgeted.
5. It does not worsen district fairness materially. For example, the ratio of p90 duration between the worst and best district should not increase by more than 5–10% without justification.
6. It does not increase rework or post-permit risk beyond an acceptable level.
7. It remains beneficial under at least two stress scenarios.
8. Its operational cost is proportionate to the expected benefit.

## Fairness criteria

Evaluate:

- median and p90 duration by district;
- median and p90 duration by architect size class;
- inspection waiting by district;
- batching delay distribution;
- access effects from appointment slots;
- no-inspection policy eligibility across districts and applicant types.

A policy that improves average duration but systematically disadvantages a district or small applicants may be rejected or modified.

## Robustness criteria

A robust intervention should:

- perform well under base demand and peak demand;
- not collapse under objection waves or resource shortages;
- not create severe new bottlenecks;
- have acceptable performance under parameter uncertainty;
- be reversible or adjustable if monitored performance deviates.

## Multi-criteria decision process

Do not select based on one metric. Use a weighted scorecard or Pareto analysis across:

- cycle time;
- SLA compliance;
- fairness;
- cost;
- risk;
- robustness;
- implementation complexity.

The simulation supports decision-making but does not claim exact optimality, especially before calibration and validation.

def load_event_log_from_csv(csv_text: str = EVENT_LOG_CSV) -> pd.DataFrame:
    """
    Load the event log with pandas.

    Do not use pm4py.read_csv; that function is not part of the
    conventional PM4Py API for CSV event logs.
    """
    df = pd.read_csv(io.StringIO(csv_text), sep=",")
    df[TIMESTAMP_KEY] = pd.to_datetime(df[TIMESTAMP_KEY])
    return df


def format_for_pm4py(df: pd.DataFrame) -> pd.DataFrame:
    """
    Format the dataframe using PM4Py column conventions.

    import pm4py

    return pm4py.format_dataframe(

        activity_key=ACTIVITY_KEY,

def parse_process_tree(tree_string: str = PROCESS_TREE_STRING) -> Any:
    """
    Parse the simplified process-tree string.

    PM4Py versions differ in the exact entry point for process-tree parsing.
    This helper tries common PM4Py locations and falls back to a structured
    placeholder if parsing fails.

    Limitations of the simplified string:
    - It is a simplified representation, not a full BPMN or Petri net model.
    - tau branches represent optional behavior.
    - Rework labels such as 'Completeness rework' may not correspond directly
      to observed activity names.
    - Parallel join semantics are simplified; in the simulation, decision
      drafting should wait for all required predecessor branches.
    """
    errors: List[str] = []

    try:
        import pm4py

        if hasattr(pm4py, "parse_process_tree"):
            return pm4py.parse_process_tree(tree_string)
    except Exception as exc:
        errors.append(f"pm4py.parse_process_tree failed: {exc}")

    try:
        from pm4py.objects.process_tree.utils import parse as parse_pt

        return parse_pt(tree_string)
    except Exception as exc:
        errors.append(f"pm4py.objects.process_tree.utils.parse failed: {exc}")

    try:
        from pm4py.objects.process_tree.parser import parse as parse_pt2

        return parse_pt2(tree_string)
    except Exception as exc:
        errors.append(f"pm4py.objects.process_tree.parser.parse failed: {exc}")

    warnings.warn(
        "Could not parse the process tree with known PM4Py entry points. "
        "Using a fallback placeholder. The simulation should encode the "
        "routing rules manually."
    )
    return {
        "parsed": False,
        "raw_string": tree_string,
        "errors": errors,
    }


def compute_variants(log: pd.DataFrame) -> Dict[Tuple[str, ...], int]:
    """
    Compute case variants.

    Uses PM4Py when available; otherwise falls back to pandas.
    """
    try:
        import pm4py

        return pm4py.get_variants(log)
    except Exception as exc:
        warnings.warn(f"PM4Py variant computation failed: {exc}. Using pandas fallback.")

        sorted_log = log.sort_values([CASE_ID_KEY, TIMESTAMP_KEY])
        variant_series = sorted_log.groupby(CASE_ID_KEY)[ACTIVITY_KEY].apply(tuple)
        return variant_series.value_counts().to_dict()


def compute_dfg(
    log: pd.DataFrame,
) -> Tuple[Dict[Tuple[str, str], int], Dict[str, int], Dict[str, int]]:
    """
    Compute a directly-follows graph.

    Uses PM4Py when available; otherwise falls back to pandas.
    """
    try:
        import pm4py

        dfg, start_activities, end_activities = pm4py.discover_dfg(log)
        return dfg, start_activities, end_activities
    except Exception as exc:
        warnings.warn(f"PM4Py DFG computation failed: {exc}. Using pandas fallback.")

        sorted_log = log.sort_values([CASE_ID_KEY, TIMESTAMP_KEY])
        dfg: Dict[Tuple[str, str], int] = {}

        for _, group in sorted_log.groupby(CASE_ID_KEY):
            activities = group[ACTIVITY_KEY].tolist()
            for current_activity, next_activity in zip(activities, activities[1:]):
                key = (current_activity, next_activity)
                dfg[key] = dfg.get(key, 0) + 1

        first_events = sorted_log.groupby(CASE_ID_KEY).first()
        last_events = sorted_log.groupby(CASE_ID_KEY).last()

        start_activities = first_events[ACTIVITY_KEY].value_counts().to_dict()
        end_activities = last_events[ACTIVITY_KEY].value_counts().to_dict()

        return dfg, start_activities, end_activities


def compute_performance_dfg(log: pd.DataFrame) -> Any:
    """
    Compute a performance DFG.

    If PM4Py is available, use its performance DFG discovery.

    If not, compute a fallback mean elapsed time between directly following
    events. This fallback is a sojourn proxy and should not be interpreted
    as pure service time because waiting may be included.
    """
    try:
        import pm4py

        return pm4py.discover_performance_dfg(log, variant="performance")
    except Exception as exc:
        warnings.warn(
            f"PM4Py performance DFG failed: {exc}. "
            "Using elapsed-time fallback. This is not pure service time."
        )

        sorted_log = log.sort_values([CASE_ID_KEY, TIMESTAMP_KEY])
        performance_values: Dict[Tuple[str, str], List[float]] = {}

        for _, group in sorted_log.groupby(CASE_ID_KEY):
            activities = group[ACTIVITY_KEY].tolist()
            timestamps = group[TIMESTAMP_KEY].tolist()

            for i in range(len(activities) - 1):
                key = (activities[i], activities[i + 1])
                delta_hours = (
                    timestamps[i + 1] - timestamps[i]
                ).total_seconds() / 3600.0
                performance_values.setdefault(key, []).append(delta_hours)

        return {
            key: float(np.mean(values))
            for key, values in performance_values.items()
            if values
        }


def compute_arrival_stats(log: pd.DataFrame) -> Dict[str, Any]:
    """
    Compute case arrival statistics from first events.
    """
    first_events = (
        log.groupby(CASE_ID_KEY)[TIMESTAMP_KEY]
        .min()
        .sort_values()
        .to_frame(name="start_time")
    )

    first_events["month"] = first_events["start_time"].dt.to_period("M")
    first_events["weekday"] = first_events["start_time"].dt.day_name()

    interarrival_days = (
        first_events["start_time"].diff().dropna().dt.total_seconds() / 86400.0
    )

    avg_interarrival_days = (
        float(interarrival_days.mean()) if len(interarrival_days) > 0 else np.nan
    )

    cases_per_day = (
        float(1.0 / avg_interarrival_days)
        if avg_interarrival_days and avg_interarrival_days > 0
        else np.nan
    )

    return {
        "case_count": int(first_events.shape[0]),
        "avg_interarrival_days": avg_interarrival_days,
        "cases_per_day": cases_per_day,
        "monthly_arrivals": first_events["month"].value_counts().sort_index().to_dict(),
        "weekday_arrivals": first_events["weekday"].value_counts().to_dict(),
    }


def add_service_waiting_columns(log: pd.DataFrame) -> pd.DataFrame:
    """
    Add timing columns.

    Important limitation:
    If only completion timestamps are available, service and waiting cannot be
    separated exactly. This function therefore creates:
    - sojourn_since_prev_days: elapsed time since previous event;
    - service_days and waiting_before_activity_days only if a start_timestamp
      column exists.

    The sojourn column is not pure service time.
    """
    enriched = log.sort_values([CASE_ID_KEY, TIMESTAMP_KEY]).copy()

    enriched["prev_timestamp"] = enriched.groupby(CASE_ID_KEY)[TIMESTAMP_KEY].shift(1)
    enriched["prev_activity"] = enriched.groupby(CASE_ID_KEY)[ACTIVITY_KEY].shift(1)

    enriched["sojourn_since_prev_days"] = (
        enriched[TIMESTAMP_KEY] - enriched["prev_timestamp"]
    ).dt.total_seconds() / 86400.0

    if "start_timestamp" in enriched.columns:
        enriched["start_timestamp"] = pd.to_datetime(enriched["start_timestamp"])
        enriched["waiting_before_activity_days"] = (
            enriched["start_timestamp"] - enriched["prev_timestamp"]
        ).dt.total_seconds() / 86400.0
        enriched["service_days"] = (
            enriched[TIMESTAMP_KEY] - enriched["start_timestamp"]
        ).dt.total_seconds() / 86400.0
    else:
        enriched["waiting_before_activity_days"] = np.nan
        enriched["service_days"] = np.nan

    # Applicant response time for missing documents.
    # This is a simplified first-request-to-first-receipt approximation.
    requests = (
        enriched.loc[enriched[ACTIVITY_KEY] == "Request missing documents"]
        .groupby(CASE_ID_KEY)[TIMESTAMP_KEY]
        .min()
        .rename("first_request_ts")
    )

    receives = (
        enriched.loc[enriched[ACTIVITY_KEY] == "Receive missing documents"]
        .groupby(CASE_ID_KEY)[TIMESTAMP_KEY]
        .min()
        .rename("first_receive_ts")
    )

    response = requests.to_frame().join(receives, how="inner")
    response["applicant_response_days"] = (
        response["first_receive_ts"] - response["first_request_ts"]
    ).dt.total_seconds() / 86400.0

    enriched = enriched.merge(
        response[["applicant_response_days"]],
        left_on=CASE_ID_KEY,
        right_index=True,
        how="left",
    )

    return enriched

class ExperimentRunner:
    """
    Runs simulation experiments over policy and scenario combinations.
    """

    def __init__(self, engine_factory: Any):
        self.engine_factory = engine_factory

    def run_experiment(
        self,
        experiment_name: str,
        policy: PolicyConfig,
        demand_scenario: DemandScenario,
        replications: int = 30,
        master_seed: int = 42,
    ) -> Dict[str, Any]:
        results = []

        for replication in range(replications):
            seed = master_seed + replication
            engine = self.engine_factory(policy, demand_scenario)
            result = engine.run(
                start_date=pd.Timestamp("2026-01-01"),
                end_date=pd.Timestamp("2027-06-30"),
                seed=seed,
            )
            results.append(
                {
                    "experiment": experiment_name,
                    "replication": replication,
                    "seed": seed,
                    "result": result,
                }
            )

        return {
            "experiment": experiment_name,
            "policy": policy,
            "demand_scenario": demand_scenario,
            "replications": replications,
            "results": results,
        }
