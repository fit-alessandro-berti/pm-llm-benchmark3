# 1. Objectives and constraints

**Optimization objectives (ordered, not collapsed into one number):**

1. **Bounded SLA risk** – minimize the *probability of breach*, especially the tail (urgent/high cases), not just average waiting time.
2. **Authorization compliance** – every executed event must satisfy skill/security/approval rules.
3. **Effective throughput** – completions per period that survive (counting rework), not just fast starts.
4. **Containment of handover damage** – the evidence shows each avoidable handover costs real hours (2.7 h on high-complexity owner changes) and cumulative churn (>2 reassignments  1.8× rework).
5. **Workload fairness** – no resource absorbs more than 4 assignments per batch; overtime-flagged staff shielded.
6. **Capability growth** – trainees receive documented-development work when SLA risk permits.
7. **Resilience** – keep the Security/Approval/Rework pools substitutable; avoid deepening single-person dependencies.

**Hard constraints (safety/compliance — violations are audit findings, never tradeable):**

| ID | Rule |
|---|---|
| H1 | Skill level 0 = not allowed, ever. |
| H2 | Security Review: level 3 only, or level 1–2 with named supervisor (R7_Gita / R8_Hugo). |
| H3 | Final Approval: finalized only by level 2–3; level 1 may prepare only. |
| H4 | High-priority cases: executing skill  2, otherwise a formal supervised pair. |
| H5 | Max 4 new assignments per resource per batch. |
| H6 | Batching Quality Check only if priority normal/low **and** SLA remaining > 24 h. |

**Conditional-hard constraint:** H7 — no *new* work to `overtime_risk = high` resources **unless** the case is urgent and no safe alternative exists (requires an override reason code).

**Soft preferences (weighted, explicitly in tension with each other):**

- P1 Continuity / handover cost (weighted by complexity and `reassignment_count`).
- P2 Skill match beyond the legal floor (weak-owner retention costs a median 3.3 h + rework).
- P3 Fairness across teams and shift hours.
- P4 Training quota:  20 % of normal/low assignments support documented training priorities, *when SLA-safe*.
- P5 Bottleneck avoidance / resilience buffers.

Precedence: **compliance > feasibility (hours/deadline) > H4–H7 > P1–P5**. Rule 5 of the scenario (prefer continuity on high-complexity/high-handover cases) is treated as a *strong* P1 preference that yields only when the owner is unauthorized (H1/H2) or genuinely over-capacity. No single scalar "optimum" is claimed; the weights are public governance parameters, reviewed monthly with workers and auditors.

# 2. Assignment policy

```text
POLICY "Explainable Dynamic Dispatch" (EDD)

INPUTS: queue Q, resource state R (open cases, hours_left, skills, flags),
        learned service-time priors (activity, complexity_band, skill_level),
        current batch counters B[res], supervision registry.

FOR each case c in Q ordered by (priority_weight DESC, sla_remaining ASC):

  STEP 1 — HARD ELIGIBILITY FILTER (produce {eligible}, {blocked, reason_code})
    a. skill[required] >= 1                              (H1)
    b. Security: skill==3 OR (skill in {1,2} AND free supervisor in {Gita,Hugo}) (H2)
       Final Approval: skill>=2 to finalize; skill==1 only as preparer-in-pair (H3)
    c. priority in {high,urgent}: skill>=2 unless supervised pair formed      (H4)
    d. hours_left(headroom) >= (est.) + already-committed minutes,
       est_deadline(start+) <= sla_deadline                  (feasibility gate)
    e. overtime_risk == "high" -> exclude unless
       (priority==urgent AND eligible_pool_empty_without_them) -> reason EX-OT (H7)
    f. B[res] < 4                                            (H5)

  STEP 2 — SCORE each eligible resource (all scores in [0,1]; weights public):
    U  urgency/deadline fit : priority weight × deadline proximity
                              + shift-cover margin (does this person's remaining
                                hours absorb earlier commitments?)
                              w_U = 0.30
    S  skill fit            : level vs complexity-adjusted baseline; penalty for
                              gap below "comfort level" on complexity  0.7;
                              light bonus for level-3 only where the specialist
                              pool is NOT a known bottleneck (anti-cherry-picking)
                              w_S = 0.25
    C  continuity           : +current_owner, scaled UP by complexity and by
                              handover_cost_band, DOWN as reassignment_count rises
                              (>2  strong retention push, per 1.8× rework evidence)
                              w_C = 0.20
    W  workload fairness    : penalty on open-case percentile and hours-headroom
                              deficit; team-level balance nudge             w_W = 0.15
    D  development          : +if activity == res.training_priority AND priority
                              normal/low AND complexity  0.55 AND supervisor/
                              QA-checkpoint mappable                       w_D = 0.05
    X  resilience/bottleneck: penalize raising single-person share of a critical
                              activity above threshold; bonus for safe cross-
                              team placements; protect a "reserve" of 1
                              Security-capable and Approval-capable headroom
                              w_X = 0.05
    TOTAL = 0.30U + 0.25S + 0.20C + 0.15W + 0.05D + 0.05X

  STEP 3 — ASSIGN with tie-breaking (deterministic, auditable):
    1) higher urgency deadline coverage  2) lower handover cost band
    3) lower cumulative reassignments created this batch
    4) resource id alphabetical            (arbitrary but reproducible)

  STEP 4 — RECORD: chosen resource, runner-up, full reason string (which term
           dominated), any override codes; emit worker-readable explanation.

EXCEPTION HANDLING:
  - No eligible resource: escalate queue with interim mitigation + alert.
  - Overrides require reason code (EX-OT-OVERRIDE, EX-CAP-RELIEF,
    EX-SUPERVISION-PAIR) and create a deviation-register entry automatically.
  - Learning loop:  updated weekly from logs; weights re-validated quarterly.
```

Design rationale: step 1 enforces everything society/regulators would call *non-negotiable*; steps 2–3 make trade-offs legible — an auditor can always ask "why X?" and get the dominating component back.

# 4. Comparison with baseline policies

| Criterion | First-available | Specialist-only | Proposed EDD |
|---|---|---|---|
| Expected throughput | Highest *starts* (lowest time-to-assign), but inflow converted poorly: mismatch inflates service (~3.3 h pattern) and churn breeds rework | Lowest: specialists queue (given evidence: Security/Approval chokepoints); idle capacity elsewhere | Slightly below first-available on starts; higher *clean* completions; targeted specialization only where rules or economics demand it |
| SLA risk | Decent on averages, bad in the tail — mismatches discovered late | Dangerous at both extremes: level-3 gates starve urgent Security cases (only 2 people authorized!) while trainees sit idle | Best bounded-tail behavior: deadline-driven ordering, feasibility gate vs. `hours_remaining`, pre-declared fallbacks (e.g., C002Bruno/Eva) |
| Error/rework risk | Worst — the evidence explicitly links it to more reassignments and mismatch | Nominally lowest errors per event, but deadline compression elsewhere creates different failures | Intermediate-low: trainees only inside a safe envelope (low priority, ample SLA, checkpoints); continuity protected on complex cases |
| Workload fairness | Myopic: chases the momentarily-lightest resource, causing whiplash; ignores overtime flags | Poorest: Gita/Hugo/Farid saturate while others coast; Gini of load explodes; burnout and absence risk | Explicit cap (4), overtime shielding, team-level balancing — the most even, and *explainably* so |
| Skill development | Accidental at best | Structurally zero: experts cherry-picked, everyone else's skills decay | Institutionalized quota + shadowing + conditional plans; admittedly under-target this batch, but the mechanism and its measurement exist |
| Continuity | Poor: pure load-chasing discards ownership | Poor-to-medium: owner rarely equals global specialist, so handovers are systemic | Highest: continuity term + rule-5 logic; avoided 2.7 h-class penalties on C016-type cases; residual losses (C003, C014) made deliberate, mitigated, and logged |
| Resilience | Brittle differently: no competence-depth logic, coverage is luck | Most fragile: single points of failure (Farid = sole Approval-3; Gita/Hugo = Security pool) with no systematic substitution | Strongest available *within this roster*: substitution awareness (similarity networks), cross-team placements (Hugo on rework), reserve-headroom protection. Honest caveat: the underlying skill matrix itself is fragile — no dispatch policy fixes a 2-person Security pool; that needs a hiring/cross-training decision |

**Bottom line:** neither baseline dominates. First-available buys speed now and pays in rework; specialist-only buys correctness per event and pays in queues and fragility. EDD trades a modest amount of immediate responsiveness for risk containment, fairness, and capability growth — a position that is defensible precisely because its concessions are explicit and auditable rather than emergent accidents.

def hard_gates(res, ev, batch):
    """Return (ok, block_reason). Encodes H1–H7."""
    s = SKILL[res].get(ev["required_skill"], 0)
    if s == 0:                                          return False, "H1-skill0"

            return False, "H2-security-gate"

        return False, "H4-priority-floor"

        return False, "H7-overtime-shield"
    if batch[res] >= 4:                                 return False, "H5-batch-cap"
    if not feasible(res, ev, svc):                      return False, "FEAS-hours/deadline"
    return True, ""

def score(res, ev, batch):
    u = PRIO_W[ev["case_priority"]] * deadline_proximity(ev) * shift_cover(res, ev)
    s = skill_fit(SKILL[res][ev["required_skill"]], ev["case_complexity"])
    c = continuity(ev["current_owner"] == res, ev["handover_cost_band"],
                   ev["reassignment_count"], ev["case_complexity"])
    w = fairness_penalty(res, batch)                    # open cases + hours headroom
    d = dev_bonus(SKILL[res], ev)                       # activity == training_priority, safe case
    x = resilience_term(res, ev)                        # concentration vs. res_similarity depth
    tot = sum(WEIGHTS[k]*v for k, v in zip("USCWDX",(u,s,c,w,d,x)))
    return tot, {"U":u,"S":s,"C":c,"W":w,"D":d,"X":x}

def recommend(queue, batch):
    out = []
    for _, ev in queue.sort_values(["case_priority","sla_deadline"],
                                   ascending=[False,True]).iterrows():
        cands = [(r,) for r in SKILL]
        elig = [r for r in SKILL if hard_gates(r, ev, batch)[0]]
        if not elig:
            out.append((ev["case:concept:name"], "ESCALATE", hard_gates.reason_codes)); continue
        scored = sorted(elig, key=lambda r: (-score(r, ev, batch)[0],
                                             ev["handover_cost_band"]=="high",
                                             r))           # deterministic tie-breaks
        best = scored[0]; batch[best] += 1
        out.append((ev["case:concept:name"], best, score(best, ev, batch)[1]))
    return out

# ---------- 4) Auditing the deployed policy ----------
SEC  = pm4py.filter_event_attribute_values(log, "required_skill", ["Security"], level="event")

    return (last > pd.Series(deadlines)).mean()

    eff = l.apply(lambda r: SKILL[r["org:resource"]].get(
                      {"ConceptName->map":r["concept:name"]}.get("k", ""), 0), axis=1)
    return None  # placeholder: join required_skill to floormap and compare

    j = deployed.merge(recommended, on="case:concept:name", suffixes=("_done","_rec"))
    return j[j.org_resource_done != j.org_resource_rec]["assignment_reason"].value_counts()
