# 1. Objectives and constraints

## Optimization objectives (multi-criteria, not single-metric)
1. **SLA risk containment** – minimize probability of breaching deadlines, weighted by case priority.
2. **Throughput** – keep queues moving, avoid idle capacity, but not at the expense of quality.
3. **Skill-match quality** – route work to a competence level appropriate to complexity and risk.
4. **Continuity of ownership** – preserve case context where handover cost or complexity is high.
5. **Workload fairness** – spread work so no one is chronically over- or under-loaded.
6. **Skill development** – give trainees supervised exposure on suitable cases.
7. **Resilience** – avoid concentrating critical skills (Security, Approval) in one or two people; keep bench strength.

These objectives *conflict* (e.g., continuity vs. fairness, specialist quality vs. bottleneck risk), so the policy is a **weighted, constrained scoring model**, not a single-objective optimizer.

## Hard constraints (safety / compliance — never violated)
- **H1** Security Review: skill 3, or skill 1–2 **only** under explicit supervision by R7_Gita or R8_Hugo. Skill 0 = never allowed.
- **H2** Final Approval: skill 2–3 to finalize; skill 1 may prepare only.
- **H3** High-priority case  minimum skill 2, unless explicitly supervised.
- **H4** No resource receives more than 4 new assignments in a batch.
- **H5** Quality Check batching only if priority  {normal, low} and SLA remaining > 24h.
- **H6** Skill = 0 blocks any assignment (even supervised) — this is a hard eligibility filter, not a scoring penalty.

## Soft constraints / preference trade-offs (tunable weights, explainable)
- **S1** Prefer continuity for high-complexity + high-handover-cost cases, unless owner skill 1 and no supervision is feasible.
- **S2** Avoid loading resources flagged overtime risk = high, unless SLA is urgent and no safer alternative exists.
- **S3** Target 20% of normal/low-priority assignments to documented training priorities, provided SLA risk stays acceptable.
- **S4** Avoid over-concentration on scarce specialist skills (Security, Approval) to protect resilience against absence.
- **S5** Balance open-case counts and remaining hours across resources.

# 2. Assignment policy

```
INPUT: queue of cases, resource table, current-batch assignment counter

for each case in queue, sorted by (priority_rank desc, SLA_urgency desc):

    # --- STEP 1: Eligibility filtering ---
    candidates = resources where skill(required_skill) > 0
    if case.priority in {urgent, high}:
        candidates = candidates where skill >= 2
                     OR (skill in {1,2} AND supervisor in {R7_Gita, R8_Hugo} available)  # Security only
    if activity == "Final Approval":
        finalizers = candidates where skill >= 2
        preparers  = candidates where skill == 1   # H2: prepare-only track
    if activity == "Security Review" and skill in {1,2}:
        require supervisor_available(R7_Gita, R8_Hugo)
    if activity == "Quality Check":
        batch_eligible = (priority in {normal, low}) and (SLA_remaining > 24h)
    remove candidates whose batch_assignment_count_today >= 4          # H4
    remove candidates with overtime_risk == "high" 
        UNLESS case.priority == "urgent" AND no other candidate exists  # S2

    if candidates is empty:
        ESCALATE: flag case for supervisor override / manual triage, log reason

    # --- STEP 2: Scoring eligible candidates ---
    for r in candidates:
        sla_score        = f(SLA_remaining, priority)          # higher when tighter deadline
        skill_score      = skill_level(r, activity) / 3
        continuity_score = 1 if r == current_owner else 0
        continuity_score *= handover_cost_weight(case)         # boosted if complexity & handover high (S1)
        workload_score   = 1 - normalize(open_cases(r) + assignments_this_batch(r))
        overtime_penalty = penalty(r.overtime_risk)             # 0 / 0.3 / 0.6
        training_score   = training_bonus(r, activity, case.priority)  # only for normal/low, aligned "training priority"
        bottleneck_score = penalty_if(r.skill_in_scarce_pool AND scarce_pool_utilization > threshold)

        total_score = 
              w1*sla_score + w2*skill_score + w3*continuity_score
            + w4*workload_score + w5*training_score
            - w6*overtime_penalty - w7*bottleneck_score

    # --- STEP 3: Selection & tie-break ---
    best = argmax(total_score)
    if tie:
        prefer (a) lower open_cases, then (b) documented training match, then (c) round-robin log position
    assign case -> best
    increment batch_assignment_count[best]
    log(case, resource, scores, reason_codes)   # for explainability & audit

    # --- STEP 4: Exception handling ---
    if best.overtime_risk == high and case.priority != urgent:
        require secondary check / manager note before confirming
    if continuity broken on high-complexity/high-handover case:
        log "continuity override" reason explicitly
```

Weight defaults (illustrative, tunable): SLA 0.30, skill 0.20, continuity 0.20, workload/fairness 0.15, training 0.10, overtime penalty 0.15 (subtracted), bottleneck penalty 0.10 (subtracted). Weights are documented and versioned so audits can trace *why* a score changed.

# 4. Comparison with baseline policies

| Dimension | First-available routing | Specialist-only routing | Proposed explainable dynamic policy |
|---|---|---|---|
| **Expected throughput** | Highest short-term throughput; cases move immediately | Lower — specialists queue up, others idle | Slightly below first-available; batching and continuity checks add minor latency, but fewer redo loops preserve *net* throughput |
| **SLA risk** | Looks good on paper but skill mismatches cause hidden delays/rework that blow later SLAs | Good for urgent skill-critical cases (e.g., Security/Approval) but non-specialist cases wait, risking normal-priority SLA creep | Balanced: urgent/high cases get skill 2 guaranteed; normal/low cases tolerate trainee pace only when SLA slack exists |
| **Error/rework risk** | Highest — trainees may get complex/urgent work (e.g., C001, C016) purely because they're "available" | Lowest per-task error rate, but backlog pressure can push rushed handling elsewhere | Low-moderate: skill floors enforced for risk-bearing work; supervised training only on low-stakes cases |
| **Fairness of workload** | Somewhat fair by open-case count, but ignores hours-remaining/overtime risk — can overload people already near capacity | Poor — specialists (R3, R4, R7, R8, R9) get chronically overloaded while others (Amal on approval, Bruno on diagnosis) are underused | Explicit workload + overtime scoring rebalances (e.g., relieving R4_David this batch) |
| **Skill development** | Accidental only — no structure, and can be dangerous if trainees land on high-stakes work | None — specialists always chosen, trainees never grow | Deliberate 20% training quota on safe cases (C009, C010, C012), tied to documented "training priority" tags |
| **Continuity of ownership** | Ignored entirely — pure load-balancing | Ignored — specialist chosen regardless of who owned the case | Explicitly scored; preserved on 11/16 cases, broken only with logged justification (C001, C003, C014) |
| **Resilience to absence/bottleneck** | Reasonable (spreads work) but no skill logic — if a specialist is out, no one accounts for the resulting gaps | Poor — creates single points of failure (e.g., only R7/R8 ever touch Security) | Improves resilience by occasionally routing supervised trainees into scarce-skill areas *when safe*, building bench strength over time |

**No single baseline dominates.** First-available wins on raw speed but hides quality debt; specialist-only wins on per-case accuracy but creates fragile bottlenecks and skill stagnation. The proposed policy accepts a modest throughput and complexity cost in exchange for lower long-run rework, better fairness, slower-building resilience, and preserved continuity — an explicit, auditable trade-off rather than a hidden one.

# 5. Explanation to workers

> "Assignments in this system are based on a transparent set of factors, not on ranking people against each other. Every case is scored on: how urgent its deadline is, how well your skills match the type of work, whether you already own the case (so we don't create unnecessary handovers), how much you already have on your plate today, and — where it's safe and the deadline allows — whether the task is a good chance for you to build a skill you're working on.
>
> This means:
> - If you already own a case and switching would cost more time or hurt the customer, we'll usually keep it with you — even if someone else is technically faster.
> - If a case is urgent and high-risk (like Security Review or Final Approval), it will always go to someone with the right skill level, or to a trainee working directly with a named supervisor. This isn't about trust — it's about protecting outcomes on cases where mistakes are costly.
> - When we give you a case tied to your training goal, it's chosen deliberately — always on lower-risk, lower-priority work with enough time buffer, and often paired with a review step. This is an investment in your growth, not a test.
> - We also watch total workload and won't keep piling work onto people already stretched thin or working overtime unless there's truly no safer option. If you're getting fewer new cases in a batch, it may be because you're already carrying a heavier load.
> - Every assignment decision is logged with its reason, so if something looks odd, it can always be explained and discussed — including with you, if you disagree with a specific case."

The tone emphasizes explainability and shared logic, not surveillance or ranking, and invites workers to question specific decisions.

# 6. Process-mining audit indicators

Using the event log columns, define these auditable indicators:

1. **Handover frequency** — via `pm4py.discover_handover_of_work_network`: count of activity handoffs per case and per resource pair; flag cases exceeding expected handover count for their complexity band.
2. **Reassignment count distribution** — aggregate `reassignment_count`; compare against historical evidence (>2 reassignments  1.8x rework rate) to validate/calibrate the continuity weight.
3. **Skill mismatch rate** — join `org:resource` + `required_skill` against the skill matrix (external reference table); compute % of activities executed at skill level <2 without a logged `assignment_reason = "supervised"`.
4. **Workload distribution** — from `workload_snapshot`, compute Gini coefficient or IQR of concurrent open cases per resource per week; alert on sustained skew.
5. **Overtime risk exposure** — track hours-remaining-at-assignment vs. actual completion timestamps; flag resources tagged high overtime-risk who repeatedly exceed nominal hours (`time:timestamp` deltas per shift).
6. **SLA misses** — via `pm4py.get_service_time` / `pm4py.insert_case_service_waiting_time` and `sla_deadline`; compute % of cases exceeding deadline, segmented by `case_priority` and by whether the policy's continuity/skill rule was followed.
7. **Rework/appeal after assignment** — filter for `concept:name == "Rework Correction"` following a given assignment (`pm4py.filter_case_performance`), correlate with prior `assignment_reason` and `handover_cost_band` to see if skill-mismatched or high-handover assignments correlate with rework spikes.
8. **Training assignment share** — % of normal/low-priority activities where `assignment_reason` includes "training" tag; compare to the 20% target (S3) over rolling windows.
9. **Specialist bottleneck indicators** — via `pm4py.discover_organizational_roles` and `pm4py.discover_activity_based_resource_similarity`: measure concentration of Security/Approval activities in 1–2 resources; compute Herfindahl-type concentration index per activity type.
10. **Deviations from assignment policy** — log the *scored recommendation* vs. *actual assignment*; compute deviation rate and reasons (e.g., manager override, escalation), using `assignment_reason` as the ground-truth explanation field, feeding a conformance-checking-style audit.

# 7. PM4Py implementation sketch

```python
import pandas as pd
import pm4py

# --- Load & format event log ---
df = pd.read_csv("resource_assignment_log.csv")
df = pm4py.format_dataframe(
    df,
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)

# --- 1. Resource network discovery (handover, collaboration, roles) ---
how_net = pm4py.discover_handover_of_work_network(df, resource_key="org:resource")
wt_net  = pm4py.discover_working_together_network(df, resource_key="org:resource")
roles   = pm4py.discover_organizational_roles(df, resource_key="org:resource")
sim     = pm4py.discover_activity_based_resource_similarity(
              df, activity_key="concept:name", resource_key="org:resource")

pm4py.save_vis_sna(how_net, "handover_network.png")
pm4py.save_vis_sna(wt_net, "working_together_network.png")

# --- 2. Service / waiting time and SLA audit ---
df = pm4py.insert_case_service_waiting_time(
        df, case_id_key="case:concept:name", timestamp_key="time:timestamp")
service_times = pm4py.get_service_time(
        df, activity_key="concept:name", timestamp_key="time:timestamp")

df["sla_breached"] = pd.to_datetime(df["sla_deadline"]) < df["time:timestamp"]
sla_breach_rate = df.groupby("case_priority")["sla_breached"].mean()

# --- 3. Skill mismatch & training audit ---
skill_matrix = pd.read_csv("skill_matrix.csv")  # Resource x activity skill levels
merged = df.merge(skill_matrix, left_on=["org:resource", "required_skill"],
                   right_on=["resource", "skill_activity"], how="left")
merged["low_skill_flag"] = merged["skill_level"] < 2
training_share = df[df["case_priority"].isin(["normal", "low"])]\
                   ["assignment_reason"].str.contains("training").mean()

# --- 4. Filtering high-risk / high-complexity cohorts ---
high_complexity_cases = pm4py.filter_event_attribute_values(
    df, "case_complexity", [">0.7"], level="case", retain=True)

urgent_reassigned = pm4py.filter_event_attribute_values(
    df, "case_priority", ["urgent"], level="case", retain=True)
urgent_reassigned = urgent_reassigned[urgent_reassigned["reassignment_count"] > 0]

# --- 5. Performance DFG for bottleneck / batching diagnostics ---
perf_dfg, start_acts, end_acts = pm4py.discover_performance_dfg(df)
pm4py.view_sna(perf_dfg)  # visualize bottlenecks (e.g., Security, Approval queues)

# --- 6. Case-level performance filtering (SLA risk hot-spots) ---
slow_cases = pm4py.filter_case_performance(
    df, min_performance=24*3600, max_performance=None)  # cases open >24h

# --- 7. Variant analysis to detect deviation from intended routing ---
variants = pm4py.get_variants(df)
# Compare variants where handover_cost_band == "high" against continuity policy
deviation_cases = df[(df["handover_cost_band"] == "high") &
                      (df["reassignment_count"] > 0)]

# --- 8. Batch discovery for Quality Check activities ---
batches = pm4py.discover_batches(
    df[df["concept:name"] == "Quality Check"],
    resource_key="org:resource", timestamp_key="time:timestamp")
```

**How this supports the policy loop:**
- `discover_handover_of_work_network` / `discover_working_together_network` reveal whether continuity rules are actually honored and whether collaboration patterns match intended supervision pairs (e.g., R7/R8 for Security).
- `discover_organizational_roles` and `discover_activity_based_resource_similarity` validate that the skill matrix matches observed behavior, and detect emergent specialization/bottlenecks the policy should rebalance.
- `get_service_time` / `insert_case_service_waiting_time` + `sla_deadline` comparisons quantify SLA risk realized vs. predicted by the scoring model, allowing weight recalibration.
- `discover_performance_dfg` highlights systemic bottlenecks (e.g., Security/Approval queues), feeding back into the bottleneck-avoidance term of the scoring function.
- `filter_event_attribute_values` / `filter_case_performance` isolate high-complexity, high-priority, or SLA-breaching cohorts for root-cause review (e.g., checking whether the R4_David overload relief this batch actually reduced his SLA breach rate).
- `discover_batches` confirms Quality Check batching stayed within the SLA/priority guardrails (H5).

This closes the loop: the policy's assumptions (skill levels, handover costs, training tags) are periodically **re-derived from the log itself**, not just asserted, keeping the model auditable and adaptive rather than a static rulebook.
