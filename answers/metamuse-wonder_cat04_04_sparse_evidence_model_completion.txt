# 1. Evidence Ledger

Both directions between `Credit Check` and `Engineering Review` in the DFG—`Credit Check  Engineering Review` 17 and `Engineering Review  Credit Check` 11—do **not** by themselves prove concurrency. Only completion timestamps, reordered by ingestion index on ties, are available (S7, D7). The same two directions could arise from true parallelism, an XOR choice between two sequential routings, case-dependent sequencing, resource availability, rework-free but ordered work with different durations, or timestamp/ingestion artefacts. Concurrency is a claim about overlapping lifecycles or independence; directly-follows counts are only claims about observed completion adjacency. They justify admitting both orders in some candidates, not asserting `AND`.

# 2. Shared Assumptions

**Event-completion semantics.** Every label denotes a completion event, not a start. A precedence edge below is therefore a constraint on completion order in the model language, used as a proxy for the unknown lifecycle constraint. We do not claim that an activity could not have started earlier.

**Fixed backbone.** All candidates enforce `Register Order` first, `Approve Configuration  Release Production  Archive Case` last, each at most once, and no activities after `Archive Case`. This follows D1–D2 and the unanimous log.

**Checks required.** Balanced and permissive require both `Credit Check` and `Engineering Review` before `Approve Configuration` (D3). Conservative requires them only because every observed variant contains both.

**Supplier Confirmation abstraction.** The silent/optional SC branch conflates three distinct realities that the exported log cannot separate: (i) stocked component legitimately skipped SC (S4); (ii) external component whose SC event was lost (S5); (iii) external component whose SC genuinely did not happen, which would be non-compliant under S3 but invisible here. Because the external/stocked attribute is absent, no candidate can express “SC iff external”. The XOR-with-silent branch must therefore be read as “no SC completion is required by the control-flow model”, not as “SC was not needed or not performed”. Robustness claims are limited accordingly.

**Expedite Review.** Treated as optional and at-most-once in balanced/permissive from D6/S6, despite only 2/30 observations; conservative treats its two observed placements as exact variants.

**No loops, duplicates, or skips of checks/approval.** No observed trace repeats an activity or omits CC, ER, ACfg, RP, or Arch; no candidate admits loops.

# 3. Conservative Candidate

**Inductive bias.** This candidate is deliberately enumerative and closed-world: the language is exactly the seven observed variants, no more. It overfits sampling accident—frequencies, singleton placements, and possibly missing SC events are frozen as structure—so it should be read as an audit baseline (“what have we literally seen?”), not as a plausible process law. It makes no concurrency claim; each variant is a pure sequence.

**Formal expression.** `model = XOR((V1), (V2), (V3), (V4), (V5), (V6), (V7))`, with each `Vi` the full sequence listed in Section 1, all beginning `Register Order` and ending `Approve Configuration, Release Production, Archive Case`.

**Code.**

```python
import pm4py

def seq(*labels):
    inner = ", ".join(f"'{x}'" for x in labels)
    return f"->( {inner} )"

RO, CC, ER, SC = "Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation"
EX, AC, RP, AR = "Expedite Review", "Approve Configuration", "Release Production", "Archive Case"

variants = [
    (RO, CC, ER, SC, AC, RP, AR),
    (RO, ER, CC, SC, AC, RP, AR),
    (RO, CC, ER, AC, RP, AR),
    (RO, ER, CC, AC, RP, AR),
    (RO, CC, SC, ER, AC, RP, AR),
    (RO, CC, ER, SC, EX, AC, RP, AR),
    (RO, ER, CC, EX, SC, AC, RP, AR),
]
tree_str = "X( " + ", ".join(seq(*v) for v in variants) + " )"
model_conservative = pm4py.parse_process_tree(tree_str)
```

**Behaviour deliberately excluded.** Any new interleaving; Expedite without SC; Expedite in any position except the two singletons; SC after ER-only (i.e. `ER, SC, CC`); SC-free Expedite cases; any trace whose no-SC status stems from a missing event paired with an otherwise novel order.

**Known underfitting risks.** Severe. Duplicate labels appear in every XOR branch: the tree has seven copies of most activities, which harms readability, can create confusing duplicate transitions after Petri-net conversion, complicates alignment explanations (“which `Credit Check` copy?”), and does not scale—each newly observed variant adds a whole branch rather than a local generalisation. If S2/D5/S6 describe the real process, this model will reject many legitimate future cases and its apparent precision is an artefact of a 30-case sample.

# 4. Balanced Candidate

**Inductive bias.** This candidate generalises only where independent evidence converges: both CC/ER orders are frequent, so they are left unordered; SC is optional in control flow but anchored to the one predecessor present in all 23 SC traces; Expedite is optional, anchored after both checks, and left unordered with SC because one singleton shows each side and S6 explicitly permits both. It prefers a partial order over a pure sequence (which would privilege S1 without warrant) and over a ProcessTree `+` block for CC/ER/SC (which would force SC to wait for both checks, contradicting V5).

**Decision logic for CC, ER, SC, Expedite, exactly.** (1) *CC vs ER:* no edge. Two frequent opposite orders (17 vs 11 adjacency) plus S2 make a fixed sequence indefensible; an XOR of two sequences would fit equally but falsely claim mutual exclusion of starts, so a partial order is the honest representation under D7. (2) *SC:* edge `CC  SC` only. CC precedes SC in all SC traces; ER precedes SC in 21/23, but V5 (×2) shows ER-completion is not required, matching D5. ERSC is therefore rejected; CCSC is retained as the weakest evidence-backed anchor, while admitting it may really be “either check” (D5) with ER-first-sufficient cases simply unobserved. (3) *Expedite:* edges `CC  Exp` and `ER  Exp` (D6/S6, and both singletons satisfy this). (4) *Exp vs SC:* no edge, because V6 and V7 show both orders and S6 sanctions both. (5) *Closure:* all of CC, ER, and—if not silent—SC/Exp precede `Approve Configuration`.

**Formal expression.** `( RO, PO{ CC, ER, SC?, Exp? ; CCSC, CCExp, ERExp }, ACfg, RP, Arch )`, where `?` is XOR with a silent transition and `PO` is a strict partial order.

**Code.**

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def T(label):
    return Transition(label=label)

def optional(label):
    return OperatorPOWL(operator=Operator.XOR, children=[Transition(label=label), SilentTransition()])

ro, cc, er = T("Register Order"), T("Credit Check"), T("Engineering Review")
sc_opt, ex_opt = optional("Supplier Confirmation"), optional("Expedite Review")
ac, rp, ar = T("Approve Configuration"), T("Release Production"), T("Archive Case")

core = StrictPartialOrder(nodes=[cc, er, sc_opt, ex_opt])
core.order.add_edge(cc, sc_opt)      # SC anchored to Credit Check (all SC traces; D5)
core.order.add_edge(cc, ex_opt)      # D6/S6
core.order.add_edge(er, ex_opt)      # D6/S6
# No CC-ER edge, no ER-SC edge (V5), no SC-Exp edge (V6, V7, S6).

model_balanced = StrictPartialOrder(nodes=[ro, core, ac, rp, ar])
model_balanced.order.add_edge(ro, core)
model_balanced.order.add_edge(core, ac)
model_balanced.order.add_edge(ac, rp)
model_balanced.order.add_edge(rp, ar)
```

**Behaviour deliberately excluded.** SC before CC completes (`ER,SC,CC` or `SC,CC,ER`); Expedite before both checks complete; Expedite or SC after approval; skipped/duplicated checks; SC or Expedite repeated.

**Known underfitting risks.** If D5 truly means “either check suffices” and ER-sufficient SC cases exist but were unsampled, `CCSC` underfits. If some no-SC traces are missing events from otherwise novel orders, those orders are still rejected. If Expedite can occur without SC (plausible—only 2 Expedite cases, both with SC, likely coincidence), this model does admit that, but if Expedite can precede ER when triggered early, D6-anchoring underfits.

# 5. Permissive Candidate

**Inductive bias.** This candidate treats medium/low-confidence precedence claims as hypotheses to stress-test rather than constraints: it keeps only the high/medium-high backbone (D1, D2, D3, D4, D6-placement-after-both for Expedite) and drops the specific SC anchor, because D5 says either check may suffice and completion order cannot show when SC *started*. It is a sensitivity instrument: behaviour admitted here but not in the balanced model marks exactly where new data would change decisions.

**Formal expression.** `( RO, PO{ CC, ER, SC?, Exp? ; CCExp, ERExp }, ACfg, RP, Arch )`.

**Code.**

```python
import pm4py
from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition, SilentTransition
from pm4py.objects.process_tree.obj import Operator

def T(label):
    return Transition(label=label)

def optional(label):
    return OperatorPOWL(operator=Operator.XOR, children=[Transition(label=label), SilentTransition()])

ro, cc, er = T("Register Order"), T("Credit Check"), T("Engineering Review")
sc_opt, ex_opt = optional("Supplier Confirmation"), optional("Expedite Review")
ac, rp, ar = T("Approve Configuration"), T("Release Production"), T("Archive Case")

core = StrictPartialOrder(nodes=[cc, er, sc_opt, ex_opt])
core.order.add_edge(cc, ex_opt)      # D6/S6 retained
core.order.add_edge(er, ex_opt)      # D6/S6 retained
# No CC->SC edge: D5 "either check" + start-time ignorance (D7).

model_permissive = StrictPartialOrder(nodes=[ro, core, ac, rp, ar])
model_permissive.order.add_edge(ro, core)
model_permissive.order.add_edge(core, ac)
model_permissive.order.add_edge(ac, rp)
model_permissive.order.add_edge(rp, ar)
```

**Boundary of reasonable generalisation.** Admitted: any completion interleaving of CC, ER, and optional SC before approval; optional Expedite once it is after both checks, on either side of SC. Still forbidden, and why: skipping CC/ER/ACfg/RP (D3/D2, unanimous log); SC or Exp after ACfg (D4/D6); Exp before both checks (D6/S6 retained even here—dropping it would contradict the only compliance statement with no counter-evidence); any repetition (no loop evidence, D6 “at most once”); anything before RO or after Arch (D1). “Reasonable” ends where a trace would require discarding a rule that has no observed counterexample.

**Behaviour deliberately excluded.** As listed above; notably `Exp` interleaved before ER/CC completion, approvals without checks, and post-approval SC/Exp.

**Known underfitting risks.** It still underfits if Expedite can legitimately start before both checks finish (start vs completion ambiguity), if SC is sometimes required to wait for both checks in a way that matters for compliance checking of interleavings, or if conditional SC requirements (external attribute) interact with ordering. Its main risk is the opposite—overfitting to stakeholder speculation (D5)—addressed in Sections 6–7.

# 6. Unobserved Behavior Audit

The conservative language is finite—exactly the seven observed sequences—so within the bound “traces over the eight labels, each at most once, length  8” it admits **no** unobserved trace; this is exhaustively checkable for this finite language, unlike the general case. Excluded traces (at least two per model) and earliest violated constraint:

- **Conservative:** (i) `RO, CC, ER, Exp, ACfg, RP, Arch` — excluded at the XOR root: it matches no enumerated variant, even though each step is domain-sensible; earliest violation is the closed-world branch choice after RO. (ii) `RO, ER, SC, CC, ACfg, RP, Arch` — no branch has SC in position 2; earliest violation is branch selection at the second event.
- **Balanced:** (i) `RO, ER, SC, CC, ACfg, RP, Arch` — earliest violation: `SC` fires before its required predecessor `CC` (edge CCSC). (ii) `RO, CC, Exp, ER, SC, ACfg, RP, Arch` — earliest violation: `Exp` fires before `ER` completes (edge ERExp, D6). (iii) `RO, CC, ER, SC, ACfg, Arch` — earliest violation: `RP` missing before `Arch` (backbone ACfgRPArch).

(ii) `RO, CC, ER, ACfg, SC, RP, Arch` — earliest violation: `SC` after `ACfg` (closure of the partial-order core before approval, D4). (iii) `RO, ER, ACfg, RP, Arch` with CC omitted — earliest violation at `ACfg`: CC is a required core node (D3).

# 8. Validation Code

This code reconstructs the log, converts all three candidates, checks soundness, computes available metrics, samples playout, and tests a manual positive/negative suite by alignment fitness on single traces (fitness 1.0  admitted; this is a conformance check, not a language-inclusion proof). Sampled playout cannot prove that one model's language includes another's or that no undesirable trace exists; even here, where languages are finite, playout with `max_traces` is only exhaustive if it returns the full enumerated language without sampling caps, which the code does not assume.

```python
import pm4py
from pm4py.objects.log.obj import EventLog, Trace, Event

# ---- assume model_conservative, model_balanced, model_permissive defined above ----
models = {
    "conservative": model_conservative,
    "balanced": model_balanced,
    "permissive": model_permissive,
}

# 1. Reconstruct the 30-case log
base = [
    (12, "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (7,  "Register Order,Engineering Review,Credit Check,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
    (4,  "Register Order,Credit Check,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (3,  "Register Order,Engineering Review,Credit Check,Approve Configuration,Release Production,Archive Case"),
    (2,  "Register Order,Credit Check,Supplier Confirmation,Engineering Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Credit Check,Engineering Review,Supplier Confirmation,Expedite Review,Approve Configuration,Release Production,Archive Case"),
    (1,  "Register Order,Engineering Review,Credit Check,Expedite Review,Supplier Confirmation,Approve Configuration,Release Production,Archive Case"),
]
trace_strings = [s for n, s in base for _ in range(n)]
assert len(trace_strings) == 30
log = pm4py.parse_event_log_string(trace_strings)

# 2-4. Convert, check soundness, compute metrics
nets = {}
for name, model in models.items():
    net, im, fm = pm4py.convert_to_petri_net(model)
    nets[name] = (net, im, fm)
    print(name, "sound:", pm4py.check_soundness(net, im, fm, print_diagnostics=False))
    print(name, "fitness:", pm4py.fitness_alignments(log, net, im, fm))
    print(name, "precision:", pm4py.precision_alignments(log, net, im, fm))
    print(name, "generalization:", pm4py.generalization_tbr(log, net, im, fm))
    print(name, "simplicity:", pm4py.simplicity_petri_net(net, im, fm))

# 5. Sampled playout (illustrative only; NOT proof of inclusion/exclusion)
for name, model in models.items():
    try:
        played = pm4py.play_out(model, max_traces=200)
        print(name, "sampled playout traces:", len(played))
    except Exception as e:
        print(name, "play_out unavailable for this object:", e)

# 6. Manual positive/negative suite via single-trace alignment fitness
def admits(net, im, fm, labels):
    trace = Trace(attributes={"concept:name": "test"})
    for lab in labels:
        trace.append(Event({"concept:name": lab}))
    single = EventLog([trace])
    res = pm4py.fitness_alignments(single, net, im, fm)
    return res["log_fitness"] >= 0.999

RO, CC, ER, SC = "Register Order", "Credit Check", "Engineering Review", "Supplier Confirmation"
EX, AC, RP, AR = "Expedite Review", "Approve Configuration", "Release Production", "Archive Case"

suite = [
    # (trace, {model: expected_admitted})
    ((RO, CC, ER, Exp, AC, RP, AR) if False else (RO, CC, ER, EX, AC, RP, AR),
     {"conservative": False, "balanced": True, "permissive": True}),
    ((RO, ER, SC, CC, AC, RP, AR),
     {"conservative": False, "balanced": False, "permissive": True}),
    ((RO, CC, EX, ER, SC, AC, RP, AR),
     {"conservative": False, "balanced": False, "permissive": False}),
    ((RO, CC, ER, SC, AC, RP, AR),
     {"conservative": True, "balanced": True, "permissive": True}),
    ((RO, CC, ER, AC, SC, RP, AR),
     {"conservative": False, "balanced": False, "permissive": False}),
]
for labels, expected in suite:
    for name, want in expected.items():
        net, im, fm = nets[name]
        got = admits(net, im, fm, labels)
        status = "OK" if got == want else "MISMATCH"
        print(status, name, "admits" if got else "rejects", labels)
```

# 9. Recommendation and Data-Collection Plan

**Immediate use: balanced.** It is the only candidate that simultaneously respects every rule lacking a counterexample, explains both frequent check orders without inventing causality, accommodates V5 and both Expedite placements, and degrades gracefully under SC missingness. Use it for conformance monitoring, with violations reported alongside which hypothesis-edge they break (e.g. “violates CCSC” rather than a bare nonconformance flag).

**Sensitivity analysis: permissive** (with conservative as the lower-bound reference). Running all three brackets the truth: conservative = seen-only, balanced = evidence-anchored, permissive = D5-literal. Where balanced and permissive disagree—SC before CC completes—is precisely the highest-value uncertainty.

**Data-collection plan.**
1. **Lifecycle timestamps:** export `start` and `complete` for every activity, plus resource/team. This directly resolves XOR-vs-concurrency (overlap of CC/ER intervals), whether SC starts after one check (D5) or waits for both, and whether S1 (“CC finishes before ER starts”) is a start rule violated in fact or an artefact.
2. **Case attributes:** export external/stocked flag, component type, supplier ID, Expedite trigger/reason, and an SC-event integration receipt/audit ID so missing events (S5) can be separated from true skips (S4). Reconcile a sample of no-SC cases against the procurement system of record.
3. **Maximally informative future traces:** (a) a case with `ER` completing, then SC, then `CC`—one such genuine trace kills the balanced CCSC edge and vindicates D5/permissive; (b) start-timestamp data showing SC never starts until CC completes across many ER-first cases—supports balanced; (c) Expedite cases without SC, and Expedite triggered before a check completes—to test D6's scope; (d) external-flagged cases with no SC event—to quantify missingness vs violation; (e) stocked cases with SC performed anyway—to test whether S3's conditional is also sufficient. Collect until the SC-anchor question has, say, double-digit informative cases rather than the current zero ER-first-SC observations.
4. **Re-estimate missingness:** join logs to the integration platform to measure the true SC loss rate; if it approaches the no-SC rate for external cases, revisit whether SC is optional at all.

# 10. Uncertainty Statement

Calibrated confidences (probability the modelling choice matches the true process, given current evidence): backbone RO-first and ACfgRPArch: **~0.95**. Both CC and ER required before approval: **~0.85**. CC/ER unordered rather than fixed CCER: **~0.8** that no universal completion sequence exists; only **~0.55** that they are truly concurrent rather than alternative sequences—D7 caps this. SC represented as optional in control flow: **~0.75** that some true skips exist (S4), but near-certain that the silent branch also absorbs missing events, so per-case interpretation confidence is low. Balanced's CCSC edge over permissive's no-edge: **~0.6**—it rests on absence of ER-first-SC in 23 SC cases plus one reading of D5. Expedite after both checks, either side of SC: **~0.65**, resting on two singletons plus S6. Expedite independent of SC presence: **~0.5**.

**Alternative interpretation that would change the recommendation.** If lifecycle data showed S1 is a real start-time rule—CC always finishes before ER *starts*, and ER-first completions occur because a queued/sequential ER sometimes… no: if CC genuinely always precedes ER in lifecycle terms and ERCC completion orders arise from timestamp/ingestion error at scale, then a sequential CCER model (a fourth candidate) would beat the balanced partial order, and the balanced model's unordered checks would be over-permissive. Conversely, if SC start timestamps showed SC routinely starts after *either* check, the permissive model should be promoted to the default and the balanced CCSC edge deleted. Either finding is cheap to obtain and would materially reorder these candidates; until then, the balanced model is a stated hypothesis, not a discovered truth.
