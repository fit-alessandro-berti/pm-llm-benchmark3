## 1. Equivalence design space

The eight executions are object-centric traces of a lead `Order`. Local identifiers (`O1`, `I11`, …) are not business attributes. Identifiers that begin with `EXT` are: they mark objects whose lifecycle is centered on another order. Equivalence must therefore be stated over labeled event sequences, typed event-to-object (E2O) incidence, object-to-object (O2O) relations and qualifiers, and external flags — not over raw local names.

**E1 — Activity-sequence equivalence.**
Two executions are E1-equivalent when their timestamp-ordered sequences of activity *labels* are identical. Object types, object identifiers, E2O incidence, O2O edges, qualifiers, and externality are discarded. Invariants: the control-flow word over the activity alphabet, including repetition and position. E1 is an equality of sequences, hence an equivalence relation (reflexive, symmetric, transitive). Concurrent events (equal timestamps) are ordered by a fixed, declared tie-break `(activity, sorted participating type names)` so the word is unique; if one instead takes the set of linear extensions, E1 becomes a partial-order language equality and remains an equivalence, but clusters can merge. None of X1–X8 actually contain ties, so both conventions agree here.

**E2 — Typed structural equivalence under identifier renaming.**
Form the directed event-object incidence graph of an execution: event nodes labeled by activity; object nodes labeled by `(type, ext∈{0,1})`; E2O edges labeled by role-less incidence; O2O edges labeled by the supplied relation/qualifier (`contains`, `packs`, `carries`, `bills`, `settles`, `partially_settles`, `completes_settlement`, `replaces`, `removed_before_dispatch`); a total order on events. Two executions are E2-equivalent when there is a type-preserving, externality-preserving bijection of object nodes (local names may change; `EXT-*` may only map to `EXT-*` of the same type) and an order-preserving bijection of event nodes that preserves activity labels, E2O incidence, and qualified O2O edges. Invariants: activity word, per-event typed cardinalities, local versus external object counts, O2O topology and qualifiers. Discarded: concrete local identifiers and the left-to-right order of equally labeled `Add Item` events when the items are indistinguishable after renaming. E2 is graph isomorphism of canonically labeled structures and is an equivalence. Concurrent events are compared as a strict partial order (events with equal timestamps are incomparable); isomorphism must preserve that poset, not an arbitrary linearization.

**E3 — Business-semantic equivalence (preferred).**
E3 is coarser than E2. First compute the E2-canonical structure, then abstract it to a *motif vector*:
- isolation: whether any E2O or O2O incident touches an `EXT` object, and on which subprocess (logistics vs finance);
- fulfillment cardinalities: `#Item`, `#Package`, `#Delivery` (local);
- finance cardinalities: `#Invoice`, `#Payment`, and whether settlement is qualified as partial/complete;
- exception vocabulary: presence of replacement / `removed_before_dispatch`, and presence of a return–inspect–repack–redispatch cycle;
- invoice timing relative to the last dispatch (all eight invoice after logistics except that X8 invoices after the return cycle).

Two executions are E3-equivalent when their motif vectors are equal. Invariants: the operational story (isolated single shipment, split box / one van, split shipments with installment payment, shared package, shared invoice, pre-dispatch substitution, post-dispatch return). Discarded: local names, item-add order, and any E2 distinction that does not change the motif (none remain among X1–X8 except X1∼X2). E3 is equality of a deterministic feature vector, hence an equivalence. Concurrency is inherited from E2: only the motif, not a particular interleaving of independent pack lines, is compared — except that “pack-then-dispatch interleaved per package” versus “all packs then one dispatch” is itself a motif distinction (`#Delivery` and the pack/dispatch schedule).

**E4 — Isolation-blind cardinality equivalence (optional, diagnostic).**
Ignore `EXT` flags and all O2O qualifiers. Keep the activity word and local type multiplicities (and E2O type sets, but not extra external participants). This is an equivalence. It is useful only as a sensitivity probe: it is what one obtains if shared objects are treated as noise and replacement is invisible.

E1–E4 are nested only in special cases. E2 refines E3 on this set. E1 does *not* refine E3: X1 and X5 are E1-equal and E3-unequal. E4 is coarser than E3 and incomparable to E1.

## 2. Canonical signatures

Preferred relation is E3. The signature is computed from the E2-canonical form so it is invariant to local renaming and to swapping indistinguishable `Add Item` events.

```python
from collections import Counter, defaultdict

LEAD = "Order"
EXT_PREFIX = "EXT"
# qualifier vocabulary actually used in the eight cases
QUALIFIERS = {
    "contains", "packs", "carries", "bills", "settles",
    "partially_settles", "completes_settlement",
    "replaces", "removed_before_dispatch",
}

def is_ext(oid):
    return str(oid).startswith(EXT_PREFIX)

def rename_locally(objects_by_type):
    """Type-wise rank: local objects I1,I2,...; EXT objects keep a type-wise EXT rank."""
    mapping = {}
    for typ, oids in objects_by_type.items():
        locals_ = sorted(o for o in oids if not is_ext(o))
        exts = sorted(o for o in oids if is_ext(o))
        for i, o in enumerate(locals_, 1):
            mapping[o] = f"{typ[0]}{i}"          # I1, P1, ...
        for i, o in enumerate(exts, 1):
            mapping[o] = f"EXT-{typ[0]}{i}"
    return mapping

def e2o_schema(events, mapping, obj_type):
    """Per activity: frozenset of (type, local_card, ext_card) over this event class."""
    acc = defaultdict(list)
    for ev in events:  # already timestamp-sorted; ties broken as in E1
        bags = defaultdict(lambda: [0, 0])  # type -> [local, ext]
        for typ, oids in ev.objects.items():
            for oid in oids:
                bags[typ][1 if is_ext(oid) else 0] += 1
        acc[ev.activity].append(tuple(sorted(
            (t, loc, ext) for t, (loc, ext) in bags.items())))
    return tuple(sorted((a, tuple(sorted(v))) for a, v in acc.items()))

def motif_vector(events, o2o, mapping, obj_type):
    types_local, types_ext = Counter(), Counter()
    for oid, typ in obj_type.items():
        (types_ext if is_ext(oid) else types_local)[typ] += 1
    quals = tuple(sorted(q for *_, q in o2o if q in QUALIFIERS))
    acts = tuple(ev.activity for ev in events)
    ext_on = set()
    for ev in events:
        if any(is_ext(o) for oids in ev.objects.values() for o in oids):
            if ev.activity in {"Pack Package", "Dispatch"}:
                ext_on.add("logistics")
            if ev.activity in {"Issue Invoice", "Record Payment"}:
                ext_on.add("finance")
    isolation = "shared-" + "+".join(sorted(ext_on)) if ext_on else "isolated"
    if "Return Item" in acts or "Inspect Return" in acts:
        exception = "return-repack"
    elif "replaces" in quals or "removed_before_dispatch" in quals:
        exception = "pre-dispatch-substitution"
    elif "partially_settles" in quals:
        exception = "installment"
    else:
        exception = "none"
    return (
        isolation,
        exception,
        acts,
        tuple(sorted(types_local.items())),
        tuple(sorted(types_ext.items())),
        quals,
        e2o_schema(events, mapping, obj_type),
        ("Delivery", types_local["Delivery"]),
        ("Payment", types_local["Payment"]),
    )

def canonical_signature(execution):
    mapping = rename_locally(group_by_type(execution.objects))
    return motif_vector(execution.events, execution.o2o, mapping, execution.obj_type)
```

Two executions are E3-equal iff `canonical_signature` agrees. The activity word is retained so X3 (`Pack, Pack, Dispatch`) does not collapse with X4 (`Pack, Dispatch, Pack, Dispatch`). External ranks are retained so a shared package is not renamed into a local one.

## 4. Cluster interpretations

**SEM-ISO-SINGLE (X1, X2).** Signature: isolated, no exception, one package, one delivery, one invoice, one settling payment, two items packed together. Business: the textbook B2C order. Risk is low and mostly about master-data quality (wrong item on the box). Opportunity: this is the reference SLA and the cost-to-serve baseline. Flattening by `Order` is adequate; flattening by `Item` duplicates invoice/payment and invents a false split. Stable under ordinary repair (renaming, reordering indistinguishable adds, dropping unused attributes).

**SEM-ISO-SPLITBOX (X3).** Signature: isolated, two pack events, one delivery that carries both packages, single payment. Business: warehouse split (weight, hazard, availability) with a consolidated last mile. Risk: pick/pack KPIs double-count work while transport KPIs look like the happy path; customers see one shipment. Opportunity: box-level costing without promising two ETAs. Flattening by `Package` loses the single delivery; flattening by `Delivery` hides the extra pack labor. Stable unless a repair step merges consecutive same-label `Pack Package` events (that repair is unsafe here).

**SEM-ISO-SPLITSHIP (X4).** Signature: isolated, interleaved pack–dispatch pairs, two deliveries, one invoice, two payments qualified as partial then completing. Business: backorder / multi-wave fulfillment plus installment or split tender. Risk: partial settlement is not the same as two invoices; dunning, credit, and “paid?” queries must read qualifiers. Opportunity: promise dates per wave. Flattening by `Order` serializes two deliveries into one case and makes the second pack look like a rework; flattening by `Payment` severs the single invoice. Moderately stable: if qualifiers are dropped, the installment story degrades to “two payment events.”

**SEM-SHARE-LOG (X5).** Signature: activity word of the happy path, but pack and dispatch also bind an external order and an external item; invoice remains local to O5. Business: multi-order consolidation (same customer, same address, milk-run). Risk: a delay or damage on P51 is charged to the wrong order if cases are projected onto a single `Order`; conversely, O5 appears “normal” in an activity-only view. Opportunity: true transport-cost allocation. Flattening by `Order` duplicates the shared package or drops `EXT-OA`; flattening by `Package` is the honest grain. Unstable if external objects are stripped — the cluster collapses into SEM-ISO-SINGLE.

**SEM-SHARE-FIN (X6).** Signature: local logistics as X1; invoice and payment also bind `EXT-OB`; settlement has no order-level allocation. Business: combined billing (framework contract, one invoice for several orders). Risk: cash application and revenue recognition cannot be attributed from the lead order alone; “O6 is paid” is not a local fact. Opportunity: credit-term analysis at the invoice grain. Flattening by `Order` fabricates a private invoice; flattening by `Invoice` is required. Unstable under “ignore EXT.”

**SEM-SUBST (X7).** Signature: happy-path labels, but `I72 replaces I71`, `P71 removed_before_dispatch I71`, and `Dispatch` is incident to the surviving item. Business: pick substitution, damage-before-ship, or cancelled line that was already packed. Risk: inventory and the invoice still “see” two added items; only the qualified O2O and the extra Dispatch incidence tell the truth. Activity-level conformance will pass a model mined from X1. Flattening by `Order` or by activity word is actively misleading; item-level lifecycle is the right grain. Stability depends on qualifier retention. If a cleaner drops unknown O2O labels, X7 becomes a silent near-duplicate of X1 (borderline, §5).

**SEM-RETURN (X8).** Signature: extra `Return Item` / `Inspect Return`, a second package that replaces the first for the returned item, second delivery, invoice after the return cycle. Business: reverse logistics with restock-and-resend of one line, other line kept. Risk: on-time-delivery computed on D81 is wrong for I82; NPS and “delivered complete” disagree. Opportunity: return-reason and inspect-to-repack cycle time. Flattening by `Order` looks like a long happy path with mysterious extra packs; flattening by `Item` is necessary for I82. Stable under qualifier loss because the extra activities remain; unstable only if return activities are filtered as “noise.”

## 5. Borderline cases

**X1 versus X2.** E1, E2, and E3 all merge them if item identifiers are not attributes and the two `Add Item` events are same-label. A defensible finer relation — *labeled-object isomorphism without permuting same-type objects in event order* — would split them, because I11-before-I12 is a different word than I22-before-I21 if identifiers leak into the key. That split is a bug for business use and a feature only for replay of a specific system log. Another defensible split is “order of item identifiers is the catalog sequence,” which the data do not support.

**X1 versus X5.** E1 merges them (same activity word). E2 and E3 split them because pack/dispatch bind `EXT-OA` and `EXT-IA`. A third relation, E4 (isolation-blind), merges them again. Both merges are defensible: a shop-floor dashboard that only counts pick/pack/ship steps wants E1/E4; a control that allocates carton cost or investigates a damaged shared box must keep E2/E3. The borderline is exactly whether externality is an attribute of the *execution* or a join artifact.

**X1 versus X6.** Same pattern on the finance side. E1 merges; E2/E3 split; E4 merges. An accountant using invoice as the case identifier will refuse the merge; a warehouse manager will not care. A further disagreement: one may treat “V61 bills O6 and EXT-OB” as two local invoices that were incorrectly modeled as one object. Under that repair X6 becomes two finance traces and is no longer comparable to X1 at all. The prompt forbids inventing events; it does not forbid noting that the *object grain* of V61 is a modeling choice.

**X1 versus X7.** E1 merges (labels). E2/E3 split (Dispatch E2O + replacement qualifiers). If a pipeline keeps activities and local multiplicities but drops O2O qualifiers *and* extra E2O types not in a allow-list, X7 merges with X1 — a silent substitution. Conversely, a legal/compliance view that treats any `replaces` edge as a different process is right to isolate X7 even when the customer-visible activity word is unchanged. This is the canonical “hidden semantics” case: structure without qualifiers is insufficient.

**X3 versus X4.** E1, E2, and E3 all split them (pack/dispatch schedule, `#Delivery`, `#Payment`, installment qualifiers). A coarse “happy isolated fulfillment” relation that only checks “order created, items added, something packed, something dispatched, invoiced, paid, no EXT, no return” would merge them. That merge is defensible for a CFO “did we get paid?” report and indefensible for carrier booking or dunning. Another relation — same object-type multiplicities, ignore event order — still splits them (`Delivery` 1 vs 2, `Payment` 1 vs 2). Only collapsing repeated labels *and* ignoring multiplicities merges them; that is too coarse to call object-centric.

**X4 versus X8.** Both have two packages and two deliveries, so a cardinality-only signature is tempted to merge them. E1 splits (return/inspect vs second payment; interleaving differs). E2/E3 split (return motif vs installment motif; `P82 replaces P81 for I82` vs two independent waves; invoice after return vs invoice after both waves). A defensible merge exists if one codes both as “multi-delivery isolated order with one invoice” and treats return activities as optional decoration. That merge hides the fact that X8’s second delivery is corrective while X4’s is planned. Payment structure also differs: X8 is a single settlement after the mess; X4 is partial then complete. Flattening by `#Delivery` is the error that creates the false friendship.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel(ocel, object_type, …)` partitions lead objects by an *exact* lifecycle key derived from the OCEL projection onto each lead object: the ordered activities of events that mention the object, together with the co-occurring object identifiers (and, in current implementations, connected-component context up to `max_objs`). The key is essentially a serialization of the E2 graph that is *not* automatically renamed. What it preserves, therefore, is activity order, E2O incidence, and whatever object ids appear in that serialization — i.e., something at least as fine as E2, and often finer than E2.

Raw identifiers make exact clusters too fine because X1 and X2 then receive different keys (`I11,I12,P11,…` versus `I21,I22,P21,…`) even though they are E2-isomorphic. Item-add swap can also change a tuple serialization if ids are listed in encounter order. The result is one cluster per execution whenever ids are unique, which is the usual OCEL situation.

Canonicalize *before* clustering, or aggregate *after*:

```python
import pm4py
from copy import deepcopy

LEAD = "Order"

def canonicalize_ocel(ocel, lead_type=LEAD):
    """Rename every non-EXT object id to Type#rank inside each lead-object component."""
    # 1. split around lead objects (connected events + objects)
    # 2. apply rename_locally from §2 inside each component
    # 3. reassemble; EXT-* ids are preserved as typed EXT ranks
    return renamed_ocel  # same API as ocel

ocel_c = canonicalize_ocel(ocel, LEAD)
raw = pm4py.cluster_equivalent_ocel(ocel_c, LEAD)   # dict: cluster_id -> OCEL

def e3_bucket(sub_ocel):
    # rebuild an Execution from sub_ocel and call canonical_signature (§2)
    return canonical_signature(execution_from(sub_ocel))

merged = {}
for cid, sub in raw.items():
    sig = e3_bucket(sub)
    merged.setdefault(sig, []).append(sub)

# optional: collapse E3 buckets that only differ by installment-as-structure
# or by ignored qualifier sets, depending on the analysis question
preferred_clusters = merged
```

Exact E2-style equivalence (canonicalized `cluster_equivalent_ocel` without the E3 fold) is preferable when the task is conformance against a reference graph, regression testing of an extraction job, or deduplication of cloned demo traces. It is the wrong default for segmentation and reporting.

`max_objs` (and any implicit connected-component bound) is a practical hazard. X5 and X6 are already “larger” than X1 because of `EXT-*` participants. If a production log makes those external orders hubs (one invoice object billing hundreds of orders, one milk-run package tying many orders), the connected execution explodes, the key becomes unique, and every lead object is a singleton cluster — or the truncation at `max_objs` silently drops the very EXT incidence that distinguished SEM-SHARE-LOG from SEM-ISO-SINGLE. Operational rule: canonicalize and *cap context by type* (at most *k* objects per type, EXT counted separately), then fold with the E3 signature so truncation cannot create spurious splits.

## 7. Robustness analysis

**Ignore all O2O qualifiers.** E3 loses `partially_settles` / `completes_settlement`, `replaces`, `removed_before_dispatch`, and “P82 replaces P81 for I82.” X4 remains separate from X1 because of extra events and `#Delivery`/`#Payment`. X8 remains separate because of `Return Item` / `Inspect Return`. X7 is the casualty: if Dispatch’s extra `Item` incidence is also treated as a qualifier-adjacent detail and dropped, X7 joins SEM-ISO-SINGLE; if that E2O edge is kept, X7 stays alone but for a weaker reason (“dispatch mentions an item”). Recommendation: never drop replacement qualifiers for compliance; they are the only record of the hidden line change.

**Ignore external objects.** Strip every `EXT-*` from E2O/O2O and from type counts. X5 and X6 become E2-isomorphic to X1 (and X2). Shared-carton and combined-invoice disappear. This is the single largest merge and the most dangerous for finance and for transport costing. Activity-sequence clusters do not change.

**Collapse repeated same-label events.** Replace the activity word by the sequence of *first occurrences*, or by the set of labels. X3’s word collapses toward X1 (`Pack` no longer repeats). X4 collapses toward a single pack–dispatch–invoice–pay skeleton if *all* repeats go, merging it with X1 at E1 and almost at E4; E3 still sees `#Delivery=2` and `#Payment=2` unless multiplicities are also collapsed. X8 loses one pack and one dispatch but keeps return/inspect, so it stays distinct. Collapsing repeats is acceptable only together with explicit cardinality features.

**Pack and Dispatch as a partial order.** On the lead order, X3 has `{Pack31, Pack32} < Dispatch31`. X4 has `Pack41 < Disp41 < Pack42 < Disp42`. If one relaxes to “each package is packed before it is dispatched, and packs are pairwise concurrent,” X4’s *per-package* poset is two copies of pack≺dispatch, while X3 is two packs preceding one shared dispatch. They still do not match. The only merge appears if deliveries are also identified, which they are not. What *does* change: a hypothetical execution that packs both items first and then dispatches them as two deliveries would become poset-closer to X4. On the given eight, cluster assignments are unchanged; X4’s interleaving remains a real distinction from X3.

**Payment multiplicity as amount (optional).** Encode `Record Payment` as one logical settle node with attribute `n_payments` or `amount`. X4 then looks like split-ship + single settlement and moves next to a new “SEM-ISO-SPLITSHIP-PAID-ONCE” rather than installment. Whether that is correct depends on whether M41/M42 are tenders or system splits of one receipt. The data say partial then complete, so the structural reading is better for credit; the attribute reading is better for “is the invoice clear?”

Under the first two perturbations the preferred seven-cluster picture collapses toward `{X1,X2,X5,X6,X7?}`, `{X3}`, `{X4}`, `{X8}`. That five- or four-cluster view is E4-adjacent and should be reported as a sensitivity case, not as the main answer.

## 8. Limitations and recommendation

Use **E2 (typed structural, after local-id canonicalization)** for **compliance monitoring**. Substitution, shared invoices, partial settlement, and return cycles are control-relevant even when the activity word is boring. E1 will certify X7 against an X1 model. E3 is almost as good on *this* sample but is allowed to forget E2 distinctions that a future trace might still need (extra unused object, different but synonymous qualifier).

Use **E3 (business-semantic motifs)** for **operational segmentation**. It is the coarsest relation that still separates planned split boxes, planned split ships, shared logistics, shared finance, hidden substitution, and returns. Those are different staffing, carrier, and customer-communication plays. E2’s extra fineness does not change actions on X1–X8; E1’s coarseness does.

Use **E2 plus retained attributes/qualifiers (do not fold into E3)** for **root-cause analysis**. Causes live in the edges E3 throws away: which item was removed, which external order shared the carton, which payment completed settlement. After a cluster is chosen, inspect the E2 graph, not the motif name.

Use **a deliberately coarser fold of E3** — or even E1 with a flag for “has return / has EXT / has installment” — for **descriptive reporting**. Executives need five pictures, not seven isomorphic variants. A reporting fold that is honest: Isolated single-ship (X1,X2), Isolated multi-box one-van (X3), Isolated multi-ship (X4), Cross-order (X5,X6 distinguished in a footnote), Exception (X7,X8 distinguished in a footnote).

No single notion wins all four jobs. E1 is reproducible and cheap but not object-centric: it cannot see sharing, substitution, or the difference between two boxes and two vans. E2 is the right mathematical backbone and the right API to wrap around `cluster_equivalent_ocel`, but it over-segments as soon as extraction noise, unused objects, or synonymous qualifiers appear, and it is unreadable in a management report. E3 is the decision-oriented quotient of E2; it is only as good as the motif vocabulary, which is hand-designed and must be revised when a new exception (credit memo, split invoice, lost package) enters the log. E4 is a robustness tool, not a destination.

The working practice is therefore layered: canonicalize local identifiers → exact E2 clusters via PM4Py → E3 signatures for names and segmentation → purpose-specific folds for reports → never go back to raw ids or to activity words alone when objects and qualifiers were in the data.
