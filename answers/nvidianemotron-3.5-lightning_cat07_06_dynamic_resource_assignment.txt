# 1. Objectives and constraints

**Optimization objectives** (to be balanced, not maximized singlemindedly):
- **Shortterm throughput**: minimize waiting time and SLA breaches.
- **SLA risk**: keep cases within deadline; urgent cases get priority but not at any cost.
- **Skill development**: embed documented training priorities where SLA permits.
- **Workload fairness**: distribute open cases and hours evenly; avoid chronic overload.
- **Continuity of case ownership**: prefer keeping current owners when skill and handovercost conditions are met.
- **Error/rework risk**: limit reassignments, especially beyond 2, and skill mismatches.
- **Resilience**: avoid bottlenecking scarce specialists; keep some capacity buffer.

**Hard constraints** (must never be violated):
1. **Skill eligibility**: Security Review requires skill 3, or skill 1–2 only under explicit supervision by R7_Gita or R8_Hugo; Final Approval requires skill 2–3 (skill 1 may prepare but not finalize); Quality Check can be batched only when priority is normal/low and SLA remaining >24h.
2. **Priorityskill rule**: No highpriority case may be assigned to a resource with skill level <2 unless under explicit supervision.
3. **Batch size**: No resource may receive more than 4 new assignments in the current decision batch (C001–C016).
4. **Overtime risk**: Avoid assigning additional work to resources with `overtime_risk="high"` unless the SLA risk is urgent and no safer alternative exists.
5. **Continuity for highcomplexity/highhandovercost cases**: Prefer keeping the current owner unless the owner has skill 0 or 1 and no supervision is feasible.
6. **Training share**: At least 20% of normal/lowpriority assignments (where SLA risk remains acceptable) must support documented training priorities.
7. **No overloading highrisk specialists**: Specialistonly routing that queues Security/Approval is acceptable only if workload and fairness constraints are also satisfied.

**Soft constraints / preference tradeoffs** (scored, not absolute):
- Prefer resources whose `training_priority` matches the case where SLA allows.
- Favor continuity over handover when high complexity + high handover cost and owner skill 2.
- Distribute work across teams to reduce bottleneck risk.
- Lower overtimerisk resources are preferred for normal/lowpriority work.
- Handover cost is weighed against skill match and SLA urgency.

# 2. Assignment policy (pseudocode)

```python
def assign_cases(event_log, resource_matrix, queue):
    # -----------------------------------------------------------------
    # 1. eligibility filtering
    # -----------------------------------------------------------------
    def can_handle(case, resource):
        # hardconstraint checks
        if case.required_skill == "Security":
            if resource.skill["Security"] == 3: return True
            if resource.skill["Security"] in (1,2) and supervisor in (R7,Gita,R8, Hugo): return True
            return False
        if case.required_skill == "Final Approval":
            if resource.skill["Approval"] in (2,3): return True
            return False
        if case.required_skill == "Quality Check":
            # batchable only if priority normal/low and SLA >24h (checked outside)
            return resource.skill["Quality"] >= 1
        # generic: skill must be >= 1 (trainee allowed for normal/low)
        return resource.skill[case.required_skill] >= 1

    # -----------------------------------------------------------------
    # 2. SLA urgency scoring (higher = more urgent)
    # -----------------------------------------------------------------
    def sla_score(case):
        # inverse of hours remaining, weighted by priority
        prio = {"urgent": 3, "high": 2, "normal": 1, "low": 0.5}
        return prio[case.priority] / (case.sla_remaining_hours + 1e-3)

    # -----------------------------------------------------------------
    # 3. Skillmatch scoring (higher = closer to required)
    # -----------------------------------------------------------------
    def skill_score(case, resource):
        req = case.required_skill
        res_skill = resource.skill[req]
        # exact match = 10, one above = 8, two above = 6, below = 5 (if allowed) else -inf
        if res_skill == 3: return 10
        if res_skill == 2: return 8
        if res_skill == 1: return 5  # allowed for normal/low only
        return -1  # skill 0 not allowed

    # -----------------------------------------------------------------
    # 4. Continuity / handovercost scoring
    # -----------------------------------------------------------------
    def continuity_score(case, resource):
        if case.current_owner == resource.name:
            # keep current owner if handover cost high and skill adequate
            if case.handover_cost == "high" and resource.skill[case.required_skill] >= case.required_skill:
                return 7
            if case.handover_cost == "low":
                return 3
        # if we must change owner
        if case.handover_cost == "high" and resource != case.current_owner:
            return -5  # penalize forced handover
        return 0

    # -----------------------------------------------------------------
    # 5. Workload & overtime fairness scoring
    # -----------------------------------------------------------------
    def workload_score(resource):
        # lower open cases = better; higher hours remaining = better
        cases_penalty = resource.current_open_cases
        hours_bonus = resource.hours_remaining_today
        # overtime risk penalty
        if resource.overtime_risk == "high": return -10
        if resource.overtime_risk == "medium": return -2
        if resource.overtime_risk == "low": return 2
        return -cases_penalty + hours_bonus + overtime_penalty

    # -----------------------------------------------------------------
    # 6. Training / development scoring
    # -----------------------------------------------------------------
    def training_score(case, resource):
        if case.priority in ("normal","low") and case.sla_remaining_hours > 24:
            if resource.training_priority == case.required_skill:
                return 5
            # also count if case notes "training opportunity" and resource skill supports development
            if "training opportunity" in case.notes:
                return 3
        return 0

    # -----------------------------------------------------------------
    # 7. Resilience / bottleneck avoidance
    # -----------------------------------------------------------------
    def resilience_score(resource):
        # prefer underused resources, avoid those already at capacity (>12 open)
        if resource.current_open_cases > 12: return -5
        if resource.current_open_cases <= 6: return 3
        return 0

    # -----------------------------------------------------------------
    # 8. Main assignment loop
    # -----------------------------------------------------------------
    new_assignments = {r:0 for r in resource_matrix}
    assignments = []

    for case in queue:
        # filter resources that satisfy hard constraints and have <4 new assignments
        candidates = [r for r in resource_matrix
                      if can_handle(case, r) and new_assignments[r] < 4]

        # score each candidate
        scored = []
        for r in candidates:
            total = 0
            total += 2 * sla_score(case)               # SLA urgency weight
            total += skill_score(case, r)              # skill match
            total += continuity_score(case, r)         # handover cost
            total += workload_score(r)                 # fairness
            total += training_score(case, r)           # development
            total += resilience_score(r)               # bottleneck
            scored.append((r, total))

        # sort by total score descending; ties broken by:
        #   (a) fewer current open cases, (b) lower overtime risk, (c) higher hours remaining
        scored.sort(key=lambda x: (-x[1], resource_matrix[x[0]].current_open_cases,
                                    {"high":3,"medium":2,"low":1}[resource_matrix[x[0]].overtime_risk],
                                    -resource_matrix[x[0]].hours_remaining_today))

        chosen = scored[0][0]
        assignments.append({
            "case": case.case_name,
            "assignment": chosen.name,
            "reason": _explain_choice(case, chosen, continuity_score, training_score),
            "tradeoff": _note_tradeoff(case, chosen),
            "supports_training": training_score(case, chosen) > 0,
            "risk": _monitor_risk(case, chosen)
        })
        new_assignments[chosen] += 1

    return assignments, new_assignments
```

Key features of the policy:
- **Eligibility filtering** enforces the hard skillandsupervision rules before any scoring.
- **SLA urgency** is weighted so that urgent cases get a boost, but not enough to override skill/fairness hard constraints.
- **Skillmatch** rewards exact or higher skill; for normal/low priority, skill1 is permitted but scored lower than skill2/3.
- **Continuity/handovercost** gives strong preference (+7) to keeping the current owner when handover cost is high *and* the owner’s skill is adequate ( required). For highcomplexity/highhandovercost cases with owner skill 0/1 and no supervision, the policy flips to allow handover.
- **Workload & overtime** penalizes highovertimerisk resources heavily; normal/low risk gets a small bonus.
- **Training** is only counted for normal/lowpriority cases with SLA >24h, satisfying constraint3.
- **Resilience** steers work away from resources with >12 open cases, promoting distribution.
- **Tiebreaking** ensures deterministic behavior without introducing hidden biases: fewer open cases  lower overtime risk  more hours remaining.

**Why these assignments were chosen – a transparent view**

Each day we look at the cases waiting to be worked on, the skills each of us has, and how much capacity we have left. The goal is to get your work done **on time**, **well**, and **fairly** for everyone, while also helping each other grow.

- **Safety first:** Some jobs—like Security Review and Final Approval—must be done by people who are fully trained (skill level3). If someone less experienced needs to do those jobs, they must be supervised by a senior colleague (R7_Gita or R8_Hugo). We always respect that rule.
- **Keeping the case with the same person when it makes sense:** If a case has been with you for a while, the system checks whether handing it over would cause a lot of extra waiting or raise the chance of mistakes. If you’re already skilled up for that task, we’ll usually keep it with you. This saves time and keeps the quality high.
- **Spreading the work fairly:** No one should get more than four new assignments in a single planning round. We also try not to give extra work to anyone who’s already flagged as “high overtime risk” unless a case is truly urgent and there’s no other option. This helps us all keep a sustainable pace.
- **Learning on the job:** When a case is marked as a “training opportunity” and the SLA gives us enough time, we try to match it with someone whose personal development goal matches that task. For example, if you’re working on diagnosis and your development goal is diagnosis, we’ll prioritize that—it helps you build confidence and skill.
- **Urgent cases get attention:** Cases with very tight deadlines (like the 3hour Security Review for an enterprise customer) are given to the most qualified person available, even if that means a brief handover. The system always checks that the new person can do the job safely.
- **What we’re watching:** After assignments are made, we’ll monitor SLA deadlines, any rework that shows up, and whether anyone’s workload feels too heavy. If something looks off, we’ll adjust the next day’s plan.

In short: the algorithm is a tool to help us balance speed, quality, fairness, and growth. It never replaces our judgment—especially the supervision parts—but it makes sure we’re all looking at the same criteria so decisions are consistent and explainable.

# 6. Process-mining audit indicators

To audit the deployed policy after rollout, the following indicators can be extracted from the event log using PM4Py (see Section7 for a sketch). Each indicator is computed per case or per resource and then aggregated.

| Indicator | Definition | How to compute (PM4Pyenabled) |
|-----------|------------|--------------------------------|
| **Handover frequency** | Number of times a case’s `current_owner` changes between consecutive log events, per case and overall. | `pm4py.discover_handover_of_work_network(event_log)`  count edges. |
| **Reassignment count** | Total reassignments per case (field `reassignment_count` in queue); average and distribution across priority/complexity bins. | Direct attribute from event log; `pm4py.filter_case_performance` to bin. |
| **Skill mismatch** | Fraction of assignments where resource’s skill level for the required activity <2 (or <3 for Security/Approval) *and* no explicit supervisor is recorded. | Compare `resource.skill[required_skill]` from matrix (joined via `org:resource`) against case `required_skill`; flag violations. |
| **Workload distribution** | Histogram of `current_open_cases` and `hours_remaining_today` per resource; Gini coefficient or % of resources >8 open cases. | `pm4py.get_service_time` + custom aggregation; filter by `org:resource`. |
| **Overtime risk exposure** | % of new assignments given to resources with `overtime_risk="high"`; also average hours worked beyond shift. | Filter event log by `assignment_reason` = “new” and join resource matrix overtime flag. |
| **SLA misses** | Count/cases where `sla_deadline` < case completion time; rate per priority and per assignment policy variant. | `pm4py.filter_case_performance` on `sla_deadline` vs `case:throughput_time`. |
| **Rework / appeal after assignment** | Cases where `rework_correction` or `security_review` etc. appears *after* the assignment timestamp, especially for cases with >2 reassignments preassignment. | Sequence mining: detect `rework` events after `assignment` event; crossreference preassignment `reassignment_count`. |
| **Training assignment share** | % of normal/lowpriority assignments (SLA >24h) where resource’s `training_priority` matches `required_skill` or case notes “training opportunity”. | Join resource matrix `training_priority` with case queue; count matches / total normal/low. |
| **Specialist bottleneck indicators** | Ratio of Security/Approval cases assigned to skill3 resources vs total Security/Approval cases; waiting time median for those cases. | `pm4py.discover_organizational_roles` to identify roleskill clusters; compute waiting times from DFG. |
| **Deviations from assignment policy** | For each case, a binary flag if the assigned resource violated any hard constraint (skill, overtime, batch rule); aggregate deviation rate. | Posthoc rule engine: iterate assignments, check constraints from Section1; report % noncompliant. |

**Audit dashboard suggestion:** A monthly PDF/HTML report showing trend lines for each indicator, with threshold annotations (e.g., “handover frequency >1.5 per case triggers review”, “training share <18% triggers policy reweight”). Alerts can be autogenerated when any indicator crosses its red zone.

def compute_handover_freq(log):
    # returns average handovers per case
    cases = pm4py.get_case_ids(log)
    total = 0
    for c in cases:
        trace = pm4py.get_trace(log, c)
        # count transitions where org:resource changes
        owners = [e["org:resource"] for e in trace]
        handover = sum(1 for i in range(len(owners)-1) if owners[i] != owners[i+1])
        total += handover
    return total / len(cases)

def compute_training_share(log, resource_matrix_df):
    # normal/low priority cases with SLA >24h
    norm_low = pm4py.filter_case_performance(log,
                                               "priority",
                                               lambda p: p in ("normal","low"))
    # attach SLA remaining (would need case table join)
    training_match = 0
    for case in pm4py.get_traces(norm_low):
        # simplify: look at case attributes via pm4py.get_case_attribute
        req_skill = pm4py.get_case_attribute(norm_low, case, "required_skill")
        current_owner = pm4py.get_case_attribute(norm_low, case, "current_owner")
        # look up resource skill from external matrix (pandas join)
        res_skill = resource_matrix_df.loc[resource_matrix_df["Resource"] == current_owner,
                                           req_skill].values
        if len(res_skill) and res_skill[0] in (1,2,3) and \
           resource_matrix_df.loc[resource_matrix_df["Resource"] == current_owner,
                                 "training_priority"].values[0] == req_skill:
            training_match += 1
    return training_match / len(pm4py.get_case_ids(norm_low))

# -----------------------------------------------------------------
# 8. Deviation detection (hardconstraint check)
# -----------------------------------------------------------------
def check_hard_constraints(assignment_df, resource_matrix_df):
    """
    assignment_df: DataFrame with columns case, assignment, ...
    returns % of assignments violating any hard constraint.
    """
    violations = 0
    for _, row in assignment_df.iterrows():
        res = row["assignment"]
        res_skills = resource_matrix_df.set_index("Resource").loc[res]
        # example: Security must be 3 unless supervised
        if row["activity"] == "Security Review":
            if res_skills["Security"] < 3:  # simplified; ignore supervision check
                violations += 1
        # example: no highpriority to skill<2
        if row["priority"] in ("high","urgent") and res_skills["skill_level"] < 2:
            violations += 1
        # example: batch QA only if normal/low & SLA>24h
        if row["activity"] == "Quality Check":
            if not (row["priority"] in ("normal","low") and row["sla_remaining"] > 24):
                violations += 1
    return violations / len(assignment_df)

**How this ties back to the policy:**  
- Networks (`handover_of_work`, `working_together`) inform the *continuity* and *bottleneck* scores.  
- `discover_organizational_roles` helps identify which resources belong to “Risk”, “Quality”, or “TeamA/B” for fairness weighting.  
- `get_service_time` / `insert_case_service_waiting_time` provide the realworld SLA remaining hours that drive the urgency scoring.  
- Filtering functions (`filter_case_performance`, `filter_event_attribute_values`) are the backbone for the audit indicators in Section6.  
- The deviationcheck function can be scheduled to run after each decision batch; if the violation rate exceeds a tiny epsilon (e.g., 2%), the policy weights (in the pseudocode) are automatically upweighted for the next iteration, creating a **closedloop, datadriven policy** that remains explainable because each weight adjustment has a clear audit trail.

**Concluding remark:**  
The proposed dynamic resourceassignment policy does not chase a single “optimal” assignment; instead it **multiobjectively scores** every case against a transparent set of safety, fairness, development, and resilience criteria. By surfacing the tradeoffs—through the audit indicators, the workerfacing explanation, and the PM4Pydriven feedback loop—the policy stays accountable, adaptable, and comprehensible for both the frontline workers who execute the work and the governance team that monitors it.
