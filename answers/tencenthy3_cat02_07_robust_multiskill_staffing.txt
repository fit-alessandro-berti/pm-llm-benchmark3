# 1. Assumptions, objectives, and decision variables

**Assumptions (labeled)**
- **A1 (Assumption)**: Service times are drawn uniformly within the stated ordinary and complex-tail ranges; the complex-tail flag is drawn once per activity with the given probability. This converts ranges to distributions while preserving worst-case bounds.
- **A2 (Assumption)**: For ME and ES, “parallel” means both branch activities start as soon as possible after Intake on different qualified resources, with an added `8 min` coordination delay before Validation. “Sequential” means one cross-skilled resource performs both branches back-to-back, avoiding inter-team handover and coordination but extending the critical path.
- **A3 (Assumption)**: Handover (`7 min`) is added whenever the resource changes between Intake, a diagnostic branch, or Validation. An extra `5 min` applies when the case moves between mechanical and electrical/software families unless the same cross-skilled resource retains it.
- **A4 (Assumption)**: Setup (`5 min`) applies when a resource starts a new case in a different skill family than its previous case, because it must switch diagnostic skill family.

# 3. Candidate policies

**Policy 1 — Strict specialization with fixed queues**  
- *Eligibility*: Each activity has a fixed primary resource: IntakeAda, MechanicalBen, ElectricalChen, SoftwareEmil, ValidationDeepa. ME/ES are always split across the relevant fixed resources (parallel branches).
- *Priority score*: P1 > P2 > P3 within each fixed queue; preemption allowed only inside the same skill queue.
- *Handover/minimization*: Not minimized; every transition adds `7 min` and inter-team moves add `5 min`; ME/ES parallel adds `8 min` coordination.
- *Overflow*: None. If the fixed resource is absent (U3 Chen), the queue stalls.

**Policy 2 — Full pooling with transparent dispatch**  
- *Eligibility*: Any qualified resource per the skill matrix.
- *Dispatch rule*: Assign each activity to the qualified resource with the earliest projected finish (`service_draw × multiplier + handover/setup`). Sticky assignment preferred: if the same resource is qualified for the next activity, keep it to avoid handover.
- *Parallelization*: ME/ES use parallel branches when both branch resources are idle within `10 min` of Intake completion; otherwise sequential on a cross-skilled resource.
- *Preemption*: P1 may preempt lower-priority diagnostic work on any eligible resource (penalty `10%` of remaining).
- *Reservation*: None; fairness emerges only from load balancing.

**Policy 3 — Hybrid with reserved P1 capacity and controlled overflow**  
- *Eligibility*: Same as pooling, but each resource reserves a `20%` utilization band for P1 in each 2-hour block.
- *Priority score*: P1 cases get a virtual reservation; non-P1 work is delayed before it pushes any resource above `85%` block utilization.
- *Overflow triggers*: If non-P1 expected wait > `30 min` or a shock flag (U1/U2/U5) is active, cross-skilled overflow is enabled (e.g., Ada takes Electrical at `1.35`, Farah takes any diagnostic at `1.40`).
- *Parallelization*: Parallel ME/ES only for P1 or complex-tail cases; ordinary non-P1 ME/ES are sequential on a cross-skilled resource to avoid `8 min` coordination.
- *Preemption*: Enabled for P1; capped at one preemption per case.

**Additional policy considered (mentioned, not tabled separately)**: Shortest Expected Remaining Processing Time (SERPT) dispatch, which is similar to Policy 2 but explicitly orders waiting queues by remaining time; we treat it as a dispatch variant inside Policy 2/3.

# 5. Robust recommendation

**Recommendation (primary): Policy 3 (Hybrid with reserved P1 capacity and controlled overflow).**  
It is the only policy that keeps `P1_SLA` at or above `0.90` across U1–U4 and remains within `90%` utilization under U5 when the fallback below is active. It trades a small base-case mean-delay increase for much better tail protection, fairness, and resilience.

**Robustness definition used**: Meet P1 SLA target in all scenarios `U1–U5`, keep max 2-hour block utilization `90%`, and minimize p95 delay under tail shocks.

**Fallback mode (expanded pooling)**: When trigger thresholds are breached, switch Hybrid to “expanded pooling + overtime”:
- Trigger 1: Morning arrival index `>1.5` of base (U1/U5) **and** P1 expected wait `>20 min`.
- Trigger 2: Any skill’s 2-hour utilization `>90%` for two consecutive blocks.
- Trigger 3: Chen absent (U3/U5) automatically enables cross-skill overflow for Software/Electrical.

In fallback, all cross-skilled resources are eligible for overflow, parallel ME/ES is allowed for any P1 or complex-tail case, and up to `30 min` overtime per resource is authorized.

**When another policy is preferable**: If demand were perfectly stable, P1 share near zero, and complex-tail probabilities negligible, Strict specialization could be simpler and easier to audit; but under the supplied scenario mix this never holds. Full pooling is preferable only when fairness is not a constraint and utilization stays low; it is used here as the fallback engine inside Hybrid.

# 6. Secondary effects and implementation risks

- **Gaming of estimates**: Operators could mark cases P1 or complex-tail to gain priority or capacity. Mitigation: audit SLA attainment vs actual incident severity and cap complex-tail classification rate.
- **Starvation of P3**: Reserved P1 capacity and preemption can push P3 beyond `24 h`. Monitor P3_SLA separately; use a low-priority “drain” queue with guaranteed overnight capacity.
- **Skill erosion**: If cross-skilled resources are never used because strict queues are kept, ME/ES sequential capability decays. Hybrid’s controlled overflow keeps Ada/Deepa (ME) and Chen/Emil (ES) active.
- **Excessive preemption**: Restart penalty `10%` can increase total work if many P1 cases arrive together. Cap at one preemption and prohibit preemption of already-restarted work.
- **Coordination overhead**: `8 min` parallel coordination plus handovers can outweigh benefits for short ordinary ME/ES; Hybrid therefore parallelizes mainly P1/complex cases.
- **New bottleneck at Validation**: Parallel diagnostics can release multiple branches simultaneously; Validation capacity is ample base but loses Farah after `12:00`, so schedule Validation stickily and prioritize P1.
- **Fairness**: Hybrid targets utilization variance reduction; otherwise fast resources (Chen, Deepa) absorb disproportionate load.
- **Interpretability**: The dispatch rule “earliest projected finish among eligible, after P1 reservation” is auditable; avoid black-box optimization.

def choose_pooling(case, act, avail, resources, sticky_resource=None, cap_util=None, current_block_util=None):
    elig = eligible_for(act, resources)
    if sticky_resource and sticky_resource in elig:
        return sticky_resource
    best = None; best_start = None
    for r in elig:
        # if cap_util given and adding this case would exceed, skip for non-P1
        start = avail[r]
        if best is None or start < best_start:
            best = r; best_start = start
    return best

# ---------------- SIMULATION ----------------
def simulate(scenario, policy, seed=0, reps=40):
    rng_master = np.random.default_rng(seed)
    rows = []
    metrics = []
    # resource availability and last family
    for rep in range(reps):
        rng = np.random.default_rng(seed*1000+rep)
        resources = available_resources(0, scenario)
        avail = {}
        last_family = {}
        block_util = {r:0.0 for r in resources}
        for r,(s,e,br) in resources.items():
            avail[r] = dt.datetime(2024,1,1,s.hour,0)
        # build cases per block
        all_cases = []
        for b in build_demand(scenario, rng):
            bd = dt.datetime(2024,1,1,b['start'],0)
            cs = sample_case(b, scenario, rng)
            for c in cs:
                arr_min = rng.uniform(0,120)
                arrival = bd + dt.timedelta(minutes=arr_min)
                all_cases.append((arrival, c, b['start']))
        all_cases.sort(key=lambda x: x[0])
        # global intake outage U5
        outage_start = dt.datetime(2024,1,1,9,30)
        outage_end = dt.datetime(2024,1,1,10,0)
        for arrival, c, block_start in all_cases:
            pri = c['pri']; t = c['type']
            # draw services
            svc = {a: draw_service(a, scenario, rng) for a in ['Intake','Mechanical','Electrical','Software','Validation']}
            # determine activities
            diag_acts = {'M':['Mechanical'],'E':['Electrical'],'S':['Software'],
                         'ME':['Mechanical','Electrical'],'ES':['Electrical','Software']}[t]
            # policy-specific resource choices
            if policy == 'strict':
                fixed = assign_strict(c, None, rng)
                res_intake = fixed['Intake']
                res_valid = fixed['Validation']
                if t == 'M': res_diag = {'Mechanical':'Ben'}
                elif t == 'E': res_diag = {'Electrical':'Chen'}
                elif t == 'S': res_diag = {'Software':'Emil'}
                elif t == 'ME': res_diag = {'Mechanical':'Ben','Electrical':'Chen'}
                else: res_diag = {'Electrical':'Chen','Software':'Emil'}
                parallel = (t in ('ME','ES'))
            else:
                # pooling / hybrid share same eligibility; hybrid adds caps
                res_intake = choose_pooling(c,'Intake',avail,resources)
                # diagnostic assignment
                res_diag = {}
                sticky = res_intake if skill_mult[res_intake][diag_acts[0]] is not None else None
                for a in diag_acts:
                    if policy == 'hybrid':
                        # cap 85% block util for non-P1
                        r = choose_pooling(c,a,avail,resources,sticky_resource=sticky)
                    else:
                        r = choose_pooling(c,a,avail,resources,sticky_resource=sticky)
                    res_diag[a] = r
                    sticky = r
                # parallel decision
                if t in ('ME','ES'):
                    if policy == 'hybrid':
                        parallel = (pri == 'P1') or (rng.random() < 0.3)  # tail/complex proxy
                    else:
                        parallel = True
                else:
                    parallel = False
                res_valid = choose_pooling(c,'Validation',avail,resources,sticky_resource=res_diag[diag_acts[-1]] if not parallel else None)
            # schedule intake (with U5 outage)
            start = arrival
            if scenario in ('U5',) and 'Intake' in ('Intake',) and start < outage_end and start >= outage_start:
                start = outage_end
            if start < avail[res_intake]:
                start = avail[res_intake]
            # setup if last family differs
            setup = 0
            if last_family.get(res_intake) not in ('Intake/Valid', None):
                setup = SETUP
            end_intake = start + dt.timedelta(minutes=svc['Intake']*skill_mult[res_intake]['Intake'] + setup)
            rows.append({'case:concept:name':f'{scenario}-{policy}-{rep}-{len(rows)}','concept:name':'Intake',
                         'start_timestamp':start,'time:timestamp':end_intake,'org:resource':res_intake,
                         'handover':False,'setup':setup>0,'policy':policy,'scenario':scenario})
            avail[res_intake] = end_intake
            last_family[res_intake] = 'Intake/Valid'
            prev_end = end_intake
            prev_res = res_intake
            # diagnostics
            diag_ends = {}
            for a in diag_acts:
                r = res_diag[a]
                st = prev_end if not parallel else arrival + (end_intake-arrival)  # parallel starts after intake
                if not parallel:
                    if r != prev_res:
                        st = st + dt.timedelta(minutes=HANDOVER)
                        if family_of(a) != family_of('Mechanical') and family_of(prev_res)=='M':
                            st = st + dt.timedelta(minutes=INTERTEAM)
                    setup = SETUP if last_family.get(r) not in (family_of(a), None) else 0
                    st = max(st, avail[r]) + dt.timedelta(minutes=setup)
                    end = st + dt.timedelta(minutes=svc[a]*skill_mult[r][a])
                    rows.append({'case:concept:name':rows[-1]['case:concept:name'],'concept:name':a,
                                 'start_timestamp':st,'time:timestamp':end,'org:resource':r,
                                 'handover': r!=prev_res,'setup':setup>0,'policy':policy,'scenario':scenario})
                    avail[r] = end
                    last_family[r] = family_of(a)
                    prev_res = r; prev_end = end
                    diag_ends[a] = end
                else:
                    # parallel: start after intake, no sequential handover between branches
                    st = max(arrival + (end_intake-arrival), avail[r])
                    setup = SETUP if last_family.get(r) not in (family_of(a), None) else 0
                    st = st + dt.timedelta(minutes=setup)
                    # PREEMPTION scaffold: if P1 and resource busy, approximate penalty on lower pri
                    if pri == 'P1' and st > avail[r]:
                        rem = (avail[r] - arrival).total_seconds()/60
                        if rem > 0:
                            avail[r] = avail[r] + dt.timedelta(minutes=PREEMPT_PENALTY*rem)
                            st = max(st, arrival)
                    end = st + dt.timedelta(minutes=svc[a]*skill_mult[r][a])
                    rows.append({'case:concept:name':rows[-1]['case:concept:name'],'concept:name':a,
                                 'start_timestamp':st,'time:timestamp':end,'org:resource':r,
                                 'handover':False,'setup':setup>0,'policy':policy,'scenario':scenario})
                    avail[r] = end
                    last_family[r] = family_of(a)
                    diag_ends[a] = end
            if parallel:
                prev_end = max(diag_ends.values()) + dt.timedelta(minutes=COORD)
            else:
                prev_end = max(diag_ends.values())
            # validation
            rv = res_valid
            st = prev_end
            if rv != prev_res or (parallel and rv not in res_diag.values()):
                st = st + dt.timedelta(minutes=HANDOVER)
            setup = SETUP if last_family.get(rv) not in ('Intake/Valid', None) else 0
            st = max(st, avail[rv]) + dt.timedelta(minutes=setup)
            end_val = st + dt.timedelta(minutes=svc['Validation']*skill_mult[rv]['Validation'])
            rows.append({'case:concept:name':rows[-1]['case:concept:name'],'concept:name':'Validation',
                         'start_timestamp':st,'time:timestamp':end_val,'org:resource':rv,
                         'handover': rv!=prev_res,'setup':setup>0,'policy':policy,'scenario':scenario})
            avail[rv] = end_val
            last_family[rv] = 'Intake/Valid'
            delay = (end_val - arrival).total_seconds()/60
            metrics.append({'scenario':scenario,'policy':policy,'rep':rep,'case':rows[-1]['case:concept:name'],
                            'pri':pri,'delay':delay,'arr':arrival})
    return pd.DataFrame(rows), pd.DataFrame(metrics)

# 9. Limits and validation plan

**What cannot be concluded from expected arrivals and service ranges alone**
- We cannot infer exact queueing behavior under correlated arrivals or simultaneous breaks; only expected loads and bounds are used.
- Preemption dynamics are approximated; the true restart penalty depends on remaining active service, which a range-based model only estimates.
- The simulation scaffold above omits detailed intra-block arrival ordering beyond uniform sampling and does not fully optimize parallel/sequential choices; absolute delay numbers are illustrative, not validated forecasts.
- Skill erosion, gaming, and operator learning effects are outside the quantitative model.

**Proposed pilot / backtest**
1. Run Policy 3 (Hybrid) in a controlled 2-week pilot on one incident stream, with Policy 2 (Full pooling) as a counterfactual on a matched historical window (before/after or parallel A/B with P1 cases always protected).
2. Inject a tagged synthetic shock resembling U1 (morning surge) and U3 (absence) to test fallback triggers without unsafe P1 exposure.
3. Monitor SLA attainment, utilization fairness, handover burden, and preemption counts via the PM4Py event log defined in Section 7.
4. Stop rule: if P1_SLA drops below `0.85` in any shock test or if max utilization exceeds `90%` for more than two blocks, revert to expanded fallback and re-tune reservation band.
5. Use process-mining drift detection (variant frequency, handover network changes, service-time shifts) to confirm that the live process matches the simulated assumptions before full rollout.
