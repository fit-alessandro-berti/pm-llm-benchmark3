## 1. Equivalence design space

### 1.1 Activity-sequence equivalence, ASEQ

**Definition.** Two executions are ASEQ-equivalent if their ordered activity labels, with multiplicities, are identical. Operationally, sort events by timestamp. If events share a timestamp, treat that timestamp as a bucket and compare multisets of activity labels inside the bucket. If a total order is required, impose a deterministic tie-break, but the cleaner definition is timestamp-bucketed.

**Preserved invariants.** Activity labels, repetition counts, and timestamp buckets.

**Discarded information.** Object types, object identifiers, external-object flags, E2O incidence, O2O qualifiers, object multiplicities, and all business roles.

**Equivalence properties.** Reflexive, symmetric, and transitive by equality of sequences/multisets.

**Concurrency handling.** Same-time events are unordered. This avoids inventing a causal order from identical timestamps.

ASEQ is useful as a coarse sanity check, but it is not object-centric by itself because it ignores the objects that make the execution object-centric.

### 1.2 Typed structural equivalence, TSE

**Definition.** Build a labeled execution graph. Event nodes are labeled by activity and timestamp rank or partial-order level. Object nodes are labeled by object type, external flag, and lead-object flag. E2O edges connect events to objects and preserve multiplicity. O2O qualifiers are treated as typed object-object edges, for example `packs`, `carries`, `bills`, `settles`, `partial_settles`, `replaces`, and `removed_before_dispatch`. Two executions are TSE-equivalent if their graphs are isomorphic under renaming of local object identifiers. External identifiers are not preserved as identities; only their type, external flag, and local role are preserved.

**Preserved invariants.** Object types, event labels, event multiplicities, E2O incidence, O2O qualifier labels, external flags, and event partial order.

**Discarded information.** Local identifier values, absolute timestamps, external object lifecycles outside the lead Order, and attribute values not represented in labels.

**Equivalence properties.** Reflexive, symmetric, and transitive because graph isomorphism is an equivalence relation.

**Concurrency handling.** Use a partial order: strictly earlier events may constrain later events, while same-time events are incomparable. If a total order is required, use timestamp ranks plus a deterministic tie-break.

TSE is finer than business semantics but coarser than raw identifier equality. It catches structural differences such as an extra Item in Dispatch, an external Order in Invoice, or two Payment events.

### 1.3 Business-semantic equivalence, BSE

**Definition.** BSE is the preferred relation used in the cluster table. Two executions are BSE-equivalent if they have the same lead object type and the same business motif vector:

- `sharing`: `ISOLATED`, `LOGISTICS_SHARED`, or `FINANCE_SHARED`;
- `packages`: number of local Package objects, plus whether repacking occurs;
- `deliveries`: number of Delivery objects;
- `settlement`: `SINGLE`, `STAGED`, or `SHARED_UNALLOCATED`;
- `exception`: `NONE`, `SUBSTITUTION`, or `RETURN_REPACK`.

A `Create Order` presence flag is recorded as a data-quality annotation but is not used to separate business clusters, because missing initialization is often a logging or repair issue rather than a distinct business process.

**Preserved invariants.** Lead Order role, external sharing domain, package/delivery cardinality, settlement motif, and exception motif.

**Discarded information.** Exact local identifiers, exact interleaving of independent Pack/Dispatch events, exact item-to-package partition beyond cardinality, payment amounts, and external object identities.

**Equivalence properties.** Reflexive, symmetric, and transitive because it is equality of a finite motif vector.

**Concurrency handling.** Only causal motifs matter: a Package must be packed before it is dispatched, and a returned item must be inspected before repacking. Independent Pack/Dispatch interleavings are ignored.

BSE is deliberately coarser than TSE. It groups executions by business behavior rather than by every structural detail.

## 2. Canonical signatures

The preferred BSE signature is computed from a lead-Order projection. Local identifiers are canonicalized by iterative role refinement, so renaming local objects does not change the signature. External objects are represented only by type, external flag, and local role.

```python
import hashlib
from collections import Counter, defaultdict

def h(x):
    return hashlib.sha256(repr(x).encode()).hexdigest()[:16]

def canonical_signature(exec, lead_type="Order"):
    events = sorted(
        exec.events,
        key=lambda e: (e.timestamp, e.activity, tuple(sorted(e.objects.items())))
    )

    objects = {}
    for e in events:
        for typ, ids in e.objects.items():
            for oid in ids:
                if oid not in objects:
                    objects[oid] = {
                        "type": typ,
                        "ext": oid.startswith("EXT"),
                        "lead": (typ == lead_type and not oid.startswith("EXT")),
                        "events": set(),
                    }
                objects[oid]["events"].add(id(e))

    qual_by_obj = defaultdict(list)
    for q in exec.qualifiers:  # q.id1, q.id2, q.label
        qual_by_obj[q.id1].append(q)
        qual_by_obj[q.id2].append(q)

    ts = sorted({e.timestamp for e in events})
    rank = {t: i for i, t in enumerate(ts)}

    obj_lab = {
        oid: h((o["type"], o["ext"], o["lead"], len(o["events"])))
        for oid, o in objects.items()
    }

    event_lab = {
        id(e): h((
            e.activity,
            rank[e.timestamp],
            tuple(sorted(Counter({t: len(ids) for t, ids in e.objects.items()}).items()))
        ))
        for e in events
    }

    for _ in range(20):
        new_obj = {}
        for oid, o in objects.items():
            evs = tuple(sorted(event_lab[eid] for eid in o["events"]))
            quals = tuple(sorted(
                h((q.label, tuple(sorted([obj_lab[q.id1], obj_lab[q.id2]]))))
                for q in qual_by_obj[oid]
            ))
            new_obj[oid] = h((o["type"], o["ext"], o["lead"], evs, quals))

        new_event = {}
        for e in events:
            objs = tuple(sorted(
                obj_lab[oid]
                for typ, ids in e.objects.items()
                for oid in ids
            ))
            new_event[id(e)] = h((e.activity, rank[e.timestamp], objs))

        if new_obj == obj_lab and new_event == event_lab:
            break
        obj_lab, event_lab = new_obj, new_event

    pkg = {
        oid
        for e in events
        if e.activity == "Pack Package"
        for t, ids in e.objects.items()
        if t == "Package"
        for oid in ids
    }
    dlv = {
        oid
        for e in events
        if e.activity == "Dispatch"
        for t, ids in e.objects.items()
        if t == "Delivery"
        for oid in ids
    }
    pay = [e for e in events if e.activity == "Record Payment"]
    inv = [e for e in events if e.activity == "Issue Invoice"]

    def has_ext(activities):
        for e in events:
            if e.activity in activities:
                for t, ids in e.objects.items():
                    for oid in ids:
                        if objects[oid]["ext"]:
                            return True
        return False

    ext_log = has_ext({"Pack Package", "Dispatch"})
    ext_fin = has_ext({"Issue Invoice", "Record Payment"})

    settle = (
        "STAGED"
        if len(pay) > 1 or any(
            q.label in {"partial_settles", "completes_settlement"}
            for q in exec.qualifiers
        )
        else "SHARED_UNALLOCATED" if ext_fin else "SINGLE"
    )

    exc = (
        "RETURN_REPACK"
        if any(e.activity in {"Return Item", "Inspect Return"} for e in events)
        else "SUBSTITUTION" if any(
            q.label in {"replaces", "removed_before_dispatch"}
            for q in exec.qualifiers
        )
        else "NONE"
    )

    share = (
        "LOGISTICS_SHARED" if ext_log
        else "FINANCE_SHARED" if ext_fin
        else "ISOLATED"
    )

    motif = (share, len(pkg), len(dlv), settle, exc)
    init_present = any(e.activity == "Create Order" for e in events)

    full = h((
        lead_type,
        tuple((
            e.activity,
            rank[e.timestamp],
            tuple(sorted(obj_lab[oid] for t, ids in e.objects.items() for oid in ids))
        ) for e in events),
        tuple(sorted(obj_lab.values())),
        motif,
    ))

    return motif, init_present, full
```

The BSE cluster key is `motif`. The `init_present` flag is a data-quality annotation. The `full` hash is useful for reproducibility and for a finer variant, but BSE equivalence uses the motif only.

## 4. Cluster interpretations

### S1 — Isolated single-package baseline

**Signature:** `(ISOLATED, 1, 1, SINGLE, NONE; init=Y)`

**Business behavior.** The Order is created, items are added, all items are packed into one Package, dispatched once, invoiced once, and paid once.

**Risks/opportunities.** Low operational risk. Good candidate for standardization, SLA baselining, and exception detection.

**Poor flattening.** Activity-label-only views are acceptable here, but object-centric views add value by confirming that one Package carries all items and one Payment settles the Invoice.

**Stability.** Stable under local renaming, minor timestamp jitter, and repair of missing or duplicated initialization events if the init flag is ignored.

### S2 — Isolated multi-package, consolidated delivery

**Signature:** `(ISOLATED, 2, 1, SINGLE, NONE; init=Y)`

**Business behavior.** The Order is split into multiple Packages, but all Packages are dispatched on one Delivery.

**Risks/opportunities.** Multi-box logistics, carrier consolidation, partial package damage, and package-level tracking are relevant. Opportunity: optimize split packaging and consolidated shipping.

**Poor flattening.** Collapsing to one Package or one activity sequence hides the split-packaging decision.

**Stability.** Stable if Package multiplicity is preserved. Renaming Packages or Items does not change the cluster.

### S3 — Isolated multi-package, split delivery, staged settlement

**Signature:** `(ISOLATED, 2, 2, STAGED, NONE; init=N)`

**Business behavior.** Packaging and dispatching are interleaved or separated into multiple deliveries, and settlement occurs through multiple Payments.

**Risks/opportunities.** Partial fulfillment, cash-flow timing, reconciliation complexity, and customer experience risk. Opportunity: installment billing, drop-shipping, or phased fulfillment.

**Poor flattening.** Counting only Packages hides split deliveries. Counting only activities hides staged settlement.

**Stability.** Stable if delivery and payment multiplicities are preserved. Adding a missing `Create Order` changes only the init flag, not the business cluster.

### S4 — Cross-order logistics sharing

**Signature:** `(LOGISTICS_SHARED, 1, 1, SINGLE, NONE; init=Y)`

**Business behavior.** The local Order’s Package and Delivery include external Order or Item objects, but the Invoice is local.

**Risks/opportunities.** Consolidated shipping, cross-order liability, inventory attribution, delivery disputes, and misattribution risk. Opportunity: shared logistics for related Orders.

**Poor flattening.** Projecting only local objects makes the execution look like a baseline single-package Order.

**Stability.** Stable under renaming of external identifiers if external flags and local roles are preserved. Ignoring external objects destroys the cluster.

### S5 — Cross-order financial sharing

**Signature:** `(FINANCE_SHARED, 1, 1, SHARED_UNALLOCATED, NONE; init=Y)`

**Business behavior.** The local Order’s logistics are isolated, but the Invoice and Payment are shared with an external Order, without explicit order-level allocation.

**Risks/opportunities.** Revenue recognition, payment allocation, auditability, and dispute resolution are central. Opportunity: group billing or consolidated invoicing.

**Poor flattening.** Local activity labels look like a normal paid Order, hiding shared financial responsibility.

**Stability.** Stable if external financial objects are preserved. Adding allocation would create a more refined subcluster but would not remove the shared-finance motif.

### S6 — Pre-dispatch substitution

**Signature:** `(ISOLATED, 1, 1, SINGLE, SUBSTITUTION; init=Y)`

**Business behavior.** An item is replaced or removed before dispatch. The Dispatch event references the replacement item, and qualifiers such as `replaces` or `removed_before_dispatch` explain the change.

**Risks/opportunities.** Billing accuracy, inventory consistency, customer communication, and regulatory compliance. Opportunity: controlled substitution workflow.

**Poor flattening.** Activity labels resemble the baseline, hiding that the shipped item set changed.

**Stability.** Stable if qualifiers or the extra Dispatch item incidence are preserved. If both are ignored, the execution may falsely merge with S1.

### S7 — Return and repack

**Signature:** `(ISOLATED, 2, 2, SINGLE, RETURN_REPACK; init=Y)`

**Business behavior.** An item is dispatched, returned, inspected, repacked, and dispatched again.

**Risks/opportunities.** Reverse logistics cost, inventory state uncertainty, double shipping, and customer satisfaction. Opportunity: RMA automation and quality inspection workflows.

**Poor flattening.** Counting only final deliveries may hide the return loop. Activity labels without object roles may obscure which item was repacked.

**Stability.** Stable if Return/Inspect events and repack relationships are preserved. Removing return events would incorrectly merge the execution into a multi-delivery or baseline cluster.

## 5. Borderline cases

### X1 versus X2

Exact identifier equality says they differ because `O1`, `I11`, etc. are not equal to `O2`, `I21`, etc. ASEQ, TSE, and BSE say they are equivalent because local renaming is ignored. A defensible disagreement arises if the order of `Add Item` events encodes item priority or customer preference; then a behavioral equivalence preserving item order could separate them. With only the supplied information, renaming-invariant equivalence is more meaningful.

### X1 versus X5

ASEQ merges them because the activity labels are identical. TSE separates them because X5 has external Order and Item objects in Pack/Dispatch. BSE separates them because X5 is `LOGISTICS_SHARED`. A coarser definition that ignores externality would merge them, but that hides cross-order logistics risk.

### X1 versus X6

ASEQ merges them. TSE separates them because X6 has an external Order in Invoice and Payment. BSE separates them because X6 is `FINANCE_SHARED` and `SHARED_UNALLOCATED`. A coarser definition could merge X5 and X6 as “shared external execution,” but it should not merge either with X1 if compliance cares about external financial objects.

### X1 versus X7

ASEQ merges them. TSE separates them because X7’s Dispatch includes an Item object and has replacement/removal qualifiers. BSE separates them because X7 has `SUBSTITUTION`. If qualifiers are ignored and the extra Dispatch item incidence is treated as incidental, a very coarse definition could merge them, but that would hide a material item-lifecycle change.

### X3 versus X4

ASEQ and TSE separate them because X4 has more Pack, Dispatch, and Payment events. BSE also separates them if delivery and settlement multiplicities are preserved. A coarser BSE that preserves only “multi-package” would merge them. The disagreement is meaningful: X3 is multi-package but operationally consolidated, while X4 involves split deliveries and staged payment.

### X4 versus X8

ASEQ and TSE separate them because their event sequences and object graphs differ. BSE can separate them by exception motif: X4 has no exception, while X8 has `RETURN_REPACK`. A very coarse definition focused only on “multiple deliveries” could merge them, but that would conflate staged payment with reverse logistics.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

`pm4py.cluster_equivalent_ocel` clusters object-centric executions using a key structure that preserves the raw OCEL identity fields used for equivalence: object type, object identifier, activity, timestamp or order position, and any retained attributes or relations. It does not infer business motifs such as shared finance, staged settlement, substitution, or return-repack.

Raw object identifiers make exact clusters too fine because every Order usually has a unique identifier. Two operationally identical Orders will not be equivalent if their identifiers differ. Therefore, exact PM4Py clusters should be treated as a starting point, not as the final business segmentation.

A useful workflow is:

1. Run `pm4py.cluster_equivalent_ocel` on the full OCEL.
2. Project each returned cluster to the lead `Order`.
3. Canonicalize local identifiers by role.
4. Preserve external flags, object types, multiplicities, and O2O qualifiers.
5. Compute the BSE motif signature.
6. Merge PM4Py clusters that share the same BSE motif.

Exact equivalence is preferable when the goal is replay, conformance checking, deduplication, regression testing, or identifying byte-for-byte identical execution patterns. Coarser business clustering is preferable for process mining, operational segmentation, and compliance monitoring.

`max_objs` matters because object-centric executions can become large when Packages, Deliveries, Invoices, or external Orders connect many cases. Large connected components make exact isomorphism expensive and can cause truncation or false non-equivalence. A lead-Order projection with external flags is usually more practical than trying to compare the full connected component.

## 7. Robustness analysis

### Ignore all O2O qualifiers

X7 loses its `SUBSTITUTION` motif and may merge with X1 if the extra Dispatch item incidence is also ignored. X4 loses explicit `partial_settles`/`completes_settlement` labels, but the two Payment events still distinguish it under ASEQ and TSE. If payment multiplicity is also ignored, X4 may merge with X3 or X1. X8 remains distinct because Return and Inspect events remain.

### Ignore external objects

X5 and X6 become indistinguishable from X1 under ASEQ and may merge under TSE if external incidence is removed. BSE loses `LOGISTICS_SHARED` and `FINANCE_SHARED`, so S4 and S5 collapse into S1. This is dangerous for compliance because cross-order logistics and financial sharing are hidden.

### Collapse repeated same-label events

X3’s two Pack events may collapse into one Pack. If Package multiplicity is also collapsed, X3 may merge with X1. If Package count is preserved, X3 remains S2. X4’s repeated Pack, Dispatch, and Payment events may collapse into single events, potentially merging X4 with X1 or X3 unless delivery and payment multiplicities are preserved.

### Treat Pack/Dispatch order as a partial order

X4’s interleaved Pack/Dispatch pattern may become equivalent to a variant where all Packages are packed before dispatch, if no causal dependency requires interleaving. TSE with total timestamps would still separate them. X8’s return-before-repack dependency remains important, so X8 stays distinct.

### Treat payment multiplicity as an amount attribute

X4’s two Payments can become one Payment with a summed amount. Then `STAGED` becomes `SINGLE`. If delivery split is preserved, X4 remains distinct from X3 because it still has two Deliveries. If delivery split is also ignored, X4 may merge with X3 or X1.

## 8. Limitations and recommendation

No single equivalence notion is best for all purposes because each purpose requires a different trade-off between detail and generalization.

**Compliance monitoring.** Use TSE plus O2O qualifiers, or BSE with sharing, settlement, and exception fields. Compliance needs evidence of shared invoices, unallocated payments, substitutions, returns, and external object involvement. A coarse activity-label view is insufficient.

**Operational segmentation.** Use BSE motif equivalence. It groups executions by business behavior: baseline, multi-package, split delivery/staged payment, shared logistics, shared finance, substitution, and return-repack. This is useful for process mining and resource planning.

**Root-cause analysis.** Use TSE or a finer variant of the canonical signature. Root-cause work needs object roles, E2O incidence, qualifiers, and partial order to trace why a Package, Item, Invoice, or Payment behaved unexpectedly.

**Descriptive reporting.** Use ASEQ or high-level motif counts. Reporting should be simple and stable, but it should not claim to capture object-centric risk if it ignores objects.

The main limitation is that BSE is a projection: it may merge executions that are structurally different but business-similar, and TSE may separate executions that are business-identical but structurally noisy. The recommended practice is to keep all three levels available: ASEQ for overview, TSE for audit and diagnosis, and BSE for business segmentation.
