## 1. Duplicate-handling decision tree

The decision tree handles multi-system event candidates before applying graph mining or process discovery algorithms. It evaluates physical reality, object involvement, and system lineage rather than relying solely on string matches of activities and timestamps.

```
Candidate Group (Events sharing business context or overlapping timestamps)
  1. Are all business attributes, source identifiers, payloads, and object links identical?
      YES  > [TERMINAL: DROP] (Exact Technical Duplicate: retain first ingested; discard copy)
      NO   > Go to Step 2
  2. Do the candidates refer to the exact same physical action confirmed by cross-system ID / reconciliation?
      YES  > Go to Step 2a
          2a. Do candidate events record disjoint or complementary authoritative attributes/objects?
              YES > [TERMINAL: MERGE ATTRIBUTES AND RELATIONS] (Consolidate into canonical event)
              NO  > [TERMINAL: RETAIN BOTH WITH REFINED LABELS] (If attributes conflict irreconcilably)
      NO   > Go to Step 3
  3. Is one event an asynchronous summary/status update derived from a detailed operational event?
      YES  > Go to Step 3a
          3a. Pipeline mode is Aggressive / Abstraction-Flattened?
              YES > [TERMINAL: MERGE ATTRIBUTES AND RELATIONS] (Absorb summary into detailed event)
              NO  > [TERMINAL: RETAIN BOTH WITH REFINED LABELS] (Qualify summary vs operational)
      NO   > Go to Step 4
  4. Did different source activities harmonize to the same activity label for distinct business steps?
      YES  > [TERMINAL: RETAIN BOTH WITH REFINED LABELS] (Restore domain-specific original activities)
      NO   > Go to Step 5
  5. Do events share activity label and timestamp, but target distinct physical/logical object instances?
      YES  > [TERMINAL: RETAIN BOTH UNCHANGED] (Legitimate concurrent fine-grained events)
      NO   > Go to Step 6
  6. Are timestamps tied with partial or missing ordering metadata and conflicting operational facts?
       YES  > [TERMINAL: QUARANTINE FOR REVIEW] (Isolate until domain expert or logs clarify order)
```

## 3. Timestamp-tie ordering rules

### Deterministic partial-order-to-total-order policy

To establish a total order without corrupting business semantics, timestamp ties must be broken using a prioritized hierarchy:

1. **Domain & Business Logic Constraints (Semantic):** Mandatory causal dependencies (e.g., `Authorize Payment` must precede `Capture Payment` for the same payment object `M1`).
2. **Within-Source Sequence Metadata (Semantic):** Explicit source-system sequence numbers (`source_seq`) within the same `source` system.
3. **Lifecycle Constraints on Shared Objects (Semantic):** State machine rules per object type (e.g., `Pick Item` $\rightarrow$ `Pack Package` $\rightarrow$ `Dispatch Package`).
4. **Source-Specific System Semantics (Semantic):** Known physical topologies (e.g., internal WMS release precedes Carrier acceptance).
5. **Technical Ingestion Order (Deterministic Fallback):** `ingested_at` timestamp used solely as a tie-breaker when semantic rules are silent.
6. **Stable Hash Fallback (Deterministic Fallback):** Lexicographical sorting on `canonical_eid` to guarantee absolute reproducibility across execution environments.

### Semantic vs. Deterministic Rules

- **Semantic Rules (1–4):** Reflect business reality. Reordering events violating these rules creates invalid process flows (e.g., capturing payment before authorization).
- **Deterministic Rules (5–6):** Arbitrary conventions applied to break unresolvable ties. They ensure algorithm stability without asserting physical truth.

### The Microsecond Addition Anti-Pattern

Adding synthetic microseconds (e.g., $+1\,\mu\text{s}, +2\,\mu\text{s}$) directly to timestamps prior to ordering is dangerous. It alters duration metrics, distorts throughput calculations, and permanently disguises identical-timestamp concurrency as a sequential execution line. Microseconds should only be introduced—if at all—as a downstream display adapter, never as a primary mechanism to force semantic sequence.

### Resolved Event Orders at Tied Timestamps

#### 1. Cluster at 10:00:00 (`e03`–`e07` after deduplicating `e04` into `e03`)
- **Semantic Dependencies:**
  - `e03` (Pick I1) and `e05` (Pick I2) target different items $\rightarrow$ Concurrent / Unordered relative to each other.
  - Both picks must precede `e06` (Pack Package P1 containing I1 & I2) due to object state constraints (cannot pack unpicked items).
  - `e06` (WMS Pack) precedes `e07` (ERP Pack Summary) because `e07` is generated via message from WMS.
- **Admissible Total Order:** `[e03, e05, e06, e07]` (or `[e05, e03, e06, e07]`).

#### 2. Cluster at 10:15:00 (`e08`–`e10`)
- **Semantic Dependencies:**
  - `e08` (WMS Dispatch / Warehouse Release) precedes `e09` (Carrier Accept) by domain logistics topology.
  - `e09` (`CARRIER`, `seq=1`) precedes `e10` (`CARRIER`, `seq=2`) by explicit carrier source sequence.
- **Unique Admissible Total Order:** `[e08, e09, e10]`.

#### 3. Cluster at 12:00:00 (`e11`–`e16` after deduplicating `e16` into `e11`)
- **Semantic Dependencies:**
  - `e11` (Issue Invoice V1) precedes payment activities for V1.
  - `e12` (Authorize M1, `seq=400`) precedes `e13` (Capture M1, `seq=401`) by PSP lifecycle and sequence.
  - `e14` (Capture M2, `seq=402`) is independent of `M1`, but follows invoice `e11`.
  - `e15` (ERP Payment Summary, `seq=41`) summarizes captures $\rightarrow$ follows `e13` and `e14`.
- **Admissible Total Orders:** `[e11, e12, e13, e14, e15]` or `[e11, e14, e12, e13, e15]`.

## 4. Conservative cleaning pipeline

The conservative pipeline preserves process granularity while eliminating confirmed redundant data.

```
       
                       Raw Ingested OCEL Logs                   
       
                                    
                                    
       
         Step 1: Verified Multi-System Reconciliation           
         - Merge e04 into e03 (WMS/Scanner physical scan)       
         - Merge e16 into e11 (ERP/Billing Invoice V1)          
       
                                    
                                    
       
         Step 2: Harmonization Relabeling                       
         - Relabel e08 -> "Release Package"                     
         - Relabel e09 -> "Carrier Accept Package"              
         - Relabel e07 -> "Pack Package (ERP Summary)"          
         - Relabel e15 -> "Capture Payment (ERP Summary)"      
       
                                    
                                    
       
         Step 3: Object Relationship Unioning                   
         - Consolidate attributes and E2O links for merged pairs
         - Preserve all object links for distinct events        
       
                                    
                                    
       
         Step 4: Topological & Source-Sequence Sorting          
         - Enforce semantic rules (e12 -> e13 -> e15)            
         - Apply source sequence metadata (C-400 -> C-401)      
         - Assign deterministic sort index                      
       
                                    
                                    
       
                    Cleaned Conservative OCEL                   
                    (Retained Events: 15 / 17)                  
       
```

### Operational Pipeline Steps

1. **Explicit Reconciliation Merging:**
   - Merge `e04` into `e03`: Aggregate scanner payload details into `e03` audit trail; union object ties (`{O1, I1, P1}`). Retain canonical ID `e03`.
   - Merge `e16` into `e11`: Aggregate billing cross-references into `e11`; keep single invoice issuance event for `V1`. Retain canonical ID `e11`.
2. **Semantic Relabeling (Harmonization Disambiguation):**
   - Disambiguate `e08` (`Release Package`) and `e09` (`Carrier Accept Package`).
   - Disambiguate operational events from summaries (`e07` $\rightarrow$ `Pack Package (ERP Summary)`, `e15` $\rightarrow$ `Capture Payment (ERP Summary)`).
3. **Preservation of Concurrency and Multi-Object Instances:**
   - Retain `e05` alongside `e03` (picks of distinct items `I1` and `I2`).
   - Retain `e13` and `e14` as distinct captures for payments `M1` and `M2`.
4. **Deterministic Sorting:** Sort events using the 6-tier tie-breaking policy, preserving original timestamps in `original_timestamp`.

## 5. Aggressive alternatives

```
 Raw Input (17 Events)
   Conservative Pipeline   15 Events (Merges e03/e04, e11/e16; relabels summaries/logistics)
   Aggressive Scenario A   12 Events (Merges summaries e07 into e06, e15 into e13/e14; merges e08/e09)
   Aggressive Scenario B   10 Events (Naive PM4Py exact-match drop/merge on timestamp + activity + shared object)
```

### Scenario A: Evidence-Based Semantic Merging

- **Policy:** Merges asynchronous ERP summary events into their operational counterparts if cross-system lineage is confirmed. Merges overlapping logistics handovers if they share identical timestamps and object scopes.
- **Actions:**
  - Merge `e04` $\rightarrow$ `e03` (Scanner into WMS Pick).
  - Merge `e16` $\rightarrow$ `e11` (Billing into ERP Invoice).
  - Merge `e07` $\rightarrow$ `e06` (ERP Pack summary absorbed into WMS Pack).
  - Merge `e08` and `e09` $\rightarrow$ Unified `Dispatch Package` event (`e08`).
  - Merge `e15` $\rightarrow$ Shared payload attributes split across `e13` and `e14`.
- **Retained Event Count:** **12**
- **Likely Semantic Damage:** Destroys warehouse-to-carrier transfer durations; removes latency tracking between warehouse operations and financial summary ledger updates.

### Scenario B: Mechanically Aggressive PM4Py Merging

- **Policy:** Runs naive library deduplication (`pm4py.ocel_drop_duplicates` or `ocel_merge_duplicates`) matching on `(timestamp, activity)` whenever `have_common_object=True`.
- **Actions:**
  - Collapses `e03`, `e04`, `e05` into a single `Pick Item` event because they occur at 10:00:00 and share object `O1`.
  - Collapses `e06` and `e07` into a single `Pack Package` event.
  - Collapses `e08`, `e09`, `e10` into a single `Dispatch Package` event at 10:15:00.
  - Collapses `e13`, `e14`, `e15` into a single `Capture Payment` event at 12:00:00.
- **Retained Event Count:** **10** or fewer.
- **Likely Semantic Damage:** High risk of severe data loss. Merging `e03` and `e05` erases item `I2`'s pick record. Merging `e13` and `e14` collapses two separate monetary transactions (`M1` = \$50, `M2` = \$50) into one transaction, creating financial accounting errors.

### Why `have_common_object=True` Fails for `e13` and `e14`

`e13` (Capture M1) and `e14` (Capture M2) share upper-level context objects `O1` (Order) and `V1` (Invoice). An automated library function checking object intersection evaluates `intersect({O1, V1, M1}, {O1, V1, M2}) = {O1, V1} != empty`. Because the intersection is non-empty (`have_common_object=True`), the naive algorithm treats `e13` and `e14` as identical physical observations of the same event. However, `M1` and `M2` are distinct fine-grained payment instances. Merging them destroys the individual payment lifecycles and distorts payment frequency metrics.

## 6. PM4Py-oriented Python implementation

```python
import copy
import pandas as pd
import numpy as np
import pm4py
from pm4py.objects.ocel.obj import OCEL

def verify_and_merge_pairs(ocel: OCEL, pair_rules: list) -> OCEL:
    """
    Custom verified-pair merge helper.
    Consolidates source pair events (keeper_eid, merged_eid), unioning E2O linkages
    and building an audit trail in event attributes.
    """
    ocel_out = copy.deepcopy(ocel)
    events_df = ocel_out.events.set_index('ocel:eid', drop=False)
    relations_df = ocel_out.relations
    
    eids_to_drop = []
    
    for rule in pair_rules:
        keeper_id = rule['keeper_eid']
        merged_id = rule['merged_eid']
        reason = rule['reason']
        
        if keeper_id in events_df.index and merged_id in events_df.index:
            keeper_row = events_df.loc[keeper_id].to_dict()
            merged_row = events_df.loc[merged_id].to_dict()
            
            # Combine payload hashes and sources into provenance
            prov_sources = str(keeper_row.get('source')) + ';' + str(merged_row.get('source'))
            prov_keys = str(keeper_row.get('source_event_key')) + ';' + str(merged_row.get('source_event_key'))
            
            events_df.loc[keeper_id, 'merged_sources'] = prov_sources
            events_df.loc[keeper_id, 'merged_keys'] = prov_keys
            events_df.loc[keeper_id, 'merge_reason'] = reason
            events_df.loc[keeper_id, 'superseded_eids'] = str(merged_id)
            
            # Re-link relations from merged_id to keeper_id
            relations_df.loc[relations_df['ocel:eid'] == merged_id, 'ocel:eid'] = keeper_id
            eids_to_drop.append(merged_id)
            
    # Remove merged eids from events
    events_df = events_df.drop(index=eids_to_drop)
    # Deduplicate relations table
    relations_df = relations_df.drop_duplicates(subset=['ocel:eid', 'ocel:oid', 'ocel:type'])
    
    ocel_out.events = events_df.reset_index(drop=True)
    ocel_out.relations = relations_df
    return ocel_out


def build_cleaning_pipelines(ocel_raw: OCEL):
    # Ensure raw log is untouched using deep copies
    ocel_base = copy.deepcopy(ocel_raw)
    
    # Preserve original state in metadata columns
    ocel_base.events['original_timestamp'] = ocel_base.events['ocel:timestamp']
    ocel_base.events['original_activity'] = ocel_base.events['ocel:activity']
    
    # -------------------------------------------------------------------------
    # PRE-CHECK: Candidate Duplicate Groups
    # -------------------------------------------------------------------------
    print("=== Pre-Check: Candidate Duplicate Groups ===")
    dup_groups = ocel_base.events.groupby(['ocel:timestamp', 'ocel:activity']).filter(lambda x: len(x) > 1)
    print(f"Identified {len(dup_groups)} events participating in timestamp/activity ties.")
    
    # -------------------------------------------------------------------------
    # SCENARIO 1: Conservative Pipeline
    # -------------------------------------------------------------------------
    print("\n--- Running Conservative Pipeline ---")
    verified_pairs = [
        {'keeper_eid': 'e03', 'merged_eid': 'e04', 'reason': 'Reconciled physical scan WMS/Scanner'},
        {'keeper_eid': 'e11', 'merged_eid': 'e16', 'reason': 'Duplicate Invoice V1 issuance ERP/Billing'}
    ]
    ocel_cons = verify_and_merge_pairs(ocel_base, verified_pairs)
    
    # Relabel harmonized collision & summary events
    activity_map = {
        'e07': 'Pack Package (ERP Summary)',
        'e08': 'Release Package',
        'e09': 'Carrier Accept Package',
        'e15': 'Capture Payment (ERP Summary)'
    }
    
    events_df = ocel_cons.events.set_index('ocel:eid', drop=False)
    for eid, new_act in activity_map.items():
        if eid in events_df.index:
            events_df.loc[eid, 'ocel:activity'] = new_act
    ocel_cons.events = events_df.reset_index(drop=True)
    
    # Priority sorting dictionary for business semantic tie-breaking
    semantic_priority = {
        'Create Order': 10,
        'Validate Order': 20,
        'Pick Item': 30,
        'Pack Package': 40,
        'Pack Package (ERP Summary)': 45,
        'Release Package': 50,
        'Carrier Accept Package': 60,
        'Handover to Carrier': 70,
        'Issue Invoice': 80,
        'Authorize Payment': 90,
        'Capture Payment': 100,
        'Capture Payment (ERP Summary)': 105,
        'Confirm Delivery': 120
    }
    
    ocel_cons.events['semantic_rank'] = ocel_cons.events['ocel:activity'].map(semantic_priority).fillna(999)
    ocel_cons.events['source_seq_clean'] = ocel_cons.events['source_seq'].fillna(0).astype(int)
    
    # Stable multi-column deterministic sort
    ocel_cons.events = ocel_cons.events.sort_values(
        by=['ocel:timestamp', 'semantic_rank', 'source_seq_clean', 'ingested_at', 'ocel:eid'],
        ascending=[True, True, True, True, True]
    ).reset_index(drop=True)
    
    # Apply PM4Py sort and index-based timedelta AFTER establishing sequence
    ocel_cons = pm4py.ocel_sort_by_additional_column(ocel_cons, 'semantic_rank', ascending=True)
    ocel_cons = pm4py.ocel_add_index_based_timedelta(ocel_cons, timestamp_key='ocel:timestamp')
    
    # -------------------------------------------------------------------------
    # SCENARIO 2: Aggressive PM4Py Library Merging
    # WARNING: This scenario demonstrates semantic data destruction.
    # -------------------------------------------------------------------------
    print("\n--- Running Aggressive PM4Py Pipeline ---")
    ocel_aggr = copy.deepcopy(ocel_base)
    
    # Mechanical library drop duplicates (Will collapse e03/e04/e05 and e13/e14 inappropriately)
    # WARNING: ocel_drop_duplicates ignores fine-grained payment/item object distinctions.
    ocel_aggr_dropped = pm4py.ocel_drop_duplicates(ocel_aggr)
    
    # -------------------------------------------------------------------------
    # REFERENTIAL INTEGRITY VALIDATION
    # -------------------------------------------------------------------------
    for name, ocel_obj in [("Conservative", ocel_cons), ("Aggressive", ocel_aggr_dropped)]:
        valid_eids = set(ocel_obj.events['ocel:eid'])
        rel_eids = set(ocel_obj.relations['ocel:eid'])
        orphaned_rels = rel_eids - valid_eids
        print(f"Validation [{name}]: {len(ocel_obj.events)} events, {len(orphaned_rels)} orphaned relation links.")
        assert len(orphaned_rels) == 0, f"Referential integrity failure in {name} pipeline!"

    return ocel_cons, ocel_aggr_dropped
```

### 6 Concrete Edges & Patterns Whose Interpretation Changes

1. **`Pick Item` $\rightarrow$ `Pick Item` (Item-Flattened / Order-Flattened DFG):**
   - *Raw:* Shows a self-loop rework edge on `Pick Item` at 10:00:00 (`e03` $\rightarrow$ `e04` $\rightarrow$ `e05`).
   - *Conservative:* `e04` is merged into `e03`. Displays parallel branch executions for `I1` (`e03`) and `I2` (`e05`) without false rework loops.
   - *Aggressive:* `e05` is dropped/merged into `e03`. The process log incorrectly indicates that Item `I2` was never picked.
2. **`Pack Package` $\rightarrow$ `Pack Package` (Order-Flattened DFG):**
   - *Raw:* Displays duplicate execution (`e06` WMS $\rightarrow$ `e07` ERP) at 10:00:00, falsely implying repacking.
   - *Conservative:* Relabels `e07` to `Pack Package (ERP Summary)`, clarifying that `e07` is an asynchronous status update rather than a physical operation.
   - *Aggressive:* Merges `e07` into `e06`, hiding the ERP message update latency.
3. **`Dispatch Package` $\rightarrow$ `Carrier Accept` $\rightarrow$ `Handover to Carrier` (Logistics Execution Trace):**
   - *Raw:* Three identical 10:15:00 timestamps lead to non-deterministic execution paths depending on database read order.
   - *Conservative:* Applies domain topological sorting (`Release` $\rightarrow$ `Carrier Accept` $\rightarrow$ `Handover`), establishing a reliable lifecycle sequence.
   - *Aggressive:* Merges `e08` and `e09` into a single node, losing the operational boundary between warehouse control and third-party logistics responsibility.
4. **`Issue Invoice` $\rightarrow$ `Issue Invoice` (Invoice V1 Lifecycle):**
   - *Raw:* Displays redundant invoice creations (`e11` ERP vs `e16` Billing), indicating duplicate billing risk.
   - *Conservative:* Merges `e16` into `e11`, combining attributes while preserving canonical issuance.
5. **`Capture Payment` $\rightarrow$ `Capture Payment` (Payment M1 vs M2 Traces):**
   - *Raw & Conservative:* Shows two concurrent payment captures (`e13` for `M1` and `e14` for `M2`).
   - *Aggressive:* Erases `e14` under the assumption that shared `O1`/`V1` linkage implies a duplicate event. This drops partial payment `M2` from audit reports.
6. **`Capture Payment` $\rightarrow$ `Capture Payment (ERP Summary)` (Financial Reconciliation Latency):**
   - *Raw:* Appears as three indistinguishable `Capture Payment` events at 12:00:00.
   - *Conservative:* Isolates `e15` as an ERP posting summary triggered after PSP authorizations/captures (`e12`, `e13`, `e14`).

### Full Reversibility Architecture

An analyst can reconstruct the raw log view using the audit trail:

1. **Unmerging Events:** Read `source_eids_merged`. Re-insert discarded EIDs (`e04`, `e16`) into `ocel_raw.events` using saved payload dictionaries in `retained_attributes`.
2. **Re-establishing Original Relationships:** Re-assign E2O relations from `canonical_eid` back to `source_eids_merged` using saved mapping keys.
3. **Restoring Activity Labels & Timestamps:** Overwrite `ocel:activity` and `ocel:timestamp` with `original_activity` and `original_timestamp`.

## 9. Failure modes and safeguards

### 1. Collapsing Distinct Partial Payments
- **Mechanism:** Automated library functions deduplicate events matching `(timestamp, activity)` when object overlap exists (`O1`, `V1`).
- **Impact:** Merges `e13` (Payment `M1`) and `e14` (Payment `M2`), creating a 50% discrepancy in recorded revenue.
- **Safeguard:** Enforce instance-level object boundary checks. Require distinct sub-object IDs (`M1` vs `M2`) to block duplicate merging.

### 2. Converting Abstraction-Level Updates into False Rework
- **Mechanism:** Retaining summary events (`e07`, `e15`) with generic labels causes process miners to identify rework loops (e.g., `Pack Package` $\rightarrow$ `Pack Package`).
- **Impact:** Artificial spikes in process complexity and false performance bottlenecks.
- **Safeguard:** Qualify summary event labels (e.g., `Pack Package (ERP Summary)`) during ingestion harmonization.

### 3. Ordering by Ingestion Time
- **Mechanism:** Using `ingested_at` to resolve timestamp ties when system ingestion latencies vary (`e07` ingested at 10:01:00 vs `e08` at 10:15:01).
- **Impact:** Misorders business steps, placing asynchronous summary records hours after subsequent operational events occurred.
- **Safeguard:** Treat `ingested_at` purely as a non-semantic final tie-breaker; prioritize domain logic and within-source sequence metadata (`source_seq`).

### 4. Treating Shared Objects as Proof of Duplication
- **Mechanism:** Assuming events sharing objects (`O1`, `P1`) at identical timestamps are multi-system duplicates.
- **Impact:** Merges concurrent operational events targeting distinct items (e.g., merging `e03` for `I1` and `e05` for `I2`).
- **Safeguard:** Verify complete leaf-level object equivalence before executing automated deduplication.

### 5. Unioning Incompatible E2O Relations
- **Mechanism:** Indiscriminately unioning relations when merging events of differing scope (e.g., merging ERP summary `e07` into WMS detail `e06`).
- **Impact:** Attaches fine-grained object ties (`I1`, `I2`) to high-level status updates, distorting object lifecycle graphs.
- **Safeguard:** Enforce strict object-type scope validation rules during relation union operations.

### 6. Changing Durations Through Synthetic Microseconds
- **Mechanism:** Adding incremental microsecond offsets (`+1ms`, `+2ms`) to tied timestamps to force a total order.
- **Impact:** Distorts process performance statistics and introduces artificial durations into process models.
- **Safeguard:** Maintain immutable `original_timestamp` fields; store sorting ranks in explicit ordinal index columns.

### 7. Losing Source-Authoritative Attributes
- **Mechanism:** Overwriting target attributes with values from secondary systems during event merges (e.g., discarding WMS location data for Scanner records).
- **Impact:** Destroys domain-authoritative data required for root-cause analysis.
- **Safeguard:** Implement source-priority rules for key attributes (e.g., WMS is authoritative for storage location, PSP is authoritative for payment status).

### 8. Applying Duplicate Functions to the Whole OCEL Without Inspecting Candidate Groups
- **Mechanism:** Running `pm4py.ocel_drop_duplicates()` directly on an raw OCEL without pre-filtering tied candidate groups.
- **Impact:** Silently removes valid operational data across the dataset.
- **Safeguard:** Mandatory execution of pre-check candidate group profiling. Require explicit approval for identified candidate duplicate groups prior to pipeline execution.
