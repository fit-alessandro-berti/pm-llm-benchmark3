## 1. Conformance semantics

To interpret deviations correctly, we must distinguish between the nature of the normative relation and the nature of the observation. The norm defines a **closed-world** assumption strictly for `forbidden` relations and `mandatory` columns within their stated scope. In these domains, absence implies noncompliance. For example, if `Order: Create Order -> Dispatch Package` were mandatory and observed, it would be a violation. Conversely, `typical` and `unspecified` relations operate under an **open-world** assumption. Here, absence does not imply noncompliance; it implies either a legitimate exception or a feature simply outside the model's coverage.

**Forbidden behavior** is absolute. If the norm states a relation is forbidden, any observation of that relation constitutes a violation, regardless of frequency.
**Missing mandatory behavior** implies a process gap or data loss. If a `mandatory` relation is absent, we must decide if it is a process failure (the system failed to validate) or a data quality issue (the validation event was logged but not linked).
**Unexpected but unregulated behavior** falls under `unspecified`. It is not a violation, but it signals a modeling gap.
**Typical-pattern absence** is common in business; for instance, if `Validate -> Close` is typical but `Validate -> Issue Invoice` occurs frequently, the absence of the typical path is not a violation, but a variation of the process.
**Likely data-quality error** applies when the observation contradicts business logic (e.g., a sensor linked to an invoice) or when counts suggest systematic logging failures.
**Abstraction mismatch** occurs when a DFG summary (like `Create -> Validate`) cannot capture intermediate steps (like a `Manual Review` event) that are hidden from the summary.
**Insufficient evidence** applies when the log lacks attributes required to determine scope (e.g., knowing if an Order was "standard").

The **open-world versus closed-world** distinction is the primary filter. For `N3` (Cancel -> Dispatch), the norm is closed-world (forbidden), so the 2 observations are violations. For `N2` (Validate -> Close), the norm is open-world (typical), so the 17 missing instances are not violations but potential process variations.

## 3. Detailed reasoning by model family

### OC-DFG
The Object-Centric Directly-Follows Graph (OC-DFG) establishes flow control. The most significant danger here is interpreting an "eventually expected" business rule as a directly-follows rule. Norm `N1` states that every newly created standard Order should *eventually* enter validation. In a DFG, this translates to a direct edge `Create -> Validate`. However, the observed data shows 98 of 100 Orders follow this path. The 2 missing instances are flagged as potential data quality or abstraction mismatches, not necessarily process failures. If the DFG abstracts away intermediate events (like a hidden `Manual Compliance Review`), the direct edge disappears. We cannot assume the process is broken without verifying if the intermediate step exists in the raw log. The `mandatory` status of `N1` forces us to treat the gap as a deviation, but the context ("unrecorded review") suggests this is an abstraction mismatch rather than a forbidden behavior.

### OTG
The Object Type Graph (OTG) captures static structural constraints. `T6` (Order `object_cobirth` Payment) is explicitly `forbidden`. The observation of 1 edge here is a clear structural violation, indicating a birth event where an Order and Payment were created in the same transaction. This is a critical integrity issue. However, `T2` (Package `object_interaction` Delivery) shows 200 edges, but 7 are `object_codeath`. The norm does not specify `codeath`, so this is unregulated. We must not classify these as violations, but we must note them as unmodeled structural relationships. The `object_cobirth` edge is a hard constraint; the `object_codeath` is an open-world observation.

### ET–OT
The Event–Object Type (ET–OT) expectations link specific events to objects. `E10` (Sensor Heartbeat -> Invoice) is `forbidden`. The observation of 1 edge is a critical violation of business logic (financial objects must not be linked to sensor streams). However, the context notes this is a suspected data-quality error due to a reused identifier. If the identifier was reused from a legacy system rather than a true sensor link, the *behavior* might be correct but the *data* is dirty. We must separate the data quality issue from the conformance violation. `E8` (Record Payment -> Invoice) is `mandatory`, but allows exceptions for unapplied cash. The observation shows 1 Payment without an Invoice. Since the event is not labeled as unapplied cash, it technically violates the `mandatory` scope unless we accept the data-quality hypothesis. This requires investigation to distinguish between a missing link and a valid exception.

## 6. Norm-completeness assessment

The provided norm is deliberately incomplete, creating several operational risks if left unresolved.

1.  **"Standard Order" Definition (N1):** The norm applies `mandatory` to "standard Order" but does not define what constitutes a standard Order versus a complex or special Order.
    *   *Risk:* 2 Orders failing validation could be special Orders that do not require validation under different policies.
    *   *Clarification:* Define attributes (e.g., `OrderType = 'Standard'`) that trigger N1.
    *   *Status:* Mandatory.

2.  **"Unapplied Cash" Labeling (E8):** The norm allows exceptions for unapplied cash but requires the event to be explicitly typed as such. The data shows no events are labeled this way.
    *   *Risk:* Legitimate financial operations are flagged as violations, or data quality is assumed to be perfect when it is not.
    *   *Clarification:* Define a specific `PaymentType = 'Unapplied'` or allow a business rule to override the mandatory check for specific invoice IDs.
    *   *Status:* Typical (if labeled) or Mandatory (if not labeled).

3.  **"Externally Shipped" Intent (N4):** The norm applies `Pack -> Dispatch` to packages "intended for external shipment". Intent is not an observable attribute in the log.
    *   *Risk:* Packages shipped internally may be flagged as violations if the norm is applied blindly.
    *   *Clarification:* Add a `DestinationType` attribute to the norm scope.
    *   *Status:* Mandatory (if attribute matches).

4.  **"Carrier Reference" vs. "Pack Package" (N4 Context):** Two Dispatch events lack a Pack Package event but have a carrier reference.
    *   *Risk:* The norm assumes packing is a prerequisite for dispatch. If the carrier reference proves the package exists, the norm might be too strict.
    *   *Clarification:* Allow `Dispatch Package` if `CarrierReference` exists without `Pack Package`, treating `Pack` as typical rather than mandatory in specific contexts.
    *   *Status:* Typical (conditional).

5.  **"Codeath" Lifecycle Definition (OTG):** Seven Package–Delivery edges use `object_codeath`. The norm says nothing about `codeath`.
    *   *Risk:* Stakeholders might view this as a missing link in the lifecycle.
    *   *Clarification:* Explicitly state `object_codeath` is an unspecified termination relation.
    *   *Status:* Explicitly Unspecified.

6.  **Sensor ID Reuse (E10 Context):** The `Sensor Heartbeat` link is suspected to be a data-quality error from reused identifiers.
    *   *Risk:* Treating this as a process violation wastes resources; treating it as data quality ignores the risk of financial data corruption.
    *   *Clarification:* Add a data quality rule that prevents joining sensor streams to financial objects based on ID collision.
    *   *Status:* Forbidden (Data Quality Rule).
