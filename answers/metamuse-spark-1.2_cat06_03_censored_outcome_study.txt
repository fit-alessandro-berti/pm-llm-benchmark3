## 1. Target definition

**Primary formulation: Policy-conditional competing-outcome prediction for every application (operationally honest).**

We do not define "90-day default for every application" as a binary observable. Default is only defined *after and conditional on* `Account Activated`. Under the observed lending policy, rejected/withdrawn/transferred cases are never exposed to credit and have no counterfactual default label.

*   **Unit of analysis:** One credit application `case:concept:name`.
*   **Prediction time (landmark) $t_0$:** A fixed early prefix point computed *as-of* the case timeline, e.g. `L_k` = after completion of `k` events (k=3,5) OR `T_h` = `start_time + h` hours (h=24h, 72h), whichever is used as the landmark. Prediction is made only if the case is still alive (not yet in a terminal state: Accepted/Rejected/Withdrawn/Transferred/Activated) at $t_0$. This is a landmark model.
*   **Horizon / follow-up:** For prediction we observe the *first* terminal outcome under the 2024-2025 policy:
    *   If activated at $t_{act}$: window $[t_{act}, t_{act}+90d+35d]$ to allow external feed delay. Label matures at `label_available_at` = $t_{act}+90d+$ feed_delay (7-35d). Until `label_available_at <= data_extract_time` the label is immature/censored.
    *   If rejected/withdrawn/transferred: terminal at decision/withdrawal/transfer time (horizon ends there).
*   **Population:** *All* applications started in observation window, not only those activated. This matches the deployment population "first few events of every application".
*   **Estimand (cumulative incidence under observed policy):** For covariate history $\mathcal{H}(t_0)$ available at $t_0$:

$$CIF_j(t_0) = P( State = j \mid \mathcal{H}(t_0))$$

for $j \in \{$`Default_90`, `NoDefault_90_survived`, `Rejected`, `Withdrawn`, `Transferred`, `Censored_Immature/Open`$\}$ where `Default_90` = activated and `default_90d=1` within 90d. This is the *competing-risk* estimand under the current selection policy. It answers: *Given what we see in the first few events, what will happen to this application under the current process and policy?* It does **not** claim to know what rejected applicants *would have done* if activated.

This is operationally defensible: it is observable, requires only testable/partially testable censoring assumptions, avoids labeling rejected as `default=0`, and gives triage value (e.g., high $P(Rejected)$ vs high $P(Default|Activation)$ imply different interventions).

**Alternative 1 (credible but narrower): Conditional default among eventually activated.**

Estimand: $P(default\_90d=1 \mid \mathcal{H}(t_0), Activated=1, \mathcal{H}_{future\_selection})$ 
Population: only cases eventually activated with mature label (n=21,600 labeled, 3,600 immature censored).
Answers: *Among the selected subpopulation the lender chooses to activate, who will default?* Useful for collections provisioning but **not** deployable to every new application without a selection model, because at $t_0$ we don't know who will be activated. Requires Inverse Probability Weighting (IPW) or Heckman-type selection correction and suffers from selective labels (see §3). If deployed naively on all prefixes it overestimates default risk for the overall population and is miscalibrated for rejected-like prefixes.

**Alternative 2 (policy-specific counterfactual): $P(default\_90d(1) \mid \mathcal{H}(t_0))$ where $(1)$ = "intervene to activate everyone".**

This answers the business's literal request "default risk if we gave everyone credit". This is a *potential outcome* estimand. It requires counterfactual assumptions: conditional exchangeability $Y(1) \perp Activated \mid \mathcal{H}(t_0), X$, positivity, consistency, and no interference even though transfer linkage shows 40% missing. It is **fundamentally untestable** because $Y(1)$ is never observed for rejected/withdrawn/transferred. We report it only as a sensitivity/bounding analysis with explicit tipping-point assumptions (e.g., rejected would have defaulted at 1.5x-3x the activated rate) and labeled `COUNTERFACTUAL-IF-ACTIVATED - DO NOT USE FOR AUTOMATED DECISION` . We do NOT make it primary.

## 2. Cohort construction

**As-of principle:** All cohort membership, features, and labels are computed as of a configurable `CUTOFF_TIME` (e.g. `data_extract_time` or backtest cutoff) using only events with `time:timestamp <= CUTOFF_TIME` and labels with `label_available_at <= CUTOFF_TIME`.

**Inclusion:**
*   `start_time = min(time:timestamp) per case` in `[2024-01-01, 2025-12-31]`
*   Case has at least `Application Started`

**Exclusion (for modeling, not for reporting):**
*   Cases with irreparably corrupted timeline (e.g., `Account Activated` before `Application Started`) after deduplication -> quarantine for audit (<1% expected).
*   No exclusion of rejected/withdrawn/transferred/open - they are retained as competing/censored.

**Terminal state derivation (as of CUTOFF_TIME = 2026-02-15):**

Let `t_act` = timestamp of `Account Activated` if exists. `t_term` = first timestamp of `Rejected`/`Withdrawn`/`Transferred`/`Account Activated`. `t_mature = t_act + 90d + max_feed_delay(35d)`. `label_available_at` provided per case when known.

| Cohort segment (as of 2026-02-15) | N | % of 48,000 | Label status in training export | Modeling role |
|---|---|---|---|---|
| **Total applications started** | **48,000** | 100% | — | Target population |
| **A. Activated, outcome mature** | 21,600 | 45.0% | IN export (18,900 NoDefault, 2,700 Default) | **LABELED** for Default vs NoDefault (12.5% default rate conditional) |
| **B. Activated, immature / feed not yet arrived** | 3,600 | 7.5% | Omit (correctly) | **CENSORED / RIGHT-CENSORED** (ordinary + delayed label). Excluded from binary training, included in survival/competing-risk as censored |
| **C. Rejected & closed** | 9,100 | 19.0% | Omit (correctly) | **COMPETING OUTCOME** (never at risk of observed default) |
| **D. Withdrawn** | 5,700 | 11.9% | Omit | **COMPETING OUTCOME** + informative censoring |
| **E. Transferred out** | 2,900 | 6.0% | Omit (60% linkable) | **COMPETING / MISSING FOLLOW-UP**. 1,740 linkable may have external outcome, 1,160 unlinked |
| **F. Still open (no terminal by extraction)** | 5,100 | 10.6% | Omit | **CENSORED (administrative)**. Mix of will-be-activated/rejected/withdrawn |
| **Check: Omitted total (B+C+D+E+F)** | 26,400 | 55.0% | — | 21,600 + 26,400 = 48,000 |
| **Naively treating omitted as non-default** | — | — | Would falsely report 2,700/48,000 = 5.6% default | **PROHIBITED - creates selection bias** |

Backtesting variant: For a historic cutoff e.g. `2025-06-30`, any case with `t_mature > 2025-06-30` moves from A -> B, and cases with `start_time` after cutoff are excluded. This prevents label leakage.

## 3. Censoring and missing-label strategy

We distinguish 5 mechanisms (different assumptions):

| Mechanism | Definition in this process | Observability |
|---|---|---|
| **1. Ordinary right censoring (administrative + immature)** | B (3,600 activated but $t_{act}+90d+35d > CUTOFF$) and F (5,100 open). Follow-up ends before label could be observed. | Censoring time known ($t_{act}+90d$ or $CUTOFF$). |
| **2. Delayed labels / feed lag** | Subset of B where default *occurred* but feed arrives 7-35d later. Label is not missing, just not yet available. `collection_status` or `Default Recorded` event may appear before feed. | `label_available_at` > `time:timestamp` ofDefault Recorded. |
| **3. Selection through activation** | C (Rejected) and part of D/E. Default is *undefined* under observed policy because no credit exposure. Not censoring - counterfactual undefined without intervention. | Deterministic given policy; never at risk. |
| **4. Transfer as competing event / missing follow-up** | E (2,900). Case leaves observation system. 60% linkable via linkage table, 40% lost. May activate elsewhere. | Partially observed; informative. |
| **5. Permanently missing outcome feed** | Partner-originated activated accounts with elevated missingness. Even after 90d+35d, `default_90d` remains null. Missing Not At Random (MNAR) suspected. | Missingness related to `source_system`/`case:channel`. |

**Primary analysis strategy: Landmark Competing Risks + Inverse Probability of Censoring Weights (IPCW)**

1.  Fit landmark competing-risk model from $t_0$ predicting cumulative incidence functions (CIF) for 5 causes (Default, NoDefault, Rejected, Withdrawn, Transferred). Right-censored cases (B+F) contribute IPCW weights; they are not dropped arbitrarily nor labeled 0.
2.  For censored cases, estimate censoring distribution $G(t \mid X, start\_time)$ stratified by calendar time / policy period and use IPCW to reweight uncensored cases for evaluation.
3.  Report conditional default risk as: $P(Default \mid Activation, \mathcal{H}(t_0)) = CIF_{Default} / (CIF_{Default}+CIF_{NoDefault})$ with confidence interval via bootstrap.

**Sensitivity analyses (at least two):**

*   **S1 - Tipping-point counterfactual bounds:** Impute $Y(1)$ for rejected/withdrawn under assumptions: rejected would have defaulted at 1x, 1.5x, 2x, 3x the activated rate conditional on `risk_score` stratum. Plot how overall "default if all activated" estimate moves. Shows untestability.
*   **S2 - Worst/best case for transfers & permanent missing feed:** (a) Complete-case (linkable only), (b) IPW for transfer missingness using `source_system`/`region`, (c) MNAR bounds where unlinked transfers are assumed 2x default rate. Similarly, pattern-mixture model for partner-originated missing feeds.

**Testability:**

*   Testable: Censoring distribution for B/F by comparing early vs late starters; feed delay distribution from `label_available_at - (t_act+90d)`; transfer linkage rate by period.
*   Partially testable: Informative censoring of open cases (F) - can test if `risk_score`/`region` predicts censoring; can use negative control (e.g., does $P(censored)$ correlate with $P(default)$ among mature?).
*   Fundamentally untestable: $Y(1)$ for rejected/withdrawn (selection), true default rate among 40% unlinked transfers and permanently missing feeds under MNAR. Requires external linkage study or explicit policy experiment.

## 4. Prefix extraction

**Principle: No peeking past $t_0$.** All features, counts, and even prefix length are defined using only events with `time:timestamp <= t_0` and `time:timestamp <= CUTOFF_TIME`.

**A. Fixed event-count prefixes:**
*   Use `pm4py.get_prefixes_from_log(log, length=k)` for k in [2,3,5] events after start. `k` includes `Application Started` as event 1.
*   **Short cases:** If case length $<k$ at $t_0$ but already terminal (e.g., early rejection after 2 events), the case does not contribute a k-prefix for default prediction; it contributes to competing-outcome prediction at its terminal time but is not padded forward. No artificial padding with dummy events.
*   **Repeated document loops `Credit Review -> Request Documents -> Credit Review`:** Keep loop iterations intact; we extract prefix iteratively, so rework is preserved as feature (see §5). Do not collapse loops.

**B. Elapsed-time prefixes:**
*   $t_0 = start\_time + h$ where h=24h, 72h, 168h (7d). Take all events with timestamp $\le t_0$. This mirrors operational early-warning schedule and is robust to variable event rates vs. count-based.
*   If terminal occurs before $h$, $t_0$ is censored at terminal time; no prediction is made after terminal.

**Handling system migration & duplicates (2025-10-15):**
*   Maintain mapping dict `pre-migration name -> canonical name` (e.g., `KYC Check`, `Identity/KYC Check`, `ID Verification` -> `Identity/KYC Check`). Apply before prefix extraction.
*   Deduplicate: if same `case:concept:name` + `concept:name` + `time:timestamp` within 5 seconds and same `org:resource`, keep earliest. Flag `duplicate_count` as feature. Validate via `pm4py.get_variants` pre/post migration to ensure variant explosion is due to rename not process change.

**Leakage guard:** Prefix extraction operates on filtered log `log[log[time:timestamp] <= t0_per_case]`. `final_limit`, `decision_reason`, `collection_status`, future events are physically not in the prefix dataframe.

## 5. Process-aware features

All features computed strictly from history $\le t_0$.

**A. Static case attributes (available at start, known at $t_0$):**
`case:channel`, `case:region`, `case:requested_amount` (binned), `source_system`

**B. Prefix-derived (dynamic):**

*Control-flow:*
*   `prefix_length`, `elapsed_time_since_start` (hours), `last_activity`, `activity_counts` (one-hot / frequency of `Identity/KYC Check`, `Credit Review`, `Request Documents`), `variant_id` (from `pm4py.get_variants` on prefix), DFG edge existence (did loop occur?)

*Timing:*
*   `sojourn_time_last`, `mean_sojourn`, `total_wait_time` (via `pm4py.insert_case_service_waiting_time` service vs waiting), `time_since_last_event`, calendar features: `hour_of_day`, `weekday`, `days_to_month_end`
*   Temporal features via `pm4py.extract_temporal_features_dataframe` (justified: waiting times matter for withdrawal risk)

*Resource/Queue:*
*   Number of distinct `org:resource`, resource workload at $t_0$ (cases assigned to resource in last 7d, computed from historical reference data), handover count

*Rework:*
*   `document_loop_count` (how many times `Request Documents` -> `Credit Review`), `rework_flag` (>1 loop), `kyc_reentry_count`

*Cohort/Calendar (requires historical reference):*
*   Applications started in last 7d/30d per region/channel (congestion), prevalence of rejection in last 30d (policy drift), indicator `is_post_policy_change` (start_time >=2025-07-01), `is_post_migration` (>2025-10-15), seasonality

**C. Features requiring historical reference data (not just case itself):**
*   Resource experience *as of $t_0$* (reconstructed, see leakage audit), queue length, historical default rate per region/channel in training period only (target encoding with time cutoff to avoid leakage)

## 6. Leakage audit

| Feature or data element | Leakage or bias risk | Valid availability rule | Keep / repair / drop | Rationale |
|---|---|---|---|---|
| `final_limit` | **High leakage + selection bias**. Populated only after final credit decision (`Accepted` branch). Missing for rejected/withdrawn. Encodes future decision. | Available only if `time:timestamp >= decision_time`. Must be NULL at early prefix $t_0$. | **DROP** for early prefix model. Only allowed in post-decision model with different $t_0$. | Using it at $t_0$ peeks into future and conditions on activation, biases coefficients and drops 55% of cases. |
| `decision_reason` | **High leakage / post-outcome**. Populated at/after Accept/Reject. Perfectly separates rejected vs activated. | Same as above. | **DROP** at early $t_0$; allowed only if predicting *post-decision* default (then it's legitimate). | Would leak terminal state into competing-risk predictor; for early warning it's future information. |
| `collection_status` | **Direct target leakage**. Updated after activation, e.g., `In Collections`, `Default Recorded` directly reveals `default_90d=1`. | Available only after `t_act`. | **DROP** entirely from prefix features. Use only to derive label, never as predictor. | If included, model achieves near-perfect AUC by cheating. |
| Future events (`Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded`) | **Temporal leakage**. They occur after $t_0$ (by definition). | Event timestamp `> t_0` -> not in prefix log. | **DROP** (filter log by $t_0$). Audit by checking `max(prefix_timestamps) < min(future_event_timestamps)`. |Violates as-of principle; would give model foresight of activation/default. |
| `documents_total` (nightly snapshot) | **Subtle same-day leakage**. Snapshot at 23:59 includes docs uploaded after $t_0$ if $t_0$ is intraday. | Repair to `documents_total_as_of_t0 = count(doc_events where doc_upload_time <= t_0)`. | **REPAIR** by recomputing from event log, not using snapshot column. | Snapshot leaks ~0-24h of future information, inflates importance of docs. |
| Updated `risk_score` | **Time-varying with leakage risk** if latest score post-$t_0$ is used. Score may be updated after Credit Review loops. | Keep only `risk_score` values with `timestamp <= t_0`; use `last_risk_score_as_of_t0`. | **KEEP (repaired)** - use as-of value. Drop rows where score timestamp > $t_0$. | Valid signal if correctly as-of; otherwise leaks post-prefix risk reassessment. |
| Resource experience (at extraction time) | **Temporal leakage / concept drift**. Experience at 2026-02-15 overstates experience at event time for early 2024 cases. | Recalculate tenure: `experience_at_event = event_date - resource_hire_date` via HR reference or incremental event-count per resource. | **REPAIR** - reconstruct historical experience. If hire date unavailable, drop and use `resource_handover_count` instead. | Otherwise model learns spurious correlation (senior staff appears more associated with old policy). |
| `label_available_at` / `default_90d` / `data_extract_time` | **Label leakage & maturity bias**. Using immature labels or using `label_available_at` as feature reveals outcome timing. | Label only usable if `label_available_at <= CUTOFF_TIME` and `CUTOFF_TIME` is the backtest cutoff. Never as feature. | **DROP as feature**; use only for cohort censoring logic and weight. | Including `label_available_at` lets model infer default from feed delay length; using immature zeros biases evaluation. |
| `pm4py.extract_temporal_features_dataframe` outputs | Low risk if computed on prefix only, but can leak if computed on full log then filtered. | Compute *after* prefix truncation. | **KEEP** if computed post-truncation. | Must ensure waiting-time features don't use future activity durations. |
| Historical target encoding (region/channel default rate) | **Leakage if computed on whole dataset**. Encodes future policy. | Compute encoding on training period only (`start_time < train_cutoff` and `label mature`). Apply to validation/test via join. | **KEEP (repaired)** with temporal cutoff. | Prevents overfitting to future policy threshold. |

Automated check: Assert `feature_table.columns` intersection `{'final_limit','decision_reason','collection_status','default_90d','label_available_at'}` is empty and `max(event_time_in_prefix) <= t0` per case.

## 7. Validation design

**Why random case split is misleading here:**

*   **Policy change 2025-07-01:** Random split mixes pre- and post-policy prefixes; model learns average selection probability, fails to reflect that same prefix has different $P(Activation)$ and possibly different $P(Default|Activation)$ after change. Overestimates performance.
*   **System migration 2025-10-15:** Random split puts renamed activities in both train and test, hiding degradation on new naming/duplicate handling.
*   **Label maturity:** Random split assigns immature cases (started late 2025) to test with incomplete labels, penalizing correct censored handling or requiring dropping recent data, causing time leakage if their future events are in training.
*   **Temporal correlation:** Violates i.i.d. - underestimates degradation over time.

**Temporal validation & backtesting scheme:**

*Define cutoffs:*

*   `TRAIN`: cases with `start_time` in [2024-01-01, 2025-03-31] and `label mature` by `CUTOFF_TRAIN = 2025-06-30` (needs activation +90d+35d). So effectively allows maturity. ~60% of mature cases.
*   `VALIDATION` (pre-policy, pre-migration): `start_time` in [2025-04-01, 2025-06-30], cutoff `2025-10-01` for maturity. Used for hyperparameter tuning, threshold selection, calibration.
*   `TEST-1 Pre-policy`: `start_time` in [2025-04-01, 2025-06-30] but evaluated as of `2026-02-15` (mature) to test stability.
*   `TEST-2 Post-policy, pre-migration`: `start_time` in [2025-07-01, 2025-10-14] - key test of policy shift.
*   `TEST-3 Post-migration`: `start_time` in [2025-10-15, 2025-12-31] with censoring adjustment (many immature) - stress test of renaming/duplicate handling.

Train only on TRAIN, tune on VALIDATION, lock model, report on TEST-2/3. Walk-forward backtest: sliding 3-month train window replicating monthly retraining to simulate deployment.

**Evaluation metrics (appropriate to competing-risk + censoring):**

*   *Discrimination:*
    *   For Default vs NoDefault *conditional* (among activated): Time-dependent AUC and PR-AUC at 90d (IPCW-adjusted), e.g., `sksurv.metrics.concordance_index_ipcw` for survival extension.
    *   For competing outcome: Multiclass AUC (one-vs-rest) for `Rejected`/`Withdrawn`/`Transferred`, and Brier score for CIFs.
*   *Calibration:* Calibration curve & Expected Calibration Error (ECE) for $CIF_{Default}$, stratified by policy period; calibration-in-the-large per region/channel. Show miscalibration after 2025-07 policy.
*   *Overall:* IPCW-weighted Brier score at 90d and log-loss for multiclass.
*   *Operational:* Decision curve analysis: net benefit at expected intervention threshold; subgroup performance by `case:region`, `case:channel`, `risk_score` bin, `source_system` (partner), and `is_post_policy_change`. Report fairness gap.
*   *Distribution shift diagnostics:* Population Stability Index (PSI) for prefix features across periods; `pm4py.discover_dfg` visual comparison pre/post policy to explain shift.

Calibration must be evaluated on mature cohort only, with IPCW.

## 8. Limitations and decision-use boundary

**What the study CAN claim (under stated assumptions):**

*   Predictive association between early prefix patterns and the *policy-conditional* outcome distribution (will this application be rejected, withdrawn, transferred, or if activated, default within 90d) under the 2024-2025 policy and data capture process.
*   Rank-ordering of applications at early landmark by $CIF_{Default}$ and identification of process bottlenecks (e.g., multiple document loops) associated with withdrawal or default.
*   Honest uncertainty: confidence intervals for CIFs using bootstrap + IPCW, and flag of censored cases where prediction is more uncertain.

**What it CANNOT claim without stronger (untestable) assumptions:**

*   **No counterfactual default for rejected:** Cannot say "this rejected applicant *would have* defaulted with probability p". That requires causal assumptions (no unmeasured confounding of activation) which are violated - we do not observe `risk_score` updates and officer judgment that drove activation.
*   **No causal effect of intervention:** Association $\neq$ intervention effect. E.g., reducing document loops may not reduce default; loops proxy for applicant quality.
*   **No unbiased overall default rate by labeling omitted as 0:** Doing so would understate true conditional default (12.5% among activated) and mislead provisioning.

**Three ways deployment could change the data-generating process (feedback loops):**

1.  **Intervention-induced selection shift:** If model triggers early outreach to high $P(Default)$ prefixes, activated pool changes composition (more high-risk activated or more withdrawn), breaking the policy under which model was trained. $P(Activated \mid \mathcal{H})$ drifts and IPW weights become stale.
2.  **Policy threshold adaptation:** Lender lowers acceptance threshold for cases flagged low-risk, increasing activation rate and potentially increasing observed default rate even if model is well-calibrated - Goodhart effect.
3.  **Applicant strategic behavior & concept drift:** Applicants learn that providing documents quickly lowers risk flag, altering process dynamics (shorter loops) without changing underlying credit risk, or resource allocation changes queue/waiting times that were predictive features.

**Decision-use boundary:** Model approved only as *early-warning triage* to prioritize manual review/collections capacity, not as automated accept/reject decision. Predictions must be shown with: (i) competing outcome probabilities, (ii) uncertainty / censoring flag ("outcome not yet mature"), (iii) policy-period indicator. Require human-in-loop for rejections and quarterly recalibration after policy changes.

## 9. PM4Py-oriented Python implementation skeleton

```python
"""
Uncertainty-aware predictive process monitoring skeleton.
Shows cohort construction, as-of prefix extraction, leakage audit.
- Survival / competing-risk modeling connected later (e.g., lifelines, scikit-survival)
- Assumes: applications_events.csv with case:concept:name, concept:name, time:timestamp
"""
import pandas as pd
import pm4py

CSV = "applications_events.csv"
CUTOFF_TRAIN = pd.Timestamp("2025-06-30")  # backtest cutoff for train maturity
CUTOFF_EXTRACT = pd.Timestamp("2026-02-15") # data_extract_time
MIGRATION_DATE = pd.Timestamp("2025-10-15")
POLICY_DATE = pd.Timestamp("2025-07-01")
FEED_LAG_MAX = pd.Timedelta(days=35)

# 1. Read & parse
df = pd.read_csv(CSV, parse_dates=["time:timestamp","label_available_at","data_extract_time"])
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True)
df["case:concept:name"] = df["case:concept:name"].astype(str)

# 2. Canonical activity mapping & dedup (handle migration 2025-10-15)
rename_map = {"KYC Check":"Identity/KYC Check","ID Verification":"Identity/KYC Check",
              "Credit Review Old":"Credit Review"}
df["concept:name"] = df["concept:name"].replace(rename_map)
df = df.sort_values(["case:concept:name","time:timestamp"])
df = df.drop_duplicates(subset=["case:concept:name","concept:name","time:timestamp"], keep="first")
# flag duplicates >5s heuristic omitted for brevity

# 3. PM4Py formatting
df = pm4py.format_dataframe(df, case_id="case:concept:name",
                            activity_key="concept:name", timestamp_key="time:timestamp")

# 4. Case-level as-of table construction (configurable cutoff)
def build_case_table(log_df, cutoff):
    g = log_df[log_df["time:timestamp"] <= cutoff]
    # case start / terminal
    case_start = g.groupby("case:concept:name")["time:timestamp"].min().rename("start_time")
    # last activity per case
    last_act = g.sort_values("time:timestamp").groupby("case:concept:name").tail(1).set_index("case:concept:name")["concept:name"].rename("last_activity")
    # activation time
    act = g[g["concept:name"]=="Account Activated"].groupby("case:concept:name")["time:timestamp"].min().rename("t_act")
    # terminal type
    term_events = {"Rejected","Withdrawn","Transferred","Account Activated"}
    # helper to get first terminal
    def first_term(sub):
        hits = sub[sub["concept:name"].isin(term_events)]
        return hits["concept:name"].iloc[0] if not hits.empty else pd.NA
    term_type = g.groupby("case:concept:name").apply(first_term).rename("terminal_type")
    # label maturity: label_available_at <= cutoff and not null
    label_info = g.groupby("case:concept:name").agg(
        default_90d=("default_90d","last"),
        label_available_at=("label_available_at","max")
    )
    tbl = pd.concat([case_start, act, term_type, last_act, label_info], axis=1).reset_index()
    # derive horizon maturity
    tbl["mature"] = tbl["label_available_at"].notna() & (tbl["label_available_at"] <= cutoff)
    tbl["censored"] = tbl["terminal_type"].isna()  # still open as of cutoff
    tbl["is_post_policy"] = tbl["start_time"] >= POLICY_DATE
    tbl["is_post_migration"] = tbl["start_time"] >= MIGRATION_DATE
    return tbl

case_tbl_extract = build_case_table(df, CUTOFF_EXTRACT)
case_tbl_train_cutoff = build_case_table(df, CUTOFF_TRAIN)

# Cohort counts audit (accounts for 48k)
print(case_tbl_extract["terminal_type"].value_counts(dropna=False))
print("Mature activated:", case_tbl_extract.query("terminal_type=='Account Activated' & mature").shape[0])
# Expected: 21600 mature, 3600 immature censored, etc.

# 5. Time-based split by case start (NOT random)
train_cases = case_tbl_extract[case_tbl_extract["start_time"] < "2025-04-01"]["case:concept:name"]
val_cases   = case_tbl_extract[case_tbl_extract["start_time"].between("2025-04-01","2025-06-30")]["case:concept:name"]
test_cases  = case_tbl_extract[case_tbl_extract["start_time"] >= "2025-07-01"]["case:concept:name"]
# NOTE: pm4py.split_train_test could be used as convenience baseline but would be misleading (random)

train_log = df[df["case:concept:name"].isin(train_cases)]
val_log   = df[df["case:concept:name"].isin(val_cases)]

# 6. Prefix extraction without future leakage
```
