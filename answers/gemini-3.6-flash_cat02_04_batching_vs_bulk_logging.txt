# 3. Consequences for performance analysis

### Cluster G1 (Genuine simultaneous batch)
* **Waiting time:** Accurately measured from arrival (`08:54`–`08:58`) to batch start (`09:00`). Average wait = $4.5$ min.
* **Service time:** Naive calculation yields $3.0$ min per case. If treated as single-item sequential work, capacity is underestimated by $4\times$. Total aggregate processing time for 4 items is $3$ minutes.
* **Resource utilization:** Naively summing reported durations ($4 \times 3 = 12$ min) over a $3$-min clock window yields an impossible $400\%$ utilization. Correct utilization during `09:00`–`09:03` is $100\%$.
* **Bottleneck detection:** Risk of misidentifying RBT-7 as a bottleneck if multi-position fixture capacity ($4$ items/cycle) is ignored in capacity models.

### Cluster G2 (Start batching / UI setup artifact)
* **Waiting time:** Severely **underestimated** for cases S02–S04 if queue wait is measured to logged start (`10:00`). S04 physically waited until `10:21` to begin service, but data shows wait ending at `10:00`.
* **Service time:** Severely **inflated** (S01: 8m, S02: 14m, S03: 21m, S04: 27m; mean = $17.5$ min) because all durations are anchored to the `10:00` UI group-start event.
* **Resource utilization:** Sum of service times ($8 + 14 + 21 + 27 = 70$ min) over a $27$-min elapsed span gives a phantom utilization of $259\%$.
* **Bottleneck detection:** Distorts T-B into appearing as an extreme process bottleneck due to artificially bloated service durations.

### Cluster G3 (End batching / Bulk completion submission)
* **Waiting time:** Accurately logged relative to task initiation (`11:02`–`11:24`).
* **Service time:** Severely **inflated** for early items (E01: 28m, E02: 20m, E03: 13m, E04: 6m; mean = $16.75$ min) because completion is pegged to folder submission at `11:30`.
* **Resource utilization:** Summed nominal durations ($28 + 20 + 13 + 6 = 67$ min) over a $28$-min span (`11:02`–`11:30`) yields $239\%$ utilization for a single worker.
* **Bottleneck detection:** High variance in service time creates false signals of case complexity spikes in early folder items.

### Cluster G4 (Sequential batching / Contiguous execution)
* **Waiting time:** Accurately reflects physical queue dynamics (P01 waits 7m, P05 waits 19m).
* **Service time:** Unbiased $4.0$ min per item.
* **Resource utilization:** Exactly $100\%$ ($20$ minutes of work executed in $20$ minutes of elapsed time).
* **Bottleneck detection:** Correctly reflects true sequential throughput constraints ($15$ items/hour).

### Cluster G5 (Shared-account artifact)
* **Waiting time:** Unbiased relative to actual analyst pickup times.
* **Service time:** Individual case durations (10m–25m) are accurate, but attributing all 4 overlapping cases to a single worker profile (`analyst_pool`) creates an illusion of human multitasking.
* **Resource utilization:** Appears as $210\%$ utilization for a single resource profile during peak overlaps (`13:12`–`13:20`).
* **Bottleneck detection:** Masked. The analyst pool capacity ($3$ workers) is hidden, making capacity analysis unreliable unless disaggregated.

### Cluster G6 (End-of-shift data entry) & Mechanistic Explanation
* **Why G6-like data creates both inflated waiting and near-zero service:**
  * **Waiting time inflation:** Queue arrivals occur throughout the afternoon (`14:05`–`16:25`). Because no progress is recorded until the end of shift (`17:00`), the calculated queue wait time ($t_{\text{start}} - t_{\text{queue\_arrival}}$) spans up to $2$ hours $55$ minutes (mean wait = $108.4$ min). The system interprets the administrative delay in logging as physical queueing in front of the workstation.
  * **Near-zero service time:** All 7 tickets are opened and closed instantaneously at `17:00` ($t_{\text{complete}} - t_{\text{start}} = 0$ min).
  * **Impact:** Distorts process discovery by showing massive queue bottlenecks coupled with infinite operational processing speed, completely hiding real physical work schedules.

### Cluster G7 (Timestamp coarsening / 15-minute rounding)
* **Waiting time:** Unreliable and mathematically corrupted. For case M02, queue arrival is `14:01` but logged start is rounded down to `14:00`, producing a **negative waiting time** ($-1.0$ min).
* **Service time:** Forced into uniform $15.0$-minute blocks for all cases. Summed duration ($75$ min) over $15$ min elapsed time yields $500\%$ phantom utilization.
* **Bottleneck detection:** False synchronization spikes at quarter-hour boundaries mask smooth operational queueing.

### Cluster G8 (Queue accumulation after downtime)
* **Waiting time:** High average wait ($47.6$ min) correctly captures the operational queue backlog built during the 35-minute safety check outage (`15:00`–`15:35`).
* **Service time:** Unbiased $7.0$ min per item.
* **Resource utilization:** $0\%$ during safety outage (`15:00`–`15:35`), jumping to $100\%$ during queue clearance (`15:38`–`16:13`).
* **Bottleneck detection:** Properly isolates an upstream availability bottleneck (safety pause) from processing inefficiency.

def pair_overlap_rate(group):
    n = len(group)
    if n <= 1:
        return 0.0
    overlaps = 0
    starts = group["start"].values
    completes = group["complete"].values
    for i in range(n):
        for j in range(i + 1, n):
            # Overlap condition: start_i < complete_j and start_j < complete_i
            if max(starts[i], starts[j]) < min(completes[i], completes[j]):
                overlaps += 1
    return overlaps / (n * (n - 1) / 2)

# 5. Robustness and alternative explanations

### Impact of Resource Identifier Assumptions

1. **Trusted Resource IDs vs. Shared Accounts:**
   * In **G5 (`analyst_pool`)**, trusting the resource ID forces the conclusion that a single analyst is performing 4 complex root-cause analyses in parallel (reaching $210\%$ peak utilization). Treating `analyst_pool` as a shared login for up to 3 analysts resolves the physical impossibility: work is performed concurrently by distinct humans.
   * In **G2 (`T-B`)** and **G3 (`T-C`)**, the resource IDs represent single workstations. If treated as shared logins, one might falsely hypothesize that multiple workers were operating T-B or T-C simultaneously. Operational context confirms single workers, pointing directly to UI software logging artifacts ("begin group" button and bulk folder submission).

2. **Exact Timestamps vs. Interval-Censored Timestamps:**
   * In **G7 (`legacy_MES`, 15-min precision)**, treating timestamps as exact leads to non-sensical findings (e.g. M02 entering queue at `14:01` after its logged start at `14:00`, creating negative waiting time). Treating timestamps as interval-censored $[t - 7.5\text{m}, t + 7.5\text{m}]$ restores mathematical consistency and reflects true underlying queue dynamics.
   * In **G6 (`manual_bulk_form`, 1-min precision)**, exact timestamp interpretation suggests $7$ tickets were completed in $0$ seconds at `17:00`. Interval-censoring highlights that the system lacks execution lifecycle capture entirely.

### Equivalent Temporal Patterns Supporting Multiple Physical Explanations

1. **Pattern A: Identical Start and Complete Timestamps ($t_s^i = t_s^j$ and $t_c^i = t_c^j$)**
   * *Physical Explanation 1 (G1):* Genuine parallel processing on a multi-position physical fixture (RBT-7 automated cell).
   * *Physical Explanation 2 (G6):* End-of-shift administrative bulk ticket closure (zero physical execution time).
   * *Physical Explanation 3 (G7):* Coarse timestamp quantization (15-minute rounding quantum collapsing sequential executions into a single interval).

2. **Pattern B: Identical Start Timestamp with Staggered Completions ($t_s^i = t_s^j$, $t_c^i < t_c^{i+1}$)**
   * *Physical Explanation 1 (G2):* UI logging artifact ("begin group" button pressed once at start, completing items individually).
   * *Physical Explanation 2:* Progressive batch unloading, where a multi-item batch starts together, but items undergo varied testing durations and exit individually.
   * *Physical Explanation 3:* Single setup step followed by immediate serial processing without individual setup steps logged.

3. **Pattern C: Staggered Starts with Identical Completion Timestamp ($t_s^i < t_s^{i+1}$, $t_c^i = t_c^j$)**
   * *Physical Explanation 1 (G3):* Bulk submission artifact (worker reviews items serially throughout the half-hour, but submits the electronic form once at folder completion).
   * *Physical Explanation 2:* Synchronized assembly release, where items are worked on independently and held until joint quality sign-off.
   * *Physical Explanation 3:* System buffering, where local tablet data syncs to the central database only when a network connection is established at `11:30`.
