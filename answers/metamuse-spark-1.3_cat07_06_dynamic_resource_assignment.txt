# 1. Objectives and constraints
## 1.1 Objectives to balance
No single objective dominates. The policy is multi-objective:

- **Short-term throughput:** minimise waiting + service time for the current batch, clear urgent queue without creating idle specialist time.
- **SLA reliability:** prioritise cases by time-remaining relative to expected handling time, not only by labelled priority.
- **Quality / error avoidance:** match skill to complexity, enforce supervision where competence is marginal.
- **Continuity:** avoid reassignments and owner changes where handover cost is medium/high, especially after 2+ reassignments or complexity >0.7.
- **Fairness:** balance new assignments and open cases, protect resources with high overtime risk and low hours remaining.
- **Skill development:** use safe normal/low cases to advance documented training priorities.
- **Resilience:** avoid single-point queues in Security and Approval, keep cross-trained capacity and supervisory cover.

Trade-off is explicit: throughput vs quality, continuity vs skill-match, fairness vs urgency, development vs short-term risk.

## 1.2 Hard constraints - safety / compliance - cannot be violated
- **H1 Skill 0 = not allowed.** Score 0 can never perform alone or supervised.
- **H2 Security Review:** only skill 3 alone; skill 1-2 only with explicit supervision by R7_Gita or R8_Hugo. Skill 0 never.
- **H3 Final Approval:** only skill 2-3 may finalize. Skill 1 may prepare but not finalize.
- **H4 High-priority cases (high/urgent):** require skill >=2, or skill 1 only in a supervised pair with a named supervisor who is accountable. No unsupervised trainee on high-priority.
- **H5 Batch limit:** no resource receives >4 new assignments in this batch.
- **H6 Hours feasibility:** estimated effort must fit hours remaining today or be explicitly split / carried over.

## 1.3 Soft constraints / preferences - to be traded off with reasons
- **S1 Overtime protection:** avoid new work for overtime risk=high (R2_Bruno, R4_David, R9_Iris) unless SLA is urgent and no safer competent alternative exists. If violated, justification and monitoring required.
- **S2 Training share:** at least 20% of normal/low assignments should support a documented training priority when SLA risk is acceptable.
- **S3 Continuity:** for high-complexity (>0.7) + high handover cost, prefer current owner unless owner skill is 0-1 and supervision is infeasible. Historical evidence: >2 reassignments = 1.8x rework, 1.4x appeal; owner change on high-complexity = +2.7h median waiting; keeping weak owner = +3.3h service + rework.
- **S4 Batching:** Quality Check may batch only if priority normal/low and SLA >24h.
- **S5 Bottleneck avoidance:** do not queue all Security/Approval to one specialist if a second competent resource can safely take work.

# 2. Assignment policy
## 2.1 Overview - explainable scoring with filters, not black box
Filter-then-score-then-adjust. Every assignment can be explained as: eligible? urgent? skilled? continuous? fair? developmental? resilient?

Pseudocode:

```
FOR each case C in queue sorted by SLA-urgency (urgent by SLA-remaining, then high, then normal/low):
  1. ELIGIBILITY FILTER
     eligible = {R | skill[C.activity](R) >0 AND H2/H3 satisfied}
     IF C.priority in {high,urgent}:
        eligible = {R | skill>=2} UNION {R_skill1 + supervisor}
        // supervisor must be skill>=2 (Security: must be R7/R8) and have capacity
     REMOVE R with insufficient hours_remaining unless no alternative -> flag exception
  2. SCORE candidates on 0-5 scales:
     urgency = f(priority, SLA_remaining, complexity)
     skill_match = f(skill level, complexity fit, specialist need)
     continuity = f(is_owner, reassignment_count, handover_band, complexity)
     fairness = f(open_cases, hours_remaining, overtime_risk, batch_count_this_round)
     training = f(training_priority_match, safe_to_learn)
     resilience = f(bottleneck relief, team cross-cover)
     total = w_urg*urgency + w_skill*skill_match + w_cont*continuity 
             + w_fair*fairness + w_train*training + w_res*resilience
     // weights shift by context: urgent SLA -> w_urg, w_skill up, w_train down
  3. ADJUST:
     IF top candidate violates S1 (high overtime) AND alternative within 1 point exists -> pick safer alternative
     IF C is high-complexity/high-handover AND top candidate breaks continuity for <1 point gain -> keep owner
     IF batch opportunity (Quality normal/low, SLA>24h, same resource) -> bonus to batching resource
  4. TIE-BREAK: continuity > lower open cases > higher hours remaining > training fit > random, documented
  5. EXCEPTION: if no eligible without violating H1-H6 -> escalate to lead, allow supervised pair or SLA renegotiation, log assignment_reason
LOG: assignment, scores, main reason, trade-off, training flag, risk to monitor
```

## 2.2 Component definitions
- **Eligibility filtering by skill and rule constraints:** hard filter H1-H4. Example: C001 Security urgent: only R7,R8 alone; R3(Sec1),R4(Sec2),R9(Sec1) only with R7/R8 supervision; R1,R2,R5,R6,R10 excluded (0).
- **SLA urgency scoring:** `urgency = priority_weight * (1 + complexity) / log(1+SLA_hours)`. Urgent 2-4h scores 5; high 6-9h scores 4; normal 18-30h scores 2-3; low 48-72h scores 0-1. High complexity amplifies urgency because delay + handover cost compound.
- **Skill-match scoring:** 5=specialist (3) on high-complexity/specialist-need; 4=competent (2) well-matched to moderate complexity; 2=competent stretched on very high complexity; 1=trainee (1) unsupervised (only allowed normal/low); supervised pair scores as supervisor minus 0.5 penalty for coordination.
- **Continuity / handover-cost scoring:** +2 if keep owner with skill>=2 and reassignments>=2 or handover=high; 0 if neutral change with low handover; -2 if change with high handover + high complexity. Penalty overridden if owner skill 0-1 unsupervised.
- **Workload and overtime fairness scoring:** `fairness = 5 - normalized(open_cases + new_assigned*2) - overtime_penalty(high=2, medium=1, low=0) + hours_bonus`. Resources with >11 open or high overtime start at 1-2.
- **Training / development scoring:** +2 if case is normal/low, SLA>20h (or >15h for low complexity), skill=1-2, and matches training_priority; +1 if shadowing/prepare role. Forced to 0 for urgent/high-complexity unless supervised and explicitly low-risk.
- **Resilience / bottleneck avoidance:** -2 if assignment would make one team/person sole queue for Security/Approval; +1 if it preserves second path (e.g., split Security between R7 and R8, Approval between R6 and R5/R2). Prefer cross-team supervision to spread knowledge.
- **Tie-breaking and exception handling:** ties broken transparently in order: keep owner, then fewest open cases, then most hours left, then training fit. Exceptions: skill gap with no cover, all competent overloaded, training request conflicts with SLA -> lead decides, records `assignment_reason = exception_[type]` and required monitoring (e.g., overtime approval, extra QA).

Socio-technical note: scores are decision support. Workers can challenge assignment if context (customer knowledge, fatigue, team agreement) not in data, and challenge is logged for audit.

# 4. Comparison with baseline policies
## Expected throughput
- **First-available:** fastest initial dispatch (lowest open cases: R10,R6,R3 first). Lowest average waiting initially, but ignores complexity fit, so service time inflates (+3.3h median when weak owner kept) and rework loops return work to queue. Good for simple routine cases (C004,C013) but poor for C001,C007,C016.
- **Specialist-only:** lowest service time and error per case when specialist free, but creates queues at R3/R4 for Diagnosis, R7/R8 for Security, R6 for Approval. Waiting explodes for Security/Approval urgents if specialist busy. Throughput collapses under bottleneck.
- **Proposed:** middle path. Slightly slower dispatch than first-available due to supervision coordination and batching (C006/C012), slightly slower service than pure specialist due to training cases (C009,C010). Overall throughput more stable because it avoids rework returns and bottleneck starvation by splitting Security (R7+R8) and Approval (R6+R5) and offloading R4/R2/R9.

## SLA risk
- **First-available:** high SLA risk for urgents needing skill: C001 could go to R10/R6 (Sec0) - invalid - or to least-loaded allowed but not necessarily fastest competent; C002/C011 might miss specialist speed. Low-risk cases safe.
- **Specialist-only:** best SLA for specialist-handled urgents if specialist available (C001->R8, C002->R6), but worst if specialist overloaded - e.g., all Diagnosis to R3/R4 (R4 only 3h left) would breach C003/C016.
- **Proposed:** explicitly SLA-sorted, protects 2-4h urgents with best-fit available specialist, preserves 7-9h highs with continuity + consult. Accepts small SLA stretch on batch/train cases where slack >20h.

## Error / rework risk
- **First-available:** highest mismatch and rework: ignores 1.8x rework after >2 reassignments, ignores 3.3h penalty of weak ownership. Risks C007 4th handover, C001 weak owner, C010 trainee finalize.
- **Specialist-only:** lowest immediate error, but over-concentration increases fatigue/overtime errors and hides learning deficits.
- **Proposed:** lowest systemic rework: enforces H2/H3, requires supervision for skill1 on high, keeps C007/C016 continuity, moves C003/C014 only to equivalent skill to avoid weak-owner penalty.

## Fairness of workload
- **First-available:** seemingly fair (to fewest open cases) but blind to hours remaining and overtime risk; would keep feeding R10/R6 until they become overloaded, and would still assign to R4 if R4 were lowest in a sub-filter, or overload R1.
- **Specialist-only:** highly unfair: R4 (14 open, high risk), R7 (10 open), R9 (11 open) would receive more; R10/R3 underused for their secondary skills.
- **Proposed:** fairest by design: caps at 4, zeroes new work to high-risk R2,R4,R9, distributes to low-risk R10,R3,R8,R6. Trade-off: medium-risk R1,R5,R7 retain ownership load.

## Skill development
- **First-available:** incidental, often unsafe (trainee on high without supervision).
- **Specialist-only:** zero development; trainees never touch cases, bottleneck worsens long-term.
- **Proposed:** deliberate 20%+ safe training (C009 diagnosis, C010 approval prep, C015 shadowing) with supervision and SLA guardrails. Slower today, more capacity tomorrow.

## Continuity of case ownership
- **First-available:** worst: breaks continuity whenever another resource is slightly less loaded; high handover cost ignored.
- **Specialist-only:** also breaks continuity whenever specialist differs from owner (e.g., C005->R6 instead of R5, C016->R3 instead of R5).
- **Proposed:** best balance: keeps 7/11 owned cases where competent (C002,C004,C005,C007,C008,C015,C016), moves only where overload/skill gap justifies (C003,C006,C010,C014,C001).

## Resilience to absence or bottlenecks
- **First-available:** resilient in numbers but fragile in skill: anyone absent still leaves skill gaps uncovered.
- **Specialist-only:** fragile: if R8 or R6 absent, Security/Approval halt; no cross-training.
- **Proposed:** most resilient: splits critical skills across two holders, builds supervised capacity, documents second-best alternatives and shadowing. Costs extra coordination and supervision time.

No optimum dominates: choose proposed if SLA + quality + fairness + learning matter jointly; accept that pure throughput or pure error minimisation would look better on a single metric.

# 5. Explanation to workers
We assign work to balance five things you care about: getting urgent customer cases done on time, matching difficulty to experience, staying with a case you already know when changing would waste time, sharing load fairly without pushing people into overtime, and giving everyone chances to learn safely.

How it works in plain language:

- Urgent cases with tight deadlines go first, to someone qualified and available. Security and Approval have strict qualification rules to protect you and the customer - if you don't have the required level, you will only be asked to do it with a named specialist supervisor, never alone.
- If you already own a complex case, we try to keep it with you, because handovers add waiting and rework. We only move it if you are overloaded, low on hours, or the case needs a specialist you can't cover even with help - and then we make sure context moves with it.
- We protect people flagged as high overtime risk and those with many open cases. If you are in that group you will get fewer new cases this round so you can finish well. If an urgent SLA leaves no safer option, we will say so openly and monitor it.
- Some routine cases with plenty of time are deliberately given as learning chances tied to your training priorities, always with backup. This is not punishment or favouritism - it is how we avoid permanent bottlenecks where only one or two people can do Security or Approval.
- Quality checks with long deadlines may be batched together to save setup time. You will always see the main reason for your assignment, what trade-off was accepted, and what to watch (for example, SLA clock, need for supervisor sign-off).

You can question an assignment if you have customer context, fatigue, or team agreements the system doesn't see. Your feedback is logged and helps improve future assignments. The goal is not to score you by algorithm, but to make decisions auditable, fair, and supportive of good work.

# 6. Process-mining audit indicators
All indicators computed from event log with `org:resource`, `required_skill`, `current_owner`, `assignment_reason`, `reassignment_count`, `workload_snapshot`, plus SLA and outcome attributes. Audit monthly and per batch.

- **Handover frequency:** share of cases where `org:resource != current_owner` at assignment; handover network density. Target: decrease for high-complexity/high-cost; alert if >30% overall.
- **Reassignment count:** mean/max `reassignment_count` per case; share with >2 reassignments. Alert if rising vs baseline; link to policy deviations.
- **Skill mismatch:** share assigned with skill 0 (must be 0), skill 1 unsupervised on high/urgent (must be 0), skill 1 supervised, skill 2 on complexity>0.7. Use role similarity to validate.
- **Workload distribution:** distribution (mean, Gini, max) of open cases / new assignments per resource from `workload_snapshot`; share to high-overtime resources. Check cap >4 violations.
- **Overtime risk exposure:** assignments to overtime risk=high, split by SLA urgency; hours_remaining violations. Every high-risk assignment must have documented urgent justification.
- **SLA misses:** share missing `sla_deadline`, median waiting/service time by priority; compare urgent vs normal. Segment by assignment_reason.
- **Rework / appeal after assignment:** rework rate (repeat activity, `Rework Correction` occurrence), appeal rate within N days after assignment; compare kept-owner vs changed-owner, specialist vs supervised trainee. Validate 1.8x/1.4x/2.7h/3.3h assumptions.
- **Training assignment share:** share of normal/low assignments with training flag / matching training priority and supervised; per-resource development hours. Target >=20%.
- **Specialist bottleneck indicators:** queue length and waiting time before Security/Approval, utilisation of R7/R8/R6, performance DFG bottlenecks; working-together overload. Alert if waiting > service time.
- **Deviations from assignment policy:** share where assigned != policy-recommended eligible top scorer; reasons (`assignment_reason` exception codes); supervisor sign-off presence for Security 1-2 and Approval 1-prepare. All deviations reviewed for pattern (favouritism, bottleneck avoidance, data error).

Socio-technical audit: supplement with worker survey on perceived fairness, clarity of reason, and ability to challenge.
