# 1. Model scope and state variables

The digital twin should be a **transient, calendar-aware, stochastic discrete-event simulation** of the municipal building-permit process. It is not a replay-only model: it must generate plausible future case streams, route them through the permit process, consume municipal resource capacity, wait for applicant/third-party actions, and expose cross-case dependencies. The model should be able to answer “what-if” questions about policy interventions under seasonal demand, bursts, resource calendars, rework, and incomplete data.

## Boundary

Included in scope:

- Municipal permit process from **Submit application** to **Issue permit** or **Reject application**.
- Applicant-side waiting, especially:
  - missing-document response times;
  - appeal/rework triggers where observable or assumable.
- Municipal resources and calendars:
  - clerks;
  - planners;
  - fire-safety reviewers;
  - environmental reviewers;
  - inspectors;
  - legal officers;
  - system tasks.
- Routing rules and policy interventions:
  - fire, environmental, public-notice routing;
  - inspection skipping for low-risk simple renovations;
  - pre-submission document checking;
  - inspection batching;
  - temporary peak inspectors;
  - legal pre-check parallelization;
  - aging-case planner reserve;
  - appointment slots;
  - environmental triage;
  - objection early warning.
- Cross-case dependencies:
  - same architect submitting related applications;
  - district-based inspection batching;
  - neighborhood objection clusters affecting public-notice duration;
  - shared-resource contention across all cases.

Excluded from the core twin, unless added as scenario overlays:

- detailed building-code compliance checking;
- full legal-text analysis;
- post-permit construction activity;
- long-term induced demand, except as an explicit scenario assumption;
- political decision-making beyond council-calendar capacity effects.

## Simulation paradigm

Use a hybrid representation:

- **Discrete-event simulation** for activity execution, queues, resource allocation, and rework loops.
- **Calendar/date-aware logic** for working hours, holidays, council weeks, public-notice minimums, and seasonal demand.
- **Agent/entity attributes** for cases, architects, districts, inspection bundles, and objection clusters.
- **Stochastic routing and durations** conditioned on case type, district, architect behavior, resource pool, and policy scenario.

## Entities

| Entity | Purpose |
|---|---|
| Application case | Main flow object moving through permit activities. |
| Activity/task instance | One execution of an activity, including waiting, service, rework, and completion. |
| Resource pool | Clerks, planners, fire reviewers, environmental reviewers, inspectors, legal officers, system. |
| Resource unit | Individual worker or capacity slot with calendar and skills. |
| Architect account | Source of correlated submissions and potential related-case grouping. |
| District | Geographic unit affecting travel time, environmental sensitivity, inspection batching, and objection risk. |
| Public-notice timer | Calendar-day timer with minimum duration and latent objection extension. |
| Objection cluster | Latent object representing neighborhood objections affecting one or more cases. |
| Inspection bundle | Group of inspections in the same district/time window to reduce travel time. |
| Scenario/policy configuration | Intervention parameters, demand assumptions, capacity changes, and stress overlays. |

## Core state variables

### Case-level state

For each case, maintain at least:

- `case_id`
- `case_type`: Simple renovation, New residential, Commercial, Complex variance
- `district`
- `architect_id`
- `application_value`
- `requires_fire`: observed flag plus imputed probability if threshold data missing
- `requires_environment`: observed flag plus imputed probability if sensitivity data missing
- `requires_public_notice`
- `prior_violations`: needed for D2; if unavailable, model as probabilistic or scenario-based
- `environmental_sensitivity_score`
- `fire_risk_score`
- `current_stage`
- `case_status`: waiting, in progress, blocked, rework, appeal, completed, rejected
- `submission_time`
- `ready_time_for_current_activity`
- `start_time_for_current_activity`
- `completion_time_for_current_activity`
- `missing_document_loop_count`
- `planning_rework_count`
- `inspection_rework_count`
- `legal_rework_count`
- `appeal_count`
- `public_notice_start`
- `public_notice_end`
- `objection_state`: none, suspected, active, resolved
- `inspection_bundle_id`
- `architect_group_id`
- `sla_due_date`
- `aging_priority_score`
- `completed_activities`
- `waiting_history`
- `service_history`

### Resource-level state

For each resource pool/unit:

- `resource_id`
- `pool`: clerk, planner, fire, environmental, inspector, legal, system
- `skills`
- `calendar_id`
- `available_capacity`
- `current_task_id`
- `reserved_capacity`: for aging cases, urgent legal work, peak inspectors, etc.
- `utilization`
- `overtime_allowed`: usually false in baseline
- `interruptions`: holidays, council weeks, non-permit duties, field/travel constraints

### Queue state

Explicit queues should be modeled, not collapsed into a single delay:

- Completeness-check queue, with Monday spike behavior.
- Missing-document response queue, applicant-driven.
- Planning-review queue, segmented by case type and planner skill.
- Fire-review queue, Tuesday-Thursday capacity constrained.
- Environmental-review queue, with 40% non-permit duty reduction.
- Public-notice timer queue, calendar-day based.
- Inspection-scheduling queue, with district batching option.
- Inspection-execution queue, with travel time and no-show risk.
- Decision-drafting join queue, waiting for required predecessor tasks.
- Legal-check queue, affected by council weeks and urgent exceptions.
- Aging-case priority queue.
- Rework queues returning cases to planning, inspection, legal, or appeal states.

### Cross-case dependency state

The model must not treat cases as fully independent. Required dependency structures include:

- `architect_group_id`: cases from the same architect submitted close in time may be related.
- `inspection_bundle_id`: cases grouped by district and scheduling window.
- `objection_cluster_id`: latent neighborhood objection event affecting multiple cases in public notice.
- Shared-resource contention: all cases compete for the same resource pools.
- Council-calendar coupling: legal capacity reductions affect many cases simultaneously.
- District coupling: travel time and environmental sensitivity vary by district.

## Level of detail

The twin should model:

- Minute/hour resolution for municipal service tasks.
- Day resolution for public notice, applicant response, inspection scheduling windows, and SLA aging.
- Calendar effects for holidays, council meetings, part-time resources, and field days.
- Heavy-tailed waiting times, especially missing-document response, environmental review, public notice with objections, and complex-variance rework.
- Non-stationary arrivals by month, day-of-week, and architect burst behavior.

The process-tree string provided is useful as a conceptual baseline, but the operational simulation should use explicit routing and join logic because the real process contains parallel reviews, decision joins, calendar timers, and cross-case batching that are not fully expressible in the simplified tree.

# 2. Parameter-estimation plan

The estimation plan should separate **PM4Py-based log/model handling** from the simulation engine. PM4Py is used to clean, format, explore, replay, and validate the event log. The simulation engine consumes estimated parameter objects, distributions, calendars, and routing rules.

## 2.1 Log preprocessing with PM4Py

Use PM4Py conventions:

- Case identifier: `case:concept:name`
- Activity name: `concept:name`
- Timestamp: `time:timestamp`
- Resource: `org:resource`

Steps:

1. Load the CSV or database extract into a pandas DataFrame.
2. Convert timestamps to datetime.
3. Use `pm4py.format_dataframe` to standardize the log.
4. Sort by case and timestamp.
5. Preserve case attributes:
   - `case_type`
   - `district`
   - `architect_id`
   - `application_value`
   - `requires_fire`
   - `requires_environment`
   - `requires_public_notice`
6. Create derived attributes:
   - month, week, day-of-week;
   - peak-season flag;
   - top-20 architect flag;
   - case-age features;
   - variant identifier;
   - rework indicators.

PM4Py functions to use where available:

- `pm4py.format_dataframe`
- `pm4py.get_variants`
- `pm4py.discover_directly_follows_graph`
- `pm4py.get_performance_dfg`, if available in the installed version
- `pm4py.filter_time_range`
- `pm4py.filter_variants`
- token-based replay/conformance functions for validation, where appropriate

Because PM4Py APIs can vary by version, the code skeleton should include safe fallbacks.

## 2.2 Arrival-process estimation

Use only `Submit application` events as municipal arrivals.

Estimate:

- Base arrival rate per working day.
- Monthly seasonal multipliers:
  - March-May and September-November approximately 1.7x January-February.
- Day-of-week multipliers:
  - Monday approximately 2.2x Wednesday.
- Hour-of-day distribution if time-of-day patterns are stable.
- Architect burst process:
  - identify top 20 architects by volume;
  - estimate weekly submission counts per architect;
  - estimate burst-size distribution;
  - estimate autocorrelation or self-excitation for repeated submissions in the same week.

Recommended model:

- A **non-homogeneous Poisson process** or **piecewise-constant NHPP** for baseline demand:
  \[
  \lambda(t) = \lambda_0 \cdot s_{month}(t) \cdot s_{dow}(t) \cdot s_{architect}(t)
  \]
- A **burst overlay** for large architects:
  - negative-binomial burst sizes;
  - or a Hawkes/self-exciting process if submission clustering is strong.
- A **case-type mix sampler**:
  - Simple renovation: 45%
  - New residential: 28%
  - Commercial: 17%
  - Complex variance: 10%

If case-type mix varies by season or architect, estimate conditional mix; otherwise use the global mix with sensitivity analysis.

## 2.3 Service-time and waiting-time estimation

Do not collapse service and waiting unless explicitly acknowledged.

Where both start and completion timestamps exist:

- `waiting_time = activity_start - activity_ready_time`
- `service_time = activity_completion - activity_start`

Where only completion timestamps exist:

1. Use the subset of activities with start timestamps, if any, to learn service-time distributions.
2. Reconstruct plausible start times for completion-only activities using:
   - previous event timestamp;
   - resource calendar;
   - queue discipline;
   - observed completion timestamp;
   - empirical waiting summaries.
3. Treat the observed time between consecutive events as a **sojourn time**, not a pure service time.
4. Calibrate the simulation so that generated waiting and service quantiles match the empirical summaries.

Use the provided median/p90 summaries as calibration targets. Fit distributions such as:

- lognormal for human service times;
- gamma or Weibull for variable review work;
- deterministic minimum plus stochastic extension for public notice;
- heavy-tailed lognormal, Weibull, or generalized Pareto for applicant response and objection extensions.

Important limitation: if start timestamps are missing, the log alone cannot uniquely separate waiting from service. The twin should therefore store both the inferred split and an uncertainty flag.

## 2.4 Branching probabilities

Estimate routing probabilities from the log and case attributes.

### Completeness loop

Estimate:

- probability of `Request missing documents` after first `Completeness check`;
- probability of multiple missing-document loops;
- distribution of applicant response time from `Request missing documents` to `Receive missing documents`.

Use case type, application value, architect history, and pre-submission-checker scenario to adjust probabilities.

### Optional reviews

Estimate probabilities for:

- Fire-safety review:
  - observed `requires_fire=yes`;
  - plus imputed probability when building-area threshold is missing.
- Environmental review:
  - observed `requires_environment=yes`;
  - plus district-based environmental sensitivity probability.
- Public-notice period:
  - required for Complex variance;
  - required for some New residential cases;
  - possibly influenced by district and project scale.

Use logistic regression or Bayesian hierarchical models where data are sparse. Do not treat missing threshold variables as observed.

### Legal check

Estimate probability and duration of legal check by case type and variant. Historical variants show that some simple paths skip legal check, while commercial and complex cases often require it.

### Reject/appeal

Estimate:

- probability of rejection after decision drafting or legal check;
- probability of appeal after rejection or legal conflict;
- rework entry probabilities after planning, inspection, legal, or appeal.

Because rework reasons are unstructured and unreliable, use repeat-event patterns as the primary quantitative source and use text only for qualitative validation or scenario construction.

## 2.5 Rework estimation

Build a stage-transition matrix for rework:

- Planning review rework:
  - return to planning or request additional documents.
- Inspection rework:
  - return to inspection scheduling or site inspection.
- Legal rework:
  - return to decision drafting or legal check.
- Appeal:
  - may reopen planning, legal, or inspection steps.

Estimate transition probabilities conditional on:

- case type;
- district;
- application value;
- prior rework count;
- resource pool;
- season, if relevant.

Use heavy-tailed distributions for complex-variance rework because the variant summary shows a long tail.

## 2.6 Resource-calendar estimation

Convert HR calendars into machine-readable capacity calendars.

Resource rules:

- Clerks:
  - 5 FTE;
  - Monday-Friday 08:00-16:00;
  - one clerk dedicated to portal support on Mondays.
- Planners:
  - 8 FTE;
  - Monday-Friday 09:00-17:00;
  - two planners only handle Simple renovation.
- Fire reviewers:
  - 2 FTE equivalent;
  - Tuesday-Thursday only.
- Environmental reviewers:
  - 3 FTE;
  - Monday-Friday;
  - 40% reserved for non-permit duties, so effective permit capacity is approximately 1.8 FTE.
- Inspectors:
  - 4 FTE;
  - field visits Tuesday-Friday;
  - travel time depends on district;
  - batching possible.
- Legal officers:
  - 2 FTE;
  - no work during council meeting weeks except urgent cases.
- System:
  - effectively unlimited capacity.

Add:

- public holidays;
- council-meeting weeks;
- vacation periods if known;
- training or non-permit blocks;
- urgent-case exception capacity for legal.

Validate calendars by checking whether historical events occur outside stated working time. If they do, either correct the calendar or add exception capacity.

## 2.7 Applicant and third-party response estimation

Model applicant response separately from municipal service.

Key distributions:

- Missing-document response:
  - estimate from `Request missing documents` to `Receive missing documents`;
  - median around 5 days in the summary, but heavy-tailed;
  - fit a mixture distribution: responsive applicants, delayed applicants, non-responsive applicants requiring reminders or rejection.
- Environmental consultant reports:
  - embedded in environmental-review waiting/service;
  - model as additional delay for high-risk cases.
- Public-notice objections:
  - not directly observed;
  - infer from public-notice duration distribution;
  - model as latent objection process.

For public notice:

- Minimum duration: 14 calendar days.
- Without objection: 14 days plus small administrative delay.
- With objection: 14 days plus extension distribution, potentially up to 60 days or more.
- Objection probability should be modeled by case type, district, project scale, and historical public-notice duration.

Do not treat objection events as observed. Treat them as latent and validate only against observable duration consequences.

## 2.8 Cross-case dependency estimation

### Architect bursts and related applications

Estimate:

- probability that a top architect submits multiple related cases in the same week;
- correlation of case types and districts within an architect;
- whether related cases tend to reach inspection at similar times.

Use this to parameterize:

- arrival bursts;
- potential document synchronization;
- inspection bundling eligibility.

### Inspection batching

Estimate:

- travel time by district;
- extra travel time for D3 and D5;
- potential travel-time reduction when inspections are batched;
- maximum bundle size;
- acceptable batching window, for example 1-3 working days.

If the flattened log does not contain route-level inspection data, use GIS estimates, expert judgment, and sensitivity analysis rather than pretending batching effects are directly observed.

### Objection clusters

Model objection clusters as latent district-week events. If one case in a district/public-notice window has a long notice duration, related nearby cases may also be delayed. Because objection events are missing, use a mixture or hidden-state model calibrated to public-notice durations.

## 2.9 PM4Py-specific handling

PM4Py should be used for:

- formatting the log;
- variant analysis;
- directly-follows graph analysis;
- performance DFG analysis;
- filtering by case type, time, variant, or attribute;
- replay/conformance checks against the conceptual process tree;
- comparing simulated traces with historical variants.

The simulation engine should not depend on PM4Py for event scheduling. PM4Py is for log and model grounding; the simulator is a separate module.

# 3. Assumptions

## Arrivals

- `Submit application` timestamp marks the start of the municipal process.
- Historical seasonal and day-of-week patterns remain broadly valid unless altered by a scenario.
- Monday submission bursts are real and not solely an artifact of backlogging.
- Top-20 architects generate correlated bursts; this behavior is exogenous unless intervention D7 changes it.
- Emergency or rare expedited cases removed from the log are excluded from the baseline or modeled as a separate urgent class if needed.
- Interventions such as pre-submission checking may change submission quality and possibly submission timing, but do not automatically change total demand unless explicitly modeled.

## Service times

- Where start timestamps are missing, the observed timestamp is treated as a completion or state-change timestamp, not a pure service start.
- Service times are conditional on case type, resource pool, district, and task complexity.
- Municipal service times do not include applicant-side waiting unless explicitly stated.
- Inspection service time includes on-site work and travel; travel is district-dependent.
- System tasks have effectively unlimited capacity and negligible stochastic delay unless a scenario adds integration failures.
- Environmental-review service time includes internal work and waiting for consultant material where not separately visible.

## Routing

- Observed routing flags are reliable for cases where present.
- Missing fire-safety threshold and environmental-sensitivity data are handled probabilistically, not as deterministic false values.
- Decision drafting waits for all required reviews, inspections, and public-notice completion.
- Fire, environmental, and public-notice activities may run partially in parallel where historically observed.
- Legal check is optional for some simple variants but expected for commercial and complex cases.
- Rejection is terminal in the base model; appeals create a rework loop with low probability.

## Resources/calendars

- HR-reconstructed calendars are the best available approximation of resource availability.
- Public holidays and council meetings reduce legal and public-notice administrative capacity.
- Fire reviewers are available only Tuesday-Thursday.
- Environmental reviewers have only 60% effective permit capacity due to non-permit duties.
- Two planners are restricted to Simple renovation; the remaining planners handle broader case types.
- Inspectors perform field visits Tuesday-Friday; Monday is used for scheduling, travel planning, or office work.
- No unplanned absenteeism is included in the baseline; absenteeism is tested in stress scenarios.
- Overtime is not assumed unless explicitly introduced as a scenario.

## Rework

- Rework probabilities can be estimated from repeated activities, even if reason codes are unreliable.
- Rework risk depends on case type, complexity, district, and prior rework count.
- Interventions reduce rework only where causally specified:
  - D1 reduces missing-document loops;
  - D8 may reduce environmental rework through better triage;
  - D9 may reduce objection-driven rework or delay.
- Unstructured rework text is not used as a primary quantitative source.

## Applicant/third-party response

- Missing-document response is applicant-driven and heavy-tailed.
- Applicant response is independent of municipal resource queues unless a reminder process is modeled.
- Public-notice objections are not observed; they are latent events inferred from notice duration.
- Third-party environmental consultant delays are embedded in environmental-review duration unless separately modeled.
- Pre-submission checking reduces missing-document probability but may increase applicant effort before submission.

## Cross-case dependencies

- Cases from the same architect and district can be related and may be eligible for inspection bundling.
- Inspection bundling reduces travel time but can increase waiting for the first case in the bundle.
- Neighborhood objections can affect multiple cases in the same district or notice window.
- Shared resources create indirect dependencies across otherwise unrelated cases.
- The flattened log underrepresents dependencies; therefore, dependency parameters should be scenario-tested rather than treated as precisely known.

## Non-stationary demand

- Demand varies by season and day-of-week.
- Peak months are March-May and September-November.
- Monday arrivals are materially higher than midweek arrivals.
- Simulation horizons must be long enough to cover seasonal cycles.
- Warm-up should not be used to remove seasonality; it should only stabilize initial queue/backlog conditions.

## Missing data

- Objection events are missing and must not be treated as observed.
- Start timestamps are missing for many activities; waiting/service split is partly inferred.
- Environmental sensitivity data are incomplete; use district and project attributes with uncertainty.
- Fire-safety threshold based on building area is not fully available; use observed flags and probabilistic imputation.
- Rare emergency decisions are removed; baseline results should not be interpreted as covering all real-world exceptions.
- Resource calendars are reconstructed from HR data, not directly from event logs; validate where possible.

# 4. Experiment matrix

The experiment matrix should compare the baseline, single interventions, combined interventions, and stress scenarios. Interventions should be evaluated under common random demand streams where possible to isolate policy effects.

| Experiment ID | Intervention / factor | Levels / parameter changes | Expected trade-offs |
|---|---|---|---|
| B | Baseline | Historical parameters, current calendars, current routing, no new policy. | Establishes current performance, bottlenecks, seasonal backlog, and tail behavior. |
| D1 | Pre-submission document checker | Reduce missing-document probability by 30%-60%; reduce completeness rework; applicant preparation time increases before submission. | Shorter municipal cycle for simple cases; lower clerk load; possible applicant friction and submission delay outside municipal control. |
| D2 | Simple-renovation no-inspection rule | Skip site inspection for Simple renovation if `application_value < 50,000` and no prior violations. | Faster simple cases and lower inspector load; risk of undetected defects; requires post-permit quality monitoring. |
| D3 | District-batched inspection scheduling | Batch inspections by district; batching window 1-3 days; travel time reduction 10%-30%, larger for D3/D5. | Higher inspector throughput; lower travel; possible increased waiting for first case in bundle and fairness concerns. |
| D4 | Temporary peak-month inspector | Add one inspector during March-May and September-November. | Reduces peak backlog and inspection tail; cost increases; off-peak effect minimal. |
| D5 | Parallel legal pre-check | For Commercial and Complex variance, legal pre-check can start after planning review; final legal check duration reduced; legal work may occur before all technical reviews complete. | Shorter critical path for complex cases; higher legal utilization; risk of wasted legal work if cases are later rejected or reworked. |
| D6 | Reserve one planner for aging cases | One planner/day reserved for cases above age threshold or SLA risk. | Improves tail and SLA compliance; may increase median cycle time for new cases due to capacity diversion. |
| D7 | Architect-facing appointment slots | Reduce Monday burst by shifting a portion of submissions to Tuesday-Thursday; appointment compliance rate 60%-90%. | Smoother clerk workload; reduced Monday queue spike; possible applicant friction and shift of submissions rather than reduction. |
| D8 | Environmental-review triage | Low-risk environmental cases get faster track; high-risk cases get deeper review; triage uses district, project attributes, and sensitivity probability. | Lower average environmental queue; risk of misclassification; requires robust risk score and sensitivity analysis. |
| D9 | Public-notice objection early-warning | Reduce objection extension duration by 20%-40% or objection probability by 10%-25% through early engagement; affects public-notice tail. | Shorter public-notice tail for affected cases; additional community-engagement cost; effect uncertain because objections are latent. |
| D10 | Combined policy: D1 + D2 + D3 + D4 | Apply document checker, simple no-inspection, district batching, and peak inspector together. | Largest potential flow improvement; frees inspection capacity; interaction effects and compounded assumptions must be tested. |
| C1 | Combined submission-quality and smoothing policy: D1 + D7 | Pre-submission checker plus appointment slots. | Reduces both missing-document loops and Monday clerk spikes; good candidate for simple-case improvement. |
| C2 | Combined complex-case policy: D5 + D9 | Legal pre-check plus objection early warning. | Targets long-tail commercial/complex cases; may reduce p90/p95 duration; legal and notice-side assumptions interact. |
| S1 | Stress: peak demand + objection cluster | Arrival multiplier 1.3 above seasonal peak; Monday burst +20%; objection probability multiplier 1.5; public-notice extension p90 increased. | Tests whether interventions remain effective under demand surge and community-objection pressure. |
| S2 | Stress: resource shortage | One inspector absent for 4 weeks; fire-review capacity reduced by 30%; legal council-meeting restriction extended. | Tests resilience and backlog growth; reveals whether batching or temporary capacity mitigates shortages. |
| S3 | Stress: applicant/third-party slowdown | Missing-document response median +50%; environmental consultant delay +30%; applicant readiness for inspections worsens. | Tests external-dependency risk; shows limits of municipal-side interventions. |
| S4 | Stress: holiday/council congestion | Legal capacity reduced for two holiday/council weeks; public-notice administration delayed; submissions shift before/after holidays. | Tests calendar bottlenecks and the value of legal pre-check and aging-case priority. |

Recommended experimental design:

- Run every policy under at least:
  - base demand;
  - peak-season demand;
  - one stress scenario relevant to the policy.
- Use common random numbers for arrivals and applicant-response streams when comparing policies.
- For D1, D7, and D10, test multiple behavioral response levels because applicant behavior is uncertain.
- For D3, test batching windows of 0, 1, 2, and 3 working days.
- For D4, test temporary inspector start/stop timing.
- For D8, test triage sensitivity because environmental sensitivity data are incomplete.

# 5. Warm-up, replications, and uncertainty treatment

## Simulation horizon

Use a **24-month horizon** per replication as the default. This captures:

- two full seasonal cycles;
- Monday burst behavior;
- council-meeting cycles;
- holiday effects;
- long-tail complex cases and public-notice extensions.

A 12-month horizon may be acceptable for screening, but it is less reliable for policies affecting annual peaks or long-tail cases.

## Warm-up

Because demand is non-stationary, the model should be treated as a **transient simulation**, not a steady-state system.

Warm-up purpose:

- stabilize initial queues and backlog;
- avoid artifacts from starting with an empty system;
- allow resource calendars and seasonal demand to reach realistic WIP levels.

Recommended warm-up:

- If starting empty: discard the first 30-60 days.
- If seeding with historical backlog: discard 14-30 days or until WIP and queue lengths stabilize.
- Use Welch plots or rolling means of:
  - WIP by case type;
  - queue length by resource pool;
  - resource utilization;
  - backlog of aging cases.

Do not use warm-up removal to erase seasonality. Seasonality is part of the experiment.

## Replications

Minimum:

- 30 independent replications per experiment for initial screening.

Recommended for final comparison:

- 100 replications per experiment, especially for tail metrics and complex-variance cases.

Use:

- common random numbers across policies for the same demand and applicant-response scenario;
- independent random streams across replications;
- fixed, recorded seeds.

Example seed scheme:

```text
seed = base_seed + scenario_hash + replication_index
```

Store all seeds and parameter draws to make results reproducible.

## Confidence intervals and uncertainty

For each experiment, estimate:

- median cycle time;
- p90 and p95 cycle time;
- SLA compliance rate;
- resource utilization;
- peak backlog;
- rework rate;
- fairness metrics.

Use:

- bootstrap confidence intervals over replications for medians and quantiles;
- paired differences when using common random numbers;
- Bayesian credible intervals if parameters are estimated through Bayesian hierarchical models.

Heavy-tailed durations require special care:

- prefer medians and quantiles over means;
- report p90, p95, and possibly p99 for complex variance;
- fit tail behavior with lognormal, Weibull, or generalized Pareto alternatives;
- test sensitivity of tail metrics to objection-extension and applicant-response assumptions;
- avoid discarding long cases as outliers unless they are proven data errors.

## Sensitivity analysis

Perform both local and global sensitivity analysis.

Key uncertain parameters:

- Monday burst multiplier.
- Peak-season arrival multiplier.
- Missing-document response distribution.
- Probability of missing documents after completeness check.
- Fire and environmental routing probabilities where thresholds are missing.
- Public-notice objection probability.
- Public-notice objection extension distribution.
- Travel time for D3 and D5.
- Inspection batching travel savings.
- Environmental-review effective capacity.
- Legal capacity during council weeks.
- Rework probabilities for complex variance.
- Prior-violation availability for D2.
- Applicant compliance with appointment slots for D7.

Recommended methods:

- one-factor-at-a-time screening for early experiments;
- fractional factorial design for intervention interactions;
- Sobol indices or variance-based sensitivity analysis for final policy comparison;
- scenario-based robustness analysis for stress tests.

# 6. Validation strategy

Validation should be iterative and layered. The twin should not be used for decisions until it passes face, replay, distributional, resource, bottleneck, and out-of-sample validation.

## Face validation

Present the model logic to process owners, clerks, planners, inspectors, legal officers, and permit managers.

Check:

- activity order;
- routing rules;
- rework logic;
- public-notice behavior;
- inspection batching assumptions;
- council-calendar effects;
- resource constraints;
- intervention definitions.

If domain experts reject a mechanism, revise before calibration.

## Event-log replay validation

Use PM4Py replay and conformance techniques to compare the conceptual process tree against the historical log.

Check:

- fitness of the simplified tree;
- variant coverage;
- missing or infrequent paths;
- whether rework loops are represented adequately;
- whether parallel review behavior is sufficiently approximated.

Because the simplified tree is not a full operational model, use replay mainly for structural validation, not as the sole validation method.

## Distributional validation

Compare simulated outputs with historical data for:

- case cycle time by case type;
- case cycle time by variant group;
- activity waiting times;
- activity service times or sojourn times where service is not identifiable;
- missing-document response times;
- public-notice durations;
- inspection waiting and travel-related durations;
- rework counts;
- rejection rates.

Use:

- Q-Q plots;
- empirical CDF comparison;
- Kolmogorov-Smirnov or Anderson-Darling tests for distributional similarity;
- quantile absolute error for median, p90, and p95;
- continuous ranked probability score if comparing full predictive distributions.

Acceptance should be based on practical fit, not only statistical significance. With 31,200 cases, small deviations may be statistically significant but operationally irrelevant.

## Resource-utilization validation

Compare simulated resource utilization against inferred historical utilization.

Check:

- clerk utilization, especially Mondays;
- planner utilization by case type;
- fire-review utilization on Tuesday-Thursday;
- environmental-review effective capacity after non-permit duties;
- inspector utilization and travel time;
- legal utilization excluding council weeks;
- queue lengths before key activities.

If start timestamps are missing, use completion timestamps, calendars, and queue reconstruction to estimate plausible busy fractions. Treat this validation as approximate.

## Bottleneck validation

The model should reproduce known bottleneck patterns:

- Monday completeness-check queue spikes;
- planning-review queue dependence on district and case type;
- fire-review constraint due to Tuesday-Thursday availability;
- environmental-review variability;
- inspection waiting due to inspector availability and district travel;
- legal delays during council weeks;
- public-notice tail due to objections.

Validate time-dependent bottlenecks:

- seasonal peaks;
- Monday effects;
- council-week effects;
- holiday periods.

## Out-of-sample validation

Use temporal holdout:

- calibrate on the first 15 months;
- validate on the last 3 months.

Alternative holdouts:

- hold out selected districts;
- hold out selected architects;
- hold out one season.

For intervention validation, use natural experiments if available:

- periods with unusual inspector absence;
- periods with council-meeting congestion;
- periods with unusually high Monday submissions;
- periods with public-notice delays.

Do not claim exact optimality or causal policy effects from an unvalidated model. Validation establishes credibility, not certainty.

# 7. Decision criteria

The municipality should use a multi-criteria decision framework. No single metric is sufficient, and simulation results should be interpreted with confidence intervals and scenario robustness.

## Primary performance metrics

| Metric | Definition | Why it matters |
|---|---|---|
| Median cycle time by case type | Days from submission to final decision. | Typical applicant experience. |
| p90/p95 cycle time by case type | Tail duration. | Captures long-tail pain and political risk. |
| SLA compliance by case type | Share of cases completed within target days. | Operational accountability. |
| Backlog/WIP | Open cases by stage and age. | Capacity pressure and staffing needs. |
| Rework rate | Share of cases with one or more rework loops. | Quality and process stability. |
| Resource utilization | Busy time divided by available capacity. | Efficiency and overload risk. |
| Fairness across districts/architects | Disparity in cycle time or SLA compliance. | Equity and political acceptability. |
| Robustness | Performance stability across stress scenarios. | Resilience to demand and resource shocks. |

## Illustrative SLA targets

These should be confirmed by the municipality, but reasonable starting targets based on the variant summary are:

| Case type | Median target | p90 target |
|---|---:|---:|
| Simple renovation | 20 days | 40 days |
| New residential | 60 days | 100 days |
| Commercial | 80 days | 140 days |
| Complex variance | 160 days | 280 days |

An intervention should be considered beneficial if it improves SLA compliance without causing unacceptable harm elsewhere.

## Thresholds and decision ranges

Recommended decision rules:

- Median cycle time:
  - meaningful improvement if at least 5% or one day for simple cases;
  - at least 5 days for complex cases.
- Tail cycle time:
  - no intervention should materially worsen p90 or p95;
  - preferred interventions reduce p90 by at least 5%-10% for affected case types.
- SLA compliance:
  - improvement of at least 3-5 percentage points for a target case type;
  - no more than 1-2 percentage point degradation for other case types unless explicitly accepted.
- Resource utilization:
  - sustainable average utilization around 65%-85%;
  - avoid sustained utilization above 90% for human resources;
  - temporary inspector should have sufficient peak utilization to justify cost.
- Rework and quality:
  - rework rate should not increase by more than 1 percentage point;
  - inspection skipping should be accompanied by risk monitoring or post-permit audit assumptions.
- Fairness:
  - p90 cycle time ratio across districts should not exceed approximately 1.25-1.30;
  - small architects should not be systematically worse than top architects by more than 10 percentage points in SLA compliance;
  - batching should not disproportionately harm D3/D5 or low-volume applicants.
- Backlog:
  - peak WIP should not grow under baseline demand;
  - aging cases above SLA threshold should decline under priority interventions.
- Robustness:
  - preferred policies should remain beneficial under at least two stress scenarios;
  - avoid policies that collapse under modest demand or capacity shocks.

## Cost and effort metrics

Include qualitative or monetized estimates for:

- pre-submission checker development and applicant support;
- temporary inspector cost;
- additional legal capacity;
- community-engagement cost for objection early warning;
- applicant time cost for appointments and document checking;
- administrative cost of batching and scheduling.

## Decision rule

Use a staged decision approach:

1. Eliminate interventions that worsen tail performance, fairness, or quality beyond acceptable thresholds.
2. Shortlist interventions with robust median and SLA improvements.
3. Compare combined policies against single policies.
4. Run sensitivity analysis on uncertain behavioral parameters.
5. Pilot the leading intervention before full rollout.

The simulation supports comparison and risk assessment; it does not prove exact optimality.

def safe_parse_process_tree(tree_string: str) -> Tuple[Optional[Any], Optional[str]]:
    """
    Attempt to parse the simplified process tree.

    The supplied tree string is conceptual. It may not parse in every PM4Py
    version because of tau handling, quoting, and simplified XOR/loop syntax.
    If parsing fails, keep the string as documentation and implement explicit
    routing in the simulation engine.
    """
    if pm4py is None:
        return None, "PM4Py is not installed; process tree string kept as documentation."

    parse_functions = []

    if hasattr(pm4py, "parse_process_tree"):
        parse_functions.append(pm4py.parse_process_tree)

    try:
        from pm4py.objects.process_tree.utils import parse as pt_parse

        if hasattr(pt_parse, "parse_process_tree"):
            parse_functions.append(pt_parse.parse_process_tree)
        elif callable(pt_parse):
            parse_functions.append(pt_parse)
    except Exception:
        pass

    last_error = None
    for fn in parse_functions:
        try:
            return fn(tree_string), None
        except Exception as exc:
            last_error = exc

    return None, f"Simplified tree could not be parsed by available PM4Py API: {last_error}"

def _unwrap_dfg(result: Any) -> Dict[Tuple[str, str], Any]:
    """Some PM4Py DFG functions return tuples containing start/end activities."""
    if isinstance(result, tuple) and len(result) > 0:
        return result[0]
    return result


def discover_dfg_safe(df: pd.DataFrame) -> Dict[Tuple[str, str], int]:
    """Return a frequency DFG using PM4Py if possible, otherwise pandas."""
    if pm4py is not None:
        for fn_name in ["discover_directly_follows_graph", "get_dfg"]:
            fn = getattr(pm4py, fn_name, None)
            if fn is None:
                continue
            try:
                return _unwrap_dfg(fn(df))
            except Exception as exc:
                warnings.warn(f"pm4py.{fn_name} failed; trying fallback: {exc}")

    dfg: Dict[Tuple[str, str], int] = {}
    for _, group in df.sort_values([CASE_ID, TIMESTAMP]).groupby(CASE_ID, sort=False):
        activities = group[ACTIVITY].tolist()
        for current_activity, next_activity in zip(activities, activities[1:]):
            key = (current_activity, next_activity)
            dfg[key] = dfg.get(key, 0) + 1
    return dfg


def performance_dfg_safe(df: pd.DataFrame) -> Dict[Tuple[str, str], float]:
    """
    Return a performance DFG.

    If PM4Py provides get_performance_dfg, use it. Otherwise compute average
    elapsed days between directly-following events per case. This fallback is
    a sojourn-based performance measure, not a clean service-time measure.
    """
    if pm4py is not None and hasattr(pm4py, "get_performance_dfg"):
        try:
            return _unwrap_dfg(pm4py.get_performance_dfg(df))
        except Exception as exc:
            warnings.warn(f"pm4py.get_performance_dfg failed; using pandas fallback: {exc}")

    performance: Dict[Tuple[str, str], List[float]] = {}
    for _, group in df.sort_values([CASE_ID, TIMESTAMP]).groupby(CASE_ID, sort=False):
        activities = group[ACTIVITY].tolist()
        times = group[TIMESTAMP].tolist()
        for (current_activity, next_activity), (current_time, next_time) in zip(
            zip(activities, activities[1:]),
            zip(times, times[1:]),
        ):
            key = (current_activity, next_activity)
            elapsed_days = (next_time - current_time).total_seconds() / 86_400.0
            performance.setdefault(key, []).append(elapsed_days)

    return {key: float(np.mean(values)) for key, values in performance.items() if values}


def arrival_summary(df: pd.DataFrame) -> Dict[str, float]:
    """Compute simple arrival-rate summaries from Submit application events."""
    submissions = df[df[ACTIVITY] == "Submit application"].copy()

    if submissions.empty:
        return {
            "total_submissions": 0.0,
            "average_submissions_per_observed_day": 0.0,
            "average_submissions_per_calendar_day_over_window": 0.0,
        }

    daily = submissions.groupby(submissions[TIMESTAMP].dt.date).size()
    window_days = max(
        (submissions[TIMESTAMP].max().normalize() - submissions[TIMESTAMP].min().normalize()).days + 1,
        1,
    )

    return {
        "total_submissions": float(len(submissions)),
        "average_submissions_per_observed_day": float(daily.mean()),
        "average_submissions_per_calendar_day_over_window": float(len(submissions) / window_days),
    }


def add_timing_columns(df: pd.DataFrame) -> pd.DataFrame:
    """
    Add timing columns.

    If only completion timestamps are available, service_time_days and
    waiting_before_activity_days remain NaN. sojourn_since_previous_days is
    still computed, but it mixes waiting, service, calendar effects, and
    applicant/third-party delay.
    """
    df = df.sort_values([CASE_ID, TIMESTAMP]).copy()
    df["prev_timestamp"] = df.groupby(CASE_ID)[TIMESTAMP].shift(1)

    delta_days = (df[TIMESTAMP] - df["prev_timestamp"]).dt.total_seconds() / 86_400.0
    df["sojourn_since_previous_days"] = delta_days
    df.loc[df[ACTIVITY] == "Submit application", "sojourn_since_previous_days"] = 0.0

    if "start_timestamp" in df.columns:
        df["start_timestamp"] = pd.to_datetime(df["start_timestamp"])
        df["service_time_days"] = (
            df[TIMESTAMP] - df["start_timestamp"]
        ).dt.total_seconds() / 86_400.0
        df["waiting_before_activity_days"] = (
            df["start_timestamp"] - df["prev_timestamp"]
        ).dt.total_seconds() / 86_400.0
    else:
        df["service_time_days"] = np.nan
        df["waiting_before_activity_days"] = np.nan

    return df

class ResourceCalendar:
    """
    Calendar placeholder.

    A production implementation should contain resource-specific patterns,
    holidays, council weeks, vacations, and non-permit duty reductions.
    """

    PATTERNS = {
        "mon_fri_08_16": {"days": {0, 1, 2, 3, 4}, "start": 8, "end": 16},
        "mon_fri_09_17": {"days": {0, 1, 2, 3, 4}, "start": 9, "end": 17},
        "tue_thu_09_17": {"days": {1, 2, 3}, "start": 9, "end": 17},
        "field_tue_fri": {"days": {1, 2, 3, 4}, "start": 8, "end": 17},
    }

    def __init__(
        self,
        pattern: str,
        holidays: Optional[List[pd.Timestamp]] = None,
        council_weeks: Optional[List[pd.Timestamp]] = None,
    ):
        self.pattern = pattern
        self.holidays = set(pd.to_datetime(holidays or []).normalize())
        self.council_weeks = set(pd.to_datetime(council_weeks or []).normalize())

    def _in_council_week(self, ts: pd.Timestamp) -> bool:
        week_start = ts.normalize() - pd.Timedelta(days=ts.weekday())
        return week_start in self.council_weeks

    def is_available(self, ts: pd.Timestamp) -> bool:
        pattern = self.PATTERNS.get(
            self.pattern,
            {"days": {0, 1, 2, 3, 4}, "start": 8, "end": 16},
        )

        if ts.weekday() not in pattern["days"]:
            return False
        if not (pattern["start"] <= ts.hour < pattern["end"]):
            return False
        if ts.normalize() in self.holidays:
            return False

        if "legal" in self.pattern and self._in_council_week(ts):
            return False

        return True

class RoutingPolicy:
    """
    Routing logic for the simulation engine.

    The simplified process tree is not sufficient for operational routing.
    This class encodes explicit business rules and policy interventions.
    """

    def __init__(self, scenario: Scenario):
        self.scenario = scenario

    def requires_fire(self, case: Dict[str, Any]) -> bool:
        if str(case.get("requires_fire", "no")).lower() == "yes":
            return True
        return float(case.get("fire_probability_imputed", 0.0)) > 0.5

    def requires_environment(self, case: Dict[str, Any]) -> bool:
        if str(case.get("requires_environment", "no")).lower() == "yes":
            return True
        return float(case.get("environment_probability_imputed", 0.0)) > 0.5

    def requires_public_notice(self, case: Dict[str, Any]) -> bool:
        if case.get("case_type") == "Complex variance":
            return True
        if str(case.get("requires_public_notice", "no")).lower() == "yes":
            return True
        return False

    def inspection_required(self, case: Dict[str, Any]) -> bool:
        if self.scenario.skip_simple_inspection:
            if (
                case.get("case_type") == "Simple renovation"
                and float(case.get("application_value", 0.0)) < 50_000
                and not bool(case.get("prior_violations", False))
            ):
                return False
        return True

    def legal_precheck_allowed(self, case: Dict[str, Any]) -> bool:
        return bool(
            self.scenario.parallel_legal_precheck
            and case.get("case_type") in {"Commercial", "Complex variance"}
        )

class ExperimentRunner:
    """Run replications for scenarios and collect KPIs."""

    def __init__(self, log_stats: Dict[str, Any]):
        self.log_stats = log_stats

    def run_experiment(
        self,
        scenario: Scenario,
        replications: int = 30,
        horizon_days: int = 730,
        warmup_days: int = 60,
    ) -> pd.DataFrame:
        frames = []

        for replication in range(replications):
            seed = abs(hash(scenario.name)) % 100_000 + replication
            rng = np.random.default_rng(seed)

            resource_pools = build_resource_pools(scenario)
            simulator = DigitalTwinSimulator(
                scenario=scenario,
                log_stats=self.log_stats,
                resource_pools=resource_pools,
                rng=rng,
            )

            kpis = simulator.run(horizon_days=horizon_days, warmup_days=warmup_days)

            if kpis.empty:
                kpis = pd.DataFrame(columns=DigitalTwinSimulator.KPI_COLUMNS)

            kpis = kpis.assign(scenario=scenario.name, replication=replication, seed=seed)
            frames.append(kpis)

        if not frames:
            return pd.DataFrame()

        return pd.concat(frames, ignore_index=True)
