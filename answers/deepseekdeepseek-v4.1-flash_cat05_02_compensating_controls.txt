```python
def _case_ids_from_pm4py_object(obj):
    cases = set()
    if isinstance(obj, pd.DataFrame):
        if "case:concept:name" in obj.columns:
            return set(obj["case:concept:name"].dropna().unique())
        if "case:concept:name" in obj.index.names:
            return set(obj.index.get_level_values("case:concept:name").unique())
    try:
        for trace in obj:
            if hasattr(trace, "attributes"):
                cid = trace.attributes.get("concept:name") or trace.attributes.get("case:concept:name")
                if cid:
                    cases.add(cid)
            for event in trace:
                if isinstance(event, dict):
                    cid = event.get("case:concept:name")
                    if cid:
                        cases.add(cid)
    except TypeError:
        pass
    return cases

try:
```

```python
# ============================================================
# PRELIMINARY CONTROL-EVIDENCE CHECK — NOT A COMPLIANCE VERDICT
# ============================================================
import io
import pandas as pd
try:
    import pm4py
except ImportError as e:
    raise ImportError("This script requires pm4py. Install it to run the PM4Py checks.") from e

csv_text = """case:concept:name,concept:name,time:timestamp,org:resource
AP-201,Prepare_Payment,2026-05-04T08:00:00Z,u17
...
AP-209,Audit_Review,2026-05-05T10:00:00Z,a07
"""

df = pd.read_csv(io.StringIO(csv_text))
df["org:resource"] = df["org:resource"].fillna("SYSTEM")
df["time:timestamp"] = pd.to_datetime(df["time:timestamp"], utc=True).dt.tz_convert(None)

# PM4Py formatting (naive UTC for compatibility)
formatted = pm4py.format_dataframe(
    df.copy(),
    case_id="case:concept:name",
    activity_key="concept:name",
    timestamp_key="time:timestamp"
)
log = pm4py.convert_to_event_log(formatted)

def case_ids_from_pm4py(obj):
    cases = set()
    if isinstance(obj, pd.DataFrame):
        if "case:concept:name" in obj.columns:
            return set(obj["case:concept:name"].dropna().unique())
        if "case:concept:name" in obj.index.names:
            return set(obj.index.get_level_values("case:concept:name").unique())
    try:
        for trace in obj:
            attrs = getattr(trace, "attributes", {})
            cid = attrs.get("concept:name") or attrs.get("case:concept:name")
            if cid:
                cases.add(cid)
            for ev in trace:
                if isinstance(ev, dict):
                    cid = ev.get("case:concept:name")
                    if cid:
                        cases.add(cid)
    except Exception:
        pass
    return cases

try:
    fe_log = pm4py.filter_four_eyes_principle(log, "Prepare_Payment", "Release_Payment")
    pm4py_fe_cases = case_ids_from_pm4py(fe_log)
except Exception as e:
    pm4py_fe_cases = set()
    print("[WARN] pm4py.filter_four_eyes_principle failed or returned unexpected type:", e)

# Manual completed-payment same-user check
prep = df[df["concept:name"] == "Prepare_Payment"][["case:concept:name", "org:resource"]].rename(columns={"org:resource": "preparer"})
rel = df[df["concept:name"] == "Release_Payment"][["case:concept:name", "org:resource"]].rename(columns={"org:resource": "releaser"})
pay = prep.merge(rel, on="case:concept:name", how="inner")
pay["same_user"] = pay["preparer"] == pay["releaser"]
manual_same_completed = set(pay.loc[pay["same_user"], "case:concept:name"])

# Attempted but blocked releases
attempt_cases = set(df.loc[df["concept:name"].isin(["Attempt_Release", "Automated_Validate_Block"]), "case:concept:name"])
release_cases = set(df.loc[df["concept:name"] == "Release_Payment", "case:concept:name"])
blocked_attempt_cases = sorted(attempt_cases - release_cases)

# Event timing
def first_time(sub, activity):
    s = sub.loc[sub["concept:name"] == activity, "time:timestamp"]
    return s.min() if not s.empty else pd.NaT

def prefix_time(sub, prefix):
    s = sub.loc[sub["concept:name"].str.startswith(prefix, na=False), "time:timestamp"]
    return s.min() if not s.empty else pd.NaT

time_rows = []
for c in sorted(df["case:concept:name"].unique()):
    sub = df[df["case:concept:name"] == c]
    time_rows.append({
        "case": c,
        "prepare_time": first_time(sub, "Prepare_Payment"),
        "release_time": first_time(sub, "Release_Payment"),
        "settlement_time": first_time(sub, "Bank_Settlement"),
        "manager_time": sub.loc[sub["concept:name"].isin(["Manager_Approve", "Manager_Ratify"]), "time:timestamp"].min(),
        "audit_time": first_time(sub, "Audit_Review"),
        "av_time": prefix_time(sub, "Automated_Validate"),
    })
timing = pd.DataFrame(time_rows)

def manager_phase(row):
    mt, rt, st = row["manager_time"], row["release_time"], row["settlement_time"]
    if pd.isna(mt):
        return "none"
    if pd.notna(rt) and mt < rt:
        return "before_release"
    if pd.notna(st) and mt < st:
        return "after_release_before_settlement"
    if pd.notna(st) and mt >= st:
        return "after_settlement"
    return "after_release_no_settlement_record"

timing["manager_timing_event"] = timing.apply(manager_phase, axis=1)
timing["audit_hours_after_release"] = (timing["audit_time"] - timing["release_time"]).dt.total_seconds() / 3600.0
timing["audit_within_24h_of_release"] = timing["audit_hours_after_release"].fillna(9999) <= 24

# Case facts constructed from the prompt table
facts = pd.DataFrame([
    {"case":"AP-201","amount_eur":1800,"vendor_active_ge_180":True,"bank_change_prev_7d":False,
```

## 1. Control-Objective Decomposition

FEP-1 is not merely “Prepare resource  Release resource.” Its objective is to prevent, or otherwise keep within tolerable risk, a single human actor from initiating and authorizing an erroneous or fraudulent transfer. The control objective decomposes into at least these threat/objective scenarios:

| Objective / threat scenario | What FEP-1 is trying to achieve | AV-2 role | MG-4 role | RA-7 role | ED-1 role |
|---|---|---|---|---|---|
| Erroneous payment due to keying, duplicate, wrong amount, wrong PO | Prevent bad payment data from being released | Prevents/blocks duplicates, amount-limit breaches, basic PO mismatches; warns otherwise | Can prevent if reviewer actually checks invoice/amount/PO before release/settlement | Detects after the fact; corrects only if recall still possible | Permits same-user only if AV-2 fully passed, amount <100k, and independent manager approves before settlement |
| Fraudulent vendor or bank-account redirection | Prevent one actor from sending money to a controlled/compromised account | Checks sanctions, bank ownership, recent bank changes; can block or warn | Strongest if independent manager verifies bank details before release/settlement | Detects later; recovery uncertain after 24h | Excludes bank changes in prior 7 days and requires independent approval before settlement |
| Duplicate/replayed invoice | Prevent paying twice | AV-2 duplicate check is preventive | Can detect if reviewer compares invoice/PO | Detects later; corrective only within recall | Requires AV-2 full pass, so duplicate should be blocked |
| Limit/authority breach and override abuse | Prevent preparer/releaser from exceeding authority or overriding warnings | Enforces operator limit and can warn/block | Requires L3+ independent approval; weak if rubber-stamped or conflicted | Can detect override patterns after the fact | Caps amount at EUR 100,000; override not allowed; AV-2 must pass without override |
| Emergency same-user handling | Allow legitimate emergency single-operator use without losing the control objective | Must be fully operational and pass without override | Must approve before bank settlement | Must audit emergency same-user payments 100% within one business day | Permission rule with seven conditions; failure of any condition removes ED-1 protection |
| Collusion or shared-account/workstation defeat of nominal four-eyes | Ensure the “second pair of eyes” is genuinely independent | Does not detect collusion | Fails if manager is conflicted, rubber-stamps, or shares credential | May detect via audit, but after settlement | Does not address collusion; ED-1 still assumes independent approval |
| Lack of goods/services receipt or commercial reasonableness | Prevent payment for fictitious services | Does not establish receipt or commercial reasonableness | Can cover if manager reviews receipt/service evidence | Detective; can trigger recovery if timely | Not sufficient by itself; ED-1 does not waive receipt concerns |
| Irrecoverable transfer/late detection | Prevent loss from becoming final | Preventive only at release point | Preventive/hybrid before settlement; weak after settlement | Detective; partly corrective only before recall window | Requires audit within one business day and manager approval before settlement |

## 2. Equivalence and Sufficiency Test

A compensating package should be graded against the control objective, not merely against whether some control event occurred. Use this structured test:

| Level | Test |
|---|---|
| Fully equivalent | Independent human authorization remains effective before release, or ED-1 is fully satisfied. AV coverage covers all material automated risks. MG-4 is truly independent, timely, and evidence-based. RA-7 is timely and within recall/correction capability if detective. No unresolved override. Evidence is strong. Collusion resistance is at least as good as nominal four-eyes. Residual risk is tolerable for case risk. |
| Partially equivalent | The package substantially reduces the FEP risk but has a material weakness: e.g., independent manager review occurs after release but before irrevocable settlement; ED-1 is nearly satisfied but one condition is unproven; AV covers most but not all material risks; independence exists formally but is weakened by shared workstation/pair concentration. Residual risk may be tolerable only with enhanced monitoring or low case risk. |
| Merely mitigating | The package detects or limits loss after the risky act, but does not preserve independent authorization before release or settlement. Examples: post-settlement manager ratification, late audit, overridable AV warning, conflicted manager, weak evidence. It may reduce expected loss but does not meet the segregation objective. |
| Ineffective | The same actor or a compromised credential effectively controls both initiation and authorization; AV is unavailable or overridden by the preparer; manager is conflicted/late after settlement; audit is after recall; high-risk facts such as bank change, new vendor, high amount, or no receipt are present; corrective capacity is absent. |

Key dimensions:

- **Timing:** Preventive before release is strongest. Approval after release but before irrevocable settlement is weaker/hybrid. After settlement, it is mostly detective and only partly corrective within recall.
- **Independence:** Different user IDs are not enough. Consider shared accounts, shared workstations, reporting lines, credential sharing, repeated pairs, and actual review evidence.
- **Coverage:** AV-2 covers duplicate, sanctions, bank ownership, seven-day bank changes, operator limit, basic PO match. It does not prove receipt, commercial reasonableness, or collusion resistance.
- **Overrideability:** A warning overridden by the preparer or by the preparer using another manager’s credential is not equivalent to a preventive block.
- **Recoverability:** A control is corrective only if it can stop, recall, or recover the payment. Bank recall is usually available within 24 hours; after that, recovery is uncertain.
- **Evidence quality:** Signed checklists, bank callback evidence, receipt/PO/service evidence, override logs, credential assignment logs, and audit working papers matter. Unsigned or rubber-stamped approvals are weak.
- **Collusion resistance:** Four-eyes can be defeated by collusion. Repeated pairs, shared workstations, conflicted managers, and shared credentials require monitoring, rotation, or independent audit.
- **Case risk:** Amount, vendor age, bank-change proximity, emergency status, and settlement status affect whether a partial package is tolerable.

“Same expected loss” is not the only possible standard because FEP-1 also serves legal/regulatory compliance, fraud deterrence, accountability, process integrity, reputation protection, and tail-risk reduction. A post-settlement detective control might produce similar expected loss in some models while still failing the control objective because it does not prevent unauthorized authorization, does not deter collusion, and may not satisfy regulators or auditors.

| AP-207 | Emergency safety repair same-user payment | ED-1 conditions, m15 before settlement, timely audit | Emergency necessity evidence | Independent second releaser would improve nominal compliance but may slow emergency repair; ED-1 already permits the same-user action. |

## 6. Evidence and Monitoring Recommendations

Collect and monitor:

- **Same-user completed-payment rate:** Track by user, team, emergency token status, and ED-1 eligibility. Alert on any non-emergency same-user completed payment. This is an alert, not proof of misconduct.
- **Override rate:** Monitor AV warning overrides by preparer, releaser, and credential owner. Alert when the preparer overrides or uses another user’s override credential, especially for bank change, limit breach, new vendor, or sanctions flags.
- **Late manager approval:** Flag manager approval after release but before settlement as hybrid; flag approval after settlement as weak. Alert on conflicted managers, direct supervisors, or repeated rubber-stamp patterns.
- **Audit before recall window:** Compute time from release/settlement to audit. Alert if audit is after 24 hours for high-risk payments or after one business day for emergency same-user payments. Distinguish “audit completed” from “audit before recall.”
- **Repeated resource pairs:** Monitor pair concentration, especially same pair across many payments. Alert if a pair exceeds a risk threshold or shares a workstation. Pair concentration is a risk indicator, not proof of collusion.
- **Shared workstations and shared/service accounts:** Check access logs, login IDs, credential assignment, and physical workstation use. Shared workstation use weakens independence even when user IDs differ.
- **Bank-change proximity:** Require enhanced verification for payments to vendors whose bank account changed within the previous seven days. AV-2 should block or warn; MG-4 must independently verify bank ownership.
- **Control outages:** When AV-2 is unavailable, high-risk or high-value payments should not proceed on same-user emergency logic. Require independent manager approval before settlement, signed manual checklist, and post-payment audit within recall.
- **Evidence quality:** Retain override logs, emergency token timestamps, manager review evidence, receipt/PO/goods-receipt proof, bank callback records, audit working papers, and recovery attempts.
- **Alert vs proof:** Alerts show control weakness, elevated risk, or anomaly. Proof of misconduct requires corroborated logs, interviews, bank records, receipt verification, credential assignment records, and consistent pattern analysis. Do not treat a metric alone as a misconduct finding.

PM4Py behavior that cannot be guaranteed across versions: `filter_four_eyes_principle` may return an `EventLog`, a `DataFrame`, a set of case IDs, or another filtered object depending on the PM4Py version. The helper `case_ids_from_pm4py` handles common return shapes, but the exact column names, timezone handling, and trace/event object attributes may vary. `format_dataframe` may also mutate or rename columns differently across versions. The code converts timestamps to naive UTC for broad compatibility; if your PM4Py version prefers timezone-aware timestamps, remove `.dt.tz_convert(None)`. The PM4Py filter only flags nominal completed-payment same-user violations; it does not judge ED-1 eligibility, control sufficiency, independence, recoverability, or collusion risk.
