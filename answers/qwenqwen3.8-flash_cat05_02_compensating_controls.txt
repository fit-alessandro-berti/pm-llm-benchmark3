## 1. Control-Objective Decomposition

FEP-1 is not merely a staffing rule; it is a segregation-of-duties control intended to reduce the risk that one person can both initiate and authorize a transfer. The control objective should be assessed against the following threat scenarios.

| Objective / threat scenario | What the control objective requires | AV-2 | MG-4 | RA-7 | ED-1 |
|---|---|---|---|---|---|
| **1. Single actor initiates and authorizes a payment** | Prevent one human from both preparing and releasing an erroneous or fraudulent transfer | Does **not** establish human independence. Can prevent some attribute errors but cannot replace a second human actor. | Can prevent if independent and performed before release; can detect if performed after release; weak if rubber-stamped. | Detective only; corrective only if the transfer can still be stopped, recalled, or recovered. | Prevents only when all conditions are enforced. If token, amount, vendor, bank-change, AV, manager, or audit conditions fail, ED-1 does not justify single-user handling. |
| **2. Payment is sent to the wrong bank account or an account recently changed by a fraudster** | Verify account ownership, recent bank-detail changes, and vendor master integrity before irrevocable settlement | Strong preventive control for bank-account ownership and seven-day bank-change checks; a clean pass is evidence only for those covered checks. | Preventive if manager independently reviews bank details before release or settlement; detective if after settlement. | Detects after the fact; corrects only within the recall window or through recovery. | Requires no bank-account change in the previous seven days. If AV-2 is unavailable or bank change exists, ED-1 fails. |
| **3. Duplicate, invalid, over-limit, or unsupported invoice is paid** | Stop duplicates, limit breaches, and basic PO mismatches before release | Preventive for duplicate invoice, operator limit, sanctions status, and basic PO match. Does **not** prove goods/services were received. | Preventive/detective if manager reviews invoice and supporting receipt before release; weak if late. | Detective; may trigger recovery if timely. | Requires AV-2 fully operational and passed without override. An override or AV outage breaks the ED-1 package. |
| **4. ## 2. Equivalence and Sufficiency Test

A compensating-control package should be judged by whether it achieves the **control objective**, not merely by whether a control event appears in the log. The following structured test can be applied.

### Dimensions of the test

| Dimension | Key question | Fully equivalent standard | Partially equivalent / tolerable | Merely mitigating | Ineffective |
|---|---|---|---|---|---|
| **Timing** | Did the control act before the point of no return? | Independent approval or block before release or before irrevocable settlement. | Control acts after release but before settlement, with low risk and no override. | Control acts after settlement or after recall window. | Control occurs too late to stop or recover the payment. |
| **Independence** | Is the reviewer a genuinely independent human actor? | Different person, not subordinate, no unresolved conflict, not using shared credentials. | Reviewer independent but timing or documentation is imperfect. | Reviewer nominally independent but relationship, credential, or workstation facts are unresolved. | Reviewer is preparer, subordinate, credential owner who enabled override, or rubber-stamp. |
| **Coverage** | Does the package cover the material risk in the case? | Covers bank ownership, recent bank change, duplicate/limit checks, receipt or service evidence, and emergency conditions where relevant. | Covers most material risks; one non-critical gap exists. | Covers some risks but misses the dominant threat, such as receipt validation or bank-change risk. | Does not cover the actual loss mechanism. |
| **Overrideability** | Can the preparer defeat the control? | No override by preparer; overrides require independent authorization and evidence. | Override possible but not used, or used under strong compensating review. | Override possible and used without independent authorization. | Preparer uses manager credential or otherwise defeats the control. |
| **Recoverability** | Can a defect still be stopped, recalled, or recovered? | Detection occurs before settlement or within recall window. | Detection occurs shortly after settlement but recovery remains plausible. | Detection occurs after recall window; recovery uncertain. | Detection occurs too late; funds unrecoverable. |
| **Evidence quality** | Is there verifiable evidence that the control actually operated? | Token logs, manager review artifacts, AV logs, override authorization, bank-change evidence, audit completion evidence. | Some evidence exists but is incomplete or inferred. | Evidence is weak, unsigned, or contradictory. | Evidence is missing, unavailable, or indicates the control did not operate. |
| **Collusion resistance** | Does the design resist repeated pairs, shared workstations, and dedicated cells? | Rotating reviewers, independent manager, analytics, segregation, no shared workstation, no repeated unexplained pairs. | Repeated pairs exist but other controls are strong and no defect found. | Repeated pairs and shared workstation create unresolved independence concerns. | Actual collusion, fabricated evidence, or shared credential use is present. |

### Decision rule

- **Fully equivalent / OBJECTIVE_MET**: The package closes the dominant threat with independent, timely, non-overrideable, well-evidenced controls. For single-user payments, ED-1 conditions must be satisfied or the case must otherwise have an equivalent independent pre-settlement control.
- **Partially equivalent / OBJECTIVE_PARTIALLY_MET**: A nominal FEP-1 violation exists, but compensating controls reduce the risk to a tolerable level for that case. Example: low-value, stable vendor, clean AV-2, independent manager before settlement, but no emergency token.
- **Merely mitigating**: Controls reduce likelihood or impact but do not substitute for the objective. Example: late audit after settlement, unsigned manual checklist, or manager review without evidence of substantive inspection.
- **Ineffective / OBJECTIVE_FAILED**: The control package does not address the actual loss mechanism. Example: AV-2 warning overridden by the preparer, dependent manager ratifies late, bank-change risk ignored, or fabricated receipt defeats nominal segregation.
- **Indeterminate / INDETERMINATE**: Key facts are unresolved, such as whether an emergency token was genuinely active before preparation or whether a repeated resource pair is an authorized independent cell.

### Why “same expected loss” is not the only standard

Expected loss is useful but insufficient because it can hide:

- **Irrecoverability**: A low-probability, high-severity, non-recoverable fraud may be unacceptable even if average loss is small.
- **Deterrence and accountability**: Controls deter misconduct and create evidence; expected loss does not capture those governance effects.
- **Collusion risk**: Two nominal humans can behave like one actor if they share a workstation, are a fixed pair, or use shared credentials.
- **Evidence quality**: A control that cannot be proven may fail audit, legal, or regulatory expectations even if no loss occurred.
- **Systemic effects**: Repeated overrides, control outages, or weak manager independence can indicate process degradation beyond one case.
- **Tail risk and fraud**: Fraud is not well represented by normal-loss averages; control design must address intentional misconduct.

## 4. Preventive–Detective–Corrective Comparison

| **RA-7** | After release/settlement | Not preventive | Strong detective if 100% emergency audit, analytics, and exception review are performed | Corrective only within recall window or through recovery | Becomes weak if audit occurs after settlement and after the 24-hour recall window |
| **ED-1** | Governance/permission around single-user release | Prevents unauthorized single-user release only if all conditions are enforced | Requires audit within one business day | Supports correction only if manager approval occurs before settlement and audit occurs within recall window | Not a blanket emergency exception; fails if token, amount, vendor, bank-change, AV, manager, or audit conditions are unmet |

### Manager action after Release_Payment but before Bank_Settlement

Under the facts given, **bank settlement is the normal point of irrevocability**, while `Release_Payment` is an internal release step. Therefore, a manager action after `Release_Payment` but before `Bank_Settlement` is **hybrid**:

- **Detective** with respect to the release decision: it can discover that the release was erroneous or unsupported.
- **Preventive** with respect to the actual transfer: it can stop settlement before the payment becomes irrevocable.
- **Corrective** only if it can still halt settlement, recall the transfer, or trigger recovery before the window closes.

If the organization treats `Release_Payment` itself as irrevocable, then the same manager action would be primarily detective/corrective, not preventive. In this process, because settlement occurs later, pre-settlement manager ratification has meaningful preventive value.

    if obj is None:

    if isinstance(obj, pd.DataFrame):

            return set(obj["case:concept:name"].dropna().astype(str).unique())
        return set()

    if isinstance(obj, (list, set, tuple)):
        return {str(x) for x in obj if isinstance(x, str)}

    if isinstance(obj, dict):
        keys = {str(k) for k in obj.keys() if isinstance(k, str)}
        if any(k.startswith("AP-") for k in keys):
            return keys

    try:
        out_df = pm4py.convert_to_dataframe(obj)
        return extract_case_ids(out_df)
    except Exception:
        pass

    try:
        return {str(getattr(t, "case_id", "")) for t in obj if getattr(t, "case_id", None)}

        return set()

### PM4Py behavior that cannot be guaranteed across versions

- `pm4py.format_dataframe` may accept different keyword names or may expect string timestamps. The code parses UTC timestamps first and falls back if the formatted DataFrame does not contain the expected columns.
- `pm4py.filter_four_eyes_principle` may return an event log, a DataFrame, a list of case IDs, or another structure depending on the PM4Py version. The `extract_case_ids` helper handles several common return shapes.
- The filter may return cases that **violate** the four-eyes principle or cases that **satisfy** it, depending on version or implementation. The code compares the filter output to a locally reconstructed completed-payment set and interprets it robustly.
- The filter may not consider `Attempt_Release` or `Cancel_Payment` as completed payments. The code separately identifies attempted but blocked releases, such as AP-205.
- The code’s audit “one business day” calculation uses a simple `pandas` business-day approximation and should not be treated as a legal or final compliance determination.
