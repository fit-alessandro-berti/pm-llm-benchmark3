**2. Severity and confidence summary**
- Critical / High confidence: SUP-703, SUP-708 (severe, unexcused).
- High / Medium confidence: SUP-705, SUP-712, SUP-714, SUP-715 (authority/resource gaps with missing evidence but clear directional failure).

**3. System-level judgment**
- **Operational compliance:** **PARTIAL NONCOMPLIANCE / MIXED.** The operation is not “materially noncompliant” in every case; 289 eligible pilot cases and all FD-7-compliant emergency cases show that temporary overlays can work. However, the presence of **critical** violations (703, 708), **post-expiry normalization** (705, 714), **hidden resource failures** (712, 715), and **data degradation masking assurance** (706, notification 29%) means the control environment is unstable. The high deviation rate is partially explained by model incompleteness and data defects, but not fully explained away.
- **Model validity:** **OBSOLETE / INCOMPLETE.** M0 is a static acyclic control-flow skeleton that cannot represent loops (`Request_More_Info`), concurrent approvals with deferred steps (emergency), multiple approval routes (standard/auto/emergency), resource/identity rules, rejected-lead scope, label mappings, or temporal rules. It generates false positives (707, 710, 709) and false negatives (712, 715).

**4. Rejection of arguments**
- **Reject prosecution’s blanket enforcement claim:** Not every deviation from M0 is a CS-9 violation. SUP-702 (PD-3) and SUP-704 (FD-7) are authorized exceptions; SUP-707 is a design improvement; SUP-706/711 are logging failures, not process failures. The prosecution correctly identifies 703/708 as severe, but overreaches if it treats 312 auto-approve cases uniformly as “noncompliant” without distinguishing eligible overlay cases from ineligible ones.
- **Reject defense’s “obsolete = excused” claim:** The defense correctly identifies model and data defects, but cannot excuse SUP-703 (ineligible + high-risk + large spend) or SUP-708 (sanctions after activation, no overlay) as “model problems.” It also cannot excuse post-expiry continuation (SUP-705, 714) by pointing to “factual emergency” or “normalization”; authority is procedural. The defense must concede that resource failures (712) and disclosure failures (715) are real control gaps that M0’s incompleteness allowed to persist undetected.

## 6. Revised Normative Architecture

**Layer 1 — Base control-flow (POWL / process model)**
- Represents concurrency (`Sanctions_Check` || `Quality_Review` for standard routes), exclusive branches (standard manual / low-risk auto / emergency provisional / reject), sequential ordering (`Register`  `Checks`/`Sanctions`  decision  `Notify`  `Close`), and approximate loop placement (`Request_More_Info` before decision).
- **Limitation:** POWL is acyclic and cannot express repetition, conditional concurrency, or temporal windows. It is used for structural sequencing and choice, not enforcement.
- **Where it belongs:** `StrictPartialOrder`, `OperatorPOWL`.

**Layer 2 — Data-aware eligibility / amount / time rules (Pandas / SQL / event predicates)**
- Eligibility snapshot at activation: `risk_class`, `corporate_group_approved`, `pilot_active_version`, `emergency_directive_active`.
- Amount cap: `spend <= 20000` for FD-7; `auto_approve` allowed only if conditions met.
- Time windows: `quality_review_due <= activate + 2 business days`; `pilot_expiry`; `emergency_expiry`; `retrospective_approval_deadline`.
- Evidence linkage: `notification_id` stable at event time; `rule_version_id` recorded per activity.
- **Where it belongs:** Pandas/data checks, database constraints, event-schema validation.

**Layer 3 — Resource / identity / conflict-of-interest rules (Organizational controls / DB / identity graph)**
- Requester  Approver (resolved via canonical identity graph, not just alias).
- Conflict-of-interest disclosure required; relationship mapping (spouse / reporting line) must be recorded and approved.
- Delegation evidence (temporary approval rights) must be linked.
- **Where it belongs:** Organizational controls / identity management system / approval workflow engine (outside POWL).

**Layer 4 — Policy-overlay governance (Governance table / organizational control)**
- Pilot authorization record: `overlay_id`, `effective_start`, `effective_end`, `authority_evidence` (minutes + email), `eligible_criteria_version`, `approval_status` (monitored / approved / not approved).
- Emergency directive record: `directive_id`, `scope` (critical relief suppliers), `spend_cap`, `monitoring_frequency`, `retrospective_deadline`, `expiry`, `extension_record`.
- Permanent amendment record: when pilot/emergency rules become standard.
- **Where it belongs:** Governance database; referenced by event data, not embedded in POWL.

**Layer 5 — Scope rules (Declared outside POWL)**
- **Rejected leads / pre-screen:** If a case fails sanctions pre-screen and never reaches full onboarding, it is either (a) not a case governed by M0, or (b) governed by a separate “Intake / Pre-Screen” model with its own minimal flow (`Register`  `Sanctions_Check`  `Reject_Supplier`  `Notify`  `Close`). The scope document must declare which applies.
- **Reactivation:** Separate process model (or extension) allowing `Register_Supplier` to be omitted if prior certification valid, but requiring `Sanctions_Check` and `Quality_Review` (or recertification evidence) and `Manual_Procurement_Approval`.
- **Withdrawal / cancellation:** Not present in M0; needs explicit scope rule.

**Layer 6 — Event / data-collection proposal**
- All activities must include: `case_id`, `event_timestamp` (immutable), `rule_version_applied`, `actor_id` (canonical, with alias resolution), `overlay_id` (if any), `notification_id` (stable, not mutable text), `eligibility_snapshot` (JSON of criteria at activation), `amount` (for spend-cap rules), `evidence_link` (immutable storage reference).

## 7. PM4Py Model and Data Proposal

```python
# Revised normative POWL (approximation)
# Limitations explicitly stated:
# 1. POWL is acyclic; Request_More_Info repetition requires external loop/state logic.
# 2. Temporal windows, amount caps, resource separation, and overlay selection
#    are enforced by Layer 2/3/4 controls, not by POWL semantics.
# 3. The emergency branch approximates deferred quality/approval via a branch
#    that activates before retrospective nodes; overlay rules enforce the 2-day window.
# 4. Decision branch selection (standard / auto / emergency / reject) is driven
#    by organizational rules / eligibility checks (Layer 2/4).

from pm4py.objects.powl.obj import StrictPartialOrder, OperatorPOWL, Transition
from pm4py.objects.process_tree.obj import Operator

# --- Common nodes ---
register = Transition(label="Register_Supplier")
sanctions = Transition(label="Sanctions_Check")
quality = Transition(label="Quality_Review")
request_more = Transition(label="Request_More_Info")  # loop approximation; repetition external

# --- Approval / activation nodes ---
manual_approval = Transition(label="Manual_Procurement_Approval")
auto_approve = Transition(label="Auto_Approve")
activate = Transition(label="Activate_Supplier")

# --- Retrospective / deferred nodes for emergency/provisional ---
retrospective_approval = Transition(label="Retrospective_Manual_Approval")
retrospective_quality = Transition(label="Retrospective_Quality_Review")

# --- End nodes ---
reject = Transition(label="Reject_Supplier")
notify = Transition(label="Notify_Requester")
close = Transition(label="Close_Case")

# --- Standard concurrent checks (base route) ---
checks = StrictPartialOrder(nodes=[sanctions, quality])

# --- Branches ---
# Standard manual-approval branch
std_approved = StrictPartialOrder(nodes=[manual_approval, activate])
std_approved.order.add_edge(manual_approval, activate)

# Low-risk auto-approval branch (PD-3 eligible; overlay selects)
auto_approved = StrictPartialOrder(nodes=[auto_approve, activate])
auto_approved.order.add_edge(auto_approve, activate)

# Emergency / provisional branch (FD-7): activation precedes retrospective approval/quality.
# The overlay ensures retrospective actions complete within directive limits.
emergency_approved = StrictPartialOrder(nodes=[activate, retrospective_approval, retrospective_quality])
emergency_approved.order.add_edge(activate, retrospective_approval)
emergency_approved.order.add_edge(activate, retrospective_quality)

# Rejection branch (minimal; scope rule determines if pre-screen or full)
reject_branch = StrictPartialOrder(nodes=[reject])

# --- Decision (exclusive choice) ---
# Branch selection is governed by Layer 2/4 rules (risk class, group, directive active),
# not by POWL semantics.
decision = OperatorPOWL(operator=Operator.XOR,
                        children=[std_approved, auto_approved, emergency_approved, reject_branch])

# --- Main process structure ---
# Request_More_Info is placed before checks/decision; repetition is handled externally.
# Note: For emergency routes, quality is deferred; base model includes it in checks,
# and the overlay explicitly records the exception.
M_revised = StrictPartialOrder(
    nodes=[register, request_more, checks, decision, notify, close]
)
M_revised.order.add_edge(register, request_more)
M_revised.order.add_edge(request_more, checks)
M_revised.order.add_edge(checks, decision)  # overlay permits deferred quality for emergency
M_revised.order.add_edge(decision, notify)
M_revised.order.add_edge(notify, close)

# --- Design notes ---
# - Concurrent checks: checks = StrictPartialOrder(sanctions, quality) satisfies M0 concurrency for standard routes.
# - Auto-approval: auto_approved branch satisfies low-risk branch requirement.
# - Emergency: emergency_approved branch satisfies provisional activation; retrospective nodes represent deferred requirements.
# - Request_More_Info: included as a node; loop not expressible; must be managed by state/data overlay.
# - Rejection / closure: reject_branch plus notify -> close.
# - Notification before closure: notify precedes close by order edge.
```

**Event / Data-Collection Proposal**

1. **Stable notification identity:** `Notify_Requester` events must write `notification_id` (immutable, generated by CRM at send time) into the onboarding event log at event time; mutable text links are deprecated.
2. **Rule/version tagging:** Every event must carry `rule_version_applied` (e.g., `CS-9-v1`, `PD-3-v1`, `FD-7-v1`) to distinguish overlay from base.
3. **Eligibility snapshot:** At `Activate_Supplier`, a snapshot JSON must be persisted: `risk_class`, `corporate_group_approved`, `pilot_active_at_time`, `emergency_active_at_time`, `actor_ids`.
4. **Actor alias resolution:** All `actor_id` fields must resolve to canonical identity; event schema must support `alias_id` mapping and flag `requester_approver_same_human`.
5. **Delegation / authority evidence:** `Auto_Approve` and emergency activation must reference `overlay_authority_id`; retrospective approval requires `retrospective_approval_timestamp` and `approval_actor_id`.
6. **Immutable timestamps:** `event_timestamp` must be set by the system at persistence; `record_timestamp` (when observed) must not overwrite it.
7. **Reactivation / withdrawal scope:** Define separate model paths (`Reactivation_Supplier`) with explicit rules for when `Register_Supplier` can be omitted and how prior certification is validated.
8. **Data-quality checks:** Deduplication on `source_transaction_id` at ingestion; notification missingness monitored as a control metric, not just a log-cleanup issue.

This architecture separates structural sequencing (POWL), data/authorization conditions (layer 2/4), identity/conflict controls (layer 3), and scope declarations (layer 5), avoiding the false confidence that a single acyclic control-flow graph can enforce a multi-layer compliance regime.
