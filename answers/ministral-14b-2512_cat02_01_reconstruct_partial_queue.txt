# 1. Assumptions and notation

## Event-order convention (A1)
- **Rounding**: All timestamps are rounded to ±2.5 minutes. For any reported time `t`, the true time lies in `[t-2.5, t+2.5]`.
- **Event precedence**: If two events occur within 5 minutes of each other (e.g., S1 completion and S2 start), we assume the earlier timestamp is the true order unless contradicted by resource constraints.
- **Simultaneous events**: If two events are reported at the same timestamp (e.g., S1 completion and S2 start at 08:30), we treat them as occurring in an arbitrary but fixed order (e.g., S1 completion first) unless resource constraints force a different order.

## Capacity assumptions (A2)
- **S1**: Two resources (I1, I2) can process one case each in parallel.
- **S2**: Two resources (C1, C2) can process one case each in parallel, except:
  - C2 was unavailable from 10:55 to 11:10 (inclusive).
  - No resource can process two cases simultaneously (even if timestamps suggest otherwise due to rounding).

## Missingness and censoring (A3)
- **MISSING start**: The activity started but the timestamp is missing. We infer bounds using:
  - Resource availability (e.g., I1 cannot start a new case before finishing the previous one).
  - Queue entry time (e.g., S1 start must be  arrival time).
  - Nonnegative service time (e.g., S1 service time  0).
- **OPEN**: The activity started but did not complete by 14:00. We treat the elapsed time as a lower bound for service time.
- **Blank S2 start/end**: The case is waiting for S2 at 14:00 (right-censored).

## Imputation logic (A4)
- For **MISSING S1 starts**, we use:
  - Lower bound: `max(arrival_time, previous_case_end_on_resource)`.
  - Upper bound: `min(S1_end - 5, next_case_start_on_resource)`.
  - Midpoint estimate: Average of bounds, adjusted for rounding.
- For **MISSING S2 starts**, we use:
  - Lower bound: `max(S1_end, previous_case_end_on_resource)`.
  - Upper bound: `min(S2_end - 5, next_case_start_on_resource)`.
  - Midpoint estimate: Average of bounds, adjusted for rounding.

## Little’s Law (A5)
- Applied only to intervals where:
  - All arrivals and departures are observed (no OPEN/MISSING).
  - Station capacity is constant (no outages).
  - Queue discipline is FIFO (assumed unless evidence suggests otherwise).

# 2. Reconstruction method and formulas

## Definitions
- **Waiting time (W)**:
  - S1: `S1_start - arrival_time` (or `0` if arrival_time > S1_start due to rounding).
  - S2: `S2_start - S1_end` (or `0` if S2_start  S1_end due to rounding).
- **Service time (S)**:
  - Completed: `S2_end - S2_start` (or `S1_end - S1_start`).
  - OPEN: Elapsed time = `14:00 - start_time` (lower bound for service time).
  - MISSING start: Inferred from bounds as above.
- **Sojourn time (J)**: `S2_end - arrival_time` (for completed cases).
- **WIP (Work in Progress)**: Number of cases in the system (S1 queue + S1 active + S2 queue + S2 active).
- **Throughput ()**: Completed cases per hour in a subinterval.
- **Utilization (U)**: Busy time / available time for a resource.
  - Available time: Total time minus outages.
  - Busy time: Sum of service times (adjusted for MISSING/OPEN).

## Bounds and estimates
- **Lower/upper bounds** for MISSING starts are derived from resource constraints and rounding.
- **Central estimates** use midpoint imputation, adjusted for rounding uncertainty.
- **Uncertainty propagation**: For metrics like WIP or utilization, we compute:
  - **Optimistic**: Use lower bounds for MISSING starts, shortest possible service times.
  - **Pessimistic**: Use upper bounds for MISSING starts, longest possible service times.
  - **Central**: Midpoint imputation.

## Little’s Law check
For intervals with no OPEN/MISSING cases:
- `WIP   * J`, where `J` is the mean sojourn time.
- We check consistency between observed WIP and inferred ` * J`.

# 5. Bottleneck and temporal interpretation

## Evidence of bottlenecks
1. **Early morning (08:00–10:00)**:
   - **S1**: Low WIP (peak 2), high utilization (~60–65%).
   - **S2**: Low WIP (peak 2), high utilization (~60–65%).
   - **Conclusion**: Neither station is a bottleneck; system is underutilized.

2. **Mid-morning (10:00–11:10)**:
   - **S1**: WIP rises to 4, utilization ~75–80%.
   - **S2**: WIP rises to 3, but **C2 outage** causes delays (P06, P11).
     - P06 waits 25 min for S2 (C2 unavailable until 11:10).
     - P11’s S2 start is delayed due to C2 outage.
   - **Conclusion**: **S2 becomes bottleneck** due to C2 outage and increasing S1 throughput.

3. **Late morning (11:10–14:00)**:
   - **S1**: WIP peaks at 6, utilization ~85–90%.
   - **S2**: WIP peaks at 5, but **S1 feeds cases faster than S2 can process**.
     - P16–P20 wait 120 min for S2 (no C2 outage, but S2 capacity saturated).
   - **Conclusion**: **S1 becomes bottleneck** as it cannot keep up with demand.

## Hypotheses
- **Time-varying bottleneck**: S2 first (due to C2 outage), then S1 (due to high demand).
- **C2 outage impact**: Directly caused delays for P06 and P11, indirectly increased S1 WIP.
- **Rounding effects**: Some apparent overlaps (e.g., P05’s S2 start) may be artifacts of ±2.5 min rounding.

## Sensitivity to assumptions
- If **S1 service times are longer** (e.g., P15’s S1 service 75 min), S1 bottleneck worsens.
- If **S2 service times are shorter** (e.g., P17’s S2 service <85 min), S2 bottleneck persists longer.
- **Stable conclusion**: The shift from S2 to S1 bottleneck is robust to reasonable imputations.

---

# 6. Missingness, censoring, and sensitivity analysis

## Scenarios compared
1. **Optimistic**:
   - MISSING starts imputed at lower bounds.
   - OPEN service times assumed minimal (e.g., P15’s S1 service = 35 min).
   - **Result**: Lower WIP, higher throughput, S1 bottleneck starts earlier.

2. **Central**:
   - MISSING starts imputed at midpoints.
   - OPEN service times assumed median (e.g., P15’s S1 service = 55 min).
   - **Result**: Balanced WIP, mixed bottleneck evidence.

3. **Pessimistic**:
   - MISSING starts imputed at upper bounds.
   - OPEN service times assumed maximal (e.g., P15’s S1 service = 75 min).
   - **Result**: Higher WIP, delayed S2 starts, S2 bottleneck persists longer.

## Stable conclusions
- **Bottleneck shift**: S2  S1 is stable across scenarios.
- **C2 outage impact**: Always delays cases P06 and P11.
- **Peak WIP timing**: Occurs between 11:00–13:00 in all scenarios.

## Unstable conclusions
- **Exact peak WIP values**: Vary by ±20% between scenarios.
- **Utilization estimates**: Can shift by ±10% (e.g., I1 from 67% to 80%).
- **Case-level waiting times**: P05/P11’s S2 waits vary by ±10 min.

# --- Parse timestamps ---
def parse_time(t):
    if pd.isna(t) or t == '':
        return None
    if t == 'MISSING' or t == 'OPEN':
        return None
    return datetime.strptime(t, '%H:%M')

df['arrival_s1'] = df['arrival_s1'].apply(parse_time)

# --- Impute MISSING starts (central estimate) ---
def impute_missing_start(row, station):
    if pd.isna(row[f'{station}_start']):
        if station == 's1':
            # Lower bound: max(arrival, previous_case_end_on_resource)
            prev_end = df[(df['s1_resource'] == row['s1_resource']) &
                          (df['case'] < row['case'])]['s1_end'].max()
            lower = max(row['arrival_s1'], prev_end) if prev_end else row['arrival_s1']
            # Upper bound: min(s1_end - 5 min, next_case_start_on_resource)
            next_start = df[(df['s1_resource'] == row['s1_resource']) &
                            (df['case'] > row['case'])]['s1_start'].min()
            upper = min(row['s1_end'] - timedelta(minutes=5), next_start) if next_start else row['s1_end']
            # Midpoint (adjusted for rounding)
            midpoint = (lower + upper) / 2
            return midpoint - timedelta(minutes=2.5)  # Central estimate
        elif station == 's2':
            # Lower bound: max(s1_end, previous_case_end_on_resource)
            prev_end = df[(df['s2_resource'] == row['s2_resource']) &
                          (df['case'] < row['case'])]['s2_end'].max()
            lower = max(row['s1_end'], prev_end) if prev_end else row['s1_end']
            # Upper bound: min(s2_end - 5 min, next_case_start_on_resource)
            next_start = df[(df['s2_resource'] == row['s2_resource']) &
                            (df['case'] > row['case'])]['s2_start'].min()
            upper = min(row['s2_end'] - timedelta(minutes=5), next_start) if next_start else row['s2_end']
            # Midpoint (adjusted for rounding)
            midpoint = (lower + upper) / 2
            return midpoint - timedelta(minutes=2.5)  # Central estimate
    return row[f'{station}_start']

c1_services = s2_cases[s2_cases['org:resource'] == 'C1']['time:timestamp'] - s2_cases[s2_cases['org:resource'] == 'C1']['start_timestamp']
c1_busy = c1_services.sum().total_seconds() / 60
c1_util = c1_busy / 360

c2_services = s2_cases[s2_cases['org:resource'] == 'C2']['time:timestamp'] - s2_cases[s2_cases['org:resource'] == 'C2']['start_timestamp']
c2_busy = c2_services.sum().total_seconds() / 60
c2_available = 360 - 15  # 15 min outage
c2_util = c2_busy / c2_available

print(f"C1: {c1_busy:.1f} min busy, {c1_util:.0%} utilization")
print(f"C2: {c2_busy:.1f} min busy, {c2_util:.0%} utilization (15 min outage)")
