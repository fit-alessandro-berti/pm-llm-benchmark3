## 6. Candidate Site B intervention

A modified intervention for Site B should be segmented and legality-aware. Eligibility for full identity–document parallelization is restricted to cases that (a) do not legally require originals, (b) arrive with sufficient digital documentation to support a first-pass Document Check, and (c) are not flagged for mandatory Legal Review based on public-sector or high-value criteria. For originals-required cases, the intervention permits early Identity Check in parallel with `Originals Receipt`, but Document Check execution still begins only after originals physically arrive; any early-created document tasks must remain in a “pending originals” state and not be worked. Identity, Document, Assessment, and Legal remain specialized roles, but explicit per-role WIP limits and daily queue huddles are introduced to coordinate priority, protect legal capacity, and manage aged work.

Queue and WIP controls include: capped open cases per reviewer (e.g., similar to Site A’s six-verification-task limit), explicit WIP caps for Legal Review, and rules that limit simultaneous release of complex cases to Legal. Resource responsibilities are clarified so that Identity and Document reviewers own early checks, assessors focus on integrated decisions, and legal reviewers handle statutory review and supplements only. Legal-review loops (`Legal Review` → `Request Supplement` → `Document Check` → `Assessment`) are preserved but flagged for monitoring; repeat-loop depth beyond a set threshold triggers managerial review. Logging requirements include real-time start and completion timestamps for all tasks, explicit flags for “pending originals,” and prohibition of back-dated entries, with periodic audits.

A compact partial-order specification for the eligible digital/no-legal segment can be expressed as:

- Activities: {`Register`, `Identity Check`, `Originals Receipt`, `Document Check`, `Assessment`, `Legal Review`, `Request Supplement`, `Approve`, `Reject`, `Notify`}.
- Mandatory precedence relations: `Register < Identity Check`; `Register < Originals Receipt`; `Originals Receipt < Document Check` when originals required; `Identity Check < Assessment`; `Document Check < Assessment`; `Assessment < Legal Review` for legally required cases; `Assessment < Approve`; `Assessment < Reject`; `Legal Review < Request Supplement`; `Legal Review < Approve`; `Legal Review < Reject`; `Request Supplement < Document Check`; `{Approve, Reject} < Notify`.
- Parallelizable relations: after `Register`, `Identity Check` and (for eligible digital/no-originals cases) `Document Check` are unordered relative to each other; `Originals Receipt` may also run in parallel when applicable.
- Loop constraint: any path `Legal Review → Request Supplement → Document Check → Assessment → Legal Review` must eventually exit to `Approve` or `Reject`.

This partial order preserves statutory ordering while allowing controlled parallelism where feasible.

The pilot separates mechanism failure from implementation failure by explicitly measuring both the structural changes (actual `true_overlap`, waiting components, and conformance to the intended partial order) and the realized outcomes (cycle time, tails, rework, appeals) within clearly defined strata. If logs show high `treatment_parallelization` and `true_overlap` in the treated segments but little or negative improvement in waiting or tails, this points to structural or contextual limits of the mechanism (e.g., downstream legal bottlenecks). Conversely, if expected overlap is not achieved, or if logs reveal ongoing pseudo-sequential work or timestamp back-entry, the issue is implementation fidelity or IT constraints rather than transportability. Cluster-level randomization and stepped-wedge rollout make it possible to compare treated and control units contemporaneously, controlling for secular trends. By stratifying effects by document channel, complexity, and legal requirement, the pilot directly maps which subsets of Site B behave analogously to Site A and which require different designs, guiding subsequent expansion or redesign.

## 8. PM4Py model-construction code

```python
import pm4py
from pm4py.objects.powl.obj import POWL, StrictPartialOrder, Event

# 1. Site A before/after process trees
pt_before_str = "->('Register','Identity Check','Document Check','Assessment',X('Approve','Reject'),'Notify')"
pt_after_str = "->('Register',+('Identity Check','Document Check'),'Assessment',X('Approve','Reject'),'Notify')"

pt_before = pm4py.parse_process_tree(pt_before_str)
pt_after = pm4py.parse_process_tree(pt_after_str)

net_before, im_before, fm_before = pm4py.convert_to_petri_net(pt_before)
net_after, im_after, fm_after = pm4py.convert_to_petri_net(pt_after)

print('Site A before is workflow net:', pm4py.check_is_workflow_net(net_before))
print('Site A after is workflow net:', pm4py.check_is_workflow_net(net_after))

# 3. Construct a Site B candidate POWL model with strict partial order and legal-review loop

# Define POWL events (activities)
reg = Event("Register")
idc = Event("Identity Check")
orig = Event("Originals Receipt")
doc = Event("Document Check")
assess = Event("Assessment")
legal = Event("Legal Review")
req_sup = Event("Request Supplement")
approve = Event("Approve")
reject = Event("Reject")
notify = Event("Notify")

# Strict partial order: edges encode precedence constraints
activities = {reg, idc, orig, doc, assess, legal, req_sup, approve, reject, notify}
order_edges = set()

# Basic ordering
order_edges.add((reg, idc))              # Identity may start after registration
order_edges.add((reg, orig))            # Originals may be requested/received after registration
order_edges.add((orig, doc))            # When originals required, Document Check waits for originals
order_edges.add((idc, assess))          # Assessment needs identity result
order_edges.add((doc, assess))          # Assessment needs document result

# Legal-review branch and supplement loop
order_edges.add((assess, legal))        # Public/high-value cases go to legal
order_edges.add((assess, approve))      # Some cases approved directly
order_edges.add((assess, reject))       # Some cases rejected directly
order_edges.add((legal, req_sup))       # Legal may request supplements
order_edges.add((legal, approve))       # Legal may approve
order_edges.add((legal, reject))        # Legal may reject
order_edges.add((req_sup, doc))         # Supplements re-enter document checking
order_edges.add((approve, notify))      # Final decision then Notify
order_edges.add((reject, notify))

spo = StrictPartialOrder(activities=activities, order=order_edges)
powl_site_b = POWL(spo)

# 5. Convert POWL model to accepting Petri net
net_b, im_b, fm_b = pm4py.convert_to_petri_net(powl_site_b)

# 6. Check workflow-net / soundness properties
is_wfnet_b = pm4py.check_is_workflow_net(net_b)
sound_b = pm4py.check_soundness(net_b, im_b, fm_b)
print('Site B candidate is workflow net:', is_wfnet_b)
print('Site B candidate soundness:', sound_b)

# 7. Optional playout to see sample traces
try:
    log_b = pm4py.play_out(net_b, im_b, fm_b, no_traces=5)
    print("Sample Site B traces:")
    for trace in log_b:
        print([e["concept:name"] for e in trace])
except Exception as e:
    print("Playout not available:", e)

# 8. Commentary (not encoded in the Petri nets / POWL model):
# - Data-dependent legal requirements (e.g., which cases require originals or Legal Review)
#   are abstracted away; the model only shows possible paths, not the decision logic.
# - Resource capacities and role specialization (identity/document/assessment/legal pools)
#   are not captured; Petri nets assume unbounded resources unless extended with schedules.
# - Case-management locks and IT constraints on simultaneous task ownership are not modeled;
#   concurrency in the net does not guarantee that the real system can execute tasks in parallel.
# - Activity durations and external delays (such as the 18-hour originals arrival time)
#   are not part of the control-flow model; they must be incorporated via simulation parameters
#   or separate timing annotations when doing performance analysis.
```

## 9. Recommendation

conditional go

A direct copy of Site A’s blanket parallelization would be unsafe and likely ineffective at Site B, but a segmented, legality-aware version focused on digital, originals-not-required, non-legal cases is worth piloting. What should be transferred is the underlying mechanism—creating independent identity and document-verification work as early as legally and technically feasible, coupled with explicit WIP controls and daily queue huddles—rather than the headline “parallelize everything after Register.” In addition, Site A’s emphasis on monitoring overlap and waiting before Assessment, and its modest capacity buffer around document checking, are valuable design elements that can be adapted to Site B’s specialized roles and thinner legal capacity. What should not be copied is the implicit assumption that legal review is absent, that documents are almost always digital and immediately available, or that IT readily supports true multi-owner concurrency; attempting to impose Site A’s control-flow diagram on Site B’s stricter environment would risk tail inflation and quality problems.

The first subgroup to enter the pilot should therefore be clearly digital, non-public, non-high-value cases without statutory Legal Review, where originals are not required and structural similarity to Site A is highest. Expected benefits in this segment include a 4–7 hour reduction in median cycle time and 5–12 hour improvement in p90 for eligible cases, mainly via reduced waiting before Assessment, with neutral quality if controls hold. Key risks are pseudo-parallelization due to case locks, hidden legal or documentation requirements surfacing as rework, and congestion in Legal Review if scope expands prematurely. Expansion should be triggered only if the pilot demonstrates genuine increases in true overlap, meaningful reductions in waiting and p90 without worsening rework or appeals, and stable legal and assessment queues. Evidence of IT constraints, legal congestion, or quality degradation should instead trigger redesign (e.g., tighter eligibility, more capacity, or different sequencing) or, if persistent, abandonment of parallelization beyond narrow segments.

## 10. Assumption register

1. 2.
