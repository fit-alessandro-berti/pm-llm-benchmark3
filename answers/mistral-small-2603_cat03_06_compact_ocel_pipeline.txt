# Retail Order Processing: OCEL 2.0 Construction and Analysis

## 1. Modeling assumptions

**Object types and capitalization:**
- Order (O100, O200)
- Item (I1, I2, I3)
- Package (P1, P2)
- Delivery (D1, D2)
- Invoice (V1)
- Payment (M1, M2)

**E2O qualifier vocabulary:**
- "primary": direct relationship to the main business entity
- "secondary": supporting relationship to related entities
- "operational": shared operational involvement
- "financial": financial relationship
- "logistical": physical movement relationship

**O2O direction conventions:**
- For containment relationships (Order contains Item, Package packs Item), use "contains" qualifier with direction from container to contained
- For transport relationships (Delivery carries Package), use "carries" qualifier with direction from delivery to package
- For billing relationships (Invoice bills Order), use "bills" qualifier with direction from invoice to order
- For payment relationships (Payment settles Invoice), use "settles" qualifier with direction from payment to invoice

**Logistics and financial events:**
- Logistics events (packing, dispatching, confirming deliveries) relate directly to Orders through Items and Packages
- Financial events (issuing invoice, recording payments) relate directly to Orders through Invoice
- This direct relationship preserves the source-system facts without analytical propagation

**Preventing analytical relation propagation confusion:**
- Only include relations that exist in the source system narrative
- Avoid adding derived relations that would make the model appear more connected than it is
- Clearly distinguish between source-system facts and analytical insights in the analysis

**PM4Py version assumption:**
- Using PM4Py 2.7+ which fully supports OCEL 2.0
- The OCEL constructor is assumed to be available as shown

def validate_ocel(events, objects, relations, o2o):
    # Check unique event IDs
    assert len(events['ocel:eid'].unique()) == len(events), "Duplicate event IDs"

    # Check unique object IDs
    assert len(objects['ocel:oid'].unique()) == len(objects), "Duplicate object IDs"

    # Check no orphan event IDs in relations
    event_ids = set(events['ocel:eid'])
    relation_event_ids = set(relations['ocel:eid'])
    assert relation_event_ids.issubset(event_ids), "Orphan event IDs in relations"

    # Check no orphan object IDs in relations
    object_ids = set(objects['ocel:oid'])
    relation_object_ids = set(relations['ocel:oid'])
    assert relation_object_ids.issubset(object_ids), "Orphan object IDs in relations"

    # Check no orphan object IDs in O2O
    o2o_object_ids = set(o2o['ocel:oid']).union(set(o2o['ocel:oid_2']))
    assert o2o_object_ids.issubset(object_ids), "Orphan object IDs in O2O"

    # Check activity/timestamp consistency between events and relations
    for _, row in relations.iterrows():
        event_row = events[events['ocel:eid'] == row['ocel:eid']].iloc[0]
        assert event_row['ocel:activity'] == row['ocel:activity'], f"Activity mismatch for {row['ocel:eid']}"
        assert event_row['ocel:timestamp'] == row['ocel:timestamp'], f"Timestamp mismatch for {row['ocel:eid']}"

    # Check no duplicate relation rows
    assert len(relations) == len(relations.drop_duplicates()), "Duplicate relation rows"

    print("All validations passed!")

**Object-centric Petri net:**

- P1 will be a place that receives tokens from both O100 and O200 (via I1 and I3)

**Object-interactions summary:**

## 6. Modeling alternatives

**1. Source-minimal relations:**
- Only include direct relationships from the source system narrative
- For example, don't include Order in the relations for packing events unless explicitly stated
- Impact: Would make the process appear more disconnected, hiding the operational relationships between orders
- Discovery results would show more isolated traces with fewer shared events

**2. Full operational involvement:**
- Include all possible object relationships in every event
- For example, in E007 (Pack Package), include all items in the system as secondary
- Impact: Would make the process appear overly connected, potentially hiding the real relationships
- Discovery results would show many more edges in the OC-DFG and OTG

**3. O2O-propagated analytical relations:**
- Use O2O relations to automatically propagate relationships to related objects
- For example, if Package P1 packs Item I1 which is in Order O100, then P1 is automatically related to O100
- Impact: Would make the process appear more connected than it is in reality
- Discovery results would show more relationships than actually exist in the source system

## 7. Failure modes

1. **Relation inflation:** Adding too many relations that don't exist in the source system, making the process appear more connected than it is.

2. **Missing direct E2O links:** Failing to include direct relationships that are explicitly stated in the process narrative, making the process appear more disconnected.

3. **Treating O2O propagation as observation:** Using O2O relations to automatically create E2O relations during analysis, which would mix source-system facts with analytical insights.

4. **Duplicate shared events after flattening:** When flattening on Order, the same invoice and payment events appear in both order traces, which might be misinterpreted as duplicate events rather than shared operational events.

5. **Ambiguous payment allocation:** The payments M1 and M2 are partial payments against V1, but the exact allocation to orders isn't specified. This could lead to different interpretations of how much each order was paid.

6. **Overly short Payment traces:** Flattening on Payment produces traces with just a single event, revealing almost nothing about the process flow.

7. **Constructor/API version mismatch:** Using a different version of PM4Py that doesn't support OCEL 2.0 or has different constructor parameters.

8. **False total order for same-time events:** Even though this example has no timestamp ties, in real data same-timestamp events might be ordered arbitrarily, affecting process discovery results.

9. **Missing operational context:** Not including operational events like "Reserve Stock" or "Pack Package" in the right object traces, losing important context about how orders are processed.

10. **Overloading qualifiers:** Using too many different qualifiers that aren't consistently applied, making the relationships hard to interpret.

11. **Ignoring financial context:** Not properly relating payment events to the invoice and orders, losing important financial process context.

12. **Incorrect O2O direction:** Using the wrong direction in O2O relations (e.g., "Order is contained in Item" instead of "Order contains Item"), which would reverse the relationships.
