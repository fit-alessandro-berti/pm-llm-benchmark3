## 1. Analytical assumptions

I treat a **case notion** as a chosen projection: one object type is promoted to case identifier, every event that is *directly* E2O-related to an object of that type is copied into that object’s trace, and directly-follows, variant, and performance statistics are computed as if those traces were independent. A case notion is therefore an analytical cut, not a recovered ground truth. The OCEL already records several overlapping units of work (commercial order, physical item, handling package, vehicle delivery, bill, settlement), so “the case” is a modelling choice that answers a question and necessarily mis-answers others.

**Convergence** is the situation in which one event is a member of several flattened cases because it is directly related to several objects of the lead type. After flattening, that event is copied, so frequencies, DFG edge weights, and “number of cases that executed A” are inflated relative to the event log’s actual cardinality. In this snapshot the convergent events are exactly those whose Related-objects set contains more than one object of the chosen type: `e13` (O2, O3), `e14` (O3, O4), `e16` (O1, O2, O3), `e17` (O3, O4), `e19` (O2, O3), `e22` (O2, O3), `e24` (O1, O2, O3), `e25` (O2, O3), `e27` (O3, O4) when the lead type is Order; the same physical events converge on items or packages whenever several items or packages share them.

**Divergence** is the complementary situation: one lead object is related to several events of the same activity because several child objects live their own lives underneath it. After flattening, the case contains repeated activity labels and self-loop or A→A edges that describe *multiplicity of work items*, not rework. O1 is the textbook divergent order: two `Pack Package` (`e11`, `e12`), two `Dispatch` (`e15`, `e16`), two `Confirm Delivery` (`e23`, `e24`). O3 is worse, because it is both split (I31 vs I32) and merged (shared P3/D2/V2 with O2, shared P4/D3 with O4).

I treat **copied shared events as both evidence and duplication**. They are evidence that the chosen objects truly participated in the same execution (P3 really packed I21 and I31 together; D2 really carried P2 and P3). They are duplication as soon as one sums case-level frequencies or interprets a DFG edge weight as “how often the warehouse packed.” Every numeric claim below therefore states the event count and the flattened-case count separately.

I **do not silently propagate** O2O links into E2O. Create Order on O1 is not attributed to I11 or P1; Record Payment on V1 is not attributed to I11. Propagation is permitted only as a named, reversible transformation (Section 7): for example, pushing invoice events onto contained items, or pulling package events onto the orders those packages pack. When I mention a propagated view I label it as such.

Performance numbers are read as timestamps of the events that survive the projection. A short lifecycle is not automatically a short real process; Payment objects participate in a single activity, so their traces are structurally truncated even when the commercial cycle ran from `e02` to `e29`.

## 3. Concrete distortion analysis

**D1 — Cross-order package P3, Order flattening.** Event `e13` (Pack Package, 10:12) is one warehouse act that packs I21 and I31 into P3 and is related to O2 and O3. Flattening on Order copies `e13` into both cases. The DFG edge Add Item → Pack Package fires for O2 (`e07`→`e13`) and for O3 (`e09`→`e13`), and the activity frequency of Pack Package becomes 6 case-occurrences against 4 events. Harmful if one reports “we packed six times”; informative if one asks “which orders were touched by a pack.” Context-dependent.

**D2 — Cross-order package P4, Order and Item flattening.** `e14` packs I32 and I41 into P4 for O3 and O4. On Order, O3 already contains `e13`, so O3’s variant is Create → Add → Add → Pack → Pack → … — a double-pack that looks like rework or a loop. It is neither: I31 left in P3, I32 left in P4. On Item, `e14` is correctly one pack per item but is still copied to I32 and I41, so item-level pack frequency is 6, not 4. Harmful as rework diagnosis; informative as evidence that O3 is a split order. Context-dependent.

**D3 — Consolidated delivery D2, Order flattening.** `e16` (Dispatch, 11:05) lists O1, O2, O3, I12, I21, I31, P2, P3, D2. One truck movement becomes three order-case events. O1 additionally has `e15` (its other half, D1), so O1 shows Dispatch → Dispatch (`e15`→`e16`) with a five-minute gap that is not a second shipment decision but the clock difference between D1 and D2. Fleet utilisation and “orders dispatched” diverge: 3 trips vs 6 order-dispatches. Harmful for capacity; informative for “which customers shared a run.”

**D4 — Consolidated delivery D2, Package flattening (complement).** Flattening on Package copies only `e16` and `e24` into P2 and P3. Cardinality of Dispatch becomes 4 (P1,P2,P3,P4) against 3 deliveries. The distortion is smaller than the order view but still overstates trips if package cases are summed. Delivery flattening (D1/D2/D3) does not inflate. The same events are therefore safe on Delivery, slightly inflated on Package, badly inflated on Order. Context-dependent: choose the grain that matches the KPI.

**D5 — Consolidated invoicing V2, Order flattening.** `e19` (Issue Invoice) is one document V2 billing O2 and O3. Flattening copies it into both orders, so Issue Invoice frequency is 4 case-events vs 3 events. Variants for O2 and O3 both contain a private-looking Issue Invoice after Dispatch, hiding that billing was batched. A discovered rule “every order is invoiced once” still holds per case, but “we issued four invoices” is false. Harmful for financial-control counts; acceptable for “was this order billed.”

**D6 — Partial payments on V2, Order vs Invoice vs Payment.** `e22` (M2, partially_settles V2, 12:40) and `e25` (M3, completes_settlement V2, next day 09:00) are each related to O2, O3, V2 and the respective payment. Order flattening copies *both* events into *both* orders: 4 events become 6 case-events, and both O2 and O3 show two Record Payment steps. Invoice flattening keeps the instalment structure inside V2 only (`e19`→`e22`→`e25`) — the only projection where “paid in two instalments” is a single-case fact. Payment flattening yields two singleton cases M2 and M3 with no successor, so the instalment relation disappears unless one reads the O2O qualifier `partially_settles` / `completes_settlement`. Harmful on Payment; informative on Invoice; mixed on Order (correct that both orders remain open until M3, incorrect as a payment count).

**D7 — Near-singleton Payment lifecycle.** M1–M4 each appear only on one `Record Payment` event. The flattened log has four traces of length 1, no DFG edges, no waiting time, 100% start-and-end activity `Record Payment`. Interpreting this as “the payment process is instantaneous and unstructured” is an object-grain artefact. Delivery is only slightly richer (two events) and similarly cannot speak to packing or billing. Harmful if offered as an E2E model; informative as a warning that object participation, not process brevity, drives trace length.

**D8 — O1 split across P1/P2, performance bias on Order.** I11 is packed `e11` 10:00, dispatched `e15` 11:00, confirmed `e23` 14:00. I12 is packed `e12` 10:10, dispatched with D2 at `e16` 11:05, confirmed `e24` 16:00. Order-level sojourn from Create (`e01` 09:00) to last Confirm or to Close (`e28` 11:00 next day) is dominated by the slower half and by overnight close policy. Mean “delivery time” on the Order log therefore hides that half the lines were confirmed two hours earlier. Item flattening shows the gap; Package flattening shows P1 faster than P2. Harmful if SLA is line-level; acceptable if SLA is “order complete.”

**D9 — O3 finance/logistics interleaving.** O3’s timestamp order is … `e22` 12:40 pay, `e24` 16:00 confirm D2, `e25` 09:00 next day pay M3, `e27` 10:00 confirm D3, `e30` close. The Order DFG therefore contains Confirm Delivery → Record Payment and Record Payment → Confirm Delivery. Neither edge is a business rule; they are the merge of V2’s second instalment with D3’s later arrival. A log skeleton will not forbid pay-after-confirm, and a conformance check against a “happy” invoice-then-deliver model will flag O3 (and O2, which also has `e24`→`e25`) as deviant. Harmful as a control-flow discovery; informative as a symptom that one lead object is mixing two subsystems.

**D10 — Item/Package lifecycle truncation vs commercial close.** None of I11–I41 or P1–P4 appear on `e18`–`e22`, `e25`–`e26`, `e28`–`e31`. Flattening there makes Confirm Delivery a terminal activity. O1 is actually closed at `e28`, after both confirms; O2 is closed at `e29` after M3. An item-level “end-to-end time” systematically understates commercial duration and cannot detect unpaid-but-delivered (not present here, but the projection would be blind to it). Harmful for cash-conversion analysis; fine for physical flow.

## 4. Traditional versus object-centric analysis portfolio

Create four flattened logs, not one, and refuse to let any of them answer questions outside their grain.

- **Order log:** order cycle time (Create→Close), whether every order is billed and paid, close-out completeness, and *existence* of split fulfilment (repeated Pack/Dispatch/Confirm on O1, O3). Do not use it for pack counts, trip counts, invoice counts, or “rework” loops.
- **Item log:** line-level path regularity, which lines shared a pack or a truck (`e13`/`e16`/`e24` vs `e14`/`e17`/`e27`), and the I11 vs I12 service-time gap. Do not use it for revenue, payment, or order close.
- **Package log:** handling-unit path Pack→Dispatch→Confirm, and the fact that P3 and P4 are the merge points. Safe frequencies for *packages packed* (4). Not safe for *trips* (use Delivery) or *orders packed*.
- **Invoice log:** billing and instalments, especially V2’s `e22`+`e25`. The only traditional log in which partial payment is a within-case pattern rather than a copy artefact.

Do **not** flatten on Payment for process discovery. Do flatten on Delivery only for a two-step transit DFG and a correct trip count (3).

Questions that require object-centric artefacts:

- **OC-DFG:** activity frequencies that must not be copied per related object of one type; comparison of Order-typed vs Package-typed vs Invoice-typed edge weights on the *same* events (`e16` is one Dispatch node with several OT-qualified arcs).
- **OTG / object interaction summary:** the many-to-many mesh O1–{I11,I12}–{P1,P2}–{D1,D2}, P3–{I21,I31}–{O2,O3}, D2–{P2,P3}–{O1,O2,O3}, V2–{O2,O3}–{M2,M3}. This is the primary explanation of every convergent event.
- **ET–OT graph:** which event types bind which object types. It shows immediately that Record Payment never binds Item/Package/Delivery, Create/Close bind only Order, Pack binds Order+Item+Package, Dispatch binds those plus Delivery. That graph is the reason Payment traces are singletons and why Item traces cannot answer cash questions.
- **Equivalent-execution clustering:** to group O4-like simple stars (one item, one pack, one delivery, one invoice, one payment) against O1-like splits and O2/O3-like merges without declaring one of those shapes “the” case. Justified precisely because no lead object is adequate alone.

Reconciliation rule: when a flattened DFG and an OC-DFG disagree on frequency, **trust the event cardinality and the OC-DFG’s per-object-type qualification**, then explain the gap with the interaction summary. Example: flattened Order DFG says Dispatch occurred 6 times; OC-DFG says the activity occurred 3 times and the Order-qualified participation is 6; OTG says D2 touches three orders. All three statements are true; only the first is commonly misread. When a flattened Order model shows Confirm→Pay and the Invoice model shows only Issue→Pay→Pay, treat the former as a merge artefact (D6, D9) and the latter as the financial control flow. Do not average them.

## 5. Lead-object decision

**Position C. Reject a single lead object for this process.**

**Decision criteria.** A defensible single lead would (i) participate in every activity class that the analysis claims to cover, (ii) keep event frequencies within a small, explainable factor of true event counts, (iii) avoid mixing independent physical streams into one clock, and (iv) still expose the consolidations (P3, P4, D2, V2, M2/M3) rather than dissolve them into copied steps. I require all four for an *end-to-end* lead. None of the six types satisfy all four.

**Strongest supporting evidence.** The snapshot is built from overlapping many-to-many links, not from a hierarchy under one root. O1 is split across P1 and P2 and then across D1 and D2. P3 merges O2 with O3; P4 merges O3 with O4; D2 then merges P2 with P3 and therefore O1 with O2 and O3; V2 merges O2 with O3 financially; V2 is settled by two payments. The same event `e16` is simultaneously one delivery, two packages, three items, and three orders. Promoting any one of those types to “the case” makes the other cardinalities wrong. Order, the only type that sees Create through Close *and* money, is also the type with the worst convergence (Dispatch 3→6, Pay 4→6) and the worst divergence (O1, O3). Package and Delivery fix logistics cardinality and destroy the commercial spine. Invoice fixes instalments and destroys logistics. Item is a good diagnostic grain and still misses every financial event. Payment is a singleton inventory.

**Strongest counterargument.** Practically, sales and audit stakeholders will demand an order-level cycle time, and Order *is* the only type related to both `Create Order` and `Close Order`. One could adopt B: Order as primary, Package/Delivery/Invoice as mandatory secondaries. That is operationally close to what Section 4 already recommends. I still reject calling Order a *lead* because the qualifier “lead” licenses people to publish Order-DFG frequencies and O3’s Confirm→Pay→Confirm path as *the* process. Given the designed consolidations, that license is the failure mode.

**Residual risk.** Without a lead, teams may produce a collage of views and never commit to a KPI owner. Order cycle time, trip count, and days-sales-outstanding will be computed on incompatible denominators (4 orders, 3 deliveries, 3 invoices) and then compared as if they were the same sample. Rejection of a lead is not rejection of measurement; it is a requirement that each KPI name its object type.

**When I would change my mind.** Move to **B** if a named stakeholder question is strictly commercial (“time from `e01`–`e04` to `e28`–`e31` per order”) *and* the analysis contract forbids publishing Order-flattened pack/dispatch frequencies. Move to **A with Order** only if the O2O consolidations were removed (no shared P3/P4, no D2, no V2, no split O1) so that order, package, and delivery were 1:1. Move to **A with Package** only if the question is warehouse execution and invoices are out of scope. I would never select Payment or Delivery as a single E2E lead on this event–object incidence.

## 6. PM4Py analysis outline

```python
import pm4py
from collections import Counter

print(ocel)

# --- Incidence: activities, object types, E2O fan-out (copy risk) ---
ev = ocel.events
obj = ocel.objects
e2o = ocel.relations

activity_freq = ev["ocel:activity"].value_counts().rename("event_count")
object_type_freq = obj["ocel:type"].value_counts().rename("object_count")
e2o_by_ot = e2o.groupby(["ocel:eid", "ocel:type"]).size().unstack(fill_value=0)
convergent_events = {
    ot: sorted(e2o_by_ot.index[e2o_by_ot[ot] > 1].tolist())
    for ot in e2o_by_ot.columns
}
print(activity_freq)
print(object_type_freq)
print(convergent_events)  # events that will be copied under each flattening

LEAD_TYPES = ["Order", "Item", "Package", "Delivery", "Invoice", "Payment"]

# --- Flatten + classical views (do not interpret visually as ground truth) ---
flat_logs, dfgs, skeletons = {}, {}, {}
flat_activity_counts, trace_lengths = {}, {}
for ot in LEAD_TYPES:
    log = pm4py.ocel_flattening(ocel, ot)
    flat_logs[ot] = log
    dfg, starts, ends = pm4py.discover_dfg(log)
    dfgs[ot] = {"dfg": dfg, "starts": starts, "ends": ends}
    skeletons[ot] = pm4py.discover_log_skeleton(log)
    acts = [a for t in log for a in t]
    flat_activity_counts[ot] = Counter(acts)
    trace_lengths[ot] = [len(t) for t in log]

# Explicit frequency gap: event count vs flattened case-event count
freq_gap = {}
for act, n_events in activity_freq.items():
    freq_gap[act] = {
        "events": int(n_events),
        **{f"flat_{ot}": flat_activity_counts[ot][act] for ot in LEAD_TYPES},
    }

# Divergence proxy: repeated activity labels inside one flattened case
divergent_cases = {}
for ot, log in flat_logs.items():
    hits = []
    for t in log:
        c = Counter(a for a in t)
        reps = {a: k for a, k in c.items() if k > 1}
        if reps:
            hits.append({"case": t.attributes.get("concept:name"), "repeats": reps})
    divergent_cases[ot] = hits

# --- Object-centric views (same ocel, no case identifier) ---
ocdfg = pm4py.discover_ocdfg(ocel)
otg = pm4py.discover_otg(ocel)
etot = pm4py.discover_etot(ocel)
interactions = pm4py.ocel_objects_interactions_summary(ocel)

# Clustering is justified by decision C: structural variants without a lead case
# (O4-like star vs O1 split vs O2/O3 merge). Inspect cluster membership
# against object ids; do not treat a cluster as a flattening.
equivalent_clusters = pm4py.cluster_equivalent_ocel(ocel)

# Reconciliation table: never resolve semantics by looking at a diagram
print("FREQ_GAP", freq_gap)
print("DIVERGENT_CASES", divergent_cases)
print("TRACE_LENGTHS", {ot: (min(v), max(v), sum(v) / len(v)) for ot, v in trace_lengths.items() if v})
print("OC-DFG / OTG / ET-OT / interactions / clusters stored in "
      "ocdfg, otg, etot, interactions, equivalent_clusters")
```

## 7. Sensitivity and validation plan

**S1 — Down-weight or drop copied shared events.** Build, for each flattening, a second log that keeps a shared event in only one case (e.g. the lexicographically first related object, or a designated “primary” order on a multi-order event). Recompute DFG weights. For Order, `e16`/`e24` should fall from 3 case-copies to 1; Pack should fall from 6 to 4 if `e13` and `e14` are also de-duplicated. If a qualitative path (O1’s Dispatch→Dispatch) disappears, it was a copy/split artefact, not a repeated business step. Report both the multi-case-participation count (evidence) and the de-duplicated count (activity volume).

**S2 — Direct E2O vs explicit O2O propagation.** Construct a derived OCEL that, as a named transform, (a) pushes each order’s Create/Close onto its `contains` items, (b) pushes each invoice/payment onto billed orders’ items, (c) pulls each package’s Pack onto the orders of packed items. Re-flatten Item and Package. If Item traces suddenly contain Issue Invoice, that is the transform, not the source log. Compare cycle times: I11 should then extend from `e05` toward `e28` instead of stopping at `e23`. Any conclusion that is not stable across {direct, propagate-down, propagate-up} must be labelled projection-dependent.

**S3 — Change the lead object on the same question.** Take one KPI, “mean time from first fulfilment act to confirm,” and compute it on Order (first Pack of that order → last Confirm), Item (Pack→Confirm per line), Package (Pack→Confirm), and Delivery (Dispatch→Confirm). O1 will look slow on Order (waits for `e24`), fast on I11/P1/D1, and intermediate on I12/P2. If the ranking of “slow work” changes with the lead type, do not publish a single ranking. Repeat for “payment after delivery”: true for O2/O3 (`e24` before `e25`), false for O4 (`e26` before `e27`), invisible on Item/Package.

**S4 — Triple frequency accounting on the OC-DFG.** For each activity, record (i) unique events, (ii) unique objects of each type related to those events, (iii) total E2O rows (events × related objects of that type). For Dispatch: (i) 3 (`e15`,`e16`,`e17`); (ii) 4 orders, 6 items, 4 packages, 3 deliveries; (iii) 6 order-participations, 6 item-participations, 4 package-participations, 3 delivery-participations. A discovery that matches (iii) for Order but is presented as (i) fails validation. Require every published edge weight to declare which of the three denominators it uses.

**Additional check.** Leave-one-consolidation-out: remove P3’s link to I31 (or drop `e13`’s O3/I31 relations) and re-flatten. If O3’s double-pack and D2’s triple-order copy are the main source of Order-DFG loops, the loops should shrink. Stability of Close Order sequencing (`e28`–`e31`) under that perturbation confirms that the commercial close is not an artefact of the merges, while instability of Pack/Dispatch loops confirms that those loops are.

Together S1–S4 implement the assumption of Section 1: copied events are evidence *and* duplication, propagation is never silent, and no flattening is “more correct” because its traces are longer. Order traces are the longest here because Order is related to the most event types, not because Order is the process.
