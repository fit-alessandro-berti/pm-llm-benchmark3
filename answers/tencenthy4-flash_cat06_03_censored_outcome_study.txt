## 1. Target definition

**Primary target:** an all-application, process-aware **competing-outcome target** where the event of interest is:

> `AD`: the application is eventually activated and has a recorded default within 90 days after `Account Activated`.

The full outcome state space is:

- `AD`: activated and default within 90 days after activation;
- `AN`: activated, matured 90-day outcome, no default;
- `REJECT`: rejected before activation;
- `WITHDRAW`: withdrawn before activation;
- `TRANSFER`: transferred before activation;
- censored / indeterminate: still open, activated but not matured, delayed label, missing feed.

**Prediction time:** primary model uses a fixed prefix ending at the third non-duplicate, canonically renamed event, intended to be `Application Started -> Identity/KYC Check -> Credit Review`. Only events with timestamp `<= t_p` are used.

**Horizon:** 90 days after `Account Activated`. Because the outcome feed arrives 7–35 days later, a no-label activated case is not called non-default until the administrative maturity rule is met; conservatively, activation timestamp plus 125 days must be before the as-of date.

**Unit of analysis:** economic application, not raw event-log row. Linked transferred duplicates should be deduplicated where the linkage table permits; unlinked transfers remain a known missing-linkage issue.

**Population:** all applications started between 2024-01-01 and 2025-12-31 with a usable early prefix. Censored cases are retained for censoring-aware modeling/weighting; they are not recoded as non-default.

**Estimand:** for a new application with prefix `X = x`, under the historical policy/process regime, estimate

\[
P(Y = y \mid X=x), \quad y \in \{AD, AN, REJECT, WITHDRAW, TRANSFER\},
\]

with censoring handled by IPW or a multi-state/competing-risk likelihood. This is a predictive estimand for the observed process, not a counterfactual default risk for cases that were never activated.

This formulation is operationally defensible because it can score every early application without pretending that rejected, withdrawn, transferred, or open cases had observed default outcomes. Statistically, it avoids the main selection error: training a binary default model only on matured activated accounts and then applying it to all applications.

**Credible alternative target:** activation-conditional survival analysis among eventually activated accounts:

\[
P(T_{default} \le 90 \mid \text{activated}, X=x),
\]

with right censoring for activated accounts whose labels are not yet mature. This answers a different question: “Given that this application becomes an activated account, what is its default risk?” It is useful for post-activation portfolio monitoring but is selective when applied to all applicants.

**Stronger counterfactual target:** “Would this applicant default within 90 days if we activated them under policy P?” This requires activation policy, positivity, sequential ignorability, and assumptions about outcomes for never-activated cases. It is not identifiable from these data without much stronger assumptions and should not be the primary model.

## 3. Censoring and missing-label strategy

**Types of missingness/censoring**

1. **Ordinary right censoring**  
   Still-open applications and activated accounts whose activation-plus-90-day-plus-feed-delay window has not elapsed by `2026-02-15`. Their future outcome is unknown, not negative.

2. **Delayed labels**  
   Default may have occurred by activation+90 days, but the warehouse feed arrives 7–35 days later. A label is usable at a backtest origin only if `label_available_at <= origin`. If the label has not arrived yet, the case is censored at that origin.

3. **Selection through activation**  
   `default_90d` exists only for activated accounts. Rejected, withdrawn, and transferred applications have no observed default outcome under the observed policy. Treating them as non-defaults would estimate a mixture of credit exposure, applicant behavior, and fraud/default risk.

4. **Transfer as competing event or missing follow-up**  
   For the primary target, transfer before activation is a competing terminal outcome. If the lender wants partner-platform downstream default, transfer becomes a missing-follow-up problem because only about 60% are linkable. The linked subset may not be representative.

5. **Permanently missing outcome feeds**  
   Partner-originated activated accounts have elevated probability of permanently missing outcome feeds. This is not ordinary censoring and may be MNAR. These cases must not be labeled `AN`.

**Primary analysis strategy**

Use a discrete-time multi-state or competing-risk model with absorbing states `AD`, `AN`, `REJECT`, `WITHDRAW`, `TRANSFER`, and censoring. Estimate class probabilities with IPCW for administrative censoring and delayed labels, using features available at the prefix time. For survival-style reporting, estimate the cumulative incidence of `AD` while treating competing terminal outcomes as competing events.

**Sensitivity analyses**

- Activation-conditional survival model among activated matured accounts only, explicitly labeled as conditional on activation.
- Partner-downstream sensitivity using the 60% linkage table, with IPW for linkage if covariates predict linkage.
- Pattern-mixture or best/worst-case bounds for permanently missing partner feeds.
- Refit separately pre/post policy change and pre/post migration.

**Assumption status**

| Assumption | Status |
|---|---|
| Event timestamps and activity renaming are correct after migration | Testable from raw logs and migration documentation |
| Duplicate events can be removed by deterministic rules | Partially testable; ambiguous duplicates require manual audit |
| Label delay distribution and whether labels were known by a backtest origin | Partially testable from `label_available_at` |
| Censoring independent of default given rich prefix/reference features | Partially testable via covariate balance after weighting |
| Partner-feed missingness MAR given observed channel/source/region | Partially testable at best |
| Permanent partner-feed missingness MNAR | Fundamentally untestable from observed labels |
| Rejected/withdrawn cases’ counterfactual default outcomes | Fundamentally untestable |

|---|---|---|---|---|
| `final_limit` | Populated only after final credit decision; strongly tied to accept/reject and outcome | Must exist at or before `t_p`; in this process it does not | Drop | Post-prefix decision artifact |
| `decision_reason` | Populated at/after Accept/Reject; reveals decision and possibly downstream risk | Must exist at or before `t_p`; normally absent | Drop | Direct future decision leakage |
| `collection_status` | Updated after activation and may directly reveal default | Never use for early prefix model | Drop | Post-outcome information |
| Future events: `Contract Signed`, `Account Activated`, `Collections Contact`, `Default Recorded` | Reveal activation and default path | Use only for target/censoring construction, not features | Keep for labels only; drop from features | Target construction is allowed; prediction cannot see them |
| `default_90d` repeated on events | Outcome label may be copied onto early event rows | Never use as feature; use only at case level for target after maturity | Drop from features | Classic target leakage |
| `label_available_at` | Feed timing may depend on default and source system | Use only to determine whether label was known at as-of/backtest origin | Drop from features | Not a predictor |
| `documents_total` nightly snapshot | Same-day snapshot may include documents uploaded after nominal `t_p` | Use only snapshots with timestamp strictly before `t_p`, or reconstruct from document event timestamps | Repair or drop | Avoid same-day look-ahead |
| Updated `risk_score` | Valid if genuinely computed at event time; may be refreshed using later information | Use latest nonmissing value with event timestamp `<= t_p`; record update count and age | Keep if audited | Time-available risk signal |
| Resource experience | Stored at extraction time, not event time | Reconstruct experience using only events before each event time | Repair; otherwise drop | Extraction-time value leaks future workload/history |
| `source_system` / migration indicators | Post-migration naming may create artificial shifts | Use first observed system at prefix time; migration flag only if known then or as diagnostic | Keep carefully | Useful for shift diagnostics, not outcome |
| `data_extract_time` | Same for all rows; not a case-level predictor | Metadata only | Drop | No predictive meaning; may encode extract batch |
| Transfer linkage table | Linkage only ~60%; linked cases may differ | Use for deduplication/sensitivity, not as a feature unless known at prediction time | Keep outside main feature table | Missing-linkage mechanism can bias downstream target |

## 7. Validation design

**Primary validation: temporal split by case start time**

Suggested windows:

- Train: applications started 2024-01-01 through 2025-06-30, pre-policy-change.
- Validation: 2025-07-01 through 2025-09-30, post-policy-change and pre-migration.
- Test: post-migration cases from 2025-10-15 onward that are matured by the as-of rule; report censored late-start cases separately.

Because activation must precede the end of the observation/feed window, many late-2025 starts may not be mature. Those cases should be censored or excluded from mature-case multiclass evaluation, not treated as negatives.

**Rolling-origin backtesting**

Use additional origins such as 2025-04-01, 2025-07-01, and 2025-10-15. For each origin:

- rebuild cohort and labels as of that origin;
- use only labels with `label_available_at <= origin`;
- train only on cases whose outcomes would have been known then;
- validate on the following time block.

This simulates real deployment under delayed labels.

**Policy change**

Evaluate pre/post 2025-07-01 separately. Include policy-regime flags and interactions where supported. If calibration shifts after the policy change, either refit, recalibrate, or restrict deployment to the relevant regime.

**System migration**

Evaluate post-2025-10-15 performance after canonicalizing activity names and removing duplicate events. Compare prefix variant distributions before and after migration to detect artificial drift.

**Calibration and subgroup performance**

Report calibration by predicted class, especially `AD`, and by:

- channel;
- region;
- requested-amount band;
- partner/source system;
- pre/post policy;
- pre/post migration;
- labeled versus transferred/censored status where relevant.

**Metrics**

For the multiclass primary target:

- multiclass log loss;
- multiclass Brier score;
- per-class calibration curves and expected calibration error;
- one-vs-rest AUC for `AD` as discrimination only;
- confusion matrix and observed `AD` rate among top-risk flagged cases.

For censoring-aware analysis:

- IPCW-weighted log loss/Brier;
- calibration of predicted cumulative incidence of `AD`;
- integrated Brier score or time-dependent calibration where a survival/competing-risk model is used;
- cause-specific cumulative incidence for competing outcomes.

**Why random split is misleading**

A random case split mixes pre/post policy regimes, pre/post migration behavior, duplicate/transferred cases, and different label-maturity periods. It also allows the model to exploit extraction-time features and outcome-correlated feed timing. Random validation therefore overstates transportability to future applications.

## 8. Limitations and decision-use boundary

**What the study can claim**

- It can estimate predictive associations between early process behavior and later observed outcome states under the historical policy and data-generating process.
- It can rank applications by probability of becoming an activated account that defaults within 90 days.
- It can show how those probabilities calibrate across time, channels, and process regimes.

**What the study cannot claim**

- It cannot estimate default risk for rejected, withdrawn, transferred, or open applications as if they had been activated.
- It cannot call missing labels non-defaults.
- It cannot estimate the causal effect of accepting, rejecting, or transferring an application.
- It cannot fully correct permanently missing partner outcome feeds without untestable assumptions.
- It cannot guarantee transportability after the policy threshold change, system migration, or changes in partner reporting.

**Predictive association versus selection effects**

A prefix pattern may predict `AD` partly because it predicts eventual activation under the historical policy. The all-application competing-outcome target preserves that distinction. An activation-conditional model removes some process outcomes but conditions on a selected population, so it answers a narrower question.

**Deployment changes that can alter the data-generating process**

1. If the model is used to flag or reject applications, applicants and staff may change behavior, changing withdrawal and approval patterns.
2. Credit-policy thresholds can change selection into activation and the relationship between `risk_score` and default.
3. Staffing, queues, or document-request practices can change prefix timing and rework patterns.
4. Partner platforms can change reporting rates, linkage quality, or activation rules.
5. Migration or interface changes can alter event names, timestamps, and duplicate patterns.

The model should therefore be used as a monitoring/decision-support signal with drift monitoring and periodic recalibration, not as evidence of counterfactual default behavior.

## 9. PM4Py-oriented Python implementation skeleton

```python
import numpy as np
import pandas as pd
import pm4py

CSV = "applications_events.csv"
CASE, ACT, TIME = "case:concept:name", "concept:name", "time:timestamp"
RISK = "risk_score"
EXTRACT = pd.Timestamp("2026-02-15")
MAX_FEED_DELAY_DAYS = 35
K = 3
POLICY_CHANGE = pd.Timestamp("2025-07-01")
MIGRATION = pd.Timestamp("2025-10-15")

raw = pd.read_csv(
    CSV,
    parse_dates=[TIME, "label_available_at", "data_extract_time"]
)

# Outcome/future columns: never valid as early-prefix features.
BLOCKED = [
    "final_limit", "decision_reason", "collection_status",
    "default_90d", "label_available_at", "data_extract_time",
    "documents_total"
]

# Canonicalize renamed activities before sorting, prefixing, or labeling.
RENAME = {
    "Identity / KYC Check v2": "Identity/KYC Check",
    "Identity-KYC Check": "Identity/KYC Check",
    "Credit Review v2": "Credit Review",
    "Document Request v2": "Request Documents",
    "Contract Signed v2": "Contract Signed",
    "Account Activated v2": "Account Activated",
}
raw[ACT] = raw[ACT].replace(RENAME)
raw = raw.sort_values([CASE, TIME])

# Remove exact duplicates created by migration; document ambiguous duplicates separately.
dup_key = [CASE, ACT, TIME, "org:resource", "source_system"]
raw = raw.drop_duplicates(subset=dup_key, keep="first")

fmt = pm4py.format_dataframe(
    raw, case_id=CASE, activity_key=ACT, timestamp_key=TIME
)
log = pm4py.convert_to_event_log(fmt)

TERMINALS = ["Rejected", "Withdrawn", "Transferred"]
TERMINAL_TARGET = {
    "Rejected": "REJECT",
    "Withdrawn": "WITHDRAW",
    "Transferred": "TRANSFER",
}

def build_case_table(df, as_of):
    """Case-level start/activation/terminal/censoring/label status as of as_of."""
    g = df.groupby(CASE, sort=False)
    first = df.sort_values(TIME).groupby(CASE).first()

    act = (
        df[df[ACT].eq("Account Activated")]
        .sort_values(TIME)
        .drop_duplicates(subset=CASE, keep="first")
        .set_index(CASE)
    )
    term = (
        df[df[ACT].isin(TERMINALS)]
        .sort_values(TIME)
        .drop_duplicates(subset=CASE, keep="first")
        .set_index(CASE)
    )
    lab = (
        df.dropna(subset=["default_90d"])
        .sort_values(TIME)
        .drop_duplicates(subset=CASE, keep="last")
        .set_index(CASE)
    )

    out = pd.DataFrame(index=g.size().index)
    out["start_time"] = g[TIME].min()
    out["activation_time"] = act[TIME].reindex(out.index)
    out["terminal_time"] = term[TIME].reindex(out.index)
    out["terminal_activity"] = term[ACT].reindex(out.index)
    out["n_events"] = g.size()

    for c in ["case:channel", "case:region", "requested_amount", "source_system"]:
        out[c] = first[c].reindex(out.index)

    out["default_90d"] = pd.to_numeric(
        lab["default_90d"].reindex(out.index), errors="coerce"
    )
    out["label_available_at"] = pd.to_datetime(
        lab["label_available_at"].reindex(out.index), errors="coerce"
    )

    # Conservative maturity: activation + 90d horizon + max 35d feed delay.
    out["maturity_at"] = (
        out["activation_time"] + pd.Timedelta(days=90 + MAX_FEED_DELAY_DAYS)
    )

    status = pd.Series("censored_open", index=out.index, dtype=object)
    target = pd.Series(np.nan, index=out.index, dtype=object)

    term_ok = (
        out["terminal_activity"].notna()
        & out["terminal_time"].le(as_of)
        & out["activation_time"].isna()
    )
    status.loc[term_ok] = "competing_observed"
    target.loc[term_ok] = out.loc[term_ok, "terminal_activity"].map(TERMINAL_TARGET)

    activated = out["activation_time"].notna() & out["activation_time"].le(as_of)
    matured = activated & out["maturity_at"].le(as_of)
    label_ok = (
        matured
        & out["default_90d"].notna()
        & out["label_available_at"].le(as_of)
    )
    delayed = (
        matured
        & out["default_90d"].notna()
        & ~out["label_available_at"].le(as_of)
    )
    missing_feed = matured & ~label_ok & ~delayed
    not_mature = activated & ~matured

    status.loc[label_ok] = "labeled_matured"
    target.loc[label_ok] = np.where(
        out.loc[label_ok, "default_90d"].eq(1), "AD", "AN"
    )
    status.loc[delayed] = "censored_delayed_label"
    status.loc[missing_feed] = "selectively_unobserved_missing_feed"
    status.loc[not_mature] = "censored_not_mature"

    out["status"] = status
    out["target"] = target
    return out

case_info = build_case_table(fmt, EXTRACT)

print("Cohort counts by status:")
print(case_info["status"].value_counts(dropna=False))
print("Outcome-state counts among resolved cases:")
print(case_info["target"].value_counts(dropna=False))

# Fixed-length prefixes from PM4Py. Prefix log contains only early events.
prefix_log = pm4py.get_prefixes_from_log(log, length=K)
prefix_df = pm4py.convert_to_dataframe(prefix_log).sort_values([CASE, TIME])

# Drop all blocked columns before any feature engineering.
prefix_df = prefix_df.drop(
    columns=[c for c in BLOCKED if c in prefix_df.columns], errors="ignore"
)
prefix_end = prefix_df.groupby(CASE)[TIME].max().rename("prefix_end")

# Leakage audit: count full-log events after each prefix end; these are excluded.
full_check = fmt.merge(prefix_end, left_on=CASE, right_index=True, how="inner")
n_after = full_check[TIME].gt(full_check["prefix_end"]).sum()
leak_cols_present = sorted(set(BLOCKED).intersection(prefix_df.columns))
print(f"Full-log events after prefix end, excluded from features: {n_after}")
print(f"Blocked columns remaining in prefix table: {leak_cols_present}")
assert not leak_cols_present

# Process-aware features from prefix events only.
first_p = prefix_df.groupby(CASE).first()
risk_rows = prefix_df.dropna(subset=[RISK]).sort_values(TIME)
risk_last = risk_rows.groupby(CASE).last()[RISK].rename("risk_score_last")
risk_n = risk_rows.groupby(CASE).size().rename("risk_score_updates")

act_counts = (
    prefix_df.assign(_one=1)
    .pivot_table(index=CASE, columns=ACT, values="_one", aggfunc="sum", fill_value=0)
)
act_counts.columns = [
    "act_" + str(c).replace(":", "_").replace(" ", "_").replace("/", "_")
    for c in act_counts.columns
]

feat = pd.DataFrame(index=prefix_end.index)
feat["prefix_len"] = prefix_df.groupby(CASE).size()
feat["prefix_span_hours"] = (
    (prefix_end - first_p[TIME]).dt.total_seconds() / 3600.0
)
feat["n_unique_resources"] = prefix_df.groupby(CASE)["org:resource"].nunique()
feat["act_Request_Documents"] = act_counts.get("act_Request_Documents", 0)
feat["act_Credit_Review"] = act_counts.get("act_Credit_Review", 0)
feat = feat.join(act_counts).join(risk_last).join(risk_n)

for c in ["case:channel", "case:region", "requested_amount"]:
    feat[c] = case_info[c].reindex(feat.index)

feat["start_hour"] = case_info["start_time"].reindex(feat.index).dt.hour
feat["policy_regime_post"] = (
    case_info["start_time"].reindex(feat.index).ge(POLICY_CHANGE).astype(int)
)
feat["migration_period"] = prefix_end.ge(MIGRATION).astype(int)

# Prefix-only process diagnostics.
dfg, start_acts, end_acts = pm4py.discover_dfg(prefix_log)
variants = pm4py.get_variants(prefix_log)
print(f"Prefix variants: {len(variants)}; DFG edges: {len(dfg)}")

# Temporal, not random, split by application start time.
# For strict historical backtests, rebuild labels/features with as_of=origin and
# events filtered to time <= origin; do not use labels unavailable at that origin.
ds = feat.join(case_info[["start_time", "status", "target"]], how="left")
model_ds = ds[ds["target"].notna()].copy()

train = model_ds[model_ds["start_time"].le(pd.Timestamp("2025-06-30"))]
valid = model_ds[
    model_ds["start_time"].between(
        pd.Timestamp("2025-07-01"), pd.Timestamp("2025-09-30")
    )
]
test = model_ds[
    model_ds["start_time"].between(
        pd.Timestamp("2025-10-15"), pd.Timestamp("2025-12-31")
    )
]

print(f"Temporal split sizes: train={len(train)}, valid={len(valid)}, test={len(test)}")

# Later: fit a multiclass/competing-risk model, or a survival model.
# Keep censored_* rows for IPCW/survival; never map them to "AN".
```
