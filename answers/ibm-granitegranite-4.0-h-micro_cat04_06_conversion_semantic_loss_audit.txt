# 2. Candidate Conversion Pipelines

| Pipeline | PM4Py calls | Expected benefit | Expected risk | Failure condition |
|----------|-------------|------------------|---------------|-------------------|
| Primary | 1. `pm4py.convert_to_petri_net(source_powl)` <br> 2. `pm4py.convert_to_bpmn(net_from_powl)` <br> 3. `try: pm4py.convert_to_process_tree(net_from_powl) except Exception as e: log_error(e)` | Preserves control flow and concurrency; leverages BPMN's visual strengths. | Failure if optional legal or verification loop cannot be accurately represented as a process tree. | Conversion fails due to semantic mismatch or unsupported POWL features. |
| Alternative | 1. `pm4py.convert_to_petri_net(source_powl)` <br> 2. `pm4py.convert_to_process_tree(net_from_powl)` <br> 3. `pm4py.convert_to_bpmn(tree_from_pt)` | Directly validates process-tree semantics before BPMN; emphasizes structural fidelity. | Risk of losing concurrency information or losing optional behavior. | Conversion fails if process-tree cannot capture concurrency or optional behavior. |

# 3. Conversion Code

```python
import pm4py

# Load source POWL model
source_powl = StrictPartialOrder(
    nodes=[
        register,
        assess_risk,
        prepare_evidence,
        optional_legal,
        verification_loop,
        release_change,
        archive_change,
    ]
)
source_powl.order.add_edge(register, assess_risk)
source_powl.order.add_edge(register, prepare_evidence)
source_powl.order.add_edge(assess_risk, optional_legal)
source_powl.order.add_edge(assess_risk, verification_loop)
source_powl.order.add_edge(prepare_evidence, verification_loop)
source_powl.order.add_edge(optional_legal, release_change)
source_powl.order.add_edge(verification_loop, release_change)
source_powl.order.add_edge(release_change, archive_change)

# 1. POWL  Petri Net
net_from_powl = pm4py.convert_to_petri_net(source_powl)

# 2. Petri Net  BPMN
try:
    bpmn_from_net = pm4py.convert_to_bpmn(net_from_powl)
except Exception as e:
    print(f"Conversion to BPMN failed: {e}")
    bpmn_from_net = None

# 3. Attempt Process Tree Intermediate
try:
    tree_from_pt = pm4py.convert_to_process_tree(net_from_powl)
    print("Process Tree Conversion Succeeded")
except Exception as e:
    print(f"Process Tree Conversion Failed: {e}")
    tree_from_pt = None

# 4. BPMN round trip
if bpmn_from_net:
    # Save BPMN model
    pm4py.save_vis_bpmn(bpmn_from_net, f"bpmn_output_{source_powl.nodes[0].label}.bpmn")

    # Convert back to Petri Net
    net_round_trip = pm4py.convert_to_petri_net(bpmn_from_net)
    print("Round-trip conversion successful")

    # Soundness check
    is_sound = pm4py.check_soundness(net_round_trip)
    print(f"Soundness check result: {is_sound}")

    # Visualize the round-trip net
    pm4py.save_vis_petri_net(net_round_trip, f"round_trip_net_{source_powl.nodes[0].label}.png")

# 5. Failure Handling
if not bpmn_from_net:
    print("BPMN conversion failed. Exiting conversion process.")
```

# 6. Visual-Semantics Review

The BPMN rendering may be misread due to the following reasons:
- **Parallel gateways:** The concurrent execution of `legal_review` and `verification_loop` may appear as parallel activities, potentially leading to confusion about their interdependence.
- **Exclusive gateways:** The XOR operation between `legal_review` and `skip_legal` might be visually represented with an exclusive gateway, which could obscure the fact that both are optional.
- **Loop visualization:** The verification loop could be depicted as a sequence of activities, losing the iterative nature of the loop.
- **Silent routing nodes:** Silent transitions are not visually represented in BPMN, which might lead to misunderstandings about transitions that occur without explicit activity.
- **Ordering of graph layout:** The layout of nodes in BPMN may not accurately reflect the order of execution, particularly for unordered activities like `legal_review` and `prepare_evidence`.

**Proposed Annotations:**
- Clearly annotate optional branches with "Optional" labels.
- Use distinct colors or shapes to differentiate between required and optional activities.
- Include footnotes or legends explaining the XOR operation and silent transitions.
- Highlight the join point before `release_change` to emphasize its significance.

# 7. Rejection Criteria

1. **Unsoundness:** If the conversion results in a Petri net or BPMN model that violates temporal logic, it should be rejected.
2. **Loss of interleaving:** If the conversion fails to preserve true concurrency, it should be rejected.
3. **Absence of optional behavior:** If optional behaviors are lost or misrepresented, the conversion should be quarantined.
4. **Incorrect loop semantics:** If the loop semantics are misrepresented, the conversion should be rejected.
5. **Final marking mismatch:** If the final marking does not match the expected `archive_change`, the conversion should be rejected.
6. **Gateway or routing-node ambiguity:** If the BPMN model introduces ambiguity in gateways or routing nodes, it should be rejected.

# 8. Canonical Representation Recommendation

**Authoritative Representation:** The Petri net should be the authoritative representation due to its ability to capture concurrency and silent transitions accurately.

**Derivative Models:**
- **BPMN Models:** Generated from the Petri net and serve as a visual representation for stakeholders.
- **Process Tree:** Generated as an intermediate representation to validate process semantics before BPMN conversion.

**Validation Evidence:**
- Soundness checks on both Petri net and BPMN models.
- Footprint and reachability graph analyses to ensure behavioral equivalence.
- Trace exploration results to validate the presence of required behaviors.

**Process-Tree Intermediate Use:**
Allowed if it aids in validating the semantics of the POWL model before conversion to BPMN. The process tree should be used to ensure that the POWL model's concurrency and optionality are correctly interpreted.

**Avoiding Round-Trip Drift:**
- Regularly validate the round-trip conversion against the original POWL model.
- Use automated testing to ensure that each conversion step preserves the intended semantics.
- Document all conversion steps and validation results to maintain a clear audit trail.

# 9. Residual Uncertainty

1. **True concurrency representation:** The conversion may not fully capture the nuances of true concurrency, especially in complex POWL models.
2. **Behavioral equivalence:** While validation steps are performed, there may still be scenarios where the converted models exhibit behavioral equivalence but differ in implementation details.
3. **Stakeholder interpretation:** Even with detailed annotations, the visual representation of BPMN may still be subject to individual interpretation by stakeholders, leading to potential misunderstandings.
