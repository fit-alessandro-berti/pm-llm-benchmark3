# 1. Policy Interpretation and Conflict Resolution

## Material assumptions
- The event log contains at least `case:concept` (case id), `concept:name` (activity label), `time:timestamp`, and `resource`.
- Activities occur with the exact labels listed in the scenario.
- Relative hours in the test cases are converted to seconds using `1 hour = 3600 seconds`.
- No `emergency_auth` or joint-authorization attribute is present in the log. Its absence means an emergency exception cannot be confirmed from the log.
- “Accepted case” is reconstructed from the presence of `Activate Vendor`; “rejected case” from `Reject Vendor`. This is a log-only proxy; a proper case attribute would be better.

## R5 / R6 conflict: two possible resolutions

**Resolution A — Strict legal precedence (chosen for implemented model).**
R5 is treated as absolute for any log-based conformance: after `Sanctions Escalation`, `Obtain Legal Opinion` must occur before `Activate Vendor`.
R6 is modeled only as an external, off-log exception. Because the log lacks the emergency attribute and joint authorization, any activation before the legal opinion is a violation unless an external authorization record is supplied.

**Resolution B — Relaxed operations tolerance.**
R5 is downgraded to “eventually obtain opinion” plus a 24-hour tolerance: after `Sanctions Escalation`, if `Activate Vendor` occurs before `Obtain Legal Opinion`, the opinion must arrive within 24 hours. Traces are routed to manual review to confirm the missing joint authorization.

## Chosen model and compliance risk
We implement **Resolution A** as the authoritative policy.  
Compliance risk: legitimate emergencies will be flagged as violations, creating operational friction and possible false positives. However, this avoids undetected illegal activation and keeps legal exposure minimal. Resolution B is discussed for T6 but is not the default log-based encoding.

# 3. Procedural Backbone

## Compact formal description
1. `Receive Onboarding Request` starts the case.
2. `Capture Master Data`, `Run Sanctions Screening`, `Verify Bank Account` run concurrently.
3. Zero or more `Request Clarification  Receive Clarification` loops may occur before and after `Classify Risk`.
4. After classification:
   - `Reject Vendor  Close Onboarding`; or
   - `Manager Approval  Activate Vendor`; or
   - `Enhanced Due Diligence  Compliance Approval  Activate Vendor`.
5. An optional parallel branch may contain `Sanctions Escalation  Obtain Legal Opinion` (intentionally not ordered strictly, because R5 is enforced externally under Resolution A).
6. After activation: optionally `Change Bank Details  Suspend Vendor  Verify Bank Account` (loop), then `Release First Payment  Close Onboarding`.

## PM4Py Python code

```python
from pm4py.objects.process_tree.obj import ProcessTree, Operator

def act(label):
    t = ProcessTree()
    t.label = label
    return t

def seq(*children):
    t = ProcessTree(operator=Operator.SEQUENCE)
    t.children = list(children)
    return t

def xor(*children):
    t = ProcessTree(operator=Operator.XOR)
    t.children = list(children)
    return t

def par(*children):
    t = ProcessTree(operator=Operator.PARALLEL)
    t.children = list(children)
    return t

def loop_zero_or_more(body_nodes):
    tau = ProcessTree()
    body = seq(*body_nodes)
    l = ProcessTree(operator=Operator.LOOP)
    l.children = [body, body]
    return xor(tau, l)

receive = act("Receive Onboarding Request")

check_par = par(
    act("Capture Master Data"),
    act("Run Sanctions Screening"),
    act("Verify Bank Account")
)

clar1 = loop_zero_or_more([act("Request Clarification"), act("Receive Clarification")])
clar2 = loop_zero_or_more([act("Request Clarification"), act("Receive Clarification")])
classify = act("Classify Risk")

esc_opinion = xor(
    ProcessTree(),
    seq(act("Sanctions Escalation"), act("Obtain Legal Opinion"))
)

reject_seq = seq(act("Reject Vendor"), act("Close Onboarding"))

post_activate = seq(
    loop_zero_or_more([act("Change Bank Details"), act("Suspend Vendor"), act("Verify Bank Account")]),
    act("Release First Payment"),
    act("Close Onboarding")
)

low_seq = seq(act("Manager Approval"), act("Activate Vendor"), post_activate)
high_seq = seq(act("Enhanced Due Diligence"), act("Compliance Approval"), act("Activate Vendor"), post_activate)

low_full = par(low_seq, esc_opinion)
high_full = par(high_seq, esc_opinion)

choice = xor(reject_seq, low_full, high_full)

root = seq(receive, check_par, clar1, classify, clar2, choice)
procedural_model = root
```

## Explanation
- **Concurrency**: the three checks use a `PARALLEL` operator.
- **Choices**: the final `XOR` enforces R1/R2/R8 at the control-flow level.
- **Clarification loops**: `loop_zero_or_more` allows multiple `Request/Receive` cycles and prevents moving to a terminal outcome without a `Receive Clarification`.
- **Terminal outcomes**: `Close Onboarding` follows either rejection or first payment.
- **Post-activation behavior**: the optional `Change  Suspend  Verify` loop approximates R11; it forces a second verify before `Release First Payment` if a change occurred, but requires `Suspend Vendor` immediately after `Change Bank Details` (stronger than “eventually”).
- **Deliberately excluded from strict procedural order**: R5’s conditional precedence of `Obtain Legal Opinion` before `Activate Vendor` after escalation is handled externally because standard process trees cannot express a condition on another activity without duplicating the whole tree.

```python
def check_four_eyes(log):
    violations = []
    for case, events in log.groupby("case:concept"):
        if not all("resource" in e for e in events):
            violations.append((case, "R9", "missing resource attribute", "not evaluated"))
            continue
        res = {e["concept:name"]: e["resource"] for e in events}
        # R9a
        if "Verify Bank Account" in res and "Activate Vendor" in res:
            appr = None
            if "Manager Approval" in res:
                appr = "Manager Approval"
            elif "Compliance Approval" in res:

           and res["Capture Master Data"] == res["Activate Vendor"]:

def check_emergency_and_r5(log):
    findings = []
    for case, events in log.groupby("case:concept"):
        if not all("time:timestamp" in e for e in events):
            findings.append((case, "R5/R6", "missing timestamp", "not evaluated"))
            continue
        evs = sorted(events, key=lambda e: e["time:timestamp"])
        esc = [e for e in evs if e["concept:name"] == "Sanctions Escalation"]
        opn = [e for e in evs if e["concept:name"] == "Obtain Legal Opinion"]
        actv = [e for e in evs if e["concept:name"] == "Activate Vendor"]
        for e in esc:
            op_after = [o for o in opn if o["time:timestamp"] >= e["time:timestamp"]]
            if not op_after:
                findings.append((case, "R4", "no legal opinion after escalation", "fail"))
                continue
            for a in actv:
                if a["time:timestamp"] >= e["time:timestamp"] and \
                   a["time:timestamp"] < op_after[0]["time:timestamp"]:
                    auth = a.get("emergency_auth")
                    if auth is not None:
                        delta = (op_after[0]["time:timestamp"] - a["time:timestamp"]).total_seconds()
                        if delta <= 24 * 3600:

                        else:
                            findings.append((case, "R6", "opinion >24h after emergency activation", "fail"))
                    else:
                        findings.append((case, "R5", "activation before opinion without auth", "fail"))
    return findings

        evs = sorted(events, key=lambda e: e["time:timestamp"])
        for i, e in enumerate(evs):
            if e["concept:name"] == "Change Bank Details":
                later = evs[i+1:]
                if not any(x["concept:name"] == "Suspend Vendor" for x in later):
                    violations.append((case, "R11", "no Suspend Vendor after Change Bank Details"))
                rel = next((x for x in later if x["concept:name"] == "Release First Payment"), None)
                if rel:
                    ok = any(x["concept:name"] == "Verify Bank Account" and
                             x["time:timestamp"] > e["time:timestamp"] and
                             x["time:timestamp"] < rel["time:timestamp"] for x in later)
                    if not ok:
                        violations.append((case, "R11", "no Verify Bank Account before later Release"))
    return violations
```

Required attributes: `concept:name`, `time:timestamp`, `resource`, and optionally `emergency_auth`.  
If `resource` or `time:timestamp` is missing, the corresponding check returns `not evaluated`.

# 9. Contradictions, Redundancies, and Blind Spots

- **Duplicated enforcement**: R1, R8, and R10 are enforced in procedural, DECLARE, and Log Skeleton layers. This is deliberate defense-in-depth but can increase alert volume.
- **Loop / post-activation inconsistency**: R11’s “eventually suspend” is approximated by an immediate `Change  Suspend  Verify` sequence in the process tree. A valid trace with other events between change and suspend would be falsely flagged by the strict procedural model but accepted by the external check.
- **Vacuity in declarative rules**: `response(Sanctions Escalation, Obtain Legal Opinion)` is vacuously true when no escalation occurs. This is correct but hides whether escalation *should* have happened.
- **Missing case attributes**: Neither “risk class” nor “emergency authorization” is in the log. Therefore R2’s accepted/rejected distinction and R6’s exception are only approximated.
- **Timestamp-only limitations**: Temporal profile uses elapsed seconds; it cannot account for business hours, time zones, or data-entry lag.
- **Support/confidence as truth**: We set `support=1.0, confidence=1.0` normatively. If a DECLARE model were discovered from historical data with lower confidence, treating those numbers as compliant thresholds could mask emerging violations.

# 10. Deployment Recommendation

- **Canonical procedural representation**: the process tree above (`procedural_model`) is the baseline control-flow reference.
- **Authoritative policy layer**: the external resource/data and conditional policy checks (R5, R6, R9, R11) are authoritative for segregation of duties and emergency overrides. DECLARE and Log Skeleton are authoritative for their simple declarative constraints.
- **Check order**:
  1. Procedural conformance (catch gross control-flow violations like T5/T8).
  2. Log Skeleton (fast count and co-occurrence checks).
  3. DECLARE (declarative precedence/response).
  4. Temporal profile (warnings only).
  5. Resource/data layer (four-eyes, emergency policy, R11).
- **Contradictory findings**: any `fail` in an authoritative layer overrides a `pass` in a weaker layer. `policy-dependent` or `warning` items are routed to a compliance officer dashboard with the raw trace, missing attributes highlighted, and the specific rule (R5 vs R6) shown.
