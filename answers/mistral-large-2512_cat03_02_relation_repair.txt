# OCEL 2.0 Repair Proposal

## 1. Consistency rules and evidence model

**Hard invariants:**
- Every E2O relation must reference existing objects and events.
- O2O qualifiers must be directional (source  qualifier  target).
- No circular O2O relations (e.g., A contains B and B contains A).
- Object types must match domain semantics (e.g., only Items can be packed into Packages).

**Strong defaults:**
- `Add Item` events should relate to exactly one Order and one Item (cardinality 1:1).
- `Pack Item` events should relate to exactly one Item and one Package (cardinality 1:1).
- `Dispatch Package` events should relate to at least one Package and one Delivery (cardinality 1:N:1).
- `Issue Invoice` should relate to at least one Order (cardinality 1:N).
- `Record Payment` should relate to exactly one Payment and at least one Invoice (cardinality 1:1:N).

**Weak heuristics:**
- Matching identifier prefixes (e.g., "A-1"  IT-A1) suggest correct relations.
- Temporal proximity suggests related events (e.g., Pack Item  Dispatch Package).
- Route hints (NORTH) suggest matching between Packages and Deliveries.
- Customer consistency (C17) suggests related Orders, Invoices, and Payments.
- Arithmetic similarity (e.g., declared_value sums  invoice total) is suggestive but not definitive.
- Scanner references (e.g., "PK7-1"  PK-7) suggest Package relations.

**Evidence against a repair:**
- Timestamp violations (e.g., Pack Item after Dispatch Package).
- Type mismatches (e.g., relating a Package to an Order with "contains").
- Cardinality violations (e.g., multiple Deliveries for one Package without bulk dispatch).
- Contradictory O2O relations (e.g., PK-8 packs IT-B1 but PK-7 already packs IT-B1).
- Unresolvable identifier mismatches (e.g., "N-421?" vs. "N-420").

**Evidence combination:**
1. **Identifier similarity** (strongest): Direct matches (e.g., "PK7-1"  PK-7) are nearly definitive.
2. **Temporal order**: Events should follow lifecycle order (Create Order  Add Item  Pack Item  Dispatch Package  Confirm Delivery  Issue Invoice  Record Payment).
3. **Cardinality constraints**: Violations suggest missing or incorrect relations.
4. **O2O consistency**: Existing O2O relations (e.g., ORD-A contains IT-A1) should align with E2O relations (ev03 relates ORD-A and IT-A1).
5. **Attribute consistency**: Route hints, customer IDs, and amounts should align where applicable.
6. **Lifecycle completeness**: Orphan objects (e.g., IT-B1 never packed) suggest missing relations.

## 8. Over-repair warnings

1. **Forcing bulk dispatch**:
   - Repairing ev10 as a bulk dispatch (DEL-X carries PK-7 and PK-8) could create a false "bulk dispatch" pattern in the OC-DFG, even though the log only shows "N-421?" (ambiguous) and no explicit bulk dispatch event.

2. **Overallocating payments**:
   - Assigning PAY-2 to INV-44 based solely on amount matching (130  ORD-A's declared_value) could misrepresent payment allocation. PAY-2 might be unapplied cash or settle a different invoice.

3. **Assuming invoice scope**:
   - Repairing INV-44 to bill both ORD-A and ORD-B based on arithmetic matching (130 + 100 = 230) could misrepresent the invoice scope. The total might include fees or discounts, or INV-44 might only bill ORD-A.

4. **Overconfirming deliveries**:
   - Repairing ev11 to confirm both DEL-X and DEL-Y (or both ORD-A and ORD-B) could create false delivery confirmations. The portal might have lost the carrier identifier, and only one delivery might be confirmed.

5. **Forcing lifecycle completeness**:
   - Repairing the log to make every object lifecycle complete (e.g., forcing ORD-B to have a delivery and payment) could create false process behavior. Some orders might legitimately have incomplete lifecycles (e.g., canceled, returned, or still in progress).

6. **Ignoring scanner outages**:
   - Repairing ev08 to relate to PK-8 without considering that the scanner outage might have created an item-only row (as mentioned in domain semantics) could misrepresent the packing process. IT-B1 might not have been packed at all.

7. **Overusing identifier similarity**:
   - Repairing relations based solely on identifier similarity (e.g., "N-421?"  DEL-Y) could create false edges. The "?" suggests ambiguity, and DEL-Y might not be the correct delivery.
