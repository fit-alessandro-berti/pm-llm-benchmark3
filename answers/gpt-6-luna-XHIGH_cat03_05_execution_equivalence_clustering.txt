## 1. Equivalence design space

I use an execution as the events attached to one focal Order, together with the objects and relations in its object-centric neighborhood. The listed event order is temporal order. Local identifiers are arbitrary names; the EXT prefix is meaningful because it marks an object whose lifecycle is centered elsewhere.

**Activity-sequence equivalence (A).** Project each execution to its ordered activity labels, retaining repeats. With timestamps, make one bucket per timestamp and compare the ordered list of buckets, each bucket being a multiset of labels; this avoids inventing an order between simultaneous events. Here the supplied timestamp order has no ties, so this is the ordinary label sequence. A preserves label order and event multiplicity. It discards object types, identities, event-to-object incidence, O2O topology, and qualifiers. This is reflexive, symmetric, and transitive because it is equality of a deterministic projection. Simultaneous events are unordered within their bucket; different timestamp buckets remain ordered.

**Typed structural equivalence under renaming (T).** Build a colored event-object graph. Event nodes are colored by activity and their position in the timestamp order (or timestamp bucket); object nodes are colored by type and local/external status. A labeled incidence edge records every event-to-object participation, including the object type and role available in the OCEL. Add O2O edges with their relation kind and endpoints, but omit qualifiers such as “partially settles” or “removed before dispatch.” Two executions are equivalent iff these colored, ordered graphs are isomorphic while the focal Order is mapped to the focal Order. Thus object multiplicities, repeated events, E2O incidence, unqualified O2O topology, and externality are preserved; identifier spelling and qualifier values are discarded. This is reflexive, symmetric, and transitive by graph isomorphism. Simultaneous events have equal time-bucket colors and no arbitrary ordering edge; only order between buckets is preserved.

**Business-semantic equivalence (S), preferred below.** Use the same graph, but retain the O2O qualifier and lifecycle motif labels as edge colors, such as replaces, removed-before-dispatch, partial-settlement, and completion-of-settlement. Preserve event multiplicity, typed E2O incidence, local/external flags, and temporal order. Ignore raw local IDs and irrelevant timestamp magnitudes; keep only their ordering and ties. Equivalence is equality of the canonical colored graph. This is reflexive, symmetric, and transitive. Ties are handled as in T. This is a deliberately fine business-semantic relation: it distinguishes materially different fulfillment and settlement arrangements while treating identifier-renamed executions alike. A coarser business view could deliberately normalize some motifs, but should name that normalization.

## 2. Canonical signatures

A reproducible signature can be made from the S graph as follows:

```python
def semantic_signature(execution):
    G = colored_directed_multigraph()
    for obj in execution.objects:
        G.add_node(obj, color=("object", obj.type, obj.is_external,
                              obj.is_focal_order))
    for i, event in enumerate(execution.events):
        # rank is shared by tied timestamps; never break ties by event ID
        G.add_node(event, color=("event", event.activity, timestamp_rank(event)))
        for obj in event.participants:
            G.add_edge(event, obj, color=("E2O", obj.type, participant_role(event, obj)))
    for rel in execution.o2o_relations:
        G.add_edge(rel.source, rel.target,
                   color=("O2O", rel.kind, rel.qualifier))
    # Encode temporal precedence, not arbitrary ordering within a tie.
    for e1, e2 in ordered_event_pairs(execution):
        if timestamp(e1) < timestamp(e2):
            G.add_edge(e1, e2, color=("before",))
    # Canonical graph labeling returns one serialization for every
    # color-preserving isomorphism class.
    return canonical_label_and_serialize(G)
```

A practical implementation can use a canonical-labeling graph library; a small pedagogical implementation can try every permutation within each node-color class and select the lexicographically smallest serialization. The latter is exact but factorial, so it does not scale. Distinct event nodes remain distinct even when their labels match. Object IDs are used only as temporary node handles and never enter node colors or the final serialization. If a source lacks a relation or qualifier, encode “unknown/absent” consistently rather than guessing it.

## 4. Cluster interpretations

- **S1 — isolated baseline.** Signature: two local items, one package and delivery, one invoice and payment. This is ordinary single-package fulfillment with settlement. It offers a clean baseline for cycle time and conformance measures; the opportunity is straightforward end-to-end monitoring. An order-level flattened event trace represents the broad sequence reasonably, but loses which items went into the package. The cluster is stable under identifier renaming and ordinary ordering repairs; it depends on correct package-item links.

- **S3 — split packages, consolidated delivery.** Signature: two item-specific packages feed one delivery. This can support parallel packing and reduce delivery overhead, while creating a consolidation bottleneck or scan/reconciliation risk at dispatch. A flattened order trace can show two Pack events but cannot reliably preserve which package carries which item or that one delivery carries both. The cluster is stable if the two package objects and their item links are valid.

- **S4 — split shipments and staged settlement.** Signature: two package-delivery pairs, one invoice, then partial and completing payments. It enables early fulfillment of available goods and staged collection; risks include customer confusion, shipping cost, and incorrect “paid” status if a partial payment is mistaken for full settlement. An ordinary event log can preserve counts but often loses package-delivery pairing and payment-to-invoice qualification; flattening by invoice can also merge distinct order logistics. The structural cluster is stable if both payment events are genuine. The exact partial-versus-complete interpretation is less stable if qualifiers are missing or repaired differently.

- **S5 — cross-order logistics sharing.** Signature: a package for the focal Order contains an external item, and an external Order is in the packing/dispatch context. Pooling can improve utilization, but creates ownership, traceability, service-level, and mis-shipment risks. A per-Order flattened log either drops the external item or duplicates shared package activity, obscuring that the package is shared. The cluster is stable only while EXT status and the cross-order links are trusted; repairing the external reference as a local typo could move it toward S1.

- **S6 — cross-order invoice sharing.** Signature: local fulfillment, an invoice connected to the focal and an external Order, and a payment without order-level allocation. Consolidated billing can simplify collection, but obscures revenue attribution, tax/accounting allocation, and which order a payment settles. A per-Order flattening may duplicate the invoice/payment or falsely imply a full local settlement. This is stable if the invoice-to-order links are authoritative; allocation repair can materially change its semantic interpretation.

- **S7 — substitution/removal.** Signature: an initially packed pair, a qualified removal/replacement for one item before dispatch, and a dispatch still involving that item. Substitution can preserve service when inventory changes, but inconsistent package contents or stale dispatch incidence can indicate a control failure. A flat activity trace is particularly poor: it looks like S1 and omits the item-level change. The separate cluster is moderately stable: the dispatch-item incidence is explicit, but its business reading depends on the quality and interpretation of the removal/replacement qualifier.

- **S8 — return and repack.** Signature: first dispatch, return and inspection of one item, then a second package/delivery that replaces the original package for that item. This supports recovery and reshipment, while adding reverse-logistics cost and risks of duplicate fulfillment, refund mismatch, or uncertain customer possession. A flat trace preserves Return/Inspect labels but cannot show that the returned item was repacked and that the second package supersedes the first for that item. This cluster is stable if the return, inspection, and package links are confirmed; the replacement relation may be less stable if inferred rather than recorded.

## 5. Borderline cases

- **X1 versus X2:** Under raw event-row equality they differ because object IDs and Add Item ordering differ. Under A they agree because the labels are the same. Under T and S they agree because the local IDs are renamed consistently and the two same-label Add events have no meaningful internal order beyond the item associations.
- **X1 versus X5:** They agree under A. Under T and S they differ: X5 has external objects and a package/dispatch context crossing Order lifecycles. A deliberately local-only projection that strips external nodes could make them agree, but that projection discards the shared logistics fact.
- **X1 versus X6:** They agree under A and look close under a signature that counts only local objects. They differ under T/S because the invoice has two Order connections and the payment lacks order-level allocation. A structure that filters EXT before canonicalization can collapse the distinction.
- **X1 versus X7:** They agree under A. They differ under T/S because X7's Dispatch event has item participation, and S additionally records the qualified removal/replacement. If a structural definition drops both Dispatch-to-Item incidence and qualifiers, X7 becomes baseline-like; that is defensible for coarse activity monitoring but loses the discrepancy central to the case.
- **X3 versus X4:** A distinguishes them by sequence: X3 has Pack, Pack, Dispatch; X4 interleaves two Pack/Dispatch pairs and has two payments. A multiset-of-labels definition would make them look more alike, but T/S preserve one versus two deliveries and their package mapping, as well as payment multiplicity.
- **X4 versus X8:** A separates them through Return and Inspect, while both have multiple shipments and package events. A coarser “multi-shipment order” semantic category might combine them; S keeps them apart because X8 has a reverse-logistics/repack lifecycle and only one payment, whereas X4 has two settlement events.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

Treat PM4Py’s equivalence key as an exact implementation key over the fields its version serializes, not as a business definition. In the exact-key use relevant here, the key captures the encoded event/activity pattern and object references/types in the selected execution; repeated events and order are preserved when included in that serialization. If raw object identifiers enter the key, two otherwise isomorphic executions such as X1/X2 can split. A key only preserves O2O relations, qualifiers, external flags, or attributes if the implementation includes them; the function cannot infer the narrative qualifiers in this prompt from activity labels alone. Check the installed version’s key construction before assigning semantics to a field.

A safe workflow is to run PM4Py’s exact clustering, then canonicalize each focal-Order neighborhood using the signature from section 2 and aggregate the exact groups by that canonical key. This removes accidental identifier sensitivity while retaining explicitly modeled business structure. When exact equality itself is the audit question—for example, detecting duplicate serialized executions—do not canonicalize away IDs or structure. Exact clusters can also fragment on harmless differences. Conversely, large connected executions can have many objects, making canonicalization costly; use `max_objs` as a guardrail, record what was truncated/skipped, and avoid treating a truncated key as full-execution equivalence.

Executable-looking outline; the small adapter isolates PM4Py return-shape differences, while `semantic_signature` performs custom graph canonicalization:

```python
import pm4py
from collections import defaultdict

LEAD_TYPE = "Order"
raw = pm4py.cluster_equivalent_ocel(ocel, max_objs=500)

def groups_from_pm4py(result):
    # Adapt this small boundary to the installed PM4Py return wrapper:
    # yield (exact_key, members) for each returned exact cluster.
    if hasattr(result, "items"):
        yield from result.items()
    else:
        for i, group in enumerate(result):
            if isinstance(group, tuple) and len(group) == 2:
                yield group
            else:
                yield (i, group)

def focal_order_ids(members, ocel):
    # Convert the version-specific cluster member representation to object IDs.
    ids = member_object_ids(members)
    return [oid for oid in ids if object_type(ocel, oid) == LEAD_TYPE]

semantic_groups = defaultdict(list)
for exact_key, members in groups_from_pm4py(raw):
    for order_id in focal_order_ids(members, ocel):
        graph = order_neighborhood_graph(ocel, order_id, lead_type=LEAD_TYPE)
        # Canonical colors include types, EXT flags, event order/incidence,
        # O2O relation kinds and qualifiers; local IDs are omitted.
        semantic_groups[canonical_graph_serialization(graph)].append(order_id)

# semantic_groups now groups Orders after ID-invariant, business-aware post-processing.
```

The three OCEL access helpers are adapters to the installed PM4Py/OCEL schema, not assumptions that a particular release uses one return wrapper. They should select events connected to the focal Order and the relevant O2O neighborhood, rather than flattening the whole log first.

## 7. Robustness analysis

- **Ignore all O2O qualifiers.** S7 loses the explicit removal/replacement meaning, but remains structurally separate here because Dispatch includes I72 and the other event/object incidence differs from X1. If the repair also removes that dispatch-item link, X7 can join S1. X4 still has two payment events, and X8 retains Return/Inspect and repack events, so their motifs remain distinguishable. This shows why “ignore qualifiers” must not silently mean “erase all item incidence.”
- **Ignore external objects.** Pruning EXT nodes and their incidences makes X5's remaining local package resemble X1, and X6's local invoice/payment resemble X1. They then join S1 if external links are wholly discarded. This may be suitable for local fulfillment throughput, but is unsafe for ownership or financial consolidation analysis.
- **Collapse repeated same-label events.** A label-only sequence may reduce X3's two Pack labels to one, making its projection closer to X1; X4 similarly reduces repeated Pack and Dispatch labels. If only the activity projection is collapsed, the typed and semantic structures do not change: two packages, deliveries, or payments remain. Collapsing event nodes as well would erase precisely the multiplicities that distinguish these executions and is a much stronger data transformation.
- **Treat Pack/Dispatch as partially ordered.** Preserve causal edges from each package's Pack to its corresponding Dispatch, but do not impose a total order between independent package workflows. X4 then admits equivalent interleavings, such as packing both packages before either dispatch, without changing its cluster. It remains distinct from X3 because it has two deliveries rather than one. X8 also remains distinct because its return/inspection conditions the later repack.
- **Treat payment multiplicity as an amount.** No amounts are supplied, so no equality of totals can be asserted. A model that sums payment amounts could merge one- and two-payment cases only if totals and invoice semantics match. X4 still has two deliveries, so it remains distinct under the preferred whole-execution key; a finance-only projection may merge it with a single-payment pattern if the required amount data confirms equality.

## 8. Limitations and recommendation

Use **qualified typed structure** for compliance monitoring when the obligations concern who owns goods, what was dispatched, what an invoice covers, or whether settlement is complete. Use **a curated business-semantic level** for operational segmentation: retain package/delivery/payment multiplicity and cross-order sharing, but define a small number of approved motifs so teams can act on clusters rather than every graph variant. Use **the richest canonical graph plus event times and provenance** for root-cause analysis, where item-level links and qualifiers may explain the failure. Use **activity sequences with selected object-centric counts** for descriptive reporting, clearly labeling the lost detail.

No one relation serves all four purposes. A coarse relation supports readable rates but can hide compliance violations and causes. A fine exact key aids forensic matching but fragments routine cases because of identifiers and incidental structure. Canonical typed signatures provide a reproducible middle ground; the business question should determine which qualifiers and relations remain in the key.
