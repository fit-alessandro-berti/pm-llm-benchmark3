        S_fair = 1  (open_cases(r)/max_open + new_assignments(r)/4)/2

PRIORITY_RANK = {"urgent": 0, "high": 1, "normal": 2, "low": 3}

def eligible(case, res, state):
    lvl = skill_level(res, case.required_skill)
    if lvl == 0:                                return False
    if case.activity == "Security Review":
        if lvl < 3 and res not in {"R7_Gita", "R8_Hugo"}: return False
        if lvl < 3 and supervisor_free(...) is None:      return False
    if case.activity == "Final Approval" and lvl == 1 and not case.prepare_only:
        return False                             # may prepare, not finalize
    if case.priority in ("urgent", "high") and lvl < 2:
        if not supervisor_available(case):       return False
    if case.batched and not (case.priority in ("normal","low")
                             and case.sla_remaining > timedelta(hours=24)):
        return False
    if state.new_assignments[res] >= 4:          return False
    if effort(case, res) > res.hours_today and not schedulable(case):
        return False
    if res.overtime_risk == "high" and not justified_exception(case, res):
        return False
    return True

def score(case, res, state):
    s = {}
    s["sla"]   = urgency(case)                                   # 0..1
    s["skill"] = skill_match(case, res)                          # 0..1
    s["cont"]  = continuity(case, res)                           # 0..1
    s["fair"]  = fairness(res, state)                            # 0..1
    s["train"] = training_bonus(case, res)                       # 0..1
    s["resil"] = resilience(case, res, state)                    # 0..1
    total = (0.30*s["sla"] + 0.22*s["skill"] + 0.18*s["cont"]
             + 0.15*s["fair"] + 0.08*s["train"] + 0.07*s["resil"])
    return total, s      # keep components  human-readable assignment_reason

def assign_batch(queue, state):
    queue = sorted(queue, key=lambda c: (PRIORITY_RANK[c.priority], c.sla_remaining))
    for case in queue:
        cands = [(score(case, r, state), r) for r in state.resources
                 if eligible(case, r, state)]
        if not cands:
            escalate(case, state)          # supervised pair / owner-retained
            continue                        # support / cross-team / SLA escalation
        (best_total, comps), best = tie_break(cands, case)
        plan = build_plan(case, best, state)   # supervisor, shadows, batch window, fallback
        state.commit(case, best, plan,
                     reason=explain(case, best, comps))   # writes assignment_reason
    state.rebalance_training_share(minimum=0.20)          # rule 3 repair pass
    state.assert_invariants()                             # caps + hard rules re-check
    return state.decisions

# 1. Objectives and constraints

## 1.1 Objectives (lexicographic, not a single scalar)

The policy is deliberately **not** framed as finding "the optimal assignment." It is a lexicographic multi-objective policy: satisfy each layer before trading within the next.

| Layer | Objective | Interpretation |
|---|---|---|
| 0 | Safety & compliance | No assignment may violate eligibility/compliance rules, regardless of speed |
| 1 | SLA attainment | Urgent/high cases finish inside deadline with high probability, not just fast starts |
| 2 | *Clean* throughput | First-time-right completions; rework loops are the biggest throughput thief (see C003) |
| 3 | Fair, sustainable workload | Equitable assignment distribution; overtime-risk resources protected |
| 4 | Capability development | 20% of normal/low assignments serve documented training priorities, where SLA risk allows |
| 5 | Continuity of ownership | Case ownership stability; handover costs avoided, especially on complex cases |
| 6 | Resilience | No single point of failure; every urgent case has a named fallback; scarce skills spread |

## 1.2 Hard constraints (safety/compliance — never traded)

- **H1.** Skill level 0 never performs an activity.
- **H2.** Security Review: skill 3, or skill 1–2 **only** under explicit supervision by R7_Gita or R8_Hugo.
- **H3.** Final Approval: finalization requires skill 2–3; skill 1 may prepare but not finalize.
- **H4.** No urgent/high-priority case is assigned to a performer below skill 2 unless a skill-3 supervisor is feasible and named.
- **H5.** Quality Check batching only when priority  {normal, low} and SLA remaining > 24h.
- **H6.** Max 4 new assignments per resource per decision batch.
- **H7.** Every assignment is logged with a machine-readable `assignment_reason` and (for urgent cases) a fallback chain. Unlogged assignments are policy deviations.

## 1.3 Soft constraints (preferences to be traded, with reasons)

- **S1.** Avoid assigning work to overtime-risk = "high" resources (Bruno, David, Iris) — *unless* SLA risk is urgent and no safer alternative exists, or a documented, time-shifted exception is justified (this is where S1 collides with S2; see C012).
- **S2.** 20% of normal/low assignments support documented training priorities, *if* SLA risk stays acceptable.
- **S3.** For high-complexity + high-handover-cost cases, prefer continuity, *unless* the owner is skill 0–1 and supervision is not feasible.
- **S4.** Prefer bottleneck avoidance: don't stack scarce-skill work on one specialist when a qualified peer is free.

## 1.4 Socio-technical design commitments

- **Explainability:** every assignment carries a human-readable rationale plus its score components.
- **Contestability:** supervisors can override; overrides are logged and reviewed, not punished.
- **Data stewardship:** the overtime flag is a *protection signal*, not a performance label, and can be corrected if stale.
- **Supervision is work:** reviewer/supervisor/shadow time is counted against hours, not treated as free.

## 1.5 Known tensions in the data (flagged for governance, not silently resolved)

- C015's note ("training candidate for Eva/Jonas") **contradicts** rule H2: Eva and Jonas have Security skill 0, and supervision under H2 is only permitted for skill 1–2. Hard rule wins this batch; a 01 "shadowing pathway" should be designed.

# 2. Assignment policy

## 2.1 Key mechanism: owner–performer split

The log schema distinguishes `current_owner` from `org:resource`. The policy exploits this: **case ownership** (context, coordination, accountability) and **activity performance** (execution of the next task) can be held by different people. This lets the policy buy skill and capacity without paying the owner-change handover cost (and without incrementing `reassignment_count`). The trade-off — performer-level coordination overhead — is real, is logged separately, and is audited (indicator A13 below). If the audit shows performer-only changes carry the same penalty as owner changes, the mechanism must be revised.

## 2.2 Pseudocode

```text
INPUT:  queue Q, resources R (skills, open_cases, hours_today, OT risk,
        training_priority), rules H1–H7, history H (event log statistics)
STATE:  new_assignments[r], hours_committed[r], coordination_duties[r]

# ---- Phase 0: preparation ----
order Q by (priority_class asc, sla_remaining asc)      # urgent & tightest first
for each case c: estimate effort(c, r) = median service time of activity
                 for resources of r's skill level (from H), scaled by complexity(c)

for each case c in Q:
    candidates = {}
    for each resource r in R:

        # ---------- HARD ELIGIBILITY (H1–H6) ----------
        if skill(r, c.required_skill) == 0: skip
        if c.activity == Security Review and skill < 3
              and supervisor not in {R7_Gita, R8_Hugo}: skip
        if c.activity == Final Approval and skill(r) == 1
              and role != "prepare-only": skip
        if c.priority in {urgent, high} and skill(r) < 2
              and no feasible skill-3 supervisor: skip
        if c.batched and not (priority in {normal, low} and slack(c) > 24h): skip
        if new_assignments[r] >= 4: skip
        if effort(c,r) > hours_remaining(r) and not schedulable_within_sla(c): skip
        if OT_risk(r) == "high" and not (urgent_sla(c) and no_safer_alternative)
              and not logged_time_shifted_exception(c, r): skip

        # ---------- SOFT SCORES (0..1 each) ----------
        U_sla   = urgency(slack(c), priority)     # 1.0 near/at deadline; decays with slack
        S_skill = skill_match(level, c)           # 31.0, 20.8, 10.5 (only if supervised);
                                                  # +bump if specialist required & level 3
        S_cont  = continuity(r, c)                # 1.0 if r is owner AND performs;
                                                  # 0.5 if owner retained, r performs (split);
                                                  # scaled by handover_band × complexity;
                                                  # large penalty if reassignment_count  3+
        S_fair  = 1  (open_cases(r)/max_open + new_assignments(r)/4)/2
                                                  #  0.3 if OT_risk == high
        S_train = 1 if training_priority(r) == c.required_skill
                    and priority in {normal, low} and slack(c) > 3 × effort
                    and supervisor plan exists; else 0
        S_resil = 1  bottleneck_pressure(r, c)   # penalty for stacking a 2nd/3rd item of a
                                                  # scarce skill on one specialist when a
                                                  # qualified peer is free; bonus for team spread

        score = 0.30·U_sla + 0.22·S_skill + 0.18·S_cont
              + 0.15·S_fair + 0.08·S_train + 0.07·S_resil
        candidates[r] = (score, component breakdown)

    # ---------- GUARDS THAT TRUMP SCORES ----------
    if slack(c) < effort + expected queue delay:
        restrict to skill-3 (or approved skill-2) candidates with feasible timing

    if candidates is empty:
        # exception ladder (soft constraints relaxed in order: train  resil  cont  fair;
        # hard rules never): (a) supervised pairing, (b) owner-retained performer support,
        # (c) cross-team borrow with consult, (d) team-lead override (logged),
        # (e) SLA escalation / deadline renegotiation. Never silently drop a case.

    else:
        r*, plan = argmax with tie-breaks:
            (1) larger SLA feasibility margin
            (2) higher continuity score
            (3) lower current open cases
            (4) training support
            (5) deterministic resource id            # auditability, no gaming
        plan may include: supervisor, shadow observer, batch window, fallback chain
        commit(c, r*, plan)
        write assignment_reason = code + component rationale
              (codes: CONTINUITY, SPECIALIST_URGENT, OWNER_RETAINED_SUPPORT,
               TRAINING_SUPERVISED, LOAD_BALANCE, SHADOW_DEV, EXCEPTION_…)
        update hours_committed, new_assignments, coordination_duties

# ---- Phase 1: batch-level repair ----
if training_share(normal/low assignments) < 0.20:      # rule S2
    swap the lowest-risk normal/low case to a supervised training pair
assert all hard rules H1–H6 hold for the committed batch
```

## 2.3 Why this shape

- **Weights are governance-tunable and versioned.** The score is an *argument*, not an oracle: the stored component breakdown is what workers and auditors see.
- **The batch repair pass exists because rule S2 (training) and rule S1 (overtime) can conflict**; the repair resolves it by choosing the safest case for a time-shifted, supervised exception (see C012), rather than by silently dropping either rule.
- **Coefficients are learned, not fixed:** handover-band penalties, urgency curve, and service-time estimates are recalibrated quarterly from the event log (Section 7).

## 4.1 Where the baselines win (stated honestly)

- **First-available** genuinely minimizes initial waiting time and is trivially simple to explain. If all cases were low-complexity with huge SLA buffers and all resources were interchangeable, it would be hard to beat.
- **Specialist-only** minimizes immediate error risk per activity and is the easiest to defend in a one-line audit ("the most qualified person did it"). On C001 and C002 it makes the *same* choices as my policy.
- **The proposed policy** pays real costs: coordination overhead, more complex explanations, dependence on fresh skill-matrix and OT data, and supervision consuming reviewer capacity. Its advantage is a *hypothesis* — that avoided rework, avoided handover penalties, and protected capacity outweigh ~2 hours of coordination — and Section 6 defines the indicators that will confirm or refute it. If the audit shows performer-level changes carry the same penalty as owner changes, the owner–performer split should be curtailed and the policy reverts toward continuity-pure behavior.

# 5. Explanation to workers

> **How we assign work — and why**
>
> When a case needs someone, we ask five questions, in this order:
>
> 1. **Is it safe and allowed?** Some steps — Security Review, Final Approval — have fixed rules about who may perform or finalize them. Those rules never bend for speed.
> 2. **How urgent is it?** Cases closest to their deadline go to people who can start now and have the right experience for that pressure.
> 3. **Does someone already know this case?** If you own a complex case, passing it to someone else costs everyone time — they re-learn context you already have. Sometimes we'll bring in a second person to *do* a specific step while you stay the owner and brief them. That's not a demotion; it's how we get specialist hands on one step without losing your knowledge of the case.
> 4. **Who has room — and protected hours?** Your workload, remaining hours, and your overtime flag all matter. The overtime flag is there to *protect* you, not to label you — if it's out of date, tell your lead and we'll fix it. If you're flagged as at risk and a case isn't urgent, it will go elsewhere, even if you're technically free.
> 5. **Can this be a learning opportunity — safely?** Some lower-risk cases go to people building a skill, always with a named reviewer. If you're asked to supervise or shadow, that counts as real work in your day, and it's time-boxed.
>
> **What you'll see:** every assignment comes with a written reason — "kept with owner, specialist support on the security step," "training assignment, reviewed by Celine," "reassigned to protect David's hours." Nothing is hidden, and nothing here is a ranking of people. Skill levels describe *task fit*, not worth; today's trainee step is how tomorrow's specialist gets made.
>
> **What you can do:** if an assignment looks wrong to you, say so. Your lead can override the recommendation — they just write down why, so we can all learn from it. We review the patterns monthly, with the team, using real outcome data: did deadlines hold, did rework go down, did the load spread.
>
> **What we ask:** keep case notes current (it makes every briefing cheap), and flag a slipping deadline early — early flags are information, not failure.

# 6. Process-mining audit indicators

| # | Indicator | Definition (from the log) | PM4Py hook | Target / alert |
|---|---|---|---|---|
| A1 | Handover frequency | Share of consecutive activity transitions with owner change (owner-level) vs. performer change (performer-level); corridor density in the handover network | `discover_handover_of_work_network`, `save_vis_sna` / `view_sna` | Owner-level , especially complexity > 0.7; investigate any dense new corridor |
| A2 | Reassignment count | Owner changes per completed case; % of cases with count > 2; validate stored `reassignment_count` against computed owner changes | owner-change computation + `get_variants` (loop detection) | % > 2 trending down; alert on any increment to 3 |
| A3 | Skill mismatch | % assignments where performer skill level < policy minimum for that activity/priority (join `org:resource` + `required_skill` with skill matrix) | dataframe join on filtered log | **0%** (hard-rule violations) |
| A4 | Workload distribution | Assignments/day and active cases per resource; coefficient of variation; max per batch | groupby `org:resource` | max  4 per batch; CV declining quarter-over-quarter |
| A5 | Overtime-risk exposure | Count and estimated hours of assignments to OT = high resources, excluding logged exceptions; realized after-hours events | `filter_event_attribute_values` on resource + timestamp analysis | Non-exception exposure  0; every exception reviewed with its outcome |
| A6 | SLA misses / near misses | % activities completed after `sla_deadline`; near-miss = within 10% of deadline; segmented by priority and activity | `insert_case_service_waiting_time`, `filter_case_performance` | Urgent/high misses  0; overall rate  |
| A7 | Rework/appeal after assignment | % cases with Rework Correction or appeal within 7 days of the audited assignment, segmented by `assignment_reason` class (continuity / specialist / supervised-trainee / owner-retained support) | variants + filtering | Re-validate the 1.8× / 1.4× / 3.3h / 2.7h historical coefficients quarterly; supervised-trainee rework  specialist baseline + small margin |
| A8 | Training assignment share | % of normal/low assignments with a TRAINING reason code matching a documented training priority | `assignment_reason` parsing |  20% rolling 4 weeks; also track trainee skill-level progression |
| A9 | Specialist bottleneck | Median waiting before skill-3-only activities (Security, Approval); queue length per scarce skill; top-resource concentration share per activity | `discover_performance_dfg` (edge waiting times), `get_service_time` | Top-resource share < 60% per activity; waiting stable; both security specialists utilized |
| A10 | Deviations from policy | Offline replay of the policy on historical queue snapshots vs. actual assignments; % match; supervisor override rate and override outcomes; missing/invalid `assignment_reason` | replay engine (Section 7) | Match > 90%; 100% of overrides carry logged reasons |
| A11 | Supervision load & quality | Hours in supervisor/shadow roles per resource; rework delta of supervised vs. solo trainee work | `discover_working_together_network` | Supervision counted in workload; no resource > 20% of time supervising |
| A12 | Batching effectiveness | Share of *eligible* Quality Checks actually batched; waiting/SLA delta of batched vs. solo | `discover_batches` | Batching applied to eligible cases without SLA near-misses |
| A13 | Handover-cost realization | Observed waiting/service-time deltas after **owner changes** vs. **performer-only changes** (owner retained) | `insert_case_service_waiting_time`, `discover_performance_dfg` | Tests the core design assumption; if performer-only changes show equal penalty, revise the owner–performer split |

A monthly audit pack (SNA visualizations, KPI table, exception log, deviation list) goes to governance *and* to the team — the same transparency promised to workers.

# 7. PM4Py implementation sketch

```python
import pandas as pd
import pm4py
from datetime import timedelta

# ------------------------------------------------------------------
# 1. Load, format and enrich the event log
# ------------------------------------------------------------------
df = pd.read_csv("service_log.csv")
df = pm4py.format_dataframe(
    df, case_id="case:concept:name", activity_key="concept:name",
    timestamp_key="time:timestamp", resource_key="org:resource")

# propagate case-level attributes to events (priority, SLA, complexity, owner)
for attr in ["case_priority", "sla_deadline", "case_complexity",
             "current_owner", "team", "reassignment_count"]:
    df[attr] = df.groupby("case:concept:name")[attr].transform("first")

skills = pd.read_csv("skill_matrix.csv")    # resource, required_skill, level, training_priority
res    = pd.read_csv("resources.csv")       # resource, team, open_cases, hours_today, overtime_risk
log = pm4py.convert_to_event_log(df)

# ------------------------------------------------------------------
# 2. Learn structural evidence that feeds/calibrates the policy
# ------------------------------------------------------------------
# 2a. Who actually passes work to whom -> continuity & handover corridors (A1)
handover_net = pm4py.discover_handover_of_work_network(log)
pm4py.save_vis_sna(handover_net, "audit/handover_network.png")
# pm4py.view_sna(handover_net)   # interactive inspection

# 2b. Real collaboration pairs -> verify supervision happens, measure its load (A11)
collab = pm4py.discover_working_together_network(log)
pm4py.save_vis_sna(collab, "audit/working_together.png")

# 2c. Emergent roles vs. declared skill matrix (governance check)
roles = pm4py.discover_organizational_roles(log)

# 2d. Cross-training candidates (activity similarity between resources)
res_sim = pm4py.discover_activity_based_resource_similarity(log)

# 2e. Batching behaviour on Quality Check (A12)
batches = pm4py.discover_batches(log)

# 2f. Effort model: service time per (activity, resource) for capacity checks.
#     Requires start/complete timestamps; if only completion timestamps exist,
#     fall back to durations derived from consecutive events.
try:
    svc = pm4py.get_service_time(df, activity_key="concept:name",
                                  resource_key="org:resource",
                                  start_timestamp_key="time:timestamp:start")
except Exception:
    svc = (df.sort_values("time:timestamp")
             .groupby(["concept:name", "org:resource"])["@@duration"]
             .median())

# 2g. Waiting/service per case -> SLA & handover-penalty measurement (A6, A13)
df = pm4py.insert_case_service_waiting_time(df)

# 2h. Where do cases queue? Edge waiting times expose Security/Approval buildup (A9)
perf_dfg = pm4py.discover_performance_dfg(df)

# 2i. Repeated diagnosis loops (C003-style) via variants
variants = pm4py.get_variants(df)

# ------------------------------------------------------------------
# 3. The policy (mirrors Section 2 pseudocode)
# ------------------------------------------------------------------
PRIORITY_RANK = {"urgent": 0, "high": 1, "normal": 2, "low": 3}

def eligible(case, r, state):
    lvl = skill_level(r, case["required_skill"])
    if lvl == 0:                                          return False      # H1
    if case["concept:name"] == "Security Review":                            # H2
        if lvl < 3 and r not in {"R7_Gita", "R8_Hugo"}:   return False
        if lvl < 3 and not supervisor_free(state):        return False
    if case["concept:name"] == "Final Approval" and lvl == 1:               # H3
        return False   # skill-1 may prepare, not finalize
    if case["case_priority"] in ("urgent", "high") and lvl < 2:             # H4
        if not supervisor_available(case, state):         return False
    if case.get("batched") and not (case["case_priority"] in ("normal", "low")
            and case["sla_remaining"] > timedelta(hours=24)): return False  # H5
    if state.new_assignments[r] >= 4:                     return False      # H6
    if effort(case, r) > res.hours_today[r] and not schedulable(case): return False
    if res.overtime_risk[r] == "high" and not justified_exception(case, r, state):
        return False                                                        # S1
    return True

def score(case, r, state):
    s = {"sla":   urgency(case),                    # tighter slack -> higher
         "skill": skill_match(case, r),
         "cont":  continuity(case, r),              # owner bonus x handover band x complexity;
                                                     # large penalty if reassignment_count -> 3+
         "fair":  1 - (res.open_cases[r]/MAX_OPEN + state.new_assignments[r]/4)/2
                     - (0.3 if res.overtime_risk[r] == "high" else 0),
         "train": training_bonus(case, r, state),   # documented priority, buffered, supervised
         "resil": 1 - bottleneck_pressure(case, r, state)}
    total = (0.30*s["sla"] + 0.22*s["skill"] + 0.18*s["cont"]
             + 0.15*s["fair"] + 0.08*s["train"] + 0.07*s["resil"])
    return total, s

def assign_batch(queue, state):
    queue = sorted(queue, key=lambda c: (PRIORITY_RANK[c["case_priority"]],
                                         c["sla_remaining"]))
    for case in queue:
        cands = [(score(case, r, state), r) for r in state.resources
                 if eligible(case, r, state)]
        if not cands:
            escalate(case, state)     # supervised pair / owner-retained support /
            continue                  # cross-team borrow / logged lead override / SLA escalation
        (best, comps), r_star = tie_break(cands, case)
        plan = build_plan(case, r_star, state)   # supervisor, shadows, batch window, fallback
        state.commit(case, r_star, plan,
                     reason=explain(case, r_star, comps))    # writes assignment_reason (H7)
    state.rebalance_training_share(minimum=0.20)             # S2 repair pass
    state.assert_invariants()                                # H1-H6 re-check
    return state.decisions

# ------------------------------------------------------------------
# 4. Audit loop (indicators A1-A13)
# ------------------------------------------------------------------
def audit(df_actual, policy_snapshot):
    kpi = {}
    # A2: owner-level reassignments
    owner_changes = df_actual.groupby("case:concept:name")["current_owner"].nunique() - 1
    kpi["reassignments_gt2_share"] = (owner_changes > 2).mean()
    # A3: skill mismatch on high/urgent work
    j = df_actual.merge(skills, left_on=["org:resource", "required_skill"],
                        right_on=["resource", "required_skill"])
    kpi["skill_mismatch_high_urgent"] = ((j["case_priority"].isin(["urgent", "high"]))
                                         & (j["level"] < 2)).mean()
    # A4: workload spread
    per_res = df_actual.groupby("org:resource").size()
    kpi["workload_cv"] = per_res.std() / per_res.mean()
    # A5: overtime exposure (non-exception assignments to high-OT resources)
    # A6: SLA cohorts via case performance filtering
    breaches = pm4py.filter_case_performance(df_actual,
                                             min_duration=timedelta(hours=24))
    # A8: training share among normal/low assignments
    nl = df_actual[df_actual["case_priority"].isin(["normal", "low"])]
    kpi["training_share"] = nl["assignment_reason"].str.contains("TRAINING").mean()
    # A9: specialist queues from performance DFG edge statistics (Security/Approval)
    # A10: policy conformance — replay decisions on snapshots, diff vs. actual
    #      (predicted resource vs. actual org:resource; flag unexplained gaps)
    # A13: waiting-time delta after owner change vs. performer-only change
    #      (validates the owner-performer split; revisit policy if penalties are equal)
    return kpi
```

**Closing the loop:** the learned evidence (handover corridors, real collaboration pairs, service-time distributions, waiting-time penalties, emergent roles vs. the declared matrix) recalibrates the policy's coefficients each quarter, and the audit indicators decide whether the trade-offs claimed in Section 4 are actually being realized. The policy is therefore not a fixed optimum but an auditable, adjustable compromise — which is precisely what makes it explainable to workers and defensible to auditors.
