## 2. Process-model consistency checks

A robust validation suite must enforce the distinction between predictive models and process conformance. The suite should include:

1.  **Prefix-time availability checks**: Automated queries verifying that every feature used at `t0` has a lineage timestamp strictly less than or equal to `t0`. Features lacking explicit historical timestamps must be flagged as unusable.
2.  **Activity-order feasibility (Footprint/Alignment checks)**: Compare extracted patterns against the normative process model footprint (e.g., "Claim Closed" must always follow "Damage Assessment Completed"). Any pattern violating the footprint (like `Claim Closed -> Damage Assessment Completed`) is flagged as a system ingestion error or sequence ambiguity, not a legitimate process deviation.
3.  **Same-timestamp ambiguity resolution**: When events share timestamps, the system must check for a reliable sequence index. If missing, the events must be treated as concurrent or unorderable. Sequence patterns derived from unorderable events should be suppressed or flagged with a warning.
4.  **Complete-trace information detection**: Analyze feature definitions to ensure they do not aggregate over the entire trace length (e.g., `total_case_duration_hours`, `appeal_seen_anywhere`). A simple check: if the feature value changes when calculated on the prefix vs. the full trace, it is leaking.
5.  **Enabled vs. Future-possible at `t0`**: Declarative checks should map the `t0` state (immediately after `Coverage Check Completed`) to enabled activities (e.g., `Damage Assessment Completed` or `Documents Requested`). Explainers must not assign causal weight to future-possible but not-yet-enabled events as if they were current state drivers.
6.  **Repeated Settlement Decision semantics**: If a trace shows two `Settlement Decision Recorded` events, the validator must check for an intervening `Appeal` event following a `Partial` or `Deny` decision. If absent, the duplicate is a data quality error, not a legitimate semantic event.

*Limitations*: A frequent Directly-Follows Graph (DFG) edge in the event log does not establish a normative rule. Process mining discovery algorithms may yield edges that are artifacts of noisy logging or same-timestamp ordering. The normative model must serve as the ground truth for feasibility.

## 5. Recommendations for explanation validation

1.  **Feature-store design (Priority 1)**: Enforce strict point-in-time correctness. The feature store must reject any feature lacking a valid historical timestamp tied to the event time, preventing future leakage (e.g., `total_case_duration_hours`, `final_handler_team`).
2.  **Historical feature timestamps (Priority 1)**: Mandate that all mutable features (e.g., `risk_score_current`, `same_day_document_count_snapshot`) store their exact state at `t0` to prevent post-hoc overwriting.
3.  **Prefix-only recomputation (Priority 2)**: Refit the model and recompute all global and local explanations using only features available strictly at or before `t0`. Model performance will likely drop, but the resulting explanations will be trustworthy.
4.  **Process-conformance tests (Priority 2)**: Integrate the normative process model as a validation layer. Automatically flag explanations that rely on process-inconsistent sequences (e.g., `Claim Closed -> Damage Assessment Completed`) or future-only states.
5.  **Calibration after feature removal (Priority 3)**: Once leaking features are removed, recalibrate the model's output probabilities. The base rates and SHAP values must be re-estimated from scratch.
6.  **Explanation stability (Priority 3)**: Test explanation stability by perturbing `t0` by a small margin (e.g., ±5 minutes) to ensure feature joins and sequence interpretations do not flip significantly due to boundary conditions.
7.  **Proxy/fairness analysis (Priority 4)**: Conduct a fairness review on `claimant_region`, `claimant_channel`, and `calendar_week`. If these proxies drive disparate impact, they must be removed from operational action paths or adjusted via adversarial debiasing.
8.  **Monitoring for schema or process drift (Priority 4)**: Continuously monitor the event log for schema changes (e.g., new fields, altered timestamp granularity) and process drift (e.g., policy changes that alter the meaning of `calendar_week`), triggering automatic re-validation of the feature lineage.
