# 1. Assumptions and Interpretation

1. **Low-risk/high-risk choice**: represented as an exclusive choice between `Supervisor Review` (low risk) and a concurrent submodel of `Quality Review` and `Regulatory Review` (high risk). The actual risk data condition is not modeled; the control-flow model only preserves the two possible visible routes.

2. **Optional supplier consultation**: represented as an exclusive choice between a silent skip and `Consult Supplier`. This makes consultation optional and at most once. The data condition “supplier involved” is not modeled.

3. **Passing inspection abstraction**: inspection result is not an activity label. A passing inspection is abstracted as the loop choosing its silent exit after `Inspect Trial`. A failing inspection is abstracted as the loop choosing the redo branch `Adjust Parameters`, followed by another `Execute Trial`–`Inspect Trial` iteration.

4. **Duplicate visible labels**: I avoid duplicate visible labels in both models. Duplication would contaminate trace alignment and make counting visible activities ambiguous.

5. **Process-tree approximation policy**: I use a **conservative under-approximation**. The process tree enforces all required release/precedence constraints, but it delays the approval route and supplier-consultation branch until after both `Plan Verification` and `Design Corrective Action` are complete. It therefore excludes some intended traces where approvals or supplier consultation start immediately after `Analyze Root Cause` and overlap verification planning/design.

6. **“May overlap” interpretation**: treated as true concurrency / absence of an order constraint, not merely unspecified order. Concurrent submodels may interleave in any order in a trace.

7. **Completion-time labels**: the model is activity-completion based. An edge `X -> Y` means `X` must complete before `Y` may start.

## 3.3 Approximation and representational limitations

This process tree is intentionally **conservative under-approximating**:

- It correctly enforces `Register Deviation -> {Contain Material, Analyze Root Cause}`.
- It correctly enforces `Contain Material -> Plan Verification`.
- It correctly enforces `Analyze Root Cause -> Design Corrective Action`.
- It correctly enforces that trial starts only after both `Plan Verification` and `Design Corrective Action`.
- It correctly enforces release only after trial loop, approval route, and supplier-choice branch complete.
- It correctly enforces the repeat-until trial cycle with `Adjust Parameters` as redo and silent exit as pass.

The main **representational loss** is:

- The approval route and supplier-consultation branch are placed **after** the first parallel join, so they cannot start immediately after `Analyze Root Cause` and overlap `Plan Verification` or `Design Corrective Action`.
- The supplier-consultation branch therefore cannot overlap verification planning or corrective-action design, even though the narrative allows it.
- The approval route can overlap the trial, but only after `Plan Verification` and `Design Corrective Action` are complete.

This approximation admits no unsafe release behavior. It rejects some intended schedules that start approvals or supplier consultation early.

```text
    tau,
    Consult Supplier
)

TrialLoop = LOOP(
    StrictPartialOrder(Execute Trial -> Inspect Trial),
    Adjust Parameters,
    tau
)
```

## 4.2 Self-contained Python code

```python
from pm4py.objects.process_tree.obj import Operator
from pm4py.objects.powl.obj import (
    StrictPartialOrder,
    OperatorPOWL,
    Transition,
    SilentTransition,
)

# Visible activities
rd = Transition("Register Deviation")
cm = Transition("Contain Material")
arc = Transition("Analyze Root Cause")
pv = Transition("Plan Verification")
dca = Transition("Design Corrective Action")
sr = Transition("Supervisor Review")
qr = Transition("Quality Review")
rr = Transition("Regulatory Review")
cs = Transition("Consult Supplier")
et = Transition("Execute Trial")
it = Transition("Inspect Trial")
ap = Transition("Adjust Parameters")
rm = Transition("Release Material")
ac = Transition("Archive Case")

# Technical silent start and end
start = SilentTransition()
end = SilentTransition()

# High-risk approval route: QR and RR are concurrent and both required
high_risk = StrictPartialOrder([qr, rr])

# Low-risk vs high-risk exclusive choice
approval_route = OperatorPOWL(Operator.XOR, [sr, high_risk])

# Optional supplier consultation: silent skip or CS, at most once
supplier_choice = OperatorPOWL(Operator.XOR, [SilentTransition(), cs])

# Trial loop: do = ET -> IT, redo = AP, exit = silent pass
trial_do = StrictPartialOrder([et, it])
trial_do.order.add_edge(et, it)
trial_loop = OperatorPOWL(Operator.LOOP, [trial_do, ap, SilentTransition()])

# Root strict partial order
powl = StrictPartialOrder([
    start, rd, cm, arc, pv, dca,
    approval_route, supplier_choice, trial_loop,
    rm, ac, end,
])

# Required partial-order dependencies
powl.order.add_edge(start, rd)

powl.order.add_edge(rd, cm)
powl.order.add_edge(rd, arc)

powl.order.add_edge(cm, pv)

powl.order.add_edge(arc, dca)
powl.order.add_edge(arc, approval_route)
powl.order.add_edge(arc, supplier_choice)

powl.order.add_edge(pv, trial_loop)
powl.order.add_edge(dca, trial_loop)

powl.order.add_edge(trial_loop, rm)
powl.order.add_edge(approval_route, rm)
powl.order.add_edge(supplier_choice, rm)

powl.order.add_edge(rm, ac)
powl.order.add_edge(ac, end)
```

## 4.3 Why intentionally unconnected nodes may remain concurrent

In a `StrictPartialOrder`, absence of an edge means no order constraint. The intentionally unconnected pairs are:

- `Contain Material` and `Analyze Root Cause`: both depend only on `Register Deviation`.
- `Plan Verification` and `Design Corrective Action`: enabled by different prerequisites and may overlap.
- `ApprovalRoute`, `TrialLoop`, and `SupplierChoice`: no edges between them, so approvals, supplier consultation, and trial work may overlap.
- `Quality Review` and `Regulatory Review`: inside `high_risk`, both are required and unordered.

Thus the POWL model directly expresses the non-block-structured cross-branch concurrency.

# 6. Semantic Comparison

| Requirement | Intended semantics | Process tree | POWL | Overconstraint or underconstraint | Business consequence |
|---|---|---|---|---|---|
| Two initial work streams | After RD, CM and ARC may proceed independently and overlap. | `+(->(CM,PV), ->(ARC,DCA))` allows CM/ARC overlap. | Edges `RD->CM` and `RD->ARC` with no CM/ARC edge. | Exact in both. | None. |
| Split dependencies into planning/design | PV depends on CM; DCA depends on ARC; PV and DCA may overlap. | Branches enforce `CM->PV` and `ARC->DCA`; branches are parallel. | Edges `CM->PV`, `ARC->DCA`, no PV/DCA edge. | Exact in both. | None. |
| Risk route | After ARC, low risk chooses SR; high risk chooses QR+RR; QR and RR may be concurrent. | XOR/parallel after the first join, so it is after ARC but also after PV/DCA. | `ARC->ApprovalRoute`; `ApprovalRoute = XOR(SR, StrictPartialOrder(QR,RR))`. | Process tree overconstrains the start time of approvals. | Overlap of approval and trial | Approval route does not need to complete before trial starts; approvals may overlap trial. | Second parallel permits approval/trial overlap after PV/DCA. | No edge between `ApprovalRoute` and `TrialLoop`; exact. | Process tree preserves overlap only after PV/DCA, not immediately after ARC. | Some valid early-review schedules are rejected by the process tree. |

| Repeat-until behavior | ET then IT; failure triggers AP and another ET-IT; pass exits; AP never after the passing inspection. | `LOOP(SEQ(ET,IT), AP, tau)` enforces ET-IT cycles and AP only as redo before another cycle. | `LOOP(StrictPartialOrder(ET->IT), AP, tau)` enforces the same. | Exact for control flow in both; pass/fail data condition is nondeterministic. | None, but the decision between pass and fail is not data-driven. |
| Release synchronization | RM requires passing inspection, completed approval route, and CS if selected. | RM occurs after second parallel, so it waits for trial, approval, and supplier choice. | Edges `TrialLoop`, `ApprovalRoute`, and `SupplierChoice` all target RM. | Process tree exact for release synchronization, but constrained earlier starts. POWL exact. | Unsafe release is prevented in both models. |
| Duplicate-label risk | Visible activities should not be duplicated. | No duplicate visible labels. | No duplicate visible labels. | None. | Trace alignment and conformance statistics are not distorted by duplicate labels. |

# 7. Preferred Representation and Validation Plan

## Canonical representation

I choose **POWL** as the canonical representation. The narrative is deliberately non-block-structured: trial waits for PV and DCA, approvals wait only for ARC, supplier consultation waits only for ARC and release, and release synchronizes all three. A process tree forces a block-structured approximation. POWL expresses these cross-branch dependencies directly with partial-order edges.

The process tree remains useful for algorithms that require a tree, but it should be documented as a conservative under-approximation.

## Validation plan

1. **Convert to accepting Petri nets where supported**
   ```python
   net_tree, im_tree, fm_tree = pm4py.convert_to_petri_net(tree)
   net_powl, im_powl, fm_powl = pm4py.convert_to_petri_net(powl)
   ```

2. **Soundness checking of converted nets**
   ```python
   pm4py.check_soundness(net_tree, im_tree, fm_tree, print_diagnostics=True)
   pm4py.check_soundness(net_powl, im_powl, fm_powl, print_diagnostics=True)
   ```
   This checks for deadlocks, proper completion, and dead transitions in the converted nets.

3. **Bounded or sampled playout**
   - Use `pm4py.play_out(powl, ...)` if supported; otherwise play out the converted Petri net.
   - Use a bounded maximum trace length and a large sample size.
   - Inspect sampled traces for expected patterns:
     - CM and ARC may interleave;
     - PV never precedes CM;
     - DCA never precedes ARC;
     - ET never precedes PV or DCA;
     - RM never precedes trial exit, approval completion, or selected supplier completion.

4. **Explicit positive and negative trace tests**
   - Encode the eight witness traces from Section 5 as positive/negative test cases.
   - Use token replay or alignment on the converted Petri nets.
   - Expected for POWL:
     - accept W1–W5;
     - reject F1–F3.
   - Expected for the process tree:
     - accept W1–W4;
     - reject W5 and F1–F3.
   - Document W5 as the intended witness exposing the process-tree approximation.

5. **Silent behavior and duplicate-label checks**
   - Traverse the visible transitions in both models and assert that labels are unique except for `SilentTransition` instances.
   - Generate visible traces and assert that no `tau`/silent label appears.
   - Inspect the loop reachability:
     - `IT` may be followed by either `AP` or silent exit;
     - `AP` may be followed by `ET`;
     - after silent exit, `AP` must not occur.

6. **Limitations**
   - Soundness is necessary but not sufficient for narrative fidelity.
   - Sampled playout cannot prove exhaustive behavior, especially with arbitrary loop iterations.
   - Data conditions for risk, supplier involvement, and pass/fail are not represented in the control-flow model.
   - PM4Py conversion and playout behavior may vary by version, so successful conversion should be treated as evidence to inspect, not proof of exactness.

# 8. Final Self-Critique

1. **Semantic weakness**: The POWL model still abstracts data-dependent choices as nondeterministic control-flow alternatives. It cannot ensure that a low-risk case chooses only `Supervisor Review`, that supplier consultation occurs only when the case data requires it, or that `Adjust Parameters` occurs only after a genuinely failed inspection.

2. **Process-tree weakness**: The conservative under-approximation is safe but materially excludes valid schedules where approvals or supplier consultation start immediately after root-cause analysis and overlap verification planning/design. This may be too restrictive for prescriptive use.

3. **Implementation/validation weakness**: The POWL and process-tree code is written against the PM4Py object API, but I did not execute it here. The exact conversion, loop child ordering, and silent-transition handling should be runtime-checked against the specific PM4Py version used, because POWL conversion semantics can vary.
