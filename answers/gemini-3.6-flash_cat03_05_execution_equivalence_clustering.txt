## 1. Equivalence design space

To cluster object-centric event logs centered on a lead object (`Order`), we define four distinct equivalence relations along the spectrum from pure control-flow sequence to domain-semantic topology.

```
       [Low Semantic Depth / High Abstraction]
                        
                        
   1. Activity-Sequence Equivalence (act)
      • Ignores objects, IDs, quantities, links
                        
                        
   2. Typed Structural Equivalence (struct)
      • Preserves graph topology, local ID isomorphism
                        
                        
   3. Behavioral Trace-Graph Equivalence (beh)
      • Preserves causal partial orders, abstracts concurrency
                        
                        
   4. Business-Semantic Equivalence (sem)
      • Preserves fulfillment motifs, exception loops, boundary markers
                        
                        
       [High Semantic Depth / Operational Relevance]
```

### 1. Activity-Sequence Equivalence ($\sim_{\text{act}}$)
* **Operational definition**: Two executions $X$ and $X'$ are activity-sequence equivalent ($X \sim_{\text{act}} X'$) if and only if the total sequence of activity labels $\langle a_1, a_2, \dots, a_n \rangle$ recorded for $X$ is identical to that of $X'$. All object bindings, multiplicities, and relationships are ignored.
* **Invariants preserved**: Exact sequential ordering and repetition of activity strings.
* **Information discarded**: All object instances, object types, Event-to-Object (E2O) incidence, Object-to-Object (O2O) relationships, O2O qualifiers, and cross-order boundary identifiers (`EXT-*`).
* **Formal properties**: Reflexive, symmetric, and transitive (a valid equivalence relation).
* **Concurrency / Same-time handling**: If two events share a timestamp, they are sorted lexicographically by activity label to yield a deterministic string sequence before comparison.

### 2. Typed Structural Equivalence under Local Identifier Renaming ($\sim_{\text{struct}}$)
* **Operational definition**: $X \sim_{\text{struct}} X'$ if and only if there exists a bi-typed isomorphism function $\pi: \text{Obj}(X) \to \text{Obj}(X')$ such that:
  1. For every object $o$, $\text{type}(o) = \text{type}(\pi(o))$.
  2. $\pi$ maps external boundary markers (`EXT-*`) to corresponding external markers in $X'$.
  3. The time-ordered sequence of events matches, and for each event $e \in X$, the mapped event $e' \in X'$ has the same activity label and the exact set of bound object types and multiplicities: $\{ \text{type}(\pi(o)) \mid o \in \text{E2O}(e) \} = \{ \text{type}(o') \mid o' \in \text{E2O}(e') \}$.
  4. Qualified O2O graph edges match: $(o_1, o_2, q) \in \text{O2O}(X) \iff (\pi(o_1), \pi(o_2), q) \in \text{O2O}(X')$.
* **Invariants preserved**: Event activity sequence, E2O object-type multiplicities per event, O2O relationship topology, O2O qualifiers, and external execution boundary flags.
* **Information discarded**: Specific concrete string identifiers for local objects.
* **Formal properties**: Reflexive, symmetric, and transitive.
* **Concurrency / Same-time handling**: Events occurring at identical timestamps are canonicalized by ordering their structural signatures (activity label + multiset of bound object types).

### 3. Behavioral Trace-Graph Equivalence ($\sim_{\text{beh}}$)
* **Operational definition**: $X \sim_{\text{beh}} X'$ if their causal partial orders (Directed Acyclic Graphs where edges represent shared object life-cycle dependencies) are isomorphic under typed local identifier renaming.
* **Invariants preserved**: Object life-cycle causal paths, E2O object-type multiplicities, O2O qualified topologies, and execution boundary markers.
* **Information discarded**: Concrete timestamp interleavings of independent, non-interfering activities (e.g., whether `Add Item` for Item 1 precedes or follows `Add Item` for Item 2).
* **Formal properties**: Reflexive, symmetric, and transitive.
* **Concurrency / Same-time handling**: Concurrent events lack causal paths between them; they form unconstrained parallel branches in the lifecycle DAG, removing artificial timestamp sorting dependency.

### 4. Business-Semantic Equivalence ($\sim_{\text{sem}}$)
* **Operational definition**: $X \sim_{\text{sem}} X'$ if they share the same high-level operational execution motif across four functional dimensions:
  1. *Logistics Topology*: Single package vs. split package vs. multi-shipment dispatch.
  2. *Process Boundary Isolation*: Isolated execution vs. shared logistics (`EXT` package/item) vs. shared financial billing (`EXT` invoice).
  3. *Lifecycle Exceptions*: Standard straight-through process vs. item substitution/removal vs. return/reinspection/repack loops.
  4. *Financial Settlement*: Single-step full settlement vs. multi-step/partial settlement.
* **Invariants preserved**: Domain-level process motifs, operational risk flags, cross-boundary dependencies, and lifecycle exception patterns.
* **Information discarded**: Minor temporal interleavings, exact item line counts (when structural behavior is identical), and local object renaming.
* **Formal properties**: Reflexive, symmetric, and transitive.
* **Concurrency / Same-time handling**: Invariant to event interleaving; evaluates canonical end-to-end milestone states.

## 2. Canonical signatures

To deterministically evaluate **Business-Semantic Equivalence ($\sim_{\text{sem}}$)** and **Typed Structural Equivalence ($\sim_{\text{struct}}$)**, we construct a reproducible canonical signature. This signature maps an execution to a hashable, human-readable string.

### Signature Construction Logic

```python
import hashlib
from collections import Counter, defaultdict

def compute_execution_signature(events, o2o_links):
    """
    Computes a deterministic canonical signature for an Order-centric execution.
    
    Parameters:
    - events: list of dicts with keys 'activity', 'timestamp', 'e2o' (dict of type -> set of IDs)
    - o2o_links: list of dicts with keys 'src', 'dst', 'qualifier'
    
    Returns:
    - dict containing:
        'struct_sig': Fine-grained typed structural signature
        'sem_sig': Coarse business-semantic signature
    """
    # Step 1: Identify local vs external objects
    all_objs = set()
    ext_objs = set()
    for ev in events:
        for obj_type, obj_ids in ev['e2o'].items():
            for oid in obj_ids:
                all_objs.add(oid)
                if oid.startswith("EXT"):
                    ext_objs.add(oid)

    # Step 2: Build local ID anonymization mapping based on first appearance and type
    type_counters = Counter()
    id_map = {}
    
    # Preserve EXT IDs as boundary flags, map local IDs to canonical placeholders T_1, T_2
    for ev in sorted(events, key=lambda x: x['timestamp']):
        for obj_type in sorted(ev['e2o'].keys()):
            for oid in sorted(ev['e2o'][obj_type]):
                if oid not in id_map:
                    if oid in ext_objs:
                        id_map[oid] = f"EXT_{obj_type}_{oid}"
                    else:
                        type_counters[obj_type] += 1
                        id_map[oid] = f"{obj_type}_{type_counters[obj_type]}"

    # Step 3: Canonicalize Events (E2O)
    canonical_events = []
    for ev in sorted(events, key=lambda x: x['timestamp']):
        act = ev['activity']
        typed_bindings = []
        for obj_type in sorted(ev['e2o'].keys()):
            mapped_ids = sorted([id_map[oid] for oid in ev['e2o'][obj_type]])
            typed_bindings.append(f"{obj_type}:[{','.join(mapped_ids)}]")
        canonical_events.append(f"{act}{{{';'.join(typed_bindings)}}}")

    # Step 4: Canonicalize O2O links and qualifiers
    canonical_o2o = []
    for link in sorted(o2o_links, key=lambda x: (x['src'], x['dst'], x.get('qualifier', ''))):
        src_m = id_map.get(link['src'], link['src'])
        dst_m = id_map.get(link['dst'], link['dst'])
        qual = link.get('qualifier', 'none')
        canonical_o2o.append(f"({src_m})-[{qual}]->({dst_m})")

    struct_str = " | ".join(canonical_events) + " || O2O: " + " , ".join(sorted(canonical_o2o))

    # Step 5: Extract High-Level Business Motifs for Semantic Signature
    pkg_count = len({id_map[oid] for ev in events for oid in ev['e2o'].get('Package', [])})
    deliv_count = len({id_map[oid] for ev in events for oid in ev['e2o'].get('Delivery', [])})
    pay_events = sum(1 for ev in events if ev['activity'] == 'Record Payment')
    
    has_ext_logistics = any(oid.startswith("EXT") for ev in events for otypes in ev['e2o'] 
                            if otypes in ['Order', 'Item'] for oid in ev['e2o'][otypes] if "EXT-OA" in oid or "EXT-IA" in oid)
    has_ext_finance = any("EXT-OB" in oid for ev in events for otypes in ev['e2o'] for oid in ev['e2o'][otypes])
    has_qualifier_removal = any(l.get('qualifier') == 'removed_before_dispatch' for l in o2o_links)
    has_return = any(ev['activity'] == 'Return Item' for ev in events)

    # Classify Motif
    if has_return:
        motif = "RETURN_AND_REPACK"
    elif has_qualifier_removal:
        motif = "ITEM_SUBSTITUTION"
    elif has_ext_finance:
        motif = "SHARED_FINANCE"
    elif has_ext_logistics:
        motif = "SHARED_LOGISTICS"
    elif deliv_count > 1 or pay_events > 1:
        motif = "MULTI_SHIPMENT_PARTIAL_PAY"
    elif pkg_count > 1 and deliv_count == 1:
        motif = "CONSOLIDATED_SPLIT_PACK"
    else:
        motif = "STANDARD_FULFILLMENT"

    sem_str = f"MOTIF:{motif}|PKGS:{pkg_count}|DELIVS:{deliv_count}|PAYS:{pay_events}"

    return {
        "struct_sig": hashlib.sha256(struct_str.encode()).hexdigest()[:12],
        "sem_sig": sem_str
    }
```

## 4. Cluster interpretations

```
                
                          Order Executions (X1-X8)        
                
                                     
         
                                                                
  [Isolated Executions]                                 [Cross-Boundary Executions]
    C1: Standard (X1, X2)                              C4: Shared Logistics (X5)
    C2: Consolidated Split (X3)                        C5: Shared Finance (X6)
    C3: Multi-Shipment/Partial Pay (X4)
    C6: Item Substitution (X7)
    C7: Return & Repair (X8)
```

### Cluster C1: Standard Single-Shipment Fulfillment (`X1`, `X2`)
* **Concise signature**: `MOTIF:STANDARD_FULFILLMENT|PKGS:1|DELIVS:1|PAYS:1`
* **Business behavior**: Perfect straight-through processing. All ordered items are packed into a single package, dispatched in a single delivery, invoiced once, and settled in full with a single payment.
* **Operational risks or opportunities**: Highly efficient execution path. Risk is low; primary opportunity is establishing this cluster as the golden benchmark for automated fulfillment cost and cycle-time calculation.
* **Traditional flattening pitfalls**: A flat order-centric view sees 1 Order, 2 Items, 1 Package, 1 Delivery, 1 Invoice, 1 Payment. A flat item-centric log duplicates package, delivery, invoice, and payment events for each item, artificially inflating event volume by $2\times$ and distorting resource throughput metrics.
* **Data-repair stability**: Highly stable. Standard operational noise rarely alters its core topological isolation.

### Cluster C2: Consolidated Split-Package Fulfillment (`X3`)
* **Concise signature**: `MOTIF:CONSOLIDATED_SPLIT_PACK|PKGS:2|DELIVS:1|PAYS:1`
* **Business behavior**: Warehouse items are packed separately (e.g., due to size, weight, or hazardous material constraints), but consolidated at the loading dock onto a single delivery truck. Single invoice and payment.
* **Operational risks or opportunities**: Increased packing material costs and packaging time; opportunity to optimize box sizing algorithms to reduce split packaging rates.
* **Traditional flattening pitfalls**: Flattening on Delivery merges packages seamlessly, but flattening on Package duplicates the downstream `Dispatch`, `Issue Invoice`, and `Record Payment` events, creating phantom concurrency.
* **Data-repair stability**: Moderately stable. If a data repair routine merges `P31` and `P32` based on shared delivery `D31`, it collapses into C1.

### Cluster C3: Multi-Shipment Partial-Payment Execution (`X4`)
* **Concise signature**: `MOTIF:MULTI_SHIPMENT_PARTIAL_PAY|PKGS:2|DELIVS:2|PAYS:2`
* **Business behavior**: Partial availability fulfillment. Item 1 is packed and shipped immediately. Item 2 is packed and shipped later upon stock arrival. Billing occurs via a single invoice, but the customer pays in two partial installments aligned with deliveries.
* **Operational risks or opportunities**: High logistics overhead (double shipping cost) and cash-flow lag due to partial payment monitoring.
* **Traditional flattening pitfalls**: Unhandled many-to-many relationships cause severe event duplication. Flattening on `Invoice` duplicates dispatch lines; flattening on `Delivery` splits financial settlement into unlinked fragments.
* **Data-repair stability**: Stable; physical dispatches and financial ledger entries prevent accidental collapse into C1 or C2.

### Cluster C4: Cross-Order Shared Logistics (`X5`)
* **Concise signature**: `MOTIF:SHARED_LOGISTICS|PKGS:1|DELIVS:1|PAYS:1`
* **Business behavior**: Co-loading / consolidated fulfillment across customer orders. Package `P51` consolidates items from `O5` alongside external order `EXT-OA` and external item `EXT-IA` to optimize freight capacity.
* **Operational risks or opportunities**: High risk of cross-contamination or mis-delivery across customer orders; opportunity for significant freight cost reduction via joint shipment.
* **Traditional flattening pitfalls**: Filtering the log for `Order == O5` completely drops `EXT-OA` and `EXT-IA`, making `P51` appear underutilized and hiding multi-order dependencies during root-cause delay analysis.
* **Data-repair stability**: Highly sensitive to boundary scoping. Removing `EXT` tags collapses C4 into C1.

### Cluster C5: Cross-Order Shared Financial Billing (`X6`)
* **Concise signature**: `MOTIF:SHARED_FINANCE|PKGS:1|DELIVS:1|PAYS:1`
* **Business behavior**: Consolidated corporate billing. Physical logistics are isolated to `O6`, but `Invoice V61` and `Payment M61` are shared across `O6` and external order `EXT-OB` (e.g., parent account monthly billing).
* **Operational risks or opportunities**: Complex revenue recognition and credit risk allocation. An unallocated payment `M61` risks misapplying credit balances across orders.
* **Traditional flattening pitfalls**: Standard order-level trace filtering either duplicates `V61`/`M61` across two order traces or attributes $100\%$ of the invoice total to `O6`, corrupting financial reporting.
* **Data-repair stability**: Sensitive to accounting adjustments. Allocating payment line items directly to orders splits the shared nodes and reclassifies C5.

### Cluster C6: Item Substitution Execution (`X7`)
* **Concise signature**: `MOTIF:ITEM_SUBSTITUTION|PKGS:1|DELIVS:1|PAYS:1`
* **Business behavior**: Out-of-stock replacement during packing. Item `I71` was originally assigned to package `P71`, but was removed before dispatch (`removed_before_dispatch` qualifier) and replaced by `I72`.
* **Operational risks or opportunities**: High inventory variance risk and picking waste; operational opportunity to track supplier quality or stockout pick-face errors.
* **Traditional flattening pitfalls**: Without reading O2O edge qualifiers, flat event logs treat `I71` as normally dispatched, or lose trace of `I71` entirely if only dispatched items are exported.
* **Data-repair stability**: Vulnerable to relational schema stripping. If O2O qualifiers are dropped, C6 becomes structurally indistinguishable from C1.

### Cluster C7: Return and Repack Execution (`X8`)
* **Concise signature**: `MOTIF:RETURN_AND_REPACK|PKGS:2|DELIVS:2|PAYS:1`
* **Business behavior**: Reverse logistics and re-shipment loop. Item `I82` is delivered, returned via `D81`, inspected, repacked into `P82`, and re-dispatched via `D82`.
* **Operational risks or opportunities**: Extremely costly rework cycle. Customer dissatisfaction risk; opportunity to analyze return reasons and quality defects.
* **Traditional flattening pitfalls**: Creating a flat trace on `Order` mixes forward and reverse logistics into a single linear timeline, making `Pack Package` appear twice without context on which item was returned.
* **Data-repair stability**: Highly stable due to explicit reverse logistics event types (`Return Item`, `Inspect Return`).

### X1 versus X2: Permuted Item Addition Order
* **Equivalence disagreement**: $\sim_{\text{act}}$ and $\sim_{\text{sem}}$ consider X1 and X2 **identical**; an overly strict total-order event-sequence definition considers them **different**.
* **Analysis**: X1 adds `I11` then `I12`. X2 adds `I22` then `I21`. Because both items belong to the same order and are added before packing, the temporal order of item addition is non-causal concurrency. Object-centric behavioral equivalence ($\sim_{\text{beh}}$) maps both to identical causal DAGs. Treating X1 and X2 as distinct clusters represents an over-segmentation artifact caused by arbitrary sequence logging.

### X1 versus X5: Co-Packing External Items
* **Equivalence disagreement**: $\sim_{\text{act}}$ considers X1 and X2 **identical** to X5; $\sim_{\text{struct}}$ and $\sim_{\text{sem}}$ consider X5 **distinct**.
* **Analysis**: At the activity-string level, X5 presents the exact same string sequence: `Create Order` $\to \dots \to$ `Record Payment`. However, `Pack Package` in X5 binds `EXT-OA` and `EXT-IA`. If an engineer strips object parameters during log abstraction, X5 collapses into X1, hiding a shared-freight operation. Domain semantics require separating X5 because co-loading introduces external operational dependencies.

### X1 versus X6: Shared External Invoice and Payment
* **Equivalence disagreement**: $\sim_{\text{act}}$ considers X1 and X6 **identical**; $\sim_{\text{struct}}$ and $\sim_{\text{sem}}$ consider X6 **distinct**.
* **Analysis**: X6 performs standard logistics, but its invoicing and payment events bind `EXT-OB`. Activity-sequence abstraction treats X6 as a normal isolated order. Semantic abstraction recognizes that X6 cannot be analyzed in isolation for credit or revenue audit trails, as payment `M61` settles a consolidated bill across multiple orders.

### X1 versus X7: Silent Item Replacement via O2O Qualifiers
* **Equivalence disagreement**: Standard E2O structure considers X1 and X7 **identical**; qualified relational equivalence ($\sim_{\text{struct}}$ and $\sim_{\text{sem}}$) considers X7 **distinct**.
* **Analysis**: In X7, activity labels and bound object types match X1 (`Order`, `Item`, `Package`, `Delivery`, `Invoice`, `Payment`). Only the O2O edge qualifier `removed_before_dispatch` between `P71` and `I71` reveals that `I71` was pulled and replaced by `I72`. Equivalence relations that ignore O2O edge attributes misclassify X7 as standard fulfillment, missing inventory loss/rework.

### X3 versus X4: Consolidated Delivery versus Split Deliveries
* **Equivalence disagreement**: Coarse delivery-count abstractions might group X3 and X4 as "Multi-Package Orders"; $\sim_{\text{struct}}$ and $\sim_{\text{sem}}$ keep them **distinct**.
* **Analysis**: X3 packs items into two packages (`P31`, `P32`) but dispatches them in a single delivery (`D31`). X4 packs and dispatches them in two separate deliveries (`D41`, `D42`), accompanied by two partial payment steps (`M41`, `M42`). X3 represents warehouse-level package splitting, whereas X4 represents customer-facing multi-shipment split fulfillment.

### X4 versus X8: Multi-Shipment Partial Payment versus Return & Repack Loop
* **Equivalence disagreement**: Multiplicity-only counting (2 Packages, 2 Deliveries) might group X4 and X8; $\sim_{\text{sem}}$ keeps them **distinct**.
* **Analysis**: Both executions contain 2 Package instances and 2 Delivery instances. However, X4 is forward multi-shipment fulfillment (partial availability). X8 is a reverse logistics exception loop (`Return Item` $\to$ `Inspect Return` $\to$ `Pack` $\to$ `Dispatch`). Grouping X4 and X8 based solely on object counts ignores the lifecycle directional semantics of reverse logistics.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

### Information Preserved by PM4Py Key Structure
`pm4py.cluster_equivalent_ocel` constructs graph signatures for connected components in an OCEL graph. By default, it preserves:
1. Multiset of event activity labels.
2. Event-to-Object (E2O) incidence bindings.
3. Connected component object structures.

### Why Raw Object Identifiers Cause Over-Splitting
If raw object string identifiers (`O1`, `I11`, `P11`) are preserved directly without bijective variable anonymization, every single execution trace forms its own singleton cluster. PM4Py addresses this by structural mapping, but raw OCEL graphs with explicit external string IDs or distinct temporal timestamps often fail to cluster isomorphic executions (e.g., X1 and X2) unless timestamps are removed and local IDs are mapped to canonical type-indexed variables.

### Canonicalization and Post-Processing Requirements
To convert raw PM4Py equivalence clusters into business-semantic clusters:
1. **Timestamp Abstraction**: Replace absolute timestamps with relative causal order or partial order graphs.
2. **Local ID Anonymization**: Relabel local object identifiers to type-indexed canonical variables ($O_1, I_1, I_2, P_1$) while preserving explicit flags for external objects (`EXT-*`).
3. **Qualifier Ingestion**: Inject O2O edge attributes (e.g., `removed_before_dispatch`) into the node/edge feature matrix before computing graph isomorphisms.

### When Exact Equivalence is Preferable vs. Coarser Business Clustering
* **Exact Equivalence ($\sim_{\text{struct}}$)** is required for *automated process execution, software auditing, and system verification*, where every structural divergence indicates a software bug or schema violation.
* **Coarser Business Clustering ($\sim_{\text{sem}}$)** is preferred for *executive reporting, operational redesign, and performance benchmarking*, where managers need to group minor variations (e.g., 2 items vs. 3 items in a split package) into unified operational categories.

### Impact of `max_objs` and Large Connected Executions
In large enterprise event logs, cross-order sharing (such as `EXT-OA` in X5 or `EXT-OB` in X6) causes object connected components to expand rapidly. If orders share packages, invoices, or delivery trucks, half the event log can merge into a single massive connected graph (the "spaghetti component" phenomenon). Setting `max_objs` limits component traversal depth, but risks truncating cross-order financial or logistics dependencies.

### Executable Python Pipeline

```python
import pm4py
from pm4py.objects.ocel.obj import OCEL

def cluster_and_canonicalize_ocel(ocel: OCEL, lead_object_type: str = "Order"):
    """
    Clusters an OCEL log using PM4Py equivalence, then canonicalizes 
    and aggregates results into business-semantic clusters centered on Order.
    """
    # Step 1: Run PM4Py's built-in structural clustering
    # Returns a list of OCEL objects, each representing an equivalence class
    equivalent_components = pm4py.cluster_equivalent_ocel(ocel)
    
    cluster_summary = []

    for idx, comp in enumerate(equivalent_components):
        # Extract lead objects of type Order
        lead_objs = [o for o, t in comp.objects_ot.items() if t == lead_object_type]
        
        # Count structural properties
        num_events = len(comp.events)
        activity_set = tuple(sorted(list(set(comp.events['ocel:activity'].tolist()))))
        object_counts = Counter(comp.objects_ot.values())
        
        # Check for external boundary markers
        has_external = any(str(o).startswith("EXT") for o in comp.objects)
        
        # Extract presence of key semantic activities
        has_return = "Return Item" in activity_set
        has_multi_dispatch = comp.events['ocel:activity'].tolist().count("Dispatch") > 1
        
        # Assign Semantic Category
        if has_return:
            sem_category = "RETURN_AND_REPAIR_LOOP"
        elif has_external:
            sem_category = "CROSS_BOUNDARY_SHARED_EXECUTION"
        elif has_multi_dispatch:
            sem_category = "MULTI_SHIPMENT_SPLIT_DELIVERY"
        elif object_counts.get("Package", 0) > 1:
            sem_category = "CONSOLIDATED_SPLIT_PACKAGING"
        else:
            sem_category = "STANDARD_STRAIGHT_THROUGH"

        cluster_summary.append({
            "pm4py_cluster_id": idx,
            "lead_orders": lead_objs,
            "order_count": len(lead_objs),
            "total_events": num_events,
            "object_distribution": dict(object_counts),
            "semantic_category": sem_category,
            "activity_profile": activity_set
        })

    return cluster_summary
```

### 1. Ignore All O2O Qualifiers
* **Impact on assignments**: Execution **X7** loses its defining distinction.
* **Analysis**: In X7, item substitution is encoded solely via the O2O qualifier `removed_before_dispatch` linking `P71` and `I71`. If an ETL pipeline strips O2O attributes, X7 becomes structurally identical to X1 and X2 (`Create` $\to$ `Add` $\to$ `Pack` $\to$ `Dispatch` $\to$ `Invoice` $\to$ `Pay`).
* **Cluster Collapse**: $\{C1, C6\} \to C1$.

### 2. Ignore External Objects
* **Impact on assignments**: Executions **X5** and **X6** lose cross-boundary flags.
* **Analysis**: In X5, ignoring `EXT-OA` and `EXT-IA` removes cross-order package sharing. In X6, ignoring `EXT-OB` removes cross-order invoice sharing. Both executions collapse into standard single-order executions.
* **Cluster Collapse**: $\{C1, C4, C5\} \to C1$.

### 3. Collapse Repeated Same-Label Events
* **Impact on assignments**: Executions with iteration or multi-step activities (**X4**, **X8**) alter structure significantly.
* **Analysis**: Collapsing repeated events reduces `Add Item` $\to$ `Add Item` to a single `Add Item` label. In **X4**, collapsing repeated `Pack`, `Dispatch`, and `Record Payment` events removes the multi-shipment signature, making X4 structurally look like a single-shipment process with two packages. In **X8**, collapsing repeated `Pack` and `Dispatch` masks the repackaging loop, leaving only the presence of `Return Item` and `Inspect Return`.
* **Cluster Collapse**: $C3 \to C2$; $C7$ degrades to a simple return marker without repack structure.

### 4. Treat Pack and Dispatch Order as a Partial Order Rather than Total Order
* **Impact on assignments**: Merges traces that differ only by non-causal event interleavings (**X1** and **X2**).
* **Analysis**: Under total order, if `Add Item(I22)` occurs before `Add Item(I21)` in X2, but `Add Item(I11)` occurs before `Add Item(I12)` in X1, total order strings differ. Under partial-order causality (where independent items have no causal edge between their additions), X1 and X2 map to the exact same partial order DAG.
* **Cluster Impact**: Strengthens $C1$ stability without collapsing distinct business motifs.

### 5. Treat Payment Multiplicity as an Amount Attribute Rather than Structure
* **Impact on assignments**: Alters financial settlement representation in **X4**.
* **Analysis**: In X4, payment settlement is split across two events (`M41` partial, `M42` completion). If the process schema models payments as amount attribute updates on `Invoice V41` rather than distinct `Payment` object creations, the two `Record Payment` events collapse into a single invoice state change.
* **Cluster Collapse**: $C3$ logistics remain multi-shipment, but its financial structure collapses to single-payment.

## 8. Limitations and recommendation

### Tailored Equivalence Recommendations

```

                       Task-Specific Recommendation                          

 Application Objective     Recommended Equivalence Level                    

 Compliance Monitoring     Typed Structural Equivalence (~struct)           
 Operational Segmentation  Preferred Business-Semantic Equivalence (~sem)   
 Root-Cause Analysis       Behavioral Trace-Graph Equivalence (~beh)        
 Descriptive Reporting     Activity-Sequence Equivalence (~act)             

```

#### 1. Compliance Monitoring $\to$ **Typed Structural Equivalence ($\sim_{\text{struct}}$)**
* **Rationale**: Regulatory compliance and financial auditing require complete structural fidelity. Cross-order invoice sharing (X6) or silent item removals (X7) represent high-risk compliance exceptions (e.g., unauthorized bill pooling or unrecorded inventory scrap). Abstracting these away would blind auditors to fraud or segregation-of-duties violations.

#### 2. Operational Segmentation $\to$ **Preferred Business-Semantic Equivalence ($\sim_{\text{sem}}$)**
* **Rationale**: Supply chain managers need actionable operational buckets (e.g., *Standard*, *Consolidated Split*, *Multi-Shipment*, *Cross-Dock Co-Loading*, *Return/Repack*). Semantic equivalence correctly clusters X1 and X2 together while isolating operational anomalies (X3–X8) into distinct optimization categories.

#### 3. Root-Cause Analysis $\to$ **Behavioral Trace-Graph Equivalence ($\sim_{\text{beh}}$)**
* **Rationale**: Investigating delay root causes requires evaluating causal dependency DAGs. Distinguishing true sequential bottlenecks from artificial logging concurrency (like the item addition sequence in X1 vs. X2) prevents analysts from diagnosing non-existent process bottlenecks.

#### 4. Descriptive Reporting $\to$ **Activity-Sequence Equivalence ($\sim_{\text{act}}$)**
* **Rationale**: High-level executive dashboards require simple control-flow summaries. While flawed for object-level mechanics, sequence equivalence provides a quick control-flow snapshot of standard paths vs. exception loops (such as the presence of return steps in X8).

### Why No Single Equivalence Notion Fits All Four Purposes

```
               HIGH 
                                                        Compliance
                                                     (~struct)    
                                                                  
  Structural                          Root-Cause                  
  Fidelity                              (~beh)                    
                                                                  
                       Operational                                
                      Segmentation                                
                        (~sem)                                    
                                                                  
                LOW  Descriptive (~act)                           
                    
                    LOW                                         HIGH
                                Domain Semantics
```

A fundamental trade-off exists between **structural granularity** and **semantic abstraction**:
* **Overly fine equivalences** (like raw graph isomorphism) preserve every local ID variation and timestamp jitter, creating thousands of micro-clusters that overwhelm operational managers and executive reporting.
* **Overly coarse equivalences** (like activity sequence flattening) obscure cross-order dependencies, item replacements, and object-to-object link qualifiers, rendering compliance auditing and root-cause bottleneck analysis ineffective.

Object-centric process mining requires explicitly selecting an equivalence level aligned with the analytical objective: preserving strict relational topology for compliance and causal diagnosis, while leveraging semantic abstraction for operational decision-making.
