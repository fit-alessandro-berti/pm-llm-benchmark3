# 1. Objectives and constraints

## Optimization Objectives (high to low priority)
1. **Minimize SLA risk** – ensure urgent/highSLA cases meet deadlines.
2. **Maintain throughput** – complete cases efficiently without excessive waiting.
3. **Balance workload fairness** – limit new assignments per resource to 4 per batch.
4. **Support skill development** – at least 20% of normal/lowpriority cases should align with documented training priorities.
5. **Preserve continuity & reduce handover cost** – prefer current owners for highcomplexity or highhandover cases unless skill is insufficient.
6. **Mitigate rework & appeal** – avoid reassignments >2 and prevent lowskill handling of highpriority cases.

## Hard (mustsatisfy) Constraints
- **Skilllevel compliance** (rules 2, 6, 7).  
- **Overtime risk** – avoid assigning to highrisk workers unless SLA is urgent and no safe alternative.  
- **Continuity rule for highcomplexity/highhandover cases** (rule 5).  
- **Maximum new assignments per resource** (4).  
- **SLA urgency enforcement** – highpriority cases must be routed to competent or supervised resources.

## Soft (tradeoff) Constraints / Preference Goals
- **Training support** – meet the 20% trainingcase quota if SLA risk remains acceptable.  
- **Reduced reassignments** – aim for 2 reassignments per case, preferring firstavailable but not at the expense of skill compliance.  
- **Balanced workload** – distribute tasks across teams to avoid overload.  
- **Resilience** – avoid specialist bottlenecks (e.g., overloading Security Review specialists).  
- **Explainability** – reasonings must be transparent to workers and auditors.

# 2. Assignment policy

## Pseudocode

```python
def assign_cases(queue, resources, batch_size=4):
    # 1. Filter resources per required skill, apply hard constraints first
    def filter_eligible(resource, skill_required):
        # skill_levels: 0 = not allowed, 1 = trainee, 2 = competent, 3 = specialist
        if skill_required == "Security":
            # rule 6: skill 3 or supervised by Gita/Hugo
            return resource.required_skill >= 3 or (resource.team in ["Risk"] and resource.name in ["R7_Gita", "R8_Hugo"])
        elif skill_required == "Approval":
            # rule 7: skill 2–3
            return resource.required_skill in (2, 3)
        elif skill_required == "Eligibility":
            # all are allowed, but lowskill leads to extra waiting (rule 4)    
            return resource.required_skill >= 1
        elif skill_required == "Diagnosis":
            return resource.required_skill >= 1  # trainees can be supervised
        elif skill_required == "Negotiation":
            return resource.required_skill >= 2
        elif skill_required == "Quality":
            return resource.required_skill >= 2
        elif skill_required == "Rework":
            return resource.required_skill >= 2
        return False

    # 2. Prioritization scoring
    def score_case(case, candidate_resource):
        score = 0
        # SLA urgency weight
        urgency_weight = {"urgent": 5, "high": 4, "normal": 2, "low": 1}[case["priority"]]
        score += urgency_weight * case["sla_time_remaining"] / case["sla_time_remaining"] if case["priority"] in {"urgent","high"} else 0
        
        # Skill match weight
        skill_match = candidate_resource.required_skill - case["required_skill"]
        if skill_match < 0:
            # resource too high for the task (wasteful)
            skill_match = 0
        match_weight = min(3, skill_match)  # 0 = trainee, 3 = specialist for exact match
        score += match_weight
        
        # Continuity / handover cost (rule 5, high-complexity)
        continuity_boost = 0
        if case["complexity"] > 0.7 and case["handover_cost"] > "low":
            if candidate_resource.name == case["current_owner"]:
                continuity_boost = 3
            else:
                continuity_boost = 1
        
        # Overtime risk avoidance
        overtime_penalty = 0
        if resource["overtime_risk"] == "high" and not (case["priority"] in {"urgent"} and candidate_resource.name not in [r for r in resources if r["overtime_risk"]!="high"]):
            overtime_penalty = 5
        
        # Training development (soft)
        trainee_bonus = 2 if case["priority"] in {"normal","low"} and candidate_resource["training_priority"] == case["activity"] else 0
        
        # Load fairness
        workload_penalty = 10 * (candidate_resource["open_cases"] / 10)  # cap at ~10 cases
        
        return score + continuity_boost + trainee_bonus - overtime_penalty - workload_penalty

    # 3. Build candidate list per case, rank by score
    assignments = {}
    for case in queue:
        candidates = [r for r in resources if filter_eligible(r, case["required_skill"])]
        if not candidates:
            raise Exception(f"No eligible resource for {case['activity']}")
        
        # compute scores
        scored = [(r, score_case(case, r)) for r in candidates]
        scored.sort(key=lambda x: x[1], reverse=True)
        
        # enforce hard constraints on top candidates
        best = scored[0][0]
        # enforce max new assignments per resource
        if best["open_cases"] + 1 > batch_size:
            # skip this resource, pick next that respects limit
            best = next(r for r, s in scored if r["open_cases"] + 1 <= batch_size)
        
        # select final resource
        assignments[case["case"]] = best["name"]
        # update open case count (for later fairness check)
        best["open_cases"] += 1
        best["hours_remaining"] = max(0, best["hours_remaining"] - estimate_time(case))
    
    return assignments
```

### Key components explained
- **Eligibility filtering** respects skill rules (2,6,7) and overtime risk (4).  
- **SLA urgency weight** pushes urgent/highpriority cases to competent or supervised resources early.  
- **Skillmatch scoring** rewards exact or higher skill level; lowskill handling incurs penalties to discourage it.  
- **Continuity & handovercost boost** prefers current owner for complex/highhandover cases unless skill insufficient (rule5).  
- **Overtime penalty** blocks highrisk workers unless SLA urgent and no safer alternative (rule4).  
- **Training bonus** encourages trainingpriority assignments for normal/low cases, satisfying the 20% rule (soft).  
- **Workload fairness** caps new assignments per resource (4) and penalizes overload.  
- **Tiebreaking** selects the highestscoring candidate; if still tied, prefers resources with lower remaining hours.  
- **Exception handling** flags cases where no eligible resource exists and triggers manual oversight.

# 5. Explanation to workers

> **Subject: Why Your Next Assignment Looks the Way It Does**  
> 
> We have designed a **dynamic assignment engine** that balances speed, quality, and your development as a professional. Here’s how it works for today’s cases:
> 
> 1. **Skill Fit** – Every case is matched first to a worker who possesses the required expertise. For highstakes tasks like *Security Review* or *Final Approval*, we ensure the skill level is 3 (specialist) or supervised by a specialist (e.g., Gita or Hugo). This keeps our SLA promises and protects our customers.
> 
> 2. **Urgency First** – Cases with tight deadlines (e.g., the *VIP Customer Negotiation* or *urgent Security Review*) jump ahead to workers who can meet them promptly, even if that means a brief supervised handoff.
> 
> 3. **Continuity Matters** – When a case has already been worked on by you, we try to keep you on it unless your skill level is too low for the next step. If it’s borderline, we bring in a supervisor to smooth the transition, reducing the chance of rework.
> 
> 4. **Fair Workload** – No worker receives more than four new cases in this batch. We spread the load across teams (A, B, Risk, Quality) so that nobody is overburdened, especially those flagged with a **high overtime risk**. Those workers are only used for urgent urgent tasks when no safer option exists.
> 
> 5. **Learning Opportunities** – About onefifth of the routine (lowtonormal priority) cases are deliberately assigned to you or your peers to work on *trainingpriority* activities (e.g., Quality Checks for Jonas, Diagnosis training for Amal). These help you grow without jeopardizing SLA.
> 
> 6. **Transparency** – The decision log (available on our dashboard) shows the exact scores the engine used: urgency weight, skill match, continuity boost, overtime penalty, and training bonus. You can see why a case was routed to a particular colleague or why a supervisor was added.
> 
> **What You Should Expect:**  
> - Most of the time you’ll stay with the case you started, especially for highcomplexity or highhandover items.  
> - If a case moves, a supervisor will be clearly listed, and the reason (e.g., “need specialist supervision”) will be in the notification.  
> - Your workload will stay within reasonable limits, and any overtimerisk flags will be logged and monitored by management.
> 
> **Why This Policy?**  
> It respects **legal and contractual SLA obligations**, **ensures fair work distribution**, **promotes continuous skill improvement**, and **maintains system resilience**—all while being fully explainable to you and auditable by our processmining tools.
