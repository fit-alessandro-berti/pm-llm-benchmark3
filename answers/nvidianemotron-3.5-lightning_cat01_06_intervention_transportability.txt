## 6. Candidate Site B intervention

**Modified intervention specification:**

- **Eligibility rules:** Parallel identity and document checks may begin immediately after `Register` **only** for cases where originals are not legally required (38% of volume, i.e., digitally submitted claims). For the 62% requiring originals, `Document Check` waits until `Originals Receipt` is recorded.
- **Concurrent tasks:** For eligible cases, `Identity Check` and (conditional) `Document Check` tasks are created simultaneously after `Register`. `Assessment` waits for both to be complete before starting.
- **Statutory prerequisites remaining mandatory:** `Originals Receipt` before `Document Check` for 62% of cases; `Legal Review` after `Assessment` for 40% of high-value/public cases; `Request Supplement` loop may re-open `Document Check` and `Assessment`.
- **Queue and WIP controls:** Enforce maximum 6 open verification tasks per reviewer (adapted from Site A), with team-level monitoring. Identity pool (4 reviewers) and document pool (7 reviewers) operate under separate caps; assessor pool (3) monitored for inflow from parallel checks.
- **Resource responsibilities:** Identity reviewers start `Identity Check` immediately post-registration for eligible cases. Document reviewers start `Document Check` only after `Originals Receipt` (for 62%) or upon document submission (for 38%). Assessors receive completed verification flags. Legal reviewers handle 40% of cases post-assessment.
- **Legal-review and supplement loops:** After `Assessment`, `Legal Review` initiates for high-value cases. If `Request Supplement` issued, `Document Check` and `Assessment` repeat from the supplemented point. Parallel checks on supplemented cases are paused until re-verification complete.
- **Logging requirements:** All task creation timestamps logged atomically; overlap percentage measured only when both identity and document checks have simultaneous ownership flags (not back-entered). Supplement loops flagged in case audit trail.

**POWL-style partial-order relation set:**

```
Register -> Identity Check
Register -> Originals Receipt
Originals Receipt -> Document Check (when originals legally required)
Identity Check -> Assessment
Document Check -> Assessment
Assessment -> Legal Review (for 40% high-value/public cases)
Legal Review -> Request Supplement
Request Supplement -> Document Check (re-run)
Document Check -> Assessment (re-run after supplement)
Assessment -> Approve
Assessment -> Reject
Approve/Reject -> Notify
```

*Conditional edges*: `Identity Check` and `Document Check` are parallel after `Register` **only** when `Originals Receipt` is not a prerequisite. `Legal Review` and `Request Supplement` branches activate exclusively for the 40% legal-review subset. The partial order preserves all statutory dependencies while allowing concurrent execution where legally and operationally permissible.

**Mechanism vs. implementation failure (218 words):** The pilot separates mechanism failure from implementation failure by manipulating two independent variables: (1) eligibility scope (who gets parallel checks) tests whether the causal mechanism—reducing pre-assessment waiting through simultaneous verification—operates under Site B’s structural constraints; if only digital-only cases improve, the mechanism is conditional on originals-absence, not universal. (2) treatment versions (parallel vs sequential vs parallel + quality gates) test whether observed gains stem from the intended process change or from ancillary implementation factors such as better logging, WIP enforcement, or auditor attention. Version C’s random dual-audit isolates the quality-gate component; if Version A (pure parallel) underperforms Version C, implementation defects (e.g., missed context, back-entry artifacts) are implicated. Process-mining measurements of genuine overlap (validated by atomic timestamps) versus observed overlap distinguish real concurrent execution from system artifacts. Stratum-specific effect estimates reveal effect modifiers (originals requirement, case complexity), while interference controls ensure team-level contamination does not mask true effects. If the pilot shows no median improvement in any stratum, mechanism failure is concluded (the precondition of parallelizability is absent). If improvement appears only with quality gates, implementation failure is diagnosed—the mechanism works but requires fidelity additions. This dual-structure allows targeted expansion, modification, or abandonment.

## 9. Recommendation: conditional go

The Site A parallelization effect is not directly transportable to Site B in unchanged form, but a segmented rollout can test and capture causal learning. What should be transferred: the **eligibility rule** that identity and document checks proceed simultaneously only for digitally submitted cases lacking originals requirements (38% of Volume); the **WIP discipline** of capping open verification tasks at six per reviewer; and the **logging protocol** for atomic timestamps to generate genuine overlap metrics. What should not be copied: simultaneous start for cases requiring originals receipt (62% of cases), ignoring the legal-review supplement loop, and assuming cross-trained reviewer flex as at Site A. The first subgroup to enter the pilot should be **digital-only cases** (38% of volume), where prerequisite barriers are absent and the mechanism from Site A is most likely to replicate. Expected benefits for this subgroup: median cycle-time reduction of 15–25% (from 44h to ~33–37h), genuine overlap increase from ~6% to >60%, and modest rework impact if quality gates are maintained. Risks for the full volume: bottleneck shift to assessment, legal-review supplement loops inflating rework toward Site B’s baseline 17%, and tail worsening (p90) if case-locking prevents real parallelism. Evidence to trigger **expansion** to mixed cases: median improvement 10% in digital stratum, rework increase 3%, and overlap % validated as genuine. **Modification** if assessment queue lengthens >20% or rework crosses 20%: add dynamic WIP caps or pre-assessment capacity buffer. **Abandonment** if legal-review trigger rate exceeds 50% of parallel checks or p90 cycle time worsens by >8% despite gates. The pilot’s transportability analysis (Section 7) will provide the data to decide between these paths.

## 10. Assumption register

1. **Assumption:** Parallel identity and document checks are legal for all digitally submitted cases at Site B.  
   **Why needed:** To justify creating concurrent tasks without breaching statutory sequencing.  
   **How to test:** Review site B’s enabling legislation and confirm no law mandates sequential verification before assessment for digital claims.  
   **Consequence if false:** Unauthorized parallel checks could trigger regulatory penalties or case dismissal; pilot must restrict to cases with explicit legal clearance.

2. **Assumption:** Site B’s legacy case-locking can be mitigated or circumvented during the pilot.  
   **Why needed:** The intervention relies on simultaneous task ownership; locks may enforce sequentiality.  
   **How to test:** Pilot a small cohort with API-enforced task-sharing or manual workarounds logged for compliance.  
   **Consequence if false:** Observed overlap % becomes an artifact of back-entry, invalidating the core transport mechanism; redesign must account for enforced sequentiality.

3. **Assumption:** Role specialization (separate identity/document/assessor/legal pools) does not prevent flexing resources during the pilot.  
   **Why needed:** Site A’s cross-trained reviewers enabled parallelism; Site B’s fixed pools may bottleneck.  
   **How to test:** Monitor pool utilization rates during pilot; temporarily reassign 10% of document review capacity to identity checks in treatment arms.  
   **Consequence if false:** Parallelization increases waiting before assessment, reversing the intended cycle-time gain; pilot must include capacity-adjustment subarms.

4. **Assumption:** The share of digitally submitted claims at Site B (38%) is sufficiently large to power a detectable effect.  
   **Why needed:** Effect size estimates derive from this eligible subset; too small a share risks underpowered results.  
   **How to test:** Audit incoming claim mix for the first two pilot months; confirm digital proportion meets minimum-support threshold (200 cases over 6 months).  
   **Consequence if false:** Pilot cannot detect the transport effect; results inconclusive, leading to unnecessary abandonment or false godecision.

5. **Assumption:** Legal-review supplement loops will not be triggered excessively by parallel checks on eligible cases.  
   **Why needed:** Parallel checks could miss context, prompting supplement requests and rework, negating gains.  
   **How to test:** Track supplement rate in treatment arms versus sequential baseline; aim for 5% increase over baseline 40% legal-review rate.  
   **Consequence if false:** Rework rate climbs beyond 20%, quality deterioration outweighs speed gains; intervention must include mandatory dual-verification for parallel checks.

6. **Assumption:** Queue saturation will not worsen if WIP caps are set at six tasks per reviewer.  
   **Why needed:** Site A’s 6-task limit maintained flow; Site B’s unconstrained pools may respond differently.  
   **How to test:** Daily monitor average queue length per role in pilot arms; compare to baseline 44h median cycle time.  
   **Consequence if false:** Queue buildup lengthens waiting before assessment, eroding the parallelization benefit; pilot must adjust caps dynamically.

7. **Assumption:** Timestamp reliability in Site B’s legacy system can support genuine overlap measurement (not just backentry artifacts).  
   **Why needed:** Site A’s overlap increase from 8% to 71% was partly attributed to improved recording; Site B must verify this.  
   **How to test:** Implement atomic timestamp logging for task creation/completion; audit a sample of overlap flags against task-completion evidence.  
   **Consequence if false:** Overlap % inflates without real concurrent execution, misleading transportability assessment and pilot interpretation.

8. **Assumption:** Case complexity distribution at Site B (48% highcomplexity) will not reverse the transport effect if parallelization is applied indiscriminately.  
   **Why needed:** Complex cases may require more contextual integration, making parallel checks errorprone.  
   **How to test:** Stratify pilot results by complexity flag; confirm median improvement in lowcomplexity subset and null/negative effect in highcomplexity subset.  
   **Consequence if false:** Applying parallelization to all cases increases rework and tail length, producing a net negative transport effect; intervention must restrict parallelization to lowcomplexity/digital claims only.
