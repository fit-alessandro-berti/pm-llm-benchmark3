## 1. Equivalence design space

Let an object-centric execution centered on a lead `Order` object $o^*$ be a tuple $X = (E, O, \tau, \pi_{act}, \pi_{time}, \text{E2O}, \text{O2O}, \text{ext})$, where $E$ is a finite set of events, $O$ is a set of objects typed by $\tau: O \to \mathcal{T}$, $\pi_{act}: E \to \mathcal{A}$ assigns activity labels, $\pi_{time}: E \to \mathbb{R}$ gives timestamps, $\text{E2O} \subseteq E \times O$ encodes event-to-object incidence, $\text{O2O} \subseteq O \times \mathcal{Q} \times O$ encodes qualified object-to-object relations, and $\text{ext}: O \to \{\text{true}, \text{false}\}$ flags external objects (`EXT-*`).

### 1.1 Activity-sequence equivalence ($\sim_{\text{act}}$)
- **Definition**: Let $\langle e_1, \dots, e_n \rangle$ be the sequence of events ordered by $\pi_{time}$ (breaking ties lexicographically by $\pi_{act}$). Define $X_1 \sim_{\text{act}} X_2$ iff $(\pi_{act}(e_1), \dots, \pi_{act}(e_n)) = (\pi_{act}(e'_1), \dots, \pi_{act}(e'_m))$. This is a non-object-centric control-flow baseline.
- **Invariants preserved**: Exact ordered sequence of activity labels and total event count.
- **Information discarded**: All object types, object multiplicities, E2O incidence, O2O topology, O2O qualifiers, and external-object boundaries (`EXT-*`).
- **Equivalence properties**: Reflexive, symmetric, and transitive (equality of tuples over $\mathcal{A}^*$).
- **Concurrency / same-time events**: Simultaneous events are canonically ordered by activity label before comparison (or, in a trace-equivalent variant, grouped into multisets per distinct timestamp) so transitivity is preserved.

### 1.2 Typed structural equivalence under identifier renaming ($\sim_{\text{iso}}$)
- **Definition**: $X_1 \sim_{\text{iso}} X_2$ iff there exist bijections $\psi: E_1 \to E_2$ and $\phi: O_1 \to O_2$ such that:
  1. $\psi$ preserves timestamp order ($\pi_{time}(e_a) < \pi_{time}(e_b) \iff \pi_{time}(\psi(e_a)) < \pi_{time}(\psi(e_b))$) and activity labels ($\pi_{act}(e) = \pi_{act}(\psi(e))$);
  2. $\phi$ preserves object types ($\tau_1(o) = \tau_2(\phi(o))$) and externality ($\text{ext}_1(o) = \text{ext}_2(\phi(o))$), and maps the lead object $o^*_1$ to $o^*_2$;
  3. $(e, o) \in \text{E2O}_1 \iff (\psi(e), \phi(o)) \in \text{E2O}_2$;
  4. $(o_a, q, o_b) \in \text{O2O}_1 \iff (\phi(o_a), q, \phi(o_b)) \in \text{O2O}_2$.
- **Invariants preserved**: Full typed E2O hypergraph, event order, object-type multiplicities, externality flags, and qualified O2O topology up to local alpha-renaming.
- **Information discarded**: Raw identifier strings (e.g., `I11` vs. `I22`) and the intra-event listing order of identifiers of the same type.
- **Equivalence properties**: Reflexive (identity bijections), symmetric (inverse bijections $\psi^{-1}, \phi^{-1}$), and transitive (composition $\psi_2 \circ \psi_1, \phi_2 \circ \phi_1$).
- **Concurrency / same-time events**: Simultaneous events form an unordered set per timestamp; $\psi$ must map events within the same timestamp stratum to one another while preserving each event's activity and E2O neighborhood.

### 1.3 Business-semantic equivalence ($\sim_{\text{sem}}$ — preferred)
- **Definition**: $X_1 \sim_{\text{sem}} X_2$ iff they share the same canonical business-semantic signature $\text{Sig}_{\text{sem}}(X)$ (defined formally in Section 2), which combines: (a) the **stutter-collapsed** activity sequence (consecutive identical activities merged into one phase), (b) the set of `(activity, object_type)` pairs involving external objects, (c) the set of local object-type profiles per activity, (d) non-baseline O2O semantic qualifiers `(src_type, qualifier, tgt_type)`, and (e) coarse outcome multiplicity buckets (`0`, `1`, `multi`) for `Delivery`, `Invoice`, and `Payment`.
- **Invariants preserved**: Lifecycle phase transitions and rework loops, cross-order contamination points (`EXT-*`), E2O role anomalies (e.g., `Item` appearing on `Dispatch`), exception/settlement O2O qualifiers (`replaces`, `removed_before_dispatch`, `partially_settles`), and customer-facing delivery/billing/payment cardinality regimes.
- **Information discarded**: Raw identifiers, item counts (`1` vs. `2` items), consecutive repetitions of identical setup/packing steps (e.g., packing 2 boxes `P31, P32` for a single consolidated delivery `D31`), and exact numerical counts above 1.
- **Equivalence properties**: Reflexive, symmetric, and transitive (kernel of a deterministic function $\text{Sig}_{\text{sem}}$).
- **Concurrency / same-time events**: Simultaneous events are sorted deterministically by `(activity, typed_e2o_profile)` before stutter-collapse; if two concurrent events share the same activity and local E2O type profile, stutter-collapse merges them cleanly.

### 1.4 Exact raw-identifier equivalence ($\sim_{\text{raw}}$ — fourth relation)
- **Definition**: Identical to $\sim_{\text{iso}}$ except $\phi$ is restricted to the identity map on $O_1 = O_2$.
- **Invariants preserved**: Everything in $\sim_{\text{iso}}$ plus raw object identifiers.
- **Information discarded**: Only raw event IDs and exact inter-event wall-clock durations.
- **Equivalence properties**: Reflexive, symmetric, and transitive.
- **Concurrency / same-time events**: Matched within identical timestamp strata using object-ID-sorted event signatures.
- **Role**: Provides the strict forensic ceiling (yielding 8 singleton clusters on X1–X8) and mirrors naive un-canonicalized structural keys.

## 2. Canonical signatures

The preferred $\sim_{\text{sem}}$ canonical signature must be deterministic, invariant to local identifier renaming, and sensitive to business boundaries, O2O qualifiers, E2O role shifts, and delivery/settlement regimes. The Python implementation below computes $\text{Sig}_{\text{sem}}(X)$ directly from raw execution data without relying on local identifier names.

```python
from collections import Counter

BASELINE_QUALIFIERS = {"contains", "packs", "carries", "bills", "settles"}

def bucket_count(n: int) -> str:
    if n == 0:
        return "0"
    if n == 1:
        return "1"
    return "multi"

def compute_semantic_signature(execution: dict) -> tuple:
    """
    execution = {
        "events": [{"ts": int, "act": str, "e2o": {obj_type: [obj_id, ...]}}, ...],
        "o2o": [(src_id, qualifier, tgt_id), ...],
        "obj_types": {obj_id: obj_type, ...},
    }
    """
    obj_types = execution["obj_types"]

    def is_external(oid: str) -> bool:
        return oid.startswith("EXT")

    # 1. Canonical sort for total order and same-timestamp tie-breaking
    def event_sort_key(ev: dict) -> tuple:
        local_types = tuple(sorted(
            t for t, ids in ev["e2o"].items() if any(not is_external(i) for i in ids)
        ))
        ext_types = tuple(sorted(
            t for t, ids in ev["e2o"].items() if any(is_external(i) for i in ids)
        ))
        return (ev["ts"], ev["act"], local_types, ext_types)

    ordered_events = sorted(execution["events"], key=event_sort_key)

    # 2. Stutter-collapsed activity trace & E2O type roles per activity
    stutter_trace = []
    ext_e2o_roles = set()
    e2o_roles_per_act = set()

    for ev in ordered_events:
        act = ev["act"]
        if not stutter_trace or stutter_trace[-1] != act:
            stutter_trace.append(act)

        local_types_in_ev = []
        for otype, oids in ev["e2o"].items():
            has_local = any(not is_external(oid) for oid in oids)
            has_ext = any(is_external(oid) for oid in oids)
            if has_local:
                local_types_in_ev.append(otype)
            if has_ext:
                ext_e2o_roles.add((act, otype))

        e2o_roles_per_act.add((act, tuple(sorted(local_types_in_ev))))

    # 3. Semantic O2O qualifiers (type-abstracted, invariant to local renaming)
    semantic_o2o = set()
    for src, qual, tgt in execution["o2o"]:
        if qual not in BASELINE_QUALIFIERS:
            src_lbl = f"EXT:{obj_types[src]}" if is_external(src) else obj_types[src]
            tgt_lbl = f"EXT:{obj_types[tgt]}" if is_external(tgt) else obj_types[tgt]
            semantic_o2o.add((src_lbl, qual, tgt_lbl))

    # 4. Outcome object-type multiplicity buckets (Delivery, Invoice, Payment)
    type_counts = Counter(
        otype for oid, otype in obj_types.items() if not is_external(oid)
    )
    outcome_profile = (
        ("Delivery", bucket_count(type_counts["Delivery"])),
        ("Invoice", bucket_count(type_counts["Invoice"])),
        ("Payment", bucket_count(type_counts["Payment"])),
    )

    return (
        tuple(stutter_trace),
        tuple(sorted(ext_e2o_roles)),
        tuple(sorted(e2o_roles_per_act)),
        tuple(sorted(semantic_o2o)),
        outcome_profile,
    )
```

Notice how local identifier renaming (`O1` $\to$ `O2`, `I11` $\to$ `I22`, `I12` $\to$ `I21`) never enters the signature, while `EXT-*` prefixes, E2O type shifts (such as `Item` on `Dispatch` in X7), non-baseline O2O qualifiers, and stutter-collapsed lifecycle loops are preserved exactly.

## 4. Cluster interpretations

### `C_STD` — Standard Isolated Single-Delivery O2C (`{X1, X2, X3}`)
- **Concise signature**: `(COAIPPDIIIRP)`, `Ext=`, `Qual=`, `D:1, V:1, M:1`, `Dispatch:{Delivery, Order, Package}`.
- **Business behavior**: An isolated customer order whose items are packed (into one or more warehouse parcels) and consolidated into a single outbound delivery, billed on one invoice, and settled in full by one payment.
- **Operational risks & opportunities**: Low coordination risk; primary opportunity is benchmarking cycle-time SLAs across single- vs. multi-box packing (comparing X1/X2 against X3) without distorting customer-delivery KPIs.
- **Flattening failure**: Flattening on `Item` duplicates `Order`, `Delivery`, `Invoice`, and `Payment` events (convergence/divergence); flattening on `Package` splits X3 into two cases while keeping X1/X2 as one, artificially breaking their equivalence.
- **Repair stability**: Stable under item-order normalization or duplicate `Pack` scan merging; sensitive only if missing `Delivery` IDs are imputed independently per package, which would misclassify X3 as split-delivery.

### `C_SPLIT` — Split-Delivery & Installment Settlement (`{X4}`)
- **Concise signature**: `(COAIPPDIPPDIIIRP)`, `Ext=`, `Qual={partially_settles, completes_settlement}`, `D:multi, V:1, M:multi`.
- **Business behavior**: Backordered or staggered fulfillment where items ship in separate deliveries, followed by consolidated invoicing settled across multiple partial payments.
- **Operational risks & opportunities**: Higher freight cost per order, split-shipment SLA exposure, and prolonged days-sales-outstanding (DSO). Opportunity to match partial shipments with milestone billing.
- **Flattening failure**: Flattening on `Order` loses which `Item` rode in `D41` vs. `D42` and blurs how `M41`/`M42` map to `V41`; flattening on `Delivery` or `Payment` fragments one order into disconnected cases and double-counts order creation.
- **Repair stability**: Stable under timestamp-tie repairs; vulnerable if ETL ETL-aggregation merges `M41` and `M42` into one net payment record, erasing installment structure.

### `C_EXT_LOG` — Cross-Order Logistics Co-Packing (`{X5}`)
- **Concise signature**: `(COAIPPDIIIRP)`, `Ext={(PP,Item),(PP,Order),(DI,Order)}`, `D:1, V:1, M:1`.
- **Business behavior**: Warehouse consolidation where items from two distinct orders (`O5` and `EXT-OA`) share a physical package (`P51`) and delivery (`D51`), while invoicing remains strictly segregated.
- **Operational risks & opportunities**: Opportunity to reduce parcel and carrier spend; risk of cross-order mis-picks, customs/manifest mismatches, and cascading delays if `EXT-IA` holds up `P51`.
- **Flattening failure**: Flattening strictly on lead `Order` `O5` either silently drops `EXT-OA`/`EXT-IA` (making X5 look identical to X1) or, in naive multi-order projections, double-counts `Pack` and `Dispatch` throughput across both orders.
- **Repair stability**: Fragile under naive scoping repairs: filtering events by `Order == O5` without 1-hop `Package` expansion strips out `EXT-*` objects and collapses X5 into `C_STD`.

### `C_EXT_FIN` — Cross-Order Unallocated Co-Invoicing (`{X6}`)
- **Concise signature**: `(COAIPPDIIIRP)`, `Ext={(II,Order),(RP,Order)}`, `D:1, V:1, M:1`.
- **Business behavior**: Physical fulfillment is order-isolated, but billing (`V61`) and settlement (`M61`) aggregate `O6` and `EXT-OB` without order-level payment allocation.
- **Operational risks & opportunities**: Opportunity for B2B statement billing; severe compliance and financial-reconciliation risk because unallocated settlements prevent exact order-level cash application and dispute resolution.
- **Flattening failure**: Flattening to `Order` either hides `EXT-OB` (misstating credit exposure) or attributes the entire `V61`/`M61` amount to both `O6` and `EXT-OB`, inflating recognized revenue.
- **Repair stability**: Fragile if ETL pipelines strip `EXT-OB` during single-order extraction or impute heuristic 50/50 payment allocations that fabricate nonexistent order-level settlements.

### `C_SUB_PRE` — Pre-Dispatch Item Substitution (`{X7}`)
- **Concise signature**: `(COAIPPDIIIRP)`, `Dispatch:{Delivery, Item, Order, Package}`, `Qual={Item:replaces:Item, Package:removed_before_dispatch:Item}`, `D:1, V:1, M:1`.
- **Business behavior**: Both `I71` and `I72` are initially packed into `P71`, after which `I71` is pulled before dispatch and replaced by `I72` (`Dispatch` explicitly records `Item:I72`).
- **Operational risks & opportunities**: Inventory-accuracy drift, undocumented customer substitution complaints, and billing discrepancies if `V71` still charges for `I71`.
- **Flattening failure**: Flattening to `Order` discards the `Item`-level `replaces` and `removed_before_dispatch` links, making X7 indistinguishable from X1; flattening to `Item` breaks the causal substitution link between `I71` and `I72`.
- **Repair stability**: Highly fragile: dropping O2O qualifiers during log export *and* stripping `Item` from `Dispatch` (treating it as noise) collapses X7 directly into `C_STD`.

### `C_RET_POST` — Post-Dispatch Return & Repack Rework (`{X8}`)
- **Concise signature**: `(COAIPPDIRIIRPPDIIIRP)`, `Qual={Package:replaces:Package}`, `D:multi, V:1, M:1`.
- **Business behavior**: Item `I82` from `D81` is returned after dispatch, inspected, repacked into `P82` (replacing `P81` for `I82`), and redelivered via `D82` before invoicing.
- **Operational risks & opportunities**: Reverse-logistics cost, delayed revenue recognition (invoice waits until `D82`), and quality defect signals tied to `I82`.
- **Flattening failure**: Flattening to `Order` hides which item triggered the return; flattening to `Package` splits `P81` and `P82` into unrelated cases, severing the `replaces` rework dependency.
- **Repair stability**: Control-flow skeleton is robust (`Return Item` and `Inspect Return` are explicit activities); however, dropping `P82 replaces P81` removes traceability to the original faulty shipment.

## 5. Borderline cases

- **X1 versus X2**: Under $\sim_{\text{raw}}$, they differ because `O1O2` and `Add Item` arrives in swapped local-ID order (`I11, I12` vs. `I22, I21`). Under $\sim_{\text{act}}$, $\sim_{\text{iso}}$, and $\sim_{\text{sem}}$, they are strictly equivalent because `I11I22, I12I21` is a valid typed isomorphism and `Pack Package` treats items as an unordered set.
- **X1 versus X5**: Identical under $\sim_{\text{act}}$ (both follow `COAIAIPPDIIIRP`) and under a naive local-projection semantics that drops `EXT-*` objects. Separated under $\sim_{\text{iso}}$ and $\sim_{\text{sem}}$ because X5 shares `P51` and `D51` with `EXT-OA` and `EXT-IA`.
- **X1 versus X6**: Identical under $\sim_{\text{act}}$ and identical in physical logistics topology. Separated under $\sim_{\text{iso}}$ and $\sim_{\text{sem}}$ because X6 shares `V61` and `M61` with `EXT-OB` without order-level allocation.
- **X1 versus X7**: Identical under $\sim_{\text{act}}$ and even identical in object counts (`1 Order, 2 Items, 1 Package, 1 Delivery, 1 Invoice, 1 Payment`). Separated under $\sim_{\text{iso}}$ and $\sim_{\text{sem}}$ solely because of E2O role shift (`Item:I72` in `Dispatch`) and O2O qualifiers (`replaces`, `removed_before_dispatch`).
- **X3 versus X4**: Separated by $\sim_{\text{act}}$, $\sim_{\text{iso}}$, and $\sim_{\text{sem}}$ because X3 consolidates `P31, P32` into one delivery and one payment, whereas X4 splits deliveries (`D41, D42`) and payments (`M41, M42`). However, under a coarser *warehouse-packing* equivalence (grouping any multi-package execution where `|Package| > 1`), X3 and X4 would merge.
- **X4 versus X8**: Both contain 2 items, 2 packages (`P*1, P*2`), 2 deliveries (`D*1, D*2`), and repeated `PackDispatch` pairs; thus, a purely multiplicity-based profile (`|Item|=2, |Package|=2, |Delivery|=2`) would cluster X4 and X8 together. $\sim_{\text{act}}$, $\sim_{\text{iso}}$, and $\sim_{\text{sem}}$ separate them cleanly: X4 is planned split-fulfillment with installment payments, whereas X8 is exception-driven reverse logistics (`Return Item`, `Inspect Return`, `P82 replaces P81`) with single settlement.

## 6. Relation to `pm4py.cluster_equivalent_ocel`

In PM4Py, `pm4py.cluster_equivalent_ocel(ocel, object_type="Order")` extracts sub-OCEL executions around the specified lead object type and groups executions that share an exact structural key. Depending on the extraction variant and log structure, the key preserves the exact event-to-object incidence structure, activity labels, object types, and O2O/lifecycle topology of each extracted sub-OCEL.

- **Why raw object identifiers make exact clusters too fine**: If raw or un-canonicalized object identifiers (or order-dependent discovery IDs) leak into structural keys, or if item arrival permutations are not canonically mapped across the full hypergraph, isomorphic executions such as X1 and X2 split into distinct singleton buckets. Moreover, exact structural keys treat X3's extra `Pack Package` step as completely disjoint from X1/X2.
- **Canonicalization and post-processing**: After calling `pm4py.cluster_equivalent_ocel`, each returned sub-OCEL should be post-processed by extracting its events, E2O links, and O2O relations, identifying any `EXT-*` or non-lead-owned objects as external boundaries, and computing `compute_semantic_signature` (Section 2) to merge PM4Py's fine exact buckets into business-semantic clusters.
- **When exact equivalence is preferable**: Exact equivalence ($\sim_{\text{raw}}$ or $\sim_{\text{iso}}$) is preferable during ETL regression testing, deterministic replay, forensic audit trails, and strict conformance checking where a second `Pack Package` scan (X3) or a swapped item arrival sequence (X2) indicates a real system anomaly.
- **Impact of `max_objs` and large connected executions**: When executions are extracted via connected components, shared external objects (`EXT-OA` in X5, `EXT-OB` in X6, or master objects like `Customer` in production logs) bridge hundreds of orders into a single giant "hairball" component. Setting `max_objs` prevents memory blow-ups by bounding or skipping oversized components, or forces analysts toward bounded lead-object projections (e.g., ancestors/descendants). However, truncation around `max_objs` can silently sever `EXT-*` linkages, causing cross-order executions like X5 and X6 to masquerade as isolated `C_STD` orders.

```python
from collections import defaultdict
import pm4py

# Assumes `ocel` is an existing pm4py OCEL object with lead type "Order"
exact_clusters = pm4py.cluster_equivalent_ocel(ocel, object_type="Order")

def sub_ocel_to_dict(sub_ocel) -> dict:
    """Convert a PM4Py sub-OCEL into the normalized input for compute_semantic_signature."""
    events_df = sub_ocel.events
    rel_df = sub_ocel.relations
    obj_df = sub_ocel.objects

    obj_types = dict(zip(obj_df[sub_ocel.object_id_column], obj_df[sub_ocel.object_type_column]))

    e2o_by_event = defaultdict(lambda: defaultdict(list))
    for _, row in rel_df.iterrows():
        eid = row[sub_ocel.event_id_column]
        oid = row[sub_ocel.object_id_column]
        otype = row[sub_ocel.object_type_column]
        e2o_by_event[eid][otype].append(oid)

    events = []
    for _, row in events_df.iterrows():
        eid = row[sub_ocel.event_id_column]
        events.append({
            "ts": row[sub_ocel.event_timestamp].timestamp(),
            "act": row[sub_ocel.event_activity],
            "e2o": dict(e2o_by_event[eid]),
        })

    o2o = []
    if hasattr(sub_ocel, "o2o") and sub_ocel.o2o is not None and not sub_ocel.o2o.empty:
        for _, row in sub_ocel.o2o.iterrows():
            o2o.append((row["ocel:oid"], row["ocel:qualifier"], row["ocel:oid_2"]))

    return {"events": events, "o2o": o2o, "obj_types": obj_types}

semantic_clusters = defaultdict(list)
for exact_key, sub_ocels in exact_clusters.items():
    for sub_ocel in sub_ocels:
        exec_dict = sub_ocel_to_dict(sub_ocel)
        sem_sig = compute_semantic_signature(exec_dict)
        semantic_clusters[sem_sig].append((exact_key, sub_ocel))
```

## 7. Robustness analysis

1. **Ignore all O2O qualifiers**:
   - **Impact**: `C_SUB_PRE` (X7) loses `replaces` and `removed_before_dispatch`, though it stays separate from `C_STD` as long as `Item:I72` on `Dispatch` is retained; if E2O `Item` on `Dispatch` were also pruned, X7 would silently merge into `C_STD`. `C_SPLIT` (X4) loses `partially_settles` / `completes_settlement` but stays separate via multi-delivery and multi-payment structure. `C_RET_POST` (X8) loses `P82 replaces P81` yet stays separate via `Return Item` and `Inspect Return`.
2. **Ignore external objects**:
   - **Impact**: If `EXT-*` objects are dropped altogether (naive single-order extraction), X5 and X6 both lose their external touches and collapse directly into `C_STD` (`{X1, X2, X3, X5, X6}`). If `EXT-*` objects are retained but their `EXT` flag is ignored, $\sim_{\text{iso}}$ still isolates X5 and X6 (due to 2 `Order` objects), whereas $\sim_{\text{sem}}$ (which ignores `Order` multiplicity when `ext_e2o_roles` is empty) merges X5 and X6 into `C_STD`.
3. **Collapse repeated same-label events**:
   - **Impact**: Under $\sim_{\text{act}}$, X3 merges into `A1_Linear7` (`{X1, X2, X3, X5, X6, X7}`). Under $\sim_{\text{sem}}$, consecutive repeats are *already* collapsed, so clusters do not change—confirming that $\sim_{\text{sem}}$ is natively robust to consecutive event-stuttering (e.g., multi-scan `Add Item` or `Pack Package`). However, globally collapsing non-consecutive repeats would erroneously flatten X4's and X8's second `PackDispatch` cycle.
4. **Treat `Pack` and `Dispatch` order as a partial order**:
   - **Impact**: In X4, the two branches `Pack(P41)Dispatch(D41)` and `Pack(P42)Dispatch(D42)` are causally independent; partial-order equivalence would properly equate X4 with an interleaved variant `Pack(P41)Pack(P42)Dispatch(D41)Dispatch(D42)`. Meanwhile, X3 remains distinct from X4 because `Dispatch(D31)` causally depends on *both* `P31` and `P32`.
5. **Treat payment multiplicity as an amount attribute**:
   - **Impact**: `M41` and `M42` in X4 collapse into a single settled `Invoice` state (`Payment=1`). While X4 still remains distinct from X3 (due to 2 deliveries) and X8 (due to no return activities), financial installment risk disappears from the cluster signature.

## 8. Limitations and recommendation

No single equivalence relation serves every analytical purpose because abstraction always trades structural fidelity for interpretability:

- **Compliance monitoring  $\sim_{\text{iso}}$ (Typed structural equivalence)**: Compliance requires detecting unauthorized substitutions (`Item` in `Dispatch` and `removed_before_dispatch` in X7), cross-order invoice co-mingling (X6), and unapproved split shipments (X4) without being flooded by harmless local ID differences (X1 vs. X2).
- **Operational segmentation  $\sim_{\text{sem}}$ (Preferred business-semantic equivalence)**: Operations teams need actionable cohorts—grouping standard single-delivery orders (`C_STD`: X1–X3) together while isolating co-packing (`C_EXT_LOG`), co-billing (`C_EXT_FIN`), split fulfillment (`C_SPLIT`), pre-dispatch rework (`C_SUB_PRE`), and post-dispatch returns (`C_RET_POST`).
- **Root-cause analysis  $\sim_{\text{raw}}$ (Exact raw-identifier trace equivalence, nested inside $\sim_{\text{iso}}$)**: Diagnosing *why* `I71` was removed in X7 or *which* package (`P41` vs. `P42`) delayed X4 requires preserving exact object identities, arrival permutations, and wall-clock timestamps.
- **Descriptive reporting  $\sim_{\text{act}}$ (Activity-sequence equivalence, paired with boundary caveats)**: High-level process-map throughput and UI-step telemetry benefit from $\sim_{\text{act}}$'s simplicity, provided analysts explicitly annotate that shared logistics (X5), shared billing (X6), and silent substitutions (X7) are invisible at the activity-label level.

Combining $\sim_{\text{sem}}$ for cohort discovery with drill-down into $\sim_{\text{iso}}$ and $\sim_{\text{raw}}$ avoids both the blindness of activity-only clustering and the combinatorial fragmentation of raw object identifiers.
